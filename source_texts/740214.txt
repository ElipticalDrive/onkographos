We can build an anti-interference volume directly in place_on_faces() using ps_face_region_loop_shells(), which makes a face-polygon volume that respects the edge dihedrals and allows an inset boundary. We could have the same thing for edges and vertices.
A reasonable use-case for an edge is this: on each edge, we want a 5mm wide (at edge height) cutter that can intersect a (poly-centred?) sphere, so as to create a spherical frame model. We can do this for faces, by intersecting a sphere with the loop shell, but not for edges. Naively, this seems like a similar conceptual area to chamfering. Edge-based volume for place_on_edges() #266
A use case for a vertex should be similar, in terms of a vertex figure construction. Vertex-based volumes for place_on_vertices() #267

Question: now that Issue #209 is complete, what now?
Claude replied:
Good question to ask before merging settles the shape of things — I read #264 (it's brand new, no commits against it yet). Short answer: yes, closely related, but I'd be careful not to treat #209 as "already solved most of #264." It solved one specific instance of a pattern #264 needs generalized twice more, and it also dodged the hardest part of #264 by staying inside a single face's flat plane.
What #209 actually established, reusable as-is
The abstract/realized vertex figure (ps_vertex_figure, ps_vertex_figure_points_from_raw) is genuinely the right shared primitive for #264 too — it doesn't know or care that it was built for truncate/rectify caps or face-region clipping, it just turns "a vertex plus some candidate points on rays from it" into a flat, principled realization. Anywhere #264 needs "where does this element's claimed region stop and the neighboring element's begin," that's the tool.
The pattern #209 used is also the right one to generalize: don't rebuild the region from scratch, take an existing region-building system and inject an extra clipping constraint derived from a neighboring element's geometry. #209 did that for face-vs-face at a shared high-valence vertex. #264 needs the same move made twice more — vertex-vs-edge handoff, and edge-vs-face handoff — which is a generalization of the pattern, not a re-application of the same code.
The part #209 didn't have to solve, and #264 will
face_regions.scad's whole machinery — ps_face_arrangement, the projected span lines, the loop-shell construction — lives inside one face's flat local 2D plane. That's why #209's fix could be "add one more line to the arrangement." An edge touches two faces; a vertex touches N. There's no single flat plane an edge or vertex region naturally lives in, so the 2D-arrangement trick doesn't carry over directly — a vertex "node" or edge "rod" region is inherently a 3D construction (or a set of per-face 2D slices that get stitched together across the dihedral). That's the real scope jump in #264, and I'd flag it explicitly rather than let it hide behind "it's the same vertex-figure stuff."
Concrete starting point for the edge case
The issue's own instinct — "similar conceptual area to chamfering" — checks out directly in the code. poly_chamfer's edge_cycles already build, per edge, a six-point band face: [v0, s_dir_v0, s_dir_v1, v1, s_opp_v1, s_opp_v0] — the two original edge endpoints, plus one inset point from each adjacent face at each end. That's already most of a rod cross-section skeleton. What it's missing for #264's use case is exactly the thing #209 just built: right now it runs all the way to the literal original vertex at both ends; a proper rod needs to stop short and hand off to a vertex node volume instead, using the vertex figure to decide where that handoff plane sits — the same "stop at a neighbor-derived boundary, not at the raw vertex" move #209 made for faces. So I'd start the edge case from chamfer's existing construction and cap it with a vertex-figure-derived plane at each end, rather than building it from face_regions.scad.
The vertex "node" case is the genuinely new problem
Be careful here not to conflate two related-but-different things: the vertex figure realization (flatten the local neighborhood into a cap plane — solved, reused everywhere now) versus the vertex node volume (the actual 3D solid the vertex owns, bounded by where it hands off to each incident edge's rod and each incident face's plate). The first gives you the right topology and the right per-edge handoff distance; it doesn't by itself give you the node's shape. That's closer to a small Voronoi-cell-style construction around the vertex, bounded by the incident edges' rod-boundary planes and the incident faces' own dihedral geometry. Worth treating as its own design problem rather than assuming "we have the vertex figure, so the node falls out."
On the sphere-intersection use case specifically — that shouldn't need special handling once edge/vertex regions exist as ordinary solids: ps_face_region_loop_shells already supports this today only because it hands back a normal CSG-able solid that the caller intersects with a sphere externally, not because of anything face-specific. Same should be true for free once an edge/vertex region builder produces something loop-shell-shaped.
One dependency worth flagging now rather than later
If the edge-rod construction leans on the same face-offset/bisector-inset machinery chamfer uses (_ps_face_inset_bisector_2d), the reflex-dihedral assumption I flagged back at the very start (item 6a — it implicitly assumes a convex/non-reflex dihedral, still untouched) stops being a "matters once concave sources are in scope" footnote and becomes directly load-bearing, since a rod's cross-section at a concave edge needs a well-defined outward direction and the bisector math doesn't currently guarantee one. Worth a quick sanity check against a concave test case before this goes far, rather than discovering it the way the miter double-inset got discovered.
If I were sequencing this, I'd split #264 into two issues rather than one — edges (extend chamfer's skeleton, cap with vertex-figure handoff planes) and vertices (genuinely new node-volume construction) — and do edges first, since it's an extension of something that already exists rather than a new shape family.
