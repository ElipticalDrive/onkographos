Deferred from the end-of-phase-1 render review.
The idea
ChunkArena::prepare builds the draw list in NodeId order. For opaque geometry, sorting the visible set front-to-back instead would let early-z reject occluded fragments before shading them.
Why it is deferred
The scene is submit-bound, not fragment-bound. At radius 64 it runs at ~3,800 FPS with ~0.10 ms of CPU per frame; the GPU is not spending its time shading occluded fragments.
Worse, the work lands in the wrong place: sorting ~1,341 entries per frame would add to the cull, which is already 13% of CPU/frame (see #130 for that measurement). So the change costs measurable CPU to save GPU time that is not currently the constraint.
When to revisit
When the frame becomes fragment-bound — a higher resolution, a heavier fragment shader, transparency, or any post-processing chain. The signal to look for is GPU time dominating while CPU/frame stays flat.
Pair it with #42 (occlusion culling) rather than treating it as independent: both are answers to overdraw, and it is worth knowing which one the profile actually asks for before building either.
Do not build this on the reasoning that front-to-back is generally good practice. It is, for scenes that are fragment-bound. Measure first.
