Summary
This PR incorporates Hilbert ordering as a second space-filling curve option to the BVH
Adds a Spin space-filling curve example that generates random points in the unit square, sorts them along a space-filling curve (Morton or Hilbert) and then generates Blueprint meshes connecting the sorted points.
Figures
Here are some figures generated from the examples using 1000 random points on a 32x32 grid:
```
> ./examples/spin_space_filling_curves_ex                                  \
           --dimension 2 --order {morton,hilbert}                          \
           --level 5 --num-points 1024 --output ${order}_level_5
```

It seems like this dispatch here is mostly to account for the case where someone has defined a custom BVH implementation, such as the one in the test which inherits from axom::spin::policy::LinearBVH<double, 2, axom::SEQ_EXEC> (at least this is my understanding). If that person had written their own 4-argument definition for buildImpl, then that definition hides the 5-argument overload. Without this dispatch, you'd get a compiler error trying to call initialize(), since it'd pass five arguments to buildImpl.
Is that actually something that people are doing and/or would get caught by if this dispatch were removed? To some extent, it feels odd to me that we have to have a compile time branch on what is, for all of our own BVH implementations at least, a purely run-time decision. Not to mention, if this hypothetical BVH power-user called setOrdering( hilbert ), their code would fail out during BVH initialization anyway.
Unfortunately I don't think just declaring it an API change would actually get rid of that much code (just this dispatch and the supportsOrdering concept), but it's worth thinking about.

I think it's specifically part of an effort to minimize the changes to initialize() and build() to preserve the kind of backwards-compatibility that I talked about in my other comment. More generally, since order is a policy-specific parameter (theoretically we could have a BVH policy which doesn't use a concept of ordering), I think it makes sense as a separate setter instead of an argument to initialize().
On a more personal level, I find setting keyword arguments like this to be kind of tedious in C++. I'm currently working on a feature which defines a new policy for BVH construction based on bucketing input primitives, I always get annoyed at having to recall "does the bucket size parameter go first or does the ordering? If bucket size goes second, what's the default value for ordering so I don't overload it wrong?" In the absence of some formal PolicyParameter struct which tells the BVH-level what to do with each policy-level parameter, having the setting here makes sense.

// Build a BVH over point boxes in input order.
template <int DIM>
void buildBVH(const Input& params, const Field<Point<DIM>>& positions, axom::spin::BVH<DIM>& bvh)
{
using Box = typename axom::spin::BVH<DIM>::BoxType;
Field<Box> boxes(positions.set());
for(const auto i : *positions.set())
{
boxes[i] = Box(positions[i]);
}
bvh.setScaleFactor(1.);
if(bvh.initialize(boxes.data().view(), boxes.size(), {.ordering = params.order}) !=
axom::spin::BVH_BUILD_OK)
{
throw std::runtime_error("Failed to build the point BVH");
}
}
