Summary
Add support for cameras mounted sideways or upside down through a global clockwise output rotation setting.
Images, CameraInfo, optical TF frames, detections, tracked features, and RGBD point clouds follow the selected orientation. Stereo matching and alignment remain in native coordinates; rotation occurs afterward and before inference or feature tracking. Pixel rotation runs on device, with metadata correction preserving consistent calibration and spatial coordinates.
Also correct decimated output sizing, preserve acquisition timestamps in Features3D, guard invalid feature coordinates, and handle rotated stereo baselines in WLS depth conversion.
Related issues
None.
Compatibility and configuration
Add read-only driver.i_output_rotation_deg: 0 (default), 90, 180, or 270. Restart the driver to change it.
Add config/mounting.yaml with an example 180° RGBD configuration.
Topic names and message types remain unchanged. Enabled rotation adds _rotated optical frames and corresponding static transforms. Quarter turns swap image width and height.
Default behavior remains unchanged; no migration is required.
Thermal pipelines require rotation 0. Rotated output also rejects unsupported automatic full-resolution output, host-decoded segmentation, and tilted-sensor distortion.
RVC2 color/mono rotation resamples pixels and can substantially reduce throughput; RAW16 depth rotation remains exact. Encoded output must satisfy the encoder’s dimension constraints.
Add test dependencies: ament_cmake_gtest, python3-numpy, and tf2_msgs.
Testing
ROS distribution and OS: ROS 2 Kilted, Ubuntu 24.04.
DepthAI library version: Installed DepthAI 3.10.0.
Camera models and connections: OAK-D-PRO-W over USB SuperSpeed; OAK4-D-W over PoE.

What changed in this PR
This PR adds support for mounting OAK cameras sideways or upside‑down via a new global, read‑only driver.i_output_rotation_deg parameter (0/90/180/270, clockwise). When enabled, pixel rotation happens on device (via ImageManip/Script) after native stereo matching/alignment and before inference or feature tracking, while calibration metadata (K/P/R/D, ROI, binning), optical TF frames, detections, tracked features, and RGBD point clouds are rotated consistently. The core math lives in a new header‑only depthai_bridge::OutputRotation (unit‑tested) and a device‑side sensor_helpers::OutputRotation wrapper. Several correctness fixes accompany the feature: decimated stereo output sizing, raw‑image buffer trimming to stride*height, FFMPEG/encoded dimensions from the output frame, fisheye distortion model propagation, Features3D timestamp/bounds handling, and WLS baseline handling for rotated projection matrices.
Changes:
New OutputRotation abstractions (bridge math + device pipeline helper) and RotatedInput for rotated NN/spatial inputs, wired through img_pub, stereo, rgbd, sensor_wrapper, camera, and detection nodes.
Guards rejecting rotation for unsupported paths (thermal, host segmentation, full‑resolution auto output, tilted‑sensor distortion) plus a static TF broadcaster publishing _rotated optical frames.
Supporting fixes in ImageConverter, stereo_param_handler decimation, wls_filter, features_3d, and extensive unit/hardware tests + config/mounting.yaml.
