Motivation
Consider this compute shader:
```
RWTexture2D<uint> outputTexture;
[shader("compute")][numthreads(1,1,1)]
void main() { InterlockedAdd(outputTexture[uint2(0,0)], 1u); }
```
On CUDA/PTX the compiler silently emitted invalid code:
```
uint _S1 = atomicAdd(globalParams_0->outputTexture_0[make_uint2(0U, 0U)], 1U);
```
outputTexture_0 is an opaque CUsurfObject, so NVRTC rejects it:
```
error : no operator "[]" matches these operands
        operand types are: CUsurfObject [ uint2 ]
```
SPIR-V handles the same source correctly (OpImageTexelPointer + OpAtomicIAdd). This PR makes the atomic work on CUDA/PTX for the supported operation/type/shape combinations described below, and diagnoses the unsupported combinations it can identify — subject to the documented format-through-indirection limitation (see Known limitation / #12737). (#12636)
Proposed solution
CUDA has no C-level atomic on a CUsurfObject, but PTX has the sured
(surface-reduction) instruction: an atomic read-modify-write against a surface
texel with no result register. Slang now lowers the result-discarding
InterlockedAdd / InterlockedMin / InterlockedMax / InterlockedAnd /
InterlockedOr on a scalar (or single vector-component) integer texel of a
1D/2D/3D RWTexture to sured, via a family of inline-PTX helpers in the CUDA
prelude — for the supported operation/type combinations in the matrix below (in
particular add/min/max at 32- and 64-bit, but and/or at 32-bit only).
The operations sured cannot express keep the E41405 diagnostic (see Fallback
below).
This is the principled layer because the atomic-on-texel IR shape is canonical
and correct — SPIR-V consumes exactly this shape, and slang-ir-validate.cpp's
isValidAtomicDest accepts an IRImageSubscript atomic destination. The only
gap was that the CUDA emitter had no lowering for it; we add that lowering rather
than reshaping the IR.
The sured matrix
Empirically, ptxas accepts these sured.b.<op>.<geom>.<ctype> combinations
(geom ∈ {1d, 2d, 3d}):
op
channel types
notes
add
u32, u64
sign-agnostic
min/max
u32, s32, u64, s64
signedness matters
and/or
b32
64-bit bitwise sured is rejected by ptxas
xor has no native sured form; array and multisampled geometries have no
sured form; the result-returning Interlocked*(..., out prev) overload cannot
be lowered (no result register). All of these keep the diagnostic.
Byte-addressed x coordinate
Like the non-_convert sust/suld paths, sured's x coordinate is byte
addressed. The emitter multiplies the texel x by the backing-element size, and,
for a single component of a vector texel (rwTexture[coord].y), adds that
channel's byte offset; y and z are texel-indexed, and 3D takes a dummy 4th
coordinate operand (matching sust.p.3d). The backing-element size comes from an
explicit [format(...)] decoration when present — validated for an exact
representation match (isImageFormatCompatible), so a converting/packing format
falls back to the diagnostic rather than computing a wrong offset — otherwise
from the texel element type.
Fallback
The cases sured cannot express are diagnosed with E41405
("this atomic operation, value type, or texture shape is not supported …"):
xor, exchange/compare-exchange, the result-returning overload, array or
multisampled textures, and any directly recoverable format/channel that is not a
plain 32/64-bit integer matching the value width. A multisampled-texture atomic is
caught before emission by a dedicated, always-run checkUnsupportedTextureAtomic
pass, because the CUDA emitter cannot even name a multisample resource type (see
the process report).
Known limitation (shared with CUDA surf read/write) — reviewer decision point
The byte stride is computed from the texture's backing format, recovered by
findImageFormatDecoration. That helper cannot see a format across indirection
— a function parameter, a call result, or a resource-array element — because CUDA
does not specialize formatted resource parameters, so the concrete resource's
[format(...)] stays at the call site. When the format is consistent with the
element type (the common case, including the compiler default) the element-type
stride is correct; it is wrong only for a contradictory declaration whose
format width disagrees with the element type (e.g. [format("r32ui")] RWTexture2D<uint64_t>) reached through indirection. The existing surf2Dread /
surf2Dwrite paths mis-stride that exact declaration identically — this is a
pre-existing, systemic CUDA-surface limitation whose real fix is producer-side
format recovery, tracked in #12737.
This PR deliberately makes the atomic path behave exactly like the surface
read/write paths (approach A): it diagnoses the mismatch it can prove at this
layer — a directly recoverable incompatible format — and inherits the
through-indirection limitation rather than papering over it in the atomic path
alone. We considered a stricter alternative (C: walk the operand graph to
recover the format context / reject any non-authoritative source), but rejected it
as (1) the "context rediscovery by graph walking" anti-pattern the codebase
methodology warns against, (2) a new behavioral divergence making atomics
uniquely stricter than the read/write paths beside them, and (3) an over-reject
risk for legitimate array/bindless uses. @jkwak-work — if you'd prefer C, or a
producer-side fix folded in here, that's your call; A is implemented in this patch
as the proposed consistent default.
Validation status — please read before assuming CI-green
The emit/diagnostic paths are covered by FileCheck and diagnostic tests, and the
sured helpers are assembled to SASS by an offline nvcc -cubin fixture. What
has and has not been exercised at runtime:
Runtime COMPARE_COMPUTE on an L40S (sm_89) PASSED for unsigned 32-bit
add/min/max/and/or and unsigned vector-component add. Those are
the paths the runtime harness actually executes (all runtime textures are
uint/uint4).
Signed 32-bit min/max and all 64-bit forms are emitted and assemble to
SASS offline (nvcc -arch=sm_89 -cubin, including the full emitted kernel), but
are NOT runtime-tested — no COMPARE_COMPUTE exercises a signed or 64-bit
texel, so their runtime correctness is unverified here and should be confirmed on
GPU CI. They are covered statically by (a) FileCheck of the emitted sured
opcode and (b) offline ptxas assembly of both the prelude helper and the full
emitted kernel.
No claim is made here about GPU-CI status or merge-readiness; those are for the
maintainers/CI to confirm.

Concepts and vocabulary
sured — PTX surface-reduction instruction: an atomic RMW against a surface
texel with no result register. sured.b.<op>.<geom>.<ctype>.
CUsurfObject — the opaque CUDA surface handle an RWTexture lowers to; it
has no operator[] and no C-level atomics, which is why the naive emit was
uncompilable.
IRImageSubscript — the pointer-like IR value for RWTexture[coord] used as
an atomic destination. getRootAddr walks GEP/field chains but not through an
IRImageSubscript, so an atomic rooted at one is precisely a texel atomic.
byte-addressed x — the sured/sust/suld x coordinate is in bytes, not
texels; the emitter scales by the backing-element size and adds a channel byte
offset for a vector-component access.
Process report
sured lowering (slang-emit-cuda.cpp). The classifier
classifyTextureAtomicForCuda is the single source of truth for the texture
atomics that reach CUDA emission — both the sured path and the emit-point
E41405 — so those two can never disagree (multisample atomics are the one case
diagnosed earlier, by checkUnsupportedTextureAtomic, because their resource type
is unrepresentable in emit; see below). It intercepts every atomic
whose destination roots at an IRImageSubscript (tryEmitTextureAtomic, called
from tryEmitInstStmtImpl before the opcode switch), and returns "supported"
only for a result-discarding add/min/max/and/or on a 1D/2D/3D, non-array,
non-multisample texture whose channel is a plain 32/64-bit integer matching the
value width, with at most one constant vector-component index. Anything else is
diagnosed. This is at the right layer because the input IR shape is the correct
canonical one (the same shape SPIR-V lowers); we are adding the missing target
lowering, not repairing a malformed shape.
Per-ctype helper names (prelude/slang-cuda-prelude.h). The helpers are named
__slang_surface_reduce_<op>_<ctype> (e.g. _add_u64) rather than being an
overload set on the value type. The emitter renders a 64-bit literal as unsigned long long, which matches neither an int64_t nor a uint64_t overload exactly;
an overload set is therefore ambiguous under offline nvcc (verified: the u64
form failed to compile before this change). Encoding the channel type in the name
removes overload resolution entirely, and the emitter appends the same <ctype>
token it computed for the PTX suffix, keeping the C++ name and PTX opcode in
lockstep.
Exact backing-format validation (slang-emit-cuda.cpp + slang-intrinsic-expand.cpp).
The x byte-stride depends on the backing element size. A channel-count- and
total-size-only check (the previous logic) already rejects a format whose byte
width disagrees (e.g. [format("rgba8ui")] RWTexture2D<uint4>: 4 bytes vs the 16
the element type implies), but it accepts a same-size conversion whose
scalar type differs — e.g. [format("r32f")] RWTexture2D<uint> (both 4 bytes, but
a float channel accessed as uint), which would still address correctly by bytes
yet reinterpret the value. We instead reuse the existing isImageFormatCompatible,
which compares both channel count and scalar base type, so any converting format
— same-size or not — falls back to the diagnostic. findImageFormatDecoration (also reused)
recovers the decoration from the struct field when the resource lives in a
global-parameter block — a direct findDecoration misses that. Both helpers were
already present as file-static functions in slang-intrinsic-expand.cpp; this PR
promotes them to shared declarations rather than duplicating the logic.
Input-shape check for the format path: the shape we can act on soundly is a
directly recoverable [format(...)], which is the resource's own canonical
decoration — validating it here is correct-at-this-layer. The shape we
deliberately do not try to repair here is a resource reached through
indirection (parameter / call result / array element), where the concrete
format is not recoverable at the access site. That is a producer-side
representation gap (findImageFormatDecoration cannot see across indirection,
and CUDA does not specialize formatted resource parameters), shared identically
by the surf2Dread/surf2Dwrite paths. Per the methodology the proper fix
belongs at the producer, not a consumer-side graph walk to rediscover the format
context; that broader fix is not attempted here and is tracked in #12737. See
the "Known limitation" section above for the reviewer decision point.
Multisample atomics: a pre-existing ICE avoided with a pre-emission diagnostic
(slang-ir-check-unsupported-inst.cpp + slang-emit.cpp). A multisampled
texture atomic is a special case. (Note: this PR only intercepts the atomic
case; the broader defect — that any declared multisample texture ICEs on CUDA,
even unused — is pre-existing on master and out of scope here.) Investigating it revealed that any
multisampled texture declared for a CUDA target aborts the compiler — even a
declared-but-unused RWTexture2DMS<uint> with no atomic at all — because
_calcCUDATextureTypeName returns SLANG_FAIL for a multisample texture, and the
resulting null type-name handle trips SLANG_ASSERT(handle != kNullHandle) in
slang-emit-cpp.cpp. This reproduces on master. The abort therefore happens at
global-parameter type emission, before any function body — so the sured
classifier's own multisample rejection never runs, and the abort occurs at every
optimization level (so it cannot be caught by the -minimum-slang-optimization-gated
checkUnsupportedInst). The scoped fix for #12636 is to diagnose the multisample
atomic before emission: a new, always-scheduled checkUnsupportedTextureAtomic
pass finds an atomic rooted at an IRImageSubscript whose image is a multisample
texture and emits E41405. (The broader "any multisample texture ICEs on CUDA"
defect is out of scope here — it is not about atomics — but is noted for a
follow-up.) Because the emit-point classifier can no longer be reached for the
multisample case, the redundant hasSampleCoord() guard there was removed; the
geometry classifier still rejects multisample defensively.
Input-shape check. For every branch that inspects an input shape — the texel
element/channel type, the [format(...)] decoration, the component GEP, the
multisample flag — the shape is the correct, intended one produced by the
front-end and the standard image-subscript lowering (the same shapes SPIR-V and
the existing sust/suld paths consume). We are not papering over an accidental
representation; we are adding a target lowering and, where the hardware genuinely
cannot express the operation, a diagnostic. The one place the producer is at fault
(multisample type emission) is explicitly identified as a separate, pre-existing
defect rather than worked around in this feature.
Closes #12636.

## Motivation

On the CUDA target, a formatted writable texture accessed **through a
function parameter** emits a different (and wrong) surface access than
the *same* texture accessed directly. The compiler fails to recover the
`[format]` backing, so it emits the plain, non-converting intrinsic and
computes the coordinate scale from the access element size instead of
the backing format. Consider this shader (the type used by the committed
regression test):

```slang
void writeThroughParam(RWTexture2D<float> t) { t[uint2(1, 0)] = 5.0f; }

[format("r16f")]                 // 2-byte backing format, accessed as a 4-byte float
RWTexture2D<float> tex;

[shader("compute")][numthreads(1,1,1)]
void computeMain()
{
    writeThroughParam(tex);      // through the parameter
    tex[uint2(2, 0)] = 7.0f;     // direct access — the control
}
```

`slangc repro.slang -target cuda -entry computeMain -stage compute`
emitted, before this change:

```cpp
// through the parameter (WRONG): plain write, byte-scaled by the 4-byte element size, no _convert
surf2Dwrite<float>((5.0f), (t_0), ((_S1)).x * 4, ((_S1)).y, SLANG_CUDA_BOUNDARY_MODE);
// direct (correct): [format] recovered, converting write
surf2Dwrite_convert<float>((7.0f), (globalParams_0->tex_0), ((_S2)).x * 1, ((_S2)).y, SLANG_CUDA_BOUNDARY_MODE);
```

CUDA surface access is byte-addressed on the x coordinate. A *plain*
`surf2Dwrite<T>` therefore scales the coordinate by the backing element
size, so when the backing format differs from the access type the
correct plain stride would be the 2-byte `r16f` size, not the 4-byte
`float` size — emitting `* 4` writes at the wrong texel and can corrupt
adjacent memory. When a conversion *is* required (as here), the correct
form is instead `surf2Dwrite_convert<T>` with an **unscaled** coordinate
(`* 1`): the `_convert` helper handles the packing, so the emitter
deliberately sets the stride multiplier to 1 for a converting write.
Either way the through-parameter access is wrong because the format is
not recovered — it emits the plain, unscaled-by-backing-size form with
no `_convert`. No diagnostic is emitted.

(The issue shader-slang#12737 reports this with a `[format("r32ui")]
RWTexture2D<uint64_t>` example. That combination exposes the same
format-recovery bug, but its converting intrinsic
`surf2Dwrite_convert<ulonglong>` has no CUDA-prelude implementation, so
even a *direct* access to it fails NVRTC independently of this bug — a
separate prelude gap. This PR therefore demonstrates and tests the fix
with `r16f`/`float`, whose converting intrinsics the prelude does
define, so the fix is verifiable end-to-end.) The same format-recovery
limitation would affect the `sured` atomic lowering proposed in shader-slang#12672.

## Proposed solution

The `[format("...")]` backing format is stored as an
`IRFormatDecoration` on the **global** texture parameter. At the
surface-access site the emitter recovers it with
`_findImageFormatDecoration` (`slang-intrinsic-expand.cpp`), which reads
the decoration off the resource instruction. When the texture is passed
through a function, the access site sees only the callee's `IRParam` —
which carries no decoration — so `_calcBackingElementSizeInBytes` falls
back to the element-type size and the `$E` stride multiplier / `$C`
`_convert` selection are computed from the wrong information.

This is fundamentally the "smuggle a resource through a function"
problem documented in the long `TODO(JS)/TimF` comment at
`slang-intrinsic-expand.cpp:191-214`: from inside the callee you can
only reach the `IRParam`, and distinct call sites may pass
differently-formatted textures, so a single un-specialized callee cannot
carry one correct format. That same comment notes the Vulkan back-end
"gets away with this kind of coincidentally, since the legalization we
have to do for resources means there wouldn't be a single `f()` function
any more."

The principled, producer-side fix is to give CUDA that same property for
the affected case: **specialize functions that take a writable-texture
parameter so the concrete global (carrying `[format]`) is referenced
directly at the access site.** This is exactly the mechanism Khronos
(SPIRV/GLSL) and WGSL already use — the resource-parameter
specialization pass (`specializeResourceUsage`) already runs
unconditionally for all targets (`slang-emit.cpp`); it is *not* gated
behind `shouldLegalizeExistentialAndResourceTypes`. Only the
per-parameter decision
`ResourceParameterSpecializationCondition::doesParamWantSpecialization`
returned `false` for CUDA. Adding a CUDA arm to that decision fixes
surface read/write — and the pending `sured` atomic path, which shares
`_calcBackingElementSizeInBytes` — uniformly, with no change to the
emitter.

Once the callee refers to the global directly,
`_findImageFormatDecoration` finds the decoration,
`_calcBackingElementSizeInBytes` returns the true backing size, and the
through-parameter access emits identically to the direct access.

**Scope.** This fixes the format-recovery defect the issue reports — a
formatted writable texture passed through a function parameter where the
*argument is a concrete global* — for both reads and writes wherever the
target's converting helper exists, and handles distinct-format call
sites via distinct specializations. Four residual cases still emit a
possibly-wrong stride (all of them *no worse than the base compiler
today* — see the Process report for the verification), so shader-slang#12737
intentionally stays open to track them:
- an **array-of-globals element** argument (`f(gTexArray[i])`) — which
is a *separate, pre-existing* format-recovery gap, not the
parameter-boundary bug (it reproduces with a direct access and no
function parameter at all);
- a **function-returned resource** (`getTex()[coord]`) — not foldable to
a single global;
- a **runtime-selected** argument (`f(cond ? gA : gB)`) — inherently
unrecoverable, since the two textures may carry different formats;
- a **mixed call** where one parameter's argument is foldable and
another's is not — `canSpecializeCall` is all-or-nothing per call, so it
leaves the foldable one unspecialized too.

Closing these needs a separate format-recovery fix for array/returned
resources and/or a capability diagnostic (the E41405-style approach
being added in shader-slang#12672); that is deliberately left as a coordinated
follow-up rather than raced against that PR. The predicate is scoped to
*writable* textures for consistency with the existing Khronos/WGSL arm;
specializing an unformatted writable texture is correctness-neutral (its
stride is unchanged) at a bounded code-size cost.

## Concepts and vocabulary

- **`doesParamWantSpecialization`**
(`ResourceParameterSpecializationCondition`) — the per-parameter
predicate that decides whether a function taking this parameter should
be specialized per concrete argument. It already returns `true` for
`ConstantBuffer<T>` on all targets and for illegal buffer/image/texture
parameter types on Khronos/WGSL; every other target previously fell
through to `false`.
- **`isParamSuitableForSpecialization` / `canSpecializeCall`**
(`slang-ir-specialize-function-call.cpp`) — the companion predicate that
decides whether a given *argument* can actually be folded. It accepts
several shapes (global shader parameters, global values, user-pointer
types, descriptor-handle casts, and index/load/field chains rooted at
one of those); for the texture-resource path relevant to this PR that
means the argument must resolve to a global (or an index into a global
array). If a parameter *wants* specialization but the argument is not
suitable, `canSpecializeCall` returns `false` and the whole call is left
unspecialized — this all-or-nothing behavior is why the "mixed call"
residual below exists.
- **`$E` / `$C`** (`slang-intrinsic-expand.cpp`) — the surface-intrinsic
template expansions: `$C` appends `_convert` to the intrinsic name when
a format conversion is required; `$E` emits the coordinate scale factor
— the backing-element byte size for a *plain* (non-converting) access,
but `1` for a converting *write* (`_calcBackingElementSizeInBytes` is
overridden to 1 there, since the `_convert` helper handles packing).
Both read the recovered `IRFormatDecoration`.

## Process report

**The one behavioral change — a CUDA arm in
`doesParamWantSpecialization`.** The bug's root cause is that the format
decoration is unreachable across the parameter boundary; the fix makes
it reachable by specializing the callee against the concrete global,
rather than patching the emitter to guess a stride it cannot prove.
Requesting specialization is scoped to `isWritableTextureType(type)` —
`RWTexture`/`WTexture`/rasterizer-ordered views — because only
writable-texture accesses go through the CUDA `surf*write`/`surf*read`
size-scaling path; a sampled `Texture` (plain `READ`) lowers to a
texture fetch and does not need it. It is gated by
`isCUDATarget(targetRequest)` (matching the sibling
`isKhronosTarget`/`isWGPUTarget` arms). CUDA is the only C-family target
that reaches this path: `CUDASourceEmitter` inherits `CPPSourceEmitter`,
but the surface intrinsics (`surf2Dwrite$C…$E`) are CUDA-only templates
in `hlsl.meta.slang`, and the CPU/C++ path never emits them.

**Input-shape check (is this the right layer?).** Yes. The `IRParam`
reaching the access site is not a malformed shape to be repaired at
emit; it is the correct IR for an un-specialized callee. The problem is
that CUDA left the callee un-specialized where the format information
only survives on the global. The producer-side fix — specialize so the
global reaches the access site — is precisely how the other targets
avoid the same bug, and it removes the need for any emit-time guess. The
alternative of carrying the format on the `IRTextureType` and reading it
at emit was rejected: it founders on the multi-call-site ambiguity in
the `TODO` (one un-specialized callee cannot carry one correct format
when call sites disagree), and it would introduce a second format
representation (decoration vs. type operand) that every consumer would
have to agree on, violating "one canonical representation per value."

**What is fixed, and what is not (verified against the base compiler).**
The fix recovers the format when the argument is a **concrete global**
texture — `f(gTex)` — for both reads and writes, and when different call
sites pass differently-formatted globals (each gets its own
specialization). Four cases are *not* covered and remain exactly as they
emit today (never worse — verified against base):
- **Array-of-globals element** (`f(gTexArray[i])`): this is a *separate,
pre-existing* bug, not the parameter-boundary bug. It reproduces with a
**direct** access and no function parameter at all —
`gTexArray[idx][coord] = v` already emits `surf2Dwrite<...> .x * 4` on
the base compiler (verified identical on this branch). The call here
*does* specialize (the suitability check traces `GetElement` to the
global), but `_findImageFormatDecoration` does not recover the per-array
`[format]` off the array-element access; fixing that lives in
`_findImageFormatDecoration` (the same file shader-slang#12672 is editing),
independent of this change.
- **Function-returned resource** (`getTex()[coord]`): the argument is a
call result, not foldable to a single global, so the callee is not
specialized and the access emits `surf2Dwrite<...> .x * 4` (verified).
- **Runtime-selected argument** (`f(cond ? gA : gB)`):
`isParamSuitableForSpecialization` returns `false` for the resource path
here, so `canSpecializeCall` bails for the whole call. This one is
*inherently* unrecoverable by specialization — the two textures may
carry different formats.
- **Mixed call** (`f(gTex, cond ? gA : gB)`): `canSpecializeCall` is
all-or-nothing per call, so one unfoldable argument leaves the foldable
`gTex` unspecialized too.

Closing these requires either recovering the format after array/GEP
reconstruction, argument-level (vs call-level) specialization, or a
capability diagnostic (the E41405-style approach being added in shader-slang#12672).
That is deliberately left as a coordinated follow-up rather than raced
against shader-slang#12672, which is why this PR **leaves shader-slang#12737 open**. The common
concrete-global case the issue reports is fixed.

**The refactor — `isWritableTextureType`.** The switch on
`IRTextureType::getAccess()` for the writable access modes previously
lived inline in `isIllegalGLSLParameterType`. Extracting it into a named
helper and reusing it in both the GLSL-legality check and the new CUDA
arm keeps the "which texture accesses are writable" classification in
one place, so the two callers cannot drift. No behavior change to the
GLSL path.

## Tests

- **New:** `tests/compute/texture-format-through-param.slang` — a
`[format("r16f")] RWTexture2D<float>` written through a function
parameter and directly, and read through a parameter. It uses one
multi-prefix source-emission FileCheck directive (`SIMPLE -target cuda`,
which runs `slangc` + FileCheck): `CUDA` asserts **two**
`surf2Dwrite_convert` calls with stride `* 1` (the through-parameter
write matches the direct one); `READ` asserts `surf2Dread_convert … .x *
2` (the through-parameter read recovers the 2-byte backing size); and a
`NEG` prefix forbids the plain `surf2Dwrite<` / `surf2Dread<` across the
whole input. Fails before the fix (only the direct write converted; a
plain `.x * 4` write and a plain read remained), passes after.
`r16f`/`float` is used (not an integer format) both to force the
size-mismatch conversion and because the CUDA prelude only defines the
converting-read helper (`surf2Dread_convert`) for float element types.
- **Real CUDA compile:** the emitted CUDA for the full test — reads
*and* writes through parameters — compiles via NVRTC (`-target ptx`)
rc=0 on an L40S with CUDA 12.6, confirming the specialization produces
valid CUDA (not just textually-correct source) and does not trip an
assert cloning an un-legalized texture global. (`float` reads use the
defined `surf2Dread_convert<float>` overload; an *integer* converting
read would hit a pre-existing prelude gap where only float overloads are
defined — orthogonal to this fix.)
- **Regression:** 779/779 across
`tests/compute/{texture-subscript,rw-texture-simple,half-rw-texture-convert*}`,
`tests/hlsl-intrinsic/texture/`, and `tests/diagnostics/` (GPU-only legs
ignored); the GLSL predicate is behavior-identical after the refactor.
