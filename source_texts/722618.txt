In the scaling issue conversation we started discussion of improving the rendering shader code.
Some of this has already been done for sphere objects.
For a general overview of the lighting modes Datoviz may support.
(As I current understand them... please correct me if this is not correct or is missing items.)
```
    Lighting Rendering Modes:

        Basic             A Single light with vec4 material properties, fast, and small.  (As currently used by spheres.)
                          Red, green, and blue light components are treated equally.  (pending... use textures.)

        Advanced        Has up to 4 lights, mat4 properties for more realistic materials.
                          May be somewhat slower than basic and use more memory.
                          Material can react differently to red, green, and blue light components.
                          Can use textures.

        Volumetric      Render 3D volumes by sampling volume data. (With multiple rendering options.)

        * Realistic       Physical Based rendering with less concern for performance.

        * RayTraceFast   Attempt to be fast enough to render in real time, but may be limited to low resolutions and quality.

        * RayTraceFull   Attempt to produce high quality production level visuals/images.  May be very slow.

    (*) Not implemented yet.
```
The mesh objects has it's own rendering shader routine code like the Advanced mode above, but it has a number of things that can be improved.
```
It currently does not handle multiple lights well, although it was designed for it.
```
```
The material parameters are currently per light, but should be per object or per object type.
```
The advanced material parameters should define how each R, G, B color light component reacts to the surface. (It's not the light that is smooth or rough, and not the light that reflects green more than red.) Each light will have it's own color, and the surface property will determine how to use the lights color.
I'm also exploring if the user API should use normalized parameter values. This may be easier to work with, but it diverges from what other programs do.
CONTEXT:
I'm currently working on a pull request to test if normalized parameters would be good. I wanted to use the mesh objects, but the above issues needed resolving first. Having a good overview to start the discussion seemed like it would be good in order to improve the overall design.
I'm nearly complete with a preliminary pull request version for discussion that includes a preliminary Advanced mode as described above.
These modes will be in their own lighting_mode.glsl files to be included.
More specifics and examples to follow...

In the routine, I use a mat4x3 to hold the parameters. It looks like this...
```
        //                              R    G    B
        mat4x3 material = mat4x3( vec3(0.05, 0.05, 0.05),     // ambient-emmission amount
                                  vec3(0.7, 0.7, 0.7),        // diffuse level
                                  vec3(1.0, 1.0, 1.0),        // specular amount
                                  vec3(1.0, 1.0, 1.0) );      // shininess
```
The rgb values are all set to be equal here, but could vary according to data from real objects.
The arangement allows combining the ambient rgb properties to the light rgb colors all at once.
```
     ambient_color = color * material[0];      // object color * ambient vec3() rgb component.
```
The current properties appear to be arranged as multiple vec4's for use with each light.

Both basic and the advanced use Blinn-Phong, as it's both faster and better looking.
As for wire frame, and other additions, those are more specific to each visual type. The parts I'm working on can be reduced to a single color function call. The color can be modified before that call, or after that depending on if you want the particular effect to be include in the lighting calculation or not. This also means the color function call can be used on 2D visuals as well. This can result in 2D components being lighted in the same way the 3D components are within a panel. (but for now, I'm just getting the lighting functions to work as they should.)
I'm currently just reading the existing binding and reassigning them in the shader. It's not optimal and I think you will need to change them. Each mode may require slightly different bindings. And those may be assigned in different places, Ie... panel or visual. So is it better to split these layouts/bindings into smaller components, or have one large structure and just not use parts of it. That seems like it may not be optimal memory wise.
Here's what I have for basic light parameters. This is what the shader needs to know about the light. And is likely to be set by the panel.
```
layout(std140, binding = USER_BINDING) uniform BasicLightParams
{
    vec4 color;            // default = white
    vec4 pos;              // default = camera position
//    vec4 atts;             // power, fov, area, attenuation.
}
basic_light;
```
The atts (light attributes) entry is needed to support different light types.
The Advanced mode is similar, but uses mat4s. 1 vec4 each for each light.
The shaders also need a layouts for the object type or each object. Uniforms for object types, and varies (in) for each object, depending on how fine grained you want the control to be.
A nice relationship I found is the 'w' component of the position can be sued to determine if it's a position or direction. For directions it will always be 0. (or can be set to 0)
And for weather or not a light is present, the alpha 'a' component of the light color can be used. If alpha on the light is 0, then skip it.
I had the parameter set as a mat4x4, but had changed it to help find a bug I was looking for.

I think I got most of it working...
Currently the visuals setter functions need to be used. The light dir/pos and color should be set in the panel, while the material parameters should remain in the visual. Having a lights object and doing a panel.add(lights) may work.
```
    visual = app.mesh_shape(sc, lighting=True)
    
    visual.set_light_color((  0,   0, 255), 0)    # Blue
    visual.set_light_color((  0, 255,   0), 1)    # Green
    visual.set_light_color((200, 200,   0), 2)    # Yellow
    visual.set_light_color((255,   0,   0), 3)    # Red
    
    visual.set_light_dir(( -9, 1, 5), 0)
    visual.set_light_dir(( -3, 1, 5), 1)
    visual.set_light_dir((  3, 1, 5), 2)
    visual.set_light_dir((  9, 1, 5), 3)
    
    # Material affect on color R    G    B  components of light.
    visual.set_light_params(( .2,  .2,  .2), 0)    # Ambient
    visual.set_light_params(( .8,  .8,  .8), 1)    # Diffuse
    visual.set_light_params(( .8,  .8,  .8), 2)    # Specular
    visual.set_light_params(( .9,  .9,  .9), 3)    # Exponent
        
    panel.add(visual)
```
Note that the colors and directions are vec3. The functions take vec4, but the extra value seems to be ignored.
Also the material parematers (light_params) should be set with only 1 call. It's not affected by how many lights are present.
A library of pre defined materials settings may be useful.
So for now I'm setting the 'a' and 'w's manually in `graphics_mesh.frag' to enable it to work for testing.
```
    // Lighting.
    if (MESH_LIGHTING > 0)
    {
        vec4 cam_pos = inverse(mvp.view) * vec4(0.0, 0.0, 0.0, 1.0);

        mat4 light_pos = params.light_dir;
        mat4 light_color = params.light_color;
        mat4 material = params.light_params;

        // Current visual setters don't set w and a.
        for (int i=0; i<4; i++)
        {
            light_pos[i].w = 1.0;      // w greater than 0.0 is a position.
            light_color[i].a = 1.0;    // Alpha greater than 1.0 is on.
        }

        out_color = advanced_lighting(in_pos, color, material, normal, cam_pos, light_pos, light_color);
    }
```
The advanced_lighting function is included in a lighting.glsl file. That file also has the basic lighting function.
