Stacked on #4921. This branch builds on model-cameras, so the commits of #4921 appear in this diff until #4921 merges. Only the last commit, "Add camera ray functions and per-hit outputs", belongs to this PR.
This PR adds the still-experimental parts of the bound SensorCamera API from Cameras in the Model. They were part of #4921, and review asked to land the core model-camera API first and move these into their own PR. All of them stay marked .. experimental::.
User ray functions. The new ray_function and ray_params constructor arguments take a @wp.func (params: wp.array2d[float], query: SensorCamera.RayQuery) -> (origin, direction). The render kernel evaluates it for every pixel sample of every view, with RayGenerationMode.FUNCTION as a fourth ray generator next to shared bundles, indexed bundles and the inline pinhole. RayQuery holds the view, model camera (or site), world, pixel, sample and image size.
Per-hit outputs. SensorCamera.update() gains face_index_image and barycentric_image, with allocate_image_face_index() and allocate_image_barycentric(). The face index is the triangle index into Model.tri_indices for deformable surfaces, the mesh face index for mesh shapes and the particle index for particles. SensorCamera.HIT_TRIANGLE_MESH, HIT_PARTICLES and HIT_NONE identify those hits in shape_index_image. User kernels can build custom imaging channels from these outputs, such as thermal images.
view_mask. A per-view bool switch in update(). Views set to False are skipped and keep their previous outputs.
Shared renderer. Bound sensors of a model that use the same load_textures and deformable_surface_mode settings share one RenderContext, so lights, ambient light and checkerboard materials set on one apply to all. In Add cameras as a Model entity #4921, each bound sensor owns its renderer, like an unbound one.
The raytracer resets face_idx and the barycentrics on Gaussian and particle hits, so the per-hit outputs never carry values from an earlier candidate.

New feature / API change
```
import warp as wp

from newton.sensors import SensorCamera


@wp.func
def lidar_rays(params: wp.array2d[float], query: SensorCamera.RayQuery):
    # params[ring, 0] holds the elevation [rad] of each laser ring.
    azimuth = 2.0 * wp.pi * (float(query.x) + 0.5) / float(query.width)
    elevation = params[query.y, 0]
    direction = wp.vec3f(
        wp.cos(elevation) * wp.sin(azimuth), wp.sin(elevation), -wp.cos(elevation) * wp.cos(azimuth)
    )
    return wp.vec3f(0.0), direction


lidar = SensorCamera(model, sites="env_*/lidar", width=1024, height=32, ray_function=lidar_rays, ray_params=rings)
ranges = lidar.allocate_image_depth()
faces = lidar.allocate_image_face_index()
bary = lidar.allocate_image_barycentric()
lidar.update(state, depth_image=ranges, face_index_image=faces, barycentric_image=bary, view_mask=active_envs)
```

# Overview

While OpenUSD can be used to describe many kinds of data, its primary and most-used domain is describing 3D scenes, and visualizing or rendering those scenes is a key process. Interactive &quot;viewport&quot; or browser renders can often give a reasonable approximation of the scene&#39;s content with minimal instruction to a renderer. But for producing &quot;film quality&quot; or &quot;final quality&quot; renders of complicated scenes with large numbers of interacting elements, special geometric, volumetric, and shading effects, studios routinely need to provide much more detailed instructions to a &quot;final quality&quot; renderer. Such instructions might include complex configuration needed to decompose the scene for a number of different &quot;render passes&quot; that each produce outputs that are then composited, and post-processed into a &quot;final frame&quot;.

UsdRender provides schemas for specifying these instructions such that they can be delivered to renderers in a standardized way. Renderers are responsible for applying your render configurations to the final render to the best of their ability. Renderers that support OpenUSD should have reasonable defaults that will be applied if render configuration isn&#39;t authored in your scene.

UsdRender provides the following schemas.

  * RenderSettings: Encapsulates all the settings and components that tell a renderer what render settings to use, and what render output to produce (via specified RenderProducts), for a single invocation of rendering the scene.

  * RenderProduct: Represents a single render output artifact, such as a rendered image file or an output depth buffer. Includes render output information (e.g. artifact type and name) and which output channels (via specified RenderVars) should be incorporated into the artifact.

  * RenderVar: Represents a quantity or &quot;channel&quot; of computed output data that can vary across an output artifact, sometimes referred to in other rendering pipelines as an arbitrary output variable (AOV).

  * RenderPass: Represents the renderer and scene configuration for a single render pass in a multi-pass rendering workflow. For example, you might have a workflow that uses separate render passes to render the foreground and background portions of a scene, and a third pass that composites the foreground and background render output into the final frame.

(usdRender_best_practices)=

## Best Practices

The following are some general best practices for using UsdRender schemas.

(usdRender_which_schemas_to_use)=

### Understand Which Schemas to Use

When configuring how to render your scene, it&#39;s important to understand which UsdRender schemas you will need to use. Some schemas rely on other schemas to fully describe the desired configuration. For example, to fully configure the final render output artifact, you need to provide a RenderProduct, and also provide a set of RenderVars that the RenderProduct uses.

Additionally, some schemas might not be needed for your rendering workflow. For example, if your render pipeline does not use multi-pass rendering, you might not need to utilize RenderPass.

When planning out your use of UsdRender schemas, here are some things to keep in mind.

  * Always provide a &#39;default&#39; RenderSettings. This RenderSettings prim will act as the default global render configuration for your scene. See {ref}`usdRender_default_rendersettings` for how to set the default RenderSettings path in layer metadata.

  * Determine if you will need to use a multi-pass rendering workflow or not. This will determine if you&#39;ll need to define RenderPass prims. Many animation production workflows benefit from the added flexibility multi-pass workflows provide, or may require multi-pass rendering to apply certain effects. However, multi-pass workflows increase the complexity of the render process and may also increase storage requirements for the output from multiple passes. See {ref}`usdRender_configuring_multipass_renders` for more details on using RenderPass.

  * Renderers that support OpenUSD should produce a default output artifact (typically an RGB image) for a renderer invocation if no RenderProduct is specified. Renderers should also provide API schemas that apply to and extend UsdRender schemas such that a single default RenderSettings can be usefully consumed by any renderer. However, you may need to override configuration specified in your RenderSettings for a particular output, or specify output channels (color, normal, alpha, etc.) for your output, or even specify renderer-specific configuration for the output (special output compression settings, etc.). If you need this level of output configuration, you&#39;ll need to provide RenderProduct and RenderVar prims with the appropriate configuration values. See {ref}`usdRender_working_with_render_product` and {ref}`usdRender_understanding_rendervars` for more details on using RenderProduct and RenderVar.

(usdRender_group_render_prims)=

### Group UsdRender Prims

As a general best practice, group all your UsdRender prims (RenderSettings, RenderProduct, RenderVar, RenderPass) in a scene under a common root prim named &quot;Render&quot;. This encapsulates render-related specifications from the rest of your scene data so that, even in large scenes, render specifications can be accessed efficiently using features like UsdStage masking. The following example has two RenderSettings and a RenderProduct grouped under a Scope &quot;Render&quot; prim.
    
    `def Scope &quot;Render&quot;
    {
        def RenderSettings &quot;PrimarySettings&quot; {
            rel products = &lt;/Render/PrimaryProduct&gt;
            int2 resolution = (512, 512)
        }
        def RenderSettings &quot;PrimarySettingsRaw&quot; {
            rel products = &lt;/Render/PrimaryProduct&gt;
            int2 resolution = (1024, 1024)
            uniform token renderingColorSpace = &quot;raw&quot;
        }
        def RenderProduct &quot;PrimaryProduct&quot; {
            token productName = &quot;/scratch/tmp/render000009.exr&quot;
        }
    }

(usdRender_default_rendersettings)=

### Provide a Default RenderSettings

It&#39;s possible to have multiple RenderSettings prims in a given stage. You might have a stage that needs to provide separate RenderSettings for renders for different purposes (preview, final, etc.). As RenderSettings provide the global render configuration for a scene, it&#39;s important to clarify what the &quot;default&quot; RenderSettings is.

Communicate to a renderer what the default RenderSettings is by using the `renderSettingsPrimPath` metadata in your stage&#39;s root layer, providing a path to a RenderSettings prim. The following example sets the default RenderSettings to &quot;/Render/PrimarySettings&quot;.
    
    `#usda 1.0
    (
        renderSettingsPrimPath = &quot;/Render/PrimarySettings&quot;
    )
    `

(usdRender_designate_camera)=

### Designate a Render Camera

RenderProduct and RenderSettings can designate the {ref}`render camera &lt;render_camera&gt;` used for rendering via setting the `camera` relationship to a Camera prim. The Camera prim determines the visual composition of the scene as an image, and represents creative choices distinct from the technical render settings used to configure image generation. This is why some attributes originate from the camera and others (such as pixel resolution) are expressed separately as render settings, and may vary per RenderProduct.

The following example has a &quot;PrimarySettings&quot; RenderSetting with /World/main_cam configured as the render camera, and a second RenderSettings, &quot;StereoSettings&quot; (also using /World/main_cam). Additionally, one of the RenderProducts (&quot;StereoProductLeft&quot;) that &quot;StereoSettings&quot; includes overrides the render camera from &quot;StereoSettings&quot; to use /World/stereo_cam/cam_left just for that product output.
    
    `def Scope &quot;Render&quot; {
        def RenderSettings &quot;PrimarySettings&quot; {
            rel camera = &lt;/World/main_cam&gt;
            # ... other settings ...
        }
        def RenderSettings &quot;StereoSettings&quot; {
            # stereo render products will override camera as needed
            rel camera = &lt;/World/main_cam&gt;
            rel products = [ &lt;/Render/StereoProductRight&gt;, &lt;/Render/StereoProductLeft&gt; ]
            # ... other settings ...
        }
    
        def RenderProduct &quot;StereoProductRight&quot; {
            rel camera = &lt;/World/stereo_cam/cam_right&gt;
            # ... other settings ....
        }
        def RenderProduct &quot;StereoProductLeft&quot; {
            rel camera = &lt;/World/stereo_cam/cam_left&gt;
            # ... other settings ....
        }
    }
    `

(usdRender_controlling_rendered_prims)=

## Using UsdRender to Control How Prims Are Rendered

UsdRender schemas provide several properties to control which prims get rendered for a render invocation or a render pass, as well as properties to control how prims get rendered, e.g. controlling which material bindings are used during a render.

(usdRender_using_imageable_purpose)=

### Configuring Imageable Purpose

USD provides several ways to {ref}`control prim visibility &lt;render_visibility&gt;` in a scene. One approach specifically designed to be used at render-time is {ref}`imageable purpose &lt;render_purpose&gt;`, which lets you author a `purpose` attribute on an imageable prim, and then configure which purposes are used at render-time.

To configure which purposes to use for a render, use the `includedPurposes` attribute on RenderSettings to list the purposes that will be rendered.
    
    `Prims that have no authored or inherited purpose (i.e. the prim has the 
    fallback &quot;default&quot; purpose) are always rendered. Renderers are expected to 
    render default purpose prims for all render situations.
    `

The following example has `includedPurposes` set to `[&quot;proxy&quot;, &quot;render&quot;]`, so only prims with `purpose` set to &quot;proxy&quot; or &quot;render&quot;, or prims that have {ref}`&quot;inherited&quot; &lt;render_purpose_inheritance&gt;` either of those imageable purposes, will be rendered. Note that prims with no authored or inherited purpose (i.e. the &quot;default&quot; fallback purpose) will always be rendered.
    
    `def RenderSettings &quot;PrimarySettings&quot; {
        uniform token[] includedPurposes = [&quot;proxy&quot;, &quot;render&quot;]
    }
    `

(usdRender_using_materialbindingpurposes)=

### Configuring materialBindingPurposes

Material binding purposes let you specify, for the same Gprim, different material bindings for different purposes, e.g. a material binding for a &quot;full&quot; render, vs a lightweight material binding for a &quot;preview&quot; render. See {ref}`material_binding_purpose` for more details.

Configure which material binding purposes are used for a render via the `materialBindingPurposes` RenderSettings attribute. For example, you might have separate RenderSettings for a final render, using the &quot;full&quot; purpose, and for your DCC tool, using the &quot;preview&quot; purpose.
    
    `def RenderSettings &quot;FinalRenderSettings&quot;
    {
        uniform token[] materialBindingPurposes = [&quot;full&quot;]
        ...
    }
    def RenderSettings &quot;DefaultRenderSettings&quot;
    {
        uniform token[] materialBindingPurposes = [&quot;preview&quot;]
        ...
    }
    `

(usdRender_using_renderpass_collections)=

### Using RenderPass Collections

If you are using a multi-pass rendering workflow, RenderPass provides additional properties to control how prims are rendered through the `renderVisibility`, `cameraVisibility`, `prune`, and `matte` collections.

  * `renderVisibility`: This collection describes which prims are visible to the renderer for this pass. Use this collection if you have separate passes for different sets of objects in the stage (e.g. separate foreground and background passes), or passes that only apply to specific types of objects. Note that this collection acts as a &quot;mask&quot; and does not override authored `visibility` values -- for example, if an imageable prim in the scene has (or inherits) `token visibility = &quot;invisible&quot;`, including this prim in this collection will not cause the prim to be visible.
  * `cameraVisibility`: Similar to `renderVisibility`, however this collection describes which prims are visible to the main render camera (set in RenderSettings or RenderProduct) for this pass. Note that objects that are not in this collection should still participate in other light paths such as shadowing, reflections, and refraction. Similar to `renderVisibility`, this collection does not override authored `Imageable.visibility` values. Also, note that this collection is applied after `renderVisibility`, so prims in this list, but not in `renderVisibility` will not be visible to the renderer.
  * `prune`: This collection defines which prims should be removed during this render pass. This is provided as an alternative to collections like `renderVisibility` and `cameraVisibility`, to support scenarios such as batch rendering, or when renderers can&#39;t support visibility toggles. The tradeoff is that pruning is likely to be a more expensive operation than visibility toggling and therefore not appropriate for certain renderer scenarios, such as renders for interactive workflows.
  * `matte`: This collection describes which prims should be rendered as &quot;matte objects&quot; (objects with zero alpha) during this render pass. Note that this list is applied after `renderVisibility`, so prims in this list, but not in `renderVisibility` will not be visible to the renderer, and therefore not rendered as matte.

Note that all of these collections are {ref}`USD collections &lt;collections_and_patterns&gt;` and therefore can be defined using relationship-mode or pattern-based collections. The following example defines two RenderPasses, a &quot;foreground&quot; pass that uses a relationship-mode collection for `renderVisibility`, and a &quot;background&quot; pass that uses a pattern-based collection for `renderVisibility`.
    
    `def RenderPass &quot;foreground&quot; 
    {
        rel renderSource = &lt;/Render/PrimarySettings&gt;
        uniform bool collection:renderVisibility:includeRoot = false
        prepend rel collection:renderVisibility:includes = [
            &lt;/World/characters&gt;,
            &lt;/World/sets/Kitchen/Table_grp&gt;,
        ]
    }
    def RenderPass &quot;background&quot; 
    {
        rel renderSource = &lt;/Render/PrimarySettings&gt;
        pathExpression collection:renderVisibility:membershipExpression = &quot;/World/Background* + /World/OLD_Background*&quot;
    }
    `

(usdRender_working_with_render_product)=

## Working with RenderProduct

A RenderProduct represents a single render output artifact, such as a rendered image file or an output depth buffer. RenderProducts can override some of the configuration in a RenderSetting (such as the {ref}`camera &lt;usdRender_designate_camera&gt;`), but also have product-specific settings, such as the output &quot;product name&quot; (for a rendered image, the image filename).

The following example RenderProduct configures `productType` and `productName`, but also overrides any authored RenderSettings values in use for `camera` and `resolution`.
    
    `def RenderProduct &quot;PrimaryProduct&quot; {
    
        # --- product-specific ---
        uniform token productType = &quot;deepRaster&quot;
        uniform token productName = &quot;/output/render000009.png&quot;
    
        # --- overrides ---
    
        # For this product, override our RenderSettings camera and resolution 
        rel camera = &lt;/Cameras/stereo_cam&gt;
        uniform int2 resolution = (3840, 2160)
    
        # ...other settings...
    }
    `
    
    `Overriding settings such as `camera` and `resolution` may, for some 
    renderers, necessitate multiple independent renders. Other renderers may be 
    able to vary these settings over RenderProducts computed in a single render.
    `

A RenderProduct must also specify one or more RenderVars, each of which represent a channel of computed output data, as described in {ref}`usdRender_understanding_rendervars` below.

(usdRender_understanding_rendervars)=

### Understanding RenderVars

A RenderVar represents a quantity or &quot;channel&quot; of computed output data that can vary across an output artifact. A RenderProduct may contain multiple channels of data representing related values or variables sampled by a render process. The RenderVar prim specifies what values the renderer should output and how the renderer should produce them.

Examples of render variables include geometric measurements such as camera-space depth, quantities emitted by material shaders, light path expressions (LPE&#39;s), and quantities intrinsic to the renderer such as computation time per pixel. Note that USD does not yet enforce a set of universal RenderVar names and formats, so renderer-specific RenderVars are expected. In the following example, the &quot;PrimaryProduct&quot; RenderProduct specifies four RenderVars representing channels for color, alpha, directDiffuse, and a general ID value.

            rel camera = &lt;/World/main_cam&gt;
            token productName = &quot;/scratch/tmp/render000009.exr&quot;

                &lt;/Render/Vars/color&gt;,
                &lt;/Render/Vars/alpha&gt;,
                &lt;/Render/Vars/directDiffuse&gt;,
                &lt;/Render/Vars/id&gt;

        def Scope &quot;Vars&quot;

            def RenderVar &quot;color&quot; {

                string sourceName = &quot;a&quot;
            }
            def RenderVar &quot;directDiffuse&quot; {
                string sourceName = &quot;C&lt;RD&gt;[&lt;L.&gt;O]&quot;

            }
            def RenderVar &quot;id&quot; {
                token dataType = &quot;int&quot;
                string sourceName = &quot;id&quot;
            }
        }
    `

# Rendering with USD

This document describes the conventions and rules USD provides for producing correct and reproducible renders. Use this information to help build a robust USD pipeline and configure your assets for rendering. As USD can be used for both interactive renders and &quot;final frame&quot; renders, some of the conventions in this document will be more applicable to one use case than the other, whereas some conventions will apply to any rendering use case.

## Configuring Render Settings

OpenUSD provides UsdRender domain schemas used to configure how your scene will be rendered. These schemas are used to communicate global configuration settings to the renderer (and rendering pipeline), which is then responsible for applying these settings to the final render to the best of their ability. Renderers that support OpenUSD should have reasonable defaults that will be applied if render configuration isn&#39;t authored in your scene.

For full details and examples, see :ref:`UsdRender Overview &lt;usdRender_overview&gt;`.</excerpt>
