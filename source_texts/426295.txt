Two bugs found during the 2026-10 cleanup (Y1 and Y2).
Merge after jaccpot #391. Fix 1 attaches a cells tree's padding subtree to the root. jaccpot's multi-GPU export walk didn't skip empty nodes, and #391 makes it do so. Without #391, 5 jaccpot unit tests overflow their list caps against this branch.
1. The adaptive LBVH returned a forest when Morton codes tie (1f00527)
When more than leaf_size particles share one Morton code, the adaptive build (build_tree, and the octree on top of it) returned several roots, with leaves no walk from the root reaches. Ties come from duplicate positions, or from padding rows that copy a real particle (sanitize_padding).
Case (leaf 8)
Before the fix
64 copies of one point among 128
6 roots; 5 of 16 leaves unreachable
28 copies
2 roots; 1 leaf unreachable
build_static_cells_tree's padding leaves share a sentinel code, so the "one subtree at the right end" its docstring promises was mostly orphaned.
Cause: the range search orders leaves by code and breaks ties by leaf index (Karras 2012's augmented delta). The split search compared codes only, so a range whose leaves all share one code collapsed onto its first leaf.
Fix: the split search now uses the same augmented delta. Where a range's first and last codes differ, both forms make the same decision, so only trees with tied ranges change. static_radix was never affected.
Tests:
Y2's strict xfails are removed.
New test_duplicate_positions_leave_no_leaf_unreachable (28 and 64 copies × static_radix / build_tree / build_octree): one root, every leaf reachable, and the root spans every particle.
Both tests fail on main for the adaptive builders.
2. Every walk route applies the kd-tree Dehnen radius default (b3e3964)
A kd-tree's Dehnen MAC defaults to dehnen_radius_scale=1.2 when the caller leaves it at 1.0. Only the joint walk applied that. The bounded count-pass routes walked at 1.0: build_leaf_neighbor_lists, build_well_separated_interactions and build_compact_far_pairs_and_leaf_neighbor_lists, each with a traversal config. They returned 1,710 near pairs against the joint walk's 2,408 (N = 512, leaf 8). So a caller that mixed routes got a far/near partition with gaps.
Fix: _resolve_dehnen_radius_scale holds the rule, and all four routes call it.
Test: test_walk_builders_agree_with_the_joint_walk[octree, kdtree] checks every builder's near and far pairs against the joint walk. The kd-tree case fails on main.

When more than leaf_size particles share one Morton code -- duplicate
positions, or padding rows that copy a real particle (sanitize_padding) -- the
adaptive build (build_tree, and the octree built on it) returned a forest:
several parent == -1 nodes, and leaves no walk from the root reaches, whose
particles then get no force and exert none. 64 copies of one point among 128
(leaf 8): 6 roots, 5 of 16 leaves unreachable; 28 copies: 2 roots, 1 leaf.

The range search already orders leaves by code and, where codes tie, by leaf
index (Karras 2012's augmented delta). The split search compared codes only,
so a range whose leaves all share one code found no split above its own
prefix, collapsed onto its first leaf and orphaned the rest. It now uses the
same augmented delta. Where a range's first and last codes differ the two
forms make the same decision, so only trees with such tied ranges change.
static_radix was never affected. _lcp_codes_only had no other caller.

Tests: test_tree_builders_degenerate_tied_codes_are_valid loses its strict
xfail on build_tree and build_octree (Y2 pinned the bug there);
test_duplicate_positions_leave_no_leaf_unreachable (new; static_radix,
build_tree, build_octree x 28, 64 copies) checks one root, every leaf reachable
and the root spanning every particle. On main both fail for the two adaptive
builders and pass for static_radix.
