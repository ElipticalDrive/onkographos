Closes #27.
Sensor frustums used to be one uniformly scaled cone/pyramid running to the catalog range or the target's center. A body hid the cone only from the current viewpoint, so rotating the camera exposed geometry that should have stopped at the surface. The FOV is now a perimeter of rays from the instrument, each ending at the nearest eligible physical surface hit and otherwise at the maximum visualization range.
surface/FovClipper (pure, no renderer state):
Samples the perimeter: around ellipses, and along every edge of polygons.
Adaptive bisection at hit/miss and body-to-body transitions.
Between two missing samples, one probe ray at the closest approach to each candidate, found in the reference ellipsoid's scaled space. This is exact for reference shapes however short the interval, so a grazing body whose limb crosses only mid-interval is found.
Hit-hit smoothing driven by range deviation, i.e. the surface bending, not the outline's own curvature.
Nearest hit across all bodies.
surface/ReferenceEllipsoidSurface: analytic PhysicalSurface for body radii, tagged reference-shape so it is never presented as terrain.
surface/ResidentTerrainSurface: bounded query over resident decoded tiles through the shared GlobeTileSurface path. Results are always partial/coarse.
Fallback rule: only unavailable falls through to the reference shape. A complete mesh's miss is authoritative, so the Define shared physical-surface queries and independent imagery contracts #148 concave fixture keeps its hole.
SensorFovClipping (renderer-owned):
Resolves visible Globe bodies' surfaces and body-fixed frames each frame.
Memoizes per sensor while epoch, origin and resident terrain are unchanged.
Caps terrain triangle tests per frame, checked per sensor. Sensors past the cap use the reference shape for that frame, flagged fallback.
SensorFrustum only builds geometry: side faces, perimeter, side lines, no end cap.
CpuMeshSurface: allocation-free intersection loop with identical results, about 5× faster.
SPICE outlines: RECTANGLE/POLYGON bounds drive the drawn perimeter when the frustum is SPICE-oriented.
Defaults and diagnostics: clipping is on by default. clipSensorsToSurfaces / setSensorClipping(false) show the raw FOV. getSensorClipSummary reports bodies, surface source (reference/terrain/mesh), coarse and fallback.
Scope: viewer clipping covers solid Globe bodies (reference ellipsoid, plus resident streamed terrain). Irregular Mesh bodies such as 67P are supported by the pure clipper and its tests, but not yet integrated into the viewer. That is tracked in #175, together with the BVH the #148 ADR anticipates. No catalog changes: range remains a maximum visualization range.
Performance (Node, real marshub tiles): a terrain-clipped sensor costs ~1 ms/frame, down from ~15.8 ms before review. 20 terrain sensors cost ~5.7 ms/frame in total, with terrain work capped at ~3 ms. Reference-only clipping costs ~0.1–0.3 ms per sensor.

Review of #174: the architecture aligns well with #27 (pure surface resolver, renderer-owned candidate selection, SPICE polygon bounds, provenance, and useful tests). However, I found one blocking correctness issue plus a significant playback-performance risk. Please address these before merging.
Blocking — missed grazing surface intersections: hiddenBetween assumes an interval shorter than a body's angular radius cannot hide an intersection between two misses. This is false; a grazing body can hit the midpoint while the endpoints miss. See the inline deterministic reproduction and requested regression test.
Playback cost: The resident-terrain path calls the linear triangle-scanning CpuMeshSurface for every perimeter ray/refinement, with the memoization invalidated each advancing epoch. Please profile real Mars terrain and several active sensors during playback and either accelerate queries or bound/degrade the terrain pass until it is safe.
Scope clarity: The renderer filters out Mesh bodies, so only the standalone clipper tests support concave meshes; the live viewer cannot yet clip an FOV at 67P/other irregular bodies. This is acceptable for #27's explicit reference-first scope, but please document and track the renderer integration.
I would also do a manual smoke check rotating the camera behind a grazing FOV and running an instrument over loaded Mars terrain during time playback.
CI on head 755eab8 is green, but that doesn't cover the grazing counterexample.
