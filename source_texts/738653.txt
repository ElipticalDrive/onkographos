What needs to be built:
Swap the SpatialIndex trait's (#32) implementation from the Phase 1 grid baseline toward the density-adaptive "Z" target — a quadtree/octree, or a pinned off-the-shelf spatial crate (the proposal names rstar as an example) — driven by real load data from an actual deployment, not done speculatively.
Context / why:
docs/PROPOSAL.md "Spatial Index: A → Z Roadmap": "a density-adaptive index... swapped in behind the same SpatialIndex trait once real deployments produce load data that justifies it — dense towns vs. sparse wilderness, dynamic entity counts, etc. External crates are acceptable here with pinned versions; this is not a place to reinvent well-solved computational geometry." This ticket should not be started until there's actual evidence the grid baseline is the bottleneck — starting it speculatively contradicts the stated rationale for why A was built first.
Acceptance criteria:
A concrete performance problem with the grid baseline is documented first (real profiling data, not assumption) before implementation starts
New implementation satisfies the same SpatialIndex trait from world: SpatialIndex trait + grid baseline implementation #32 — no caller code changes required
If using an external crate, it's pinned to a specific version per the proposal's guidance
Benchmarked against the grid baseline on the same workload to confirm it's actually an improvement for the case that motivated it
Related: Epic #64 (Phase 2), depends on #32; do not start without a documented load-data justification
