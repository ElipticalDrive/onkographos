Summary
Replace bitonic sort with radix sort in the GPU BWT suffix array construction. LSB-first 8-bit radix sort (8 passes) replaces bitonic sort's O(log²n) kernel launches per doubling step. New kernels: bwt_radix.cl (compute_keys, histogram, scatter) and bwt_rank.cl (compare, prefix_sum, propagate, rank_scatter) move rank assignment to the GPU via parallel Blelloch scan.
Adaptive key width: skip radix passes where digits are guaranteed zero based on max_rank. First doubling step uses 2 passes instead of 8; later steps scale up as ranks grow (4 for <64K, 6 for <16M, 8 otherwise).
Event chain batching: replace per-kernel .wait() calls with OpenCL event dependencies. All run_* methods accept wait_event: Option<&Event> and return Event. Only one host sync per doubling step (the convergence scalar read).
Fix critical bug: enqueue_read_buffer offset was in elements instead of bytes, causing convergence detection to read garbage.
Remove dead bitonic sort code, add FSE benchmark, expand all benchmarks with large size tiers.

Key design decisions
GPU uses circular comparison (sa[i]+k) % n vs CPU SA-IS's doubled-text approach. Both produce valid BWTs that round-trip correctly, but byte output may differ for periodic inputs. Tests use round-trip verification.
Radix sort histogram uses column-major layout (hist[digit * num_groups + group_id]) so the existing prefix sum produces global scatter offsets directly.
Scatter kernel uses sequential per-workgroup processing (thread 0 only) for stability — simple and correct.

The GPU BWT was 14-640x slower than CPU due to bitonic sort's O(log²n)
kernel launches per doubling step. This replaces it with LSB-first 8-bit
radix sort (8 passes per step) and moves rank assignment from sequential
CPU readback to parallel GPU prefix sum (Blelloch scan + scatter).

Key changes:
- New kernels: bwt_radix.cl (compute_keys, histogram, scatter) and
  bwt_rank.cl (compare, prefix_sum, propagate, rank_scatter)
- Fix critical bug: enqueue_read_buffer offset is in bytes, not elements
- Remove dead bitonic sort code (kernel compilation + method)
- GPU BWT tests use round-trip verification (GPU circular prefix-doubling
  produces valid but not byte-identical output vs CPU SA-IS for periodic inputs)
- Add FSE benchmark to stages.rs, expand all benchmarks with large sizes
  and timeout caps

GPU BWT throughput improved ~1.8x at 64KB (56ms → 31ms) but remains
slower than CPU — future work needs fused kernels or a different algorithm.

Two optimizations that reduce GPU BWT time by 4-9x at small/medium sizes:

1. Adaptive key width: skip radix passes where digits are guaranteed zero.
   If max_rank < 256 (e.g. first doubling step), only 2 passes instead
   of 8. Passes scale up as ranks grow: 4 passes for <64K, 6 for <16M.

2. Event chain batching: replace per-kernel .wait() with OpenCL event
   dependencies. All run_* methods now accept wait_event and return Event.
   Only one host sync per doubling step (the convergence scalar read).

Benchmark results (vs previous radix sort commit):
  1KB:   29.8ms → 3.4ms  (8.8x faster, 295 KiB/s)
  10KB:  33.1ms → 5.9ms  (5.6x faster, 1.6 MiB/s)
  64KB:  30.8ms → 4.1ms  (7.5x faster, 15.3 MiB/s)
  256KB: 48.8ms → 11.6ms (4.2x faster, 21.6 MiB/s)
  4MB:   562ms  → 333ms  (1.7x faster, 12.0 MiB/s)
  16MB:  2.50s  → 1.73s  (1.4x faster, 9.2 MiB/s)

* Optimize parallel LZ77 thresholds, add GPU prefix sum and Deflate chaining

Parallel LZ77 improvements:
- Raise MIN_PARALLEL_SIZE from 64KB to 256KB to avoid thread overhead
  dominating at small sizes (was 8x slower, now correctly falls back)
- Add MIN_SEGMENT_SIZE (128KB) to cap thread count: each thread must
  process enough data to amortize the 32KB hash-chain warmup cost
- Skip warmup for the first segment (starts at position 0, no prior context)
- Reduce test data sizes to keep debug-mode test times under 60s

GPU prefix sum (Blelloch scan):
- New PrefixSumBlock kernel: work-efficient parallel scan within work-groups
  using local memory, with block totals output for multi-level reduction
- New PrefixSumApply kernel: adds block offsets after recursive scan
- Multi-level recursive scan handles arbitrarily large arrays
- Replaces CPU prefix sum in Huffman encoding, eliminating host round-trip

GPU Deflate stage chaining:
- New deflate_chained() method: LZ77 → Huffman on GPU without intermediate
  host download of LZ77 data for the prefix sum step
- Integrated into pipeline: Deflate with OpenCL backend uses chained path
  for inputs >= MIN_GPU_INPUT_SIZE (64KB)
- New huffman_encode_gpu_scan() uses GPU Blelloch scan instead of CPU

Benchmarks added for GPU Huffman (CPU vs GPU scan) and GPU chained Deflate.

Post-optimization parallel LZ77 results (Canterbury corpus):
  65KB: 2t/4t/8t now fall back to 1t (was 8-16x slower, now no overhead)
  1MB 8t: ~24 MiB/s (thread overhead still significant for match-finding)
