Hi, following the contribution guidelines, I would like to ask whether a single-threaded block LSD radix sort would be relevant to this project's research before working on an integration.
The algorithm is based on Robert Clausecker and Florian Schintke's Parallel O(sqrt(n)) Overhead LSD Radix Sort and the authors' reference C implementation. It reuses consumed input blocks and tracks their logical order with permutation metadata, preserving stability without a full-size output array.
I have a Rust adaptation under development for voracious_sort. It has not been merged into that project's upstream or published in a crate release. A single-backend implementation snapshot is available. The implementation is generic over records and radix keys (T: Radixable<K>, K: RadixKey), including signed and unsigned integers, floating-point keys, and custom key-and-payload records satisfying the library's trait bounds, including Copy.
This is an adaptation with changes from the reference, rather than a direct translation:
Our own adaptive block-size policy. Instead of the reference's fixed 512-record blocks, the public entry point chooses the block size from input length, record size, and radix. For n records of s bytes and R = 2^radix buckets, it uses max(1, ceil(4 * sqrt(9*n / (2*R*s))), floor(1024/s)) records per block. The square-root term comes from balancing estimated scratch and block-metadata costs. The factor 4 and approximately 1 KiB floor are our experimentally tuned choices for 8-bit digits, not parameters prescribed by the paper or proven optimal across configurations. This retains O(sqrt(n)) auxiliary space for fixed radix and record size.
Generic key widths and configurable digits. The code handles converted key widths including 128-bit keys, supports 1–8 bits per digit, and handles a partial final digit, instead of the reference's four byte passes over 32-bit keys.
Skipping constant digits. A union/intersection pre-scan identifies digits that cannot change record order. It can finish after a prefix when every key bit already varies; otherwise it scans the remainder. Constant inputs return without scattering. The research snapshot has no comparison-sort or conventional stable-LSD fallback: every nonconstant input uses the same block backend for its varying digits.
Scatter-loop changes. Small records are processed in groups of up to four to reduce loop-control overhead, while larger records stay scalar. Scatter has a separate optimization boundary from pass setup and block reordering. These choices were evaluated with local ablations.
Rust storage and metadata handling. Scratch uses MaybeUninit<T> with explicit initialized-prefix tracking, rather than assuming arbitrary generic records can be zero-initialized. The implementation adds lifetime, allocation/index, and debug invariant checks, and reuses the counts allocation for bucket start offsets instead of allocating a separate starts vector per pass.
The snapshot has passed local release/debug integration tests, an all-features release test run, and ASan integration tests in voracious_sort. Coverage includes integer widths through 128 bits, floating-point keys, and stability/payload checks for custom records. These checks are separate from this repository's functionality and safety tests, which have not yet been run against this implementation.
The research question would be how block reuse affects runtime and memory usage across input sizes, record sizes, and patterns compared with conventional out-of-place LSD and comparison-based stable sorting. The existing rust_radsort_radix wraps Jakub Valtar's radsort crate, which is a different implementation from Clausecker's similarly named project. I have not integrated or benchmarked this candidate in your harness and am not claiming a performance advantage here.
The integration would follow the repository's existing adapter conventions in src/other, benchmark types and patterns, and functionality-test requirements. Key adapters for the repository's benchmark types would need to preserve their existing ordering semantics. Unsupported types or operations such as arbitrary sort_by would be explicit, following the existing radix adapters, with no hidden comparison-sort fallback. Stability would also be checked with key-and-payload records. Source attribution and license notices would be retained.
Would this be useful to investigate here before the voracious_sort upstream contribution? If so, would you prefer a pinned Rust dependency or a vendored implementation?
