Replaces the PMREM atlas with cube render targets in WebGLRenderer and WebGPURenderer.
Quality: Closer to Blender Cycles, with 37–82% lower mean RGB error on the Royal Esplanade, Pisa, Spot1Lux and Venice Sunset sphere grids compared with dev (sphere interiors, matching ACES tone mapping). Reduces aliasing in near-mirror reflections.
Correctness: Corrects excess brightness at high roughness. White-furnace tests stay within 0.05% of unit energy for metals and dielectrics across WebGL, WebGPU and its WebGL fallback.
Rendering: Lower synchronized frame time in a 30-sphere, 1080p scene on Apple M1: ~25% in WebGL, ~16% in WebGPU, and a modest ~3% in its WebGL fallback. PMREM generation is excluded.
Generation: Slower for the tested 1K HDRI, faster for the tested 2K HDRI on all three backends.
Memory and downloads: The prefiltered KTX2 environments use ~33% less GPU texture memory at the same 512px face resolution (3 MiB → 2 MiB). Total file size drops from 15.09 MB to 14.10 MB (~6.6% smaller).
Apple M1, dev (b6493e1cfa) → this PR (19bdd854e1), in milliseconds. Warm measurements wait for GPU completion after each generation or frame; loading and compilation are excluded. Medians of 63 alternating pairs across three runs for 1K and rendering, and 21 pairs for 2K. Frames use precomputed PMREMs without MSAA; these are render latencies, not displayed FPS.

PMREM: Stop blending into the second mip level below its resolution.
…
4c8ce9d
```
The sharpest level is already blurred by one of its texels, so a GGX lobe narrower than that cannot be represented. Sampling ignored this and blended toward the level prefiltered for a much higher roughness, which spread small bright lights into halos on nearly smooth surfaces.

roughnessToMip() now removes the blur the sharpest level already has before mapping roughness to a level, leaving everything above that resolution untouched.
```

@mrdoob I've spend my time today to closer debug how the PMREM works now.
The new storage approach (cubemap) of a PMREM is fine and it matches what other engines do.
However, there are two changes in the PR that are not 100 % correct:
The first one is how the minimum roughness is computed:
three.js/src/renderers/shaders/ShaderChunk/lights_physical_fragment.glsl.js
Lines 10 to 11
in
6101189
// GGX width scales with roughness squared; large normal variation needs a linear floor.
float roughnessFloor = max( 0.4 * sqrt( geometryRoughness ), geometryRoughness );
The second one is how roughness are mapped to mipmaps:
three.js/src/renderers/shaders/ShaderChunk/envmap_common_pars_fragment.glsl.js
Lines 11 to 21
in
6101189
float roughnessToMip( const in float roughness ) {
float r = clamp( roughness, 0.0, 1.0 );
// Subtract the base level's texel footprint from the GGX lobe.
float texelAngle = 1.5707963267948966 / float( ENVMAP_SIZE ); // a cube face spans PI / 2 radians
r = sqrt( sqrt( max( r * r * r * r - texelAngle * texelAngle, 0.0 ) ) );
return ENVMAP_MAX_LOD * r * ( 2.0 - r );
}
What currently on dev goes wrong is the completely missing filtering with very low roughness values. You essentially get an unfiltered mirror and that is a quality regression, imo.
When I understand it correctly, the root cause is roughnessToMip() can currently return 0 which means the unfiltered base level. But that should never happen for any value a user assigns to material.roughness. Even 0. That's what the old 0.0525 constant guaranteed. The new roughnessFloor drops to zero on flat geometry so you end up with an unfiltered texture.
Please be aware that restoring the previous minimal roughness isn't enough on its own: roughnessToMip( 0.0525 ) still returns 0 at 256 and 512 PMREM resolution, so a nonzero roughness is still mapped to the unfiltered base level. So roughnessToMip() needs a fix as well.
I've realized a fix heavily depends on with what reference you want to align the PMREM with. In below branch, I've added a Filament version of roughnessToMip() and Filament's Desktop minimum roughness constant. As expected, that visually changes the output with low roughness. You get more bloom on highlights, a better roughness ramp and slightly softer but properly filtered, stable results with low roughness.

Do you know why the rougher spheres are now darker on the lower half when compared to the master branch?
Prod over-blurred the diffuse lighting. So light from above leaked onto the undersides. The PR fixed that.
It computes the diffuse lighting as the cosine-weighted hemisphere a Lambertian surface receives. Prod approximated it with a chain of blurs that came out too wide.
So in that regard, the PR is correct and a real improvement, imo.
BTW: Dev and Prod both pick the indirect diffuse from the last mip. The way how it is generated is completely different though.
