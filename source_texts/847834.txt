Phase 2 of docs/todo/SLAB_READ_PERF_PLAN.md: a decoded-chunk cache under read_native.
The viewer reads 128² bricks through all z. Every store is one z-plane per chunk (512² or 1024²), so one brick decodes 16–64x the bytes it keeps, and the 64 bricks of a timepoint all decode the same chunks. The cache keeps the decoded chunks, so after the first brick, the rest of a timepoint are copies.
How it works (api/src/chunk_cache.jl)
Same results: read_native assembles the block from cached chunks and applies the byte-order swap afterwards, exactly as before. Shapes, dropped integer dimensions and BoundsError all match arr[idx...], which the tests check.
Single-flight, claim-first: each chunk is decoded once even under 16 concurrent bricks (measured: exactly 124 decodes per raw timepoint). A read decodes chunks nobody else holds first, starting at a random offset, and only then waits on the rest. Walking chunks in one shared order made a cold scrub slower than no cache.
Only partial-chunk reads: a read that uses every chunk it touches in full (whole volumes, 2D planes, aligned tiles) bypasses the cache. Through the cache, those were 1.4–2.7x slower cold and no faster on a revisit.
No stale reads: the key is the level directory's (path, inode, mtime). Writers stage and promote, so a rewrite arrives as a new directory. .partial stores, which are read while being written, are never cached.
Bounded: LRU by bytes. Settings → Storage → Server read cache (not "viewer cache", which is already the browser's VRAM budget): auto = 1/16 of RAM, clamped to 256 MiB–4 GiB; or Off, or 512 MB–32 GB. It applies to the running server, no restart. Counters are in /api/diagnostics → chunkCache.
Off until the server starts it: start() sets the budget, so spike scripts and tests keep measuring real decodes.

Whole-movie sweep (181 timepoints, 1 GB budget): the cache peaks exactly at budget, each chunk is decoded once, and it takes 26.5 s.
Flat volumes: unchanged, within run-to-run noise.
Reservations
Through the server, the response path is now the limit. Raw scrub 4.9–6.3 → 2.3 s (1.9 s revisit), derived 1.72 → 1.57 / 1.02 s; server read per brick about 300 → 21 ms. Each brick now spends about 110 ms in transfer against about 20 ms reading: HTTP.jl buffers a Content-Length body whole before writing it. That's the next bottleneck for bricks and flat volumes alike, and it's outside this plan.
One-off JIT cost: the first slab request after start pays about 1 s compiling the cache path.
Carve-out widened (plan Decision 11): the cache is included by image_render.jl, still the only file with using Zarr, and reads chunks only.
No prefetch: the claim-first cold pass already lands close to the revisit times, so I didn't build it.
Python suite: one unrelated failure locally, a denoise-trainer smoke test that hit the free-VRAM guard because the GPU was in use. This branch touches no Python.
