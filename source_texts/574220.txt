Summary
Fixes the signed distance function (SDF) for the octahedron geometry in hyperbolic_func within SmallPT.cpp.
Details
Replaced the astroid/superellipsoid power formula (pow(..., 2./3.)) with the exact octahedron SDF formula utilizing std::abs() (|x| + |y| + |z| - r).
Removed outdated //TODO comments regarding distance function validation.
Added code comments explaining the geometry transformation and distance calculation.
Testing
Verified via direct point evaluation on rotated boundary vertices. The updated function returns 0 (within double precision limits ~1e-16), whereas the old implementation resulted in an error margin of ~0.225.

This changes one of four places that spell out the same solid, and leaves the other three saying the old thing. HyperbolicSolid::distance_func, further down this file, still holds the pow(..., 2./3.) formula, and that is the one the renderer uses: ImplicitSolid::intersect ray-marches by stepping fabs(distance_func(pt)), while hyperbolic_func is only ever called to get the normal. The demo would now trace one surface and shade it with the normals of a different one. The three h_func_d* functions under TEST_TYPE_BY_HAND are derivatives of the 2/3-power formula too, so that path splits the same way.
Before changing those, it is worth deciding which solid was meant, because I do not think it was an octahedron. The surface x^(2/3) + y^(2/3) + z^(2/3) = r^(2/3) is the astroidal ellipsoid, whose other name is the hyperbolic octahedron. That is where hyperbolic_func and HyperbolicSolid get their names, and it explains the TODO you removed: it does not look like an octahedron because it is not one, it has concave faces. The bug the TODO was chasing is somewhere else. pow with a negative base and a non-integer exponent is a domain error and returns NaN, so every point outside the all-positive corner of the rotated frame evaluated to NaN and there was nothing to see. Wrapping each base, pow(std::abs(x_rot), 2./3.) and so on, fixes that, keeps the solid the file is named after, and leaves the hand-written derivatives correct. Putting a real octahedron here instead is a reasonable thing to want, but then say so in the commit message and change the other three places with it. Worth noting the check in the description does not separate the two: the six axis vertices lie on both surfaces, so the old formula returns 0 there as well.
On tests, test/Misc/RunDemos.C compiles this file, so a build break here would be caught. Nothing runs it, and scene[] never constructs a HyperbolicSolid, so no test in the tree observes the maths in either direction. That is fine for a demo fix, but it does mean review is the only check this gets. The head commit also has no check runs at all, so nothing has compiled it yet.
I read the code rather than building or rendering it.

This is not a distance, and two things here read it as one. |x| + |y| + |z| - r is the distance to the nearest face plane multiplied by sqrt(3). ImplicitSolid::intersect sphere-traces by stepping t += fabs(distance_func(pt)), which needs a value that never overshoots the surface. And HyperbolicSolid::normal returns the clad gradient without normalising it, on the comment that a signed distance function has a unit gradient; the gradient of this one is a rotated (1, 1, 1) with signs, whose length is exactly sqrt(3), so every shading dot product comes out 1.73 times too large. Scaling by 1/sqrt(3) fixes both. This only applies if the octahedron is what you settle on.
Suggested change
return std::abs(x_rot) + std::abs(y_rot) + std::abs(z_rot) - r;
// 1/sqrt(3): |x|+|y|+|z|-r is the distance to the nearest face plane times
// sqrt(3). Scaling it down never overshoots the surface, which the sphere
// trace in ImplicitSolid::intersect needs, and makes the gradient a unit
// vector, which HyperbolicSolid::normal assumes.
return (std::abs(x_rot) + std::abs(y_rot) + std::abs(z_rot) - r) *
0.5773502691896258;
