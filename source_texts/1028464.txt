Use case
A renderer and a compute worker each own a thread-confined RHI context, but the contexts wrap the same native VkDevice and VkQueue. CPU command recording can proceed independently; calls that access that shared queue on the host must follow Vulkan's synchronization requirements.
Relevant queue calls occur through both the public command queue and internal helpers: submission, buffer initialization/readback, presentation, and swapchain teardown. Locking only an application's public submit() call does not cover all of these paths.
Downstream workaround and its limitation
A downstream patch routes queue submit, present and idle calls through one process-wide mutex. That prevents overlapping covered host calls, but it also serializes unrelated queues/devices and holds the global lock through an idle wait. It is not the design proposed for upstream.
Requested design discussion
Could native-device/queue import support an explicit shared synchronization object, or another documented mechanism shared by all wrappers of the same native queue?
The critical section should cover only host operations requiring queue synchronization, not ordinary CPU recording or completion polling. Queue identity and lifetime must be handled correctly; a mutex attached separately to each RHI wrapper is insufficient. Native calls made outside RHI must participate in the same protocol, or be explicitly prohibited while RHI owns access.
This is host synchronization for one native queue, not Vulkan/CUDA external-memory ownership transfer and not a claim that all RHI device methods become thread-safe.
Validation
Exercise two contexts submitting from separate threads, concurrent internal upload/readback paths, presentation and surface teardown under validation. Also test separate native queues/devices to ensure they do not acquire an unnecessary common lock. Check that idle-wait handling cannot prevent unrelated progress and that device destruction retires every user of the synchronization object.

Triage — design-discussion / enhancement (needs maintainer design input)
Confirmed the mechanism and the underlying hazard against main @ e17f6d7 (source only — a data race isn't GPU-free reproducible, so no reproduced label):
The shared native queue is real and needs no explicit import. DeviceNativeHandles carries only instance/physicalDevice/device (include/slang-rhi.h:3431-3433); the VkQueue is always fetched via vkGetDeviceQueue(m_device, m_queueFamilyIndex, 0, …) (src/vulkan/vk-device.cpp:1857), so two DeviceImpl wrapping the same native VkDevice receive the same VkQueue handle.
Queue host-calls are entirely unguarded today — and this is already latent within a single Device, not only across contexts. Two internal submitters (CommandQueueImpl::submit vk-command.cpp:2131; VulkanDeviceQueue::flushStepA vk-device-queue.cpp:124), plus present/teardown (vk-surface.cpp:578 / :392) and both vkQueueWaitIdle sites (vk-command.cpp:2143, vk-device-queue.h:42), all touch the same handle with no lock. The existing mutexes guard only the command-buffer pool.
The lifetime caveat you flagged is confirmed: destroying one DeviceImpl runs vkQueueWaitIdle on the shared queue (~DeviceImpl → waitOnHost / flushAndWait, vk-device.cpp:152,158), idling the other wrapper's in-flight work; the imported instance/device are (correctly) not destroyed.
Solution space (full detail in triage notes — not selecting one; this is a design call):
A — app-supplied shared sync object via native import. Only an app-shared object can satisfy your hard requirement that native calls made outside RHI participate; cost is new public API/ABI surface.
B — library-owned per-native-queue lock registry (keyed on the VkQueue handle, refcounted, retired with the last wrapper). No API change and avoids the global-mutex over-serialization — but a library-private lock can't be shared with the app's own raw calls.
C — document the app-synchronized contract + expose queue identity (getNativeHandle already returns {VkQueue, …}, vk-command.cpp:2148), plus a single internal choke-point so an app lock can reach RHI-internal submits.
Recommended starting point: a design-neutral prerequisite worth doing regardless — route all six internal queue host-calls through one guarded wrapper (a single choke-point that also closes the latent intra-Device hazard) — then layer the shareable object (A) on top, with the public-API shape as a maintainer decision. Agreed the process-wide static mutex should not land as-is.
Next step: maintainer design input on the public contract before implementation. Happy to prep a draft of the design-neutral choke-point consolidation on request.

Obviously I favour A, with B as the safe default... one shared synchronization object per native queue, auto managed but accessible to native integrations. That fits independent (e.g. in my heavy PoC renderer/worker) contexts without forcing coarse application-level locking.
My train of thought. All RHI wrappers of the same queue should share that object, with an explicit mechanism for application-owned native calls to participate. Different queues should remain independent. Lock around the submit/present/queue-idle calls including internal helpers, not CPU recording or fence/timeline waits. Resolve and retain the shared object when creating/importing the context, rather than performing registry lookups on every submission. This should introduce no additional GPU waits.

Thanks — that lines up with the recommended hybrid (B as the safe default, A layered on top for sharing). A few specifics I'd affirm:
Resolve-and-retain the shared object at context create/import (rather than a per-submit registry lookup) is a good refinement — it removes any hot-path lookup cost and gives the object a clean lifetime tied to the set of wrappers.
Guarding submit / present / queue-idle including the internal helpers (and leaving CPU recording and fence/timeline waits outside) matches what the code needs: today those internal submitters — CommandQueueImpl and VulkanDeviceQueue, plus surface present/teardown — all touch the one shared VkQueue unguarded, so the lock has to sit at that shared choke-point, not on the public submit() alone.
Three constraints the design must keep: out-of-RHI native calls can participate in the same object; distinct queues stay fully independent (no common lock); and the object is correctly retired when the last wrapper (device) of a queue is destroyed.
On the public-API shape — how the shared object is exposed/supplied at native import — I'll defer that to a maintainer; I'm not authorizing an API design or committing to an implementation here.
One piece that is safe and useful regardless of the eventual API: the design-neutral choke-point consolidation — routing all six internal queue host-calls through a single guarded wrapper. That's available as a first step whenever a maintainer greenlights the direction, and it closes the confirmed latent intra-Device hazard on its own.

app-owned lock state passed through a Vulkan-specific desc chained to DeviceDesc. Every RHI device wrapping the same VkQueue gets the same userData and callbacks... the queue handle lets the app keep locks for distinct queues independent. RHI would call them around each queue host operation that requires external synchronization, including internal helpers. The app would use that same lock state around its own direct Vulkan calls.
```
struct VulkanQueueHostSyncDesc
{
    static constexpr StructType kStructType = StructType::VulkanQueueHostSyncDesc;
    StructType structType = kStructType;
    const void* next = nullptr;

    void* userData = nullptr;
    void (*lock)(void* userData, NativeHandle queue) = nullptr;
    void (*unlock)(void* userData, NativeHandle queue) = nullptr;
};
```
