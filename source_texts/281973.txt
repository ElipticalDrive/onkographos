In one sentence: With normalization_scheme='instance_minmax', 'instance_zscore' or 'percentile_minmax', a 2D slice such as scroll[z, :, :] is now normalized as one image. Before, every row was normalized on its own.
One real example: I opened Scroll 1 with Volume(type="scroll", scroll_id=1, normalization_scheme="instance_minmax") and read plane z=125 of level 3 (z=1000 at full resolution) as v[125, :, :, 3]. That plane is 986 x 1012.
Before: On main, every one of the 986 rows of that slice has its own min of 0 and max of 1, because each row was min-max scaled separately. Reading the same plane as 3D (v[125:126, :, :, 3][0]) gives different values, up to 0.4032 apart. Viewed as an image, the slice shows horizontal streaks. instance_zscore gives every row mean 0. A single-voxel read with an instance scheme raises IndexError.
After this PR: The 2D read equals the same plane read as 3D, and equals the min-max formula applied to the whole plane. The max difference is 0.0000. Only 5 of the 986 rows now reach both 0 and 1. 3D reads and normalization_scheme='none' are unchanged.
Proof:
Same script, same plane, run on main and on this branch:
```
main:      max |2D read - same plane read as 3D| = 0.4032
           rows whose own min is 0 and max is 1: 986 of 986
this PR:   max |2D read - same plane read as 3D| = 0.0000
           rows whose own min is 0 and max is 1: 5 of 986
```
Why / where this is useful: Anyone who views or processes single slices through Volume with one of these schemes gets wrong values today without any error. example1_data_access.ipynb does this: it opens Scroll 1 with instance_minmax (cell 14) and then plots scroll[7000, 4600:4800, 4000:4200] (cell 22). The Volume docstring says these schemes are "computed per slice/volume instance", so per-row results contradict the documentation.
I personally verified that the example and proof above were produced by this PR on the stated data.
Details
Cause. Volume.__getitem__ added its temporary channel axis only when the read was 3D (original_ndim == 3). The three per-instance schemes then loop for c in range(data_slice.shape[0]). On a 2D read, dim 0 is y, so the loop normalized each row. On a 0-d read there is no dim 0, so it raised IndexError.
Change. The temporary axis is now added to any read that has no channel axis, but only when a normalization scheme is set. It is removed afterwards, so the returned shape is unchanged. global_zscore and ct are element-wise and return the same values as before. With 'none', nothing is touched, so a raw read still returns the stored dtype.
Tests (vesuvius/tests/data/test_volume_normalization.py, new, uses only a local zarr in tmp_path):
For each instance scheme, a 2D read equals the same plane read as 3D and equals the reference formula; the y gradient survives.
1D reads match the formula; 3D reads are unchanged; a single-voxel instance_zscore read returns 0 instead of raising.
global_zscore on a 2D read, and 'none' returning raw uint16 values.
Before the fix 7 of these 12 tests fail; after it all 12 pass. The existing tests/data suite passes under zarr 3.2.1, 3.4.1 and 2.18.7. Tested on Windows 11 with Python 3.14.4.
Prepared with AI assistance (Claude Code); the commands and outputs above were run on the stated data.
