Triage update — 2026-09-16
Review baseline: main 524a1df.
Disposition: Keep open with narrowed scope.
Current assessment and challenge: Single-tile cylindrical voxels shipped; octree LOD and mosaic are the remaining expansion, not absent voxel support.
Next step / remaining scope: Keep this open for octree LOD and mosaic requirements. Build on the existing single-tile cylindrical voxel implementation.
Original report / roadmap (historical context; current scope is above)
Part of #346. The Tier-B high-fidelity track (draft spec, CesiumJS-only today).
Move from point clouds to true volumetric voxels + LOD + multi-radar mosaic.
Scope
Cylindrical voxels: encode VoxelGrid as glTF with EXT_primitive_voxels (cylinder shape, dims [radius, angle, height]) + 3DTILES_content_voxels + 3DTILES_bounding_volume_cylinder. The azimuth axis maps 1:1 from radar rays; radius/height via 4/3-Earth. Quantities → EXT_structural_metadata SCALAR properties with noData.
Implicit OCTREE tiling + .subtree availability for sparse coverage.
National mosaic: stitch N sites into one octree with geometricError-driven LOD; honour per-site coverage envelopes.
Client-side isosurfaces / CAPPI slices / threshold (the payoff over point clouds).
Risks / notes
Draft extensions, CesiumJS-only, spec in flux (axis-reorder rule [radius,angle,height]↔[radius,height,angle] between the two extensions). Keep Tier-A .pnts/mesh as the always-works fallback.
Bandwidth: quantize to UINT8/16, exploit noData sparsity, octree LOD for the mosaic.
Done when
A single site renders as voxels in a recent CesiumJS build.
(Stretch) a multi-site mosaic with octree LOD.
Status update — CesiumJS voxel support as of 1.142 (2026-06-09)
Checked the current state of the voxel path (was "≥1.127" in our notes; CesiumJS is now 1.142, 2026-06-01). It has matured and settled — a burst of breaking refinements through 2025, then quiet:
Version
Voxel change (relevant to this issue)
1.127 (Mar '25)
Cesium3DTilesVoxelProvider realigned to load glTF tiles via EXT_primitive_voxels; the old custom-JSON voxel format dropped
1.129 (May '25)
Breaking: VoxelProvider.min/maximumBounds are now physical values, not shape-space
1.130 (Jun '25)
Voxel shader FragmentInput reworked to eye-coordinate attrs; 3D-texture support + a Volume Cloud sandcastle (ray-march transfer-function reference); orthographic-camera fix
1.135 (Nov '25)
Breaking: voxel rendering requires WebGL2 (default since 1.101)
1.138 (Feb '26)
Memory: Megatexture → Texture3D (helps large grids — relevant vs our MAX_VOXELS = 32M)
1.139–1.142
no voxel changes — settled
Still labeled experimental in 1.142, but stabilizing. EXT_primitive_voxels remains a draft glTF/3D-Tiles extension and CesiumJS-only — keep Tier-A .pnts/isosurface/echo-top as the always-works fallback (now also time-dynamic, #350).
Implications for this issue
Target CesiumJS 1.142 specifically and render-verify (the 2025 API churn makes "≥1.127" too loose). Bump the "recent CesiumJS build" Done-when to 1.142.
WebGL2 required — our token-free /3dtiles/viewer already gets WebGL2 by default, so no change.
Bounds are physical — supply the cylinder extents directly as [radius_m, angle_rad, height_m] (our VoxelGrid already carries radius_range/angle_range/height_range).
Texture3D megatexture eases large grids, but still quantize (UINT8/16) + exploit NaN/noData sparsity for bandwidth.
Reference the Volume Cloud sandcastle (1.130) for the ray-march transfer-function / colormap shader.
Substrate already in place
VolumeEngine::read_voxel_grid(quantity, time, dims, reference_time) already returns the cylindrical VoxelGrid ([radius, angle, height], NaN = nodata) this issue needs — so the work is an encoder (VoxelGrid → EXT_primitive_voxels cylinder .glb + 3DTILES_content_voxels + 3DTILES_bounding_volume_cylinder, quantities → EXT_structural_metadata SCALAR with noData) + shader/transfer-function config + render-verify, not new data plumbing.
Suggested phasing
MVP (this issue's core Done-when): single-site cylinder voxels, no octree — VoxelGrid → EXT_primitive_voxels .glb, served behind a ?representation=voxels like the existing mesh products, toggled in the viewer; render-verify in 1.142.
Stretch: implicit OCTREE tiling + .subtree availability, then the national mosaic with geometricError LOD.
First prototype starting now off the existing read_voxel_grid.

5b (voxel HTTP route) requirement, from #358 review: distinguish capability absence from data absence at the routing layer. Today VolumeEngine::read_voxel_grid defaults to LocationNotFound (404) for engines that don't support voxels, and PolarVolumeSiteView's impl also returns 404 when valid == 0 (no echoes) — so a client can't tell "this collection has no voxel capability" from "no data this window".
Fix in the route PR: add supports_voxel_grid: bool to VolumeInfo (default false; PolarVolumeSiteView::volume_info sets true). The 3D-Tiles handler checks the flag first → 404 "not supported" at the routing layer (or simply omit voxel links for unsupporting collections), so read_voxel_grid is only invoked when supported and its 404 then unambiguously means "no data in this window". (Deliberately not added in the #358 foundation PR — it'd be an unused field there; it belongs with the route consumer.)
