Historically the random number generator used by perl has evolved over time, in the early days it was the system RNG, then later we rolled our own version drand48 for cross platform stability. But these days drand48 has a bunch of flaws so it would be nice to be able to use something better.
However this is not so easy. Most code just calls rand() because it is the easiest thing to do. Most people dont bother adding support for their own hook, or burdening their user with providing an RNG, especially as there is no standard for doing so. Some code maybe ends up with support for an RNG hook, like List::Util did, but IMO such cases are a rarity, and a proliferation of slightly different hooks for this would not be helpful.
In theory one can override CORE::rand() and CORE::srand() before a module is loaded, and thus change the RNG, but the reality is there is no good way to overload srand()/rand() in another packages namespace. (So when people say "just put your pet RNG on CPAN" it is kind of a cop out, that RNG is likely to never really be useful as it just wont get used by most code.)
At the same time we dont really want to change Perls internal code to use something other than drand48(). There is lots of code that expects that doing srand(1234) will produce test results that look a specific way, so changing cores RNG would cause all kinds of unfortunate drama through the ecosystem.
This patch takes a different approach: ${^RNG} is used as a hook for rand() and srand(). If ${^RNG} contains an object then it uses the objects rand_uv() and srand() methods to do its thing. If it contains an unblessed subref then it calls it with no arguments for rand() and with arguments for srand() (srand(undef) is defined to be the same as srand()).
This is wired into the macro Drand01() which despite its name and appearance is actually a pTHX style macro, but which actually hides the fact by access what looks like a global var, but is actually an interpreter var under threads, thus hiding that it does operate on aTHX just not directly. This allows us to redirect so that modules like List::Util will still respect the hook even though they bypass pp_rand() for most of their random calls.
I thought about using ${^HOOKS}{RNG} instead of ${^RNG}, but for the time I decided to just use ${^RNG} as it feels better to do somethinglike:
```
local ${^RNG} = RNG::PCG->new();
```
than it does to do:
```
local ${^HOOKS}{RNG}
```
and it allows the rng internals to avoid the hash lookup. Although currently it is not optimizing the ${^RNG} package var fetch, and the var is not magic in any way so the ${^RNG} hook is not being stored in an interpreter var so the current implementation could be sped up we wished. IMO it is preferable to keep this as simple as possible.
As part of this patch I have added a new dist/RNG which contains XS code to implement the two dimensional PCG-XSH-RR 64/128, which allows for 128 bit state with only 64 bit or 32 operations. This seems to be the state of the art RNG these days.
I also implemented an RNG::SHA which uses SHA256 to produce the stream of random values.
I chose to make RNG use a UV as its base currency, so rand() calls ${^RNG}->rand_uv() which returns a UV, which is then converted into whatever the user requested. I did it this way so that any floating point operations or conversion to floating point operations could be performed by the C code. It feels like a more flexible foundation than using a float.
Modules like List::Util which bind to Drand01() at the C level still call the callback, so even without using List::Util's hook you can override it just like any other perl code.

Hashing with a cryptographic grade hash the seed concatenated to a counter which is incremented each time will provide a usable stream of secure random bits.
If the seed isn't already good, then it's not secure. Too many Perl modules have used similar techniques, and they are easily broken.
If you think otherwise then prove it and report it to NIST.
If you re going to cite the NIST, then please use something based on NIST recommendations, which are more complicated thansimply incrementing a counter:
The seed should have a minimum length larger than the hash state, e.g. 440 bits for SHA-1
The initial counter is random, not 0
There's a maximum number of data that can be extracted before it must be reseeded with new entropy
There is no need for that kind of construction on most systems nowadays. (A possible reason hashes were chosen instead of stream ciphers was because hashes were not subject to US export controls in the 1990s.)
I have actually used this algorithm (actually with SHA-1) at large scale and we never found any bias. We also ran Test01 and Dieharder on the code for days on end without any sign of RNG weakness.
It isn't just about bias. It's about predictability. Rainbow tables for cracking this kind of construction are practical, and the hardware for attacking these is much more powerful and accessible.
CPANSec has been issuing CVEs for the type of construction that you are using.
Putting this in core will give new life to this zombie algorithm that CPANSec has been trying to kill off.

RNG framework design notes
This note records the constraints and design decisions behind this PR.
Additional API documentation is in perlrng and the RNG::* modules. The
framework defines provider interfaces and supplies implementations for
generating random bytes.
The framework includes an HMAC-SHA-256 provider based on the HMAC_DRBG
mechanism described in NIST SP 800-90A. It is (obviously) not FIPS validated.
Including it helps exercise the infra requirements for cryptographic providers
and future integration with a reviewed cryptographic library.
The golden rule for seeding
Except for secure initialization, srand() must return something that can be
fed back into srand() with the same provider to recreate the original
sequence. This replay rule guides pretty much every decision about seeding,
including argument conversion, state normalization, and return values.
Secure initialization is the exception because returning a replayable seed
would expose material which could reproduce the generator's state. It
returns a redacted seed instead.
Drand48 compatibility and historical behavior of srand()
srand() has more historical irregularities than most Perl internals. Much of
this dates from when Perl delegated random-number generation to the C library
srand() and rand() functions, and used data and infra managed by Configure
to do so. Perl has long used its own Drand48 implementation, but srand()
retains conversion behavior inherited from earlier designs.
The old conversion does not match normal Perl numeric conversion. It ignores
a sign and a fractional part, does not support exponent notation, and produces
a native UV. Only the low 32 bits initialize built-in Drand48. For example,
srand(-1.234) historically means the same thing as srand(1).
The new design confines this compatibility behavior to the two Drand48
implementations. The built-in seed has 32 significant bits, while
RNG::Drand48 extends the interface to 48 bits.
A compatible decimal seed wider than the provider width warns.
The provider retains the low 32 or 48 bits and returns that initializer.
A string seed which uses the hash fallback returns the resulting initializer.
RNG::Drand48 returns a decimal string when the initializer is too wide for
the native UV, preserving its full value for replay.
The masked return value and the warning when a seed exceeds the provider
width are deliberate changes. For example, built-in srand(2**32) produces
the same sequence as srand(0), but warns about narrowing the seed.
Nonnumeric strings now use a hash fallback instead of becoming UV_MAX with
an overflow warning.
The initializer is not always the internal state. For seeds within 32 bits,
Drand48 shifts the seed left by 16 bits and appends the fixed low bits
0x330e.
The historical true return for zero
Before Perl 5.14, srand() always returned 1. On July 28, 2010, Karl
Williamson's 8383299294
changed it to return the seed so that programs could record an automatically
chosen seed and reproduce a run. The commit noted that the previous return
behavior was undocumented and that returning zero could break code relying
on its truthiness.
Later that day, Nicholas Clark's
da1010ecc5
made a zero seed return "0 but true". This was a deliberate compatibility
decision, preserving the historical true return while making it numerically
equal to zero without warnings. That commit added tests for all three
properties. Both changes shipped in Perl 5.14.
A zero seed retains the historical "0 but true" return when using the
default RNG or RNG::Drand48. Both recognize that exact string as zero when
it is passed back as a seed. Other RNGs treat it as ordinary string seed
material and should not be expected to produce the same sequence as zero.
Why we have a small integer parser
grok_number() returns its integer result in native UV.
It cannot represent a 48-bit value on a 32-bit Perl.
It cannot reliably preserve the low bits and overflow diagnostic required by
the compatibility rule when the input is wider than native UV.
Changing current grok_number() would not help an extracted RNG
distribution built against an older Perl.
The Drand48 paths therefore use a narrow parser which returns U64. It
accepts decimal digits with leading and trailing whitespace, an optional sign,
and an optional fractional part. As described above, the sign and fractional
part are ignored. It also accepts the exact string "0 but true" without a
warning. Exponent notation, other non-decimal text, and decimal integers
larger than U64 use the UTF-8 string-hash fallback.
There are two small implementations, one in core and one in dist/RNG.
Sharing a new core helper would either raise the distribution's minimum Perl
version or require another compatibility shim. Matching tests cover the
grammar and the U64 boundary in both layers.
The code comments describe this special-purpose parser. The user documentation
describes its compatibility behavior without exposing this implementation
detail. Do not broaden its grammar without reconsidering the compatibility
contract.
String seeds and argument conversion
Modern generators have different state sizes and initialization rules.
Xoshiro uses a multiword state, and HMAC_DRBG accepts arbitrary seed
material and derives its internal state. A machine integer is too small for
many generator states. A string of sufficient length has more capacity for
entropy and is independent of the host integer width.
pp_srand distinguishes absent input, ordinary values, references, and
RNG::SeedBase raw material. It normalizes an ordinary seed once, before
provider dispatch, by stringifying it and representing it as UTF-8 octets.
This gives 42 and "42" the same seed meaning and avoids making it depend
on whether a scalar currently has integer, floating, or UTF-8 storage.
Each provider is free to interpret the string. Drand48 uses the compatibility
rules above. The other bundled providers hash ordinary string arguments to
squeeze or stretch them into the required initialization size. Other providers
are strongly encouraged to follow this approach.
With the same provider, seeds with identical UTF-8 representations produce
the same sequence regardless of the host integer width. Hashing also means
that a tiny change in the seed should produce a significant change in the
sequence, something that is not true of normal Drand48 seeding.
The framework has two abstract base classes
RNG::Provider and RNG::SeedBase define the two sides of the RNG API.
Neither is a usable implementation on its own, just the Perl equivalent
of an abstract base class.
RNG::Provider defines a source of random data. A provider implements
rand_bytes and srand, and can be installed in ${^RNG}.
RNG::SeedBase defines a carrier for provider-specific raw seed material.
A seed object implements is_redacted, bytes, and provider.
The required base methods throw an exception if they aren't overridden.
Core recognizes objects by inheritance from these base classes. It does
not use similarly named methods as a duck-typed interface.
The bundled generator classes are concrete RNG::Provider implementations.
RNG::Seed::Raw is the normal concrete RNG::SeedBase implementation. A
program may supply another subclass, but the provider may throw if it does
not contain the information needed for initialization.
Seed representations and return values
An ordinary string seed is input to a provider's derivation process. Raw seed
octets bypass that derivation and initialize the provider directly. Keeping
these representations distinct avoids treating an ordinary string as raw
state by accident.
RNG::Seed->from_string creates ordinary string seed objects. They retain
string seed expansion and do not implement RNG::SeedBase.
RNG::Seed->from_bytes creates raw seed objects implementing RNG::SeedBase.
The provider checks that raw material has exactly its required width.
Raw material is never silently padded, truncated, or derived.
Returning the original argument is less surprising to users. When an ordinary
zero seed is passed to the non-Drand48 bundled RNGs, they return an RNG::Seed
object which evaluates as true and stringifies to "0". Feeding that object
back into srand() retains ordinary string seed expansion.
Direct state initialization helps test the RNG against reference vectors and
lets some providers use system entropy without hashing it first. Automatic
large-state initialization can return an RNG::Seed containing generated
material.
Providers may adjust raw seed material to meet an algorithm's requirements.
These adjustments must be idempotent, so applying them again leaves the
normalized value unchanged. PCG MCG forces its state odd with seed | 1,
and Xoshiro replaces an all-zero state with its documented valid state. The
PCG LCG increment adjustment is described below.
For secure automatic initialization, the redacted RNG::Seed records
initialization and names the provider. Passing it to srand() throws instead
of treating its serialized form as an ordinary string seed.
Providers and the fast path
The ordinary rand() path keeps the provider check in C and avoids Perl-level
method lookup. Some XS providers offer a private native U01 callback and
state pointer, which core may cache after validating the provider.
U01 means a uniform value in the half-open interval [0,1). The native
callback is an optimization, not a second provider interface. The cache is
cleared before reseeding or replacing the provider.
Provider callbacks can run arbitrary Perl, including changing ${^RNG}. The
callback code keeps the provider alive, handles both kinds of Perl stack
correctly, and refreshes SP after stack growth and callback execution. With
PERL_RC_STACK enabled, it also handles the reference counts for arguments and
results.
Older XS code commonly uses Drand01() and seedDrand01(). They expand
through Perl_drand48() and Perl_drand48_init().
Those macros use the direct built-in Drand48 state when no provider is
selected.
They dispatch through the provider-aware helpers only when
PL_rng_provider is non-null.
This preserves the fast path for List::Util and other existing XS users,
without changing their source code.
PCG variants and arithmetic
RNG::PCG currently exposes the extended XSH-RR 64/32 algorithm as its default.
There are additional algorithms which each have their own class and XS
callbacks:
RNG::PCG::RXS_M_XS_64_64.
RNG::PCG::XSL_RR_128_64_MCG.
RNG::PCG::XSL_RR_128_64_LCG.
The variant constructor option in RNG::PCG selects a subclass.
The 128-bit variants use native unsigned __int128 arithmetic when the
compiler advertises it with __SIZEOF_INT128__ == 16. Otherwise, they use a
portable implementation built from 64-bit operations on two words.
The XSL-RR 128/64 variants advance the state before producing output, matching
PCG's reference implementation. RXS-M-XS 64/64 produces output from the old
state. The tests check all three variants against PCG's published vectors,
using raw initializers to separate the algorithm from our seed expansion.
Ordinary seeds pass through the shared HMAC-SHA-256 seed expander with a
separate domain label for each algorithm. The LCG variant derives 32 bytes,
using 16 for the state and 16 for the stream increment. The low increment
word is adjusted with | 1. Raw LCG seeds carry the same state and increment
layout and receive the same idempotent adjustment.
Keep core and distribution boundaries clear
The built-in RNG is not a RNG::Provider. Core must not load the RNG
distribution or create RNG::Seed objects to implement built-in rand() or
srand(), because these must work in miniperl.
dist/RNG supplies concrete providers, seed objects, and old-Perl shims.
Minitest has no RNG extension or distribution library available.
t/op/srand.t tests ordinary built-in behavior only.
t/op/rng/contract.t tests the complete core/framework contract outside
minitest.
This keeps bootstrap testing small while retaining coverage of the real
framework classes in normal core and extracted-distribution builds.
Performance measurements
The built-in path was measured against an unmodified blead build with the same
unthreaded, non-debug configuration. Cachegrind reports raw instruction
counts per workload iteration after subtracting startup and loop overhead.
Lower is better. These numbers are from the latest compatible run on
October 5, 2026.
The local builds use GCC 13.3.0 with -O3, -fstack-protector-strong, and
double-precision NV. The PCG128 providers use native 128-bit arithmetic in
these builds. The local blead checkout is at

PCG, and rand() optimization changes. The saved profiles do not include a
