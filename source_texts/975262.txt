The library can paint two of the seven shading types, both hardcoded.
PdfCanvas.cs:400-451 builds /ShadingType 2 (axial) and /ShadingType 3 (radial), each pinned to
/DeviceRGB, each with an inline Type 2 function of exactly two colour stops and /Extend [true true]
(:416, :443, :463). Types 1, 4, 5, 6 and 7 have no representation at all.
Scope
Type
Name
1
Function-based
2, 3
Axial and radial — generalised, not replaced
4
Free-form Gouraud-shaded triangle mesh
5
Lattice-form Gouraud-shaded triangle mesh
6
Coons patch mesh
7
Tensor-product patch mesh
Plus the entries common to all shadings that the hardcoded pair cannot express: /ColorSpace other
than DeviceRGB, /Function from B2's model including function arrays, /Extend, /Background,
/BBox and /AntiAlias.
Types 4–7 are stream shadings with packed vertex data governed by /BitsPerCoordinate,
/BitsPerComponent, /BitsPerFlag and /Decode. The bit packing is where errors hide, so it wants
value-level known-answer tests on the encoded bytes rather than "a shading was produced".
Compatibility constraint
PaintAxialGradient and PaintRadialGradient are in PublicAPI.Shipped.txt and cannot be removed
in the 2.x line. Keep them as convenience overloads over the general model, and assert byte-identical
output so the reimplementation is provably behaviour-preserving.
Acceptance
Each of the seven types written, read back, and rendered without error by an external viewer.
A multi-stop gradient via a Type 3 stitching function, which is impossible today.
A shading in a non-RGB colour space, which is also impossible today.
Existing gradient output unchanged, byte for byte.
Relates to
B2 — the functions this consumes.
B4 — shading patterns, which wrap a shading as a fill colour.
B5 — the colour spaces a shading can be defined in.
Plan labels used above, resolved: B2 #250 · B4 #252 · B5 #253.
