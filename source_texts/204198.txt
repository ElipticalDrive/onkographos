This PR adds a method, find_volume, to the GeomQueryTool which enables it to determine point containment without checking each volume in the problem (though a loop over the volumes is also made available via the find_volume_slow method, added here.
‌
This method relies on a global surface tree created by the GeomTopoTool to find the nearest intersection for a ray constructed using an input location and a direction that is passed into the function or randomly generated if a direction is not passed. This intersection is found regardless of the ray’s orientation with respect to the triangle normal. The dot product of the ray direction and the triangle normal is used to determine if the point on the “forward” or “reverse” side of the surface. The surface-to-volume sense tag on that surface is then used to look up the correct volume for that point and return it.
Ambiguous situations (a tangent intersection or a point on the boundary of the surface) are handled by calling point_in_volume for both of the parent volumes of the surface that is hit. this method of querying both parent volumes could always be used, but results in additional ray queries and is avoided when possible. The volume containing that point is then returned from the method.

Patrick Shriwise (@pshriwise) commented on 2019-07-08
Ok so a couple updates here…
‌
I ran into some real problems when adding tests for points numerically on triangles of a volume’s surface for ray’s with randomly selected directions. For some directions, the Plucker test was returning very small values (both positive and negative). The negative values were problematic in that sometimes no hits were found. I've now updated the find_volume algorithm to fire a ray with an effectively infinite search window in both the positive and negative ray direction. It will still preferentially select the nearest hit along either the negative or positive direction and narrow the search window as it traverses the OBB tree. The rest of the algorithm remains unaltered in terms of using the dot product to determine which volume one is in with one small change - if the distance to the nearest hit is negative, the direction vector is flipped before performing the dot product calc. This addresses any issues we might have with coincident points and allows us to always select one of the two volumes adjacent to the surface for that scenario.
‌
Secondly, I've replaced the tangent intersection block of code with some error output and a return of MB_FAILURE for that case. I’ll ponder that some more, but I don’t think we should ever be in that scenario.
