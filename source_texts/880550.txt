Issue body actions
The compositor holds one canvas-sized RGBA image, and each layer composites into it in order. Print canvases (e.g. 7,000 × 10,000 at 300 dpi) cost hundreds of MB per canvas copy. Snapshot copies multiply that.
The region renderer now exists (render.render_region, _render_layers(..., limit=...)): it draws an exact crop and skips layers that miss the region. That is the building block for tiling.
Proposal:
Split the canvas into tiles (e.g. 512² or 1024²) and render each tile with the region path. Paste the tiles into the output, or stream them straight into the PNG/TIFF/PDF encoders.
Render tiles in a thread pool. Most heavy work (resvg, resize, blur, alpha_composite) runs in C and releases the GIL.
Documents that read the whole canvas (render.region_renders_alone is false: lighting, adjustment layers, canvas-edge blur, selection-masked effects) keep the single-canvas path.
Done when:
Tiled output equals the full render, pixel for pixel.
Peak memory for a large canvas drops measurably.
A perf budget covers a large print canvas.

Measured app-level scaling evidence from the October 16, 2026 audit (finding F08):
Tested October 16, 2026 against the published vixl_engine-0.27.0-py3-none-any.whl, installed in a fresh Python 3.12.14 environment on Linux x86-64, with server and pdf extras. Runtime reported 0.27.0. Wheel SHA-256 matched the release checksum: 54f1bdc753d3f1ebc9f8f880d989ebf3677ff5f84a926a451fc103a80c8c77c7. These are app-level observations, not source-review conclusions.

Core workload (run each size in a fresh process):
```
import resource, time
from vixl import Project
n = 4096
resource.setrlimit(resource.RLIMIT_AS, (1500*1024*1024, 1500*1024*1024))
p = Project(n, n, background="#ffffff")
p.apply([
 {"type":"shape","shape":"rectangle","name":"panel","x":0,"y":0,
  "width":n,"height":n,"fill":"#235cdb"},
 {"type":"effect","target":"panel","name":"blur","amount":8},
 {"type":"text","name":"title","text":"Large canvas render",
  "size":n//20,"x":40,"y":40,"color":"#ffffff"}
])
t = time.monotonic()
p.render()
print(time.monotonic() - t, resource.getrusage(resource.RUSAGE_SELF).ru_maxrss)
```
Five logical CPUs; single measurements, uncontrolled font/cache effects, not a repeated benchmark. RSS covers the entire worker, not just an isolated compositor allocation. No crash/OOM was observed and no claim is made that this whole-canvas blur workload can simply use the existing independent-region path.
A separate 1024×1024 simple-rectangle run accepted 4,096 layers (full render ~0.321 s) and cleanly rejected layer 4,097 without increasing the layer count. A 10,000-operation batch completed (~2.317 s); 10,001 was rejected with a clear resource_limit. Layer count alone is therefore a poor capacity proxy for large effects.
Related operational limits: #623. The timeout-detachment behavior was read in documentation, not stress-verified in this audit.
