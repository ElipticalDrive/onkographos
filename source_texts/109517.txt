Points at #77. Adds the first 3D rendering in the repo: the simulation has been three-dimensional since #72, but every figure still reduces it to an x–z slice at the first y index (aux03_plotting.xz_slice).
Four files, all new; nothing existing is modified.
What this adds
postprocessing/X13_3d_volume.jl — GLMakie volume render and isosurfaces of one snapshot.
One --field lays the panels out by --mode (volume and isosurface of it); a comma-separated list lays them out by field, one panel each. --scale appends the _ℓ<ℓ> every budget term carries, so the six-term figure is one line:
```
julia --project postprocessing/X13_3d_volume.jl <file> \
  --field Q,wb_rs,Π_K,Π_A,ε_Ks,ε_As --scale 1 --mode isosurface --overlay b
```
Q, enstrophy and speed are derived here from u, v, w. They have to be: the file's own ω is the spanwise component alone, which is enough for the 2D slice figures and useless for 3D structure. All three velocities are written at cell centres, so the gradient tensor is a centred difference on one grid with no staggered interpolation.
--overlay b draws a reference field as contours on the two vertical bounding walls, so a Q or Π panel shows where the billow actually is.
postprocessing/render3d.pbs + submit_render3d.sh — batch rendering, one figure per time.
```
bash submit_render3d.sh TIMES=100,120,140
bash submit_render3d.sh FROM=60 TO=160 EVERY=10
```
postprocessing/subset_for_plots.py — cuts a run to a laptop-sized NetCDF (chosen fields and records, z cropped, float32) that X13 reads unchanged. 2.15 GiB → 0.006 GiB on the Nz=128 test run.
The thing worth knowing: this needs no GPU and no display
GLMakie needs an OpenGL context, not a GPU, and a Casper compute node has neither a display nor the NVIDIA driver exposed to one. /usr/bin/Xvfb plus Mesa's software rasteriser (LIBGL_ALWAYS_SOFTWARE=1) gives a context on a plain CPU node, so this is an ordinary batch job — no modules, no VirtualGL, no FastX session. The job starts its own Xvfb on a free display, smoke-tests the context before rendering, and kills the server from an EXIT trap.
Measured on Casper at Nz=1024: about 90 s per six-panel figure, so a full 101-record set is ~2.5 h and fits in one job.
Two traps found getting there, both recorded in the scripts:
xvfb-run is not installed on Casper, only the Xvfb binary it wraps.
julia +1.13 is a juliaup feature; Casper's julia reads it as a filename. The job finds 1.13 the way simulation.pbs does.
Two things that only bite on the production runs
Virtual merges. A multi-GPU run's merged 3D file is HDF5 virtual datasets, and NCDatasets throws a KeyError on the storage code until it is registered. X13 calls allow_virtual_storage!, as merge_rank_output.jl:290 says every Julia reader of such a file must.
Memory. Everything is read and differentiated on the cropped z slab, with one cell of margin for the centred difference. Cropping afterwards instead would peak around 15–25 GB at Nz=1024 to render a third of it.
Figure conventions, and why
Settled by iterating against a real run; each one replaced something that did not work.
One fraction set for every panel — 0.18, 0.515, 0.85 of each panel's own range — so a surface means the same thing wherever it appears. Positive fields previously took quantiles of their own distribution, which put surfaces where the data was but at magnitudes unrelated to any other panel.
One symmetric :balance scale everywhere, including positive-definite fields, whose lower half then goes unused. That makes the colourbars the same object, and the empty half states that the quantity never changes sign — true of ε_Kˢ by construction and of nothing else here. :magma made it the loudest panel for no physical reason.
The overlay is wall contours, not isosurfaces. Two sets of interpenetrating isosurfaces always fight, and transparency cannot separate them: GLMakie ignores alpha on a volume contour (--overlay-alpha 0.05 and 1.0 render byte-identically).
Testing
No automated tests — these are figure scripts, and the repo's suite covers budget closure rather than rendering. What was verified by hand:
Every option exercised against a local Nz=128 3D run (72 × 24 × 128, Re = 258): the six-panel figure, single-field --mode both, derived and budget fields, --zlim spanning the whole domain, and the one-level edge case.
The crop-before-differentiate change is a numerical no-op, as it must be: Q at t = 108 gives the same shape, colour range (±0.0726) and levels before and after.
subset_for_plots.py output round-trips: the subset reconstructs Lz = 7.81, z = ±3.91 against the full file's 25.0 and ±12.5, Lx/Ly unchanged, and X13 gives identical ranges on all six fields.
submit_render3d.sh exercised against a stubbed qsub: list, range, both given, missing EVERY, nothing given, reversed range, unknown key.
The .pbs render loop run under bash against the local run, two times, one figure each.
The signs on the rendered figure are a free correctness check and come out right: ε_Kˢ positive, and ε_Aˢ, τ(w,b_r), Π_K and Π_A all signed, as CLAUDE.md says to expect.
Caveat
Everything was tuned on an Nz=128 / Re=258 run that never goes three-dimensional — rms(v)/rms(u) ≈ 1e-4 throughout, so the isosurfaces are prismatic. That validated the mechanics, not the aesthetics. On the Nz=1024 / Re=1032 run expect a second round of tuning: fewer levels, lower alpha, and possibly more than one wall for the overlay, since a single wall is only representative while the flow is spanwise-uniform.

The companion to X12, which cuts planes: this one looks through the volume.
For the KH run the isosurface is the more useful of the two, since Q or
enstrophy picks out the streamwise vortices that braid the billow -- the
reason the simulation went 3D in the first place.

GLMakie, not CairoMakie: a volume render is GPU raymarching, which Cairo

in Project.toml. It needs OpenGL, so this is a workstation (or VirtualGL)
script, not a batch one -- X12 stays the no-display path.

Verified offscreen via GLMakie.activate!(visible=false) on a 36x12x64 run:
both panels render and save. Content there is flat, correctly so -- t = 10
is still the undisturbed tanh profile.

Derived fields are recomputed here rather than shared with X12: the file's
omega is spanwise only, and u, v, w are at cell centres, so the gradient
tensor is a centred difference on one grid -- periodic in x and y, one-sided
at the z walls, matching how the pipeline treats the bounded axis.

Two things that only bite on the HPC runs, neither reachable from the
single-GPU test case.

A multi-GPU run's merged 3D file is HDF5 virtual datasets over the rank
files, and netCDF-C reports a storage code NCDatasets does not map, so a
read throws KeyError. merge_rank_output.jl:290 exists for exactly this and
says any Julia reader of a virtual file calls it first -- X13 did not, so
it would have failed on every Nz=1024 run. Copied rather than included:
that file pulls in Oceananigans and HDF5_jll for what is one line.

Everything is now read and differentiated on the cropped z slab instead of
the whole column. At Nz=1024 one field is 0.91 GB and the gradient tensor
is nine of them, so cropping afterwards peaked around 15-25 GB to render a
third of it. One cell of margin each side keeps the centred z difference
exact over the slab proper and collapses to the true walls when the crop
spans the domain.

Numerically a no-op, as it must be: Q at t=64 of the Nz=128 run gives the
same shape, colour range (+/-0.0906) and levels (+/-0.077, +/-0.0272)
before and after. Also checked --zlim 20 (margin collapses, z=128, no index
error), enstrophy (positive path) and Pi_K_l1 (a budget field).

subset_for_plots: cut an HPC run down to a laptop-sized file
…
8eb48a6
```
Run it on Casper, scp the result, point X12/X13 at it. Four reductions:
only the fields asked for, only the records asked for, z cropped to the
active layer, and float32 with zlib. On the Nz=128 test run, 2.15 GiB ->
0.006 GiB for three records of nine fields, 336x.

Named neither plot*.py nor X*.py: it writes data, not a figure, so
plots.pbs's glob and the extra-figures family both leave it alone.

Three things a plain to_netcdf of a sliced dataset gets wrong, all of them
found by running the output back through the plotting scripts:

- X12 goes through load_dataset_and_grid, which reconstructs the grid from
  NetCDF groups that xarray does not carry across. The three groups are
  copied, with z and size in underlying_grid_reconstruction_kwargs rewritten
  to the crop -- otherwise Lz, z_min/z_max and dV describe the uncropped
  domain. Verified: the subset reconstructs Lz = 7.81, z = +/-3.91 against
  the full file's 25.0 and +/-12.5, with Lx and Ly unchanged.
- The grid's own spacing variables are time-independent, so a field list
  dropped them and load_dataset_and_grid died on ds.Delta_x_caa. Every
  time-independent variable now comes along; they are 1D and free.
- virtual_rank_files is dropped. A merged multi-GPU file carries it and
  check_rank_files refuses the file when the rank files are absent, which
  they are once it has been copied away.

--zlim defaults to 5, wider than the plotting scripts' 4, because they
derive Q by centred differences: cropping to exactly what gets plotted
leaves them one-sided on the boundary. At 5 then plotted at 4, Q comes back
bit-identical to the full file (+/-0.0726); at 4 it shifts to +/-0.0727.

X13: --overlay, a reference field as contours on the bounding walls
…
43c1eb7
```
Puts b behind every panel as a shared reference, so a Q or Pi panel shows
where the billow actually is. Three approaches, in the order they failed:

- Isosurfaces of b in the box, grey. Muddy: the panels use :balance, whose
  midpoint *is* grey, so it read as washed-out data rather than context.
- Same, in a saturated hue off that axis. Legible as context, but it
  occludes the thing the panel is about, and transparency cannot fix that:
  GLMakie ignores alpha on a volume contour. Measured, not assumed --
  --overlay-alpha 0.05 and 1.0 render byte-identically. Clipping it to a
  curtain over part of the span helped and still looked cluttered.
- Shaded on the bounding walls. Occludes nothing, but a filled wall is
  still a second data layer, and a full-range colormap bottoms out at black:
  the floor came out solid black, which reads as a rendering fault. A floor
  is wrong anyway -- b at fixed z is nearly uniform, so it carries nothing.

What works is line contours on the two vertical walls. Lines read as
annotation rather than as a competing surface, and the deformed interface
is legible behind every panel of the six-term figure. `transformation` is
how Makie puts a 2D recipe on a plane of a 3D axis.

--overlay-style iso keeps the isosurface version for comparison; the wall
one is the default.

One X13 invocation per time, one figure each, into extra_figures/. A time
that fails is reported and the rest of the list continues.

The job asks for no GPU, which is the part worth knowing: GLMakie needs an

simulation.pbs does.

TIMES and FIELDS travel colon-separated: `qsub -v` splits its own list on
commas, so a comma in either value truncates the variable list.

The job starts Xvfb on the first free display between 99 and 160 so two of
these on one node cannot collide, and kills it from an EXIT trap. It
smoke-tests the GL context before rendering, since a failure there would
otherwise surface only after a long software render.

Loop body verified locally under bash against the Nz=128 run, two times,
one figure each. Note it must be bash: $JULIA holds "julia +1.13", two
words that zsh does not split.

X13: positive fields on the positive half of :balance, not :magma
…
b884f9f
```
eps_Ks was the loudest panel of the six for no physical reason: :magma is
a dark, fully saturated ramp while the signed panels use :balance, which
is near-white wherever the field is small. The positive half of :balance
(its white midpoint through to red) puts them on the same footing, and a
positive field then reads as the red half of the signed scale, which is
what it is.

Two further changes, without which the colormap alone does not fix it:

- The colour range starts at 0 rather than the 1st percentile, so white
  means zero in every panel.
- Positive levels are the same fractions of the colour range the signed
  ones use (0.18-0.85) instead of the 0.80-0.995 quantiles. Quantile-chosen
  levels put all six surfaces above the 80th percentile, so every one
  mapped to the dark end whatever the ramp.

The cost is that eps_Ks is now the busiest panel rather than the darkest:
its distribution is skewed, so the lowest level sits well below the 80th
percentile and wraps the active region in large sheets. --levels is the
knob if that is the wrong trade for a given figure.

X13: one symmetric colour scale for every panel, signed or not
…
46cf7ac
```
A positive-definite field now gets the same (-hi, hi) :balance scale as
the rest, with its lower half unused, rather than the positive half of the
ramp over (0, hi).

The two render identically -- v maps to 0.5 + v/2hi either way -- so this
is a colourbar change, not a picture change. It earns its place twice: the
bars become the same object, so magnitudes compare across panels without
rescaling by eye, and the empty half states that the quantity never changes
sign, which is true of eps_Ks by construction and of nothing else in the
six-term figure. The cost is half a bar of dead space and correspondingly
fewer ticks over the populated half.

`signed` still decides the levels -- a symmetric pair about zero, or
one-sided -- so a positive field is not given surfaces it has no data for.

Drops BALANCE_POS, dead with both cases on the full ramp.

X13: one set of contour-level fractions for every panel
…
2b65b20
```
Levels are now the same fractions of each panel's own colour range --
0.18, 0.515, 0.85 at the default --levels 6 -- whatever the field. A
surface therefore means the same thing in every panel: this much of that
panel's range. Checked on the six-term figure, Pi_K's +0.00011 of 0.000609
and eps_Ks's 1.25e-05 of 6.95e-05 are both 0.18.

Two asymmetries went into making this not already true. Positive fields
took quantiles of their own distribution, which put surfaces where the data
was but at magnitudes unrelated to any other panel. And even on fractions,
signed fields used nlevels/2 fraction values against positive fields'
nlevels, so the magnitudes still differed.

A positive field now gets exactly the magnitudes the signed panels put
their red surfaces at and has no blue counterparts, so `--levels n` is n
surfaces where the field changes sign and n/2 where it does not. That is
the honest reading of the flag once levels are placed by magnitude.

It also settles the eps_Ks panel, which was either uniformly dark (all six
levels above the 80th percentile) or cluttered (six evenly spaced levels
wrapping the active region in sheets): three graded shells at the shared
fractions are neither.

submit_render3d: FROM/TO/EVERY for a strided range of times
…
eec5b0e

TIMES still takes a list; FROM=60 TO=160 EVERY=10 renders every 10th time
over a range instead, which is what the Nz=1024 run's 101 records want.
The two are mutually exclusive rather than one silently winning, so a typo
in either is an error.

FROM/TO/EVERY rather than a 100:10:200 range literal because colon is

output format follows the locale; the endpoint comparison carries a 1e-9
tolerance so an inclusive TO survives the accumulated float addition.

Exercised against a stubbed qsub: list, range, both-given, missing EVERY,
neither given, reversed range and an unknown key all behave, and the
emitted -v list is well formed in each.

The wall contours stopped short of the box edges, leaving a bare strip
along each wall -- clearest as a gap at the far end of the back wall. They
were drawn over the data's own coordinates, so they covered only the data
footprint, while Axis3 draws the box wider than that.

How much wider was worth measuring rather than guessing: Axis3 autoscales
to the data extent plus 5% on every side (6.87 -> 7.557, x1.1 overall), and
it pads z as well as x and y. Those limits are now written out explicitly

the corners.

each cost a render to rule out: it is not occlusion, not `transparency` on
the isosurfaces, and not the contour plane sitting inside the volume --
pinning the limits to the data, and moving the plane outside the volume
with the limits extended to meet it, both leave the gap exactly as it was.

X13: b_r as a derived field
…
d1f835e
```
b_r = b - b✶(z), the buoyancy relative to the Winters sorted reference
state. The simulation writes it only to the 2D writer, and that is a single
x-z slice with no 3D structure to contour, so it is rebuilt here.

On a uniform grid the sort is exact and needs no iteration: order every
cell by buoyancy, and since each model level holds Nx·Ny cells of equal
volume, the k-th group of Nx·Ny sorted values is the fluid that comes to
rest at level k. The sort has to see the whole column -- a reference state
built from a slab is a different reference state -- so this is the one
derived field that reads beyond the z crop.

Checked against the simulation's own b_r on the plane the 2D writer keeps:
corr 0.99995, rms difference 1.0% of rms. The residual is expected, since
the online field uses the ThreeDimensionalSort z✶ with its tie handling
rather than an equal-volume column average, and the 2D file is Float32.

* Run on several GPUs above Nz=512: x-slabs over MPI, rank files merged after

NZ ≤ 512 runs as before, on one GPU without MPI. Above that, the wrappers ask PBS for
NGPUS GPUs (default 4, one Casper A100-80GB node, up to NZ=1024), simulation.pbs launches
`--ranks NGPUS` MPI ranks, and the script builds Distributed(GPU(); partition=Partition(x=R)).
Every rank writes its own files; merge.pbs, a CPU job chained on the run, stitches them into
the one-GPU layout (merge_rank_output.jl) and draws the figures, so the post-processing reads
the run as always.

What a distributed grid broke, read in Oceananigans 0.113.3 and Oceanostics 0.21.2:
- The staged Gaussian filter clamps its x-pass at each rank's slab edge. A compute! method in
  distributed_diagnostics.jl gathers the slabs and runs the x-pass on the global Nx, bit for
  bit the one-process filter.
- VerticalSort errors on a Distributed grid, and its 1x1 Periodic column costs 9x its data in
  halos. sorted_column(b) gathers and sorts the whole domain on every rank, on a Flat column,
  in both paths.
- Average(dims) divides by one rank's cell count: ε̄ is an area integral.
- NetCDFWriter writes every rank to the same file; and on a distributed grid a written window
  gets x halo-communication conditions it holds no cells for, so the first compute! of any
  computed output failed. Rank files, and a Field constructor for x-windows that keeps their
  windowed conditions.
- The per-point noise repeated over every slab: it is one global array now, indexed by global
  cell, in both paths, so any decomposition starts from the same w.
- show_gpu_status left every rank on the last GPU; the progress message's reductions must run
  on every rank before only rank 0 logs.

MPI: Casper's OpenMPI (CUDA and UCX) through MPItrampoline and an MPIwrapper built against it
(setup_mpi_env.sh), in an environment and depot of their own that only multi-GPU jobs load;
pointed at the system library directly, HDF5_jll loads a second OpenMPI that cannot share the
process.

Memory, both paths, same numbers: the filter is memoized per operand, E_a and ε_A are built
once, Υ̃ once per scale, Kˢ and S̃ are one Field each for their output, integral and tendency,
and the tendency outputs no longer allocate buffers the writer never uses.

tests/test_distributed_diagnostics.jl checks the filter, the column, its lookups and the
windows on 2 and 4 CPU ranks against one process, bit for bit.

* Keep the CUDA toolkit off the ranks' library path and give UCX its settings before Julia starts

The openmpi module brings cuda/12.9 onto LD_LIBRARY_PATH, which the dynamic linker searches before a library's own
RUNPATH, so CUDA.jl's 12.6 artifacts picked up libcublasLt, libcusparse and libnvJitLink from the system ("loaded from
a system path"). OpenMPI, UCX and MPIwrapper need only the driver and find the rest through their RPATHs, so the
toolkit comes off the path again after the module load.

MPI.jl sets UCX_ERROR_SIGNALS (leave SIGSEGV to Julia, which stops threads for GC with it) and UCX_MEMTYPE_CACHE from
its __init__, after MPItrampoline has loaded UCX, which has read its settings by then ("unused environment
variables"). simulation.pbs now sets both before Julia starts and forwards them to the ranks.

Checked on two V100s at Nz=64 against one GPU: no system-path or unused-variable warning, and the comparison with the
one-GPU run is identical, number for number, to that of the run without either change.

* X13: b_r as a derived field

b_r = b - b✶(z), the buoyancy relative to the Winters sorted reference
state. The simulation writes it only to the 2D writer, and that is a single
x-z slice with no 3D structure to contour, so it is rebuilt here.

On a uniform grid the sort is exact and needs no iteration: order every
cell by buoyancy, and since each model level holds Nx·Ny cells of equal
volume, the k-th group of Nx·Ny sorted values is the fluid that comes to

03_subset_3d.py writes every variable with xarray's default _FillValue = NaN, so NCDatasets read a subset's
coordinates and fields as Union{Missing, Float64}. Makie's contour! has no method for that, so the wall overlay
threw before the figure was saved, and read3d's Float64.() would throw on any masked value, such as the NaN last
record of a tendency. With maskingvalue = NaN every array reads as plain Float64. The simulation's own files
declare no fill value, so for them nothing changes: the six-panel render of the Nz=1024 run at t = 120 is
byte-identical before and after, and the subset of that record now draws the same figure.
