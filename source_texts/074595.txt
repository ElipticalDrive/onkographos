It is bit more complicated to get started and I don't have the bandwidth. I asked claude to do an evaluation:
ƒVDB-Reality-Capture vs. SlicerPhotogrammetry (OpenDroneMap)
These two projects solve overlapping but fundamentally different problems using different reconstruction paradigms. Here's how they compare:
What each project does
ƒVDB-Reality-Capture (NVIDIA)
SlicerPhotogrammetry (SlicerMorph)
Reconstruction method
3D Gaussian Splatting (radiance fields)
Classical stereophotogrammetry (SfM + MVS via OpenDroneMap)
Pipeline scope
Radiance field reconstruction + mesh extraction. Assumes camera poses already exist (e.g., from COLMAP)
Complete end-to-end: photo/video masking (SAM/SAMURAI) → image clustering (ViT) → SfM → MVS → textured mesh
Primary output
Radiance field (Gaussian splat) that can be rendered; meshes/point clouds extractable as a secondary step
Textured 3D mesh directly
Scale
100M+ Gaussians from 400+ high-res images; out-of-core data handling; multi-GPU
Typical specimen-scale photo sets (dozens to low hundreds of images)
Integration
Python library + frgs CLI tool
Fully integrated into 3D Slicer (GUI-based workflow)
Target audience
General-purpose reality capture, computer vision researchers, VFX/production
Biologists, morphologists, museum professionals
License
Apache 2.0
BSD-2-Clause
Potential benefits of ƒVDB-Reality-Capture
State-of-the-art reconstruction quality — 3D Gaussian Splatting often produces more photorealistic results than classical MVS, especially for complex surface appearance (translucent, specular, or fine-detail surfaces). NVIDIA claims 50% better throughput and 30% lower runtime than gsplat, with higher quality.
Novel view synthesis — the radiance field can render arbitrary viewpoints at high fidelity, useful for visualization, web-based inspection, or data augmentation.
Scalability — handles very large captures (hundreds of high-resolution images, 100M+ primitives) with out-of-core data loading and multi-GPU support.
Speed — GPU-native sparse data structures (VDB) make it significantly faster for the reconstruction step.
Why it may not be a practical replacement for SlicerPhotogrammetry
No SfM or masking pipeline — ƒVDB-Reality-Capture starts from camera poses. You'd still need an SfM tool (COLMAP, OpenSfM, etc.) to estimate camera positions and a separate masking step. SlicerPhotogrammetry handles this entire workflow.
Mesh quality for measurement — For geometric morphometrics (landmarks, distances, shape analysis), you need clean, watertight, metrically accurate meshes. Classical MVS (OpenDroneMap) produces meshes directly from dense point matching, which is well-understood for dimensional accuracy. Meshes extracted from Gaussian splats are a secondary derivative and may have artifacts — this is an active research area.
No 3D Slicer integration — SlicerPhotogrammetry feeds directly into SlicerMorph's downstream analysis tools (GPA, ALPACA, landmarking, etc.). ƒVDB-Reality-Capture would require an export→import workflow.
Calibrated scale — SlicerPhotogrammetry supports GCP (ground control point) files and ArUco markers for physical scale. ƒVDB-Reality-Capture doesn't address physical calibration.
Infrastructure — Both need NVIDIA GPUs, but ƒVDB is a Python library you'd have to integrate yourself, whereas SlicerPhotogrammetry runs via Docker/NodeODM with a push-button UI (or pre-configured on MorphoCloud).
Bottom line
For the SlicerMorph/morphometrics use case, ƒVDB-Reality-Capture doesn't replace the SlicerPhotogrammetry workflow — it solves a different (narrower) part of the pipeline using a newer technique. It could theoretically produce higher visual fidelity captures, but:
You'd lose the integrated masking, clustering, and GUI workflow
Extracted meshes from Gaussian splats are not yet proven for metrically rigorous morphometric analysis
You'd need to build glue code for SfM, scale calibration, and Slicer import
Where ƒVDB-Reality-Capture could add value: if you need ultra-high-fidelity visualizations of specimens (e.g., web-based 3D viewers, publications), or if you're reconstructing very large scenes, it would be worth investigating as a supplementary tool rather than a replacement. The mesh extraction step is improving rapidly in the Gaussian Splatting literature, so this could become more relevant for measurement in the future.
