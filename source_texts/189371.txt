Summary
The optimized BVH box test can miss a valid boundary hit when a ray has a zero direction component and starts exactly on the corresponding bounding plane. 0*infinity produces NaN, which survives interval updates and makes the final comparison false.
Source evidence
Reviewed Gyunity commit: 6e5346526976ce3789a7110d81d17979d1885977.
BVHAccel.cpp:127–149: X-slab products initialize tmin/tmax. Conditional updates do not replace a NaN lower bound, and the final predicate contains tmin < ray.mTmax.
Callers compute invDir=1/ray.mDir, producing infinity for a zero component.
Minimal geometry
Triangle vertices: (0,0,0), (1,0,0), (0,1,0).
Ray origin: (0,0.25,1); direction: (0,0,-1).
The ray hits the X=0 edge at t=1. For the bounding box, minX=0, so initial tmin=(0-0)*(1/0)=NaN. The current Y/Z updates do not repair it, and the final predicate rejects the hit.
Expected: agreement with direct triangle intersection and the brute-force accelerator.
Proposed validation
Compare direct intersection, BVH and kd-tree for min/max faces, positive/negative zero directions, parallel rays outside the box and edge/vertex hits. Use a slab implementation with deliberate handling of parallel components and NaNs if a fix is warranted.
Numerical verification and decision
Reproduced in actual C++ in both Gyunity Debug and Release. Keep as a P2 inherited robustness issue, not a Gyunity-only PBRT divergence.
RenderingNumeric.BvhParallelBoundary uses the exact triangle/ray above:
Direct triangle: hit at t=1.
Gyunity brute-force: hit.
Gyunity kd-tree: hit.
Gyunity BVH: miss.
The compiled PBRT-v3 probe gives:
General Bounds3::IntersectP overload: hit.
Optimized inverse-direction overload: miss.
Thus the missed valid hit is independently reproduced, but the optimized PBRT-v3 code shares the same limitation (src/core/geometry.h:1410–1437). Merely matching PBRT is not sufficient to establish correctness for this edge case. Any fix should be treated as a deliberate robustness improvement over the inherited algorithm, with cross-accelerator tests, not as repairing a mistranscribed PBRT formula.
Gyunity baseline: 6e5346526976ce3789a7110d81d17979d1885977; PBRT local base 13d871faae88233b327d04cda24022b8bb0093ee. The bounds probe compiles the actual local header; other reference checks link the existing Debug library. No PBRT files were modified.
Regression source: GyunityTest/tests/RenderingNumericTest.cpp on user/xiaoyxue/math_render_review. Evidence: Test\math_render_numeric\tests-Debug.xml, tests-Release.xml, and pbrt-reference.log. No fix applied.
