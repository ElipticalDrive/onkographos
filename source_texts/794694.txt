Purpose
Quest / PICO の WebXR で Three.js GaussianSplat が左右眼とも同じ映像になっていた問題を修正し、検証済みの Three.js runtime を SceneSync 本体へ適用します。
PlayCanvas は見た目（輪郭・鮮明さ）で優位でしたが、renderer runtime の置換は別trackとして #544 に分離しました。このPRは Three.js で Editor / Static ZIP / Single HTML を完成させます。
Production runtime
Three.js fixed commit: cbba126004263d0c32d3d6d05a4fe218d261fa47
renderer: WebGPURenderer
default backend: WebGL (?webgpu=1 で WebGPU)
Gaussian XR stereo patch:
highpModelViewMatrix → ArrayCamera / eye camera対応の mediumpModelViewMatrix
combined screenSize → eyeごとの cameraViewport.zw
accepted Smooth kernel:
cutoffを2 sigmaからsqrt(8) sigmaへ拡張
quad edgeでalphaが0になるよう正規化
fixed commitのsourceが変化してpatch targetが見つからない場合は明示的に失敗
extensionはGLBロード時にlazy初期化し、通常起動・handoffを追加CDN fetchから切り離す
Three.js本体はvendorせず、既存どおりCDN依存
共通のpatched GLTFGaussianSplatLoaderExtensionを次の3経路で初期化・登録します。

PlayCanvas production runtimeの検証・導入条件は #544 に記録しています。

Desktop side-by-side visual result:
PlayCanvas: individual ellipse shape, axis and overlap remain readable; lower halo / overdraw
Three.js smooth-kernel experiment: tails overlap too strongly, causing brightness accumulation and a broad glowing ring
Decision:
Use PlayCanvas output as the current visual-quality reference.
Do not include the smooth-kernel experiment as-is in the Three.js stereo fix.
Keep the verified XR stereo fix independent: per-eye model-view matrix and viewport.
The smooth option remains diagnostic only. It copies the wider normalized fragment profile, but does not reproduce the complete PlayCanvas projection, alpha compositing and color pipeline.
Before choosing a full renderer migration, compare the real Insta360 scene at matched camera poses and measure Quest frame time / overdraw.

PlayCanvasのSOG直読込とKHR GLBは描画時性能がほぼ同等で、Three.jsとの差は入力形式だけでは説明できません。固定Three.js commitのWebGL fallbackではSHをvertex shaderで評価する経路なども含め、大規模SH3データの負荷が非常に高いと考えられます。
