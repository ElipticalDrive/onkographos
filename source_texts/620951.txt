The fix
Convention B: everything on the capture side lives in display orientation. The bitmap and intrinsics already did; the view matrix did not, because it came from camera.pose.inverse(), which ARCore documents as the physical camera "relative to the image readout". MetricMarks.glViewToCvDisplay applies the missing R_z; MetricFingerprintBuilder.buildSingle routes through it.
The direction was derived, not guessed. At rotationNeeded = 90 the capture path maps pixel (u,v) → (rawH − v, u) and swaps fx/fy, so a sensor ray becomes
```
d_d = ((cy_s − v)/fy_s, (u − cx_s)/fx_s, 1) = (−d_s.y, d_s.x, 1) = R_z(+90)·d_s
```
Hence display = R_z(+rotationDeg) · sensor, pre-multiplied since p_display = R_z (V_sensor p_world). This is the same model that reproduces §8.1's table exactly, so the published figures and the fix now rest on one model rather than two.
buildSingle's new rotationDeg has no default — a default would let a caller silently reinstate the defect.
0.6 settled which convention is right, not just whether the composition changes
PoseFusion.composeCorrected needs no change, and the reason is decisive. vCurrent is Camera.getViewMatrix, which ARCore documents as "incorporates the display orientation … equivalent to camera.getDisplayOrientedPose().inverse().asMatrix()".
So the live side of that composition was always display-oriented, while capture stored sensor-frame points. The two sides never agreed. Convention B moves capture to display and they now do — convention A would have required changing the live side too. That is a stronger result than the design's "recommendation: B".
