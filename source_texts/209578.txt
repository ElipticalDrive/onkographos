This PR draft adds basic LOD mesh generation.
It works by changing how a mapblock mesh is generated depending on the distance to the player. Only certain node types are included in LOD generation, so for example plantlikes are not rendered. The allowed nodes are then used for a greedy mesher to further reduce vertex counts. The less detailed the LOD, the fewer node samples are used for mesh generation.
After a certain threshold, the mesh is rendered with only one material, without a texture to reduce material swaps.
The threshold after which LODs should be used, the rate at which LOD level increases, and the threshold for textureless mesh generation are configurable in the settings.
The LOD mesh generation is significantly faster than regular mesh generation, on less detailed meshes. The meshes also use considerably less RAM, since their vertex count is a lot smaller. The LODs also yield a performance improvement in my testing.
I redid this benchmark now, with 5.15 merged.
These stats were gathered by standing still in a pre-emerged world with 4000 node render and send distance, and a mesh chunk size of 16, for 15 minutes. They show how these system resources change over time or as more chunks get generated. The lod settings had a threshold of 15 blocks, a quality of 2, and a texture threshold of 2.

Dang it. I forgot a pretty important part in this never ending story. The LODs should update when moving around. I just didnt notice before when using a large mesh chunk size and a low block timeout.
To "fix" this, Ive added an lod field to the client's MapBlock and moved the lod calculation to the step function and handleCommand_blockData for now (see commit 91820bb). This approach has a few problems though:
Updating all blocks' lods in the step function would cause immense amounts of lag, so its only really feasible to update the lod for a few closer blocks.
There are still some more places where MapBlocks get created, where the lod doesnt get set. These blocks often cause the mesh to suddenly get rendered with the wrong (default) lod, even when the player is currently in said block. Tracking down every last place where blocks can be created, to set the lod there seems wrong, so I feel like my approach of having the lod tied to MapBlock objects may already be flawed.
Anyone have some input on this?

My plan for this is that we should wait for a general LOD system to be implemented (by whom?) first - as described in #15172 (comment) - and then we can see how your PR fits on top of that. I hope there isn't some systematic mismatch.
I'm pretty sure this is more general than the issue you linked – unless you mean it the other way around, first solve a specific case and then go general (like Einstein did with relativity).
Honestly, it feels like it'd be less technical debt to first get a meshgen general LOD and then throw in mesh drawtype LODs into it... of course another option would be to do what Godot did in Godot 3, aka first make a LOD shim system that theoretically has LODs but does nothing, and then build handling specific cases (meshgen, mesh drawtype, etc.)... but I don't think that would go well. Godot ended up throwing that thing out of the window with Godot 4, because it didn't match the best implementation they figured out, and building a new one around the actual implementation. The new system however still doesn't cover all usecases, and specifically doesn't work well (almost at all) with voxel (or other heavily chunked) terrains (last time I checked). What we can make of it however is that we shouldn't blindly set up a system of semi-static (because specific LOD distances could be dynamic and set by a heuristic for example) handling of distances etc. along with maybe LODs for mesh drawtype, and then build more general LODs on top of it, because it may end up being incompatible.
IMO, probably the safest option would be to wait until someone gets a mesh drawtype LOD system somewhat working in another PR (which theoretically should be way easier than this), and then look at both that and this PR and think how to unify it into a consistent system. Other options are:
Get this done first. Runs the risk of making it significantly harder to handle mesh drawtype LODs.
Get mesh drawtype LODs done first and then go back to this. Runs the risk of making it significantly harder to make this working with the assumptions mesh drawtype LOD system would make... and, to be frank, also the risk of losing contributor focus.
Get a shim LOD system working first in a branch (setting LOD levels for mapblocks and a debug way to visualize them), then rebasing this and building any other LOD systems on top of it. Runs the risk of making everything incompatible with the assumptions we would make.
Honestly, all options should be considered, but all risks must also be acknowledged. And on top of all these, comes the ultimate party breaker, the elephant in the room: this is a reverse SSCSM situation. LOD system running client-side is nice and ultimately needed, but we need to also look for a way to send semi-LOD'd blocks to clients too, because network bandwitch is limited. The scenes above look nice, and we probably could get even further horizons, but how long will those blocks load? And I don't even mean mapgen (although we'd probably need to run a broad-strokes mapgen to quickly churn out LODs for ungenerated blocks too), I don't even mean loading from DB, I mean the network will come back to bite us when we do a good LOD system, because clients won't be able to obtain blocks quickly enough to make use of it.
