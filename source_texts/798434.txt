The terrain is the one thing that fills the whole screen, and its shader was sampling ten anisotropically-filtered textures at every pixel of it: eight splat layers plus two control maps, every layer multiplied by its weight and summed. Most of those samples were multiplied by zero.
PEI's own splatmaps say by how much:
Layers a tile names
8
Layers a tile paints, on average
3.4 — three of the sixteen paint exactly one
Splat texels giving all their weight to ONE layer
87%
Splat texels using at most two
99% (mean 1.14)
So four or five of the eight were sampled across a whole tile only to be scaled by a weight that is zero everywhere on it — and even among the layers a tile does paint, one sample in the blend is the common case and eight is nobody's.
What changed
The shader is generated per painted-layer count instead of written out for eight.
Per tile. A tile binds only the layers its new SplatmapTile.ActiveLayerMask() reports. A tile painting four or fewer therefore carries one control texture rather than two — a sample saved and half the control VRAM, on twelve of PEI's sixteen tiles.
Per pixel. Each remaining sample sits behind its own weight (if (weight > 0.0)), so the layers this pixel does not paint are not fetched at all.
render_mode specular_disabled. SPECULAR is 0, which makes f0 zero and with it the entire Schlick-GGX lobe, so the render mode drops ALU that was multiplying out to nothing. It is what the flat fallback material has always done.
Roughly ten fetches per ground pixel down to two or three.
Not one pixel moves — and that was checked, not argued
PEI rendered terrain-only (water/foliage/objects switched off, so nothing animated is in frame) is bit-for-bit reproducible between runs — two captures of the same build differ on 0 of 5,988,600 channel samples. That makes it a real oracle rather than an eyeball test, and it caught two mistakes in the first draft of this change:
textureGrad cost the anisotropic taps. Hoisting dFdx/dFdy out of the branch and sampling with explicit gradients is the spec-tidy way to sample inside a conditional, and it came back visibly blurrier — deltas to 110/255, layer texture detail washed out while the splat boundaries stayed crisp. The sample keeps its implicit LOD instead, which is well-defined here for the reason the spec's warning is about the opposite case: uv is computed in uniform control flow, so every lane of the quad, helper lanes included, holds the value the derivative is taken from.
SPECULAR = 0.0 is not redundant with specular_disabled. The render mode guards direct light alone; the sky's indirect specular reads f0 regardless, and leaving SPECULAR at its 0.5 default gave f0 = 0.04 and lit the ground measurably brighter everywhere — deltas to 17/255 across the whole surface.
With both corrected the capture is identical to the unmodified render: 0 of 5,988,600 channel samples differ.
Measuring it
terrain.splat.unpainted.enabled prices the per-pixel half in a running frame:
```
r.vsync.enabled 0
perf
terrain.splat.unpainted.enabled 1     # sample the layers a pixel gives no weight to
perf
```
The image is identical with it on, so the difference between the two frames is the fetches and nothing else. The per-tile half is not switchable — it is decided when the material is built.
Tests
SplatmapTile.ActiveLayerMask against a painted tile, an empty one, and the early exit when all eight are painted.
The material a textured tile ends up wearing: which layers it binds, that a tile painting three needs one control texture and not two, that each painted layer's weight lands in the channel that multiplies its own texture, and that unfilled channels read zero so they add nothing to the blend or to the total.
The generated shader's shape — one branch per painted layer guarded by that layer's own weight, a total that still sums every one of them, no textureGrad, and SPECULAR still written.
The console binding, including telling "no terrain loaded" apart from "terrain wearing the flat-colour fallback", which has no splat layers to skip.
2474 unit tests, 11 terrain runtime tests and 17 console runtime tests pass, and the 13 structural metrics still match PEI.json.

Two halves of the same thing, both reported from a real measuring session.

Ctrl+C over the scrollback did nothing. The label has SelectionEnabled and
the selection works, but its FocusMode is None — deliberately, so that typing
always reaches the prompt — and RichTextLabel's own copy shortcut only fires
when it is focused. The key was reaching the LineEdit, which copied its own
empty selection. The overlay takes the keystroke now, and only when there IS
something selected in the log: with nothing selected it lets it fall through,
because then the selection the person means is the one in the input box.

`copy` puts the whole scrollback on the clipboard as plain text, which is
what a bug report wants and what dragging a selection across a few hundred
scrolling lines cannot practically produce. Both paths ask the display server
for a clipboard first, since Godot only warns when there is none and a copy
that quietly did not happen is worse than one that says so.

Pasting was the other half. A recipe is written one command per line — in a
note, in an issue, in this repo's own docs — and the prompt is a LineEdit,
which drops the newlines. Four commands arrived as

    terrain.enabled 0perfterrain.enabled 1perf

one word, no such name. The console's grammar already runs several statements
from one line, so that is what a pasted block becomes: a newline separates
statements exactly as `;` does, `//` now ends its own LINE rather than
everything pasted under it, and a quote left open ends there too instead of
swallowing the commands below. Flatten() joins them back into the one line
the prompt can hold, and the round trip keeps a quoted `;` whole.

A single-line clipboard is left alone — the LineEdit's own paste already
handles the selection, the caret and the undo stack, and there is nothing
about it to fix.

Two defects in yesterday's clipboard work, both found in review, both real.

Flatten undid the rule it exists to serve. A line break ends a quote and a
`;` does not, so joining `echo "open` and `perf` gave `echo "open; perf` —
separator inside the quote, second command swallowed, which is precisely the
"one stray quote must not reach the commands below it" the newline rule was
added for. The quote is closed on the way now. That costs nothing: Words
already reads an unterminated quote as running to the end of its statement,
so `echo "open` and `echo "open"` were always the same two words.

InsertTextAtCaret does not replace the selection. The LineEdit's own paste
deletes it first and this path does not go through paste_text, so pasting a
recipe over a selected command kept both and ran the two welded together.
The insert is split out of PasteBlock to do it — and split for a second
reason: a headless session has no clipboard, so PasteBlock refuses at its
first guard and everything past it was unreachable from the suite. Now the
part worth testing is reachable, and the test fails without the fix.

  * The README said pasting runs the commands. It fills the prompt; Enter
