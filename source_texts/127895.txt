Contributor
Next crate off the buildout branch. Boxes, spheres, planes, rays, triangles and a view volume, computed in the same fixed point as everything else in the simulation ring, so a cast that decides a hit decides it the same way on every machine.
What it is
Aabb, Sphere, Plane, Ray, Triangle and Frustum. Triangle is Moller-Trumbore.
Frustum stores four numbers rather than six planes, and it is worth saying so plainly because an earlier version of this description claimed the latter. The half-height at a forward distance is a straight line, h(d) = base + slope * d, and perspective and orthographic are its two ends -- base == 0 for one, slope == 0 for the other. One type covers both with no discriminant, which is what lets it be Pod; an enum could not be. near_half_height and far_half_height are the geometric reading, derived.
The arithmetic, and where it ended up
This crate contains no integer type and reads no bit pattern, and nothing in the cast path is wider than a word. Every quantity here is an I24F8, an I16F16, a Direction or a GlobalPoint, and every operation is named for the geometry rather than for the width it needs.
It took three review rounds to get there and each one invalidated the last one's reasoning, which is the useful part of the history:
Round one: the widening was in the wrong place. The crate's claim is "accumulate wide, narrow once" -- and it was skipping that at its inputs. GlobalPoint's subtraction saturates each component, so every difference of two points was clamped before any accumulator saw it. Measured, before the fix:
```
box [-6000 km, 6000 km]:  half_extent 4194 km (should be 6000)
                          centre     -1805 km (should be 0)
sphere at one end of the world, radius 8388 km:
                          contains(other end, 16000 km away) = true
triangle spanning the world:
                          normal (-0.707, 0, 0.707), 31 degrees out
```
Round two: most of the widening was not needed, and my justification for it was wrong. The module comment argued that three Q39 products cannot fit an i64 because 3 * 2^62 exceeds i64::MAX. A Direction is a unit vector, so the sum is a dot product and Cauchy-Schwarz bounds it by sqrt(3) * 2^62 -- 7.99e18 against 9.22e18, 13% of headroom. I had widened from a bound I never checked. corvid_vector/tests/project.rs now searches for the corner of the range that reaches it and finds it exactly: the bound is tight, so the headroom is real and it is all there is.
Round three: the wide offset was not worth its type, and it was the thing forcing the rest. A WideOffset -- the difference of two points, one bit wider than either -- was what made a cross product 2^65 and a triple product 2^98. Deleting it takes the whole cast back inside an i64. An offset is a GlobalPoint like any other, which is a constraint rather than an observation: two points more than 8388 km apart have no offset in this type, and checked_sub is how a caller finds that out. A saturated difference clamps one axis and not the next, so what comes back is a different bearing rather than a shorter one; a miss is the better answer, and every method here already had somewhere to put one.

corvid_vector/tests/measure.rs goes looking for the corner of the range that reaches each of those rather than taking the algebra's word for it -- for the determinant, every pair of the eight corners against two thousand directions, checking the sign against an f64 reference.
Three things came out better than a relocation:
The sphere's discriminant is exact where it was not. It was disc = b^2 - c with c = |oc|^2 - r^2; both terms are near 2^62 at the edge of the range and their difference is the small number that decides hit from miss. It asks rejection_squared for the squared closest approach directly now, so whether a ray finds the sphere is exact even when the distance it answers has to clamp.
The triangle's fourth determinant is gone rather than bounded. It is a volume where the other three are areas -- a whole metre of scale further out, reaching 5.9e20, and the only thing in the workspace that ever needed more than a word. Once u and v are known the hit is located already, so the routine walks to it and projects back onto the ray.
A box wider than a component needs no special path at all. Its middle is the corners interpolated halfway, which is in range because a midpoint lies between two points that are, and lerp never leaves the interval it is given. The half extent follows from the middle.
Everything else review found
Every comment was real. Besides the arithmetic:
An inverted box reported overlapping. [1, 0] satisfies both interval comparisons against [-1, 2], so an empty box met things. Empty operands are rejected first.
The frustum culled spheres that were partly inside -- the one answer its documentation promises never to give. It inflated the half-height vertically, which is not conservative for a plane that leans; the radius is projected onto the plane's normal now, which is radius * slope.hypot(1) using corvid_fixed's own hypot.
A negative radius was visible to the frustum, while Sphere reads one as empty everywhere else.
Angle16::half clamped silently. 270 degrees halved to 90. It answers Option now, None past a half turn.
slope_of derived a tangent from sin_cos and a division, including its own guard for the quarter turn -- eleven lines re-deriving what Pitch32::tan already does. Two lines now, over a new I24F8::to_i16f16.
direction(0, 1, 0) did not compile. The signed-normalized types take an i8 now, saturating: the range is -1.0 ..= 1.0, so three integers are all it holds, and i8 is the narrowest width that spells them.
The nursery lint group was not ready, and was forcing thirteen files' worth of allow attributes -- mostly redundant_pub_crate, which argues with the workspace's unreachable_pub rather than with the code. Gone, and the allows with it.
Three dependencies were not used. corvid_transform was named nowhere in src and was pulling corvid_rotation into every build; corvid_hash is tests-only; corvid_bits has since lost its last caller here.
The README said everything was world space while shipping a frustum whose methods take eye-space FinePoint. Corrected, and the missing Frustum row added.
The integer conversions had no tests, despite my doc comment saying tests/conversion.rs checked them. It does now, at both endpoints of all four pairs.
every_shape_round_trips omitted Frustum. Included.
What is still known-wrong
tests/wire.rs freezes digests with literal values but round-trips the encoding rather than recording bytes. The digest table catches a width change, since corvid_hash absorbs declared widths; it would not catch a pure reordering. Literal hex for every public type belongs in one pass.
One i128 remains in corvid_vector that is not inherent to GlobalFinePoint's own width: unit_component, the private last step of normalize, multiplies a Q30 by a Q31 by the 2^31 - 1 unit, which is 2^92. Any two of the three already reach 2^61, so no reordering helps; splitting it into two shifts would fit an i64 and cost a last bit on every normalized direction.
The landed-crate additions
Each lands with its first caller rather than ahead of one: Direction::X/Y/Z, the lowercase point builders, the integer conversions on the fixed-point scalars, Angle16::half, and the ones review asked for --
From for the signed-normalized types, saturating. Lossy, unlike most From, and deliberately so: clamping is what the type already does everywhere. One impl and no more -- an unsuffixed literal reaches an impl Into parameter as an inference variable and rustc commits it only when exactly one candidate applies, so a second impl would make direction(0, 1, 0) ambiguous and stop it compiling again.
Direction::from_ratio([i64; 3]), whose caller is GlobalPoint::cross_direction: a cross product of two Q8 bit patterns reaches 2^62, so it fits a word and fits nothing narrower. The scale cancels -- but not always exactly, since the reduction shifts by a whole number of bits, so a power-of-two scale is bit-identical and any other can differ in the last places. Both cases are pinned as tests rather than left to be discovered.
GlobalPoint::project / distance_squared / rejection_squared / cross_direction / volume, Direction::align / along, and Volume in corvid_vector; I24F8::squared / to_i16f16 / the two div_signed32, and I48F16::root in corvid_fixed. These are the relocation.
Tests
56 in corvid_shape across four files, plus 13 new in corvid_vector for the projections and the determinants, plus doctests. tests/frustum.rs is new -- there was no frustum test at all, which is how both of its bugs survived -- and holds the reviewer's own counterexample.
Every behaviour fix is pinned by a test that fails against the old code, checked by reverting rather than assumed. That caught one test that proved nothing: the first triangle I wrote for normal was coplanar, and a vector already axis-aligned does not move when its components saturate, so both versions answered +Z. Tilting the face is what separates them.
Several of the new ones check a claim rather than a behaviour, which is the point of them: every bound in the table above is asserted both to hold and to be approached, so a bound that were merely generous fails too. a_projection_is_the_same_number_the_narrow_one_answers checked fifty thousand cases before the wide path was deleted; what survives it is the_widest_projection_in_the_world_still_fits_an_i64 and a_volume_at_the_corner_of_the_range_still_fits_a_word.
check.sh exits 0 on 1.97.1, every file under the size limits. The crate-wide allow attributes flagged as a NOTE are expect_used/unwrap_used and cast lints in tests, matching what main already does.

Done in a813a24. Direction::from_ratio([i128; 3]) -> Option<Direction> is public on corvid_vector, and Triangle::normal goes through it:
```
pub fn normal(&self) -> Option<Direction> {
    let first = offset_bits(self.b, self.a);
    let second = offset_bits(self.c, self.a);
    Direction::from_ratio(cross_wide(first, second))
}
```
from_ratio is normalize_bits with a name and a contract rather than a new algorithm -- it is the same reduction every normalize on a point type already calls, exposed for the caller whose vector is a cross product or a difference of far-apart points and has therefore already left a component's range.
It was measurably wrong, not just theoretically. Reverting to the old body makes the new test fail, which is the check worth reporting. A face whose corners describe (-0.2425, 0, 0.9701):
```
old: (-0.707, 0, 0.707)   -- about 31 degrees out
new: (-0.2425, 0, 0.9701)
```
My first attempt to demonstrate this proved nothing: I used a coplanar triangle, which gives +Z under both versions because saturating a vector that is already axis-aligned does not move it. Tilting the face is what separates them.
