Bug report
Bug summary
When creating a volume render in parallel, "Scene" data is collected in a stored variable. After the for-loop ends, the stored data needs to be merged but an error arises in combining the objects. The code below works fine in serial but not in parallel.
Code for reproduction
Online dataset to generate error: maestro_xrb_lores_23437
Run in serial, works: python code.py
Run in parallel, does not work: mpirun -np 4 python code.py
```
import yt
import glob 
import numpy as np


# Initial position to set camera
init_pos = np.array([0.3,0.1,0.55])

# yt inputs
yt.enable_parallelism()
yt.funcs.mylog.setLevel(50) # eliminate output from yt load

# Load data file
glob1 = glob.glob('maestro_xrb_lores_23437')
files = sorted(glob1)
ts = yt.DatasetSeries(files, parallel=1)
time = np.zeros(len(ts))

# Scenes to save for storage
my_scenes = {}

# Iterate through all data sets in parallel. Store scenes and frame
# fr-frame, sto-storage, ds-data set
for fr, (sto, ds) in enumerate(ts.piter(storage=my_scenes)):

    time[fr] = ds.current_time
    print('creating scene for... time = %0.3f' % time[fr])

    # Create volume render
    im, sc = yt.volume_render(ds, lens_type='perspective', sigma_clip=2)  

    # Store results
    sto.result = sc
    sto.result_id = fr
```

This seems to work without raising any exceptions (based on your example above):
```
# Load data file
glob1 = glob.glob('enzo_tiny_cosmology/DD000[0-3]/DD000[0-3]')
ts = yt.load(glob1)
time = np.zeros(len(ts))

# Scenes to save for storage
my_scenes = {}

# Iterate through all data sets in parallel. Store scenes and frame
# fr-frame, sto-storage, ds-data set
for fr, (sto, ds) in enumerate(ts.piter(storage=my_scenes)):

    time[fr] = ds.current_time
    print('creating scene for... time = %0.3f' % time[fr])

    # Create volume render
    im, sc = yt.volume_render(ds, lens_type='perspective', sigma_clip=2)

    # Store results
    sto.result = im
    sto.result_id = fr
```
It should be possible to store the Scene object like you're doing so I'm leaving this issue open but hopefully the workaround of just storing the image itself on the storage object will be good enough for now.
