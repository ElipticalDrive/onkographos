Summary
Phase 2 of #82 (the .interp half of Proposal 0005 step 5, following phase 1's .sel half in #121): a genuine N-D interpolation over a multi-dim compact affine coordinate.
x.interp(lat=..., lon=...) groups queried coordinate names sharing dims the same way .sel does (square-system requirement, one joint group per call for now — a second group raises NotImplementedError).
Inverts the affine map once per call (shared across every query point) to a fractional index — never rounded, unlike .sel's closed-form pick — then pulls the tensor's values via fiery.interpol.grid_pull (order ≥ 1, or order 0 with the backend) or a built-in separable nearest gather (order 0, no backend needed). Solved in float64 regardless of the spacing's own/default dtype, matching .sel's and the 1-D .interp path's conventions.
Output shape, resolved against xarray's own precedent (researched xarray.indexes.CoordinateTransformIndex — its own affine-inversion index type — and vectorized/pointwise indexing generally): a query with every name given as a scalar is a single point, dropping all spanned dims (the existing .interp/.sel scalar convention). Any name given as a list/tensor makes the whole group "many": every name's query broadcasts to a common length N, and the spanned dims collapse into one new axis of N sampled points — not an outer-product grid, since the dims are coupled (you can't vary one queried name without moving through every spanned dim at once). This mirrors xarray's own vectorized/pointwise-indexing convention for a value-based query on a multi-dim coordinate; CoordinateTransformIndex in fact only accepts this shape (rejecting a bare scalar/list outright).
The new axis is named via a new name= keyword on interp (default unnamed, matching xstack's convention for a brand-new axis) and carries every queried name's own sampled values as a riding coordinate — mirroring how xarray's vectorized indexing collapses its own auxiliary coordinates onto the new dimension for free.
Composes with ordinary 1-D .interp indexers in the same call. Querying a spanned dim directly afterward fails naturally (the dim no longer exists once the joint pull replaces it) — no special-case guard needed, unlike .sel where the position still existed post-solve.
Tests
Exact and interpolated scalar queries, many-query new axis (named and default-unnamed), axis insertion position with an interspersed unrelated dim, mixing with an ordinary 1-D indexer, broadcasting a length-1 query against a list, mismatched-length raise, under-determined raise, singular-map raise, multiple-simultaneous-groups raise, empty query, nearest without the backend, higher order requiring the backend, gradient-safety through a learnable spacing, and a 100-trial randomized differential test against a hand-computed bilinear reference.
Full suite: 507 passed; lint/format/spell clean.
Progress on #82 (phases 1 and 2 both landed — closes the issue, pending a final review pass).

Per Opus review of PR #124:

- lengths.discard(1) can leave n=0 (an empty query, #96's empty-axis
  case) while the per-name broadcast only expanded a length-1 sibling
  when n > 1, so an empty query paired with a scalar/length-1 one on
  the same group crashed inside torch.stack instead of producing a
  well-formed empty axis. Broadcast whenever n != 1, not just n > 1.

- interp's name= parameter always binds a matching keyword argument to
  itself before **indexers_kwargs ever sees it, so interp(name=3.0) on
  a dim literally called "name" was a silent no-op (indexers ends up
  empty, nothing happens, no error) -- exactly the collision risk this
  keyword introduces. Reject a non-str, non-None name with a clear
  TypeError pointing at the indexers={"name": ...} escape hatch,
  instead of silently doing nothing.

- Clarified the public interp() docstring: the new axis only carries
  riding coordinates when a name was actually resolved.

Hand-checked the closed-form affine inverse against manual bi/trilinear interpolation for axis-aligned, rotated, and sheared cases — exact to 1e-9. Scalar-drops/many-collapses shape logic, new-axis insertion position, gradient flow (analytic vs. finite differences, ~1e-7), the one-group-per-call restriction, and the natural (structural) failure on re-querying a consumed dim all checked out.

Same fix as the .sel counterpart: naming the new parameter `indexers=`
reintroduced exactly the collision class this escape hatch set out to
fix -- a dim literally called "indexers" worked via **kwargs before,
but keyword-binds to the new named parameter instead now.

Python 3.8+'s `/` positional-only marker isn't available on this
project's 3.7 floor (CI tests it), so use *args instead, which is
positional-only by construction on any supported Python version:
`def interp(self, *indexers_positional, method=..., ...)`. A keyword
argument named anything (including "indexers") can never bind to a
bare *args slot, so it falls through to **indexers_kwargs exactly as
before this escape hatch existed.
