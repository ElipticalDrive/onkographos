What problem(s) does this PR solve?
Proper fix for Normalmap inverts at certain angles on mesh rotated by bone. #81446
Additional information
My previous PR #117401 had some caveats. For instance, it did not take the binormal sign encoding into account.
The way it works is that the binormal sign is encoded in Oct.y. Oct.y is encoded as UNORM16, so values > 0.5 means positive, and values < 0.5 means negative. Since UNORM16 encoding does not allow a value of exactly 0.5 (aka zero once unpacked), the binormal sign was flip-flopping between positive and negative.
The fix is to clamp the Oct.Y value between [1.0/65535.0; 1-(1.0/65535.0)]. This also avoids the issue with compression detection altogether (what PR #117401 tried to fix).
I also removed usage of some sign function as its not very efficient on the GPU because it handles many different cases (+/-INF and zero). It's a lot simpler to just check if >= 0

All normal values cannot be represented with Octahedral encoding anyway.
According to this paper: https://jcgt.org/published/0003/02/01/paper.pdf
Oct32 (Oct 2x16bits) has a mean error of 0.00131° and a max error of 0.0037°. Worst case scenario, this would introduce an error of 0.0074° (max error x2 since we remove two non-adjacent possible values out of 65535).
I believe this is more than acceptable for a normal encoding. From my own investigations, I found that 2x12 bits is more than enough to represent a normal vector accurately with no visible artifacts.
Besides, the modified code here is only used for tangent encoding, which requires even less precision in theory.
The other alternative to clamping is to check the 0.5 value case specifically, but floating point comparison is always a pain. I find my method more elegant than this + the encoding detection from before, although a bit more convoluted perhaps.

I did a test in python to validate my assumptions. Interestingly, I don't get the same result as from the paper, I believe this is because I am comparing directions against a 64bits vector reference, whereas the paper compares against 32 bits as the reference.
How to read this graph:
I am generating 1 million unit vector directions using a Fibonacci distribution for better uniformity. This direction is encoded in a Vector3 with 64bits per channel. From this reference vector, I compute a Vector3 with 32bits per channel (float32). From this 32 bit vector, I compute the octahedral encoding, quantize it in 16bits per channel (Oct32), then decode it to a Vector3 again to measure the angle error from the encoding/quantization/decoding.
I do the same thing again, but clamping the quantized result before decoding (Oct32_clamped).
All the graphs here represent the error compared to the reference 64 bits Vector, measured in degrees.
Top left is a histogram representing the distribution of the error angle
Top right is a box plot of the same data, showing mean value and standard deviation
Finally a table that shows precise values
As you can see, there is no difference between the clamped/unclamped encoding, suggesting that the error between the two is minimal.
In good faith, I also tried with Oct30 (15 bits per channel, since Godot uses 1 bit for the binormal sign), and I get similar results.
I also did another test, which is actually closer to what is happening with my proposed fix, by using the Oct32 decoded result as a reference:
You can see the max error is negligible with 0.0442 degrees. Again, we are talking about a TANGENT vector, so the error is far less important than the normal error.
