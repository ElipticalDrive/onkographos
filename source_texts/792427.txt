Title: Implement PLY header parsing to support pre-allocation and dynamic schemas
Description
The read_ply_binary function currently reads the PLY header into a buffer but does not parse it. It relies on reading the file stream until EOF to determine the number of points.
This approach causes two main issues:
Performance: Vectors (points, colors, normals) are initialized with zero capacity, causing frequent reallocations as they grow. We need to parse the element vertex <count> line to pre-allocate memory.
Correctness: The code assumes a fixed property layout. It should parse the header to validate the schema or adapt to different PLY property definitions.
The goal is to implement a proper parser for the header metadata to resolve the TODO and enable these optimizations.

How do you plan to fix it?
My plan is to extend read_ply_binary with PLY header parsing that reads lines up to end_header, extracts the element vertex entry to obtain the vertex count, and collects the corresponding property lines for the vertex element. Using this information, I will pre-allocate the output buffers (points, colors, normals, etc.) with the exact vertex capacity instead of growing them dynamically. I will also build a small schema from the property lines (name, type, and order) so the reader can handle different valid vertex layouts, including optional normals and colors. The binary read loop will then use this schema to map each field into the correct output arrays and return a clear error if required properties for points are missing. Finally, I will add tests with multiple PLY headers (varying property order and subsets) to confirm that pre-allocation and dynamic schemas work as intended.

Good morning @sidd-27,
I’ve been digging into the read_ply_binary implementation. After testing it against some real-world datasets like the Artec Golden Tiger, I noticed a few things that I think we should address. Since I am still relatively new to Rust, I tried my best to implement these fixes idiomatically, but I would really appreciate your constructive feedback on the approach.
As per my understanding, I think these are the main issues with the current code and how I've tried to address them:
Data Integrity (Element Context): The current reader doesn't distinguish between vertex and face elements. In models with large face lists, it keeps reading past the vertex section and interprets face indices as points.
The Fix: I added a state tracker to the header loop to calculate the exact header_stride and ensure we only parse data strictly within the element vertex scope.
Memory Efficiency: Without parsing the vertex count from the header, the vectors are growing dynamically.
The Fix: I'm now using Vec::with_capacity based on the parsed vertex count to eliminate reallocations and unnecessary memory copies.
Stride Alignment & Robustness: The current logic is fragile if the file schema doesn't perfectly match our structs (e.g., missing normals or extra properties).
The Fix: I rewrote the reading loop to use a zero-filled buffer. It reads min(header_stride, property_size) bytes, which allows files with partial schemas (like missing normals) to load safely without panicking.
Security (DoS Prevention): There’s currently no check to verify if the file on disk is actually large enough to hold the data the header claims.
The Fix: I added a metadata correlation check to prevent "PLY Bombs." It verifies the expected data size against the actual file metadata before any allocation happens.
Summary of Changes I propose:
In parser.rs:
Implemented a state machine in the header loop to strictly isolate vertex properties.
Added a security check to validate claimed vertex_count * stride against file size on disk.
Switched to a count-based reading loop using read_exact and consume to handle extra properties (like intensity) without losing alignment.
In properties.rs:
I plan to add Dynamic variant to the PlyType enum to support arbitrary schemas:
```
pub enum PlyType {
    OpenSplat,
    XYZRgbNormals,
    Dynamic {
        stride: usize,
        offsets: std::collections::HashMap<String, usize>,
    },
}
```
Updated size_of() and deserialize() to handle varying buffer sizes and the new dynamic stride logic.
