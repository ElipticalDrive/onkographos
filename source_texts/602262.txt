Describe the project you are working on
3rd-person (very) small open world -action game in NPR-style.
Describe the problem or limitation you are having in your project
The quality of close-up dynamic shadows isn't good without increasing shadow resolution. However, the extra resolution is spent wastefully decreasing the performance unnecessarily. Often the shadows of the environment could be rendered at a lower resolution but the resolution has to be set high to get passable shadows for characters. This is especially true for the self-shadows on the characters and smaller detail.
Most notably, a global shadow map is inefficient when used with baked lighting since only a few dynamic objects are left to light/shadow. This greatly diminishes the effectiveness of baking shadows in the first place.
Describe the feature / enhancement and how it helps to overcome the problem or limitation
By rendering dynamic meshes to their own shadow map-atlas, they could benefit from better-quality shadows. This gives agency to the developer to up the effective shadow resolution where it's most needed (e.g. player-character, certain enemies). This also considerably increases the performance when used alongside baked lighting/shadows since the resolution of the shadow map is used more efficiently for the remaining dynamic objects.
When used alongside a traditional global shadow map (i.e. no baked static shadows), per-object shadows do have a performance hit. That said even with mainly dynamic lighting, the overall cost might be lower if it avoids the need to use a higher-resolution shadow map. For reference here's an extract from the CryEngine documentation about the cost (link):
... The drawbacks are increased memory consumption of the additional shadow maps and increased shadow filtering cost. As an example, the additional cost amounted to approximately 0.25ms for the main protagonist in Ryse on XboxOne.

Describe how your proposal will work, with code, pseudo-code, mock-ups, and/or diagrams
At least CryEngine and Unreal Engine support per-object shadows (In Unreal land, per-object shadows are called inset shadows). In Unreals case they're enabled by default for dynamic objects. Some snippets from above:
Objects marked to render per-object shadows work by rendering a depth buffer for the object from the perspective of the light with the help of their bounding box and then projecting it onto the world.
For animated skeletal meshes it may save time computing a new tighter bounding box every frame.
The per-object shadows could/should be only used for directional lights since they're the main culprit for low-resolution shadows.
In addition to relevant project settings etc. it would be useful if shaders could customize what layers they sample and probably also how much; only cast or only receive per-object shadows or blend with the global ones etc.
If this enhancement will not be used often, can it be worked around with a few lines of script?
Not without modifying the rendering pipeline.
Is there a reason why this should be core and not an add-on in the asset library?
Cannot be done without modifying the rendering pipeline. Guess you could write your own renderer :^)

If you want detailed shadows for dynamic objects but still want far away static objects to cast shadows, shadowmasking is probably a better solution. It allows you to greatly reduce your DirectionalLight3D's Shadow Max Distance property without affecting how static shadows look in the distance. This can actually improve performance, as fewer objects need to be included in the shadow mapping draw calls.
Per-object shadows seem like a highly AAA-oriented solution to me. I don't think this kind of solution would see a lot of usage in Godot, considering how demanding it is (and how it needs highly detailed models to really be beneficial, unlike shadowmasking which benefits almost any scene out there). We should probably be looking into ways to make shadow rendering cheaper in the first place 🙂
Godot 3.x used to support contact shadows, which trace pixel-perfect shadows in screen-space (this is intended for contact hardening). These were very expensive though, and regularly caused GPU lockups to occur if the camera got too close to a mesh. Contact shadows were removed in 4.0 in favor of shadow normal offset bias/shadow pancaking, which provide similar contact hardening capabilities but with a much lower performance cost.

Individual shadows can be more expensive if used with dynamic lighting. I would make the bold claim that all games in Godot using baked lighting would benefit from this feature with both increased performance and shadow quality.

@clayjohn can correct me if they had something else in mind, but the proposed per-object shadowing system (as seen in cry engine and unreal) in its simplest form works by creating a shadow map per object (atlas if there are many) instead of a one big one. It's practically the same as how point- and spotlights work (except only shadows are local, light is still global). So ground shadows are indeed included.
I actually created an unpolished implementation of this ~month ago which yielded promising results (i.e. it didn't crash immediately) and thought of many ways it could be improved. I will finish it at later date and use it in my own project since I need to know which object cast the shadow --- unless a better solution emerges before then.
A simple demonstration (no shadow-bias).
Edit: you can also reference the ps3 title Final Fantasy XIII (2009), that used the technique (characters have separate shadows) https://twitter.com/AmazingThew/status/1579256188537278465. Image from link (left=character shadows, top-right=environment shadows, bot-right=depth):

I’ve made a working prototype of this feature for my game and would like to help get it into the engine.
I suggest implementing per-object shadows by creating a new node ShadowGroup3D for the editor. The dev would just place their character meshes inside such ShadowGroup3D node and it would automatically replace cascade shadows with a projection tightly fit around the character.
Video recorded with Godot 4.8 beta (custom build, master branch). Params shared by all 3 video clips:
Mobile renderer
Sun shadows: 2 cascade splits (PSSM), 80 m max distance, blend splits off
Soft shadow filter quality: Soft Very Low
Shadow blur 1.0, bias 0.1, normal bias 2.0
16-bit shadow depth
4× MSAA
Comparison screenshots:
Close-up shot
Self-shadowing demo
How it would work?
User places character meshes inside ShadowGroup3D, which registers these meshes as group members inside the renderer server. Once the merged bounds of all meshes within the ShadowGroup3D get closer to the camera than the given max distance, their cascade shadows get replaced with a tightly fit shadow projection. All shadow groups share a dedicated quadtree Shadow Group Atlas. Atlas gets created only when shadow groups exist. Shadow group atlas dynamically allocates tiles to each shadow group-directional light pair that enters the working distance range and evicts groups that go too far or get disabled by the user script. Tile size depends on the settings of each individual ShadowGroup3D node. One shadow group may have resolution set to either: Full (the whole atlas), Half (half the width, max 4 per atlas), Quarter (max 16 per atlas)… Size acts as a priority hint, groups with bigger sizing evict groups with smaller sizing setting. Sizing is flexible enough to accommodate different games where character may be one, two, or many. In short, shadow groups act like an opportunistic algorithm that tries to replace the cascades with a focused high quality shadow for meshes that developer thinks are important. When a shadow group goes too far from camera, its shadow falls back to normal cascade with a smooth transition.
Parameters each ShadowGroup3D would have:
Resolution (enum): Full, Half, Quarter, Eighth, Sixteenth. Acts like a priority hint, more important characters get bigger resolution.
Max distance (float) in meters from camera after which shadow group gets evicted from the atlas and falls back to standard cascade shadows. Max distance is also capped by the light’s own max distance, so shadow group disappears together with cascade shadows when the camera moves too far.
Fade start (float) from 0.0 to 1.0 defining how early the shadow group starts lowering its density to smoothly transition into cascade fallback.
Enabled (bool), a flag that allows the dev to switch to using normal cascade shadows and free up a slot in atlas for more important shadow groups.
Is it self-shadowing only or do groups actually cast shadows on the floor?
The groups cast both self-shadows and shadows on the floor. You can see self-shadowing in the end of the video.
Is the cost too high?
One advantage is that the shadow group method offers the devs a cost efficient way for improving shadows for important objects without increasing the size of the directional atlas. In my tests cascade-only approach and shadow groups seem to run with comparable frame times where shadow groups even show slightly lower average frame time which shows potential. Not naming numbers because I cant consider this a proper benchmark yet. Another analytical advantage of using shadow groups is to reduce draw calls for the character since cascades render the character multiple times when character is in-between the cascades. For games that don’t use shadow groups the cost would be zero or near-zero: the shader path is compiled out, the atlas is never created without existing shadow group, and the per-instance data reuses existing padding.
What would be the user experience?
The dev would just put important meshes inside ShadowGroup3D node and it would just work out of the box. Devs would see this node as hint for the renderer to give higher quality shadows to the meshes. Fallback to normal cascades would be smooth.
How does the hand-over to the cascades work?
Shadow group gradually blends its quality and bias to match the cascade.
What happens when the atlas is full? Who wins?
Shadow group with higher resolution setting evicts those groups that have lower resolution. Evicted groups fall back to normal cascades. With equal resolution the winner isn't defined yet, can consider adding a tie-breaker such as a priority integer or a flag.
Does it work with several directional lights?
Yes it does but it causes shadow group to consume one tile per light in the Shadow Group Atlas.
How does it interact with baked lighting and shadowmasks?
I haven’t tested this interaction yet but I’m ready to look into this for compatibility.
Why a group and not a single object?
Characters may consist of many objects at once: weapons, hair etc. Group approach offers the developer a natural editor-friendly tool to choose what meshes go into one atlas tile and what meshes should be separate.
What types of games would benefit from this feature?
Games that can get away with lower atlas resolution while keeping shadows crisp for their characters, NPCs and other important objects as @clayjohn pointed out. Especially good for mobile to achieve better perceived quality without having to increase the directional shadow atlas resolution.
VR games that want highest quality shadows at affordable cost for the player body, hands, weapons and items picked up by the player for close inspection while keeping the shadows cast by the rest of the world within the cascade atlas.
Fighting games where all you need is 2 super crisp shadows for your main fighters while the backdrop gets low res directional atlas
High end titles that want to have a dedicated super detailed shadow for their main characters
Large world games that want their sun to cast shadows even at the distant objects while keeping their characters shadow focused and crisp.
Is there demand for this aside from me?
I’ve posted a video on r/godot and people responded pretty well with at least 298 upvotes: https://www.reddit.com/r/godot/comments/1xcwui7/highquality_character_shadows_without_increasing/
Why I'm working on this?
I'm making a space game that would run on both PC and standalone VR. I need high max distance value for my directional light which makes my character shadow blocky and shimmery. Increasing shadow atlas size too much won’t be a good idea for performance. So I dug into Godot internals and built a prototype of ShadowGroup3D. It allowed me to prioritize shadow quality just for my character and its immediate surroundings while retaining normal cascades for the rest of the environment.
I already have a working feature prototype and recorded a comparison video on the Macbook running with M4 Max. I’m building my game with Mobile renderer, hence the feature only supports Mobile pipeline for now. However I’m ready to add support for Forward+, optimize it, test it on other platforms, write the docs and prepare a PR.
Would the rendering team be interested in this?
