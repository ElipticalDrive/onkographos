The world half of the game: a data-driven level format, swept circle-vs-grid
collision with a DDA raycast, procedural textures, and a player controller that
can actually walk around The Damp Cellar.
Levels are an ASCII grid plus a legend, because a level you can read in the
editor is a level you will actually edit. The parser rejects anything
malformed rather than loading it subtly wrong: a ragged row silently shifts
every cell after it, an unknown character would become a hole in the world, and
a missing player start drops you at the origin, which is usually inside a wall.
The tests that matter are the ones about the map itself. parseLevel exposes a
flood fill, and level.test.ts asserts every shipped level parses, has a
reachable exit, strands no walkable cells, and embeds no entity in a wall.
Those checks paid for themselves immediately: E1M1 as first written had its
exit sealed off behind 43 unreachable cells, a wall row that leaked at the map
edge, the red-key door on the inside of the vault it was supposed to gate, and
three entities buried in solid rock. Every one of those is invisible until
someone plays to the end and finds nothing there.
Collision is in grid units, not world units, so the maths never divides by
cellSize and a scale error cannot drop a body through the floor. Movement
resolves one axis at a time, which is what produces wall-sliding rather than
stopping dead on a diagonal. The axis sweep scans cell by cell from where the
body is to where it wants to be: snapping to the destination cell's boundary --
which is what this did first -- overshoots any step longer than one cell, fails
its own fit check, and reverts the whole move, so a fast body stops dead in
open floor. Scanning also means it cannot tunnel.
circleFits tests every cell the body's bounding box touches. A radius-0.28
circle straddles a cell boundary most of the time, so checking only the centre
cell lets the body's edge sink into a wall.
The raycast is Amanatides-Woo DDA, stepping boundary to boundary rather than
sampling along the ray. Fixed-step sampling misses thin walls and slips past
corners, which shows up as shots passing through geometry. The axis-aligned
case is guarded explicitly: 0/0 is NaN and every comparison against NaN is
false, so an unguarded ray would run to max distance and report a miss.
Geometry emits wall faces only where a solid cell meets an open one, merged
into one buffer per texture. Drawing all six faces of every block renders the
inside of every wall -- invisible, but still rasterised and depth-tested -- and
a mesh per cell would be 300 draw calls on this map alone.
Textures are drawn to a canvas from a seeded PRNG: no assets to host, and a
wall looks the same on every machine. Mipmaps are off, because averaging
texels at distance is exactly the smoothing the low-res target exists to avoid.
74 tests. The collision suite includes an exhaustive sweep asserting no start
position and direction ever ends inside geometry. Mutation-checked: skipping
intervening cells in the sweep, checking only the centre cell in circleFits,
and sealing E1M1's exit with one character each fail the suite.

Fix WASD moving in the wrong direction relative to the camera
…
edecf93
```
W did not move forward, and the way it was wrong changed with the camera's
yaw -- so the controls felt like they rotated independently of the view rather
than simply being reversed.

The camera is rotation.set(pitch, yaw, 0, 'YXZ') and a three.js camera looks
down its own -Z, so the ground-plane basis is:

  forward = (-sin(yaw), 0, -cos(yaw))
  right   = ( cos(yaw), 0, -sin(yaw))

Both z terms are negative. The old code negated neither, which mirrors the
basis about the x axis instead of reversing it. A mirrored basis still has unit
length and still keeps forward perpendicular to right, which is why it looked
plausible: it is a reflection, not a rotation, so W pointed somewhere different
and wrong at every angle.

The comment above it already said "forward is -z". Nothing checked that the
code agreed with the comment, so it didn't.

Extracted as movementDelta() and tested against three.js's OWN camera basis --
building a real PerspectiveCamera at each yaw and comparing to
getWorldDirection() -- rather than against a second hand-derivation, which can
be wrong in exactly the same way the implementation is. That is how this
survived the first two builds.

Includes a determinant check. Unit length and perpendicularity both pass under
the old bug; the cross product is what actually distinguishes a rotation from a
reflection, and it is the assertion that pins this down.

Reintroducing the original expression fails 30+ assertions across a full
revolution of yaw.
```
