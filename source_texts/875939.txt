Is your feature request related to a problem? Please describe.
Resonite has a lot of incredibly useful tools for handling various meshes and using them in different scenarios. You can quickly see all the actions you can perform on a Mesh here:
If there's one major feature I feel that is missing from this list, is a basic Mesh Decimation feature.
There can be lots of situations where you end up importing a mesh, and it ends up being far more dense than you expect. This can happen moderately often with users who work with CAD files, and it ends up being far more detailed than is necessary for just visualizing.
Describe the solution you'd like
Since Resonite is a VR-first engine, VR is still quite a GPU relient medium. As CPU performance improves in Resonite with more updates and changes, GPU performance will most certainly become the next bottleneck. You can see this case in the default Cloud Home world, as most users will see a GPU bottleneck rather than CPU in that world.
Decimation and LODs can be quite a vital first-step towards improving GPU performance in multiple scenarios.
Decimation options, much like the ones you see in Blender for Planar and Collapse style-decimation could massively help with those who need to quickly reduce poly-counts for optimization over strict-detail. Here's a list of possible use-cases for this feature:
Users working with complex and small CAD models can get pretty expensive due to GPU Overdraw wasting performance. Quickly being able to decimate the Mesh while having most of the required detail to visualize it on a lower-end system could help them a lot.
Digitally Sculpted models can require really dense meshes to allow artists to work with more detail. Those who wish to show off their sculptures in-world will always have to either end up doing the manual work of retopology or decimating before import, but an option in-engine would be massively helpful for those who wouldn't mind the quality trade-off to make their creations more performant.
Users are in full-control when manually adding Levels of Detail to their creations, and get to choose how much detail to preserve at certain distances. This would allow users to quickly improve rendering performance on their own avatars, items, or worlds.
Describe alternatives you've considered
Currently, the only method I have found for creating LODs for items is manually exporting the item itself as a GLTF file and decimating them in Blender. While this can be rather effective, it's a pretty slow and involved process to keep things like Transformations, UVs, Normals, and Materials properly preserved. The other limiting factor with this method is that it will not work with Skinned Meshes, since Resonite's exporter does not support exporting Meshes with Bones and Weights, so you must have the source-file of the asset you're working with in order to create decimated asset variants for it.

This is actually something that we want to add as part of the asset variant system. This will allow users to load lower density meshes on lower machines, without forcing that variant on everyone else - similarly to how users can enforce lower resolution textures.
The biggest part of work on this one is identifying a good decimation algorithm that we could integrate - one that produces good quality meshes and also has appropriate licensing that allows integration. There's a few I've seen, but some run into issues where they destroy some meshes, but I haven't done a deep dive on any of them.
If anyone's aware of any good algorithms/libraries for integration for us to look at, feel free to share!

I've found a couple good resources which talk about the math involved in mesh decimation, and linked them below.
https://www.cs.cmu.edu/~./garland/Papers/quadrics.pdf
https://webdocs.cs.ualberta.ca/~lin/ABProject/papers/4.pdf
https://odgy.medium.com/mesh-decimation-done-right-95245c4b5f52
The concepts in mesh decimation seem to be pretty simple. Every vertex/edge is examined in multiple passes and sorted by their significance to the topology. The least significant are deleted, and holes are triangulated.
Determining if a vertex is significant is done by approximating a plane from its neighbors, and finding its distance from the plane. For an edge, its as simple as finding the angle between the faces that it creates.
There was also another method that I found called quadric error which seems to be the best method (?), however with the short time I have spent on this, I was unable to fully understand it. Definitely worth some research.
I have linked some random projects below which implement the methods described above.
https://github.com/ShuTheWise/MyQem
https://github.com/nanolabo/nanomesh
https://github.com/Whinarn/MeshDecimator
Anyway, hope this helps.

I can't give you definitive answer on that, but probably not:
We need to evaluate the algorithms first and how well they work first. This step can't be skipped and needs to be done first before any coding actually happens.
We don't publish our core libraries right now, so you can't really reference in them in good way
We need to figure out and design how this will integrate with the engine. It's likely that the approach you'd choose wouldn't fit with out design needs and we wouldn't accept it
We also have certain requirements for code quality and maintainability. I don't know yours, so I can't say whether we'd consider it or not
We would still have to do work of integrating this with our asset variant system and other mechanisms, which is substantial work, so even if the code was accepted, it wouldn't really make it happen instantly - we'd still need to prioritize this on our end
