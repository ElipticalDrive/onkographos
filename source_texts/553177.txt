Summary
Per-visual blend mode + opacity, then multi-channel rendering as composition (one visual per channel, additively blended) — the next vispy-parity step. Additive is commutative, so multi-channel is order-independent and needs none of the OIT/A-buffer machinery (that stays a later, mesh-gated effort).
Commits
Foundation — BlendMode {Normal, Additive} + per-visual opacity as first-class Visual-trait state, on Image and the 5 volume visuals, exposed in Python and WASM.
Two pipeline variants per visual (premultiplied-alpha / additive), selected by blend mode; additive disables depth-write so coplanar layers don't reject each other.
Output standardized to premultiplied alpha → Normal is visually unchanged, Additive composites on the same convention.
opacity threaded through VTUniforms/VolumeUniforms and applied at every shader return site.
Examples — slice viewer and volume renderer compose N visuals (one per channel) with per-channel colormaps + additive; single-channel is unchanged.
Logical atlas tile is now derived per-dataset from the LOD-0 storage chunk (capped, uniform across LODs), so a tile maps to ~one stored chunk — avoids fetch storms on thin-chunked data (e.g. idr0062 chunk_z=1).
Added idr0062 (2-channel CZYX) to the volume renderer as a multi-channel volume test.
Verification
Single-channel regression: beechnut / marmoset render identically to before (premultiplied-output + uniform-layout change validated).
Multi-channel 2D: idr0062 in the slice viewer composites its channels additively in distinct colors.
Multi-channel 3D: idr0062 in the volume renderer raymarches the channels and sums them additively.
Deferred follow-ups
Per-channel UI — contrast limits, visibility, and colormap per channel (currently one shared contrast + an auto-assigned palette).
TODO(loader) — a true concurrent-fetch cap (semaphore-wrapped zarrita store); the current cap bounds in-flight tiles, not the per-tile fetch fan-out. Belt-and-suspenders now that tiles are chunk-aligned.
Phase 5b (joint-shader / N-D-transfer translucent multi-channel volume) remains out of scope.

slice web: budget-based atlas allocation instead of hardcoded 512 slots
…

```
The slice viewer hardcoded 512 tiles/channel, which thrashes when the
visible working set is larger — notably a side-on slice of data with
thin z-chunks (each z-slice is its own tile), where the plane crosses
the full z-extent. "Loaded" then plateaus below "visible" while pending
churns.

Port the volume viewer's VRAM-budget allocation (atlasSizeBytes +
computeMaxChunks binary search) and add a matching budget selector,
dividing the budget across the N per-channel atlases. This doesn't try
to predict the orientation-dependent working set — it just hands each
atlas as many slots as the budget allows (thin tiles are cheap, so that
is tens of thousands). When even that is exceeded, the library's thrash
warning fires.
```
