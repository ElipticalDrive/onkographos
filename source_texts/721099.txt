Follow-up to #12737 (closed). That issue's original example was a [format("r32ui")] RWTexture2D<uint64_t> write on CUDA. #12766 fixed the stride when such a texture is passed through a function parameter. The converting write itself still fails, even with direct access:
```
[format("r32ui")] RWTexture2D<uint64_t> tex;

[shader("compute")]
[numthreads(1, 1, 1)]
void computeMain() { tex[uint2(1, 0)] = 5; }
```
At master b00d9e4, -target cuda emits surf2Dwrite_convert<ulonglong>(…, x * 1, …) and exits 0. -target ptx then fails in NVRTC 12.6:
```
prelude/slang-cuda-prelude.h(1684): error : extern inline function "surf2Dwrite_convert(T, cudaSurfaceObject_t, int, int, cudaSurfaceBoundaryMode) [with T=ulonglong]" was referenced but not defined
```
Cause
When the [format] decoration is found and its scalar base type or channel count differs from the element type (_isImageFormatCompatible/_isConvertRequired, source/slang/slang-intrinsic-expand.cpp:234-267), the $C expansion (:555-600) appends _convert without checking which element types the prelude implements. The prelude declares surf{1D,2D,3D}write_convert<T>, but specializes it only for float, uint and int, plus their 2- and 4-component vectors:
prelude/slang-cuda-prelude.h:1662-1664 (1D)
:1743-1745 (2D)
:1836-1838 (3D)
Every specialization uses a 32-bit sust.p … .b32 operand. Any other element type reaches the undefined primary template.

For comparison, rgba8/float4, r8/float, r16ui/uint and rgba16ui/uint4 writes compile through NVRTC. A matching format and type such as r64ui/uint64_t or r16f/half uses the non-converting surf2Dwrite<T> and also compiles. The three I also checked with v2025.4 (r32ui/uint64_t, r32i/int16_t, rgba16f/float3) fail the same way there.
Expected
Either the prelude implements the converting write for these element types, or the compiler reports the unsupported combination itself instead of leaving it to NVRTC. For three of the pairs (a 64-bit element with a 32-bit format, and double), SPIR-V validation also rejects the shader. The maintainers may want to decide whether those combinations should be supported at all.
Related
Support format conversion on RWTexture in CUDA #11088 is the broader issue that CUDA format conversion is incomplete for reads and writes. It includes conversions that compile but produce wrong data, and draft CUDA surface format conversion prototype #11090 is a prototype for it. On the read side, the prelude's converting-read helpers decode half data and are defined only with half support (prelude/slang-cuda-prelude.h:1545-1594). An rgba8/float4 read currently fails with identifier "surf2Dread_convert" is undefined. This issue isolates one measured part: converting writes whose element type has no specialization, which NVRTC rejects.
Draft PR Fix #12627: lower partial RWTexture texel writes on CUDA to a surface read-modify-write #13363 adds E56007 for partial-texel accesses the prelude can't express. Open proposal CUDA: spell RWTexture Load/Store surface accesses once, through kIROp_ImageLoad/kIROp_ImageStore #13364 would move that check to every CUDA image access. As written in Fix #12627: lower partial RWTexture texel writes on CUDA to a surface read-modify-write #13363, the check treats every non-layered converting write as available without looking at the element type, so moving it unchanged would not catch these writes. That would also need a type-aware check, or an implementation for these types. Neither is on master.
