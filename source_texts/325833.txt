static freeze.
Taming 3DGS restricts the Adam step to the gaussians a batch actually rendered.
This lands it here behind an off-by-default --sparse_adam, with a fused CUDA
kernel that skips rows outside the visibility mask.

What the measurements changed about the plan
The visible fraction collapses as densification proceeds — 0.71 at 75k
points but 0.12 at the 1M cap. Four views out of eight cover most of a coarse
cloud but barely an eighth of a fine one, so an early reading badly understates
the mask's value.
A pure-torch masked step would have been a slowdown. index_select → Adam →
index_copy_ moves ~11 row-widths where the dense step moves 7, so it only wins
below ~64% visible; at N=1M it costs 36.5 ms against torch's 19.5 ms at full
visibility. That forced the kernel, which launches over all rows and returns
before touching memory for masked-out gaussians.

What a reviewer should weigh
Masking is a behavioural change, not only an optimisation. A dense Adam step
still moves a gaussian with no gradient, because stale momentum keeps being
applied while the moments decay. Masking freezes those gaussians instead. That is
what the method accepts; it is called out because it is not obvious.
tests/test_sparse_adam.py asserts those gaussians and their moments really do
not move — exactly zero, not approximately.
I predicted that would show up as slower mid-run convergence and an earlier
revision reported it as measured. Withdrawn: those numbers were the 3-image
metric, and they came from the one pair whose dense arm was contended. It also
cannot be re-measured from what was saved, since only chkpnt7000.pth and
chkpnt_best.pth are written — so the mid-run trajectory is simply unmeasured,
in either direction. Anyone wanting to early-stop should save mid-run
checkpoints and score them on the full set.
The 700-iteration smoke test cannot gate this flag: it never leaves the
~0.7-visible regime where there is no speedup to collect, and its held-out
number is the 3-image estimator.
I did not copy upstream's omission of bias correction — that makes it a
different optimizer and would confound a speed A/B with an optimizer change.
With an all-true mask this kernel reproduces dense Adam to ~1 ulp, asserted over
20 steps.
Implementation notes
SparseGaussianAdam subclasses torch.optim.Adam and keeps its state layout,
so GaussianModel's densification/pruning surgery on optimizer.state and
existing checkpoints keep working.
Composes with the corrected static freeze unchanged: the base snapshots frozen
rows and restores them after the step, which is exact whatever the optimizer
did, and a static row the batch never touched was not stepped at all.
densify_and_prune runs before optimizer.step(), so the mask can go stale;
those params fall back to a dense step. In practice that never fires — they
carry no gradient, so the p.grad is None check short-circuits first — making
it defensive. The unit test drives it directly.
fetchPly builds positions as np.vstack([x, y, z]).T, so _xyz arrives
F-contiguous (stride (1, N)) until the first densification cat. The
optimizer relays such params out at construction. Worth a separate fix at the
loader: for the first ~500 iterations every rasterizer call re-lays-out _xyz
too.
Opacity decay's visibility (frustum ∧ temporal, counted per gaussian) is not
nested inside the union radii > 0 mask, so a few sub-pixel gaussians can have
opacity decayed without an Adam step. Recorded in the experiment doc; no
correction made.
SPARSE_ADAM_STATS=1 reports kernel / fallback / skip counts at exit, so it is
possible to confirm the kernel is doing the work rather than silently falling
back.
The extension is JIT-built on first use and cached, so the flag costs nothing
when off. Needs ninja, now declared in environment.yml.
One file carried in from the integration branch
This branch also contains scripts/evaluate_full_heldout.py, byte-identical to
the copy on agent/quality-fixes (sha256 3914f9f7c2899e4c...), so the add/add
merge resolves cleanly when the stack lands. It is here only so the quality table
above is reproducible from this branch instead of requiring the integration
branch. It is not part of the sparse-Adam change and can be dropped if you would

Refs #17. A dense Adam step touches all 161 floats of every gaussian on every
iteration, so its cost scales with N no matter how few gaussians the batch
actually rendered. Instrumenting a full run shows how wasteful that is here:
once densification reaches the 1M-point cap, the union of `radii > 0` over a
four-view batch covers only ~12% of gaussians, while the step itself takes
~19.8 ms of a ~200 ms iteration.

This adds a fused CUDA Adam step that skips rows outside the visibility mask,
behind an off-by-default `--sparse_adam`. Measured against torch's optimizer at
N=1M on an A6000: 2.3x faster at 100% visible (torch's foreach path makes
several passes over the state; this makes one) and 13.4x at 12% visible.

The arithmetic matches torch.optim.Adam's single-tensor path term for term,
including global-step bias correction, so an all-true mask reproduces the dense
update to float32 rounding. Upstream's kernel drops bias correction, which
makes it a different optimizer; keeping it means the flag is a pure speed
change. tests/test_sparse_adam.py covers that equivalence, that invisible
gaussians and their moments stay frozen, and the two fallbacks below.

Implementation notes:

- SparseGaussianAdam subclasses torch.optim.Adam and keeps its state layout, so
  GaussianModel's densification/pruning surgery on optimizer.state and existing
  checkpoints keep working.
- densify_and_prune runs before the step, so the mask can be stale; parameters
  whose leading dimension no longer matches fall back to a dense step (they are
  freshly cat-ed and carry no gradient, so it is a no-op either way).
- fetchPly builds positions as np.vstack([x, y, z]).T, leaving _xyz
  F-contiguous until the first densification cat. The optimizer relays such
  parameters out at construction, which is a pure layout change.
- The extension is compiled on first use and cached, so the flag costs nothing
  when off. It needs ninja, now declared in environment.yml.
