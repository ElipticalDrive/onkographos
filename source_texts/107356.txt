Summary
nanovdb::tools::cuda::PointsToGrid::countNodes builds the tree one level at a time. After each level it copies that level's node count to the host and blocks, then sizes the next level's buffers from it. For ValueOnIndex input, one voxelsToGrid call blocks the host six or seven times. On small inputs those waits dominate the build.
Every level's count is bounded by the number of input points. Intermediate buffers can therefore be sized without reading counts back, leaving one readback, before getBuffer, which needs exact counts for the grid buffer.
Motivation
fVDB rebuilds grids from voxel coordinates every training step in dynamic sparse-conv workloads (GridBatch.from_ijk → tools::cuda::voxelsToGrid). Measured on an RTX PRO 6000 (SM120), CUDA 13.0, B = 1:

At 848 voxels the GPU work is a few microseconds, so the build cost is sync and launch overhead. These totals include fVDB's wrapper (a joffsets host copy and a metadata readback). By code inspection, PointsToGrid accounts for six or seven of the host waits per grid. fVDB also calls voxelsToGrid once per grid in a batch, so the waits scale with batch size.
For comparison, FlexGEMM's hash-based sparse-conv neighbor build does one host sync in total and takes 0.13 ms at 848 voxels.

The serial path at line 715 also launches a voxel-key kernel and a radix sort per tile, so small inputs pay extra launches too.
Proposal
Size the per-level buffers (tile keys, voxel and leaf prefix sums, leaf and lower keys) by pointCount, which bounds every level's count. Keep the counts on the device.
Make the steps that consume a count work from the device copy. Scans and run-length encodes can run over the bounded range and ignore the tail. The lower-node count (DeviceSelect::Unique over leaf keys) needs a bounded or sentinel-padded input, or a small unique-count kernel.
Choose between segmented and serial voxel-key sort without the tile count, for example always segmented, or by pointCount.
Read {tiles, lower, leaves, voxels} back in one D2H before getBuffer, which needs exact counts to size and lay out the grid buffer.
Drop the wait at line 812, which appears redundant. Consider making the trailing sync in getHandle optional for callers whose buffers are stream-ordered.
The Point build path keeps its extra readbacks for the density bisection and the points-per-leaf limit; this proposal targets the voxel path.
Expected result
One host wait per voxelsToGrid call instead of six or seven.
Fewer launches for inputs with fewer than 32 tiles.
Temporary scratch grows toward pointCount-sized buffers at each level. The builder already allocates pointCount-sized key and index buffers, so peak memory should change little.
Follow-up
A batched voxelsToGrid, sorting keys prefixed by grid index once for the whole batch, would make the wait count independent of batch size. This mirrors the batch-capable TopologyBuilder in #2336.
