Found while reviewing #1271. extract_isosurface calls marching_cubes with the default gradient_direction='descent', and in scikit-image that flag flips the face winding (faces = np.fliplr(faces)), not the normals. The stored per-vertex normals are outward, as the demo intends — but the right-hand-rule geometric normal of every triangle then points inward.
Measured on skimage 0.26 with the demo's own extraction path (synthetic ball, spacing=(0.29, 0.26, 0.26)):
stored-normal radial alignment: +0.999 (outward — the existing test checks this, and it passes)
dot(geometric winding normal, stored normals): mean −0.999, 100% of faces negative
with gradient_direction='ascent': +0.999, and the stored normals stay outward (unchanged)
Render consequence: the demo leaves double_sided=True, so the projection applies no winding post-pass, and the fragment shader negates the stored normal on back faces (shader-glsl.ts:212, gl_FrontFacing ? N : -N). Viewed from outside, every exterior triangle is back-facing, so the outward normals are flipped inward: both isosurfaces render near the ambient floor (~0.26 shade where a facing fragment should be ~0.96) with the headlight gradient inverted (rims brighter than facing centers) — the one thing this reference demo exists to show off, rendered wrong. The new viewer icosphere fixture measures +0.99996 winding-vs-normal agreement, matching add_mesh's documented CCW contract; the demo is the odd one out.
Fix: pass gradient_direction='ascent' (verified: winding and normals then agree) or flip faces[:, ::-1]. Two collateral corrections while in there:
the demo and test docstrings attribute the outward orientation to 'descent' — descent only flips winding; the normals get their outward sense from the kernel's −∇V regardless, so the stated rationale for the flag is wrong either way;
no test checks winding-vs-normal consistency (the outward test checks normals alone, which is why this slipped) — a cross-product dot check like the measurement above would pin it.

Plan:
Pass gradient_direction="ascent" in the demo so the right-handed winding agrees with the outward normals (measured: dot(winding, stored) goes -0.999 → +0.999; stored normals stay outward either way).
Fix the demo/test docstrings that wrongly credit "descent" for the outward orientation — the flag only controls winding here.
Add a winding-vs-normal consistency check to the test (the current outward test looks at normals alone, which is why this slipped).
