Issue body actions
Impeller has no indirect draw support on any backend, and flutter_gpu's only draw entry points take element and instance counts from Dart. Draw parameters therefore have to round trip to the CPU, so GPU culling, GPU-side LOD selection, and any GPU-driven submission are not expressible.
For large scenes this is a higher ceiling than any per-draw constant factor. It is also the last major piece of the modern draw-submission model that flutter_gpu is missing.
How other HALs do it
Shape
Vulkan
vkCmdDrawIndirect / vkCmdDrawIndexedIndirect with drawCount + stride, plus vkCmdDrawIndirectCount for a GPU-supplied count
D3D12
ExecuteIndirect with a command signature, MaxCommandCount, optional count buffer
Metal
drawIndexedPrimitives:indirectBuffer:indirectBufferOffset:, single draw only. Indirect command buffers are the multi-draw analogue
OpenGL ES
glDrawElementsIndirect in 3.1. Multi-draw only in 3.2 or via extension
WebGPU
drawIndirect / drawIndexedIndirect, single draw. Multi-draw is still a proposal (gpuweb#5175)
SDL_GPU
SDL_DrawGPUPrimitivesIndirect(pass, buffer, offset, draw_count), multi-draw folded into the one entry point
Bevy
multi_draw_indirect{,_indexed,_count} over wgpu, batched into bins by a GPU preprocessing pass. Recently flipped to on by default
Unity
Graphics.RenderMeshIndirect and BatchDrawCommandIndirect for BatchRendererGroup. Multiple meshes handled by a mega-mesh plus per-command offsets
Filament
No indirect draw. Solves the same problem with hardware instancing and per-instance parameter arrays
Filament is worth noting as the counter-example. A lot of ground is coverable with instancing alone, which flutter_gpu already has.
The argument layout is already portable
The indirect argument struct is identical across Vulkan, D3D12, Metal, GLES, and WebGPU. Indexed is five uint32s (indexCount, instanceCount, firstIndex, baseVertex, baseInstance), non-indexed is four (vertexCount, instanceCount, firstVertex, firstInstance). So the buffer format needs no abstraction, and a compute shader that writes args is portable by construction.
Sketch
```
// Buffer contents are the standard 5-word indexed / 4-word non-indexed layout.
pass.drawIndirect(argsView);
pass.drawIndexedIndirect(argsView);
```
Vulkan's blanket buffer usage in allocator_vk.cc does not currently include eIndirectBuffer, so that has to be added.
Pitfalls
Multi-draw is not universal. Vulkan and D3D12 have it natively, Metal and GLES 3.1 do not. If drawCount is in the signature it needs an encode-side loop on those two. Worth deciding up front, since widening the signature later is breaking.
baseInstance is not free everywhere. ES 3.1 core requires it to be zero without EXT_base_instance, and WebGPU gates it behind indirect-first-instance. Either gate it on a capability or document the constraint.
Indirect count (vkCmdDrawIndirectCount and the D3D12 count buffer) is the piece that actually unlocks GPU culling without a readback, but it is Vulkan and D3D12 only. Better as a follow-up than as part of the first landing.
Do not validate the argument buffer
Worth stating explicitly, because it is where this feature can be meaningfully better than the same feature elsewhere. Dawn injects a compute dispatch per indirect buffer to bounds-check draw arguments, because untrusted content could otherwise read out of bounds. Measured cost is 412 indirect draws in separate buffers spending ~3ms on validation, roughly half the render pass, versus ~10us when consolidated into one buffer.
flutter_gpu's callers are trusted application code, so none of that applies. A bad argument buffer is the app's bug, the same as a bad index buffer is today.
