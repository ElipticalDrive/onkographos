Summary
Keep the RawVolume interface and use lazy 32-voxel chunks for volumes of 64 MiB or more. Smaller volumes keep the existing contiguous array.
Leave untouched chunks unallocated and represent uniform fills with a default voxel. Reads do not allocate chunks.
Add VolumeDataAccessor as discussed in VOXEL: reduce memory for large RawVolume instances #888: borrow the buffer for a full dense volume, otherwise copy the requested region without changing source storage.
Use the accessor for undo serialization and texture extraction. Texture snapshots include only the extraction region and a one-voxel halo.
Performance
Empty and uniformly filled 256^3 volumes use a 4 KiB chunk directory instead of a 64 MiB voxel array.
Full 256^3 chunk snapshots took 15.5-19.6 ms, compared with 96-131 ms for copying voxel by voxel. A 64^3 snapshot uses 1 MiB and took 0.10-0.13 ms.
Measured locally with GCC/WSL, three repetitions. The snapshot comparison does not measure undo compression speed.
Test plan
All 193 active voxel tests pass on Windows/MSVC and Linux/GCC; 3 existing tests remain disabled.
All 29 memento tests pass on both platforms.
All 11 accessor and texture extraction tests pass in a focused ASan/UBSan build with leak detection.
Added coverage for chunk boundaries, concurrent publication, voxel metadata, moves, copies and snapshot ownership.
Known limitations
Full sampler scans are slower than dense storage. Fully allocated cyclic moves also need temporary chunk payload.
clear() and fill() retain allocated chunks to preserve existing references.
Legacy voxels()/data() calls still materialize the source. Internal readers use storage-independent access.
The 64 MiB threshold is an initial choice and may need tuning based on review and further benchmarks.
Refs #888.
