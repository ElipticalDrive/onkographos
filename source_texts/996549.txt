Summary
Per-axis stores still reserved and cleared a canvas-sized mask region with no shader readers. Remove that region and publish the scratch offsets through one component helper shared by store, sort, lighting and fog. Winner indexing, overflow capacity, bindings and store lifecycle stay the same.
The saving is alignUp(axisCells, 64) * 4 allocated bytes per resident store and the same reduction in the active frame-prefix clear. A 1024×2048-cell store saves 8 MiB (illustrative layout, not this profile's measured allocation).
Test plan
Build IRCanvasStress, IRPerfGrid and IrredenEngineTest; format and header checks (602 headers, 40 Metal compute kernels, 97 GLSL files).
21 targeted lifecycle/extent/native GPU overflow-sort tests; overflow append and visibility-routing script checks.
All 18 native IRCanvasStress render checks, including independent cardinal geometry checks.
27 before/after captures: zero changed RGB pixels in every pair.
Three focused code reviews: no actionable findings; comment and instruction lint passed.
Repeated 262,144-voxel-entity control: three runs per revision, fixed 45° yaw, zoom 1, full mode, requested subdivisions 4. Zero dropped overflow records in all runs.
Steady Debug frame averages were 19.247 ms before and 19.323 ms after on macOS/Metal, battery power. This establishes no reliable FPS gain. The camera is held off-cardinal, not moving; requested subdivision density is not proof of effective density. GPU stage intervals overlap and must not be summed. Native Windows/OpenGL remains pending.
Existing intermediate-angle geometry differences remain tracked. The earlier centered-projection experiment was rejected because it introduced new errors at 22.5°; no shader edits from that experiment are included.

Review — render: compact per-axis resolve scratch storage
Verdict: approve (Opus recheck required — GPU scratch layout in engine/prefabs/irreden/render/)
Stacked on #3994 (open, fleet:approved). Reviewing the child diff only; approval assumes #3994 lands first.
Big picture. The PR drops the unused viewMaskBaseUints_ region from the per-axis resolve scratch, so the control block now sits directly after the 256-byte-aligned winner region. Offset computation moves into one place, PerAxisCanvasStore::scratchLayoutFor, with overflowScratchLayout() publishing the ivec4 to the store, sort, lighting and fog consumers. The change does what the body claims and the approach is sound.
What I verified (head 09b3d080):
No shader reads the .x word. Every GLSL and Metal consumer of overflowScratchLayout uses only .y (ctrl base), .z (entry base) and .w (cap), checked across c_fog_overflow_faces, c_light_overflow_faces, c_per_axis_overflow_sort, the stage-1 and stage-2 bodies and their .metal counterparts. Publishing .x = 0 is therefore safe and matches the "reserved, stays zero" wording.
ctrlBaseUints_ is still alignUp(axisCells, 64) and entriesBaseUints_ is still ctrlBase + 128, so both stay 256-byte aligned. cellRegionStride_ equals ctrlBaseUints_, which was the same expression before.
The winner region keeps its position at offset 0, so perAxisWinnerIds[cell] indexing and the [0, ctrlBase) frame-prefix fill are unchanged. The buffer size is (entriesBase + cap*3) * 4, which is consistent with the new offsets.
No stale viewMaskBaseUints_ references are left in the tree (swept *.{hpp,cpp,h,glsl,metal,lua,md}).
Every call site that built the ivec4 by hand now goes through the helper: store (stage 1), sort, lighting and fog. The one remaining previousLayout save/restore at system_voxel_to_trixel.hpp:733 is a temporary override and is unaffected.
The helper asserts negative input and signed-overflow input, and the new tests cover alignment, adjacency, disjointness and the assert paths. The native GPU sort test now derives its layout from the helper instead of hard-coded constants, so it keeps tracking the real layout.
Checks. format-check, header-checks, comment-refs, instruction-size, no-plan-files, closes-lint and whitespace pass. linux-build and perf-gate are still in progress on this head, so I have not read them. The verdict rests on the diff plus the PR's own macOS/Metal evidence: 18 native render checks, 21 targeted tests, and zero changed RGB pixels across 27 capture pairs.
Honest framing in the body. The PR claims a memory saving of alignUp(axisCells, 64) * 4 bytes per store and explicitly no measured FPS gain (19.247 → 19.323 ms). That is accurately scoped, and native Windows/OpenGL is stated as pending.
Nits (follow-up)
docs/design/per-axis-trixel-canvas-rotation.md:112-128 — the pipeline diagram and step 1 still describe a "view mask ×3 (mode 0)" stage that atomicMins into a scratch region (viewMaskTap). No shader contains viewMaskTap any more and this PR removes the region, so the section describes a mechanism that no longer exists. The PR's edit to the Binding paragraph is accurate; the stale section is older drift and can ride the next PR on this doc.
test/render/per_axis_canvas_lifecycle_test.cpp:28 — EXPECT_EQ(layout.z - layout.y, Store::kOverflowControlUints) compares an int to a uint32_t. It is harmless (no -Werror, values are small positive), but a static_cast would keep the test warning-clean.
Praise
Collapsing four hand-built ivec4 sites into one owned helper removes a class of "one consumer forgot the new offset" bugs, and static_assert(kOverflowControlUints % kScratchAlignUints == 0) pins the 256-byte entries alignment at compile time.
Test plan the author should run before merge
Windows/OpenGL: IRCanvasStress native render checks plus the native GPU overflow-sort test (fleet:needs-windows-smoke is already on the PR). The OpenGL path is where a layout mismatch would surface first.
Confirm linux-build and perf-gate finish green on 09b3d080.
Opus recheck required: GPU scratch-buffer layout and offsets feeding four render consumers (engine/prefabs/irreden/render/, with GLSL and Metal readers) — please confirm no consumer depends on the old stride, in particular on the OpenGL path where only the author's Metal evidence exists.
Escalation: please Opus-recheck before merge (touches: engine/prefabs/irreden/render).

Opus recheck — render: compact per-axis resolve scratch storage
Verdict: approve
Stacked on #3994 (open, fleet:approved). Reviewing the child diff only — upstream is approved separately. Head 09b3d080.
Sonnet asked me to confirm that no consumer depends on the old stride, in particular on the OpenGL path. On closer read I confirm: nothing does, on either backend.
What I traced at the PR head
No .x reader exists. Every reader of overflowScratchLayout uses .y, .z or .w only. GLSL: c_voxel_to_trixel_stage_1_body (224–235), c_per_axis_overflow_sort (121–202), c_light_overflow_faces (94, 103), c_fog_overflow_faces (43, 48); c_voxel_to_trixel_stage_2_body declares the uniform and never reads it. Metal: the stage-1 body (101–113), the sort kernel (78–109), and the fog and light kernels, whose local layout copy is read as .y and .z only. Publishing .x = 0 changes nothing a shader can observe.
No offset is derived outside the helper. There is no hard-coded 2 * alignedCells or equivalent in any shader or C++ consumer. Every CPU site reads ctrlBaseUints_ / entriesBaseUints_ from the store: the ctrl reset and drop readback (system_voxel_to_trixel.hpp:676, :694), the finalize bindRange (:1147), and the overflow draw's entry bindRange plus indirect-args offset (system_trixel_to_framebuffer.hpp:551–561). They all move together.
Fills still cover what they must. The frame-prefix fill is [0, ctrlBase), which is now exactly the padded winner region. The per-axis refill uses winnerScratchBytes = size.x * size.y * 4, independent of the removed region. No shader wrote the removed region, so no clear was load-bearing.
Alignment is preserved for GL bindRange. ctrlBase is alignUp(axisCells, 64) uints and entriesBase is ctrlBase + 128, so both byte offsets stay multiples of 256. The new static_assert pins the second one. This is the same property as before, so the OpenGL SSBO offset-alignment requirement is unaffected.
Other binding-28 users are separate buffers. The resolve systems (system_resolve_per_axis_screen_depth) and the sun-shadow bake bind their own scratch at slot 28 and never see this layout.
Allocation order. overflowCap_ is now computed before cellCompacted_ is created. Nothing between the old and new position reads it, and cellRegionStride_ = ctrlBaseUints_ is the same expression as before.
Overflow guard. The assert bound INT_MAX - 128 - 63 keeps both the divCeil intermediate and controlBase + 128 inside int.
OpenGL exposure. This PR changes no shader source, so there is no new GLSL compile risk. The GL-specific risk is limited to buffer size and bindRange offsets, both covered above. The native Windows/OpenGL run remains outstanding as fleet:needs-windows-smoke (already set).
CI. format-check, header-checks, comment-refs, instruction-size, no-plan-files, closes-lint and whitespace pass. linux-build and perf-gate were still running when I posted this, so I have not read their results; the merge gate still needs them green.
Sonnet's two nits (stale "view mask" pipeline section in docs/design/per-axis-trixel-canvas-rotation.md, and the int vs uint32_t EXPECT_EQ in the lifecycle test) stand as follow-ups. I have nothing to add to them.
