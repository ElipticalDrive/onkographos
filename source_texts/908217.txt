Problem
Two bugs surfaced when trying to read real-world .nvdb files in fVDB:
Wrong-type dispatch for multi-grid handles. detail::io::loadOneGrid calls handle.gridType() and handle.gridMetaData() without the gridId argument, so every grid in a multi-grid GridHandle is dispatched as if it were grid 0. Loading e.g. {Float, Float, Vec3f} therefore fails at grid 2 with Grid has type Vec3f, but expected float.
Cryptic concat error for heterogeneous per-voxel shapes. Even when dispatch is correct, JaggedTensor packs per-grid data along dim 0 via torch::cat, which requires matching dtype and matching trailing sizes. A file that contains a Float grid at [N, 1] alongside a Vec3f grid at [M, 3] bubbles up as Sizes of tensors must match except in dimension 0. Expected size 1 but got size 3 for tensor number 2... with no hint at which grids are actually incompatible or how to load them.
A third papercut: .nvdb files saved with ZIP compression fail to open because NANOVDB_USE_ZIP was never set at build time.
What changed
C++ (src/fvdb)
detail/io/LoadNanovdb.cpp — loadOneGrid: thread gridId through every handle.gridType(...) / handle.gridMetaData(...) call so per-grid dispatch is actually per-grid.
detail/io/LoadNanovdb.cpp — new validateTrailingShapeAndDtype helper: runs in fromNVDB before JaggedTensor construction and raises a TORCH_CHECK_VALUE that names both the reference grid and the offending grid, prints their shapes/dtypes, and tells the caller to use name= / index= / load_nanovdb_single to load them one at a time. No perf impact on the happy path (data.size() <= 1 early-out).
New NanoVDBGridMetadata struct (src/fvdb/NanoVDBGridMetadata.h): POD with name, type, gridClass, voxelCount, voxelSize, indexBBoxMin, indexBBoxMax.
New fvdb::read_metadata(path) (src/fvdb/FVDB.{h,cpp}): public C++ entry point backed by a new detail::io::readNVDBMetaData wrapping nanovdb::io::readGridMetaData. File-header-only; no voxel data is materialized.
Python bindings (src/python/Bindings.cpp)
Bound NanoVDBGridMetadata as a Python class with read-only accessors and a compact __repr__.
Bound fvdb.read_metadata as a free function taking path.
Python API (fvdb/functional)
_io.py: added read_nanovdb_metadata(path) and a grid_names_in_nanovdb(path) convenience wrapper; both with docstrings and a short usage example.
__init__.py: added both names to __all__. Reordered the existing from ._xxx import ... blocks into alphabetical order while I was in there.
Build (src/CMakeLists.txt)
find_package(ZLIB REQUIRED), -DNANOVDB_USE_ZIP, and ZLIB::ZLIB in target_link_libraries so NanoVDB's ZIP-compressed .nvdb reader is actually compiled in.
Tests (tests/unit)
__init__.py: bump set_testing_git_tag to the fvdb-test-data commit that ships the new io/mixed_types.nvdb fixture (46e7bd4...).
test_io.py: new TestLoadMixedTypeNanovdb class driven by a single _MIXED_TYPES_GRIDS truth table covering all four grids in the fixture (density float, pressure double, label int32, velocity Vec3f). 19 tests total covering:
read_nanovdb_metadata enumerates names / types / voxel counts.
grid_names_in_nanovdb returns the right names.
Loading the whole file without a selector raises ValueError, the message is lowercase-matched against "mixed value type", references at least one grid by name, and contains an actionable hint (name= / index= / load_nanovdb_single).
By-name load for each of the 4 types on CPU and CUDA, with round-trip value verification.
By-index load for each of the 4 types on CPU and CUDA.

```
Improve behavior and ergonomics of reading .nvdb files, especially when a
single file contains grids of multiple value types.

Correctness:
- LoadNanovdb.cpp: loadOneGrid() was calling handle.gridMetaData() and
  handle.gridType() without the gridId, so every grid in a multi-grid
  GridHandle was dispatched using grid 0's type. Files with, e.g., a Float
  grid at index 0 and a Vec3f grid at index 2 would fail with a misleading
  "Grid has type Vec3f, but expected float" error. Pass gridId through to
  gridMetaData(gridId) and gridType(gridId) in every relevant call site,
  including the TensorGrid branch and the default error path.

Error reporting:
- fvdb::JaggedTensor packs per-grid data tensors via torch::cat along dim 0,
  which requires matching dtype and matching trailing shape. Grids with
  heterogeneous value types (e.g. a Float grid [N, 1] next to a Vec3f grid
  [M, 3]) therefore cannot share a single JaggedTensor. Previously this
  surfaced as a cryptic torch::cat size-mismatch error deep in tensor ops.
  Add validateTrailingShapeAndDtype() in both fromNVDB() overloads that
  checks shape/dtype uniformity up front and raises a TORCH_CHECK_VALUE
  naming the specific offending grids and suggesting the name=/index=
  selectors or load_nanovdb_single as workarounds.

New metadata-only API:
- Add fvdb::NanoVDBGridMetadata (new header src/fvdb/NanoVDBGridMetadata.h)
  holding name, type string, grid-class string, voxel count, voxel size,
  and index bbox min/max.
- Add fvdb::read_metadata(path) / detail::io::readNVDBMetaData(path), which
  wraps nanovdb::io::readGridMetaData and only reads file headers (no voxel
  data). This lets callers enumerate a .nvdb file without paying the cost
  of a full load and is the supported way to inspect files with mixed value
  types before choosing which grids to load individually.
- Bindings.cpp: bind NanoVDBGridMetadata (with a __repr__) and expose
  read_metadata as _fvdb_cpp.read_metadata.
- fvdb.functional: add read_nanovdb_metadata(path) and the convenience
  wrapper grid_names_in_nanovdb(path), and export both from
  fvdb.functional.__init__.

Also reorders the import blocks in fvdb/functional/__init__.py
alphabetically while touching the file.
```

Re-reviewed in detail. The two bug fixes (per-grid type dispatch and the actionable mixed-type error) are clearly correct and well-tested for the load path; the metadata API is a clean addition.
A few things to address before merge — comments are inline. Summary by severity:
Blockers
fvdb/functional/_io.py:17 — TYPE_CHECKING import points to a non-existent module; static type-check / IDE tooling will fail to resolve NanoVDBGridMetadata.
fvdb/_fvdb_cpp.pyi — new bindings (NanoVDBGridMetadata, read_metadata) are not added to the type stubs.
Doc bugs that will mislead callers
src/fvdb/NanoVDBGridMetadata.h:18 — example grid_class strings ("LS", "TensorGrid") don't match what nanovdb::toStr(GridClass) actually returns ("SDF", "TENSOR").
Structural / readability
src/fvdb/detail/io/LoadNanovdb.cpp — validateTrailingShapeAndDtype runs after mergeGrids + makeGridBatchData; hoisting it before saves all that work on the error path.
src/python/Bindings.cpp — def_property_readonly lambdas are unnecessary; pybind11/stl.h already auto-converts std::array<T, N> to a Python tuple via def_readonly.
fvdb/functional/_io.py — new metadata functions sit under the # Save section divider.
Test coverage gaps
grid_class / voxel_size / index_bbox_* are exposed but not asserted (and would have caught the grid_class doc bug above).
CUDA-parameterized loads don't assert data.jdata.device.type, so a silent device= regression would pass.
The by-index load test only checks shape/dtype, not the round-tripped value — the by-name test does, and the same proof matters for the index path.
Adjacent (not blocking this PR)
Filed #642 for a pre-existing latent bug in nanovdbTensorGridToFVDBGrid (always reads blindMetaData(0) inside the loop). Not introduced here, but the per-grid dispatch fix in this PR makes the bug more reachable for multi-grid TensorGrid files.

```
## Summary

`LoadNanovdb.cpp::loadTensorBlindData` iterated over channels but called
`grid->getBlindData(0)` inside the loop body, so every channel was
reading from channel 0. Same bug at four sites (L210, L236, L366, L370).
Replace `(0)` with `(i)` at each call site.

## Why this matters

Reporter caught this while reviewing the recently-merged PR #641 and
dropped the exact line numbers. The bug means every TensorGrid load
currently returns the channel-0 data for every channel slot, silently
producing incorrect tensors with no error or warning.

## Changes

- `src/fvdb/detail/io/LoadNanovdb.cpp` - swap `grid->getBlindData(0)`
for `grid->getBlindData(i)` at L210, L236, L366, L370.

## Testing

Existing TensorGrid load tests cover this; they pass with the fix on
HEAD 7e8213e.
```
