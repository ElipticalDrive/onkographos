SPLAT-FUSED: path-traced fusion of splats + LiDAR + terrain
This branch delivers the end-to-end render_fused path and a professional, deterministic map-sheet example that exercises it with real terrain data.
The real purpose
forge3d.splat.render_fused renders 3D Gaussian splats, a LiDAR point cloud and an exact terrain heightfield in a single path-traced pass with unified occlusion — one ReSTIR integrator, one transmittance T = T_splat × T_lidar × T_terrain. That is the "sensor + terrain fusion" primitive the engine was missing: you can drape derived/incoming sensor data (a 3DGS capture, a COPC LiDAR scan) over a real DEM and get correct mutual shadowing and occlusion, path-traced rather than rasterized.
Until now there was no end-to-end exercise of that path with real data, no HDRI environment map, and the background sky was a flat band ending in a hard horizon silhouette. This PR closes those gaps and ships a regression-locked test example (examples/splat_fused_map.py) that proves the whole thing works and is byte-identical across reruns.
Result
--dem fuji, hero view, 1280×896 @ 128 spp: hypsometric terrain, a violet splat block on the summit shoulder and a terracotta LiDAR swath in the foreground valley, under an HDRI sky (Poly Haven CC0) with aerial-perspective fog. Full sheet: title, fused-layers legend with hit counts, scene/atmosphere/camera/render readout, scale bar, north arrow, optional AOV insets.
What's in this PR
Engine (src/ + python/forge3d/)
env_map + env_rotation_deg on render_fused / render_fused_sequence: a pre-loaded equirect HDRI replaces the Hosek-Wilkie bake (loader box-averages to ≤1024 texels, rotates about +y, normalizes to median upper-hemisphere luminance, clamps at 12× so the HDRI's sun reads as a bright blob). No shader change needed — the kernel samples whatever equirect is uploaded.
Real aerial perspective: fusion_media_along (closed-form height fog) refactored out of fusion_media_transmittance (bit-identical); a FUSED_TERRAIN_EDITS anchor composites L = L·T + env·(1−T) at the primary hit. At density 0 the transmittance is exactly 1, and the fix below makes that path byte-identical to the base line rather than merely close to it (the original edit re-associated the radiance sum, which differs by 1 ULP in f32 for a large share of pixels).
In-memory point arrays (point_positions / point_colors) so a cloud needs no file.
Certificate records fused.env_map alongside fused.fog_*; the fix below changes the recorded identity from the HDRI's absolute path to its basename plus the SHA256 of its bytes, and adds the missing fused.env_rotation_deg.
Example (examples/splat_fused_map.py) — the end-to-end test harness
HDRI sky (--hdr auto|none|PATH, cached CC0 Poly Haven 2k) + aerial fog (--fog, --fog-falloff), gated off on the plan view; hero lighting moved golden-hour → lit daytime.
--dem digitizes all three layers from one DEM (heightfield, a splat block on the summit shoulder, a LiDAR swath in the foreground valley — deliberately separated so they read as distinct sensors).
Camera presets, orbit overrides, contour overlay on plan views, tiling, AOV insets, a sidecar report.json.
Professional sheet: fused-layers legend, scene/atmosphere/camera/render readout, scale bar, north arrow; content-aware canvas so the readout never clips.
Docs — docs/splat-fused.md "Map-sheet example" section, CHANGELOG entries.
How to try
```
python examples/splat_fused_map.py                # offline fixture: ridge + splats + COPC swath
python examples/splat_fused_map.py --dem fuji     # real DEM, full fusion story
python examples/splat_fused_map.py --dem fuji --view top --aovs   # north-up hypsometric map
```
Closes the "no HDRI" limitation noted in the feature documentation.
The fixes on top of the feature
The feature above is worth having, but the branch did not compile its own acceptance test, and two
of its claims about its own output were not true. Those are fixed here, and each fix is locked with
a test.
1. The branch's acceptance test did not compile (blocker)
Adding env_map to FusedRenderDesc left the two FusedRenderDesc initializers in the acceptance test without it:
```
error[E0063]: missing field `env_map` in initializer of `FusedRenderDesc<'_>`
   --> tests/test_splat_fusion_occlusion.rs:222:5
   --> tests/test_splat_fusion_occlusion.rs:1406:24
```
Both now pass env_map: None — the analytic Hosek-Wilkie sky the fixture already used — so the rendered output is unchanged. The suite goes from does not compile to 17/17 passing.
2. The signed certificate leaked a machine-specific path, and omitted the rotation (major)
fused.env_map recorded the HDRI's absolute path, which puts the machine's directory layout into the signed payload, and env_rotation_deg was not recorded at all — so two renders of the same file at different rotations had identical signed inputs even though they produced different pixels.
The recorded identity is now the file's basename plus the SHA256 of its bytes: the basename names the asset, the hash pins its content (two different files that share a name do not collide), and neither leaks a path. The rotation is recorded next to it, and the sequence entry point now records the same scene-defining inputs as the single-view one (kappa, lidar radius, opacity, surfels, BRDF) instead of a subset.
3. "Bit for bit at fog density 0" was false (major)
#253's description claims the aerial-perspective edit leaves the base line bit-identical at fog density 0. It did not. Folding the media transmittance into the radiance sum re-associates
```
frame_radiance + sun + ibl   ->   frame_radiance + (sun + ibl)
```
which is equal in exact arithmetic but differs by 1 ULP in f32 for a large share of pixels — small enough for the tolerance-based golden not to notice, large enough to break byte identity. The edit now keeps the base line's own statement verbatim on the branch a zero density takes, and two source-level tests pin it: the base line's statement appears exactly once, the re-associated sum exists only inside the fog branch, and the media transmittance short-circuits to exactly 1.0 without fog.
4. The sheet's own footer claimed a guarantee nothing tested (minor)
The sheet says "seed N reproduces this sheet byte-for-byte", but only the beauty was hashed across reruns — a sheet that drifted would have made the claim false while the test still passed. The sheet PNG now gets the same sha256 rerun check. It passes.
Also: --hdr-rotation did not state the sign it uses, so a positive angle meant two different things to a reader (it now names the convention it follows — the sun's azimuth: 0° = +x, 90° = +z; world north is −z), and a missing --hdr file raised a bare traceback instead of the clean error: the DEM path prints.

The paging case is a flake, not a fix
paging_policies_respect_the_residency_pool is timing-dependent and unchanged by this branch. It passed 17/17 on the final head and has also failed here; that is the flake, and this PR does not fix it. Evidence:
A/B against the branch's own code. Reverting the fog edit (item 3) reproduces the identical failure 3/3 times, and the branch's render_fused.rs / stream.rs changes are env-map plumbing and a purely additive PointArraySource — neither touches the paging path.
The root cause is a race between the render and the asynchronous page loader, not a defect in either. The render's 24 frames finish before the loader has delivered the far-field pages they asked for. Instrumenting the pool shows the kernel requests ~46 distinct far-field pages on the first service, and in_flight then climbs to 50 and never drains before the render ends — so the pool is never filled enough to evict or defer. The loader's backlog is a function of this machine's CPU speed, which is why the same test passed on the reference machine (the 2026-10-03 evidence records it green there).
The same code passes with a longer render. Raising the case from 24 to 240 frames lets the loader catch up: loads 10 → 19, deferred_pages 0 → 70, and the assertion passes.
So the assertion is currently a statement about CPU speed as much as about the pool. The two options I see are to give the loader a bounded chance to settle before the assertion (the pool's service/pending_pages are public, but the pool lives inside the renderer, so this needs a small API addition), or to assert on the deterministic property instead — the working set the render demanded exceeded the pool. I have not changed that test: it is your acceptance gate, its formulation is tracked separately, and it does not block this PR. The table above reports the head's actual result rather than promising a fix.

Five more fixes, from the audit and the bug list. Each is a separate commit, and the two that could be checked are checked.
1. The signed certificate did not identify the render. It recorded the scene — page count, primitive count, extinction, LiDAR radius — but not the render: no frame size, no camera, no sun, no exposure, and on the sequence path no seed at all. Two different images from one scene therefore carried the same signed inputs. Both paths now record the frame size, the tile, the sky, and the camera/sun/exposure/seed of every view (fused.view0.cam_origin, fused.view1.seed, … for a sequence; unprefixed for the single view). The test asserts the property rather than the format: change the width, the camera, the sun, the exposure or the seed and the recorded inputs must change.
2. The HDRI loader dropped the Radiance Y orientation. The resolution line says which way the scanlines run — -Y top to bottom, +Y bottom to top — and the parser read the two numbers and threw the sign away, so a +Y file came out upside down. For an equirect environment that is an inverted sky. The sign is now read, +Y rows are flipped back, and a line with neither sign is refused rather than guessed at.
3. The DEM download was trusted on size alone. The HDRI preset was md5-checked on every cache hit; the DEM was not, so a truncated or corrupted download rendered as a wrong terrain, silently. The LFS pointer carries the SHA256 of the real bytes, so the download is checked against it, a cached download is checked before it is reused, a mismatching cache is discarded and re-fetched, a partial download is removed instead of being left to look like a cache hit, and a pointer without a hash is refused.
4. The fly-through rebuilt the scene N times. It called render_fused per frame, so the scene was rebuilt, every page re-streamed and the pipeline recompiled N times. It is now one render_fused_sequence call: one scene, one residency pool, one compiled kernel, N views. The frames are unchanged — I rendered the fly-through both ways and compared every frame's pixels: identical. The sun and the exposure moved into each FusedView; the sky, environment, fog and LiDAR radius stay shared.
5. Two uncalled accessors deleted. FusedGpu::pending_pages and FusedGpu::resident_slot had no callers anywhere. Zero-caller structure is deleted rather than kept for a future that may never arrive; if the open paging item needs one, it writes the API it needs.
Also: VIEW_PRESETS["low"] and "hero" share their angles and differ in the framing around them, which the table did not say; and --hdr-rotation now says what it is for — the captured sky's sun sits where the capture put it, so the rotation is how you line the visible disc up with the analytic sun's shadows. I did not hard-code a default rotation for it: the capture's sun azimuth is not a value I can verify from here, and a wrong constant is worse than a documented knob.
