Objective
Allow GPU-driven rendering with occlusion culling on WebGPU devices that lack immediates or expose fewer than 12 storage textures per shader stage.
Solution
Add a dynamic uniform buffer fallback for immediates. Preserve the existing immediates path on devices that support it, and use a dynamic uniform buffer (UBO) otherwise. This extends device compatibility while keeping the existing behavior unchanged on devices with immediates support.
Add depth pyramid generation with one dispatch per mip when fewer than 12 storage textures are available, preserving SPD on supported devices. Paths are selected during initialization. The existing requirement for 10 storage buffers per shader stage remains unchanged.
Fix WebGPU WGSL validation errors in the mesh preprocessing shader, mesh_preprocess.wgsl, caused by infinite constants and atomics in read-only storage buffers.
Testing
Tested on configurations supporting the original rendering path and on configurations requiring the uniform buffer and depth pyramid fallbacks.
Native and wasm32 Cargo checks passed.
Local Metal checks compared fallback mip values against a CPU reference, covering odd and rectangular sizes and MSAA ×4.
To reproduce, enable DepthPrepass and OcclusionCulling on a Camera3d. Test devices with fewer than 12 storage textures and devices supporting the original SPD path. Both require at least 10 storage buffers per stage.

Overall, this looks good! Great work on enabling GPU-driven rendering for WebGPU.
A couple of important things before we move forward:
Please check the README for our branching and tagging workflow. This PR should not be merged directly. Instead, we need to create a separate branch and tag it according to the documented process.
We should definitely open an upstream PR in bevy. We are not bevy experts, and it's important that these changes are reviewed by its maintainers. More importantly, we want these changes upstream so that bevy maintainers can maintain the immediates, fallbacks, and related functionality going forward.
I believe enabling GPU-driven rendering on webgpu would be a welcome improvement for bevy. However, the maintainers may suggest significant architectural or implementation changes, potentially requiring us to rework parts of the current solution.
That's why I think getting upstream feedback is essential before we commit to this implementation.

It's worth noting that this should be used with care, as memory usage scales with the constant. For example, a value of 1_000_000 would require a 256 MB buffer, with 252 MB wasted.
