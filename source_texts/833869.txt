Review — C1b, scoped to eviction identity
Re-ran everything on c1b-one-lru-rule @ 93a89156 against origin/develop cdb5c488. No blocking findings; 2 low; 1 note. The load-bearing question is answered below first.
Eviction identity — VERDICT: EXACT, both call sites
I lined lru_victim up against both deleted scans clause by clause, including the edge cases the PR body does not claim.
route_lru (develop reader.rs:957-972) → lru_victim: behaviour-identical, including the sentinel edge.
The old scan carried a sentinel the new one does not: best_used initialised to u16::MAX, against a used field that can legitimately reach u16::MAX — touch() rebases only when tick == u16::MAX on entry, so the call that finds tick == u16::MAX - 1 increments to u16::MAX and stamps a live slot with it. So the sentinel is collidable in practice, not just in theory. It is nonetheless benign, and I checked why rather than assuming: the collision only bites when the minimum live stamp is u16::MAX, i.e. every live slot is tied at u16::MAX, and then the old code's untouched best = 0 is already the correct lowest-index tie answer. Every other input updates best on the first slot. So old and new agree on every reachable input; Option<S> removes a latent sentinel rather than changing an outcome. Ties: both use strict <, so first-minimum-wins → lowest index. Empty: both return i on the first empty in slot order.
TileCache::reserve's closure (develop cache.rs:99-108) → lru_victim: behaviour-identical.
The old shape is two passes — keys.iter().position(|&k| k == EMPTY), then, only on None, a 1..N scan seeded at victim = 0. The new shape is one pass that early-returns. Same answer in both clauses: position yields the first empty by index, and the fused loop returns at the first empty by index; the seeded 1..N scan with strict < is first-minimum-wins, identical to the generic's. The fused pass also tracks a running minimum over slots preceding an empty one, which the old code never computed — dead, because the empty clause short-circuits before it is read.
The empty sentinel is not the same in the two callers, and that is the right outcome. RouteSlot.tag == 0 is a reserved value in an index + 1 key space; TileCache's EMPTY is file offset 0, unusable because the header sits there. Two different key domains that happen to both spell empty as zero. The generic takes a bool the caller computes, so neither sentinel crosses the seam and the coincidence is not load-bearing — the right call. Worth stating explicitly since a key == 0 signature would have coupled them for free and looked equally clean.
Tick rebase through the generic — the test's claim holds, and cannot fail.
touch()'s rebase assigns each live slot rank = 1 + |{live j : used[j] < used[i]}|. Distinct live stamps → 1..live, order preserved. Tied live stamps → equal ranks, and lru_victim's strict < resolves equal ranks to the lowest index — the same slot the tied pre-rebase stamps would have selected. So the rebase is order-preserving through the generic in both the distinct and the tied case, which is the part the assertion does not reach. Dead slots (tag == 0) keep a stale used across the rebase's continue and across clear(), but the empty clause short-circuits before any stamp is compared, so the staleness stays unreachable — unchanged from develop either way.
lru_clock_rebases_without_changing_eviction_order is fully deterministic (tick is set to u16::MAX, not reached), so it cannot flake. One honest limitation: it slices slots[..2] with both slots live, so its lru_victim assertion exercises only the lowest-stamp clause — the empty clause and the all-equal tie are covered by the new obc-formats unit test instead, which is the right split.
Coverage sanity. The four eviction golden rows (corridor/thin/{all,water}/full-walk, corridor/sparse/{all,water}/warm) do pin RouteCache's eviction path, and they are unmoved. TileCache has no counter gate, as the PR says — its cover is eviction_takes_the_least_recently_used_slot, which is a real property test, and the identity argument above is exhaustive over the two clauses, so I do not think the missing counter is load-bearing for this change.
