What changed
Adds a Marching Cubes render mode to Particle-Viewer using GLSL 4.3 compute shaders. Particles contribute to a 3D density field voxel grid; isosurface triangles are extracted on the GPU and rendered with Phong shading. The mode is gated on GL 4.3 compute shader availability and exposed through the existing Controller Panel.
Why
Closes #124. Spheres cannot convey the shape of dense particle clouds from arbitrary camera angles. Marching Cubes produces a geometrically accurate 3D isosurface with correct silhouettes suitable for close-up inspection and high-quality recording.
Acceptance criteria
AC1: GL 4.3+ -- select MC from sub-panel, lit 3D mesh replaces sphere rendering
AC2: GL <4.3 -- MC greyed with tooltip "Requires OpenGL 4.3 compute shaders"; M key skips MC
AC3: Camera orbit does not trigger mesh recompute (verified by static code trace: all markDirty() call sites in viewer_app.cpp are AC-specific; Camera class has zero reference to MCRenderer)
AC4: Live mode updates mesh on new timestep; Freeze mode holds the last mesh
AC5: Grid Resolution/Iso-value/Influence Radius changes trigger recompute and persist to window.cfg (round-trip tested in WindowConfigTests::SaveAndLoad_MarchingCubesParams_RoundTripsAllFourKeys)
AC6: Insufficient VRAM -- 256^3 greyed, auto-downgraded to 128^3, VRAM notification shown
AC7: Screenshots and recordings capture MC output; M during recording shows a non-recording notification (not captured in output)
AC8: VR test (MarchingCubesVRTest) uses 64-particle 4x4x4 grid fixture and auto-skips on GL < 4.3; baseline mc_64_grid.png requires a GL 4.3 machine to generate and commit (not available on dev machine)
AC9: Unit tests for RGB color blending math (MCColorBlendingTests) pass without GL context
AC10: Manual check required -- run in Spheres mode before and after this PR and confirm no frame-time regression. The MC pipeline allocates GPU resources only when GL 4.3 is available and is unreachable in Spheres mode; no Spheres-path code was changed.
AC11: Interior voxels where all 8 density corners exceed iso_value produce case index 255; edge_table[255] = 0 emits zero triangles. GL_DEPTH_TEST and GL_CULL_FACE (managed by MCRenderer::render()) occlude back geometry.

Design decisions
GPU-side Marching Cubes: density field and cube extraction both run as compute shaders (density_field.comp, marching_cubes.comp). Avoids CPU readback latency; mesh SSBO drives the draw call directly.
Live/Freeze toggle: exposes the recompute trigger explicitly rather than always-live or always-freeze. Default is Live for immediate feedback on first use.
GL_CULL_FACE managed by MCRenderer: render() enables and restores GL_CULL_FACE + GL_DEPTH_TEST internally. The VR test SetUp does not duplicate these -- the internal management is the authoritative path (verified by Tester amigo re-review).
256^3 VRAM gate: resolveGridResolution() uses GL_GPU_MEMORY_INFO_CURRENT_AVAILABLE_VIDMEM_NVX (NVIDIA) or total VRAM estimation; downgrades to 128^3 when < 280 MB available. The mc_256_available flag drives both the UI disable and the A-button confirm guard.

fix(rendering): request GL 4.3 context and fix MCTables SSBO on NVIDIA
…
c8bfa5e
```
Two bugs prevented Marching Cubes from working on NVIDIA hardware:

1. SDL3Context requested GL 4.1 (macOS cap), so GLAD_GL_VERSION_4_3 was 0
   on NVIDIA GL 4.6 hardware. MC was always shown as unavailable.
   Fix: try GL 4.3 context first on non-Apple platforms; fall back to 4.1.

2. MCTables was a std140 UBO. std140 pads each int to 16 bytes: the block
   is 69,632 bytes, exceeding GL_MAX_UNIFORM_BLOCK_SIZE (65,536 on NVIDIA).
   marching_cubes.comp failed to link, producing 0 vertices (blank render).
   Even if it had linked, the CPU uploads compact ints (4-byte stride) but
   std140 reads at 16-byte stride, so all MC table lookups returned garbage.
   Fix: change MCTables to std430 SSBO (tight packing, no size limit).

Also: ComputeShader now zeroes program_ on link failure so callers can
detect the error via program() == 0.

MC VR test uses a 5% diff ratio (vs global 0.01%) because atomic-counter
non-determinism changes triangle draw order between runs, causing ~2-3%
speckled pixel differences at co-planar shared edges.

Adds:
- SDL3ContextVersionTest: asserts GLAD_GL_VERSION_4_3 != 0 on NVIDIA
- MCRendererComputeTest: asserts vertex_count > 0 after MC pipeline runs
- baselines/mc_64_grid.png: first correct MC baseline (red rounded cube)
```

```
…quared-distance space

Replace length() (sqrt = SFU instruction) with dot() (pure ALU) in the
per-particle distance check. The polynomial kernel uses ratio^2 = dist^2/ir^2,
so no sqrt is needed at any point in the loop.

Before: every particle iteration calls length() -> sqrt -> SFU even for
the skip path. With 64k particles x 262k voxels that is ~16 billion
sqrt calls per density pass, saturating the 272 SFUs on RTX 3080.

After: only dot(), multiply, and subtract. Zero SFU calls in the entire
dispatch. The kernel (1 - dist_sq*inv_ir_sq)^3 is algebraically identical
to (1 - ratio^2)^3. Visual regression baseline passes with no pixel diff.
```
