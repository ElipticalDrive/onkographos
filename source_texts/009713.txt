Introduction
In this part I will talk about the new capabilities of the ray tracer. The improvements are an acceleration structure, transforming objects and instancing. So this is an upgrade about the raytracer’s performance and to further tweak the objects in the scene. This part was quite enjoyable as I wondered off to unknown terrirtory and implemented exciting stuff I have not before.
All images seen in the post are rendered by my raytracer. The tests are conducted using the Apple MacBook M3 Pro chip with 5 performance cores with 4.06 GHz and 6 efficiency cores with 2.8 GHz. I decided to post the total time it took to render the images and separate the time it took to build the acceleration structure and the time for the latter parts of rendering. I did not really focus on the time it took to build the acceleration structure while analyzing the outputs as it will be insignificant in a scene that will take hours at the following stages of the project.
In this part, I will talk about the problems I encountered at the end of the post and focus on the fantastic new things that were implemented this time around. There are also some exciting scenes and videos at the end so stay tuned!

The Acceleration Structure
The first thing I wanted to do was building the acceleration structures in the scenes. This would decrease the time it took to render complex scenes if I wanted to test transformations and instancing with them, so this was the first step.
In regular ray tracing, we cast a ray then check if that ray intersects with a shape in the scene by going over every single object, whether it be a triangle, sphere, a triangle that is part of a mesh or a torus if you are into that. This step takes the longest time in our ray tracer as this search for intersection usually takes a very long time. In a realistic mesh, there can be millions of triangles and we go through every single one of them. This approach has a complexity of O(n) and any way we can get this down would be a huge improvement. This is where acceleration structures come into play.
The main idea is that, we can partition *elements in the scene into smaller bounding boxes and then the *elements inside these smaller bounding boxes until we get to the smallest *object or *space we want. Then we can form a binary tree with these bounding boxes and perform intersection tests with them until we find an intersection with a bounding box that is a leaf node (could be 2 with different ones but I am trying to explaing the most basic case). This way, we basically turn the issue into a binary tree search that will have O(log n) complexity which is a huge improvement.
The reason I put stars before elements, object and space is because there are approaches to this partitioning process. We can partition the space or the objects in the scene. Here, I could choose to implement the corresponding structures k-D tree and Bounding Volume Hierarchy for each of these approaches.
Bounding Volume Hierarchy
I chose to go with the BVH acceleration structure as it is supposed to be easier to implement and slightly faster than the k-D tree alternative. Here, we build a binary tree made of tight bounding boxes of objects inside of them, going from the whole scene in the root node to the tiniest primitive triangles or spheres in the leaf nodes.
To get this done, I created a bounding box class first to easily use in these trees. One of the most important things I focused on is that all bounding boxes should be axis-aligned for the basic intersection tests, even after transformations (in depth later in the post). After doing this, I needed to build the tree.
Building the Tree
This step requires for us to partition the objects in a scene with an algorithm quite similar to the partitioning step of quicksort. This was quite lucky for me as the latest ‘CENG315 - Algorithms’ homework I did was about quicksort so it was a piece of cake. we run this recursive function that takes all the primitives we want in the BVH we want to build.
I could approach the partitioning a few different ways. First I get the whole bounding box of all of the objects in the scene and that step does not change. Then we could pick the middle of x, y or z of this bounding box, find the axis with the largest min-max value difference and pick its middle point as a partitioning point or use Surface Area Heuristic as a mean of making the whole process faster by calculating costs but I will not get into this. I calculated the partitioning points by using the middle of the min-max points of the axis with the largest difference in them.
After we find the basis for partitioning, we should actually do it and create bounding boxes. This is where the quicksort-like step comes in. This function likely has 5inputs : shapes_array, start_index, end_index, partition_axis and partition_value. (Could be less but I did it like this) Let’s say we are partitioning a scene based on the x-axis with a value called ‘x-mid’. We will put the triangles with a center x-value smaller than ‘x-mid’ on one side of our array and the larger ones on the other side, we should return the index where the latter array starts (let’s call it partition_index) to use in our next recursive calls for each side. So we use the same shapes_array in our next call but use the new start_index and end_index pairs: (start_index, partition_index) and (partition_index, end_index). Then recalculate the new partition_axis and partition_value using the primitives in this range in our array.

Intersection Tests
After building the BVH structure, I obviously needed a way to traverse the tree and perform intersection tests. This was quite easy as I only needed to perform axis-aligned box intersections with the bounding box in each node. If I stumble upon a leaf node, I find the t_value in our main formula: o + td, using the intersection tests from Part 1. There could be more than one t_value found so we return the smallest one in our recursive function as we are trying to find the nearest intersection.
Linearization
Upto this point, I used regular pointers to access the child right and left nodes of each parent node, but linearizing this and accessing each of them using an array should make this process faster. I did this quite easily by forming an array of BVH nodes and adding left_child_index and right_child_index to my bvh_node struct. When I calculate a new bvh_node, I push it to the end of the array and return its index to the parent node to use it as a child node index. This proved to improve the results.
In the last part, I reported the time it took to render the Dragon scene as 113.63 minutes without BVH. There was also a issue with backface culling in the last part, but when I put this BVH intersection function everywhere, the problem disappeared. I searched why it might be but still don’t have a clue. So I culled all backfaces in the following tests.

The results were astonishing. With a non-linearized BVH structure, it took a total of 3.46 seconds, 2.94 building the tree and 0.52 the rest of the operations to render the scene. With a linearized BVH structure, it dropped to a total of 3.19 seconds, 2.78 building the tree and 0.41 the rest of the operations. Here I do not really care about the time it took to build the tree as it will not matter in a big scene that will take hours even with the acceleration structure. The time it took to perform the intersection tests and shading is what really matters and there was a 20% improvement with the linearized version.
The sad thing here is that this was the fastest it got. To implement transformations and instancing, I needed to make changes to the functions and I used the non-linearized one as a base because I am more used to it and it would be easier to debug if something went wrong. I thought I would have the time to also finish the linearized version of that after I finished that but I did not have the time to as 2 other homework collided with this one and I was afraid to break it. I also commented out the backface culling and did not use it after I started programming transformations and instancing as I did not have the time to figure out a way to introduce it after implementing the new capabilities. The linearization should take little time to implement with the changed functions as they already exist but not used. I could get it running in the time I have to write this post, but will not because I could not get it done in time. All of the test results, if not reported otherwise, will use a non-linearized BVH structure and no backface culling.
Transformations
Transforming objects is quite easy and I do not want to focus on that easy linear algebra part of the implementation. We have a total of 3 main transformations: translation, rotation and scaling.
With translation, we just take a point and add the translation x, y and z values to change its position. With rotation, we are provided an angle of rotation and an axis. The axis has 3 components x, y, z and can be a combination of them, so it does not have to be just x, y or z. And scaling would ideally scale an object in x, y and z axes. We could combine these transformations by multiplying them back to back to find an end full_transformation_matrix.
To make these computations easier, we use matrices to do them and for that to apply to all transformations, we add a new dimension to our points in 3D. We just add a w = 1 to our [x, y, z] points to make them [x, y, z, w = 1] before we make our calculations and this is called an homogeneous coordinate. Here, the same ratio of x, y and z to w (whatever it may be) represents the same point, just in a different layer in the dimension we add to the 3D point. So [3x, 3y, 3z, 3] is the same point as [x, y, z, 1], only difference is that the latter is on the original 3D non-homogeneous space with w = 1 so we should ideally use that in a setting it matters. Here, we do not actually need to check this as we only do rigid body transformations and w will always be 1. If we did perspective transformations it would matter and I would need to divide every position after transformations by w. I still decided to do it for good measure, but I still do not think it would make a difference.
You can find the basic transformation matrices with a quick Google search so I will not focus on them and just move on.
Implementing the Transformations — Instancing Starts
I created classes for each transformation and found their value if an object used them and multiply them back to back. I used the Eigen library to do this as it provides help with the inverse and transpose operations I will need and let’s me actually use the insertion operator to build a matrix or vector in row-major order so I can directly see what I put into each matrix in 4x4 format in my code. I also used it in a recent digital geometry project so I am familiar with it and that’s another reason I went with Eigen.
I recently acquired the book ‘Ray Tracing from the Ground Up’ by Kevin Suffern. I enjoy the book and read the topics covered in class. He talks about 2 ways of implementing transformations. The first is doing things directly buy applying transformations to vertices, normals or any other thing you want and use it like that. The second is instancing. Where we have only one copy of the object in memory in its own local space. Then we can create more than one box in the scene for the rays to intersect with and when they do, we can go back to this object’s local space to find intersections.
This could be harder to do with an acceleration structure as we previously partitioned every single primitive into one BVH tree, no matter which object or mesh. For this to work properly with the acceleration structure, we must introduce top level and bottom level acceleration structures. The main idea is that we will create bottom level acceleration structures for every object in the scene: spheres, meshes, triangles. And we will create bounding boxes for all of them to use in our top level acceleration structure. We will apply the transformations provided for them to the corners of these bounding boxes. So we will have a tree for each object in the scene in their own local space and one tree for their bounding boxes in world space.
This could be hard to visualize and although I understood the concept in class, I had trouble visualizing and implementing it. So I scribbled some rough notes on my girlfriend’s iPad to share with you how I formed the whole process in my mind. I think I thought of the whole local space and world space concept in a different way. They all actually are represented in world coordinates, but different worlds (could say verses or dimensions) where we should apply changes to our camera to actually see. Instancing
In a normal sense, instancing is creating clones an object in a scene with different transformation without copying the object information. Only one copy of the information of a complex mesh is created in the memory and it is accessed for each instance using the transformation matrices. I explained all of this before so will not go in depth again. The only difference is that there are multiple bounding boxes for each shape in the main scene’s TLAS with different transformations applied to them. This was really easy to implement so I will not talk much about this. Here are some cool results, all of these use the TLAS — BLAS approach:

I am quite happy with the results in this part. The only issue I have is like I mentioned, I am not quite happy with some of these times and will look into changing it to a linearized form like before and re-introduce backface culling. The time to run the intersection test and shading did not change much but there should still be a huge performance boost. This part was more difficult for me than it was supposed to be but it was still enjoyable. See you in the next part!
