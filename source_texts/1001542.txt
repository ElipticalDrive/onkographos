X1 part 2c: 3D mip chains are rebuilt once per source and frame, as ADR-0050 decision 5 says. This closes the N1 part of #641.
This is a draft stacked on #624 (part 2b), which is stacked on #622 and then wave/m3-3. Auto-merge is off. #629 (part 3) moves on top of this PR. There is no wire change.
Before / After
Before: a layer or an import drawn in 3D got its chain rebuilt on every render or render_into call that drew it, changed or not. So a capture shown in 3D by two mixes was rebuilt twice per tick. Only an upload was rebuilt by change (after rewrite_rgba8).
After:
Every Image counts its changes, and a chain is rebuilt only when that count has moved since its last build. What marks a change:
rewrite_rgba8 marks an upload (as before).
render_into marks the layer it drew into.
ResourceCache::import and import_premultiplied mark an import the first time a cache frame hands it out, or when the key's texture changes.
The new public Image::mark_changed marks an import the caller keeps outside the cache, whose texture the platform rewrites.
So a source is rebuilt at most once per source and frame, however many mixes or nested scenes draw it, and not at all while it is unchanged.
What
image.rs: generation now counts every change. pub fn mark_changed replaces is_static. There is also a test-only mip_builds.
mips.rs: claim(image) compares generations only. built_call is removed, plus a test-only build counter.
compositor.rs: the per-call calls counter is removed. render_into marks its target after the submit.
cache.rs: import_as marks the import once per cache frame.
tests/three_d.rs, two new tests:
a_layer_rebuilds_its_mips_only_after_it_is_drawn_into: red, then a second draw that doesn't rebuild, then render_into green, which rebuilds and shows green.
an_import_rebuilds_its_mips_once_per_frame: two cache frames, each drawing the import in 3D from two calls, give one build per frame.
Docs:
render README: pipeline step 2, the Testing paragraph, and Open questions (the change-count question is replaced by whether the cache should take the frame's version).
ARCH › GPU pipeline.
progress.toml.
How it was tested
cargo fmt -p jstream-render, cargo clippy -p jstream-render --all-targets -- -D warnings, cargo test -p jstream-render (156 passed on llvmpipe) and cargo xtask docs check.
Regression check (R-TEST-001): with the cache's mark and render_into's mark both disabled, both new tests fail. I edited the code and then reverted it.
The 3D goldens are unchanged, because each draws a fresh upload once.
Not run / not verified
No hardware, WARP or macOS run. No workspace-wide clippy, wasm32 check, cargo deny or benches. Disk is tight, so only the changed crate was built.
jstream-core wasn't built. It calls ResourceCache::import and is unaffected at the call site. No core path draws 3D until feat(graph): accept 3D placements, protocol 0.34 (X1 part 3) #629 lifts the rejection.
A capture that delivers no new frame in a tick is still rebuilt that tick, because the cache doesn't see the frame's version. This is listed under Open questions, and render: 3D mips rebuild per call, and crop bleed at coarse levels #641 keeps that part.
The crop bleed at coarse levels (render: 3D mips rebuild per call, and crop bleed at coarse levels #641's N2 part) isn't addressed here.

* feat(protocol): the drawn 3D polygon and unplace (X1 part 1, ADR-0050)

ItemGeometry::drawn_polygon clips the content rectangle to the box and then
by the near plane w >= 1/256, in the local frame, and returns three to five
vertices with canvas point, local point, texture coordinate and w, so a
compositor can interpolate perspective-correctly. ItemGeometry::unplace is
the inverse map. Pure functions with no wire form; no caller yet.
