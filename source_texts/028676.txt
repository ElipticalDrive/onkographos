Description
This PR adds isosurface rendering to the labels layer in 3D. Isosurface rending adds shading based on lighting, so the labels look more like real surfaces. I haven't added it yet, but we can add a "Rendering" combobox to the layer controls to switch between translucent (current default) and iso_categorical (name suggestions welcome).
iso.mov
Example code
```
  """
Display a labels layer above of an image layer using the add_labels and
add_image APIs
"""

from skimage import data
from scipy import ndimage as ndi
import napari


blobs = data.binary_blobs(length=128, volume_fraction=0.1, n_dim=3)
labeled = ndi.label(blobs)[0]
viewer = napari.view_labels(labeled, name='blob ID')

labels_layer = viewer.layers['blob ID']
labels_layer.rendering = 'iso_categorical'
viewer.dims.ndisplay = 3

napari.run()
  }
```
A few notes:
I perform the surface detection treating the image as a binary image (equivalent to setting the iso threshold to 0). This assumes that the texture data sent to vispy from the Labels layer always has 0 as the background value.
Accurately calculating the gradient (for finding the surface normals) on is difficult on binary images. This is especially apparent for small blocks of labels that protrude from the main body (e.g., one voxel sticking out from a surface). This results is dim diffusive lighting (which is just a function of the dot product of the surface normal and illumination). I made a hack to address this, but I'm not sure we should keep it in (see comment below). There are probably better ways to address thiss...
I didn't include specular illumination (surface reflections) since the bad normal estimation leads to large sections of surfaces have the same normal and then they become big reflectors (see below).

@alisterburt , I believe I have addressed your comments. In particular, I refactored and added some comments to the shading code, which I hope makes it more clear.
@haesleinhuepf , I have added the combobox in the layer controls to set the rendering mode and added rendering as a kwarg in the add_labels() and view_labels() functions.
I believe this PR is ready for review!
Open questions:
what do we want to call the new rendering mode? I am currently calling it iso_categorical because it's a special case of isosurface rendering where the values are categorical (as opposed to continuous as in intensity images). However, I am open to other suggestions! Thoughts @jni , @alisterburt , @sofroniewn ?
Do we want to add this behavior as a new rendering mode or something else? @alisterburt suggested that we add a new parameter, shading that toggles between None (renders in translucent mode) or flat (renders with this iso_categorical mode. I agree that shading is probably more descriptive. However, the image layer already combines iso with the other render modes. It seems like we should do the same here given that the two layers already share so much (including the render components). Perhaps we can rethink the render vs. shader split in a future PR/issue.
What should be our new default rending mode? Obviously I am biased, but I think this looks much better than the current translucent default. However, defaulting to iso_categorical (or whatever we call it) would change the default appearance of 3D labels. While not a breaking change in the sense that old code would still work, it is a pretty stark contrast visually.

Thanks for the reviews and comments, @alisterburt , @sofroniewn , @jni, and @brisvag !
With regards to the background value, I agree that the napari texture representation of labels should always have background as 0. Is it too confusing to allow users to still set the background value via the iso_threshold property? iso_threshold is currently part of the Labels layer as a result of Labels being a subclass of _ImageBase (e.g., on master, one can currently set the rendering to iso on the Labels layer). I could see this as being confusing for a couple of reasons: (1) the threshold value is from 0-1 (i.e., it's in the normalized texture values we send to vispy not the integer labels in the layer data) and (2) it isn't really advertised as part of the public API in the Labels docstring, even though it is public (in the sense that it isn't preceded by a _). Perhaps the simplest thing is to set the background value to zero as a constant in the shader, which makes it easy to expose as an option later, but doesn't add a potentially confusing choice for the user. Thoughts?
I have integrated @alisterburt 's suggestions.
I will track down the uniform not set warning that @sofroniewn observed. I think I just need to add the default value to the vispy visual. Alternatively, we can set that as a constant in the shader. I don't really see needing to make that user settable. Numpy uses 1E-8 as the default. I think we can probably do the same.
I can make that fix and make iso_categorical the default rendering later today and then if there aren't any other suggestions, I think we will be good to go!
