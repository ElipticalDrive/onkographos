Why. Catalogues and VBT (VisIVO binary tables) larger than RAM cannot be opened: the 3-D viewer loads every point in memory. The same holds on a cluster backend, where the data stay next to the GPU.
What exists today. All points are loaded at open. Cubes have a brick pyramid built out of core (#69) and a view that reads only the blocks it needs (#70); points have no equivalent.
Scope
One out-of-core octree format for point data, shared by catalogues and VBT. Each node holds a subset of points (level of detail), its bounds and per-column ranges; it is built in bounded memory, like the cube pyramid (docs/brick-pyramid.md).
The view loads the nodes it needs for the camera, within a point budget, coarse far away and complete near the camera, and refines when the view stops.
The same files work with the desktop's local backend and with a cluster backend, and are reused across sessions.
Selections, filters and colouring by column keep working on the nodes loaded.
Done when
A catalogue and a VBT several times larger than RAM can be explored interactively, on a local and on a remote backend.
The build is measured (time, memory) like benchmark/brick_pyramid.
Notes. Server-side rendering of point data (#83) uses this octree. Part of #73.
