Interestingly I'm working on a fairly similar problem. my thoughts are roughly:
For simple convex shapes, do a basic triangulation then use loop-blinn for curves. For conic, cubic, chop into quads.
For simple concave shapes, do ear clipping then similar loop blinn approach for exterior
For self intersecting ... I'm not sure yet. I was actually thinking about applying the slug algorithm. Not sure how well it will perform.
Besides the shapes themselves, once you start using SDFs the simple approach to blend modes Impeller was using no longer works. For example, BlendMode::clear will clear pixels that aren't "covered" by the SDF unless you're also using discard. But if you use discard then no AA.

Besides the shapes themselves, once you start using SDFs the simple approach to blend modes Impeller was using no longer works. For example, BlendMode::clear will clear pixels that aren't "covered" by the SDF unless you're also using discard. But if you use discard then no AA.
In software we used to apply the blend mode before we applied the AA/SDF factor. That's not possible with shader code directly (no access to destination pixels). A 2-pass approach can provide the original destination pixels as an input to the shader, though.

Having the library of functions is nice, I'm using a round rect sdf and stroked round rect sdf and that is usually 95% of what is needed. Doesn't solve the general path case though, and I don't want to use subdivision × tessellation for quality reasons
It's a great library if you rely on MSAA which we do for most devices, but for desktop we are investigating them for computational AA and then you need to worry about not just which side of the border you're on, but how far you are in pixel (or local) distances. The library gives you distances in whatever space you deliver the geometry in, but we have conflicting needs:
stroke widths are computed in local coordinates
the "AA gradient" (i.e. whether you are within half a pixel from the border) is computed in device coordinates
preventing stroke dropouts when the stroke width is smaller than a device pixel also needs to be evaluated in device coordinates.
