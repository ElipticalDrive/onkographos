Replacement implementation contract
Keep this as the player-facing large-world presentation epic. Client owns authorization/session/resource orchestration; renderer owns retained structural chunks; Go/protocol own manifests, visibility, revisions, and bounded delivery. A larger visual radius must not enlarge authoritative live gameplay state.
New implementation and tests are independent MIT work unless an exact contribution by an approved MIT provenance grantor is admitted through the recorded file-level MIT grant. Preserve every player-facing, accessibility, disclosure, and performance design decision below.
Required verification
Test pure state/geometry/material/UI behavior headlessly where possible and run supported Linux/Windows integration paths.
Add bounded malformed, stale, lifecycle, resource-loss, and recovery cases appropriate to the owner.
Add shared Go/Rust protocol fixtures for authoritative fields; presentation never reconstructs hidden rules.
Use released shared renderer/protocol/toolkit contracts and wrapper-managed replacement scenarios.
Preserved product/design specification and historical implementation notes
Why
Atrinik should be able to show a much larger isometric scene so distant buildings, roofs, towers, and terrain appear before the player is almost beside them. Increasing the existing map-size constants is not a performant way to get there: it couples presentation range to authoritative LOS, per-player delta caches, network traffic, lighting, sound, interaction, and rich client cells.
The current feat/smoothlighting branch already provides the difficult visual foundation this needs:
CLIENT_CMD_MAP carries independently framed physical depths from -MAP2_MAX_DEPTH through +MAP2_MAX_DEPTH.
server/src/socket/request.c serializes structural boundaries, roofs, support height, explicit fog state, and camera cutaways per depth.
client/src/gui/widgets/map.c merges all active depths into one back-to-front painter order and screen-culls projected tiles.
ordinary movement scrolls a circular five-window history cache instead of copying it, and the renderer has stage profiling.
smooth server-authored lighting and structural wall/roof filtering already work across linked levels.
However, the branch's sizes are easy to misread. The player setting is 9–17 logical tiles. MAP_RENDER_OVERSCAN adds two anchors on every edge, so the default/max 17×17 view requests a 21×21 MAP2 wire window. The server's MAP_CLIENT_X/Y, LOS arrays, cutaway arrays, and per-player map cache are fixed at 21×21. MAP2 also packs each tile coordinate into five bits, so the current record format cannot address a window larger than 32×32.
A direct resize scales several expensive structures together:
the current client MapCell is 5,376 bytes;
one active 21×21 depth with the 5×5 fog-history grid is about 56.5 MiB before lighting, sprites, and render commands;
all 13 possible depths would be about 735 MiB;
even a 31×31 window would be about 123 MiB per active depth;
the server MapCell is 444 bytes, about 191 KiB per 21×21 depth per player, and draw_client_map2() scans every requested tile across every linked depth and up to 49 layer/sub-layer slots.
The target should therefore separate a large, cheap scenery radius from the current bounded live/interaction radius.
Related work:
Depends on the GPU renderer in atrinik/client#23 for the intended large-scene presentation path.
Coordinate retained chunk/cell render packets and camera transforms with atrinik/client#22 rather than building a second map cache.
Add resolution-independent UI scaling and native display/frame pacing #20 owns UI/world scale and responsive layout. This issue owns how enough world data reaches the map view when a large or wide viewport can show more scenery.
atrinik/client#21 can eventually implement the visibility falloff as a material, but the data/visibility contract should not depend on arbitrary shader support.
Target experience
A normal viewport can render at least a roughly 41×41 structural footprint, or the screen-derived equivalent at the selected world scale, while the authoritative live area remains the current 17×17 logical / 21×21 wire window.
Large multi-storey buildings are complete in the distance, including linked positive depths, roofs, walls, support elevation, tall sprites, map seams, and painter overlap.
Walking ordinarily reveals only new scenery chunks/edge cells. It does not cause the server to run gameplay LOS, inspect every object layer, or send live deltas for the complete large scene.
The world outside the player's current visible area remains recognizable instead of turning into a hard grayscale square. A soft radial light/visibility boundary around the player communicates the live visible area.
The radial boundary does not grant vision through walls. It is a soft presentation of the server-authoritative visible-tile mask, capped by a radius, not a client-side replacement for LOS.
Mobs entering or leaving visibility fade over a short interval instead of popping. They become targetable/non-targetable immediately when authoritative state changes; a fading-out image is a non-interactive render ghost and cannot disclose movement after the last server update.
Distant scenery cannot be clicked, targeted, heard, inspected, or used for pathfinding until it enters the live area.
Secret, private, or player-specific geometry is never accidentally published as distant scenery.
Proposed architecture
1. Keep two independent radii
Define separate client/server concepts:
Scene radius: presentation-only structural geometry needed to fill the map widget plus sprite overscan. It is viewport/zoom-derived, chunked, cacheable, and may be much larger than 21×21.
Live radius: authoritative gameplay interest, LOS, dynamic objects, interaction, lighting changes, targeting, ambient sound, and camera cutaways. Retain the current 17×17 logical / 21×21 MAP2 wire size initially.
Do not make MAP_CLIENT_X/Y the maximum drawable world size. Keep them as the live-area bound until profiling justifies a separate gameplay change.
The server must not run blocked_los, per-object visibility filtering, sound matching, target/probe work, animation inspection, or rich delta-cache comparison for scene-only tiles.
2. Split structural geometry from live state
Replace the monolithic client cell ownership with two representations.
A compact structural cell/chunk contains only data needed to draw the distant shell, for example:
physical map identity, local/world tile position, and relative stack depth;
floor, floor-mask, eligible static decoration, wall, and roof faces;
sub-layer, height/support elevation, multi-part quick position, align/rotation/zoom, draw-double, and structural camera semantics;
conservative baked/ambient presentation light if required for distant geometry.
It must not contain object UIDs, player names/colors, probes/HP, target/friend state, living/item/effect entities, damage animations, dynamic glow state, ambient sound, current LOS, or other gameplay information.
The live overlay retains the authoritative rich state inside the current MAP2 area:
actors, items, effects, animated or interactive objects, doors, names, targets, probes, sounds, current light samples, fog/visibility, and cutaways;
changed structural state inside the live area;
explicit overrides/tombstones so a live change can replace or suppress a cached base face without destroying the underlying chunk.
Rendering resolves each tile as base structural geometry plus live overrides plus live entities, then feeds the result into the branch's single cross-depth painter order. A live clear removes only the overlay unless the command explicitly invalidates base geometry.
Split large optional fields out of dense cells. In particular, fixed player-name/color buffers and entity-only state should not be paid for by every empty structural tile in every history window. Prefer compact arrays/sparse records with measured memory caps over a second large dense MapCell.
3. Stream cacheable geometry chunks
Add an independently framed geometry protocol rather than stretching the existing five-bit MAP2 tile record.
Recommended chunk contract:
use 16×16 structural chunks initially;
identify a chunk by authenticated server identity, stable physical map ID/path, map generation/revision, stack depth, and chunk X/Y;
announce uncompressed length, compressed length, content hash, format version, and bounded object/face counts;
use explicit integer widths and coordinates large enough for the target scene; do not inherit the five-bit MAP2 coordinate field;
length-delimit each level/chunk and reject duplicate identities, impossible coordinates/depths, decompression bombs, trailing bytes, and hash mismatches;
use the existing authenticated asset-source/digest model for immutable chunks where practical. HTTP/CDN is allowed only after size and SHA-256 metadata arrives over the authenticated game connection; in-band QUIC remains the fallback;
use the existing zlib dependency unless measurement demonstrates a compelling reason to add another codec.
A small scene manifest should describe physical map placement around the camera, TILED edge links, stacked depths, chunk revisions, and hashes. This lets the client stitch adjacent physical maps and reuse chunks across ordinary movement and connected-map transitions without flattening upper maps into base sub-layers.
The server should build each eligible chunk once per map generation, cache the serialized result, and share it among players. The client should keep a bounded memory LRU and may keep a digest-keyed on-disk cache scoped by stable server identity. Request nearby chunks first, then prefetch a guard ring at low priority. Missing chunks render as absent scenery and must never stall gameplay packets or frame presentation.
Coordinate delivery scheduling with atrinik/atrinik#126 so large geometry transfers cannot head-of-line block login, live MAP2 updates, or inputs.
4. Define static eligibility and invalidation explicitly
Layer alone is not a safe definition of static geometry: doors use the wall layer, roof objects use the hidden flag for camera semantics, and map scripts can mutate apparently structural objects.
Introduce an explicit, conservative geometry classification during content collection/map load. Only map-owned, presentation-safe, non-secret objects should enter a shared distant chunk. Doors, living objects, pickups, effects, containers with state, invisible/secret barriers, player-specific substitutions, and script-owned mutable objects remain live-only unless their type has an explicit safe distant representation.
For runtime mutations:
a live override takes precedence immediately within the live area;
changing an eligible structural object bumps the owning chunk revision and sends an invalidation/hash update to affected clients;
map reset/reload changes the map generation and invalidates all old chunks for that physical map;
a stale chunk may remain in the content cache by digest but must not remain attached to the active scene manifest;
cutaway state remains a live camera overlay. Do not publish a per-player cutaway as shared geometry.
The proposal must document whether distant terrain/building exteriors are intentionally discoverable before gameplay LOS. Recommended policy: only an explicitly authored/exported public exterior shell is eligible. Secret/interior geometry remains live-only. This makes the disclosure boundary reviewable rather than inferring it from current LOS side effects.
5. Replace grayscale fog with a visibility/light mask
Keep server/src/server/los.c authoritative. For live tiles, carry a binary/graded visibility state sufficient for the client to build a soft screen-space mask. The displayed mask is:
authoritative visible tiles ∩ configured radial cap, with a short feathered edge.
Walls and blockers shape the visible region; the outer range reads as a circle/ellipse in the isometric projection. The player therefore gets a clear pool-of-light cue without implying that a mob behind a wall is visible.
Outside the live mask:
draw eligible structural geometry in its normal palette with a configurable ambient/distance treatment rather than SPRITE_FLAG_FOW grayscale;
do not draw live entities or live effects;
do not extrapolate dynamic lights. Use chunk ambient/baked presentation light or a documented neutral distant-light policy;
retain explored/unexplored state separately if gameplay still needs discovery. Visual styling and information authorization must not be represented by one overloaded fow bit.
After atrinik/client#23, implement the feather as one GPU mask/material pass, not per-sprite CPU copies. Until then, a bounded cached alpha mask is acceptable for proving semantics, but do not add a permanent second software renderer.
6. Fade live entities without weakening authority
The current tile/layer MAP2 stream can identify living targets, but smooth transitions need identity to survive a tile move or clear. Make stable entity identity explicit for fade-eligible dynamic records and define spawn/update/remove semantics.
Recommended behavior:
fade in for about 150–250 ms after the first authoritative visible update;
on LOS/range removal, remove targeting, hit testing, names/HP, and gameplay ownership immediately, then retain only the last received sprite transform as a non-interactive render ghost for the fade duration;
cancel/reverse a pending fade if the same entity identity reappears before completion;
never interpolate into an unseen tile or continue animation/movement from local prediction after removal;
cap the ghost list and clear it on teleport, new map, level shift, logout, resource reload, or renderer reset.
Static geometry does not fade on every live-radius crossing. It remains in the scene layer; only live overrides and entities transition.
7. Retain and cull render data
Build the large scene on atrinik/client#22's retained packets:
compile each geometry chunk into retained per-cell draw packets once per chunk/resource revision;
keep camera position separate so ordinary movement changes a transform and attaches/detaches only edge chunks;
visit only chunks and cells whose projected bounds can intersect the viewport, including guard bounds for tall, doubled, rotated, zoomed, multi-part, and stacked sprites;
merge stable geometry packets with the small live packet set in the existing global painter order;
do not repaint or resort the whole cached world merely because one live entity animates;
keep minimap ownership separate. A large scene cache must not cause the dynamic minimap to traverse or redraw the complete scene at gameplay frame rate.
Instrument chunk hits/misses, bytes, cells culled/visited, packets reused/built, live overrides, sort/merge time, uploads, draw count, geometry memory, live memory, and invalidation reasons.
Protocol and security requirements
The authoritative wire specification must define direction, command IDs, framing, field order, widths, byte order, version/format identity, coordinate space, limits, compression, hashing, map generation, chunk invalidation, and malformed-input behavior.
Update together:
common/toolkit/socket.h command IDs/constants and packet helpers;
server producer/cache/invalidation code and client dispatch/parser;
all MAP2/live-overlay senders and consumers affected by the cell split;
bot or test consumers;
the owning ADS protocol document;
round-trip, malformed-input, cache-revision, and cross-map/depth fixtures.
This repository's greenfield posture allows replacing the superseded map contract rather than maintaining two permanent paths. During implementation, either update all in-repository consumers in one breaking change or use a short-lived development-only version gate that is removed before completion.
Never trust a server-provided face index, count, coordinate, compressed size, uncompressed size, chunk count, depth, string length, or manifest placement without bounds checks. Persistent chunks remain scoped by authenticated server identity and verified digest, like region maps and other assets.
Implementation sequence
Add profiler counters and capture current branch baselines for bandwidth, draw_client_map2 CPU, client parse time, cell memory, map traversal/sort/lighting, and frame time in ordinary, stacked, and moving scenes.
Refactor the client into compact structural data plus sparse/rich live data while preserving the current 17×17 visible result and MAP2 behavior. Prove the memory reduction before increasing range.
Add geometry classification, chunk serialization/cache, scene manifest, authenticated delivery, parser, and revision invalidation. Render a larger base-depth scene with live MAP2 unchanged.
Extend chunks and retained painter packets through linked positive/negative depths, adjacent TILED maps, roofs, support height, tall sprites, and cutaway overlays.
Add the soft authoritative visibility mask and replace grayscale fog presentation without changing LOS or disclosure policy.
Add stable live-entity lifecycle records and render-only fades.
Make scene radius viewport/world-scale-derived, add prefetch/LRU budgets and diagnostics, then tune defaults from measurements.
Remove superseded monolithic geometry/fog state and any temporary compatibility path; update ADS and architecture guidance.
Acceptance criteria
The client displays at least a roughly 41×41 structural scene, including representative +1/+2 stacked buildings and adjacent map seams, while the live gameplay area remains 17×17 logical / 21×21 wire.
Increasing scene radius does not increase blocked_los dimensions, per-tick live tile scans, target/sound/entity processing radius, or the server's rich per-player MAP2 delta cache.
Distant chunks contain only explicitly eligible public structural presentation data. Secret, player-specific, interactive, and dynamic state is absent and covered by tests.
Ordinary one-tile movement reuses existing chunks/render packets and fetches or attaches only new edge/guard chunks. Returning to an unchanged area uses verified cache entries without retransmission.
Geometry loading is asynchronous and lower priority than live gameplay. Missing, corrupt, delayed, or failed chunks do not block input, live updates, or frame presentation.
Structural mutations, map reset/reload, connected transitions, level shifts, teleports, and cutaways invalidate/override exactly the affected state without stale faces or flashes.
Base geometry and live overrides preserve the branch's unified cross-depth painter order, roofs/walls, tall/double sprites, support elevations, smooth lighting, door hints, and camera cutaways.
The visibility treatment has a soft radial outer boundary but never expands server LOS through blockers. Outside it, authorized scenery remains recognizable and live entities/effects are absent.
Mobs fade in/out smoothly, lose interaction immediately on authoritative removal, never move after their last visible update, and cannot leave unbounded render ghosts.
Far tiles cannot be targeted, inspected, sounded, path-clicked, or otherwise treated as live.
Client memory for distant geometry is independently bounded and materially smaller per tile than the 5,376-byte live MapCell. The current five-window rich-cell cost does not scale with scene radius.
Server serialization is shared by map generation/chunk rather than rebuilt per player per tick, and measurements show no material live-update regression with a large scene enabled.
Protocol parsers reject malformed, duplicate, oversized, out-of-range, mismatched-hash, and decompression-bomb inputs without partially applying another chunk/level.
Linux and portable MinGW client/server builds pass with warnings as errors, relevant tests pass, and profiler/screenshot evidence is attached.
Validation plan
Add deterministic geometry encode/decode and manifest-placement tests across chunk boundaries, adjacent physical maps, negative/+1/+2 depths, nonzero support height, and maximum allowed coordinates/counts.
Add malformed and fuzz-style parser cases for truncation at every field, duplicate chunk/depth, invalid face/layer/sub-layer, overflow, invalid revision/generation, bad hash, compressed-size mismatch, and trailing bytes.
Add server tests for static eligibility and disclosure: ordinary floors/walls/roofs included; doors, hidden secrets, mobs, items, effects, sounds, targets, player-specific objects, and scripted mutable state excluded unless explicitly classified.
Test live overrides/tombstones and chunk invalidation with doors, destroyed/created walls, map reset, script mutation, connected transitions, and rapid leave/re-enter.
Capture screenshots at the current view and large scene radius for a map edge, adjacent tiled maps, a tall tree/building, one-storey and three-storey roofs, indoor cutaway, long wall, darkness/light transition, and missing/delayed chunks.
Exercise mob fade across radial range, behind a wall, during rapid LOS toggling, movement, death, teleport, level transition, logout, and target selection.
Record initial-load and steady-state bytes, server serialization/cache time, draw_client_map2 time, client parse time, cells/chunks visited and culled, packet reuse, sort/merge, uploads, frame CPU/GPU time, and peak/steady memory at 17×17 live with at least 41×41 scenery.
Test lossy/high-latency delivery and asset fallback so gameplay stays responsive while scenery fills progressively.
Out of scope
Increasing aggro, AI simulation, combat, sound, targeting, interaction, or pathfinding range.
Replacing the server's authoritative two-dimensional gameplay LOS with a voxel/3D visibility system.
Sending distant mobs, items, effects, secret interiors, or dynamic light sources.
Flattening linked physical maps into base-map sub-layers.
A full 3D engine or rewriting authored sprite art.
Treating region-map PNGs as world geometry; they remain navigation/map assets rather than isometric scene data.
