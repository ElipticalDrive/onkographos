Part of #11375. Algorithm: GreedyGaussianSegmentation / GGS in sktime/detection/ggs.py (internal sktime implementation).
What does this implement/fix? Explain your changes.
Performance. GGS.add_new_change_point, the split subroutine of greedy Gaussian segmentation (section 3.1 of the paper), evaluated every candidate split point in a Python loop: updating running means and covariances, and computing a Cholesky decomposition and a matrix inverse per candidate, for every one of the k_max greedy steps and again in adjust_change_points.
The covariances of all left and right parts are differences of cumulative sums of the samples and of their outer products, so all candidates are now evaluated at once with batched numpy linear algebra (np.linalg.cholesky, np.diagonal, np.linalg.inv on stacked matrices), in blocks of candidates to bound memory use (~2^21 floats per block). The selection rule is unchanged: the first candidate with the lowest objective, if below the unsplit objective.
Bug fix. While verifying equivalence, a bug in the previous implementation surfaced: the running mean of the left part was initialized as data[0, :] / n, with n the number of columns, instead of data[0, :]:
```
m, n = data.shape
...
mu_left = data[0, :] / n
```
For univariate data this is harmless (n == 1), but for multivariate data the objective of every candidate was off by the contribution of the first sample, so the chosen split point could differ from the minimizer of the GGS objective. The new implementation agrees with a direct evaluation of log_likelihood on the two parts for every candidate, which is the definition of the split objective; for univariate data it agrees with the previous implementation (same change points, same log-likelihoods up to rounding).
Example (random data, 300 x 2, lamb=1): the direct objective gives split index 100 with gain -98.6250; the new implementation returns (100, -98.6250); the old one returned (100, -98.6907), i.e., a wrong gain, and on other inputs a different index.
Does your contribution introduce a new dependency? If yes, which one?
No.
What should a reviewer concentrate their feedback on?
the bug fix changes results for multivariate data; the new test pins the split to the direct objective.
memory: per block, arrays of shape (block, n, n) are created; the block size is chosen so that this stays around 16 MB.

Reproducible benchmark (loads the old implementation from main):
```
import subprocess, time
import numpy as np
from sktime.detection.ggs import GGS

src = subprocess.check_output(["git", "show", "main:sktime/detection/ggs.py"])
ns = {}
exec(compile(src.decode(), "ggs_main", "exec"), ns)
GGS_old = ns["GGS"]

rng = np.random.default_rng(0)
for n, d, k in [(1000, 3, 5), (5000, 5, 5), (20000, 10, 8)]:
    X = rng.normal(size=(n, d))
    t0 = time.perf_counter(); GGS_old(k_max=k, lamb=1.0).find_change_points(X); t_old = time.perf_counter() - t0
    t0 = time.perf_counter(); GGS(k_max=k, lamb=1.0).find_change_points(X); t_new = time.perf_counter() - t0
    print(n, d, k, f"{t_old:.3f}s -> {t_new:.4f}s ({t_old / t_new:.0f}x)")
```
Did you add any tests for the change?
Yes, in test_ggs.py:
test_GGS_add_new_change_point_matches_objective (univariate and multivariate, two lamb values): the split point and gain equal the minimizer of log_likelihood(data[:i]) + log_likelihood(data[i:]) over all candidates. The multivariate cases fail on main because of the bug above.
test_GGS_add_new_change_point_no_improvement: segments too short to split return (0, 0.0) as before.
Existing tests pass. check_estimator(GreedyGaussianSegmentation) has the same 16 pre-existing failures on main and on this branch (test_output_type, test_predict_points, test_predict_segments, doctest example), unrelated to this change.
