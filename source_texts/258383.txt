Item 1 — #828 GPU blackbody volume emission, device grid cache, RNG keying
One shared formula. include/astroray/volume/blackbody_lut.h is a single
__host__ __device__ luminance-normalised Planck evaluated in log space over
one ln-T table of the pkg122 photopic integral (2048 entries, 30 K…1e6 K,
linear interp, 0 below 30 K). The CPU reads the host table; the GPU uploads
that same vector (gpu_spectral_tables.cu, lazy, only when a medium has
blackbody). Temperature grids upload as a dense block beside the NanoVDB
density buffer; the blackbody term is evaluated in gpu_gridVolumeTrack
under the existing HasGridVolume axis, gated exactly like the CPU
BoundedMedium::emissionAt.
CPU defect fixed (found here). normalizedPlanck formed the ratio with a
FLOAT normaliser: on main it returns NaN for T ≈ 25–140 K (normaliser
overflows to inf, float(planck) underflows to 0) — the cold rim of any
temperature grid. A first fix using a per-kelvin memo was itself wrong
(critic finding): luminance / Cycles intensity was 0.095 @60.5 K, 1.035
@500.4 K, 0.992 @1234.5 K, with a 7 % step across 500.5 K. With the shared
table: 1.0004 / 1.0000 / 1.0001 / 1.0000 / 1.0000 at 60.5 / 500.4 /
1234.5 / 2718.3 / 6543.2 K (tests/test_issue828_blackbody_cpu.py, CPU-only).
GPU↔CPU parity (tests/test_pkg269_gpu_hetero_parity.py, per-channel ROI mean):
blackbody slab 1500 K 0.989 / 0.984; slab 3200 K, I 0.7, tint (1,.8,.6)
0.999 / 0.998 / 1.009; temperature-grid fire with a cold rim 0.998 / 1.002
(blue channel ~0 at 1800 K, excluded). Renders finite on both backends.
test_results/batchQ/issue828_fire_{cpu,gpu}.png. The chromatic absorption slab
also moved closer to Cycles under the new observer: CPU Tr
0.678 / 0.150 / 0.134 vs Cycles 0.687 / 0.153 / 0.135 (was 0.633 / 0.154 /
0.134 under 10°).
Device grid cache. NanoVDB + temperature buffers now ride the Viewport render much slower than F12 and than Cycles; owner observes the scene being re-uploaded to the GPU every frame #801 reuse
decision; clear_grid_media / set_volume_grid / add_homogeneous_medium
invalidate it. New last_render_info()["grid_uploads"] counts host→device grid
copies of the last GPU render, so tests/test_issue828_grid_cache.py gates on
the driver's own counter (2 on an upload render, 0 on reuse, re-upload after
each mutation) instead of an image difference that passed on main too.
192³ density+temperature (56 MB): upload 4.5 ms → reuse 0.8 ms (min-of-7).
RNG keying (GPU volumes follow-up: blackbody volume emission on the GPU, device-side grid cache, 8-media cap (after #820) #828 review note): the free-flight salts are disjoint bit fields
— tracker 0xE | bounce(8) | draw(20), shadow 0xD | bounce(8) | medium(3) | draw(17) — so a long flight can no longer alias into another bounce/medium.
8-media cap: the addon reports it, and only on a GPU render (the CPU
honours every medium).
emissionFloor stays on upload: with blackbody on the GPU a density-free
blackbody medium needs those tentative collisions.

Past the volume-bounce cap the engine ends at the first non-emissive surface;
Cycles continues through TRANSPARENT surfaces
(PATH_RAY_TERMINATE_AFTER_TRANSPARENT). The engine's alpha pass-through is a
shade-stage BSDF lobe a terminated path never reaches, and transparent_bounces
is itself unwired (pkg201 park note).
Both backends return 0 below 30 K (the shared table's floor). At Blackbody
Intensity 1 that is ≤ (30/T)⁴ of a fire's luminance.
Only the nearest medium a ray segment enters is tracked (pkg268/269
behaviour, unchanged here): a second medium further along the same segment is
skipped — e.g. a fire behind a smoke volume's AABB is invisible through it.
Worth a follow-up issue; the corpus/showcase scenes place volumes side by side.
Cycles' total max_bounces also sets terminate-after; the engine's total depth
ends the path loop (pre-existing).
