Issue body actions
When a loop converts half or bfloat to float on RISC-V without zvfhmin / zvfbfmin, the loop vectorizer falls back to a fixed VF and emits a remark that doesn't say which type was rejected, or that enabling an extension would fix it.
Godbolt Link:
https://godbolt.org/z/c1qcv8cWW
To reproduce:
```
void fma_fp16(float *dst, const _Float16 *a, const _Float16 *b, int n) {
    for (int i = 0; i < n; i++)
        dst[i] += (float)a[i] * (float)b[i];
}
```
clang --target=riscv64-unknown-linux-gnu -O3 -mabi=lp64d -march=rv64gcv -S -Rpass=loop-vectorize -Rpass-analysis=loop-vectorize
Remarks with -march=rv64gcv
```
remark: Scalable vectorization is not supported for all element types found in this loop. [-Rpass-analysis=loop-vectorize]
remark: the cost-model indicates that interleaving is not beneficial [-Rpass-analysis=loop-vectorize]
remark: vectorized loop (vectorization width: 4, interleaved count: 1) [-Rpass=loop-vectorize]
remark: floating point conversion changes vector width. Mixed floating point precision requires an up/down cast that will negatively impact performance. [-Rpass-analysis=loop-vectorize]
remark: floating point conversion changes vector width. Mixed floating point precision requires an up/down cast that will negatively impact performance. [-Rpass-analysis=loop-vectorize]
```
The generated loop calls __extendhfsf2 8 times per iteration, with vector spills and reloads around each call.
Remarks with -march=rv64gcv_zvfhmin
```
remark: the cost-model indicates that interleaving is not beneficial [-Rpass-analysis=loop-vectorize]
remark: vectorized loop (vectorization width: vscale x 4, interleaved count: 1) [-Rpass=loop-vectorize]
remark: floating point conversion changes vector width. Mixed floating point precision requires an up/down cast that will negatively impact performance. [-Rpass-analysis=loop-vectorize]
remark: floating point conversion changes vector width. Mixed floating point precision requires an up/down cast that will negatively impact performance. [-Rpass-analysis=loop-vectorize]
```
The loop uses vfwcvt.f.f.v, with no calls.
The same happens for __bf16 without zvfbfmin: the fallback is per-element lhu + shift + vmv.s.x + vslideup.vi.
Impact
Under QEMU (VLEN=256), the baseline fp16 kernel executes about 76x more dynamic instructions than the zvfhmin build, and the bf16 kernel about 17x more than the zvfbfmin_zvfbfwma build. The "not supported for all element types" remark and the "floating point conversion changes vector width" remark look similar, but only the first can be fixed with a flag, and its text doesn't say so.
Suggestion
The check in LoopVectorizationPlanner.cpp (isElementTypeLegalForScalableVector) already knows which type failed. Two possible improvements:
Name the type, e.g. "Scalable vectorization is not supported for element type 'half' found in this loop." This is target-independent.
Optionally, let the target add a reason, e.g. "requires the 'zvfhmin' extension", since RISCVTTI knows which extension makes the type legal.
I'm happy to work on (1) if that sounds reasonable.
Reproduces on trunk (Godbolt link above), 22.1.8, and 23.1.3.
