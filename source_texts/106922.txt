Destination
Produce a re-evaluated rolling roadmap of three to five one-sentence outcome candidates and select exactly one next milestone that is ready to hand to to-spec, grounded in the current implemented engine and the completed robust Vulkan triangle evidence. Treat the dense raster proof as a provisional next outcome until its demonstration, boundaries, interfaces, evidence, risks, and dependencies are resolved.
Notes
Planning and decisions only: do not create implementation tickets, write engine code, publish a draft milestone, apply devlog, or activate a milestone.
Re-evaluate rather than merely repeat Chart the first five demonstrable voxel-engine milestones and Lock the first five milestone outcomes and order.
Use the implementation and retained evidence from Milestone: Robust Vulkan triangle through desktop lifecycle as the starting state. On current main, the Render Backend owns a triangle-specific render pass, graphics pipeline, shaders, and command recording; no Voxel Frontend, Storage Tier, or Render Path is implemented.
Use grilling for human decisions, domain-modeling to protect the canonical language in CONTEXT.md, and codebase-design when placing the Render Backend–Render Path seam.
A selected milestone is ready only when its goal, viewer payoff, completion demo, success criteria, technical shape, risks and rabbit holes, non-goals, and capture plan are supported by resolved evidence.
Keep every later outcome at one-sentence roadmap resolution and treat it as a hypothesis rather than a commitment.
Decisions so far
Place the Render Backend–Render Path seam after the triangle proof — The backend owns Vulkan execution and presentation and drives a small public Render Path lifecycle; paths own strategy-specific GPU state and record through borrowed, bounded contexts.
Bound the read-only Voxel Frontend slice for the dense proof — The dense milestone proves a validated immutable read seam and revision-tagged background raster preparation over a private dense tier; edits, change history, and tier interchangeability remain deferred.
Choose the minimal raster surface strategy for the dense proof — The dense proof builds one revision-tagged whole-volume exposed-face mesh with baked material color and path-owned static indexed GPU buffers, leaving greedy incremental partitioning for the editable milestone.
Revalidate the dense raster demonstration and evidence contract — The dense proof retains the canonical scale ladder but fixes a bounded-surface scene, exact semantic face oracle, revision-attributed responsive lifecycle proof, and reproducible first-frame/frame-time audit bundle.
Shape the dense raster milestone contract — The milestone now coherently joins the validated immutable read seam, revision-tagged whole-volume exposed-face path, Windows lifecycle proof, correctness gates, descriptive baselines, bounded risks, non-goals, and capture evidence.
Select the next milestone and refresh the rolling roadmap — The dense raster proof is selected for to-spec in a four-outcome dependency order; editable raster, portable compute ray, and cross-tier storage independence remain hypotheses.
Not yet specified
None. The refreshed rolling roadmap and selected next milestone are resolved in Select the next milestone and refresh the rolling roadmap.
Out of scope
Engine implementation, source edits, implementation tickets, and file-level implementation plans.
A draft milestone issue, devlog activation, or a planned-work checklist.
Detailed specifications for later roadmap candidates.
Production performance targets unsupported by measured voxel workloads.
Hardware ray tracing, sparse-DAG work, streaming, editor tooling, networking, physics, and gameplay.
