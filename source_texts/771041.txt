Babylon.js allocates a mip chain for a multisampled render target only when the runtime reports supportsMultisampledMipmaps. This check is in ThinNativeEngine._getRenderTargetHasMips, which is already in npm 9.31.3. NativeEngine never reported the capability.
As a result, the glTF transmission helper's opaque scene texture (generateMipmaps + 4× MSAA) loses its mips, and rough refraction samples only mip 0. This is why KHR_materials_volume and the OpenPBR thin-walled transmission IBL test were excluded.
bgfx creates the multisampled surface with a single mip on every backend: D3D11 m_rt2d, D3D12/Vulkan m_singleMsaa*, and Metal m_ptrMsaa. It then generates mips on the single-sample resolve target, so this PR reports the capability as true.
It enables:
GLTF Extension KHR_materials_volume
GLTF Extension KHR_materials_volume with analytic light
OpenPBR Thin Walled Transmission IOR vs Roughness - IBL
Verification: Win32 D3D11 V8, all three pass against BN's existing reference images. Before this change they differed by 3.1%, 6.0% and 4.1%.
The two KHR_materials_volume tests are excluded on JavaScriptCore because on Linux JSC/OpenGL CI createScene does not resolve within 600s (under investigation; they were excluded everywhere before this PR).
bgfx bump: bgfx is updated to the latest upstream (BabylonJS/bgfx 5a0a8926). This fixes two D3D12 bugs exposed by multisampled render targets with mips:
Resolving array layer > 0 used _mip + layer*numMips as the source subresource, but the multisampled source has only one mip per layer. This caused RESOLVESUBRESOURCE_INVALID_SUBRESOURCE_INDEX and device removal.
Write-only color render targets were created with DENY_SHADER_RESOURCE, which D3D12 rejects without ALLOW_DEPTH_STENCIL. The 1x1 write-only target used by SubmitResolveSwitch then had no resource, and FrameBufferD3D12::postReset crashed.
Verified on D3D12 with the debug layer: a 2-layer 4x MSAA render target with mips renders with no resolve errors.
