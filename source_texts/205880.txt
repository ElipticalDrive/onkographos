Split out of #88, where it was the finding rather than one of the listed items.
The number
At the export's real resolution (256), on the benchmark's enclosure:
```
simplify 81%,  contour 15%,  grid 4%,  bounds 0%,  project 0%
```
and simplification takes 1,069,344 triangles down to 50,694.
So the export spends 15% of its time generating a million triangles and 81% of it throwing 95% of them away. Everything in #88 made both halves of that cheaper; none of it made the million triangles unnecessary.
Why the obvious fixes do not apply
Parallelism — QEM edge collapse is inherently sequential. Mesher/export performance: ~22s to export, and bounds re-proved on every edit #88's A4 was measured and gains nothing, partly for this reason.
Faster simplification — Mesher/export performance: ~22s to export, and bounds re-proved on every edit #88's A1 already took the data structures from JS objects and string keys to typed arrays, for 1.35×. There is no second 1.35× of the same kind available.
Skipping empty cells — Mesher/export performance: ~22s to export, and bounds re-proved on every edit #88's A2 was measured: ~2%, because empty cells are cheap. The cost is in the cells that have geometry.
Not decimating — not an option. Decimation is error-bounded at 5% of a voxel and removes 95% of the triangles; without it the STL is twenty times larger for no fidelity gain.
The proposal
evaluateCPUWithProgress already builds an octree and already knows which blocks it could not prove empty — that active-block information is returned today and unused beyond a cheap iteration hint. Dual contouring runs on the dense grid underneath it and emits a quad per sign-changing edge, so a flat face 64 voxels across becomes ~8,000 triangles that QEM then collapses back to 2.
Contouring the octree instead — emitting one vertex per leaf rather than per voxel, with the standard crack-patching between differently-sized neighbours — produces something close to the post-simplification triangle count directly. The interval enclosure that decides subdivision is already sound and already tested, so the octree's structure is trustworthy input.
Why this is not small
Crack-patching across level boundaries is the part that goes wrong, and it goes wrong as holes in an exported mesh.
dualContour's manifold-preserving multi-patch handling (PATCHES, cellBase, the per-edge patch map) all assumes uniform cells.
The QEF vertex placement and the crease-preservation work in simplify.ts would need to keep working against a non-uniform cell size.
Gates that already exist
dualContour.test.ts — watertight, edge-manifold, outward-oriented, two-sheets-in-one-cell, and the crossing-accuracy contract.
simplify.test.ts — sharp-feature and crease preservation.
npm run bench with a committed corpus, so the claim is checkable.
e2e/sdf-parity.spec.ts — unaffected, since this changes the mesher rather than the field.
Worth doing only if export time is still a complaint after #88's work and the resolution setting from #105. Filed so the finding is not lost.

The proposal above does not work, and here is the measurement
evaluateCPUWithProgress already builds an octree and already knows which blocks it could not prove empty ... Contouring the octree instead — emitting one vertex per leaf rather than per voxel
I wrote that without checking what the octree's leaves actually are. They are voxels.
Instrumented subdivide's leaf-size distribution, res 192, Open-Top Enclosure — an object that is essentially six flat faces and some fillets:
```
size  64:        2
size  32:       64
size  16:      360
size   8:      884
size   4:   20,644
size   2:   74,504
size   1:  612,032   <-- 86% of all leaves
```
612,032 voxel-level leaves, against 602,496 triangles out of the contour. Essentially one-to-one. The octree is already fully subdivided along the entire surface, and it has to be: the stop test at gridEval.ts:110 is enclosure.lo > 0 || enclosure.hi < 0, which asks "might the surface be in this block", not "is the surface curved here". A block straddling a perfectly flat face contains the surface, so the interval contains zero, so it recurses — all the way down.
So there is no adaptivity in this octree to harvest. "Emit one vertex per leaf" and "emit one vertex per voxel" are the same thing on the case this issue is about. Same failure mode as #88's A2 and A4 and #89's item 7: the issue assumed a structure already carried the information, and it did not.
What the cost actually is
Re-profiled while I was in here (res 192, enclosure, 602,496 input triangles):
```
quadrics + adjacency + heap seed      971 ms    setup
collapses at ZERO error             ~3730 ms    602,496 -> 43,848 tris
collapses within the 5% budget       ~754 ms     43,848 -> 29,856 tris
```
93% of the input is collapsed at zero error — those triangles carry no information at all. That part is real and does support this issue's motivation. But it also means the previous framing ("simplification is 81%, make it cheaper") was pointing at the wrong lever, and so was mine.
#118 took the bookkeeping out of that middle row (1.22× here, output verified bit-identical). What is left is genuine QEF math per neighbour per collapse, so there is no more to win without generating fewer triangles.
What the work actually is
Adaptive contouring needs a second subdivision criterion the octree does not currently compute — stop descending when the surface inside the block is well approximated by one plane, i.e. a QEF residual or normal-variation test — and then Ju et al.'s bottom-up node collapse plus the cellProc/faceProc/edgeProc recursion that makes the result crack-free by construction.
That is a substantially bigger and riskier piece of work than "reuse the octree we already have", which is what this issue currently claims. The gates listed at the bottom are still the right ones, and the failure mode is still silent holes in an exported mesh.
Retitling and rescoping this rather than leaving the misleading premise in place. Not starting it on the strength of the numbers above alone — the honest next step is a prototype that reports triangle count and watertightness before anything is wired into the export path.

Built a throwaway prototype that answers the one question worth answering before anyone writes crack-patching: if the octree were collapsed bottom-up by QEF residual (Ju et al. 2002), how many vertices would survive? It builds hermite data per surface cell, merges QEFs up the octree, and collapses a node when one vertex still fits within the same error budget the simplifier uses. It does not produce a mesh — it counts.

Fidelity is RMS distance of each mesh's vertices from the true SDF surface, in voxels. Max error was identical to production on every preset, and adaptive came out better than QEM on two of them.
So the original claim — that this "produces something close to the post-simplification triangle count directly" — holds. It lands within 1.3–3.0x of what QEM achieves, at the same fidelity, without generating the million triangles first.
A wrong turn worth recording
My first run of this said the opposite: 3–5x worse than QEM on vertex count and ~10x worse on fidelity, which read as a clear "close this issue".
That was entirely an artefact of the prototype. It used a single linear interpolation for edge crossings where dualContour.ts uses 4 iterations of Illinois false position, and a gradient epsilon of voxel * 0.5 where production uses min(dx,dy,dz) * 0.01 — 50x too large. The tell was that the reported error did not move at all across a 16x sweep of the collapse budget, which meant it was not coming from collapsing.
It polluted both metrics at once, and not in the same direction: bad crossings put vertices further from the surface and inflated the QEF residuals that decide whether a node may collapse, so it under-collapsed and looked inaccurate. Fixing the crossings alone took Wall Bracket from 10,548 surviving vertices to 2,716.
Worth stating plainly because the failure mode is generic: a prototype that approximates the thing it is measuring against will flatter or condemn it for reasons that have nothing to do with the question.
What is still unproven
The numbers above are the best case, and the risky part is untouched:
No topology or manifold checks. A real implementation needs them and they only ever prevent collapses, so true counts are somewhat higher than these.
No mesh is produced. Crack-patching between differently-sized neighbours — the part that fails as holes in an exported STL — is not prototyped at all. Watertightness is completely unmeasured.
Vertex-to-surface distance is a lower bound on mesh error: a mesh can have every vertex on the surface and still bulge between them.
Where that leaves the issue
The sizing case is now made: the mesher would generate 2.4–23.7x fewer vertices, so simplification — ~80% of export time at res 256 — would receive proportionally less input. That is worth doing.
The correction from my previous comment stands unchanged: the existing octree carries no adaptivity to harvest (86% of its leaves are single voxels), so this still needs a planarity subdivision criterion plus crack-free cellProc/faceProc/edgeProc recursion. What has changed is that the payoff at the end of that work is now measured rather than assumed.
Next step, if this is picked up: prototype the crack-free contouring itself and run it against dualContour.test.ts's existing watertight / edge-manifold / outward-oriented gates. Those gates already exist and are the ones that would catch the failure mode.

Prototype passes every gate, and there is a way to do this without crack-patching
Built the contouring prototype. It passes all of dualContour.test.ts's gates on analytic shapes and on five presets, and it is 1.0–2.4x faster end to end.
The important part is that it avoids the risk this issue was blocked on.
Octree vertex clustering instead of adaptive recursion
Ju et al.'s adaptive dual contouring needs cellProc/faceProc/edgeProc recursion with fiddly index tables, and its failure mode is holes in an exported STL. That is what made this issue "not small".
That machinery turns out to be avoidable. Quads are already emitted per sign-changing grid edge, each referencing four cells through vertexFor (dualContour.ts:326). If cells inside a collapsed octree node simply hand back the same vertex, connectivity is untouched: there is still exactly one quad per sign-changing edge and neighbouring quads still share endpoints. The output is a quotient of a mesh that was already watertight, so cracks cannot arise by construction — there is nothing to patch.
Ring corners that collapse together are dropped in place, preserving winding; a ring with fewer than three distinct vertices had no area and is never emitted. That is where the triangle count actually falls — the quad is not removed by a later pass, it is never created.
The real risk moves from cracks to manifoldness, when two surface sheets land in one node. Handled by never letting a multi-patch cell join a cluster, which is the same reason dualContour splits patches in the first place.

Caveats
The prototype's contour stage is slower than production's (2,863 vs 2,160 ms on Wall Bracket) because clustering is bolted on with Maps and extra passes. All the win currently comes from simplification, so a real implementation should be faster than these numbers, not slower.
It contains at least one thing that would not survive review: positions.push(...newPos) blows the stack on large meshes.
Measured at res 64 and 128 only. The export runs at 256, where simplification's share is larger — the win should be bigger there, but that is extrapolation, not measurement.
Gates run are the existing ones. A production change needs the full suite, the golden images, and the bench corpus.
Where this leaves the issue
The approach is viable and the risk is far lower than this issue assumed, because the crack-patching can be skipped entirely. Worth building properly.
