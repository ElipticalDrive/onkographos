Summary
Replaces the engine's hardcoded per-face brightness multipliers with a Lambert + ambient shading model driven by a single global directional sun, and unifies shadows / lights across the voxel-pool and SDF rendering paths.
Global sun. RenderManager owns sun direction / intensity / ambient. All voxel and SDF surfaces read the same FrameDataSun UBO each frame. Default sun direction (0.3, 0.2, -0.93) recovers the Z>X>Y face-shading order the old hardcoded multipliers gave us.
All C_LightSource types implemented. POINT, SPOT, DIRECTIONAL previously did nothing; they now flow through COMPUTE_LIGHT_VOLUME and LIGHTING_TO_TRIXEL. DIRECTIONAL entities override the global sun for that canvas.
Unified shadow paths with voxel-pool / SDF parity. Voxel pool uses occupancy-grid ray march; SDF uses analytic shape march. Both now exclude self-cells the same way: SDF via selfEntityId skipping in the analytic walk, voxel-pool via a per-entity bbox table built each frame in system_build_occupancy_grid and uploaded to a new OccupancyEntityBoundsBuffer SSBO. Top and side faces of voxel-pool cubes match the SDF cube's shading at all zoom levels (was self-shadowed at zoom ≥ 4 before this fix).
Caster culling + alloc-free reuse. SDF caster collection frustum-culls + sun-cone-culls and reuses scratch vectors — no per-frame allocations, no CPU dirty-flag bookkeeping.
Nine IRLighting* demos sharing one lighting_demo_scene.hpp scaffold (AO / SunShading / SunShadow / Emissive / Point / Spot / Directional / Combined / DebugOverlays). Each demo renders a voxel-pool row and an SDF row anchored to the floor so the two paths compare visually at every zoom.
+Z direction reconciled. AGENTS.md and the iso-basis docs now say +Z = down (gravity / iso-screen-down), validated against code (sdfCone, voxel-pool floor anchoring, Z_FACE outward normal (0, 0, -1)).
Engine baseline updated. docs/agents/CLAUDE-BASELINE.md codifies a "no CPU-side dirty flags" preference — prefer culling, alloc-free reuse, and GPU-side computation.

DIRECTIONAL entities override the global sun for that canvas, with
defaults that match the global so creations that don't customize see
no visible change.

Shadows handle voxel-pool and SDF surfaces consistently:

- Voxel pool: occupancy-grid ray march in `c_compute_sun_shadow.glsl`,
  rebuilt each frame from `C_VoxelPool` only (shape descriptors no
  longer pollute the grid).
- SDF: analytic shadow march against `shapeCasters[]`, fed by a CPU
  collector that frustum-culls + sun-cone-culls casters and reuses
  scratch vectors alloc-free.
- Both paths share the same `pos3D` reconstruction, with a 0.5-voxel
  shift along the face's outward normal so subdivision-mode
  sub-pixel offsets on X / Y faces don't self-shadow against the
  surface voxel itself (the bug that made voxel-pool tops dark at
  zoom ≥ 4).

scaffold (AO, sun shading, sun shadow, emissive, point, spot,
directional, combined, debug overlays). Each demo renders a row of
voxel-pool shapes and a row of matching SDF shapes anchored to the
floor, so the two paths can be compared visually side-by-side at
every zoom level.

Reconciles `AGENTS.md`'s +Z convention with code reality: +Z is
**down** (gravity / iso-screen-down), not up. Validated empirically
against `sdfCone` orientation, voxel-pool floor anchoring, and
`Z_FACE` outward-normal `(0, 0, -1)` in the lighting shader.

Codifies a "no CPU-side dirty flags" preference in
`docs/agents/CLAUDE-BASELINE.md`: prefer culling, alloc-free reuse,
and GPU-side computation over per-frame dirty bookkeeping. The new
shadow-caster collector and occupancy-grid build follow this rule.

`light_volume_test`, `sun_direction_test`, `sun_lighting_test`,
`sdf_test`. Extracts SDF helpers into `engine/math/.../math/sdf.hpp`

Voxel-pool entities populate the occupancy grid with their own voxels,
so the sun-shadow occupancy march was treating the surface voxel as
its own occluder — top and side faces of a voxel-pool cube ended up
self-shadowed at higher zoom levels, while the SDF cube next to it
rendered cleanly. Earlier face-aware origin shifts patched the most
common case but rounded back into the surface voxel for some sun
directions, so the fix is to mirror the analytic path's
selfEntityId-based exclusion instead of fighting the rounding.

`system_build_occupancy_grid` now reads each contributing voxel's
owner entity from `C_VoxelPool::getEntityIds()` (already populated by
`system_update_voxel_set_children`) and accumulates a per-entity
bbox in world-cell space. The packed list is uploaded to a new
`OccupancyEntityBoundsBuffer` SSBO at slot 4, and the count is
forwarded to the shadow shader through `FrameDataSun`. The shader
linear-scans the (small) list to find the surface entity's bbox and
skips occupancy hits that fall inside it during the march. The
analytic SDF path is unchanged.

Removed the now-unused face-derived `pos3D` shift in both the GLSL
and MSL shaders so SDF and voxel-pool surfaces use the same ray
origin (the reconstructed pos3D plus one sun-direction step).

Layout test for `FrameDataSun` updated for the new
`occupancyBoundsCount_` slot, and a new layout test pins
`GPUOccupancyEntityBounds` at 48 bytes / std430 packing. All 348
tests pass.

Verified visually with `IRLightingSunShadow --auto-screenshot` at
zoom 2 and 4: the voxel-pool cube (left) and the SDF cube (right)
now have matching face shading and matching floor shadows. See
`docs/pr-screenshots/claude-lighting-fidelity-polish/voxel-sdf-parity/`.

diagnosing other lighting bugs and brings AO into parity between

Praise
The voxel-pool self-shadow fix via OccupancyEntityBounds SSBO mirrors the analytic path's selfEntityId exclusion cleanly. The approach avoids per-face heuristics (pos3D.z -= 0.5) that broke at zoom ≥ 4 for some sun-direction signs.
ir_sdf_common.glsl / ir_sdf_common.metal as a single authoritative source for the SDF dispatch eliminates the ~210-line duplication between c_shapes_to_trixel and c_compute_sun_shadow. The comment block enumerating the four update sites for new shapes is the right forward guide.
FrameDataSun has a static_assert(sizeof == 48) — the size is correct (16+4+4+4+4+4+4+4+4 = 48 bytes). GPUOccupancyEntityBounds similarly asserts 48 bytes. Both match their shader-side std140/std430 counterparts.
Lighting invariant #1 (grid-build iterates full pool, not the render-culled subset) is compliant: system_build_occupancy_grid.hpp does not include cull_viewport_state.hpp and does not call visibleIsoViewport. The SDF rasterization inner loop is also camera-independent.
348/348 tests pass with six new test suites (GPUOccupancyEntityBoundsLayout, frame_data_sun_layout_test, light_volume_test, sun_direction_test, sun_lighting_test, sdf_test).
Needs Opus to verify
1. system_compute_sun_shadow.hpp:313-328 — beginTick vs endTick ordering for frameData update.
The third lambda passed to createSystem<...>() at line 313 updates frameData.sunDirection_ and calls detail::resolveSun(). The per-entity tick at line 254 reads frameData.sunDirection_. If the third arg is the endTick (fires AFTER per-entity ticks), then on each frame the per-entity tick reads sun data from the PREVIOUS frame's endTick — a one-frame lag. If it's the beginTick, the order is correct. Sonnet cannot resolve this from reading the system CLAUDE.md alone. Opus should confirm the createSystem API wiring.
2. system_build_occupancy_grid.hpp:61-64 + system_compute_sun_shadow.hpp:327 — inter-system state coupling via detail::occupancyEntityBoundsCount().
BUILD_OCCUPANCY_GRID sets a function-local static int s_count (via detail::occupancyEntityBoundsCount()); COMPUTE_SUN_SHADOW's beginTick reads it to populate frameData.occupancyBoundsCount_. This is the T-064 anti-pattern applied across two system headers — the coupling is invisible without reading both includes. Opus should assess whether this should be moved to a field on C_OccupancyGrid (set by the build system, read by the shadow system via ECS), or whether the current approach is an acceptable pragmatic exception.
3. system_compute_sun_shadow.hpp:226-228 — resource-creation ordering dependency.
s_occupancySSBO = getNamedResource<Buffer>("OccupancyGridBuffer") succeeds only if system_build_occupancy_grid::create() already ran (it creates that named resource). There is no API-level enforcement of this ordering; it relies on registration order in registerPipeline(). A creation that registers COMPUTE_SUN_SHADOW before BUILD_OCCUPANCY_GRID will crash at runtime with a null dereference. Opus should confirm whether this is guarded elsewhere or is an acceptable documented invariant.
Nits
system_build_occupancy_grid.hpp:87-95 — four new function-local statics (s_boundsSSBO, s_boundsByEntity, s_boundsUpload, detail::occupancyEntityBoundsCount()). system_compute_sun_shadow.hpp:197-232 adds two more (frameData, shapeCastersByCanvas). These are all new additions in this PR, adding to the T-065 migration surface. They follow the existing pattern in the 12-file deviation list but expand it.
system_compute_sun_shadow.hpp:304-306 — comment "Assumes a single matching canvas per frame. Switch to += with a beginTick reset if the filter ever matches multiple entities." This is a correctness note for a real latent bug path. Worth filing as a follow-up issue given that multi-canvas lighting demos are an explicit goal.
system_build_occupancy_grid.hpp:287-292 — the IR_ASSERT(false, ...) + break for the 256-entity overflow: in a release build where asserts are stripped, the loop silently stops uploading bounds. The comment says "bump the constant if a creation needs more" which is the correct fix, but a warning log before the assert would help diagnose the issue in release builds.

Opus recheck — render: lighting fidelity polish — global sun, unified shadows, demos
Verdict: approve (concur with Sonnet, with two additional nits)
Sonnet handed Opus three specific concerns plus the broader "math through the shadow march and inter-system occupancyEntityBoundsCount() coupling." I traced all four end-to-end, plus GLSL ↔ Metal parity across every touched shader, and the FrameDataSun UBO layout across the four sites that bind it. The PR lands cleanly. Two small additional nits below.
Concur — Sonnet's three Opus questions all resolve
1. system_compute_sun_shadow.hpp:313-328 — second lambda IS beginTick (no one-frame lag).
createSystem at engine/system/include/irreden/ir_system.hpp:14-37 defines the parameter order as (name, functionTick, functionBeginTick, functionEndTick, ...). The third argument to createSystem<...>(...) here is the begin-tick. Per-frame ordering for COMPUTE_SUN_SHADOW is therefore:
beginTick — s_program->use(), clear shapeCastersByCanvas, resolveSun(), write frameData.sunDirection_ / sunIntensity_ / sunAmbient_ / shadowsEnabled_ / aoEnabled_ / occupancyBoundsCount_ (the last from IRSystem::detail::occupancyEntityBoundsCount(), which BUILD_OCCUPANCY_GRID's per-entity tick has already populated this frame — see point 2).
Per-entity tick — reads frameData.sunDirection_, collects + uploads casters, dispatches.
frameData is fresh by the time the per-entity tick reads it. No one-frame lag.
2. Inter-system detail::occupancyEntityBoundsCount() static — the value is fresh under the current pipeline order.
I traced the full RENDER pipeline order (engine/render/CLAUDE.md "the pipeline, one frame"):
```
BUILD_OCCUPANCY_GRID   →   COMPUTE_VOXEL_AO   →   COMPUTE_SUN_SHADOW   →   COMPUTE_LIGHT_VOLUME   →   LIGHTING_TO_TRIXEL
```
Each system fires beginTick → all per-entity ticks → endTick before the next system runs. So:
BUILD_OCCUPANCY_GRID's per-entity tick (line 99-305) sets detail::occupancyEntityBoundsCount() = static_cast<int>(s_boundsUpload.size()) after every populate+upload.
COMPUTE_SUN_SHADOW's beginTick (line 313-328) reads it via frameData.occupancyBoundsCount_ = IRSystem::detail::occupancyEntityBoundsCount().
By the time COMPUTE_SUN_SHADOW's beginTick fires, BUILD_OCCUPANCY_GRID's per-entity tick has already run, so s_count is the current frame's value. Correct.
This is the T-064 anti-pattern (function-local static for system state, invisibly coupled across two system headers) and the count would be cleaner as a field on C_OccupancyGrid (set by build, read by shadow). Sonnet flagged this and so do I — it should be folded into the T-065 sweep, not fixed here. The PR doesn't make the deviation list materially worse and the existing convention in this file (s_shapeBuf, s_shapeTileDescBuf) is the same shape.
3. Resource-creation ordering — same pattern used elsewhere; not a new risk.
Both system_compute_voxel_ao.hpp:47 (OccupancyGridBuffer) and system_lighting_to_trixel.hpp:106 (ComputeSunShadowFrameData) already do cross-system getNamedResource lookups against buffers another system created. The convention is: pipeline registration order (= createSystem<NAME>() call order) satisfies the create-resource dependency, because the C++17 brace-init-list in registerPipeline({...}) evaluates left-to-right and each createSystem<NAME>() runs the corresponding System<NAME>::create() synchronously. The PR documents this in system_compute_sun_shadow.hpp:11-14 ("Pipeline order: must run after BUILD_OCCUPANCY_GRID").
system_compute_voxel_ao.hpp:50-58 actually goes a step further and defers the ComputeSunShadowFrameData lookup into the lambdas (because AO is constructed before sun-shadow in pipeline order, so the resource doesn't exist at AO's create-time). That's a clean handling of the same pattern. No action needed for this PR.
Concur — math through the shadow march
I worked the BOX-vs-rasterizer convention end-to-end because it's the obvious place a 0.5-voxel inflation could sneak in: the rasterizer applies params - 1 for BOX (c_shapes_to_trixel.glsl:455-458, mirrored in .metal:491-493) and the CPU SDF occupancy rasterization applies IRMath::SDF::effectiveParams (system_build_occupancy_grid.hpp:209-210), but the new analytic shadow march in analyticShapeShadowHit passes shape.params directly to evaluateSDF. The math actually lines up correctly — the threshold values cancel the halfSize differential:
Rasterizer: halfSize = (params-1)/2 = 3 for params=7. Cells carved where sdfBox(cell, 3) ≤ 0.5 → continuous extent [-3.5, 3.5].
Occupancy grid (CPU SDF): same effective = params-1 = 6, halfSize = 3, cells set where sdfBox(cell, 3) ≤ 0. Same 7 cells per axis.
Analytic shadow: halfSize = params/2 = 3.5, hit when sdfBox(p, 3.5) ≤ 0.05 → continuous extent [-3.55, 3.55].
Difference: 0.05 voxels (the analytic threshold itself) past the geometric cell edge. Both representations describe the same continuous surface; the rasterizer's 0.5 threshold thickens its cell-center surface to the cell-edge boundary, and the shadow's 0.05 threshold matches that cell-edge boundary directly. Brilliantly, this also means SPHERE / CYLINDER / CONE / TORUS — none of which need the -1 conversion — also work consistently across rasterizer and shadow because the same threshold-vs-halfSize relationship holds. No 0.5-voxel inflation. No bug.
Concur — GLSL ↔ Metal parity is clean
I diffed every touched shader pair (c_compute_sun_shadow, c_compute_voxel_ao, c_lighting_to_trixel, c_shapes_to_trixel, ir_iso_common, ir_sdf_common). The Metal mirrors are functionally identical: same roundHalfUp (floor(x + 0.5) on both sides — matches IRMath::roundHalfUp at engine/math/include/irreden/ir_math.hpp:56-58), same evaluateSDF dispatch, same DDA cell-edge logic, same faceOutwardNormal returning the -X / -Y / -Z outward normals consistent with +Z = down and the iso view-direction (1,1,1).
FrameDataSun UBO layout is consistent across every binding site — verified via test/render/frame_data_sun_layout_test.cpp pinning offsets at 0/16/20/24/28/32/36 and total size 48. The c_compute_sun_shadow shaders correctly label the field at offset 36 as padding (the shader doesn't read it; aoEnabled_ is consumed only by c_compute_voxel_ao); cosmetic naming inconsistency only.
Concur — Sonnet's three nits
All three are correct and worth carrying forward as nits, not blockers:
New function-local statics expand the T-065 migration surface (six new sites this PR).
The "Assumes a single matching canvas per frame" comment is correctness-relevant and worth a tracked follow-up given the multi-canvas lighting demos goal.
The 256-entity overflow IR_ASSERT(false, ...) silently breaks in release builds — a spdlog::warn (or whatever the convention is for "soft warning fired during release-build hot path") before the break would help diagnose silent-truncation symptoms.
Additional Opus nits
system_compute_voxel_ao.hpp:108-123 partial subData write is fragile. AO's beginTick writes only aoEnabled_ at offsetof(FrameDataSun, aoEnabled_) to the shared ComputeSunShadowFrameData buffer. The other fields in the buffer carry over from the previous frame's COMPUTE_SUN_SHADOW beginTick. This works today because c_compute_voxel_ao reads only aoEnabled — but the partial-update pattern is invisible from the CPU-side struct definition, and a future change adding a new field that AO needs would silently read stale data. Worth a short comment block at the AO beginTick lambda saying "AO only writes aoEnabled_; other fields are stale-from-last-frame and AO must not read them. Sun-shadow's beginTick is the authoritative writer."
system_compute_light_volume.hpp:86-88 allocates std::queue and std::unordered_set per light per frame. floodFillEmissive constructs both inside the per-light callback, and visited.reserve(radius³) allocates fresh per call. Demo-scale fine; production gameplay with N lights × 60 fps will see noticeable allocator churn. The PR description already flags GPU wavefront BFS as deferred (#358 / #360 / #361 et al.) so this is tracked. Worth adding a thread-local scratch (queue + set) at namespace scope to short-circuit the alloc, even before the GPU rewrite — follow-up not blocker.
Verdict
approve. Mainline math is correct end-to-end (rasterizer ↔ occupancy ↔ analytic shadow all converge on the same continuous surface across BOX / SPHERE / CYLINDER / CONE / TORUS); GLSL/Metal parity is clean; UBO/SSBO layouts pinned by tests; the inter-system static-state coupling works under the current pipeline order and is the right thing to fold into T-065 rather than fix here. The voxel-pool/SDF self-shadow fix via OccupancyEntityBounds SSBO mirrors the analytic path's selfEntityId exclusion correctly. fleet:needs-linux-smoke already correctly applied (render PR authored on macOS); the OpenGL backend is the lagging side that needs cross-host validation before merge.
