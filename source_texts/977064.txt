Problem
crates/simulation/src/explosion.rs plan_blast scanned the full radius AABB (world.block HashMap lookup per cell — up to 13,824 cells at the max authored 12 m blast radius, crates/game_packages/src/lib.rs blast_spec bound) and then ran world.raycast for each of up to 3 axis faces on every in-sphere candidate. Interior voxels — the large majority — still paid a full DDA (each step another HashMap lookup) that inevitably terminated on a nearer neighbour voxel. Up to two detonations per server tick.
Fix
Build a dense Vec<u8> occupancy snapshot of the blast AABB once (u8::MAX sentinel for unloaded chunks, preserving block()? short-circuit semantics). The candidate scan reads it instead of the chunk HashMap.
Before raycasting a Target::Grid face, look up the voxel immediately across that face toward the blast. That voxel is provably the last interior cell the DDA enters before the reach distance (the face-center endpoint is strictly inside the shared face square). Solid → the march hits it first, so the face can never be the first hit; unloaded → the march returns None. Either way the face is invisible and the raycast is skipped — interior voxels cost one array read.
Remaining LOS work (exposed faces, body faces, player exposure samples) uses a local raycast_block, a line-for-line port of VoxelWorld::raycast's DDA — same normalization, step, axis-tie ordering, None-on-unloaded short-circuit, and bound checks — reading the occupancy grid with a world.block fallback for cells outside the snapshot. It returns the first solid cell, so hit.block == cell becomes hit == Some(cell).
Result is identical: same destroyed voxels, same affected bodies/players, same ordering. Dynamic-body pre-filtering from the sibling PR is untouched. Verified: cargo check -p simulation clean, zero warnings.
