The two follow-ups, as shipped
#1038 — GPU per-view ordering. Cull, LOD and the back-to-front sort are two
compute dispatch groups feeding glDrawArraysIndirect, with no readback on the
frame path. The sort is bitonic, not the radix the issue proposed, and that
is a deliberate trade of asymptotics for provability: a radix only replaces the
CPU reference if it is stable, and a stable GPU radix needs per-tile ranking
that is easy to get subtly wrong. Ordering on the pair (complemented depth
key, unique cloud index) is a total order, so stability is not a property the
sort needs — exactly one permutation is correct, and the parity test asserts
index-for-index equality rather than "same set, roughly ordered". ADR §3.3 says
what a radix would still buy and why it remains the right endpoint.
#1039 — hierarchical LOD by merging. No ranking function fixes the selection
budget: the property that matters, a region's total integrated opacity, is not a
property any single splat has, so it cannot be preserved by choosing among them.
Clusters are replaced by one Gaussian matching their moments — mass, mean, and
the second moment about that mean including the parallel-axis term. At a
quarter of the splats, same pose, same classifier:

Ride-along finding — and a correction to it
.ply is already registered as AssetType::MeshSource, so a Gaussian-splat PLY dropped in the
Content Browser is routed to assimp. I first wrote that it imports as a point mesh and silently
loses everything but x y z. That was inferred from reading AssetExtensions.cpp, never tested,
and it is wrong. Running the fixture through assimp with the engine's own import flags:
```
ASSIMP Error: Validation failed: Mesh  contains no faces
```
The scene comes back NULL and Model::LoadModel returns with no model. Dropping
aiProcess_ValidateDataStructure does not change the outcome, only the message ("No output
meshes: all meshes are orphaned and are not referenced by any nodes"), because a splat cloud is
vertices with no faces and the mesh path has nothing to keep.
So the real failure mode is a confusing error, not silent data loss — materially less severe
than I claimed. It is still why the importer stays out of the asset registry, and still why a real
feature has to discriminate on file content (an f_dc_0 property) rather than on the extension; but
it is a message problem to fix alongside the asset type, not a correctness bug to fix now. ADR 0018
§4 and §6 and notes-editor-and-assets.md are corrected, including a note about the write-up
mistake itself — a claim about what an importer does is cheap to verify and easy to get backwards.
Review guide
Where I'd look hardest
OloEditor/assets/shaders/tests/SplatSpike_BitonicSort.comp — the network's
2t - (t & (j-1)) pair mapping, the (lo & k) direction taken from the
global index in the tile-local pass, and the starting j being passed in
rather than assumed to be kTile/2. That last one is subtle: for a small k
the network has no steps above k/2, and starting at the tile width anyway
runs compare-exchanges the algorithm does not contain and silently returns an
unsorted array.
OloEngine/src/OloEngine/Renderer/Splat/GaussianSplatLod.cpp —
WithVarianceFloor. A splat too flat to pack has determinant zero, weighs
nothing, and gets erased by the first coarsening; the mass test cannot catch
it because its baseline uses the same function. The floor has to apply to the
merged covariance too, because a cluster of coplanar splats is itself
rank-deficient.
SplatSpike_Cull.comp against GaussianSplatView.cpp — a textual mirror,
and the parity test compares sort keys bitwise, so the depth expression is
written longhand on both sides to keep the association identical.
What I verified, and how — named above. The check that would have failed if
the ordering were wrong is GpuOrderedFrameMatchesTheCpuOrderedFrame, and it
did fail, at 11.7/255, until a real bug was fixed: a UniformBuffer claims its
binding point at construction, so the ordering rig's camera UBO silently took
binding 7 from the evidence test's own and the CPU-ordered frame was drawing
through a buffer nothing wrote.
Least confident about — the GPU timings, which moved by up to 4× across runs
on a machine that was building other worktrees; hence a range rather than a
figure, and hence a conclusion phrased to survive the slow end. Second: the
kMinVariance floor of 6e-8 is set to the half denormal limit, which is the
right reason but is only exercised by a synthetic test, not by a real scan
with genuinely flat splats.
Deliberately not tested — Vulkan beyond compiling the shaders. The prototype
binds five SSBOs and two UBOs to fixed binding points, which is exactly the model
the heap-bindless Vulkan backend does not have (ADR 0010/0011). Named as
remaining work in ADR §6. Also untested: any interaction with the engine's own
passes, because by design there is none — see the contract table.

…ype, decision record (#971)

#971 asked for a constrained viability spike, not a feature, and the answer it
wanted is a recommendation backed by measurements. The recommendation is
"proceed with constraints, and not yet", and ADR 0018 is where it lives.

What decided it: correct compositing needs the whole visible cloud re-sorted
from the eye every frame. Measured in Release on this box, that per-view pass is
2.6 ms at 100 k splats and 16.6 ms at 500 k — a whole 60 Hz frame — while
published 3DGS captures of one room are 1–6 M splats. Nothing about the quality,
the memory (32 B/splat, 7.8× smaller than the source PLY) or the GPU raster cost
(1.8× an equivalent opaque pass) argued against splats. One pass on the wrong
processor did.

So this lands the spike and stops there: a PLY importer and its CPU ordering
pass, an EWA rasteriser under assets/shaders/tests/, a checked-in fixture with
its generator, CPU contract tests, and rendered evidence from four poses. It is
wired into no scene, no component, no asset registry entry and no production
shader binding, and ADR 0018 §4 states every interaction it does NOT have —
shadows, depth writes, collision, probes, serialization, Vulkan — so the
prototype cannot drift into a half-feature.

Two negative results are pinned by tests rather than left in prose: the
screen-area × alpha budget does not degrade gracefully (it deletes the faint
diffuse mass and keeps the bright detail — 98 % of the shell gone at a quarter
budget, 84 % of the discs kept), and the radix sort is not measurably faster
than std::stable_sort on the CPU; it is kept only because it is the formulation
that ports to a GPU sort.

Also fixed on the way: `.ply` was already registered as `AssetType::MeshSource`,
so a splat PLY dropped in the Content Browser is read by assimp as a point mesh
and silently loses everything but x y z. That is why the importer stays out of
the registry, and the general rule is now in notes-editor-and-assets.md.

…ount, half overflow, biased control (#971)

Six findings from the Phase 3 self-review, all real, all folded in here rather
than left for CodeRabbit.

Two are safety bugs in the importer, both of the shape "the contract says it
returns a LoadResult and it doesn't":

* `element vertex` is untrusted, and the five per-property arrays were sized
  from it three lines BEFORE the payload-length check. A 250-byte file
  declaring 4294967295 vertices reserved ~240 GB and died on std::bad_alloc.
  The length check now runs first, bounded by the minimum bytes a record can
  occupy in each format.
* `Build`'s parallel-array precondition was only an `OLO_CORE_ASSERT`, which
  compiles out entirely outside `OLO_DEBUG` — a Release caller with mismatched
  spans read out of bounds. It now returns an empty cloud, with the assert kept
  to name the bug in a debug build.

One is a silent-drop bug in the packing: a covariance term above 65504 became
+inf through `packHalf2x16`, so `ConservativeSigma` was inf, `depth - radius`
was -inf, and the splat vanished from EVERY camera with nothing logged. Terms
are clamped to the half range now.

One biased a number the ADR quotes. The opaque control indexed `b_Splats`
directly while being drawn `survivors` times, so it rasterised a PREFIX of the
cloud rather than the culled set — a different set covering a different area,
which is not a control. It reads the same order buffer now. The measured ratio
barely moved (1.8x at 500k either way, and the culled fraction was under 1 %),
but the claim it supports is only true of the fixed version.

One was a documented direction that was backwards: `DepthSortKey` mapped a
non-positive or NaN depth to 0 while calling that "the far end". In a
DESCENDING sort 0 is the NEAR end, drawn last, on top of everything. It maps to
0xFFFFFFFF now, so a degenerate splat is drawn first and painted over. Not
reachable today (the near-plane test filters those splats first), but the
function is exposed for reuse.

The last was a dead ADR link in a header comment.

Three tests added for the new behaviour: the lying vertex count, the half-range
clamp, and the corrected sentinel direction. 22 splat tests pass; the 232-test
Shader*/AssetContentValidity sweep is unchanged.

…0018 reverses to proceed (#1038, #1039)

The two preconditions ADR 0018 named before Gaussian splats could be a
supported asset type, implemented and measured. Both landed, so the ADR now
concludes the opposite of what it did three commits ago — and the measurement
was the argument in both directions.

#1038, GPU per-view ordering. Cull, LOD and the back-to-front sort move into
two compute dispatch groups feeding glDrawArraysIndirect, with no readback on
the frame path. Measured on this box:

    splats      CPU (1 thread)   GPU      speed-up
      4,096      0.14 ms         0.085     1.6x
    100,000      2.60 ms         0.262     9.9x
    500,000     16.55 ms         0.506      33x
  2,000,000    155.3  ms         4.683      33x

16.55 ms was the number that said "do not proceed": a whole 60 Hz frame for
500 k splats when published captures are 1-6 M. 0.506 ms is not.

The sort is bitonic, not the radix the issue proposed, and that is a deliberate
downgrade in asymptotics for an upgrade in provability. A radix is only a
drop-in for the CPU reference if it is STABLE, and a stable GPU radix needs
per-tile ranking that is easy to get subtly wrong. Ordering on the PAIR
(complemented depth key, unique cloud index) is a total order, so stability is
not a property the sort needs to have — exactly one permutation is correct, and
the parity test asserts index-for-index equality with the CPU rather than "same
set, roughly ordered". It holds on four poses, eight counts straddling the
padding boundary, and a cloud where every depth is bit-identical.

#1039, hierarchical LOD by merging. The selection budget does not degrade
gracefully and no ranking function fixes it: the property that matters — a
region's total integrated opacity — is not a property any single splat has, so
it cannot be preserved by choosing among them. Clusters are replaced by one
Gaussian matching their moments (mass, mean, second moment about that mean
including the parallel-axis term, mass-weighted colour). At a quarter of the
splats, measured on the same pose and classifier:

  selection  shell 2,074 of 103,956 px (98 % gone)   10.056/255 from the full frame
  merging    shell 106,865 px (kept)                  3.022/255

Also fixed, and caught by the new end-to-end test rather than by reading: a
UniformBuffer claims its binding point at CONSTRUCTION, so the ordering rig's
camera UBO silently took binding 7 from the evidence test's own and the
CPU-ordered frame was drawing through a buffer nothing wrote. Both sides now
bind explicitly; the two frames are byte-identical (0.0000/255).

ADR 0018 is rewritten and renamed — the old filename asserted a conclusion the
document no longer reaches. It keeps the reversal visible rather than tidying it
away, because "the first draft said do not proceed, on that evidence correctly"

…s, stale UBO bindings, a wrong dispatch claim (#1038, #1039)

Six findings from the Phase 3 self-review of 209a41d, all real.

The one that mattered: **a splat too flat to pack weighed nothing.** A splat
fitted to a flat surface -- most of a real scan -- is oblate, and the 32-byte
record stores covariance as halves whose denormals stop at 6e-8, so a thin axis
below sigma = 2.4e-4 packs to exactly zero. Its determinant was then zero, its
mass was zero, it contributed nothing to the moment fit, and the first
coarsening erased it: exactly the failure #1039 exists to prevent. Worse, the
mass-preservation test could not have caught it, because the baseline it
compares against was computed by the same function -- both sides would have
agreed the vanished splats never existed.

The floor is now applied in both places a determinant is taken. Flooring only
the members would have fixed the weighing and still refused the merge, because
a cluster of coplanar splats -- a patch of wall -- is itself rank-deficient in
the direction none of its members has thickness in. `AVeryFlatSplatStillWeighs
Something` pins both halves and asserts up front that the packing really did
underflow, so it cannot quietly stop testing anything.

The rest:

* `ReleaseBindings` freed the five SSBOs and left the two UBOs on bindings 7
  and 8 -- `UBO_USER_0` and `UBO_USER_1`, the post-process and motion-blur slots
  -- pointing at destroyed buffers. Same hazard the previous commit documented,
  fixed at one call site and not the other.
* `ReadbackOrdering` read shader-written SSBOs with only a `ShaderStorage`
  barrier; GL orders a client-side read behind `GL_BUFFER_UPDATE_BARRIER_BIT`,
  which every other readback in the repo pairs. Issued in the readback rather
  than in `BuildOrdering`, so the frame path does not pay for it.
* `BuildOrdering` silently ignored `ViewSettings::MaxSplats`, which is correct
  by design (level selection replaces the budget) and was a divergence the
  header claimed could not exist. It now warns when a caller sets a budget that
  would actually have changed the answer.
* Clusters whose merge was refused were dropped with no counter, so a chain
  built from a cloud that rejects could lose geometry silently. `DroppedClusters`
  reports it and the fixture asserts zero.
* The "2 log N dispatches" claim in the shader header, the class header and
  ADR 0018 was wrong -- the loop issues 78 global + 21 local at 2^21, not
  21 + 21, and the ADR's own fixture numbers (6 + 12 at N = 4096) disproved it.
  Corrected to what it is: a constant-factor win, 231 to 99, with the global
  half still O(log^2 N) -- which is the actual argument for a radix sort later.

Also widened ADR 0018's GPU timing table to the range observed across three
runs (0.5-2.2 ms at 500 k, 4.7-10.7 ms at 2 M) rather than its best case; this
box was building sibling worktrees during two of them. The conclusion is
unchanged and does not depend on which end is right.

**The measurement.** CodeRabbit pointed out the ADR claimed 1-6 M capability
while measuring only to 2 M. Adding a 4 M point showed 19.5 ms, so the claim was

    2,000,000 splats  ->  padded 2^21  ->   1.28 ms

Five per cent more splats, 6.1x the cost. The bitonic network sorts a
power-of-two array, so ordering cost is a step function of the PADDING rather
than a curve in the cloud size -- an artist who adds a few splats to a scan and
crosses 2^21 would watch the frame time triple with no visible change to the
scene. ADR 0018's supported envelope is now 2 M splats per view, stated as the
2^21 boundary rather than a round number, and the cost model is documented on
`PaddedCapacityFor` where an implementer will actually meet it.

That also promotes the radix sort from "the nicer algorithm someday" to a filed,
motivated issue (#1043): a radix needs no padding at all and makes four passes
