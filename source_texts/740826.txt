Changelog entry (a user-readable short description of the changes that goes into CHANGELOG.md):
Speed up mortonDecode on AArch64 by decoding with compile-time shift and mask sequences instead of a lookup table. The output is unchanged on every architecture.
Description
mortonDecode picks its decoder with #if !defined(__BMI2__): x86 with BMI2, and everything else. AArch64 has no pdep/pext equivalent, so it always falls through to MortonNDLutDecoder. All seven instantiations have ChunkCount = 8, so a row costs 8 loads from a 256-entry table plus a shift-and-or fold per output field.
This adds the missing arm: a branch-free parallel-suffix bit compress ("sheep and goats", Hacker's Delight 7-4) with every mask folded by constexpr. It is portable scalar code with no intrinsics and no lookup table: a field costs at most six shift-and-mask steps and no data-dependent load. At ND=7 clang loads the masks from the constant pool: fixed addresses with no data dependence, rather than a per-row table access.
One correction to the report: the eight table loads are not a dependency chain. Each index is a ubfx/lsr/and off the input code, never a prior lookup, so they issue in parallel; the cost is eight L1 accesses plus the fold, not stalls.
Scope is ND=2/3/5/7, from egor-click's table re-timed against the generic template, not the stale figures in his patch comment. ND=4 measures inside noise there and ND=8 slower, so both keep the decoder they had. ND=6 keeps it too: his table predicts the CI Arm deltas at ND=2/3/5/7 to within 11 points, but the two arm_release runs of the new perf test put ND=6 at -13.1% then +2.5%, neither classified as a change.
x86 is unaffected by construction: the new code sits inside #if !defined(__BMI2__), which a default x86-64-v3 build cannot preprocess. The one x86 build that compiles it, amd64compat (no BMI2), still selects the table decoder because selection is gated on __aarch64__: compile coverage, no behavior change.
I have no AArch64 host, so the ns/row figures are egor-click's; I measured equivalence, arm selection, and the morton_decode.xml Arm deltas cited above.

```
The field mask in the AArch64 compress decoder covers every bit position
congruent to 0 mod ND up to bit 63, not merely the low FieldBits of them.
The narrower span looks equivalent and is not: MortonNDLutDecoder folds
bits above the field width back into the low fields, so shortening the
mask changes what the decoder returns for codes with the top bits set,
and this arm exists to stand in for that decoder.

No SQL test can catch a regression here. The differing bit sits at 63 for
ND=3 and ND=7 and at 60 for ND=5 and ND=6, always above the in-domain
range, so no in-domain case observes it. An out-of-domain reference is
barred as well: BMI2's BuildSelector<FieldBits> matches the narrow form,
so x86 and AArch64 genuinely return different values there, and a
.reference capturing either would be permanently red on the other. That
divergence is pre-existing and not addressed here.

A static_assert on Decode() therefore has to carry the invariant. It
covers the mask, moveMasks() and the compressStep chain end to end, runs
on every non-BMI2 target including amd64compat, and costs nothing at
runtime. ND=2, 4 and 8 are excluded because both spans are identical
there and an assertion would be vacuous.
```

Internal second-model review
Two independent reviews of this change over two rounds: a cold code review and a separate
second-model gate, each without access to the other's notes. Verdicts below, with the evidence for
anything I declined.
❌ Test liveness of the field mask bound (raised independently by both reviews, round 1)
fieldMask() spans every bit position congruent to 0 mod ND up to bit 63, not just the low
FieldBits of them. The shorter span decodes a code with the top bit set into the wrong field
width, so the bound is load-bearing. No SQL test can cover it: the extra bit sits at bit 63 for
ND=3 and ND=7, and bit 60 for ND=5 and ND=6, always above the documented input domain, and an
out-of-domain reference is not available either, since BMI2's selector matches the shorter span and
so genuinely returns the other answer on x86. Measured per domain: the shorter span produces 0
in-domain mismatches at every dimension, and 10,078 / 18,710 / 18,740 / 10,034 out-of-domain
mismatches at ND=3/5/6/7.
Fixed with a static_assert on the decoder's compile-time output at those four dimensions, inside
the non-BMI2 block and outside the AArch64 guard, so every non-BMI2 target checks it. Verified in
both directions: clean as written, and shortening the bound fails the build at all four. ND=2/4/8
are omitted because both spans are identical there, so an assert would be vacuous.
❌ "Zero loads" was too strong (round 2, and it corrects my own wording from round 1)
The draft claimed the compress decoder performs zero loads and references no data symbol. That is
false at ND=6 and ND=7: clang outlines the decoder there and loads its mask vectors from
.rodata.cst16. I reproduced it on the shipped kernel with the CI AArch64 flags and counted rodata
references per dimension: 0, 0, 0, 5, 8 for ND=2/3/5/6/7.
The distinction that survives is data dependence, so I measured that instead. Register-indexed
loads, the shape a table lookup has, are 8 for the table decoder at ND=2 and zero for the compress
decoder at every one of ND=2/3/5/6/7; total loads are 9/24/33/43/60 against 2/3/4/13/17. The
constant-pool loads sit in the outlined helper's prologue and are loop-invariant, not per-row table
accesses. The description now says exactly that.
❌ Table size stated for one dimension only (round 2)
The draft said "512-byte table" while describing all seven instantiations. Measured
sizeof(LookupTable): 512, 768, 1024, 1280, 1536, 1792 and 2048 bytes for ND=2 through 8, with
LutSize 256 and ChunkCount 8 in every case. Reworded to "256-entry table", which is the
dimension-independent fact the argument needs.
⚠️ AArch64 vectorization claim - raised by me, then withdrawn on measurement. I flagged the
original body's NEON claim as unsupported. Recompiling the shipped kernel shape for
armv8.2-a+simd+... refuted my own objection: the ND=2 kernel is 43 of 95 instructions vector, the
ND=6 decode helper 84 of 147, on v*.2d/v*.16b. The claim was correct.
💡 amd64compat framing - reworded. That build (X86_ARCH_LEVEL=1, no BMI2) is the only x86
configuration that compiles the new region, so it is the compile-coverage argument rather than a
caveat. It still selects the table decoder, since selection is gated on __aarch64__.
Confirmed and unchanged, re-verified in round 2 rather than inherited: the new decoder is
bit-identical to the lookup-table decoder it replaces, checked against LUT semantics re-derived
independently from the vendored header over roughly 60,000 codes per dimension for ND=2 through 8,
covering zero, all-ones, every single-bit and single-zero 64-bit pattern, and every 8-bit chunk
boundary and its complement; all 11 new reference constants recomputed from an independent model,
matched, and confirmed in-domain; shrink() really is the second consumer of the changed typedefs
and every ratio is covered; non-BMI2 targets other than AArch64 keep the table decoder bit-for-bit;
no new setting, no format change, no weakened assertion.
The new tests were also checked against a second mutation class: dropping any single compress step
reddens the round-trip block at every dimension, except the highest step at ND=2 and ND=3 where it
is a no-op in-domain, and those two are caught by the maximum-in-domain constants. Every dimension
has at least one assertion that fails for each active step.
Not covered: I have no AArch64 host, so the timings are the reporter's and no performance test
exercises the win. The body says so.

Deterministic repro?

b
Root cause explained?
Yes. #if !defined(__BMI2__) has two outcomes, x86-with-BMI2 and everything else. __BMI2__ is an x86 ISA extension, so AArch64 can never satisfy it, and no arm sits between the two, so it falls through to MortonNDLutDecoder. All seven instantiations have ChunkCount = 8, giving 8 table loads plus a shift-and-or fold per output field, per row.
c
Fix matches root cause?
Yes. It adds the missing arm at the layer where the gate lives and swaps only the seven decoder typedefs. No widened bound, no no-random-* tag, no reduced dataset, no defensive check.
d
Test intent preserved / new tests added?
Yes. No existing assertion weakened or removed. Both existing morton test files gained coverage of the changed path: round-trip identity at every dimension, maximum in-domain and chunk-boundary codes, and every shrink ratio, which exercises shrink(), the second consumer of these decoders.
e
Both directions demonstrated?
Yes. The output is bit-identical to master on every architecture, so the failing direction cannot be "master reds it". Instead I forced the new decoder live on x86 and mutated it: dropping one compress step reddens both test files, while the unmutated forced-live build passes both. Each probe build carries its own Build-ID and an assertion that the compress decoder is actually present in the binary.
f
Fix is general across code paths?
Yes. Both consumers of the changed typedefs are covered, the DECODE loop and shrink(), and a repo-wide grep confirms nothing outside this file names them. src/Functions/mortonEncode.cpp has the identical gate and is deliberately out of scope, per the reporter.
g
Fix generalizes across inputs (params/datatypes/wrappers)?
Yes. Bit-identical to the table decoder over 500,146 codes per dimension for ND=2 through 8 across the full 64-bit range: every single-bit and single-zero pattern, every 8-bit chunk boundary and its complement, zero, all-ones, span endpoints and 500,000 pseudorandom codes, 0 mismatches. A negative control using the obvious i < FieldBits field mask diverges at ND=3/5/6/7, so the check can fail. mortonDecode takes UInt64, so there is no Nullable, LowCardinality or Array wrapper surface at this layer.
h
Backward compatible? (maintainer-approved exception only)
Yes, trivially. No setting, no default change, no serialization format change, so SettingsChangesHistory.cpp is not engaged. Output is bit-identical on the modified arm, so there is no user-visible behaviour change.
i
Invariants and contracts preserved?
Yes. The decoder is a pure constexpr value type with no state, no allocation, no locking and no error path, and Decode() keeps its signature and tuple arity per dimension. The one non-obvious invariant is that fieldMask() must run to bit 63, because MortonNDLutDecoder folds positions above ND*FieldBits back into the low fields; it is enforced and covered by the negative control in (g).

There's a lot of complex bit math in this PR. To ensure that it is all correct we could add a compile-time test like:
```
  /// Both decoders are GF(2)-linear bit maps, so agreement on the 64 single-bit codes implies
  /// agreement on every 64-bit code. Checked at compile time, so a change to fieldMask,
  /// moveMasks or the dimension list cannot silently alter what mortonDecode returns.
  template <size_t Dimensions, size_t FieldBits>
  constexpr bool compressMatchesLut()
  {
      constexpr auto lut = mortonnd::MortonNDLutDecoder<Dimensions, FieldBits, 8>();
      constexpr auto compress = MortonNDCompressDecoder<Dimensions>();
      for (size_t bit = 0; bit < 64; ++bit)
      {
          const UInt64 code = UInt64(1) << bit;
          bool equal = true;
          [&]<size_t... I>(std::index_sequence<I...>)
          {
              ((equal = equal
                    && UInt64(std::get<I>(lut.Decode(code))) == UInt64(std::get<I>(compress.Decode(code)))), ...);
          }(std::make_index_sequence<Dimensions>{});
          if (!equal)
              return false;
      }
```

```
`FunctionDocumentation` described `code` as a plain `UInt64`, which is wider
than the values the function actually defines. A code only carries
`N * intDiv(64, N)` bits for an `N`-dimensional decode, and above that bound
the two decoder arms disagree: measured on this tree, `mortonDecode(3,
0x8000000000000000)` returns `(2097152,0,0)` from the table decoder and
`(0,0,0)` from the BMI2 one, and the same split appears at ND=5, 6 and 7.
ND=2, 4 and 8 use all 64 bits, so they have no out-of-domain region at all.

The bound is the upstream library's own contract - `MortonNDLutDecoder`
exposes `InputMask` to clear exactly those upper bits before a `Decode` call -
and `mortonDecode` never applies it, so it is a property users have to know
rather than one the function enforces. Both arms already behave this way on
master; nothing here changes what any build returns.
```
