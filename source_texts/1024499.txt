Summary
Epic #2314 (L2). Spots were point lights — direction_ / coneAngleDeg_ uploaded but never read. This adds real cone shaping via a winning-light ID channel in the light volume — the human-picked O(1)-per-pixel mechanism, no ray marching.
ID volume: a parallel RGBA8 ping-pong pair on C_CanvasLightVolume (id/255 in .r, 0 = none). The seed writes each light's index, the propagate carries the winner's ID inward in lockstep with the color/alpha, and LIGHTING_TO_TRIXEL fetches it at the surface cell → applies an analytic cone factor when the winner is SPOT. Occlusion is inherited from the flood.
True apex: GPULightSource gains a true-origin field (80 B/light) so an out-of-window spot's cone orients from the real apex, not the clamped boundary seed cell.
Byte-identity + zero cost when no spot: a has-SPOT flag in LightVolumeParams.worldOriginVoxel_.w (coherent uniform branch) skips the ID ops in seed/propagate and the consumer read entirely, so scenes with no seeded SPOT are byte-identical and pay no extra propagate bandwidth.
Both backends (4 GLSL + 4 Metal shaders).
Format deviation from the plan (R8UI → RGBA8)
The plan specified R8UI, but the engine's TextureFormat offers no R8UI/R16UI, and R32I routes through Metal's image-atomic scratch (the #1640 gap) which makes cross-dispatch ping-pong reads unreliable. Normalized RGBA8 round-trips across the 32 propagate dispatches exactly like the color volume already does. The .r-only 0–255 range caps spot-capable light IDs at 255 (a non-issue for the "few dozen lights" workload; documented on the component).
Screenshots — lighting_spot cone (macOS/Metal)
The spot demo now dims the sun so the cone pool reads clearly. Cardinal vs 45° yaw show the cone stays world-oriented (same floor position) as the camera rotates — a camera-locked/mis-oriented cone would slide.

Summary of what I verified
This adds real SPOT cone shaping via a parallel RGBA8 winning-light-ID ping-pong pair on C_CanvasLightVolume, gated by a has-SPOT flag packed into LightVolumeParams::worldOriginVoxel_.w. I read every touched C++ system/component and all 8 shader files (4 GLSL + 4 Metal) in full, plus dispatched two independent render-invariant passes to cross-check:
CPU/GPU struct sync — GPULightSource grew 64B→80B (trueOriginVoxel_), guarded by static_assert(sizeof(GPULightSource) == 80, ...). All 5 members are vec4, so no 16-byte-boundary padding traps. C++, GLSL (seed + lighting_to_trixel), and both Metal mirrors declare the same 5 members in the same order.
Binding-point parity — every image unit (0–3 for clear/seed/propagate ID textures, 7 for the consumer's lightVolumeId) and SSBO slot (4, LightSourceBuffer) agree across GLSL binding=N, Metal [[buffer(N)]]/[[texture(N)]], and the C++ bindAsImage/bindBase call sites. The apparent binding=7 "collision" between the UBO and the new image is not real — UBO and image-unit bindings are independent namespaces on both backends.
GLSL/Metal parity — complete across all 4 shader pairs, including the has-SPOT gating branch (worldOriginVoxel.w != 0 / params.worldOriginVoxel.w != 0) applied identically on both backends, and the "no radians() in Metal" kDegToRad workaround in the cone-factor port.
Byte-identity claim for no-spot scenes — holds end-to-end. The clear pass unconditionally zeroes the ID texture every frame (no per-frame staleness can leak forward), and seed/propagate/consumer all gate their ID ops on the same uniform, UBO-sourced flag — a genuinely coherent (dispatch-wide) branch, not per-thread divergent.
True-apex vs. clamped-seed-cell — gatherLightSources correctly threads the unclamped origin as trueOriginVoxel_ and the axis-clamped cell as the seed position; spotConeFactor on both backends reads trueOriginVoxel_, not the seed cell.
RGBA8 round-trip — id/255 write + round(r*255.0) read is an exact reconstruction for integer k ∈ [0,255] under RGBA8 UNORM with NEAREST filtering (confirmed against the backend texture-format enums). winId - 1 indexing into lights[] is bounds-safe: it's only ever populated from lightIndex < lightCount_ this same frame.
GPU lifetime — the new ID pair rides the same memoryBarrier calls that already gate the color pair after clear/seed/each propagate iteration, and volume.swap() swaps both pairs in lockstep. No fence gap.
Test coverage — GatherHasSpotFalseWithoutSpotLights and GatherSpotFlagsHasSpotAndCarriesTrueOrigin in test/render/per_canvas_light_scope_test.cpp assert exact clamped-seed (63 on the clamped axis) vs. unclamped-true-origin (70,0,0) values and the hasSpot flag — real value assertions on the two headline claims, not just build/run success.
RGBA8-over-R8UI/R32I deviation — the PR body's stated reason (no R8UI/R16UI in TextureFormat; R32I's Metal image-atomic-scratch cross-dispatch ping-pong unreliability, #1640) matches the engine's documented Metal R32I ping-pong hazard; RGBA8 round-trips exactly like the existing color volume already does. Reasonable, well-justified deviation from the plan.

Low risk (both sites are pure documentation, correctness is unaffected), but worth fixing so a future reader doesn't repurpose .w for something else or "clean up" the has-SPOT write as dead code.

Verdict: approve (with nits)
Stack: standalone (baseRefName = master, mergeable = MERGEABLE). Reviewed the rebased head fdab38ee. Sonnet's first pass was thorough and escalated the CPU/GPU-sync / cross-dispatch class explicitly; I focused this pass on the invariants a single-canvas read can't confirm: the per-canvas buffer lifetime three systems deep, and the byte-identity reasoning (not just the outcome).
Confirming Sonnet's pass
Sonnet flagged the GPU struct growth (64→80 B), binding-point parity, GLSL/Metal parity, the RGBA8 index+1 round-trip, and the true-apex-vs-clamped-seed split as the recheck-worthy items. On close read I confirm all of them for the single-light-volume-canvas path that every shipping demo/test actually exercises:
GPULightSource is 5×vec4 with static_assert(sizeof == 80); C++, both GLSL decls (seed + consume), and both Metal decls list the same members in the same order. The propagate pass never declares the struct (it only touches the volume textures), so there's no stale-layout twin.
winId = round(idNorm*255) exactly reconstructs lightIndex+1 for k ∈ [0,255] under RGBA8 UNORM; lights[winId-1] recovers lights[lightIndex]; the 256th light degrades to omni (id 0), documented.
The clear pass zeroes the ID texture unconditionally every frame, and seed/propagate/consume all gate on the same uniform flag, so the coherent-branch → byte-identity claim holds for the no-spot case.
SSBO slot 4 vs image-unit 4 do not collide (independent namespaces on both GL and Metal); the ID pair rides the existing memoryBarriers and volume.swap() swaps both pairs in lockstep — no fence gap.
Opus-only finding — latent multi-canvas staleness (not a shipping regression)
COMPUTE_LIGHT_VOLUME.update() runs per canvas and re-uploads the single global LightSourceBuffer (SSBO) and LightVolumeParamsBuffer (UBO) each iteration, so after the system finishes both hold only the last-processed canvas's light list and its hasSpot flag. LIGHTING_TO_TRIXEL then, also per canvas, binds each canvas's own ID volume (unit 7) but reads the has-SPOT gate (worldOriginVoxel.w) and indexes lights[winId-1] from those global buffers — i.e. from the last canvas's data, not the one being lit.
.xyz is safe because it's cameraAnchorVoxel() — identical for every canvas in a frame. This PR is the first per-canvas-varying data threaded through these global buffers (.w has-SPOT, and light-list identity), so the "last canvas wins" property of the global buffers becomes semantically load-bearing for the first time.
Concretely: with 2+ rendered C_CanvasLightVolume canvases where a SPOT-bearing canvas isn't processed last, the non-last canvas either (a) skips the cone entirely (global .w came from a no-spot last canvas → spot renders as an omni sphere), or (b) applies the wrong light's axis/aperture/apex (winId indexes the last canvas's list). Worst case is a visual miss, never a crash — LightSourceBuffer is always sized to kLightVolumeMaxSources (256), and the originAndType.w == kLightTypeSpot check on the stale entry usually fails → falls back to omni. No-spot canvases stay byte-identical thanks only to the winId > 0 guard (the flag routing itself is not per-canvas-correct — worth noting since the header rationale attributes byte-identity to the coherent flag).
Why this is a nit and not a blocker: no current scene hits it. Every creation attaches exactly one C_CanvasLightVolume (to mainCanvas); the per-axis path shares the main canvas's volume+params (consistent); and the one deliberate multi-volume demo (main_per_canvas_scope.cpp, #363) is emissive-only with a non-rendered sentinel B canvas. Per-axis and single-canvas correctness are intact. But per-canvas light scope (#363) is a supported, unit-tested feature area, so a future author adding a spot to a multi-canvas scene would silently get wrong cones. Recommend either (a) a short comment + IR_ASSERT documenting the single-light-volume-canvas assumption of the spot path in LIGHTING_TO_TRIXEL, or (b) a tracked follow-up to make the has-SPOT flag / light-list per-canvas (re-upload or per-canvas buffer). This does not need to block #2318 — flagging so the human can decide scope before merge.
Nits
(Sonnet's nit, confirmed still open at head) engine/render/src/shaders/c_lighting_to_trixel.glsl:131 still says ".w is reserved" — this PR makes .w the load-bearing has-SPOT gate, and the Metal twin was correctly updated. Pure doc; fix so a future reader doesn't repurpose or "dead-code" the flag. (If the C++ LightVolumeParams::worldOriginVoxel_ member doc also still says reserved, same fix there.)
Praise
The true-apex (trueOriginVoxel_) vs clamped-seed-cell split is exactly right — an out-of-window spot orients from its real apex instead of the window-edge seed, and the two headline unit tests assert the actual values (63 clamped / 70 true), not just build-success.
Zero-cost-when-absent gating is genuinely coherent across all three passes, and the R8UI/R32I → RGBA8 substitution is well-justified against the documented Metal R32I ping-pong hazard (#1640).
