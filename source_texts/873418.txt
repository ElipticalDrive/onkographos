What does this pull request do?
Batch 9c of the conventions work (rotations and rigid motions): the kornia.geometry.linalg transform helpers and NamedPose. The kornia/ changes are docstrings and comments only, confirmed by a token diff against main. #4976 has merged, so the interim Conventions-page links in relative_transformation and in Se3 (left over from #4977) now point at the "Rotations and rigid motions" section.
relative_transformation block:
trans_ab maps frame-b coordinates into frame a, so relative_transformation(trans_01, trans_02) is trans_12.
Only a rigid trans_01 and the top three rows of each input are used; neither is validated.
The contrast with relative_camera_motion: on world-to-camera extrinsics that returns the [R|t] of E2 E1⁻¹, which is relative_transformation(E2⁻¹, E1⁻¹).
Pointers:
compose_transformations and inverse_transformation point at relative_transformation. inverse_transformation is rigid-only and not validated.
relative_camera_motion states the exact matrix relation.
point_line_distance: known defect Epipolar and homography error metrics add eps to the value: Sampson 90% low at ‖F‖ = 1e-3, exact matches score 1e-4 #4881 (point_line_distance ignores the homogeneous coordinate of a (*, N, 3) point, although the docstring says "possibly homogeneous" #4935 was fixed by fix(geometry): divide point_line_distance by the weight of a homogeneous point #4975, so its wart pin and note are gone). The float16 clause distinguishes the all-zero line (0 / 0 = nan) from a = b = 0, c != 0 (inf).
NamedPose: dst_from_src naming, composition order (the matrix product for valid rigid poses; a non-unit Se3 quaternion is not guaranteed to satisfy it, So3 does not normalise its quaternion: So3(Quaternion(ones)) has matrix det 37, log() = 0 for a 120-degree rotation, and So3 * p scales p by |q|^2 #4942), the ValueError on a frame mismatch, and inverse swapping the names. from_rt and from_matrix describe the random-name fallback like __init__.
API pages: NamedPose gets an API page, and batched_squared_norm joins the linalg page.
Other docs: precision.rst now says only an Se2 NamedPose cannot be built in bfloat16.
12 pins (10 test_convention_*, 2 test_wart_*), each checked with deliberate code changes in a throwaway copy of the repo; the composition-order and inverse pins cover an Se2 pose as well as Se3.
Documents #4881 and #4937 as known defects, each with a test_wart_*_<issue> pin. transform_points is left untouched while #4958 is open.
What did you check?
On macOS arm64 (M1). Per branch on current main: the sub-batch's tests (float32/float64 and --dtype=all, where every failure is a pre-existing half-precision one) and a fresh Sphinx -W build of this branch alone. On the combined 9a+9b+9c branch (base 624c2bb):
Sentence review: a separate falsification pass re-ran every changed sentence. It found and fixed 2 false and 7 overreaching sentences, and added a pin for the top-three-rows rule.

MPS float32 passes.
The seeded half-precision profiles give the same failure IDs as the unpinned tree.
Docs and lint:

A fresh Sphinx -W build of this branch alone is clean.
pre-commit is clean.
Open PRs: fix(geometry): accept unbatched transforms in transform_points #4958 still applies cleanly on top of this branch.

Intended verdict: REQUEST_CHANGES (GitHub does not permit a formal review of my own PR).
[P2] Qualify the NamedPose matrix-composition claim for unit Se3 rotations. kornia/geometry/pose.py:51 says the matrix of c_from_b * b_from_a equals the product of their matrices. NamedPose accepts Se3 poses with non-unit quaternions, for which this is false because So3.matrix() uses the unit-only formula (So3 does not normalise its quaternion: So3(Quaternion(ones)) has matrix det 37, log() = 0 for a 120-degree rotation, and So3 * p scales p by |q|^2 #4942). With zero translations and quaternion data [1.8, .2, -.6, .4] and [1.4, -.8, .4, 1.0], the largest matrix difference is 14.2688. The new test uses only Se3.exp unit rotations. State the precondition in this block and cover or cross-reference the accepted non-unit wart.
[P2] State the actual point_line_distance denominator in its convention. kornia/geometry/linalg.py:289 says an unnormalised line's distance is |ax + by + c| / ||(a,b)||, but the function uses ||(a,b)|| + eps; the following Epipolar and homography error metrics add eps to the value: Sampson 90% low at ‖F‖ = 1e-3, exact matches score 1e-4 #4881 sentence and new wart pin show that this changes the answer. For point (1.5, -0.7), line (3, 4, 10) returns about 2.34, while the same line scaled by 1e-9 returns about 1.95. Present the ideal geometric formula as such, then give the actual kornia formula so the contract does not promise scale invariance.
Validation: focused linalg/pose CPU float32/float64 tests passed (244 passed, 9 skipped); Ruff passed. The two counterexamples were reproduced locally. An independent half-precision run found two existing bfloat16 So2 failures in older tests; the added tests passed or skipped as designed. A full Sphinx build was not completed.

Intended verdict: REQUEST_CHANGES (this is a self-authored PR, so GitHub does not accept a formal self-review).
kornia/geometry/pose.py:51-53 says an Se3 pose with a non-unit quaternion “does not satisfy” the composition matrix identity. That is too categorical. A NamedPose containing the non-unit quaternion [2, 0.2, -0.6, 0.4], composed with an identity pose, satisfies (b * a).pose.matrix() == b.pose.matrix() @ a.pose.matrix() exactly in the focused repro. The #4942 defect means the identity is not guaranteed for general pairs. Please use that wording so the convention does not assert a false universal claim.
