The original motivation was just to add binvox support.

So... I hate to do the multiple major refactorings things, but when you say things like "I think we should aim to make it the API as nice as we can and do a "major" release" I get a little excited. I think the latest push is much more elegant. Key points:
there's now only one Voxel class. VoxelMesh was refactored into a MeshVoxelizer in creation and is no longer a Voxel - it just creates voxels from meshes while caches intermediate results.
all voxels now come with a transformation - even if it's the identity. To reduce uneccessary operations I've created Transformation classes that do some basic caching and have potential for optimized point/matrix transformations (e.g. the identity transform does nothing, rather than multiplying by an identity matrix). There's potential for more optimization here (e.g. a Translation or Scale variant) but I spent a while going down that route and decided it was probably just premature optimization at this point. Obviously everything else in the library uses simple matrices, and maybe these optimizations aren't worth the overhead/code complication factor.
I've written the code assuming Encodings, Transformations and Voxels are immutable... but I'll have to go through and make sure I haven't left any leaks. I'm still using DataStore and Cache which means there are lots of uneccessary checks going on, but if you're happy with the immutability I can switch these out.
different ndarray encodings have been moved into a separate class (Encodings) which provide a numpy-like interfaces to things which are conceptually nd arrays. There's a dense, run length and binary run length encoding version, plus various lazy implementations for flipping and transposing. A sparse implementation seems an obvious addition, though (a) I'm not entirely sure what the best way to go about this is and (b) I don't need it for my current work, and this is a fairly deep rabbit hole as it is. I'm happy to think about that later, but I don't think it's necessary right now. The flipping/transpose could be folded into the transform, but that makes saving/loading from binvox a bit trickier (it saves xzy axis order for some reason, so keeping flip/transpose operations separate from continuous rotations is handy).
Added a simple example script.
If you're happy to break some other minor things not directly related to voxel stuff, how do these sound:
I've made a slight tweak to util.grid_linspace. I'll survive with this rolled back, but I don't see much argument for not having it. I also feel returning a stack version of the shaped arrays makes more sense (ie grid_linspace(range(10), [n1, n2, ..., nk]).shape == (10, 10, ..., 10, k). That would involve touching the code in a few places, but nothing crazy.
DataStore feels like it should be a collections.Mapping. The only thing that throws a spanner in the works is this empty default return. Any issue with me making that an error (users could replace any questionable calls with store.get(key, np.empty((0,)))?

I'm definitely not sold on Transformations myself - which I know sounds odd coming from the person who introduced them. I've removed and then re-implemented them a couple of times already. I think the use cases as they apply to voxels is only a subset of the full possibilities, and this PR is big enough as it is. There are a few minor conveniences to having them around for voxels though so I've only implemented a subset.
I'll put my argument for them here, but I'm very happy to remove them and just use matrices if nobody's convinced.
1 A separate object for caching
Certain operations are intrinsic to the transform itself and independent of the occupancy grid (per-voxel volume and pitch / origin if we choose to use them). This could probably be done with just a different Cache object, but from what I can tell that wouldn't work nicely with @caching.cache_decorator and it doesn't seem to fit the overall style of the rest of trimesh.
2 Visitor pattern for optimized implementations (not implemented)
Geometry objects have apply_translation, apply_scale methods which fallback to apply_transformation if not overriden (as a side note, this could be extended to include apply_transpose) indicating optimized implementations can be supported. Generally, Transformations are supposed to represent lazy transforms, so we could use a visitor pattern to still leverage those optimized implementations.
```
class Scale(Transformation):
  def apply_to(self, other):
    return other.apply_scale(self._data)

class Translation(Transformation):
  def apply_to(self, other):
    return other.apply_translation(self._data)

###############################
class Geometry(object):
  def apply_transform(self, transform):
    if isinstance(transform, Transformation):
      return transform.apply_to(self)
    else:
      # matrix fallback
      return self.apply_matrix_transform(transform)

  def apply_scale(self, scale):
    return self.apply_matrix_transform(transformations.scale_matrix(scale))
```
3 Compound mutable transformations
```
>>> scale = Scale(2)
>>> translation = Translation([1, 2, 3])
>>> combined = CompoundTransformation(translate, scale) # translate then scale
>>> print(combined.matrix)
[
 [2, 0, 0, 2],
 [0, 2, 0, 4],
 [0, 0, 2, 6],
 [0, 0, 0, 1]
]
>>> scale.scale = 3
>>> print(combined.matrix)
[
 [3, 0, 0, 3],
 [0, 3, 0, 6],
 [0, 0, 3, 9],
 [0, 0, 0, 1]
]
```
4 Generic lazy transformations
Something like the following might be useful.
```
rotation = Rotation(angle=0, axis=(0, 0, 1))
base_scene = Scene()
base_scene.add_geometry(primitives.Box())
scene = LazyTransformedGeometry(base_scene, transform=rotation)
# rendering loop
def tick():
      # rotate
      rotation.angle += 1.0
      scene.draw()
```
Which would be equivalent to
```
angle = 0
def tick():
  global angle
  angle += 1.0
  rotation = rotation_matrix(angle=angle, axis=(0, 0, 1))
  scene = base_scene.copy().apply_transform(rotation)
  scene.draw()
```
In terms of implementation this is actually worse since Trimesh.apply_transform operates in-place, hence the required copy - but this is more intended to illustrate the possible interface.
For convenience/backwards compatibility I would suggest all publicly exposed interfaces that accept transformations should also accept 4x4 matrices.
I agree that consistency is more important than most of the minor potential optimization discussed. I also accept this adds a layer of abstraction/code complexity that might not be worth it.

Absolutely not. In fact, if we want mutable transformations it might be simplest just to have the one with cached decomposition. I like a separate inverse class because it prevents thrashing (x.inverse.inverse is x), so you can make better use of caches and avoid potential numerical drift. It also means if y = x.inverse then y is ALWAYS the inverse of x - even if x is mutated. This may not be desired, but it suits my way of thinking.

Changelog summarising main changes below. Not sure if you want to include it anywhere.
CHANGELOG
The Voxel class has undergone a major rewrite and been renamed VoxelGrid. It is now defined by separate encoding and transformation_matrix objects and can be thought of as a 3D occupancy grid with unit side lengths that is transformed lazily by an arbitrary transformation matrix. It now implements Geometry in its own right.
Main changes compared to the old Voxel class:
VoxelGrid.pitch and VoxelGrid.origin are still provided for ease-of-transition, but for new code prefer to use Voxel.transformation_matrix directly. Note that VoxelGrid.pitch is ill-defined for transformation matrices which aren't diagonal apart from the translation part and will raise an error when computed if so.
trimesh.voxel.encoding.Encodings classes have been added which represent various encodings of ND arrays - e.g. dense, sparse, run-length-encoding etc. Most methods mimic numpy equivalents, though not all numpy implementations are required so an Encoding is not a numpy array. As a fallback, they contain dense which gives the dense numpy array.
VoxelMesh class has been removed.
Trimesh.voxelized has a new method - binvox - which uses the binvox CL tool.
Filling in voxels can be achieved using Voxel.fill (operates in-place) and now supports a number of implementations.
Added functionality:
hollow: remove internal voxels
strip: strip leading/trailing planes of zeros
revoxelized: create a new VoxelGrid based on a different shape with the same bounds.
Smaller tweaks
util.grid_linspace and util.grid_arange now using meshgrid with indexing='ij'. As a result, the returned arrays have the same rows, just in different orders.
caching.DataStore now implements collections.Mapping, and raises a KeyError if one attempts to access attributes that are not present in the underlying data dict. Old behaviour can be replicated by replacing data[key] with data.get(key, np.empty((0,))).
Various apply_transforms now return the object having the transformation applied to (previous versions returned None). This makes chaining operations easier in some instances. Note they still mutate the object.
