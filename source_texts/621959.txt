In some visualization use cases, it can be helpful to share an existing CUDA buffer with OpenGL to enable fast rendering without copying. One of my colleagues outlined the steps needed for sharing memory with OpenGL in this comment ( vispy/vispy#1986 (comment) ). There's some CUDA functionality that would be nice to use that I don't think is wrapped today (though please correct me if that is wrong). At the simplest level, it would be helpful to have a way to take a CuPy array and convert that into something OpenGL could use.

I checked both of your solutions, but unfortunately none of them seem to work.
The required CUDA/OpenGL interoperability python wrappers are not all available through CUDA-Python (cudaGraphicsGLRegisterBuffer is missing, cuda_gl_interop.h functions are not wrapped).
The new sharing mechanism (nvscibuf, nvscisync) cannot be used yet because we do not have access to the required libraries (nvscisync.h, nvscibuf.h, libnvscisync.so, libnvscibuf.so), at least for cuda 11.4 on ubuntu 20.04.
It would be nice to add this feature in CuPy (by using the CUDA/OpenGL interop API) to offer an alternative to PyCuda.
How to implement a locking mechanism that allows graphics and compute APIs to safely share the same memory segment?
The locking mechanism is provided by cudaGraphicsMapResources() and cudaGraphicsUnmapResources(). It would be the user responsibility to map resources to CUDA before using the shared buffer in CuPy. Typically, OpenGL resource mapping returns a CUDA pointer that we could wrap in a cupy.cuda.UnownedMemory object that can later be used to create a cupy.ndarray. This could be feasible today if we had access to cudaGraphicsGLRegisterBuffer in python.
How does this interoperability work in the presence of a memory pool (say CuPy's built-in one or RMM)?
I think that shared buffers can only be allocated in OpenGL and mapped to CUDA, so we can ignore memory pools (OpenGL owns the memory).

For No.1: I am surprised that CUDA Python didn't expose them. My bad. We are checking internally and will update here.
For No.2: Asked for clarification internally, and I don't think the nvsci* APIs are suitable for this purpose. Specifically, they are typically for Tegra platforms to interact with camera libraries etc. AFAIK they are not distributed as part of the CUDA Toolkit.
The access plan (OpenGL -> CUDA) you described is in line with my understanding (it was a nice learning process for me 🙂). We need to expose CUDA-OpenGL as well as a subset of CUDA-Graphics interop APIs to achieve this need.
