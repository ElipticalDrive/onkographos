Transparent blocks should only occlude themselves (foliage excluded)
This is not the case at all currently, as transparent blocks are treated like solid blocks and occlude everything in the hidden face culling phase. The assumption that all blocks are opaque allows the culling to be very efficient because it can use a binary opacity mask, without caring about block type.
This assumption is wrong with transparent blocks, because we want them to only occlude themselves, thus requiring to check block types before occluding a transparent face.
Technical plan
The simplest solution is to get rid of the opacity mask entirely and return to a more naive hidden face culling code where we iterate block by block and fill the face masks with a custom logic that supports transparent blocks.
Binary Greedy Meshing then proceeds as usual with the face masks, this part is still faster than regular greedy meshing.
To indicate which voxels are transparent the user could pass a HashSet<u16> of transparent values
(because at this point the voxel are represented with u16).
This would certainly be slower than the cached opacity mask version, so we could expose 2 functions in case some users don't care about transparency support and want the fastest version.
Workaround
There is currently a workaround for users: make a mesh for each transparent block types. This is relatively simple to do, users just have to maintain (or build) an opacity mask for each transparent block type in the chunk; of course it gets expensive quickly (in memory and speed) so it is only advisable if the game only has 1 glass type + water for example.
Foliage
Foliage is a different matter entirely, because we usually don't want foliage blocks to occlude anything (themselves included) as doing otherwise would make it seem very hollow, which is okay for glass or water but is weird for foliage. This is outside the scope of this issue.

Ok so after a good deal of micro optimizations, I brought down the meshing from 3ms back to 600μs, which is still x2 times slower than the fully opaque version (as expected), but a reasonable trade-off in exchange for transparent block support.
Since the cost is reasonable I won't split it into a transparent and opaque version unless people ask for it because it makes no difference in my use-case where I don't store opacity masks (opacity masks took 300μs to build so it ends up exactly the same as the new meshing with transparency)
