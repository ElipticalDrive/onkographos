Part of #6868.
Problem
@ifc-lite/pointcloud keeps every decoded point in GPU memory.
Above maxPointsInMemory (25M) it thins the cloud by stride.
LAZ is decoded whole-file in memory.
Nothing can read COPC (Cloud Optimized Point Cloud), the open LAZ-compatible octree format that can be read over HTTP range requests.
Scope
COPC reader. Parse the header, the copc info VLR and the hierarchy pages, with bounded recursion over the page tree. Decode node chunks through the existing laz-perf dependency in the decode worker. The byte source is range-reading (File/Blob or HTTP).
View-dependent LOD selection. A pure function from octree nodes, camera and point budget to the set of nodes to show:
Refine the node with the largest projected screen span first, while it exceeds a pixel threshold; frustum-cull.
Cap the node count, then share the budget evenly across the chosen nodes (water-filling).
Includes a progressive-refinement pacer: a fast first pass sized to a time budget from a learned read rate, then refine.
Viewer integration. Stream nodes in and out as the camera moves, through the existing point-cloud renderer chunk API.
Picking and snapping go through loaded nodes.
The section/crop box and the deviation pass keep working.
Done when
A COPC file opens and renders at least 2× the old 25M cap without resident-memory growth beyond the budget.
LOD selection is unit-tested on synthetic octrees for budget, ordering and culling invariants.
Existing formats are unchanged.
