With #104, a tiny block takes a visible time to disappear after it's broken. Reported in game on the PR branch, not measured yet.
Probable cause
Not confirmed. Read from the code:
Static pieces now live in the chunk mesh, so a broken piece stays drawn until its section is rebuilt and uploaded.
StaticMesh#requestChunk calls LevelRenderer#setSectionDirty(x, y, z), which isn't marked as a player change. The rebuild is async and goes in the low priority queue.
The request comes from SubgridRenderer#render, so it only runs on the next frame that draws the grid.
prioritizeChunkUpdates is 0 here, so vanilla doesn't compile the section on the main thread.
To investigate
Measure the time from the client's piece change to the section upload, near and far, with few and many sections waiting.
Compare with breaking a normal block in the same place.
Check how much comes from the queue, and how much from compiling the section.
Check placing pieces, and redstone in a grid, which take the same path.
Possible fixes
Mark the change as the player's (blockChanged with flag 8), which uses the high priority queue.
Compile the section on the main thread for a change near the player (rebuildSectionSync), with a look at the cost in a dense section.
Ask for the rebuild when the pieces change, not on the next frame drawn.
