Summary
Follow-up to #2-#28. The GGX conductor material has been isotropic (single alpha) since it was added - real brushed/machined metal has a genuinely directional highlight (elongated, not round), which an isotropic BRDF cannot produce regardless of roughness value. This had been deliberately deferred earlier over two concerns: correctly generalizing Heitz 2018's VNDF sampling to the anisotropic (alphaX/alphaY) case, and needing a real, consistently-oriented tangent direction across a curved surface.
What changed to make this tractable now
A local, sparse reference checkout of Blender Cycles' own Metal-backend renderer (intern/cycles/kernel/closure/bsdf_microfacet.h) was pulled in as a cross-check. ggxD/ggxLambda/ggxG1/ggxG/sampleGGXVNDF were all generalized to take alphaX/alphaY and full local-frame vectors, and verified algebraically AND against Cycles' own bsdf_aniso_D/bsdf_aniso_lambda/microfacet_ggx_sample_vndf before being committed. buildAnisotropicOnb() solves the tangent-direction problem by projecting a fixed world-space reference axis onto the local tangent plane via Gram-Schmidt - the same construction Cycles' own make_orthonormals_tangent() uses, adapted for this POC's analytic sphere having no per-vertex tangent data of its own.
alphaX == alphaY reduces every one of these functions exactly to the isotropic formulas this POC used before - not a separate code path, the same functions degenerating correctly at their own boundary case. TriangleMaterial::roughness - otherwise idle for materialType 4 - now doubles as alphaY, with roughness == 0.0 falling back to the isotropic case automatically.
The gold conductor sphere's own roughness was changed from an isotropic 0.15 to a genuinely anisotropic alphaX = 0.08, alphaY = 0.45 - a deliberate showcase change.
Result
Verified two ways: the committed scene shows the gold sphere with a clearly elongated, "brushed metal" highlight. A dedicated render at the EXACT previous parameters (alphaX = 0.15, alphaY = 0, forcing the isotropic fallback) reproduces the original round, symmetric highlight near-identically, confirming the anisotropic generalization's own degenerate case is a true no-op.
docs/METAL_GPU_FEASIBILITY.md section 34 records the full details.
Verification
Both the ad-hoc clang++ build and the CMake RT_BUILD_METAL target build and render correctly, ctest continues to pass
Dedicated render at the exact original parameters confirms the isotropic fallback is a true no-op
Visual inspection confirms a genuine anisotropic streak (not noise/antialiasing artifact)
