Root cause established. Classification: BROKEN — and this is a downstream symptom of #986, not an independent defect.
Read-only investigation at 330a764fc14. The "Not established" item in the body above is now established.
Why p_cached_depth is absent in painterly mode
It was never absent — painterly never publishes it, because painterly was never meant to use it.
p_cached_depth at the composite is p_input.raster_output.depth (render_pipeline_stages.cpp:2855).
raster_output.depth is assigned in exactly two places: the cached-render reuse path (:2618) and render_baseline_stage, which passes it into render_tile_fallback (:2645).
render_painterly_stage (:2730-2778) sets r_output.color, internal_size, raster_path and render_time_ms — and never assigns r_output.depth. It stays default-invalid.
Same shape as #851: a field the painterly branch simply does not fill in.
The log confirms which depth is missing. gs_log_scene_depth_contract_skip_once (output_compositor.cpp:79-97) prints source_depth alone only when the source is missing and the scene depth is present — and the observed message was exactly missing required source_depth. So scene_depth was fine.
Why that is #986's problem and not a depth-wiring problem
Painterly's own composite sources depth from a different accessor: get_painterly_depth_texture() (gaussian_splat_renderer.h:910 → _get_painterly_depth_texture, .cpp:2052), used at output_compositor.cpp:1650-1653, with p_cached_depth only as a fallback. That is coherent design — painterly's depth lives behind its own accessor precisely because raster_output.depth is not populated on that path.
And that depth is valid at runtime. Proof: the [Painterly] Failed to load composite shader warning is emitted inside composite_painterly_output at painterly_renderer.cpp:1265, which is reached only after the if (depth_for_composite.is_valid()) gate at output_compositor.cpp:1654. The warning fired, so the gate passed.
So painterly had a valid depth for its designed composite the whole time. It reaches the standard composite only because #986 makes composite_painterly_output fail, and the standard composite then demands a variable the painterly raster stage never fills.
Also note painterly_composite.frag.glsl:71-79 does its own scene-depth interleave and never reads composite/depth_test. On the designed path the setting is simply irrelevant to painterly, and painterly would render at both values.
Why not the other two classifications
Not "never wired." Painterly's composite is fully implemented and depth-aware — correct premultiplied source-over blend state (painterly_renderer.cpp:1284-1292), scene-depth interleave, device-ownership validation. It is blocked by a shader-load bug, not by absent design.
Not "constrain to depth_test=false." Painterly appears to work at depth_test=false only because that value collapses missing_required_scene_depth (output_compositor.cpp:1672) to false and lets the fallthrough proceed. At that setting painterly is being composited by the standard composite — which is also why its encoding happens to be correct (the GPU-001 follow-up: painterly composite bypasses the sRGB->linear source decode on the pre-upscale path — painterly splats blended as linear, then tonemapped #930 finding). "Painterly works at depth_test=false" is two bugs cancelling, not a supported configuration; constraining to it would enshrine the accident.
Envelope implication
Painterly's alpha-envelope status turns on #986 alone. Repair #986 and painterly composites through its own path, with valid depth, at both depth_test values. Leave #986 unrepaired and painterly is an incomplete feature regardless of any depth wiring.
This issue should be blocked on / folded into #986 rather than fixed on its own. Fixing the depth wiring alone would make painterly render at depth_test=true via the standard composite — which is the wrong composite for painterly and, per #986, the configuration whose encoding is correct only by accident.
Secondary gap, independent of the above, not blocking
render_painterly_stage not publishing r_output.depth has a second consequence today: at render_pipeline_stages.cpp:1904-1907, an invalid r_raster_output.depth makes the pipeline call output_compositor->invalidate_cached_render() whenever scene-depth compositing is expected. So painterly also permanently defeats cached-render reuse in that configuration — a silent per-frame cost, not a correctness bug. Worth folding into whichever change repairs #986.
No code changed and no branch opened for this investigation.

Addressed by #999 (head 21555bfb9fa, base 5dfeb44b5b4). The symptom reproduces exactly; the cause in the "Not established" section is now established, and it is not downstream of #986 — it is an independent defect that #986's fix happens to mask.
Why p_cached_depth is absent in painterly mode
render_painterly_or_baseline_stage (modules/gaussian_splatting/renderer/render_pipeline_stages.cpp:2773-2788 on base) never assigns r_output.depth. The baseline path gets it for free — render_tile_fallback publishes it through an out-parameter (:2645) — and the cached-reuse path copies it (:2618). The painterly branch simply has no such assignment, so raster_output.depth stays invalid on every painterly frame, reaches integrate_final_output as p_cached_depth (:2855), fails has_source_depth (interfaces/output_compositor.cpp:1680) and trips missing_required_scene_depth (:1683).
_get_painterly_depth_texture() is not implicated — it returns a valid texture, which is exactly why the painterly composite itself (output_compositor.cpp:1661) can source depth from it while the strict contract cannot.
Same omission also explains a second symptom nobody had connected: render_pipeline_stages.cpp:1904-1907 invalidates the render cache whenever require_scene_depth && !r_raster_output.depth.is_valid(), so painterly was re-rendering from scratch every single frame.
Fixed at the cause, not by the composite
#999 assigns r_output.depth = renderer->get_painterly_depth_texture() in the painterly stage. Painterly's depth is the same normalized-linear texture both composites expand as mix(z_near, z_far, d), so it is the correct source depth. That fix stands on its own: it also restores the strict-depth fallback on the legacy post-scene phase (forward mobile / multiview / reflection probes), where the painterly graphics composite deliberately does not run.
Scene-specificity: your caution was right, and it cut the other way
The table in this report is reproducible, but the "painterly on" rows measured the baseline fallback, not painterly: painterly/enabled = true without a PainterlyMaterial takes RenderFallbackReason::PAINTERLY_UNAVAILABLE, and there is no PainterlyMaterial anywhere under tests/.
