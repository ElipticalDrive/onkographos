Summary
Cave#nearestRadial now collides against the exact rendered rock mesh (cached per-row rings/patches) instead of the analytic radial approximation, so sphere contacts match the drawn surface on steep banks, ramps and rock features. The old surface-gradient normal correction is removed.
Ball physics: adaptive substepping keeps every integration step under half a ball radius (including fast falls), preventing tunneling between steps. Rock and bronze-slab contact resolution alternate for up to 64 passes so a curved slab meeting a bank clears both contacts; ordinary contacts still exit early.
WallSolid: zero-area collapsed triangles are excluded from rendering and collision queries (closestPointToPoint could yield NaN), and the wall half-angle comparison gains an epsilon so generated end columns never degenerate.
ChaseCamera: replaced the cave-axis blend/look-ahead/curve-amplification/FOV-fit camera with a fixed world-space offset behind the ball. The close-obstruction depthTest fallback and its material hacks in main.ts are removed. Config loses CAMERA_BALL_BLEND, CAMERA_LOOK_AHEAD_SECTIONS and CAMERA_CURVE_AMPLIFICATION; gains CAMERA_FOLLOW_HEIGHT.
Evidence

bun run build (tsc + vite): green
biome check: 20 diagnostics, identical count and kinds before and after this change (pre-existing; dist/ noise dominates a bare bun run lint)
Risk
Camera behavior is intentionally much simpler; framing near walls is no longer guaranteed by pull-in logic (fixed offset instead).
nearestRadial allocates a cached ring/patch per cave row; eviction mirrors the existing chunk eviction.
Rollout
Single commit on a feature branch; revert by deleting the branch. No data or protocol changes.

Code review (zeachco style)
Good work: the new tests validate collisions against independently sampled rendered geometry (Raycaster crossings, matrixWorld triangle walks) instead of the same math under test — exactly the right evidence for a "collision must match what is drawn" change. The NaN guard and wall-angle epsilon both close plausible corruption paths, and the removed config knobs have zero stale references. bun test 50/50, build green, lint diagnostics identical to main (all pre-existing).
1. main.ts:53 — wireframe defaults to on. Blocker (or explain)
let wireframe = true renders the cave and both ball materials as wireframe; main had false. Reads like a leftover from visually verifying mesh contacts. If deliberate for this dev phase, say so; otherwise initialize to false (the backtick toggle still works).
2. ChaseCamera.ts — fixed world-space offset ≠ behind the ball. Should-fix
Verified with the path generator: seed 7 tangent z reaches +0.025, seed 40 +0.377, and pure ±X runs have z ≈ 0. On those stretches the +Z-offset camera sits beside or in front of the ball, and the view snaps 180° when the ball crosses the camera's z-plane. Either offset along the negated tangent/velocity (keeping the no-smoothing property the tests assert), or record the accepted limitation in this PR.
3. ChaseCamera.ts / main.ts — camera can enter rock, no fallback. Question
The clearance ray + depthTest hack are gone; a narrowing tunnel or wall feature between camera and ball now yields a hidden ball with no mitigation. If "briefly hidden ball" is the accepted price of the simplification, make that acceptance explicit.
4. Ball.ts contact loop — measure it. Should-fix (perf)
#resolveRock runs every pass of the up-to-64-pass loop, and each call is a mesh scan (9 rows × 40 patches × 2 triangles, bounds-pruned) per substep per ball — even in the common 1-pass case. Worst case ~46k point-triangle queries per substep. Please measure frame time on seed 5 with 6+ balls vs main; if noticeable, skip the scan when position/velocity didn't change since the last pass, or lower the alternation bound (tests exercise far fewer than 64).
5. Ball.ts:537 — substep estimate clamps horizontal speed. Should-fix
Math.min(Math.hypot(vx, vz), effectiveMaxSpeed()) bounds the estimate, but the integration uses the real velocity — bounces/slope launches can exceed the cap, so a step can exceed half a radius exactly when moving fastest. Use the actual horizontal speed or comment why the cap is safe.
6. Cave.ts #nearestRock — degenerate result when no rows queried. Question
If all candidates fall below #controlOffset * SAMPLES, best stays Infinity → dist = -Infinity with stale #rockNearest/#rockNormal; the ball silently passes through rock. Likely unreachable, but an isFinite(best) guard would make failure explicit.
7. #nearestRock — #rockClosest doubles as scratch delta. Nit
subVectors overwrites the closest-point vector with the delta; correct but requires tracing the aliasing. Comment or separate scratch vector.
8. tests/cave-path.test.ts — magic frame f === 59. Nit
Derive from speed/distance or assert "was ≤ front+1 at some frame", else tuning silently voids the check.
9. tests/cave-terrain.test.ts — golden coordinates. Nit
Fine as independent samples, but one comment on how they were sampled prevents future "fixes" to match the implementation.
Verdict: approve after #1 and #5; #2 and #3 need an explicit fix-or-accept decision.

self-review: Context and intent
Context
Problem/request: The cave game's sphere-vs-terrain contacts did not match the drawn surface: the analytic radial approximation missed steep banks, ramps and rock features (visible gap between what the mesh draws and where the ball stops), fast falls could tunnel through bronze slabs between fixed physics substeps, and collapsed (zero-area) slab faces could poison closestPointToPoint with NaN distances. Separately, the chase camera had accumulated four interacting mechanisms (cave-axis blend, look-ahead aim, curve amplification, FOV fitting, plus a close-obstruction depthTest fallback) whose interplay was hard to reason about and harder to test.
Affected users/systems: Anyone playing the cave game (src/games/cave); the AI-training loop that depends on honest terrain sensors and collisions.
Evidence/root cause: The pre-existing failing/incorrect-contact stretch motivated commits 352753e and c804de9; the new tests (seed 3 sphere contacts use the visible rock on steep banks and ceilings, a fast fall cannot tunnel through a slab between physics steps) pin the defect being fixed.
Desired behavior: A ball resting or rolling against rock stays exactly radius away from the rendered triangles; a ball falling at any achievable speed cannot skip a slab in one step; the camera is a simple, deterministic function of ball position.
Goal and non-goals
This PR will: make Cave#nearestRadial query the exact rendered rock mesh (cached rings/patches); make WallSolid reject zero-area triangles and degenerate end columns; adaptively substep integration so each step is < half a ball radius including falls; alternate rock/slab contact resolution until both clear; replace the chase camera with a fixed world-space offset; remove the depthTest fallback and its material hacks.
This PR will not: change scoring, gates, path/feature generation, sensors (Sensor.ts ray queries untouched), or any non-cave game.

self-review: Design, tradeoffs and evidence
Change and scope
Affected: src/games/cave/classes/{Cave,Ball,WallSolid,ChaseCamera,Config}.ts, src/games/cave/main.ts, four test files.
Behavior changes: sphere contacts now resolve against mesh triangles (steep banks/ceilings included); falls can no longer tunnel; camera is a fixed offset (0, +CAMERA_FOLLOW_HEIGHT, +CAMERA_FOLLOW_DISTANCE) in world space with fixed 72° lens.
Config: removed CAMERA_BALL_BLEND, CAMERA_LOOK_AHEAD_SECTIONS, CAMERA_CURVE_AMPLIFICATION; added CAMERA_FOLLOW_HEIGHT. No stale references remain.
Deliberately not changing: wallRayDistance/castWheelRay (still used by Sensor.ts), feature/path generation, all other games.
Design and tradeoffs
Why mesh-exact contacts: "collision must match what is drawn" is the game's core fairness property; approximating the analytic tube again invites the same drift the new tests catch. Ring/patch caches mirror the existing per-chunk eviction, so memory stays bounded with the streamed terrain.
Why the fixed camera: the previous blend/look-ahead/FOV-fit stack was five interacting mechanisms with heavy test scaffolding; a pure function of ball position is trivially testable and jitter-free. Tradeoff accepted: no obstruction clearance and no direction following — on lateral tunnel stretches the view is sideways rather than behind (verified: seed 7 tangent z reaches +0.025, seed 40 +0.377), and the ball can be briefly hidden behind rock. This is pending an explicit accept-or-fix decision (review findings Add circuit boost clones #2/Cave: exact mesh contacts, robust slab resolution, fixed-offset camera #3).
Why adaptive substeps: velocity-scaled step length is the smallest change that removes tunneling without a global physics-freq bump; the estimate clamps horizontal speed at effectiveMaxSpeed, which is the one known soft spot (review finding #5).
Alternatives rejected: widening PHYSICS_SUBSTEPS globally (costs everyone for a rare case); keeping the analytic radial normal and patching it per-feature (what this PR removes — it was the root cause).
Acceptance criteria
Given a ball resting against any rendered rock triangle, distance to that triangle ≥ radius − 0.001 (covered: seed 3 banks/ceilings, seed 5 slabs).
Given a fall at any speed, the ball never appears below a slab deck between frames (covered).
Given any ball position, camera pose is the fixed offset — jump, impact, respawn, direction and speed cannot alter it (covered).
Testing and evidence
bun test: 50 pass / 0 fail, 110,245 assertions in 5.6s.
bun run build (tsc + vite): green.
biome check src tests: 20 diagnostics, identical count and kinds before and after this change (pre-existing; a bare bun run lint additionally scans ignored dist/).
Not tested: manual browser play; frame-time measurement of the 64-pass contact loop vs main (review finding #4) — unknown until measured, seed 5 with several balls is the suggested benchmark.

self-review: all findings addressed in b7ab9c5.
wireframe — fixed. let wireframe = false; the backtick toggle is unchanged.
camera behind the ball — fixed. The boom is now the negated horizontal tangent (velocity, then +Z, as fallbacks), so lateral stretches no longer put the camera beside/in front of the ball. The pose stays a pure function of the current ball state (asserted by a no-lag test that returns to a prior state).
camera in rock — fixed rather than accepted. ChaseCamera.update takes an optional Cave and runs castRay along the boom, shortening it by CAMERA_COLLISION_MARGIN (2) when rock sits between the ball and camera. Covered by a stub-cave test.
contact-loop cost — measured and reduced. Two changes: the per-substep progress query now calls a new Cave#locate (centerline s,a only) instead of nearestRadial, and the redundant confirmation scan after an already-resolved rock contact is gone. On seed 5 with 8 balls the benchmark is noisy but back at the pre-PR level; structurally this removes ~1 exact 9×40×2 mesh scan per substep per ball. I intentionally kept the 64-pass alternation bound: an A/B showed the seed-5 slab/bank case needs many alternating pushes (it fails below ~16), so the win is dropping redundant scans, not capping the loop.
substep velocity — fixed. The estimate now uses the real horizontal speed; the effectiveMaxSpeed() clamp is gone, so a bounce/slope launch above the cap still substeps below half a radius.
#nearestRock degenerate result — fixed. Number.isFinite(best) is checked and throws with the query point and s, instead of leaving stale nearest/normal.

golden coordinates — documented how the seed-5 samples were taken (chunk-mesh triangle midpoint offset inward by a ball radius).
