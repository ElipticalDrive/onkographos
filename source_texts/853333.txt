The following trivial LLVM IR attempts to convert a 16-bit float to a 64-bit integer and store the result somewhere:
https://godbolt.org/z/q9q3M4v6G
```
define void @half_to_i64(ptr %in, ptr %out) {
  %half = load half, ptr %in, align 2
  %i64 = fptosi half %half to i64
  store i64 %i64, ptr %out, align 8
  ret void
}
```
Compiled for an AArch32 target with the fullfp16 attribute, the generated machine code expects to perform the conversion via a libcall: it emits the instruction bl __fixhfdi. However, this library function does not exist! compiler-rt doesn't have it, and neither does any Arm build of libgcc that I've been able to find. So this code will fail to link against any set of libraries I know of.
The same is true if you start from C, e.g. feeding this to clang:
```
#include <stdint.h>
void half_to_i64(const _Float16 *in, int64_t *out) { *out = *in; }
```
Reproducer command lines for the above:
```
llc -mtriple armv8a-none-none-eabihf -mattr=fullfp16 fptosi.ll -o -
clang -O1 --target=arm-none-eabi -march=armv8a+fp16 -S -o - fptosi.ll
clang -O1 --target=arm-none-eabi -march=armv8a+fp16 -S -o - fptosi.c
```
I think that this whole family of functions for converting between half-precision and integers (__fixhfsi, __fixhfdi, __floatsihf, __floatdihf, and the unsigned variants) do exist somewhere, but not everywhere: they seem to be RISC-V specific.
On the LLVM side, it looks as if those function names were introduced in commit f7bc7c2, with [RISCV] in the title. On the libgcc side, they've existed in the source tree since gcc 14 (gcc-mirror/gcc@e230261 introduced them), but they're only enabled in RISC-V builds, even as of gcc 16. (For example, I checked the binary builds of libgcc 16 available as Ubuntu 26.04 packages: the libgcc.a in libgcc-16-dev-riscv64-cross matches a grep for fixhfdi, but the one in libgcc-16-dev-armhf-cross does not.)
I'm not sure which is the right thing to do, out of getting these functions into AArch32 support libraries (by agreement with libgcc), or not emitting them from LLVM on AArch32 targets. But we should do one or the other.

For fptosi, GCC seems to transforms it to half->float fpext + float->i64 libcall. This seems to be valid according to alive.
We should also be able to convert to half->i32 fptosi + i32->i64 as the range of half isn't very large, which I think is what #230779 is looking to do. fptosi.sat needs to be careful about the edges.
sitofp can probably do a similar thing if alive is to be believed, generating the equivalent of
```
define half @example(i64 %in) {
entry:
  %out = sitofp i64 %in to float 
  %f = fptrunc float %out to half
  ret half %f
}
```
