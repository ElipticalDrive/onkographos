Folks, I intend to merge this PR soon, can I get an (hopefully approving) review?
Current state is as good as it's gonna get for now:
Redistribution via ParMETIS works well for all meshes I've tested, it's enabled by default but optional, and additionally the number of partitioning refinement iterations can be controlled by the user (via XML attribute partitionRefinement, 1 is default, 0 to disable ParMETIS, higher values for better quality).
MPI neighbor candidates are now detected via an all-to-all exchange of partition bounding boxes - this is much faster than building the whole ghosting layer via vtkGhostCellsGenerator filter. We then let GEOSX figure out exact neighbors and remove candidates that do not share common nodes.
For pre-partitioned datasets (.pvtu), and only if partitionRefinement="0", we now don't do anything (i.e. keep original partitions) as long as every rank has at least a piece of the mesh, otherwise still redistribute as usual.
There are some outstanding issues related to reading .pvtu datasets that I won't be able to fix immediately. Additional investigation needed for all of these:
When reading on fewer ranks than partitions in file, some heap corruption occurs. I've put an explicit user-friendly error trigger in place for now.
When reading on exact number of ranks, and with partitionRefinement="0", there are spurious ghosting errors in GEOSX.
When reading on more ranks than partitions in file, and with partitionRefinement="0", some heap corruption or segfaults occur.

There are some outstanding issues related to reading .pvtu datasets that I won't be able to fix immediately. Additional investigation needed for all of these:
When reading on fewer ranks than partitions in file, some heap corruption occurs. I've put an explicit user-friendly error trigger in place for now.
When reading on exact number of ranks, and with partitionRefinement="0", there are spurious ghosting errors in GEOSX.
When reading on more ranks than partitions in file, and with partitionRefinement="0", some heap corruption or segfaults occur.
Update: all of these are caused by duplicate points that VTK produces when it merges partitions (either in the PVTU reader or the redistribution filter). The next VTK release will include fixes for the redistribution filter, as well as a new filter that can be used to "clean up" the mesh and remove duplicate points. As soon as it becomes available (likely within a month or two), I will update the code.
For now, I implemented a simple duplicate point check using an unordered_set. It will detect the issue and terminate with a user-friendly error rather than segfault or heap corruption. The error message also includes a suggestion to pre-sanitize datasets using "Clean grid" filter in Paraview (which helps in some cases, but not universally).

The VTK code is a bit more general and complex than needed here. For example, it takes an additional block_assigner parameter which specifies the distribution of partitions. Our use case is simpler, since every local partition goes directly to only one target rank, and respectively every rank receives exactly one partition from every other. Therefore we can simplify some data structures used in exchange (e.g. use vector instead of vector<vector> for storing blocks) and do strictly less work, even if it's just O(1) less.
