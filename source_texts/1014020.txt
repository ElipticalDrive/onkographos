Groundwork (3db88db)
IVoxelStorage gains what K26 measures: its Type, MemoryBytes, and WriteData. A12's serialization now exists, with a matching reader.
VoxelStorages makes, writes and reads any scheme.
WorldConfig.Storage (plus octree depth) picks the scheme. ChunkView and World create chunks through it; a new scheme makes new chunks.
VoxelStorageTests (renamed from FlatVoxelStorageTests) is the contract every scheme passes:
random edits checked against a plain array;
layer reads matching single reads;
bounds checks;
a serialization round trip;
meshing the same as flat storage.
The schemes (2874848, efc9e72)
K28 ByteVoxelStorage: one byte per sample. Densities run 0–1, so an unsigned byte maps them directly; 0 and 1 stay exact for the brush.
K24 RunLengthVoxelStorage: runs along X, Y or Z. An edit splits a run and merges equal neighbours.
K25 OctreeVoxelStorage:
a power-of-two cube with uniform leaves, eight children, or dense bricks at a configurable max depth;
equal children collapse back, and uniform bricks become leaves again;
node arrays with free lists, so no garbage per edit.
CompressedStorageTests check collapse, surface-only detail, every octree depth, and run merging.

Quantizing to bytes changes RLE and octree compression by under 1%.

K28, K24: single-byte and run-length voxel storage
…
2874848
```
ByteVoxelStorage (K28) keeps one byte per sample, a quarter of the flat
float size. Densities run 0-1 around the iso level, so a byte maps them
directly, rounded to 1/255; 0 and 1 stay exact for the brush (K16).

RunLengthVoxelStorage (K24) stores each line along one axis (X, Y or Z,
three storage kinds) as runs of equal values: run ends plus values,
binary-searched; an edit splits a run and merges equal neighbours, so
neighbouring runs never repeat a value. Layer reads decode runs straight
into the layer (one lookup per sample for Z runs). VisitRuns exposes the
runs for the storage view (K27).

Both pass VoxelStorageTests (60 checks across the five schemes so far).

K25: Sparse octree voxel storage
…
efc9e72
```
OctreeVoxelStorage pads the sample grid to a power-of-two cube. A node is
a uniform leaf, eight children, or at the configurable maximum depth a
dense brick. Writes divide uniform leaves on the way down; eight equal
uniform children collapse back into their parent and a brick that turns
uniform becomes a leaf again, so solid and air cost one node each. Nodes
live in parallel arrays with free lists (no garbage per edit). Layer
reads walk only the nodes the layer crosses. VisitNodes exposes the tree
for the storage view (K27); the serialized form is depth-first tags.

CompressedStorageTests check the octree collapses uniform regions, keeps
detail only near a surface, stays correct at every depth, and that
run-length storage merges runs back.

StorageBenchmark compares flat float and byte, run-length X/Y/Z and the
octree (8³ and 4³ bricks) on hills and caves at 16³-64³: memory,
serialized size, runs or nodes, fill, meshing reads and brush strokes,
plus a quantized pass for the compressed schemes.

At 64³: bytes are 0.25× with no structure; the 4³-brick octree is the
smallest in memory (0.28×) but ~35% slower per stroke; run-length X
serializes 12× smaller than flat. Runs along X or Z beat Y, since every
column crosses the surface. Quantizing barely changes compression, and
byte densities show no visible stepping (K28). Flat float stays the
default; M12 picks at scale.
