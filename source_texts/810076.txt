What
A draw whose PA_SC_CONSERVATIVE_RASTERIZATION_CNTL (context 0x313) isn't the default 0x6000 is skipped (conservative rasterization is unsupported).
0x6001 adds OVER_RAST_ENABLE (bit 0 in amdgpu's gc_10_3_0_sh_mask.h). It becomes VK_CONSERVATIVE_RASTERIZATION_MODE_OVERESTIMATE_EXT in the pipeline's rasterization state and key.
VK_EXT_conservative_rasterization is enabled only if primitiveOverestimationSize is at most 1/256 pixel (the vertex grid of PA_SU_VTX_CNTL 0x2d) and degenerateTrianglesRasterized is set; otherwise the pipeline throws.
Only triangles reaching the rasterizer are overestimated, read before the stage decode from VGT_GS_OUT_PRIM_TYPE (geometry shader), VGT_TF_PARAM (tessellation) or VGT_PRIMITIVE_TYPE.
Still throws: points, lines, isolines, rect lists, per-stream GS types, other 0x313 values and centroid interpolation. One TechnicalDebt line.
PPSA26344 v1.008: from about 250 s on, 2.2-2.4 draws per present are skipped this way: DRAW_INDEX_INDIRECT triangle strips with 0x313 = 0x6001 into a seven-target 3840x2160 G-buffer at 0x5050bc0000.
feat(agc): single-sample sample masks as a per-quad-pixel discard #448 edits the sample-mask check that followed the 0x313 check in DecodeState.
feat(agc): multisampled color and depth targets with CB resolves #419 adds multisampling; whichever lands second should keep conservative draws single-sample (per-sample overestimation isn't modelled).
Tested
Windows 11, MinGW-w64 GCC 15.2.0, based on main c81c2b3: configure -DBUILD_TESTING=ON, full build, --target libs, ctest:
431/431 tests pass (ctest --output-on-failure)
Same build on lavapipe (Mesa 26.2.4 llvmpipe, 8-wide subgroups, VK_DRIVER_FILES): 430/430 pass; agc_driver_flat_store is left out there because it takes several minutes on Windows llvmpipe
New agc_driver_conservative_rasterization (GPU): three triangles write just the 6 pixels whose centres they cover, or with overestimation the 13 they touch; lavapipe (no extension) checks the throw and skips.
Extended agc_driver_graphics, also with points, lines and triangles out of geometry shaders and tessellation. Both fail or do not build on main.
PPSA26344 v1.008: a 2,700 s run with this change has no conservative rasterization is unsupported skips (a 1,500 s run without it had 1,432, 5-7 per present once the menus open), and no other error skips those DRAW_INDEX_INDIRECT draws.
Not tested: Linux (CI), console behaviour.

Author
Thanks for catching that the check only looked at the input topology. It now looks at the primitive that actually reaches the rasterizer, on every path.
With GS_EN set (the Geometry and TessellationGeometry paths) it reads VGT_GS_OUT_PRIM_TYPE and only accepts a triangle strip with no per-stream types. With only HS_EN set it reads VGT_TF_PARAM: a triangle or quad domain with clockwise or counter-clockwise triangle output passes, while point mode, line output and isolines throw. Otherwise it reads VGT_PRIMITIVE_TYPE as before, so point, line and rect lists throw. Each rejection names the register and its value.
One thing I found while writing the tests: on the old head these draws already threw, just not for this reason. DecodeShaderStages only lets VGT_GS_OUT_PRIM_TYPE 2 and clockwise triangle tessellation through, so nothing wrong could render with today's routings. That would have changed silently as soon as either one was widened, though. So the conservative decode now runs at the start of DecodeState, before the stage decode: it holds on its own, and the tests can see it.
ConservativeRasterizationTests now has GS point, line and per-stream outputs, tessellation point mode, line output and isolines, and a combined tessellation and GS draw that emits lines. All of them must throw with the conservative reason. It also checks that triangle strips out of a GS (fed points, lines or triangles) and clockwise tessellated triangles still get overestimation. All ten rejection cases fail on e86533b, where they hit the stage-routing or old vertex-path messages instead, and pass now. The draw key and sameDecode didn't need changes: the key already hashes 0x29b, 0x2d5 and 0x2db, and the new check only decides between accepting and throwing.
The new head is 29c2244.
Details
On e86533b with the new test: GS outputs 0x0, 0x1 and 0x80000002 throw VGT_SHADER_STAGES_EN=0x2020: unsupported geometry input or output assembly. VGT_TF_PARAM 0x9, 0x29 and 0x28 throw only triangular, fractional-odd, clockwise tessellation is supported by the reference path. The combined draw throws combined tessellation and geometry is unsupported. The vertex point list throws point-list vertex rendering requires point-size output support.
On 29c2244 each case throws e.g. conservative rasterization of lines is unsupported (VGT_GS_OUT_PRIM_TYPE=0x1): only triangles are overestimated.
Windows 11, MinGW-w64 GCC 15.2.0, merged with main b1c5f10: agc_driver, agc_driver_graphics and agc_driver_conservative_rasterization pass on the RTX 3080 Laptop and on lavapipe (Mesa 26.2.4 llvmpipe, where the GPU test checks the throw and skips).
Full runs of 29c2244: Windows ctest 431/431 on NVIDIA and 430/430 on lavapipe; Linux (WSL Ubuntu 24.04, GCC 13.3, Mesa 25.2.8 llvmpipe, upstream's job config) merged with main 1081602, 454/454.
