Summary
Refs #586. PR 1 of 3: stop the unsorted fall-through.
When the global-composite (tile-overlap) sorter does not exist, TileRenderer::render() used to run binning, emit, raster and resolve anyway and present tiles in atomic-append order, i.e. mathematically incorrect alpha compositing dressed up as a normal render, owned only by a counter and a throttled WARN (renderer/tile_renderer.cpp:1074-1092 at base). This PR makes that frame a publish reject: the choke point returns false, run() returns an invalid RID, TileRasterizer reports success=false and nothing is presented for that frame. Presenting nothing is honest; presenting wrong ordering that looks like a render is not. The transient reasons (sorter exists, one dispatch failed) keep the previous counter + WARN behaviour and are still presented.
This carries forward the design intent of the parked PR #852 (reject the frame, not composite unsorted) and the review findings there that concern this step (count the pre-binning reject; do not let a rejected frame report stages that did not run as if they had). It deliberately does not carry #852's static guards, lane promotion, or retry machinery. What this PR does not do, stated plainly: the sorter-unavailable state still latches for the session (renderer/tile_render_resources.cpp:1299-1319), so after this PR a latched renderer presents nothing instead of wrong pixels until teardown. Making the latch retry is PR 2; keeping a failed grow from destroying a working sorter is PR 3. Both are sequenced after this one on purpose.
What lands
renderer/sort_fallback_policy.h: unsorted_composite_must_reject_frame() — the whole correctness decision as one pure function (no default label; fall-through fails closed). SORTER_UNAVAILABLE rejects; SORT_DISPATCH_FAILED / ASYNC_SORT_NOT_SUBMITTED do not. New GLOBAL_SORT_RESOURCES_UNAVAILABLE reason for the pre-binning exit.
renderer/tile_renderer.cpp: at the existing single choke point a fatal reason returns through _reject_global_composite_frame(), which counts the reject, records the reason, WARNs on the same throttle as the unsorted counter, keeps the measured assignment-stage CPU cost (the stage ran up to the exit; hiding it would report the degraded path as free — review round 1), and zeroes only the stages that did not run: rasterization on both exits, plus the prefix/sort CPU pairs on the pre-binning exit (at the choke point those already hold this frame's values). The pre-binning resource exit (which already rejected, uncounted) goes through the same helper. Its scope is stated in the code: the two sorted-path-unavailable exits, not every return false in run().
renderer/tile_render_types.h, tile_renderer.h, render_debug_state_orchestrator.cpp: global_composite_rejected_frames / global_composite_last_reject_reason, exposed through get_binning_debug_counters(). They partition with unsorted_composite_frames: a degraded frame lands in exactly one.
renderer/tile_render_resources.cpp, gpu_sorting_config.cpp: the three disable_sorter() messages and the gpu_sorting: radix_bits x workgroup_size product is never clamped (18KB > 16KB shared memory) -> sorter unavailable -> silently unsorted output #634 portability warning no longer promise "rendering unsorted tiles"; they say translucent frames are rejected (§8 of the acceptance bar: a message the code contradicts is a defect).
Tests: two pure-function cases in tests/test_sort_fallback_policy.h; one [GaussianSplatting][TileRenderer][RequiresGPU] case in tests/tile_renderer_regression_test.cpp that provokes the real disable_sorter() path (below) and asserts the observable consequence.
docs/reference/renderer_release_gate_manifest.json: RequiresGPU snapshot re-pinned 156 → 157 with the repo's own functions (sha256_last_changed_by records the derivation).

* gaussian_splatting: build the replacement before retiring the working tile sorter on a grow, and back the grow off (refs #586, PR 3 of 3)

ensure_resources() shut down and unref'd the live tile sorter BEFORE the
preflights and create_sorter() ran for a grow or key-layout change, so a
grow that failed at the one moment it is likely to fail (VRAM pressure)
traded a working, slightly-too-small sorter for no sorter at all -- since
#976 every translucent frame rejected, since #977 until the no-sorter retry.
The optional shrink already built before retiring; the grow now does too.

On a failed grow the working sorter, its capacity and its buffers stay and
the frame renders sorted at the old budget: records above it are clamped by
the prefix pass (_get_effective_overlap_capacity) and counted by the
existing overflow-drop telemetry. The grow is re-attempted on the shared
GPU-003 backoff with its OWN counter (sorter_grow_failure_count /
last_sorter_grow_failure_frame): frames keep publishing meanwhile, so PR 2's

* docs/governance: define the two-stage release acceptance bar (#360)

Records the maintainer's decisions on what GodotGS must satisfy before it
ships, and how each claim is verified. Defines the bar only; enforcing it is
follow-up work, so this refs #360 rather than closing it.

Two stages. The Public Alpha ships earlier on a reduced bar (single resident
scene, correctness blockers only, no API promise) and must say "alpha" on the
tin. v1.0 carries the production promise: full envelope including multi-node
and streaming, evidence-integrity gaps blocking, a bounded public settings
surface, and a peer-relative performance comparison run out-of-band.

Design notes:

- The blocking criterion is stated as a RULE, not a pinned issue list, so the
  release checklist regenerates by query and cannot go stale. Internal
  refactors deliberately do not block: a bar that gates on "decompose
  publish()" ends with P1s relabelled P2 to unblock, which is the same shape
  as weakening a gate to make a check pass.
- The verification gate must assert that required lanes RAN, not merely that
  they did not fail. A job-level `if:` yields conclusion: skipped, which counts
  as SUCCESS against a required check.
- The performance section records that lighting/shadow/effector cost is driven
  by scene composition, not by a feature switch, and flags that
  direct_light_scale and indirect_sh_scale are post-multiplies applied after
  the accumulation work -- zeroing them blanks the image while paying the full
  cost, so a parity number produced that way would be false.

Code citations were read at base de2cb80 and carry file:line.
