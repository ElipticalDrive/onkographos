Summary
This PR extracts more features from Adds a bump-based Marching Cubes option #1950 in preparation for adding a Bump-based Marching Cubes algorithm
I will remove these changes from Adds a bump-based Marching Cubes option #1950 after this is merged
It streamlines the Marching Cubes example
It removes the internal field generation mechanism from the example. This was moved to the gen-cartesian-blueprint-mesh.py Python script in Improves blueprint Cartesian mesh generator script #1995
It removes the internal validation mechanism from the example. This was moved to Marching Cubes unit tests in Bugfixes, enhancements and improved Marching Cubes testing #1996
Users now supply the field name for contouring
It adds a --list-fields option to the example to print out fields in the provided Blueprint mesh, as well as their min/max ranges
Also update the data submodule, since the Marching Cubes meshes now require fields. This was added to axom_data in Adds scalar fields to the multidomain structured grids axom_data#44
Misc:
On Windows: Creates a static library for Marching Cubes that gets linked into the shared build. This was necessary to fix a linker error related to too many exported symbols. Windows only allows 65K symbols, and with the original and bump-based Marching Cubes, there were more than 150K symbols
Improves build/link times for MIR by omitting source files for policies that are not in the configuration

…

```
The error was found when adding a bump-based MC backend.

The number of exported symbols in the various MC objects
with our shared library config and `CMAKE_WINDOWS_EXPORT_ALL_SYMBOLS=ON`
was too high.

MSVC gave the following link error:
  LINK : fatal error LNK1189: library limit of 65535 objects exceeded

The fix was to make the MC object a private static library.
Without the fix, we had 153,966 export symbols. With the fix, we're down to 26,380 symbols.
```
