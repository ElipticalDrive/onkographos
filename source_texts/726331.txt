Why
3dgs-io v2.0.0 shipped the breaking splatsim.scene/v3 bundle layout (autowarefoundation/3dgs_io#46): per-Gaussian LiDAR attributes are embedded inside each chunk SPZ as an NGSP v4 extension record instead of .lidar sidecar files, the chunk index moved into scene.json.gaussians.chunks, and bundles no longer carry a Cesium tileset.json. splatsim's loader only understood v2, so v3 bundles — including connected scenes produced by the new geodetically-correct scene-connect tool (autowarefoundation/3dgs_io#48) — could not be loaded.
What
Dependency: pin 3dgs-io to v2.0.0. This pulls spz v3.0.0 transitively (required to parse NGSP v4 chunks); splatsim's pyproject mirrors 3dgs_io's CMAKE_ARGS=-DCMAKE_DISABLE_FIND_PACKAGE_zstd=TRUE extra-build-variable because uv does not propagate it from a git dependency (distro libzstd.a is non-PIC).
Loader (splatsim/_usdz.py): read_scene_json / load_spz_scene accept both splatsim.scene/v2 and /v3.
v3: chunks are read in gaussians.chunks index order; LiDAR attrs come from the embedded extension record via extract_lidar_extension, with a hard error when a chunk that should carry the record lacks it.
v2: unchanged sidecar path through the renamed decode_lidar_extension (payload format is identical).
The attr→tensor wiring (intensity/raydrop, optional lidar_mask, optional raydrop_sh) is factored into one shared helper.
Tests: follow the encode_lidar_sidecar → encode_lidar_extension rename; new v3 coverage builds a real NGSP chunk, embeds a LiDAR record, and round-trips it through load_spz_scene (plus chunk-index loading and missing-record error cases).
Validation
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 uv run pytest: 191 passed.
Real data (RTX 4090): the 7-scene odaiba outbound v3 bundle produced by 3dgs_io's scene-connect loads all 32,340,153 gaussians (raydrop_sh degree 2 intact) and the 5-sensor LiDAR rig returns a stable ~0.5 M points/frame at 0/50/100/200/500 m along the rig trajectory — the scenario that originally failed (~50 m LiDAR dropout) was caused by the broken ecef_anchor in the old externally-connected bundle, fixed on the 3dgs_io side.
Backward compatibility: existing v2 bundles (scene_unified_vad.usdz) still load with spz v3.0.0.

fix(lod): gate per-cell tier on nearest cell point, not center
…
413d8a7
```
Tier selection used the cell-center distance while the whole-cell
max-range cull used center-minus-radius. Octree leaves are density-
adaptive, so a sparse region stays one large cell (radius tens of
metres). The center-distance gate made a large cell the sensor stood
at the EDGE of read as "far" and drop to a coarser tier, then snap to
the fine tier the instant the moving ego crossed far enough for the
center to fall under the threshold -- a step change in kept Gaussian
count (tier0 1.0 -> tier1 0.5 is a 2x density jump) right at the cell
boundary, seen as LiDAR returns abruptly thinning on approach and
popping dense on crossing.

Subtract cell_radius (clamped at 0) before the tier gate so selection
uses the cell's nearest point, matching the max-range cull convention
and removing the boundary pop. Only relaxes tiers toward finer near a
boundary, so density can only increase.
```
