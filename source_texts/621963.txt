Improvement rationale
CUDA-JS currently owns device memory and computation but has no public graphics/display interop path. Visualization-oriented consumers therefore must copy results back through host memory before another graphics API can use them. Generic CUDA external-memory/semaphore or graphics-resource interop belongs below media/ray/product semantics and can remove that forced host round trip on supported profiles.
This issue owns a lower mechanism assessment, not rendering/window/swapchain semantics and not an assumption that WebGPU exposes the required native handles everywhere.
Candidate first profiles
Compare the smallest viable interop shapes for current Node/platform reality, for example:
import/export of a bounded external device-memory resource through a supported OS/API handle family;
external semaphore synchronization for producer/consumer ownership transfer;
a specifically qualified Vulkan/OpenGL/D3D/WebGPU bridge only where both sides expose a stable interoperable handle contract.
Select one profile from actual consumer/platform evidence rather than promising every graphics API at once.
Required contract
opaque external-resource capability; no raw native pointer/handle in ordinary API;
exact external owner/importer identity and finite byte/range/layout requirements;
explicit ownership-transfer/synchronization/coherence semantics;
one visible owner for lifetime and terminal disposition while resources are shared;
correct behavior when the graphics/device adapters are different or non-peer compatible;
imported/exported resource identity in compatibility/evidence records;
fail closed before partial native ownership on unsupported handle/API/device combinations.
Evidence
independent native layout/handle/semaphore oracle for every promoted OS/API profile;
CUDA writes become visible to the graphics consumer only after the declared synchronization edge and vice versa where bidirectional use is admitted;
repeated frame/resource reuse does not leak handles, allocations, semaphores or contexts;
a host-copy baseline remains available and output-equivalent;
any latency/bandwidth claim includes graphics API, adapter identity, synchronization and host-copy control.
Ecosystem boundary
cuda-media may own image/frame/pixel/codec semantics; cuda-ray may own ray/geometry/traversal semantics; rendering/window/swapchain/canvas meaning remains external/product-owned. CUDA-JS owns only the native CUDA memory/synchronization interoperability mechanism.
Non-goals
Renderer or canvas framework, automatic device matching, arbitrary native-handle passthrough, universal WebGPU interop guarantee, graphics API administration, implicit synchronization, or treating external memory as zero-copy on every platform.
