Abstract—High-fidelity 360° virtual tours require the transmission and rendering of massive equirectangular projections, often
reaching 8K resolutions. Traditional WebGL frameworks, such
as A-Frame, rely on monolithic texture mapping, forcing client
devices to decode and load the entire image payload into Video
RAM (VRAM) prior to rendering. This paradigm introduces
severe Initial Load Time (ILT) bottlenecks and memory overflow
crashes on legacy hardware and constrained networks.
This paper details a novel viewport-adaptive 360° rendering
architecture developed for the Temple360 platform over a sixmonth research period. Our methodology employs an offline data
pipeline to normalize and partition equirectangular images into a
Dual-Tier Spatial Grid of micro-tiles. On the client, we implement
an O(k) frustum culling engine that dynamically calculates
spherical intersection bounds, fetching only the k visible tiles
within the user’s Field of View (FOV). Furthermore, we introduce
a Progressive Spatial Resolution (PSR) heuristic utilizing an
Exponential Moving Average (EMA) of network latency to
dynamically swap highly compressed baseline tiles for HighDefinition (HD) variants in real time. We provide an algorithmic
complexity analysis and experimental evaluation, demonstrating
an 85% reduction in peak VRAM allocation, a 600% acceleration
in Time to Interactive (TTI), and a mathematically grounded
solution for dynamic hotspot reprojection across a shifting 2D
canvas.

I. I NTRODUCTION
The democratization of cultural heritage through virtual
tourism relies heavily on web-based delivery mechanisms.
Platforms like Temple360 aim to provide immersive, highresolution darshan (viewing) experiences of sacred temples
directly through standard web browsers. However, achieving
high visual fidelity in 360° virtual environments presents a
formidable systems engineering challenge in terms of payload
size, bandwidth, and memory management.
Standard WebXR implementations rely heavily on frameworks such as A-Frame and Three.js, which internally build
on WebGL [10]–[12]. These libraries employ a monolithic
texture-mapping paradigm: a single, continuous equirectangular image is applied to the interior normals of a 3D spherical
mesh. While this approach benefits from native GPU hardware
acceleration during the rendering loop, it incurs catastrophic
initialization costs. An uncompressed 8K image (8192 × 4096
pixels) utilizing a 4-byte RGBA color depth requires approximately 134 Megabytes of VRAM. For users accessing
the platform via mobile networks in developing regions, this
results in unacceptably high Initial Load Times (ILT) and
frequent browser tab crashes due to memory exhaustion.
In parallel, there is a large body of work on adaptive
360° video delivery that addresses bandwidth and latency constraints at the transport and encoding layers using tile-based
HTTP streaming, viewport-adaptive encoding, and superresolution [1]–[6], [9]. These systems, however, typically
assume dedicated video players and do not directly solve the
problem of monolithic WebGL texture binding in generic webbased virtual tours.
To circumvent the fundamental limitations of monolithic
WebGL texture wrapping, we engineer a custom rendering
pipeline from first principles. By treating the panorama not as
a single image, but as a queryable spatial database, we develop
a viewport-adaptive renderer. This system mathematically calculates the active viewing frustum, issues targeted network
requests for specific spatial tiles, and stitches the environment
dynamically on a 2D HTML5 canvas. This paper details the
mathematical foundation, algorithmic complexity, and systemlevel trade-offs of this architecture.
II. S YSTEM A RCHITECTURE : O FFLINE P IPELINE
The architecture is strictly decoupled into a server-side
offline preprocessing pipeline (the Converter/Checker) and the
online client-side rendering engine.
A. Aspect Ratio Normalization and Padding
Equirectangular projection mathematically demands a precise 2 : 1 aspect ratio, mapping 360◦ of longitude to 180◦ of
latitude. Raw photographic data often deviates from this ratio.
The preprocessing algorithm first evaluates the source resolution (Wsrc , Hsrc ). If Wsrc /Hsrc ̸= 2, a padding algorithm
calculates the geometric center and applies non-destructive
black-pixel padding to enforce the 2 : 1 constraint, ensuring
zero additional distortion during spherical reprojection.
B. Dual-Tier Spatial Partitioning
Once normalized, the image undergoes spatial partitioning.
The monolithic projection is sliced into an M × N grid of
discrete micro-tiles. To support highly constrained networks,
the Converter generates a Dual-Tier Spatial Grid, producing
two distinct variants for every coordinate (u, v):
1) Compressed Baseline (Tcomp ): Aggressively quantized
WebP representations (e.g., Q = 30). These serve as the
“scaffolding” to guarantee immediate visual feedback.
2) High-Definition (THD ): Low-compression variants
(e.g., WebP Q = 90 or JPEG) representing maximum
fidelity.
These tiles are indexed in a static server directory structure
(e.g., /scene_id/hd/u_v.webp), allowing the client to
execute O(1) direct URL lookups without requiring an active
database query layer. The use of a regular spatial grid is
conceptually aligned with classical spatial data structures used
for efficient querying on large images and maps [13].

The client-side engine replaces standard WebGL spherical
meshes with a dynamic 2D canvas updated at 60 Hz. The core
of this engine is the mathematical frustum culling algorithm
operating in spherical coordinates.

B. The Meridian Wrap-Around Problem
A critical mathematical challenge in 360° tile calculation occurs at the longitudinal seam (where θ = π wraps to θ = −π).
If the calculated umax > 1.0, the bounding box conceptually
splits. Our algorithm detects this overflow and bifurcates the
request array, requesting tiles from [umin , 1.0] and mapping
the remainder to [0.0, umax − 1.0]. This guarantees that all
visible tiles are requested, even when the camera straddles the
meridian.
C. Dynamic Hotspot Reprojection
Because we discard the 3D WebGL sphere, interactive
hotspots (info panels, scene links) cannot be anchored to static
3D meshes. Instead, they must float over the 2D canvas as
DOM elements. This requires dynamic reprojection on every
frame.
A hotspot stored at 3D coordinate P = [x, y, z, 1]T is
multiplied by the View Matrix V (derived from the camera’s
inverse transform) and the Projection Matrix Pproj (derived
from the FOV):

and DOM-based UI overlays.
IV. N ETWORK H EURISTICS AND C ACHING
A. Progressive Spatial Resolution (PSR)
To handle varying bandwidths in mobile networks, particularly in deployment conditions, the renderer utilizes Progressive Spatial Resolution (PSR). The engine calculates an Exponential Moving Average (EMA) of recent tile fetch latencies
(Lcurr ):
EM At = α · Lcurr + (1 − α) · EM At−1
(4)
where α is a smoothing factor (e.g., 0.2). If EM At falls below
a defined millisecond threshold, the engine asynchronously
upgrades the currently visible Tcomp tiles by dispatching
requests for the THD variants. When EM At rises above a
back-off threshold, the system suppresses HD upgrades to
avoid rebuffering and stalls, analogous in spirit to QoE-driven
rate-adaptation strategies in 360° video streaming [1]–[3].
B. LRU Tile Caching Policy
To prevent memory leaks as the user pans around the 360°
environment, the engine implements a Least Recently Used
(LRU) cache policy. Let Cmax be the maximum allowed
number of tiles in memory. As new tiles are fetched, the
algorithm updates their timestamps. If the total cached tiles
exceed Cmax , the engine explicitly deletes the image objects
with the oldest timestamps, releasing them to the browser’s
garbage collector. The cache parameters can be tuned per
device class to respect VRAM limits on low-end smartphones
versus desktops.
V. A LGORITHMIC C OMPLEXITY A NALYSIS
Let the equirectangular projection be divided into an M ×N
grid, totaling Ttotal tiles. Let the viewing frustum encompass
exactly k tiles, where k ≪ Ttotal .
A. Time Complexity
In a naive monolithic approach, mapping the texture requires O(M × N ) decoding time before the first frame. In
our architecture, the bounding-box calculation requires O(1)
time. Determining the visible set by iterating through the
boundary indices takes O(k) time. The per-frame rendering
loop therefore issues exactly k draw calls. Thus, the realtime computational complexity of our visible-tile selection and
drawing pipeline is strictly O(k).
B. Space Complexity
Server-Side: Due to the Dual-Tier grid, the server stores
both Tcomp and THD per coordinate. The space complexity
is O(2 · (M × N )), effectively doubling the storage footprint
compared to a single-resolution tiling.
Client-Side: A standard A-Frame/WebGL renderer requires
O(M × N ) VRAM for the monolithic texture. Thanks to
the LRU cache and frustum culling, our client-side space
complexity is strictly bounded to O(k + Cbuf f er ), where
Cbuf f er is the small cache margin. This mathematical bound
is the precise mechanism that prevents legacy device crashes,
at the cost of streaming additional tile requests over time.
The primary trade-off observed is the rendering-speed overhead. Drawing k individual tiles to a 2D canvas via JavaScript
incurs higher CPU overhead than a single WebGL shader
pass, resulting in frame rate drops during aggressive camera
panning. Mitigating this overhead (e.g., by batching draw calls,
tuning tile size, or offloading more work to WebGL) is an
important avenue for future work.
VII. C ONCLUSION
We have engineered a custom viewport-adaptive 360° renderer that optimizes both time and space complexity for webbased virtual tourism. By abandoning monolithic O(M × N )
texture mapping in favor of O(k) frustum culling and EMAbased network heuristics, the Temple360 platform provides
high-fidelity access even under severe client hardware and
bandwidth constraints. While the system concedes peak rendering frame rates and assumes non-trivial hotspot reprojection calculations, the substantial improvements in Time to
Interactive and memory stability demonstrate that tiled spatial
partitioning is a practical and scalable strategy for web-first
panoramic deployments.
