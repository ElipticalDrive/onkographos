Summary
Make tile heights from the world YAML grid fully usable so hills, mountains and cliffs are possible: visible terrain with cliff sides, correct picking on raised tiles, and units/objects standing on the actual tile height.
Depends on: World format v2 (grid documented as height levels, units in the world file, tileToWorldPos used for unit placement).
Height convention
grid values are height levels (uint8, 0-255): 0 = flat ground, 1 = one tile length above 0, 2 = two tile lengths, and so on.
Introduce a single height scale constant (world units per height level, default 1.0 = one tile length) used everywhere heights are converted to world Y, so the scale can be tuned later without touching maps.
Current state
Heights are already parsed: WorldBuilder stores the grid as std::vector<std::uint8_t> and buildWorldMesh (WorldBuilder.cpp ~:167-200) places each tile quad at y = map[row * size + col].
Unit occupancy (World::_idxToEntityId), tile flags (World::_vflags) and heights are separate per-tile layers, so heights do not conflict with unit IDs.
Missing:
no vertical faces between neighbouring tiles of different height (hills render as floating plates with gaps);
mesh normals are vec3(0) and the world shader uses a flat colour, so height steps are hard to see;
picking (PositionCalculation::getWorldPosition, ~:10-26) intersects the plane y = 0, so clicks on raised tiles resolve to the wrong tile;
World does not keep the heights after loading; World::tileToWorldPos returns y = 0, so units, movement waypoints and misc objects would stand inside hills (spawnMisc currently reads the height itself in Lua).
Implementation
Heights in World: store the height map (and the height scale) in World when the world is created (WorldBuilder::loadWorld). Add float getTileHeight(std::int32_t idx) (world units, height level x scale).
tileToWorldPos returns the tile height as Y. Everything using it (unit spawning from units:, misc objects, movement waypoints via followPath, projectiles targeting positions) automatically lands on the tile surface. Remove the separate height lookup from spawnMisc in Lua.
Cliff sides in buildWorldMesh: for each tile edge where the neighbour is lower (or the grid border), emit a vertical quad from the neighbour height (or 0 at the border) up to the tile height. One quad per edge, correct winding, so no gaps are visible from any camera angle.
Normals + simple lighting: set proper normals for top faces (up) and side faces (outward), and add basic directional lighting (ambient + diffuse) to worldshader so height steps are readable. Optional: slight colour tint by height level. Existing tile flag effects (hover, reachable, fog/visibility) must keep working on top faces; side faces use the flags of their owning tile or stay unhighlighted.
Height-aware picking: replace the y = 0 plane intersection with a ray test against tile top faces (e.g. step the ray through the grid in screen-to-world order and take the first tile whose top it hits, or test the ray against each tile top within the grid for small maps). Hover, clicks (PlayerControl), and worldPosToTile must resolve the tile the cursor visually points at, including tiles partially hidden behind higher terrain.
Shader tile index: worldshader.fs derives the tile index from worldPos.xz; verify it is unaffected by height and correct for side faces.
Out of scope
Movement cost by height difference (climbing rules, equipment) - separate ticket later. Reachability/BFS stays height-agnostic for now.
Height affecting line of sight or hit chance.
Slopes/ramps (only stepped heights).
Editor support for heights (covered by the WestEditor ticket).
Tests
World unit tests: getTileHeight and tileToWorldPos Y for flat and raised tiles, height scale applied.
Mesh test (if buildWorldMesh can be exercised without GL): vertex/face counts for a small grid with a single raised tile (top quads + expected side quads), no side quads for a flat grid.
Picking test for the pure math part (ray vs. raised tile tops), if extracted into a testable function.
Manual: a demo world with a hill (e.g. heights 0/1/2/3 in a small area) and a cliff edge; check visuals from different camera angles, hover/click accuracy on and behind hills, units and trees standing on top of raised tiles, units walking up and down along the path, fog/LoS and reachable highlights on raised tiles.
Acceptance criteria
Hills render as solid stepped terrain without gaps, with visible shading between levels.
Hover and clicks select the visually targeted tile on raised terrain.
Units, misc objects and movement waypoints sit on the tile surface at every height.
Existing gameplay (movement range, LoS, fog, blocked tiles) behaves as before on flat maps.
