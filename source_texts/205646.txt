jolt-ray-edge-repro.zip
A ray that lands exactly on an edge two triangles of one MeshShape share can miss both triangles. CastRay then reports no hit, as if the ray had passed through a gap. The triangles share their vertices exactly, so there is no gap. Rays that land anywhere else always hit.
This is easy to run into with a mesh on a regular grid, such as terrain, voxel or surface-nets meshes, or a floor of quads: a ray lines up with an edge whenever the camera stands on a grid line and faces along an axis. We found it through Godot, which uses Jolt by default (godotengine/godot#124689); the attached program reproduces it with Jolt alone.
Results
Jolt v5.6.0, Windows 11 x64, MSVC 19.39, Release, default CMake options. A floor of 0.5 m quads at y = 0, each split into two triangles, spanning −12 m to 12 m. Rays from eye height (y = 1.6) through 1,617 points every 1/8 m, from x = −2 to 2 and z = 2 to 8, which takes in every shared edge and vertex there, and through 20,000 random points in the same area. All targets lie well inside the floor, so every ray should hit it.

RayTriangle4 alone calls it directly on the unquantized vertices of every triangle, so the misses come from the test itself.
MeshShape::CastRay misses four to six times as many. I haven't looked into why; perhaps the vertex quantization, or the order in which the codec stores each triangle's vertices, changes the rounding.
The watertight test is Woop, Benthin and Wald, "Watertight Ray/Triangle Intersection" (JCGT 2013), used by Embree and pbrt, written as a plain scalar function, HitsWatertight in the attached main.cpp. It never missed.
Likely cause
RayTriangle4 (and RayTriangle) is Möller–Trumbore. Each triangle computes its barycentric coordinates from its own first vertex and edges, so on an edge two triangles share, rounding can put the point just outside both.
The watertight test shears every vertex into a space where the ray runs along +Z. The shear depends only on the ray, so a vertex shared by several triangles lands in the same place for each, and the edge tests are 2D cross products of those points: neighboring triangles compute the same value for a shared edge with opposite signs, and so can't both reject the ray. Exact zeros are decided again in double precision, which makes vertices watertight too.
The shear (which axis is Z, and the three shear factors) is set up once per ray, so in TriangleCodec...::TestRay it could be done before the loop over triangle blocks. I haven't measured the cost.
Workaround
Cast a second ray a millimeter to one side, in a direction lined up with no grid axis, and take the nearer hit.
Program
jolt-ray-edge-repro.zip holds main.cpp and a CMakeLists.txt that builds it against a clone of JoltPhysics beside it:
```
git clone --branch v5.6.0 https://github.com/jrouwe/JoltPhysics.git
cmake -S . -B build
cmake --build build --config Release
build/Release/RayEdgeRepro
```
It prints the table above.

I am aware of this issue and potential fixes for it. It is likely though that that will only shift the issue. E.g. if you have 2 terrain sections connecting, then it is very likely that the edge between these sections will have the same issue (because both triangles must be converted from local to world space and will have float round off issues). We program our collision check defensively if it is important they cannot miss: use a small swept sphere instead of a single ray or we use multiple rays.
I'll leave this ticket open, maybe I'll get around experimenting with this.
