Problem
Rendering code needs a consistent interpretation of projected depth. With standard depth, near geometry typically maps to smaller depth values; with reverse-Z, it maps to larger values. This choice affects more than Gaussian splats: depth testing and clearing, transparent sorting, depth reconstruction, depth-based effects, occlusion and depth pyramids may all depend on it.
PR #3619 addresses one manifestation by adding an explicit depthConvention option to SplatRenderer. That is a useful scoped fix, but requiring each renderer or effect to receive an independent setting can lead to duplicated configuration and inconsistent interpretation of the same camera and depth attachment.
Goal
Design a shared way to describe and propagate the active depth convention so camera, render-pass setup, renderers, and depth consumers can agree on its meaning. Keep the design usable when luma.gl is embedded in an application that owns the camera or render pass.
Design questions
Where should the authoritative convention live: camera or projection metadata, render-pass/depth attachment metadata, a rendering context, or a combination? How should it flow to consumers?
How should externally supplied projection matrices and externally owned render passes express the convention? Can common projection types be detected safely, and when is explicit metadata required?
Should common depth comparisons provide a convenience default (less/less-equal versus greater/greater-equal), and how are ambiguous comparisons such as always handled? A depth comparison alone does not prove the projection convention.
How should explicit overrides, defaults, backwards compatibility, and mismatched camera, comparison, and clear values be handled?
How do WebGL and WebGPU clip-space differences, orthographic and perspective projections, infinite far planes, and custom projections affect the contract?
Which existing depth consumers should adopt it, including splat sorting, other transparent sorting, depth reconstruction and effects, occlusion, and depth pyramids? Identify actual consumers before changing their APIs.
How should convention changes invalidate cached or GPU-derived state, and what tests should cover both conventions and external integration?
Scope and acceptance criteria
Document the chosen source of truth, propagation and override rules, including behavior when convention information is unavailable.
Inventory affected luma.gl APIs and consumers and propose an incremental migration that preserves existing behavior by default.
Cover standard and reverse-Z perspective and orthographic cases, depth clear and comparison configuration, and externally owned camera/render-pass integration in the test plan.
Decide how the SplatRenderer option introduced by fix(splats): support explicit reverse-Z alpha ordering #3619 relates to the shared design.
The convention describes the active projection/rendering setup rather than the splat asset itself. loaders.gl should not need to infer it from splat data; an application or camera integration that owns the projection can supply the metadata.
