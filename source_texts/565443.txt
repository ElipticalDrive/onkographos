Enabling volumetrics kindof defeats the jaggy-removing of MSAA, since I think it is only doing the raymarching once per pixel, which would result in alias-like behavior on pixels with samples that vary greatly in depth. You can see this on the screenshot below. There are multiple methods to "fix" this, but one of them would be to do the MSAA resolve in shader, and do more raymarches (or "extend" the current one further) on pixels that fit the conditions. (not very fast, but it would fix the jaggies)
Here is a screenshot showing the artifacts.
full screenshot here
If you could figure out a method that allows the volumetric shadows to be rendered separate from the fog itself, then you could probably get away with rendering it at a lower resolution before rendering the world, and then compositing it similar to a SSAO upscale and blur.

Most of post-process effects (namely, motion blur, SSR, SSAO, DoF, and volumetric fog) are not designed to work with MSAA at all. MSAA is mainly intended for low-end video cards where most options have to be turned off and even FXAA is too costly, yet antialiasing is desired by users.
Plus, MSAA textures are harder to use since they need a special texture type, hence separate shaders, more #ifs, and increased code complexity.
I know FXAA’s quality is not very good but adding a bunch of code to make existing effects work with MSAA doesn’t seem like a right option. I’d propose temporal AA (#597) instead.

Temporal AA is nice, but MSAA is already implemented. The only screenspace effect that has noticeable artifacts with MSAA is volumetric fog, all others can do the MSAA resolve before and then sample a usual texture (like how its currently implemented) without any issue.
Also, using MSAA textures would be more of a "quick fix" than a real workaround. Volumetric fog shouldn't need to do a separate raymarch for every sample, or even every pixel.
Is the volumetric fog raymarching done as a fullscreen quad?
If it is, I guess a cheap fix would possibly be to render it in the sunlight pass(or other pass where the actual geometry is drawn). It would do separate raymarches for each of the MSAA samples on the edges of triangles, so that would probably fix the artifacts, and it wont have any overdraw performance issues because of the depth-first prepass. -- but this is also more of a "quick fix" and not an optimal solution.
Even without MSAA, implementing some method of volumetric fog that isn't dependent on being exactly the same resolution/samples as the screen would have its benefits... mainly performance. You could also do a temporal refinement both in screenspace jitter and also raymarch step jitter, like the method by Crytek (which I currently cant find a link for).

There's an additional issue with dealing with MSAA: the OpenGL driver of macOS (which is my primary development environment) doesn't support multi-sample texture in the compatibility profile mode. MSAA texture simply cannot be created. The core profile on macOS mandates the use of a new version of GLSL, which might not be supported by some lowest-end video cards we currently support.
If we had a UE4-style temporal AA, which is not very hard to implement and requires so few features that it can run even on WebGL 1.0, these problems could be addressed all together and would nullify the investment in MSAA-compatible post process (assuming that temporal AA worked very well).
Still, it'd be better if it could render the volumetric fog in a lower resolution, as you suggest. The current implementation (one ray per pixel) is obviously eating up too much GPU time.
