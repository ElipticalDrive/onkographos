Raised on #12630 (comment 6509184430). Porting CUDA code that reads inputs through cudaTextureObject_ts created over linear device memory (cudaResourceTypeLinear, tex1Dfetch<T>(tex, i)) has no direct Slang target today.
Current behaviour (master 977df12):
```
[shader("compute")][numthreads(128, 1, 1)]
void k(uniform Buffer<float> flt, uniform float* outp, uniform uint n, uint3 tid: SV_DispatchThreadID)
{
    if (tid.x >= n) return;
    outp[tid.x] = flt[tid.x];
}
```
-target cuda / -target ptx: error[E36107] with a note on __ShapeBuffer. The rejection is the type-level [require(cpp_glsl_hlsl_metal_spirv)] on __ShapeBuffer (source/slang/hlsl.meta.slang:590), added by Fix #12274: diagnose typed Buffer<T> access on CUDA/PTX instead of silent empty kernel #12289 so that Buffer<T> access fails loudly instead of compiling to an empty kernel ([PTX] Buffer access silently compiles to an empty kernel #12274).
spirv / metal / hlsl compile.
On master, CUDA Texture1D.Load still reaches an empty stub (CUDA/PTX: Texture1D.Load silently compiles to an empty kernel #12630). Draft Fix #12630: implement Texture1D.Load for CUDA/PTX #13377 adds an array-backed path and documents linear-memory texture objects as unsupported.
Request: lower read-only Buffer<T> on CUDA/PTX to a CUtexObject read with tex1Dfetch<T>(obj, i) (PTX tex.1d.v4.{f32,u32,s32}.s32, no level), and keep Texture1D for CUDA arrays.
Workaround today (verified on an L40S, CUDA 12.6: 1000/1000 values correct with a CU_RESOURCE_TYPE_LINEAR float texture object):
```
float fetchLinear(uint64_t tex, int i)
{
    __target_switch
    {
    case cuda: __intrinsic_asm "tex1Dfetch<float>((cudaTextureObject_t)$0, $1)";
    }
}
```
Pass the CUtexObject as a uniform uint64_t. The emitted PTX is tex.1d.v4.f32.s32. Plain pointer loads are another option; the reporter measured them within 7% of the texture path on sm_89.
This workaround changes the declared type. Code that keeps Buffer<T> has no workaround without global flags: a user __target_intrinsic(cuda, "tex1Dfetch<$TR>($0, $1)") function or a __target_switch + __intrinsic_asm function that takes Buffer<uint> still fails with E36107 on cuda and ptx (checked at master 977df12), because the check is on __ShapeBuffer itself.
With -ignore-capabilities, the same __target_intrinsic version compiles. The CUDA kernel parameter is already CUtexObject, the PTX is tex.1d.v4.u32.s32, and on the L40S it returned 1000/1000 correct values from a CU_RESOURCE_TYPE_LINEAR uint32 texture object. So the gap is the __ShapeBuffer requirement and the missing case cuda: in Load (the subscript calls Load), not the parameter type. -ignore-capabilities turns off every capability check (see #13555), so it is a data point, not a recommended workaround.
Points a fix has to decide:
Binding: slang-rhi already reserves an eight-byte slot for a CUDA typed buffer, but it writes a device pointer into it (src/cuda/cuda-shader-object.cpp:20-36), not a texture-object handle.
Element types the texture hardware can return (32-bit single channel is the reported case; float3-like formats have no texture format).
RWBuffer<T> stays out of scope (texture objects are read-only).
slang-rhi creates texture objects only over CUDA arrays or mipmapped arrays (src/cuda/cuda-texture.cpp:196-205), not over linear memory. Its typed-buffer path would need texture-object creation and binding. Raw-CUDA hosts that make their own texture objects would not need that. One OptiX user reports that their host already binds each typed buffer as a linear-memory CUtexObject in the eight-byte slot (comment below).
Related: #12274, #12289, #12630, #13377.

The uint64_t workaround above changes the declared type. Lowering Buffer<T>.Load and the subscript to tex1Dfetch<T> would remove the need for either workaround.
