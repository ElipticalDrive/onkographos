Summary
Replaces PR #1. The original branch was 5 months stale; cherry-pick conflicted on every overlapping file, so this is a clean reimplementation of the same design on top of current main.
The single `VolumeVisual` becomes `VolumeCore` + six concrete visual types, one per rendering algorithm. Each type's API exposes only the parameters that apply to its mode — Direct/Additive get density, MIP gets attenuation, Iso gets threshold, etc. — rather than one struct with mode-irrelevant setters.
Type
Algorithm
`DirectVolume`
Front-to-back alpha compositing (Beer-Lambert). Also hosts existing debug modes (LOD tint / atlas direct / step heatmap).
`AdditiveVolume`
Additive accumulation, no occlusion. Useful for multi-channel composition.
`MipVolume`
Maximum Intensity Projection. `set_attenuation(>0)` switches to vispy-style attenuated MIP.
`MinipVolume`
Minimum Intensity Projection.
`AverageVolume`
Mean intensity along the ray.
`IsosurfaceVolume`
First-hit isosurface with Phong shading + sub-voxel bisection against a smooth manual-trilinear field.
Shader
Six fragment entry points (`fs_translucent`, `fs_additive`, `fs_mip`, `fs_minip`, `fs_average`, `fs_iso`) sharing the setup_ray / compute_advance / contrast_normalise helpers. Three notable details:
Attenuated MIP follows vispy: each step's attenuation is driven by accumulated contrast-normalised density, not raw ray distance. So empty regions don't burn through the attenuation budget. Includes a contrast-ceiling early termination — once `maxval > contrast_max * scale`, no future sample can do better.
Isosurface bisection uses manual trilinear (8 page-table walks per sample) because the VT atlas sampler stays Nearest. Hardware linear filtering would leak between tile slots since there are no border guards yet. The cost is only paid for the ~10 samples inside the bisection + gradient stencil, not the coarse ray-march.
Gradient stencil for the iso normal is sized to the resident LOD's voxel — collapsing it to a fixed step would zero the gradient inside coarse voxels.
Page-table encoding unchanged
Stays at `(resident:1, atlas_id:2, t:13, slot:16)` — multi-atlas friendly, no encoding changes from PR #5.
API surface
Rust: `DirectVolume::new(…)` / `AdditiveVolume::new(…)` / etc. with identical signatures to the old `VolumeVisual::new`. `VolumeVisual` itself is gone.
Python: a local `py_volume_class!` macro generates `PyDirectVolume` / `PyAdditiveVolume` / `PyMipVolume` / `PyMinipVolume` / `PyAverageVolume` / `PyIsosurfaceVolume`. Common methods (set_contrast, set_colormap, set_relative_step_size, set_lod_bias, set_chunk_data_u16, wanted_keys, get_stats) are in the macro body; mode-specific ones (set_density_scale, set_attenuation, set_iso_threshold, set_debug_mode…) pass through the `extra: { … }` arm.
WASM: `js_volume_class!` does the same shape. `JsViewer` gains six `addX_Volume` methods, one per type, so each visual reference is type-checked.
Examples
`volume_renderer/python` and `volume_renderer/web` pick `DirectVolume` / `JsDirectVolume` and document the other five in a code comment. A full Mode-dropdown UI is straightforward to add on top but adds ~380 LOC of UI plumbing — left as a follow-up; orbit_stream already exercises the Direct path end-to-end and the others are wired through the bindings and ready to call.
`orbit_stream` switches `VolumeVisual::new` → `DirectVolume::new` (one-line change).
Test plan
`orbit_stream` still renders the ZSNS001 OME-Zarr on Linux GL (NVIDIA L40) — verifies DirectVolume regression-free
Each of the six modes produces a sensible image on Metal (Mac) with a synthetic volume
Python `volume_renderer` example still loads and renders
WASM `volume_renderer` example still loads and renders
HPC L40 GL: ray-marching helpers work on the core profile (no naga regression on the multi-entry-point shader)
Closes
Closes #1 (replaces with this reimplementation against current main).

fs_iso: drop manual trilinear, halve bisection iterations
…
1cd862b
```
Both the bisection refinement and the gradient stencil were sampling
the manual trilinear field — 8 page-table walks per sample, 11 samples
per hit pixel, ~88 walks before lighting. Visually nice in theory but
the orbit-stream's typical viewing distance makes the smoothness
indistinguishable from Nearest, while burning a lot of GPU time.

Replace `sample_trilinear_adjusted` calls in fs_iso with the cheap
`sample_adjusted` (= sample_vvt + contrast_normalise + 0 fallback for
unresident regions). The gradient stencil straddles a full voxel so
+h/-h always land in different voxels — Nearest gives a well-defined
gradient. The bisection now converges to the voxel-boundary crossing
rather than the smooth iso-crossing; at 3 iterations on a step_size = 1
LOD-0-voxel coarse step that's 1/8 of a voxel of t-precision, below
any visible pixel at orbit distance.

Bisection iterations 5 → 3.

Net per hit-pixel: 88 page-table walks → 9. ~10× faster on iso pixels.
The manual `sample_trilinear_adjusted` function is now unused and
deleted; `lod_voxel_size_uv` stays (still drives the stencil size).

fs_iso: replace 6-tap central difference with 3³ Sobel-Feldman gradient
…
9f0380b
```
The 6-tap stencil produces visible noise/faceting on flat iso surfaces
when sampled at Nearest — each axis sample is a single voxel's value,
so the gradient direction snaps between voxel boundaries.

The 3³ Sobel kernel weights the 26 neighbours of the surface voxel:
on-axis (4), face-adjacent (2), corner (1). Smooths over a 3-voxel
neighbourhood; the directional sum is much closer to the true gradient
than two-sample differences.

Cost: 26 page-table walks per hit pixel for the gradient (vs 6 before),
plus 3 for bisection = 29 total. Still ~3× cheaper than the manual-
trilinear version (88), and the lighting is dramatically smoother.

Kernel is ported from napari's `calculateGradient` GLSL (the
"smooth" gradient path). Border/background-detection fixes from
napari's version are not included — sample_adjusted's natural 0 for
unresident regions gives reasonable behaviour at the volume boundary.

fs_iso: stop double-negating the Sobel normal
…
6cc0b27
```
napari's sobel_gradient uses `val * -float(i) * w`, which produces the
gradient pointing FROM HIGH VALUES TO LOW (−∇f, downhill). For an iso
surface enclosing a high-density interior that's already the outward-
pointing normal direction.

The previous fs_iso had `normal = -grad / glen` — which was correct
for the older 6-tap `f(+h) - f(-h)` stencil (= +∇f, uphill) but
double-negated when paired with the napari Sobel (G is already −∇f,
so −G points UPHILL = INTO the surface = away from the camera).
Result: Phong's `max(dot(normal, light), 0)` clamped to 0 nearly
everywhere → only ambient, surface looked flat / unlit.

Drop the `-` on normal. The Sobel result is used directly as the
outward normal.

volume_renderer python: viewer absorbs vertical resize, not controls
…
ea5609d
```
ViewerWidget defaulted to QSizePolicy.Preferred which doesn't actively
claim extra space, so resizing the QMainWindow vertically would either
no-op or stretch the control rows weirdly.

Set the viewer's policy to Expanding/Expanding, drop the minimum-size
floor to 320×240 (was 800×600 — prevented small windows), and pass
stretch=1 to addWidget so the QVBoxLayout solver gives all extra
vertical space to the canvas. Control rows keep their natural height.
