Description
get_intersection iterates over get_height, which interpolates over 4 calls, unless rounded to the nearest vertex, in which case it only does one call. So snap to the nearest vertex before every call. I considered doing it once before the loop, but if it's off axis, it will always need to be snapped.
We iterate one meter at a time, which is inaccurate if vertex_spacing != 1. direction should be multipled by vertex_spacing after being normalized, as should 4000. However if vs is sub 1, you'll need to not snap to the nearest vertex if the distance is less than 1.
Bonus points:
Rather than iterating linearly, iterate like quick sort does, which will change the algorithm from O(n) to O(log n). Most checks are going to be sub 1000m, likely sub 500m and even 100m. So I'd start looking at 100m, then:
If passed the terrain, check at 50m then continue to divide the remaining in half.
If it hasn't passed, check 1000m, 10,000m, 100,000m. Then divide the remaining section in half. Somewhat like the following picture.

You can check at 0 initially. You first want to establish outside bounds. So, 0 and 100 are good initial checks based on practical use. If 100 is above the terrain, increase 10x each time until 100,000.
Once you have outside bounds, check at the midpoint of your range. You'll be testing points above and below the true terrain height, getting closer and closer to it until within tolerance. (eg <0.001). This is sphere assisted ray marching, though it's not mentioned here.
Look at 0, if below the terrain, quit w/ MAX
Look at 100, if within -.001 quit w/ height
If above the terrain at 100, look at 1000
if above at 1000, look at 10,000, then 100,000 (maximum)
if below at 1000, look at 500
If below at 100, look at 50
if above at 50, look at 75
if below at 50, look at 25
Once you've found the outer bounds (eg. 0 and 100,000 or 0 and 1000), then do a binary search, checking the half way point, and bringing in your minimum or maximum bounds each iteration. Quit when the distance is within tolerance (0.001).
Currently it iterates linearly from 0 to 4000 as O(n) and costs 4000 iterations before determining if it has failed. This new algorithm is O(log n), and can determine a failure in 4 iterations, and a success in up to 31: 1 check if below at 0, 3 more checks if above at 100,000, and up to 27 more iterations (log2(100,000/0.001)) if somewhere between 10,000 and 100,000m (to use the full bounds).
Before submitting a PR, read our contributing doc, and submit to another branch.

If you know the nearest vertices 2 vertices, you can get the other two (or one as below), then you can calculate the intersection point of a ray and a square in 3D space. Grok implements it here in GDExtension, assuming we know for sure the ray intersects the plane and excluding bounds checking:
```
Vector3 calculate_ray_square_intersection(
    const Vector3& ray_origin, const Vector3& ray_direction,
    const Vector3& v0, const Vector3& v1, const Vector3& v2) {

    // Define 4-vertex plane from any three vertices
    Plane plane(v0, v1, v2);
    
    // Compute ray-plane intersection
    float t = -plane.distance_to(ray_origin) / plane.get_normal().dot(ray_direction);
    return ray_origin + ray_direction * t;
}
```
