Layers currently do two jobs at once, and they are not the same job.
A layer is an editing/compositing concern: its own grid, a box, visibility,
a stack order, one on top of another. That part works well. But it is also the
only way to say "this is the left arm", and for that it is the wrong shape —
layers are a flat list of 16, they composite by stacking, and there is no way to
say one thing is part of another.
Proposal
```
Scene
 ├── robot
 │    ├── body
 │    │    ├── base   (layer)
 │    │    └── paint  (layer)
 │    ├── left_arm
 │    └── right_arm   → instance of left_arm      (see #3)
 └── sword
```
Layer = how pixels combine. Object = what the thing is. An object owns a
transform and some layers or child objects; layers keep doing exactly what they
do now, inside one.
```
list_objects
create_object    name [, parent]
move_object      name, dx, dy, dz
rotate_object    name, axis, quarter_turns
set_object_visible / rename_object / reparent_object
```
What it has to respect
Bounds already did the hard part. A layer has an origin and a size in
scene space, so an object transform is a transform of its layers' origins —
no re-voxelisation, and the cost stays proportional to contents.
Snapshot is the undo unit and would have to carry the object tree, the
way it now carries the scene size. Every structural change is already
snapshot-based, so this is an addition to one type rather than new machinery.
.vxm needs a version. VXM3 stores a flat layer list; objects mean
VXM4, with VXM3/VXM2/VXM1 still loading as a single unnamed root
object. That rule has held three times now.
The composite has to stay O(1)-ish per read. get walks layers today.
Walking a tree per read would be worse; the flattened draw order should be
computed when the tree changes, not per lookup.
Why it matters
This is the thing that makes an agent's edits semantic. "Make the robot's left
arm longer" becomes an object operation instead of a coordinate hunt, and the
structure survives in the file so the next session still knows what the parts
are.
It is also where this stops being a MagicaVoxel clone. MagicaVoxel has a world
editor; what it does not have is a scene graph that a human and an agent are
both editing through the same API.
Depends on #1 for the transform maths. Enables #3.
From the roadmap discussion — item 2 of 1–4.

Shipped in #30. Objects are a name, a visibility and a parent in a flat arena
with a root at index 0; layers name the object they belong to; .vxm is VXM4
with VXM3/VXM2/VXM1 still loading as one root object holding every layer.
Eight MCP tools, and describe_model carries the tree.
The constraint in this issue — "an object transform is a transform of its layers'
origins, no re-voxelisation" — turned out to settle the design: there is
deliberately no transform stored on an object. move_object applies its
translation to Bounds::origin at the moment it is asked, so layer boxes stay in
scene coordinates and get, the raycaster and the extractor never learn what an
object is. Moving a finished robot costs three u16 per layer, and
allocated_cells is asserted unchanged across a move.
The compositing requirement held too. Layer::shown caches "own flag AND every
object above it", recomputed only on a structural change, so get costs exactly
what it did before. Its drift test found a real bug on the way in:
remove_object moves layers up out of a hidden object, putting them back on
screen, and was not recounting.
rotate_object is not here — it needs re-voxelisation and belongs with the
transform machinery rotate_selection already has — and the layer panel still
lists layers flat. Both are #32.
