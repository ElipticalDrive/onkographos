Fixes #1777. Fixes #1805.
Summary
Problem: The CUDA kernel keeps the clipped triangles of each box in fixed MAX_TRIS = 100 per-thread arrays. BoxIntersections writes tri_verts_updated[offset] before the count is clamped, and the merge step appends Box2 triangles to box1_intersect[box1_count++] without a bound. Inputs whose clipped surface needs more than 100 triangles therefore write out of bounds or silently drop faces, giving wrong volumes and IoU (or the illegal memory access reported in box3d_overlap may cause “RuntimeError: CUDA error: an illegal memory access was encountered” in some cases #1805).
Bound: ClipTriByPlane emits at most two triangles, so 12 box triangles clipped by six planes produce at most 12 * 2^6 = 768 triangles per side. MAX_TRIS is now derived from this control-flow bound, and a CUDA_KERNEL_ASSERT checks every append.
Storage: The per-side lists and the clipping scratch live in one bounded global workspace (at most 2400 workers, 253 MiB) instead of per-thread arrays; threads reuse their slot with a grid-stride loop. The two side lists are read through a concatenated view, so the summation order of PolyhedronCenter / BoxVolume is unchanged.
Follow-up commit: Clipping alternates between the output and scratch buffers instead of copying back after every plane, and the coplanar filter compacts Box2 in place, removing the Keep buffer. Results are bitwise identical to the first commit.
CPU path: Unchanged; it already uses growable vectors.
#1805 input
The #1805 boxes clip to 31 triangles on one side and 109 on the other (140 total), on both the native CPU helpers and the CUDA helpers.

Memory: Device memory taken by the first call drops from 4252 MiB (local-memory reservation for the 15408-byte stack) to 94–348 MiB; the stack is now 992 bytes with 255 registers.
Throughput trade-off: Large batches are slower because the 253 MiB budget caps the kernel at 75 blocks of 32 threads. As a diagnostic only (not in this PR), a 1 GiB budget brings 100x100 to 2.233 ms. A per-face polygon clipper would remove the triangle fragmentation and the global workspace entirely; I'd suggest that as a separate change since the CPU path should move with it.
Validation
Environment: Linux, Python 3.12.13, PyTorch 2.11.0+cu130, CUDA 13.0, NVIDIA B200 (sm_100).
Regression tests: New tests cover the box3d_overlap may cause “RuntimeError: CUDA error: an illegal memory access was encountered” in some cases #1805 boxes in both orders and in mixed batches, pair counts around the block size and the worker cap (31/32/33, 2399/2400/2401), worker reuse on a 49x49 batch, repeated calls, a non-default stream, a non-current device, and empty inputs, on CPU and CUDA.
Module suite: All 18 tests in tests/test_iou_box3d.py pass (Python seed 0).
Memory checking: The new regression tests pass under compute-sanitizer --tool memcheck with 0 errors. A diagnostic build with the old capacity of 100 stops at the new assert before writing out of bounds.
Agreement: On 12x15 independently rotated high-overlap boxes, CPU/CUDA differences are at most 3.6e-7 (volume) and 3.0e-7 (IoU). On 30704 rotated pairs, the two commits produce bitwise identical outputs.
Formatting: clang-format, flake8, usort and git diff --check pass on the changed files.
Evidence and reproduction
#1805 results and clipping trace: CPU/CUDA volume and IoU in both argument orders, and the triangle count after each clipping plane.
Benchmark results: latency and first-call memory for all 13 cases at the baseline, first commit and final revision; raw per-sample data is in the benchmark-*.json files.
Module suite and memcheck run on the final revision; small-capacity diagnostic showing the assert fires before an out-of-bounds write.
Reproduction instructions: revisions, scripts, fixture, and validation limits.
Storage: Evidence is maintained on the fork's pr_assets branch; figure and data links pin commit b51df1c.
Verification limits
One GPU model and one software stack; the full repository test suite was not rerun for this change.
The throughput regression above is measured and accepted in exchange for correctness and bounded memory; the budget is a fixed constant rather than tuned per device.

Author
Follow-up: #2060 builds on this PR and replaces the triangle splitting with per-triangle polygon clipping on both CPU and CUDA.
While validating this fix against exact float64 intersections, I found that the existing algorithm (on main, and unchanged here) also has an accuracy problem: faces are matched as coplanar up to ~2.5 degrees apart, and coincident faces are only deduplicated above an absolute 1e-4 area. Rotated boxes can be off by up to 0.25 in IoU, and boxes smaller than ~0.01 with shared planes can give IoU above 1 or inf. #2060 fixes that as well, removes the workspace added here, and is faster than main on both CPU and CUDA (100x100 on a B200: 1.32 ms on main, 5.53 ms here, 0.68 ms in #2060).
The two can be reviewed in order, this PR first as the minimal capacity fix. If you would rather land a single change, #2060 contains both commits from this PR, so reviewing only #2060 is enough.
