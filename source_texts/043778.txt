Goal
Select the long-term rendering backend for the Multiwfn GUI using reproducible scientific visualization tests rather than appearance alone.
The final solution must be open source, visually polished, embeddable in both Qt WebEngine and a browser, and capable of representing Multiwfn volumetric results correctly.
Required capabilities
Periodic crystal structures and triclinic cells.
Fractional display ranges such as [-0.25, 1.5] along each lattice vector, not only integer 2x2x2 supercells.
Periodic cube/volume rendering without broken boundary surfaces.
Multiple simultaneous cube layers with independent isovalues, colors, opacity, visibility, and materials.
ESP/IRI-style rendering: extract an isosurface from cube A and color every surface vertex by interpolated values from cube B.
Arbitrary and crystallographic 2D volume slices, with contour and filled-map views.
Good lighting, transparency, outlines, depth handling, export quality, and acceptable performance on large grids.
A customizable UI and a stable programmatic API suitable for GUI/CLI parity.
Candidates to prototype
3Dmol.js, BSD-3-Clause: already integrated; supports cube volumes, multiple surfaces, and cross-volume coloring. Fractional periodic display is currently implemented by this project, but periodic boundary quality and material flexibility need stronger validation.
MatterViz, MIT: polished materials-oriented UI built on Three.js/Threlte. It currently supports CUBE/CHGCAR, multiple parsed volumes, multi-layer isosurfaces, periodic halo padding, integer supercell tiling, and HKL slices. Its current supercell parser accepts positive integers only, and cross-volume surface coloring does not appear to be implemented yet.
Mol*, MIT: mature structure/volume representations and themes; suitability for materials workflows and cross-volume coloring needs a prototype.
NGL, MIT: supports CUBE and other density volumes; periodic-range and cross-volume behavior need verification.
vtk.js, BSD-3-Clause: strong general-purpose contour, scalar-coloring, slice, and volume pipeline, but molecular/crystal interaction would require more custom work.
JSmol, LGPL-2.1: mature periodic, cube, and molecular electrostatic-potential functionality; visual quality, bundle size, and integration ergonomics need comparison.
Other open-source candidates are welcome if their license and maintenance status are documented.
Evaluation prototype
Render the same reference datasets in each serious candidate:
A triclinic periodic structure using non-integer fractional display ranges.
A periodic density isosurface crossing cell boundaries.
An ESP-colored electron-density surface using two cube files.
Positive and negative orbital lobes plus at least two additional cube layers.
An arbitrary 2D slice and an HKL slice.
Record screenshots, load time, interaction frame rate, memory use, implementation complexity, package size, license, and maintenance activity.
Acceptance criteria
A comparison document and runnable prototypes are committed.
Scientific correctness is checked against Multiwfn reference output, not only screenshots.
Missing capabilities are classified as small adapter work, upstream contribution, or fundamental limitation.
The selected engine and fallback plan are documented before replacing the current renderer.

MatterViz follow-up after upstream evaluation (2026-07-12)
The MatterViz assessment above is now outdated in an important way. I opened janosh/matterviz#375 to discuss multi-volume isosurfaces and cross-volume scalar coloring. The maintainer replied in under eight hours and implemented the proposal in janosh/matterviz#376, including several capabilities that I had originally listed as possible follow-up work. All CI checks on that PR currently pass.
I then reviewed the expansion, coordinate-sampling, and coloring paths in detail. This found an integer-supercell coordinate issue: a tiled periodic grid was passed to finite marching cubes with inconsistent endpoint semantics, so repeated surfaces could drift from the atomic supercell and from the Cartesian frame used for color sampling. I submitted janosh/matterviz#377, which was accepted into the feature branch. The maintainer independently reproduced deviations of up to 0.75 from the requested isovalue in the old path; the regression test after the fix recovers the isovalue to about 1e-5. This was a particularly positive upstream interaction: the report received a substantive implementation quickly, and a correctness-oriented follow-up contribution was verified and merged in roughly another day.
Current relevant functionality
With #376 and #377, MatterViz now covers most of the difficult requirements in this issue:
Multiple CUBE/CHGCAR-family files can coexist in one scene, with same-cell imports appended rather than replacing the previous volume.
Each isosurface layer independently selects its geometry volume, isovalue, positive/negative lobes, solid colors, opacity, visibility, and optional scalar-color source.
A surface extracted from volume A can be colored by trilinearly sampling volume B at every generated vertex. Sampling is performed in Cartesian coordinates and supports different origins, different grid densities, non-orthogonal lattices, and periodic wrapping.
Color-source volumes may remain loaded without rendering a surface of their own.
Continuous colormaps, explicit or automatically fitted color ranges, signed symmetric ranges, and fallback colors for finite out-of-bounds samples are supported.
Integer supercells and VESTA-style fractional ranges such as [-0.15, 2.15] now use consistent endpoint-aware extraction. Periodic surfaces repeat and are clipped at the requested bounds; finite volumes are cropped rather than repeated implicitly.
Existing volumetric support includes CUBE, CHGCAR/PARCHG/ELFCAR/LOCPOT-style data, multiple blocks such as charge plus magnetization, periodic halo handling, and HKL slice sampling.
The wider structure viewer already provides triclinic cells, periodic image atoms, bonds, coordination polyhedra, symmetry overlays, measurements, trajectories, editable display settings, multiple synchronized views, and PNG/GLB/OBJ plus CIF/XYZ-style export.
One remaining distinction is that the existing slice core is primarily HKL-oriented. A complete Multiwfn integration would still need a user-facing arbitrary Cartesian plane, contour/filled-map rendering, and parity with Multiwfn's plane-definition workflows.
Performance characteristics
The implementation contains several good performance decisions:
Isosurface geometry uses indexed Three.js buffer geometries instead of duplicating triangle vertices.
Marching-cubes geometry is cached per layer signature. Changing opacity, solid color, colormap, or color range does not regenerate the surface.
Per-vertex scalar samples are cached separately, so changing the colormap/range only remaps an existing float buffer.
Slider-driven geometry rebuilds are debounced and scheduled through requestAnimationFrame.
Large geometry grids are block-downsampled to a default budget of 500,000 points. The source color volume can remain at full resolution.
Atoms and several other repeated objects use instanced rendering. Recent upstream work also specifically addressed multi-second freezes for large structure supercells.
The new demo includes a pair of 80 x 80 x 96 grids, about 1.2 million source grid points in total, as a stress scenario.
These choices should make ordinary molecular and solid-state grids interactive, and recoloring should be much cheaper than changing the isovalue. However, the current marching-cubes and trilinear-sampling path is still CPU-side TypeScript operating on nested arrays. It is not yet a GPU 3D-texture or compute pipeline. Very large Multiwfn grids, many simultaneous surfaces, or frequent isovalue animation still require explicit benchmarking of load time, peak memory, rebuild latency, and frame rate. The 500k geometry budget is a pragmatic interactive limit, not evidence that full-resolution extraction is inexpensive.
Lighting and visual quality
MatterViz has a stronger default materials-oriented presentation than a minimal molecular viewer:
Atoms, bonds, cells, polyhedra, and isosurfaces use MeshStandardMaterial-style lighting rather than only flat or Lambert shading.
The scene combines configurable directional and ambient light.
Isosurfaces expose opacity and wireframe modes and use restrained metalness/roughness defaults.
Transparent surfaces are rendered in separate back-face/front-face passes with controlled render order, which is materially better than a single naive transparent pass for nested shells.
Atom colors, radii, backgrounds, labels, cell styling, projections, and themes are already integrated into a polished control UI.
The current code does not appear to provide a full high-end post-processing stack such as SSAO, contact shadows, depth peeling, or configurable tone mapping. Transparent surface intersections can therefore still show the usual WebGL sorting limitations, especially with many overlapping layers. For publication-quality rendering, shadows, edge enhancement, supersampled export, and transparency behavior should remain explicit prototype criteria rather than being inferred from the demo screenshots.
Extensibility and integration
MatterViz is MIT-licensed and implemented as a typed Svelte 5 component library on Three.js/Threlte. Its volume parsers, samplers, grid checks, coloring utilities, marching-cubes code, layer model, and structure components are separate modules with public TypeScript types. Important viewer state such as volumetric_data and isosurface_settings is bindable, which is useful for keeping a future GUI and CLI/state model synchronized. The repository also ships reusable file-viewer, VS Code, and anywidget integrations, demonstrating that the components can be embedded outside the documentation site.
The main integration cost is framework coupling. Multiwfn's Qt WebEngine frontend could load a prebuilt MatterViz application or custom bundle without difficulty, but using individual components directly is less framework-neutral than the imperative API of 3Dmol.js. If the final GUI is not otherwise Svelte-based, we would need a thin message/state bridge or a web-component-style wrapper. In exchange, MatterViz provides substantially more ready-made materials UI and typed application structure than a lower-level Three.js integration.
Upstream health
At the time of this update, MatterViz has about 346 stars and 40 forks under the MIT license. It is smaller than Mol* or 3Dmol.js, but very actively developed: the main branch received about 12 commits in the preceding month, recent releases have followed a frequent 0.4.x cadence, and recent work covers performance, accessibility, exports, embedding, coordination polyhedra, symmetry, and viewer infrastructure. The repository currently has very few open issues, though that also reflects its smaller user base.
The response to #375/#377 is stronger evidence for this project than star count alone. The maintainer understood a specialized scientific-volume request, implemented it with extensive unit and browser tests, empirically verified a numerical bug report, accepted an external fix, and simplified the resulting implementation afterward.

3Dmol.js remains the lowest-risk fallback because it is already integrated and its imperative API is convenient. Mol* remains the strongest candidate if the project prioritizes a mature representation/state framework and expects very large biological structures. MatterViz is now the closest semantic match for Multiwfn's materials and volumetric workflows, with the most promising combination of visual polish, hackability, and responsive upstream collaboration.
Updated recommendation
MatterViz should be promoted from "interesting candidate with a missing core feature" to a leading prototype candidate alongside the existing 3Dmol.js backend. It should not be selected solely because upstream responded quickly; the final decision should still use the common reference datasets and record cold-load time, isovalue rebuild latency, recolor latency, memory, interaction FPS, transparency artifacts, export quality, and implementation size.
A practical next step is to implement the same Multiwfn-generated density/ESP pair and fractional periodic scene in MatterViz and 3Dmol.js first. Mol* should remain in the comparison if its prototype can express cross-volume coloring without building a disproportionate amount of custom representation infrastructure.

Research update: source-level capability audit and platform direction
I completed a source-level audit of Multiwfn, CatGo, MatterViz, 3Dmol.js, Mol*, NGL, vtk.js, and JSmol against three separate axes: (1) periodic structure visualization, (2) structure editing/modeling, and (3) CUBE/volumetric visualization. This is a progress update, not a final engine-selection decision.
Key findings:
MatterViz is the leading frontend candidate to prototype: its materials-oriented periodic rendering, editor-oriented direction, and volume support make it the strongest match for the desired integrated workflow.
3Dmol.js remains the lowest-risk fallback because it is already integrated and has established volumetric rendering support.
CatGo is a useful architecture reference, not a code-reuse candidate by default: it refines MatterViz for an AI-assisted materials workflow, but its AGPL licensing requires a deliberate licensing decision before any reuse.
Mol, NGL, vtk.js, and JSmol each cover useful subsets*, but none is presently a better single foundation for the combined periodic-materials editor + structure viewer + CUBE viewer target.
A robust platform should keep the scientific model layer separate from the web renderer: use a domain backend/tool layer (e.g. pymatgen/ASE-compatible operations) for structure construction and validation, and expose typed operations to AI agents. Multiwfn should remain the trusted producer/reference for volumetric results.
The main unresolved items require executable prototypes and comparison against Multiwfn reference data, especially:
triclinic periodic cells and boundary behavior;
periodic CUBE isosurfaces;
cross-volume scalar coloring (surface from A, color from B);
arbitrary planes/contours; and
realistic performance and memory behavior.
I recommend first building a common benchmark around these cases for MatterViz and 3Dmol.js, then selecting the primary engine based on measured correctness and maintainability.
The full static-audit report and dashboard are ready locally. I recommend versioning them under the repository documentation tree and linking them here, rather than attaching a standalone HTML file, so that review history and future updates remain traceable.
