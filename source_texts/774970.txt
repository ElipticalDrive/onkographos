Proposed new feature or change:
np.interp takes a 1D list of scalars as an input y. When one wishes to interpolate multiple variables with the same basis/lookup points, np.interp() must be called repeatedly. The majority of the cost associated with this is the initial finding of what indexes should be looked at and the ratios of [n] and [n+1] required to get the interpolated value, so this is wasteful.
A toy example of the above:
```
In [1]: import numpy as np

In [2]: N = 10001
   ...: x = np.linspace(0, 1, N)
   ...: y1 = np.sort(np.random.normal(0, 1, N))
   ...: y2 = np.sort(np.random.uniform(0, 1, N))

In [3]: xr = np.random.random(1000000)

In [4]: %%timeit
   ...: y1i = np.interp(xr, x, y1)
   ...: y2i = np.interp(xr, x, y2)
   ...:
   ...:
131 ms ± 357 µs per loop (mean ± std. dev. of 7 runs, 10 loops each)

In [5]: %%timeit
   ...: ycomplex = y1 + (complex(imag=1) * y2)
   ...: ycomplexi = np.interp(xr, x, ycomplex)
   ...: y1ic = np.real(ycomplexi)
   ...: y2ic = np.imag(ycomplexi)
   ...:
   ...:
65.3 ms ± 190 µs per loop (mean ± std. dev. of 7 runs, 10 loops each)
```
By combining arrays y1 and y2 in to a complex number, interpolating that, then decomposing them, the same result is achieved in approximately half the time, indicating that the majority of the runtime arises from working out what indexes and ratios are required for each xp.
There are two issues with this:
It is limited to pairs of y vectors. In the event you have 1000 y vectors, there is still a ~500X speedup still on the table (assuming the limiting step as described above)
It is completely ridiculous, and anyone suggesting casting pairs of vectors to a complex number to speed up a production codebase will quite rightly be dismissed as having gone insane.
Both of these problems can be addressed by allowing the input for y to be an ndarray.

I experimented with a gufunc implementation called linear_interp1d(x, xp, fp) in ufunclab. The gufunc has signature (),(n),(n)->(). The implementation has a fast(er) code path when the strides of the x and xp arrays are 0, where it only searches for the x indices once.
This script shows how the gufunc broadcasting can be used to replace looping with numpy.interp. In this example, the fp array has shape (5, N).
```
import numpy as np
import ufunclab as ul


rng = np.random.default_rng()

N = 10001
xp = np.linspace(0, 1, N)

fp = rng.normal(0, 1, size=(5, N))

x = rng.random(1000000)

ynp = np.array([np.interp(x, xp, t) for t in fp])

yul1 = ul.linear_interp1d(x, xp, np.expand_dims(fp, 1))
yul2 = ul.linear_interp1d(x[:, None], xp, fp).T

assert np.allclose(ynp, yul1, rtol=1e-15, atol=1e-15)
assert np.allclose(ynp, yul2, rtol=1e-15, atol=1e-15)
```
To use the function with higher dimensional arrays requires some familiarity with gufunc broadcasting, and to take advantage of the fast path, you have to know even more about what goes on in a gufunc loop. The two ways that linear_interp1d is used to compute the result above illustrate this. Here's the timing for the three methods:
```
In [129]: %timeit ynp = np.array([np.interp(x, xp, t) for t in fp])
371 ms ± 454 µs per loop (mean ± std. dev. of 7 runs, 1 loop each)

In [130]: %timeit yul1 = ul.linear_interp1d(x, xp, np.expand_dims(fp, 1))
362 ms ± 836 µs per loop (mean ± std. dev. of 7 runs, 1 loop each)

In [131]: %timeit yul2 = ul.linear_interp1d(x[:, None], xp, fp).T
90.9 ms ± 67.4 µs per loop (mean ± std. dev. of 7 runs, 10 loops each)
```
The version that computes yul1 is barely faster than using a loop with numpy.interp. The version that computes yul2 shapes the input arrays so that the fast code path is activated, and we get a nice speedup.
