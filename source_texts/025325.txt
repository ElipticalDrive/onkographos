Summary
Adds the ability to export a textured 3D surface mesh directly from InVesalius's volume rendering view. Users can now export their CT/MRI surface as a production-quality textured OBJ or VRML file with a single click from the Export tab.
Implementation
InVesalius already provides beautiful volume rendering with full WW/WL, CLUT, and projection type controls. However, users could not export this as a textured 3D mesh for use in external tools like Blender, MeshLab, Unity, or for 3D printing with colors.
This feature bridges that gap by physically baking the volume rendering appearance onto the surface mesh and exporting it as a standardized textured 3D file format that natively retains these color maps.
How It Works
User loads a DICOM dataset and creates a 3D surface.
User enables Volume Rendering and adjusts settings (WW/WL, CLUT, projection type) as desired.
User navigates to the Export tab.
User clicks the new hyperlink: "Export 3D surface from volume rendering...".
User picks a save location and selects a format (Wavefront OBJ or VRML).
A responsive Progress Dialog appears while the high-resolution texture is generated asynchronously.
Output files are compiled and saved gracefully:
OBJ Format: mesh.obj + mesh.mtl + mesh_texture.png
VRML Format: mesh.vrml + mesh_texture.png
Technical Implementation
Algorithm
Based on the medical_triangle_texture algorithm by Thiago Franco de Moraes (2016):
For each triangle in the surface mesh, the algorithm natively shoots rays along the surface normals INTO the dense CT/MRI volume.
It dynamically samples HU values utilizing sub-voxel trilinear interpolation.
Applies the active WW/WL + CLUT scalar mapping to accumulate genuine RGB colors using Front-to-Back opacity accumulation.
Packs all distinct triangle mappings into a massive single 2D atlas image (5000x5000 default) and assigns sub-pixel UV coordinates sequentially to the matching mesh faces.
Reference:
Moraes et al. (2016). Isosurface rendering of medical images improved by automatic texture mapping. Computer Methods in Biomechanics and Biomedical Engineering: Imaging & Visualization. https://doi.org/10.1080/21681163.2016.1254069
Rust Engine Optimization
The core texture generation fully converted legacy Python/Cython wrappers and ports processing heavily into the native invesalius_rs Rust module suite via _native.generate_surface_texture().
Data Flow
Project().surface_dict → mesh (vertices, normals, faces)
Slice().matrix → CT/MRI volume (int16 Z,Y,X)
Slice().spacing → voxel spacing (mm)
project.raycasting_preset → dynamically grabs WW/WL + 16-bit preset CLUT dictionaries
↓
_native.generate_surface_texture()
↓
Generates RGB high-res texture atlas (.PNG) + Barycentric UV maps
↓
Strict syntax construction to portable OBJ / MTL or VRML standards

Key Design Decisions
Presets: Utilizes exact settings from the actively viewed volume plane (Volume()) and dynamically scrapes .plist definitions for embedded 16-bit CLUT tables rather than demanding separate user configuration. "What you see is exactly what exports."
Volumetric Spatial Alignment: Added absolute normalization vectors shifting mesh coordinates by mesh_min - [10, 10, 10]. This elegantly reverses the Y-axis flips inherent in VTK image data imports, ensuring volumetric arrays are never raycasted onto empty grid spaces.
Strict 3D Viewer Compliance:
OBJ: Sanitizes whitespace inside saved .png files replacing them with underscores to prevent parsing failures in legacy MTL managers like MeshLab.
VRML: Extensively formats V2.0 structural arrays ensuring commas are strictly internal and all MF-Values are perfectly enclosed inside [ ] brackets, bypassing primitive OutOfMemory crashes discovered in native 32-bit viewers like FreeWRL.
No Cython Dependencies: Pure Rust execution is robust.
Testing Guidelines
Build Instructions:
Since this feature relies on entirely new Rust backend routines for the rendering algorithms, you must first compile the native module before testing the workflow:
```
cd invesalius_rs
maturin develop --release
```
Manual Execution Steps or (see video for execution)
Launch application via python app.py.
Load standard DICOM
Create an explicit 3D surface from a mask.
Activate Volume Rendering and apply distinctive visual colorations (e.g. Bone + Skin preset).
Navigate directly to the active Export tab on the left-side workflow.
Click "Export 3D surface from volume rendering..." and assign a test save location favoring OBJ format.
Verify progress bar fills naturally without blocking the main GUI frame.
Observe output directory contains standard files (.obj, .mtl, .png atlas).
Open mesh.obj inside MeshLab / Blender verifying dynamic color patterns fully mapped uniformly across mesh triangles.
Repeat workflow but explicitly define VRML output format. Open rendered VRML inside strict clients like FreeWRL to ensure valid parsing structure parsing completion.

Additionally, I would like to mention that while VRML export is supported, it may not work reliably for very large meshes (e.g., millions of faces). This is due to limitations of the VRML format and some viewers when handling large array-based geometry.
In my testing, OBJ export works consistently for large datasets since it streams geometry more efficiently.
So currently:
OBJ is recommended for large medical volumes
VRML works better for smaller meshes
I will continue to explore possible improvements or safeguards ( warnings or decimation) for VRML export.

Hi @paulojamorim,
Thank you for this insight! I understand the idea:
Instead of using a pre-existing surface from a mask, we would:
Use the transfer function opacity threshold to automatically extract an isosurface from the volume (similar to marching cubes, but driven by the transfer function rather than a manual mask)
Generate texture on that auto-extracted surface
This would ensure strong alignment between the rendered volume and the exported textured surface.
While thinking about how this could be implemented, a couple of considerations came to mind:
Multiple opacity peaks
Volume rendering presets can contain multiple opacity peaks (example: highlighting both skin and bone). Since standard isosurface extraction methods typically rely on a single threshold, handling multiple density ranges consistently may require additional logic.
Performance considerations
Extracting a high-resolution surface at export time could introduce additional processing overhead, especially for large datasets.
I think this is a strong approach, and I would like to explore it further to understand how best to implement it.
It would also be great to hear @tfmoraes thoughts on this approach.
Thank you!
