Idea
Occlusion culling: skip drawing (or even considering for depth-sort) primitives that are fully hidden behind other geometry from the camera's point of view. Doesn't fix draw order the way #59's clustering approach does - it's orthogonal, cutting the number of primitives that reach the sort/draw pass at all rather than resolving ambiguous ordering between them. Most valuable in scenes with a lot of geometry the camera can't actually see all of at once - examples/3d/examples/terrain-style scenes, and especially whatever static level geometry #107 ends up supporting (a wall fully hides everything behind it from a given viewpoint).
This was candidate #5 in #59's original list, explicitly deferred there since #59 scoped down to depth-sort correctness (clustering) rather than primitive-count reduction. Filing separately so it isn't lost, per the project owner's request to investigate it in the future.
Scope questions for whoever picks this up
What's cheap enough to check on Roku's CPU budget - simple heuristics (e.g. "behind a large static wall/floor" bounding-volume tests) vs. anything more precise?
Whether this composes with Renderer needs a smarter depth/visibility algorithm than a per-object painter's sort #59's clustering (an occluded object presumably never needs to enter a cluster at all) and/or Static entity/geometry support with BSP-based rendering for level design #107's static-geometry BSP (a BSP traversal order can double as a form of occlusion-aware culling for free in some classic implementations).
Needs the same "measure, don't guess" treatment every rendering change in this repo gets - a rendererTest or examples/depthsort-style before/after comparison, not just theoretical reasoning about cost.
No implementation direction decided yet - this issue exists to track the idea, not to commit to an approach.
