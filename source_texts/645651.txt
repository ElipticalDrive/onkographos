Problem / motivation
The renderer uses a fixed tile size across all zoom levels and data densities. That single size is a compromise: small tiles keep individual jobs cheap and center-first latency low but multiply per-tile fixed overhead and cache-key churn, while large tiles amortize overhead but coarsen caching/eviction and raise worst-case per-tile rasterize cost on dense cells. Neither extreme is optimal across the range of zoom levels and dataset densities the viewer handles.
This is a follow-up to #422, which landed center-priority scheduling and listed adaptive tile size as a "if beneficial" candidate to investigate.
Proposed solution
Investigate (and only adopt if it demonstrably wins) an adaptive tile-size policy that selects a tile size per band / load condition:
Choose size from signals like zoom band and observed per-tile geometry/rasterize cost, so dense low-zoom cells and sparse high-zoom areas can differ.
Treat this as an investigation first: prototype behind a policy seam and measure before committing, since it interacts with cache-key layout, GPU residency, and the scheduling/cancellation model.
If adopted, ensure the disk/hot cache key includes the effective tile size so entries from different policies never collide, and that changing the policy invalidates cleanly rather than serving mismatched tiles.
Preserve center-first scheduling and visible-before-predicted tiering regardless of the chosen size.
Affected area
Renderers (Skia / Mapsui)
Alternatives considered
Keep a single tuned fixed size: simplest and avoids cache-key/eviction complexity; may be the right answer if the adaptive gains do not justify the added surface area. This issue explicitly allows "measured no benefit -> close" as an outcome.
Metatile raster jobs (tracked separately): amortizes overhead without changing the cache granularity, and may capture most of the large-tile benefit at lower risk; worth comparing head-to-head before adopting adaptive sizing.
Spec references (optional)
N/A (rendering performance architecture; not a product-spec semantic change).
Additional context
Split out from #422 (center-priority tile scheduling and related pyramid-tiling optimizations). This is the lowest-confidence item of the set and is gated on evidence: use the viewer-evaluation loop across a range of zoom levels and dataset densities (e.g. dense UKHO S-101 cells vs. sparse areas) and the rasterize-duration / cold-latency / cache-hit telemetry to decide whether it beats a well-tuned fixed size and/or metatile batching. Acceptance: either a measured net improvement with no correctness regression, or a documented decision not to pursue.

Relationship to #529: the completed metatile implementation is the lower-risk alternative this issue explicitly anticipated. It targets the same fixed per-tile raster overhead by batching adjacent 2x2 misses while preserving ordinary tile-granular cache keys, eviction, prediction, and GPU residency; adaptive sizing would instead change the logical grid and therefore has a much larger cache/scheduling/invalidation surface.\n\n#529's preliminary A/B showed promising logical-tile raster reductions, but regressions in time-to-idle, paint p95, and peak working set, so metatiling remains default-off pending the planned alternating multi-run gate. Treat this issue as lower priority until that evaluation is complete. If metatiling clears its gate, it likely captures most of the available benefit and this issue may be unnecessary. If it does not, adaptive sizing should only proceed if measurements specifically identify logical tile granularity—not batching—as the remaining bottleneck.
