GPU-003 (refs #922): the GPU-sorter init path tripped a one-way latch — after kSorterInitMaxFailures (5) failed creation attempts, RenderSortingOrchestrator::refresh_gpu_sorter() early-returned forever ("GPU sorting permanently disabled for this session"), the success-path counter reset was unreachable once latched, and initialize_sorting() never cleared the latch either. With the instance route's fallback policy being REUSE_PREVIOUS_SORT → FAIL (no CPU sort), ~5 seconds of transient VRAM pressure at startup left splats frozen at the last sorted order or not rendering for the rest of the session, with only log lines as signal.
Base: 1abc46684cb (branch contains exactly 2 commits on top of it; review against the immutable 1abc46684cb..head diff).
Finding verified at head (not just at the audit snapshot)
Audit finding GS-AUDIT-GPU-003 was taken at 55bd3953475; every cited line re-verified at 1abc46684cb before work started:
renderer/render_sorting_orchestrator.cpp:276-289 — permanent early-return once sorter_init_failure_count >= kSorterInitMaxFailures; :318 increment; :333-336 reset unreachable after the latch.
renderer/render_types/render_state_types.h:140-143 — counter + kSorterInitBackoffFrames=60, kSorterInitMaxFailures=5; repo grep confirms no other reset site.
renderer/sort_fallback_policy.h:178-185 — instance pipeline: REUSE_PREVIOUS_SORT then FAIL, no CPU sort.
initialize_sorting() (render_sorting_orchestrator.cpp:350-397) sets sorter_needs_rebuild but routes back into the latched refresh_gpu_sorter, so explicit re-init could not recover either.
Fix (commit 2)
The retry decision is extracted into pure helpers in sort_fallback_policy.h (the file that already owns sort-lifecycle policy, with existing unit-test coverage conventions):
sorter_init_backoff_frames(n) — doubles per consecutive failure (60, 120, 240, 480, 960 frames), capped at 1800 frames (~30 s @ 60 fps).
should_attempt_sorter_init(n, frames_since_failure) — invariant: for every failure count, returns true once the capped interval has elapsed. The cap bounds the retry rate (the old latch's OOM-thrash concern); nothing bounds the retry count.
sorter_init_degraded(n) — the old "permanently disabled" threshold, now an observability threshold only.
refresh_gpu_sorter() consumes the policy. Two repairs from Codex review round 1 are part of the fix: a failed build now leaves sorter_needs_rebuild armed (the per-frame path sort_gaussians_for_view only calls refresh_gpu_sorter while that flag is true, so clearing it on failure - as both the base code and the first draft did - would strand the probes after the first failure; the backoff gate, not the flag, rate-limits attempts), and the backoff delta is computed in uint32 modular arithmetic so a frame_counter wrap cannot bypass the window. Entering the degraded state is surfaced once per episode as a RECOVERABLE RenderingError through record_rendering_error (→ diagnostics orchestrator), with failure count / retry interval / frame context and recovery steps — not only a log line. The degraded ERROR log re-fires once per probe interval (mirroring should_warn_unsorted_composite's not-one-shot contract). A successful rebuild resets the counter and the reported flag, so a later episode reports again.
No change to sort math, sort keys, culling, or any healthy-session path: with sorter_init_failure_count == 0 the flow is byte-identical to before. Visual output on real-scan content is therefore expected unchanged on any session whose sorter initializes; no screenshots were produced for this PR — if the maintainer wants eyes on a degraded-VRAM session, that needs a controlled OOM rig this PR does not build.
