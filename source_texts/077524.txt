Problem
Non-traditional data types (e.g., Gaussian splats and voxels) require rendering techniques that aggregate data into one place on the GPU. However, these systems are at odds with cesium-native's own systems for tile selection and resource preparation.
The assumption is that after prepareInMainThread, a model will have fully initialized on the runtime side and the tile will be ready to render. This is not true for splats or voxels, because there is an extra latency between when the game components/objects are created vs. when their data actually makes it into their respective rendering systems.
For voxels in Unreal (CesiumGS/cesium-unreal#1685), this is mitigated because of the custom VoxelOctree class which maintains its own traversal history. For splats, many tiles are hidden too early before the intended level of detail appears, leading to large incorrect gaps.
Possible Solutions
One idea is to have some overridable isReady function on the render resources. This way, native won't choose to hide a tile if the contents of its children aren't actually "ready" according to some runtime metric. I'm not sure how this would work API wise, though I think it's possible and perhaps the easiest solution.
There is also the possibility to bring parts of the splat/voxel systems in Unreal into cesium-native; they both use a "registering"/"unregistering" system for their respective rendering techniques. But maybe that would be too heavy handed?

bool Tile::isRenderable() const noexcept {
if (getState() == TileLoadState::Failed) {
// Explicitly treat failed tiles as "renderable" - we just treat them like
// empty tiles.
return true;
}
if (getState() == TileLoadState::Done) {
// An unconditionally-refined tile is never renderable... UNLESS it has no
// children, in which case waiting longer will be futile.
if (!getUnconditionallyRefine() || this->_children.empty()) {
return std::all_of(
this->_rasterTiles.begin(),
this->_rasterTiles.end(),
[](const RasterMappedTo3DTile& rasterTile) noexcept {

});
}
}
return false;
}

One possible way to handle this without any architectural changes is to hook into the prepareInLoadThread portion of the load (which is asynchronous) instead of the prepareInMainThread portion (which is synchronous). prepareInLoadThread can do main thread work if it needs to. There's an example of this in cesium-unity.
Making prepareInMainThread asynchronous (e.g., via polling as you've proposed above) is possible, too. At one point that would have been a scary change, but today I think it already ends up being asynchronous in some cases anyway, such as:
When there's a TilesetOptions::mainThreadLoadingTimeLimit.
When the GltfModifier needs to run.

Rather than a polling-based system (canRender), you could also consider making prepareInMainThread return a Future. In most cases it will return a Future that is already resolved, so the overhead should be minimal. When calling that method starts up async work, though, you may need some way to throttle it so that you don't end up with too many jobs in flight at the same time. Even if those jobs are queued on the Unreal side, throttling is still important, because otherwise we could easily end up filling Unreal's queue with a bunch of jobs that are now irrelevant because the camera moved elsewhere.

Register component with a greater system in Unreal
Deploy a render-thread command on the Unreal side to copy data to the GPU

I took a quick look at that branch. Some things I noticed:
In CesiumGltfComponent.cpp:
There's a comment that says "Not safe to capture asyncSystem here." Why? I can't think of any reason it would be unsafe.
bool requiresMainThreadContinuation = false; looks unused?
loadModelAnyThreadPart has a structure like return CesiumGltfTextures::createInWorkerThread(...).thenInWorkerThread(...).thenInMainThread(...). But in most cases there's no need to do any main thread work, yet it will still wait to dispatch a task to the main thread, wasting time. A better pattern is: return CesiumGltfTextures::createInWorkerThread(...).thenInWorkerThread((...) => { ...; if (necessary) return runInMainThread(...) else return createResolvedFuture(...); }) Hope my sketchy pseudocode makes sense.
The thenInWorkerThread at the end of loadModelAnyThreadPart doesn't look like it does anything useful.
Just above that, there's a .all(...).thenInWorkerThread(...) that is a little inefficient. I think that loop should be very low cost, so a thenImmediately would probably be more appropriate.
Also, if a tile is unloaded before its UnrealPrepareRendererResources::prepareInMainThread is called, I don't think the UCesiumGltfComponent created in the prepareInLoadThread portion will be destroyed. There's a small chance this could be the cause of the "lingering" you see, but I'm not entirely sure why it would happen, considering that the UCesiumGltfComponent is initially hidden.
So maybe a few things to try cleaning up, but I'm not sure if it will help.
