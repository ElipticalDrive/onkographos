Summary
Make the AHRS backends publish their attitude as a single quaternion and derive
the euler angles and rotation matrix from it, instead of each backend supplying
all three representations independently and applying the board-mounting trim in
its own way.

Description
Each AHRS backend used to fill in the roll/pitch/yaw eulers, the rotation matrix
and the quaternion separately, and applied AHRS_TRIM differently in each
(quaternion.rotate(-get_trim()) in some paths, a trimmed matrix in others,
euler subtraction elsewhere). Those forms could disagree. The trimmed rotation
matrix was exact, but the quaternion's rotate(-trim) treated the trim as an
axis-angle rotation vector, so with a trim that is non-zero on more than one axis
the quaternion disagreed with the matrix. The EKF euler angles disagreed with both
for any non-zero trim, by up to 3.8 deg with a (3,-2,0) deg trim at large
attitudes.
This change makes the quaternion the single source of truth:
A backend fills in Estimates::quaternion and calls
derive_attitude_from_quaternion(), which fills the euler angles and the
rotation matrix from that quaternion, so the three representations can never
disagree.
AHRS_TRIM (the autopilot-body to vehicle-body mounting offset) is applied by
composing the backend quaternion with a trim quaternion,
get_quat_vehicle_body_to_autopilot_body() (= from_euler(trim).inverse()),
which is exact for simultaneous trim on all three axes. This reproduces the
historical trimmed rotation matrix
(R_backend * rotation_vehicle_body_to_autopilot_body) rather than the old
component-wise euler subtraction.
EKF2/EKF3 no longer expose getEulerAngles()/getRotationBodyToNED() to
the AHRS layer; getQuaternionBodyToNED() composes the EKF quaternion with the
DAL trim quaternion, and the logged NKF1/XKF1 eulers are derived from it.
AP_DAL carries the trim as a quaternion and rebuilds it from the logged trim
on replay, so replayed estimators see the same trim as the original flight.
get_quat_body_to_ned() returns the stored quaternion directly instead of
reconstructing it from the rotation matrix.
ExternalAHRS is unchanged in behaviour: it already supplies a vehicle-body
attitude, so it does not apply the trim composition.
What changes numerically
The new values are always the correct ones — they make the published eulers,
rotation matrix and quaternion mutually consistent, and consistent with DCM.
Rotation matrix: unchanged for DCM, EKF2 and EKF3 with any trim, and so
are DCM's euler angles.
Published quaternion (AP_AHRS::get_quaternion(), ATTITUDE_QUATERNION):
unchanged for a single-axis trim. With a trim that is non-zero on more than one
axis it changes for DCM, EKF2, EKF3 and SIM, because the old
quaternion.rotate(-trim) treated the trim as an axis-angle rotation vector
rather than as the euler rotation used for the matrices: 0.05 deg for a trim of
(3,-2,0) deg, 0.38 deg for (5,4,6), 0.87 deg for (10,10,0). SIM's matrix and
eulers move with it. get_quat_body_to_ned() and the EKF
getQuaternionBodyToNED() were already derived from the exact matrix, so they
are unchanged for DCM and the EKFs.
EKF2/EKF3 logged and returned euler angles: change for any non-zero
AHRS_TRIM, including a single axis — not only multi-axis trim. For example
with AHRS_TRIM_Y=5° at 30° bank and level pitch the old EKF output was
roll 30.09 / pitch -0.67 / yaw +2.5; it is now 30 / 0 / 0. These eulers feed
the Plane attitude and navigation controllers, and a single-axis AHRS_TRIM_Y
is common on Plane, so this is behaviour worth noting even though the new
values are the correct ones.
Testing
SITL, all pass on this branch:
AP_Math unit test QuaternionTest.TrimCompositionMatchesRotationMatrix:
asserts the quaternion-composition trim gives the same rotation matrix as the
historical matrix form across a range of attitudes and a trim that is non-zero
on all three axes.
test.Plane.AHRSTrimMission: flies a Plane AUTO square circuit (four turns)
and then the flaps.txt landing, with a 5 deg board pitch mounting offset
(SIM_BRD_TRIM_Y) corrected by AHRS_TRIM_Y. It then compares the logged ATT
attitude with SIM truth wherever the bank is 20 deg or more. Mean pitch/yaw
error over about 385 banked samples is 0.20/0.30 deg on this branch, and
1.34/3.24 deg with the same test against master's code. The test fails above
0.75/1.5 deg, so it fails without this PR.
test.Copter.Replay including its Trim subtest (significant AHRS_TRIM):
replayed estimators reproduce the trim-dependent outputs of the original
flight, exercising the AP_DAL trim-quaternion-on-replay path.
Copter and Plane build cleanly.
test.QuadPlane.QAUTOTUNE fails in CI on this PR. It is a marginal test rather
than a behaviour change here. Autotune's position hold yaws the vehicle towards
its start point once it has drifted more than 5 m
(AC_AutoTune::get_poshold_attitude_rad), and the level timeout can expire
during that turn, ending the tune with "AutoTune: Failed to level". In the pair of
logs examined, the attitude matched SIM truth throughout on both; this branch's
flight drifted to 5.4 m, where master's peaked at 5.0 m.
Whether a run crosses that threshold depends on the exact trajectory, which
