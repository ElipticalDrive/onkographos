Area: GPU memory adaptation, gl_input_front in gst::video_adapt (CUDA memory into a GL consumer)
About: #1142 removed the global VideoConvertMode and its CUDA-GL interop probe. Strom no longer falls back to system memory on its own when interop cannot work. A GL consumer's input front puts cudadownload straight before glupload with no system-memory pin (on purpose: CUDA to GL is the zero-copy path), so the interop copy happens inside cudadownload.
Where interop is not available, what happens is up to nvcodec. That is the case on WSL2, and when GL runs on a non-NVIDIA GPU (a laptop with an integrated GPU). nvcodec either falls back to a copy through system memory, which is fine, or posts its own error from <input>_cudadownload (for example CUDA_ERROR_OPERATING_SYSTEM). Such an error names neither the block nor the remedy. Neither outcome has been seen on a real host. This is a judgment from the code only.
Example: nvh264dec → GPU Vision Mixer on WSL2.
Direction:
Check on a real host what cudadownload does: a WSL2 box, or an NVIDIA host with GL forced to another EGL device.
If it errors, pin to system memory up front when a cheap check says interop cannot work. That means WSL, or a GL vendor that is not NVIDIA from gpu::gl_renderer_info(), which is still probed. The front then becomes cudadownload → system memory → glupload, with one WARN naming the input. This is simpler than catching the error at runtime and re-splicing.
If it falls back silently, at most a log line is needed.
A guard test needs a host without interop, so it can't run in CI. A unit test on the decision (interop unavailable → pinned front) is feasible.
Relates to: #969, #1142, docs/DOCKER_GPU_SETUP.md (WSL2 cause).
