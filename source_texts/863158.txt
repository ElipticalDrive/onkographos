Closes #1493.
What was actually wrong
Nothing in the renderer. The gate blending-modes.spec.ts › GSplat normal mode › background splat shows through the overlap (real alpha-over) sampled a sparse lattice of canvas fractions (gx/gy += 0.05) and asserted each colour class had at least one hit. The red-dominant region in that scene is a genuinely thin rim — the two big splats project nearly concentric (centres ~44 px apart against ~46/54 px screen sigmas, and the nearer green splat is the larger on screen), so the background survives only in a crescent covering ~0.35% of the frame.
Against that, a 140-point lattice (float accumulation cut it to 14 x 10 over x ∈ [0.15, 0.80], y ∈ [0.25, 0.70]) expects about one hit: a coin-flip oracle. It finally came up tails when the canonical gsplat truncation radius moved 3.0 → 2.75 (#1179/#1181/#1182 — deliberate and documented): the tighter kernel shrinks the support ~9% and doubles the subtracted shift C = exp(-T²/2), which dimmed the single marginal sample from rgb ≈ (51, 21, 3) to ≈ (39, 5, 2) against an r > 40 threshold.
Measured on the real frame (headless Chromium, 1280x720, ?dpr=1, whole frame = 921,600 px):

So the background splat is clearly visible and alpha-over is compositing. The spec sanctions the rest of what makes the rim thin — GSPLAT_DEPTH_SORTING_SPEC.md §10 is explicit that coverage is clamp(intensity·opacity) so "dim splats occlude almost nothing … while saturated ones occlude hard", and this fixture is deliberately the saturated case (amplitude 2.0 x opacity 0.5, peak projection ⇒ coverage 1.0 at the core).
What changed
Test-side only — one test body in blending-modes.spec.ts. No shader, material, constant, fixture or Python change.
One captureCanvasRGBA capture, then every pixel of the whole frame classified, instead of 140 lattice probes. No sub-box: the old rectangle was not even centred on the content (y ≤ 0.70 effectively cut nearer the bottom half of both discs) and re-introduced the framing sensitivity that caused this issue.
Per-class floors as fractions of the frame (so the gate is invariant to canvas scale and dpr): 0.08% for the thin red rim (4.4x under healthy, 4.7x over the defect's residual), 0.5% for green and mixed (4.0x / 3.1x under healthy, against a defect value of 0.000% for mixed). Both measurement sets and the margin arithmetic are recorded next to the constants, with an instruction to retune by re-measuring rather than nudging.
Dominance predicates are now three-way (r > 2g && r > 2b), matching the sibling additive test's form, so magenta/cyan can no longer count as red/green. The brightness floors stay at 40/30 (not the sibling's 100/80) because the crescent's pixels bottom out near r ≈ 63.
The scene-identity banner is asserted absent before the capture: it is the one non-neutral overlay whose fill (rgba(160,44,44) / rgba(150,110,20)) would satisfy the red and mixed predicates, and at ~1.9% of the frame it is larger than any healthy class — a whole-frame scan would otherwise be vacuously passable if the watchdog ever raised it.
The counts are logged on success too, so margin erosion shows up in a passing run instead of surfacing as a red gate later.
Test evidence
All runs in a real headless-Chromium Playwright run of this fixture:
Fixed gate, current renderer: passes — red=3215 (0.349% vs floor 0.080%) green=18429 (2.000% vs floor 0.500%) mixed=14173 (1.538% vs floor 0.500%).
Negative control — coverage = 1.0 forced in the LUXAR_NORMAL_PREMULT branch (bit-identical to the pre-fix alpha=1.0 contract under One/OneMinusSrcAlpha): fails, red=156 (0.017%) … mixed=0 (0.000%). Shader restored; the diff is the spec file alone.
Whole GSplat normal mode (premultiplied coverage alpha) describe block: 6/6 pass.
pnpm typecheck, pnpm lint, prettier clean.
Honest notes:
Running the full blending-modes.spec.ts in my checkout gives 18 pass / 4 fail; all four failures are the Blending Modes point-cloud tests that read datasets/examples/ (not generated in that checkout) and they fail identically on stock main there. Untouched by this change.
The WASM module was not built in that checkout, so these runs used the TypeScript backend. Pixel output is the same path either way, but the absolute counts were measured on the TS backend.
The gate keeps a 4.4x margin on the red class, which is a property of the auto-framing. A fatter separation between the two big splats would make that margin comfortable, but it means changing a fixture six tests share (and preserving the reversed twin's depth-sort invariant), so it is not folded in here.
One measurement worth recording: a 3x over-occlusion control (coverage = clamp(3·intensity·opacity)) still reads mixed 1.386% / red 0.326% and passes. These are hue-dominance classes, so this gate bounds the total-replacement defect, not graded over-occlusion; that is stated in the comment rather than implied.

What I checked and found clean:
Chrome can't satisfy the predicates. This is the real hazard of scanning the whole frame instead of a crop, and the negative-control run bounds it empirically: with the splat overlap destroyed, the whole frame yields 156 red-dominant pixels (a fifth of the 737-pixel floor) and zero mixed. Nothing in the rail, the panels, or the debug overlay reaches these classes.
No single splat can produce a mixed pixel. Worked the ACES matrices by hand for the red fixture colour (1, 0.1, 0.1): green and blue enter the input matrix equal but come out of the output matrix with b ≈ 0.9·g, nowhere near the b < min(r,g)/2 cut. Green-only clamps r to the floor. The discriminator really does require both splats.
The banner guard is wired to the right thing. #luxar-scene-identity-banner is the id ui/scene-identity-banner.ts actually assigns, the element is position: fixed over the canvas, and captureCanvasRGBA takes an element screenshot, so it would indeed composite into the frame. Worth having.
The lattice arithmetic quoted in the comment is right (14x10 = 140 points over x ≤ 0.80 / y ≤ 0.70 at 64x36 px spacing), the Desktop Chrome project is 1280x720 so the recorded fractions are the ones CI will measure, samplePixelsAt is still used by seven other tests in the file, and typecheck / eslint / prettier are clean. No spec or guide documents the old sampling method, so nothing to sync.
Dropped as not worth changing:
The banner absence is asserted just before the capture rather than after it, so there is a nominal window. The watchdog only raises against a scene swap or a dead data server, neither of which happens against a static fixture server inside a 20 s test — not worth the churn.
The red class keeps only a 4.4x margin because the two big splats project nearly concentric. Widening the separation means editing a fixture six tests share (and preserving the reversed twin's sort invariant); the comment records both measurement sets and says to retune by re-measuring, which is the right call here.
The sibling additive points test above still uses a lattice, but it was already densified to ~5.5k probes for ~8 expected hits, so it is not in the same coin-flip regime. Leaving it alone.
