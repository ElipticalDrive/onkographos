🤖 Written by Claude (AI), checked by @BimingtonBill.
I propose a measured experiment: draw each cell's static objects from persistent GPU buffers built from #185's data, and compare it with stock Bevy on #184's scenes, to decide whether Mudcrab needs its own static-world render path, or a contribution to Bevy. Part of #183.
Describe the problem
Bevy 0.19 already renders on the GPU efficiently: GPU preprocessing and multi-draw indirect (one GPU call drawing many objects, with the object list in a GPU buffer) are on by default, main enables two-phase occlusion culling (skipping objects hidden behind others) on its cameras (crates/engine/src/render.rs:192-251), and Bevy only re-processes meshes that changed. So the open question is narrow: for a world that is almost entirely static, does skipping per-object render entities save enough CPU time and memory to justify a dedicated path? It may not; that's why it's an experiment.
Describe the proposed solution
Prototype: per-cell instance buffers uploaded when a cell loads and freed when it unloads; GPU culling and indirect draws over them; per-instance flags (enabled, hidden), so enabling an object flips a bit instead of spawning entities.
Parity checklist before any adoption: alpha-masked and blended materials, shadows, picking and selection, origin rebasing (keeping coordinates small far from the world origin), runtime changes, Vulkan and DX12 (including fix(engine): prevent stale indirect draws on DX12 #166's DX12 workaround), grass.
Compare CPU frame time, GPU time, memory and load time against stock Bevy on the same scenes.
Where it lives: if it helps, the general part (a persistent instance-buffer path for static scenes) could go into Bevy itself rather than stay Mudcrab-only.
Path-tracing fit: the instance list maps directly onto a ray-tracing scene: one acceleration structure per unique mesh (a BLAS, the search tree rays test against), one entry per placement in the top-level structure (the TLAS), per-instance flags as ray masks. Today wgpu's ray tracing is experimental and documented for Vulkan only, and Solari is effectively NVIDIA-only, so this is a design constraint, not a near-term target.
Deliverable: numbers and a recommendation: adopt in Mudcrab, contribute to Bevy, or drop.
Importance
nice to have, until #184 shows how much per-object work costs.
Questions: Would the team rather explore this directly as a Bevy contribution?

🤖 Written by Claude (AI), checked by @BimingtonBill.
A first concrete piece for this experiment, which I'm starting now: near terrain drawn as fewer, larger meshes with one shared material.
The problem. Each terrain cell is drawn as four separate quadrant meshes, each with its own material, so a typical outdoor view submits over a thousand terrain draws. The cost lands on the render thread's CPU (extracting, preparing and queuing each entity), not on the GPU. On my local branch, one distant view measured 14.2 ms of render-thread time per frame with 1,156 terrain patches in view, against 7.2 ms for the same view with only 100. The GPU stayed under 1.5 ms in both. In Bevy 0.19 the draw cost is per entity, and batches split by material bind group: the terrain material is not bindless, so every quadrant material starts a new batch.
The plan (two halves, same look):
Converter: one merged terrain mesh per cell (quadrants joined; same vertices, normals and colours), plus a per-worldspace texture array holding the landscape textures, with per-vertex layer indices and weights. This is per-cell derived data in the sense of Proposal: derived render data and mutation contract (per-cell instances that stay moddable) #185, keyed the same way.
Engine: one shared terrain material that reads those indices and weights from the array, so every cell lands in the same batch set.
Not in scope: distant terrain (Feature request: native LOD for terrain, static objects, and trees #103/feat(lod): initial native terrain LOD and verified asset reuse #105, which keep their own chunks) and grass. PR fix(engine): prevent stale indirect draws on DX12 #166 (the DX12 indirect-draw fix) touches the same draw path; I'll rebase onto it once it merges and test DX12 as well as Vulkan.
How I'll check it: image comparisons against the current terrain at fixed views, plus the #184 baseline (the travel route) before and after. First step: a cheap data measurement, the maximum number of texture layers that actually overlap at one vertex across Skyrim's terrain, which sets the material's layer budget.
