I looked into both errors (gsplat main 28e794c, torchpq 0.3.0.6, the latest release on PyPI, whose clustering/KMeans.py line numbers match your traceback).
1. ValueError: Cannot take a larger sample than population
_compress_kmeans hard-codes n_clusters=65536, and PngCompression has no way to change it. torchpq picks the initial centroids with np.random.choice(n_data, size=[self.n_clusters], replace=False) (KMeans.py:272), so any scene with fewer than 65,536 Gaussians fails. Here there are 50,000.
2. UnboundLocalError: ... 'required' (after lowering n_clusters)
This one is in torchpq. gsplat creates KMeans(..., distance="manhattan"). On CPU tensors, KMeans.get_labels takes the data.device.type == "cpu" branch (KMeans.py:323), which only assigns required for "euclidean" and "cosine"/"inner" (KMeans.py:328-331). With "manhattan", if required < remaining: (KMeans.py:332) raises. torchpq documents manhattan as GPU-only (KMeans.py:40), and CUDA tensors take the max_sim_cuda path instead (KMeans.py:307). So this happens whenever the splats passed to compress are on the CPU, whatever the number of Gaussians.
Both reproduce with torchpq 0.3.0.6's KMeans.py on CPU input of shape [45, N], as _compress_kmeans builds it (only the cupy kernel imports stubbed, no CUDA):
```
n_clusters=65536, N=50000 -> ValueError: Cannot take a larger sample than population when 'replace=False'
    at KMeans.py:415 fit, KMeans.py:272 initialize_centroids
n_clusters=100, N=5000    -> UnboundLocalError: cannot access local variable 'required' where it is not associated with a value
    at KMeans.py:418 fit, KMeans.py:332 get_labels
```
Possible fixes in gsplat:
Clamp n_clusters to the number of Gaussians in _compress_kmeans.
If the number of Gaussians is <= n_clusters, skip k-means and store each Gaussian's quantized shN as its own centroid (labels = arange(N)). The .npz layout and _decompress_kmeans stay the same.
Expose n_clusters as a PngCompression argument, checked against the number of Gaussians.
For the CPU case, _compress_kmeans could move shN to CUDA for clustering when available, or raise a clear error that torchpq's manhattan k-means needs CUDA.
Which direction would you prefer? I'm happy to open a PR.
