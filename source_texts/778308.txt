FORM LAB's material data stores metallic and roughness images separately, and the Joy Engine preview samples the red channel of each independently. projects/form-lab/src/export-glb.js currently embeds both images but assigns metallic ?? roughness directly to glTF's metallicRoughnessTexture. With two maps, the roughness map is unreferenced. With one map, both properties are unintentionally sampled from that image, and its green/blue channels need not match the authored red-channel data.
The glTF format requires roughness in G and metallic in B, with missing maps contributing 1 before multiplying the authored factors: https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#material-pbrmetallicroughness-metallicroughnesstexture
A bounded fix should add asynchronous image preprocessing before the synchronous GLB serializer: decode the two images, resample to a documented shared resolution, pack source roughness R into G and metallic R into B, fill absent inputs with 255, encode PNG, and pass the prepared packed map into serialization. Keep source document maps unchanged and export from the last successful geometry/material snapshot. Close decoded images and bound temporary image allocations. Until that preprocessing exists, reject separate metallic/roughness texture export explicitly rather than silently writing an incorrect material.
Validation should use distinct non-grayscale pixel values to verify source-channel selection, two-map packing, each one-map case, preserved factors, and no data loss. No packing implementation was attempted during the normals/PBR preview change because native browser image decoding is asynchronous and exportGlb currently has a synchronous public API.
