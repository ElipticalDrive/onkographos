Tiles give @kernel a grouping below the workgroup: a kernel constructed with a tile width
divides each workgroup into tiles of N consecutive work-items (by @index(Local, Linear)), like CUDA's
tiled_partition<N>, whose work-items exchange values without going through local memory.
```
@kernel function f(out, x)
    t = @tile()               # Tile{N}: t.index (tile within the workgroup), t.lane
    v = tile_reduce(t, +, x[@index(Global, Linear)])
    t.lane == 1 && (out[@index(Tile)] = v)
end
k = f(backend; tile = 16)
k(out, x; ndrange = 16 * ntiles)
```
No declaration, a width at construction: f(backend; tile = N), also with a static
workgroup size and ndrange. What sets a kernel with tiles apart is the width, which the host
needs for the launch geometry, so that's the only switch. A kernel that uses @tile() or
@index(Tile) has to get one: @kernel notes the use, and construction rejects a missing
width. There is no default, since the sub-group width W differs between back ends (32 or
64 on AMD); width-agnostic kernels pass tile = KernelInterface.sub_group_size(backend).
A width that follows a run-time parameter (DGSEM's polynomial degree) works the same way.
tile_width(kernel) returns the width on the host, tile_width(t) in the kernel, where it
is a constant; it is a type parameter of Kernel and reaches the device through
CompilerMetadata.
Tiles are a capability. Tiles of N work-items need a power-of-two N ≤ W; a
workgroup can hold any number of them, and they diverge independently, also where several
share a sub-group (KernelInterface.supports_partitionable_subgroups, KernelInterface: sub-group shuffles, votes, reductions and scans #831).
supports_tiles(backend, N) reports whether a backend provides that, and constructing a
kernel it doesn't support throws, with the reason. There is no fallback.
Back end
Tiles
CUDA, AMDGPU, oneAPI, OpenCL.jl on Intel GPUs
any power of two N ≤ W (W is 32 or 64)
Metal
any power of two N ≤ 32; the narrow tile_barrier is a SIMD-group-scope fence that relies on Apple GPUs executing SIMD-groups in lock-step (KernelInterface: sub-group shuffles, votes and segments Metal.jl#998)
KernelAbstractions' PoCL back end, OpenCL.jl on PoCL or Intel's CPU runtime
none: their sub-groups can't diverge from each other (on PoCL, sub-group operations are work-group barriers)
An earlier version of this PR gave narrow tiles a workgroup each where segments couldn't
diverge, with a tiles_per_workgroup query. That leaked into user code (the DGSEM
benchmarks in DGSEM benchmarks: variants with tiles (#864) #874 had to query it to choose the number of elements per workgroup), and
didn't help: unpacked narrow tiles were 1.7–2x slower than packed ones on CUDA, behind the
local-memory kernels, and on PoCL every tile operation is a work-group barrier, 2–7x slower
than local memory. Kernels that should also run on the CPU need a variant without tiles,
as with oneDPL, AdaptiveCpp or Kokkos.
Launch: the workgroup has a multiple of N work-items, and every tile is entirely
inside or outside of the ndrange. N-D ndranges work, e.g. (4, 4, nelements) in workgroups
of (4, 4, k), and are launched on a 1-D grid so that tiles stay on sub-groups. Automatic
sizing picks a valid shape. Construction and launch check the geometry before compiling.
Operations, taking the tile so that helper functions can use them: tile_shfl,
tile_shfl_{up,down,xor}, tile_any/all/ballot, ordered tile_reduce, tile_scan,
tile_exclusive_scan, tile_barrier. They need control flow that is uniform over the tile
only: tiles can diverge, loop differently or return. They lower to KernelInterface's
sub-group operations with a width of N. @index(Tile) numbers tiles workgroup by
workgroup.
@kernel passes what it finds in a kernel's body (use of tiles or collectives) as methods
of the kernel's own function, so that this also works for kernels in a local scope and in
precompiled packages with overloaded kernels.
Documented in the manual under Tiles and Choosing the tile width, plus a new section, Choosing how work-items communicate, that compares local memory, the workgroup collectives, tiles and KernelInterface kernels. The 0.10 release notes have an entry.
Tested with the KernelAbstractions testsuite on PoCL (tiles throw), CUDA (RTX 5080), AMDGPU
(gfx1036) and Metal (M1 and M3). Stacked on #830.

I tried tiles on DGSEM volume integral kernels as in Trixi.jl (tensor-product elements with Nq = 4 nodes per direction, so a 2D element has 16 nodes and a 3D slab 16, and a 2D element maps onto one tile). The benchmarks used c5b02cf with CUDA.jl's vc/ki-subgroup-ops (cff88d481) on a Quadro RTX 4000 (sm_75), and PoCL. Inside Trixi, a tile version of the 2D flux differencing half sweep was the fastest kernel I measured. I checked that the points below still apply to the current head (677881c); the new configurable widths address what I would have said about passing the width as a parameter.
1. Several sub-group-sized-or-smaller tiles per workgroup (N < W). tiles_per_workgroup(CUDABackend(), 16) == 1, so tile = 16 (one 2D element) launches 16-thread workgroups. Compared with packing two elements into a 32-wide tile by hand, that is 188 vs. 135 µs for the weak form and 631 vs. 334 µs for the flux-differencing half sweep (Float32, 65536 elements). The shuffles already take the width into account. What is missing for N < W are segmented versions of the collectives:
tile_reduce/tile_scan: an xor butterfly over the masks N/2…1 (shfl_up with width for the scan);
tile_ballot: shift and mask the sub-group ballot by the tile's lane offset;
tile_any/tile_all: from the segmented ballot;
tile_barrier: the sub-group barrier suffices.
With these, tiles_per_workgroup(backend, N) could return typemax(Int) for every power-of-two N ≤ W on backends with independent sub-groups, like CUDA's tiled_partition<N>.
2. N-D ndrange / tile shape. Tiles need a 1-D ndrange. DG kernels are naturally written with @index(Global, NTuple) over (Nq, Nq, nelements). With tiles, the decomposition into (slot in tile, i, j, element) and the handling of padding lanes have to be written by hand. Two options:
accept an N-D ndrange where the workgroup covers the leading dimensions completely (workgroupsize[1:end-1] == ndrange[1:end-1]), so padding only occurs in the last dimension and tiles are runs of the linear local index;
or a shaped tile, e.g. tile = (4, 4), with Cartesian lanes and tile_shfl(t, x, (l, j)).
When Nq² does not divide the tile width (Nq = 3, 5), some lanes are in range but map to no node. This works because the shuffles take the lane modulo N. Documenting that idiom (clamp the loads, guard the stores, keep all lanes in the shuffles) would help.
3. shfl_fields / shfl_words are not inlined in larger kernels. Both are @inline @generated, but @inline on a @generated definition does not apply to the generated body, and the generated bodies carry no Expr(:meta, :inline).
In a 3D kernel that shuffles an SVector, the LLVM IR has 32 calls to julia_shfl_fields_* with the value passed through an alloca, and SASS shows local-memory traffic (96 LDL / 52 STL).
Swapping only the shuffle path for a component-wise one in the same kernel and the same run: 2137 µs vs. 492 µs (160 SHFL, no local memory).
Returning Expr(:block, Expr(:meta, :inline), shfl_fields_expr(T, :val)) from the generator fixes it: the KI path then has no calls, 160 SHFL and no LDL/STL. shfl_words probably needs the same.
I verified that locally and reverted it. The code is from Add @groupreduce and @groupscan #830's KernelInterface commits.
4. Struct shuffles on PoCL cost one work-group barrier per field. On PoCL, an SVector{4} shuffle becomes four sub_group_shuffles, each effectively a barrier, so the tile kernels were 1.2–4x slower than the same kernels with @localmem + a barrier (e.g., 2D weak form 3989 vs. 1015 µs). Suggestions:
shuffle an aggregate with a single exchange on backends where a shuffle is "store, barrier, load";
or use vector shuffles (intel_sub_group_shuffle on float2/4/8/16) where cl_intel_subgroups is available;
and document that tile shuffles are slow on the CPU backend.
(Investigated with the assistance of Claude Code.)

I let Claude rework this PR, #831, and the back-end PRs around those four points:
1. Several narrow tiles per sub-group. Tiles narrower than the sub-group now share it, though not quite as you sketched. Tiles may diverge: a tile-uniform return, different trip counts, padding tiles that skip the body. With two tiles in a warp, that makes FULL_MASK shfl.sync/__syncwarp UB, so the sub-group barrier isn't enough. Instead:
KernelInterface has width variants of all communication functions: sub_group_ballot/any/all(pred, width), sub_group_reduce/scan/exclusive_scan(..., width) and sub_group_barrier(width), next to the width shuffles.
supports_independent_segments(backend) says whether only the caller's segment has to execute them.
CUDA uses a mask per segment, like tiled_partition<N> (a constant full mask when the width is the warp size). AMD and Intel GPUs need nothing extra.
tiles_per_workgroup(backend, N) is now an upper bound: any number on CUDA, AMD and Intel GPUs, a single narrow tile per workgroup on Metal and the CPU. Those can't do better: MSL and OpenCL have no barrier for part of a sub-group, and PoCL's sub-group operations are work-group barriers. Tiles behave the same everywhere; only performance differs.
On an RTX 5080, a kernel like yours (ndrange (4, 4, 65536), tile=16, shuffles of an SVector{4, Float32} and a tile_reduce) takes 35.2 µs with a tile per block and 14.8 µs with 16 per block.
2. N-D ndranges. I took your first option:
Kernels with tiles accept an N-D ndrange, as long as every tile is entirely inside or outside of it, e.g. (4, 4, nelements) in workgroups of (4, 4, k).
They are launched on a 1-D grid so that the tiles stay on the sub-groups.
The automatic workgroup size picks a shape that satisfies this.
@index(Tile) numbers the tiles workgroup by workgroup, so with tile=16 and Nq = 4 it's the element.
No shaped tiles.
The idiom for Nq = 3 or 5 (lanes without a node still take part in the tile operations) is in the @tile docs.
3. Inlining. Right, with a narrower cause: @inline does apply to a generated function, except when the generator returns the body with an explicit return. The generated bodies are now marked for inlining. A shuffled SVector{5, Float32} is 5 SHFL and no local memory.
4. Struct shuffles on PoCL. Structs are now packed into 32-bit words, with small fields sharing a word. The words go through a hook that KA's PoCL backend implements with OpSubgroupShuffleINTEL on a vector, so it's one work-group barrier per up to 16 words. PoCL 7.2 had stopped accepting SPV_INTEL_subgroups on its CPU device; pocl/pocl#2394 fixes that and will be in the next pocl_jll. Four shuffles of an SVector{4, Float32} over 4M work-items now take 1.7 ms instead of 4.6 ms. Each shuffle on the CPU is still a barrier, so @localmem and @synchronize can still be faster there.

KernelInterface: sub-group shuffles and votes
…
aa64cc5
```
Add `shfl`, `shfl_up` and `shfl_xor` next to `shfl_down`, their variants within segments of
a `width`, and the votes `sub_group_any`, `sub_group_all` and `sub_group_ballot`. Back ends
implement the shuffles for their native primitive types; other primitive types are shuffled
as `UInt32` or `UInt64` words and `isbits` structs field by field, with `supports_shuffle`
derived accordingly.

Which work-items form a sub-group stays unspecified. Back ends that form them from
consecutive work-items report `supports_linear_subgroups`, and those whose sub-groups can
communicate in control flow that differs between the sub-groups of a work-group report
`supports_independent_subgroups`. The testsuite computes the expected results from the
sub-groups that formed, so that it runs without either guarantee.

The POCL back end implements the shuffles and votes with SPIRVIntrinsics, for widths of up
to 64 so that the ballot covers every lane. PoCL forms sub-groups from consecutive
work-items, but executes sub-group operations as work-group barriers, so it reports linear
but not independent sub-groups.

Co-authored-by: Tim Besard <tim@juliahub.com>

b6903d2

KernelInterface: shuffle structs as packed words
…
c497ccd
```
Structs and tuples were shuffled field by field, a shuffle per primitive
field, so that e.g. an `NTuple{2, Float16}` took two. Pack their fields
into `UInt32` words instead, with fields of less than 4 bytes sharing a
word, and shuffle the words through `shfl_word_tuple`. A backend can
implement that to exchange all words at once: on PoCL, where every
shuffle is a work-group barrier, that would help, once its CPU device
accepts vector shuffles from SPIR-V.

The generated fallbacks also weren't inlined: `@inline` on a generated
function doesn't apply to a body that the generator returns with an
explicit `return`, so shuffling an `SVector` in a larger kernel left a
call, with the value passed through memory. They now mark their bodies
for inlining.

KernelInterface: partitionable sub-groups
…
9e6a0ca
```
Tiles narrower than a sub-group have to share it, and to be useful they
have to be able to diverge from each other, like CUDA's
`tiled_partition<N>`. Add the votes, collectives and barrier within
segments of `width` lanes (the shuffles already had a `width`), and
`supports_partitionable_subgroups`: whether a sub-group can be
partitioned into segments that diverge independently, so that only the
work-items of a segment have to execute these together. It extends
`supports_independent_subgroups` to segments, and implies it.

The fallbacks build on the functions without a `width`, so that they
are correct wherever the whole sub-group executes them. Backends that
report partitionable sub-groups have to make them work for a segment
alone: CUDA needs a mask of the segment's lanes, other backends a ballot
that only reports active lanes and a barrier that a segment can execute.
OpenCL and Metal have no barrier for part of a sub-group, so there it
takes hardware that executes a sub-group in lock-step, like Intel's and
Apple's GPUs, and a fence. PoCL never reports it, as its sub-group
functions are work-group barriers.

The shuffles with a `width` of other types now shuffle `UInt32` words
with a `width`, so that a backend's shuffles with a `width` handle them.
```
POCL: shuffle packed structs with vector shuffles
…
8d7ce1f
```
Every shuffle on PoCL is a work-group barrier, so a struct packed into
words cost a barrier per word: tile kernels shuffling an `SVector` were
several times slower than ones using local memory. Exchange the words
with the vector shuffles of `SPV_INTEL_subgroups`, a barrier per up to
16 words, which PoCL's CPU device accepts with `cl_intel_subgroups`

work-items take 1.7 ms instead of 4.6 ms.

KernelInterface gets `shuffle_source`, the lane a shuffle reads from,
for backends that exchange the words with a shuffle from a lane.

```
Work-group reductions and scans for `@kernel`, as collectives like `@synchronize`: they are
statements of their own that every work-item of the workgroup reaches, and the split of the
kernel body makes the work-items that pad a partial workgroup take part, contributing the
neutral element without evaluating the value. The value is converted to the type of
`neutral` before the call, so that a union-typed value doesn't split the collective, and
`neutral` is evaluated once. The upper bound of a dynamic workgroup size is the keyword
`groupsize`.

`@groupreduce` needs a commutative operator, `@groupscan` only an associative one, in the
order of `@index(Local, Linear)`. Both use local memory.

Reduce sub-groups first in @groupreduce where the backend can
…
8fe0876
```
On backends with sub-groups, `@groupreduce` reduces every sub-group with
`KernelInterface.sub_group_reduce`, which backends can implement natively, and then the
results of the sub-groups. That only relies on the sub-group ids, so it needs neither linear
nor independent sub-groups.

KernelAbstractions picks the algorithm instead of a user-facing option: kernels that use
collectives get the backend's sub-group capabilities in their `CompilerMetadata`, and use
the sub-groups for types the backend can shuffle. Floating-point types need the backend's
support for that type, since a native shuffle may be selected by type alone; other
primitive types and structs are shuffled as packed words. Kernels without collectives don't
query the capabilities.

Add tiles
…
23d70e6
```
A kernel constructed with a tile width, `f(backend; tile = N)`, divides its workgroups into
tiles of `N` consecutive work-items (by `@index(Local, Linear)`), like CUDA's
`tiled_partition<N>`. The work-items of a tile communicate with operations that take the tile
(`tile_shfl` and its variants, `tile_any`, `tile_all`, `tile_ballot`, `tile_reduce`,
`tile_scan`, `tile_exclusive_scan` and `tile_barrier`), in control flow that only has to be
uniform over the tile. `@tile()` returns the work-item's tile and lane, and `@index(Tile)` the
global index of its tile.

Tiles aren't declared in the kernel: what sets a kernel with tiles apart is its width, which
the host needs for the launch geometry, and which is passed when the kernel is constructed.
A kernel that uses `@tile()` or `@index(Tile)` has to get one; the `@kernel` macro notes that
use, so that construction rejects a missing width. There is no default: the sub-group width
differs between backends (32 or 64 on AMD GPUs), so kernels name the width they're written
for. The width is a type parameter of `Kernel` (`tile_width(kernel)`) and reaches the device
through the kernel's `CompilerMetadata`, where `tile_width(t)` is a constant.

Tiles are a capability: a power-of-two `N` of at most the sub-group width `W`, any number of
tiles per workgroup, and tiles that diverge independently, also where several share a
sub-group (KernelInterface's segments). `supports_tiles(backend, N)` reports it, and
constructing a kernel with tiles a backend doesn't support is an error. All GPU backends
support widths up to 32. The CPU backend has no tiles, as its sub-group functions are
work-group barriers, which can't diverge. Falling back to a tile per workgroup there would
leak into how kernels choose their workgroup size, and be slower than a kernel using local
memory, which is what such backends need instead.

The ndrange can have several dimensions, e.g. one per index of the nodes of an element, if the
workgroups divide it into whole tiles. Such kernels are launched on a 1-D grid, so that the
tiles stay on the backend's sub-groups. Without an explicit workgroup size, the launch picks
one that does; construction and launch check the geometry before compiling.
