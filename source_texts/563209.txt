Problem
The OptiX backend creates and links ray-tracing pipelines in src/cuda/optix-api-impl.cpp, but it never computes program-group stack requirements or calls optixPipelineSetStackSize (or optixPipelineSetStackSizeFromCallDepths).
OptiX documents that its internal default is correct only when there are no direct-callable programs or motion transforms. Once a pipeline contains a Slang [shader("callable")] entry invoked through CallShader, the backend cannot rely on that default.
This is separate from #857. Correcting the emitted entry-point prefix lets OptiX create the callable program group, but does not establish a valid runtime stack contract for non-trivial direct callables.
Reproduction shape
A ray-generation, miss, or closest-hit shader calls a direct callable whose body has a non-zero direct stack requirement. slang-rhi links the callable program group but launches the pipeline without configuring directCallableStackSizeFromState. An intersection or any-hit caller has the analogous directCallableStackSizeFromTraversal requirement.
The existing callable runtime test is a leaf callable and may happen to use no measurable direct stack, so it is not sufficient coverage for this defect.
Expected direction
Accumulate stack sizes for every linked OptiX program group.
Provide or derive maximum direct-call depth separately for calls from traversal (intersection/anyhit) and state (raygeneration/miss/closesthit).
Configure the pipeline stack after linking.
Add a callable runtime test whose generated direct-callable body requires stack.
The public RayTracingPipelineDesc currently exposes only maxRecursion; it has no direct-callable-depth or traversable-graph-depth contract, so the API/default policy needs to be decided as part of the fix.

Triage — slang-rhi#858 (OptiX direct-callable stack sizes)
Confirmed at source (GPU-free): DeviceImpl::createPipeline (src/cuda/optix-api-impl.cpp:707) links the pipeline with optixPipelineLinkOptions.maxTraceDepth = desc.maxRecursion (:1010, then optixPipelineCreate :1013) but never calls any stack-size API. A tree-wide grep for optixPipelineSetStackSize* / optixUtilComputeStackSizes / optixProgramGroupGetStackSize finds zero hits in src/+include/ (the only real maxTraceDepth match is :1010). Direct-callable/continuation stacks therefore run on OptiX defaults, so a non-trivial [shader("callable")] invoked via CallShader can under-run its stack. The claim holds.
Subsystem / severity / priority: CUDA/OptiX backend · medium (runtime correctness/robustness, but narrow — OptiX-only, non-trivial direct callables, and gated behind OptiX callable program groups use the wrong Slang symbol prefix #857 which is what lets the callable program group be created at all) · P2. Not reproduced: stack overflow is observable only on an OptiX GPU (none here), so this was confirmed at the code level rather than at runtime.
No structural blocker to the fix: the linked program groups are retained on PipelineImpl::m_programGroups (:560, moved at :1043), so the pipeline handle + all groups + maxRecursion are in scope immediately after optixPipelineCreate (:1024) — the natural insertion point. OptiX's optixUtilComputeStackSizesDCSplit (optix_stack_size.h) produces exactly the from-traversal (IS/AH) vs from-state (RG/MS/CH) split described here, feeding optixPipelineSetStackSize(...).
API/policy decision (as flagged): RayTracingPipelineDesc (include/slang-rhi.h:2169-2187) exposes only maxRecursion; a direct-callable-depth / traversable-graph-depth contract would be new surface. The struct carries a structType+next extensibility chain, so the ABI-clean options are append-at-end (default-initialized) or a next-chained extension struct — versus an internal default depth. Which one is a maintainer design call.
Test coupling: the sole callable test ray-tracing-intrinsics-call-shader (tests/test-ray-tracing-intrinsics.cpp:469) is masked D3D12 | Vulkan (CUDA excluded, :468) and its callable callableWriteAttribute (.slang:332-336) is a leaf — so there is no OptiX coverage today, confirming the "insufficient coverage" note. A non-leaf callable OptiX test additionally needs OptiX callable program groups use the wrong Slang symbol prefix #857's enablement (symbol-prefix fix + a SLANG_RHI_FETCH_SLANG_VERSION bump to ≥ v2026.17 for compiler callable support).
