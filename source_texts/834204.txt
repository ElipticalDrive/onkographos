How to improve performance of a ray marched scene with hundreds of SDFs?
Question
So I am working on a game in Unity, and the scene is rendered with SDFs. There a can be up to a couple thousand of objects that make up the scene.
I have optimised the SDFs as much as I can to avoid expensive operations such as sqrt. I only march objects that are can be visible to the camera, reducing the rendered objects by a couple of hundred at any given time, but the bottleneck seems to come from taking the union (minimum distance) of all these SDFs in order to build the scene.
Does anyone have an idea on how to optimise such a scene/specifically the union operation? Or if it is just a limitation I have to accept?

Render them one at a time. Emit a box that covers the maximum extents of the object to the standard rasterization pipeline. March the object for as long as the ray is inside that box. If you hit, set the distance as the depth buffer value, and if not, discard the fragment. This has the nice benefit that it also works if you want to add some triangle geometry to the scene.
Another option is to build an acceleration structure over your objects. A BVH is usually simple and effective, and for a couple thousand objects you should be able to build it dynamically every frame. This is an especially good option if you want secondary rays for shadows or reflections (since the first can't really help with those).

The difference would be that instead of considering every object for every pixel, you'd draw a box for every object which would only be the size of the object, and only march that object for the pixels that cover this box. You should also clip the ray so that you only start marching from when the ray enters the box, and stop when it exits the box -- this usually doesn't leave too many steps to take. The time save comes from only considering objects when they can matter, basically a more fine-grained version of your frustum culling. This can be suboptimal though, if you have a bunch of objects behind each other, then this method would in the worst case first render all of the objects and only then decide to use the closest one (you can help this by sorting the objects so that the closest ones are handled first, the GPU can then cull the latter ones based on their bounding box being further away than the closest found intersection).
No, you can use an acceleration structure also to reason about distances. The basic idea is that we split the objects in two sets (usually left/right or top/bottom or front/back) and compute the bounding box for both sets. Then, when you want the closest distance to an object, you first determine which bounding box is closer to your query point, and find the closest distance to its set of objects. If this distance is smaller than the distance to the other bounding box, you can be sure that no object in the other set is going to be closer than your already found distance and you can now safely skip half of the objects. In an actual implementation you do this splitting recursively.
This reminds me, another thing people do with SDFs is level of detail; if you're far enough from an object, you can just replace it with a sphere to save computation. This obviously won't help with the linear step of having to compute the min from every object.

As others have said, bounding shapes will be your friend. Test a cheaper bounding shape before you evaluate the full sdf inside it.
Another optimization that works well is to generate a pre-pass at 1/8 resolution or so, and just store the distance to the first sdf intersection in that pixel. Then in the full resolution pass, you effectively have a coarse "Start distance" for each 8x8 group (or Tile) of pixels. Now you can just start your raymarch at that distance and save alot of evaluations.

You could implement the clustering method used in SDFGI (see section 3.3). Essentially you sort your SDF primitives into small clusters, which results in far more coherent memory accesses during marching, on top of way fewer SDF evaluations overall (due to the cluster distance culling thing in the paper too). Ideally the cluster size is small enough to fit into L1 cache, then the repeated accesses during evaluation are hitting the cache and things stay fast.
