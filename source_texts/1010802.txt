Change
Add an opaque type Rng (a single 64-bit state) and five pure functions, each returning the value and the next state:
random.seeded(seed: Int) -> Rng
random.next_int(rng: Rng, min: Int, max: Int) -> (Int, Rng) — inclusive on both ends, the same range rule as random.int; drawn with unbiased rejection.
random.next_float(rng: Rng) -> (Float, Rng) — in [0, 1), built from the top 53 bits.
random.next_choice[T](rng: Rng, xs: List[T]) -> (Option[T], Rng)
random.next_shuffle[T](rng: Rng, xs: List[T]) -> (List[T], Rng) — Fisher-Yates.
The algorithm is SplitMix64 written in pure Almide.
Why
The current random has 4 functions and no way to pass a seed. When a test needs reproducible randomness, models write a Random(seed)-shaped API.
6/9 surveyed languages have seeded generators: Go rand.New(rand.NewPCG(..)) (F), Python random.Random(seed) (F), Kotlin Random(seed), OCaml Random.State, Erlang :rand.seed, and Deno's seeded random. All of them mutate the generator; Almide has value semantics, so it uses the "return the next state" shape that Gleam and Elixir (:rand.uniform_s returns {value, state}) use.
let (x, rng2) = random.next_int(rng, 1, 6) is the standard Almide tuple-destructuring shape. Reusing an old rng (repeating the same value) is caught in one form: writing random.next_int(rng, 1, 6) as a statement is rejected by R-L0-05 (discarding a non-Unit value is an error).
These are plain fn, not effects: they do not read the environment (ADR-0022).
Rules: R-L0-04 (copy by default; mut rng is not in the closed verb set, so the next state is returned); R-L0-03 (the subject Rng first); R-L0-02 (module of the returned type); L1 R-L1-04.
Current use count: 0.

Axes
(a) Other languages: 6/9 (4 unconditionally, 2 through a runtime or OTP).
(b) Native and wasm: pure computation, no host capability. SplitMix64 needs only addition, XOR, logical right shift (int.bshr_logical, R-int-06) and wrapping multiplication, so the sequence is identical on both targets and goes under ADR-0016 numeric determinism.
(c) LLM writability: matches the Random(seed) intent with Almide's tuple-return idiom.
(d) Kind of change: addition (1 type, 5 functions).
Completeness rule
Two sources, one role table: environment randomness (effect, current 4 functions) and the seeded Rng (pure) cover the same four roles: integer in a range, Float in [0, 1), choose one, shuffle. Seeded names are derived mechanically: prefix the environment function's name with next_, take Rng as the first argument, return (result, next Rng).
The sequence is fixed across versions: SplitMix64, bit-identical on native and wasm, unchanged across Almide releases. Changing it requires a dialect epoch breaks entry.
Only random.bytes(n) is cryptographic; the others are documented as not for secrets.
One shuffle: random.shuffle (effect); list.shuffle is being retired.
Compatibility
Additive; no compatibility impact.
Gate
In the same PR:
A spec pinning the first 8 values from seeds 0, 1 and int.max_value(), and a spec/wasm_cross fixture asserting identical sequences on both targets. The pinned values go into an als contract (new C number placed in als first).
A signature gate checking the completeness-rule-1 mapping (next_ + environment name, Rng first, tuple return).
