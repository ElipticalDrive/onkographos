Merge commit: f74ebc66bf20
This is a (long-awaited) refactor of OrientedBoxTreeTool that removes special purpose logic for managing intersections that is specific to the use cases of GeometryQueryTool (and perhaps related methods).
The main approach is to introduce the notion of an intersection registration context that is handed the fundamental information for each intersection and uses its own logic to determine if/how to accumulate that intersection in its list. A base class for this kind of context is provided, and also serves as a default that accumulates all intersections.
A specialization of this base class is introduced in GeomQueryTool that now holds all the logic that was previously implemented in OrientedBoxTreeTool and optionally invoked by the presence of a specific set of variables.
This refactor preserves a conventional interface for querying the intersections between a ray and sets.

Paul Wilson (@gonuke) commented on 2017-05-19
This is the supported behavior. This test is firing a ray from outside the cube through along the axis of the cube, at the exact center. For most simple tri-meshes of a cube, this means that it is firing the ray exactly at the edge between two facets, on each of the two surfaces that it crosses. With the Plucker tests, each of those is identified as a separate hit, returning a total of 4 hits. The standard test expects to find only 2 hits. This is the most general solution - there may be use cases in which the user wants all the hits. That said, if we want a different behavior, we can certainly discuss it.
