Claims #1948 (R6 of #620): a second image executor, gpu-path, that path-traces the Render workspace's product scene on the GPU through wgpu, progressively, next to the existing cpu-product one.
An original procedural scene (87,412 triangles, 23 materials) rendered by this branch on an RTX 4090. Everything in it is generated by a script; no imported models or textures.
What is in this PR (phase 1: opaque, progressive)
Four commits:
render: route bounded image jobs through registered executors: the CPU image API stays as it is; a generic image factory lets a second executor share the bounded queue, memory admission, cancellation, the immutable captured scene and PNG ownership, and the engine's capability resolution picks the installed host.
gpu: add bounded opaque path tracing with software BVH traversal: a balanced median BVH per job on the CPU, indexed vertices/triangles/materials uploaded, an original WGSL integrator with software traversal (runs on every adapter, no ray-query extension), the existing GGX/Smith/Schlick surface (surface.rs) as its oracle, next-event estimation on the studio lights, indirect bounces and Russian roulette. Dispatches are bounded (≤262,144 paths each) and cancellation is checked between them.
ui: expose progressive image jobs in Render workspace and CLI: transient sampling controls in the Render workspace and solidcraft-cli render … --progressive --samples N; docs/render-path.md states exactly what is and is not supported.
gpu: stabilize surface hits and respect software viewport fallback: secondary rays start from barycentrically interpolated hit points (reconstructing them from the ray distance put shadow rays behind skinny pole triangles), and the job device opens on the viewport's adapter, so safe-mode software fallback holds.
Advertised: RenderMode::Preview, PNG, PBR, Progressive. Not advertised and not implemented here: HDRI, refraction, absorption, EXR, Final mode, denoising.
Verification
8 path tests on lavapipe here, and on RTX 4090 Vulkan, DX12 and the WARP software adapter: offline WGSL validation, 81 BRDF comparisons against the f64 surface.rs oracle, a rendered plane with face appearances against the CPU studio, a sphere furnace, fixed-seed repeatability, hostile admission, cancellation never publishing a frame, and a skinny-triangle self-shadow regression that fails before the fix.
GPU crate 23 passed (2 benchmarks ignored), render crate 113 passed, Render UI tests pass; clippy -D warnings, wasm and layers clean.
1,048,576 triangles at 1920×1080: 4.3 ms per sample on the 4090 (Vulkan), 6.6 ms on DX12, BVH build 1.3 s, upload 84 MB; 0.83 s per sample on lavapipe.
On main at 72145d4, the ui-egui tests fail only where main itself does: ja.json lacks the two grid messages from #2035, and inspect.silhouette has no icon yet. This branch adds Czech, Japanese and Chinese for its own three new messages. The engine suite passes except a wall-clock test (fillet_beside_a_modelled_thread_finishes, 62 s on a loaded machine).
Coordination
This is the GPU lane only. @0xlillith's CPU ray tracing (#1368, #1698 and the slices #1651–#1696) owns the CPU side, and #1698 also edits job/host.rs and job/image.rs; I will rebase whichever lands second and would like the GPU executor to use the same scene, material and environment contracts and to be checked against the CPU tracer as its oracle, as the GPU solver in FieldCraft is checked against its CPU scheme. Glass (#1655), HDR environments (#1693) and the rest would come to the GPU as follow-up PRs on those contracts, not as competing ones. @bluecmd, I reviewed the shared host seam at f729a03469dadae1e84179245033515c3305ceab. The executor-factory direction works with the CPU integration. There is one concrete resource-lifetime fix we should preserve when combining them.
Release task-owned scratch before shrinking the completed-frame charge
In Running::advance, TaskPoll::Complete shrinks the reservation to the PNG, publishes Completed and notifies waiters while Running.task: Box<dyn ImageWork> is still alive. It is dropped after guarded_step returns, in the cooperative/native owner.
The GPU task still owns its accumulation/readback/uniform buffers, bind group and PNG task; its PNG branch returns the completed bytes without dropping those fields. That creates a logical accounting window in which scratch remains owned after its charge has been released. This is a source-level lifetime finding; I have not reproduced an RSS spike or made a claim about driver-internal reclamation.
Our published CPU host already makes the task removable and clears it before shrinking the reservation. Could we retain that order in the generic host, for example with an optional task that is taken/dropped before shrink, while keeping the final cancellation/publication lock? An alternative is to retain the full scratch charge until the task is destroyed.
A deterministic regression can use an ImageWork whose destructor observes the budget: the original task charge must still exist during Drop; after completion the task must be gone and the PNG/retained-record charges must remain. This should distinguish the two orders without sleeps or RSS measurements. The final-step cancellation case should still publish no frame.
Rebase seams to retain
The newer CPU integration also carries captured EnvironmentInput, retained request/HDR metadata, a fallible bounded task slot, raster/raytrace capability selection, and the shared Check/Start builder with invalidation. Those need to travel through the generic factory along with the opaque path. CPU primary-AA samples, reflection samples and GPU progressive spp remain separate controls.
I also checked the documented budget distinction: this PR creates separate CPU/GPU host pools. Our integration notes will state both pools and their per-job caps explicitly. Film #1696 and the new PngTask can share output/ownership guarantees while keeping suitable internal storage for each executor.
The coordination replies are now in #1368 and #1655. I am continuing the CPU/main reconciliation and can review the generic-host adjustment against the resulting exact head.

Desktop UI walkthrough: progressive GPU path render (bf67f31)
Full-quality video (51.7 s, 1280×720, H.264): ui-gpu-path.mp4
Exported frame: stage1-gpu-path-512spp.png
What is shown:
The real solidcraft desktop app: a release build of this PR's head, bf67f31.
It ran under Xvfb on an NVIDIA GB10 (DGX Spark) with the Vulkan backend.
The path host is installed through set_wgpu → solidcraft_gpu::path::host_on_adapter, on the viewport's adapter.
The flow, in order:
Open the workspace menu and choose Render.
Tick Perspective camera.
Set Width 1280 and Height 720.
Tick Progressive rendering and set Samples per pixel to 512.
Click Check Render Request, then Start Render. Progress shows until "Image ready to export", about 11 s.
Click Export PNG. A GTK file chooser opens through xdg-desktop-portal.
The progressive request resolves to the gpu-path executor (native_worker host). On this branch cpu-product does not offer Progressive.
What was scripted (honest disclosure):
Two steps went through the app's --control server rather than mouse input:
Building the scene: engine.script replaying the original examples/studio/stage1.json recipe from Render: studio lighting, clear coat and glass on the GPU path tracer (in progress, #1948) #2191.
Setting the camera: ui.camera, using that recipe's studio view.
All other steps are synthetic pointer/keyboard events on the visible widgets: ui.click, ui.key and ui.text, with xdotool for the file name in the save dialog.
The app has no viewer for the finished frame. The final seconds show the exported PNG opened in feh, outside SolidCraft.
Lighting is the executor default, because this panel has no lighting controls. * Sketch offset keeps its source lines free to turn (#4464)

An offset adds a Parallel between each source line and its offset line.
Since offsets became associative, the offset's points are held during a
solve, so each Parallel pinned its source line to the offset line's

* Timeline: suppressing a feature keeps later features' body names (#4302)

Bodies numbered by the counter (`BodyN`) take the next free number on every
recompute, so suppressing a feature that made one moved every later counted
body down one (`Body2` became `Body1`) and broke what named it, such as a
Move of `Body2`. timeline.suppress now stores the current names of later
features' counted bodies in their `body_names` first, as body.rename already
does for a renamed counted body (#1109). Engine only: no evaluation or
design-format change.

Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>

* Timeline: a body made while a feature is suppressed keeps its name (#4302)

Suppressing a feature freed its counted name (`Body1`), so a body made
meanwhile took it and became `Body3` once the feature was back. Suppress
now also stores the suppressed feature's own counted names, and the
evaluator adds the names stored on earlier suppressed features to the
state's `reserved_body_names` (the names a rename freed, #4957), which the
`BodyN` counter passes by. They are taken from the design before each
feature is computed and are part of the state digest, so a cached result
is only reused when they match.

* Hole: place a Single hole by distances from reference edges (#37) (#2931)

A Single hole can take up to two straight edges of its face as references,
each with the distance of the hole's centre from that edge's line, measured
in the face's plane. `solid.hole` takes them as `references: [{edge, distance}]`;
the edges are found again by their persistent names, else their points, so
the hole follows them when the part changes, and each distance is a
parameter. A bad reference (no edge there, a curved edge, one square to the
face, parallel edges, a negative distance, a centre off the face) is refused.

In the Hole dialog, Reference 1 and 2 follow the face, each with its Distance
row; the canvas shows each distance as a dimension from its edge to the hole,
with a box just past the edge to type it in. Picking an edge measures its
distance (and its box takes the keyboard), typing one moves the hole, and
moving the hole measures them again. Edit Feature picks the edges again with
their distances.
