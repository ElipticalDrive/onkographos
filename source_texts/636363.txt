Two changes toward "large maps shouldn't take an hour, and you shouldn't have to wait for the whole thing to see it."
perf: ~44% faster meshing
Profiling a dense world showed meshing is 74–77% of render CPU, and the greedy pass (6 full-volume grid sweeps, each re-probing neighbours) was ~62% of that. Two byte-identical wins:
Shared face-visibility mask — buildFaceVis precomputes each cell's 6-direction visibility once; the sweeps read one contiguous byte and walk an incremental grid index instead of rebuilding coordinates + re-probing neighbours. The dense solid interior collapses to a single masked skip.
Pure-occluder skip — a per-id flag lets the per-block pass skip terrain blocks the greedy pass already emits whole, instead of re-walking them.
Result: New World geometry 24.6s → 13.8s (−44%), wall −18%. Proven byte-identical against the pre-change baseline (single-threaded output reproduces the exact tile hashes under the same tile order).
feat: progressive live rendering
Tiles already stream to disk per-worker — the only thing blocking a live view was the end-of-run manifest and finalize-at-end atlas. Both are fixed by leaning on the append-only id property (a texture/biome keeps its id once assigned).
Renderer republishes manifest.json (and terrain.vtexarr, when it grows) every ~400 ms as tiles land, written atomically (temp + rename) so a polling browser never reads a torn file. Tiles now render spawn-outward, so the map blooms from spawn. New manifest fields: rendering, progress, textureLayers.
Viewer polls a rendering: true manifest, streams new tiles through the existing nearest-first + fade-in machinery, widens the texture array on growth, and installs the lowres pyramid + full zoom range when the bake finishes. Emits a progress event for a UI readout.
Usage: run vantage serve <dir> --open alongside vantage render <world> --out <dir> and watch the world materialise tile by tile instead of waiting for all of them.
Verification
69/69 Zig tests, 46/46 web tests, TS typecheck — green.
Geometry deterministic and byte-identical to baseline.
End-to-end via Playwright: the viewer loads a live manifest, streams the tile total from 53 → 112, fires the completion event, ingests lowres, and renders the full world correctly.

## What

A new **`vantage live <save>`** command: open a world in the browser
**now** and bake each tile the moment it scrolls into view, instead of
pre-rendering the whole map. This is the on-demand ("dynamic") follow-on
to the progressive bake from #23.

```sh
vantage live "~/.minecraft/saves/My World" --open   # → http://127.0.0.1:8268/
```

A 726-region world (Luna) is explorable in **seconds at ~20 MB RSS** —
the world stays on disk, only the assets + texture atlas are resident —
where a full `render` takes an hour. Tiles cache into `--out` as they
bake, so panning back is instant and the cache doubles as a partial
render you can later `serve`.

## How it works

- **The manifest lists every populated tile up front** (cheap — straight
from the region location tables), marked `dynamic`/`rendering`. Each
tile is baked lazily on its first fetch. The viewer already fetches only
near-camera tiles nearest-first, so baking naturally follows the
viewport — no viewer-side scheduling changes.
- **Atlas-coverage gating (the one real hazard).** The texture atlas
grows as tiles bake in *viewport* order, so a fetched tile can reference
atlas layers the viewer doesn't have yet. The viewer now computes a
tile's max layer (from its own layer ids) and, if it exceeds the loaded
atlas, **widens the atlas before the tile is drawn** — so nothing is
ever sampled against a missing-texture atlas. A coalesced refetch shares
one request with the progressive poll, which also tightens that path's
residual atlas race.
- **Empty tiles.** A batch render omits tiles that mesh to nothing; a
live manifest can't (it lists them before baking). The server returns an
empty body and the viewer marks them empty (no geometry, no retry)
instead of choking on a 0-byte parse.

## Refactor (no behaviour change to `render`)

In service of the above, shared by `render` and `live`:
- `Shared` + `bakeTile` — the long-lived bake state and the per-tile
bake, extracted from `runRender`.
- `resolveWorld` + `enumerateTilesSpawnOutward` — world/asset loading
and tile enumeration.
- `serve` gains an optional on-demand `Producer` hook, so **one** HTTP
server implementation covers both static and live.

## Verification

End-to-end in a real browser (New World + Luna):
- On-demand bake **~190 ms/tile**, cache hit **~2 ms**.
- Atlas grows **366 → 565 layers** mid-session with **zero**
missing-texture glitches (the gating works).
- Live render is **identical to the batch render**: 81/132 tiles
written, 51 empty, **565 atlas layers** — exact match, confirming both
the emptiness logic and that the incrementally-grown atlas ends up the
same as the batch atlas.
- Flat footprint: **19.8 MB RSS** (Luna, 726 regions) / 38 MB (New
World, active streaming).
- **0 console errors, 0 warnings**; `rendering` flips to `false` once
every tile has been baked.
- All tests pass: **72 Zig, 47 web** (added coverage for `parseTilePath`
and the `dynamic` manifest flag). `render` output verified byte-for-byte
unchanged.

## Follow-ups (not in this PR)

- No lowres underlay in live mode yet (the zoomed-out coarse rings need
a whole-world pass); hires streams on demand near the camera. The biome
palette/legend for newly-appeared biomes settles on the next manifest
poll (same as the existing progressive mode) — normal rendering is
unaffected since grass/foliage tint is baked into vertex colours.
