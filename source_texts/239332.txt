Objective
Let user compute shaders author mesh instances that the standard mesh pipeline draws: culled per view, drawn with any Material, with shadows, prepass, and deferred, as one indirect draw per batch. This is the low-level primitive that GPU particle systems need to draw lit meshes (see #20569), and the piece bevy_hanabi's lighting request (djeedai/bevy_hanabi#215) would build on.
Today every MeshInputUniform slot is owned by one entity and written from ECS extraction. The only way to draw compute-written instances is a custom render command with a hand-rolled instance buffer (custom_shader_instancing), which gets no material, culling, or shadow support.
Solution
We add a new kind of renderable GpuBatchedMesh3d (please feel free to bikeshed) entity, paired with a MeshMaterial3d, reserves a persistent output buffer of max_capacity GpuMeshInstance slots. A producer writes them from compute in the GpuInstanceBatchSystems::Publish set in the rendergraph. A renderer-owned materialize pass then copies the slots into a GPU-only tail of the mesh preprocessing input and culling buffers, applying a CPU-owned template for mesh, material, and flags. A range-unpacking pass expands the batch into ordinary preprocessing work items, from which point they appear as if they were "regular" mesh-materials.
Design points:
Producers write GpuMeshInstance slots into the reservation's output buffer. The renderer builds the actual mesh inputs from them each frame, so changing a batch's mesh or material needs no re-reservation.
The output buffer persists across frames, so a producer can skip frames and the last published instances keep drawing.
In sorted phases a batch is one item, ordered by its entity's Aabb center. Instances within it aren't sorted, since we'd need DGC for that.
The only new trait method is GetFullBatchData::get_instance_batch. It defaults to None, so Mesh2d and third-party batchers are unaffected.
Changes outside the new module that reviewers should look at:
Mesh3dVisibility is now the visibility class of 3D mesh draws, required by Mesh3d and by GpuBatchedMesh3d, instead of Mesh3d itself.
MeshCullingData gains a per-slot is_active: u32 in its trailing padding, read by mesh_preprocess under frustum culling. Stride is unchanged.
Merged sorted phase items now get an empty batch_range, and render_range draws each item with a non-empty range instead of skipping batch_range.len() items. That length used to count both instances drawn and items consumed, which instance batches break. This also fixes a bug on main where the transmission node could redraw a merged item multiple times.
Retained transparent items keep the sort center they were queued with (2D: Changes to Z-ordering of entities with custom materials (not sprites) not reflected properly in rendering #24826). Batches refresh theirs in place each frame in PhaseSort. When Re-sort retained transparent phase items when their entity moves #25708 lands, we can get rid of the batch specific system.
Not supported here: motion vectors, transmissive materials, per-instance sorting, 2D.
Testing
gpu_particles example.
Ran gpu_particles, transparency_3d, mesh2d, and mesh2d_alpha_mode on macOS/Metal (M2 Max) with GPU preprocessing fully supported, no validation errors.
Showcase
cargo run --release --example gpu_particles
Migration Guides
Mesh3dVisibility is the visibility class of 3D meshes.
Merged sorted phase items have an empty batch_range
Disclosure: claude code was used to review and fix a variety of bugs to ensure no regressions in rendering.
