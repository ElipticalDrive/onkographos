Proposal:
Summary
Add compression for string attributes in the columnar storage engine. Currently
string attributes are stored mostly uncompressed (only their lengths are
compressed), which makes string-heavy tables take significantly more disk space
compared to engines with per-column codecs (e.g. ClickHouse).
Filing this as a formal feature request as suggested by maintainers in chat.
Current state
Columnar data is stored in blocks (up to 65,536 rows), with a per-block
encoding scheme (const, table, etc.).
String attributes have no effective compression scheme: they are stored mostly
as-is, and only their lengths are compressed when table-level compression is
not applicable.
docstore_compression (e.g. lz4hc) covers full-text fields in docstore,
but not string attributes in columnar storage.
String hashes help with filtering/grouping but do not reduce the on-disk size
of the string data itself.
Motivation / use case
Scenario: log / observability storage (typical for Manticore users). String
attributes such as service, level, host, user_agent, trace_id,
message_id typically dominate the table size, while numeric fields
(timestamps, durations, counters) are a minority.
Cardinality is mixed: level/service are low-cardinality, user_agent/
trace_id are high-cardinality — so a single scheme (dictionary-only or raw)
is not enough; per-block adaptive compression is needed.
I don’t have a production dataset to share yet, but the effect can be
demonstrated on a synthetic log dataset (see below). Qualitatively, the effect
is well known: engines with per-column codecs (ClickHouse: LowCardinality,
ZSTD, Delta) compress string-heavy log data several times better than
engines that store strings mostly uncompressed.
Proposal
Introduce a per-block compression scheme for string attributes, selected
automatically (similar to how const/table are chosen today).
As a first step, use LZ4 (fast, well-known, low CPU overhead) — see Add lz4 compression to strings #13.
Consider FSST as a follow-up / alternative for better compression ratio
and possibly faster encoding — see #1632.
Keep backward compatibility: old blocks remain readable; new blocks are
marked with the new scheme.
Ensure interaction with string hashes and existing filtering/grouping logic
is preserved.
Additional context
Related issues: Add lz4 compression to strings #13 (LZ4 for strings), #1632 (FSST evaluation).
Comparison with ClickHouse: per-column codecs (LowCardinality, ZSTD,
Delta, etc.) give significantly better compression on string-heavy
analytical data.
