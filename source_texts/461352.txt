Adds the Vulkan ray-tracing camera backend for Chrono::Sensor and aligns its LEGACY rendering behavior with the existing OptiX backend.
Key changes
Add Vulkan RT scene synchronization, acceleration structures, materials, textures, lights, and camera rendering.
Support point, directional, spot, and environment lighting.
Support diffuse, specular, metallic, opacity, normal-map, and environment-map rendering.
Match OptiX LEGACY material defaults, BRDF behavior, reflection, transparency, recursion, and visibility semantics.

baseline, falloff, default materials, and all material variants

Sensor: document what the shader-staging test can and cannot prove
…
520ef2d
```
The staging guard is worth running under ctest, but a from-scratch build
cannot exercise the property the staging rule was written for. On a clean
build staging has just run, so source and staged copy always match and the
test passes whether or not the dependency edge works. What a clean run does
catch is staging being removed or broken outright, since the staged file is
then absent and the assertion names it.

Those are two different failure modes and only the second needs an
edit-then-rebuild cycle, so the header now says so plainly and gives the
four-command manual procedure for the incremental case. The stale-shader
failure message points at that procedure, so someone who trips the guard is
led from the symptom to the check rather than having to know it exists.

Recorded here rather than in a separate script on purpose: anyone who cares
about this test opens this file, either because it failed or because they are
changing the staging rule, whereas a checker script elsewhere in the tree is
found only by someone who already knows to look for it.

Also records the measured cost of the manual procedure, 0.05 s on Linux with
Ninja, because nothing recompiles: with CH_USE_SENSOR_NVRTC on the shaders
are compiled at runtime, so the only work is one file copy. That number is
the reason a CI step was considered; it was dropped after Radu made the case
that Chrono's CI does not test build-machinery behaviour anywhere else, and
that a single exception is a precedent with a maintenance cost.

No functional change. Comment block plus one line appended to an existing
failure message. Compiled and run on an RTX 5090: test passes, and a
deliberately corrupted staged copy still fails with the new pointer line
present.

Teach the exported CMake package config about the HIP GPU backend

```
Chrono::DEM and Chrono::FSI_SPH already build against either GPU backend: both
src/chrono_dem/CMakeLists.txt and src/chrono_fsi/sph/CMakeLists.txt gate on
"NOT CHRONO_CUDA_FOUND AND NOT CHRONO_HIP_FOUND". The exported package config
was never taught the same thing and probed only for CUDA, so a downstream
find_package(Chrono COMPONENTS DEM) against a HIP build reported the component
missing even though libChrono_dem had been built and worked. The installation
manual already documents the intended behaviour, that Chrono::FSI-SPH and
Chrono::DEM require a GPU backend of either kind, so this makes the exported
config match documented intent rather than proposing new behaviour.

Changes:
  - Export CHRONO_GPU_BACKEND_RESOLVED, and initialise CHRONO_CUDA_FOUND and
    CHRONO_HIP_FOUND unconditionally before either probe. Only one probe runs,
    so leaving either uninitialised lets a value already present in the
    consumer's scope decide a component gate.
  - Skip the CUDA probe on a HIP build, which otherwise warns "CUDA not found"
    about a toolkit that was never used.
  - Add a HIP probe. It passes the ROCm root to find_package(hip) through PATHS
    rather than prepending it to CMAKE_PREFIX_PATH, because this code runs in
    the consumer's scope: a prepend persists after find_package(Chrono) returns
    and silently biases every later find_package toward ROCm's bundled
    dependencies.
  - Accept either backend in the DEM and FSI_SPH component gates.
  - Stop requiring host Thrust for FSI_SPH on a HIP build. HIP builds
    deliberately ignore ROCm's Thrust for host targets and Chrono_fsisph builds
    without it, so requiring it here rejected a working HIP build.

Chrono::Sensor is deliberately left CUDA-only, since its ray-tracing paths need
OptiX.

Tested on ROCm 7.2.0 and gfx950 (MI350X) with CMake 3.25.2, against both the
build tree and an install tree: DEM and FSI_SPH consumers configure, compile and
link; Sensor reports absent when optional and fails the configure when required;
a consumer's CMAKE_PREFIX_PATH is unchanged across find_package(Chrono); and a
consumer compiling its own .hip sources works. A stand-in ROCm exporting no
hip::host correctly leaves CHRONO_HIP_FOUND false and fails a REQUIRED DEM
configure. CUDA regression checked on 12.8 and sm_120.

Not covered: Windows and MSVC, CHRONO_GPU_BACKEND=AUTO resolving to HIP, static
builds, and ROCm versions other than 7.2.0.

Sensor: give every RNG buffer its own stream under a fixed seed
…
ab615be
```
SetRandomSeed stored one value and nine call sites handed it straight to
init_cuda_rng. cuRAND separates generators within a buffer by its subsequence
parameter, and that parameter is already spent on the per-pixel index, so the
seed is the only thing telling one buffer's sequence from another's. One seed
at nine sites therefore made them one stream: two 64x64 buffers produced 4096
identical draws out of 4096, and a 640x360 buffer was a bit-exact prefix of a
1280x720 one. Any study that enabled reproducibility and used more than one
stochastic sensor got correlated noise between sensors, with nothing reported.
A single-sensor scene looks perfectly correct, which is why the existing suite
passed with the defect present: no test in it built two stochastic sensors.

Each buffer now derives its own seed from a stream key, bit-packed into 64 bits:

  [63:33] manager id   [32:13] sensor ordinal   [12:5] filter stream   [4:0] usage

The fields occupy disjoint bit ranges and each is range-checked against its
width, so distinct keys cannot collide. Adding the base seed cannot merge two
ids either, since x -> base + x is a bijection on the 64-bit ring for a fixed
base. Out-of-range fields throw rather than wrap, because wrapping would map two
sensors onto one stream, which is the defect.

Why each field exists:
  usage           separates purposes, via a closed RngUsage enum, one constant
                  per stochastic buffer in the module.
  sensor ordinal  separates instances of one purpose, minted in AddSensor.
  filter stream   separates two filters of the same purpose on one sensor, which
                  PushFilter permits since it applies no type check.
  manager id      separates managers that exist at the same time, whose ordinals
                  both restart at zero while the base seed is process-global. It
                  is the lowest free slot, released on destruction, NOT a
                  counter: a counter would give a rebuilt manager a different id
                  and break reproducibility across repeated construction, which
                  the byte-exact render tests rely on.

Identity is assigned in AddSensor rather than only in PushFilter, because
PushFilter is not the only route into a sensor's filter list. Seven sensor
classes fill the protected m_filters directly in their constructors, and
ChPhysCameraSensor puts a cuRAND-owning noise filter there. Every sensor passes
through AddSensor, so that is where the assignment cannot be bypassed.

GetRandomSeed() is deleted rather than deprecated, so a missed or future call
site is a compile error instead of a silent correlation. init_cuda_rng and its
kernel are widened to 64-bit to match curand_init and to carry the whole key.
The fixed-seed state is now mutex-guarded and read as a pair, so a concurrent
clear cannot be observed as "fixed, value zero". ChSensorManager is no longer
copyable, since it owns an identity slot its destructor releases.

Unchanged on purpose: sensor names are never generated or used as a key;
ChFilterPhysCameraNoise keeps its caller-supplied m_FPN_seed for the
fixed-pattern buffer and routes only shot noise through the new helper; with no
fixed seed every buffer still reads the clock afresh.

Tests: utest_SEN_rng_streams adds 22 cases needing no GPU, covering injectivity
over 10k ordinals by 20 purposes, all four fields varying together, out-of-range
rejection, duplicate same-purpose filters, filters added without PushFilter,
coexisting managers, reproducibility across rebuilds, slot reuse, the
unseeded path, a topology fuzzer over 40 randomized scenes, and a birthday-bound
check over 90k derived seeds. utest_SEN_camera_convergence adds render-level
cases: two cameras must differ under one fixed seed with and without noise
filters, the pair must stay reproducible across rebuilds, two physical cameras
must get independent shot-noise streams, and a buffer-level check that a 640x360
buffer is no longer a prefix of a 1280x720 one. That last one predicts its own
threshold, 1/(2s*sqrt(pi)) = 2.2% byte agreement for independent streams, and
measures 2.1752%, against 100% for a prefix.

The render-level cases fail against the pre-fix code with mean |diff| 0, two
cameras producing byte-identical frames, and pass after.

Two diagnostics in the HIP probe added by a15a755 could send a reader to the
wrong place.

The success message printed CHRONO_ROCM_ROOT, which records where ROCm was when
Chrono was built. find_package is free to resolve a different installation from
the consumer's environment, so with a stale or overridden CHRONO_ROCM_ROOT the

was not and when it resolved but exported no hip::host target. The second case
means an incomplete ROCm installation, not a search-path problem, and telling
someone to set CHRONO_ROCM_ROOT there sends them to fix something that was never
wrong. The two cases now get separate messages.

resolve exactly as before in every case.

directory; a stand-in hip package exporting no hip::host produces the
incomplete-installation message and leaves CHRONO_HIP_FOUND false; an

Sensor: use OptiX-IR instead of PTX for runtime shader compilation
…
eaf2723
```
On Blackwell / RTX 50-series GPUs (sm_120) the driver's OptiX PTX front end aborts
inside optixModuleCreate, so every Chrono::Sensor program that compiles shaders at
run time dies on startup. Feeding OptiX an OptiX-IR module instead compiles cleanly.

Measured on an RTX 5090, driver 610.43.02, CUDA 12.8, in one worktree with only this
file changed between the two runs:

  without this change   utest_SEN_interface and utest_SEN_optixengine abort, exit 134
  with this change      both pass, and the full sensor suite is 11/11

Before the change five of the eleven sensor unit tests abort, so the module's own
test suite cannot run on this hardware at all.

NVRTC gained --optix-ir and nvrtcGetOptiXIR in CUDA 12.0. Chrono's documented
requirement is newer than CUDA 12.3, but the sensor module's find_package(CUDAToolkit
REQUIRED) carries no version argument, so nothing enforces that. The path is therefore
guarded on CUDA_VERSION >= 12000 and falls back to PTX below it. The fallback is
byte-for-byte the behaviour every build had before this change, so nothing regresses
on an older toolkit; such a build simply does not gain Blackwell support, which it
could not have had anyway.

OptiX needs no companion check. OptiX-IR input landed in OptiX 7.5, and Chrono already
calls optixModuleCreate rather than the older optixModuleCreateFromPTX, so it requires
7.7 or newer regardless. optixModuleCreate detects the buffer format itself and is
given an explicit size, so the call is identical for either input. That explicit size
also matters because OptiX-IR is binary and may contain embedded NUL bytes, which the
std::string holding it tolerates only because nothing downstream relies on a
terminator.

```
…projectchrono#792)

Three coupled defects, plus a runtime check on the invariant the first fix establishes. They are
fixed together because correcting the guard of item 2 is what lets markers reach the hashing code
along x and y, so fixing it alone would widen items 1 and 3 from one axis to three.

1. Out-of-bounds device write. calcGridHash adjusted an out-of-range bin index by a SINGLE grid
period, so a marker more than one period outside a periodic axis kept an out-of-range index and the
returned hash exceeded numCells. findCellStartEndD uses that hash to index arrays sized numCells, so
the write went out of bounds, silently: no fault, no diagnostic, exit 0. An in-kernel diagnostic
counted 165 to 375 out-of-range hashes per configuration for a body outside a 0.1 m periodic domain.
The reduction is now total: periodic axes wrap, non-periodic axes clamp to the edge bin, and within
one period of the domain the result is unchanged.

2. Spurious termination. In calcHashD, "p.x < c.x || p.y < c.y || p.z < c.z && IsFluidParticle(...)"
applied the rigid-body exemption to the z comparison alone, since && binds tighter than ||, so a
body whose BCE markers left the domain along x or y terminated the run. That defeats the intent of
a191fe7, "Fix that allows rigid bodies to be initialized and travel across computational domain
boundaries". Both checks are now parenthesized.

3. Phantom forces, and markers that should interact but do not. Modify_Local_PosB is the whole body
of Distance, so it is the distance used by 30 call sites. It applied the minimum-image shift on every
axis without consulting x_periodic, y_periodic or z_periodic, and applied it at most ONCE. On a
NON-periodic axis that fabricates an interaction between markers a box length apart, which item 1's
reduction makes reachable by placing an outside marker in the edge bin. On a PERIODIC axis a marker
more than one period out was binned into its correct image cell yet measured a whole box away, so it
silently failed to interact with fluid it was sitting next to; rigid-body markers reach that state
because ApplyPeriodicBoundary*_D deliberately does not wrap them. The shift now consults the flags
and is total, so it agrees with the bin reduction of item 1.

This also repairs utest_FSI-SPH_Poiseuille_flow, which fails on ROCm/HIP in the default single
precision before it: 0 of 3 checks at a final density error of 2.27234e-04, against 3 of 3 and
8.42285e-06 after. It passes on CUDA and in double precision both before and after, so the
manifestation is specific to HIP in single precision; why has NOT been established.

calcHashD now also raises the existing error flag if a hash it computed falls outside the grid. The
reduction makes that impossible by construction, so it should never fire; it is there because the
failure it guards against is otherwise silent.

Cost, measured because this touches the module's hottest device function, and it cuts both ways.
Where the division never executes, on a 106k-particle non-periodic settling case, this is at worst
neutral against unpatched and 2.5% faster than the single-period variant it supersedes. Where it does
execute, on the fully periodic Poiseuille channel, it is slower: per unit of simulated time 2.6%
slower than that variant and 3.9% slower than unpatched, with the two populations disjoint in all 49
pairs in both comparisons. Both figures come from 7 interleaved repeats per side. Normalizing by
simulated time is necessary on that rung because unpatched does not finish the regression, and it
carries the caveat that the unpatched solution is diverging while the other two are not. A fully
periodic domain is the worst case for this change, since all three axes then take the division path.

New unit test utest_FSI-SPH_domain_guard, five cases, four of which fail on unfixed code: the
rigid-body exemption; that fluid outside is still reported, so the exemption cannot be mistaken for
removing the guard; periodic equivalence of a body one and ten periods out; that a non-periodic body
beyond kernel support leaves the fluid identical to a run with no body; and mixed periodicity, one
periodic axis and two non-periodic ones at once, which is the common production case and which
neither uniform case covers. Item 1 has no black-box test, which is measured rather than assumed:
with the reduction left un-total, and the diagnostic confirming hundreds of out-of-range hashes, the
periodic case still passes at zero deviation, because the out-of-bounds writes do not perturb
observable output. Its evidence is the diagnostic and the runtime check.

The out-of-line helper's noinline attribute is spelled per compiler behind a macro, because this
device header is also compiled by the host compiler (ChFsiFluidSystemSPH.cpp includes it) and every
single spelling is wrong somewhere: bare __noinline__ does not compile in a host translation unit,
__attribute__((noinline)) without inline does not link, and MSVC rejects GNU attribute syntax.

Validated on MI350X (gfx950, ROCm 7.2, Release) in both precisions and on CUDA in single precision
(RTX 5090, nvcc 12.9, host g++ 13.3), alongside the module's existing unit tests and a 106k-particle
settling regression, and in both cases with the new test shown to abort against an unpatched library
built in the same worktree. Not validated, and neither is silent: no Windows build of Chrono was made, and
CUDA in double precision cannot currently be run at all, for reasons that predate this change.

Sensor: document the reproducibility contract for stochastic sensors
…
e75b502
```
SetRandomSeed was documented only in the header. Two of its properties are surprising enough that a
user relying on reproducibility should meet them in the manual rather than discover them.

Registration order matters: a sensor's random streams derive from its AddSensor ordinal, so adding,
removing or reordering sensors changes which numbers the OTHER sensors draw under the same fixed
seed. Anyone comparing two runs needs to build the scene identically in both.

The fixed value is a base seed, not the seed handed to cuRAND. Each buffer derives its own from the
base plus the sensor, filter and purpose, so two cameras never draw the same sequence. That is the
property sensor fusion depends on, and it is the opposite of what the API did before.

different light distances so the falloff run has a real gradient.

material handling.
