Volumetric rendering or mesh generation for a semi-open world game?
Question
Hello fellow cube enthousiast.
I have a project i am planning out which would attempt to utilize only voxels for the art style and perhaps some simulations. Ideally all voxels should be stuck to the voxel grid (so no sub-voxel animations and rotations).
I plan to write a custom engine for it using wgpu and rust considering most engines aren't designed with voxels in mind.
I have two approaches I've got in mind:
Use the usual triangle meshes and use a shader to stick all vertices to its nearest point in the grid.
Utilize a compute shader with a texture3d buffer and draw the voxels to the frame using a similar technique to raymarching, then update the texture buffer for each change.
I tried looking into it more but i can't seem to find any literature comparing the two methods. So I was wondering what you guys would consider to be the most optimal approach?

For an open world game, you’re generally going to find the more established tech (tri meshes) to be less constraining, faster to get up and running, and have waaaaaayyyy fewer issues down the road. Volumetric with raw 3D textures otoh is going to be way too VRAM heavy for a large open area, whereas alternative data structures will require lots of effort and reinventing the wheel, as it were.
Iow, only do volumetric if you specifically require it for your concept and have the resources to feasibly implement it, or have some goal more important than “shipping a finished product in a reasonable timeframe.”

There's not one, two or even three methods of drawing axis aligned cubical voxels.
You've got the following categories, though usually things are mixed around. Note that when I say "complicated" that doesn't necsiarly mean "slow" it just means hard to program, or maybe you won't find the most satisfactory solution.
CPU mesh generation methods
These are the slowest most memory intensive voxel techniques. They also aren't even the easiest to do ("greedy meshing" is a lot more complicated than some of the other techniques out there) for example, you have to re-mesh every update, and that wastes a lot of CPU time.
Mesh generation techniques
Instead of feeding voxel mesh data from the CPU, you just generate the primitives instead, which only needs the actual voxel data itself. This is typically called the "Primitive Generation Pattern", which is used for more than just voxels, any kind of simple geometric primitive that can be homogenously generated in a vertex shader/mesh shader, which can include quads, and even vertex circles.
Often combined with other methods to get the compressive effects, like what greedy meshing does to reducing vertices, though greedy meshing often ends up loosing out on memory even with it's supposed compressive effects.
Ray intersection techniques
intersect using rays but not necessarily raytracing ie, usually using DDA/grid marching. Sometimes use raytracing as well, though AFAIK, I've never seen raymarching used for this, the performance is not really better than raytracing or grid marching.
Compression render techniques:
Octree methods: the slowest, most memory intensive of these techniques, voxels are not really "sparse" (though voxelized mesh data is), and not really "empty-space-sparse", since empty chunks can just... not exist instead of taking up memory at all. Octrees may exist at a higher level sometimes, usually above chunk level.
modified SVO methods like DAG methods, harder to edit, slower to traverse, way harder to deal with color on, especially if you have to "sparsify" (ie try to take the surface only) when ever updates take place (not necessary to do this though for DAG, is basically required for raw SVO). Though can have excellent memory characteristics for geometry, since most voxel geometry is a "filled surface" geometry.
RLE/other compression methods. Very simple, very fast, compression works well, but poor ability to LOD, also will have to modify the algorithm to remove hidden blocks (blocks that are obscured by other blocks) in order to get the most out of it. Not straight forward to edit, however, because it's so easy/simple/fast to produce an RLE, one can simply re-generate the RLE per chunk that is edited.
AABB decomposition. Easy to render, not necessarily as easy to generate.
The biggest issue with Voxel data is memory, so often you might have something that may be less efficient computationally, but because you can actually fit all the voxels in, it works better than something "more efficient", ie you can actually render all your voxels.
I see a lot of people who don't know what they are doing stick to CPU mesh generation methods. Maybe since you know what WGPU even is you wouldn't feel the need to go down that route? But you also suggested using a 3D texture, I would suggest you learn what a shader storage buffer is, don't use textures where they won't help, plus there's a max 3D texture size. You'll see old code and code that must run on stuff like WebGL2 use 3D textures instead of SSBOs because they don't have access to SSBOs. Web GPU does, which WGPU targets.
I've recently seen someone who used primitive generation per chunk, but the fragment shader actually grid marched https://www.reddit.com/r/VoxelGameDev/comments/x1oep5/optimizing_my_voxel_rendering_engine_and_online/ Note that this user has chosen to limit themselves to what is possible in Webgl2 for maximum reasonable compatibility in the browser, so they use textures for what could be SSBOs. They still get to use depth testing here to accelerate things (which the explain in either their posts or video) because they will only increase depth in the fragment shader, ie with conservative depth https://www.khronos.org/opengl/wiki/Fragment_Shader#Conservative_Depth
```
layout (depth_<condition>) out float gl_FragDepth;
```
There are also some interesting choices to be made here with respect to forward and deferred rendering, but the core rendering process will be the same.
Other people are using DAG methods here with great success. It gets a big hairy to efficiently use it though (and actually, anytime you have actual chunks) when you don't have access to GPU global data pointers with out type and descriptor restrictions, ie through BufferDeviceAddress in vulkan, or just straight up using CUDA/OpenCL. Virtual memory and memory pools really only exist in CUDA right now, so if you have to emulate that, you really can't in WGSL, as I don't think physical addresses even exist in it.

Keep in mind, what your goal will be. If you plan a game which is CPU intensive, your bottleneck will be the CPU, is it graphically intensive than the GPU will be your bottleneck, etc. Ideally you balance your workload over the available ressources.
Is your world (terrain) generally static than (complex) pre-meshing it would be the better approach, is your world highly dynamic, it may fit better on the GPU side. How much other geometry or effects are you going to use, how much GPU will that use up etc.
So in general, there is no "best" approach to do it - there is only the best fitting approach for a distinct goal and each of it comes with its pros & cons which may or may not be relevant for the game you have in mind.
Often it's reasonable to think about a hybrid approach, like many games nowadays do. For example having regular mesh terrain and only subsections of it are actual voxel-data etc
