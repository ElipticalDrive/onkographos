The further I dig in, the more I think it might be working mostly as expected, but it's just not clear the way it's expected to work.
The add_field_table call is supposed to receive an individual TransferFunction object, of which the ColorTransferFunction actually has four (.red, .green, .blue and .alpha). So I believe the thing we're supposed to be doing is more akin to:
```
mv.add_field_table(tf_temp.red, field_id=0, weight_field_id=-1, weight_table_id=-1)  # temperature → RGB
mv.add_field_table(tf_temp.green, field_id=0, weight_field_id=-1, weight_table_id=-1)  # temperature → RGB
mv.add_field_table(tf_temp.blue, field_id=0, weight_field_id=-1, weight_table_id=-1)  # temperature → RGB
mv.add_field_table(tf_density.red, field_id=1, weight_field_id=-1, weight_table_id=-1)   # density → Alpha

# Link channels 
mv.link_channels(table_id = 0, channels = [0])
mv.link_channels(table_id = 1, channels = [1])
mv.link_channels(table_id = 2, channels = [2])
mv.link_channels(table_id = 3, channels = [3, 4, 5])       
```
But that produces an empty image for me. (I think the weight field might also need to be set in this case.) The way the code works is described at https://yt-project.github.io/yt-4.0-paper/ under "Transfer Function Sampler" but that speaks specifically to the way it works for a traditional ColorTransferFunction. The PlanckTransferFunction may be a place to look, which is next up on my list. You may have success with it, but it definitely demonstrates the use of weighting and whatnot.
So I think we're actually not that far off, but getting the exact items right is tricky. (I'm also wondering if I missed something with whether temperature should be logged or not, and if that's killing my images.)

Just for clarity: I think the original issue here as @neutrinoceros posed is a little different from what we've been discussing.
For single-field rendering, the color-mapping works just fine, and it would be pretty easy to, for example expose a control to set or modify the colormap used for a default colormap (more below).
The question of multi-variate TF rendering is separate: I'm pretty sure the reason the bug report above shows an inability to change the colormap is simply that the MV TF is just not being used (they are setting the TF with source.tfh.tf = mvtf and not calling source.set_transfer_function, because source.set_transfer_function will error with a MV TF right now. If you don't call that set_transfer_function, all you get is the default TF). So fixing support for MV TF is a separate problem, I think we should open a new issue (I'll do that now).
Exposing colormap for single-field rendering
On the topic of @neutrinoceros 's original issue, when you call create_scene, a default transfer function gets built, ultimately from:
yt/yt/visualization/volume_rendering/transfer_function_helper.py
Lines 117 to 127
in
f50dfe4
def setup_default(self):
"""Setup a default colormap
Creates a ColorTransferFunction including 10 gaussian layers whose
colors sample the 'nipy_spectral' colormap. Also attempts to scale the
transfer function to produce a natural contrast ratio.
"""
self.tf.add_layers(10, colormap="nipy_spectral")
factor = self.tf.funcs[-1].y.size / self.tf.funcs[-1].y.sum()
self.tf.funcs[-1].y *= 2 * factor
It'd be feasible to add a colormap kwarg to create_scene to control the colormap used there, would need to add the kwarg to several different functions but I don't think that'd be hard.
A source.set_cmap would work if there was some careful validation: if you construct a transfer function manually, source.set_cmap would only make sense where you have a transfer function that maps to a colormap: e.g., it would not make sense to apply a colormap if you've added gaussians manually or if you've added a TF that uses separate colormaps for different ranges. So I think a set_cmap would only make sense if the user has not made any manual modifications to the transfer function, and that seems annoying/difficult to track with the current design of the transfer function handler.
Rather than a source.set_cmap, I think it'd be better to have a source.reset_transfer_function(cmap: str | None = None) so that it's very clear that it's over-riding any existing transfer functions.
