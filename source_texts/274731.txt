Thanks for the reports, and sorry for the slow reply. Neither linked file can be downloaded any more (the EBRAINS bucket now needs a login, and Dryad returns 403), so we tested with synthetic NIfTI images in which each frame has a known value:
Image
Result on the current code
512×512×1100 (more than 1000 slices)
Loads, and the values are correct in all slices tested
256³ × 129 frames, just over 2³¹ voxels (2.2 GB)
Loads, and the values are correct in all frames tested
256³ × 257 frames, over 2³² voxels (4.3 GB)
Refused by the memory check (see below)
So the crash with more than 1000 slices seems to be fixed in the current code. We did find two problems that affect very large images, and plan to fix them in 4.6.2:
4D images with more than 2³² voxels in total. ITK-SNAP finds each time point in the 4D image with a 32-bit offset, which wraps around once a time point starts more than 2³² voxels into the image. Those time points then show the wrong data. This may be related to what you saw with 27 vs. 26 time points.
The memory check on macOS. Before loading, ITK-SNAP refuses an image larger than the free memory it measures. On macOS that measure counts only free and inactive memory, so it can refuse images that would fit.
We will test the fix with a 4D image over 2³² voxels on a machine with enough memory.
