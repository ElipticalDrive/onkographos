Four things that were each measurable rather than speculative.
Send the splats compressed
Locally generated worlds shipped as uncompressed PLY -- 56 bytes per splat, every field a float32 -- while Marble worlds arrived as .spz. Same viewer, two very different download sizes.
Spark already ships the encoder and SplatMesh already reads either format, so this changes byte count and nothing else. Measured on this project's own worlds:

full_res.ply is kept: it is the lossless original and /api/extract-prop cuts props out of it at runtime. npm run assets:spz backfills existing worlds; pruning the superseded detail-level PLYs is a separate opt-in flag.
Equivalence was checked by pushing both formats through Spark's own setPackedSplat -- the four uint32 that actually reach the GPU. Both pipelines come back within 1/255 on every rgb channel and every alpha, positions within 1.22e-4 units (0.12 mm at metric scale), spherical harmonics preserved at degree 3.
An earlier commit in this branch reported a 4.7% colour deviation on the Splatfacto path. That was wrong and is corrected here: I had read word 3 of the packed buffer as the rgba, and it is not — rgba is word 0. The write-up in PROJECT_REPORT.md keeps the mistake rather than quietly replacing it, because "find out which word holds what before diffing a packed buffer" is the reusable part.
Let the backend hand its VRAM back
backend/README.md claimed each inference temporarily unloaded model weights. It never did -- clear_vram() cannot touch weights a module global still references, and all eight models here were lazy-loaded globals that were never cleared. Harmless in-process; not harmless across processes, since ns-train runs as its own subprocess and cannot see what this one holds, so generating a world and then reconstructing a video OOMs on a 16 GB card.
POST /api/unload now drops them, and reconstruction calls it inside GPU_JOB_LOCK before spawning. Unloading SHARP returns 2816 MB on the 5060 Ti. The registry's real risk is a ninth model being added and forgotten, so the test parses server.py with ast and asserts coverage -- no torch or CUDA needed to run it.
Run the checks that were only ever run by hand
npm run check and nine pytest files already existed with nothing running them. The backend job installs what the CPU suites import rather than requirements.txt, which would pull gigabytes of wheels for models no runner can execute. The three suites left out say why at the point they are skipped.
It earned its keep on the first run, by failing: python-multipart was an undeclared dependency of every UploadFile/Form endpoint, present only transitively, and FastAPI raises for it at import time. It is now in requirements.txt.
Pin the conventions that keep going subtly wrong
worldTransform, walkableMap, spawn, placements and dropTargets had no tests between them, and they hold every coordinate convention this project has gotten wrong before -- failures that do not crash, they just put the collider somewhere the splat is not.
Frontend 62 -> 111 tests; the backend CPU set 86 -> 89.

```
backend/README.md claimed each inference "temporarily unloads model
weights". It never did. clear_vram() returns the allocator's cached
blocks, but it cannot touch weights a module global still references,
and all eight models here are lazy-loaded globals that were never
cleared.

Harmless inside one process, since run_heavy already serialises the
work. Not harmless across processes: ns-train runs as its own
subprocess and cannot see the gigabytes this one is holding, so
generating a world and then reconstructing a video OOMs on a 16 GB card.

MODEL_GLOBALS registers the eight, unload_models() drops them, and
POST /api/unload queues behind any inference in flight. Reconstruction
reaches it through a hook rather than importing server.py, which would
cycle, and calls it inside GPU_JOB_LOCK -- the one moment nothing is
mid-inference, and the reason it cannot go through run_heavy on a
non-reentrant lock. Unloading SHARP returns 2816 MB on the 5060 Ti.

The risk is not that unloading breaks, it is that a ninth model gets
added and never registered. So the test parses server.py with ast,
finds every global a function declares and assigns, and asserts the
registry covers them. Reading the source rather than importing it keeps
that test runnable without torch or CUDA.
```

```
worldTransform, walkableMap, spawn, placements and dropTargets had no
tests, and between them they hold every coordinate convention this
project has gotten wrong before. Those failures do not crash: the
collider ends up somewhere the splat is not, and clicking to free an
object cuts geometry from the wrong place and reports success.

So the tests fix the conventions, not the arithmetic. An explicit
rotationX has to beat flipY, including when it is zero. groundPlaneOffset
is already in metres, so the metric scale must not multiply it again. A
spawn point is [x, z] on the floor plane, not [x, y] -- the same two
numbers either way, which is why swapping them goes unnoticed. And
walkableMap's timeout has to join the caller's signal rather than be
replaced by it, which is how a wedged backend once left a generation
sitting at 86% forever.
```

```
Two things CI and a second look each caught.

The Splatfacto colour deviation reported in the last commit does not
exist. Diffing the packed splat buffers, I read word 3 as the rgba and
built a conclusion on it; word 3 is not the colour. Hold every field
fixed and vary one and word 3 never moves -- rgba is word 0, where
cc998066 is exactly opacity 0.8, b 0.6, g 0.5, r 0.4. Read the right
word and both pipelines agree: rgb and alpha within 1/255 on every
channel of every splat, positions within 1.22e-4 units.

The tell was there and I missed it. Re-encoding with maxSh: 0 threw the
harmonics away entirely and the "deviation" came back byte-identical,
which should have said the measurement was not looking at colour.

Separately, CI found an undeclared dependency on its first run:
python-multipart. Every UploadFile/Form endpoint needs it, it was only
ever present transitively, and FastAPI raises at import time -- so a
fresh environment loses the whole app, not one route. Now in
requirements.txt as well as the workflow.
```

Stop a refresh from throwing away a generation
…
9a04f6f
```
POST /api/generate owned the work it started: progress streamed back down
that connection and request.signal aborting tore the pipeline down and
deleted the staged world. So a reload, a closed laptop or a flaky tunnel
discarded a Marble generation eight minutes in -- one that had already
been paid for.

The request now creates a job, starts the pipeline detached from itself
and returns an id. Progress goes to a file the browser polls, the same
shape the video path has always had, on the Node side because the image
pipeline is what holds the Marble key. The key stays in the closure; the
job file records only which backend ran, and a test reads the raw file
to keep it that way.

The first design kept ownership in a module-level Map and inferred a
crash from its absence. Unit tests passed; the app disagreed within a
minute. Next bundles each route handler separately, so the Map in
/api/generate is not the Map in /api/generate/jobs/[id]: the list route
declared a demonstrably live job interrupted, and DELETE could not find
the controller it needed, marking a job cancelled while the pipeline ran
on. Both now go through the file. A 2 s heartbeat proves liveness -- 60 s
to call it dead, because a busy event loop is not a corpse -- and the
same tick re-reads its own status, so a cancel written by any route
reaches the pipeline.

Starting a second generation answers 409 with the running job's id
rather than a conflict, because the caller almost always wants to watch
that one: it is the same path the modal uses to reattach after a reload.

Verified against a stub backend that accepts and never answers, so a job
stays in flight: the work outlives the connection, stays visible as
running from another route, refuses a second start, and cancels within
six seconds with the staged world removed.
```
