Summary
C_VoxelPool cached two derived cull structures behind two evictors. Both derive from the same three inputs (allocated prefix, per-voxel alpha, per-voxel global position), every producer called only the world-AABB one, and markChunkBoundsDirty() had zero callers tree-wide. On a cardinal camera — the default, residualYaw_ == 0 — an in-place position or alpha rewrite froze the iso bounds at the last alloc/dealloc, and the resulting geometry drop was self-latching.
Collapsed the pair into one range-taking evictor, markCullBoundsDirty(start, count), tracked per 256-slot chunk with independent pending bits for the two consumers (they run on different frames; neither may consume the other's work).
Completed the trigger set for inputs the position-range channel structurally cannot carry: the active-mask mutators, the GRID inverse arm's deactivated tail, and edits made while C_VoxelSetNew::visible_ is false (visibility gates the pool's active-mask write, not the authored alpha the bounds read).
queuePositionRange now invalidates before its saturation early-return, and UPDATE_VOXEL_SET_CHILDREN stages a GPU-slotted set's real range with a separate upload flag instead of zeroing start/count — which had silently dropped invalidation for exactly the sets that move most.
The detached re-voxelize branch consumes the pending set it satisfies. rebuildChunkBounds' m_staticReVoxelizeBound branch re-derives every chunk and returns early; it was returning without consuming the cardinal bits allocateVoxels arms, which made isRangeVisible admit every detached range unconditionally and forever. See "Opus recheck fix" below.
demos/perf_grid: --auto-profile now reports means, not one frame. Every number it emitted was an n=1 sample (IRTime::renderFrameTimeMs() is a single inter-frame delta; CpuFrameHistogram keeps only the last frame), which is why AC4's third bound could not be settled on the first pass. See "AC4, re-measured" below.

Opus recheck fix — the static-bound branch was not consuming its pending set
The opus recheck was right, and the defect was real: this PR had disabled UPDATE-side culling for detached re-voxelize pools, a pool mode master culled correctly.
rebuildChunkBounds has three branches. The first, taken when m_staticReVoxelizeBound is set (#1556), assigns every chunk the same iso bound projected from a conservative origin-centered world-AABB, then returns. That bound reads neither position nor alpha, so after it runs no chunk owes a cardinal recompute — but the branch never said so. allocateVoxels arms kCullPendingCardinal for the allocated range, REBUILD_DETACHED_VOXELS' per-tick active-mask writes re-arm it, and nothing on that early-return path clears it. isRangeVisible's Decision-6 rule ("pending ⇒ admit conservatively") therefore answered TRUE for every detached chunk on every frame, permanently.
The fix is one line plus its rationale: the branch consumes m_pendingCardinalChunks before returning. Only the cardinal bit — ensureChunkWorldBounds is the world bit's sole consumer and this branch never runs it, so the world cache keeps owing its work, preserving the independent-consumer property the rest of the PR establishes.

AC4, re-measured (addresses the first review's one needs-fix)
The review was right that the first pass did not establish AC4's third bound. The cause was not sample count — it was that the tool emitted no mean at all. --auto-profile logged IRTime::renderFrameTimeMs(), a single inter-frame delta, and CpuFrameHistogram only ever retains the last frame. So "n=6 runs" was six one-frame samples drawn from a strongly bimodal population (update ticks on a subset of render frames), and adding runs adds one such sample each. Measured here: one run's trailing frame read 7.904 ms where that same run's 225-frame mean was 9.666 ms — an 18 % error from a single sample.
Fix to the instrument: demos/perf_grid now folds every post-warmup frame into a running mean + stddev and logs Auto-profile mean — frame:… sd:… n:… plus a per-scope mean line, alongside the existing single-frame lines (left intact). Warmup is the first quarter of the window. The commit is demo-local — it touches no engine code, and it was cherry-picked unchanged onto origin/master to build the baseline arm, so both sides are measured by identical instrumentation.
Fix to the schedule, and it mattered. A block-sequential A/B (all fixed runs, then all baseline runs) reported +10.6 % / +11.6 % — i.e. a fail. An interleaved paired schedule on the same binaries reports +4.97 % / +3.86 %. Between-block drift on this host is large enough to move the answer across the bound, so the sequential result is discarded as confounded, not averaged in. Both binaries live in the same directory as the staged assets and alternate order each round; each round is a matched pair, analysed with a paired t-interval so between-round drift cancels. Where the frame cost actually goes — read this, it is the non-obvious part. frame = input + update + render holds exactly in the profile, and voxelStage1 is nested inside render. render is net flat (static +0.001 ms, CI straddling zero; moving −0.110 ms), so the +0.36 ms cull rebuild is absorbed within the render stage — correct bounds mark fewer chunks visible, and the downstream saving offsets the rebuild. The frame-level rise is therefore carried almost entirely by update (+0.44 / +0.46 ms), which is the Decision 6 cost: isRangeVisible is now conservative on pending ranges, so the UPDATE movers stop skipping sets they used to skip incorrectly. AC4's "so moving cost into UPDATE cannot pass" clause is exactly the right thing to check here, and it is satisfied — the UPDATE rise is counted in the total, and the total passes on both arms with room.
Cross-check against an instrument I did not write. save_files/profile_report.txt already emits Frame time: avg=… p50=… p95=… p99=… over the whole run — an averaged CPU frame time that existed before this PR. On the final baseline run it reads avg=9.31 ms (300 frames, warmup included, max=41.65 ms cold first frame) where the new accumulator read 9.244 ms (225 frames, warmup excluded). The two agree to within the warmup contamination that explains the gap, which is the independent corroboration that the accumulator is summing what it claims to.
Stating the obvious follow-up, since a reviewer will ask it: if profile_report.txt already had a mean, why add code? Three reasons, and the first is the one that actually mattered here — (1) the report's avg includes the cold prefix, so it is not the steady-state figure a gate wants; (2) it has no row for voxelStage1, which is a profile scope nested inside the render pipeline, not a system row in the per-system table, and AC4 gates on exactly that name; (3) the n=1 Auto-profile stats line was printed in the run's own stdout with no mean beside it, so the trap was placed exactly where the author reads. Putting the mean next to the single-frame line removes the trap at its source rather than relying on the author knowing to go read a different file. The honest version of the first pass's failure is not "the tool had no mean anywhere" — it is "the mean was in a file the workflow never pointed at, and the number in front of the author was n=1".

Perf notes for the reviewer
Range-scoping buys nothing in this benchmark, by design of the benchmark. IRPerfGrid --mode voxel_set --grid-size 64 fills the whole 262 144-slot pool and UPDATE_VOXEL_SET_CHILDREN rewrites every visible set's positions every tick, so all 1024 chunks are notified every update tick — the plan predicted exactly this. The range-scoping's benefit is proven by AC3's work counts, not by this scene; what this scene measures is the chunk-local reduction, which is what carries the gate (+0.36 ms measured vs the refuted whole-pool +1.331 ms).
The per-frame samples are bimodal, and that is now handled in the instrument rather than in prose. update ticks on only a subset of render frames, so frames split into rebuild frames and cache-hit frames. The first pass reported an all-frames figure and an update-tick-conditioned figure side by side because a single sample could not span both modes. With --auto-profile now averaging every post-warmup frame, the reported mean is the correctly weighted mixture and the conditioning is no longer needed — the stddev the instrument prints is the spread, not an artifact.
The third bound is now resolved, not flagged. Both arms pass with the whole 95 % CI below 10 % (+4.97 % static, +3.86 % moving). Two things had to change to get there and both are in this PR's diff or its method: the instrument had to emit a mean at all, and the A/B had to be interleaved rather than block-sequential. The earlier "+10.5 %, I am not claiming this passes" was the honest call on the evidence available then; it is superseded by evidence, not by re-framing.
Notes for the reviewer
isRangeVisible is now conservative on pending ranges (the plan's Decision 6). It feeds the UPDATE movers, which run before the render pipeline re-derives bounds; answering from a chunk that already owes a recompute is what latched an edited set off-screen. It cannot feed back: an off-screen set is skipped, so it never writes, so it never becomes pending. Cost is bounded at one extra tick for a set that just changed, and is now quantified: it is the +0.44 / +0.46 ms update rise in the AC4 table, the dominant term in the frame-level delta. The explicit non-claim from Decision 6 still holds — a transform change that an already-stale UPDATE cull rejects before any pool write is a separate defect, not widened into here.
REBUILD_DETACHED_VOXELS is exempt as a producer; its branch is not exempt as a consumer. It writes pool.getColors(), so a colour-writer sweep finds it, but it returns on the m_staticReVoxelizeBound branch before the cached path (render: detached re-voxelize — GPU scatter fill (P2) #1556) — so adding a producer-side notification there would evict a cache that path never reads. The first draft of this PR stopped at that half-truth and left the branch returning without consuming the bits allocateVoxels arms; the opus recheck caught it. Corrected in the code, in voxel/CLAUDE.md, and covered by three regressions — see "Opus recheck fix" above.
Producer coverage was swept, not assumed. fleet-rules-sweep --pattern 'getPositionGlobals\(\)' over 950 files: every non-const production accessor is in the two systems this PR wires; the render-side and light-grid uses are const reads.
