To me, after much experimentation, it feels like on fast camera moves, the sorting algorithm might get busy with outdated camera positions and therefore has no time to prepare a camera position that would be much closer to the current position of the camera. On extreme fast moves this gets more pronounced.
In-flight sort operations aren't cancelled, but any queued sort operation is updated to reflect the most recent state. So at most one stale camera position is "blocking" the sorting. For extreme fast camera movements there will be a large delta between the camera pose the current splat ordering was computed for and the new camera pose.
Is there no way to implement an algorithm that would detect fast camera moves and start droping outdated sorts or favouring a sort that is closer to the current camera position?
As mentioned above, there is at most one scheduled sort operation that is being updated to the latest state, which can be seen as form of "dropping" sorts. Cancelling the in-flight sort operation isn't supported. There are effectively two atomic steps in the sorting process (on the GPU and the CPU), so cancelling the in-flight sort tends to not be beneficial. It will still consume these resources and still delay the next sort operation. And with the sort result being dropped, rendering will continue to happen with even staler data.
That said, if the cancellation can happen in between the two, it might help improve the situation. So this might be worth trying. Alternatively two sort operations could theoretically be in-flight if they were staggered, which could also help bring down latency.
Could you give advice on how to handle updates better from outside Spark (when autoUpdate is disabled)?
Spark has always been quite opinionated about the render loop and how it drives the updates and sort operations. I don't believe there are any examples or documentation that really goes into detail how to manually update things properly. @asundqui might be able to go into more detail, as v2 also introduced onDirty callbacks to close a gap in manually updating.
That said, you'd only indirectly influence the sorting logic this way, so I doubt it'll give you the control you're looking for.
I would personally prefer to stick with Spark 1.x for now, until the build size is reduced back to an acceptable level (it grew from 700kB -> 5MB!), therefore I didn't test LOD yet. I don't expect this to be fixed by using LOD...as I don't think my relatively lightweight splats (below 2Mio) need LOD. But I would certainly test, if you think this had good chances of getting rid of the glitches.
The increased bundle size should see a significant reduction in the next release (see #321). It's likely still going to be bigger than Spark 0.1 simply by the fact that it contains additional features like the LoD system, paged splats and a new splat representation.
Though, I don't see a reason why the LoD system would improve the issue at hand, as it's purely bound by the sorting. In theory LoD could mean rendering at a lower splat budget, meaning less splats to sort and thus faster sorting, but that's assuming you'd not be rendering the entire model (i.e. higher LoD levels).
For testing I used a beefy old HP z820 Workstation with dual Xeon CPU, 128GB RAM, Win 10, Chrome browser and a 2080 TI 11GB VRAM GPU and I have to admit I also used a Macbook Air M1, 8GB, OSX, Chrome browser. But I truly tested, the issue is definitely not only present on the M1, and the workstation should definitely deliver enough horsepowers for this.
Not to claim that either of these devices are underpowered or the issue at hand doesn't exist, but interestingly enough both you're test devices have characteristics that make Spark's sorting slow. For sorting Spark employs both the GPU and CPU, though more out of necessity than optimization. To enable global sorting and dyno modifiers, splats are accumulated and transformed on the GPU. Since GPU sorting is infeasible with WebGL2, a readback is performed to get per-splat depth which then gets sorted in a WebWorker.
This readback tends to be expensive on tile based GPUs, like in Apple M-series devices. Whereas the CPU sorting is single-threaded and thus benefits from CPUs with high single-core performance.
I'll try and see if either staggering sorts and/or cancelling in-flight sorts for large viewpoint changes improve the situation. The ideal solution would of course be fully GPU based sorting, especially with the way Spark updates splats, but that is still a ways away.

Generally you'd render less splats on a mobile phone than you would on other device classes. This in turn means that there's less work to do for both the GPU readback and the CPU sorting. Not an exact correlation, but this tends to even out with the lower performance of the device. In other words the behaviour is mostly comparable. Though, mobile phones have their own unique quirks, as some do boast high resolutions and refresh rates relative to their performance.
Spark is designed with global sorting and dynamic effects for splats in mind. As a result the current sorting approach is unfortunately more expensive to execute on many devices. There is some work to improve the CPU part of sorting (see #327), though without a full GPU based sorting solution the GPU work + readback remains. The main criterium is the number of frames of latency before a new sort result is available. This is always going to be at least 1, as that'll be the frame that kicks off a new sort operation.
Cancelling the in-flight sort operation might improve on this latency, though I haven't had the time to experiment with it yet.

Awaiting the prepare ensures that both an update and sort have taken place, essentially turning the asynchronous process into a sequence. As you've noticed this comes at a high performance cost. Also worth pointing out that the code as posted, isn't quite correct. Ideally all rendering work happens synchronously within a rAF callback, which is now broken up by the await. What's worse is that there is no guarantee that the next rAF callback happens after the work started by prior ones has completed. This is probably why you're seeing the errors regarding sorting.
So you'd actually have to schedule a rAF once you are ready to render (i.e. prepare has finished) and once done schedule the next sequence (prepare followed by rAF).
It goes without saying that this isn't really a solution, though it is interesting to consider the possibility of deliberately missing frame(s) if the camera delta is too large to await a sort operation. The main drawback is that Spark would need full control of the render loop, as by default it reacts to the Three.js render call, at which point the main colour buffer has likely already been cleared/overwritten. It remains subjective whether one would want a lag spike over a (few) frame(s) with stale sorting, but it wouldn't hurt if this could be implemented on the user-side.

By increasing the pixel ratio, you're increase the GPU workload of rendering the frames. If this causes the framerate to drop below the refresh rate, the GPU might have little to no idle time. So it can take longer for the GPU step of the sorting process to even take place.

I also have a question regarding how to selectively antialias with Spark. I would like to combine splats with other opaque objects. These objects should get decent antialiasing….but just these objects, not the splats, ofc for performance and also visual reasons.
It's not possible to selectively apply antialiassing in WebGL, as this is a property of the framebuffer. Depending on how the opaque objects are intended to interact with the splats, there are some tricks possible (e.g. render splats to render target, blit to MSAA framebuffer and render opaque objects on top). But if you want proper depth testing and MSAA, that's sadly not possible.
Using post-processing to apply a screen-space antialiasing technique is an option, though not always ideal in terms of performance.

Hi @notthesame23 I suspect your idea of rendering at 2x the resolution and then downsampling would work and look good, but you will not get good performance from it :/. Rendering 4x the pixels will result in 4x the fragment shader invocations, there's no way to just run the fragment shader once and have it apply to 4 pixels. On the other hand, I don't think your bottleneck is the fragment shader - If you look at the source code for various web 3DGS renderers, you will see that they're all pretty similar and do very simple math operations. The bottleneck in graphics these days is usually memory bandwidth. And because of that, rendering to 4x the pixels and then downsampling it 2x will result in MUCH more memory bandwidth usage... probably at least 5x if not more. Antialiasing with transparent or skinny objects in graphics in general is a difficult problem with no simple solution.
One thing you could try however: If your non-splat objects are thin lines, you could have them render as transparent, and render it in a second transparent pass (use Three.js' "Layers" feature to do this) to render them OVER the splats. These lines can be drawn antialiased and blended into the splats, which looks nicer. However, the Z-buffer won't be able to occlude them perfectly, so it's only appropriate for UI-like elements where it's okay if depth ordering isn't perfect.
I do believe that your main problem has to do with splat sorting and the latency there. As @mrxz has pointed out, Spark does a GPU depth calculation + readback + CPU sorting because that's what WebGL2 requires, if you want to support dynamic 3DGS modifiers like Spark. On some devices the readback is especially slow! So when rotating in orbit view you will temporarily see the old sort order. I suppose it may be possible to cancel an in-flight sort if the discrepancy is too large, but I don't think this is a good general solution.
One thing we might consider however if your scene allows it: In older Spark versions we had a "float16" sort functionality. For this we read back 1/2 the data and the sorting itself takes about 1/3 of the time, which would speed up the process quite a bit. It can result in more Z-fighting between splats, but in some cases that's perfectly fine. We can try adding that back into Spark 2.0 as an option... it should result in at least 2x faster sort updates.
