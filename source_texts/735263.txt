What
PR2 of the brepjs-voxel performance & scale stack. After PR1 (BVH distance), the FWN sign pass — mesh.is_inside(p) per voxel, O(voxels·triangles) — was ~98% of voxelize_mesh end-to-end. This accelerates it to ~O(voxels·log triangles) with a Barnes-Hut / Barill-2018 hierarchical winding number that reuses the PR1 BVH (one tree, two traversals).
Each BVH node carries a first-order point-dipole expansion (area-weighted normal sum about the area-weighted centroid, aggregated bottom-up). A query approximates a node by its dipole when |p − center| > β·radius (β = 2), else recurses and evaluates the exact solid angle at leaves.

Log-scaling is visible: the sign-pass speedup grows 30→107× as N quadruples.
Correctness — sign identical to exact FWN
Zero sign mismatches vs the exact O(N) FWN oracle across every voxel of unit-cube, holey-cube (the keystone), and icosphere. The keystone (holey interior stays inside, w ≈ 0.833) routes through the fast path unchanged.
The winding number is approximate; the opening criterion — not expansion accuracy — guarantees the sign. Near-0.5 (near-surface) nodes are evaluated exactly; the dipole is used only for far nodes where w is unambiguously ~0 or ~1.
The β = 2 dipole-only margin is empirical, not a proven bound (the docstring says so). Committed adversarial guards — high-aspect slab, far disjoint emitter, single open triangle — lock it so a future β/leaf-size change can't silently erode it.

Greptile Summary
This PR accelerates the winding-number sign pass in voxelize_mesh from O(voxels·triangles) to ~O(voxels·log triangles) by layering a Barnes–Hut hierarchical approximation on top of the PR1 BVH. Per-node first-order dipole expansions are computed bottom-up at build time; a query opens a node exactly when the query point is within β·radius, otherwise uses the cheap dipole term.
bvh.rs: Adds NodeExpansion (center, dipole, radius, total_area) stored in a Vec parallel to nodes; adds winding_number_fast/is_inside_fast using a shared caller-owned stack; adds compute_expansions with a post-order bottom-up pass that is correct because build_recursive always allocates a parent's slot before recursing, guaranteeing child indices are strictly greater.
ops.rs: Replaces mesh.is_inside(p) with bvh.winding_number_fast(p, BETA, &mut stack) in the production path; adds isolated sign_field_exact/sign_field_fast helpers for benchmarking only.
benches/voxelize.rs: Adds an isolated sign_pass benchmark group and updates comments to explain that BVH construction is included in the timed region (conservative lower bound).
Confidence Score: 5/5
Safe to merge. The hierarchical winding number is mathematically correct, the post-order expansion build is guaranteed sound by the BVH allocator, and the sign-parity gate (zero mismatches across five fixture meshes plus three adversarial cases) gives strong empirical coverage.
The dipole sign convention, radius bounding, and area-weighted centroid combination are all verified correct. The one structural assumption — that inner nodes carry strictly smaller indices than their children, enabling a single reverse-iteration post-order pass — is guaranteed by build_recursive reserving the parent slot before recursing. No functional defects were found; the only flag is a P2 noting the icosphere test helper is duplicated verbatim in both bvh.rs and ops.rs and could drift silently.
No files require special attention.

Good catch on the sign_pass benchmark methodology (P2). You're right that sign_field_fast calls Bvh::build inside the timed region while the exact baseline has no setup — so the reported 29.6×/107× are a conservative lower bound on the true per-query traversal gain, since production voxelize_mesh builds the BVH once and amortizes it across both passes (and end_to_end already captures that real combined cost).
I went with your "at minimum" suggestion — a clear caveat comment on both the sign_pass and distance_pass groups noting the build is inside the timed region and the ratios understate the win — rather than hoisting the build out via a prebuilt-Bvh shim. Doing the hoist cleanly would require making mod bvh public and adding traversal-on-prebuilt-BVH shims, i.e. widening the crate's Rust surface — the exact thing flagged on PR1. Since the bias is conservative (numbers only get better with the fix) and the production path is what end_to_end measures, the transparency comment is the better trade. Fixed in the latest commit.
