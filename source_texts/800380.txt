Follows #1387 and the tinyvdb update in #1386, both merged.
Why
A signed distance field (SDF) stores, for points around an object, how far each point is from the object's surface (negative inside). Collision checks near a surface only need the distances close to it. So SDF files written by NanoVDB, OpenVDB and fVDB store only those: a thin shell of values around the surface, called a narrow band.
Tesseract can only hold an SDF as a full 3D box of values. readSignedDistanceFieldNVDB fills in the whole box around the object, and refuses anything over 256 million values. Memory therefore grows with the box, not with the surface. For a scanned part on a 1 mm grid:
Kept as stored
Filled into a box
load time
0.11 s
0.40 s
memory
149 MB
257 MB
The gap widens quickly with a finer grid or a bigger part, because the box grows with volume and the shell only with area.
This PR lets a SignedDistanceField keep one NanoVDB grid exactly as it's stored, and read it in place. Nothing is expanded into a box: not when loading, not during collision checks, not when serializing.
Reading the shell safely
The shell only holds real distances near the surface. Near its edges, a careless read makes the edge of the data look like a surface.
Cells without data. A NanoVDB grid records which cells hold values.
In a grid declared a level set (grid class LevelSet), the empty cells still mean something: a fixed "far away" value, positive outside and negative inside. They're read like any other cell.
In any other grid an empty cell holds no distance; fVDB stores 0 there, which would look like the surface. A distance is only returned where every cell it's interpolated from holds data.
The band clamp: where the shell's values stop. Beyond a certain distance, the stored values no longer grow; they only say "at least this far". The file doesn't record that distance, so the caller passes it in.
Outside the surface, a read at that limit, or anywhere the grid has no data, returns "no answer": +infinity, with a zero gradient. Collision checks then measure from where the field does answer. A test checks that a probe beyond the shell still gets its true separation.
Inside the surface, the value is returned as read: a contact at least that deep.
Bounds are exactly the cells that hold data.
Checks when loading:
NanoVDB format version 32;
not a density grid (a fog volume);
every part of the grid inside the file's bytes.
The grid is then kept once, uncompressed.
A NanoVDB file can hold several grids, and this PR doesn't guess what they mean. readSparseSignedDistanceFieldNVDB(bytes, band_clamp, scale, grid_name) reads one grid by name; the name can be left out when the file holds only one. getSignedDistanceFieldNVDBGridNames lists a file's grids. Several fields on one link combine like any other geometries.
Other changes
Interpolation. setInterpolation() picks trilinear (the default, so results don't change) or tricubic (Catmull-Rom), for grid-backed and sparse fields. Tricubic passes through the stored values and stays smooth across cell edges, so contact directions don't jump when a point crosses from one cell to the next. setGradientInterpolation() lets the direction use a different method from the distance. getDistanceAndGradient() returns both from one lookup.
URDF. <tesseract:signed_distance_field> gets optional grid and band_clamp attributes. Without them, an .nvdb file is read into a full box, as before.
Writing. writeSignedDistanceFieldNVDB writes a sparse field's grid as it's stored. readSignedDistanceFieldNVDB still reads one grid into a full box.
Breaking: serialization. The cereal archive of SignedDistanceField now records a format version (1) and the interpolation settings. A sparse field stores its grid as a standard NanoVDB file (what writeSignedDistanceFieldNVDB writes), plus the band clamp of each grid, which NanoVDB has no field for. A dense field stores its sample grid as before. Archives written before this change no longer load.
Benchmark. collision_sdf_interpolation_benchmark, a test target rather than part of the libraries, compares the interpolation methods, and sparse against dense, on analytic shapes or a given .nvdb file.
Tests
Sparse and dense fields agree, in distances and gradients.
The empty-cell rules, for level sets and for other grids.
Reads at the band clamp, inside and outside the surface.
Picking grids by name from a file with several.
NanoVDB write and read round trips. Malformed, density-grid, wrong-version and truncated files are rejected.
The interpolation methods, and using a different one for direction.
Serialization round trips. Unknown versions are rejected.
URDF grid and band_clamp: reading, writing and errors.
Bullet and FCL contacts with:
sparse fields, and sparse against dense;
scaled sparse fields;
a collision margin reaching past the shell.

A SignedDistanceField can now be built from one NanoVDB FloatGrid and its
band clamp, and kept in its stored sparse form. Queries read the voxels
around the point with PNanoVDB's cached accessor; nothing is densified, so
memory follows the surface rather than a box around it. Bullet and FCL query
it in place like any other field.

- What an inactive voxel means depends on the grid's class. In a level set
  (NanoVDB grid class LevelSet) inactive voxels and tiles hold the
  background, positive outside and negative inside, so they are read like
  active ones. In any other grid an inactive voxel holds no distance (fVDB
  writes 0, which would read as surface), so a read is answered only where
  every voxel it uses is active.
- Where the grid cannot answer, and wherever it answers at or past its band
  clamp outside the surface, the distance is +infinity with a zero gradient:
  the grid knows only that the surface is at least that far away. Collision
  checks then measure from where the field does answer, and several fields
  combine as any geometries do. A read at or past the clamp inside the
  surface is returned as read, a contact at least that deep.
- The domain is the grid's exact active voxel bounds, computed from its leaf
  value masks, and recorded in the stored grid's root box.
- At load a grid must be NanoVDB major version 32, not a fog volume, and have
  every node array inside its buffer. The grid is stored once, as its bare
  uncompressed buffer, and read in place.
- setInterpolation chooses trilinear (the default; results unchanged) or
  tricubic Catmull-Rom for grid-backed and sparse fields; tricubic passes
  through the samples with a continuous gradient. setGradientInterpolation
  reads the direction with a different method from the distance, for example
  a trilinear distance with a tricubic gradient. getDistanceAndGradient
  returns both from one lookup.
- readSparseSignedDistanceFieldNVDB(bytes, band_clamp, scale, grid_name)
  reads one grid of a NanoVDB file as a sparse field, by name when the file
  holds several; getSignedDistanceFieldNVDBGridNames lists them. Nothing is
  assumed about how the grids of a file relate. The clamp travels beside the
  file, not in it. readSignedDistanceFieldNVDB still reads one dense grid, and
  writeSignedDistanceFieldNVDB writes a sparse field's grid as stored. The
  URDF element gains optional grid and band_clamp attributes next to scale.
- The cereal archive gains an explicit format version (1) and stores the
  interpolation settings. A sparse field is stored as a standard NanoVDB
  file plus one band clamp per grid. Unversioned archives no longer load.

collision_sdf_interpolation_benchmark (a report, not a test) compares the
interpolation methods through the helpers Bullet's SDF algorithms use:
accuracy against exact geometry (a sphere, a bore, a box's edges and
creases, and a 90 degree inside corner), direction smoothness, probe contact
error, build time, memory and query cost, for grid-backed and sparse fields.

Given a real millimetre NanoVDB field instead, it reports load time and
memory dense and sparse, their agreement, query / hull / probe timings per
method, and direction smoothness along the surface, with each discontinuity
classed as an interpolation jump (distance continuous) or a data jump (the
edge of the grid's data).
