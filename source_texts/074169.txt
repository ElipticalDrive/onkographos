Summary
A large series does not display on a device that has a small texture limit. A volume of
3072 × 512 × 512 voxels does not fit in a 3D texture on a device that has a limit of 2048 voxels
for each edge. Today Cornerstone3D allocates that texture, the allocation fails, and the viewport
shows black. No error occurs, and no message tells the user why.
This issue adds a multi-resolution model to ImageVolume and to VoxelManager. A volume can hold
more than one representation of the same data at the same time. A render path selects the
representation that the device can hold. The volume reports the quality of the data that the
render path used, so that a viewport can show a quality indicator.
The existing API does not change. A viewport, a tool, a segmentation and an annotation continue to
use the same methods, and they get the same geometry, the same number of slices and the same
positions. New code opts in to the new API.
Scope, and the rule for a change to this document
This document has two requirement sections, and the two sections stay separate:
§ User requirements — what the user must be able to do, or must be able to determine, to
work safely.
§ Implementation requirements — how to do the work.
You can change an implementation requirement freely when a better approach appears. You change a
user requirement in two cases only: the requirement describes the behaviour wrongly, or the
intended behaviour for the user changes. An implementation that is inconvenient is never a reason
to change a user requirement.
The model
A representation is a grid
A representation is a grid. A grid has an origin, a direction, a spacing and a set of
dimensions. One type therefore describes each of these cases, and a grid can be more than one of
them at the same time:
A sub-resolution grid covers the whole volume, and its spacing is larger. This is the usual
decimation. The client needs a sub-resolution grid when a texture does not load.
A sub-region grid covers a part of the volume, at the full spacing. A thin oblique slab is a
sub-region grid, and the client moves that slab as the user moves the plane. A full-resolution
oblique MPR view uses such a slab.
A level of a server-side brick store is a grid whose values are on the server.

A composite voxel manager
A composite voxel manager holds sub voxel managers. The sub voxel managers can have different
extents, different resolutions and different qualities at the same time. The nesting can be partial,
and the nesting can overlap.
ImageVolume can reference more than one texture. A texture maps to one sub voxel manager, or a
texture maps to a set of sub voxel managers. The mapping is many to many.

Three viewports then show this data:
A 3D viewport at a low magnification uses the decimated texture. One display pixel covers 1/8 of
a source voxel in each dimension, so the view is lossless.
An oblique viewport shows a plane that is inside the 512 × 1024 × 25 slab. The view is
lossless.

and the viewport shows the quality indicator.
The third and the first viewport read the same volume. The quality is therefore a property of the
pair — the data, and the reader that uses the data. The quality is not a property of the data
alone.
§ User requirements
MR-U-1. A large series displays on a device that cannot hold the full-resolution texture. The
user sees an image at a reduced resolution. The user does not see a black viewport.
MR-U-2. A change of the resolution does not change what the user measures or draws. The number
of slices stays the same. An annotation stays at the same position. A segmentation applies to the
same voxels. A scroll position and a thumbnail do not change.
MR-U-3. The user does not select the resolution. The software selects the resolution from the
data that is available, from the capability of the device, and from the performance target.
MR-U-4. The user can determine the quality of what each viewport shows. Two viewports over one
volume report their quality independently.
MR-U-5. A viewport that shows reduced data at a magnification where the reduction is not
visible reports the view as lossless. The user does not get a warning that is not necessary.
MR-U-6. An image refines as more data arrives. The user sees the refinement in each
orientation. The user does not see an error, and the user does not see a blank region.
MR-U-7. A consumer that reads the voxel values can determine the quality of the values that it
read.
§ Implementation requirements
Group 1 — the API of VoxelManager
MR-API-VM-1. Extract a true IVoxelManager interface directly from the VoxelManager
class. Today packages/core/src/types/IVoxelManager.ts holds
export type IVoxelManager<T> = VoxelManager<T>, which is an alias to the class and not an
interface. Each consumer then depends on the interface. The composite voxel manager implements the
interface, and the composite does not have to extend the class.
The extraction has two consequences, and the work must resolve each one:
Four members are optional instance properties that the factories install, and they are not
methods of the class: getCompleteScalarDataArray, setCompleteScalarDataArray, getRange and
invalidateCache. Only createImageVolumeVoxelManager and
createScalarDynamicVolumeVoxelManager install the first one. The interface must therefore mark
each of the four as optional, or the work must make them methods of the class.
About eight call sites read members that are not part of the public surface: map,
sourceVoxelManager, _get, _set, _getConstructor and _getScalarDataLength. Most of them
are in packages/tools/src/utilities/segmentation/createLabelmapMemo.ts and in
packages/tools/src/stateManagement/segmentation/labelmapModel/labelmapEditTransaction.ts. The
interface must include those members, or those call sites must change.
MR-API-VM-2. The existing public surface of VoxelManager does not change. getAtIJK,
getAtIndex, setAtIJK, forEach, getScalarData and the other existing methods keep their
signatures and their behaviour.
MR-API-VM-3. getAtIJK returns the nearest value that is available. getAtIJK never returns
undefined for a voxel that is in bounds. The values are already wrong today when the load is not
complete, so this is not a new defect. What changes is that a consumer can now discover the defect.
MR-API-VM-4. A composite voxel manager holds sub voxel managers. Each sub voxel manager has
its own grid.
MR-API-VM-5. A caller that addresses a sub voxel manager directly reads from that sub voxel
manager. No selection rule applies to such a read. A render path does this when it draws the
sub-resolution data.
MR-API-VM-6. For every other read, the selection takes three inputs, and not one: the
region, the statistic of MR-API-VM-6.2, and a ceiling, which is the resolution that the
caller will use. The composite selects the sub voxel manager that has the highest resolution that
is not higher than the ceiling, among those that match the statistic and that cover the region.
The loaders keep every sub voxel manager up to date, so that sub voxel manager holds the data that
has the least loss.
A read that states no ceiling gets the highest resolution that exists. A tool, a measurement and
a segmentation state no ceiling, so their behaviour does not change, and MR-API-VM-2 holds.
The ceiling is necessary. An earlier version of this issue stated the rule with no ceiling. Under
that rule, a request that fills a texture at one eighth selects the full-resolution data, and the
code then reduces that data at each fill.
MR-API-VM-6.1 — the selection does not create. When no sub voxel manager sits at the ceiling,
the selection returns the best one that exists, and that one is coarser than the ceiling. The
selection never creates a sub voxel manager. Whether a new sub voxel manager is worth its cost
depends on the configuration, and on the data that is available, so a caller makes that decision.
A separate API creates a sub voxel manager at a stated grid and a stated statistic. A creation
derives the data from a higher resolution, or from a direct load. Nothing derives a
representation from a lower resolution.
MR-API-VM-9 gives the reason for this split: the selection runs for a region, and the selection must
be cheap enough for the inner loop of a brush tool or of a statistics routine. A query that can
allocate a volume and reduce that volume is not cheap.
MR-API-VM-6.2 — the statistic. A representation is identified by the pair of its grid and
its statistic, and not by its grid alone. Two representations can have identical geometry and hold
different values.
Statistic
What it holds
State
average
the box average
this issue builds this one
minimum
the smallest value in each group

the largest value in each group

A minimum and a maximum let a ray cast make a short circuit, and they are likely to exist at a very
low resolution over the whole volume. This issue does not build them, and this issue must not
prohibit them.
The default selection considers the average statistic only. A minimum or a maximum is
reachable through the direct addressing of MR-API-VM-5, and through that only. Without this rule, a
minimum at a high resolution wins the selection of MR-API-VM-6, and getAtIJK returns a minimum in
place of the data. That result is wrong, and it is not lossy, so no quality record reports it.
MR-API-VM-7. Where two sub voxel managers have the same resolution and the same statistic, the
composite selects the one whose quality record is better.
MR-API-VM-8. The selection rule of MR-API-VM-6 and MR-API-VM-7 is a volatility. The
composite hides the rule behind a method. A later implementation can then select a different
access pattern, and no call site changes.
MR-API-VM-9. The composite resolves the selection for a region, and not for each voxel. A
test for the best source inside the inner loop of a brush tool or of a statistics routine is too
slow.
MR-API-VM-10. A quality query returns an absolute record for a region. The record states
which data exists, at which spacing, with which loss, and how much data is missing. The record
does not state a verdict.
MR-API-VM-11. A separate pure function compares an absolute record against the requirement of
one reader, and the function produces the verdict. Each render path can therefore produce a
different answer from the same record, according to what that render path can use.
MR-API-VM-12. One vocabulary describes the quality. The vocabulary applies at more than one
granularity inside one voxel manager. The frames of the existing frame loaders are child voxel
managers that hold different data, so the quality record of a frame and the quality record of a
region are the same thing at two scales.
MR-API-VM-13. ImageQualityStatus stays as the comparable summary, and the code derives that
summary from the absolute record. Every existing minQuality floor and every existing
quality-regression guard continues to work.
MR-API-VM-14. The values of ImageQualityStatus can change. Add the necessary values, and
renumber the gaps. The values are not a stable format for storage, and the issue says so.
MR-API-VM-15. An API accepts new data for a region at a stated quality. A loader delivers a
brick, a sub-resolution frame, or a full frame through this API.
MR-API-VM-16. A tuple of dimensions selects a 3D grid. The index space stays three-dimensional,
and getAtIJK does not take more arguments.
MR-API-VM-17. The voxel manager answers a query about the meaning of the z dimension. The z
dimension is spatial, or the z dimension is time, in the same way as it is now. A different parent
voxel manager can define a different meaning for z, according to the selector that the parent
passed in.
MR-API-VM-18. The type of the grid admits per-level differing extents and non-uniform
tiling. A WSI pyramid and a stack-progressive pyramid are therefore expressible. This issue adds
no loader for them.
Group 2 — the API of ImageVolume
MR-API-IV-1. The existing public surface of ImageVolume does not change. dimensions,
spacing, origin, direction, imageIds, getImageIdIndex and the other existing members keep
their behaviour.
MR-API-IV-2. ImageVolume holds a pool of textures. The key of an entry is the pair of
the grid descriptor and the statistic of MR-API-VM-6.2. The pool counts the references to each
entry.
The pool is generic over the kind of the grid. One pool, one key and one rule for the lifetime
serve every kind of texture. To add another kind of texture for a render path must need no new
mechanism for the cache. In particular, the pool does not assume that the direction of a grid is
aligned with the axes of the volume.
An oblique texture grid is an example, and it is not a new kind of object. An oblique texture
grid is a texture grid at an integer offset from the original integer image indices, with a view
up and a view right. That is the description that the fill rules of the segmentation already use, so
those fill rules generate the texture sets and the fragments. This issue does not build an oblique
slab. This issue must not make one impossible.
MR-API-IV-3. A render path claims an entry, and a render path releases an entry. Two viewports
that show the same oblique plane therefore share one slab, and they do not allocate two.
MR-API-IV-4. An API gives the alternate representations to a caller.
MR-API-IV-5. The composite computes which sub voxel managers fill a texture. The composite
fills a grid from the best sources that it has. There is no strategy parameter in this version.
A later version can add one if that becomes necessary.
MR-API-IV-6. A texture refills lazily. New data marks a region of each affected texture as
dirty, and the refill happens in the next render of that texture. The dirty flag belongs to the
texture pool and to the region.
MR-API-IV-7. The pool counts the cost of a texture before it allocates the texture. The
pool compares that cost against a declared limit. The code therefore knows in advance whether a
texture can work.
MR-API-IV-8. When the pool cannot allocate, the pool first removes the entry that has no
references and that is the least recently used. If that does not release sufficient memory, the
pool refuses the request, and the render path selects a grid that it can afford.
MR-API-IV-9. getCompleteScalarDataArray does not change. It returns what it returned
before. If that allocation exhausts the memory, that result is accepted.
Group 3 — the changes in other areas of the code
MR-CODE-1 — the capability profiles. This issue adds no new capability probe. Instead the
code holds a list of named capability profiles, and an application states which profile applies.
The examples state a profile in the same way. Two example profiles:
32gb fast — 32 GB of texture memory, fast, and the default maximum edge of 2048.
256 edge slow — a maximum texture edge of 256, with other defaults.
This list is task T4 of the set-aside breakdown, which defines the GPU classes and the default
memory figure of each class.
MR-CODE-2 — the check before the allocation.
packages/core/src/RenderingEngine/vtkClasses/vtkStreamingOpenGLVolumeMapper.js:409 calls
create3DFromRaw with the dimensions of the image data and no size check. The mapper must compare
the dimensions against the profile of MR-CODE-1 before it allocates. This is the only place where
the dimensions are known and the allocation has not yet started.
MR-CODE-3 — the automatic selection of a grid. When the full-resolution grid exceeds the
maximum edge of the profile, the code selects an alternate grid that fits, and the code reports the
reduction. A device with a maximum texture edge of 256 is a real case: a 512 × 1024 × 25 oblique
slab must become 256 × 256 × 25.
MR-CODE-3.1 — the choice is a pluggable function. A render path takes a function that
chooses which texture the render path uses. The function is a parameter of the render path, and the
function is not a branch inside the render path.
This issue ships one implementation of that function, and that implementation reads the
capability only. It compares the grid against the profile of MR-CODE-1, and it selects a grid that
the device can hold.
The function can become complex later, and the signature must permit that. Two later tasks supply
their own function: the degradation of the fidelity during an interaction, which reads a performance
target, and an automatic policy that reads a recorded snapshot of the capability. Neither is in
this issue. "The texture is too large" and "the frame rate is too low" are different causes with
different timing, and this issue implements the first one only.
A render path can change its texture at run time, and the code consults the function again when
the circumstances change. The function is not consulted once at set-up.
vtkSharedVolumeMapper.setScalarTexture already permits the change.
MR-CODE-3.2 — no texture exists until the function chooses it. The full-resolution texture is
never created unless the selection function chooses it. ImageVolume creates no texture in its
constructor. An API selects the child texture object, and the public property
vtkOpenGLTexture is assigned only when the selected texture is the full-resolution one.
This requirement is the repair for the defect in the summary of this issue. Today
ImageVolume.ts:146 creates the texture unconditionally, the mapper then fills that texture at the
full dimensions, the allocation fails, and the viewport shows black. When nothing asks for the
full-resolution texture, the code issues no oversized allocation.
The existing API of ImageVolume for a viewport does not change, per MR-API-IV-1. A tool, a
segmentation and a measurement see no difference. The rendering API does change, because the
rendering is what this issue updates. createVolumeActor.ts:53 and createVolumeMapper.ts:39 are
rendering, and they change.
The reduction applies for each axis, and the reduction is not uniform. A volume that has an
edge of 2049 voxels exceeds a maximum edge of 2048 on one axis and by one voxel. The code
must reduce that one axis. A uniform reduction by a factor of 2 on three axes takes 8 times fewer
voxels for an excess of one voxel, and that result is wrong.
MR-CODE-4 — one mechanism for two causes. "The texture is too large" and "there is not
sufficient GPU memory" produce the same result for the user. MR-CODE-3 and MR-API-IV-8 therefore
share one mechanism, and that mechanism has two causes.
MR-CODE-5 — more than one texture for one volume, and one texture in the shader.
ImageVolume holds a pool of textures, per MR-API-IV-2, so one volume has more than one texture.
The shader still binds one texture at a time. A render path claims the texture that it needs
for one draw, and it releases that texture afterwards.
vtkStreamingOpenGLVolumeMapper.js:104 has a flag multiTexturePerVolumeEnabled for more than one
input port. This work does not make that flag live, and this paragraph corrects an earlier
version of this issue that said the opposite. Three facts give the reason:
The flag is a local const at :105, and the file never writes the value to
model.previousState. The only mention of previousState in the file is its initialization at
:612.
vtk.js reads model.previousState.multiTexturePerVolumeEnabled in its shader path, at
node_modules/@kitware/vtk.js/Rendering/OpenGL/VolumeMapper.js:295. To make the flag live is
therefore to change the shader path of a vendored library.
To bind more than one texture at one time is the composition that the "Out of scope" table
of this issue already defers: "The composition of more than one texture in the shader, with a
page table — This is Part 2 of the rendering plan."
The flag stays dead until Part 2.
MR-CODE-6 — the reduced frame must stay reduced.
packages/core/src/cache/classes/BaseStreamingImageVolume.ts:330 and :392 set targetBuffer to
the full rows and the full columns of the volume. Then
packages/dicomImageLoader/src/decodeImageFrameWorker.js:203 calls scaleImageFrame, and the
default scaling is replicate. A smaller decoded frame therefore goes back up to the full
dimensions before the texture sees it, and the saving disappears.
The composite must take the reduced frame at its true decoded size, before that up-scale. The
primary grid keeps today's behaviour exactly. The true decoded size is available at the point where
the worker returns the frame, and the code discards it today.
MR-CODE-7 — the render paths. This issue changes two render paths. Each one selects a
grid, reads that grid, and reports the quality that it used.
Planar/VtkVolumeSliceRenderPath, that is the MPR and planar path. This path is the critical
one, and it is the path that must clear the quality indicator where the display resolution is
below the data resolution.
Volume3D/VtkVolume3DRenderPath. This path is secondary, and an earlier version of this issue
put this path out of scope.
The reason for the change is not that one render path is insufficient to prove the contract. The
reason is that a 3D volume render samples the whole texture, and an MPR view samples one plane, so
the two paths ask a different question of the same data. A design that serves only the MPR path can
omit something that only a 3D consumer needs, and that omission would reach the interface, which is
the one thing this issue must get right. Two paths also prove MR-API-VM-11 directly, because
acceptance criterion 7 asks for two viewports that disagree.
MR-CODE-8 — progressive loading. The composite consumes both models:
The JLS model puts the reduced data at a separate path on the server, for example
/jlsThumbnail/. mkdicomweb generates that path. JLS has no sub-resolution decode, and
decodeLevel has no effect on JLS. This model has the same shape as a brick store.
The HTJ2K model reduces the data in the decoder, with decodeLevel, and usually with a
byte range (rangeIndex, chunkSize). decodeHTJ2K.ts:85 calls decoder.decodeSubResolution.
This is the only reduction on the client.
The reference examples are packages/tools/examples/volumeProgressive/ and
packages/core/examples/stackProgressive/.
MR-CODE-9 — the composite consumes the existing machinery. The composite reads
ProgressiveRetrieveImages, cachedFrames and ImageQualityStatus. The composite does not
duplicate them. cachedFrames is already the quality record of each child voxel manager, at frame
granularity.
MR-CODE-10 — no deprecation in this issue. cornerstoneStreamingImageVolumeLoader,
BaseStreamingImageVolume and decimatedVolumeLoader keep their current state. The set-aside
breakdown puts the deprecation in task T2, and time constraints move the deprecation to later work.
MR-CODE-11 — the examples. packages/tools/examples/volumeProgressive/ and
packages/core/examples/stackProgressive/ are the examples, and each one must do these things:
Show the fidelity information. The example displays the quality record of each viewport, and
the display changes as the data arrives.
Give the user a selector for the GPU capability profile. The user selects a profile of
MR-CODE-1, and the example then behaves as a device of that class behaves. The user can
therefore switch to different GPU settings, and can see the effect, on one machine.
Render a volume that has an edge of 2049 voxels. This is the minimum demonstration. With the
default profile, whose maximum edge is 2048, the full-resolution grid does not fit. The example
must still show an image, and the example must report the reduction. This case demonstrates the
breakdown, and it tests the rule for each axis in MR-CODE-3: the correct result reduces one axis
only.
Acceptance criteria
Every existing consumer of ImageVolume and of VoxelManager works without a change. The
survey counts about 250 call sites of .voxelManager in about 110 files.
IVoxelManager is an interface, and IVoxelManager is not an alias to the class. A class that
does not extend VoxelManager can implement the interface, and the existing consumers accept
that class.
A volume whose full resolution exceeds the maximum edge of the profile displays at a reduced
resolution, and the code issues no oversized allocation.
A volume that has an edge of 2049 voxels renders under the default profile, whose maximum
edge is 2048. The code reduces one axis, and the code does not reduce three axes.
A composite voxel manager reports the resident resolution for each region.
A consumer gets the same geometry, the same instance count and the same metadata, whichever
sub voxel manager holds the data.
Two viewports over one volume report their quality independently, and one of them can report
"lossless" while the other reports "lossy".
Data that arrives refines the image, in each orientation, and the code does not upload the
whole texture again.
A named unit test builds a WSI-shaped composite from synthetic tiles. The test uses per-level
differing extents and non-uniform tiling. The test does not use a clean pyramid of powers
of two.
The volumeProgressive example and the stackProgressive example load through the composite,
with the JLS model and with the HTJ2K model.
Each of those two examples shows the fidelity information, and each one gives the user a
selector for the GPU capability profile. The user switches profile, and the image and the
fidelity information change accordingly.
Each of those two examples renders the volume that has an edge of 2049 voxels, and each one
reports the reduction to the user.
The MPR render path draws a sub-resolution texture in place of the full-resolution texture, and
the render path reports the quality that it used.
The 3D render path draws a sub-resolution texture in place of the full-resolution texture, and
the render path reports the quality that it used. The 3D render path and the MPR render path
can report a different quality for the same volume at the same moment.
The code issues no oversized allocation. Under every profile, and for every volume, the
code never asks for a texture that exceeds the maximum edge of the profile. A volume whose
full-resolution grid does not fit produces no full-resolution texture, because the selection
function never asks for one.
The unit tests, the integration tests and the documentation are merged.

Facts about the current code
These facts come from a survey of the repository. They explain why some requirements above are
larger than they look.
There is no interface. types/IVoxelManager.ts is
export type IVoxelManager<T> = VoxelManager<T>, and IImageVolume is
type IImageVolume = ImageVolume. "The interface does not change" therefore means "the class
does not change".
A volume voxel manager is already virtual, and it is already composite.
createImageVolumeVoxelManager holds no voxels. It resolves each slice through
cache.getImage(imageId).voxelManager. The voxels live in the image cache, as one IImage for
each slice.
The GPU upload is already per slice.
vtkStreamingOpenGLTexture.updateTextureImagesUsingVoxelManager() reads
image.voxelManager.getScalarData(), and it calls gl.texSubImage3D for one slice. The
updatedFrames array gates the upload. The override of modified() marks every frame, and the
comment on that override says "this is really not efficient, but it works for now".
There is one GL texture for each ImageVolume. The constructor creates it, and every actor
shares it.
An oversized allocation fails silently. vtk.js does not validate the size in
create3DFromRaw. WebGL raises a GL error, and WebGL throws no exception. No code in
packages/core/src or in packages/tools/src calls gl.getError(). The viewport shows black.
The existing probe reads the 2D limit. utilities/renderingCapabilities.ts reads
gl.getParameter(gl.MAX_TEXTURE_SIZE). MAX_3D_TEXTURE_SIZE occurs once in the repository, in
a console.log in the touchAllTools example. maxTextureDimension3D occurs nowhere. Nothing
reads the maxTextureSize field that the probe produces.
ImageQualityStatus.SUBRESOLUTION does not mean "fewer pixels". Its producers are
getImageQualityStatus.ts:11, which returns SUBRESOLUTION when the bytes are not complete;
extractMultipart.ts:28, for a partial response; and an explicit label in a retrieve
configuration. Nothing derives the value from decodeLevel, and nothing compares the decoded
size against the metadata. MR-API-VM-13 permits the renumber that corrects this.
#decimation= is written and it is never parsed. decimatedVolumeLoader.ts:117 writes the
URL fragment. A search of the repository finds no reader. A decimated volume therefore fetches
and decodes full-resolution frames, and the reduction happens only in the replicate down-scale.
getCompleteScalarDataArray has 21 call sites, which include the grow-cut routines, the
metabolic statistics and convertMapperToNotSharedMapper. getScalarData has 32 call sites.
The branch feat/rle-labelmap-voxel-representation already adds a representation concept —
VoxelManagerEnum with the values Volume and RLE, plus getWritableScalarData() and
setFromScalarData(). A representation that is not a typed array is therefore an idea that
VoxelManager already supports.
