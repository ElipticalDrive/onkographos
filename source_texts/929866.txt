What
A streamed HLOD world, including V4 paged worlds, and N movable GaussianSplatNode3D instances now draw in the same frame, in one draw list, one depth sort and one byte ledger. Until now, a single node next to a paged world made the world draw nothing.
Director: the exclusivity check is removed (has_hlod_world_submission). A row builder produces row 0 = world and rows 1..N = visible nodes.
Publisher:
Each node asset is packed once after the world and charged to the ledger before allocation.
Instance draw records use the offset T − camera, computed in double.
A world that is still loading keeps drawing the instances.
Moving nodes take PR1a's row re-upload path, so they cause no rebuild.
Budget rule as in ADR §5: objects first, the world keeps a floor, and refusals are per object, deterministic and explicit.
Two fixes the GPU runs forced:
A renderer-wide full-fidelity fallback turned off LOD whenever node assets existed. It no longer applies on the HLOD route.
The overlap-record storage now grows to hold the objects' estimate.

The world floor F
F = 1/2 of each performance cap of a view:
the view's splat cap C_view: the world's max_splats before the world contract clamps it to the world's data count;
the overlap-record cap: the configured hard cap, or the overlap storage when none is configured.
How the caps split:
The visible objects reserve R from C_view first, at most C_view − F.
The world cut gets min(W_need, C_view − R), where W_need is the world's own cap (≤ its data count).
So when the world and the objects fit under C_view, the world is not degraded at all. When they do not, the
world keeps F and the objects are refused whole, in screen-importance order, ties broken by the instance key.
The overlap storage grows to hold the objects' record estimate next to the world's seed, priced against the
route's ledger headroom. The world's record budget is unchanged when that growth fits.
Why one half:
Decision 3 requires a fixed floor so objects can never starve the world. Half is the largest object share that
still guarantees the world never gets less than the objects.
The HLOD selector refines in priority order, so a world cut under half of its caps is the same refinement
sequence stopped earlier. It is coarser, but it never drops a region (complete-or-nothing, BV I-4).
With the default view caps (millions of splats), objects get far more than a typical object set needs, so
refusals are rare in practice. When they happen, they are explicit: the reason
hlod_instance_reserve_exceeds_object_share and the counters hlod_instance_refused_objects and
hlod_instance_reserve_refusal_frames.
F is an internal constant (renderer/hlod_world_instances.h). A project setting would be R3 (F3).
The draw list is not a performance cap. It is sized for the world's nodes plus every row's chunks, so it never
refuses an object.
Byte ledger: the instance region is charged to the same device ledger and, on streamed or paged worlds, to the
atlas page budget, as ADR 4.5 states. If the atlas byte cap cannot hold the world's cut and the objects, the world's
page budget shrinks (the cut gets coarser). The world-floor rule covers the view caps, not bytes.
GPU evidence
tests/runtime/test_hlod_resident_main_view.gd (already registered in streaming-gpu-ci and release-ci; no new
registration) gains a world + 8 moving instances proof, run on a V4 paged world and on a whole-tree resident world.
It is fail-closed:

every frame, both sources draw, there is exactly one depth sort, and no *not_exclusive* reason appears;

moving the nodes causes 0 rebuilds and takes the row re-upload path;

every wait loop checks its deadline right after frame_post_draw, before accepting an observation.
It is red on base and green on this branch. A C++ [RequiresGPU] doctest is not possible: the doctest harness
renders through RasterizerDummy, which has no render target.
Deferred follow-ups (not in this PR)
A visibility change still rebuilds the bundle: it moves the director's asset-set generation.
Instance assets are re-packed on every frame the route is not prepared (warm-up, or a persistent refusal).
Shadow and extra views still refuse the HLOD route (F5).
A byte-ledger floor: the world has no guaranteed share of the atlas page budget against the instance region.

…once; world+instances waits fail past the deadline (Refs #788, #1131)

Codex P1 on #1308 (publisher): the world's overlap-record need was read
from the allocated storage, which already held the previous frame's
object reservation, and the objects' estimate was added on top again. A
stationary view with visible node instances regrew the overlap storage
(reallocating the buffers and rebuilding the sorter) on every frame until
the record cap or the ledger headroom stopped it.

The world's need is now tracked apart from the storage
(gs_hlod_bundle::world_overlap_need): while the storage is the one the
route last sized, the tracked need is used; any other storage (first
frame, measured-overflow growth, new device) is read whole as the
world's, once. The requirement is absolute: world need + this view's
estimate, counted once (world_plus_objects_overlap_records). When it
exceeds the storage, the route grows to the world need + 3/2 of the
estimate (world_plus_objects_overlap_growth, the slack the measured
overflow growth uses) and falls back to the exact requirement if the
slack does not fit the headroom, so moving objects do not reallocate on
every small rise. The same tracked need feeds the objects' record share.

New render stats: hlod_overlap_capacity_records (the storage the last
prepared view drew with) and hlod_instance_overlap_growths (cumulative
growths for the objects' estimate).

Tests:
- CPU doctest "a stationary view with objects grows the overlap storage
  once, not every frame" drives the publisher's sequence over frames
  (stationary, leave/return, rising estimate, two alternating views,
  foreign storage growth).
- test_hlod_resident_main_view.gd: a stationary phase after warm-up
  (30 frames, both modes) fails if either new stat moves.

Codex P1 on #1308 (test): the world+instances budget loop accepted an
observation from a frame that ended past the deadline. The warm-up and
budget loops now check the deadline right after frame_post_draw and fail
explicitly (tests/AGENTS.md: the deadline binds the pass). The motion
phase loop already did; the pre-PR1b loops in the file already did.

… region's frame scratch (Refs #788, #1131)

Codex P1 on #1308: prepare_hlod_frame() admits the frame scratch for
the relative atlas it draws from, world pages plus the node instances'
region at the atlas tail (total_gaussians = stream records +
region.records); prepare_hlod_scratch() sizes the subpixel history and
the SH colour cache from that combined count. The streamed page budget
reserved per-record scratch for the world's pages only. With a
ledger-bound budget and a large instance region the scratch admission
then refused every frame (tile_capacity_warmup_or_memory_limit), and
the prepared bundle kept the same page count, so it never recovered.

ResidentAtlasBudget::hlod_stream_page_budget_with_instances() takes the
region's records: their atlas bytes come off the atlas limit (as the
publisher did inline) and their per-record scratch is added to the
fixed scratch before the ledger term is computed. Overflowing products
refuse (0 pages) instead of wrapping. The publisher calls it in place of
the inline subtraction.

Other per-record charges on that path were checked: the bundle's fixed
bytes already hold the region's atlas records and chunk tables
(gs_hlod_bundle::bundle_bytes), and the visible-sized scratch
(projection, visibility, history floor) is sized from relative_capacity,
which already includes the objects' share.

Test: "a ledger-bound page budget reserves the instance region's frame
scratch too" (test_resident_atlas_budget.h) checks, for regions of 0 to
5M records, that the headroom left after the bundle still admits the
scratch prepare_hlod_scratch() asks for; that without instances it is
the world-only budget; and the atlas-bound, exhausted and overflow cases.

…ions first, optional overlap growth from the rest (Refs #788, #1131)

Codex P1 on #1308 (the fourth finding of one class): every step of
prepare_hlod_frame() allocates from the same headroom, route_limit -
route_bytes. The two overlap growths (the measured-overflow growth and
the growth for the objects' record estimate) ran on the full headroom,
before the view grid and the frame scratch were provisioned. On a
ledger-bound streamed bundle whose scratch was not allocated yet they
could spend the bytes the page budget reserved for that scratch, and
every frame was refused with tile_capacity_warmup_or_memory_limit.
Nothing shrinks again (neither the grown storage nor the page count),
so the world stayed blank.

The order is now explicit (ResidentAtlasBudget, resident_atlas_budget.h):
- hlod_mandatory_outstanding_bytes(): what the world still owes this
  frame. That is the view's tile grid (hlod_view_grid_outstanding_bytes,
  the rule hlod_view_grid_action now admits by), the frame scratch
  (TileRenderer::get_hlod_scratch_outstanding_bytes, from the same plan
  prepare_hlod_scratch admits by, via the new _plan_hlod_scratch()) and
  the ViewSet charge of the views (history and draw records per view,
  charged against the same headroom on every frame). The sum saturates.
- hlod_optional_growth_headroom(): the headroom minus that. Both overlap
  growths get only this. A refused optional growth leaves the storage as
  it is and blocks nothing.
The scratch request is built once, before the growths, and reused by
the admission.

Test: "optional overlap growth never spends the world's mandatory frame
allocations" (test_resident_atlas_budget.h) runs the frame's sequence:
with a ledger that admits the growth only from the full headroom, the
growth is refused and the scratch and the view are admitted; with room
for both, both happen. It also covers the steady state, saturation, and
grid outstanding == grid action.
