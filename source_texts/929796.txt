Hi! First contribution here, and thanks for the library. This is the first of three small PRs that let oxivgl build for the ESP32-C3 (riscv32imc); see #131. This one is the Rust side, and build: derive RISC-V -march/-mabi… (#133) teaches the build scripts about the chip. This one and that one are both needed.
What I ran into
driver.rs, indev.rs and scanout.rs use swap, fetch_add and fetch_sub, which core::sync::atomic doesn't provide on cores without the A extension, such as the ESP32-C3. The crate fails to compile there with 9 "method not found" errors.
What this changes
Those three files now use portable-atomic. Targets with native atomics (Xtensa, host) keep using them, so nothing changes for them. Files that only load and store atomics are untouched.
I deliberately didn't enable a backend feature, following portable-atomic's advice for libraries: on cores without atomic compare-and-swap the application picks one. esp-hal's esp32c3 feature already enables unsafe-assume-single-core, and enabling critical-section in the library as well is a hard compile error in portable-atomic.
How I tested it
Host: unit (78), leak_check (71) and doc (42) tests pass, unchanged, since the host uses native atomics.
Together with the build PR, riscv32imc builds once the application selects a backend (I checked with --cfg portable_atomic_unsafe_assume_single_core). Without one you get portable-atomic's own "requires atomic CAS" error, which seems like the right signal.
On its own this PR can't build for the C3, because the build scripts still assume an S31.
Not run on hardware.
Questions for you
Would you like the crate to expose a feature that forwards the backend choice? I left it out so applications stay in control, but I'm happy to add it.
