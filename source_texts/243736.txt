Context
Split off #558 (Phase D of the SceneDB + Helio + reflection/properties-panel unification, master tracking issue #561) — voxel volumes turned out not to fit the "thin wrapper around an existing insert/update/remove descriptor" pattern the other Phase D primitives used, so it gets its own design pass and its own issue.
What exists today
helio::Scene has real native support (crates/renderer/helio/crates/helio/src/scene/voxel.rs, scene/core.rs, helio-voxel-core):
Scene::insert_voxel_volume(VoxelVolumeDescriptor) -> Result<VoxelVolumeId> and remove_voxel_volume(id) — no update_voxel_volume.
VoxelVolumeDescriptor { voxel_size: f32, root_extent: f32, local_to_world: Mat4, movability: Option<Movability>, mode: Option<VoxelMode>, material_palette: Vec<GpuVoxelMaterial> }.
GpuVoxelMaterial { color: [f32;3], roughness: f32, metalness: f32, emissive: f32, .. } — a palette of multiple materials per volume, not one.
Actually populating voxel content is a separate op-based system: GpuVoxelEdit { volume_id, op_type, material, center: [f32;3], radius: f32, .. } — brush-style sculpting ops, no author-facing surface anywhere today.
Why this blocks a simple #[engine_class] wrapper
No update-in-place. Every other Phase D primitive (reflection captures, water volumes, post-process volumes) has an update_* call so the properties panel can push edits into the live volume. Voxel volumes only have insert/remove — any property change (even just voxel_size) means destroying and recreating the volume, which would also discard any voxel content already sculpted into it. That's a real data-loss trap for an editor component, not just an inconvenience.
Multi-material, not single-material. material_palette is a list; the properties-panel pattern used everywhere else in this initiative (one struct, flat #[property] fields) doesn't have a precedent for an author-editable list of sub-materials yet.
No placement mechanism for the actual voxels. The descriptor only describes the volume's bounds/transform/materials — nothing places voxel data into it. A real component would need to also expose (or generate) GpuVoxelEdit ops, which is a sculpting/brush UI, not a properties-panel field.
What to decide before implementing
Does update_voxel_volume get added to Helio (submodule change) so property edits don't require destructive recreation? Or does this component intentionally treat placement/size as immutable-after-creation (only local_to_world/transform-style fields updatable via a lighter path, everything else requiring explicit delete+recreate, similar to how a mesh's vertex data isn't "properties-panel editable" either)?
Is voxel content authoring in scope for this component at all, or is this issue only about placing an (initially empty, or procedurally-generated-at-spawn) voxel volume, with sculpting deferred to its own separate feature/issue?
How does material_palette get authored — fixed-size array of N slots (simple, matches the rest of this initiative's style) or a real variable-length list (new properties-panel capability)?
