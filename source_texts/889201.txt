Goal
After the new engine has a working end-to-end rendering prototype, evaluate PlanetSmith's GPU-driven voxel rendering optimizations as a separate, measured experiment. Do not block the planned architecture, the initial terrain prototype, or continuous-LOD/streaming work on this.
References
Original video: I Built a Custom GPU-Driven Rendering Pipeline (10x Faster) — PlanetSmith devlog
Timestamped third-party transcript: Sozai — Custom GPU-Driven Rendering Pipeline
Related planned issues: [FV] 19 — GPU residency, unified page/mesh arenas and nonblocking lifecycle #43 (FV19 GPU residency / memory lifecycle), [FV] 20 — exact near-camera microvoxel block geometry and local meshing #44 (FV20 exact near-camera microvoxel rendering), [FV] 29 — GPU-driven culling, meshlet/indirect draw optional optimization #53 (FV29 GPU-driven culling and indirect drawing).
Branch architecture: frontier/ARCHITECTURE.md
Agent reuse rules: frontier/AGENTS.md
Evidence qualification: The linked transcript is third-party and appears machine-transcribed/translated, so check technical claims against the original video or other primary sources before implementing. Developer-reported FPS gains are not benchmarks for MicroVoxel.
When to start
Only after the new branch has a runnable prototype with (1) authoritative 6.25 cm voxels and exact nearby voxel geometry, (2) working distant landscape and basic transition/streaming behavior, and (3) repeatable CPU/GPU frame-time + memory benchmarks (FV02 and FV20, plus usable terrain prototype from FV11/FV15).
This issue is an optimization research task, not a prerequisite for the main renderer, terrain generation, or flight streaming. Do not wait for the entire finished game, but do wait until there is a meaningful baseline to compare against.
What to investigate from the video
Shared GPU vertex/index arenas and indirect draws: avoid per-chunk mesh objects / CPU draw-call overhead; evaluate indexed indirect draw support in Rust/wgpu and portability fallbacks. Note the old successor already has shared arenas—don't assume a benefit without profiling.
Hierarchical GPU visibility/frustum culling: compare with existing CPU-selected and planned GPU culling paths. Avoid unsafe sampled occlusion or culling errors at long distance.
Paged / pooled GPU geometry allocation: study stable addresses, compaction, deferred retirement and upload stalls; compare with FV19 before duplicating functionality.
Packed vertices: test compact face/vertex encodings and on-GPU decompression against current formats, preserving exact 6.25 cm voxel positions, face normals, material/color, and edit fidelity.
Editing implications: incremental update of changed bricks/mesh ranges; ensure modifications do not force global buffer recreation or break rendering.
Distant terrain limits: the described approach does not itself solve mountain silhouettes, automatic LOD, or smooth aircraft travel. Keep those within the planned adaptive landscape/streaming architecture.
Experiment and decision
Build a small opt-in alternative backend on frontier-voxel-engine without replacing the working default.
Benchmark fixed seeds/routes at 1080p including dense editable voxels, caves/towers, forests, a static distant landscape and rapid movement, on the same device.
Measure p50/p95/p99 frame times, isolated GPU geometry/culling/draw timestamps, CPU submission overhead, memory residency + transient allocation, geometry upload/update throughput, edit latency, missing/incorrect voxels and temporal artifacts.
Ship only independently validated improvements. Revert/reject improvements that are neutral, device-specific without a fallback, create visible pops, or make the engine more complicated without meaningful wins. Report result in an issue comment and link any benchmark artifacts.
Legacy reference policy
B/R (baseline/read-only) — inspect main/successor/viewer/src/gpu.rs, successor/viewer/src/visibility.rs, existing GPU allocator/profiling records and main/agent_context/ENGINE_REDESIGN_IMPLEMENTATION.md solely to compare existing shared arenas, culling and GPU behavior. New implementation stays in frontier/; any narrowly justified allocator port must comply with the selective-port conditions in frontier/AGENTS.md. Never transplant the old LOD planner, coarse mesh rebuilding, stale-job scheduler, or visual fade system.
