Training knobs on the NeRF endpoint are validated too late to matter.
In backend/ml/routes/nerf_routes.py, train_nerf takes bare epochs, batch_size and learning_rate, then writes the learning rate straight into the shared global trainer's optimizer before training validates anything. A NaN, infinite, negative or astronomical rate therefore poisons the optimizer for every later request even when the current one fails downstream validation, and the failure surfaces as a 500 instead of a 422. The file already imports Field, so the guard belongs on the signature.
What I would change:
Declare the three parameters with Query bounds (epochs 1 to 100, batch sizes within reason, learning rate strictly between 0 and 1 exclusive, which also excludes NaN and infinities through comparison semantics), adding Query to the fastapi import. Validation then runs before the optimizer is ever touched, and the shared trainer stays clean.

The ordering bug is the core of this one: the learning rate hits shared state before validation.
train_nerf assigns the rate into the global trainer's optimizer and only then calls train, where the policy checks live. Any rejected value has already poisoned later requests by that point. Moving validation to the signature with Query bounds means bad input never reaches the assignment line, and the exclusive 0-to-1 range additionally excludes NaN and infinities through comparison semantics. Query joins the fastapi import; the trainer call itself is unchanged.
