The -p option currently produces what seems to be an orthographic projection, where all objects appear with the same size regardless of their distance from the viewer. This projection maintains parallel lines and provides no sense of depth.
A true perspective projection would make distant objects appear smaller, with lines converging toward vanishing points — similar to how real cameras or rendering engines represent 3D scenes. You can see this link for some interactive examples.
Implementation:
I would be interested in working on this improvement myself. However, I have not been able to find where in the GMT source the code handling the -p option (projection and 3D transformations) is implemented. Could you please indicate which source file(s) contain this logic?
I believe some of the required functionality might already exist in GMT through the General Perspective projection, so this could potentially be adapted or reused for implementing a true perspective view.

Update on this topic
GMT uses the PostScript (PS) language to generate figures. Native PostScript only supports affine transformations, which is why GMT’s current -p option is limited to affine 3D projections (rotation, translation, and scaling) and cannot produce true perspective projections by itself.
To obtain real 3D perspective, there are essentially two options:
Implement the perspective projection in C and pass the projected coordinates to PostScript.
Implement the perspective projection directly in PostScript.
Regarding the second option, I found the PostScript package ps3d.inc, developed by Bill Casselman and described in his book Mathematical Illustration (more info here: https://personal.math.ubc.ca/~cass/graphics/manual/). From what I have seen, it provides true 3D perspective capabilities, including real perspective projections, text rendered in perspective, and spheres and other regular polyhedra with shading. Examples can be found in Chapters 13 and 14 of the book.
While performing the 3D calculations in C would likely be faster, I believe that approach would complicate features such as rendering text in true perspective. For this reason, my current idea is to continue exploring option 2, i.e., performing the perspective calculations in PostScript. Once this is implemented and evaluated, it should then be possible to assess whether performance becomes an issue and, if so, consider ways to optimize or partially move computations elsewhere.
I contacted the author by email, and he explicitly authorized the inclusion of this package in GMT, provided proper attribution is given.
I will continue investigating this direction. In the meantime, I would welcome any general comments or suggestions on how best to proceed.

You have to include some commands in the header of the ps file. For example, this is the PS file that creates the image below
```
%!PS-Adobe-2.0
%%BoundingBox: 0 0 372 180


/w 372 def
/h 180 def

(ps3d.inc) run
(epsetup.inc) run
(cube.inc) run

% ------------------------------------------------

[0 0 6 1] set-display
0 0 -4 translate3d

/light [0 1 0 0] def
/floor [0 1 0 2] def

/wd 3 def
/dp 3 def
/fl floor 3 get neg def

/grid {
wd neg 1 wd {
  /i exch def
  i fl dp neg moveto3d
  i fl dp     lineto3d
} for
dp neg 1 dp {
  /i exch def
  wd neg fl i moveto3d
  wd     fl i lineto3d
} for
stroke
} def

page-begin
0 0.5 translate

gsave
0.8 0.8 0.8 setrgbcolor
newpath
grid
grestore

gsave3d
% the shadow
gsave
0.6 0.6 0.6 setrgbcolor

floor light plane-project

[1 1 1] A rotate3d
-0.5 -0.5 -0.5 translate3d

cube {
  % [ n [P[0] P[1] ... P[n-1]]]
  1 get /f exch def
  /ell f length def
  newpath
  f ell 1 sub get 
  aload pop moveto3d
  f {
    aload pop lineto3d
  } forall
  fill
  
} forall

grestore
grestore3d

gsave3d

[1 1 1] A rotate3d
-0.5 -0.5 -0.5 translate3d
/O origin cim3d transform3d def
% O = origin in current coordinates
/L light cim3d transform3d normalized def
% L = light in current coordinates

cube {
  % [ n [P[0] P[1] ... P[n-1]]]
  dup 
  0 get /n exch def
  1 get /f exch def
  % n = normal function
  /ell f length def
    n 
    O 
    dot-product 
  0 ge 
  {
    newpath
    f ell 1 sub get aload pop moveto3d
    f {
      aload pop lineto3d
    } forall
    gsave
      n normalized L 
    dot-product
    [0.40 0.60 0.80 1] 
    shade 0 0 setrgbcolor
    fill
    grestore
    stroke
  } if
} forall

grestore3d

grestore 
showpage
```
Link: https://personal.math.ubc.ca/~cass/graphics/manual/code/cube5.txt
