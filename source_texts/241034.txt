Hi there!
First of all, thank you so much for this amazing library!
I've been learning about 3D Gaussian Splatting by using MetalSplatter
with PLY files converted via ml-sharp, and this open-source project
has been incredibly helpful for my studies.
I have a question that I hope you don't mind me asking:
When I load my PLY files (~1.18M splats) using an app I built based on
this library, the Vision Pro fan spins up and there's noticeable
flickering during rendering, especially when moving my head.
However, when I load the exact same PLY file in your released
MetalSplatter app from the App Store, it renders beautifully -
no fan noise, no flickering, and smooth interaction with gestures.
I've tried various approaches to fix this (adjusting sortTimeout,
deviceAnchor handling, etc.) but haven't been able to match the
performance of your released app.
I was wondering if you could share some insight on how you optimized
the rendering in the released version? The visual quality seems the same,
so I'm curious if you're using a different format (like SPZ perhaps?)
or some other technique.
Any guidance would be greatly appreciated! 🙏
Thank you again for your work on this project!

Does the "shaking" look like the foreground is bouncing rapidly back and forth when you head moves (and more with more movement)? That sounds like the effect that led me to develop the "high quality depth", so I'd again suggest double-checking that you're leaving that enabled. The root cause of that flickering was actually the Vision Pro's frame extrapolation going wonky because it was using the (poor) depth produced by default when one renders splats.
But the scene disappearance sounds like something deeper. Perhaps it's actually dropping too many frames and the Vision Pro is giving up. I'd first make sure that the sample app isn't doing the same thing (if it is, then it's not your app). If it isn't, then Instruments is your best bet to see what's going on (maybe the Metal System Trace instrument?)
One other possibility: the MetalSplatter app is using a slightly older version of the MetalSplatter library (I haven't submitted it with the latest library, but will soon) and isn't using the 26 SDK; so the problem could actually be an issue with the latest MetalSplatter library, or and issue when building with the iOS 26 SDK. If you aren't able to make any headway, we could investigate this via a TestFlight of a new MetalSplatter app build once I have one available.

Behavior

The effect is worse on larger PLYs (1.4M splats vs 1.15M).
Metal System Trace summary
Display VSYNC is stable at 90fps (11.11ms).
Average FPS ≈ 43; median frame time ≈ 33ms (most frames in 33–50ms bucket → 30fps fallback).
Command Buffer submission rate ≈ 30.4/s.
CPU encoder time is tiny (~0.058ms avg), so CPU encoding is not the bottleneck.
GPU driver-level command buffer time frequently 55–91ms (sometimes >100ms).
A few severe stalls (e.g. an 8.2s gap, hundreds of missed VSYNCs).
Thermal state transitions to “Fair” after ~33s.
Interpretation
The bottleneck appears to be GPU work (sort + splat rendering), not CPU or draw submission.
Large head motion + long sort time often causes frame drops, and that’s likely when the scene “disappears”.
Changes tried
Pre-allocating index buffers and triangle index buffer.
Switching PLY load to SplatIO + SplatChunk to avoid repeated buffer reallocations.
Sort throttling (position/angle threshold + minimum interval + avoid queuing while a sort is running).
World-locked model transform (fixed to initial device anchor).
Open questions
Could the released MetalSplatter app (older library / pre‑26 SDK) be avoiding some GPU cost in the sort/render path?
Is there any known change in the latest MetalSplatter or iOS/visionOS 26 SDK that increases GPU cost or sorting overhead?
In the released app, when do you actually trigger a re‑sort? Is it every frame, or only after certain camera deltas/intervals? I see the flicker mostly when a re‑sort kicks in, so understanding that trigger would really help.

*SampleApp modifications: Since my PLY files (generated by ml-sharp) have a different element ordering, I modified SplatPLYSceneReader to continue instead of throwing an error on non-point elements. Initially, I also reverted queryDrawables() → queryDrawable() to avoid a runtime crash (cp_frame_end_submission() before cp_drawable_encode_present()), but later migrated back to queryDrawables() by always calling encodePresent on each drawable.
Key Observations
Screen recording does NOT capture the shaking — confirming it's a frame reprojection artifact, not a sorting issue
Shaking scales with splat count — 1.5M splats shake noticeably, while smaller models (~500K) are mostly smooth
UI windows also shake when a large model is loaded — indicating system-wide frame drops, not just a model rendering issue
Analysis
The shaking appears to be caused by changes in reprojection behavior in the visionOS 26 SDK:
Your released app uses the old SDK, where queryDrawable() (layered stereo rendering) has well-optimized reprojection → smooth even with 1.5M splats
In the visionOS 26 SDK, queryDrawable() is deprecated, and its reprojection support appears to have been degraded
Migrating to queryDrawables() (per-eye rendering) improves reprojection quality, but doubles the number of render passes, exceeding the 11ms/frame budget for large models
This aligns with your earlier analysis that "the problem could actually be an issue with the latest MetalSplatter library, or an issue when building with the iOS 26 SDK."
My conclusion is that the behavioral change introduced by the SDK difference is causing the shaking in both the SampleApp and my app, which is not present in your released app built with the older SDK.
Going forward, it seems like optimizations such as GPU-based sorting will be necessary. If I'm misunderstanding anything here, I'd really appreciate your feedback. Thank you!
