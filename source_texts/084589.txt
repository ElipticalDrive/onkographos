Phase-0 feasibility spike — SplatNode (3DGS on Android/Filament)
Throwaway spike, no PR / no merged code. Goal: de-risk the one unknown that decides this epic — can Filament 1.71.5 render Gaussian splats without forking Filament, and does the required custom material actually compile under the pinned matc toolchain? It can, and it does. Details, decisions, and a phased plan below.
Executive verdict — GO-WITH-CAVEATS
The core rendering unknown is now proven at the ABI/shader level: a production-shape splat material (hardware-instanced, per-splat data fetched from textures in the vertex shader, camera-facing billboard, gaussian fragment, premultiplied alpha blending) compiles cleanly under the repo's pinned matc 1.71.5 (MATERIAL_VERSION 71), for both the lean Android OpenGL profile and the all-backend profile. No Filament fork required.
First-mover window: real and open. No declarative Compose/SwiftUI splat node exists; <model-viewer> has none; the standards layer (KHR_gaussian_splatting RC), Apple (GaussianSplatComponent), and Niantic (SPZ 4, on-device training) all moved in the last two quarters. This is worth building now.
The caveats are why it's not an unqualified GO — see Risks. The big one: the compile proof is not a runtime proof. It proves the shader is valid and ABI-correct; it does not measure FPS or prove the mandatory CPU sort keeps up at scale. P1 must gate on a real emulator/device render.

Reasoning. PLY + SPZ together already cover essentially the entire content firehose today (Inria, Scaniverse, Marble, Polycam, KIRI). PLY ships first because it needs no external decompressor and is the universal trainer output — it's the debug baseline. SPZ is the priority interchange format (10× smaller, full SH preserved) but requires porting Niantic's quantization/decompression logic. KHR_gaussian_splatting is still a release candidate (Feb 2026), ratification expected Q2 2026 — wire the parser but keep it behind an extension flag so format churn can't destabilize the shipped loaders. This matches the epic's own scoping.
Rendering approach decision — instanced camera-facing quads + custom unlit/blended material + CPU sort
This is the only path that fits Filament 1.71.5 without forking it, and it's what every WebGL viewer (antimatter15, mkkellogg/GaussianSplats3D, spark/gsplat) and the Filament maintainers themselves recommend (google/filament#8033: "It can be implemented using our material system. It's not supported natively.").

Sorting — three options, decided:
(a) CPU radix sort in a worker, re-sorted on camera motion — proven, portable, the standard. P1/P2 primary. Radix-sorting ~500k depth keys is a few ms off the render thread; gate re-sort on a camera-direction delta so it's not per-frame.
(b) GPU compute sort — ruled out, Filament has no compute (would require forking → out of scope, see QUALITY RULES on the Filament pin).
(c) Weighted / stochastic order-independent transparency (OIT) — avoids sorting entirely via accumulation blending, which Filament can express. Softer than perfectly-sorted alpha but no per-frame sort hitch. Mobile-GS uses depth-aware OIT to hit up to 127 FPS on modern mobile GPUs. P2 exploration / escape hatch if the CPU sort proves to be the bottleneck.
Proto findings — what was PROVEN vs DESIGNED
PROVEN (actually compiled, in an isolated throwaway worktree, never pushed):
I wrote a splat_probe.mat and compiled it with the repo's cached, ABI-matched matc:
~/.cache/sceneview/matc-1.71.5/bin/matc → --version reports 71.
```
matc -a opengl -p mobile  splat_probe.mat  → exit 0,  14,432-byte .filamat   (Android target)
matc -p all      -a all   splat_probe.mat  → exit 0,  88,132-byte .filamat   (gl+vulkan+metal codegen)
```
Blob introspection (strings) confirms the whole feature set is baked in and valid:
instancing → flat out int instance_index; instance_index = gl_InstanceID;
vertex-stage texture fetch → textureLod(materialParams_splatPositionScale, …) and …_splatColorOpacity
gaussian fragment → variable_splatColor.w * exp((-0.5 * dot(variable_quadUvColor.xy, variable_quadUvColor.xy)) * 9.0)
premultiplied color path + custom vertex→fragment interpolants.
The load-bearing parts of the material (the exact shape splat.filamat will take):
```
material {
  parameters : [
    { type:sampler2d, name:splatPositionScale, format:float, precision:high }, // xyz=center, w=scale
    { type:sampler2d, name:splatColorOpacity,  format:float },                 // rgb=SH0 color, a=opacity
    { type:int,       name:texWidth }
  ],
  requires:[position], variables:[quadUvColor, splatColor],
  shadingModel:unlit, blending:transparent, instanced:true, doubleSided:true
}
vertex {
  void materialVertex(inout MaterialVertexInputs m) {
    int idx = getInstanceIndex();
    int tw = materialParams.texWidth;
    highp float2 uv = (float2(float(idx % tw), float(idx / tw)) + 0.5) / float(tw);
    highp float4 posScale = textureLod(materialParams_splatPositionScale, uv, 0.0);
    float4       col      = textureLod(materialParams_splatColorOpacity,  uv, 0.0);
    highp mat4 view = getViewFromWorldMatrix();
    float3 camRight = float3(view[0][0], view[1][0], view[2][0]);   // view-matrix rows = world camera axes
    float3 camUp    = float3(view[0][1], view[1][1], view[2][1]);
    float2 corner = getPosition().xy;                               // unit quad [-1,1], instanced N times
    float3 c = mulMat4x4Float3(getWorldFromModelMatrix(), posScale.xyz).xyz;
    m.worldPosition = float4(c + (corner.x*camRight + corner.y*camUp) * posScale.w, 1.0);
    m.quadUvColor = float4(corner, 0.0, 0.0);
    m.splatColor  = col;
  }
}
fragment {
  void material(inout MaterialInputs m) {
    prepareMaterial(m);
    float2 uv = variable_quadUvColor.xy;
    float g = exp(-0.5 * dot(uv, uv) * 9.0);      // isotropic gaussian, ~3σ at quad edge
    float a = variable_splatColor.a * g;
    m.baseColor.rgb = variable_splatColor.rgb * a; // premultiply (#2224)
    m.baseColor.a   = a;
  }
}
```
Two matc errors I hit and fixed are themselves findings for whoever implements P1: (1) Filament wraps samplers — you cannot pass sampler2d as a helper-function argument, the fetch must be inlined; (2) mulMat4x4Float3(m, v) returns a float4 (homogeneous), take .xyz.
DESIGNED (not run — honest scope of the spike):
No device render. I did not build the demo APK or render on the emulator. The compile proves ABI + shader validity, not FPS, and not that the CPU sort keeps up. That's the first thing P1 must do (pure-Filament render works on the plain arm64 emulator with no ARCore — PlaneGridPreviewDemo pattern via DemoHostActivity, per CONTRIBUTING.md).
The proto uses isotropic per-splat scale. Correct 3DGS needs the anisotropic 2D-projected covariance (rotation + 3D scale → screen-space ellipse). That's a vertex-shader math extension of the same proven material — P2 quality, not a new capability.
No loader, no sort, no SH evaluation written — designed below, not coded.
Phased implementation plan
P1 — Loader + static render (M/L). PLY + SPZ parse in sceneview-core/commonMain (KMP-shared, alongside the existing geometry/math/collision); harden splat.filamat from the proto; SplatNode composable + rememberSplatInstance(...) mirroring ModelNode/rememberModelInstance (SceneView.kt:759); load the material via MaterialLoader.createMaterial(".../splat.filamat") + setTexture; upload splat attrs to RGBA16F textures; instanced quad geometry with batched draws; fixed order first (accept popping) to validate pixels; SH0 only; cap ~250k. Gate on an actual emulator render.
P2 — Sorting + quality (M). CPU radix sort in a coroutine worker keyed on camera direction, motion-gated re-sort, per-sort index upload; anisotropic covariance (proper ellipse); SH degree 1; optional weighted-OIT path; raise cap to 500k (Marble "lite"); AR placement of a splat scene on a plane in arsceneview.
P3 — KHR glTF extension (S/M). Parse KHR_gaussian_splatting primitives (+ KHR_gaussian_splatting_compression_spz); gate behind ratification; SPZ/PLY stay the primary path.
P4 — iOS + web parity. iOS SplatNode = thin wrapper over RealityKit GaussianSplatComponent/Resource once on the OS 27 SDK (parsing shared from KMP core — nearly free); web = port the same quad + CPU-sort technique into sceneview.js (WebGL2, no Three.js). The KMP core parser + sort is shared across all three renderers.
Perf budget (mid-range Android, prior-art numbers)
Target: ≤500k splats, SH0–SH1. 100–200k is the comfortable real-time zone; 500k is the cap with OIT and/or lower SH. Matches Marble's 500k "lite" export tier.
GPU memory: SH0 at RGBA16F ≈ ~28 B/splat in textures → 500k ≈ ~14 MB VRAM. SH coefficient counts: 0/9/24/45/72 for SH degree 0/1/2/3/4 — SH3 (45 coeffs) is prohibitive on mid-range Android; keep SH0/SH1 for P1/P2 and document the cap.
Sort: CPU radix of ~500k depth keys = a few ms on a worker, re-triggered on camera-direction delta, not per frame.
Ceiling reference: Mobile-GS reports up to 127 FPS on modern mobile GPUs with first-order SH distillation + OIT — that's the optimized academic ceiling, not what a naive CPU-sort viewer gets; treat it as the north star, not the P1 baseline.
Risks
No compute + no SSBO in Filament → CPU sort is mandatory; at 500k the sort + per-sort texture upload is the perf wildcard. Mitigate: worker thread, motion-gated re-sort, OIT fallback.
Runtime is unproven. The compile proof measures nothing about FPS. P1 must gate on a real render.
Format churn. KHR_gaussian_splatting is RC, not ratified (expected Q2 2026) → keep behind a flag. SPZ spec is stable (MIT) but the decompressor is real porting work.
65535 instances/draw → batched draws (minor, ~8 draws at 500k).
Memory: full SH is prohibitive on mid-range → SH0/SH1 only; hard count cap.
.filamat ABI invariant: any future Filament bump must recompile splat.filamat with the matching matc (existing repo rule; the proto already rides tools/GenerateFilamat.sh — add one MATS entry, Profile B -a opengl -p mobile).
Bottom line: GO-WITH-CAVEATS. The rendering approach is de-risked to the ABI/shader level today — the material compiles under matc 1.71.5 and the instanced-quad + vertex-texture-fetch + blended-gaussian path is valid without forking Filament. Ship PLY+SPZ + the proto material as P1, gated on an actual emulator render; CPU-sort and anisotropic covariance are P2; KHR glTF and iOS/web parity follow. The unproven part is runtime performance at scale, which is exactly what P1 exists to measure.

P2 design — SplatNode web (sceneview-web/, Kotlin/JS + Filament.js)
Feasibility — verified empirically (2026-07-16)
1. KMP parsers are already JS-ready — nothing to port. The 7 splat files (sceneview-core/src/commonMain/.../core/splat/) are 100% pure commonMain: zero expect/actual, imports limited to kotlin.math, gzip inflate is pure-Kotlin by design (Inflate.kt:21-28), binary reads are plain ByteArray arithmetic. The js(IR) target already exists (sceneview-core/build.gradle.kts:17-20) and sceneview-web already depends on it via api(project(":sceneview-core")) (sceneview-web/build.gradle.kts:26). The splat commonTest suite already runs on jsTest. Only the web-side wiring is missing.
2. The effective web runtime is Filament.js 1.70.2 → target MATERIAL_VERSION = 70. samples/web-demo/site/js/filament/{filament.js,filament.wasm} are byte-identical (cmp) to website-static/js/filament/ (documented v1.70.2). The npm pin filament@1.52.3 in sceneview-web/build.gradle.kts:29 only feeds the Kotlin/JS bundler — at runtime the global Filament comes from the page's <script> (the lazy-externals pattern). So the splat blob must be v70, not v71 (Android blobs, matc 1.71.5) and not v52.
3. splat.mat compiles UNCHANGED with matc 1.70.2 web profile.
```
matc(1.70.2) --version → 70
matc -p mobile -a opengl -o splat_web.filamat sceneview/src/main/materials/splat.mat → COMPILE OK (16 434 bytes)
```
All shader features used are core WebGL2/ESSL 300 es: vertex textureLod (VTF ≥16 units guaranteed), int ops, gl_InstanceID, RGBA16F + FLOAT upload + NEAREST.
4. Required embind APIs are all registered in the 1.70.2 wasm (verified via strings filament.wasm): RenderableManager$Builder + instances, Texture$Builder + RGBA16F + setImage, VertexBuffer$Builder/IndexBuffer$Builder, blendOrder, globalBlendOrderEnabled, setLayerMask, sampler MinFilter/MagFilter/WrapMode + CLAMP_TO_EDGE. None of these are bound in sceneview-web/bindings/Filament.kt yet → new externals to add (same lazy js("Filament") + unsafeCast discipline as the existing code).
Architecture (same rendering as P1 Android — same Filament engine, WebGL2 backend)
SplatNode (jsMain) following the existing Node/NodeBackend pattern: shared unit quad (4 verts POSITION FLOAT3 + 6 USHORT indices) hardware-instanced; two square RGBA16F data textures (positionScale, colorOpacity), FLOAT upload, NEAREST/CLAMP — identical texel layout as Android SplatBuffers.
Material: the same splat.mat source, compiled v70. New GenerateFilamat.sh entry with a separate pinned version — new filamentWeb = "1.70.2" in gradle/libs.versions.toml — making the web ABI invariant explicit and --check-able. Blob embedded as a base64 constant in a generated Kotlin file (sceneview-web has no resource-shipping mechanism; 16 KB → ~22 KB in the bundle, no runtime fetch, works via CDN single-file distribution).
Painter's sort: synchronous CPU sort in jsMain on the frame loop, re-sort threshold = camera moved > 1% of bounding radius (P1 parity). 8k splats ≈ ~1 ms in JS — no Web Worker needed at this scale. Index-order + full texel repack + re-upload, exactly like Android. (Dedup of the sort into commonMain = deliberate P3 follow-up; P2 does not touch Android P1 code.)
