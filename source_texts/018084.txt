Issue body actions
Preservar SDF como autoring tool extrayendo mesh para render.
Approach
Dual Contouring sobre voxel grid sparse (octree de SDF samples)
Hermite data en cada cell (intersection + normal)
QEF solver para vertex placement preciso en aristas
Output: meshlet-compatible buffers (vértices + índices) listos para Phase 1 pipeline
Cuándo
Phase 2 del roadmap, post mesh GPU-driven pipeline operativa.
Por qué importa
Preserva la identidad SDF del engine. Autoría sigue siendo CSG suave + brushes; runtime extrae mesh y lo renderiza con la pipeline state-of-the-art.
Referencias
Nick's Voxel Blog: Implementing Dual Contouring
dexyfex.com: Voxels and Dual Contouring
Dual Universe (proven shipped product con dual contouring)
godot_voxel (Zylann, MIT, github.com/Zylann/godot_voxel) — implementación de referencia
con mesher de LOD (Transvoxel) en producción; útil para el diseño de QEF solver, manejo de
Hermite data y transition cells entre niveles de LOD aunque el algoritmo base difiera
(ver nota de diseño en el epic epic(world): Phase 2.5 — Voxel + Dual Contouring hybrid pipeline (caves/destruction) #397).
Ver docs/research/stack_decisions_2026-05-02.md.
Nota (2026-09-05)
El título de esta issue ("fast-surface-nets primary + custom DC follow-up") quedó desalineado
con #614 Finding 2: para LOD sobre octree, Dual Contouring es crack-free por construcción y
Marching Cubes/Surface Nets necesita Transvoxel para lo mismo que DC no tiene que resolver.
Sigue habiendo un caso de uso real para Surface Nets (más simple, sin QEF, cuando no hace
falta preservar features/esquinas ni LOD por octree) — si esta issue se separa en dos
(extracción simple vs. extracción con LOD), hacerlo como issues nuevas en vez de forzarlo
acá. Por ahora el approach de arriba (DC puro) es el que aplica al pipeline planet-scale de
#397/#313/#614.

Re-scoped 2026-05-02 (max dep adoption):
Dos paths concurrentes para minimizar reinvención.
Path A (PRIMARY) — fast-surface-nets drop-in
Crate: fast-surface-nets v0.x (bonsairobo)
Performance: ~20M triángulos/seg single core, glam SIMD acelerado
Soporta sparse data sets — chunks fit together seamlessly (clave para nuestro chunking)
Cubre 90% del use case: caves orgánicas, terreno smooth, destrucción organic
Trade-off: pierde aristas afiladas (cliffs perfectos, cubos voxel-style). Output siempre suave
Decisión: arrancamos con esto. Ship Phase 2.5 funcional rápido
Path B (FOLLOW-UP) — Custom DC para sharp features
Si Path A nos limita en zonas con aristas (rocas afiladas, destrucción tipo voxel-cube, edificios subterráneos), agregamos DC custom
Reference para implementación: source de WilstonOreo/sdf2mesh (DC en wgpu+WGSL, slice-by-slice)
NO importar sdf2mesh como dep (es CLI tool, no library runtime)
Custom porque integración con nuestro SVO + edit pipeline es específica
Issue separada cuando llegue el momento — no bloquea Phase 2.5 inicial
LOD seams (ambos paths)
Crate: transvoxel v0.x (Gnurfos)

Adopt drop-in, NO custom
Inversa (offline asset baking)

Adopt drop-in cuando sea necesario
