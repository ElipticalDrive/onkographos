Four findings, all four on round 1's own fixes, all four valid.

R2-1 (check-context-staleness.py, Major) — `sh()` returned "" on a non-zero exit, so
`changed_files()` and `last_commit_epoch()` could not tell failure from emptiness. A bad
ref made the script print "nothing to check" and exit 0. That is the worst available
failure mode for a staleness gate: it reports the knowledge base owes nothing *because
it could not run*, and nobody notices a clean result. Round 1 actually demonstrated this
without my seeing it — the injection probe printed "Changed code files: 4" from the two
working-tree diffs while the base-dependent diff had silently failed.

`sh()` now raises `GitError` by default, with `allow_failure=True` on exactly the two
calls whose failure is legitimate: the merge-base probe (a repo with neither main nor
master) and `git log` for an untracked file (no commit is a real 0, and the caller's
`newest_code > doc_epoch > 0` already refuses to call a doc stale on it). `main()` exits
2 with a one-line reason instead of a traceback, so "KB owes nothing" (0) and "check
could not run" (2) are distinguishable by a caller. This converges on the design
sawyerdesign-io's copy of this script already used — its `allow_failure` keyword was the
right answer and worth adopting rather than reinventing.

R2-2 (check-context-staleness.py, Major/security) — argument injection surviving the
shell's removal, which is the part I got wrong in round 1. argv form stops `;` and
`$(...)`, but a `--base` beginning with `-` is still read by git as an OPTION:
`--upload-pack=touch /tmp/x` reaches `git diff` as a flag, not a revision. Now rejected
by value, and every base is additionally resolved through `git rev-parse --verify
--quiet <base>^{commit}` so a nonexistent ref fails loudly instead of becoming a false
"no changes". Added `--` to the three diff invocations so a ref that collides with a
filename cannot be reinterpreted as a path. Verified: leading-dash base exits 2 and
creates no file, nonexistent base exits 2, shell-metachar base exits 2, normal run and
merge-base fallback still exit 0, untracked doc does not crash.

R2-3 (triage SKILL.md, Major) — `reply` was missing from the category vocabulary while
both the completeness gate and the coverage table require replies to prior fixes to
appear as findings. Added, with a note that it is a category rather than bookkeeping.

R2-4 (triage SKILL.md, Major) — the real one: Phase 4 told you to cite `Fixed in <hash>`
and forbade keying a finding before its fix was committed, while Phase 5 (commit) came
afterwards. Unsatisfiable as written. I hit it in round 1 and worked around it silently
by committing before replying, which is exactly the kind of undocumented deviation that
makes a workflow rot. Phase 4 is now explicitly split: 4a replies to and resolves
REJECTED findings before the commit (their disposition is complete when written, and an
unkeyed rejection is re-litigated every round), Phase 5 commits and pushes, 4b replies
to FIXED findings with the real pushed hash and writes their ledger keys. Push, not just
commit, before 4b — a hash that exists only locally reads as done and cannot be checked.

Also closed a gap this round exposed that no reviewer raised: the autofix stop condition
checked comment counts and Greptile confidence but never `mergeable` or the check
rollup, so it could report "all clear" on a PR that GitHub calls CONFLICTING. It did
exactly that this round — PR #18 went red without anyone touching it when PR #19 merged
to main. Both are now round-triggering conditions, Phase 5 gained a mergeability step,
and the summary block reports mergeable state and check counts.

Gates: lint, typecheck, typecheck:cli, build, test:gh-parity, test:relief all pass.
sync-skills applied, .agents mirrors verified byte-identical, user-root fallback copies
updated to match.
