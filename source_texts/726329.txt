Summary
Fix RAD splats rendering as flat, opaque, tile-shaped regions in the 3DGUT Vulkan viewer. The same source splats render correctly from PLY and through the 3DGS path, but the RAD/LOD 3DGUT raster pass was reading geometry using the wrong storage layout and index space.
Cause
Projection already decodes the canonical quantized RAD page pool and resolves LOD indices correctly. The 3DGUT raster pass independently reloads geometry to evaluate pixel rays, but previously:
Read packed half-precision rotations, log-scales and opacity as ordinary fp32 arrays.
Used projected/sorted slot IDs directly as source geometry and transform indices.
Applied sigmoid opacity activation to Spark RAD opacity values and omitted LOD fade weights.
Used the ordinary Gaussian alpha kernel for high-density LOD parents.
This made the ray-evaluated splat disagree with the footprint used for tile binning, producing flat color regions with visible tile boundaries.
Changes
Decode both ordinary fp32 attributes and the existing quantized RAD pool through byte-addressed buffers. Match projection's scale clamp and safe quaternion normalization.
Resolve physical geometry indices through the same CPU/GPU LOD index streams used by projection. Use logical indices for node transforms while keeping projected colors indexed by render slot.
Bind the existing LOD indices, logical indices and fade weights to both 3DGUT raster variants, including the path with selection overlays disabled.
Pass the existing quantized-pool page-size field to rasterization instead of introducing another storage format or uniform flag.
Decode Spark RAD opacity, apply LOD fade weights, and evaluate high-density parent opacity with the existing Spark alpha function.
Match the expanded GUT/Spark parent support between projection and tile-key generation so parent kernels are not clipped at tile boundaries.
The fix reuses existing GPU buffers. It adds no per-splat allocation, scene copy or CPU readback to the rendering path. No export formats or UI/preferences are changed.
Reproduction and regression coverage
The new generated-fixture GPU test imports anisotropic colored splats from PLY, converts them to RAD through the application CLI, then compares actual viewport pixels at the same camera position.
Coverage includes:
One splat and three splats with distinct colors, rotations and opacity values.
Native and Portal rendering profile settings for RAD.
Selection overlays enabled and disabled.
Coarse LOD cuts with high-density parent kernels, compared with the existing 3DGS path.
4097 leaf splats in an 8112-node RAD hierarchy spanning four resident pages, exercising geometry indices beyond the first page and odd/even packed opacity entries.
On the previous build, the single-splat comparison fails with a mean absolute RGB error of 29.8695/255; the three-splat case fails at 8.5101/255. After this fix:

Thanks a lot, Francesco! This fixes the RAD tile artifacts in 3DGUT properly. I verified it on Linux (RTX 4080, Release):
The new GPU test fails on the base (mean error ~25/255), and all 9 cases pass on the branch. The 18 renderer contract tests pass too.
Viewport captures of a garden scene (1M splats, converted to RAD with the CLI), 3 views:
RAD in 3DGUT used to render as flat tile blocks, at 14 dB PSNR against the source PLY. It is now at 32–35 dB.
It is also 35–38 dB from RAD in 3DGS with the same LOD cut, and the difference image shows no tile structure.
Ordinary PLYs in 3DGUT and RAD in 3DGS are bit-identical to master.
I found one speed cost for ordinary scenes: choosing between the Spark and ordinary evaluators inside the inner raster loop made 3DGUT rasterization 3.9% slower on a 5M-splat PLY with no RAD loaded (8.23 → 8.55 ms, mean of 3 × 500 frames). Reverting just that line restored the time. A [branch] hint did not help, so the cost comes from compiling the Spark kernel into the ordinary loop.
I hope you don't mind that I pushed a follow-up commit to your branch (ca57959) so we can merge:
Separate RAD variants: Spark RAD scenes get their own 3DGUT raster variants (rasterize_forward_3dgut_rad, rasterize_forward_3dgut_plain_rad), chosen when the Spark opacity LOD flag is set. The ordinary variant compiles without the RAD path.
One shared evaluator:
The ray math is computed once.
RAD leaves (opacity ≤ 1) blend like ordinary splats, because there the Spark cutoff only removes alpha below the blend threshold.
Only LOD parents take the Spark kernel.
