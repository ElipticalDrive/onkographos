This PR introduces a basic rigging mechanism for GaussianSplatting meshes.
When rigging is enabled, each splat gets an extra attribute that stores its rig node index (in an extra texture). For each rig node, a transform matrix is provided. This transform matrix replaces the model matrix of the GaussianSplattingMesh in all transforms computations, including the rendering shaders (through a new uniform) and the sorting worker.
This is only "basic" in the sens that it only allows for a single rig node to influence a given splat, meaning it can only do rigid deformation (no skinning weights, no bending). It is nonetheless quite useful already when one wants to mix multiple GSplat meshes within the same scene while ensuring proper global sorting of the splats.
This repository shows an example of how to use this rigging mechanism to load multiple GSplat Meshes and move them around. Under the hood the demo uses a single GaussianSplattingMesh object in which all GSplats are merged. Individual GSplat objects are replaced by empty placeholder meshes from which the model matrix is used to drive the rig.
Points that need proper review:
This is my first significant contribution to Babylon.js, I might have missed obvious things.
The WGSL version of shaders was automatically ported from the GLSL one by an LLM.
The performance overhead has not been properly benchmarked. Hopefully, there is none as long as the rig mechanism is disabled.
The rig texture uses Uint32 but Uint8 might be largely enough (meaning the rig would be limited to 256 nodes). The rest of the bits could eventually be used to provide a second rig node and skinning weights if we want to move on towards a more advanced rigging behavior.
NB: Modifications to loader/package.json are only temporary and meant to help building the example by pointing at my dev version of Babylon.js (could not find another way to do it). Modifications to packages/dev/buildTools/tsconfig.json come from #17678

I wonder if adding an incomplete implementation of bone/rig support to gsplat isn't a bit premature... We might get stuck later if we want to improve it, because we won't be allowed to make breaking changes, and I don't know if that will be possible or not.
As it stands, the implementation can't really be used for skeletal animations, because it only supports a single “bone” and no weights. I don't think many people (if any) will use it for that purpose. In a real implementation, we will probably want to leverage our Bone and Skeleton classes in some way.
In fact, the goal of the PR is to be able to (optionally) associate a specific (world) matrix with an individual splat, and perhaps the implementation should stick to that goal?
Another concern is that moving/rotating gsplats that have been merged into a single final gplat is not very user-friendly, as it is up to the user to generate the final global matrix (so the user can't simply update some gsplat.position or gsplat.rotation properties)... It would be preferable to keep the original gsplats, so that they can be manipulated as usual via their position/rotation/scale properties. Perhaps we could have a gsplat container (which would also be a gsplat mesh). We would add the gsplats to be merged into this container. When the “merge” method is called on the container, all merged data is associated with that container and is removed from the merged meshes so that they are not rendered by themselves: only the container should be rendered.
These are just my thoughts, please take them with a grain of salt!
You should probably discuss this with @CedricGuillemet, who will know better than me what to do.

After some thought I am not 100% sure I see what the API would look like. A problem I see if parts remain individual GaussianSplattingMesh objects is that notable parts of the API no longer make sense. It would not make sens to deactivate depth sort for one part and not the other, would not make sense to get attribute textures since the only attribute textures would be the merged ones, would be a pretty different code path to render only one part, etc.
One possible trade-off is to implement the GaussianSplattingMeshAssembler as part of the GaussianSplattingMesh, and the only API change is that we add a addPart(other: GaussianSplattingMesh) that returns a GaussianSplattingMeshPart (that is more or less a TransformNode). Other new methods introduced by this PR, like setNodeIndex() or setWorldMatrixForNode(), etc. become private.

```
…rts (BabylonJS#17679)

This PR introduces a basic rigging mechanism for GaussianSplatting
meshes.

**When rigging is enabled**, each splat gets an extra attribute that
stores its **rig node** index (in an extra texture). For each rig node,
a **transform matrix** is provided. This transform matrix replaces the
model matrix of the `GaussianSplattingMesh` in all transforms
computations, including the **rendering** shaders (through a new
uniform) and the **sorting** worker.

This is only "basic" in the sens that it only allows for a single rig
node to influence a given splat, meaning it can only do rigid
deformation (no skinning weights, no bending). It is nonetheless **quite
useful already** when one wants to mix multiple GSplat meshes within the
same scene while ensuring **proper global sorting** of the splats.

[This repository](https://github.com/eliemichel/Babylon-Rigged-GSplat)
shows an example of how to use this rigging mechanism to load multiple
GSplat Meshes and move them around. Under the hood the demo uses a
single `GaussianSplattingMesh` object in which all GSplats are merged.
Individual GSplat objects are replaced by empty placeholder meshes from
which the model matrix is used to drive the rig.

**Points that need proper review:**
- This is my first significant contribution to Babylon.js, I might have
missed obvious things.
- The WGSL version of shaders was automatically ported from the GLSL one
by an LLM.
- The performance overhead has not been properly benchmarked. Hopefully,
there is none as long as the rig mechanism is disabled.
- The rig texture uses Uint32 but Uint8 might be largely enough (meaning
the rig would be limited to 256 nodes). The rest of the bits could
eventually be used to provide a second rig node and skinning weights if
we want to move on towards a more advanced rigging behavior.

NB: Modifications to `loader/package.json` are only temporary and meant
to help building the example by pointing at my dev version of Babylon.js
(could not find another way to do it). Modifications to
`packages/dev/buildTools/tsconfig.json` come from BabylonJS#17678
```
