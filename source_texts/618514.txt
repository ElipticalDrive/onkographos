First half of Stage 3. An OptiX pipeline builds an acceleration structure from the same flat arrays the CPU renderer uses and traces against it, so ray/box and ray/triangle work lands on the fixed-function hardware. Nothing shades yet — that is the second half.
Traversal is where the CPU renderer spends its time (the dragon: 658 box visits per ray against 87.5 triangle tests), and box traversal is exactly what RT cores do. So it is the part worth getting right first, and worth verifying on its own before any shading is layered on top.
Shape of it
OptiX in its simplest useful form: one raygen program, one miss program, one hit group per primitive kind, and hit groups that report a distance, a pair of barycentrics and an index — nothing else. The shader binding table records carry no data at all; everything the programs read comes from the launch parameters. That avoids nearly all of the machinery that makes OptiX look forbidding.
Triangles use OptiX's built-in intersection, so the hardware does the work.
Spheres are custom primitives with an intersection program mirroring Geometry::intersectSphere — including its refusal to reject on tca < 0, since a ray originating inside a sphere still has a valid forward hit. Using OptiX's built-in sphere would mean a second implementation of something this project already has, and the two would agree right up until one was changed. A structure cannot mix primitive kinds, hence two of them under one instance array.
Device code is compiled at runtime by NVRTC, so its source has to travel with the binary. It is embedded at build time rather than read from disk, so a built renderer doesn't depend on the checkout it came from. Only the OptiX headers come from the filesystem via an include path, since they're a fetched dependency already.
Is it correct?
Checked the same way the CPU hierarchy was — against a reference already trusted. device_traversal fires identical rays at both backends. Seven scenes, 200,000 rays each, from three primitives up to the dragon's 202,522 triangles:
hit/miss disagreements
0
wrong primitive reported
0
worst distance difference
1.3e-4 relative
Exact agreement is neither expected nor asked for: OptiX uses its own watertight triangle algorithm on different hardware, and a ray grazing a shared edge may legitimately go to either triangle. A systematic disagreement would be a defect — so I checked the test has teeth by deleting the offset that maps sphere indices into the shared numbering. That makes 6.7% of hits report the wrong primitive, 130× the threshold.
Speed, stated carefully
Traversal alone, against a single CPU thread:
Scene
GPU
CPU (1 thread)
cornell_box
174 M rays/s
9.2 M rays/s
dragon
240 M rays/s
7.2 M rays/s
The number worth noticing isn't the ratio. It's that the GPU is faster on the dragon than on the Cornell box while the CPU is slower — the RT cores absorbing exactly the traversal breadth the CPU cannot. What this is worth to a finished image is the next stage's question, and it will be answered by rendering one rather than by scaling these.
Two smaller things
The primitive records move from Geometry.h into Primitives.h. The container needs std::vector and is host-only for that reason; the records themselves have to exist on a device.
setup-gpu-deps.sh now takes the whole of cudart's include directory rather than a hand-picked pair of headers. OptiX 9.1's device headers include cuda_fp16.h, which drags in its own companions, and naming the closure by hand is always one header short of working. 4.1 MB either way.
Verification
All thirteen scenes still render byte-for-byte identical images on the CPU.
22 tests pass without GPU support, 30 with it.
.cu files are now covered by scripts/format.sh and by CI — device code is the one part no compiler in the workflow parses, so nothing else would notice it drifting.
Release, Debug, viewer, headless and GPU builds all clean.
Next
The ported path loop: Integrator::radiance as a raygen program, a dedicated occlusion trace for shadow rays, device buffers for materials and lights, and --device cpu|gpu. Its gate is the furnace test passing on the GPU and deterministic GPU output before any speedup is claimed.
