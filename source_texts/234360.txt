1. splat-transformをformat conversion layerとして採用
当初はSceneSync自前でPLY reader / SPZ reader / 中間表現 SplatCloud / KHR GLB writer を実装していたが、
3DGSのcodecを保守し続けることはSceneSyncの目的ではなく、実際に渡される形式も増え続けている
（Insta360 AppはSOG、XGridsはLCC2を出力する。どちらも自前実装では読めなかった）。
変換を丸ごと @playcanvas/splat-transform に任せ、SceneSync側にはparser / encoderを一切残さない。
```
.ply / .spz / .sog / .lcc2 / .lcc / .splat / .ksplat / .zip
        ↓
@playcanvas/splat-transform      ← フォーマット変換はすべてここ
        ↓
KHR_gaussian_splatting GLB       ← SceneSyncの交換形式
        ↓
inspectGaussianSplatGlb()        ← 通す前に検証
        ↓
SceneSync既存GLB経路（upload / broadcast / asset cache / SceneDocument / Export）
```
.glb（KHR拡張付き）は検証のみでバイト列をそのまま通す。splat-transformにGLB readerは無いので再変換しない。

4. 向きが既定で正しくなった
splat-transformはGLB出力時にY-down PLY → Y-up glTF の標準変換を焼き込む。旧writerはこれをしていなかった。
```
PLY (1, 2, 3)  →  GLB POSITION (-1, -2, 3)
```
upAxisCorrection: 'flip-x-180' は残しているが、splatデータは書き換えず glTF node の rotation として書く方針も維持。
Editorに専用UIは追加せず、上下が逆なら既存のTransform gizmoで直す。
5. ASCII / big-endian PLY は明示的に拒否する
splat-transformのPLY readerはヘッダの宣言に関係なくレコードをlittle-endian binaryとして読むため、
ascii / binary_big_endian を渡すとエラーにならずゼロ値のsplatになる。
3DGSの学習結果は例外なく binary_little_endian なので実害は無いが、黙って空のシーンを取り込むと原因が分からない。
ヘッダを見て事前に弾く。
6. ブラウザへの配り方（vendor bundle）
静的配信なのでブラウザで import '@playcanvas/splat-transform' は解決できない。CDNには逃げず、
build時にbundleして html/assets/vendor/ にコミットする（Rapier / Loomletと同じ方式）。

7. Worker経路
```
main thread                          worker（vendor bundle）
  file.arrayBuffer()
  ── postMessage(transfer) ────────→  convertGaussianSplatToGlb()
  ←── postMessage(transfer) ────────  glb
  new File([glb])
  worker.terminate()
```
Workerが作れない場合（module worker非対応、CSPの worker-src）は同じbundleを import() してメインスレッドで変換
中止は worker.terminate()。splat-transformに協調的キャンセルは無いため、chunk pool / decoder state / 出力バッファをまとめて捨てられるこれが最も確実
GLBは MemoryFileSystem の可変長スラブ上のviewで返るので、postMessage前にexactサイズへ詰め直してからtransferする

「constant memory」ではない。 splat-transformのreaderはchunk単位で読むが、GLB writerにはまだstreaming版が無く、

```
SceneSync's interchange representation for Gaussian Splats is a GLB carrying
KHR_gaussian_splatting. This adds the import side: .ply and .spz captures are
decoded and normalized to that GLB, so everything downstream only ever sees
GLB.

New under html/assets/js/scenesync/loaders/gaussian-splat/:

- splat-cloud.js         intermediate representation, in KHR conventions
- ply-splat-reader.js    INRIA 3DGS PLY (binary LE/BE and ascii)
- spz-splat-reader.js    Niantic SPZ v1-v3
- khr-glb-writer.js      SplatCloud to KHR GLB
- import-gaussian-splat.js  format sniffing entry point

No external dependencies; runs in Node and the browser alike.

Activations are applied at read time so the writer stays conversion-free:
PLY log scales are exponentiated, opacity logits go through a sigmoid, and
wxyz quaternions are reordered to xyzw and normalized. Higher order SH is the
subtle part, since PLY stores f_rest channel-major while KHR splits it into
one accessor per coefficient.

Coordinate systems are deliberately left alone by default. Neither format
records which way is up, so guessing would break correctly-oriented assets.
The optional flip is written as a glTF node rotation, leaving splat data
byte-faithful and the correction reversible.

Ambiguous inputs fail with a named reason rather than importing as a
degenerate cloud: plain point clouds, compressed SuperSplat PLYs, list
properties, sparse f_rest, unsupported SPZ versions and truncated files.

Tested with 47 Node tests, including a cross-format check that the same scene
encoded as PLY and as SPZ decodes to matching values within quantization
error, which exercises both decode paths against each other.

Also adds scripts/convert-gaussian-splat.mjs so captures can be converted
before the drag & drop UI lands, and a 16 splat degree 1 SH fixture in all
three formats.

Dropping a .ply or .spz on the SceneSync editor now converts it to a
KHR_gaussian_splatting GLB and hands it to the existing GLB path, so upload,
broadcast, asset cache and SceneDocument need no 3DGS-specific case.

The conversion lives in gaussian-splat-file-import.js rather than in
DragDropManager, because drag-drop-manager.js imports three (loaded from a CDN
importmap, absent from package.json) and so cannot be imported in Node. Keeping
the logic in a dependency-free module makes it testable.

Failures are reported with a reason the user can act on: a plain point cloud
PLY, a compressed SuperSplat export and an unsupported SPZ version each get
their own message rather than a generic load failure. Files above the presence
server's upload limit are rejected before being read.

The object keeps the dropped file's name for display while the GLB is what
gets uploaded; the original is recorded in userData.importedFrom.

On the r170 three.js currently pinned in index.html the converted GLB parses
cleanly into THREE.Points and shows as a 1px white point cloud at the correct
position and scale, verified against three@0.170.0. Proper splat rendering
still waits on a three.js release with Gaussian Splatting, at which point the
same GLB renders correctly with no re-import.

Run Gaussian Splat conversion in a Worker and cut write cost
…
100282a
```
Benchmarking the importer at realistic capture sizes showed a million splats
at SH degree 3 taking 4.4s and peaking at 2.7GB, which would freeze the editor
and crowd a browser tab's memory ceiling. Two changes follow from that.

Conversion now runs in a module Worker, with the source buffer transferred in
and the GLB transferred back so neither crosses the boundary twice. Workers
are not always available -- module worker support and a CSP that permits
worker-src are both required -- so an inline fallback keeps the drop working.
The fallback re-reads from the File rather than pre-emptively copying the
source, which would otherwise double peak memory on every import for a path
that almost never runs. A failure caused by the file itself is not retried
inline, since it would only reproduce.

The GLB writer no longer materializes each SH coefficient. buildSplatAttributes
returns a write callback per attribute and the payload is allocated once and
written in place, removing fifteen 12MB temporaries and a full copy at degree
3. Write time for a million splats drops from 3450ms to 2444ms.

Adds scripts/benchmark-gaussian-splat-import.mjs, which releases its synthetic
splat objects before measuring so the numbers reflect what the browser holds.

Tested with 81 Node tests. The worker client is covered with a stub Worker,
and the worker module itself is exercised through a self shim so the message
contract is verified rather than assumed.

Add maxShDegree to trade spherical harmonics for size
…
782b7f7
```
SH degree, not splat count, is what sets import size: degree 3 carries 45
floats per splat against 3 at degree 0. maxShDegree drops bands above a given
degree at read time, so the intermediate cloud shrinks along with the GLB.

At 500k splats from a degree 3 PLY the GLB goes 112.5MB at degree 3, 72.5MB at
2, 43.9MB at 1 and 26.7MB at 0. The source buffer is still held, so resident
memory does not fall proportionally.

The default keeps every band. Reduction is lossy in a way worth being explicit
about, which corrects an assumption this work was carrying: the spike notes
recorded that Three.js ignores SH1-3 and that starting from SH0 was therefore
free. Reading GaussianSplat.js shows otherwise -- createSphericalHarmonicsComputeNode
evaluates the higher bands against the view direction, so dropping them changes
how a splat looks as the camera moves. The spike doc now carries that correction.

SPZ needed care: its SH section is sized by the header, so a truncated read has
to stride over the source layout rather than copy a flat prefix. The tests
check the second splat specifically, which is what catches getting that wrong.

Reduced output still satisfies Three.js's requirement that SH bands be complete
and contiguous, since degrees 1..n are always kept. The verification script now
covers reduction to degree 2, 1 and 0 alongside the existing cases, and all
eight pass against Three.js dev.

Delegate 3DGS format conversion to @playcanvas/splat-transform
…
7144dc1
```
SceneSync had grown its own PLY reader, SPZ reader, SplatCloud
intermediate and KHR GLB writer. Maintaining a 3DGS codec is not what
SceneSync is for, and the formats people actually hand us keep
multiplying — Insta360 exports SOG, XGrids exports LCC2, neither of
which we could read.

Hand the whole job to @playcanvas/splat-transform (MIT), behind one
adapter. SceneSync's remaining share is: recognise the drop, normalize
it to a KHR_gaussian_splatting GLB, validate that GLB, and push it down
the ordinary GLB path. No format parser or encoder is left in the tree.

  .ply .spz .sog .lcc2 .lcc .splat .ksplat .zip
      -> splat-transform -> KHR GLB -> existing GLB path

Notable consequences:

- Positions now come in the right way up. splat-transform bakes the
  standard Y-down PLY to Y-up glTF conversion, which the old writer did
  not. upAxisCorrection stays, still as a node rotation rather than a
  rewrite of the splats.
- ASCII and big-endian PLY are refused. splat-transform's reader decodes
  every record as little-endian whatever the header says, so those would
  otherwise import as a scene full of zeros. Every trainer writes
  binary_little_endian.
- LCC2 is a directory, so it is dropped as a zip; the archive's manifest
  decides the format. SceneSync export zips still reach their own
  importer first.
- 1M splats at SH degree 3 now peaks around 1.5 GB rather than 2.5 GB.
  It is not constant memory: the GLB writer has no streaming path yet
  and materializes the scene once, so peak tracks the output size.

The library cannot be bare-imported from a static site, so the build
bundles it into html/assets/vendor/ alongside Rapier and Loomlet, at a
version pinned exactly in package.json. The build strips the SuperSplat
viewer that splat-transform embeds for its html output (3 MB of
PlayCanvas engine SceneSync never runs), asserts each rewrite still
matches, and refuses to finish unless the bundle it just produced
converts all four fixture formats.

Verified against three.js's own GLTFGaussianSplatLoaderExtension: PLY,
SPZ, SOG and LCC2 all load as GaussianSplat with matching positions,
colors and SH bands. The Worker path is exercised in Chromium, webp.wasm
included.

Fix the drop path and Worker fallback for splat captures
…
f9e2a83
```
Three problems found in review of the splat-transform migration.

A zipped LCC2 capture could not actually be dropped on the editor. Every
ZIP is offered to the Scene Sync Export importer first, and that importer
claimed ZIPs it could not read — a capture archive got "this ZIP is not a
Scene Sync Export" and never reached the converter. It now declines a ZIP
with no scene.json and lets the drop continue; a ZIP that *has* a
scene.json, broken or not, is still its own. There is now a test through
DragDropManager.handleFile() rather than only through the converter, so
the dispatch order is covered where it actually lives.

One corrupt file could also demote the rest of the session to main-thread
conversion. splat-transform throws ordinary Errors for a truncated SPZ or
a broken archive, and only UnsupportedSplatInputError was recognised as
the file's fault, so those were read as Worker trouble: the same bad file
was converted again on the main thread and the Worker was switched off
for good. Cancelling did the same thing — an abort started a main-thread
conversion of the work just cancelled. What matters is whether the Worker
answered, not what it answered, so that is what the code now asks.

maxShDegree took any number. Trimming only runs when the cap is below the
file's own degree, so 4 or 99 read as "keep everything" — the opposite of
the size reduction asked for, with nothing to explain it. Out of range is
now a RangeError.

```
* feat(scenesync): handle KHR_gaussian_splatting GLB in Unity/Godot

Scene Sync の 3DGS 交換形式である KHR_gaussian_splatting GLB を、Unity 版 /
Godot 版でも Editor / Runtime の両方で扱えるようにする。各エンジンに形式ごとの
parser は持たせず、SceneSync Web が正規化した GLB を受け取って描画へ回す。

3層構成（Unity / Godot 共通）:

- 検出: GLB の JSON chunk を読んで KHR_gaussian_splatting を判定。判定規則は
  Web 実装 khr-gaussian-splatting.js と同じ（POINTS mode / 必須 attribute /
  extensionsUsed 宣言は error、未知の kernel 等は warning）
- 振り分け: 差し替え可能な backend（UnitySplats / godot-gsplat 想定）へ渡す。
  未登録なら依存ゼロの点群プレビューへ落とす
- 描画: backend 側

Editor:

- Unity: GameObject > Scene Sync > Import Gaussian Splat GLB... と
  [ExecuteAlways] な SceneSyncGaussianSplatSource。シーンを開いた時点で
  Scene View に表示され、Play モードへ入る必要がない
- Godot: Project > Tools のメニュー（Undo/Redo 対応）と @tool の
  SceneSyncGaussianSplatNode3D。視覚ノードは保存せず参照から再構築する

Runtime:

- Unity: DownloadAndCreateObject と LoadGlbFromBytes で分岐。ImportedGlbRoot
  構造・transform・visibility・physics/Loomlet metadata の扱いは通常 GLB と同じ
- Godot: import_glb() で分岐。通常 mesh と混在する GLB では mesh 側も従来経路で
  読み込んで同じ親に付ける

renderer 本体は同梱していない。backend の登録口だけを持つため依存は増えていない。

Tests: godot/tests/test_gaussian_splat_glb.gd（88 assertions、run_all.sh に追加）、
unity/.../Tests/Editor/SceneSyncGaussianSplatGlbTests.cs
