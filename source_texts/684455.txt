CloudFront Edge Caching for Public USGS 3DEP Lidar EPT Data
This document describes the successful setup of a new AWS CloudFront distribution to efficiently cache and serve public USGS 3DEP Lidar EPT (Entwine Point Tile) data. The primary goal was to leverage CloudFront's global edge network for fast, cached delivery.
1. CloudFront Distribution Setup
A new CloudFront distribution (e.g., dsg9qw31ql1tp.cloudfront.net) was created to serve the Lidar EPT datasets.
1.1 Origin Configuration
Two S3 origins were configured to provide both a potential user-controlled cache and access to the primary public data source:
Public USGS Lidar S3 Bucket (Primary Data Source):
Origin Domain: usgs-lidar-public.s3.us-west-2.amazonaws.com
Origin Path: Left blank (the EPT data paths are relative to the root of this bucket).
Grant CloudFront access to origin: Set to No (as this is a publicly accessible S3 bucket).
Rationale: This origin directly provides the source Lidar EPT data.
Private User S3 Cache Bucket (Optional Primary Cache):
Origin Domain: endolith-usgs-lidar-pointclouds.s3.us-west-2.amazonaws.com (replace with your bucket name)
Origin Path: Left blank.
Grant CloudFront access to origin: Configured with Origin Access Control (OAC) to securely allow CloudFront to read from this private S3 bucket.
Rationale: This bucket acts as a potential first-check point. If desired, this bucket could be manually or programmatically pre-populated with frequently accessed data. CloudFront itself does not automatically write data into this origin.
1.2 Origin Group for Failover
An Origin Group was created within the new distribution to manage how CloudFront fetches content:
Primary Origin: The Private User S3 Cache Bucket.
Secondary Origin: The Public USGS Lidar S3 Bucket.
Failover Criteria: Configured to failover on 403 Forbidden and 404 Not Found responses from the primary origin. This ensures that if the requested EPT file is not present in the private cache bucket, CloudFront automatically fetches it from the public USGS source.
1.3 Default Behavior Configuration
The Default Cache Behavior (Default (*)) of the new CloudFront distribution was set to point to this newly created Origin Group. This means all incoming requests to the distribution's root path will attempt to retrieve data via this failover mechanism.
2. Implementing Long-Term Edge Caching
To ensure maximum performance and reduce repeated fetches from the USGS origin, a custom CloudFront Cache Policy was created and applied.
2.1 Custom Cache Policy Creation (LongDurationLidarCache)
A new custom Cache Policy was created with the following key settings:
Name: LongDurationLidarCache
Description: "Assuming USGS S3 bucket is only ever added to, not modified."
Default TTL (Time To Live): 31536000 seconds (equivalent to 1 year). This is the crucial setting that determines how long CloudFront will keep an object in its edge cache by default.
Minimum TTL: 0 seconds
Maximum TTL: 31536000 seconds (1 year)
Cache Key Settings (Headers, Cookies, Query strings): All set to None. This ensures that CloudFront treats different requests for the same path as identical for caching purposes, maximizing the cache hit ratio for static files.
Compression Support: Gzip and Brotli Enabled.
2.2 Applying the Cache Policy
The LongDurationLidarCache custom policy was then attached to the Default Cache Behavior (Default (*)) of the CloudFront distribution.
3. Outcome and Performance Improvement
Successful Content Delivery: The CloudFront distribution now successfully fetches Lidar EPT data, correctly stripping any path prefixes, and delivers it to viewers.
Significant Speedup: Due to the LongDurationLidarCache policy, EPT data is cached at CloudFront's global edge locations for up to one year. Subsequent requests for the same data are served directly from this high-speed edge cache, leading to a dramatic improvement in access times.
Private S3 Cache: The private S3 bucket continues to function as a primary origin in the failover group. While CloudFront does not automatically write data into it, it serves as an option for you to manually or programmatically pre-populate for specific use cases.
4. Monitoring Cache Performance
While CloudFront doesn't provide a direct "total bytes cached" metric, you can monitor the effectiveness and volume of cached data via:
CloudWatch Metrics: In the AWS CloudWatch console, navigate to CloudFront > Per-Distribution Metrics for your distribution. The CacheHitRate metric provides the percentage of viewer requests that were served directly from the CloudFront cache, indicating caching efficiency.
CloudFront Access Logs: By enabling logging for your distribution, you can analyze the x-edge-result-type field in the logs (e.g., Hit, Miss) to gain detailed insights into cache behavior for individual requests.

CloudFront Edge Caching for Public USGS Lidar Data: Successful Setup
This document describes the successful configuration steps to enable long-duration caching of public USGS 3DEP Lidar EPT data using CloudFront's edge cache.
Goal
To serve ept.json files from the public USGS S3 bucket via CloudFront, ensuring very fast access for repeat requests by caching them at CloudFront's global edge locations for an extended period.
Successful Changes
Created a New CloudFront Distribution:
A fresh CloudFront distribution (dsg9qw31ql1tp.cloudfront.net) was created to ensure standard behavior, bypassing an anomalous path-stripping issue observed in a previous distribution.
Origin Configuration:
Origin Type: S3 bucket
Origin Domain: usgs-lidar-public.s3-us-west-2.amazonaws.com (Direct endpoint to the public USGS S3 bucket).
Origin Path: Left blank.
Grant CloudFront access to origin: No (as the USGS S3 bucket is public).
Other Origin Settings: Used recommended defaults (e.g., connection attempts, timeout).
Default Cache Behavior:
The distribution's default behavior (Default (*)) was configured to point directly to this usgs-lidar-public S3 origin.
Security Protections (WAF): None (for initial setup and public data).
Created a Custom Cache Policy for Long Duration Caching:
A new custom Cache Policy named LongDurationLidarCache was created.
Purpose: To explicitly instruct CloudFront to cache content from the USGS S3 origin for a very long time at its edge locations.
Key Settings:
Default TTL (seconds): 31536000 (1 year)
Minimum TTL (seconds): 0
Maximum TTL (seconds): 31536000 (1 year)
Cache Key Settings (Headers, Cookies, Query strings): All set to None. This maximizes the cache hit ratio for static EPT files by ensuring that variations in viewer requests for these items do not create separate cache entries.
Compression Support: Gzip and Brotli Enabled (for efficient data transfer).
Attached the Custom Cache Policy to the Default Behavior:
The LongDurationLidarCache policy was attached to the Default (*) behavior of the new CloudFront distribution (dsg9qw31ql1tp.cloudfront.net).
This action initiated a CloudFront distribution deployment.
Outcome
Upon deployment completion, requests to the new CloudFront distribution for EPT files (e.g., https://dsg9qw31ql1tp.cloudfront.net/AK_BrooksCamp_2012/ept.json) now work correctly and are significantly faster.
CloudFront is now successfully:
Stripping the initial path (e.g., dsg9qw31ql1tp.cloudfront.net/AK_BrooksCamp_2012/ept.json results in a request for /AK_BrooksCamp_2012/ept.json to S3).
Fetching content from the public USGS S3 bucket.
Caching that content at its edge locations for up to 1 year, leading to high-speed subsequent accesses.
Note: The user's private S3 bucket (endolith-usgs-lidar-pointclouds) and the origin group were not part of this final successful configuration for direct caching, as the primary goal was met by directly caching from the public USGS S3 bucket with a long TTL.
