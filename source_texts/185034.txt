Summary / Resumen
Sandbox voxel games provide players with an interesting challenge while at the
same time giving them lots of freedom to do what they want.
However, a lot of these games have very locked featuresets and require tooling
created by the community to expand on this content. This often means extracting,
modifying and deobfuscating binaries to be able to add hooks and events, and
results in major breaking changes every time the game is updated.
The goal of this project is to develop one such game, but placing the focus on
creating simple yet flexible APIs that are designed for third parties to use. The
game’s own content should also make use of these APIs to prove that they are in
fact usable.
The move to modern graphics APIs has been very slow, and very few of these
games support them, with most focusing on OpenGL and maybe DirectX 11. They
are often limited to specific platforms as well, reducing the pool of players they
could draw attention from.
One of the core objectives is to support Vulkan, a next generation rendering API
with a focus on performance and optimization. It is however important not to rely
on it directly, and allow for other rendering APIs to be used depending on the
context, such as in other platforms.
Keywords: videogames, game engines, rendering, vulkan, voxel, API design

Chapter 1
Introduction: The Game That
Could Have Been
Making a game is no easy task, and it becomes orders of magnitude more difficult
if building a custom engine and tooling in-house. There are often hundreds if not
thousands of moving pieces that constantly need to interact with one another to
create the experience that the game’s developers aimed for, and as such game
development is not to be taken lightly.
Even simple ideas can amount to a massive time investment, and it is very easy for
scope creep to drive a developer into overtime on something that could have been
completed much faster had certain restrictions been established from the start.
While this project may be used to exemplify good systems and API design techniques, it also serves as a great example of not-so-good preproduction and planning,
lack of prior research (although intentional), scope creep, and the effects of burnout.
I think the first question that needs to be answered is why this project exists in
the first place, and it comes down to a few reasons:
• Familiarity with the genre (voxel sandbox - see: Minecraft)
• The desire to learn about new graphics technologies (Vulkan)
• Investigating the design principles behind open-ended APIs that manage
to retain a high level of concreteness
• An interest in modding as a first-class citizen: implementing the game’s
content using only the public-facing API
With those as the main set of goals, the project was divided into three: Platform
Bindings, Engine and Game.
The platform-specific code would be developed first and provide an abstraction
for anything that may be different across runtimes, such as window management,
rendering, user input and audio. This would then act as the base to build the voxel
engine, which would be developed in parallel with the game, the latter acting as a
large scale integration test.

Out of these, the ones we will focus on the most will be the engine and game.
However, it is still interesting to elaborate on some of the design decisions made
when creating the platform-specific code, as its abstractions had to be designed to
fit virtually any backend possible, even if only one is implemented at the time of
writing.
This document will act as a post-mortem of sorts, going over most of the systems

Subsequently, it will explore the development timeline to give better context as to

I hope it will be an interesting read and that you might get a thing or two out of it.

Chapter 2
Objectives
The main goal of this project is to develop an engine for games with heavy
voxelization (terrain, logical clustering, networking/persistence) and to create a
game that utilizes it and shows off its capabilities.
2.1
Functional Goals
The main things this project tried to achieve from a technical and design point of
view are the following:
• Developing a framework for cross-platform 3D application development
• Supporting at least one modern graphics API
• Creating a toolkit specifically geared towards the creation of voxel games
with a lot of the optimizations that this constraint allows for
• Making a game that serves both as an example of the engine’s capabilities,
and as an integration test for the systems and APIs provided by it
• Developing a public-facing API and providing third-party developers with
the tools they need to create their own content for the game
• Relying exclusively on the modding API to add all the content of the game
2.2
Functional Non-Goals
When developing a project it is always important to decide not only what is to be
achieved, but also what is to be avoided. In this case:
• Supporting multiple platforms by the established deadline (future work)
• Targetting multiplayer experiences as the core of the engine
• Developing a complete game with a compelling amount of content

Terminology
3.1
General Terms
AABB: Axis-aligned bounding box. A cuboid that is aligned to the axes of the
world and represents a positive (or sometimes negative) space.
Blittable Type: A data type whose instances are stored as a contiguous block of
memory without referencing any other objects.
Mod: Shorthand for modification.
Modding: The action of creating mods.
Nibble: 4 bits, or half a byte.
Octree: A tree data structure where each inner node divides into a cluster of
2x2x2 (8) child nodes. They generally have limited depth, and if all the child
nodes of any given inner node contain the same data, they may be represented
just by this parent node without taking up extra space. They are generally
used to reduce the footprint of heavily repetitive data in 3D space.
Quadtree: The same as an octree, except used to represent 2D data instead of
3D.
Ray Casting: A technique by which it is possible to calculate the closest point of
intersection between a ray (defined by its start and end positions, or a start
and magnitude vector) and some arbitrary geometry.
Serdes: Serializer-deserializer. A process that can convert objects into bit streams
and back.
Unmanaged Type: Blittable type.
Voxel: A cubical unit of space.

Chapter 3. Terminology
Videogame / Game Development Concepts
Game Engine: An optional piece of code that provides a game developer with
tools to create their game, from graphics to physics and audio, all the way to
networking and data persistence.
Game Loop: The part of a game’s code that executes repeatedly and usually
handles all the gameplay logic. In a lot of games it is the same as the render
loop.
Procedural Terrain Generation: The process of generating terrain programmatically, frequently using noise and a random seed.
Render Loop: The part of a game’s code that executes repeatedly and handles
all the rendering-related logic. In a lot of games it is the same as the game
loop.
Sandbox Game: A game where the player is given some tools and constraints
and they are free to do whatever they want.
Voxel Game: A game where the terrain (and usually other elements like entities)
is made up of voxels.
3.3
Technologies and Libraries
.NET: Formerly .NET Core. The official cross-platform framework for C# application development created by Microsoft.
GLFW: A small library providing cross-platform window management, input
handling, and graphics context creation.
DirectX: Microsoft’s Windows-only counterpart to OpenGL (version 11 and
under) and Vulkan (version 12 and up).
Metal: Apple’s proprietary counterpart to Vulkan.
MoltenVK: An abstraction layer that allows Vulkan code to run on devices that
only support Apple’s Metal, since Apple does not support Vulkan.
OpenAL: A widely cross-platform library for easy audio playback. It is not
actively maintained anymore.
OpenGL: A legacy 3D graphics API that is supported by virtually all devices
with advanced graphics support. It was created in 1992 by Silicon Graphics
and control over the standard was transfered to the Khronos Group in 2006.
It has been superseded by Vulkan.

Chapter 4
Platform Bindings and Backend
Technologies
The choice to develop an in-house engine brings with it several major challenges,
among which are the need for a cross-platform rendering backend and window
management solution, a method to capture user input, and a way to play sounds
through the system’s speakers or headphones.
This project’s goal is to provide a simple C# API that acts as an abstraction for
all of the low level platform-dependent logic.
The platform bindings are more to be considered a byproduct of DigBuild’s development since a third party abstraction could have been used in their place without
any major compromises. As such, they will not be covered in the annexes.
This chapter’s goal is to explain the basics of their functionality and their role in
the overall project to give better context to the reader, but not to go into detail on
how they work.
4.1
Rendering Backend
Modern game development requires making the most out of the usually limited
hardware in a wide variety of devices, and as such modern lower level APIs such
as Vulkan, DirectX 12 and Metal are quickly replacing their beloved predecessors
OpenGL and DirectX 11. These newer APIs grant developers much more fine
grained control over the graphics drivers, allowing them to optimize their rendering
pipelines and therefore increasing performance. However, this comes at the cost of
boilerplate and additional steps where the same thing would have been a single
function call in their legacy counterparts. It is worth noting that these newer APIs
are not targetted to end users wanting to build their own graphical applications,
but rather to engine and tooling developers who want to be able to squeeze every
last bit of performance out of the target hardware.
The render API of choice for this project was Vulkan, as it is widely supported
on Windows and Linux systems, and can be used on MacOS through MoltenVK.
10
Chapter 4. Platform Bindings and Backend Technologies
However, the project is architected in a way that additional render backends such
as OpenGL can easily be added to support legacy systems.
One of the main advantages of Vulkan is its approach to sending commands to
the GPU. OpenGL synchronously executes commands as they are fired by the
CPU, which causes rendering to be heavily reliant on the processor as it has to
wait for every action to complete before allowing the program to continue. Vulkan,
on the other hand, uses Command Buffers, which are recorded on the CPU and
submitted to a queue on the GPU for execution. The application can optionally

while the GPU is busy.

The choice of a backend for audio playback is never an easy one, with options

layered sound playback with 3D effects and advanced signal processing.

was cross-platform support, so OpenAL was picked to handle sound. It is not a
very advanced audio library, but it provides the basic playback and 3D positioning

bindings, it can be swapped with a more advanced library such as FMod if necessary.
4.4
Internal API
One of the main difficulties in supporting multiple tools and libraries with different
API surfaces arises from the need to create an abstraction. In the platform bindings,
this abstraction is located within the C++ code, since any high performance library
that needs to interact with the system will be written in C/C++.
This abstraction layer was created to allow new window management systems,
render APIs and user input handlers to be added in the future, supporting new
platforms while retaining the same developer-facing API.

from the .NET runtime. For the most part, this API just acts as a bridge between
the C++ abstraction layer and user code, providing stronger typing than if the

5.1
Structuring Voxel Worlds
The first building block for almost any game is a location for it to take place in.
They go by different names depending on the genre and sometimes the specific
game, but “world” or “level” are the most common. The game world generally
acts like the central data structure containing everything that is part of gameplay
except for the user interface, storing terrain features, entities, information about
the time of day and weather, etc.
This engine differs from most voxel engines in that the world has very few direct
responsibilities and instead offloads them to user-provided data structures and
procedures. This means that anyone - be it the game itself or a third party mod can add new data structures and logic to the world to store any information they
see fit.
In addition to world-level data storage and due to the (virtually) infinite in size
nature of the game world, the engine also provides two levels of subdivision: regions
and chunks. Chunks divide the world into 16x256x16 blocks and data associated
with them tends to be highly localized. Regions are clusters of 64x64 chunks along
the horizontal plane.

By default, the engine ships with data structures for terrain, lighting, and entity
storage.
5.1.1
Terrain Storage
Voxel terrain presents several interesting challenges when compared to the more
traditional “mesh” terrains found in most games. Among other things, it can be
modified, must be persisted when changed, and has a high density of data as it
must store not only what is on the surface, but everything underneath as well and
also all the invisible air blocks above it.
The built-in implementation of block storage happens at the chunk level and is
handled through 5-layer octrees. These allow the system to reduce the footprint
of repetitive data, such as chunks filled with only air blocks or only stone, both
in system memory and in disk. However, in chunks with more complex block
arrangements or large varieties of blocks this might result in the data taking up
more space. This is acceptable because the simpler chunks will greatly outnumber
the complex ones.
Figure 5.1: Quadtree (2D) example of block data compression.
Along with their type, some blocks may also want to store instance data on a
per-position basis such as inventories, fluid containers or progress bars. Since
this data is unique to each block and rather uncommon, it is stored in its own
Position→Instance lookup table within the chunk, which in most cases will be
completely empty and thus take up minimal space.

Lighting Storage
The approach to light value storage is very similar but employs some additional
tricks to pack data slightly more efficiently. To understand why these changes were
made, it is necessary to first know how light is represented and propagated.
A light value is in the range of 0-15, which allows it to be stored in just 4 bits,
or a nibble (half a byte). Non-illuminated blocks have a light value of 0, and
light-emitting blocks may have any value from 1 to 15. This value is reduced by
1 every time it propagates to a neighboring block until it reaches 0. The light
value at any given position could be represented by the following formula, which
employs the Manhattan/Taxicab distance between the current block and nearby
lightsources to determine the propagation loss:
light(Pos ) = max ({0} ∪ {LVal − kLPos − Posk1 | (LPos, LVal ) ∈ Lights})
The naïve approach to storage would be to save each light value as a byte, since
that is the smallest unit of memory we can allocate. However, this wastes half a
byte per block position, resulting in only 50% of the allocated memory actually
being utilized.
Figure 5.2: Light values as they propagate out from two sources
(in 2D).
Since the light value at any given position only takes up half a byte and if one
block’s light value is non-zero there is a high change that neighboring blocks will
also have a non-zero value, the light values for a 2x2x2 region can be packed in the
32 bytes of a single integer. This also removes the need for the lowermost layer
of the octree, requiring only 4 layers to store all the light values in a 16x16x16

5.1.3
Entity Storage
Storage and retrieval of entities are very difficult to implement correctly in a
chunk-based game due to the fact that entities not only have a position, but also
occupy a volume and can move between chunks, and may at any point in time be
located at one or several chunk boundaries. There must also be a way to look up
any given entity by ID, regardless of where it is in the world.
The built-in implementation is not ideal since it does not account for the volume
of an entity, but in a lot of cases that ends up being irrelevant, and everything else
is handled by storing data in two different ways:
• Entities are stored at the chunk level based on their position and are persisted
to disk
• A dictionary of IDs to entity instances is stored at the world level for lookups,
and is only populated with currently loaded entities
This allows chunks and their respective entities to be loaded and unloaded dynamically while still allowing for quick lookups. When an entity’s position changes, it
must notify the chunk it was in that it has left, and inform the new one that it
must now handle its storage. Since the engine doesn’t provide any logic to handle
entity positioning and movement, this must be handled by the game developer.
5.2
Blocks, Items and Entities
The next set of things that are needed once worlds have been established are the
elements that will occupy said worlds. Blocks, items and entities make up the
core content of both the game and third-party mods and are architected almost
identically to each other. From here on they will be collectively refered to as game
objects.
Much like other systems in the engine, they are built on the core principles of
modularity and extendability, and as such are composed of two sets of elements:
data classes and behaviors. These allow for high modularity and code reusability.
5.2.1
Data Classes
A data class represents some information that is fully local and internal to a game
object, meaning its contents may only be accessed by behaviors in the same game
object with access to a direct handle. Due to the clonable nature of every bit of
data in the engine, all data classes must contain a Copy() method that returns a
new deep copy of the instance where it is called.

5.2.3
Attributes and Capabilities
Since a game object’s data classes and behaviors are internal, other objects or
systems cannot access any information within them or communicate with them
directly. Attributes and capabilities provide a way to interface with a game object
regardless of any implementation details.
Attributes represent read-only information about a game object, like the position
and bounding box of an entity, or the light output of a block.
Capabilities expose interfaces with properties and methods which third parties can
use to interact with and modify the state of the game object, such as interfacing
with an inventory or a tank.
In a lot of cases attributes and capabilities are seen in tandem, providing both a
read-only view of the data, as well as an interface to modify it.
When initially registered, a default value must be provided, or alternatively a
fallback function that will return a value. This allows for attributes and capabilities
to be present even in game objects that do not explicitly support them, like
deriving the collision and raytrace bounding boxes for a block from its bounding
box attribute, or making the default light emission of a block be 0.

Ticking and Job Scheduling
Recurring and deferred workloads are some of the most common in games since
most actions do not happen immediately, and computations like physics need to
take place every tick.
DigBuild engine’s world API provides access to a Scheduler class which allows
developers to defer work to later ticks. This deferred work can take two forms: tick
events and jobs.
5.3.1
Tick Events
Tick events are the simplest way of scheduling deferred workloads. They allow an
Action to be called after a certain amount of ticks. They are most often used for
one-off deferred work.

Jobs
The job system offers a more data-oriented flow, allowing the developer to register
a job handle with a function that will be called with every element that is enqueued
to the job in any given tick. Sequential and parallel processing are supported by
default, but custom job types such as fork-join can be implemented via the API.

str => Console.WriteLine(str)
)
// Scheduling

5.4
Events and Event Buses
Events within game objects are dispatched and handled internally to preserve
ordering and allow for more fine-grained control over event flows. However, systems
generally need to notify other systems when something happens so that they may
react accordingly. This is where the event system comes into play.
Event buses act as a central location where event consumers can register handlers
for all the events they must react to, and where they can post their own events as
they take place.
The API provides no guarantees for the order in which handlers will be called, but
it will always happen sequentially (avoiding any potential race conditions).
Events posted to the bus cannot have a return value like the ones in game objects,
so if something similar is needed, a value within the event must be modified and
retrieved once it has been dispatched to all handlers. This is also a valid approach
for short-circuiting events, requiring handlers to check whether the event should be
processed or ignored.
5.5. Terrain Generation
5.5
21
Terrain Generation
Procedural terrain generation is an incredibly complex topic that even at the surface
level (no pun intended) could very well take up hundreds of pages to explore (again,
no pun intended). Every terrain generation system takes a different approach and
is generally very specific to the kind of game being made, technical requirements,
and other factors such as the kinds of elements that can make up the world (terrain,
rocks, buildings, lootable chests, etc).
Chunk-based procedural generation presents several problems, the main of which
is posed by terrain features that span multiple chunks or are located on chunk
boundaries. Terrain voxelization helps with this to an extent, making the parts of
each feature that are in a chunk physically belong to that chunk, but it does not
solve problems like depending on information about surrounding areas.
The approach taken in engine divides terrain generation into two passes:
• An initial description phase where attributes are assigned and modified by
the different terrain features in order to create a pure data representation of
a vertical slice of the world (chunk)
• A population phase where each feature analyzes the previously generated
descriptor and populates the terrain with blocks and other relevant data
Although seemingly simple, this system offers a great deal of flexibility and can
result in very complex procedural worlds without excessive amounts of overhead.
5.5.1
Description Phase
During the description phase, features are allowed to query other chunks to determine if larger elements or those on chunk edges are feasible, but are not allowed
to change their values. Furthermore, the only information they can access about
neighboring areas is what has been settled by the features that generated prior to
the current one. This prevents excessive cascading problems and allows generation
to happen, effectively, one feature at a time, even across large areas of terrain with
massive features.
A feature will generally set the value of certain attributes in this phase, such as
the terrain type (grassy, sandy, salt water) or height at a specific position. In some
cases it may also want to modify existing values, such as a lake feature reducing
the terrain height in the area where it generates and changing its terrain type to
fresh water.
Since each feature can alter any other feature’s already established values, they
can cooperate to create more complex formations and compliment or even disable
each other. For example, an area may originally be a forest, but if a lake feature
generates in the middle of it, the new terrain type will prevent trees from appearing
in the water.

Population Phase
The population phase is quite straightforward in that the only input it receives is
the previously generated description. Features must check all the attributes that
are relevant to their generation and utilize those to populate the blocks or other
chunk information that may be needed.
5.5.3
Worldgen Features and Attributes Applied
A worldgen feature does not necessarily have to affect the terrain, as the name
might seem to imply, nor does it even have to write any data to the world during
the population phase.
Features may be used to initially populate generation attributes with values drawn
from noise functions, such as an initial heightmap of the world, but they may also
use other noise functions to affect existing attributes, such as an “inland factor”
pushing the terrain above or below the ocean level.
Already populated attributes may also be used to constrain the generation of
certain features, like making sure lakes don’t try to generate in the middle of an
ocean, or avoid planting trees on a body of water.
The specific order that is used when applying the different worldgen features will
greatly affect the generated terrain and its properties, so it is always important to
make sure constraints are properly established to ensure correct generation of the
terrain.
It is also worth noting that blocks are not the only thing that can be generated
by features. Any data that exists at the chunk level can be. That includes things
like entities and lighting, but also third party data like the initial density of magic
energy in the air added by a mod.
5.6
Entity Physics
Realistic physics simulations are generally very complex in nature and require
exponentially more computation power the more objects there are in close proximity to deliver accurate results. Game developers employ a plethora of different
techniques to reduce this overhead and simplify the problem so that thousands, or
even millions of objects can be processed every frame.
The physics system in the engine is simple while remaining fairly extendable. It
operates on the intersection between an axis-aligned bounding box and some user
defined geometry, calculating an offset by which this AABB travelling in a certain
direction must be displaced to avoid colliding with the target geometry.
The ICollider interface defines the contract for this behavior as a function of the
colliding AABB and its motion vector.

5.8
Serializing Code Entities
Data persistence is of course also a core element in most kinds of games, although
not all. The engine takes a fairly standard approach to data persistence using the
serdes (or serializer-deserializer) model across two classes: IDeserializer, and
ISerdes which extends the former.
A deserializer exposes a way to turn a bit stream into an object, optionally parsing
additional information from the current context. A serdes adds to that the ability
to encode said object into a bit stream.
IDeserializer and ISerdes interfaces:
public interface IDeserializer<out T>
{
T Deserialize(Stream stream, IDeserializationContext context);
}
public interface ISerdes<T> : IDeserializer<T>
{
void Serialize(Stream stream, T obj);
}
Combined, they provide a simple yet effective framework for serialization and
deserialization of objects, and allow this process to not necessarily be managed
by the object itself, but also by a third party. This may prove especially useful
when something needs to be encoded differently depending on the context, like
disk persistence and networking.
Several implementations are provided by default, such as one for blittable (unmanaged) types, and prefabs for arrays, lists and dictionaries. There is also a prefab
that wraps any other serdes to automatically handle nullability.
One thing that developers must always take into account when writing serdes logic
is the possibility that data may change over time, so it is generally recommended
to include some form of versioning in serdes, be it a version header or something
more advanced.
5.8.1
Serdes Made Easy: CompositeSerdes
The simplest way to handle serialization and deserialization of regular objects is
by way of a CompositeSerdes. This class allows the developer to easily create a
serdes for any type and includes simple yet versatile versioning.
A composite serdes is made up of one or more members, composed of an ID, an
expression that points to the field or property that holds the data and a serdes for
it.
5.9. Data Persistence
25
For correct functioning of the composite serdes, all IDs must follow a set of rules:
• It must be unsigned and positive, and as such higher than 0
• It must be unique within the composite serdes
• If the member is removed, its ID must never be used again in that serdes
• If the serialization logic changes, the member must be assigned a new ID
These properties of the ID are what create the intrinsic versioning of the composite
serdes. A very easy way to achieve this is to increment a number by one for each
member and use that as the ID.
A very obvious problem with that ruleset, however, is that data loss is not only
possible but enforced when changing the serialization of a member. The composite
serdes solves this by using the same ID, but as a negative number, which will
instruct the system to only perform deserialization.
CompositeSerdes usage example:
// Target class
public class MyDataClass
{
public int Score { get; set; }
// public int Health { get; set; }
public float Health { get; set; } // Replaces int health
public ItemInstance ItemInHand { get; set; }
}
// Serdes definition
new CompositeSerdes<MyDataClass>()
{
{ 1u, d => d.Score, UnmanagedSerdes<int>.NotNull },
//{ 2u, d => d.Health, UnmanagedSerdes<int>.NotNull },
{ -2, d => d.Health, UnmanagedSerdes<int>.NotNull
.Casting(i => (float) i) },
{ 3u, d => d.ItemInHand, ItemInstance.Serdes },
{ 4u, d => d.Health, UnmanagedSerdes<float>.NotNull }
};
In this example the Health property has been changed from an int to a float. A
deserializer for the int version is provided, which allows data in the old format
to still be deserialized, and any further serializations will omit index 2 and only
output 1, 3 and 4.

In most cases, geometry and animations alone are not enough to convey an idea
visually, and particles provide a simple way to add that extra bit of flare or noise
to a visual element that really makes it feel complete.
The included implementation heavily leverages modern GPUs’ ability to do what
is called “instanced rendering”. This is a technique wherein a set of vertices are
provided to the renderer, and it is told to draw them several (possibly thousands

attached, like a position, color, etc. This proves to be a very efficient way to draw
the same geometry over and over, and provides a massive reduction in memory
footprint.
Particles are defined as two structs: one that represents the particle in system
memory, and one that represents it in GPU memory. The CPU representation must
implement the IParticle<TGpu> interface and specify the GPU representation as
a type argument.

An interesting thing to note is that particles on the CPU and GPU are updated
separately. This is because particles on the CPU update every game tick (for
example 20 times per second), and particles on the GPU update every frame (for
example at a rate of 60FPS). This is done to reduce computation costs for things
like physics, which happen during the CPU tick, but still provide the ability for
smooth animations and transitions of GPU-bound data.

The particle system will ensure that all particles that are currently alive are kept

by particles that have just died with other particles that are still alive. This also
makes it easy to spawn new particles, since they just need to be added to the end
of the contiguous block of memory taken up by the ones that are currently alive.

Bootstrapping
When initially launched, the game will perform several tasks in order to initialize

6.3
Game Controllers
The game state, logic and rendering, are all managed by controllers. They are in
charge of all the housekeeping needed for any one part of the game to be functional,
like allocation and deletion of any resources.
6.3.1
Gameplay Controller
The only controller present at the time of writing is the “gameplay controller”,
which as the name implies, manages everything related to gameplay. This includes
creating the world and its dependencies (save handlers, terrain generation, etc),
handling mouse/keyboard/controller input, and maintaining the UI stack. This is
also where networking would be managed in the case of supporting multiplayer.
Aside from handling all the business logic, it is also in charge of all rendering
associated with it, which in this implementation includes the world and UI rendering.
Of course, putting so many responsibilities into one class could easily lead to messy,
unmanageable code. This is why almost everything is delegated to more specific
handlers, such as the world renderer, UI manager, or input controller, and the
gameplay controller purely acts as an aggregator and holder of shared state.

6.4
World Generation
DigBuild’s approach to world generation greatly exploits the possibilities offered by
the engine’s API by creating a heavily dynamic and inter-connected system that is
capable of generating complex worlds with very few parameters. It does this by
dividing generation into 3 main phases:
• Establishing constraints
• Picking biomes
• Populating terrain
Doing this provides a simple yet consistent structure for any generation attributes
and features that may be added down the line and gives them additional contextual
information they can use to improve their generation.
6.4.1
Environment Constraints
The first step towards creating wildly dynamic worlds in DigBuild is determining
an initial set of constraints that will determine the overall look of the world. These
constaints are a projection of a smooth noise function (simplex noise) onto the
horizontal plane, and used to determine the following factors:
• Inlandness: How inland (1.0), coastal (0.5), or completely submerged under
the ocean (0.0) a bit of terrain is.
• Temperature: How hot (1.0), temperate (0.5), or cold (0.0) a bit of terrain
is.
• Lushness: How densely packed with flora (1.0) or barren (0.0) a bit of
terrain is.
These could be expanded upon to introduce constraints based on height, humidity,
fault lines and more, and potentially make some of those depend on each other, so
the farther inland some terrain is, the higher the chance of it having a high peak,
for example.
6.4.2
Biomes
Biomes provide a clear and easy delimitation between different environments,
terrain types, and can greatly aid in fencing worldgen features to areas of the world
that meet certain criteria.
The biome system in DigBuild has two jobs: picking a biome for any given position
based on some constraints, and defining a new set of attributes and constraints for
the features generating afterwards.
The selection system uses each biome’s constraints to calculate a score for each
position in the world, and the biome with the highest score is chosen for that
location. This may result in slightly harsh borders between biomes and could be

after they have been calculated before determining the biome for a given position.
The biomes included with the game are: grassland, pasture, tundra, plaeau, beach,
gravel beach, ocean and frozen ocean.

6.4.3
Features
Although one may initially assume otherwise, picking a biome alone does not
actually result in any terrain generation. A biome only provides the guidelines for
future features to generate, and that includes things like terrain.
In their default order of execution, the worldgen features in DigBuild and their
functions during the description phase are:
• Terrain: computes the terrain height and type (ground, water, etc) based
on the biome hints.
• Terrain Smoothing: applies a smoothing function to terrain height to make
biome transitions smoother.
• Tall Grass: determines where grass/weeds will spawn, preferring areas of
higher lushness in grasslands, pastures and plateaus.
• Barley: similar to tall grass, except only in pasture biomes.
• Water: determines where large bodies of water will spawn (ocean, frozen
ocean).
• Trees: determines where trees will spawn, preferring ground terrain in lush
environments.
Figure 6.4: Barley growing among a patch of grass
Once the chunk description has been computed, it can proceed to population:
• Terrain: populates the overall terrain shape, from the bottom of the world
to the terrain height, with dirt except for the topmost layer which is either
specified by the biome, or alternatively defaults to grass.
• Terrain Smoothing: does not populate anything.
• Tall Grass: spawns grass patches where they have been set to generate.
• Barley: spawns barley patches where they have been set to generate.
• Water: fills from the terrain height up to the water level with water blocks,
and replaces the top layer with ice depending on the temperature.

The system is equipped with an advanced yet easily extendable function parser

6.6.1
Defining Geometry
All geometry definitions must be located within the geometry folder at the root of
the mod’s asset directory. Nesting folders inside it is allowed and in most cases
recommended for organization purposes. It is advised to create an items and
blocks folder inside the geometry root to sort the respective models.
The JSON format for geometry is simple, but can vary depending on the types used.
At the root is an elements array, which contains every piece of geometry that is
part of the model. Each element must have a _type member which determines
what provider will be in charge of supplying the geometry. Any other members of
the element are fully dependent on the selected type.
6.6.1.1
Foreword: Parametrized Expressions
Certain data may be parametrized when defined inside a geometry element. This
is done through DigBuild’s expression parser. It allows for string interpolation into
other strings, as well as basic math operations when working with numbers and is
extendable to support more advanced features.
To interpolate a string, the standard ${variable_name} format is used. If this
variable may not be present and in that case should have a default value, one can
be specified like this: ${variable_name|default_value}.
Numeric operations must take place within double braces {{ 1 + 2 }} and variables may be used as operators like so: {{ ${angle} * 90 }}. The supported
operations are addition, subtraction, multiplication, division and modulo. Parentheses are currently not supported.
6.6.1.2
Basic Cuboid Geometry
The most common type is digbuild:cuboid, which takes in 4 inputs:
• from: a 3 element array indicating the first corner of the cuboid.
• to: a 3 element array indicating the second corner of the cuboid.
• textures: an object where each key-value pair represents a face of the cuboid
and its texture. If a face is ommitted, it will be missing from the geometry.
• layer: the world render layer the generated geometry will be in.
Out of those, each of the individual textures as well as the layer can be parametrized
with an expression.

• model: the fully qualified name of the OBJ to be included, or alternatively
the relative path to it (in both cases without extension).
• layer: the world render layer the generated geometry will be in.
In this case, only the layer can be parametrized with an expression.

6.7
UI Stack and User Input
DigBuild expands on the engine’s basic UI element framework with a more complete
system of its own.
At the core of it is the UiManager class, which manages what is internally called
the “stack” of UIs currently open and passes all input events to them. The main
game HUD is one of these UIs and lives at the bottom of the stack. Other UIs
such as inventories, crafting screens and even the pause menu may be opened on
top of it and can take over user input or pass it through as they choose.
The IUi interface is used to define user interfaces, but more often than not the
aptly named SimpleUi implementation can be used in its place. This one takes in
a root UI element (as per the engine’s API), and can determine a set of factors like
whether the game should pause when it is open, if the mouse should be visible or
not, and if UIs farther down the stack should receive events that this UI doesn’t
handle. It also provides events for resizing and UIs opening and closing on top of
it.

of passing the events it receives over to the game input subsystem. This opens

gameplay, such as holding the Alt key to release the mouse and interact with the
elements in the HUD without opening another UI.

give the game its look.
6.8.1
Night Sky Starfield
The sky is drawn using a fragment shader that uses screenspace coordinates and
some transform matrices to generate a cuboidal grid around the player that tracks
the camera’s movement.
Figure 6.6: The sky grid used to draw stars
This grid is then used to place one randomly sized and colored point of light in
every cell, with slight offsets to break up the pattern.

Figure 6.7: Oversized circles of random colors in the sky
Multiple layers of this with different scaling factors and scattering produce the
night sky that is seen in the game.
Figure 6.8: A fragment of the finalized night skybox
6.8.2
Water Shader and Fog
The world goes through several postprocessing steps, but the most interesting one
is the one where water and fog are added since both of these effects rely heavily on
the data in the depth buffer.
Water processes the data from two separate depth buffers - the world’s and the
water layer’s - and determines where water should and should not appear. It then
uses the delta between these depths to smoothly transition between a lighter, more
transparent water color in areas closer to the surface, to a darker, more opaque
shade in the case of deeper water.

player, hiding the fact that there are no more chunks loaded in that direction. It
employs a negative exponent of the depth to create a smooth fade where areas in
close to medium proximity to the player are clearly visible and farther areas are
covered in fog.

The development of this project began all the way back in December of 2020. At

Chapter 1
Introduction
Software development these days is tending towards agile development methodologies, with tight iteration loops and fast turnarounds that result in quick results
and the ability to discover and correct erroneous assumptions during the design
and specification phases, as well as to adapt to fit new requirements.
These days, this is in most cases a far more suitable approach than the waterfall
development strategy that was predominant in the 90s. The market moves very
quickly and products need to adjust to new conditions just as fast, or they will
become outdated before they even reach the public. Agile development can help
greatly reduce that risk and allows developers to focus on the most important tasks
at any given time without losing track of everything else.
1.1
Why Agile?
This project was intended to not only be a learning experience, but also a challenge
on handling unknowns and the unexpected. Not having any experience with any of
the core technologies that were chosen prior to the beginning of the project meant
that it was likely for numerous adjustments to have to happen along the way to
correct for mistakes and wrong assumptions.
Additionally, due to wanting to continue development after this thesis, the project
was given a considerably larger scope than what could be completed in the allocated
amount of time. This was done to preserve an overarching vision, as introducing
certain features or systems down the line without accounting for them ahead of
time could require large parts of the code to need to be re-structured or completely
rewritten, whereas considering them early on had little to no extra cost.
A game that is expanded upon over time will inevitably face technological debt
throughout its entire development. Planning far ahead enough to know a rough
estimate of what might be needed in the future without committing to specifics
can be of great help in avoiding unnecessary work which may be undone in the
near future, as well as anticipating changes and being ready for them.
2
Chapter 1. Introduction
It is for these reasons that agile was chosen. However, due to the team size of just
one person it was necessary to find an agile methodology that would not incur in
excessive overhead due to being designed for large teams. After all, a good part of
what these methodologies specify are tools and methods for teams to coordinate
with each other, and in this case there is not much need for that.
1.2
Kanban
Out of all the options available, kanban was selected due to its simplicity and very
low overhead, as well as its ability to easily scale down to just one person.
Trello was the tool of choice, and several boards were created for the different work
areas, allowing tasks to be located next to those that most resemble them:
• Platform Bindings: Anything to do with the platform bindings project
• Engine: Anything to do with the engine project
• Game Tech: Technical/backend systems for the game
• Gameplay: User-facing elements such as UIs, mechanics and content
Each board was given five columns:
• Incoming: Where new cards go as they are created
• To-do: Daily workload
• Doing: Currently active tasks
• Testing: Completed tasks, untested
• Done: Completed tasks, fully tested
Figure 1.1: An example of one of the Trello boards.
Any new work, be it features or bugfixes, would be added to the “incoming” column.
At the beginning of a work day, one or more cards would be moved to the “to-do”
column, and work would begin. The active task(s) would be placed in the “doing”
1.2. Kanban
3
column, and upon completion they would be moved to “testing”, where they would
remain until they had been thoroughly tested, at which point they would be moved
to “done”.
The method for handling bugs found during testing differs on a case by case basis:
• If it is quick and easy enough to fix, it should be done on the spot
• If it is so big that it breaks the system, the card should be moved back to
“doing”
• If it is minor or requires additional research, the card may be moved to “done”
and a new one be created for the bug in “incoming”
Cards would additionally be tagged based on their role and relevance, such as
“mechanic” or “world” in the gameplay board.

Chapter 2
Estimation Process
In agile development it is not uncommon for rough and very general time estimations
to be provided by the system architects, which are later refined on a per-task basis
by the developers as they move those tasks out of the backlog and into their
personal work pile.
In this project, per-task estimation was substituted with per-day task estimation.
That is, instead of assigning a task an amount of expected work hours, each day a
set of tasks that could conceivably be completed within the available development
time would be selected. Longer tasks that could not be subdivided and would span
multiple days would often be picked in isolation, and if a day’s work could not be
finished, it would roll over into the next day.
It is very important to note that due to the very iterative development approach
used, no one system was developed and then never touched again. In some cases,
systems required tweaks or even complete redesigns from the ground up later in
the development process due to emerging requirements.
For this reason, time frames for the development of specific sections of the codebase
will not be provided, since they simply do not exist. Instead, work-day estimations
will be calculated for every system based on both the design and implementation
time, including all further iterations and tweaks.
An additional time estimate will be provided for the design and development of
code elements that do not necessarily belong to a system, but act as support
elements like collections, helper classes, etc. as well as code audits, cleanup and
non-code-related work.
2.1
Scope Limitations

Game
The game was the project that presented the smallest difference between the

Key Takeaways
• It is sometimes better to start from scratch than to waste time patching a
broken system (platform bindings, rendering, game architecture)
• Agile should not be an excuse for rash, uninformed decisions (platform
bindings)
• There are many hidden costs and complexities in the unknown (platform
bindings, model loading)
• Code that seems to work should be assumed not to in all untested cases

• Unexpected changes to one system will inevitably cascade into others (rendering)

Chapter 1
Introduction
A key step in the development of any project is figuring out what needs to be
achieved and in what way. The choice of employing agile methodologies means
that new requirements may appear along the way, and that the priorities of each
one are constantly changing.
This annex will document all the historic requirements in the engine and game
projects, as well as analyze their design and implementation into systems in both
projects’ codebases.
1.1
The Case For Agile Methodologies
One of the key differences between agile and traditional approaches is that the
focus is placed on the task at hand, and as a result much of the time and labor
that would usually be spent on the initial documentation is instead put into a fast
iterative development approach.
This does not mean that no documentation is produced - after all, stakeholders
need to be able to understand and approve what is going into production. However,
the fast iteration times allow developers to focus a lot more on the back-and-forth
with stakeholders to refine the goals during development, rather than planning
everything upfront and writing the code at the end like traditional methodologies
require.
Especially in situations with large levels of uncertainty like this one (such as not
knowing any of the languages and APIs used), being able to quickly change course
without having to spend weeks documenting and architecting systems on paper is
incredibly beneficial to overall efficiency.
Additionally, with just one person taking on every role in the project, from stakeholder to developer to architect, the need for documentation as a tool for communication ends up relegated to documenting for posterity’s sake.
2
Chapter 1. Introduction
1.2
User Stories and Stakeholder Involvement
One of the key differences between agile and other approaches like unified process
is that use cases are replaced with user stories.
User stories allow stakeholders and developers to agree on a set of goals for the
product. These goals are generally written from the point of view of the end user,
and do not get into technical or implementation details. They just aim to make
the problems clear to everyone so that solutions can then be developed.
This is a much better fit for modern software due to the ever increasing importance
of user experience and user interface design. While use cases lend themselves to
defining screen, menu and API hierarchies, user stories simply define functional
and technical requirements in specific contexts, and allow an expert in UX design
to work out all the specifics of the user-facing elements involved.
1.3
Turning User Stories Into Code
Most agile methodologies tend to focus on the core development loop but do not
really specify a way to get from user stories to actionable tasks that can be made
part of the development backlog. This is left to each team to figure out.
In most cases, an architect will take these user stories, figure out how they relate to
each other, and sketch out a rough outline of the systems that will be required for
them to be fulfilled. Developers can then reference these outlines while designing
and implementing the systems.
The line between an architect, a systems designer and a programmer is often
blurred, with one person taking multiple of these roles and being responsible for
whole systems, from design to API to implementation. This segregation of work
by system instead of by position in the development chain places a much bigger
responsibility on each individual, but at the same time gives developers a sense of
ownership and accomplishment, allows for better specialization, and improves work
parallelization and adaptability considerably.
1.4
Architectural Choices
It’s important to make certain key architectural choices before designing any
systems to ensure clarity and consistency across the entire codebase. As such, the
following guidelines were created upfront:
• Types should be sealed whenever possible
• Aggregation and composition should be prefered over inheritance
• Only types and members that need to be part of the public-facing API should
be exposed
1.4. Architectural Choices
3
• A construct that has or could have multiple implementations should be
defined as a contract (interface)
• Code should avoid depending on specific implementations as input and output
types, as well as depending on implementation-specific members

2.3. System Architecture
2.3
27
System Architecture
With an intial set of user stories in place specifying what each end user expects,
the next step is to analyze them and sketch out an architecture that fulfills these
expectations. This is the point at which technical and functional requirements will
start taking shape.
These architectural outlines can later be handed over to the developers, who will
design the systems in detail, and subdivide the work into smaller actionable work
units which can be prioritized and added to the backlog.
For each system a complexity score will be given based on technical and practical
difficulty, a necessity score based on the importance within the overall project, and
a priority score that combines the two and helps determine the order in which
systems are implemented.
Note that this section is only meant to specify the overall architecture of each
system, as well as basic API functionality. How they are implemented is up to the
developer and their choices are not relevant to this document.
2.3.1
Game Objects
The game object system covers the three main types of things a player will encounter
in the game: blocks, items and entities. While they all behave very differently and
are used in different ways throughout the codebase, they are built upon the same
base architecture.
User stories: 001 to 017
Complexity: 4/5
Necessity: 5/5
Priority: 5/5
Dependencies:
• Worlds
Game objects must be composed of ordered behaviors and unordered data classes.
Behaviors must handle the business logic, while data classes must provide local
state storage.
Behaviors and data classes must not be exposed directly. Instead, attributes and
capabilities may be used. Attributes must represent read-only data about the game
object, while capabilities must represent a mutable interface.
Behaviors must be composed as a set of event handlers which react to incoming
events, and optionally forward them to the next behavior in the chain. They may
optionally provide a contract, allowing them to track local state. They may also
28
Chapter 2. Engine Requirements
expose attributes and capabilities or delegate this to the next behavior in the chain
just like events.
Data classes must be composed of fields and properties and may implement behavior
contracts. They must be able to be deep-cloned. If a class is to be persisted, it
must be able to notify other systems when its values have changed.
Events must provide the context in which they happened as well as any arbitrary
user-provided state, and may optionally specify a return type.
Attributes must be retrieved with a read-only context of the game object for state
queries. They must always be present and a fallback value or provider must be
specified during registration.
Capabilities must be retrieved with a writable context of the game object for state
queries as well as actions. They must always be present and a fallback value or
provider must be specified during registration.
Game objects must be constructed using a builder. This builder must allow data
classes to be added, and if they are to be persisted, must also accept a serdes for
them. It must also allow behaviors to be added at either the start or the end of
the chain, and for those that have a contract, it must require the user to provide a
handle to a data class that fulfills it.
Behavior event subscriptions and attribute/capability providers must be added to
a builder as part of the behavior’s initialization phase for a given game object.
Additionally for items and entities, instance types must be provided which must
store the type, as well as any instance data. In the case of item instances, they
must also store the count, and in the case of entity instances they must store a
unique identifier. None of this is needed for blocks due to their state (if present)
being stored externally.
Item instances with a count of 0 must be treated the same regardless of the item
type bound to them.
2.3.2
Events
The event system allows other systems to communicate by posting events to a bus
and allowing others to subscribe to them.
User stories: 018
Complexity: 1/5
Necessity: 5/5
Priority: 5/5
Dependencies:
• None
2.3. System Architecture
29
Events may be any user-provided type given they implement a base IEvent interface.
Unlike events in game objects, they cannot specify a return value nor be shortcircuited.
Event buses must provide a way to subscribe and unsubscribe a handler from any
given event, as well as to post events. There may be more than one event bus
active at a time.
The order in which handlers are called when an event is posted is not guaranteed,
but it must happen synchronously and sequentially.
2.3.3
Inventories
Inventories provide a way to store item instances and act as an API surface for any
system that needs to insert and extract items. Inventory slots act as the backing
implementation for item storage.
User stories: 019 to 022
Complexity: 1/5
Necessity: 4/5
Priority: 4/5
Dependencies:
• Items
Inventories must provide a way to begin a transaction and enumerate their contents.
Transactions must allow insertion of item instances, and extraction by amount,
optionally including a filter for what may be extracted. They must not commit
any changes to the backing storage until the transaction is manually committed by
the user. They may optionally support checkpoints and rollbacks.
Inventory slots must store an item instance and be able to notify third parties
when this item instance changes. They must also be able to filter what is allowed
into them. They may optionally be lockable to their current contents if not empty
to prevent other items from taking their place.
Implementations for slots and simple inventories must be provided.
2.3.4
Networking
The networking system allows processes potentially running on different machines
in completely different networks to talk to each other in a fast and reliable way.
User stories: 023 to 025
30
Chapter 2. Engine Requirements
Complexity: 2/5
Necessity: 2/5
Priority: 1/5
Dependencies:
• Registries
Packets must be defined as a combination of type that contains the data and a way
to handle it, as well as a serdes implementation.
Connections must be a generic way of representing a client’s connection to a server
or a server’s connection to any of its clients, and must provide a way to send packets
to the other party and close the connection.
The server network manager must operate a TCP server on a user-specified port,
await connections from clients, and be able to notify external systems when this
happens. It must also provide ID remapping for all the supported packet types
to reduce networking overhead, as well as synchronize these IDs to all clients.
Additionally, it must provide a way to send packets to all the clients at once.
The client network manager must connect to the server at a specified address,
receive the packet ID mappings, and use them. It must also expose the current
connection.
All network communication must happen off-thread, including sending packets and
handling received ones.
2.3.5
Particles
The particle system provides developers with the tools to generate lots of similar
geometry in a fast and efficient way.
User stories: 026 to 028
Complexity: 2/5
Necessity: 2/5
Priority: 2/5
Dependencies:
• None
Particles must be defined as blittable structs in CPU memory. They must be able
to be updated every game tick and provided with a context that they may use
freely during this update. They must be able to notify the particle system when
they need to disappear. They must also have a blittable GPU representation that
can be updated every frame and interpolated for smooth animation.
2.3. System Architecture
31
Particle systems must be tied to a specific particle type and keep a buffer of both
the CPU and GPU representations of each active particle. They must provide a
way to create new particles, as well as to update them. After each update, all
particles that are still alive must be located in concurrent memory.
Particle update contexts must provide a random number source as well as a way to
determine the direction of the wind.
Particle renderers must be tied to a specific particle system and must provide a
way to update the particles and draw them on screen. They must also manage all
the render resources related to particle rendering.
2.3.6
Physics
The physics system provides developers with the tools to compute collisions between
objects, as well as between a ray and some geometry.
User stories: 029 to 032
Complexity: 3/5
Necessity: 5/5
Priority: 5/5
Dependencies:
• None
Colliders must provide a way to determine the intersection between an axis-aligned
bounding box moving along a path and whatever physics body they represent.
Ray colliders must provide a way to determine the intersection between a ray and
whatever physics body they represent.
Implementations for 1:1 and 1:N AABB-AABB collisions and ray collisions must
be provided, as well as “null” colliders that represent a non-collidable body.
Raycasters must provide a way to perform a ray collision within a grid-aligned
context.
Grid-aligned raycasting contexts must provide a way to perform a ray collision at a
specific position in the grid.
2.3.7
Registries
The registry system allows key-value pairs to be registered by other systems and
then freezes them so they cannot be modified.
User stories: 033 to 039
32
Chapter 2. Engine Requirements
Complexity: 1/5
Necessity: 5/5
Priority: 5/5
Dependencies:
• Events
Registry managers must provide a way to define registries and to build all of them.
Registry building must involve firing a building event to allow systems to add items,
and a built event to notify systems that the registry is ready and the contents are
locked.
Registry builders must provide a way to add entries to the registry and must be
able to validate keys and values. They must only be able to be created through a
registry manager.
Registries must be composed of resource name-value pairs. They must provide an
item count, enumeration, forward and reverse lookups, and key/value existence
checks.
Type registries must be composed of type-value pairs. They must provide an item
count, enumeration, forward lookups and key existence checks.
Registry building events must contain the registry builder.
Registry built events must contain the built registry.
2.3.8
Serialization and Deserialization
The serdes system allows objects in memory to be converted into bit streams and
vice versa.
User stories: 040 to 045
Complexity: 2/5
Necessity: 4/5
Priority: 3/5
Dependencies:
• None
Deserializers must provide a way to convert a bit stream into an object, optionally
relying on contextual data.
Serdes must be deserializers, and additionally must provide a way to convert an
object into a bit stream.
Deserialization contexts must provide a way to retrieve a value for a given type.
2.3. System Architecture
33
Implementations for arrays, lists, dictionaries and unmanaged types must be
provided, as well as an “empty” serdes that does not read/write data and always
creates new instances of the given type during deserialization. A generic nullable
wrapper for all nullable-type serdes must also be provided.
Simple deserializers and serdes must be constructed from delegates, which handle
the serialization and deserialization.
Simple deserialization contexts must be defined as mutable type-value dictionaries
with an optional parent context.
Composite serdes must be defined as a composition of serdes and deserializers,
each with an ID and mapped to a member of the target type. These IDs must be
used during serialization/deserialization to identify the members and delegate the
serdes logic to their respective implementation. A negative ID, must mean that the
member is only to be deserialized, while a positive ID must mean that the member
is both serialized and deserialized. An ID of 0 is deemed invalid.

Data Containers
The data container system allows for the aggregation and management of data

User stories: 046 to 049
Complexity: 2/5
Necessity: 4/5
Priority: 4/5
Dependencies:
• None
Data classes must be clonable types composed of fields and properties. Optionally,
they may be change notifiers.
Change notifiers must be able to notify other systems of a change in their state.
Untargetted data handles must be bound to a specific data class and be able to
create new instances of it. They may have both a name and serdes, or neither. The
bound data class may optionally be a change notifier.
Targetted data handles must be bound to a specific data class, as well as a read-only
representation of it. They may have both a name and serdes, or neither. The
bound data class may optionally be a change notifier.
Data containers, both targetted and untargetted, must provide a way to retrieve
the local value of a handle. If no value is present, a new instance must be created,
stored and returned. They must additionally pass through events from data classes
that are change notifiers. They must also be clonable.

Texture Stitchers
The spritesheet and stitcher system allow for lots of small textures to be combined

User stories: 051
Complexity: 3/5
Necessity: 4/5
Priority: 3/5
Dependencies:

Sprites must be defined as a UV coordinate and size in the 0-1 range.

Ticking, Scheduling and Jobs
These three sub-systems provide the infrastructure for almost all the logic happening
during the game tick.
User stories: 051 to 055
Complexity: 3/5
Necessity: 4/5
Priority: 4/5
Dependencies:
• None
Tick sources must notify external systems every time they tick. If they are deemed
stable (predictable ticking intervals), they must also provide an interpolator for
the current tick.
Interpolators must provide a value between 0 and 1 for the progress of the current
tick.
2.3. System Architecture
35
Jobs must accept some inputs and a scheduler, and return a task which completes
when the inputs have been processed.
Default implementations for sequential and parallel jobs must be provided, being
constructed with a callback that will only accept one input.
Schedulers must be constructed with a tick source and must allow work to be
scheduled to future ticks. They must provide an event that will be fired when the
deferred tick happens, as well as a way to enqueue inputs to a job that will run on
that tick.

Worldgen features must be able to describe what is to be generated in a chunk
from some context, for which they must update attributes in that context with

Chunk description contexts must allow querying the attributes of the current and

2.3.14
Worlds
Worlds are the core data structure for all the content in a game and provide the
scaffolding that most systems depend on.
User stories: 065 to 069
Complexity: 3/5
Necessity: 5/5
Priority: 5/5
Dependencies:
• Blocks
• Entities
Worlds must be composed of a chunk manager, a scheduler and a set of data classes.
They must provide a way to query the absolute time, the gravity, the chunk at a
given position, and the data for a specific handle.
Chunk managers must provide a way to create loading claims on certain chunks,
which may take effect immediately or be deferred. Claims must provide a way to
be released.
Chunks must be composed of a position and a set of data classes and must provide
a way to query them. They must also be change notifiers and forward any events
from the data classes that make them up.
A built-in implementation of chunks, chunk managers and claims must be provided,
as well as an off-thread chunk loader for deferred claims. A base implementation of
worlds must also be provided, subdividing them into regions of 64x64 chunks and
providing cached storage of both regions and chunks.
A built-in implementation of block storage in chunks must be included. It must
provide a way to get the block and data at any position, set a new block, and
enumerate the contents. Block storage must use octrees to minimize memory

footprint, while data storage must use a position-based dictionary due to being

A built-in implementation of chunk and world entity storage must be included.
Entities must be persisted in the chunk they are in, while world storage is used to

2.3.15
Rendering
Rendering is a must in almost every game engine, and it is especially hard to get
right.
What is exposed here is the final design for the rendering system. However, there
were previous iterations that looked nothing like this one and those have been
excluded.
User stories: 070 to 080
Complexity: 5/5
Necessity: 5/5
Priority: 5/5
Dependencies:
• None
Render layers must have a vertex type and provide a way to draw the contents of
a vertex buffer of that type to the screen. They must manage their own resources
and may store render-local data in a binding set. They must also provide methods
for applying transforms to the position and normal data of each vertex, as well
as to set light values. They may make use of externally provided uniforms and
textures.
Geometry buffers must provide a way to retrieve a vertex consumer for a given layer,
and must also provide a way to set a transform matrix for all incoming geometry.
They must collect the geometry provided to these consumers until it is needed for
rendering, and upload it to the GPU.
Uniform buffer sets must provide a way to read and write data to user-defined
uniform buffers. They must manage the instantiation of said buffers and upload
their contents to the GPU.
Texture sets must provide a way to retrieve globally shared textures and must
provide a default sampler.
Block models must provide a way to collect static and dynamic geometry based on
some contextual data and a set of visible faces.

Chapter 2. Engine Requirements
Item and entity models must provide a way to collect dynamic geometry based on
some contextual data.
Model data must provide a way to look up, create and update an arbitrary data
class by type.
World renderers and chunk renderers must provide a way to be updated at the
start of a frame, and must provide a 3-pass draw process:
• Resource initialization and uniform collection
• Per-layer rendering
• Resource disposal
Chunk renderers must additionally provide a way to differentiate between “express”
and “heavy” updates so that their load may be balanced across frames.
Chunk uniform push events must provide a read-only view of the current chunk
and a writable uniform set.
A built-in implementation of a world renderer that renders chunks, as well as a
chunk renderer that renders blocks must be provided.
2.3.16
Miscellaneous
All code in the project that has not been described in the previous sections originates
from certain needs at the time of implementing other systems. They are generally
small isolated types, support interfaces, collections, helpers or other structural
elements that allow the different systems to work properly.
A few notable ones are:
• Main engine class: Initializes all the members of the engine that are
required for operation and subscribes to relevant events.
• Resource names: Composed of a domain and a path, they represent the
fully qualified name of a resource.
• Octrees: Memory-efficient storage of sparse data in 3D space. User story
081.
• Grids: Read-only 2D data storage.
• Lock stores: Key-based monitor synchronization.
• Caches: Maps that store temporary values with periods extended through
updates/reads.
• Math types: 3D vectors with different semantics (block position, chunk position, chunk offset, generic int vector), axis-aligned bounding boxes, directions,
ranges and more.
• Noise generation: FastNoiseLite library and a wrapper for easy simplex
noise generation. User story 082.
• Rendering aides: Camera, view frustum and shader types.

3.4. System Architecture

System Architecture
With an intial set of user stories in place specifying what each end user expects,
the next step is to analyze them and sketch out an architecture that fulfills these
expectations. This is the point at which technical and functional requirements will
start taking shape.
These architectural outlines can later be handed over to the developers, who will
design the systems in detail, and subdivide the work into smaller actionable work
units which can be prioritized and added to the backlog.
For each system a complexity score will be given based on technical and practical
difficulty, a necessity score based on the importance within the overall project, and
a priority score that combines the two and helps determine the order in which
systems are implemented.
Note that this section is only meant to specify the overall architecture of each
system, as well as basic API functionality. How they are implemented is up to the
developer and their choices are not relevant to this document.

3.4.11
Model System
The model system allows for complex geometry with advanced state management
and transforms to be defined through simple JSON files.
User stories: 053 to 057
Complexity: 4/5
Necessity: 2/5
Priority: 2/5
Dependencies:
• Engine/Rendering
3.4. System Architecture
71
Model managers must provide a way to load block and item models from resources,
initialize their dependencies, and bake them, as well as a way to dynamically query
and override baked models.
Raw models must provide a way to load their textures from a sprite loader, as well
as to be built into a final usable model.
JSON models must be defined as an ordered list of variants, each with a ruleset
and some geometry, and an optional global flag to mark the model as dynamic.
Raw JSON models must be able to be built into block and item models.
Geometries must provide a way to add their contents to a geometry buffer, querying
data and face visibility as needed. They are created from raw geometries.
Raw geometries must provide a way to load their textures from a sprite loader, as
well as to be built into a geometry.
Geometry JSONs must be defined as a set of elements, each marked with a provider
and defining the required parameters for said provider to generate some geometry.
The geometry of every element is combined and represented as a partial geometry.
Partial geometries consist of a set of unresolved variable and must provide a way
to apply substitutions on those variables. They must also be able to be primed
into geometries.
Geometry providers must be able to provide a partial geometry from a JSON
element.
Built-in implementations for cuboid geometries, geometry JSON imports, OBJ
imports and transforms must be provided.
Model expressions must be defined as trees of string concatenations, mathematical
operations, and variable interpolation with optional default values. They must be
able to receive substitutions, as well as to enumerate their required and optional
variables. They must be able to be compiled into a native C# expression. They
may be evaluated as numbers.
Model expression parsers must be able to convert a string representation of an
expression into a model expression instance.

3.5
Gameplay and Content Design
In the case of the game like this one there are not only internal systems that need to
be developed and act as a support mechanism for everything else, but also content
which requires certain systems to be designed a specific way to support certain
playstyles or mechanics.
While the previous section focused on the technical aspects of these support systems,
this section will go over some of the design and gameplay choices and ideas, and
how they relate to those systems.
Especially due to the simplicity of the implementation of all of these mechanics
with the already established systems, it is not necessary to go into detail on how
they are to be implemented.
3.5.1
Player-Centric Experience
The player should be the protagonist of this game, which leads to a lot of mechanics
being designed around player interaction, from basic block placement and removal,
to interacting with inventories and exploring the world.
3.5. Gameplay and Content Design
73
The player’s need to move around the world is fulfilled by a combination of the
UI manager, the main HUD, the game input class, the player controller, and the
physics behavior. Input events pass through the UI system and are handled by the
game input class, which is later queried by the player controller to act on the input
by updating the physics system to add forces to the player entity.
The player’s interaction needs are handled through a similar flow, except instead
of applying forces to the physics entity, it retrieves the current item in the player’s
hand, tries to use it, and if that fails, tries to interact with the block that is being
looked at (if present).
Item pickup is done through the pickup behavior added to the player entity, which
attracts item entities towards them and if they are within range, adds them to the
player’s inventory.
The player inventory is made up of the ten hotbar slots and eight equipment slots,
and may be expanded through items like pouches which can store other items within
themselves. Equipment is accessible through the Q, E, Z and C keys, matching
the corners of the equipment screen in which they were placed without needing to
open the screen again.
Crafting is currently disabled but is designed to use a hexagonal seven-slot grid
where the player must place items forming a pattern, four slots for additional items,
and a catalyst or tool to be used for the craft. The output is a single item, and all
inputs except for the catalyst are consumed during crafting.
Another core element of the player experience is the selection box drawn around
the currently selected block. This makes use of the player camera’s raycasting
ability, the highlight event, and the world render pipeline to draw a wireframe of
the currently selected block’s bounding box.
3.5.2
Creating the World
The world in DigBuild is currently made up of eight different biomes controlled by
two constraints: inlandness and temperature. This is enhanced through additional
features that bring additional character to the terrain generation.
The first point where terrain generation begins to differentiate itself is in land and
water bodies. The crossover between these two is controlled by the inlandness
factor, where 0 represents the middle of the ocean, and 1 represents the innermost
part of a continent. In addition to ocean and landmasses, there are also beach
biomes that act as a buffer between them.
Inland it is possible to encounter plateaus - elevated terrain that adds more vertical
diversity to the world.
74
Chapter 3. Game Requirements
The temperature in an area will also determine what kind of terrain is to be
generated, from grassy areas to frozen land, and goes from 0 representing a gelid
climate, to 1 being the hottest possible.
Trees, tall grass and barley are used to decorate the terrain and appear based on a
lushness factor, where 1 is very lush and 0 is barren.
The eight biomes and their highlights are the following:
• Grassland: Spawns in temperate climates. The terrain surface is grass, and
it has tall grass and trees.
• Pasture: Spawns inland in temperate-hot climates. The terrain surface is
grass, and it has tall grass, barley and trees.
• Tundra: Spawns in cold climates. The terrain surface is snow and has trees.
• Plateau: Spawns inland in temperate-hot climates. The terrain surface is
grass and it has tall grass and trees.
• Beach: Spawns at the edge between land and ocean in temperate-hot climates.
The terrain surface is sand.
• Gravel beach: Spawns at the edge between land and ocean in cold climates.
The terrain surface is gravel.
• Ocean: Spawns in temperate-hot climates. The seabed is made of sand.
• Frozen ocean: Spawns in cold climates. The seabed is made of gravel.
In addition to terrain generation, the skybox and day-night cycle provide an extra
layer of character to the experience. During the day, the sky is a light blue color
and all the terrain looks bright, but as it becomes night, both the sky and the
terrain darken, and the stars come out. This leverages the world’s absolute time
counter, as well as world rendering layers, and shaders.
3.5.3
Additional Features
Logs in DigBuild will fall if there is nothing underneath them to support them, and
as such, trees can be cut down from the root by breaking a single block. Leaves
will decay if they are not in reach of a log, so they will also begin disappearing
along with the wood.
When leaves decay they will drop sticks and sapplings, the latter of which can be
planted into a new tree.
Campfires use the particle system to give the appearance of a fire using otherwise
static geometry.
Pouches have an inventory of their own inside them, and can be used to extend
the player’s inventory space either by using them in the player’s hand, or putting
them in an equipment slot. Clicking the item or pressing the matching equipment
key will bring up their user interface.

3.1
Keyboard and Mouse Controls
As in most games, the W, A, S and D keys are used to control player movement
foward, left, backward and right respectively, while Spacebar is used for jumping.
The mouse is used to aim the camera, while the left mouse button uses an item
or block, and the right mouse button performs a punch. The mousewheel scrolls
through the hotbar.
User interfaces can be exited by pressing the Escape key, and pressing it while in
the main HUD will open the pause screen.
While in the main HUD, the Alt key can be held to release the mouse cursor and
allow for interaction with UI elements even though no screen is open.
The Q, E, Z and C keys can be used to activate the items in the matching corner
slots in the equipment screen. The middle mouse button may be used to lock an
inventory slot’s contents.
3.2
Controller Input
Controller input is partially supported, with the left joystick controlling
player movement and the right trigger handling jumps.
The right joystick controls the direction of the camera, while the A button uses
an item or block, and the B button performs a punch. The dpad left and dpad
right buttons scroll through the hotbar.
User interfaces can be exited by pressing the Menu button, and pressing it while in
the main HUD will open the pause screen.
On PlayStation controllers, the A and B buttons are X and O respectively. The Menu
button is the Options button.
UIs can currently not be used with a controller. For those, a mouse and
keyboard must be used instead.

Try scrolling to the campfire and stone blocks in your inventory and placing them

With an empty hand or a non-interactable item selected, the “use” action will interact with the block the player is looking at. The only block with this functionality

Inventory Management
Items within an inventory, be it the player’s, a block’s or another entity’s, live inside
slots. These can store up to 99 of any given item, though each item may have a
limit to its stack size in addition to that (for example, pouches are non-stackable).

Items can be picked up from a slot by left-clicking, at which point they will follow
the cursor. When left-clicking another slot, they will attempt to go into it. If the
items of the target slot are of the same type, they will try to merge into a larger
stack. If they are of different types, they will be swapped.
Certain slots may be lockable to specific contents, ensuring that when the items
are removed or run out, no other kind of item can take their place. One such case

Chapter 4
Known Bugs and Missing Features
The game’s content is not very extensive and several features are either not present
or not fully working due to the heavy focus on the technical aspects of the engine
over content and gameplay.
Some known bugs are:
• Movement physics can be unstable, with large jumps making the player fall
through the ground and having to restart the game
• The bloom effect of campfire particles may in some instances render through
other blocks
• There is currently no swimming animation or water collision
• Block lighting is disabled due to high computation costs while generating
geometry for rendering
