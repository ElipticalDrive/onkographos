# Summary / Resumen

Sandbox voxel games provide players with an interesting challenge while at the same time giving them lots of freedom to do what they want.

However, a lot of these games have very locked featuresets and require tooling created by the community to expand on this content. This often means extracting, modifying and deobfuscating binaries to be able to add hooks and events, and results in major breaking changes every time the game is updated.

The goal of this project is to develop one such game, but placing the focus on creating simple yet flexible APIs that are designed for third parties to use. The game's own content should also make use of these APIs to prove that they are in fact usable.

The move to modern graphics APIs has been very slow, and very few of these games support them, with most focusing on OpenGL and maybe DirectX 11. They are often limited to specific platforms as well, reducing the pool of players they could draw attention from.

One of the core objectives is to support Vulkan, a next generation rendering API with a focus on performance and optimization. It is however important not to rely on it directly, and allow for other rendering APIs to be used depending on the context, such as in other platforms.

Keywords: videogames, game engines, rendering, vulkan, voxel, API design

## Chapter 1

# Introduction: The Game That Could Have Been

Making a game is no easy task, and it becomes orders of magnitude more difficult if building a custom engine and tooling in-house. There are often hundreds if not thousands of moving pieces that constantly need to interact with one another to create the experience that the game's developers aimed for, and as such game development is not to be taken lightly.

Even simple ideas can amount to a massive time investment, and it is very easy for scope creep to drive a developer into overtime on something that could have been completed much faster had certain restrictions been established from the start.

While this project may be used to exemplify good systems and API design techniques, it also serves as a great example of not-so-good preproduction and planning, lack of prior research (although intentional), scope creep, and the effects of burnout.

I think the first question that needs to be answered is why this project exists in the first place, and it comes down to a few reasons:

- Familiarity with the genre (voxel sandbox see: Minecraft)
- The desire to learn about new graphics technologies (Vulkan)
- Investigating the design principles behind open-ended APIs that manage to retain a high level of concreteness
- An interest in modding as a first-class citizen: implementing the game's content using only the public-facing API

With those as the main set of goals, the project was divided into three: Platform Bindings, Engine and Game.

The platform-specific code would be developed first and provide an abstraction for anything that may be different across runtimes, such as window management, rendering, user input and audio. This would then act as the base to build the voxel engine, which would be developed in parallel with the game, the latter acting as a large scale integration test.

Out of these, the ones we will focus on the most will be the engine and game. However, it is still interesting to elaborate on some of the design decisions made when creating the platform-specific code, as its abstractions had to be designed to fit virtually any backend possible, even if only one is implemented at the time of writing.

This document will act as a post-mortem of sorts, going over most of the systems that were created as part of this project as they are in their final state, and should impart a solid understanding of the inner workings of the engine and game without getting overly technical. Exploring the source code to learn more about those systems is left as an exercise to the reader.

Subsequently, it will explore the development timeline to give better context as to how everything got to its current state and any setbacks and learnings encountered along the way.

I hope it will be an interesting read and that you might get a thing or two out of it.

## Chapter 2

# Objectives

The main goal of this project is to develop an engine for games with heavy voxelization (terrain, logical clustering, networking/persistence) and to create a game that utilizes it and shows off its capabilities.

### 2.1 Functional Goals

The main things this project tried to achieve from a technical and design point of view are the following:

- Developing a framework for cross-platform 3D application development
- Supporting at least one modern graphics API
- Creating a toolkit specifically geared towards the creation of voxel games with a lot of the optimizations that this constraint allows for
- Making a game that serves both as an example of the engine's capabilities, and as an integration test for the systems and APIs provided by it
- Developing a public-facing API and providing third-party developers with the tools they need to create their own content for the game
- Relying exclusively on the modding API to add all the content of the game

### 2.2 Functional Non-Goals

When developing a project it is always important to decide not only what is to be achieved, but also what is to be avoided. In this case:

- Supporting multiple platforms by the established deadline (future work)
- Targetting multiplayer experiences as the core of the engine
- Developing a complete game with a compelling amount of content

### 2.3 Personal Objectives

As with any project, this one also presents several goals which were in good part the driving force for its selection among the many available options and what provided interest and challenge. Some of these are:

- Learning C++ and C# through using them in real scenarios
- Learning the basics of modern graphics programming and in particular the Vulkan API
- Improving my API and systems design skills
- Creating, at least at the engine level, what would be my ideal voxel game and modding API

# Terminology

### 3.1 General Terms

AABB: Axis-aligned bounding box. A cuboid that is aligned to the axes of the world and represents a positive (or sometimes negative) space.

Blittable Type: A data type whose instances are stored as a contiguous block of memory without referencing any other objects.

Mod: Shorthand for modification.

Modding: The action of creating mods.

Nibble: 4 bits, or half a byte.

Octree: A tree data structure where each inner node divides into a cluster of 2x2x2 (8) child nodes. They generally have limited depth, and if all the child nodes of any given inner node contain the same data, they may be represented just by this parent node without taking up extra space. They are generally used to reduce the footprint of heavily repetitive data in 3D space.

Quadtree: The same as an octree, except used to represent 2D data instead of 3D.

Ray Casting: A technique by which it is possible to calculate the closest point of intersection between a ray (defined by its start and end positions, or a start and magnitude vector) and some arbitrary geometry.

Serdes: Serializer-deserializer. A process that can convert objects into bit streams and back.

Unmanaged Type: Blittable type.

Voxel: A cubical unit of space.

### 3.2 Videogame / Game Development Concepts

Game Engine: An optional piece of code that provides a game developer with tools to create their game, from graphics to physics and audio, all the way to networking and data persistence.

Game Loop: The part of a game's code that executes repeatedly and usually handles all the gameplay logic. In a lot of games it is the same as the render loop.

Procedural Terrain Generation: The process of generating terrain programmatically, frequently using noise and a random seed.

Render Loop: The part of a game's code that executes repeatedly and handles all the rendering-related logic. In a lot of games it is the same as the game loop.

Sandbox Game: A game where the player is given some tools and constraints and they are free to do whatever they want.

Voxel Game: A game where the terrain (and usually other elements like entities) is made up of voxels.

### 3.3 Technologies and Libraries

.NET: Formerly .NET Core. The official cross-platform framework for C# application development created by Microsoft.

GLFW: A small library providing cross-platform window management, input handling, and graphics context creation.

DirectX: Microsoft's Windows-only counterpart to OpenGL (version 11 and under) and Vulkan (version 12 and up).

Metal: Apple's proprietary counterpart to Vulkan.

MoltenVK: An abstraction layer that allows Vulkan code to run on devices that only support Apple's Metal, since Apple does not support Vulkan.

OpenAL: A widely cross-platform library for easy audio playback. It is not actively maintained anymore.

OpenGL: A legacy 3D graphics API that is supported by virtually all devices with advanced graphics support. It was created in 1992 by Silicon Graphics and control over the standard was transfered to the Khronos Group in 2006. It has been superseded by Vulkan.

Premake: An open source tool that allows for easy definition of projects and workspaces in multiple languages as Lua files, and which can then generate platform and tooling-specific project files for different IDEs and build environments.

ReSharper: A plugin for Visual Studio developed by JetBrains. It adds a lot of the features of JetBrains IDEs to Visual Studio.

Visual Studio: Microsoft's flagship IDE with support for dozens of languages and an extensive plugin ecosystem.

Vulkan: A low-overhead, cross-platform API for 3D graphics and computing that targets high-performance real-time 3D graphics applications, such as video games and interactive media.

It was created by the Khronos Group to supersede OpenGL in modern graphics applications. It was initially released in 2016.



### Chapter 4

# Platform Bindings and Backend Technologies

The choice to develop an in-house engine brings with it several major challenges, among which are the need for a cross-platform rendering backend and window management solution, a method to capture user input, and a way to play sounds through the system's speakers or headphones.

This project's goal is to provide a simple C# API that acts as an abstraction for all of the low level platform-dependent logic.

The platform bindings are more to be considered a byproduct of DigBuild's development since a third party abstraction could have been used in their place without any major compromises. As such, they will not be covered in the annexes. This chapter's goal is to explain the basics of their functionality and their role in the overall project to give better context to the reader, but not to go into detail on how they work.

### 4.1 Rendering Backend

Modern game development requires making the most out of the usually limited hardware in a wide variety of devices, and as such modern lower level APIs such as Vulkan, DirectX 12 and Metal are quickly replacing their beloved predecessors OpenGL and DirectX 11. These newer APIs grant developers much more fine grained control over the graphics drivers, allowing them to optimize their rendering pipelines and therefore increasing performance. However, this comes at the cost of boilerplate and additional steps where the same thing would have been a single function call in their legacy counterparts. It is worth noting that these newer APIs are not targetted to end users wanting to build their own graphical applications, but rather to engine and tooling developers who want to be able to squeeze every last bit of performance out of the target hardware.

The render API of choice for this project was Vulkan, as it is widely supported on Windows and Linux systems, and can be used on MacOS through MoltenVK. However, the project is architected in a way that additional render backends such as OpenGL can easily be added to support legacy systems.

One of the main advantages of Vulkan is its approach to sending commands to the GPU. OpenGL synchronously executes commands as they are fired by the CPU, which causes rendering to be heavily reliant on the processor as it has to wait for every action to complete before allowing the program to continue. Vulkan, on the other hand, uses Command Buffers, which are recorded on the CPU and submitted to a queue on the GPU for execution. The application can optionally wait for these buffers to complete execution, but it doesn't have to. This can result in major performance increases as it almost completely eliminates the CPU ↔ GPU synchronization bottleneck and allows other code to run on the render thread while the GPU is busy.



Figure 4.1: Rendering in OpenGL

The rendering backend handles most low level things like resource ownership, swapchain creation and re-creation, context sharing across windows, etc. This allows the developer to focus on the code that will be displaying images to the screen instead of micromanaging all of the low level elements.



Figure 4.2: Rendering in Vulkan

### 4.2 Window Management and User Input

Another challenge that arises when creating a custom rendering backend is that of window management, as it is greatly platform-dependent. As that is outside of the scope of this project, GLFW was chosen as the window management implementation for the entire desktop rendering backend. GLFW provides the tools to create render targets on Windows, Linux and MacOS, as well as to manage their render contexts and handle user events.

User input is also heavily platform-dependent. Luckily, GLFW provides the hooks for handling mice, keyboards and controllers. While controller support leaves a lot to be desired, it is sufficient for regular gameplay, and the internal structure of the bindings allows for the use of a more feature-complete controller library down the line if desired.

### 4.3 Audio Subsystem

The choice of a backend for audio playback is never an easy one, with options ranging from simple "call a function to play a sound" APIs to far more complex layered sound playback with 3D effects and advanced signal processing.

This project did not require very advanced audio features and the main requirement was cross-platform support, so OpenAL was picked to handle sound. It is not a very advanced audio library, but it provides the basic playback and 3D positioning features needed for a simple 3D game and, as with most things in the platform bindings, it can be swapped with a more advanced library such as FMod if necessary.

### 4.4 Internal API

One of the main difficulties in supporting multiple tools and libraries with different API surfaces arises from the need to create an abstraction. In the platform bindings, this abstraction is located within the C++ code, since any high performance library that needs to interact with the system will be written in C/C++.

This abstraction layer was created to allow new window management systems, render APIs and user input handlers to be added in the future, supporting new platforms while retaining the same developer-facing API.

### 4.5 Developer-facing API

While the platform-dependent code is for the most part written in C++, a C# API is required for the game and engine to be able to interact with the native code from the .NET runtime. For the most part, this API just acts as a bridge between the C++ abstraction layer and user code, providing stronger typing than if the native code were being used directly.

### 4.6 Testing and Debugging

The platform bindings ship with a demo C# project that shows off some of its capabilities and that may also act like an integration test for the core set of features. This project must run on any supported device and should behave the same regardless of the backends being used.

## Chapter 5

# Engine Architecture and Game Scaffolding

With a platform-agnostic API in place to manage rendering, audio and input, development on the engine can begin.

The goal of the engine is to provide structural elements to greatly ease the development of voxel games, and can also act as a common API surface for mod developers.

This chapter will cover some of the most important systems and APIs provided by the engine and how they contribute to any game made using it.

### 5.1 Structuring Voxel Worlds

The first building block for almost any game is a location for it to take place in. They go by different names depending on the genre and sometimes the specific game, but "world" or "level" are the most common. The game world generally acts like the central data structure containing everything that is part of gameplay except for the user interface, storing terrain features, entities, information about the time of day and weather, etc.

This engine differs from most voxel engines in that the world has very few direct responsibilities and instead offloads them to user-provided data structures and procedures. This means that anyone - be it the game itself or a third party mod can add new data structures and logic to the world to store any information they see fit.

In addition to world-level data storage and due to the (virtually) infinite in size nature of the game world, the engine also provides two levels of subdivision: regions and chunks. Chunks divide the world into 16x256x16 blocks and data associated with them tends to be highly localized. Regions are clusters of 64x64 chunks along the horizontal plane.

By default, the engine ships with data structures for terrain, lighting, and entity storage.

#### 5.1.1 Terrain Storage

Voxel terrain presents several interesting challenges when compared to the more traditional "mesh" terrains found in most games. Among other things, it can be modified, must be persisted when changed, and has a high density of data as it must store not only what is on the surface, but everything underneath as well and also all the invisible air blocks above it.

The built-in implementation of block storage happens at the chunk level and is handled through 5-layer octrees. These allow the system to reduce the footprint of repetitive data, such as chunks filled with only air blocks or only stone, both in system memory and in disk. However, in chunks with more complex block arrangements or large varieties of blocks this might result in the data taking up more space. This is acceptable because the simpler chunks will greatly outnumber the complex ones.

Figure 5.1: Quadtree (2D) example of block data compression.

Along with their type, some blocks may also want to store instance data on a per-position basis such as inventories, fluid containers or progress bars. Since this data is unique to each block and rather uncommon, it is stored in its own Position→Instance lookup table within the chunk, which in most cases will be completely empty and thus take up minimal space.

#### 5.1.2 Lighting Storage

The approach to light value storage is very similar but employs some additional tricks to pack data slightly more efficiently. To understand why these changes were made, it is necessary to first know how light is represented and propagated.

A light value is in the range of 0-15, which allows it to be stored in just 4 bits, or a nibble (half a byte). Non-illuminated blocks have a light value of 0, and light-emitting blocks may have any value from 1 to 15. This value is reduced by 1 every time it propagates to a neighboring block until it reaches 0. The light value at any given position could be represented by the following formula, which employs the Manhattan/Taxicab distance between the current block and nearby lightsources to determine the propagation loss:

light(
$$Pos$$
) = max ({0}  $\cup$  { $LVal$  -  $\|LPos - Pos\|_1$  |  $(LPos, LVal) \in Lights}$ )

The naïve approach to storage would be to save each light value as a byte, since that is the smallest unit of memory we can allocate. However, this wastes half a byte per block position, resulting in only 50% of the allocated memory actually being utilized.

#### 5.1.3 Entity Storage

Storage and retrieval of entities are very difficult to implement correctly in a chunk-based game due to the fact that entities not only have a position, but also occupy a volume and can move between chunks, and may at any point in time be located at one or several chunk boundaries. There must also be a way to look up any given entity by ID, regardless of where it is in the world.

The built-in implementation is not ideal since it does not account for the volume of an entity, but in a lot of cases that ends up being irrelevant, and everything else is handled by storing data in two different ways:

- Entities are stored at the chunk level based on their position and are persisted to disk
- A dictionary of IDs to entity instances is stored at the world level for lookups, and is only populated with currently loaded entities

This allows chunks and their respective entities to be loaded and unloaded dynamically while still allowing for quick lookups. When an entity's position changes, it must notify the chunk it was in that it has left, and inform the new one that it must now handle its storage. Since the engine doesn't provide any logic to handle entity positioning and movement, this must be handled by the game developer.

### 5.2 Blocks, Items and Entities

The next set of things that are needed once worlds have been established are the elements that will occupy said worlds. Blocks, items and entities make up the core content of both the game and third-party mods and are architected almost identically to each other. From here on they will be collectively refered to as game objects.

Much like other systems in the engine, they are built on the core principles of modularity and extendability, and as such are composed of two sets of elements: data classes and behaviors. These allow for high modularity and code reusability.

#### 5.2.1 Data Classes

A data class represents some information that is fully local and internal to a game object, meaning its contents may only be accessed by behaviors in the same game object with access to a direct handle. Due to the clonable nature of every bit of data in the engine, all data classes must contain a Copy() method that returns a new deep copy of the instance where it is called.

#### Example data class:

public class CounterData : IData, ICountingBehavior { public uint Number { get; set; } public ComplexType SomethingElse { get; set; } public CounterData Copy() { return new CounterData() { Number = Number, SomethingElse = SomethingElse.Copy() }; } public static ISerdes Serdes [...] }

Persistence to disk is optional and, if enabled for any given handle of a data class, requires a fully qualified name and a serialization and deserialization handler to function correctly. In this case the class must also implement IChangeNotifier, which allows the save system to know when the data has changed so it can be persisted at the next possible opportunity.

### 5.2.2 Behaviors

Behaviors handle all the business logic behind game objects. Much like data classes, they are internal to a game object and cannot be accessed externally. They have two main roles: handling events, and exposing attributes and capabilities.

If a behavior needs to store data locally to the game object, it must define a contract interface. This contract, if present, must be fulfilled at the time of attaching the behavior to a game object.

The Build(...) method in a behavior allows its designers to subscribe to any of the events supported by the target game object, as well as to register providers for attributes and capabilities.

#### Example contract:

public interface ICountingBehavior { // We need to store a number we can get and set uint Number { get; set; } }

#### Example behavior:

public class CountingBehavior : IBlockBehavior

{ public void Build( BlockBehaviorBuilder<...> block ) { // Subscribe to the "activate" (click) event block.Subscribe(OnActivate); } private BlockEvent.Activate.Result OnActivate( BlockEvent.Activate evt, ICountingBehavior data, Func next ) { // Increase the number when the block is activated data.Number++; // The interaction was a success, so the next() function // isn't called and a value is returned directly instead return BlockEvent.Activate.Result.Success; } }

### 5.2.3 Attributes and Capabilities

Since a game object's data classes and behaviors are internal, other objects or systems cannot access any information within them or communicate with them directly. Attributes and capabilities provide a way to interface with a game object regardless of any implementation details.

Attributes represent read-only information about a game object, like the position and bounding box of an entity, or the light output of a block.

Capabilities expose interfaces with properties and methods which third parties can use to interact with and modify the state of the game object, such as interfacing with an inventory or a tank.

In a lot of cases attributes and capabilities are seen in tandem, providing both a read-only view of the data, as well as an interface to modify it.

When initially registered, a default value must be provided, or alternatively a fallback function that will return a value. This allows for attributes and capabilities to be present even in game objects that do not explicitly support them, like deriving the collision and raytrace bounding boxes for a block from its bounding box attribute, or making the default light emission of a block be 0.

#### 5.2.4 Integrating Data and Behaviors

As mentioned before, every game object is composed of a set of data classes and behaviors which are added during construction and cannot be modified afterwards. Any number of handles of the same data class and instances of the same behavior may be added to any given game object.

If a behavior requires a contract to be fulfilled (that is, it needs to be able to store some data), this must be done by a data class or one of its members when the behavior is attached.

This is also where the serdes is provided for data classes which need to be persisted to disk.

#### Example block creation:

CountingBlock = registry.Create("digbuild", "counter", builder => { // Add a new handle of type CounterData var data = builder.Add( new ResourceName("digbuild", "counter"), CounterData.Serdes // Serialize/deserialize with the world ); // Attach a new counting behavior whose // contract is fulfilled by this handle builder.Attach(new CountingBehavior(), data); });

### 5.3 Ticking and Job Scheduling

Recurring and deferred workloads are some of the most common in games since most actions do not happen immediately, and computations like physics need to take place every tick.

DigBuild engine's world API provides access to a Scheduler class which allows developers to defer work to later ticks. This deferred work can take two forms: tick events and jobs.

### 5.3.1 Tick Events

Tick events are the simplest way of scheduling deferred workloads. They allow an Action to be called after a certain amount of ticks. They are most often used for one-off deferred work.

Example deferred tick event: Action sayHi = () => Console.WriteLine("Hello World!"); world.TickScheduler.After(5).Tick += sayHi;

#### 5.3.2 Jobs

The job system offers a more data-oriented flow, allowing the developer to register a job handle with a function that will be called with every element that is enqueued to the job in any given tick. Sequential and parallel processing are supported by default, but custom job types such as fork-join can be implemented via the API.

Example job registration and scheduling: // Registration LogJob = registry.CreateSequential( "digbuild", "console\_log", str => Console.WriteLine(str) ) // Scheduling world.TickScheduler.After(5).Enqueue(LogJob, "Hello World!");

### 5.4 Events and Event Buses

Events within game objects are dispatched and handled internally to preserve ordering and allow for more fine-grained control over event flows. However, systems generally need to notify other systems when something happens so that they may react accordingly. This is where the event system comes into play.

Event buses act as a central location where event consumers can register handlers for all the events they must react to, and where they can post their own events as they take place.

The API provides no guarantees for the order in which handlers will be called, but it will always happen sequentially (avoiding any potential race conditions).

Events posted to the bus cannot have a return value like the ones in game objects, so if something similar is needed, a value within the event must be modified and retrieved once it has been dispatched to all handlers. This is also a valid approach for short-circuiting events, requiring handlers to check whether the event should be processed or ignored.

### 5.5 Terrain Generation

Procedural terrain generation is an incredibly complex topic that even at the surface level (no pun intended) could very well take up hundreds of pages to explore (again, no pun intended). Every terrain generation system takes a different approach and is generally very specific to the kind of game being made, technical requirements, and other factors such as the kinds of elements that can make up the world (terrain, rocks, buildings, lootable chests, etc).

Chunk-based procedural generation presents several problems, the main of which is posed by terrain features that span multiple chunks or are located on chunk boundaries. Terrain voxelization helps with this to an extent, making the parts of each feature that are in a chunk physically belong to that chunk, but it does not solve problems like depending on information about surrounding areas.

The approach taken in engine divides terrain generation into two passes:

- An initial description phase where attributes are assigned and modified by the different terrain features in order to create a pure data representation of a vertical slice of the world (chunk)
- A population phase where each feature analyzes the previously generated descriptor and populates the terrain with blocks and other relevant data

Although seemingly simple, this system offers a great deal of flexibility and can result in very complex procedural worlds without excessive amounts of overhead.

### 5.5.1 Description Phase

During the description phase, features are allowed to query other chunks to determine if larger elements or those on chunk edges are feasible, but are not allowed to change their values. Furthermore, the only information they can access about neighboring areas is what has been settled by the features that generated prior to the current one. This prevents excessive cascading problems and allows generation to happen, effectively, one feature at a time, even across large areas of terrain with massive features.

A feature will generally set the value of certain attributes in this phase, such as the terrain type (grassy, sandy, salt water) or height at a specific position. In some cases it may also want to modify existing values, such as a lake feature reducing the terrain height in the area where it generates and changing its terrain type to fresh water.

Since each feature can alter any other feature's already established values, they can cooperate to create more complex formations and compliment or even disable each other. For example, an area may originally be a forest, but if a lake feature generates in the middle of it, the new terrain type will prevent trees from appearing in the water.

#### 5.5.2 Population Phase

The population phase is quite straightforward in that the only input it receives is the previously generated description. Features must check all the attributes that are relevant to their generation and utilize those to populate the blocks or other chunk information that may be needed.

#### 5.5.3 Worldgen Features and Attributes Applied

A worldgen feature does not necessarily have to affect the terrain, as the name might seem to imply, nor does it even have to write any data to the world during the population phase.

Features may be used to initially populate generation attributes with values drawn from noise functions, such as an initial heightmap of the world, but they may also use other noise functions to affect existing attributes, such as an "inland factor" pushing the terrain above or below the ocean level.

Already populated attributes may also be used to constrain the generation of certain features, like making sure lakes don't try to generate in the middle of an ocean, or avoid planting trees on a body of water.

The specific order that is used when applying the different worldgen features will greatly affect the generated terrain and its properties, so it is always important to make sure constraints are properly established to ensure correct generation of the terrain.

It is also worth noting that blocks are not the only thing that can be generated by features. Any data that exists at the chunk level can be. That includes things like entities and lighting, but also third party data like the initial density of magic energy in the air added by a mod.

### 5.6 Entity Physics

Realistic physics simulations are generally very complex in nature and require exponentially more computation power the more objects there are in close proximity to deliver accurate results. Game developers employ a plethora of different techniques to reduce this overhead and simplify the problem so that thousands, or even millions of objects can be processed every frame.

The physics system in the engine is simple while remaining fairly extendable. It operates on the intersection between an axis-aligned bounding box and some user defined geometry, calculating an offset by which this AABB travelling in a certain direction must be displaced to avoid colliding with the target geometry.

The ICollider interface defines the contract for this behavior as a function of the colliding AABB and its motion vector.



Figure 5.3: Axis-aligned bounding box colliding with an arbitrary shape.

#### ICollider:

public interface ICollider { bool Collide(AABB target, Vector3 motion, out Vector3 intersection); }

The engine provides null colliders as well as single- and multi-AABB implementations out of the box. The AABB implementations support both static and swept (interpolated) collision.

### 5.7 Raycasting

While not often getting as much recognition as other ray-related techniques such as raytracing and raymarching, the ability to cast a ray in any direction and determine what it collides with is paramount in game development. It is key to everything from player interaction to NPC AI, and even physics.

The implementation in engine targets voxelized environments and is as such based on the classic DDR algorithm, which proves to be a quick and efficient solution to axis-aligned world traversal.

Similarly to the physics system, IRayCollider provides the contract for ray collision with any arbitrary user-defined shape.

#### IRayCollider:

public interface IRayCollider { bool TryCollide(Raycast.Ray ray, [NotNullWhen(true)] out THit? hit); }

### 5.8 Serializing Code Entities

Data persistence is of course also a core element in most kinds of games, although not all. The engine takes a fairly standard approach to data persistence using the serdes (or serializer-deserializer) model across two classes: IDeserializer, and ISerdes which extends the former.

A deserializer exposes a way to turn a bit stream into an object, optionally parsing additional information from the current context. A serdes adds to that the ability to encode said object into a bit stream.

IDeserializer and ISerdes interfaces: public interface IDeserializer<out T> { T Deserialize(Stream stream, IDeserializationContext context); } public interface ISerdes : IDeserializer { void Serialize(Stream stream, T obj); }

Combined, they provide a simple yet effective framework for serialization and deserialization of objects, and allow this process to not necessarily be managed by the object itself, but also by a third party. This may prove especially useful when something needs to be encoded differently depending on the context, like disk persistence and networking.

Several implementations are provided by default, such as one for blittable (unmanaged) types, and prefabs for arrays, lists and dictionaries. There is also a prefab that wraps any other serdes to automatically handle nullability.

One thing that developers must always take into account when writing serdes logic is the possibility that data may change over time, so it is generally recommended to include some form of versioning in serdes, be it a version header or something more advanced.

### 5.8.1 Serdes Made Easy: CompositeSerdes

The simplest way to handle serialization and deserialization of regular objects is by way of a CompositeSerdes. This class allows the developer to easily create a serdes for any type and includes simple yet versatile versioning.

A composite serdes is made up of one or more members, composed of an ID, an expression that points to the field or property that holds the data and a serdes for it.

For correct functioning of the composite serdes, all IDs must follow a set of rules:

- It must be unsigned and positive, and as such higher than 0
- It must be unique within the composite serdes
- If the member is removed, its ID must never be used again in that serdes
- If the serialization logic changes, the member must be assigned a new ID

These properties of the ID are what create the intrinsic versioning of the composite serdes. A very easy way to achieve this is to increment a number by one for each member and use that as the ID.

A very obvious problem with that ruleset, however, is that data loss is not only possible but enforced when changing the serialization of a member. The composite serdes solves this by using the same ID, but as a negative number, which will instruct the system to only perform deserialization.

CompositeSerdes usage example: // Target class public class MyDataClass { public int Score { get; set; } // public int Health { get; set; } public float Health { get; set; } // Replaces int health public ItemInstance ItemInHand { get; set; } } // Serdes definition new CompositeSerdes() { { 1u, d => d.Score, UnmanagedSerdes.NotNull }, //{ 2u, d => d.Health, UnmanagedSerdes.NotNull }, { -2, d => d.Health, UnmanagedSerdes.NotNull .Casting(i => (float) i) }, { 3u, d => d.ItemInHand, ItemInstance.Serdes }, { 4u, d => d.Health, UnmanagedSerdes.NotNull } };

In this example the Health property has been changed from an int to a float. A deserializer for the int version is provided, which allows data in the old format to still be deserialized, and any further serializations will omit index 2 and only output 1, 3 and 4.

### 5.9 Data Persistence

While some games are designed around the idea of not allowing the player to save their progress, most titles want to give their players the possibility to take a break and pick up the game again at almost any time they want.

The engine does not provide a way of persisting world data per se, since each game may want to do that differently, but it does provide a simple yet flexible framework to segment the world and notify the game code whenever a change that needs to be persisted has happened.

As was mentioned earlier, worlds are composed of regions, which in turn are made up of chunks. The system that internally handles chunk loading and generation, also interfaces with the persistence API to load already existing chunks and regions and save them when a change is made or they are unloaded.

The main API for this system is the IRegionStorage interface, a supplier for which is provided during the creation of the world.

#### IRegionStorage interface:

public interface IRegionStorage { // Chunk loading and saving bool TryLoad( RegionChunkPos pos, [NotNullWhen(true)] out Chunk? chunk ); void Save(Chunk chunk); // Region data loading. Saving is handled by subscribing // to the container's change notifier DataContainer LoadOrCreateManagedData(); }

The Chunk class provides a serdes for easy serialization and deserialization of all data within it to a bit stream, and the target format is left down to the implementation. It may be plain binary files, a SQLite database, or a more esoteric format containing other metadata and partial write mitigation.

### 5.10 Networking

Multiplayer functionality is highly desirable in modern games. Seeing the state of the world over the past year, many people took to multiplayer videogames as a way to socialize and interact with others while they could not leave their homes. Not only that, but multiplayer games can be an experience of their own, like in the game Journey by Thatgamecompany.

The network stack in the engine is simple but effective. It employs a server-client architecture and provides reliable communication over TCP sockets.

Packet types can be registered using resource names and the networking system will take care of assigning each of them a numeric ID, which reduces overhead considerably, especially in packets with smaller payloads, and synchronizing those mappings with all the connected clients so they can understand each other.

A packet simply needs to implement the IPacket interface and be added along with a name and a serdes to the corresponding registry to be ready for use. Client and server network managers then allow for those packets to be sent back and forth.

### 5.11 Particle Systems

In most cases, geometry and animations alone are not enough to convey an idea visually, and particles provide a simple way to add that extra bit of flare or noise to a visual element that really makes it feel complete.

The included implementation heavily leverages modern GPUs' ability to do what is called "instanced rendering". This is a technique wherein a set of vertices are provided to the renderer, and it is told to draw them several (possibly thousands

or millions) of times. Each of these instances of the geometry may have some data attached, like a position, color, etc. This proves to be a very efficient way to draw the same geometry over and over, and provides a massive reduction in memory footprint.

Particles are defined as two structs: one that represents the particle in system memory, and one that represents it in GPU memory. The CPU representation must implement the IParticle interface and specify the GPU representation as a type argument.

#### IParticle interface:

public interface IParticle where TGpuParticle : unmanaged { bool Update(IParticleUpdateContext context); void UpdateGpu(ref TGpuParticle gpu, float partialTick); }

An interesting thing to note is that particles on the CPU and GPU are updated separately. This is because particles on the CPU update every game tick (for example 20 times per second), and particles on the GPU update every frame (for example at a rate of 60FPS). This is done to reduce computation costs for things like physics, which happen during the CPU tick, but still provide the ability for smooth animations and transitions of GPU-bound data.

#### Example fire particle:

// System memory representation public struct FireParticle : IParticle { public const byte MaxAge = 22; public byte Age; public Vector3 Position; public Vector3 Velocity; // Called every game tick public bool Update(IParticleUpdateContext context) { // Update position and velocity [...] // Once this returns false, the particle will die return ++Age < MaxAge; } // (Cont'd)

// Called every frame with a partial tick for interpolation public void UpdateGpu(ref GpuFireParticle gpu, float partialTick) { gpu.Position = Position + Velocity \* partialTick; gpu.Age = (Age + partialTick) / MaxAge; } } // GPU memory representation (instance data, readable in the shader) public struct GpuFireParticle { public Vector3 Position; public float Age; }

The particle system will ensure that all particles that are currently alive are kept in contiguous memory for faster iteration, and will intelligently fill in blanks left by particles that have just died with other particles that are still alive. This also makes it easy to spawn new particles, since they just need to be added to the end of the contiguous block of memory taken up by the ones that are currently alive.

### 5.12 Rendering the World

So far we have mainly tackled data structures and business logic that happens during the game loop, but very few games can get away without any visuals.

World rendering in the engine involves a considerable amount of moving parts which allow for some very advanced techniques to be used without too much added complexity for the developer.

A collect-then-execute approach allows any renderable element to contribute any form of geometry they want to the world, regardless of depth, fragment ordering and other similar issues commonly encountered in rendering.

#### 5.12.1 Render Layers

### 5.12.3 The Render Hierarchy

Just like the world is divided into regions and those into chunks, rendering is also divided into levels to provide a simple way to fully leverage the backing data structures.

The top level is taken by the world, and IWorldRenderer implementations can be used to accumulate geometry and uniforms that exist on the world level. An implementation of this is coincidentally the chunk renderer, which loops through all the chunks and draws them.

Chunks are drawn by a set of IChunkRenderer instances, which may access any local data in the chunk while drawing. Since multiple chunks will be on screen at once, chunk renderer updates may be dispatched in parallel for higher efficiency on multi-core systems. An implementation of this would be what draws the blocks that make up the terrain in a chunk.

These two interfaces and any types derived from them provide a flexible framework for drawing any geometry as part of the world.

### 5.13 User Interfaces

A player often needs to interact with elements in the game that are not part of the world, and giving developers the tools to create dynamic user interfaces opens up a lot of possiblities for new forms of interaction.

While not too complex or feature-packed, the UI framework provided by the engine is enough to create anything from basic to very complex user interfaces in minutes. It all revolves around the IUiElement interface.

IUiElement interface:

public interface IUiElement { void Draw( RenderContext context, IGeometryBuffer buffer, float partialTick ); void OnCursorMoved( IUiElementContext context, int x, int y ); void OnMouseEvent( IUiElementContext context, uint button, MouseAction action ); void OnScrollEvent( IUiElementContext context, double xOffset, double yOffset ); }

The built-in UI elements are designed around the idea of nesting, and as such UiContainer generally acts as the glue for other UI elements and gives them a space to exist in.

Also included are UiButton, with an idle, hovered and clicked state, UiLabel which displays a line of text, UiRectangle which draws a solid colored rectangle, and UiTextbox, which, when clicked, allows the user to input text.

This functionality can be enhanced by game developers by allowing multiple UIs to be layered on top of each other like windows, handling how cursor events are passed through to other UI elements, and managing control over the keyboard.

### 6.1 A Few Words on Modding

Mods wildly expand the possibilities within a game, allowing the community around it to create and share new content that the creators may not have thought of or considered balanced/fitting, and in cases even altering the base experience to the point where it becomes unrecognizable.

### 6.2 Bootstrapping

When initially launched, the game will perform several tasks in order to initialize its internal state.

- Creating an event bus
- Loading all the mods (including the built-in mod with the content of the game)
- Initializing and populating all the registries
- Creating a new instance of the game
  - – Initializing particle renderers
  - – Initializing the audio subsystem
  - – Creating a new window
  - – Setting up the gameplay controller to handle logic and rendering
- Starting the game loop

Once the game is running, it may be stopped or closed at any time, and the bootstrapper will keep the main thread alive until all runtime resources have been evicted and perform an orderly shutdown.

### 6.3 Game Controllers

The game state, logic and rendering, are all managed by controllers. They are in charge of all the housekeeping needed for any one part of the game to be functional, like allocation and deletion of any resources.

### 6.3.1 Gameplay Controller

The only controller present at the time of writing is the "gameplay controller", which as the name implies, manages everything related to gameplay. This includes creating the world and its dependencies (save handlers, terrain generation, etc), handling mouse/keyboard/controller input, and maintaining the UI stack. This is also where networking would be managed in the case of supporting multiplayer.

Aside from handling all the business logic, it is also in charge of all rendering associated with it, which in this implementation includes the world and UI rendering.

Of course, putting so many responsibilities into one class could easily lead to messy, unmanageable code. This is why almost everything is delegated to more specific handlers, such as the world renderer, UI manager, or input controller, and the gameplay controller purely acts as an aggregator and holder of shared state.

### 6.4 World Generation

DigBuild's approach to world generation greatly exploits the possibilities offered by the engine's API by creating a heavily dynamic and inter-connected system that is capable of generating complex worlds with very few parameters. It does this by dividing generation into 3 main phases:

- Establishing constraints
- Picking biomes
- Populating terrain

Doing this provides a simple yet consistent structure for any generation attributes and features that may be added down the line and gives them additional contextual information they can use to improve their generation.

### 6.4.1 Environment Constraints

The first step towards creating wildly dynamic worlds in DigBuild is determining an initial set of constraints that will determine the overall look of the world. These constaints are a projection of a smooth noise function (simplex noise) onto the horizontal plane, and used to determine the following factors:

- Inlandness: How inland (1.0), coastal (0.5), or completely submerged under the ocean (0.0) a bit of terrain is.
- Temperature: How hot (1.0), temperate (0.5), or cold (0.0) a bit of terrain is.
- Lushness: How densely packed with flora (1.0) or barren (0.0) a bit of terrain is.

These could be expanded upon to introduce constraints based on height, humidity, fault lines and more, and potentially make some of those depend on each other, so the farther inland some terrain is, the higher the chance of it having a high peak, for example.

#### 6.4.2 Biomes

Biomes provide a clear and easy delimitation between different environments, terrain types, and can greatly aid in fencing worldgen features to areas of the world that meet certain criteria.

The biome system in DigBuild has two jobs: picking a biome for any given position based on some constraints, and defining a new set of attributes and constraints for the features generating afterwards.

The selection system uses each biome's constraints to calculate a score for each position in the world, and the biome with the highest score is chosen for that location. This may result in slightly harsh borders between biomes and could be

fixed by applying a smoothing function to the scores with a given block radius after they have been calculated before determining the biome for a given position. The biomes included with the game are: grassland, pasture, tundra, plaeau, beach, gravel beach, ocean and frozen ocean.



Figure 6.3: Grassland, beach and tundra biomes meeting in one spot

The grassland biome in Figure 6.3 is defined as follows:

#### Example grassland biome:

new SimpleBiome() { Constraints = new WorldgenRangeSet { // Inlandness = (0.5, 1.0) { WorldgenAttributes.Inlandness, 0.5f, 1.0f }, // Temperature = (0.4, 1.0) { WorldgenAttributes.Temperature, 0.4f, 1.0f } }, Attributes = new BiomeAttributeSet { // Make the surface block grass { BiomeAttributes.SurfaceBlock, GameBlocks.Grass }, // Set the terrain type to ground { BiomeAttributes.TerrainType, TerrainType.Ground }, // Hint that the terrain height should be 12-16 blocks { BiomeAttributes.TerrainHeightRange, new RangeT(12, 16) } } }

#### 6.4.3 Features

Although one may initially assume otherwise, picking a biome alone does not actually result in any terrain generation. A biome only provides the guidelines for future features to generate, and that includes things like terrain.

In their default order of execution, the worldgen features in DigBuild and their functions during the description phase are:

- Terrain: computes the terrain height and type (ground, water, etc) based on the biome hints.
- Terrain Smoothing: applies a smoothing function to terrain height to make biome transitions smoother.
- Tall Grass: determines where grass/weeds will spawn, preferring areas of higher lushness in grasslands, pastures and plateaus.
- Barley: similar to tall grass, except only in pasture biomes.
- Water: determines where large bodies of water will spawn (ocean, frozen ocean).
- Trees: determines where trees will spawn, preferring ground terrain in lush environments.



Figure 6.4: Barley growing among a patch of grass

Once the chunk description has been computed, it can proceed to population:

- Terrain: populates the overall terrain shape, from the bottom of the world to the terrain height, with dirt except for the topmost layer which is either specified by the biome, or alternatively defaults to grass.
- Terrain Smoothing: does not populate anything.
- Tall Grass: spawns grass patches where they have been set to generate.
- Barley: spawns barley patches where they have been set to generate.
- Water: fills from the terrain height up to the water level with water blocks, and replaces the top layer with ice depending on the temperature.

- Trees: spawns trees where they have been set to generate.

### 6.5 Blocks, Items and Entities

DigBuild on its own provides a relatively limited palette of blocks the player can use to create their own builds, with most being purely decorative. The interactive blocks, however, tend to present some interesting or unique behavior such as:

- Grass: when a solid block is placed on top of it, it becomes dirt.
- Logs and Small Logs: can be built up from the ground and when one of them is broken, all the ones above will also fall.
- Leaves: will despawn if they cannot pathfind to a log through other leaves in a 3 block radius. They drop twigs and saplings.
- Stone Stairs: present directionality and two bounding boxes.
- Crafter: emits light and displays a user interface when clicked. This user interface is currently disabled and does not do anything.
- Campfire: emits lights and produces fire particles.

Most of the items in the game are just the inventory-friendly counterparts of blocks, however three items stand out from the rest:

- Twig: drops from leaves.
- Sapling: will spawn a tree when clicked onto the world.
- Pouch: stores items. When in the player's hand or an equipment slot, any picked up items will go directly into it. Its inventory can be opened by clicking.

Only two entities are part of the core game, mainly due to the added complexity and time investment of creating animated models and rigging them:

- Player: the entity which represents the user. Has a 10 slot hotbar and an 8 slot equipment inventory for armor and other items like pouches.
- Dropped Item: the in-world representation of an item after it has been dropped by a block. It will slowly approach the player when they get nearby until it gets picked up.

### 6.6 Block and Item Models

Arguably one of the most interesting systems which are native to DigBuild and not part of the engine is the model system, which allows for complex geometry to be created, combined and even animated through very simple JSON files.

The system is equipped with an advanced yet easily extendable function parser which allows certain data in a model to be parametrized and operated on, be it for specification in higher levels of the model hierarchy, or deferred to code for more advanced functionality.

#### 6.6.1 Defining Geometry

All geometry definitions must be located within the geometry folder at the root of the mod's asset directory. Nesting folders inside it is allowed and in most cases recommended for organization purposes. It is advised to create an items and blocks folder inside the geometry root to sort the respective models.

The JSON format for geometry is simple, but can vary depending on the types used. At the root is an elements array, which contains every piece of geometry that is part of the model. Each element must have a \_type member which determines what provider will be in charge of supplying the geometry. Any other members of the element are fully dependent on the selected type.

#### 6.6.1.1 Foreword: Parametrized Expressions

Certain data may be parametrized when defined inside a geometry element. This is done through DigBuild's expression parser. It allows for string interpolation into other strings, as well as basic math operations when working with numbers and is extendable to support more advanced features.

To interpolate a string, the standard \${variable\_name} format is used. If this variable may not be present and in that case should have a default value, one can be specified like this: \${variable\_name|default\_value}.

Numeric operations must take place within double braces {{ 1 + 2 }} and variables may be used as operators like so: {{ \${angle} \* 90 }}. The supported operations are addition, subtraction, multiplication, division and modulo. Parentheses are currently not supported.

#### 6.6.1.2 Basic Cuboid Geometry

The most common type is digbuild:cuboid, which takes in 4 inputs:

- from: a 3 element array indicating the first corner of the cuboid.
- to: a 3 element array indicating the second corner of the cuboid.
- textures: an object where each key-value pair represents a face of the cuboid and its texture. If a face is ommitted, it will be missing from the geometry.
- layer: the world render layer the generated geometry will be in.

Out of those, each of the individual textures as well as the layer can be parametrized with an expression.

Built-in \_cube.json geometry:

{

"elements": [

{

"\_type": "digbuild:cuboid",

"from": [ 0, 0, 0 ], "to": [ 1, 1, 1 ], "textures": {

"neg\_x": "\${textures/neg\_x}", "pos\_x": "\${textures/pos\_x}", "neg\_y": "\${textures/neg\_y}", "pos\_y": "\${textures/pos\_y}", "neg\_z": "\${textures/neg\_z}", "pos\_z": "\${textures/pos\_z}"

},

"layer": "\${layer|digbuild:solid}"

} ] }

#### 6.6.1.3 Including JSON and OBJ Geometry

In a lot of cases it is convenient to be able to use geometry that is already in use elsewhere or that exists in a format that is not natively supported. For that purpose, DigBuild also provides JSON and OBJ geometry includes.

Other JSON geometry can be loaded using the digbuild:include type on an element. It has two inputs:

- geometry: the fully qualified name of the JSON to be included, or alternatively the relative path to it (in both cases without extension).
- variables: (optional) defines a set of substitutions to be applied to the included geometry's variables.

Only the overridden variables may be parametrized with an expression.

OBJ geometry can be loaded using the digbuild:include\_obj type and specifying two inputs:

- model: the fully qualified name of the OBJ to be included, or alternatively the relative path to it (in both cases without extension).
- layer: the world render layer the generated geometry will be in.

In this case, only the layer can be parametrized with an expression.

#### Built-in \_cube\_all\_sides.json geometry:

{ "elements": [ { "\_type": "digbuild:include", "geometry": "\_cube", // Include the cube from earlier "variables": { "textures": { // Set all textures to the same variable "neg\_x": "\${texture}", "pos\_x": "\${texture}", "neg\_y": "\${texture}", "pos\_y": "\${texture}", "neg\_z": "\${texture}", "pos\_z": "\${texture}" } } } ] }

#### Built-in campfire.json geometry:

{ "elements": [ { "\_type": "digbuild:include\_obj", "model": "campfire", "layer": "digbuild:solid" } ] }

#### 6.6.1.4 Transforming Geometry

Being able to transform some geometry can also be incredibly useful, and as such the digbuild:transform type provides a way to perform simple operations on other elements. The inputs are as follows:

- rotation: a JSON object with a single key-value pair representing the axis to rotate around and the angle in degrees.
- element: a raw geometry element, like the ones found in the elements array of the geometry JSON file.

The rotation angle may be parametrized with an expression, and of course also anything within the transformed element that supports it.

#### Built-in \_cube\_rotated\_top.json geometry (abridged):

{

"elements": [

[...], // Fixed -X, +X, -Y, -Z and +Z faces

{

// +Y face rotated by a multiple of 90 degrees

"\_type": "digbuild:transform",

"rotation": { "y": "{{\${angle} \* 90}}" },

"element": {

"\_type": "digbuild:cuboid",

"from": [ 0, 0, 0 ], "to": [ 1, 1, 1 ], "textures": {

"pos\_y": "\${textures/pos\_y}"

},

"layer": "\${layer|digbuild:solid}"

} } ] }

### 6.6.2 Parsing Geometry

When loading a geometry JSON, each element is parsed independently. Initially the \_type property is read and used to determine which provider will be in charge of each element, and after that the provider is invoked with the element's data to obtain a bit of partial geometry.

#### IGeometryProvider interface:

public interface IGeometryProvider { IPartialGeometry Provide( JsonElement json, JsonSerializerOptions jsonOptions, ResourceManager resourceManager, ResourceName currentFile ); }

Partial geometry is such that variables may remain unresolved. It provides a method to apply a set of substitutions and return a new partial geometry with those changes applied, as well as a way to prime it and turn it into raw geometry.

IPartialGeometry interface: public interface IPartialGeometry { IEnumerable RequiredVariables { get; } IPartialGeometry ApplySubstitutions( IReadOnlyDictionary variables ); IRawGeometry Prime(); }

Raw geometry is such that all data required for loading is present and the only unknown data is that which is only available at runtime. It provides a way to load any of the textures it depends on, as well as to generate the finalized geometry. At this point, UVs are known relative to the texture, but not yet to the spritesheet.

#### IRawGeometry interface:

public interface IRawGeometry { void LoadTextures(MultiSpriteLoader loader); IGeometry Build(); }

Geometry is in a format that is ready to be passed to the vertex consumers in a geometry buffer, and which only depends on runtime data that is provided at that time. By this point, UVs are relative to the spritesheet and everything that can be baked for better performance, is.

#### IGeometry interface:

public interface IGeometry { void Add( IGeometryBuffer buffer, IReadOnlyModelData data, DirectionFlags visibleFaces ); }

### 6.6.3 Defining Models

All model definitions must be located within the models folder at the root of the mod's asset directory, and the items and blocks folders inside it will be used to retrieve their respective data. The name of the JSON file must be the same as that of the game object it represents (without the domain, of course).
