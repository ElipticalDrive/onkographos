Summary
Adds a full 3D point cloud extension to the embedding view — camera-controlled point-cloud
rendering, picking, and lasso/marquee selection — alongside the existing 2D view, and
demonstrates it end-to-end with real astronomical data pulled live from
LSDB (Gaia DR3 and Euclid Q1).
A chart renders in 3D automatically whenever it has a z field; a "Switch to 2D" / "Switch to
3D" button below the view lets users flip between a flat projection and the full 3D cloud at
any time, without losing the current selection/filter state.
Rebased onto the new embedding pipeline
Upstream's refactor of the in-browser embedding pipeline (computeEmbedding →
createEmbeddingProjector / createEmbeddingScorer, with the orchestration moved into
app/compute_projection.ts) landed while this PR was open, so the 3D path has been ported
to the new structure:
EmbeddingProjector.umap() takes an outputDim: number = 2 param, passed as the 3rd
argument to createUMAP() instead of the hardcoded 2.
computeProjection() takes an optional zColumn, derives
outputDim = zColumn != null ? 3 : 2, and conditionally ALTER TABLE / UPDATEs the z
column in the SQL write-back.
FileViewer.svelte passes zColumn through, computed from
spec.embedding.compute.dimensions === 3.
embedding/index.ts and embedding.worker.ts are upstream's versions unmodified — no
3D-specific code belongs in either file anymore.
History is also cleaned up: rebased onto current main, no merge commits, no unrelated
README changes, and the demo .parquet binaries are gitignored rather than committed.
What's included
3D view (packages/component)
EmbeddingView3D / EmbeddingView3DMosaic: a three.js-based 3D point cloud view (orbit/pan/
zoom with damping, auto-fit on first load only, reset-camera button, fly-to animation on
point focus), wired into the standard Mosaic cross-filter/selection machinery the same way
the 2D view is.
Hover tooltip + click-to-select (raycaster-based picking) that highlights the point and jumps
to its row in the data table.
Marquee/lasso drag-select in 3D screen space, resolved to a real SQL filter (via row
identifier when available, coordinate matching otherwise) and applied through Mosaic —
visible immediately in histograms and the data table. Since 3D has no persistent brush
outline to redraw as the camera moves, an active filter shows a "Filter active" badge in the
status bar instead.
Cone-of-view (camera-frustum) culling for large datasets: idle-scheduled, chunked, cancellable
downsampling (downsample_3d.ts, reservoir-sampled) so panning a large point cloud stays
responsive. Points render as anti-aliased circles (canvas-generated sprite texture) at a
density-aware size (scaled to average inter-point spacing, not just bounding radius), matching
the look of the 2D view.
Bundle size: three.js is not a static import. It's dynamically imported inside onMount,
only once a 3D view actually mounts, so 2D-only sessions never download it — confirmed via a
built-output check (main chunk 870KB → 244KB, three.js split into its own 871KB chunk fetched
on demand) and a live network-request check (2D session: zero three.js requests).
Backend (packages/backend)
--z <column> (precomputed 3D coordinate) and --umap-n-components 3 CLI flags, threaded
through compute_projection/async_compute_projection and EmbeddingAtlasOptions.
In-browser (Transformers.js/WASM) embedding pipeline also supports computing a 3D UMAP
projection, exposed via a "Compute a 3D projection" option in the settings/chart-builder UI.
Testing
New packages/component/test/downsample_3d.test.ts (vitest, 7 cases): frustum culling,
maxPoints cap, multi-chunk idle scheduling, empty-dataset and isStale-cancellation edge
cases. downsample_3d.ts itself was decoupled from three.js (a structural FrustumLike
interface instead of THREE.Frustum) so the algorithm is testable without a three.js
dependency at all.
New packages/backend/tests/test_projection.py cases for the 3D projection path.
Demo: real LSDB astronomical data
Two independent real catalogs, fetched live from LSDB's public HATS server
(server.data.lsdb.io), demonstrate the feature end-to-end:
Gaia DR3: a 9°-radius cone search (~357k raw stars), thinned via a single 3D ellipsoidal
Gaussian (not independent per-axis falloffs, which produced an unrealistic, lumpy shape) down
to ~5,340 stars, with positional jitter to blur out real small-scale catalog structure that
thinning alone can't remove.
Example screenshots:3D/2D
Euclid Q1: the EDF-North deep field (~9,733 raw objects → ~1,720 after the same
thinning), using a brightness-based Z-depth proxy (documented as such — Euclid Q1's base
catalog has no distance/redshift column, this is a visualization convenience, not a real
measurement).
Example screenshots:
Fetch/prep scripts (get_real_stars.py, prepare_stars_parquet.py, get_euclid_data.py,
prepare_euclid_xyz.py) regenerate the demo data locally on demand — the generated .parquet
files themselves are gitignored, not committed.
Status & testing
npm run check (component + viewer + embedding-atlas + examples + backend): 0 errors.
npm run test:js (includes the new packages/component vitest suite): all passing (7/7 new
cases).
packages/backend pytest suite: passing, including 2 new 3D-projection cases.
Manual/automated browser verification (headless Chromium, software WebGL): both real datasets
load with zero console/page errors; hover tooltip, click-to-select → table row, camera reset,
marquee-lasso → Mosaic filter → "Filter active" badge, and the 2D/3D toggle (preserving the
active selection across the switch) all verified working against live data.
The in-browser compute-a-3D-projection path was exercised end-to-end through the new
EmbeddingProjector, producing distinct _proj_x/y/z per row and a correctly-rendered 3D
chart. Caveat: my environment can't run real UMAP WASM or transformer inference, so those two
were stubbed for that run — the wiring and data flow are verified, but the actual
outputDim = 3 UMAP output would benefit from a check in a real environment.
Points render as soft anti-aliased circles (canvas sprite texture + alphaTest), not the WebGL
default hard-edged squares, matching the 2D view's look.
Development note
Not yet run against the full test:rust/Cargo suite (no Rust code touched by this change, so
not expected to be affected).
The 3D feature is purely additive (new components/files + a few threaded-through optional
parameters); no existing 2D code paths were removed or restructured, and 2D remains the
default when no z field/column is present.

```
spreading the data over a wider area.
```

```
Addresses the maintainer's bundle-size concern from PR review: three.js
(~870KB) was statically imported at the top of EmbeddingView3D.svelte,
so every user downloaded it even if they never opened a 3D chart.

- EmbeddingView3D.svelte: three.js/OrbitControls are now loaded via
  dynamic import() inside onMount, only when a 3D view actually mounts.
  Type annotations stay fully typed via `typeof import("three")` and
  indexed-access aliases (zero runtime cost); all existing `new THREE.X`
  call sites are unchanged since they only run after the load resolves.
- downsample_3d.ts: removed its own static three.js import too (it was
  imported statically by EmbeddingView3D.svelte, so leaving it would
  have defeated the code-splitting) by replacing THREE.Frustum/Vector3
  with minimal structural types (FrustumLike/Point3) - a real
  THREE.Frustum still satisfies FrustumLike with no cast needed, and
  this makes the algorithm trivially unit-testable with no three.js
  dependency at all.
- Confirmed via build output: dist/index.js dropped from 870KB to
  244KB, with three.module-*.js (871KB) and OrbitControls-*.js (23KB)
  now separate, lazily-fetched chunks. Verified live in a browser that
  the chunk is fetched exactly when a 3D chart mounts, and re-ran the
  full functional regression suite (hover, click-to-select, camera
  reset, marquee selection -> Mosaic filter) with no errors.
- Added vitest to packages/component for the first time (mirroring
  packages/utils's config, wired into the root test:js script) with 7
  unit tests for the downsampling algorithm: frustum culling,
  maxPoints capping, multi-chunk idle-scheduled processing, isStale
```

fix: LSDB _healpix_29 sets the DataFrame index, not a column
…
b7816ca
```
cone.compute() returns an LSDB NestedFrame with `_healpix_29` (an internal
spatial-partitioning index) as the DataFrame's *index*, not a column -
`df.drop(columns=["_healpix_29"], errors="ignore")` silently no-ops on it,
and to_parquet() then serializes the named index back as a real column.
Its int64 values exceed JavaScript's safe integer range (2^53), crashing
the viewer's Arrow/BigInt-to-Number conversion and leaving the data table
stuck on "Loading...".

Reset the index and convert to a plain pandas DataFrame (NestedFrame's
to_parquet override doesn't accept index=False) before writing, in both
fetch scripts and their derived xyz-parquet writers.
```
