The thing is, you're basing the entire design on this particular use case.
Also you're answering this particular need by a way that has huge side effects.
The basic use case for deferred is to render Point, Spot and Directional lights. The area of influence of those lights should be rendered as Geometries, yes. But they should not be part of the scene graph for the following reasons :
1- Those geometries are not managed by the user and may interfere with his scene management (for picking for example). That would be source of many confusions. We already have some cases like this in the engine, for example the skybox, or the BatchNode, that are adding "non-user" geoms in the scene graph and it has always been a source of confusion. Since we're at the design time, I'd rather not do the same mistake as in the past.
2- You already have a LightNode class that allows you to manipulate light as a node in the scene graph. The user decides if he needs it or not. You say that it adds an indirection, I'm not really sure why you think so. That's a Node, you manage it as a Node.
3- You don't need to. In 3.0, you already have an exhaustive list of lights by doing rootNode.getWorldLightList(). in 3.1 master if you do the light pass just right after the geometry pass you'll even have a intersectsFrustum flag set on each light. We could even come up with something that only gives you the lights in the frustum.
the deferred processor can easily iterate over them and render a geometry for each one in a framebuffer. You'd have 3 geometries (for all the lights).
A full screen quad for directional light, no updates needed.
A Sphere for point light. Just have to set the scale depending on the light radius, and update its position
A Cone for spot lights. you have to update the position, the direction, the range and the outer angle. That's actually the most expensive, because range and outer angle would need to update the underlying mesh (you might get away with non uniform scaling for range even). But those operations can easily be done only if needed.
So the pseudo code would be
```
viewport.setOutputFrameBuffer(ligthFB)
for each light in rootNodesLightList {
     if light.intersectFrustum{
           updateLightTransformsIfNeeded(light, appropriateLightGeom)
           renderManager.renderGeometry(appropriateLightGeom)
     }
}
viewport.setOutputFrameBuffer(whateverFrameBufferThereWasBefore)
```
This way would entirely separate the light management from the scene graph making it very unintrusive to user code and scene management. It would also allow to switch back and forth from forward to deferred just by adding or removing a SceneProcessor.
Now for your particular use case, if I understand it correctly, you need an API so that the "appropriateLightGeom" is the one you want. For example you could have a map in the processor that matches a light and a geom. Something like defferedProc.setLightVolume(light, geometry) or even defferedProc.setLightVolume(lightType, geometry) could be enough.

Switching is no work at all, it's nice side effect if things are done properly. You probably won't need it, it's not something that has to be changed at run time (wouldn't make sense). but deferred performances is very relative to the scene, the number of lights, the hardware you're running on. Having an easy way to switch without changing all your materials, is a nice feature.
The lighting material already has a gbuf technique (it doesn't work afaik) but to use it, you just have to go renderManager.setForcedTechnique("gbuf"). This means, in your scene, you just set lighting material (as usual) and the processor select the correct technique for you. and the normal forward rendering renders your gbuffer. Your processor should extend FilterPostProcessor or work in a similar way. In the post frame of your processor, you have to render the light buffer
Then you just have to add Filters to the processor : LightingFilter which you feed with the Gbuffer, and the light buffer. You can of course add any filter before or after the lightingFilter this way you completely control your rendering pipeline.
And once again to switch back to forward you just have to remove the processor from the viewport.
About lightNodes
"it's uncommon", not sure why it's an argument. Blender has tons of things that are not in JME and the other way around, we don't design things regarding if it's common or not.
"Not available in the SDK" true. Support for lights and camera manipulation is poor. But you have to admit than making them geometries to manipulate them is a bit hacky.
"It's not coherent". Never occurred to me to be honest, but even if we were to revise ourselves and make Lights and Camera Spatials, they wouldn't be geometries neither. They would just benefit from the transforms updates. Also the fact that a light lights only its subgraph is a necessary optimisation for forward rendering, and you're right that maybe it was the motivation behind this design at first. It's not really related to Deferred though.
"Do not extend spatial/nodes". You have to understand why you can read that on the wiki. People making a game with stock JME and using standard rendering don't need to extend Node or Geometry. 99% of the time it's bad design that tend to mix model and view (like I make a characterNode that extends Node an that has health stats and so on...). that's very bad practice in general and we absolutely want to avoid that.
Now, for core features it's not prohibited to extends Spatial, Node or geometry, we're still in an OOP architecture. You have to sort out what is advised to the average user for a game development and what an advanced user should do for core features like deferred.
"Both light and camera have transforms". Well that's true and not true. Transforms are translation,rotation and scale. Not all the light types need all this, but I admit it could be adapted in some way. I'm not completely against the idea to have Lights and Geometries as spatials, we just have to think thoroughly about the implications it would have.
About Picking, "that's not an issue". It's not an issue if you have a correct management of your scene graph and separate the lights from the rest of the scene. I would not assume that's what's gonna happen in real life If you let the user handle that by himself.
About the use cases, I understand the practical need you have behind that. but again, that's a hack, that is fixing issues with the exporter/SDK by changing how things are considered in the engine itself. IMO this issues should be fixed another way.
