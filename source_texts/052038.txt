Owner
Hearthlight: real sun/moon shadow map + voxel ray-traced local lights for Minecraft 26.2 + Iris.
How it works
Stage
What it does
shadow.vsh/gsh/fsh
One shadow pass, two jobs: a distorted sun/moon shadow map (terrain, translucents, entities, players, block entities, alpha-tested) and a geometry stage that voxelises terrain into a 128³ volume of half-block octants.
prepare_a/b/c.csh
Count voxelised blocks, collect emitters into an SSBO light list, bin them into 8³-block cells.
gbuffers_*
Albedo, normal, vanilla sky/block light, emissive flag. The hand writes a zero mask.
deferred.fsh
Ambient sky + sun/moon PCF shadow map + tinted vanilla fill + ranked ray-traced local lights + fog and horizon haze. Hand pixels are identified through depthtex2 and left alone.
final.fsh
Hue-preserving highlight normalisation and exposure.
This round
The hand, properly this time. Relying on the G-buffer mask only works while the hand's own program runs; if it falls back or writes nothing, the terrain's mask is still underneath and deferred re-lights the hand away. depthtex2 is the world depth Iris copies immediately before the hand is drawn, so depth < depthtex2 identifies hand pixels directly, whatever program drew them. They now return before any lighting, with HAND_BRIGHTNESS applied. The hand also no longer goes pure black in unlit rooms (the hand pass floors the vanilla lightmap at 0.10), and Debug View 7 paints hand pixels red so it is unambiguous whether the hand is drawn at all.
Local-light shadows removed, as agreed. The depth-buffer ray was the source of the phantom wedges: 16% of traceable pixels were wrongly shadowed because the depth buffer only stores the nearest surface. Sun and moon shadows are unaffected.
More settings, on five screens: sun and moon strength, sun warmth, shadow quality and softness, sun path tilt; daytime and night ambient, sunrise/sunset tint, rain darkening, horizon haze; light intensity, range, colour strength, vanilla fill, daylight suppression; shadow resolution and distance, lights per pixel, ray steps; hand brightness, fog distance, exposure. Debug View now reaches 7.
Verification
Minecraft cannot be run here. Three offline harnesses run against the shipped zip:
tools/validate.py — expands every #include, injects Iris' own defines, compiles and links all 24 stages with glslang.
tools/iris_compat.py — preprocesses each program exactly as Iris does; no identifier collides with an Iris define.
tools/simulate.py — volume/SSBO layout, id tables, packed light byte, octant bit layout, shadow distortion, the sun/moon direction convention, the octant DDA, and checks that the hand is identified through depthtex2 and that the removed ray stays removed.
Known limitations
Entities cast sun/moon shadows but do not block local (torch) light.
Local-light occlusion is half-block resolution.
In first person your own body is not rendered, so it casts no sun shadow; use third person.
The hand item is vanilla-lit (plus Hand Brightness).
Download: tools/Hearthlight.zip.

Minecraft cannot run in this sandbox (no game jar is reachable and there is no
OpenGL driver), so tools/simulate.py ports the pure-maths parts of the shaders
to Python and exercises them on synthetic scenes.

It found a real bug: the flood fill averaged its six neighbours (a Jacobi
diffusion), which needs O(r^2) frames to converge and decays as exp(-r/4), so a
torch only tinted the three or four blocks around it. Switched to a
component-wise max with a 0.8 per-block falloff:

  reach          3 blocks -> 15 blocks
  fill time      179 frames at 8 blocks -> 8 frames
  sealed room    black -> lit, no leak through walls

Also fades the tint in from 0.02 to 0.10 luma so the end of the light volume is
not a visible ring, and adds a stage-link pass to validate.py (39 stages, 18
links).

Cause. Iris #defines MC_RENDER_STAGE_<PHASE> (one per WorldRenderingPhase,

```

```
so Iris' preprocessor rewrote that line into const int 0 = 0; before its parser
ran — hence the error on basic, the first program it compiled.
Fix (035c806): the declarations are gone; the pack now uses Iris' macros.
The ordinal list lives in Iris (WorldRenderingPhase), not in the pack.
Why the existing tests missed it. tools/validate.py expanded includes and
compiled with glslang, but never applied Iris' defines, so MC_RENDER_STAGE_NONE
looked like an ordinary identifier. A plain compile cannot see a macro collision
that only exists after someone else's #defines.

Make the coloured light volume actually fill, and stop it leaking
…
8883064
```
The light volume was coming out empty, so every surface got a white tint and the
only warm colour on screen was vanilla's own lightmap. Three holes:

1. Voxelization only ran when renderStage was one of the four terrain phases.
   If that uniform was stale the volume stayed empty and *nothing* reported an
   error. Inverted the test: every phase writes except entities, the hand and
   the outline, which are the only ones that are definitely not world geometry.

2. The flood fill classified 'opaque' as 1..31 plus emitters, so any other value
   was treated as air. An unmapped block id under Sodium reaches the buffer as
   255, which meant light walked straight through those blocks. Now anything
   that is not plainly air (0) or explicitly transparent (80..95) is solid.

3. The held light had no occlusion at all and lit the far side of walls. It now
   marches eight samples through the voxel volume towards the camera and is
   cut when geometry is in the way.

Also added, so this cannot silently regress or be misdiagnosed again:

- nearby_emitter_colour(): a 3x3x3 search of the raw voxel buffer used when the
  propagated volume has nothing at a surface. A torch tints the blocks it is
  touching from the first frame, before the flood fill reaches them.
- DEBUG_VIEW 5: paints the raw voxel volume (red solid, green emitter, blue
  transparent, black air). Black ground = the shadow pass is not writing;
  red ground = the volume is fine and the problem is propagation.

Real-shaped sun shadows, and light from translucent blocks
…
83409d8
```
The 1-block voxel grid cannot express a door panel, a fence rail, a trapdoor,
a player or a dropped item, so the sun gets a second shadow from the depth
buffer: one ray per pixel marched through depthtex1 (no translucents, so glass
and water still pass sunlight). It takes over from the voxel ray once it has
walked far enough to be trusted and falls back to it near the screen edge or
when the sun is behind the camera. That removes the blocky squares at doors
and gives players and items a shadow at all.

Lava and nether portals are drawn in the translucent pass, which the shadow
pass never sees, so they never emitted. gbuffers_water now writes emitters
into the light volume (emission only, never occupancy, so water cannot start
blocking light).

Emitter audit: copper torch and the eight copper lanterns (green, 1.21.9),

I had claimed shadowLightPosition was in shadow view space. It is not: Iris'
CelestialUniforms.getShadowLightPosition() delegates to getSunPosition() /
getMoonPosition(), and those multiply by CapturedRenderingState's *gbuffer*
model view. Rotating it with shadowModelViewInverse therefore threw the sun and
moon to an arbitrary direction, which is what painted the huge wrongly-oriented
shadow regions across the ground. Back to gbufferModelViewInverse.

The simulator test that "confirmed" that change was written to match my own
mistake, so it has been rewritten to assert the verified convention and to
show how far the wrong matrix lands (15-38 degrees).

The fine local-light ray is now off by default. A cross-check against analytic
ray casting over 60 randomised scenes shows 284 of 1794 traceable pixels
wrongly shadowed: the depth buffer stores only the nearest surface, so geometry
between the camera and the lit floor (a fence, the lamp itself) casts a phantom
shadow over it. That is inherent to screen-space shadowing, so the feature is
opt-in and documented with the measurement rather than shipped on.
