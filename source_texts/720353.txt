This adds write support to USD for ParticleField3DGaussianSplat objects.
It also changes the reading of ParticleField3DGaussianSplat slightly. Previously, we were only loading radiance:sphericalHarmonicsCoefficients that the radiance:sphericalHarmonicsDegree indicated were used. That meant you would not load data if the degree indicated fewer coefficients were used than what were present( # coefficients = ( degree + 1 ) * ( degree + 1 ) ).
Now we're treating the degree and the coefficients as more-or-less independent quantities. They are related though, so I'm warning if they don't agree and continue loading.
Writing has some similar edge cases that might be worth more discussion. Since we're collecting the ParticleField3DGaussianSplat:# primvars into a single vector, some decisions need to be made if the data isn't formatted correctly. My goal is to keep as much data as possible to let the user make fixes if needed. I believe the only data that will be lost from this code is if a coefficients primvar has a valid index (like ParticleField3DGaussianSplat:15) but non-V3fVectorData type or non-Vertex interpolation. The fallback in that case is ideally to write the data out as a separate variable, but to USD the :# suffix gets interpreted as a namespace with a number as the name and it is warned as being invalid.
Perhaps we should not emit our own warning and let USD complain? The ParticleField3DGaussianSplat:# format is something of our making, so my thought is we should be the ones making the warning.
