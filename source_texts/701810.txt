Summary
The ground the tracer stands on: the workspace's first compute pipelines, a
ray-tracing acceleration structure, and a traversal kernel, opened by two measured
de-risking spikes that hold the authority to stop or reshape the release before the
large stages are committed to.
Problem and value
Nothing in the workspace dispatches compute, and there is no acceleration structure of
any kind: picking is a linear scan over meshes. A path tracer is not an extension of
the existing renderer but a second renderer, and the responsible way to start one is
to measure the four things that could sink it (traversal speed, build time, payload
size, device stability) on real hardware before writing the parts that assume the
answers. The spikes produce numbers; a miss is a named scope change, not a silent
proceed, and the recorded fallback is a tiled high-resolution raster still on the same
job infrastructure.
Scope
In: the two spikes and their recorded gate numbers; a new GPU-free crate with a
binned-SAH two-way BVH builder and a two-level structure (one cached bottom-level tree
per object, a top-level tree over instances); the compute pipeline scaffolding in the
renderer; and the traversal kernel with closest-hit and any-hit entry points.
Out: adopting an external BVH crate, rejected because the workspace standardizes
on one math library and the builder needed here is the well-understood part of the
release; and hardware ray tracing, which does not exist in the browser standard.
Acceptance criteria
Gate numbers recorded before the later stages open: a trivial compute kernel
runs and reads back on both shells with no feature or limit change; measured
traversal speed projects a 1920x1080 still at 256 samples inside ten minutes; a
one-million-triangle build completes in the import worker in under five seconds
without blocking the render loop; the spike's compressed payload delta is under
150 KB; thirty consecutive four-megapixel dispatches lose no device on either
shell.
The BVH builder is deterministic, asserts a depth bound of 32, and reaches every
triangle, with tests for each.
An exhaustive ray-set comparison against the existing CPU raycaster passes for
the same geometry, the highest-value test in the release, because a wrong BVH
produces a plausible image.
Device creation on both shells still requests Features::empty() and
Limits::default(); needing more is a stop condition, not a negotiation.
The traversal stack is fixed at 64 entries and the builder guarantees the depth
that makes that safe.
Design considerations
Core WebGPU is the ceiling for both shells. One kernel, no extensions, no raised
limits, so the browser and the desktop stay the same code. The storage-buffer budget
is exactly met by design (seven arrays bound, one reserved), and any ninth logical
array is a design error to resolve by merging, never by raising limits.
The builder is GPU-free and lives in its own crate, because it must run in the
import worker, which has no GPU; putting it in the renderer would drag GPU types
into the worker, and putting it in the geometry kernel would mix a rendering
acceleration structure into geometry code.
Two-level structure over per-object trees, cached on the same shared-pointer
identity the renderer already uses to dedupe geometry, so a moved object rebuilds
only the top level and instanced geometry from v0.8.2 maps on directly.
Technical plan
The new crate depends on the core crate and a pod-casting utility only: no
filesystem, no threads, wasm-clean by construction. Node layout is 32 bytes with the
left child implicit at the next index. The compute pipelines join the renderer's
existing bind-group layout registry. Both spikes are throwaway code; their deliverable
is the recorded numbers.
Dependencies
Gates every other epic in the release. Depends on v0.8.2 having shipped, in
particular instancing and the complete scene delta.
