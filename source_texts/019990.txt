Closes #405. Implements openspec/changes/add-mesh-multires whole.
What was missing
On a mesh layer, fine detail and coarse form are the same edit. The detail IS
the vertex positions and nothing records which part of a position was form and
which part was wrinkle, so a pass that changes proportions destroys the pass
before it. MeshSculptor cannot fix that — its contract is that topology never
changes, and that contract is why a mesh layer is worth holding after a
retopology pass. DynamicSurface answers a different question and
voxel_remesh a third.
The model
```
P(0) = the base cage                 the production geometry, sculpted directly
S(n) = Subdivide(P(n-1))             pure Catmull-Clark, no detail
P(n) = S(n) + Frame(n) * Detail(n)   the level as the artist sees it
```
Levels are not a stack of unrelated meshes: with no relationship between a level
and its parent, a change to the parent has no defined effect on the child, so
either the fine detail or the coarse edit has to be discarded. The relationship
IS the feature.
The four decisions the change asked for
Catmull-Clark. mesh::Mesh already carries quads, an imported
retopologised character is quads, and the rule turns a triangle cage into
quads at level 1 — so every level above 0 is pure quads and everything that
reads a level has one face arity to handle. SubdivisionRule takes another
rule and the encoding records which one built a hierarchy.
Detail is blocked sparse, fp32, 256 vertices a block, with dense
promotion above 75% coverage — and the promotion is a SPEED decision rather
than a memory one, because the block table costs four bytes per 256 vertices
and the sparse form is smaller until coverage passes 99.9%.
A level is whole, not region-scoped. The voxel construction does not
transfer: outside a refined region a voxel level reads its parent, which works
because the lattice is regular. On an irregular surface the transition has to
be owned by particular faces. Deferred with the reason recorded rather than
approximated.
Per-level face lists are cached, everything else is derived. 16 bytes a
face, so 4^L * 16 * F0 — 82 MB at level 4 over a 20k cage, which is exactly
why preflight_add_level exists.
What shipped
mesh::MultiresSurface — level lifecycle, build-then-publish add_level
with cancellation, preflight_add_level that prices a level by arithmetic and
refuses over budget rather than allocating half of it, independent sculpt and
display levels, local propagation with a normal halo, droppable per-level
caches, and export of any level as an ordinary mesh::Mesh.
mesh::MultiresSculptor — not a second brush engine. The active level's
positions live in a mesh::Mesh inside that level's cache with an Adjacency
over it, so a stamp is MeshSculptor::stamp on that level. Every verb, the
geodesic reach, the mask gate, automasking, alpha stamping and the local
normal recompute come along unchanged. At the cage the two paths are
bit-identical; above it they agree to a frame round trip, and the test asserts
each on its own terms.
Detail in a transported frame — built once at the cage and rotated by
shortest arc up the hierarchy, never rebuilt. The measured difference is
below.
mesh::MultiresDelta + session::History::Step::Kind::Multires, appended so
older journals still replay, reached through a host-supplied resolver as the
adaptive kind is.
project_surface (normal ray first, closest point as the fallback) and
MultiresSurface::project_from. transfer_attributes keeps its contract: it
still moves no position, asserted byte-for-byte.
A versioned encoding that writes the cage, the rule, the level count, the
active levels and each level's detail — and nothing that follows from those.
C ABI (clay_multires, clay_multires_sculptor), pyclay, Swift smoke,
examples/68_mesh_multires.py, benchmarks and docs.

A bug this found
The multires suite under ASan caught a latent heap-buffer-overflow in
Adjacency::build: it indexed class_of_ with a raw corner and never checked
it, so a Mesh filled by hand with an out-of-range index was a read past the
end. Not reachable from a host — clay_mesh_from_triangles and pyclay's
from_triangles both refuse one — but reachable from C++, because mesh::Mesh
is a plain struct and the function's contract never said otherwise. Fixed, with
a regression test that aborts under ASan when the guard is reverted.
Two spec deltas amended, with the reason
A MultiresSurface is a standalone handle, exactly as a DynamicSurface
is: no scene::Layer owns one. Two deltas were written assuming otherwise, and
both are amended rather than worked around:
scene-model — the memory accounting is per surface
(MultiresSurface::memory()), because io::document_memory cannot see a
handle no layer holds, and inventing a layer home for this representation
ahead of the one that shipped before it would be the wider change made for
the narrower reason.
file-io — the .clayspace format gains no chunk at all, so a document
written after this change is byte-identical to one written before it. That is
stronger than the backward-open guarantee the delta originally asked for.
Deliberately not here
Sculpt layers (the next change — DetailField is the storage they share),
vector displacement, multires erase and smear, baking detail to maps, GPU
evaluation, unsubdivide / apply-base / rebuild-subdivisions, crease weights
beyond the mesh boundary, and region-scoped levels. brush::apply_to_multires
is also absent, and that is precedent rather than omission: apply_to_mesh has
no adaptive counterpart either, and a stroke-engine hook for a third
representation should make the same decision for both at once.

Each of these was found in a review of my own work on this branch, and each is
either a claim the code could not back or a defect the tests could not see.

1. detail_field.h cited two benchmarks that DID NOT EXIST, so its block size
   and promotion threshold were asserted round numbers while task 1.2 asked for
   a measurement. Both benchmarks are now real, the block size is a PARAMETER
   so it can be swept at all, and both constants follow what the sweep says
   rather than what the comment did:
     - block size 256 -> 1024. Total cost to hold one footprint, KiB:
         reached      64      256     1024     4096
             400   72.25       25       16       49
           4,000  139.75       94       88       97
          40,000  814.75      769      760      769
       1024 is least at every footprint; below it the block table over the
       level dominates, above it the last partly-used block does.
     - dense promotion 0.75 -> 1.0. BM_MultiresDetailAccess measures 611 M/s
       sparse against 605 M/s dense, so promotion buys no measurable speed —
       while promoting at three-quarters coverage allocates a third MORE than
       the sparse form it replaces. A threshold with nothing on the benefit
       side belongs where it cannot cost anything either.
   The checksum is now hashed per non-zero vertex rather than per block, so it
   stays representation-independent across block sizes, and the encoding
   records the block size so a round trip is still byte-exact.

2. The preflight's estimate was never compared to reality, and was 34-50% LOW
   — the dangerous direction for a budget whose job is to refuse before an OOM
   kill. It now applies a measured capacity factor, prices the detail field's
   block table, and test_multires.cpp holds it as a CEILING over the actuals.

3. Dead code: child_edges computed and discarded in preflight_add_level.

4. MultiresMemory::runtime_index was a subtraction from LevelCache::bytes().
   Correct today, and one edit away from underflowing size_t into a memory
   report of sixteen exabytes. It is two positive sums now.

5. drop_intermediate_caches() releases the levels BETWEEN the cage and the ones
   in use — the lever a host wants while an artist details at a fine level.
   That needed evaluate_up_to to stop walking from the cage when nothing below
   has moved, without which a released level came straight back on the next
   stamp and the trim bought nothing.

6. The attribute-export fallback was unreachable dead code pretending to be a
   fallback; it is a stated precondition now. Added the untested combination it
   was hiding: a cage split for HARD EDGES — duplicate positions with no uv or
   colour on them — which welds geometrically and still splits on export.

7. brush::apply_to_multires: the stroke engine reached one of three mesh
   representations. It shares mesh_stamp_settings, mesh_mask_gate and
   mesh_automask_inputs with apply_to_mesh rather than copying them, so what a
   stroke IS cannot drift between representations. Reachable from C
   (clay_multires_sculptor_apply_stroke) and pyclay (apply_stroke).

   Extracting that shared helper immediately found a bug I had just written:
   apply_to_mesh evaluated class_position(kNoClass) eagerly for every
   non-dragging verb — a read past the end whose result was discarded, caught
   by ASan through the new test.

8. Cognitive complexity was never actually measured: clang-tidy was absent and
   the skill fell back to lizard's CYCLOMATIC metric. Measured properly now,
   which found one critical function (ensure_attributes at 31) and two
   warnings. After splitting those three: 66 functions, average 3.7, worst 18,
   nothing above the acceptable band.

Also fixed a nanobind reference leak the new binding introduced: a default
argument constructing a StrokePreset leaks one instance and sixty-one types at
interpreter shutdown. The existing mesh binding requires its preset for the
same reason.

Two findings from reviewing CyberdyneCorp#406, neither caused by it.

THE RENDER BUG (CyberdyneCorp#407) is not what I filed it as. It is not every mesh preview
and it is not Volume.from_mesh: example 45, whose mesh comes from doc.mesh(),
renders correctly and always has. What is wrong is the hand-built cube-sphere
that 66_dynamic_topology builds for itself — its triangles wind INWARD.

  signed_volume  -4.1383   winding number at the centre  -1.022

A closed mesh wound inward has a winding number of -1 in its interior rather
than +1, so Bvh::is_inside is false everywhere, so the sampled field is POSITIVE
at the centre of the model. There is then no zero crossing for a ray to find:
0 of 625 rays hit a mesh sampled this way against 625 of 625 for one wound
