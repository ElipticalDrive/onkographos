Fixes #1093
The eval3d rasterizer does not currently return gradients for viewmats or viewmats_rs. With with_ut=True and with_eval3d=True, this leaves camera pose optimization without a geometric image gradient. View-dependent SH colors still provide a gradient through the camera position, but cannot correct a rotation about the camera center.
This PR backpropagates the existing per-pixel ray gradients through camera ray generation. It enables pose refinement with 3DGUT, including gradients for both rolling-shutter endpoint poses. The API is unchanged. The additional buffers and pose backward pass are used only when a pose tensor requires gradients and explicit rays are absent.
Method
For a world-to-camera pose [R | t], ray generation computes
```
o = Rᵀ (o_cam - t)
d = Rᵀ c
```
The eval3d backward already computes derivatives with respect to the world-space origin o and direction d. A new CUDA kernel chains these derivatives into the camera poses and reduces the contributions per image. It shares the forward pass's camera-model dispatch, including the image-plane origins used by orthographic cameras.
For rolling shutter, the kernel differentiates the interpolated pose with respect to both endpoints. It uses the forward pass's shutter timing and normalized quaternion interpolation, with SO(3) Jacobians for the endpoint rotations. Small-angle coefficients use Taylor expansions to avoid cancellation in float32.
Pose gradients are intended for parameterizations that produce valid rotations, such as R @ so3_exp(xi). Global shutter returns the usual matrix-entry gradient used by the EWA projection backward; rolling shutter returns a matrix gradient with the correct derivatives along rotation tangent directions. Derivatives for arbitrary changes to the rotation matrix entries are not specified.

Reproduction
```
python examples/simple_trainer.py mcmc \
    --data_dir data/360_v2/garden --data_factor 4 \
    --max_steps 7000 --eval_steps 7000 --save_steps 7000 \
    --disable_viewer --disable_video \
    --pose_noise 0.01 --pose_opt --pose_opt_lr 1e-4 \
    --with_ut --with_eval3d
```
Remove --with_ut --with_eval3d for EWA. Remove --pose_opt for fixed noisy poses, and also remove --pose_noise 0.01 for reference poses. Use separate result directories. The saved runs used a wrapper around the trainer to read out the final pose residuals; it did not change the training loop or MCMC preset.
All runs and tests used PyTorch 2.9.1 (the upstream GPU CI version) and CUDA 12.8, with this branch as submitted and no local patches. Upstream rows use unmodified 512d366b, built the same way.
Validation
All 22 new tests in tests/test_eval3d_viewmat_grads.py pass cleanly (~6s on RTX 4070 Ti SUPER, PyTorch 2.9.1), covering:
Reference Gradients: Verified against PyTorch autograd through the eval3d reference for global shutter and all four rolling-shutter directions (including coincident endpoints and 0.3 rad relative rotations).
Finite Differences: Central finite differences through rasterization() across pinhole, OpenCV distorted pinhole, fisheye, F-Theta, and orthographic cameras.
Edge Cases: Identical rolling-shutter endpoints, batched/invisible scenes, and verification that Gaussian-position gradients remain completely unchanged when pose gradients are active.
Gradient Routing: Validates MixedBatch and ParallelBatch renderers, and ensures ray gradients are correctly routed when explicit rays are provided.
The gradient comparisons use valid rotation perturbations. Finite differences use a sparse synthetic scene because visibility and alpha cutoffs make dense-scene numerical derivatives unstable.
Also checked locally, outside the test file: image-based pose recovery in a fixed synthetic scene (two cameras offset by 2-4° and 5-9 cm, 400 Adam steps). With 3DGUT the loss drops from 2.0e-2 to 3.8e-6 and the rotation errors to 0.0048 and 0.00044 rad, on par with EWA on the same setup (0.0049 and 0.00045 rad).
Full upstream suite (pytest tests/, full pytest.ini build configuration, PyTorch 2.9.1), excluding the native C++ tests: 2,631 passed, 22 failed, 132 skipped. The 22 failures are 21 numerical-tolerance cases (three 2DGS v_colors, twelve F-Theta and six orthographic UT projection) and the missing optional compression dependency. All 22 fail the same way on unmodified 512d366b, built and run the same way.
A local RTX 4070 Ti SUPER benchmarked with 111,785 Gaussians at 1920×1280 (medians over 20 backward passes): enabling pose gradients adds at most 5.0% additional backward time with zero measurable peak memory overhead across 1, 3, and 6 cameras (global and rolling shutter). When requires_grad=False, overhead is zero. Python and C++/CUDA formatting checks pass.
Scope
Included: Propagates camera-ray gradients to viewmats and viewmats_rs (supporting explicit ray-generation graphs or direct rasterizer pose inputs).
Excluded: Does not add gradients for camera intrinsics, distortion parameters, LiDAR, or external distortions. When using UT with depth (D/ED), the direct pose derivative of projected Gaussian depth is omitted (tracked separately in [fix] 3DGUT: hit-distance and normal gradients at clamped alpha #1083).
