When submitting a new Job Run, submission may be disallowed due to another run of this job being queued or busy already. This may lead to wrong behavior, as a trigger due to new data would not trigger a new job run - thus, incomplete data is computed and no other run is started.
The SCHEDULING state should be extended or another state should be added to handle cases such as this. To implement this, a proper queuing system for jobs may be appropriate, with the queues being available for viewing, reordering and deleting single runs also in the Status Interface.

We don't necessarily want to run the jobs in parallel as this may starve an executor (if I get 10 Datasets that are all relevant and for all, a new processing is started, this may take hours to finish), especially as most jobs are not written with parallel execution in mind (overwriting some manifest.json or overview.json that defines the outputs may lead to race conditions between the different runs, and potentially invalid states)
If 10 new dataset runs come in, we maybe want only the latest to actually run, so we let the current run finish and only run the latest request after the first finished, to avoid running the same job 10 times
Runner Groups may be used by multiple jobs, and we don't want all of them to execute the same job
