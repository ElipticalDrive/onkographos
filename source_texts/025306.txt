What
A browser-based viewer for MorphoDepot Organizational repos: volume rendering of the specimen
scan, tinted by its segmentation, reachable from the RepoClerk dashboard. No Slicer install and
no GitHub account needed to look at a specimen.
Tracking issue — MorphoDepot is still moving under this, so treat the design below as where we
got to on 2026-09-18, not as a spec.
Why open it now
Feasibility is established rather than assumed. Steve Pieper's WebGPU "colorize volume" work
(SlicerLive, Apache-2.0) renders exactly this shape of
data, and MorphoDepot repos drop into it. Two specimens were taken end to end and checked
against their sources:

Worth noting up front: of the 11 Organizational specimen repos, only mus-musculus-E15 has a
rich multi-structure segmentation (50). Seven have a single Cranium. So this will look its
best on one repo today and improve as segmentation work lands.
Design as of 2026-09-18
Ours, self-hosted. No dependency on a third-party page.
No baked or derived data as the end state. Rendering wants roughly 60M voxels; the
Organizational specimens run from 195M to 3.8G. That reduction should come from the data at
rest, not from a second copy we maintain:
volume — once source volumes are multiscale (zarr), fetch the resolution level that fits.
No derived artifact, no staleness.
segmentation — read baseline.seg.nrrd straight from the repo. It is 1–19 MB compressed,
and decompresses as a stream in slice order, so a reader can subsample while reading and never
hold the full array in memory.
Net: nothing to bake, nothing to keep in sync, always showing current repo state.
Interim. Until volumes are multiscale, direct reads work for the smaller specimens. The
large ones need the migration first — neotoma-cinerea-skull is 230 MB / 3.8 Gvoxel and
bos-taurus-diceCT-eyeball-2026 is 1.2 GB.
Which repos appear — gate on a DOI. prepareReleaseSnapshot
(MorphoDepotLib/logic_release.py) writes baseline.seg.nrrd from the picked segmentation and
mints the DOI in the same operation, so a DOI means there is real segmentation content. This is
causal, not a correlation. It holds across all 11 Organizational specimen repos: 10 have
.zenodo/state.json with a concept DOI and a 1.1–19 MB baseline; the one without
(bos-taurus-diceCT-eyeball-2026) has a 2 KB placeholder baseline with zero segments.
collection-* repos are skipped.
Journal schema — add doi. Journals carry volumeSize and sourceVolumeChecksum but no
DOI. Both this viewer and the extension-side README link need it, so it belongs in the journal
rather than being re-fetched per repo.
Blobs must not be committed here. Clients keep a local clone of RepoClerk
(MorphoDepotLib/logic_repoclerk.py, git clone --depth 1), so anything committed to this repo
is downloaded by every Slicer user. The viewer page itself is small and fine; bulk data is not.
Known issues to resolve
Overlapping segments are 4D. scapanus-townsendii-head has
sizes: 2 796 1673 741, kinds: list domain domain domain, with each layer restarting at
label value 1. They must be merged into distinct label values. Trap: the layer axis is NRRD's
fastest, so after the usual reshape(reversed(sizes)) it is the last numpy axis, not
the first — getting this wrong silently yields 741 "layers" instead of 2.
Between-release state. A repo can hold issue-*.seg.nrrd files from merged contributions
alongside baseline.seg.nrrd; release drops them from the working tree (they stay in
history). No Organizational repo has any right now, so this is latent. The repo color table
gives contributors shared label values, which makes merging tractable; the open question is
what to do when two contributors touch the same label.
Display window. These are 8-bit microCT, not Hounsfield units, so the window has to come
from the data rather than from a CT preset.
Scope
Organizational repos only.
