I use fidget for SDF voxelization for a little game engine I've been working on and its by far the most useful thing in existence for this purpose. I currently have a custom CPU renderer that produces an octree by recursively simplifying tapes. Next I need to try and move generation entirely to the GPU, making use of the async compute queues to free up CPU threads.
It would be useful for users of this crate (and me so I don't have to port shader side bug fixes to my version) if a public interval evaluation and point sampling API was available.
Initial Motivation (skip if you dont care)
My initial plan for opening this issue was to suggest a volumetric rendering API be added alongside heightmap rendering and be supported on the CPU and GPU, but when designing this to be usable for my purposes I ran into some problems. It would be simple enough to output a list of tiles covering regions, where some are marked as filled or empty and others contain an offset into a buffer of distances (and optionally gradients as well). However, what if a user wanted to evaluate a grid of samples at the bottom tile rather than sample the center of the bottom voxel? Furthermore, what if they want a grid of points that isn't centered inside each grid cell, but spans from the edges and corners of the voxels inward? Simple, just add a new mode for rendering from the corners. But now you're evaluating the same point multiple times across neighboring tiles, and there's room to optimize by only evaluating shared points once. I've run into and solved each of these problems for my custom renderer, but porting all of this functionality to a public API (and mirroring on the GPU) would definitely go against your goal of keeping the maintenance burden low.
My Constraints
My engine uses Vulkan for everything so I will need to rewrite the wgpu code in Vulkan myself, but it would be nice if the wgsl shaders were public so I could compile them to SPIRV with naga, as well as the portion of Rust code that handles shader assembly.
I need the results of interval evaluation to stay on the GPU so my own shaders can use them directly. If the shaders are public, I could solve this by implementing a custom pass that makes use of the interval simplification directly.
The CPU and GPU evaluation results should be (mostly) consistent enough that I can use CPU generation as a fallback.
The Design
Instead of supporting a custom rendering pipeline, all fidget needs to do is provide the general framework to let users manipulate interval, point, and gradient evaluation manually. There's two ways I can think of to solve this:
The complicated option is to have fidget own the passes that perform interval and bulk point evaluation. This would be a more mature API for general purpose users.
The simple option is to pubify and document the shader code, letting the user write the pass themselves. If you want to take this approach for now, I could try and design the general purpose version to work with my engine, consolidating it into fidget later on if I've proven it's flexibility.
Any thoughts on this plan? Am I completely insane? Does any of this align with the goals you have for fidget going forward? If you don't have the time to work on this, I'd love to give the problem some crack. There's also a couple GPU optimizations for this crate I want to try out later on, so it would be good to get familiar with the internals before that PR comes.
