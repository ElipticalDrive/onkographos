## Summary

The spec 021 octree prototype (branch `021-octree-size-field`, PR #113, `admesh/_stages/octree_grid.py`) is correct but its data structures do not scale. Leaf **count** grows ~linearly with feature-size ratio (good), but **build** and **query** cost do not.

## Concrete complexity

- `_build_adjacency()` compares **all leaf pairs** (double loop) → **O(N²)**.
- `_balance_2to1()` **rebuilds** that O(N²) adjacency inside its split loop → up to **O(N³)** worst case.
- `locate()` and `interpolate()` **linear-scan every leaf** per query point → **O(N)** each, **O(N·Q)** across a distmesh run that calls the size field many times.

## Measured (river-into-bay, `scripts/render_scalability.py`)

| feature-size ratio | leaves | build time |
|---|---|---|
| 10 | 1342 | 1.0 s |
| 20 | 2920 | 3.7 s |
| 40 | 5950 | 13.2 s |

Leaf count ~linear; build time ~quadratic in leaves. Spec targets ratios 10³–10⁴ → near the `h_min` floor that is millions of leaves → current build/query is intractable (a finer-inlet run already timed out). See `output/octree_scalability.png`.

## Proposed fix

1. Pointer/hash quadtree with **O(log N) point location** (tree descent) — replaces `locate`/`interpolate` linear scans.
2. **O(N) neighbour finding** via parent/sibling links during subdivision — replaces all-pairs `_build_adjacency`.
3. **Work-queue balancing** (queue of split candidates) — replaces full adjacency rebuild per split.
4. Numba / vectorize the per-leaf Python loops (gradient fit in `octree_medial.medial_leaves`, rasterization).

## Acceptance

Build + size-field query for feature-size ratio ≥ 1000 completes in seconds with leaf count ≥ 10× below the uniform-at-finest baseline (SC-004).

Refs: PR #113, `output/octree_scalability.png`, spec 021 report.
