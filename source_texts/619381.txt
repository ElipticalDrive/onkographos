The ray trace is 2.43 ms of a 319 ms query -- 0.76 percent. Upload, launch
and download together are 8.7 ms, so under three percent of a query is device
work. The partition is complete: stage_sum_ms equals wall_ms to three
decimals in every run, and the protocol rejects a reply whose stages sum past
the wall time they were taken inside.
What a resident worker would actually buy
The cacheable stages come to 192.1 ms and teardown's 7.8 ms goes with them,
leaving about 119 ms per query -- of which 88.7 ms is the host reference
intersection, not the device. Ray generation is another 22.1 ms and is
constant for a fixed query set, so it caches under a reuse key naming scene,
query set and ray count. Validation does not: it is the check that the device
answer is right and runs per query by construction.
So a worker that cached everything cacheable would spend three quarters of
each query in host arithmetic verifying an 8.7 ms device round trip. That
ordering is the finding, and it is what the resident worker has to answer
before any streams or events are worth adding.
Two ways this measurement could have lied, and did not
The first pair blamed the cache for first touch. Run cold-then-warm on an
idle card, cuda_context_ms read 401.351 against 130.628 and
optix_context_ms 206.565 against 52.511 -- 548 ms of apparent cache saving.
Four alternating runs hold both stages flat whatever the cache state while
module_ms tracks it exactly (1.082, 32.576, 0.355, 32.840). It was driver
initialization. order-series.tsv retains the series.
The retained reply carried the account name. optix_host.h gives the Linux
default cache location as /var/tmp/OptixCache_<username> -- a different
directory for every caller, so a warm timing against it depends on who ran it,
and eirikr travelled into a tracked artifact past both the harness scrub and
the publication gate. The service now sets OPTIX_CACHE_PATH (which the header
says takes precedence over the API) to one declared location, the harness
scrubs the reply on the way in like every other capture, and the latch capture
takes the same scrub. A first run against a fresh location is a populate, not a
hit, and reported module_ms at 22.859; the retained warm arm is the run after.
The cache is a ledger property
optix_host.h: there is no in-memory cache, so optixModuleCreate either
compiles the PTX or reads a compiled module back. A module timing that does not
pin this measures run history. geometry-profiles.tsv gains module_cache
with a second row at disabled; the service sets OPTIX_CACHE_MAXSIZE=0 for
it; the runtime reads the state back off the context, because the header says
the environment takes precedence over the API and can close a cache the row
asked for. PROTOCOL_VERSION 2 requires the readback to agree with the request.

Allow for millisecond rounding in stage-sum validation
The runtime serializes wall_ms and each of the twelve stage timings independently to three decimal places, but this comparison permits only 0.000001 ms of excess. A valid run can therefore be rejected whenever several stages round upward while the wall value rounds downward—even though the unrounded stages remain inside the wall interval. Allow for the aggregate serialization error (up to roughly 0.0065 ms), or validate unrounded values before formatting.

Reviewed the runtime stage boundaries, retained warm/cold results, profile/schema changes and successful clone-local run. This is useful measurement instrumentation; no resident worker or reduced verification is being enabled. The identical latch-scrub change from #94 must remain together with #94's shared compute-client parser.
Design decision: keep the full per-ray reference comparison and the one-shot implementation as the default/control. Do not hold the compute lease while waiting for future requests. Any future resident worker requires explicit memory-residency admission, per-job compute ownership and synchronized retirement; merely allowing an extra process name is insufficient.
The approximately 119.5 ms worker result is a projection, not a measured runtime. The 88.719 ms validate stage combines reference construction, comparison and reductions. For identical scene/ray bytes, independently computed reference results can be cached while still comparing every fresh GPU result; this is not sampling and must never cache a previous GPU answer as its own reference. Dynamic scene changes invalidate such reference reuse.
Two measurement qualifications for follow-up: (1) the warm stage sum is 319.475 ms versus wall_ms 319.477 ms, so not exact equality at three decimals; independently rounded millisecond values need a rounding-aware sum tolerance, not the current 1e-6 ms limit; (2) runtime wall_ms excludes the later digest/JSON work and differs from the retained roughly 415 ms client time. Preserve both. No device measurement was performed during this review.
