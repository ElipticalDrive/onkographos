Suggested by Viktor on discord.
"I am sorry for what you're about to see but when it comes to voxel rendering then I can't control myself.
You could significantly improve performance because currently it's pretty bad in theory atleast I haven't ran it.
By that I mean there's not really many optimizations in voxel rendering/rendering by itself at all.
Also I would recommend you in idea understand how the rendering part works.
Before I even get to voxel rendering itself.
You are doing frustum culling on the CPU.
if frustum.intersects_box(offset, offset + Vec3::splat(16.0)) {
visible.push((mesh, offset));
}
}
let uniform = FrameUniform {
view_projection: camera.view_projection().to_cols_array_2d(),
};
gpu.queue.write_buffer(&self.frame, 0, bytemuck::bytes_of(&uniform));
Just in general I would encourage(you or claude whatever) to use a more GPU driven pipeline.
So an example would look like this:
```
if (should_draw) {
    uint i = base_v + p_v;
    deref(push.culled_chunks_voxels[i]).data_ptr_offset = draw_offset;
    deref(push.culled_chunks_voxels[i]).scale = scale;
    deref(push.culled_chunks_voxels[i]).x = request.x;
    deref(push.culled_chunks_voxels[i]).y = request.y;
    deref(push.culled_chunks_voxels[i]).z = request.z;
    deref(push.culled_chunks_voxels[i]).dominant_count = request.dominant_count;

    uint verts_per_block = (push.pass_index == 2) ? 36u : 18u;

    deref(push.indirect_cmds[i]).vertex_count = draw_count * verts_per_block;
    deref(push.indirect_cmds[i]).instance_count = 1;
    deref(push.indirect_cmds[i]).first_vertex = octant_id;
    deref(push.indirect_cmds[i]).first_instance = 0;
}
```
That is a snippet from one of my projects in a compute shader. Ignore most of what's going on there.
I do frustum culling and also HiZ culling beforehand to set that should draw for every single chunk.
Then I write a command to a command buffer.
```
CulledChunkInstance chunk = deref(push.culled_chunks[gl_DrawID]);
```
And in the vertex shader I get the chunk command information I wrote earlier in the compute shader.
Which usually has a pointer to some other buffer with the vertex information.
That pipeline is a very GPU driven rendering pipeline.
All you do from the CPU is upload or remove chunks and run the shaders.
Then I also see it does this in your shader:
struct Vertex {
// x, y and z in sixteenths of a block within the sub-chunk, then the
// texture layer.
@location(0) position_layer: vec4,
// u and v in sixteenths of the texture, the face (bits 0 to 2) and
// class (bits 3 and 4), and a spare byte.
@location(1) uv_face: vec4,
// The tint, sRGB-encoded, with the blend opacity in alpha.
@location(2) tint: vec4,
// Per draw: the sub-chunk's origin minus the camera, in blocks.
@location(3) offset: vec4,
}
Which uses 4 integers per vertex for its chunk position stuff it looks like. Then another 4 floats just for an offset within the chunk.
And then another 4 integers and 4 floats for uv face and tint.
Thats 16 * 4 bytes per vertex which is a lot.
If you had a vertex pulling technique where you had a big buffer and obtained vertex data from that big buffer in the vertex shader itself you could store the chunk position once at the very front.
Idk how your chunks are stored but for a reference a 16x16x16 chunk only needs 12 bits to point to any sub block in that chunk because it's 4 bits per x y and z.
Also using instance rendering per voxel face is something you can do.
So you don't store vertex data at all and all previous data per vertex you store per voxel face.
So you use 1/4 the memory for the exacy same data per voxel face.
There's so much more to be said but I think I've said enough."
