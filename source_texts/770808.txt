Problem
DictFSSTAnalyzeState::FinalAnalyze() was a single line:
```
return LossyNumericCast<idx_t>((double)total_string_length / 2.0);
```
DICT_FSST reported "half the raw bytes" for any input — never looking at the cardinality of the data, never accounting for the dictionary being rebuilt for every block, not even using total_count. Compression selection picks the method with the lowest estimate, so DICT_FSST could win with a size it cannot deliver.
Two shapes of data hit this:
Duplicates spread further apart than one block's dictionary can reach. Every block re-stores the values it sees, so almost nothing is deduplicated.
Large unique values. Only one or two fit per block, so each block is mostly empty.
Both end up needing far more blocks than the estimate suggests, and a block a large dictionary leaves mostly empty still costs a full block. A ratio of the raw size cannot express that. The dictionary compression this superseded could: it charges segment_count * block_size.
Reproduction
300k rows, 300 distinct values of 5760 bytes, scattered, 16KB block size:
```
ATTACH 'repro.db' AS db (BLOCK_SIZE 16384);
USE db;
CREATE TABLE t AS
WITH vals AS (
    SELECT g AS grp,
           (SELECT string_agg(md5(g::VARCHAR||'-'||x::VARCHAR),'') FROM range(180) x) AS txt
    FROM range(300) t2(g)
)
SELECT vals.txt AS description
FROM (SELECT (hash(i) % 300) AS grp FROM range(300000) t(i)) i
JOIN vals USING(grp);
CHECKPOINT db;
```

Fix
Both layouts DICT_FSST can produce are now estimated per block, and neither can bypass block accounting:
Dictionary layout — simulate the block packing, the way the dictionary analyze state already does, and charge for the blocks it needs. Memory during analyze stays bounded to one simulated block's distinct values: the hash set and its backing heap are both reset at each simulated block boundary.
FSST_ONLY layout — it stores every value encoded, with a symbol table per block and no selection buffer, so the values that fit a block follow from their encoded length. Whole blocks are charged. Only estimated where the mode is reachable: it requires every value in a segment to be unique, and a segment holds one block worth of values, so "no simulated block held a value twice" is exactly that condition.
FinalAnalyze returns the cheaper of the two.

…duckdb#27072)

The CTE join filter pusher only recognized join conditions whose sides were
bare column references and whose key domain was another materialized delim
CTE. Selective queries that fell outside this pattern materialized and
processed every recursive partition, a regression against the 1.5.x delim
join plans. This generalizes the pass:

- Keys may be deterministic single-column expressions (e.g. struct fields),
  composed through projections and aggregate groups on both the source and
  target paths.
- The key domain may also be a plain copy-safe subtree (base table scans,
  filters, projections), duplicated via LogicalOperatorDeepCopy, so a
  selective scan restricts partitions even when no delim CTE survives
  flattening.
- Sources are narrowed through joins to the smallest copy-safe subtree, and
  target keys translate transitively across inner-join equality conditions,
  so restrictions propagate through nested lateral joins.
- Filters are also collected from semi joins (correlated EXISTS) and the
  left side of left joins.

Keys whose expressions can throw (e.g. overflow-checked arithmetic or lossy
casts) are still not pushed, matching filter pushdown conservatism.

Ports duckdb-bot#223 to `main`. The patch applies cleanly.

Partitioned `COPY ... TO 's3://...'` sends two blocking `HEAD` requests
before each output file's `PUT` (#26268). Both checks came from cleanup
of failed queries (duckdb#24840): `CopyOutputLifecycle::GetOwnership` calls
`FileExists`, and the Parquet and CSV writers call it to decide whether
to use `FILE_FLAGS_EXCLUSIVE_CREATE`. On S3 neither changes the outcome:
`DirectoryExists` always returns true, so failed queries already keep
every output, and `httpfs` ignores `FILE_FLAGS_EXCLUSIVE_CREATE`.

For paths recognized by `FileSystem::IsRemoteFile`, this skips both
checks, returns `PRESERVE` from `GetOwnership`, and opens outputs
without `FILE_FLAGS_EXCLUSIVE_CREATE`. Local checks and cleanup are
unchanged. Other remote filesystems, such as Azure, now also keep failed
`COPY` outputs.

Per the original PR, with a local S3 endpoint delaying every response by
50 ms, writing 180 partitions dropped from 18.3 s to 3.4 s (Parquet) and
4.5 s (CSV), with zero `HEAD` requests.

Tests in `test/api/test_copy_output_lifecycle.cpp` count existence
checks and exclusive-create opens for partitioned and single-file
copies, and check that a failed remote copy removes nothing.

Follow-up to duckdb#25183. This PR started as the headroom fix for the
automatic read-ahead reservation (`ScanReadAhead::PushJob` asking the
governor for `pending_io_bytes + MINIMUM_JOB_IO_CHARGE`); main has that
line since 417308b, so after merging main this PR is down to what
the growing reservation exposed, and to making the budget observable and
measured.

### Table scan: re-check a settled read-ahead job's row group before
decoding it

A job's zonemap checks run when the job is produced. With the
reservation growing to its cap even a single-threaded scan runs several
row groups ahead, so a Top-N boundary set after a job was produced no
longer pruned the row groups already in flight: they were decoded and
emitted. `CollectionScanState::RecheckPreparedRowGroup` re-runs the
row-group zonemap check once per settled job, before its prepared vector
is decoded; a row group pruned since then is dropped (its prepared rows
leave `rows_scanned`, it is not counted as scanned). The I/O has already
happened at that point, the decode and the downstream work are saved.

Test `test/sql/topn/top_n_pruning_read_ahead.test` (from the review):
`threads=1`, `storage_block_prefetch='debug_force_always'`, `ORDER BY i
LIMIT 8193` over five row groups plus three all-NULL ones. The table
scan reads 16,384 rows on main and 10,240 rows here.

### Parquet: main's recheck misses NULLS FIRST boundaries

main already re-checks dynamic filters before decoding a queued Parquet
row group (3c7d7c9, `ParquetReader::DynamicFiltersExcludeRowGroup`),
but it found the filter through `GetOptionalDynamicFilterData`, which
matches only a bare `dynamic_filter(i)`. `ORDER BY i NULLS FIRST` pushes
`i IS NULL OR dynamic_filter(i)`, so all eight queued row groups were
still decoded. It now uses `ExpressionFilter::ContainsInternalFunction`,
as `ColumnData::CheckZonemap` does. Test
`readahead_dynamic_pruning_nulls_first.test`: 8 decoded groups on main,
1 here.

The earlier revision's multi-file `RecheckRowGroupFilters` hook and its
plumbing are gone: the review found that it returned the scan state to
the pool without `FinishRowGroup`, so a pruned group's prefetch ranges
leaked into the next group's prefetch log. `recheck_prefetch_log.test`
(from the review) pins that down; it passes on main and here.

### `ReadAheadBudget` log and the SQL-level test for the headroom line

A `ReadAheadBudget` DEBUG log type (one entry per pushed job:
`pending_bytes`, `budget_bytes`, `active_jobs`, written under the push
lock next to the `AsyncTaskSchedule` entry) and
`readahead_budget_growth.test`: 64 small Parquet files, `threads=16`,
`memory_limit='8GB'`, `debug_local_file_system_delay_ms=5`;
`max(budget_bytes)` must exceed four times the 8 MB x threads minimum,
and `pending_bytes <= budget_bytes + 16 x 16 MB` for every entry.
Without the headroom line the budget stays at the minimum and the first
assertion fails. Skipped under `force_external` (every reservation is
pinned at its minimum) and the restart configs (logging state is lost),
like the sibling log tests.

When DuckDB filters rows with `OR`, it checks one condition at a time.
Each condition picks out the rows that pass it, and those rows are added
to the result. The rows from each condition are in order, but adding
them one list after another leaves the combined list out of order. So
today, after the last condition, DuckDB sorts that list again, for every
batch of rows. That sort is most of the cost of an `OR` filter.

This PR merges each condition's rows into the result in order as they
arrive, the way you would combine two sorted lists, so nothing needs to
be sorted at the end. If a condition's own rows are ever out of order,
which a nested `AND` can cause, they are sorted first. The rows returned
are exactly the same as before.

To measure it, I ran each query below five times on thirty million rows
with one thread and took the median. I turned off filter pushdown so the
filter is evaluated by the code this PR changes, rather than inside the
table scan:

    (hash(i) % 1000)::INT AS v,
    hash(i * 3) % 2 = 0 AS x,
    hash(i * 5) % 2 = 0 AS y
FROM range(30000000) r(i);

SET disabled_optimizers = 'filter_pushdown';
SELECT count(*) FROM m WHERE v < 250 OR v >= 750;
SELECT count(*) FROM m WHERE x OR y;
SELECT sum(CASE WHEN v < 250 OR v >= 750 THEN 1 ELSE 0 END) FROM m;

Preserve thread caps at the sink and aggregate states across repeated…
…

… finalization (duckdb#27770)

**Sink thread caps.** `Pipeline::TryGetMaxThreads` accumulates a
pipeline's parallelism cap from left to right: the source's
`MaxThreads()`, each parallel operator folded in with `MinValue`, then a
clamp to the scheduler's thread count. The sink is the exception. Its
callback receives the accumulated value, but the return value is
assigned directly, so a sink returning more than its input raises a cap
that the source or an operator has already lowered. Every stage should
only be able to lower the accumulated cap, never raise it.

No in-tree sink currently returns more than its input, and
`PhysicalBatchCopyToFile` composes its memory-based limit with
`MinValue` itself. The defect is reachable through the C++ operator API
and surfaced with a sink that reported the scheduler count: the source's
single-thread requirement was silently discarded and the pipeline was
scheduled wide. The fix composes the sink's answer with `MinValue`,
matching the operator loop, and removes the trailing scheduler clamp
that the pre-sink clamp already makes redundant. The added API test
builds a minimal source/operator/sink pipeline with configurable limits
and checks the composed result and the callback's input for caps below,
at, and above the scheduler count. SQL cannot replace a sink's
`MaxThreads` callback or observe the composed value deterministically,
so the reproducer uses the C++ API.

**Aggregate state across repeated finalization.** A USING KEY recursive
CTE finalizes the same aggregate states repeatedly: every recurring scan
and direct key probe of an iteration reads them, later iterations update
them, and the final drain reads them once more. A finalizer must leave
the state valid for further reads and updates. Two finalizers changed
the state they exported.

`MinMaxNOperation::Finalize` sorted its heap in place with `sort_heap`,
so the next iteration inserted into an array that no longer was a heap:

```sql
WITH RECURSIVE t(k, v, iter) USING KEY (k, min(v, 3), max(iter)) AS (
    SELECT 0, i, 0 FROM range(1, 4) r(i)
    UNION ALL
    SELECT n.k, 2, 1 FROM t n JOIN recurring.t r USING (k) WHERE n.iter = 0
)
SELECT v FROM t;
```

returns `[2, 3, 1]` instead of `[1, 2, 2]` after a single update. The
finalizer now sorts an index array over the slots as a heap, which
yields the same order including ties, and leaves the heap untouched.
`BignumIntermediate::ToBignum` trimmed the intermediate before copying.
It now computes the trimmed range and copies from it, so the conversion
is const. The trim is value-preserving and every finalize of the keyed
state is currently serialized, so this part is not observable through
SQL today, but it violates the same lifecycle contract.

The new tests cover the read-then-update lifecycle for the n-variants of
min, max, arg_min and arg_max, the holistic aggregates, owned string
states and BIGNUM sums, at several thread counts and with operator
caching on and off.

…argument names (duckdb#27468)

`FunctionSerializer::Deserialize` can reinterpret a genuine expression
alias as a named-argument name. The exposure is not specific to one
function: every varargs function receives an automatic `*args` +
`**kwargs` signature (`SimpleFunction` constructors), and any
kwargs-capable function whose trailing argument carries an alias is
affected. Scalars, aggregates and window functions all deserialize
through this shared path. `least` is the repro, with round-trip
verification over scalar subqueries:

```sql
SET debug_verify_serializer=true;
SELECT least((SELECT 41), (SELECT 42), (SELECT 43));
-- Serialization Error: Error during bind of function in deserialization:
-- Duplicate named argument "SUBQUERY" in function call to '"least"'
```

With exactly one trailing subquery the round trip succeeds, but the
argument is silently rebound as a named argument through the `**kwargs`
catch-all:

```sql
SELECT least(10, 20, (SELECT 3));  -- round-trips as least(10, 20, SUBQUERY := ...)
```

In-tree varargs functions fold the kwargs back into the argument list,
so the value comes out right today. The deserialized plan is still not
the plan that was serialized, and any function whose bind inspects
argument names would see different arguments after a round trip.

### Mechanism

Subquery flattening replaces a `BoundSubqueryExpression` with a
`BoundColumnRefExpression` whose alias comes from
`Expression::GetName()`. Without an explicit alias that falls back to
`BoundSubqueryExpression::ToString()`, the literal string `SUBQUERY`.
That is the one in-tree producer of such trailing aliases, but the
deserializer would misread an alias from any producer.

`FunctionSerializer::Deserialize` has a compatibility heuristic,
`RestoreNamesFromAliases`, for plans serialized before argument names
were written (fields 508 and 509). Those fields were only written when a
call had named arguments, so a freshly serialized all-positional call
was indistinguishable from an old plan whose trailing arguments were
named. The heuristic consumed genuine aliases of trailing children of
any kwargs-capable function as argument names. Two trailing children
aliased `SUBQUERY` collide as duplicate names, and a single one becomes
a keyword argument.

### Fix

The ambiguity is on the wire, so current plans are made self-describing.
`SerializeNamedArguments` now always writes the positional count (field
508) when serializing for v2.0.0, including for all-positional calls,
and the deserializer runs `RestoreNamesFromAliases` only when the field
is absent. Fields 508 and 509 are gated on the v2.0.0 storage version
and no released reader predates them within that format, so the
unconditional write affects no released reader. Plans written by older
releases keep taking the heuristic path. Fixing the shared serializer
covers all function classes and all alias producers at once.

Pre-v2.0.0 compatibility mode has no such fields, and named arguments
genuinely travel in child aliases there. For that path the heuristic is
narrowed to functions without a `*args` parameter. The pre-v2.0.0 writer
folds the `**kwargs` of a `*args` function into the positional list, and
no released version could bind named arguments to such functions, so a
trailing alias on a `*args` function is always a genuine alias.
Functions that take only keyword arguments (`struct_pack`,
`struct_insert`, `struct_update`, `union_value`) keep restoring names
from aliases, the case the heuristic was written for and the one shape
where the alias is the name by the legacy convention.

Stopping the aliasing of machine-generated subquery column references in
`plan_subquery.cpp` was rejected: it hides one producer of trailing
aliases while leaving the deserializer ready to misread any other
genuine alias.

### Tests

`test/sql/serialization/function_argument_names.test` covers the
multi-subquery failure for `least`, `greatest` and `concat`, the silent
single-subquery reinterpretation, subqueries in non-trailing positions,
nested kwargs-capable calls, a zero-argument call, and genuine named
arguments (`least(3, x := 2)`, `struct_pack`, `struct_insert`,
`union_value`, the legacy positional `struct_pack` alias capture,
table-function keyword arguments). The struct results are returned
directly because `typeof` folds to a constant at bind time and would not
see the deserialized plan. A second section repeats the key cases under
`SET storage_compatibility_version='v1.4.4'`, where only the heuristic
narrowing applies: subquery cases must read back positionally while
`struct_pack` field names are still restored from aliases.

Result assertions alone cannot distinguish the unconditional field write
from the heuristic narrowing, since in-tree varargs functions produce
the same values either way.
`test/sql/serialization/function_argument_metadata.test` therefore pins
the serialized metadata through `json_serialize_plan`: an all-positional
call must record its positional count, a named call its argument names,
and the legacy positional `struct_pack` call its captured names. The
all-positional assertion fails if the unconditional write of field 508
is reverted while every result-level test stays green.

This PR removes the specialized `PartialBlock` implementations
`PartialBlockForIndex`, `PartialBlockForCheckpoint` and
`InMemoryPartialBlock` by introducing a new interface `BlockPackable`.
This interface acts both as a capability, where implementers are able to
be moved through the `PartialBlockManager`, as well as a generic
container within `PartialBlockManager` itself. The only required
function to implement the interface is a `Finalize` step, which acts as
a callback to inform the packable object where it resides on disk.

`PartialBlockAllocation` which were passing around blobs of information
through callers and internals of `PartialBlockManager`. Instead we now
offer a single entrypoint `Write(BlockPackable, BufferHandle,
byte_size)` that handles block creation, allocation and registration
internally. In `FULL_CHECKPOINT` mode it returns the corresponding block
pointer which is set eagerly (because metadata needs to know up front
where we will be placing the data), and a `nullptr` otherwise.

Hopefully the internal flow should be easier to follow:
- First acquire a partial block, either through creation or reuse (this
does not allocate memory).
- Then copy the data into a buffer backed by the partial block, or reuse
the source buffer if able.
- Then check if we want to do an intermediate flush in case the partial
block is almost full, if we do not flush add it back to the internal
registry for reuse.

Alignment zeroing is now inlined which allowed us to remove
`UninitializedRegion`, and the inline zeroing itself can perhaps be
completely removed depending on the solution to
duckdblabs/duckdb-internal#11200.

Note this does not pack column segments and index buffers together, it
does make this behavioral change easier afterwards.

This is the next slice of the parser performance work, following duckdb#27527.
It takes the matcher from "one frame per grammar level" to "one frame
per *interesting* level" in the two places that dominate the frame
count: the expression precedence ladder and rules that start with a
choice.

### What changes

**Prepared list groups** (commits 1 and 4). Most of `expression.gram` is
a ladder of collapsible lists of the shape `X <- Y Tail?` where every
element after the first is an optional with a literal-only FIRST set.
Those chains are now prepared as a *group* when the grammar is compiled,
with the merged FIRST set of all their tails. A list frame that enters a
group jumps straight to the innermost member, and when that member
completes and the merged tail set rejects the next token,
the whole group collapses to the result in one step instead of
completing one frame per level. The last commit lets a member with an
optional prefix join the group too, when its FIRST set proves the prefix
absent at the current token.

**Leading choices and choice regions** (commit 3). A list whose first
element is a choice now matches the choice in place: the alternatives
are tried with the list frame's own speculative cursor and the chosen
result simply becomes the list's first child, so no choice frame is
pushed. When the alternative is itself a plain list, the frame enters it
as a *choice region* (a small arena record remembers the enclosing list,
alternative index and arena mark) and keeps going; if the region fails,
it is resumed and the choice continues with the next alternative. Custom
selectors and the public single-step execution stay on their existing
paths.

**Smaller stuff** (commit 2). Generated transforms size their output
vectors from the parse tree instead of first collecting list items into
a temporary vector, and a list frame appends child references directly
into a span of the result arena that it hands to the `ListParseResult`,
instead of filling an arena vector and copying it on completion.

… subqueries (duckdb#27958)

A correlated subquery whose aggregate repeats an empty grouping set
returns wrong results, and the default optimizer pipeline raises an
internal error:

```sql
SELECT o.k, a.c
FROM (VALUES (7), (8)) AS o(k),
LATERAL (
    SELECT count(*) AS c
    FROM (VALUES (1)) AS i(k)
    WHERE i.k = o.k
    GROUP BY GROUPING SETS ((), ())
) AS a
ORDER BY ALL;
```

The expected bag has `(7, 0)` and `(8, 0)` twice each. Default settings
raised `INTERNAL Error: Attempted to access index 2 within vector of
size 2`. With `PRAGMA disable_optimizer` each pair appeared once.
Investigating this exposed four independent defects.

**Recovery multiplicity and GROUPING() in decorrelation.**
`FlattenDependentJoins::PushDownAggregate` adds the delim keys to every
grouping set, so each originally empty set emits one row per present
key. Keys without inner rows are recovered by a LEFT join against the
delim scan, which null-extends exactly once, while n empty sets need n
recovered rows. The recovery now joins recovered rows against an n-row
constant table on the count(*) marker, so aggregate rows still
null-extend once and recovered rows multiply. GROUPING() on recovered
rows produced NULL instead of the empty-set mask. The existing
marker/CASE replacement machinery now also maps grouping-function
bindings to constant masks projected next to the empty-input aggregate
values. The INNER shortcut that drops missing keys entirely is
restricted to the only equivalent case, a single empty set without
grouping functions under NULL-propagating consumers. Previously a
sum-only subquery over `GROUPING SETS ((), ())` lost a row and its
scalar variant lost the cardinality error.

**The NULL-propagation shortcut flag crossed row-observing operators.**
The INNER shortcut consumes `propagate_null_values`, whose contract is
that nothing above the aggregate can distinguish one all-NULL row from
no row. Several descents forwarded or reset the flag across operators
that do observe row presence: aggregates, windows, cross products, set
operations, DISTINCT, and ORDER BY. A `row_number()` over a correlated
ungrouped sum returned NULL instead of 1, a DISTINCT under an INNER
lateral returned zero rows, and cross-product and UNION ALL shapes lost
the scalar cardinality error. Every descent now either clears the flag
or documents why forwarding is sound. Filters and projections keep the
existing volatile/throw/becomes-NULL screening.

**Aggregate deduplication vs positional consumers.** The internal error
is an optimizer interaction. The grouping-sets rewrite materializes the
aggregate directly as a materialized CTE definition, whose readers are
positional. `CommonAggregateOptimizer` merged the identical marker
count(*) into the user's count(*), shrinking the CTE's column count
while consumers kept reading the old position. Binding remaps cannot
reach positional consumers. The optimizer now tracks whether the current
chain's column count is positionally constrained (set-operation
children, materialized and recursive CTE children) and skips
deduplication there. Projections and aggregates reset the constraint
because their parents consume them by binding. Plain projected
duplicates still merge.

**Single-join uniqueness proofs.** Both deliminators convert a SINGLE
join to LEFT when the aggregate's groups are covered by the join keys.
That proves at most one row per key only for a single grouping set. With
multiple sets the scalar subquery cardinality error was silently lost on
both delim paths. `Deliminator::TrySwitchSingleToLeft` and the CTE
rewriter's `SingleJoinRHSIsDeduplicated` now bail out when the aggregate
has more than one grouping set.

All wrong behaviors above reproduce on main before this change. Nested
shapes may now plan a LEFT recovery join where the INNER shortcut
previously applied, a plan-only effect of the conservative flag audit.

Known limitations: the CTE definition keeps the redundant marker
aggregate state instead of merging it, and the consumer side of a
materialized CTE is protected conservatively although its bindings pass
through. The same positional hazard class exists in principle for
projection maps populated by `ColumnLifetimeAnalyzer`, but no reachable
shape was found. Independent of decorrelation, the binder drops
all-empty grouping-set lists when no aggregate is present, which will be
reported separately.

Model the phases of the DICT_FSST writer in the analyze simulation
…

The estimate charged the raw dictionary of every simulated block and decided
once per row group whether FSST_ONLY was reachable. The writer does neither:
it fills a segment with room for a symbol table reserved, then decides for that
segment whether to FSST encode its dictionary, and continues in the layout it
chose. A dictionary that compresses well was therefore estimated at several
times its size, and a single repeated value anywhere ruled out FSST_ONLY for
all segments.

Each simulated block now has a mode, mirroring DictFSSTCompressionState:
unencoded with the symbol table reserved, then unencoded, DICT_FSST or
FSST_ONLY once it fills up, decided the way TryEncode decides. FSST_ONLY is
therefore per block, and its blocks do not hash or remember their values.

The size of an encoded dictionary and of its symbol table are measured by FSST
encoding the first 16 KB of the values of a block, at the first decision and
every fourth after it. Two behaviours of the writer are modelled so the
estimate matches what it produces: FSST only encodes a string while the output
buffer holds twice its length plus 7 bytes, and the writer is given a buffer
as large as the dictionary, so a dictionary of few large strings stays
unencoded. And a value added in DICT_FSST mode reserves twice its length until
it is encoded.

The set of a block grows by a factor of four, as blocks hold more values now.

The encode threshold and the check for an encoded state move to the shared
header so the writer and the simulation use the same ones.

Tests: a Catch test requires the estimate to be within 15% of the bytes the
writer produces for five kinds of data, which the previous estimate was off by
a factor of 8 to 30 for compressible data. Two SQL cases cover the selection of
DICT_FSST for an encoded dictionary and for unique values with one duplicate.
