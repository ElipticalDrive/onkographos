The embergen samples are really good. My volumetric data is more plasma-like, meaning that it can be bright, but nearly transparent. In other words, its colors have premultiplied alpha, and the renderer does something like this:
```
vec4 sum = vec4(0);
float dt = 0.001; // approx voxel size

for (float t = dt*0.5; t < tmax; t += dt) {
  vec3 p = rayOrigin + t*rayDirection;
  vec4 col = texture3D(volumetricData, p);
  
  // shadowData[p] = integral(s=0..inf, volumetricData[p + s*sunDir].a)
  col.rgb *= texture3D(shadowData, p);

  // Don't do this, alpha is premultiplied.
  // col.rgb *= col.a;

  sum +=  dt*col*(1.0 - sum.a);
  if (sum.a > 0.995) break;
}

return sum;
```

Here is one of my samples - a 100 x 100 x 100 grid with 'density' and 'color' components: flame_100.zip
It would be good to support volumetric mipmaps for quick previews. For some reason, even Blender doesn't get this right.
Custom data compression would help too. Using 4 x float32 to store one RGBA voxel is often too much. For example, the density component can be represented with 1 byte and a non-linear mapping to float32: x -> 1.0 / (1.0 + exp(-x)).
A related nice feature would be block read-writes. Similar to OpenVDB's copyToArray/copyFromArray, your webgpu implementation could provide API to download or upload a block of the 3d texture: copyToArray(ijk_min, ijk_max, cpu_array) would download data to CPU, and copyFromArray would upload data to GPU.

For reference, here is a couple renders from Blender (30 mins per frame with full GI settings):
the same scene without GI (note the color change):
Blender 5.2.0a scene: flame_100.zip
The render doesn't use the color component. Instead, it sets the color to a const value of #ffc819. There is a point light source at the (0,0,0) position. The density grid is downsampled to float16 and values below 0.001 are discarded. It would be even better if voxels were stored as 8 bit values with a custom density function, e.g. byte -> 1/(1 + exp(-3.7*byte/255)).
If I were to implement something like this in GLSL, I'd precompute shadows in concentric spheres and store them in a separate VDB grid with 8-bit voxels of the same shape as the scene. This works because the shadow data is meaningful only where density > 0, and because there is only 1 point light source. This can be done in O(N) time, and in this case N=94400. A decent scene would have 1 billion active voxels. Then I'd do the usual raymarching pass, using the precomputed shadow data along the ray. To do global illumination (GI), I'd make each voxel in the volumetric shadow data sample light intensity from its neighborhood. Moreover, the shadow data can be stored at 2x lower resolution without much visible difference.
