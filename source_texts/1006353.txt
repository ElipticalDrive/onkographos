fix(niivue): keep the chunked entry when a refresh races a plan swap …
…
5195521
```
…on WebGPU

swapVolumeChunkPlan sets vol.chunkPlan before the WebGPU renderer's swap
awaits a new uploader, and the swap records the plan on the cached entry
only after that await. A refresh landing in between (updateGLVolume, or a
setVolume colormap change) saw the new plan on the volume and the old one
on the entry, evicted the entry with every resident brick, and rebuilt it
from one brick; the swap then resumed on the evicted entry and leaked an
uploader and a brick.

- The swap records itself on the entry as pendingSwap while it runs, and
  _ensureChunkedVolumeEntry waits for a swap to the plan it was asked for
  before deciding to evict.
- The swap takes the display key before its await. When the colormap or
  window changed since the resident bricks were baked, none carry over, and
  the key it stores is the one its uploader baked, so a pending refresh
  still finds the entry stale. Before, a colormap change racing a swap could
  leave the volume drawn in the old colormap (this half also affects main).

WebGL2 creates its uploader synchronously, so it has no such window.
e2e/chunk-plan-swap-race.spec.ts covers both refresh kinds in both orders
on both backends.

Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
```

fix(niivue): settle the chunk stream when the view needs no more bricks
…
2cff5dd
```
whenChunkStreamSettles resolved at once only when every brick was
resident, and otherwise waited for chunkStreamIdle, which fires only after
a busy frame. A 2D view that needs only some bricks, all already resident,
never has a busy frame, so the promise, and setVolumeChunkGrid with it,
sat out the full 30 s timeout.

After the kicked draw it now waits two animation frames; if no
chunkStreamProgress fired and nothing is pending or in flight, the stream
is settled. A busy stream still waits for chunkStreamIdle, so a 3D view
still resolves with every brick resident.

e2e/chunk-stream-settle.spec.ts covers the 2D partial working set, the
single-brick case, and the fully tiled 3D render on both backends.
```

fix(niivue): drop stale bricks when a WebGL2 plan swap follows a disp…
…
1ab7255
```
…lay change

A colormap or window set on the volume but not yet refreshed leaves the
resident bricks baked with the old state. The WebGPU swap already refuses to
carry those bricks into the new plan; the WebGL2 swap kept them and recorded
the new display key, so the volume stayed drawn in the old colormap and no
later refresh found the entry stale.

The WebGL2 swap now takes the display key before it rebuilds the uploader and
remaps the manager with an empty match when the key changed, so it re-admits
brick 0 with the new state and the stream refills. The decoded tier still
carries over: it holds source bytes.

e2e/chunk-plan-swap-race.spec.ts gains the case on both backends; it fails on
WebGL2 without this change (8 stale bricks kept, expected 1).
```

Rechecked 1ab72555ae17 against 919d7f0dedcd.
Hold: one new P2 in the stream-settlement shortcut. The plan-swap repairs and display-key invalidation look correct, but packages/niivue/src/NVControlBase.ts:3930–3931 now treats zero pending/in-flight uploads after two frames as settled even when bricks are still cross-fading. The renderer's existing settled verdict explicitly includes !fadeActive; ChunkStreamEmitter documents that this is what makes completion safe for screenshots.
Reproduced twice in a real Chromium/WebGL2 view, including an independent rerun: use an AXIAL slice through the first brick, a coarse floor, supported chunkFadeMs: 3000, and await setVolumeChunkGrid(0, [1,1,4]). The call returned after about 1.59 s / 2.38 s with resident=1, total=4, pending=0, inFlight=0, and the fade still active. An immediate center pixel differed from the fully settled image (independent rerun: RGB [252,184,22] versus [255,179,0]). This makes the public wait complete while the image is still changing, despite its screenshot-readiness contract. The existing new tests use no coarse floor and miss this case. A controlled comparison using the previous settle function waited for its 30 s timeout and returned stable pixels; the full previous tree was not rerun. Default-duration fades did not reproduce on this slow software GPU, so this report specifically concerns the supported longer-fade configuration.
Please retain the no-new-work fast path, but resolve it from a drawn frame's actual settled verdict, including fade completion, rather than upload counts alone. Add a coarse-floor/fade case that verifies the returned image has settled. This is the new code blocker for #292 and its descendants; #300's previously reported spread race is fixed.

An additional independent browser probe nevertheless exposes the fade-settlement regression described on #292.
Standards: no production-code blocker. Two nonblocking test-maintenance notes: the new plan-swap spec requires a private cache object's identity (package AGENTS.md asks for public-contract assertions), and the two new specs duplicate their pixel probe/volume fixture.
