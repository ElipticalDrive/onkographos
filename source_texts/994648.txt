What and why
On top of #36, in the voxel stack. Every brick kept nine arrays of 4096. Six are used only while it is stepped: flows east, up and north, heads, shares and its part. A sleeping brick's flows were cleared to zero and the rest went unused. So a still lake took the same 133 KB a brick as moving water, up to about 136 MB at the default MaxBricks of 1024.
Brick.Rest(), as a brick falls asleep (where its flows were cleared): its flows, heads and shares become one all-zero array, and its part one all-zero index array. Both are shared by every sleeping brick and never written. It keeps its water, solids and closed faces, about 37 KB.
Brick.Wake(), as it wakes: fresh cleared arrays, the state the old code left them in.
Who reads a sleeping brick's arrays, and why that is safe:
its neighbours' flows look at its flows, which read zero as before;
no flow is worked out into a sleeping brick, so its shares are never asked for;
the heads pass, which wrote heads for sleeping bricks that nothing reads, now skips them, so nothing writes to the shared arrays.
The MaxBricks description and the README give the two figures.
Where it shows
Server simulation
Client (drawing, swimming, current)
Docs only
How it was tested
New test: two pools in bricks apart, one still and one fed all along. The still one rests, holds only zeros where its flows, heads and shares were while the other steps, and wakes with its water as it was when water is poured in. All 161 tests pass. The benchmark checksums are unchanged (pool 233587.81837429912, river 4938.90663962093).
Scratch benchmark (.NET): a 160 × 160 m pool 3 m deep, settled, 240 bricks all asleep. The heap after a full collection was 31.2 MB (133 KB a brick) before and 8.6 MB (37 KB a brick) after.
dotnet build -c Release passes (analyzers on) and tools/format-check.sh too
Tried in the game

Performance

Resting water blocks use less memory while retaining their water. They resume operation when new water is added, while neighboring moving water continues to be processed.

Normal simulation paths preserve the intended isolation, and no new externally callable interface was identified. A conditional recovery risk remains: an allocation failure during wake-up can leave shared storage attached to an apparently active brick.
Retained concerns
Low · reliability · inferred: Wake does not preserve exclusive ownership across allocation failure. Once FlowX is replaced, Resting becomes false even if a later allocation fails and leaves other fields referencing shared storage. If execution subsequently reuses the grid, Wake can skip repair and solver writes can corrupt arrays shared by sleeping bricks. The base retained independently allocated working arrays and did not have this wake-time mixed-ownership state. Successful execution is guarded correctly; continuation after allocation failure remains an unverified operational precondition.
Security review details
Security Blast Radius
inferred — If a partially awakened brick is reused and writes remaining shared storage, corruption can affect every sleeping brick referencing that storage in the same process, including other grids. This is broader than corruption of one brick; no cross-process or tenant attack path was established.
Trust Boundaries and Controls
observed — The normal server path gates simulation to an enabled server instance and retains the same VoxelServer between updates. Grid mutation is deferred while a step is underway, sources and drains run after a completed step, and publication finishes an outstanding step before reading bricks.
Resilience and Maintainability Implications
inferred — Successful repeated wake calls preserve ownership, but exception recovery does not have the same guarantee: FlowX acts as the completion sentinel before the remaining allocations complete. No grid invalidation or repair is present in the inspected update chain; host behavior after an allocation exception remains outside the established evidence.
Hardening Proposals
proposed — Allocate the complete working set into local variables before publishing any replacement fields, and mark the brick awake only after successful restoration. This would make allocation failure leave a retryable resting state rather than mixed shared and private ownership.
