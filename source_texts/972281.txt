Overlap the reduce-scatter and allgather phases across fragments on the host path so fragment i's allgather (pure network) runs concurrently with fragment i+1's reduce-scatter (network + CPU reduction). Previously the host branch of the SRA-knomial pipeline heuristic disabled pipelining (n_frags=1), leaving the NIC idle during every reduce step and the CPU idle during the entire allgather.
The host else-branch of get_pipeline_params() now sets conservative defaults: threshold 256KB, 512KB fragments, nfrags floor 2, pdepth 2, parallel order. Env override UCC_TL_UCP_ALLREDUCE_SRA_KN_PIPELINE still takes precedence. Correctness is unchanged: the CUDA in-place path already runs the identical fragmented schedule, and per-frag scratch is sized from max_frag_count (smaller frags -> smaller scratch).

Summary: The gtest job (shard 0) failed: 2 of 7759 tests failed — test_schedule.pipelined_real_subscription_failure_first and test_schedule.pipelined_depth_16_exact_lifecycle. Build and all other stages passed.
Root cause: These tests use a fault-injection harness that registers process-global hooks and counters — ucc_event_manager_set_subscribe_fault_cb(fault_subscribe_cb) and ucc_schedule_pipelined_set_lock_observer(fault_lock_observe) (test/gtest/core/test_schedule.cc:1025-1026), plus static globals g_fault_subscribe_attempt, g_fault_subscribe_fail_at, g_fault_lock_inits/destroys, etc. (lines 927-936). Once installed, fault_subscribe_cb stays active for the rest of the single gtest process and fires for every subsequent ucc_event_manager_subscribe() call — including from unrelated test_schedule tests — incrementing the shared g_fault_subscribe_attempt counter (and potentially returning a spurious UCC_ERR_NO_MEMORY when a stale g_fault_subscribe_fail_at matches). The two failing tests are exactly the ones with the tightest exact-equality oracles (EXPECT_EQ(fail_at+1, g_fault_subscribe_attempt) == 1, and EXPECT_EQ(32, g_fault_subscribe_attempt)), so cross-test contamination / gtest's non-source execution order makes them fail while the looser fault tests pass. The ucc_schedule_pipelined_init/_finalize unwind logic itself (src/schedule/ucc_schedule_pipelined.c) is internally consistent with the expected counts, confirming the defect is the leaked global test state rather than the production code path.

File: test/gtest/core/test_schedule.cc:1013-1027 (fault_reset installs hooks; no matching teardown) and the assertions at lines 1058, 1072-1076, 1111-1119.
Suggested fix: Make the fault harness self-contained per test. Add a TearDown() (or explicit cleanup at the end of each fault test / fault_expect_subscription_unwind) that unregisters the global hooks and resets counters, e.g.:
```

ucc_schedule_pipelined_set_lock_observer(NULL);

```

🤖 CI Triage Agent — UCC/ucc-test-mpi · commit 3a6f121d
TL;DR: All 8 ranks of ucc_test_mpi SIGSEGV'd at the entry (+0x34) of ucc_event_manager_notify with fault address (nil) — a stack overflow caused by unbounded notify → completed_handler → task_complete → notify → frag restart → post recursion in the pipelined schedule, newly reachable because PR #1354 turns on SRA-allreduce pipelining for host memory, where fragment tasks complete inline. Fix: make fragment restart asynchronous (enqueue the frag on the progress queue) instead of calling ucc_frag_start_handler() inline from ucc_schedule_pipelined_completed_handler().
Full analysis
Summary: Stage "Run UCC MPI tests (bulk)" (node 206) failed: ucc_test_mpi --mtypes host,cuda segfaulted (exit 139, core dumped) on every rank on funk17/funk18 immediately after the test banner, aborting the Slurm step.
Root cause: The backtraces are identical on all ranks and show a mutually recursive cycle inside libucc:
```
ucc_context_progress
 → libucc+0x1801a            (progress queue → ucc_task_complete)
 → ucc_event_manager_notify+0x6b
 → libucc+0x1cc13            (ucc_schedule_completed_handler, inlines ucc_task_complete)
 → ucc_event_manager_notify+0x34   <-- SIGSEGV, address (nil)
```
Faulting at offset +0x34 (function prologue) with address (nil) "Sent by the kernel" is the signature of a guard-page hit, i.e. stack exhaustion, not a bad pointer — the 21-frame backtrace is simply the truncated top of a deep recursion.
The recursion is structural in the pipelined scheduler:
ucc_task_complete() → ucc_event_manager_notify(UCC_EVENT_COMPLETED_SCHEDULE) → ucc_schedule_pipelined_completed_handler() which, still inside that notify stack, synchronously restarts the next fragment via ucc_frag_start_handler(...) → task->post() (src/schedule/ucc_schedule_pipelined.c:130). If the freshly posted fragment's tasks complete inline, their completion re-enters ucc_task_complete → notify → the same handler, which restarts the next fragment, and so on. Depth grows with schedule->super.n_tasks (total fragments), so a large host allreduce blows the 8 MB stack.
Why this only breaks now: before PR #1354 the only pipelined SRA path was CUDA, where completion is driven asynchronously through the progress queue (no inline completion, no recursion). The new host branch in ucc_tl_ucp_allreduce_sra_knomial_select_pipeline_params() enables UCC_PIPELINE_PARALLEL with threshold=262144, frag_size=524288, pdepth = (total >= 4*frag_size) ? 4 : 2 (src/components/tl/ucp/allreduce/allreduce_sra_knomial.c:218-239). For host buffers the knomial reduce-scatter/allgather tasks frequently complete inline during post()/progress, and a multi-MB allreduce yields n_frags_total in the hundreds — hundreds of nested notify/handler/post frames.
Implicated commit: eade84c8 — "TL/UCP: enable host-side SRA allreduce pipelining", Ferrol Aderholdt (branch HEAD 3a6f121d, "REVIEW: address formatting"; same series: 4795822a, 6086aabd)
File: src/schedule/ucc_schedule_pipelined.c:111-139 (restart loop; inline ucc_frag_start_handler call at line 130), reached via src/components/tl/ucp/allreduce/allreduce_sra_knomial.c:218-239 (new host pipeline params)
Suggested fix:
Break the recursion — do not post fragments from inside the completion notify chain. In ucc_schedule_pipelined_completed_handler(), mark fragments UCC_COLL_TASK_FLAG_RESTART_PENDING (already done) and let the pipelined schedule's own progress/ucc_progress_queue_enqueue path drain and restart them after the stack unwinds, instead of calling ucc_frag_start_handler() in the while loop at line 130. This keeps the depth O(1) regardless of n_frags_total.
As a short-term mitigation while (1) is implemented, cap the number of restarts performed inline per handler invocation (e.g. restart at most one fragment and return UCC_OK), and/or bound n_frags_total for the host path by raising frag_size/lowering pdepth in ucc_tl_ucp_allreduce_sra_knomial_select_pipeline_params() so the host branch cannot generate hundreds of fragments.
Add a regression test that drives a host-memory SRA allreduce with msgsize >> frag_size (many fragments) so inline-completing fragments exercise the restart path — the current gtest coverage clearly does not reach the deep-recursion case.
Related: PR #1354 (this change); prior restart-path fixes in the same code: c8314d31 "SCHEDULE: fix task restart in ppln schedule (#1262)" and 4f67436b "CORE: fix n deps overflow in pipelined schedule (#1051)".

## What
Start the first fragments of a pipelined schedule under the schedule
lock in `ucc_schedule_pipelined_post()`, and complete a schedule that
finishes during post only after the unlock.

## Why ?
`ucc-test-mpi` aborts in the `-T` pass with `ucc_schedule.c:132
Assertion '0' failed` (`ucc_dummy_progress`), for example builds 88, 90
and 94 on #1366. #1364 made the completed handler finish the schedule
only from its outermost frame, after unlocking, but post still starts
the first fragments without the lock:

1. Since #1354, host allreduce on a single-node team pipelines by
default (SRA knomial, 2 MB = 4 fragments at depth 4), so post starts
several fragments in a row.
2. In `THREAD_MULTIPLE` another thread can complete fragment 0 during
that loop. Its completed handler updates `n_frags_in_pipeline`,
`next_frag_to_post` and `n_frags_started` under the lock, while the
poster updates them without it.
3. A lost update can restart a finished fragment after the schedule has
completed. Its tasks stay in the progress queue after the owner frees
them, and TL/UCP tasks and schedules share one mpool, so the stale entry
is later progressed as a schedule and hits `ucc_dummy_progress`.

In CI the abort is on the single-node `half` team in the default `-T`
configuration.

## How ?
- `ucc_schedule_pipelined_post()` takes the recursive schedule lock
(`THREAD_MULTIPLE` only) around `ucc_schedule_start()` and counts itself
as the outermost `handler_depth` frame. A schedule that completes during
post, inline or on a thread waiting for the lock, is completed after the
unlock, as in the handler. The handler already posts restarted fragments
while holding this lock, so posting under it is not new.
- New checks in `test/gtest/core/test_schedule.cc`:
- Fragment setup records whether it ran without the lock in
`THREAD_MULTIPLE`. `nested_completion` and `nested_failure` check it,
and `post_starts_frags_locked` covers 4 fragments at depth 4.
- `cross_thread_completion`: fragment tasks complete on helper threads
while post is still starting fragments, 200 reposts, checking one
completion per post and the fragment counts.

Signed-off-by: Tomislav Janjusic <tomislavj@nvidia.com>
