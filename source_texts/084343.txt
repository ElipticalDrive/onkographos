Adds rendering to a depth slice of a volume (3D) texture, on both WebGL2 and WebGPU, and mipmap generation for volume textures on WebGPU. Fixes #6342.
Changes:
New slice option on RenderTarget, used to render to one depth slice of a volume texture. To render to several slices, create a render target for each slice, all sharing the same texture
Rendering to a volume texture does not support multisampling, as a multisampled rendering cannot be resolved into a depth slice on WebGPU - the samples option is ignored, with a warning. A volume texture cannot be a depth buffer, so the depth buffer is a 2D texture, which the render targets of all slices can share
WebGPU: the mipmaps of volume textures are generated - after their data is uploaded, and after rendering to their slices. Previously they were not supported. The shader generating them is only created when a volume texture first needs it
When a volume texture has mipmaps, they are regenerated for the whole volume after rendering to a slice, as each mip level is filtered from several depth slices. The RenderTarget docs describe generating them only once when rendering many slices
API Changes:
RenderTarget constructor: new options.slice, the depth slice of a volume texture to render to. Defaults to 0.
New RenderTarget#slice getter.
```
const volume = new Texture(device, { width: 128, height: 128, depth: 32, volume: true, mipmaps: true });

// a render target for each depth slice, all sharing the volume texture
const renderTargets = [];
for (let slice = 0; slice < 32; slice++) {
    renderTargets.push(new RenderTarget({
        colorBuffer: volume,
        slice,
        depth: false,

        // generate the mipmaps of the volume once, after the last slice is rendered
        mipLevel: slice < 31 ? 0 : undefined
    }));
}
```
Examples:
render-targets/volume-texture: the fog volume can now be dynamic - rendered on the GPU into the depth slices of the volume texture, updating a few slices each frame - and can use mipmaps, generated from the uploaded data or after the slices are rendered, with an option to display a chosen mip level
Hidden test/texture-copy-read-layered: now also renders to the depth slices of volume textures and verifies the result, including the mipmaps generated after rendering and after upload

[P2] Handle unfilterable float32 volumes before generating their mips
Automated review by Codex (OpenAI AI agent). The new shader and auto pipeline layout require a filterable texture_3d<f32>, but RGBA32F (also R32F/RG32F) is only filterable when device.textureFloatFilterable is true. This is reachable even when the application's texture uses nearest filtering: the volume upload calls generateVolume whenever automatic mips are needed. Reproduced with DEVICETYPE_WEBGPU_BARE, a 4×4×4 PIXELFORMAT_RGBA32F volume filled with 0.5, mipmaps: true, and nearest min/mag filters. createBindGroup reports that UnfilterableFloat does not match Float; the encoded passes become invalid and a subsequent base-level read returns zeros instead of the uploaded values. On the PR base the identical upload/read succeeds (with the existing unsupported-volume-mips warning), and disabling mipmaps on this head also succeeds. Please account for the format/filtering capability before issuing these passes, using a non-filtering/manual-average fallback or explicitly skipping unsupported generation without invalidating the command encoder, and add a bare-WebGPU float32 regression test.

[P2] Preserve normalized sampling for odd mip dimensions
Automated review by Codex (OpenAI AI agent). Multiplying the destination coordinate by two only matches the filtered branch when the source extent is exactly twice the destination extent. When a source mip dimension is odd, this instead samples blocks anchored at the low edge and drops the final row/column/slice; min(..., last) does not address that shift. Reproduced on this head with a nearest-sampled 3×3×3 RGBA32F volume whose voxels are [x, y * 10, z * 100, 1]: mip 1 is [0.5, 5, 50, 1] on DEVICETYPE_WEBGPU_BARE, versus [1, 10, 100, 1] on regular WebGPU. The same issue exists in the 2D fallback (webgpu-mipmap.js:35): a 5×3 R32F x-gradient ends at 1.5 rather than 2. Please derive load coordinates/weights from the source and destination extents to preserve the normalized sample positions, and add odd-width/height/depth regression coverage; the new 8×8×8 tests cannot exercise this.
