Vulkan Ray
Tracing Payload Structure Explained
In Vulkan ray tracing pipelines, the ray payload is a user-defined
data structure used to pass execution context and shading results back
and forth between different ray tracing shader stages. This article
explains the technical definition of ray payloads, how they are declared
and used in GLSL shaders, how data flows across ray generation, hit, and
miss stages, and the performance considerations that dictate their
design.
What is a Ray Payload?
A ray payload functions as the primary communication bridge during
ray traversal. When a ray is cast, the calling shader provides a payload
instance to store data that downstream stages need to access or modify.
Typical payload data includes surface hit colors, hit distances, surface
normals, ray bounce counters, and visibility flags.
Because Vulkan allows custom payloads, there is no fixed hardware
structure; developers define the layout according to the specific
rendering algorithm being implemented (such as direct lighting, ambient
occlusion, or path tracing).
Payload Declarations
Across Shader Stages
Ray payloads are declared using GLSL storage qualifiers linked by
specific location indices. The declaration syntax depends on whether the
shader initiates the ray or responds to the ray traversal.
1. Caller Shaders
(Ray Generation, Closest Hit)
Shaders that call traceRayEXT() declare the payload with
the rayPayloadEXT qualifier, assigning it an explicit
location index.
```
struct RayPayload {
    vec3 hitValue;
    float hitDistance;
    int depth;
};

layout(location = 0) rayPayloadEXT RayPayload prd;
```
When invoking traceRayEXT(), the last parameter must
match the location index assigned to the payload:
```
traceRayEXT(
    topLevelAS,           // Acceleration structure
    gl_RayFlagsOpaqueEXT, // Ray flags
    0xFF,                 // Cull mask
    0,                    // SBT record offset
    0,                    // SBT record stride
    0,                    // Miss index
    rayOrigin,            // Origin
    tMin,                 // Min distance
    rayDirection,         // Direction
    tMax,                 // Max distance
    0                     // Payload location
);
```
2. Callee Shaders
(Closest Hit, Any Hit, Miss)
Shaders executed as a result of traversal—such as Miss shaders
(rmiss), Closest Hit shaders (rchit), and Any
Hit shaders (rahit)—receive the payload using the
rayPayloadInEXT qualifier at the same location index.
```
struct RayPayload {
    vec3 hitValue;
    float hitDistance;
    int depth;
};

layout(location = 0) rayPayloadInEXT RayPayload prd;
```
These shaders write directly to the fields of prd. Once
traversal concludes, control returns to the calling shader, where the
modified payload fields can be read.
Data Flow Lifecycle
Initialization: The Ray Generation shader
instantiates the payload structure, initializes its values (e.g.,
setting the bounce count or initial color), and calls
traceRayEXT().
Traversal: The hardware Traversal Engine processes
bounding volume hierarchies (BVH). If an Any Hit shader is present and
active, it can read or write to rayPayloadInEXT to handle
effects like alpha-tested transparency.
Evaluation:
If an intersection is confirmed and traversal finishes, the Closest
Hit shader executes, writing the evaluated lighting or material
parameters into rayPayloadInEXT.
If no intersection occurs, the Miss shader executes, typically
writing background or environment map color into
rayPayloadInEXT.
Resolution: Control returns to the Ray Generation
shader immediately following the traceRayEXT() invocation,
where the final values stored in rayPayloadEXT are
composited into an image or used to launch subsequent rays.
Memory and Performance
Considerations
While payloads are flexible, their size directly affects hardware
performance:
Hardware Limits: Devices expose maximum payload
size limits via
VkPhysicalDeviceRayTracingPipelinePropertiesKHR::maxRayPayloadSize.
The payload must not exceed this value.
Register Pressure: Large payload structures
increase register usage across all ray tracing stages. If a payload
cannot fit into GPU registers, the driver spills the data into
high-latency device memory (VRAM), reducing throughput.
Data Packing: Payloads should be tightly packed.
Align members along 4-byte or 16-byte boundaries (following standard
alignment rules) and compress data types (such as packing floating-point
normals into octahedral representations or 8-bit integers) to keep the
total payload footprint as small as possible.
