Refs #89. Information only: adds diagnostics, changes no renderer code, no tolerance and no pass/fail.
rea_b07_vol and rea_batch07_vol differ from the pinned images by 0.6% to 1.1% of the pixels on the hosted macOS device (virtualized), along the contours of the styles; the cause was "not isolated". crates/x3d-render/tests/device_volume.rs (run by the existing "Device diagnostics (information)" step, output in the macos-diag artifact, lines diag: filter|gradient|blend) separates three hypotheses:
H1, the trilinear filter of the voxel texture: distinct weight levels and worst error of a 2x2x2 and a 2x2 texture swept at 8192 fractions.
H2, the gradient normal of normal_fn (central differences of those samples), compared with the CPU in exact weights and in 8-bit rounded or truncated weights.
H3, the blend of hundreds of view-aligned planes into the 8-bit target (SRC_ALPHA, ONE_MINUS_SRC_ALPHA, as volume_gpu.rs), compared with the CPU per-step models.
Linux results so far (RTX 3060 Ti, lavapipe): the probes run and differ between devices (below, in the PR comments). render_rea_b07_vol on lavapipe fails on 290 shots (2% to 17% of pixels over 8, max 14 to 63), so the volume pass depends on the device's 8-bit blend and filter, not only on the macOS device.

MiniMax-M3.1-Flash QA
Review findings
1. The new diagnostic test is not actually protected by the CI workflow
Location: .github/workflows/macos-tests.yml
The device_volume test is added to:
```
cargo test ... --test device_volume ... 2>&1 | tee macos-diag/device_diag.log || true
```
The trailing || true masks every failure, including:
Rust compilation errors
WGSL shader compilation/validation errors
GPU/device initialization failures
Panics in the diagnostic code
Assertions added to the test in the future
As a result, the CI job will remain green even if this new test is broken. The same issue already applies to the other diagnostic commands in this workflow, but adding another test without making the workflow distinguish “diagnostic result” from “diagnostic infrastructure failure” increases the risk of silently shipping a broken diagnostic.
Recommendation: Either:
Keep the test intentionally non-failing but validate compilation separately, for example:
```
cargo test -p x3d-render --release --test device_volume --no-run
cargo test -p x3d-render --release --test device_volume -- --nocapture --test-threads=1
```
with the second command allowed to fail only if the test is explicitly designed to be informational; or
Remove || true and have the test itself skip cleanly when no compatible device is available, while allowing real compilation/runtime errors to fail CI.
At minimum, the workflow should record the command status separately from the diagnostic output.
2. The test can still panic on GPU/WGSL validation errors despite being documented as “information only”
Location: crates/x3d-render/tests/device_volume.rs
Probe::new() uses:
```
let module = device.create_shader_module(...);
let pipeline = device.create_compute_pipeline(...);
```
and the code later uses:
```
self.device
    .poll(wgpu::PollType::wait_indefinitely())
    .unwrap();
```
Depending on the wgpu version and backend, shader validation or device errors may be reported through validation errors, an uncaptured error, or a panic from the pipeline/device operation. The let Some(probe) = ... else { ... } only handles failure to obtain an adapter/device; it does not make the test robust against backend-specific validation failures.
This is particularly relevant because the test is explicitly intended to run on virtualized macOS/Metal and GL environments, where backend capabilities and shader validation behavior may differ.
Recommendation: Use the project’s existing error-handling conventions for wgpu validation, and either:
convert validation failures into a skipped diagnostic with a clear diag: message; or
explicitly assert that shader/device setup succeeds and let that infrastructure failure fail CI.
This should be documented separately from the informational comparisons, which should remain non-failing.
3. The test currently provides no regression protection
The two new tests only emit diag: messages and return successfully regardless of the measured differences. This is consistent with the file’s stated purpose, but it means the PR cannot establish that volume rendering is correct or that the hypotheses are actually resolved.
For example, the workflow will collect:
```
diag: filter ...
diag: gradient ...
diag: blend ...
```
but there is no threshold, expected range, or baseline comparison. A backend change that makes filtering or blending significantly worse will not be detected.
Recommendation: If these are intended strictly as one-time diagnostics, consider keeping them in a separate diagnostic test target or clearly marking them as non-regression tests. If they will remain in the normal test suite, add assertions for the properties that are considered stable, such as:
maximum interpolation error within a documented tolerance;
gradient angle and magnitude agreement within a documented tolerance;
blend output agreement within a small 8-bit quantization tolerance.
4. The device-selection helper does not verify that the requested backend was actually selected
Location: crates/x3d-render/tests/device_volume.rs
device() requests an adapter using headless_backends(...), but it does not verify the adapter’s backend. On systems with multiple available backends, or when the requested backend is unavailable, request_adapter may select another backend depending on the wgpu implementation and environment.
That matters because the test’s purpose is to compare Metal and GL behavior. The output currently reports diagnostics without clearly identifying the actual backend used.
Recommendation: Inspect adapter.get_info().backend and include it in the diagnostic output, or fail/skip if it does not match the requested backend. For example:
```
let info = adapter.get_info();
eprintln!("diag: probe backend: {:?}", info.backend);
```
Ideally, the test should explicitly state whether it ran on the requested backend.
Summary
I do not see an obvious algorithmic error in the trilinear interpolation or central-difference implementation: the CPU coordinate mapping and GPU offsets appear consistent with the stated shader behavior.
The main concern is CI reliability: the new test is added to a workflow that masks all failures with || true, while the test itself can still panic on backend or shader-validation errors. Separating diagnostic findings from infrastructure failures, validating the actual backend, and documenting whether the tests are intended to provide regression assertions would make this change safer and more useful.
