Summary
allocate homogeneous EXL3 eager-parity staging during runtime planning only when the configured fallback is reachable; serving refuses an unplanned late allocation
share prefill-only native mixed-Trellis buffers across exact-compatible serialized target runtime geometries
keep decode buffers owner-local because CUDA graphs capture their addresses
keep target and MTP-draft roles isolated, refuse inferred compatibility with older B12X builds, and copy any persistent output view before reuse
add startup telemetry (prefill_reused=True/False) for the live gate
This is a focused stacked successor to #228 for the two remaining actionable items in #203. The paired backend allocation contract is B12X #130.
Expected memory effect (not yet a GPU claim)
For the current GLM mixed target geometry at 3,072 prefill rows, the backend layout calculates one buffer set at 850.16 MiB/rank. If the two current layer partitions instantiate exact-compatible layouts as expected, one set is recovered. Under the production default (VLLM_EXL3_TRELLIS_MIN_M=1 with prefill Trellis enabled), the guarded parity path is unreachable and avoids the previously derived ~82.2 MiB/rank staging arena. The combined ~932 MiB/rank remains an estimate until the AIBoss gate records allocator and KV deltas.
If configuration makes parity reachable, its arena is instead allocated during eager runtime planning so normal automatic KV sizing counts it. That configuration does not receive the parity-staging saving.
No PP/TG or numerics gain is claimed. Kernel plans, launch order, math, and dtypes are unchanged.
Safety boundaries
sharing is enabled only when B12X supplies an immutable exact layout identity; old packages retain owner-local buffers
the pool is scoped by model and target/draft role
a worker runs one model batch at a time and its layers are stream-ordered; this assumption is part of the sharing contract
decode/captured buffers are never pooled
allocations are eager and exact-keyed; no grow/reallocation path exists
the mixed output's persistent FP32 buffer cannot escape into the residual stream, including a future same-dtype backend
reachable parity staging is allocated before serving; an impossible/unplanned parity path raises instead of allocating after KV sizing
Normal automatic KV sizing profiles these persistent allocations. Explicit --kv-cache-memory-bytes and --num-gpu-blocks-override remain operator escape hatches: they intentionally decouple KV allocation from measured safe capacity, so this PR cannot protect an oversized manual value.
Performance and concurrency
no request hot-path lookup or new synchronization is added; pool lookup occurs only while eager runtimes are planned
the existing FP32-to-model-dtype output conversion remains the lifetime boundary, and its common path is unchanged
fewer persistent arenas should shorten startup allocation work slightly, but no startup-time claim is made before GPU measurement
recovered VRAM is expected to become KV blocks under automatic sizing, reducing preemption and improving usable long-context concurrency; this PR does not change max_num_seqs or claim higher kernel throughput
future execution of model layers concurrently on independent streams would invalidate the sharing assumption and must reintroduce owner-local or synchronized storage

Memory-accounting and performance/concurrency audit after commit 244d85a6f:
Accounting result
Mixed prefill pool: the first exact-compatible layer allocates the persistent B12X arena during the normal dummy profile; later compatible target layers reuse it. Every model layer executes in that profile, so automatic KV sizing sees the surviving allocation.
Parity staging: the first draft's lazy allocator had a real late-allocation risk for reachable non-default parity configurations. It is now fail-closed: reachable staging is allocated while the eager runtime is planned, while the production default (min_m=1, prefill Trellis enabled) proves parity unreachable and allocates zero. Serving raises rather than allocating an unplanned arena after KV sizing.
Output lifetime: shared backend output cannot escape into a later layer's reuse. The common FP32→model-dtype conversion remains unchanged; a future same-dtype backend is forced to copy without hot-path storage-pointer queries.
Decode/graphs: decode buffers stay owner-local because their addresses are captured. CUDA-graph memory remains handled by the existing graph profile/capture phase.
Roles/processes: target and MTP draft use separate pools; TP/DCP workers are separate processes and therefore separate allocations.
This closes the new source-level accounting gaps under automatic KV sizing. It is not an absolute guarantee for manual capacity controls: --kv-cache-memory-bytes and --num-gpu-blocks-override intentionally bypass/replace profile-derived safe KV capacity. A turnkey profile that sets either too aggressively can still OOM despite this PR; the GPU gate must use auto sizing for the primary safety proof and test any supported fixed override separately.
Performance / concurrency implications
No kernel, launch geometry, math, dtype, request-time synchronization, or request hot-path lookup changes; PP/TG parity is expected, not a speedup.
Pool lookup and layout matching happen only during startup planning.
Automatic sizing should convert most recovered VRAM into additional KV blocks. The likely user-visible gain is fewer preemptions and more usable long-context concurrency, not a higher max_num_seqs setting or faster kernels.
Sharing is safe because one worker executes one model batch at a time and layers are stream-ordered. If vLLM later overlaps different model layers on independent streams, this pool must be revisited.
Focused validation: 20 passed, Ruff clean, format clean, git diff --check clean. GPU evidence remains required before the draft is promoted: real mixed-K allocation identity, ABBA outputs, stable graph replay, allocator/KV delta, no post-profile growth, MTP smoke, C1/C8 PP/TG/MAL, and preemption/concurrency behavior on AIBoss/Fruit.

🗄️ Data Integrity & Integration | 🟠 Major | ⚡ Quick win
The copy condition misses the first allocating layer.
_mixed_trellis_prefill_buffers stores every newly allocated buffer set in _MIXED_TRELLIS_PREFILL_BUFFERS. The allocating runtime records buffers_reused=False, but its buffers are already shareable. A later compatible layer then receives the same buffers and overwrites them inside the same forward pass.
For a same-dtype backend, copy=False returns a view of that shared storage. The first layer's output can then change after a later layer runs.
Base the copy decision on whether the buffers are shared, not on whether this runtime reused them.
🐛 Proposed fix
```
-        output = raw_output.to(
-            dtype=x.dtype,
-            copy=state["buffers_reused"] and raw_output.dtype == x.dtype,
-        )
+        output = raw_output.to(
+            dtype=x.dtype,
+            copy=state["buffers_shared"] and raw_output.dtype == x.dtype,
+        )
```
Set "buffers_shared": share_prefill_buffers and layout sharing is active in make_state, so both the allocating layer and every reusing layer copy out.

Adversarial review fixes — B1, B2, C1, C2, C3
All findings addressed. Verified with pytest tests/quantization/test_exl3_prefill_plan.py --noconftest -v → 25 passed (20 existing + 5 new). CPU-only macOS; no CUDA/b12x/exllamav3 required.
B1 (BLOCKER) — guaranteed KeyError on mixed-bitrate forward
Root cause: _prepare_mixed_rank_sliced_weights only wrote {tiers, tier_ids, tier_bits, global_to_combined, descriptor_map, rotations, tile_config} — the four keys broadcast_suh, broadcast_svh, prefill_tiers, prefill_tile_config had no producer, so every mixed-bitrate layer raised KeyError.
Fix: Ported the producer logic from lilab/feat/gg-r20-exl3-consolidated-20260802:
Added _mixed_trellis_prefill_tile_config static method (separate from decode tile config for future divergence; currently returns the same geometry).
Added _select_rotation_rows static method to handle broadcast rotations (shape[0]==1) without crashing on index_select.
Compute broadcast_suh/broadcast_svh from the rotation backing shapes; added gate/up SUH consistency check.
Prepare prefill_tiers (aliased to decode tiers when tile configs match, to avoid doubling memory).
All four keys now populated in the exl3_mixed_trellis dict.
New tests: test_mixed_prepare_populates_required_keys drives _prepare_mixed_rank_sliced_weights directly (not hand-writing the dict) and asserts all four keys exist with correct values. test_mixed_prepare_broadcast_rotations verifies broadcast rotation slabs set the flags to True.
B2 (BLOCKER) — uniform prefill chunking corrupts output
Root cause: The uniform prefill path appended run() output without cloning, binding the same prefill_scratch arena every iteration. If run() returns a view, chunk i is overwritten by chunk i+1 and torch.cat yields N copies of the last chunk.
Fix: Added .clone() after each run() call (matching the existing mixed path).
Fake API change: _FakeFusedMoeApi.run() now writes into one persistent output arena and returns a view (mirroring the real B12X backend contract).
New test: test_uniform_prefill_chunks_clone_persistent_output — parametrized for equal-sized chunks (256/128), short final chunk (200/128), and single chunk (100/128). Verified both directions: without the clone, the two multi-chunk cases FAIL (first 128 rows overwritten with last chunk data); with the clone, all three PASS.
C1 — VLLM_EXL3_PREFILL_CAPACITY saves no memory on uniform path
Fix: Changed _plan_with_scratch(max_batched_tokens, ...) to _plan_with_scratch(prefill_capacity, ...) so the arena is actually bounded by VLLM_EXL3_PREFILL_CAPACITY, matching the mixed path.
C2 — misleading copy= guard
Fix: Changed copy=state["buffers_reused"] and raw_output.dtype == x.dtype to copy=raw_output.dtype == x.dtype. The aliasing hazard (buffers.output persistent across forward passes) exists regardless of buffers_reused. Updated the comment to explain the persistence-across-passes rationale.
C3 — undocumented process-lifetime global
Fix: Expanded the comment at _MIXED_TRELLIS_PREFILL_BUFFERS to document: entries persist for the worker process lifetime (never evicted outside tests), total memory grows with distinct (scope, device, layout) combinations, and reuse is safe only because layers execute strictly sequentially and stream-ordered within a single forward.
Nothing deliberately left unfixed
All six findings (B1, B2, C1, C2, C3, and the B2 test contract) are fully addressed.
