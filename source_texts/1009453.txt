Summary
Replaces the DirectTransferGenerator and the per-request transfer index with a new regular transfer implementation. The transfers between stops are found once per profile when the graph is built, stored as path templates, and turned into Raptor transfers for the preferences of each request from the closest profile. Walk, wheelchair, bicycle and car are supported as profile types.
Issue
Closes #7998, part of #8061.
Motivation. transferRequests is a List<RouteRequest>, and every entry means one full street search per stop. Entries are only deduplicated when they find the identical edge path, so adding one wheelchair entry to Norway grew the stored transfers by 62.8% and the build time by 18%. At request time every transfer in the mode bag was re-costed, whether the request needed it or not. The config also exposed dozens of RouteRequest fields that have no meaning for transfers.
How it works.
The build config gets a transfers block, grouped by profile type (walk, wheelchair, bicycle, car). Every profile has a required id, optional user preferences (speed, reluctance, safety factor, bicycle walking and optimize triangle) and a routing request the street search is based on. Without the block a single default walk profile is used. See doc/user/TransferConfiguration.md.
Each profile still runs its own discovery search, but a profile can have a parent, also of another type (e.g. a wheelchair profile with a walk parent). Paths that are the same once re-costed with the child's preferences are stored once, within the resueLimit (a CostLinearFunction, e.g. 10s + 1%). This is what saves the stored paths; the search cost is not reduced.
The max duration is set per type, and depends on which stops the mode can use: all stops for walk and wheelchair, stops that allow bicycles for bicycle, stops that allow cars for car. Bicycle can also have longer limits between stops that allow all modes or cars. The street search from a stop is bounded by the longest limit that applies to it, and there is no search from a stop that cannot be used by the mode. Paths that are too long for the two stops they connect are dropped.
At request time the snapshot of the repository finds the closest profile for the request's preferences and re-costs its paths. The result is kept in a cache sized by cacheMaxSize. The keys of the profiles and of the warmup entries are never evicted and not counted against the max size, so a request that matches a configured profile never pays for the first computation. Warmup entries are also created when the server starts.
User preferences are rounded (Speed, Reluctance, NormalizedRatio) so values that are close are the same cache key. A normalized distance is used to find the closest profile.
The repository is split in a build repository, written when the graph is built, and a transactional one that publishes a new snapshot on commit, so real-time updates can change the transfers. A report of the cache keys, with hits per key, is added to the ReportApi sandbox.
Design decisions.
raptor now asks for a RaptorDataProvider with a separate RaptorTransferDataProvider, so the transfers can be supplied by another module than the transit data. The behavior of Raptor is the same.
The new transit/transfer module does not depend on the application. The routing request is a type parameter, and the street search is a SPI (TransferPathProvider) implemented in the application.
Deduplication works across types, but inheritance does not: the routing request and the user preferences are only inherited from a parent of the same type, since the preferences of another type have different default values and fields. A parent of another type is only used to deduplicate street paths.
Stops of a station that does not allow transfers are neither source nor target of a transfer (this also fixes the old behavior where they were only pruned by the pattern pruning).
NOTE! This is a breaking config change. transferRequests, maxTransferDuration and
transferCacheRequests are no longer read for the regular transfers, and the old per-request
transfer cache and the OnDemandRaptorTransfer feature are removed. The flex and via settings
move to transfers.flex.requests, transfers.flex.maxDuration and transfers.via.maxDuration.
The old keys are reported as unknown parameters, so an old config fails loudly instead of
silently changing behavior.
NOTE! The transfer analyzer uses a fixed 30 minute search radius until it has a config of its
own. Rebuilding station transfers when a station changes is not implemented (TODO in the code).
Unit tests
✅ Unit tests are added at the lowest level: the transfer store, the profile ordering and inheritance, the max duration validation, the cache (eviction, retained keys, carry-forward to the next snapshot, metrics), the repository lifecycle, the value types and the config parsing. The config documentation is generated and verified by the doc tests.
Performance
✅ The goal for this PR is to have at least the same performance as the old code. There are several optimizations we can do, but we need to refactor the regular transfers first. Routing is on par with dev-2.x, the graph build is 3–6% slower on Norway and Skanetrafiken, and the transfers use 10–20% more memory. The transfer lookup is a small part of the Raptor search (about 4–5% of the Raptor time by the "Minute Transfers" timer of SpeedTest), so the faster RaptorTransfers cannot show up much in SpeedTest. The main thing for performance, with parts still pending, is to compress the Routing Regular Transfers used by Raptor. This allows us to cache more of them, and get better memory spatial locality. Cache miss. SpeedTest does not measure a cache miss: in dev-2.x the transfers for the request preferences are created at startup, and in this PR by the JIT warm-up requests that run before the timer starts. The time to create the transfers for one set of preferences, logged when the server starts, is a good estimate of the cost of one miss. The new code is on par with the sequential old code. In dev-2.x only the creation at server start is parallel (a miss in a request is parallel only with the ParallelRouting feature), the new code creates the transfers on one thread in both cases. So the server start is a little slower, and a miss costs about the same as before. A request with preferences that match a profile or a warmup entry never pays this, so configure a warmup entry for the preferences that clients use.

The old index is a copy of the structure in the benchmark and it is read through its concrete type, so the real index is not faster than this. The lookup is about 4–5% of the Raptor time, so the end to end gain is estimated to be about 1–3% (not measured), which is lost in the noise of SpeedTest.
A packed int[] layout was about 3.5–4x faster per lookup in an earlier prototype and about 20–25% smaller Object(toStop, duration, c1, pathRef) → int[] {toStop, duration, c1}. It is not part of this PR, it needs a small change in Raptor first, but it is a trivial optimization.

The regular transfers between stops are generated at graph build with the new module, for
each configured profile, and stored in the serialized graph. A routing request is matched to
the profile with the closest user preferences, and the Raptor transfers are created from the
paths of the profile and cached, with warmup entries created at startup.

- Configure the transfers per profile type (walk, wheelchair, bicycle, car) in the
  transfers section of build-config.json: profiles with user preferences and a reuse limit,
