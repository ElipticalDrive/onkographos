NonUniformResourceIndex(i) was declared [require(cpp_cuda_glsl_hlsl_spirv, nonuniformqualifier)], so bindless code that marks its indices failed on Metal and WGSL:
```
Texture2D tex[8]; SamplerState s; RWStructuredBuffer<float4> o; StructuredBuffer<uint> idx;
[numthreads(64,1,1)]
void main(uint3 t : SV_DispatchThreadID)
{
    o[t.x] = tex[NonUniformResourceIndex(idx[t.x])].SampleLevel(s, float2(0.5), 0);
}
```
```
slangc repro.slang -target metal -entry main -stage compute   -> error[E36107] at NonUniformResourceIndex
slangc repro.slang -target wgsl  -entry main -stage compute   -> error[E36107] at NonUniformResourceIndex
```
Without the call, the same code compiles, so the only way to keep one source for all targets was a #if around every index.
Why the identity is the right lowering on these targets
Metal has no non-uniform qualifier. A resource array is assumed to be indexed non-uniformly unless the index is declared metal::uniform<T> (MSL spec 4.1, section 2.14.1 "The Need for a Uniform Type"), so the marked index needs nothing.
WGSL has no qualifier either. The WebGPU proposals for binding arrays allow non-uniform indexing without an annotation: sized binding arrays proposes it for every binding type and notes that implementations can derive the annotations from the uniformity analysis. Rejecting the call would only force portable code to #if it out. A diagnostic would not help either: WGSL gives the user no annotation to write in its place.
Change
The declaration gains [require(metal)] and [require(wgsl)], with a doc comment that explains the two targets. The C-like emitters already lower kIROp_NonUniformResourceIndex to its operand, so the emitted code is the index itself. This is also what the header of slang-ir-float-non-uniform-resource-index.cpp already describes for Metal and WGSL ("the wrapper is dropped at emit time"); only the declaration's capability requirement kept those targets from getting there.
This does not touch how resource arrays themselves are emitted for WGSL. array<texture_2d<f32>, N> is still rejected by Tint; that is #9528.
Related: #12161 (non-uniform DescriptorHandle on non-SPIR-V targets).
Test
tests/cross-compile/non-uniform-resource-index-metal-wgsl.slang compiles the repro for Metal, for WGSL, and for WGSL with an unbounded array. It checks that the sample uses the index directly and that no NonUniformResourceIndex call is left. Before the change, all three runs failed with E36107.
Verification
slang-test -api none: tests/metal, tests/wgsl, tests/cross-compile, tests/spirv, tests/hlsl, tests/hlsl-intrinsic, tests/bugs, tests/compute, tests/language-feature and tests/gpu-feature all pass.
With and without the call, the WGSL output is byte-identical. The Metal output differs in one respect: with the call, the entry-point resources are read through the kernelContext struct rather than through the entry-point parameters directly. The two are equivalent, and the indexing expression is the same. The difference comes from the IR side-effect classification, not from anything Metal-specific: IRInst::mightHaveSideEffects does not list kIROp_NonUniformResourceIndex as side-effect free, so the loads from kernelContext placed after the wrapper are not forwarded to the parameters. Marking the op side-effect free removes the difference, but it also changes the HLSL and CUDA output of existing tests (tests/compute/nonuniformres-nested-rwstructuredbuf.slang), so I left it for a separate change.
Metal: verified through the emitted MSL only (no Mac here).

Fixes shader-slang#9528

WGSL cannot use a texture or a sampler as an `array` element. An array
of them is a `binding_array`. Slang emitted `array<...>` for every array
type, so a plain `Texture2D textures[8]` gave WGSL that every WGSL
compiler rejects:

```slang
Texture2D<float4> textures[8];
Texture2D<float4> unboundedTextures[];
SamplerState samplers[4];
```

```wgsl
// before
@binding(0) @group(0) var textures_0 : array<texture_2d<f32>, i32(8)>;
@binding(1) @group(0) var unboundedTextures_0 : array<texture_2d<f32>>;
@binding(2) @group(0) var samplers_0 : array<sampler, i32(4)>;
```
Tint: `error: texture_2d<f32> cannot be used as an element type of an
array`; naga rejects it as well.

```wgsl
// after
@binding(0) @group(0) var textures_0 : binding_array<texture_2d<f32>, i32(8)>;
@binding(1) @group(0) var unboundedTextures_0 : binding_array<texture_2d<f32>>;
@binding(2) @group(0) var samplers_0 : binding_array<sampler, i32(4)>;
```

### Change
`WGSLSourceEmitter::emitSimpleTypeImpl` prints `binding_array<` instead
of `array<` for a sized or unsized array whose element type is a texture
(`IRTextureTypeBase`) or a sampler (`IRSamplerStateTypeBase`). Indexing
is unchanged (`textures_0[i]`), and so are layout and reflection. The
global arrays that the default `DescriptorHandle` lookup declares on
WGSL become `binding_array` too.

### Who accepts what
| | Tint (Dawn c943ea32) | naga 25 (wgpu) |
|---|---|---|
| sized array of sampled textures | yes (`sized_binding_array` language
feature; unsafe APIs in Chrome for now) | yes (`TEXTURE_BINDING_ARRAY`)
|
| unsized array of textures | no ("requires 2 template arguments") | yes
|
| array of samplers | no ("element type must be a sampled texture type")
| yes |
| `array<texture_2d<f32>, N>` (before) | no | no |

So the output is valid wherever the implementation supports the array at
all. For Dawn's unbounded case, see the resource-table PR (shader-slang#13641).

`NonUniformResourceIndex` on these arrays is handled by shader-slang#13694 (identity
on WGSL). The two branches merge cleanly. With both,
`textures[NonUniformResourceIndex(i)]` should compile to valid WGSL; I
have not built them together.

### Tests
`tests/wgsl/binding-array.slang` (FileCheck) covers:
- a sized texture array;
- an unsized texture array;
- a sampler array;
- the default `DescriptorHandle` heap.

The Tint bundled with slang-test (`slang-tint-0`) does not know
`binding_array`, so the test can't validate through `wgsl-spirv-asm`. I
checked the outputs by hand with Tint c943ea32 and naga 25:
- Tint accepts the sized texture array and translates it to SPIR-V and
HLSL, and rejects the other forms as the table above says.
- naga accepts the first three.

No runtime test: as far as I can see, slang-rhi's WebGPU backend
(`wgpu-shader-object-layout.cpp`) creates one bind-group-layout entry
per binding, with no array size (Dawn's
`BindGroupLayoutEntryArraySize`), so a `-wgpu` compute test cannot bind
the array yet.

with and without this change: `tests/functional/*`,
`tests/dispatcher/smoke`, and one C++-target diagnostic. My build has no
slang-llvm or CUDA. Three nvrtc/OptiX tests and one diagnostics test
failed once on a PCH-file race and passed on rerun.
- I compiled every `-target wgsl` SIMPLE test in the tree with master
and with this branch. Only `desc-heap-direct-index.slang` changes (its
heap declarations become `binding_array`), and it still passes.
- `slang-test -api wgpu -api-only tests/wgsl
tests/language-feature/descriptor-handle` (WebGPU runtime tests): 12/12

### Notes
- The default `DescriptorHandle` path on WGSL is still not valid WebGPU
after this change. Every heap is declared at `@binding(0)` of the
bindless group, and naga rejects the texture and sampler heaps as
conflicting bindings. Fixing that needs a decision about how descriptor
handles should work on WGSL (see the open questions in the
resource-table PR), so it is not part of this PR.
- `binding_array` of storage textures, and of buffers (`var<storage> a :
binding_array<...>`) for wgpu, are not covered: Slang declares those
differently, and arrays of buffers already fail with E56105
(`array-of-resource-type-not-supported-in-wgsl`).

This continues shader-slang#13694 and includes its commits. On top of them it
declares the capability with one new alias, removes the long comments
the earlier commits added to `hlsl.meta.slang` and
`slang-ir-float-non-uniform-resource-index.cpp`, and keeps the
documentation corrections.

## Motivation

Before shader-slang#13694, `NonUniformResourceIndex` was declared for CPU, CUDA,
GLSL, HLSL and SPIR-V only. A shared HLSL-style shader like this was
rejected on Metal and WGSL:

```slang
Texture2D tex[4];
SamplerState samp;
RWStructuredBuffer<float4> outBuf;

[shader("compute")]
[numthreads(4, 1, 1)]
void main(uint3 tid : SV_DispatchThreadID)
{
    outBuf[tid.x] = tex[NonUniformResourceIndex(tid.x)].SampleLevel(samp, float2(0.5, 0.5), 0);
}
```

`slangc -target metal` reported `E36107: entrypoint 'main' uses features
that are not available`, pointing at `NonUniformResourceIndex`. Some of
our documentation also assumed this was intended, saying that Metal and
WGSL cannot take the call. Neither target needs a non-uniform
annotation, so the rejection was only a gap in the capability
declaration.

## Proposed solution

Declare the intrinsic for every target that has no non-uniform
annotation, and let the emitter write just the index there. The
declaration becomes two requirements, one for the targets that carry the
annotation and one for the targets that do not:

```slang
[require(glsl_hlsl_spirv, nonuniformqualifier)]
[require(cpp_cuda_metal_wgsl)]
T NonUniformResourceIndex(T index);
```

This is the principled place for the change because the shape of the IR
is already correct: the `floatNonUniformResourceIndex` pass in textual
mode leaves a `kIROp_NonUniformResourceIndex` wrapper around the index,
and the C-like emitter already knows how to print it as its operand.
Only the capability declaration was wrong.

## Change summary

| Area | Change |
| --- | --- |
| `source/slang/hlsl.meta.slang` | `NonUniformResourceIndex` is
`[require(glsl_hlsl_spirv, nonuniformqualifier)]` plus

## Concepts and vocabulary

- **Compound capability alias**: a name for a set of targets in
`slang-capabilities.capdef`, such as `cpp_cuda_metal_wgsl`. A
`[require(...)]` attribute accepts a target when it is in the set.
- **Several `[require]` attributes on one declaration** are
alternatives: a target is accepted if any one of them accepts it. Inside
one attribute, a comma combines the entries with AND, so
`[require(glsl_hlsl_spirv, nonuniformqualifier)]` means "one of those
three targets, and also `nonuniformqualifier`".
- **`nonuniformqualifier`**: an alias for `sm_5_1`. It is only needed
for targets that really emit an annotation.
- **Textual mode** of `floatNonUniformResourceIndex`: the variant of the
pass that runs for every non-SPIR-V target. It moves the wrapper onto
the index expression and adds no decoration.

## Process report

**Why Metal and WGSL were rejected.** The old declaration was
`[require(cpp_cuda_glsl_hlsl_spirv, nonuniformqualifier)]`. Capability
checking found no match for `metal` or `wgsl`, so the entry point got
`E36107`. The code generation stage was never reached.

**Why dropping the call is correct there.** For the example above,
`floatNonUniformResourceIndex` (`slang-emit.cpp:2457`, called for every
non-SPIR-V target) leaves `NonUniformResourceIndex(tid.x)` wrapped
around the index. The wrapper has no target-specific emitter on CPU,
CUDA, Metal and WGSL. `CLikeSourceEmitter::emitInstExpr`
(`slang-emit-c-like.cpp:2454`) first asks the target emitter, then falls
back to `defaultEmitInstExpr`, whose `kIROp_NonUniformResourceIndex`
case (`slang-emit-c-like.cpp:2869`) emits only `inst->getOperand(0)`.
`CUDASourceEmitter::tryEmitInstExprImpl` and
`CPPSourceEmitter::tryEmitInstExprImpl` both have no case for this op.
The op is also `FoldPolicy::Always` (`slang-emit-c-like.cpp:1556`), so
it never gets its own temporary. The output for the example is
therefore:

- Metal: the index expression is used directly to index the
`array<texture2d<float, access::sample>, 4>`.
- WGSL: `textureSampleLevel((tex_0[i_0]), ...)` on a
`binding_array<texture_2d<f32>, 4>`.
- CUDA: `tex2DLod<float4>(globalParams_0->tex_0[i_0], ...)`, where the
texture is a `CUtexObject` handle.

HLSL and GLSL keep their own cases in `slang-emit-hlsl.cpp:1550` and
`slang-emit-glsl.cpp:2795` and still print the wrapper.

**Why one alias with CPU and CUDA.** CPU and CUDA already accepted the
call, through the first `[require]`. CUDA has no non-uniform annotation:
a `cudaTextureObject_t` is an opaque 64-bit handle and a thread can load
any element of an array of them. Putting CPU and CUDA in the same alias
as Metal and WGSL expresses the single rule "these targets have no
annotation, so the call is the identity", and the first attribute now
lists only targets that emit an annotation. One side effect: CUDA used
to get `nonuniformqualifier` (`sm_5_1`), whose CUDA entry requires
compute capability 6.0. It is now accepted without that condition. This
is harmless, since nothing is emitted for it.

**Input-shape check.** This change adds no guard or special case for an
IR shape. The wrapper-around-index form comes from
`floatNonUniformResourceIndex`, is the intended canonical form, and the
existing emitter already handles it. The producer needs no change. The
only thing that was wrong was a capability declaration.

**Not covered.** `llvm` is still rejected (`E36107` pointing at
`NonUniformResourceIndex`), and its emitter has no handling for this op.
The `c` target cannot take part either, because it fails earlier on
buffer indexing. This PR leaves both as they are.

**Documentation.** `docs/generated/tests/_meta/prompts/_common.md` said
the core module excludes Metal from `NonUniformResourceIndex`'s
capability set. That assumption is no longer true, so the sentence is
rewritten as a generic example and the Metal-specific bullet is removed.

**Deleted tests.** The two generated negative tests expect `E36107` for
Metal and WGSL, which this PR removes on purpose, so they can never pass
again. shader-slang#13694 listed them in `expected-failures.txt`, but that file is
for tests that should pass and do not, such as compiler bugs or bundles
waiting for a fix. The suite's own remediation notes
(`prompts/_remediate.md`) say to delete a test whose claim is wrong, so
this PR deletes the two tests, removes their rows from the Functional
coverage tables in the Metal and WGSL bundle READMEs, and removes the
expected-failures entries. `regenerate.py lint` reports the same result
as before the change (0 errors, 81 warnings).

**Not changed here.** The design pages
`docs/generated/design/target-pipelines/metal.md` (pass table row 7) and
`wgsl.md` (`floatNonUniformResourceIndex`) still describe the rejection.
They are generated and say not to edit them by hand, so they need to be
regenerated with the documentation workflow. Until then, regenerating
the Metal or WGSL test bundle from those pages could recreate the
negative tests.
