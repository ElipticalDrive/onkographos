Performance Improvement
Changelog entry (a user-readable short description of the changes that goes into CHANGELOG.md):
Speed up mortonEncode and mortonDecode: each input column is resolved once per call instead of reading every value through a virtual accessor inside the row loop, and the ratios of a constant range mask are read once per call instead of once per row per output field. Both the pdep/pext and the lookup-table code paths benefit. Results are unchanged.
Description
mortonEncode and mortonDecode read every input value through the virtual IColumn::getUInt inside their per-row loops, once per dimension, so a call pays one un-inlinable indirect call per row per argument for a body that is a couple of pdep instructions on x86-64-v3 and a few table lookups elsewhere. The range-mask variants also re-read row 0 of a constant tuple, once per row per output field. Both __BMI2__ arms pay it.
The type of every value argument is fixed for the whole invocation: getReturnTypeImpl admits only UInt8, UInt16, UInt32 and UInt64. UIntColumnSpan resolves each column's storage once at the top of executeImpl, and the row loops index through it; anything that is not a plain fixed-width vector keeps getUInt. The constant mask ratios are hoisted per invocation; the non-const-mask path keeps its per-row read.
Results do not change: 55 differential queries covering all four widths, 1 to 8 dimensions, const and non-const masks, mixed widths, Nullable, LowCardinality, sparse, Dynamic, Variant, 0 and 1 rows and four max_block_size values are byte-identical, as are 15 error paths and the ten existing space-filling-curve tests, which pass 500 of 500 at --test-runs 50.
On a RelWithDebInfo build (ENABLE_THINLTO=0, clang++-22, -march=x86-64-v3, one Xeon 6975P-C core, max_threads=1) the two- and three-argument shapes gain most, five- and eight-argument shapes little, and a hilbertEncode control is flat. That configuration is not the shipped one, so the number worth quoting should come from the added tests/performance/space_filling_curve.xml under CI.
Reported, diagnosed and originally patched by @ snelheidai, who asked me to open the PR (#117652 (comment)). His patch used a typeid_cast chain; this version uses the IColumn fixed-and-contiguous interface, so the header gains no include.
hilbertEncode and hilbertDecode carry the same per-row read and are out of scope here; UIntColumnSpan is in the shared header so they can follow.

`mortonEncode`'s `getReturnTypeImpl` caps neither the range-mask tuple size
nor the argument count, so a nine-element mask reaches `executeImpl` and is
rejected only at the bottom of it, after the per-invocation mask-ratio fill
has run. The fill is therefore bounded by the destination array's size rather
than by `nd`, and without that bound libc++ hardening reports an
out-of-bounds write on a query a user can send. Hardening is on in every
shipped configuration: `cmake/cxx.cmake` selects `_LIBCPP_HARDENING_MODE_FAST`
for release builds and `_EXTENSIVE` for debug ones, and
`_LIBCPP_ASSERT_VALID_ELEMENT_ACCESS` is live in both.

No test pinned that. Removing the bound left all ten in-tree
space-filling-curve tests passing, which is enough for a later change to drop
it as redundant. With these two queries appended, the same removal aborts
`02457_morton_coding_with_mask` and nothing else, so the test now carries the
bound on its own.

The value argument has to be non-constant. An all-constant call is folded by
`useDefaultImplementationForConstants`, which materialises argument 0, clears
`RangeMask::is_const` and skips the fill entirely, so that form looks like a
pass while testing nothing.

The `mortonDecode` line records the asymmetry: decode does cap the tuple size
in `getReturnTypeImpl`, so its identical bound is defensive rather than
load-bearing.

#
Question
Answer
a
Deterministic repro?
This is a performance change, so the repro is the measurement: 9 queries run interleaved on Build-ID-asserted RelWithDebInfo binaries, medians over 5 rounds, with a master-vs-master third arm as the noise floor (0.935 to 1.014). sum(mortonDecode((1, 2), number).1) over numbers(120000000) at max_threads=1 goes 0.554 s to 0.231 s and reproduces every round, far outside that band. The same measurement was then repeated on a build whose two morton translation units were recompiled with -mno-bmi2, so that the lookup-table kernels run: own noise floor 0.974 to 1.010, and all eight morton queries outside it.
b
Root cause explained?
IColumn::getUInt is virtual and is called once per row per argument, but the concrete type of every value argument is fixed for the whole invocation: getReturnTypeImpl admits only UInt8, UInt16, UInt32 and UInt64. The dispatch re-answers, per value, a question settled before the loop started, and cannot be inlined. For the range-mask variants the re-read value is one constant tuple element, since RangeMask::read ignores the row index when is_const.
c
Fix matches root cause?
Yes. The dispatch moves to the top of executeImpl, where the type is known and stable. Nothing is widened, no bound relaxed, no check removed, no setting or threshold introduced, and getUInt is retained as the accessor for any column that is not a plain fixed-width vector.
d
Test intent preserved / new tests added?
No existing test is weakened, relaxed or deleted; all ten space-filling-curve tests pass, and 500 of 500 at --test-runs 50 with randomization on. What to add was decided by crossing mutants against the tests that ship, not by taste. Seven mutants were built. Reading UInt16 as UInt32, UInt8 as UInt16, UInt32 as UInt64, hoisting the decode mask wrongly, and dropping the encode is_const guard each redden between 1 and 5 of the ten existing tests, so no new test is warranted for those. Removing the bound on the mask-ratio fill reddened nothing, so 02457_morton_coding_with_mask gains the oversized-mask-tuple case, after which that mutant reddens exactly that file. tests/performance/space_filling_curve.xml is added, which is the coverage this path genuinely lacked.
e
Both directions demonstrated?
Yes, on both dispatch arms. Performance: master versus fixed on the same binaries for the pdep/pext arm (hilbertEncode control 0.998) and again for the lookup-table arm (control 0.989), each with its own noise arm. Correctness: 55 differential queries and 15 error paths byte-identical, plus the six mutants above shown to redden.
f
Fix is general across code paths?
Both morton translation units, all four read sites in decode (nd == 1 with and without a mask, the lookup-table arm, the BMI2 arm), all eight ENCODE arities, and both mask hoists. Both __BMI2__ arms were compiled, with a deliberately broken control to prove the check is live, and both were then timed. The two arms were shown to be genuinely different code three ways: pdep/pext counts in the objects go to zero, the linked binaries have distinct Build IDs, and removing pext makes master's own decode queries 2.2 to 2.9 times slower while the hilbertEncode control moves 0.8%. hilbertEncode and hilbertDecode carry the same per-row read and are deliberately out of scope so this PR has one cause; UIntColumnSpan sits in the shared header so they can follow.
g
Fix generalizes across inputs (params/datatypes/wrappers)?
All four native widths and mixed widths; 1 to 8 dimensions; const, non-const and mixed-const masks; Nullable with interleaved NULLs, LowCardinality, sparse serialization, Bool, Dynamic, Variant; UInt64 max; 0 and 1 rows; max_block_size 7, 11, 13 and 65409; and a nine-element mask tuple. Every one byte-identical to master. ColumnConst is the one class that forwards all three storage predicates to a single-row nested column, so it is excluded by a runtime term rather than a chassert, which compiles away in release.
h
Backward compatible? (maintainer-approved exception only)
N/A: no setting, default, threshold, serialization or format change, and no error code or message change. SettingsChangesHistory.cpp is not involved. Error paths were verified identical before and after.
i
Invariants and contracts preserved?
Span invariant: at executeImpl every value argument is a non-const, fixed-and-contiguous column whose getDataType() is one of the four native widths, so getRawData() is row-indexable at sizeOfValueIfFixed() bytes; anything else takes getUInt. Mask invariant: RangeMask::read ignores the row when is_const, so the hoist is value-preserving, and the non-const path is untouched. The fill loop is bounded because a nine-element mask tuple does reach executeImpl and is only rejected below the fill; without the bound, libc++ hardening reports the out-of-bounds write. Nothing is carried across blocks: spans and the ratio array are rebuilt per executeImpl call, and the differential suite varies max_block_size to show it.
