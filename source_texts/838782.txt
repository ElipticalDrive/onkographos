This might be 3 or 2 different requests.
x) allowing multiple transfer functions. I.e. assign one data vector to red, one to green, one to blue, and most important have a different data vector to decide opacity.
x) using automatic 'histogram equalization' to create colormaps that fit to the data values shown.
x) being able to interactively adapt color map. (Compare Paraviews version). Essentially you can click and drag on colors in the colormap and move them. E.g. if you have a rainbow colormap you can click on green and drag it towards blue to either make regions of certain color bigger or smaller.

Investigation findings (2026-06-12)
Three distinct colormap enhancement requests:
1. Multiple transfer functions / RGBA channel assignment
Currently CreateStandardColorMap maps a single scalar field to a single RGBA colormap. Supporting per-channel data (R from field1, G from field2, opacity from field3) would require changes to the ViewScene rendering pipeline to accept multiple field inputs mapped to color channels. This is a significant renderer change. The comment notes ShowFieldGlyphs partially covers this case.
2. Histogram equalization
Auto-stretch the colormap to match the data distribution. The data min/max is already available; a histogram equalization step would compute percentile-based breakpoints and remap the colormap transfer function accordingly. This is purely algorithmic — a new option in CreateStandardColorMap or a new RescaleColorMap module. Effort: small-medium.
3. Interactive colormap editing (Paraview-style drag)
This requires a custom QWidget that renders the colormap as a gradient bar with draggable control points. The current CreateStandardColorMapDialog has a static preview. A draggable transfer function editor is a non-trivial Qt widget but is a self-contained UI component. Effort: medium.
Priority recommendation: Item 2 (histogram equalization) is the most useful and self-contained. Items 1 and 3 are larger efforts better tracked separately.

Update (2026-11-04)
Better title: Colormap features: separate data per channel and opacity, histogram equalization, draggable color stops
Better description
Three independent requests, none of them done as asked. This comes from reading the code; nothing was run.
Per-channel data and separate opacity. ShowField takes one field and one colormap (src/Modules/Visualization/ShowField.h:107), and a colormap's alpha comes from the same data value as its color (src/Core/Datatypes/ColorMap.cc:234). ShowFieldGlyphs has primary, secondary and tertiary data and colormap ports (src/Modules/Visualization/ShowFieldGlyphs.h:105), which is likely what the 2019 "kind of possible" comment meant. Its transparency data input is commented out (src/Modules/Visualization/ShowFieldGlyphs.cc:264). I did not trace how far those ports go toward RGBA assignment.
Histogram equalization. No code for it in the visualization modules or the ColorMap type. RescaleColorMap's autoscale adjusts the range (src/Modules/Visualization/RescaleColorMap.cc:98) and does not reshape the color distribution.
Dragging colors. Partly covered. CreateStandardColorMap has a shift control (src/Interface/Modules/Visualization/CreateStandardColorMapDialog.cc:59), invert, and a two-color Custom map (src/Interface/Modules/Visualization/CreateStandardColorMapDialog.cc:67). Opacity points can be dragged (src/Interface/Modules/Visualization/CreateStandardColorMapDialog.cc:287), but colors cannot. So the June 2026 comment's "static preview" is wrong: it is an editor, just for alpha only.
Nearby open issues: #2420 (import, export and editing), #2421 (scaling), #2357 (UI refactor), and ctkTransferFunctionWidget on the #2126 list, which is not in the tree.
Concrete steps
Split this into three issues, since they share no code.
Histogram equalization: add an option that builds a data-derived lookup applied in ColorMap::getColorMapVal (src/Core/Datatypes/ColorMap.cc:240), exposed through RescaleColorMap, with tests in src/Modules/Visualization/Tests/RescaleColorMapTests.cc.
Draggable colors: extend ColormapPreview with color stops, stored in module state alongside AlphaUserPointsVector.
Per-channel: write down what is wanted first (glyphs only or all of ShowField). Opacity from a second field means carrying that value to the renderer per vertex.
Status: still valid - equalization and color dragging are absent, and separate opacity data is not available in ShowField.
