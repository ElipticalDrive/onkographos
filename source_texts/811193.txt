Opus recheck — render(metal): light-volume samplers interpolate to match GL parity
Verdict: approve.
Final pass on the rebased head 6e7fc493c. Sonnet asked for a recheck because the change moved into the shared c_lighting_to_trixel_body.metal during the rebase and hadn't had a final pass since. I checked the GPU-side items Sonnet didn't cover and confirm the change is correct:
The format can be linearly filtered on every Metal device. The value volume is TextureFormat::RGBA8 (component_canvas_light_volume.hpp), which maps to MTL::PixelFormatRGBA8Unorm (metal_texture.cpp:15). Normalized 8-bit formats support linear filtering on every Apple GPU family. The supports32BitFloatFiltering caveat applies only to float32 textures, and this texture isn't one. Both kernels already declare the argument as texture3d<float, access::sample>, so the access qualifier needs no change.
Metal and GL now compute the same result. Both GLSL twins (c_lighting_to_trixel_body.glsl:425-428, c_light_overflow_faces.glsl:174-176) use the same (localPos + halfExtent + 0.5) / size coordinate through texture(sampler3D) with the CPU-declared LINEAR filter. The Metal sites use that same formula and now the same filter. The rgb * a product is taken after interpolation on both backends.
Every Metal consumer is covered. A grep of engine/render/src/shaders/metal finds exactly two lightVolume.sample sites, and this PR flips both. Master's split means the one body edit covers the c_lighting_to_trixel and _shapes wrappers.
The spot-light ID lookup stays unfiltered. lightVolumeId is texture3d<float, access::read> with an integer-cell .read(uint3(idCell)), so linear filtering can't reach it. The ID cell is computed as floor(localPos + halfExtent + 0.5), the same texel a nearest sample would pick, so spot attribution is unchanged.
No change to lifetimes, bindings, sync or hot-path cost. Only the constexpr sampler changed. Slot 5, the ping-pong swap and the dispatch geometry are untouched. The per-pixel cost goes from one nearest fetch to one trilinear fetch, which GL already pays.
The reference re-bless is legitimate. The 18 shape_debug and 5 lighting macOS references absorb two things: this change, and drift from master's earlier lighting PRs, which never re-blessed the macOS references. The worker's master-control run (master's .metal files against master's references gives the same 4/5 and 16/33 failure numbers) confirms that split. Re-blessing on the rebased head is the correct baseline. The two yaw45 shots that already fail on master stay untouched.
Stack: base is master, so this is a standalone review. Cross-host OpenGL validation is still gated by the existing fleet:needs-windows-smoke label.
No nits.

fleet_branch_match.py's link-line and closing-ref grammars split body/text
on "\n"; a CRLF-stored body (a PR body edited from a native-Windows host)
leaves a trailing \r on every line, which the strict end-anchored link-line
pattern then rejects. `fleet-pr-closes-lint` was firing UNDECLARED on a
correct standalone `Closes #N` line for exactly this reason (PR #3740).

Added `_normalize_newlines`, called once at each body/text entry point
(`strip_code`, `raw_closing_refs`, `body_would_close_refs`) rather than at
every downstream split site.
