Summary
Completes Phase 2 of the ARCore-fallback work started in #1857 (merged: HomographyTracker native planar tracker + BridgedHomographyTracker's gyro bridging). This PR takes it from "tracking math with nowhere to render" to "actually visible and switched on" for devices where ArUiState.isArCoreAvailable == false.
2a — camera intrinsics + projection matrix
CameraIntrinsicsEstimator (core:common): Camera2 LENS_INTRINSIC_CALIBRATION when available, else the focal-length/sensor-size pinhole fallback, rescaled to the actual tracked-frame resolution. Split into a pure computeIntrinsics (fully unit-tested, no mocking) and a thin CameraCharacteristics-reading wrapper, after an interesting CI failure — see the dedicated fix commit for what happened (a mockk/Android-stub-jar interaction with Size/SizeF-typed generic stubs, not a logic bug).
ProjectionMatrix (feature:ar): CameraIntrinsics → an OverlayRenderer-ready GL projection matrix. Derived from scratch in the class doc, closed-loop tested against an independent pinhole computation.
2b — CameraX ImageAnalysis wiring
CameraPreview.kt's shared non-AR-mode camera controller enables IMAGE_ANALYSIS (AR mode drives its own ARCore Session, unaffected).
HomographyTrackingAnalyzer: decodes YUV→RGBA via the existing native YuvConverter, rotates to display orientation the same way takePictureAsBitmap already does, rotates intrinsics via the existing CaptureRotation convention, feeds BridgedHomographyTracker.trackFrame, and emits HomographyTrackedFrame (pose + that same frame's projection matrix).
2c — GL rendering
HomographyOverlayRenderer: a GLSurfaceView.Renderer wrapping the existing OverlayRenderer (already fully decoupled from ARCore types), with cross-thread pose/texture updates via AtomicReference/@Volatile.
HomographyFallbackOverlay: self-contained composable — owns its own reference capture ("Capture Target" button), the tracker, the analyzer, and the GL surface — layered over CameraPreview with the same setZOrderMediaOverlay(true) + PixelFormat.TRANSLUCENT pattern MainScreen.kt already uses for AR mode's own GL surface.
2d — activation
Wired into MainScreen.kt's EditorMode.OVERLAY branch, gated on !arUiState.isArCoreAvailable. Zero behavior change for any other mode or any ARCore-capable device — additive code, with the one touched line (the manual 2D design-layer draw) guarded to skip only this exact combination so the design doesn't render twice.
Known simplification, documented in code: the captured reference photo's own full frame is treated as the tracked rectangle (not the artist's actual marked corners). Letting the artist mark the shape's real bounds — reusing TargetCreationFlow's UnwarpScreen, the way AR mode's own target capture does — is follow-up work, not a blocker to trying this end to end.
Test plan
All new/changed unit tests pass: CameraIntrinsicsEstimatorTest, ProjectionMatrixTest, HomographyTrackingAnalyzerTest, plus ARCore fallback: planar tracker + gyro bridging (Phase 1) #1857's RotationDeltaMathTest/HomographyArTrackerTest.
Native/Gradle build — could not be locally compile-verified in this environment (network-blocked Gradle plugin resolution); please confirm in CI.
On-device: an ARCore-unavailable (or force-disabled) device, Overlay mode, tap "Capture Target" on a printed/painted shape, confirm the design tracks it live and roughly matches its on-screen size/skew as the phone moves. This is the one thing that genuinely needs hardware — flagged throughout the phase (the gyro-bridge alignment sign in particular, per ARCore fallback: planar tracker + gyro bridging (Phase 1) #1857).

```
Continues the ARCore-fallback work (#1857): ARCore self-calibrates and
supplies fx/fy/cx/cy plus a ready-made GL projection matrix every frame;
CameraX supplies neither, so BridgedHomographyTracker's pose has had
nowhere to render through OverlayRenderer's draw(view, proj, anchor) path.
This adds both missing pieces, independently of any camera wiring:

- CameraIntrinsicsEstimator (core:common): reads Camera2's
  LENS_INTRINSIC_CALIBRATION when a device reports it, else falls back to
  the focal-length/sensor-size pinhole approximation (centered principal
  point) -- then rescales either to the actual frame resolution the caller
  will track at, since CameraCharacteristics describes the full sensor
  array, not necessarily what ImageAnalysis delivers.
- ProjectionMatrix (feature:ar): converts CameraIntrinsics into an
  OverlayRenderer-ready GL projection matrix. Derived from scratch in the
  class doc (not recited from memory) and closed-loop tested against an
  independently-computed pinhole projection, the same way CaptureRotation's
  own convention is pinned by CaptureRotationTest.

Both pieces are pure/mockable and fully unit-tested -- unlike
GyroOrientationBridge's IMU-alignment sign, nothing here needs on-device
verification.

Still no CameraX ImageAnalysis wiring, OverlayRenderer integration, or
EditorMode/ArUiState routing -- next in this phase.
```

Add gyro-only bridging for the ARCore-fallback tracker
…
8f48a56
```
Vision-only tracking (HomographyArTracker) drops out hard the moment a frame
fails to match — a hand or spray can blocking the lens, a fast pan. This
bridges that brief gap with the gyroscope instead of the accelerometer:

- GyroOrientationBridge: reads TYPE_GAME_ROTATION_VECTOR (Android's own
  gyro-only sensor fusion, not a hand-rolled integrator) and, given a
  reference orientation marked at the last confident vision lock, computes
  how the CAMERA (not just the device) has rotated since. Rotation only,
  deliberately never position/translation — bridging translation needs the
  accelerometer, which means double integration (drift grows with time^2,
  not linearly) plus gravity subtraction that's circular with orientation
  plus per-device bias calibration. None of that is worth it for a ~400ms
  bridge; gyro drift over that window is a fraction of a degree.
- RotationDeltaMath: the quaternion/rotation-matrix math behind it, split
  out pure and unit-tested (RotationDeltaMathTest) since it's the part most
  likely to have a subtle sign error.
- BridgedHomographyTracker: composes HomographyArTracker + the gyro bridge
  into the one call a live-tracking loop will actually want (trackFrame),
  decaying confidence across the bridge window.

Honestly flagged, not silently assumed: the fixed IMU-body-to-camera-optical
alignment's Z-axis has no flip (CDD-guaranteed for the rear camera vs a
device's default-orientation sensor frame) but the quarter-turn rotationDeg
sign — mirroring CaptureRotation's existing sensor-to-display convention —
has not been verified on physical hardware. Flagged in GyroOrientationBridge's
class doc with what to check.

Still Phase 1 territory: no CameraX/OverlayRenderer/EditorMode wiring yet.
```
