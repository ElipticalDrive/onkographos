Summary
This is the third PR in the grids design stack. It builds on #20, is independent of #21, and contains no code.
Warp covers reprojection and regridding between any two grids. Its struct lands after Select and Reduce (roadmap step 6). Its shape is fixed now, so that adding it changes neither the schema nor Select. It resolves the three Warp issues recorded in #20's discussion note.
What this proposes
The proposal is a new file, plans/warp.md.
Resampling is defined in ArrIR, not by GDAL. The methods are Nearest, Interpolate (with a kernel and a scaling choice), Mode and Conservative (planar or spherical area, with or without renormalising). Each has its own definition. Where implementations disagree, the choice is a field. For example, gdalwarp widens its kernel when downsampling, and xESMF doesn't. There's no Average: GDAL's average isn't assumed to equal Conservative.
Each variable has its own output. Warp lists the variables it warps, each with its own method, output type, rounding, out-of-range rule and nodata. A single set of options can't serve int16 and float32 variables together, or a land-cover class and a temperature. Variables not listed stay on the source grid.
Cell edges come from an explicit EdgeRule. Nearest, Mode and Conservative need edges, which grids with centre coordinates only lack. Requiring bounds would block the common swath case. Implying edges silently would break purity rule 4. So the plan states either FromBounds or MidpointsBetweenCentres.
The target geometry is a binding with a declared schema, like Open. Mesh and DGGS targets are defined by data, and the plan can't contain data. The declared schema is what lets the plan validate offline.
Missing values are declared in the schema. Each variable says which values are missing, and whether NaN counts, or that this isn't known. A warp of a variable with unknown missing values is invalid. target_nodata is always required, because whether a target cell ends up empty depends on data and geometry that validation can't see. The declaration lives in the logical schema, not the layout, since arrir can't depend on arrir-layout. Reduce's skipna needs the same field.
Mode ties are an explicit option, ModeTie::Smallest or Largest, so adapters have a rule to match.
Reference fixtures check the meaning. Small fixtures, with expected values worked out by hand from the definitions, are checked into the repository. Every adapter that emits Warp must match them, GDAL's and xESMF's included.
The transformer's error threshold is a field, because gdalwarp approximates by default.
Effect on the schema: the target's dimensions replace the placement dimensions. So (time, row, column) warped to a mesh becomes (time, face). The source grid is dropped once no data variable is placed on it.
One semantic decision: resampling semantics belong to ArrIR. Every adapter, GDAL included, either matches them or rejects the plan.

1. Does gdalwarp's mode break ties by the smallest or the largest value, or by something else, such as scan order?
Short answer: by default it uses scan order. You can change this with the
warp option MODE_TIES=FIRST|MIN|MAX (GDAL >= 3.11, added in commit
94e69abd2e), e.g. gdalwarp -r mode -wo MODE_TIES=MIN .... The default is
FIRST.
Option documentation: alg/gdalwarper.cpp:1524. It says that by default
"the first value encountered will be used".
Default value: alg/gdalwarper.cpp:1549 (eTieStrategy = GWKTS_First).
Enum and field: alg/gdalwarper.h:242, alg/gdalwarper.h:456.

2. Does GDAL's average equal Conservative { area: Planar, renormalise: true }, or does it differ, for example because it measures overlap in source pixel space?
Short answer: it is renormalised, but it is not exact conservative
remapping. Overlap is measured in source pixel space, against an
axis-aligned rectangle built from only two opposite corners of the
destination pixel. The result matches planar conservative remapping only when
the destination pixel maps to an axis-aligned rectangle in source pixel space,
i.e. the same CRS (or a pure scale/translate) with north-up grids on both sides.
What the code does (alg/gdalwarpkernel.cpp)
GWKAverageOrModeComputeLineCoords() (~line 6873) transforms only the
destination pixel's top-left (x, y) and bottom-right (x+1, y+1)
corners into source pixel/line coordinates. The other two corners and the
edges are never transformed.
GWKAverageOrModeComputeSourceCoords() (~line 6919) swaps those values if
needed so that min < max, giving the rectangle
[dfXMin, dfXMax] x [dfYMin, dfYMax] in source pixel space. A code comment
there calls this "really an approximative fix" and says that a correct
version would take the bounding box of the whole transformed square. The
antimeridian wrap is handled heuristically (bWrapOverX).
COMPUTE_WEIGHT_Y / COMPUTE_WEIGHT (~line 6849) give each source pixel a
weight equal to its fractional overlap with that rectangle, as
x_fraction * y_fraction. Only the first and last row/column of the window
get partial weights.
The GRA_Average branch (~line 7960) computes a weighted incremental mean
over valid pixels only: nodata/masked pixels and pixels with
density <= BAND_DENSITY_THRESHOLD are skipped and add no weight. That is
the same as sum(w*v) / sum(w_valid), i.e. renormalise = true.
Options that change this: NODATA_VALUES_PCT_THRESHOLD (default 100) and
EXCLUDED_VALUES / EXCLUDED_VALUES_PCT_THRESHOLD switch to a variant
(~line 7760) that can output nodata when too much of the footprint is
invalid. Even then, valid values are still averaged with renormalisation.
How it differs from a true planar conservative scheme
Area is measured in source pixel space. Each source pixel counts as one
unit of area. For a north-up affine source this is proportional to planar
area in the source CRS. It is not planar area in the target CRS, and it is
not area on the ground: for example, with a lon/lat source, high-latitude
pixels get the same weight as equatorial ones.
Rectangle, not polygon. The footprint is an axis-aligned box in source
pixel space. Curved or rotated footprints are not intersected exactly.
Only two corners are used, so rotation or shear can make the box badly
wrong. In the extreme case it collapses to a line, after which the code
forces at least one source pixel (iSrcXMax++).

3. Can gdalwarp turn off kernel widening when downsampling, so that it can emit KernelScaling::Point?
Short answer: yes. Pass the warp options XSCALE=1 and YSCALE=1:
```
gdalwarp -r cubic -wo XSCALE=1 -wo YSCALE=1 ...
```
Why this works
GDALWarpKernel::PerformWarp() (alg/gdalwarpkernel.cpp ~1092–1295)
normally estimates dfXScale / dfYScale for each warp chunk, as the ratio
of destination pixels to source pixels. It samples a grid of up to 10x10
points, removes outliers, averages, and rounds to 1/n when close. If
XSCALE / YSCALE are set, they override that estimate (lines
1289–1292).
The kernel radius is nXRadius = dfXScale < 1 ? ceil(dfXFilter / dfXScale) : dfXFilter (line 1319). The kernel argument is (i - dfDeltaX) * dfXScale
(e.g. ~4133, ~4252, ~4780). With scale = 1, both the radius and the argument
stay at their native, point-sampled values.
The general path uses std::min(poWK->dfXScale, 1.0) (~4854, ~4964). So
values above 1 (upsampling) never narrow the kernel, and XSCALE=1 is
exactly "no widening".
Side effect: with scale > 0.5, CanUse4SamplesFormula() (~1041) allows the
fast 2x2 bilinear / 4x4 cubic paths. This is the classic point kernel.
Documentation: alg/gdalwarper.cpp:1391. That documentation recommends
setting a fixed value anyway for reproducibility, because the automatic
value can vary between chunks.
Which resampling methods it affects
It affects the convolution kernels: bilinear, cubic, cubicspline, and
lanczos. It has no effect on near or on the area-based methods
(average, rms, mode, min, max, med, q1, q3, sum), because
their footprint comes from the transformed pixel corners (see Q2). In those
methods, dfXScale only sets a bounds-check margin.

integers: decrement by 1, or lowest + 1 if the value is lowest (for

the check, and then rounds to 0 = nodata in the integer output. Nodata
avoidance is therefore only reliable when the working type is integer. You can
force that with -wt Int16 etc., but then the kernel's rounding rule applies.

Question 5: should the layout's fill count as a missing value in the Schema?
No. The Schema's missing values come from the CF attributes only (_FillValue, missing_value), and the layout's fill stays in arrir-layout.
They answer different questions. fill is structural: it's what unwritten elements read as, which the physical layer needs when a chunk is known-empty. A missing value is meaning: which values to skip, mask or propagate. That's what the logical layer needs, for example for reductions that skip NaN.
Promoting fill would be inferring a fact the source didn't state. A store with fill = 0 and no CF attributes is saying unwritten elements are zero, not that zero means missing. The contract's rule that unknown facts aren't invented applies here. A host that promotes fill to a missing value does so in its adapter, not in the schema. I believe xarray does this for some Zarr stores, but I'm not sure of the details across Zarr v2 and v3, so that's worth checking.
In a byterefs 0.1 table the two can't conflict. Validation requires fill to agree with _FillValue and missing_value wherever those are set. So the question only matters when no CF attributes exist, and then the schema records that no missing value is declared. Whether a store should be publishable without CF attributes at all is a description-contract question for byterefs (its Q10), not for arrir.
One detail for the schema: CF missing values are stated in the packed type, before scale_factor and add_offset are applied. The schema should record a missing value together with the type it applies to, so an adapter compares raw values, not decoded ones.

Follow-up on questions 1-4, from implementing them in rwarp ([hypertidy/rwarp#3](hypertidy/rwarp#3), merged, checked against gdalwarp 3.14.0dev-739fcf03bf with fixtures). Most of it confirms the answers above. Three findings change what the GDAL adapter in #23 can promise. Details and repros: [osgeo-upstream notes](https://github.com/mdsumner/osgeo-upstream/blob/main/notes/2026-10-28-gdalwarp-kernel-findings.md).
Q3: gdalwarp's default widening isn't a fixed rule in chunked warps. PerformWarp estimates dfXScale/dfYScale from sample points that don't include the chunk's destination offset (~L1092-1295), so every chunk estimates its scale at the top-left of the whole output. A lon/lat source warped to EPSG:3857 with cubic gives a different answer with a small -wm than without: 319,985 of 320,000 pixels differ, by up to 0.113 on data in [0, 1]. The same happens on GDAL 3.8.4, so it's long-standing.
So KernelScaling::WidenWhenDownsampling matches gdalwarp only for single-chunk warps.
For the adapter: emit XSCALE/YSCALE explicitly (computed for the output, or 1 for Point), and treat the automatic estimate as unreliable.
Also confirmed: bilinear and cubic widen only once the scale is at most 0.5 (CanUse4SamplesFormula); lanczos widens at any scale below 1.
Q1: MODE_TIES can only be trusted for 8/16-bit working types. As answered above, MIN/MAX are ignored on a value's first occurrence in the list path for 32/64-bit and float types. In a fixture where every 2x2 block has four distinct values, Int32 and Float32 differ from Byte on 768 of 1024 pixels for MIN and MAX.
For the adapter: accept ModeTie::Smallest/Largest only when the working type is 8- or 16-bit, or reject them.
rwarp implements the 8/16-bit behaviour for every type, so it gives the same answer as GDAL's histogram path everywhere.
Q2: average overweights edge pixels when the footprint overhangs the source. The box start is clamped to 0 but its partial fraction isn't (COMPUTE_WEIGHT ~L6849), so an edge pixel gets weight above 1. That's one more way average differs from Conservative { area: Planar, renormalise: true }, alongside the two-corner box. rwarp offers both footprints: GdalBox (gdalwarp-compatible, edge weights included) and Exact (first-order conservative, via coverage fractions, about 25 times the cost).
Q4: unchanged. The two rounding rules (half up in the kernel for integer working types, half away from zero in GDALCopyWords for float) and the nodata-avoidance gotcha both reproduce on GDAL 3.8.4 as well. rwarp#3 includes the rounding and clamping work.

Heads-up on where rwarp is going for Conservative, because it bears on how AreaMeasure is defined here. Design: rwarp design/conservative.md (with curvilinear-frontend.md for curvilinear and periodic grids).
What rwarp does now, and plans
Now (0.3): Footprint::Exact is first-order conservative remapping. Each target cell's outline is transformed into the source grid, intersected exactly with the source cells, and averaged by area over valid cells. That is ESMF's conserve in what it computes, with areas measured in source index space.
Planned, one PR per stage, each with its own oracle:
Weights as values: a table of (target cell, source cell, overlap) plus target-cell areas, computed with no pixels read.
An ESMF oracle suite: fixtures from ESMF or TempestRemap, committed, so cargo test needs no ESMF.
A spherical measure.
Curvilinear and periodic grids (cells from corner bounds, as ESMF defines them).
Mesh sources and targets: mesh to grid, and grid to mesh. Mesh to mesh is out of scope.
Second order.
So rwarp could execute Conservative plans that the GDAL adapter in #23 rejects, and Planar exists already.
How it maps onto Conservative { area, renormalise }
renormalise: true is ESMF's fracarea and rwarp's FracArea. false is destarea and DestArea. xESMF defaults to the destarea form (conserve), so it's good that ArrIR makes this a required field rather than a default.
Planar matches rwarp's current measure for an affine source: area in source index space is planar area in the source CRS, up to a constant. For a curvilinear source the two differ unless the cell definition makes them agree; rwarp's curvilinear note does this with an equal-area cell map.

Conservative { edges: CellEdges, area: AreaMeasure, renormalise: bool }

Two more connections
Weights are a data-free plan artifact, like a chunk list. Given the two grids, they're computed with no pixels read, then applied to any number of variables or time steps. That puts them in the physical-planning layer (or an adapter's output), not the logical plan, and it fits purity rules 1 and 2.
Mesh targets reach rwarp through the same shape as GeometryBinding here: the mesh is bound data, not plan parameters. rwarp's stage 5 burns mesh faces into the grid, so its output is the weight table transposed.
The ESMF fixture suite (stage 2) could also feed this PR's reference fixtures for Conservative. The fixtures record how far each implementation is from ESMF's great-circle definition, as a number to shrink rather than a failure.

Update in 5b13e59, following Mike's answers to questions 1 to 5:
Type conversion moved out of Warp into a new Cast operation (plans/cast.md). The test for splitting was whether each is useful alone: a float warp needs no conversion, and an astype needs no warp. gdalwarp converts at the end of its computation, so Cast(Warp(x)) describes it, and the GDAL adapter emits the pair as one call.
WarpVariable is now { var, resampling, empty_value }. The output type follows from the method: the source type for Nearest and Mode, float64 for the others.
empty_value must be NaN or one of the source's declared missing values, so Warp never writes a valid value that reads as missing.
Cast holds Rounding (now including NearestTiesUp, gdalwarp's rule for integer working types), OutOfRange, and MissingEncoding { value, collision }. Collision is Nudge or Keep. It ends with a table of the combinations gdalwarp can emit, taken from Mike's reading of the source and not yet checked by fixture.
Every resampling variant that takes options holds a named struct: Interpolate(InterpolateOptions), Mode(ModeOptions), Conservative(ConservativeOptions). This is added to design.md as a convention.
GeometryRules { edges, edge_shape, error_threshold } groups the settings that describe the grids rather than the values.
Edge shape is split from the area measure, as Mike suggested. EdgeShape is StraightInIndex, StraightInLonLat or GreatCircle, and AreaMeasure is Planar (source index space) or Spherical. The edge shape sits in GeometryRules rather than in the Conservative options, because containment for Nearest and overlap for Mode depend on it too. This is new question 6.
The kernel's widening factor is stated in the plan: KernelScaling::Widen { column, row } replaces WidenWhenDownsampling, because gdalwarp's own estimate varies between chunks (osgeo-upstream#50).
MidpointsBetweenCentres is redefined in the coordinates' own CRS, with each corner at the mean of the four centres around it. This matches gdalwarp's geolocation transformer with PIXEL_CENTER.
Missing values. The layout's fill doesn't count as missing. CF missing values are compared in the packed type. Packed variables are added to "Not settled".
Reference data. Regridding weights are noted as a physical-planning output. Conservative fixtures can come from ESMF and TempestRemap, via the gdal-r-esmf image in hypertidy/gdal-r-ci.
Questions 1 to 5 are summarised as answered.
