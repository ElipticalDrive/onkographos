Split from #1050 (epic #943). Slice (c) — environment / froxel volumetric lighting for scenes (3D raymarchers).
Problem: only hit pixels get lighting. 3D miss rays return a flat InSetColor or the gradient sky (GpuKernelUtils.MissColor, ShadingPipeline.SkyColor); VolumetricInScatter runs only on the hit path. So the space around the object stays black unless an HDRI or backdrop is shown.
Existing infrastructure: froxel volumetrics (Engine/Rendering/Lighting/FroxelCameraVolume.cs, FroxelVolumePass, D3D + Vulkan kernels) are relief-only — the API takes HeightfieldRaymarch2D.ReliefCamera, and occlusion is heightfield-based.
Plan (spike first)
Quick win: fog / ambient in-scatter on miss rays, out to a configurable max distance (fog colour instead of black). CPU ShadingPipeline + GPU MissColor. New LightingFxData field(s), byte-identical default.
Spike: generalise froxel to a camera abstraction (orbit camera + 3D depth AOV, sky +Inf → far plane) with DE-based shadow occlusion. Measure cost; decide on CPU+D3D+Vulkan slicing.
Follow-up slices per backend, from the spike.
Batch parity: every new LightingFxData field must flow through LightingFxPresetData (DTO drift test) → --lighting-preset; add a dedicated flag via LightingFidelity if warranted.

Known limits
Haze builds up fast over full depth: a fog density of 0.03–0.05 is a good starting point.
UserBulb shadows are slow: roughly 5 s per frame at 24 steps and 480×300, because its DE is numerical. This is noted in the tooltip and in --help.
Still CPU-only: thin-lens DoF and depth output (stereo) take the CPU trace.
Optional later: moving populate/composite into the D3D/Vulkan froxel kernels would need a GPU-side DE. Not planned.
