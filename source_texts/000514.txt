Texture Mapping
● Most popular DVR method
○ Image-order method
○ Used in most medical rendering applications
● Original concept: take "slices" out of the data set, render
them back to front with alpha blending.
Source: R.Crawfish - Ohio State University
Problem:
● For correct perspective: need slices
perpendicular to view direction
○ Interpolating values = expensive
○ This will lead to 3D texture mapping
volume rendering
jeroen.baert@cs.kuleuven.be
2D Texture Mapping
● Solution: View volume as set of slices parallel to coordinate
planes (axis-aligned)
○ Pick the best orientation for viewing direction at render time
● Problems:
○ Sudden jumps in image quality when
different parallel-plane dataset is used
○ Sampling rate is not even : artifacts
Source: R.Crawfish - Ohio State University
jeroen.baert@cs.kuleuven.be
3D Texture Mapping
● Use slicing panes parallel to view plane
(Cabral et al, 1994)
○ Eliminates artifacts from 2D texture mapping
● Expensive, but can be GPU-accelerated
● Lighting / shadows added in multiple passes
Source: R.Crawfish - Ohio State University
Disadvantages:
○ Need entire dataset in GPU
memory
■ Methods have been proposed for
cleverly swapping data in/out
○ Limited bit resolution of GPU
textures
■ Has become non-issue with recent cards

Splatting
● Proposed by Westover (1990)
○ Object-order method
● Represent each voxel using 3D
reconstruction kernel
○ Usually Gaussian-like kernels
● Integration of kernels on line of
sight -> footprints
Source: Westover90 (Original Splatting Paper)
● Mapping footprints on image
plane
○ Order important: front-to-back
○ Similar to throwing snowballs at
glass window, hence splatting
jeroen.baert@cs.kuleuven.be
Splatting
Advantages
● Kernels can be preintegrated
○ Lookup table
● Interpolation is performed in 2D space
● Only relevant voxels are displayed
Disadvantages
● Inherent: Reconstruction and Compositing on a per-voxel basis:
artifacts where voxels overlap.
● Image quality heavily influenced by type of kernel used
● Using preintegrated kernels: integrated as a whole, not piecewise
○ Color bleeding
○ Brightness variations
● Aliasing artifacts

Shear-Warp: Hybrid Method
● Proposed by Lacroute (1994)
● Problem with Image-order methods?
○ For every pixel: go through volume again
■ Redundant calculations
● Problem with Object-order methods?
○ Goes through every voxel in storage order
■ Hard to formulate early termination
● Shear-Warp = Hybrid method
○ Trying to combine the advantages of two DVR classes
jeroen.baert@cs.kuleuven.be
Shear-Warp: Hybrid Method
1. Shear: Transform volume dataset to sheared object space
(Aligning nearest face of volume with image plane)
2. Project: Render on image plane using alpha blending
(Easy, because axis-aligned now: similar to 2D texture mapping)
3. Warp: 2D-warp the intermediate image
Source: Zou et. Tinnies (Magdeburg 2003)
jeroen.baert@cs.kuleuven.be
Shear-Warp: Hybrid Method
Advantages
● Intermediate image scanlines align with volume data
● All filter operations in 2D: speed and efficiency
● Capable of rendering at interactive framerates
jeroen.baert@cs.kuleuven.be
Shear-Warp: Hybrid Method
Disadvantages
● Choice of resampling filters is
limited to 2D
○ Artifacts become easily visible
● 3 persistent data copies of the
volume needed
○ Each compressed along a different
axis (run length encoding)
○ For access from arbitrary direction
● Sampling rate inconsistent for
different directions
○ Aliasing artifacts

Discrete Volume Rendering Equations
● Can be derived from general rendering equation
○ Volume Rendering, H.C. Hege 1993 paper
● Shows relation between color / sample opacity in a ray
casting rendering scheme.
● Base for all DVR ray casters
● Iλ = Intensity on point x on image plane, for ray r and wavelength λ
● Cλ (s) = Light emtted at point s in space, in the direction of r,
with wavelength λ
● α = 1 - transparancy.

KD-trees
Why KD-trees?
● Generalisation of binary search tree
○ Binary Search tree where every element
is a 3D coordinate.
○ So for volume rendering: k = 3
● Balanced
○ We want to find intersections fast.
● Hierarchical bounding volumes
Separation planes =
X, Y and Z-axis of volume data.
Cuts space into rectilingual regions
jeroen.baert@cs.kuleuven.be
Octree
An Octree is not a KD-tree
● Each node : 8 children
○ Not binary
● Not balanced
Voxels are split using
split points.
Cuts space in 8 cubes
jeroen.baert@cs.kuleuven.be
KD-trees versus Octrees?
Everlasting debate: it depends on the application and data
● KD-tree
○ Supports overlapping polygonal geometry
○ Better for irregular geometry (adaptable split panes)
○ Easier intersections (2 vs. 8 regions)
● Octree
○ Efficient for sparse scenes
○ Maps easily to regular-spaced grids (volume data!)
○ More regular structure: memory consumption
BOTH are used in current GPU ray casters
jeroen.baert@cs.kuleuven.be
Traversing the tree
Traversing tree = most important operation in GPU raycasting
● For now, we'll assume all volume data fits in GPU memory
Several algorithms proposed
● Applicable to octrees and kd-trees
○ Only difference lies in how to select next child to traverse
■ Easier for kd-trees: simple split pane
■ Octrees have 8 children
Keeping a stack on GPU is/used to be difficult/expensive
● Stackless algorithms
● Stack-based algorithms

Seminal paper for stackless GPU-based traversal:
Stackless KD-Tree Traversal for High Performance GPU Ray Tracing
S. Popov, J. Gunther, H.P.Seidel, P. Slusallek (Eurographics 2007)
● Written for polygon-based ray tracing, but most concepts

jeroen.baert@cs.kuleuven.be
Stackless: KD-restart
● Simplest stackless
algorithm
● Depth-first search for leaf
○ Leaf found & ray stops
■ end
○ Leaf found & ray continues
■ calculate exit point
■ restart search at root
● Complexity ~ O(n.logx(n))
○ n = number of nodes
○ x = degree of tree used
jeroen.baert@cs.kuleuven.be
Stackless: KD-restart: (Dis)Advantages
● Very Costly algorithm
○ For every neighbour:
restart at root
● Low memory consumption
○ Only the tree
○ No extra data needed
■ (If no LOD is used)
● Easy implementation
jeroen.baert@cs.kuleuven.be
Stackless: KD-backtrack
● Same as KD-restart
○ At every descent
■ Check if ray crosses split pane
■ If not: mark as new restart point (store pointer)
● When neighbour has to be found
○ Jump back to restart point
■ Instead of root
● Complexity is also ~ O(n.logx(n))
○ But in practice: as fast / faster than KD-restart
■ In worst case scenario the restart node is always the root node
○ Only beneficial if split-pane check is easy
jeroen.baert@cs.kuleuven.be
Extension: Parent pointers
● Introduce parent pointers
○ Eliminates need to return to root
○ Memory usage increases significantly
● Is basicly an implicit stack ...

Extension: Neighbour Pointers
● Introduced by Popov07 / Gobetti08
● Also known as "ropes"
● Store pointers to adjacent
neighbour nodes
○ In every leaf
○ Usually 6 pointers
■ For each side of cube
○ Computed when KD-tree
is constructed (pre-process)
jeroen.baert@cs.kuleuven.be
Extension: Neighbour Pointers
● Memory requirement ~ x6
● Speedup for ray casting
○ Can jump directly to object space
neighbours in algorithms
○ No backtrack/parent pointers
needed
○ Complexity ~ O( logx(n) )

Stack-based algorithms: GPU
● Seems the most logical approach
● Preferred class for CPU-based ray tracing
○ Only recently (> 2009) in use on GPU
Why?
● Variable-size stack was hard to implement on GPU
● Stack can grow fast: limited memory
● Recursion was/is limited on GPU
○ So an elegant algorithm like this used to be
impossible on GPU:
■ Do some logic
■ Pop or push nodes on/off the stack
■ Call self with new arguments
jeroen.baert@cs.kuleuven.be
Stack-based algorithms: GPU
But we do want to use GPU!
Pro
● Significantly higher raw compute power (vs. CPU)
● High parallelism : excellent for ray casting
Con (are slowly fading, but major issues remain)
● Low memory (vs. regular RAM/System Memory)
○ Remember: we need a stack for every ray shot = every GPU thread
● Low bandwidth
● Historically optimized for rasterization of polygons
● Limited programmability
○ (major improvements in last years: CUDA, OpenCL, ...)

Stack-based: Full stack
● Easiest algorithm = O(log(n))
○ Traverses the tree like Depth-First-Search
○ Remember:

■ Sometimes multiple nodes need to be popped at once

Stack-based: Short Stack
● Keeping a full stack for each ray shot / each tread
○ Expensive
● Short-stack = mixture of
KD-restart and stack approach
● Exploits the fact that neighbour
nodes are usually close
○ Not much backtracking needed
○ No full stack needed
● Stack of limited size
● Look for neighbour node
○ Use stack first
○ Underflow?
■ Restart

● Preferred stack-based method on GPU's
● Stack size small: usually ~ 3

Extension: Ray Packets
● Observation : rays around pixel follow ~ the same path
○ Only difference in small section at the end
○ So lots of redundant work when tracing neighbouring rays
● Ingo Wald (2004): Interactive Distributed Ray Tracing
○ First steps into realtime parallelisation of ray tracing
● Concept:
○ Pack rays in 4x4, 8x8, 16x16 grid
○ Treat packet as single ray + boundary checks
○ Shoot ray through volume until rays take different paths (not all rays in
same node)
○ Fork, compute exit points, and ray trace each ray individually
jeroen.baert@cs.kuleuven.be
Extension: Ray Packets
● Observation : rays around pixel follow ~ the same path
○ Only difference in small section at the end
○ So lots of redundant work when tracing neighbouring rays
● Ingo Wald (2004): Interactive Distributed Ray Tracing
○ First steps into realtime parallelisation of ray tracing
● Concept:
○ Pack rays in 4x4, 8x8, 16x16 grid
○ Treat packet as single ray + boundary checks
○ Intersect ray with geometry until rays take different paths
■ (when part of the ray packet intersects in a different node)
○ Fork, compute exit points, and ray trace each ray individually
● Speedup is depends strongly on volume data set
