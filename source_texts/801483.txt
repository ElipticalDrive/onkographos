Pull request overview
This PR updates TypeGPU’s WGSL code generation for mat4x4f.translation to avoid repeated evaluation of the translation-vector expression by switching from a 16-scalar matrix constructor to a 4-column vec4f-based constructor, while keeping the CPU-side matrix layout unchanged.
Changes:
Generate translation matrices in WGSL via mat4x4f(vec4f(...), vec4f(...), vec4f(...), vec4f(v, 1)) to ensure the translation vector is evaluated once.
Add a regression test that uses a side-effectful helper to assert single evaluation and correct translation column placement.

ℹ️ Clean, well-scoped fix — the translation column now embeds the vec3 expression exactly once, and the regression test is genuinely asserting the bug. One adjacent component (scaling4) shares the same pattern and is worth a look.
Reviewed changes
translation4 codegen (packages/typegpu/src/data/matrix.ts) — the final matrix column changes from expanding the vector three times as ${v}.x, ${v}.y, ${v}.z to a single vec4f(${v}, 1) inside the four-column mat4x4f constructor. Column-major layout and the CPU normalImpl are unchanged; generated WGSL is valid (vec3f(scalar) splat plus vec4f(vec3f, f32) both legal forms).
Regression test (matrix.test.ts) — a nextValue() helper mutates a tgpu.privateVar, and the test asserts nextValue() is emitted exactly once inside vec4f(vec3f(f32(nextValue())), 1). This test genuinely fails on the old expansion (3 calls), so it's not theatre.
Verified locally: the focused matrix.test.ts suite passes 37/37.
ℹ️ scaling4 shares the same per-component expansion pattern
scaling4 (packages/typegpu/src/data/matrix.ts:613) still emits mat4x4f(${v}.x, 0, 0, 0, 0, ${v}.y, 0, …, ${v}.z, 0, …), i.e. the identical ${v}.x/y/z per-element expansion this PR just eliminated in translation4. A side-effecting vec3 expression passed to d.mat4x4f.scaling(...) would still be evaluated three times on the GPU — the same bug class from #2859. Unlike translation it can't be collapsed with a single vec4f(v, 1), because the components land on the matrix diagonal in different columns; a same-class fix there needs a temporary binding or codegen restructuring. Not blocking this PR (scope is specifically the translation matrix), but worth a decision on whether to track it as a follow-up.

scaling4 codegen (packages/typegpu/src/data/matrix.ts) — now delegates via scaling4Gpu[\$gpuCallable].call(ctx, [v]) to a module-level fn([vec3f], mat4x4f) WGSL helper, so the vec3 expression is consumed once (diagonal built from vector.x/y/z).
