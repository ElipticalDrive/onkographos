```
The flat 2D grid could be drawn with one vertex per cell ("Points": fast, but the colours are interpolated between vertices, so cells look blurred) or with one quad per cell ("Cells": sharp, but slower).
Add a third, additional mode - Texture - which keeps both existing modes untouched: one RGB pixel per cell in a vtkImageData shown on a single quad with nearest-neighbour magnification. It is sharp like Cells and needs no lookup table with rows*cols entries, no per-cell scalars and no extra points; a new step only rewrites the pixels. The image is RGBA and the actor is told about transparent cells (ForceTranslucent), like the lookup table modes do since #158.
```

Add --benchmark: measure reading, colouring and rendering of the steps
…
d554906
```
Shows the steps from --step (the first one by default) to the last one,
synchronously and without any delay, prints the time of every step split
into phases and a summary (median, mean, min, max) and exits:

  read        reading and parsing the files of the step
  coloring    CPU time of colouring the cells (calculateCellColor and
              writing the colours into the lookup table / texture pixels)
  VTK update  the rest of updating the scene
  render      drawing, including waiting until the GPU has finished

Why the existing --autoPlay and --metrics are not enough: the playback is
driven by a timer with a delay between steps and the paint waits for vsync,
and the "Step Loading" metric covers only reading the files.

* the swap interval is set to 0 when --benchmark is on the command line
  (the surface format has to be set before the window is created)
* the first step is a warm-up (OpenGL objects, texture upload) and is not
  counted in the summary
* the report also contains the grid size, the rendering mode really used,
  the OpenGL renderer and, on Linux, the peak memory (VmHWM)
* BenchmarkStatistics.h (statistics and the table) has unit tests
* Visualizer::lastColoringTime() / resetLastColoringTime() give the time
  of the colouring phase

Also fixes the option added in the previous commit: with .choices() argparse
takes the next argument as one more value of the option, so
"--renderingMode=texture --benchmark" was rejected. The value is now checked
in main() (before the window is created) with a clear error message.
```

Texture mode: copy the colour channels instead of converting them
…
3933cf0
```
fillColorImage() converted every channel of every cell with
toByte(toUnitColor(c)), i.e. lround(clamp(c / 255.0, 0, 1) * 255.0), which
is the identity for a byte: the colours (and the "is it transparent" test,
alpha != 255) are exactly the same as when the bytes are copied.

That code is instantiated in the model plugin, which is compiled without
optimization on Linux ("-shared -fPIC"), so the conversion was expensive:
measured at -O0 it cost about 96 ns per cell against 17 ns for the copy
(identical pixels and flag, checked for all 256 values of a channel). On a
5923 x 5923 grid this phase of --benchmark was about 0.9 s per step slower
in the Texture mode than in Points because of it.

Note: the template code lives in the plugin (lib*Plugin.so in the model
directory), so a model compiled before this change has to be recompiled
(remove the .so) to get the faster loop.
```

Why this PR makes sense
Problem (#138): Points mode is blurry (colours are interpolated between neighbouring vertices), Cells mode is sharp but slow and memory hungry on large grids.
This PR adds a third mode, Texture (the existing modes are unchanged, Points is still the default): one RGBA pixel per cell on a single quad with nearest-neighbour filtering. It is sharp like Cells (offscreen check: pixel-identical to Cells, also with transparent cells), and needs no lookup table with rows×cols entries, no per-cell scalars and no extra points. Grids larger than 8192 px per side fall back to Cells.
Also in this PR: Settings → Rendering submenu (Points / Cells / Texture), --renderingMode=points|cells|texture, --benchmark (so the numbers below can be reproduced), --autoPlay documented, deprecated --silent removed.
Measurements

render is 3.7× faster than Points and 4.7× faster than Cells
a whole step is 36% / 40% shorter, 50 steps took 285 s instead of 442 s / 476 s

every Texture step (slowest: 6.7 s) is faster than every Points / Cells step (fastest: 7.9 / 8.6 s), so the difference is not noise
Caveat: one machine with an integrated GPU, so the absolute render times will differ on a discrete GPU. The rest of a step is now dominated by reading the files and CPU colouring (the model plugin is compiled without optimisation), which is independent of the rendering mode and out of scope here.
Reproduce:
```
for m in points cells texture; do
  OOpenCal-Viewer <dir> --step=<N> --renderingMode=$m --benchmark > bench_$m.txt
done
```

Make Texture the default rendering mode
…
6314d92
```
On a 5923 x 5923 grid (35 M cells) the Texture mode draws a step 3.7x faster
than Points and 4.7x faster than Cells, a whole step is 36-40% shorter and
the peak memory is 2.3-2.5x lower (see the measurements in the PR). It is
also sharp, unlike Points, so it is what the user should get without having
to choose.

* GridWorldMapping::defaultRenderingMode is the only place that names the
  default; SceneWidget and the default arguments of drawWithVTK() use it.
* Settings -> Rendering starts with Texture checked (the menu is also
  synchronised in the MainWindow constructor, so the .ui file cannot
  disagree with the code).
* --renderingMode help and COMMAND_LINE_ARGUMENTS.md say that texture is the
  default; --renderingMode=points brings back the old rendering.
* test: the default is Texture.

Points and Cells stay available and unchanged. The mode is still not
remembered between runs.

Known consequence: a grid with more than 8192 rows or columns does not fit
in a texture and is drawn as Cells, so for such grids the default is now
Cells instead of Points.
```
