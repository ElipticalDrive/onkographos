Summary
Adds color-by-volume mapping to the isosurface pipeline node so a charge-density isosurface can be painted by a second scalar field — e.g. an electrostatic-potential cube mapped onto an electron-density contour (the standard ESP-mapped density rendering). A second commit fixes a pre-existing viewer nondeterminism this PR's CI run surfaced (details below).
Color-by-volume (commit 1)
New colorVolumetric input port (volumetric) on the isosurface node. Connect a second load_volumetric node (e.g. esp.cube) to it.
New params on IsosurfaceParams: colorMode ("solid" | "volume", default "solid" — fully backward compatible), colormap ("rwb" red→white→blue chemistry ESP convention / "bwr" / "rainbow"), and optional colorRange ([min, max]; omitted = auto range — symmetric around 0 for the diverging maps, sampled min/max for rainbow).
New src/pipeline/executors/volumeColor.ts: world→grid trilinear sampling that handles non-orthogonal CUBE step lattices (3×3 matrix inverse, boundary clamping), colormap stops, auto-range computation, and RGBA vertex-color fill.
Executor: samples the color volume at every marching-cubes vertex; falls back to the solid colors when no color volume is connected (with a node warning surfaced by the execution engine) or when the color grid is degenerate.
Node UI: "Color by" selector, colormap picker, and min/max range inputs (blank = auto); the solid color pickers show only in solid mode.
Python API: Isosurface(color_mode=..., colormap=..., color_range=...) with the new inp.color_volumetric port (handle colorVolumetric), validation, and dict round-trip.
Catalog / AI prompt schema updated (fixture node-schema-section.txt regenerated), docs (json.md, python.md) and CHANGELOG.md updated.
Deterministic frame-vs-snapshot geometry (commit 2)
The first CI run failed E2E webapp host (pixel) on subsystem-rendering/webapp-default with a full-page diff of exactly 11.29 %. Root-causing it showed a pre-existing app race, reproduced identically on a build of main in the same environment (2/8 runs): while a trajectory streams in, the boot-time pipeline executes several times and the Viewport's snapshot / frame geometry updates land in either order. When the snapshot lands last, the viewer shows the structure file's coordinates (the PDB) at "frame 1/100" instead of trajectory frame 0 (the XTC) — a bimodal coin flip per load, visible to users too.
Viewport.tsx now re-applies the current trajectory frame right after every loadSnapshot, so frame data always wins while a trajectory is loaded (guarded on matching atom counts against stale frames).
The E2E pinFrame helper forces one fresh frame application through the test-mode playback store before returning.
The ten webapp-host baselines that had encoded the racy structure-coordinate variant were re-recorded and visually inspected (camera/webapp-{orthographic,perspective,reset}, modify-node/webapp-{default,scale-0_5,opacity-0_4}, subsystem-rendering/webapp-{default,labels,line,polyhedra}). JupyterLab-host baselines are unaffected (verified passing pre- and post-fix); VSCode-host baselines are untouched.
The update-e2e-baselines label has been applied so the CI-container baselines (tests/e2e/baselines-ci/) are re-recorded on this branch — they encode the same racy variant and would otherwise fail deterministically.

test(e2e): make atom-bond-junction independent of the demo trajectory
…
72f9c62
```
The spec was flaky in CI and locally (~1 run in 6): the projected atom
positions came back thousands of pixels off-screen, bit-identical every time,
and resetCamera could not recover. The screenshot showed an empty viewport with
"Atoms 2 · Bonds 1" in the HUD and "1 / 100" on the playback bar.

Cause: the webapp boots by loading its caffeine_water demo plus a 100-frame
XTC, and dropping a fixture in replaces only the structure — the demo
trajectory stays wired. Since #673 frame data always wins over the snapshot, so
caffeine_water's frame-0 coordinates land on this fixture's two atoms and fling
them out of view; resetCamera fits the snapshot's bounds, not the frame's, so
it cannot bring them back. Remove the trajectory node and re-drop the fixture
(removing the node stops further frame updates but leaves the coordinates a
frame already wrote), then poll until the camera has actually fitted before
reading any screen coordinate.

Two smaller fixes in the same pass:

- Settle setBondsVisible on the rendered midpoint pixel rather than
  `data-bond-count`. That attribute has three writers (snapshot load, pipeline
  bond streams, per-frame distance bonding) and whichever lands last wins, which
  is what timed out on the first CI run. Polling the pixel the spec is actually
  about cannot go stale, and if the stick never arrives the failure names that.
- Turn the viewport's pivot marker off. Its crosshair sits exactly on the view
  centre, which for this two-atom fixture is the sampled midpoint.

Verified with 12 consecutive local runs (all green, was ~2 failures per 12) plus
the webapp-host neighbourhood: 27 passed.
```
