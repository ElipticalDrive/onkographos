Phase 10, part A (CLAUDE.md §8.6 stages 3 and the hardware half of 4): the GPU-driven production renderer. Scene data lives on the GPU, culling and draw generation happen on the GPU (two-phase occlusion culling), the hardware raster writes a 64-bit visibility buffer, and one resolve pass shades it with the reference renderer's own shading code. The engine now renders with it by default (r.pipeline=1). Decisions and numbers: ADR-0029; design: docs/render.md "The production path".

Each pyramid reads the whole 8-byte visibility buffer (0.13 ms at 4K); a single-pass downsampler and a 32-bit depth copy are the candidates, measured in the next part. benchmarks/render_budgets.txt now holds every production pass to its recorded time + 5 % on the RTX runner.
What is in it
GPU scene (engine/render/src/vis_scene.c): instance/transform/mesh/material-map tables by pool slot, updates scattered by compute, 64-bit positions as hi/lo floats (10,000 km from the origin renders like the origin), material ranges from a new TLSF range allocator (core/range_alloc.h), meshlets built by the render module (moved from the cooker; byte-identical cooked output).
Frame (vis.c, shaders/render/vis_*): instance and meshlet culling (frustum, normal cone, occlusion against last frame's pyramid, then the deferred ones against this frame's), mesh-shader raster (or DrawIndexedIndirectCount over a 16-bit index pool), imageAtomicMax into the R64 visibility buffer, depth pyramids, resolve with analytic barycentrics and derivatives, blended surfaces forward on top. Debug views for clusters, triangles, instances.
Engine/editor/samples: r.pipeline, r.occlusion, r.cone_culling cvars; the editor's stats panel shows the GPU counters; pbr_viewer --pipeline / P; scene_demo logs what the GPU culled.
RHI (each with a test): uploads overlapping within one batch are ordered; the render graph orders every read after the last write and every write after every read; consecutive passes share a command buffer (one per batch and thread, CLAUDE.md §10.5); geometry_shader and subgroup features; driver quirks (NphGpuDeviceInfo.quirks).
ntest_skip is declared noreturn (static analysis knew no better).
Bugs found on the way
Lavapipe (Mesa 25.2.8): fragment shaders of mesh-shader pipelines read zeros from push constants (diagnosed on a throwaway CI branch: mesh-stage push constants, per-vertex and per-primitive outputs all work). Recorded as NPH_GPU_QUIRK_MESH_FRAGMENT_PUSH_CONSTANTS; lavapipe takes the indirect raster, and the RTX runner now also runs the render tests under validation, so the mesh-shader path stays covered.
Depth pyramid: built as if Vulkan rounded mip sizes up; it rounds down, so odd mips lost their last row and column and could cull visible geometry at the right and bottom edges. Found by the new culling-twin test; a readback test now checks every texel.
Sync validation: overlapping uploads in one batch (write-after-write), and reads by different stages of the GPU-driven counters (read-after-write) in the render graph.
A production frame that also computed the environment needed more than a thread's 32 command buffers.
Replacing a whole population of instances between two frames ran out of material ranges.
Tests
New: test_vis.c (12: images against the reference, culling invariance, frustum, mesh vs indirect, far from origin, instance lifecycle, population swap, alpha modes, debug views, cooked vs built meshlets, culling math vs C twins on 8,192 random cases, depth pyramid readback); render graph read tracking and command-buffer grouping; overlapping uploads; mesh pipeline draws and fragment push constants; engine draws the showcase on both pipelines and compares.
Windows MSVC Debug / Development / Shipping: all 70 CTest suites pass; validation and sync validation report nothing. GCC, clang, and clang-tidy clean on the changed files.
Phase 10 continues with the software rasteriser, tile classification and clustered lights, virtual shadow maps, the radiance cache, TAA and post, and the reference scenes.

feat(core): a range allocator, TLSF over offsets for GPU sub-allocation
…
303c474
```
The renderer must sub-allocate GPU buffers whose contents the CPU never
touches: the meshlet-index pool of the indirect-draw path and the
per-instance material tables, and Phase 13's streaming pools after them.
Core's TLSF keeps its headers inside the managed memory, so it cannot
manage a range it does not own.

nph_range_alloc hands out offsets into [0, size) with the bookkeeping out
of band: Two-Level Segregated Fit (Masmano et al., ECRTS 2004) with the
8-bit floating-point size classes of Aaltonen's OffsetAllocator (2023),
256 classes under a two-level bitmap. Allocation rounds up to a class and
takes the first non-empty class at or above it; freeing coalesces with
both neighbours. Both are O(1). Ranges carry their node, so a double
free or a forged range is asserted and refused.

Tests: the size classes bracket every size up to 2^16 and random u32s,
packing and coalescing, refusals (zero, too large, the allocation count,
double frees, forged ranges), the meaning of a refusal under class
rounding, and 50,000 random operations against a model of the space with
the invariants validated along the way. Benchmarks (Profile, Ryzen 7
5800X): alloc + free of 64 units 29.5 ns, the random mix of 1024 live
ranges 21.8 ns per operation, level with TLSF.

fix(gpu): order overlapping uploads within one batch
…
5cda87b
```
Copies recorded into one command buffer may run in any order, so two
uploads into overlapping bytes of the same buffer in one batch raced:
synchronisation validation reported WRITE_AFTER_WRITE when the GPU-driven
renderer rewrote a scene record, or freed a range and handed it out again,
before the batch was flushed.

Each buffer now keeps the envelope of what the current batch wrote to it.
A copy that overlaps the envelope gets a transfer-to-transfer barrier first
and the envelope restarts; otherwise the envelope grows. That is O(1) per
upload, appends never pay for it, and the later upload always wins.

The new tests upload overlapping and disjoint spans in two batches, outside
and inside a frame, on the default and the single-queue layouts, and check
the bytes; without the barrier they report the hazard.

fix(gpu): order every read after the write and every write after ever…
…
26b5087
```
…y read

The render graph kept one (stages, access) per resource and mip: a read
replaced it, so a later read in another stage found a read before it and no
barrier. The GPU-driven renderer's counters showed it: written by a compute
pass, read as indirect arguments, then copied for statistics, the copy got
no barrier from the write (READ_AFTER_WRITE under synchronisation
validation).

Each resource and mip now keeps the last write, or layout transition, as
its state, and separately the read stages and access already ordered after
it. A read those do not cover gets a barrier from the write; a write or a
transition waits for the write and for every read since; transitions start
a new read set; cross-queue uses reset both. Aliasing predecessors, the
present transition, and the state written back to imported resources
include the reads.

The new test writes a buffer by transfer, reads it as indirect arguments,
copies it, rewrites it, and copies it again; synchronisation validation is
the oracle, and the old model fails it.

fix(gpu): consecutive passes share a command buffer
…
6e0d69c
```
Every pass recorded into a primary command buffer of its own, so a frame's
command buffers grew with its passes, and a thread may begin only
max_commands_per_thread (32) per frame: a GPU-driven frame that also
computed the environment (about forty passes) recorded on one thread failed
with FULL. CLAUDE.md §10.5 asks for a constant number of command buffers.

Each batch's passes now split into consecutive groups, one command buffer
each: one group per batch without a job system, one per worker with one,
each recorded by one job and submitted in order. Every pass keeps its
barriers, its timestamps, its profiling zone, and, when it shares the
command buffer, a debug label of its name.

The existing tests' command-buffer counts change accordingly, and a new
test records 24 passes on a device that allows a thread 4 command buffers.

NTEST_SKIP leaves the test immediately (it longjmps out), but nothing told

CLAUDE.md §8.6 stages 3 and the hardware half of 4 (ADR-0029):
NphRenderView.pipeline = NPH_RENDER_PIPELINE_PRODUCTION draws the frame
with scene data on the GPU, culling and draw generation on the GPU, a
64-bit visibility buffer, and one resolve pass that shades with
surface.glsl, the reference renderer's own code.

The GPU scene (vis_scene.c): instance, previous-transform, mesh, and
material-map tables indexed by pool slot; changes travel as at most
max_instance_updates records per frame and a compute pass scatters them.
Translations reach the GPU as high and low floats differenced from the
camera's part by part (Cozzi & Ring 2011), so 10,000 km from the origin
renders as the origin does. Material ranges come from the TLSF range
allocator; a destroyed instance's ranges return two frames later, with
room for a whole population replaced between frames. Meshes get meshlets
(64 vertices, 124 triangles) and, without mesh shaders, a slice of a
16-bit index pool.

A frame (vis.c, shaders/render/vis_*): two-phase occlusion culling (Haar &
Aaltonen 2015; Karis et al. 2021) of instances and then meshlets, by
frustum, normal cone, and the depth pyramid (Mara & McGuire 2013 sphere
projection), against last frame's pyramid and then this frame's for what
phase 0 deferred; subgroup-aggregated appends; a mesh-shader raster
(32 threads per cluster, back-face and small-triangle culling) or
DrawIndexedIndirectCount where mesh shaders are missing or carry a quirk;
imageAtomicMax of (depth, cluster, triangle) into R64_UINT; depth pyramids
whose mips follow Vulkan's sizes; a resolve with analytic barycentrics and
their derivatives (Schied & Dachsbacher 2015); blended surfaces forward on
top; cluster, triangle, and instance debug views; the GPU's counters in
the frame statistics, two frames late. The CPU's cost per frame does not
depend on the object count. Devices without 64-bit image atomics, int64,
subgroup ballot and arithmetic, or the geometry-shader feature draw with
the reference renderer, logged once.

Tests (test_vis.c, 12): images against the reference (100 % of pixels
within 3 levels), with every alpha mode and side, and far from the origin;
culling switched off changes nothing; the frustum culls what is off
screen; mesh shaders and indirect draws give the same image; instances
move, hide, and go, and a population is replaced between frames; the
debug views; cooked and built meshlets draw the same; the culling math
against double-precision C twins (render/reference.h) on 8,192 random
cases; and the depth pyramid read back and checked texel by texel. The
golden tests render every scene through the production path too, against
the same baselines (scores within 1e-4 of the reference's on the RTX
3060 Ti); golden_approve.py never approves those renders.

The twin test found the pyramid built as if Vulkan rounded mip sizes up:
odd mips lost their last row and column, which could cull visible geometry
at the right and bottom edges. The last texel of each row and column now
takes the extra source texel.

pbr_viewer gains --pipeline and P (and the three new debug-view names its
table lacked); scene_demo draws on the production path by default and logs
what the GPU culled.

CLAUDE.md §10.7 asks every renderer PR for its cost in milliseconds and
DRAM bytes; Phase 10's exit asks for a CPU cost constant in the object
count. render_perf drives the renderer on a device, scene by scene:
<scene>.cpu is the median CPU time of nph_render_frame itself,
<scene>.gpu and .gpu.p99 the frame's mean and 99th-percentile GPU time,
and <scene>.gpu.<pass> each pass's mean time with its declared footprint
(an upper bound on DRAM traffic) from the GPU profiler. Until the
reference scenes arrive the scenes are synthetic: grids of 1,024, 10,240,
and 102,400 cubes at 512 x 512, and a 4K field of 16,385 instances, each
through both pipelines.

The reference run (RTX 3060 Ti, Profile) is recorded in benchmarks/results;
the production path's CPU cost is 5 to 6 µs at every size (the reference's
grows from 0.2 to 13.4 ms), and the 4K field takes 2.06 ms of GPU time.
scripts/render_budgets.py turns it into benchmarks/render_budgets.txt:
every production pass at its mean plus 5 % (50 µs floor below 0.2 ms), the
CPU entries at a flat 50 µs.

The GPU performance workflow now runs render_perf against those budgets,
and runs the render tests under validation as well as the gpu tests: the
production path's mesh-shader raster runs only on that runner, since
lavapipe takes the indirect one. The CTest smoke run renders the 1k grids.
