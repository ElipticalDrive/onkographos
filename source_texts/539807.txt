Why
The README mentioned Gaussian splats only as a one-line capability — "Fit and visualize oriented Gaussians for volume reconstruction" — with nothing about the thing that actually makes them interesting: they are how Luxar does scalable volume rendering of volumetric and timelapse data. A reader landing on the header had no way to know a multi-gigabyte light-sheet stack or a 400-timepoint movie fits in a browser.
What changed
A new Volume Rendering with Gaussian Splats section (after the Gallery, linked from the lede and the capability table):
Voxels vs. fitted Gaussians — why 3D-texture ray-marching does not survive modern microscopy, and a size table from the two fits bundled in this repo.
Emission and absorption — the volumetric mode as the Max 1995 emission–absorption model in closed form, the absorption knob κ from 0 (bit-identical to additive) to a dense medium, and orientation-consistent absorption.
Timelapses are one dataset — per-timepoint 3D fits stacked onto a time axis in a single .gsplats.zarr, barrier-first chunking, time/channel as hard coarsening barriers with per-group mass conservation, and batch-fit run / batch-fit submit.
Scaling — the six LOD recipes, prefix-optimal streaming ladders, viewport-relative coverage_fraction selection, and the cal → fit → lod pipeline.
Photogrammetric interop — the five import dialects.
The lede gains a "volume rendering, without the voxels" paragraph; the capability table trades one gsplat row for three linked ones.
Numbers are measured, not asserted

Correctness notes
Claims were checked against the code rather than written from memory, which caught four things worth flagging:
No cross-fade claim. BLENDABLE_MODES is {additive, luminous}, so volumetric level switches do not cross-fade. The wording says level switching "self-calibrates" and stops there.
No joint 4D fitting claim. The shipped path is per-timepoint 3D fits stacked with σ_t = 0, not learned space–time Gaussians.
flat has no ladder, so the streaming-ladder default is scoped "apart from flat".
κ interpretation is framed as interpretive ("interpretable as turbidity"), not as a validated physical calibration.
Drive-by fix
The add_points example listed "normal", "additive", "max". There are six modes (additive, volumetric, normal, max, opaque, luminous) and the default is additive.

* docs(readme): correct four inaccuracies in the volume-rendering section

Follow-up to #672. A verification pass over the merged section found four
claims that do not survive checking against the code and artifacts.

1. "about 10 bytes per splat" was attached to BOTH bundled fits. Measured:
   Tribolium 10.31 B/splat, but C. elegans 13.12 B/splat — its 400 nested
   per-timepoint zip containers add overhead. Scoped the figure to the
   single-file Tribolium fit.

2. The cited paths `demos/data/gsplats_tribolium/` and
   `demos/data/gsplats_celegans/` do not resolve from the repo root; the
   real prefix is `packages/luxar/src/luxar/`.

3. "any prefix is the best L² approximation of the whole" overclaimed the
   streaming ladder. The default ordering (`auto`) resolves to `greedy` —
   itself only (1-1/e)-optimal — at N <= 5000, and to `self_energy` above
   it, which lod/README.md marks prefix-monotone "sometimes", guarantee
   "no", trailing greedy by 2-10% AUC. Every dataset discussed in that
   section is well above 5K splats, so the default is never the optimal
   ordering. Reworded to what is actually true.

4. "renders in any WebGL2 browser" contradicted the README's own
   Requirements note ("Touch/mobile devices are not currently supported").
   Now "any WebGL2 desktop browser".

Also disambiguated "additive/luminous (pure emission, the default)" —
only additive is the default.

* docs(readme): broaden the opening to the whole system

The opening undersold Luxar. It described the project as point clouds, lines
and splats, then spent a full paragraph on Gaussian-splat volume rendering —
so a reader met one capability up close and the rest not at all.

Rewrites the lede around what Luxar actually is: a compiler plus a GPU viewer.
It now states the model (describe a scene in Python, compile to a chunked,
spatially indexed Zarr archive, stream and render it) and then the three ideas
that carry the design — compile-don't-load (space-filling-curve ordering,
~64 KB chunks, view-intersecting fetch), n-dimensions-as-first-class (named
axes with units, nD slicing, sliders), and represent-don't-rasterize (volumes
fitted to Gaussians). The volume-rendering pitch is folded into the third
point; the dedicated section below still carries the detail.

"Why Luxar?" no longer restates the lede: it explains what moving work out of
the interaction loop buys, and what the one archive can be served from.

Key Capabilities was three-eighths gsplat rows. Regrouped to cover the system:
three geometries, nD, scale/LOD/streaming, volume rendering, appearance
(HDR/bloom/tone mapping/colormaps/six blending modes), the cal-fit-lod
pipeline with CUDA and cluster fitting, classical-3DGS interop, and export.

Every added claim verified against the code: 64 KB from TARGET_CHUNK_BYTES,
Hilbert/Morton ordering, colorcet+matplotlib registry, bloom post-processing,
six-mode enum, five import dialects, native export targets. Anchors checked
with github-slugger; PyPI long_description still renders.

* docs(readme): fix two overclaims in the broadened opening

Self-review of the previous commit found two claims that don't hold.

1. "every non-displayed axis becomes a slider" — dimension-sliders.ts:301-320
   routes binary categoricals to a TOGGLE and 3-9 categories to a DROPDOWN;
   only the remainder (including all discrete-numeric axes) get a slider.
   Now says "a navigable control — a slider, or a toggle or dropdown for
   categorical axes".

2. "a double-clickable native macOS/Linux app" — only macOS produces a
   double-clickable .app; Linux produces a portable folder
   (docs/tutorials/distributing_scenes.rst:16,109-114, and the README's own
   CLI reference already said ".app / portable folder"). Split the two.
