From my experience (By pr #318), voxelization can be viewed as a sparse hashing problem. Getting the sparse index can be solved by torch.unique at the complexity of O(nlogn), while the hash-reduce part can be implemented by atomicMax at the complexity of O(n). Just like the implementation in Apollo: https://github.com/ApolloAuto/apollo/blob/master/modules/perception/lidar/lib/detector/point_pillars_detection/preprocess_points_cuda.cu
From my observation, this part is the performance bottleneck for many lightweight detectors on many datasets. For example the CenterPoint with pillar encoder on NuScenes dataset:
https://github.com/open-mmlab/mmdetection3d/blob/d1123084973dd3a910760e77c499afad76d16cea/configs/centerpoint/centerpoint_02pillar_second_secfpn_4x8_cyclic_20e_nus.py
I managed to reimplement this part and it can reduce the training iteration time by more than a half, a huge improvement.
I also understand that your implementation is designed for determinism. Because hard voxelization involves points/voxels discarding, the ordering between points matters so that we could guarantee that always to discard the same portion of input points. In your implementation, the former points/voxels take precedence over the latter ones when discard points, thus your implementation is deterministic.
My reimplementation is non-deterministic because the hash-reduce kernel may be executed in any order, with no ordering between input points at runtime. Different runs for the same data can result in different portions of points being discarded.
If you think the performance gain is worth more than keeping the determinism, then my reimplementation is ready for PR.
Looking forward to your reply!

ic, yeah. additionally, scatter-reduce can also be implemented in PyTorch easily (at least for mean / sum)
```
# The following code are copied from pytorch_scatter https://github.com/rusty1s/pytorch_scatter
# Copyright (c) 2020 Matthias Fey <matthias.fey@tu-dortmund.de>
# MIT License 
from typing import Optional, Tuple
import torch 

@torch.jit.script
def broadcast(src: torch.Tensor, other: torch.Tensor, dim: int):
    if dim < 0:
        dim = other.dim() + dim
    if src.dim() == 1:
        for _ in range(dim):
            src = src.unsqueeze(0)
    for _ in range(other.dim()-src.dim()):
        src = src.unsqueeze(-1)
    src = src.expand_as(other)
    return src

@torch.jit.script
def scatter_sum(src: torch.Tensor, index: torch.Tensor, dim: int = -1,
                out: Optional[torch.Tensor] = None,
                dim_size: Optional[int] = None) -> torch.Tensor:
    index = broadcast(index, src, dim)
    if out is None:
        size = list(src.size())
        if dim_size is not None:
            size[dim] = dim_size
        elif index.numel() == 0:
            size[dim] = 0
        else:
            size[dim] = int(index.max()) + 1
        out = torch.zeros(size, dtype=src.dtype, device=src.device)
        return out.scatter_add_(dim, index, src)
    else:
        return out.scatter_add_(dim, index, src)

@torch.jit.script
def scatter_mean(src: torch.Tensor, index: torch.Tensor, dim: int = -1,
                 out: Optional[torch.Tensor] = None,
                 dim_size: Optional[int] = None) -> torch.Tensor:

    out = scatter_sum(src, index, dim, out, dim_size)
    dim_size = out.size(dim)

    index_dim = dim
    if index_dim < 0:
        index_dim = index_dim + src.dim()
    if index.dim() <= index_dim:
        index_dim = index.dim() - 1

    ones = torch.ones(index.size(), dtype=src.dtype, device=src.device)
    count = scatter_sum(ones, index, index_dim, None, dim_size)
    count.clamp_(1)
    count = broadcast(count, out, dim)
    if torch.is_floating_point(out):
        out.div_(count)
    else:
        assert 0 
        # out.floor_divide_(count)
    return out
```
I am actually not sure if we really need hard voxelization. I feel dynamic is both faster + simpler (we can probably do discarding of more voxels later)

@Tai-Wang
I have some more suggestions for dynamic voxelization. I suggest to devide the dynamic scatter op into 2 parts, one for indexing and the other one for scatter-reduction.
Dynamic voxelization, as what @tianweiy just pointed out, as a whole can be devided into 3 parts:
Calculating Coors: Calculate the target position coors in the voxelized tensor for every point. This part can be shared for both hard/dynamic voxelization
Indexing: Calculate the result non-empty coors set and the routing information between each entry of points and coors. The indexing result is used to guide the following scatter-reduction. torch.unique shall be used here.
Scatter-Reduction: Dump the pointwise features to the voxelized features and do the reduction on the fly. torch_scatter.scatter or equivalent ops shall be used here.
The core thought is, the "Scatter-Reduction" itself does not cost much time according to my observation, but "Indexing" does. torch.unique is the most computationally expensive op among the three.
Currently, in MMDet3D's implementation, the first part is the dynamic_voxelization, while the latter 2 parts are packed into dynamic_scatter. For some use cases where we have to repeatedly do the scatter-reduction for features that belongs to the same point cloud, we have to use dynamic_scatter multiple times, which means we have to do the "Indexing" part multiple times, which is wasteful.
All voxel encoders that use dynamic_scatter to get cluster centers features waste time on the redundant Indexing. An extreme use case is pillar-od, where we need both cluster centers (1st scatter-reduce) and covariance matrices (2nd scatter-reduce) for both BEV and cylindrical views, and we still need one final scatter-reduce for DynamicPillarFeatureNet before backbone -- 4 redundant indexing in total if we use dynamic_scatter.

Hi — this issue ended up being directly relevant to some deployment work I’ve been doing, so I wanted to share a result that may be useful upstream.
I recently released LaserPerception v0.1.0, and during deployment profiling I hit the same deterministic hard-voxelization bottleneck discussed here.
I first tested the faster deterministic=False path. It was dramatically faster, but on saturated voxels it retained different point subsets. Those differences propagated into observable detector-output variation, so I rejected that path for the production runtime.
I then implemented an alternative that preserves the official deterministic hard-voxelization semantics exactly.
Approach
The implementation uses the existing dynamic voxel-coordinate CUDA operation, followed by GPU/PyTorch tensor operations to reconstruct the deterministic hard-voxel output:
preserve every point's original input index
construct an explicit ordering from voxel coordinate + original point index
group points by voxel
preserve original point order inside each voxel
order output voxels by each voxel's first occurrence in the original input
retain the first max_num_points points per voxel
preserve first-encountered max_voxels behavior
preserve invalid-point rejection and zero-filled unused slots
It uses no custom CUDA/C++, no TensorRT plugin, and does not use deterministic=False.
Exactness validation
Against the official deterministic implementation:
81/81 nuScenes mini_val samples were bit-exact
exact voxels
exact coors
exact num_points
exact voxel ordering
exact within-voxel point ordering
exact zero padding
I also ran a frozen 20-sample detector suite:
20/20 exact raw TensorRT outputs
20/20 exact final detection values
The acceptance criterion was bit equality rather than a numerical tolerance.
Performance
On representative full-history nuScenes inputs on an RTX 4060 Laptop GPU:
Workload
Official deterministic hard layer
Exact implementation
W1
238.9 ms
1.76 ms
W2
261.9 ms
1.92 ms
That is approximately 136x at the hard-voxelization layer boundary for those measured workloads.
For context, the W1 direct live detector path in the same diagnostic work fell from roughly 333 ms to 43 ms, but that is a different boundary and should not be interpreted as a 136x end-to-end inference speedup.
These timings are measurements from the RTX 4060 Laptop GPU, WSL2, and project environment used for that diagnostic session, not portable performance guarantees.

A follow-up from the downstream LaserPerception work: I eventually exercised the deterministic hard-voxelization contract on a substantially denser foreign input domain (KITTI Raw, 64-beam LiDAR, multi-sweep accumulation), and it exposed two useful behaviors.
First, the upstream voxelizer contract allowed max_voxels=40000, while my TensorRT deployment profile only accepted 30,000. On the frozen KITTI corpus, 218/428 H10 frames exceeded 30k and 68/428 reached the 40k cap. That was enough to make the original deployment fail before network execution. I ended up treating the TensorRT profile as part of the same structural input contract and rebuilt only its maximum shape to 40k.
Second, I instrumented which sweep first created every retained/discarded pillar. Across 124,696 discarded H10 pillars, all were first touched by the three oldest sweeps:
sweep 8: 5,165 (4.14%)
sweep 9: 48,096 (38.57%)
sweep 10: 71,435 (57.29%)
No pillar first touched by the current scan or sweeps 1–7 was discarded. So the deterministic “earlier input wins” semantics discussed in this issue produced a measurable recency-protection effect under saturation.
I also preregistered a test for whether the 40k cap was the main reason detector recall degraded cross-domain; the result did not support that as the primary corpus-wide explanation.
The full cross-domain write-up and exact evidence hashes are in the project technical note. I thought the first-touch retention result in particular might be relevant to the original determinism discussion here.
