Problem Statement
The backend architecture and performance of godot_voxel are exceptionally powerful for handling smooth volumetric terrains and procedural generation at runtime. However, there is a major workflow bottleneck for level designers: the lack of an out-of-the-box, user-friendly native editor dock for sculpting, cave carving, and texture painting directly inside the Godot editor.
Currently, achieving any kind of interactive, manual level-editing workflow requires developers to write complex custom editor scripts from scratch (handling raycasting, voxel tool modifications, history/undo stacks, and viewport input mapping). This creates a massive barrier to entry for developers who want to build detailed open worlds featuring both realistic exterior landscapes and true underground cave networks natively in Godot, without being forced to rely purely on code or external DCC tools like Blender.
Proposed Solution
Introduce a native, polished editor dock/plugin integrated into godot_voxel that provides standard, artist-friendly brush tools right inside the Godot 3D viewport.
Key features desired for this editor toolset:
Brush Modes:
Add / Sculpt: Raise and build up terrain.
Remove / Carve: Dig into the terrain to form true horizontal tunnels, overhangs, and closed cave systems.
Smooth / Flatten: Clean up rough voxel geometry.
Texture Painting:
Direct splatmap/material painting on smooth voxel surfaces using MODE_TEXTURE_PAINT or equivalent, allowing seamless blending of rock, grass, and dirt layers without destroying geometry.
Brush Controls:
Adjustable radius, strength/opacity, and falloff settings.
Dynamic shortcuts (e.g., scroll wheel for sizing, hotkeys for mode-switching).
Undo / Redo Integration:
Built-in history stack (e.g., up to 20 steps via Ctrl+Z / Z) to safely test edits without risking destructive mistakes.
And more...
Alternatives Considered
Heightmap-based solutions (like Terrain3D) offer gorgeous native editor UI and painting docks, but are mathematically locked to 2.5D grids and cannot form true caves or overhangs.
Writing custom editor scripts from scratch is inefficient and fragments the community, as every developer ends up reinventing basic sculpting wheels.
Conclusion
Having an official or semi-official native editor toolset would instantly bridge the gap between godot_voxel's elite performance backend and a true, production-ready AAA world-building workflow in Godot.

It sounds like you either have set these bounds yourself, or that your VoxelViewer is not moving so you reached the edge of the loaded area. When you move around you're supposed to move the viewer too (usually child of the player) so terrain far from you unloads and new chunks get loaded. This is streaming, and as I mentionned earlier, it is one thing that can make your idea of making a voxel terrain editor quite harder than it sounds depending on what your expectations are.
As for texturing you have to use a custom shader, as indicated in the docs and shown in the demo project.

Like
soooo
many
people before you, you're hitting what the doc is trying to explain: https://voxel-tools.readthedocs.io/en/latest/api/VoxelTool/#i_grow_sphere
So here is yet again an explanation: this function was contributed but has caveats because it makes assumptions on how voxel data is generated. The way it works is to add/subtract values to SDF. So the bigger the SDF value, the longer it takes for surface to move. However, default generators clip SDF away from the surface to speed up calculations and save memory, which leads SDF to jump to high constant values beyond some distance. This has no impact on min/max operations and is usually fine in some games, but grow_sphere specifically gets messed up by it, slowing it down a lot unexpectedly in areas where SDF got clipped. If you really want to use that function you have to use a generator that doesn't optimize away SDF values and configure it so that it never clips SDF this way. Because this means storing accurate SDF everywhere, that will impact performance and memory usage.
