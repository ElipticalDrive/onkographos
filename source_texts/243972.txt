Vendored nianticlabs/spz, creating a reader and writer for the .spz compressed 3D gaussian splat format.
Each point in a .spz file must contain the following attributes:
```
- XYZ position
- XYZ scale
- XYZW rotation
- RGB colors
- opacity
- 0/9/24/45 spherical harmonics
```
I've tried to bake in interchange to/from PLY, which is the standard format for storing uncompressed gaussian splats; most attributes, other than XYZ positions and RGB/Alpha, are assigned to proprietary dimensions that use a PLY naming convention (like f_rest_* for spherical harmonics). Dimensions which correspond to these naming conventions are expected to be present in the writer -- if not, it writes zeroes.

I didn't spend that much time with the writer.
My general thought is that this should all use UnpackedGaussian. When you read, call unpack() and work with the unpacked data. This eliminates the need to copy the "unpacking" code from the library.
I would do the same when writing. Currently all the points are in the "cloud" at once, then they are packed into another data structure when saveSpz is called. It's a ton of data duplication. In the write case there is no interface for UnpackedGuassian. I would make one and make a PR against the SPZ library. That way you can just fill up the UnpackedGaussian for each point and then add it to the cloud through a pack() call or some such. The worst that can happen is that they don't want the PR and then you just use that internally.
Also, In the existing writer code, there are calls to unpackXXX which I don't think belong. When writing, you'd be packing, not unpacking, but I'm pretty sure that's happening in the library when you call saveSpz anyway -- see saveSpz and packGaussians. I'm guessing this doesn't currently pass a round-trip test.
