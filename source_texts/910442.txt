Why Einsum is decomposed rather than lowered per-exporter
Einsum was absent from all four hand-written backends, and it is most of what an attention, MLP or NeRF graph is made of — PyTorch emits it for linear layers, attention projections and ray/sample contractions. Teaching three translators the op would mean three copies of the same logic.
Instead onnxsim/einsum_decompose.py rewrites it once, at the ONNX level, on the way into each exporter:
```
Einsum(bnc,cd->bnd)  ->  MatMul              # already in matmul order
Einsum(bij,bjk->bik) ->  MatMul              # shared batch axis
Einsum(mj,nj->mn)    ->  Transpose, MatMul
```
The rewrite is exact: ONNX MatMul computes A[batch,m,k] @ B[batch,k,n], which is by construction the einsum's own output order, so no output-side transpose or reshape is ever needed, and an operand already in matmul order contributes no Transpose.
It is deliberately narrower than a general einsum optimizer. Traces, diagonals, outer products, scalar reductions and per-axis broadcasts (a batch axis only one operand carries) are left exactly as they were, so the exporter still raises its usual "unsupported op" error naming the op — never a silently wrong model, which is the property these exporters are built on.
Two implementation notes worth reviewing
MIL's gather_nd does not match ONNX's GatherND on NCHW. It indexes the tensor's leading axes and moves the trailing (non-indexed) axis to the end. The Core ML GridSample therefore samples through a channel-last view of x; the result comes back (N, flat, C) and is restored to ONNX's NCHW order with one transpose and one reshape, both pure metadata. Core ML's MIL has no native grid-sample op.
Core ML GridSample requires a compile-time-constant grid and static output dims, since MIL ops carry static shapes. It raises a clear error rather than guessing when those don't hold.
Verification
Einsum — 7 lowered and 10 refused equations, each numerically compared against onnxruntime (max_abs_diff = 0).
GridSample — the emitted MIL graph is replayed op-by-op in numpy and compared against ONNX's own reference across 7 configurations: 2-D and 3-D, bilinear and nearest, zeros and border padding, and both align_corners settings. Grids deliberately sample outside [-1, 1] so the padding path is exercised.
No regressions — the full non-hardware suite was run with and without this change; the failure sets are byte-identical. The pre-existing failures are missing optional deps in this environment (onnxscript, onnxruntime extras) plus a coremltools build missing libmilstoragepython, and are unaffected by this PR.
Known limitation (deliberate)
Per-axis broadcast einsums (bnc,cd->bnd) are refused even though MatMul would broadcast them correctly. This follows the vendored optimizer's existing behavior and keeps the rewrite to equal-rank operands, which the exporters' matmul paths are best tested on. Happy to relax it if you'd rather have the extra coverage.

Share one GridSample plan between the Core ML and TFLite exporters
…

```
The Core ML GridSample lowering added for NeRF-shaped graphs recomputed, from
scratch, exactly the arithmetic the TFLite exporter already had: mapping
normalized grid coordinates to source pixels, picking the neighbouring
corners, and weighting them. Two copies of the same numerics, free to drift
apart and to disagree with ONNX's own reference implementation.

Neither target has a native grid-sample kernel -- Core ML's MIL has no such op
and TFLite's converter has no ONNX translation for one -- so both lower it
themselves as corner `gather`/`gather_nd` taps plus elementwise weighting.
That arithmetic is pure numpy and target-independent; only the emission
differs. Lift it into `onnxsim/gridsample_plan.py`, which reduces a GridSample
to the list of taps (gather indices, bilinear weight, out-of-range mask), and
have both exporters lower that one plan:

- Core ML now emits MIL ops straight from the plan and no longer derives
  coordinates or corners itself.
- TFLite's `_numpy_grid_sample` -- the reference used for const-folding and
  for the numeric tests -- becomes a thin evaluator over the same plan.

The rewrite is behaviour-preserving: `_numpy_grid_sample` still matches ONNX's
GridSample across 2-D/3-D, bilinear/nearest, zeros/border and both
`align_corners`, now from the shared plan, and the plan itself is additionally
checked against ONNX applied independently of either consumer. Four new tests
cover the plan directly and assert the two exporters keep sharing it.
```

One finding worth flagging: torch emits bsf,fc->bsc for a NeRF-style RGB projection, and that form is refused by the decomposer — operand 2 carries no batch axis. It's left as Einsum, so an exporter still reports it as unsupported rather than mis-lowering it. The test asserts that refusal explicitly so it's a documented decision rather than a silent gap. Relaxing it would mean broadcasting a weight matrix against a per-sample tensor, which the exporters' matmul paths are least well tested on.
