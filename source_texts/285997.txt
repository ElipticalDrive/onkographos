Slight speed improvement using matrix operations to calculate metaball contributions to the bounding volume.
I kept the axis parameter on the torus because I found it convenient to have the torus start aligned a particular way before applying rotation. axis parameter has been removed.

By the way, here's the integral for the cone-shaped metaball, with the "wire" of length L going from $z=-L/2$ to $z=L/2$. If $r_1$ and $r_2$ are the radii of the cone ends, the radius interpolation along the length of the wire would be
$r(z) = \frac 1 2 (r_1+r_2) + \frac z L (r_2-r_1)$
The field contribution at point $(x_0,z_0)$, with an influence of 1/p, is
$\int_{-L/2}^{+L/2} r(z)\left[x_{0}^{2}+\left(z_{0}-z\right)^{2}\right]^{-p/2} dz$
Wolfram Alpha doesn't want to solve it.

The simplest and most elegant solution is to pass _origin as a hidden parameter and use it if it's defined. isosurface() needs to know an origin regarless, so it uses either the one for the bounding box supplied, or calculates it from the center of the box implied by the array. So it already has a notion of "origin". If a private _origin argument is defined, it would just use that.
Each voxel that contains the surface is a data structure that includes an x,y,z coordinate among other things, and that coordinate is determined by the origin of the bounding box.
In the case of metaballs, a bounding box must be specified, but that can't be passed into isosurface() when passing an array, so it would be cleaner to pass the origin of the bounding box as a private argument. isosurface() needs an origin anyway to work, whether it calculates one or receives one.
I've just made this change, which eliminated a handful of lines of duplicate code, and also eliminated the need to dereference vnf to move the coordinates in it.

Earlier timing tests were using the wrong version of code without the matrix operation to build the fieldarray. Now using the correct version.
Timing tests (approx average of 5 runs each case), using Example 1.
Case 1. This is my baseline, and takes 4.4 seconds to execute.
```
function mb_shaping(r, coeff, cutoff, influence) =
    sign(influence) * 0.5*(cos(180*(r/cutoff)^4)+1) * (coeff/r)^(1/abs(influence));

function _mb_sphere(dv, coeff, cutoff, influence) =
    let(r=norm(dv)) r>=cutoff ? 0
    : influence != 1 ? mb_shaping(r, coeff, cutoff, influence) : coeff/r;
```
Case 2. Moving the r>=cutoff and influence==1 checks into mb_shaping(), execution time increased to 5.0 seconds.
Case 3. Removing the check for influence==1 and just letting it calculate, execution time increased to 5.6 seconds.
Case 4. Moving the r>=cutoff check back into mb_sphere and letting mb_shaping() calculate: 5.5 seconds (one trial was 5.6 but average was 5.5).
Case 5. Bypassing mb_shaping() altogether and putting everything inline in mb_sphere: slightly under 4.4 seconds, negligible difference from "baseline".
This is all with influence=1. If I set influence=1.1 for all 5 balls in Example 1, the execution time for the baseline case becomes about 5.7 seconds, comparable to case 3 and 4 (because the cos x^4 function is being calculated every time).

I'm not aware of any OpenSCAD lint. I also think that OpenSCAD style is not something that has been much discussed nor that there is much agreement on. The BOSL2 project is pretty big and Revar and I have probably written more OpenSCAD than most people.
I don't see anything wrong with writing something like
```
foo = f(
        a,
        b,
        c,
       )
```
which sounds like what you said about using an parentheses as an opening brace, args on separate lines, and closing paren by itself. No problem at all, with one condition. The indentation must be correct to make it clear that the args are subsidiary to the f. So the above is fine. I will note that a downside of organizing a let statement this way is that it makes it harder to manipulate the let block, like to add an assert above it, or move it somewhere, so I'd say it's somewhat less convenient. But this is nevertheless perfectly readable and fine. And this is ok:
```
longreturnval = f(
                  a,
                  b,
                  c,
                )
```
and this is OK:
```
longreturnval =
  f(
    a,
    b,
    c,
  )
```
but this is NOT ok because the indentation fails to expose the relationship between the arguments to f and the code properly.
```
longreturnval = f(
    a,
    b,
    c,
  )
```
The arguments are at a lower level than f so they need to be indented more than f to reveal this relationship visually. (I wouldn't do this in C code either.) As long as you follow a style where this holds, I'm going to be able to read your code. The reason I couldn't read the code was that the indentation didn't obey the requirement that things at a lower level were indented more, and things at the same level were indented the same. So if you follow that rule, I think even if you don't exactly follow my style, I'll be able to read your code and it shouldn't be a problem. So two clauses of a conditional (with ?:) should generally be indented the same because they're at the same level, and they should both be indented more than the parent they are being assigned to, for example. Computations in a for should all be indented more than the for.
I do sometimes put the let on the same line. And then my code looks like this:
```
longreturnval = let(
                     a=3,
                     b=4
                )
                a+b;
```
The assignments are lower level than the let so they have to be indented more.
And would not write C like this where I follow a close brace with code. I find it confusing and the code is at the wrong level of indentation.
```
if (i==0) {
   a=3;
   b=4;
} d=a+b;
```
And similarly I don't write OpenSCAD that way like this:
```
let(
      a=3,
     b=4
) a+b;  
```
But this choice is only confusing if there the code is complicated and there's a chain of conditions or the a+b is something big and ugly.
With regards to distance I'm not sure I know exactly what the right answer is. You could try things and test.
If I gave you a function f(dv) that I said computes a distance that we can use to make a metaball, but I refused to divulge how it worked---it's a black box---how would you use it to create a metaball function?
What if I gave you a black box function g(dv) that I said computes a 1/r decaying metaball function with some interesting geometry and I again refuse to divulge any details and you need to make a cutoff for it. How would you do that? I suggest that this second case is the situation, and the expression coef/(1+dist) is that returned distance.
Is the cutoff supposed to be relative to the origin or relative to the object's border? It might be the case that we should be using dist+<object size> somehow in cutoff.
The "coef" that appears in revshift is an adjustment to correct for the fact that I undersized the shape so that I would get rounding. That is, it's not what determines the size. It is connected only to the amount of rounding.
Ultimately the proof is in the testing: have you tried your implementation as it is to see if the cutoff appears where you expect, or reasonably so? Did we err in deciding to make cutoff relative to the computed geometry's distance instead of just absolute distance?

function _mb_cuboid_basic(dv, inv_size, xp, neg) =
   let(
       dv=inv_size * dv,
       dist = xp >= 1100 ? max(v_abs(dv))
                         : (abs(dv.x)^xp + abs(dv.y)^xp + abs(dv.z)^xp) ^ (1/xp)
      ) neg/dist;
function _mb_cuboid_influence(dv, inv_size, xp, ex, neg) = let(
    dv=inv_size * dv,
    dist = xp >= 1100 ? max(v_abs(dv))
                      :(abs(dv.x)^xp + abs(dv.y)^xp + abs(dv.z)^xp) ^ (1/xp)
) neg / dist^ex;
function _mb_cuboid_cutoff(dv, inv_size, xp, cutoff, neg) = let(
    dv = inv_size * dv, 
    dist = xp >= 1100 ? max(v_abs(dv))
                      : (abs(dv.x)^xp + abs(dv.y)^xp + abs(dv.z)^xp) ^ (1/xp)
) neg * mb_cutoff(dist, cutoff) / dist;
function _mb_cuboid_full(dv, inv_size, xp, ex, cutoff, neg) = let(
    dv = inv_size * dv,
    dist = xp >= 1100 ? max(v_abs(dv))
                      :(abs(dv.x)^xp + abs(dv.y)^xp + abs(dv.z)^xp) ^ (1/xp)
) neg * mb_cutoff(dist, cutoff) / dist^ex;

function mb_cuboid(size, squareness=0.5, cutoff=INF, influence=1, negative=false) =
   assert(is_num(cutoff) && cutoff>0, "\ncutoff must be a positive number.")
   assert(is_finite(influence) && influence>0, "\ninfluence must be a positive number.")
   assert((is_finite(size) && size>0) || (is_vector(size) && all_positive(size)), "\nsize must be a positive number or a 3-vector of positive values.")
   let(
       xp = _squircle_se_exponent(squareness),
       neg = negative ? -1 : 1,
       inv_size = is_num(size) ? 2/size
                : [[2/size.x,0,0],[0,2/size.y,0],[0,0,2/size.z]]
   )
   !is_finite(cutoff) && influence==1 ? function(dv) _mb_cuboid_basic(dv, inv_size, xp, neg)
 : !is_finite(cutoff) ? function(dv) _mb_cuboid_influence(dv, inv_size, xp, 1/influence, neg)
 : influence==1 ? function(dv) _mb_cuboid_cutoff(dv, inv_size, xp, cutoff, neg)

What happens if all values above 1e9 are clamped to 1e9? Nothing. Two adjacent corners of the voxel that large are simply made equal, and since they are above the isovalue, they're inside the surface anyway. If any other corner is outside the surface, 1e9 or larger would result in an interpolation causing the surface to be almost on top of the corner less than the isovalue.
Reason not to use 10^300 - requires investigation. The larger "infinity" is, the smaller a triangle can be, and I remember reading that there is a lower limit for a triangle size for an STL file to be used in other applications. I don't want a triangle to be a single point, which is what's liable to happen in an interpolation between 1e300 and 1. I don't remember what that limit is, but if "best practice" is to keep triangle legs longer than 0.000001, then the clamp should be 1e6. I suppose one thing that is different is I'm quickly scanning code I don't understand and you're looking at code you wrote and know well. I'm not sure I understand what you mean about "increase the previous indent for the next line". The way I see it, after you write an assignment, or open a function call, or anything that has semantic importance, you have two choices. You can continue on the same line. If you do that, you're obligated to keep the entire rest of the RHS of the assignment, functioncall, etc to the right of the equals, or opening delimeter:
```
very_long_name_that_is_too_long = pathmaxlonglongname^2 + anotherlongname
                                   - longname + f(longvariable)
                                   + anothervariable
```
Alternatively, you can decide that this is too far to the right and instead you write the entire content of the RHS starting on the next line, but only one level indented, so like this:
```
very_long_name_that_is_too_long =
  pathmaxlonglongname^2 + anotherlongname
     - longname + f(longvariable)
     + anothervariable
```
I apply this rule generally. Important code shouldn't be lurking at the end of a line after other commands. I think the only common case where I write two things on one line is a tight conditional assignment. This kind of indentation rule prevents that problematic situation because if for whatever reason you choose to put something important at the end of the line, the indentation makes it very clear that there was something important there: the eye scans up and hits that important something. When you combine statements onto one line but then only indent one level, the eye scans up and sees the first thing, which is actually irrelevant, a distraction from what is actually going on.
In OpenSCAD with conditionals I think you can do this:
```
very_long_name = condition ? answer1
                                               : answer2
```
but if that is awkward, then
```
very_long_name = condition
     ? answer1
     : answer2
```
is a good choice. The leading ? makes it very clear you're looking at part 1 of a conditional, and the indentation makes it clear that everything there is connected to the computation of very_long_name. It's also legit to write
```
very_long_name = condition ? answer1 : answer2
```
but if you write
```
very_long_name = condition ? answer1
:answer2
```
it now appears that answer2 goes with some higher conditional somewhere. It would be like C code that said:
```
    if (condition) a=3;
else a=9;
```
because the "else" (or in Openscad the colon) is indented left of the condition. It would even be OK to write
```
very_long_name=
  condition
  ? answer1
  : answer2
```
Note that I'm not insisting that opening braces be alone by themself, the C equivalent to:
```
if (condition)
  { 
      a=3;
  }
```
That would be the OpenSCAD equivalent of
```
let
  (
    a=3;
  )
```
It's perfectly fine to put the opening paren up with the let.
I think it comes down to the question of, when reading unfamiliar code with unknown structure, is my eye drawn to the key things that define the structure or am I repeatedly surprised as I try to understand the structure, or am I so confused that I have no clue what the code structure is at all. Ideally I can see the structure in a single glance at 75 lines of code without having to really read the code.
