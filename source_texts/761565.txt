The XDG API has another ray query function xdg::closest(). This isn't strictly necessary for particle transport but the typical use case is in implementing reflecting boundary conditions within particle transport codes.
My current development efforts with the GPRTRayTracer does not implement a closest() function. The Embree equivalent is rtcPointQuery. As far as I can tell, this isn't a ray-driven algorithm so will probably need to be implemented via a compute shader in GPRT and bypass the ray tracing pipeline entirely? So this may be a bit more difficult than I first anticipated but still doable.

Doing some more reading on this, I am thinking that we will definitely have to bypass the RT pipeline entirely. Ideally, we reuse the same maths defined in closest.cpp and rewrite the code in a way that's portable between slang and C++ and it will be invoked via a compute shader.
As for actually traversing the BVH this unfortunately is a bit more complicated with a library built around an RT pipeline. I think the BVHs built for the pipeline are pretty opaque and can only be traversed via ray traversal calls. These are:
TraceRay() - Can only be called from inside the RT pipeline and enforces descending through the pipeline
RayQuery() - A method to perform ray traversal without a full pipeline (can be called from compute or fragment shaders)
So I think we may have to write our own methods for constructing a simple BVH structure as well as a traversal algorithm for the point queries too.
I'll need to do some more reading but we may want to explore implementing our own construction of an Linear BVH or Surface Area Heuristic BVH.
@pshriwise so if my understanding is correct potentially quite a lot more work than I initially thought.

As we discussed, it may actually be possible to abuse the ray traversal calls in such a way that allows us to perform the closest point queries. It won't necessarily be the most performant way of doing such operations but downstream use cases won't require xdg::closest() calls to be highly performant anyway.
Something similar to how tetrahedron point contain checks are performed will likely be the approach. Where a ray with a meaningless direction is passed to the ray traversal and we perform the closest check algorithm in place of the intersection shader?
