KICKOFF.md required a ~40 line reference SSIM implementation to be handed over and matched before writing ssim.ts. It was never provided during Session 1, so the shipped metric is a documented variant: non overlapping 8x8 uniform windows, partial edge windows included, population statistics, Wang constants, unweighted mean over windows.
The variant is internally verified (hand derived literals and an independent in-test reference agree to 1e-12; see packages/core/test/metrics/ssim.reference.test.ts) but it is not anchored to the standard 11x11 gaussian sliding window SSIM scale that published values use.
Two things must happen before M5 (the allocator):
If the original reference implementation still exists, run it against the pinned fixtures in ssim.reference.test.ts and reconcile any behavioral difference deliberately (GOVERNANCE.md: metric changes are never silent).
BRIEF section 3.4 sets hard floors at ssim 0.97 (global) and 0.99 (above the fold / LCP). Those numbers were written with the standard SSIM scale in mind. Recalibrate them against this variant empirically (the corpus, once it exists, is the right instrument) or switch the metric to the standard formulation and re-pin the reference tests.
From the Session 1 adversarial verification pass (finding: major).

Phase 1 calibration results (commit 8bb95ed): the 0.97 global and 0.99 above-fold floors are VALIDATED for the 8x8-window variant, no correction needed. packages/codecs-node/test/ssim-floor-calibration.test.ts encodes three seeded photo-like fixtures with sharp mozjpeg at q50-95 and measures both cupel SSIM and an in-test reference standard Wang 11x11 gaussian SSIM on identical encodes: the variant tracks the standard scale within 0.012 wherever readings exceed 0.96, is never more than 0.002 stricter, and the floor crossings land on identical quality-ladder rungs under both formulations on every fixture.
Two notes for the record:
The reference implementation this issue said was never delivered now exists inside that calibration test; if the shipped metric should ever switch to standard SSIM, that is the starting point.
Caveat: grain-heavy content never clears 0.97 at ANY JPEG quality under either formulation and collapses to keep-original by design. If the M8 corpus shows this biting too often on real photos, the fix is a policy discussion, not a metric rescale.
Leaving open for owner judgment on whether reconciliation with the original hand-written reference is still wanted; the M5 blocker portion is resolved.

Phase 2 wave A added two more calibration guesses in the same family as the floor recalibration tracked here, both in packages/core/src/decide.ts and exported so callers can see them:
LOW_HEADROOM_SSIM_MARGIN = 0.01. BRIEF 4.5 defines when headroom is low but names no margin; decideAsset implements low headroom as floor = min(1, baseFloor + 0.01).
RECOVERY_TOLERANCE.effectiveResolutionRatio = 0.05 (5% pixel-area band) for acceptRecoveredSource, alongside the 2-quality-point tolerance BRIEF 4.1 does document. Spectral effective resolution is noisy (headroom.ts calibration notes show 2x upscales measuring cutoffRatio 0.50-0.60 against truth 0.5), and the band applies to improvements and regressions alike so noise is never accepted as improvement.
Both need corpus calibration together with the SSIM floors when this issue is picked up (M8 real-photo corpus). Values are pinned by tests in packages/core/test/decide.test.ts.
