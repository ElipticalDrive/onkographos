Summary
This PR extends spin::BVH by adding a new policy BucketedLinearBVH which enables "buckets" of primitives to be grouped into the same leaf node of a LinearBVH. In an effort to keep the existing LinearBVH policy as unchanged as possible, this is accomplished by, at a high level:
Adding a new policy/template option to spin::BVH and removing overloads to as-of-yet unsupported methods via concepts.
Adding a new LinearBVHType template parameter to LinearBVH and LinearBVHTraverser and removing overloads to as-of-yet unsupported methods for bucketed leaves. Additionally, this template parameter:
When set to BucketedPrimitiveLeaves, an otherwise empty struct BucketLeafData in LinearBVH is populated with indirection arrays from buckets to primitives.
Provides a overload to LinearBVH::buildImpl which takes a max bucket size and grouping strategy. The work done in "Step 3: Emit the BVH` is factored out into a single function invoked by both overloads.
LinearBVH::getTraverser() constructs a host-only LinearBVHTraverser of the analogous type. The specialization LinearBVHTraverser<BucketedPrimitiveLeaves> is a wrapper to the LinearBVHTraverser<SinglePrimitiveLeaves> that converts a per-primitive leaf action into a per-bucket leaf action which applies the per-primitive leaf action to every primtiive in the bucket.
To simplify traversal through leaves, a new host-only traverse_leaves() method is provided which accepts a leaf-action callback which is indexed directly to the original primitive array. For single-primitive leaves, this is a single std::int32_t index, and for bucket-primitive leaves, this is an ArrayView<std::int32_t> which can be iterated through. The analogous reduce_tree() methods have been intentionally replaced with reduce_leaves(), as this is near-universally the more useful API for reductions, which rarely expect access to the underlying BVH storage arrays.
Refactoring methods in build_radix_tree.hpp to separate the tasks of 1) Initializing and sorting the list of Morton/Hilbert codes for each input primitive 2) Building the radix tree heirarchy from the list of sorted codes and propogating AABBs. With this refactor:
A bucketed BVH only needs to insert a step 1.5) which partitions the list of sorted codes into buckets. The first code in which becomes the representative fed into the tree construction. Currently this is done serially, but could be improved later.
Bucketed BVHs use the same fast construction algorithm as an ordinary BVH, as steps 1 and 2 are themselves entirely unchanged.
Bucket Grouping Strategies
We currently support two partitioning/grouping strategies:
- BucketedBVHGrouping::Sequential: Given a max bucket size of N, groups of N primitives are selected in order from the sorted list to form buckets. This is computationally efficient and minimizes the number of buckets, but may result in low spatial coherence, as bucketed primitives can have far-away spatial keys.
- BucketedBVHGrouping::SharedPrefix: Forms buckets based on shared prefixes in the list of codes. This will result in many "underfilled" buckets, but every bucket is guaranteed to have very high spatial coherence, as primitives must have a shared code prefix to be bucketed together.
Here's a visualization of what the two different grouping strategies look like for each of the different BVH orderings. As you can see, there is a tradeoff between bucket count and spatial locality between the two strategies.
Note that the shared-prefix strategy groups primitives in the same way they would be organized in higher levels of a single-primitive BVH, as the Kerras linear BVH also builds tree topology from shared prefixes.
