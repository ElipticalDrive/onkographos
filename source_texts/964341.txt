Member
MayaFlux's IO namespace has always been able to read industry-standard 3D formats (glTF, FBX,
OBJ, PLY, Alembic-adjacent volume formats via VDB) into live buffers, but writing them back out
was a much narrower door. This PR closes that asymmetry for spatial data: geometry with
materials, and time-varying particles, curves, and grid state.
Two tracks:
Mesh export (ModelWriter/AssimpModelWriter) now carries bound diffuse textures out to
disk, not just vertex data. A MeshBuffer, MeshNetworkBuffer, or ComputeMeshBuffer with a
texture bound via bind_diffuse_texture()/set_texture() gets that texture downloaded and
written as a sibling image, with the material pointed at it, whether the texture came from a
loaded file, a procedurally generated image, or a live GPU render target.
Spatial export (new SpatialCache/SpatialExport/SpatialTransfer) writes time-sampled
Alembic archives from particle networks, path/graph geometry, and
cellular-automaton/reaction-diffusion grid state, with full per-vertex color/normal/uv/tangent
data, correct point-vs-curve topology, and either a one-shot snapshot or a live, ticking capture.
Relevance
MayaFlux is a real-time engine: interactive, GPU-resident, built for things changing every frame.
Professional DCC tools (Blender, Houdini, Maya) are built for the opposite: offline lighting,
look-dev, compositing, and render farms. Neither replaces the other, and until now MayaFlux
couldn't hand its work to them at all.
This closes that gap in both directions the write side needs:
MayaFlux as a simulation backend. Run a Conway's Game of Life, a reaction-diffusion system,
a spring network, or a spatial-hash particle swarm live in MayaFlux, where it's cheap to iterate
on the rule and watch it evolve interactively, then capture the entire time-sampled evolution as
a single Alembic archive and hand it to Houdini or Blender for lighting, shading, and a real
render. The simulation logic lives where it's fast to develop; the pixels come from where the
renderer is.
Round-tripping geometry with its look intact. A mesh authored in Blender already loads into
a MeshBuffer with ModelReader, gets deformed, procedurally textured, or driven by a live
compute shader inside MayaFlux, and can now go back out with its diffuse texture attached rather
than as an untextured shell. What comes back into the professional tool actually looks like
something, not a lookdev restart.
Grid and particle state as a shared interchange format. Alembic is the format Houdini,
Blender, Maya, and Katana already agree on for cached simulation data. A RelaxationGridBuffer
automaton or a PhysicsOperator particle network now speaks that format directly, so MayaFlux
slots into an existing pipeline instead of requiring one to be built around it.
The read side of this stays deliberately asymmetric for now: SpatialCache is write-only, there
is no SpatialReader. Bringing an externally-authored Alembic cache into MayaFlux is a real
gap, tracked, not addressed here.
Features
SpatialCache (Alembic-backed, Ogawa archive): points, curves, arbitrary per-vertex attributes
as native Alembic GeomParams, with color and normal getting Alembic's own dedicated
OC3fGeomParam/ON3fGeomParam types rather than a generic vector, so an importer knows what
it's looking at.
SpatialExport: reads any GraphicsOperator's live vertex buffer directly as
Kakshya::Vertex records, no separate attribute-description machinery, so a stream never has
more or less than what the buffer actually holds. Topology-aware: a PathOperator writes one

Alembic: grid/automaton state (Conway's Game of Life)
RelaxationGridBuffer's snapshot signal only supports one listener, so RelaxationGridCapture never subscribes itself; it's
fed from inside the caller's own existing listener:
```
auto grid = std::make_shared<Buffers::RelaxationGridBuffer>(
    GRID_W, GRID_H, sizeof(uint32_t),
    "relax_conway_rule.comp", "relax_vertex_emit.comp") | Graphics;

auto grid_capture = make_persistent_shared<IO::RelaxationGridCapture>(
    grid, "conway", 1.0F,
    [](std::span<const uint8_t> bytes) {
        const auto* cells = reinterpret_cast<const uint32_t*>(bytes.data());
        std::vector<uint32_t> alive(cells, cells + (bytes.size() / sizeof(uint32_t)));
        return std::vector<IO::SpatialAttribute> { IO::SpatialAttribute {
            .name = "alive",
            .scope = IO::SpatialScope::Varying,
            .values = Kakshya::DataVariant { std::move(alive) } } };
    });

Kriya::on_signal(grid->snapshot_source(), [grid_capture](const std::vector<uint8_t>& bytes) {
    // whatever this listener already did with the snapshot, unchanged, plus:
    grid_capture->write_snapshot(bytes);
});

on_key_pressed(window, IO::Keys::C, [grid_capture]() {
    if (grid_capture->is_capturing()) {
        grid_capture->stop();
        return;
    }
    grid_capture->start("conway.abc");
});
```
Every generation of the automaton becomes one Alembic time sample carrying live/dead state as a named per-point attribute,
alongside the fixed grid positions. Opened in Blender, the whole run scrubs like any other point cache.
Testing
Exercised directly through the example scenes rather than unit tests, since this is fundamentally an "does the file mean
anything to another tool" concern:
CPU-only particle producer, time-sampled physics network capture, and GPU-authoritative readback capture, each verified by
loading the resulting .abc in Blender.
Color/normal/uv correctness verified independently by compiling a small standalone reader against libAlembic/libImath and
inspecting actual sample values rather than trusting the writer's own success return.
Curve topology (paths vs. graph edges) verified against a filament/web network that previously exported as a flat point
cloud.
Conway automaton capture verified end-to-end: archive finalization (an Ogawa file left open throws on read),
per-generation attribute variation, and the DX of feeding a capture from an already-existing snapshot listener without
touching RelaxationGridBuffer itself.
Mesh diffuse texture export verified against MeshBuffer, MeshNetworkBuffer (shared and per-slot), and ComputeMeshBuffer.

```
Closes the read/write asymmetry IO has for non-mesh spatial data:
particles, point clouds, and curve/edge topology that ModelWriter's
Assimp backend cannot carry meaningfully (confirmed empirically —
Assimp silently drops custom attribute names, node metadata, and
point/line topology on export). Alembic natively supports named
per-vertex attributes, time sampling, and object metadata, so it is
the backend for this data instead.

SpatialSample/SpatialAttribute deliberately reuse existing MayaFlux
vocabulary rather than inventing new type surface: attribute values
are Kakshya::DataVariant (float/vec2/vec3/uint32_t), and topology is
Portal::Graphics::PrimitiveTopology, scoped to reject the TRIANGLE_*
values ModelWriter already owns. SpatialCache::write() picks Alembic's
Points or Curves schema from the sample's topology, so the caller
never discusses Vulkan primitive topology at this level beyond setting
that one field.

A vec3 attribute named exactly "color" or "normal" is declared through
Alembic's dedicated OC3fGeomParam/ON3fGeomParam rather than a plain
OV3fGeomParam: those are MayaFlux's own fixed vertex field names, and
the dedicated type — not the value's shape, three floats either way —
is what tells an importer this is actually color or normal data.
Confirmed against Blender: it now lists "color" as a recognized color
attribute rather than a generic vector, though wiring a recognized
attribute into the viewport/shader is a separate Blender-side step
this doesn't touch.

SpatialExport packs a MayaFlux source's current state into one
SpatialCache::write() call. write_operator_sample() reads a
GraphicsOperator's raw vertex buffer as Kakshya::Vertex records
(PointVertex/LineVertex/MeshVertex all share its exact 60-byte

write_network_geometry_buffer_sample() resolves a NetworkGeometryBuffer's
driving network and picks CPU or GPU readback: a GpuFieldOperator
anywhere in the operator chain means the CPU-side GraphicsOperator
buffer is stale, so instead it downloads the live vertex bytes
straight off the buffer itself (it is a VKBuffer, same
download_from_gpu_async() pattern download_compute_mesh() uses for
ComputeMeshBuffer) and reads the same Kakshya::Vertex columns from
there, plus the declared hash_cluster_id state field as "cluster" when
present. Without a GpuFieldOperator, every GraphicsOperator on the
network (primary plus any chained) is CPU-readable and each is written
as its own set — one plain stream_name for a single operator, one
child stream per operator (named "<stream_name>_<get_type_name()>")

entries play for a multi-submesh ModelWriter export.

RelaxationGridBuffer's cells occupy, matched against its own emit
shaders, for feeding a POINT_LIST sample; cell state itself stays the
caller's problem since its format is rule-defined.

SpatialTransfer adds the session-level layer on top: SpatialCapture
records one or more SpatialCaptureSource entries into a shared
SpatialCache on the frame clock, the same GraphicsRoutine/FrameDelay
shape VolumeCapture uses, except every sample lands in one archive
Alembic keeps open rather than a numbered file per frame. Its stop()
only flags a stop_requested atomic and asks the scheduler to drop the
task without waiting for the coroutine to actually exit; everything
the coroutine touches lives in a separately reference-counted

destroyed the instant stop() returns never leaves a still-resuming
coroutine dereferencing freed memory. save_spatial_snapshot() is the
single-sample counterpart: open, write every source once, close.

curves, graph edges) are not implemented yet — GraphicsOperator has no
way to report its own render topology today, and neither operator's
vertex grouping (per-path contiguous runs vs. per-edge fixed pairs)
reduces to the same chunking rule, so this needs its own follow-up
rather than a quick branch here.

…rator

SpatialCache producers previously wrote every sample as POINT_LIST
regardless of source, silently flattening PathOperator's interpolated
strips and TopologyOperator's graph edges into unstructured point
clouds. Fixing this needed a way to ask "what primitive topology is
this vertex data actually for" that distinguishes a real answer from
silence, since GeometryWriterNode::get_primitive_topology() previously
had no way to tell "POINT_LIST because nobody said otherwise" from
"POINT_LIST because that is what this geometry is".

GeometryWriterNode::get_primitive_topology() is now backed by a real,
settable m_primitive_topology member (default POINT_LIST) with a
matching set_primitive_topology(), rather than a hardcoded literal in
the base class: a node's topology is now always a genuine answer, not
a silent fallback. PathGeneratorNode and TopologyGeneratorNode already
carried this exact pattern themselves (their own private member, getter,
and setter, defaulting to LINE_STRIP and LINE_LIST respectively); both
now set the inherited member in their constructors instead of
duplicating the mechanism. LineSegmentsNode and MeshWriterNode are
unchanged, still overriding get_primitive_topology() to a fixed value,
since nothing should be able to reconfigure what those two produce.

GraphicsOperator gains declared_topology(), returning nullopt only
when the operator holds no underlying node at all (a real ambiguity:
an operator with zero paths/topologies/collections genuinely has no
topology opinion) and otherwise the first node's own
get_primitive_topology(). PathOperator, TopologyOperator, and
PhysicsOperator each forward to their first path/topology/collection,
the same first-element choice get_vertex_layout() already makes for
the aggregate.

SpatialExport's write_operator_sample() and the GPU-authoritative
write_network_geometry_buffer_sample() path both branch on this: a
LINE_STRIP operator (PathOperator) run-length-encodes
build_cluster_ids() into one curve per contiguous path run; a
LINE_LIST operator (TopologyOperator) chunks into fixed 2-vertex
curves, one per expanded edge, since a graph's edges are independent
segments rather than one connected strip; anything else keeps the
original POINT_LIST behavior unchanged. Curve samples correctly carry
no ids/velocities (Alembic's Curves schema has neither) and fail
outright rather than guess if a LINE_LIST operator ever reports an odd
vertex count. write_operator_sample()/the GPU path also now read a
GraphicsOperator's raw vertex buffer as whole Kakshya::Vertex records
(position, color, scalar, uv, normal, tangent) instead of position
alone, since PointVertex/LineVertex/MeshVertex all share its exact
60-byte layout and Vertex's own doc already calls it pipeline-ready
for this.

SpatialCache gains glm::vec2 (OV2fGeomParam, for uv) and dedicated
color/normal GeomParam types (OC3fGeomParam/ON3fGeomParam, selected by
attribute name rather than a new type) alongside the existing
float/vec3/uint32_t support, since Alembic distinguishes a color or a
normal from a plain vector at the property type level, not by a
value's shape — without this, an importer had no signal that a "color"
attribute was actually color data rather than an arbitrary direction.
Confirmed against Blender: color now shows as a recognized color
attribute, and PathOperator/TopologyOperator sources now import as
actual curves rather than points.

feat(io): add RelaxationGridCapture, a single-consumer-safe grid capture
…
6b332b4
```
RelaxationGridBuffer::snapshot_source() is a single-consumer
BroadcastSource by its own documented contract: register_waiter()
unconditionally overwrites the waiter slot, so a second
Kriya::on_signal() listener on the same source silently orphans
whichever one registered first. A capture helper shaped like
SpatialCapture (subscribing itself) would have made that mistake
inevitable for any caller who also wants their own listener on the
same grid, which is the common case.

RelaxationGridCapture is a pure sink instead: start()/stop()/
is_capturing() manage a SpatialCache the same way, but write_snapshot()
is called by the caller from inside whatever snapshot_source() listener
they already own, rather than the class subscribing on its own.
Positions and ids come from the existing relaxation_grid_positions(),
computed once at construction and reused for every sample. The one
piece that can't be generic (turning a snapshot's raw bytes into
named attributes, since cell state format is rule-defined) is the
constructor's one caller-supplied callback. No changes to
RelaxationGridBuffer itself: everything here is built from its
existing public accessors.

```
IOManager::capture_spatial()/stop_spatial_capture() mirror
capture_volume/VolumeCapture: resolve a filepath to a shared
SpatialCache (opening it on first use, reusing it if another capture
already targets the same path), spawn a SpatialCapture, and track it

valid file behind: an Ogawa archive left open is not a valid file,
only a growing one. stop_spatial_capture() now reference-counts

last one stops, so an archive several captures still share stays open

archive.

close() can now run on whatever thread calls stop_spatial_capture(),

save_volume() already has, since save_spatial_snapshot() is Spatial's
one-shot counterpart. capture_spatial() and RelaxationGridCapture
deliberately get no Depot entry, matching capture_volume's own
precedent: a start/stop session doesn't fit a "pick a file, save

…
3228389
```
MeshBuffer, MeshNetworkBuffer, and ComputeMeshBuffer each carry a bound
diffuse VKImage, but save_mesh() never looked at it: AssimpModelWriter
only ever wrote a diffuse_path material property when one was already
present as a submesh attribute, true only for meshes round tripped
through ModelReader from a file. A texture bound programmatically or
produced on the GPU had nowhere to go.

save_mesh() for all three buffer types now downloads a bound texture
via the existing IO::save_image() and writes it next to the model file
as <model-stem>_diffuse.png, then sets that path as the diffuse_path
submesh attribute AssimpModelWriter already reads. A mesh with no
pre-existing submesh region gets one synthesized covering the whole
mesh, so the attribute has somewhere to live.

MeshNetworkBuffer additionally carries its own shared diffuse texture
independent of any per-slot MeshSlot::diffuse_texture. Its save_mesh()
overload packs that texture once and reuses the path across every slot
that has no distinct texture of its own; a slot's own texture still
takes precedence and gets its own sibling file.

ComputeMeshBuffer gained has_diffuse_texture()/get_diffuse_texture()
getters mirroring MeshBuffer's, since the field already existed but
had no reader.

The Alembic/SpatialCache export path is unaffected: the particle,
point cloud, curve, and grid data it reads from carries no bound
texture anywhere in the codebase, so there is nothing analogous to
pack there.
