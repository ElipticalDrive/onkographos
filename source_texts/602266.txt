Problem
Across #49-#53, this project has established that there is no single
"catch-all" optimization for the CPU-side stencil shadow-volume
construction (#48) -- each candidate technique has a genuinely different
content-shape sweet spot, and some are actively counterproductive outside
their target case:
Rendering/GLFF: investigate normal-cone bounding hierarchy to cull the per-frame shadow-volume triangle test #49 (normal-cone bounding hierarchy) -- general/mesh-agnostic, but
weak specifically on round/convex shapes (a flat 6-bucket cube
partition has ~54.7° cones, close to adversarial for a sphere).
Rendering/GLFF: investigate ring/segment-aware + binary-search silhouette culling for primitive (SphereMesh/CylinderMesh) shadow casters #50 (ring/segment-aware + binary search) -- strong for primitive
SphereMesh/CylinderMesh content with known regular topology, not
applicable to arbitrary imported meshes without equivalent metadata.
Rendering/GLFF: investigate a lower-poly shadow-volume proxy mesh (LOD) decoupled from render detail #51 (LOD/proxy shadow mesh) -- universally applicable, large
guaranteed win, but trades away silhouette precision -- not
appropriate for a caster whose exact shadow shape matters.
Rendering/GLFF: investigate direction-quantized precomputed silhouette tables for slow-changing light #52 (direction-quantized precomputed tables) -- strong when light
direction changes slowly/discretely, actively unhelpful (possibly
net overhead) for a caster that's rotating quickly, which is most of
this project's own current test content.
Rendering/GLFF: investigate temporal coherence (incremental terminator tracking) for the per-frame silhouette walk #53 (temporal coherence) -- strong for realistic/moderate rotation
speeds, needs an explicit correctness safety net for fast rotation.
Right now there is exactly one option: today's full per-triangle
algorithm (#48), applied uniformly to every shadow caster in every scene,
with no way for a content author to choose or override it per mesh.
Data collected from prior investigation
The full design conversation across #48-#53 (2026-09-09) -- see each
issue's own thread for the specific tradeoff analysis. No configuration
mechanism exists today; MeshInstance/GeometryInstance shadow settings
currently only expose Godot's stock cast_shadow enum (off / on / double-
sided / shadows-only), nothing about HOW the shadow geometry itself gets
computed.
Success criteria
A per-mesh (or per-GeometryInstance/MeshInstance) inspector-
exposed property selecting the shadow-volume optimization strategy
used for that specific caster -- at minimum an enum with a slot for
each of Rendering/GLFF: investigate normal-cone bounding hierarchy to cull the per-frame shadow-volume triangle test #49-Rendering/GLFF: investigate temporal coherence (incremental terminator tracking) for the per-frame silhouette walk #53 as they land, plus today's default.
Default must preserve today's exact behavior for anything not
explicitly configured -- no silent behavior change for existing
scenes/content when this lands.
The selection mechanism itself should be built so each strategy
"plugs in" independently as its own issue is implemented, rather than
needing this configuration surface redesigned every time a new
strategy lands -- i.e. it's fine (expected, even) to build this
BEFORE more than one real alternative strategy exists, so later work
only needs to register a new enum case + implementation.
In-editor guidance (tooltip and/or docs) helping a content author
actually pick the right strategy for their content shape and use
case -- per this whole investigation, the "right" choice is genuinely
content-dependent and not obvious without understanding the
tradeoffs each sibling issue worked out. Don't ship a bare enum with
no explanation of when to use which value.
Not considered fully valuable/done until at least one alternative
strategy beyond today's default actually exists and is wired into the
selector -- track this dependency explicitly. A one-option enum
technically satisfies criteria 1-2 but isn't meaningfully
"configurable" yet; don't close this as complete on that alone.
Prior progress
None yet -- this is the umbrella/integration issue tying together #49
and the four sibling technique issues (#50, #51, #52, #53) filed
alongside it. No configuration mechanism, no editor UI, no strategy
selection code exists yet.

Architecture: 3 independent axes, not 1 enum
Re-reading #49-53, each technique actually answers a different question:
Geometry source — which triangles get walked at all.
RENDER_MESH (default, today's behavior)
LOD_PROXY (Rendering/GLFF: investigate a lower-poly shadow-volume proxy mesh (LOD) decoupled from render detail #51) — lower-poly shadow-only stand-in mesh

for whichever geometry axis 1 selected.
FULL (default, today's unconditional per-triangle test)
NORMAL_CONE (Rendering/GLFF: investigate normal-cone bounding hierarchy to cull the per-frame shadow-volume triangle test #49) — flat 6-bucket clustering, general/mesh-agnostic
RING_SEGMENT (Rendering/GLFF: investigate ring/segment-aware + binary-search silhouette culling for primitive (SphereMesh/CylinderMesh) shadow casters #50) — only valid for primitive SphereMesh/
CylinderMesh content with known ring/segment topology; falls back to
FULL (or NORMAL_CONE if also selected... mutually exclusive with
NORMAL_CONE within this axis, pick one) when the mesh doesn't qualify
Temporal/caching layer — an optional wrapper deciding whether axis 2
even needs to run in full this frame.
NONE (default)
DIRECTION_QUANTIZED (Rendering/GLFF: investigate direction-quantized precomputed silhouette tables for slow-changing light #52) — precomputed bucket-snap lookup, best for
slow/discrete light changes
TEMPORAL_COHERENCE (Rendering/GLFF: investigate temporal coherence (incremental terminator tracking) for the per-frame silhouette walk #53) — incremental boundary tracking, best for
moderate real rotation speeds, with a mandatory correctness safety net
These three axes are independent and compose (e.g. LOD proxy geometry +
normal-cone algorithm + temporal-coherence caching, all at once) — this is
the actual mechanism behind "different combinations . per mesh."
Default combination (RENDER_MESH + FULL + NONE) is byte-for-byte today's

same non-negotiable requirement #54 already specified.

The pattern that emerged
Every technique that adds a new per-item coarse test on top of the
existing per-triangle work (#49's cluster check, #50's ring/trig check,
#53's reuse-or-retest check) shows a small but real, consistently
reproduced regression on this specific G4/PPC/RV250 target -- the
baseline exact per-triangle test (3 multiplies, 2 adds, 1 compare, no
indirection) is already about as cheap as a check can be on this hardware,
so almost any additional per-item decision logic costs more than it saves.
Every technique that instead reduces or skips work outright without
adding a new per-frame decision (#51's fewer triangles, #52's whole-frame
cache reuse) shows a large, real win.
This is a genuine, hardware-specific finding worth carrying into any
future GLFF perf work on this target: prefer "do less work" techniques
over "do the same work smarter" techniques here, specifically because this
CPU's simple float math is cheap relative to almost any branch/trig/
indirection you'd add to avoid it.
This issue's own scope
The composable 3-axis selector (shadow_geometry_source /
shadow_silhouette_algorithm / shadow_temporal_cache) is fully
implemented and working -- all 5 real techniques (plus their NONE/
FULL/Render Mesh defaults) are wired in and freely combinable per
instance, exactly as requested. The all-default combination remains
byte-for-byte identical to pre-#49 behavior, verified throughout via the
FULL-algorithm baseline every other issue's correctness sweep compared
against.
Known gap: formal doc/classes/GeometryInstance.xml documentation for
the new shadow_* properties was not added -- the in-editor guidance
requirement (criterion 4) is met via the Inspector's own enum hint strings
(visible in the property dropdown), but the class-reference docs don't yet
carry a matching writeup. Worth a follow-up if this ships broadly.
