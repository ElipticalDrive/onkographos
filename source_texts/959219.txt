In #730 there is an added depth-only pass to help disambiguate blending within a layer (e.g. channels) and between layers (occlusion). This PR also restores the volume to the multi-viewport example.
Here's what it looks like on main:
In this PR we conditionally render that depth-only pass into a depth texture, which can be subsequently sampled. This is useful in the volume layer where we can terminate rays at the scene depth, allowing us to compose the volume layer with slices or other opaque objects.
Neuroglancer does something similar, but because it renders everything to offscreen framebuffers depth is just another attachment. They then bind the opaque depth to the volume shader as uDepthSampler. We render to the default framebuffer, which WebGL does not let you sample depth from. We might be able to optimize similarly with an offscreen pipeline, but I think that's out of scope here.
That's half the battle, but our "premultiplied" blend mode used in the volume layer also assumes front-to-back draw order and attempts to blend "under" with ONE_MINUS_DST_ALPHA. This is why the whole volume is occluded in the example above. Instead this PR reverses the draw order and changes to composite premultiplied "over" (updating the name to premultipliedOver as well). The cost here is that we no longer have the opportunity to do certain cross-chunk volume optimizations, such as early ray termination (we can still do early-termination within a chunk). We're not making use of this at the moment anyway.

i don't think this is the right shape.
to support this depth pass you added a second texture model to WebGLTextures (createDepthTarget, bindTarget, disposeTarget, and the targets map). none of it has to do with what WebGLTextures is for: a texture-object cache with an upload pipeline.
the changes to disposeAll is a clear tell because it has to enumerate things it doesn't own.
meanwhile WebGLDepthPass already mostly owns the resource. it owns the raw texture handle, the framebuffer, the sizing logic, etc. it only delegates creation and deletion so it reads as split to me.
imo a better shape is letting the pass create/bind/delete its own depth texture. so basically:
WebGLTextures drops the public methods and the map, back to what it was
unit allocate stays centralized in reservePersistentUnit(). the renderer owns the unit and takes care of binding it bindTexture() is deleted.
WebGLDepthPass handles depth texture creation and active/bind.
i know it means that we're not accounting for the chunk memory budget but i can make an argument that it's better because this is not evictable memory? either way a handful of MBs is probably not a big deal.

```
// add two functions to the renderer

private renderDepthPrePass(layers: Layer[], camera: Camera, frustum: Frustum) {
  this.state_.setColorMask(false);
  this.state_.setDepthFunc(this.gl_.LESS);
  this.state_.setPolygonOffset(true);

  this.state_.setDepthFunc(this.gl_.LESS);
```

looks good 👍
one non-blocking concern!
the rendering code is accumulating logic that isn't self-describing. i already re-derive the stencil code from scratch every couple of months and this feature adds two more things future-me will find confusing:
why the depth pre-pass always runs. the answer is an invariant: the color pass never writes depth, so occlusion is established up front even when a viewport is simple enough not to need it. but why does the color pass never writes depth? nothing in the code says that.
why the depth target exists at all. it's not redundant with the pre-pass, it's there because the volume shader needs depth as data to clamp rays mid-fragment which the hardware depth test can't do. again invisible unless you already know it and easy to forget.
none of this is a problem with the implementation. the approach is right. it's that the why lives in our heads and in the PR discussion instead of the repo.
maybe we need a document explaining the visibility model in detail (color pass never writes depth, pre-pass feeds the fixed-function test, depth target feeds shaders that read depth, stencil resolves coplanar overlap, etc). maybe we can slo think harder about naming that hints at purpose (something that ties the depth target to scene depth for shader sampling rather than depth generically.
either way, this is good to go, but i think documenting this will help us in the future and better to do it now before we forget. maybe we can fold it into a guide on the docsite?
