Description
I'm currently using the WebGL version of the Path Tracer, plus Spark.js as the splat renderer (also WebGL), but overlaying the splat renderer with occlusion mask on top of the path tracer render, so it currently doesn't appear on reflections or affects lighting.
Solution
Having the native WebGPU splat renderer integrated with the WebGPU Path Tracer would be ideal. I see three different levels for this:
Simply visualizing splats in the Path Tracer, without them affecting the actual lighting/reflections. Similar to my current workaround of a masked splat on top of the Path Tracer, but in one single render pass. Very basic, and more a patch than a solution.
Getting the splats to actually be read by the rays, maybe as geometry instances, translating each splat into its actual geometry (just a plane with a Guassian falloff for the opacity). This would already capture them both in lighting/shadows and reflections. Probably without considering Spherical Harmonics, nor sorting.
A combination of both. Reading the splats as geometry for the PathTracer, but rendering the splats themselves with a standard sorted splat rasterizer method on top, so visually they include SH and their actual values.
Alternatives
Between levels 2 and 3, a decision needs to be made: Do splats need to be affected by the actual lighting from the scene? AKA, relighting them. Or should they simply interact with the rays for lighting and reflections of other objects, but actually show their true value with the SH?
Open question for now.

Hello! it should be possible at some point to allow for including a "primitive type" in a BVH-packaged geometry at some point, so this may come later down the line.
You suggestion 3 seems like the only real option here since flat planar geometry is not sufficient for splats, but as you mention the question is lighting. Cycles seems to effectively treat the splats as "emissive", meaning they'd be treated as a light in subsequent bounces, which I don't love. But "Basic" unlit materials have a similar conceptual issue, so perhaps they can have a shared solution.
Are you expecting lit splats or do you have any comparable treatment from other tools you're referencing?
For reference these seem to be the papers that Cycles uses for implementation:
Stochastic Ray Tracing of Transparent 3D Gaussians, Sun et al., EGSR 2025
3D Gaussian Ray Tracing: Fast Tracing of Particle Scenes, Moenne-Loccoz et al., SIGGRAPH Asia 2024
PGSR: Planar-based Gaussian Splatting for Efficient and High-Fidelity Surface Reconstruction, Chen et al., 2024
3D Gaussian Splatting for Real-Time Radiance Field Rendering, Kerbl et al., SIGGRAPH 2023
Gaussian Point Splatting, Rijsdijk et al., ACM TOG 2026
3DGUT: Enabling Distorted Cameras and Secondary Rays in Gaussian Splatting, Wu et al., CVPR 2025
https://arxiv.org/pdf/2405.15425
