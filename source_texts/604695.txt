Two new env vars on the shipped GICP pipeline, both off/inert by default.
MOLA_VOXEL_STRIDE_{MAP,ICP} (maximum_voxel_stride)
FilterDecimateAdaptive walks occupied voxels with stride nVoxels/budget and
takes the first point of each visited voxel. With a fixed point budget the
stride is whatever the scene makes it: measured medians are 3.5-5.0 on the map
stage and ~3.3 on the ICP stage for KITTI, i.e. the sampler never visits
70-80% of the occupied cells, and sparse voxels get the same one vote as dense
wall or floor voxels. Bounding the stride raises the effective budget until
nVoxels/budget <= s and never lowers it, so the absolute count stays a floor
for sparse inputs.
The bound is what makes a coarse decimation voxel safe: coarsening alone only
shrinks nVoxels toward the fixed budget, and past the crossing the sampler
emits duplicate points inside cells it has already visited instead of coverage.

MOLA_DECIMATE_METHOD (decimate_method)
Both stages hardcoded FirstPoint, so evaluating VoxelAverage meant switching
to a hand-maintained copy of the whole pipeline. Those copies have drifted from
the baseline in ways that are not the intended axis (one carries a 3x smaller
remove_points_farther_than), so arms run through them varied more than one
thing at a time. As an env var the ablation runs on the shipped pipeline and the
copies can be retired.
Defaults
Unchanged. maximum_voxel_stride defaults to 0 (off) and decimate_method to
FirstPoint, so this PR changes no shipped behavior. Picking a stride default is
a separate change, gated on the Oxford confirmation currently running.

On the mp2p_icp version constraint: the finding is correct that maximum_voxel_stride and decimate_method are not in a released mp2p_icp — git describe --tags --contains on the merge of MOLAorg/mp2p_icp#90 resolves to no tag, so the newest release (2.12.0) predates it. Both are loaded with the optional macros (DECLARE_PARAMETER_IN_OPT, MCP_LOAD_OPT), so an older build ignores the keys rather than failing.
Two reasons this does not need to block, and one follow-up that should happen:
Both keys are inert at their defaults. maximum_voxel_stride defaults to 0 (bound disabled) and decimate_method to FirstPoint, which is what both stages did unconditionally before this PR. So an older mp2p_icp silently ignoring them reproduces exactly the current shipped behaviour — there is no divergence for a default user, only for someone who sets the env vars and is on a pre-feat: push KFs to central map server #90 build.
The ${...} + MCP_LOAD_OPT combination is verified to engage, which is the part actually worth checking here: decimate_method is an enum read via name2value(... .as<std::string>()), so it depends on the text substitution having already happened. It has — lidar3d-default-voxelavg.yaml has shipped the same pattern, and switching that axis moves measured accuracy (KITTI 0.576 -> 0.608 translation error, Oxford pooled vertical drift +3.93 -> +3.11 mm/m). A parameter that had silently failed to load could not have produced either delta.
Follow-up: the version_gte constraint should be added when mp2p_icp next tags a release containing #90. Adding it now would name a version that does not exist yet and break rosdep resolution for everyone, which is the worse failure.
