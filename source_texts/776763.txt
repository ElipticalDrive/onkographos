Summary
GPU TSDF volumetric fusion (src/gpu_tsdf_fusion.cu) — the
KinectFusion-style projective TSDF integration step that the repo's mapping
section (occupancy grid, CSM / NDT submap SLAM, branch-and-bound loop closure)
did not yet cover. It demonstrates the canonical mapping idiom:
one thread = one voxel.
Volume: 96^3 = 884,736 voxels, axis span 5 m, VOXSZ ≈ 0.052 m,
MU = 0.20 m.
Depth source: 24 synthetic depth frames (160 × 120) generated by
analytic sphere-tracing of a 3-sphere snowman on a ground plane, with the
cameras orbiting the scene.
Each voxel integrates every frame: project into the camera, read measured
depth at that pixel, form sdf = depth_measured − pc.z, truncate to
[−MU, +MU], and fold into the running weighted average.
A single __host__ __device__ fuse_voxel(...) is called by both the
serial CPU triple loop and the batch CUDA kernel.
Correctness — deterministic by construction
In contrast to the iLQR demo (#129), TSDF fusion has no data-dependent
branches — every voxel processes the frames in the same fixed order. With
FMA contraction disabled (--fmad=false) the CPU and GPU volumes are
bit-identical:

Adds gpu_tsdf_fusion (src/gpu_tsdf_fusion.cu) - the KinectFusion-style
projective TSDF integration step that the repo's mapping section
(occupancy grid, CSM/NDT submap SLAM, branch-and-bound loop closure)
did not yet cover.

- 96^3 = 884,736 voxel volume, 24 synthetic depth frames (160x120)
  from cameras orbiting a 3-sphere snowman on a ground plane.
- One thread = one voxel: each voxel integrates every frame
  independently (project, depth lookup, projective signed distance,
  truncate to +/- mu, weighted running average).
- Single __host__ __device__ fuse_voxel(...) drives both the serial
  CPU triple loop and the batch CUDA kernel.

Correctness (in contrast to gpu_batched_ilqr): TSDF fusion is a
deterministic weighted average. Each voxel processes the frames in
the same fixed order with no data-dependent branches. With
--fmad=false the CPU and GPU volumes are bit-identical
(max|diff| = 0.0). The win is pure throughput.

Latest local run:
- CPU serial fuse 134 ms, GPU fuse 0.125 ms -> ~1075x.
- 691,228 observed voxels, ~10.7k surface-band voxels.

GIF deployed to the gh-pages root; readme entry added to the
SLAM / Multi-view geometry section.
```

Textbook Lorensen & Cline iso-surface mesh extraction (Bourke's 256-entry
edge/triangle tables) running as one thread per cube cell.  The natural
successor to gpu_tsdf_fusion (#130): TSDF builds the SDF volume, Marching
Cubes turns its zero-level-set into a triangle mesh.

Setup
- 128^3 = 2,097,152 voxels, 2,048,383 cells, iso = 0.
- Same 3-sphere snowman scene as the TSDF demo, SDF evaluated analytically.
- Single __host__ __device__ mc_cell() shared by CPU and GPU paths.
- Fixed-slot output (cell_idx * 5 + t): both volumes write to identical
  indices, so vertex buffers are byte-comparable.

Correctness — deterministic by construction
- triangles: CPU 81,890 == GPU 81,890.
- 0 / 2,048,383 cells with mismatched triangle counts.
- vertex max|diff| = 0.0 over 737,010 floats (bit-identical, --fmad=false).

Performance
- CPU serial MC 68 ms, GPU MC 4.08 ms -> ~17x.
- Per cell: CPU 33 ns vs GPU 2.0 ns.
- Modest speedup vs TSDF's 1075x reflects that MC is genuinely compute-light
  (8 corner reads + table lookup + at most 12 edge interps per cell).
  The headline is the bit-identical mesh, not the throughput.

Outputs
- gif/gpu_marching_cubes.gif (rotating mesh, deployed to gh-pages root).
- docs/gpu_marching_cubes.md.
```
