Closes #714.
Moves terrain LOD selection and seam resolution off the CPU. TerrainQuadtree::SelectLOD's recursive descent, the unordered_set-backed FindLeafAt neighbour queries in ResolveNeighborLODs, and the per-chunk TerrainChunkLODData upload no longer run per frame; terrain draws from a GPU-built indirect list.
How it works
A persistent worklist, one dispatch per tree level, nothing read back:
kernel
job
TerrainNodeSelect.comp
pops a pending node, frustum-culls it, tests screen-space error, atomicAdd-appends either its 4 children or itself to the visible list
TerrainCullArgs.comp
1 thread: swaps the counters, writes the next DispatchComputeIndirect args and the draw's instanceCount
TerrainLODMap.comp
split map → selected level per texel
TerrainSeamMap.comp
packs four max(0, mine − neighbour) deltas per visible node
Terrain then draws as one instanced indirect call over a shared unit patch grid. The vertex stage reconstructs each instance's terrain rect from its node coord and snaps edge vertices to the coarser neighbour's spacing.
Per the issue's note on #713: the worklist uses atomicAdd compaction, not a prefix scan. An unordered append is all a worklist needs and no consumer here reads the ordering.
Acceptance criteria
1. SelectLOD / ResolveNeighborLODs no longer run per frame; terrain draws from a GPU-built indirect list. Done. The CPU descent remains only as a fallback when compute is unavailable or OLO_TERRAIN_CPU_LOD=1 forces it.
2. No cracks, from ground level and from above. Proven two ways.
Exhaustively, in TerrainGPUQuadtreeTest: every +X boundary in a selected set, over 15 camera poses × 4 split thresholds, comparing the two edges' vertex sets for exact equality — both sides are integer multiples of the same dyadic step, so a tolerance would only hide a real crack. It also asserts at least one boundary joined two different levels; that guard fired for real during development, when every pose used the shipped 8 px threshold and the descent always reached leaves, so the check was passing vacuously.
Visually: background pixels inside the terrain body, live editor, measured.

Depth ceiling: the GPU tree is no longer clamped to TerrainLODConfig::MAX_LOD_LEVELS — that cap existed because the CPU descent is a per-frame single-threaded walk. This is a structural change, not a measured one: at the scene sizes tested the chunk-derived depth (4) is still below the old cap (5), so nothing here demonstrates the extra headroom being used.
Two pre-existing bugs this uncovered
No sandbox scene set TessellationEnabled, so the quadtree LOD path had zero runtime coverage — not in AssetSceneLoadTest, not in any visual test. TerrainGpuLodTest.olo now enables it.
That hid a real defect: FindChunkForNode maps a selected node to the one chunk at its centre, which is correct only while every selected node is a leaf. Select one level up and the node covers 2×2 chunks while three go undrawn. The committed evidence PNGs are the same scene and pose with only the LOD path differing — the CPU frame leaves 80.1% background, the GPU frame 0.000%. The GPU path removes the mapping entirely: a visible node is the drawn primitive.
Supporting changes
RHI: DispatchComputeIndirect (GL glDispatchComputeIndirect / Vulkan vkCmdDispatchIndirect) did not exist. DrawBoundElementsIndirect gained an explicit topology so terrain can draw PatchList indirectly — explicit rather than a default argument, since a default on a virtual resolves from the static type.
TerrainQuadtree: node bounds now come from an exact min/max height pyramid shared with the GPU descent. The previous per-node strided resample (every extent/16 texels plus corners) could miss a spike and produce an AABB that clipped its own terrain. Sharing the array is also what lets TerrainGPUQuadtreeTest assert an identical selected-node set rather than a fuzzy overlap.
BuildFromPyramid and a std::span overload of BuildHeightPyramid let the selection math be tested with no GL context. Populating a TerrainData uploads a heightmap texture, so the L1 tests were faulting through a null GL entry point when run in isolation.
OLO_TERRAIN_CPU_LOD=1 forces the CPU path — the A/B lever the perf table above uses.
Notes for review
Shadow casters deliberately stay on the chunk meshes. The GPU visible list is culled against the camera frustum; replaying it per cascade would drop every caster that is off-screen but still shadowing. A correct fix is a second descent with the light's frustum — its own change.
A .comp never goes through shaderc on the GL backend. OpenGLComputeShader::Compile hands GLSL straight to glShaderSource, so glslc passing says nothing about whether the driver accepts it. All four kernels compiled under glslc and glslangValidator -G while NVIDIA rejected them over a parameter named packed — a GLSL reserved keyword. Worse, the failure is an infinite hang, not an error: OLO_CORE_ASSERT → MessageBoxA with no headless suppression, so the test process sits at ~0% CPU forever. Both are written up in the agent-rules doc.
Testing
Full suite: 5949 tests, 5927 passed, 45 skipped, 0 failures.

TerrainGPUQuadtreeVisualEvidenceTest — 3 L8 tests: top-down coverage, ground-level silhouette, and the GPU-vs-CPU coverage A/B.

Three fixes found by actually running the thing.

1. The four terrain compute kernels did not compile on the GL backend.
   `OpenGLComputeShader::Compile` hands include-resolved GLSL straight to
   `glShaderSource` — compute never travels the shaderc/SPIR-V hop the graphics
   shaders take — so `glslc` and `glslangValidator -G` both accepting them
   proved nothing. NVIDIA's front-end rejected a parameter named `packed`, a
   GLSL reserved keyword, with "abstract parameters not allowed in function
   definition". Renamed to `packedNode` (and a shadowing `distance` local for
   hygiene). It failed as an infinite hang, not an error: OLO_CORE_ASSERT calls
   MessageBoxA with no headless suppression, so the test process sat in
   NtUserWaitMessage at ~0% CPU.

2. TerrainGPUQuadtreeVisualEvidenceTest classified background by `luma ~= 86`,
   taken from a different fixture's clear colour. This scene renders the editor
   grid at luma 123-165, so the classifier matched nothing and the coverage
   assertion passed while measuring an empty set. Recalibrated from measured
   pixels to EXACT neutrality plus the real band: empty 80.1%, terrain 0.000%
   (the tolerant `|r-g|<=1` form scores terrain at 10.5% and is useless). The
   anti-vacuous assertion in the A/B test is what surfaced it.

3. Registered the change with two guards that would otherwise have covered it
   silently or failed: ShaderReflectionBindingTest capped SSBO bindings at 53
   and the terrain slots are 54-62 (the existing 57/63 evade it only by living
   in OLO_VULKAN branches the test does not compile), and
   ShaderUBOSizeConsistencyTest SKIPS unlisted blocks, so TerrainCullParams had
   no GLSL<->C++ size guard at all.

Evidence PNGs are the two top-down captures, same scene and pose, differing only
in the LOD path: the GPU frame is fully covered, the CPU frame draws one chunk
and leaves the rest empty.

Tests: TerrainGPUQuadtree.* 8/8 pass standalone;
TerrainGPUQuadtreeVisualEvidence* 3/3 pass.

The levers you flip for one run of an already-built binary — poison the
transient pool, force the CPU terrain path, run the gameplay schedule on one
thread — were 21 independent `Env::IsTruthy(...)` reads across twelve TUs.
The environment was never the wrong INPUT for these; what was missing is
everything around it:

  * **No list.** "Which levers exist?" had no answer but a grep, and "which
    are on in this session?" had none at all — an editor launched hours ago
    with OLO_RG_POISON_TRANSIENTS set looked identical to a clean one.
  * **Not addressable from code.** A test or tool that wanted one on had to
    write the environment; that was the `_putenv_s` the harness carried.

Core/DebugLevers.inl is now THE list, included several times with different
macro definitions (the trick Scene.cpp uses for the generated OnComponent*
lists) so the accessors, setters, seeding and enumeration are all generated
from it. Add a lever there and nowhere else. Levers::LogActive() prints the
non-default ones at startup (silent otherwise) and olo_debug_levers answers
the same question against a running editor.

Six shapes, because flattening them would change behaviour: TOGGLE is lenient;
EXACT takes only "1", for levers where a typo silently disabling the fast path
is a mystery perf cliff rather than a visible failure; TRISTATE keeps "force
off" distinct from "leave the hardware-derived default alone" (two task-graph
knobs need this); INT/NUMBER return optional so set-to-zero stays
distinguishable from unset, which is what std::atoi destroyed at the old call
sites; TEXT has no setter because every text lever is a path read once at init.

Two bugs found while migrating:

  * OLO_ENV_BAKE_DUMP is a *directory path* at one site (IBLPrecompute writes
    "<value>/face0.png") but a truthy toggle at two others — so the documented
    `=1` switched the logging on and wrote the PNGs into a relative directory
    named "1", which does not exist, so stbi_write_png failed and no images
    appeared. It is TEXT now and all three sites agree.
  * Migrating the task-graph knobs left ParseOversubscriptionRatio with zero
    production call sites but 15 tests still pinning it, plus duplicate
    inf-rejection in the new code. Both are gone: the parse lives once as
    Levers::ParseNumberLever and SchedulerConfigTest now pins that, so the
    cases cover every numeric lever instead of one variable.

DebugLeversTest guards the invariant: it fails if a new Env:: read of an OLO_*
variable appears anywhere under OloEngine/src outside the registry, which is
exactly how the previous 21 accumulated. It immediately caught
OLO_EDITOR_UNSAVED_PROMPT, allowlisted as launch-time modal state (the
Core/Interactivity.h concept) rather than a debug lever.

Deliberately NOT a console-variable system: no name lookup, no editor console,
no runtime change without a restart. That layer is #821, and this is the
registry it needs underneath.

…#818 review)

Four findings from #818's CodeRabbit review, verified against current code
before fixing (one had already been partly addressed, one turned out to be the
most serious of the four):

* **Sanitize the split threshold at every read, not just the GPU one.** The
  GPU descent already guarded terrain.m_TargetTriangleSize against NaN/<=0 (a
  user-editable, YAML-round-tripped value), but the CPU fallback's lodCfg and
  the streamer's config still took the raw one. NaN there makes every
  `screenError < TargetTriangleSize` comparison false, so the CPU descent never
  splits — one root-sized patch, silently. One SanitizedTargetTriangleSize()
  helper now backs all three read sites.

* **All four children or none, in the GPU select kernel.** The child-expansion
  path marked a node as split (retiring it from rendering) BEFORE reserving its
  four child worklist slots, then wrote only the children that fit under the
  capacity. A reservation that straddled the cap produced a split parent with
  some children missing — a hole, not a dropped node. Reservation now happens
  first; a straddling reservation leaves the parent unsplit and lets it render
  itself, coarser than the target error but with no gap. The slots a straddling
  reservation already claimed below the cap still get written (a new
  OLO_TERRAIN_NODE_SKIP sentinel), because TerrainCullArgs.comp clamps
  PendingCount to capacity and an unwritten slot would be read next level as
  stale data from the previous level — which is why the old code filled
  partial groups at all. Sentinel value 0xFFFFFFFF's level field (15) is
  provably unreachable by TerrainGPUQuadtree::kMaxDepth (12), asserted at both
  the C++ and the sampled-node test level.

* **A missing shared patch mesh must fall through to the CPU path.** GPU-driven
  mode was gated on tessellation + dispatched state only; a null shared mesh
  (lazily built on first call) drew no terrain at all instead of falling back.
  The mesh check is now part of what makes the branch GPU-driven in the first
  place.

* **CPU fallback selection only emitted the chunk under a node's centre.** The
  quadtree is built to depth ceil(log2(numChunks)) specifically so a LEAF maps
  to one chunk; selection legitimately stops above the leaf level wherever the
  screen-space error is already small enough, and every such node covers a
  2^k x 2^k block of chunks. FindChunkForNode's centre mapping drew one of
  those and silently dropped the rest — a hole growing with how coarse the
  selected node is, invisible except on the CPU path (no sandbox scene enables
  tessellation, so nothing in the suite exercised it before this branch).
  Replaced with ChunkRangeForNode, which emits the whole covered block. Chunk
  count is ceil(resolution/64) and not necessarily a power of two, so quadtree
  boundaries can land inside a chunk and two adjacent nodes can both claim
  it — a per-frame claim set dedupes so no chunk submits twice.

  TerrainGPUQuadtreeVisualEvidenceTest's CPU/GPU comparison test had encoded
  this bug as the expected result: it asserted the CPU path left >10%
  background, with a comment explaining the gap was "three quadrants wide" by
  design. That assertion is now the one that was actually wanted — both paths
  cover the frame — so a regression in either path fails it, where the old
  form could pass by the CPU path getting worse. The measured evidence
  (assets/tests/visual/TerrainGpuLod_cpu_topdown.png, read back and checked
  independently of the test's own code): centre background dropped from 80.1%
  to 0.002%. The GPU capture came out byte-identical, confirming the change
  touched only the CPU path.

Not fixed: the review also flagged that terrain shadow casters are camera-
frustum-culled rather than shadow-cascade-aware, which can drop an off-screen
caster that still shadows the visible frame. Left alone — the non-tessellated
CPU path does the identical GetVisibleChunks(tileCull.ViewFrustum, ...) cull,
so this is pre-existing, engine-wide terrain behaviour and not a #714
regression; fixing it means changing shadow submission on paths this branch
never touched.

Also resolves the PR's SonarQube quality-gate failure (D reliability rating on
new code, gated on a single cpp:S990 flagged on the getenv this branch already
replaced with the shared Env/Levers accessors) — the stale 14-line NOSONAR
justification above it, which argued for a call that no longer exists, is
replaced with a pointer to where the consolidation actually landed.

Verified: glslc compiles all four terrain compute kernels clean. A standalone
simulation of the reservation logic (9 capacity/parent-count configs x 25
random thread orders) shows the old rule producing holes and the new rule
producing zero holes and zero stale-slot reads. A numeric sweep of
ChunkRangeForNode's math (39 chunk-grid sizes x 40 random LOD covers) finds
zero uncovered chunks, and confirms two-node chunk-sharing is real (35 of 39
sizes), i.e. the dedup is load-bearing rather than defensive. Full suite:
5958 tests ran, 5936 passed, 0 failures, 0 errors.
