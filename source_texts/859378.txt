Motivation
hard_voxelize(deterministic=True) is the default voxelization in
MMDetection3D-style pipelines. Its deterministic CUDA path is dominated by two
legacy bottlenecks in voxelization_cuda_kernel.cuh:
Kernel
Launch
Complexity
Issue
point_to_voxelidx_kernel
parallel over points
O(N^2) worst
every thread re-scans all previous points to count same-voxel predecessors (for (int i = 0; i < index; ++i))
determin_voxel_num
<<<1, 1>>>
O(N), fully serial
the whole per-voxel numbering loop runs on a single thread
Measured on an NVIDIA L4 (200k points, max_points=35, max_voxels=20000):
73.85 ms per call, which makes voxelization a dominant preprocessing cost.
Modification
Replaces those two kernels with a hash + stable-sort pipeline, orchestrated
inside HardVoxelizeForwardCUDAKernelLauncher with ATen ops, so the Python API
and the pybind registration stay untouched:
voxel_index_kernel: per-point 1-D voxel id lin = (z * grid_y + y) * grid_x + x
(the same float32 arithmetic as dynamic_voxelize_kernel); out-of-range -> -1.
stable argsort by lin: equal ids become adjacent segments and keep their
original relative order, so each group head is the first point of that voxel in
input order -- exactly what the legacy first-occurrence numbering relies on.
group_meta_lead_kernel: group_start[G + 1] (sentinel group_start[G] = N)
plus each group leader's original row id.
voxels are ranked by leader order (second stable sort + index_copy_), then one
scatter_kernel writes features / coors / counts, deriving the in-group slot and
the group size on the fly (no materialized rank arrays).
The legacy launcher is kept verbatim as a static V1 function and is used whenever
NDim != 3 or points is not float32.

Complexity: O(N^2) back-scan + a <<<1, 1>>> serial pass -> 3 kernel launches with
sort-based grouping (O(N log N) comparison bound; PyTorch's CUDA sort is radix/merge,
~O(N) for the int32 key).
BC-breaking (Optional)
None for supported inputs.
Output on the optimized path is byte-identical. Verified on an L4 by hashing
every returned tensor for the official test_voxel.npy input and for a 200k-point
random input: the patched and the unpatched build produce the same sha256
(d0b8c54c97cef568... and 8c9e83f2a8766cf8...).
Scope is CUDA + NDim == 3 + float32. NDim != 3, other dtypes,
deterministic=False, dynamic_voxelize and CPU/NPU/MLU/MUSA keep the exact
legacy behavior. Non-float32 CUDA input still raises what it raised before
(expected scalar type Float but found Double, not implemented for 'Half'),
which the fallback test pins down.
One behavior difference, strictly a fix: with num_points == 0 the legacy path
launched a kernel with 0 blocks and raised
RuntimeError: CUDA error: invalid configuration argument; the new launcher
returns 0 voxels. Covered by test_voxelization_v2_empty_and_single.
Requires PyTorch >= 1.9 for the stable argsort overload used in the launcher.
Use cases (Optional)
Voxelization-heavy 3D detection preprocessing. NVIDIA L4, torch 2.4.1+cu118,
CUDA 11.8, voxel_size=[0.2, 0.2, 8.0], range [-51.2, -51.2, -5.0, 51.2, 51.2, 3.0],
max_points=35, max_voxels=20000, mean of 20 calls after 3 warmups:

Replace the O(N^2) back-scan in point_to_voxelidx_kernel and the
single-threaded determin_voxel_num (<<<1, 1>>>) with a hash + stable-sort

order inside each voxel, which preserves the legacy first-occurrence voxel

is used whenever NDim != 3 or points are not float32.

Only the deterministic CUDA path changes; nondeterministic hard_voxelize,
dynamic_voxelize and CPU/NPU/MLU/MUSA backends are untouched.

Adds tests/test_ops/test_voxelization_v2.py (byte-identical check against
tests/data/for_3d_ops/test_voxel.npy plus randomized checks).
