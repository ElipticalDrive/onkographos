Moves the Delaunay3D pin from c9b3eec to wildmeshing/Delaunay3D f1c7c19 (danielepanozzo/integration):
upstream main e18e96a, which adds Morton-ordered insertion in tetrahedrize() (2d0279a) above 1150 vertices;
our Locate a point that is not a vertex: searchTetrahedron(tet, point) MarcoAttene/Delaunay3D#2 (orphan inc_tet / point search), merged onto it — the two conflicted textually only, and Fixes #2 is mergeable again upstream;
Morton insertion order: break ties by vertex index MarcoAttene/Delaunay3D#3, a one-line tie-break: upstream sorts by the Morton code alone, and std::sort leaves points sharing a grid cell in an order that differs between libc++, libstdc++ and MSVC. Ties are common on real meshes (9–65% of vertices on the inputs I measured), so without it the tets would come out in a platform-dependent order — which is exactly what reference_hashes.txt must not see.
What moves. The Morton order changes the order tets are created in, not which tets: symbolic perturbation makes the tetrahedrization independent of insertion order (checked: identical tet sets before/after on lattices, random sets up to 1M points, and real models). So 14 reference hashes move: default and -t for exactly the 7 models with more than 1150 vertices (100071_sf, 37989_sf, Octocat-v1, Octocat, bunny, double_sphere, upsample_box). The other 7 models and the 2D hashes are unchanged. The new hashes were generated on macOS arm64; this PR's CI is what checks them on Linux x86-64/arm64 and Windows.
What does not. embed_tri_in_poly_mesh never calls tetrahedrize() — remakePolyhedralMesh inserts the surface into the caller's tet mesh — so every embed, tracking and feature-vertex test passes unchanged (45/45 locally, serial ctest). In wildmeshing-toolkit all 50 registered integration configs are byte-identical with this pin.
Speed. tetrahedrize() alone: random 1M points 28.8 s → 3.3 s, Thingi10K 46024 surface 3.5 s → 0.56 s; bunny/Octocat unchanged; a dental crown model 0.87 s → 1.16 s.
