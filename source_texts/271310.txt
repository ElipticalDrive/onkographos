Description
Closes #2054
_compute_morton_codes now interleaves bits for 1–3 spatial dimensions with a few whole-tensor shift-and-mask steps, on every device. Each quantized coordinate's bits are spread D positions apart in five steps; the dimensions are then shifted by 0, 1 and 2 and summed. Their bits do not overlap, so the sum is a bitwise OR. The generic per-bit loop remains for D ≥ 4.
On CUDA, the function used to materialize every bit of every quantized coordinate at once: bits with shape (N, D, n_bits) and dtype int64 (504 B per point in 3D), then bits << shifts, a second tensor of the same size. BVH.from_mesh calls it on the cell centroids, so the build peaked at 1100 B per cell above the baseline (55 GB at 50M cells), while the finished BVH keeps 120 B per cell. In an earlier sweep at 29e400cf8, which has the same _compute_morton_codes, a 300M-cell build ran out of memory on a 277 GiB GB300. ClusterTree.from_points calls the same function.
The first commit on this branch processed those bits in chunks of 2^21 rows. That bounded the temporary, but at its peak two chunks were alive, it launched five kernels per chunk, and it was no faster. The spreading version needs no loop. Its temporaries are a few (N, D) int64 arrays (72 B per point in 3D) for any N, and every call makes the same 29 kernel launches. The Morton step is 2× faster at 1M points and about 4× faster from 10M points up. Quantization is unchanged, so the codes, and so every BVH field, are bit-identical.
End-to-end, for the case that motivated this (a 50M-cell surface mesh with 100k on-surface query points), mesh.sample_data_at_points(q) with default arguments builds a BVH on every call. On a GB300 its peak drops from 55.0 GB to 17.0 GB above the mesh (PyTorch's reserved memory: 60.1 GB to 27.1 GB), and the call takes 86 ms instead of 111 ms.
Testing
GPU runs used one NVIDIA GB300 (277 GiB) on Linux aarch64 with Python 3.13.16 and PyTorch 2.13.0+cu130. They compared upstream main 354896ae7, the chunked first commit 3c53ddf4d, and this branch. Times are medians of 15 calls after a warm-up, with torch.cuda.synchronize() around each call. Peak is max_memory_allocated above the pre-call baseline.

```
On CUDA, _compute_morton_codes materialized every bit of every quantized
coordinate at once as an (N, D, n_bits) int64 tensor, plus a shifted
copy of the same size: about 1 kB per point. BVH.from_mesh therefore
peaked at 1100 B per cell (55 GB at 50M cells) and ran out of memory on
a 277 GiB GB300 at 300M cells.

Process the interleave in chunks of 2^21 rows and apply the mask and
shift in place, so the temporary stays near 1 GB. Quantization still
uses the global minimum and extent, so codes are bit-identical. On a
GB300 the BVH.from_mesh peak drops to 340 B per cell with unchanged
build time.
```

```
For 1-3 spatial dimensions, spread each quantized coordinate's bits D
positions apart with five whole-tensor shift-and-mask steps, then
combine the dimensions. This replaces the CUDA row-chunk loop, which
still materialized every bit as int64 (504 B per point in 3D, with two

On a GB300, the temporaries are 72 B per point in 3D, and a call makes
29 kernel launches for any N. At 50M points the Morton step takes
9.1 ms instead of 35.8 ms on main, and BVH.from_mesh at 50M cells takes
```
