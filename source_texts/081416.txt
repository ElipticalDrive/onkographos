The topic does indeed come up now and then .... however, the problem is
that it isn't even clearly defined what exactly "overlapping" volumes
mean. For example, for any point X that is in two different volumes, do
we average the scalar values? Add them? blend them somehow? Or take the
minmum/maximum? Once we have this scalar value, which transfer functoin
do we use?
Or do we first evluate each volume's transfer function and then
add/mul/blend/min/max the respective opacities?
Interestingly, though many different users/customers have asked about
this feature, there seems to be little consensus as to what we should
actually implement :-/. Of course, one option would be to implement all
those options in some generic way - possibly using some kind of flags to
indicate which operation to apply - but without actual use cases this is
a recipe for desaster.
Until we get a better idea of what users would actually require, the
current plan is to allow multiple volumes, but to simply ignore whether
or not they overlap; i.e., to treat them just as if they were behind
each other. That's not perfect, but easy to do, and will likely do the
trick for most users, anyway.
Can you be a bit more specific as to for what you'd actually need
overlapping volumes, and what exactly you'd expect them to do?
Cheers,
Ingo

FWIW, you can always write a renderer that does exactly what you want. You can do this via the OSPRay SDK (found in the include/ directory of an OSPRay install), or by writing an "OSPRay module". I'll include what I just posed in issue #49 here:
An example of a simple OSPRay module can be found here: https://github.com/jeffamstutz/module_nanort
The example implements a triangle mesh which forwards ray intersection calls to a small, header-only ray tracing library called NanoRT. While the geometry type itself is not related to this topic, it is a fairly small example of how to extend OSPRay in the source tree and use it in the sample viewer. Any object type (including renderers, which are really just monolithic primary-ray shaders) which doesn't meet your needs, you can substitute your own instead.

Similar to @florianlink, we also need to classify each sample separately and then blend the color values. We're also doing this currently in our OpenGL shader.
Regarding masking: This is also a critical feature we need. However, I think a masking geometry would be even more appropriate and powerful. I imagine this would also be rather simple to implement by keeping track of the number of remaining intersections with the masking geometry along the sample ray (odd: inside volume -> sample; even: outside -> don't sample). It would be even better, if the mask was also applied to isosurfaces.
Thanks for your hint on writing a custom renderer. However, if avoidable, we would rather not want to maintain a modified SciVis renderer fork.

Regarding inside/outside: Assuming a closed geometry, I would prefer something like the even-odd-rule, independent of normals. As I sketched before, in a first pass one could record all intersections with the geometry along the ray and sort them. Then, at every sample location, check if we "passed" an intersection and pop it from the queue. The sample is inside the mask, it the number of remaining intersections is odd.

We will most likely address this issue specifically when we reach OSPRay 2.0 (targeting later this year). Part of OSPRay 2.0 will be moving on from ispc and just use C++ for shading. That will open up some possibilities with making it easier to extend certain parts of the API (e.g. think "a volume sampler"). Furthermore, programmable callbacks (which the calling application could specify) would be a much more tractable problem to solve without the C++/ispc barrier.
Until then, it's not possible for us to satisfy all of the multitudes of methods to blend multiple volume samples: when we talk to users, everyone wants something different specific to their application. Right now, your best bet is to implement your own renderer which handles multiple volumes the way your applications wants.
