Problem
Scenes trained with 3DGUT (NVIDIA 3dgrut, or gsplat with with_ut / with_eval3d) are optimised for a different gaussian evaluation than EWA splatting: each gaussian is evaluated by its peak response along the pixel's view ray (the method introduced by 3DGRT and reused by 3DGUT), not by its projected 2D footprint. Rendered with EWA, as SuperSplat does today, these scenes come out noticeably washed out and hazy compared with how they were trained.
What I've built
I have a working implementation on a fork: https://github.com/husuninder/supersplat/tree/eval3d (4 commits on top of current main, compare: main...husuninder:supersplat:eval3d).
Rendering: the projector writes a few per-splat ray terms to an extra cache texture (16 B/splat), and the fragment stage evaluates the ray response exactly from a term interpolated linearly across the quad. Picking, rings and selection keep the existing EWA footprint. Orthographic views fall back to EWA.
User access: a per-layer 3D Evaluation toggle in the Transform panel, off by default and saved in the document, with a tooltip saying to turn it on for 3DGUT-trained scenes. It's per layer because it depends on how a scene was trained, and nothing in a PLY marks a 3DGUT scene today.
No change by default: with the toggle off, rendering is identical to main.
npm run build, npm run lint and npm run lint:locales pass; the tooltip is translated for all locales.
Only the 3D evaluation is implemented, not 3DGUT's unscented-transform projection: for an undistorted pinhole view the UT only affects the quad bounds, which still come from the EWA footprint.
Verification
