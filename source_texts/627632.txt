Why
Motion blur today is camera-only: engine/shaders/postfx.wgsl's motion_blur rebuilds each pixel's world position from depth and reprojects it with last frame's prev_view_proj. Anything that moves while the camera is still (an enemy sprinting past, a melee swing, a door slamming, ragdolls) never blurs. Worse for a first-person game, the viewmodel blurs with the world. Post-FX runs once over the composited camera stack (render::draw::stack::run_post_fx), so when the player turns, the gun, which is fixed to the camera, is smeared as if it were world geometry. Trepang2 and every modern shooter keep the weapon crisp and blur the world and the enemies.
The gold-standard fix is a per-object motion-vector buffer: each opaque draw writes its own screen-space velocity, built from this frame's and last frame's transforms. This issue is that groundwork. #1436 is the blur that reads it. (TAA, the other usual consumer, is deliberately out: the operator prefers FXAA, 2026-10-25.)
What
Previous-frame state per drawn instance. The renderer keeps each entity's previous model matrix (keyed by entity id, per view, so render-texture cameras keep their own), plus the previous bone palette for skinned meshes (Animator + skinning). An entity drawn for the first time, or teleported, has no usable history: its object motion is zero and only camera motion applies (Unity's behaviour for a renderer with no last-frame data). A Transform set directly (not interpolated) counts as a teleport only when a script asks for it (e.g. a reset hook, decided in the PR, following Unity's Renderer.ResetMotionVectors / camera resetMotionVectors idea, not a distance heuristic).
A velocity target, Rg16Float at full view resolution, written as a second colour attachment of the opaque forward pass: ndc_now.xy - ndc_prev.xy, using prev_model × prev_view_proj vs model × view_proj. Cutout surfaces write it too. Transparent surfaces, particles, decals, trails and UI don't (Unity's default). Sky pixels are camera-only, from depth = far.
Per camera in a stack. Each camera in the stack writes velocity with its own matrices, so an overlay viewmodel camera writes its gun's motion relative to its camera (≈0 when only the player turns) and the world camera writes the world's. The composite keeps the nearest camera's velocity, exactly as the depth it composites. (The blur must read the view's own camera: Post-FX reads the scene's first active volume and camera, not the view's own camera #1434.)
Camera cuts. On the first frame of a view, after a resize, a scene load, or a camera switch, prev_view_proj and the per-entity history reset, so there's no one-frame smear.
Cost and gating. The target is allocated and written only when the view will run motion blur (quality tier ≥ Medium and the camera has it on). Otherwise the pipeline variant without the second attachment runs, so Low pays nothing. Debug.Stats reports whether the velocity pass ran.
Not in scope
The blur itself (#1436), TAA, per-renderer "motion vector mode" overrides (add only when a game asks).
Acceptance
A headless GPU test (lavapipe): a cube translating across a static camera writes non-zero velocity on its pixels and zero on the background; a static scene under a rotating camera writes velocity that matches camera-only reprojection; a skinned mesh whose bone moves writes velocity on the moved vertices only.
A viewmodel test: world camera + overlay camera with a child cube; rotating the camera rig gives the overlay cube ≈0 velocity.
The first frame after a scene load writes zero object velocity.
Code: render::postfx, render::draw::stack, render::passes (the forward pass), engine/shaders/ (the forward shaders' outputs), the skinning path. Read src/render/CLAUDE.md first.
