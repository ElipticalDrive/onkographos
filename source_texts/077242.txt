Problem
On an oblique volume, each 2D slice tilts across the crosshair arms. The slice hides the parts of the arms behind it, so the crosshair looks broken. For example, the white-matter-lesions example FLAIR (6.7° from plumb) loses the axial arm right of centre.
The hidden part is useful, though: which half is hidden shows which way the slice tilts (see the review below). This PR keeps that cue and keeps the arms visible.
Change
On 2D tiles of an oblique volume (volumes[0].oblique_angle > 0), the crosshair x-ray pass now runs straight after the solid crosshair, before the meshes, at 15% opacity. That pass redraws only the occluded fragments (depth greater, no depth write). 15% is the alpha NiiVue 0.x used for the same ghost (drawCrosshairs3D(false, 0.15, …), as in the shear demo).
The arms stay world-aligned. Arms in front of the slice draw solid, and arms behind it draw faint.
Because the pass runs before the meshes, an opaque mesh still hides the arms behind it.
It is skipped:
on axis-aligned volumes;
on render tiles;
while mesh.xRay > 0, because the existing x-ray pass after the meshes already redraws hidden arms;
on WebGPU when the tile has no free uniform slot.
hiddenArmAlpha in view/NVCrosshair.ts holds the rule for both renderers.
An earlier version of this PR moved the arms onto the slice plane. The revert commit drops that.
Verification
Oblique FLAIR: the hidden arms now draw faintly instead of disappearing (screenshots in the thread).
Oblique MNI152 with a pial mesh: the mesh still hides the arms behind it.
Axis-aligned volumes: the FLAIR with its rotation removed, and MNI152 with the mesh, render pixel-identically to e05a2b6.
Unit tests: the tests cover the alpha rule. bun test passes apart from the 12 fixture tests that also fail on main.
WebGPU: checked only by reading the code, not by eye.

```
A 2D slice is drawn on the background volume's voxel plane, but the
crosshair cylinders follow the world axes. For an oblique volume the two
planes are tilted, so each arm leaves the slice in depth and the depth
test hides part of it: arms taper, vanish for a stretch, or show a spike
beside the gap.

fitSegmentsToSlice moves each in-plane arm endpoint along the tile's
viewing axis onto the displayed slice. On screen the arms do not move;
in depth they sit in the slice as they do for an axis-aligned volume.
Both renderers pass the tile's slice type to update(); render tiles are
unchanged.
```

```
Review follow-ups for the oblique 2D crosshair fix:

- WebGPU: arms now differ per orientation, so a frame with more than
  MAX_CROSSHAIR_TILES crosshair tiles let a later tile overwrite an
  earlier tile's clamped slot with another plane's arms. The renderer now
  gives each distinct geometry its own slot per frame (beginFrame, update
  returns the slot) and lets tiles with identical geometry share one.

- crosshairSegmentsForTile builds, fits and explode-offsets the arms in
  one place for both renderers.
- Leave untilted planes bit for bit unchanged so axis-aligned tiles still
  share one WebGL upload; check 2D slice types explicitly.
- Tests check against the drawn plane, cover a sheared affine and the
  WebGPU slot sharing; drop a stale Bun-import comment.
```
