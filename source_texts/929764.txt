Overview of feature request
Extend the generic StateStoreProvider contract with a real provider-atomic compare-and-swap operation, including a safe dynamic-plugin FFI representation.
At current-main revision e759606fa065bee0ef9e60017e263f0f85dd0e44, lib/src/state_store/mod.rs exposes get, set, delete, batch, listing, sync, and durability operations, but no conditional write. Code that must reserve a key or update an owner epoch can only compose get and set; an instance-local mutex cannot make that sequence atomic across processes, replicas, or independently loaded plugin instances.
Generic race fixture:
Configure two independent clients against one shared persistent StateStoreProvider partition and an absent key lease.
Start both clients behind a barrier.
Each reads lease; both can observe None.
Each writes its own owner value.
Both callers may report that they acquired the lease, although only the last value survives.
Expected: a provider-level conditional write allows exactly one caller to transition absent→owned. The loser receives a mismatch/existing result and cannot report acquisition.
Actual contract: the trait has no operation capable of expressing that atomic transition. Implementing a default create_if_absent as get followed by set would falsely promise atomicity and must not be used.
Impact: generic plugins cannot safely implement cross-replica reservations, leases, fencing tokens, idempotency keys, or monotonic state transitions on the host-provided state store.
Historical prototypes explored this API in e7190b1d566fb76c1e0c3035b27f8a474a097f53 and strengthened it in 37d0fe354792036cfcc7ba18531806c1918b8f5f. Those patches also contain application-specific code and must not be applied wholesale. They are design evidence only.
Possible implementation: add a CAS operation whose expected value may be absent, with explicit Swapped, Mismatch, and Unsupported outcomes. Implement it atomically in Memory and persistent providers. Bridge it through a POD FFI result so ownership does not cross the dynamic-library boundary. Any vtable extension must be paired with an SDK ABI version increase and loader rejection of physically shorter incompatible tables before dereference.
Acceptance criteria
StateStoreProvider exposes documented atomic compare-and-swap semantics, including absent→value creation.
Memory and every provider claiming support perform the comparison and write in one provider-level critical section/transaction.
Providers that cannot guarantee atomicity return an explicit unsupported error; there is no get+set fallback.
Concurrency tests with two independent callers prove exactly one absent→owned winner and protect against stale-owner updates.
Dynamic-plugin FFI uses a stable POD result and does not transfer allocator-owned data for the CAS status.
The FFI vtable change advances the SDK ABI version; the loader rejects older physically smaller state-store vtables before reading the new slot.
Native and dynamic-plugin tests cover swapped, mismatch, unsupported, and backend error paths.
The API and tests remain generic and do not include WorkGraph router policy.
Additional context
This capability gap is preserved as report-L275 in issue #889 and draft preservation PR #890. The historical router that exposed it was removed from Core, but the missing primitive remains in the public generic state-store contract.
