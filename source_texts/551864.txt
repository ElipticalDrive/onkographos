Is your feature request related to a problem? Please describe.
Every volumetric in the engine is procedural — Renderer/CloudNoise.cpp generates cloud noise, FogVolumeComponent uses analytic shapes, Precipitation/Snow/Particle are simulated. There is no way to import an authored volume, which is how smoke, fire and hero cloud assets are actually produced (Houdini/EmberGen/Blender all export .vdb). #437 (dynamic fire propagation) and #633 (volumetric clouds) both eventually want this.
Describe the solution you'd like
An OpenVDB importer producing an engine 3D texture / sparse volume asset: read the grid, resolve its transform and voxel size, resample the sparse tree into a dense or brick-tiled 3D texture, and expose it as an asset a fog-volume or cloud component can reference. Animated sequences (a .vdb per frame) as a follow-up slice.
Describe alternatives you've considered
Baking VDBs to 3D texture slices offline in a DCC and importing them as flipbooks — works, but loses the transform/voxel-size metadata and makes iteration painful.
Additional context
Reference: D:\repos\Timberdoodle\src\scene\openvdb_loader.cpp / .hpp (Apache-2.0) — a compact, non-invasive integration worth reading before deciding how much of OpenVDB to vendor. Their src/scene/tex_compression/sdf_bc1_compressor.cpp is a related trick for compressing SDF/volume data on the GPU.
Fits the interchange work in #655 (USD/Alembic importer registry) — the MeshImporterRegistry pattern there is the natural place to hang a volume importer.
Acceptance criteria
A .vdb smoke grid imports and renders through the existing volumetric path with correct world-space scale and orientation.
Import is asset-cook-friendly (no runtime OpenVDB dependency in the shipped runtime if avoidable).
