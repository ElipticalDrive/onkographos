Blender grid rendering interprets voxel transforms in such a way that the voxel
values are located at the center of a voxel. This is inconsistent with OpenVDB
where the values are located at the lower corners for the purpose or sampling
and related algorithms.
While it is possible to offset grids when communicating with the OpenVDB
library, this is also error-prone and does not add any major advantage.
Every time a grid is passed to OpenVDB we currently have to take care to
transform by half a voxel to ensure correct sampling weights are used that match
the density displayed by the viewport rendering.
This patch changes volume grid generation, conversion, and rendering code so
that grid transforms match the corner-located values in OpenVDB.

The volume primitive cube node aligns the grid transform with the location of
the first value, which is now also the same as min/max bounds input of the
node.
Mesh<->Grid conversion does no longer require offsetting grid transform and
mesh vertices respectively by 0.5 voxels.
Texture space for viewport rendering is offset by half a voxel, so that it
covers the same area as before and voxel centers remain at the same texture
space locations.
OpenVDB grid file import does not require changes. This was generally
incorrect already due to file grids using corner locations, and now displays
files correctly.

```
Blender grid rendering interprets voxel transforms in such a way that the voxel
values are located at the center of a voxel. This is inconsistent with OpenVDB
where the values are located at the lower corners for the purpose or sampling
and related algorithms.

While it is possible to offset grids when communicating with the OpenVDB
library, this is also error-prone and does not add any major advantage.
Every time a grid is passed to OpenVDB we currently have to take care to
transform by half a voxel to ensure correct sampling weights are used that match
the density displayed by the viewport rendering.

This patch changes volume grid generation, conversion, and rendering code so
that grid transforms match the corner-located values in OpenVDB.

- The volume primitive cube node aligns the grid transform with the location of
  the first value, which is now also the same as min/max bounds input of the
  node.
- Mesh<->Grid conversion does no longer require offsetting grid transform and
  mesh vertices respectively by 0.5 voxels.
- Texture space for viewport rendering is offset by half a voxel, so that it
  covers the same area as before and voxel centers remain at the same texture
  space locations.

- [x] OpenVDB grid file import does not require changes. This was generally
  incorrect already due to file grids using corner locations, and now displays
  files correctly.
- [x] Cycles does not render generated grids from object data and does its own
  conversion for file imports, so is not affected by this patch.
- [ ] The grid bounds have now changed and don't include the 0.5 voxel padding
  on the left side any more. This could be accounted for when converting grid
  bounds to object bounds. However, grid bounds are not well defined already
  (not accurate on the right side, sampling will yield non-zero values outside
  current bounds). This needs more discussion.
```

Here's a comparison of the different render engines and the object bounds (bottom). Left image is main, right image is after the patch.
main
patched
The cube on the left side is "corner-located" like the official OpenVDB sample files, meaning its grid origin is aligned with the left-most voxel value at (-1, -1, -1). The grid has 11 x 11 x 11 voxels of size 0.2. The cube on the right is generated by geometry nodes with the same nominal bounds from (-1,-1,-1) to (1,1,1) and same voxel count, but currently is shifted left by half a voxel to make it render symmetrically, putting the grid offset at (-1.1, -1.1, -1.1).
You can see that all the engines render the cube consistently, but with an asymmetric offset for the vdb file compared to the generated volume from geometry nodes on the right side. Note that the bounding boxes are only accurate on the lower-left corner due to using a rough bounds estimate based on active leaf nodes, rather than exact active voxels.
After the patch both the .vdb files and generated volumes are symmetric, as are the bounding boxes. The grid generated in geometry nodes now has the same origin of (-1, -1, -1) as the loaded vdb file.
⚠️ One obvious bug here is the missing voxels in the Cycles render. This might be caused by how the grid bounds are interpreted. The problem already appears in main for Volume objects from .vdb files.

I want to note that the OpenVDB cookbook has a section on voxel interpretations that confirms the vertex-centered assumption in this patch for SDF/LevelSet and "fog"/density volumes.
https://www.openvdb.org/documentation/doxygen/transformsAndMaps.html#sVoxels
We haven't been using staggered velocity grids in geometry nodes at all so far, but this will become important for simulations in the future. Staggered grid transforms would still be cell centered, i.e. integer cell coordinates map to the centers of voxels. The interpretation of staggered velocity vectors locates each component on the respective voxel face, so specialized samplers are used to take this into account (see StaggeredBoxSampler).
