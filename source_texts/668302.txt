Summary
Profiling showed FluidSimGPU.Sort at ~90% of sim time: ~105 bitonic merge dispatches per substep (~1800/frame), each paying FindKernel/SetBuffer/driver overhead.
Cell keys are already integers in a small range, so the sort is replaced with a counting sort: atomic per-cell counts → two-level Blelloch exclusive scan in groupshared memory → scatter into per-cell ranges. O(n) work, six dispatches per substep.
The scan output doubles as the start-index table, so the UpdateSpatialLookup_UpdateStartIndices kernel, the -1 sentinel logic, the power-of-two padding, the ping-pong buffers, and Sort.compute are all deleted. Neighbor loops iterate [CellStarts[key], +CellCounts[key]); the hash-collision dedupe and 3×3 cell filter are unchanged.
Kernel ids and buffer bindings are resolved once in SetupKernels() (bindings persist on compute shaders), making the substep loop pure Dispatch calls — no per-dispatch Set* traffic.
Merged force kernels: pressure and viscosity walked identical neighbor lists; a single ComputeForces kernel now accumulates pressure + viscosity + gravity + interaction into VelocityDelta, applied at integration. Neighbor traversal drops from 3 walks to 2 per substep.
Bigger hash table: the cell table is now NextPowerOfTwo(2N) instead of exactly N (load factor ~0.5 instead of ~1), cutting wasted iterations over far-away bucket-mates; the modulo becomes a bit-mask. Capped at the two-level scan limit (262,144 cells; error logged beyond ~131k particles).
Test plan
Sim behaves the same as before (within float rounding; within-cell order is nondeterministic, force ordering between pressure/viscosity changed from sequential to simultaneous).
Profiler: FluidSimGPU.Sort collapses from ~90% of sim time; Gfx.WaitForPresentOnGfxThread shrinks at 50k particles.
Particle count changes at runtime reinitialize correctly (buffers + kernel bindings rebuilt).
Non-multiple-of-512 particle counts work (scan zero-padding path).

Pull request overview
This PR replaces the previous GPU bitonic sort used to build the spatial lookup with a GPU counting-sort pipeline (counts → two-level exclusive scan → scatter), aiming to dramatically reduce dispatch count and per-dispatch overhead in the simulation substep loop.
Changes:
Removed the dedicated Sort.compute bitonic sort shader (and its scene reference) in favor of a counting sort implemented inside FluidSim.compute.
Added a two-level Blelloch exclusive scan and scatter kernels to build per-cell ranges (CellStarts/CellCounts) for neighbor iteration.
Refactored FluidSimGPU to cache kernel IDs and persistently bind buffers once in SetupKernels(), making the substep loop primarily Dispatch calls.

At 50k particles the GPU is the bottleneck (Gfx.WaitForPresent dominates).
Two reductions without quality loss:

The pressure and viscosity kernels walked identical neighbor lists; they
are merged into a single ComputeForces kernel that accumulates pressure,
viscosity, gravity and the interaction force into VelocityDelta (renamed
from ViscosityDelta), applied by the integration kernel. Neighbor
traversal per substep drops from three walks to two, and a dispatch goes
away. Both forces now read the same pre-substep velocity field.

The cell table was sized exactly ParticleCount (load factor ~1), so hash
buckets were frequently shared with far-away cells whose entries were
iterated and rejected. The table is now NextPowerOfTwo(2 * ParticleCount)
(capped at the scan limit of 262144), cutting bucket sharing, and the
power-of-two size turns the hash modulo into a bit-mask.
