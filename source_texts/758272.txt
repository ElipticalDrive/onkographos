Since I'm going to have to rewrite OctreeNode and I might as well clean up the internals of this convoluted mess, I think I need to take a little time to familiarize myself not only with Octrees, but with Cubiquity's implementation of them.
This issue is then for the exploration of Octrees, and Cubiquity's implementation
Ahem
Defintiion
An octree is a tree where each internal (non-leaf) node has eight children. Each spans a particular space defined by a bounding box, and has a CHOSEN middle point. That middle point essentially breaks the octree node into eight cubes if one imagines planes sticking out from it parallel with X, Y, and Z.
Each child may be another internal node (whose middle point must be within the space his parent node gave him) or a leaf that contains stored items.
Octrees often contain indexes to an array of octree items for the whole octree.
Why are Octrees even used in Voxel Worlds?
Great support for LOD (Level of Detail)
Often Octrees are used for rendering/collision detection/culling (space partitioning!). Butwhen working with Voxels, they can also be used for storage, yielding:
Extremely tight compression of sparsely-populated spaces. That is because:
Already works in cubes. Perfectly matches how Voxels operate. And as it's used for rendering AND collision detection AND raytracing, it can speed up a LOT of operations
Competitor for space-partitioning is K-D Tree (a special case of binary space partitioning trees)
Questions I ask myself...
Why the hell does OctreeNodeAlt have to be a Monobehavior, or attached to a game object? All so that it can easily find it's parent's renderer/collision mesh?
Meshes, and the Building Thereof
It is important I come to some kind of understanding about what the devil the Octree Node is actually doing with meshes, renderers, and colliders. so let me try and trace through what's happening.
First of all, the octree assesses whether the mesh has been updated since the last time a synchronization happened.
Then it asks whether that node even has a mesh (which one supposes is a strange order in which to ask the questions, actually)
Fascinatingly, there is a commented out Mesh renderingMesh = volumeRenderer.BuildMeshFromNodeHandle(nodeHandle);
I believe I have gotten around all of this by creating a derived OctreeNode class, which is actually what was required in lieu of having BuildMesh code in collider.
There is a need to trickle down attributes about the VolumeRenderer and the VolumeCollider down to a very low level (each and every node). There are better ways to do this, I think, but I'm going to just pass both of them down the line for now.
