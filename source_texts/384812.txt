Abstract: Adjoint methods (reverse-mode automatic differentiation) are essential in computational science for gradient-based optimization, sensitivity analysis, and inverse problems. However,
hand-coded adjoint operators are notoriously error-prone due to the complexity of reversing the
control flow and correctly applying the chain rule. This challenge becomes particularly acute in
the context of LLM-assisted code generation, where the ability to validate generated code without
manual review is critical.
This report presents adjointcheck, a modern C++23 library that provides rigorous, automated
validation of adjoint implementations. The library offers two complementary verification methodologies: (1) Exact AD Validation using dual numbers, which provides machine-precision verification
by comparing against forward-mode automatic differentiation, and (2) Taylor Convergence Testing,
which verifies the asymptotic behavior of finite difference approximations for codes that cannot be
templatized.
We detail the mathematical foundations of both methods, the software architecture leveraging
C++23 features such as std::mdspan, and demonstrate the library’s effectiveness through the
validation of an LLM-generated WENO5 flux scheme adjoint—a challenging test case from Computational Fluid Dynamics. As a foundational component of a broader design-pattern-driven LLM
approach to automatic differentiation (to be detailed in a forthcoming companion report), adjointcheck enables trust in adjoint implementations without requiring manual code inspection.
Key-words: Automatic Differentiation, Adjoint, Validation, LLM, Code Generation, C++23,
Taylor Test, Dual Numbers

Introduction
1.1
Scientific and Technological Context
Automatic Differentiation (AD) is experiencing a resurgence of interest across the computational
science community. Several converging factors drive this renewed attention:
• Deep Learning: Backpropagation in modern deep learning frameworks (PyTorch [1],
TensorFlow [2], JAX [3]) relies fundamentally on reverse-mode AD, bringing AD concepts
to a broad developer audience.
• New Tools: Emerging actors develop novel AD capabilities, particularly in the Julia
ecosystem (Enzyme [4], ForwardDiff [5]), demonstrating the continued relevance of the
field.
• Legacy Tools: Established tools like Tapenade [6] remain in active use for scientific
computing, as evidenced by joint requests from ONERA and Dassault for continued Inria
support.
However, these tools have specific applicability domains and may prove ineffective—or
entirely unusable—for many practical use cases. A typical example is applying reverse-mode AD
to differentiate numerical simulation codes written in C++ or modern Fortran (2008+). The
complexity of object-oriented designs, template metaprogramming, and legacy interoperability
often defeats automated differentiation approaches.
Our key insight is that successful AD implementation requires more than code generation—
it demands the application of well-established software engineering principles and design
patterns. We are developing a novel design-pattern-driven approach to LLM-assisted
adjoint code generation, which will be detailed in a forthcoming companion report. This
approach combines:
• Pattern-based development: Structuring code around established patterns (Visitor,
Strategy, Factory) that provide clear separation between forward and reverse passes.
• LLM-assisted code generation: Using Large Language Models guided by architectural
constraints and standardized interfaces to generate adjoint implementations.
• Automated validation frameworks: Rigorous testing that verifies both mathematical
correctness and design adherence.
This approach is innovative and promising, but its effectiveness hinges on a critical requirement: the generated code must be validated with maximal confidence. Without mathematically rigorous guarantees, the approach cannot achieve its full potential. Only when tests
provide such guarantees can adjoint code generated by LLMs be fully validated without
manual code review.
The adjointcheck library addresses precisely this need. As a foundational component of
the broader design-pattern-driven LLM approach, it provides the validation infrastructure that
enables trust in adjoint implementations—a role that will be demonstrated in the forthcoming
companion report.
This work is part of the “AD for all” project within the AMDT team of the SED (Service
d’Expérimentation et de Développement) at Inria Université Côte d’Azur.

The Validation Challenge
Manual implementation of adjoint (reverse-mode differentiation) code is notoriously error-prone.
The adjoint must reverse the computational flow of the forward code, correctly propagate sensitivities backward through each operation, and carefully manage intermediate values needed
during the reverse pass. Even experienced developers can introduce subtle bugs: a transposed
index, a missing negation, or an incorrect accumulation order.
The core question is: given a forward operator F : Rn → Rm and a purported adjoint
implementation F ∗ , how can we rigorously verify that F ∗ correctly computes ∇F ?
A single mistake can produce a gradient that appears plausible—close enough to pass casual
inspection—but is incorrect enough to cause optimization failures, erroneous sensitivity analyses,
or misleading scientific results.
Two complementary verification approaches exist:
1. Finite Difference Comparison (Section 2.3): Compare adjoint results against numerical
derivatives computed via finite differences. Simple to implement and does not require
modifying the forward code, but introduces truncation errors that must be analyzed via
convergence tests.
2. Automatic Differentiation Comparison (Section 2.2): Compare the manual adjoint
against derivatives computed by Automatic Differentiation (AD). Provides machine-precision verification, but requires the forward code to be generic (e.g., templated to support
dual number types).
adjointcheck provides both methods in a unified, easy-to-use C++23 framework. Section 2 explains the mathematical foundations of these techniques, including the chain rule (Section 2.1.1) that underlies all derivative computations.

What the User Provides vs. What is Automated
A key question for potential users is: “What do I need to do, and what does the library do for
me?” This section clarifies the division of labor.

What the User Must Provide.
The user is responsible for supplying:
1. A forward operator F : The primal computation (e.g., a physics simulation, a numerical
scheme). For exact AD validation, this must be written as a C++ template accepting a
generic scalar type (Section 3.4 shows how). For Taylor testing, no templating is required.
2. An adjoint operator F ∗ : The reverse-mode derivative implementation that computes
∇F . This may be hand-coded, generated by an AD tool, or produced by an LLM.
3. Wrapper classes: Thin adapters (typically 10–20 lines each) that plug the forward and adjoint operators into the library’s abstract interfaces (ForwardOperator, AdjointOperator).
4. Test points and perturbation directions: Input vectors at which to validate. Random
or representative inputs typically suffice.
What the Library Automates. Once the user provides the above, adjointcheck automatically:
• Computes reference derivatives using dual numbers (forward-mode AD) or finite differences.
• Evaluates the user’s adjoint operator on the same inputs.
• Compares results and reports whether the adjoint is correct (pass/fail).
• Provides diagnostic metrics: exact error magnitude, or convergence rates for the Taylor
test.
No manual inspection of the adjoint code is required if the tests pass.
The LLM Workflow: Generate–Validate–Iterate. When using LLM-assisted adjoint generation (detailed in the forthcoming companion report), the workflow is:
1. Prompt the LLM: Provide the forward code, mathematical context, and structural constraints (e.g., design patterns). The LLM generates a candidate adjoint implementation.
2. Integrate and validate: Wrap the LLM-generated adjoint in an AdjointOperator and
run adjointcheck.
3. Interpret results:
• Pass: The adjoint is mathematically correct. No code review needed.
• Fail : The library reports the error type and magnitude. The user (or an automated
feedback loop) provides this diagnostic to the LLM with a request to fix the issue.
4. Iterate: Repeat steps 1–3 until validation passes.
What Happens When LLM Output is Incorrect?
adjointcheck will detect it:
If the LLM produces a buggy adjoint,
• GradValidator reports a numerical error significantly above machine precision (e.g., 10−8
instead of 10−15 ). The error magnitude hints at the bug type: O(1) errors suggest missing
terms; errors proportional to input values suggest sign or coefficient errors.
• TaylorTester reports convergence rates deviating from the expected 1.0 (gradient) and
2.0 (residue). This indicates the adjoint does not correctly compute the gradient.

The user then feeds this diagnostic back to the LLM: for example, “The Taylor test shows
gradient rate 0.5 instead of 1.0, suggesting the adjoint is incomplete. Please review the derivative
of the weight normalization step.” The LLM revises the code, and the cycle repeats. In practice,

Summary of Effort.
For a typical operator:
• User effort: Write wrapper classes (∼20–50 lines), choose test points, run validation.
• Automated: All derivative computation, comparison, and pass/fail determination.
• Time to validate: Seconds for small operators; minutes for complex ones.
The key benefit is that passing validation provides a mathematical guarantee of correctness—not
just “it compiles and runs,” but “it computes the correct gradient.”

Methodology and Mathematical Verification
Before diving into the technical details, let us establish the core problem in intuitive terms.
Suppose you have a complex simulation—perhaps modeling airflow over a wing or heat transfer
in an engine. You want to know: “If I change this input parameter slightly, how much will the
output change?” The answer is a derivative, and computing it efficiently is crucial for optimization
and sensitivity analysis.
For simple functions, derivatives are straightforward. But for large-scale simulations with
millions of operations, computing derivatives by hand is impractical. This is where Automatic
Differentiation comes in: it systematically computes exact derivatives by tracking how each
elementary operation contributes to the final result.
This section details the two complementary validation methodologies employed by adjointcheck. We first introduce the two fundamental modes of Automatic Differentiation (AD), then
describe how the library leverages each to verify adjoint implementations.
2.1
Automatic Differentiation: Forward and Reverse Modes
Automatic Differentiation (AD) [8] is a family of techniques to compute exact derivatives of
functions implemented as computer programs. Unlike symbolic differentiation (which operates
on mathematical expressions) or numerical differentiation (which uses finite differences and introduces truncation errors), AD applies the chain rule systematically to elementary operations,
yielding derivatives that are exact to machine precision.
2.1.1

Every computer program, regardless of its complexity, can be decomposed into a sequence of
elementary operations: arithmetic (+, −, ×, /) and standard functions (exp, log, sin, cos, etc.).
AD exploits this by applying the chain rule at each step.

Computational Cost and When to Use Forward Mode. The computational cost of

(derivatives with respect to all inputs), we would need to repeat this process for each input

Implementation via Dual Numbers: Forward mode can be elegantly implemented using
dual numbers, which we introduce informally here and formalize in Section 2.2.
A dual number is a pair (x, d) often written as z = x + dε, where x is the value and d is the
derivative we are computing. The symbol ε is a formal element satisfying ε2 = 0 (explained in
detail in Section 2.2.2). This property is the key: when we expand any smooth function F (x+dε)
as a Taylor series, all terms with ε2 and higher powers vanish, leaving exactly F (x) + F ′ (x) · d · ε.
By overloading arithmetic operations to work on dual numbers, a single evaluation of F (x+dε)
automatically yields both the function value F (x) (the real part) and the directional derivative
⟨∇F (x), d⟩ (the dual part). The autodiff library [9] provides a modern C++ implementation
of this technique.

2.1.4
How the Library Uses These Modes
Understanding both modes is essential because adjointcheck exploits their equivalence for validation:
• The library computes forward-mode derivatives automatically using dual number arithmetic (detailed in Section 2.2).
• The user provides a reverse-mode (adjoint) implementation that they want to validate.
• The library compares both results: if they match to machine precision, the adjoint is
correct.
This comparison is the core of the exact validation strategy described next.
2.2
Exact AD Validation (Dual Numbers)
The most powerful validation approach uses dual numbers—a mathematical trick that computes exact derivatives without any approximation error.
2.2.1
The Key Idea: Generic Code
The approach requires that your forward code can work with different number types, not just
ordinary floating-point numbers. In C++, this is achieved through templates: instead of writing a
function that only accepts double, you write a function that accepts any numeric type. Consider
this simple example:
// Specific : only works with double
double square_double ( double x ) { return x * x ; }
// Generic : works with ANY type T that supports multiplication
template < typename T >
T square ( T x ) { return x * x ; }

The generic version can be called with ordinary doubles (square(3.14)), but also with dual
numbers. A dual number carries both a value and its derivative simultaneously. When you
compute square(dual_number), the result automatically contains both x2 and its derivative
2x—computed exactly, with no approximation.
This “write once, get derivatives for free” approach is the foundation of exact AD validation:
if your forward code is generic, the library can automatically compute exact derivatives and
compare them against your adjoint.
2.2.2
Mathematical Principle
Now let us formalize this. A dual number is defined as z = x + dε, where:
• x ∈ R is the primal value (the ordinary number)
• d ∈ R is the dual component (representing a perturbation direction)
• ε is a special element satisfying ε2 = 0 (but ε ̸= 0)
Understanding the Dual Unit ε. The condition “ε2 = 0 but ε ̸= 0” may seem paradoxical:
no real number has this property. The resolution is that ε is not a real number—it is a new
algebraic element that we formally adjoin to the real numbers, similar to how the imaginary unit
i is introduced to construct complex numbers.
Recall that complex numbers are built by declaring that i2 = −1, even though no real number
satisfies this equation. We simply define i to be a symbol with this property, and complex
numbers become expressions of the form a + bi with normal algebraic rules. Similarly, dual
numbers are built by declaring that ε2 = 0 while ε ̸= 0. The dual numbers are then expressions
of the form x + dε.
Formally, dual numbers form the quotient ring R[ε]/(ε2 ): we take polynomials in ε with
real coefficients and declare that ε2 = 0. The key algebraic property is that ε is nilpotent (its
square vanishes), whereas i is not (i2 = −1 ̸= 0).

Software Architecture
Having established the mathematical foundations for adjoint validation, we now turn to the
software design. A validation library is only useful if it integrates seamlessly with existing
codebases. Our architectural choices are driven by the practical realities of scientific computing:
large datasets, performance-critical code, and diverse numerical types.
adjointcheck is designed to accommodate two common scenarios:
• Legacy/existing code: Codebases with strong constraints—non-templated implementations, third-party libraries, or compiled binaries—can use the Taylor Convergence Test
(Section 2.3). This method requires only the forward and adjoint operators to be callable,
without any modifications to their internal implementation.
• New or refactorable code: Projects with flexibility to adopt modern C++ practices can
leverage template genericity to enable exact validation via dual numbers (Section 2.2).
By writing forward operators as templates accepting generic scalar types, the same code
serves both production (double) and validation (autodiff::dual) without duplication.
This dual-mode design ensures that adjointcheck provides value across the entire software
lifecycle—from validating legacy adjoints that cannot be modified, to guiding the development
of new high-precision implementations.
adjointcheck is engineered as a modern C++23 library. It leverages the latest standard
features, particularly std::mdspan, to provide zero-overhead abstractions for multi-dimensional
data access.
3.1
Design Goals and Rationale
The library was designed around three key principles, each addressing a specific challenge in
scientific software development:
1. Zero-Copy Data Access: Scientific simulations often work with large arrays (millions
of elements). Copying data for validation would be prohibitively expensive. By using
std::mdspan views, the library operates directly on existing data without allocation overhead. This means users can validate adjoints without modifying their memory layout or
data structures.
2. Template Genericity for AD Support: To enable exact validation via dual numbers,
the forward operator must work with different scalar types. Rather than requiring users
to maintain separate codepaths, a single templated implementation serves both production
(double) and validation (autodiff::dual). Write once, validate automatically.
3. Separation of Concerns: Clear boundaries between components make the library easier
to understand, test, and extend. The user focuses on their physics; the library handles
validation mechanics:
• Operators: User-defined physics/math kernels (what you want to validate)
• Validators: Library-provided testing engines (how validation is performed)
• Results: Structured output for pass/fail and diagnostics (what you learn)
These principles ensure that integrating adjointcheck into an existing project requires minimal code changes while providing maximum diagnostic value.

3.8
Limitations
The current implementation has several known limitations:
• The GradValidator requires the forward operator to be templatized on the scalar type,
which may not be feasible for all legacy codes.
• The Taylor test can suffer from numerical precision issues at very small step sizes due to
floating-point cancellation.
• For complex-valued operators, the two validators use different conventions: TaylorTester
validates Hermitian adjoints (AH ) using the standard conjugate inner product, while
GradValidator with complex dual numbers validates Wirtinger derivatives (AT ) following
the autodiff library convention. Users must ensure their adjoint implementation matches
the convention of the validator they use.

We began this report with a challenge: how can developers trust that their adjoint implementations are correct—especially when those implementations are generated by Large Language Models? The answer required both mathematical rigor (dual numbers, Taylor analysis) and practical
software engineering (zero-copy interfaces, template genericity). The result is adjointcheck.
Looking forward, with adjointcheck established as a validation framework, the next natural
step is to leverage it as a quality gate for LLM-generated differentiation code. By integrating the
library into LLM workflows—whether through carefully crafted prompts and system messages
that instruct models to produce testable code, or through dynamic Model Context Protocol
(MCP) servers that provide real-time validation feedback—we can create a robust pipeline where
generated adjoint implementations are automatically verified before deployment. This approach,
which we term design-pattern-driven LLM-assisted differentiation, will be explored in detail in
a forthcoming companion report. The key insight is that adjointcheck serves not merely as a
post-hoc testing tool, but as an integral component of an automated differentiation development
environment where validation guides generation.
The library provides two complementary verification strategies: Exact AD Validation via
dual numbers (machine-precision when the forward code is templatized) and Taylor Convergence Testing via finite differences (applicable to any code, including legacy implementations).
Through the challenging WENO5 flux scheme example, we demonstrated successful validation
with errors ∼ 10−15 for the exact method and proper convergence rates for the Taylor test.
Future Work Several extensions are planned or under consideration:
• Higher-order derivative validation: Extend the framework to validate Hessian implementations using second-order dual numbers or nested Taylor tests.
• Sparse Jacobian support: Add specialized validators for operators with known sparsity
patterns, enabling efficient validation of large-scale systems.
• C++26 std::linalg integration: When std::linalg becomes widely available, delegate vector operations to standard library implementations for improved performance and
consistency.
