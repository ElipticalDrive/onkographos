What this does
Chooses, measures, and wires in VGGT's per-pixel confidence: a shared confidence_keep_mask predicate excludes VGGT's exact confidence floor (the default moves from 0.0 to the measured 1.0001, D-045), and recon/tsdf_fusion.py's fuse_run now ANDs that same predicate into both the marching-cubes and Poisson keep-masks, reading the threshold from each run's own run.json by default so the fused surface always matches points.ply. Adds a committed, tested confidence-threshold sweep (recon/confidence_sweep.py) replacing R-17's one-off script, and reruns R-18's golden-set mesh check (manual, both methods, before/after) — see R-20's notes for the full tables and an honest account of what the rerun could and couldn't show (Poisson is blocked locally by an unrelated, pre-existing Open3D/macOS crash). Files R-23 for the matching confidence gap in R-09's provenance observation count, deliberately left out of this story's scope.

Two issues to fix before this merges.
1. min_confidence == 0.0 fast path skips confidence filtering entirely, breaking R-20's own invariant (tsdf_fusion.py:489)
When resolved_min_confidence resolves to exactly 0.0 (the common default/override case), fuse_run sets depth_conf=None and uses keep_mask=segmented_mask with no confidence check at all (lines ~489-492, 531-532). But select_point_cloud (which built points.ply) always applies confidence_keep_mask, which drops any pixel with NaN/Inf confidence even at min_confidence=0.0 — confirmed by vggt_runner.py's own test test_confidence_keep_mask_drops_non_finite_and_below_threshold.
So if VGGT ever emits a non-finite confidence at a pixel with otherwise-valid depth, that pixel is excluded from points.ply but not from the fused mesh — violating R-20's stated invariant ("a pixel left out of the cloud is left out of the fused surface too") and confidence_keep_mask's own docstring guarantee. No existing test covers a non-finite depth_conf value together with min_confidence == 0.0.
2. fuse_run failures collapse into one unrelated error code (service.py:348)
The new except clause in run_reconstruction_pipeline catches every FileNotFoundError/ValueError fuse_run can raise — the new R-20 cases (missing run.json, run.json predating min_confidence) as well as the pre-existing R-21 board-fit failures — and reports all of them under metric_alignment_failed. A caller can't distinguish "fusion's confidence bookkeeping failed" from "the board-fit failed" except by string-matching the message, which D-032's frozen contract doesn't guarantee stable. The comment acknowledges this is a stopgap pending D-031's process for a dedicated error code — worth either doing that now or at least filing the follow-up explicitly rather than leaving it implicit in a comment.

Re-reviewed the true current head (b16a9b3). My two original findings are genuinely fixed:
The min_confidence == 0.0 fast path was reverted — confidence_mask is now computed unconditionally (commit 27ff724), closing the gap where a NaN/inf-confidence pixel could reach the fused mesh but not points.ply.

The three D-044→D-045 reference typos are fixed.
One new issue, found by directly diffing confidence_sweep.py's sweep_run against tsdf_fusion.py's fuse_run at this head:
sweep_run omits the valid_depth gate fuse_run applies before segmentation (confidence_sweep.py's per-threshold loop). fuse_run computes segmented_flat[valid_depth] = segment_part(flat_points[valid_depth], ...) — an invalid-depth pixel (depth<=0 or non-finite, which unprojects to the camera center per unproject_depth_to_world) is never passed to segment_part, regardless of confidence. sweep_run computes valid_depth too, but only to feed measure_board_surface — the per-threshold loop does trusted_points = board_frame_points[trusted] where trusted = confidence_keep_mask(flat_confidence, threshold), with no valid_depth filter applied before segment_part(trusted_points, ...).
This matters because the sweep's own docstring/purpose is to measure "exactly" what fuse_run does — the evidence D-045's chosen default (1.0001) is based on. If a camera-center point ever clears the confidence threshold and happens to fall inside the footprint/height window, it's silently counted as real geometry in the stray-fraction/coverage numbers at a threshold where fuse_run itself would never have included it — numbers this story's completion record presents as a faithful measurement of the shipped behavior.
Suggest gating trusted_points/flat_confidence by valid_depth the same way fuse_run does, before the per-threshold loop. Everything else — the confidence mask sharing, R-21 compatibility, the honest Poisson-incomplete note — looks solid.
