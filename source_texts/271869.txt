The benchmark merged in #63 measures .4spl against image codecs — the comparison it mostly loses, because a 48-byte palette entry per color is a hard cost that PNG never pays. Volumes are the comparison the format was designed to win: one palette for an entire (x, y, z) grid, with each entry's mu_z/sigma_z recording where in depth its color lives. Nothing per-slice can amortize that, and of the mainstream volumetric containers only TIFF has a palette at all.
What's here
tools/refvolumes.py — dependency-free encoders and decoders for the containers that store a 3D grid as one object:
Format
Variant
NIfTI-1
single-file n+1, DT_RGB24, plain and .nii.gz
NRRD
raw and gzip encoding, RGB-color axis
MetaImage
.mha, CompressedData = True (zlib)
TIFF stack
multi-page: Deflate RGB pages, or palette pages sharing one ColorMap across the stack
Each was cross-checked during development against the canonical reader for its format — nibabel, pynrrd, SimpleITK/ITK and Pillow — so the sizes reported belong to files those tools actually open. None of them is a runtime dependency; the harness is standard library only.
tools/benchmark_volumes.py — the separate harness: four synthetic volumes (segmentation labels, sparse structures, voxel terrain, continuous-tone density), the volumetric containers above, the per-slice baselines they replaced (PNG, PNG8, QOI, GIF-over-z), generic compressors over the raw voxels, and 4splat across every scheme plus lossy --colors N runs. Every size is proven by decoding the file again and comparing voxel for voxel; the run exits non-zero if anything claiming to be lossless is not.
tools/benchmark.py — Clip grows a depth axis so encode-volume/decode-volume share the one runner with the 2D harness.
tests/test_benchmark_volumes.py — 54 tests: header fields each reader keys on, IFD chaining, single-slice volumes, a full 256-entry ColorMap, a check that all pages point at one shared ColorMap block, and an end-to-end run against the built binary asserting the file really is written with depth = N, frames = 1.

1.6–2.0× smaller than every real volumetric container on structured data, 1.3× on continuous tone, and 4–7× smaller than per-slice PNG. The mechanism is visible in the numbers: those containers hand raw voxel bytes to a general-purpose codec, while .4spl substitutes a one-byte index per voxel first, so the stream reaching the compressor is a third the size.
Two results that do not flatter the format, kept in the README as they are: bzip2 over raw voxels ties on labels and beats .4spl on angio and ct, and the 256-color ct volume is where palette overhead stops paying against a well-filtered per-slice PNG (--colors 32 gets it to 15,651 at 41.1 dB if lossy is acceptable).
Note on scope
Only 3D is reachable. stack_to_video_quantized() already accepts depth × frames slices in t-major, z-minor order and the header has always carried both fields, but no CLI command feeds it both axes — so a time-varying volume can currently only be built through the low-level encode with a hand-made palette and index. The README says so plainly; a follow-up adds the CLI entry point and extends this benchmark to 4D.

The header has always carried depth and frames, and stack_to_video_quantized()
has always accepted depth x frames slices, but no CLI command fed it both -- so
the (x, y, z, frame) grid the format is named for could only be built by hand.
This closes that gap and measures what it buys.

encode-4d takes --depth D and depth*frames slices in t-major, z-minor order
(slice s is t = s / depth, z = s % depth, the order the index itself uses),
refusing a count that is not a whole number of volumes. decode-4d reports both
axes; video_to_slices already reconstructed the general case.

encode-video and encode-volume were near-identical copies of the same
slice-reading loop, so rather than add a third they now share one
encode_stack_command() over the general codec: a video is depth 1, a volume is
frames 1, and 4D sets both. decode-volume and decode-4d share their body the
same way.

The volumetric benchmark grows two 4D grids, and the containers that have a
time axis are told the depth so they describe the same grid rather than one
tall stack -- NIfTI's dim is literally (x, y, z, t), NRRD gains a time axis,
MetaImage becomes NDims = 4, each cross-checked against nibabel, pynrrd and
ITK. TIFF has no such axis and its rows say so.

The margins are the widest anywhere in either benchmark. On a 4-color pulsing
structure a .4spl grid is 1,359 bytes against 4,619 for .nii.gz (3.4x) and
19,060 for per-slice PNG (14x), and it is the first case that also beats bzip2
over raw voxels. The 256-color grid stays near parity until --colors 32.
