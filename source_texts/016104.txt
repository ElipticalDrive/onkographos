ABSTRACT
Volume rendering based on 3D texture mapping is widely used in CT/MRI medical imaging, but constrained by
GPU memory bottlenecks. While greedy packing strategies, which pack sub-textures into the first available empty
space to minimise gaps, are effective in 2D texture mapping, adapting them to native 3D texture mapping introduces memory inflation due to the hardware constraint requiring uniform texture dimensions. This paper presents
a CPU-GPU hybrid pipeline that mitigates this issue through a novel post-packing optimisation to minimise
memory waste, with CPU pre-processing and GPU rendering. Experimental results demonstrate an average 30.9%
reduction in memory usage compared to the default 3D texture mapping baseline, achieving memory-efficient
rendering without compromising visual quality.

Volume rendering, 3D texture mapping, medical imaging, graphics memory optimisation.

INTRODUCTION
Volume rendering is a powerful technique for visualising scalar fields, commonly applied in medical imaging modalities such as Computed Tomography (CT)
and Magnetic Resonance Imaging (MRI). Among the
various approaches, 3D texture mapping [Cab94] has
become a standard technique for hardware-accelerated
visualisation. However, despite the processing power
of modern GPUs, memory capacity remains a major
bottleneck. As dataset resolutions increase, large volumes often exceed the graphics memory limit, leading
to rendering failures.
In this work, we extend this greedy approach by leveraging modern hardware capabilities to implement
the 3D texture mapping on a CPU-GPU hybrid pipeline. Offloading interpolation and rendering tasks to
the GPU makes it a more streamlined process; however, we discovered that directly applying the original
greedy packing to 3D textures introduces a new issue:
an increased memory requirement. This occurs because 3D texture objects require strict size alignment.
We solved this by proposing a post-packing optimisation. This mechanism analyses the initial greedy packing layout and reorganises the partitioned textures into
uniform size, where the slices are then stacked and uploaded to a 3D texture object for rendering. While this
optimised approach performs well on dense datasets,
we observed a noticeable memory performance degradation when applied to sparse datasets. To address
this, a regular 2D packing approach was introduced,
which safeguards memory performance by detecting
potential memory overhead at an early stage and deciding whether to bypass the greedy packing pipeline,
apply regular 2D packing instead, and directly send
the packed data to the GPU for regular 3D texture
mapping, thereby reducing processing time.
To address these memory limits, prior research has applied techniques such as empty-space skipping along
with opacity thresholding [Kru03, Li03b] and geometry partitioning [Bet05] to discard voxels that don't
contribute to the final rendering. The efficiency of
these methods depends on how the remaining textures
are packed. Notably, Li and Kaufman [Li03a] demonstrated a greedy strategy for 3D partitioning and 2D
packing. However, due to hardware limitations at the
time, they relied on 2D texture mapping, utilising

In volume rendering, both the shear-warp rendering
method and 3D texture mapping approaches aim to accelerate the rendering of volumetric data. The shearwarp method, as detailed by [Lac94, Lee22], is an object-order algorithm that decomposes the viewing
transformation into three simpler steps: a 3D shear of
the volume data, a projection of the sheared volume
into a distorted intermediate image, and a final 2D
warp to produce the correct view. This factorisation
cleverly aligns voxel scanlines with pixel scanlines,
enabling efficient processing and the use of coherence-based optimisations. Conversely, 3D texture
mapping treats the volume dataset as a 3D texture that
is sampled by view-aligned proxy geometry.
Similarly to how these modern structures isolate important data, Kauker et al. [Kau16] addressed sparsity
using a linked-list data structure that explicitly stores
only non-empty voxels, thereby eliminating memory
overhead for empty space. This structure supports efficient sparse volume rendering by limiting traversal
to relevant data points. In a related manner, the proposed method begins by evaluating dataset sparsity to
identify non-empty voxels, subsequently applying a
2D greedy packing approach that addresses the legacy
constraints of 3D packing by packing their corresponding pixels into memory-optimised 2D slices.
To improve rendering performance and reduce aliasing, a standard mipmapping strategy is applied to the
final retained textures. This creates a discrete Level of
Detail (LOD) system using pre-computed, down-sampled versions of the texture atlas [LaM99]. During rendering, the hardware automatically selects the appropriate resolution level based on the object's distance
from the camera to reduce computation time and minimise aliasing. While this increases memory usage
slightly due to storing lower-resolution textures, the
trade-off is justified by the improvement in overall
rendering speed and visual stability.

Greedy-based Approach
The greedy-based approach consists of greedy-partitioning and greedy-packing before sending the data to
the GPU for subsequent volume rendering. To accelerate rendering via empty-space skipping, our method
partitions the volume by adapting the box-growing algorithm and 2D greedy-packing proposed by [Li03a].
While their approach partitions voxels based on both
density and gradient magnitude, the approach introduced in this paper applies only to the alpha value as
density magnitude from the original dataset to create a
more streamlined process.

EXPERIMENTAL RESULT
The software stack utilised in the development of our
CPU-GPU hybrid pipeline adopted the WebGL 2.0
graphics API, which natively supported the OpenGL
ES 3.0 specification for hardware acceleration within
the browser environment. The system was implemented using JavaScript (ES6+), while all shaders—
including vertex and fragment programs—were developed in GLSL ES 3.0 and compiled at runtime. Using
this implementation, we evaluated our approach
against a 30 fps real-time performance constraint, following established targets for interactive applications
[Ake18]. This threshold served as our primary benchmark; to indicate this clearly, results in Table 2 meeting or exceeding this limit are bolded, while Figs. 1315 include a solid red horizontal line to indicate the 30
fps requirement. Results comparing our baseline with
the proposed approach are summarised in Table 2.
Due to architectural differences, legacy hardware results are restricted to a representative subset of original datasets. The M3 Pro, the primary platform for this
paper, reaches the hardware limit of 120 fps on the
base datasets. Fig. 13 shows the performance for
scaled stress-test configurations, demonstrating that
the empty-space skipping technique improves rendering performance and scales directly with the density
threshold. The fps consistently improves as more empty
voxels are skipped. In stark contrast, the A14 Bionic
(Fig. 14) shows remarkable stability. Its fps remains
largely flat across all thresholds, suggesting that its performance is not primarily limited by fragment processing and is less sensitive to geometric complexity.
The Nvidia 1050M (Fig. 15), a discrete GPU, exhibits
the most volatile performance. For some datasets, increasing the threshold and thus the box count (Fig. 18)
leads to a significant decrease in fps; consequently, the
results reveal a strong dependency on hardware architecture, with varying levels of efficiency observed
across the proposed greedy-based pipeline.

VOLUME RENDERING
This final stage of the rendering pipeline takes the retained texture, applying mipmapping [LaM99] to improve rendering performance, and displays the resulting volume. It represents the culmination of the partitioning, packing, and post-packing pipeline.
Mipmaps are pre-computed, down-sampled versions
of the main texture at sequentially lower resolutions
(Fig. 11). When the volume is viewed from a distance,
the GPU samples from a smaller, more appropriate
mipmap level instead of the full-resolution texture.
This reduces aliasing artefacts, resulting in a smoother
visual result and improved rendering speed
Figure 11: An illustration of mipmap levels, from the
full-resolution texture (L0) to lower-resolution versions (L1, L2, L3).
With all pre-processing and optimisations complete,
the final 3D texture atlas and its associated lookup tables are uploaded to the GPU. The volume is then rendered slice-by-slice. For each slice, a proxy polygon is
drawn, and a fragment shader uses the lookup tables
to sample the correct texels from the packed texture.

The M3 Pro and A14 Bionic platforms, which feature
a unified memory architecture, are largely insensitive
to the number of partitioned boxes. With the CPU,
GPU, and RAM integrated on a single chip, the cost
of transferring geometry data is minimal. As a result,
they benefit directly from the primary optimisation—
empty-space skipping—without being significantly
penalised by the CPU-intensive partitioning and the
increased number of draw calls.

The results demonstrate that the post-packing stage is
a highly effective "damage control" measure. Its impact is most significant in cases where the initial
greedy packing failed. For the Head dataset (Table 3)
at density threshold t=0.17, the optimisation converted
a 157.2% memory increase into a final saving of
74.5%. Additionally, despite the fact that the algorithm doesn't perform well on sparse datasets at high
density thresholds, as shown in Table 5, it is still effective on reclaiming the initial overhead. The proposed approach, regular 2D packing, is designed as an
alternative for this scenario.
In contrast, the performance on the discrete Nvidia
1050M GPU illustrates the pipeline's main bottleneck.
Figs. 18 - 19 indicate a clear inverse relationship between the number of boxes generated and the resulting
frame rate. When partitioning yields a high number of
individual boxes, the computational cost of the hybrid
approach becomes apparent. The combined impact of
CPU-bound partitioning, geometric data transfer, and
excessive draw calls eventually outweighs the benefits
of rendering fewer fragments. Nawfal and Ali [Naw18]
proposed a possible alternative for addressing this bottleneck. Their approach utilised CUDA to execute the
required computational operations concurrently on the
GPU. These pre-processing tasks, such as partitioning
and packing, could be migrated directly onto the device which, when executed natively, allows the geometric data to remain entirely resident in video
memory. This avoids the performance drop by never
requiring the CPU-to-GPU memory transfers during
the rendering pipeline.
Conversely, it made no changes to the already efficient
Pancreas dataset in Table 4. A detailed analysis of
these results is presented in the following section.

Memory Efficiency
The pipeline is built on a strategic trade-off between
rendering speed and memory efficiency. Its primary
limitation arises from the initial greedy packing,
which can result in significant memory overhead. For
large datasets, this can exceed GPU memory limits,
leading to the execution failures observed in our results (Fig. 13: threshold = 0.16, 0.3 and Fig. 15: threshold = 0.16). While the post-packing optimisation is a
powerful corrective measure, it cannot always fully

behaviours of the unified memory systems (M3 Pro,
A14 Bionic) versus the discrete GPU (Nvidia 1050M)
highlight a critical trade-off in this hybrid approach.

compensate for an inefficient initial layout. As demonstrated with the Head dataset (Table 3), the technique
successfully mitigates significant overhead; however,
for larger or sparser datasets, GPU memory limits may
still be reached, as evidenced by the execution failures
in Fig. 13 and 15. To address datasets that exceed the
GPU memory limit, an alternative approach was proposed by [Xue15] using an on-demand streaming
strategy. Their semi-adaptive partitioning approach
first divides the entire volume into smaller, independent sub-blocks of varying sizes, each guaranteed to fit
within the GPU's memory. These blocks are organised
hierarchically into a Binary Space Partitioning (BSP)
tree [Vid08] which, when traversed according to the
viewpoint, allows only the currently visible blocks to
be loaded from external storage. This avoids memoryrelated failures by never requiring the entire dataset to
be resident in the GPU at once.

Regular 2D packing Rendering
The regular 2D packing approach in Fig. 1 is designed
specifically for sparse datasets, for example, Legs
512x512x263, Oral Tumour 512x512x84, and Amputated Arm 512x512x161. Based on experiments, Table
5 confirms that sparsity significantly impacts memory
efficiency, even after applying post-packing optimisation. Fig. 20 describes the average memory saving
compared to the baseline across the density threshold
[0, 0.5]. While the regular 2D packing approach
matches the baseline’s memory usage and is 4 to 6 times
faster than the greedy-based approach (Fig. 22).The
greedy-based approach demonstrates divergent performance between dense and sparse datasets. Specifically,
while sparsity degrades memory efficiency for the
greedy-based approach on sparse datasets, it conversely
provides improvements on dense datasets. Fig. 20 implies memory performance changes drastically within
the threshold range of [0.4, 0.5]; Fig. 21 clearly shows
the range of dataset sparsity with its corresponding averaged memory performance. All datasets have above
60% sparsity, and the three sparse datasets (results
marked with 'x') have over 80% sparsity, resulting in
a memory overhead. However, two dense datasets
achieve better performance despite high sparsity; these
are considered more balanced than the others, having
high alpha voxels in one cluster and low alpha voxels in
the other(s). When a higher threshold is applied, it reveals a distinct gap in alpha values; consequently,
empty regions are easily eliminated and only the informative ones retained. Therefore, having more sparsity is only considered beneficial in this particular case.
Another potential approach involves the two-stage
process of Block Trimming and Texture Block Merging [Ton99]. In this approach, the first stage analyses
each partitioned data block to find the tightest bounding box of its non-empty "object voxels," effectively
discarding large, empty surrounding regions. These irregularly sized blocks are then merged into denser
"texture chunks" via horizontal and vertical merge operations to optimise memory usage. However, to maintain high rendering performance while avoiding a significant increase in pre-processing time, we introduce
regular 2D packing rendering as a direct alternative.

CONCLUSION
This work presented a memory-reduction pipeline for
volume rendering based on 3D texture mapping. By extending the greedy packing algorithm [Li03a] with a proposed post-packing optimisation algorithm, this method
achieved an average of 30.9% memory savings without
any negative impact on perceived image quality.

Future work will focus on addressing larger datasets that

7.1.3 Visual Quality Comparison (Baseline vs
Greedy-based Approach)
To ensure the memory optimisations did not compromise image quality, an experiment applying a density
threshold in the range [0, 0.5] was evaluated based on
the Structural Similarity Index Measure (SSIM)
[Wan09]. An SSIM value ≥ 0.95 (see results in Fig.
23) is considered equivalent to "Very high structural
similarity" [Fly13] (selected results shown in Figs. 24
- 26). Across the density threshold range [0, 0.29], our
system achieved an average memory saving of 30.9%
while maintaining an SSIM value ≥0.95. Over the
course of examinations, the radiologist may increase
the density threshold further based on their own requirement, which will lead to further savings in
graphics memory.
