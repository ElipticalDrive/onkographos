Phase 6 of PLAN.md: Boids on the GPU, with a spatial grid so the flock scales, a CPU reference the GPU is tested against, and a HUD showing GPU time per pass.
Simulation (BoidsSimulation, step.wgsl)
CPU reference: the old Rule/Vec2 sketch is finished into it (features/boids/reference): Separation, Alignment and Cohesion as Rules, and BoidsReference stepping a small flock the plain way. step.wgsl follows it operation for operation.
stepNaive: every pair, O(N²).
The spatial grid:
countCells puts each boid in a cell, keeping atomicAdd's old value as its rank in the cell.
An exclusive scan of the counts gives each cell's start.
scatter writes the boids into cell order (a counting sort).
stepGrid searches the 3×3 cells around each boid.
Cells are at least the perception radius wide and at least 3 across. The output stays in cell order, for memory locality.
GpuScan (shaders/common/scan.wgsl): a Blelloch exclusive scan in 512-value blocks in shared memory. The block totals are scanned the same way, then added back. Two levels, up to 262,144 values.
The murmuration (BoidsScene, render.wgsl, BoidsControls)
One 4× MSAA pass: a lit fog bank, then every bird as an instanced triangle. The vertex shader reads the boid storage buffer directly (no vertex buffer). Birds heading towards the lamp catch its light.
Pointer: the left button attracts, the right repels, and the wheel sets the radius.
Panel: flock size (1,024 to 262,144, log scale), the three weights, perception and speed.
Profiling (GpuProfiler, ProfilingHud)
Timestamps: timestamp-query spans per pass. A span can cover several passes. Results are read back through rotating MAP_READ buffers (no stalls) and smoothed.
HUD: an outline readout per DESIGN.md, with the slowest pass in Lamp, the total, and the frame rate from the heartbeat.
On Boids: count, scan, scatter, neighbours and draw.
On Life: step and draw.
Tests
The scan matches a CPU scan on random input, across every block boundary up to 262,144 values.
The naive step matches the reference boid by boid (N = 64).
The grid step finds the same neighbours (N = 256).
Speeds stay between their limits.
A 2×2 neighbourhood fails the grid test, and a broken down-sweep fails the scan test.
Checked in headless Chrome
32,768 and 262,144 boids.
The flock gathering at the pointer.
The HUD on both pages (timestamp-query works even on SwiftShader).
Not done
Not measured: the 100k-boids-at-60-fps goal and Life at 2048×2048. SwiftShader isn't representative; the HUD shows the real numbers on real hardware.
Extras: predators, obstacles and trails are not done; colour by heading is.

[ADD] Profiling HUD: GPU time per pass from timestamp-query
…
beebab5
```
- GpuProfiler: one timestamp query set per frame.
  - Each pass asks for a named span; a span can start in one pass and
    end in another, so the scan's three passes and a frame's Life
    generations each read as one span.
  - Resolved into rotating MAP_READ buffers and read a frame or two
    late, so profiling never stalls the GPU.
  - Smoothed. A pass that doesn't run every frame stays listed, and one
    that stopped drops out after about two seconds.
- The device asks for timestamp-query as an optional feature; without
  it, the HUD says the browser can't time GPU passes.
- ProfilingHud (DESIGN.md's readout, in an outline pane): each pass as
  name, bar and milliseconds, the slowest in Lamp, then the total, the
  frame rate from the heartbeat's timestamps, and page extras.
  - Boids: count, scan, scatter, neighbours, draw, flock size and grid.
  - Life: step, draw and grid size, so Life's 2048 x 2048 cost can now
    be read on real hardware.
- The scene host opens, resolves and reads each frame's spans;
  FullscreenPass, GpuScan and both simulations accept spans.
```
