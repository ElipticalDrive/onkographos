What problem(s) does this PR solve?
Two independent additions to the Forward+ renderer, plus one round of bringing the fork's comments and documents back in step with its code. 27 commits on top of the previous merge; master is an ancestor, so this is a fast forward.
A second ambient occlusion estimator. The engine has only ever shipped Intel's ASSAO, a point-obscurance estimator that scores poorly against a traced reference on contact detail and on thin geometry. This adds a slice-based horizon march with a visibility bitmask (GTAO plus Therrien 2023) as an alternative: a depth prefilter that builds a five-level linear-depth pyramid, a gather that marches slices and accumulates occlusion into a 32-bit visibility mask, and a separable denoise-and-upsample pass. Both estimators write the same occlusion buffer, so nothing downstream knows or cares which one ran.
It is selected per-Environment by the new Environment.ssao_method (Project Default / Screen Space (Legacy) / Ground Truth), which defers by default to the new rendering/environment/ssao/method project setting. Tuning lives under rendering/environment/ssao/ground_truth/: screen_radius, slices, steps_per_slice, thickness, intensity_scale, scale_radius_with_distance and visibility_bitmask. ssao_enabled, ssao_power, half_size and the fade distances carry over; ssao_detail, ssao_horizon, ssao_sharpness, quality and adaptive_target are legacy-only and the inspector hides them when the new estimator is active. Forward+ and single-view only — stereo and XR fall back to legacy, and an orthographic camera is not supported (see below).
Because tuning ambient occlusion by screenshot is how you end up with an estimator that looks right and measures wrong, docs/rt_shadows/ao_validation/ ships a harness that traces a scene on the CPU two ways — a world-space reference and a screen-visible-geometry reference — and scores a render against both. Several commits here are corrections that harness found and that a screenshot would not have: a self-occlusion floor, uneven step spacing, a half-pixel offset in the half-resolution upsample, and a strength curve that was crushing occlusion to black. Section 9 of the fork guide has the resulting numbers.
Raytraced shadow settings are now live. Every raytraced_shadows/* setting except the master enabled flag can be changed in the inspector or through ProjectSettings.set_setting() and takes effect on the next frame, instead of requiring a restart. directional/enabled and the two directional/demoted_shadow_* settings are live but snapshotted once per frame, because a sun's cascade count has to be one answer for the whole frame. Alongside that: the traced penumbra now matches the geometry it comes from; the temporal accumulation window shortens when the clamp had to correct it, which cuts ghosting behind moving casters; the caster gather skips the index query for a light whose volume the sun already encloses; and the BLAS cache compares source buffers instead of asking the rendering device to revalidate every structure every frame.
One documentation and comment audit. About 74 comments and document passages across the fork were wrong, stale, or described the opposite of what the code does — an a-trous pass said to feed its output back when it stores its input, a prefilter falloff described in the wrong direction, an encoding claim off by a factor, volumetric fog listed as a reader of shadow maps it no longer reads. All corrected against the code. Investigation history that had accumulated in comments moved to FINDINGS.md, where the fork's contract says it belongs.
Additional information
What is off by default
Everything new. rendering/environment/ssao/method defaults to 0 (Screen Space (Legacy)) and Environment.ssao_method defaults to SSAO_METHOD_DEFAULT, which follows it — so _use_gtao() returns false and neither the gather nor its buffers are ever reached in a project that does not ask for them. The raytraced shadow work is all behind raytraced_shadows/enabled, still false and still restart-required. A project that opens this build and changes nothing renders what it rendered before.
Two caveats. The GTAO effect object is constructed unconditionally with the other Forward+ effects, so four compute pipelines are compiled at startup even when the estimator can never run — that is what lets the per-Environment switch work without a restart, and it matches how ss_effects, taa and fsr2_effect are already built. And in the raytraced path, the DirectionalLight3D shadow-mode demotion and the 1024 atlas cap apply to every directional light once raytraced directional shadows are available, not only to raytraced ones; that is unchanged behavior, just now reachable without a restart.
The one behavioral change
ssao_radius now scales the whole march rather than half of it. Previously it moved the world-space cutoff and the back-face thickness but not the screen-space span the steps walk, so lowering it truncated the march while still spreading its steps over the full span, and raising it widened a cutoff the steps never reached. Both are now derived from the same product.

What caught it: the fork guide, the class reference and GTAO::filter_radius_for() all described the radius as a multiplier on the on-screen reach, and only the shader disagreed. The comment audit found a code defect rather than a documentation one.
Known not to work: orthographic cameras
The ground truth estimator is wrong under an orthographic projection, and it neither falls back nor warns. Three places assume perspective: the distance-scaled world radius still grows with depth when an orthographic view's extent does not, inflating both the sample cutoff and the back-face thickness; view_dir is built with the opposite sign to the perspective branch, reversing the term that lets thin surfaces pass light; and gtao_filter.glsl has no orthographic case at all, so its plane-distance weights measure against a warped plane.
This is documented as unsupported in fork guide section 9.4 rather than fixed. A fix needs an orthographic frame rendered on a GPU to validate, and a partial one would leave it wrong while looking addressed. Use the legacy estimator on an orthographic viewport.
What to look at hardest
The occlusion gather and filter shaders, and the raytraced shadow denoiser changes. Those are where a defect shows up as a picture that is subtly wrong rather than as a failure, and they are the parts no test covers.
What CI does not cover
CI is green on the head commit, but it is Windows-only now, which means the --doctool class reference check, the GDExtension API compatibility check, and the project export and converter tests no longer run. Unit tests do — --test runs in the Windows job.
The class reference was therefore checked by hand: every new bound surface — Environment.ssao_method with its three enum constants, RenderingServer.environment_set_ssao_method with its three, and all eight new project settings — matched against the committed XML for type, default, enum name, argument names and doctool's own emission order. It matches, so --doctool should produce no diff. The API change is purely additive — one new method, one new enum, no existing signature touched — so the dropped compatibility job had nothing to reject either. That check is now yours to run, not CI's.
CI also never compiles GLSL, since Godot builds RD shaders at runtime, so the shaders were validated with glslangValidator including both gtao_filter variants, and their push-constant layouts compared against SPIR-V reflection. The build configurations CI dropped are where a scons disable_3d=yes break was hiding: _rt_report_cpu_cost was defined inside #ifndef _3D_DISABLED and called from an unguarded body. Fixed here.
Nothing in this branch was verified on real hardware. The engine was not built or run while preparing it; every occlusion number quoted comes from the CPU model in docs/rt_shadows/ao_validation/, not from a rendered frame. Look at an actual frame before trusting the estimator in a shipping scene.
AI assistance
This work was done with AI assistance. An AI coding assistant wrote most of the new shader and C++ code in this branch, the CPU validation harness, and the documentation, working from direction and review at each step; the corrections the harness found were diagnosed and applied the same way. The comment-and-document audit was AI-performed end to end, checking each passage against the code it describes, as was a pre-merge review whose findings are the last commit here. Every claim in the documentation was re-derived against the source rather than taken on trust, but the code has not been run on a GPU, so treat the rendering behavior as reviewed rather than demonstrated.

Measured against a closed-form ground truth for the test scene -- an omni
light of known radius over a post of known size, cross-checked against a
dense visibility quadrature and confirmed by the 50% crossing landing within
a pixel of the analytic shadow edge at every distance -- the shipped shadow
was 28% too sharp at stock settings, and got sharper still as the sample
count was raised. Three independent defects were doing it.

The probe early out could not answer for a disk. Two rays that agree were
taken to mean the whole emitter agrees, but two points on the rim, opposite
each other, still both read lit over the whole outer half of a penumbra:
where a fifth of the emitter is covered they agree a third of the time. The
binary answer they hand back pulls that pixel to fully lit, and the same
happens on the umbra side, so the soft edge was squeezed from both ends --
72% of its true width at sixteen samples per light. Every sample is now
traced. The default of one sample never reached the early out, so this costs
nothing at stock settings and costs exactly the rays that were asked for at
any higher count.

The history clamp collapsed to a window of no width. Its sigma was the
spread of the current frame's 3x3, and those nine values are counts of
blocked rays out of a handful: in the shallow ends of a penumbra they agree
often -- at one ray per light and a true visibility of 0.95, about two frames
in three -- and the measured spread is then exactly zero, pinning the
accumulated value to that binary answer. It was removing a third of every
penumbra. The spread is now floored with the standard error those ray counts
actually carry, with the usual two pseudo counts so the floor cannot collapse
along with the spread. It tightens on its own as the sample count rises.

The eight bit accumulator ratcheted. It re-reads its own rounded output every
frame, so once the step it wants to take is under half a quantization level
the value stops moving -- and not symmetrically: in the lit end of a penumbra
the occasional blocked ray is a step down large enough to land while the many
lit rays each ask for a step up too small to, so the value crept darker and
the edge spread. That was making a stock penumbra about 15% too wide, hiding
part of the other two. Rounding is now dithered per pixel and per frame, at
the cost of one hash and no memory.

Stock settings now measure 17/28/38/47/55/51/52 pixels of 10-90 penumbra
across the test scene where the geometry calls for 16.3/26.2/36.0/45.9/51.5/
51.5/51.5, and sixteen samples per light reproduce it exactly. Contact
hardening is now the curve the scene actually implies rather than a curve of
the denoiser's own.

The variance clamp already stops a moved blocker leaving its old shadow
behind, but it only fixes the value, not the weight: history_length carries
on as though the pixel had been converging all along, so the alpha stays at
one over the full window and the shadow's NEW position fades in over half a

difference from the converged reference is entirely the new shadow still
filling in.

How far the clamp had to move the history is a direct measure of how wrong it
was, so the window is now shortened in proportion. A history sitting inside
the window is not moved at all -- which is every pixel in the steady state --
so this costs nothing where nothing is wrong, and the still-camera penumbra
measures identically to before. The worst of the four channels drives it,
because they share one window and arriving late is worse than being brief.

falls from 3.45 to 2.35 and the pixels off by more than eight levels from
9.7% to 5.7%, with no measurable change to noise in either the umbra or the
penumbra after a camera cut.

The master `enabled` flag has a real reason to need a restart: vertex buffer
creation bits are fixed at upload time, so a mesh loaded while it was off has
nothing an acceleration structure could be built from. `directional/enabled`
never had that reason. It only chooses which of two shadowing paths a sun
takes, and both are rebuilt every frame; it was restart-required because it
had been declared so.

What it does need is to hold still for a frame. Whether a sun is raytraced
decides how many cascades it gets, and that has to be the same answer for the
culler, for the shadow atlas layout and for the light buffer, which run at
three different points in a frame; read on demand it could differ between
them and put cascades in the wrong atlas rects. So it is snapshotted once per
frame in RaytracingScene::update_frame_settings(), called from
RendererSceneRenderRD::update() before any viewport draws -- where Godot
already snapshots its own per-frame rendering settings. The two
demoted_shadow_* settings answer the same question from the other side and are
snapshotted with it, which also retires the caveat the fork guide carried
about dragging that slider costing a bad frame.

Verified the way the other live settings were: a project that writes the
setting at runtime renders the same frame as one that started with it on
(mean absolute difference 0.035 of 255, the residue of ten frames of
accumulation from before the write), and both differ clearly from one where
it stayed off (0.995, peak 72).

The guides carried three stale claims that this turns up, now corrected: the
tuning section said its knobs need a restart when every one of them is live,
the softness advice quoted the class reference's `0.5` for the sun without
noting that Godot uses the value as an angular radius, and the sample-count
advice was written when raising it was nearly free.

The BLAS cache re-validated each cached entry on every frame, and the check it
used was acceleration_structure_is_valid(). That is a _THREAD_SAFE_METHOD_, so
it took the rendering device's lock once per cached surface per frame -- twice,
because the caller checked again on the way past. In a scene of a couple of
thousand casters it was three quarters of the time that loop spent and a
quarter of the whole raytraced path's CPU cost.

The check was for a real case. A PrimitiveMesh rebuilds its surfaces on the
same RID whenever a property changes, and ArrayMesh.clear_surfaces() does the
same on purpose; the vertex buffer goes, and blas_create() registered the
structure as a dependency of that buffer, so the structure goes with it. A dead
structure handed to tlas_build() takes the whole build down.

But being freed along with that buffer is the ONLY way one of these structures
disappears without this cache doing it, so asking whether the buffer is still
the one the structure was built from answers the same question without the
lock: RID_Owner bumps a generation counter when it reuses a slot, so a buffer
RID that still compares equal is the same buffer, and its dependents are
therefore still alive. A surface that has gone away gives back a null RID,
which fails the same comparison. Both cases end where they did before, dropping
the entry to be rebuilt.

The stale-entry sweep also ran every frame to find entries nothing had asked
for. Entries are not eligible for sixty frames, so it now runs every eighth,
which costs a stale entry at most seven more frames of life.

In the hostile scene above -- three thousand props, sixteen lamps, a raytraced
sun, a spotlight on the camera -- the build half falls from 0.48 ms to 0.23 ms
per frame and the whole path from 1.28 ms to 1.00 ms, with every test scene
rendering identically and the penumbra measurements unchanged. A test that
grows a PrimitiveMesh and rebuilds an ArrayMesh at runtime confirms both still
produce a shadow of the new geometry.

GODOT_RT_DEBUG now also reports what this path costs the CPU, split into
gathering and building, averaged over 120 frames with peaks: the two halves
scale with different things, and which one a slow scene is paying for is not
guessable. The fork guide records what moved the number in testing -- chiefly
that a raytraced sun is two thirds of the cost and that its shadow distance,
not caster_distance_scale, is the lever.

Do not query the index for a light the sun's volume already covers
…
6560a50
```
Casters are gathered by querying the scenario's geometry index once per
raytraced light, and the pass counter throws away an instance a previous
light already claimed. It throws it away at the leaf, though, after the
traversal has descended to it, so overlapping lights pay for the same part of
the index over and over. In the stress scene sixteen lamps turned 2124 index
visits into 5164 and found 96 casters the sun had not already found.

A light whose bounds sit entirely inside a volume that is going to be queried
anyway cannot find anything that volume will not, so its query can be skipped
outright. That is not a corner case: a raytraced sun's caster volume is the
camera frustum swept towards the light, and in an interior, a street or a town
square it swallows the lamps whole.

The enclosed volumes are moved to the back of the list rather than removed
from it, because the per-element multimesh cull below asks a different
question of the same list -- whether one element of a multimesh is reached --
and consults the directional volumes only when scatter_casters lets it. With
scatter_casters set to Disabled, a list with the enclosed lamps missing would
lose exactly the elements those lamps were the only reason to include.

Gathering falls from 0.77 ms to 0.60 ms per frame in the stress scene, and the
whole raytraced path from 1.00 ms to 0.83 ms; with thirty-two lamps, from
1.05 ms to 0.84 ms. The caster count is identical before and after, as it has
to be, and every test scene renders to the same pixel.

Add the GTAO passes: depth prefilter, bitmask gather, filter

The first three quarters of a replacement for the screen space occlusion the
engine ships. Nothing calls these yet; the existing effect is untouched and
still the only one wired in.

The depth pyramid is new rather than the one the screen space effects already
build, for three reasons. That one is deinterleaved into four array slices, so
a shader reading it can only address its own slice -- workable for a disk of
scattered point samples, useless for a march that walks a straight line and
must read whatever texel the line lands on. It is based at half resolution, so
the innermost steps would have no full resolution depth to read. And it filters
toward the CLOSEST of each group of four, which dilates thin geometry across a
coarse texel's whole footprint; a march that reads one such texel early keeps
that horizon for every step after it. This one is full resolution, flat, and
biased toward the farthest, so thin geometry falls out of the coarse levels
instead of spreading across them.

The gather marches GTAO's slices but replaces the running horizon angle with a
32 sector occupancy mask, so two occluders with sky between them stay two
occluders and a thin wall stops occluding once the march passes behind it.
Sectors are resolved by their cosine share of the arc rather than by counting
set bits: equal weighting answers a different question from the one occlusion
asks, and the near field bounce approximation the forward shader applies on top
was fitted against the cosine weighted quantity.

Two things follow the reference implementation this is modelled on. The radius
can be held to a fixed share of the screen at every depth instead of a fixed
distance in the world -- without that the on-screen span shrinks with distance
until the steps land on the same texel and most of the sample budget is spent
re-reading it. And thickness follows the radius rather than staying a fixed
distance, or a march reaching ten times further at distance would push every
back face into the same shallow shell.

Reduced resolution changes only how many pixels get their own answer. The march
reach, its first step and the fade are all derived from the full resolution
pixel footprint, so halving it thins the far field rather than pulling the near
field apart, and the filter weights the result back up against the depth each
texel was actually computed on.

Selected by rendering/environment/ssao/method; the default is unchanged, so a
project that does not set it renders exactly as before. The legacy effect is
untouched -- not a mode inside it, a sibling that happens to write the same
buffer.

That last part is what keeps the rest of the renderer out of it. The forward
pass binds whatever texture is in RB_SCOPE_SSAO/RB_FINAL and never asks who
filled it, so the occlusion channel, the near field bounce approximation on top
of it, light affect, specular occlusion and the debug view all keep working
with no shader change. Radius, intensity, power and the fade come from the same
Environment properties the legacy effect reads. Detail, horizon and sharpness
describe the other estimator and are ignored.

Three bugs found by rendering it rather than by reading it.

The view space reconstruction took a normalized device position, but the two
terms the other screen space effects derive from the projection are expressed
for a UV in zero to one. Feeding one to the other put every sample in the wrong
place, which read as heavy occlusion everywhere with a bright hole at the
camera.

Elevation angles were taken as an unsigned three dimensional angle against the
view direction. They have to be measured inside the slice plane and carry a
sign: a sample lying flat on the shaded surface has zero elevation and must
occlude nothing, and an unsigned angle puts it in the middle of the arc
instead, which darkened every flat plane uniformly.

The slice basis was not orthonormal. Stepping along the slice at constant depth
gives a direction lying in the plane but not perpendicular to the view
direction, and measuring against a skewed axis puts every sample at the wrong
elevation. Samples at or below the shaded surface's own plane are now rejected
outright as well, since they cannot occlude the hemisphere above it.

Half resolution now differs from full by a mean of 1.14 of 255 across the test
scene, with 0.7% of pixels apart by more than 10 -- silhouettes, where the
weighted upsample has the least to work with. The near field is identical
because the march reach, its first step and the fade all come from the full
resolution pixel footprint either way.

Single view only for now; a stereo pair keeps the legacy effect.

Two references, because one number cannot separate a wrong implementation from
a method working as designed. Reference A traces the scene's real geometry and
is the ceiling any screen space technique is measured against. Reference B
marches the same cosine distributed rays against a depth buffer built from the
camera's own view, so an occluder the camera cannot see does not occlude; the
gap between A and B is what screen space costs, and the gap between B and the
shader is what this code gets wrong. The scene is ambient lit with a flat white
material, so dividing a render by the same render with occlusion disabled
recovers the occlusion term itself rather than something shading has mixed.

Against reference B, correlation with the reference by sample count: 0.62 at
two slices by four steps, 0.66 at three by six, 0.71 at four by eight, 0.79 at
six by twelve. The legacy effect sits at 0.74. The shipped default was two by
four -- visibly undersampled, and worse than the effect it was meant to replace.
It is now four by eight, where the bias vanishes and both the RMSE and the worst
case beat the legacy effect (0.066 against 0.088, and 0.41 against 0.57).

The depth pyramid moves to 32 bit float. Half float carries an 11 bit mantissa,
so at a view depth of six the quantum is about five millimetres -- the same
order as the depth difference between neighbouring pixels on a slanted plane,
which reconstructs coplanar neighbours to either side of the shaded surface at
random. A sample must now also clear a small elevation above that surface to
count as an occluder, since one lying within a few degrees of it is grazing
rather than occluding.

What is still wrong, measured and not yet fixed: moderately occluded regions
read about 0.14 too bright even at high sample counts, and fully open surfaces
about 0.04 too dark. Both are estimator errors rather than sampling noise --
they do not shrink with more samples.

Fix three defects the traced reference found in the occlusion
…
74a178e
```
The gather was measurably wrong in ways that did not shrink with more samples,
so more samples was never going to find them. Two references now bracket the
problem: one traces the real geometry, which is the ceiling any screen-space
method could reach, and one marches the same rays against a depth buffer built
from the camera's own view, which is what a correct implementation could reach.
The gap to the first is the method; the gap to the second is the code.

A CPU model of the gather sits alongside them and reproduces the shader exactly.
That is what localized each fault: where the model and the shader disagreed the
plumbing was wrong, and where they agreed but both missed the reference the
estimator was wrong.

The three defects:

Sector weighting had no Jacobian. Each of the 32 sectors was worth its share of
the arc, which is not what it covers. Sweeping a slice about the view direction
turns each sector into a ring whose circumference goes with the sine of the
angle from that axis, so a sector pointing back at the camera sweeps almost no
solid angle and one at the edge of the arc sweeps the most. The two sectors
either side of the surface normal were being counted about ten times too
heavily and the grazing ones half as heavily as they should be. The integral of
cos(t - n) * |sin t| has a closed form, so the weights are now evaluated
outright, stepping cos(2t - n) around by a rotation rather than calling a trig
function per sector. Occlusion also resolves as a ratio of two weighted sums
rather than a mean of per slice fractions, which makes an unoccluded surface
come out at exactly one whatever its orientation and whatever the dither picked,
while leaving the weighting between slices the one the integral asks for.

The march read a nearest sampler and reconstructed elsewhere. The depth that
comes back describes the surface at the middle of whichever texel the step
landed in, not at the point the step asked for. Pairing that depth with the
asked for direction put every sample off its own surface by up to half a texel
of depth slope, and on a plane seen at a glancing angle half of those landed
above the shaded point. The floor was occluding itself by a flat three percent
everywhere, steady enough to read as the effect working.

Steps were spaced quadratically. A horizon march can crowd its steps near the
shaded point because one early hit stands in for everything behind it. A mask
cannot: an occluder that falls between two steps is not approximated, it is
absent, and the far half of a quadratic march is where the gaps get wide enough
for a whole box to fall through one. Spreading the same eight steps evenly
roughly halves the error.

pixels, so on any viewport that is not square every elevation was measured
against an axis the samples did not lie on.

Thickness moves from 0.25 to 0.3, which is the joint optimum across a solid
scene and a thin one. It is a real tradeoff and now a documented one: a deeper
shell is more accurate on thick solid shapes, where a shallow one lets light
leak through the back of an object the camera cannot see behind, and less
accurate on foliage, railings and slats, where it closes gaps that are open.

Screenshots of a real interior showed the occlusion as harsh black wedges with
speckled edges, nothing like the soft field the synthetic scenes scored well on.
The estimator was not the problem. Modelled on a closed room with the camera
inside it, the gather scores 0.0112 mean absolute error and 0.927 correlation

validated on. Putting a FLAWLESS traced occlusion through the shipped output
curve reproduces the artifact exactly, and sends 3.7 percent of the frame to
pure black.

That is the whole finding. Scaling occlusion by subtracting a multiple of its
distance from white has a hard floor: at the stock intensity of two, every
visibility at or below 0.63 lands on exactly zero. An ordinary concave corner IS
about 0.63. So a third of the tonal range collapsed onto one flat value inside
the gather, before anything downstream saw it -- which is also why the filter
looked broken. It was averaging zeros with zeros. The curve's slope at the white
end is three, so it amplified the dither on the way in and then clipped it, and a
smooth field came out looking like a coin flip per pixel.

The curve is now a ratio. Same slope at the white end, so a lightly occluded
surface looks the way it did and existing tuning still means what it meant; it
approaches zero without arriving, so a corner stays a gradient. At intensity one
it is exactly the identity, which is what the harness measures. On the room:
mean absolute error 0.0480 to 0.0156, and the black fraction to zero.

Three other things came out of the same investigation.

Environment.ssao_intensity defaults to 2.0 and that number belongs to the legacy
estimator, whose obscurance is a proximity average rather than a visibility
integral and measures a fraction of the real deficit. This one reports the
deficit directly, so the same number doubles a figure that is already right. A
new ground_truth/intensity_scale, defaulting to 0.5, divides it back down rather
than moving an Environment default the legacy estimator still needs.

The half resolution stride was recovered in the shader as full_size.x divided by
gather_size.x. gather_size_for rounds UP and integer division rounds DOWN, so
that yields 2 at every even width and 1 at every ODD one -- at which point the
gather answers only for the top left quadrant and the result is magnified over
the rest of the screen. Roughly half of all viewport widths. The stride is now
passed in the push constant. Its signature is a brighter, smoother, left/right
asymmetric image, so it was not what the screenshots showed, but it is real.

Under scale_radius_with_distance the world reach was anchored to screen WIDTH via
uv_to_view_mul.x, which carries the aspect ratio, while a camera holds its

height now. The fixed-radius branch was already aspect invariant and is left
alone, with a comment saying so.

interior scene at 1280x720 -- the two existing scenes are both open, seen from
above, with a mean occlusion under one percent, so a correct occlusion barely
enters the range the transfer operates on: 0.3 to 0.7 percent of those frames

stops hardcoding the power so the shipped configuration can be scored at all,
and the comparison prints the fraction of the frame below one 8-bit code, which
is the number that would have shown this on day one.

All four engine changes are provably neutral on the existing scores: the new

The gather answers for full resolution PIXEL k * stride, whose center sits at
continuous coordinate k * stride + 0.5. The upsample inverted that with the
obvious form, (pos + 0.5) * source_size / dest_size - 0.5, which assumes instead

resolution render of the interior scene against a full resolution one at

this and nothing else.
