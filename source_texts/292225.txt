Description & Context
Fixes #315
Enables parallel reduction and aggregation for LINQ method chains on GPU devices. When data.AsStackEnumerable().AsParallel().Sum() is invoked inside [GpuKernel], the Roslyn AST transpiler emits cooperative warp shuffle down (__shfl_down_sync) and shared memory block reduction trees instead of sequential single-thread loops.
Additionally, this PR introduces contiguous batch storage (GpuBigUIntArray / GpuBigIntArray), vectorized Linq query extensions (SelectMultiply, Sum), and reusable CUDA Graph compilation (CompileToGraph) for arbitrary-precision integers (GpuBigInt). This allows large-scale polynomial commitments, inner products, and multi-scalar accumulation (MSM) in zero-knowledge proofs to execute with zero heap allocations and up to ~40x speedup over multi-threaded CPU PLINQ.

Detailed Highlights
GPU Stream Compaction (Blelloch Scan):
Added parallel BlockExclusiveScan and AddBlockSums for CUDA, enabling highly concurrent zero-allocation Where filtering.
Implemented multi-block scaling (rounded to powers of two) to prevent CudaErrorLaunchFailed on datasets larger than 2,048 elements.
Vectorized CUDA Graph Memory Management:
Eliminated dynamic buffer resizing in VectorWhereExpression. Sub-arrays are now statically allocated (with MemsetZero padding) to prevent topology invalidation during CUDA Graph capture (CudaErrorStreamCaptureInvalidated).
Unified parameter naming (hStream) across Roslyn transpiler templates to prevent fallback to the default stream (CS1739).
Compiler & Transpiler (Kassyi.GSharp.Compiler):
Enhanced StackLinqFusionRule.cs to recognize AsParallel() invocations within StackLinqChain.
Implemented parallel block reduction emission: transforms linear loops into grid-stride loops followed by warp shuffle down (__shfl_down_sync) and shared memory tree reductions in CUDA C++.
Fixed compiler warnings in WrapperEmitter.cs.
Standard Library (Kassyi.ZeroAlloc.Linq):
Introduced ParallelStackEnumerable ref struct and AsParallel() extension method on StackEnumerable.
Provided CPU fallback implementations and XML documentation comments for parallel sequences.
GPU BigNum Arithmetic & Vector LINQ (Kassyi.GSharp.Stdlib.GpuMath):
Batch Multi-Precision Storage: Added GpuBigUIntArray and GpuBigIntArray for contiguous, strided allocation of multi-precision integers in GPU device memory.
Vectorized Kernels (GpuBigIntVectorKernels.cu.cs): Implemented grid-stride block kernels for addition, subtraction, scalar multiplication, and multi-pass parallel sum reduction trees.
Vector LINQ Pipeline (VectorExpressions.cs, GpuBigIntVectorLinqExtensions.cs): Added deferred vectorized expression ASTs (AsVectorizedEnumerable, SelectMultiply, Sum).
BigNum StackLinq Extensions (GpuBigIntStackLinqExtensions.cs): Added Select, Where, Sum, Max, Min, Average, Count, and Aggregate over ParallelStackEnumerable<GpuBigInt>, constructing balanced binary evaluation trees via ArrayPool.
CUDA Graph Engine (GpuBigIntExpr.cs, GpuBigIntExecutableGraph.cs): Implemented warm-up pass, AST-to-Graph compilation (CompileToGraph), and one-shot execution (EvaluateWithCudaGraph), eliminating CPU launch latency for repetitive evaluation.
Benchmark Suite (Henicos.Benchmarks):
Implemented GpuBigIntLinqBenchmark.cs comparing CPU PLINQ, GPU Sequential AST, GPU CUDA Graph, and GPU Vectorized Array pipelines.

Key Architectural Takeaways
Near 40x Speedup & 255M ops/sec Throughput at 1M Scale ($N = 1,048,576$):
For cryptographic / ZKP scalar accumulation workloads, GpuBigIntArray + vectorized CUDA Graph achieves 4.10 ms (255.75 million 256-bit operations/sec), outpacing multi-threaded CPU PLINQ (163.80 ms / 6.40 M ops/sec) by 39.95x.
Launch Overhead Elimination (Over 1,400x Graph Gain):
Naive sequential kernel launches suffer from Windows driver / CPU scheduling latency (~33 ms to ~143 ms). Precompiling the reduction pipeline into native CUDA Graphs (CompileToGraph) eliminates host-side dispatch overhead, achieving up to 1,431x launch speedup over sequential execution.
One-Shot vs. Precompiled Trade-off:
EvaluateWithCudaGraph (one-shot graph capture) incurs on-the-fly graph instantiation overhead. For high-frequency pipelines (e.g. proof generation loops), precompiling via .CompileToGraph() once and calling .Execute() repeatedly is strictly optimal.
