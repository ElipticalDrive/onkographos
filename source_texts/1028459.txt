One potential problem we have with batch processing is that any one slow item will clog up the whole batch. This pr implements a queueing method instead, where we keep N queues that each have their own workers. There's still a chance of individual items backlogging a queue, but we can try increased concurrency here to reduce the chances of that happening

Critical — shared pool torn down on every strategy close/rebalance
SimpleQueueProcessingStrategy.close() (and join(), which re-calls close()) always runs self.queue_pool.shutdown(). The factory creates one FixedQueuePool and reuses it for every create_with_partitions call.
Arroyo’s StreamProcessor closes then joins the strategy on partition revoke/reassign. After the first rebalance, workers and queues are shut down, but factory.queue_pool still points at that dead pool. The next strategy submits into shut-down queues / dead workers until process restart. factory.shutdown() only runs on full consumer exit, so it does not recover this.
```
def close(self) -> None:
    self.shutdown_event.set()
    self.commit_thread.join(timeout=5.0)
    self.queue_pool.shutdown()  # kills factory-owned pool
```
Fix direction: Own the pool on the strategy (create in create_thread_queue_parallel_worker, shut down only there), or recreate the pool in create_with_partitions and never shut it down from strategy close while the factory still holds it. Also make join() drain/wait without calling close() again.

High — offsets marked committed without a confirmed Kafka commit
```
self.commit_function(committable)
for partition, offset in committable.items():
    self.queue_pool.offset_tracker.mark_committed(partition, offset)
```
commit_function wraps Arroyo Commit and is invoked without force=True. Under ONCE_PER_SECOND (and similar policies), many calls only stage offsets. The tracker still advances last_committed and drops state via mark_committed.
That diverges tracker state from broker commits. On rebalance/crash before a forced flush, offsets may never have been committed (reprocessing), or other logic may assume tracker state mirrors Kafka. If commit_function raises, the outer except logs but prior partial behavior is ambiguous; the success path unconditionally marks committed after a possibly no-op policy-gated call.
Fix direction: Only mark_committed after a successful forced commit (or after an API that reports what was actually committed). Prefer committing from the main consumer thread / poll() with force=True on shutdown/rebalance join, matching CommitOffsets.join().

Medium — join() does not drain work or final-commit; double-shutdown with close()
Arroyo requires: close() (non-blocking) → join(timeout) (drain in-flight work, commit offsets, release resources). Here:
