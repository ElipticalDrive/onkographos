Issue body actions
Ported from havokentity/demont-engine#100.
Add proper participating-media raymarching (delta / ratio tracking on density, HG phase with optional dual lobe, NEE through media) as a SHAPE_VOLUME BVH variant, rather than the ad-hoc slab march.
Status in this fork
APPLIES-BUT-SUPERSEDED by docs/NEXTGEN_PLAN.md Step 5b.
What actually shipped is a hand-rolled inline cloud march in shaders/PathTrace.slang (L10229 per docs/NEXTGEN_PLAN.md Appendix A) plus shaders/CloudsRaymarch.slang / CloudsComposite.slang. The parent's scoped deliverables never landed: there is no VolumeRaymarch.slang, no SHAPE_VOLUME BVH leaf variant, and no delta/ratio tracking.
Two fork-specific facts:
The CloudsRaymarch/CloudsComposite pre-pass is built on Vulkan (src/rhi_vulkan/VulkanDevice.cpp:1819, :1822) but never dispatched, because CloudsComposite's only call site is inside the use_engine_tonemap block and src/engine/Engine.cpp:12873 sets backend_is_metal = false.
shaders/GodRays.slang — the issue's other named consumer — has no Vulkan pipeline at all (see the ported #266 / #290).
docs/NEXTGEN_PLAN.md Step 5b names this as "ratio-tracking volumetric integrator (M)" and Step 5 requires each item to carry a unit test against the cited formula or reference table. That is the supersession: same technique, narrower scope (no BVH SHAPE_VOLUME refactor), tied to the planetary cloud/atmosphere march.
Acceptance criteria
Ratio-tracking integrator replaces the rectangle-rule cell weighting in the live cloud march (see the ported #287 — the Beer-Lambert-exact weight is the cheap first step).
HG phase, single + multi-scatter, with NEE transmittance ratio-tracked back to the light.
A unit test against a cited reference (per docs/NEXTGEN_PLAN.md Step 5's rule), not just a golden.
Cloud goldens re-pinned with owner sign-off; the change is attributable.

Verdict: STILL OPEN. No integrator work landed. One correction to the body.
Confirmed absent:
No shaders/VolumeRaymarch.slang. ls shaders/*.slang = 34 files; the volumetric-adjacent ones are CloudsRaymarch.slang, CloudsComposite.slang, PathTraceCloud.slang, GodRays.slang.
No ratio / delta tracking and no SHAPE_VOLUME: grep -rn "ratio_track|ratioTrack|deltaTrack|SHAPE_VOLUME" shaders/ src/ returns nothing.
PathTraceCloud.slang is not an integrator — it is the hash/fbm noise field module (cloud_hash_u32, cloud_hash, cloud_value_noise), imported by PathTrace.slang:2136 and CloudsRaymarch.slang:81. The march itself is still inline in PathTrace.slang.
Correction to the body
The bullet "the CloudsRaymarch/CloudsComposite pre-pass is built on Vulkan but never dispatched" is now only half right:
clouds_raymarch IS dispatched on Vulkan. src/engine/Engine.cpp:13248-13262 — gated on push.clouds_runtime[0] == 1u (r_clouds_mode == procedural_raymarched), push.clouds_p1[3] > 0, the pipeline + ping-pong textures + cloud_trans_tex being allocated, and denoiser_active_. Nothing backend-gated.
clouds_composite is still never dispatched on Vulkan. Its only bind site is src/engine/Engine.cpp:15021-15024, which sits inside the if (use_engine_tonemap) { block spanning :14750-:15738, and use_engine_tonemap is (tonemap_pipeline_id_ != 0 && !kind_is_optix && backend_is_metal) at :13904-13905 with const bool backend_is_metal = false; hard-coded at :13901.
Net effect on Vulkan today: the raymarch pre-pass runs and its cloud_trans_tex output is consumed downstream (StarsComposite / AuroraComposite), but its clouds_color_tex is never alpha-blended into the HDR — so in procedural_raymarched mode the engine pays for a march whose colour is discarded. That is arguably its own bug and may deserve splitting out; it does not change this issue's verdict.
shaders/GodRays.slang still has no Vulkan pipeline (no build_pipeline("godrays", ...) in VulkanDevice.cpp), so the second named consumer is unchanged too. All four acceptance criteria unmet.
