Later optimisation, once #399 (projection blocking) and #398 (relaxation) are in and meshes reach millions of nodes.
GPU-friendly steps (per node / per element, no global solve):
transfinite interpolation filling the blocks;
elliptic smoothing (Winslow / Thomas–Middlecoff) — Jacobi-style sweeps, the dominant cost on big meshes;
projection onto analytic surfaces (plane, cylinder, sphere, cone, torus); free-form faces stay on the CPU kernel;
quality metrics per element;
node relaxation (Node relaxation: relax spikes inside a sphere of influence, surface nodes sliding on the geometry (UV) #398) with a node colouring so neighbours never move in the same pass.
Stays on the CPU: block planning, interval assignment, the provenance plan (#402), B-rep queries on free-form surfaces.
How: wgpu compute shaders (already a dependency for rendering), behind the same API with a CPU fallback (results identical within tolerance; tests compare both). Must not break wasm (use WebGPU there or the CPU path).
Worth it when: smoothing/projection time exceeds a few seconds — benchmark first on a 1M-node block mesh and report CPU vs GPU.

Every stage is sequential today (no rayon in fieldcraft-mesh), so the honest comparison for a GPU port is against a multi-threaded CPU version as well, not only against this baseline. Linux baseline before any GPU work, with a multi-threaded CPU version as the comparison. Code: bluecmd/fieldcraft@aaf7969 (branch mesh-gpu on upstream develop e9ccf10), cargo test -p fieldcraft-mesh --release --lib tapered_block_benchmark -- --ignored --nocapture (project/bench.rs).
Mesh: one tapered block (a square frustum, 2 wide at the bottom, 1 at the top, 1 high, six analytic planes), 99 divisions a side: 1 000 000 nodes, 970 299 hexes, project_mesh with Elliptic smoothing and 3 sweeps. The Windows harness from the earlier comment was not kept, so this block is a new one and its taper may differ; compare within this table, not with the 7950X numbers.
How measured: mean of 3 runs per row. "Smoothing" is the pipeline minus the same pipeline with Smoothing::None. "Certified" is the element_quality loop timed on its own over the output mesh. Rows run one after another in one process.
What changed for the threaded rows:
The certified loop and the smoother's whole-mesh scaled-Jacobian scans run on fieldcraft-parallel blocks and are folded in element order, so the mesh is bit for bit the same as develop on any thread count ("Sequential" rows).
"Coloured" also changes the sweep order. Movable nodes are put into classes no two of which share an element (greedy in node order: 8 classes on this grid). Each class moves in parallel against a frozen grid, so every move reads the same neighbours on 1 or N threads. It keeps the per-node guard (full / half / quarter step, accepted only if the scaled Jacobian and edge ratio around the node hold) and the whole-element certificate.
amd64: Xeon D-1541 (8 cores / 16 threads, 2.1 GHz), Kubernetes pod limited to 14 CPUs on a lightly loaded node.

What this says:
Certified quality dominates. It is 59–69 % of the sequential pipeline and runs 6× (amd64) to 14× (GB10) faster on threads, with no change to the result.
The sweep order must change before a parallel smoother can help. The current sweep moves one node after another in place, and each acceptance check reads neighbours already moved in that sweep. Threading only the scans around it leaves smoothing at 11–17 s; the coloured order brings it to 3–5 s. On this block it costs nothing on one thread, and min/mean SJ agree to 4 decimals.
After threading, the whole 1M-node pipeline takes 8 s on GB10 and 16 s on the D-1541. Of the 8 s, about 3.6 s is certified quality, 3.0 s smoothing and about 1.5 s the parts still sequential (TFI, targets, gap, boundary tags). That is what a GPU port can still win: a few seconds at 1M nodes, more as meshes grow.
Question before going further: may the coloured order become the only order of project_mesh's guarded sweeps? It keeps results deterministic and independent of the thread count, but the meshes mesh.project produces would no longer match develop bit for bit; no oracle fixture uses a projected mesh. The GPU port needs that order too, so the CPU path would stay its exact oracle algorithm (same order, f64).
Proposed next steps:
PR 1 (CPU): the parallel certified loop and scans (bit-identical); if you agree, the coloured sweeps as the default order.
PR 2 (GPU): a fieldcraft-mesh-gpu crate at L7 like lbm-gpu, behind a backend hook in mesh, wasm untouched. It covers the coloured Winslow sweep of free interior nodes, with boundary and curve nodes kept on the CPU, and a GPU pre-pass for certified quality. GB10's f64 rate is low, so the plan for the pre-pass: certify in f32 with a safety margin, and send only elements the f32 pass cannot settle back to the CPU's f64 Bernstein certificate. The certificate itself stays on the CPU. Tests compare the GPU path with the coloured CPU path within a stated tolerance.
