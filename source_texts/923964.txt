Summary
Follow-up to PR #58 — fixes the camera-quaternion inversion bug flagged in Devin Review on crates/aec_export/src/gltf_export.rs:800.
The bug. camera_lookat_components built the 3×3 rotation matrix m in row-major order (m[row][col]), but mat3_to_quat documents and implements the column-major convention (m[col][row]) — using the standard qx = (m[1][2] - m[2][1]) / s extraction formula. Feeding a row-major matrix into a column-major extractor computes the quaternion of Rᵀ, which is the inverse rotation. Every camera node in the exported glTF therefore had an inverted orientation: rotating glTF's local forward (0,0,-1) by that quaternion produced a vector pointing away from the target instead of toward it.
Concrete example (from Devin Review): camera at (5, 0, 0), target (0, 0, 0), up (0, 1, 0):
Correct R (columns = right, up, -forward) maps local -Z → world (-1, 0, 0) — toward origin.
Buggy R (row-major fed to col-major extractor) maps local -Z → world (+1, 0, 0) — away from origin.
Light orientations were unaffected (they use direction_to_quat, which is axis-angle / matrix-convention-independent).
The fix. Restructure the matrix construction so each top-level array element is a column (basis vector), not a row:
```
// OLD (row-major, wrong):
let m = [
    [right[0], recomputed_up[0], -forward[0]],
    [right[1], recomputed_up[1], -forward[1]],
    [right[2], recomputed_up[2], -forward[2]],
];

// NEW (column-major, matches mat3_to_quat):
let m = [
    right,
    recomputed_up,
    [-forward[0], -forward[1], -forward[2]],
];
```
This is the architecturally correct fix (matrix convention now matches at the construction site) rather than a workaround that transposes at the boundary.
Why no regression test caught this on the original PR. The existing 16 unit tests and 5 integration tests in gltf_export only asserted on translation, camera intrinsics (yfov / znear / zfar / aspect), and structural fields (mesh / material / light counts) — none of them exercised the quaternion value. This PR adds 3 regression tests that close the gap.
Tests
Three new regression tests + one helper in gltf_export::tests:
rotate_by_quat(q, v) — applies a unit-quaternion rotation to a vector using the standard v + 2 * cross(q.xyz, cross(q.xyz, v) + q.w * v) formula. Used by every camera-orientation test.
camera_lookat_quaternion_rotates_local_forward_toward_target — 4 concrete cases (+X→origin, +Z→origin, diagonal, off-axis with non-origin target). For each, asserts rotate_by_quat(q, [0,0,-1]) aligns with the (target − position) unit vector to within 1e-5. This is the direct functional contract of camera_lookat_components.
camera_lookat_quaternion_is_not_the_inverse_rotation — explicitly checks dot(rotated, to_target) > 0 for a known-buggy case. The old row-major code would have produced dot ≈ -1 here; the fixed code produces dot ≈ +1. This test would fail loudly under the previous bug.
camera_lookat_quaternion_recomputed_up_matches_world_up — verifies the rotated local +Y aligns with the recomputed_up vector (Gram-Schmidt orthogonalization output), confirming the second column of the matrix is correctly placed.

`camera_lookat_components` previously laid out the lookAt rotation
matrix in row-major form (m[row][col], with each top-level array
holding the x/y/z components of right/up/-forward respectively) but
fed it into `mat3_to_quat`, which indexes its input as m[col][row]

rendering libraries.

The two indexing conventions disagree on a rotation matrix R by
exactly the transpose. Since R is orthogonal, R^T = R^{-1}, so the
extracted quaternion was the INVERSE of the intended rotation. Every
camera node in every exported glTF file had its local -Z (the glTF
camera 'forward' axis) pointing AWAY from the target instead of
toward it. Lights are unaffected because they use direction_to_quat
(axis-angle, independent of matrix convention).

The fix rewrites the matrix construction so each top-level element
of `m` is a column basis vector:

  m[0] = right       (image of local +X)
  m[1] = recomputed_up  (image of local +Y)
  m[2] = -forward    (image of local -Z)

This produces exactly the m[col][row] layout mat3_to_quat expects;
the extracted quaternion is now R, not R^{-1}.

3 new regression tests rotate (0, 0, -1) by the camera quaternion
and assert the result aligns with (target - position):

- camera_lookat_quaternion_rotates_local_forward_toward_target —
  four position/target/up cases including the bug-report example.
- camera_lookat_quaternion_is_not_the_inverse_rotation — pins the
  dot-product sign so the row/col layout can't silently regress.
- camera_lookat_local_up_aligns_with_world_up — pins the local +Y
  → world +Y contract for the standard up vector.

📝 Info: Gram-Schmidt fallback correctly handles degenerate forward ∥ up case
When forward is (anti-)parallel to up, cross(forward, up) collapses to near-zero. The old code's normalize fallback (line 925-926) returns [0, 0, 1] which is NOT guaranteed to be perpendicular to forward, producing a non-orthonormal rotation matrix. The new fallback at lines 823-847 picks the world basis axis with the smallest |forward[i]| component (guaranteed to be linearly independent from forward), then applies Gram-Schmidt to make it exactly orthogonal. I traced this through the pathological case forward=[0,-1,0], up=[0,1,0]: abs_x=0 is the smallest, so alt=[1,0,0], proj=0, effective_up=[1,0,0] — correctly perpendicular to forward. The threshold 0.999_999 (~0.08° from parallel) provides adequate margin for float noise.

Thanks for the confirmation — the Gram-Schmidt route was the architecturally correct fix here vs. the easier-but-broken "just return [0,0,1] and hope" fallback. Two notes for completeness:
Why the smallest-|forward[i]| heuristic, not a fixed axis: picking a fixed axis (say always [1,0,0]) would fail when forward happens to be parallel to that axis (e.g. camera pointing along +X with up [1,0,0] — pathological but representable in a procedurally generated test fixture). Choosing the axis with the smallest |forward[i]| guarantees the projection residual alt - proj·forward has magnitude sqrt(1 - min(|forward[i]|²)) >= sqrt(2/3) ≈ 0.816, which is well-conditioned for the subsequent normalize.
Why threshold 0.999_999 (~0.08°) instead of a tighter or looser bound: below ~0.08°, cross(forward, up) has magnitude sin(angle) < 1.4e-6, which after normalization amplifies float noise by ~7e5×. Above that, the standard cross(forward, up) path remains numerically stable. The orthonormality test I added (camera_lookat_rotation_matrix_is_orthonormal_even_in_degenerate_case) pins the boundary case at forward = -up exactly, so any regression in either branch trips the test.

When the requested forward direction is (anti-)parallel to the supplied
`up` (a common case: plan-view camera looking straight down at a floor
plan with world +Y up), `cross(forward, up)` collapses to zero and
`normalize` returns a fallback `[0, 0, 1]` that is not perpendicular
to forward. The resulting 3x3 matrix is non-orthonormal and the
extracted quaternion is a slightly distorted rotation.

Fix: detect the degenerate case via `|dot(forward, up)| > 0.999_999`
and replace `up` with a Gram-Schmidt-orthogonalized alternate world
basis axis — picking the axis with the smallest |forward[i]| component
so the projection residual is well-conditioned. The remaining cross
product is then well-defined and the matrix is guaranteed orthonormal.

Adds two regression tests that pin the new contract:
- `camera_lookat_exactly_degenerate_forward_equals_up_returns_finite_quaternion`
  now also asserts the lookAt invariant (rotated local -Z aligns with
  target direction) — previously only finite/unit was required.
- `camera_lookat_rotation_matrix_is_orthonormal_even_in_degenerate_case`
  probes the three local basis vectors and verifies unit length +
  mutual perpendicularity after rotation.

Good observation — applied as 57d79e7. recomputed_up is now normalized for symmetry with the adjacent right construction.
Rationale: while mathematically |cross(right, forward)| = |right| · |forward| · sin(90°) = 1 exactly, the cross product itself accumulates a few ULPs of float noise (~1e-7 at f32 precision). The downstream mat3_to_quat uses sqrt(trace + 1) and divides — both numerically stable, but the residual still propagates into |q| - 1 by a couple of ULPs. Normalizing here:
Keeps the rotation matrix orthonormal to f32 precision (rather than to cross-product residual)
Matches the pattern at the adjacent let right = normalize(cross(forward, effective_up)) line
Costs one sqrt + 3 muls per camera (negligible — there's only a handful per export)
Tightens the orthonormality test bound (camera_lookat_rotation_matrix_is_orthonormal_even_in_degenerate_case now passes with < 1e-7 rather than < 1e-5, though I left the test threshold at the broader bound to avoid spurious failures on different f32 implementations)
