Texturing with greedy meshing?
Question
I'm currently working on building a block-style terrain system, and for efficiency's sake I'm using a greedy algorithm to do the meshing. The problem is that because a single quad can now represent many many block faces, I have no idea how to do texturing; I can't just map the corners of the quad to some coordinates on a texture atlas because the blocks can be arranged completely arbitrarily. Help?

Yeah in voxel-polygon-skinning renderers combining aligned faces usually reduces vertex count by over 20x! but it fundamentally necessitates the use of texture packing, i created an ultra fast left leaning tree to ensure good memory use (little or no gaps) and fast packing (no more than log2(face bount) iterations to find a spot), i use 3D texture arrays to avoid state changes between chunks and i dynamically repack texture layers as it's associated chunks become unloaded.
Keep in mind however that any kind of linear speed-up type optimisation (like optimal quad meshing or the lazier greedy quad meshing) will really not go as far as you would like, ultimatey you need to use optimisations which scale up with view distance (such as octree dynamic LOD generation) the reason for this is that view distance exponentially increases the number of loaded blocks so a 20x vert reduction will likely lead to only a 2-3x view distance improvement.
For many decades all GPU's have been able to handle over 2 million polygons which translates to over 512x512 view distance (once you do the basic things like bury algorithm and view frustum culling) it would be INCREDIBLE to play a minecraft with infinite view distance but at this point i suggest focusing on game-play mechanics, difficult and cunning enemies, interesting and inventive objectives, robust and useful interaction mechanics, these are all places where Minecraft falls flat on it's face and they are all places where you can swoop in and succeed as a game developer!
I suggest keeping your advanced graphics technology out of your game engine and in it's own test bed untill it's ready, otherwise your game itself will suffer and be to hard to complete.
I made my first Minecraft clone within one year of programming: https://www.planetminecraft.com/project/new-c-driven-minecraft-client-461392/
But it has taken me over a decade to make a sparse voxel octree which renders fast and beautifully on any machine and which has both high speed modification and efficient on disk compression.
Have a lovely day! Best of luck!

another approach that you could consider is, in addition to your vertices, also sending a 3d "voxel id texture" to the shader, the same size as the chunk, containing texture IDs for each voxel in the chunk. make sure it is linearly sampled of course!
for each fragment in the shader, you would then determine which texture the fragment should be shaded with by reading the 3d "texture id array" at the corresponding voxel position. once you know which voxel texture from your texture array to use, you shade the voxel like normal using that texture. the UV coordinates for the fragment can be found by fmod(spatial fragment position, voxel size) / voxel size.
this method removes the need to send UV coords with your vertices, as they are automatically calculated for each fragment. however, ideally you will need to have a 2d texture array containing all the voxel textures you need to use. i think that setup is pretty common though. you could probably do this with a texture atlas too, but it would take some additional thinking.
lmk if u have questions :)
