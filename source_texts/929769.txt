This PR adds atomic compare-and-swap to the driver/storage API via HTTP-style ifMatch / ifNoneMatch preconditions on setItem and setItemRaw. Useful for atomic swaps or write-once object storage.
```
// Atomic create-only (write-once objects):
await storage.setItem(`/objects/${hash}`, blob, { ifNoneMatch: "*" });

// Optimistic swap (HEAD/refs):
const { etag } = await storage.getMeta("/refs/HEAD");
await storage.setItem("/refs/HEAD", newCommit, { ifMatch: etag });
// → throws CASMismatchError if HEAD changed since the read
```
API
setItem(k, v, { ifMatch?, ifNoneMatch? }) returns { etag } when CAS opts are passed; void otherwise.
getMeta(k) returns etag?: string on CAS-aware drivers.
CASMismatchError on precondition failure; CASUnsupportedError thrown upfront when CAS opts hit a driver lacking flags.cas (no silent precondition-skip).
Cross-bundle catches: prefer CASMismatchError.is(err) / err.code === "ERR_CAS_MISMATCH" over instanceof (driver code and bundled main each carry their own class definition by design — drivers transpile per-file, the rest of src is bundled).

Merge Risk: 🟡 Moderate · up to 9cba6
Conditional writes can still lose updates or report success when no write occurred on Redis, PlanetScale, S3, and db0. Existing PlanetScale tables may fail plain writes if the etag column migration does not apply. These issues should be resolved before merging.
Security architecture risk: 🟠 High · up to 9cba6
The new atomic-write guarantee is not consistently enforced. Concurrent operations can bypass preconditions in several drivers, and HTTP version-token handling can allow stale updates or report failure after a write has already occurred. These are data-integrity risks; the reviewed paths do not establish a new authorization bypass.
Retained concerns
High · security · inferred: Filesystem, db0, and PlanetScale advertise CAS while implementing general conditions as a read/check followed by a separate write under an instance-local lock. Separate instances can validate the same old token and both overwrite successfully. Unconditional writes and deletes bypass these locks, so even one instance can violate the precondition between validation and commit. The documented cross-process limitation and genuinely atomic filesystem create-only path narrow, but do not resolve, the mismatch with the shared atomic-write contract.
High · security · inferred: Concurrent Redis CAS operations share one cached client and therefore connection-scoped WATCH state. Two operations can both read the old value before either executes; the first EXEC clears the watches, allowing the second EXEC to succeed without protecting its earlier check. A mismatch or error in another operation can also issue UNWATCH against shared state. This defeats the single-winner guarantee without requiring multiple processes. The SET NX create-only fast path is not affected by this ownership problem.
Medium · security · inferred: HTTP GET reads the value and then independently reads metadata for the newly exposed ETag. A concurrent write between those reads can produce a response containing old bytes with the new version's token. An HTTP consumer using that returned token in If-Match can then overwrite the intervening update despite working from stale data. This affects consumers of the endpoint's GET validator; the bundled HTTP driver's value-reading methods discard that validator.
Medium · security · inferred: The new HTTP client advertises CAS and sends the mutating PUT before checking whether the server supports it. The merge-base server ignores conditional headers and performs an unconditional write; only afterward does the new client detect the missing ETag and throw CASUnsupportedError. Thus a mixed-version deployment or server rollback can overwrite an existing value during an ostensibly create-only operation while reporting failure. Current-server 412/501 handling prevents this case only when requests reach an upgraded server.
Security review details
Security Blast Radius
inferred — The demonstrated risk is integrity of keys writable through affected driver instances, not unrestricted access to an entire tenant or environment. Redis WATCH interference can cross operations on different keys sharing one client, although each eventual mutation still targets the key selected by its authorized operation. Deployment-specific tenant, credential, and datastore boundaries were not supplied.
Security Findings and Attack Paths
inferred — Concurrent permitted writers can invalidate the advertised single-winner guarantee: filesystem and SQL checks can become stale before mutation, while one Redis operation can consume or clear another operation's watches. Applications relying on CAS for protected state transitions can therefore accept an overwrite they intended to reject.
inferred — HTTP introduces two distinct integrity paths: an old response body can receive a newer ETag, and an old server can mutate state before the new client reports unsupported CAS. Neither path requires bypassing the existing authorization hook.
Trust Boundaries and Controls
observed — Important fail-closed controls are present: unsupported local drivers are rejected before write dispatch, current servers translate condition failures to explicit HTTP errors, filesystem create-only uses atomic link creation, and Redis create-only uses SET NX. These controls limit the concerns to the affected execution and compatibility paths rather than all conditional writes.
Hardening Proposals
proposed — Align capability advertisement with enforceable guarantees: use backend-atomic conditional mutations where available, fail closed for unsupported condition scopes, and give each Redis WATCH transaction exclusive connection ownership through commit or cleanup.
proposed — Return values and validators from one consistent read. Establish a server-version or protocol-capability guarantee before enabling conditional HTTP mutations, including during rollback, and validate these guarantees with interleaved writers and mixed-version scenarios.
