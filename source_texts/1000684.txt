🧹 Nitpick comments (4)
shaders/hlsl/lights.hlsli (4)
87-117: NdotL early-out successfully addresses previous concern.
The early-out check at lines 107-109 correctly prevents specular highlights when the surface faces away from the light, resolving the issue raised in the previous review.
However, traditional Blinn-Phong modulates the specular term by a material specular reflectance property (e.g., specularColor or specularStrength from a material or specular map), not just lightColor. Consider adding a material specular parameter to make the specular response physically plausible and artist-controllable.
🔎 Example: Adding material specular parameter
```
 float3 CalculateBlinnPhong(
     float3 lightDir,
     float3 viewDir,
     float3 normal,
     float3 lightColor,
     float3 albedo,
+    float3 specularColor,
     float shininess)
 {
     // Diffuse (Lambertian)
     float NdotL = max(dot(normal, lightDir), 0.0);
     float3 diffuse = NdotL * lightColor * albedo;
 
     // No specular if surface faces away from light
     if (NdotL <= 0.0)
         return diffuse;
 
     // Specular (Blinn-Phong)
     float3 halfDir = normalize(lightDir + viewDir);
     float NdotH = max(dot(normal, halfDir), 0.0);
-    float3 specular = pow(NdotH, shininess) * lightColor;
+    float3 specular = pow(NdotH, shininess) * lightColor * specularColor;
 
     return diffuse + specular;
 }
```
You would then need to update all call sites to pass an appropriate specularColor (e.g., float3(1.0, 1.0, 1.0) for non-metallic, or derived from a specular map/material property).
130-147: Consider adding material specular parameter for consistency.
This specular-only function has the same consideration as CalculateBlinnPhong: the specular term should ideally be modulated by a material specular property for physical correctness, not just lightColor.
165-179: Unused metallic parameter should be addressed.
The metallic parameter is passed but never used. In physically-based workflows, metallic typically affects the Fresnel term and specular response. Either integrate it into the lighting calculation or remove it from the signature to reduce API surface area and avoid confusion.
202-231: Spot light logic is correct; consider parameterizing radius.
The cone attenuation and distance attenuation calculations are correctly implemented. The hardcoded radius = 50.0 at line 217 is acknowledged in the comment but could be replaced with a SpotLight struct member in a future update for greater flexibility.
