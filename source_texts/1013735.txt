I suspect this is because PontZen packs colour into a single integer attribute rather than the standard red/green/blue byte fields. Is there a spec of the packed layout I can use to unpack it correctly, or a reference unpacker I can crib from?

Hi, standard .ply colour readers won't work on PontZen output. PontZen writes a single 32-bit unsigned-integer attribute per point that encodes four channels. This lets the OpenDPC Unity player upload the whole sequence to VRAM in one pass and unpack per-channel inside the vertex shader. Standard loaders ignore the integer attribute (or misinterpret it as a generic 32-bit scalar) and fall back to default colours, which is the garbled result you're seeing.
Reference unpack (Python, plug into whichever .ply parser you use):
```
import numpy as np

def unpack_pontzen(packed: np.ndarray):
    # packed: uint32 array, shape (N,)
    r = (packed >>  0) & 0xFF
    g = (packed >>  8) & 0xFF
    b = (packed >> 16) & 0xFF
    l = (packed >> 24) & 0xFF
    return np.stack([r, g, b], axis=-1).astype(np.uint8), l.astype(np.uint8)
```
In three.js, equivalent shift-and-mask in the vertex shader on a uint attribute. The geometry stays in the standard x/y/z float fields, no special handling there. One quirk: the luminance byte is not redundant with R/G/B. It's stored as a separate channel so the renderer can choose between RGB display and a luminance-only fallback (used by the JND sub-platform for one of the diagnostic modes) without re-deriving luminance per frame. If you want geometry-only without dealing with the packed attribute, the underlying point positions are unchanged — drop the colour attribute entirely and you'll get a uniform-grey viewer with correct geometry.
