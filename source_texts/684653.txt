📖 Explanation — head 2a6ef6a · 2026-10-22
Background
render-test is the harness slang-test uses to run compute tests on real GPUs. For each TEST_INPUT it creates the resource and binds it to the shader parameter. For textures, that work is in assignTexture (tools/render-test/render-test-main.cpp):
It creates the texture with ShaderResource usage for Texture2D(...) and with UnorderedAccess usage for RWTexture2D(...). The choice comes from srcVal->textureDesc.isRWTexture, which the input parser sets only for the RW* spellings.
If the parameter is a descriptor handle, it asks slang-rhi for a handle with a DescriptorHandleAccess of Read or ReadWrite. On Vulkan, slang-rhi writes Read as a sampled-image descriptor and ReadWrite as a storage-image descriptor (BindlessDescriptorSet::allocTextureHandle). It does not check the texture's usage.
Key fact. On SPIR-V and D3D12, DescriptorHandle<T> is laid out as a plain uint2 (slang-type-layout.cpp, the DescriptorHandleType case). Reflection reports uint2, not Texture2D.Handle. On CUDA, CPU and Metal the layout is T itself, so render-test binds the texture the ordinary way there.
Deep background (skippable)
A shader reads a texture through a descriptor. Vulkan has a sampled image type (read-only, can filter through a sampler; an SRV on D3D12) and a storage image type (read/write, no filtering; a UAV on D3D12). A texture's usage flags are fixed when it is created. A storage-image descriptor is only valid for an image created with VK_IMAGE_USAGE_STORAGE_BIT; otherwise the validation layer reports VUID-VkWriteDescriptorSet-descriptorType-00339 and the behaviour is undefined.
In bindless rendering, descriptors live in one big array (the heap) and a shader gets a descriptor handle, an index into it. Slang spells this Texture2D.Handle. On SPIR-V the generated code indexes __slang_resource_heap with the handle and reads the slot as the declared type, here a sampled image.
Intuition
Before this change, render-test asked reflection which access the handle needed. Reflection only knew uint2, whose element type is uint, whose resource access is NONE. A default: case mapped NONE to ReadWrite. So every texture handle got a storage-image descriptor, including read-only textures created without storage usage, and the shader read 0 from them.
```
flowchart LR
  A["TEST_INPUT: Texture2D(size=4, content=one)<br/>isRWTexture = false"] --> B["texture created<br/>usage = ShaderResource"]
  B --> C["before: reflection uint2 → NONE → ReadWrite<br/>STORAGE_IMAGE descriptor"]
  C --> D["shader reads 0<br/>VUID-00339"]
  B --> E["after: isRWTexture → Read<br/>SAMPLED_IMAGE descriptor"]
  E --> F["shader reads 1.0<br/>no VUID"]
```

The fix asks the one place that knows the answer: the input that created the texture. The same flag now picks both the texture's usage and the descriptor's access, so they cannot disagree.

Edge cases. A test that binds an RWTexture2D(...) input to a read-only Texture2D.Handle gets a storage-image descriptor, as before this change; no in-tree test does that. Buffer handles keep the old reflection-based access. render-test creates buffers with both SRV and UAV usage, so their descriptors are valid; a read-only Buffer<float>.Handle and StructuredBuffer<float>.Handle pass on Vulkan with 0 VUIDs.
Code walkthrough
The series has five commits: the failing test, the fix, a comment that states the new contract, a wider test, and a split of that test for D3D12.
The tests. Two files under tests/language-feature/descriptor-handle/, each on -vk -render-feature bindless -emit-spirv-directly, -dx12 -profile sm_6_6 -render-feature bindless, and -cuda. Each CHECK-NEXT sits next to the write it checks, and every slot expects 1.0.
desc-handle-texture-test-input-gh-13824.slang, the top-level handles:
boundTex.Load: a directly bound Texture2D, which gives the reference value.
tex.Load and tex.SampleLevel(samp, …): a top-level Texture2D.Handle with a SamplerState.Handle. This is the issue's repro.
rwTex[int2(0,0)]: an RWTexture2D<float>.Handle, which guards the ReadWrite arm. Forcing Read for every texture makes this slot read 0 (VUID-00337 with validation on).
desc-handle-texture-test-input-nested-gh-13824.slang, the nested placements:
s.t.Load and s.t.SampleLevel(s.samp, …): a Texture2D.Handle inside ConstantBuffer<S>, the struct-field variant from the issue.
gParams.reader.read(): a Texture2D.Handle inside a TextureReader passed through the IReader interface value (AnyValue), the third placement the issue names.
On CUDA a handle has the layout of the resource itself, so render-test binds the texture directly there. The cuda lanes confirm the expected values; they do not reach the changed branch.
Why two files. On D3D12, slang-rhi's root signature puts ConstantBuffer parameters one register too high when the shader also has global uniform data. RootSignatureDescBuilder::addAsConstantBuffer (external/slang-rhi/src/d3d12/d3d12-shader-object-layout.cpp) counts the global CBV at b0 and then adds the sub-objects' own offsets, which already include it. With all cases in one file, the root signature had b0, b2, b3 while the shader used b0, b1, b2, and CreateComputePipelineState failed ("CBV descriptor range (BaseShaderRegister=1) is not fully bound"). The nested file has no global uniforms, so its registers line up. This is a pre-existing slang-rhi issue and this PR does not change it.
The fix. In assignTexture, the handle branch:
```
-            // Determine access mode from the shader parameter's resource type
-            auto handleType = dstCursor.getTypeLayout()->getType();
-            auto resourceType = handleType->getElementType();
-            auto resourceAccess =
-                resourceType ? resourceType->getResourceAccess() : SLANG_RESOURCE_ACCESS_READ_WRITE;
+            // The `TEST_INPUT` kind decides the access: an `RWTexture*` input sets `isRWTexture`,
+            // which also chose the `UnorderedAccess` state (and so the texture's usage) above. The
+            // input kind must match the shader's handle type (`Texture2D.Handle` vs
+            // `RWTexture2D.Handle`), and render-test cannot check that here: on SPIR-V and D3D12
+            // the handle is reflected as a plain `uint2`, which carries no resource access.
+            DescriptorHandleAccess access = srcVal->textureDesc.isRWTexture
+                                                ? DescriptorHandleAccess::ReadWrite
+                                                : DescriptorHandleAccess::Read;
             DescriptorHandle handle;
-            DescriptorHandleAccess access = getDescriptorHandleAccess(resourceAccess);
```
The comment states the contract this change creates: a test author must spell the TEST_INPUT to match the handle type, because render-test cannot see the handle's resource type.
getDescriptorHandleAccess stays, because the two buffer paths in assignBuffer still call it.

Quiz — three questions
1. Why did reflection give the wrong access for a Texture2D.Handle on Vulkan?
A. slang-rhi ignored the access it was given and always wrote a storage image.
B. On SPIR-V the handle is laid out as a plain uint2, whose element type has no resource access, and NONE mapped to ReadWrite.
C. The Slang compiler emitted SPIR-V that declared the heap slot as a storage image.
D. render-test created the texture with storage usage but asked for a sampled-image handle.
Answer
B. Reflection reports the uint2 layout type, so getElementType() is uint and its resource access is NONE. The default: case of getDescriptorHandleAccess returned ReadWrite. slang-rhi did what it was asked, and the emitted SPIR-V was correct: it read the slot as a sampled image.
2. After the fix, what decides whether a texture handle is Read or ReadWrite?
A. The declared shader type, now read from a new reflection API.
B. Whether the shader writes to the texture anywhere in the entry point.
C. The TEST_INPUT spelling: RWTexture2D(...) sets isRWTexture, which also gave the texture UnorderedAccess usage. The input must therefore match the handle type.
D. The target: Vulkan always gets Read, D3D12 always gets ReadWrite.
Answer
C. The fix uses srcVal->textureDesc.isRWTexture, the same flag assignTexture already used to pick the texture's usage. No reflection API changes, no shader analysis, and the rule is the same on every uint2 target.
3. Why does the -cuda lane pass both before and after the fix?
A. On CUDA a descriptor handle is laid out as the resource itself, so render-test never takes the descriptor-handle branch and binds the texture normally.
B. CUDA ignores the descriptor access, so ReadWrite is harmless there.
C. The test skips the handle reads on CUDA.
D. CUDA textures are always created with both read and write usage.
Answer
A. areResourceTypesBindlessOnTarget is true for CPU, CUDA and Metal, and there DescriptorHandle<T> has the layout of T. isDescriptorHandleType then returns false and render-test calls setBinding. The CUDA lane checks the test itself, not the changed branch.
