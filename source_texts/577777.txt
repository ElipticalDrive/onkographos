Pull Request Description
What does this PR change?
TL;DR: primitives that share a mesh and an applied PBMaterial are now drawn with Graphics.RenderMeshInstanced instead of one MeshRenderer draw each. Stacked on #10242 (shared box mesh), which it needs so boxes batch at all.
RenderInstancedPrimitivesSystem (per scene, SyncedPreRenderingSystemGroup) collects (mesh, material) batches via PrimitiveInstanceBatches and issues one draw per 1023 instances. Shadow casting follows MaterialData.CastShadows; bounds are the union of instance bounds.
The entity's MeshRenderer stays alive (visibility, highlight, video-texture bounds, scene-bounds clipping all keep working) but is hidden with forceRenderingOff while instanced. PrimitiveMeshRendererComponent.InstancedRendering tracks that so the renderer is restored when the material is removed or the mesh type changes.
Default-material primitives (no PBMaterial) are not instanced: each owns a distinct pooled material, so there is nothing to batch.
Scene.shader already compiles multi_compile_instancing in all four passes; enableInstancing is switched on per material the first time it is batched.
Gated by FeatureId.PrimitiveInstancing (alfa-primitive-instancing, on in the Editor, --primitive-instancing true|false in any build).
Known trade-offs:
Culling is per batch, not per instance. A scene-wide batch is always submitted; for low-poly primitives that is cheaper than 1000 culled draws.
SceneContentStatsSystem reports instanced primitives as not visible (it reads Renderer.isVisible).
Reflection probe usage is Off on the instanced draws (same as the landscape path); highly metallic primitives may look slightly different from the renderer path.
Motivating scene: dcl-snowdrift, which spawns ~1000 identical snow cubes.

PR Review — opti: draw primitives sharing mesh and material with GPU instancing
STEP 2 — Root-cause check: PASS
This is a new optimization, not a bug fix. The PR introduces GPU instancing for primitive renderers sharing a mesh and material, reducing draw calls via Graphics.RenderMeshInstanced. The approach is correct — it issues one draw per (mesh, material) batch instead of one draw per MeshRenderer, with the standard Unity 1023-instance-per-draw limit.
STEP 3 — Design & integration: PASS
New unit: RenderInstancedPrimitivesSystem — a per-frame collection and rendering system.
MANDATORY OWNER SEARCH. The system manages instanced rendering of primitives whose lifecycle is owned by:
Creation: InstantiatePrimitiveRenderingSystem (creates PrimitiveMeshRendererComponent, resets forceRenderingOff and InstancedRendering on instantiation)
Destruction: ReleaseOutdatedRenderingSystem (releases outdated renderers on mesh-type change) and ReleasePoolableComponentSystem<MeshRenderer, PrimitiveMeshRendererComponent> (finalizes on world dispose/entity destroy)
Material lifecycle: ApplyMaterialSystem (applies loaded material to renderer), CleanUpMaterialsSystem (cleans up materials)
The new system does NOT duplicate any of these lifecycle responsibilities. It is a rendering-phase aggregator that:
Collects per-frame data (transforms, visibility) into batches
Hides the MeshRenderer from the normal draw path
Issues RenderMeshInstanced calls
This is the same pattern as the existing RenderGroundSystem (landscape instancing at Explorer/Assets/DCL/Landscape/Systems/RenderGroundSystem.cs) and ChatReactionsParticleRenderer. Per-frame collection is unavoidable: transforms change every frame, visibility toggles each tick, and entities appear/disappear. An event-driven approach would need to track creation, destruction, transform changes, material changes, and visibility changes — fragile for no gain.
PrimitiveInstanceBatches is a helper that pools List<Matrix4x4> objects across frames (cleared via Clear() each tick, never recreated). The batches dictionary is a cache of Batch objects keyed by (Mesh, Material) — this is the "temporary collections for per-frame aggregation" carve-out from CLAUDE.md §1. The per-frame data (which instances are in which batch) is rebuilt every frame. The dictionary's lifetime is the world's lifetime (created in PrimitivesRenderingPlugin.InjectToWorld line 56), so entries do not survive scene transitions.
System group placement (SyncedPreRenderingSystemGroup) is correct — it runs before rendering, synchronized with scene state, matching the group used by SyncGlobalTransformSystem and similar presentation-phase systems.
TEARDOWN / CONSUMPTION TRACE: No subscriptions, events, callbacks, or IDisposable resources are opened by this diff. The forceRenderingOff flag is a reversible mutation on the MeshRenderer, not an acquired resource. RestoreRenderer reverts it when the material is removed, and InstantiatePrimitiveRenderingSystem.Instantiate (line 132) resets it on pool reuse — so even entity destruction (where [None(typeof(DeleteEntityIntention))] skips the restore) is safe.
STEP 4 — Member audit: PASS
PrimitiveMeshRendererComponent.InstancedRendering (new bool field) — consumers:
RenderInstancedPrimitivesSystem.CollectInstances (sets to true + hides renderer)
RenderInstancedPrimitivesSystem.RestoreRenderer (resets to false + shows renderer)
InstantiatePrimitiveRenderingSystem.Instantiate (resets to false on pool reuse)
This is a state flag on the component tracking whether the entity is currently drawn via instancing. It is not a derived predicate and does not re-validate caller-guaranteed state. Appropriate.
PrimitiveInstanceBatches.BatchCount, InstanceCount(int), WorldBounds(int) — all internal, used only by tests. Acceptable for test visibility.
STEP 5 — Line-level findings
One P2 finding below, posted as an inline comment with suggestion.
Categories checked clean:
R1 (alloc-free hot paths): After warm-up, the per-frame paths (Clear → CollectInstances [Query] → Add → Render) are allocation-free. ValueTuple<Mesh, Material> keys use reference equality — no boxing. List<Matrix4x4> capacity is retained across Clear() calls. RenderParams is a struct (stack-allocated). new Batch(...) allocates only on first encounter of a (Mesh, Material) pair, not per-frame.
