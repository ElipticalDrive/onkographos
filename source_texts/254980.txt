When a gsplat scene is rotated while it loads, the back-to-front order lags the camera for seconds. On the hosted h2afva timelapse it lagged by up to 180° (fully inverted) for 11.7 s. There are three causes, all already on dev, and this PR fixes them test-first.
Per-frame re-sorts were paused while the loader was busy. The isLoadInProgress gate in evaluateDepthSortPerFrame is wired to isUpdateInProgress(). That stays true through the whole progressive-refinement drain and every view pass, so during a load the order only moved on rung commits. The gate was an optimisation from feat(viewer): depth-sorting Phase 3 — camera-triggered gsplat re-sorts #553, not an invariant: a re-sort that races a commit is already discarded by the generation guard, and the commit's own sort queues behind it. It is dropped, which also covers view passes during a drag.
The first sort ran for the pose before auto-framing. The same gate held back the re-sort after the framing move. Fixed by (1), with its own regression test.
A grown node was drawn in storage order until its sort landed. Appends, and pool grows (every doubling rung), reset the ordering to identity for a sort round-trip: 75–225 ms per rung above the 250k synchronous-sort limit. The node now keeps drawing the previous population in its sorted order, and the new splats appear one sort later, already sorted. Every path on which that sort can never arrive releases the hold.

Review of dcd56ef — approving. One nit below, nothing blocking.
What this does. It fixes three reasons the gsplat back-to-front order fell behind the camera while a scene streamed in:
evaluateDepthSortPerFrame no longer skips within-mesh re-sorts while isLoadInProgress() is true. That signal now gates only the starved-worker init retry.
The auto-framed pose therefore gets its re-sort without waiting for the refinement drain to finish.
A gsplat commit that grows the population no longer draws it in storage order. On an append (same geometry) or a pool grow (fresh geometry, seeded with the previous geometry's drawn permutation), instanceCount is held at the previous population. It is raised only when an ordering of exactly the grown count is installed: at the chunked flip, or by the live write from the synchronous sort. The coordinator releases the hold (repair plus draw everything) on every path where that ordering can never arrive.
Findings
nit: packages/luxar-viewer/src/rendering/gpu-buffer-pool/gsplats-adapter.ts, releaseGeometry (~L350). On a grow while a hold is active, the old geometry goes back to the free bucket and keeps its heldDrawTargets entry. Today that is harmless, because every re-adoption starts with writeSortedIndexIdentity (directly, or through holdSortedIndexDrawFromSeed), and that clears the entry. The vouched && held branch in writeCommitOrdering also needs sameBuffers. Still, a pooled buffer carrying another tenant's hold state is the kind of thing that bites the next person who adds a path. Suggested fix: call releaseSortedIndexDrawHold, or just drop the entry, next to the existing cancelSortedIndexOrderingApply in releaseGeometry. Optional.
Considered and dropped
scheduleSort releases the hold on !camera or when the worker isn't ready. This can end a hold before a later sort would have raised it. But the per-frame path only dispatches for registered nodes, and the commit path only reaches scheduleSort after ensureWorker resolves, so this is rare and degrades safely to the repaired full draw. Not worth more code.
A vouched (preserveOrdering/repairFromCount) recommit while held ends the hold and draws [drawn order, storage-order tail]. That is the same fallback as a release, and the recommit's own sort replaces it one round-trip later. It's a defensible choice, not a defect.
While a hold is active, instanceCount is below visibleSplatCount, so the debug-state and scene-stats readers of instanceCount report the drawn count for one sort round-trip. That is the honest "drawn" number. The commit path keys its lineage on visibleSplatCount, not instanceCount, so append/repair bookkeeping is unaffected.
What I checked
Read the full modified files plus the consumers: commitGSplatsGeometry (the prevCount source, the lineage conjuncts, and the fact that noteDepthSortCommit always runs after the pool update), the pool grow path (releaseGeometry → adoptOrAllocate → post-grow evictUnused), the chunk pump, writeSortedIndexOrdering, writeSortedIndexOrderingLive, repairSortedIndexForCount, the per-frame scheduler, the capture force loop, mode-switch, release and demotion. I also checked every other writer of the ordering buffer, including the non-pool gsplat-geometry.ts path (it never holds) and the points/lines adapters (unchanged).
The seed is sound. The previous geometry's active buffer over [0, instanceCount) is a complete permutation in every state (identity, sorted, or an existing hold's prefix). The lineage proof makes it an ordering of the new geometry's prefix. The view is consumed inside updateGSplatsGeometry, before mesh.geometry is swapped or the placeholder is disposed. Dispose does not touch the CPU arrays.
Hold/raise invariants: during a hold, every drawn frame samples [0, drawn) of a complete permutation. Raising happens only on a matching count. Stale-generation results correctly keep the hold, because the newer commit's scheduleSort runs in a microtask before any worker reply can land, so resortQueued is already set. Small nodes raise inside the commit through trySynchronousFirstSort. Hidden or culled nodes finish the flip once drawn again, so there is no stuck hold.
Clamps: the held target comes from writeSplatTexels's returned count. It matches the clamped count the commit hands the worker, so the flip's state.count meets it.
Removing the loader gate: a re-sort that races a commit is dropped by the generation guard, and the commit's sort queues behind it. loadInProgress is still read for the retry only, and the pipeline/configure comments and the spec agree with that.
Ran at this head: the three touched suites pass (313/313), and pnpm typecheck and pnpm lint are clean (suppression baseline untouched). Mutation check: dropping the flip-time raiseHeldDraw and dropping the mode-switch release together fail 5 of the new tests, so they catch real breakage.
Cross-PR: Viewer perf 1/5: verification infrastructure, render-on-change, WebGPU uploads #2945 adds a render-on-change fingerprint keyed on visibleSplatCount ?? instanceCount, so a raise will not change it for gsplats. That is fine as long as the flip keeps calling requestRender() (it does). Worth remembering when those two meet.
Docs are in sync: the rendering, coordinator and pool READMEs, GSPLAT_DEPTH_SORTING_SPEC.md, and the changelog.d/2974.md fragment.

What it does.
