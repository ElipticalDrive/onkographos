Neuroglancer's Zarr v3 reader now decodes refkv.precomputed, so an archive made by refkv's precomputed profile opens in the fork. A shard is read through its own indexes, as the precomputed data source reads it, and never whole.
Through a 14.7 MB BANC archive from d-v-b/refkv#203, the viewer's rendering is pixel-identical to Neuroglancer's own precomputed:// reading of the same volume, in 6 views across zooms and the volume's edges. It makes the same number of requests, less info, none of them for a whole object.
How it reads a shard
The codec resolves as sharding_indexed does: Neuroglancer's chunk is one precomputed chunk (128 × 128 × 16 for BANC, not the 4096 × 2048 × 256 Zarr chunk). src/datasource/precomputed/sharded.ts now exposes its minishard index reader, so both data sources share it, along with the existing JPEG, PNG and compressed_segmentation decoders. A chunk takes three requests: the shard index's 16-byte entry, the minishard index, and the chunk. The 12-byte position is a literal in the archive and takes none. Clipped chunks are filled with the array's fill value, which codecs now receive through CodecArrayInfo.

So fetch never gives the stored bytes, and refkv's spec revision 11.4 says that a reader using fetch does not make the exception for coded objects. The errors now name this cause, including Chromium's otherwise opaque "Failed to fetch", and src/kvstore/vzip/index.rst documents it. The one way to read such an object in a browser is a request without Range, which is what the precomputed:// data source does. That would need refkv's reader rule (§5.2 forbids it) and the vzip reader to change, since the value would no longer be the stored bytes. The agent did not make that change, and it is the choice to overrule if Harris15 should display here.

Refusing subsampled chroma means an RGB volume written that way shows errors here, although precomputed:// displays it with those differences. None of the volumes tested here is such a volume, and refkv's survey was not checked for this property.
Also refused: a chunk stored as brotli without the header (no decoder here), a PNG of several 16-bit channels (from reading decompressPng, which transposes bytes rather than samples), and a compressed_segmentation stream cut short (the decoder would read zeros).
Beyond the codec: a minishard index range that runs backwards, or an offset past 2^53, now fails in the precomputed:// data source too, where it read other bytes before. decode_jpeg and decode_png join Zarr's async computation modules, which only worked before because the precomputed data source was also enabled.

A Zarr chunk of the refkv.precomputed codec (refkv's spec/zarrify/precomputed.md,
section 6) is a 12-byte position and one object of a Neuroglancer precomputed
volume. An array of shards resolves as sharding_indexed does, with a precomputed
chunk as Neuroglancer's chunk, found through the shard's own indexes: the shard
is never read whole. Chunks decode with the precomputed encodings' decoders, and
a clipped chunk is filled with the array's fill value, which codecs now receive.

The codec refuses what it cannot decode as refkv's Python codec does: brotli, a
JPEG with subsampled chroma or of other than 8 bits, a PNG of several 16-bit
channels, and a compressed_segmentation stream cut short. A JPEG otherwise may
differ from libjpeg's by 1 level, as the precomputed data source's do.

An object stored with a Content-Encoding stays refused: Chromium fails such a
range and Firefox and WebKit decode it, and refkv's reader rule says that a
reader using fetch makes no exception. The errors now name the cause, and the
vzip kvstore's page documents it.
