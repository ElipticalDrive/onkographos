Goal
The Morton sort in BarnesHutTree.sortedByCode runs four 16 bit passes on a single core, while the GPU waits for the tree. Spread it over every core.
Acceptance criteria
Per thread histograms over contiguous blocks, a prefix sum across blocks, then a parallel scatter, so the sort stays stable.
Output identical, bit for bit, to the current sort: a test compares order and the sorted codes on a few random and clustered particle sets, including more than 16,777,216 particles if memory allows.
Sort phase time measured before and after at 700k, 2M and 5M, recorded in this issue.
Consider whether 8 passes of 8 bits or 3 passes of 21 bits behave better once parallel; keep whichever measures fastest.
Pointers
Sources/SillageCore/BarnesHutTree.swift, sortedByCode.
Depends on
#26 (6.0) for the baseline.

Radix width, sort phase alone at 12.5M codes on a utility queue, four blocks per core: 8 bits (8 passes) 32 ms, 10 bits 27, 11 bits (6 passes) 26, 12 bits 32, 13 bits 30, 16 bits 49 (14 blocks), 21 bits (3 passes) 161 (14 blocks). Wide digits lose because each block's histogram stops fitting in cache. The old serial sort was 130 ms there; the extra 13 ms in the baseline was a copy of the index buffer on every build, gone too.
The tree is now bounded by the node split (123 ms at 5M), still serial.
