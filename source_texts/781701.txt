Problem
Resizing a video meant running Get Video Components first, which decodes the
whole video into a float32 RGB tensor before scaling it. Peak memory therefore
grows with video length and resolution, and long or high-resolution clips can
exhaust system memory.
What this does
Resize Image/Mask/Video now accepts VIDEO both as its input and as the match-size
reference. Every resize mode uses the same dimension arithmetic for IMAGE, MASK,
and VIDEO.
File-backed videos retain their resize operations and apply them as frames are
decoded. The save path processes frames incrementally instead of materializing
the full source-resolution video as an IMAGE tensor. Crop and resize operations
remain ordered, so repeated resizes still perform repeated interpolation.
Scaling uses comfy.utils.common_upscale rather than the swscale scale filter.
This keeps VIDEO interpolation consistent with the existing IMAGE and MASK paths,
regardless of the underlying VideoInput implementation.
Resize does not change the temporal structure of the video. Frame PTS, frame
durations, frame count, VFR timing, trim windows, and audio synchronization are
preserved, including through Concatenate Video.
Odd target dimensions remain the video's logical dimensions. They are cropped
down only when an encoder requires even dimensions. For example, scaling
1920x1080 to one megapixel produces a logical size of 1365x768.
The existing node_id and class name are unchanged. The display name is updated
to Resize Image/Mask/Video.
Memory
Peak RSS for the graph, measured in the same environment. The components path is
Get Video Components -> Resize Image/Mask/Video -> Create Video -> Save Video; the
VIDEO path is Load Video -> Resize Image/Mask/Video -> Save Video.

Existing MASK behavior corrected
Resizing a MASK with Lanczos down to a single row previously dropped the height
axis and returned (batch, width). It now returns (batch, height, width), like
the other interpolation methods. This is the only intentional change to existing
IMAGE/MASK tensor results; IMAGE results remain unchanged.
Tests
pytest tests-unit and ruff check . pass.
Two new test files add 119 cases covering the generic fallback, IMAGE and VIDEO
parity across every resize mode and interpolation method, operation ordering,
odd dimensions, rotation, color space, bit depth, alpha shapes, VFR timing,
mixed edited and unedited chunks, concatenation, and the remux fast path.

Handle odd component dimensions at the encoder boundary.
VideoInput.as_resized can return a VideoFromComponents with dimensions such as 7x5. VideoFromComponents.save_to passes those dimensions directly to the h264 or libsvtav1 stream with yuv420p or yuv420p10le. Unlike VideoFromFile._save_transcoded, it does not crop before the 4:2:0 conversion, so saving can fail for odd dimensions.
Apply the positive even-dimension crop only at the encoder boundary. Preserve the odd logical tensor dimensions until encoding.
