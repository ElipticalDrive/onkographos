Purpose
Implement and benchmark an algorithm/layout-level redesign for ERWT3D focused on the contest requirement:
```
physical layout optimization
slice pre-alignment
fast indexing
no redundant X/Y/Z full copies
storage ratio < 1.5x
balanced high-performance X/Y/Z slicing
```
This issue follows the HDD profiling results from PR #42:
```
50G no-write: ~94-96 s
50G packed:   ~141-148 s
coverage:     ~100% superblocks touched
```
The conclusion from profiling is that I/O scheduling has mostly reached a sequential-scan-like regime. Further major gains require a better data layout and indexing strategy, not just larger read windows.
Background and algorithm references
This issue should borrow ideas from mature multidimensional array and spatial-indexing systems:
```
1. Chunked multidimensional arrays, as used by Zarr/HDF5-style formats.
2. Morton/Z-order physical ordering for mapping 3D tile coordinates to a 1D file order while preserving spatial locality.
3. Hilbert/space-filling curve ordering as a higher-locality alternative to Morton order.
4. R-tree/Hilbert R-tree style spatial indexing concepts: group nearby multidimensional objects and use bounding boxes / linearized keys for fast lookup.
5. Lightweight auxiliary indices similar in spirit to chunk-level metadata/index structures, without full X/Y/Z data replicas.
```
References to use in design notes:
```
- Zarr stores large multidimensional arrays as chunk grids for random access and parallel I/O.
- Z-order/Morton order maps multidimensional coordinates to one dimension by bit interleaving while preserving locality.
- Hilbert R-tree uses space-filling curves to impose a locality-preserving linear order on multidimensional rectangles.
- R-tree-style spatial indexing groups nearby objects using bounding boxes, enabling efficient filtering.
```
Current baseline to beat
From latest results:
```
20G no-write: ~37.5 s
20G packed:   ~58-63 s
50G no-write: ~94-96 s
50G packed:   ~141-148 s
storage ratio: ~1.04-1.08x
current tile/superblock: 64^3 float32 = 1MB
```
Target:
```
50G no-write < 80 s if possible
50G packed   < 120 s if possible
storage ratio < 1.5x always
```
Core idea
Current 64^3 superblock layout is likely not optimal for balanced X/Y/Z slicing under the contest workload. Implement a new layout/index path:
```
axis-balanced tile shape
+ Morton3D or Hilbert3D physical tile order
+ slice-to-tile fast index
+ decode-once scatter-many execution
+ compact metadata/index under 1.5x storage
```
This should turn ERWT3D from only an I/O-scheduled format into a contest-optimized 3D storage structure with explicit physical layout and indexing.

Part B: Physical tile ordering
Add physical order option:
```
--tile-order linear|morton3d|hilbert3d
```
B1. Morton3D
Implement Morton/Z-order key for tile coordinates:
```
morton_key = bit_interleave(tile_x, tile_y, tile_z)
```
Write tiles in Morton key order and store tile directory:
```
tile_id
logical_tx, logical_ty, logical_tz
morton_key
file_offset
byte_size
tile_shape
```
B2. Hilbert3D optional
If feasible, implement Hilbert3D order or include it as an experimental comparison. If implementation cost is high, leave it behind a separate flag and first complete Morton3D.
Benchmark:
```
linear vs morton3d vs hilbert3d if available
```

```

```
Output:
```

docs/results/layout_hilbert_experimental.csv  # optional
```
Part C: Slice-to-tile fast index
Build a compact index for direct slice lookup:
```
X_slice[k] -> tile_id list
Y_slice[k] -> tile_id list
Z_slice[k] -> tile_id list

tile_id -> file_offset, byte_size, tile coordinate, physical order key
```
This index must not duplicate data values. It is metadata only.
Add a CLI option:
```
--slice-index on|off
```
Index design options:
```
1. dense offset table for regular tile grids
2. compressed tile_id lists per slice
3. bitset / range list if compact
4. physical-order sorted tile lists for each slice
```
For each index design, report:
```
index_size_mb
index_build_time_ms
slice_lookup_time_ms
storage_ratio_with_index
```
Output:
```
docs/results/layout_slice_index.csv
```
Part D: Decode-once scatter-many
Current contest workload touches nearly all superblocks. The critical algorithm is to process each tile once and scatter it to all target slices that need it.
Implement contest execution path:
```
1. collect X/Y/Z target slices
2. use slice-to-tile index to produce tile -> target-output mappings
3. deduplicate tile_id
4. sort tiles by physical file offset
5. read each tile once
6. decode each tile once
7. scatter to all X/Y/Z output buffers that intersect this tile
8. release tile or keep in bounded tile cache
```
Add:
```
--contest-exec-mode current|decode-once-scatter-many
--contest-tile-cache-mb N
```
Metrics:
```
unique_tiles_read
tile_decode_count
tile_reuse_count
avg_outputs_per_tile
T_read_ms
T_decode_ms
T_scatter_ms
T_total_no_write_ms
memory_peak_mb
```
Output:
```
docs/results/layout_decode_reuse.csv
```

Implementation notes
Morton3D should be implemented first because it is simpler than Hilbert3D and easy to explain.
Hilbert3D is optional/experimental unless Morton3D gives no benefit.
The slice-to-tile index should be compact and deterministic.
The index should be stored inside ERWT3D metadata or in a sidecar only for experimentation; final solution should prefer integrated metadata.
Do not add full data replicas along X/Y/Z.
Keep memory controlled by --memory-limit-mb.
The benchmark must distinguish warm and cold results.
Expected outcome
This issue should determine whether ERWT3D can beat the current near-full-file sequential read bottleneck by changing tile shape, physical order, and indexing. If the best layout still touches nearly 100% of tiles, document that the contest workload is intrinsically full-volume for the current storage ratio and that remaining improvements are limited to decode/cache/scatter and hardware throughput.
