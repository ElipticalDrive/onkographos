Stability and Performance of OpenCL-OpenGL
Interoperability and OpenGL Compute Shader
Environments in GPU-Accelerated Fluid Simulation: A
Multi-Platform Comparative Study
Marcin Hajder
Institute of Computer

Cardinal Stefan Wyszyński
University, Warsaw, Poland
m.hajder@uksw.edu.pl
While OpenGL compute shaders and OpenCL-OpenGL interoperability offer structurally comparable paths for
GPU-accelerated CFD, no prior work has directly compared these two approaches in the context of large-scale
GPU simulations. This paper presents such a comparison in a large-scale urban fluid flow simulation across four
contemporary consumer GPU platforms representing Nvidia, Intel, and AMD architectures, and two simulation
domain sizes, evaluating both peak throughput and sustained stability, using application-level frame time measurements supplemented by hardware performance counters. Across all tested configurations, native OpenGL
compute shaders consistently achieve higher throughput than the OpenCL interoperability path. Developers targeting large-scale simulations should nonetheless account for progressive performance degradation, as its extent
and distribution across API paths varies substantially by platform and driver stack, ranging from uniform degradation on Intel, through cache thrashing-driven erosion of the OpenGL compute shader path on Nvidia, to complete
stability on AMD hardware, where both implementations additionally exhibit the smallest performance gap of all
tested platforms.

The growing demand for large-scale numerical simulations has established the Graphics Processing Unit as
the dominant computational platform in scientific computing. "GPU computing has reached a tipping point
in the HPC market that will encourage continued increased in application optimization" [7]. The massively
parallel architecture of modern GPUs, offering thousands of concurrent execution threads, makes them particularly well suited for compute-intensive workloads
such as Computational Fluid Dynamics. In CFD applications, the simulation domain is typically discretized
into a dense grid, and each time step requires updating
every cell according to governing equations, a workload
that maps naturally onto the GPU execution model. A
typical scenario involves pairing a GPGPU-driven simulation with a real-time visualization of the resulting
data, such as in modeling of fluid dynamics [4, 5].

real-time visualization, the developer must choose both
a compute API and a graphics API, and establish a

OpenCL is a programming interface designed for
computation in heterogeneous environments, capable
of running on both the CPU and GPGPU. It is an
open standard managed by The Khronos Group [9].
When combined with OpenGL for real-time visualization, the cl_khr_gl_sharing extension
provides the interoperability mechanism.
When
the extension is available, "it allows OpenCL to
efficiently share OpenGL resources such as textures and buffer objects without the overhead of
transporting GPU data back and forth to the host
memory" [8]. This sharing requires explicit ownership
transfer via clEnqueueAcquireGLObjects and
clEnqueueReleaseGLObjects calls before and
after each compute pass [10], introducing a synchronization overhead absent in the native compute shader
path.
In large-scale simulations, the computational workload
is not static, as the simulated physical state evolves,
the spatial complexity of the solution increases, altering
the memory access patterns of the compute kernels and
potentially affecting sustained throughput. Especially
problematic are long-duration simulations, where accumulated energy drift can significantly distort the behavior of the modeled phenomena [3]. Performance stability, the degree to which throughput is maintained over
the full duration of a simulation, is therefore an equally
important characteristic alongside peak throughput, and
one with direct implications for numerical stability and
the practical usability of the simulation.
In this paper we present a comparative performance
study of OpenCL-OpenGL interoperability and native
OpenGL compute shaders in a GPU-accelerated CFD
simulation. We evaluate both peak performance and
long-term stability over 5,200 frames using applicationlevel frame time measurements supplemented by hardware performance counters. To assess the generality of our findings, experiments were conducted on
four GPU platforms: Nvidia RTX 5070 Ti (Blackwell),
Nvidia RTX 4070 (Ada Lovelace), Intel Arc B570 (Battlemage), and AMD Radeon RX 9070 XT (RDNA4).
Our results reveal a fundamental trade-off between the
two approaches, with OpenGL compute shaders offering higher throughput across the full simulation duration on all tested platforms, while exhibiting progressive performance degradation on Nvidia hardware.

Both OpenCL and OpenGL compute shaders offer similar development cost for simulation kernels: the mathematical core of the simulation translates to structurally
analogue code in both OpenCL C and GLSL, making
the two approaches directly comparable. This implementation symmetry allows the effect of API choice to
be isolated from confusing factors such as algorithmic
differences or code maturity.
A relevant distinction lies in the current state of
both interfaces. OpenGL has reached end of active
development, with no new versions planned [19],
and support for certain modern GPU capabilities is
absent, most notably, there are no plans to introduce
ray tracing support in OpenGL [16]. In contrast,
OpenCL continues to evolve as an open standard under
active Khronos working group maintenance [11], with
OpenCL 3.1 released in May 2026 promoting SPIR-V
ingestion, subgroups, and integer dot products to core.
This context motivates the investigation of OpenCL
interoperability as a forward-looking platform choice.
Vulkan, while offering greater low-level control and
supporting modern GPU features, was excluded from
this comparison on the grounds of substantially higher
development cost: our prior work [8] quantified this
cost via source lines of code across OpenCL-OpenGL
and OpenCL-Vulkan implementations, finding that the
Vulkan path incurs a significantly higher implementation burden without a commensurate performance
benefit for simulation workloads of this class.

The simulation operates on a large-scale urban fluid
flow domain, discretized into a dense grid of velocity,
density, pressure, and divergence fields. All simulation
states are stored in 32-bit IEEE 754 floating-point format. Because the computational workload scales with
the domain area, the two sizes selected for this study,
4 × 4 km and 8 × 8 km-represent distinct throughput
regimes. Both domains represented with 1 square meter
resolution grids of 4096 × 4096 and 8192 × 8192 cells.
Söderström [18] examined the usability of GPGPU
frameworks for scientific simulation by comparing DirectCompute, CUDA, and OpenCL using a
Barnes-Hut N-Body problem. DirectCompute, which
dispatches HLSL shaders via Direct3D 11, engages
computation into the graphics API without a separate
interoperability scheme; it therefore presents a design
point equivalent to the native OpenGL path studied
here. Both works share the goal of determining
whether vendor-neutral APIs like OpenCL are viable
alternatives to graphics-driven compute for simulation
workloads.
Both implementations utilize a GPU-resident data management strategy. Velocity, density, pressure, divergence, and all intermediate buffers reside entirely in
VRAM throughout the simulation, with no host-device
transfers between time steps. Moving data between
host and device involves significant performance costs:
the PCIe bus imposes a bandwidth load, while memory
management operations and the inseparable overhead
of bus transfers add latency that would not appear with
direct memory access [8]. The present implementation
avoids this bottleneck entirely by keeping all buffers
GPU-resident throughout the simulation, ensuring that
frame time measurements reflect purely GPU-side computation.
Söderström’s work differs from this study in one significant structural area. The N-Body simulation rebuilds its
Barnes-Hut octree at every time step, repopulating the
GPU memory dependencies and preventing cache state
from accumulating. In contrast, grid-based CFD fields
persist in VRAM, allowing access patterns to evolve
and reveal performance outcomes invisible to per-step
metrics.
Both implementations share a common work-group
size of 16×16 threads per dispatch, selected empirically
as the configuration yielding the lowest frame times
across the tested domain sizes.
More notably, neither study performs the specific
comparison addressed here: OpenCL-OpenGL interoperability and native OpenGL compute shaders
within a shared graphics-coupled pipeline. Sans and
Carmona contrast OpenCL interop with a fragmentshader path rather than with a compute shader, while
Söderström compares OpenCL against DirectCompute
on Windows without any interoperability mechanism.
Neither study, moreover, examines performance as
a function of simulation time, nor do they confirm
findings with hardware performance counters. By
relying on host clock averages, they leave unaddressed
whether throughput remains stable as the physical
state evolves. This work addresses that gap through

OpenCL–OpenGL Interoperability
Direct access to OpenGL textures is provided via the
cl_khr_gl_sharing extension [10], eliminating
the need for expensive host memory copies when
executing OpenCL kernels. Texture ownership is
explicitly managed: it is transferred to the OpenCL
context through clEnqueueAcquireGLObjects
before relevant compute pass and returned to OpenGL
through clEnqueueReleaseGLObjects afterward. Although the OpenCL specification permits

OpenGL Compute Shaders
The OpenGL path implements the same computational
passes using GLSL compute shaders (introduced in
OpenGL 4.3 [19]). Because the simulation kernels and
rendering pipeline share a single context, textures remain GPU-resident without requiring explicit ownership transfers. The mathematical core of each pass is
structurally analogous to its OpenCL counterpart, with
differences limited to API-specific constructs and the
absence of manual synchronization. Texture access in

In the early frames, the velocity field is spatially
smooth and the advection kernel samples the velocity
texture at positions that fall within a small, coherent
region of GPU L2 cache. As the simulation progresses,
the velocity field becomes increasingly turbulent, and

distant positions. The working set of the advection
kernel consequently grows beyond the capacity of the
L2 cache, causing a progressive drop in the L2 hit rate
and a corresponding increase in VRAM bandwidth
utilization. This is a typical L2 cache thrashing pattern
driven by the evolution of the simulated physical state
rather than by any change in the code path. When

CONCLUSIONS
This study evaluates the sustained performance of two
structurally comparable GPU compute approaches, native OpenGL compute shaders and OpenCL-OpenGL
interoperability, within a large-scale CFD simulation
across four GPU platforms and two domain sizes. The
OpenGL Compute Shader implementation consistently
achieves better performance results than the OpenCL
Interoperability path across all tested platforms.
On the Intel Arc B570, the OpenGL path is served by
the Mesa/iris driver stack, while the OpenCL Interoperability path uses the Intel NEO compute runtime (intelcompute-runtime), both operating over a common xe
kernel driver. Both the OpenGL Compute Shader and
the OpenCL Interoperability implementations degrade
at nearly identical profile across both domain sizes. Unlike the Nvidia case, no stability advantage is observed
for the OpenCL path. Per-call both CPU and GPU timing recorded with the OpenCL Intercept Layer, reveal
that the performance degradation extends down to the
kernel level throughout the simulation, the advection
kernel grows from 8439 µs to 9460 µs (+12.1%), the
pressure kernel from 4451 µs to 6284 µs (+41.2%), and
the Jacobi kernel from 2588 µs to 3046 µs (+17.7%).
Interestingly, the acquire and release calls average just
0.043 µs each during the entire simulation, irrelevant
compared to kernel processing time, confirming that the
cl_khr_gl_sharing overhead is not the cause of degradation on this platform. This result suggests that both execution paths operate within a shared unified memory
space at a level below the interoperability scope [12],
implying that both solutions are subject to the same underlying performance constraints as the velocity field
evolves.
On Nvidia platforms, the OpenGL compute shader
implementation achieves high throughput, but its performance gradually declines as the simulation evolves.
Hardware analysis on the RTX 5070 Ti traces this
degradation to L2 cache thrashing: as the velocity field
becomes increasingly turbulent, the advection kernel’s
working set exceeds L2 cache capacity, causing a
steady rise in VRAM bandwidth consumption.
In contrast, the OpenCL interoperability implementation maintains stable performance throughout the simulation. The OpenCL path operates at a high, constant
VRAM throughput from the first frame, with no cachedriven degradation, while the acquire/release synchronization imposes an additional fixed overhead that does
not grow with turbulence. Notably, this fixed overhead is a property of the Nvidia proprietary driver stack
rather than of the cl_khr_gl_sharing extension
itself, on AMD and Intel hardware the same calls are
effectively free. These distinct profiles indicate that the
two implementations are handled by fundamentally different layers of the driver stack on Nvidia hardware.
On the AMD Radeon RX 9070 XT hardware, none
of solution reveals measurable erosion over the full
simulation duration, and the performance gap between
the OpenGL and OpenCL paths is the least observable of all tested platforms. This behavior suggests
a potential connection to the unified Mesa/Gallium3D
driver stack shared by both execution paths on this platform: Mesa/radeonsi handles the OpenGL path and
Mesa rusticl handles the OpenCL path, likely sharing the same underlying Gallium3D pipeline. Memory
controller utilization measured via the gpu_metrics
sysfs interface confirms this perspective: both paths
saturate the memory subsystem at virtually identical
levels, 82.9% for OpenCL and 82.7% for OpenGL, a
difference indistinguishable from measurement noise.
Per-call timing from the OpenCL Intercept Layer tells
the same story: across the full 5200-frame run, no kernel shows a measurable drift, with all execution times
staying within 0.2% of their frame-one values. These
results point to the Mesa/Gallium3D stack as the equalizing factor: when both API paths share the same underlying pipeline, the performance gap narrows to its
minimum and neither path degrades. Moreover, these
results suggest that for large-scale simulations running
on the RX 9070 XT, the throughput penalty for picking
OpenCL over OpenGL is the smallest recorded across
all tested platforms and effectively irrelevant in practice.
The precise mechanism underlying the stability of the
OpenCL path, whether the VRAM-bound execution is
a direct consequence of the acquire/release synchronization, a distinct texture mapping strategy employed
by the driver, or another internal effect, cannot be established definitively with the profiling instrumentation currently available for OpenCL workloads. The
OpenCL Intercept Layer confirms that all simulation
kernels on the RTX 5070 Ti remain stable across the full
5200-frame run (per-kernel drift below 1.5%); we additionally performed a control run on the 4×4 km domain
without per-frame acquire/release, in which OpenCL
frame times remained equally stable. This points to a
property of the Nvidia OpenCL ICD itself: kernels operating on image2d_t objects appear to bypass the
texture cache hierarchy used by the OpenGL compute
shader path, which would explain both the absence
of cache-driven degradation and the consistently high
VRAM throughput observed from the first frame. Establishing this mechanism conclusively would require
per-kernel memory access counters for OpenCL workloads on Nvidia hardware, which current tooling does
not support.

A further practical consideration concerns tooling
availability. Hardware profiling support for OpenCL
interoperability workloads proved noticeably broader
on Nvidia than on AMD, and broader on AMD than
on Intel, a gradient that directly shaped the scope
of analysis available on each platform. Despite the
substantial GPU ecosystem shifting its development
focus from OpenGL toward its successor Vulkan,
hardware profiling and diagnostic support remains
considerably wider for the OpenGL path than for
OpenCL interoperability workloads. As shown in this
study, the Nvidia Nsight toolchain was unable to instrument OpenCL compute kernels directly, requiring
fallback to Nsight Systems for VRAM throughput
data and to the OpenCL Intercept Layer for per-call
timing. On the AMD platform, VRAM bandwidth was
accessible via the gpu_metrics sysfs interface, but
cache hit rate metrics remain unavailable, precluding
direct observation of cache-level behavior. On the Intel
Arc B570, no memory bandwidth metric is exposed
by any available userspace interface under the Linux
xe kernel driver; Intel VTune Profiler, which provides
OpenCL memory bandwidth analysis for Arc GPUs on
Windows, was outside the scope of this Linux-based
study. In contrast, the OpenGL path on Nvidia hardware was fully transparent via Nsight Graphics and the
Nsight Perf SDK, enabling the collection of per-frame
performance counters. This asymmetry in tooling has
tangible consequences: analysis, optimization, and
debugging become significantly more complex for
OpenCL interoperability workloads. Such tasks require
a broader, less integrated toolset, which inherently
increases development and maintenance overhead.
On the AMD Radeon RX 9070 XT, both implementations remain stable throughout the simulation with
no measurable erosion, and the performance gap between the OpenGL and OpenCL paths is the smallest
observed across all tested cases. This observation implies the unified Mesa/Gallium3D driver stack shared
by the OpenGL (radeonsi) and OpenCL (rusticl) paths
on this platform. It should be noted that the AMD results are specific to this flexible driver stack configuration; a deployment using the ROCm OpenCL stack,
which follows a separate execution path, would most
likely result in different interoperability characteristics. Of all tested platforms, AMD offers the most predictable execution environment for large-scale simulations: both API paths remain stable, both impose equivalent memory subsystem pressure, and the performance
margin between them is the smallest observed. Developers for whom API-independent stability is a primary
concern will find the open Mesa/Gallium3D stack the
least penalizing choice, regardless of whether they favor OpenCL interoperability or native compute shaders.
