What do you mean by "correct"?
If you mean "numerically", then they are correct assuming JAX does compute the correct gradient, but this was already the case without smoothing;
If you mean physically, then they are most likely incorrect, because the smoothing technique is a numerical trick introduced to allow continuously differentiable Ray Tracing. I will very likely investigate any possible physical link (e.g., with UTD coefficients) in a future paper, but this is still ongoing work.
In the end, the smoothing technique is mainly applied to make optimization easier, but it is disabled when computing the exact RT solution.

Hello! I guess the line you are referring to is from Scene.all_valid_paths?
DiffeRT2d/differt2d/scene.py
Lines 1211 to 1215
in
5fc52f0
for tx_key, rx_key, valid, path, path_candidate in self.all_paths(
approx=approx, **kwargs
):
if is_true(valid, approx=approx):
yield (tx_key, rx_key, path, path_candidate)
The all_valid_paths function is a more convenient wrapper for plotting purpose, as path validity is represented by a Truthy value, which can be any real number between 0 and 1.
The is_true check actually breaks the "fully differentiable ray tracing", as it creates a discontinuity in the output. However, if you look at the power optimization example, it uses accumulate_over_paths (see code below), which does not check for validity, but rather multiply the output value by the path validity (which is continuously differentiable).
DiffeRT2d/differt2d/scene.py
Lines 1257 to 1266
in

for _, _, valid, path, path_candidate in paths_group:
interacting_objects = self.get_interacting_objects(path_candidate)
acc = acc + valid * fun(
transmitter,
receiver,
path,
interacting_objects, # type: ignore[arg-type]
*fun_args,
**fun_kwargs,
)
So, in the end, we do not perform any check during optimization, but only for plotting purposes. Did I answer your question?
