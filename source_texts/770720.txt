Description
This PR aims to provide an implementation of using Cosmos3 to perform domain randomization to the camera streams.
```
┌─ simulator process ────────────── GPU 0 ─┐
│  Isaac Sim + Kit + policy                │
│  VisualDRRuntime                         │
│    └─ RemoteCosmosBackend  (client)      │
│         dispatch: 1 frame → 1 free worker│
└──────────────┬───────────────────────────┘
               │  control: prompts, seeds, ids   (CPU queue — small, no pixels)
               │  payload: rgb / depth / seg     (CUDA IPC — GPU→GPU, no host copy)
    ┌──────────┼──────────┬──────────┐
    ▼          ▼          ▼          ▼
┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
│worker 0│ │worker 1│ │worker 2│ │worker 3│   ← one process per GPU
│ GPU 1  │ │ GPU 2  │ │ GPU 3  │ │ GPU 4  │
│ Cosmos │ │ Cosmos │ │ Cosmos │ │ Cosmos │   ← CosmosBackend, unchanged
└────────┘ └────────┘ └────────┘ └────────┘
```
For demonstration, we use the Franka stacking demo which provides raw semantic IDs to extract for generation. nixl is used for the runtime-backend transport layer to allow efficient communication and future model extensions.

Add staged rewards for cube stacking

```
The stacking tasks ship imitation-learning configurations and set
rewards to None, so there is nothing for a reinforcement-learning
configuration to start from. These terms are built on the tasks' own
object_grasped, object_stacked and cubes_stacked predicates, so what
earns reward and what counts as success cannot drift apart.

Reach shaping uses a bounded tanh kernel rather than a raw negative
distance, so it cannot dominate the stage rewards when the arm starts
far from the cube. Stage rewards pay per step for a condition that
holds rather than for entering it, so a policy cannot farm them by
repeatedly crossing a boundary.

The shipped task configurations are unchanged and still set
rewards = None; callers opt in by assigning their own rewards group.

Vectorize runtime visual DR and add a Cosmos backend
…
3e1ce4f
```
The runtime now applies DR to every environment at once. Episode
boundaries, action-chunk gating and partial resets are read from the
environment rather than declared by the application, so DRObservation
and ActionChunkSchedule are gone and the application owns only model
residency. Style and restyle decisions derive from a hash of the seed,
environment index and episode index, so they are stable across replicas
and across repeated reads of one observation.

Preserved regions are now named by foreground class, and an
unrecognised semantic id is kept rather than replaced: an asset nobody
tagged survives generation instead of dissolving into the background,
which is the failure that stays invisible until a policy has learned
around it.

The Cosmos backend runs against a stock cosmos-framework checkout and
the public Cosmos3-Nano checkpoint. Foreground preservation is a
composite rather than mask-guided denoising, which is what removes the
need for a patched checkout.

Three defects found while bringing this up on hardware:

- For 128-wide attention heads cuDNN answers through a runtime-compiled
  engine, and once Omniverse Kit has started it can no longer compile a
  shape it has not already seen. Sequence lengths follow the prompt, so
  no fixed warm-up covers them. The backend probes cuDNN on load and
  falls back to torch's Flash kernels, which need no runtime
  compilation and return the same logsumexp statistics.

- Cosmos' loader keeps a state dict sharing storage with the model
  parameters, so moving them to host freed nothing and the next
  activation allocated a second copy. Residency grew by the size of the
  model on every offload cycle, defeating the point of offloading.

- The RTX renderer reports idToLabels keys as RGBA strings even when
  colorization is disabled and the buffer holds uncolored int32 ids.
  Those channels are the little-endian bytes of the stored id.

Sampling defaults follow Cosmos' tuned transfer values rather than its
image2image defaults, which are for the mode that has no control hint.

```
Some background conditions should drift rather than be drawn afresh each
frame. Time of day is the clearest case: the laboratory has windows, and
independently sampling the lighting every frame reads as flicker rather
than as time passing.

PromptBankCfg gains a phrase sequence and the number of steps to walk it
in. The phrase is appended to whichever variant the episode selected, so
the room stays the same room while its light changes. The walk follows
wall-clock steps rather than episode progress, so it does not reset each
episode, and clamps at the final phrase rather than wrapping, so a run
longer than the span ends at midnight instead of snapping back to dawn.

The demo takes its lab from dawn to midnight over a 230-step rollout.
Measured background brightness across that run falls 142 to 74 after
mid-morning, rising slightly at sunset and again at midnight where
interior lights sit against dark glass.

Run visual DR generation on dedicated GPUs, with replicas
…
f48fe95
```
A diffusion model and a simulator do not share a GPU well: one frame
costs seconds, and the simulator waits through all of them. This moves
generation into worker processes on their own GPUs, and runs several so
the environments randomized in one step are generated at once -- the
only parallelism available while Cosmos rejects batched transfer
inference.

The runtime does not change. It already chunks the environments it wants
randomized by max_batch, so setting that to the worker count hands the
backend exactly one frame per worker, which it fans out concurrently.

Image payloads move by CUDA IPC: sending a CUDA tensor through a
torch.multiprocessing queue shares the allocation rather than copying
it, and the worker's device-to-device copy is a peer transfer, so pixels
never reach host memory. Prompts, seeds and identifiers travel as
ordinary objects on the control queue.

Measured on H100s at sixteen sampler steps: 3.62 s per frame with one
worker, 2.02 s with two, 1.18 s with four. One remote worker costs about
what the in-process backend does, so the transport is not the expense.

Workers run without Omniverse Kit, which is incidentally why the cuDNN
attention fallback is inert in them: Kit's startup is what breaks
runtime kernel compilation, and no Kit starts there.

Device indices are indices into what this process can see, so
CUDA_VISIBLE_DEVICES has to cover the union of the workers' GPUs and the
simulator's. Naming a device outside that set fails at construction with
that explanation rather than at the first generation.

Same-node only; crossing machines needs a real transport behind the same
class, which is where NIXL would go.

Pasting the render back is one answer to preserving the foreground, not

Document when a custom Cosmos checkout will not run here
…

Installing a custom checkout and a distilled transfer checkpoint works as
far as loading the model, which stock cannot do -- its exported config
carries keys stock's schema does not have. Generation then fails on
attention backend selection.

The reason is worth recording. The base Cosmos3-Nano path needs no
FlashAttention: it falls back to cuDNN, or to torch's Flash kernels once
Kit breaks cuDNN's runtime compilation. A model using variable-length
packed attention has no cuDNN path at all, so FlashAttention becomes
mandatory -- and the Cosmos dependency index publishes it only for
CPython 3.13 against torch 2.9 or 2.10, while Isaac Lab is CPython 3.12
with torch 2.12.

So the Python and torch versions reported as a conflict in testing are
real for such a checkout, and not for the base model path this PR
defaults to.

Build the preserved mask even when the composite is off
…
46fb109
```
Mask construction was gated on composite_foreground, on the reasoning
that nothing would be pasted back so nothing needed protecting. That
was wrong: a backend may send the same mask to the model as a guidance
signal. With the composite cleared it received an all-zero mask, so
guided generation preserved nothing and silently did nothing at all.

The mask is now built whenever preserve_classes names something, and
composite_foreground decides only whether the runtime pastes it back.

The difference is not subtle. Generating without the composite but with
a real guidance mask reproduces the workbench colour exactly, [106,106,105]
against the render's [106,106,105], where the empty mask gave [84,71,63];
the cubes keep their colours rather than fusing; and the frame is still
lit as one scene, with no mask seam.

This also retracts a conclusion drawn from the earlier behaviour: mask
guidance was never tested without the composite, only an empty mask was.

Remove the fringe around preserved objects under mask guidance
…
25bb5e7
```
Generating with a guidance mask and no composite left a bright rim
tracing every preserved silhouette. Two causes, both introduced here.

The latent mask was reduced with max, which keeps a cell whenever any of
its pixels are foreground. That holds a rim of original background
around each object, and against a regenerated scene the held pixels read
as a halo. Reducing with area instead measured close to half the excess
brightness while still keeping thin structures such as the gripper
fingers.

The stacking prompts had also been told to describe the foreground. That
was a workaround for the mask being empty whenever the composite was
off; with a real mask it is unnecessary, because the mask preserves the
foreground. It was also harmful: the clause biased generation brighter
around the objects, and measured on matched scenes it made cube colours
worse rather than better, 19/25/56 red/green/blue against the render's
33/33/34 where describing nothing gave 33/33/34 exactly.

Over sixteen frames the workbench now differs from the render by 0.09 of
a level on average, and no fringe is visible.

boundary_px compounds the same rim -- dilation helps hide the composite's
seam but widens what guidance holds -- so the field documents leaving it
at zero when generating with a mask.
