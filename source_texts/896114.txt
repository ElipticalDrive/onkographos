Summary
Phase 1 of #8 (Voronoi-based polycrystal generator). Lands the consumer side — a convex polyhedral shape that ingests pre-computed Voronoi cell geometry. The actual tessellator (which needs CGAL or Voro++ — heavy deps) lands as a follow-up so this PR can be reviewed without a 200 MB dependency churn.
Why no CGAL dependency yet
The full polycrystal generator wants to (a) sample N seed points in the RVE box, (b) compute a periodic 3D Voronoi tessellation, (c) emit each cell. Step (b) needs CGAL or Voro++. Adding either as a hard rvegen dep just to land an unused phase-1 shape is premature.
This PR keeps rvegen's deps unchanged and ships only the consumer side: any external tool (Voro++, qhull, CGAL outside rvegen, even SciPy scipy.spatial.Voronoi from Python) can produce cell geometry; rvegen ingests it. The follow-up adds the in-tree tessellator.
What ships
rvegen::voronoi_cell<T> — convex polyhedron defined by vertices + faces:
Direct C++ ctor from std::vector<gte::Vector3<T>> (vertices) + std::vector<std::vector<size_t>> (faces as vertex-index lists)
is_inside(p) — half-space test against each face. Outward normals are derived once at construction via the centroid trick (centroid of the convex cell is on the inward side of every face).
volume() — divergence theorem via signed tetrahedra from centroid
make_bounding_box(), get_middle_point(), set_middle_point() (translate; planes translate too), clone(), shape_id()
static_indexing integration so the collision dispatcher can address it
Test fixture
A unit cube as a degenerate Voronoi cell (8 vertices, 6 quad faces) — exercises every code path:
Volume = 1.0 within FP tolerance
Origin inside; (0.6, 0, 0) and (0.51, 0.51, 0.51) outside
A tetrahedron exercises set_middle_point translation and the 3-vertex face path.
What's NOT in this PR (follow-up)
voronoi_polycrystal_generator — produces N tessellated cells for a given seed-point distribution. Needs Voro++ (lightweight, ~5 MB) or CGAL (heavy, ~200 MB). Voro++ is the leading candidate.
Periodic Voronoi — cells that wrap across the RVE box boundary
voronoi_cell_input — JSON-driven loader (cell vertex/face data is heterogeneous; needs careful schema design or a separate file format)
Precise collision_details(voronoi_cell, X) overloads — falls back to AABB until then
Drive-by fix
Same pre-existing tests/extra_types_smoke.cpp brace bug fixed in PRs #17–#23.
Test plan
Unit-cube cell volume = 1.0 within 1e-12
Inside/outside parity correct for origin and corner-adjacent points
Translation via set_middle_point shifts the inside region (face planes translate too)
Tetrahedron fixture exercises 3-vertex faces
All 15 ctest tests pass

Review: PR #25 voronoi_cell
Correctness
volume() per-tetrahedron std::abs() masks bugs. With consistent winding (the convex-cell case), every signed tet has the same sign, so per-term abs equals abs-of-sum and gives the right answer. With inconsistent winding (a Voronoi-cell loader emits faces with mixed orientation — easy mistake), per-term abs adds magnitudes and produces a falsely large volume. The principled formula:
```
// current — masks bad winding
sum += std::abs(apex[0]*cx + apex[1]*cy + apex[2]*cz);
return sum / T{6};

// safer — exposes bad winding
sum += apex[0]*cx + apex[1]*cy + apex[2]*cz;
return std::abs(sum) / T{6};
```
The unit-cube test will pass either way because the test winding is correct. A test with intentionally-flipped face would catch the difference.
Convexity is silently assumed. is_inside uses half-space intersection, which is only correct for convex polyhedra. Voronoi cells of interior seeds in a convex domain are always convex — but the moment a Voronoi cell touches a periodic boundary or a non-convex domain, this falls apart. Worth a runtime_assert or at least an explicit doc warning that the consumer must guarantee convexity.
Robustness
rebuild_face_planes derives an outward normal from v[0], v[1], v[2] of each face. If the face polygon's first three vertices happen to be collinear (rare but possible for specific Voronoi tessellators), the cross product e1 × e2 is zero, mag = 0, and if (mag > 0) n /= mag skips the normalisation, leaving n = (0,0,0). Then every subsequent is_inside test against that face becomes 0 ≤ 0 (true), and the face contributes nothing — the cell becomes effectively unbounded on that side.
Fix: walk the face vertices to find the first non-collinear triple.
set_middle_point translates _centroid and _face_planes correctly but doesn't update derived state if the cell is later mutated by some other path (e.g. directly modifying _vertices). Currently no public path to do that, but set_centerline-equivalent might land in a follow-up. Note in the comment that any mutation outside set_middle_point requires rebuild_face_planes.
Centroid choice
The "centroid" is the mean of vertices, used for face-orientation tests. For a convex polyhedron this is guaranteed to be strictly inside, so the orientation flip works. Good.
For volume, the same centroid is used as the apex of the signed-tetrahedron sum. If the centroid happens to lie on a face plane (degenerate but mathematically possible), one of the tetrahedra has zero volume — fine, doesn't break anything.
Test coverage
Unit cube and tetrahedron fixtures are good.
No test for a degenerate (collinear-first-three-vertices) face — would catch the normal=0 bug.
No test exercising actual Voronoi cell geometry (irregular polyhedron with ≥6 faces of mixed shape). With a phase-1 PR not yet linked to a tessellator, that's hard to do without bringing in test fixture data; could land alongside the eventual tessellator PR.
Naming
voronoi_cell<T> — but the type is really a generic convex polyhedron. The name implies a specific data source. If a future user wants the same shape for, say, a polyhedral inclusion from CAD, they'd be surprised by the name. Consider convex_polyhedron<T> and have the eventual voronoi_polycrystal_generator produce instances of it.

Second-pass review:
Collinear threshold is absolute, not relative. mag_eps = epsilon * 1024 ≈ 2.3e-13 for double. Cross-product magnitude scales with the input vertex magnitudes squared. For unit-cube-scale inputs (extent ~1) the threshold works; but for a cell at metre-scale or with vertices in micrometres, the threshold doesn't track. Real fix: divide mag by |e1| · |e2| to get sin(angle) which is scale-invariant. Tracked as follow-up — not blocking the unit-cube test.
