For your interest, I've added a specification of the RT draft here.
DirectX and Vulkan Ray Tracing are very similar in their style and usage.
DXR seems to have the most features and control
Vulkan's API is similar to NVIDIA Optix (and there is a new cross-vendor extension in progress, page 29). Interesting here is also "Aiming for substantial compatibility with DirectX Ray Tracing (DXR)"
Metal seems to be different to the other APIs
My current concerns are:
The validations layers of VK_NV_ray_tracing are sloppy
At least with Vulkan, it's pretty easy to crash the entire driver when making a mistake - I'm positive that DXR has similar flaws
Metal could too different to the others (no hardware acceleration for ray intersection, no RT shaders, ..)

I've made an example of the VK_KHR_ray_tracing extension here, which I'll use as a base to port the current VK_NV_ray_tracing implementation in Dawn.
Currently I'm mainly waiting for bug fixes related to the current NVIDIA driver, the validation layers don't support the new extension and it's not possible to build AS on the host yet.
The new extension indeed offers the same features as DXR, though most of them are not implemented in the drivers yet.
Regarding Metal and OpenGL:
Since the new RT shaders are similar to compute shaders, it might be possible to emulate them and give a unified interface to the RT stuff in WGSL.

Adding such a large feature to WebGPU will take considerable time, especially since to be useful ray-tracing needs bindless resources, which are just as complex a feature (if not more). That said we could start discussions if other members of the group are ok spending some of this group's time on it (it could be boxed to its own set of label, discussions etc so it doesn't derail WebGPU Milestone1/2 discussions).
What you'd need to start is a comprehensive investigation of what the various APIs add for ray-tracing, what the similarities are and what the differences are, and ideally how developers expect to want to code against this extension. Then some iteration cycles between proposals and implementation experience, to finally get to something that's agreed upon. It will take a lot of time and effort.

Just wanted to pitch my 2 cents. I was following this from the original proposal by @maierfelix and about a year ago I started working on a WebGPU renderer.
I quickly ran into lack of RTX support, so I rolled my own implementation. But no matter how hard you try - you can't approach hardware RTX performance inside of a shader, not on triangle and trees.
The reason is not a surprise to anyone here - divergence. On WebGPU things are arguably even worse, as wave intrinsics (subgroups extension) have uniformity constraints that prevent us from optimizing.
I got pretty far, shadows work in real-time at a good perf point, but it's still some 4-8x worse than native RTX performance.
I think that having RTX support, even without hardware bindings would be pretty valuable, as it would make RTX available to people who aren't like you or I, who are experts in this field.
Why do I think RTX is valuable?
shadows ( hard shadows are generally fast enough even with SW implementation )
physics ( we can have 10s of thousands of collision checks, this would be amazing for games and particle effects )
radiance/irradiance fields (they don't need to be updated every frame, and can be updated incrementally with just a few rays each time)
non-real-time usecases, implementing path tracers that accummulate 1000s of samples to produce pretty pictures
As a realistic path forward, I recommend looking at microsoft's DXR fallback implementation
https://github.com/TeamWisp/DXR-Fallback-Layer/tree/master/src
Give kids the toy, make it better over-time. We all agree that RTX is here to stay and that it will come eventually.
Instead of waiting for years until the perfect implementation is done that supports all underlying APIs and hardware - let's get a good-enough SW solution going.

No, browser extensions don't have that level of access to the system. It's also not possible to just patch in ray tracing support, it would have to swap out the entire WebGPU implementation.
If a ray tracing implementation were in the browser already then there could be a command line flag or chrome://flags / about:config entry for enabling it. But this requires some browser work in addition to the significant native implementation work (wgpu already has some support though I don't know what the status of it is; Dawn has nothing). Generally that won't happen until we have a specific design that we're hoping for people to start prototyping with so we can get feedback.
Depending on what you want to do I would perhaps suggest starting with using ray tracing in wgpu from a Rust native application, and eventually (after probably many breaking wgpu changes) it can be cross-compiled for the web too.
