Pull request overview
This PR migrates the ROS 2 interface from the removed SDFMesh geometry to a proper volumetric SignedDistanceField representation, ensuring the field can be serialized over tesseract_msgs, converted in tesseract_rosutils, and visualized in tesseract_rviz. It also includes RViz stability/performance fixes observed during testing (mesh resource cleanup and avoiding unnecessary edge-list building) plus a monitoring hang mitigation via bounded service waits.
Changes:
Introduce SIGNED_DISTANCE_FIELD message support (new SignedDistanceField.msg, repurposed Geometry slot 8) and add toMsg/fromMsg conversions + tests.
Add RViz rendering for SignedDistanceField as a voxel “surface shell”, and fix resource leaks by removing generated Ogre mesh resources on clear.
Add a runnable ROS 2 example + launch file for SDF publishing/visualization, and bound environment-monitor service waits to avoid executor-thread hangs.

fix(rviz): drop buildEdgeList and release generated mesh resources on…
…
6d141f6
```
… clear

Two GUI-thread killers in createEntityForMeshData, hit once per CAD mesh
per full scene rebuild (and a rebuild is queued for every add/remove-link
environment event, so planning traffic multiplied both):

* Ogre::Mesh::buildEdgeList() builds stencil-shadow edge lists rviz never
  uses; on large CAD collision meshes the edge sort dominated every
  rebuild (profiled at 96-100% GUI-thread CPU for entire planning runs,
  with UI interactions stalling for minutes behind the backlog). Removed.

* convertToMesh() registers a named mesh in Ogre::MeshManager, but the
  clear paths only destroyed entities and scene nodes -- every rebuild
  leaked all generated mesh buffers (multi-GB per planning session). Add
  removeGeneratedMeshResource() and call it beside destroyEntity() at all
  three RESOURCE_NS clear sites (scene-graph render manager, contact-
  results render manager, manipulation widget).

Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>
```
fix(monitoring): bound the monitored-environment service waits
…
0f7e4e4
```
newEnvironmentStateCallback blocked on future.wait() for its
GetEnvironmentInformation / GetEnvironmentChanges / ModifyEnvironment
calls. If the monitored process exits while a response is in flight --
routine for a planner that runs one plan and exits, and a full
environment carrying SDF collision links is a 100MB+ response taking
tens of seconds to serve -- the future never resolves (rclcpp futures do
not error when the server disappears) and the monitor's executor thread
parks forever: no error, no further syncs, the displayed environment
silently frozen at its last state. Observed live as an rviz2 thread
stuck in future::wait() inside newEnvironmentStateCallback with the
planner long dead, scan links never appearing.

Replace each wait() with a 60s bounded wait; on timeout, prune the
pending request and return -- the 30Hz state subscription retries the
sync on the next message.

Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>
```
