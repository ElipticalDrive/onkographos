Copy Markdown
Setting SH degree to 0 caused excessive memory allocation because the full CUDA kernel path ran even when only a constant basis (Y₀⁰) was needed.
Changes
Short-circuit in gsplat/SphericalHarmonics.cpp: Forward/backward pass returns immediately when degree==0 using simple tensor ops instead of launching CUDA kernels
Forward: coeffs[..., 0, :] * SH_C0 where SH_C0 = 0.2820947917738781
Backward: Zero direction gradients, coefficient gradients = v_colors * SH_C0
Helper function: Added num_sh_coeffs(degree) returning (degree+1)²
Documentation: Updated parameter descriptions to clarify degree==0 means "disabled SH"
Tests: Added test_sh_degree0.cpp covering constant output, direction independence, gradient correctness, mask handling, and memory efficiency
```
// Before: Full CUDA kernel launched even for degree==0
// After: Early return with minimal tensor operations
if (degrees_to_use == 0) {
    auto sh0 = coeffs.select(-2, 0);  // [..., 3]
    return sh0 * SH_C0;  // No CUDA kernel overhead
}
```
Original prompt
Problem
Setting spherical harmonic degree to 0 currently causes PyTorch to allocate excessive memory in LichtFeld-Studio, because the code attempts to run the full SH basis computation and precomputations even when degree==0. We need degree==0 to be a supported configuration that effectively disables spherical harmonics (i.e., produces a single constant basis coefficient per direction) and takes a very small memory footprint.
Goals
Add a safe helper for computing SH basis that short-circuits degree==0 and returns a small ones-tensor without heavy computation or autograd graph overhead.
Make callers use this helper (or modify existing SH basis function) so that degree==0 is handled without large allocations. Ensure shapes are consistent and broadcasting works when using a single coefficient per direction.
Update any config/argument validation so degree==0 is an accepted value and document it as "disabled SH".
Add a small unit test that verifies degree==0 returns a ones basis and that evaluation with SH coefficients behaves as expected (no large tensors created in the normal path).
Keep behavior for degree>0 unchanged.
Required changes (high-level, agent should find exact files):
Create a utility module (or modify existing one) e.g., src/lichtfeld/utils/spherical_harmonics.py or lichtfeld/spherical_harmonics.py implementing:
def num_sh_coeffs(degree: int) -> int
def sh_basis(dirs: torch.Tensor, degree: int, device=None, dtype=None, requires_grad: bool=False) -> torch.Tensor
If degree == 0: return torch.ones(..., 1, device=device, dtype=dtype) with requires_grad only if requested.
Otherwise, delegate to or inline the existing SH computation code used in the repo.
Add a brief docstring describing that degree==0 means disabled SH and will produce a constant basis.
Update all call sites that compute SH basis to import and use this helper (or update the existing function in-place) so degree==0 is handled early.
Ensure that downstream multiplication/aggregation code accepts num_coeffs==1 via broadcasting or minor shape adjustments.
Avoid creating intermediate large tensors (for example, replace any code that does meshgrid over full images + full SH matrices without handling degree==0 specially).
Update configuration parsing/validation if there is any code that rejects degree==0. Add a note in README or config docs that degree==0 disables SH.
Add unit test file tests/test_sh_degree0.py (or under existing tests structure) with two simple tests:
sh_basis returns a ones-tensor of shape (N, 1) for degree==0 and given directions.
evaluate_sh_lighting (or equivalent function in repo) when given degree==0 and coefficients [c] yields c for any direction (i.e., constant output), and does not allocate excessive memory (basic smoke test).
Implementation notes for the agent
If the repository already has an SH implementation, modify it in place: add the deg==0 short-circuit at the start and avoid autograd allocations (create the ones tensor with requires_grad=False unless explicitly requested).
If the repo uses caching or precomputes SH bases in large arrays, ensure caches handle the scalar basis case and do not attempt to build full grids.
If necessary, add small compatibility adapters where shapes differ (e.g., expand dims or use matmul with transposes so broadcasting works).
Keep all changes well-documented with a small code comment explaining why degree==0 must be short-circuited (pytorch memory issues).
Run repository tests (if CI is configured) and ensure new tests pass.
What to include in the PR
Code changes described above.
A concise PR description summarizing the changes and the reason (avoid large allocations when degree==0). Mention that degree==0 now represents "disabled SH" and returns a single constant basis coefficient.
Add tests.
Update any docs/config where SH degree validation occurs.
Do not change behavior for degree > 0 except to call the same existing SH implementation.
If you cannot find an explicit SH module, search for occurrences of the terms: "spherical", "spherical_harmonic", "sh_basis", "sh_coeff", "spherical_harmonics", "spherical harmonic" and update those files accordingly.
If multiple candidate implementations for SH exist, update all of them or create a single canonical helper and migrate callers to it.
If any of the tests or code paths require additional adjustments to accept num_coeffs == 1, make minimal compatibility fixes rather than big refactors.
Please create a branch, apply the changes, and open a pull request into the repository's default branch with the PR title set to the problem_title above.
