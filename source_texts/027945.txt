Background
One feature I've needed for a while is the ability to show multiple data cubes with different colormaps in a single volume rendering. I finally spent some time looking into this, and have come up with two solutions. I would like to contribute at least one of these to the VisPy code base (ideally both in the long run).
Both approaches below apply to the additive volume rendering.
Preview
### Approach 1
I modified the fragment shader for additive volume rendering to be able to include an arbitrary number of textures and corresponding colormaps:
https://github.com/astrofrog/vispy-multivol/blob/master/multivol/multi_volume_shaders.py
In the raytracing loop, I then average the colors from the different textures. I then created a MultiVolumeVisual class to which I can pass a list of tuples of (data, clim, cmap), and the class deals with setting things up correctly:
https://github.com/astrofrog/vispy-multivol/blob/master/multivol/multi_volume_visual.py
Approach 2
I modified the fragment shader for additive volume rendering so that instead of using the colormap to get the color for a given texture value, I simply take the value of the texture itself:
https://github.com/astrofrog/vispy-multivol/blob/master/multivol/rgba_volume_shaders.py
I then created a RGBAVolumeVisual class that takes a 4d array with shape (z, y, x, 4) and then passes that directly to the texture.
https://github.com/astrofrog/vispy-multivol/blob/master/multivol/rgba_volume_visual.py
The data should be normalized before being passed to this class. So in this case, one can combine the multiple datasets/volumes by hand in Python using Numpy arrays, and pass the resulting array to the RGBAVolume class.
Summary
Both methods work well, and there are functional examples in the https://github.com/astrofrog/vispy-multivol repository and a screenshot at the top of this issue.
Approach 2 could be implemented with minimal effort into VisPy - one simply need to check if the data passed is 4-d (I think this is already allowed) and if so, set a flag for the OpenGL code, then modify the in_loop code fragment to ignore the colormap if that flag is set. This could all be done in a dozen lines at the most. I could also add a rgba_cube boolean option in the __init__ if needed.
Would there be interest for me to open a pull request implementing approach 2?
In the longer term, I think it would also be nice to have approach 1, because it allows the existing OpenGL colormaps to be used (whereas for approach 1, one has to have colormaps that can work in Python on Numpy arrays), so if there is interest, I can also open a pull request for this (for this one, I think it makes sense to create a separate VolumeVisual class rather than try and make VolumeVisual more complex.
For full code/description of the approaches with examples see here: https://github.com/astrofrog/vispy-multivol

I just came across this issue when looking back in on vispy after a year or two of just using gloo in my own apps...
As I understand it, this issue is about multichannel volumes, where all channels are coincident in the same 3D box and voxel grid? The advantages and tradeoffs might be:
Texture sampling a single multi-channel texture should be faster than sampling multiple independent textures (i.e. better cache locality). However, I have noticed that a 2-channel volume texture is usually much slower on multiple vendors' GPUs and should be avoided. It is faster to pack them into a 3-channel texture with a zero-padded extra channel, or to use two 1-channel textures if the padded channel requires too much texture RAM for your system.
Separate textures would allow one to have different resolution grids for each channel or even different storage types or precisions.
Separate textures would allow one to combine more than 4 channels.
In my own volume app which use gloo but not this volume visual, I use a multi-channel float16 texture for fluorescence data and a uint8 RGB texture for a voxel to object ID map. In regular rendering, I use nearest interpolation of the latter texture to determine an object ID and then lookup additional precomputed object classification information for each voxel to modify the color transfer function by class. (I also use the same object ID texture in an off-screen render to do voxel-level object picking with the mouse, and the "current pick" from mouse hovering introduces yet another class to further modify voxel class to show the user what is going to be picked if they click at that position.)
I am wondering if anybody is considering multiple volume rendering where the volumes are potentially overlapping in space but not using the same 3D box. I could make use of such composite visuals to show aligned before/after images and offer options like fast A/B and A+B rendering toggles.
I think allowing several volume visuals w/ separate transforms to be fused into one ray-casting integral would be fantastic. It would require some generalization of the ray planning to produce a depth-sorted list of start/end texture coords for each distinct texture which intersects the ray.
What is the design goal for vispy visuals? Lots of different variant visuals or one generic/flexible visual with lots of knobs and extension mechanisms?
