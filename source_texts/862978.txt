Hi Jaesung, big fan of this repo & the Vulkan version - it's the fastest radix sort I've come across, and runs flawlessly on my Nvidia desktop & laptop.
Noticing there seems to be an issue trying this on mobile where subgroup sizes can drop below 32 (tested with subgroup size 16). It seems to me the upsweep & spine stages correctly construct global & per-partition prefix sums, but the downsweep stage fails to insert keys in the globally correct offsets in this case.
I realise this repo is WIP and you may not be interested in (or have the time for) adding support for other architectures, but any chance you could give a pointer for which modifications might be necessary to be portable across subgroup sizes? Cheers

Hi colonelsalt, thanks for your interest in my work.
Yes, this repo is WIP and not actively maintained. I am not familiar with webgpu environment, nor restrictions on mobile devices, but I just tried to transfer my Vulkan code to webgpu. This is the minimal working code in my high-end desktop environment with NVIDIA RTX 5090, and hasn't been benchmarked yet.
The shared memory localHistogram is used to compute prefix sum of an array of size RADIX * waveCount = 4096, because in your case waveCount = WORKGROUP_SIZE / laneCount = 256 / 16 = 16. This overflows the size of localHistogram. First thing you'd try is to increase it to 4096.
```
const PARTITION_SIZE = 2048;
var<workgroup> localHistogram: array<atomic<u32>, PARTITION_SIZE>;  // (R, S=8)=2048, (P) for alias. take maximum.

    // local histogram reduce 4096 or 2048 or 1024  (4096 is over the size of `localHistogram`)
    // local histogram reduce 256 or 64 or 16
    // local histogram reduce 16 or 2 or 1
```
However, there's a chance of error due to shared memory limit. Second thing to try is to reduce WORKGROUP_SIZE from 256 to 128 in downsweep. Dispatch count must be doubled; a quick modification for test would be downsweepPass.dispatchWorkgroups(partitionCount * 2);.
I am sorry that I can't test it on my own, but I am happy to discuss with you and help debugging.

Hi thanks for the response & debugging tips!
You are indeed correct that the code as-is overflows the localHistogram for subgroup size 16, but doubling the size by itself doesn't seem to fix the issue. Halving WORKGROUP_SIZE & doubling the dispatch count seems to break the whole algorithm (even on a discrete Nvidia card) - my hunch is that the assumption WORKGROUP_SIZE == RADIX is baked into the code in a few places, but I'd probably need a few more days of careful reading to say that for certain.
FWIW if you were interested in testing on your end since this is WebGPU it should be straightforward to run your web app and access it from an Android device through a browser (iOS doesn't have support for subgroup semantics in WGSL at all at the moment). Alternatively switch to CPU-internal rendering on desktop (I get subgroup sizes of 16 on my laptop Intel chip).
Either way, I'll keep digging here & update if I find a solution. I'm also inclined to think the issue is somewhere in the recursive local histogram reductions, but not 100% sure yet.
