Disclaimer: I am not a member of this project, just a curious watcher.
Solving K u = F where K is positive definite can be done in a number of ways. Two common ones are:
The "direct" method using Cholesky decomposition to factorize K into L * L' where L is a lower triangular matrix followed by forward and backward substitution to solve for u in L (L' u) = F by first solving for y in L y = F and then solving for u in L' u = y. This approach is great and is generally super fast but it has 2 problems. The time complexity of this algorithm is O(n^3) where K is an n x n matrix. So for large matrices, it can take a long time to complete the factorization. The second problem is that often L will be a dense matrix even when K is sparse. This is actually usually the bottleneck, memory, where you can run out of RAM way before the method becomes too slow to be feasible. This is why the general recommendation for linear systems is: if you have enough memory, use a direct solver. Note that you don't need to compute the inverse of K to solve K u = F. This is why you have K \ F in Matlab and Julia for example to solve the system without computing the inverse. The direct solver for a least square problem would use QR or SVD factorization.
Iterative solver such as CG. CG can avoid the problems of the Cholesky factorization but it has its own set of problems. Firstly, it's often slower for most reasonably sized matrices. Secondly, when solving K u = F1 and then K u = F2, you can't easily "reuse" information from the first solve to speed up the second. But in the Cholesky case, once you have L, you can solve K u = F2 much much faster with O(n^2) time complexity and O(n) memory. Thirdly, the convergence rate of CG and iterative methods in general depend on the condition number of the matrix K. This is why it's actually a bad idea to solve least square problems using A' A x = A' b because the condition number of A' A is the square of the condition number of A so CG will be slow. There are other iterative solvers which avoid this though if you pass in A and b instead of A' A and A' b, e.g. LSMR and LSQR. A' A is also usually less sparse than A and this multiplication is costly if A is large.

Hello,
Thanks @mohamed82008 for the great feedback and discussion.
I was not the one who wrote the code for the solver, but from what I remember from our discussions, we went with CG to solve for K u = F because it was straight-forward to implement/code and for scalability reasons. We were coding the solver ourselves because we wanted to make the software easy to install and so didn't want to rely on external libraries (which is what we use in our research) that would also require installation. We didn't go the route of a direct method because when you go into 3D problems, the matrices get too large for direct methods to be practical. Since we'd have to implement an iterative solver for 3D problems we decided to only implement an iterative solver and just not bother with implementing a direct solver.
I would also not recommend doing the direct solve by taking the inverse of a matrix because that tends to be computationally expensive. @mohamed82008 mentioned this, but definitely use u = K\finstead of u = inv(K) * f in MATLAB.
Since we already implemented CG for the Ku = F solve, we just re-used it for least-squares rather than code another solver specifically for the least-squares problem.
