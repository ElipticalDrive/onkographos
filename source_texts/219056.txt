Issue body actions
Pan/zoom on a 209M-point COPC (the WV 3DEP merge) hangs: measured with a rAF long-frame monitor during live interaction, the main thread stalls up to 1.9 seconds whenever a batch of streamed octree nodes lands. Average fps between stalls is fine (~50), so this is batch-rebuild jank, not steady-state render cost.
Why
maplibre-gl-lidar decodes LAZ in workers, but every stream update rebuilds the deck.gl layer dataset on the main thread: node buffers get merged into fresh typed arrays and the layers are recreated, so cost scales with the full in-memory budget rather than the delta. Camera movement triggers repeated rebuilds (debounced at 150ms by default). Point picking additionally maintains a picking buffer over the whole set.
Shipped mitigation (size-aware tuning)
Clouds over 20M points now load with a 1.5M streaming budget, 400ms viewport debounce, and picking off by default (panel toggle still available); smaller clouds keep 4M/150ms/picking. This trades density for responsiveness inside the current renderer and is honest about being a tuning knob, not a fix.
The real fixes, in order of leverage
Incremental node management in the renderer. The mature viewers (Potree, Cesium, deck.gl's Tile3DLayer traversal) never rebuild the world per update: each octree node becomes its own GPU resource, added/removed individually, with screen-space-error-driven traversal deciding which nodes are resident. deck.gl supports this shape today (one PointCloudLayer per node, or Tile3DLayer's managed traversal). Worth an upstream issue/PR against maplibre-gl-lidar: append/evict per-node layers instead of dataset rebuild. Biggest win, benefits every consumer of the library.
Screen-space error LOD. Budget alone picks how MANY points; SSE picks the RIGHT points per view (coarse nodes when zoomed out, deep nodes only in the close-up frustum). COPC's octree carries everything needed. This is what makes "zoom out over 200M points" cheap in Potree.
3D Tiles as the heavy-cloud path (strategy phase B). Convert COPC to 3D Tiles 1.1 server-side (py3dtiles / pdal pipelines) and render with deck.gl Tile3DLayer, which already implements SSE traversal, per-tile GPU resources, and eviction. Phase B of the 3D direction wants Tile3DLayer anyway for meshes and terrain; point clouds riding the same renderer consolidates the stack. The COPC endpoint stays for interchange and external viewers either way.
Suggested sequence: file the upstream incremental-append issue now (1), prototype Tile3DLayer with a converted copy of the WV cloud when phase B starts (3), and treat (2) as part of whichever renderer wins.
