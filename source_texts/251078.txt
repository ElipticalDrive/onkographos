Base: f98243887a7 (origin/master). Risk class: R3: GLSL edits in tile_binning.glsl and both tile rasterizers, plus the C4b telemetry contract (ADR addendum included). classify_change.py fails closed to R3 for any GLSL change.
What this changes
At the default gpu_preset="high", the rasterizers keep only the nearest 12,288 records of a 16 px tile and drop the rest, which leaves tile-shaped holes in far views of real scans. This PR fixes the two side defects. It does not change the default cap, because the measurements below show that removing the loss costs a lot of frame time. That decision is the maintainer's (see "Decision needed").
The loss is now visible in production (C4b, third channel). Both rasterizers OR GS_OVERFLOW_DROP_RASTER_TILE_CAP into the resident overflow_drop_signal. The fragment path now counts too, once per tile from the tile-origin fragment, which matches the compute path. The signal word is a channel bitmask, so the binning sites move from atomicMax(…,1) to atomicOr(GS_OVERFLOW_DROP_BINNING). The layout is unchanged (88 bytes).
Per-frame production counters. The always-on readback now copies the whole 88-byte snapshot instead of 4 bytes, still in one async copy, and keeps the sampled frame's overflow_splats_clamped / overflow_tile_count. get_overflow_stats() gains sampled_dropped_records, sampled_raster_truncated_tiles (tiles the rasterizer truncated; binning drops count only in records), sampled_drop_frame_serial, overflow_drop_events, raster_tile_cap_drop_events and raster_tile_cap. The raster channel has its own warning, shown once per renderer, which names the setting and the cap in force.
The setting is honoured. max_raster_splats_per_tile now follows the max_overlap_records rule. 0 is the new registered default and means "auto" (the preset's cap, or 65,536 under custom). A positive value overrides any named preset. Before this PR, the editor showed 65,536 while 12,288 was in force.
Why the cap exists, and what raising it costs
It is a loop bound, not memory. The compute rasterizer already streams a tile through shared memory in batches of GS_TILE_SPLAT_CAPACITY = 1024 (tile_rasterizer_compute.glsl:229-283), so shared memory does not depend on the cap. The records already exist in the sorted overlap buffers, so raising the cap costs 0 VRAM. What the cap bounds is time: one 256-thread workgroup walks all records of its tile serially, so the densest tile is the critical path of the raster pass. The cost is roughly linear in min(peak tile depth, cap), about 0.3 ms per 1,000 records on an RTX 3090. Saturated tiles exit early, so the extra time is spent only where the dropped records would actually show.
It cannot sensibly be derived from the record budget. The record budget is a VRAM quantity, while the cap trades per-tile latency against content. An adaptive cap would need a frame-time controller, and that is out of scope here.

At the default, all four scans lose content at ordinary distances. Removing the loss adds +33% to +75% whole-viewport GPU time in those views (+2.3 to +10.9 ms on a 3090). 32,768 still leaves holes. Near views (1x for holzbank, lamp and tischgruppe) are unaffected.
Pixel evidence (local, agent session scratchpad tilecap/holz_d6_cap_compare.png and weg_d1_cap_compare.png): holzbank d6 at the default shows rectangular black tiles under the seat (x 448-511, y 256-287, matching #1137); 32,768 and 65,536 draw the grass there. weg d1 at the default has several 16 px black blocks along the path edge; 32,768 still has one; 65,536 has none.
Decision (recorded)
Maintainer decision, 2026-10-02: Option A. Keep the default cap of 12,288. Keep the new warning, the counters, and the honoured setting. Document the holes as an alpha limitation until HLOD (#1136) lands. That entry is in docs/development/known-public-alpha-limitations.md with status Active. It is not ledger-accepted: no acceptance-bar §8.1 row and no public_alpha_issue_ledger entry exist yet. That formalisation, an R3 manifest edit, is a follow-up if wanted. The fact that the test project runs at cap 65,536, so CI never exercises the shipped default, is filed separately as #1139.
Options that were considered
A. Keep 12,288 (this PR). The loss is now a warning plus counters, and a project can opt in with the setting. HLOD (docs: ADR — hierarchical LOD for streamed splat worlds, accepted (Refs #1131) #1136) is the cure, because it lowers far-field tile depth. Document it as a known alpha limitation.
B. high = 32,768. Fixes holzbank, tischgruppe and most lamp/weg views. Up to +60% viewport GPU (lamp d6). weg d1 and lamp d6 keep holes.
C. high = 65,536. No loss on any measured scan. Up to +75% viewport GPU (weg d1: 14.5 to 25.4 ms).
A structural fix (splitting a hot tile across several workgroups and merging the results) would remove the critical path. It is not small enough for alpha.

P1: with two channels in the sticky signal word, the frame-start re-arm could erase a bit
another channel set while a readback of the first was in flight, losing that channel's
warning and counter. The poll now clears the signal word right after recording its copy, in

rasterizers write the signal too.

Tile binning drops records one at a time and has no per-tile once-flag, so
overflow_tile_count only ever counts tiles the rasterizer truncated: past the per-tile
raster cap, or with the whole record range beyond the overlap budget. The production field
is renamed sampled_dropped_tiles -> sampled_raster_truncated_tiles, and the header, API
docs, ADR, limitations page and warning text now say exactly that. sampled_dropped_records
still counts records from every channel, so it can be non-zero while the tile counter is 0.
