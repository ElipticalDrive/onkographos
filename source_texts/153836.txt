Finding (iOS parity audit, 2026-07-18 — adversarially verified)
SplatNode / SplatCloud / rememberSplatCloud (3D Gaussian Splatting, shipped on Android by #2646 with the splat-preview demo, documented at llms.txt § SplatNode) is:
Absent from SceneViewSwift — grep -ri "splat" SceneViewSwift/Sources/ returns zero hits; no symbol under any name.
Absent from every parity table in docs/docs/cheatsheet-ios.md — not in the "Node Types — 3D" table, not in Android-only — no port planned, not in Deprecated, not in Approximated.
Point 2 is the actual bug. The iOS cheatsheet is otherwise scrupulous — it honestly documents ~25 deliberate Android-only gaps (DOF, playbackDataset, StreetscapeGeometry, Terrain/Rooftop anchors, SemanticMode, hand tracking, …), and the audit confirmed all of those are correctly deferred, not parity bugs. SplatNode is the only silent gap: an AI generating SceneViewSwift code for splat content today gets no signal the capability doesn't exist on iOS. For an AI-first SDK that's a doc-contract break, not a nice-to-have.
Fix — two independent layers
Now (docs, trivial): add a SplatNode row to the cheatsheet's Android-only table (and the llms.txt iOS-parity note if applicable) stating splatting is Android-only today. This restores honesty immediately.
Later (product decision): whether to port Gaussian Splatting to RealityKit at all. Non-trivial (no first-party RealityKit splat primitive; would need a custom Metal path or a mesh-impostor approximation). Needs a maintainer call on priority vs the existing Android-only precedents — fine to park as needs-decision.
Provenance
Found by the parity-audit workflow (iOS-only run, 3 agents, every claimed gap adversarially verified against source; this was the single confirmed HIGH — the rest of the SceneViewSwift public surface is either mirrored or honestly deferred). Demo-catalog parity (samples/ios-demo vs the 51 Android demos) is being audited separately.
