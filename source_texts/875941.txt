What
Dense now decimates the mesh inside OpenMVS TextureMesh (--decimate <ratio>), so the textured mesh is aimed at post.target_faces before post runs. Two new [dense] keys control it: texture_decimate (default true) and texture_headroom (default 0.95, validated in (0, 1]).
Why
Post's seam-keeping decimation stops at 740,903 faces on vartiosaari, above the 500,000 target, because the many-chart OpenMVS atlas blocks collapses (ADR-0012). Collapsing across seams reaches the target but produces texture speckles. Decimating before texturing gives an atlas built for the reduced mesh.
How
After ReconstructMesh, Dense::run reads the face count of mesh.ply with the existing ply::element_counts and computes decimate_ratio(target_faces, headroom, faces) = target_faces * headroom / faces. The flag is omitted when the ratio would be 1 or more or the mesh has no faces; the ratio is clamped to 1e-6 because OpenMVS reads 0 as "auto".
texture_mesh_args(out, ratio) is the single definition of the TextureMesh argument list; openmvs_steps calls it with None, and the run loop replaces the TextureMesh step's arguments with texture_mesh_step_args(out, config), which reads mesh.ply only when texture_decimate is on. Stage::steps is unchanged.
Stage::config includes post.target_faces when texture_decimate is on, so changing the target invalidates the dense cache; with decimation off it does not. REVISION stays 1: the new [dense] fields already change the fingerprint.
mesh.ply and the mesh_faces metric remain the undecimated ReconstructMesh output (TextureMesh writes only mesh_textured.glb).
Docs: configs/defaults.toml and the docs/kickoff.md [dense] block, a "Decimation before texturing" section in ADR-0011, and a cross-reference in ADR-0012. Post's own decimation is unchanged.

Should fix before merge
ADR-0011 still says the validation is pending. docs/adr/0011-splat-and-dense-images.md:77-78 ends with "Pending: re-running dense on both datasets on the GPU host…". The popos run has finished, so replace that bullet with the results: ReconstructMesh faces → --decimate ratio → post mesh_faces for each dataset, TextureMesh time 455 s→111 s and 1377 s→102 s, and "no speckles". The ADR is the long-term record, and the PR comment will be hard to find later.
Fix this →
Nits / optional
The ratio is not recorded in the metrics. Dense::run (crates/dense/src/lib.rs:265-272) records mesh_faces from the undecimated mesh.ply, as intended. The --decimate ratio itself only shows up in the TextureMesh log. You had to piece it together from logs for the validation table, which suggests it should be easier to find. A texture_decimate_ratio metric (or 1.0 when the flag is omitted) would put it in the manifest. The function that builds the arguments could return the ratio along with them.
mesh.ply header is read twice. It is read once in texture_mesh_step_args and again at line 261. The cost is negligible because only the header is parsed. It only matters if you do item 2, since the face count could then be reused.
Two tests depend on the default config without checking it. texture_mesh_step_reads_mesh_faces_only_when_decimating and target_faces_is_in_the_config_only_when_decimating load reposalmi-laajasalo.toml and assume texture_decimate comes out true from defaults.toml. If that dataset config ever set texture_decimate = false, the first assert_ne! and the --decimate assertion would fail with a confusing message. Setting config.dense.texture_decimate = true; explicitly at the start of each test fixes this.
Edge case at the rounding boundary (harmless). A ratio in [0.9999995, 1) formats as 1.000000. OpenMVS only decimates when the value is below 1, so it does nothing in that case, which is the right result. I mention it only so nobody later tightens the check to ratio <= 1.0 expecting a change in behaviour.
Change in config fingerprint shape. With decimation on, Stage::config returns {dense: {...}, target_faces}. With it off, it returns the bare dense object. That is fine for invalidation and is tested. Keeping REVISION = 1 is also fine: adding the new fields already changes every existing dense fingerprint, so caches built before this PR re-run once. That is expected, given that the output does change.
Checked, no issues
--decimate is a face fraction, the 1e-6 clamp stops the value from formatting as 0.000000 (which OpenMVS reads as "auto"), and the flag is skipped for empty meshes and for meshes already under the target.
Validation: !(h > 0.0 && h <= 1.0) rejects NaN, and the non-finite list also covers dense.texture_headroom.
The host reads mesh.ply before mount() rewrites the paths, so it reads the host path.
Processes are still spawned only through ToolRunner, as ADR-0003 requires.
Stage::steps still lists the log names in run order.
Docs: defaults.toml, kickoff.md, ADR-0011 and ADR-0012 agree. The headroom explanation (hole filling in Mesh::Clean) matches the review finding.
I did not run cargo in this job. The PR comments report fmt, clippy and nextest all passing (245 passed, 6 skipped) with a private target dir.
