The version was pinned at 2.14.4 because 2.21.4 rendered nothing, and the pin
was always meant to buy time rather than settle anything: non-unified rendering
is documented as being removed, so the choice was when rather than whether.

Unified rendering is the default from 2.15 on, and GSplatComponent#instance
returns null there. Two things were being reached through it. The cue to draw,
which mattered because drawing happens on demand here and the sorter announcing
a finished ordering was what asked for the next frame; and the gaussian
positions, which frame the scene on load. Both are published API now.

The cue is the gsplat system's frame:request, which PlayCanvas added for
exactly this case -- it fires once per frame when streaming or sorting has
produced something a render would show, and the engine's own documentation for
it sets renderNextFrame from the handler with autoRender false. It is read from
pc.GSplatComponentSystem.EVENT_FRAMEREQUEST rather than written out, so a
rename upstream is a build error here instead of a blank canvas. The positions
are GSplatResourceBase#centers, guarded by hasCenters because reading centers
on a resource that has none can allocate one. The `as unknown as` cast that hid
the whole failure from the type checker is gone.

There was a second break, not in the release notes and missed by the earlier
trial. 2.21.4 selects the parser for a gsplat asset from the extension of the
name it is given, and the editor's "open a .ply from this machine" hands the
viewer a blob: URL, which has no name at all. The asset was refused outright
with "No parser found for resource" before any rendering was reached. Scenes
from the backend were unaffected -- their URLs end in scene.ply -- so testing
only that route would have shipped a viewer that could not open a local file.
The asset is now given a filename alongside the url, falling back to scene.ply
when no extension can be found, which is honest: the only control that produces
a nameless URL accepts only .ply.

The hoped-for simplification is not available. The GPU sort that prompted
"find out whether this machinery can be deleted" is WebGPU-only; this viewer
asks for WebGL2, which is also all iOS Safari offers, so the engine resolves to
CPU sorting in a worker and the scheduling has to stay. Only the cue moved.

The off-axis projection stays as it is. Measured rather than assumed: in
side-by-side mode the two eyes sit at local x of -0.06 and +0.06 with all three
Euler angles zero, and their projection matrices are identical in every
vertical term (m[5] 1.71516871, m[9] 0) and opposite in the horizontal skew
(m[8] -0.04197516 and +0.04197516). Not within a pixel -- the same bits.

Verified by loading a scene and looking at it, because that is the only check
that catches this class of fault: 2.21.4 passed typecheck, lint, all 142 tests
and the build while rendering nothing at all, and again while unable to open a
local file. A 1,179,648-gaussian scene reads mean luma 52.91 against 13.14 for
the clear colour. 180 frames elapse while idle and 0 are rendered, so drawing
on demand survived. A 20-step camera drag produces 20 renders and one more when
the ordering arrives. Frame time under continuous drag is 16.7 ms median in
both mono and side by side, which is the display's own interval. Side-by-side
export gives 1920x1080 with content in both halves. Checked from the backend,
from a local file, on viewer.html, and against the production build.

package-lock.json loses 446 lines because 2.21.4 dropped the optional canvas
dependency and its tree. Nothing was removed by hand.
