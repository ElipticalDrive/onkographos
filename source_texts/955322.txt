Summary
Morton (Z-order) ids were planned as a spatial sort key for DuckDB and Parquet: bit 52 would flag them, and then encode_morton/decode_morton would be exported (README "Future enhancements"). Measurements show they don't help at our data scale. This PR shelves the plan and deletes the unused internal code.
Deletes src/beahiv/morton.py and tests/test_morton.py. Neither was exported or used, so the public API is unchanged.
Removes the README "Future enhancements" section (Morton was its only item) and the "likely a Morton flag" wording for bit 52 in README and cell_id.py. Bit 52 stays reserved, with no planned use.
Removes the morton.py mentions from AGENTS.md.
Adds a JOURNAL entry with the full measurements.
Why
I prototyped the full plan first: the bit-52 flag, each decoder refusing the other layout, batch versions, and a 2.5× faster interleave. Then I measured it.
DuckDB 1.5.5: 10M points over 600 × 600 km (~28/km², about crime-data density), 100 m cells, 100k-row groups. Each figure is the share of rows read for an x/y box query, averaged over 20 boxes:

Almost all the gain comes from sorting by any spatial key, and the plain cell_id already is one: Parquet query time drops from 52 ms to 4–6 ms. A 100k-row group covers about 3,600 km², larger than a typical query box, so plain order's column-shaped strips are only about 6 km wide.
Morton only pulls ahead when row groups are much smaller than the query box. With 10k rows per group (5 km box), plain reads 0.96% and Morton 0.46%. Even then, Hilbert does better (0.29%). Z-order row groups that span one of the curve's jumps get wide x/y ranges, which weakens pruning.
On the original question about non-orthogonal axial (q, r): the 60° skew costs Z-order only about 5–10%, because aligned blocks become √3:1 rhombi instead of squares. The skew was not the problem; the data scale was.
If dense data ever needs this, a Hilbert sort column written next to cell_id would be enough, with no need to change the id format or spend bit 52.
