Overview
Adds bilinear interpolation to 2D lookup tables, as one property: bilinear = true (default false).
With it, table.name(col_key, row_key) interpolates between column keys as well as between row keys, and clamps at the table's edges on both axes. Without it, 2D tables behave exactly as before: the column key must match exactly.
Refs #412. This delivers the bilinear part of that issue. Per-axis interpolation methods and extrapolation policies, proposed in the first version of this PR, are not included; see the review thread above and ADR-0009.
What this is faster or clearer than (ADR-0009 §6)
A bilinear lookup can already be composed from one 1D table per column and an expression that interpolates between them. The dedicated form is clearer, since the grid is written once as a grid, and faster, since it is one lookup that finds each bracket once.
Cost to models that do not use it
None measured. The choice is resolved at expression lowering into its own AST variant (Lookup2DBilinear); bilinear is never read by a lookup. The existing lookup functions (clamped_lerp, LookupTable1D::lookup, LookupTable2D::lookup, find_column) are not edited.
Against the merge base, 30 interleaved reps, median of paired differences, one machine (Apple M5): -0.1%, -0.3%, +0.8%, -0.3%, +0.8% on speed tests 1 to 5, and +0.2%, 0.0%, 0.0% on three synthetic models using existing 1D and 2D tables. Output is byte-identical on all eight. An identical rebuild of the merge base measures within about 0.5% of itself. Tests 3 and 5 sit at the edge of that and are worth a re-run on a quiet machine.
Behaviour
Interpolates down the two columns either side of the column key, then between those two results.
A column key that equals one of the table's column keys returns bit for bit what the exact-match lookup returns.
Both axes clamp. There is no exact-match error on a bilinear table.
NaN in either argument gives NaN, as for 1D tables.
bilinear takes true or false. bilinear = true on a 1D table is an error at model load, and in the IDE linter.
Implementation notes
LookupTable2D::lookup_bilinear finds the column bracket and the row bracket once each. For key sets of 32 or fewer the bracket is found by counting keys below the argument without branching; longer sets use a binary search.
The engine reaches it through lookup_bilinear_with, an out-of-line function that takes the evaluation of the two arguments as a closure. Inlined into evaluate, the lookup cost models with no bilinear table 3-4%; this arrangement costs them nothing and is as fast for models that use it. The commit messages carry the measurements.
Loader, canonical saver, IDE validator, autocomplete and tooltip, user docs and engine docs are updated.
Testing
Engine: 936 tests pass. The bilinear tests were checked by putting eight faults into the code one at a time (wrong and reversed column weight, fixed bracket, no exact-key return, lowering always bilinear, saver line deleted, stateful argument not advanced, 1D accepted) and confirming a test fails on each.
IDE: ./gradlew build passes, with new validator tests.
Regression suite: all models verify.
Website: mkdocs build --strict passes.
Not covered yet
No test has a table with more than 32 keys, so the binary-search fallback is not exercised in the repo.
No model in regression_tests/speed/ uses a table, so the suite does not guard these timings.
Both are planned with the follow-up that applies the same bracket count to the existing 1D and exact-match lookups.

Agentic review results:
Three independent review passes (performance, behaviour, scope) primed with the Manifesto and ADRs on cbdb960:
The bilinear 2D implementation is correct.
Existing lookups are slower: up to 3.8x per lookup, and +32% on a table-heavy model run (ADR-0004 §3.1, §3.5).
Existing results change at a table's last breakpoint (1 ulp, from the <=/>= guards becoming </>).
next_lower, exact rows, per-axis methods and on_extrapolation are additional to scope with implications for UX and performance (Manifesto §2.7, §3); new warn error level prints to stderr, which the IDE and Python cannot see, has implications for UX.
The eight-argument lookup_axis spills to the stack on every call; main's clamped_lerp fits in registers. Smaller is faster.
The new tests check property round-tripping only; no new lookup semantics are tested.
The test file was committed as CRLF, so the diff shows 923 lines for 65 real ones.
What the minimal version looks like:
A bilinear = true property on 2D tables, default false. One new method on the existing 2D type that runs the current clamped_lerp down the two bracketing columns and lerps between them, about fifteen lines. A second AST variant in dynamic_input.rs chosen at lowering, so the existing Lookup2D arm is untouched. Loader, saver, one validator case, one autocomplete entry, a short docs subsection, and numeric tests. Roughly 100 lines, zero edits to the current lookup functions, so existing performance and behaviour is safe.

Great stuff Tom. Sorry I had a heckers week. Your bilinear is in!
I fiddled a little bit to eek out a bit of performance in the 1D case.
Also an agent found an interesting result from the interpolation (the existing approach; nothing you introduced). Tiny floating point numerical errors sometimes lead to answers that land outside the segment in the PWL table. We're talking about errors in the last 2bits of the f64. The following 1D table returned −1.4e−17 for x = 0.1
0, 0.1,
0.1, 0,
1.1, 7
Numerical noise is inevitable, but this example that caught my attention because it goes negative and (slightly!) and that may lead to havoc depending on how the modeller is using the value.
So I checked the cost of a clamp across the board (it's about 1%) and applied that in commit d86d8e3 for correctness.
