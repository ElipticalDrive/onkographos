Attacks the confirmed bottleneck: on device the debug HUD showed ray 80ms vs blit 32ms (grid 110x55, 8 cores) -> ~9 FPS. The raymarch dominates.
Why it was slow: the heightfield hit was found by marching the ray in tiny fixed ~0.12u steps, i.e. hundreds of iterations and World.heightAt lookups per ray.
Fix: the world is a heightfield of integer columns, so the sampled column only changes when the ray crosses a cell boundary. This PR replaces the fixed-step loop with a 2D DDA (Amanatides-Woo grid traversal): one heightAt per column, a few dozen boundary steps per ray instead of hundreds. The hit test is exact for the blocky world -- a taller column is a vertical wall (hit on entering it below its top), and a descending ray hits the flat top where its y crosses the column height.
Note: this is an algorithmic change, not pixel-identical to the previous sampler (it's actually more precise at block edges). Isolated to Renderer.java, easy to revert. After merging, please re-check the HUD ray value -- it should drop several-fold.
Reality check: even so, blit (~32ms) alone caps around ~30 FPS, so 60 isn't reachable with the current ASCII-grid size on this device; the next lever is a smaller gridW/gridH (a visual tradeoff), left out of this PR.
