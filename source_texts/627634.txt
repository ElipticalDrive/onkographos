What changed
The camera-only motion blur (reprojecting each pixel's depth through last frame's view-projection, inside the composite) is replaced by per-object motion blur over the velocity target #1435 writes: the reconstruction filter of McGuire et al. 2012, weighted as Jimenez refined it for CoD: Advanced Warfare (2014).
Shader engine/shaders/postfx/motion_blur.wgsl (new, standalone; split along the motion-blur seam only, postfx.wgsl's grading code is untouched apart from deleting the old motion_blur fn and its call):
fs_tile_max_x then fs_tile_max_y: TileMax in two passes (each tile's pixel rows, then the tile), one texel per tile holding its longest streak. A streak is the pixel's NDC motion in pixels × intensity, clamped to max_length × view height; a non-finite motion (checked on the exponent bits) is no streak, so no inf/NaN reaches the gather or bloom. Two passes keep a 216 px tile (4K, clamp 0.2) at two 216-tap loops instead of one 46k-tap loop.
fs_neighbor_max: the longest streak of each tile's 3×3 neighbourhood, so blur spreads past a silhouette.
fs_gather: samples taps along the neighbourhood streak, each offset by a screen-space interleaved-gradient-noise jitter (pixel-keyed, not time-keyed). Tap weight = behind · reach(center_radius) + in_front · reach(tap_radius). Order is stack first, then distance (behind()): a tap drawn by a higher camera of the stack is wholly in front, a lower one wholly behind; on the same camera, a soft compare on each pixel's view distance from the velocity target (0.1 m soft band). Uncovered weight keeps the centre colour. A pixel whose neighbourhood streak is under 1 px returns textureLoad of the centre, so a still frame is exact.
Rust render::postfx::motion_blur (new):
MotionBlurPasses: the renderer-owned layout and four LazyPipelines, listed in Renderer::lazy_pipelines and so warmed by a windowed renderer.
BlurTargets: per view, owned by PostFx::blur. A full-res HDR "blurred scene" target and the params uniform, kept while the view's size holds, plus TileTargets (TileMax rows, TileMax, NeighborMax; Rg16Float), kept while the tile size holds too, so a clamp ramp rebuilds only the tile textures. Allocated only while the view blurs, dropped on resize or on a frame without blur.
PostFx::run_motion_blur encodes the four passes before the chain. PostFx::scene_color() is what bloom's bright-pass, the composite and the UI backdrop's composite_into now read (motion blur before bloom, as URP/HDRP).
BlurParams (params.rs) is pure: the tile size is the half-streak rounded up to a multiple of 8 (Unity's rule, so the 3×3 neighbourhood covers every streak). BlurParams::per_frames(n) divides the shutter by n.
Velocity target widened (Per-object motion vectors: a velocity buffer from each draw's current and previous transform (incl. skinned) #1435's): Rgba16Float. .b = the surface's distance from the camera that drew it (fs_velocity: length(world_position - camera_pos); the sky and unwritten pixels: render::motion::SKY_DISTANCE = 65504, mirrored in sky/motion.wgsl and held equal by a test). .a = the drawing camera's index in its stack (0 the base; the sky and the clear stay 0), from a new CameraUniforms.stack vec4 (x; Rust CameraUniform::stack, layout test updated to 256 bytes). It clears and composites like the velocity (nearest camera wins), so the blur's depth order survives a DepthOnly overlay that cleared the depth buffer, an overlay with a different near plane or FOV, and a wall nearer to the world camera than the gun is to its own camera.
Behind-camera guard (restored from the old blur): fs_velocity writes zero motion where last frame's clip.w <= 1e-4, a surface that was behind the camera last frame (a projectile past the player's head), instead of a huge reprojected streak.
Render-texture shutter: a render-texture camera drawn every N frames has a motion history N frames old. StackPass::motion_frames carries the frames since the slot last drew (render_texture::slots::frames_since, 1 on a first draw and for the screen), and the blur's shutter is divided by it, so a monitor's blur matches one frame's.
Gate: motion::wanted(post, graphics, full, scene_view) decides both the velocity pass and the blur (blur_params(..).filter(..)), and run_motion_blur also needs this frame's velocity target. So no velocity target (first frame, a cut, Low, the player option, a shader preview, post_fx = false, the editor's Scene view) means no blur and no targets. The Scene view never blurs (Unity's doesn't), so flying the editor camera writes no velocity; the Game view and Play still blur.
Removed: PostParams::prev_view_proj (and its common.wgsl mirror), the motion-blur slots in PostParams.flags / misc (now unused), and CameraCtx::base_prev_view_proj (no reader left).
Knobs on CameraComponent (the issue's decision, answered yes):
motion_blur_intensity: Unity's Intensity, the shutter fraction. Default 0.5 (180°), clamped 0..=1.
motion_blur_max_length: Unity's Clamp, the longest streak as a fraction of view height. Default 0.05, clamped 0..=0.2.
Each one has a shared authoring op (set_motion_blur_intensity / set_motion_blur_max_length, which hold the clamps), a Camera-card slider (the motion-blur widgets moved to inspector/components/camera/motion_blur.rs), Graphics.Get/SetMotionBlurIntensity / MaxLength, a field op, doc rows and save/load (serde default for a file without them).
Timing: new GpuPass::MotionBlur (gpu_passes.motion_blur in Debug.Stats) covers the three tile passes and the gather.
Getters without a screen camera all read "off" (false, 0, 0, 0): nothing blurs, so none claims a default. Graphics.md says exactly that.
Docs: docs/api/Graphics.md gains a Per-object motion blur section (Scene view, stack-then-distance order under an overlay, the behind-camera guard, render-texture shutter, bloom order) and the two rows; docs/api/Debug.md gains the motion_blur pass key; docs/api-faithfulness.md's motion-blur row lists all four setters at their real read-site. PostFx::run's doc no longer says the blur reads depth_view.
Why
The camera-only blur smeared the viewmodel and never blurred anything moving under a still camera (an enemy sprinting past, a swing, a ragdoll). A gather along each pixel's own velocity would blur inside a silhouette and leave the edges hard, which reads worse than no blur. The reconstruction filter is what shipping shooters use, and Trepang2-class combat is the bar.
Effect
An object moving past a still camera blurs, and its blur reaches past its silhouette onto the background.
The world blurs under camera rotation while a DepthOnly overlay camera's gun stays sharp, even with the player pressed against a wall.
A still frame is pixel-identical to motion blur off.
Behaviour change: motion blur no longer needs an active PostProcessing volume. It is the camera's, like FXAA, and the velocity pass (Per-object motion vectors: a velocity buffer from each draw's current and previous transform (incl. skinned) #1435) already ran without one, so a camera with motion blur on and no volume used to pay for velocity and get no blur. A camera with motion blur on (new cameras default to on) now blurs whatever moves in Play.
Decisions
Blur as its own pass, before the composite, not inside it. The composite just reads scene_color(). That keeps the blur out of Post Processing: colour grading (white balance, lift/gamma/gain) through an internal LUT #1440's grading code and makes "off" a byte-exact pass-through.
Tile size from the clamp (Unity's rule) rather than a fixed ≈20 px, so the 3×3 NeighborMax always covers the longest allowed streak at any resolution.
Clamp is a fraction of the view's height (Unity's convention; the issue said "screen fraction").
Soft distance band 0.1 world units, on Euclidean view distance in a half float (its step passes 0.1 beyond ~128 m, where the compare becomes a hard nearer-wins).
Stack index in a new CameraUniforms.stack slot rather than a push constant or a second uniform: every pass already binds the camera uniform, and the sky shaders' .a stays 0 untouched.
Render-texture shutter divides by the actual frames since the last draw (update_every in steady state), so a monitor that skipped frames while hidden still blurs one frame's worth.
Review fixes (second brief): Scene view gate, per-camera distance in the velocity target, bloom after blur, two-pass TileMax, size-only key for the blurred target, faithfulness row, consistent no-camera getters. Folding the passes into PostFx::run's encoder (optional) was not done: the blur still submits its own encoder.
Review fixes (third brief): stack order before distance, the behind-camera guard plus non-finite streaks, the render-texture shutter, PostFx::run's doc.
main is merged in, not rebased: the container refused the force-push, so 65e0816 (Post Processing: colour grading (white balance, lift/gamma/gain) through an internal LUT #1440, colour grading) came in as a merge commit. The conflicts were the shader registry list, the renderer's resource lists, the camera card's module list and postfx.wgsl's header and old motion_blur fn (deleted; grading's LUT kept).

Seam
PostFx::scene_color() is the HDR image bloom and the composite read: the blurred scene when motion blur ran this frame, else scene_hdr. A later pass that must run after motion blur and before the composite should read and write through it.
The velocity target (render::motion::VELOCITY_FORMAT, Rgba16Float) carries .xy NDC motion, .b the drawing camera's view distance (SKY_DISTANCE where the sky or nothing drew) and .a that camera's stack index (CameraUniforms.stack.x). Any pass writing it as a second colour target writes all four.
motion::wanted(post, graphics, full, scene_view) is the one gate for velocity and blur.
postfx::params::blur_params is the one place the camera's knobs become BlurParams, StackPass::motion_frames how many frames one draw's velocities span, and GpuPass::MotionBlur its timing bucket.
