Summary
On Windows, the trainer rejects a valid dense roma.ply larger than 2 GB with PLY: truncated header. The file is intact; the loader's 32-bit file-size query fails and produces an empty input buffer.
Environment
Spirula Studio 2026.10.16, upstream commit 65246c5579c127081bff6f4422bd12a542906f78
Windows 11
Dense output: dense/roma.ply
File size: 12,742,277,921 bytes (12.74 GB)
Vertex count: 471,936,212
PLY header: complete, 197 bytes
Integrity check: full SHA-256 matches dense/manifest.json
The same sizing code remains in release 2026.10.30 and current master, so updating alone does not address this failure.
Reproduction
Generate or import a binary little-endian PLY point cloud larger than 2 GB on Windows.
Open its dataset in the trainer.
Observe PLY: truncated header despite the file having a complete header and valid checksum.
Expected behavior
The trainer reads the large valid PLY, or reports a genuine resource-limit error if allocation fails.
Actual behavior
The trainer reports a truncated header before parsing the valid file.
Root cause
read_ply_points in src/data/parsers/NerfstudioParser.cpp uses:
```
std::fseek(f, 0, SEEK_END);
long fsize = std::ftell(f);
std::fseek(f, 0, SEEK_SET);
bytes.resize((size_t)(fsize > 0 ? fsize : 0));
```
On Windows/MSVC, long is 32-bit even in 64-bit builds. For this 12.74 GB file, ftell returns -1; the conditional then resizes bytes to zero. PlyVertexReader consequently reports PLY: truncated header.
Affected code on current master (f87882cb0d967e3fdfee7eb0c478ea7b84c1ce5c):
spirula-studio/src/data/parsers/NerfstudioParser.cpp
Lines 246 to 249
in
f87882c
bytes.resize((size_t)(fsize > 0 ? fsize : 0));
if (!bytes.empty() && std::fread(&bytes[0], 1, bytes.size(), f) != bytes.size())
throw std::runtime_error("PLY: cannot read " + path);
}
Suggested fix
Use 64-bit file sizing, preferably std::filesystem::file_size with explicit error handling, then validate that the result fits size_t before allocating. _fseeki64/_ftelli64 would also address the Windows size-query failure, but filesystem sizing is portable.
No patched build has been tested yet; this report is based on the observed runtime failure, full-file integrity verification, and the affected source path.
