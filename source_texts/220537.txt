Describe the project you are working on
A VR application which makes use of multiple viewports and which ray marches volume data, making rendering quite expensive. This is especially dependent on the screen area covered by of the direct volume rendering. Thus the quality of the ray marching needs to be varied based on current FPS to prevent VR sickness (by keeping a target frame rate).
Describe the problem or limitation you are having in your project
Related to: #8399
Currently there is no method exposed to obtain all active viewports. This in turn means that there is currently no way to get completely accurate frame times of the GPU (independent of vsync). Thus, it is not possible to improve quality settings adaptively. (Or show correct profiling data in the application.)
While there are multiple solutions suggested in the related issue (and the example of the debug menu is linked), none of them work completely.
The method:
```
var viewport_rid := get_viewport().get_viewport_rid()

# Enable measurements (call once in `_ready()`).
RenderingServer.viewport_set_measure_render_time(viewport_rid, true)

# Get measurements (call once every frame).
var frametime_cpu := RenderingServer.viewport_get_measured_render_time_cpu(viewport_rid) + RenderingServer.get_frame_setup_time_cpu()
var frametime_gpu := RenderingServer.viewport_get_measured_render_time_gpu(viewport_rid)
```
Does not work, as you cannot get the RIDs of all viewports which will be rendered. You can iterate the scene tree and get viewports contained in it, this does however not account for viewports directly constructed on the RenderingServer using viewport_create(). This is used for example by the material or mesh preview in the editor. While this is not that relevant at runtime of the application, users might be using viewport_create()in their own code.
Additionally:
RenderingServer.frame_pre_draw and RenderingServer.frame_post_draw do not work, as they are affected by vsync.
The Visual Profiler and its data are not exposed in any way (that I found).
Describe the feature / enhancement and how it helps to overcome the problem or limitation
Expose a method in RenderingServer that returns the list of active viewport RIDs.
In the context of this issue this would allow fetching all active viewports on RenderingServer.frame_pre_draw to then enable the measuring for all viewports and finally collect the data on RenderingServer.frame_post_draw.
Describe how your proposal will work, with code, pseudo-code, mock-ups, and/or diagrams
In RenderingServer implement and create bindings for:
```
virtual TypedArray<RID> viewport_get_active_viewport_rids() const = 0;
```
(I am open for a better name).
This could expose (map back to RID) the active_viewports property of RendererViewport. The function itself would be implemented in RendererViewport.
If this enhancement will not be used often, can it be worked around with a few lines of script?
It can only be worked around partly by fetching all viewports within the scene with for example:
```
var viewports := get_tree().root.find_children("*", "Viewport", true, false)
```
This however does include inactive viewports. Additionally, all viewports created without Nodes using viewport_create() are missing.
This change would not be needed if #1807 was implemented.
Then you could manually keep track of the rendering time of each viewport by connecting to the signals. Additionally, you could also construct your own list of active viewports by making use of the viewport- and frame- pre_draw and post_draw signals.
Is there a reason why this should be core and not an add-on in the asset library?
It is not possible to access this data from GDScript or GDExtension.
If there is interest, I would be happy to contribute a PR implementing this functionality.
