Issue body actions
Summary
Add a new geoscience object schema isosurface-volumes to represent the output of isosurfacing algorithms applied to scalar field data. This schema captures isosurfaces at threshold values, volumes bounded by those surfaces, and boundary surfaces at the domain extents — all sharing a common triangulated mesh geometry with parts.
Motivation
Isosurfacing is a fundamental operation in geoscience workflows for:
Grade shell visualization: Extracting surfaces at ore grade thresholds (e.g., 0.5 g/t, 1.0 g/t Au)
Geophysical modelling: Visualizing density or magnetic susceptibility boundaries
Domain decomposition: Partitioning a volume model into regions above, below, and between thresholds
Property visualization: Displaying continuous property distributions from block models or interpolation results
Currently, there is no standard schema for representing the complete domain model output of isosurfacing operations — including the relationship between threshold values, the resulting surfaces, and the enclosed volumes. The existing geological-model-meshes schema serves geological interpretations with features like "Fault", "ContactSurface", and "OutputVolume", but does not capture the threshold-based semantics of isosurfaces.
A dedicated schema would enable:
Interoperability between isosurfacing compute tasks and consuming applications
Preservation of threshold metadata for downstream analysis
Clear representation of volume relationships (below/between/above thresholds)
Standardized boundary surface representation for domain extents

Parts sharing
Like geological-model-meshes, the schema leverages parts to enable conformal meshes:
Parts can be shared between adjacent isosurfaces and volumes
The reversed flag allows the same part to represent opposite faces
This ensures watertight volumes and exact abutment at shared boundaries
Component reuse
The schema reuses existing components:
base-spatial-data-properties — uuid, name, bounding_box, CRS
embedded-triangulated-mesh — shared geometry with parts
embedded-mesh-object — base for isosurfaces, volumes, boundary surfaces
one-of-attribute — optional attributes per entity
reversible-index — part references with reversal flag
Future extensibility: Category-based domain models
The isosurfacer library also produces category-based domain models (CategoryVolumes) where surfaces represent boundaries between discrete category values rather than numeric thresholds. A separate schema (category-volumes) should be created for this use case, sharing the same mesh infrastructure components (embedded-triangulated-mesh, embedded-mesh-object) but with category-specific metadata:
Category boundary surface: References a category_pair (two adjacent category IDs) instead of a threshold
Category region: References a single category value instead of threshold bounds
This separation follows the library's type design and keeps each schema focused on its semantic domain.
Drawbacks
Overlap with geological-model-meshes: Both schemas share similar structures (embedded mesh with volumes and surfaces). However, the semantic differences are significant — geological-model-meshes captures geological interpretations with features like "Fault" and "Vein", while isosurface-volumes captures threshold-based domain decomposition.
Schema proliferation: Adding another mesh-collection schema increases the number of objects. Mitigation: the schemas serve distinct use cases and share common components.
Alternatives
Extend geological-model-meshes: Add threshold properties and boundary types to the existing schema. Rejected because:
The feature enum would need incompatible values
Geological models have materials; isosurfaces have thresholds
Different organizational structure (folders vs. threshold-sorted arrays)
Use triangle-mesh with custom attributes: Store each surface/volume separately with threshold metadata in attributes. Rejected because:
Loses the conformal mesh benefit of shared parts
No standard way to represent volume relationships
Multiple objects instead of one cohesive domain model
Generic domain-model schema: A single schema for any mesh-based domain decomposition. Deferred consideration — could be a future generalization if patterns emerge across multiple specialized schemas.
Combined threshold/category schema: A single schema supporting both numeric and category-based domain models via a discriminator. Deferred because:
Increases schema complexity
The two models have different required fields and semantics
Adoption strategy
Non-breaking addition: This is a new schema; no existing schemas or consumers are affected.
Compute task integration: The isosurfacer library (core-compute-tasks) will be updated to serialize outputs to this schema for Evo workflows.
Initial lifecycle state: The schema should start as Tech Preview to allow refinement based on real-world usage.
Documentation: Full documentation page following the standard template, with diagrams showing the relationship between isosurfaces, volumes, and boundary surfaces.
Anything extra
Similar schema for reference:
geological-model-meshes (v2.2.0) — shares the embedded mesh pattern but with geological feature semantics

While this is a well presented and reasoned proposal, I disagree with some of the conclusions and design choices.
I agree, the geological-model-meshes schema is too specific to be easily used for your purposes. I think this schema is also too narrow though and it may make sense to look instead to have an extendible schema used for representing these sorts of mesh based volumetric models. Initially it could focus on representing these numeric isosurface volumes but allow it to be extended to deal with the other cases like the categorical isosurface volumes or Leapfrog style combined models.
To do this I would switch to having just surfaces and volumes collections with a possible type field to disambiguate if needed. Arguably the type of volume is implied by the specified thresholds.
I'm not sure it's clear about the link between surfaces and volumes. If a volume includes a surface does that mean it includes that entire surface, or can it only overlap partially (which is often the case with the boundary surfaces).

Here is the updated RFC (with comments originated from @timmclennan applied):
Summary
Add a new geoscience object schema volumetric-model-meshes for mesh-based volumetric models: a collection of surfaces and volumes built from a single shared triangulated mesh decomposed into parts.
The schema is deliberately generic. Its first consumer is numeric isosurfacing (grade shells and the volumes between them), but it is designed so that categorical isosurfacing, and Leapfrog-style combined models, can be represented by the same object without a breaking change — by adding enum values and optional properties only.
Motivation
Mesh-based volumetric models appear throughout geoscience workflows:
Grade shells and grade-tonnage reporting: surfaces at ore grade thresholds (0.5 g/t, 1.0 g/t Au) and the volumes between them.
Geophysical modelling: density or magnetic susceptibility boundaries and the regions they enclose.
Categorical domain models: closed regions per rock type, with the surfaces between adjacent categories.
Combined/interpreted models: a mixture of the above, organised for review and export.
What these have in common is structural, not semantic: a single conformal triangulated mesh, decomposed into parts, where parts are combined (and optionally reversed) to form closed volumes and open surfaces. What differs is only the metadata attached to each surface and volume — a threshold, a category, a boundary face, a geological feature.
There is currently no schema for this shape of data:
triangle-mesh represents a single mesh with parts, but has no concept of named volumes/surfaces composed from those parts, and no place for threshold or category metadata.
geological-model-meshes has the right structure, but its semantics are fixed to geological interpretation (feature enums such as Fault, Vein, StratigraphicContactSurface, plus materials). Isosurfacing output does not map onto those enums.
A generic schema gives us:
One object type to implement, document, and support instead of one per algorithm.
Conformal geometry preserved end-to-end — volumes that exactly abut, because they share parts.
Threshold/category metadata preserved for downstream analysis (grade-tonnage, volumetrics).
A defined extension path: new model kinds are new enum values and new optional properties, i.e. MINOR version bumps.

surfaces and volumes are the only places where surface and volume definitions live. The remaining properties are index groupings: ordered lists of indices into those two arrays. They carry no geometry and no metadata of their own. See Index groupings.
Both surfaces and volumes are required but may be empty, so no cross-property "at least one of" constraint is needed. An object with two empty collections is valid but degenerate; producers are expected to emit at least one of either.
Index groupings
The earlier revision modelled volumes_below / volumes_between / volumes_above / boundary_volume / boundary_surfaces as containers — each holding its own surface or volume definitions. That was rejected in review because it hard-codes one algorithm's output shape into the object's structure.
They return here as references, not containers. Each is an optional array of integers (or, for boundary_volume, a single integer) indexing into surfaces or volumes. This keeps the flat, extensible collections the reviewer asked for while preserving the two things the typed collections were genuinely good at:
Named, ordered access. A grade-tonnage consumer wants "the volumes above each threshold, in threshold order" without re-deriving it from bound presence and re-sorting. The grouping arrays state the producer's intent directly.
Producer intent where bounds are ambiguous. A volume with neither bound could be the model extent or an unbounded generic region. boundary_volume says which, unambiguously and in one place.
Rules:
All groupings are optional. A consumer that ignores them entirely can still reconstruct equivalent groupings from volume_type and the presence of lower_bound/upper_bound (see the bounds table below). Producers should emit them; consumers must not require them.
Indices are 0-based into the corresponding array and must be in range, unique within a grouping, and ordered as documented above.
Groupings must be consistent with the per-item metadata. An index in volumes_between must refer to a volume with both bounds present; an index in boundary_surfaces must refer to a surface with surface_type ModelBoundary. Where they disagree, the per-item metadata wins — it is the normative source.
A surface or volume may appear in no grouping at all (e.g. a NoData patch, or a Generic region), and the isosurfaces / volumes_* groupings need not be exhaustive.
A surface or volume must not appear in more than one of the mutually exclusive volume groupings (volumes_below, volumes_between, volumes_above, boundary_volume).
JSON Schema can enforce the types, uniqueness, and 0-based integer form, but not in-range or cross-property consistency. Those are producer responsibilities, checked by the compute task's own tests rather than by validation.
Because the groupings are pure index lists, adding a new one later (say category_regions) is a MINOR bump and costs existing consumers nothing.

The bounds remain the normative statement of what a volume encloses; the grouping arrays are a derived, ordered index over them. A consumer with no interest in the groupings partitions and sorts on lower_bound/upper_bound directly and gets the same answer.

Categories
An integer on its own says nothing. categories: [1, 2] is only meaningful if the reader knows what 1 and 2 are, so the object carries the mapping.
Each integer in categories is a key into category_lookup — a lookup-table element, the same key→name structure that category-data uses for category attributes elsewhere in the schema library. The keys are the category codes of the source data (the values of the categorical attribute the model was built from), not positional indices into an array and not indices into surfaces/volumes.
```
{
  "category_lookup": {
    "keys_data_type": "int64",
    "values_data_type": "string",
    "length": 2,
    "data": "<blob: (1, \"Granite\"), (2, \"Basalt\")>"
  }
}
```
Rules:
Every integer appearing in any categories array must be present as a key in category_lookup. category_lookup may contain keys that no surface or volume references — a category present in the source data but absent from this model extent.
Keys are carried through unchanged from the source attribute, so that a consumer can join this object back to the block model or grid it came from. Producers must not renumber them.
Order is significant for surfaces, not for volumes. On a CategoryBoundary surface with two entries, categories[0] is the category on the front side of the triangles as wound and categories[1] is the category behind — the same orientation convention the reversed part flag operates on. On a volume, categories is an unordered set.
A CategoryBoundary surface with a single entry separates that category from everything outside the model, or from a region with no category (a NaN or unassigned area). The absent second side is not given a sentinel key.
A volume with multiple entries is a merged region — several source categories treated as one domain. This is common in practice ("all waste rock"), so the property is an array rather than a single integer.
This mirrors how geological-model-meshes handles materials: an object-level collection of definitions, referenced by key from each item, rather than repeating the definition on every item.
The relationship between surfaces and volumes
This was ambiguous in the previous revision and is specified here explicitly.
Parts are the only linkage. There are no index references from a volume to a surface.
triangle_geometry.parts.chunks defines a set of disjoint or overlapping triangle chunks. A part index identifies one chunk.
A surface is a set of part references. A volume is a set of part references whose union forms a closed hull.
A surface and a volume are related exactly when their part index sets intersect. The intersection may be complete or partial.
Concretely:
A volume does not necessarily contain a whole surface. In the example above, the "Top boundary" surface is made of parts 10 and 11, but the "Above 1.0 g/t" volume only uses part 10. The volume is bounded by part of that surface. This is the normal case for model-extent surfaces, which are cut into patches by the isosurfaces crossing them.
An isosurface is typically shared in full by exactly two volumes, with opposite reversed flags — this is what makes the volumes conformal and watertight.
Producers must therefore split parts finely enough that every part is wholly inside or wholly outside every volume. A part must never be partially used; partial use is expressed by having more, smaller parts.
Consumers derive relationships by set intersection on part indices:
```
surfaces_bounding(volume) = { s in surfaces : parts(s) ∩ parts(volume) ≠ ∅ }
volumes_bounded_by(surface) = { v in volumes : parts(surface) ∩ parts(v) ≠ ∅ }
shared_area(surface, volume) = parts(surface) ∩ parts(volume)      // may be a strict subset
```
Denormalised surface_indices on each volume were considered and rejected: they would either duplicate information already derivable from parts, or — worse — imply whole-surface containment, which is exactly the ambiguity raised in review. If profiling later shows the intersection is expensive for large models, a derived index can be added as an optional, explicitly-partial hint in a MINOR version.
Parts semantics (chunk offsets, triangle_indices, and the reversed traversal flag) are unchanged from embedded-triangulated-mesh and reversible-index; see Understanding parts.

Response to feedback
Feedback
Resolution
"This schema is also too narrow… look instead to have an extendible schema for mesh based volumetric models"
Renamed to volumetric-model-meshes and de-specialised. Nothing in the object mentions isosurfacing except enum values; the same object serves categorical and combined models. An explicit extension path is defined
"Switch to having just surfaces and volumes collections with a possible type field"
Done. Five collections collapse to surfaces and volumes, with surface_type / volume_type discriminators. The old collection names survive as optional index groupings — arrays of indices into surfaces/volumes — which retain named, ordered access without duplicating any geometry or metadata
"Arguably the type of volume is implied by the specified thresholds"
Agreed. lower_bound/upper_bound presence encodes below/between/above and is normative; the table above defines the mapping. volume_type remains optional and is not used to distinguish iso-volume sub-kinds. The volumes_* groupings are a convenience index over the same information, not a second source of truth
"Not clear about the link between surfaces and volumes… does a volume include the entire surface, or can it overlap partially"
Specified: linkage is via shared part indices, partial overlap is explicit and expected, parts must never be partially used, and volume→surface index references are dropped to avoid implying whole-surface containment
Drawbacks
Weaker validation. A generic schema cannot enforce, for example, that an IsoVolume's bounds line up with the thresholds of the isosurfaces bounding it, or that volumes tile the model extent without gaps. These become producer responsibilities and documentation, not schema constraints. The previous design did not really enforce them either, but its collection names implied more than they guaranteed.
Consumers must do set intersection to relate surfaces and volumes, rather than following an index. This is cheap relative to loading the mesh itself, and is the price of representing partial overlap honestly.
Optional discriminators mean two ways to say some things. A volume with no bounds and no volume_type is legal but uninformative. The index groupings add a third: volumes_between and "both bounds present" overlap, and nothing in JSON Schema stops them disagreeing. Mitigated by naming the per-item metadata as normative, documenting producer expectations, and validating consistency in producer tests.
Overlap with geological-model-meshes remains. Both describe volumes and surfaces over an embedded mesh. Convergence is possible later — geological-model-meshes could in principle become a profile of this schema — but that would be a breaking change for existing consumers and is out of scope here.
Alternatives
The original isosurface-volumes design (typed collections containing the definitions: isosurfaces, volumes_between, volumes_below, volumes_above, boundary_volume, boundary_surfaces). Rejected following review: it hard-codes one algorithm's output shape, needs a new collection or a new object for every new model kind, and encodes in collection names what is already implied by threshold bounds. The names are retained here as index groupings, which give the same ergonomics without partitioning the data.
Extend geological-model-meshes. Rejected: its feature enums are geological and would need incompatible additions; materials are mandatory to its model and meaningless for isosurfaces; and every change is a breaking change for existing consumers.
One object per surface/volume, using triangle-mesh plus attributes. Rejected: loses part sharing and therefore conformality, provides no standard way to express the relationships between regions, and multiplies object count.
A discriminated union at the object level (one schema, model_type: "numeric" | "category", with different required properties per branch). Rejected: oneOf validation errors are notoriously opaque, and the branches would share almost all their content. Optional per-item metadata achieves the same with less machinery.
Explicit surface_indices on volumes. Rejected as described above — either redundant or misleading. Reconsider as an optional hint if profiling justifies it. Note this is a different question from the index groupings: surface_indices would assert a relationship the parts already define exactly, whereas the groupings assert producer intent that no other property carries in ordered form.
No index groupings at all, requiring consumers to filter and sort volumes themselves. Rejected: it discards the producer's ordering and forces every consumer to reimplement the same partition, and it leaves the model extent indistinguishable from an unbounded generic volume unless volume_type is present.
Adoption strategy
Non-breaking. This is a new object schema. Nothing existing references it, and no consumer is affected.
Tech Preview first. Published with badge="techPreview" so the enums and optional properties can settle against real data before SLAs apply. Promotion to Supported once at least the numeric and categorical producers are shipping.
First producer. The isosurfacing compute tasks in core-compute-tasks serialise the isosurfacer library's domain model to this schema. The library already exposes everything the numeric case needs — surfaces with thresholds, volumes with optional lower/upper thresholds, boundary patches tagged by face, and a boundary hull — so no upstream change is required.
Consumer guidance. Documented rules: treat unknown enum values as Generic; never assume a volume contains a whole surface; sort volumes by bounds rather than relying on array order.
Migration. None. Any prototype data written against the earlier isosurface-volumes draft maps mechanically onto the new layout: concatenate the volume collections into volumes and the surface collections into surfaces, recording each item's original position as an index in the corresponding grouping array.
Open questions
Name. volumetric-model-meshes is used throughout this document. domain-model-meshes and mesh-domain-model (matching the internal MeshDomainModel type) were also considered. Preference from maintainers welcome.
Bound inclusivity. This RFC assumes lower_bound inclusive, upper_bound exclusive, so that adjacent volumes tile the property range without overlap. Worth confirming, and stating in the property descriptions either way.
Should surfaces and volumes be required-but-possibly-empty, or optional? Required-and-empty is proposed for predictable consumer code.
Should the index groupings be required too? Optional is proposed, so that producers of non-isosurface models need not emit empty arrays whose names mean nothing to them. The alternative — required-and-empty — would make consumer code simpler at the cost of noise in every categorical model.
Are all six groupings worth having in 1.0.0? boundary_volume and boundary_surfaces are unambiguously useful. isosurfaces is nearly derivable from surface_type: "Isosurface" and adds mainly the ordering. The volumes_below / volumes_between / volumes_above triple is fully derivable from bound presence; it earns its place only if consumers value the producer-supplied ordering.
folders and materials now or later? They are needed for combined models and add no cost to the numeric case if optional. Including them in 1.0.0 avoids a near-term MINOR bump; deferring keeps the initial surface area small.
Should NoData be a surface_type, or an attribute on parts? As a part attribute it would compose with other surface types; as an enum value it is simpler to consume.
Embed category_lookup, or reference the source attribute? Embedding makes the object self-describing and is proposed here. Referencing the source object and attribute would avoid duplicating the table and keep the two in step, but makes the object unreadable without a second fetch, and breaks if the source is deleted. A provenance reference could be added alongside the embedded table later without conflict.
Anything extra
Related schemas:
geological-model-meshes (v2.2.0) — the structural pattern this schema follows (embedded mesh, parts, volumes and surfaces), with geological rather than volumetric semantics.
triangle-mesh — the right choice when a single surface is all that is needed; the existing single-threshold isosurfacing task will continue to emit this.
