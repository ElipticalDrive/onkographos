Issue body actions
Separate the source direction of directional lights from shadow coverage domains
Problem and classification
The current public shadow declaration exposes only mapSize/bias/normalBias/near/far. The actual shadow-camera anchor and XY bounds of directional lights are left to Three defaults, so a valid caster in an accepted scene can receive light without casting a shadow. This is especially a problem in buildings/interiors and broad blocking, where authors have no way to specify coverage precisely from source alone. This is an existing shadow-domain implementation defect/expressiveness limit, not a regression first introduced in r186.
r186's SunLight added a camera-fitted cascaded shadow path for WebGLRenderer, so a new alternative exists to address this limitation. This issue aims for code-authorable, bounded, deterministic shadow coverage, not unconditional adoption of a named addon. Adopt whichever policy is proven, manual volume or view-fitted cascade.
Actual call path and evidence
IAutoMovieLightBase.transform explicitly says a directional light means orientation only, and IAutoMovieLightShadow does not represent XY/anchor. validateLightPlacement in stageScene rejects directional positions. lowerLightPlacement moves translation to the origin. buildLight/applyShadow/aimLight sets the local -Z target from the source quaternion but configures only the shadow camera's near/far. Three directional shadow XY defaults to [-5,5].
Two independent boundaries fail.
Build the source directly with buildLight and place the light at y10; the XY limit still applies. Floor center (6,-.1,0), size 32x.2x14, with the same two boxes of size 1x2x1 at (0,2,0) and (12,2,0). Source direction (0,-1,0), intensity 3, ambient .12, map1024/bias-.0001/normalBias.02/near.1/far80. Camera (6,20,23)->(6,0,0), fov45, 900x600. Currently a shadow appears only on the x0 box. In the twin where shadow XY alone is changed to [-20,20]x[-10,10], both boxes show shadows.
Using origin, the actual anchor of the staged directional light in the same scene, leaves both boxes in front of the near plane, so neither casts a shadow. Increasing shadow far alone does not solve this near/anchor issue. Telling authors to "raise the directional position" also conflicts with the stage validator.
A 3rd twin used r186 SunLight with a downward direction and the same intensity/mapSize/far, and both boxes showed shadows. drawCalls were current6, manual-fit7, SunLight10. This is a same-GPU coverage comparison of equivalent scenes; it does not claim pixel equivalence between different shadow algorithms or cost superiority. Observed on AMD Radeon8060S/ANGLE D3D11 Chromium, AA off, pixelRatio1, preserveDrawingBuffer/gl.finish. Manual reference marks and box coordinates were the oracle; this was not validation applied to the entire manor.
I checked the official r186 addition and SunLightShadow source. The new SunLight determines direction from position->origin, not target/quaternion, and the current cascade count is 2. Replacing an existing light by class name alone would violate the source-direction contract from the start.
Approach and consequence surface
The physical direction of an infinitely distant source and the spatial domain/observer fitting of a finite shadow approximation are separately owned meanings. Authoring data specifies a volume or bounded fit policy, far, resolution, and bias; the engine determines valid range, cost, and identity; only the viewer creates actual shadow cameras. Adding one arbitrary world-size constant to the default or moving author geometry to suit the lighting is not a solution.
Handle, under the same model: camera pan/direct seek under a fixed source, source rotation, lower floors/basements/high roofs, broad sites, shadows from offscreen casters onto onscreen receivers, cascade boundaries/texel snapping, differences between shadow-camera and view-camera clipping, and scene/shot replacement and disposal. If automatic camera fit is chosen, include fit inputs and bounded shadow distance in view/frame identity and do not inherit previous camera state. Unsupported coverage must produce an explicit diagnostic.
Scope
Layer
Obligation
docs/requirements
Realize caster/receiver identity and coverage in lighting/shadows-reflections-and-transmission.md#lighting-shadow-identity, #lighting-shadow-time-sampling, and rendering/geometry-visibility-and-culling.md#rendering-frustum-boundaries. Do not newly promise photorealistic softness or unlimited range.
docs/specifications
Separate source direction from shadow-domain/fit/culling in camera-light-and-visibility/light-transport-color-and-budget.md#clv-shadow-state-sampling and editorial-render-and-delivery/render-products-visibility-and-color.md#spec-render-visibility-culling.
packages/*
Connect interface shadow policy and engine stage/validation, light resolution, and budget identity; viewer buildLight/applyLightMotion, view update, and lifecycle; and render admission and profile. New exports cite the relevant specification.
sandbox engine surface
Existing source-authored scene/light declarations must let authors choose volume/fit. If a new planner is needed, connect it so it is actually consumed through the production surface/bridge; do not require generic Three objects or MCP writes.
scaffold skills
In source-authoring/cinematography.md, guide authors through choosing and checking shadow coverage for building scale and moving cameras using the canonical API. Do not teach a directional-position workaround that conflicts with the stage.
tests
Use pure tests to verify staged-origin positive/negative coverage, translated/rotated domains, boundary touch, offscreen casters, invalid/zero/unbounded volume, unavailable mode, direct-seek/order parity, generated-source reachability, and target identity.
viewer/capture
Verify the x0/x12/height twin above on real GPU and check that every supported guide pass preserves geometry truth. The shadow/texture budget path must bound new cascade costs/resources first.
Acceptance and verification
Using only source accepted by stageScene, authors must be able to declare the intended shadow domain for a box above the origin and a box 12m away, and observe both shadows. Unrelated source intensity/direction/geometry must not change. Boundary/outside-domain rejection and disabled shadow are deterministic and independent of prior frames/host order. Decide whether to adopt SunLight based on coverage, stable fit, cost, guide/capture parity, and code authorability.
Run the narrow pnpm --filter @automovie/test start --include test_film_stage_scene_environment test_viewer_pbr_environment test_viewer_shadow_participation, the new pure cases, the full build/tests, and scaffold generated-consumer gates. Do not replace verification of actual shadow casting with a test that checks only fitting numbers.
Coordination
Registered dependencies: the new shadow policy consumes the supported shadow matrix from #2499 and the actual pass limit from #2500. #2501 is a separate environment/material residency cost axis, and spatial indirect lighting #2505 is not to be bundled into this implementation.
Closed #1356 handled source aiming, #2039 handled mesh cast/receive flags, and #1853 handled environment/lighting connections; none opened this domain. Cross-checked with searches for shadow frustum, SunLight, and cascaded, both open and closed. Coordinate with shadow-filter compatibility and pass/resource-limit issues, but do not bundle a separate WebGPU migration or GI/area-light shadow promises. This strengthens prototype accuracy so location/contact/space can be read; it is not detailed appearance production.
Work boundary
This issue is an independent implementation handoff from follow-up research on Three.js r169->r186. Research baseline: AutoMovie 1e3ff5d84205f83149cc738426d869d0906dd01f; rechecked HEAD b45f4c709bbfba080d4273639bc28d20c9029f69 also had no differences in the relevant library/runtime source below. Issue registration does not mean implementation is complete and does not request splitting existing Draft PR #2497.
The contract and public evidence are owned by evidence-graph; generated-authoring reachability by scaffold; single semantic ownership of documentation by documentation; and pure tests, change-location coverage, and actual consumers by development. GPU conclusions remain a separate observation under viewer-verification. interface is pure types, engine is pure TypeScript without Three, and viewer is the only library that imports Three.
