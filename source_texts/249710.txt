This PR implements support for hexahedral and quad elements/faces in XDG. While the changes span a lot of files, the important one lie in the mesh managers. One important thing to note is that element containment changes significantly. Where we were using barycentric coordinates for to check tet containment before, this approach now uses Plücker a dot product check against each face to determine if the query location is on the correct side of each element face. This approach assumes that the faces are linear and may need to be updated for additional face types.
Some changes to accessing element connectivity, element vertices, and face vertices have been updated, changing from fixed size arrays to vector types to support variable number of vertex coordinates for faces/elements.
Several tests that are either equivalent to or similar to existing tet/tri models have been added to ensure functionality for these new element/face types.
One current limitation of this implementation is that all elements in a volume/faces on a surface are expected to be the same type. Support for mixed element types in a given volume will be included in later work.
Note: Performance testing is underway for this branch currently.

Update:
I found that the current algorithm used in hex containment wasn't sufficient for robust element walking of hexes. Due to small but significant numerical differences (not just floating point) the points of quad faces aren't exactly planar in many cases. This requires us to both a) check both triangles when considering point containment for hexes/performing ray distance queries on quad faces and b) use a consistent diagonal across the face so that queries aren't dependent on the connectivity ordering of the face depending on the element we're querying that face from (i.e. the winding of the face may be correct in many orderings, but the diagonal used to separate the face into triangles will change). I've introduced a vertex sort based on lexicographical ordering of the vertex coordinates for now though I'd like to change to another method (probably vertex IDs) for a consistent ordering that doesn't require a lot of floating point comparison later on.
I caught this after trying some basic transport with the walk-elements tool and to check problems like this more quickly in the future I've added some tests that walk elements using the same code as that tool.

Somewhat, yes. If the model contains only hexes (only possible in MOAB meshes at the moment), then the connectivity is always consistent and it's just a matter of us returning reversed normal for volumes with the appropriate sense.
In the context of a hex mesh and, for example, firing a ray to determine re-entry into the mesh from the implicit complement we do need to ensure that the quad is treated the same for both the ray fire operation to determine the entry location and the subsequent hex operations for walking elements/determining tally segments.
