Yes, I think your idea with the equalizer was a great hint. Thanks!
After reading through the Android reference, I am probably going this route:
https://developer.android.com/reference/android/media/audiofx/DynamicsProcessing
DB table: station_configs; StationUuid (Primary), volumeGainDb (real), eqEnabled (bool), eqBands (json, text) -> use this table for other things (Notes, Buffer settings per station, UserAgent etc.). When the table exists there will be more ideas...
GUI: Station dialog -> enable EQ for this station -> Equalizer (Exoplayer live update) -> OK -> write to DB
Flow: Via audiosessionID -> on start query station_configs -> Dynamics is bound to the audiosessionID -> AMARadio uses the audiosessionID for the stream
audiosessionID: Check when the ID is available -> Stream start is too late -> prepare would be ideal.
Stop: The good thing is DynamicsProcessing is bound to the audiosessionID. It's only temporary.
Backup via ZIP (Json files -> import!)
Android Auto: Sound is rendered on the smartphone -> it should work. But car volume control can't write to DB. Everything must be configured before Android Auto starts a session. Android Auto forbids an equalizer GUI for safety reasons.
CAST: Doesn't work -> can only send Station name and StationUuid via json. Cast device pulls stream directly.
API 28 -> min Android 9 (min 10 for AMARadio is a probability)
When: Probably not in the November release.

Testers are always welcome, since the google play release takes 10 day minimum at the moment and if I made a mistake I have 10 days of crashes and I can't fix it. I really have fear of releasing an update.
The relative Volume can be set in dynamicsprocessing via a variable (probably AutomaticGainControl) .
To your idea with the front up check: I have not only a problem with different stations, I have also a problem with different songs on the same station. I listen mostly to classical and sometimes an old recording is to low in volume and the next is CD quality with full range and it blast my ears out. The other thing is the compression of the streams (mp3). Everything is cut at the top and bottom of the Bands. If my understanding of dynamicsprocessing is right it can be used to normalize the volume at the top and the bottom. Only thing is clipping and crackling (didn't test it with android but in Audacity I had some troubles to normalize a MP3 file). That's a problem that only a user can fine tune -> this is only my opinion at the moment not a final decision .
I think I will do it both ways one general setting for normalization ("good" stations doesn't need the normalisation they are normalized from the source and work in the parameters, "bad" stations or songs get normalized via the dynamicsprocessing). -> that's only an idea not sure if it works.
And to your idea with front check, why not? I can run a python skript with ffmpeg and log the volume into a database and decide later. With the data, we can fine tune a median or average for standard dynamic tuning. It ads to the AMARadio Toolbox like the station icon download ( I downloaded all station icons per script for a test to see how much space does AMARadio needs, when a crazy person clicked trough all stations (30000 favicons / 322mb )). And I can use my lichess fishnet server for this, that's running 24/7 anyways.
