Summary
This RFC explores an open-world quantization type system that can add new formats without introducing a new ONNX element type or incrementing the IR version for each format.
The current candidate represents one logical quantized value as a composite over one or more typed storage tensors, with an embedded whole-tensor ONNX decoder. Runtime plugins are optional accelerators; the model remains semantically complete without them.
The document is intentionally marked Draft — design discussion. It records the preferred direction, implementation costs, alternatives, and unresolved questions rather than presenting the protobuf sketch as final.
Why composite storage
Existing formats do not share one physical representation:
GPTQ, AWQ, ORT MatMulNBits, MXFP4/NVFP4, AQLM, and SpQR commonly store packed values, scales, zero points, codebooks, or sparse metadata in separate typed tensors.
GGUF/ggml formats and Sherry STQ1_0 use one self-contained packed stream.
A mandatory single payload would require copying/repacking most Hugging Face and ORT checkpoints and can destroy useful sharing such as AQLM codebooks. The candidate design supports both cases: a GGUF/STQ tensor has one UINT8 payload component, while GPTQ/AQLM use multiple components.
Candidate design
QuantizationProto: URI, ordered component interface, static parameter schema, logical element type, and inline whole-tensor FunctionProto decoder.
QuantizedTensorProto: logical name/shape plus component bindings and parameter values.
ModelProto.quantization_storage: model-global storage-only TensorProtos retaining physical dtype, external data, mmap, and sharing.
GraphProto.quantized_initializer: logical quantized initializers in the graph value namespace.
Possible TypeProto.QuantizedTensor arm, currently an explicit open question because of its ecosystem cost.
DequantizeExtensible with output_dtype=UNDEFINED, resolved to the declaration's logical element type; explicit values have Cast semantics.
No encoder, decoder SHA, embedded test vector, closed quantization-family enum, or model-local function registration is required.
Runtime model
A runtime quantized value consists of the declaration, logical shape, effective static parameters, and immutable named component handles. Plugins negotiate support using the URI plus the complete component/parameter interface and may provide dequantization or fused kernels.
The RFC includes detailed checker, external-data, composition, namespace, and decoder ABI requirements.
MoE and Gather
The document examines quantized Gather for MoE. A quantization-preserving Gather is circular without an encoder or format-specific storage transform. The current recommendation is decoded-output semantics:
```
Gather(quantized_tensor(T), indices) -> tensor(T)
```
with semantics Gather(Decode(X), indices). A capable plugin can select and decode only the required experts or fuse Gather with MatMul.
Major open questions
Model-global versus graph-local storage pool.
Separate component/parameter mechanisms versus one formal binding mechanism.
Logical decoder element type and output_dtype default.
Whether TypeProto.QuantizedTensor belongs in the first revision or should follow a smaller variadic DequantizeExtensible design.
Graph inputs/outputs, containers, and control-flow boundaries.
Decoded-output versus quantization-preserving Gather.
Optional single-axis fixed-block profile versus multi-axis metadata.
Mechanically checkable decoder restrictions.
URI governance and merge conflicts.
Full tooling/runtime implementation cost.
Each question includes a recommendation and alternatives in the RFC.
STQ1_0 / Hy-MT1.5
The RFC retains an exact STQ1_0 example:
256 logical weights per 42-byte block
separate 4-bit code and 1-bit sign streams
embedded FP16 scale
inline 32 × 4 ternary codebook
stride-16 placement within each 64-weight chunk
Full RFC
See docs/proposals/0008-ExtensibleQuantizationTypes.md.

Contributor
I am worried that this RFC would add a lot of complexity into the specification with the (explicit) goal of pushing dtype support of crucial kernels out of the specification. I think having standardized data types and an explicit set of operators that (ought to) support them enables users to reason about how their models will perform. It is not only raw operator support that enables portability between runtimes, but also comparable performance. I fear that we'll lose this portability, if the specification gives up on defining what data types are supported natively by these crucial operators.
Furthermore, I think we should always aim at producing graphs that express the most efficient compuation possible. This RFC recommends defining graphs as custom-dtype -> DequantizeExtensible() -> MatMul(). The RFC states that runtimes SHOULD optimize such subgraphs to get competative performance. I realize this is already an existing pattern, but this RFC seems to entranche it further. IMHO, we should aim for a specification that allows us to write performant graphs by default without putting that extra work on downstream runtimes. Runtimes are still free to rewrite these ideal graphs into something else if they like to.
The quantization landscape is evolving faster than ONNX can add new types:
I'd like to challenge that. Yes, weare slow to add things to the specification today, but I don't think this is a law of nature, yet it seems to be the prime motivation for this RFC(?). What can we do to make the process more efficient?
I think we should strongly considere extending the supported data types of the standard and be explicit what operators they support. Independent downstream tools can convert models pretty easily from one quantization to the other. Users can use such tools if they want to run brand new models on old runtimes that may not know of a particular data type yet.
Concerning rapid experimentation with new data types: If users want to experiment with funky data types to squeeze out the best possible performance they can already do so today. The optimal performance requires a custom operator in any case. The custom operator (e.g. MyQuantizedMatMul_MXFP4) can simply consume weights as an uint8 tensor with shape (..., num_blocks, bytes_per_block) and interpret these bytes as it pleases. Users can even put custom meta data into the ValueInfoProto if they like.

Contributor
My initial quick thoughts:
The current proposal, to a large extent, can be realized as a new pair of Quantize/Dequantize ops. The proposal actually has such a Quantize/Dequantize op pair. Much of the other proto extensions can essentially be encoded as attributes of these ops. Including the FunctionProto, when needed.
Attributes in ops are a simpler and more extensible approach than updating the proto definition. The proto extensions may have some efficiency advantages in avoiding duplication of same information across multiple Q/DQ nodes. But we can likely achieve something similar using a model-local function to consolidate the multiple occurrences ofQ/DQ nodes with same attributes. In any case, not sure it is worth introducing new proto structures to, essentially, freeze attributes of a specific op. Op+attribute allows the proposals to evolve even more over time (without updating the IR).
The serialized form of the quantized tensor can be represented as a tensor of uint8 usually.
The globally unique URI can be an attribute, though it does require some official recognition/support to ensure uniqueness. I am not entirely sure if we need it. (We could resort to model-local functions again, to represent the Q/DQ ops, with domains being owned by the domain-owner.)

QuantizationProto
```
// Describes how a tensor is quantized. Eight variants cover the
// common families: linear affine/symmetric, scalar codebook lookup,
// vector codebook (additive VQ), micro-float (exponent+mantissa),
// sparse (outlier separation), logarithmic, custom function, and
// recursive block-wise quantization.
// BlockQuantizationProto can nest QuantizationProto to express
// multi-level hierarchies (e.g. K-Quants, MXFP).
// Optional pre/post rotations support QuIP#, SmoothQuant, etc.
message QuantizationProto {
    oneof kind {
        LinearUniformProto linear = 1;
        CodebookUniformProto codebook = 2;
        VectorCodebookUniformProto vector_codebook = 3;
        FloatingPointUniformProto floating_point = 4;
        SparseQuantizationProto sparse = 5;
        LogUniformProto log = 6;
        FunctionUniformProto function = 7;
        BlockQuantizationProto block = 8;
        TilingQuantizationProto tiling = 13;
        IdentityProto identity = 14;
    }
    string doc_string = 9;             // human-readable description
    repeated StringStringEntryProto metadata_props = 10;  // arbitrary key-value metadata
    optional RotationProto pre_rotation = 11;   // rotation applied before quantization
    optional RotationProto post_rotation = 12;  // rotation applied after dequantization
}
```
LinearUniformProto
Classic affine/symmetric: value = (q - zero_point) * scale.
```
message LinearUniformProto {
    int32 data_type = 1;          // quantized element type (same enum as TensorProto.data_type)
    int32 bits = 2;               // number of bits (e.g. 4, 8)
    bool symmetric = 3;           // true if zero_point is always 0
    oneof scale {
        float scale_float = 4;    // scale as float
        int32 scale_int = 5;      // scale as shared exponent (value = q * 2^scale_int)
    }
    int64 zero_point = 6;         // quantization zero point
    int32 axis = 7;               // axis for per-channel, -1 if per-tensor
}
```
CodebookUniformProto
Lookup-table based: value = codebook[index] * scale.
```
message CodebookUniformProto {
    oneof scale {
        float scale_float = 1;    // scale as float
        int32 scale_int = 2;      // scale as shared exponent
    }
    repeated float codebook = 3;  // lookup table values, len(codebook) = base
    int32 packed_count = 4;       // number of values packed
    int32 packed_bytes = 5;       // into this many bytes
}
```
VectorCodebookUniformProto
Additive vector codebook quantization (AQLM, residual VQ).
Each block of vector_size values is reconstructed as the sum
of lookups from num_codebooks codebooks.
values[0:vector_size] = sum(codebooks[k][index_k] for k in range(num_codebooks))
```
message VectorCodebookUniformProto {
    int32 num_codebooks = 1;      // number of additive codebooks (e.g. 2)
    int32 codebook_size = 2;      // entries per codebook (e.g. 256 for 8-bit index)
    int32 vector_size = 3;        // floats per codebook entry (e.g. 8)
    int32 index_bits = 4;         // bits per index (e.g. 8)
    repeated float codebook_data = 5;  // all codebooks concatenated:
                                       // num_codebooks * codebook_size * vector_size floats
}
```
FloatingPointUniformProto
Micro-float quantization: value = (-1)^sign * 2^(exp - bias) * (1 + mantissa).
Covers FP6, FP4, MXFP and similar reduced-precision floating-point formats.
```
message FloatingPointUniformProto {
    int32 sign_bits = 1;          // sign bits (usually 1)
    int32 exponent_bits = 2;      // exponent bits (e.g. 3 for E3M2, 2 for E2M1)
    int32 mantissa_bits = 3;      // mantissa bits (e.g. 2 for E3M2, 1 for E2M1)
    int32 exponent_bias = 4;      // exponent bias (e.g. 3 for E3M2)
    bool has_inf = 5;             // true if format supports infinity
    bool has_nan = 6;             // true if format supports NaN
    bool split_storage = 7;       // true if sign+exp and mantissa stored separately (TC-FPn)
    int32 packed_count = 8;       // number of values packed
    int32 packed_bytes = 9;       // into this many bytes
}
```
SparseQuantizationProto
Sparse + dense decomposition (SpQR, SqueezeLLM). Outlier values above
a threshold are stored separately in higher precision; the rest uses
a base quantization scheme.
```
message SparseQuantizationProto {
    QuantizationProto base_quant = 1;  // quantization for non-outlier values
    int32 outlier_data_type = 2;       // data type for outlier values (e.g. FLOAT16)
    float outlier_threshold = 3;       // absolute value threshold for outlier detection
    float outlier_ratio = 4;           // fraction of values stored as outliers (e.g. 0.01)
}
```
LogUniformProto
Logarithmic quantization: value = sign * base^(q + offset).
```
message LogUniformProto {
    int32 bits = 1;               // number of bits (e.g. 4, 8)
    float base = 2;              // logarithm base (e.g. 2.0)
    float offset = 3;            // exponent offset
    bool has_sign = 4;           // true if sign bit is stored separately
}
```
FunctionUniformProto
Custom quantization/dequantization defined by op names.
data_type and bits describe the storage format of the quantized
data so the runtime can read the raw bytes correctly. The custom ops
referenced by quantize_op and dequantize_op handle the actual
conversion logic. The dequantize op takes a tensor of data_type
and returns FLOAT32; the quantize op does the reverse.
```
message FunctionUniformProto {
    int32 data_type = 1;          // storage element type (how raw bytes are interpreted)
    int32 bits = 2;               // bits per element (for sub-byte packing)
    string quantize_op = 3;       // op: float32 -> data_type (e.g. "custom::Quantize")
    string dequantize_op = 4;     // op: data_type -> float32 (e.g. "custom::Dequantize")
}
```
BlockQuantizationProto
Recursive block quantization. Each block has a size and a nested
QuantizationProto describing how elements within the block are
quantized. Nesting allows multi-level hierarchies (K-Quants, MXFP).
If there are more blocks than entries in elem_quant, the list
is cycled from the beginning (elem_quant[i % len(elem_quant)]).
```
message BlockQuantizationProto {
    int32 block_size = 1;                          // elements per block at this level
    repeated QuantizationProto elem_quant = 2;     // one per block
}
```
TilingQuantizationProto
Multi-dimensional block quantization. Extends BlockQuantizationProto
to N dimensions: weights are partitioned into tiles of shape
tile_shape along the given axes, and each tile is quantized
independently. Useful for prepack layouts (MatMulNBits) where
quantization parameters vary along more than one axis.
```
message TilingQuantizationProto {
    repeated int64 tile_shape = 1;                 // block size per axis (0 = full tensor dim)
    repeated int32 axes = 2;                       // axes being tiled (e.g. [0, 1])
    QuantizationProto elem_quant = 3;              // quantization scheme (same for all tiles)
    repeated int32 perm = 4;                       // permutation of axes in memory layout
}
```

QuantizedTensorProto
A quantized tensor cannot rely on shape × sizeof(data_type) to compute
its storage size (sub-byte packing, block metadata, sparse outliers, etc.).
It carries its own byte size explicitly.
```
message QuantizedTensorProto {
    repeated int64 dims = 1;       // logical shape of the tensor
    bytes raw_data = 2;            // quantized payload
    int64 n_bytes = 3;            // byte size of raw_data
    int32 quantized_type = 4;      // index into ModelProto.quantizations
}
```
Pseudo-code
Dequantization
```
def dequantize(qtensor: QuantizedTensorProto, model: ModelProto) -> float[]:
    quant = model.quantizations[qtensor.quantized_type]
    data = qtensor.raw_data
    n_elements = product(qtensor.dims)

    match quant.kind:

        case LinearUniformProto as q:
            values = unpack(data, q.bits)
            if q.scale_float:
                result = (values - q.zero_point) * q.scale_float
            else:
                result = (values - q.zero_point) * (2 ** q.scale_int)

        case CodebookUniformProto as q:
            indices = unpack_base(data, len(q.codebook), q.packed_count, q.packed_bytes)
            result = [q.codebook[i] * q.scale for i in indices]

        case VectorCodebookUniformProto as q:
            result = zeros(n_elements)
            for k in range(q.num_codebooks):
                indices = unpack(data[k], q.index_bits)
                codebook_k = q.codebook_data[k * q.codebook_size * q.vector_size:]
                for i, idx in enumerate(indices):
                    result[i*q.vector_size:(i+1)*q.vector_size] += codebook_k[idx]

        case FloatingPointUniformProto as q:
            bits_per_elem = q.sign_bits + q.exponent_bits + q.mantissa_bits
            raw_values = unpack(data, bits_per_elem, q.split_storage)
            result = [fp_decode(v, q.sign_bits, q.exponent_bits,
                                q.mantissa_bits, q.exponent_bias)
                      for v in raw_values]

        case SparseQuantizationProto as q:
            result = dequantize_with(data.dense_part, q.base_quant)
            for (index, value) in data.outliers:
                result[index] = value

        case LogUniformProto as q:
            raw = unpack(data, q.bits)
            if q.has_sign:
                sign = extract_sign(raw)
                magnitude = raw & ((1 << (q.bits - 1)) - 1)
            else:
                sign = 1
                magnitude = raw
            result = sign * (q.base ** (magnitude + q.offset))

        case FunctionUniformProto as q:
            tensor = unpack(data, q.bits, q.data_type)
            result = call_op(q.dequantize_op, tensor)

        case BlockQuantizationProto as q:
            result = []
            blocks = split(data, num_blocks=len(q.elem_quant))
            for i, block_data in enumerate(blocks):
                block_values = dequantize_with(block_data, q.elem_quant[i])
                result.extend(block_values)

    # Apply post-rotation if present
    if quant.post_rotation:
        result = apply_rotation(result, quant.post_rotation)

    assert len(result) == n_elements
    return result
```
Quantization
```
def quantize(tensor: float[], quant: QuantizationProto) -> QuantizedTensorProto:
    # Apply pre-rotation if present
    if quant.pre_rotation:
        tensor = apply_rotation(tensor, quant.pre_rotation)

    match quant.kind:

        case LinearUniformProto as q:
            if q.scale_float:
                values = round(tensor / q.scale_float) + q.zero_point
            else:
                values = round(tensor / (2 ** q.scale_int)) + q.zero_point
            values = clip(values, 0, (1 << q.bits) - 1)
            raw_data = pack(values, q.bits)

        case CodebookUniformProto as q:
            scaled = tensor / q.scale
            indices = [nearest(scaled[i], q.codebook) for i in range(len(tensor))]
            raw_data = pack_base(indices, len(q.codebook), q.packed_count, q.packed_bytes)

        case BlockQuantizationProto as q:
            blocks = split(tensor, q.block_size)
            raw_data = b""
            for i, block in enumerate(blocks):
                raw_data += quantize(block, q.elem_quant[i]).raw_data

        # ... other variants follow same pattern

    return QuantizedTensorProto(
        dims=shape(tensor), raw_data=raw_data,
        n_bytes=len(raw_data), quantized_type=<index>)
```

@xadupre Thanks for putting together the alternative proposal. I checked it against Hy-MT1.5-1.8B-1.25bit / Sherry STQ1_0.
I think QuantizedTensorProto is the right direction for separating the logical tensor shape from its packed storage size. However, the current QuantizationProto variants do not appear sufficient to describe STQ1_0 losslessly and portably.
Its physical block layout is:
```
logical values:   256
bytes per block:  42
qs:               offset 0,  64 x 4-bit codebook indices = 32 bytes
sign:             offset 32, 64 x 1-bit table selectors  = 8 bytes
scale:            offset 40, 1 x FLOAT16                 = 2 bytes
```
Each combined 5-bit index selects one of 32 four-element ternary vectors. The four decoded lanes are not four consecutive weights: groups use a stride-16 layout within each 64-weight chunk, for example (w0, w16, w32, w48). The decoded vector is then multiplied by the FP16 scale embedded in that 256-weight block. This is 1.25 bits/weight for the ternary codes and 1.3125 bits/weight including the block scale.
VectorCodebookUniformProto can describe a 32-entry codebook of four-element vectors conceptually, but its additive-VQ semantics and single packed index stream do not describe the split qs/sign streams. BlockQuantizationProto also does not currently specify field offsets, bit packing, or the stride-16 scatter rule. Finally, the scale cannot be a declaration-level constant because every 256-weight block stores its own scale in the payload.
A portable representation would therefore need something like structured block fields plus an explicit element-layout mapping:
```
block_size: 256
bytes_per_block: 42
fields:
  qs:    offset=0,  count=64, bits=4
  sign:  offset=32, count=64, bits=1
  scale: offset=40, count=1, data_type=FLOAT16
codebook: float[32][4]
layout: stride-16 groups within each 64-element chunk
```
The custom-function escape hatch could identify STQ1_0, but without these storage/layout semantics it would require a custom operator and would not provide a portable fallback decoder. PR #8214's inline dequantization approach has a similar issue with its current (packed, scale) signature because the STQ scale is embedded in the packed block.
With block-field and layout support, I believe Hy-MT1.5-1.8B-1.25bit can be represented exactly in ONNX. Efficient inference would separately require runtimes to recognize the declaration and provide/fuse an STQ1_0 MatMul kernel; the model-format change alone would not reproduce the mobile performance from ggml-org/llama.cpp#22836.

My current view is that the PR's proposal is the better architectural foundation, while @xadupre's proposal contributes an important improvement to the storage model.
The PR's URI-based, model-local declarations and portable fallback decoder provide the key extensibility property: ONNX should need one IR-version bump to introduce the framework, but adding a new quantization format should only require adding a new descriptor/URI and should not require another IR-version bump.
QuantizedTensorProto improves the design by cleanly separating logical tensor shape from arbitrary packed storage. That is useful for sub-byte packing, embedded block metadata, sparse data, and formats where shape * sizeof(data_type) is not meaningful.
However, the closed oneof taxonomy in the comment (Linear, Codebook, VectorCodebook, Block, etc.) is less future-proof. A future format outside those categories would require extending the protobuf/IR again, and STQ1_0 already exposes gaps around multiple packed fields, field offsets, embedded per-block scales, and non-contiguous element mappings.
I suggest combining the strongest parts of both approaches:
Keep the PR's URI/version-based format declarations and model-local portable decoding semantics.
Add an explicit quantized-tensor storage envelope with logical shape, opaque payload/external data, byte length, and descriptor reference.
Replace or underpin the closed format variants with generic named block fields: offset, count, scalar type, bit width, bit/byte order, and alignment.
Add a restricted declarative element-layout mapping for reshape, tile, permutation, constant gather/scatter, bit extraction, codebook lookup, and scaling.
Require unknown descriptors to round-trip unchanged; the checker should validate structural safety without needing to recognize every URI.
Version formats independently through their URI/version. Semantic format changes create a new descriptor version, not a new ONNX IR version.
In short: use the PR as the extensibility architecture, incorporate QuantizedTensorProto's explicit storage concept, and avoid making the list of quantization families the extension boundary.

Here is my suggestion:
Design goal: quantized tensor interchange and runtime layouts
Goal
Define quantized tensors in ONNX so their semantics and interchange
representation are portable, without requiring all runtimes to share one
backend-specific execution layout. A backend may transform the portable
representation into a layout optimized for its hardware and kernels, including
during ahead-of-time optimization.
Prefer a compositional representation: separate compact component tensors
plus a reconstruction graph built from reusable primitives, rather than a new
serialized tensor type or operator for every named quantization format.
Keeping the serialized payload comparable in size to the original format is
a primary requirement; runtime performance can be obtained through fusion
and backend-specific repacking.
Separate three concerns
Semantic quantization format describes what the tensor means and how
values are reconstructed. For Q2_K, this includes the code bit width,
hierarchy of subblocks and superblocks, quantized local scales/minima,
and superblock scale/minimum. These rules define the quantized values,
independently of the kernel that consumes them.
Interchange encoding describes the portable serialized representation:
component roles and types, shapes, and packing rules. It should have a
canonical, backend-neutral form where practical, so independent
implementations can read and exchange models reliably.
Runtime layout describes backend-specific physical arrangements such
as tiling, swizzling, padding, and interleaving for a particular kernel,
device, or execution provider. These are implementation details and may
be produced by a lossless transformation from the interchange
representation.
Standard ONNX boundary
Standard ONNX should first provide the primitives needed to describe compact
component storage and portable reconstruction. Family-specific Q/DQ functions
can compose these primitives where useful, without requiring a new IR type for
every format. These are proposed capabilities, not a claim that all necessary
operators already exist.
Interleaving weight codes, scale codes, minima, and other components into one
byte stream should not define the core semantic family. Treat such layouts
initially as backend- or operator-specific encodings. They may have portable
decoders, but ONNX need not standardize each layout as a distinct tensor type.
Compact component tensors and Pack/Unpack
Store each logical component independently, using an ordinary typed tensor
where its dtype is suitable. Use a UINT8 tensor as a compact byte sequence for
codes whose bit width is not directly supported, such as 3- or 5-bit values.
Pack low-bit scale or minimum codes in the same way; do not expand them to
floating point in the serialized model.
A proposed Unpack primitive converts a byte sequence into one UINT8 element
per code. For N unsigned m-bit codes, the packed payload needs
ceil(N * m / 8) bytes, whereas the unpacked result needs N bytes.
Expansion is an execution-time operation, not a requirement to serialize
expanded codes. A corresponding Pack primitive would allow quantization
graphs to produce the compact representation.
The primitive contract must specify:
Code bit width, bit order, and how codes cross byte boundaries.
Logical element count, since trailing padding alone cannot identify it;
the graph can reshape the result to the intended logical shape.
Padding rules and validation of input length and code range.
Prefer one canonical contiguous packing rule instead of arbitrary kernel
layouts in Unpack. Packing operates on unsigned code bit patterns; signed,
offset-binary, or other interpretations belong to the reconstruction graph.
Pack should reject out-of-range codes rather than silently discard bits.
Separate components preserve essentially the same raw payload size when all
low-bit data remains packed. Each component can add a final partial byte, and
tensor metadata and external-data alignment add overhead, so compare total
serialized sizes rather than assuming exact equality. Avoid a separate
initializer for every block: use tensors containing the codes or parameters
for all blocks.
Reconstruction through existing operations
After unpacking, use ordinary arithmetic, indexing, reshaping, broadcasting,
and casts to reconstruct the tensor:
Decode local scales and minima from their packed codes and higher-precision
superblock parameters.
Apply the resulting parameters to the weight codes at the appropriate
subblock granularity.
Use lookup operations for scalar or vector codebooks, where needed.
Use 8-, 16-, or 32-bit intermediates as appropriate, subject to existing
operator support. Widen before arithmetic that could overflow. Define
intermediate precision and rounding explicitly: an algebraically equivalent
graph is not necessarily numerically identical to a reference decoder.
Reuse blocked DequantizeLinear where its formula and types match; additive
minima or other rules may require ordinary arithmetic instead.
For example, a conceptual Q2_K representation can contain separate packed
2-bit weight codes, packed 4-bit local scale codes, packed 4-bit local minimum
codes, and FP16 superblock scale and minimum tensors. Unpack and arithmetic
reconstruct the local parameters, then reconstruct the weights. The
256-value superblocks and 16-value subblocks are expressed through shapes and
indexing rather than an interleaved record layout.
This can cover many Q/DQ schemes, including hierarchical K-quants, without
making every physical layout a standard format. It does not imply that all
quantizers reduce to bit unpacking: base-3 encodings, sparse outliers,
permutations, and vector codebooks need their own reconstruction logic.
Defining an encoder additionally requires rounding, clipping, and any
calibration policy; Pack alone is not a quantization algorithm.
Optional interleaving and splitting
If preserving an existing interleaved byte stream is necessary, consider
generic interleave/deinterleave primitives as a later layer. They would combine
several component byte sequences into a record stream or recover the
components from one. Reuse existing reshape, transpose, slice, split, gather,
and concatenation operations where they already express the mapping; add
primitives only for gaps or a substantially clearer reusable contract.
Such a contract must specify record boundaries, field sizes and offsets,
ordering, padding, and element mappings. Byte fields containing FP16 or other
typed values also need an explicit byte order and byte-to-typed-value
reinterpretation contract: a numeric Cast from UINT8 is not a bitcast.
Variable-length or sparse records should not be assumed to fit a fixed-record
primitive.
This layer should remain orthogonal to quantization semantics. Two byte
arrangements that reconstruct the same quantized tensor are still different
encodings and require explicit decoding information. An opaque backend
encoding without portable decoding semantics is not a portable interchange
representation.
Backend transformation and cache
A runtime may losslessly repack the canonical interchange data into its
preferred layout during model loading or ahead-of-time optimization. The
portable component representation and reconstruction graph remain the source
of truth and fallback.
The graph supplies reference semantics; it does not require an optimized
runtime to materialize every unpacked component or a full floating-point
weight tensor. A backend can recognize and fuse unpacking, parameter
reconstruction, and a consuming operation, or lower the graph to a
backend-specific packed kernel. Such transformations must preserve the
specified numerical semantics.
Optionally cached optimized data should be disposable and associated with
the backend, device, and runtime configuration that created it; it must not
be required to interpret the ONNX model.
Intended outcome
ONNX guarantees what quantized tensors mean and how they can be exchanged.
Backends remain free to choose their own storage transformations and
execution strategies without changing the model's semantics. Standardization
focuses first on compact primitive building blocks and compositional decoding,
with interleaved encodings treated as an optional, separate concern.

A TLDR summary is:
We just need one standard interchange format for a k-bit tensor (for k < 8). We formalize it via a pair of Pack and Unpack operators.
We express the quantize/dequantize ops for any format via a graph of more primitive ops (including Unpack, Add for zeropoint adjustment, Mul for scaling, along with appropriate indexing/broadcasting to represent "blocking").
Backends can do fusion, as done before for QDQ patterns, to replace subgraphs by a custom quantized-MOE or quantized-matmul op.
Backends can transform standard interchange format to custom runtime format for more efficient access by a custom op (as already done for packing).
