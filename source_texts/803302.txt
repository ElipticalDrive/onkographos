Aside from writing your own random number generator, the current way of generating random numbers in Regent is to use C functions like drand48_r. This approach has a few drawbacks, the major are:
those functions are not thread-safe
they can't be used in the openMP and CUDA tasks variants
they do not work on all the platforms (for instance drand48_r does not exist on macOS)
I think that it would be useful to have a Random number generator in Regent that should be:
thread-safe
compatible with __demand(__openmp)
compatible with __demand(__cuda)
available on all the platforms where Regent gets installed
Please let me know if I am not considering some existing solutions to generate random numbers in Regent

The challenge with parallel/distributed/portable PRNGs is that a PRNG stream has state, and that state needs to live somewhere, and it needs to be modified on ~each call to get a pseudo-random value. The modification implies some sort of ordering requirement, which you can weaken if you don't mind non-determinism, but you can't eliminate.
My favorite PRNG for these use cases is the Philox generator from the D E Shaw folks (https://www.deshawresearch.com/resources_random123.html) for which we have a Regent implementation here:
https://github.com/StanfordLegion/legion/blob/stable/language/examples/philox.rg
This generator is basically a hash function that takes 96 bits that contain a stream seed and a sequence number within the "stream" (since you can pick arbitrary sequence numbers, it's not ordered like most streams) and jumbles them up to get a pseudo-random value. The seed does not change (so no race conditions on updates), and the sequence number can be managed in more parallel-friendly ways (e.g. stepping the "current sequence number" by the number of iterations in the parallel loop you're kicking off, and then having each iteration of the loop independently compute the random number for its offset within the chunk of sequence IDs that were claimed). Making sure to give indpendent sequence IDs to different threads is sufficient to get independent random numbers, BUT you can also generate the same values in different places if that's what you need.
If you wanted, you could wrap the Philox generator in a stateful object that has a more traditional srand/drand interface (by just keeping an internal sequence id counter and doing (possibly atomic) increments on drand calls), but that would re-introduce all the state management and thread-safety/determinism concerns.

I realize you're not talking about this case, but another one to care about it supplying random number generators for use in control-replicated tasks. It would be good to have some runtime support to guarantee that all shards of a control-replicated task are getting the same random numbers (e.g. for running a genetic algorithm from the top-level task). Ideally we would want that not to disable Regent's static analysis that recognizes when task variants are replicable or not.

The only difficulty I see from a user perspective is giving independent sequence IDs to the threads.
For deterministic behavior (i.e. getting the same results if you use the same seeds), I think it's probably better to think about it in terms of distributing independent sequence IDs to loop iterations or tasks based on their index. Then the actual order and any concurrency of execution has no impact on the values produced by the PRNG.
It would be good to have some runtime support to guarantee that all shards of a control-replicated task are getting the same random numbers
Since you have control over both the seed and the sequence ID in these counter-based random number generators, you can get this behavior by making sure all shards use the same seed and compute sequence IDs in the same way.
