ℹ️ The earlier Copilot pass-usage-conflict findings do not hold
Copilot flagged the single-compute-pass design in both the executor and the global-illumination example as WebGPU validation errors ("sampled and storage-write usages in one pass usage scope"). That premise is incorrect: the WebGPU spec defines a compute pass as having one usage scope per dispatch, not one per pass, so a texture written by one dispatch and sampled by a later dispatch in the same beginComputePass() is conformant. I checked the code and no single dispatch binds a storage-write and a sampled view of the same subresource. The concerns can stay resolved.
Technical details
```
# Cross-dispatch write→sample in one compute pass is legal

## Evidence
- W3C WebGPU spec, "Resource Usages": usage scopes are per-dispatch — "In a compute pass, each dispatch command ... is one usage scope", while "one render pass is one usage scope".
- gpuweb#547 resolution: "compute passes are different in that the scopes are dispatch-sized".
- Dawn tracks compute usage per dispatch (`SyncScopeUsageTracker` built per `dispatchWorkgroups`) and validates only within each scope.
- wgpu-core `flush_bindings`: "compute passes have a separate usage scope for each dispatch" and drains barriers between dispatches.

## Affected sites
- `packages/typegpu-radiance-cascades/src/holographic/index.ts` — `sectors` written by the down level-0 dispatches, sampled by the later `integrate` dispatch.
- `apps/typegpu-docs/src/examples/rendering/global-illumination/index.ts` — `rasterize`/`bounce` write `emission`/`medium`, sampled by `hrcMedium` in subsequent dispatches.

## Required outcome
- None. The only rule that would bite is aliasing a storage-write and sampled view of the same subresource *within one dispatch*, which the code never does.
```
