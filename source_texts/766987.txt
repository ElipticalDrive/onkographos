Goal
Replace the visually flat, perfect-sphere ground on solid celestial bodies with believable local, deterministic, configurable terrain: hills, mountains, steep slopes, craters/depressions and uneven ground. Generate and render only nearby terrain at appropriate LOD. Architect it so a future server can define planets/celestial bodies with a small versioned definition, not huge per-vertex meshes. This iteration remains client-only and offline.
Codebase findings (current main)
client/renderer/src/spheres.rs and spheres.wgsl present bodies as analytic textured spheres with detail tiling; sphere instances expose only center, radius and material.
client/world/src/geometry.rs uses nominal spherical radius for surface distance and landing volumes.
client/character/src/controller/surface.rs projects the player eye to body.radius + eye_height, thus navigation/collision currently assumes a perfect sphere.
client/ship/src/controller/assist.rs computes radial landing endpoints from nominal sphere radius, which must eventually sample the actual landing footprint.
client/world/src/resource_generation.rs already has bounded deterministic cube-sphere cell sampling and versioned seeds for deposits. Reuse conventions where appropriate, but avoid coupling terrain detail to resource spacing.
client/world/solar-system-layout.md documents compressed spherical body catalog and client/renderer does not own celestial identities or gameplay authority.
Proposed architecture
Define a portable, renderer-neutral, versioned terrain definition per solid body: generator/version, seed, baseline radius/reference frame, feature/biome layers (amplitude, wavelength/frequency, roughness, ridge/crater/erosion controls, masks), max/min elevation, slope limits or profile, optional authored features and sparse overrides. Values in meters; stable body identity and explicit procedural-version compatibility. Provide a config format suitable for future network serialization, validation and size budgeting.
Implement a deterministic body-local surface query (e.g. surface_height(body_id, unit_direction), plus normals/material and coarse min/max elevation bounds). Pure evaluation of seed + config + body-local coordinates; identical irrespective of player position, camera, time, thread scheduling, chunk load order or client machine. Define seam and version policies; no RNG per frame or view-relative random generation.
Render terrain in streamed cube-sphere patches / clipmap / quadtree with LOD around players, with bounded CPU/GPU allocation and stable patch IDs. Evaluate suitable alternatives before choosing. Maintain a distant analytic sphere / low-detail surface while transitioning to near terrain without cracks, popping, visible seams or unstable depth. Reuse f64 world precision and camera-relative f32 GPU transforms, avoid reallocating/regenerating everything each frame. Keep planet-scale data unallocated.
Use the same authoritative height samples for character ground contact, gravity-aligned surface walking, jumping/step/slope policy as applicable, surface collision, and ship landings. Landing feet should meet sampled terrain (accounting for footprint/slope) instead of intersecting hilltops or floating. Coordinate with landing legs Raise landed scout hull 2 m above terrain and add deployable landing legs #168 and ramp Convert aft exit door into a bottom-hinged walkable boarding ramp #169; record integration dependencies as needed, without breaking existing landed scenarios.
Update surface resource placement/streaming to project deposits and spawned fragments onto the actual terrain and honor slopes and surface normals. Maintain stable IDs, in-session mining state, sparse changes, and accurate collision support when patches stream out/in.
Preserve existing compressed-body orbits/catalog/visual-only Sun behavior; terrain is for solid bodies. Avoid terrain altering orbital layout or inadvertently overlapping landing volumes; document conservative extrema and query bounds.
Provide representative different profiles on at least Earth, Moon and Mars; include gentle plains, rolling hills, sharp mountains/ridges, crater depressions and steep areas. Ensure variation is planet-fixed, not random locally per player. Explicitly distinguish height-field craters/pits from true caves, tunnels, overhangs and through-holes (volumetric geometry explicitly deferred until after Phase 0).
A future server should send a tiny config + seed + generation-version + optional sparse authored feature/override patches or content hashes; clients reconstruct terrain deterministically. Do not implement networking/server/persistence now, and do not tie definitions to renderer-only structs. Document compatibility, migration, validation, bounds, reproducibility tests, cache keys and a reasonable compact serialized example.
Add tests and native scenarios: sample consistency across sessions/chunk loading order; seams/poles/patch borders/LOD transitions; floating-point precision far from world origin; ground collision & traversable slopes; crater depressions; mining deposit anchoring; touchdown and ramp with uneven surface; terrain streaming memory/CPU/GPU budgets and screenshots.
Update docs/maintenance-map.md, world/character/renderer contracts and tests; add reports/issue-<number>/README.md at completion per AGENTS.md.
Acceptance criteria
At ground level users see meaningful 3D elevation variation and can physically traverse hills/slopes/depressions; ground is no longer just a smooth sphere with a textured surface.
Seed/config/coordinates produce stable, reproducible geometry across visits and reloads; no reshuffling terrain when the player moves.
Only nearby high-detail patches occupy significant memory/GPU resources; terrain loading/unloading is bounded and distance-dependent. Stable far-to-near representation without visible gaps at seams or LOD edges.
Surface height/rendering, collisions, resources and landing ground contact agree within specified geometric tolerances.
The data model represents body-specific terrain compactly, supports validation/versioning and optional sparse authored exceptions, and remains serializable for future server authority without adding a server now.
Model/regression/native tests and a documented performance comparison pass on the reference hardware. Record triangle counts, active patches, memory usage and frame-time cost; do not claim a fixed FPS floor without measurement.
Design and sequencing notes
Make an explicit decision whether to first ship a narrow height-query/terrain-config contract and then rendering+physics, or split implementation into child issues; avoid one mega-PR if complexity requires staged work.
Account for Raise landed scout hull 2 m above terrain and add deployable landing legs #168 landing legs and Convert aft exit door into a bottom-hinged walkable boarding ramp #169 boarding ramp when integrating uneven landing sites; landing may need slope-aware site selection. Avoid quietly invalidating their fixed 2m hull-clearance intent.
Heightfield depressions/craters are in scope; actual caves, tunnels, overhangs and arbitrary holes through rock are out of scope for Phase 0. Document these as possible post-Phase-0 features requiring volumetric geometry and a separate design/implementation phase; no Phase 0 placeholder mechanics or support are required.
Avoid full-planet meshes or per-vertex server payloads. Prefer compact declarative parameters and sparse edits, with explicit evaluation-version compatibility.
