Severity: P2 (intermittent engine crash reachable from GDScript) | Confidence: MEDIUM — reproduced twice in five runs; not root-caused
Found while gathering runtime evidence for #833. Not caused by that change: the call is on origin/master's starter-template overlay too.
The claim
Calling GaussianSplatNode3D.get_statistics() from GDScript every frame intermittently crashes the engine with a CrashHandlerException, inside the call.
Measurement
Optimized editor 4.5.rc.custom_build.5cec9d8b6 (target=editor, from 5cec9d8b60c; gaussian_splat_node_3d.cpp and render_diagnostics_orchestrator.cpp at that commit are byte-identical to origin/master). Windowed 1280×720, the shipped starter template with its default project settings — notably rendering/driver/threads/thread_model=2 (multi-threaded) — one GaussianSplatNode3D with 768 splats, route INSTANCE.RASTER.COMPUTE, data source ResidentInstanceAtlas.
A scratch autoload read all 113 gaussian_splatting/* custom monitors plus get_statistics() once per rendered frame for 8 s. Five runs:

Both crashes have the same single GDScript frame:
```
CrashHandlerException: Program crashed
================================================================
GDScript backtrace (most recent call first):
    [0] _run (res://probe.gd:134)
-- END OF GDSCRIPT BACKTRACE --
```
where :134 is exactly var st: Dictionary = gnode.get_statistics(). The C++ backtrace is present but unsymbolized (<couldn't map PC to fn name> for every frame), so I cannot name the faulting function; a PDB-backed rerun would.
Dropping the sampling rate to ~4 Hz (every 15th frame), which is the rate the shipped overlay actually refreshes at, completed 444 frames without a crash.
Why it is plausible rather than a probe artefact
get_statistics() (gaussian_splat_node_3d.cpp:1460) calls renderer->get_render_stats(), which builds a large Dictionary out of live PerformanceMetrics, DebugState, StageMetrics and the rasterizer's RasterStats (render_diagnostics_orchestrator.cpp:1871 → build_render_stats()). With thread_model=2 the render thread is mutating those structures while the main thread reads them; the per-frame read is simply a much harder hammer on that than the 4 Hz overlay. The same console shows the engine already complaining about main-thread/render-thread synchronisation from the neighbouring viewport-texture reads, so the two are contending.
What I did not do
Not root-caused, not symbolized, not bisected, and no attempt to establish whether the crash needs the concurrent monitor reads or the screenshot capture in the same loop. It is reproduced, not diagnosed — 2 of 5 is a rate, not a mechanism.
Why it matters
get_statistics() is a public, ClassDB-bound API and the natural one for any per-node HUD: the #833 overlay now sources its GPU pass times and validity flags from it, and tests/examples/godot/test_project has HUDs in the same shape. A tool that polls it per frame — which is the obvious thing to write — may take the process down. Either the read needs to be safe at frame rate, or the API needs to say it is not and the in-tree consumers need to be checked against that.
Suggested next step: rerun the per-frame loop against a dev_build with PDBs to symbolize the faulting frame, then decide between locking the snapshot build or documenting a rate limit.
