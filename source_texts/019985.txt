What this pull request does
This pull request lets a reviewer see the Cornerstone3D multi-resolution volume work in
OHIF. Two deploy previews build OHIF against the Cornerstone3D branch. A
?customization=gpu/<class> URL states the class of the GPU, and a volume viewport
reduces its texture to fit that class.
The Cornerstone3D pull request is
cornerstonejs/cornerstone3D#2931.
This pull request does not change platform/core. The changes are in the cornerstone
extension, in the CI scripts, in the public customization files, and in the documentation.

What to check
The large series opens. The 2464-image series displays in all three MPR views.
A reformat holds no band and no black line. Watch the sagittal view and the coronal
view while the series loads. Each view must refine as the data arrives. A block of one
image that repeats down the view, or a black line across the view, is a defect. Report
the defect with the link and the GPU class.
The measurements do not change. Draw a length and a rectangle ROI on the 2464-image
series under gpu/low-tablet and again under gpu/high-texture-4096. The length, the
area and the mean value must be the same, because a measurement reads the
full-resolution voxels.
A segmentation stays aligned. Open the same study in the basic viewer
(Netlify · Playwright), then
load the SEG series. The labelmap must stay aligned with the CT images.
The GPU class changes the reduction. gpu/low-tablet shows a strong reduction,
gpu/medium reduces less, and gpu/high-texture-4096 reduces nothing for a series of up
to 4096 images.
Known limits
These two limits are not defects:
The resolution of a viewport does not change while a volume loads. The values refine,
so a reformat gets sharper, but the grid does not get finer.
Nothing probes the device. The deployment states the profile.
Local test
platform/docs/docs/development/multiresolution-testing.md gives the pnpm commands
that link the Cornerstone3D branch into a local OHIF.
Changes
GPU capability profile.
The new customization cornerstone.gpuCapabilityProfile names a Cornerstone3D capability
profile. The OHIF default is medium: a texture edge of 2048 and 8 GB of texture memory.
OHIF does not use the Cornerstone3D default high (32 GB), because a device with an 8 GB
GPU crashed under high. The Cornerstone3D branch now states 8 GB for medium, and not
16 GB.
The values of low in the documentation were wrong. low states a texture edge of 256 and
2 GB of texture memory.
extensions/cornerstone/src/utils/initGpuCapabilityProfile.ts applies the profile with
setActiveGpuCapabilityProfile before a mode opens a viewport. The function applies the
profile again when the global or the mode customization changes.
A build of @cornerstonejs/core without profiles logs a warning and keeps its behaviour.
Five files in platform/app/public/customizations/gpu/ set the profile:
low-tablet, low, medium, high, and high-texture-4096.
high-texture-4096 is a control for the demonstration, and not a real device. No device
is tested to render a texture edge above 2048. Do not use this profile in production.
Fix in the cornerstone extension. The updateVolumeData command now skips the frame
updates when the volume has no texture. A multi-resolution volume has no texture until a
viewport mounts the volume at full resolution.
CI: CircleCI and Netlify read the CS3D_REF line. These commits are the same commits
as in #6137. The two pull requests keep the same CI code until one of them merges into
master.
.scripts/ci/cs3d-apply-ref.sh applies the CS3D_REF line in the CircleCI unit test
job, in the CircleCI Cypress job, and in the Netlify deploy preview.
.scripts/cs3d-read-ref.mjs reads the line with the rules of the Playwright gate.
.scripts/cs3d-read-ref.test.mjs fails when the two copies of the rules disagree.
eslint.config.mjs ignores libs/, so a cloned Cornerstone3D does not count against
the React Compiler lint budget.
CI: the .cs3d-ref file. CircleCI and Netlify give a build only the number of the pull
request, and not the description. The script reads the description through the GitHub API
without a token. When the API does not answer, for example at the rate limit, the script
reads the .cs3d-ref file at the repository root. That file holds the same line as the
CS3D_REF line below. The description wins when the API answers. The script prints a
warning when the file and the description disagree. Thus CircleCI and Netlify do not need a
GITHUB_TOKEN.
Documentation.
multiresolution-testing.md is a new page. The page says how to run the branch locally
and in CI, how to select a GPU class, and what to check.
specificCustomizations.md documents cornerstone.gpuCapabilityProfile.
cs3d-integration.md documents the CircleCI and Netlify jobs and the .cs3d-ref file.
Expected result of the merge guard
The CS3D Branch Merge Guard job reports a red result while the CS3D_REF line names a
branch. That result is correct and it is advisory: a merge of this pull request would
leave master dependent on unreleased Cornerstone3D code. Do not merge this pull request
until the Cornerstone3D work has a release. Then change the line as the integration page
describes, and delete .cs3d-ref in the same change.
