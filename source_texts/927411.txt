Summary
This is picking up where #514 left off, basically just that PR rebased on main.
This PR introduces a ChunkStore/ChunkStoreView architecture to enable efficient chunk sharing across multiple viewports. Currently, ChunkManagerSource conflates two responsibilities: managing a canonical chunk data store (for a given source) and determining viewport-specific chunk visibility. This design prevents resource sharing when multiple viewports render overlapping portions of the same data source.
The implementation splits ChunkManagerSource into two complementary classes:
ChunkStore: Manages the canonical data store and global state for all chunks for a single source by aggregating view state across associated ChunkStoreView objects
ChunkStoreView: Represents a layer/viewport-specific "view" into that store, calculating LOD, visibility, and prefetch requirements based on its camera and slice position
Multiple layers (including in separate viewports) can now share the same ChunkStore while each maintains its own ChunkStoreView. The ChunkStore aggregates chunk requirements across all views: chunks are kept loaded if any view needs them, and disposed when no views reference them. Priority for loading is determined by taking the minimum priority across all views.
ChunkStoreView maintains an efficient sparse Map<Chunk, ChunkViewState> rather than tracking all chunks. View state aggregation happens synchronously during the update cycle, with maybeForgetChunk() called inline to clean up no-longer-visible chunks within a view.
chunkManager.update() is now called after rendering, as chunk view states are updated as the runtime iterates over viewports to render. This performs the view state aggregation and ultimately chunk queueing and discarding.

@aganders3 @andy-sweet Continuing the conversation about ChunkStore and ChunkStoreView:
I still think their relationship is flipped:
Right now ChunkManager tracks views_ per store and even does a reverse lookup.
It also owns aggregateChunkViewStates and updateAndCollectChunkChanges.
These are per-store responsibilities, yet they live in the manager.
A cleaner split IMO:
ChunkStore owns its ChunkStoreView[]. It’s the place where all view states are merged into final chunk state.
ChunkManager owns the set of ChunkStores (one per ChunkSource) and the global ChunkQueue store lifecycle.
ChunkStoreView focused on cameras, viewports, and policies. Computes per-view ChunkViewState. Nothing else.
ChunkStore just collects those states and resolves the final flags for each chunk.
This feels like the right interim model. Thoughts?
I’ll keep reviewing/thinking about it tomorrow.
These are the open questions I have:
How do we reprioritize when a viewport is minimized?
What does sharing a single layer across multiple viewports look like? (separate views per layer?)
Is the layer manager even useful now?
I'm happy to stamp as it is so we can work on the demo and we can revisit this design later

Initially I instead had views_: ChunkStoreView[] as a property on ChunkStore, which I think is what you're suggesting. This also works, but I lifted some of the responsibilities out to the ChunkManager in order to break the parent/child relationship and (direct) cycle between the ChunkStore and ChunkStoreView. However I agree it created this awkward set of maps:
```
class ChunkManager {
  private readonly stores_ = new Map<ChunkSource, ChunkStore>();
  private readonly views_ = new Map<ChunkStore, ChunkStoreView[]>();
```
The other motivation was this way a layer would only need a reference to a ChunkStoreView instead of also holding a reference to the corresponding ChunkStore. Given we have ChunkStoreView.store as a public property, maybe this is a distinction without a difference. We can also avoid needing this reference by adding ChunkStoreView.dispose() to have it remove itself from ChunkStore._views (instead of needing ChunkStoreView.removeView(view)).
I think you're right though, and I'm talking myself (back) into the design you're proposing...
How do we reprioritize when a viewport is minimized?
I think this is still an open question, but I honestly haven't given it much thought. It does seem reasonable to distinguish between "closed" and "minimized", where a minimized viewport would continue to request data in the background but at a lower priority, but it may need to keep track of some things e.g. what size it expects to be restored to. This could also be related to disposal policies and resource management. For example I think Neuroglancer maintains some number of chunks in a "recent" state before freeing memory.
What does sharing a single layer across multiple viewports look like? (separate views per layer?) (from Slack: I assume the same layer will need to have separate store views?)
In the current implementation this is not supported. The simple workaround is to make another instance of the layer and it can share some, though I recognize this is a little unsatisfactory and perhaps unintuitive.
I don't really like the idea of a layer having multiple ChunkStoreView instances because I think it would also need to maintain separate lists of renderables for each (or its list of renderables will be constantly changing), but there might be a better solution I'm not thinking of.
I have an open question which is: what should happen if a layer is in multiple viewports? I'm thinking here if a ChunkedImageLayer is placed in a 2D viewport (as we have) and then we also want to see it represented in the 3D view intersecting a volume rendering. In Neuroglancer for example the 3D view ("sections") is a representation of what you see in the 2D views. If the layer had a ChunkStoreView for each viewport, it would show the whole slice in 3D, not the crop of the viewport (what we probably want).
Is the layer manager even useful now?
The layer manager has had pretty small utility in general to this point, so I'm not sure. Ultimately it is a list, and with 3D views and OIT even the ordering in the list is perhaps not as important as we once thought. Maybe it could be useful as an intermediary for managing layers in multiple viewports, instead of introducing multi-viewport-aware logic in a layer itself? That's a pretty speculative idea though.

### Summary
This is a follow-up for #531 as discussed in
#531 (comment).

The main purpose of this refactor is to transfer ownership of the
`ChunkStoreView` instances to their corresponding `ChunkStore`, away
from `ChunkManager`.
* Added natural `ChunkStore.views_ : ChunkStoreView[]` 
* Removed confusing mapping and reverse-lookup on `ChunkManager`
* Moved store-specific functions to `ChunkStore`:
  * `updateAndCollectChunkChanges`
  * `aggregateChunkViewStates`
* `ChunkStoreView.store` is no longer a public attribute
* Automated cleanup of `ChunkStore` when no views remain
