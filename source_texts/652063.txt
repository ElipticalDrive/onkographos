Summary
Normalize integer-valued volumes without signed overflow or loss of adjacent large 64-bit differences. The global and per-channel paths now share the same integer calculation: NumPy's matching-width unsigned subtraction before floating-point scaling, writing directly into the float64 output rather than allocating an additional full-volume unsigned copy. Floating-point normalization retains its existing behavior.
Tests
Full Highdicom suite: 2,087 passed, 153 skipped (optional codec and integration dependencies unavailable).
Integer normalization regressions cover all signed/unsigned widths, full ranges, adjacent int64/uint64 values (global and per channel), constant inputs, non-mutation, strided arrays, and byte order. Tests are grouped with related normalization tests in tests/test_volume.py.
In one exploratory tracemalloc comparison on a 2-million-voxel int64 array, peak traced allocation fell from approximately 48.1 MB to 16.1 MB. This is a local illustrative measurement, not a cross-platform performance benchmark.
Precision boundary: The subtraction preserves small integer offsets before conversion, but float64 normalization does not make arbitrary 64-bit integer magnitudes exactly representable.

Agreed the full-array astype was too expensive. The new shared global/per-channel integer path uses NumPy unsigned subtraction with out pointing directly to the float64 output, avoiding that extra full-volume copy. Casting extrema to float64 before subtracting loses adjacent int64/uint64 differences—the new per-channel regression reproduced both failures before this change and passes afterward. On one 2-million-element int64 example, peak traced allocation decreased from about 48.1 MB to 16.1 MB; full suite: 2,087 passed, 153 skipped. Arbitrary integer magnitudes are still not exactly representable as float64.
