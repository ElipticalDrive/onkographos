You need to call file.setCopyMaxBytes( 0 ) before file.open().
Otherwise the default behaviour is to copy the whole VDB locally if it is less than 500 megs. I was just hunting down the problems that this has been causing at IE today. Apparently this is intended to help in cases where users are doing delayed loading of files that are being overwritten. I would argue that this is probably always bad default behaviour, but it is definitely bad behaviour when we just need the bounding boxes.

My concern is that users have a lot to think about generally, and given the opportunity to stop thinking about some particular detail, they'll often take it. That's how we ended up with * in the set field of all our SceneReaders, which was really quite painful until we added on-demand set loading. In this case, we don't have the opportunity to add on-demand loading, because that bit is inside Arnold.
I don't see any reason not to merge as-is and then think about adding wildcards later, but it is interesting to know that you think it would be appropriate to add that here rather than as a wrapper.
Cool, let's merge then, but if we want wildcards later we'll definitely add 'em in the ArnoldVDB node itself, since it's already doing most of the work. If I was going to argue for a wrapper approach, it would have been to use a wrapper around the ExternalProcedural node directly, with all VDB details in the wrapper. I've partly gone for this approach because I want to support Arnold's features as well as possible out of the box, but also because I want to introduce the thin end of the OpenVDB wedge - I'm really keen to get some real VDB nodes into Gaffer, and I see this as a step in that direction...
