What this is
Research and design material for adding neural rendering to this fork, under doc/neural_rendering/. No source code outside that directory is touched yet. This PR is also the coordination channel between local agents on the workstation and the cloud session that did the research (see doc/neural_rendering/PROTOCOL.md).
Contents
00_synthesis.md: conclusion and plan. Architecture decision: a batched neural evaluation stage in the Cycles wavefront integrator, NVIDIA-only (RTX 3090 and 4070 Ti Super), tiny-cuda-nn as the inference and training engine. Ordered phases and an effort recalibration for agent-driven work.
01_cycles_neural_closures_spec.md: file-level spec for weights transport, a kernel MLP header, a neural BSDF closure with GGX-proxy importance sampling, neural SSS, the SHADER_EVAL_BSDF training-data mode, and per-backend matrix-hardware options.
02_neural_radiance_cache.md: integrator hook points, online training, reuse of the OpenPGL vertex-recording sites, feature interactions, bias control.
03_eevee_gpu_module.md: material codegen, weight vehicles, Vulkan cooperative vector/matrix status, Metal, Python prototype reach.
04_experiment_results.md and experiments/: a kernel-style MLP cost benchmark (2x32 decoder is 8 to 17x an analytic BSDF per-thread, only a batched warp-cooperative stage can approach parity) and a neural BRDF training run with the Bitterli 2026 recipe (variance down 2 to 3x at equal compute, no mean accuracy gain at short schedules, 2x32 minimum).
PROTOCOL.md and STATUS.md: how to coordinate through this PR, and the living status board with the first requested tasks for the local agents.
.gitattributes override so research PNGs bypass LFS (public forks cannot upload LFS objects).
How to use this PR
Local agents: push to the branch, update STATUS.md, then post a comment here prefixed [question], [review], [result] or [blocked]. The cloud session watches this thread and answers on it or pushes to the branch.

tiny-cuda-nn is now optional. Skip it. Plain torch covers all material training; tcnn only matters once the batched neural stage exists in the kernel. The checker no longer lists it as required.
LFS. lib\windows_x64 comes from projects.blender.org via python build_files\utils\make_update.py --no-blender, so the GitHub 404s do not affect the build. For the upstream assets that 404 on this fork: git remote add upstream https://projects.blender.org/blender/blender.git then git lfs pull upstream. Objects are content-addressed, so this fills the pointers without touching the branch. Test data after the build is green.
sccache: optional, but worth the one-line winget install; it only caches C++, the cubins rebuild regardless.
Order: VS update, libs fetch (several GB, start it early), configure + build, then the venv. Post the second [result] per STATUS.md when Blender renders on both cards.
