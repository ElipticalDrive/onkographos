Question
What renderer-owned surface derivation and GPU representation should the provisional dense raster milestone use to turn the dense Voxel Volume into an inspectable image—such as exposed unit faces, greedy meshing, instanced cubes, or another bounded approach—so it proves storage-neutral Voxel Frontend consumption and a real raster Render Path while preserving greedy incremental remeshing as a meaningful later outcome?

Resolution
Decision
Use a non-greedy exposed-face mesh for the provisional dense raster proof. The raster Render Path reconstructs the logical contents returned in arbitrary Voxel Region batches and emits one unit quad wherever an occupied Voxel Value borders Empty. Coordinates outside a known Voxel Volume are Empty under the established frontend contract, so finite-volume boundary faces follow the same rule as internal cavities.
The derived result is one immutable, whole-volume raster artifact for the demonstrated Voxel Volume. It is built on a worker from a retained Voxel Scene View, tagged with that view's Voxel Scene Revision, and installed by the Render Path only after the build is complete. There is no partial publication, spatial update partition, or incremental replacement in this milestone.
Surface derivation
For each occupied coordinate, inspect its six axis-aligned neighbors and emit only the faces adjacent to Empty. Adjacent occupied voxels suppress their shared face regardless of whether their Voxel Material identities differ. Every emitted face remains an independent unit quad: coplanar faces are not merged.
The derivation consumes only logical coordinates, Voxel Values, Voxel Material catalogue data, volume origin, and uniform voxel size. It cannot depend on dense memory order, batch order, batch shape, or any Storage Tier layout. Diagnostic surface evidence compares the resulting semantic set of exposed unit faces rather than triangle order or buffer partition.
Renderer-owned artifact and GPU representation
The background artifact contains an indexed triangle mesh with four face-local vertices and six 32-bit indices per exposed quad. Each vertex carries the scene-space position, the axis-aligned face normal needed for inspectable shading, and the Voxel Material's resolved linear base color. Resolving the stable material identity to color happens during derivation; the first proof does not add a GPU material table, per-material draw sorting, or storage-visible material encoding.
The raster Render Path owns the completed CPU artifact and its static Vulkan vertex and index buffers, graphics pipeline, descriptors or constants needed for camera state, and raster-specific depth/presentation-dependent resources. The Render Backend only supplies the previously decided bounded device and frame contexts. The path may split buffers or draw calls mechanically when checked index, size, or Vulkan device limits require it, but such splitting has no Voxel Region, Storage Tier, or incremental-update semantics.
All coordinate transforms, vertex/index counts, byte-size calculations, allocations, uploads, and material resolution are checked. Overflow, an impossible allocation, a missing catalogue entry despite publication validation, or worker/upload failure is returned with build phase and source revision context through the Render Backend to the application/UI boundary. Geometry is never silently truncated, and an incomplete artifact is never installed.
Why this is the minimal proof
Instanced cubes would draw hidden internal geometry and would not prove renderer-owned surface derivation strongly enough.
Greedy merging now would consume the central geometry and update payoff reserved for the editable raster milestone.
Spatial submeshes, streaming segments, and progressive installation would introduce update scheduling and partial-publication semantics before edits or competing revisions exist.
A GPU Voxel Material lookup table or per-material draw partition would add indirection and batching without strengthening the one-revision storage-neutral read proof.
Shader-expanded face records would make the first raster path less conventional without answering a milestone risk.
Roadmap consequence
Revalidate the dense raster demonstration and evidence contract can require an inspectable material-colored image, exact diagnostic exposed-face evidence, responsive background preparation, revision attribution, and contextual failure propagation. The later editable raster outcome retains a clear payoff: partition derived work, consume revisions and change sets, greedily merge faces, and replace only affected results without publishing stale work.
No canonical domain term changes, ADR, new Wayfinder ticket, or fog graduation are required.
