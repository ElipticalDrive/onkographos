Problem and motivation
City-meshing demos download Lantmäteriet point-cloud tiles through the DTCC backend and local cache, but the resulting PointCloud and derived city/mesh do not identify the actual input snapshot or acquisition dates. A mesh built today may represent a scan from several years ago. Without concrete source records we cannot assess temporal consistency with building footprints, explain differences between model runs, audit data quality, or reproduce the same model after upstream tiles change.
Acquisition time, source processing/update time, file creation time, download time, and model generation time must remain distinct. An area can contain several scan dates; a single inferred date is insufficient.
Evidence in the current code
dtcc_core/io/data/wrapper.py defaults to http://compute.dtcc.chalmers.se:8000 for LiDAR.
io/data/lidar.py::download_lidar resolves intersecting tiles, caches their LAZ files, and returns paths. It does not return a provenance record or preserve upstream metadata sidecars.
io/pointcloud.py::_load_las retains coordinates, classification, intensity and returns, but does not carry GPS time, Point Source ID, or header/source metadata into PointCloud.
datasets/pointcloud.py::collection_period explicitly says acquisition date, scan campaign and cache tile vintage are not surfaced.
DatasetContext/DatasetProvenance and export manifests already exist, but the point-cloud source description is generic rather than the concrete inputs used by a request.
Concrete local-cache inspection: the bounds in demos/build_city_volume_mesh.py, EPSG:3006 [319720, 6397660, 320220, 6398160], intersect 19B002_639_31_7575.laz and 19B002_639_32_7500.laz. The 489,368 points inside those bounds have Point Source ID 3402 and adjusted GPS timestamps indicating 2019-11-29, approximately 11:51 UTC. Both file headers report creation on 2020-11-16. This describes the inspected cached inputs, not a guarantee about current backend content.
Proposed implementation
Capture source records at ingestion. Coordinate with dtcc-data to expose provider, exact upstream product, tile/asset ID, scan campaign, asset version/publication ID, acquisition interval and metadata references. Preserve original metadata with the cached input and store SHA-256, bounds, horizontal/vertical reference systems, source processing dates, retrieval time and source terms/attribution. Avoid credentials in recorded URLs.
Use authoritative metadata and preserve its meaning. Older Laserdata skog deliveries have *_strip.json (scan date, strip ID and scanner details), *_tile.json (classification level/latest processing change) and campaign delivery reports. New STAC deliveries document acquisition start/end fields. Where metadata is unavailable, valid LAS GPS timestamps can establish point acquisition times; respect the GPS encoding flag, epoch and leap seconds, and record the evidence used. Report unknown values explicitly rather than substituting file dates or filename prefixes.
Carry lineage through processing. Retain GPS time and source/strip identity, or an equivalent lossless association, when loading and filtering points. Union/deduplicate source records on merge and retain the relationship to contributing regions/strips. Propagate lineage through PointCloud → City → terrain/buildings → surface/volume meshes, including processing parameters and DTCC version.
Extend existing context and manifests. Expose concrete request provenance through DatasetContext/DatasetProvenance and persist it through model serialization and export. Use an accompanying manifest where a target mesh format cannot embed it. Keep the existing download APIs compatible.
Make cache vintage explicit. Preserve original retrieval and version metadata on cache hits; provide pin/reuse and explicit refresh behavior. Legacy cache entries without metadata must be marked unknown, not stamped with today's date as their original retrieval time. Checksums identify exact bytes; retaining inputs is needed to reproduce runs if upstream versions disappear.
Acceptance criteria
A downloaded PointCloud exposes its concrete source assets and distinct acquisition/processing/retrieval timestamps, with documented unknown values.
LAS GPS time and strip/source associations survive bounds filtering, classification filtering, merging and supported round trips.
Multi-date and multi-campaign inputs remain distinguishable.
A derived city mesh and its export manifest identify the exact source snapshots and processing parameters.
Offline fixtures cover GPS encodings, unavailable metadata, mixed scan dates, cache hits/refresh, lineage propagation and serialization/export.
Document provenance inspection and explain the distinction between acquisition date and file creation/download date.
