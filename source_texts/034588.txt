Summary
Our existing Marching Cubes functionality in quest only supports structured (Cartesian) grids, but we have users that want to run Marching Cubes on unstructured quad and hex meshes
This feature PR adds a bump-based Marching Cubes option to quest to run on structured and unstructured meshes
The algorithm is policy-based, and runs on cpu, omp, cuda and hip execution spaces
I left the original MC algorithm in place since it is currently more performant on structured grids
This is likely due to the new algorithm performing more work. Specifically:
it welds the vertices of the MC
it also generates a polygonal MC mesh, but our application requires a triangle mesh, so we currently triangulate the output polygons
We should instead have an option to use a triangle-based clipping table, which would avoid the extra work
Also improves the python script that generates Cartesian meshes as input to our MC example, and adds a new script to generate unstructured meshes for the MC example
Benchmark performance
Comparing the original ("native") Marching Cubes implementation against the new Bump-based MC
on hip (rzadams) and cuda (rzvector), using "seq", "cuda" and "hip" execution policies.
Dataset: $960^3$ over $[0,2\pi]^3$ using gyroid scalar field at scale $(1,1,1)$.
Marching cubes generates 8,933,625 triangles
Note that this is a much bigger dataset than we'd typically expect to extract
For reference, here's a screenshot (from VisIt) of a $256^3$ grid gyroid isosurface with about 630K triangles
For the timings below, we report inclusive and exclusive timings, as well as the percentage of the exclusive time on GPU, where appropriate
Seq entries have the form inclusive (exclusive).
GPU entries have the form inclusive (exclusive; %GPU).

Bump is around the same time as native for "cuda"
Bump "hip" is currently several times slower than bump "cuda", but much faster than native "hip"
The hip timings appear to account for allocation and initialization of large buffers, while the cuda ones don't.
(speculation) I suspect the latter are optimized away by nvcc but not by hip
Bump timings use an Umpire QuickPool with an initial 20GB allocation.
I didn't modify or try to optimized the native approach.
The expensive native hip runtime is almost definitely due to buffer allocation and initialization and could likely be improved
The Bump CPU times take about twice as long on the CPU as their native counterpart
A significant portion of the overhead is due to the welding, which is done in the bump algorithm, but not the native algorithm.
