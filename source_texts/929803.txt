mca_atomic_ucx_fop() only enters the UCX progress loop when the request is still pending. A fetching atomic that completes immediately (the normal case for a PE reading its own symmetric variable) never calls ucp_worker_progress().
shmem_signal_fetch() is shmem_uint64_atomic_fetch() on the local PE, so a PE polling a signal word in a loop never progressed its worker. Other PEs doing shmem_put_signal(..., SHMEM_SIGNAL_ADD, ...) block in the strong fence (ucp_worker_fence) between the put and the signal, which cannot complete without the target making progress. With three or more PEs the fence never finished and the signal total stayed below the expected sum (for example tests-sos signal_fetch hung and each PE saw sig=1 instead of N*(N-1)/2).
Call ucp_worker_progress() after every fetching atomic so that polling with atomic fetches keeps the worker serviced.
Tests: add oshmem/test/shmem (check-shmem harness) with signal_add_total.c (many SHMEM_SIGNAL_ADD put_signal/_nbi, default and ctx, from all PEs to one target; final signal must equal the total) and signal_add_data.c (per-sender data+signal pairs; receiver waits on the signal then checks data).

The diagnosis is right, but the fix is incomplete in a way I think should be addressed before this lands.
mca_atomic_ucx_cswap() has the identical bug and is not fixed. oshmem/mca/atomic/ucx/atomic_ucx_cswap.c:71 ends in the same opal_common_ucx_wait_request(), which returns at the UCS_OK == request fast path in common_ucx.h:200 without ever entering MCA_COMMON_UCX_WAIT_LOOP. It is registered as module->super.atomic_cswap, so shmem_atomic_compare_swap() is affected exactly like the fetching atomics this PR fixes.
That matters more than it might look, because compare-and-swap is the canonical polling primitive: spin-on-cswap is what OSHMEM's own MCS lock does in _shmem_mcs_test_lock(), and #14618 is independently working around this very root cause by adding an opal_progress() call inside that function. Fixing cswap here would address it at the source for every caller — the MCS lock, the ticket lock's polling, and user-written test-and-set loops — rather than patching call sites one at a time as each one is discovered.
Separately: there is no docs/release-notes/changelog/v6.1.x.rst entry, and this is a hang fix in the default path.

This is unconditional, so it also runs on the path where opal_common_ucx_wait_request() already executed MCA_COMMON_UCX_WAIT_LOOP. On that path the extra ucp_worker_progress() is pure overhead added to remote atomic latency, which is a headline metric.
The gap you identified is specifically the inline-completion path, so gating on it is strictly more targeted and leaves remote atomics untouched: capture UCS_OK == status_ptr before wait_request consumes the request, and only progress in that case.
