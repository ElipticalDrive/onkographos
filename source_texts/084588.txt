This is a draft extension proposal for using Niantic Spatial's SPZ compression library for compression 3D Gaussian splatting data using the base KHR_gaussian_splatting extension with glTF. This extension targets version 2 of SPZ.
As we get closer to done with the base extension for 3D Gaussian splatting, KHR_gaussian_splatting, it has made more and more sense to break out the KHR_gaussian_splatting_compression_spz_2 extension for SPZ compression of 3DGS data. This allows them each to independently go through the ratification process and neither will hold up the other.
For previous history and conversations regarding the development of this extension, please look at the PR for KHR_gaussian_splatting before this linked comment.

@weegeekps and working group members — thank you for your patience on this PR. We fully understand that the working group's current focus is on finalizing the base extension's editorial draft, and this message is in no way meant to rush any timeline. We would simply like to share some engineering observations from our reference implementations of the current draft, as input for the community and working group to consider. These points reflect our own implementation experience; we may well have misunderstandings, and we welcome corrections.
Relationship between the draft and SPZ v4 In our implementation we noticed that the draft's naming and description still anchor to SPZ v2, while Niantic's reference implementation has since moved to SPZ v4 (Zstd compression, 32-byte header, ILV header-zone extension layout); our own converter already produces v4-based output, so we would be curious to learn whether the working group plans to have the draft explicitly cover v4, and whether our reading is correct.
GLB packaging approach We currently package the original SPZ stream byte-identically into the GLB (SPZ stored as-is in buffer → bufferView → spz_2.bufferView , so GLB size ≈ SPZ size); in practice this preserves the "lossless" semantics the draft describes well, and we would like to ask whether the draft intends to allow or encourage re-compression, or keep it strictly pass-through.
JSON fields Besides the draft's bufferView , our current GLB JSON also carries three metadata fields — spzVersion , compression , coordinateSystem — which are non-standard since the draft schema only defines bufferView ; we are unsure whether they should be standardized or better placed in extras , and would appreciate the community's thoughts.
How extension fields are added We add fields by extending fastgltf's GaussianSplatSpzCompression struct ( bufferView + the three metadata fields) and serializing them in the JSON writer; the mechanism itself works well, but a canonical field set in the schema would likely improve interoperability.
Handling of the ILV 003 extension We parse the Adobe coordinate system extension ( 0xADBE0003 ) from the SPZ v4 ILV header zone, treat it as descriptive metadata rather than an instruction (consistent with the "descriptor, not instruction" consensus in the base PR discussion), validate its value range [0, 16], and record it in the GLB metadata; we would like to ask how this coordinate system information should be reconciled with the draft's LUF requirement on the glTF side — or whether our understanding is off.
High-performance WASM and queue mode Both projects ship usable high-performance WASM builds — spz2glb (memory pooling + device-aware memory management) and spz_gatekeeper (zero-copy pointer inspection + serial batch queue) — enabling in-browser SPZ→GLB conversion and compliance validation; this may indicate the extension has practical potential for web-scale use, though there may well be gaps we haven't considered.
Benchmark dataset (experimental early work) Our companion spz-anime-text2scene-bench dataset (6/10 scenes, ~587 MB, CC BY 4.0) is currently an experimental early-stage effort that we ourselves treat as a "to-be-improved baseline"; we welcome community feedback and plan to expand coverage and align formats as the specification stabilizes.
Thank you again for the working group's patience. We are happy to contribute testing and feedback as a reference implementation, and we look forward to the clarification whenever the working group is ready to post it.

Disclaimer: I don't have the authority to answer these questions. Until Adam chimes in, I'll share my thoughts and interpretations. These should be considered as purely subjective.
Relationship between the draft and SPZ v4
This is related to the first point that was brought up in the discussion of the original PR (even before splitting out the base extension). From what I see, there are roughly three options:
Leave this extension to be specific for SPZ v2
Introduce new extensions, ...spz_3, ...spz_4....
Generalize this extension to cover other SPZ versions
All this is revolving around aspects of stability and backward compatibility. Of course, when SPZ versions 5, 6, 7 ... are published, then this should not imply ...spz_5, ...spz_6, ...spz_7 extensions. When the current extension is generalized, then it still has to be limited to a particular set of supported SPZ versions (as supporting the extension now cannot mean that it will also work with future SPZ versions).
And to be clear: SPZ v4 is a new file format. It is completely unrelated to SPZ v2 (except for trivial details, like quantizing a float into a byte). It could have been published by a different company, with a different name, and nobody would even think of asking about any form of "compatibility" between SPZ v2 and this new file format.
GLB packaging approach We currently package the original SPZ stream byte-identically into the GLB
This sounds reasonable. Compressing data that is already compressed rarely makes sense. (In addition to the complexity that could result from adding another "layer" of compression here, both for the specification and for the implementations)
JSON fields Besides the draft's bufferView , our current GLB JSON also carries three metadata fields — spzVersion , compression , coordinateSystem
The spzVersion is related to the first point. It still raises the question about the possible values for this field (I assume 2, 3, 4, but not 1 or 5...)
The compression is something that I'd consider to be an inherent part of the SPZ payload.
The coordinateSystem seems to be related to a comment above, and #2613 (even for the base extension). glTF does (fortunately) define a single coordinate system, and I'd be leaning towards using this coordinate system for splat data as well (regardless of the encoding). Iff SPZ allows for different coordinate systems, then this should be made absolutely clear.
Related: nianticlabs/spz#14 , nianticlabs/spz#84 , nianticlabs/spz#42 ... (these questions don't just go away - they'll bubble up again and again...)
How extension fields are added We add fields by extending fastgltf's GaussianSplatSpzCompression struct ( bufferView + the three metadata fields) and serializing them in the JSON writer; the mechanism itself works well, but a canonical field set in the schema would likely improve interoperability.
This sounds like an implementation detail. In the previous point, you mentioned that you stored some ~"(arbitrary) additional fields", and of course, these may not be supported by some serialization layer, unless they are officially made part of the specification and its JSON schema.
Handling of the ILV 003 extension
This sounds like something that came in with SPZ v4, and is not (and cannot be) handled in this extension unless it is explicitly generalized to handle SPZ v4 as well. (And it looks like it's a good example why claiming support for ~"different versions" can be difficult. If such a new format can add ~"arbitrary metadata", it may be necessary to be very explicit about which parts or flavors of this metadata are anticipated to make sense in the context of glTF).
High-performance WASM and queue mode
I think this is related to the specific library that is used for loading the SPZ data. And it may unfold into two (fairly separate) questions:
Which versions of SPZ does that library support? (For example, https://github.com/drumath2237/spz-loader is used in some projects, but only supports SPZ v2...)
Which technology is that library using? (Referring to WASM, zero-copy or whatnot...)
Benchmark dataset (experimental early work)
You seem to refer to https://github.com/spz-ecosystem/spz-anime-text2scene-bench (aber ich habe mir das noch nicht näher angeschaut, weil ich dazu Google Translate benutzen müßte). In general, the questions about data sets also fall into two categories:
Compliance tests. These can usually be "small" data sets with specific features. I started creating some of these at Test data sets for KHR_gaussian_splatting #2562
Benchmark data sets. Of course, these should be based on real-world example data sets. But I think that for some forms of analysis, it can also be very useful to generate artificial test data. I've been doing that in some very narrow contexts as well. But usually, there are several "dimensions" along which this test data set generation can happen. A very shallow one is whether the goal of these benchmarks is to analyze the performance of a renderer, or the compression ratios that can be achieved with a certain compression method (and the nature and structure of the data sets will be vastly different depending on the exact goal)

@javagl — thank you very much for the detailed and candid response, and for the related issues you linked. We cross-checked several points against both of our projects (spz_gatekeeper and spz2glb), and would like to add the following details.
1. How we support multiple SPZ versions
Both projects dispatch on the compression magic, rather than assuming a single version:
spz2glb first detects the magic — gzip (0x1F8B) routes to the SPZ v2/v3 header parser, Zstd (0x28B52FFD) routes to the v4 32-byte header parser. Rotation data is handled per version (version >= 3 selects the 4-byte smallest-three quaternion layout; v2 uses the 3-byte layout). The v4-only ILV header zone is only read on the Zstd path.
spz_gatekeeper applies a version policy: version < 1 → error, version 1..4 → normal validation, version > 4 → warning but continue (via the kKnownMaxVersion constant). v4 uses its own header parsing path. Compression mapping: v3 = gzip, v4 = Zstd.
2. How we validate across versions
spz2glb ships a built-in five-layer verification: L1 GLB structure & KHR extension contract → L2 binary losslessness (byte-identical to the original SPZ) → L3 decoding consistency → L4 GLB↔SPZ metadata consistency → L5 ILV extension integrity (TLV structure + 003 value range [0, 16]).
spz_gatekeeper is the format-compliance engine: it parses the ILV layout [u32 type][u32 length][value] and skips unknown types via length (no false positives). Semantic validation is only applied to extensions registered in the extension registry (currently 0xADBE0002 / 0xADBE0003) — which is precisely the "boundary" you mentioned: registered = semantic commitment, unregistered = structurally valid but no semantic promise.
3. How we handle the 003 extension
Both projects treat 0xADBE0003 (Adobe Coordinate System) consistently: as a descriptor, not an instruction (no coordinate transformation — that is left to the renderer's coordinateConverter()). L5 validation enforces the value range [0, 16]. The ILV header zone is located via tocByteOffset in the SPZ v4 header, whose field layout is aligned with the upstream Niantic NgspFileHeader (32-byte) spec — identical parsing in both projects.
4. The GLB structure we produce
The GLB JSON carries the full extension chain: outer KHR_gaussian_splatting {kernel, colorSpace, sortingMethod, projection}, nested KHR_gaussian_splatting_compression_spz_2 {bufferView, spzVersion, compression, coordinateSystem} — bufferView points directly at the original SPZ stream (byte-identical embedding; GLB size ≈ SPZ size), and spzVersion explicitly declares the version.
5. WASM + CLI dual-end collaboration
Both projects provide in-browser WASM modules — spz2glb for fast batch v3/v4 packaging with per-file JSON conversion reports; spz_gatekeeper for drag-and-drop validation with audit reports — and the reports are consumable by each project's CLI: spz_gatekeeper's browser report can be exported as browser_to_cli_handoff and re-checked by the CLI (compat-check --handoff --json, final verdict on the CLI side); spz2glb's web queue mirror produces the same JSON report structure as the CLI. Both projects are WASM + CLI dual-end, sharing one JSON contract.
6. Benchmark dataset (in response to your compliance-vs-benchmark split, with clarifications)
The dataset actually started as an attempt to address spz issue #87 (canonical samples per format version). It is an experimental composition; we do not claim it is correct:

@javagl — thank you for the follow-up, and for the exploration and community contributions behind JSplat. As before, these are just notes from our own implementation experience; we may well be wrong on some points, and we welcome corrections.
1. Design background: why registry-driven
We noticed that the upstream Niantic library uses a tryParseExtension switch-case, hardcoding extension handling type by type. As SPZ versions (v2/v3/v4) and vendors (Adobe, Niantic, ...) keep producing new extensions,such a structure can become harder to maintain as the number of extensions grows over time. The gatekeeper's role is a neutral format-compliance validator (not a storage or writer), so we moved "extension management" into a governance layer that is independent of version parsing: a two-layer registry — one layer declares contracts, the other performs semantics.
2. The two-layer registry
Spec layer ExtensionSpecRegistry: each extension registers an 11-field contract — type / vendor_id / extension_id / vendor_name / extension_name / category / status / spec_url / short_description / min_spz_version / requires_has_extensions_flag — registered per type, not bound to a specific SPZ version.
Validator layer ExtensionValidatorRegistry: runtime payload validators keyed by type, auto-registered at static init via RegisterValidator<T>; the validator interface has only 3 virtual methods (Validate/GetName/GetType) — we only validate, never write, which differs from the upstream SpzExtensionBase with its 8 virtual methods.
Parsing: ILV records are walked as [u32 type][u32 length][value], and unknown types are skipped via length — structurally valid by construction, no false positives.
3. min_spz_version: making "generalization" operable
Version-dependent differences (gzip/zstd header parsing, quat layout) are handled by the core parser, so extension contracts are decoupled from versions — the registry itself expresses "which SPZ versions this extension applies to" through min_spz_version. Current registrations: 0xADBE0002 is stable without a version restriction; 0xADBE0003 is draft with min_spz_version=4. Should spz_2 ever be generalized, this kind of structure could directly host cross-version contract management.
4. The 4-state matrix: an explicit boundary for semantic commitment
Registration × validator = 4 combinations, each with its own issue code (A/B/C/D, no gaps):
spec ✓ + validator ✓ → full semantic commitment (L2_EXT_VALIDATION only on validation failure)
spec ✓ + validator ✗ → contract declared, validation pending (L2_EXT_REGISTERED_NO_VALIDATOR)
spec ✗ + validator ✓ → validator exists but undeclared (inconsistent, L2_EXT_UNREGISTERED_VALIDATOR)
spec ✗ + validator ✗ → structurally valid, no semantic promise (L2_EXT_UNKNOWN)
This is our engineering answer to "claiming support for different versions is difficult": no overclaiming (unregistered = no semantic promise), no blind spots (all four states covered), and observable status (queryable from both CLI and WASM).
5. WASM capabilities
The WASM module shares the same registry/report vocabulary as the CLI. Browser-side capabilities include:
Zero-copy inspection: inspectSpzPtr(ptr, size, strict) reads SPZ bytes directly from WASM memory (avoiding JS↔WASM copies); inspectSpz/inspectSpzText are the regular entry points.
What the current checks cover:
Format layer: magic, version validity (invalid / newer-than-known-max → error/warning respectively), SH degree range, reserved-zero, file sizes (too small / truncated / base payload)
Compression layer: gzip decompression failure; ZSTD decompression failure on the v4 path
v4-specific: 32-byte header parsing, ILV extension-zone parsing, TOC parsing
Extension layer: declared-but-no-data, ILV parsing (error in strict mode, downgraded to warning in non-strict), validator semantics, the three state codes of the 4-state matrix, undeclared trailer
strict/non-strict runs through all of the above
Governance exports: listRegisteredExtensions() / describeExtension(type) / getCompatibilityBoard() — the registry contracts and the maturity board are browsable inside the browser.
JSON report contents:
inspectSpz returns top-level ok (true when no errors) / strict, plus the full GateReport JSON (spz_l2: flags / trailer_size / ilv_records[{type,length,offset}]; issues: code / severity / message / location)
Both audit modes share a 12-field verdict schema: audit_profile / policy_name / policy_version / policy_mode / audit_mode / verdict / final_verdict / release_ready / summary / budgets / issues / next_action (budgets items carry per-item status: within_budget / over_budget)
Handoff: the browser can export browser_to_cli_handoff, which the CLI merges via compat-check --handoff --json — the final verdict always lives on the CLI side
Memory engineering : device-aware SmartMemoryManager, a serial BatchQueue (max 2), 64KB chunked writes into a reserved buffer, and C++-side HotObjectPool/BumpAllocator
Canonical samples and our synthetic fixture
To be honest about the canonical samples: our current synthetic fixture is still quite early-stage. gen-fixture produces a minimal SPZ with a placeholder payload and a single ILV record — a minimal-sample tool aimed at extension-validator development and compliance smoke tests within the gatekeeper itself. It does not yet cover the diversity of real scenes.
We have also learned from projects like JSplat that programmatically generated scene samples (e.g., a unit-cube scene read and written across multiple formats) are closer to a "reproducible sample" target than a placeholder fixture. We are considering borrowing that idea to grow our synthetic samples over time. Building compliance test data sets is a long-term community effort, and we will keep following the relevant discussions (such as #2562 ).
These are our current practices and reflections. Thank you again for the discussion — we are happy to share more implementation details if that would be useful.

@javagl — thank you for the follow-up, and for naming the fundamental question that sits exactly at the junction of our two tools: "what does an SPZ v4 extension (e.g. a coordinate system) mean for glTF, is it allowed, and where do conversions happen?" Let me share how we split that responsibility in our implementations.
spz_gatekeeper — the semantic-commitment side. As a neutral format-compliance engine, it separates "structurally valid" from "semantically compliant" through the two-layer registry ( ExtensionSpecRegistry + ExtensionValidatorRegistry ) and the 4-state matrix (spec × validator): a registered extension carries a semantic commitment; an unregistered one is only structurally valid with no promise. In short, it defines what an extension can be understood to mean .
spz2glb — the data-transport side. It follows a strict pass-through principle: it only reads extension metadata from the SPZ ILV records and packs it into the GLB extensions field as-is — no coordinate transforms, no semantic interpretation; when there is no ILV extension, the corresponding metadata fields are simply omitted. In short, it defines how extension data can be carried .
On your question of whether an extension is "allowed" in glTF: we treat permissibility as a spec-side decision (a working-group boundary call), and transportability + observability as the implementation's responsibility . The tools do not preempt the spec on permissibility — they faithfully carry whatever is declared and make its status queryable via the registry / reports.
From the start, the two tools were designed as complementary, interoperable components of a single end-to-end toolchain: spz_gatekeeper confirms "the input is compliant", spz2glb completes "the output is standard". We hope this engineering experience can serve as a humble reference anchor for the working group's discussion.
On engineering feasibility, our test data may be useful as reference:
Test coverage : the toolchain is validated on two sources of SPZ files — high-fidelity .spz (v3) and .ply exported from Tencent HY-World (web-generated) , and .ply → .spz v4 produced by Niantic SPZ Converter . The two classes differ in geometric detail and encoding path, covering the main version branches of the current SPZ ecosystem.
spz2glb packaging performance : for 25+ MB SPZ files from both sources, lossless SPZ→GLB packaging is stable at 200+ ms with a memory peak around 50+ MB (~2× input size) — suggesting the draft's lossless packaging approach is engineering-efficient, with no theory-to-practice gap.
spz_gatekeeper compliance validation : its current mainline is WASM security hardening (performance optimization is a follow-up). Current compliance checks — header integrity, ILV extension parsing, ZSTD/gzip decompression paths — are stable in the 800+ ms range (observed values of the current WASM implementation); we expect them to shrink after the performance work.
Draft feasibility : together the two tools show with measured data that the SPZ_2 draft's "compressed-stream pass-through into GLB" scheme is not only self-consistent in theory but also landable in engineering — the end-to-end flow (compliance validation + lossless packaging) completes in about 1 second , which is practically meaningful for browser-side real-time distribution.
We understand the current focus is the spz_2 extension itself; the above is engineering background for reference. We are happy to narrow the scope if needed, and we will adjust our implementation per the community consensus. Thank you again for the discussion.
