Purpose
Direct volume rendering draws a scalar field over a volume as a translucent cloud, by casting a ray through the volume for every pixel and accumulating colour and opacity from a transfer function that maps each value to a colour and an alpha. It shows the whole interior of a volume at once, without choosing iso-values or planes in advance, and is how CT and MRI scans, microscopy stacks, combustion and astrophysical simulations are usually first inspected.
In a figure, volume rendering is most useful with a clear transfer function shown beside it, and in combination with axes, slices or isosurfaces of the same data. It is inherently a raster technique: its result cannot be expressed as vector paths.
Example
Source: Plotly documentation.
Examples in other libraries
matplotlib: No native chart type and no widely used extension within matplotlib.
MATLAB: volshow and the Volume Viewer app, both in the Image Processing Toolbox rather than in MATLAB itself.
Chart.js: No three-dimensional charts and no widely used plugin that provides them.
Plotly: 3D volume plots (the volume trace), which approximates rendering by drawing surface_count translucent isosurfaces, with opacityscale acting as the transfer function's alpha.
Typical API
volume (or volshow, after MATLAB) takes the volume grid and values proposed in #140, a colour scale for colour and an opacity transfer function for alpha.
```
let mut ax = fig.axes3(0, 0);
ax.volume(&x, &y, &z, &density)
    .color_scale(scale)
    .opacity_map([(0.0, 0.0), (0.2, 0.05), (1.0, 0.6)])   // value fraction to alpha
    .sampling(VolumeSampling::Linear)
    .step(0.5);                                           // in voxels
```
Sketch of the IR, for review and not a decision:
```
Artist::Volume(Volume {
    id, label, visible,
    grid: VolumeGrid,                // as proposed in the isosurface issue
    values: NodeId,                  // [nz, ny, nx]
    color_scale: NodeId,             // colour of each value
    opacity: OpacityMap,             // piecewise-linear alpha over the scale's limits
    sampling: VolumeSampling,        // Nearest | Linear
    step: f64,                       // ray step in voxels
    blend: VolumeBlend,              // Composite | MaximumIntensity | Average
})
```
Transfer function: colour through an existing colour scale, so that a colourbar (Add a colorbar node #8) shows it, and alpha through a piecewise-linear opacity map; Plotly calls the latter opacityscale, and MATLAB's volshow calls it Alphamap.
Blend mode: compositing, maximum-intensity projection (common for angiography and microscopy) or average.
Sampling and step: interpolation between voxels and the ray step, which trade quality against speed.
Interaction with other artists: opaque surfaces, lines and markers inside the volume must stop the rays at their depth, which requires the volume to be drawn after them with the depth buffer read, not written.
The canvas would draw a volume with a raymarching pipeline in wgpu, sampling a 3D texture and reading the depth buffer of the axes' depth group so that other artists occlude it correctly. The offscreen renderer uses the same pipeline, so the gallery and the export see what the window shows, and a machine without a graphics device needs a software adapter as ADR 0013 describes.
A volume has no vector form. Every export to PDF or SVG must therefore embed the volume's axes as an image, and the export report must always carry a warning naming the node and a typed reason for the rasterisation, under the project rule that the report warns whenever vectors become pixels. The reason may be an existing one (the artist must be an image) or a new, specific reason such as VolumeRendering; this is a decision for review. Without any graphics adapter the volume cannot be drawn at all, so export must fail for it or omit it with a warning, and the choice should be stated.
Possible duplicates and overlaps
Add isosurface chart type #140 and Add volume slice chart type #141: these share the volume grid and the value array; Plotly's volume trace is in fact a stack of isosurfaces.
Add voxels chart type #143: a voxel plot draws opaque boxes for selected cells of a volume, a discrete alternative to a rendered cloud.
scalar_image: the existing raster artist; a maximum-intensity projection along an axis is a scalar image computed in the facade.
Add consistent opacity/alpha properties to artists #34: opacity of image artists, and the translucency limitation recorded in ADR 0013, bear directly on compositing a volume with other translucent artists.
Add a colorbar node #8 and Consider custom colorbars and classification key legends #24: the transfer function should be shown by a colourbar with an opacity ramp, which may need a variant of the colourbar.
Alternative approaches
Approximate rendering by many translucent isosurfaces, as Plotly does: it reuses Add isosurface chart type #140 and avoids a raymarching pipeline, but needs correct ordering of many translucent layers, which the current renderer does not provide, and gives banded results.
Approximate rendering by many translucent axis-aligned slices (texture slicing): simpler than raymarching and expressible as stacked images, but shows artefacts when the view direction is oblique to the slices.
A dedicated raymarching pipeline, as sketched: correct and fast on a graphics device, at the cost of a new shader path that the exporter can only rasterise.
