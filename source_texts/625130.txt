Near as I can tell, mx_hash_int is implementing the exact same thing as the hash function inside OSL. That seems fairly trivial to add, and that would eliminate the need for all the code in this patch that is "below" mx_hash_int.

Note that the very definition of cellnoise (which is in MaterialX, and I presume is identical to that of OSL) serves the same purpose as this -- returning a deterministic uncorrelated [0,1] range value for each "cell" [i,i+1)^N in the volume. And that appears to be exactly what is at the heart of this construct and how it's used.
I feel like maybe an opportunity was missed here, where the specification of the worley functions in MX could have simply stipulated that the random point positions within each integer lattice cell were by definition identical to the cellnoise results for the contents of the cell. That would allow the top level of the mx_worley_noise_TYPE functions to call cellnoise to get the offsets and thus eliminate the majority of the lines of code in this module, as well as guaranteeing use of any carefully optimized cellnoise implementations in the {CPU, SIMD, or GPU} inside OSL or any other languages. Expanding the entire implementation out in shader source code down to every last bit twiddle seems very unlikely to be as efficient as the versions we've already optimized behind the cellnoise implementations.
The whole idea of cellnoise, back from when I first implemented it in PRMan (circa 1996?) was to be a "primitive function" from which you could build up higher level things like worley patterns, without having to get lost in the bit-by-bit details. This is literally what it was born to do!
Is it too late to allow for changes in the canonical pattern in order to pave the way for all the benefits of having cellnoise and worley overlap in their implementation and results?

In MaterialX, there are only versions of cellnoise which return a single float value. They boil down to a simple hash function on the cell location. It would be good to extend the GLSL noise library to include versions that returned a vec2/vec3/vec4 for the "offset" inside the cell. If OSL versions already exist for these functions, it would be ideal to use them for multiple reasons. These would be perfect for the Worley noise implementation (as Larry points out).
Maybe a future spec of MaterialX could also expose the cellnoise functions that return vector types.
The MaterialX GLSL implementation for Worley Noise would need to be patched with the OSL hashing functions. It's not too late to change the reference implementation (IMO).
