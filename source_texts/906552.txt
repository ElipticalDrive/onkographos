In one sentence: Open a complete automated fiber collection (hundreds of thousands of fibers) in VC3D instantly, see the fibers crossing each CT slice, and pull any single fiber into Line Annotation, without importing the collection in the project.
One real example: Starting with an automated fiber collection of PHerc. 0175A (61,486 fibers, 3.9 GB as .afv), I opened it in VC3D next to the CT. It draws every fiber crossing the current slices (1,112 in XY and 3,520 in YZ in the screenshot) and lists all fibers by length in the dock.
Before: The only way to see such a collection in VC3D was to import its JSON as native annotations: one file per fiber, and minutes of loading before anything was displayed. Every fiber then became an editable annotation.
After this PR: VC3D opens an .afv file, a single read-only file holding a whole automated fiber collection, by reading only its metadata and one catalog page, then draws in each planar view (oblique included) only the fibers crossing the current slice. A dedicated renderer with its own caches keeps the views responsive with thousands of fibers on screen. The dock lists fibers by length, filters by minimum length and H/V, selects a fiber by clicking its trace, and Open in Line Annotation copies just that fiber into the editable annotations, even without a Lasagna dataset (automated fibers do not use lasagna to be created in the first place, so this is a workaround for scrolls without lasagna data).
Proof:
With rainbow colors: 4,095 fibers drawn in a zoomed view (top), 27,183 over a whole slice (bottom).
A fiber picked in the dock and opened in Line Annotation, on data without Lasagna. The strip shows the notice "No Lasagna normals: cut orientation follows the curve, not the sheet."
The dock is shown or hidden from View → Fibers → Automated Fiber Volume, next to the native fiber docks.

Why / where this is useful: Automated fiber tracing produces hundreds of thousands of fibers per scroll region. VC3D's native fiber annotations aren't built for that: importing a collection of more than 300k fibers and 8M points took over 8 minutes and created one file per fiber before anything showed up. With this PR, the whole collection opens instantly and can be browsed on the CT, and only the fibers worth correcting become editable annotations.
I personally verified that the example and proof above were produced by this PR on the stated data.
Details
Data: the .afv file used here is the one I submitted on ash2txt.
Format: one SQLite file with an RTree over blocks of at most 256 segments. The format is documented in volume-cartographer/docs/fiber-collections.md so that tracing pipelines can write it directly.
Commits: the .afv reader (core); a display-only frame so stored curves can be shown in Line Annotation without Lasagna normals (lasagna); the VC3D dock, overlay and Line Annotation entry point (VC3D).
Rendering and cache: each view keeps a 32 MiB cache of spatial-index rows and decoded fiber blocks around the current and neighboring slices, so panning, zooming and changing slice reuse data already read. With All fibers, zooming or panning inside the slice already loaded makes no new query. The fiber layer is drawn once per view change into an image, reused while CT tiles arrive, instead of redrawing thousands of polylines each time.
Tests: ctest -R test_fiber_collection writes small .afv files and checks the reader: exact clipping, sampling, filters, cached against uncached results, catalog order and rejected files. The screenshot was taken on macOS arm64.
Dependencies / CI: SQLite with RTree is added to the Debian, Homebrew and vcpkg dependency lists. The published Linux CI image (vc3d-deps/linux) has no libsqlite3-dev, so the Linux jobs install it, as they already do for valgrind. Once libsqlite3-dev is added to vc3d-deps/linux/install-deps.sh, those steps can go. Windows (via qt6-base) and macOS (via opencv → vtk) already have SQLite.
Limitations: planar CT views only; one .afv per project; Save Project As does not copy the attachment; each view keeps at most 8 MiB of visible geometry and says so beyond that; The automated fibers volume are read-only until I figure out the best way to make them editable like native annotations.
Follow-up: a stacked PR uses the same .afv files as Spiral Fit input.
Current scope
For now, Automated Fiber Volumes are read-only in VC3D. You can open any of their fibers in Line Annotation, or use the whole catalog as a Spiral Fit input next to the native fibers (#1932).
This is on purpose: I don't know yet how this data will be most useful, and I don't want to decide too early how it should be used. I see it as raw data, with native VC3D fibers acting as overrides on top of it, but that isn't settled yet. That's why this is still a proof of concept of what large fiber volumes could become. Most of the work here is the format itself and a dedicated renderer that can display that many fibers.

core: add a reader for Automated Fiber Volumes (.afv)
…

```
An .afv is a single read-only SQLite file holding a large fiber
collection, written outside VC3D: exact binary64 geometry split into
blocks of at most 256 segments, an RTree over block bounds, and one
annotation per fiber. The format is documented in
docs/fiber-collections.md.

vc_fiber_collection is a small reader depending only on SQLite. It
serves a length-sorted catalog and view queries that return the visible
runs of fibers crossing an oriented slice, with exact clipping, optional
stable per-fiber sampling, a byte budget and a bounded cache.
test_fiber_collection writes small .afv files in that format and checks
the reader against them.

SQLite with RTree is added to the Debian, Homebrew and vcpkg dependency
lists. Until the published Linux dependency image includes it, the Linux
CI jobs install libsqlite3-dev themselves, as they already do for
valgrind.

Co-authored-by: Cursor <cursoragent@cursor.com>

```
Adds an Automated Fiber Volume dock (File > Open Automated Fiber
Volume..., View > Fibers, or --fiber-collection) that attaches one .afv
per project, read-only, without importing it:

- a catalog of fibers sorted by length, with minimum length and H/V
  filters;
- an overlay on planar CT views, including oblique slices, drawing only
  the fibers that cross each slice, with an optional per-view limit;
- selection from a catalog row or by a plain left click on a trace. The
  click is only used once native tools, collection points and fiber
  annotation have declined it, and never during segmentation editing,
  line placement or a drag. A slider follows every stored point of the
  selected fiber;
- Open in Line Annotation, which copies only that fiber into the
  editable annotations and fits it in both strips. Without a Lasagna
  dataset the strips use the display-only frame from
  lineModelForInspection() and show a notice.

The attachment (relative path and UUID) is saved next to the project.
Overlay controllers can now skip unchanged rebuilds through
needsOverlayRebuild(), which defaults to rebuilding.

See docs/fiber-collections.md.

Co-authored-by: Cursor <cursoragent@cursor.com>

  1. [P2] Opening one new AFV fiber reloads all existing native annotations.
     The new entry point calls the bulk importer, which synchronously rereads every native/external fiber file, clears alignment and geometry caches, and republishes the entire fiber list.
     Clicking successive unimported fibers therefore causes project-wide work on the GUI thread, potentially including existing broken-link prompts. The importer already behaved this way; 
     this PR introduces a frequent browsing operation that invokes it. Prefer a shared single-fiber import/update path that preserves unaffected caches.
