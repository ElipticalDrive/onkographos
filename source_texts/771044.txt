Summary
Generate WebGPU 3D texture mipmaps with a texture_3d<f32> shader and render every depth slice of each destination mip, instead of binding a 3D view to the 2D mipmap shader.
Allocate and expose mip levels based on width, height and depth; keep the existing 2D path unchanged.
Invalidate cached mipmap bindings when a GPU texture is recreated and document the depth-aware behavior of RawTexture3D.
Add a browser regression that checks slice values, depth-only volumes, updates, recreation and WebGPU validation errors.

Request substantial changes
Value assessment — This fix is needed: the old path cannot correctly generate mipmaps for 3D WebGPU textures, and depth-aware allocation plus per-slice rendering addresses the root issue for the tested RGBA8/POT case.
Design assessment — A dedicated 3D pipeline is the right layer, but the implementation assumes every accepted raw-texture format is filterable floating point. That is not true for the existing public API. Mip-count ownership is also split: allocation computes the correct count, while InternalTexture.mipLevelCount is synchronized only at initial raw-3D creation.
Hot-path assessment — This path can run on every RawTexture3D.update(). The per-slice render passes are inherent to this render-based approach; the per-update descriptor/view creation is avoidable but secondary to the correctness blockers below.
Findings
High — unsupported texture formats reach the new float/filtering pipeline. createRawTexture3D accepts integer formats/types and TEXTURETYPE_FLOAT, but generate3DMipmaps always binds texture_3d<f32> to a linear sampler and writes a float fragment output. Integer formats require typed i32/u32 inputs/outputs and non-filtering access; 32-bit float formats require the optional float32-filterable feature for this sampler. Valid API inputs therefore produce WebGPU validation errors. The existing integer-format discussion is correct; the same guard/variant is also needed for float32 on devices without that feature.
Medium — mipLevelCount becomes stale after a 3D texture resize. A 4x4x4 raw texture starts at 3 levels, but texture.updateSize(1, 1, 8) allocates a 4-level GPU texture while leaving texture.mipLevelCount at 3. Synchronize this field in the common allocation/resize path and update its declaration comment, which still says only raw 2D and 2D-array textures have a correct value.
Medium — the createTexture(ImageBitmap, ..., is3D=true) branch remains wired to the 2D generator. The method now computes a depth-aware count but still calls generateMipmaps, whose shader is texture_2d<f32>. Route this branch to generate3DMipmaps or reject that input combination explicitly.
Better approach — Centralize 3D mip capability selection in the allocation/generation layer: select a typed generation implementation per GPUTextureFormat (or explicitly disable/reject unsupported generation), and update InternalTexture.mipLevelCount whenever dimensions/allocation change. Extend the browser regression with integer, float32-without-filterability, resized depth, and at least one NPOT volume.
Open question — If generated mipmaps are intentionally unsupported for integer 3D textures, should the public API throw, or force generateMipMaps=false with the repository-standard warning behavior?

Thanks for the correction. I found three remaining correctness blockers in the sampler-free textureLoad path:
Odd/NPOT extents drop the trailing texel. The shader uses origin = destinationPosition * 2, while each destination mip extent is floor(source / 2). For a source extent of 5, the generated coordinates only read origins 0 and 2, so texel 4 is never sampled; the clamp cannot recover a coordinate that is never generated. The existing odd-depth filterable test expects the edge contribution, but the typed tests only cover even/POT extents. Please preserve the existing NPOT reduction semantics and add a typed odd-extent regression.
Signed integer averaging is incorrect for mixed signs. Dividing every sample into quotient/remainder parts before combining loses cancellation across the quotient boundary because WGSL signed division truncates toward zero. For [8, -1, -1, -1, -1, -1, -1, -1], total / 8 should truncate to 0, but the shader computes 1. Please use an overflow-safe reduction equivalent to dividing the combined total once, and cover mixed-sign data.
The float32 variant can overflow while computing a representable average. It sums eight full texels and multiplies by 0.125 afterward; eight values of 2^126 should average to 2^126, but the intermediate sum reaches/exceeds the f32 limit. Please use an overflow-safe averaging order and add a high-magnitude finite-float regression.
Thanks for pushing this path forward!

Request substantial changes
Value assessment — The follow-up commit addresses the previous validation, ImageBitmap, resize metadata, and NPOT coverage findings. Typed 3D mipmap pipelines are the right direction.
Design assessment — The overflow-avoiding quotient/remainder reduction is valid for unsigned integers, but it does not preserve WGSL's truncate-toward-zero result for signed values when the quotient and combined remainder have opposite signs.
Hot-path assessment — This remains texture-update work rather than a per-frame cost unless callers update the volume each frame. The new issue is correctness, not avoidable overhead.
Finding — High: Signed integer mipmaps are incorrect for mixed-sign texels. For [-9, 7, 0, 0, 0, 0, 0, 0], the expected reduction is truncate(-2 / 8) = 0; the shader computes (-9 / 8) + ((-9 % 8 + 7 % 8) / 8) = -1. The regression only uses nonpositive signed samples, so it misses this branch of the arithmetic.
Recommended change — Keep the overflow-safe quotient/remainder accumulation, but apply the correction required when the integral quotient and residual fraction have opposite signs, or use another overflow-safe reduction that is exactly equivalent to truncating the total sum divided by eight. Add a mixed-sign signed-integer test such as the input above.

Thanks for the correction. One NPOT integer case remains:
[P2] Keep fractional precision across all interpolation axes. The odd-size path calls interpolateInteger successively for X, Y, and Z, and each call returns an integer, so it truncates before the next axis. For a 5x5x1 unsigned texture at mip destination (0, 0), both X and Y weights are 3/4. With contributing texels [0, 0; 0, 2], the destination-centered result is 2 * 3/4 * 3/4 = 18/16, which truncates once to 1; the shader truncates the second row to 1, then truncates 1 * 3/4 to 0. The current regressions only make one axis nontrivial, so they cannot expose this. Please carry quotient/remainder (or equivalent rational precision) through all three axes and truncate only at the final output, with a multi-axis NPOT integer readback test.
Thanks for pushing the typed path forward!
