VC3D: Fiber Map workspace (interactive fiber network unroll)
Adds a permanent Fiber Map tab to VC3D: an interactive 2D map of manually linked
H/V fiber networks, unrolled about the scroll umbilicus. It is a C++ port of the
fiber_network_unroll.py review tool's top_clusters.png view, live against the fibers
loaded in the app.
Note: after #1454 was squash-merged, this branch was rebuilt from main as four
reviewable commits on 2026-08-21; the previous head is preserved at the tag
archive/fiber-map-workspace-20260819. A comment below maps every prior finding to
its fate. The three core-side files the old branch carried are gone — that work was
lifted into #1454 and is upstream.
What it does
Layout (vc3d::fiber_map::buildLayout, FiberNetworkLayout.{hpp,cpp} — byte-identical
to the reviewed tag): extrinsic unroll — x = unwrapped angle about the umbilicus × the
network's median radius, y = z. Per-fiber whole-turn offsets are snapped by walking the
branch-link graph Prim-style (best-agreeing link first), so crossings coincide and loops
close by construction; links whose endpoints still disagree by more than 0.25 turns are
flagged suspect. Networks are packed side by side, ordered inner→outer by median
umbilicus radius on a fixed tick grid. Traced runs draw solid; interpolation-only runs
draw faint and dashed. Line-point tails are clipped to the outermost control points,
keeping the one sample beyond each so a run still reaches them.
Workspace (FiberMapWorkspace.{hpp,cpp}): QGraphicsView map plus a left "Fibers"
dock grouped by network. Clicking a fiber in the list highlights it in the map and vice
versa; the highlighted fiber shows its control points, and ctrl+right-click on one
offers "Go to control point N in <fiber>". Right-drag pans and the wheel zooms,
matching the volume viewers. Link markers reuse the line-annotation branch palette;
colours follow the application theme in light and dark. Toolbar: top-networks and
min-fibers spinboxes plus an explicit Rebuild layout button.
Stable identity. Runtime fiber ids are reassigned on every package load, so the
snapshot and layout carry each fiber's file name and the control-point action resolves
it through fiberIdForFileName() when the action fires. A stale map cannot navigate to
whatever fiber inherited an id.
Staleness: one derived decision
The layout never rebuilds itself, and fiber edits do not notify the workspace at all:
there are no connections to the controller or to CState. The controller keeps counters
that are cheap to bump — the fiber generation (bumped at exactly two mutation sites),
a package counter, and #1454's umbilicus counter — plus a stat()-level fingerprint over
the resolver's own candidate scan, covering the umbilicus file changing underneath VC3D.
The workspace compares them at the moments that matter: on tab show, on rebuild, and
before acting on a click, a fiber-list selection, or a control-point menu action. The
accepted cost is deferred detection — a tab already visible when something changes keeps
its picture until the user does something.
The whole decision is one pure function of two dependency sets
(FiberMapStaleness.hpp), so each arm is asserted rather than read:
a different package, or a different grid (voxel counts), leaves the layout
meaningless — geometry unrolled over one set of voxels says nothing about another —
so it is cleared;
changed fibers, a changed umbilicus, a changed voxel size, or changed
layout settings leave it out of date: the banner says so and the map refuses to
act, but the geometry survives for the rebuild. The voxel size belongs here whether or
not the umbilicus scale came from it: the layout's smoothing sigma, resample step,
label pads, panel tick and minimum gap are all physical quantities converted through
that figure. PHerc0139_ds2 holds two volumes of one scan with byte-identical voxel
counts and recorded voxel sizes 2.5% apart, and switching between them marks the map
stale rather than discarding it.
Two structural changes relative to the reviewed tag, both from the same invariant —
staleness is derived from the dependency comparison wherever a dependency can express
it, and latched only where it cannot:
The stale reason is a member, not the label's text — and the latched reason is a
second member beside it, so a higher-priority derived reason displayed over a latch
and later reverted resurfaces the latch's own wording. The status label's five
writers are enumerated in the workspace commit, and rebuildLayout()'s last act is a
full dependency refresh, so a build summary can never be what a stale map is left
saying — the fix for the final review round's finding 3, made structural rather than
patched. The mid-build umbilicus race is expressed as data for the same reason: the
fingerprint is recorded before the snapshot parses the file, so a rewrite the token
can see (size or mtime moved — its stated contract) leaves the recorded token
disagreeing with the disk and the end-of-rebuild refresh raises the banner through
the ordinary arm.
The settings spinboxes join the dependency value instead of latching a flag. A
setting changed and changed back reads as current again, as does one scan's volume
switched away and back — a derived reason clears itself when its cause reverts. The
one latch left is the menu callback's file-name fallback, which fires only when a name
stops resolving under an unchanged generation — an invariant violation nothing in the
dependency sets can prove wrong, so only a rebuild clears it.
An empty layout is still a built layout, tracked separately from "nothing built yet" — a
map built before an umbilicus was attached would otherwise go on reporting that it found
none indefinitely.
Every interaction is gated, including the fiber list. The currentItemChanged
handler evaluates without mutating and queues the destructive half for the next turn of
the event loop, because a clear would delete the QTreeWidgetItem the signal is still
being delivered with. The control-point menu callback captures the full dependency set
at menu-build time and re-compares through the same shared decision when the action
fires, applied non-destructively inside menu.exec()'s nested event loop.
Data and units
LineAnnotationController::fiberMapSnapshot() exports geometry, per-segment traced
flags, branch links (pending included), the umbilicus and the frame it is in.
Umbilicus framing is the shared implementation's job, end to end. The resolver
picks the file (resolveScrollUmbilicus, umbilicus: frame metadata, project attachment, shared resolver #1454); deriveUmbilicusScale() carries its
coordinates into the fibers' frame — stamped grid dimensions (exact integers), then
the stamped voxel size, then the power-of-two grid inference — and
decideUmbilicusLoadAction() says what may be acted on. Fiber geometry is never
consulted: where annotation happens to reach says nothing about the grid the umbilicus
was drawn on. A stamp naming a volume this project has is cross-checked against it via
core umbilicusStampContradiction(), and a contradicted stamp — dimensions or voxel
size — is refused outright with the helper's reason. The old branch's inline copy of
this check refused only the dimension case (the voxel-size case warned and scaled
anyway — the final round's finding 1) and skipped the dimension check entirely when
the named volume's voxel size was unreadable; both fail-opens are gone by construction.
A stamp naming an unattached volume resolves but is labeled unverified; a registered
volume (transform.json) is called out as outside what a scalar mapping can express.
UseLegacy is refused here deliberately: the legacy reading is line annotation's
compatibility path (its registration inverse or raw points) and this consumer has
none, so the pre-rebuild status line words an unstamped file conditionally —
"(unstamped — frame must be inferred)" — rather than calling usable a file a rebuild
may refuse.
Voxel size is never assumed. It comes from deriveAnnotationFrame() (umbilicus: frame metadata, project attachment, shared resolver #1454,
via the controller's annotationFrame()): the exact coordinate factor from the
open-data tags, else the store's own pyramid position — never a resolution ratio where
something exact was said. The layout computes in voxels; physical units appear
only in labels, and fall back to vx when the voxel size is unknown rather than
printing a wrong centimetre figure.
Testing
test_fiber_map_staleness (16 slots): every arm of the dependency decision, including
the new ones — settings changes mark stale and revert to fresh, changed fibers outrank
changed settings in the naming order, and the unknown→known voxel-size transition (an
untagged store derives factor 1 with full extents under umbilicus: frame metadata, project attachment, shared resolver #1454's exact-factor
semantics) marks stale in both directions without clearing. Every new arm was
mutation-checked: deleting the settings arm fails exactly the two settings cases,
reordering it ahead of the fibers arm fails exactly the ordering case, and turning the
voxel-size arm into a clear fails exactly the two relabel cases.
test_fiber_network_layout (7 slots, needs -DVC_TESTING=ON): network filtering,
whole-turn offset snapping and loop closure, suspect-link detection, pending-link
plumbing, units and tail clipping, traced/interpolated run splitting, and voxel
geometry being independent of the voxel size.
Suite green at each of the four commits individually: 150/150 after the first two,
151/151 after the tests land (ctest -LE network; exclusion by label, since
-E network also matches this PR's own layout test). No new warnings.
Headless launch with a project loaded (--volpkg, offscreen): zero umbilicus
resolution and zero fiber-map log lines at startup — the status lookup is structurally
reachable only from tab show and interaction, and neither fired.
Read-verified only: the widget wiring around the staleness decision. The offscreen
controller fixture the earlier review discussion pointed to did not survive umbilicus: frame metadata, project attachment, shared resolver #1454's
restart, and a CState-plus-package harness is beyond this PR; the decision itself is
unit-tested, and the label has three writers, enumerated in the workspace commit.
Known gaps
WindingMark::number is computed and tested but not rendered: the gridlines are
drawn, the numbers beside them are not. The reference script labels them and this
should too; deliberately not added without seeing it on screen.
Label chips do not avoid each other (the reference script's greedy collision layout is
deliberately not ported); the panel ground and z-extent lines are the only framing.
Frame equality is not pose proof (final round, finding 2, inherited from umbilicus: frame metadata, project attachment, shared resolver #1454):
AnnotationFrame carries no origin or pose, so equal voxel counts and voxel size are
also consistent with a crop or a registration, and a switch to such a volume would
leave the map looking fresh. Fixing it needs volume-identity plumbing beyond this PR.
Smaller declared residuals — the fingerprint's metadata-token limits, the
registered-volume note not being a tracked dependency, tag edits over-bumping the
fiber generation, and the un-enumerated remainder of transient _fibers windows —
are listed at the end of the finding-fate comment below. Happy to file any of these
as tracked issues.

All four of your points are implemented, across three commits on top of the original
workspace commit. Taking them in your numbering:
1. Runtime ids should be mapped to filenames as the persistent ids. Done. The
snapshot and the layout now carry each fiber's file name, and the ctrl+right-click action
resolves it through a new fiberIdForFileName() when the action fires rather than using
the id captured when the map was built. If the file is gone the action marks the map stale
and logs instead of navigating. Combined with point 4, a stale map also refuses to act at
all, so the "opens the wrong fiber after a reload" path is closed from both ends.
2. Don't silently assume a resolution; work internally in base voxels and use units for
display, falling back to vx. Done, in both halves.
FiberMapSnapshot::voxelSizeUm is now std::optional<double> with no default. It comes
from the volume's open-data coordinate identity, else the volume's own level-0 resolution
(voxelSize() / 2^baseScaleLevel()), else it stays unset — the 2.4 µm default is gone.
The layout then computes in voxels end to end: the cm-suffixed fields became voxel
fields, the conversion is gone, and the tuning parameters (smoothing sigma, resample step,
label pads, panel tick, minimum gap) are passed in as voxel quantities, derived from their
physical intents when the voxel size is known and taking documented defaults equal to
their 2.4 µm values when it isn't. Physical units now appear only in labels, and where
the voxel size is unknown they read vx — a network header shows r ≈ 5167 vx instead of
a centimetre figure that would have been wrong.
I split that into two commits so the wide unit conversion is revertable on its own, and
held it to "no change for a known voxel size": the pre-change layout was compiled beside
the new one and six synthetic scenarios run through both, matching structurally with a
worst deviation under 4e-13 cm (multiply re-association only).
One consequence worth flagging: the frame label no longer prints a µm figure when the
scale came from stamped dimensions, since that figure played no part in the mapping — it
names the grid instead (umbilicus: 8174×8174×18946 grid → ×4), which is what the mapping
actually used.
3. Do we need scale guessing? Not from the fibers, no — that logic is deleted. Where
the annotation happens to reach says nothing about which grid the umbilicus was drawn on,
and using it failed in both directions on real data (an earlier coverage score picked a
too-large scale and made the plot look like a 3D scroll; the intersection-over-union
version that replaced it rejects a legitimate umbilicus whenever annotation covers little
of the scroll, which is what the automated review caught).
What replaced it is deterministic rather than a guess: stamped grid dimensions against
the fibers' grid — exact integer ratios, no micrometres in the geometry path at all — else
the stamped voxel size, else identifying which power-of-two downsample of the fibers' grid
the points fit inside and nearly fill (≥60% of that grid's z extent; since candidates sit a
factor of two apart, that bound makes the match unique rather than needing a tie-break),
else refuse with a message naming the remedy. On PHercParis4 the dimensions give exactly
×4, which is the value the old heuristic was guessing at.
4. Don't add overhead/hooks; increment a generation number so the unroll can check
whether it is based on stale data when opened or refreshed. Done exactly that. The
workspace no longer connects fibersChanged / fiberSaved / fibersDeleted at all;
LineAnnotationController exposes fiberDataGeneration(), bumped where the loaded fiber
set changes (emitFiberSummaries(), which every in-memory mutation already routes
through, plus the save path). The workspace records the generation its layout came from
and compares it on tab show, on rebuild, and before acting on a click or the context menu
— that last one because a change while the tab is frontmost would otherwise leave a stale
map interactive, which is the same hazard as point 1. Umbilicus status is resolved at most
once per generation, and the startup path no longer touches the filesystem at all (checked
on a headless launch: zero umbilicus resolution before the tab is opened).
Also in this stack since you last looked: link markers now use the line-annotation branch
palette so a crossing reads the same here as in the slice views, the map follows the
application theme in light and dark, right-drag pans as in the volume viewers, connected
components are called networks throughout rather than clusters, and a fiber-selection
bug is fixed: QGraphicsPathItem::shape() ignores that a pen is cosmetic and strokes the
path with the pen width taken as scene units, so every fiber carried an invisible
clickable ribbon vastly wider than the drawn line and stacking order rather than proximity
decided which fiber a click hit. Selection is now decided purely by nearest-segment
distance.
Gaps I'd rather state than have you find: the voxel-size resolution and the cm/vx
display are compile- and read-verified only (the former needs a VolumePkg/CState
fixture, the latter lives in a QMainWindow, and neither fits the layout-only test
target), and the level-0 fallback hasn't been exercised against a real untagged or
non-2.4 µm store because none was available here.

Rebased onto current main (via the updated base PR), and all four review points are
addressed. Taking them in the order they compound rather than the order they were raised.
1 — the annotation frame was derived twice. The snapshot's voxel size honoured a stamped
source resolution and fell back to the store's level-0 resolution; its voxel counts were only
ever multiplied by an open-data scale factor, with no reference to baseScaleLevel(). On an
untagged rebased store that pairs a level-0 resolution with level-N counts, so the map
reported a scroll 2^N too short and handed deriveUmbilicusScale() a target grid that could
refuse a correctly stamped umbilicus over an axis-ratio mismatch the pairing had invented.
The shared derivation is in the base PR, since the function it corrects lives there; both of
this PR's inline copies now call it. Worth noting for review: the reviewer that found this
also flagged the ratio validation in fiberMapSnapshot() as a fourth instance. I don't think
it is — that block only fires when the three axis ratios disagree with each other, and
scaling all three by the same factor cannot change whether they agree. It deliberately
tolerates a uniform rescale, so it is untouched.
2 — the redundant bump on save completion. Removed, and its comment was wrong on both
counts. saveSessionAsFiber() does go through emitFiberSummaries(), and does so after
already adding or updating the entry in _fibers — so the mutation that prompted the save
had bumped the generation. The save changes nothing a snapshot reads: the task only writes to
disk, the result carries no fiber state back, and the fileName a later navigation resolves
by is assigned at session creation. The second bump made every save look like fresh fiber
data.
3 — staleness ignored the frame and the umbilicus. A rebuilt layout depends on the
coordinate frame the unroll happens in and on which umbilicus resolves, neither of which the
fiber generation covers.
They are not equally severe, so they aren't treated alike. Changed fibers or a changed
umbilicus leave the map out of date — the existing banner. A changed coordinate frame
leaves it meaningless, since geometry unrolled about one grid says nothing about another,
so that clears the layout outright, as does a package switch, where the fibers themselves are
gone.
Comparing the derived frame rather than the volume's identity is what makes this usable in
practice: two stores of one scan at different downsample levels derive the same frame, so
switching between them costs nothing, while a store of a different scan does not compare
equal. That behaviour is asserted in test_annotation_frame.
On the mechanism, since the generation counter here was a deliberate choice: fibers still use
it, with no hook on the annotation path. The umbilicus gets a fingerprint rather than a
signal because attaching, detaching or repointing it emits nothing at all — it is the
project's field plus a stat(), never the resolver's directory search, and a file found by
discovery rather than named by the project is out of scope and documented as such. Only the
package switch takes a connection, and only because it cannot wait for the next interaction:
leaving another scroll's fibers on screen until the user clicks is showing a wrong picture
rather than a late one. That slot drops the layout and does nothing else.
This also fixed the umbilicus status cache, which was keyed to the fiber generation and so
threw the answer away on every save to redo filesystem work that could not have changed. It
keys on the umbilicus fingerprint now.
4 — the control-point menu could act on a stale index. menu.exec() runs a nested event
loop, so the fiber set can change while the menu is open. Resolving the runtime id from the
file name already handled a reload reassigning ids, but not an edit changing the fiber's
control points, which would leave the captured index meaning a different point or none. The
generation is captured at menu-build time and compared before navigating.
Full suite 150/150. That count is one higher than I have been reporting, and the reason is
worth flagging: my sweeps used ctest -E network, which quietly matched
fiber_network_layout and excluded this PR's own layout test from every run I called green.
It passes, and the exclusion is by label now.
The patch tracer is still not converted to the shared resolver — noted in the base PR as a
follow-up, not done here.
