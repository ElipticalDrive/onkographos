Context
the reference package's headline is a GPU path tracer (global illumination, PBR/subsurface, water, volumetric smoke, EXR/AOV).
The 3-D tier is PyVista on VTK's OpenGL rasterizer. Verified 2026-10-25 (viz3d, VTK 9.6.2): the OSPRay module is
absent (vtkRenderingRayTracing will not import; no Plotter.enable_ray_tracing), so path tracing is unreachable
with the current dependency. This is an investigation / engine decision, not a feature.
Scope
Produce a written recommendation choosing one of: (A) adopt an OSPRay-enabled VTK via PyVista (reuses the
scene API as a render pass — but first determine it is installable in the viz3d pixi solve-group on CI
platforms); (B) a second rendering path / engine; (C) declare photorealism permanently out of scope. For
each: availability + cost, what it delivers vs the reference package §4, API impact, CI/baseline-testing. No dependency or code
changes in the spike.
Full brief: planning/3d/parity-tasks/task-8-path-tracing-ospray-investigation.md.
Definition of Done
A recommendation picks (A)/(B)/(C) with evidence on all four questions
For (A): a concrete yes/no on installability in viz3d on CI, with the residual gap after adoption stated
The comparison file §4/§5 rendering-quality caveat is updated to reflect the decision

Spike outcome — ratified: (C) photorealism out of scope for three_d, with a revisit trigger to (A)
Decision (maintainer-ratified, 2026-10-27). No dependency or code change.
Option (A) — OSPRay-enabled VTK via PyVista — is not installable today (concrete NO, all CI platforms).
Verified against conda-forge repodata and the live viz3d env:
ospray 3.2.0 and embree 4.4.1 both solve for win-64, linux-64 and osx-arm64 — the library is available on every CI platform, so arm64 is not the blocker.
But no distributed VTK is built with the OSPRay module: across every build of conda-forge vtk through 9.7.1, not one links ospray (RenderingRayTracing is compiled out). The live env confirms vtkmodules.vtkRenderingRayTracing is absent on VTK 9.6.2 (only the OpenGL2 rasterizer is present). Kitware's PyPI wheels and pyvista 0.48.4 (no enable_ray_tracing/ospray hook) are the same.
The only missing ingredient is a VTK compiled with VTK_MODULE_ENABLE_VTK_RenderingRayTracing=YES, which nobody ships — reaching it would need a from-source VTK build, infeasible for the pixi/CI model and out of scope for the spike.
Four questions, summarized:
(A): not installable; even if it were, delivers shadows/AO/GI/reflections but not PBR-subsurface/water/volumetric-smoke/EXR (partial §4 close), needs manual vtkOSPRayPass wiring, and ray-traced baselines become smoke-tests.
(B) a second engine / external path tracer: could close more of §4 but only by rebuilding what the reference tool already is — forks the scene model, heavy new dependency, non-deterministic CI. Disproportionate.
(C) out of scope: zero cost; Task 5 (sun/shadows/SSAO) is the honest rasterization-grade relief answer; keeps deterministic image baselines.
Why (C): three_d is the interactive scientific-visualization tier; photorealistic path-traced cartography stays with the reference tool. Residual gap: the entire §4 'rendering quality' row (path tracing, PBR/subsurface, water, volumetric smoke, AOV/EXR) remains out of scope by design.
Revisit trigger (pre-authorizing a move to (A)): because ospray/embree already solve on all three platforms, the sole blocker is the VTK build flag. If conda-forge or a Kitware wheel ever ships a VTK with the RenderingRayTracing module, reopen (A) — it then becomes a render_quality("raytraced") / photoreal=True render-pass toggle (builders untouched; tests gated on importorskip('vtkmodules.vtkRenderingRayTracing')), delivering shadows/AO/GI as a partial, honest §4 improvement.
