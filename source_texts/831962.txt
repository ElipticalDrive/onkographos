Owner
Makes the painterly viewport composite actually run, and run correctly, at the shipped composite/depth_test=true default.
Base: 5dfeb44b5b414d5f8cc2a21cdb4121fe8bab44da (origin/master at branch time).
Risk class: R3 — every code file is R2 (renderer/shaders), but tests/ci/check_gs_pre_upscale_hook.py is on the R3 "CI deterministic-check / release-gate machinery" list in .agentic/policy.json. Design record for that placement: #996 (written during implementation, not before — disclosed, not backdated).
Three defects, each hiding the next
A — the composite could never load its shader. _ensure_painterly_composite_resources loaded painterly_composite.{vert,frag}.glsl from disk at runtime and passed the raw text to shader_compile_spirv_from_source. Both files begin with a Godot ShaderRD stage delimiter (#[vertex] / #[fragment]), which is not GLSL, so SPIR-V came back empty and painterly_composite_failed latched. In an exported project the res://modules/... paths do not exist at all. The correct machinery was already in the same class — the embedded PainterlyCompositeShaderRD — but its entry point _ensure_composite_resources() was never called from anywhere.
B — the push constant was the wrong size. ERROR: This render pipeline requires (48) bytes of push constant data, supplied: (36). Where the 48 comes from: SPIRV-Reflect sizes a push-constant block as last_member.offset + RoundUp(last_member.offset + last_member.size, 16) - last_member.offset (thirdparty/spirv-reflect/spirv_reflect.c:2785-2803, SPIRV_DATA_ALIGNMENT = 16), so the block size is always rounded up to a multiple of 16. Godot adopts that reflected value verbatim (servers/rendering/rendering_device_commons.cpp:1292) and then requires an exact match (servers/rendering/rendering_device.cpp:4745). Nine floats = 36 → requirement 48.
C — found only after A and B were fixed. With the composite finally running it wrote every pixel and still produced nothing. An instrumented build that colour-coded each discard showed 337,459 of 518,400 pixels rejected by the scene-depth occlusion test and zero pixels surviving it — including in a scene with no geometry at all, where the depth buffer holds only the clear value. The composite linearized scene depth from raw camera-projection columns (abs(proj_32 / (proj_22 + raw))) instead of the depth-corrected pair the host derives once in interfaces/gs_scene_depth_linearize.h — the header that says "ONE derivation shared by the whole-pixel composite and the per-splat raster clip". It also hardcoded a 0.0005 bias where the shared constant is GS_COMPOSITE_DEPTH_EPSILON_VIEW = 0.01, and depth-tested unconditionally, ignoring composite/depth_test.
What changed
Route the composite at the embedded PainterlyCompositeShaderRD, which understands the stage delimiters, ships inside the binary, and is created on RD::get_singleton() — the device that owns the viewport framebuffer. Delete the unreachable runtime loader (load_graphics_shader, its only caller), its two orphaned on-disk shader copies, and the dead duplicate resource path.
Pad both sides of the push constant to 48 and assert it. check_gaussian_layout_sync.py now enforces the 16-byte rule on every registered push-constant struct — its own std430 engine rounds to the block's max member alignment (8 here), so it could not have seen this — and CompositePush is no longer on the deferred list.
Move viewport_blit.glsl's scene-depth linearize / sanitize / background-detect trio and the occlusion predicate they feed into shaders/includes/gs_scene_depth_guard.glsl, with every input passed as an argument, and call it from both composites. The painterly push constant now carries depth_linearize_mul / depth_linearize_add / depth_is_orthogonal from the one host derivation, the shared epsilon, and a depth_test_enabled flag plumbed from the same setting read the compute path uses.
GPU-001 follow-up: painterly composite bypasses the sRGB->linear source decode on the pre-upscale path — painterly splats blended as linear, then tonemapped #930's decode lands with it. Painterly output is premultiplied, display-referred, sRGB-encoded LDR and this pass always draws into the LINEAR pre-tonemap internal texture, so: unpremultiply, decode with the exact piecewise EOTF, re-premultiply. srgb_to_linear_exact moves from viewport_blit.glsl into shaders/includes/gs_srgb.glsl rather than being copied.
The composite is gated to the pre-upscale phase, because its destination is get_internal_texture() unconditionally; in the legacy post-scene phase (forward mobile / multiview / probes) that buffer has already been consumed, so those paths keep the present-redirecting compute composite.
Painterly renders nothing at the shipped default composite/depth_test=true: strict depth contract skips the composite (QA pin depth_test=false masks it) #987's root cause: render_painterly_or_baseline_stage never assigned raster_output.depth, while the baseline path publishes it through render_tile_fallback's out-parameter. That is why the strict scene-depth contract saw no source depth and skipped the composite at the shipped default — and why the render cache was invalidated every painterly frame (render_pipeline_stages.cpp:1906). Painterly's depth is the same normalized-linear texture both composites expand as mix(z_near, z_far, d), so it is the correct source depth.

Review of #999 raised fifteen findings. The correctness ones:

- **Orthographic fallback.** The push-constant fill derived the scene-depth
  pair unconditionally with a hardcoded `orthogonal = false`, even in the
  `scene_data == nullptr` branch, so an orthographic camera would get a
  perspective derivation of an ortho matrix -- re-creating blocker C in
  exactly the branch added to handle it. The compute composite deliberately
  does NOT derive when scene_data is missing. Now mirrors it: derive only
  from scene_data, and when there is none, fall back to z_near/z_far AND
  disable the depth test. The guard only ever removes fragments it can prove
  are occluded, so with no trustworthy depth description it must fail open,
  never blank the frame.

- **Cached render hid material edits.** #987's `raster_output.depth` fix
  newly lets painterly frames reuse the cached render, and the reuse
  signature has no PainterlyMaterial term -- so under a static camera a
  material edit would not reach the screen. `_on_painterly_material_changed`
  now invalidates the cached render. A material edit is an editor-rate
  event, so re-rendering once beats hashing a resource that changes one
  inspector drag at a time.

- **Blank evidence surface.** A successful painterly composite left
  `last_output_copy_attempted` / `last_output_copy_success` at false,
  because the `!composited` block is the only place they are assigned. Every
  QA surface saw "no copy attempted" for a frame that had just drawn a
  fullscreen pass. It read as clean only because `copy_failed = attempted &&
  !success` short-circuits.

- **Sampler free window.** The two composite samplers are created on the
  VIEWPORT device but were freed only inside `device_still_valid` (which
  tests `rd`), while the tail of `_shutdown_internal` clears their RIDs
  unconditionally -- a permanent leak in a window the composite now reaches.
  `_free_tracked_rid` resolves each RID's own owner device, so the frees
  move out of that branch.

Guard gaps the review found in the guards this series added:

- Six new anchors + six new mutations in check_gs_pre_upscale_hook.py for
  the contracts that were fixed but unguarded: the shared scene-depth guard
  include, the `depth_test_enabled` gate, the shared depth epsilon, the
  shared host derivation, and the setting plumbing. Self-test now flags
  25/25 reverting mutations (was 19/19).
- check_gaussian_layout_sync.py records why its new 16-byte rule cannot yet
  reach the deferred blocks (function-local structs the parser cannot read)
  rather than leaving the gap silent. Tracked as #1000.

Hygiene: regenerate docs/api/shader_reference.md with
scripts/generate_shader_docs.py instead of hand-deleting two sections;
delete the dead `composite_pipeline` member and its teardown; drop the now
unused `core/io/file_access.h` include; drop the redundant `% 16`
static_assert (the `== 48` one entails it and the guard enforces the rule);
drop the redundant per-frame pipeline warm-up and the now-unused framebuffer
format parameter; fix a whitespace regression in the layout guard.

Declined here and filed instead: #1000 (16-byte rule coverage for the
deferred blocks), #1001 (`blend_strength` is a hard-wired no-op; the pass
does not assert its shader/cache device matches `draw_device`).

Re-measured after these changes: every one of the sixteen coverage numbers
is identical to the pre-review run, and all twelve painterly-off captures
remain bit-identical to base.

* docs: correct the #1025 entry - FSR2 does not ghost, and the old text told users to avoid it

The moving-camera case has now been measured (#1025 comment 5751997279), on a
real scan, on both the base and #1026 binaries. The entry I shipped was a
prediction taken verbatim from #1026's section 8.1 row, and it was wrong in the
direction that costs a user a working feature.

- FSR2: NO ghosting. 0.000 frames of staleness at scale 1.0 across a slow pan, a
  normal pan and a dolly, at the floor set by an in-frame geometry control; at
  scale 0.5 the splat trail is at or below the control's in two of three motions.
- TAA: a real ~1.5 px trail, 0.27-0.87 frames stale, 6-26x the control, and it
  does NOT grow with camera speed because the variance clip is computed from the
  current frame.
- Base and #1026's head agree within 0.01 frames, so the jitter fix neither
  causes nor cures it.

The workaround change is the one that matters: it said "keep scaling_3d_mode =
bilinear at scale 1.0 and use_taa = false". Half of that was pushing users off
FSR2 for a defect FSR2 does not have. It now says use_taa = false, which is
Godot's own default, and states plainly that FSR2 needs no workaround.

Also corrected: the entry said fixing this "edits render_forward_clustered.cpp
and needs its own ADR". The ladder inverted under measurement - velocity
write-back does not require depth write-back, and it is not an engine-boundary
change, because the module already holds the buffers and the previous-frame
camera. What survives is the honest reason it is not alpha work: a wrong velocity
smears confidently and reads as a renderer bug rather than a missing feature.

The correction is recorded in the entry rather than silently swapped, same as the
#1030 direction fix.

And a coupling that was undocumented anywhere, now on the #989 entry because that
is where it will bite: the destination alpha #989 is about IS FSR2's reactive
mask. Godot has no dedicated reactive texture - params.reactive is an
alpha-swizzled view of the internal colour buffer, and the composite writes splat
coverage into that alpha. That is WHY splats do not ghost under FSR2. Whoever
fixes transparent_bg changes FSR2's temporal behaviour silently, and no test
would notice.
