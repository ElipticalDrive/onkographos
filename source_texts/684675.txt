Summary
Implements getDescriptorHandle on the Metal backend so bindless DescriptorHandles work for buffers, texture views, samplers, and acceleration structures. Before this change every Metal resource inherited the base SLANG_E_NOT_AVAILABLE, so bindless was unavailable on Metal even though the compiler/emit side already supports it.
Fixes shader-slang/slang#10842.
Motivation
On Metal, a bindless resource is referenced in an argument buffer by its raw native id — MTL::Buffer::gpuAddress() for buffers and MTL::ResourceID (from gpuResourceID()) for texture views / samplers / acceleration structures. The existing argument-buffer path in src/metal/metal-shader-object.cpp already writes exactly those values (buffer getDeviceAddress() + range.offset at :562, texture gpuResourceID() at :523, sampler at :546, acceleration structure at :588). A DescriptorHandle::value is a single uint64_t, and each of those native ids is a single 64-bit value, so the handle can carry the native id verbatim.
Proposed solution (Approach A1)
The handle's value is the raw native id/address — MTL::ResourceID is struct { uint64_t _impl; }, so ._impl is the 64-bit id; buffers use gpuAddress() + resolvedRange.offset. This is precisely what the arg-buffer consumer reads, so the host and device agree by construction. A static_assert(sizeof(MTL::ResourceID) == sizeof(uint64_t)) guards this equivalence so a future metal-cpp bump that widened ResourceID fails the build instead of silently dropping data.
No descriptor heap or slot allocator. The handle is derived directly from the resource's native id, so no descriptor slot is allocated or reclaimed; resource lifetime remains the application's responsibility, and this change does not alter the backend's existing residency mechanisms. This makes the Metal BindlessDescriptorSet much thinner than the Vulkan/D3D12 ones (which allocate heap slots) — it holds no per-set state.
Feature::Bindless is advertised inside the existing ArgumentBufferTier2 block. The backend already hard-fails device init below Tier 2 (src/metal/metal-device.cpp:93-101), and the pre-existing ParameterBlock arg-buffer path already calls gpuResourceID()/gpuAddress() unconditionally under that same gate — so bindless adds no new availability requirement.
Combined texture+sampler is intentionally not supported and keeps returning SLANG_E_NOT_AVAILABLE: a combined handle would need two 64-bit gpuResourceIDs (128 bits), which cannot fit in a single 64-bit DescriptorHandle::value. Tracked as won't-do in shader-slang/slang#11540.

The Metal overrides do not cache the handle (unlike Vulkan, which caches and frees on destruction): the value is a pure function of the resource's stable native id, so there is no allocated slot to reclaim and nothing to cache.
The Metal BindlessDescriptorSet keeps the vk/d3d12-shaped alloc*Handle surface for cross-backend consistency and to serve as the "bindless is enabled" gate that the resource overrides check — not because heap allocation is expected later; the raw-id model deliberately holds no per-set state (the vk/d3d12 m_device/m_desc members drive heap sizing and are absent here).
The acceleration-structure override is implemented for scope + vk/d3d12 parity but ships without a dedicated test: there is currently no bindless-acceleration-structure test for any backend (vk and d3d12 both ship allocAccelerationStructureHandle untested). The Metal test masks added here cover all existing applicable bindless tests (buffers/textures/samplers); a first-ever bindless-AS test — for all backends — is left as a separate follow-up.
Residency note
Metal has two residency modes, and this affects only the non-default fallback:
Residency-set path (default, GPUFamilyApple6+): every created resource is added to a device-wide residency set, so a resource referenced by a bindless handle is resident purely by existing. Bindless works with no extra wiring — matching D3D12/Vulkan, which also have no per-handle residency.
Per-encoder useResource fallback (SLANG_RHI_METAL_NO_RESIDENCY_SET, or no residency-set support): residency is driven by the argument-buffer binding path, which a bindless handle bypasses. Bindless-only textures are therefore not made resident in this mode (buffers are covered via pointer-field resolution, AS via the use-all-AS path, samplers are not MTL::Resources). Per Approach A1 the maintainer waived per-handle residency bookkeeping (resource lifetime/residency is the application's responsibility); this dependency is documented in the class doc comment rather than worked around.

Root-caused — and it turns out my earlier framing of the residency risk was the wrong lens entirely. Thanks for merging #807: with metallib_4_0 disabled the Metal device now reports Metal: supported (with bindless among its features) and my bindless cases executed for the first time. Exactly two fail — bindless-buffers.metal and bindless-textures.metal (1041 test cases | 1039 passed | 2 failed, 77 failed assertions).
Neither failure is a residency problem, and the interesting part is that Metal's DescriptorHandle ABI is not the one this test assumes.
What the shader actually receives
Compiling the failing test with the exact Slang the build fetches (build/_deps/slang-src/bin/slangc, 2026.12.2):
```
slangc tests/test-bindless-buffers.slang -target metal -entry computeMain -stage compute -o out.metal
```
```
[[kernel]] void computeMain(
    float device*                             result_1             [[buffer(4)]],
    texture_buffer<float, access::read>       buffer_1             [[texture(0)]],
    float device*                             structuredBuffer_1   [[buffer(0)]],
    uint32_t device*                          byteAddressBuffer_1  [[buffer(1)]],
    texture_buffer<float, access::read_write>  rwBuffer_1           [[texture(1)]],
    float device*                             rwStructuredBuffer_1 [[buffer(2)]],
    uint32_t device*                          rwByteAddressBuffer_1[[buffer(3)]])
```
Every uniform ....Handle becomes an ordinary directly-bound parameter with its own [[buffer(n)]]/[[texture(n)]] slot. There is no uniform/argument-buffer parameter carrying handle values, so the 64-bit values the test writes via setDescriptorHandle are never read. result works because it is bound with setBinding; the six handles are never bound to anything, which explains the zeros the CI run observed.
Importantly, that direct binding is intentional upstream, not a codegen bug — I initially assumed the opposite and was wrong. slang-emit-metal.cpp:149-153 deliberately unwraps DescriptorHandle<T> to T's layout before assigning slots, and tests/metal/entry-point-descriptor-handle-buffer.slang is a regression test (for #11066) whose CHECK lines require .Handle params to receive [[buffer(n)]]. So on Metal a top-level .Handle parameter is currently a normal bound resource, and setDescriptorHandle is simply not the way to feed it. Please read my earlier "residency waiver" comment with that correction in mind.
Why residency is not the cause
The runner is Apple Paravirtual device, argument-buffer-tier-2 without Apple6, i.e. exactly the !m_hasResidencySet per-encoder useResource path — so the suspicion was reasonable.
But the shader never dereferences a handle value at all, so residency of a handle target isn't yet reachable as a question. The zero reads are fully explained by the missing bindings.
I won't lean on "there was no residency warning" as proof: resolvePointerFieldResidency (src/metal/metal-shader-object.cpp:716-752) only inspects reflected ordinary-data pointer fields, and these directly-bound resource params never traverse that path, so its silence here is expected either way.
To be explicit: this run does not clear the residency question at all — bindless isn't being exercised, so nothing about residency was tested either way. And to correct another thing I had backwards earlier: this paravirtual runner (no Apple6) is already the !m_hasResidencySet fallback machine, since the residency set requires supportsFamily(GPUFamilyApple6) (metal-device.cpp:124-132). So what's needed to close the fallback question is a genuine argument-buffer handle test on this runner; separate Apple6+ hardware is what would validate the residency-set path.
A real bug this surfaced in my own patch
Splitting the six cases by the slot they land in is instructive:
Slang declaration
emitted MSL
correct 64-bit value
StructuredBuffer<float>, ByteAddressBuffer (+ RW)
float device* / uint32_t device* → [[buffer(n)]]
gpuAddress() ✅
Buffer<float>, RWBuffer<float> (typed)
texture_buffer<float,…> → [[texture(n)]]
a texture gpuResourceID ❌
My allocBufferHandle returns getDeviceAddress() + offset for all buffer kinds and explicitly discards format (metal-bindless-descriptor-set.cpp:31-33). For typed Buffer<float>/RWBuffer<float> that is the wrong class of value — those want a texture-buffer resource ID. My "format is irrelevant here" comment is therefore wrong, and the reviewer's byte-for-byte equivalence check didn't catch it because the pre-existing bound path has the same shape: metal-shader-object.cpp:562-563 also writes getDeviceAddress() + offset for TypedBuffer/MutableTypedBuffer. Matching that path is not validation.
Worth flagging separately: slang-rhi never creates a Metal texture-buffer object anywhere (no newTextureBuffer/textureBufferWithDescriptor in src/metal/), so typed Buffer<T>/RWBuffer<T> look like a pre-existing gap in the Metal backend, bindless aside. I'd rather not fix that here uninvited — it's your call whether it's in scope for #10842 or a separate issue.
Where that leaves the PR
I'm withdrawing the "just mask the tests" suggestion I was about to make — the PR advertises Feature::Bindless and marks four getDescriptorHandle APIs supported in docs/api.md, so deleting the only end-to-end coverage while keeping those claims would be hiding the problem rather than resolving it.
What I think is actually needed, and I'd like your direction before I spend the cycles:
Re-express the tests through the ABI Metal really supports — a ParameterBlock/argument buffer. A probe shows those handles do land as argument-buffer struct members (Params_default_0 constant* params [[buffer(0)]]), which is the representation this PR's raw ids are meant for. That would tell us which handle classes genuinely work end-to-end.
Fix the typed-buffer encoding (or explicitly reject typed buffers from getDescriptorHandle on Metal until the backend can create texture-buffer views).
Resolve the feature-advertisement question: Feature::Bindless is currently advertised from argument-buffer-tier-2 alone (metal-device.cpp:252). On the !m_hasResidencySet fallback, buffer handles may still be covered — resolvePointerFieldResidency walks reflected pointer fields and resolves raw addresses through m_addressToBuffer — but texture/sampler handles are the demonstrably uncovered class, since they aren't pointer fields and have no equivalent reverse lookup. If that's a genuine restriction, the feature gate should encode it rather than leaving it to a comment.
Happy to take any or all of those. I'd suggest (1) first, since it decides how much of (2)/(3) is real. If you'd prefer to hold #802 until Metal bindless has a settled story, that's a legitimate outcome too — the host plumbing here is a prerequisite either way.
Caveat on all of the above: I have no Metal hardware. Everything is either read from the CI job log or reproduced with the fetched slangc 2026.12.2 on Linux (source emit + reflection only) — I can't self-certify runtime behavior.
