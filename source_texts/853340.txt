Source: velt-lang/velt (the f16/bf16 types PR, linked below; design velt-lang/velt#2049). Not yet released.
Reference, types.mdx (number types table and the "Velt-only names" list): two new number types.
f16: IEEE 754 half precision (binary16): 11 significant bits, largest finite 65504.
bf16: bfloat16, f32's top 16 bits: 8 significant bits, f32's range.
They are storage types, made for model weights and other low-precision data:
An f16[]/bf16[] takes 2 bytes per element.
Arithmetic doesn't run in them: + - * / % **, comparisons and unary - widen the operands to f32, and the result is an f32. A literal beside one is an f32 too, so w == 0.1 is false, as in JS with a Float16Array element.
They convert to f32, f64 and number implicitly and exactly.
Into one only as converts: it rounds to the nearest value (ties to even) once, from the exact source. This holds from number, f32, any integer type, and between f16 and bf16.
A literal is its value rounded the same way. A literal that rounds to infinity is an error (literal out of range for f16``).
Bitwise operators reject them.
Equality, includes, indexOf, Map/Set keys and Object.is go by value, as for other numbers (-0 == 0; NaN is found by includes and as a key).
Printing, templates, String() and JSON.stringify show the value: ${0.1 as f16} is 0.0999755859375.
```
const w: f16 = 0.1;          // 0.0999755859375
const b: bf16 = 0.1;         // 0.10009765625
const x: f32 = w;            // implicit, exact
const y = w * w;             // an f32
const z: f16 = (w * 3) as f16;
const ws: f16[] = [1, 2.5, 0.1];
```
Not yet (later #2049 PRs):
compound assignment and ++/-- on an f16 place;
toBits/fromBits;
sort() without a comparator;
converting an any into one;
Atomic<f16> arithmetic (load, store, exchange and compareExchange work, on the bits).
velt check --ts reports f16/bf16 as not TypeScript types, suggesting number and Math.f16round.
Comparisons and collections (decided in review):
Comparisons of an f16/bf16 with a literal, a number or an f64 run in f64, which is exact, so the answer is always JS's for a Float16Array element: one == 1.00000001 is false for one: f16 = 1. With an f32 or another storage float they compare in f32. Arithmetic keeps the f32 literal (one * 1.00000001 is 1).
The search and key methods of an f16/bf16 collection compare a number exactly too:
xs.includes(0.1) is false for xs: f16[] = [0.1], which holds 0.0999755859375. xs.includes(0.1 as f16) is true.
The same holds for indexOf/lastIndexOf, Map.get/has/delete and Set.has/delete.
A Set<f16> holds f16 values: t.add(0.1) stores 0.0999755859375. So t.has(0.1) is false, t.has(0.1 as f16) is true, and the size is 1. Writes round as = does; lookups compare exactly. A JS Set of numbers has no equivalent.

Update (velt-lang/velt#2049, owner decision 2026-11-03): f16 and bf16 compute as number, the JavaScript model. This replaces the f32-arithmetic and literal-type rules described above, in this issue and in #73.
An f16/bf16 is a number with 16-bit storage, exactly like a Float16Array element:
Reading one widens it to number (f64), exactly. It also converts implicitly to f32.
Arithmetic is ordinary number arithmetic: w * 0.1, w1 + w2, w * w, w | 0 and ~w compute in f64 (bitwise ones with ToInt32), and the result is a number.
Comparisons are exact, so the answer is always JS's (one == 1.00000001 is false).
Storing rounds once: w = 0.1, w = x as f16, and compound assignment w op= x, which is w = (w op x) as f16 with the operation in f64. x can be any number type that converts to number exactly. w++ and w-- work the same way.
As expressions, assignments give the number before the store rounds it, as in JS: (w = 0.1) is 0.1, (w += 0.1) is the f64 sum, and ++w is old + 1.
Results are identical to Node's Float16Array for every operator and literal (Velt's tests sweep all 65,536 patterns), apart from which NaN bit pattern a store writes. That is implementation-defined in JS as here: Node writes 0x7e00, while Velt keeps the payload.
Velt's own f32 keeps f32 arithmetic. For f32 speed with f16 data, write (w as f32) * k. The fast path for AI kernels is the explicit f16x8/bf16x8 SIMD types (later).
Example:
```
const w: f16 = 0.1;      // 0.0999755859375 stored
const x = w * 0.1;       // number: 0.00999755859375
let acc: f16 = 0;
acc += 0.1;              // 0.0999755859375, as Float16Array's e[0] += 0.1
const s: number = w + w; // a number; `as f16` to store it
```

One more line for the f16 page (from the #2191 review): storing a NaN into an f16/bf16 keeps the NaN's sign and the top bits of its payload, quieted, as the conversion instructions do. Node writes 0x7e00 instead. JS leaves the encoding to the implementation, so code shouldn't rely on a NaN's bits (toBits()) after a store.

Performance note for the f16 page (owner decision on #2191).
Fast without changing results. One + - * / of two f16 values (or two bf16 values), or of one and a literal the type holds exactly (0.5, 2, -3, 65504), stored back into an f16/bf16 runs as fast as the f32 arithmetic it compiles to:
w = a * b, w += z, xs[i] *= ys[i], x * 0.5, x / 2;
one f32 operation, then one conversion instruction (vcvtps2ph on x86 with --cpu x86-64-v3, fcvt on arm64).
The results are still exactly what JavaScript's Float16Array stores (rounding twice through f32 is provably harmless for one such operation).
Slower, but exact. Anything else computes in number (f64) and stores through a slower exact narrowing on x86:
a literal the type can't hold (x * 0.999);
a number or f32 operand;
%, **, or a chain like a * b + c.
On x86 this costs roughly 2–4× the f32 path in vectorized loops.
In hot loops:
Write a constant as an f16 once: const k = 0.999 as f16; ... xs[i] *= k;. That rounds the literal once, so the result can differ from x * 0.999 in JavaScript, a choice you make visibly. It's also what Rust code has to do, since Rust has no f64 literal in f16 arithmetic.
Or compute in f32 explicitly: xs[i] = ((xs[i] as f32) * 0.999) as f16.
