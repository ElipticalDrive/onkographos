Tracking issue for concrete paths to the #60 goals (Milky Way scale, eventually Local Group). Ordered roughly by impact-per-effort, with the client-side ceilings that motivate them. Ideas 4–5 are the "server side component / precomputed frames" direction.
Current ceilings (measured from the code as of #130)
CPU octree rebuild — the octree is built in JS (worker) from a GPU→CPU readback of all positions, then re-uploaded. At ~1M particles the build takes on the order of a second, so the tree is dozens of physics frames stale. This is the hard wall for live-sim particle count.
Render readback — every frame does GPU→CPU mapAsync readback of positions, then re-uploads them to WebGL through three.js. ~16 MB/frame each way at 500k particles; scales linearly with N.
Octree buffer over-allocation — maxOctreeNodes = 8×N at 32 B/node = 128 MB at 500k, which is exactly the default WebGPU maxStorageBufferBindingSize. A 1-particle-per-leaf octree needs at most ~2×N nodes; combined with requestDevice limit raises this is ~4–8× headroom for free.
Client-side (prerequisites for any scaling)
1. Fix octree allocation + request adapter limits — small change, raises the slider ceiling from 500k to ~2M. (Ceiling #3.)
2. GPU-resident octree build — replace the CPU/worker build with a GPU pipeline: Morton-code particles → GPU radix sort → Karras-style linearized tree build → bottom-up mass/COM aggregation. Eliminates the GPU→CPU→GPU round trip and the stale-tree problem entirely. This is the standard approach in CUDA N-body codes (e.g. Bonsai). Realistic target: 5–10M live particles at interactive rates. (Ceiling #1.)
3. End-to-end WebGPU rendering — switch the canvas to three.js WebGPURenderer (R3F v9 supports it) sharing the simulation's GPUDevice, and render points directly from the storage buffer (or via a GPU→GPU copy into a three-managed buffer). Zero readback, zero CPU touch per frame. (Ceiling #2.)
Server-side / precompute (the orders-of-magnitude unlock)
4. Server-precomputed simulation, streamed playback. The in-browser "Pre-computed" mode already proves the playback model; move the compute off the client:
Run big simulations offline on a GPU box (CUDA Barnes-Hut / fast-multipole; existing codes like Bonsai or GADGET-4 can do 10⁸–10⁹ particles).
Store keyframe snapshots (positions at, say, 1–10 Hz sim time), compressed: quantized positions (12–16 bits/axis relative to an octree cell) + delta encoding gets you to ~4–6 bytes/particle/keyframe.
Client streams keyframes over HTTP range requests (fits the existing Cloudflare Pages/R2 deployment) and interpolates between them on the GPU — exactly the mix(prev, next, alpha) machinery that now exists in both backends (Add GPU render interpolation to Barnes-Hut backend for smooth 60 FPS motion #130).
Realistic target: 10⁷–10⁸ particles rendered from precomputed data, limited only by bandwidth and VRAM, not physics.
5. Hierarchical LoD tiles over the precomputed data (the 300B-star path). You never render 300B points — at galactic zoom a pixel covers millions of stars. Precompute an octree of aggregate tiles per keyframe (like Potree/3D-Tiles for point clouds, or Gaia Sky):
Each tile stores a representative sample of its stars + aggregate luminosity; deeper tiles refine.
Client streams only tiles that intersect the frustum at screen-appropriate depth — a few hundred MB of tiles gives the appearance of the full dataset at every zoom level, from galactic rotation down to a solar-system fly-in (issue goals? #60's LoD requirement).
The simulation itself can also be hierarchical: simulate 10⁷–10⁸ "tracer" super-particles for dynamics, and procedurally amplify to stars inside tiles at render time (standard technique in cosmology visualization).
6. (Less attractive) live server-side sim streamed over WebSocket/WebRTC — pays the latency/bandwidth cost every frame forever and needs a stateful GPU server; precompute + streaming (4–5) gives a better experience for the goals in #60, which are about watching evolution, not steering it. Noting it for completeness.
Suggested sequencing
1 → 2 (or 3) client-side to get to ~10M live, in parallel with a spike on 4 (offline sim of ~10⁷ particles + quantized keyframe format + streaming playback), then 5 for LoD.
