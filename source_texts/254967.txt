Gaussian Splatting data-texture reads can make WebGPU rendering substantially slower than WebGL2 on some GPUs. This change avoids unnecessary render-target usage for sampled-only data textures and adds experimental, opt-in GPU depth sorting that keeps the sorted indices on the GPU.
On an NVIDIA T400 with a static camera and about 932,000 splats, the texture change improved WebGPU performance from 14.5 to 54.3 FPS for an SPZ scene with multisample anti-aliasing enabled, compared with 58.2 FPS on WebGL2. This is hardware-dependent evidence, not a general performance guarantee.
GPU sorting remains off by default because it competes with rendering; the asynchronous CPU worker was faster during camera motion on the T400. Enable it before loading through GaussianSplattingMeshBase.UseGpuSort or a mesh's useGpuSort override. GpuSortMinFrameInterval can trade ordering freshness during camera motion for lower GPU cost; data changes bypass that throttle.
Sampled-only Gaussian Splatting data textures exposed through getters are no longer render-target-capable on WebGPU. Streaming atlases retain the render-target usage needed for GPU decoding. WebGL, Native, unsupported devices, streaming meshes, and custom scene render functions outside the frame graph retain CPU sorting. Enabling point splatting or disabling depth sorting also moves a GPU-sorted mesh back to the CPU path.
Local visualization coverage has two known limitations: the WebGPU Gaussian Splatting image-based-lighting shadow tests hang the D3D12 driver on the baseline as well, and the WebGL2 compound level-of-detail test is flaky on the baseline. GPU sorting for streaming remains follow-up work.

[Responded by Copilot on behalf of CedricGuillemet] Addressed the two remaining review requests in 9ad7ce2 and 5e881a6 (plus a clean merge of master in 87421c7).
The local scan and scatter passes no longer read past the storage buffers in the last partial workgroup: out-of-range threads use zeroed values and every thread still reaches the barriers. The other sort passes already guard their reads. The WebGPU integration tests (partial/full 1024-key blocks, scan chunk boundaries, plain/compound/SOG rendering) pass against the rebuilt shaders.
Added a warm compound Parse regression: the mesh is rendered (source applied, null part-index texture cached) while Parse restores the proxies, then the test checks that compound sorting receives the part-index texture and matrices, and that later proxy moves only re-sort. It fails if the first-matrix source invalidation is removed.
The first-matrix invalidation and the interval buffer cap were already addressed in 101d504 and abd74f7.

The Gaussian Splatting page did not cover the opt-in GPU depth sort from
BabylonJS/Babylon.js#19013, nor several features added since: loader
options, point splatting, the debugger, hosted streamed parts and the
streaming `splatBudget`. This brings the page up to date so users can
discover and tune them.

New or extended sections:

- GPU depth sorting: `UseGpuSort`, `useGpuSort`,
`GpuSortMinFrameInterval`, and the conditions that fall back to the CPU
sorter. A note says it is off by default and may change.
- Rendering and sorting settings, loader options and safe orbit camera
limits.
- Point splatting (WebGPU) and the `GaussianSplattingDebugger`.
- Streaming: `splatBudget`, resident-memory semantics, and streamed SOG
as a part of a compound mesh. The section is no longer labelled
experimental.
- Supported formats now mention compressed and half-float PLY and SPZ
v4, also reflected on the importer page.

Thumbnails are added for the Gaussian Splatting playgrounds that were
missing one.

This is a draft because the GPU sort API only exists in the still-open
Babylon.js#19013. Everything else was checked against Babylon.js
`master`. The GPU sort section should be re-checked against the final
API before merging.

Worth a look: `rangeResidency` is described in text only, because its
playground is a 90-splat unit test.

To preview locally: `npm run dev`, then open
`/features/featuresDeepDive/mesh/gaussianSplatting`.
