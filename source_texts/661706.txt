Issue being fixed or feature implemented
Block files are the bulk of a node's disk usage and are stored as raw serialized blocks. Measured over 20 random mainnet block files, zstd level 3 shrinks a block by 19% on its own at about 400 MB/s; undo records shrink by 23%.
On a current mainnet node that is about 41 GB of block files and 6.4 GB of undo files, so roughly 7.5 GB and 1.4 GB saved; decompression runs at disk speed, so reads stay disk-bound.
What was done?
Each new block record in blk*.dat and undo record in rev*.dat can be written as one zstd frame. The high bit of the record's size field marks a compressed payload, so records stay self-describing for reindex and existing files are read as before and never rewritten. A record that would not shrink is stored plain, which keeps every stored payload within the existing size limits. The undo checksum keeps covering the uncompressed data.
All readers go through a new ReadRawBlockFromDisk that masks the flag and decompresses when needed: ReadBlockFromDisk, the reindex scanner in LoadExternalBlockFile and TxIndex::FindTx. The txindex format is unchanged; offsets stay relative to the serialized block. P2P, RPC, REST, ZMQ, indexes, wallet rescans, pruning and -loadblock work unchanged on top of that.
The level comes from the new -blockcompression=<level> option. The default in this release is 0, so nothing changes on disk unless the operator opts in, and a 24.1 node can be downgraded to 24.0 without reindex in the default configuration. v25 is planned to enable level 3 by default; since 24.1 already reads compressed records, a downgrade from v25 to 24.1 will not need a reindex either. Levels above 5 produce a startup warning since they cost several times the CPU for no measurable gain.
zstd is an optional build dependency like ZeroMQ: --with-zstd defaults to auto, --without-zstd and NO_ZSTD=1 for depends turn it off, and ENABLE_ZSTD tells the code whether it is linked. A build without zstd accepts only -blockcompression=0, refuses to start on block files whose tip record is compressed with a message naming both ways out (a build with zstd, or -reindex), and reports any other compressed record it meets as unreadable.
contrib/linearize/linearize-data.py reads flagged records (via the zstandard module or Python 3.14's compression.zstd) and always writes plain records to bootstrap.dat. test/config.ini reports ENABLE_ZSTD so functional tests can gate checks on it.
How Has This Been Tested?
New unit tests in blockmanager_tests write a compressible block and undo record, check the flag and the stored size against the serialized size, read them back, check reindex accounting against the stored record, check level 0 stores plain records and that a hand-written legacy record still reads. util_tests covers compress/decompress round trips, empty input, truncated frames, garbage and the content-size bound, and the no-zstd stubs.
feature_remove_pruned_files_on_startup runs with compression on, prunes compressed block and undo files, reads a surviving block, expects a pruned one to be reported as pruned and checks the surviving records carry the flag when the build has zstd. feature_reindex, feature_init, feature_txindex, rpc_blockchain, rpc_rawtransaction, rpc_getblockfrompeer, feature_pruning and feature_loadblock were run with compression enabled where their assertions allow it. Tests whose assertions depend on blocks-per-file counts or on incompressible padding pin -blockcompression=0.
Built and run with --enable-werror in both configurations, with system libzstd and with --without-zstd; every commit builds in the no-zstd configuration.
Breaking Changes
None in the default configuration. With -blockcompression above 0, block files become unreadable for versions before this one and for builds without zstd; both need -reindex to recover. Nodes that never set the option can downgrade freely.
Once enabled in v25, downgrade v25 -> v24.0 will require reindex, but v25 -> v24.1 will stay free of breaking changes.

Stream large undo records instead of duplicating them
When a valid block spends many large-script UTXOs, its undo data can be hundreds of MiB even though the block itself is capped at 2 MiB. Extend the no-zstd startup guard beyond the active tip.
The guard at src/init.cpp:2121-2127 rejects startup only when the active tip's block record is compressed. A node that wrote compressed records and later restarted at level 0 has an uncompressed tip. On a build without zstd, that node passes the guard while older block and undo records remain compressed. The guard never checks undo records.
Reads of those older records fail. In a no-zstd build, UndoReadFromDisk returns false for a compressed record (src/node/blockstorage.cpp:619-622). DisconnectBlock then returns DISCONNECT_FAILED (src/validation.cpp:2336-2338). A reorg that must disconnect a block with a compressed undo record can therefore fail. ReadRawBlockFromDisk also fails with a logged error on compressed block records (src/node/blockstorage.cpp:941).
Check all retained block and undo records, not only the tip. Alternatively, persist a marker when the first compressed record is written, and refuse startup on a no-zstd build when that marker is set. A full scan adds startup I/O. The marker needs a storage change. Choose one approach before implementation.
