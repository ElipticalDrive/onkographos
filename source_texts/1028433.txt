One potential problem we have with batch processing is that any one slow item will clog up the whole batch. This pr implements a queueing method instead, where we keep N queues that each have their own workers. There's still a chance of individual items backlogging a queue, but we can try increased concurrency here to reduce the chances of that happening

This PR adds an opt-in thread-queue-parallel mode for uptime result processing; the existing default remains serial.
The consumer decodes each message, derives a grouping key (such as a subscription ID), and routes it to one of a fixed number of queues. --max-workers sets the number of queues and worker threads; if unset, it uses 20.
Each queue has one worker, so messages for the same key are invoked in FIFO order. Different keys can be processed concurrently, although keys that hash to the same queue share a worker.
It adds per-partition offset tracking and a background commit loop, plus queue-depth and commit metrics. Tests cover ordering, concurrency, offset handling, shutdown, and Kafka commits.
A few implementation caveats: processing exceptions are still marked complete in the worker’s finally block, so failed messages can be committed; retry or dead-letter handling should happen before treating them as complete. Also, after committing a prefix, the offset tracker can lose the watermark for a missing offset—for example, it may commit 100 and later 103 when 101 was never tracked, despite the stated gap-blocking behavior. Finally, the queues are unbounded, so queue.put() does not provide the claimed natural backpressure.

ERROR: Do not set worker.shutdown before requesting non-immediate queue shutdown. A worker processing an item will see the flag on its next loop check and exit even if its queue still contains work, defeating shutdown(immediate=False) and leaving submitted items unprocessed. Let workers continue until get() raises queue.ShutDown, then join them.
Graceful shutdown can abandon queued messages instead of draining them.
