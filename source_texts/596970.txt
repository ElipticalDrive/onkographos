Fixes #4312.
Problem
In builds without large worlds (32-bit Real), the engine rounds the view direction far from the world origin. A camera that turns slowly holds still and then jumps in steps. #4312 has the full analysis.
Cause
The engine builds the view matrices as LookAt(position, position + direction, up). LookAt gets the direction back as target - eye. Far from the origin, position + direction is rounded to the precision of position. Thus the direction is rounded too.
Fix
The fix follows the suggestion of @odunov in #4312. A new function LookTo(eye, direction, up) builds the view matrix from the view direction, so position + direction is never computed. It is in Matrix (C++ and C#) and in Double4x4 (C++). LookAt now calls LookTo with target - eye. Thus both use one implementation, and LookAt gives the same matrices as before. The four places that the issue names build the view matrix with LookTo:
Camera::GetMatrices (the camera view of the renderer, and Camera::ProjectPoint and UnprojectPoint)
RenderView::SetProjector (C++) and RenderView.SetProjector (C#)
EditorViewport.CreateViewMatrix (the editor viewport camera)
RenderView::SetFace does not change, because its axis-aligned unit directions do not round.
Test
A new FlaxTests case CameraView (Source/Engine/Tests/TestCameraView.cpp):
Test Camera view direction far from the origin: a camera turns in 0.01° steps over 2° (201 steps). The test reads the yaw back from the view matrix of Camera::GetMatrices. Each step must give a new yaw, with an error below 0.001°. The test also checks that the view matrix near the origin is equal to Matrix::LookAt(position, position + direction, up).
Test RenderView::SetProjector view direction far from the origin: the same steps through RenderView::SetProjector.

All 28 FlaxTests test cases pass (Windows, Development, no large worlds). On Linux (Ubuntu 24.04, WSL, built as the Linux CI does, with large worlds), all 28 test cases pass too.
Editor test (Windows, Development editor, DX11): a copy of the BasicTemplate sample in play mode, with a camera at (407037, 100490, 526640). The camera turns at 12° per second in a ring of 12 spheres. I captured the window about every 0.2 s and measured the horizontal shift of the game view between two captures (phase correlation).
1.12.6912 without large worlds: the shift alternates between about 44 px and 0. The view holds, then jumps. 14 of 89 pairs had no shift.
1.12.6912 with the same change in Camera::GetMatrices: the shift is steady, 20 to 35 px for each capture interval.
master with this PR: the shift is steady, 36 to 62 px. The capture intervals were longer in this run.
I made these measurements with the first version of this PR. It computed the same matrix.
The editor viewport also renders correctly with LookTo in EditorViewport.CreateViewMatrix. I did not build on Mac. The change has no platform code.
Risk
Low. The matrices are the same as before, except for the rounding.

@cNori, thank you for this detailed check. You are correct: the translation row is the same computation as in LookAt, -dot(axis, eye). This is intended. The PR gives the same matrix as LookAt.
The change is in the input to LookAt, not in its math. In builds without large worlds (32-bit Real), Camera::GetMatrices on master passes target = position + direction. This sum is rounded to the precision of position before LookAt runs. LookAt then gets the view direction back as target - eye. This is where the direction is lost. With large worlds, Camera::GetMatrices on master already computes this sum in double, and the PR gives the same matrix there.
At the test position (407037, 100490, 526640), the float spacing is 0.031, 0.0078 and 0.0625. Thus each component of the unit direction is rounded to these steps. At the yaw of the test (30°), these steps move the yaw by about 1.5° to 1.8°.
With the PR, LookAt gets eye = 0 and target = direction. Thus the direction is never rounded. No bits come back from the void, because the PR does not remove them in the first place. The rounding of the position itself does not change. That is the normal 32-bit limit that you describe.
The PR adds a test for this, Test Camera view direction far from the origin. It turns the camera in 201 steps of 0.01° and reads the yaw back from the view matrix:
On master, it gets 2 different yaw values (max error 1.29°) and fails.
With the PR, it gets 201 values (max error 0.0000°) and passes.
A second section does the same for RenderView::SetProjector. To check it, run FlaxTests with and without the change in Camera.cpp.
