I was reading the paper introducing Taichi [1] and I noticed that it mentions a simple and very nice-looking API for storing data in s-nodes with Morton encoded memory layout.
As @bobcao3 mentions in #3790 (comment) I suppose as a workaround it may be possible in some cases to sort data using the nice utility provided by @AmesingFlank in #3790, but:
(1) the API mentioned in that paper looks quite user friendly! I'd love to have it available :-)
(2) I wonder if there would be any performance gains to be had from an API built into the s-nodes rather than "manual" sorting? (I really don't have a good sense of this and would be curious to learn what you experts think -- perhaps it would be approximately equivalent?)
Thanks again for Taichi, I'm loving it!! :-D
[1] https://yuanming.taichi.graphics/publication/2019-taichi/taichi-lang.pdf

Hi @bobcao3, as I look back at my comment and the paper cited above, I see I may have confused a couple of issues by mentioning sorting in this context.
(1)
In the paper cited above, the idea of a morton() "decorator" on dense s-nodes is described, such as this example from the top of page 6:
```
root.dense(ijk, 512).morton().bitmasked()
.dense(ijk, {8, 4, 4}).place(flags, u, v, w);
```
In this case, I guess it would not really have anything to do with sorting, but is really just more of a convenient index aliasing so that one can use standard Cartesian (i,j,k,...) indices into a ti.field, but with the guarantee that the field will be stored in physical memory with Morton encoded layout.
For this idea, I think the API presented in the paper or something like it would be fine. I guess the API has moved on since the paper was published, and no longer uses "decorators" with dot notation like root.dense(ijk, 512).bitmasked(), but instead we now write root.bitmasked(ijk, 512). If the decorator notation is no longer supported, perhaps an optional boolean keyword argument would suffice: root.bitmasked(ijk, 512, morton=True). Just brainstorming, I think there would be many good ways to expose an API for this functionality.
(2)
I was really thinking about the more limited case above, but your idea of a sorted heap is very cool and interesting! I agree that a lambda sounds like a generic and powerful approach to allow arbitrary sorting schemes, though a key field of some sort would be adequate for my needs, which are primarily dabbling in MPM and SPH, for which I believe z-curve (or Hilbert curve) spatial sorting would be adequate (though I am not an expert).
For the simple case of a key field, I could imagine an API something kind of like:
```
x = ti.Vector.field(2, dtype=float)  # position
v = ti.Vector.field(2, dtype=float)  # velocity
C = ti.Matrix.field(2, 2, dtype=float)  # affine velocity field
F = ti.Matrix.field(2, 2, dtype=float)  # deformation gradient
material = ti.field(dtype=int)  # material id
Jp = ti.field(dtype=float)  # plastic deformation

particles = ti.root.morton_heap(ti.i, n_particles, key_field=x)
particles.place(x, v, C, F, material, Jp)
```
where key_field must be a ti.Vector.field of dimension 2 or 3 that is subsequently placed in the s-node. And then after every n-substeps, you might call particles.sort() to invoke the sort.
Anyway, just brainstorming -- the Taichi team has world experts on these topics, so I'm sure there are much better ideas close at hand! :-)

Thanks for bringing this up! IMHO, the original design in the taichi-2019 paper, where a SNode can be followed by 1) either another SNode (e.g. dense().pointer()), or 2) a decorator (e.g. dense().morton()) can be a bit confusing. Taichi's SNode API has since moved on to focus on 1. Another source of confusion would be to define the scope of the decorator, i.e., for dense.dense.morton, does it apply to the rightmost dense, or both?
That said, the decorator is still a very concise API. On top of my head I believe that dense, bitmasked and pointer can all support morton encoding. WDYT if we simply add a flag to each SNode's API, e.g. dense(..., morton=True)?
