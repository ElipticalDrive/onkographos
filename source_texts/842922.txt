This has been come up a few times, and we discussed this yesterday
If a user defined function includes iterative algorithm with a fixed point the implict gradient is 0, but autodiff will diff through that iterative algorithm which may significant cost per each iteration. In such cases it would be useful if the user could define the gradient computation. If that gradient computation could be part of the user defined function (e.g. returning a tuple of value and gradient), then the value and gradient could be computed using the same intermediate values. This would be useful in cases, where the user defined function is something which would not be likely to be added to Stan math, but where avoiding the autodiff through iterative part could make the gradient computation order of magnitude faster.
It's not clear how complicated this would be to implement, but it was suggested that I create this issue and tag @SteveBronder

I just gave it a few more minutes thought and realize that our real problem is that we would really like this to return a continuation with closure. That is, ideally what a user-defined function would return would be like how we write autodiff internally---it would return a value and supply a closure to use as a continuation in the reverse pass. The signature would be something like this:
```
(value, continuation[1] ..., continuation[N])  f(argument[1], ..., argument[N])
```
If argument n is of type and size T[n] and the value is type and size T[0], then the continuations will have types:
```
continuation[n]: T[0] -> T[n]
```
I say that this is a closure, because you probably also want to save bits of the computation leading to the value for use in the continuation calculations. This is the part I don't know how to do---save intermediate values calculated in the forward pass for reuse in reverse pass.
In the reverse pass, they will be given the adjoint of the return value and will be expected to return
```
continuation[n](v) = value.adjoint * gradient_arg[n] f(arg[1],..., arg[N])
```
where the * is conforming to whatever the types are. It's easiest to just think of this all as flattened arrays mathematically and in terms of the PyTree structures used by JAX computationally. Stan is a bit of hack in the middle ground where the argument types that matter here are scalar, vector, row vector, or matrix.
Here's a short tutorial I wrote on the forums ages ago about how to think about autodiff this way and it explains what closures and continuations are (terms from programming language theory not everyone in stats is going to be familiar with).
https://discourse.mc-stan.org/t/a-new-continuation-based-autodiff-by-refactoring/5037

The way that a system like JAX handles this is that a function with custom gradients has a forward, which returns a tuple where the first element is the value and all other elements are 'scratch space' for use in the reverse mode. The reverse mode function accepts the same tuple type and returns a tuple of the same size and types of the arguments of the forward function with the adjoints.
This is actually perfectly adaptable to Stan, I think. Here's the straightforward translation of their example function:
```
real f(real x, real y){
  return sin(x) * y;
}

tuple(real, tuple(real, real, real)) f_fwd(real x, real y) {
  real sin_x = sin(x);
  return sin_x * y, (cos(x), sin_x, y);
}

tuple(real, real) f_bwd(tuple(real, real, real) res, real g){
  real cos_x, sin_x, y;
  cos_x, sin_x, y = res;
  return (cos_x * g * y, sin_x * g);
}
```

The other thing worth discussing is how we'd like the user to tell us they've done this. In JAX, you annotate f with @jax.custom_vjp and then have to call f.defvjp(f_fwd, f_bwd) at some later point.
In Stan, we could rely on function names (meaning if you have the triplet of functions foo, foo_fwd, foo_bwd, we just assume you're doing this), but that would prevent some kinds of typechecking and help (e.g., if you accidentally named the function foo_backward, we'd have no way of knowing your intent, and you'd miss out on the functionality).
So I'd like some other way of doing it, but I'm not sure what that is.
