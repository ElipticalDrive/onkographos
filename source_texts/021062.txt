Im interesting in doing a raymarched rendering of animated volume data. From looking at the texture class it only goes up to 3d. Is there something simple im missing that would allow this to be done in pygfx; or would this be a nontrivial feature request?
Ideally id like to be able to put a 5d array in gpu memory (xyzt with a number of components) and then inject a little shader code to customize how those components sampled at each voxel are mapped to rgb and accumulated though I suppose I could precompute mappings to some rgb density as well if thats more convenient.
Would it see feasible to implement something like that into pygfx, without having to fall back to pure custom shader code?

In general, GPUs don't support textures with more than 3 dimensions at the hardware level. You can have multiple channels per voxel though, so ultimately a 3D array with RGBA voxels would add up to a 4D array.
You can manage the time axis on the CPU, and swap out the memory on the GPU quite easily, there's an example here: https://github.com/pygfx/pygfx/blob/main/examples/feature_demo/synced_video.py
I'm guessing you already found our volume rendering examples, you can put the approaches demonstrated there together to make it work.
If the performance of this approach does not meet your requirements, you would have to manage memory in a different more efficient way. But this gets complicated fast. There's more than one way to do it.
You could create a much larger 3D array and apply a tiling scheme to upload more frames to the GPU. But it's likely you won't be able to upload the full dataset without hitting a constraint on the maximum dimensions of the texture. So you would have to implement out of core rendering memory management techniques.

so it probably makes most sense to put each time slice into mem as a seperate 3d texture and pre-bake the mapping to RBG into them, then bind that gpu mem resource to the volume draw call each frame.
Swapping out the texture (i.e. geometry.grid) will cause the shader to re-compose the pipeline. It should be able to re-use the wgsl shader from cache, but it'd still be relatively expensive. That said, it may be fast enough.
I think technically (from the pov of wgpu) it should be possible to swap out a binding very cheaply as long as its the same format, but we don't have a way to do that (yet). Until we have such a feature, it might be more performant to just bind to all textures from the start, and then select the correct one in the shader.
I'm not sure how the frames relate in your case, but I've done rendering of 3D data in motion (many years ago), where I had a displacement field in another texture that I used during the sampling to "move the data". The displacement field had a lower resolution, which made it feasible to simply upload a new field at each frame. So if the data allows it, a bit of creativity can also come a long way :)
