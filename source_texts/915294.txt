I'm making another request here since it's a little different from the saving one (#764)
Basically I'd like to have a way to manually instance items that are in a VoxelInstancer library.
The point would be able to manually instance items, stuff like planting a tree, dropping an item and that interaction would then be saved in VoxelStream.
Simple example:
I plant a tree at a specific position using a mouse raycast using and function like VoxelInstancer.instance_item(item_id, transform)
The instancer registers it and save it similarly to the persistent option.
If it gets removed whether by queue_freeing the collider or digging the terrain below it is also saved so that it doesn't get spawner again when leaving the terrain.
This could also be used to use a custom script to instance object from the instancer with a different algorithm instead of using the current VoxelInstanceGenerator parameters/conditions.
The end result would be something similar to Voxel edit (like adding a chunk of terrain) but with scene item/multimesh item instead of regular Voxel block.

being able to manually place an instance was possible
I think it's easy to add [to existing instance chunks], but what you want to build with that might hit the limitations.
There is one issue with this however, which is currently preventing me from adding that:
This system has been heavily built around mesh chunks and signals sent for them from the terrain node. And these chunks don't exist in places where there is no ground.
It will eventually happen that you place something in a chunk that doesn't have a mesh, even if you think you're placing based on a ground hit (probability is low but not zero). I think the instance chunk will pretty much desync and remain there forever, even if you move far from it... and the opposite is true too: if you edit the ground until it causes a mesh chunk to become empty, that will trigger the unload of the instance chunk associated with it.
To change that would indeed require pretty annoying backward changes or significant rewrites.
This is why currently that system is exclusively for "naturally spawned" environment props, because that way they are unambiguously associated with existing mesh chunks of the terrain system (not because they happen to spawn on them, but because they get populated in sync with mesh chunks getting loaded), which in turn means the instancer doesn't need to implement any chunk streaming logic.
