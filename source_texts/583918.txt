What & why
Gaussian Splatting keeps per-splat attributes in 2D textures and looks them up from the vertex shader at texel center (getDataUV: (index + 0.5) / textureSize). That is a table fetch, not image filtering. Adjacent texels are different Gaussians (world positions can be far apart), so bilinear has no geometric meaning.
The streaming atlas path already creates centers / covariances / colors with TEXTURE_NEAREST_SAMPLINGMODE. The CPU RawTexture path used by #M05L0C still passed TEXTURE_BILINEAR_SAMPLINGMODE. On implementations where float bilinear is inexact at texel centers, that mixes in a neighbor splat (~1/256) and the first frame of https://playground.babylonjs.com/#M05L0C#0 turns to fog. Nearest on the same textures matches the atlas path and the integer/texelFetch tables.
Fix
Switch the CPU data-texture helpers to nearest:
gaussianSplattingMeshBase.pure.ts _updateTextures(): FLOAT centers, HALF_FLOAT covariances, UNSIGNED_BYTE colors
gaussianSplattingMesh.pure.ts: compound part-index RawTextures
getDataUV / texture() are unchanged. SH / uint tables and the atlas samplingModes were already nearest.
Scope
I did not change:
shader UV math (+ 0.5 stays; it already aims at texel center)
the MRT streaming atlas path (already nearest)
sort / covariance / SH math
This is a sampling-mode default for lookup textures, not a 3DGS algorithm change.
Testing
Inspected both creation paths: atlas nearest vs CPU bilinear (now nearest).
Isolated the GS vertex fetch: RGBA32F + GL_LINEAR at texel center vs GL_NEAREST on the same UV. Nearest returns the stored texel; bilinear can mix the neighbor on some GPUs.
#M05L0C#0 with updateSamplingMode(NEAREST) on centers/cov/colors restores a sharp splat on the GPU that fogged with bilinear.
On a spec-correct GPU, bilinear-at-center ≈ nearest-at-center, so visual change should be none / within 1 ULP for the intended lookup.
