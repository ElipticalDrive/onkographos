This is how data leaves a hospital: a folder of files, one per slice, named by whatever the
archive felt like. Turning it into a volume is four decisions, and each one taken wrongly
produces a volume that trains without complaint and means something other than it claims.

**Order.** Not the filename, which sorts slice 10 before slice 2. Not `InstanceNumber`
either: it need only be unique within a series and is not required to follow the anatomy,
which is why it is the documented fallback for files with no geometry rather than the first
choice, and why `Series.sorted_by` says which was used. The order comes from
`ImagePositionPatient` projected onto the slice normal - a physical distance along the axis
the slices advance in, which cannot disagree with the anatomy.

**One series at a time.** A folder out of an archive usually holds several: a scout, a
reconstruction, a different phase. `SeriesInstanceUID` separates them, and stacking two of
them interleaves two anatomies at two resolutions into something that looks like a volume.

**One window for the whole series.** `read_dicom` honours the window a file records, and
different slices of one series can record different ones. Applied slice by slice, the same
tissue is a different brightness on adjacent slices - a gradient the scanner never measured.
Resolved once, from the first slice, then applied as fixed bounds.

**Orientation,** through the same canonical path a NIfTI takes, so one CT read from its DICOM
and the same CT after conversion arrive identically oriented. There is a test that stores one
anatomy with reversed in-plane axes and asserts the arrays come back equal.

A gap in the positions is an error rather than a stacked array: a missing slice does not make
the volume shorter, it puts everything past the gap in the wrong place, and no metric would
show it. Slice spacing is measured from the positions, never from `SliceThickness`, which
describes how thick a slice is and not how far apart they sit.

Two things found while writing the tests, both mine:

- the affine crashed when a series had orientation but no positions - exactly the fallback
  path the sorting code was written to handle.
- with only two gaps the median sits between them and cannot say which is wrong. Naming one
  would be arithmetic accident dressed as a diagnosis, so short series get a message that
  says so and lists the gaps.

Wired in two ways, because that is how the data sits: a 3D model with several DICOM files in
a sample, and a series directory named in a CSV. Several *volumes* per sample - one per
modality, BraTS shape - is refused with a message rather than the first being read and three
quarters of the data ignored.

424 tests, ruff clean, distributions build.

from_yaml() read a configuration and nothing wrote one, so the two
interfaces were one pipeline and a half. Its own docstring promised the
round trip through `as_dict()`, a method no spec has ever had.

It writes what was set, not what the object holds. On a two-field model
to_dict() returns 29, and the difference is not verbosity: a model given
weights and no architecture adopts the architecture from the sidecar, and
the adoption fires on architecture not being in model_fields_set. Dump the
defaults and the file looks like the original and quietly stops doing what
it did. defaults=True keeps the opposite want as a second mode.

Two things only the round trip found:

Every discriminator must be written even when unset. `task` is obvious.
DiceLoss(smooth=0.5) is not: `name` is a Literal with a default, so what was
set alone gives `loss: {smooth: 0.5}`, which comes back as "Unable to
extract tag using discriminator 'name'".

And "annotated Literal" is the wrong rule for finding tags - it also catches
box_loss and annotation_format, which are user choices, and writing them
unset freezes the default this function exists to leave out. A discriminator
pins one value, so the rule counts them: 31 single-value Literal fields
across the spec, all of them name or task, and the only two with more are
those choices.

Mutated three ways, each verified to land after two attempts failed on a
line ruff had rewrapped: no tag restoration (5 failures), defaults always
(5), any Literal treated as a tag (1).

No version bump: this rides in 0.8.0a11 with #118 and #119, so R can take
all three halves from one release.

seed has said where it stops since 0.8.0a8 - twelve decimals on the
processor, the fourth decimal after one epoch on a GTX 1070, because cuDNN
picks algorithms nothing constrained. This constrains them:
use_deterministic_algorithms, cudnn.deterministic, and cudnn.benchmark off,
which is the one that was choosing per shape.

An opt-in because the cost arrives where nothing else here does: some
convolutions much slower, and an operation with no deterministic
implementation raises when it is reached, so a run can stop ten minutes in.
Whether one has such an algorithm is a fact about the installed torch and
the device, not about the configuration, so this refusal cannot happen
before the run the way every other one does. The field says that.

It needs seed, and asking without one is refused: constraining the
algorithms while the draw still varies leaves the run as unrepeatable as
before and only slower, which is the half promise #122 was filed about.

CUBLAS_WORKSPACE_CONFIG is set to :4096:8 when nothing else has - cuBLAS
needs it from CUDA 10.2 on or torch raises, and it is read when CUDA
initialises, which is why this is in the constructor rather than fit(). An
existing value is somebody's choice and stands.

Tested: the flag reaches torch, nothing is asked when nobody asked, the
variable is set without trampling one, the spec refuses the half promise,
and an ordinary run still trains with it on. Two CUDA runs agreeing needs a
card and CI has none, so that is documented rather than asserted - the same
line test_seeding.py takes about the other half.

Mutated three ways, each landing: the flag doing nothing (2 failures), no
validator (1), the variable overwritten (1).

No version bump: rides in 0.8.0a11 with #118, #119 and #120.
