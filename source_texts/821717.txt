Ray marching using SDFs vs. traditional ray tracing using 3D meshes, speed comparison
Hi there,
I was thinking about using signed distance functions (SDFs) to represent geometry in my next project, but I am not sure if I have a good understanding of what the advantages are compared to using 3D meshes. One thing that came to mind however is ray marching (with SDFs) vs. traditional ray tracing (with 3D meshes). I wonder which one would be more performant. Traditional ray tracing calculating ray-triangle intersections, such as explained in this scratchapixel blogpost, or ray marching in combination with signed distance functions, which is further explained here. Does anyone know the unambiguous answer to this question? Or are there certain cases in which one method outperforms the other, but not always?

I would say it is the latter. With traditional ray tracing you generally get a faster output for primitive based geometry, like spheres or meshes consisting of triangles. This is especially true with the right data structures and hardware acceleration (like RTX).
The key difference with using ray marching is the multiple steps it needs to converge on a surface. This reduces performance but also lets you render fractals, volumetric data and constructive solid geometry very intuitively. You could not for example render fractals with the same amount of details using traditional ray tracing.
To sum up, it really depends on what you want to use the respective algorithm for. I personally implemented both in a little toy software renderer and compared them on similar scenes (Cornell boxes). The speed increase from traditional raytracing over ray marching was not that significant, if I remember that correctly. But its been a while since I tried that. Hope this helped :)

To sum up, it really depends on what you want to use the respective algorithm for.
This is pretty much it. They're just different tools. You can trace geometry where the intersection with a ray has an analytical solution, and you can march distance fields which may not (and usually don't).
You can even mix them if you wanted to. They both, at a high level, check a ray for intersections against everything in the scene and then keep the nearest one. You can march and trace the same ray just as you trace the same ray against many objects.

You are actually missing nothing! There are exact ray intersection formulas for most primitives, like spheres, triangles, etc. Those can be used exactly as you described, for finding the intersection point(s) directly.
The difference between these intersection functions and SDFs is, that the first one is returns a distance from a point in space along the ray direction to the object, while with an SDF you loose the direction and only get the closest distance to a point on the surface. This point is usually not the point where the ray will intersect the object.
But why use ray marching if it does not return the distance we actually want? Direct intersection functions have some caveats, the main one beeing that not every shape can easily be described by a combination of primitives. The obvious example would be fractals, as it is their nature to only be describable by approximation. Another great reason to use SDFs is their way simpler math. If you ever derived an efficient ray sphere intersection by hand, you probably know that this can get very messy very quickly. Now imagine having to do the same for a torus. Not that it can't be done, Inigo Quilez has the code on his website and an example on Shadertoy, but seeing the 1 line of SDF-GLSL code for the sphere and the 2 lines for the torus is just extremely satisfying. I think (but am not quite certain) this "way simpler math" argument also holds for the incredible number of SDF operations, like boolean operations, onion skinning, smoothing, just to name a few. Ray marching is also absolutely necessary for finding intersections in density volumes, for example in a smoke simulation. These computations often even need a techique I know as "ray-casting" where the step length for each marching step stays constant.
Your intuition was already very correct! Hope that explains it a bit more :)
