Thanks for picking this up. The block-level semantics look right: only the last 64 KB of the dictionary is used, offsets can point back into it, and a match can run from the dictionary into the source, so the output decodes with the existing UncompressBlockWithDict. Extending FuzzBlockRoundTrip with a dictionary is what we were hoping for. Several things need to change before this can go in, though.
Main blocker: the compressor is duplicated. compressBlockWithDict is a ~270-line copy of compressBlock's match loop and sequence encoder. The fast compressor was recently tuned, and a second copy will drift from it; every future fix would have to land twice. Please integrate the dictionary into compressBlock itself: a dictionary lookup that is only consulted when the hash table has no candidate inside the source, with the no-dictionary path unchanged. Include a benchmark (anchored, e.g. -bench 'BenchmarkCompress$') showing the no-dictionary Fast path doesn't regress.
Other issues:
Compression level is silently ignored. In lz4stream/block.go, CCompatFast and every HC level fall back to the Fast dictionary path whenever a dictionary is set. CCompatFast promises the C library's exact output, which this isn't. Until those levels support dictionaries, return ErrOptionNotApplicable for a dictionary with any level other than Fast.
The dictionary is re-hashed on every block. Every position of up to 64 KB of dictionary is hashed for each block; with 64 KB blocks that roughly doubles the hashing work. C's LZ4_loadDict primes the table once, hashing every third position, and reuses it. Prime once per stream and reuse the primed table.
The Reader can write into the caller's buffer. DictionaryOption stores the caller's slice directly, and for linked-block frames Reader later does r.dict = append(r.dict, dst...). If the caller's slice has spare capacity, decoded data overwrites their memory past len(dict). Please store a copy, or at least slices.Clip(dict).
The aliases aren't needed. WithDict and WithWriterDict duplicate DictionaryOption; please remove them.
Concurrency is silently disabled for Writer and Reader when a dictionary is set. That's acceptable for a first version but should be documented on the option.
Tests: the fuzz extension covers most of what the 14 new unit tests check. Please keep the fuzz change, drop the new block_dict_test.go, and keep one or two frame-level round-trip tests in the existing test files (see AGENTS.md).
It would be easier to review as two PRs: first Compressor.CompressBlockWithDict built into compressBlock, with the fuzz change and the benchmark; then the frame options, with points 1, 3 and 4 fixed. Please also write "Part of" rather than "Fixes" on the first one, so the issue stays open until both parts have landed.

Each miss compares len(c.dict) in memory, at all three probe positions.
Suggested direction: keep the miss path exactly as in v4, and consult the dictionary only after all three in-block probes have missed, behind a hasDict flag hoisted out of the loop. Move the dictionary probe and match extension into separate //go:noinline functions that return values rather than write through pointers, so the loop never takes an address for them. I measured what it would take, and an integrated dictionary check can't be made reliably free with today's Go compiler, so it's a design choice for @pierrec rather than something for you to chase. The first variant is slow because taking &offset keeps offset on the stack and the three non-inlined calls add spills to the loop. Once those were removed, the remaining 1.4–1.9% doesn't come from executing the extra check: the inputs that run it most (random, e) were faster than v4 in two of the three variants, and zeros, whose time is all in an untouched match-extension loop, moved by up to +6%. It's code layout: any change inside the function moves its loops, and Go has no way to control loop alignment in Go code or to specialize a function on a constant. liblz4 avoids this by force-inlining LZ4_compress_generic with the dictionary mode as a compile-time constant, which in effect makes a separate copy of the loop.
Options.
Separate dictionary loop. CompressBlock keeps v4's source, so its instructions are unchanged, and it measured within noise (+0.14%). CompressBlockWithDict gets its own loop in a new block_dict.go: one candidate per position, block before dictionary, about 230 lines including its sequence writers. It's fuzzed through FuzzBlockRoundTrip and covered by the short-dst boundary test, and liblz4 decodes its output. The cost is a second, simpler loop to maintain. Its ratio is good for small messages and weaker for large blocks: 26.6% vs liblz4's 23.3% on 2,000 ~235-byte JSON log messages compressed individually with a 16 KB dictionary, but 23.56% on 64 KB blocks of log text, where not using the dictionary gives 22.82%. Both can be improved in that loop without touching CompressBlock: most of the gap to liblz4 on small messages comes from ending matches 14 bytes before the end of the block, as CompressBlock does, where the format allows 5.
Integrated. One loop with the dictionary checked after the in-block probes. 27.1% on the small messages and 22.81% on the 64 KB blocks. Neither option's ratio dominates; it depends on the data. The cost is 1.4–1.9% on every Fast compression without a dictionary, including the default Writer, with individual inputs moving up to ±8% depending on layout.
Generated pair. The Fast loop written once as a template and generated as two functions, with and without the dictionary, which is what liblz4 gets from inlining. No cost without a dictionary, and the tuned three-probe parse with one. The cost is a code generator for the Fast compressor, like the one the decoders already have, which future tuning of the Fast loop would have to go through.
Prefix mode. Copy the dictionary in front of the block, seed the hash table with its positions, and run the existing loop from the end of the dictionary, as liblz4's _continue path does. No dictionary check in the loop, and the tuned parse with the dictionary. The cost is O(dictionary size) work per call: copying and seeding, about 5,400 table inserts per call with a 16 KB dictionary. That's fine for large blocks but many times the cost of compressing a ~235-byte message, the case dictionaries are mostly for. CompressBlock's entry and exit change slightly, so it would need the same measurement.
My preference is option 1 now, with option 3 later if dictionary users need the tuned parse: the default path stays as it is, and the dictionary path is simple enough to review on its own. But it's your call. Option 1 is implemented and tested on a branch based on this PR, and I can push it here if you agree.
