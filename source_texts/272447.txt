Problem
The current lighting preview draws deterministic debug overlay quads. It does not yet produce a real renderer light mask or shader-composited lighting pass for exported-game-quality visuals.
Why now
Issue #192 added PreviewSnapshot.lighting and a native debug overlay. The next renderer step should consume the same payload in a GPU path instead of expanding the debug overlay into final rendering behavior.
Scope
Design a first GPU light-mask or fragment shader path for PreviewLighting.
Support point and cone attenuation using color, intensity, radius, falloff, direction, and cone angle.
Keep the CPU debug overlay available as a diagnostic mode.
Add renderer tests or snapshot assertions for payload-to-GPU-buffer conversion.
Out of scope
Physically accurate shadows.
Final art-direction controls.
Editor light-authoring controls.
Proposed approach
Add a renderer-owned light uniform/storage payload parallel to the existing sprite instance buffer, then compose lighting as a separate pass or fragment shader branch. Keep the debug overlay as an optional comparison path.
Acceptance criteria
Native preview can render point and cone lights through a GPU-oriented path using PreviewSnapshot.lighting.
Radius, intensity, falloff, color, cone direction, and cone angle visibly affect the output.
The debug overlay can still be used to compare payload shape during development.
Renderer tests cover light payload packing/conversion.
Definition of done
Rust tests cover point and cone GPU payload conversion.
Documentation explains the chosen pass/shader shape and remaining limits.
Native preview still launches with snapshots that include lighting.
Risks and open questions
We may need to choose between a light-mask render target and a sprite fragment shader branch.
WGPU limits for many lights need budget checks before this becomes user-authored.
Test expectations
Run targeted renderer/native-preview tests.
Run cargo test --workspace.
