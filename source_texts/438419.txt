A cheap way to improve render performance when there's lot of hidden objects...
Include a lazy optimisation for shadow:
I narrow the far plane of the view with OQ results splitting cull traversal in 3 traversal:
for OQ (just to submit queries)
for not occluded (that give me the narrow frustum with the nearest far plane possible)
for the rest (don't care the far plane of this frustum)
2&3 may be merged but include terrain in far plane computation can be of some use for fine tuning
NB:
You can check drawcharge of the oq compromise with stats (it's part of the few quads)
Indoor is treated as outdoor...(differents octree parameter -for other scene scale-should be used for indoor, but it wouldn't be very usefull as indoor dont lag)
octree occlusion culling is hierarchic so keep max BVH OQ level count low for more reactivity SOLVED
bug still exists with hierarchical terrain+oq+shadow culling (some are drawn even if occluded when include terrain in far plane computation is true) SOLVED
little bug with ingame shadows settings (can't enable it if shaders disabled) but switching shadow on/off ingame is so usefull that i let the bug be.

The two approaches modern engines use to get around the pop in are:
Using heuristics like oversized occlusion geometry (so a query also covers the region an object is likely to move into), ignoring query results for fast-moving objects or when the camera moves quickly (as those query results are likely to be wrong) and whatever else happens to be effective for the game.
Using the query results in a compute shader having dispatched everything that might possibly be drawn in a few huge draw calls.
Both of these approaches are hard enough to get right that lots of games don't use occlusion queries at all, instead relying on CPU-based approaches.
For example, in Skyrim, when indoors, all objects in a room are parents of one node. Everything in the same room as the camera is submitted provided it passes view frustum culling. If a door object passes view frustum culling and is open, the room it connects to is added to the scene being considered.
Also in Skyrim, when outdoors, some objects (like buildings) have occlusion planes inside them. Occlusion planes encountered during the cull pass are remembered. Objects are tested against these planes, and if their bounding volume is entirely behind one, they don't get drawn. Remembering the planes can be done either by just storing them in a list and testing against them directly for every bounding volume, or by rasterising them in software to a low-resolution depth buffer and then rasterising bounding volumes (also in software) and seeing if they'd pass. This doesn't actually work out much slower than hardware occlusion queries but doesn't have the pop-in issue, and so is the approach used by lots and lots of games. OSG has some level of support for this (mp3butcher once accidentally disabled it when trying to make shadow volume stuff optional) but I've never got it to do anything when playing with the example.
(Also, because Bethesda is Bethesda, they accidentally broke this code in Skyrim Special Edition, so that only has view frustum culling.)

not really active on this but i spot a zfar computation weirdness when occlusionquerrynode gets hierarchical....setting default include terrain in far plane computation to false and max BVH OQ level count to 1 hides this weirdness and get correct zfar narrowing with shadowcams ... this misbehavior can be adress in a further pr ...
Hierarchical oqns is really hard compromise to find as:
hierarchical nature implies chained queries (more frame latency)
parent oqn asks a lot of rasterization work to the gpu to give an answer (more frame latency)
The wiser seams to have only 1 level of queries and a compromise on spatial granularity (min node size)
