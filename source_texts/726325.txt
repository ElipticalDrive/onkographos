Summary
Phase 1: got the original graphdeco-inria/gaussian-splatting repo running in Docker and reproduced its reported metrics on tandt/truck (PSNR 25.49 / SSIM 0.885 vs. the paper's 25.19 / 0.879).
Phase 2: ported the reference algorithm onto this repo's own shape (Hydra + Lightning + wandb + shared module.py callbacks, matching fit_gsplat.py), using gsplat.rasterization + gsplat.strategy.DefaultStrategy for rendering/densification instead of diff-gaussian-rasterization. This is a faithful port, not a from-scratch reimplementation: free xyz, real growing/shrinking densification, SH degree ramp, opacity reset — everything the earlier abandoned fit_3dgs.py prototype skipped.
Vendors gaussian-splatting/ (COLMAP parsing, camera math) and a patched gsplat-src/ (v1.5.3 + the upstream fix for a real operator-precedence bug in DefaultStrategy's opacity-reset scheduling — step % reset_every == 0 & step > 0 silently never fires due to Python operator precedence).
fit_3dgs.py validated against both the vendored reference and the Phase 1 repro on truck: PSNR 25.75 / SSIM 0.890 / LPIPS 0.172 (1.98M Gaussians) — in line with both.
Extended with load_scene_h5(), a drop-in alternative scene loader for our own render_objaverse.py h5 captures (no COLMAP data) instead of a real capture — same (pcd, scene_extent, train_cams, test_cams) shape downstream, so the rest of the training loop doesn't care which loader ran. Verified on the 50-view and 250-view porsche renders (PSNR 33.6 / 36.6 on held-out views), including a world-space Chamfer-distance check of the fitted geometry against the depth-peel-unprojected ground truth point cloud (not just the photometric loss).
Test plan
Phase 1 repro matches the paper's reported truck metrics
fit_3dgs.py on truck matches both the Phase 1 repro and the paper within normal implementation variance
fit_3dgs.py h5 path (load_scene_h5) runs cleanly end-to-end on the 50-view and 250-view porsche datasets, full 30k iterations, no crashes
Camera convention sanity-checked by projecting the world origin through a train view and confirming it lands at image center at the expected depth
Chamfer distance between fitted Gaussian means and depth-unprojected GT point cloud computed for both porsche runs, confirming geometric (not just photometric) accuracy

…
04827c7
```
New option (default stays "set", the existing free-xyz + densification
behavior): gaussian_layout=layered seeds one Gaussian per depth-peel hit
in the primary train view's 6-layer peel -- fit_gsplat.py's own seeding,
reused verbatim via init_gaussians_layered() (which calls
fit_gsplat.init_gaussians() directly rather than reimplementing the
unprojection/KNN-scale/front-pixel-colour logic a third time) -- and
disables densification/pruning entirely (self.strategy stays None,
every call into it guarded), since growing/splitting/pruning would
break the fixed 1:1 Gaussian<->(u,v,layer) correspondence layered mode
exists to preserve.

Only valid with hdf5_path (needs depth_peel/depth_intrinsics -- COLMAP
scenes and depth-less h5s raise a clear SystemExit, checked before
training starts).

Color model stays full SH (sh0/shN, degree ramp) same as "set" mode --
not fit_gsplat.py's flat sigmoid color -- so training itself is
otherwise identical between the two layouts; the params stay a plain
flat ParameterDict either way, gsplat/DefaultStrategy/render() never
see anything shaped like a grid. "layered" only changes how the seed
is built, that densify/prune never runs, and that one extra file gets
written: save_output_layered() scatters the final flat params back
into a fit_gsplat.py-schema (H, W, L, .) grid .h5 (gaussian_means/
scales/quats/opacities/colors + layer_valid, colors DC-only baked down
from sh0 since that schema has no SH slot), written alongside the
usual flat .h5/.ply, so orbit_video.py and anything else built for
fit_gsplat.py's own output can consume a layered run unmodified --
verified directly (orbit_video.py rendered the grid .h5 with no
changes needed).

Verified end-to-end on the 50-view porsche h5: seeded exactly 14,880
Gaussians from the primary view's depth peel, count stayed exactly
14,880 through training (confirming densify/prune truly never ran),
final eval and grid-.h5 write both succeeded.

module.py/fit_3dgs.py: fix PanelCallback/OrbitCallback never firing
…
333b129
```
Root cause: trainer.global_step, under MANUAL optimization, is driven
entirely by hooks Lightning injects onto LightningOptimizer proxies'
own .step() method (see lightning's manual.py _ManualOptimization
on_run_start/_on_before_step/_on_after_step). fit_3dgs.py's
training_step calls .step() directly on the raw torch.optim.Adam
objects it built itself (deliberately -- gsplat's grow/prune/reset
tensor surgery needs the real optimizers, and there are 6 separate
ones, one per param group, which would inflate Lightning's per-.step()
-call counter 6x if routed through the proxies anyway), so those hooks
never fire and trainer.global_step silently stays 0 for the entire
run -- confirmed directly by instrumenting a run and watching it sit
at 0 across 10/10 training_step calls.

Two places in this codebase read trainer.global_step and both broke
silently as a result:
  - module.py's PanelCallback/OrbitCallback/ScaleLayersCallback all gate
    their "step" cadence on `n = trainer.global_step; if n == 0 or n %
    every_n_steps != 0: return` -- with n stuck at 0, that first
    condition is always true, so none of them EVER fired for a single
    fit_3dgs.py run. Verified via the wandb API: every prior fit_3dgs.py
    run (both COLMAP and h5, both "set" and "layered" layout) logged
    zero panel/orbit media, only scalar metrics.
  - fit_3dgs.py's own get_preview_source() used trainer.global_step as
    its cache key -- even once the above were fixed, this would have
    kept returning the exact same frame from the FIRST cache miss
    forever (same key every call), instead of a fresh one each time
    cadence fires.

Fix: module._completed_steps(trainer, pl_module) -- trainer.global_step
for a LightningModule using automatic optimization (fit_gsplat.py/
train_gs.py, both unaffected, since Lightning drives their single
optimizer's .step() itself), pl_module.step_count for one using manual
optimization (fit_3dgs.py already tracks that, accurately, for its own
should_stop/LR-schedule/SH-degree-ramp bookkeeping). All three
module.py callbacks now read cadence through it; fit_3dgs.py's
get_preview_source() cache key uses self.step_count directly.

Verified: a 40-iter run with callbacks.panel.every_n_steps=10 and
callbacks.orbit.every_n_steps=20 synced 12 media files this time (was
always 0) -- 4 distinct panel PNGs (steps 0/2/5/7) and 2 distinct orbit
MP4s each for train/val (steps 3/8), confirming both the cadence gate
and the cache-key fix (different content each firing, not the same
frame repeated).

fit_3dgs.py: opacity_reset_interval=null properly disables the reset
…
60391bc
```
Was: disabling periodic opacity reset meant a caller had to know to pass
some CLI number bigger than iters (e.g. opacity_reset_interval=1000000)
-- a magic sentinel with no meaning of its own, easy to get wrong (too
small and it quietly still fires; tied to nothing if iters ever changes).

gsplat.strategy.DefaultStrategy itself has no boolean "off" for this --
checked directly against gsplat-src and its own examples, reset_every is
always a plain int, gated only by `step % reset_every == 0 and step > 0`.
So the sentinel can't be avoided at the library level, but it doesn't need
to leak to the config surface: opacity_reset_interval=null now means
exactly what it says, and __init__ does the int(cfg.iters) + 1 conversion
itself, once, in one place, documented -- not something every caller has
to reinvent.

Verified by spying on gsplat.strategy.default.reset_opa: null -> 0 calls
across 25 iterations, opacity_reset_interval=10 (unaffected default path)
-> 2 calls as expected.

fit_3dgs.py: layered mode -- means = frozen original + optimizable of…
…
e345c0c
```
…fset

Was: layered mode's means was one free tensor, initialized to the
depth-peel-seeded position, indistinguishable afterward from set mode's
fully-free xyz. Now: means_original (a buffer, requires_grad=False,
never touched by any optimizer) holds the seeded position permanently;
self.params["means"] is repurposed to hold an OFFSET from it instead
(zero-initialized, so training starts exactly at the seed), still a
real Parameter with its own Adam optimizer -- "original should be
frozen, offset should be optimizable" means self.params["means"]'s key
name doesn't change (gsplat.strategy.DefaultStrategy.check_sanity
asserts "means" is present in both params and optimizers_dict), just
what it represents does.

Fit3DGSLightningModule._active_means() is the one place that resolves
means_original + offset into the actual world-space position --
render()/get_preview_source()/run_final_eval()/params_np() all go
through it now instead of reading self.params["means"] directly as if
it were always a position (params_np() specifically: the saved .h5/
.ply/grid.h5 all still get real positions, not raw offsets, so no
output-format changes needed).

Added cfg.mean_offset_reg_weight (default 0.01, untuned): an L2 penalty
on the offset itself (self.params["means"].pow(2).sum(-1).mean()),
added to the train loss only, pulling Gaussians back toward their
seeded origin instead of letting the offset drift unconstrained. No
effect in "set" mode -- means has no offset split there at all,
_active_means() just returns self.params["means"] unchanged.

Verified: means_original.requires_grad is False, the offset's
requires_grad is True and its magnitude actually grows away from zero
during training; _active_means() == means_original + offset exactly;
the saved .h5's "means" dataset is in real-position range (~[-0.5,
0.5], matching the object's known unit-cube normalization), not the
offset's much smaller range; higher mean_offset_reg_weight measurably
shrinks the trained offset's magnitude (mean squared offset: 8.9e-5 at
weight=0 vs 7.9e-5 at weight=1.0, same seed/steps); "set" mode
regression-checked unchanged (identical Gaussian count/loss on truck).
