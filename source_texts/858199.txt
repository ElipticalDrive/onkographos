Hi @benjaminum,
I'm a mechanical engineer and I've been using Open3D for the past year or so for a handful of related applications which are either related to working with 3d mesh data from structured light scanners or doing simulations to guide the design of industrial robotic workcells.
A few weeks ago I ended up implementing triangle intersections using Open3D's TriangleMesh in order to check line of sight between points in a scene, as well as test if points were inside specific volumes. It's not quite a raytracing application in the classical sense, but it ran too slowly to be useful until I put a BVH around it.
I followed this implementation:
http://geomalgorithms.com/a06-_intersect-2.html#intersect3D_RayTriangle()
...and what I noticed is that about half of the calculations for each triangle are unique to the triangle and have nothing to do with the ray being tested. I also noticed that the second part of the algorithm is simply a test to determine if a point is within the bounds of a triangle, which is also useful when projecting a point onto a set of triangles.
So, to answer your question, my personal applications aren't classical raytracing, but would typically involve ray and segment checks against triangle meshes for measurement, simulating vision, inside/outside.
From my perspective as a user of Open3D:
I think it would be useful to have a general purpose ray/segment/line to triangle intersection algorithm that doesn't require a lot of setup to use, as the occasional quick check on single rays/segments is a common thing to need but most libraries require a lot of setup to accomplish this, since most ray/triangle intersection software and literature are graphics and are highly optimized
That being said, most applications involve a large number of rays being tested against a large number of triangles, so I think it would be important to reasonably consider performance during the implementation by avoiding repeated work and making sure that data structures are thread-safe.
I personally favor having simple, un-opinionated constructs that expose the core feature, then providing several opinionated, complex constructs that are meant for more specific, higher performance applications. Users who's use-case fits into the bounds of an opinionated option can use it, but those who can't aren't forced to re-invent the wheel from nothing. I don't want to have to create an entire TriangleMesh and initialize a BVH around it, then prepare a 'batch' containing a single ray in order to check against a single triangle. It would still be great to have a BVH that could be generated from a TriangleMesh and could run ray batches against it, but hopefully the core classes/structs that was built on would be exposed so that I could just check my one triangle against my one ray.
Embree looks great, but looks highly specialized towards graphics raytracing. My personal feelings are that if I was trying to do a graphics oriented problem I'd probably go deep into one of the highly specialized libraries like Embree or something GPU based. What I really value about Open3D (and this is just me, other users and the maintainers may feel differently) is that it's a general purpose, relatively efficient 3D toolkit that compiles on a lot of different platforms without too much hassle that I can use as a starting point when I need to create my own tools or do something slightly off the beaten path.
