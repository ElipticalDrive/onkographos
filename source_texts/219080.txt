Some things to be aware of for future work on Potree.
Handling large number of individual point clouds
Better control of near/far plane. Perhaps allow custom values as well.
Attributes
Handle arbitrary number of attributes, and composites of arbitrary combinations of attributes
Handle different classes of attributes: scalar (intensity), vector of scalars (normals), RGB values, enumerations (classification, source ID, ...), double values (GPS Time)
Automatically display the most suitable attribute. E.g. rgba by default; if rgba not available or zero, try intensity or some other. (Intensity Value Display #867 (comment))
File Format
Single file for octree data, multiple files for metadata? e.g. cloud.json, hierarchy.data, octree.data, ...
User Interface
Display current projection. E.g. in Measurement Panel, show projection along with the coordinates.
Misc
Support named projections as well as proj4 strings. Currently only proj4 strings are supported. (add correct access to named projections like they are used in proj4js #729)
Support layers. Each layer can contain arbitrary amounts and types of objects. Show/hide layers.
Render only if necassary. To save battery & reduce power consumption/heat/fan noise.

So addressing the concerns:
Typescript does take time to build but it is a couple seconds that could shore up the ability to extend and make it easier to use Potree as an API. I do understand the hesitation though and the added complexity that comes with it. I think looking at where the JS community is heading and how modern libraries are used/extended a strongly typed library is easier to interface with and easier to maintain long term as typescript would ideally help reduce the variabilities naturally introduced.
Would you consider 3 interfaces? Just the visualizer, no toolbar, minimal and full featured? This would allow for the visualizer to be used without needing the toolbar. The toolbar is great but if others wanted to pull potree into their react/angular/etc app, the visualizer could be all they want with the ability to build tools on top of it using common methods exposed by potree. (This type of extension would also be made easier with typescript since the extending apps would know what to pass and expect from the functions without needing to go to documentation or through the code)
Can you explain the additional overhead? I'm not sure I understand where the complexity would be except if it is the pushing the repo to npm on tags. The argument for potree being an npm package could also be made that inorder to keep potree as small as possible, we can make it just a pointcloud visualizer, then for each type of file (metadata.json, ept.json, copc, laz) there is a library that can be loaded to enable that view. This would reduce the need to maintain all types of packages inside the main potree repo.
For the dependencies, I do agree that the community has hyper optimized no repeat code to a detriment, but by pulling in the libs to the package, it does make it more difficult to manage or to hot swap packages for specific needs. It also makes it difficult to know the full versions that are used which leads to questions like: "Was this edited for potree? Is this the stock version?" It also creates some challenges knowing which libraries are true dependencies.

Don't get me wrong, I love static typing and would love to use Typescript, but any build time above 1 second is already 1 second too long. I tried typescript multiple times, and it was always too long. I prefer to develop by "immediately" seeing code changes with ctrl+s and F5, without having to wait multiple seconds.
A basic visualizer is what I'm after anyway. Potree will be a point cloud rendering app, with optional GUIs on top. It won't come without the visualization part, though.
As for the other two bullet points, I don't really want to deal with npm. If someone does, they are welcome to, as long as it adheres to the licensing which will probably be AGPL and not FreeBSD anymore. (To hopefully put a bit of a damber on SaaS commercialization with no financial contribution back to Potree)

Odnosząc się do obaw:
Budowa Typescriptu zajmuje trochę czasu, ale jest to kilka sekund, które mogą wzmocnić możliwość rozszerzenia i ułatwić korzystanie z Potree jako API. Rozumiem jednak wahanie i związaną z tym dodatkową złożoność. Myślę, że patrząc na to, dokąd zmierza społeczność JS i jak nowoczesne biblioteki są używane/rozszerzane, biblioteka silnie typizowana jest łatwiejsza w interfejsie i łatwiejsza w utrzymaniu w dłuższej perspektywie, ponieważ maszynopis idealnie pomógłby zmniejszyć naturalnie wprowadzone zmienności.
Czy rozważyłbyś 3 interfejsy? Tylko wizualizator, bez paska narzędzi, minimalny i w pełni funkcjonalny? Umożliwiłoby to korzystanie z wizualizatora bez konieczności korzystania z paska narzędzi. Pasek narzędzi jest świetny, ale jeśli inni chcieliby wciągnąć potree do swojej aplikacji response/angular/etc, wizualizator może być wszystkim, czego chcą, z możliwością budowania na nim narzędzi przy użyciu typowych metod ujawnianych przez potree. (Ten rodzaj rozszerzenia byłby również łatwiejszy dzięki maszynopisowi, ponieważ aplikacje rozszerzające będą wiedziały, co przekazać i czego oczekiwać od funkcji bez konieczności przechodzenia do dokumentacji lub przez kod)
Czy możesz wyjaśnić dodatkowe koszty ogólne? Nie jestem pewien, czy rozumiem, gdzie byłaby złożoność, z wyjątkiem sytuacji, gdy jest to pchanie repozytorium do npm na tagach. Argumentem za tym, że potree jest pakiet npm, może być również to, że aby utrzymać potree tak małe, jak to możliwe, możemy zrobić z niego tylko wizualizator chmury punktów, a następnie dla każdego typu pliku (metadata.json, ept.json, copc, laz) istnieje biblioteka, którą można załadować, aby włączyć ten widok. Zmniejszyłoby to potrzebę utrzymywania wszystkich rodzajów pakietów w głównym repozytorium potree.
Jeśli chodzi o zależności, zgadzam się, że społeczność hiper zoptymalizowała bez powtarzania kodu ze szkodą, ale ściągając biblioteki do pakietu, utrudnia to zarządzanie lub wymianę pakietów na gorąco dla określonych potrzeb. Utrudnia również poznanie używanych pełnych wersji, co prowadzi do pytań typu: „Czy to było edytowane dla potree? Czy to jest wersja standardowa?” Stwarza również pewne wyzwania, wiedząc, które biblioteki są prawdziwymi zależnościami.
