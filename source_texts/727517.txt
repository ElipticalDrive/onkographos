The current implementation of Physics::Transformations::Rotations::rotation_matrix_3d requires axis of rotation and the angle of rotation as separate arguments. However, this creates a bit of a restriction when the angle is small.
For some applications, "rotation vector" (say v) is used to represent a 3D rotation as a field where the axis and angle are not known apriori separately. The rotation matrix is computed taking the exponential of the skew-symmetric composed using the rotation vector (refer Axis–angle representation). The Rodrigues formula is a closed-form expression of this exponential and requires axis and angle to be given (which is what the current implementation uses). Now to compute the axis and angle from v, one simply uses axis=v/norm(v) and angle = norm(v). However, as one can see the axis becomes undefined when norm(v) is close to 0. In such a case one would need to use the series expansion of the exponential up to an order of the required accuracy.
It would be nice to have such a scenario taken care of in Physics::Transformations::Rotations::rotation_matrix_3d.

Perhaps I don't quite understand the issue. Are you saying that the existing implementation, given by
```
template <typename Number>
Tensor<2, 3, Number>
Physics::Transformations::Rotations::rotation_matrix_3d(
  const Tensor<1, 3, Number> &axis,
  const Number               &angle)
{
  // Make things work with AD types
  using std::abs;
  using std::cos;
  using std::sin;

  Assert(abs(axis.norm() - 1.0) < 1e-9,
         ExcMessage("The supplied axial vector is not a unit vector."));
  const Number c              = cos(angle);
  const Number s              = sin(angle);
  const Number t              = 1. - c;
  const Number rotation[3][3] = {{t * axis[0] * axis[0] + c,
                                  t * axis[0] * axis[1] - s * axis[2],
                                  t * axis[0] * axis[2] + s * axis[1]},
                                 {t * axis[0] * axis[1] + s * axis[2],
                                  t * axis[1] * axis[1] + c,
                                  t * axis[1] * axis[2] - s * axis[0]},
                                 {t * axis[0] * axis[2] - s * axis[1],
                                  t * axis[1] * axis[2] + s * axis[0],
                                  t * axis[2] * axis[2] + c}};
  return Tensor<2, 3, Number>(rotation);
}
```
is not accurate?
Or -- I think that's what you're saying -- this method cannot be used if someone wanted to encode everything with one argument (a vector with magnitude)? If this is your suggestion, would that be addressed by offering a second function that takes only one vector that encodes both direction and angle? We'd of course always be happy to take a patch that provides this functionality!
