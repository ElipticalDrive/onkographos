render: re-voxelize inverse resampling — hole-free coverage (#1619)
Closes #1619. Implements the architect's Option A (decision in the PR thread): replace the non-surjective forward scatter with inverse resampling so detached re-voxelize solids are hole-free at every size. Also fixes the Metal-only backend bug the verification uncovered: the sticky image-atomic scratch bind clobbered c_revoxelize_detached's params UBO at slot 16 on every encode after the app's first R32I distance-image bind, silently no-op'ing every re-voxelize fill dispatched after frame 1 (#1619 dropout root cause; per-kernel gating via the functionUsesImageAtomicScratch registry).
Problem
Forward scatter dispatches one thread per source voxel, rotates+rounds to a dest cell, and writes it. Forward rotation+round is not surjective onto the rotated-AABB lattice — covered dest cells get no source voxel, producing banded coverage holes / whole-face dropout on spinning DETACHED_REVOXELIZE solids (worse on small cubes).
Fix
While rotating, c_revoxelize_detached now dispatches one thread per dest cell of the rotated-AABB cube, inverse-maps it to the source via roundHalfUp(R⁻¹·c), and on a hit authors position + color + active for that dest slot from a per-pool source occupancy+color grid (C_DetachedRevoxelizeBuffer::sourceGrid_, seeded once alongside the resident locals). Surjective by construction → hole-free.
At identity the existing forward path runs unchanged (byte-identical to #1556).
Why the shared raster stays untouched
Slot i is redefined from "source voxel i" to "dest cell i". The compact → stage1 → stage2 path still reads position[i]/color[i]/active[i] and rasterizes active slots — no shared-shader edit. The GPU authors color + active per dest slot (CPU skips those uploads in inverse mode), the dispatch + frame voxelCount walk the dest-cell count, and the model-space canvas marks every dest chunk visible. Dest cube sized to the rotation-independent bounding-sphere AABB (architect-blessed memory tradeoff over the closed-form bound).
New binding kBufferIndex_RevoxelizeSourceGrid (aliases legacy unused slot 9 to stay inside Metal's 0–30 cap). RevoxelizeDetachedParams extended to the dispatch-domain descriptor (std140 64 B, static_asserted). GLSL + Metal in lockstep.
Exposed-face mask is unaffected — re-voxelize already bypasses it (visibleFaceIds_.w = 1), so no per-dest-cell neighbour probe is needed.
voxel/CLAUDE.md updated to document the two-mode fill.
Metal: image-atomic scratch (slot 16) now binds only for the five kernels that declare it, so it can never alias kBufferIndex_RevoxelizeDetachedParams again. Like threadgroupSizeForFunctionName, the registry does not self-detect — new scratch-consuming kernels must be added to it.
Verification (macOS / Metal, pose-deterministic)
Captured with --no-spin per the architect's direction (proof solids hold their off-cardinal initialRotation; deterministic fixed-step capture). Before = merge-base build: the teal proof cube shows the forward-scatter coverage banding AND sits at a frozen near-cardinal pose — both facets of the pre-fix Metal scratch clobber, which froze every re-voxelize fill at its frame-1 output. After = this branch: correct held pose, hole-free coverage, all solids present (proof solids, 5 canary cubes, orbit re-voxelize shapes).

NEEDS-DESIGN
Instrumented the re-voxelize fill + downstream raster per the issue's "instrument-first" mandate. The diagnosis in the issue is correct (forward scatter is non-surjective → holes), and it reproduces on current master. But the lead approach as written can't be a drop-in, because of a data-model constraint the one-liner glosses over. Surfacing it so you can pick the approach (the issue already says "architect picks after instrumenting").
What the code actually does (the binding constraint)
The re-voxelize fill (c_revoxelize_detached.{glsl,metal}) is one thread per source voxel slot voxelId; it writes globalPositions[voxelId] (binding 5). The downstream raster then reads, all keyed by that same voxelId slot:
globalPositions[voxelId] — binding 5 (position)
voxels[voxelId].colorPacked / .materialFlagBone — binding 6 (color + exposed-face flags), c_voxel_to_trixel_stage_{1,2}.glsl
activeMask[voxelId>>5] — binding 8, c_voxel_visibility_compact.glsl
These three bindings are shared with the main world-canvas raster (same compact → stage1 → stage2 path), and the identity/cardinal fast path must stay byte-identical. The compact pass dispatches liveVoxelCount slots; stage1/2 read color/flags from the pool's own ColorBuffer by slot.
The inverse-resampling lead dispatches over destination cells and fills cell c iff roundHalfUp(rotateByQuat(c, conj(quat))) ∈ source occupancy. That's surjective (hole-free) — but its output is destination-cell-indexed, and the number of occupied dest cells can exceed the source voxel count (a rotated solid's discretized cell count grows on the diagonal). So you can't just "change globalPositions to a dest-cell index": dest cell j needs (a) a slot to live in, (b) the color of whatever source voxel inverse-maps to it, and (c) an active bit — none of which line up with the source-indexed ColorBuffer/active-mask the raster reads.
The architectural question(s)
How should resampled dest-cell colors reach the raster, given color is read from the source-indexed ColorBuffer (binding 6) shared with the main canvas?
How should the re-voxelize pool be sized, given correct inverse coverage needs up to the worst-case rotated-AABB occupied-cell count (> source count), not the authored source count?
Must the fix stay on the shared compact/stage1/stage2 bindings, or is a re-voxelize-private mini-raster acceptable?
Options (you pick; I don't have to be right)
A — Resize + resample-write. Size the re-voxelize private pool to the worst-case rotated-AABB occupied-cell count. Change the fill from "write rotated position of my source voxel" to "I am dest cell c_i: if inverse(c_i) is occupied, write position[i]=c_i, color[i]=color[inverse(c_i)], active[i]=1, else active[i]=0." Keeps the shared raster contract (slot i is self-consistent across all three bindings) at the cost of: a source-occupancy lookup (hash/bitset of authored locals + CPU mirror), a bigger pool, and the fill now writes color (today it only writes position). Hole-free by construction; needs a CPU mirror for bit-identity and a clean identity fast-path.
B — Color-indirection buffer. Keep the pool source-sized; add a per-dest-slot indirection (destSlot → srcVoxelId) the raster consults for re-voxelize pools only. Smaller memory delta but touches the shared raster shaders with a re-voxelize branch (parity + fast-path risk).
C — 3D morphological dilation of the forward-scattered set (issue's stated fallback). Cheaper, approximate; still needs extra slots for the added cells, so it shares A/B's sizing problem in a smaller form.
D — Source supersampling. Seed residentLocals at K× sub-cell density so forward scatter over-covers. Preserves the forward-scatter data model but multiplies pool size + color entries by K. (voxel/CLAUDE.md notes supersampling was considered-and-deferred for the related render: re-voxelize P3 — spinning-shape temporal noise, culling clip, and 3-face visibility #1570 temporal-flicker concern.)
My lean is A (genuinely surjective, keeps the shared contract self-consistent, matches the issue's "inverse resampling" intent), but it makes the fill author colors and resize the pool — a contract change with parity blast-radius across the shared raster, so it's your call, not mine. Once you pick, any opus-worker can resume from this PR (claim commit + plan + this thread).

Architect decision — design-unblocked → Option A
Excellent escalation: instrument-first, confirmed the repro on master, and surfaced the real binding constraint instead of forcing the one-liner. The lead stands, with the data-model question answered.
Decision: Option A (resize + resample-write). Reject B, C, D.
The reason A wins: it keeps the slot-indexed contract byte-identical and only redefines what slot i holds — "dest cell i" instead of "source voxel i". The shared compact → stage1 → stage2 raster is UNTOUCHED (it still reads position[i] / color[i] / active[i] and rasterizes active slots). The whole change confines to the fill + pool sizing + a source lookup. That's exactly why B is worse — it branches the shared raster shaders for re-voxelize, putting main-canvas byte-identity and Metal parity at risk. C (dilation) and D (supersampling) are approximate — they don't solve it once and for all (the user's explicit goal), so not the primary; keep C only as a fallback if A's sizing is prohibitive.
Your three questions
Colors — the fill authors dest-cell color per frame into the re-voxelize pool's own ColorBuffer (color[i] = srcColor(inverse(c_i))). Re-voxelize-only; the main canvas still seeds its ColorBuffer once and is unchanged. Add a source-color lookup beside occupancy (pack into residentLocals.w or a parallel resident-colors buffer). stage1/2 just read color[i] → no shared-shader change. Same for the active bit: the fill sets per-slot active so empty dest cells (inverse miss) are inactive, in whatever representation c_voxel_visibility_compact already consumes.
Pool sizing — size to a closed-form bound = occupied volume + one-cell boundary shell (≈ N³ + C·N², C≈6), not the loose rotated-AABB cube (~5×) and not the source count. Rotation is volume-preserving; only the discretization boundary grows. Derive the exact bound CPU-side. If the closed form is fiddly, fall back to the AABB cell count (accept the memory) — never a hard cap that silently drops cells (that reintroduces the holes).
Shared bindings — stay ON the shared contract via dest-cell slot semantics. Do not add a re-voxelize branch to the shared raster shaders.
Constraints (re-emphasized)
CPU mirror replicates the inverse resampling bit-identically (roundHalfUp on inverse(c)).
Identity fast-path byte-identical: at identity inverse(c)=c → dest = source, color = seeded, position = source. Short-circuit to today's behavior.
GLSL↔Metal parity in lockstep. DoD unchanged: hole-free at all sizes, no whole-face dropout on the small canary cubes, thin-shape guard re-enabled, render-verify ROI committed.

Nits (addressable with fleet:has-nits):
N1 — destCount vs maxSingleVoxels bound (detached_revoxelize.hpp:119-122, system_voxel_to_trixel.hpp:320-355):
The shared GPU buffers (voxelPosBuf_, voxelColorBuf_, voxelActiveMaskBuf_) are all sized to maxSingleVoxels, but destCount = (2*ceil(maxRadius)+1)^3 is architecturally uncapped. For current small rotating solids (e.g. 100-voxel sphere → maxRadius ≈ 3 → destCount ≈ 343) this is safe. For elongated models (64×1×1 bar → destSide ≈ 65 → destCount ≈ 274k) or a dense pool near the total capacity, threads with slot >= maxSingleVoxels would write out-of-bounds into the shared SSBOs — the if (slot >= dest_.x) return; guard only prevents access beyond destCount, not beyond the buffer allocation. Consider a CPU-side clamp destCount_ = IRMath::min(destCount_, maxSingleVoxels) in seedResidentLocals, or document the invariant that DETACHED_REVOXELIZE pools are bounded such that destCount <= maxSingleVoxels.
N2 — Divergent inverse condition (system_voxel_to_trixel.hpp:291-292 vs :514-516):
tick() derives revoxInverse from revoxBuffer->isAllocated() (residentLocals_.second != nullptr), while dispatchReVoxelize() re-derives inverse from buffer.sourceGrid_.second != nullptr. Both resolve identically in practice since seedResidentLocals allocates both buffers atomically. However, if these diverged, revoxInverse == true in the caller would skip CPU color/active uploads while inverse == false inside dispatchReVoxelize would run MODE 0 (positions only) — corrupting the dest-slot active state. Unifying the condition (e.g. dispatchReVoxelize accepts a caller-derived bool isInverse) would eliminate the latent divergence.
