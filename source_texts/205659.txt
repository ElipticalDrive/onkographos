Issue body actions
Problem
The raytracer's surface layer (src/surfaces/) contains exactly three concrete types — Sphere (sphere.py), Cube (cube.py), and InfinitePlane (infinite_plane.py) — all registered through src/surfaces/__init__.py. There is no polygon primitive, which means the renderer cannot represent any real-world geometry. The scene format is a custom text dialect (evidenced by src/scenes/pool.txt), so OBJ meshes have no ingestion path at all. This ticket adds:
A Triangle surface that fits the existing Surface contract (src/surfaces/surface.py).
A load_obj() function that converts an OBJ file into a flat list of Triangle instances ready to be added to a scene.
Acceptance criteria
src/surfaces/triangle.py defines a Triangle class that subclasses the abstract Surface base from src/surfaces/surface.py.
Triangle.__init__ accepts three Vector3 vertices (v0, v1, v2) and a Material, matching the constructor signature pattern used by Sphere and Cube.
Triangle.intersect(ray) implements the Möller–Trumbore algorithm, returning a RayHit on a valid hit (t > ε, u ≥ 0, v ≥ 0, u+v ≤ 1) and None otherwise.
The returned RayHit carries the correct interpolated or flat face normal; face normal ((v1−v0) × (v2−v0)).normalize()) is the baseline — smooth normals are out of scope.
Triangle is exported from src/surfaces/__init__.py alongside Sphere, Cube, and InfinitePlane.
src/surfaces/triangle.py also exposes load_obj(path: str, material: Material) -> list[Triangle] that parses v and f lines from a Wavefront OBJ file and returns one Triangle per triangulated face; non-triangular faces (quads, n-gons) are fan-triangulated.
The scene description format (.txt) gains an obj <path> <material_name> directive that the scene loader (src/scene.py) resolves by calling load_obj and extending the surface list.
A new scene file src/scenes/teapot.txt (or any low-poly OBJ asset checked into src/scenes/) renders without NaN pixels or self-intersection fireflies at the default settings.
Unit tests in tests/test_triangle.py cover: definite hit (ray passes through centre), definite miss (ray aimed away), parallel ray (determinant ≈ 0), ray hitting edge/vertex boundary, backface ray with culling disabled.
All existing tests and the pool.txt scene continue to produce identical output (no regression).
Implementation approach
1. src/surfaces/triangle.py — new file
```
from src.surfaces.surface import Surface
from src.ray_hit import RayHit
from src.vector3 import Vector3
from src.consts import EPSILON   # verify name — consts.py likely defines a small float

class Triangle(Surface):
    def __init__(self, v0: Vector3, v1: Vector3, v2: Vector3, material):
        self.v0, self.v1, self.v2 = v0, v1, v2
        self.material = material
        edge1 = v1 - v0
        edge2 = v2 - v0
        self.normal = edge1.cross(edge2).normalize()   # flat face normal, precomputed
        self._edge1 = edge1
        self._edge2 = edge2

    def intersect(self, ray):
        h = ray.direction.cross(self._edge2)
        det = self._edge1.dot(h)
        if abs(det) < EPSILON:
            return None           # parallel
        inv_det = 1.0 / det
        s = ray.origin - self.v0
        u = inv_det * s.dot(h)
        if u < 0.0 or u > 1.0:
            return None
        q = s.cross(self._edge1)
        v = inv_det * ray.direction.dot(q)
        if v < 0.0 or u + v > 1.0:
            return None
        t = inv_det * self._edge2.dot(q)
        if t < EPSILON:
            return None
        hit_point = ray.at(t)     # assumes Ray.at(t) exists; see ray.py
        return RayHit(t=t, point=hit_point, normal=self.normal, material=self.material)
```
Verify before writing: Open src/ray.py to confirm the method that evaluates origin + t*direction (likely ray.at(t) or ray.point_at(t)). Open src/ray_hit.py to confirm the exact constructor signature — it may be a dataclass, a namedtuple, or a plain class, and parameter names may differ (e.g. distance not t). Match exactly.
2. src/surfaces/__init__.py — add one import
The existing file almost certainly has a pattern like:
```
from src.surfaces.sphere import Sphere
from src.surfaces.cube import Cube
from src.surfaces.infinite_plane import InfinitePlane
```
Add:
```
from src.surfaces.triangle import Triangle
```
If there is a SURFACE_TYPES dict mapping string keys to classes (used by the scene loader), add "triangle": Triangle.
3. OBJ loader — in src/surfaces/triangle.py
```
def load_obj(path: str, material) -> list:
    vertices = []
    triangles = []
    with open(path) as f:
        for line in f:
            parts = line.split()
            if not parts:
                continue
            if parts[0] == 'v':
                vertices.append(Vector3(float(parts[1]), float(parts[2]), float(parts[3])))
            elif parts[0] == 'f':
                # OBJ indices are 1-based; strip texture/normal suffixes (e.g. "1/2/3" → 1)
                indices = [int(p.split('/')[0]) - 1 for p in parts[1:]]
                # fan triangulation for quads/n-gons
                for i in range(1, len(indices) - 1):
                    triangles.append(Triangle(vertices[indices[0]],
                                              vertices[indices[i]],
                                              vertices[indices[i+1]],
                                              material))
    return triangles
```
Scope limit: Ignore vn, vt, mtllib, usemtl, o, g lines entirely for now. The caller supplies a single Material for the whole mesh.
4. src/scene.py — OBJ directive in scene parser
Read src/scene.py first to understand how the pool scene is parsed. The text format for pool.txt likely has one directive per line (sphere, cube, etc.) followed by parameters. Add handling for:
```
obj assets/teapot.obj matte_white
```
In the parsing loop, when the directive token is obj:
```
from src.surfaces.triangle import load_obj
# ...
elif token == 'obj':
    path, mat_name = params[0], params[1]
    material = materials[mat_name]   # adjust to actual material lookup pattern
    self.surfaces.extend(load_obj(path, material))
```
Path resolution: Make the OBJ path relative to the scene file's directory, not the CWD, to avoid breakage when the renderer is invoked from different directories.
5. Test asset
Check in a small OBJ into src/scenes/ (e.g. a 4-face tetrahedron hand-authored or a Creative Commons low-poly mesh). Do not check in a full Utah Teapot (15k faces) — it will make the unaccelerated renderer unusably slow and inflate the repo. A 50–200 face mesh is sufficient to validate correctness.
6. tests/test_triangle.py — new file
Test cases must construct Triangle directly (not via the scene file) so they are isolated from the parser:
```
# hit through centroid
# miss: ray parallel but offset
# parallel: ray direction coplanar with triangle
# very-near-zero t rejected
# quad fan-triangulation in load_obj produces 2 triangles
```
Risks & edge cases
Risk
Detail
RayHit constructor mismatch
ray_hit.py constructor parameters are unknown. If it uses positional args or different names the Triangle.intersect return will silently pass wrong data. Read ray_hit.py before writing a single line.
Vector3 operator coverage
Möller–Trumbore needs -, .dot(), .cross(), scalar multiply, and .normalize(). vector3.py may be missing one (e.g. cross is rare in minimal implementations). Check before assuming.
Ray.at(t) method name
ray.py may expose point_at, at, or no helper (requiring inline ray.origin + t * ray.direction).
EPSILON name in consts.py
Might be EPS, EPSILON, SMALL, or a bare 1e-8 inline literal. Using the wrong name causes an AttributeError at runtime.
Scene text format delimiters
pool.txt format is unknown — it could be whitespace-delimited, CSV, or key=value. The OBJ directive must follow whatever convention exists, not introduce a new one.
Performance with no BVH
Even a 200-face mesh adds 200 intersection tests per ray per bounce. At 500×500 with 4 bounces that is 200M extra calls. Flag this in the PR and document that BVH acceleration is the natural next step.
Negative OBJ indices
OBJ allows negative (relative) indices (f -3 -2 -1). The loader above does not handle them. Document as a known limitation.
Winding order and normal direction
OBJ convention is counter-clockwise = front face. If the scene camera looks at the back of an OBJ mesh, all face normals will point away and the mesh will appear black. The fix is either two-sided lighting in ray_tracer.py or noting that meshes must be oriented correctly.
load_obj path in tests
Unit tests that exercise load_obj need a fixture OBJ file. Use tmp_path (pytest) to write a minimal OBJ inline rather than depending on a repo asset path.
Open questions
Does surface.py define an abstract method signature? If intersect has a different name or signature (e.g. def hit(self, ray, t_min, t_max)), the new class must match it exactly — Möller–Trumbore's early-exit logic may need to move inside those bounds.
Does the scene loader hold surfaces in a flat list or a spatial structure? If ray_tracer.py iterates a flat scene.surfaces list, adding hundreds of triangles works but is O(n) per ray. If there is already a BVH stub, triangles should be inserted into it.
Is Material passed by name string or by object reference in the scene file? The OBJ directive proposal assumes a materials dict keyed by name — confirm against how pool.txt references materials.
Should backface culling be on or off by default? For closed meshes culling is fine and cheaper; for single-sided panels or inverted normals it causes invisible geometry. Recommend a cull_backfaces=False kwarg on Triangle.__init__ (default off) and document it.
Is there a test harness / CI already? The file tree shows no tests/ directory. Confirm where tests should live and how they are run before creating tests/test_triangle.py.
