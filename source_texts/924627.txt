Question
What state does a Minecraft chunk depend on that is stored outside that chunk, and what would have to be repaired for an arbitrary individual chunk to be reverted to an earlier version without corrupting the world?
The map's fixed requirement is per-chunk cherry-pick rollback. This ticket establishes whether that requirement is cheap or expensive.
Inventory, for a current modded Minecraft version, everything that couples a chunk to the world around it or to global files:
Sky and block light propagation across chunk borders, and how the light engine behaves when a chunk's stored light no longer matches its neighbours
The separate entities/ region files introduced in 1.17, and how entity ownership relates to chunk ownership
POI / village section data
Structure references and structure start data, including starts that span chunks
Chunk status and the world-generation state machine — what happens when a full chunk is replaced by an earlier full chunk with different neighbours
level.dat, scoreboard.dat, and anything else global that a chunk's contents can imply
Block entities and their cross-chunk references
How mod-added chunk data (attachments, capabilities, mod-specific NBT) is stored, and whether it survives the same treatment
For each, state whether a stale reverted chunk causes visible corruption, silent corruption, a crash, or nothing, and what repair — relight, POI rebuild, structure-reference rewrite — would fix it.
Also answer the question the map deferred: does expanding from a pure build canvas to arbitrary mods break per-chunk rollback? If the answer is "it depends on the mod," say what property of a mod makes it safe or unsafe.

Findings: docs/research/chunk-external-state.md (branch research/chunk-external-state)
Verdict: cheap for a purpose-built build canvas, expensive for a vanilla-worldgen world — and the difference is one world-creation decision that cannot be made later.
The failure modes sort into three tiers.
Tier 1 — mechanically repairable, cheap. Light and POI are the only chunk-external state fully derivable from blocks, and the engine rebuilds both from a single flag: isLightOn = 0 (chunk + its 8 neighbours) and POI Valid = 0. The POI format documents its own self-heal — when Valid is false "the entries in Records are removed and the value is set back to true when the chunk is loaded the next time" — and PoiManager.checkConsistencyWithBlocks(SectionPos, LevelChunkSection) re-derives POI straight from chunk blocks. Entities are not derivable, but they're cleanly separable: the revert unit is region/ + entities/ + poi/ for a chunk coordinate, never region/ alone.
Tier 2 — no repair exists, but avoidable by design. Structure references and worldgen features spill. Features "can at most write to a 3×3 chunk area centered on the placement chunk"; structure membership is a graph spanning an 8-chunk radius (addStructureReferences); a full chunk never re-runs either stage; and no vanilla command and no existing tool rebuilds structure references — MCASelector can only delete them. The corruption is silent: NaturalSpawner resolves structure-gated spawning through StructureManager off chunk-stored references, so a reverted chunk quietly stops counting as inside its fortress/monument/bastion with zero visual signal.
Highest-leverage finding: generate the build dimensions with structures disabled and undecorated terrain and this entire tier collapses to nothing. Generator settings live in level.dat and are fixed at world creation — this is a decision with a deadline.
Tier 3 — irreducible; bounds what "without corrupting the world" can mean. Multi-block spans cut by a chunk border (doors, double chests, beds, beacon pyramids, portal frames) will be left half-reverted and no tool can infer intent. Container contents duplicate on revert. Both are fine in creative and disqualifying for survival.
The deferred question: do arbitrary mods break per-chunk rollback?
They don't break the format, they break the guarantee. The discriminating property is sharp:
A mod is safe iff all of its authoritative state describing a chunk lives inside that chunk's own NBT. Unsafe iff it maintains out-of-chunk state referencing in-chunk positions.
Both loaders' sanctioned mechanisms are on the safe side — NeoForge Data Attachments serialize into the host NBT under neoforge:attachments, Fabric's Data Attachment API under NBT_ATTACHMENT_KEY on Entity/BlockEntity/ServerWorld/Chunk. Those revert atomically for free. The unsafe class is mods with a global index into chunks: SavedData/PersistentState BlockPos maps, energy/item networks, claim systems, chunk-loader ticket stores, sidecar dirs in the world folder. The doc has a 5-point audit checklist. Immersive Portals looks safe on this axis (portals are entities, so they ride in entities/). Cost is governance — re-audit per mod addition — not an architectural blocker.
Falls out for the Git representation (not this ticket's call, but load-bearing)
.mca cannot be the stored form. It is a sector-allocating, zlib-compressed, timestamp-stamping container where a one-chunk edit relocates sectors and rewrites the location table — a one-chunk change produces a whole-file binary diff, and cherry-picking a chunk out of a committed .mca blob is not a Git operation at all. Explode to one file per chunk; treat .mca as a build artifact. Also: normalize LastUpdate/timestamps or the repo churns on every save, and keep global files (level.dat, scoreboard.dat, maps, raids.dat, random_sequences.dat, playerdata) as a separate coarse tier that always follows HEAD.
Open, worth a cheap prototype
Current NeoForge/Fabric behaviour for an unknown block name in a reverted palette when a mod is removed between commits (drop to air / refuse to load / prompt). No first-party statement found; determines how strictly the mod list must be pinned.
Whether the isLightOn = 0 repair actually produces seam-free borders across a revert.
Confirm structures really is empty in the chosen build-dimension config — the load-bearing assumption behind the verdict.
Whether Immersive Portals writes dynamic-dimension config into level.dat (community-asserted, unconfirmed against source).
Full inventory with per-item on-disk location, failure class, and repair — plus a summary table and source list — is in the file. Leaving this open for triage.

Second pass — grounded in decompiled source, with material corrections
The file has been updated. The verdict is unchanged, but several claims got sharper and two were wrong.
Corrections to my first comment:
Heightmaps are not "nothing". The deserializer recomputes only the maps it can't find — if (nbt.contains(type.getName(), LONG_ARRAY)) chunk.setHeightmap(...) else enumSet.add(type) — so a present-but-wrong heightmap is trusted forever. It silently breaks mob spawn Y, lightning targeting, and snow/ice formation, with no visual artifact. It does not affect sky light (the light engine uses its own ChunkSkyLight). Repair is free: delete the Heightmaps compound on every revert.
The lighting seam is permanent, not merely stale. When isLightOn is set and Status ≥ light, ServerLightingProvider skips propagateLight entirely, then calls setLightOn(true) again — so the wrong values get re-saved as authoritative. And relight declares dependsOn(INITIALIZE_LIGHT, 1) while ChunkSkyLightProvider.propagateLight reads the 4 cardinal neighbours, so the 8 neighbours must be stripped too or their side of the seam stays frozen. Vanilla also writes the tag only when true — test for presence, not value.
New, and operationally important:
c.<x>.<z>.mcc sidecars. Chunks needing ≥256 sectors are written outside the region file, leaving a 1-sector stub with the compression id OR-ed with 128. A cherry-pick tool that ignores .mcc reverts the stub and keeps HEAD's payload — crash or gross corruption. Bulk schematic imports with fat palettes are exactly the chunks that exceed 1 MiB, so this is not a corner case for this project.
An unparseable Status is a crash, not a silent problem (Registries.CHUNK_STATUS.get is @Nullable, NPEs in getChunkType). Combined with the light-array length assertion, this argues that chunk NBT must never be exposed to Git's line-level merge.
features has blockStateWriteRadius(1) — confirmed verbatim in ChunkGenerationSteps, matching the wiki's "3×3 chunk area". And duplication is a risk of the naive repair, not of the revert: re-running features re-places the same feature onto modified terrain and appending features (vines, snow layers, block_pile) stack.
Starlight/Moonrise change the contract. They write isLightOn: false deliberately plus starlight.light_version (9 fabric / 10 Moonrise) and test presence, not truth. Cross-engine reverts self-heal for free; same-engine reverts are the dangerous case.
DataVersion = 3450 is a Mojang-authored one-field relight — ChunkDeleteLightFix at 3451 strips isLightOn and all light arrays. Doesn't dirty neighbours, so it's a supplement, not a substitute.
below_zero_retrogen is dead data on a full chunk (read only in the ProtoChunk branch). blending_data is the sneaky one — it's consumed when a neighbouring chunk generates for the first time, so reverting it at the worldgen frontier produces a seam later, in a chunk you never touched.
Nothing off the shelf performs the Tier 1 repair. MCASelector's NBT Changer has no isLightOn, no light arrays, no heightmap op; Chunky has no relight; there is no vanilla relight command; and /paper fixlight is unavailable because Map: Self-hosted server architecture with per-chunk version control #1 rules Paper out. This is ~20 lines the project has to write — small, but it must be written.
Region files churn worse than I said. Every single-chunk write rewrites both 4 KiB header sectors and stamps wall-clock seconds into the timestamp table, and free() runs after allocate() so even same-size rewrites can relocate. region-file-compression=none would make the intermediate form deterministic.
Net effect on the revert transaction. Per chunk: write region + entities + poi + any .mcc; then delete Heightmaps, strip isLightOn + starlight.light_version, set POI Valid = 0, drop block_ticks/fluid_ticks; then strip isLightOn on all 8 neighbours. Server stopped. That reduces every lighting and heightmap failure to nothing and leaves only the irreducible cross-chunk features problem — which the "structures off, undecorated terrain" world configuration eliminates entirely.
Source caveat now recorded in the file: class bodies are quoted from community Mojang-mapped/Yarn-mapped decompile mirrors, verified to 1.21.1 / 1.20.4. 1.21.5+ is unverified — ChunkSerializer was renamed SerializableChunkData and 1.21.9 reworked ticket types. Also, the wiki's Chunk format page does not document isLightOn at all; those semantics are source-only.
