Fixes #395.
Problem
While metal_raytrace is on, every frame re-tessellated every cylinder impostor (24 triangles each) and re-copied every mesh triangle into _rtTris on the CPU, only so that ensureRayTracingAS could hash a 1,024-sample subset and discover that nothing had changed. Model-space geometry is invariant under camera motion, so during a pure rotation all of that was wasted main-thread work.
Approach
Key the RT geometry on VBO identity instead of contents, as the issue suggests.
Spheres and triangles are extracted once per CPU buffer into an _rtGeomCache entry — keyed the same way _vboCache already keys its GPU uploads — and kept alive with it. A frame now only records which entries it drew, folding each entry's identity + generation into a running signature. ensureRayTracingAS compares that signature against the built one and, when it matches, does nothing at all: no gather, no concatenation, no hash.
Details:
Draw-call scalars the extraction depends on (mode, count, stride, offsets, sphereSizeScale, uniRadius) are hashed into the entry, so a setting change such as sphere_scale re-extracts even though the buffer pointer is unchanged.
invalidateVBOCacheEntry drops the matching RT entry. Indexed draws register their index buffer as an alias of the vertex buffer, so freeing either one drops the cached triangles.
Buffers that yield no RT geometry (lines, points) are cached empty and left out of the frame record, so churn in e.g. the selection-indicator CGO does not signal a geometry change and force an acceleration-structure rebuild.
The concatenated _rtTris vector is gone entirely: entries are written straight into the shared MTLBuffer the triangle AS is built from.
The frame record stores keys rather than RTGeom*, because an entry can be erased mid-frame by invalidateVBOCacheEntry while the concatenation runs one frame later.
The OIT/shadow passes still skip accumulation, unchanged.
The signature is now exact (identity + generation) rather than a sampled hash of coordinates, so it can no longer miss a change the old 1,024-sample subset would have missed.
Measurements
Rebased onto #396, which acquires the drawable after the scene is encoded. The two changes are complementary and the distinction matters for reading these numbers: #396 stopped the main thread parking in currentDrawable, but explicitly did not reduce SceneRenderMetal CPU (1637 -> 1515 samples in its own table). This PR removes that remaining CPU.
Baseline is a2cbd11 (master, with #396) built in the same worktree; 32 objects / 57,696 atoms, cartoon + sticks, cmd.rock(1), 10 s sample, window frontmost, Apple silicon.

Total physical footprint is unchanged (both dominated by GPU allocations), while CPU-side resident memory drops: retaining the per-VBO triangle lists costs about what the per-frame _rtTris vector it replaces did (~15 MB of sticks here), and dropping the intermediate copy plus the per-frame newBufferWithBytes churn more than pays for it.
Verification
Built the macOS app and drove two dev instances (fixed and baseline) side by side over MCP. Confirmed by screenshot that RT AO and traced shadows render identically, and that they correctly follow:
sphere_scale changes (params-signature re-extraction),
hide spheres / hide sticks — no ghost occlusion left behind where the geometry was,
translate of a selection — occlusion moves with the atoms, nothing stale at the old position.
