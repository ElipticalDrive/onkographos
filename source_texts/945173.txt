Tested versions
Reproducible in 4.8.dev7 (c971f93) and 4.8.beta2 (cafc17a).
Not reproducible with rendering/textures/streaming/enabled=false.
System information
macOS 15.5 (Darwin 24.5), Apple M4 (Apple9), Metal 3.2, Forward+, 1920×1080, MSAA 2×.
Issue description
After migration from 4.7 to frozen 4.8 my game performance deteriorated. I have isolated the case -enabling texture streaming greatly increases GPU time for textured meshes on my machine. If I disable it, got performance back almost like if it is untextured.
To reproduce it I did test repo with 36 overlapping spheres and four materials. Below you can find the test results,where each table cell contains results from two runs, in ms. Each result is the median of 8 rounds using viewport_get_measured_render_time_gpu. The material testing order changes between rounds.

Steps to reproduce
Open the attached project streaming-repro.zip from first comment on macOS using Metal and Forward+, with texture streaming enabled.
Run it with the window in front. It prints a RESULT line with GPU timings and quits.
Set rendering/textures/streaming/enabled=false, restart, and compare the results.

@vetertann
I profiled the MRP on master with both the Metal 3 driver and Vulkan (MoltenVK). At least on macOS 27.2, on the GPU, Metal isn't slower than MoltenVK. Most of the difference in the reported numbers comes from Godot's GPU timestamps, which read about 2 ms high on Metal. The material feedback atomic does have a cost, and it's about the same on both drivers.
Setup: Apple M4 Max, macOS 27.2 (26B123), master dev editor build, 1920×1080, MSAA 2×, MRP running only the textured material.
Reported vs actual GPU time
"Reported" is viewport_get_measured_render_time_gpu. "Actual" comes from an Instruments Metal System Trace. With streaming on the GPU is about 90% busy, so actual is the trace length divided by the number of frames rendered. With streaming off the GPU isn't saturated, so actual is the total fragment work per frame.
