Things found while profiling smooth-union rays in #282 (MeshCSG's scene, float, RTX 3080, 512×512). Each is independent of the shape being traced.
1. An intersection-only ray query
The public ray API has firstHit(), which returns everything (t, normal, primitive, entering), and intersects(), which returns only whether there is a crossing. A CFD code cutting cell edges, or a particle code that needs a collision distance, wants t (and perhaps the entering flag) and nothing else, but has no call that returns only that.
For a marched crossing, firstHit() always computes the normal by central differences of the shape's value (6 evaluations) and looks up the primitive. On a smooth-union fillet ray that is 6 of about 20 mesh-distance evaluations.
The query must report the hit point on the surface (as HitT::m_point does), not only t: that is what a cut-cell or collision code uses.
To decide: a query that returns the first crossing (status, t, point, whether the ray enters) without normal or primitive, as a new function (e.g. firstCrossing()) or a RayOptions switch on firstHit(); and whether ray forms skip their normal work too.
2. Shadow and occlusion rays need any crossing, not the first
Shader::shadow() calls firstHit() and reads only hit(), so every shadow ray that ends on a marched surface pays for a normal that is thrown away, and for refining the crossing. A shadow ray needs only some crossing: a marched intersects() can stop at the first sign change, with no refinement and no normal. Today a marched intersects() falls back to firstHit().
Check the occlusion rays the same way. This also covers part of #255 (shadow and occlusion rays of tapes that hold meshes).
3. The device renderer in one launch
Renderer::renderOnDevice() launches one synchronous kernel per band of rows (8 bands), so that a canceled render stops after the band under way. Each band is only about 1.25 waves of blocks for a 168-register kernel, and every launch waits for its slowest block. Measured against a single launch:

Cancellation and progress would then need a flag the kernel reads (and a counter it writes) instead of a check between launches.
Pixel order was measured too: row-major (today's) is fastest. 8×4 tiles were 12% slower, randomly shuffled 32-pixel segments 40% slower, and random pixels 2.6× slower (every warp then waits for a slow ray), so the order stays.
The renderer's view modes are in #284
The depth, x-ray and cost views first planned here are in #284, with see-through surfaces: they share the span-list query and the viewer's mode switch. #284 is the pull request right after this one, and builds on its hit-point query.
All three items above go in one pull request.
