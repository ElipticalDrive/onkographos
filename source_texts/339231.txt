When a code base is ported to AD, there is no built-in way to check that the derivatives clad generates agree with finite differences of the primal. Most of what that needs exists already: numerical_diff::central_difference(f, grad, printErrors, args...) is public and handles arrays, pointers and custom types (demos/CustomTypeNumDiff.cpp), and the flag infrastructure for the numerical-diff fallback gives a way to switch a mode per translation unit, per request, and to tell headers about it with a macro.
Step 1: a checking function, library only
```
auto grad = clad::gradient(f);
clad::check_report r = clad::check_gradient(f, grad, x, y); // AD vs central differences
if (!r.ok())
  r.print(); // the input that disagrees, AD vs FD values, abs/rel error
```
check_gradient runs grad.execute and numerical_diff::central_difference on the same inputs and compares each input's derivative against a combined relative and absolute tolerance, with defaults that can be overridden.
check_derivative(f, d, args...) does the same for forward mode.
No compiler change; tests cover a smooth function, a non-smooth one, and an array input.
Step 2: an automatic mode for a whole code base
A -fverify-derivatives switch, defined next to the numerical-diff fallback in Analyses.td, plus a clad::opts::verify_derivatives bit for one request.
When on, the plugin predefines a macro and every CladFunction::execute also runs the step 1 check, printing any mismatch with the function's name and source location.
The only compiler change: clad already rewrites clad::gradient(f) to pass the generated code, and would also pass the primal f.
Off by default: it costs about two primal evaluations per input on every call.
Where finite differences disagree with a correct derivative
The report should say so rather than count these as failures:
non-smooth code: abs, min/max, branches, and floor or round near a kink;
integer and enum inputs, which cannot take a small step (skipped);
primals with side effects or state, since finite differences call the function many times;
badly scaled inputs, where a fixed step loses accuracy (a per-input tolerance helps);
vector-valued and void functions with output parameters: step 1 starts with scalar-output gradients and forward derivatives, then extends to Jacobians.
