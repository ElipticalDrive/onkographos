Part 1 of the RUXP LOD extension accepted in #321 (see docs/research/potree-vs-ruxp-lod.md §6–7, Issue A).
Store the fused cloud in Morton/Hilbert curve order in the ProjectDB blobs at rux create clouds time, so any prefix of the stored points is a uniform spatial sample — prefix paging then doubles as LOD with no per-request server compute (this is #320's stated design goal: LOD and paging collapse into one mechanism).
Write path: sort points by Morton code of their voxel coordinates before chunking into blobs; record a storage_order=morton flag in the cloud metadata (additive schema/metadata change following the existing conventions).
Read path: point_lod.cpp skips the voxel-downsample pass when the flag says storage order is already spatial.
Determinism: same input cloud → same ordering (STANDARDS §6).
Existing projects without the flag keep the current path (no migration required).
Estimated effort per the research doc: ~1 week. Blocks #B (tile index) and #C (multi-level LOD).

Implementation complete — feat/morton-order-clouds-394
What was built
Write path (libs/reusex/src/segmentation/reconstruct.cpp):
After the outlier-removal step produces out_cloud / out_normals / out_labels, a Morton sort is applied before the DB write:
Compute the cloud's bounding box.
Quantise each point's x/y/z to 10-bit integers ([0, 1023]) relative to the bbox.
Interleave bits with expand3 (x→bits 0,3,6,…; y→1,4,7,…; z→2,5,8,…) to produce a 30-bit code.
std::stable_sort by code — ties resolved by storage index (STANDARDS §6).
Apply the same permutation to out_normals and out_labels (CONTRACTS.md §3.2).
Metadata (stays at schema v14): "storage_order":"morton_10bit" is injected into the existing parameters JSON column of the point_clouds table. No schema migration, no new column. Absent key → sequential/unspecified. Two new public API members:
ProjectDB::point_cloud_storage_order(name) — single-cloud accessor.
ProjectSummary::CloudInfo::storage_order — populated in project_summary().
Read path (apps/rux/src/gui/point_lod.cpp):
voxel_lod() now calls point_cloud_storage_order() after the under-budget early return. When the result is "morton_10bit" and the cloud is over budget, it returns db.point_cloud_page(name, 0, max_points) directly with subsampled=true and voxel_size=0.0 (same sentinel the under-budget path uses). The full voxel pass is skipped entirely. The unflagged path is byte-identical to before.

Design note — what "uniform spatial sample" means here
For synthetic uniform 3D volumes, a Morton prefix covers one Z-curve octant (the first ~12.5 %). For real indoor point clouds (which are surface-heavy, not solid volumes), the first Morton octant spans the most densely scanned surfaces, producing a usable sparse whole-room representation. The voxel LOD path remains available for cases that need guaranteed uniform coverage.

Fix applied — bit-reversed Morton ordering (review verdict addressed)
Three items from the merge review verdict:
1. Sort key: plain → bit-reversed (the central fix)
Was wrong: plain ascending Morton puts all of the first ~12.5% of points in one octant (x<mid ∧ y<mid ∧ z<mid). The spatial concentration test in my original commit even proved the defect — it asserted every prefix point lies below the bbox midpoint on all three axes.
Fixed: Added reverse_bits30(v) helper (standard 32-bit swap then >> 2) applied to the sort key before stable_sort. Bit-reversal promotes the coarsest-level octant bits to the most-significant position, giving BFS-style coverage: the sort visits one representative from each of the 8 top-level octants, then from each of the 64 sub-octants, etc. Any stored prefix now round-robins across all spatial octants rather than concentrating in one.
Metadata updated: "storage_order":"morton_10bit_bitrev".
2. Spatial coverage test (was proving the defect, now guards the fix)
Replaced MortonLod_Prefix_IsSpatiallyConcentrated (which asserted all prefix points below bbox midpoint — i.e. the WRONG property) with MortonLod_Prefix_IsStratiified:
A 5 % prefix (400 of 8 000 points) must span ≥ 80 % of the full cloud's per-axis bbox range on all three axes
Fails against plain Morton (a 5 % prefix spans ~50 % = one octant); passes against bit-reversed Morton
3. Render: honest method, correct result
Previous render used a sqlite3 truncation on a plain-Morton cloud. The new renders:
Re-ran rux create clouds on a scratch copy with the fixed code → storage_order: morton_10bit_bitrev confirmed in sqlite3
Extracted 10 % prefix by reading the first N * point_step bytes from the cloud blob — this is byte-identical to what point_cloud_page(name, 0, N) returns, which is what the LOD path serves
Full cloud (26 144 pts):
First 10 % prefix (2 614 pts) — bit-reversed Morton:
The 10 % prefix covers the whole scan footprint at low density — sparse whole room, not a corner.
Bonus fix: PlanarRegionGrowing ordering sensitivity
The bit-reversed cloud ordering exposed a pre-existing bug in libs/reusex/extern/include/pcl/planar_region_growing.hpp: the algorithm found 3 planes instead of 5 on the corridor fixture, because two internal operations depended on array ordering:
Seed curvature sort: used array-index tie-breaking → different seeds for the same physical points in different orderings. Fixed with spatial (x,y,z) tie-breaking.
Radius search neighbor lists: FLANN's tree-traversal order changes with input ordering, causing different growing sequence for equidistant neighbors. Fixed by re-sorting each neighbor list by (distance, x, y, z) after the radius search.
Both fixes make PlanarRegionGrowing::segment() fully invariant to cloud ordering (STANDARDS §6). All 935 tests pass.
