For volumetric rendering and reproducing the residency octree technique (https://github.com/keller-mark/pluot-private/issues/13), we will need to support multiple render targets:
https://github.com/vitessce/vitessce/blob/0ff9f3b43ca28ef9858d3db0ce06417f6dd174a9/packages/view-types/spatial-accelerated/src/VolumeView.js#L260
We may also need to support multi-pass rendering(?):
https://github.com/vitessce/vitessce/blob/0ff9f3b43ca28ef9858d3db0ce06417f6dd174a9/packages/view-types/spatial-accelerated/src/VolumeView.js#L506
Our current draw function is executed within a single render pass, so this is not sufficient.
Perhaps we can add a trait for a pre-draw function, that allows a layer to do a full render pass before draw? Do we only need to support two passes, or do we need to support 3?

From llm:
In WGSL, @location(0) in a fragment shader output specifies which color attachment in the render pass the output will be written to.
What it corresponds to
When you create a render pass, you define color attachments in the colorAttachments array. The @location(N) attribute maps directly to the Nth attachment (zero-indexed).
Multiple outputs
Yes, you can output multiple vectors to multiple locations from a single fragment shader. You do this by defining a struct with multiple members, each with a different @location attribute:
```
struct FragmentOutput {
    @location(0) color: vec4<f32>,      // Goes to colorAttachments[0]
    @location(1) normal: vec4<f32>,     // Goes to colorAttachments[1]
    @location(2) position: vec4<f32>,   // Goes to colorAttachments[2]
};

@fragment
fn fs_main(in: VSOut) -> FragmentOutput {
    var out: FragmentOutput;
    out.color = vec4<f32>(1.0, 0.0, 0.0, 1.0);
    out.normal = vec4<f32>(0.0, 1.0, 0.0, 1.0);
    out.position = vec4<f32>(0.0, 0.0, 1.0, 1.0);
    return out;
}
```
This is commonly used for Multiple Render Targets (MRT), which is useful for techniques like:
Deferred rendering (G-buffer)
Post-processing effects
Picking/selection buffers
Your render pass descriptor would need corresponding color attachments for each location you're writing to.

Since we define the colorAttachments when defining the RenderPassDescriptor passed to encoder.begin_render_pass, we will need to think about how to structure this. Perhaps we always support 3 render targets in 3D mode? But how will we pass the outputs back to the layer? We may need a post-draw method on each layer? But it would not make sense for multiple layers to render to the same colorAttachment, as they will have no knowledge of the other layers. Perhaps the 3D volumetric rendering is a really special case, and would be the only layer to support multiple render targets? Or we would just check at runtime that there is only a single layer that needs to support multiple render targets per draw call? Or, before the render pass, we ask each layer if it needs an extra render target, and assign it an index?

So, it seems like, when considering #139 , we will need to "ask" each layer for its needs regarding compute passes and multiple render targets, before executing prepare and draw.
It seems like, when when considering #139 , we will need to pass sufficient things to prepare that a full compute pass can be executed, and its results poll-ed and buffers mapped-back.
Regarding multiple render targets, before defining the RenderPassDescriptor and executing draw, we will need to "ask" each layer how many extra render targets it needs. Then, when calling draw, we will need to tell it the indices (or just an index offset) where these extra render targets will be located. We then may need to do some dynamic shader modification so that the @location(DYNAMIC_INDEX_HERE) is filled-in with the correct location indices.
Finally, layers that draw to multiple render targets will need to support a postdraw method, which we will use to "send" the resulting buffer data (and hopefully cache it). Worth noting that a given layer may not always need to render to the extra targets on every frame, e.g. if the stuff it needs from the extra passes has been cached. But this may add a lot of complexity / dynamic shader needs, so perhaps this can wait, and for now we can assume the number of render targets will be stable every frame, to reduce complexity. We can address this if performance becomes an issue. Maybe it is enough to just dynamically determine whether to read the extra buffers + pass them to postdraw.

Worth noting also that supporting compute shaders in prepare will couple things more tightly to WGPU. In other words, regardless of whether calling the draw_raster or draw_svg drawing function variant for drawing, a layer may need to do some computation using a compute shader, preventing the vector-based code path from being fully separated from the WGPU code path. This is ok, but something to keep in mind.
