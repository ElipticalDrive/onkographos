The ID of a geo point stored the quantized latitude in the upper 30 and the quantized longitude in the lower 30 of its value bits. The only interval of IDs that a query rectangle could be mapped to was therefore a latitude band around the globe, which makes a prefilter on the IDs useless for points: for all streets in Freiburg on osm-planet it keeps every OSM node between 47.9 and 48.1 degrees, 54 million rows. The two coordinates are now bit-interleaved (a Morton or Z-order code), so that the points of every quadtree cell form one contiguous range of IDs and a geographic rectangle maps to a small number of such ranges. The quantization and the precision of a point are unchanged, encoding and decoding cost a few more bit operations.
The first commit is that change and nothing else, and it is the one worth reviewing closely. On osm-switzerland, the operations on points that use no grid at all (encoding at index build, geof:latitude, distances, export, point spatial joins) show no measurable difference, while a block prefilter reads 2.9 times fewer rows for a rectangle around Zurich. The function that turns a rectangle into those ranges is deliberately not here, it comes with the prefilter that calls it.
The second commit lets qlever-upgrade-index bring an index in the previous format into the new one, which is much faster than rebuilding it. The IDs of all points are rewritten, and only the parts of the permutations whose order actually changes are sorted again: inside the runs of consecutive rows that agree on all columns before their first point. A run is a single row unless a subject or a predicate has several points, so for osm-planet this means one sort of the point section of POS, OSP and OPS each, and nothing at all for the other three permutations. A run is sorted in memory, or beyond the budget of --memory-for-sorting by the external sorter of the index builder. The precomputed information of every geometry holds its bounding box and its centroid as encoded points as well, so the geometry vocabulary is converted too, whether its geometries are points or not.
An index without a single encoded point needs no conversion, and a server simply accepts such an index in the previous format, because the two formats do not differ for it. The materialized views of an index with points are deliberately not converted but retired together with the index in the old format, since creating them again costs no more than converting them would. The conversion refuses to start when the filesystem has less free space than the second copy of the index that it writes, which for a large index is several terabytes.
Verified on real data. The osm-planet index (214 billion triples, 2.4 TB) was converted in three and a half hours, writing 1.36 trillion rows at 106 M/s, and is now served in the new format. On osm-switzerland, the converted index answers the four spatial-join queries and the export of five million points exactly as the index built from scratch by master does.

Decode geo points that are encoded in Z-order (#55)
…
287d1cb
```
QLever changed how it encodes the two coordinates of a geo point in the value bits of an ID. Before ad-freiburg/qlever#3432 the quantized latitude occupied the upper 30 of those bits and the quantized longitude the lower 30; since then the bits of the two are interleaved (a Morton or Z-order code), so that the points of a geographic rectangle have IDs in few contiguous ranges, which is what makes QLever's prefilter for spatial joins work for points. Points that a query computes are not in the geometry cache but read from their ID, so with the old decoding they were drawn somewhere else on the map entirely.

Which of the two encodings a backend uses cannot be told from an ID, and petrimaps serves backends of both kinds at the same time: osm-planet has been converted, while other indexes still have the previous encoding. The question is therefore asked in the same way as the datatype value of a point already was, and from the same answer: the backend computes a point with known coordinates, and the encoding is the one whose decoding reproduces them. This is correct by construction, because a QLever server refuses an index whose format does not match its own, so the encoder compiled into the server always agrees with the index it serves. A backend that cannot be asked keeps the previous behavior, which is right for every index that was not rebuilt or converted since the change.
```
