The big slowdown on the sparse 3D spreading case is interesting. My first suspicion would be that this is caused by the individual subproblems running extremely quickly and then waiting for the global write lock to the fine grid. In current master this is much less pronounced since there are fewer subproblems.
With fine-grained locking, or colouring, this will go away.
A solution (though a bit clumsy) could be to have a "writeback thread" with a queue to which all finished tiles are appended in a thread-safe fashion. This has the drawback that memory consumption is much harder to predict and control. Personally I'd favor fine-granular locks or lock-free approaches.

Possible alternative locking strategy that just came to my mind:
there is a global vector (or perhaps set) of "cuboids that are currently being written to"
whenever a thread has something to write, it checks its own cuboid against this vector. If there is no overlap, the thread adds its own cuboid to the vector, then does the writing, then removes the cuboid again. Changes to the vector require locking of course.
If there is overlap, the thread waits on a change to the vector and then tries again.
This requires only one lock, and it only needs to be held for very brief periods.

```
The sort bins the points into cubic tiles of the fine grid sized to one
core's L2, and spread and interp run the same loop over (vector, tile)
```

perf: one subgrid tail, and the add back carries the zeroing
…
339c43a
```
Folds the review of the tiled spread and interp back into the branch.

The SIMD tail lives once past the last row of the subgrid buffer instead of
inside every row's stride. The kernel lanes that reach past a row's end are
zero, so the store there writes back what it read, and only the last row can
reach past the allocation. Subgrid::set_row_layout sets the first axis, its
tail and the row stride together, so the three cannot disagree.

drain_wrapped_subgrid, formerly add_wrapped_subgrid, adds each cell back into
the fine grid and zeroes it in the same walk. The three std::fill calls at the
head of the spread kernels are gone, and the cells no run reaches, the tail and
the anti-alias gap, keep the zero they already hold. Dense 3D spreading
measures 3.3% faster on one thread and neutral on six.

spread_tile_doublings measures the buffer the subproblem allocates,
(edge+ns+line)*(edge+ns)^(d-1) + tail, rather than the bare tile, so the L2
ceiling it checks is the one it elects against. It follows the precision for
the line and the tail; the 16-byte budget per complex cell stays fixed, as on
spread_bytes_per_point.

The interp kernels assert the subgrid-relative index before casting it
unsigned, a precondition they documented but never checked, and spreadSorted
asserts du0 is zero before the kernels accumulate into it.

test_unsorted_cut pins the schedule a plan gets where the sort is skipped: the
tile layout is written only by indexSort, which setpts calls after clearing it,
so the empty layout an unsorted plan carries reaches every later spread and
interp as one tile cut into equal chunks. A type-3 arm crosses the sort rule in
both directions, since only a plan that re-sizes its fine grid can leave a stale
layout behind.

The docs, the CHANGELOG and the debug strings follow the renamed drain.
```
