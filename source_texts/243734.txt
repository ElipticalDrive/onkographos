So far I've been considering two methods for generating larger things in a blocky world:
Instancing:
VoxelInstancer can be ported to VoxelTerrain, in which case it will only be able to work at LOD0 (any higher value will never spawn). It shoud only need to wire up the appropriate events internally. It is important to note however, that so far the existing instance generator is not scriptable yet, and was thought to run on smooth meshes. Blocky meshes have a lot of faces oriented 90 degrees so at the very least it needs a cutoff to prevent things from spawning sideways (it has such option). There is no restriction in where stuff will spawn relative to cubes as well, it could be centered or half-way, or anywhere on a face, and it does not know what the face is (ground, leaves, concrete...). Also, currently it is limited to simple models because its first use case was foliage, trees and rocks, and cannot be told to generate something only once in the entire world. In the future it should be able to spawn scenes. Also in theory voxels can be used as a source of instances, but in any case, there are no voxels involved in what it spawns, which is why it exists.
Structure generation:
This is an approach coming from Minecraft, and is purely based on voxels (there are no meshes or scenes involved). The idea is to define the things to spawn in voxel form: a tree, a house, a fortress, as boxes, or collections of boxes. Then the entire process happens inside the generator: in a given block, take the XZ coordinates, hash them, then based on a seeded chance you decide if a thing should spawn in that chunk. If it does, you paste it (or generate it) within the box it is supposed to occupy. It is possible that box overlaps the borders of the block, so this can be solved by also querying neighbor positions (not blocks) and see if they would generate such structure. If they do, then pick boxes that overlap with the current block, and place/generate only that bit. It is important to see that this does not actually query any existing neighbor: This is made possible under the guarantee that the generator is deterministic. Which means blocks do not depend on the existence of other blocks, and they can keep generating independently in threads.
I believe I described this in earlier issues, maybe here How do I use the generator to generate advanced terrain #163 (comment)
And I implemented that technique with the trees in https://github.com/Zylann/voxelgame/blob/aa87dabbf16780c923c59e3dadd078d912e458c8/project/blocky_game/generator/generator.gd#L144
Hybrid:
A combination of both may also be possible, mainly to solve the case where a spawned mesh instance must also alter the voxels it lies on. The generator can first detect if the thing should spawn, prepares the ground within a box, and places voxel metadata in the spawn point. Then the instancer can run afterward, find the metadata and place an instance there. But it's also possible to do this without metadata if the spawn conditions are deterministic as well, so both systems can run the same logic and obtain the data they need.

You can preload your MagicaVoxel stuff when the game start and store voxels somewhere. So far VoxLoader purely exists just so .vox files can be decoded. What you do with the data is up to you.
I havent tested the following code and it probably isnt exact here and there, but just to give an idea of what that approach would be like:
```
class CityDesc:
	var voxels: VoxelBuffer
	var position: Vector3


class WorldDesc:
	var cities := [] # Contains CityDesc instances
	# Other stuff...


class Generator : VoxelGeneratorScript:
	# May be set before the game starts, and never modified afterward
	var _world_desc : WorldDesc

	const AIR_MASK = 0

	func _generate_block(voxels, origin_in_voxels):
		# Generate stuff: ground with noise, trees with procedural structures etc
		# ...

		# Place pre-generated cities
		var block_box = AABB(origin_in_voxels, Vector3(16,16,16))
		for city in _world_desc.cities:
			var city_box = AABB(city.position, city.voxels.size())
			if city_box.intersects(block_box):
				voxels.paste(city.voxels, city.position - origin_in_voxels, AIR_MASK)
		# Should be ok with a handful of cities
		# buf of course if you have thousands of them
		# you may want to use a smarter data structure than an array.
		# Could also be optimized out if you know the minimum and maximum height they can be
```

class Generator extends VoxelGeneratorScript:

Make things like leaves and things that need transparency work
Once again I have no clue how you expect MagicaVoxel to give you textured voxels such as leaves, but you have an example of this already in the demo. The voxel resource named leaves in VoxelLibrary has a material ID corresponding to a specific slot on VoxelTerrain, in which a specific material was used. That material renders voxels with alpha clip on transparent parts of their texture.
You will also note that there is a third material for semi-transparent voxels such as water.
None of these materials are specific to a given voxel though, because each voxel uses a texture atlas. They are UV-mapped such that they use only a part of a larger texture, so only 3 materials are needed in total, to render many types of voxels.
For texture-less voxels which just have a single color (like ALL of those you get from a .vox file), you'd need a material without a texture and voxel as albedo enabled, and maybe another for semi-transparent version.
Would I need to change the generators and stream to get a different mesher working?
Not entirely, depends what you are actually doing. You can change a mesher without touching the generator just fine. And if you use VoxelMesherCubes with the same color palette you use in MagicaVoxel, then your city generation should pretty much give you the same output.
The problem is, the existing demo stuff was written for a different strategy. The demo uses voxel types, while you seem to be using colors. You would have to change the logic so that instead of writing types in the TYPE channel, it writes corresponding color values into the COLOR channel.

I think one or two devs did something similar by tweaking VoxelMesherBlocky, so that on top of mesh batching it would look through other channel to apply coloring from. With Magica it would require to know the palette as well.

Then you'd have to have a mapping between MagicaVoxel values, and these voxel types. In such case, you'd only need to set the TYPE channel.
In other words, values you get with VoxLoader are in the COLOR channel, and correspond to the position on this palette:
So you would need as many Voxel resources for every color your city is using. That sounds awkward, but that's really because VoxelMesherBlocky was not thought for such a use case so far.

Is there a way to add new voxels at runtime to the VoxelLibrary ?
It is possible to do it before the terrain starts to use it, but not afterward (or requires the entire terrain to be reloaded and remeshed). You may also do this after the existing data was loaded. _init runs before the resource is loaded so items added from here will be overriden.
So the sequence should be:
Load VoxelLibrary (it will contain base voxels you may have configured in editor)
Add extra voxels from code like you did
Instantiate the scene that contains the terrain
Assign the VoxelLibrary to it
Add the scene to the tree
then I would set the colors manually
