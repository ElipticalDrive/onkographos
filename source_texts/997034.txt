Summary
NRRD volumes are loading in a different direction now as of the Slicer 5.9.0-2025-08-20 build with the assumption that the changes made to the NRRD IO reader in 11df881. cc: @lassoan @cpinter
Steps to reproduce
In a Slicer version, go to Sample Data module and load MRHead.
File->Save and choose to save the volume to disk in file format "NRRD (.nhdr)" in the split file format with the individual header file.
Open the nhdr file and change space: left-posterior-superior to space: left-anterior-superior. Full header below:
```
NRRD0004
# Complete NRRD file format specification at:
# http://teem.sourceforge.net/nrrd/format.html
type: short
dimension: 3
space: left-anterior-superior
sizes: 256 256 130
space directions: (0,1,0) (0,0,-1) (-1.2999954223632812,0,0)
kinds: domain domain domain
endian: little
encoding: gzip
space origin: (86.644897460937486,-133.92860412597656,116.78569793701172)
data file: MRHead.raw.gz
```
Load the .nhdr back into Slicer and observe the listed "Scan Order" in the Volumes module. In Slicer 5.9.0-2025-08-18 it is Scan Order "Sagittal LR" while starting with Slicer 5.9.0-2025-08-20 it is Scan Order "Sagittal RL".
Slicer 5.9.0-2025-08-18 (8a96c0c)
Slicer 5.9.0-2025-08-20 (ec6d323)
Environment
Slicer version: Slicer-5.9.0-2025-08-20 and latest Slicer-5.9.0-2025-09-03
Operating system: Windows

Changing left-posterior-superior to left-anterior-superior means that the anterior/posterior direction of the image should be swapped.
In Slicer-5.8.1 the left/right direction is swapped.
In Slicer-5.9.0-2025-09-03 the anterior/posterior directions are swapped.
So, it looks like the behavior was incorrect in Slicer-5.8.1 and it is correct now.

Before the recent update, I think most NRRD files were usually read by a simpler, specialized NRRD reader class. It is very surprising that this reader handled some orientations incorrectly, but it is probably due to that in practice medical images use either LPS or RAS. I agree that this should be somewhat highlighted in the release notes (orientation mixup is a serious issue, but if the occurrence is near zero then the overall risk is very low).
@pieper it would be nice if you could have a look at this, too, just to confirm that you have the same conclusion.
