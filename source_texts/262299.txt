Piece G55: Morton-sorted cell index (geom-bvh; chapter 19.9). Stacked on piece/G54 (#366), the box tree, which is stacked on piece/G45 (#267); merge after both.
Done when: Linear octree with 123-bit Morton keys for point neighbour searches (welding, envelopes); key-sorted results identical for shuffled input, every thread count and wasm32; 10M points in under 1 s on 8 threads.
What changed
geom-bvh gains cells, the point index beside the box tree (chapter 19.9: it "indexes points, not boxes. It serves welding and other point searches, where one sort builds it").
The code. Each coordinate is offset by 2^40, which makes a grid coordinate's 41 bits non-negative. The three are interleaved into one 123-bit Morton code (morton): x in bits 0, 3, 6, ..., y in bits 1, 4, ..., z in bits 2, 5, .... The cell of side 2^L at an aligned corner is then one contiguous run of the sorted codes, so the index is a linear octree that stores nothing but the points in (code, key) order.
CellIndex::build:
Points are sorted by key (skipped when already in order), and a repeated key is refused.
Runs of 32,768 points are coded and sorted as one geom-run phase, then merged in pairs, a phase per round, and gathered as a phase.
What is sorted is (code, position in key order). These are all distinct, so the order is unique: the same for any pool, input order or sorting algorithm.
within(centre, radius): the keys of the points at Euclidean distance at most the radius, decided on exact squared distances in i128, ascending.
The search box meets at most three cells of side 2^L per axis, for the smallest L with 2^L above the radius. Cells the ball cannot reach are skipped.
It charges the meter one unit per point scanned, so a cancelled or over-budget search returns an error and no keys.
pairs_within(radius): every pair at most the radius apart, as (smaller key, larger key), ascending. It runs one search per point as a geom-run phase.
to_bytes gives the canonical bytes. points, codes, len and is_empty are readable.
Decisions taken here
core's unstable sort within runs, not geom-run's stable sort.
geom-run's sort calls a key function per comparison. It took 4.9 s for ten million points on eight threads here.
Sorting distinct (code, position) slots in place has one possible answer, so it is as deterministic as the stable sort. It allocates nothing.
Merges and the gather stay inside geom-run phases.
3D only. The board names 123-bit keys, and welding and envelopes are 3D. 2D points can use z = 0.
Exact distance, any radius. Radii past 2^42 reach every point, and are clamped there for the box arithmetic only.
How it was checked
tests/cells.rs:
Codes equal a naive bit-by-bit interleave on 5,000 points, the frame's corners included, and every aligned cell from level 0 to 40 is one run.
Every search equals brute force: sparse points over the whole frame, dense points, clusters, points at the frame's edge, the eight corners and 200 equal points. Radii run from 0 to past the frame (u64::MAX), with 1,000+ centres. Pairs are checked on every set of up to 1,000 points.
The index equals a brute-force sort of (code, key), across several runs of the code sort.
Bytes and answers are identical for the serial executor and pools of 1 to 8 threads (tasks dealt round-robin, run backwards), for shuffled, sorted and reversed input of 35,000 points.
The documented bytes; a repeated key refused; cancellation and short budgets.
tests/cells_determinism.rs: the new golden geom-bvh/cells. It covers seven indexes (1 to 20,000 points), their bytes, 504 searches with the work each charged, and 14 pair searches, hashed with SHA-256 and run on every CI target (wasm32 included).
Mutation gate, run locally on cells.rs (cargo-mutants 27.1.0): 119 mutants, 81 caught, 27 unviable, 11 kept in the ledger as equivalent, each with its argument. The equivalents are:
bit operations on bit groups that never overlap, where | and ^ give the same number;
a merge comparison of slots that are never equal;
the cell gap at the cell's first coordinate, which is 0 either way.
The first runs also found loops a mutant could make endless. The merge rounds are now bounded by the number of runs, and each axis by three cells. A cell past the frame needs no bound: its code is past every point's, so its run is empty, as the comment beside the code argues.
Coverage (cargo llvm-cov, nightly, branches): cells.rs 94.7% of lines; geom-bvh above the 90% bar.
Locally, on Linux and on Windows: clippy -D warnings, fmt, every geom-bvh test, the map, provenance and golden checks, engine-geometry's tests and the quality-gate tests.
Benchmarks (cargo bench -p geom-bvh --bench cells, wall clock, a development machine's WSL with other builds running)

geom_num::brent: Brent's zero (bisection, secant, inverse quadratic
interpolation) and minimum (golden section, parabolic interpolation),

result keeps its bracket (or is an exact zero), the minimum is never
