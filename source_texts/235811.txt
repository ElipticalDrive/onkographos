Summary
Would the Newton team be interested in supporting OpenCV lens-distortion camera models (pinhole with radial/tangential/thin-prism coefficients, and fisheye/equidistant) natively in the tiled camera sensor?
Motivation
Reproducing a real calibrated camera in simulation is a common sim-to-real need: real cameras (and calibrations from tools like OpenCV / LeRobot) come as fx/fy/cx/cy + distortion coefficients — non-square pixels, an off-center principal point, and lens distortion — none of which a single-FOV pinhole can express. Being able to render through that exact calibration lets a policy see in sim what it will see on hardware.
What we did (out-of-tree, on top of Newton)
We implemented this in Isaac Lab without any Newton change, by exploiting the fact that SensorTiledCamera renders an explicit per-pixel ray field. Instead of Utils.compute_pinhole_camera_rays(...) (single vertical FOV), we build the ray field ourselves with two Warp kernels that invert the OpenCV forward model per output pixel:
pinhole — rational radial (k1..k6) + tangential (p1,p2) + thin-prism (s1..s4), fixed-point inversion;
fisheye — equidistant (k1..k4), fixed-point solve for the incidence angle then tan(theta);
then emit the normalized camera-space direction (with the OpenCV +Z-forward/+Y-down → Newton OpenGL -Z-forward/+Y-up axis flip). The rest of the pipeline (update(..., camera_rays=...)) is unchanged. It validates end-to-end on GPU: distorted vs. undistorted renders differ as expected and the reported intrinsics match the authored calibration.
Kernels (single self-contained file):
https://github.com/AntoineRichard/IsaacLab/blob/2c3831bafaa8421825e666254821880cb1800da8/source/isaaclab_newton/isaaclab_newton/renderers/opencv_distortion_rays.py
Full integration / draft PR (for context on how it plugs in):
liorbenhorin/IsaacLab#1
Question / possible native API
The out-of-tree version works, but a native path would be more efficient and reusable across Newton users. A few shapes we could imagine:
A distortion-aware ray-generation util alongside compute_pinhole_camera_rays, e.g. compute_opencv_camera_rays(width, height, fx, fy, cx, cy, coeffs, model) returning the same (camera_count, H, W, 2) field.
Per-camera intrinsics + distortion accepted directly by SensorTiledCamera (rather than a single FOV), so distortion is a first-class camera property.
Would you be open to (1), (2), or a different design? Happy to contribute the kernels upstream if there's interest. The math is standard (matches OpenCV undistortPoints / the fisheye model), so the main design question is the API surface, not the implementation.
