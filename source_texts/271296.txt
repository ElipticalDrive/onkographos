Bug Description
On CUDA, wp.Mesh and wp.Bvh with the default bvh_constructor="lbvh" quantize each primitive's centroid to a Morton code with 10 bits per axis over the total bounds (compute_morton_codes, warp/native/bvh.cu lines 205-209, the same on main and in 1.18.0). When a mesh mixes very different scales, many primitives share one code. Each pair of equal keys gets the delta 64 in compute_key_deltas (line 224), and build_hierarchy splits a run of them with its parity tie-break, so the subtree over the run is deep. mark_packed_leaf_nodes (line 437) then turns every node at depth 32 or more (BVH_QUERY_STACK_SIZE, bvh.h line 18) into a leaf that holds its whole range. Closest-point queries near the fine part of the mesh then test those primitives one at a time.
The scales involved are common in simulation. We hit this in PhysicsNeMo's signed_distance_field, which builds a wp.Mesh with the default constructor on every call. DrivAerML puts a car of 16.6M faces, with a mean edge of 0.34 mm, inside a wind tunnel of 24 x 8.8 x 4 m. A Morton cell is then 23 x 8.6 x 3.9 mm, so hundreds of car faces share each code.
Reproducer
A sphere of 1.28M faces, alone and inside a 24 x 9 x 4 box of 12 faces, with 100k closest-point queries near the sphere. It needs only warp-lang and numpy.
```
"""Warp's CUDA LBVH on a mixed-scale mesh: a fine sphere inside a large box.

The sphere's faces are far smaller than the cells of the 10-bit-per-axis Morton grid that spans the box, so many
faces share one Morton code. Closest-point queries near the sphere are then several times slower with the default
LBVH than with SAH, while the sphere alone shows only a small gap.

Run: python warp_lbvh_repro.py
"""

import time

import numpy as np
import warp as wp


def uv_sphere(radius, n_lat, n_lon):
    """A UV sphere with 2 * n_lat * n_lon triangles (degenerate at the poles)."""
    theta = np.linspace(0.0, np.pi, n_lat + 1)
    phi = np.linspace(0.0, 2.0 * np.pi, n_lon, endpoint=False)
    t, p = np.meshgrid(theta, phi, indexing="ij")
    points = radius * np.stack([np.sin(t) * np.cos(p), np.sin(t) * np.sin(p), np.cos(t)], -1).reshape(-1, 3)
    i, j = np.meshgrid(np.arange(n_lat), np.arange(n_lon), indexing="ij")
    a, b = i * n_lon + j, i * n_lon + (j + 1) % n_lon
    c, d = a + n_lon, b + n_lon
    faces = np.concatenate([np.stack([a, c, b], -1).reshape(-1, 3), np.stack([b, c, d], -1).reshape(-1, 3)])
    return points, faces


def box(lower, upper):
    """The 12 triangles of an axis-aligned box."""
    (x0, y0, z0), (x1, y1, z1) = lower, upper
    points = np.array(
        [[x, y, z] for x in (x0, x1) for y in (y0, y1) for z in (z0, z1)], dtype=np.float64
    )
    faces = np.array(
        [[0, 1, 3], [0, 3, 2], [4, 6, 7], [4, 7, 5], [0, 4, 5], [0, 5, 1],
         [2, 3, 7], [2, 7, 6], [0, 2, 6], [0, 6, 4], [1, 5, 7], [1, 7, 3]]
    )
    return points, faces


@wp.kernel
def closest_point_distance(
    mesh: wp.uint64, queries: wp.array(dtype=wp.vec3), max_dist: float, out: wp.array(dtype=float)
):
    tid = wp.tid()
    x = queries[tid]
    q = wp.mesh_query_point_sign_normal(mesh, x, max_dist)
    if q.result:
        out[tid] = q.sign * wp.length(wp.mesh_eval_position(mesh, q.face, q.u, q.v) - x)


def timed(fn, repeats):
    """Median wall time of fn() in ms, synchronizing the device around each call."""
    times = []
    for _ in range(repeats):
        wp.synchronize_device()
        t0 = time.perf_counter()
        result = fn()
        wp.synchronize_device()
        times.append(1e3 * (time.perf_counter() - t0))
    return float(np.median(times)), result


def measure(name, points, faces, queries, constructor):
    points_wp = wp.array(points.astype(np.float32), dtype=wp.vec3)
    faces_wp = wp.array(faces.astype(np.int32).ravel(), dtype=wp.int32)
    build_ms, mesh = timed(lambda: wp.Mesh(points=points_wp, indices=faces_wp, bvh_constructor=constructor), 5)
    out = wp.zeros(len(queries), dtype=float)
    launch = lambda: wp.launch(closest_point_distance, dim=len(queries), inputs=[mesh.id, queries, 1.0e6, out])
    launch()  # compile and warm up
    query_ms, _ = timed(launch, 10)
    print(f"{name:<14} {len(faces):>9,} faces  {constructor:<4}  build {build_ms:8.1f} ms  query {query_ms:7.1f} ms")
    return out.numpy()


if __name__ == "__main__":
    wp.init()
    rng = np.random.default_rng(0)
    sphere_points, sphere_faces = uv_sphere(0.3, 800, 800)  # 1.28M faces, edges of 1 to 2 mm
    box_points, box_faces = box((-12.0, -4.5, -2.0), (12.0, 4.5, 2.0))  # 24 x 9 x 4, like a wind tunnel
    both_points = np.concatenate([sphere_points, box_points])
    both_faces = np.concatenate([sphere_faces, box_faces + len(sphere_points)])
    queries = wp.array(rng.uniform(-0.6, 0.6, (100_000, 3)).astype(np.float32), dtype=wp.vec3)
    print(f"warp {wp.__version__}, {wp.get_device()}")
    for name, points, faces in (("sphere alone", sphere_points, sphere_faces), ("sphere in box", both_points, both_faces)):
        d_lbvh = measure(name, points, faces, queries, "lbvh")
        d_sah = measure(name, points, faces, queries, "sah")
        print(f"{'':<14} max |distance difference| between the two trees: {np.abs(np.abs(d_lbvh) - np.abs(d_sah)).max():.2e}")
```

The tunnel's few thousand faces make the LBVH query 61x slower and its build 28x slower. The SAH and median trees are good, but they are built on the host in 14 to 19 s. The cuBQL builder takes 1.7 s and has no winding-number support. So none of the other constructors replaces LBVH for this mesh.
A workaround we tried
Passing groups= with each face's rank in a 63-bit Morton order makes every key unique, because the group fills the upper 32 bits of the sort key. On DrivAerML's car and tunnel this gives a 15.9 ms build and a 28.1 ms query. But one group per face also stops leaf packing, so ordinary meshes get slower: an AeroZoo vehicle of 1.35M faces goes from 9.9 to 16.0 ms per call. It also relies on the key layout rather than on the documented contract of groups. We did not adopt it.
Possible fixes
Use 63-bit Morton codes (21 bits per axis) for ungrouped trees. The sort already runs on 64-bit keys.
Or make equal keys unique, as Karras (2012) does, by appending each primitive's sorted index to equal codes. A run of duplicates then becomes a balanced subtree.
Optionally, warn once when the depth limit forces a packed leaf larger than leaf_size, since queries then slow down without notice.
Related
#2013 and #2052 report depth limits in grouped LBVH trees. #1184 changed the delta rule for equal keys. #1842 tracks BVH and mesh query performance.
System Information
Warp 1.17.0 and 1.18.0 on CUDA. RTX 4090 Laptop GPU for the reproducer, GB300 for the full-size case.

This is a long-time known problem. When building with world-ids the BVH use 64 bits Morton code and the first 32 bits are reserved for world ids, that can be too many. Reserving a few bits for the increased world id can be appealing. Let me investigate into this.
