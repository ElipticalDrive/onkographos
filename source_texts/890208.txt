Describe the situation
mortonEncode and mortonDecode fetch every input value through the virtual IColumn::getUInt
inside their per-row loops. mortonEncode is variadic up to eight arguments and the ENCODE
macro expands one colX->getUInt(i) per dimension, so a five-argument call pays five
un-inlinable indirect calls per row for a body that is a couple of pdep/pext instructions on
x86-64-v3 and a handful of table lookups on AArch64. The range-mask variants additionally re-read
row 0 of a constant tuple through the same virtual accessor, once per row per output field.
Resolving each column once per invocation instead of once per row is worth 1.10x-1.29x end to
end depending on shape, on both architectures. It is arch-neutral, adds no intrinsics, and changes
no results.
What a reviewer can re-run first
There is no dashboard history for this path: no tests/performance test covers mortonEncode
or mortonDecode, so performance.ci.clickhouse.com has no run to link and I am not going to
invent one. A perf XML that would cover it is in the collapsed block further down; the cloud perf
bots would report no_change for this change today because ClickBench and TPC-H never call these
functions.
Fixture — paste into a stock clickhouse-local, nothing external needed:
```
-- masked decode: the largest effect
SELECT sum(mortonDecode((1,2), number).1) FROM numbers(120000000) SETTINGS max_threads=1;
-- masked encode
SELECT sum(mortonEncode((1,2), number, number*2)) FROM numbers(120000000) SETTINGS max_threads=1;
-- five-argument encode
SELECT sum(mortonEncode(number, bitShiftRight(number,1), bitShiftRight(number,2),
                        bitShiftRight(number,3), bitShiftRight(number,4)))
FROM numbers(120000000) SETTINGS max_threads=1;
```
On master the three take about 1.05 s / 1.29 s / 1.49 s; with the patch 0.75 s / 1.00 s /
1.29 s. max_threads=1 is the only setting that matters — it keeps the kernel rather than the
scheduler on the critical path.

Processor time falls in proportion to wall clock while rows read, bytes read, FunctionExecute,
ArenaAllocBytes and peak memory are bit-identical. There is no plan change and no I/O change.
Mechanism
Read at 0f7cac9ea103e2101c7162fb6657bf5578ea2c77.
The column arrives as an abstract ColumnPtr and its concrete type is never recovered —
convertToFullColumnIfConst() strips ColumnConst and nothing else:
src/Functions/mortonEncode.cpp:24 — const ColumnPtr & col##INDEX = non_const_arguments[...]
src/Functions/mortonDecode.cpp:37 — const ColumnPtr & col_code = non_const_arguments[1].column
So every value read below is a virtual dispatch:
src/Functions/mortonEncode.cpp:71-117 — the ENCODE argument lists, one colX->getUInt(i)
per dimension per row
src/Functions/mortonDecode.cpp:170 (lookup-table arm) and :233 (BMI2 arm) —
Decode(col_code->getUInt(i))
src/Functions/mortonDecode.cpp:24-25 and src/Functions/mortonEncode.cpp:27, via
src/Functions/FunctionSpaceFillingCurve.h:47 — the loop-invariant range-mask reads
Both architecture arms are affected identically: the indirect call sits outside the
#if defined(__BMI2__) split, which is why this is not a platform-specific issue.
A ColumnUInt64-only fast path would be wrong. FunctionSpaceFillingCurve.h:105 and :140 admit
any native unsigned type, so UInt8/UInt16/UInt32/UInt64 all reach executeImpl — and
mortonDecode's own documented example declares n8 UInt8.
The patch
One primitive, UIntColumnSpan, added to src/Functions/FunctionSpaceFillingCurve.h (the header
both files already include, so hilbertEncode/hilbertDecode can adopt it later without a second
copy). It resolves a column once to {const void * data, size_t width} and reads through an
ALWAYS_INLINE switch on the loop-invariant width; any column that is not a plain fixed-width
vector — sparse, low-cardinality, nullable — keeps getUInt as the fallback, so the fast path is
an optimisation and never a semantic change. The constant range-mask ratios are hoisted into a
std::array<UInt64, 8> before the row loop.
The pattern is Velox's DecodedVector (velox/vector/DecodedVector.h: class DecodedVector,
valueAt<T>(), isIdentityMapping()) narrowed to the native-unsigned case — resolve the physical
encoding once per batch, then read through a non-virtual typed accessor. DuckDB reaches the same
place from the other side: UnaryScalarAdapter in
src/include/duckdb/common/vector_operations/unary_executor.hpp is templated on the concrete
input type and its per-row Operation is inline, so no DuckDB scalar row loop contains a
per-value virtual getter.
Two shapes were tried and rejected on measurement, not taste:
materialising each block into a UInt64 scratch buffer measured slower than the virtual call
it replaces on two-field decode (1.991 vs 1.868 ns/row);
templating the loop on the concrete column type is the upper bound (2.995 ns/row at five
arguments, against 4.208 for the shape that ships) but needs 4^8 instantiations of the ENCODE
switch for an eight-argument variadic function. Those two figures come from different rounds of
the same microbench, whose virtual baseline itself moved 6.844 -> 6.420 ns/row between them, so
read the gap as a magnitude rather than a precise delta. Roughly a third of the encode headroom
is therefore deliberately left unclaimed.

+/// A read-only view of a native unsigned integer column that resolves the column's concrete
+/// type ONCE per invocation instead of once per row.
+///
+/// The space-filling-curve functions read every input value through the virtual
+/// IColumn::getUInt inside their row loops. That is one indirect call per row PER ARGUMENT --
+/// mortonEncode with five arguments pays five of them for a body that is a handful of bit
+/// operations -- and none of them can be inlined, so the call also stands between the loop and
+/// any vectorisation. `width` is loop-invariant, so the switch below is an inlined predicted
+/// jump and not a call.
+///
+/// `fallback` keeps the generic reader for any column that is not a plain fixed-width vector
+/// (sparse, low-cardinality, nullable, ...), where getUInt remains the only correct accessor.
+struct UIntColumnSpan
+{
+    const void * data = nullptr;
+    const IColumn * fallback = nullptr;
+    size_t width = 0;
+
+    ALWAYS_INLINE UInt64 operator[](size_t row) const
+    {
+        switch (width)
+        {
+            case 8: return static_cast<const UInt64 *>(data)[row];
+            case 4: return static_cast<const UInt32 *>(data)[row];
+            case 2: return static_cast<const UInt16 *>(data)[row];
+            case 1: return static_cast<const UInt8 *>(data)[row];
+            default: return fallback->getUInt(row);
+        }
+    }
+};
+
+inline UIntColumnSpan makeUIntColumnSpan(const IColumn & column)
+{
+    UIntColumnSpan span;
+    span.fallback = &column;
+    if (const auto * col_u64 = typeid_cast<const ColumnUInt64 *>(&column))
+    {
+        span.data = col_u64->getData().data();
+        span.width = 8;
+    }
+    else if (const auto * col_u32 = typeid_cast<const ColumnUInt32 *>(&column))
+    {
+        span.data = col_u32->getData().data();
+        span.width = 4;
+    }
+    else if (const auto * col_u16 = typeid_cast<const ColumnUInt16 *>(&column))
+    {
+        span.data = col_u16->getData().data();
+        span.width = 2;
+    }
+    else if (const auto * col_u8 = typeid_cast<const ColumnUInt8 *>(&column))
+    {
+        span.data = col_u8->getData().data();
+        span.width = 1;
+    }
+    return span;
+}

Limits
Measured on locally built binaries on one x86-64-v3 host; the AArch64 numbers above are
kernel-level microbenchmarks rather than full-server A/B, so CI runners (including Graviton)
should confirm the end-to-end figures on that architecture.
Two-field decode's interval guarantees ~8.5% rather than the ~10% point estimate; eight-field
decode and mixed narrow widths are within or close to noise.
The typed-span-per-concrete-type variant is faster still at five-plus arguments; it is not
proposed here because it would multiply the ENCODE switch instantiations.
