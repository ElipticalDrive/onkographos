Abstract
Hardware ray tracing has become a foundational tool for photorealistic rendering across games,
film, architectural visualization, and scientific computing. However, the performance of these
systems is fundamentally limited by the divergence inherent to ray tracing workloads. This
thesis examines how contemporary GPU ray tracing architectures address divergence. Through
targeted microbenchmarking of modern NVIDIA RTX devices, the shader scheduling system
that underpins Vulkan ray tracing and OptiX is reverse-engineered. Ray tracing pipelines are
compiled into stackless, asymmetric coroutines that are cooperatively scheduled at runtime,
reducing divergence from nested shader execution. Shader Execution Reordering (SER) extends
this system to support sorting of suspended work items and global work redistribution. Adding
SER to an existing academic path tracer yields up to 30% speedups on standard test scenes. The
emerging work graph programming model is evaluated as an alternative scheduling substrate for
GPU path tracing, with mixed results. Finally, open directions for academic research on hardware
ray tracing are outlined.

Chapter 1
Introduction
Hardware ray tracing has played an increasingly large role in modern computer graphics.
Previously relegated to cinematic productions, with individual frames requiring days to render,
advances in hardware ray tracing have enabled high-fidelity, physically-accurate rendering on
consumer hardware. In addition to enabling more photorealistic graphics, wider adoption of ray
tracing has benefited game developers, reducing the amount of time needed to bake lighting,
and making it easier to convincingly light dynamic worlds in their games. Outside of games, ray
tracing has also found usage in accelerating film production, architectural visualization, scientific
computations, and audio rendering.
Despite the growing adoption of this technology, the underlying mechanisms for how these
systems work are still not widely understood. Academic works have largely neglected the actual
engineering behind these hardware ray tracing systems. This disconnect between academic study
and industry practice makes it difficult to propose and evaluate new hardware designs for ray
tracing.
The fundamental performance bottleneck in ray tracing is divergence. This thesis studies the
problem from two angles:
1. Reverse-engineering scheduling techniques in a contemporary implementation of hardware
ray tracing
2. Evaluating the fine-grained scheduling abilities of work graphs for path tracing applications
Specifically, this thesis is organized as follows:
• Chapter 2 provides an overview of ray tracing, GPU architectures, challenges with mapping
ray tracing workloads to GPUs, and the current landscape of hardware acceleration for GPU
ray tracing.
• Chapter 3 covers a series of experiments that aim to reverse-engineer the shader scheduling
and work reordering mechanisms of ray tracing pipelines on contemporary NVIDIA devices.
‣ Experimental results reveal that a stackless, asymmetric coroutine execution model is used
to schedule ray tracing workloads.
‣ Shader Execution Reordering [4] is characterized through microbenchmarking, which shows
that it is able to reorder batches of ~12,000 rays across the entire GPU.

‣ We add Shader Execution Reordering support to an existing path tracer, with up to 30%

Chapter 2
Background
2.1 Ray tracing
Ray tracing refers to a broad class of techniques used for modeling light transport.
One particular technique, known as path tracing, is regarded as creating the most visually
accurate images. It aims to solve the “rendering equation” of light transport [5] through Monte
Carlo integration. In practice, a very simple path tracer first casts rays into the scene from the
camera, which then bounce around the scene according to the material properties of objects that
they intersect. When a ray connects to a light source, the contribution from that light along the
path the ray traveled is accumulated into the final image. Russian roulette is a commonly used
method to avoid tracing infinitely long paths. Each bounce can probabilistically terminate the
path, especially if its contribution to the final image after a certain depth would be negligible.
Previously limited to offline renderers and movies, ray tracing and path tracing techniques
are increasingly being adopted by games and other interactive applications to enhance the visual
fidelity and photorealism of their graphics. Many visual phenomena are naturally captured by
path tracing, including refraction, reflections, global illumination, soft shadows, and caustics
— see Figure 2.1 for an example. Most of these effects are possible to achieve with traditional
rasterization-based approaches as well, but require screen-space approximations.
For more details about path tracing and physically-based rendering, the reader is referred to
the excellent PBRT textbook [6].

2.2 GPU Architecture
Though initially designed specifically for hardware acceleration of 2D and 3D rendering through
rasterization, GPUs are now the preeminent platform for highly parallel computation involving
millions of threads at once.
GPUs organize these threads into groups called warps or wavefronts (the terminology differs
by hardware vendor), where each thread in the warp must execute the same instruction. This
is sometimes referred to as single-instruction, multiple-thread (SIMT) execution. When a warp
encounters non-uniform control flow, like a conditional where the threads in the warp don’t
all take the same branch, the hardware will execute both branches and deactivate some of the
threads in each branch to maintain correctness.
Each GPU core (SM in NVIDIA’s terminology) can time-multiplex multiple warps to help hide
the latency from long-latency instructions. However, this is limited by the maximum number of
live registers that a warp uses, which is determined statically from the instruction binary. For a
given program, the number of warps which can be resident on a GPU core without overflowing
its register file is known as the occupancy.
CHAPTER 2: BACKGROUND
5
In addition, an important memory optimization is the use of memory access coalescing to
reduce required memory bandwidth. Conceptually, it is possible for every thread within a warp
to access any location in memory. However, threads in the same warp will usually read adjacent
locations in memory. To optimize this common case, special hardware is used to detect and
opportunistically coalesce these memory accesses.
There are a few key consequences from this architecture:
• Execution divergence from irregular control flow incurs large performance penalties. Threads
in a warp which are masked off are not doing useful work.
• Suboptimal occupancy incurs large performance penalties. “Hot spots” in kernels which
require large numbers of live values can degrade the performance of the kernel as a whole,
since the number of warps which can be scheduled is determined statically.
• Divergent memory accesses incur large performance penalties. Non-regular memory access
patterns are uncoalesced and create large amounts of traffic.
For more details about the topic, the reader is referred to Hennessy and Patterson [7].
2.3 Ray tracing on the GPU
The embarrassingly parallel nature of ray tracing algorithms means they are amenable to being
run on the GPU. However, the irregularity inherent in ray tracing makes building a performant
implementation challenging.
In rasterization workloads, the spatial locality of rasterized fragments generated in a single
draw call generally results in good locality for texture accesses. In addition, a single draw
call is associated with one fragment shader and one vertex shader, so execution divergence is
manageable.
In contrast, for ray tracing workloads:
• A single ray may require invoking many different kinds of shaders and sampling many different
textures as it encounters objects with varying material properties while bouncing around the
scene.
• Even worse, the probabilistic, data-dependent nature of Russian roulette sampling can lead to
heavy work imbalance and execution divergence as some paths extend longer than others.
• PBR shaders can result in high register pressure, decreasing occupancy or introducing stack
spills. If they are combined into a single program, the occupancy will be limited by the most
register-intensive shader.
Megakernels and Wavefronts
There are two common approaches to architecting a ray tracing system on the GPU: megakernel
and wavefront.
CHAPTER 2: BACKGROUND
6
Megakernel renderers work by merging all of the ray tracing logic into a single, monolithic
kernel that handles ray generation, ray-scene intersection, light sampling, and material evalua­
tion. Generally, the logic for material evaluation looks like a large switch statement over different
material types. This leads to large amounts of execution divergence: in the worst case, all 32
threads in the warp must execute different shaders, and compute throughput is reduced by that
factor as well.
The wavefront approach was first proposed in Laine et al. [8]. The primary trait of wavefront
renderers is that they decouple traversal from shading by separating them into separate kernels.
Separate kernels can also be used for evaluating different materials, performing light sampling,
generating camera rays, etc. This approach can increase occupancy by allowing kernels which
need relatively few registers to saturate the hardware with more warps. In addition, by separating
different materials into their own kernels, a large source of divergence is removed.
However, the main downside of this approach is memory bandwidth. Rather than keeping
accumulated path state (throughput, radiance, etc.) in registers, these values must be loaded
from and spilled to global memory to persist between different kernel launches. Nonetheless, the
savings from increased coherence can outweigh the loss of efficiency caused by the increased
cost of working in global memory, the synchronization needed between different stages, and the
overhead of requiring more kernel launches.
Hardware Acceleration for Ray Tracing
Since the Turing generation of GPUs, NVIDIA has included dedicated hardware for accelerating
ray queries directly into their devices. Other major hardware vendors have followed suit.
At a high level, such systems can be categorized into distinct “levels” [9] that each define a set
of operations within a ray tracing pipeline that are offloaded to hardware. Some of these levels
are described below:
1. Intersection hardware: At this level, fixed function units offload the floating-point opera­
tions needed to test if a ray intersects with a bounding box, triangle, or other simple primitive.
SIMT units are still required to traverse the acceleration structure (typically a bounding
volume hierarchy) in software.
2. BVH traversal hardware: At this level, additional hardware (usually referred to as a RT
Unit or RT Core) offloads the traversal of the BVH from SIMT units. These RT units handle
scheduling of intersection tests and memory accesses into BVH data structures.
3. BVH traversal hardware with Coherency: At this level, more work is done to extract
coherency out of the rays processed by hardware; incoherent rays are sorted based on the
objects they intersect before shading occurs.
Though there are “levels” beyond the ones listed here, the second and third levels represent the
state of most contemporary graphics hardware. The rest of this thesis will consider systems of
this type.

Raytracing APIs
Similarly to fixed-function raster-operation hardware, the usage of dedicated ray tracing hard­
ware is mostly done through graphics APIs that aim to be standardized across vendors and
provide a common target for game engine developers. All three major modern APIs (Vulkan,
DX12, and Metal) have native support for ray tracing.
However, there are also vendor-specific APIs that align more closely to general-purpose
compute frameworks. In particular, the OptiX [10] API builds off of NVIDIA’s CUDA compute
stack, allowing for hardware acceleration of ray tracing tasks alongside normal CUDA kernels.
These APIs (OptiX, HIPrt, Embree) generally emphasize visualization and photorealistic renders
more than real-time rendering capabilities, but still provide access to the same underlying
functionality.
Figure 2.2: Visualization of the ray tracing pipeline. Built-in functionality highlighted in blue.
Adapted from the OptiX programming guide [1]
Vulkan, DX12, and OptiX expose a state machine programming model for individual rays called
the ray tracing pipeline. A launch spawns a grid of ray generation shader invocations, with
each invocation being assigned a launch index. Each invocation can call a TraceRay primitive to
intersect a ray against an acceleration structure.
Depending on the outcome, a miss program or a closest-hit program associated with the
intersected geometry is invoked. References to these shaders are placed into the “shader binding
table” (SBT), providing a way to do per-geometry dynamic dispatch. Both miss and closest-hit
programs can recursively call TraceRay as well.
Prior Work
Outside of vague marketing claims, relatively little is known about commercial implementations
of hardware ray tracing. The most comprehensive source is from Intel [11], [12], who provide a

high-level functional overview of their system. Previous studies [13] have also performed some
coarse analysis on NVIDIA’s RTX implementation.
In the academic space, Vulkan-Sim [14] augmented GPGPU-Sim [15] with a functional simu­
lation of a ray tracing traversal / intersection accelerator and a matching timing model to study
the performance characteristics of hardware-accelerated ray tracing. Arches [16] implemented
a performant cycle-level simulation which could exploit more concurrency during simulation.
Kim et al. [17] quantified the effect of data and execution divergence on the performance of ray

2.4 LuisaRender
LuisaRender [2] is an academic path tracer which aims to maximize portability. The LuisaCom­
pute framework it is built on exposes an embedded DSL within C++ for parallel computation
on GPUs, a just-in-time compiler for code generation, and a runtime abstraction for multiple
different platforms (CUDA, DirectX, Metal). DSL code is written against a set of common resource
abstractions (buffers, textures, acceleration structures), which are allocated and managed by
platform-specific code when using a specific backend. The same DSL source code can then
be lowered to the specific shading language (CUDA C++, HLSL, Metal Shading Language) the
backend expects before being compiled and shipped off to the device.
Figure 2.3: A high-level overview of the LuisaRender system. From the original paper [2]
Using LuisaRender allows for the same sampling and material evaluation routines to run on
multiple devices with little to no modification. In addition, its modular architecture means
the integrator, which is responsible for scheduling computation, is easily swapped, enabling
smoother comparisons between different scheduling strategies.

Chapter 3
Scheduling Hardware Ray Tracing
This chapter presents a set of microbenchmarks to uncover implementation details of Vulkan
and OptiX ray tracing pipelines on NVIDIA devices. The experiments reveal that ray tracing
pipelines are compiled into stackless, asymmetric coroutines which are cooperatively scheduled
at runtime, and that Shader Execution Reordering extends this system to support cross-SM work
scheduling.
3.1 Methodology
The goal of these microbenchmarks is to investigate how ray tracing workloads are mapped and
scheduled onto hardware.
In order to characterize the divergence of ray tracing shaders, it is necessary to track
which hardware threads actively executed together within a single warp. To do this, a marker
(exec_marker) is generated using a global atomic counter and platform-specific intrinsics (List­
ing 6.1). Additional intrinsics1 can be used to query the identity of the physical hardware units
that a given thread is executing on. These are referred to as smid, warpid, and laneid in the
following results.
Each experiment stores measurements of smid, warpid, laneid, and timers to global memory
at each launch index. Python scripts are used to interactively visualize the results for further
analysis.

The three GPUs tested represent three different generations of GPU architecture (Ampere, Ada,
and Blackwell). Unless noted otherwise, the results below apply to all six combinations.

3.2 Experiments
Launch index mapping
The first experiment establishes how launch indices are mapped onto threads at the entry point of
the ray tracing pipeline. Specifically, each thread generated by the ray-generation stage records
its position in the grid of launch indices and the (smid, warpid) corresponding to the physical
hardware units it executed on.
Figure 3.1 shows a visualization of the result, for a 32 × 32 sized ray tracing launch. The
launch indices are colored according to the recorded values of smid and warpid. These results
show that a warp operates on an 8 × 4 rectangle of launch indices, with each of the 32 threads
in the warp executing the ray-generation shader for one launch index. exec_marker verifies that
each rectangle is executed as a single cohort. (smid, warpid) alone cannot establish this because
warp slots are recycled as work completes. 4 warps are grouped together to form a single thread­
block which executes on an SM. The same scheme for mapping launch indices to threadblocks
and warps also extends to larger launch sizes as well.

Shader Scheduling within the Ray Tracing Pipeline
The second experiment builds on the first by introducing additional stages of the ray tracing
pipeline, and tracking how smid, warpid, and exec_marker evolve as a ray moves through those
different stages. Specifically, an acceleration structure is built over three triangles. Two of the
three triangles invoke the same shader (ch1) when intersected, but have separate entries in

the SBT. The third triangle invokes a different shader (ch2) entirely, and any rays that miss all
triangles invoke the miss shader (ms).
Each launch index picks uniformly randomly between four targets (one for each triangle, one
for miss) and traces a ray towards it; this causes the associated shader to be executed. Within all
three shaders, a secondary recursive ray is also launched, again picking a target at random.

Figure 3.3 visualizes how a single 8 × 4 rectangle of launch indices traverses the pipeline3. The
four target colors correspond to the two ch1 triangles (orange and teal), the ch2 triangle (blue),
and the miss shader (green). exec_marker reveals that shader invocation is serialized into one

Several conclusions can be drawn from this:
1. The mapping between launch indices and hardware threads is static.
A single launch index is handled by one hardware SIMT thread for its entire lifetime,
rather than being passed around and scheduled on multiple SIMT threads. This contrasts with
Intel’s implementation [11], where threads are destroyed upon calling into TraceRay, and new

2. Some cooperative scheduling mechanism exists to increase RT core utilization.
In particular, the recursive calls to TraceRay from within the shader invocations of l1

The original OptiX paper [10] provides some hints. It describes a set of program transfor­

returning control to internal scheduling code. Profiling the experiment binary confirms that
the ray generation, miss, and closest-hit shaders are all split into multiple subroutines around
TraceRay calls; though OptiX predates hardware ray tracing by almost a decade, its scheduling
system still persists.

a set of asymmetric, stackless coroutines4, with a software-managed stack of coroutine

A careful reading of the OptiX and Vulkan RT specifications supports this idea:
• “Direct callables”, which can be called indirectly through a function table, are not allowed to
call optixTrace (the equivalent to TraceRay). “OptiX-enabled” functions are also not able
to call optixTrace. OptiX forcibly inlines every other function which is not a direct callable
or OptiX-enabled function. Thus, only these two categories of functions which make use of
the normal call stack are unable to suspend their execution. This kind of function coloring
limitation [19] implies that the coroutines must be stackless.
• The coroutine scheduler must support (possibly transitively) recursion between multiple
coroutines. In the absence of recursion, it is possible to statically analyze the call tree
of a given asynchronous function and create a minimally sized structure that allows for
resumption from any suspension point within that function or its (transitive) callees.

Extending this to support recursion, such a structure would need to contain itself; in
many coroutine systems, this is handled by requiring heap allocation to create the necessary
level of indirection5.
Dynamic heap allocation on the GPU is usually not preferable. Instead, both Vulkan and
OptiX require the programmer to specify a maximum ray trace depth and an upper bound
on the depth of the call tree for schedulable shaders. This clearly points towards a worstcase allocation strategy, with a stack of coroutine frames being allocated up-front to every
launch index.
The original OptiX paper also describes how the scheduler decides which coroutine to run
next if multiple are available, stating that “… one simple scheme that works well determines
a schedule by assigning a static prioritization over states.” Exact details are not provided,
but a reasonable guess is that the simpler a coroutine is, the higher a prioritization it gets.
SIMT efficiency during these simple coroutines is lower, but if they schedule more expensive
continuations, the overall efficiency is improved, since expensive operations are made more
coherent.
For instance, the trivial closest-hit and miss shaders of the microbenchmark would receive
higher priority than the internal TraceRay coroutine. All four are thus scheduled before any
secondary ray is launched, leading to a full warp’s worth of rays being traced, which is
maximally efficient. This ability to defer expensive coroutines to increase coherency while
running them can be useful for user code as well (e.g. complex shading networks).
In prior works, there has been little discussion about the usage of cooperative scheduling
and coroutines on GPU. The primary work in this area is LuisaCompute’s coroutine system
[20] and some work to port Rust’s async/await onto GPU [21]. Furthermore, this area is also
relatively unexplored in the ray tracing hardware architecture community. Vulkan-Sim [14]
models only the SIMT scheduling for control flow built into the core itself, and would thus
suffer from compounding divergence in a recursive ray tracing setup.
However, for many practical ray tracing applications, this coroutine scheduling logic can
be avoided or minimized. Specifically, all hardware ray tracing APIs have user-accessible
intrinsics (TraceRayInline) that bypass the ray tracing pipeline entirely. Even for applications
using the ray tracing pipeline, restructuring to remove recursion is usually possible.

Characterizing Shader Execution Reordering
The third experiment extends the second experiment by introducing the shader execution
reordering (SER) feature available in both Vulkan and OptiX. When using this feature, the
single call to TraceRay is split into separate calls for acceleration structure traversal and shader
invocation. Between these two points, a special ReorderThread intrinsic can be called to perform
shader execution reordering.
Reordering reduces divergence when working on a set of rays by sorting them using some
key, and repacking rays with similar sort keys into the same warp to continue execution after
ReorderThread. The sort key incorporates, in order from most to least significant, the shader ID
of intersected geometry, a user-supplied hint, and spatial information from intersection testing.
Therefore, threads that need to execute the same closest-hit or miss shader after acceleration
structure traversal are repacked into the same warp following a reorder, reducing divergence.
The user-supplied hint can be used to incorporate information about material properties (e.g.
surface roughness), reducing execution divergence within a shader. The lowest spatial coherence
bits can improve the locality of texture samples during shading.

of this queue would also correspond to the figure of 12,000 found earlier.
3.3 Shader Execution Reordering
The previous section establishes a possible mechanism for SER, but doesn’t provide insight into
how it generates a performance uplift in a realistic workload. To study this, support for shader
execution reordering was added to LuisaRender’s default megakernel integrator. In order of
priority, the coherence hint passed into ReorderThread incorporates:
• Hit info: A ray can miss all the geometry in the scene, hit a light source, or hit a regular object.
These represent different control flow paths through the integrator. When a ray misses all
geometry, the path is terminated. When it hits a light source, the MIS weight combining the
emission from the light with the previous bounce’s direct lighting must be resolved.
• Material info: LuisaRender assigns each material in the scene a tag, which is used for shader
dispatch after a call to TraceRayInline. Since LuisaRender relies on TraceRayInline for all
ray queries, its SBT contains no information about the materials of different geometry in the
scene. Thus, the tag must be incorporated into the coherence hint to affect reordering.

• Russian roulette info: Russian roulette probabilistically terminates paths with low throughput,
creating divergence when some threads in a warp survive and others do not. Making an edu­

packs them together can thus reduce divergence.

3.4 Summary
Together, the experiments above establish a baseline for the analysis of NVIDIA’s hardware ray
tracing platform on all of its modern compute architectures. Each ray tracing launch index is
statically mapped onto a hardware thread, and a cooperative, coroutine-based scheduler is used
to manage divergence from recursive calls to TraceRay. This scheduling strategy is recognizably
descended from the original OptiX runtime [10].
Shader Execution Reordering builds on this system by introducing the ability to spill corou­
tine state to a global reorder queue rather than the per-launch-index coroutine stack. The queue
entries can be sorted in batches of ~12,000 elements each into coherent groups. The post-reorder
continuations can be dispatched to SMs across the whole device. Queue overflow leads to in-place
continuation; draining the queue causes reordering to be skipped. In practice, Shader Execution
Reordering can decrease render times by up to 30%.

Work Graphs for Path Tracing
Despite being a widely adopted architecture for GPU path tracers, wavefront renderers have
serious weaknesses. Path state which would otherwise live in registers must be spilled to global
memory between kernels, and with millions of in-flight rays, this consumes valuable memory
bandwidth. Dispatch sizing also presents a challenge for implementations, as dispatches are
launched from the CPU, which cannot know how much work must be done at each wavefront
stage a priori. For instance, the number of rays which exit the scene without intersecting any
geometry dictates the optimal dispatch size for the miss shader. Reading back this information
from GPU to CPU requires costly synchronization, so renderers often dispatch the worst-case
size and exit early from threads that have no work to do, leading to many wasted warp launches.
Analogous issues arise in GPU-driven rendering pipelines, where modern game engines
preprocess scene information (e.g. culling, LOD selection, virtual geometry [22]) on the GPU
itself. These irregular workloads similarly force either expensive roundtrips to CPU or subop­
timal hardware utilization. ExecuteIndirect and CUDA Dynamic Parallelism (CDP) aim to solve
this by exposing dispatch machinery to device-side kernels, but these come with their own
drawbacks. A common workaround is to use persistent threads [23], however, this approach is
brittle, hardware-specific, and difficult to debug.
Work graphs [24] aim to address these issues by introducing a dataflow-like execution model
to the GPU. Different nodes are arranged into a graph and can execute downstream nodes by
outputting “records” along the edges of the graph. Industry adoption has been limited, but work
graphs have seen success in accelerating Sparse Matrix-Vector multiplication [25] and procedural
generation tasks [26], [27].
Work graphs are an appealing choice for path tracing, since the different stages within a
wavefront renderer are naturally mapped onto nodes of a work graph. Passing data through
records replaces intermediate buffers, and the work graph runtime can automatically compact
records into SIMT warps for efficient execution, sidestepping the difficulty of dispatch sizing.
Essentially, a renderer built on work graphs aims to achieve the same occupancy benefits and
divergence reduction of a wavefront renderer, but without the memory bandwidth and dispatch
overheads. The following sections evaluate how work graphs compare to existing megakernel
and wavefront integrators.

4.2 Integrator Design
Two integrators were added to LuisaRender using the newly added work graph feature.
The work graph integrator maps the processes of ray intersection, material shading, and light
sampling onto different nodes within a work graph (Figure 4.1). Records contain state that needs
to be passed from one stage to another. For example, the world-space ray origin and direction
are needed by all nodes following the entry node. As such, the record definition for each edge
contains these fields.
Unfortunately, it is not possible to map the bounce and sample accumulation loops onto the
work graph programming model due to the inability to create back-edges. For simplicity, the
implementation does one dispatch per bounce. By keeping a path state buffer which contains the
information of a next bounce, paths which are not terminated by Russian roulette can be updated
in the path state buffer and extended in the following work-graph dispatch. It may be possible to
avoid this by unrolling the work graph to the maximum depth of a ray.

4.4 Discussion
One limitation of the existing work-graph API is that calls to write an output record must
be threadgroup-uniform. This makes building an implementation cumbersome, as shader code
needs to be structured to hoist these calls out of conditional statements and loop bodies.
The “direct” implementation using work graphs is 2.8× slower than the megakernel integrator
when rendering in sRGB. Interestingly, the intermediate buffers that are allocated by the work
graph runtime don’t scale with the size of the record. The hybrid work graph integrator only
passes a single index (4 bytes) in its records, while the direct implementation has 128 bytes within
a single record, but both request the same amount of backing memory from the driver.
This experiment clearly demonstrates that occupancy and coherence do not always lead
to faster renders. Despite the hybrid renderer having higher coherence and occupancy, it still
underperforms compared to the megakernel.
Although the performance of the work graph integrators are worse than the megakernel,
they do exhibit interesting behavior at runtime.
Figure 4.3: NSight Graphics capture for work graph renderer
Generally, compute shaders are unable to have heterogeneous threadblock sizes, as the register
usage and shared memory usage is pessimized over the whole kernel. However, when using
work graphs, different work graph nodes are actually scheduled as separate threadgroups with
varying sizes and register file usages. This is more similar to rasterization workloads, where
fragment shaders and vertex shaders from different draw calls are opportunistically scheduled
by the hardware to maximize usage. The dynamic behavior of the hybrid work-graph integrator
resembles many small wavefronts in series with each other, and a periodic behavior of different
hardware pipes being utilized is clearly visible in Figure 4.3. However, while the peak utilization
of RT cores and SM resources is higher than the megakernel, sustained throughput remains lower.
Ampere is the first generation to support work graphs, and it is likely that the hardware
was not designed for work graphs. If future implementations are able to use shared memory for
transferring records between nodes and remove the restriction on acyclic graph structure, work
graphs could be a more viable alternative.

heterogeneous, dynamically-scheduled threadgroups not seen in traditional compute workloads.

Future Work
This thesis explored the issue of divergence in hardware ray tracing, using microbenchmarks
to expose existing approaches deployed in contemporary NVIDIA GPUs and evaluating work
graphs as an alternative scheduling substrate for path tracing. The next steps are to translate the
insights from this work into an academic ray tracing accelerator design.
5.1 Radiance
The Radiance project [29] is an academic GPU architecture being developed at Berkeley, with an
emphasis on neural graphics applications. An early revision of the SIMT core was taped out at
the beginning of April 2026. A key goal of Radiance is to serve as a testbed for GPU architecture
research in the academic space, and its design is well-suited to integration of a custom ray tracing
accelerator. The design space is very large; a few key points are outlined below.
Traversal and Intersection Accelerator
Like other contemporary GPU architectures, ray intersection and ray traversal will both be
offloaded to this accelerator. Existing datapaths [30] for ray-triangle intersection can be leveraged
to reduce development effort.
BVH Encoding and Traversal Stack
Two choices arise within the traversal hardware itself: how to encode BVH nodes, and how to
track traversal state. A wider BVH reduces tree depth and increases opportunities for parallel
intersection testing, but requires more intersection tests per node visited. Compressed or quan­
tized BVH formats reduce memory traffic at the cost of decode logic. A short-stack representation
reduces the per-ray memory footprint at the cost of occasional traversal restarts. A BVH node
cache helps reduce memory traffic. A treelet-based prefetching scheme [31] can reduce the
latency of pointer-chasing through nodes in the BVH.
CHAPTER 5: FUTURE WORK

Coherency Mechanism
The experiments in Chapter 3 examined Shader Execution Reordering, showing that it utilizes
a global producer-consumer queue where large batches are sorted according to a coherence
key. Replicating this in hardware would be a substantial undertaking. However, the results from
Chapter 3 suggest that the sorting can be done by the SIMT units. A purely software scheduler
using persistent threads to schedule reordering, shading, and intersection tasks is a flexible option
for an initial design.
5.2 Async on GPU
The program transformations described in Section 3.2 are also generally applicable outside of
ray tracing. In particular, Zheng et al. [20] discusses how an annotated GPU kernel can be split
into coroutines scheduled by different runtime strategies, namely wavefront, persistent threads,
and state machine. This framework could be extended with a work graph scheduler, although
the inability to resolve cyclic dependencies in work graphs makes this challenging. In the other
direction, automated transformation from work graph nodes into coroutines is straightforward,
and would allow for emulation of work graphs on LuisaCompute’s other backends.
More generally, in light of increasing asynchrony exposed by GPU instruction sets
(cp.async.bulk, tcgen05.mma), it is worth investigating whether suspendable coroutines could
form the basis of a highly decoupled GPU architecture. Currently, asynchronous accelerator
operations require manual insertion of mbarrier-style primitives for synchronization, leaving
the programmer to find useful work while waiting on the accelerator’s results. Borrowing the
async programming model from CPUs could solve both issues, but running the scheduler on
SIMT cores is a performance bottleneck. The Neutrino coprocessor being designed for Radiance
would function as an async runtime in hardware, tracking dependencies between accelerator
operations and SIMT threads.
Taken together, these directions trace a realistic path towards a GPU ray tracing architecture
where divergence and asynchrony are addressed at the hardware design level.
