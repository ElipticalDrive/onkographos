Description
Add opt-in anti-aliasing to SensorCamera. Camera ray helpers now generate (height, width, sample_count, 2) bundles with centered subpixel samples for pinhole and fisheye cameras.
RenderConfig.anti_aliasing supports SSAA, which traces and shades every subsample, and MSAA, which traces every subsample but shades once per shape within a pixel. MSAA deliberately shares shading across samples of the same shape to reduce shading work; texture and lighting variation within that shape is therefore not supersampled. The default NONE mode renders one ray per pixel.

New feature / API change
```
import warp as wp
from newton.sensors import SensorCamera

# Given a finalized model and its current state:
camera = SensorCamera(model)
width, height = 640, 480
rays = SensorCamera.compute_camera_rays_pinhole(
    width, height, camera_fov=1.0, multisamples=4, device=model.device
)
transforms = wp.array(
    [wp.transform_identity()], dtype=wp.transformf, device=model.device
)
color = camera.create_color_image_output(1, width, height)

camera.update(
    state,
    transforms,
    rays,
    color_image=color,
    render_config=SensorCamera.RenderConfig(
        anti_aliasing=SensorCamera.AntiAliasing.MSAA
    ),
)
```

New Features
Added SSAA and MSAA options for smoother camera renders, with configurable subpixel sampling for pinhole and fisheye cameras.
SSAA averages color and albedo across samples; MSAA shades covered surfaces and blends results with clear-color contributions for missed samples. Depth and geometric outputs use the nearest hit.
Single-sample rendering remains the default; multisampled rays require SSAA or MSAA.
Documentation
Updated camera guidance to describe multisample ray generation and anti-aliasing options.

Merge Risk: 🔵 Low · up to 3e44e
Anti-aliasing is opt-in, and default single-sample rendering keeps its shape semantics under the new four-dimensional ray layout. One known limitation remains. In MSAA, shading may come from an off-center subsample in some sample configurations, which can shift color slightly against depth and segmentation. The change is mergeable, but the owner should be aware of this limitation.
Security Architecture Review
Security architecture risk: 🔵 Low · up to 3e44e
The change remains within caller-controlled rendering. Sample shapes and rendering modes are checked, and shading reuse is confined to one pixel. Existing custom ray buffers must adopt the new sample axis, and larger sample counts increase memory and rendering costs. No introduced security vulnerability was established, but concurrent execution and exposure through untrusted callers were not demonstrated.

No architecture-level concerns identified.

Security Blast Radius
inferred — The inspected exposure is caller-selected computation and memory on the rendering device. Sample count multiplies ray allocation and tracing work without an application-level upper bound. No externally attacker-controlled entrypoint or shared-service resource policy was supplied, so this is not established as a denial-of-service finding.
Trust Boundaries and Controls
observed — MSAA shading reuse is local to a pixel invocation rather than shared across views or calls. Cache matching uses shape identity and, for shared particle or triangle-mesh sentinel IDs, a particle or face sub-index. Cached color values are read only after a matching initialized identity is found.
Resilience and Maintainability Implications
observed — RenderContext mutates call-dependent flags before some validation, but each sequential call resets those flags before cache lookup. That ordering and cache-key snapshotting predate this PR. Source therefore does not support retaining a newly introduced stale-flag retry concern; concurrent shared-context behavior remains unverified.
