Add instanced Gaussian splat rendering spec

0510891
```
Proposal for rendering procedural scenes with repeated elements
efficiently using instanced splat templates instead of baking
entire scenes.

Key concepts:
- Bake unique objects once as "splat templates"
- Runtime instancing with per-instance transforms
- Animation support via expression evaluation
- Hybrid SDF/splat for dynamic objects (lasers, effects)

Includes:
- Architecture overview
- File format specs (.isplat bundle, manifest.json)
- WebGL2 rendering pipeline with instanced vertex shader
- JavaScript API design
- Integration plan with Lucid SDF system
- 4-phase implementation roadmap
```

Review Summary
This is an excellent and comprehensive technical specification for instanced Gaussian splat rendering. The document demonstrates deep understanding of both 3D Gaussian Splatting techniques and real-world optimization needs for procedural scenes.
Strengths
Technical Excellence
Well-motivated problem: Clear articulation of the inefficiency in traditional splat baking for repeated elements
Sound architecture: The component diagram and data flow are logical and well-structured
Practical examples: Concrete comparisons (50,000 splats → 4,300 templates, 10MB → 1MB) make benefits tangible
Implementation-ready: Includes actual GLSL shader code and detailed API specifications
Documentation Quality
Comprehensive scope: Covers everything from file formats to rendering pipeline to integration APIs
Clear structure: Logical progression from problem → solution → implementation → phases
Good use of diagrams: ASCII art diagrams effectively communicate architecture
Practical examples: JSON manifest examples are detailed and realistic
Forward-thinking Design
Extensible: Animation system uses flexible expression trees rather than fixed keyframes
Hybrid approach: Acknowledges that some objects (lasers, dynamic effects) should remain SDF-based
Multiple sorting strategies: Documents tradeoffs between performance and quality
Integration planned: Considers both standalone use and integration with Lucid system
Areas for Improvement
Performance Considerations
Memory bandwidth concerns: The specification doesn't address GPU memory usage for large instance counts. Consider adding:
Memory usage estimates for different instance counts
Guidance on texture size limits for instance transform storage
Discussion of uniform buffer vs texture approaches for different hardware
Sorting complexity: While Option B (global sorting) is noted as "correct but expensive," more detail on computational complexity would be valuable:
O(n log n) cost for sorting all transformed splats
Memory requirements for indirect draw buffers
Break-even points between sorting strategies
Security & Validation
Bundle validation: The .isplat ZIP format should include security considerations:
File size limits to prevent zip bombs
Path traversal protection for template file references
Validation of JSON schema to prevent injection attacks
Animation expression security: The expression evaluation system could be a vector for code injection:
Whitelist allowed expression types
Sandbox expression evaluation
Limit recursion depth and computation time
Technical Gaps
Error handling: Missing specification for:
What happens when template files are missing or corrupted
Invalid animation expressions
GPU memory allocation failures
Compatibility: The spec mentions "Compatible with existing splat viewers (via export/flatten)" but doesn't detail the flattening process or potential quality loss.
Implementation Details
LOD system: Phase 4 mentions LOD but the specification would benefit from more detail on:
Distance-based instance culling
Template simplification strategies
Memory management for LOD levels
Color tinting: Open question CNRY: Deepfield image panorama episode #3 about color modulation needs resolution - this affects shader design significantly.
Minor Issues
Line 478: Broken reference link to ../README.html (should probably be ../README.md)
Manifest schema: Consider adding version field to individual templates for incremental updates
API naming: setInstanceTransform might be better as updateInstanceTransform to indicate it's a state change
Recommendations
Add memory budget section: Include guidance on GPU memory usage and practical instance count limits
Security hardening: Add validation and sandboxing requirements to the specification
Error handling specification: Define behavior for common failure modes
Reference implementations: Consider linking to or including minimal reference implementations
Performance benchmarks: Include target performance metrics (e.g., "1000 instances at 60fps on mid-range mobile GPU")
Overall Assessment
This is a high-quality technical specification that demonstrates strong understanding of the problem domain and provides a solid foundation for implementation. The document successfully bridges the gap between academic Gaussian splatting research and practical game engine integration needs.
The specification is implementation-ready and would serve well as a blueprint for development teams. With minor additions around security and error handling, this could serve as an industry-standard approach to instanced splat rendering.
Rating: Excellent - This specification shows the level of technical depth and practical consideration that characterizes production-ready graphics systems.
