Chunk visibility in 2D is using an awkward and inflexible "camera bounds" that makes assumptions about camera orientation. We should be using the frustum to calculate visible chunks. This should generally work for both 2D and 3D, using an intersection of the frustum and any "slicing" (likely from the layer itself). LOD selection may still need separate 2D/3D code paths.
See #553 (comment) for some more relevant discussion.

I think this issue is a bit unclear.
For true 2D presentation the camera assumptions are intentional. The camera does not rotate around the data and chunk visibility reduces to a straightforward tile/viewport intersection test. That's not awkward or inflexible it's exactly what most 2D tiled viewers do and it's the behavior I would expect.
I think what you mean is rendering 2D slices within a 3D context (orthoslices)? That case is more awkward because chunk visibility becomes a 3D problem: frustum culling combined with a Z-slab or slice constraint. That is a fundamentally different test.
We could argue for a unified visibility path between 2D and 3D but we can also argue against it. LOD selection will almost certainly need separate logic for 2D and 3D anyway (with orthoslices falling into the 3D bucket or maybe not?). If we already need divergent paths there unifying visibility may not actually buy us much.
At this point I'm not convinced either approach is clearly better. Until we see what orthoslices actually look like in practice keeping the paths separate feels like the safer choice. We shouldn't let it block LOD selection for volume rendering.
One more clarification: we already apply frustum culling to geometry. Geometry outside the frustum should not render. This issue seems specifically about chunk loading not rendering and that distinction is sometimes unclear.
We may need clearer terminology for all this.

I'm hoping I've understood a bit better from what is discussed here the issue that @shlomnissan noted with the volume rendering PR before it was fixed. The volume layer was trying to control the LOD in the initial implementation, but instead that LOD should be controlled by a mixture of the policy and the chunk store view.
With this in mind, for the moment we basically are creating a fixed policy that specifies the LOD to use for rendering by setting the min and max LOD in the policy to both be the desired LOD.
For example createExplorationPolicy({lod: {min: 1, max:1}}) to select LOD 1. I note this here partly because if the problem to tackle in this main issue is addressed, likely the examples would want to update and use a policy that ranges from a real min to max LOD and have the best LOD to use be computed by the chunk store view.

I don't think I agree with this. When the data are coming from a 3D source, it's still a 3D problem even for 2D presentation. This is also true if we want to combine any 3D data in the presentation. I think this further breaks down if/when we enable oblique slicing, where I do expect the camera to move in arbitrary orientations. I know this is not a high priority, but I think it's worth keeping in mind when we consider implementation.
The awkwardness I find is in considering "Z" bounds, when the through-plane dimension of a 2D presentation may not either be the Z-dimension of the data or the Idetik coordinate space, but is instead relative to the camera. I don't think we need a separate or additional coordinate system relative to the camera just for 2D presentation. Awkwardness is subjective, but the inflexibility is that ChunkedImageLayer currently only supports 2D presentation of XY planes (Z slices).
I think this matches your expectations for 3D presentation of 2D slices (orthoslices): renderable objects used in a 2D viewport can be also displayed in a 3D viewport as something like a reference (i.e. in the case of orthoslices).
