Review — demo(shape_debug): createVoxelPoolShape uses IRMath::SDF::evaluateGrid (#2120)
Verdict: approve
Summary
Replaces createVoxelPoolShape's hand-rolled per-cell IRMath::SDF::evaluate loop with a single batched IRMath::SDF::evaluateGrid call into a distances buffer, then a threshold pass. Mechanical perf/reuse cleanup found during PR #2117 review (simplify-scan-render-leak); pre-existing before that PR, not introduced by it.
Verification performed
Confirmed the byte-identical claim algebraically. evaluateGrid samples each cell at vec3(x,y,z) - size*0.5 + 0.5; C_VoxelSetNew's centerAroundOrigin ctor (component_voxel_set.hpp:151-157) offsets by -(size-1)*0.5. Since size*0.5 - 0.5 == (size-1)*0.5 exactly (both reduce to a multiple of 0.5, exactly representable in float for the demo's size range), sdfPos == pos bit-for-bit — the claim holds, not just "close enough."
Confirmed the loop-order claim. evaluateGrid iterates z outer, y, x inner, incrementing flat sequentially — flat = z*size.y*size.x + y*size.x + x for the n-th cell, which is exactly IRMath::index3DtoIndex1D (ir_math.hpp:1504: index.z*size.x*size.y + index.y*size.x + index.x). positions_/voxels_ are laid out via the same index3DtoIndex1D call in the ctor, so distances[i] lines up with vs.positions_[i]/vs.voxels_[i] one-for-one, matching the old per-cell loop that read vs.positions_[i].pos_ directly.
Checked the allocation-failure edge case (C_VoxelSetNew ctor's span-mismatch branch zeroes size_/numVoxels_ on an out-of-voxels condition). The new code reads vs.size_/vs.numVoxels_ (not the local size parameter) for both the distances buffer size and the evaluateGrid call, so this degrades to a correct no-op exactly like the old for (i < vs.numVoxels_) loop did — no behavior change in the failure path.
Confirmed the post-carve recomputeFaceOccupancy + syncActiveMask calls (required per voxel/CLAUDE.md whenever a carve bypasses C_VoxelSetNew mutators) are untouched by this diff and still present immediately after the loop.
std::vector<float> distances allocation happens once per shape-entity creation (not a per-frame/tick path), so this isn't a hot-path allocation concern.
No render/, system/, world/, ECS, GPU-buffer, or concurrency surface touched — this is a CPU-only refactor inside creations/demos/. Doesn't meet the cross-host smoke-tag criteria (no engine/render/, shader, engine/system/, or CMake changes).
Test plan: author's fleet-build + render-verify (macOS/Metal, 21/21 shape_debug shots) is sufficient evidence given the verified-exact math above; the 2 shots with nonzero delta are explicitly the known non-cardinal-yaw scatter jitter (unrelated demo behavior), not attributable to this change.
Praise
The inline comment correctly states the non-obvious why (the exact offset-formula equivalence and ordering match) rather than restating what the diff does — exactly the kind of comment that earns its keep.
Test plan the author should run before merge
Already covered by the author's test plan (build + render-verify, 21/21 shots) — re-verified the underlying math claim independently above.
