Problem Statement
The current 3D camera is an arcball (orbit) camera that rotates around a fixed target point. This is ideal for inspecting a volume from the outside, but makes it impossible to freely navigate through the interior of a volume or explore unconstrained 3D space. Users working with large volumetric datasets need a spaceship-style fly camera with full 6 degrees of freedom — forward/backward, left/right, up/down translation plus pitch, yaw, and roll rotation.
Additionally, when navigating inside a volume, samples immediately in front of the camera create visual clutter. An adjustable near clip distance that makes everything before a plane (or sphere) transparent is needed to reveal clean cross-sections of the interior.
Finally, there is currently no keybinding infrastructure at all — all interaction is mouse-only. Adding keyboard-driven camera control requires building a general-purpose keybinding system that can serve future keyboard-driven features beyond just the fly camera.
Solution
Add a new fly camera mode alongside the existing arcball camera, switchable via UI toggle or keyboard shortcut. The fly camera uses quaternion-based orientation for gimbal-lock-free rotation and frame-rate-independent movement driven by held keys. A 3-layer keybinding system (key state tracker, binding registry, consumers) provides the input infrastructure. An adjustable clip distance (plane or sphere mode) clips away volume samples near the camera, usable in both 3D camera modes.
Key controls:
WASD: forward / left / backward / right
QE: down / up
IK / JL / OU: pitch / yaw / roll
F: toggle between arcball and fly mode
Mouse drag: mouselook (yaw + pitch) in fly mode
Scroll wheel: adjust movement speed in fly mode
[ / ]: decrease / increase clip distance
User Stories
As a volume viewer user, I want to fly freely through a 3D volume, so that I can explore interior structures that are hidden from an orbit perspective.
As a volume viewer user, I want to switch between arcball and fly camera modes, so that I can use whichever navigation style suits my current task.
As a volume viewer user, I want to switch modes via a keyboard shortcut (F), so that I can toggle quickly without reaching for UI controls.
As a volume viewer user, I want to switch modes via a UI button, so that I have a discoverable entry point for the feature.
As a volume viewer user, I want my view position to be preserved when switching between arcball and fly mode, so that I don't lose my place in the volume.
As a volume viewer user, I want to move forward/backward/left/right with WASD keys, so that I can translate through 3D space intuitively.
As a volume viewer user, I want to move up/down with E/Q keys, so that I can navigate vertically.
As a volume viewer user, I want to pitch the camera with I/K keys, so that I can look up and down.
As a volume viewer user, I want to yaw the camera with J/L keys, so that I can look left and right.
As a volume viewer user, I want to roll the camera with O/U keys, so that I can tilt the view for unconstrained 6DoF navigation.
As a volume viewer user, I want to use mouse drag for mouselook in fly mode, so that I get fine-grained yaw/pitch control.
As a volume viewer user, I want movement speed to automatically scale to the volume size, so that navigation feels natural regardless of dataset dimensions.
As a volume viewer user, I want to adjust movement speed with the scroll wheel, so that I can fine-tune how fast I fly.
As a volume viewer user, I want movement to be frame-rate independent, so that flying feels smooth regardless of rendering performance.
As a volume viewer user, I want movement to pause when the browser tab is backgrounded, so that I don't teleport across the volume when I return.
As a volume viewer user, I want to see a brief hint overlay ("WASD move · QE up/down · IKJLOU look · Scroll speed") when entering fly mode, so that I know the controls.
As a volume viewer user, I want the hint to dismiss on first keypress or after 5 seconds, so that it doesn't obstruct my view during use.
As a volume viewer user, I want the canvas to auto-focus when I switch to fly mode, so that keyboard controls work immediately.
As a volume viewer user, I want keyboard bindings to only activate when the viewer is focused, so that typing in text fields doesn't trigger camera movement.
As a collaborating user, I want peers to see my fly camera state, so that peer cursors and awareness work correctly in fly mode.
As a collaborating user following a peer in fly mode, I want to see exactly what they see, so that follow mode works faithfully across camera modes.
As a developer, I want keybindings defined in a central config object, so that I can easily change or extend bindings.
As a developer, I want the key state tracking system to be reusable, so that future features can add their own keyboard-driven interactions.
As a volume viewer user, I want to clip away volume samples near the camera, so that I can see clean cross-sections of the volume interior without visual clutter.
As a volume viewer user, I want to adjust the clip distance with bracket keys ([ / ]) while flying, so that I can interactively reveal or hide near structures without breaking flow.
As a volume viewer user, I want a slider UI for precise clip distance control, so that I can set an exact clip distance.
As a volume viewer user, I want the clip distance to default to a small non-zero value in fly mode, so that samples right against the camera don't clutter my view.
As a volume viewer user, I want the clip distance to default to zero in arcball mode, so that the full volume is visible when orbiting from outside.
As a volume viewer user, I want to choose between plane clipping and sphere clipping, so that I can experiment with different cutaway styles.
As a collaborating user following a peer, I want to see their clip distance applied, so that I see exactly the same clipped view they see.
As a volume viewer user, I want clip distance to work in both translucent and MIP render modes, so that clipping behaves consistently regardless of rendering style.
Implementation Decisions
Camera Enum Refactor
Rename Camera::View2D to Camera::Slice (serde tag "slice"), Camera::View3D to Camera::Arcball (serde tag "arcball"), add Camera::Fly (serde tag "fly").
This is a breaking serialization change. No backward compatibility shims.
Fly Camera State
position: [f64; 3] — eye position in world space.
orientation: [f64; 4] — quaternion (x, y, z, w). Stored internally as quaternion; input arrives as euler deltas converted to axis-angle quaternion rotations.
fov, near, far, viewport — shared projection parameters.
speed_multiplier — persists during fly mode session. Base speed derived from volume bounding box diagonal.
Rotation speed fixed at ~pi/4 rad/sec.
Clip Distance
Both Arcball and Fly structs carry clip_distance: f64 and clip_mode: enum { Plane, Sphere }.
Default clip_distance: 0.0 for Arcball, ~0.5-1% of volume diagonal for Fly.
Clip mode: Plane (default) — a flat plane perpendicular to the view direction at clip_distance from the eye. Sphere — everything within radius clip_distance of the eye is invisible.
Serialized with presence (lives on camera structs), so follow mode adopts leader's clip settings.
Clamped to [0, volume_diagonal].
Clip Distance Shader Implementation
New clipParams: vec4f uniform added to the volume shader uniform buffer: x = clipDistance, y = clipMode (0.0 = plane, 1.0 = sphere), z and w reserved for future use.
Shader computes ray intersection with the clip plane or sphere and adjusts tStart forward if the intersection is further than the current entry point.
Applies identically to both translucent and MIP render modes.
Clip Distance Controls
UI: slider + clip mode toggle (plane/sphere) in the toolbar, visible in 3D modes.
Keyboard: bracket keys [ / ] for continuous adjustment (held keys, via RAF loop and key state tracker). Adjustment rate proportional to volume diagonal.
Added to keybinding registry as "clip.decrease" and "clip.increase".
WASM API Rename
Getters become mode-neutral: view_proj_3d() → view_proj(), inv_view_proj_3d() → inv_view_proj(), eye_position_3d() → eye_position(), ray_hit_local_3d() → ray_hit_local(). These dispatch on the Camera enum internally.
Arcball mutations get prefixed: rotate_3d() → arcball_rotate(), pan_3d() → arcball_pan(), zoom_3d() → arcball_zoom().
New: fly_tick(dt, forward, right, up, yaw, pitch, roll) — single per-frame command where forward/right/up are -1/0/1 from held keys, yaw/pitch/roll are floats. Rust handles all orientation × direction × speed × dt math.
New: fly_adjust_speed(factor) — multiply speed_multiplier.
New: camera_mode() -> String — returns "slice", "arcball", or "fly". Replaces is_3d().
Mode Switching
Arcball → Fly: position = eye_position(), orientation derived from view direction + up vector. Speed multiplier initialized to 1.0. Clip distance set to default (~0.5-1% of volume diagonal).
Fly → Arcball: target = point along view ray (volume center or fixed distance ahead, whichever closer). Theta/phi/distance derived from position relative to target. Clip distance reset to 0.0.
Keybinding System (3 Layers)
Layer 1 — Key State Tracker: useKeyState hook mounted on the viewer container (tabIndex={0}). Maintains Set<string> of pressed keys. Clears on blur. Suppresses when active element is <input>/<textarea>. Calls preventDefault() on bound keys.
Layer 2 — Binding Registry: Plain config object mapping action names to keys (e.g., "fly.forward": "w", "clip.increase": "]"). Easily changeable.
Layer 3 — Consumers: useFlyCameraInput hook reads key state + bindings, runs RAF loop computing dt (clamped to 100ms max) from timestamps, translates held keys to fly_tick parameters. Also provides mouselook pointer handlers. Clip distance adjustment is another consumer reading clip.increase/clip.decrease from the same key state.
Input Strategy Pattern
VolumeViewer swaps pointer handler sets based on camera mode: arcball handlers (existing behavior) vs. fly handlers (mouselook drag, scroll = speed adjust).
Canvas Focus & Hint
Auto-focus canvas on mode switch and on pointerdown.
Hint overlay shows on every fly mode activation: "WASD move · QE up/down · IKJLOU look · Scroll speed". Dismisses on first keypress or after 5 seconds.
Render Pipeline
Minimal changes: renamed getter calls in volumePath/minimapPath/PeerCursors. New clipParams uniform passed to volume shader. Shaders otherwise unaffected.
Presence & Multiplayer
Fly variant and clip distance serialize fully via serde. Peers see fly camera state and clip settings in PresenceState.
Follow mode faithfully reproduces leader's camera, including fly mode and clip distance.
Peer cursor math uses generic getters — works with Fly by adding match arms.
Delta Time
dt computed in JS from requestAnimationFrame timestamps, passed to Rust via fly_tick. Clamped to 100ms max.
Testing Decisions
Good tests for this feature verify external behavior through the public API without depending on internal implementation details (e.g., test that fly_tick moves the camera to the right position, not that a specific quaternion multiplication was called).
Modules to test:
Quaternion math & Fly camera logic (Rust unit tests)
fly_tick produces correct position given known orientation, direction, speed, and dt.
fly_tick produces correct orientation given known yaw/pitch/roll inputs.
view_proj() returns a valid (invertible) 4x4 matrix for Fly camera.
eye_position() returns the Fly camera's position directly.
Mode conversion: Arcball → Fly → Arcball preserves approximate view direction and eye position.
Speed multiplier correctly scales movement distance.
dt clamping: large dt values don't cause excessive movement.
Quaternion normalization: orientation stays unit-length after many successive rotations.
Clip distance logic (Rust unit tests)
Clip plane intersection correctly computes adjusted tStart for known ray/plane configurations.
Clip sphere intersection correctly computes adjusted tStart for known ray/sphere configurations.
Default clip distance scales correctly with volume diagonal.
Clip distance clamping to [0, volume_diagonal] works.
Keybinding system (TypeScript tests)
Key state tracks pressed/released keys correctly.
Key state clears all keys on blur event.
Bound keys are suppressed (preventDefault) when viewer is focused.
Key events are ignored when an input/textarea element is focused.
Out of Scope
Collision detection with volume boundaries
Movement inertia or damping
Crosshair overlay in fly mode
User-customizable keybinding UI (bindings are changeable in code, not via UI)
Gamepad or controller input
Animated clip plane transitions
Further Notes
The fly camera's base movement speed is derived from the volume's bounding box diagonal, ensuring reasonable defaults across datasets of varying size. The scroll wheel multiplier (~1.2x per tick) gives fine-grained speed control on top of this.
The clip distance default for fly mode (~0.5-1% of volume diagonal) prevents the "face pressed against the glass" effect when flying inside volumes, while being small enough not to hide meaningful structure.
The keybinding system is intentionally minimal (no event bus, no priority system, no context stacks). It can be extended when additional consumers arrive.
Delta time comes from JS requestAnimationFrame timestamps, passed to Rust via the fly_tick WASM call. This avoids needing a clock in WASM.
Clip mode (plane vs. sphere) is included primarily for experimentation. Plane mode is expected to be the primary mode used in practice.
