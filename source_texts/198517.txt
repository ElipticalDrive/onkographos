Issue body actions
The RTK forward projection filters use a bounding box (structurally represented as voxel indices boxMin and boxMax) of the input volume to determine ray-casting bounds. The physical volume extent of an ITK image as defined and illustrated in the ITK Software Guide, section 4.1.4 ranges from its origin minus half a voxel to the point that is size[dim] voxels away from it along each direction. However, in both CPU and GPU implementations, the box coordinates are not computed corner-to-corner (as would be expected following the previous description), but voxel-center-to-voxel-center. This makes the bounding box half a voxel too small along each boundary.
For example, in a recently added test, the axis-aligned ray integral from accumulating through a 10-voxel-wide volume of constant intensity 1.0 is not 10 (the path length multiplied by the intensity) but 9. In the limit of a single voxel volume, we would have boxMin == boxMax, resulting in a 0-valued forward projection even when the voxel is definitely crossed by the source-detector ray.
Interestingly, the comment in the CudaForwardProjectionImageFilter class (linked and highlighted previously) correctly states that the box limits in ITK indices should be "index-0.5 to index+size-0.5" (i.e. a box of width size). The implementation immediately following the comment defines instead a size-1-wide bounding box.
Unless there is a deliberate reason to use voxel-center bounds, it seems that the box coordinates should be offset by -0.5 for boxMin and +0.5 for boxMax to match the physical extent of ITK images.

This has been a design choice. RTK is using linear interpolation in its forward projectors. Outside these limits, linear interpolation is not possible. So cumbersome processing is required to extrapolate the additional 0.5 voxel border (see e.g. itk::LinearInterpolateImageFunction).
Thanks for pointing out the wrong comment, #985 aims at fixing it.
Is there a reason why you think it is a problem? IMO, it is only a problem for 2D reconstruction but I wouldn't change this choice.

I see, thanks for the explanation. This was a small problem for me when I wrote the ray-cast clipping test which I mentioned previously. I originally tried using a single-voxel volume to make the test minimal and as simple as possible, but the projection value was always zero because of the shrinked bounding box.
I understand this design choice since linear interpolation on the boundary is tricky. I am a bit biased because I mostly work with the GPU filter, in which we get all that for free with CUDA textures, so I believe no further change would be needed in that part of the codebase. For the CPU filter, my naive intuition would be to clamp the continuous index to the [0, size] range before interpolating its intensity value to get the equivalent behavior. But I am definitely not familiar enough with the CPU implementation to tell whether this would be sufficient or correct, nor whether the performance cost would be acceptable.
Another reason I thought the half-voxel boundary was intentionally being modeled is that the CUDA ray-casting code carefully accounts for sampling offsets at the entry/exit points of the box by stepping half a voxel inside the box for the first ray sample and compensating for up to half a voxel step length error at the last sample.
In practical applications, with comparatively large volume sizes and small voxel spacing, I agree that the impact would be limited and likely dominated by other sources of numerical error like the discretization of the ray integral itself. So I think fixing the inconsistency between the comment and implementation as done in #985 is already satisfactory.
