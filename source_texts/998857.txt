Summary
The Node viewer binding can prepare DBT inputs with volumeHandler: { kind: "laplacian-mip" }, but the current render path only returns raw stored-frame pixels. For derived volume handlers such as laplacian-mip, renderFrame currently rejects the display frame with DERIVED_FRAME_NO_RAW_SOURCE.
For Electron viewer integration, we need a Node API that can render display frames produced by volume handlers, including derived laplacian-mip projections.
Current behavior
The landed Node API exposes:
```
prepareDicom(input: DicomInput, options?: PrepareOptions): PreparedDicom
renderFrame(prepared: PreparedDicom, frameIndex: number): RenderedFrame
```
FramePlan.displayFrames can contain { kind: "derived" }, and tests intentionally assert that raw rendering rejects derived frames. That is correct for a raw stored-frame API, but it leaves no Node path for actually displaying the derived MIP image.
Requested behavior
Please expose a viewer rendering path that returns pixels for display-frame outputs from volume handlers, including laplacian-mip.
A possible API shape:
```
renderDisplayFrame(prepared: PreparedDicom, frameIndex: number): RenderedFrame
// or prepared.renderDisplayFrame(frameIndex)
```
Expected behavior:
prepareDicom({ path }, { volumeHandler: { kind: "laplacian-mip" } }) produces a one-frame derived display plan for DBT volumes.
renderDisplayFrame(prepared, 0) returns the projected laplacian-mip image bytes instead of throwing DERIVED_FRAME_NO_RAW_SOURCE.
The existing raw stored-frame rendering contract remains available for callers that need original stored-frame samples and exact stored-frame mapping.
Returned frame metadata remains viewer-safe: width, height, dtype, samples per pixel, photometric interpretation, pixel spacing, rescale/window metadata where meaningful, display-frame index, and frame source.
The display rendering path does not crop, resize, or pad unless the caller explicitly requested such a transform.
The result should be safe to consume from Electron/Node with large buffers and without unnecessary copies where practical.
Why this is needed
mammogram-annotator plans to use dicom-preprocessing as its DICOM renderer. For standard 2D mammograms, raw stored-frame rendering is enough. For DBT inputs, the annotator needs to present a 2D laplacian-mip projection for annotation. Without a derived display-frame render API, DBT inputs prepared with laplacian-mip cannot be displayed through the Node binding.
We are planning to consume the Node bindings from git/source dependencies rather than requiring npm publication.
Suggested tests
laplacian-mip DBT input returns one derived display frame and renders successfully through the new display render API.
Existing raw renderFrame behavior continues to reject derived-only frames with DERIVED_FRAME_NO_RAW_SOURCE.
Single-frame and stored-frame display plans still render identically through raw and display render paths where applicable.
Frame metadata is preserved for derived display output.
Invalid frame indexes and unsupported transfer syntaxes continue to return structured errors.
Path and byte inputs have parity for the display render path.
