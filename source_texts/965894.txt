Limitations

Overview
Adds bounded diffuse indirect illumination to the experimental ray-tracing scene renderer via a configurable maxBounces option (clamped between 0 and 8, defaulting to 0). The ray generation shader now evaluates multi-bounce paths through traceDiffusePath using cosine-weighted hemisphere sampling, accumulating surface emission, direct lighting, and throughput across bounces.
The ray-tracing uniform buffer layout is expanded to pass transport settings to the compute passes, and retained history is automatically invalidated when transforms or lights change while indirect bounces are active. In addition, example applications and documentation migrate public basemap styles from CARTO to OpenFreeMap.

Indirect lighting stays unstable
With maxBounces > 0, traceDiffusePath feeds noisy indirect samples into the existing history clamp. The clamp pulls the saved average toward each new sample before averaging. If history and its neighbors are zero but a new sample is 10, it raises history to 5 regardless of the saved sample count. Rare emitter hits can therefore cause bright flashes instead of averaging out across unchanged frames.
Skip this clamp for unchanged progressive history so indirect samples can average correctly.

Indirect light bypasses fog
With positive fogDensity and maxBounces, indirect light bypasses fog between the camera and the first surface. evaluateDirectLighting applies fog only to each hit's local light. traceDiffusePath then adds later hits without applying the first segment's visibility, so distant surfaces can remain brightly lit through dense fog.
Apply the camera fog to the combined surface radiance, rather than only its direct-light contribution.

Secondary bounces reuse primary shading
Medium Severity
traceDiffusePath adds evaluateDirectLighting at every bounce. That shader was built for camera rays, so it reapplies ambient fill and distance fog on secondary hits. With the default ambient term, indirect paths pick up extra energy, and fog is mixed using bounce-segment length rather than camera distance, so GI looks too bright and fog-tinted when maxBounces is enabled.

Fresnel term can produce NaN
Medium Severity
The bounce Fresnel uses pow(1.0 - max(dot(direction, halfDirection), 0.0), 5.0) without clamping the argument into [0, 1]. Direct lighting already clamps this. If the half-vector dot slightly exceeds 1, pow of a negative base is undefined in WGSL and can write NaN into the pixel. Progressive history and temporal reprojection then keep that NaN until a reset.
