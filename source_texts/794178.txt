Frustum Culling: Stop Sending the GPU What the Camera Cannot See
A practical guide to camera-frustum culling for small 3D games: why clipping is not a substitute for culling, how bounding spheres and AABBs keep tests cheap, and when a BVH becomes worth adding.
By Evan Sorrell / Pixelwolf
Image credit: MarinaVladivostok / Wikimedia Commons // CC0 1.0
A small 3D game can waste a surprising amount of work on things the player cannot see.
A house behind the camera, a forest beyond the left edge of the screen and a room on the other side of a wall may all still exist in the scene. The renderer does not automatically know which higher-level objects are worth submitting. The graphics pipeline will clip primitives against its clipping volume, but relying on that alone means you can still spend CPU time preparing objects and GPU time transforming geometry that never contributes to the final frame.
Frustum culling is the cheap first filter: test an object's simple bounding volume against the camera's visible volume before submitting the object for drawing.
The frustum is your camera's visible volume
With a perspective camera, the visible region is shaped like a truncated pyramid. It is bounded by six planes: left, right, top, bottom, near and far. Anything completely outside one of those planes cannot appear in the image.
The distinction between clipping and culling matters. OpenGL's pipeline clips primitives to the clipping volume as part of vertex post-processing. That is necessary for correct rasterisation, but it is late in the process. Application-level frustum culling is an earlier decision: do not submit an entire object when a cheap test already proves that it cannot be visible.
Khronos' current Vulkan tutorial uses exactly this pragmatic pattern in its simple-engine example: extract the camera frustum planes once per frame, keep an AABB for each mesh instance, transform that bound to world space and test it against the planes before drawing.
Do not test every triangle
The culling test should be much cheaper than the work it avoids. Testing every triangle against six planes usually defeats the point.
Instead, wrap an object in a simple bounding volume. Two useful choices are a sphere and an axis-aligned bounding box (AABB).
A bounding sphere is extremely cheap to test. For a normalised frustum plane with normal n and distance term d, calculate the signed distance from the sphere centre c:
```
distance = dot(n, c) + d;
```
If distance < -radius for any frustum plane, the whole sphere is outside and the object can be rejected. If it survives all six planes, keep it as a possible draw.
An AABB is tighter for many buildings, props and level chunks. A common plane test selects the box corner that lies furthest in the direction of the plane normal. If even that most-positive corner is outside the plane, the entire box is outside. This keeps the test conservative: an object may occasionally survive even though none of its pixels will finally be visible, but a visible object should not be incorrectly thrown away.
Conservative is better than clever and wrong
Frustum culling is not trying to prove that an object definitely contributes a pixel. It is trying to cheaply prove when an object definitely cannot.
That means false positives are acceptable. A large tree whose AABB touches the frustum may be submitted even if its actual branches remain off-screen. The cost is a draw that could theoretically have been avoided. A false negative is much worse: a visible object disappears because the culling bounds or plane maths are wrong.
Give animated objects enough room for their full motion. A character's bind-pose bounds may not contain a sword swing, cloth movement or exaggerated animation. Particle systems, foliage and procedural meshes need the same consideration. Bounds are production data, not merely a mathematical afterthought.
Transform the bounds carefully
A sphere is easy under translation and uniform scale: transform the centre and scale the radius. Non-uniform scale is more awkward because the transformed sphere becomes an ellipsoid; a safe simple approach is to multiply the radius by the largest absolute scale component.
For an AABB, blindly transforming only the original minimum and maximum corners is wrong once rotation enters the picture. The transformed box must contain all transformed geometry. You can transform all eight corners and rebuild a world-space AABB, or use the object's transform and local extents to derive conservative world extents.
Whatever method you choose, calculate world bounds when the object transform changes rather than rebuilding them unnecessarily for static objects every frame.
Start with a flat object list
For a small game, do not begin by writing an octree.
If you have a few hundred independently drawable objects, six cheap plane tests against a flat array can be perfectly reasonable. It is simple to debug, cache-friendly when the data is laid out sensibly, and gives you a baseline measurement. The important optimisation is often avoiding expensive per-object setup and draw submission for obviously invisible objects, not building the most sophisticated spatial structure possible.
Instrument it. Record how many renderable objects exist, how many fail the frustum test and how many reach the draw list. If 900 of 1,000 objects are being rejected cheaply, the system is doing useful work. If almost everything is always visible, a more elaborate hierarchy may cost more CPU than it saves.

When a flat list stops being enough
As scenes become larger, a hierarchy can reduce the number of individual tests. A bounding-volume hierarchy groups objects inside larger bounds. Test the parent bound first; if it is outside the frustum, reject the whole branch. Only descend into children whose parent might be visible.
The same idea appears in octrees, loose octrees, grids and other spatial structures. The best choice depends on the world. A mostly static open environment, a dense indoor level and a scene full of moving entities have different update and query costs.
For an indie renderer, add hierarchy because profiling shows the flat pass becoming expensive, not because a rendering textbook says every engine needs one.
Frustum culling does not solve occlusion
A frustum only answers whether an object is inside the camera's potential field of view. It does not know that a mountain is hiding a village or that a closed wall hides the room behind it.
That is a separate occlusion problem. Portals and room systems can work well for structured interiors. Hierarchical depth or hardware occlusion queries can help in other renderers. But those techniques introduce their own latency, bookkeeping and complexity. Frustum culling remains valuable because it is cheap, deterministic and easy to apply before more expensive visibility work.
A practical order for a small renderer
Keep the implementation boring at first. Store local bounds with each mesh. Maintain world bounds for each instance. Extract the six frustum planes once when the camera matrices are updated. Test renderable objects against those planes. Build a compact visible list. Only then perform material sorting, state setup and draw submission.
During development, add a debug mode that draws the bounds and reports the culling result. Move the camera slowly across the edge of objects. Test near-plane intersections, large objects, rotated objects, scaled objects and animated meshes. A culling bug is much easier to diagnose when you can see the box that made the decision.
Most importantly, measure the result. Polygon count is visible and easy to obsess over, but a renderer's workload is also shaped by how much scene data it processes and submits. Rejecting an entire invisible object with a handful of arithmetic can be far more useful than shaving another dozen triangles from that object's mesh.
For a small 3D game, that is the real value of frustum culling: not clever graphics programming, just refusing to do work you already know cannot matter.
