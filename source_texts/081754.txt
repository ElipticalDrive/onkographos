The idea behind picking max area type is to favor walkable areas when there's walkable and non-wealkable area close to each other.
The reason for the current merge logic (take largest) is that many games have small geometry, which is not navigable based on slope. Think lo-res pebble or tree roots. Or even the vertical section of stairs. There were even more exotic cases on production levels. rcFilterLowHangingWalkableObstacles handles the same problem in case the obstacle is floating. This happens more when the cell height is small.
An earlier version of Recast tried to reconstruct the slope from the rasterized data, but It was not very reliable. That would have solved the root cause (pun intended).

Quick note; in my experience the 'climbing' is really 'stepping' and wouldn't be handled with e.g. bespoke climbing animations, but normal locomotion with IK to place the feet and alter pose. Actual climbing needs something more, e.g. off-mesh links. Physics-wise, on a basic level it's handled by bumping a capsule collider over the physics geometry (with an end cap radius of the climb height), but that's quite unreliable so many games use extra raycasts around characters to move the collider up/down if they need to step.

TL;DR: there are many ways, some will treat your example as walkable, some will not :( We can either be conservative and cause a break in the navmesh, demand good physics from users and join it up, or provide options for users to configure it to match the navmesh to how their physics works.
The situation in your last diagram with the floating object? Annoyingly, it depends on the physics implementation - some games will happily move a character up that, some won't. As such it's hard to know what to do with the navmesh :(
The best implementations (i.e. the ones that seem to map capsules most accurately to what humans would actually be able to do given the geometry) will indeed have a several raycast checks for flat terrain in 2D range (not necessarily agent radius, maybe a bit further), within step height, with a check that there's line of sight to that point so they're not stepping on terrain the other side of a thin wall. As such, the obstacle on the right in your example would be traversable.
The most common implementation (i.e. the one everyone starts with and is all over the web in physics character controller tutorials) is applying lateral forces to a capsule with end cap radius ~= agent radius, and allowing contact resolution to move the character in the right direction. In that case, in your example the object probably won't be traversable as the capsule will probably collide with the slope first rather than the corner with the flat part, and that slope is steep enough that gravity will counteract the upwards component of the force.
So here it looks like we need to either
Be conservative and put a break in the navmesh there, so we don't generate paths that some codebases can't navigate
Be a bit opinionated about how end users should make characters follow these paths, joining the navmesh in these cases and telling people they should have better character controllers
Provide options to handle this in different ways
Sorry, I feel like I've just made it more complicated than it was! Just thought I'd offer some observations about how I've seen things done out 'in the wild'. Take it with a pinch of salt, clearly I've only seen a tiny proportion of all games' implementations :)

Here's an error that's happening both in some custom code using Recast, as well as in latest Unity, with three simple cubes:
The cube on the bottom has AreaID = Water (think e.g. an ocean), the large 'tower' block and the slope leading up to it have AreaID = Walkable. In our custom code we use 0 = NonWalkable, 1 = Walkable, 2 = Water. Unity uses 0 = Walkable, 1 = NonWalkable, and then 3 is the first user-defined area, though they're probably doing some internal remapping to play well with Recast's internal RC_NULL_AREA = 0.
The issue that I'm seeing is that the Water area from below is being merged / propagated up all the way along the non-walkable upright triangle, where it even takes precedence over the Walkable because it has the larger ID:
```
// Merge flags. 
if (rcAbs((int)s->smax - (int)cur->smax) <= flagMergeThr) 
    s->area = rcMax(s->area, cur->area); 
```
I 'fixed' this by giving Walkable a large ID, but of course that's more of a workaround than a general solution.
