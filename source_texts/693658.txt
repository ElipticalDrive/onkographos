Abstract
1
With network technologies now offering latencies approaching that
of memory, sharing distributed memory becomes an increasingly
feasible approach. However, memory virtualization remains largely
unexplored on distributed supercomputers, and developers rely on
complex programming models to achieve high performance. We
propose a hardware-software co-design approach to enable a single
virtual global address space. Our method introduces the concept
of virtual nodes, which are identified by the most significant bits
of the virtual address, thereby defining address space ranges that
correspond to different nodes within the distributed system. To
support this approach, we provide the necessary hardware support
and validate its efficacy using two open-source simulators: gem5
and SST. Experimental results demonstrate that programming this
system closely resembles the shared memory programming model,
and we present its scalability using a benchmark. These results
demonstrate the viability of implementing a shared virtual address
space in distributed systems, simplifying the development of highperformance computing applications.
Virtualization is a technique that allows a single physical resource
to be shared concurrently by multiple applications. Memory virtualization, in particular, ensures that multiple processes can safely
and efficiently utilize the same physical memory, reducing conflicts
and enhancing programmability. It also facilitates optimizations,
such as the sharing of common data (e.g., system libraries, static
data and kernel), reducing memory usage and data duplication. As
systems transitioned from single-core to many-core architectures,
memory virtualization played a key role in enabling efficient core
communication and synchronization.
In High Performance Computing (HPC), supercomputers comprise thousands of nodes, each running the same application. Within
a node, many-core processors share memory through a coherent
virtual address space, which specifies the location of data in memory. However, across nodes, which are interconnected by a highperformance communication network, direct remote memory access is not straightforward. As a result, memory coherence cannot
be efficiently maintained, and memory virtualization is not typically applied. In this case, applications are divided into multiple
processes, each running on a different node and owning a separate
address space. For two processes to communicate and synchronize
tasks, they must exchange messages, which often involves copying
data between nodes, potentially resulting in data duplication. This
makes programming for these systems very challenging and makes
it impossible to share references to data via pointers.
In this work, we introduce a simple virtual global address space
(VGAS) scheme, along with the corresponding hardware support for
distributed systems and a novel programming paradigm. To validate
and evaluate our design, we developed a simulation platform that
combines two open-source simulators: gem5, a cycle-approximate
CPU simulator [3]; and the Structural Simulation Toolkit (SST),
a framework for large-scale simulation [7, 10]. This platform is
available on Gitlab1 .

some studies date from prior the widespread adoption of multi-core
architectures. However, with the advancement of network technologies, which now offer latencies closer to that of memory, remote

introduced the concept of a Distributed Shared Memory (DSM),
providing a virtual address space that is shared among all processors of a distributed system. They argued that the biggest challenge
in building such systems is the memory coherence problem, and
present two classes of algorithms—centralized and distributed—
demonstrating that the former might induce traffic bottlenecks. In
this work, we do not focus on the coherence problem, but rather
in the sharing of a virtual address space and virtual-to-physical
translation, along with its hardware support. Nonetheless, these
problems are orthogonal, and memory coherence can still be implemented on top of our solution.
Since the introduction of Remote Direct Memory Access (RDMA),
remote data access without CPU involvement has been possible.
When combined with low-latency networks, this approach is very
valuable, but it comes with a few disadvantages. Namely, the requirement of exclusive memory ranges to be registered and pinned
indefinitely, so that the Network Interface Controller (NIC) can
directly read and write from the system memory without CPU intervention through remote physical pointers. If the memory were
to be deallocated or relocated, the remote pointers would become
invalid. Therefore, while RDMA offers performance benefits, it also
introduces constraints that must be carefully managed.
Many existing solutions are based on RDMA. Dragojevic et al. [4]
introduced FaRM, which provides a shared memory abstraction
with a Partitioned Global Address Space (PGAS)-based programming model. However, it is heavily dependent on RDMA. Grant et
al. [5] presented RVMA, a RDMA-like solution for remote memory
access with virtual addresses. These addresses are, however, limited
to mailboxes implemented in the NIC of each node, which must be
processed by the receiving application. Our approach aims to map
all shared data into the global address space, not just mailboxes.
Wang et al. [11] introduced xBGAS, a microarchitecture extension to the RISC-V architecture. With extended registers and new
instructions, the xBGAS extension provides direct accesses to remote shared memory at the Instruction Set Architecture (ISA) level,
and memory accesses are separated into local and global instructions. However, xBGAS only takes into account a shared physical
address space, whereas a virtualized approach would be more flexible and more easily integrated with existing Operating System (OS)
mechanisms such as paging, protection and dynamic reallocation.
Finally, Besta et Hoefler [2] introduced the use of an extended
Input-Output Memory Management Unit (IOMMU) to handle remote memory accesses efficiently. However, remote memory is not
mapped into a global space; instead, remote accesses are intercepted
and handled locally by the CPU. They also proposed the use of extended IOMMUs for enabling virtualization of remote memories,
but to the best of our knowledge, no subsequent work has been
conducted in this area.

Virtual Node
A Virtual Node (vnode) is a new abstraction that is associated
and mapped to a Physical Node (pnode). The vnode identifier is
incorporated into the virtual address (Figure 1), and is used to define
address space ranges that belong to a node and can be accessed
globally. The pnode uniquely identifies a node. A few assumptions
are made:
(1) Memory coherence is maintained within a vnode.
(2) A vnode can be mapped to only one pnode at a given time.
(3) A vnode can be remapped from one pnode to another.
(4) Vnode and pnode identifiers 0 are reserved for local accesses.
(5) Virtual-to-physical node translations are coherent accross
the entire system.
The number of vnodes is inherently limited by the number of bits
used to identify them. Gem5’s current RISC-V model supports only
39-bit virtual addresses, thus limiting us to 4-bit vnode identifiers
for the prototype presented in this work. Nevertheless, this work
targets supercomputers with large address spaces, so it could also
be implemented for 48- or 57-bit virtual addresses.

In order to perform the virtual-to-physical node translation, we
introduce a new component to the MMU, called the Node Management Unit (NMU). The NMU has access to a page table-like
data structure, named node table, that maps the process identifier (ASID) and the vnode identifier to the corresponding pnode.
This data structure must remain coherent across the entire system,
meaning that whenever a vnode is remapped to another pnode, all
nodes must be informed and then update their translation table (as
per assumptions 3 and 5). To limit the latency penalty of remote
accesses, after the first access to a remote data, the system uses a
segment of the local memory as a cache, called the global data
cache. The NMU maintains another hardware-managed directory
which maps virtual addresses to global data cache entries.
Node translation takes place immediately before address translation, and is used as a selector to determine whether to perform
a local or remote memory access. For local memory accesses, the
standard translation process is followed. If the access is remote,
the NMU first checks for a local data copy. If found, it forwards
the request with the translated address to the global data cache.
Otherwise, a new remote memory access is requested.

3.2
Our system is designed to enable the sharing of virtual addresses
across multiple distributed nodes. To support this, we introduce
node identifiers and new components that facilitate global memory
accesses.
Remote Memory Access
To manage and facilitate remote memory accesses, we introduce the
Global Memory Controller (GMC), analogous to xBGAS’s Remote Memory Controller [8]. Its main functions include forwarding

Figure 2 illustrates the entire process of a remote read from Node
A to Node B, which begins with configuring the IOMMU and the
GMC in all system nodes before the application is executed. After
the configuration step is completed, the application can be executed,
with memory accesses handled by the MMU for address translation
(Step 1). The NMU handles the vnode translation: if the access is
local, or a local copy is available, the request is forwarded to the
memory hierarchy (Step 8); otherwise, a message containing the
virtual address, the pnode and the global data cache address is sent
to the GMC, initiating a new remote memory access (Step 2). The
GMC configures the offload-enabled NIC, which packetizes and
sends the memory request to the appropriate node (Step 3). Once
the request is received in Node B, the NIC reads its content, and
the address is translated by its IOMMU. If the data is not mapped,
a page fault interrupt is triggered and handled by the CPU (Step 4);
otherwise, the process proceeds to the address translation and
memory access (Step 5). Once the data is fetched, it is sent back to
the requesting node (Step 6). Node A’s GMC writes a copy of the
data to the global data cache (Step 7) and signals the MMU, which
can finally fetch the data (Step 8).

Programming model
For decades, message-passing programming models have been the
gold standard for distributed systems, offering good performance
and enabling fine-grained control over data. However, this model is
inherently complex and comes with several limitations, such as the
lack of shared address spaces. This prevents processes from directly
accessing data from one another, requiring explicit data sharing. It
also requires explicit data copies, mapping it to multiple address
spaces and making it impossible to share pointers between nodes.
With our system, processes in different nodes can share an address space. This introduces a new programming paradigm where
data sharing between nodes is no longer explicit, resembling the
shared memory model. A key advantage is that dereferencing and
sharing pointers become possible among distributed nodes. Instead
of explicitly managing buffers separately in each node, synchronization buffers can be mapped into the shared address space, reducing
overheads and unnecessary copies. Synchronization mechanisms
for these buffers are simplified, as processes can rely on shared
memory constructs to coordinate access to shared memory regions.
As previously mentioned, one of the current implementation
limitations is the lack of global memory coherence. This means
that memory changes in global data are not immediately visible to
other nodes, which can lead to inconsistencies and synchronization
issues. To address this limitation, the programming model must
explicitly ensure memory coherence. To facilitate synchronization,
we implemented a set of buffers that are shared between each pair
of nodes, exclusively for control messages such as task start and
end notifications. These buffers serve as a common memory that
can be accessed by any node, but written by only one of them. By
using them, developers can easily synchronize the nodes. With

Implementation
Our design was implemented and tested using an integration of
gem5 and SST [6], as shown in Figure 3. In [6], packets could only
be sent from gem5 to SST components, but we extended this functionality to enable SST components to send packets to gem5 devices.

allows us to leverage gem5’s existing models to be accessed from
any device. It simplifies the development process and ensures compatibility between the two systems.

Results
Figure 4: Results for the merge sort benchmark
For a first evaluation, we developed a merge sort benchmark to
assess the performance of our distributed system. The data array is
initialized by Node 1, and a notification is sent to each participating
node, indicating they can retrieve the data from Node 1 using their
pointers. Given that memory is not coherent across nodes, each
node handles a different segment of the array at any given time and
performs the sorting operation locally. This distributed approach
allows for parallel processing, which can significantly enhance the
sorting efficiency for large dataset. At the conclusion of the local
sorting process, Node 1 gathers all the sorted subarrays from the
participating nodes and merges them into a single sorted array.
We evaluate the scalability of this implementation using up to 8
nodes, with different dataset sizes (Figure 4). Our analysis reveal
that scaling is relatively consistent across all dataset sizes, scaling
up to 4 nodes. However, the implementation of page-granularity
only results in an average performance speedup of 1.04×. This slight
improvement can be attributed to the current limitation of the pagegranularity implementation, where a local copy is still required,
thereby constraining the potential performance gains. Furthermore,
our analysis indicates a slight slowdown when using 8 nodes. One
potential reason for this slowdown is a bottleneck on Node 1, which
is accessed concurrently by all nodes to retrieve the data. This
concurrent accesses could lead to contention, limiting the overall
performance gains expected. Additionally, the slowdown might be
attributed to a limitation in the benchmark’s implementation, as
the gathering of sorted subarrays could be performed concurrently
by other nodes rather than being handled exclusively by Node 1.

Conclusion
Although memory virtualization is essential in modern systems,
it currently lacks on computers with distributed memory. We proposed virtual nodes, which can be integrated into the addressing
scheme to map data across multiple physical nodes. We introduced
hardware support for the translation and remote memory accesses,
and implemented it using two widespread open-source simulators.
The current implementation is somewhat limited, and several
new features are envisioned to enhance its functionality. Firstly,
we would like to test our implementation with more nodes, but it
depends on the gem5 implementation. Node translations should
be managed by the OS rather than being hardcoded into the NMU.
This would enable node translation remapping, providing greater
flexibility. Additionally, a node translation coherence protocol is
