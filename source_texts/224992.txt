Adds mujoco_warp/_src/diff.py, a custom-adjoint dispatch layer that makes MuJoCo Warp safe to use with Warp's reverse-mode autodiff (wp.Tape) and gives analytical adjoints (starting with #1535) a place to register.
Motivation
MuJoCo Warp modules compile their kernels with wp.set_module_options({"enable_backward": False}), because naive kernel-by-kernel autodiff through iterative constraint solvers (Newton / CG), Cholesky factorizations, and discrete contact pipelines is numerically unstable and memory-prohibitive.
As a result, on main, calling mjw.step(m, d) inside with wp.Tape(): records ~100 kernel launches whose adjoints are skipped. tape.backward() completes without an error, but the gradients through step are wrong (e.g., for an Euler slide joint, d.qvel.grad is 0 instead of dt).
Changes
Every public function in mujoco_warp is wrapped via _differentiable(globals()):
Context
Behavior
Outside wp.Tape
Passes straight through (if tape is None: return fn(*args, **kwargs)).
Inside wp.Tape, no registered rule
Raises NotImplementedError naming the function instead of silently producing wrong gradients. This includes functions that are not differentiable (e.g., put_model, make_data, reset_data).
Inside wp.Tape, registered AdjointRule
Unsupported requires_grad=True fields or arguments raise NotImplementedError. Otherwise the rule's input/output .grad buffers are enabled and either the forward call runs with the tape paused and a custom backward is recorded via tape.record_func (backward=fn), or the tape stays active so @wp.kernel(enable_backward=True) kernels record natively (backward=None).
This PR registers no adjoint rules; it provides the API that analytical adjoints register into.

Usage
Both examples run as-is on this PR. This PR registers no adjoint rules, so register the rules in the second example before running the first. The fwd_kinematics and step backward bodies are placeholders (the analytic VJPs come from the #1535 follow-up), so they contribute zero gradient; the mul_m rule is a complete adjoint.
Users: standard Warp autodiff
Users only use standard Warp autodiff (arr.requires_grad = True, with wp.Tape() as tape:, tape.backward(), tape.zero()) and existing mujoco_warp functions.
```
import mujoco
import warp as wp
import mujoco_warp as mjw


@wp.kernel
def site_target_loss(
  # In:
  site_xpos: wp.array2d[wp.vec3],
  target: wp.vec3,
  # Out:
  loss_out: wp.array[float],
):
  worldid = wp.tid()
  err = site_xpos[worldid, 0] - target
  wp.atomic_add(loss_out, 0, 0.5 * wp.dot(err, err))


xml = """
<mujoco>
  <option timestep="0.01" integrator="Euler"/>
  <worldbody>
    <body name="link" pos="0 0 0">
      <joint name="hinge" type="hinge" axis="0 1 0" damping="0.1"/>
      <geom type="capsule" size="0.04" fromto="0 0 0 0 0 -0.5" mass="1.0"/>
      <site name="tip" pos="0 0 -0.5"/>
    </body>
  </worldbody>
</mujoco>
"""
mjm = mujoco.MjModel.from_xml_string(xml)
mjd = mujoco.MjData(mjm)
m = mjw.put_model(mjm)
d = mjw.put_data(mjm, mjd, nworld=32)
loss = wp.zeros(1, dtype=float, requires_grad=True)

# step() and fwd_kinematics() automatically enable requires_grad=True on the
# Data fields their rules list (qpos, qvel, site_xpos, ...):
with wp.Tape() as tape:
  mjw.step(m, d)
  mjw.fwd_kinematics(m, d)
  wp.launch(
    site_target_loss,
    dim=d.nworld,
    inputs=[d.site_xpos, wp.vec3(0.0, 0.0, 0.5)],
    outputs=[loss],
  )

tape.backward(loss=loss)
qpos_grad = d.qpos.grad.numpy()
tape.zero()
```
Under a tape, only functions with a registered rule can be called. Non-differentiable work (model/data creation, resets, host copies, or simulation used as a constant) runs outside the tape; re-entering the same tape resumes recording:
```
tape = wp.Tape()
with tape:
  wp.launch(policy_kernel, ...)  # differentiable part
mjw.step(m, d)                   # non-differentiable work outside the tape
with tape:
  wp.launch(loss_kernel, ...)    # re-entering the same tape resumes recording
tape.backward(loss=loss)
```

Design notes
Field indexing (_FIELDS): At import time, _FIELDS indexes all top-level and nested wp.array fields of Model (including opt.*, stat.*), Data (including contact.*, efc.*), and RenderContext. For a registered rule, a requires_grad=True field that is non-float or not listed by that function's rule raises NotImplementedError naming the field; a requires_grad=True standalone array not in array_args raises naming the function.
Containers are found by type, not parameter name: Model, Data, and RenderContext arguments are identified by type in signature order, independent of keyword order. The first Data is the input and the last is the output; for in-place calls they are the same object. Only array_args are matched by name, since standalone arrays share a type.
Why in_fields/out_fields are auto-promoted: Enabling .grad on the rule's inputs and outputs chains gradients across multi-function sequences and multi-step rollouts without users enabling requires_grad on intermediate Data fields.
Why model_fields is opt-in: A rule may support many Model parameters (body_mass, geom_friction, dof_damping, ...). Opt-in avoids allocating .grad buffers and running parameter VJPs when only differentiating state and controls.
Promoted flags stay set: Warp frees .grad when requires_grad is set to False, so promoted flags are left set to keep gradients readable. Promoted arrays are tracked per function in a weakref.WeakSet and exempt from validation while that rule remains registered; re-registering a rule resets its previously promoted arrays (requires_grad = False) and clears its set.
Per-rule field validation: _validate(obj, rule) validates Model, Data, and RenderContext fields strictly against the called function's rule.fields[cls] (exempting arrays auto-promoted by an active rule). If a user enables requires_grad = True on a field supported by step (e.g., m.dof_damping) and calls fwd_kinematics (whose rule does not list dof_damping), fwd_kinematics raises NotImplementedError instead of silently contributing zero gradient.
CUDA graph capture: supported checks (which may synchronize with the host) are skipped while the arrays' device is capturing, so taped forward and backward passes can be captured with wp.ScopedCapture and replayed with wp.capture_launch.
Warp internals: diff.py reads and pauses the active tape through warp._src.context.runtime.tape (the attribute wp.Tape.__enter__ sets; Warp has no public getter) and uses warp._src.types.type_scalar_type to detect float vector/matrix dtypes (no public equivalent). Both are unchanged in Warp 1.15–1.17; pyproject.toml already requires warp-lang>=1.15, and diff_test.py exercises both, so a Warp change that moves them fails CI.
Known limitations
Unregistered functions raise under wp.Tape even when no gradient would flow through them (e.g., get_data_into); call them outside the tape.
Rules assume the first Data argument is the input and the last is the output.

Behavior changes (diff.py)
Change
Previous commit
updates
When validation runs
The forward ran on a scratch tape before field and argument validation, so an invalid call could launch kernels and mutate Data before raising.
All static checks run before the forward, and supported runs before any gradients are enabled. A rejected call launches nothing and leaves the tape unchanged.
When gradients are enabled
requires_grad was enabled on rule arrays after the forward.
It is enabled before the forward, so native (backward=None) launches and wp.copy see the gradient buffers.
Input vs. output roles
In-fields and out-fields were merged and checked by path on every Data argument.
The first Data is checked against in_fields and the last against out_fields. Allowed arrays are matched by identity, so a Data field passed as an array argument, or arrays shared through dataclasses.replace, work across calls.
Arrays promoted by an earlier call
Exempt unless the current call read them before writing them. Only kernel launches were inspected.
Exempt only if the current call neither reads nor writes them. Both kernel launches and wp.copy are inspected. Overwriting such a field would send this call's output gradient to the earlier rule, so it now raises; rules must list every promoted field they overwrite.
Standalone array arguments
Checked only if requires_grad was already set.
Also rejected when the same array is about to get gradients through another argument role, even on the first call. The error names the argument.
Native rules (backward=None)
Accepted kernels compiled with enable_backward=False, which silently gave zero gradients. tape.gradients from the scratch tape were dropped.
Raise requires a backward rule when any recorded kernel has no adjoint. Launches are appended only after the checks pass, together with the scratch tape's tape.gradients.
Tape use for custom rules
A scratch tape recorded about 100 launches for every call.
The scratch tape is used only for native rules or when there are promoted fields to check. Otherwise the forward runs with the tape paused.
supported
Ran on the user's tape, so its launches were recorded and API calls inside it raised. Only a sequence of reasons was accepted.
Runs with the tape paused. A single string is accepted. It is skipped during CUDA graph capture (wp.get_device().is_capturing replaces _device(bound)).
Tracking promoted arrays
Per-rule weak sets. Re-registering a rule reset requires_grad on its arrays, which freed .grad and could crash a pending tape.backward().
One global weak set. Re-registering keeps the promotions.
Gradients disabled after recording
tape.backward() hit CUDA error 700.
The recorded backward raises RuntimeError("Gradients for '<fn>' were disabled after recording.").
Registration validation
Generators were consumed during validation and registered as empty.
Arguments that are not sequences are rejected.
Simplifications (diff.py)
Removed the _Untaped context manager, _call_untaped, _validate, _unsupported, _device, AdjointRule.fields and the per-rule _PROMOTED dictionary. One _call(tape, fn, ...) helper switches the active tape.
_inputs (read-before-write tracking) became _accessed, a plain union of the arrays read or written. Added _has_adjoint.

Test checkpoint replay (mujoco_warp/_src/diff.py:271-277, mujoco_warp/_src/diff_test.py:675-733): The callback keeps references to mutable data, so reused buffers can contain the wrong step's state during backward. The linear rollout test cannot catch this because its gradients do not depend on that state. Use this nonlinear sketch for ordinary replay and CUDA graph capture, then compare its gradients with a full recorded rollout.
```
# Assume square(x, y) has a registered custom rule: y = x * x.
# Its backward adds 2 * x * y.grad to x.grad, then clears y.grad.
with wp.ScopedDevice("cuda:0"):
  # Allocate buffers before capture so their addresses stay fixed.
  x = wp.zeros(1, dtype=float, requires_grad=True)
  y = wp.zeros_like(x, requires_grad=True)
  seed = wp.zeros_like(x, requires_grad=False)
  checkpoints = [wp.empty_like(x, requires_grad=False) for _ in range(2)]

  def checkpointed_replay():
    # These resets are captured and run on every graph launch.
    x.fill_(2.0)
    seed.fill_(1.0)
    for saved in checkpoints:
      wp.copy(saved, x)
      square(x, y)
      wp.copy(x, y)  # 2 -> 4 -> 16, without recording a full rollout.

    # Enter with no active tape, as #1727's backward callbacks do.
    for saved in reversed(checkpoints):
      wp.copy(x, saved)
      with wp.Tape() as replay:
        square(x, y)  # Restore and recompute one step on a fresh tape.
      replay.zero()  # Also captured, so gradients reset on every launch.
      replay.backward(grads={y: seed})
      wp.copy(seed, x.grad)

  # Warm up kernels and run support checks before capture.
  checkpointed_replay()
  assert seed.numpy()[0] == 32.0  # d(x_initial**4)/dx_initial at 2.
  wp.synchronize()

  with wp.ScopedCapture() as capture:
    checkpointed_replay()

  for _ in range(2):
    wp.capture_launch(capture.graph)
    assert seed.numpy()[0] == 32.0  # Repeated launches must not accumulate.

```
import contextlib


def _call(tape, fn, *args, verify_access=True, **kwargs):
  with contextlib.ExitStack() as cleanup:
    cleanup.callback(setattr, wp_context.runtime, "tape", wp_context.runtime.tape)
    cleanup.callback(setattr, wp.config, "verify_autograd_array_access", wp.config.verify_autograd_array_access)
    wp_context.runtime.tape = tape
    if not verify_access:
      wp.config.verify_autograd_array_access = False
    return fn(*args, **kwargs)
