Hey all. In response to the multiple questions, here's the deal:
Have a nifti file of betas per condition ripped out of the output of 3dDeconvolve using 3dTcat. With 19 conditions, this gives a new file with 19 sub-bricks which is then brought into PyMVPA. The issue is that any resultant statmap (e.g., searchlight) that uses the original dataset to map2nifti ends up confusing 3dttest which refuses to run on 4D files. However, the searchlight map, for instance, is 3D.
From PyMVPA's perspective the original dataset has dimensions [4,61,71,61,19 etc.] and the Afni extensions (data.a.imghdr.extensions) still contains info about the original 19 sub-bricks. Since map2nifti simply copies the extensions over to the new stat map this fools 3dttest into thinking it's dealing with a 4D file.
The simple fix is setting data.a.imghdr.extensions = []. I also tend to fix the dimensions (setting 19 to 1) but if memory serves that doesn't matter from 3dttest's perspective.
It may be possible to parse the afni extensions and remove only those attributes that are causing afni to think that it's dealing with a 4d file, but that seems like it would be difficult to account for every contingency.

Yes, setting the header to nothing is the easiest solution. However it will
also destroy some meta-information that can be useful for AFNI; in
particular labels of each sub-brick (volume) and maybe stat codes (though
NIFTI provides support for the latter if I remember correctly).
In the case where the data is not modified (loading and saving) it would be
preferable to keep the AFNI extension data though. One approach is a manual
option to keep the data. Another would be to use heuristics to decide
whether the AFNI data should be kept or not. One simple approach would be
seeing if the number of sub-bricks has changed (e.g. by looking at
DATASET_RANK[1]);
if it has changed then nuke the headers.
Another approach would be to store the AFNI data in a more structured way -
so that slicing (selecting a subset of samples) actually keeps the
information for the samples that are kept. This would apply to all the
BRICK_* attributes, although some of them are a bit messy: STATSYM is a ';'
delimited string, LABS and KEYWORDS are '~' delimited, and STATAUX is the
most messy with different lengths according to which statistics are
represented. The obvious approach would be to store these as sample
attributes.... in that case the user could also set the labels for each
sub-brick manually for viewing in the AFNI viewer.
In this approach, saving a file would require setting SCENE_DATA
appropriately and generating a new id code.
Of course the best approach would actually have proper code to read AFNI
header data and treat them in a nibabel-ish way. That seems quite an effort
though.
To summarize three approaches:
nuke the attribute data by default
use a simple heuristic like whether the number of sub-bricks in the
header is different from the number of samples; nuke only in that case
parse all attributes and assign them as sample attributes and dataset
attributes. But that is more work to implement and test, and not as pretty
as now fmri dataset attributes become part of the dataset attributes.

e.g. if you 'kept' the extensions and you saved 11 of accuracies maps

encoded in the extension and ran 3dtest which would find 'ok -- matching

doing paired t-test on', i.e. something which might divert heavily from what
you think it should be doing. Do we want users to find it hard way? ;)

None: if extensions present, dump, and warn

False: dump extensions
