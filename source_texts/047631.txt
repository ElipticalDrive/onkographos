Add GPU voxelization, SuperSplat v1.1 pair export, CLI and lichtfeld.io APIs around one immutable packed volume. Reuse LFS activated tensors, tensor memory pools/current streams, memory-pressure accounting, progress callbacks and atomic output staging. Remove unused production CPU/dense paths and unreleased codecs; Walk belongs to #3791.
Source snapshots finish their reads on the relevant streams, including exceptional exits, without a device-wide synchronization. Contiguous bounds reductions and device sorting avoid the strided-reduction/host-sort bottlenecks. Export carries subtree cursors instead of restarting traversal for every output cell. Logical native bounds remain exact; export alone adds up to three empty cells per axis for v1.1 block alignment, with logical sceneBounds and correctly reflected cell positions.
Generation stops before exceeding 64 million sparse output records and checks pool-aware memory requirements for growth, compaction and actual CUB workspace. Export-intended runs reject provably impossible mixed-leaf topology early; raw records are not treated as format nodes. Auto remains scale-relative and reports its resolved size; explicit resolution is never silently changed. Pair overwrite uses one approval and rollback on ordinary failure/cancellation, with path-bearing diagnostics. Two-file publication is not crash-atomic or concurrent-reader-atomic.
Validation before the upstream-only rebase: exact-head full Release build with all 32 cores; 3 CPU, 5 CUDA and 7 CLI/export tests; independently decoded signed-axis permutations, density/scale checks, cross-stream snapshot failure and pair rollback; generated stubs match. Controlled 5M .05 input: 6.076 s before these review fixes versus 1.461 s after, packing 2.024 s versus 0.326 s, sampled peak GPU memory 1,956 MiB. Output is byte-identical to the independently checked 600/600-cell reference. The CUDA fatbin is approximately 249 KiB after separating host tensor preparation. These are local measurements, not a comparison against an unavailable original binary.
This layer adds 2,172 lines against master 8ba8e91416ed59d1a6497a393e1725dfa849e92d. The complete three-PR stack adds exactly 5,500 physical text lines, including tests, docs, generated stubs, all ten locales and build integration; the walking icon PNG is 704 bytes. Optional triangle surfaces/GLB, morphology, connected filtering, cutaway, coarsening and in-place regeneration remain deferred. Original work is preserved in local archives.
Synced onto upstream 8ba8e9141 (#3820), preserving its STBN source/include fix exactly. Each layer differs from its previously validated head only by those two upstream files; collision code and the combined 5,500-line count are unchanged. The new top head passed the full all-core Release build, native suites and generated-stub check; source gates and the full Python suite pass after the upstream fix.

Built the stack and ran it on real scenes. The voxelizer itself is correct and quick:
Format: an independent decoder of the v1.1 format agrees with every file it wrote.
Density: a recheck against the raw splats matched 600 of 600 sampled voxels, on a 137k-Gaussian and a 5M-Gaussian scene.
Speed: 5M Gaussians take 3.7 s at 0.05, using about 2 GB of VRAM.
Failure handling: a cancelled or failed run keeps the previous pair every time.
Tests: all new tests pass.
The main problem is size. The three PRs add 11.5k lines: 7.2k code, 3.2k tests and 0.9k locales. Voxelize, Walk, preview and export should land at around 2–3k lines in total, so this needs to be rebuilt much smaller, not trimmed.
About 2,300 of the ~4,400 production lines here have no caller in this PR.
The Walk solver and capsule query (collision.cpp, ~320) are only used by #3791.
Sparse fill/carve (collision_sparse.cpp, ~265) and selectCluster (~150) are only used by the #3793 UI. The CLI can't reach either.
A second, dense fill/carve pipeline (collision.cpp:45–216 and 838–939, ~275) is only created by the legacy v1 decoder and the tests.
The CPU voxelizer voxelizeSparse (~186) has no production caller in any of the three PRs.
collision_serialization.hpp (252) includes ~95 lines decoding v1/v2 payloads that no released build ever wrote.
The Vulkan collision preview (~525 with shaders) is only drawn by #3793. It is still created eagerly in VulkanMeshPass::init, so a failure in that pipeline fails viewport init for everyone. It also enables VK_KHR_fragment_shading_rate for everyone.
Could you drop the dense path, the CPU voxelizer and the legacy codecs, and move the rest into the PR that uses it?
The voxelizer doesn't use our tensor library.
voxelizer.cpp copies four tensors to the host (220 MB for 5M splats). It then redoes sigmoid, exp and quaternion→axes in a TBB loop that SplatData already does on the GPU.
The outlier statistics are six nth_element passes on the CPU, and the bounds and BVH are CPU code too.
collision_voxelization.cu has its own Stream and a raw cudaMalloc Buffer, so it ignores the memory pool. On a 5M scene, VRAM sits at 1.75 GB after the model reset and peaks at 2.25 GB.
The 1.9 s host std::sort of the bricks (out of 7.9 s at 0.01) should run on the device.
There are seven copies of the stop check. CollisionProgress duplicates ExportProgressCallback/scale_export_progress, and Temporary duplicates ScopedAtomicOutputFile.
--auto assumes metres. recommendCollisionVoxelSize floors at 0.05 and rounds to 0.01 (collision.cpp:411–418), although the docs say the values are in scene units. A 137k scene scaled by 0.01 gets 0.05, a 16-cell grid with 48 voxels. --voxel-size 0.0005 on the same scene gives 3.9M voxels.
gridBounds is written as the whole power-of-two cube instead of the logical grid (collision_export.cpp:141–151, 230–242).
Viewers treat space outside gridBounds as solid. Here the padding becomes empty space inside the grid.
For example, a 24-unit scene gets 51-unit bounds, and a 301×109×79 grid is exported as 512³.
So a walker can leave the scene where it should hit a wall.
The overwrite prompt asks once per file (voxelizer.cpp:34–48). A single y covers the .json. The .bin prompt then hits end of input and the pair is skipped.
A read-only target fails with "basic_ios::clear: iostream error" (collision_export.cpp:52), with no path or errno. The old pair does survive.
voxelize can't be reached from Python or MCP, here or later in the stack. Every other export has both: lichtfeld.io.save_ply/sog/spz/usd and MCP scene.export_*. Could it get a lichtfeld.io function and an MCP tool too?
Smaller things:
occupiedCount() walks the whole tree twice, about 1 s each at 0.01, and validate() runs three times on the final volume.
--filter connected with the default seed kept 665 of 5M splats on one scene and said nothing. The seed-snap note only exists in selectCluster, which the CLI never reaches.
A cell size that is too fine burns time before failing. At 0.005 on a 5M scene it ran 26 s, then reported "tree budget exceeded". An estimate up front would fail fast.
There are two new -Wmissing-field-initializers warnings (async_task_manager.cpp:802), and unrelated churn in test_preferences_panel.py and vulkan_context.cpp.

Rebuilt it and reran everything from my last review.
Size: 63% smaller.
Correctness: every output still decodes cleanly against the v1.1 format, and the density recheck from the raw splats matches 600 of 600 sampled voxels on a 137k-Gaussian and a 5M-Gaussian scene. Voxel counts are within 0.01% of the old version.
Fixed from my last review:
--auto scales with the scene;
gridBounds is the logical grid;
one overwrite prompt per pair;
write errors name the file;
single tree walk;
tensor/pool use, GPU Morton/BVH and the device brick sort;
shared progress and atomic-file helpers.
Python works: generate_voxels/save_voxels give the same counts as the CLI, and cancel works.
It's now slower than the previous version, 19–35% on 5M-Gaussian scenes:
0.05: 3.7 → 4.4 s;
0.02: 5.7 → 7.2 s;
0.01: 13.9 → 18.8 s.
Two places cause it:
The four bounds reductions over a strided tensor column (collision_voxelization.cu:513–515) take 2.8 s on a 5M scene at any cell size; nsys shows 4 × 703 ms. Reducing them inside an existing kernel, or over contiguous data, should make them negligible.
The writer calls classify from the root for every output node (collision_export.cpp:17, 135–140). At 0.01 that costs 10.9 s, against ~3.7 s before.
Without these two, the new GPU path would be faster than the old one at every size.
GPU memory for the results is no longer bounded.
The output cap is gone. Chunks are copied into one buffer and merge-sorted into a second buffer of the same size, while the check at :671 only reserves max(compact, sort).
A 5M scene at 0.002 grew to +13.1 GB of VRAM and died after 77 s in collision.sort_bricks with a raw cudaMallocAsync failure report.
Those 397M records could never be exported anyway, since the format allows 16.7M nodes.
#3791 runs this same function in the GUI next to training. Could you check the record count against the export limit right after voxelization, before any sort? That also makes 0.005 fail 14 s earlier.
The Walk solver is still here with no caller: collision_walk.cpp/.hpp plus test_collision_walk.cpp, 414 lines. Only #3791 uses it, so it belongs there.
ctest -R lichtfeld.voxelize_cli fails in a normal Release build. test_voxelize_cli.cpp:14 uses __FILE__ as an input file. The compiler-cache prefix map makes that a relative path, and the test has no WORKING_DIRECTORY. A fixture file, or a path from PROJECT_ROOT_PATH, would fix it.
Smaller things:
CUDA fatbin: liblfs_core.so grows by 8 MB (+6.6%), 6.5 MB of it CUDA fatbin for a single architecture. Only 17 of the 610 GPU functions in collision_voxelization.cu.o are collision code; the rest are tensor/cub templates pulled in through collision.hpp → tensor.hpp. Moving the tensor-using host code (~330 lines) into a .cpp and keeping only the kernels in the .cu would drop most of that.
gridBounds block alignment: the span isn't a whole number of 4-voxel blocks (e.g. 473 cells), which the format requires (collision_export.cpp:122, 198).
--auto is now much finer: 0.008 on a 137k scene (783M voxels) and 0.009 on a 5M scene (2.25G voxels, 60% of the node limit). Bigger scenes will hit the limit only after a long run.
Progress labels: shows raw identifiers ("collision.prepare", …).
Device sync: captureCollisionSource calls cudaDeviceSynchronize (collision.cpp:32, 42), which will stall the GUI once #3791 calls it.
Python options: with cleanup=False it still applies max_gaussian_area; the CLI rejects that combination.
Size: the whole collision feature is now ~4.8k lines: 3.2k code, 1.25k tests, 250 locales. The target is still about 2–3k. Moving Walk up and trimming tests would bring #3789 to ~1.5k; the rest has to come from #3791/#3793.
