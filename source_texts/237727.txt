I have two questions. In the conclusion of your ToG '13 paper, you assert "Extension of the algorithm to incorporate additional knowledge of the scanned surface..." as an avenue for future work. To that end:
Is there a simple example of how one would evaluate the cell corners if primal, or cell centers if otherwise, to 3D points in the same world-space as the input point cloud? I.e., I'd like to visit each grid point as a world-space 3D position, and then call a new constraint function for evaluation at that point in space?
Based on the evaluation of an external constraint function, if one wanted to force a grid cell to be exterior, is there a fixed (negative) background grid value defined? Or should some other value that would be better suited to this purpose?
It seems most efficient to apply this step immediately prior to the iso-surface extraction, rather than by modifying the coefficients within the solver. Would you agree?
Thank you for any guidance you're able to provide, and also for publishing such a powerful library.
With kind regards.

In answer to the evaluation question, yes, it's pretty straightforward to evaluate at a corner/center.
The simplest way to do this is to use the MultiThreadedEvaluator class to sample, as in PoissonRecon. This allows you to evaluate at any position. (The evaluation is done in the unit cube coordinates, but you can use the xForm/iXform object to go back and forth between coordinate spaces.)
The evaluation can be done more efficiently using the _getCornerValues and _getCenterValues method, but that is trickier.
Though I am not sure what you mean by "call a new constraint function for evaluation".
You can do this for the derived voxel grid, but cannot do this for the octree representation because the value at a point is the combination of values from the different levels of the octree. If you are working on the voxel grid, it probably makes sense to set the value to 0 or 1 (depending on if you want the point to be inside or outside), since the derived function should approximate an indicator function.

I see.
One approach could be as follows:
If you know where the bulging happens (e.g. you’ve run PR and found a surface outside the visual hull) you can explicitly constraint the implicit function to have a value of 0 at those points.
This is a bit tricky to implement because the screened Poisson Reconstruction assumes that all points have the same target value of 0.5 (so that they lie on the iso-surface) but you can also add points with different constraints. To see how this is done, look at the code in PointInterpolant.cpp.
Lines 298-311 define a ConstraintDual class which has an overloaded “()” operator (line 304) supporting introducing a constraint at point “p” with value “data.template data<0>()”.
If you need help figuring out how to introduce those constraints, let me know and I’ll see if I can clarify.

There are two ways to go about doing this, depending on the type of data you have.
You can (relatively easily) introduce soft point constraints indicating that you want the implicit function to have prescribed values at certain prescribed locations. (For example, this is how the "PointInterpolant" implementation works.)
A harder situation is when you have some sort of envelope outside of which you know that the implicit function has to be equal to zero. This is something we have been working on recently and are hoping to submit for publication in the near future. The code is not quite ready for public consumption, but if you have a data-set I would be happy to try running it and sharing the results.

If you look at PoissonRecon.cpp Line 816, for example, you will see call to the FEMTree::finalizeForMultigrid method. The fourth argument it takes is a functor which takes a single argument (an octree leaf node, of type FEMTree::FEMTreeNode) and returns a boolean value indicating if the node is to be considered a Dirichlet constraint.
Note that the method FEMTree::centerAndWidth may be useful, as it can take an octree node and set references to the node's center and width.
