Adds clipping planes to cameras and to mesh instances. A plane cuts geometry open: the part behind it isn't rendered. A camera's planes clip everything it renders, for section views of a building or an assembly. A mesh instance's planes clip only that mesh, in every pass including shadows, for cutaways. The new example, graphics/clipping-planes, uses mesh instance planes to cut open a turbofan engine.
Try the example live on this branch's preview deployment.
API
CameraComponent#clippingPlanes: up to 8 Planes in world space that clip everything the camera renders. The parts behind any of them, on the side opposite to the normal, aren't rendered. They apply to all of the camera's passes, including picking. They don't clip shadows, which meshes cast whole, or screen space elements.
MeshInstance#clippingPlanes: up to 8 planes that clip one mesh instance, in every pass: forward, prepass, picking and shadows. A mesh instance is clipped by its own planes and by the camera's. Each set uses its own clipIntersection, and a part that either set clips isn't rendered.
RenderComponent#clippingPlanes gives the component's planes and its clipIntersection together to its mesh instances, including ones it creates or is given later. They replace the clipping of the mesh instances, even when the component has no planes, so planes assigned to a mesh instance directly last until the component next writes its clipping: when its clippingPlanes or clipIntersection are assigned, or it gets new mesh instances.
clipIntersection, on all three, clips only the parts behind all of the planes instead. Two planes cut a wedge, three a corner.
The planes are copied on assignment, as clearColor is. The getters return the copies, and a change to them applies when the array is assigned again. Cloning a component copies its planes as assigned, but not planes assigned directly to mesh instances. More than 8 planes trigger a debug assert, and the rest are ignored. The component properties are component data, so addComponent takes them and cloning keeps them.
```
// a section view: cut away everything the camera renders above a height of 3
cameraEntity.camera.clippingPlanes = [
    new Plane().setFromPointNormal(new Vec3(0, 3, 0), Vec3.DOWN)
];

// a cutaway: cut the top front quarter out of an entity and its descendants
const planes = [
    new Plane().setFromPointNormal(Vec3.ZERO, Vec3.DOWN),
    new Plane().setFromPointNormal(Vec3.ZERO, Vec3.FORWARD)
];
for (const render of entity.findComponents('render')) {
    render.clippingPlanes = planes;
    render.clipIntersection = true;
}
```
Changes
Two scopes. Camera planes need no setup per object, cover content loaded later, and can differ between cameras, as in a split view. Mesh instance planes leave the rest of the scene whole, as a cutaway on a stand needs, and clip shadows too.
Per mesh instance, not per material. The meshes of a glTF often share materials, so clipping a material would clip all of them.
Mesh instance planes clip every pass. They're mesh instance parameters (clipPlanes[0] and clipParams), so every draw of the mesh instance uses them. Clipped parts cast no shadows, write no depth and can't be picked.
Camera planes clip the camera's passes. They're view uniforms (camera_clipPlanes[0] and camera_clipParams), set for each pass and part of the view uniform buffer on WebGPU. Shadow maps render with the light's shadow camera, so they aren't clipped. Spot and omni shadow maps are shared by all cameras, so they couldn't follow one camera's planes anyway. The chunk skips the camera planes for SCREENSPACE shaders.
Shaders compile once. A mesh instance with planes gets a new shader define, SHADERDEF_CLIP. A camera with planes adds CLIP_PLANES to its camera shader params, so its shader variants are keyed per camera, as fog is. The new clipPlanesPS chunk, in GLSL and WGSL, discards clipped fragments at the start of the lit forward, other and shadow passes. Only the first planes compile new variants: for a camera, that's every shader it renders. Moving the planes, or changing their number, only updates the uniforms.
Materials. StandardMaterial and LitMaterial are clipped. A ShaderMaterial gets the CLIP_PLANES define for either kind of planes, and its shader opts in by including clipPlanesPS and calling applyClipPlanes with the world space position of the fragment.
Batching. Mesh instances with planes are excluded from batching, as skinned and morphed ones are. Clipping a batched render component rebuilds its batch group without it, and the batcher adds the excluded entity back to its layers, so it renders on its own. Camera planes don't affect batching. Planes given directly to a mesh instance that's already batched apply once its batch group is rebuilt with BatchManager#markGroupDirty, as other changes to batched mesh instances do.
Example
graphics/clipping-planes: a turbofan on a stand in a studio. It uses mesh instance planes, so the stand and the floor stay whole.
The cut. Two planes through the engine's axis, with clipIntersection, cut out a wedge. A third plane across the axis sets how far back the cut goes. The cut opens over 3 seconds when the example starts.
Section caps. A second render component draws each part's mesh again under the same planes, unlit red with front faces culled. Where the cut opens a part, its back faces show as a solid cut face. This needs closed meshes, and shows their inner surfaces rather than a face generated at the plane. The caps reuse each part's mesh and node, and the instancing buffer of each blade row, so no geometry is copied.
Controls for the cut (enabled, opening, rotation, length, caps and spin) and the post effects (MSAA, SMAA, TAA or no anti-aliasing, bloom, ambient occlusion and vignette).
The turbofan was made for this example. It's a 600 KB GLB with Draco compressed geometry, KTX2 textures (Basis ETC1S and UASTC) and instanced blade rows (EXT_mesh_gpu_instancing). Its materials use clearcoat, anisotropy, iridescence, sheen, specular, transmission, volume, IOR, dispersion, emissive strength and texture transforms. The studio environment atlas (77 KB) was made for it with EnvLighting.
Under CameraFrame the clear color isn't linearized (Fog + Tonemapping #7181), so the camera clears to the fog color passed through Color#linear(), and the floor fades into the backdrop.
Testing
test/scene/clipping-planes.test.mjs adds 51 tests:
Mesh instances copy their planes and set them as uniforms. They enable the define while they have planes, keep their shaders as the planes move, use at most 8, and apply them to their own forward and shadow draws.
Cameras copy their planes and set them as uniforms of their draws. They enable the defines while they have planes, keep their shader variants as the planes move, and use at most 8. Shadows aren't clipped by them. They take the planes from component data and keep them when cloned.
The forward, prepass, picking and shadow shaders of StandardMaterial and LitMaterial are clipped by mesh instance planes, and their camera passes by camera planes, together with the mesh instance's own. Screen space shaders skip the camera planes. ShaderMaterial gets the define from both.
Render components apply their planes to current and later mesh instances, take them from component data, keep them when cloned, and remove them.
Assignment: each owner keeps the values when given its own planes in another order, and keeps its copies, and their normals, independent whatever is put into the returned array. A changed clipIntersection changes only the mode. Clones take the planes as assigned. Render components take at most 8 planes, and give their planes and mode together to all of their mesh instances, also ones given later, from either setter, replacing the clipping of the mesh instances, also when the component has none.
A clipped entity renders on its own, outside of its batch, and stays hidden while its render component is disabled. The batch group is rebuilt when planes are pushed into, or cleared from, the returned array and assigned, and when the component removes planes of its mesh instances. A mesh instance given planes directly is clipped once its group is rebuilt. Batching follows the assigned planes, not changes to the returned ones.
Full suites pass: 4339 tests on Node, 4338 on Dawn (test:webgpu). Types and docs build cleanly.
In the browser, on WebGL2 and WebGPU:
Mesh instance planes: union and intersection clipping, shadows (light falls into the cut), picking through clipped parts, and the example, including portrait on a phone-sized viewport.
Camera planes: a plane through the example's scene cuts the engine, the stand and the floor. In user-interface/world-to-screen, a plane that clips all of the world geometry leaves the screen space labels, and the Picker hits a capsule without the plane and nothing with it.
Not in this PR
Gaussian splats and particle systems aren't clipped.
Hardware clip distances (GraphicsDevice#supportsClipDistances, WebGPU support for ClipDistances feature #7134) could replace the discard where they're supported.
Planes for a subtree of the scene, which would also apply to entities added to it later.
An option to keep the whole shadows of clipped mesh instances.
Anti-aliased cut edges. The cut is a hard discard, which alpha to coverage could soften.

Using both RenderComponent#clippingPlanes and MeshInstance#clippingPlanes on the same mesh instances can leave a mesh instance in a mixed state.
1. RenderComponent#clipIntersection writes only the mode, not the planes
The component's clippingPlanes setter and its meshInstances setter both replace the planes and the mode of each mesh instance. The component's clipIntersection setter only writes the mode. So a mesh instance with its own planes ends up with those planes and the component's mode:
```
// a wedge cut out of one part
meshInstance.clippingPlanes = [planeA, planeB];
meshInstance.clipIntersection = true;

// later, e.g. from a UI toggle
render.clipIntersection = false;
// the mesh instance keeps [planeA, planeB], now in union mode, and most of the part disappears
```
castShadows and the other properties the component passes down are single values, so this can't happen with them. Planes and mode have to stay in sync, so both component setters should write the planes and the mode together. Then the component always replaces the whole clipping state of its mesh instances.
2. Docs: how long planes set directly on a mesh instance last
The docs say to assign a mesh instance its own planes after it's given to the component. Those planes are replaced again the next time the component assigns its planes, or gets new mesh instances (asset load, type change). That includes when the component has none of its own. Could MeshInstance#clippingPlanes say they last only until the component writes again?
3. File name
src/scene/clip-planes.js mainly holds ClipPlaneSet, so per our naming convention it should be clip-plane-set.js.
4. Rebase
#9752 is merged, so a rebase on main should drop the iridescence commit and standard-iridescence.test.mjs from this PR.

5. Could more of the clipping state move into ClipPlaneSet?
Camera and MeshInstance both keep the same members around the set: _clipIntersection and the two uniform arrays (clipPlanesData / _clipPlanesData, clipParamsData / _clipParamsData). Their clipIntersection setters and _updateClipUniforms() are almost the same, and RenderComponent keeps its own _clipIntersection too. Only the reaction to a change differs per owner:
MeshInstance sets or deletes the parameters and toggles SHADERDEF_CLIP
Camera sets shaderParams.clipPlanes
RenderComponent passes the state on to its mesh instances
If the set owned intersection and the uniform data, with a method that writes the uniforms in place of the free writeClipPlanes, each owner would keep a single _clipPlaneSet and a small hook.
It also fixes point 1: the component could pass on the whole set, e.g. meshInstance._clipPlaneSet.copy(componentSet), so the planes and the mode always travel together.
MeshInstance goes from four clipping fields to one.
Camera's copy becomes set.copy(other).
Two details: RenderComponent never uploads uniforms, so the arrays should be allocated on the first uniform write rather than on assignment. And the component's clipIntersection getter can read this._clipPlaneSet?.intersection ?? false, so reading it doesn't create a set.
