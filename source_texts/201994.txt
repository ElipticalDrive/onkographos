PR Details
Adds a voxelization system to Xenko, and uses it to implement voxel cone tracing.
Description
I'm not sure how detailed to be here, I hope this is alright :).
On the user facing side it adds a Voxel Volume component, a Voxel light type, and various things to hook up in the graphics compositor.
The Voxel Volume Component stores all the settings for voxelizing the region around it (the extents of the region is based on its scale). It has a voxelization method which determines how the voxel fragments are generated (e.g by a render per axis, or a single render with an axis projection geometry shader); a storage method - what and how exactly will the fragments be stored (e.g standard 3D texture, clipmaps); and can have various 'output' attributes added to it such as the surface's color, or MSAA coverage. By the time the main frame begins rendering, these attributes have been voxelized and can be sampled.
To handle voxelization, a 'Forward & Voxel Renderer' renderer has been added (inheriting from ForwardRenderer). It doesn't do much other than having a VoxelRenderer on which it calls .Collect and .Draw at the right times. It also has a VoxelDebug which it calls on to draw any debug visualizations.
The VoxelRenderer is responsible for taking the attributes, voxelization method and storage method, and collecting a list of renders that need to be done (these are called voxelization passes in code). For instance, the Tri-axis Voxelization method needs a render per axis. Sometimes an attribute has special requirements (such as using a specific voxelization method) and will use a pass of its own rather than being grouped with other attributes. And sometimes an attribute can have a dependency on another attribute, causing that attribute to be stored as well. The resulting passes are then grouped by whether they can share a RenderStage.
When called to draw, it simply loops over each voxelization pass and asks its voxelization method to render it.
The voxelization happens in two stages.
In the first stage, the geometry is rendered and each attribute stores data in an intermediate uint Buffer (an attribute can request however many uints per voxel it requires). This allows for combining fragments that lie in the same voxel (by use of an InterlockedMax for example), or for later processing of non local attributes (such as the solidity attribute, which considers the space between a front face and back face to be solid).
Ideally there'd be a way for attributes that don't care about fragment collisions to skip the intermediate buffer, currently there isn't.
Then in the second stage, the intermediate buffer is processed in columns by a compute shader. For each voxel, the attributes are able to read their data, process it, and then write to a texture.
The resulting attribute textures are then mip-mapped.
After this, other code can fetch a sampling shader source from an attribute, which allows it to sample at a specific position, normal and radius.
So then the Voxel light type has a Voxel Volume component reference, which it uses to get the attribute to sample from.
Outside of sampling directly from an attribute, it is also possible to create a marcher. A marcher, as you might guess, marches through the volume while sampling the attribute at each step (e.g. cone marching or beam marching). Finally a specific arrangement of marchers can be created, called a march set (e.g 6 marchers as hemisphere around a normal). These are all just normal C# classes and interfaces, which allows the Voxel light type to have plenty of customization regarding how the marching is performed, for trading performance/quality.
Voxel visualization can also be performed with these marchers.
Hopefully that all makes some sort of sense. If you're interested in looking at this yourself, I'd recommend starting from VoxelRenderer and working from there, since it handles all the top level stuff. For any questions or clarifications please ask! :)
I've attempted to implement all this as a separate Xenko module. I'm pretty unfamiliar with most of the environment for this (having only used C# in Unity previously), so my apologies if that hasn't worked out right.
Motivation and Context
Voxel GI is a technique for approximating global illumination in real-time, which is handy for scenes with moving geometry and lights. While it is expensive compared to local lighting, it reproduces effects like light bouncing and ambient occlusion, and requires no special GPU support like DXR.
Additionally, I hope that the voxelization architecture allows for further uses of the voxel data in the future; e.g for volumetrics, direct shadows, and perhaps physics and sound occlusion.

Adding a simple bounding box was pretty easy. Later on it might be nice to have it show the individual voxel cascades, but for now it's still good seeing what area is being voxelized.
To add the gizmo I had to add Voxels as a dependency to the Editor, I hope that's alright.
Regarding the last commit, previously any modification to the graphics compositor would cause the voxelization to stop working until an editor restart.
Seems that RenderViews keep track of the last frame they were collected on and don't collect if it's >= to the current frame; changing anything in the compositor causes the frame counter to reset, meaning the RenderViews won't collect until the frame counter catches up again.
This isn't a problem normally since the RenderViews get reset along with the compositor class they are stored in, but here the RenderViews are stored outside so they don't get reset.
The > part of the >= should normally never trigger anyway, so I figure this is a safe change. Hope that makes sense :)
