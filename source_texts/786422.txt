Handoff implementation plan (agreed with @milysun, 2026-08-05/06)
Scoped against feature/v0.7-fixes. Companion context: #35's filter matrix (this feature samples from filtered rows); stratified sampling is explicitly split out to its own optional/low-priority issue (see cross-reference comment).
Current state
The AI preview annotates the corpus in row order, page by page (AI_PREVIEW_PAGE_SIZE; each page navigation posts a new result query). No randomisation, no row-count control on Run All. Corpora are typically sorted (source/date/speaker), so "the first N rows" is a poor sample for judging a prompt, and Run All is all-or-nothing on cost.
Agreed design
1. The sampling source is the currently filtered rows.
Whatever #35's filter state yields is the population: no filter → the whole block; "rows coded in column A" → that subset; etc. This is the versatility principle: "100 random rows coder A has done", or "the same rows, stronger model / new prompt / new codebook" all fall out of one mechanism.
2. Draw-and-pin with a seed.
Drawing a sample selects N rows from the current population and pins them (persist the seed and the drawn row identities in the analysis settings). The seed guarantees reproducibility — same population + same seed → same sample — and is displayed/editable so a second coder can reproduce the draw.
Later filter changes intersect the pinned sample (they do not redraw): sample 200 of 5000, then filter to rows coded in column A → maybe 55 of the 200 remain in scope; preview and Run All operate on those 55.
The effective count is always visible — a summary line such as: Sample: 200 rows (seed 42) · 55 match current filters · population 2,000. The user must never be surprised by how many rows an AI run will process.
Resample (explicit button) redraws N from the current population (post-filter). No overlap guarantee with the previous draw — it's a resample. New draw, new pin.
3. Sample-size input — reuse the preprocessing Sample Rows convention (SliceSubTab.tsx random-sample mode): one "Fraction / Count" field — float in (0,1) = proportion of the current population, integer ≥ 1 = absolute count — plus the seed field (with the same optional no-seed behaviour). Same semantics, same validation, consistent results across Wordflow. Reuse/extract the existing input + hint logic rather than reimplementing.
4. Limits are implicit — no extra parameters.
Lower limit: not user-specified. If the effective sample is smaller than one page, just show/process what exists (8 filtered rows → all 8). The current page size is the natural floor for a useful preview; no UI control for it.
Upper limit: the population size. Requesting more than the population returns the whole population (with the summary line making that visible).
5. Run All gains the same cost control.
Run All processes the pinned sample ∩ current filters when sampling is active (the summary count is the run size), or everything as today when no sample is drawn.
Unlike preview, Run All writes annotations in place for the processed rows; unprocessed rows stay empty — deliberately compatible with processing_mode: fill_missing so a later full run completes the rest.
Purpose: run a bounded, randomised, persisted batch cheaply, pipe the output into other analysis tools for verification (not just eyeballing the preview), then commit to full scale.
Implementation notes
Persist per annotation tab/analysis settings: {seed, sample_size_input, drawn_row_ids (or source row indices), population_descriptor}. The drawn-row pin makes intersection display cheap and "same rows" literal; the seed makes the draw auditable/reproducible.
Sampling executes server-side over the filtered query (Annotator: Show metadata / compare-to column logic #35's SQL builder provides the population); reuse the same RNG semantics as the preprocessing random-sample op so identical seed+population give identical rows across the two tools.
Preview pagination pages through the effective sample (55 rows → pages of the sample, not of the corpus).
Row identity: use the stable source-row identifier already used by the annotation table (sourceRowIndexColumn machinery) — verify it survives filter changes and workspace reload; if not, that's the first thing to fix.
UI placement: a "Sampling" group in the AI settings area (fraction/count field, seed field, Draw/Resample button, summary line). The summary line renders wherever Run All's confirmation lives, too.
Guard: Resample while a run/preview is in flight should be blocked or clearly abort-and-redraw — no half-sample runs.
Acceptance criteria
With no filters: drawing 200 from 5,000 pins 200 rows; preview pages show only those; Run All processes exactly 200 and writes in place; rerunning preview with a different model/prompt hits the same 200.
Applying a value filter (per Annotator: Show metadata / compare-to column logic #35) shrinks the effective set (e.g. 55); the summary shows 55 match current filters; Run All processes exactly 55.
Resample under that filter draws 200 fresh rows from the 2,000-row population; summary updates; no expectation of overlap.
Same population + same seed → identical sample (cross-session, cross-user); seed is visible and settable.
Fraction input: 0.4 on a 2,000-row population → 800 rows; 100 → 100 rows; population smaller than request → whole population, summarised honestly; validation matches the preprocessing tool.
Run All without an active sample behaves exactly as today; fill_missing later completes unsampled rows.
No-filter/no-sample preview behaviour unchanged (row-order pages).
Verification
Unit tests: draw determinism (seed), intersection logic, fraction/count parsing parity with the preprocessing tool, population math in the summary.
Component tests: sampling controls, summary line, Resample redraw, Run All confirmation showing the effective count.
Backend tests for the sampled-population query + in-place partial write with fill_missing compatibility.
pnpm -C frontend check; backend package checks per backend/AGENTS.md.
Out of scope
Stratified sampling — split to its own optional/low-priority feature issue (cross-referenced in a follow-up comment); the Sampling UI group leaves a natural slot for a future random | stratified by [column] mode switch, but nothing is built for it now.
Changing AI_PREVIEW_PAGE_SIZE or the preview's non-persistence.
Annotator: Show metadata / compare-to column logic #35's filter mechanics (companion plan).
Medium change — consider specs/active/31-annotation-sampling/ if the implementer wants a working spec folder; this issue comment is the agreed scope of record.
