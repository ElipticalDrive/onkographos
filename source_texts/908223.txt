I think it would be good to just have a VDB object accessible from the RenderMan tab. Within Object Attributes you would select the sequence and then you would type in the grid you want to render into PrimVar. That's kind of how we're used to doing it.
I suppose you could make an OpenVDB node that would open a VDB sequence and allow you to select the grid from a list and will set the Primitive Variable from that selection. I guess at that point you'd apply the volume shader to arbitrary geometry to serve as bounds? I'd prefer this myself, however...
I am not 100% sure how VDB works behind the scenes, though one thing I'd be concerned with here is having to load the VDB file multiple times for each grid rather than just noodling the data and loading once.
If the PrimVar node had an input, you could load in the VDB sequence in a similar way as an image texture, and if you wanted a drop-down menu on the PrimVar you could have it detect the presence of an input and change the string input to a selection based on the input. PrimVar though should still be allowed to function as it is currently when a node isn't attached.
This would be pretty slick, and may have other uses as well, though i am not sure if Primitive Variables work this way or not and in Maya and Houdini I don't think PrimVar has any inputs, so even if it were possible, this would represent a paradigm change in how the node operates.
If we're OK with that, then I think this is a really flexible way to handle multiple VDBs. Because the density value is float it would seem we could combine VDBs together using arithmetic into the same shader. This could be extremely useful.

From the 2.77 release notes:
OpenVDB caching
Point cache UI for OpenVDB
Smoke simulations can now be cached using OpenVDB as a back-end (rBe9452f909cdb). The simulation fields can be found in the .vdb files under the following names:
"color"
"density"
"heat"
"heat old" (the temperate at the previous fame)
"flame"
"fuel"
"react" (reaction coordinates, used for fire)
"velocity"
"shadow" (the shadows of the volume computed for viewport rendering)
"texture coordinates" (used for turbulence)
Notes:
The presence of a given field depends on the simulation settings, e.g. "texture coordinates" is only written if high resolution is enabled
If high resolution is enabled, the corresponding low resolution fields are suffixed with " low".
So looks like "temperature" is "heat" here

Houdini Pyro does have a standard naming convention and this is what some of what you're seeing in that tutorial. I could look them up if you want, but Houdini lets you name anything whatever and also there are other standard fields, in both Houdini and Maya, such as "coordinates" in Maya, or "rest" and "vorticity" in Houdini. Specifically in Houdini, I can easily calculate any arbitrary data and stick it into a VDB grid called "pressure", "discharge", "dust", "debris" "bonkertheclown" whatever. So it's important that we have arbitrary grid imports so that we're not limited to any one workflow.
And in fact Arnold can import these grids, as I had just tested with a grid called "cloudball" in Maya 2017.
IIRC the Pxrprimvar node is typically used to extract grid data to be piped into the PxrVolumeShader. If you do have a UI to define the grid for the VDB container object this would be for visualization only, or to selectively choose which grids to import while excluding those not needed. But the actual grid to render would be defined using the PxrPrimvar, that way you don't have to reload the VDB file in order to get to the grids within, At least that is how I understand it. Bear in mind that very high resolution VDB files can be huge, on the order of gigabytes/frame.
Unfortunately, I still don't have RfM up and running to take a closer look, but I did notice that RenderMan 21 has shown up in Houdini, so I will refresh how to get RfH up and running and report back. Like everything with H It's kind of a process.
