Describe the bug
Instruction.Marshal in asm/instruction.go writes every atomic instruction with an immediate of 0 (BPF_ADD), whatever atomic op the opcode carries. It computes cons := int32(ins.Constant) at the start, and only later, in the atomic branch, sets ins.Constant = int64(atomic >> 8); cons is not updated after that, so the op is lost.
As a result CmpXchg, Xchg and the Fetch* variants all run in the kernel as a plain atomic add. A compare-and-swap loop built with asm.CmpXchg.Mem adds the new value to memory instead of swapping it, and the verifier accepts it, so it fails silently.
Expected: the immediate holds the atomic op, e.g. 0xf1 (BPF_CMPXCHG) for CmpXchg.
Workaround: set ins.Constant = 0xf1 on the instruction before marshaling. Fix: compute cons after the atomic branch, or assign it there.
How to reproduce
```
package main

import (
	"bytes"
	"encoding/binary"
	"fmt"

	"github.com/cilium/ebpf/asm"
)

func main() {
	var b bytes.Buffer
	if _, err := asm.CmpXchg.Mem(asm.R6, asm.R2, asm.DWord, 0).Marshal(&b, binary.LittleEndian); err != nil {
		panic(err)
	}
	fmt.Printf("% x\n", b.Bytes())
}
```
Run go run .
Output: db 26 00 00 00 00 00 00
Expected: db 26 00 00 f1 00 00 00
The same happens with asm.Xchg (expected imm 0xe1) and asm.FetchAdd (expected 0x01). A program using the instruction in a CAS loop on a map value shows the add behaviour at run time (seen on Linux 6.8).
