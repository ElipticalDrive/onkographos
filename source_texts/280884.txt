Summary
This started as a look at replacing the BVH with tinybvh-rs. Its BVH8_CPU layout traced 1.8–2.4× faster than crust-rt on a triangle soup, but the crate isn't usable here:
it's a beta cxx binding that segfaults when that BVH is dropped;
its build script hardcodes -march=native;
it supports triangles and closest-hit only: no occlusion query, t_min, masks, instancing, curves or motion blur;
it would put C++ behind unsafe on the hot path.
Its plain and HQ (SBVH) binary BVHs were no faster than crust-rt. The speed comes from 8-wide nodes, so this PR takes that idea instead of the library.
docs/simd.md already concluded that the width should be chosen per tree by size, with both widths compiled in. This PR does that on stable, in safe code:
WideNode<W>, collapse::<W> and both traversals are generic over a Width trait (W4, W8). A tree stores enum Tree { Four, Eight }, matched once per query. The binary SBVH, the leaves and the Tri4 packets are the same at either width; only the collapse differs.
On stable, an 8-wide node is two Vec4 halves: 256 bytes, 32-byte aligned, no new dependency, still forbid(unsafe_code). Outside the cache the gain comes from fetching fewer nodes, not from wider arithmetic. The nightly bvh8 feature now only swaps the halves for one f32x8.
crust_rt::NodeWidth (Four | Eight | Auto) is a new field on CommitOptions. Auto, the default, goes 8-wide from 2^18 primitives. Each instanced scene chooses for itself, so an instance field gets an 8-wide top level over 4-wide prototypes.
CRUST_BVH_WIDTH=four|eight|auto forces the width in the renderer; four is the old behaviour. ray_throughput gains --width.
Capability
intersection-kernel (design record: new section "BVH8 per tree" with its trap, plus a spec requirement) and cli (the CRUST_BVH_WIDTH requirement). The change record is archived at openspec/changes/archive/2026-10-20-bvh8-per-tree/. docs/simd.md has the full measurements.
Image impact
Bit-identical under the default (auto). Every sample scene is below 2^18 primitives per tree, so it stays 4-wide exactly as before. I checked with crust diff against a main build at -s 16 on 10 scenes: cornellbox, instancing, nested_instancing, curves, hair, subdivision, materialx_teapot, motionblur, implicit_shapes, displacement. All identical. I did not run the full check_images.sh golden set.
Forcing eight is not fully bit-identical. Seven of those scenes match, but subdivision, implicit_shapes and hair change a handful of pixels (trimmed relmse ≤ 5e-7). A debug build that traced every query at both widths showed every mismatch was an exact tie: two different primitives hit at bitwise-equal t, at coplanar contact faces where meshes sit on the ground quad. The first leaf visited wins a tie, and the widths visit in different orders. Either answer is the same point of degenerate geometry, the same thing a rebuilt BVH does to ties. This is documented in the spec, the design record and CLAUDE.md, not fixed: an order-independent tie-break would need an id compare in every primitive test and would move the 4-wide images too. On 2.2M random primary and secondary rays, and in the new bitwise unit test, the two widths agree to the bit.

Reading
Moana gets slower under auto, consistently. Both pairs gave about +5% on min, and the profiled closest-hit cost rose 9%. It also costs about 0.5 GiB of BVH and 0.75 GiB of peak RSS.
ALab's gain is small, −2 to −4% on Render time with Trace −9%, and 3 reps cannot resolve it from noise. The first Moana four arm also spread widely (min 29.8 s against mean 31.2 s).
A reference count above 2^18 does not predict which width wins. Both scenes cross the threshold, and they go opposite ways. This repeats the quantised-BVH8 production A/B (b17aeb4): the random-soup sweep in ray_throughput was measured single-threaded with a 33 MiB L3, and it did not predict production trees rendered on all threads with a 16 MiB L3.
There is no log of which trees went 8-wide, so these runs cannot say whether Moana's loss comes from the 21.7 M-reference top level or from the large prototypes. A -l debug per-tree width census, like node_format_census on the quantised branch, would settle that.
Still running
6-rep four vs auto and four vs eight on both scenes. eight forces every tree to 8 wide. If it loses on Moana by more than auto, the smaller trees can't take 8 wide either. If it loses by about the same, the loss is in the large trees auto already sends to 8 wide.
crust diff of four against auto at -s 16 --indirect-clamp 0 on both scenes, to check that the only image differences are exact ties.
I'll add those results here when they're done. Tentative suggestion: if Moana's ~5% loss holds at 6 reps, ship the generic Width machinery with Auto resolving to four-wide, keep CRUST_BVH_WIDTH=eight as an opt-in, and add the per-tree census before the threshold is tuned on production scenes.
