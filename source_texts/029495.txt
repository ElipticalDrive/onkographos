Merge order: tier 4. Rendering: to be replaced by a rebuilt renderer PR. See the roadmap, #232.
Summary
Note
Third of three stacked pull requests, on top of #215 (it targets claude/renderer-examples), which is on top of #214.
Warning
The performance receipt is yellow (host and CUDA), accepted by the maintainer ("Algorithm changed"): the renderer's checksums change because tapes are now ray traced exactly instead of sphere traced to a tolerance. Every flagged case is 28–83% faster, and no pool grows. See Performance.
Background
#214 added ray queries and a renderer that sphere traced everything except TriMeshSDF, plus a few renderer-specific shortcuts to keep ray-traced meshes fast (the section plane's own ray form, ray-cast shadows and occlusion only for ray-traced shapes). The plan from #211 is to ray trace wherever a primitive can answer a ray, combine CSG through a ray version of the tape, and sphere trace only what has no ray form. This does that, removes the shortcuts, and starts on the tape's device performance (#210).
Solution
Closed-form ray forms for the plane, sphere, box, finite and infinite cylinders and capsule (with outward normals, and a one-step span() for each); PlaneSDF, InfiniteCylinderSDF and CapsuleSDF gain const getters. The RayForm contract now takes the RayOptions, so a ray form may sphere trace part of its shape.
Spans (RaySpan, RaySpans, union, intersection, complement) describe where a ray is inside an object; spansOf() finds them for any shape.
The tape followed along a ray: Tape::firstHit() reads the tape's own clauses on stacks of spans and rays. Primitives with a ray form give their spans, point maps move the ray (its parameter kept), negation is a complement, min and max are a union and an intersection, and a BVH union traverses its own BVH with ray–box keys over its operand sub-programs. The compiler marks each subtree a ray cannot follow (smooth blends, offsets, Blur, Mollify, elongation, repetition, primitives without a ray form), under a node it can, with one Op::RayMark clause (length, box, quality) that the value evaluator skips and the ray query sphere traces as a clause range. Nothing else is stored. An expression with nothing a ray can follow, or needing more span sets than the ray evaluator holds, is sphere traced as before. Leaf ids are those primitiveAt() gives. deepCopy() now keeps getNumPrimitives() (a bug from [DO NOT MERGE] Renderer: ray queries on any shape, a renderer and an SDL2 viewer (1/3) #214).
The renderer is generic: shadows and occlusion are rays (firstHit()) for every shape, and the section plane is the intersection of any shape with a half-space along the ray; the if constexpr shortcuts from [DO NOT MERGE] Renderer: ray queries on any shape, a renderer and an SDL2 viewer (1/3) #214 are gone.
Tape: device evaluator spills its value/point stacks to local memory (~20x slower than a hand-written SDF on GPU) #210, measured, not fixed: Performance/Tape times Tape::signedDistance() of the classic CSG solid against the same solid written by hand (and a smooth tape and a 64-sphere BVH union), on the host and as host/device pairs. On an RTX A4000 in float the tape is ~35× slower than the hand-written solid (1.74 ns vs 0.05 ns a point), on one host core ~3×. Small register-resident stacks per sub-program (unrolled selects), inlined analytic primitives, and out-of-line BVH union/Blur/Mollify were tried and measured: the kernel stays at 255 registers and its time within noise (and the smooth and union tapes got slower), so they are not included. Letting nvcc inline every device function (no EBGEOMETRY_DEVICE_NOINLINE) makes the kernel twice as slow (3.69 ns), and capping it at 64 registers changes nothing, so it is neither an inlining nor a register (occupancy) problem: the cost is the interpretation itself, a 16-byte clause read and a data-dependent branch per clause and an out-of-line call per sub-program. Nsight Compute could not read the GPU's counters without administrator rights, so there is no profile. Closing the gap needs a different evaluator design, which Tape: device evaluator spills its value/point stacks to local memory (~20x slower than a hand-written SDF on GPU) #210 leaves open. For rendering, the ray program avoids most of it: the CSG solid's camera rays are 80% faster on the device.
Probes: Render/union64/firstHit and Render/mixed/firstHit cover the ray program's BVH union and its sphere-traced nodes.
Docs: closed-form ray forms, spans and the ray program (Rendering.rst, ImplemRender.rst), the probes (PerformanceTesting.rst), and the ray program in CLAUDE.md's notes on the tape.
Side-effects
A tape gains one clause per subtree a ray cannot follow under a node it can (none for the classic CSG solid); pool bytes are unchanged in every probe.
Renders and firstHit() on tapes change slightly: crossings are exact rather than within the march's tolerance (sharp edges no longer show stray "seen from inside" pixels).
Two device discrepancies were found that also fail on dev (built from dev with CUDA on an RTX A4000), and are not caused by this PR: Tape: Blur evaluates differently on a CUDA device than on the host (TestTape [gpu]) #217 (TestTape's blur case, device 5.39682 vs host 5.35446) and TriangleAoSoA: signed distance has the opposite sign on a CUDA device for one query (TestTriangleSoA [gpu]) #218 (TestTriangleSoA, query 77: device 1.84245, host −1.84245).
Performance/Receipt.cmake now receives the report in a file (REPORT_FILE), so a ; in it survives.
No HIP toolchain was available locally; CI's GPU-HIP job is the first HIP compile of the ray evaluator.
Alternative solutions
Sphere tracing inside the boxes of every node with no ray form only, without a ray program for the rest (the "hybrid" of [DO NOT MERGE] Renderer prototype: sphere tracing, ray tracing and a hybrid for visualizing shapes (#93) #211): slower than following exact spans for sharp CSG and meshes, which make up most of what users render.
Keeping the renderer's shortcuts: faster to write, but it special-cased ray-traced shapes in the renderer instead of the shapes answering rays.
Performance
The host and CUDA comparisons against origin/claude/renderer-examples are both yellow for changed checksums only: tapes are now ray traced exactly where they were sphere traced to a tolerance, so the crossings, and the frame's pixels, move by up to the tolerance. Every flagged case is faster (host 30–41%, device 82–83%), and no pool grows. Accepted by the maintainer: "Algorithm changed". An earlier minor flag on PointCloudHashGrid/sphere/neighbor-morton/float/host did not reproduce over 10 rounds.

firstHit() on a tape used to compile a second clause list beside the
scalar one, with its own copies of the primitives and BVH unions and
scalar sub-programs for the nodes it sphere traced, doubling a tape's pool.

parallelForKernel took its functor by value, and a query that calls a
function that is not inlined (a Tape's evaluator) needs the functor's
address, so every thread first copied the whole functor from the kernel's
parameter space to its local memory: 376 bytes for a Tape<float>, which
made a tape about 30 times slower on a device than the same solid written
by hand (#221). The kernel's parameter is now EBGEOMETRY_GRID_CONSTANT,
__grid_constant__ under CUDA 11.7 and later (compute capability 7.0 and
later), which the threads read in place; it is empty for HIP and older CUDA.

Measured on an RTX A4000 with the same one-line change on #216's tree:
the classic CSG tape 1.56 -> 0.36 ns a point (float), 1.91 -> 1.01 ns
(double), with every host/device answer the same.

Also: Performance/Tape (from #216, identical), whose sphere and chain16
cases separate a cost per device thread from one per clause; the
"Large queries" section in RunningOnGPU.rst.
