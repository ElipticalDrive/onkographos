Talking with @jcohenadad we realized that when I uploaded glioma-brain-brats-2024 I used the nifty files as they were provided by the the Brats organizer: uncompressed (they are nii, not nii.gz).
We concluded that this is a bad behavior as non-compressed segmentation volumes are significantly larger than compressed segmentation volumes (I'm currently working on fixing this on glioma-brain-brats-2024).
@jcohenadad proposed we forbid the upload of non-compressed nifty files, to make sure nobody else make the same mistake again. Is that possible, what do you think @mguaypaq?

This is a good idea, but it requires some changes at the level of the server. And since we are currently migrating the server from NeuroGitea to Forgejo-Aneksajo (see https://github.com/neuropoly/computers/issues/1202), I would rather wait until the migration is done before looking at how to do this.
Some possibilities:
I'm not sure if it does what we want, but Forgejo configuration has a ALLOWED_TYPES setting for repository.upload
Possibly a failing filter for *.nii set in .gitattributes? No, according to the gitattributes manual a failing filter is treated as a no-op, instead of an error.
Maybe a git pre-receive-hook on the server? No, git hooks are disabled by default, for good security reasons.
Maybe a branch protection rule which targets all branches but only **.nii? Seems annoying to deploy, and limited in what it can check.
Ideally we eventually set up something like GitHub Actions on Forgejo-Aneksajo, and then we can run arbitrary checks on pull requests and/or pushed commits. This wouldn't prevent uploads, but would alert us to common problems like this.
