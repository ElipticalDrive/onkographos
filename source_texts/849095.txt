It would be nice of unstructured meshes could support a single geometry. We use tetrahedral meshes (only tetrahedral), thus we store our data as such:Vertices: {x,y,z,x,y,z,...}Tetrahedrons/connections: {v1,v2,v3,v4,v1,v2,v3,v4,...} VisIt wants VISIT_CELL_TET for every set of four tetrahedrons causing either an overhead of N/4 elements. There are two options to get around this: What we currently do: copy the connections and att VISIT_CELL_TET where needed (introduces a memory overhead) Modify our internal representation of the connections to fit VisIt (would make our simulation code platform-dependent and introduces a slight memory overhead) My guess is that meshes of mixed geometries are far more rare than meshes of only one geometry. The ideal solution would allow for both mixed geometries and passing a list (such as our list of connections described above) and a single VISIT_CELL_TET passed in a separate variable, which would solve the issues with both options above. As Brad Whitlock suggests, doing this internally might be a solution, but it would also mask the overhead to the end user. Another option, if possible, would be to implement this in VisIt as well, to truly allow for the connectivity to be passed without memory overhead. Briefly discussed here: http://visitusers.org/forum/YaBB.pl?num=1405092511

Josef N wrote:It would be nice of unstructured meshes could support a single geometry.We use tetrahedral meshes (only tetrahedral), thus we store our data as such: Vertices: {x,y,z,x,y,z,...} Tetrahedrons/connections: {v1,v2,v3,v4,v1,v2,v3,v4,}This is how lib sim's internal data model for mesh topology is designed to operate. It is based upon VTK's data model and must conform to VTK's format. It can support a wide variety of mesh types without introducing frequent downstream changes. In addition, any time an opeator is applied to a mesh object, it is going to result in proliferation of nonhomogenous element types. Consider a clip operator applied to a mesh of all HEX elements. So, even if the original form of the topology was optimized for a mesh homogeneous in element type, that optimization is lost almost immediately as the mesh flows through any pipeline where topology can be changed (clip, onionpeel, threshold, iso-volume, etc.).VisIt wants VISIT_CELL_TET for every set of four tetrahedrons causing either an overhead of N/4 elements.There are two options to get around this: - What we currently do: copy the connections and att VISIT_CELL_TET where needed (introduces a memory overhead) Modify our internal representation of the connections to fit VisIt (would make our simulation code platformdependent and introduces a slight memory overhead)There is no expectation that libsim's interface be 1:1 for how any particular application chooses to store its mesh and field data internally. That is an ideal goal, of course, but it is just not practical in all cases. Field data (e.g. variables on the mesh) are much more easily handled via zerocopy, 1:1 with libsim's interface. However, mesh topology, for reasons described earlier, is not. Even if there was a way to pass your applications mesh topology data natively to libsim, without having to alter it, at some point downstream of your application, the topological representation will need to get altered to match what VTK is expecting. Maybe that is all you are really interested in, avoiding having to reformat the topology information your code operates on natively when handing it off to libsim?My guess is that meshes of mixed geometries are far more rare than meshes of only one geometry.It turns out this case is very common, both as meshes produced by computational codes as well as meshes that get processed in VisIt's pipelines.The ideal solution would allow for both mixed geometries and passing a list (such as our list of connections described above) and a single VISIT_CELL_TET passed in a separate variable, which would solve the issues with both options above.True, but again, that means a lot of downstream code is going to have to be modified to be cognizant of this particular way of storing mesh topology information. The data model we use is based largely on VTK's data model. In fact, it is because we employ VTK under the covers that we require mesh topology to be stored this way. This is how VTK does it.As Brad Whitlock suggests, doing this internally might be a solution, but it would also mask the overhead to the end user. Another option, if possible, would be to implement this in VisIt as well, to truly allow for the connectivity to be passed without memory overhead.Briefly discussed here: http://visitusers.org/forum/YaBB.pl?num=1405092511 Thank you Mark, for an excellent explanation! Then I'm just fine with how things are. Oh, and what I wanted was to minimize memory overhead. Since it can't be avoided I'd prefer the current solution because it's more transparent to the developer compared to VisIt hiding it internally for convenience (which is the alternative, if I got you and Brad right).
