Six comments, all legitimate. Comment 1 was the actual bug blocking
the CSG mesh path -- my session-1 diagnosis (JobSystem starvation)
was wrong. The real culprit was much simpler: SupportsHardwareRT()
returning false caused Engine::EnsureMeshUpdated() to early-return
before ever submitting the bake. After fixing that the bake fires
on first dispatch, RebuildMeshResources calls my CreateBLAS /
CreateTLAS, the kernel sees the bound TLAS, and the drilled CSG
cube renders correctly alongside the analytic spheres.

1. SupportsHardwareRT(): now returns true. Embree gives us a
   software-emulated BVH + triangle intersection pipeline that's
   semantically equivalent to hardware RT for the engine's
   purposes -- the flag literally gates whether the engine builds
   ASes and binds them, which we want. Added a comment explaining
   why a 'CPU + Embree' backend reports true for this.

2. CMake: re-enable EMBREE_GEOMETRY_INSTANCE (was OFF in session 1
   but the TLAS path immediately tries to create
   RTC_GEOMETRY_TYPE_INSTANCE geometries -- they failed silently
   without instance support). Embree rebuilds the relevant
   intersector / builder shards but the binary size delta is tiny
   for the triangle-only configuration we already have.

3. SoftwareTracer.cpp: read exposure_state[0] (slot 6) and
   multiply HDR radiance by it before ACES tonemap, matching the
   GPU paths. Manual r_exposure changes now affect the software
   render. Auto-exposure still doesn't apply on Software because
   that GPU dispatch is a no-op here, but the engine seeds
   exposure_state from r_exposure on the manual path, so manual
   mode works correctly.

4. SoftwareDevice.cpp: PresentOutput's per-frame
   std::vector<uint32_t> heap churn replaced with a class-member
   scratch buffer that resizes only on swapchain growth.

5. SoftwareTracer.cpp: add <cmath> and <algorithm> includes
   explicitly. The TU was relying on transitive includes through
   GLM / Embree headers, which is fragile across compiler /
   stdlib versions.

6. SoftwareDevice.cpp: ReadbackTexture now returns false when
   dst_size < src_size instead of silently truncating. Lets the
   screenshot / capture path fail loudly on a non-RGBA32F target
   rather than process partial bytes as full data.

Side effect of #1: my session-1 PR description's 'CSG mesh bake
doesn't reliably complete' note was wrong; it's actually reliable
once the engine knows it should bake. The thread-count cap
(hw_concurrency - 4) is still useful but not strictly necessary.

Atmospheric refraction lifts the sun's lower limb more than its upper
limb, vertically squashing the apparent disc into an oval as it nears
the horizon. New cvar r_sun_horizon_flatten (default 1) enables the
physical effect; 0 keeps a perfect circle. Effect fades to <1% above
~5 deg elevation, ~19% squish at the horizon (4:5 oval).

CPU side computes the differential via Saemundsson 1986 across the
real solar disc (~0.265 deg radius), independent of r_sun_size so
cinematic sun multipliers don't distort the physical ratio. Result
is pushed via sun_extra.z (was reserved). State transitions on the
cvar and on entering/leaving the active-refraction band emit
LOG_INFO lines per the engine's log-on-state-transition convention.

Shader (sunDisc in PathTrace.slang) builds a sun-local horizon frame
and tests elliptical disc-membership when sun_extra.z < 0.999, with
a circular fast path otherwise. The squashed oval is fully contained
inside the original circular cone (vertical radius shrinks; horizontal
unchanged), so the existing cos(r_deg) gate is a valid superset
prefilter for both branches. Halo stays circular -- it's at-observer
scattering rather than source-side refraction, and the gradual
falloff would hide any anisotropy regardless.

Verified with denoiser-off vertical-luminance profile through the disc
column at elev=0.3 deg: disc top edge moves down 16 px in flat=1 vs
flat=0, matching the predicted 16 px (= 18.6% * 173 px disc radius
half-distributed top/bottom). CPU log confirms vertical-scale=0.814
at the same elevation.

Software backend's sun is a 2-line procedural-sky stub (PR #24
session-1) that doesn't model atmospheric refraction; out of scope
for this change.

Branched from v0.3.14 because Mac is investigating a separate build
issue on origin/main; rebase before merge.

Adds a Schneider/Decima-style raymarched cloud pre-pass as an alternative
to the existing inline path-traced cloud march. The two modes coexist;
the user picks via r_clouds_mode cvar (default "pathtraced", new value
"procedural_raymarched").

Dual-mode design:
  pathtraced (default): the existing PathTrace.slang inline cloud march
    runs unchanged -- bit-for-bit preserved vs pre-#24 main. All Metal
    goldens regenerate without change (verified clean across 24 cells
    including bsc_night_clouds + clouds-bearing sky scenes).
  procedural_raymarched: dedicated CloudsRaymarch compute pre-pass
    raymarches the cloud layer (32 jittered samples) with 6-step
    Beer-Lambert light-marching toward sun + moon (exponential growth,
    Schneider production tuning). Powder term + HG phase. PathTrace.slang
    gates its inline cloud-density sampling OFF in this mode AND skips
    the cloud_trans_tex write (the pre-pass owns it). A small
    CloudsComposite kernel alpha-blends the pre-pass output into the
    post-denoise HDR using premultiplied alpha.

Push struct layout:
  PtPush grew by 16 bytes for the clouds_runtime uvec4. The previous
  Metal push_buf_ was sized at exactly 1024 B; bumped to 2048 B to
  prevent the trailing 16 B from getting silently truncated by setBytes
  (manifested as cloud-bearing scenes going pitch-black -- the shader
  was reading garbage clouds_runtime and corrupting downstream uniform
  reads through MSL layout reorder). Documented inline.

Plumbing:
  * Shader: PathTrace.slang reads clouds_runtime.x to gate the inline
    march; cloud_density_at returns 0 in raymarched mode; the final
    cloud_trans_tex write is skipped.
  * Pipelines: CloudsRaymarch + CloudsComposite registered on Metal and
    Vulkan (resolve()/build_pipeline() entries in Engine + each device).
    Vulkan keeps the 112B push split + 1024B Frame UBO tail; the new
    push fits.
  * Textures: 2x RGBA16F clouds_color ping-pong (temporal EMA history)
    allocated alongside cloud_trans_tex when denoiser is active. Same
    lifecycle as the existing denoiser G-buffers; freed and re-created
    on swapchain resize.
  * Dispatch: when r_clouds_mode == procedural_raymarched AND clouds_p1.w
    > 0 AND denoiser is active, CloudsRaymarch fires AFTER PathTrace
    (overwrites cloud_trans_tex with the raymarch result) and
    CloudsComposite fires BEFORE StarsComposite (blends clouds into
    HDR; celestials still see the new cloud_trans for occlusion).
    All gates off -> zero per-frame cost on the pathtraced path.

Perf (clouds_godrays.cfg, 768x432, 16 frames, Metal + svgf_atrous):
  pathtraced (baseline): ~6.3s total / ~10s without warm cache
  procedural_raymarched: ~2.4s total
  -> 2.6x faster on this scene; the bigger wins land on cloud-heavy
     compositions where the inline march dominates frame time.

  * New golden cell: clouds_raymarched__metal__svgf_atrous (pinned PNG

* feat(planet): real MODIS land cover, modulated by slope and a derived snowline (#300)

The terrain shaded with one albedo and a fixed snowline, so at 6 264 m the
Himalayas came out uniform white and from orbit the planet was a well-lit
uniform sphere. This ships a measured albedo raster and replaces the two
shading shapes sitting on top of it with physical models.

THE DATA. MODIS MCD43A4 v061 Nadir BRDF-Adjusted Reflectance, bands 1/4/3
(620-670 / 545-565 / 459-479 nm) as R/G/B, baked to a 2048x1024 RGBA8
equirectangular grid on the DEM's own registration. NASA LP DAAC: no
copyright, citation requested not required.

MCD43A3/C3 -- the products that are actually albedo rather than nadir-view
reflectance -- would be better, and the tool implements the path to them,
but every archive of them is behind a NASA Earthdata Login (measured: 404 /
302-to-URS / 401 / AccessDenied). Blue Marble was rejected on a checkable
ground: Stockli et al. 2005 sec. 2.5 applied an unpublished cubic-spline
contrast enhancement, measured at 0.9x-10.9x varying by band AND site, so
it cannot be undone -- and #280 has just made that kind of baked-in
illumination visible. assets/planet/PROVENANCE.md records all of it,
including what NBAR is NOT.

Validated rather than asserted: median luminance ratio 0.96 against
published visible-band reflectance at nine sites, area-weighted mean land
reflectance 0.160, and -- the check a grey sphere cannot pass -- every
vegetated site has G > R and G > B, every soil site R > G > B, every ice
site neutral to 15%.

THE TWO MODELS. Both were shapes; both are now derived and cited.

  Slope -> rock exposure now ramps across the measured threshold hillslope,
  30 deg (Burbank et al. 1996) to 45. The ramp it replaces was zero below
  SIXTY degrees and did not saturate until 84, so it exposed no rock on any
  terrain a heightfield can represent. That is why the Himalayas were white:
  the measured rock fraction at that camera has a median of 0.918.

  Snowline is now the warm-season freezing level -- zonal-mean temperature
  (North, Cahalan & Coakley 1981) plus half the annual range, over the
  6.5 K/km environmental lapse rate (ICAO/ISO 2533), anchored at the
  measured tropical ELA (Kaser & Osmaston 2002). Against published
  equilibrium-line altitudes at 0/45/60/80 deg it halves the mean error,
  245 m against 441 m. More importantly it is evaluated at the SHADED POINT
  rather than at the site, so a globe no longer has one snowline everywhere.

The procedural classification stays, in its proper place: the path for a
body with no data, and the per-texel fallback wherever the raster has no
coverage.

A LATENT BUG THIS TRIPPED. MetalDevice.h and VulkanDevice.h each carried a
bare 2048-byte PushConstants staging array; sizeof(PtPush) reached 2064 and
BOTH silently dropped the last 16 bytes, so the terrain ignored its new
raster on two backends with no error anywhere. The header's own comment
already recorded two earlier instances (#21 mesh motion blur, #24 black
clouds). The size is now one shared pt::rhi::kMaxPushConstantBytes,
static_asserted against sizeof(PtPush) in Engine.cpp, and PushConstants()
logs rather than truncating in silence.

BINDING 47 / ENGINE SLOT 22, both the last available: 37 is GodRays' mask
texture, 40-45 are reserved by OceanCascades.slang, 46 is #280's LUT, and
slot 22 is the last entry in every backend's 24-wide table.

TESTS. tests/pt_planet_albedo_test.cpp, 20 cases: container round-trip and
truncation refusal, the C1 interpolation bound with a plain-bilinear
negative control, the snowline table against published ELAs, the old slope
ramp pinned as a failure, the raster's spectral shape and its variation
(five of ten reflectance deciles populated), and the wire formats across
five files with occurrence counts and a CRLF case.

GOLDENS. planet_surface's exposure is re-derived by measurement: at 0.01587
the frame is unclipped but its median is 0.682, so rock and snow both sit in
the tone curve's shoulder and it reads white whatever it contains. 0.004
puts the median at 0.314 with 190 distinct luminance levels. planet_aerial,
planet_lod_seam and orbital_limb are re-pinned for the shading change; a new
planet_land_orbit cell pins the full disc, where the raster is the point.
Closes #300

* fix(atmosphere): the medium has a floor -- stop integrating air below the datum (#300)

planet_land_orbit rendered dark with a yellow-brown cast over the whole
disc. It was not the land cover, not the tone curve and not the sun's
spectrum -- #280 already made that blue-weighted, which is why a warm disc
pointed at the surface term rather than at the light.

THE MECHANISM, MEASURED. ptAtmoOpticalDepth clipped its interval to the
TOP of the shell (#260) and left `max(h, 0)` as its only floor. That clamp
is not a bound: it charges every sub-datum metre at SEA-LEVEL extinction,
so the error grows linearly with depth and without limit.

Nothing exercised it until terrain streaming, because before that the
ground WAS the datum. With terrain on the two radii are chosen on
different bases -- the atmosphere's datum becomes the SITE's geocentric
radius (6 373 458.18 m at 27.99 N) while P3's analytic backstop is
WGS-84 b - 10 935 - 65 (6 345 752.31 m), a constant picked to sit inside
every chunk everywhere. The backstop is 27 705.87 m below the datum, and
from orbit the backstop IS the visible planet, every pixel of it.

Read out of the Metal kernel at the sub-solar nadir pixel by writing
atmosphericTransmittance() to the framebuffer under r_tonemap_op linear:

    tau   R 0.4608   G 0.7597   B 1.4338     shader, as shipped
    tau   R 0.4632   G 0.7575   B 1.4260     the same rule, on the host
    tau   R 0.0662   G 0.1468   B 0.2761     the true nadir column

5.2x the optical depth in G and B. And because the excess is Rayleigh --
lambda^-4 -- it reddens as it dims: transmittance R/B goes 1.23 -> 2.62.
Both reported symptoms out of one term, which is why brightening the frame
would have been the wrong fix.

THE FIX IS THE MEDIUM'S OWN DEFINITION, not a tolerance. `b` declares air
on [ground_radius, top_radius]; the integral now covers the part of the
ray inside it, via the same ptRayShell every other shell consumer uses.
What it discards is the air over genuinely sub-datum GROUND, and unlike
the tail it replaces that is bounded in closed form: the deepest exposed
land on Earth is the Dead Sea shore at -430 m, i.e. 0.0094 of optical
depth in green, 0.9% of transmittance -- against an error that was
previously unbounded.

ptRayShell moves above ptAtmoOpticalDepth. Slang has no forward
declaration here and Vulkan is not built on macOS (#290), so the ordering
is pinned as a test rather than proved by the Metal build. The SPIR-V
lowering was checked by hand rather than assumed: slangc with -target
spirv -DPT_TARGET_SPIRV over the same module chain emits an 8.86 MB
module with no diagnostics, and spirv-val accepts it. That retires the
compile/lowering half of the #290 risk for this change. Pixel correctness
on Vulkan remains unverified here, as it is for everything else on this
platform.

THE SAME DEFECT ON THE IN-SCATTER SIDE. The primary-hit aerial-perspective
march clipped to the shell but passed r_inner = 0, so it marched the same
27.7 km as a slab of sea-level air -- and being in-scatter it ADDED light.
Measured at nadir, sub-solar: sigma_s(0) * 27.7 km * P_R(-1) * E =
(7.4, 21.6, 54.4) W/m^2/sr against a true column in-scatter of
(2.1, 6.2, 15.7). skyPhysical has carried the ground clamp since #260;
this march now carries it too, so the two agree about where the air ends.

No image golden moves for that half, and that is the point: every fixture
with r_sky_mode physical has r_planet_terrain 0, and without terrain the
analytic body sits AT the datum, so the clamp is a no-op on all nine of
them. That is the gap the defect lived in. Guarded by a source pin until a
cell combines the two.

RED-THEN-GREEN. Reverting the mirror reds 18 assertions in "the air column
ends at the datum, not at the surface it hits"; reverting either shader
clause reds the source pins. "the clip is a no-op for every ray that starts
inside the shell" had been pinning the defect -- its downward rays ran
30 km from 10 km up, straight through the ground -- so its t is now capped
at the ground crossing, which is what a primary ray actually does, and it
gains a floor sub-case mirroring its existing ceiling one.

GOLDEN DECOMPOSITION. planet_land_orbit is the only image that moves:
mean 23.28, max 334.2, 14.19% of pixels -- 4.6x the land-cover ablation
that cell exists to measure, i.e. the atmosphere bug was a bigger effect
on the frame than the feature under test. Thresholds re-measured, not
inherited: the r_planet_land_albedo 0 ablation now moves it by mean 5.011
with 6.91% bad (unloading the raster gives identical figures), so
MEAN_DELTA 0.8 keeps 6.3x and FAIL_PERCENT 1 keeps 6.9x. Three repeat
renders are bit-identical. 205/208 pass; the three failures are the held
night cells awaiting #280's airglow remainder.

r_exposure 0.05 re-derived against the corrected frame and left alone: it
sits on the plateau of distinct luminance levels (221) and at the peak of
both chroma separations, with nothing clipped. Swept and tabulated in the
fixture header.

TWO THINGS DELIBERATELY NOT DONE HERE, both recorded in the fixture:

  * This cell uses r_sky_mode procedural at 30 000 km -- a sky DOME whose
    own docstring says the observer is implicitly at ground level. Space
    renders as (0.0281, 0.0572, 0.1710) of painted sky blue instead of
    zero, and the aerial-perspective march spans min(primary_t, 60 000 m)
    outside the physical mode, so from 30 000 km it samples vacuum:
    r_volumetric_intensity 0 and 5 render this cell BIT-IDENTICALLY. The
    disc has extinction and no atmosphere. Switching to physical halves
    the distinct levels the disc carries (221 -> 114) and surfaces the
    from-orbit magnitude of #280's multiple-scattering table. Measured at
    nadir, sub-solar, once the slab above is removed: the march returns
    (8.36, 15.54, 24.93) against a single-scatter Rayleigh backscatter of
    (2.12, 6.23, 15.71), i.e. the table supplies 3.9x / 2.5x / 1.6x in
    R / G / B. An r_sky_ground_albedo 0 ablation moves only 3-7% of it, so
    that is the multiple-scattering term proper and not the ground bounce.
    Nothing has characterised it from orbit, and this change does not.

  * The ocean has no body colour. Measured on planet_ocean_orbit: with the
    atmosphere removed the off-glitter water is (1.23, 1.45, 1.64), B/R
    1.33 -- neutral and near-black -- against (3.86, 8.82, 21.81), B/R
    5.66 as shipped. All of the blue is atmospheric Rayleigh. P7's
    in-scatter march is gated on primary_in_water, so a ray refracting in
    from OUTSIDE gets Beer's law absorption and no scattering: there is no
    water-leaving radiance for a camera outside the medium. That is a
    missing term, not a wrong constant, and it is scoped out rather than
    approximated with a blue albedo.
