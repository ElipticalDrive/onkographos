Feature request
VoxelLayer and ObstacleLayer should optionally raycast for invalid pointcloud points padded with inf or 0. These invalid points can come from sensors (depth cameras etc.) when they do not hit an obstacle (Gazebo's depth camera plugin pads invalid points with inf, for example, or D435 depth camera optionally pads these points with 0) I don't know if this is already a feature for laserscans with inf_is_valid parameter, but that parameter is not supported for pointcloud data.
Feature description
The observation cloud is the filtered version of the pointcloud with global z value between min_obstacle_height and max_obstacle_height here
https://github.com/open-navigation/navigation2/blob/07fbc50edb75ee97b3650716227caa6925874e84/nav2_costmap_2d/src/observation_buffer.cpp#L135C17-L135C18
The clearing raycast feature only raycasts for points in the observation cloud here, which results in absent obstacles only being cleared if they were previously in front of an existing obstacle. Obviously it should not behave like this.
https://github.com/open-navigation/navigation2/blob/07fbc50edb75ee97b3650716227caa6925874e84/nav2_costmap_2d/plugins/obstacle_layer.cpp#L652
Implementation considerations
This feature could be added as an additional parameter.

So those points are invalid? They shouldn't be used to raycast then. We need some kind of "hit" to know an obstacle is there to raytrace up-to. Laser scanners have the option for inf is valid because those are active laser sensors and no return is better-chance-than-not total clear space past the bounds of its power rating. 3D sensors are frequently passive or with an abundant reasons why you wouldn't get data back for a particular pixel, so the assumption that Inf is a meaningful measurement is mostly untrue in my experience.

We are investigating a general 3D occupancy update / clearing issue with Nav2 VoxelLayer on ROS 2 Jazzy (Raspberry Pi 5, Astra depth camera, PointCloud2). This is not an issue limited to eight persistent voxels.
In controlled experiment AST-03.16E.48, the robot remained stationary:
0–15 s: baseline, mean 733.82 MARKED voxels
15–35 s: suspended object present, mean 734.90
35–75 s: object removed, mean 822.67
225 VoxelGrid publications; one consecutive change from 883 to 814 MARKED voxels.
Local costmap XY resolution: 0.025 m; voxel Z resolution: 0.05 m, 16 vertical voxels. The PointCloud2 source has marking and clearing enabled, observation_persistence: 0, expected_update_rate: 0, raytrace_max_range: 3.0 m, obstacle_max_range: 2.5 m. The depth-processing path discards invalid returns and subsamples pixels.
We have not spatially attributed the extra voxels to the suspended object, so these counts indicate unexpected occupancy evolution, not proof of a specific clearing defect.
We read the discussion here about invalid depth returns not being evidence of free space. We do not propose blindly treating invalid points as free space.
Could maintainers advise on:
How to instrument per-update clearing-ray traversal and voxel state transitions before clearing, after clearing, and after marking?
How to distinguish insufficient valid clearing rays from immediate re-marking or reuse of stale observations?
Whether observation_persistence: 0 can still reuse the most recent cloud in update cycles without a new message?
Whether sparse depth-camera sampling can explain persistent marks at this resolution, and what tests best discriminate this?
Whether there are known Jazzy-specific fixes or recommended alternatives for reliable dynamic-obstacle removal with depth cameras?
We can share a minimal reproducible dataset, effective YAML and exact package versions after verification. We are seeking guidance for a safe, reproducible diagnosis, not claiming a Nav2 bug. Thank you.
