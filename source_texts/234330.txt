Summary
PngCompression compresses the higher-order SH coefficients (shN) with K-means into 65,536 centroids.
This PR adds gsplat/compression/kmeans.py with weighted_kmeans(), a plain-PyTorch Lloyd's algorithm
with per-splat weights, and exposes it through three options:
```
PngCompression(kmeans_backend="builtin", kmeans_weighting="opacity_area", kmeans_chunk_size=4096)
```
With these settings, mean PSNR improves by +0.111 dB on MipNeRF360 and +0.052 dB on
Tanks & Temples, at -0.10% / +0.08% size, and PSNR is higher on every scene of both benchmark scripts.
Three commits:
9348e32: the backend and the options. Defaults unchanged, files byte-identical.
a4c31082: kmeans_chunk_size, the memory knob of the builtin backend. Defaults unchanged.
61cd1baf: makes the builtin backend with opacity_area weighting the default. It stands alone:
drop it if you prefer TorchPQ as the default, and the options stay.
Motivation
On MipNeRF360 (garden / bicycle, mcmc.sh settings) almost all of the shN loss is the clustering, not
the 6-bit codebook:

So the lever is which 65,536 centroids we spend, not how we store them. The current call clusters
every splat with equal weight, although a large, opaque splat covers far more of the rendered image
than a small, nearly transparent one.
Method
Weights per splat: sigmoid(opacity) * exp(sum of the two largest log-scales), that is, opacity
times the splat's largest cross-section up to a constant factor. They are computed from the
pre-activation parameters after the PLAS sort, so they line up with the splats being clustered.
(kmeans_weighting="opacity" uses sigmoid(opacity) alone.)
Clustering: Lloyd's algorithm with euclidean assignment (chunked, kmeans_chunk_size points at a
time) and a weighted mean update, accumulated in float64. Initial centroids are n_clusters points drawn
without replacement with a fixed seed. It stops when the summed squared centroid change is <= tol
(1e-4) or after 100 iterations. An empty cluster becomes the zero vector, as in TorchPQ.
Unchanged: file format, file layout, meta.json, the 6-bit codebook with one scalar min/max,
uint16 labels, and the decoder (_decompress_kmeans). Directories written by either backend decode
with any version.

Summary
PSNR is better on all 11 scenes, LPIPS on all 11, SSIM on 10 of 11 (garden -0.00016). Size stays
within -0.47% and +0.27% per scene (-0.10% / +0.08% on average).
The weighted update recovers about 21% of the compression loss on MipNeRF360 on average, and
36% / 23% on train / truck.
Seeds: on garden and bicycle, three k-means seeds all gain (+0.082 / +0.104 / +0.103 dB and
+0.027 / +0.031 / +0.033 dB). The current scheme's own seed-to-seed spread there is
0.019 / 0.007 dB.
kmeans_weighting="opacity" also passes our acceptance rule (fixed before the runs), but gains
less: +0.049 dB on MipNeRF360 and +0.005 dB on Tanks & Temples.

Time: 1.26x on MipNeRF360 on average (0.74x-1.59x per scene), and faster on Tanks & Temples
(0.86x / 0.71x). TorchPQ always runs its full 100 iterations; the builtin backend stops at tol.
Memory: measured as torch.cuda.max_memory_allocated() over compress() in the benchmark
process, with the 1M-splat scene loaded, so the absolute figures include the scene. The increase
over TorchPQ is +2.11 GB on 7 MipNeRF360 scenes and +2.35 GB on the other 4 (garden and bicycle
ran in separate jobs, plus train and truck).
Sizing it yourself: the largest buffer of the builtin backend is the assignment matrix,
kmeans_chunk_size x n_clusters x 4 bytes: 4096 x 65,536 x 4 B = 1.07 GB at the default. The
float64 copy of the weighted points adds N x D x 8 bytes (0.36 GB for 1M splats at SH degree 3).
Lowering kmeans_chunk_size shrinks the first term linearly without changing the result (tested);
I have not measured its effect on speed.
GPU coverage: the builtin path ran on GPU on all 11 scenes above (9 MipNeRF360 + 2 Tanks &
Temples). I have no GPU locally, so the repo's CUDA-only tests/test_compression.py test stays
skipped in my runs. The CI that runs on pull requests (Core Tests) is CPU-only; the GPU workflow
runs on pushes to main and on manual dispatch. With the default flip, that CUDA test exercises
the builtin backend.
Reproducibility
Builtin backend: the initial draw is seeded and independent of the caller's numpy / torch state,
and the result does not depend on kmeans_chunk_size (both are tested). On GPU, all 18 rows
(9 scenes x 2 weightings) gave identical metrics and file sizes in two separate sessions. The
float64 index_add_ uses CUDA atomics, so on GPU this is observed, not guaranteed.
Current TorchPQ path, for comparison: re-running it on the same 9 checkpoints in a later session
gave identical results on 7 scenes, and +0.0024 dB / +0.00006 dB on the other two. So it
reproduces to about 0.002 dB, not bit-exactly. Paired against that re-run instead, the mean gain is
+0.1106 dB and every scene still gains.
Also in this PR
No TorchPQ / CuPy needed for kmeans_backend="builtin": it is plain PyTorch and runs on CPU.
A CPU-only run with TorchPQ blocked compressed and decompressed 4,096 splats (0.21 s / 0.013 s),
with the decoded shapes matching.
n_clusters is clamped to the number of splats in the builtin path, so scenes with fewer than
65,536 splats work. This sidesteps the "larger sample than population" failure reported in
#787 for users who choose the builtin
backend. The TorchPQ path is unchanged, so this does not fix PngCompression issue #787 by itself.
The TorchPQ backend rejects weights with a clear error instead of silently ignoring them.
After the default flip, PngCompression(kmeans_backend="torchpq") without
kmeans_weighting=None fails when the object is created. It does not fail late, after sorting.
Backward compatibility
Commits 1-2: defaults unchanged, output byte-identical. The full PngCompression() output was
diffed file by file against main with a stubbed TorchPQ: all 9 files identical.
Commit 3 (default flip): the default output differs from before only in shN.npz; the PNG files
are identical. The decoder is untouched, so directories from either version decode with either
version.
The previous output stays available:
PngCompression(kmeans_backend="torchpq", kmeans_weighting=None) writes the same 9 files as main's
PngCompression(). That was diffed against main, and tests pin it against the previous encoder.
Not changed by the flip: requirements, extras and docs (TorchPQ / CuPy stay where they are).
benchmarks/compression/results/*.csv still hold the TorchPQ numbers. A docs / extras cleanup,
including those CSVs, can follow separately.
Tests
tests/test_kmeans.py runs on CPU without TorchPQ and covers:
weights of one reproduce the unweighted result
determinism per seed, and independence from the caller's numpy state and from the chunk size, both
in weighted_kmeans and through PngCompression(kmeans_chunk_size=...) (same centroids and labels)
empty clusters become zero, and argument validation (including chunk_size < 1)
the weighting formulas
a round-trip through the unchanged decoder
n_clusters clamping, and errors for an unknown backend or misused weights
the torchpq path byte-identical to the previous encoder, for _compress_kmeans and for
PngCompression
a full PngCompression round-trip on CPU with TorchPQ blocked, including the defaults
the new defaults, and the torchpq + weighting error (commit 3)
The flip changes one test expectation: with TorchPQ blocked, PngCompression() no longer raises
ImportError; only the explicit torchpq backend does.
How I would like to land it
9348e32: the backend and the options, defaults untouched. Nothing changes for existing users.
a4c31082: kmeans_chunk_size, defaults untouched.
61cd1baf, easy to drop: makes kmeans_backend="builtin", kmeans_weighting="opacity_area" the
default. If you prefer to keep TorchPQ as the default, drop this commit; the options stay. A
docs / extras cleanup (installation notes, TorchPQ / CuPy as optional, regenerated results CSVs)
can follow separately.
I am happy to split, rename or drop any part, and to rerun the benchmarks on other scene sets.

```
Adds gsplat/compression/kmeans.py: weighted_kmeans(), Lloyd's algorithm in plain torch with

_compress_kmeans gains weights and backend ("torchpq" default, "builtin"); PngCompression

files stay byte-identical to before (tests/test_kmeans.py pins that against the previous
encoder).
```

PngCompression: expose the builtin K-means chunk size
…
a4c3108
```
kmeans_chunk_size (default 4096, the previous fixed value) is passed through
_compress_kmeans to weighted_kmeans. It sets how many points each assignment
step handles at once; the largest buffer of the builtin backend is a
chunk_size x 65536 float32 distance matrix (1 GiB at the default), so a smaller
chunk lowers peak memory. It does not change the result.

weighted_kmeans now rejects chunk_size < 1, which would otherwise skip the
assignment loop.
```
PngCompression: default to the builtin weighted K-means backend
…
61cd1ba
```
kmeans_backend now defaults to "builtin" and kmeans_weighting to
"opacity_area". The torchpq backend stays available and unchanged:
PngCompression(kmeans_backend="torchpq", kmeans_weighting=None) writes the same
files as the previous default. Requirements are not changed.

Because the default weighting cannot be used with torchpq, that combination now
fails when the object is created, with a message naming kmeans_weighting=None,
rather than after sorting and writing the PNG files.

Tests: the ImportError expectation without TorchPQ now needs the explicit
torchpq backend, since the defaults no longer import it. The byte-for-byte pins
against the previous encoder use the torchpq backend explicitly, and one more pins
the full PngCompression torchpq path. Also tested: the new defaults, and the
torchpq + weighting error.

This commit can be dropped on its own; the options stay available without it.
```
