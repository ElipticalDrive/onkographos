Summary
Work in progress toward moving chunk meshing off the CPU. Flying forward causes major frame stutters; the root cause was measured with real instrumentation (not guessed): MeshSnapshot::capture does a synchronous main-thread copy of each chunk's neighbor-bordered voxel data before every mesh dispatch, costing 13-17ms per dispatch batch against a 5ms/frame budget at 200Hz. A GPU compute mesher only fixes this if chunk data lives persistently on the GPU, so the shader reads neighbors directly instead of gathering a CPU snapshot per dispatch.
This PR covers the first three milestones of that rewrite:
M0: request the adapter's real device limits in request_device instead of wgpu's tiny defaults (256MB buffer / 128MB storage-binding), which would reject the voxel pool outright. Confirmed on an RTX 5070: ~2GB storage-binding limit, ~4GB buffer limit.
M1: persistent GPU voxel pool (src/renderer.rs) mirroring the CPU chunk pool's ring buffer, synced incrementally on chunk generation and after each relight rather than gathered per mesh dispatch. Sized to a separate, smaller GPU_POOL_VIEW_DISTANCE (~315MB at radius 20) to bound VRAM independently of the larger CPU streaming/collision radius.
M2: compute shader (assets/shaders/chunk_mesh_test.wgsl) porting the CPU mesher's standard-block path (face culling, AO, smooth per-vertex lighting, partial-height blocks like snow layers/torches/bells) to read directly from the GPU pool. Verified against the CPU mesher on a real chunk: 8820/8820 vertices match after canonical sorting.
Known gap: water, lava, and wheat are not yet ported to the compute shader (explicitly skipped). The CPU mesher still does all real rendering today — the new compute shader only runs as a one-shot startup diff test (World::run_gpu_mesh_m2_test), gated behind a one-time flag in main.rs, with no effect on gameplay or visuals.
Full plan and remaining milestones (M3: indirect draw wiring, M4: multi-chunk arena allocation, M5: full pipeline swap with a CPU/GPU toggle, M6: delete the CPU mesher) are in the hashed-splashing-haven plan doc from this session.
Test plan

2103-2166: 🚀 Performance & Scalability | 🟠 Major | ⚡ Quick win
VERTEX_COUNT_SAMPLES grows unbounded and gets progressively more expensive to process.
samples is never capped or cleared — every upload_mesh call pushes another entry for the lifetime of the process. Every 64th push then clones the entire (ever-growing) vector and sorts it just to print quantiles, so the cost of this periodic stat computation keeps increasing the longer a session runs, on a path invoked whenever a chunk mesh finishes (a moderately hot path during exploration/edits). This is flagged as temporary M1 instrumentation, but as merged code it runs in every build until explicitly removed.
Cap or reset the buffer so the cost stays bounded, e.g.:
⚡ Proposed fix
```
 fn record_vertex_count_sample(count: u32) {
     let mut samples = VERTEX_COUNT_SAMPLES.lock().unwrap();
     samples.push(count);
     if samples.len() % 64 == 0 {
         let mut sorted = samples.clone();
         sorted.sort_unstable();
         let p50 = sorted[sorted.len() / 2];
         let p99 = sorted[(sorted.len() * 99 / 100).min(sorted.len() - 1)];
         let max = *sorted.last().unwrap();
         let avg = sorted.iter().map(|&v| v as u64).sum::<u64>() / sorted.len() as u64;
         println!(
             "Chunk mesh vertex counts ({} samples): avg={} p50={} p99={} max={} (36 bytes/vertex)",
             sorted.len(),
             avg,
             p50,
             p99,
             max
         );
+        samples.clear();
     }
 }
```
