Motivation and context
Existing 3d workspace misses support of camera calibration data that is required for UI features relying on 3d-2d relations.
This PR:
Adds camera calibration metadata support for related images
Support intrinsic/extrinsic matrices in own/Sly formats
Adds Camera Ray feature to 3d annotation workspace UI:
Clicking on calibrated 2d related image creates a camera ray in 3d view from the camera origin to the clicked point
CameraRay.mov
This PR additionally fixes the following existing issues:
Importing 3d project with related images ends with an exception
When 3d task is created from a cloud storage by manifest it's missing related images
Backup-restore 3d task created from zip created on MacOS ends with an exception
See individual commit messages for details.
How has this been tested?
Tested manually
Camera ray UI
Creating task with calibration sidecars in own/Sly formats using different sources: upload/connected file share/remote sources/cloud storage
Exporting/importing datasets with media and calibration in Sly format
Backup/restore preserving calibration using local/cloud storage, lightweight/heavyweight backups
Added e2e test
Added unit tests
Added REST API tests

Just as a side note I found it extremely complicated to perceive how all these scenarios are currently handled in the code when I was implementing it. I think we miss some abstractions to keep the code complexity under control.
Anyways, related to manifests (points 1,2 and 4 I believe):
The problem is that the current manifest tool doesn't work on 3D layouts at all so I just didn't want to include this additional scope to this task.
I only included manifest changes in this task to support backup/restore scenarios which are only real scenarios of generating a manifest for 3D task now and they seem to work fine as per my testing.
So would you mind excluding support for the remaining manifest scenarios from the scope of this PR?
Going a bit deeper into this, one of the concerns that complicate this support is that the proposed structure of the manifest's related image metadata doesn't include information about the source of the metadata (calibration) but only the metadata itself. It makes it impossible to obtain paths to the calibration sidecars without determining the format by the layout (only reading manifest). Including this info in the manifest also didn't seem like a good idea as different formats could provide completely different metadata structure. Some of them might use aggregated/shared calibration files. Some have calibrations excluded from the original format entirely (e.g KITTI Raw) so there will be nothing to fill as the source. With metadata(calibration) only we could still support calibration for such formats with advance manifest generation. One option I see is if we declare manifest as the priority source for the metadata and only fallback to native calibration if manifest is absent. It may remove the need for most of the changes that otherwise yet to be done.
Good catch, thanks, fixed
