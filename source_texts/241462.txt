Problem
3D SDF primitives (types 100-119) are currently not part of the 2D spatial hash grid. They are excluded because:
They have zero-area AABBs (set intentionally in computeAABB)
They are skipped in declareBufferNeeds(), computeDerivedSize(), and rebuildAndUpload() grid sizing
As a result, the fragment shader raymarches every 3D primitive for every pixel — brute-force O(pixels × march_steps × N_3d_prims). With 64 march steps per pixel and finite-difference normals (6 extra SDF evaluations), this becomes very expensive as the number of 3D primitives grows.
Current architecture
2D prims: spatial hash grid → O(1) per-pixel lookup, only evaluate nearby prims
3D prims: brute-force loop in evaluateSDF3D() over all prims with type >= 100
Shader: 0x0003-ydraw.wgsl lines ~158-227, controlled by YDRAW_FLAG_HAS_3D = 8u
Possible approaches
3D spatial hash / BVH: partition 3D prims into a grid in 3D space, march rays through occupied cells only
Screen-space tile culling: project 3D prim bounding spheres to screen tiles, only raymarch relevant prims per tile
Per-pixel bounding sphere test: before full raymarch, do a cheap sphere intersection test to skip prims that can't contribute
Hybrid: use the existing 2D grid with projected 3D bounding boxes to cull at the tile level, then raymarch only candidates
Related
3D shapes were disabled in ydraw-zoo (issue ydraw-zoo: 3D shapes don't scale/cull correctly in infinite zoom #58) partly due to coordinate mapping issues, but performance was also a concern
See src/yetty/shaders/lib/distfunctions.wgsl (evaluateSDF3D) and src/yetty/shaders/cards/0x0003-ydraw.wgsl (raymarch loop)
