Summary
Adopts NanoVDB's VoxelBlockManager (VBM) for per-active-voxel iteration on CUDA. The leaf scan launches one thread per 512-slot leaf position and discards inactive slots. The VBM decode costs O(1) per active voxel, in registers, so its cost tracks active voxels instead of leaf slots. A batch's VBMs are built together in one launch, and a batch is iterated in one launch.
First step of #817, which tracks the remaining consumers and follow-ups.
Depends on AcademySoftwareFoundation/openvdb#2291 for buildVoxelBlockManagerBatch. Until it merges, get_nanovdb.cmake pins NanoVDB to its head (swahtz/openvdb 29165acb, on top of develop/nanovdb). The pin moves back to AcademySoftwareFoundation/openvdb before this merges.
Changes
VbmCache: lazily built VBMs for every grid of a GridBatchData (~0.16 B/voxel), reached through GridBatchData::vbm() / vbmAt(bi).
The first use builds all of the batch's VBMs into one buffer with one memset and one kernel. Grid g's VBM starts at block floor(cumVoxels_g / 128) + g, which leaves room for every grid without a scan (at most one unused block per grid), so the build kernel derives each grid's entry from the batch's device-side voxel offsets and metadata. Sizes come from host metadata, and the build never synchronizes the host.
Each GridBatchData, views included, owns its own cache. Never invalidated (topology is immutable) and never serialized.
The buffer is one tensor from the CUDA caching allocator, read through typed uint32_t/uint64_t pointers. The build event is created only when a second stream first acquires the cache; that stream waits on it and record_stream()s the buffer once, and later calls from it skip both.
The destructor takes no device guard, so freeing a grid in a forked child cannot throw.
forEachActiveVoxelVbmCUDA: one launch per batch. Each 128-thread group takes one VBM block and finds its grid by binary search on the batch's compact voxel offsets (8 bytes per grid). Blocks between grids are skipped.
reinitialize_sdf: stencil kernels use the register decode instead of the shared-memory one, and reuse the cached VBM instead of rebuilding it every call.
BasePerActiveVoxelProcessor (.ijk, morton/hilbert): CUDA path iterates via the VBM. CPU and PrivateUse1 keep the leaf scan.
PadGrid: uses allocateProcessedRootTiles, since the newer develop/nanovdb deprecates allocateProcessedRoot.
Benchmark: single-grid occupancy sweep, build cost, and batches of 1-256 random or shell grids from 32³ to 256³, warm and cold.
Performance
active_voxel_iteration_benchmark, RTX PRO 6000 Blackwell (sm_120), CUDA 13.4, median of 5.
Batches
Each grid is either a 25% random subsample of a dim³ box (every leaf present, about a quarter full) or a 3-voxel-thick spherical shell inscribed in it (the narrow-band case). Warm reuses the batch's VBMs. Cold runs on a freshly built batch, so the VBM path includes the build. Speedup is leaf scan ÷ VBM.

End to end
reinitialize_sdf (order 3, repeated calls, 396k-voxel narrow shell) took 889 µs on main at f655b758 and 715 µs here (1.24×), measured before the batched rework. Its kernels are unchanged by the rework.
Notes
Block width. The decode's rank step reads 2^L/64 jumpMap words per voxel. At L=9 (512) the VBM was ~12% slower than the leaf scan on dense grids. L=7 keeps it at parity.
Launch shape. VBM kernels use 256-thread blocks. A <<<blockCount, 512>>> launch with __launch_bounds__(512) silently dropped work from a register-heavy callback on sm_120 / CUDA 13.0.
GatherScatterDefault stays on the leaf scan. Its topology build is bound by counter-atomic contention, which Warp-aggregate the per-tap counter atomics in the conv topology build #838 addresses first. Routing it through the VBM is tracked in Extend VoxelBlockManager iteration across CUDA ops (follow-ups to #747) #817.

Not from Python today, since no fvdb binding releases the GIL. I'd still make an argument for keeping it for two reasons:
The cache is built lazily behind a const GridBatchData &, and several Python grid objects and views can share one GridBatchData. The usual C++ contract is that const calls are safe to make concurrently, and a lazy build that writes members breaks that without a lock.
Autograd runs C++ backward functions on its own per-device threads without the GIL. Nothing in backward touches the VBM yet, but the channel-folded ops in Extend VoxelBlockManager iteration across CUDA ops (follow-ups to #747) #817 (pools, refine, inject) will, and their backward could then race the forward of another op on the same grid.
An uncontended std::mutex costs tens of nanoseconds, which is small next to the kernel launch it guards. In the reworked cache, the lock also protects the list of streams that have waited on the build (the fix for @harrism's repeated cudaStreamWaitEvent comment). So std::call_once alone wouldn't cover everything.

At the pinned NanoVDB (0ab0a81e), buildVoxelBlockManager reads lowerCount through DeviceGridTraits::getTreeData, which is a plain cudaMemcpy on the legacy default stream. fvdb isn't built with per-thread default streams, and torch's pool streams are created cudaStreamNonBlocking, so that copy isn't ordered after stream.
Scenario: build a grid under torch.cuda.stream(s) and call .ijk on it immediately. The header read can run before the builder's writes on s land. That gives a wrong lowerCount (a short VBM, or an out-of-bounds node read for a garbage count), and the bad entry is cached for the life of the grid. The leaf-scan path never read device memory from the host, so it didn't have this exposure. (BuildPaddedGrid/PadGrid already make the same read, so it's not new to fvdb, but this PR puts it on the .ijk/morton path.)
Since the build blocks anyway, a cheap interim fix is to C10_CUDA_CHECK(cudaStreamSynchronize(stream.stream())) before calling buildVoxelBlockManager, until openvdb#2291 removes the read.

Fixed. The destructor no longer takes a device guard, and it destroys the event with C10_CUDA_IGNORE_ERROR, so teardown in a forked child or at process exit is best-effort and can't throw. test_fork_safety.py now calls grid.ijk before the fork, so the child frees a grid whose cache is built.
One limit remains, and it's PyTorch's rather than ours. If a batch's VBMs are acquired from a second stream, the cache record_stream()s its buffer for that stream. Freeing any record_stream()ed tensor in a forked child aborts, because PyTorch's allocator records an event on the recorded stream at free time, and that throws in the child. I reproduced it with a plain tensor and no fVDB. Single-stream use never calls record_stream(), and the build event is now created only for a second stream, so the common DataLoader case frees normally. The limit is documented in VbmCache.h (e184a04).

This and making those benchmarks made me make some deeper changes to openvdb#2291 to allow for batched VBM creation. This was reworked along the lines you suggested.
Each batch now gets one build (one memset and one kernel, with no host sync) and one iteration launch over all of its grids, in place of one launch and one blocking build per grid. The description has the data point you asked for: batches of 1-256 grids, random or narrow-shell, from 32³ to 256³, warm and cold. They're compared against the leaf-scan kernel that main uses, in active_voxel_iteration_benchmark, not as a Python timing against main itself.

We decided to accept that rather than keep the leaf scan for cold batches: it's a fixed cost once per batch, it doesn't grow with grid count, and it no longer syncs the host.

VbmCache builds one NanoVDB VBM (firstLeafID + jumpMap) per grid on
first use and keeps it for the life of the batch. Topology is immutable
after construction, so entries never need invalidation; the cache is
shared with sliced/indexed views (entries are keyed by the grid's byte
offset into the shared buffer, the only view-stable identity) and is
never serialized.

The VBM block width is 128 voxels (kLog2BlockWidth = 7): the decode's
rank step scans 2^L/64 jumpMap words per voxel, and at 128 the register
decode is faster than the legacy leaf scan at every occupancy including
fully dense grids (see the active-voxel iteration benchmark), while 128
also remains a sane CUDA block width for consumers whose launch shape
derives from the VBM block width. Metadata cost is ~0.16 B per active
voxel.

Entry buffers are torch::Tensor storage from PyTorch's CUDA caching
allocator, so their lifetime is stream-safe: get() makes a consumer
stream that differs from the build stream wait on the recorded build
event (execution ordering) and record_stream()s the buffers for it
(lifetime ordering), so destroying the owning GridBatchData while a
cross-stream consumer kernel is still in flight cannot recycle the
buffers under it. The NanoVDB handle only sees non-owning views, and
only for the duration of the in-place buildVoxelBlockManager call,
which is sized from host metadata to avoid the blocking device read of
activeVoxelCount that the allocating overload performs.

VbmCacheTest pins the decode contract: bitwise coordinate parity with
activeGridCoords, the sequential OnIndex invariant (decoded value index
== slot), view sharing, empty grids, non-multiple-of-block-width sizes,
cross-stream consumption with the owner destroyed mid-flight, and
isSequential() across every grid production path (which the register
decode requires).

per-thread register budget in a way that was observed to silently drop
work from a register-heavy callback.

sliced GridBatch views (shared cache entries) and batches containing
empty grids.
