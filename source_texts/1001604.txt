Current status — 2026-09-02
FUTURE / RESEARCH. Apple tile/imageblock specialization remains a secondary target study. It must reuse portable renderer semantics and cannot become a baseline or a dependency for work on available hardware.
Companion note
Computer-science / architecture companion: walnut-burgundy/computer-science#44
Why this deserves its own backend note
The practical development machine is not an Apple device. The renderer should continue to be developed and tested first on hardware actually available to the project, and its mathematical semantics must remain portable.
At the same time, Apple GPUs are an unusually tempting research target for the holomorphic / meromorphic / metamorphic renderer. Apple is not literally the only vendor with derivatives, subgroups, shared memory, tiling, or pixel-local storage. PowerVR, Mali, Adreno, NVIDIA, AMD and Vulkan expose overlapping ideas under different names. What is striking about Apple is the unusually coherent combination Metal exposes on Apple-designed GPUs: explicit imageblocks, tile shaders, raster-order groups, quad/SIMD-group collectives, threadgroup memory, and a tile-based deferred renderer designed around keeping intermediate image data on chip.
That combination lines up suspiciously well with the mathematical structure of this renderer.
The backend therefore should have two goals at once:
keep a boring portable path which defines the renderer correctly everywhere;
allow an Apple-specific experimental path to push local complex analysis and singularity handling as far as the hardware permits.
Do not weaken the first goal to get the second.
The motivating mathematical picture: ordinary tiles and exceptional tiles
Most of the complex plane visible in a frame is locally boring. A regular holomorphic region does not need the same work as a tile containing or bordering a zero, pole, suspected unresolved singularity, branch/cut boundary, very large phase variation, or a failed local conformality / Cauchy–Riemann diagnostic.
Treat the screen as roughly:
```
ordinary tile  ordinary tile  ordinary tile
ordinary tile  EXCEPTION      ordinary tile
ordinary tile  ordinary tile  EXCEPTION
```
The ordinary path should remain cheap. The exceptional tiles may receive extra samples, extra precision, explicit derivative/regularity checks, singularity classification, or a more careful perturbation/refinement pass.
That is a much better match for the renderer than making every fragment execute the pathological case.
Why Apple's explicit tile machinery is interesting
Apple documents its GPUs as tile-based deferred renderers. Beginning with the A11 / Apple4 family, Metal exposes features specifically aimed at retaining and manipulating data in tile memory:
imageblocks: structured per-pixel data resident in tile memory;
tile shaders: compute-like work executed inside the render pass with access to the entire imageblock;
raster order groups: ordered access by overlapping fragment threads, including fine-grained synchronization on newer GPUs;
imageblock sample-coverage control;
quad-scoped permute / ballot / reduction operations as later families add them;
SIMD-scoped permute / reduction operations on later families;
ordinary threadgroup memory, barriers, atomics and compute facilities alongside the tile-specific mechanisms.
Apple explicitly describes tile shaders as a way to perform compute work while intermediate data remains in tile memory instead of round-tripping through device memory.
Authoritative references:
Apple, Tailor your apps for Apple GPUs and tile-based deferred rendering: https://developer.apple.com/documentation/Metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering
Apple, Metal Feature Set Tables: https://developer.apple.com/metal/feature-sets/
Apple, Metal 2 on A11 — Imageblocks / Tile Shading / Raster Order Groups: https://developer.apple.com/videos/play/tech-talks/602/
The current feature tables put imageblocks, tile shaders, raster-order groups and quad-scoped permutes at Apple4, i.e. the A11 generation. This is important: the interesting experiment does not require targeting only the newest expensive iPhone. An old A11-class iPhone 8/X is already in the first generation with the distinctive programmable tile machinery.
Later Apple families add richer collectives: quad ballots, SIMD permutes, quad/SIMD reductions, floating-point atomics and other useful mechanisms. Record those as capabilities rather than assuming a single monolithic "Apple GPU".
Possible Apple fast path for the complex renderer
A concrete experiment could be:
Pass / stage A — local field evaluation
For each sample, compute some subset of:
f(z) or the internal complex representation;
phase;
log |f|;
derivative or cheap derivative surrogate;
local finite/overflow/underflow flags;
zero/pole proximity information when known analytically;
cheap regularity / conformality indicators.
Keep these intermediate quantities in an imageblock when the target allows it.
Tile stage — neighborhood reasoning
Use tile / quad / SIMD-local operations to inspect the neighborhood without exporting the entire intermediate field to general device memory.
Candidates:
estimate phase and log-modulus variation across the tile;
compare neighboring values for Cauchy–Riemann / conformality diagnostics;
vote/reduce whether the tile is ordinary or exceptional;
detect unresolved sign/phase winding or very large local expansion;
identify whether a known zero or pole influences this tile;
decide whether a second sampling level is warranted.
Exceptional-tile refinement
Only exceptional tiles pay for expensive work:
denser local samples;
a more accurate derivative;
higher precision where supported and useful;
singularity-aware antialiasing;
explicit zero/pole or winding analysis;
a more expensive holomorphic-preservation / metamorphic perturbation test;
whatever later mathematics proves to be the correct local oracle.
The exact criterion should come from the mathematics, not from GPU folklore.
Final color
Feed the resulting mathematical value/metadata into the same canonical Wegert/value-to-color semantics used by the portable path. Hardware specialization must not silently redefine the picture.
Cross-vendor reality
Do not record a false claim that Apple invented all of this.
Related mechanisms already exist elsewhere:
PowerVR: TBDR, tile buffers, pixel-local storage / transient-attachment techniques;
Arm Mali: tile rendering and Pixel Local Storage;
Qualcomm Adreno: tile rendering, GMEM, and newer explicit Vulkan tile-memory extensions;
NVIDIA/Tegra: warps + workgroup shared memory rather than the same TBDR interface;
AMD: waves + LDS;
Vulkan/SPIR-V: subgroup abstractions and shared memory across vendors.
What makes Apple worth a dedicated experiment is the combination and explicitness of imageblocks + tile shaders + raster-order groups + quad/SIMD collectives in one Metal model.
References for the cross-vendor side remain:
PowerVR TBDR: https://docs.imgtec.com/starter-guides/powervr-architecture/html/topics/tile-based-deferred-rendering-index.html
PowerVR on-chip / PLS guidance: https://docs.imgtec.com/starter-guides/powervr-architecture/html/topics/rules/do-use-on-chip-memory-efficiently-for-deferred-rendering.html
Arm Pixel Local Storage: https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/introducing-pixel-local-storage
Qualcomm tile memory: https://www.qualcomm.com/developer/blog/2026/05/high-performance-memory-extension-optimize-memory
Vulkan subgroups: https://www.khronos.org/blog/vulkan-subgroup-tutorial
Backend capability model
Keep these independent. Do not collapse them into a boolean isApple or hasTiles:
fragment derivatives / quad-neighbor access;
quad permute / vote / ballot / reduction;
subgroup/SIMD-group permute / vote / ballot / reduction;
subgroup width/query semantics;
workgroup/threadgroup shared memory;
barriers and memory-order constraints;
tile/pixel-local memory;
tile shader stage;
raster-order / overlapping-fragment ordering;
floating-point atomics;
Float16 / Float32 / wider-precision behavior;
divergence rules;
maximum tile/imageblock sizes and storage limits.
Prefer semantic operations in the compiler IR over vendor product names. Apple-specific lowering can then exploit the strongest path without infecting source programs.
Development policy
The project should continue developing against the devices actually available. Apple should be treated as an aspirational specialization target, not the definition of correctness and not a reason to stop supporting cheap hardware.
But this target is worth keeping alive precisely because it may be the hardware on which the holomorphic / meromorphic / metamorphic renderer can most closely realize the mathematically ideal local algorithm: cheap regular regions, aggressively examined exceptional tiles, minimal unnecessary memory traffic, and explicit local cooperation where the complex geometry calls for it.
The point is not to micro-optimize for Apple for its own sake. The point is that some Apple GPU mechanisms appear unusually well matched to the structure of the mathematics, and that is interesting enough to investigate seriously.
