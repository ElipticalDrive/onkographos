Thanks, @SpiritCroc for the proposal. I think fixing this lost-update-problem in account data and SSSS is a long overdue task. Thank you for taking this on!
I've read through your proposal and I'd like to discuss a higher level change that's why I am not leaving inline review comments; it makes it hard to describe the full picture.
Similar to @jevolk I am wondering why we shouldn't piggy back on the ETag system that http already provides for us: using the tag in the PUT as the If-Match header the server should reject updates that don't match. This also resolves the problem of older clients not implementing this accidentally overwriting it: if a revision is present on the server, the request must match it or the update will be rejected by the server.
When a client gets their PUT rejected with the specific 412 status, they should pull the latest version and re-apply their changes. The way this conflict resolution is done depends on the data in question and thus should be defined separately for each specified event type. But a common resolution could be that you only try to apply the changes, if the version isn't too old and just throw away your local copy if more than say 2 updates have happened.
Taking this further, in the spirit of the HTTP spec, why allow for this to be an opaque string that the client defines? In HTTP ETags are provided by the server. Yes, they are opaque strings (to the client), but the server can actually use them to hold information, like a hash or a counter. What, for example, if we defined that this holds an atomically increasing version counter? Every time an If-Match-guarded PUT is accepted, the version number is increased by exactly 1. As the homeserver is a central instance for this information the key is guaranteed to collision-free, provided by it and ensured to be correct. This also avoid update loops where two or more clients see a different etag, download the update, just set their tag and keep overwriting each others data. As this enforces a strict order between the requests and thus clearly describes what is a newer version: the one with the higher counter.
The homserver can easily extend the sync response by adding a version (or to stay within the http-wording ETag)-field on each account-data-event in the sync as well as just use the ETag-header on specific GET requests. For first time creation we can accept the If-Match to be 0 or be omitted, which allows older clients to still create an instance at first but not save updates to it.
For backwards compatibility we could also guard this behind a new path-version prefix and only reject updates on the old API path if a versioned update has been performed on the specific item.
WDYT?

ETag sounds like an interesting approach for sure. I don't know really how much of HTTP the Matrix spec should embrace, or try remain protocol-agnostic to a certain degree. It may be worth doing a separate MSC to weigh against in more detail. (We at Beeper are fine with using this as is for now, as we have it implemented and it works for what we want).
This also resolves the problem of older clients not implementing this accidentally overwriting it: if a revision is present on the server, the request must match it or the update will be rejected by the server.
I think this is not a problem but a feature. Say any client decides today to opt-in, having e.g. your avatar image overrides for a certain chat that happen to be stored in room account data, to be atomic. Then suddenly all other clients break in updating that image if they're not aware of this.
This also avoid update loops where two or more clients see a different etag, download the update, just set their tag and keep overwriting each others data.
Can you elaborate how this would happen with this current proposal?
For backwards compatibility we could also guard this behind a new path-version prefix and only reject updates on the old API path if a versioned update has been performed on the specific item.
Again, I think backwards compatibility should mean, old clients should be able to continue writhing arbitrary account data, and not get locked out by later clients writing something.
