Actual MeshExtraction output on data/sample: the mug's 1600 splats → a watertight mesh (3724 verts, 7448 tris) via voxel occupancy + marching tetrahedra. Rendered from the mesh produced by running Ingest→Segmentation→MeshExtraction.
Implements MeshExtractionModule (M0-6). A segmented cluster's splats are voxelized into a
union-of-ellipsoids occupancy field — each grid corner stores its smallest Mahalanobis distance
to any splat, thresholded at iso_std standard deviations — then isosurfaced with the existing
M0-4 marching-tetrahedra core. The grid is padded by the ellipsoid extent so the surface is fully
enclosed, which guarantees a watertight, manifold, deterministic Mesh.
Occupancy is a min-reduction (order-independent) scattered only into each splat's bbox, so it's
fast and deterministic. Near-transparent splats and degenerate requests are rejected as Result errors.
Tested by meshing the fixture's mug cluster (30k tris): asserts every edge is shared by exactly
two triangles (manifold + watertight), the mesh lands in the golden mug region, it's byte-identical
on re-run, and bad requests error out. ctest --preset engine-core is green (30/30).
Local build+test (engine-core): PASS.

Good question — short answer: no, it won't look like the real mug photo; it's a geometry proxy, not a beauty render.
Why it looks blocky (visible in the attached render): at voxel_size = 0.01 m on a ~4.5 cm-radius mug, the surface is coarsely sampled, so marching-tetrahedra gives a faceted/blocky surface, and the union-of-ellipsoids occupancy adds a slightly bumpy "shrink-wrap" look. It does capture the shape (cup + hollow + handle) and is watertight — which is exactly what M0-7 physics needs (a collision mesh, not a pretty one). No color/texture.
Where realism comes from: the Gaussians themselves carry color/appearance. The plan (build guide §1) is to render meshes for the physics/rearrangement view and render the splats for the realistic view — so "looks like the real mug" is the splat render's job, not the mesh's.
If we want the mesh itself closer to real: finer voxels (0.005 m → ~4× tris, smoother), Laplacian smoothing, and better thin-feature handling — that's precisely SPIKE-6 (non-convex/thin-object mesh quality), flagged for post-M0 hardening; the handle + thin walls are the hard cases.
Happy to commit a splats-vs-mesh side-by-side so you can see the difference directly (it'd show in the Files-changed tab since we're private now).

Exactly — you've got the loop right:
prompt ("put the mug on the other side") → Rearrange proposes a new pose → Physics validates it (drops to rest, stable, no overlap) → Render the rearranged scene, which should look like the original photo but with the mug moved.
How the mesh/splat split serves that: physics runs on the meshes (the watertight mug + table are collision geometry — that's what this PR builds). Once physics settles on the mug's new transform, we apply that same rigid transform to the mug's Gaussians (segmentation already tagged which splats are the mug) and re-render the splat scene → photorealistic, just rearranged. Mesh = where it can go; splats = what it looks like.
Honest catches on "looks like the original":
Hybrid splat+mesh rendering is hard and is deliberately deferred (SPIKE-5) — splat rasterizers don't natively composite with mesh depth. The v1 render path is meshes; the photoreal splat path comes later.
Disocclusion is the real gremlin: when the mug moves, the table surface under its old spot was never observed, and the mug's back may be unseen — so you get holes that need inpainting to look clean.
Baked lighting/shadows: the mug's captured appearance and its shadow don't automatically relight in the new position.
So the north star is "pixel-perfect, just rearranged"; the honest v1 will be "clearly rearranged, with some artifacts at the moved/vacated regions." M0 (this milestone) is proving the physics-proxy half of that — mesh → Bullet → a rendered PNG. The photoreal splat-rearrangement render is M1+.
