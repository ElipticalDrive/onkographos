Follow-up to #29 and the teapot-in-cube fix (f89eab4). Render order between overlapping/nested transparent objects is usable now but not correct — it is all held together by heuristics.
Root constraint
Every solid is MeshStandardMaterial { transparent: true, depthWrite: false } (geoCube/geoSphere/geoTeapot/parametricPlane). With no depth writes there is no depth-buffer occlusion between objects at all — correctness depends entirely on paint order (renderOrder, then Three's per-frame back-to-front distance sort). computeNestingRenderOrders (Scene3D.jsx) papers over this by pinning a camera-independent renderOrder from bounding-box containment.
Known imperfections
No real occlusion. A nested object is either always drawn before the container (container blends over it — current behaviour) or always after (floats on top). You can never get the geometrically-correct "see it through the near wall, it hides the far wall" look from paint order alone.
AABB approximation. Containment is world-AABB based. A small object sitting in the empty corner of a sphere's / teapot's AABB (outside the actual mesh) is treated as "nested" and ordered as if inside.
boxMostlyContains thresholds are eyeballed (centre-inside + smaller volume + ≥60% overlap). Objects near the threshold can still flip between scene rebuilds if geometry changes slightly.
Composites get one stamped renderOrder for the whole subtree. geo_show_point_on_object (annotated_object), the parametric-plane point+normal group, and the sphere centre marker are each a single top-level objects entry, so computeNestingRenderOrders never orders siblings within them — that order falls back to the unstable per-frame distance sort. Opaque markers happen to survive this because depth-test resolves them; a transparent-inside-transparent composite would flicker.
Non-nested overlap still flickers. Two genuinely overlapping (neither contains the other) transparent solids — e.g. two half-overlapping spheres — get renderOrder 0 and fall back to the distance sort.
Edge-line depthWrite inconsistency. The EdgesGeometry LineSegments on each solid keep depthWrite: true (the default) while the fill they're parented to is depthWrite: false, at the same stamped renderOrder.
Sentinel juggling. Things outside the objects array need hand-picked renderOrder sentinels (axes -100, grid -1, SelectionHighlight 9990+). Every new always-on-top / always-behind element has to be manually slotted into that band.
The effect only recomputes on [objects] identity change, not on in-place transform mutation (fine today because runAndSync rebuilds the array on every edit).
Directions for a proper fix
Weighted-blended OIT (order-independent transparency) — removes the sorting problem entirely for the translucent solids.
Depth pre-pass for solids (write depth from a cheap opaque pass, then blend) — gives real occlusion; needs care so overlapping translucents still show through each other where intended.
Split container rendering into back-face then front-face passes so a nested object slots between them.
Per-object depthWrite for a nested near-opaque object so it occludes the container's far side.
None are trivial; this issue is to track the design work.
