Implements the M0 Render mesh path. SPIKE-2 is resolved to a self-contained CPU
rasterizer rather than EGL/OSMesa/a hidden GLFW window — macOS has no EGL and
deprecated OpenGL, so any real-GL path makes the Linux and macOS CI runners diverge;
a CPU rasterizer keeps engine-core truly headless and dependency-free everywhere
(rationale in docs/spikes/SPIKE-2-headless-gl.md, mirroring the SPIKE-1 precedent).
RenderModule projects each SceneObject's triangles through the Camera
(p_cam = R·p_world + t, +Z forward), z-buffers, two-sided Lambert + ambient shades
from a fixed light, and writes an 8-bit RGB PNG. Eigen-only — no GL/glfw/glad.
PNG written by a dependency-free encoder (stored DEFLATE blocks + Adler-32/CRC-32),
so no zlib/libpng is added either. Deterministic: fixed per-object palette + light.
main.cpp already delegates to the Orchestrator; the end-to-end CLI render lands
with M0-9 (orchestrator lane).
Tested: 5 new tests in test_render.cpp (valid non-empty PNG with foreground, output
differs from an empty scene, byte-identical re-render, missing-size/empty-path
rejection). Verified the output decodes as a real PNG (CRCs + deflate) with correct
dimensions and foreground pixels. ctest --preset engine-core: 39/39 pass.
Local build+test (engine-core): PASS.
Generated by scripts/auto-loop.sh (task M0-8, lane render); CI will re-verify.

On the splat renderer timeline — the good news is we mostly don't build one:
gsplat (Apache-2.0) — the same library we use for reconstruction — already ships a CUDA splat rasterizer. So "real splat renderer" = wiring gsplat's rasterizer into a render step, not writing one from scratch.
Where it lives + what gates it:
It's Python/CUDA, so it belongs on the recon/GPU-service side, not the C++ engine (the language boundary is deliberate — engine stays CPU/laptop-testable). So it comes online when the recon service does.
Hard gates: (1) a CUDA GPU box, (2) the recon service stood up (SPIKE-4, M1) — which brings gsplat + CUDA online, (3) the Rearrange module producing the moved object's pose (M1).
Proposed sequencing (milestone-relative — we haven't committed calendar dates yet):
M1 — recon service (gsplat/CUDA online) + Rearrange v1 (mesh/physics-based). Photoreal render still text-only/mesh here.
End of M1 / early M2 — first splat render of a rearrangement: apply the physics transform to the moved object's Gaussians, re-rasterize the whole scene with gsplat from a camera. This is a small increment once the recon service exists, because the rasterizer is already right there. Result: "clearly rearranged, photoreal-ish, with disocclusion holes."
M2+ — the hard polish: disocclusion inpainting (holes where the object was), hybrid mesh+splat compositing (SPIKE-5), relighting/shadows. This part is genuinely research-y.
So: a basic photoreal rearranged render is realistically a late-M1/early-M2 item — gated mainly on the GPU service + Rearrange, not on renderer difficulty. Want me to write this into an M1 plan doc with the concrete task breakdown?

The clean answer: keep the whole scene as splats and move the object's Gaussians — so you never hybrid-composite mesh+splats. The mesh is only for physics; the render is 100% splats, rasterized by gsplat.
Pipeline (per moved object):
Segmentation already tags each Gaussian with an object_id → you have {object splats} + {background splats}.
Rearrange/physics gives a rigid transform T = (R, t) for the new pose.
Transform that object's Gaussians:
mean: μ' = R·μ + t
orientation: compose R into each Gaussian's rotation quaternion (this rotates the covariance)
scale, opacity: unchanged
SH color: rotate the SH coefficients by R — the easy-to-miss step. SH encodes view-dependent color in the object's original frame, so if the object rotates you must rotate the SH lobes (Wigner-D matrices) or highlights bake to the old orientation. (Pure translation → SH unchanged.)
Concatenate transformed-object + untouched-background Gaussians into one set.
Rasterize with gsplat's CUDA renderer from the chosen camera (the original capture camera, to match the source image).
What's missing / the hard parts:
Disocclusion inpainting — the gremlin. The background under/behind the object was never observed (occluded at capture), so moving it away reveals a hole with no Gaussians; likewise the object's unseen back faces are missing. Filling these plausibly (2D image inpainting, or 3D Gaussian infilling) is the genuinely hard, unbuilt piece — deserves its own spike.
Shadows/lighting — the object's appearance is baked from capture: it won't re-light, its old shadow stays baked into the background, and it casts none at the new spot. Relighting/shadow-synthesis is deferred.
Plumbing we don't have yet: the Rearrange module (produces T), the transform-Gaussians step (small — 3–4), and the gsplat render call on the GPU service (small integration).
Realistic v1 = steps 1–5 → "clearly rearranged, photoreal-ish, but with a hole where the object was." v2 adds disocclusion inpainting. Move-and-rasterize is small; inpainting is the real research item.
Want me to write steps 1–5 up as the M1 "splat re-render" task, with disocclusion inpainting as its own spike?
