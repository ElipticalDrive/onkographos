Abstract
Volume rendering based on 3D texture mapping is widely used in CT/MRI medical imaging, but constrained by GPU memory bottlenecks. While greedy packing strategies, which pack sub-textures into the first available empty space to minimise gaps, are effective in 2D texture mapping, adapting them to native 3D texture mapping introduces memory inflation due to the hardware constraint requiring uniform texture dimensions. This paper presents a CPU-GPU hybrid pipeline that mitigates this issue through a novel post-packing optimisation to minimise memory waste, with CPU pre-processing and GPU rendering. Experimental results demonstrate an average 30.9% reduction in memory usage compared to the default 3D texture mapping baseline, achieving memory-efficient rendering without compromising visual quality.

ABSTRACT
Volume rendering based on 3D texture mapping is widely used in CT/MRI medical imaging, but constrained by
GPU memory bottlenecks. While greedy packing strategies, which pack sub-textures into the first available empty
space to minimise gaps, are effective in 2D texture mapping, adapting them to native 3D texture mapping intro-
duces memory inflation due to the hardware constraint requiring uniform texture dimensions. This paper presents
a CPU-GPU hybrid pipeline that mitigates this issue through a novel post-packing optimisation to minimise
memory waste, with CPU pre-processing and GPU rendering. Experimental results demonstrate an average 30.9%
reduction in memory usage compared to the default 3D texture mapping baseline, achieving memory-efficient
rendering without compromising visual quality.
Keywords
Volume rendering, 3D texture mapping, medical imaging, graphics memory optimisation.
1. INTRODUCTION
Volume rendering is a powerful technique for visual-
ising scalar fields, commonly applied in medical im-
aging modalities such as Computed Tomography (CT)
and Magnetic Resonance Imaging (MRI). Among the
various approaches, 3D texture mapping [Cab94] has
become a standard technique for hardware-accelerated
visualisation. However, despite the processing power
of modern GPUs, memory capacity remains a major
bottleneck. As dataset resolutions increase, large vol-
umes often exceed the graphics memory limit, leading
to rendering failures.
To address these memory limits, prior research has ap-
plied techniques such as empty-space skipping along
with opacity thresholding [Kru03, Li03b] and geome-
try partitioning [Bet05] to discard voxels that don't
contribute to the final rendering. The efficiency of
these methods depends on how the remaining textures
are packed. Notably, Li and Kaufman [Li03a] demon-
strated a greedy strategy for 3D partitioning and 2D
packing. However, due to hardware limitations at the
time, they relied on 2D texture mapping, utilising
multi-texturing to bind two textures at once in order to
simulate trilinear interpolation.
In this work, we extend this greedy approach by lev-
eraging modern hardware capabilities to implement
the 3D texture mapping on a CPU-GPU hybrid pipe-
line. Offloading interpolation and rendering tasks to
the GPU makes it a more streamlined process; how-
ever, we discovered that directly applying the original
greedy packing to 3D textures introduces a new issue:
an increased memory requirement. This occurs be-
cause 3D texture objects require strict size alignment.
We solved this by proposing a post-packing optimisa-
tion. This mechanism analyses the initial greedy pack-
ing layout and reorganises the partitioned textures into
uniform size, where the slices are then stacked and up-
loaded to a 3D texture object for rendering. While this
optimised approach performs well on dense datasets,
we observed a noticeable memory performance degra-
dation when applied to sparse datasets. To address
this, a regular 2D packing approach was introduced,
which safeguards memory performance by detecting
potential memory overhead at an early stage and de-
ciding whether to bypass the greedy packing pipeline,
apply regular 2D packing instead, and directly send
the packed data to the GPU for regular 3D texture
mapping, thereby reducing processing time.

In volume rendering, both the shear-warp rendering
method and 3D texture mapping approaches aim to ac-
celerate the rendering of volumetric data. The shear-
warp method, as detailed by [Lac94, Lee22], is an ob-
ject-order algorithm that decomposes the viewing
transformation into three simpler steps: a 3D shear of
the volume data, a projection of the sheared volume
into a distorted intermediate image, and a final 2D
warp to produce the correct view. This factorisation
cleverly aligns voxel scanlines with pixel scanlines,
enabling efficient processing and the use of coher-
ence-based optimisations. Conversely, 3D texture
mapping treats the volume dataset as a 3D texture that
is sampled by view-aligned proxy geometry.
To improve rendering performance and reduce alias-
ing, a standard mipmapping strategy is applied to the
final retained textures. This creates a discrete Level of
Detail (LOD) system using pre-computed, down-sam-
pled versions of the texture atlas [LaM99]. During ren-
dering, the hardware automatically selects the appro-
priate resolution level based on the object's distance
from the camera to reduce computation time and min-
imise aliasing. While this increases memory usage
slightly due to storing lower-resolution textures, the
trade-off is justified by the improvement in overall
rendering speed and visual stability.
Aiming for higher memory efficiency, texture-based
methods evolved to partition volumes into smaller
sub-volumes or "bricks" [Wei04]. For sparse datasets,
Kähler et al. [Kah03] extended this by using Adaptive
Mesh Refinement (AMR) hierarchies to cluster rele-
vant data into tight, axis-aligned bounding boxes,
which are then compacted into a single volume using
a 3D packing algorithm.
While these earlier bricking techniques relied on geo-
metric packing constraints, alternative modern ap-
proaches have introduced advanced hierarchical struc-
tures to bypass empty space and stream data. Crassin
et al. introduced GigaVoxels [Cra09], which relies on
an adaptive !!- tree (typically an octree) to manage a
"brick pool" stored in texture atlases. By employing a
ray-guided streaming approach that dynamically loads
only the visible bricks needed for the current screen
resolution into GPU memory, GigaVoxels achieves >
99% active VRAM reductions.
For time-varying and highly sparse topologies,
Museth introduced VDB [Mus13], a hierarchical data
structure sharing characteristics with B+ trees, featur-
ing large branching factors to compactly encode dy-
namic sparse volumes. Building on this, Hoetzlein de-
veloped GVDB [Hoe16], extending the VDB topology
with a memory pooling design tailored for GPU com-
pute and ray tracing. Complementing these software-
driven approaches, Morrical et al. [Mor20] utilised
NVIDIA’s RTX cores to accelerate spatial searches
via hardware-based ray tracing. They employ a
Bounding Volume Hierarchy (BVH)—a more flexible,
geometry-aligned alternative to standard octrees—op-
timised for hardware traversal. While they navigate a
trade-off by swapping simple point queries for com-
plex ray-primitive intersections to gain hardware
speed, they manage peak memory overhead via prim-
itive splitting. An alternative to such hierarchical
structures is spatial hashing; Lefebvre and Hoppe
demonstrated Perfect Spatial Hashing [Lef06], which
losslessly packs sparse data into dense tables, bypass-
ing geometric bin packing entirely.
Similarly to how these modern structures isolate im-
portant data, Kauker et al. [Kau16] addressed sparsity
using a linked-list data structure that explicitly stores
only non-empty voxels, thereby eliminating memory
overhead for empty space. This structure supports ef-
ficient sparse volume rendering by limiting traversal
to relevant data points. In a related manner, the pro-
posed method begins by evaluating dataset sparsity to
identify non-empty voxels, subsequently applying a
2D greedy packing approach that addresses the legacy
constraints of 3D packing by packing their corre-
sponding pixels into memory-optimised 2D slices.

proaches globally cluster sparse data instead; how-
ever, as noted by Beyer et al. [Bey15], they inherently
suffer from localised memory padding waste due to
"ghost voxel" duplication at brick boundaries: adding
a standard 1-voxel overlapping boundary to a small 8!
brick inflates its memory footprint by ~95% (expand-
ing from 512 to 1000 voxels). While Perfect Spatial
Hashing [Lef06] completely bypasses these geometric
padding wastes, its perfect hash precomputation re-
quires a static sparsity structure. Meanwhile, modern
Streaming and Hierarchical Methods (GigaVoxels
[Cra09], VDB [Mus13], GVDB [Hoe16]) offer unpar-
alleled scalability and dynamic topology handling by
restricting the active GPU footprint, but achieving this
requires maintaining highly complex data manage-
ment infrastructure for multi-level page tables and ad-
dress translations during ray-marching.
Beyond architectural considerations, 2D rectangle
packing is an NP-Hard optimisation problem. While
exact solvers [Hua12] guarantee optimal bounds, their
massive computational cost makes them impractical
for real-time systems. Conversely, simple Shelf algo-
rithms run extremely fast but waste significant surface
area whenever a rectangle's height does not match the
shelf ceiling [Jyl10]. To resolve this spatial ineffi-
ciency, Jylänki [Jyl10] identified the Maximal Rectan-
gles Best Short Side Fit (MAXRECTS-BSSF) algo-
rithm as a top-tier variant for empty-space manage-
ment. However, translating these theoretical 2D pack-
ing algorithms into a practical 3D volume rendering
pipeline requires a specialised approach.
Our proposed Greedy-based approach bridges this gap
by applying fast 2D packing strategies directly to the
non-empty voxels. By compacting isolated non-empty
voxels into 2D texture slices, we explicitly bypass the
severe 3D texture padding waste of AMR structures
and the complex decoding overheads of out-of-core
streaming.
3. PROPOSED SOLUTION
We propose two approaches for 3D texture-based vol-
ume rendering: a main greedy-based approach and an
alternative regular 2D packing approach. They both
apply the pre-processing from applying a configured
density threshold and seed map, and choosing which
strategy to adopt is defined during the sparse check
section (Fig. 1).

3.1 Greedy-based Approach
The greedy-based approach consists of greedy-parti-
tioning and greedy-packing before sending the data to
the GPU for subsequent volume rendering. To accel-
erate rendering via empty-space skipping, our method
partitions the volume by adapting the box-growing al-
gorithm and 2D greedy-packing proposed by [Li03a].
While their approach partitions voxels based on both
density and gradient magnitude, the approach intro-
duced in this paper applies only to the alpha value as
density magnitude from the original dataset to create a
more streamlined process.
3.1.1 Seed Map
The algorithm begins by creating a binary "seed map"
of the volume. A voxel is marked as a seed if its alpha
value is above a user-defined density threshold, indi-
cating it is part of a non-empty region, or the set of
"important voxels". Voxels below this threshold are
considered empty regions and labelled as "unim-
portant voxels". As illustrated in Fig. 2, these seeds are
further sent to the Sparse check stage for evaluation to
decide which rendering approach to adopt.
Figure 2: Separating seed voxels by density threshold.
3.1.2 Sparse Check
A fast-pass sparse-check algorithm is derived from the
seed map. The seed map has each voxel labelled as ei-
ther an empty or a non-empty region. They are now sep-
arated as foreground and background, background
voxels introduced sparsity (Fig. 3 (a)), and they are then
compared to the user-defined sparsity threshold (Fig. 3
(b) ). This result serves as the starting point: if the cur-
rent dataset sparsity is less than the user-defined spar-
sity threshold, the greedy-based approach is selected;
otherwise, regular 2D packing is utilised.

3.1.3 Greedy Partitioning
The core of the algorithm iterates through each seed
voxel in the map. For each unassigned seed, a new
1x1x1 box is initialised. This box is then expanded us-
ing a greedy partitioning algorithm by evaluating the
profit of extending the box by one unit in six scenarios
along the 3 axes, x: left, right, y: up, down and z: for-
ward, backward (Fig. 4). The most profitable direction
is chosen for expansion. In our context, "profit" is de-
fined by the number of new seed voxels that would be
encompassed by the expansion versus the number of
empty voxels. The process continues until no further
expansion yields a positive profit. Once a seed voxel
is included within a box, it is marked as "taken" and
removed from the seed map to ensure that subsequent
boxes do not overlap (Fig. 2). This process results in a
set of variably-sized bounding boxes that tightly en-
capsulate the significant regions of the volume, as
shown in Fig. 5. This collection of boxes forms the ba-
sis for the subsequent texture packing and rendering
stages.

3.1.4 2D Greedy Packing
To efficiently compact the partitioned bounding boxes
into a memory-optimised texture atlas, our implemen-
tation adopts a 2D slice-based approach over direct 3D
packing. The process operates on a per-slice basis: for
each 2D slice of the volume, intersections with the 3D
density boxes produce a list of 2D rectangles contain-
ing the relevant texture data. These rectangles are then
packed into a compact 2D texture. Finally, all the in-
dividually packed slices are stacked to form the final
3D texture object for rendering on the GPU.
The 2D packing is handled by a recursive greedy al-
gorithm. It begins by sorting all rectangles for a given
slice in descending order of area, placing the largest
one first to define the initial packed area. Each subse-
quent rectangle is then placed into one of the remain-
ing empty regions. To find the best fit, the algorithm
recursively evaluates four placement scenarios for
each adjacent gap to the current packed area (green dot
regions in Fig. 6): (a) place right, (b) place top, (c)
place right-transposed, and (d) place top-transposed.
The chosen placement is the one that minimises the
growth of the slice's total bounding area. Finally, the
coordinates and orientation of each packed rectangle

3.2 Regular 2D Packing
Following the sparse check outlined in Section 3.1.2,

4. Post-packing Optimisation
While the 2D greedy packing algorithm is effective at
compacting individual slices, its local optimisation
leads to a global issue: it typically produces a mix of
tall (height > width) and wide (width > height) slices.
Since the dimensions of a 3D texture are determined
by the maximum width and height across all slices,
this mixture requires significant padding, leading to
wasted memory. Our post-packing optimisation ad-
dresses this issue by standardising slice orientations.
The algorithm analyses the set of packed slices, deter-
mines the majority orientation (either tall or wide), and
rotates the minority group by 90 degrees to match it.
This rotation step is followed by a repacking process
applied only to the affected slices, which reduces the
required padding, shortens post-processing time, and
produces a more memory-efficient final 3D texture.
The algorithm first pre-classifies each slice as square-
like or imbalanced based on a user-defined aspect ratio
threshold, denoted as ratio. It then evaluates two lay-
out strategies—forcing all imbalanced slices to be tall
or wide—and selects the one with the smallest overall
texture area.

5. VOLUME RENDERING
This final stage of the rendering pipeline takes the re-
tained texture, applying mipmapping [LaM99] to im-
prove rendering performance, and displays the result-
ing volume. It represents the culmination of the parti-
tioning, packing, and post-packing pipeline.
Mipmaps are pre-computed, down-sampled versions
of the main texture at sequentially lower resolutions
(Fig. 11). When the volume is viewed from a distance,
the GPU samples from a smaller, more appropriate
mipmap level instead of the full-resolution texture.
This reduces aliasing artefacts, resulting in a smoother
visual result and improved rendering speed
Figure 11: An illustration of mipmap levels, from the
full-resolution texture (L0) to lower-resolution ver-
sions (L1, L2, L3).
With all pre-processing and optimisations complete,
the final 3D texture atlas and its associated lookup ta-
bles are uploaded to the GPU. The volume is then ren-
dered slice-by-slice. For each slice, a proxy polygon is
drawn, and a fragment shader uses the lookup tables
to sample the correct texels from the packed texture.
The rendering outputs that are obtained by combining
the efficiencies gained from empty-space skipping, re-
duced texture size, and mipmapping are illustrated in
Fig. 12. To ensure a consistent and fair evaluation of
memory performance, mipmapping was enabled for
both the baseline approach and our proposed methods
throughout all experiments.

6. EXPERIMENTAL RESULT
The software stack utilised in the development of our
CPU-GPU hybrid pipeline adopted the WebGL 2.0
graphics API, which natively supported the OpenGL
ES 3.0 specification for hardware acceleration within
the browser environment. The system was imple-
mented using JavaScript (ES6+), while all shaders—
including vertex and fragment programs—were devel-
oped in GLSL ES 3.0 and compiled at runtime. Using
this implementation, we evaluated our approach
against a 30 fps real-time performance constraint, fol-
lowing established targets for interactive applications
[Ake18]. This threshold served as our primary bench-
mark; to indicate this clearly, results in Table 2 meet-
ing or exceeding this limit are bolded, while Figs. 13-
15 include a solid red horizontal line to indicate the 30
fps requirement. Results comparing our baseline with
the proposed approach are summarised in Table 2.
Due to architectural differences, legacy hardware re-
sults are restricted to a representative subset of origi-
nal datasets. The M3 Pro, the primary platform for this
paper, reaches the hardware limit of 120 fps on the
base datasets. Fig. 13 shows the performance for
scaled stress-test configurations, demonstrating that
the empty-space skipping technique improves render-
ing performance and scales directly with the density
threshold. The fps consistently improves as more empty
voxels are skipped. In stark contrast, the A14 Bionic
(Fig. 14) shows remarkable stability. Its fps remains
largely flat across all thresholds, suggesting that its per-
formance is not primarily limited by fragment pro-
cessing and is less sensitive to geometric complexity.
The Nvidia 1050M (Fig. 15), a discrete GPU, exhibits
the most volatile performance. For some datasets, in-
creasing the threshold and thus the box count (Fig. 18)
leads to a significant decrease in fps; consequently, the
results reveal a strong dependency on hardware archi-
tecture, with varying levels of efficiency observed
across the proposed greedy-based pipeline.

7. ANALYSIS
As summarised in Table 1, existing volume rendering
techniques navigate hardware memory constraints
with varying trade-offs. The proposed CPU-GPU hy-
brid pipeline offers a streamlined alternative, along-
side an additional strategy specifically designed for
sparse data handling. As the subsequent evaluations
will demonstrate, this structural advantage enables the
proposed approach to achieve an average memory re-
duction of 30.9% against baseline 3D texture mapping,
while maintaining real-time performance on modern
unified memory.
Building upon this Foundation, this section interprets
the causes for observed differences in rendering speed,
memory efficiency, and visual quality. Whereas Li
and Kaufman’s approach [Li03a] achieves an average
of 3.1:1 compression rate on gradient textures, which
are combined with uncompressed density textures for
final rendering. This paper's enhanced greedy-based
rendering avoids memory increase by processing the
density texture only, ensuring any optimisation keeps
memory usage below the baseline. Furthermore, we
evaluate the performance of regular 2D packing ren-
dering as an alternative to the greedy-based rendering.
7.1 Greedy-based Rendering
7.1.1 Rendering Performance
The experimental results reveal that the pipeline's per-
formance is fundamentally tied to the hardware archi-
tecture, particularly the memory model. The distinct
behaviours of the unified memory systems (M3 Pro,
A14 Bionic) versus the discrete GPU (Nvidia 1050M)
highlight a critical trade-off in this hybrid approach.
The M3 Pro and A14 Bionic platforms, which feature
a unified memory architecture, are largely insensitive
to the number of partitioned boxes. With the CPU,
GPU, and RAM integrated on a single chip, the cost
of transferring geometry data is minimal. As a result,
they benefit directly from the primary optimisation—
empty-space skipping—without being significantly
penalised by the CPU-intensive partitioning and the
increased number of draw calls.
In contrast, the performance on the discrete Nvidia
1050M GPU illustrates the pipeline's main bottleneck.
Figs. 18 - 19 indicate a clear inverse relationship be-
tween the number of boxes generated and the resulting
frame rate. When partitioning yields a high number of
individual boxes, the computational cost of the hybrid
approach becomes apparent. The combined impact of
CPU-bound partitioning, geometric data transfer, and
excessive draw calls eventually outweighs the benefits
of rendering fewer fragments. Nawfal and Ali [Naw18]
proposed a possible alternative for addressing this bot-
tleneck. Their approach utilised CUDA to execute the
required computational operations concurrently on the
GPU. These pre-processing tasks, such as partitioning
and packing, could be migrated directly onto the de-
vice which, when executed natively, allows the geo-
metric data to remain entirely resident in video
memory. This avoids the performance drop by never
requiring the CPU-to-GPU memory transfers during
the rendering pipeline.

powerful corrective measure, it cannot always fully

for larger or sparser datasets, GPU memory limits may
still be reached, as evidenced by the execution failures
in Fig. 13 and 15. To address datasets that exceed the
GPU memory limit, an alternative approach was pro-
posed by [Xue15] using an on-demand streaming
strategy. Their semi-adaptive partitioning approach
first divides the entire volume into smaller, independ-
ent sub-blocks of varying sizes, each guaranteed to fit
within the GPU's memory. These blocks are organised
hierarchically into a Binary Space Partitioning (BSP)
tree [Vid08] which, when traversed according to the
viewpoint, allows only the currently visible blocks to
be loaded from external storage. This avoids memory-
related failures by never requiring the entire dataset to
be resident in the GPU at once.
Another potential approach involves the two-stage
process of Block Trimming and Texture Block Merg-
ing [Ton99]. In this approach, the first stage analyses
each partitioned data block to find the tightest bound-
ing box of its non-empty "object voxels," effectively
discarding large, empty surrounding regions. These ir-
regularly sized blocks are then merged into denser
"texture chunks" via horizontal and vertical merge op-
erations to optimise memory usage. However, to main-
tain high rendering performance while avoiding a sig-
nificant increase in pre-processing time, we introduce
regular 2D packing rendering as a direct alternative.
To reduce the initial data footprint, future iterations
could integrate lossy compressions such as the Dis-
crete Wavelet Transform (DWT), Tensor Approxima-
tion (TA) or native hardware block compression for-
mats—specifically Block Compression 7 (BC7), as it
natively accommodates the alpha channel required by
the volumetric datasets. However, because this pipe-
line explicitly targets medical imaging, these tech-
niques must be approached with caution; as noted in
the state-of-the-art survey by [Rod14], aggressive
thresholding or block truncation can eliminate critical
diagnostic details such as subtle tissue boundaries.
Alternatively, recent developments in modern
graphics APIs, such as Vulkan and Direct3D 12 offer
a lossless hardware-level solution through sparse tex-
ture binding [Bil12, Obe12]. This mechanism decou-
ples the dataset's virtual volume size from its physical
memory footprint. By utilising hardware-managed
page tables, the GPU natively performs virtual-to-
physical address translation, ensuring that physical
memory pages are only allocated for the specific sub-
regions actively being sampled.
To address the scalability issues currently facing on
larger datasets, a practical direction would be to incre-
mentally integrate these API-level sparse texturing
features, building directly upon the proposed alterna-
tive regular 2D packing approach.

8. CONCLUSION
This work presented a memory-reduction pipeline for
volume rendering based on 3D texture mapping. By ex-
tending the greedy packing algorithm [Li03a] with a pro-
posed post-packing optimisation algorithm, this method
achieved an average of 30.9% memory savings without
any negative impact on perceived image quality.
Furthermore, we addressed the observed memory effi-
ciency loss in sparse datasets by introducing the regular
2D packing approach. This alternative is designed specif-
ically to prevent memory overhead in scenarios where
the greedy algorithm is less effective, and this strategy
eliminates any scenarios where a memory saving wasn't
achievable.
Future work will focus on addressing larger datasets that
currently exceed memory limits by integrating semi-
adaptive partitioning, utilising hierarchical subdivision to
enable view-dependent data streaming, as well as reduc-
ing the pre-processing time of the greedy-based approach
by migrating tasks to the GPU to leverage parallelism,
thereby reducing computational cost and improving
graphics memory efficiency.

Jan 2013
Eric Huang
Richard E. Korf
We consider the problem of finding all enclosing rectangles of minimum area that can contain a given set of rectangles without overlap. Our rectangle packer chooses the x-coordinates of all the rectangles before any of the y-coordinates. We then transform the problem into a perfect-packing problem with no empty space by adding additional rectangles. To determine the y-coordinates, we branch on the different rectangles that can be placed in each empty position. Our packer allows us to extend the known solutions for a consecutive-square benchmark from 27 to 32 squares. We also introduce three new benchmarks, avoiding properties that make a benchmark easy, such as rectangles with shared dimensions. Our third benchmark consists of rectangles of increasingly high precision. To pack them efficiently, we limit the rectangles' coordinates and the bounding box dimensions to the set of subset sums of the rectangles' dimensions. Overall, our algorithms represent the current state-of-the-art for this problem, outperforming other algorithms by orders of magnitude, depending on the benchmark.

State-of-the-Art in GPU-Based Large-Scale Volume Visualization
Article
May 2015
COMPUT GRAPH FORUM
Johanna Beyer
Markus Hadwiger
Hanspeter Pfister
This survey gives an overview of the current state of the art in GPU techniques for interactive large-scale volume visualization. Modern techniques in this field have brought about a sea change in how interactive visualization and analysis of giga-, tera- and petabytes of volume data can be enabled on GPUs. In addition to combining the parallel processing power of GPUs with out-of-core methods and data streaming, a major enabler for interactivity is making both the computational and the visualization effort proportional to the amount and resolution of data that is actually visible on screen, i.e. ‘output-sensitive’ algorithms and system designs. This leads to recent output-sensitive approaches that are ‘ray-guided’, ‘visualization-driven’ or ‘display-aware’. In this survey, we focus on these characteristics and propose a new categorization of GPU-based large-scale volume visualization techniques based on the notions of actual output-resolution visibility and the current working set of volume bricks—the current subset of data that is minimally required to produce an output image of the desired display resolution. Furthermore, we discuss the differences and similarities of different rendering and data traversal strategies in volume rendering by putting them into a common context—the notion of address translation. For our purposes here, we view parallel (distributed) visualization using clusters as an orthogonal set of techniques that we do not discuss in detail but that can be used in conjunction with what we present in this survey.

State‐of‐the‐Art in Compressed GPU‐Based Direct Volume Rendering
Article
Sep 2014
COMPUT GRAPH FORUM
Marcos Balsa Rodriguez
Enrico Gobbetti
José A. Iglesias Guitián
Susanne K. Suter
Great advancements in commodity graphics hardware have favoured graphics processing unit (GPU)-based volume rendering as the main adopted solution for interactive exploration of rectilinear scalar volumes on commodity platforms. Nevertheless, long data transfer times and GPU memory size limitations are often the main limiting factors, especially for massive, time-varying or multi-volume visualization, as well as for networked visualization on the emerging mobile devices. To address this issue, a variety of level-of-detail (LOD) data representations and compression techniques have been introduced. In order to improve capabilities and performance over the entire storage, distribution and rendering pipeline, the encoding/decoding process is typically highly asymmetric, and systems should ideally compress at data production time and decompress on demand at rendering time. Compression and LOD pre-computation does not have to adhere to real-time constraints and can be performed off-line for high-quality results. In contrast, adaptive real-time rendering from compressed representations requires fast, transient and spatially independent decompression. In this report, we review the existing compressed GPU volume rendering approaches, covering sampling grid layouts, compact representation models, compression techniques, GPU rendering architectures and fast decoding techniques.

VDB: High-resolution sparse volumes with dynamic topology
Article
Jul 2013
ACM T GRAPHIC
Ken Museth
We have developed a novel hierarchical data structure for the efficient representation of sparse, time-varying volumetric data discretized on a 3D grid. Our “VDB”, so named because it is a Volumetric, Dynamic grid that shares several characteristics with B+trees, exploits spatial coherency of time-varying data to separately and compactly encode data values and grid topology. VDB models a virtually infinite 3D index space that allows for cache-coherent and fast data access into sparse volumes of high resolution. It imposes no topology restrictions on the sparsity of the volumetric data, and it supports fast (average O (1)) random access patterns when the data are inserted, retrieved, or deleted. This is in contrast to most existing sparse volumetric data structures, which assume either static or manifold topology and require specific data access patterns to compensate for slow random access. Since the VDB data structure is fundamentally hierarchical, it also facilitates adaptive grid sampling, and the inherent acceleration structure leads to fast algorithms that are well-suited for simulations. As such, VDB has proven useful for several applications that call for large, sparse, animated volumes, for example, level set dynamics and cloud modeling. In this article, we showcase some of these algorithms and compare VDB with existing, state-of-the-art data structures.
