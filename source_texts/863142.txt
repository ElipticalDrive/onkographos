Goal
Carry pinned gsplat projected Gaussian depth into the project-owned Direct Evidence CUDA boundary with exact row alignment and fail-closed validation, while leaving authoritative RGB and the current P/N/V/boundary semantics unchanged.
Owning runtime and repository seams
Companion/CUDA only. The implementation is expected to touch the narrow vertical slice around:
selection-service-companion/src/selection_service_companion/gsplat_renderer.py;
selection-service-companion/src/selection_service_companion/direct_gaussian_evidence.py;
selection-service-companion/src/selection_service_companion/cuda/direct_evidence.cu;
selection-service-companion/tests/test_direct_gaussian_evidence.py;
applicable locked-renderer/readiness tests.
Do not add a Browser protocol field or a standalone depth artifact.
Frozen input contract
The pinned gsplat projection metadata supplies meta["depths"], aligned one-to-one with the projected rows consumed by means2d, conics, opacities, evaluated colors, flatten_ids, and the render-row Stable-ID mapping.
Before dispatch, require:
CUDA float32, contiguous, finite values;
shape [1, N], where N == meta["means2d"].shape[1];
the same CUDA device as every other Direct Evidence tensor;
no implicit cast, CPU copy, padding, sorting, or row reordering.
A missing, malformed, non-finite, mismatched, or cross-device depth tensor fails with the existing renderer/Direct-Evidence failure taxonomy before publication.
Identity migration
Rotate all identities whose meaning changes:
Direct Evidence ABI version;
checked-in CUDA source digest;
runtime build ID and extension name;
readiness/capability expectations and fixtures.
Do not rotate the production Gaussian Evidence artifact schema in this stage because no published P/N/V field changes.
TDD sequence
Add failing Python validation tests for missing, wrong-shape, wrong-dtype, non-contiguous, non-finite, and wrong-device depth.
Add a projected-row fixture that proves depth row i reaches CUDA row i, including a nontrivial flatten_ids order.
Update the C++/CUDA signature and loader call.
Keep the kernel read-only with respect to depth in this stage.
Re-run existing authoritative RGB, P/N/V, boundary-contact, cancellation, source-lock, and readiness tests.
Acceptance criteria
Every Direct RGB/Evidence invocation passes validated projected depth through Python → extension binding → CUDA.
Invalid depth fails before any RGB/Evidence result can publish.
The row-alignment fixture detects any accidental reorder or broadcast.
Existing RGB bytes/digests and P/N/V/boundary outputs remain unchanged within their existing exact/tolerance contracts.
Source/build/readiness identities are self-consistent and a stale compiled extension cannot advertise Ready.
No Browser payload, Candidate binding, Runtime Profile capability requirement, or user-facing behavior is added.
Verification
Accepted execution evidence is recorded in the Issue review thread. It includes the targeted supported-GPU Direct Evidence suite with no #49 skips, the complete Companion suite, the full repository test gate, locked runtime/GPU identities, and lint.
Failure and rollback
This is an all-or-nothing ABI migration. Python and CUDA versions may not be mixed. Any incompatibility leaves Direct Evidence unavailable and preserves prior Views, Stable Masks, Evidence, and Candidate state. Rollback is a source/ABI identity revert, not a permissive compatibility branch.
Non-goals
No M0/M1/M2 accumulation, CWED validity policy, S1 Seed, classified Negative Evidence, Consensus readout, Browser depth image, or production policy cutover.

Review — commit 597c83d4ac61f6ac8ffbab274443306a485f97c3
结论：暂不关闭 #49。 实现方向整体正确，但有两个阻断性的验收缺口；另有一个非阻断性能备注。
做得好的部分
ABI 已从 supersimplat-direct-evidence-abi/v1 旋转到 /v2，CUDA source digest、runtime build ID 和扩展名一起旋转。
meta["depths"] 在 authoritative RGB 与 Direct Evidence 两条入口都检查了 CUDA、float32、contiguous、[1,N]、同设备和 finite，失败发生在结果发布前。
Python → pybind → CUDA launch 的参数链已经接通，kernel 在本阶段明确保持只读，不改变 RGB/P/N/V/boundary 语义。
已加载 extension 的 __name__ + abi_version 会参与 readiness/load 校验，旧 extension 不会继续被当作当前 ABI 使用。
Browser 侧只旋转既有 runtime identity 期望，没有新增 depth payload、Candidate 字段或 Runtime Profile capability。
Blocking 1 — 当前 row-alignment fixture 没有证明 compiled CUDA boundary 内的行对应关系
test_projected_depth_rows_reach_the_compiled_abi_without_reordering 通过 RecordingExtension 在 调用 compiled extension 之前 捕获 Python 参数，并检查：
depth tensor data pointer/stride 未变化；
flatten_ids == [1, 0]；
在 Python 中按该索引读取可得到 [29, 11]。
这能捕获 Python wrapper 中的 copy/reorder/broadcast，但不能捕获 C++ binding 或 kernel launch 中对 depth pointer/row 的错误连接。当前 CUDA kernel 又显式执行 (void)projected_depths，所以即使 compiled 路径内部把 depth 行接错，所有现有输出仍会相同，测试不会失败。
而 #49 的验收条件明确要求：
projected-row fixture proves depth row i reaches CUDA row i and detects accidental reorder or broadcast.
请补一个 compiled-boundary 可观察 的 sentinel fixture。实现方式可以是 test-only ABI probe/checksum/echo，或其他不会改变生产 RGB/P/N/V 的 compiled assertion；关键是 [11,29] 与非平凡 flatten_ids=[1,0] 的对应关系必须由编译后的 C++/CUDA 路径实际读取并验证，而不只是在 Python 调用点验证。
Blocking 2 — 缺少 #49 要求的实际验证证据
该 commit 当前没有 GitHub status checks，也没有关联 workflow run；#49 下此前也没有测试记录。因此目前只能确认测试代码被加入，不能确认以下验收事实真的在支持的 GPU 上成立：
CUDA extension v2 可以实际编译和加载；
projected-row fixture 在 compute capability 8.9 上通过；
authoritative RGB bytes/digests 与 P/N/V/boundary 输出未变化；
stale build/readiness fail-closed；
完整 Companion suite 没有回归。
请在本 Issue 附上至少以下证据：
针对 selection-service-companion/tests/test_direct_gaussian_evidence.py 的实际 GPU 测试命令与完整结果；
rtk npm run test:companion 的结果；
因本提交同步修改了 Browser runtime-ID expectations，补充相关 TypeScript 测试结果，建议至少 rtk npm test；
GPU 型号、compute capability、CUDA/PyTorch/gsplat identity，以及加载出的 ABI/runtime build ID；
明确列出 row-alignment、invalid-depth、unchanged RGB/P/N/V/boundary 测试均为 executed/passed，而非 skipped。
Non-blocking note — finite validation 当前产生两次完整 GPU reduction/synchronization
同一个 depth tensor 先在 Python _validated_projected_depth() 中执行一次：
```
torch.isfinite(depths).all().item()
```
随后 C++ binding 又执行一次：
```
torch::isfinite(projected_depths).all().item<bool>()
```
这会为每次 Direct RGB/Evidence 调用增加两次全量 depth scan 和 host synchronization。它不是本次 correctness blocker，但建议在后续修订中合并为一次权威 finite check，或至少把额外成本明确带入 #53 的 locked-GPU latency/VRAM qualification；不要让重复同步无意中成为长期 production cost。
修复 Blocking 1 并补齐 Blocking 2 的实际证据后，我可以再次 review；在此之前 #49 保持 open。
