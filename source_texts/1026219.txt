Issue: #305
Summary
Plane builders populated dxplane, but geometric queries read separate fields containing stale or uninitialized coefficients. Both builders now copy the calculated normal/distance before deriving sign bits, preserving their original mathematical behavior.
The follow-up integrates the accepted D1 correction, retains all three clear-rectangle regressions and registers the two original plane checks as game.presentation.plane_*. The probe.* executable commands remain unregistered aliases. Approximate-value failures now report their calling line and actual/expected values.
Design and compatibility
The production fix remains four assignments. The 36-byte x86 layout, direct-field camera construction, normal scaling, winding, ray conventions, resource formats and host interface are unchanged. No allocation or RNG call is added by the builders. This is the functional D7 correction separated from #97's post-baseline quality work.
CalcVis uses the corrected geometry only for temporary calculations and Debug markers. Its shadow flags are discarded, its group-visibility array remains zero-cleared, and its local storage record is never saved. It does not rewrite maps or generate Release visibility output. Run time, Debug diagnostics and the Debug flyer's computed target can change. Skipped non-land plane construction is a separately recorded pre-existing caller limitation.
Validation
Current clean revision: pinned full MinGW Debug/Release standalone builds, 806 engine checks per configuration (1,612 total), plus all thirteen focused clear-rectangle/plane checks repeated in each configuration.
Desktop-dependent native-process/current-desktop cases were excluded. ctest -N -R probe selects zero registered cases.
Eight current plane cases compiled against isolated header copies in Debug/Release: 80 executions. Complete candidate passes 8/8; removing all coefficient copies, only normals, or only distances leaves 2/8 passing; omitting builder sign-bit updates leaves 3/8. Failures identify the actual call sites and expected/actual values. Production source and registered binaries were not changed by the controls.
Repository, branch, whitespace, UTF-8 and local documentation target/anchor checks pass. The integrated D1/D7 conflict resolution preserves both registration sets.
Earlier revision d327d3b passed 3,184 full checks across all four local MinGW Debug/Release EXE/DLL profiles. Those results describe that revision; supported MSVC and current-head DLL validation remain with this revision's CI. Native rendered appearance, CalcVis run time/Debug markers, flyer input and original-host playtests remain under NV-03 / #191. Complete baseline acceptance remains separate.
Documentation
Corrects the CalcVis effects and the previous map-rewrite claim, reconciles D1/D7 catalog/index/ledger records and positional-audio evidence, and records the remaining non-land caller investigation without expanding the production fix.

Reviewed d327d3b against its merge base, the current dev 01f9dd8. All 13 checks pass on this head.
The fix adds four assignments so that both SPlane builders copy the coefficients they calculate into the norm/dist fields that every query reads, before deriving sign bits. With the production hunk reverted, six of the eight new cases and both plane probes fail in Debug and Release, and three wrong fixes are caught. The correction restores what the builders did before the union was removed. Its only live consumers are the CalcVis tool and a Debug-only flyer command, and no persisted or Release gameplay output changes. I found nothing blocking. The guide and ledger say that CalcVis output can change and that CalcVis rewrites its input map, and neither is true (Should-fix 1). The two plane probes are registered under probe.* names, unlike every earlier promoted probe (Should-fix 2).
The defect exists at the base. At 01f9dd8 the builders called D3DXPlaneFromPointNormal/D3DXPlaneFromPoints into dxplane and then UpdateSignBits (Math3D.hpp:90-99). UpdateSignBits and every query read only norm, dist and signbits: IsOnSide, CalcPointDist, Distance, BoxSide and FindIntersect (Math3D.hpp:105-163 at this head). SPlane() is empty (:88), so a built plane answered queries with whatever those fields already held, and its sign bits came from that stale normal. Until a2dcad3 the fields were a union with dxplane (Math3D.hpp:66-74 at a2dcad3^), so the original engine's builders did produce consistent queries. The four copies (:92-93, :100-101) restore that behavior without bringing back the union.
The fix is complete.
Writers of dxplane: only the two builders. No production code reads dxplane (the only reads outside the builders are in tests), so after the copies the two representations cannot diverge on any path that is read.
Planes built directly: the camera frustum planes set norm/dist and call UpdateSignBits (MatrixCamera.cpp:732-758) without using a builder. Their readers (MatrixCamera.cpp:768-797, :991; MatrixCamera.hpp:384-398) are unchanged. direct_fields pins this path and also shows that UpdateSignBits leaves dxplane untouched.
Ordering: sign bits are derived after the copy. An aliased normal argument (BuildFromPointNormal(plane, p, plane.norm)) is still read before it is overwritten, because D3DX writes only dxplane and the copy comes afterward. reuse_and_alias covers this.
Layout: no member is added. D3DXPLANE (16) + D3DXVECTOR3 (12) + float (4) + byte with 3 bytes of padding is 36 bytes, aligned to 4. The layout case pins the size, alignment and four offsets with static_assert (plane_tests.cpp:134-137), so MinGW and the MSVC CI jobs both compile-check it. SPlane appears in no storage record, resource format or host structure. It is held only in process memory, by the camera, the CalcVis temporaries and one Debug local.
Cost: four float copies per build. Neither caller is on a per-frame path in Release.
Every caller, and what changes. These are the only calls of either builder. Commented-out calls are at MatrixMap.cpp:1189-1190, MatrixFlyer.cpp:796-797 and MatrixEffectWeapon.cpp:390-391.
CMatrixMap::CalcVis triangle planes (MatrixVisiCalc.cpp:287-288): two planes per land cell, read by the silhouette-edge filter (:300, :312, :326 with IsOnSide; :306, :319, :333 with norm !=) and by BuildShadowFor through the edge copies (:140-141).
BuildShadowFor shadow plane (MatrixVisiCalc.cpp:154, :157): read at :178 to mark shadowed terrain points.
What CalcVis produces: the shadow flags live only in the temporary aps buffer. They are read only by the Debug sphere markers (:216-222), and the buffer is freed at :422. The DATA_GROUPS_VIS record is filled from m_GroupVis, which is freshly zero-cleared at :346 and not written between :346 and :402-419. The local CStorage is never saved: the file has no Save call, and ~CStorage is defaulted (CStorage.hpp:316). This has been true since the initial import. The correction therefore changes no saved map, no m_GroupVis contents and no Release output. What changes:
The set of silhouette edges is now computed from real geometry. Before the fix it was decided by heap contents, because STempCalcs comes from HAlloc (:238-239).
CalcVis may run longer, since BuildShadowFor is O(source points x edges x map points). I did not measure this.
In Debug, the green edge cones (:146) and shadow spheres (:219) now show real geometry.
CalcVis entry points:
EXE map-argument startup (MatrixGame.cpp:113-127) computes, appends to calcvis.log and exits without running the loop, so its Debug markers are never drawn.
The Debug F7 key (MatrixFormGame.cpp:1634-1637, inside the _DEBUG && !_RELDEBUG block from :1582).
The CALCVIS console command (DevConsole.cpp:133-138, :167). The console is activated from cheats.cpp:83, :88.
Debug flyer targeting (MatrixMap.cpp:1216-1223, under #ifdef _DEBUG at :1209): hp is an uninitialized local, so at the base FindIntersect used stack garbage. Depending on that garbage, it either did not retarget or retargeted to an arbitrary point. Now, with KA_AUTO held (right mouse by default, MatrixConfig.cpp:274) outside the interface and a flyer as the active object, the flyer targets the point where the mouse ray crosses the horizontal plane at the flyer's height. Release and the DLL compile this block out. I did not establish whether ordinary play can make a flyer the active object.
The tests drive the production header. matrixgame_plane_tests includes Math3D.hpp and calls the real builders and queries. Before construction, every field is set to a distinct sentinel (plane_tests.cpp:14-21), so an omitted copy fails deterministically and no uninitialized read becomes a golden value. coefficients requires both representations and the sign bits to agree (:22-32).
Box sides: box_octants compares BoxSide with an independent eight-corner classification for all eight sign combinations, including inclusive contact (:67-92).
Intersections: intersection_contract pins the parallel and near-parallel rejection (and that it leaves the output untouched), direction scaling, negative parameters and origins on the plane (:93-107).
Scaling: non-unit normals keep their scale (:110-111).
All checks are MG_CHECK, which throws in Release (test_support.hpp:23-27). The cases need no world, window or device and touch no global state. The labels are geometry rendering (tests/CMakeLists.txt:818-825).
