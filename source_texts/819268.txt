The underlying data structures of the Sparse Voxel Octree do not lend themselves particularly well to runtime modification, as one of the main features of the design is that it is sparse, so empty spaces use very little memory. The data structures of the octree are extremely compact and designed to be statically allocated prior to generation (this is done with a two step rasterisation process).
The issue with this is that it becomes very hard to update the octree data at runtime without a lot of very awkward/expensive copies/moves.
There are a couple of approaches I am considering to support runtime updates:
1 - Mark all the voxels in the first pass rasterise as blocked, which will cause every voxel in the bounding volume to include data down to leaf nodes.
Upside : This approach means that updating blocking data at runtime is fairly trivial, as we can ignore the higher level octree layers and just flip the bits on the leaf nodes we need to update.
Downside : This completely undoes all the memory benefits of the sparse voxel octree. All empty space is fully rasterised. Pathfinding queries are much more expensive.
Potentially still a very viable option for simpler games. May work for larger worlds on less limited hardware. Pathfinding costs possibly mitigated by Jump Point Search or other optimisations.
2 - A selective option, adding support for dynamic volumes inside a bounds volume. Functions the same as above, but only forces a limited region of the greater bounds volume to be rasterised.
Upside : Doesn't waste loads of memory on empty spaces. Gives LDs control on which parts of the volume need to be dynamic. Makes handling registration/detection of moving elements much cheaper.
Downside : More complex. Limited scope of 'dynamic' area. Still loses efficiency of the sparse octree to some degree.
3 - Crude approach. Simply update another copy of the octree data in the background, and swap it out when generation is complete.
Upside : Simple from an engineering standpoint.
Downside : Significant runtime memory allocation. Double memory usage.
Summary
I think I've convinced myself to implement multiple strategies. Probably starting with Option 3 as it is the simplest. Although 2 is tempting. I will flesh out technical designs further.
