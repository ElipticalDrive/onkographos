# Evaluation of Acceleration Structures for Ray Tracing Performance

A performance comparison of four spatial acceleration structures — Brute Force, Uniform Grid, KD-Tree, and Bounding Volume Hierarchy (BVH) — used to speed up ray-object intersection testing in ray tracing.


## Why I Built This

My background is robotics, not computer graphics — so it's fair to ask why this project exists. The honest answer: **spatial acceleration structures aren't really a graphics topic, they're a general computational geometry problem**, and the exact same structures show up constantly in robotics:

- **Collision detection** for motion planning uses BVH and KD-trees to avoid checking a robot's geometry against every obstacle in a scene, the same way ray tracing avoids checking every ray against every object.
- **LIDAR and point-cloud processing** (nearest-neighbor search, obstacle clustering) relies on KD-trees and grid-based spatial partitioning.
- **SLAM and occupancy mapping** use grid- and tree-based spatial structures to keep map queries fast as the environment scales.

Ray tracing is simply a clean, well-benchmarked domain to study *how* these structures behave under different spatial distributions (spread out vs. clustered vs. dense) — insight that transfers directly to deciding which spatial structure to reach for in a robotics pipeline. This project was a way to build and benchmark that intuition from first principles rather than just treating these structures as a black box in a robotics library.

## Problem Statement

Ray tracing requires testing rays against every object in a scene to determine what they intersect. A brute-force approach checks every object for every ray, and computational cost grows rapidly as scene complexity increases — this quickly becomes a bottleneck for any scene with a non-trivial number of objects.

## Objective

- Reduce the number of intersection computations required per ray
- Improve overall rendering performance
- Compare multiple acceleration methods across different scene distributions to understand which structures perform best under which conditions

## Methods Implemented

| Method | Approach |
|---|---|
| **Brute Force** | Baseline approach — checks every ray against every object in the scene with no spatial optimization |
| **Uniform Grid** | Divides the scene into equally sized cells; rays only test against objects in the cells they pass through |
| **KD-Tree** | Recursively partitions space along alternating axes, creating a binary tree that narrows down candidate objects quickly |
| **BVH (Bounding Volume Hierarchy)** | Groups objects into a hierarchy of bounding volumes based on spatial proximity, rather than partitioning empty space itself |

## Insights

- Structured, evenly distributed scenes benefit the most from spatial hierarchies in general — every method outperforms brute force by a wide margin.
- BVH adapts best to clustered and dense object distributions, staying stable even as scenes get less uniform — because it partitions based on object proximity rather than fixed spatial regions.
- Grid-based methods struggle as object density becomes non-uniform, since empty or sparsely populated cells still cost traversal time.
- Tree depth and node-splitting strategy noticeably affect KD-tree performance, and its advantage narrows in dense, clustered scenes compared to BVH.

## Conclusion

- Brute force is computationally expensive and scales poorly — this is the baseline every other method needs to beat.
- KD-tree substantially improves performance through space partitioning, but its advantage shrinks as object distributions become denser and less uniform.
- **BVH consistently delivered the best overall performance** across every tested scene type, including the scenarios where the other structures degraded.
- Uniform grid performance is highly dependent on how uniformly objects are distributed in the scene — it's the most scene-sensitive of the four methods.

## Running It

<!-- Inferred from your build files — please replace with your actual invocation/flags -->

**Linux / macOS (Makefile):**
```bash
make
./bin/<executable_name>
```

**Windows (Visual Studio):**
1. Open `base_freeglut.sln` in Visual Studio
2. Select the `x64` platform configuration
3. Build the solution (Ctrl+Shift+B)
4. Run the generated executable (output typically lands in `x64/` or `bin/`)

**Reproducing the benchmark results above:**
1. Run the compiled ray tracer with each of the four scene configurations (spread, clustered-corner, dense cluster 1, dense cluster 2)
2. For each scene, run once per acceleration structure (brute force, uniform grid, KD-tree, BVH)
3. Collected metrics (render time, intersection count, rays/sec) are written to `results/`
