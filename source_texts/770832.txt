What?
Adds static zstd dictionary support to turbo-persistence and enables a 64 KiB dictionary for the TaskData family.
Family
Compression
Infra
LZ4
TaskMeta
LZ4
TaskCache
LZ4
TaskData
zstd3 + static dictionary
Also adds zstd_dictionary, a small offline tool that trains a replacement dictionary from copied cache directories and prints an LZ4/zstd3/new-dictionary comparison.
Why?
TaskData dominates persistent cache size and contains recurring serialized structures derived from JS/CSS and module graphs. A static dictionary gives zstd useful matches immediately.
Corrected held-out evaluation groups small values into production-like 8–12 KiB compression units:

The raw byte savings equal 9.65% of the copied holdout cache-directory size. Timings are single-process diagnostics; real Next.js builds are the final validation.
A separate TaskMeta experiment did not justify replacing LZ4: dictionary-zstd was 26.55% smaller, but 4.01× slower to encode and 4.61× slower to decode.
How?
CompressionConfig supports LZ4, zstd3, and zstd3 with a static dictionary.
Meta files record the zstd dictionary ID and validate it at open time.
Writers reuse prepared dictionary compressors; readers reuse a thread-local decompressor.
sst_inspect accepts multiple source dictionaries keyed by dictionary ID.
The checked-in dictionary and replacement command live in src/database/taskdata-dictionary/.
```
cargo run -p turbo-persistence --release --bin zstd_dictionary -- \
  --family 2 \
  --source-dictionary turbopack/crates/turbo-tasks-backend/src/database/taskdata-dictionary/taskdata.zdict \
  --output /tmp/taskdata.zdict \
  path/to/cache-a path/to/cache-b
```
The command compares against its training inputs, so its output is diagnostic rather than held-out evidence.
Verification
```
cargo test -p turbo-persistence -- --test-threads=1
cargo test -p turbo-persistence --all-targets --no-run
cargo test -p turbo-tasks-backend
cargo fmt --all -- --check
cargo clippy -p turbo-persistence -p turbo-tasks-backend --all-targets -- -D warnings
```
The production corpus used 194 test/production files, yielding 204 training and 38 held-out TaskData caches. The checked-in artifact is 65,536 bytes with zstd dictionary ID 1166300072.

Train TaskData zstd dictionary on real-world apps

The previous dictionary was a proof of concept trained against the
`test/production` test fixtures. Retrain it against 34 real-world Next.js
applications from the `next-benchmarks` corpus (9.88 GB of TaskData values),
excluding private applications and the synthetic bundler fixtures.

Measured on cold `next build` cache sizes with `sst_inspect`, plain `Zstd3`
versus `Zstd3WithDictionary`:

- training set (32 apps): -5.8% TaskData bytes, -6.2% value bytes
- held out (5 apps):      -4.5% TaskData bytes, -4.9% value bytes, -3.2% cache

Every application improved, by between 2.7% and 13.3%. The held-out
applications were never seen during training, so -4.5% is the figure to
expect in practice.
