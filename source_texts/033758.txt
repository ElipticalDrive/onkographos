Abstract
Layered 3D Gaussian Splatting (3DGS) enables progressive novel-view synthesis, but large scenes such as city models remain gigabytes in size even after
state-of-the-art compression, making full pre-download impractical under bandwidth limits or sub-second startup targets. Progressive delivery transmits content
incrementally according to viewing demand, but existing systems plan it for
each user independently. When several users explore the same scene concurrently, as in virtual tours or XR classrooms, their viewpoints differ yet depend
on the same lower-layer blocks, so per-user delivery fetches the same prerequisites from the origin once per user, duplicating shared upstream traffic. Edge
caches and request aggregation remove part of this duplication, but they act
only after requests exist: they neither plan which blocks a group should fetch
jointly nor respect rendering dependencies, so a refinement block can arrive
before its required lower layers and remain unusable. We present GaussCast,
a dependency-aware delivery framework that structures layered 3DGS scenes
as versioned cell–layer–chunk retrieval blocks with explicit dependency metadata. An edge proxy aggregates short-horizon user demand, fetches a shared
base of widely needed prerequisite blocks once upstream, and spends the remaining budget on per-user supplements; admission enforces dependency closure
1
under per-window byte budgets and user rendering deadlines. We implement
GaussCast over Information-Centric Networking and describe mappings to
HTTP/CDN and relay deployments. In trace-driven evaluation with multi-user
sessions derived from real 6DoF navigation traces, GaussCast reduces shared
edge-to-origin upstream traffic by 26% and time-to-first-frame by 27%, and
improves viewport quality and fairness over per-user baselines, with gains growing as cross-user overlap increases. Implementation and evaluation artifacts are
publicly available at https://github.com/ulen2000/gausscast-sim.

1 Introduction
3D Gaussian Splatting (3DGS) represents scenes as explicit Gaussian primitives,
enabling high-quality novel-view synthesis at interactive rates [1]. Compression techniques—including anchors, spatial hierarchies, pruning, quantization, and entropy
coding [2–11]—have substantially reduced scene sizes. For instance, HAC++ [10]
compresses certain scenes to under 10 MB, making full download feasible for many
single-room or object-centric scenarios. Compression alone, however, does not eliminate the delivery challenge for all deployment contexts. Large-scale environments—city
models, multi-room building interiors, and detailed outdoor scenes—remain in the
gigabyte range even after state-of-the-art compression [4, 5, 12]. For such scenes, downloading the full compressed model before interaction is impractical under bandwidth
constraints or sub-second startup targets; for example, mobile Extended Reality (XR)
over a 10–20 Mbps link cannot pre-fetch a multi-hundred-megabyte scene while targeting sub-second startup. Progressive delivery addresses this by transmitting scene
content incrementally according to predicted viewing demand. Recent layered 3DGS
systems show that progressive transmission improves the viewing experience when
bandwidth, latency, or scene scale preclude full pre-download [12–14].
Existing progressive 3DGS systems optimize single-user streaming. We address a
complementary problem that arises when multiple users concurrently access the same
scene—common in virtual tours, collaborative design reviews, XR classrooms, and
digital-twin exploration. Although users render different viewpoints, they frequently
depend on overlapping lower-layer scene data. Per-user delivery sends these shared
prerequisites separately for each user over the shared upstream path (the edge-to-origin
link between the client-facing cache tier—such as a content delivery network (CDN)
point of presence, campus gateway, or wireless backhaul aggregation point—and the
content origin), wasting upstream bandwidth, increasing congestion, and degrading
startup latency and quality for all users.
Figure 1 illustrates the setting. Users explore different regions but require common
base-layer blocks. We call the coarse lower layers that make a region renderable its
prerequisites, and the higher layers that add detail its refinements. We define the shared
retrieval base (or shared base ) as the set of prerequisite and closure blocks the proxy

problem, but do not coordinate which blocks to fetch jointly. More critically, they
ignore rendering dependencies: a refinement that arrives on time but ahead of its
required lower layers is still unusable, wasting bandwidth without improving rendered
quality.
GaussCast addresses these challenges through dependency-aware shared
retrieval. It does not propose a new codec or renderer; instead, it operates on existing layered 3DGS representations and coordinates their delivery across users. Key
design principles include: (1) structuring scenes as versioned, named retrieval blocks
with explicit dependency metadata, (2) aggregating short-horizon user demand at an
edge proxy to identify reusable shared prerequisites, (3) enforcing dependency closure during admission—the set of prerequisite blocks a refinement depends on—so a
block is scheduled only when its missing dependencies fit the budget and meet rendering deadlines, and (4) using digest-linked verification to keep per-block cryptographic
overhead practical. These principles enable the proxy to build a shared retrieval base
of reusable prerequisites fetched once upstream, then allocate remaining budget to
user-specific supplements, while ensuring that admitted content is both dependencycomplete and renderable before its deadline. The core of GaussCast is this planner.
ICN naming, digest-linked verification, cache retention, and optional parameter tuning are implementation mechanisms that support the planner but are not required for
the abstraction.

1. We formulate multi-user layered 3DGS delivery as a dependency-aware shared block
retrieval problem, separating how a scene is compressed from how its blocks are
scheduled, shared, and cached across concurrent users.
2. We design a versioned retrieval-block representation that keeps three concerns
independent: naming structure for transport, rendering-dependency graph for
usefulness, and digest-linked structure for verification. This separation allows
GaussCast to work with any layered 3DGS pipeline without requiring changes to
the codec or renderer.
3. We develop a closure-aware planner that builds a shared base and per-user supplements under cache, deadline, byte-budget, and fairness constraints. The planner
admits a block only with its missing prerequisites, and weights view-dependent
value per user, so that admitted content is both renderable before its deadline and
relevant to the user’s viewpoint. We prove that admitted blocks satisfy dependency
completeness, and add optional online parameter tuning.
4. We implement and evaluate GaussCast with layered 3DGS scenes and multiuser sessions constructed from real six-degrees-of-freedom (6DoF) traces. Compared
with per-user delivery, GaussCast reduces shared edge-to-origin upstream traffic
by 26%, lowers time-to-first-frame by 27%, improves viewport quality by 0.97 dB
PSNR, and improves fairness, with gains growing as cross-user overlap increases.
2 Problem Scope
GaussCast addresses scenarios where three conditions hold: (1) multiple users access
the same scene version with sufficient lower-layer overlap, (2) full pre-download is
infeasible due to scene scale, bandwidth limits, or sub-second startup targets, and (3)
users join with cold caches or access updated scene versions. Table 1 characterizes
target and non-target deployments.
The benefit depends on measurable overlap. Before comparing delivery policies, we
therefore characterize the workload itself: across the multi-user windows constructed
from real 6DoF traces, concurrent users share a substantial fraction of lower-layer
4
blocks (Section 7), which shows that the reuse opportunity GaussCast targets is
present rather than assumed. When overlap is low, GaussCast allocates a small
shared budget and prioritizes per-user supplements rather than forcing counterproductive sharing. GaussCast operates at delivery time above the codec and renderer.
Compression reduces per-block size; shared retrieval reduces how many times each
compressed block crosses the shared upstream path when users join concurrently
or when updates invalidate cached content. CDN and Information-Centric Networking (ICN) caches remain effective; GaussCast adds rendering-aware priorities and
dependency enforcement.
3 Related Work
3.1 3DGS Representation and Compression
3DGS represents scenes with explicit Gaussian primitives for real-time view synthesis [1]. Subsequent work improves its structural organization and scales it to larger
scenes. Scaffold-GS uses anchor-guided organization [2]; Octree-GS and hierarchical
3DGS provide level-of-detail hierarchies [3, 5]; CityGaussian and related systems handle large-scale scenes through spatial partitioning and distributed training [4, 15, 16].
These methods provide the spatial and hierarchical structure that delivery systems
build upon.
A parallel line of work reduces storage and transfer cost. LightGaussian applies
pruning, distillation, and quantization [6]; Compressed 3D Gaussian Splatting uses
sensitivity-aware clustering [7]; HAC and HAC++ achieve strong compression through
context modeling and entropy coding, reducing certain scenes below 10 MB [8, 10]; and
EAGLES targets compact representations with lightweight encoding [9]. Progressive
compressed bitstreams further enable on-demand partial access [17], and recent surveys review this rapidly growing literature [11]. These advances make individual scene
blocks smaller, but they do not address how blocks are scheduled, shared, and cached
when many users access the same scene. GaussCast is complementary: it assumes
blocks are already compressed and coordinates their delivery across concurrent users.
For small scenes whose full compressed model fits the startup budget, pre-download
remains simpler; GaussCast targets cases where scene scale, bandwidth constraints,
or strict latency requirements make progressive multi-user delivery necessary.
3.2 Progressive and Adaptive 3DGS Delivery
Progressive 3DGS delivery systems are closely related. LapisGS builds cumulative
layered 3DGS for adaptive streaming and progressive rendering [13]. L3GS creates layered representations and scheduling algorithms for bandwidth-adaptive delivery [12].
LTS maps multi-layer 3DGS to DASH-style streaming [14]. Recent work studies viewport prediction, bitrate adaptation, saliency-aware tiling, and dynamic 3DGS video
delivery [18–20]. These systems demonstrate that progressive delivery and adaptive
scheduling improve single-user experience. When several users access the same scene
concurrently, however, two constraints appear that single-user schedulers were not
5
designed to handle. First, concurrent users request overlapping lower-layer prerequisites at nearly the same time, so independent per-user scheduling repeatedly transfers
the same blocks over the shared upstream path. Second, a refinement carries no rendering value until its prerequisites arrive, so admitting it early wastes bandwidth without
improving quality. GaussCast addresses this coordination problem with dependencyaware planning: a block is admitted only when its missing prerequisites fit the budget
and meet rendering deadlines for all users who need it.
3.3 Multi-User Immersive Media Delivery
Multi-user immersive systems exploit overlap, caching, and multicast. For 360-degree
video, tile-based streaming and edge caching exploit viewport overlap [21–24]. For
point clouds and volumetric video, systems study adaptive delivery, edge computation, multiview transcoding, and multi-user sharing [25–28], as recent surveys of the
volumetric pipeline summarize [29]. These works demonstrate that multi-user content creates shared delivery opportunities and that independent per-user scheduling
scales poorly. However, they do not enforce rendering dependencies: a 360◦ tile or
point-cloud segment carries visual value as soon as it arrives, whereas a 3DGS refinement block remains unusable until its prerequisite lower layers are present. Layered
3DGS differs in two ways that make dependency-unaware sharing insufficient. First,
the rendering value of a 3DGS block is view-dependent: the same block contributes
differently to different viewpoints through projected footprint, depth ordering, and
alpha compositing, unlike a 360-degree tile whose contribution to a covering viewport
is fixed. Second, a block becomes useful only when its lower-layer prerequisites are
already available, so a block cannot be treated as an independently useful unit the way
a video tile can. GaussCast reflects both properties in its planner: it estimates peruser, view-dependent value when ranking candidates, and it admits a block together
with its missing prerequisites as one unit, so that admitted content is both relevant
to the user’s viewpoint and renderable before its deadline.
3.4 Name-Based Delivery, Caching, and Verification
Information-Centric Networking (ICN), including Named Data Networking (NDN),
retrieves content by name and supports in-network caching, request aggregation, and
data-centric security [30–33]. GaussCast uses these mechanisms because retrieval
blocks are immutable within a scene version and can be fetched by name. Interest
aggregation through the Pending Interest Table (PIT) records downstream interfaces
for outstanding Interests with the same name, forwards one Interest upstream, and
returns the arriving Data to all recorded interfaces [31, 34]. This mechanism benefits
GaussCast when several users, planned in the same cycle, request the same Data
name before the first copy returns: the network then performs one upstream fetch
instead of many. Interest aggregation and in-network caching, however, only decide
how to satisfy requests that have already been issued. They do not decide which blocks
a group of users should request together, whether a block’s lower-layer prerequisites
have been scheduled, or whether a refinement can still arrive before its rendering
deadline. These are the decisions GaussCast makes at the edge proxy, above the

4.1 Retrieval Blocks and Dependencies
We consider a static or slowly changing layered 3DGS scene published under a
versioned namespace. Within one version, retrieval block names and content are

immutable. Updates create new versions or delta manifests. The scene is decomposed
into retrieval blocks R = {r1 , r2 , . . . , rN }. We denote each block r ∈ R as a tuple
r = (c, l, k ), where c is a spatial cell identifier, l is a representation layer (indexed
from 0), and k is a chunk index (indexed from 1). Each block has size s(r), a content
digest, and a hard dependency set D(r). A retrieval block is a transport, cache, and
scheduling unit; it does not correspond to a semantic object in the reconstructed scene.
Layered 3DGS representations require lower layers to be decoded before higher
layers can be rendered. Progressive delivery must therefore track block dependencies:
a refinement layer provides no rendering value until its prerequisite base layers arrive.

5 GaussCast Design
5.1 Overview
GaussCast separates edge planning from data transfer. Edge planning uses visibility,
layer priority, dependencies, deadlines, cache state, and fairness. The retrieval path
fetches named blocks, aggregates repeated requests when supported, caches returned
data, and verifies content. Figure 2 shows the end-to-end workflow: the publisher
produces versioned retrieval blocks and dependency metadata offline; the edge proxy
receives per-user demand summaries, computes a shared base plus user-specific supplements (the per-user block sets scheduled after the shared stage, predominantly
refinements together with any prerequisites only that user needs) under a closureaware admission test, and issues a retrieval plan; the retrieval path fetches the named
blocks, collapses concurrent requests for the same block, fills the edge cache, and verifies content before rendering. The central mechanism is the two-stage closure-aware
planner illustrated in Figure 3; the publishing, naming, and verification machinery
exists to support the planner. The remainder of this section follows these three stages
in order.
5.2 Offline Publishing
The publisher starts from a layered 3DGS scene produced by an existing pipeline [12–
14]. The publisher partitions the scene into cells, layers, and chunks. In our prototype,
a retrieval block typically contains 0.5–2 MB of coded Gaussian data. Large blocks
can be segmented for transfer while scheduling and caching remain at block granularity. GaussCast separates three structures. The naming structure identifies retrieval
blocks and manifests. The rendering dependency graph defines when a block becomes
useful. The authentication structure defines how a block is verified. This separation
keeps the retrieval path simple: the retrieval path fetches named bytes, while the proxy
reasons about rendering prerequisites. A representative namespace is:

5.7 Optional Parameter Controller
GaussCast does not rely on learning: the default system runs the deterministic
closure-aware planner with fixed parameters and is dependency-safe on its own. We
optionally evaluate a lightweight controller that adjusts only high-level knobs—the
shared-budget ratio, the dependency/cost/congestion weights, and the cache-retention
and supplement thresholds—as bandwidth, overlap, or cache pressure drifts. Its inputs
are aggregate signals (group size, mean lower-layer overlap, cache occupancy, queue
backlog, mean RTT and throughput, miss and late ratios, and the fairness index), and
it is trained with proximal policy optimization (PPO) [40]; the exact action, state,
and reward are given in Appendix B. The controller never selects individual blocks,
changes names or digests, bypasses cache-version checks, or admits a block that fails
the closure and deadline tests. It is therefore a tuning aid rather than a core contribution, and it adds only a few percent on top of the deterministic planner; we report
its effect separately in Section 7.11 and Appendix E.

If the delivery mechanism supports request aggregation, concurrent requests for
the same shared-base block can be collapsed into one upstream fetch. In the ICN
prototype, this collapse is Interest aggregation through the PIT: the first Interest
for a name is forwarded upstream, later downstream Interests with the same name
are recorded while the first Interest is pending, and the returned Data satisfies the
recorded downstream requests. Because a 0.5–2 MB block is carried as multiple Data
17

block is shared across users only when their Interests for the same segments coincide
while pending. Reuse for users that arrive after Data has returned is provided by the
content store rather than by the PIT entry itself. Aggregation complements rather than
replaces the planner: it merges identical outstanding names, while the planner decides
which prerequisites should be requested together, what to retain for slightly later
users, and whether a refinement can meet its deadline. If the delivery mechanism lacks
request aggregation, the proxy can still fetch each planned block once and redistribute
it through an application-level relay.
6.2 Cache Retention
The cache policy favors reusable prerequisite blocks. It is compatible with standard
cache freshness and validation rules; the proxy only changes retention priority among
blocks that are valid for the requested scene version and digest. Freshness, version,
expiry, and digest checks are applied before retention scoring so that reuse cannot
silently mix stale blocks from different scene versions. The retention score combines
near-future demand, membership in the shared base, dependency centrality, age, and
size, with all terms normalized over the currently cached set:
Hx (r) = β1 ρx (r) + β2 1[r ∈ Bx ] + β3 cent(r) − β4 age(r) − β5 s(r).
(25)
The policy is asymmetric: lower-layer prerequisite blocks are kept more aggressively
than transient higher-layer refinements. The cache-policy sensitivity study separates
this bias from generic least-recently-used retention.
6.3 Digest-Linked Verification
The publisher signs the root manifest and, when useful, subtree roots. Lower-level
manifests and data segments are authenticated through digest links or Merkle paths.
This avoids one public-key verification per small block. Static digest hints are generated by the publisher, and plan-carried hints are attached by the proxy to reduce
manifest traversal. A hint cannot create a new trust path. If a hint is stale, missing, or malicious, the client falls back to standard digest-linked traversal; security is
unchanged and only latency can increase. Figure 4 shows the trust boundary.

7 Experimental Evaluation
The evaluation answers five questions: (1) does the workload contain reusable lowerlayer blocks; (2) does GaussCast reduce upstream traffic, startup delay, and late
misses; (3) does closure-aware planning improve useful delivery compared with sharing
without closure checks; (4) how do the gains change with overlap, concurrency, compression, dependency sparsity, and prediction horizon; and (5) are planning, control,
and verification overheads practical?
19
Workload characterization first establishes whether sharing opportunity exists;
end-to-end results then measure user-visible benefit; ablations separate closure-aware
planning from generic caching and request aggregation; sensitivity tests identify when
the system should fall back to simpler delivery; and overhead studies check that
block-level retrieval is practical. For the main traffic, latency, and quality metrics, we
report the mean and standard deviation over all paired samples. Each configuration
is replayed over 60 trace windows and 10 network seeds (600 paired samples); unless
noted otherwise, the differences between GaussCast and each baseline reported for
a given metric (upstream bytes, TTFF, late miss, and PSNR) are statistically significant at p < 0.01 under a paired Wilcoxon signed-rank test with Holm correction
for multiple comparisons. Because the test pairs GaussCast against each baseline
window by window, the reported gains reflect a consistent per-window improvement
rather than an average inflated by a few high-overlap windows.
7.1 Prototype and Setup
Prototype.
We implement GaussCast on Mini-NDN [43] with NFD forwarders [44]. The default
topology is a three-tier tree with one publisher, one core forwarder, two aggregation
forwarders, four edge forwarders (which provide transport and same-name request
aggregation but do not partition the planning domain), and clients attached to the edge
layer. The edge tier hosts one planning proxy that runs Algorithm 1: in the notation of
Section 4, its user set Ux contains all concurrent clients of the session (16 by default),
so demand aggregation, shared-base decisions, and the edge-cache state span the full
group rather than only the clients attached to a single edge forwarder; the forwarders
below the proxy provide transport and same-name request aggregation. Upstream
bytes are measured on the shared edge-to-origin link between this cache tier and the
publisher. The sharing domain of every reported number is therefore explicit: the
upstream reduction comes from planner-level reuse and same-cycle aggregation within
this one domain, not from incidental cache overlap between independently planned
edges. Deployments that partition clients into several independent planning domains
would retain the intra-domain gains and add only whatever reuse their upstream
caches provide; we do not evaluate such federation. We also implement an HTTP/CDN
baseline in Mininet [45] with the same link capacity, propagation delay, and cache
budget to enable fair comparison.

Rendering and quality measurement.
The PSNR, SSIM, and LPIPS values in Table 9 are measured on rendered viewport

layers of every visible cell present, that is, the complete converted layered representation and not the original uncompressed training model—which we take as the
per-frame reference image, and once from the set of blocks that the policy under test
has actually delivered and made renderable by that frame’s deadline. The reported
metrics compare the policy’s rendered frame against this reference, so they capture the
visual cost of missing or late refinements rather than reconstruction error of the codec
itself, which is common to all policies and therefore cancels in the comparison. When a
cell’s required prerequisites have not yet arrived, the renderer falls back to the highest
complete layer prefix available for that cell (the coarse base, or the background floor
if even L0 is missing), exactly as a deployed client would; a block that arrives without
its prefix contributes nothing and is counted as unusable rather than improving the
frame. All policies share this identical renderer, reference, fallback rule, and the same
sampled poses and frame count (30 fps over each 60 s window), so the only difference
between rows is which blocks each policy manages to deliver in renderable form.

each frame’s deadline, so all rows sit in the 28–29 dB range rather than near the

The single-user systems we build on assume one session per origin connection and
expose no multi-user demand interface, so running their original codebases under
shared delivery would fall back to independent per-user fetching. We instead reimplement their session-centric delivery model on the same substrate as GaussCast,
holding the codec, renderer, prediction module, cache budget, and network topology
identical so that any measured difference reflects the planning policy rather than implementation details. This is a conservative comparison: where possible, baselines run on
the same codec, renderer, prediction module, cache budget, topology, and link traces
as GaussCast, and substrate-specific features such as PIT aggregation are isolated
through separate HTTP, ICN, no-aggregation, and cache-only variants, so multi-user
dependency-aware planning is the only variable in each pairing.
PerUser-HTTP Each user fetches blocks independently through a matched
HTTP/CDN stack, following the session-centric delivery model of single-user layered
3DGS systems [12, 14]. Standard cache reuse of completed cacheable objects is allowed,
but there is no rendering-aware shared planner and no explicit same-cycle request
collapsing.
PerUser-ICN Each user uses named retrieval with per-user planning, isolating the gain
from generic PIT aggregation [34] and content-store reuse without shared dependencyaware planning.
DependencyAware-PerUser Each user runs the closure-aware admission test of
GaussCast on a per-user basis—a block is admitted only with its still-missing
prerequisites—but the proxy performs no cross-user shared planning. On the same
24
named-retrieval substrate as PerUser-ICN, this isolates the effect of dependency closure alone, and together with PerUser-ICN, SharedGreedy, and GaussCast forms a
2 × 2 design over the two mechanisms (closure-aware admission and cross-user sharing).
SharedGreedy The proxy aggregates cross-user demand under a common budget and
benefits from aggregation and cache reuse, but ranks blocks by aggregated value
density without closure-aware admission, in the spirit of overlap-driven multi-user
prefetching [27, 28].
GaussCast-noClosure Shared and supplement stages use GaussCast scores but
admit blocks individually instead of inserting full missing closures together, isolating
the contribution of closure-aware admission.
GaussCast-noAggregation The full planner runs, but same-cycle request aggregation
is disabled, isolating the contribution of forwarding-plane collapsing.
GaussCast-cacheOnly The full planner runs over an HTTP/CDN-style cache with
standard object reuse but no same-cycle request aggregation, modeling a pragmatic
Web-cache deployment.
GaussCast-Full The complete system with closure-aware planning, asymmetric
caching, request aggregation, and the learned controller.
OracleSharedPrereq An idealized, non-deployable upper bound rather than a baseline
policy: every distinct prerequisite block is charged to the shared upstream link at
most once over the whole run, modeling perfect deduplication of prerequisites with
hindsight. Its remaining behavior matches GaussCast. It is an upper bound only on
the prerequisite-deduplication component, not on end-to-end utility or on all possible
scheduling policies, so the gap between GaussCast and this bound shows how much of
the achievable prerequisite-sharing saving GaussCast realizes online without future
knowledge.
Metrics include upstream bytes, edge-cache hit ratio, time-to-first-frame (TTFF),
late-miss ratio, useful bytes, unusable bytes, peak signal-to-noise ratio (PSNR), structural similarity (SSIM), learned perceptual image patch similarity (LPIPS), Jain
fairness, planner latency, verification CPU cost, and control overhead. TTFF is measured from session join to the first frame whose required prerequisite closure is
complete. Late-miss ratio counts admitted user–block pairs arriving after their useful
deadline. Useful-byte accounting is computed after dependency validation rather than
from delivered bytes alone. This metric set separates traffic reduction from quality
improvement and deadline performance. All ratios are paired against PerUser-HTTP
on the same scene, trace window, and network seed, so the reported deviations measure the per-pair difference rather than the larger absolute spread across heterogeneous
scenes.

7.5 Useful Delivery and Visual Quality
The useful-byte decomposition separates useful, late, and unusable bytes. A byte is
useful if it contributes to a frame that can be rendered before the deadline. A byte is
late if it arrives after its useful deadline. A byte is unusable if it arrives but cannot be
rendered because prerequisites are missing. Figure 7 separates whether a policy saves
bytes by avoiding duplication or merely shifts bytes into late or unusable transfers.4
Naive sharing does not by itself improve useful delivery. SharedGreedy reduces
late bytes relative to PerUser, but its unusable fraction rises to 15.2% because it
admits overlap-heavy refinements without guaranteeing that their missing prerequisites complete in time. GaussCast avoids this by admitting each block together with
its still-missing closure, raising the useful fraction to 86.1% and lowering the unusable
fraction to 5.9%. This explains why the quality gap exceeds the byte gap: the benefit
of dependency-aware planning is less about transferring fewer bytes and more about
converting limited bandwidth into dependency-complete, renderable content.

Dependency sparsity.
To test whether the results depend on the conservative full-prefix dependency, we also
vary the dependency density itself as a stress test. This does not assume that every
layered codec exposes these exact densities; it shows how the planner behaves as the
amount of prerequisite data changes.
As dependency density increases (Table 15, Appendix D), more lower-layer data is
shared across users, so upstream bytes drop from 0.88 at 25% density to 0.74 at the fullprefix setting—the regime GaussCast is designed for. Late miss rises modestly (0.071
to 0.096) because denser prerequisites lengthen each closure and leave less slack before
refinement deadlines, yet it stays well below the per-user baseline at every density.
Useful-byte share declines only slightly (88.4% to 86.1%) and quality improves with
density because more complete prerequisites enable higher-layer refinements; even the
sparsest setting already exceeds SharedGreedy’s PSNR, since closure-aware admission
helps quality independently of how much prerequisite data each block carries. The
planner thus degrades gracefully toward per-user behavior under sparse dependencies
rather than failing, and its largest gains coincide with the conservative full-prefix
model that real layered 3DGS pipelines expose. This study and the byte-scaling study
above agree: the gain shrinks smoothly as the shared prerequisite mass falls, whether
because blocks are smaller or because fewer of them are required.

8 Discussion and Limitations
When GaussCast helps and when it does not.
GaussCast benefits only the regime defined in Section 2, and degrades by design
outside it: the overlap, sparse-dependency, and strong-compression studies all show
the planner shifting budget to per-user supplements as the reuse opportunity shrinks,
and for scenes whose compressed model already fits the startup budget, pre-download
remains the simpler choice. The system adapts to the measured workload instead of
forcing counterproductive sharing.
Updates and cache validity.
The prototype assumes stable scene versions within planning windows. When the publisher updates the scene, new objects are released under a new version namespace and
delta manifests. Unchanged subtrees retain their digests (because block names include
content-addressed digests, identical content yields identical names) and remain cached;
updated blocks receive new digests and are fetched as distinct objects. Clients do not
mix blocks across versions unless the manifest declares unchanged compatible subtrees.
Highly dynamic 3DGS video—where scene content changes at frame rates—would
require temporal dependency edges and stricter expiry rules, which is future work.
Application scenarios.
GaussCast targets shared virtual tours (museum exhibits, real-estate walkthroughs),
XR classrooms (instructor-led exploration), collaborative design reviews (architecture, engineering), and digital-twin exploration (facility management, urban planning).
These scenarios share characteristics: multiple concurrent users, large-scale scenes,
overlapping viewing regions, and cold-cache joins. For single-user streaming or scenarios where users explore entirely disjoint regions, existing per-user adaptive streaming
systems remain appropriate.
Security and privacy.
The publisher is trusted for content authenticity. Proxies and forwarders are trusted
for performance but not content integrity. Digest-linked verification prevents proxies
from authenticating unauthenticated data, while versioned names and freshness checks
reduce stale replay. Clients report compact session summaries revealing coarse viewing
intent to the edge proxy. Upper-level proxies use aggregate block-demand summaries
instead of raw pose or gaze traces. Stronger privacy can use coarse visible-cell sketches
or block-demand filters, trading accuracy for privacy. The prototype does not address
traffic-analysis attacks on timing or object-name sequences.
34
Trace construction and deployment model.
The evaluation uses real 6DoF traces but forms concurrent sessions by grouping trace
windows with controlled start-time offsets because source traces were recorded individually. This controlled setup makes overlap and cold-start timing measurable but does
not fully model social interaction or correlated intent in live events. Our evaluation
spans the three spatial regimes of Table 1 (bounded indoor, object-centric outdoor,
and gigabyte-scale multi-room indoor), which is the range over which the mechanism’s
behavior is determined: GaussCast depends only on per-cell lower-layer overlap,
dependency closures, and the shared upstream bottleneck, none of which are specific to
a particular scene category. A city-scale model is, in principle, a larger instance of the
same regime, with more cells and deeper hierarchies under the identical block, dependency, and overlap abstractions, so we expect the same mechanisms to apply. The
magnitude of the gains may differ if larger working sets or deeper hierarchies change
the cache-hit rate or the planner’s candidate-set size, which are implementation limits
rather than changes to the dependency-closure or shared-retrieval abstractions themselves. We do not evaluate a city-scale deployment directly: at that scale the active
candidate set, cache working set, and cross-user overlap statistics may behave differently from the gigabyte-scale Berlin scene we measure, and confirming the trends there
remains future work. The current objective focuses on shared upstream paths. Deployments where last-hop wireless airtime dominates should add downstream airtime to
the budget model; the dependency-closure test remains unchanged.
The one-cycle planner is greedy. Because block values interact through shared closures and upstream costs, GaussCast does not claim constant-factor approximation
guarantees. Proposition 1 holds only when completion-time estimates are conservative.
Short-horizon prediction can fail under abrupt motion; the design uses explicit closure,
budget, cache, and deadline checks, and Section 7.9 shows that these checks bound
the cost of prediction error rather than letting it inflate wasted traffic—the unusable fraction grows only gradually as the horizon lengthens and prediction degrades.
Evaluation reports late misses and planner latency against strong baselines instead of
relying on single weighted scores.
Retrieval mechanism differences.
Section 6 notes that same-cycle aggregation depends on deployment: PIT-based aggregation helps only while Interests for the same segment are pending. HTTP/CDN or
relay deployments need request collapsing or relay logic to match it. Users arriving
later are served by cache retention rather than aggregation, so cache policy carries
more weight in sessions with low arrival synchrony.
9 Conclusion
GaussCast addresses a delivery challenge that persists after layered 3DGS representation and compression: when multiple users render different views of large-scale
scenes, they often depend on overlapping lower-layer blocks. By structuring scenes as
named, cacheable, versioned retrieval blocks with explicit dependency metadata, an
edge proxy can fetch reusable prerequisites once and add user-specific supplements.
35
The closure-aware planner uses cache state, deadlines, and dependency information to
avoid scheduling refinements before required lower layers can arrive—a coordination
problem that generic caches, request aggregation, and relays reduce but do not solve.
The resulting design is most appropriate for shared, progressive 3DGS viewing
with measurable lower-layer overlap and cold or changing cache state. For small scenes
where full compressed download fits startup budgets, pre-download remains simpler.
For large-scale environments under bandwidth or latency constraints with concurrent
user access, GaussCast reduces shared edge-to-origin upstream traffic by 26%, lowers
time-to-first-frame by 27%, and improves quality and fairness, with gains that grow
with cross-user overlap in the evaluated workload.

C Active Candidate Set and Safety Checks
The proxy does not score every block in the full scene during every cycle. It builds
the active candidate set Ax using frustum filtering, recent pose history, layer limits,
predicted motion, and cache state. Blocks outside the prediction horizon or below a
minimum value threshold are pruned. This keeps one-cycle planning latency bounded
by the number of visible or near-visible blocks rather than the full scene size.
All optional optimization modules stay outside the trust boundary. The controller
may change high-level parameters, cache retention changes only the eviction priority of
valid blocks, and plan-carried verification hints only shorten manifest traversal. None
of these modules can authenticate data, mix incompatible scene versions, or admit a
block that fails the dependency-closure and deadline tests.
