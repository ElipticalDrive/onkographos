Distributed spatial join uses spatial partitioning scheme based on a K-D-B-tree https://en.wikipedia.org/wiki/K-D-B-tree to partition both sides of the join, then processes individual pairs of partitions using R-Tree formed from the geometries in the build partition.
K-D-B-tree describing the partitioning scheme is provided by the user via spatial_partitioning_table_name session property. The value is the name of the table having one row and one column storing the JSON representation of the K-D-B-tree. The name of the column doesn't matter. To create such a table, run a query:
CREATE TABLE p AS SELECT spatial_partitioning(ST_GeometryFromText(wkt)) as v FROM t
spatial_partitioning is a new aggregate function that takes a geometry, builds a KDB tree and returns its JSON representation as a string. The above query will compute minimum bounding box containing all of the geometries and partition it into non-overlapping rectangles using a sample of the data. For each partition, the number of geometries overlapping partition rectangle will be roughly the same. The implementation uses reservoir sampling with maximum sample size of 1M geometries.
The presence of the spatial_partitioning_table_name session property turns a broadcast spatial join into distributed spatial join. Distributed join is available for inner joins using ST_Contains, ST_Intersects or ST_Distance functions to define join condition.
```
CREATE TABLE t_partitioning AS 
SELECT spatial_partitioning(ST_Point(t.longitude, t.latitude)) as v FROM t;

SET SESSION spatial_partitioning_table_name = 't_partitioning';

SELECT * 
FROM t, u
WHERE ST_Contains(ST_GeometryFromText(u.wkt), ST_Point(t.longitude, t.latitude))
```
TransformSpatialPredicates optimizer rule reads KDB tree from the table specified in spatial_partitioning_table_name session property and plans the distributed spatial join.
```
- filter (ST_Contains(a, b)) 
   - cross-join 
      - probe
      - build
```
becomes
```
- spatial_join(ST_Contains(a, b))
  - unnest(pids)
     - project(pids := spatial_partitions(kdbTree, a))
        - probe
  - unnest(pids)
     - project(pids := spatial_partitions(kdbTree, b))
         - build
```
and
```
- filter (ST_Distance(a, b) <= r) 
   - cross-join 
      - probe
      - build
```
becomes
```
- spatial_join(ST_Distance(a, b) <= r)
  - unnest(pids)
     - project(pids := spatial_partitions(kdbTree, a))
        - probe
  - unnest(pids)
     - project(pids := spatial_partitions(kdbTree, b, r))
        - build
```
Since the number of spatial partitions may not match the number of nodes available for the join stage, AddExchanges adds hash-based exchanges over partition ID columns. Therefore, a single node may process multiple spatial partitions.
Unlike hash partitioning, spatial partitioning may place a single row into multiple partitions (e.g. a polygon may intersect multiple partitions) and cause multiple nodes to produce identical pairs of matching geometries. To avoid duplicate results, the spatial join operator uses inline deduplication technique. It works as follows:
on each node, a join operator figures a set of spatial partitions it is processing using task ID and a mapping between all spatial partition IDs and corresponding extents: task_id = hash(spatial_partition_id) % total_tasks
when considering a potential match (e.g. a pair of geometries with intersecting bounding boxes), the join operator runs a sequence of checks:
check if probe.spatial_partition_id == build.spatial_partition_id and skip the match if not;
if neither probe nor build geometry is a point, compute the intersection of the bounding boxes and check whether the reference point of that intersection belongs to the spatial partition; the reference point is defined as lower left corner (it can be anything, but must be consistent across all join operators and must belong to the intersection); if the reference point located outside of the spatial partition, skip the potential match;
This technique relies on (1) non-overlapping spatial partitions (provided by the K-D-B-tree) and (2) containment check that considers partition extent as a rectangle open on the right and upper sides (e.g. any given point belongs to only one partition).

```
spatial_partitions(KDBTree, Geometry) function returns a list of spatial
partition IDs for a given geometry. This function will be used to partition
inputs for a spatial join defined via ST_Contains or ST_Intersects.

spatial_partitions(KDBTree, Geometry, distance) function returns a list of
spatial partition IDs for a geometry representing a set of points within the
specified distance from the input geometry. This version will be used to
partition inputs for a distance query (e.g. a spatial join defined via
ST_Distance(a, b) <= r).

For a given geometry, a set of spatial partitions is defined as a set of
partitions whose extents intersect geometry's bounding box. For points, to
avoid unnecessary duplication of data when points fall on the borders of the
partition extents, spatial_partitions function returns at most one partition
by considering partition extents as rectangles open on the right and upper
sides.
```

@drnextgis Presto uses two levels of spatial partitioning when doing spatial joins. (I'm assuming you know how distributed joins work in general; if not, we can talk about that too!) Each join worker has a set of rows/geometries from the build side table (generally, the table on the right of the join). It will create an R-tree out of these, so when the geometries from the probe side (eg, the left side) come streaming through, it uses the R-tree to only select candidates (by envelope intersection).
By default, all of the build rows/geometries go to all of the join workers (this is a broadcast join). However, if you set the spatial_partition_table session parameter, each join worker will only be responsible for a subset of the spatial partitions: they will only see build geometries that intersect the partitions for which they are responsible. To create that table, you use a query such as:
```
CREATE TABLE my_spatial_partition AS
SELECT spatial_partitioning(geometry) as v
FROM my_source_table
```
Under the hood, the spatial partition is a kd-tree.
Does this answer your question?

That is correct. There are a number of optimizations done for joins that are not done for normal filters. This is partly because it's not clear when the benefit of the optimizations will offset their cost.
In the case you describe, there's no way to build an R-tree, because the rows from osm_spain_buildings will be streaming. The cost of the filter goes like O(N_rows). Were we to build an R-tree (in addition to requiring all those rows to fit in memory), the cost of building the R-tree would be O(N_rows * log(N_rows), then the lookup would cost O(log(N_rows)). Whether that's beneficial depends on the constants.
