Background and intent
COPC Adapter already streams original COPC sources in the browser and visualizes point clouds via CesiumJS and Three.js. A future extension for GIS, surveying, construction, and digital twins could extract a bounded area of interest (ROI) and construct a derived 3D building surface or mesh.
Automatic point-cloud-to-building-model conversion does not exist in the current library. Connecting points with similar Z values is insufficient for vertical walls, roof boundaries, vegetation, occlusions, sparse regions and noise.
This is a small, reproducible feasibility study, not approval to ship a production mesh generator or expand the COPC runtime core.

Questions the research must answer
Can a bounded 3D COPC ROI be queried without downloading the full file, with an honest completeness/LoD contract?
Can a prototype distinguish ground, flat roofs and vertical walls using normals, local neighborhoods, segmentation and classification instead of Z proximity alone?
How can it avoid constructing false surfaces across missing regions, scan gaps or noisy boundaries?
What objective error/coverage metrics can evaluate reconstructed meshes against known geometry or held-out source points?
Which part belongs in an optional browser Worker/WASM module versus a separate opt-in offline/CLI/server processing pipeline?
How can the prototype preserve correct georeferencing in Cesium while avoiding Float32 world-scale precision loss in a dataset-local Three frame?
Should this ever belong in the renderer-neutral COPC streaming library, or remain an independent optional analysis/conversion module?
Preconditions and bounded scope
Finish [FEATURE][P2] Add bounded, streaming-aware spatial point queries for GIS tools #241's region, source-coordinate, LoD, completeness, provenance, point/byte/time-budget and cancellation contract before integrating real streaming queries into this prototype.
Before [FEATURE][P2] Add bounded, streaming-aware spatial point queries for GIS tools #241, only small synthetic/static fixtures and algorithm/API boundary research are allowed; do not write an alternative query engine as a workaround.
Start with one small building/terrain ROI with known reference geometry or reliable validation points.
Confirm dataset license, CRS, units and allowed use. Never commit a multi-GB COPC, proprietary scan or unclear-license dataset.
Treat original COPC as immutable/read-only. Generated mesh is a separate derived result.
In sparse or occluded regions, explicitly return partial / insufficient-data rather than inventing a complete building shape.
No new package/runtime dependencies without explicit license/maintenance review.
Phase A — Define the data, frame and budget contract
Inputs:
Explicit 3D AABB ROI (in the source coordinate frame first).
Requested resolution/maximum octree depth, point/byte/time bounds, AbortSignal.
Explicit classification/field-selection policy.
Source identity/CRS, height units and treatment of original Z versus transformed/display height.
Outputs:
Actual point count and provenance (nodeKey, point index or equivalent), selected hierarchy coverage and completion/partial reason.
Local working-frame transform and inverse georeferencing transform.
Optional derived mesh buffers with declared coordinate frame and units, geometry validity status and resource usage.
Checks:
No parent/child LoD duplicate points or accidental double counting.
No automatic vertical-datum correction, hidden terrain snap or undocumented height offset.
Use a local origin for floating-point numerics while retaining high-precision georeferencing metadata.
Phase B — Compare surface estimation candidates
Use the same small known dataset to compare at least:
Z-based / 2.5D grid or heightmap — reasonable for ground or simple single-valued roof surfaces, but incapable of representing multiple Z layers or vertical walls.
3D local-neighbor normals + robust plane fitting (RANSAC-like candidate) — investigate horizontal roof and vertical facade hypotheses.
Optionally, spatial clustering, connectivity analysis and denoising where justified by reference quality.
Record:
What density and geometry conditions each candidate requires.
Sensitivity to outliers, missing scans, occlusion and thresholds.
Why similar-height-only linking fails for walls and complex structures.
Algorithm/data limitations; do not claim one general-purpose solution based on a single fixture.
Phase C — A minimal, bounded mesh proof of concept
Target one simple roof plane and/or one vertical wall, or a known simple box-shaped building first.
Generate triangles only for sufficiently supported local regions and refuse speculative surface fills.
Verify vertex/index buffer limits, triangle winding, normals, duplicate vertices, degenerate/inverted/self-intersecting triangles where feasible, and boundary holes.
Maintain a hard maximum input point count and output vertex/triangle/memory/time budget.
Visualize generated mesh alongside original points in Three.js using a small example; avoid a new viewer framework.
If justified, show a minimal Cesium scene placement using the same explicit CRS/world frame, without altering source height or geometry semantics.
glTF/GLB export is a future decision, not required in this study.
Phase D — Quantitative quality, speed and failure analysis
Quality metrics (use appropriate reference data, declare units):
Distances from held-out/reference points to reconstructed surfaces (e.g. RMS, p50/p95).
Positional/height deviation from known planes, edges or surveyed geometry.
Coverage over well-sampled regions and count of unsupported/falsely filled regions.
Invalid/degenerate triangles and sensitivity to scan density and downsampling.
Consistency through source-to-local-to-world coordinate round trips.
Workload metrics:
ROI query time and Range bytes (when [FEATURE][P2] Add bounded, streaming-aware spatial point queries for GIS tools #241 is available).
Source/matched/retained point counts; vertex/triangle counts.
CPU allocated-buffer bytes, observed memory/Worker pressure and total wall time.
Cancellation responsiveness and browser main-thread stalls.
Impact on live Cesium/Three rendering when optional analysis is running.
Do not conflate estimated CPU buffers with exact GPU VRAM, or a visual match with metrological accuracy.
Architectural decision and safety requirements
Keep COPC source bytes and original XYZ immutable.
Use independent analysis budgets, not visualization's maxRenderedPoints, as the sole safety limit.
Never scan/decode an entire multi-GB source in the browser to bypass an incomplete ROI query.
Keep mesh computation ownership separate from stream cache/renderer lifecycle.
Do not make mesh processing part of normal COPC load(), viewer render loop or camera selection.
Do not add mandatory conversion, a default mesh mode, package exports or public APIs as part of this research.
If external libraries are considered, document browser/WASM footprint, licenses and deployment cost before approval.
Expected deliverables
A recommendation: FEASIBLE / LIMITED / NOT VIABLE YET with explicit reasoning.
Comparative evidence for at least two estimation approaches and known failure cases.
A small reproducible PoC (if supported by evidence) with bounded resources and no changes to normal streaming behavior.
Candidate input/output and CRS/provenance/completeness/budget contracts.
Mesh accuracy, triangle/vertex, execution-time and resource observations plus limitations.
Proposed follow-up issues, if warranted, for optional ROI preprocessing, roof/facade surface generation, export and Cesium/Three examples.
Documentation policy: Follow AGENTS.md. Do not add standalone files under docs/benchmarks without explicit maintainer approval; put findings and artifact links in the issue/PR.
Acceptance criteria
At least one legally usable small dataset/synthetic fixture with known reference geometry, CRS and units.
Clear [FEATURE][P2] Add bounded, streaming-aware spatial point queries for GIS tools #241 dependency and ROI completeness/resource budget contract.
Reproducible failure case for similar-Z-only links (e.g. vertical walls, scan gaps, occlusion).
Evaluation of at least two surface-estimation strategies with recorded conditions.
Bounded mesh PoC for a small ROI or a documented technical reason why it is not currently feasible.
Quantitative point-to-surface/geometry error, triangle/vertex count and runtime where a PoC exists.
Correct Cesium georeferencing and Three local-frame precision semantics; no unverified datum assumption.
No full file downloads, unbounded memory or modifications to public COPC streaming behavior.
Explicit recommendation about whether to open a separate implementation issue.
Existing tests preserved, unrelated source refactoring excluded.
Non-goals
Automatic reconstruction of entire NYC (~26.5 GB) or production-certified digital-twin geometry.
Photorealistic correction, textures, learned building semantics or arbitrary complex topology.
Guaranteed real-time meshing, multi-scale 3D model export or full editing UI.
Mandatory browser-side mesh processing and general LAS/LAZ-to-COPC conversion.
Priority and workflow
P3 research only. Obtain #241's stable API/data contract and consider #302 stability evidence before expanding beyond static fixtures. Production implementation requires a separate, approved issue.
Follow PLAN → BOUNDED POC → MEASURE → DECISION → REVIEW; stop at AWAITING MAINTAINER REVIEW. Do not merge or publish automatically.
