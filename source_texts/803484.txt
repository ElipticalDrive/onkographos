Issue body actions
Goal
Add a 2.5-D cloud visualization mode that renders existing 2-D simulation fields as a shallow, navigable visual scene with camera/perspective controls.
This is a visualization feature, not a solver feature. The physics remains a 2-D vertical slice. The renderer should create a 3-D-looking view by visually extruding or thickening the 2-D cloud/rain fields into a shallow depth dimension.
Product intent
Cloud Lab should become fun to look at and experiment with. Users should be able to manipulate initial conditions, run a simulation, and then view the resulting cloud field from different perspectives.
The 2.5-D view should make clouds feel spatial and beautiful without pretending Cloud Lab is running a true 3-D atmospheric model.
Required scientific honesty
This feature must be clearly labeled as:
```
2.5-D visual extrusion from 2-D simulation fields
```
or equivalent plain-language copy.
The UI/docs must make clear:
the solver still computes a 2-D vertical slice
depth is a rendering approximation
no out-of-plane air motion is simulated
camera rotation changes the view, not the physical model
this is not true 3-D CFD
this is not volumetric radiative transfer
Do not alter solver outputs or simulation physics.
Conceptual model
The existing simulation fields are on an x-z grid:
```
x = horizontal distance
z = height
```
The renderer should create a shallow visual depth dimension:
```
y = visual extrusion depth / slab thickness
```
For example:
```
2-D field:      x-z cloud water slice
2.5-D view:    same x-z cloud water rendered as a shallow translucent slab or pseudo-volume
```
The 2.5-D scene should be generated from existing fields such as:
cloud_liquid_water_kg_per_kg
rain_water_kg_per_kg, if available/useful
terrain profile, if available later
existing grid metadata
UX requirements
Add a visualization mode option such as:
```
2.5-D cloud view
```
or:
```
Cloud scene (2.5-D)
```
The mode should be distinct from:
raw scientific scalar fields
existing bulk cloud appearance view
future true 3-D simulation, if ever added
Camera controls
Add user controls for:
rotate/orbit left-right around the slice
tilt/elevation angle
zoom
reset camera
Initial controls can be simple sliders/buttons. Mouse/touch drag controls are optional if they are easy and tested.
Suggested initial parameters:
```
view_azimuth_degrees
view_elevation_degrees
zoom
```
The default view should still be understandable immediately and not require camera manipulation.
Perspective behavior
The view should support different visual angles over the same 2-D simulation field.
Expected user experience:
rotate slightly to see visual depth
tilt to see cloud tops/base more clearly
zoom in/out
reset to the default view
Do not allow camera controls to imply true 3-D model state. Keep labels clear.
Rendering requirements
Implement a first practical 2.5-D rendering approach. Codex should choose the least risky frontend approach compatible with the existing visualization architecture.
Acceptable first approaches include:
Option A: Canvas-based pseudo-3D projection
render the 2-D cloud field as layered offset slices
use alpha/opacity based on cloud liquid water
use simple perspective/isometric projection
good enough for first pass if it remains performant
Option B: Lightweight WebGL / three.js scene
render cloud field as a semi-transparent slab or set of billboards/voxels
support camera controls more naturally
only use if dependency/performance/complexity are justified
Option C: Hybrid approach
keep existing 2-D canvas for scientific view
add contained 2.5-D renderer component for the cloud scene
The implementation should prioritize maintainability and performance over cinematic realism.
Visual behavior
The 2.5-D view should, at minimum:
use cloud liquid water to determine opacity or brightness
suppress numerical noise / near-zero cloud water
make cloud structure visibly thicker than a flat heatmap
preserve the ground/height orientation clearly
keep axis/scale context available or explain the view is perspective-based
degrade gracefully when no cloud water is present
If rain water is present, it may be shown as a simple visually distinct overlay/streak layer, but rain is optional for this first issue.
Integration with bulk optical rendering
If the existing bulk cloud appearance renderer already provides optical-depth-like values, reuse it where practical.
If issue #90 or related sun-angle controls are complete:
integrate the same light direction/sun-angle settings into the 2.5-D view where practical
If not complete:
provide a simple fixed/default light direction
document that richer sun-angle controls are handled separately
Do not block 2.5-D visualization on full optical controls.
Suggested controls
Add controls only when the 2.5-D mode is active.
Minimum:
camera azimuth
camera elevation/tilt
zoom
reset view
Optional, if already supported by cloud appearance renderer:
light/sun azimuth
light/sun elevation
extrusion depth / slab thickness
opacity multiplier
Keep advanced visual controls collapsed if they become too many.
Data and performance constraints
Do not change backend frame schema unless absolutely necessary.
Do not add new solver fields.
Use existing grid and field data.
Keep the renderer responsive for current S/M/L model sizes.
If large grids are slow, document limits and degrade gracefully.
Avoid recomputing expensive derived geometry on every small UI update if memoization is practical.
Testing requirements
Add frontend tests where practical for:
2.5-D mode can be selected
camera controls render only in 2.5-D mode
camera controls update renderer state
reset camera restores defaults
zero cloud-water frame renders a no-cloud/empty state without crashing
cloud-water frame produces non-empty render inputs
existing 2-D scientific field views still work
changing camera controls does not mutate simulation frame data
If exact pixel rendering tests are impractical, test the derived render model / projection helper functions and component state transitions.
Documentation requirements
Update relevant docs, likely:
docs/visualization-dashboard.md
docs/product-vision.md if needed
docs/scientific-roadmap.md if needed
Document:
what 2.5-D means
what is real solver output vs visual extrusion
camera controls
limitations
relationship to bulk optical rendering
future path toward true 3-D, if ever justified
Acceptance criteria
User can choose a 2.5-D cloud visualization mode.
Existing 2-D simulation fields are rendered with apparent depth/perspective.
User can adjust camera azimuth, elevation/tilt, and zoom.
User can reset the camera to default view.
The visualization is clearly labeled as 2.5-D visual extrusion, not true 3-D simulation.
The renderer uses existing fields and does not change solver physics.
The app still supports normal 2-D scientific field views.
Tests, lint, and build pass.
Non-goals
Do not convert solvers to true 3-D.
Do not add out-of-plane dynamics.
Do not implement full volumetric ray marching unless it is already straightforward and contained.
Do not implement true Mie scattering or full radiative transfer.
Do not require PySDM.
Do not change backend simulation physics.
Do not add terrain or new rain physics in this issue.
Follow-up opportunities
After this lands, future focused issues may add:
richer sun-angle and optical controls if not already complete
terrain-aware 2.5-D view
rain-shaft perspective rendering
camera presets
saved visualization/camera settings per run artifact
export snapshot/video
eventual true 3-D feasibility spike, only if justified
Impact audit
Consider impacts on:
visualization mode selector
cloud appearance renderer
replay/time scrubbing
side-by-side comparison
saved run artifacts
frontend performance
responsive layout
documentation and truth/confidence labels
