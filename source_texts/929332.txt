Follow-up to #224.
Summary
Problem: on Metal, linear interpolation on a Float32 range grid ran at 74 % of copy bandwidth (a hand-written kernel reaches 100 %).
Cause: the cell's left edge lo + (idx − 1)·h is rebuilt from an Int64 index, and 64-bit integer ↔ float conversions are costly on Metal. In isolation, an Int64 round trip measured 10× an Int32 one.
Fix: on Float32/Float16 grids the left edge is rebuilt from (idx − 1) % Int32. The index itself, the clamps, the loads and the returned Int are unchanged, and results are bit-identical to master.

Changes
_idx_type(T): Int32 for Float32/Float16 grids, Int otherwise. It is used at the 8 left-edge rebuild sites of the range searches: muladd((idx - 1) % _idx_type(T), h, lo).
Float32/Float16 range grids are limited to typemax(Int32) ÷ 2 (≈ 1.07e9) points (ArgumentError), so the narrowing is always exact.
Performance
CUDA (V100S): no difference observed. Master, this PR and an all-Int32 index all reach 85 % of copy.
CPU (M1 Pro, Julia 1.13.2):
Float64: LLVM IR identical to master.
Float32: native code identical apart from the 32-bit conversion operand.
ABAB against master: within noise (±0.8 %).
Not covered
The float → Int64 truncation stays 64-bit. It is hidden by memory latency here; revisit when compute-heavier families reach the GPU.
Tests
test/test_range_cell_index.jl:
32-bit conversion in the IR, and the length guard (both fail on master);
bit identity with the all-Int chain (Float32/Float16 grids, Float64/Dual queries, at the length limit);
end cells for far out-of-domain queries.
The JLArrays GPU tests and the real-GPU suite on Metal pass.

The range search rebuilds the cell's left edge `lo + (idx - 1)*h` from an
Int64 index; on Metal the Int64 -> float conversion is emulated, which held a
Float32 range lookup at 74 % of copy bandwidth. On Float32/Float16 grids the
offset is now converted from `(idx - 1) % _idx_type(T)` (Int32), so Metal
reaches ~100 % for every extrapolation. The index, clamps, loads and returned
Int are unchanged and results are bit-identical; Float64 IR and Float32
native opcodes match master on the CPU.

Float32/Float16 range grids are limited to typemax(Int32) ÷ 2 points so the
narrowing is always exact (Int grids skip the check at compile time).
