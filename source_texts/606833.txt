Opening a project with many copies of a dense painted mesh can exhaust system
memory while rendering the assembly thumbnail, before slicing starts. On the
tested Linux/NVIDIA setup, a project with 41 painted objects reached a 12 GiB
memory-cgroup limit and was killed. With this change, plate 2 completed slicing
under the same limit at approximately 7.3 GiB application peak RSS.
Changes
Release CPU vector capacity after geometry has been uploaded to OpenGL.
Reuse colored geometry between volumes that share the same underlying mesh
and face painting, in both normal rendering and thumbnail rendering.
Validate cached bindings using annotation timestamps and remove bindings when
their owning volume is released. Borrowers reuse the owner's arrays without
copying VBO handles or taking ownership of them.
Reproduction
The project contains one painted object on plate 1 and twenty copies each on
plates 2 and 3. Its two mesh payloads each contain 795,273 vertices and 1,590,562
triangles. Forty components reference the second mesh payload.
Open an equivalent dense painted project with many matching copies.
Allow assembly thumbnails to render, then select plate 2 and slice it.
Compare the original and patched GUI with the same renderer and memory cap:
```
systemd-run --user --scope -p MemoryMax=12G -p MemorySwapMax=0 \
  env WEBKIT_DISABLE_DMABUF_RENDERER=1 \
  ./BambuStudio.AppImage /path/to/project.3mf
```
Tested with Bambu Studio 02.08.04.57, an Ubuntu 24.04 AppImage on Arch Linux,
GNOME/Wayland through Xwayland, and an RTX 3070 with NVIDIA driver 615.78.08.
No software-rendering override was used.

Validation
Compiled the changed translation unit and relinked using the cached Ubuntu
24.04 build's compiler and linker commands; no public header or class layout
changed.
Repeated GUI loading, plate selection, and plate 2 slicing with the supplied
project under the same 12 GiB cap. The user confirmed slicing completed.
Checked the packaged AppImage's host CLI launch and verified the embedded
executable's checksum against the tested executable.
git diff --check passed.
No automated rendering regression tests were added. Painting edits, cache-owner
deletion/replacement, repeated load/unload cycles, plate 3, and other platforms
or drivers have not been exercised. The reproduction supports excessive retained
and duplicated rendering memory; it does not prove an unbounded allocation leak.

These results are based on a single run per version and should be considered preliminary observations rather than statistically validated improvements. Memory growth is measured relative to each run's idle baseline to account for differences in initial system memory usage.
