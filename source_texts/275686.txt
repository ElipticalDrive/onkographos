Additional Notes
Architectural decisions worth flagging:
Composite runs before bloom extraction — fog is part of the HDR scene the bloom chain processes, so brightening fog regions naturally bloom. Alternative was post-bloom composite, which would have given a "fog over a sharp scene with halos" look — less physical.
Per-frame descriptor sets for composite, single set for inject — composite's HDR view changes on resize; inject only references the persistent froxel image. Matches the bloom / postprocess pattern.
Logarithmic depth slicing — packs more froxels close to the camera where view-space resolution matters most. depth(z) = near * (far/near)^(z/Z_RES) per Frostbite convention.
Froxel grid transitions UNDEFINED → GENERAL each frame — discards prior content. 41c will switch this to non-discarding GENERAL → GENERAL so temporal reprojection can read the prior frame's froxels.
Phase 8 acceptance criteria for "Froxel-based volumetric fog with neon light shafts" and "Temporal reprojection for fog noise reduction" stay unchecked — both are satisfied only after 41b/41c land.

First of four planned sub-etapes for Etape 41 (volumetric fog + light
shafts). 41a ships the froxel-grid plumbing and a working composite
pipeline with a placeholder height-falloff density. No light injection
yet — that lands in 41b.

- Allocator::createImage3D — new method for 3D images.

- 160 x 90 x 64 froxel grid (rgba16f, 7.4 MB) with logarithmic depth
  slicing along the view direction (more resolution near the camera).
  Frustum-aligned x/y tiles match screen-space.

- inject_density.slang — per-froxel compute reconstructs the world-space
  position of each froxel centre via inv_view_projection and writes a
  height-falloff extinction coefficient (full strength below
  FOG_HEIGHT_BASE = 4 m, exponentially attenuated above with 6 m
  falloff). Scattered radiance stays zero in 41a; 41b will sample
  emissive geometry per froxel via TLAS shadow rays here.

- volumetric_composite.slang — per-pixel raymarch through the froxel
  column, accumulates transmittance *= exp(-extinction_per_slice) and
  per-slice scattered radiance per Wronski 2014 / Frostbite "Adaptive
  Volumetric Shadow Maps". Composites onto HDR as
  final = scene * transmittance + scattered.

- recordFrame extension: inject dispatch (writes froxel) → barrier →
  composite dispatch (RW HDR, R froxel) → barrier → existing bloom
  chain. The composite runs before bloom extraction so the bloom chain
  operates on the fogged HDR (the fog itself can bloom).

- Per-frame composite descriptor sets (x MAX_FRAMES_IN_FLIGHT). Caught
  the classic "single descriptor set + multiple frames in flight" race
  during build verification: updating a set while a prior frame's
  command buffer is still pending requires per-frame copies (matches the
  existing bloom / postprocess pattern).

Visual verification: noticeable haze increasing with depth, sun has a
soft halo, glass tower silhouette softens at base. Both fog math and
sequencing match canonical literature; 41b will plug in real lights.

Three findings from a hyperfocused review of PR #103:

1. CRITICAL: froxelToWorld math bug. The previous code did
   camera_pos + ray_dir * view_z, but view_z is the linear depth along
   camera_forward (the slice's depth in view space) while ray_dir is
   the (non-axis-aligned) direction from camera through the NDC point.
   Advancing by view_z along ray_dir lands at view-space depth
   view_z * dot(ray_dir, camera_forward), which is < view_z at corner
   pixels. For 41a's height-falloff density this only manifests as
   slightly more fog at corners (the world-y is closer to ground than
   it should be), but for 41b (per-froxel emissive sampling via shadow
   rays) the wrong world position would actively miss / mis-target
   lights. Fix: compute camera_forward in the shader from
   inv_view_projection (unproject NDC centre, subtract camera_pos,
   normalise) and advance by t = view_z / dot(ray_dir, camera_forward).
   ~6 extra ALU ops per froxel; sub-microsecond on the 4090.

2. Defensive: hdr_to_general barrier's dstAccessMask now includes
   eShaderStorageWrite. The volumetric composite reads AND writes HDR
   in-place; the prior read-only mask happened to be safe (composite's
   read precedes its write in program order so the prior color-attach
   write is transitively visible to the write too) but listing both is
   self-documenting and matches what a sync-validation tool would
   recommend.

3. Defensive: static_assert on the C++ push-constant struct sizes for
   both VolumetricInjectPushConstants (112 bytes) and
   VolumetricCompositePushConstants (32 bytes). The struct layouts
   match Slang's std430 byte-for-byte partly by coincidence — Mat4 in
   the inject struct happens to land at offset 32 (16-byte aligned)
   because the preceding 8 floats sum to exactly 32. Reordering would
   silently diverge between C++ (no padding) and std430 (would pad).
   The asserts catch any future reordering at compile time.
