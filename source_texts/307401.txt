Purpose
A design proposal, not code: docs/sdf-and-large-assembly-rendering.md, linked from the README. It proposes three rendering tiers composed in one frame.
Tier
What it draws
Mesh
Today's GLB path
Field
Ray-marched SDF trees, or sampled grids, using yapCAD's Lipschitz bounds for safe stepping, with capped section views
Splat
Generated 2D Gaussian surfels, one part ID per splat, as a memory-bounded context tier for very large assemblies
In the hybrid mode, the geometry of interest (selected, isolated, sectioned, pinned or nearby) renders exactly through the mesh or field tier, and everything else renders as splats. Memory then scales with screen resolution rather than assembly size.
Covered in the doc
Additive v1 contract changes: sdf and splat source representations, a LOD hierarchy, a set_focus command, and v0.3 geometry reading.
Correctness: a conformance fixture so the GLSL evaluator can't drift from yapCAD's numpy reference.
Determinism: how agent renders stay deterministic.
Plan: a phased plan, with on-demand streaming deliberately placed before splats.
Risks and open questions.
Nothing is implemented; this is for review.
Revised 2026-10-16
The original argued for a field tier from first principles. Work on yapCAD's
SDF meshing since then produced measurements that make a stronger and more
immediate case, so the doc now rests on evidence rather than expectation.
A third problem statement. The doc motivated fields by SDF parts not
needing tessellation and by large assemblies not fitting in GPU memory. The
measured case is neither: a 70 x 30 x 4 mm plate engraved with three lines of
3 mm block text — a slab minus 212 stroke boxes — took 674 s to mesh and
simplify, now 147 s after yapCAD's union culling and batch consolidation
(rdevaul/yapCAD#95), and the simplified result still has 62 boundary edges,
because two 0.215 mm cells across a 0.43 mm stroke is not enough to resolve
it. Raising the resolution does not help: at 490³ the plate fails outright
with 165 coincident vertices. So small parts with fine features are not
previewable by meshing either, and are not yet meshable correctly at all
(rdevaul/yapCAD#94).
That sharpens the architectural point the doc was circling: a preview is a
picture, and a picture need not be watertight. Meshing exists to feed
manufacturing, where correctness matters and latency does not. Rendering wants
the opposite trade. Serving both from one tessellation is what makes engraved
lettering look intractable rather than like a shader.
Other changes:
Context now records what moved in yapCAD — mesh transport keeps small faces
(#86), simplification no longer emits slivers (#83), and the absolute
degeneracy epsilon remains the open root cause (#85) — so anyone reasoning
here about what a preview mesh contains starts from that issue.
Points at the companion yapCAD doc, docs/sdf-meshing-and-simplifier-performance.md,
which covers the meshing side (including feature-size responsive dual
contouring) where this one covers rendering the field without meshing it.
The splat tier's claim that decimation degrades worst on thin features is
now backed by the same measurement instead of asserted.
Phase 1 is split into viewer work and the yapCAD conformance fixture. The
fixture gates the generator's CI check, not the generator, and it is the
same per-node-kind audit as yapCAD's meshing work, so it is scheduled there
and not costed here. The one-to-two-week estimate now covers the viewer side
only.
Phase 1 gets a named acceptance fixture: the engraved plate. It is a few
hundred nodes, anyone can regenerate it, and it is precisely the case that
defeats meshing — if lettering reads sharply at zoom and sections cap
correctly, the tier works. The splat tier still needs a large synthetic
assembly; YapRover is far too small.
Still a proposal; nothing here is implemented.
