Adds new Radiosity-based Lightmapping algorithms on top of Ben Houston's LightMapper (#34991 and #34944, both merged), and baking them into vertex colors.
Radiosity.mp4
Live Demo: https://raw.githack.com/zalo/three.js/light-baking-radiosity/examples/webgpu_lightmap_baking.html
Ray Radiosity Lightmapper: imports three-mesh-bvh (from a CDN) to compute per-texel radiosity; I would consider this the gold-standard for lightmapping quality. (I would understand if you believe this is better submitted to three-mesh-bvh)
Stochastic Radiosity Lightmapper: an evolution of the Progressive Shadowmapping demo already in three.js and which requires no dependencies and no BVH.
Vertex Baking (LightBaker with target: 'vertex', VertexLightMapper): bakes any of the GI methods into the vertices instead of light maps, so meshes need no lightmap UVs. The meshes are subdivided to a maximum edge length, cut along their contacts, refined where the light changes and simplified where it is smooth. A vertex bake takes a fourth to a fortieth of the size of a light map; it is the demo's default.
Ben's BVH work (SAH tree with small leaves, triangle corners next to the triangle data, nearest-first traversal, scene data packed into one storage buffer) makes Ray Radiosity about twice as fast, e.g. a 7.4M triangle town baked into its vertices at 64 samples in 22 s instead of 51 s.
The two methods look fairly similar, the Ray Radiosity lightmapper edges out the Stochastic Radiosity lightmapper in "quality per time" on small scenes. BUT The Ray Radiosity system loses big on large complex scenes, which need vast BVH's to be computed and then expensive WebGPU shaders to be evaluated.
There are also luxury features like denoising, seam stitching, and more to squeeze the absolute best quality lightmaps out of three.js. I can break these out into future PRs; just wanted to make sure people could find this code now if they wanted it.
Dependent on #34991 and #34944
Changes in just this PR: bhouston/three.js@light-baking...zalo:three.js:light-baking-radiosity
There's also a version of this that I think would work well baked directly to vertex colors, but we can look into that later.

LightMapDenoiser: Add a mode for correlated noise.
…
ee0caa7
```
All texels of a stochastic radiosity sample share its directions, so their
noise is correlated: it is streaky and blotchy, and averaging neighbors does
not reduce it like independent noise. The filter assumed independent noise,
shrank its noise estimate over the passes and stopped averaging in its wider
passes. The new correlation option keeps the estimate for correlated noise,
so the wider passes remove the streaks, and a lower luminancePhi keeps the
contact shadows.

The example bakes the radiosity with 64 directions per sample on desktop
GPUs, like the LightBaker of mrdoob#35124, instead of 16, at the same speed, and
bakes 1024 samples.
```

LightBaker: Add radiosity algorithms.
…
2b88921
```
Adds two radiosity solvers for LightMapper and LightBaker, which bakes the
scene with them into denoised, seam-stitched directional light maps.

- StochasticRadiosity: stochastic depth radiosity, an evolution of the
  progressive shadow map example, without dependencies or a BVH. Direct
  lights are evaluated with their shadow maps, the bounces are cached in a
  light map.
- RayTracedRadiosity: per-texel radiosity with rays traced through a
  three-mesh-bvh BVH on the GPU, with emissive surfaces and rect area lights
  sampled by a light tree, sky importance sampling and a bounce cache.
- LightBaker: prepares the scene (unwrap, atlas pages, outlines), bakes
  with stochastic radiosity, ray traced radiosity, light probes or VXGI
  until the noise drops below a tolerance, then denoises and stitches.
- LightMapDenoiser, LightMapSeams, ReflectionProbes, DirectionalLightMapNode
  (dominant direction light maps) and unwrapUVs repacking.
- LightMapper accumulates samples in float targets.

Co-Authored-By: Ben Houston <neuralsoft@gmail.com>
Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
```

RayTracedRadiosity: Pack read-only scene data into one storage buffer.
…
6a64282
```
The gathering shaders bound 9-10 storage buffers per fragment stage (four from
the BVH plus triangles, materials, emitters, light trees, lights and sky), above
the WebGPU default of eight, so pipelines failed on devices without a raised
limit such as Safari. Materials, emitters, light trees and analytic lights now
share one vec4 buffer with offsets, bringing each shader down to seven.
```
RayTracedRadiosity: Build the BVH with SAH and small leaves.
…
449c935
```
The merged scene geometry was built with three-mesh-bvh's default CENTER split
and 10-triangle leaves. A SAH tree with 4-triangle leaves cuts the GPU time per
4096^2 light map sample from ~280 ms to ~180 ms in the Space Ship Hallway scene
(53k triangles), for ~60 ms more build time. Only the triangle order changes, so
the stochastic transparency pattern decorrelates while the mean is unchanged.
```
RayTracedRadiosity: Store triangle corners next to the per-triangle d…
…
b31237f
```
…ata.

The intersection tests loaded three indices and then three interleaved
position/surface structs per triangle. The corners are now packed in BVH order
with the material entry and footprint in one vec4 buffer, which replaces the
triangle buffer, and indices are only read on accepted hits. Output is
bit-identical and a 4096^2 light map sample drops from ~163 ms to ~154 ms. The
unused position attribute of the BVH is dropped as well.
```
RayTracedRadiosity: Traverse the BVH with nearest-first child tests.
…
276984f
```
The generic three-mesh-bvh shapecast pushed both children and tested their bounds
on pop, ordered by split axis. The rays now test both children at the parent,
descend into the nearer one and push the other with its entry distance, which is
skipped once a closer hit is found (Aila and Laine, 2009). The merged scene is
one cluster, so the TLAS is skipped. Ties between coplanar hits go to the lower
triangle index so results do not depend on traversal order. A 4096^2 sample takes
4-10% less GPU time (Space Ship Hallway 154 -> 138 ms).
```

LightBaker: Bake into the vertices.
…
de2431e
```
Adds VertexLightMapper, which bakes the light of any irradiance source into
the vertices of the meshes, so they need no light map UVs. Vertex bakes take
a fourth to a fortieth of the size of light maps.

- VertexLayout welds the vertices of all meshes and instances by position
  and normal into records, with records of their own for the back of
  double-sided and open meshes, and optional smoothed normals.
- The light is gathered at points over the triangles and added to their
  corners, or at the vertices (`sampling`).
- subdivideGeometry() splits long edges, imprintContacts() cuts the meshes
  along their contacts so that no triangle straddles them, the parts inside
  other meshes take no light, simplifyGeometry() removes vertices where the
  light is smooth and keeps the vertices of the original geometry.
- projectLightMaps() and refineByLightMapError() move finished light maps
  onto the vertices, vertexLightMap() shades materials with a baked
  attribute.

LightBaker gets the `target` option ('lightMap' or 'vertex') with
`maxEdgeLength`, `refine`, which splits edges at the shadows and bakes again,
and `simplify`. RayTracedRadiosity and StochasticRadiosity can cache their
bounces in the vertices. RayTracedRadiosity also gets reservoir sampling of
many lights, specular reflection at bounces, the back of open surfaces,
baked hemisphere lights, light shapes (caps, source radius, shadow rules,
facing, wrap, no shadows, occlusion), and ambient and contact occlusion.
LightMapper exposes `maxSamples`, so bakes on GPUs without
'float32-blendable' stop at its 256 samples instead of spinning.

The vertex cache reads the triangle corners that the BVH stores next to the
per-triangle data, and the analytic lights, six vec4 each, share the packed
scene buffer.

The example bakes into the vertices by default, with Max Edge, Refine,
Simplify and Wireframe controls, and can move a light map onto the
vertices.

Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
```

VertexLightMapper: Fix the cuts of contacts with sliver triangles.
…
f3c693a
```
The denominator of the barycentric coordinates in imprintContacts() was
d00 d11 - d01², which cancels to zero or below for slivers, so their cuts got
NaN positions, and a single NaN position left the layout without triangles. It
is the squared length of the cross product now, and cuts that are still not
finite are skipped. The Space Ship Hallway has two such triangles.
```

We vendor three-mesh-bvh alongside fflate; something like: examples/jsm/libs/three-mesh-bvh.module.js.
I'll have to think about this more. I know it's not the intent of three but my concern is that this kind of vendoring of libraries takes visibility away from the original project which could otherwise benefit from contributions and recognition. AI is already making it hard enough for people to understand where their work is actually coming from.
Three.js has always had a tenuous and stubborn relationship with third party libraries with users often thinking three.js needs to own everything just by the nature of how the "examples" folder is maintained. I specifically added documentation pages for community projects (#21010) and added the first "external" example pages years ago (#23907) to help with this.
I understand why three.js has organized itself this way over the years but with AI increasing the accessibility to projects it may be a good time to re-evaluate three.js' policy on external libs. Optional peer dependencies are also available, now, which may be one approach for embedding these kinds of dependencies in example directories.

Even in the age of AI, I still think having the external libs used in the examples increase visibility for those libraries. There are probably hundreds of forgotten external libraries because didn't get added as an example and the maintainers didn't have the bandwidth or reason to continuously promote them.
It also serves as a way for us to point users/agents to the best ones. On that note, I've yet to add box3d examples.

Should the rest of the features in this PR be PR'd to the pathtracing repo instead?
I'd be happy to house some of the necessary changes there. From a practical perspective the path tracer is already making an effort to have parity with three.js on its standard material features while making sure the memory usage & fast, so I think there's benefit to architecting this to share that.
I think there are features here that are generally useable and should live in the three repo, designed to be generic:
SVGF Denoiser (some changes in the path tracer still needed to use this)
SeamStitchGenerator (already reusing the code in the above-linked AO branch)
GutterFillGenerator (path tracer is using a different version but I would prefer to use a common one)
UVUnwrapper (the path tracer branch is currently using xatlas, which is quite slow)
And the following I'd been planning to add to the path tracer project that would be relevant:
Generators for ao maps, light maps, specular occlusion maps, thickness maps, etc
CLI renderer (probably using puppeteer to start but maybe node / dawn at some point)
Some other features I hadn't considered until I saw this PR include vertex color light / ao generation and this kind of radiance cache approach - both of which I'd be happy to see the path tracer adjusted to support more cleanly. The tangent benefits are that this would mean the normal path tracer would get a faster denoiser (SVGF) and radiance cache mechanism for closer-to-realtime feedback.
three.js examples are nice because AIs (and humans!) will discover them and naturally stumble across good developer practices and tooling so scenes naturally get better looking over time😄
