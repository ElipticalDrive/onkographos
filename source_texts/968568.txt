Parent
Scene plugin: declarative 3D rendering
What to build
Transforms []Transform on MeshDraw and ModelDraw: one draw, N instances — a forest, a particle field, a tile floor.
Every scene draw is already instanced with instances = 1 in the degenerate case, and that machinery is built in full. What this ticket adds is making an instanced draw explicit, which is a feature rather than an optimisation and so earns its place independently — while driving the exact path the future automatic collapser will drive. Because the sort ships in v1, that collapse will be output-identical when it lands.
Culling is per instance, not all-or-nothing, and survivors pack contiguously. The cost is N sphere tests — exactly what N separate draws would have paid.
A blend-class instanced draw splits into N single-instance sort entries, because sorting the set by its nearest instance would composite visibly wrong.
The instances share the draw's Plays and MorphWeights, so a hundred trees sway in lockstep and a hundred independently-animated characters need a hundred draws. Per-instance animation is out of scope. Instancing morphed geometry saves draw calls, not vertex work: 100 morphed heads is one draw and 100× the morph ALU.
Acceptance criteria
Transforms []Transform on both draw types; non-empty overrides the single Transform, one instance per entry
Per-instance frustum culling with survivors packed contiguously
A blend-class instanced draw splits into N single-instance sort entries
firstInstance indexes within the pass's bound range, so WGSL's instance_index stays pass-relative and the shader is unchanged
One material record per batch, padded to 256, no dedupe — documented as degenerating to one record per draw while the automatic collapse is deferred
BatchView{MeshID, MaterialID, FirstInstance, InstanceCount} is populated correctly for a multi-instance draw
Instances share the draw's Plays and MorphWeights; per-instance animation is explicitly out of scope
A crate visible to two cameras is packed twice, since sorting is per pass — documented, not worked around
A no-GPU test asserts per-instance culling counts and the packed FirstInstance/InstanceCount of each batch

Decisions
The batch is the call, not the key. Each record an instanced call expands
into carries that call's group (drawRecord.group, the recording ordinal of
the group's first record plus one — unique within a frame with no counter to
reset, zero meaning "stands alone"). The packer collapses a run of one group;
it does not collapse two adjacent draws that merely share a sort key.
That distinction is load-bearing. Merging equal keys is the deferred automatic
collapse (#49), and doing it early here would make that ticket unfalsifiable —
and it would silently turn a WireBox's twelve edges, which share the unit box
and the bundled material, into one batch. TestAWireBoxStaysTwelveSingleInstanceBatches
pins that.
A group's survivors arrive contiguous, so the run is found with a scan rather
than a second grouping pass. The instances of one call share a mesh and a
material and therefore a sort key; the sort's final tiebreak is the recording
ordinal; and every other draw was recorded wholly before or wholly after the
call. That is the ordering constraint #82 flagged, and it holds.
Batching is per pass, because the sort is. An instanced crate two cameras
both see is packed into both passes' instance slices. Not worked around.
PassView.Instances still counts instances, not batches — it is not
len(Batches) any more, which is now said out loud in its doc.

Verified by eye
A throwaway cog-examples/cmd/scene/instancing (since #96 is the real demo):
144 unit cubes from one Mesh call, each bobbing and turning on its own phase,
with an explicit Bounds so the temporary mesh culls. It reported
```
recorded 144, culled 7, instances 137, batches 1  [0, 137)
```
steadily, and the frame showed 137 distinct cubes at distinct positions,
rotations and heights — a packing that dropped or reused an instance record
would show as a tile sitting still or copying its neighbour. Deleted afterwards.
