Port of a fix from driveclub-recomp #145.
Not yet compiled or tested against DCport — please treat it as a reviewed proposal, not as a verified fix.
Symptom
Daytime tunnels can stay brightly lit, and some tunnels show a sharply bounded dark rectangle.
DCport does not document this; it is the same renderer generation as driveclub-recomp, where the
same effect was reported as issue #34
and fixed by #145.
Cause
DriveClub's local-light/probe culling compute shader (pgm_hash 0xbfce517c) reads guest-side
HTILE metadata to reject light volumes before the ambient pass. Vulkan depth writes never update
that guest buffer, so the captured tiles stay at 0x0000000f and valid volumes are rejected.
The ambient shader (0x2c918c06) then only tests the volumes that survived, so the tunnel loses
its local light.
In that shader bits 18..31 are Zmin and bits 12..17 index a 64-entry Z-span table whose last entry
expands to 16383, so the value 0x0003f00f covers the whole depth range [0, 1] conservatively.
This is a DriveClub-specific workaround, not general HTILE emulation: it only widens culling, and
the ambient pass still tests volumes against per-pixel positions.

Where it goes
The runtime tree is Supermedo/bloodborne_pc at
de2e38a (1.9.2) with windows/runtime/driveclub-runtime.patch applied (that patch does not touch
BindBuffers, so this insertion point is unmodified upstream code). Verified here: the DCport patch
applies 76/76 files to that commit, and this patch then applies 1/1 on top.
Differences from the original #145
Original (driveclub-recomp)

Why
buffer_cache.ObtainBuffer(addr, size, desc.is_written, desc.is_formatted)
ObtainBuffer(addr, size, flags) with the ObtainBufferFlags already built above
bbport's newer API
No thread guard
!UseDrawPipe()
bbport can run BindBuffers on the recording thread (vk_draw_pipe); runtime.FillBuffer records a command and must stay on the GPU thread
Host-side expansion of the lighting tile list + push_data.ud_regs[0] = tiles
not included
Shader::PushData in bbport has no ud_regs (it carries xoffset/yoffset/buf_offsets/scene_size); the record count cannot be raised from BindBuffers as-is
The omitted half only matters above 1080p: at 1080p the guest tile list is exactly 816,000 bytes
(8160 tiles × 100), the size #145 calls “the original”; 1440p needs 1,440,000. DCport's default and
recommended render size is 1080p, and its own documentation already warns about 1440p/4K, so the
1080p fix is the useful half. If you want the 1440p half too, the record count has to be found in
bbport's user-data path first.

Testing (not done yet)
Build the runtime on top of de2e38a + driveclub-runtime.patch + this patch.
Drive a daytime tunnel that currently stays lit (and one showing the dark rectangle), with
SETUP > Threading on Auto/Off.
A/B with BB_LIGHTING_CULL_FIX=0 in the environment: the old, wrong lighting should come back.
Worth checking as a side effect: auto exposure when entering and leaving a tunnel.
Known limits of this version: no effect with SETUP > Threading = On (the fill is skipped by
design), and above 1080p the tile list is still the guest-sized one (see the table above).

Fix tunnel lighting with conservative HTILE culling bounds

Thank you @dnfcf524-max, this was a great write-up! It's in DCport 0.5.0: https://github.com/qnfn/Driveclub-Port/releases/tag/windows-v0.5.0
We wrote it our own way rather than applying the diff as is, with two differences:
It also runs with the draw pipe on. DCport records draws on its draw-recording thread by default, which already records buffer copies in BindBuffers, so the fill is safe there. With the !UseDrawPipe() guard it would never have run for most players.
Checked against our own shader translation. Binding 1 of bfce517c is the buffer the shader decodes with bits 12–17 / 18–31 and the 16383 limit; binding 0 only holds constants. The log prints Light culling: depth tiles at ... span the whole depth range once per session. BB_DC_LIGHT_CULL=0 turns it off for comparison.
Credit to HeyOkay (driveclub-recomp #145) and to you is in the code comment, the README and the release notes.

Thanks @darkresident, the screenshot and log made it easy to find! It's fixed in DCport 0.5.1: https://github.com/qnfn/Driveclub-Port/releases/tag/windows-v0.5.1 (the launcher offers the update by itself: Restart to update).
The cause was the 1440p render size (-resolutionscale 1.3333 in your log). The game makes its per-tile light lists for 1080p only, so at 1440p they ran out about 57% of the way down the screen, exactly where the edge was. They are now sized for the real render size, at 1440p and 4K alike. Idea from driveclub-recomp #145 by HeyOkay.
