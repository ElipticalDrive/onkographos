Hi Emanuele, when I was trying with OFusion, I found that during integration only voxels near the depth points are updated, while we actually need all voxels along the ray from the camera be updated to model the free space for navigation. I think this was caused by the step setting when building the octant list. The step size near the camera seems to be too large that most blocks are skipped. So I change it from 30voxelSize to 8voxelSize to make sure all blocks along the ray can be processed, as shown below. Do you think it would be a proper fix for this issue? Thanks!
in compute_stepsize in bfusion/alloc_impl.hpp:
```
  if(dist_travelled < hf_band) new_step = voxelSize;
  else if(dist_travelled < hf_band + half) new_step = 10.f * voxelSize; 
  else new_step = 30.f * voxelSize;
```
-->
```
  if(dist_travelled < hf_band) new_step = voxelSize;
  else new_step = 8.f * voxelSize;
```

Hi Xuesong, thanks a lot for looking into this. The voxels representing free space between the camera and the surface should actually be modelled. The step function effectively says that we do not need full resolution for free space (at least in our use case) and so it allocates bigger voxels for it. This should be reflected when you sample the field, however in the current version trilinear interpolation is supported only on the leaves at maximum resolution and it falls back to nearest neighbour when the sample points fall into a coarser voxel.
If you are not able to see this than something might gone miss in the massive refactoring for the opensource release. I can have a look and get back to you.
Also, your solution would be fine but effectively what you end up doing is fully allocating the whole space, sort of invalidating the point of a sparse octree structure -- meaning very bad computation performance overall.
