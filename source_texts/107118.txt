Summary
This PR adds an internal render-command batching layer for WebGPU draw submission, bringing the WebGPU engine into congruence with a pattern Babylon.js core already ships: the bgfx-based NativeEngine batches its engine commands through a CommandBufferEncoder (thinNativeEngine.pure.ts) and flushes them across the JS/native bridge in bulk, rather than paying one Node-API crossing per call. The WebGPU engine had no equivalent layer, so on hosts like BabylonNative with WebGPU backed by wgpu-native, every setPipeline, setBindGroup, setVertexBuffer, setIndexBuffer, and draw* crossed the JavaScriptCore/Node-API boundary individually — the CPU bottleneck profiled in this forum post.
This is also the same architecture browsers use one layer down for the identical boundary problem: Chromium's Dawn wire protocol serializes WebGPU commands into batched buffers across the renderer-to-GPU-process boundary, and Unreal's FRHICommandList records on the render thread and translates on the RHI thread. The boundary here is N-API rather than IPC or a thread hop; the remedy is the same.
Scope note: this is transport-level, order-preserving submission batching — not draw merging. It does not reorder, sort, or combine draws, so it composes with (rather than competes against) instancing, and the stream format reserves multi-draw fields for future multi-draw-indirect lowering (wgpu exposes MDI natively even though it is not yet in the WebGPU spec).
Architecture
RenderCommandBatcher — small generic lower-or-replay adapter: try the optional lowering path; for a draw that cannot lower, flush pending lowered work first, then replay the original command exactly once. Ordering is preserved unconditionally.
WebGPURenderPassCommandStream — the WebGPU-specific lowerer: encodes draws as opcode words into a reused Uint32Array, state-diffing pipeline, index/vertex buffers, and bind groups so redundant state is elided before it is ever recorded, then submits the whole batch through a single _recordCommands call on the render pass.
Flush boundaries: batched draws are recorded before every direct render-pass mutation — viewport, scissor, stencil reference, blend constant, full-quad clears, occlusion query begin/end, debug marker push/pop/insert, and render-pass end — through a ThinWebGPUEngine._flushRenderPassCommands() seam (a no-op for engines that do not batch). Without these boundaries, a draw batched inside an occlusion-query bracket would be recorded after the bracket closes (the query reports zero samples and the mesh wrongly disappears as occluded), and GPU captures would attribute draws to the wrong debug group.
The draw hot path is allocation-free: the engine reuses two scratch draw-command objects (both the lowering and replay paths consume commands synchronously), and the stream reuses scratch id arrays. With no provider installed — always the case in browsers — the per-draw overhead is a null check and a work-free flush, and draws take the standard WebGPU encoder calls unchanged.
Failure policy: a protocol-version mismatch or a backend recording failure logs one error (enriched with the provider's diagnostics) and permanently falls back to direct encoder calls for that engine — nothing throws from the render loop.
Typed indexed/non-indexed draw command variants instead of a magic numeric draw type.
Host contract
A host opts in by installing a provider on the engine:
```
engine.renderPassCommandRecorderProvider = {
    protocolVersion: 1,                       // must equal WebGPURenderPassCommandStreamProtocolVersion in the decoder build
    isEnabled: () => true,                    // host-controlled toggle
    getResourceId: (resource) => /* host handle id for a pipeline/buffer/bind group, or 0 */,
    getLastError: () => /* optional backend diagnostics for failure logs */,
};
```
and exposing a _recordCommands(words, drawCount, multiDrawCallCount, multiDrawDrawCount, wordCount) hook on its render-pass encoders. The recorder must consume the words synchronously — the buffer is reused after the call returns. The protocolVersion handshake mirrors the PROTOCOL_VERSION guard the bgfx-based NativeEngine uses to keep the JS encoder and native decoder from drifting.
Test coverage
Contract-level unit coverage of the batcher and stream: lowering absent/present/disabled, fallback replay with flush-before-replay ordering, state-diff behavior per state kind, indexed/non-indexed/indirect draws, late resource ids, command storage growth, render-pass boundary flushing, no-provider behavior, protocol-version mismatch, and permanent fallback with diagnostics when backend recording fails.
Flush-boundary scenario tests (webgpuRenderPassFlushBoundaries.test.ts) drive the real registered engine prototype methods against a semantic model of the native render pass: a GPU timeline that executes direct calls and decoded command-stream batches in submission order, attributing each executed draw to the occlusion query and debug groups open at execution time. Assertions are on user-visible outcomes — "which draws did query N observe", "which draws are inside group X", "did the draws stay on the batched path" — not on encoder-call ordinality.

Future work
Multi-draw-indirect lowering through the reserved multiDrawCallCount/multiDrawDrawCount stream fields (wgpu-native exposes MDI; the WebGPU spec does not yet).
Lower debug markers (pushDebugGroup/popDebugGroup/insertDebugMarker) into stream opcodes so that enabling GPU profiler markers does not fragment batches with boundary flushes — today markers stay correct (flushed) but each marker costs a bridge crossing and splits the batch, which is acceptable for profiling sessions only.
The command-stream types already admit GPURenderBundleEncoder, so the same lowering could batch bundle construction under compatibilityMode = false if profiling justifies it.
Comparison numbers against compatibilityMode = false and snapshot rendering on the same scenes.

```
JS numbers; an id beyond Number.MAX_SAFE_INTEGER would encode imprecisely
and corrupt the stream. Treat out-of-range ids like missing ones - the
draw falls back to direct encoder replay - and document the range in the
provider contract. Also document at the failure site why a failed backend
recording drops the in-flight batch instead of retaining replayable
```

KTX2: transfer a loaded file to the worker, and free the levels once …
…
4c48a99
```
…uploaded (BabylonJS#19059)

Forum: [64298](https://forum.babylonjs.com/t/64298) #2 and BabylonJS#11: isolated
PRs with measured gains, each benefit measured separately.

When a KTX2 texture is decoded in a worker (the default), Babylon copies
the file before posting it to the worker, and the levels the worker
sends back stay in memory until a garbage collection finds them, long
after they were uploaded to the GPU. V8 counts ArrayBuffer memory toward
its next full GC, so an app that loads many KTX2 textures runs full GCs
far more often than its JavaScript needs. This PR removes the copy when
nothing else holds the file, and frees the levels once they are
uploaded.

**What it does.**
- When the engine loaded the file from the texture's url with no offline
provider involved, nothing else holds it: the worker gets its buffer
(transferred) instead of a copy. The engine says so with a new optional
argument of `IInternalTextureLoader.loadData`, `ownsData`, passed only
on that path. A provider can keep the buffers it serves in a cache, so a
file it serves is still copied. Data a texture is created from
(`buffer`) is still copied, and so is a view on part of a buffer: it can
belong to the caller, and with `doNotHandleContextLost` a texture does
not keep it, so the texture alone cannot tell.
- Once the levels a worker sent are uploaded, their buffers are released
with `ArrayBuffer.prototype.transfer(0)` where it exists, which frees
the memory at once. Nothing else holds them: the worker transferred
them, and the uploads copy them (WebGL's `texImage2D` and
`compressedTexImage2D`, WebGPU's `writeTexture` or a mapped buffer).
- The decoder on the main thread (no workers) is unchanged: there, the
levels can belong to the decoder.
- Context loss is unaffected: a texture loaded from its url loads it
again, and one created from data keeps that data (`_buffer`).

**Measured.** In our app, which streams KTX2 textures as the player
moves, these two changes took full GCs from 30.2 to 17.0 per minute (2
runs each). The numbers below come from a test page made for this PR,
which we can share.

Chromium 147, RTX 3080 Laptop GPU, Windows 11, 1280×720. A page that

files of our own procedural content, each url loaded anew from a local
server. Babylon's KTX2 decoder and transcoders are served locally, with
the default worker pool. A Chrome trace counts V8's garbage collections
on the main thread, from the first load to 2 s after the last. The
external memory is `backingStorageSize` from `Runtime.getHeapUsage`,
sampled every 50 ms. Each arm ran 4 times, the arms alternating, with a
new browser for each run. Ranges are over the 4 runs, on master as of
today (dbd14a5).
```

Materials: keep pipeline names and plugin declarations as flat strings (

```
BabylonJS#19060)

Forum: [64298](https://forum.babylonjs.com/t/64298) #2 and BabylonJS#11: isolated
PRs with measured gains, each benefit measured separately.

An effect's pipeline name and a material's plugin declarations live as
long as the effect and the material. Today V8 keeps them as ropes,
strings made of many pieces. The pipeline name comes from a global
`replace` of each line break (`replace(/\n/g, "|")`), and the plugin
declarations grow with `+=`, one line per uniform. A rope is one heap
object per piece, and every full garbage collection marks all of them.
This PR builds the same strings with `split` and `join`, which V8 keeps
as one flat string each.

**What it does.**
- `Effect`: the pipeline name is `key.replace(/\r/g,
"").split("\n").join("|")` instead of `.replace(/\n/g, "|")`, in the
constructor and when the pipeline context is created. The same applies
in `effect.webgl.functions`. The string itself does not change.
- `MaterialPluginManager`: the ubo, vertex and fragment declarations of
the plugins are pushed into arrays and joined once, instead of being
grown with `+=`. The strings do not change either.
- On WebGL, the pipeline name is also a key of the pipeline cache, and
V8 flattens a string used as a key, so the effect part matters mostly on
WebGPU.

**Measured.** In our app (WebGPU), a heap snapshot had 220k concatenated
strings: 132k under plugin declarations and 54k under pipeline names.
With this change the heap had 13% fewer nodes. The numbers below come
from a test page made for this PR, which we can share.

ready and 60 frames have run, the runner forces 2 full GCs, then 5 more
inside a Chrome trace (for each, the main thread's pause and its atomic
mark), and takes a heap snapshot. Each arm ran 4 times, the arms
alternating, with a new browser for each run, on master as of today
(dbd14a5). Ranges are over the runs; the GC times are the median of all
```

```
…ometry's (BabylonJS#19065)

Forum: [64298](https://forum.babylonjs.com/t/64298) #2 and BabylonJS#11: isolated
PRs with measured gains, each benefit measured separately.

`refreshBoundingInfo()` runs for every mesh when its vertex data is set.
Besides the bounding info, it fills the mesh's positions with one
`Vector3` per vertex, which the mesh keeps. Picking and collisions read
those points. But when the positions are not transformed (no morph
targets, skeleton or baked vertex animation applied), they are the
geometry's own positions. The geometry already makes its own `Vector3`
points the first time picking or collisions need them
(`Geometry._generatePointsArray`), and all its meshes share them. So
today every mesh holds an extra copy, one `Vector3` per vertex, whether
it is ever picked or not, and each clone of a mesh holds its own.

**What it does.** In `AbstractMesh._getData`, when the positions are not
transformed, the mesh keeps none of its own. `Mesh._positions` already
falls back to the geometry's points. Picking, collisions and the WebXR
near interaction already call `_generatePointsArray()` before they read
them. With morph targets, a skeleton or baked vertex animation applied,
the mesh keeps the transformed positions, as before.

**Measured.** In our app, this change took the heap from 2.03 M to 1.95
M nodes (-4%); 25 meshes held 39,691 of these `Vector3`. The numbers
below come from a test page made for this PR, which we can share.

Chromium 147, RTX 3080 Laptop GPU, Windows 11. The page makes 20 sphere
geometries (16 to 54 segments), each used by 10 meshes, the first one
and its 9 clones: 200 meshes and 623,200 vertices in all. It times the
creation of the meshes. Once the scene is ready and 60 frames have run,
the runner forces 2 full GCs, reads the JS heap, traces 5 more forced
full GCs and takes a heap snapshot. Then it picks every mesh once with a
ray through its center, and reads the heap again after 2 more forced
GCs. Each arm ran 4 times, the arms alternating, with a new browser for
each run, on master as of today (dbd14a5). Ranges are over the runs; the
GC times are the median of all the forced GCs.
```

```
Forum: [64422](https://forum.babylonjs.com/t/64422) #1 and #2.

A submesh skips its draw in a shadow map when its render id is the
scene's (`ShadowGenerator._renderSubMeshForShadowMap`), which keeps a
pass from drawing it twice. The scene's render target loop increments
the render id before each target, but `RenderTargetTexture.render()`
called by hand did not for a 2D target, and incremented it only after
each face or layer of a cube or array target. So two shadow maps
rendered by hand, one after the other, shared a render id, and the
second one skipped the casters the first had drawn; and the first face
or layer of a cube or array target could inherit an id an earlier render
had used.

**The change.** `RenderTargetTexture.render()` increments the render id
before each pass: before the render of a 2D target, and before each face
or layer, the first one included. The id stays the same during a pass,
so a submesh is still drawn once in it. In the scene's loop, the passes
of a target get fresh ids as before, with one more increment for a 2D
target.

**Measured.** The repro Playground of the forum post
(https://playground.babylonjs.com/#Q5U9HP#1) counts the shadow map
texels the caster covers, in a page that runs its code with a given
build. On 9.32.0 the two maps rendered by hand count 30388 and 0 texels;
with this branch, 30388 and 30388. With `scene.incrementRenderId()`
between the two renders, 9.32.0 gives 0 and 30388 (the first map took
the id the second one had used) and this branch 30388 and 30388; with it
before each render, both give 30388 and 30388.

**Unit tests.** `renderTargetTexture.renderId.test.ts`, 4 tests: two 2D
targets rendered by hand both draw a submesh another render drew with
the current id, as two shadow maps sharing a caster; the first face of a
cube target and the first layer of an array target get a fresh id, and
each face or layer its own; and the render id stays the same from the
start to the end of each pass. On master, the first three fail and the
last one passes. The Materials, Lights, Scene, Rendering and
PostProcesses unit suites: 619 passed.
```
