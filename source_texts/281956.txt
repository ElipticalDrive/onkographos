In one sentence: Make vesuvius.data.Volume normalize and convert voxel intensities without integer overflow, lost 64-bit precision, or corrupted non-finite values.
One real example: Eight original CT chunks from PHerc1447 (256³ uint8 voxels, 16,777,216 total) were read through the actual Volume API in Zarr 2/3, with 660 local checks and two remote HTTPS checks against an independently verified local copy. This is bounded real-scroll coverage, not a whole-scan claim. Original provenance, byte hashes and the full scope: https://github.com/albertotranquilli-cmyk/grok-self/issues/25#issuecomment-6382778312.
Before: Integer conversion could wrap or truncate, instance_minmax could erase contrast between adjacent 64-bit values, and certain extreme inputs could overflow normalization. The test harness also had a uint64 outlier fixture that silently converted the intended 2**64-1 value to zero.
After this PR: Saturating rounded integer conversion, exact integer-domain min-max scaling when necessary, explicitly handled non-finite data, and a correctly constructed uint64 outlier regression. Minimal before/after witness: np.uint64 [2**64-2, 2**64-1] through instance min-max to uint8 was [0,0], now [0,255]; uint8 [0,1,3] min-max to uint64 now yields the mathematically rounded midpoint 6148914691236517205.
Proof: All original cast/normalization test cases in the two touched test modules were executed against the exact three-file Git blobs:
Zarr2 GitHub Actions — 583 passed, 2 warnings, 0 failed
Zarr3 GitHub Actions — 1,022 passed, 3 warnings, 0 failed
Both jobs use Python 3.12, NumPy 2.3.5, Zarr 2.18.7 or 3.4.1, respectively, and verify SHA-1 Git blobs for source and tests before running. Validation branch codex/validate-volume-e8d5737 adds only a separate CI workflow and retains identical source and test blobs to this PR's head. A prior bounded PHerc1447 run against this identical implementation blob is linked above, but was not rerun on the isolated PR commit. The two tested modules cover synthetic edge cases; the CT data audit demonstrates the actual read path on real data.
Why / where this is useful: Researchers reading and preparing CT voxels through Volume can use numerical conversions and normalization without silently losing extrema or having integer values wrap.
The two original Volume cast/normalization test modules pass on Zarr2 and Zarr3 in a clean hosted test run.
The PR consists of one focused commit, exactly three changed files, with no unrelated fork history.
A fresh screenshot of a real data/script before-and-after session, as requested by this repository's contribution guidelines.
A human-authored first-hand motivation note from the contributor, reproduced verbatim below. Implementation and testing used AI assistance as disclosed.
Contributor's motivation — personally written and supplied by the contributor
I want to support the Vesuvius Challenge by helping make the tools used to process and analyze CT scans more reliable.
This contribution focuses on numerical accuracy in Volume, specifically how integer voxel values are converted and normalized. It addresses a case where two different 64-bit integer values can map to the same output, causing information loss. The proposed fix preserves the intended numerical range and improves handling of extreme values.
The changes were validated with Zarr 2 and Zarr 3, including end-to-end checks through the Volume interface; additional checks used a subset of real PHerc1447 scan data.
I believe preventing silent numerical errors matters for scientific reproducibility and for trustworthy tools supporting papyrus analysis. My aim is to offer a small, verifiable improvement that can help other researchers working with the Vesuvius dataset.
The implementation and testing were carried out with AI assistance under my direction.
Details
Scope: vesuvius/src/vesuvius/data/volume.py, vesuvius/tests/data/test_volume_int_cast.py, and vesuvius/tests/data/test_volume_int_cast_e2e.py. Git code blob a09472fd9919a3235f886f74e66de0321b73ee8d; test blobs a69d7289217cd58ff948a616174064086394a66e and ae34f85379c68b5ec3d2021c098857a6561e59f9. Head commit e8d57377faf389f233a90ba6cc32fd956d754d7d is based directly on upstream main 6f2024569404a46b0f008eee292773945c07a684.
The numerical policy changes (NaN/±inf finite-only normalization, ties-to-even saturation) can change results for extreme inputs. Two prior test warnings on Zarr2 and three on Zarr3 are float64-to-float32 overflow notices, not hidden. Does not claim full monorepo testing, remote S3 performance, Torch or every scan voxel. This is a DRAFT submission pending any further real-data visual evidence required by maintainers and their review.
