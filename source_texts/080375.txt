Stacked on #110. Base is feat/multichannel-microscopy-formats, so the diff here is just this branch's 39 commits.
Draft, opened to exercise CI.
The through-line: make a streamed multi-LOD volume look right. That started as the swap flicker and grew to cover every reason a brick could read wrong (geometry, brightness, opacity, reconstruction), then the controls and demos needed to see those defects at all.
The flicker
Every refocus swaps the chunk plan, synchronously destroying unmatched bricks, and a brick with no resident texture draws nothing, so the scene background showed through until the re-stream landed. NVChunkedVolume now fetches the coarsest pyramid level once and installs it as a whole-volume floor behind the octree (coarseFloor: false opts out; skipped when that level is too big for one texture upload). Adds chunkFadeMs (default 120 ms, 0 disables) on both backends so fine detail dissolves in over the floor instead of popping.
The OME-Zarr demo builds its plans by hand, so the automatic floor never reached it; it now builds one from the coarse data it already keeps resident.
Also in this group: picking tissue exposed by a clip plane in chunked volumes (installs NVImage.pickSampler in the NVChunkedVolume constructor, teaches clipRaySegment cutaway mode to return a skip slab, and makes both views march before falling back).
Brick misregistration (the real seam)
A multi-LOD brick's fetch box is snapped out to whole voxels of its own pyramid level, so it covers up to one level voxel more than the brick owns on each face. Both backends' chunkUniformsFor and chunkSampleTransform treated that fetched box as the owned box, so the shader mapped the brick's common-grid edges onto the fetched region's edges. Content inside every coarse brick was shifted and stretched, and because neighbouring bricks snap independently, two neighbours disagreed about the level coordinate at their shared face. That disagreement is a geometric seam, which no brightness knob can remove.
chunkOwnedTexBox is now the single source for the remap in all three call sites. On the real hoa_heart pyramid this moves brick content by up to 3.4 / 6.3 / 8.7 common voxels at L2 / L3 / L4 and corrects a stretch of up to 5.9 / 12.4 / 23.7, about 61 um of displacement on an L4 brick. A single-level plan takes an exact path and is bit-identical to before.
Ray-march ringing and slab tiling
Oversampled the 3D ray march.
Each fine sample now owns the slab it is the midpoint of, clipped to the brick's segment, so slab thicknesses tile [0, len] exactly at LOD interfaces.
The empty-space skip now probes one stride past each cube's exit face. It restarted at every chunk / coarse-floor cube face and strode 1.9 level voxels, so material in the last sub-stride was never probed, the cube contributed zero, and its exit face showed as a discontinuity. CPU replica: worst-case two-cube split error -3.99% to +0.68%. Browser A/B (HOA heart, pinned L4, 64 chunks, WebGPU): whole-image TV -2.7% x / -2.2% y.
The coarse floor renders as volume rather than a dark shell.
Gamma and LOD compensation
scene.gamma was declared, settable, and persisted in NVD, but no renderer ever read it, so the property was dead while FEATURE_PARITY claimed it worked. It is now wired into both backends' ray-march and the 2D slice tiles. Semantics follow the old package (classified RGB raised to 1/gamma, alpha untouched, 1.0 an exact no-op). Measured headless on both backends, mean canvas luminance: 13.59 at 0.7, 17.85 at 1.0, 29.56 at 2.0, 36.91 at 3.0, the two backends agreeing to within 0.003.
Downsampling averages voxels, which destroys the correlation between a sample's colour and its opacity, so a coarse brick integrates darker than the fine data it stands in for. volumeLodBrightnessCompensation applies a per-chunk exponent that multiplies the gamma exponent, so a level-0 brick or any single-level plan is an exact no-op. The coarse floor draws through its own uniform block and initially got no correction at all, which put the scene's largest brightness step exactly at the edge of the resident fine region; its downsample now comes from its own dims.
The law was wrong, and that was the seam. The lift grew with downsample - 1, which assumes a level-4 brick loses eight times what a level-1 brick loses. Averaging does not work that way: every level reduces the same 2x2x2 neighbourhood, so it is one comparable step per level. It is now log2(downsample). Under the old form a level-6 brick asked for exponent -0.386 on a seven-level pyramid, the 0.25 clamp caught it, and the correction became the artifact: measured across the strongest seam on hoa_heart, +35.7% at the default against -34.0% with compensation off, having overshot the null by about 6x. The floor sat pinned at the clamp, which was the pale flash on zoom. Default refit to 0.08 per level; seam response is now monotonic across the whole slider (-33.0% at 0, -10.1% at 0.08).
volumeLodOpacityCompensation is the matching alpha knob, ray-march only, and defaults to 0 as a measured choice: over four probe regions, raising c from 0 to 0.5 cut mean alpha error from 6.7% to 5.1% while driving colour error from 15.3% to 25.7%. Sparse thin material has a genuine deficit that no global scale recovers; fixing it needs a coverage-preserving pyramid, not a renderer knob.
Both coefficients are exact no-ops on a non-multi-LOD volume and nothing on screen said so, so nv.lodCompensation() reports isActive plus an inactiveReason, then per level the downsample factor, bricks drawn, and the exact exponent and scale handed to the shader (floor reported separately, via a new ViewBackend.coarseFloorDims() in both views). Setting a non-zero coefficient with no multi-LOD volume loaded now warns at the moment of the set. Covered by e2e/lod-compensation-report.spec.ts.
Opt-in tricubic B-spline reconstruction
volumeIsCubicInterpolation, both backends, default off. It fixes the texel staircase; it does not remove the ringing (see above). Cubic needs a 2-voxel halo, so chunking.ts gained LINEAR_MIN_HALO / CUBIC_MIN_HALO / planSupportsHalo / planSupportsCubic, and NVChunkedVolume.raiseHaloTo() re-plans a loaded volume when the setter fires. Both views gate cubic per draw on halo >= 2 and on not-a-label-volume, including the coarse-floor cube. Public default halo stays [1,1,1]. New unit test src/volume/chunkHalo.test.ts carries a CPU replica of sampleTricubic.
New example vox.interp.html (linear vs cubic, A/B split or flip); the range demo gained an interp selector, a draggable A/B divider, and a samples-per-voxel control.
Named budget plans
A chunked volume had exactly one policy: an octree focused on the crosshair. That is right for exploring and wrong for a whole-volume figure or for holding a frame rate while rotating. budgetPlans.ts owns the BudgetPlan type, three presets (focus / uniform / interactive) and resolveBudgetPlan. Precedence lowest first: focus baseline, named preset, explicit plan object, individual options, so every existing call keeps its behavior. radius: 'volume' is all uniform needs, since the detail shrink pass only bites beyond the radius and the budget pass converges on the finest uniform level that fits. setBudgetPlan switches mid-session and re-folds over the load options so an app-pinned knob still wins; minLevel and halo come from current state so a switch cannot undo setMaxDetail or undercut a wider kernel already streamed for. targetFrameMs is resolved and readable but nothing acts on it yet.
Design doc: docs/budget-plans.md. Remaining streaming work is tracked in docs/streaming-todos.md (off-thread chunk decode is the next item).
Chunk 0 eviction blanked the volume (WebGL2)
Reported as "stopped loading chunks when I moved the crosshairs to the opposite surface of the clipped volume".
draw() early-returned on a null volumeTexture / volumeGradientTexture. For a chunked volume those are only a best-effort alias of chunk 0 (the real textures bind per chunk, and the coarse-floor cubes bind the floor textures), so a refocus that evicted chunk 0 silently killed the whole volume. WebGPU already branched on the chunked entry before its equivalent guard, which is why this was WebGL2-only.
Two dangling-pointer paths fixed alongside it: swapChunkedVolumePlan never refreshed the aliases after manager.remap() destroyed unmatched chunks, and switching from a chunked volume to a single one let the single-volume path delete textures the chunked cache entry still owned.
GPU context recovery
A lost context was permanent: NVViewGL latched _contextLost and stopped rendering, and its webglcontextlost listener was { once: true } so a second loss was not even reported. Both views now expose an onContextLost hook, wired by the controller inside its RAF callback so it survives view recreation (the same treatment overlayDraw gets). WebGL2 calls preventDefault() (which is what makes the browser promise a replacement) and fires on webglcontextrestored; WebGPU has no restored event so it fires straight from device.lost, with a _destroyed latch so deliberate teardown does not ask for a rebuild. The controller rebuilds via recreateView, capped at two attempts, with a canvas overlay while rebuilding and a "GPU most likely ran out of memory" message on giving up.
The range demo asked for an 8 GB GPU residency budget against a 2 GB plan budget, so the LRU never evicted and each refocus piled bricks on top of the old ones: 1.67 GB across 177 bricks measured on hoa_heart L0. WebGL2 now gets 1.25 GB, deliberately below the plan budget. WebGPU unchanged.
Block inspection (how the above gets seen)
A registration or reconstruction error inside one brick is nearly invisible in the full render and obvious with the brick beside its own fine data. Two demos, in two halves.
examples/vox.block.pick.html, CPU-resident NIfTI. pickExplodedBlock(clientX, clientY) resolves a pointer onto one visible brick, CPU-side: it slab-tests each brick's EXPLODED mm AABB and inverts the exploded matRAS, because GPU depth picking cannot see the render-time per-brick translation. extractSubVolume / extractChunkBlock (src/volume/ChunkExtract.ts) copy a voxel box out as a complete NIfTI whose affine is the parent's with its origin walked to the box, so an oblique parent stays oblique and the child reports true anatomical mm. The brick's DATA region is used rather than its halo region, so adjacent blocks tile the parent without overlap.
examples/vox.block.pick.zarr.html, streamed multi-LOD hoa_heart, which is the part that actually tests chunkOwnedTexBox. A streamed volume has no CPU img, so extractSubVolume returns null and the right pane cannot be built by copying. It opens a SECOND streamed volume over the same store, cropped to the picked brick's common-grid box, and lets that volume's octree pull the crop toward level 0 near its crosshair. A brick is already one texture's worth at its own level, so re-fetching it there buys nothing; the detail comes from the crop source's finest levels. Picking needed a core fix: pickExplodedDraw sampled the parent's CPU img, so on a streamed volume every pick landed on the brick's box face. It now falls back to vol.pickSampler (mm-space, backed by the coarse floor), in control/ so both backends get it.
The lattice you pick out of also needs a block COUNT you choose, and the planner could not express one. chunkVolumeMultiLOD sized bricks from a scalar cellEdge, so the count fell out of the pyramid: on hoa_heart L5 (181x186x246, not a cube) the reachable counts step 2, 8, 12, 16, 27, and 4 or 9 are unreachable at any edge length. maxBricks only coarsens by raising the level floor, which fights the demo's own level control. A new gridDims option replaces the octree with an exact lattice, gridDims[a] bricks per axis all drawn from minLevel, and sets real gridDims / stride on the plan so chunkAtVoxel indexes it (multi-LOD plans previously returned a degenerate [1,1,1]). An axis grows when a brick would exceed deviceLimit, since emitBrick clamps an oversize texture and that squashes the sampling, so callers read the built plan's own gridDims back. The zarr demo gets a Blocks control (4 / 9 / 16) on top of it, choosing the factorization whose blocks come out closest to cubic, and reports what was built plus the asked-for count when an axis had to grow. Its lattice budget option is dropped as inert: the plan budget only shapes the octree, and GPU residency is capped separately by the renderer.
Per-pane block-loading badges in both the zarr block demo and the range demo. pending is the GPU upload QUEUE, not a finite work list (the octree re-requests its working set every frame), so the badge keys on the resident count moving, counts against what the stream actually asked for rather than the plan total (absent and empty bricks are never fetched and the LRU evicts), and holds a per-episode high-water mark so the bar only moves forward. Verified against a fake clock in isolation, then live on both backends.
DANDI app: one store, two viewers
VolumeSliceSource adapts a chunked volume store to the NVSlide tile source interface, so one OME-Zarr drives both the volumetric view and the deep-zoom pane without opening the store twice. apps/dandi-demo puts them side by side over a single zarrita byte cache: a plane the deep-zoom viewer already pulled costs the volumetric stream nothing. The panes link both ways (crosshair moves the slide plane, debounced; clicking the slide refocuses the multi-LOD budget). It lives in apps/ rather than packages/niivue/examples because its measuring ruler comes from @niivue/uikit, which builds against niivue's dist, and importing it from examples would close a cycle in the task graph. The ruler holds endpoints in slide base pixels and scales each leg by its own axis spacing, so it stays pinned to tissue through pan, zoom and level swaps on anisotropic planes.
Three verified stores: a 106 MB OCT block, the 4.5 GB OCT volume it comes from, and a 17.7 GB light-sheet SPIM. On the 30 GB NeuN slab, the ruler reads 2.96 mm on WebGPU and 550 um on WebGL2, both matching the level's um-per-pixel by hand.
Known remaining
Residual LOD seams. At the refitted default the measured step across a level boundary is about -10% on hoa_heart, down from +36%. No single coefficient nulls every dataset (sparse thin material wants ~0.11, dense structure ~0.05), so closing the rest is structural: cross-LOD blending at brick faces, or publishing a coverage-preserving pyramid. The max/mean blend prototype landed every measured region within 4% at every level and is the stronger lead. Tracked in docs/streaming-todos.md.
OME-NGFF translation still never reaches a streamed volume's affine. Measured on hoa_heart, every level's translation is exactly half its own scale, which is the voxel-centre convention rather than a world origin, so for this store the gap is a uniform half-voxel shift with no inter-level misregistration. It still matters for any store declaring a real world origin. Shape of the fix is written up in the TODO; vox.block.pick.zarr.html prints the numbers so the convention is visible.
Verification
nx affected -t format lint typecheck test build, check-boundaries, and codespell all green. 1191 unit tests pass. Rendering changes verified manually in the browser on both backends via each demo's ?backend=webgl2|webgpu switch.
Not verified by a live test: the context-recovery path. I could not get a context loss to reproduce on demand (five rapid refocuses across all six faces held), so that path is verified by construction and typecheck only.

```
Double-clicking a cavity opened up by the clip plane in the range demo
moved the crosshair to the volume's outer bounding box instead of the
tissue under the cursor. A chunked/multi-LOD volume has no whole-volume
texture, so depthPick cannot run its GPU readback pass and falls back to
CPU ray math. Three gaps made that fallback useless:

- Nothing ever set NVImage.pickSampler, so the CPU path could only ever
  return the box entry point. NVChunkedVolume now installs a sampler
  backed by its coarse floor. It is built in the constructor, before
  init() adds the volume, because prepareVolume shallow-copies the
  NVImage at addVolume time and anything attached later never reaches
  the mounted copy.
- clipRaySegment skipped clip handling entirely in cutaway mode, so a
  carved-away region stayed pickable. It now mirrors the shader: the
  kept interval is what a cutaway removes, returned as a skipMin/skipMax
  slab that rayBoxEntryMM advances past and rayMarchFirstVisibleMM
  steps over.
- A null march result fell through to the GPU pass that cannot sample
  the volume. Both views now march first and fall back to the box or
  clip surface, which is what the shader does on its own miss.

Verified in examples/range.html on the HOA heart with a solid clip
plane and in cutaway mode, on both WebGL2 and WebGPU: picks land on
tissue, never inside the removed half.
```

fix(niivue): oversample the 3D ray march to kill render ringing
…
6843b5b
```
The fine ray march took exactly one sample per voxel, which sits at the
Nyquist limit of the trilinear reconstruction. The ray integral is then
quantized against a sample lattice coherent across the screen, painting
concentric "wood grain" rings over smooth structures. It is not a chunked
or multi-LOD artifact: the single-level, non-chunked coarse floor shows
the same rings.

Add volumeSampleRate (samples per voxel along the ray), default 2,
clamped to [1,4], on both backends. Measured over a fixed camera and
fixed residency, the detrended high-frequency residual RMS of a 512x512
patch falls 11.94 (rate 1) -> 8.30 (2) -> 7.94 (3) -> 7.85 (4), and mean
luminance falls 66.5 -> 61.7 -> 60.8, confirming rate 1 was systematically
over-estimating the ray integral. Cost in the worst case tested (retina,
2.6x zoom, 168 brick cube draws) is 48ms -> 80ms per frame at rate 2.

The stepRatio clamp at >= 1 had to go now that oversampling is possible,
or the opacity correction would under-compensate. The empty-space skip
scales with the rate so the fast pass still strides 1.9 voxels of real
distance. The fine-loop cap goes 2048 -> 8192 to accommodate rate 4; every
loop exits on ray length long before that. WebGPU carries the rate in the
former pad lane of rayStepTexVox, so the uniform struct size and offsets
are unchanged. Depth picking stays at one sample per voxel.

Also re-anchor the fast-to-fine handoff onto the ray's own sample lattice
(snapToSampleLattice). The fast pass strides 1.9 voxels, not a whole
number of fine steps, so resuming the fine march where the fast pass
stopped left the fine lattice with a phase set by floor(depth / 1.9) -- a
sawtooth in depth-to-first-hit that shifted a chunk's samples whenever a
neighbour changed where empty-space skipping ended. Real defect, though
it was not the cause of the rings.
```

fix(niivue): tile ray slabs exactly across LOD brick boundaries
…
93a57ae
```
Each fine sample now owns the slab it is the midpoint of, clipped to the
brick's own [0, len] segment, and that slab thickness drives the opacity
(step-size) correction instead of a constant per-brick stepRatio.

Same-level neighbours already tiled correctly because they share the
global sample lattice. At a LOD interface they do not: the step-D and
step-2D lattices are both centered but do not nest, so the boundary
gained or lost up to ~1.5 fine steps of optical depth and drew as a
bright or dark seam along every level change. Attributing the ray length
each sample actually owns makes the slabs sum to len exactly for any
lattice phase, so a brick contributes the same optical depth regardless
of where its samples fall.

The correction factor is now refPerLen (reference steps per unit ray
length) and is left unclamped: a coarse brick owns longer slabs and
scales up, oversampling owns shorter ones and scales down, and both
directions are correct.

Mirrored in the WGSL renderer for backend parity.
```

fix(niivue): render the coarse floor as volume, not a dark shell
…
afa8dfb
```
Two independent defects made a floor-backed brick (any region whose fine
chunk is not resident) render as a flat dark shell instead of coarse
detail, which read as "black blocks" next to the streamed fine ones.

1. The floor was baked with `overlayOpacity = 1`, which selects the
   overlay path in the orient shader and makes alpha binary
   (`a = step(0, a)`). Every voxel above threshold came out fully
   opaque. The base volume and every streamed chunk bake with 0 (alpha
   straight from the colormap LUT), so the floor was the odd one out.
   Measured on the coarse texture: alpha was 255 for 100% of non-empty
   voxels before, a 57-69 mean ramp after.

2. The floor cubes marched at the fine common grid's density
   (`rayStepTexVox = volumeTexDimsFull`) while sampling a texture ~64x
   coarser. The step-size correction gives each step an optical depth of
   `fineVoxels / steps` reference steps, so the first in-tissue sample
   saturated to alpha 1 and the ray terminated on the outer surface.
   They now march at the floor texture's own voxel density, matching an
   equivalent coarse-level brick draw.

Both land on WebGL2 and WebGPU. Measured in examples/range.html on
hoa_heart (5787x5943x7865, 176 bricks, all but one forced to the floor
path), crop luminance mean / max:

  binary alpha, fine-grid steps   6.94 /  63.4   (before)
  binary alpha, floor-dim steps  14.69 / 147
  LUT alpha,    fine-grid steps  25.87 /  63.4
  LUT alpha,    floor-dim steps  32.28 / 177     (after)

For reference the same level-6 data drawn through the normal brick path
measures 29.56 / 92, and the resident fine bricks reach 233.
```

feat(niivue): opt-in tricubic B-spline volume reconstruction
…
5669e52
```
Adds volumeIsCubicInterpolation (default false) on both backends. When set,
the 3D fine ray-march reconstructs the volume texture with a cubic B-spline
built from 8 hardware-trilinear fetches instead of a single trilinear fetch.

Hardware trilinear is only C0, so band edges in a dense scalar volume carry a
blocky texel staircase. The B-spline is C2 and removes it. It is approximating
rather than interpolating, so it cannot overshoot: it does not introduce new
ringing, and it does not remove the concentric ringing in the HOA heart data
either (that survives a C2 reconstruction unchanged).

The fast skip pass stays trilinear; it only needs a coarse alpha test, so
8 fetches there would be waste.

Chunk safety: the filter reaches 2 texels either side of the sample, so a
chunked volume needs a brick halo of at least 2 for brick faces to reconstruct
from real neighbour data. Each chunk cube binds its own sampler, so the cubic
coordinates already use that chunk's own dimensions and halo.

Cost on a 240-brick mixed-LOD heart at 2 samples/voxel: 28.6 -> 58.1 ms/frame.
At 1 sample/voxel cubic runs 27.2 ms, so pairing the filter with a halved
sample rate is cheaper than trilinear at 2 and still staircase-free.
```

fix(niivue): never reconstruct cubic from clamp-to-edge brick data
…
601480c
```
sampleTricubic reaches texels idx-1 .. idx+2, so it needs two source
voxels past a brick's owned data at every internal face. Streamed chunks
default to a one-voxel halo, which is right for trilinear and for the
gradient tap but leaves the outermost cubic taps to be served by
clamp-to-edge, so two bricks reconstruct different values on a shared
face and the face shows as a seam.

Three parts:

- chunking.ts gains LINEAR_MIN_HALO / CUBIC_MIN_HALO, planSupportsHalo
  (true volume-boundary faces are exempt, clamp is correct there),
  planSupportsCubic and warnIfCubicUnsafe (warn-once per volume,
  re-armed if a volume goes safe then unsafe again).
- Turning the filter on re-plans what is already loaded:
  NVChunkedVolume.raiseHaloTo() raises the plan's halo and refocuses,
  and NVControlBase keeps a registry of live chunked volumes so the
  volumeIsCubicInterpolation setter can call it on each. The public
  default halo stays [1,1,1], so trilinear rendering pays nothing.
- Both views gate cubic per draw on planSupportsCubic(plan) and on the
  volume not being a label volume, the coarse-floor cube included, so a
  plan that still cannot feed the kernel falls back to trilinear with a
  warning rather than seaming silently.

Verified on both backends with a fixed camera and frozen streaming: with
the gate in place a cubic frame is pixel-identical to the linear frame on
an unsafe plan, and forcing the gate open reproduces the seams (WebGL2
53858 differing pixels, WebGPU 1023026). With a sufficient halo the
filter engages and the plan reports safe. Level-dependent kernel width
across pyramid levels was measured and left as is: cubic lowers
gradient energy in every direction (row 1.278 -> 1.020, column 0.627 ->
0.537, diagonal 1.929 -> 1.473) and adds no interior discontinuity, so
the reconstruction stays uniform across levels.

chunkHalo.test.ts is a CPU replica of the shader kernel: trilinear exact
at halo 1, tricubic exact at halo 2, tricubic wrong at halo 1.
```

fix(niivue): probe one stride past a cube's exit face in the empty-sp…
…
a00e6b0
```
…ace skip

Each chunk (and each coarse-floor cube) restarts the fast empty-space skip at
its own entry face and walks in 1.9-voxel strides. The loop stopped at
samplePos.a > len, so any material lying in the last sub-stride of a cube was
never probed: the cube reported "found nothing", contributed zero, and its exit
face showed as a discontinuity. The skip is therefore not subdivision
invariant, and the same ray split across two cubes does not reproduce the
single-cube result.

Let the probe run one stride past the segment end (fastLimit = len +
stepSizeFast), reading halo or clamp-to-edge texels. This can only ever produce
a false HIT, and the fine march that follows is still clipped to [0, len], so
an over-eager probe costs a few empty samples and changes no output.

A CPU replica of one cube's march over a realistic alpha band (peak 0.03, sigma
0.02) measures worst-case error against the unsplit march improving from
-3.99% to +0.68% for a two-cube split, and from -3.82% to -0.62% over an
eight-cube sweep, with the spread across split offsets dropping from 4.43% to
1.23%.

On the HOA heart at a pinned LOD 4 this reduces whole-image total variation by
2.7% (x) and 2.2% (y) with no visible regression, verified on both backends.
It does NOT remove the residual straight seam lines seen at some cube face
planes, which are a separate defect still under investigation.
```

```
Moving the crosshair to the opposite face of a clipped volume made the
WebGL2 range demo stop streaming and blank the volume.

draw() early-returned on a null volumeTexture/volumeGradientTexture. For a
chunked volume those fields are only a best-effort alias of chunk 0 -- the
real textures are bound per chunk (and the coarse-floor cubes bind the floor
textures) -- so a refocus that evicts chunk 0 silently killed the whole
volume. WebGPU already branched on the chunked entry before its equivalent
guard, which is why the report was WebGL2-only.

Two related dangling-pointer paths fixed alongside it:

- swapChunkedVolumePlan never refreshed the aliases after manager.remap()
  destroyed every chunk the new plan does not match, so they could name a
  deleted texture. All three sites now go through _syncChunkedAliases.
- Switching from a chunked volume to a single one let the single-volume path
  delete whatever it found in the aliases, freeing textures the chunked cache
  entry still owns. The pointers are dropped before that path runs.

```
feat(niivue): rebuild the view after a GPU context loss
…
a1dcf4c
```
A lost GPU context was permanent. NVViewGL latched _contextLost and stopped
rendering, and its 'webglcontextlost' listener was { once: true }, so a
second loss was not even reported. Streaming froze mid-plan with no
indication of why.

Both views now expose an onContextLost hook, wired by the controller inside
its RAF callback so it survives view recreation (the same treatment
overlayDraw gets). WebGL2 calls preventDefault() on the loss -- which is what
makes the browser promise a replacement -- and fires the hook on
'webglcontextrestored'; WebGPU has no restored event, so it fires straight
from device.lost, with a _destroyed latch so a deliberate teardown does not
ask for a rebuild.

The controller rebuilds the view via recreateView, capped at two attempts
since a scene that genuinely does not fit in VRAM would otherwise loop
forever. A canvas overlay says the view is rebuilding, and on giving up says
the GPU most likely ran out of memory and to load less at once.
```

```
The demo asked for an 8 GB GPU residency budget against a 2 GB plan budget,
```

feat(niivue): compensate coarse-LOD dimness and gamma the 2D slices
…
9d0c937
```
Downsampling averages voxels, which destroys the correlation between a
sample's colour and its opacity. Front-to-back compositing weights colour
by opacity, so a coarse brick integrates darker than the fine data it
stands in for: a level-3 brick reads roughly 16% dim next to level 0.

Correct it with a per-chunk exponent e = 1 - c * (k - 1), where k is the
geometric mean of the per-axis downsample ratios for that brick's source
level and c is volumeLodBrightnessCompensation (default 0.022, fit
against the pig-heart pyramid: mean brightness error across levels 1-3
drops from 7.5% to 1.5%). The exponent multiplies the existing gamma
exponent, so a brick at level 0 (or any single-level plan) is an exact
no-op and nothing changes for non-chunked volumes. Sparse materials stay
under-corrected; the deficit is data-dependent and this is a heuristic.

It rides a draw-time uniform rather than being baked into the orient
prepass colour texture. The prepass is the shared colour source for both
the ray-march and the slice tiles, so baking there would be the smaller
diff, but it would force a re-upload of every resident chunk on every
slider tick, add a second 8-bit quantization, and freeze the coefficient
at upload time.

Gamma now also reaches the 2D slice tiles, which previously ignored it.
Both exponents ride the same lane in SliceUniforms (a free pad float, so
the struct does not grow), and the views push the same two values to the
slice renderer and the volume renderer so a slice and the render panel
agree on brightness.

Both exponents apply to intensity-derived layers only. The 3D drawing
pass used to pick gamma up implicitly through rayMarchPass and now passes
1.0, matching the V1 fiber-direction branch in the slice shaders: those
carry categorical label colours and encoded vectors, not luminance, and a
pow() would bend them.

Verified on both backends against the pawpawsaurus OME-Zarr pyramid
(level 2 bricks): the coefficient moves the mean monotonically in 3D and
2D, WebGPU and WebGL2 agree to within 0.3/255, and returning to 0
reproduces the original frame.
```

```
The ray-march already raises a coarse sample's alpha to the number of
reference steps it stands for, which is exact only if the coarse voxel is
homogeneous. It is not: the true transmittance through the k fine voxels
the brick replaces is prod(1-a_i), and since log(1-a) is concave that
product is smaller than (1-mean(a))^k, so a coarse brick is systematically
too see-through by an amount set by the intensity variance inside it.

volumeLodOpacityCompensation scales that exponent by 1 + c*(k-1)
(lodOpacityScale, capped at 8x). Both backends, ray-march only: a 2D slice
tile shows one sample with no accumulation, so there is no aggregated alpha
to correct there.

It defaults to 0, and that is a measured choice. Simulating the march over
a real OME-Zarr pyramid says the variance term is ~0 wherever structure is
dense enough to saturate the ray; inflating alpha there only front-loads
accumulation onto the nearer, dimmer samples and makes the accumulated
colour worse. Over four probe regions, raising c from 0 to 0.5 cut mean
alpha error from 6.7% to 5.1% while driving colour error from 15.3% to
25.7%. Sparse thin material has a genuine deficit (~-30% at level 3) but no
global scale recovers much of it: c=0.5 improves it to -30.6%. Fixing that
case needs a coverage-preserving pyramid, not a renderer knob.

level 1, mixed levels 1-2): mean falls 16.016 -> 15.907 on WebGL2 and
15.952 -> 15.826 on WebGPU across c = 0 -> 0.35, matching the CPU
prediction that inflating alpha lowers accumulated colour, and 0 restores
```

feat(niivue): demote an evicted chunk to a decoded tier instead of dr…
…
e166f92
```
…opping it

A chunked volume's GPU residency is a fixed byte budget, so a moving view
evicts bricks constantly, and an evicted brick cost a full fetch + decode +
assemble + upload to bring back. Hold its decoded source bytes instead, so
its return costs only a texture upload.

The tier necessarily shadows the resident set: to have an evicted chunk's
bytes you must still hold them at the moment of eviction, so a tier that
drops bytes on upload has nothing to demote later. That shadow is affordable
because source voxels are 1-4 bytes against the GPU's 8 (RGBA8 color + RGBA8
gradient), so decodedTierBudgetBytes sizes the tier at the shadow plus a 50%
tail, scaled by datatype and capped at 384 MiB. Eviction is plain LRU, which
is what the structure wants: the newest entries are the chunks still on the
GPU and the oldest are the chunks evicted longest ago, so dropping from the
old end keeps exactly the frontier a reversal crosses back over.

The tier is owned by the render entry, not the uploader, so it survives an
uploader rebuild: a colormap or window change now re-orients bytes it already
holds instead of re-fetching every chunk. A multi-LOD plan swap re-keys it
with the same content match the residency manager uses.
```

feat(niivue): cache OME-Zarr chunk bytes across sessions
…
d6037b6
```
Every tier we have dies on reload. For a DANDI volume over S3 that is the
most visible cost left: the second visit re-fetches what the first one
already paid for.

This adds a persistent tier of raw compressed store bytes, below the byte
LRU and above the fetch store, so it only ever sees what memory could not
answer. Persisting at that layer is format-agnostic, keyed by something
already stable (the store key), and is the smallest form a chunk has.

Cache Storage has no size bound and no eviction, so our in-memory index is
the budget: each entry's byte length rides in its backing key, and one
keys() listing rebuilds both the index and the accounting without reading
a body. Absences are deliberately not persisted -- bytes never change, but
a missing chunk in a store still being written can become bytes tomorrow.

With the worker pool running the workers share one backing and own a scope
apiece, which is sound because routing is deterministic: a brick always
returns to the worker that holds it.

Off by default (it writes to the user's disk). The DANDI demo opts in with
512 MB and reports the warm-start rate in its HUD.
```

fix(niivue): anchor the 2D wheel zoom on the crosshair
…

```
The pan/zoom wheel handler meant to hold the crosshair still while the
zoom changed, but compensated with

  pan2 = pan1 + (zoom1 - zoom2) * mm

which is wrong twice over. calculateMvpMatrix2D scales the ortho window
about the CENTRE of the volume's mm extents, so the offset has to be
measured from that centre rather than from the world origin; and holding
a point across a zoom change takes a RATIO of the two zooms, not their
difference. The inverse of that window is

  pan2 = (zoom1 / zoom2) * (d + pan1) - d,  d = anchorMM - centre

so the old term was off by a factor of the new zoom and drifted worse the
deeper you zoomed - five times too large at 5x - and drifted from the
first step on any volume whose mm origin is not its centre.

The compensation now lives next to the transform it inverts, as
NVTransforms.zoomPan2DAbout: only that module knows how the window is
built, and keeping the pair adjacent is what stops them diverging again.
Radiological needs no special case - it negates the U axis and panU
together, which leaves the hold-fixed condition unchanged.

Tested against the real calculateMvpMatrix2D rather than by restating the
algebra, since the bug was a compensation that disagreed with the window
the renderer actually builds: project the anchor before and after a zoom
step and assert its clip position is unchanged, over an off-centre
volume, a 20-step deep zoom, radiological, a non-zero starting pan, and
all three tile permutations.
```

fix(niivue): make crosshairWidth canvas pixels everywhere

```
crosshairWidth was a world-mm cylinder radius on 2D slice tiles and on the
3D render tile, but a canvas-pixel thickness in the mosaic cross-lines path.
The same number therefore meant two different things, and on the mm side the
drawn weight tracked the volume's field of view and the tile's zoom: a small
2D tile drew a hairline while a large render tile drew a fat bar, and zooming
in thickened the crosshair.

Canvas pixels win, since that is what a screen weight should be. Both
projections are orthographic, so each tile has a single depth-independent
mm-per-pixel and an orthographically projected cylinder is exactly 2r wide
from any angle: mmPerPixel2D and mmPerPixelRender invert the two matrix
builders, and crosshairRadiusMM turns the requested pixel width into that
tile's world radius at draw time. The default stays 1.

Each tile now rebuilds the geometry for its own radius. WebGL2 keeps its
single buffer set and skips the upload when nothing that shapes the geometry
moved; WebGPU cannot rewrite one buffer between draws inside a frame (all
queue writes land before the submit), so each drawing tile takes its own
vertex-buffer slot, mirroring the per-tile uniform dynamic offsets.
```

fix(niivue): reject non-finite chunk loader limits
…
a9188a6
```
maxConcurrentLoads and retryAttempts are public options on NVChunkedVolume,
and both are safety limits. The clamp caught 0, negatives, NaN and fractions
but not Infinity, which survives Math.floor and Math.max untouched and so
defeats the exact bound it is asked to impose:

  maxConcurrentLoads: Infinity leaves `active < maxConcurrent` permanently
  true, removing the flood cap (measured: all 5 concurrent reads in flight
  at once instead of the intended bound).

  retryAttempts: Infinity is the worse half. withRetry's loop never ends, so
  a transient fetch failure retries forever on a backoff of 80 * 2 ** i that
  overflows to Infinity around i = 1024, leaving the read parked on a delay
  that never resolves.

Route both through positiveIntOption, which rejects any non-finite input to
the same floor of 1 the other unusable values already land on.

Tests cover Infinity on both options; each fails against the old clamp (5
concurrent reads, and still retrying at 500ms) and passes with the guard.
The NaN and fractional case is added as a characterization test: the old
clamp already handled those, and this pins that down.
```
fix(niivue): keep the slide tile cap when given Infinity or NaN
…
e21df06
```
Same defect class as the chunk loader limits, found while reviewing them.
NVSlide's cap was a bare Math.max(1, x), which passes Infinity and NaN
through untouched. Neither raises the cap, both remove it: every capacity
test is `_activeLoads >= cap`, false for either value, so no tile is ever
queued and every request goes straight to _runLoad. Measured on a 30-tile
manifest: peak concurrency 30 instead of the intended 12.

Flooring also makes the effective cap match the number asked for; 2.5
previously admitted a third load.

Non-finite input falls back to the documented default of 12 rather than to
1 as the chunk loader does. The difference is deliberate: createSourceChunkLoader
receives values its caller has already defaulted, so it cannot know the
intended default and 1 is its safe floor, whereas here the default is in
scope and serializing tile loads to 1 would be its own performance bug.

NVSlide is not otherwise touched by this branch, so this is a standalone
commit that can be dropped without affecting the rest.
```
