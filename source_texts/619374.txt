After looking into OptiX for a while, I found that
There is only triangle, curves and general custom pipeline in OptiX. Thus, for your AABB request, it may be better to convert it into 12 triangles than implementing a custom pipeline, because implementing a custom pipeline means no RT hardware will be used for AABB hit record generation.
Implementing individual ray length feature on my side is equivalent to use the maximum for the far parameter and filter with torch later.
Certain features in OptiX only support the closest hit. If you need one call for all hits, the input/output buffer protocol for variable length hits is also hard to design, with huge efforts synchronizing between GPU threads required to collect the hit records for all hits. The usual solution is to emit a new ray at the hit point until nothing is hit again.

TorchOptiX is aimed for a minimal and modular design for tracing rays in torch.
As far as I see, the MOCHI algorithm is perfectly fine to implement in PyTorch with TorchOptix. You just express all operations in PyTorch. The only thing is there are many memory operations that can be fused by writing cuda instead of python and thus this is not optimally efficient. But in contrast, you get for free a differentiabile algorithm of ops other than tracing hits.
If you do need an optimally efficient implementation for collision detection, and do not need differentiability, TorchOptiX is not designed for this. I guess you can look for MOCHI implementations and add a binding layer to pytorch.
I am personally interested in writing a library like OWL with python support/pytorch interop, but it will be until I finish my current projects.
