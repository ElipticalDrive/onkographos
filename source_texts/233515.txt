Summary
Add ability to render roads... and all the changes that it needed.
Showcase
Feature description
This PR adds two new tasks (RenderSurfacesTask and RenderLinesTask) replacing RenderVectorTask.
Beside that, it does a lot of code change in voxelization, mainly to allow passing arguments to voxelizers and change their behavior (that wasn't possible formerly).
These changes are not only useful for roads rendering but will also be used in facade rendering and maybe in future geometry handling (for example, it should make easy to shrink or grow drawn polygons).
A bit more in deep PR explanation
Switch from Voxelizable to Convertible
Before this change, voxelization was done using voxelizeXd method on a VoxelizableXd object. This did not give any control on how voxelization should be preformed (no possibility to pass any parameter to voxelizer).
This change brings a new way to perform voxelization:
1 - Instanciate a voxelizer (unfortunately no interface yet as voxelizer could provide any kind of positionedXd objects);
2 - Convert your Convertible...Xd object into something voxelizer could handle (most likely to be a ShapeXd object for vectors);
3 - Iterate over voxels using voxelize(...) voxelizer method;
During voxelizer instanciation various parameters may be provided to influence the voxelization algorithm.
For example, ThickLineatVoxelizer2d takes the thickness of lines to render. Maybe later it could have other parameters for how to draw angles and ends.
There is a shortcut to perform step 2 & 3 at once. Voxelizers directly take Covertible objects (no need to convert then voxelize).
Changes in ShapesXd interface and code
ShapeXd interface does not provide any voxelize* method anymore (they are replaced by voxelizer's voxelize(ShapeXd) method).
Instead it gives access to lines, lineStrings and polygons of the geometry (later it will probably give acces to points also).
Linear ring are now managed as specific shapes. This will allow to draw joints correctly all around and later, to distinguish interior and exterior side of the linearities.
Code concerning voxelization has been removed from ShapeXd objects (LineXd in particular). Now voxelization algorithm is entirely in voxelizer's code. Totally different algorithms can now cohabit without complexifying ShapeXd objects code.
LineXd index is not any more the number of the voxel in "thin line voxelization" algorithm. It is now the real distance (as decimal number) to the starting point. VectorXd classes has been introduced to manage floating point vectors and lines have a direction() unit vector easing a lot geometry computation.
Thick linear voxelizer
Main goal of this PR was to introduce road rendering which implies the ability to draw thick lines.
Thick linear iterators and voxelizer take a thickness value and browses all voxels belonging to a line of this thickness. Along with voxel coordinates, some more information are given: the position of that voxel in line relative coordinates ((0,0) is starting point, (length, 0) is ending point, (0, y) is on the right of the line and (0, -y) on its left). This is used to project textures on roads.
ThickLinearVoxelizer3d does not perform real 3d stuff but rather extrapolates ThickLinearVoxelizer2d results and adds a z component in proportion of the progression on the line. This is exaclty whats needed for roads (road is allways flat and horizontal from side to side) but if we need to voxelize pipes or tunnels we may need a real 3d voxelizer. Best would have been to have another name (like 2.5d) for this kind of voxelizer.
RenderVectorTask has been removed and replaced by two distinct tasks: RenderSurfacesTask and RenderLinesTask.
RenderSurfacesTask unlike RenderVectorTask is not able to remove border from polygons but this may be a future development (implying linear rings orientation). Only building renderer whas still using that capability and it's going to be rewritten.
A world on thick voxelization process
To draw thick lines, each line segment is drawn as a quadrilateral shapes. Two opposite sides, named "borders" are parallel to the drawn segment and two other sides, named "bevel", depends to neighboor segment. If there is no next/previous segment, bevel is orthogonal to segment. If there is a next/previous segment, bevel direction is the bissector of angle formed by neighboor segments. Bevel always contains line start or end (A or B point).
Once these four sides known (angle and position), bounding box of the segment to draw can be computed. Next step is to iterate through all X coordinates and compute the two intersection between x-scanline and two of bevel and/or borders. Voxels to return through iterator can then be listed.

J'ai poussé une refactorisation importante que je vais devoir squasher:
```
* Renommage de `LineXd` en `SegmentXd` et tout ce qui en découle;

* Suppression de `lines()` des interfaces `ShapeXd`;

* Suppression du `extends ShapeXd` sur `SegmentXd`, ex `LineXd`;
```
Pourquoi:
```
* "Segment" évidement plus clair que "Line" surtout si on introduit de vraies "Lines" (infinies).

* Il n'y a jamais de forme qui soient des lignes toutes seules. Et même s'il y en avait, on les modéliserait par des LineStrings mono-Segment.
```
Autre amélioration possible: avoir une classe LineXd et SegmentXd en hériterait. Ce sera plus facile à faire avec la possibilité en java 25 de faire des calculs avant d'appeler le super. Actuellement, ça force une petite désoptimisation.
PS: Je vais inclure tes suggestions
Au lieux d'enlever complétements cette declaration :
```
    /**
     * {@return iterable over all lines in the shape}
     */
    Iterable<Line2d> lines();
```
On pourrait pas juste :
```
    /**
     * {@return iterable over all segments in the shape}
     */
    Iterable<Segment2d> segments();
```
Le remplacer par segments
