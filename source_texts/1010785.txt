Automated change by O for SRT-80. It passed the company verify command and the review gate before this PR was opened.
Summary
sw has no pseudo-random number builtin, and I could not find string repetition or bitwise operations either. The only randomness source is uuid(). Programs that need random choices (chaos testing, simulations, load generators, shuffling) end up parsing hex digits out of a UUID.
Repro (all fail to compile on main @ ae943e8)
```
random(100)           -> swc: unknown function 'random'
string_repeat("ab",3) -> swc: unknown function 'string_repeat' — did you mean 'string_replace'?
bit_and(12, 10)       -> swc: unknown function 'bit_and'
```
docs/SW_LANGUAGE.md lists uuid() as "a random RFC-4122 v4 UUID string" and nothing else random (grep for rand|random|prng|shuffle|bit finds only that line). The bit-op names above were my guesses, so if bitwise operators exist under other names they are undocumented.
Real-world hit
swarm-live "Life at Scale" kills random cells for a chaos button. A linear-congruential hash over the cell index drew visible diagonal stripes on a 64x64 board, so I ended up with:
```
fun hexv(u, k) { v = ord(string_sub(u, k, 1))  if (v < 58) { v - 48 } else { v - 87 } }
fun rand_idx(n) {
    u = uuid()
    x = ((((hexv(u,0)*16 + hexv(u,1))*16 + hexv(u,2))*16 + hexv(u,3))*16 + hexv(u,4))*16 + hexv(u,5)
    x % n
}
```
It works but is a hack, allocates a string per draw, and cannot be seeded for reproducible runs.
Suggested fix
random(n) -> int in [0, n), plus random() -> float in [0, 1), backed by a per-scheduler PRNG (xoshiro/PCG), so no lock on the hot path.
random_seed(n) for reproducible tests.
string_repeat(s, n), and bitwise band/bor/bxor/bsl/bsr (or document them if they exist).
Env
swarmrt main @ ae943e8 (swc 2.1.0), macOS arm64.

I'm rejecting this PR: random_seed doesn't make random reproducible once other processes run, which is the main thing the docs promise.
Blocking finding
Seeded draws can't be reproduced when other processes run. The generator state lives on the scheduler thread, not on the process (src/swarmrt_lang.c:2640, static _Thread_local uint64_t g_prng[4]). Three things follow:
A seeded process that yields can resume on another scheduler and keep drawing from that scheduler's unseeded state.
Any other process on the same scheduler eats into the seeded sequence.
random_seed reseeds every process on that scheduler.
The docs line at docs/SW_LANGUAGE.md:765 says "seed … so random is reproducible", and that doesn't hold for chaos tests, simulations or load generators. Those are the issue's own use cases, and all of them spawn processes.
rep.sw (scratchpad): three spinner processes call random(5); main runs random_seed(42), makes 200k draws (a), waits in receive … after 20, then makes 1k more draws (b).
At SW_SCHEDULERS=1, three runs gave b = 110753693, 896919155 and 528166202, all different.
a also changes with the scheduler count: 408021424 at 1 scheduler, 983223923 at 4.
swc run gave the same split: 408021424 362360701 and then 408021424 298708556.
mig.sw (scratchpad): six spinners; main seeds, then loops 50 times over receive after 1 plus 50 draws. Three runs at SW_SCHEDULERS=4 printed 802844313, 287768436 and 292153969.
Fix: keep the state on the process (seeded lazily per process), so random_seed covers only the caller and its sequence follows it across schedulers. The new test only passes because it never yields or spawns.
Non-blocking
Every builtin already overrides a user function with the same name, in both backends: on base, a user fun uuid() is ignored. This PR adds seven common names (random, band, bor, …), so any user program that defines one now silently calls the builtin. For example, fun random(n) { 7 } printed 31 and 68 on the PR and 7 on base. Nothing in lib/, examples/ or tests/ defines these names.
Pointing the docs at Std.string_repeat is accurate; it already exists at lib/Std.sw:381.

Build: the rebuild printed no warnings at the new code (swarmrt_lang.c lines 2636–2700, or the codegen.c edits). Every warning shown points at older lines.
New tests: the compiled test passed earlier (O's run). The interpreted copy, swc run tests/sw/run/test_random_bits.sw, prints OK random_bits with exit code 0.
Can the test fail? I made two deliberate breaks: random_seed turned into a no-op, and bxor returning a | b. The test then reported FAIL seed_reproducible and FAIL bxor (exit code 1). I put the original file back, rebuilt, and the test passes again.
Beyond the issue: I probed the reproducibility runs above and the user-function name clashes. The CSPRNG call (arc4random_buf) is the same one uuid() already uses, so there's no new portability gap.
NOTE: Builtins override user functions with the same name, in both swc build and swc run, on base too: a user fun uuid() is ignored. Any PR adding a builtin with a common name silently changes programs that define that name.
