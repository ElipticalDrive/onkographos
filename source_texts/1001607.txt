Motivation
The direct load wavelet pipeline is using double buffer and VMEM to LDS loading with wave specialization.
This PR adds new gfx1250 specific features to improve performance of both memory and compute waves:
memory: TDM support for matrix B (it can not be applied to matrix A because of Im2Col loading from VMEM to LDS). This allows to issue a single instruction to load full B tile instead of multiple global_load_to_lds instructions that require also OOB checks
compute: use named barrier to synchronize only compute waves and generate ping-pong between ds_read and wmma instructions. This is useful because some instances could use more vgprs and by using this approach we can better hide ds_read latency at the cost of extra registers
JIRA ID : ROCM-27829
Technical Details
TDM:
ThreadGroupTensorSliceTransfer_TDM supports VMEM -> LDS loading using tensor instructions
amd_tdm.hpp holds scalar registers tensor descriptors encodings and it is based on the ones in ck tile (that already supports tdm)
Named Barrier ping-pong:
named barriers are exposed in amd_named_barrier.hpp through NamedBarrier struct
new Run method in BlockwiseGemmXdlops_k0mk1_k0nk1_m0n0m1n1m2m3m4n2_loop_knm_v1 implements the actual ping-pong
Instances:
2 new instances using only TDM because they don't have extra vgpr available for named barriers ping-pong
3 new instances using both TDM and named barrier ping-pong
split wavelet pipeline instances into multiple files

Review: #13718 — TDM and named barriers in wavelet pipeline conv fwd
PR: feat(ck): TDM and named barriers in wavelet pipeline conv fwd #13718
Author: EnricoDeg
Branch: users/enricodeg/ck/wavelet-tdm → develop
Scope: gfx1250-only. Adds Tensor Descriptor Memory (TDM) loads for matrix B and
AMDGPU named-barrier-based ping-pong scheduling to the Composable Kernel direct-load
wavelet-model conv-fwd pipeline. New instances for conv2d/conv3d f16/bf16.
Reviewed from the PR diff only (no local build/GPU run against this code was performed).
Findings
1. (Needs verification) Compile-time LDS-size guards were dropped from both wavelet kernel entry points
device_grouped_conv_fwd_multiple_abd_xdl_waveletmodel_cshuffle_v3.hpp, both
__global__ entry functions previously gated the __shared__ char p_shared[...]
declaration(s) with:
```
if constexpr(LDS_size <= get_lds_size(get_device_arch()))
{ ... declare p_shared and call GridwiseGemm::Run ... }
```
and
```
if constexpr(2 * LDS_size <= get_lds_size(get_device_arch()))
{ ... declare p_shared_0/p_shared_1 and call Run ... }
```
The PR removes both if constexpr wrappers, so the shared-memory array(s) and the
GridwiseGemm::Run call are now unconditional. CK traditionally instantiates every
tile config in an instance table across build archs, including ones whose
LDS requirement exceeds a given arch's actual LDS size — invalid combos are meant to be
filtered out at IsSupportedArgument/selection time, not at kernel-body compile
time. These if constexpr guards were presumably there to keep those over-sized
__shared__ declarations from reaching codegen for arch/tile combos that exceed
get_lds_size. With them gone, a tile size that's invalid for a given arch (new or
pre-existing non-TDM instances alike, since this is the general, non-TDM entry point)
could now fail to compile instead of being silently skipped, for whichever
archs are being targeted by this file's instantiations.
The PR does add an analogous check in GridwiseGemm_xdl_waveletmodel_cshuffle_conv_v3::IsValidCompilationParameter()
(num_buffers * LDS_size > get_lds_size(...) → return false), but that function
gates instance selection, not whether the kernel body itself compiles — it doesn't
by itself prevent __shared__ char p_shared[LDS_size] from being emitted for every
multi-arch build target.
Ask: confirm this compiles clean for every arch in the current GPU_TARGETS build
matrix (not just gfx1250), and that no existing non-TDM wavelet instance has a tile
config whose LDS_size exceeds some other target's LDS budget.
2. (Needs verification) NamedBarrier::Join() is called every Run(), never paired with a Leave()
In the new named-barrier specialization of
BlockwiseGemmXdlops_k0mk1_k0nk1_m0n0m1n1m2m3m4n2_loop_knm_v1::Run, the first line is
barrier.Join(). This Run() overload is invoked twice per main-loop iteration (A0/B0
and A1/B1) via GridwiseGemmMathWave::RunMathWavePipeline, so Join() fires many times
per kernel over the lifetime of the barrier, and there is no corresponding Leave()
anywhere in the new NamedBarrier struct or its call sites. If s_barrier_join is not
idempotent for a wave that's already a participant (vs. a pure "declare membership"
op), repeated joins without an intervening leave could desync the barrier's expected
participant count over many loop iterations, which would surface as a hang on real
hardware rather than a compile error — exactly the kind of bug that's easy to miss in
code review and only shows up at scale/iteration count. Worth double-checking against
the AMDGPU named-barrier intrinsic semantics (s_barrier_init/join/leave/wait) and,
ideally, soaking a large-K-loop shape to rule out iteration-count-dependent hangs.
3. (Minor / doc accuracy) "WMMA" terminology in xdlops (MFMA) code
The PR description says ping-pong scheduling happens "between ds_read and WMMA
instructions," and the new code in blockwise_gemm_xdlops.hpp itself comments "Wmma
step consumes subtiles" / "wmma cycles to hide latency" / uses mfma_input_type_a
alongside those comments. This file is the xdlops (MFMA) blockwise-gemm, not the
WMMA one — gfx1250 here is presumably being driven through the MFMA/xdlops path. The
comments read as if lifted from a WMMA-pipeline implementation. Not a functional issue,
but worth fixing so future readers aren't misled about which matrix unit is involved.
4. (Style) Alias shadows template name
```
using NamedBarrier = NamedBarrier<TileMathThreadGroup, UseNamedBarrier>;
```
Using the same identifier for both the class template and the instantiated alias is
legal C++ but reads confusingly on a diff/grep and in compiler diagnostics (errors
inside NamedBarrier<...> will reference the alias, not obviously the template). A
distinct alias name (e.g. MathWaveBarrier) would be clearer.
5. (Low severity / for the record) wait_dscnt<cnt>() encoding changes
synchronization.hpp's wait_dscnt went from a hardcoded "wait for ds-count 0" to a
templated wait_dscnt<cnt>() that waits for an arbitrary ds-count, needed by the new
TDM/ping-pong fine-grained synchronization. Spot-checked the bit arithmetic for cnt = 0 against the previous hardcoded constants for all three branches (gfx12, gfx11,
pre-gfx11) and they reduce to the same values (0xfc07, 0xc07f), so the refactor
looks encoding-correct for the old call sites. The gfx11 branch masks cnt to 6 bits
(& 0x3F) and the pre-gfx11 branch to 4 bits (& 0x0F), consistent with each arch's
differing s_waitcnt LGKMCNT/DSCNT field width — this looks right, but is worth a
second pair of eyes since it's inline assembly-adjacent bit-packing with no unit test
visible in this diff.
6. Test coverage is not visible in this diff
No test files are touched by this PR (only kernel/device headers, library instance
tables, and new instance .cpp registration files). Given the repo's own
documented norm (CK: never land a perf/scheduling change without a parity run), and
that this PR touches low-level synchronization primitives (named barriers) and a new
HW load path (TDM) with real correctness risk (findings #1 and #2), it's worth
confirming in the PR thread that the existing grouped-conv-fwd correctness/parity
suite was actually run against the five new instances on real gfx1250 hardware, not
just compiled.
Positive notes
The feature is correctly gated behind is_tdm_supported/is_named_barrier_supported
(both gfx125_t-only) and IsSupportedArgument rejects the config on other archs at
runtime with a logged message.
static_assert(!((UseTdm || UseNamedBarrier) && !DirectLoad), ...) correctly encodes
that both features are only meaningful under the direct-load pipeline.
The B-grid-descriptor GemmN computation (GetLength(I1) vs GetLength(I0)) is
consistently updated at all four call sites to account for TDM's [N, K] vs.
[BK0, N, BK1] descriptor shape — this is the kind of thing that's easy to miss in
one spot and I checked all occurrences; they're consistent.
TransformLdsDescTdm's merge-transform dimension mapping was checked by hand against
the stated [BK0, N, BK1] → [N, K] intent and is correct.
Reasonable new instance variants (_Tdm, _PingPong name suffixes) and factory
wiring (grouped_convolution_forward.hpp, .inc decls, CMakeLists.txt) all look
complete and consistently threaded through for both conv2d and conv3d, f16/bf16.
Overall
Net-additive, clearly scoped to gfx1250, with sensible fallback behavior for other
archs. The two items worth getting a second opinion on before merge are #1 (dropped
compile-time LDS guard in the kernel entry point — a potential build-matrix regression)
and #2 (repeated Join() without Leave() — a potential long-run hang risk). Both are
plausible-but-unconfirmed from static reading of the diff; recommend asking the author
to confirm against the full build matrix and a multi-iteration correctness/perf run
before approving if not already done.

feat(ck): TDM and named barriers in wavelet pipeline conv fwd
 (#13718)

## Motivation

The direct load wavelet pipeline is using double buffer and VMEM to LDS
loading with wave specialization.
This PR adds new gfx1250 specific features to improve performance of
both memory and compute waves:

- memory: TDM support for matrix B (it can not be applied to matrix A
because of Im2Col loading from VMEM to LDS). This allows to issue a
single instruction to load full B tile instead of multiple
global_load_to_lds instructions that require also OOB checks
- compute: use named barrier to synchronize only compute waves and
generate ping-pong between ds_read and wmma instructions. This is useful
because some instances could use more vgprs and by using this approach
we can better hide ds_read latency at the cost of extra registers

JIRA ID : ROCM-27829

## Technical Details

TDM:
- `ThreadGroupTensorSliceTransfer_TDM` supports VMEM -> LDS loading
using tensor instructions
- `amd_tdm.hpp` holds scalar registers tensor descriptors encodings and
it is based on the ones in ck tile (that already supports tdm)

Named Barrier ping-pong:
- named barriers are exposed in `amd_named_barrier.hpp` through
`NamedBarrier` struct
- new Run method in
`BlockwiseGemmXdlops_k0mk1_k0nk1_m0n0m1n1m2m3m4n2_loop_knm_v1`
implements the actual ping-pong

Instances:

feat(ck): TDM and named barriers in wavelet pipeline conv fwd
 (#13718)

## Motivation

The direct load wavelet pipeline is using double buffer and VMEM to LDS
loading with wave specialization.
This PR adds new gfx1250 specific features to improve performance of
both memory and compute waves:

- memory: TDM support for matrix B (it can not be applied to matrix A
because of Im2Col loading from VMEM to LDS). This allows to issue a
single instruction to load full B tile instead of multiple
global_load_to_lds instructions that require also OOB checks
- compute: use named barrier to synchronize only compute waves and
generate ping-pong between ds_read and wmma instructions. This is useful
because some instances could use more vgprs and by using this approach
we can better hide ds_read latency at the cost of extra registers

JIRA ID : ROCM-27829

## Technical Details

TDM:
- `ThreadGroupTensorSliceTransfer_TDM` supports VMEM -> LDS loading
using tensor instructions
- `amd_tdm.hpp` holds scalar registers tensor descriptors encodings and
it is based on the ones in ck tile (that already supports tdm)

Named Barrier ping-pong:
- named barriers are exposed in `amd_named_barrier.hpp` through
`NamedBarrier` struct
- new Run method in
`BlockwiseGemmXdlops_k0mk1_k0nk1_m0n0m1n1m2m3m4n2_loop_knm_v1`
implements the actual ping-pong

Instances:
- 2 new instances using only TDM because they don't have extra vgpr
available for named barriers ping-pong
 - 3 new instances using both TDM and named barrier ping-pong
 - split wavelet pipeline instances into multiple files
