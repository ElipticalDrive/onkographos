GaussianSplatGroup renders multiple independently transformed Gaussian splat clouds with a shared depth sort and one instanced draw. This allows overlapping clouds to alpha-blend against each other, unlike separate GaussianSplat objects.
Requires WebGPURenderer. WebGPU sorts on the GPU; the WebGL2 fallback (forceWebGL: true) sorts on the CPU.
Usage
```
import { GaussianSplatGroup } from 'three/addons/objects/GaussianSplatGroup.js';

const group = new GaussianSplatGroup();
scene.add( group );

const idA = group.addSplat( splatGeometryA );
const idB = group.addSplat( splatGeometryB );

group.setMatrixAt( idA, matrixA );
group.setMatrixAt( idB, matrixB );

renderer.render( scene, camera );
```
addSplat() accepts the same geometry attributes as GaussianSplat and returns an ID for setMatrixAt(), setVisibleAt(), and deleteSplat(). Updates happen automatically during rendering. The group retains caller-owned source geometries for compaction and raycasting; their attributes should remain unchanged while added. Disposing the group does not dispose these source geometries.
Incremental allocation
Adding a cloud packs it into the first free range that fits and queues uploads for that range.
Deleting a cloud marks its slots inactive and frees its range for reuse. Existing clouds stay in place.
Hidden clouds remain resident. Visibility and transform changes update record data without repacking splats.
When no contiguous range fits, capacity grows by at least doubling. Existing arrays are copied into replacement buffers and uploaded in full, preserving cloud offsets. A fragmentation fallback can still require a full repack.
compact() explicitly repacks every retained cloud, including hidden clouds, and shrinks capacity to fit. Buffers never shrink automatically; autoCompact has been removed.
One counting sort orders the entire allocated capacity, routing hidden and unused slots after the visible draw range. Retaining capacity and hidden clouds reduces streaming update costs at the expense of memory and sorting work. Deletion currently queues updates for all per-splat attributes in the freed range.
Options
initialSize: preallocates splat capacity. Fragmentation can still require growth before all slots are occupied.
shDegree (default 2, integer 0–3): fixed spherical harmonics degree; missing bands are padded with neutral coefficients and extra source bands are truncated.
binCount (default 4096): depth sort resolution.
workgroupSize (default 256): compute workgroup size.
The example is examples/webgpu_gaussian_splat_group.html. It compares grouped and independent rendering and exposes visibility and compaction controls.
The implementation also shares packing, shading, and covariance-aware bounds with GaussianSplat, retains the loader optimizations and spherical harmonics irradiance refactor, and adds regression coverage for culling, raycasting, and rendering after buffer growth and compaction on both backends.

Thanks Ben! And sorry for the delay - I've put together a demo here showing the GaussianSplatGroup usage with 3DTilesRendererJS (repo here).
There are still some significant frame spikes due to repacking the gaussian splats CPU-side and reuploading every time the splats change. With 3d tiles the tiles (and therefore the splats) change basically every time the camera moves / new content loads so it's an expensive event that happens frequently. I'm running on an Macbook M1 Pro, which uses a 120hz screen, so this rebuild step alone is 100% of the frame budget.
BatchedMesh deals with this by allowing for space pre-allocation of a certain size so we can reupload the just the one or two geometries that will have changed rather than the full geometry buffer every time. Though I think this is a more common need for BatchedMesh than it will be for splats in general, and necessarily requires some user-side management.
A couple options that come to mind for splats that may help address this without being too complicated (hopefully) or require user management:
My previous prototype kept all the GaussianSplatMesh buffers on the GPU and performed the "merged" buffer rebuild entirely on the GPU using compute kernels, which avoided the CPU-side rebuild and upload penalty. This of course means a bit of a waste of GPU memory but it's fast.
We could use a memory paging system where splats are uploaded split among multiple pages, which would mean we can avoid reuploading splats that are already inserted. This means that the splats for a single set could be fragmented among multiple pages and there will be some gaps in the splat buffer, but that's okay as long as we can requickly rebuild the index buffer to account for that.
I think 2 is most promising with fewer downsides that I would go for but I'm curious to hear your thoughts.

GaussianSplatGroup: incremental packing
This is based on @gkjohnson's feedback.
The group no longer rebuilds and reuploads its shared buffers whenever a splat cloud is added, removed, or toggled. Each operation now costs only what it touches:
addSplat packs the new cloud into the first free range of the shared buffers and uploads just that range (via addUpdateRange). No other cloud is touched.
deleteSplat returns the cloud's range to a coalescing free list for reuse. Nothing is repacked.
setVisibleAt flips a per-cloud flag in the 64-byte record buffer. Hidden clouds stay packed, and the counting sort routes their splats (and freed slots) into an extra discard bin past instanceCount, so they are never drawn. A visibility toggle uploads no splat data at all.
Growth happens only when no free range fits, doubles capacity, and copies the old arrays into the larger ones in place. Offsets are preserved, so there is still no per-splat repack.
compact() is the only operation that repacks everything, and it is explicit. The autoCompact option is gone; initialSize still preallocates.

A reproduction with the new code is here: https://bhouston.github.io/3d-tiles-splat-test/ (fork of your test repo with three.js as a submodule on this branch).
Trade-off
Hidden clouds now stay resident on the GPU, and capacity doubles on growth. In the run above, peak capacity was about 4.6 times the visible splat count. That is what makes visibility toggles free, but memory no longer drops when a tile is hidden. Deleting still frees the range.
What still uploads from the CPU
I think this is okay for now, but I will list it for you:
Delete writes the dead record index into each freed slot's center entry and re-uploads that range for every per-splat attribute, about 104 bytes per splat at SH degree 3, even though only 4 bytes per splat changed. Proportional to the deleted cloud, not the group.
Growth copies the old CPU arrays into the new larger ones (a typed-array copy, not a per-splat loop), and the renderer then uploads the whole new buffer.
compact() re-packs every cloud from its source geometry on the CPU and uploads the new buffers in full. Explicit and never automatic.
Possible next steps
I do not think we need to do this yet, but if you want better performance at the cost of increased complexity:
Cheaper delete. Queue the freed range for the center attribute only, cutting the delete upload to 16 bytes per splat. A few lines.
Zero-upload delete. Tombstone the deleted record (visible flag stays zero) and don't recycle its record index until the freed range has been fully overwritten by later adds. The sort already skips it. Only worth it if delete uploads still show in profiles after the change above.
GPU-side growth. Use copyBufferToBuffer from the old buffer into the new one instead of the CPU copy plus full upload. Needs a small addition to the renderer's storage attribute path.
Growth policy. A growthFactor option, or grow-to-fit plus fixed headroom, if doubling is too aggressive for large tilesets.
Sort over the high-water mark rather than full capacity, so unused tail slots do not cost histogram and scatter work.
Delete instead of hide on the plugin side for tiles unlikely to return, to reclaim memory sooner.
Paging (your option 2 in full) only if free-list fragmentation turns out to trigger repacks in practice. It has not in testing so far.
