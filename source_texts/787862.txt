What
3D textures with more than one mip level were refused ("mipmapped 3D textures are not implemented").
Thick volumes (SW_4KB_S / SW_64KB_S): each slab of blockDepth slices holds the whole mip chain. The smallest level comes first and level 0 last, the order 2D chains use. A level's width and height are padded to the 3D block, and the slab stride is the size of the whole chain. A level has max(depth >> level, 1) slices, so it uses only the first slabs.
Thin volumes (D/R 64KB_X): each depth slice holds the 2D mip chain, as array layers do.
SurfaceGeometry::HasLayer(level, layer) tells the texture upload, write-back and copy loops which depth slices a level has. For anything that is not 3D, and for single-mip 3D textures, it is always true.
Thick mip tails still throw ("3D texture mip tails are not implemented"). In a 4 KiB block a level enters the tail only once it fits half a block, e.g. 8x8 at 32 bpp.
GTA V's character shaders sample a 64x64x32 RGBA8 volume in SW_4KB_S with 3 levels. Every character draw into the G-buffer was skipped, about 900 every 10 s in the Prologue, so only the characters' eyes rendered. With this PR the characters render.
Tested
Windows 11 Pro, AMD Ryzen 5 7600, NVIDIA GeForce RTX 5080 (driver 32.0.16.1074), 32 GB DDR5-5600, MinGW-w64 GCC 15.2.0.
GTA V (PPSA04264), with fix(agc): a replaced device's unit shadows leave the registry #373–feat(agc): 4 KiB standard color targets and color views of one array slice #377 and the other fixes still in progress: the Prologue's characters render. Before, their draws were refused.
Other titles were not re-run. The change only affects 3D textures with more than one level, which were refused before.
ctest: all tests pass. A new tiling test covers the slab layout of a 3-level SW_4KB_S volume, the per-level depth and the tail refusal.

feat(agc): thick mip tails of mipmapped 3D textures
…
92a86d4
```
3D textures in SW_4KB_S or SW_64KB_S whose smaller levels reach the mip
tail were refused ("3D texture mip tails are not implemented"). The
tail now follows addrlib's GFX10 thick layout
(Gfx10Lib::ComputeSurfaceInfoMacroTiled):

- a level enters the tail once its size, rounded up, fits the thick
  tail extent (the block with its height halved for 4 KiB blocks and
  its width halved for 64 KiB blocks) and at most GetMaxNumMipsInTail
  levels remain (5 for 4 KiB, 10 for 64 KiB);
- each slab starts with one tail block, then the other levels from the
  smallest to level 0;
- tail level i sits in slot maxMipsInTail - 1 - i, at the element offset
  addrlib derives from that slot's byte offset and the 256-byte thick
  micro block, at every depth slice.

Levels outside the tail are padded from their rounded-up size, as
addrlib's GetMipSize does; this changes the layout only for sizes that
are not powers of two.

The tests check element addresses of five volumes (4 KiB and 64 KiB
blocks, 1 to 16 bytes per element, odd sizes, a chain that starts in
the tail) against Mesa addrlib's Addr2ComputeSurfaceAddrFromCoord for
a Navi10 configuration.

(cherry picked from commit 0e531c1)

integ: boykopovar#394 now carries 66a4625 (levels padded from their rounded-up
size), which this branch already took through the follow-up; the
follow-up is rebased over it: same ComputeThickLayout, boykopovar#394's 33x20x12
padding test kept, its 8x8x8 tail refusal test dropped (tails are now
laid out).
```
