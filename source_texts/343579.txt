Describe the project you are working on:
Large open world games
Describe the problem or limitation you are having in your project:
When working with large, open world games, it's important that level streaming be employed in order to reduce the amount data that is loaded into both RAM and GPU memory at any given time. Level streaming itself already solves this problem by only loading in chunks of a scene that is immediately relevant to the player and unloading those that aren't, and mesh LODs help reduce the strain on the GPU for distant meshes that are still loaded. The former can be implemented today, and the latter will be supported in Godot 4.0, but there is still one problem that hasn't been addressed but is important to tackle for large open world games: textures.
Large open world games often contain A LOT of textures. For hi res games, these textures are often huge as well. Constantly loading and unloading all of these different textures is extremely inefficient and makes the level streaming process slower and more "spiky".
Describe the feature / enhancement and how it helps to overcome the problem or limitation:
A popular solution to this is virtual textures (also called Sparse or Mega textures). Unity and Unreal both offer these already and I believe that Godot could also benefit from them. Essentially, with virtual texturing, you have a few extremely large textures that usually contain multiple textures, but when the texture data is uploaded to the GPU, only the pieces of the texture that are relevant to what is currently being rendered is uploaded. This means that the actual texture data can reside in memory for longer periods of times, reducing loading/unloading contention during level streaming, but significantly reduces the amount of GPU memory that is used when rendering the textures, since only a small portion is actually uploaded.

Describe how your proposal will work, with code, pseudocode, mockups, and/or diagrams:
A good explanation of virtual textures can be found in this video: https://www.youtube.com/watch?v=MejJL87yNgI
An additional feature of the VT implementation should be the support for asynchronous loading of textures in order to assist in reducing contention when steaming these large textures from disk during level streaming. I think this might already be planned in Godot 4.0 via StreamTextures, but I haven't looked too much into them to really know how relevant they are here.
If this enhancement will not be used often, can it be worked around with a few lines of script?:
No
Is there a reason why this should be core and not an add-on in the asset library?:
Texturing is a core component of Godot's rendering pipeline. In Godot 4.0 it might be something that can be added as a plugin, depending on what the rendering APIs end up looking like, but at least in 3.X, it must be core.

@Mantissa-23
as far as I understand, it's used extensively. All current desktop GPUs and graphics APIs (D3D11 and newer) have "sparse resources" feature, which maps different virtual areas of a resource (texture or buffer) to physical GPU memory (in a similar manner to the way OS implements virtual memory). This allows for direct use of hardware resources without having to sacrifice performance and memory by relying on additional look-up textures.
Unreal Engine uses it in 2 ways:
Runtime Virtual Texturing (RVT), the engine generates the virtual texture at runtime
Streaming Virtual Texturing (SVT), the engine prebakes the virtual texture and streams in parts of it at runtime
As for in-house engines, I'd assume most engines centered on large open-world games are using it but it's very hard to verify without in-depth graphics debugging.

To give a better perspective on this topic regarding industry standards:
Currently, the main use of virtual textures is for terrain rendering. Virtual terrain tiles are rendered into a physical texture at run-time. Usually requiring a full G-Buffer to store terrain materials and do proper blending later on.
Another niche use is to use virtual textures as part of the texture streaming system. Instead of loading a full texture with the full mip chain, the lower mip chain is loaded into resident memory, while the high mips are streamed on demand directly into the physical texture. This way only visible tiles in higher mip levels are effectively loaded in memory. This is only possible with hardware support using API features such as Tiled Resources on D3D. (I could not find a modern application of this apart from Metro 2033 and PUPB)
I don't know any other use for virtual texture in today's games.
Terrain rendering uses splatting to sprinkle different material types and blend them together seamlessly without paying the cost of re-evaluating terrain splatting for every pixel
Some games also splay decals in the virtual texture (projection decals, or mesh-based)
Some games re-use the virtual texture to "blend" the terrain with other object via the object's material. Usually called "terrain sampling" or something similar. This allows for seamless transitions of objects with the terrain for free*.
Mega texture was the proprietary tech of id software. Since then they replaced it with virtual texture in Doom 2016, and I believe they don't even use it in their latest titles.
Opinion on VT for terrain
I never saw the real benefit of virtual texturing. Some people claim it improves performance for terrain rendering and terrain sampling. I have yet to see it to be honest. Yes terrain rendering cost is reduced because you don't need to evaluate splatting per pixel, but a new and highly fluctuating GPU pass is needed to render terrain tiles on demand. This does not scale similarly depending on your type of game.
Since we only have a fixed budget to render terrain tiles, and we need to render tiles at different Mip levels to get a decent tri-linear/anisotropic filtering, this introduces a lot of mip popping. It's not dissimilar to regular mip streaming (with sampler feedback and the like), but this is entirely avoidable for the terrain if you just don't use virtual textures.
Speaking of anisotropic filtering, you need to implement it yourself. Since the physical texture is usually 2D with no mips, virtual mips are encoded as tiles in the physical texture. This means no hardware mip or mip interpolation, so no trilinear/anisotropic filtering ad-hoc.
(*) Terrain sampling is not entirely free. Sure you don't pay the cost of splatting the terrain material and so on, but you do pay the cost of adressing the physical texture and manual texture filtering (multiple texture samples per physical texture).
It uses A LOT of memory to be viable (10'000x10'000px physical texture @32bpp x3 (albedo, normal, misc params) = 1GiB+). This is memory on top of the memory required to store textures used to render the terrain tiles to begin with. We could reduce memory consumption by using block compression, but then it requires more budget for compression, and it complexifies the technique a lot.
It's a massive undertaking, and it's not trivial to implement. Virtual texturing is a complex system that is partly GPU-driven and partly CPU-driven.
It needs heuristics to determine which tile to prioritize.
It's difficult to debug (especially for users). Good luck making a RenderDoc capture of the specific tile you want to debug.
The only positive side I see is that mesh decals are easier to handle, since you can't easily sample from an arbitrary mesh in any shader (unlike projection decals for instance which are easy to evaluate).
In short
Virtual textures might be worth looking into for the Terrain rendering in Godot, but I would first invest in a well optimized terrain splatting first. Only then weigh in if the time necessary to implement and the extra memory cost is worth it.
Opinion on Mega textures
I don't think Mega Texture have any kind of future to be honest. They use a lot of disk space, streaming is horrible and popping is clearly visible with or without SSD. Maybe things could be improved with direct storage, but this is API specific.
I'm not mentioning the authoring part for Mega Texture, since I'm not sure how it works exactly (painting like Substance Painter in the world directly? Decals everywhere?).
Opinion on Sparse textures
This is called Tiled Resource on D3D.
I found this blog post from PUBG describing their solution(https://playerunknownproductions.net/news/virtual-texturing). They use an earth-size environment, so it makes sense for their needs. The memory gain is interesting (80% less memory), but I feel it's not entirely in good faith, since they don't specify what they measured exactly (are they comparing all MIPs loaded vs their solution? Or just sampler feedback without the virtual texture?)
Apart from PUPB's future game and Metro 2033, I don't know any other game using this technology.
I would love to know the memory consumption of just using the sampler feedback
Hard requirement for sampler feedback (no vulkan / openGL support). It can be emulated, but at a higher cost I assume
Hard requirement for direct storage. I don't know what the support of this technology is with modern hardware and different APIs
I consider it not worth the trouble. Just optimize your assets™
But more seriously, I think a decent streaming system goes a long way before needing this kind of technology
