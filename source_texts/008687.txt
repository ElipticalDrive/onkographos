A PHYSICS-BASED SIMULATION ENVIRONMENT FOR LUNAR ROVER
OPERATIONS
Nevindu M. Batagoda
Under the supervision of Professor Dan Negrut
at the University of Wisconsin-Madison
This thesis extends Project Chrono, a multi-physics simulation engine, to create a robotics
simulation framework for lunar applications. The work enhances Chrono’s capabilities in
three key areas: lunar scene modeling, sensor simulation, and large-scale world simulation.
New features were developed to accurately model lunar lighting, dust dynamics, and terrain
deformation, alongside the creation of a new module, Chrono::Worlds, for managing extensive
lunar environments. Motivated by the need for high-fidelity simulation tools to support lunar
exploration and robotics, this project advances Project Chrono toward realistic and scalable
lunar mission simulations.
First, a Hapke-based Bidirectional Reflectance Distribution Function (BRDF) model was
implemented to realistically render the lunar surface’s unique optical properties, including
the opposition effect and high dynamic range lighting conditions. Terrain deformation
visualization was enhanced using voxel-based rendering of Smoothed Particle Hydrodynamics
(SPH) terrain data, enabling realistic modeling of wheel-regolith interactions. Additionally, a
dust modeling and volumetric rendering pipeline was introduced to simulate and visualize
dust clouds kicked up by rover mobility, accounting for their impact on sensors and visibility.
Second, the Chrono::Sensor module was expanded to a novel Time-of-Flight (ToF) sensor
model based on transient rendering techniques. These enhancements allow simulation of SPADbased ToF phenomena, providing higher-fidelity virtual sensor data critical for perception
algorithm development.
Third, a new module, Chrono::Worlds, was developed to enable efficient management and
simulation of large-scale lunar terrains, utilizing Level-of-Detail (LOD) management through
viii
a quadtree data structure. Both NASA Lunar Reconnaissance Orbiter (LRO) datasets and
procedurally generated lunar terrains were integrated to support extended rover operations
over kilometer-scale domains.
The developed simulation environment was validated through several applications, including recreating imagery from the NASA POLAR dataset, simulating dust-affected rover
operations, and operating rovers such as VIPER and RASSOR on both real and synthetic lunar
terrains. This work positions Project Chrono as a comprehensive and open-source platform
for simulating complex lunar robotics scenarios with high physical and visual realism.

1.1
Motivation & Objectives
Space robotics is a rapidly growing field, with increasing interest in exploring celestial bodies
such as the Moon and Mars. As we prepare for future missions, it is crucial to develop advanced
simulation tools that can accurately model the complex environments and interactions that
robotic systems will encounter. Due to the high costs and risks associated with real-world
testing, simulation plays a vital role in the design, testing, and validation of robotic systems.
High-fidelity simulations can help researchers and engineers understand how their systems
will perform in various scenarios, allowing them to optimize designs and reduce the likelihood
of failures during actual missions. An increased focus has been placed on lunar exploration in
recent years, with several landers from Intuitive Machines, Firefly Aerospace, and Astrobotic
scheduled to land on the Moon in the coming years. NASA’s Artemis program aims to return
humans to the Moon by 2029, with a focus on sustainable exploration and establishing a
long-term presence on the lunar surface. The European Space Agency (ESA) is also planning
its own lunar missions, including the Lunar Pathfinder and the Moonlight initiative, which
aims to provide communication and navigation services for lunar missions. As these missions
become more complex, the need for accurate and efficient simulation tools becomes even
more critical. As such space programs across the world have invested in developing extra
terrestrial robotic simulation tools. This thesis focuses on developing such a lunar robotics
simulation framework using the multi-physics simulation engine Project Chrono [7].
Project Chrono is an open-source multi-physics simulation engine that provides a flexible
and extensible framework for simulating complex physical systems. It has been widely
used in various applications, including robotics, vehicle dynamics, sensor simulation and
terramechanics. However it is not currently suitable for simulating lunar environments, as it
lacks the necessary features and capabilities to accurately model the unique challenges posed
by lunar terrain and lighting conditions.
2
In this thesis, we add on to the existing capabilities of Project Chrono in three areas:
• Lunar scene modeling: We extend the rendering engine capabilities of the sensor
simulation module Chrono::Sensor to support typical lunar scene details such as lunar
lighting/shadows, lunar dust, and deformable lunar terrain.
• Sensor simulation: We extend the Chrono::Sensor module to support high-fidelity
Time-of-Flight sensor simulation.
• World simulation: We develop a new module called Chrono::Worlds, which is designed
to support large terrain simulations in Project Chrono. This module allows for the
efficient management and simulation of large-scale realistic lunar environments based
on NASA’s Lunar Reconnaissance Orbiter (LRO) terrain data.
1.2
Thesis Organization
The thesis is organized to discuss the main components of the lunar simulation framework.
Chapter 1 and Chapter 2 provides an introduction and motivation for the work and gives a
description of existing space robotics simulation frameworks and also discusses the current
capabilities of Project Chrono. Chapter 3 discusses the lunar scene modeling capabilities
added to Project Chrono, which include lunar lighting/shadows, lunar dust simulation, and
terrain deformation. Chapter 4 discusses the sensor simulation capabilities added to Project
Chrono, which includes the new Time-of-Flight sensing module. Chapter 5 discusses the
Chrono::Worlds module for large scale lunar terrain simulation. Chapter 6 details the various
applications that demonstrate the new features and capabilities added to Project Chrono.
These applications include comparison with real-world POLAR dataset images, demonstration
of lunar terrain deformation, rover dust simulation, rover operations on large-scale lunar
terrains such as the Apollo 17 landing site. Though unrelated to lunar exploration, we
demonstrate the use of the new Chrono::Sensor ToF sensor module in an application involving
3
the use of Non-line-of-Sight (NLOS) imaging for early hazard detection in autonomous
driving.Finally, Chapter 7 concludes the thesis and discusses future work.

2.1
State of the Art Space Robotics Simulators
Simulation in robotics is a powerful tool that allows researchers and engineers to test and
validate algorithms, designs, and systems in a controlled environment before deploying them
in real-world scenarios. This involves creating a virtual representation of the robot and its
environment, enabling the study of various aspects such as kinematics, dynamics, sensor
performance, and control strategies [8]. Simulation can also facilitate the development of data
driven development of machine learning algorithms used in robotics, where large amounts
of synthetic data can be generated to train models for perception, navigation, and decisionmaking tasks. In normal Earth based robotics, simulation is used in conjunction with physical
testing to validate the performance of the robot in real-world scenarios due to the sim-to-real
gap that exists in synthetic data [9]. However, physical testing in space robotics is often
constrained to earth as deploying robots in space is quite expensive. As such simulation
is often used as a primary tool for testing and validating algorithms and designs before
deploying them in real-world space exploration scenarios. As such it is necessary to have
accurate simulators that can simulate the unique conditions of space environments, such
lighting conditions, terrain modeling, robot dynamics, and sensor performance.
Several simulation platforms have been developed to support space robotics applications, particularly for planetary exploration, where realistic sensing, dynamics, and terrain
interaction are crucial. NASA has developed multiple simulators in this domain. EDGE
(Engineering DOUG Graphics for Exploration) is a proprietary platform that integrates
graphics through the DOUG engine and physics via the TRICK simulation environment [10].
EDGE supports real-time simulation and visualization for space missions, including lunar
and planetary exploration. DOUG provides the real-time 3D graphics framework for these
simulations, while TRICK handles the physics modeling. Additionally, NASA developed the
DLES (Digital Lunar Exploration Sites) dataset [11], which offers high-resolution terrain
5
models and lighting data, particularly focused on the lunar South Pole, supporting mission
planning activities such as the Artemis program. Building on DLES, the DUST (DLES
Unreal Simulation Tool) simulator [12] leverages Unreal Engine 5 for rendering and relies on
the Chaos Physics engine rather than TRICK. Figure 2.1 illustrates the relationship between
the simulation tools used by NASA planetary exploration simulations.
Figure 2.1: Relationship between NASA simulation tools for planetary exploration. [1]
Similar in goals to EDGE and DUST is DARTS (Dynamics And Real-Time Simulation)
[13], developed at JPL, which uses procedural terrain generation techniques (e.g., Perlin and
Voronoi noise) to create complex extraterrestrial environments. DARTS is paired with the
Iris tool [14] for sensor simulation. Table. 2.1 details a comparison of the simulators discussed
in this section.
6
A joint project between NASA Ames and Open Robotics produced a Lunar rover simulator
based on Gazebo [15], employing the Open Dynamics Engine (ODE) [16] for physics simulation.
Although ODE is a game-oriented engine similar to PhysX [17] and Chaos Physics, it was
adapted for space applications by incorporating empirical slip modeling through drawbar-pull
curves. The rendering relied on Ogre3D [18], enhanced with modified shadow mapping
algorithms and custom shaders to better model lunar surface reflectance characteristics such
as the opposition effect.
Outside of NASA, the German Aerospace Center (DLR) developed URSim [19], which,
like DUST, is based on Unreal Engine (version 4.0 [20]) and uses the PhysX engine. URSim
focuses on photo-realistic rendering and real-time dynamics for robotic perception and control
studies, supporting the investigation of perception-action loops in simulated extraterrestrial
environments.
From the commercial sector, NVIDIA’s IsaacSIM [21] offers an integrated simulation
platform combining dynamics and sensor simulation, targeted toward robotics applications.
While it is freely available, it is not open-source, and does not natively support lunar terrain
modeling. Recent efforts have begun exploring its use for extraterrestrial terramechanics
simulation [22, 23].
Some simulators focus exclusively on sensing rather than integrated dynamics and sensing.
GUISS (Graphical User Interface Simulation Software) [24] emphasizes camera simulation for
icy environments using Blender Cycles [25], while DLR’s Oaysis platform [26] and BlenderProc
[27] provide real-time rendering and procedural dataset generation capabilities, respectively.
Although not directly linked to space exploration, related efforts in high-fidelity sensor
modeling and validation, such as those reported in [28], further illustrate the growing interest
in accurately simulating image acquisition processes for autonomous systems [29, 30].
In contrast to many of the aforementioned platforms, the Chrono simulation engine [7, 31,
32] offers an open-source, physics-based environment specifically designed to handle deformable
terrain interactions. Chrono supports realistic sensor simulation, both for active and passive
7
imaging systems, and allows for the coupling of vehicle dynamics with terramechanics
phenomena. Its capabilities include integration with ROS-based autonomy stacks for realtime or near-real-time simulation, as well as support for simultaneous hardware-in-the-loop
(HIL) and software-in-the-loop (SIL) testing.
Chrono stands out for its principled modeling of soil deformation and vehicle-soil interactions, which enables unique functionalities not currently available in other open-source
platforms. It has been employed in various NASA-sponsored projects, including the VIPER
mission, the RASSOR excavator [33], and the Moon Ranger project at Carnegie Mellon
University. Chrono thus addresses a critical gap in publicly available simulation tools for
space robotics, offering a comprehensive environment that blends terramechanics, dynamics,
and sensor simulation.

2.2
Project Chrono Multi-body Dynamics
2.2.1
Vehicle Modeling
Chrono::Vehicle [34] is a specialized module within Chrono that supports the modeling of a
wide variety of ground vehicles, including both wheeled and tracked platforms. It provides a
comprehensive set of templates for vehicle subsystems such as tires, suspensions, steering
mechanisms, drivelines, sprockets, and track shoes. Chrono::Vehicle can simulate vehicles
operating on rigid, flexible, or granular terrains and supports real-time or offline visualization.
This module is designed to work in tandem with other Chrono components, including
Chrono::FEA (for finite element analysis), Chrono::DEME (for discrete element granular
simulations), and several visualization modules like Chrono::VSG, Chrono::Irrlicht, and
Chrono::OpenGL. Chrono::Vehicle enables flexible simulations through either monolithic
approaches or co-simulation, allowing different subsystems (vehicle, tires, terrain, driver, etc.)
to be modeled independently but simulated together.
Vehicles can be instantiated either through C++ class templates or JSON specification
files, facilitating both user-defined and example-based setups. For tires, Chrono::Vehicle offers
three modeling options: rigid tires (cylindrical or non-deformable meshes), semi-empirical
models (e.g., Pacejka [35], Fiala [36], TMeasy [37]), and finite element-based flexible tires
(ANCF or Reissner shell models).
Tracked vehicles are modeled as full multibody systems, supporting both segmented tracks
and continuous-band tracks modeled using bushing or FEA elements. Contact interaction
(internal and terrain-related) supports both non-smooth (complementarity-based) and smooth
(penalty-based) formulations.

2.2.2
Terrain Modeling
Soil Contact Model (SCM)
The Soil Contact Model (SCM) in Chrono [38] is a semi-empirical deformable terrain model
designed for real-time simulation on commodity hardware. It builds upon classical terramechanics work, generalizing the Bekker pressure-sinkage relationship [39] and incorporating
shear stress modeling via the Janosi-Hanamoto formulation [40]. Chrono’s SCM implementation uses OpenMP [41] for parallelization, enabling real-time factors (RTF) close to or better
than 1.0 in basic rover simulations without high-frequency terrain features.
While SCM provides an excellent trade-off between computational efficiency and accuracy,
its assumptions limit its applicability to scenarios with small wheel sinkage, low slip ratios,
and approximately cylindrical wheels without pronounced grousers [42, 43]. For visualization,
SCM can generate a deformable terrain mesh, which can be rendered in real-time with
Chrono’s visualization modules or sensed through Chrono::Sensor.
Continuum Representation Model (CRM)
Chrono’s Continuum Representation Model (CRM) [44, 45, 46] approximates granular terrain
as a continuum medium governed by balance laws for mass and momentum. The terrain
is assumed incompressible, and field variables include the velocity u and the Cauchy stress
tensor σ, satisfying:

sinkage, which can significantly affect the performance of lunar rovers. The CRM model

understand the dynamics of lunar rovers and optimize their designs for improved performance
in the challenging lunar environment.

2.3
Chrono::Sensor - sensor simulation engine
Chrono::Sensor provides a versatile framework for the simulation of cameras, LiDAR, Timeof-flight (ToF), GPS, and IMU sensors to support autonomous robot simulation [57]. The
primary purpose of Chrono::Sensor is to generate realistic synthetic sensor data that can be
used to train and validate perception algorithms in a simulated environment [58]. This is
particularly important for lunar rover applications, where real-world data collection is often
limited or impractical due to the harsh and remote conditions of the lunar surface.
Figure. 2.7 shows some examples of the sensors supported by Chrono::Sensor. The
framework is designed to be extensible, allowing users to add new sensor types and models as
needed. It also supports a wide range of sensor parameters, including field of view, resolution,
and noise characteristics, enabling users to create realistic sensor simulations tailored to their
specific applications.
Camera, LiDAR and ToF sensor simulation in Chrono::Sensor are based on real-time ray
tracing using NVIDIA’s OptiX library [59]. Unlike game engines such as Unity 3D [60] or
12
Unreal Engine, Chrono::Sensor emphasizes accurate sensor data modeling rather than humanoriented rendering. Game engines, while capable of producing visually compelling images,
are not designed to replicate physical sensor behavior faithfully, making them unsuitable for
high-fidelity sensor modeling. Chrono::Sensor, is designed to model the non-idealities in the
sensor data acquisition process, including the effects of sensor noise, and timing aspects such
as exposure time, and sensor lag and update rate.
These timing aspects are tightly synchronized with the simulation time to ensure correct
sensor behavior. Sensors and physics computations run on separate threads for efficiency,
while maintaining time coherence. If sensor computations are faster than dynamics updates,
sensing waits, and vice versa. Sensor lag time can be leveraged to increase efficiency without
compromising synchronization.
An overview of the synchronization between the physics engine and sensor simulation is
illustrated in Fig. 2.5 and Fig. 2.6.
Figure 2.5: Illustration of coherence between device-side ray tracing operations and the

By virtue of its NVIDIA OptiX-based ray tracing engine, Chrono::Sensor is a fully
GPU-accelerated real-time path tracing engine, capable of simulating complex light transport
phenomena such as reflections, refractions, global illumination and transient rendering. In this
work, we extend the capabilities of Chrono::Sensor to support high-fidelity sensor simulation
for lunar environments. This includes modeling the reflectance properties of lunar regolith,
the effects of lunar dust on sensor performance, and rendering deformable lunar terrain
simulations. We also introduce new sensor models, including Time-of-Flight sensors, which
can be used in future lunar exploration missions.

3.1
Hapke Bidirectional Reflectance (BRDF) Model
3.1.1
Introduction
A crucial part of setting up a lunar robotics simulator is being able to represent the behavior
of light on the moon accurately. The Lunar surface is covered in lunar regolith, which is
a low albedo and retroreflective material and has a strong influence on the reflectivity of
the lunar surface. The lack of atmospheric scattering and the nature of the Lunar regolith
are the primary factors dictating the lighting conditions on the moon that lead to hard
lighting resulting in long shadows, oblique angles of sunlight, and High Dynamic Range
conditions due to the contrast between shadowed and illuminated regions. However, the
most outstanding phenomenon caused by interactions of light with the lunar surface is the
opposition effect/surge. The opposition effect is the apparent increase in brightness noted
when we observe the lunar surface from the direction of illumination (sun) Figure 3.1. The
primary reason for the opposite effect is the shadow hiding that occurs. Shadow hiding is
the effect where all shadows disappear when the viewing and illumination directions are
very close [61]. Hence, it is necessary to implement a reflection model that captures the
above-mentioned properties of the moon.
One of the most commonly used and important models used to describe the reflectance
distribution of celestial bodies with a regolith is the Hapke model. The initial Hapke model
was developed by the astronomer Bruce Hapke in 1963, and it models the lunar surface as
a layer of cylinders, each always oriented towards the direction of illumination such that
reflection towards the incident direction is less attenuated [62]. There have been several
revisions to the Hapke model over the decades with the most recent one in 2012 [63]. The
2012 Hapke model factors in multiple scattering, surface roughness, coherent backscatter,
size of regolith particles (angular width), and porosity of particles – aspects that the original

model did not consider. The recent Hapke model has nine parameters altogether as opposed
to five in the original one. For the Lunar Sensing module, we implemented thus far the
modern Hapke model, with some simplifications.

3.2
Deformable Lunar Terrain Visualization
3.2.1
Introduction
In space robotics exploration scenarios, wheel-terrain interaction is a critical aspect of rover
mobility. The ability to accurately estimate wheel sinkage and slippage is essential for effective
navigation and terrain assessment. In this context, Visual Wheel Sinkage Estimation (VWSE)
21
plays a vital role in enabling autonomous rovers or teleoperators to gauge wheel performance
in various terrains. To facilitate the development and testing of VWSE algorithms, it is
crucial to accurately capture wheel sinkage in simulation environments. This requires a
simulator that not only provides high-fidelity terramechanics but also incorporates a virtual
camera sensor capable of capturing wheel sinkage data.
In Project Chrono, we achieve this through a co-simulation between the Chrono::FSI and
Chrono::Sensor [57] modules. Chrono::FSI uses a Continuous Representation Model (CRM)
[45], which is based on the Smoothed Particle Hydrodynamics (SPH) method, to model the
lunar terrain as a continuum media. Compared to the Soil Contact Model (SCM) [66], the
CRM model is more faithful in capturing the terramechanics. However, rendering the CRM
wheel-terrain interaction in a camera sensor simulation is not trivial, as the CRM model
treats the terrain as a collection of particles and, as such, has no mesh information. To
address this we used voxelization methods to capture images of the lunar terrain mechanics.
3.2.2
Voxel Rendering using NanoVDB
We opted to render CRM simulations via voxelization using NanoVDB [4], a lightweight
version of the OpenVDB library [67]. NanoVDB is designed specifically for GPU-based
applications and enables efficient access, traversal, and modification of sparse volumetric data
structures directly on the GPU. Unlike traditional dense grids, which store every voxel even
when empty, NanoVDB uses a hierarchical, tree-based structure composed of multiple levels:
a root node, internal nodes, and leaf nodes. Each node level partitions space into progressively
smaller blocks, allowing for memory-efficient storage of active regions while skipping over
large empty areas. The leaf nodes store voxel values and can be accessed quickly during
rendering or simulation operations. NanoVDB further optimizes access patterns by flattening
the tree structure into linear arrays, which reduces memory indirection and improves cache
performance during traversal on modern GPUs.
22
Figure 3.3 shows the structure of a VDB grid. Our initial plan was to create a voxel grid
on the GPU that stores all the particle information and then construct a level set from the
particle point cloud. Having a level set provides us with an iso-surface that can be used to
easily calculate ray-surface interactions and render the terrain. For the level setting, we first
rasterized all particles as spheres and then used a Constructive Solid Geometry (CSG) based
union operation to create a level set.
Figure 3.3: NanoVDB Grid Structure [4].
However, we noticed that the final surface created was overly smooth, and all information
about small granular particles being kicked up by the wheel-terrain interactions was lost.
Furthermore, we encountered issues with NanoVDB’s level set intersection methods not
providing the proper intersection point for level sets.
As such, we decided against the level-setting approach and opted to directly render all
the voxels in the volume using predefined mesh geometry that represents granular particles.
We chose to use meshes instead of spheres and cubes for more realism, and will be discussed
in the next section. This approach is more computationally expensive but provides a more
23
accurate representation of the terrain. To ease the computational burden, we can determine
how many particles will be aggregated into a single voxel, essentially allowing us to decimate
the particle cloud while maintaining the overall shape of the terrain.
3.2.3
Modeling Granular Lunar Particle Geometry
We found that the use of spheres or cubes to represent the voxels, gives the final terrain
rendering too much of a clean and smooth appearance leading to an unrealistic depiction of
the lunar regolith. We observe that lunar regolith is composed of irregularly shaped particles
of various sizes and orientations. As such, we decided to improve our pipeline to use any
mesh geometry to represent the voxels. And for generating said mesh geometry, we created
a Blender [25] script to generate random meshes that represent lunar regolith as close as
possible.
The mesh generation script begins by modeling a sphere with a specified radius and a
variable number of subdivision surfaces. To create fine geometric details, we apply a randomly
generated displacement texture to the sphere, followed by edge smoothing. Subsequently,
the mesh may be randomly flattened, elongated, or left round to introduce more variation
in the regolith geometry. It is important to note that this workflow was selected based on
visual observations of both real and simulated lunar terrains, without a physical basis for
the choices. Figure 3.4 illustrates some of the generated meshes. To enhance the realism
of the terrain further, each voxel is given a random translational offset and scaling, which
helps prevent the appearance of the uniform grid-like nature inherent in the underlying CRM
particles in the rendering.
24
Figure 3.4: Randomly generated meshes to represent lunar regolith.
In our simulations, we pregenerate a set of 100 lunar regolith meshes and, when initializing
the voxel grid, we randomly assign one of these meshes to each voxel.

3.3
Dust Modeling and Visualization
3.3.1
Introduction
In lunar environments, dust presents a significant challenge to perception systems. It can
obstruct the view of cameras and sensors, complicating navigation and task execution. For
28
instance, when estimating the sinkage of a rover’s wheels, dust can obscure the wheel-terrain
interaction, hindering accurate measurements of how deeply the wheels are sinking.
To better understand the effects of dust on perception, we aim to model and sense dust
in simulation. In order to simulate dust, we 1) need a physics model that can describe the
emission and propagation of dust particles in the lunar environment, and 2) rendering pipeline
that can visualize the dust particles in a way that is consistent with the physics model. In
this section we describe our work on implementing a particle system in Chrono that can
simulate dust and a volumetric rendering pipeline in Chrono::Sensor that can visualize the
dust particles. We then demonstrate the over dust simulation pipeline by simulating a VIPER
rover traversing a deformable lunar terrain and kicking up dust particles.
3.3.2
Dust Modeling
Due to the lack of atmosphere on the Moon, the main forces acting on dust particles are
gravity, electrostatic forces, and any collisions with the terrain or other objects. Given the
terramechanics emphasis of our project, the current implementation ignores the electrostatic
forces and models the dust particles as point bodies ejected and falling under the influence
of gravity. Our current dust model works only with the Continuous Representation Model
(CRM) terrain, as we use the velocity of terrain particles as the ejection criterion for dust
particles. We plan to extend this model to support other terrain representations in the future.
The overall dust algorithm is as follows:
Dust Simulation Algorithm
A dust particle p has the following properties:
• Position: Particle position in 3D space.
• Velocity: Particle velocity in 3D space.
• ExtinctionSteps: Remaining steps before particle extinction.
29
• isActive: Boolean indicating whether the particle is active.
The dust simulation algorithm is detailed in Algorithm 1. The algorithm takes as input
CRM markers with position and velocity, a velocity threshold above which CRM markers will
eject dust particles, an influence radius that controls the density of the dust cloud, the total
lifespan of a dust particle, the maximum number of dust particles that can exist at any given
time in the simulation (needed to control the dust cloud memory footprint), and the list of
active dust particles. The algorithm outputs a density grid representing the dust volume and
the updated active dust marker list. Table 3.3 lists the parameters used in the dust particle
simulation.
At the start of the simulation, the list of active dust particles is empty. At each subsequent
update step, the list of active particles is appended with newly ejected dust particles. A
maximum buffer size is set to avoid unbounded growth of the “live” dust particles. Particles
that have gone out of bounds or have reached the end of their lifespan are removed. Thus,
dust particles are continuously created and removed from the simulation.
To render the dust particles as a volume, we must create a density field that represents
the dust cloud. This is done by creating a voxel grid that represents the dust cloud. The
density of each voxel is determined by the dust particles within a certain radius of the voxel.
The density of a voxel is influenced by the distance of the dust particles from the voxel center:
the closer the dust particle is to the voxel center, the higher the voxel density. The density of
the voxel is calculated using a Gaussian function. The density field is then normalized to
create a density grid representing the dust cloud. The larger the radius of influence of a dust
particle, the denser the appearance of the dust cloud.

3.3.3
Dust Visualization
Now that we have a dust simulation algorithm, we need to visualize the dust particles in a
way that is consistent with the physics model. The goal of this visualization is to create a
realistic representation of the dust cloud that can be used for perception tasks. In order to
achieve this, we implemented a volumetric rendering pipeline in Chrono::Sensor that can
visualize the dust particles as a volume. The volumetric rendering pipeline uses a NanoVDB
[4] voxel grid to represent the dust cloud, and uses ray marching techniques to render the
dust particles. The volumetric rendering pipeline is designed to be flexible and can be used
to visualize any type of volume data, not just dust particles. In this section, we describe the
volumetric rendering pipeline and show some offline rendering results of dust simulations
sourced from the internet (as VDB files).

Volumetric Rendering
Volumetric rendering is a technique used in computer graphics to create and visualize threedimensional data sets that contain information about volume densities, such as clouds, smoke,
fire, or other translucent materials. Unlike traditional surface rendering, which only considers
the outer surfaces of objects, volumetric rendering captures the entire volume, allowing for
more realistic and detailed representations of complex phenomena.
One of the common methods for volumetric rendering is ray marching. This technique
involves casting rays from the camera into the scene and stepping through the volume in
small increments. At each step, the algorithm samples the volume to determine the density
and color of the material encountered. These samples are accumulated along the ray to
compute the final color and opacity that will be displayed on the screen.

4.1
Time of Flight (ToF) Sensor modeling
4.1.1
Introduction
ToF sensors and active imaging have recently gained popularity in the space exploration/robotics
community due to their effectiveness in detecting and imaging objects in low-light conditions.
They have also been adopted in lunar landers for altitude estimation during landing operations. By providing simulation tools to model high fidelity ToF sensors, we can support the
development of future novel applications of ToF sensors in space robotics.
This section describes the high fidelity Time-of-Flight (ToF) sensor model implemented
in Chrono::Sensor. While Chrono::Sensor already has a LiDAR model (which is also a ToF
sensor), it is a simple model that fails to model failure cases of LiDAR such as when dealing
with transparent or specular surfaces. The new ToF sensor model, leverages the full multibounce path tracing capabilities of Chrono::Sensor to model the ToF sensor. Importantly, the
new ToF model, leverages the new transient rendering capabilities of Chrono::Sensor to model
the ToF sensor. The ToF model is a general purpose model which can be used to model an
ToF sensor. In this work we focus on modeling the characteristics of a SPAD (Single Photon
Avalanche Diode) based ToF. The ToF sensor model is designed to be modular, allowing for
the addition of new optical effects and the adjustment of parameters to match real-world
ToF sensors. We first explain transient rendering and how it is used to model the ToF sensor.
We then describe SPAD sensor model and how its noise characteristics are modeled.
4.1.2
Transient Rendering
Transient rendering [72] is a simulation technique that models how light travels through a
scene over time, capturing not just the final illumination but the entire dynamic process
of light propagation. Instead of computing a steady-state image like traditional rendering,
44
transient rendering tracks the time-resolved behavior of photons, allowing the visualization and
analysis of light interactions at extremely fine time scales, often in the order of picoseconds or
femtoseconds. The transient rendering formulation is similar to the path tracing formulation,
but with the addition of a time variable. In facet, the transient rendering technique is a
generalization of the path tracing technique. The transient rendering technique is based on
the following equation [72]:

This technique is particularly useful for applications such as Time-of-Flight (ToF) imaging,
where the time it takes for light to travel from a source to a sensor and back is critical for
depth estimation and scene reconstruction. Different types of ToF sensors, have different
time resolution requirements. For example, SPAD (Single Photon Avalanche Diode) sensor
typically operate in the range of picoseconds, while other ToF sensors may operate in the
range of nanoseconds. The transient rendering technique allows for the simulation of these
different time scales, making it a versatile tool for modeling various ToF sensor technologies.
At very high time resolutions, it is possible to separate the different bounces of light in
a scene, separating the direct light from the indirect light. This is useful for modeling ToF
sensors, such as SPADs that are used for imaging methods like Non-Line-of-Sight (NLOS)
imaging [73]. Figure4.1 shows a comparison between the steady state rendering and the

30ps after the light source was turned on.

Single-Photon Avalanche Diode (SPAD) sensors are highly sensitive photodetectors capable of
detecting individual photons with precise temporal resolution. Operating in Geiger mode, a

SPAD is biased above its breakdown voltage, so that the absorption of a single photon triggers
a self-sustaining avalanche of carriers, resulting in a detectable macroscopic current pulse.
After each detection event, the SPAD undergoes a quenching and reset process to prepare
for subsequent photon arrivals. SPAD arrays, consisting of many such detectors, enable
high-speed, low-light imaging with temporal resolutions on the order of tens to hundreds

A SPAD stores measured data in a 3D histogram, where each bin represents the number
of photons detected within a specific time interval. Each SPAD has a maximum number
of time bins it can store. The histogram is updated in real-time as photons are detected,
allowing for the accumulation of data over time. The histogram can be used to generate a
depth map by analyzing the time-of-flight information of the detected photons. In Figure.4.1
we show the histogram at one pixel of the transient image of the Cornell box scene.

terrain simulation engine
5.1
Introduction
Being able to simulate rover operations over larger swaths of lunar terrains is an essential
component for a lunar rover simulation framework. In this case "large" refers to any rover
simulation operating on a lunar terrain that is on the kilometer scale. The Lunar Reconnaissance Orbiter (LRO) has provided high-resolution terrain data of the Moon, which can be
used to create realistic lunar terrains for simulation. The LRO terrain data is available in
a variety of formats, including Digital Elevation Models (DEMs) [75, 75]. These datasets
can be used to create realistic lunar terrains that accurately represent the topography and
surface features of the Moon. However, the size of these datasets can be quite large, making
it difficult to manage and render them efficiently in a simulation environment.
Currently in Chrono, if one was to initialize a large lunar DEM terrain (say, a 14x14km
Apollo 17 landing site terrain), with a rover, the entire simulation would be quickly bogged
down by the sheer size of the terrain. As such it is necessary to have a terrain management
system that can handle large terrains efficiently. To address this issue, we implemented
a tile-based large scale terrain management system in Chrono. We call this new module
Chrono::Worlds.
5.2
Chrono::Worlds Architecture
At its core, Chrono::Worlds is a terrain management system that uses a QuadTree data
structure to manage large terrains. The QuadTree data structure is a tree data structure in
which each internal node has exactly four children. The QuadTree data structure is used to
partition a 2D space by recursively subdividing it into four quadrants or regions. The overall
framework and pipeline of Chrono::Worlds is shown in Fig. 5.1.
51
Figure 5.1: Chrono::Worlds framework for large scale terrain management.
When a terrain height map is loaded, it is first tiled into a coarse set of tiles based on a
predefined resolution. Each of these coarse tiles is initialized as a QuadTree and manages
its own Level-of-Detail (LOD). The LOD management works by dynamically adjusting
tile subdivisions based on camera distance: tiles closer to the camera are subdivided to
increase detail, while distant tiles are merged to reduce detail. During subdivision, we upscale
the corresponding height map terrain section using bilinear interpolation, resulting in more
detailed terrain near the camera position. The Chrono::Worlds framework also supports
terrain deformation through the Chrono SCM terrain model. Any deformed nodes are marked
as "dirty" and tracked by the terrain manager. For performance optimization, collision physics
are only enabled for tiles closest to the camera position (marked cyan), while other tiles have
physics disabled. Each QuadTree tile maintains information about its terrain mesh, allowing
the rendering algorithm to efficiently sample and render the terrain based on the camera’s
view frustum. Figure 5.2 shows the Apollo 17 landing site scene in Chrono::Worlds, with
Fig. 5.2 (a) showing the different levels of detail of the terrain and Fig. 5.2 (b) showing the
mesh rendering of the terrain.

In this section, we present the validation of our lunar camera sensor simulation models using
the NASA POLAR dataset. The goal of this work is to evaluate the realism of the synthetic
images generated by our simulation models and quantify the sim-to-real gap between synthetic
and real images.terrain. The way we attempt to quantify the sim-to-real gap is by using an

obtain real lunar surface images from rovers due to limited access and availability. As such,
researchers resort to use lunar surface analogs on Earth to train and validate perception
algorithms. We use one such dataset, the POLAR dataset [77], by NASA Ames to compare
our synthetic sensor data against.

6.1.2
Evaluation of the Sim-to-Real Gap Using Object Detection
Experimental Setup
To assess the realism of the synthetic images and quantify the sim-to-real gap, we employed a
data-driven object detection algorithm, YOLOv5 [76]. The goal was to evaluate how closely
synthetic datasets rendered with different BRDFs (Principled vs. Hapke) resembled real-world
images when used for downstream perception tasks.
The target objects were rocks, with ground-truth (GT) bounding boxes manually labeled
in the POLAR dataset and available through Polar3D. For synthetic images, ground-truth
bounding boxes were automatically generated using the semantic segmentation camera in
Chrono::Sensor and post-processing [1].
Datasets and Metrics
Experiments focused on Terrains 1, 4, and 11 of the POLAR dataset. Both real and synthetic
datasets were split into training and testing sets with a 2:1 ratio. Evaluation metrics included:
• mAP@0.5: Mean average precision at an Intersection over Union (IOU) threshold of
0.5.
• mAP@[0.5:0.95]: Mean average precision averaged over IOU thresholds from 0.5 to
0.95.
• IOUmean: Mean IOU between predicted and ground-truth bounding boxes, selecting
the best prediction for each ground-truth box.
Training and Evaluation Procedure
YOLOv5s was fine-tuned using transfer learning, starting from pretrained weights provided
by the official YOLOv5 repository. The models were trained and validated for 200 epochs,
and the best validation weights were selected for testing. Three different training datasets
were considered:
61
• Real POLAR photos
• Synthetic images rendered with the Principled BRDF
• Synthetic images rendered with the Hapke BRDF
Each trained model was evaluated by cross-testing on real and synthetic testing sets.

7.1
Conclusion
In this thesis, we have developed a lunar robotics simulation framework using the multi-physics
simulation engine Project Chrono. We have extended the existing capabilities of Project
Chrono in three areas: lunar scene modeling, sensor simulation, and world simulation. The
new features and capabilities added to Project Chrono include:
• Lunar scene modeling: We have extended the rendering engine capabilities of the
sensor simulation module Chrono::Sensor to support typical lunar scene details such as
lunar lighting/shadows, lunar dust, and deformable lunar terrain.
• Sensor simulation: We have extended the Chrono::Sensor module to support highfidelity Time-of-Flight sensor simulation.
• World simulation: We have developed a new module called Chrono::Worlds, which is
designed to support large terrain simulations in Project Chrono. This module allows
for the efficient management and simulation of large-scale realistic lunar environments
based on NASA’s Lunar Reconnaissance Orbiter (LRO) terrain data and also supports
procedural generation of lunar terrains.
We have demonstrated the effectiveness of the new features and capabilities added to
Project Chrono through several applications, including comparison with real-world POLAR
dataset images, demonstration of lunar terrain deformation, rover dust simulation, rover
operations on large-scale lunar terrains such as the Apollo 17 landing site. Though unrelated
to lunar exploration, we demonstrated the use of thew new Chrono::Sensor ToF sensor module

Through the work done in this thesis, we have shown that Project Chrono can be used to
simulate lunar environments and robotic systems effectively. The work done in this thesis is
a significant step towards developing a comprehensive lunar robotics simulation framework.
7.2
Future Work
Some of the future work that can be done to improve lunar simulation framework includes:
• Adding CRM terrain model support to the Chrono::Worlds module. The CRM terrain
model is a more accurate representation of lunar terrain than the SCM terrain model,
and it can be used to simulate more realistic lunar terrain deformation. As such being
able to simulate large swaths of lunar terrain using the CRM terrain model would place
Chrono lunar simulation framework a cut above other lunar simulation frameworks.
• Adding support for ChronoUnity support for lunar simulation. ChronoUnity [6] is
a Unity wrapper for Project Chrono that allows for the use of Unity’s scene editing
capabilities to edit simulations. ChronoUnity works by using the C# SWIG bindings of
Chrono to interface with the Unity Engine which is also programmed using C#. Chrono
simulations which used to be in rather monolithic C++ files, can now be modularized
into ChronoUnity "Game Object" components which leads to a more friendly user
experience. ChronoUnity also allows for the use of Unity’s rendering engine, which
can be used to create more realistic lunar scenes. This is particularly useful for lunar
simulation, as the Unity rendering engine can be used to create realistic lighting and
shadows, which are important for simulating lunar environments.
As such enabling ChronoUnity support for the Chrono lunar simulation framework, will
allow an user to create,edit and manage lunar robotics simulations much easily. Though
some work has been done to add ChronoUnity support for lunar simulation, work is
still needed to be done to support sensor simulations and the Chrono::Worlds module
in ChronoUnity. Figure 7.1 shows the framework of ChronoUnity and how it can be
