Extends the benchmark from monocular D-NeRF to multi-view video (Neural 3D Video, N3DV), as proposed in #1. Draft: the notebooks have run end to end on single scenes (smoke and pilot runs); no result of the study exists yet.
What is in it
Three new notebooks (05–07):
4DGaussians
4DGS native-4D
Spacetime Gaussians, ours_full, trained as one model on the 300 frames
They keep the same monitor, the same metrics and the same JSON schema as notebooks 01–03. The monitor core is byte-identical across the three.
300 frames, as the three papers do, so the results can be checked against the published numbers. Spacetime Gaussians' paper covers 300 frames with six 50-frame models; this study trains one model on the whole window (STG_BLOCK_FRAMES=300), a configuration the paper reports on one scene, with upstream's code and hyper-parameters. One model per method also defines Protocol B on 300 frames. The six-block layout and a 50-frame study remain available.
Protocol A at each method's official budget, not at a common one: 3 000 + 14 000 steps for 4DGaussians, 30 000 for the other two, with about 30 samples of the metrics per run. Spacetime Gaussians is also read at 10 000 steps (the paper's 300-frame model) and at the per-scene snapshot of its configs.
LPIPS from the code the three repositories share. They bundle the same lpipsPyTorch module (identical files) and call it on images in [0, 1]; the notebooks do the same. Every evaluation records it with VGG (lpips) and with AlexNet (lpips_alex), because on N3DV two of the three papers report AlexNet and the third does not state its backbone.
Run anywhere, drive over SSH. The notebooks detect whether they run on a lightning.ai Studio, on Colab or on a plain Linux machine. Every setting is overridable with BENCH_<NAME>, scripts/run_benchmark.py runs Part 1 headless, PREPARE_ONLY=true does the data preparation (COLMAP included) on a cheaper CPU machine, and all results go to one Google Drive folder through rclone.
Videos of every final model. At the end of a run each notebook renders four videos into <run>/videos/ (held-out view next to the ground truth, a fixed novel view, a sweep across the camera rig, bullet time), on camera paths that are the same for the three methods. Not yet run on a GPU.
Host memory per run. Besides peak VRAM, every run records the peak host memory of its training processes.
A smoke-test path. A short run of one scene goes to its own folder, and scripts/estimate_gpu_hours.py turns it into measured seconds per step, peak VRAM, preparation time, disk, and an estimate of the GPU hours of the full study.
Analysis pipeline parametrised by study: GS_STUDY=n3dv (300 frames) and GS_STUDY=n3dv_f50 (50 frames). A table reads each run where its authors read it. The monocular outputs are byte-identical to before.
Documentation:
METHODOLOGY_MULTIVIEW.md: which differences between the methods were removed and which only declared.
OPEN_DECISIONS_MULTIVIEW.md: the choices behind the protocol, taken and open, with pros, cons and sources.
DISCLOSURES_MULTIVIEW.md: what a reader of the results has to be careful about, including the corrections found before the study runs (§7).
Dynamic 3D Gaussians: set aside
It was the fourth method of this extension and was set aside before any run. In the only published N3DV comparison (Spacetime Gaussians paper, Appendix B, Table 6) it is last in quality (30.67 dB PSNR, 0.099 LPIPS, against 31.59–32.05 dB and 0.044–0.047) with a 2.7 GB model against 100–200 MB, and first only in rendering speed, which this benchmark does not measure. Its per-frame cost had also forced a 50-frame main window. Details in METHODOLOGY_MULTIVIEW.md §1.1.

Extends the benchmark to the multi-view setting, as proposed in issue #1. Four
notebooks, one per method that accepts multi-camera input:

  04  Dynamic 3D Gaussians (Luiten et al.)      studied, never benchmarked
  05  4DGaussians (Wu et al.)                   multi-view counterpart of 02
  06  4DGS native-4D (fudan-zvg)                multi-view counterpart of 03
  07  Spacetime Gaussians (Li et al.)           studied, never benchmarked

Same analysis as the monocular study: the same ten metrics, the same two
protocols, the same JSON schema and the same analysis pipeline. The core of
the benchmark monitor is byte-identical in the four notebooks -- it is
delimited by explicit markers -- and everything repository-specific lives in a
glue block behind ten named functions. Two of the four repositories have no
training_report(...) to wrap: their loops call report_progress(...) and
controlgaussians(...), which the monitor wraps instead, reading the rest of
the loop state from the calling frame.

Conventions, chosen so the four methods are comparable: N3DV at 1352x1014
(the resolution every official N3DV config uses), cam00 held out as the
dataset itself prescribes, and the first 50 frames of each scene -- the
longest window in which all four fit a free-tier T4, and the one where
Spacetime Gaussians' native 50-frame chunk equals the whole window. The test
split is then exactly 50 views for every method, so MAX_EVAL_VIEWS stays at 0.

Eight differences between the methods were removed (resolution, test split,
temporal window, a shared COLMAP initial cloud, one LPIPS backend, background,
metric definitions, sampling grid) and eight could only be declared (batch
size, optimisation structure, model variant, environment map, per-frame
initialisation, per-camera exposure, storage definitions, densification).
Forcing the second group would have reported numbers about methods nobody
runs.

Protocol B targets ship as None: they are derived from Protocol A results,
and no multi-view run exists yet.

Checked without a GPU or the dataset: valid nbformat, every code cell
compiles, the generated monitor compiles, the monitor core is byte-identical
across the four, each glue block defines all ten hooks, cells 0.1/0.2/3
execute standalone, a run from another frame window is never reused, and
_Monitor.step() produces a well-formed entry against a stubbed repository.
Nothing touching CUDA, COLMAP or N3DV could be executed.

The multi-view runs will be made on lightning.ai cloud GPUs, not on Google Colab,
and driven from a terminal rather than a browser. Three changes make that work.

**Platform detection (new cell 0.0).** The notebooks worked out of /content and
imported google.colab unconditionally. They now detect Colab, a lightning.ai
Studio (/teamspace/studios/this_studio, persistent) or a plain Linux machine, and
derive every path from WORKDIR instead of hard-coding one. Installing system
packages picks up sudo where it is needed. Nothing else in the notebooks changed.

**Every setting is an environment variable.** Each value in cell 0.1 now reads a
BENCH_<NAME> variable and keeps its literal as the default, so the interactive
workflow is untouched while an unattended run can be configured entirely from a
command line. scripts/run_benchmark.py executes Part 1 of a notebook headlessly
with a real Jupyter kernel -- so the pip installs and the magics behave exactly as
in the browser -- stops at the Part 2 marker (Part 2 renders and would compete for
the GPU), streams output live so a multi-hour cell can be followed with tail -f,
saves the executed notebook for inspection, and exits non-zero when a cell fails.

**One Drive folder for the whole study.** Each notebook used to write its own
top-level Drive folder. They now share one, with a subfolder per method named
exactly as results/analysis/scripts/study.py expects, so the folder collects the
JSON of all four methods and can be analysed as it is. On Colab it is the mounted
Drive; anywhere else the notebook writes locally and keeps it in step through
rclone, pulling at startup so a fresh machine resumes instead of retraining, and
pushing each run as soon as its JSON is final. A failed sync is reported and never
loses a finished run.

Checks grow from 181 to 240: cell 0.0 executes and its platform and WORKDIR are
honoured, every path lands under WORKDIR, each BENCH_ override actually wins, the
four notebooks declare four distinct folder names that study.py knows, and they
agree on one study root. The headless runner was exercised end to end on a
synthetic notebook: settings reach the kernel, output streams, Part 2 is skipped
and a failing cell gives exit code 1.

  resamples the initial cloud); a colmap wrapper forces SIFT on the CPU for the
  upstream per-frame preparation.

Converting the LLFF poses of poses_bounds.npy to COLMAP's convention, the
stage negated the middle column of the rotation as well as the last one, so
every camera had determinant -1. COLMAP then triangulated a few hundred
spurious points (357 on sear_steak, mean track length 2.0) and dense fusion
kept 39. 4DGaussians and 4DGS native-4D were initialised from that cloud.

The conversion is now columns (1, 0, -2), as in hustvl's
scripts/llff2colmap.py and Spacetime Gaussians' script/pre_n3d.py, and the
stage asserts that the rotations are proper. Checked on a local CPU COLMAP:
the same 21 images give 3 926 points, a mean track length of 5.8 and a
reprojection error of 0.69 px, and the points reproject at a median 0.5 px
