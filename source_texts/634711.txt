parse_dxp only lists texture names, and the comment above it invites an issue for anything more. This adds decoding of the texture data itself.
What's added
dxp::DxpPack: reads the full DxP2 (v2) table dump (names, DDSx headers, data records). Layout is documented on the type and follows DDSxTexturePack2 in Dagor's texPackMgr2.cpp
ddsx::DdsxHeader / ddsx::Texture, following ddsxTex.h, ddsxTexMipOrder.h and Gaijin's own ddsx2dds converter:
decompression: Oodle via the pure-Rust, MIT-licensed oozextract, and zstd. zlib/7zip return an error (not used by the game)
mips reordered from smallest-first into DDS order, including cubemaps and volume textures
textures with generated mips (0x6000 flags) store only the top mip plus 12 trailing bytes, which are dropped
Texture::to_dds(): keeps the original pixel format and every stored mip. BC7 gets a DX10 header; A8R8G8B8, A8B8G8R8, L8 and A8 use bit masks; DXTn/ATIn and the float formats go through FourCC
optional png feature: Texture::to_rgba() / to_png() for the top mip (BC1-5 and BC7 through texture2ddecoder, plus the uncompressed formats; half-floats are clamped)
explicit errors for empty placeholder entries, delta textures that need a paired base (0x20000), array textures and unknown formats
parse_dxp and everything else is unchanged
Verification
cargo test: 64 passed; cargo test --features png: 66 passed (9 new DDSx unit tests, plus an integration test on samples/dxp/hq_tex_water_garbage_piles.dxp.bin). python_bindings and wasm_bindings still cargo check (host target only, I don't have wasm32 installed)
Full War Thunder 2.59.0.80 install (macOS), all 4,318 .dxp.bin packs, 148,335 non-empty textures:
147,945 decoded and written as DDS (99.7%): DXT1, DXT5, BC7, ATI1, ATI2 and D3DFMT 21/28/32/50/111/113
375 delta textures needing a paired base, rejected as expected
15 tiny $tq thumbnails in zzz-tq_pack fail inside oozextract (Leviathan streams of ~760 bytes, while 22,600 others in the same pack decode fine). Looks like an oozextract edge case, I'll report it there
PNG output spot-checked by eye for every format
wt_ext_cli built against this branch produces byte-identical output to master for unpack_vromf (aces, char, game, gui, wwdata) and unpack_dxp_and_grp: 31,735 files compared
Notes
oozextract is a regular dependency (6 small transitive deps, no tokio). Happy to put it behind a feature if you'd rather keep the default build lean
I only have stable rustfmt, so alignment follows the nightly config by hand

data records. Texture::from_ddsx decompresses a texture (Oodle via the

- empty placeholders, delta textures needing a paired base, array

Thanks, that makes sense, and I'm happy to maintain it. Splitting it out keeps wt_blk lean.
I'd suggest one crate for both textures (#28) and models (#29), say wt_assets, but whatever name you prefer works. Reasons to keep them together:
Both read the same kind of game data. DXP packs and GRP packs are the two halves of a vehicle (geometry and its textures), and anyone exporting a model needs both.
Both pull in the same heavy dependencies (oozextract for Oodle, image/PNG output, meshopt index decoding), which would then stay out of wt_blk entirely.
Fuzzing has already turned up a batch of hardening fixes for both readers (allocation limits, bounds checks, Oodle panics turned into errors). They would land there in one place.
Would you rather have it as a separate repository in the organization, or as a folder (workspace member) inside wt_blk?
Once it's set up, I'll move both PRs there, keeping their history, with the fuzz fixes and a CI workflow, and close #28 and #29 here. wt_ext_cli #24 would then depend on the new crate instead of a wt_blk branch.
