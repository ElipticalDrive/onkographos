WGSL workgroupBarrier scope within workgroup vs across workgroups
💡 Result:
In WGSL, both workgroupBarrier and storageBarrier are designed to operate exclusively within the scope of a single workgroup [1][2][3]. They cannot be used to synchronize memory accesses or coordinate execution across different workgroups [1][3]. Key aspects of this limitation include: Workgroup Scope All synchronization functions in WGSL, including workgroupBarrier and storageBarrier, have a Workgroup execution scope and a Workgroup memory scope [4]. This means they only coordinate the behavior of invocations belonging to the same workgroup [1][5]. Execution Independence Workgroups are executed independently [1][3]. The WebGPU compute model does not guarantee the order in which workgroups execute, nor does it provide a mechanism for one workgroup to block, wait for, or synchronize with another workgroup using standard barriers [1][3][5]. Memory Visibility While workgroupBarrier ensures memory consistency for the workgroup address space and storageBarrier handles the storage (buffer) address space, their effects are strictly local to the invocations within a single workgroup [1][2]. Using these barriers does not guarantee that memory writes made by one workgroup will be visible to invocations in a different workgroup [1][3]. Alternatives for Inter-Workgroup Synchronization Because standard barriers cannot synchronize across workgroups, developers requiring cross-workgroup data exchange must typically rely on atomic operations [1]. Atomic types in the storage address space have a wider memory scope (QueueFamily), which allows them to provide visibility and availability guarantees across different workgroups [1].
