What happens. renderer/include/engine/renderer/render_device.h (struct RenderDevice, :377) is a bind/set/draw table: bind_program (:438), set_param_* (:444-461), bind_texture_slot (:411), draw_indexed and draw_indexed_instanced (:485-487), bind_render_target (:496). The word "compute" does not appear in the header, DeviceCaps (:328) has no compute flag, and the only pipeline-state concept is the RenderState struct (:298) applied per draw through apply_render_state (:503). Tile light culling is computed on the CPU (renderer/src/light_culling.cpp). In the bgfx backend each bind_render_target claims a fresh view (render_device_bgfx.cpp:1180-1185) and each draw is setState plus submit (:938-941).
DeviceCaps holds instancing, uniformBlocks, timestampQueries, cookedPrograms, maxTextureSamplers, maxTextureDimension, depthBlit, textureArrays, depthZeroToOne and textureOriginBottomLeft (:328-361); the uniform-buffer entries it does carry are dead in bgfx (caps.uniformBlocks = false, render_device_bgfx.cpp:1300). Skinning is a vertex-shader palette: a mat4[128] uniform array uploaded per skinned draw per program (gbuffer_skinned.vs.sc:21, render_device_bgfx_programs.cpp:545-560, cap 128). bgfx itself supports compute shaders on the backends that have them, so the missing piece is the engine contract, the shader cook and a caps flag (WebGL2 has none).
Failure scenario. #618 plans particles with CPU simulation first and "GPU simulation later behind the same asset", and #623 plans renderer scalability; neither can use the GPU for simulation, skinning, culling or clustering without a new device contract, and a second real backend behind bgfx has to reimplement a GL-style state machine.
GPU skinning once per frame for all passes (which would also fix forward skinning at the root, #809), GPU-driven culling and virtual texturing cannot start until the contract can express compute and storage buffers.
Commercial benchmark. Unreal's RHI has compute shaders and pipeline-state objects, Godot's RenderingDevice exposes compute pipelines, and Unity has compute shaders; GPU particles and GPU-driven culling are built on them.
Unity and Unreal use compute for GPU particles, skinning, culling and light binning.
Why this class and severity. A capability the repository does not claim (the vision lists no GPU compute): class:feature. P3: nothing on the current roadmap needs it before the CPU-first particle system, and bgfx can express compute (bgfx::dispatch) when it is needed.
Fix direction. Add compute programs, dispatch and storage buffer/image bindings as caps-gated optional entries on RenderDevice (null-device parity included), leaving the bind-style calls as the compatibility layer. Do this before the first GPU-simulated feature, not with it.
The shader cook manifest also needs a compute stage, and the fake device needs a matching implementation for CPU tests.
Closure. Feature acceptance: caps.compute is false on the null device and true where bgfx supports it, a compute dispatch test runs on the real backend in the gpu lane, and no upper layer includes a bgfx type.
Related. #618 (particles), #623 (renderer scalability), #616 (character animation), #809 (forward skinning), #672 and #673 (Metal and D3D12 backends), #933 (the state-contract gaps: stencil, scissor, depth bias, additive blend).
