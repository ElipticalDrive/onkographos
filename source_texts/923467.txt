Why
#12 is the umbrella for interest management. This issue is the preferred SpacetimeDB-shaped implementation: chunk/region indexes + multi-lifetime subscriptions + shared anonymous views — not per-client "entities near me" recompute.
At small N, SELECT * FROM player_pose is fine. At zone scale, row count in each client's subscription dominates more than row width.
Design (SpacetimeDB-aligned)
```
player_pose
  + chunk_x, chunk_y (or region_id), indexed

Client subscriptions (group by lifetime):
  - always: self pose, self ack, self health/action
  - zone: nearby chunk pose queries (subscribe new before unsubscribe old)
  - rare: metadata tables

Prefer anonymous shared views / shared chunk queries so players in the same
chunk share materialization, rather than ViewContext "near me" per subscriber.
```
Acceptance criteria
Written design note in-repo (chunk size, subscribe radius, edge/hysteresis, teleport)
Pose (and ideally projectiles) carry chunk/region key with indexes matching query patterns
Client uses multi-subscription lifecycle (subscribe-before-unsubscribe; no overlapping full-table + filter waste)
Local player never loses own state when crossing chunks
Threshold documented: when full-table is still OK vs when chunking is required
Test plan: join, leave, sprint across chunk boundary, two players in same chunk
Links SpacetimeDB view/subscription guidance in the design note
