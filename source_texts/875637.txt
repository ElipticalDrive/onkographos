Owner
This PR changes FastNoise2's output, but only at float rounding level, and only for three nodes. For every seed, Divide with a constant RHS, Fade with constant Fade Min and Fade Max, and Remap with all four range values constant (and every node tree that contains one of them) give values that differ from before by about one ulp: at most 3.7e-7 of the output range in the measurements below, typically 5e-8, with 2-57% of the samples changing. It is not a re-seeding: the noise pattern, statistics and look are unchanged. With a generator connected to Divide's RHS, to Fade Min or Fade Max, or to any of Remap's range inputs, the nodes are bit identical to before, and so is every other node. One visible edge case changes: a constant RHS of 0 in Divide now gives +-inf with every compiler (clang and GCC builds gave NaN, MSVC builds already gave +-inf). No API, metadata or node layout change. Worth a line in the release notes for users who compare outputs bit for bit.
What changes in the noise
All three nodes divided by a value that is the same for every point, once per point:

Remap
From Min/Max and To Min/Max are constants
toMin + ( source - fromMin ) / ( fromMax - fromMin ) * ( toMax - toMin )
FMulAdd( source - fromMin, s, toMin ), s = ( toMax - toMin ) / ( fromMax - fromMin )
r and s are scalar divisions computed once per call, which every compiler rounds correctly. Before, the per point division was compiled differently per compiler: clang and GCC (-ffast-math) turn a vector division into a reciprocal estimate plus one Newton step, which is not correctly rounded, and MSVC uses a real division. So before, the same node gave slightly different values on MSVC, clang and GCC builds; now every compiler multiplies by the same correctly rounded r / s (see "Compiler consistency" below). Remap's multiply-add is FastSIMD's FMulAdd, as in the other modifiers: fused on AVX2/AVX-512, a multiply and an add on SSE2/SSE4.1, the same with every x86 compiler (WASM and AArch64 follow FastSIMD's FMulAdd for those targets). The clamp of Remap, the interpolation and zero range handling of Fade are unchanged.
Which outputs change. Only the three nodes in the conditions above, and the node trees that contain them. In the test harness (1212 rows: about 100 node configurations x 4 feature sets x 2D/3D/4D x grid / random / far / tileable / GenSingle x 2 seeds) the only rows that are not bit identical are Op_Divide, Op_Fade and (GCC only) Op_Remap; at a tolerance of 1e-3 of the output range only the 12 Op_Divide rows differ, because that harness case divides by the default RHS of 0 (NaN before, +-inf now on clang and GCC; bit identical on MSVC). The harness Op_Fade / Op_Remap cases use power of two ranges, so they change by at most 1.3e-7 of the range there.

Block paths. The composite block evaluation uses the same maths as the per vector path. Divide's block path used to decline a constant RHS (only so the block loop wouldn't compile the division into a multiply by the reciprocal, which would have changed the output); now that both multiply, a constant RHS over an LHS with its own block path (fractals, other composites) is evaluated a block at a time, exactly like Multiply with a constant RHS. Fade's and Remap's block paths take the reciprocal / scale computed once per block call. Modulus keeps its per point division and its per vector constant RHS path (comment updated).
Why
Speed. A multiply (Remap: one multiply-add) instead of a division per point: with clang/GCC the division is a reciprocal estimate, a Newton step and a multiply (about 4 dependent operations), with MSVC a divps (about 10 cycles latency on Zen 4 and several times the throughput cost of a multiply). The gain is limited to these three nodes, and in the benchmarks only Divide shows it; Remap is slower with MSVC in 3D. See Speed.
Compiler consistency. These three nodes now round the same with every compiler (their sources can still differ between compilers, as before). With White noise sources (which are bit identical across compilers, so only the operator's rounding is compared), Divide, Fade and Remap outputs over 4 feature sets x 2D/3D/4D x grid and random positions are byte identical between clang-cl 23, MSVC 19.51, MSVC 19.44, GCC 16, GCC 13 and Linux clang 23. Before, MSVC builds differed from clang builds in 13%, 3% and 29% of the samples (Divide, Fade, Remap) and GCC builds in up to 44%. In the test harness, clang-cl 23 vs MSVC 19.51 builds differ in 91 rows at 1e-3 instead of 103 (the x / 0 rows now agree).
Path consistency. With clang the old per point division compiled differently depending on where the node was inlined (uniform grid row loops, block loops, per vector position array path), so grid, position array and GenSingle could disagree in the last bit. With the precomputed scale, Remap's outputs at the same coordinates differ between those paths in about half as many samples as before on clang builds (7618 instead of 16812 samples over the test set, clamped 7938 instead of 26441, FBm source 10258 instead of 18086); the remaining differences come from the lattice sources and match the generator-input controls. MSVC and GCC builds didn't have this and are unchanged within a few percent either way. On no toolchain does the maximum difference between paths grow for any configuration.
Quality evidence
Before = base branch, after = this PR, clang-cl 23 unless stated. Hashing, gradients and seed handling are not touched, so seed statistics and spectra are those of the base branch; the output moves by at most 3.7e-7 of its range, which bounds any change of the output statistics to that level.
Images (512 x 512, left before, middle after, right |after - before| scaled to its own maximum, black = identical): constdiv_Divide_FBm.png (max 5.2e-8 of the range), constdiv_Fade_FBm.png (6.1e-8), constdiv_Fade_quintic.png (3.7e-7), constdiv_Remap_FBm.png (4.5e-8), constdiv_Remap_FBm_clamp.png (9.9e-8), constdiv_Tree_Add_Divide_Remap.png (8.8e-8). Same result as the first implementation of this change (on the earlier perf branch). With White sources, which are identical in both branches, the Divide, Fade and Remap outputs of this PR are byte identical to it on every feature set, dimension and path, although the two base branches differ there (their per point divisions round differently in the newer row and block paths). With lattice sources, Divide and Fade change the same samples within 0.3% with the same maximum ulps; Remap's changed sample counts differ (the "before" side differs between the bases), the maxima relative to the range are the same.
Finite outputs and ranges. Far (|coord| ~2e5), huge (3e7 .. 1e12) and NaN / inf / 1e30 input sets, every feature set and dimension, all six compilers: no sample is non-finite after the change where it was finite before (with ordinary inputs). The only non-finite outputs on ordinary inputs are division by zero (constant RHS 0, and a generator RHS that is exactly 0), the same samples before and after. Clamped Remap never leaves [To Min, To Max].
Consistency across code paths (grid vs position array vs GenSingle at the same coordinates, random positions vs GenSingle, every feature set vs SSE2): the maximum path difference of no configuration grows, on any toolchain.
Speed
Divide gets faster with both compilers and Fade does not change measurably. Remap is unchanged with clang-cl 23 and slower with MSVC 19.51 (VS 2026), almost all of it in 3D. Nothing else moves.
Measured on a Ryzen 9 7950X, one pinned core, nothing else running: clang-cl and MSVC under Windows, GCC and Linux clang under WSL 2 on the same machine. Both builds use FastSIMD 7aff025 and run interleaved in one process, in 3 processes with the A/B order alternating; each figure is the median of the per-process new/old time ratios (lower is faster). Two identical builds give feature-set geomeans of 0.998-1.001 and 99% of single rows within 1.5% (worst 9.1%) under Windows, and 0.999-1.005 and 2.4% under WSL, where a few single rows were 8-26% off in every process, so a lone Linux row is not evidence on its own. Divide. The gain is largest in 2D (clang-cl 23: 0.960; MSVC 19.51: 0.955, AVX-512 0.929) and smallest in 4D (0.985, 0.981).
Fade. The harness case evaluates three noise sources and interpolates, so its one division is a small part of the cost.
Remap, MSVC 19.51. Three stable regressions, all in 3D: AVX-512 1.137 (processes 1.137, 1.138, 1.111), SSE4.1 1.052 and SSE2 1.038. AVX2 2D (1.058) and AVX-512 2D (0.969) are unstable. The cause has not been investigated: the new code only drops the division, and neither 4D nor clang-cl 23 shows it.
Default set. MSVC 19.51 SSE2 and SSE4.1 come from a disturbed run (65 of their rows with processes more than 0.05 apart); the rows whose processes agree give 0.998 and 0.997.
GCC 16. Only the default set was measured: no change beyond noise, 0.999-1.000 per feature set and no row above 1.03.
Not measured: GCC 13 and Linux clang 23 builds, the Divide/Fade/Remap set with GCC 16, AArch64, random positions, and Divide with a constant RHS over a composite LHS (the new block path).
Testing
Builds: clang-cl 23, MSVC 19.51, MSVC 19.44 (Windows), GCC 16, GCC 13, clang 23 (Linux), Emscripten 6.0.12 (WASM, no warnings), clang 23 AArch64 cross compile (NEON and AArch64 feature sets).
Test harness vs the base branch, every toolchain: at 1e-7 only Op_Divide, Op_Fade, Op_Remap rows are not bit identical (MSVC 19.51/19.44: all 1212 rows bit identical); at 1e-3 only the 12 Op_Divide rows (x / 0, NaN -> +-inf) on clang-cl 23, Linux clang 23, GCC 16 and GCC 13. Against master built with the same FastSIMD, the DIFF rows are those of the base branch (MSVC 19.51 far coordinate / jitter rows, Linux clang 23 Op_AddDimension) plus these 12 Op_Divide rows.
Constant denominator test (new tool): 22 node trees (Divide by 3.7 / -0.3 / 0.1 / 0 with Simplex, Value, FBm and White sources; Fade with constant ranges, linear / Hermite / quintic, FBm and White sources, zero range; Remap with and without clamp, FBm and White sources; an Add tree of Divide and Remap; controls with a generator in the denominator) x 2D/3D/4D x 4 feature sets x two grid shapes (block path with a partial last block, row path), 4099 random positions, GenSingle and GenTileable2D, on all six compilers: changes within 2 ulp / the table above, controls and zero range Fade bit identical, no larger path differences, no finiteness changes, clamp respected; edge input sets as above; byte comparison of the White-source outputs across the six compilers.
Dependencies
None. Independent of the other output-changing PRs: it only touches Divide, Modulus (a comment), Fade (Blends.inl) and Remap (Modifiers.inl), and merges cleanly with each of them.
