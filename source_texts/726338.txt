Why
A scene USDZ's sequence_tracks.json says where every dynamic object is at every moment. Until now splatsim had nothing to draw there — the Gaussians are one static world-frame cloud, so a moving car is either smeared into the background or cut out of it and gone.
3dgs_io v2.1.0 added the other half: splatsim.actor_assets/v1, a bank of object-local Gaussian clouds plus the bindings that say which track renders with which asset. This is splatsim's consumer for it.
Poses come from outside
The library hands out RigidBody instances and the scenario drives them — a CARLA bridge, a scenario runner, the gRPC service. The bundle's own tracks are metadata here, exposed through ActorAssetLibrary.bound_track_ids for callers replaying a recording, not a playback engine.
```
scene = Scene.from_config("scene.usdz")
print(scene.actor_library.asset_ids)          # what the bundle ships

scene.spawn_actor("sedan_0007", name="car_01", position=(113.6, -58.5, 1.9))
scene.spawn_actor("sedan_0007", name="car_02", position=(120.0, -58.5, 1.9))
scene.set_pose("car_01", (114.1, -58.5, 1.9), (0.966, 0.0, 0.0, 0.259))
```
Instances share their base tensors, so fifty of the same sedan cost one upload.
What's in the diff
splatsim/actor_assets.py — ActorAssetLibrary reads the bank out of a scene USDZ and spawns instances. An asset's Gaussians and its per-Gaussian LiDAR attributes go through cloud_to_tensors and attach_lidar_attrs exactly like a background chunk: nothing about an actor is a special kind of Gaussian.
Scene.spawn_actor / SceneConfig.actors — spawn at load time for static props and spawn points, or at runtime from a scenario. Scene.actor_library exposes the bank.
RigidBody(source=...) now accepts GaussianTensors already on the device, which is how bank assets arrive.
attach_lidar_attrs moved from _usdz.py to _conversions.py and made public, so the USDZ loader and the actor bank share one implementation instead of two.
3dgs_io pin v2.0.1 → v2.1.0 (pyproject.toml + uv.lock).

View-dependent bands: camera and LiDAR
An actor's heading changes every frame, so leaving its view-dependent bands in the object frame makes highlights — and raydrop — spin with the car. Posing an actor re-expresses both its colour SH and its raydrop_sh in the world frame; the LiDAR path consumes actor assets through the same Scene.collect_tensors walk a background chunk uses, so intensity, raydrop and the participation mask all reach the LiDAR renderer unchanged in kind.
The rotation about +Z is exact and closed-form — it mixes only (m, −m) pairs, no Wigner-D — which covers the yaw-only poses road vehicles have. RigidBody.sh_rotation_is_exact reports when a pose is tilted far enough out of the ground plane for it to be an approximation, rather than silently approximating.
Note the two SH layouts differ and are handled separately: colours are [N, K, 3] with the DC term at index 0, while raydrop_sh is [N, K] and DC-less (its DC lives in the scalar raydrop_logit), so band l starts at l² and l²−1 respectively.
The direction is the subtle part. The rotation helper's contract is f_out(d) == f_in(R_z(angle) @ d), so 3dgs_io's world→object extraction uses +yaw while instancing object→world here needs the inverse, −yaw. Tests that only pin apply_rigid_transform against the helper prove agreement, not direction, so the invariant tests evaluate the bands along real rays and assert that the unrotated version would be wrong.
apply_rigid_transform keeps its old behaviour by default (rotate_sh=False), so existing rigid bodies are untouched; only actors opt in.

End to end against a bundle written by 3dgs_io's own writer (not a hand-rolled zip): build a scene → extract_actor_asset at the track box → add_actor_assets_to_usdz → load through ActorAssetLibrary and pose from the track. Quality pass over the actor wiring — no schema change, no behaviour change.

Efficiency, on the per-frame transform path:
* rotate_sh_about_z was a Python loop over SH bands: ~70 kernel launches and a
  full [N, K, 3] clone per actor per gather, where master's colours were a
  zero-copy passthrough. A +Z rotation only ever mixes the (m, -m) pair, so it
  is now one gather and one blend against per-coefficient tables cached by
  (coefs, device, dtype) — four kernels, no clone, and the DC and m == 0 slots
  fall out for free (cos 1, sin 0). Same math: still exact to 1e-15 against an
  independent evaluation of the 3DGS real-SH basis.
* yaw/tilt read straight off the quaternion instead of building a 3x3 to take
  three entries out of it, and split into yaw_from_quat / tilt_from_quat so
  neither caller discards half a tuple.

Altitude:
* RigidBody.posed(base=None) — the body owns its transform. Scene's LOD branch
  was a second place that had to mirror how a body wants to be transformed,
  and had already grown a rotate_sh argument to keep in sync; it is now
  rb.posed(base), and the rotate_sh property it existed to read is gone.
* attach_lidar_attrs moved from _usdz to _conversions and lost its underscore.
  It populates a GaussianTensors from a decoded attribute dict — a tensors
  concern, not a USDZ one, which is why it took usdz_path and chunk_name only
  to build error strings. Two modules now import it publicly, with one `source`
  label instead of two USDZ-shaped parameters.
* Scene.from_config builds the Scene and then routes configured actors through
  spawn_actor, deleting a duplicate name-collision guard (with its own
  divergent message), the eager library construction and an assert/noqa. The
  bank is loaded once, on first spawn, either way.
* quat_xyzw_to_wxyz lives in _geometry, whose docstring says outright that it
  exists so these transforms stop being re-implemented per module — and which
  pose_from_track_frame and _lidar_sensors_from_rigs were both re-deriving.

Two problems, both found by finally evaluating the bands along a real ray
instead of asserting that apply_rigid_transform agrees with its own helper.

1. raydrop_sh was passed through unrotated. The previous comment claimed the
   LiDAR path did not consume actor assets — it does: Scene.collect_tensors
   walks the rigid bodies, and lidar_renderer calls it for every sensor. So a
   posed actor's view-dependent drop bands were being evaluated along the
   world-space sensor ray while still expressed in the object frame. A car
   facing east dropped rays with the pattern it had facing north — up to 0.78
   absolute error in drop probability in the check below. raydrop_sh now
   rotates with the colour SH, off the same yaw. The band-0 term lives in the
   scalar raydrop_logit and is rotation-invariant, so it needs nothing.

   The bands use the DC-less layout ([N, K], band l at l*l-1) against the
   colours' DC-first one ([N, K, 3], band l at l*l), so the mixing tables took
   a dc_offset and the blend handles both ranks; the closed form is otherwise
   identical.

2. The rotation went the wrong way — for the colours too. The rotators
   re-express coefficients so f_out(d) == f_in(R_z(angle) @ d). Instancing
   needs the world bands to answer for the object frame, f_world(d) ==
   f_object(R^-1 d), which is the inverse: -yaw, not +yaw. (3dgs_io's
   extract_actor_asset goes world -> object and correctly passes +yaw; this
   side is the mirror image and had copied the sign.) The existing tests could
   not catch it: they pinned apply_rigid_transform against rotate_sh_about_z,
   which proves the two agree and says nothing about direction.

So the tests now pin the invariant that actually matters, for both band sets:
a posed actor evaluated at the world ray must equal the object-frame asset
evaluated at the same ray seen from the object frame — and each asserts that
the unrotated version would have been wrong, so a no-op cannot pass. Also
covered: the DC-less rotation against the exact packing lidar_renderer uses
(degrees 1-3), raydrop rotating for an RGB-mode asset (it does not depend on
sh_degree), raydrop_logit staying put, and the LOD lidar_view gather — the
path the LiDAR renderer actually takes — still handing back rotated bands.

Verified end to end on a bank asset through the real evaluators: 4.8e-07 logit
for raydrop, 6.0e-07 for colour, against 4.26 and 3.34 unrotated.

The rest of the LiDAR path already treated an actor like any other source and
needed no change: lidar_mask is applied per-source before the scene concat, so
an asset without one participates fully; assets with no raydrop bands are
zero-padded to the scene's SH width and contribute only their scalar logit;
and _resolve_lidar_attrs falls back per-source. Documented in the README rather
than left to be rediscovered.
