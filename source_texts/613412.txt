Summary
Implements #110: voxel mesh vertices are packed from 28 to 16 bytes (−42.86 %) with chunk-local coordinates, and the chunk world origin moves to per-draw data (VoxelDrawData SSBO indexed via firstInstance/gl_InstanceIndex) — no per-chunk descriptor binds or updates, fully compatible with the arenas/indirect architecture from #109/#121.
Vertex format (28 → 16 bytes)
```
struct Vertex {
    uint32_t packedPos;        // X 9 bits, Y 14 bits, Z 9 bits @ scale 1/16
    uint32_t packedData;       // normal | texIndex | biome | AO | skyLight | blockLight
    uint16_t texCoordU;        // greedy UVs are integer block extents
    uint16_t texCoordV;
    uint32_t packedBiomeColor; // RGBA8
};
```
Position ranges vs actual geometry: X/Z are chunk-local 0..16 (9 bits @ 1/16 → 0..31.94 covers greedy endpoints at chunk/section boundaries); Y covers 0..256 face vertices (14 bits @ 1/16 → 0..1023). Unit tests round-trip every integer boundary (0..16 × 0..256 × 0..16) and the 1/16-grid plant offsets exactly — no cracks by construction, and precision no longer depends on world distance at all.
UV semantics preserved: greedy UVs are integer block extents and plant/LOD UVs are 0/1 — uint16 stores them exactly, so texture tiling behavior is bit-identical (no normalization anywhere).
Mesher emits the packed format directly (buildSectionGreedy, plant quads, buildLODMeshRanged) — no 28-byte intermediate + conversion pass. Plant geometry was re-anchored from arbitrary decimals (.05/.1/.9/.95) to the 1/16 grid (1/16, 2/16, 14/16, 15/16), which the packing can represent exactly; visually verified in-game.
VertexHasher updated; operator== is field-exact; decodePosition(origin) / decodeTexCoord() give tests a canonical semantic representation.
Per-draw origin
VoxelDrawData { ivec3 worldOrigin; uint flags; } (16 B, std430) in a frame-mapped SSBO at set 0, binding 2. The descriptor is written once per frames-in-flight buffer at init (no mid-command-buffer updates, per project convention).
Each collected draw writes its entry and carries its table index in VkDrawIndexedIndirectCommand::firstInstance; the vertex shaders reconstruct worldPos = chunkOrigin + unpack(packedPos). gl_InstanceIndex includes firstInstance per Vulkan semantics — no extra feature.
Disjoint table regions per pass (opaque 0, water 65 536, shadow 131 072 + cascade × 65 536; 393 216 entries / 6 MiB per frame), partial vmaFlushAllocation per pass, and the FT_VOX_DRAW_DIRECT diagnostic path is kept working (same table, firstInstance as the draw's firstInstance).
Chunk::IndirectDraw carries chunkOrigin in the per-chunk cache ([Vulkan/Performance] Replace per-chunk mesh buffers with shared GPU arenas and indirect drawing #109), so populating the table is a straight copy per draw — no extra chunk lookups in the record path.
Shaders
terrain.vert, shadow.vert, water.vert: aPos → uint aPackedPos, aTexCoord → uvec2, identical unpack (same masks/scale as CPU), world position reconstructed before foliage wind (wind phase uses world position exactly as before). Fragment shaders unchanged.
Review follow-up (drawIndirectFirstInstance + layout hardening)
Vulkan drawIndirectFirstInstance is now explicitly queried and enabled - it is required for firstInstance-indexed per-draw data and was previously left off, leaving the per-draw origin silently ignored on strictly-conformant implementations. Devices lacking it are rejected cleanly at initialization; startup logs drawIndirectFirstInstance=yes.
The per-frame draw-data table layout is centralized in Renderer/VoxelDrawDataLayout.hpp (single source for the opaque/water/shadow-per-cascade regions and total count derived from shadow::kCascadeCount - 5 regions of 65 536 entries, static-asserted non-overlapping); the three passes share it and Debug-assert base + count <= kEntryCount.
Vertex::packPosition uses named bit constants and Debug range asserts (no more silent masking); layout static_asserts lock the attribute offsets to the Vulkan vertex-input declarations.
The out-of-scope network test port change was reverted (54321 restored) - the WinNAT issue needs an ephemeral-port fix of its own, not a third magic port.
The gl_InstanceIndex == firstInstance contract (instanceCount is always 1) is documented in all three vertex shaders.
Tests & validation
test_render_helpers: packed-position round-trip at all integer boundaries (X 0..16, Y 0..256 step 16, Z 0..16), plant 1/16 fractions, UV precision, the contract maximum (CHUNK_SIZE, CHUNK_HEIGHT, CHUNK_SIZE), struct size/offset static_asserts.
test_mesh_facekey / test_mesh_result_pool / test_mesh_upload green.
Full CTest Release: 20/21 - the single failure is NetworkIntegrationTest, pre-existing and environmental (its restored hard-coded port 54321 sits in a Windows/WinNAT excluded range; bind fails before the test body, reproduced on a fresh main binary).
Vulkan drawIndirectFirstInstance=yes logged; FT_VOX_VALIDATION=1 FT_VOX_VALIDATE_INDIRECT=1 and the FT_VOX_DRAW_DIRECT=1 diagnostic path both run with 0 new VUIDs (only the two known pre-existing swapchain/imageView VUIDs on main).
Visual: spawn view (trees/snow/water/foliage coherent, no seams), (10000, 110, 10000) smooth greedy water, and (+1 000 000, -1 000 000) - river, forests, beaches and water all seam-free at a megablock from the origin, which is precisely the precision win of chunk-local vertices + exact ivec3 origins.
Post-review 30 s smoke (grade S, 9920): vertex upload ~82 KB/frame (-45 %), gpu.live 8 arena pages (-25 %), GPU Shadow 0.178 ms (-28 %), Opaque parity - magnitudes match the A/B.

#110)

The packed-vertex renderer writes a non-zero firstInstance into every
VkDrawIndexedIndirectCommand (and uses it in the FT_VOX_DRAW_DIRECT
diagnostic path) to index the per-frame VoxelDrawData table in the
vertex shaders. Honoring firstInstance is optional in Vulkan: without
the core-1.0 drawIndirectFirstInstance feature enabled, the field is
ignored and every chunk renders at the world origin.

The feature is now queried, explicitly enabled, and devices lacking it
are rejected at initialization with an explicit error instead of
silently mis-rendering. Startup logging reports it next to
multiDrawIndirect.
