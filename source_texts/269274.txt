Merge this before #3. #3 (Vulkan error handling) is stacked on this branch. It changes dispatch_compute's signature, which the FFT code here calls from 12 sites, so the two cannot merge in either order.
Backend choice: hand-written radix-2, not VkFFT
#1 left the backend open between a hand-written Cooley–Tukey shader and integrating VkFFT. This PR takes the hand-written route.
The deciding factor is that VkFFT's Vulkan backend generates its kernels at run time, so it needs glslang as a runtime dependency. That breaks the gem's "the only link dependency is the Vulkan loader" rule (CONTRIBUTING.md) and undoes the current design where glslangValidator is a build-time tool only. The README roadmap now records this reasoning, and keeps VkFFT as an option if the hand-written transform runs out of road.
API
```
GPU::SFloat#rfft                    # -> GPU::SComplex, n-point DFT (n a power of two >= 2)
GPU::SComplex#magnitude(k)          # -> GPU::SFloat, sqrt(re^2 + im^2)
GPU::SComplex#power_spectrum(k)     # -> GPU::SFloat, re^2 + im^2
GPU::SFloat#power_spectrum(k)       # convenience: rfft + power
```
k defaults to n / 2 — the non-redundant bins of a real-input transform, as sketched in the issue.
```
sig  = GPU::SFloat.cast(samples)
bins = sig.power_spectrum   # rfft + |X|^2, all on the GPU
bins.to_a                   # only now does anything reach the host
```
How it works
1 + log2(n) dispatches over a single complex buffer of 2n interleaved floats. Nothing is copied to the host until #to_a.

Bit-reversing up front lets the butterflies run in natural order and in place. Each invocation of fft_stage owns one butterfly, and a pass's pairs partition [0, n) exactly — so the in-place writes cannot race within a pass, and the per-pass dispatch boundary is the barrier between passes.
fft_stage needs only one storage buffer, so this adds a LAYOUT_1BUF descriptor set layout alongside the existing 3BUF/2BUF. Every push block stays within the existing 16-byte range, so no pipeline layout change was needed.
GPU::SComplex reuses the existing NArray buffer type, so size / to_a / head are adjusted in mrblib for the two-floats-per-point layout. sum / mean are withdrawn there — summing interleaved re/im components is meaningless. They raise NoMethodError rather than NotImplementedError, because the latter is a ScriptError and would slip past an ordinary rescue => e (including the test helper's).
What I verified, and where
Built mruby 3.x with this gem and ran everything on Mesa lavapipe (software Vulkan, llvmpipe, Vulkan 1.4):
44 tests pass, 16 of them new (ALL TESTS PASSED). The gem compiles with no warnings.
examples/fft_spectrum.rb — a 50 Hz + 200 Hz signal peaks in bins 50 and 200 only, at powers 262144 (=512²) and 65536 (=256²), matching theory exactly.
The shaders' index math was cross-checked against a naive reference DFT for n = 2…1024: max relative error 2e-7, i.e. FP32 round-off. The same check confirms the butterfly pairs partition [0, n) on every pass.
All shaders compile with glslangValidator and pass spirv-val.
Not verified on real hardware. I had no physical GPU available — no Raspberry Pi 5 / V3D and no discrete GPU. The last acceptance-criteria box in #1 ("runs on Pi 5 (V3D) and on desktop") is therefore still open, and the README's "Verified on" section says so explicitly rather than implying hardware coverage this PR does not have. Please run test/narray_test.rb and examples/fft_spectrum.rb on the Pi before merging.
Two things worth a second opinion on real hardware:
bitfieldReverse on V3DV — used by fft_bitrev, and core GLSL 4.50, but worth confirming on the Pi's driver.
cos/sin precision in the twiddle factors. Fine on lavapipe; V3DV's transcendentals may differ enough to matter at larger n. A twiddle lookup table is the fallback if so.
If either turns out to be a problem, note that #3 is what makes it diagnosable: on this branch alone, a driver that rejects fft_stage.spv is reported as Run \make -C shader` first.`
Follow-ups (not in this PR)
Left out to keep this focused; noted in the README roadmap:
The log2(n) passes are log2(n) separate submit+fence round trips, since dispatch_compute waits on a fence per call. Batching them into one command buffer with vkCmdPipelineBarrier between passes is the obvious win for the streaming use case in Add FFT (spectral transform) on Vulkan compute #1.
Inverse transform, real-input packing (halves the work), non-power-of-two lengths.
Note on test dependencies
The new tests use Math.cos / Math.sin, i.e. mruby-math from the default gembox. That is already the build configuration CONTRIBUTING.md prescribes, so no new requirement — just flagging it.

Cross-check script
```
def ref_power(samples, k)
  n = samples.size
  re = 0.0; im = 0.0
  n.times do |t|
    ang = -2.0 * 3.141592653589793 * k * t / n
    re += samples[t] * Math.cos(ang)
    im += samples[t] * Math.sin(ang)
  end
  re * re + im * im
end

def make_signal(n)
  Array.new(n) do |t|
    0.7 +
      1.3 * Math.sin(2 * 3.141592653589793 * 3 * t / n) +
      0.5 * Math.cos(2 * 3.141592653589793 * 7.5 * t / n) +
      0.2 * Math.sin(2 * 3.141592653589793 * (n / 4) * t / n)
  end
end

[2, 4, 8, 16, 32, 64, 128, 256, 512, 1024].each do |n|
  samples = make_signal(n)
  got = GPU::SFloat.cast(samples).power_spectrum.to_a
  ref = Array.new(got.size) { |k| ref_power(samples, k) }
  peak = ref.max
  worst = 0.0
  got.each_index { |k| d = (got[k] - ref[k]).abs / peak; worst = d if d > worst }
  puts "#{n}: #{worst}"
end
```
