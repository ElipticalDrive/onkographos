Fixes #1039.
Problem
A GL texture or buffer name means something only inside the client's GL context. A server process can't reach it. So plain forwarding can't make cuGraphicsGLRegisterImage work: run on the server with no current GL context, the real driver returns CUDA_ERROR_INVALID_GRAPHICS_CONTEXT, which test_graphics_apis.py also rejects. Until now the call didn't reach codegen at all and fell through to the missing-API path (CUDA_ERROR_NOT_SUPPORTED).
Change
Codegen: @remoteclient <helper>. The generated wrapper still routes, and still calls the driver on a local route. On a remote route it returns <helper>(args...) instead of sending an RPC, and no RPC id, server handler, or registration is generated. These use it:
cuGraphicsGLRegisterImage, cuGraphicsGLRegisterBuffer, cuGLGetDevices_v2 (new)
the existing cuGraphicsUnregisterResource, SubResourceGetMappedArray, ResourceGetMappedMipmappedArray, ResourceGetMappedPointer_v2, ResourceSetMapFlags_v2, MapResources, UnmapResources. Their RPCs were unreachable, since nothing could ever create a CUgraphicsResource on a server, so they're removed.
cudaGL.h includes GL/gl.h, which neither the codegen image nor every client build has. So these three declarations come from the annotations, the same way the legacy ABI entry points do (CUDA_GL_FUNCTIONS). cuda_compat.h gets GLuint/GLenum/CUGLDeviceList. The unversioned cuGLGetDevices, cuGraphicsResourceGetMappedPointer and cuGraphicsResourceSetMapFlags names (what cuda-bindings resolves) now map to their _v2 entry points. They were previously missing.
Client staging (cuda_client_graphics.cpp). A remote registration keeps a CUDA copy on the server:
Textures get one CUmipmappedArray per layer or cube face, covering the full mip chain of the base level, as the driver does. Buffers get one cuMemAlloc.
Map uploads the GL contents (glGetTexImage / glGetBufferSubData), skipped for write-discard. Unmap writes CUDA's changes back (glTexSubImage* / glBufferSubData), skipped for read-only. Both copies are ordered on the mapping stream and synchronized.
Supported: 2D, rectangle, cube map, 3D and 2D-array textures in the 8/16/32-bit normalized, integer and float formats (RGB formats padded to 4 channels, as the driver does), and buffers.
The application's texture/buffer bindings, PBO bindings and pixel-store state are saved and restored around each transfer.
Error codes match what the native driver returned for the same calls. No current GL context → INVALID_GRAPHICS_CONTEXT; unknown GL name → INVALID_HANDLE; texture without storage → INVALID_VALUE; and NOT_MAPPED, ALREADY_MAPPED, NOT_MAPPED_AS_ARRAY and NOT_MAPPED_AS_POINTER where the driver returns them.
GL entry points are resolved at runtime (libOpenGL.so.0 / libGL.so.1, then eglGetProcAddress / glXGetProcAddressARB), so the client doesn't link GL. Any GL implementation works, Mesa included, since nothing needs the GL context to be on the server's GPU.
The CUDA_PYTHON_SKIP_LIST=test_graphics_apis.py skip is dropped from the integration suite.
Limitations
Linux clients only; other platforms return CUDA_ERROR_NOT_SUPPORTED from the staged registration.
Renderbuffers return CUDA_ERROR_NOT_SUPPORTED.
cuGraphicsResourceGetMappedMipmappedArray works for 2D/rectangle/3D textures, but returns NOT_SUPPORTED for cube maps and 2D arrays, which are staged a face or layer at a time.
Each map/unmap copies the whole object through the client, so it costs bandwidth that native interop doesn't.
Testing
All runs on a GH200 against a local lupine_driver_server. The client ran under bwrap with the host libcuda.so.1 hidden, so every device was remote, and with a Mesa llvmpipe GL context via Xvfb. That mirrors the CI client container, which has no NVIDIA GPU.
test_graphics_apis.py (cuda-bindings 13.4.4 tests):
before: AssertionError: cudaGraphicsGLRegisterImage returned cudaErrorNotSupported, plus LUPINE missing Driver API called: cuGraphicsGLRegisterImage, matching the issue
after: 3 passed
Round-trip script (not checked in): checks that GL data reaches CUDA on map and CUDA writes reach GL on unmap. It covers 2D with 3 mip levels (per level, and through the mipmapped array), R32F rectangle, all 6 cube faces, RG16F 3D, RGBA32UI 2D array, buffers, read-only and write-discard flags, restored GL state, and every error case above.
through Lupine: 60/60
natively on the real driver with NVIDIA EGL: 54/54. That run skips three cases that crash the native driver: unregistering twice, unregistering while mapped and then again, and unregistering after GetMappedMipmappedArray. The staged path returns the documented error for all three.
./codegen/run.sh leaves no diff; test/run_unit_tests.sh passes (20/20); clang-format 18 is clean on the changed files.
