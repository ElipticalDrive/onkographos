Original prompt
Problem
The VolumetricClouds.shader currently uses a flat 2D noise approach (FBM2D, SampleLayerMask, RenderSimpleLayer) that produces clouds that look like a 2D texture painted on the sky dome — no depth, no self-shadowing, no volumetric feel.
Goal
Replace the current 2D approach with volumetric raymarching through a flat horizontal cloud slab/plane at a configurable height. This should NOT use a spherical shell dome — instead, clouds exist as a flat horizontal layer at a given altitude that the camera raymarches through.
Requirements
Raymarching approach
Cast a ray from the camera through each pixel's view direction
Intersect the ray with a flat horizontal cloud slab defined by a bottom altitude and a top altitude (e.g., cloud plane at height _CloudShellRadius with some thickness)
March through the slab from entry to exit, sampling 3D noise at each step
Use the existing _CloudStepCount property (Range 8–64, default 32) to control quality vs performance
3D Noise
Use the existing 3D Noise3D and FBM/FBMFine functions already in the shader's history (see commit 412b301 for reference)
SampleDensity should sample 3D FBM noise at world-space positions within the cloud slab
Lighting & Shading
Beer-Lambert transmittance: accumulate light absorption as the ray traverses the cloud
Depth-based self-shadowing: deeper samples are darker (simulating light being absorbed from above)
Henyey-Greenstein phase function: forward scattering creates silver linings when looking toward the sun
Rim light on thin cloud edges
Sunrise/sunset warm tinting using the existing _CloudSunsetColor and time-of-day system
Shadow-to-lit gradient using _CloudShadowColor
Two cloud layers
Layer 1: main cumulus clouds at _CloudShellRadius height, full _CloudStepCount steps
Layer 2: higher altitude cirrus at _Cloud2ShellRadius height, 75% of L1 step count
Composite using Porter-Duff "over" blending (already exists in current code)
Performance
Angle-based LOD: reduce steps for near-horizon pixels (long oblique paths need fewer samples)
Early-out: break the raymarching loop when transmittance drops below 0.01
Inspector preview guard: skip raymarching when _ScreenParams.x < 256
Keep the NUM_STEPS_MAX 64 / NUM_STEPS_MIN 4 compile-time bounds
Properties & C# compatibility
Keep ALL existing property names and types — WeatherManager.cs already sets them correctly
Keep the existing camera matrix uniforms (_CloudInvProjectionMatrix, _CloudCameraInvView)
The VolumetricCloudRenderPass.cs render pass already handles everything on the C# side — no changes needed there
Wind animation should use _CloudDirection, _CloudSpeed, and _Time.y
Key existing properties to use
_CloudShellRadius / _Cloud2ShellRadius — cloud plane heights
_CloudScale / _Cloud2Scale — noise frequency
_CloudCoverage / _Cloud2Coverage — how much of the sky is covered
_CloudDensity / _Cloud2Density — optical thickness
_CloudSharpness / _Cloud2Sharpness — edge definition
_CloudEdgeSoftness — soft cloud edges
_CloudVariation — turbulence amount
_CloudHeight / _CloudLayer2Height — height bias for masking
_CloudHorizonCoverage — how far down toward horizon clouds extend
_CloudZenithBlend — zenith blending factor
_CloudShellFlattening — can be repurposed for slab thickness control
_CloudDissolveOffset — weather transition dissolve
_TimeOfDay, _SunDirection, _MoonDirection — lighting
_CloudStepCount — raymarching quality
Reference
The shader at commit 412b301eacd168302d357e06d93b8df8c331fbec has the full volumetric implementation with spherical shells. Use it as reference for the noise functions, lighting model, and Beer-Lambert integration — but replace the spherical shell geometry with a flat plane intersection.
The file to modify is Assets/Shaders/VolumetricClouds.shader.

Beer–Lambert integration isn’t scaling optical depth by the actual march segment length. stepFrac is derived from numSteps instead of stepSize/path length, so when effectiveSteps is reduced by LOD (and when the slab intersection distance changes with view angle) the clouds will become systematically more/less transparent than intended. Consider making optical depth proportional to the distance traveled per step (e.g., use stepSize or (tExit - tEntry)/effectiveSteps) so absorption is consistent across angles and LOD.

optDepth ignores stepSize and therefore ignores the actual length through the slab. This prevents thicker horizon paths from naturally accumulating more extinction and also makes the LOD step-count reduction change the final opacity/brightness. Scale optDepth by the physical step distance (or equivalent normalized distance) so extinction matches the marched distance.
