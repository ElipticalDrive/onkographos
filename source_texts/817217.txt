Alright @MasDennis, @ToxicBakery, @jayschwa, @Davhed, @AndrewJo, time for you guys to weigh in...
Pull request #899 by @Ayrton81 seeks to add an optimization to the terrain generation by splitting it into quadrants and only rendering what is visible to the view frustum. I am proposing taking this one step further and both @Ayrton81 and @MasDennis agree we should handle this now. Unfortunately view frustum culling is what I am in the middle of with Rajawali and I am still a bit burdened at work with a different project, but I will do my best to get it working.
Some Background
For review, and those who have not been following it in detail the scene graph keeps track of objects which inherit IGraphNodeMember. In all current cases this is handled by ATransformable3D and thus the terrain classes can (and most likely already are) being added to the tree directly.
My Concerns
I would like to see the chunking be arbitrary. In the case of a grid, arbitrary x,y count for example
There is culling logic in the terrain classes, some of which was planned for removal with the scene graph. This fragments the culling operations and makes it harder to extend/bug fix. I realize this is the result of not being aware of the details of the scenegraph development.
Should the terrain pieces be added directly to the scene graph or should there be a terrain manager? There are pros and cons to this. In the case of just splitting the terrain into quadrants, the count is small and therefore will make minimal impact on searching the scene graph however the size is large, so they will end up being tested in almost every case. On the other side of the coin, having a smaller node but more of them allows deeper nesting in the graph but more objects in the graph meaning a lot can be culled, but we still potentially end up with larger test sets.
A Possible Solution
We extend the Terrain class, including the TerrainGenerator to make it easier to treat each terrain chunk as a node of sorts. The most important factor here is adjusting the terrain chunk's bounding volume. In this way, Terrain objects can be generated which have static children on them such as buildings or plants and the entire group can be added to the scene graph. The scene graph has an option for adding children recursively or not. This would be extended from its current scene wide configuration to allowing for this to be set on addition/deletion for a specific object.
For complex terrain with lots of static objects when the developer DOES NOT want to test against them, the Terrain chunks can be added without recursion. In the event they do plan on testing against each item, then they can be added to the scene graph recursively. We can provide a flag or enum which can be set in the scene which will allow the developer to select which behavior they would like based on their needs and scene complexity.
Either way, it might make more sense for me to merge #899 into scenegraph rather than having it merged into master. Since the plan is to have scenegraph (#535) merged into master for v0.10 Anchor Steam, this would still ensure this contribution could be provided in a (hopefully) timely manner to the public API. Your thoughts?
