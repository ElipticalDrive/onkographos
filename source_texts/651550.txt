What is in it
1. forge/ParallelFor.hpp (new, header-only) — a reusable worker facility. The index
range is cut into many more tiles than there are workers and each worker claims the next
unclaimed tile from one shared atomic cursor: dynamic self-scheduling over an
over-decomposed space, the balancing property a work-stealing deque gives with one atomic
instead of a deque per worker. An equal static split is wrong here twice — the cores are
asymmetric (10 P + 4 E) and the work is uneven. This is the seam other loops will want:
the kernel is otherwise single-threaded, Tessellate.cpp holds the only real pool, and
BooleanTol.cpp / Features.cpp / Booleans.cpp each spawn one thread as a timeout
watchdog, not for parallelism.
2. Threading voxelIoU — per-worker classifier pairs (Perform mutates the
classifier), per-worker deep copies of both solids via the
BRepBuilderAPI_Transform(identity, Copy=true) this file already called, all Loads on
the calling thread before any worker starts, per-worker counters padded to a cache line
and merged in worker order.
3. An exact bounding-box cull — a cell centre outside a solid's Bnd_Box, slackened by
the classifier's own tolerance, cannot be IN or ON, and BRepBndLib already inflates that
box by the shape's face tolerances. 38.3% of all classifier calls across the corpus are
now never made (5,275,648 -> 3,252,700); 49-64% on the rows where the candidate and the
reference actually differ, which is every row a benchmark contains.

…a denominator

voxelIoU returns four SUMS (inA, inB, intersection, union). Two different
occupancy grids can produce the same four sums -- one cell gained here, one lost
there, cancelling exactly -- so "the counts matched" is strictly weaker than
"every cell matched", and the gap between them is exactly the shape a
parallelisation bug takes.

This adds an env-gated instrument (FORGE_VOXEL_CELL_DIGEST=1) that folds the
per-cell (inA,inB) state pair into one FNV-1a 64 value in the canonical i-j-k
order of the serial loop, and prints the number of cells it folded plus the
number of BRepClass3d_SolidClassifier::Perform calls it made. A later claim of
bit-identity is then checkable against a stated denominator instead of against
the absence of a complaint.

MEASURED, before any change to the loop, on forge_verify at the real default
gridN=64 (fixture: candidate BOX(10,10,10) vs reference box10.step):

    VOXELIOU_CELL_DIGEST gridN=64 cells=262144 digest=95688c7e269a06ed
      inA=238328 inB=238328 intersection=238328 union=238328 errs=0
      classifierCalls=524288

524,288 = 2 x 64^3, serially, for the simplest solid there is. Wall clock for

voxelIoU issues 2 x gridN^3 BRepClass3d_SolidClassifier::Perform calls per scored
part -- 524,288 at the real default gridN=64 that forge_verify.cpp:710 sets and
no benchmark row overrides. They ran serially on one core of fourteen.

WHAT THIS DOES

include/forge/ParallelFor.hpp is a new header-only worker facility: the index
range is cut into many more tiles than there are workers, and each worker claims
the next unclaimed tile from one shared atomic cursor. That is dynamic
self-scheduling over an over-decomposed space -- the balancing property a
work-stealing deque gives, with one atomic instead of a deque per worker. An
equal static split would be wrong here twice over: the cores are asymmetric
(10 P + 4 E) and the work is uneven (a cell deep inside a solid classifies far
faster than one that lands on a face). It is header-only so that sixty lines of
standard library do not put the CMakeLists.txt -> OCCT_REMOVAL_TRACKER.md ->
archie_op_vocabulary.json -> ui/ArchieOpVocabulary.hpp cascade between a caller
and the core.

voxelIoU then gives each worker its own classifier pair -- Perform() mutates the
classifier, so one cannot be shared -- and its own deep copy of each solid, via
the BRepBuilderAPI_Transform(identity, Copy=true) this file already called. All
Loads happen on the calling thread before any worker starts. Counters are
per-worker, padded to a cache line, and merged in worker order.

… calls never made

The grid voxelIoU builds spans the UNION of the two bounding boxes, because an
offset candidate must be penalised rather than silently re-centred. That is the
right grid and the wrong amount of work: whenever the candidate and the
reference differ in size or placement -- which is every row where the IoU is not
already 1 -- a large part of that union is empty for at least one of them, and
the loop classified all of it anyway.

A cell centre outside a solid's Bnd_Box, slackened by the same tolerance the
classifier is given, cannot come back IN and cannot come back ON. BRepBndLib
already inflates the box by the shape's own face tolerances, so the test is
conservative twice over. The answer is OUT either way; this stops paying
BRepClass3d_SolidClassifier to say so.

── THE TOCTOU THREAD: DECIDED WITH EVIDENCE, NOT FIXED BY REFLEX ────────────
classifyPoint() makes separate registry lookups and a concurrent release()
between them would be a use-after-free. The question that settles whether to add
registry API for it is whether that race is reachable. MEASURED on this tree:

  * classifyPoint() has NO production caller. Every call site is a gate. The four
    consumers it was built for still call BRepClass3d_SolidClassifier directly.
  * The kernel's threaded regions are Tessellate.cpp, VoxelIoU.cpp (new in #277)
    and the one-thread timeout watchdogs in BooleanTol/Features/Booleans. NONE of
    the five calls classifyPoint(), and NONE calls ShapeRegistry::release().
  * release() is reached only from src/binding.cpp (the addon entry point),
    src/ShapeHandle.cpp (the RAII destructor) and two temporary-cleanup sites
    (ShapeQuery.cpp, ClassASurfacing.cpp) — all on their caller's own thread.

NOT REACHABLE TODAY, so the lease is DEFERRED rather than added — it is new
public API on a type most of the kernel includes, and I declined the same cost
once already for the cache-erase variant. The precondition is now documented in
ShapeClassify.hpp ABOVE THE DECLARATION, with that evidence and with the exact
trigger that voids it: migrating a consumer onto this seam, or threading one that
is already on it. A latent race is worth naming even when it cannot fire.
