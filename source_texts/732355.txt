Follow-up to #902, which was closed because it was out of date and the MuJoCo C refactor didn't happen. One open question there was how the change would interact with memory alignment work in Warp. I reran the idea on current main with a narrower approach and measured each field separately; the gains are larger and cleaner than in #902, so I'd like to restart the discussion here.
Data stores xiquat, geom_xquat and site_xquat (MuJoCo's (w, x, y, z) convention) instead of ximat, geom_xmat and site_xmat, and drops xmat, which was only ever quat_to_mat(xquat). The producers in kinematics no longer expand the quaternions, and consumers call quat_to_mat where they read the field, so their matrix math is unchanged. For xmat the results are bitwise identical; for the other fields matrix entries can differ in the last bit because the quaternion is rounded before the conversion. put_data and make_data convert from mjData and get_data_into converts back, so code that only goes through mjData is unaffected. One consumer needed care: the nxn broadphase filter would convert both quaternions for every pair, so it now converts only after the bounding sphere test, which makes it slightly faster than on main. There is one commit per field, so any subset is easy to split out.

The gain comes from the producer kernels: _compute_body_matrices disappears and _compute_body_inertial_frames, _geom_local_to_global and _site_local_to_global get 60 to 75% cheaper, which matches the steps/s numbers. Consumers converting locally cost nothing measurable. The hot ones (_cinert, _cdof, GJK/EPA, tendon wrapping) need the full matrix anyway, and where only one column is read the compiler drops the rest of the conversion. Rendering doesn't regress (render megakernel on an RTX PRO 6000: -0.5% on franka, -2% on aloha_pot, within noise). Yuval's intuition about sites holds for most models: site_xmat only matters for site-heavy models like myoarm (+4.1%) and is neutral elsewhere.
On the alignment question from #902: these gains are on the current Warp nightly without any pending Warp changes. I also tried the wide vector stores proposed in NVIDIA/warp#2132, and they make no further difference for the quaternion producers, so the result doesn't depend on them.
The cost is API. Removing the four Data fields breaks direct users of mjw.Data: MJX's warp backend passes geom_xmat and friends by name into mujoco_warp (generated code in mjx/mujoco/mjx/warp), Newton writes geom_xmat and site_xmat for static geoms and sites, and mjlab reads geom_xmat/site_xmat but converts them to quaternions right away. The Apollo notebook in contrib now builds xmat from xquat. Options I see:
Replace all four fields at once and update MJX and Newton alongside.
Phase it in: add the quaternion fields, move MJX and Newton over, then remove the matrices.
Go field by field. Dropping xmat alone is +0.5% to +3.1% and adds no field since xquat already exists; site_xmat could stay if the site-heavy case isn't worth the churn.
Two tests fail on this branch for reasons that are already present on main. test_mesh_mesh_common_translation fails because GJK/EPA on main loses a deep contact for about 5% of tiny orientation perturbations (one ulp up to 1e-3 rad), and the quaternion path happens to hit one of them; I'll file that separately with a reproducer. test_tree_discrete_cg compares deterministic and atomic runs of a chaotic CG scene against a 1e-3 tolerance; on main, perturbing the density by 1e-5 to 1e-3 already spreads that difference from 3e-5 to 2.2e-3, and two of eight such perturbations fail there too. The plane-mesh selection test now accepts the hull starting at another vertex tied for deepest, since rounding picks the other one of two equally deep corners.
Which route would you prefer?
