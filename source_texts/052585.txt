Background
We've started to improve the GI capabilities of three.js last year with the addition of SSGI. Earlier this year we've added a Light Probe Grid system and this PR enhances the project with a node for Voxel Cone Tracing. Every time I had some free slots in the last months, I've experimented in this area and developed multiple PoCs. Now I feel this attempt is good enough for submission.

Comparison
To classify Voxel Cone Tracing, it's important to understand the difference between the existing techniques in the repo. In essence, VXGI sits between SSGI and Light Probe Grids.
SSGI
Pros: Best for full dynamic scenes with changing occluders and light emitters. Because it's a screen-space technique, it works with all lights and mesh types.
Cons: Inconsistent lighting due to Screen-Space artifacts. No proper integration in lighting/scene pass. Noise/disocclusion artifacts.
Light Probe Grid
Pros: Best Performance. Irradiance properly integrated in lighting/scene pass. No noise/disocclusion artifacts.
Cons: Requires (expensive) baking. No dynamic occluders and lights. Noticeable light leaking. No AO estimation.
VXGI
Pros: Best overall lighting quality. No Screen-Space artifacts. Irradiance properly integrated in lighting/scene pass. Dynamic lighting (performance depends on light count and voxel resolution).
Cons: Works best with static occluders since Voxelization is expensive. The amount of light leaking depends on the quality settings. Not all light and mesh types (e.g. BatchedMesh) are supported yet. Noise/disocclusion artifacts.
Implementation
The primary resource of VXGINode is Interactive Indirect Illumination Using Voxel Cone Tracing. At some points, it deviates from the paper and adapts approaches from other VXGI techniques.
In general, VXGI works best in small and medium size scenes with static occluders. In this scenario, the technique can demonstrate its full strength and deliver proper GI quality with great performance. VXGINode accommodates this design target. It uses a dense and not a sparse tree (like in the paper) since you get much better performance with this approach. That makes it no good candidate for large scenes with a lot of open space though (you would need a sparse tree for that). However, there are other GI techniques like SDFGI which are by definition better suited for exactly this use case (large, dynamic scenes).
The implementation depends on compute shaders and storage buffers so VXGINode is not compatible with WebGL 2.
Usage
VXGINode does cone tracing which means the quality of the effect mainly depends on three factors: The number of cones used for tracing, their aperture/angle and the resolution of the voxel volume (the data they are operating on). If you want to ramp up quality in VXGI, increase the number of cones, make their angle narrower or increase the resolution. The default settings (3 cones and 40°) produce 60 FPS in both demos with a medium-tier mobile device (Pixel 8a).
VXGINode is not path tracing so if you compare renderings to Ground-Truth path-traced images, you might find VXGI produces a too dark result in certain areas (e.g. the ground level in Sponza). A typical way to mitigate this is to add some additional source of indirect light like a subtle ambient or hemisphere light. Their contribution is modulated by the AO VXGINode automatically computes. The GI from the node already accounts for occlusion.
Given how VXGI works, it is not immune to light leaking. However, there are effective ways to mitigate this issue. Next to increasing the quality like mentioned above, there is an opt-in called directionalRadiance which is the most effective way to reduce light leaking. It comes with a performance hit though and not every scene needs it. However, the Sponza demo is one example that clearly benefits from enabling directional radiance.
Roadmap
Improve support for more object types (e.g. BatchedMesh).
Support dynamic updates to occluders without requiring a complete Voxelization.
Make the image more temporal stable (same root cause as SSGI, requires a spatio-temporal denoiser).
Implementing SDFGINode as an alternative for large, open, dynamic scenes. Godot for example also provides a solution for both.
Additional Notes
The flicker you see in the Sponza demo at bright areas is unrelated to VXGI. Our TAA struggles to stabilize the image when it encounters very bright values (which is a typical TAA problem).

safeDirection and/or invDirection can be moved out of here, as this is a rather hot method, and this can be generalized to something like:
```
// Williams et al. 2005, "An Efficient and Robust Ray-Box Intersection Algorithm"
vec2 intersectAABB( vec3 invRayOrigin, vec3 invRayDir, vec3 boundsMin, vec3 boundsMax ) {
    vec3 t0 = mad( boundsMin, invRayDir, invRayOrigin );
    vec3 t1 = mad( boundsMax, invRayDir, invRayOrigin );
    vec3 tNear = min( t0, t1 );
    vec3 tFar = max( t0, t1 );

    float tEnter = max( max( tNear.x, tNear.y ), max( tNear.z, 0 ) );
    float tExit = min( min( tFar.x, tFar.y ), tFar.z ); // Clamp to far range?

    return vec2( tEnter, tExit ); // Can then move the testing here and export a float
}
```
mad is emulated from HLSL/Slang like in https://shadertoy.com/view/scy3Dd, which I ported from a BVH kernel optimized for Apple M2. Perhaps these should be their own nodes?
```
#define mad( a, b, c ) ( ( a ) * ( b ) + ( c ) )
float safercp( float x ) {
    return 1.0 / ( abs( x ) < 1e-6 ? ( x < 0.0 ? -1e-6 : 1e-6 ) : x );
}
vec3 safercp( vec3 v ) {
    return vec3( safercp( v.x ), safercp( v.y ), safercp( v.z ) );
}
```
