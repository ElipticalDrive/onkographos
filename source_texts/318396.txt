I can see two possible approaches to take with this:
Adding a set of overloads for each of the ray tracing queries that accept arrays of positions/directions so that we keep the same unified ray tracing interface.
Define a new abstract GPU ray tracing interface that derives the base class and adds any extra GPU specific stuff needed (including buffers as well as functions for array based queries) which the GPRT concrete can be derived from.
Also, would the array based queries only be useful for GPU? Or do you think Embree ray tracing could also see benefits with the array queries?
@pshriwise what do you think?

I think we'll need to play with both a bit to understand the Pros and cons of each. The big question, as you identified is GPRT buffer management and whether to place that on the user by requiring that the buffers go in and out of the API, or handling that automatically inside XDG -- maybe options for both?
Also, would the array based queries only be useful for GPU? Or do you think Embree ray tracing could also see benefits with the array queries?
Embree does support ray packet tracing (in groups of 8 or 16 rays), but this is more useful for rays that are coherent (similar origins and directions). Given the stochastic nature of the rays in Monte Carlo, I don't think there will be much benefit to this in transport but there could be promise in other applications (e.g. view factor determination where rays originate from the same area of a surface and could be grouped by angle).
In the end, I think the best thing to do is get things started via path of least resistance and then write some mini-apps in the repo to determine the best approach. If I had to guess at the moment, it will be easy enough to manage the buffer sizes internally since we know a priori how many particles will be in flight in event based transport mode on GPU and how many threads are being employed on CPU, but we shall see!

@pshriwise
I've made some pretty good headway in a first implementation of array based API calls on this branch https://github.com/Waqar-ukaea/xdg/tree/GPRT-array-queries. It diverges from the HEAD of PR #94 so I'll wait until that's merged before opening any PRs in relation to this issue. New "batch" prefix ray query calls:
```
  // Array version of point_in_volume
  virtual void batch_point_in_volume(TreeID tree,
                                     const Position* points,
                                     const Direction* const* directions, // [num_points] array of Direction pointers
                                     const size_t num_points,
                                     uint8_t* results,
                                     std::vector<MeshID>* exclude_primitives = nullptr) const = 0;

  // Array version of ray_fire
  virtual void batch_ray_fire(TreeID tree,
                              const Position* origin,
                              const Direction* direction,
                              const size_t num_rays,
                              double* hitDistances,
                              MeshID* surfaceIDs,
                              const double dist_limit = INFTY,
                              HitOrientation orientation = HitOrientation::EXITING,
                              std::vector<MeshID>* const exclude_primitives = nullptr) = 0;
```
Couple notes:
Stubs for Embree have been put in place since I've added these at the ray_tracing_interface level - I'm not sure if we will ever want to batch embree calls though.
I've gone for a C-style API here with raw array pointers being passed in and return parameters being populated.
I have a simple test for both batch_point_in_volume() and batch_ray_fire() which essentially takes all of the results from the scalar runs and populates an "expected_results" vector and then runs all of those scalar test_cases in one single batch.
Right now these tests live inside the test_point_in_volume.cpp and test_ray_fire.cpp test cases for GPRT as a final set of assertions over a loop at the end of the test case.
I'm thinking I'll probably define a separate set of test cases to more explicitly test the batch interface but right now these simple tests I have in place are passing so have the first example of launching multiple rays with our GPRTRayTracer class :)
