Contribution by gaiaclary in #6466
Description
GLB imports used a different rotation order from the avatar skeleton, causing a small orientation mismatch for the hand collision volumes. The mismatch occurs because the importer composes the XML rotations as
Rx * Ry * Rz
while in GLM the avatar skeleton's mayaQ(..., XYZ) convention corresponds to
Rz * Ry * Rx
This difference only shows up with bones with nonzero rotations around more than one axis
(e.g. the hand volumes), so it is not exposed by single-axis torso volumes.
The fix is to reuse mayaQ(..., XYZ), as LLAvatarAppearance::setupBone() does, and explicitly
convert the quaternion components to GLM's constructor order. Volume scale,
translation overrides, and bind/rest remapping retain their existing handling.
Validation
Native comparison against the avatar quaternion/matrix calculation passes
for all 26 collision volumes and three additional cases. The old order
differs for both hands and the general three-axis case.
macOS arm64 Viewer app build passes.
Manual in-world comparison: amplified hand probes show a visible DAE/GLB
difference after importing with the older Viewer. Fresh imports with the
corrected Viewer overlap. Skin weights were enabled, joint positions disabled.
The original small boxes looked coincident in both Viewers; two-metre probes
make the roughly 0.522-degree error visible. The default-rest calculation
predicts about 18 mm displacement at their tips.
Reproduction
The accompanying hand-volume-testcase.zip in The PR contains synthetic DAE/GLB probes.
Freshly upload both formats with skin weights ON, joint positions OFF,
scale 1.0 and matching LOD settings.
Wear both on the same avatar, use contrasting colors and inspect the rod tips.
Repeat fresh uploads with the corrected Viewer: the tips should coincide.
Note: Since the fix is in the GLB importer, upload the GLB file again using
the corrected Viewer. Previously uploaded meshes remain unchanged.
