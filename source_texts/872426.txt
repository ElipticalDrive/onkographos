It would be great for (research purposes and others) if this editor could enable users to visualize and edit labelled gaussian point clouds.
Such a feature would require:
Creation or adoption of a standardized label data format for Gaussian Splatting data. Perhaps using an existing label format developed by segments.ai would be a good approach to avoid standard proliferation.
CRUD operations on labeled Gaussian Splat data. To enable users to load, edit, update, apply, and save labels for a .ply file within the editor.
Option to visualize gaussian cloud based on class id. Perhaps by including additional metadata of the class RGB that a point would be rendered as belonging to that class. This would need to be data-visualization friendly by perhaps recommending ordinal data color gradient choices.
I've started the development of such a feature in a fork: supersplat-classifier. Currently, it also includes hot-reloading of .ply files. Ideas and suggestions are welcome :)

The scope-splitting point above seems important. I would keep labeling as a small import/edit/export contract first, then let hot reload or streaming sit on top later.
A minimal first slice could be:
import one compact per-splat label field, such as class_id or instance_id;
keep the human-readable class metadata in a separate table: id, name, color, visibility/default selection behavior;
preserve the imported field through save/export even if only simple class coloring is supported at first;
expose selected-label stats: class id, count, approximate bounds, source field name, and whether the label came from import or editor edits;
write a tiny sidecar or export receipt with source hash, label-table hash, edited labels count, and output hash.
That keeps the feature useful for research workflows without requiring SuperSplat to become a full annotation platform immediately. It also gives reviewers a simple way to tell whether labels survived round-trip editing, which is often the part that quietly breaks.
