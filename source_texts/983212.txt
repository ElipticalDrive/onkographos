The CMB spec has required embedded octree cells to be stored in root-local Morton order since v1, matching discretize.TreeMesh, but the Python package never checked it: writers and readers accepted any order. A file in another order still loads, but consumers that rely on the documented order, such as discretize, then pair model values with the wrong cells without any error. This PR makes the package enforce the order it specifies. The file format, binary layout, and golden fixtures are unchanged.
Add octree_order_keys(position, shape), which returns each cell's int64 root-local Morton key without sorting or modifying its inputs. numpy.argsort(keys, kind="stable") gives the permutation into CMB order, to be applied to level, position, and every model.
write_file and build_file_bytes reject embedded octree geometry whose keys do not strictly increase, including repeated positions and positions outside the base grid. The check runs in their shared validation path, before write_file opens the output. The error names the first offending index and explains the permutation fix.
read_file applies the same check after verifying the geometry and before reading any model payload, for full, selective, and models=[] reads. Accepted files keep their stored order.
Nothing reorders arrays. read_header, read_array, read_arrays, list_models, and read_contents do not check cell order, so they can still open and migrate files written in another order. Reference-mode files store no geometry, so their model order cannot be checked; the docs say so.
The check works through 65,536 cells at a time and computes keys from bit-slice lookup tables cached per grid shape: with power-of-two dimensions, a key is a fixed rearrangement of its position's bits. It adds about 10 ms per 2.1 million cells to octree reads and writes (a geometry-only read_file goes from 3.4 ms to 12.8 ms), with peak memory close to main.
The specification now gives the key formula alongside the existing traversal, adds a rectangular example where root-local and global Morton order differ, and lists the order check among reader validations. The README gains an "Octree cell order" section with a migration recipe that uses the low-level readers. The discretize guide notes that TreeMesh already uses this order, and its timing tables are marked as predating the check because the benchmark dataset is not in the repository. Octree documentation now says "cell" rather than "leaf".
Compatibility: files written in another order previously loaded with read_file and are now rejected, and the writers now reject such inputs. Because this rejects files and inputs that earlier releases accepted and adds a public function, the plan is to release it as 0.3.0; no version constants change here. Closes #10: the any-order proposal it describes was dropped in favor of this enforcement, so two valid files for the same octree always share one cell order.
Validation: all 465 tests pass locally, and Ruff lint and formatting are clean. New tests cover hand-checked keys on rectangular grids, including layouts where global Morton order differs; rejection of global, position-sorted, reversed, shuffled, and repeated orders through both writers; read-side rejection using checksum-valid out-of-order files built from fixtures; unchanged low-level and reference-mode behavior; a migration round trip; identical errors for any chunk size; lookup-table keys matching the coordinate formula on grids from 1×1×1 to 2**63 cells; and a memory bound on the check.
