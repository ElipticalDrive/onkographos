The native trainer (rux create gsplat, PR #241 draft) trains end-to-end but is explicitly not review-ready until two gaps close (per the 2026-09-08 status on #240):
Densification: the working 3DGUT world-space rasterizer exposes no screen-space absgrad, so classic clone/split densification is unavailable — the recommendation on the issue is MCMC relocation (gsplat ships the kernels, needs no screen-space gradient). Current version prunes only.
Held-out evaluation: PSNR is currently measured on training views; a held-out split (e.g. every Nth frame) is needed for honest quality numbers.
Also tracked for the same PR: the two pkgs/gsplat-cuda defects left as FIXME/TODO in package.nix (#301, #302) — batch them into the same derivation-rebuild cycle since any fix costs a ~70 min CUDA rebuild.
Acceptance: PR #241 flips from draft with held-out PSNR reported and densification active; NewOffice quality visibly improves over the 21.4 dB prune-only result.

Both are direct kernel launchers — no c10::Dispatcher, no TORCH_LIBRARY schema, nothing that lived in ext.cpp. This is exactly the failure mode that killed rasterize_to_pixels_3dgs, and MCMC does not have it. (The higher-level gsplat::relocation / gsplat::mcmc_perturb_positions wrappers are also global symbols but are not declared in any installed header, so the trainer will call the launch_* pair.)
Consequence for the package: MCMC needs nothing added to pkgs/gsplat-cuda. So the derivation change is exactly #301 + #302, batched into one rebuild, which is already running.
Plan
1. Package (#301 + #302), one rebuild — in flight
cudaCapabilities is now a derivation argument. Default ["8.9"] (the dev machine's RTX 6000 Ada), not the old 80;86;89. I checked before choosing: flake.nix declares no substituters, so nothing here is cached or shared and the extra two architectures bought nothing but ~45 min per build. Other hardware overrides the package alone — gsplat-cuda.override { cudaCapabilities = [...]; } — which is deliberately not nixpkgs' global config.cudaCapabilities, since that rebuilds the entire CUDA closure. Note config.cudaCapabilities defaults to [], not to the local GPU, so the issue's suggested default would have silently produced an empty arch list.
pybind11 is now consumed as ${pybind11_INCLUDE_DIRS} instead of target_link_libraries(... pybind11::headers), so it stops landing in the static library's exported INTERFACE_LINK_LIBRARIES. The consumer-side find_package(pybind11 CONFIG QUIET) workaround in reusexLibrary.cmake comes out with it.
Both FIXME/TODO blocks removed from package.nix.
2. Held-out evaluation — deterministic strided split (every Nth view held out, N a parameter), reported alongside train PSNR at each checkpoint. Seeded and reproducible per STANDARDS §6; the split is a pure function of view count and stride, so it does not depend on the RNG at all.
3. MCMC densification — 3DGS-MCMC: relocate dead Gaussians onto live ones via the relocation kernel (with the binomial table and Adam moment reset), grow toward a capped budget, inject the covariance-scaled noise each step, and add the opacity/scale regularizers the paper's SGLD formulation requires.
4. Evidence — prune-only vs MCMC on the same NewOffice region, same seeds, held-out PSNR curves plus rendered pairs at matching iterations, on a copy of the project DB.
Will report numbers either way — including if MCMC does not beat 21.4 dB, which is a real possibility for LiDAR-seeded scenes that already start at scan density.

Both deliverables are implemented, measured and pushed (5ad8ba6, 46c659a on feat/gaussian-splatting). I am not closing this issue, because its acceptance criterion is not met — and the reason is the interesting part.
Held-out evaluation ✅
Every Nth view (--holdout-every, default 8) is excluded from training; train and held-out PSNR/SSIM are reported together at each checkpoint over equally-sized, stride-sampled view sets. The split is a pure function of the view count and never touches the RNG, so it is identical across runs and configurations (STANDARDS §6).
MCMC densification ✅ implemented, ❌ does not help

Capacity is not this scene's bottleneck. Those three rows span a 3.1× range in model size and differ by 0.09 dB. The premise in this issue and in #240's last status — that NewOffice saturates near 21.4 dB because it cannot resolve detail finer than the seed — is wrong. Density control in either direction is not the limit.
And the held-out split is exactly what exposed it. MCMC's training-view PSNR rose 20.99 → 21.25 dB. Under the training-view-only reporting we had before, that is a +0.26 dB improvement and I would have shipped MCMC as a win. Held-out went down. That is the whole value of task 3 landing before task 4.
Two mechanisms, for the record
The seed is already at scan density — densification exists to grow a sparse SfM cloud; we start where it finishes.
Growth without separation is a no-op. sample_add puts each new Gaussian exactly on top of its source and relies on the Langevin noise to separate the pair. The noise is gated by sigmoid(-k·(α−t)) with k=100, t=0.005, so a healthy Gaussian (α≈0.5) gets a gate of ~1e-22 — no motion. The duplicates never separate.
Which leads to the third finding:
The paper's opacity/scale regularizers destroy this scene
They are what keeps a population near the death threshold, so the noise gate opens and growth means something. At the paper's 0.01 the model collapses to 12.73 dB held-out, with MCMC relocating 415 M Gaussians — ~68 % of the model on every refine pass.
Cause is scene topology, not tuning. 3DGS-MCMC assumes object-centric capture where nearly every Gaussian projects into nearly every view, so the constant regularizer pull is balanced by photometric gradient almost every step. A corridor traverse is the opposite: each of 344 views sees a small fraction of 1.2 M Gaussians, so most Gaussians get only the regularizer gradient — and Adam, being scale-invariant, applies that lone tiny gradient at the full learning rate. At lr_opacities = 5e-2, an off-screen Gaussian dies in ~60 iterations.

Package defects ✅
#301 and #302 both fixed in one derivation change → one rebuild. Verified on the output: cuobjdump reports sm_89 only, and the exported link interface no longer mentions pybind11. #302 closed; #301 was auto-closed by the tdg action when the TODO comment came out.
Where I think the real limit is
The renders are uniformly soft in a way that reads as smear rather than missing detail. The suspects are pose error — this scan's SLAM baseline measures ~22 mm plane-flatness RMS, which at 480 px is on the order of a pixel of reprojection error across the model — and the 480 px training resolution. Neither is addressed by anything in this issue.
What I need from you
PR #241 is left in draft. The instruction was to flip it only if quality improves over the 21.4 dB baseline, and it does not. Two ways to go:
Review and merge as-is. Held-out evaluation is a genuine improvement to the trainer and belongs on main regardless; MCMC is off by default and costs nothing when unused. The negative result is documented in docs/research/gaussian-splatting.md §5.3.
Hold the PR until the pose/resolution work lands, so Native Gaussian Splatting: working C++/CUDA trainer (rux create gsplat) [WIP] #241 tells a single story that ends in a quality gain.
My recommendation is (1) — the held-out split is what makes every future quality claim on this trainer trustworthy, and sitting on it means the next experiment is measured with the same broken ruler. But it is your call, which is why this is still open.
