Contributor
In the initial contribution of Gaussian Splats (PR #33950), I only supported a single color per splat. This PR adds support for view-dependent rendering of Gaussian Splats via the loading and usage of a spherical harmonics per splat.
Visual Results
The main result is that for the Lion, when you turn it around, it now correctly shows white fresnel/sheen-like fringes (a view dependent effect), where as previously it didn't have this fringe:
Live link:
https://rawcdn.githack.com/mrdoob/three.js/cda74101ee2fc5f3e59bdd2252310b7d9dca97b1/examples/webgpu_gaussian_splatting.html
Coefficient Packing
My implementation tries again to stay as simple as possible. The loaders convert SH coefficients into byte representations in the range of -1 to +1. I then pack those bytes into Int32 during the load process. Higher order SH require more Int32 per splat than lower order SH.
I then unpack them in the renderer and the calculate the SH contribution.
There are much more complex packing methods for SH coefficients in libraries like Spark but I found it was added significant complexity/slowness to both loading and rendering for what was at most an 11.5% memory saving.

View Dependent Calculation via Pre-Pass
The view dependency is constant across the rendered ellipsoid, thus I use a pre-pass in WebGPU to calculate the per splat SH contribution - idea suggested by Florian Hahlbohm.
Unfortunately I was not able to get the pre-pass working in WebGL fallback, so in that case I calculate the SH contribution in the vertex shader, once per each vertex of the splat (4x.)
Code and Bundle Impact
Measured against the PR merge base, the runtime addon changes add about 17.6 KB of raw source. For a typical bundle that exports GaussianSplatMesh, SPZLoader, KSPLATLoader, and GLTFGaussianSplatLoaderExtension, the additional cost for view-dependent Gaussian Splat loading + rendering is 2KB of compressed minified code - not bad in my opinion:
