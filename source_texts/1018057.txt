OpenVDB's io::File::open() does allocations for strings, metadata, and grid descriptors without first checking if the file is big enough to plausibly hold them, which means that small vdb files with corrupted (or malicious) headers can trigger multi-GB allocations or a near-endless loop. Because valid_file() calls open(), this is reachable while probing the format of any input, as found by our nightly fuzzer.
OpenVDB opens the file by path, so OIIO can't interpose on its reads. Instead, our new open_vdb_file() walks the same header, metadata and descriptor layout itself and rejects the file if any declared length or count exceeds the bytes remaining.
The way this walk works follows OpenVDB's parsing for all supported versions (9.0 through 14.0), including the quirks where the library ignores a declared size: registered fixed-size metadata types must declare exactly their size, delayed-load metadata must be empty at file level, and, for OpenVDB before 11.0 (which reads the UUID with a whitespace-skipping formatted read), the UUID must be in canonical form. Otherwise a crafted file could make the scanner and the library parse the remaining bytes differently. Files without grid offsets, which open() streams in full, and the later readGrid() path are still unbounded inside OpenVDB; the deferral log is updated accordingly.
I'll also alert the OpenVDB team to these issues. Hopefully, for some future version of OpenVDB, this will all be no longer needed on the OIIO side.
