So, just some thoughts while looking at the code from a train ride. I will have to validate them once I'm set up and sitting at my pc.
The grids like player and target could be cached in a class, accessible through a Concurrent Dictionary. Maybe including a lock for read/write access management per grid.
The grid of the player could be stored so that it aligns with the orientation of the cockpit. Then for rendering we could use the view specific matrix for the draw.
I'm thinking of building this data once when entering the cockpit, then using callback to update it when needed, using OnBlockAdded/Removed/Changed.
Not sure if that would work for the enemy grids as I don't know how to best decide on the stored orientation. But ideally any grid should follow the same implementation path.
All that grid building and updating could be offloaded to a dedicated thread, so that it does not block the main game tick.
I need to check if the grids can be accessed in a threadsafe way though.
If not: Skip on concurrency and run the updates in batches. But looking the documentation it should be doable:
https://forum.keenswh.com/threads/parallel-modding-guide.7396636/
Once that is working another level of optimization could be chunks. Instead of rendering each voxel, big grids could be set up as chunks of 4x4x4 and render those as single blocks.
Frustum culling for the rendering of camera facing blocks needs to be done too. I haven't checked if the draw method already does this, but it needs to be updated either way for the cache and/or chunks.

More thoughts:
Cleaner separation of code. CircleRenderer is quite monolithic by now.
A first step could be a class for handling grid data:
bascially combining:
localGridBlocks = new List();
localGridDrives = new List();
probably also: _localGridWCWeapons
The class can attach to its grid using OnBlockAdded() and OnBlockRemoved().
That can set an internal flag like "needGridUpdate".
Give the class an Update() function that is called during each UpdateAfterSimulation().
If the flag is set, update the grid, otherwise update all other relevant data like jump drive states etc.
Baiscally making this your go-to point to store, update and retrieve data, but NOT render it.

I'm also wondering if there is a more efficient way to update the data of a grid.
doing localGridBlocks = new List(); will likely release and later reallocate memory for the list, which can be quite performance heavy.
if the target size of the list is known it could be reallocated with that size.
For example in HG_GetBlockInfo()
instead of:
List blockInfo = new List();
it could be more efficient to initialize the list after GetBlocks() using this:
List blockInfo = new List(blocks.Count());
