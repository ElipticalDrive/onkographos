# The RACE II Engine for Real-Time Volume Rendering

Harvey Ray and Deborah Silver y

### Abstract

In this paper, we present the RACE II Engine, which uses a hybrid volume rendering methodology that combines algorithmic and hardware acceleration to maximize ray casting performance relative the total amount of volume memory throughput contained in the system. The challenge for future volume rendering accelerators will be the ability to process higher resolution datasets at over 10Hz without utilizing large-scale, and therefore, expensive designs. The limiting performance factor for large datasets will be the throughput between the volume memory subsystem and computational units. Unfortunately, the throughput between memory devices and computational units does not scale with Moore's law. As a result, memory efficient solutions are needed that maximize the input-output relationship between volume memory throughput and frame rate. The RACE II design utilizes this approach and achieves an input-output relationship of up to 4 larger than many solutions proposed in literature. As a result, this architecture is well suited for meeting the challenges of next generation datasets.

## 1 Introduction

Volume rendering has become an integral part of several disciplines such as medical imaging and numerical simulations which produce large 3D datasets. For the past several years, researchers have developed efficient algorithms and custom-hardware to achieve realtime performance. The fastest software-based solutions use the shear-warp algorithm [2] that allows for up to 10Hz for 2563 datasets. Other solutions use texture mapping hardware found on graphics workstations to achieve similar performance [1]. The VolumePro [9] accelerator card has been commercially available from RTVIZ for nearly a year and delivers 30Hz rendering performance for 2563 datasets.

As illustrated by VolumePro, dedicated hardware can outperform software-based solutions which currently require expensive platforms and high-performance texture-mapping engines. Furthermore, VolumePro requires the least amount of memory bandwidth. Software based solutions tend to require a hardware platform with much more memory bandwidth and computational throughput (measured in instructions per second) when compared to dedicated rendering hardware. Note that the computation of one sample can require over 50 CPU instructions for high-quality images. Other custom accelerators such as VIZARD II [5] and the VG-Engine [13] are expected to deliver interactive performance with lower computational throughput than VolumePro but they require more memory throughput. Also, average performance is less than 30Hz for 2563-16bit datasets. It is not clear if any of the current solutions will meet the demands of next generation datasets without utilizing large designs. The culprit is the required throughput between the computational units and the memory devices.

Moore's law state that semiconductor density doubles every two years. A corollary to Moore's law is that computational throughput doubles every 18 months due to the simultaneous increase in semiconductor density and clock speeds. Unfortunately, Moore's law

only applies to on-chip computational and memory throughput. It does not apply to chip-to-chip throughput which will be the limiting factor for volume rendering performance for large datasets. By doubling the resolution of a dataset in each dimension, we can expect total throughput between memory devices and computational units to increase eightfold. If Moore's law did apply to chip-tochip throughput, it would take approximately 6 years to handle a doubling of the dataset resolution unless we resort to large scale designs. For small-scale volume rendering accelerators, it would take at least 6 years to maintain todays performance for a doubling of the dataset resolution. The volume memory throughput must be minimized to enable us to render increasingly large datasets.

The goal of our work is to reduce the chip-to-chip throughput requirements to the volume memory by utilizing a thrashless and fully pipelined ray casting algorithm for parallel [3] and perspective [12, 10] projections. This architecture, called the RACE engine, supports conventional software-based acceleration techniques such as space-leaping and early-ray termination for unprecedented performance relative to volume memory throughput. This is a fundamental step for small-scale, high-performance volume rendering architectures.

# 2 Performance Metric

In [11], a metric was introduced which allows us to compare different hardware designs. The metric attempts to quantify how efficiently data is being accessed and processed. The peak rate at which the entire dataset can be read from the memory system is called the dataset access rate or DAR. For example, a state-of-the-art Pentium III class machine uses 64-bit DIMMS operating at 133MHz to store the dataset. This yields a DAR of 32Hz for a 2563 - 16 bit dataset. The average volume rendering performance is given by f rame second . A Pentium III class machine would deliver less than 5Hz on average except for extremely sparse datasets. To get an idea of how well an architecture is using the memory system, we divide the frame rate by the DAR rate which yields the memory efficiency. For the Pentium III, this would be 5Hz by 32Hz which equals 0:15. VolumePro, on the other hand, has a DAR of 32Hz and delivers 30Hz performance. Its memory efficiency is 0:94 for any dataset. Therefore, we estimate that a single VolumePro board will outperform as many as 5 Pentium III class systems.

Based on published performance, the memory efficiency for the VIZARD II [5] engine is (0:125 0:2) and for the VG-Engine [13] (0:125 1:5). These solutions aggressively utilize algorithmic optimizations especially [13]. Unfortunately, overall acceleration is compromised because their underlying algorithm thrashes the volume memory system. As a result, good performance is primarily achieved for iso-surface like classifications and when using small gradient kernels. A survey of the volume rendering accelerators [11] reveals that no volume rendering solution presented in literature is able to consistently outperform its DAR. The above statement is especially true for semi-transparent datasets. This dictates that these architectures will require a minimum of 8 GByte second of volume memory throughput to render a 5123 - 16 bit dataset at 30Hz and at least 64 GByte second of volume memory throughput to render a 10243 -16 bit dataset at 30Hz. ## 3 Block processing

Volume rendering consists of the following steps: reconstruction, classification, shading, and composition. Reconstruction is the bottleneck because typical interpolation and gradient kernels require access to as many as 32 voxel per filtered sample. To match the DAR, the hardware must not refetch voxels. Since DRAM memory devices are most likely to be used today, voxels must be accessed in burst-mode or page-mode. This places two constraints on the volume rendering algorithm. (1) voxels should be accessed in a regular order and (2) voxels should be accessed in sets if burst-mode is to be used. Note that newer DRAM devices can sustain full bandwidth random reads within a memory page; however, we must take care to hide the latency of opening and closing memory pages. Because of the first criteria, voxels can be buffered in a deterministic manner completely eliminating refetch to the large volume memory. Also, voxels can be prefetched allowing continuous operation of the DRAM memory. The combination of the first and second conditions allows us to fetch the entire dataset at the peak rate provided by the DRAM memory devices (similar to [9]).

Figure 1 graphically illustrates our hybrid ray casting algorithm (first proposed in [10]). The dataset is subdivided into equally sized voxel-blocks. These blocks can be processed in either back-to-front (BTF) or front-to-back (FTB) order, however, FTB ordering can support occlusion based acceleration techniques. In hardware, the FTB generator translates into a simple x-, y-, and z-counter. The six possible counting directions are handled by permutating and/or inverting the coordinates [2]. Perspective projections require an additional translation per coordinate [10].

The set of pixels in image-space affected by the voxel-block is called the footprint. The footprint is related to the size of the voxelblock and viewing parameters. Since the viewing parameters are arbitrary, the average number of pixels affected per block can be estimated using three special viewing angles. These are an orthogonalview, a side-view, and a diagonal-view. An orthogonal-view of a voxel-block will yield a footprint containing b 2 pixels where the b is the number of voxels on each side of the voxel-block. For a side-view, the footprint contains 2b 2 pixels. Lastly, a diagonal-view maximally reveals three faces of a voxel-block, therefore, its footprint contains 3b 2 pixels. A voxel-block has 6-faces (orthogonalviews), 12-sides (side-views), and 8-corners (diagonal-views). By taking a weighted average of these cases, we can get an estimate for the number of pixels inside the footprint of a voxel-block for uniform resampling from any view angle. This result is 54 26 b 2 .

As the algorithm proceeds from FTB, each voxel-block is mapped into image-space using standard graphics techniques (Figure 1B and C). Each pixel in the footprint is essentially a ray in the conventional scanline ray-casting algorithm. These rays (or pixels) are read from a special frame buffer to ascertain the ray's current position in object space, accumulated color, opacity, and increment vector (Figure 1A). A primary benefit of rendering the dataset in a predictable order is that the next voxel-block can be prefetched into a second buffer while rays intersecting the previous block are rendered.

Each ray-segment is rendered and advanced until it exits the voxel-block (Figure 1D) and then its state is written back into the frame buffer. Each pixel inside the frame buffer tracks necessary rendering information for a single ray. This effectively doubles the amount of per pixel information compared to standard accelerators; however, this is minor compared to the volume memory. In practice, this design uses up to 16 bytes per pixel. Each pixel is read and written once per voxel-block, so approximately 108 26 b 2 pixel operations will be needed per voxel-block.

Since voxel-blocks do not touch or overlap, there is a space between adjacent voxel-blocks (not shown in the figure) of 1 unit in each direction. A ray can potentially start in this intra-block spacing. This may cause a problem for perspective projections because these rays depend on voxels from multiple voxel-blocks that have not been loaded and these rays will fan-out in opposite directions. As a result, we re-fetch one voxel-block per row of voxel-blocks and one row of voxel-blocks per slice for perspective projections. Therefore, two slices of voxel-blocks are refetched from the entire dataset during perspective projections. If the dataset resolution, n, is much larger than the voxel-block resolution, b, this penalty is small. For example, a 5123 dataset with 163 voxel-blocks requires that we refetch 6:25% of the dataset.

#### 4 Algorithmic Optimizations at a Block Granularity

In the volume rendering solutions mentioned previously (see also [11]), there is an anomaly because the fastest solution requires the least amount of memory bandwidth (i.e., VolumePro); furthermore, it is the only solution that does not utilize algorithmic optimizations. Unfortunately, current solutions that support algorithmic optimizations provide a much lower reconstruction rate due to irregular traversal of the dataset and/or the lack of a dedicated rendering pipeline. These designs sacrifice overall acceleration by focusing only one aspect of acceleration. The hybrid projection guided ray casting algorithm addresses this problem.

#### 4.1 Transparency-based speedups

Space-leaping (skipping empty regions of the volume) is a powerful technique that allows for significant speedups by greatly reducing the percentage of voxels that are accessed per frame. Although this is a dataset dependent speedup, researchers have reported huge gains using these techniques [4, 14] and they are an integral part of software based rendering solutions. One drawback of space-leaping is that the dataset often requires a lengthy preprocessing overhead before the algorithm can be applied.

In prior work [10], we proposed a method that takes advantage of the FTB block processing to streamline the computation using an empty space data-structure called the Transparent Voxel-Block (TVB) table. Since an entire voxel-block is fetched from the memory system at once, it can be tagged transparent or non-transparent once each voxel is compared to a user-defined threshold.

If a block is flagged transparent, a single bit is stored into the corresponding position in the TVB table. This mapping from voxelblock space into the 3D TVB table is accomplished by examining the most significant bits of the x, y, and z voxel-block coordinates. After the first frame is rendered by accessing each voxel once, subsequent frames (of the same dataset) may utilize spaceleaping. This improved algorithm allows the FTB counter to potentially skip voxel-blocks. Since transparency is computed for an entire voxel-block, speedups will improve as the size of the dataset increases relative to the size of the voxel-block.

As mentioned earlier, there is a small intra-block spacing between each voxel-block that must be accounted for during rendering. Samples along a ray that lie within or near an intra-block space may require voxels from several adjacent voxel-blocks. As a result, a 3-3-3 window inside of the TVB table must be checked. If the

#### 4.2 Occlusion-based speedups

Early-ray termination is an occlusion based optimization technique that reduces the number of samples that contribute to the final image [4]. If a sample along a ray contributes a negligible change to the accumulated pixel color, it can be skipped. If each sample within a voxel's region of influence is occluded, then this particular voxel does not need to be accessed from the memory system.

What is needed is a method that allows us to quickly determine when we can skip a voxel-block due to occlusion. Using a brute force approach, the opacity of each ray (or pixel) from the 2D footprint can be compared to a user-defined early-ray termination threshold. If the ray's opacity is greater than the threshold, then we do not need to access the voxel-block from the volume memory. Using the earlier estimate of footprint size, the average number of compare and pixel-read operations is 54 26 b 2 per voxel-block. Assuming 8 3 voxel-blocks, then approximately 133 compares would be necessary to determine if a block is occluded versus only 27 for space-leaping. Unfortunately, if the block is skipped we would have consumed pixel memory throughput to examine the opacity of each of the rays residing inside of the footprint. What is really needed is a method that consumes no additional voxel-throughput or pixel-throughput. To achieve this, we need a separate data structure that allows us to determine occlusion in parallel with voxeland pixel-memory accesses.

The FTB counter generates a 3D coordinate of each voxel-block. The coordinates are then used to prefetch the voxel-block and to compute the image-space footprint. Once the image-space footprint is known, the pixels are transferred over a pixel-bus. Obviously, these pixels can not be rendered until the voxel-block has completely been loaded from memory. Once the voxel-block has been prefetched, the pixels contained within the footprint of the voxel-block are processed and then written back into the frame buffer over the pixel-bus. Simultaneously, the FTB counter and scan-conversion hardware advances to the next block. As a result, we can determine if the footprint is occluded before we process the voxel-block or if it has become occluded after the voxel-block was processed. In the first case, the voxel-block has already been pre-fetched from memory, therefore, it is too late to conserve voxel memory throughput. Consequently, occlusion is determined at the point rays exit a voxel-block by simply comparing the opacity of each ray as they are written into the frame buffer.

To take advantage of this, voxel-blocks whose footprint has become occluded can be flagged in an Opaque Voxel-Block (OVB) table (see [6] for a similar approach). The OVB table is a 2D data-structure and is shown in Figure 2. If a voxel-block's entire footprint is flagged opaque by the process above, the OVB table is marked. The mapping of 3D voxel-block position into the 2D OVB table is simply the inverse of the shear operation that normally occurs during the shear-warp algorithm. Conceptually, the OVB table is a binary base-plane. We know that from the shear-warp algorithm that shears are simple incremental operations [2]. Following [2], the location of the base-plane is determined by the face of the dataset most perpendicular to the viewing rays. Fortunately, this ordering is consistent with our FTB counter.

Before the FTB counter generates a voxel-block prefetch, it checks the OVB table to determine if the block can be skipped without consuming pixel-throughput and potentially voxel throughput. In practice, the spacing of the voxel blocks and the size of the reconstruction filters requires that we check a 3 - 3 window in the OVB table to ensure that the voxel-block is both occluded and that none of its voxels contribute to a reconstruction kernel of a visible sample. Again, this assumes that the reconstruction kernels are smaller than the size of a voxel-block. As a result, only 9 comparisons are necessary for a parallel projection to determine occlusion versus O(b 2 ) in a brute-force approach.

The above method is problematic because shears in general can be fractional (0:0 1:0). A fractional shear will prevent a voxelblock from mapping precisely onto a base-plane super-pixel. In fact, a voxel-block may partially overlap up to 4 base-plane superpixels. To handle fractional shears, the resolution of the baseplane image can be doubled in each direction such that the voxelblock can completely occluded these smaller quad-pixels (see Figure 2). For perspective projections, scaling occurs when mapping from object-space onto the base-plane; therefore, an even higherresolution base-plane and a variable number of comparisons are needed to determine occlusion. Therefore, in the present design, this acceleration technique is not used for perspective projections.

Using this result, 16 comparisons are required to determine occlusion. For a 2563 size dataset and 8 3 voxel-block, the OVB datastructure consumes only 128-128 or 16K bits. The TVB and OVB data structures combined will typically require less than 10KByte of storage. In addition, they can yield over a threefold reduction in the number of voxels accessed per frame justifying their cost. The number of binary comparisons necessary for the FTB counter to skip a voxel-block scales as O(1). As a result, these acceleration tables are suitable for a low-cost hardware solution.

### 5 Resample and Composite Engine (RACE) II

The architecture designed for the projection guided ray casting algorithm discussed above is shown in Figure 3. This is called the RACE II engine. It contains 4 components: rendering units, a controller, volume memory, and pixel memory. The rendering units implement the image-order ray-casting algorithm, voxel-buffering, and clipping. The control unit provides synchronization for each processor and generates memory addresses for all transactions on both memory buses. The volume memory stores the data volume. The pixel memory (frame buffer) is used to track color, opacity, and location of each ray during the ray casting process. Before rendering starts, the frame buffer is initialized with the entry point of each ray into the dataset and the increment vector (i.e., for perspective projections). Conventional rasterization techniques can be used to initialize the frame-buffer [10]. Since these operations occur in O(n2 ) computational time, they do not limit the performance of the architecture.

#### 5.1 RACE Processors

The entire frame-buffer and volume memory are divided among each processor using low-order interleaving. Each processor receives a stream of pixels (rays) from the frame-buffer and queues them in an Input Queue (See Figure 4). Each ray entering the Input Queue is stamped with a tag (pixel-tile address) and offset (relative position inside of the pixel-tile). Each 2D footprint must be appropriately delimited so that the processor can match clippingregions to rays (pixels). A clipping-region is a bounding box in object-space that corresponds to a valid interpolation and central difference region based on the data inside the internal voxel-buffers. Unlike voxel-blocks, there is no spacing between adjacent clippingregions. Each voxel-block has a unique clip-region based on the current FTB ordering.



Figure 3: RACE II architecture

Each ray entering the processor is optionally stamped with two boolean flags: start-of-footprint (SOF) and end-of-footprint (EOF). In addition, a space-leap (SL) flag is used to determine if the ray can be advanced through a transparent block. These status flags are generated by the RACE controller. rays take one of two paths. 1) accept path (path #1, for rendering) or the algorithmically skipped/clipped path (path #2, reject). Path #1 processes ray segments that are not algorithmically eliminated and whose current location lies within the bounding box defined by the active clipping-region. Each of these rays are loaded into the Accept Queue.

Along path #1, all rays are rendered using the conventional raycasting algorithm until they exit the clipping-region. Once they exit, rays are written to the current cache-line or the next sequential cache-line. No cache misses occur along this path, because, a cache-line is reserved before the ray enters the Accept Queue and a cache-line is not discarded until all rays from the cache-line (i.e., pixel-tile) has been processed.



Figure 2: Determining occlusion on-the-fly using object-space shearing.

Rays exiting the Accept Queue are interleaved into the inputs of the internal ray-casting pipeline using the Ray Interleave Unit. This guarantees that two adjacent samples along a single ray are delayed by d clock cycles, where the delay d matches the number of pipeline stages in the composition hardware (if not, a data-hazard would arise preventing full-speed rendering performance [13]). As a result, samples from different rays enter the pipeline on consecutive clock cycles.

Path #2 handles two cases: the segment of the ray can be algorithmically eliminated (skipped/occluded) or the ray's current xyz location is outside of the active clipping-region. Along Path #2, the Clip-and-Add Unit advances the ray's position through the transparent voxel-block if the SL flag is set.

After exiting the clip-and-add circuitry, rays are stored inside the pixel cache. If a cache-hit occurs on the current cache-line, the ray is written at the appropriate address in the cache line. The cache is indexed by three pointers: one for Path #1 (render), one for Path #2 (reject), and a read pointer for the Output Queue. Each pointer increments sequentially through the cache in a wrap-around fashion. Because the cache is indexed, only one tag comparison is necessary regardless of the size of the cache. No comparison is necessary for the read-port of the cache. The read port cycles through each cache-line waiting until the entire cache-line is dirty before advancing. This guarantees that pixel-tiles are retired in a first-in, first-out manner thereby synchronizing processors with the RACE controller which generates a single pixel-memory write address.

If the Output Queue is not empty, a flag is sent to the controller to indicate a write pending status. If the queue is full, a critical write-pending status flag is sent to the controller. Once the controller receives at least a write pending status from each processor and the pixel-bus is inactive, it sends a write acknowledge signal to each processor. In turn, queues (or FIFO) from multiple processors simultaneously respond placing pixels serially onto the pixel-bus.

In the RACE architecture, voxels are streamed into each processor at the peak rate of the memory system. Each processor has a dedicated voxel bus; however, the bus responds to a single memory address. All processors distribute voxels to their left neighbors in parallel and in a circular fashion. A few clock cycles after the voxel-block is accessed from memory, each processor has its own private copy of the voxel-block. Unlike [8], this alleviates the need for a specialized memory system. The fixed stream of voxels is also used to compute a central difference gradient for each voxel. As a result, the gradient and interpolation block buffers operate in parallel on the same address provided by the rendering pipeline. Internally these buffers are eight-way interleaved to support per clock interpolation and gradient computation.

## 6 Performance

The RACE II architecture was simulated in software using a C++ clock cycle simulator. The simulation conservatively assumes that the pixel memory bus operates at the same rate as the voxel memory bus and that the entire dataset lies within the view volume. In practice, embedded DRAM technology can be used for the relatively small pixel memory to enhance performance. Voxel-blocks sizes were varied between 64(43 ) 32768(323 ) voxels. Pixel-tiles were sized to accommodate 16 pixels per processor. For example, if 4 processors are simulated a pixel-tile containing 64 pixels is used. This allows RACE to hide the memory latency when accessing the pixel-memory. Each processor was configured as follows: the Input Queue can store up to 128 rays, the Accept Queue can store up to 16 rays, the Pixel Cache can store 128 rays, and the Output Queue can store up to 128 rays. The auxiliary on-chip storage requires less than 10KByte of memory. Voxel buffers are doubled buffered and require either 256, 2K, 16K, or 64K bytes of memory based on the block resolution b. The internal slice-buffers dominate on-chip storage and require 448KBytes for a 2563 dataset. In [7], the size of the slice buffers were reduced by a factor of 8 by rendering the dataset in eight sections with less than a 8% performance penalty due to a small amount of voxel-refetch. A similar method can be used here. Furthermore, memory density scales with Moore's law. Therefore, we assume that on-chip slice buffer will not undermine the performance or feasibility of the RACE architecture.

The RACE controller requires less than 16KByte of on-chip storage for the OVB table, TVB table, and internal buffers. An 8 entry pixel-address buffer is used to record the pixel-tiles that are being rendered by the RACE processors. This prevents us from reading stale data from the frame-buffer. We simulated the performance of the RACE II architecture for six different datasets. Each dataset was rendered using a plausible classification mapping. For example, CT datasets were rendered with a mapping of soft tissue to a semi-transparent value and bone to an opaque value. # 7 Future Work

The RACE II architecture can be extended to use floating point precision frame-buffers and computational units to rival the imagequality of software based ray casting solutions. Frame-to-frame coherence [3] may allow us to double the memory efficiency by using temporal coherence. We are currently working on an algorithm to allow the RACE II architecture to intermix traditional polygon defined scenes with a volume dataset. These are exciting areas of future research.

## 8 Conclusion

In this paper, we presented a hybrid rendering methodology designed to lower throughput between volume memory devices and computational units. The architecture achieves superior performance for a given level of voxel throughput. This general purpose visualization architecture will directly support up to 20Hz performance, 7Hz for stereoscopic viewing, real-time classification, and will allow the visualization of rapidly changing datasets using only 400MByte second of voxel memory bandwidth for 2563 - 16 bit datasets. Consequently, we expect RACE II to offer real-time performance without requiring dedicated volume memory storage for current generation datasets. Furthermore, next generation datasets can be rendered by RACE II using similar volume memory bandwidth that many current solutions use to render 2563 dataset.

Based on simulated results, the RACE architecture can significantly improve performance with a faster pixel interface when small voxel-blocks are utilized. We believe the trade-off between low voxel-throughput and higher pixel-throughput is intuitive since frame-buffers are much smaller and can potentially be cached onchip. The RACE II design achieves high performance by accessing each voxel in a deterministic manner, voxel-buffering, minimizing voxel refetch, and applying algorithmic optimizations at a block granularity. It is a first step toward optimizing the input-output relationship between frame-rate and volume memory throughput.
