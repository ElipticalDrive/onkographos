Block processing
Volume rendering consists of the following steps: reconstruction,
classification, shading, and composition. Reconstruction is the bottleneck because typical interpolation and gradient kernels require
access to as many as
voxel per filtered sample. To match the
DAR, the hardware must not refetch voxels. Since DRAM memory
devices are most likely to be used today, voxels must be accessed in
burst-mode or page-mode. This places two constraints on the volume rendering algorithm. (1) voxels should be accessed in a regular
order and (2) voxels should be accessed in sets if burst-mode is to
be used. Note that newer DRAM devices can sustain full bandwidth random reads within a memory page; however, we must take
care to hide the latency of opening and closing memory pages. Because of the first criteria, voxels can be buffered in a deterministic
manner completely eliminating refetch to the large volume memory. Also, voxels can be prefetched allowing continuous operation
of the DRAM memory. The combination of the first and second
conditions allows us to fetch the entire dataset at the peak rate provided by the DRAM memory devices (similar to [9]).
Figure 1 graphically illustrates our hybrid ray casting algorithm
(first proposed in [10]). The dataset is subdivided into equally sized
voxel-blocks. These blocks can be processed in either back-to-front
(BTF) or front-to-back (FTB) order, however, FTB ordering can
support occlusion based acceleration techniques. In hardware, the
FTB generator translates into a simple x-, y-, and z-counter. The
six possible counting directions are handled by permutating and/or
inverting the coordinates [2]. Perspective projections require an
additional translation per coordinate [10].
The set of pixels in image-space affected by the voxel-block is
called the footprint. The footprint is related to the size of the voxelblock and viewing parameters. Since the viewing parameters are arbitrary, the average number of pixels affected per block can be estimated using three special viewing angles. These are an orthogonalview, a side-view, and a diagonal-view. An orthogonal-view of a
voxel-block will yield a footprint containing b2 pixels where the
b is the number of voxels on each side of the voxel-block. For a
side-view, the footprint contains b2 pixels. Lastly, a diagonal-view
maximally reveals three faces of a voxel-block, therefore, its footprint contains b2 pixels. A voxel-block has 6-faces (orthogonalviews), 12-sides (side-views), and 8-corners (diagonal-views). By
taking a weighted average of these cases, we can get an estimate
for the number of pixels inside the footprint of a voxel-block for
2

26 b .

mapped into image-space using standard graphics techniques (Figure 1B and C). Each pixel in the footprint is essentially a ray in the

In the volume rendering solutions mentioned previously (see also
[11]), there is an anomaly because the fastest solution requires the
least amount of memory bandwidth (i.e., VolumePro); furthermore,
it is the only solution that does not utilize algorithmic optimizations. Unfortunately, current solutions that support algorithmic optimizations provide a much lower reconstruction rate due to irregular traversal of the dataset and/or the lack of a dedicated rendering
pipeline. These designs sacrifice overall acceleration by focusing
only one aspect of acceleration. The hybrid projection guided ray
casting algorithm addresses this problem.
4.1 Transparency-based speedups
Space-leaping (skipping empty regions of the volume) is a powerful
technique that allows for significant speedups by greatly reducing
the percentage of voxels that are accessed per frame. Although
this is a dataset dependent speedup, researchers have reported huge
gains using these techniques [4, 14] and they are an integral part of
software based rendering solutions. One drawback of space-leaping
is that the dataset often requires a lengthy preprocessing overhead
before the algorithm can be applied.
In prior work [10], we proposed a method that takes advantage
of the FTB block processing to streamline the computation using
an empty space data-structure called the Transparent Voxel-Block
(TVB) table. Since an entire voxel-block is fetched from the memory system at once, it can be tagged transparent or non-transparent
once each voxel is compared to a user-defined threshold.
If a block is flagged transparent, a single bit is stored into the corresponding position in the TVB table. This mapping from voxelblock space into the D TVB table is accomplished by examining the most significant bits of the x, y , and z voxel-block coordinates. After the first frame is rendered by accessing each voxel
once, subsequent frames (of the same dataset) may utilize spaceleaping. This improved algorithm allows the FTB counter to potentially skip voxel-blocks. Since transparency is computed for an
entire voxel-block, speedups will improve as the size of the dataset
increases relative to the size of the voxel-block.

4.2 Occlusion-based speedups
Early-ray termination is an occlusion based optimization technique
that reduces the number of samples that contribute to the final image
[4]. If a sample along a ray contributes a negligible change to the
accumulated pixel color, it can be skipped. If each sample within
a voxel’s region of influence is occluded, then this particular voxel
does not need to be accessed from the memory system.
What is needed is a method that allows us to quickly determine
when we can skip a voxel-block due to occlusion. Using a brute
force approach, the opacity of each ray (or pixel) from the D
footprint can be compared to a user-defined early-ray termination
threshold. If the ray’s opacity is greater than the threshold, then
we do not need to access the voxel-block from the volume memory.

or the algorithmically skipped/clipped path (path #2, reject). Path
#1 processes ray segments that are not algorithmically eliminated

Along path #1, all rays are rendered using the conventional raycasting algorithm until they exit the clipping-region. Once they
exit, rays are written to the current cache-line or the next sequential cache-line. No cache misses occur along this path, because, a
cache-line is reserved before the ray enters the Accept Queue and
a cache-line is not discarded until all rays from the cache-line (i.e.,
pixel-tile) has been processed.
The entire frame-buffer and volume memory are divided among
each processor using low-order interleaving. Each processor receives a stream of pixels (rays) from the frame-buffer and queues
them in an Input Queue (See Figure 4). Each ray entering the Input

As a result, the gradient and interpolation block buffers operate in
parallel on the same address provided by the rendering pipeline. Internally these buffers are eight-way interleaved to support per clock
interpolation and gradient computation.
Rays exiting the Accept Queue are interleaved into the inputs
of the internal ray-casting pipeline using the Ray Interleave Unit.
This guarantees that two adjacent samples along a single ray are
delayed by d clock cycles, where the delay d matches the number
of pipeline stages in the composition hardware (if not, a data-hazard
would arise preventing full-speed rendering performance [13]). As
a result, samples from different rays enter the pipeline on consecutive clock cycles.
Path #2 handles two cases: the segment of the ray can be algorithmically eliminated (skipped/occluded) or the ray’s current xyz
location is outside of the active clipping-region. Along Path #2, the
Clip-and-Add Unit advances the ray’s position through the transparent voxel-block if the SL flag is set.
After exiting the clip-and-add circuitry, rays are stored inside the
pixel cache. If a cache-hit occurs on the current cache-line, the ray
is written at the appropriate address in the cache line. The cache is
indexed by three pointers: one for Path #1 (render), one for Path #2
(reject), and a read pointer for the Output Queue. Each pointer increments sequentially through the cache in a wrap-around fashion.
Because the cache is indexed, only one tag comparison is necessary
regardless of the size of the cache. No comparison is necessary
for the read-port of the cache. The read port cycles through each
cache-line waiting until the entire cache-line is dirty before advancing. This guarantees that pixel-tiles are retired in a first-in, first-out
manner thereby synchronizing processors with the RACE controller
which generates a single pixel-memory write address.
If the Output Queue is not empty, a flag is sent to the controller
to indicate a write pending status. If the queue is full, a critical
write-pending status flag is sent to the controller. Once the controller receives at least a write pending status from each processor
and the pixel-bus is inactive, it sends a write acknowledge signal to
each processor. In turn, queues (or FIFO) from multiple processors
simultaneously respond placing pixels serially onto the pixel-bus.
In the RACE architecture, voxels are streamed into each processor at the peak rate of the memory system. Each processor has a
dedicated voxel bus; however, the bus responds to a single memory address. All processors distribute voxels to their left neighbors
in parallel and in a circular fashion. A few clock cycles after the
voxel-block is accessed from memory, each processor has its own
private copy of the voxel-block. Unlike [8], this alleviates the need
for a specialized memory system. The fixed stream of voxels is
also used to compute a central difference gradient for each voxel.

Future Work
The RACE II architecture can be extended to use floating point
precision frame-buffers and computational units to rival the imagequality of software based ray casting solutions. Frame-to-frame
coherence [3] may allow us to double the memory efficiency by using temporal coherence. We are currently working on an algorithm
to allow the RACE II architecture to intermix traditional polygon
defined scenes with a volume dataset. These are exciting areas of
future research.

Based on simulated results, the RACE architecture can significantly improve performance with a faster pixel interface when
small voxel-blocks are utilized. We believe the trade-off between
low voxel-throughput and higher pixel-throughput is intuitive since
frame-buffers are much smaller and can potentially be cached onchip.
The RACE II design achieves high performance by accessing
each voxel in a deterministic manner, voxel-buffering, minimizing
voxel refetch, and applying algorithmic optimizations at a block
granularity. It is a first step toward optimizing the input-output relationship between frame-rate and volume memory throughput. We
believe that hybrid accelerators will emerge as a dominant method
