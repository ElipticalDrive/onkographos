fix(3d-tiles): render tile splat content at the anchor
…
95923b4

```
Three root causes, found by measuring each transform live:

1. Group recenter must cancel the plugin's sceneMatrix exactly. The
   GaussianSplatPlugin positions every tile SplatMesh with
   sceneMatrix = rootTransform x upRotationMatrix, so the tiles group is
   now recentered with its exact inverse (upRot^-1 x rootTransform^-1) --
   verified recenter x sceneMatrix = identity. The earlier bounding-sphere
   or transform-only recenters left the content km off the anchor.

2. The traversal camera must reuse the scene camera's projection matrix
   verbatim. CameraSync builds a custom perspective (centerOffset,
   MapLibre near/far mapping), so a standard PerspectiveCamera recomputed
   from fov/aspect/near/far produces a mismatched frustum that culled
   every tile (loaded stayed 0). With the copied projection + identity
   view the frustum equals the render transform and tiles stream
   naturally with LOD refinement on zoom.

3. The plugin's CameraRelativeSparkRenderer re-bases splats around
   camera.matrixWorld, which MapScene overwrites to identity every frame,
   pinning splats to the screen. It is hidden and a plain shared
   SparkRenderer (the exact mechanism VLayerSplat uses) renders the tile
   SplatMeshes through the world-group transform instead.

Also defaults rotation to [90, 180, 0] (same frame convention as
VLayerSplat) and pins the demo to altitude 0 so the tileset's ~2250 m
ellipsoidal height doesn't float the content past the far plane on the
flat basemap (no DEM covers the bonsai anchor).

Verified in-browser: tiles stream naturally (39 loaded at z18.5, 47 at
z20), splat content renders grounded at the anchor, LOD refines on zoom.

Closes #142
```

fix(three): render splats in a metre scene frame
…
3831222
```
Splat content was invisible on both the splat and 3D-tiles examples, and
the 3D-tiles layer detached from the ground on zoom.

Three independent root causes:

1. Duplicate three.js instances. Spark registers its `splatDefines` shader
   chunk on THREE.ShaderChunk of *its* three instance. The WebGLRenderer
   resolved a second instance, so every splat program failed to compile
   with "Can not resolve #include <splatDefines>" while plain three meshes
   still drew fine. Dedupe three, spark and the 3d-tiles stack in the app's
   vite resolve config.

2. Half-float precision. Spark packs splat centres into half-float
   textures. The shared scene worked in mercator-fraction units, where a
   30 m object spans ~3e-7 units at an offset of ~0.5 — far below
   half-float resolution, so every centre quantised to the same point.
   The scene now uses a local ENU metre frame anchored at the map centre,
   with the mercator conversion folded into the draw projection.

3. LOD traversal read a fused mercator projection. 3D-tiles
   screen-space-error maths needs a plain perspective, so the entry now
   exposes a dedicated lodCamera in the same metre space. MapLibre v6's
   `transform.fov` is already in degrees (`fovInRadians` is separate);
   converting it again produced a ~2578 deg FOV that starved LOD
   selection — only 2 tiles ever loaded, now 228.

Spark also needs continuous frames for its async sort/readback, so the
custom layer keeps the map painting while a splat renderer is attached.
```

Splat rendering: three root causes found and fixed (3831222)
Splats were invisible on both the splat and 3D-tiles examples, and the 3D-tiles layer detached from the ground on zoom. These turned out to be three independent bugs stacked on top of each other — every matrix/camera theory chased earlier was downstream of #1.
1. Duplicate three.js instances → splat shader never compiled
Spark registers its splatDefines shader chunk onto THREE.ShaderChunk of its three instance (lazily, in getShaders()). The WebGLRenderer was resolving a second three instance, so every splat program failed to link:
```
THREE.WARNING: Multiple instances of Three.js being imported.
THREE.WebGLProgram: Can not resolve #include <splatDefines>
```
Plain three meshes still drew fine (verified with a debug box + points), which is why this masqueraded as a transform bug for so long.
Fix: add three, @sparkjsdev/spark and the 3d-tiles stack to vite.resolve.dedupe — the same pattern the repo already uses for deck.gl/luma.gl.

```
  ignores centre elevation, so on terrain the camera sat underground
  (373 m for a 1950 m glacier target) and the whole scene was culled.

- MapLibre's depth buffer uses its own projection's depth convention,
  which the standard perspective matrix does not share, so every
  fragment failed the depth test. The custom layer now clears depth
```
