Demo of multiscale rendering of zebrahub volumes in blender
🤖 -----
Adds an experimental Blender target that reads the chunks needed for a view from a multiscale source and publishes them as native volume grids in memory. Geometry nodes convert carrier-mesh float attributes into native grids for the viewport, EEVEE and Cycles; no VDB conversion is required.
The remote OME-Zarr example defaults to Zebrahub ZSNS001 and provides resolution overlays, level colors, brightness/absorption controls, and an orbit/close-up demo path. Perspective chunk projections are clipped at the near plane so chunks behind a camera inside the volume do not outrank visible chunks.
Launch the demo
With this branch and its ome-zarr dependencies importable in Blender 5.2+'s Python:
```
blender --python examples/blender_ome_zarr.py -- --time 400
```
Use N sidebar → Lodstone → Play demo path for the scripted tour, or orbit/zoom manually. Play + render finishes the tour with a prepared render. Render with finest data prepares the scene camera at a separate memory budget; plain F12 renders what is already loaded. The budget can limit the selected resolution.
Time and channel selection now follow NGFF axis names, including 4-D (t,z,y,x) and (c,z,y,x) sources, and reject out-of-range indices before replacing an existing controller.
Critical-review fixes
Render preparation invalidates pending/in-flight navigation plans and waits for its exact generation. Supersession/cancellation is an error rather than false success.
Timeouts, source/publication failures and render-invocation failure/cancellation restore the previous interactive camera policy and memory budget. Successful completion/cancellation preserves a custom interactive budget.
Timer callbacks retain stable identities for cancellation; controller startup is idempotent and closed controllers cannot restart.
Native verification checks actual rendered pixels and exits nonzero on failure. Regression tests exercise the real Blender timer registry and camera worker, including corrupting a grid to verify the check fails.
Local validation
Python suite: 203 passed, 2 optional skips (Blender runtime module and SceneX absent in the ordinary Python environment).
Blender runtime and adapter tests: 24 passed using Linux bpy 5.2.3 LTS.
Native-grid check: exact index order, anisotropic physical-center sampling and in-place update all have zero maximum absolute error; streaming reaches level 0; Cycles and EEVEE both produce nonconstant renders; no Lodstone volume objects remain after close; ok: true.
Whole-repository Ruff check/format, CI-equivalent Pyright with OME-Zarr dependencies, and wheel/sdist builds pass.
Blender CI verification
The pinned Linux/Python 3.13/bpy==5.2.3 job is enabled. Its first successful run executed 13 runtime tests and the native-grid CPU Cycles check (ok: true, exact grid/physical/update samples and a nonconstant render).
The runtime command uses uv run --extra test --with bpy==5.2.3 python -m pytest, ensuring pytest uses the interpreter with Blender installed. The temporary CI patch has been applied and removed.
Draft limits
This is a Lodstone Blender adapter, not a Microscopy Nodes UI integration. The earlier cached-VDB Microscopy Nodes prototype is separate.

```
Add an experimental Blender dense target. Each published level is copied
into an in-memory attribute on a carrier mesh, and a geometry-node graph
(Cube Grid Topology + Field to Grid) turns it into a native float grid.
The viewport, EEVEE and Cycles render it like any Blender volume; no VDB
or other file is written.

Chunk reads and planning stay on Lodstone's background threads; Blender
data changes run on the main thread through a timer-drained queue.
prepare_render() loads the render camera's view at a separate budget,
and render handlers only set flags.

Includes a remote OME-Zarr example (Zebrahub ZSNS001 by default) and a
headless Blender check of voxel order, physical placement, streaming and
rendering.
```

```
Corners behind a perspective camera were divided by a negative w, which
mirrors them through the screen center and gives them very negative NDC
depth. With a camera inside the data box (any close-up), chunks behind
the viewer outranked the chunks it was looking at, and the dense focus
window landed out of view.

Clip each chunk box against the OpenGL near plane (z + w >= 0) before
projecting: keep corners in front, add the edge crossings, and treat a
box entirely behind the plane as invisible. Orthographic views are
unchanged.
```
