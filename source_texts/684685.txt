Motivation
With the spvBindlessTextureNV capability, converting a DescriptorHandle<T> to a resource aborted the compiler with an internal error for every descriptor kind except textures and samplers:
```
error[E99997]: ... Slang::InternalError unexpected: Unsupported result type for CastDescriptorHandleToResource
```
slangc exited 255. Reported in #12185 (pdeayton-nv). Concretely, all of these aborted:
RWStructuredBuffer<float>.Handle / ConstantBuffer<T>.Handle / ByteAddressBuffer handles
RaytracingAccelerationStructure.Handle — even though the reporter expected acceleration structures to be convertible
The same shaders compile fine without the capability, because they take a descriptor-heap path instead. SPV_NV_bindless_texture defines integer conversions only for image and sampler types; buffers have no encoding under it, and acceleration structures have a valid conversion (OpConvertUToAccelerationStructureKHR) that was simply not wired up.
Proposed solution
The root cause was that under spvBindlessTextureNV the handle representation was capability-wide uint64, while the spvBindlessTextureNV arm of defaultGetDescriptorFromHandle forwarded every descriptor kind to __castDescriptorHandleToResource, whose SPIR-V emitter only knows how to encode images and samplers.
Following review (@csyonghe / @pdeayton-nv, "option a"), the representation of DescriptorHandle<T> is now kind-dependent rather than the unsupported kinds being diagnosed:
uint64 for the kinds SPV_NV_bindless_texture can convert — the texture/sampler family (textures, samplers including comparison samplers, combined texture-samplers, and texel buffers). These lower through __castDescriptorHandleToResource to the OpConvertUTo*NV opcodes.
uint2 for every other kind — buffers and acceleration structures. These reuse the existing dynamic-resource-heap path (identical to the plain spirv/glsl arm), so the original abort is fixed by construction: buffer handles compile via the heap path, and acceleration-structure handles keep their uint2 packing and lower via OpConvertUToAccelerationStructureKHR.
For buffer and acceleration-structure handles this matches the representation already used on the plain (no-capability) SPIR-V path, so those handles' layout no longer changes just because the capability is enabled. (Texture/sampler handles are uint2 on the plain path and uint64 under this capability — that is the encoding difference the extension requires.)
Because the width now depends on the kind, a global constant can be built at one width and read at the other, and that mismatch used to survive to module scope where it produced invalid SPIR-V. The four DescriptorHandle↔integer representation casts (and Select, which a ?: initializer can put between them) are therefore added to isInlinableGlobalInst, so such an initializer sinks into the function that uses the handle and the widths reconcile there.

Concepts and vocabulary
DescriptorHandle<T> representation — how a bindless handle is stored in SPIR-V. Under spvBindlessTextureNV it is kind-dependent: uint64 for the texture/sampler family, uint2 otherwise (and uint2 on the plain spirv/glsl path for all kinds).
isBindlessTextureNVEncodableResourceType — the single classifier for "is this a kind SPV_NV_bindless_texture can convert", i.e. the kinds that use the uint64 representation. slang-type-layout.cpp carries a mirrored AST-side predicate with the same kind set.
The four representation casts — Cast{UInt2,UInt64}ToDescriptorHandle and CastDescriptorHandleTo{UInt2,UInt64}. When the integer side matches the handle's representation they emit no instruction and the operand is forwarded, so the operand must already have the result's type; a runtime cross-width cast emits an OpBitcast instead.
isInlinableGlobalInst — the list in slang-ir-legalize-global-values.cpp of global instructions that may be cloned into a using function. An op in this list can appear in a global initializer even when it is only legal inside a block.
getDescriptorFromDynamicResourceHeap — the uint2-handle heap-lookup path, factored out of the old spirv/glsl arm so the spvBindlessTextureNV arm can reuse it for buffers/AS.
Process report
hlsl.meta.slang — kind-dependent producer. The old spvBindlessTextureNV arm was return __castDescriptorHandleToResource<T>(handleValue); for all kinds. It now routes the texture/sampler family to __castDescriptorHandleToResource and everything else to getDescriptorFromDynamicResourceHeap. Input-shape check: CastDescriptorHandleToResource is only valid for kinds the extension can encode; forwarding buffers to it was an over-broad producer emitting an input shape the consumer cannot represent, so narrowing it here is the right layer. A T.kind if/else is used rather than a static_assert switch because getDescriptorFromHandle<T> is type-checked as an un-specialized generic, where an eager static_assert(false) arm would fire even for textures. The lessThan/lessThanOrEquals split is required because a uint2 and a packed uint64 order differently (lexicographic lo-major vs numeric), so ordering must compare in each kind's native representation; equals needs no split since bit-equality is representation-independent.
Global-scope width mismatch (slang-ir-legalize-global-values.cpp). Both integer constructors are available for every kind, so user code can write a global whose initializer width differs from the kind's representation:
```
static const DescriptorHandle<SamplerState> kSampler = DescriptorHandle<SamplerState>(uint2(3, 4));
static const uint64_t kSamplerBits = (uint64_t)kSampler;
```
Because the representation casts emit nothing and forward their operand, that used to hand a %v2uint constant to uint64 arithmetic — spirv-val rejects it with "Expected arithmetic operands to have the same dimension as Result Type". The symmetric case, a uint64-initialized buffer handle reaching the descriptor heap, emitted OpCompositeExtract on a scalar, which asserts inside spirv-opt while constant folding. Bridging the widths needs an OpBitcast, which is not valid outside a block, so the fix is to stop the value surviving at module scope at all: the four casts and Select join BitCast in isInlinableGlobalInst, the chain is cloned into the using function, and ordinary folding reconciles the width there — at -O1 no bitcast is emitted at all. Input-shape check: the mismatched-width initializer is valid input (nothing in the type system ties the constructor's width to the kind's representation), and it is not an emit-layer problem, so the fix belongs in the global-value legalization that decides what may remain at module scope rather than in a consumer-side guard. Note this makes the mismatch well-defined rather than rejected — whether the type system should instead reject a cross-width round-trip is a separate semantic question, discussed on the PR.
Representation casts in emit (slang-emit-spirv.cpp). When the handle's representation matches the integer side named by the cast op, the cast forwards its operand. At runtime, when they differ, a real OpBitcast is emitted in a block (v2uint↔ulong shares the (hi<<32)|lo = __asuint64 layout). The module-scope constant-reinterpret path that an earlier revision of this PR carried is gone, because the inlining above makes it unreachable.
Width consumers. The representation width is decided in one place per layer and consumed identically by type emit, DefaultConstruct legalization, byte-address storage and cast-op selection, IR layout, the sizeof/alignof peephole, and AST layout/reflection. The peephole additionally honors the requested layout rule: a uint2 handle has std430/std140 alignment 8 but natural alignment 4, so alignof(DescriptorHandle<RWStructuredBuffer<float>>, Std430DataLayout) must equal alignof(uint2, Std430DataLayout). A uint64 handle is 8 under every rule, which is why a hardcoded-natural query was previously invisible — surfaced by @pdeayton-nv's explicit-query repro.
Verification (GPU-less; SPIR-V validation on):
The reporter's four categories — constant-buffer, structured-buffer, byte-address-buffer, and acceleration-structure handles — no longer abort. AS emits OpConvertUToAccelerationStructureKHR and passes spirv-val.
Plain texture → OpConvertUToImageNV; combined texture-sampler → OpConvertUToSampledImageNV; texel buffer (a non-combined image type) → OpConvertUToImageNV; SamplerState / SamplerComparisonState → OpConvertUToSamplerNV.
Global width mismatch: at -O0 the initializer is sunk into the function (OpSelect → OpBitcast after the entry point's OpLabel) and the binary validates; at -O1 it folds to a %ulong constant feeding OpIAdd and a %uint heap index, with no OpBitcast left.
sizeof/alignof agree with emission for the tested kinds: uint2 handles report std430/std140 alignment 8 and natural 4; uint64 handles report 8 under every tested rule.
Existing image/sampler cases remain supported; plain-image conversion is corrected from the previous unconditional OpConvertUToSampledImageNV to the type-correct OpConvertUToImageNV.
Closes #12185.

I like this direction — scoping the NV conversion opcode to texture / sampler / combined-texture-sampler is cleaner than generate-then-diagnose, and if it works it lets the E55215 diagnostic, the legalization guard, and the shared isBindlessTextureNVEncodableResourceType predicate all go away. But there's a representation blocker I ran into that I think decides how (and whether) this restructure lands, so I want to raise it before I change anything.
The handle is uint64 capability-wide under spvBindlessTextureNV, not per-kind. In slang-emit-spirv.cpp (the kIROp_DescriptorHandleType case, ~2717–2733), the descriptor-handle type is emitted as OpTypeInt 64 whenever spvBindlessTextureNV is implied — for every T.kind, not just texture/sampler — and as uint2 otherwise. The case spirv: / case spvDescriptorHeapEXT: heap arms all index with ((uint2)handleValue).x, and the case spirv: acceleration-structure expression is RaytracingAccelerationStructure(__asuint64((uint2)handleValue)). Those all assume a uint2 handle.
So if I delete the case spvBindlessTextureNV: arm and let the non-texture/sampler kinds fall through to case spirv: / case spvDescriptorHeapEXT:, under bindless-texture those arms receive a uint64 handle and try to consume it as uint2. We already saw this exact mismatch during this review: __asuint64((uint2)handleValue) fails SPIR-V validation under spvBindlessTextureNV (thread above — the %ulong handle can't feed __asuint64's %v2uint parameter). A buffer handle routed to the heap path hits the same uint64-as-uint2 problem.
That's really the "well-defined behavior when bindless-texture is / isn't combined with DescriptorHeapEXT" question, and I think it comes down to a representation decision that's yours to make:
(a) Make the bindless-texture handle representation kind-dependent — uint64 only for the kinds that go through the NV conversion op (texture/sampler/combined), uint2 for everything else — so the heap/AS expressions keep working unchanged for the non-NV kinds. This is the larger change: the "uint64 under spvBindlessTextureNV" decision is currently made capability-wide (per-capability, not per-kind) in a number of places, so making the width kind-dependent means threading the kind through all of them and keeping them agreed. It's not just the kIROp_DescriptorHandleType emit rule (slang-emit-spirv.cpp ~2717); the same capability-wide choice also appears in the equals/comparison arms (hlsl.meta.slang ~27485), default-construct lowering (slang-ir-spirv-legalize.cpp ~1744), the byte-address / structured-buffer storage-type path (slang-ir-byte-address-legalize.cpp), and the layout / reflection rules (slang-ir-layout.cpp ~446, slang-type-layout.cpp ~479 and ~5677). That list isn't exhaustive — the point is that it's a representation change spanning emit, legalization, and layout/reflection, so those would all need auditing so a uint2-represented non-NV kind isn't still sized or processed as uint64 somewhere.
(b) Keep the handle uint64 capability-wide and give the heap-indexing and AS expressions a uint64-aware decode when bindless-texture is active. This needs a defined encoding contract for what the 64-bit handle means as a heap index when both bindless-texture and DescriptorHeapEXT are in play — a uint64 → uint/uint2 conversion that type-checks isn't automatically the semantically correct index, so the contract has to be specified, not just made to compile.
Which of those do you have in mind? Once the representation is settled, the discrimination mechanism itself is simple: a nested __target_switch on spvBindlessTextureNV (it implies _spirv_1_0, so it's a valid nested case inside case spirv: / case spvDescriptorHeapEXT:) routes texture/sampler/combined → the NV op and everything else → that arm's heap path. The work is the representation audit above, not the switch.
Two smaller notes so we're aligned on scope:
Texel buffers (Buffer<T>.Handle, RWBuffer<T>.Handle) aren't DescriptorKind.Texture / Sampler / CombinedTextureSampler — they're UniformTexelBuffer / StorageTexelBuffer. Today they go through OpConvertUToImageNV (they are OpTypeImage). Under a strict "texture/sampler-only" classification they'd move to the heap path, so they're subject to the same representation decision above; I'd want to confirm we still want them on the NV op.
I couldn't find a source-level "is capability X active" query in .meta.slang — capability gating here is structural (which __target_switch arm is selected, or a [require] on a callee), which is why the nested-switch is the tool for the discrimination rather than an inline if.
