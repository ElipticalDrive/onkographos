This commit bundles four changes that accelerate the AVX2 path of BVH8_CPU in particular for incoherent rays.
The kernel now sorts intersected children by the true tmin distance and no longer uses the precomputed per-octant order perm. This involves a bitonic sort on integer keys formed from the tmin bits with the lane index in the lower three bits. The previous permutation approach was quite inaccurate: on the Sponza benchmark, the first traversed child is only the closest one in 19% of the node visits. Sorting per ray reduces the number of traversal steps on Sponza by 8%. Sorting mainly benefits closest-hit queries, so the any-hit path in IsOccluded stays as-is. I also tried on BVH4, and the same change is harmful there.
The kernel already had a specialized path for steps with a single intersected child. This commit adds a second one for two intersected children, which skips the sorting network. The highest and lowest set bits of the mask identify the two lanes, and one comparison orders them. This covers about a quarter of all node visits and shortens the path to the next node address. Since this path pushes onto the stack as well, the debug overflow check now follows the branch chain instead of sitting in the multi-child branch.
The nearest child can already be extracted after the first three sort stages, when the lower half is ascending and the upper half descending. That way, the descent into this node can overlap with the remaining sorting steps.
The traversal now prefetches the cache lines of every intersected child in a loop right after the slab test, before branching on the child count. Incoherent rays otherwise stall on each node they descend into and again on the nodes they pop later.
Performance on the Sponza speedtest on a Ryzen 9 7950X, in MRays/s. Shadow rays use IsOccluded, which is unchanged.
```
             primary    shadow    diffuse
  before        11.3      31.3        5.3
  after         12.9      31.3        6.4
```

I added some toggles to tiny_bvh.h to test the individual optimizations:
BVH8_USE_PREFETCHING for the two prefetching blocks;
BVH8_SORTING_NETWORK to run the sorting network instead of the method from the paper;
BVH8_2VALIDNODES to include the special handling of the '2 valud nodes' case.
The last two are clearly a win, in all scenarios. But for the prefetching I can't reproduce the gains on my CPU (AMD Ryzen AI 9 HX 370). Your CPU seems similar; can you verify prefetching is a win by itself?
