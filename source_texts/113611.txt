As long as the supercube is a rectangular cube, the current unordered_map is a very inefficient solution for a quick retrieval of a cube from coordinate in the supercube. A simple 3D table of the supercube would be the best - dereference would cost practically nothing.
It would only have to be copied - also, very quickly - when the supercube is changing.
It seems that somehow the current unordered_map hashing is not a bottleneck in normal knossos usage, including high-throughput random voxel-wise access from python, probably due to a heavier burden on the actual thunking. However, should in the future more efficient random access schemes be used within the C++ code, that cannot be efficiently binned into cubes to allow pre-hashing the cube pointer for each bin - a hashed access to cubes may be the bottleneck, and direct table reference the solution.

The boost hash function we use performs 20M/sec hashes of a coordinate key (no additional data
structure overhead included, e.g. collision list query) which is very good.
Since most voxel-wise operations are spatially correlated, an effective no-hash can be achieved
without changing the functional aspects of Dc/Oc2Pointer - according to Joergen's suggestion -
by simply keeping the last queried Coordinate-Cube pair as cache, and invalidating it whenever
the hash is changed (i.e. element entered or removed).
