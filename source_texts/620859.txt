Owner
Scene.atPose(pose, scene) places a subtree at a Camera3D.mappedPose with full orientation: origin at position, local +Z along forward, +Y along up, local +X on the pose's left. Same convention as Anim.lookAt (aims local +Z) and Scene.quad (faces +Z), and as Camera3D.fromPose in #837.
One rigid matrix (MappedTrackingPose::to_matrix) on an ordinary transform group, so no new node, renderer path, or serde shape.
Forward is kept; up is re-orthogonalized. A zero, non-finite, or parallel basis is a teaching error (same rule and tolerance as fromPose).
Registered in the typed registry; .funi docs, skill, and a docs/vr.md held-object snippet.
examples/held-pose: an asymmetric marker on the right grip (or a fixed rolled demo pose without XR). Cyan = local +Z, green = +Y, pink = +X (the hand's left).
held-pose-demo golden: demo grip yawed 65° left, pitched 20° up, rolled 40° left. Hidden GL, --fixed-time 0.
Verification
CPU tests: identity, yaw/pitch/roll vs Scene.rotateY/X/Z, translated pose, inner/outer transform order, basis normalization, degenerate/missing/non-finite input, Scene.equals + serde round-trip, and a rolled mapTrackedPose → atPose pipeline against OpenXR ground truth.
npm run test:held-pose: injects level, rolled-90°, and yaw+pitch+roll grips under --emulate-xr, composes /scene matrices, and checks each arm against directions computed from the quaternion in JS.
Mirrored-basis proof: temporarily negating local +X in to_matrix failed 4 e2e checks (every pink-arm check) and 5 of 6 CPU tests; reverted.
Golden held-pose-demo (1600x1200): 0 differing pixels inline and --pipelined.
cargo test -p functor_runtime_common (1001 + 33 pass); desktop cargo build --features=strict; npm run check:docs. All re-run after review fixes.

Review (/xreview: Claude + Codex + de-dup)
No Critical/High/Medium correctness findings; the visual check confirmed the golden's arm directions numerically.
Fixed: merged two tolerance helpers in the tests.
Kept, both engines (Low): to_matrix rejects finite but extreme magnitudes (~1e20) via magnitude() overflow. It deliberately matches fromPose's rule; mapped poses are unit length.
Kept: the e2e overlaps the CPU roll test, but it is the injected-quaternion → /scene ground truth this PR requires. --emulate-xr stays to show that injection overrides the emulator.
Kept: the serde round-trip test (cheap; pins the "no new node" claim). The degenerate-pose message stays identical to fromPose's.
Deferred: the e2e post/get/waitReady/step helpers are copied from xr-pose-injection.mjs (and feat(camera): Camera3D.fromPose + sniper-scope tracked rifle #837's sniper e2e). Extract them to e2e/mcp-rpc.mjs in a follow-up.
Follow-up
Whichever of this PR and feat(camera): Camera3D.fromPose + sniper-scope tracked rifle #837 lands second: share one basis/validation helper (MappedTrackingPose::to_matrix) and feat(camera): Camera3D.fromPose + sniper-scope tracked rifle #837's mapped_pose_from_value decoder between fromPose and atPose. Note that Camera::world_basis uses a looser degeneracy rule (is_normal), so a near-parallel pose can map but not place.
