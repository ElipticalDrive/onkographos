Summary
Adds a Triton kernel for quantize_per_tensor_dynamic. The operator dynamically quantizes a
float32 tensor to qint8 / quint8 with per-tensor parameters derived from the input at runtime:
the [min, max] range is reduced on device, extended to include zero, mapped onto the qmin/qmax
grid (halved under reduce_range=True), with ATen's small-scale cutoff at
fp32(6.1e-5) = 6.0999998822808266e-05 and the 0.1 fallback for degenerate (zero-range) inputs;
the nudged integer zero point is chosen from the pair (min-side, max-side) with the smaller
arithmetic error and rounded half-to-even.
The implementation mirrors ATen's split exactly:
qparams: amin/amax are reduced on device and synced to the host (the same two
.item<float>() pulls ATen performs), then ChooseQuantizationParams is replayed in host
doubles with fp32 rounding of every intermediate the C++ code stores in a float — the computed
scale / zero_point are bit-exact against the reference (verified on 1600+ randomized
amax configurations across all four dtype x reduce_range modes, plus the degenerate all-zero /
tiny-amax branches).
elementwise pass: a Triton kernel computes rint(x * (1/scale)) + zero_point with one fp64
reciprocal per program and per-element fp32 math (measured ~2x faster than the all-fp64 form;
the fp32 product and fp64 quotient only disagree near half-integer boundaries, so lanes whose
remainder is within NEAR_HALF = 0.499 of the tie are queued and recomputed in exact fp64 by a
fix kernel — those are the same at-tie lanes where the two precisions can differ by one
quantization level). Lanes with huge quotients saturate identically on both paths and skip the
repair.
Channels-last / channels-last-3d inputs keep their layout end to end (ATen's quantizer follows
suggest_memory_format); a channels-last input yields a channels-last int_repr, which the
_empty_affine_quantized + set_ wrap preserves (_make_per_tensor_quantized_tensor would
silently normalise the strides to contiguous). The .out overload validates the destination
dtype/shape (a shape mismatch surfaces ATen's QuantizedCUDA resize_ gap) and lands through
quantized copy_, which overwrites the integers and adopts the dynamically computed quantizer.
Measured ATen contract (torch 2.8.0a0 on H20-3e, all covered by tests):
only torch.float32 inputs are accepted ("Quantize only works on Float Tensor"); qint32 is
rejected ("dtype QInt32 not supported"); the empty input raises on the min() reduction exactly
like the reference.
All-zero input -> degenerate branch: scale = 0.1 (zp = qmax for qint8, qmin for quint8);
tiny amax (1e-10) -> the small-scale branch lifts scale to 6.0999998822808266e-05.
reduce_range=True halves the grid (qint8: [-64, 63], quint8: [0, 127]), so the scale
doubles and the zero point re-nudges accordingly.
Testing
Direct call flag_gems.quantize_per_tensor_dynamic(x, dtype, reduce_range), compared against
torch.quantize_per_tensor_dynamic on the same device: dtype, qscheme(), q_scale(),
q_zero_point() and int_repr() are all bit-exact.
Coverage: 5 shapes (2-D, 3-D, 4-D, 5-D, up to 1024x1024) x {qint8, quint8} x {reduce_range
False/True}, the degenerate all-zero and tiny-amax branches, a 0-dim input, a strided input,
channels-last / channels-last-3d memory formats, rejected non-float32 dtypes, rejected qint32,
the empty-input error, and the .out overload (quantizer adoption + dtype/shape mismatch).
Dequantized values are compared end-to-end.
pytest tests/test_quantize_per_tensor_dynamic.py -> 38 passed; --ref cpu -> 38 passed;
--ref cpu --quick -> 26 passed (CI parameters).
Tested on: Nvidia (H20-3e).

Notes (honest recording, per the batch's reporting rule):
Large tensors (>16 MiB) run ~1.48x: ATen's elementwise kernel pays a per-element fp64
division (493us at 4096^2), while the fused fp32 fast path + fp64 repair-queue pipeline runs the
whole quantization in ~86us GPU time.
Small tensors are host-bound (~0.15x at 64x64): the dynamic contract forces two device-to-host
scalar syncs (min/max .item(), ~40us each under the dispatcher, paid identically by ATen)
plus the flag-queue allocation and a second kernel launch. ATen does the same amax syncs but
with a single fused elementwise kernel; the extra Triton launch overhead dominates at sizes
where the GPU work is negligible.
KernelGen SimpleOpt (18/18 workloads PASSED, 7 rounds, best round geo_mean 43.9x on its own
timing set — reference-latency noise inflated that round; like-for-like 2.9-5.3x) found the same
two levers: per-element fp64 math removal and the flag-queue repair architecture adopted here.

Review: Request Changes
Thanks for the contribution. The main computation is Triton, both dispatch keys are reachable, and the qparams are bit-exact against ATen (I compared 12,024 local cases with zero mismatches). There is a new correctness bug plus two unresolved performance issues.
P1
New correctness bug: the BIG_Q=200 bound is wrong — src/flag_gems/ops/quantize_per_tensor_dynamic.py:43,158. The premise "anything above 200 saturates" is false because q = a + zp and zp can be as low as -128, so q ≈ 72 does not saturate. Reproduced with mn=-1, mx=1000: at x=787.06, the fp32 path yields q=72 while the fp64 reference yields q=73, and the fix-up is skipped — a one-level quantization error. Raise the threshold to 256.
Queue/second-launch cost (previous item b, unresolved) — :288 allocates an n-element int32 queue each call (~64MB for 4096²), :313 launches 64 fix-up programs even when cnt == 0, and :258/:259 still perform two .item() syncs (ATen uses a single aminmax). This is why small sizes are 0.14x/0.29x.
.out still double-copies (previous item c, unresolved) — :397 out.copy_() goes through the ATen quantized copy, adding a full O(n) pass. Master's quantize_per_tensor_out:356-366/583-586 already solves this with _int_view + a Triton copy_; please reuse it.
Note
Previous item (a) does not hold: ATen also rejects Half, so _validate is correct and the Half branches at :360/:375 are simply dead code.
Verified-compliant
Triton main computation, dual reachable dispatch keys, conf/operators.yaml/exports/marker complete, and degenerate branches well tested. Tests call flag_gems.* directly, so there is no dispatch test and no guard against a native copy_.
