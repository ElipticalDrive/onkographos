Copy link

Issue body actions
Context
I evaluated Cellulose as the meshing backend for a voxel game engine (voxel_browser (https://github.com/RechieKho/voxel_browser)) with fully-editable terrain (block break/place is a core, frequent operation, not just world generation). Cellulose was chosen expecting it to be a strong fit specifically because of greedy meshing — fewer draw calls, less GPU vertex data for large static regions.
In practice it had to be reverted after landing, for reasons that seem structural to greedy meshing rather than implementation bugs on my end, and I think they're worth raising here in case they're solvable at the library level (or worth documenting as a known tradeoff).
What went wrong
My renderer avoids GPU buffer churn on every edit by over-allocating each chunk's vertex/index buffers with headroom, and using UpdateMeshBuffer() in place when a re-mesh still fits, only falling back to a full buffer recreate when it doesn't. This is important because on at least one GPU vendor's driver (NVIDIA, confirmed via ASan), rapid UnloadModel/UploadMesh-style VAO/VBO create/destroy churn triggers driver-internal heap corruption — not a bug in the calling app, but real enough that avoiding the churn pattern matters.
With a hand-rolled, non-merging mesher (fixed 4 verts / 6 indices per visible face), a single block edit changes vertex/index count by a small, local, bounded amount — almost always within the headroom, so it stays on the cheap in-place update path.
With greedy_mesh, a single block edit near a merge boundary can restructure an entire run of merged faces — splitting one large merged quad into several, or coalescing several into one. The resulting buffer-size delta is proportional to the size of the affected merged region, not to "one voxel changed." In practice this meant:
Buffers blew past their headroom far more often, forcing full buffer recreation on a large fraction of ordinary terrain edits.
That reintroduced exactly the GPU churn pattern that causes thd above.
Even setting the crash aside, it produced a noticeable FPS dip during active terrain modification, since normal play (mining/building) is dominated by frequent single-block edits, not static geometry.
Why I think this is worth an issue here rather than just my app
The core tension is: greedy meshing's whole value proposition is amortizing cost over large coplanar regions, but a frequently-edited voxel world is adversarial to that — edits are local, but merged output isn't. mismatch for this workload rather than something I got wrong inthe integration, but I'd like a sanity check from you.
Questions / possible directions:
Is there (or could there be) an incremental re-mesh path in Cellulose that re-merges only the affected region, bounding the vertex/index delta closer to the edit's actual footprint, instead of implicitly re-deriving arbitrarily large merged runs?
Is there a middle ground — e.g., merging within fixed-size sub-blocks of a chunk (capping how large a single merge run can grow) — that would trade away some draw-call savings for bounded per-edit buffer volatility?
Would it be worth documenting in the README/docs that greedy_ or rarely-edited geometry, and that highly dynamic voxel terrain (block-by-block edits every frame) is an anti-pattern for it as currently designed? That would have saved me the investigation, and might save the next
person evaluating it for a Minecraft-like use case.
Happy to share the throwaway integration branch / repro numbers (quad counts, buffer-fit rates) if useful — this was evaluated and reverted in RechieKho/voxel_browser (https://github.com/RechieKho/voxel_browser), see STATE.md §8's 2026-09-16 entry for the full writeup.
