An octree is currently being used for chunk LODs, but it would be more efficient to store actual voxel data in a single persistent datastructure and sampling from it, rather than recreating the data every time a chunk is loaded in. This also allows for much easier terrain modification.
The current SDF/isosurface approach is perfect too, because when building the octree, homogeneous nodes can be skipped if the SDF at their center is bigger than half their side length—ie the closest point on the surface is outside their node bounds.
A more detailed breakdown of how to build an sparse voxel octree from an SDF can be found here: https://gamedev.stackexchange.com/questions/191541/how-to-construct-a-octree-density-from-sdf-for-mc
One issue: I'm not using a real 3D SDF, it's more height/density, so I'd need to figure this out. Or construct the octree differently.

Could you elaborate on what you mean here with primitives?
Signed Distance Fields, or SDFs, are functions that define the distance of a point in space to an implicit surface. They're mostly used with a couple easy and well-documented functions for primitives like spheres, cones, rectangles, torus, etc. Iñigo Quilez actually has a whole post on it: https://iquilezles.org/articles/distfunctions/
The issue is that they only really work for these simple shapes you can easily calculate a distance to, so using it means the entire terrain has to be constructed out of weird combinations of spheres, triangles, and the like, instead of smooth height functions.
True, but as far as my understanding goes, your fundamental issue is that the scale of what you are trying to accomplish is such that storing the map is not a possibility.
Noita does actually save their worlds, because there's so much editing going on they cannot regenerate without losing data, so they load/unload from disk the relevant parts. https://youtu.be/prXuyMCgbTc?si=U_-o24dScVvHqMHn&t=783
As for memory usage, our solution can actually be a lot more efficient than Noita here using octrees, which store data at variable density, leaving large areas that are completely solid or completely empty taking up very little data. The scale of the planet actually works well here, because all the data is concentrated at the surface, and pretty much everything else should (theoretically) be compressible enough it's almost free.
This 3 minute video explains it well: https://www.youtube.com/watch?v=NjCp-HIZTcA
See more here: https://en.wikipedia.org/wiki/Octree
(Visualisations of an octree)
Our advantage over noita is that we only care about density, not block type (Noita has many materials everywhere it needs to keep track of), while we only have solid/air, and can completely collapse neighbouring voxels as long as they don't intersect a surface.
Even comparing to something on a much bigger scale, like Minecraft, who do store the entire loaded world's voxel data (not in memory all at once), our solution is still more memory efficient because of being able to store large areas in the very little data, so memory costs should be quite manageable.

Since this is on a sphere even the 2D heightmap needs 3D noise as offset, because you get reprojection issues otherwise :(
Noise domain warp (I assume from this https://iquilezles.org/articles/warp/) is awesome and often used in terrain gen to make stuff like ridges and rivers, but it doesn't change dimensionality, so 3D noise (+ warp even) is just easier.
I've been doing some testing and honestly the fake 3D noise->height SDF works fine. Even the edge cases it might miss are loaded in properly anyway when the player gets close enough to notice.
I also want to try building the octree backwards from known geometry, which wouldn't even need SDFs. Should also save a lot of memory, we'll see :)
