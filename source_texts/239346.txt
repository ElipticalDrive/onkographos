This adds a RenderRegion parameter to Renderer::render, so a frame where only part of a retained target changed can redraw just that part. RenderRegion::Viewport keeps today's behaviour; RenderRegion::Rects(&rects) writes only the pixels covered by the rectangles and leaves the rest of the target untouched.
Inside the rectangles the scene is drawn under a scissor, once per rectangle, so damage should be merged into a few rectangles. The target init is confined too: a ClearSettings::Viewport clear is drawn as rectangles (a load-op clear ignores the scissor), and ClearSettings::Rects is intersected with the region. Rectangles are clamped to the target and made disjoint, so overlapping damage doesn't blend translucent content twice.
The scheduler drops root strips that miss the region, which cuts host-side strip encoding and upload for small regions. It never changes the strips it keeps, so the scene inside the region matches a full render. Layers are always rendered in full, since filters can move pixels into the region.
Rect clears now pass their color to the shader as floats instead of RGBA8, so a confined viewport clear stores what the full-target load-op clear would: exactly on 8-bit targets, and within one half-float step on float targets, where the two conversions may round differently. Previously the color was quantized to 8 bits, and on some GPUs rounded differently from a load-op clear even on 8-bit targets. This also makes ClearSettings::Rects store the same value as a viewport clear of the same color; no reference snapshots changed.
The WebGL renderer is unchanged; it always redraws its whole drawing buffer (see #1869). vello_cpu has no equivalent yet.
Tests: scheduler unit tests for the culling, two snapshots, and byte-exact comparisons of confined and full renders with layers, a root blend, a root clip rect, several region shapes, translucent clears and a float target.

I reshaped the PR to the consumer-driven decomposition suggested by @taj-p:
RenderConfig { load: TargetLoad, scissors: &[RectU16] } - the scissors are a set of pairwise-disjoint damage rects, so a diagonal pan's two edge strips are one render call. Each root pass runs its draw sequence once per rect under that rect's scissor (dynamic pass state, so the target load is still paid once).
TargetLoad::{Clear, Load, DontCare} rides the first root strip pass's LoadOp - there's no standalone clear pass anymore, and DontCare forwards wgpu's opaque-coverage token for the tiled-GPU case you described. Your "render to scratch + copy the rect" sketch works on top of this today for full-target scratches; region-sized scratches would additionally need a render offset in vello, which I think is worth a separate issue.
clear_rects is the caller-driven region clear (one scissored-quad pass for N rects), used with Load when the scene won't repaint the damage opaquely.
In my engine, the scene is rebuilt every frame - my retained scene graph culls at encode time, so on a partial frame the vello Scene only ever receives content intersecting the damage.
One potential issue with this approach is that culling happens at the end of the pipeline. It's much better, at scene construction, for a consumer to push_clip_path the damage regions so they don't pay per-pixel costs for pixels that will eventually be thrown away at rasterization time.
I tried this first, and it initially failed to produce same results, because with any clip active, rects (including image and glyph quads) leave the GPU analytic rect path and go through CPU strip generation + mask intersection — and the two rasterizers quantize fractional-edge anti-aliasing differently. The analytic path quantizes the edge position to unorm8 and computes coverage in the shader; the strip path computes exact f32 coverage and quantizes after. At half-ties they round in opposite directions, so a full-viewport integer clip that removes nothing still changed rendered bytes by ±1 LSB at fractional edges. My damage pipeline treats "partial render == full render, byte-for-byte" as a hard invariant, so that ruled the clip recipe out as it stood.
Rather than drop the idea, the second commit makes it byte-exact: clip paths that are disjoint, axis-aligned integer-rectangle sets are detected in ClipContext, and rect content clamps to the set analytically instead of demoting (an integer clip edge is exactly a 0/255 coverage step, so this is provably identical to the mask intersection). Scene::set_cull_hint covers the scene-construction cost for everything else by culling flattening/strip generation to the damage bounds — including line segments now, which previously never flatten-culled at all. There's a GPU test (clip_exact.rs) pinning clipped-vs-unclipped byte equality for rects, texture rects, paths and strokes.
Nice side effect: this speeds up every rectangular clip viewport (scrolling containers), damage or not — on a clip-heavy stress scene in my engine it's ~2.3× on scene encode and ~2× on the frame.
