Description
Once Phase 2 successfully fetches and caches the raw 3D assets (STLs, GLBs, Textures) without flooding the network, these geometries must be processed. Currently, the library eagerly computes bounding volumes (computeBoundingBox, computeBoundingSphere) and immediately attaches meshes to the active scene graph. For high-poly robotic assemblies, running these spatial computations synchronously across dozens of meshes creates a severe CPU spike, freezing the UI. Furthermore, the lack of a spatial index (BVH) makes subsequent raycasting operations for drag controls highly inefficient ($O(N)$).
Phase 3 introduces the Shadow Assembly pattern. Raw meshes will be queued into a deferred evaluation loop that yields to the main thread. We will also integrate three-mesh-bvh to build collision trees in the background. Finally, the loader will guarantee Atomic Delivery: the robot is only handed over to the simulation engine once it is 100% complete and mathematically indexed.

Loading
Implementation Requirements
1. Deferred Math Processor (Yielding Loop)
Create a micro-task queue to handle the heavy mathematical operations on resolved geometries.
Implement a chunking mechanism (e.g., processing 1 or 2 heavy geometries per frame).
Use requestIdleCallback (with a fallback to setTimeout or await sleep(0)) to yield control back to the browser's main rendering thread.
Operations per geometry: Ensure that computeBoundingBox() and computeBoundingSphere() are executed exclusively inside this yielding loop.
2. Spatial Indexing (BVH Integration)
Integrate three-mesh-bvh to drastically optimize raycasting for the URDFDragControls.
Invoke computeBoundsTree() on all visual and collision geometries during the deferred math loop.
Update URDFDragControls.ts and URDFViewer.ts to leverage the .boundsTree property when intersecting objects, changing the raycasting complexity from linear to logarithmic.
3. Draw Call Batching (Optional / Future-proofing)
If multiple meshes belong to the same link, or are connected via fixed joints, implement an optional step to merge them using BufferGeometryUtils.mergeGeometries. This reduces WebGL draw calls and overhead for highly fragmented models.
4. The Atomic Guard & Cache Generation
Ensure the final robot is delivered safely to the simulation context.
Do not call URDFRobot.updateMeshCaches() iteratively. It must be called exactly once after the deferred math queue is entirely empty.
The main URDFLoader.loadAsync() promise must only resolve after the updateMeshCaches() pass is complete.
Acceptance Criteria
No UI Freezing: Loading a complex robot (e.g., MHS Helicopter) must not drop the framerate of the existing simulation below an acceptable threshold (e.g., 30fps) during the math computation phase.
Logarithmic Raycasting: URDFDragControls hover and drag events must demonstrate stable 60fps performance even when intersecting models with >500k polygons, validating the BVH integration.
Atomic Handover: The URDFViewer receives the geometry-loaded and urdf-processed events only when the robot's physical bounds, BVH, and mesh caches are 100% computed. No mid-load center-of-mass shifts can occur.
Clean Abort: If the loading token is revoked (as defined in Phase 1) while the deferred queue is still processing, the loop must immediately halt and discard pending operations to save CPU cycles.
Test Strategy
Yield Verification: Stub computeBoundsTree with a heavy while loop (e.g., blocking for 50ms). Load 10 meshes. Assert that the main loop executes a requestAnimationFrame tick between the processing of the chunks.
BVH Raycast Test: Programmatically fire raycasts at an ingested model and verify that the intersections are calculated using the three-mesh-bvh codepaths rather than standard Three.js triangle checks.
Atomicity Assertion: Hook into the onLoad callback and assert that robot.flatVisualMeshes.length accurately reflects the total sum of loaded geometries precisely at the moment of resolution, not before.
