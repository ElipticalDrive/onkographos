100% agree - a few points to think over after I'll have the first API version ready:
Fog Volume name has to stay, but only in the context of OpenVDB. It's an recognised OpenVDB grid class type (example.)
BUT - this kinda doesn't really belong to this repo / VDBLoader package. It's coded here right now only because there's no alternative to it in core three - and I don't want to over-engineer stuff by creating 1000 packages before the thing's even usable. But indeed, having volume material in a VDBLoader package feels like locking MeshStandardMaterial within GLTFLoader package - they are independent and can be used separately depending on the context.
Originally I wanted this repo to be independent of three. Not sure yet how it'll look in the end - but I'd like VDBLoader to also be accessible to folks using Babylon / pure WebGL - just as a data structure they are able to read from.
