Hi all,
A bit of a two part best practice/intended functionality question. I'd be very happy to split into two issues if that's more convenient.
I've been trying to come up with a scene camera which I can use to simulate a real world camera, i.e. place the camera at a point and look out in a particular direction defined by some rotation (quaternion, matrix, etc.).
It doesn't look like any of the existing cameras really achieve what I'm looking for out of the box, so I'm considering subclassing Base3DRotationCamera() and implementing it as I need. Obviously if there's a simpler way to do this I'd be very keen to hear it.
As I was investigating the ArcballCamera(), (seems close to what I need, but it orbits around a point, rather than looking out from a point), it appears that the distance property doesn't handle a distinction between None and 0.0
If this is not the intended functionality I can look at fixing it, I believe the problem occurs in line 316 scene/cameras/perspective.py.
An example of the functionality is included below:
Pressing d cycles through an arcball distance parameter of [0.0,0.1,None], and there's no difference in the display between 0 and None.
Presumably making any change to this might effect the Turntable camera.
I am running vispy 0.14.3, but I don't believe the arcball has changed since then.
```
import numpy as np
import vispy.scene as vscene
from vispy.scene import ArcballCamera, visuals
import vispy.app

# Make a canvas and add simple view
canvas = vscene.SceneCanvas(keys='interactive', show=True)
view = canvas.central_widget.add_view()


# generate data
pos = np.random.normal(size=(100000, 3), scale=0.2)
# one could stop here for the data generation, the rest is just to make the
# data look more interesting. Copied over from magnify.py
centers = np.random.normal(size=(50, 3))
indexes = np.random.normal(size=100000, loc=centers.shape[0] / 2,
                           scale=centers.shape[0] / 3)
indexes = np.clip(indexes, 0, centers.shape[0] - 1).astype(int)
symbols = np.random.choice(['o', '^'], len(pos))
scales = 10**(np.linspace(-2, 0.5, centers.shape[0]))[indexes][:, np.newaxis]
pos *= scales
pos += centers[indexes]

# create scatter object and fill in the data
scatter = visuals.Markers()
scatter.set_data(pos, edge_width=0, face_color=(1, 1, 1, .5), size=5, symbol=symbols)

view.add(scatter)

view.camera = vscene.ArcballCamera(fov=90.0,distance=0.1)
view.camera.name = 'arcball'
view.camera.center = (0,0,0)

# add a colored 3D axis for orientation
axis = visuals.XYZAxis(parent=view.scene)

@canvas.events.key_press.connect
def on_key_press(event):
    global view
    global camera_types
    if event.key == 'd':
        if view.camera.distance == 0.0:
            view.camera.distance = 0.1

        elif view.camera.distance == 0.1:
            view.camera.distance = None

        elif view.camera.distance is None:
            view.camera.distance = 0
        print(f'New {view.camera.distance=}')
        print(f'Camera used distance {view.camera._actual_distance=}')

canvas.show()

if __name__ == '__main__':
    vispy.app.run()
```

In terms of the first point (a programmatic specification of a 3D camera position and orientation, not interactive), and achieving this via an existing camera or subclassing a camera. The arcball camera is almost what is needed but the distance factor needs to be settable to 0, and the _get_rotation_tr() implementation yields incorrect rotations for an arbitrary quaternion input.
Setting up the camera to point at each of the axes in turn with a defined quaternion (and accounting for the camera frame defintion) yields inconsistent results, and the problem seems to be with the matrix calculation from the quaternion inside _get_rotation_tr().
I'll preface the following with the fact that the mouse control of the arcballCamera works right now and feels good. With the following change not so much.
Altering the _get_rotation_tr() implementation from (
vispy/vispy/scene/cameras/arcball.py
Lines 70 to 73
in
63d352e
def _get_rotation_tr(self):
"""Return a rotation matrix based on camera parameters"""
rot, x, y, z = self._quaternion.get_axis_angle()
return transforms.rotate(180 * rot / np.pi, (x, z, y))
to (critical change is the order of axes for the matrix calculation in the return statement)
```
    def _get_rotation_tr(self):
        """Return a rotation matrix based on camera parameters"""
        rot, x, y, z = self._quaternion.get_axis_angle()
        return transforms.rotate(180 * rot / np.pi, (x, y, z))
```
Now yields what I would consider the expected behaviour when specifying a quaternion.
As the arcballCamera doesn't really seem to be intended for what I'd like, I don't see any reason to recommend any changes to it, and I'll carry on with my own local subclassing. But in case anyone else ever has this problem, that's what I'd change when implementing a subclass of Base3DRotationCamera.
