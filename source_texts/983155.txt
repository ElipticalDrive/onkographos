Why now
Upstream has merged the whole "introduce + deprecate" arc of openvdb #2232, shipping in OpenVDB 13.1:
#2288 single-space GridHandle<cuda::Buffer<std::byte, R>>
#2292 cuda::copyTo cross-space transfers, pinned handles
#2293 reset() via destroy(), single-space NodeManager
#2301 DeviceBuffer deprecated; cuda/HandleStorage.h lets every tool emit single-space output; VoxelBlockManagerHandle gains single-space accessors; TopologyBuilder stages its root via allocateProcessedRoot/uploadProcessedRoot
#2319 DistributedPointsToGrid per-device resources; UnifiedBuffer deprecated
One release later upstream deletes hasDeviceDual, the dual GridHandle accessors and the BufferT::create fallback. nanovdb::GridHandle<fvdb::TorchDeviceBuffer> is our grid storage everywhere (GridBatchData.h), and it depends on exactly those things. We should migrate inside the deprecation window rather than at the removal.
Where we are
Route NanoVDB builder scratch through PyTorch's active CUDA allocator via upstream memory-resource seams #732 routed builder scratch through BuilderResource (= TorchResource, PyTorch's caching allocator) at all 13 CUDA builders plus our own PadGrid.cuh.
Update NanoVDB for single-space GridHandle and widen Torch-pool coverage #752 bumped the pin past #2288 and converted the small ready-now pieces (VBM metadata buffers via an adapter, SaveNanoVDB staging). It is now behind main (which moved to the #2220 pin in Use fused NanoVDB ReadAccessor::getDimAndActive in the HDDA iterators #754) and predates #2292/#2293/#2301/#2319.
TorchDeviceBuffer is already single-space internally: one pointer plus a runtime torch::Device. We never call deviceUpload/deviceDownload. Its hasDeviceDual = true is load-bearing only for the dual GridHandle constructor, handle.deviceData()/deviceGrid<>(), nanovdb::cuda::mergeGridHandles, and the tools' BufferT::create output path. All four go away at the remove step.
Two sites still spell nanovdb::cuda::DeviceBuffer (PadGrid.cuh default template arg and root staging). With -Werror, the pin bump alone turns those into build errors.
Design
One device buffer type, device index in the resource. NanoVDB's traits pick host vs. device per type at compile time, so a runtime-device buffer type like TorchDeviceBuffer cannot satisfy the single-space concept. Instead:
```
// src/fvdb/TorchDeviceResource.h
struct TorchDeviceResource : nanovdb::cuda::SyncFromAsync<TorchDeviceResource> {
    torch::Device mDevice;  // CUDA:i or PrivateUse1; default = current CUDA device
    // CUDA: CUDAGuard(mDevice) + c10 raw_alloc_with_stream / raw_delete
    // PrivateUse1: c10::GetAllocator(PrivateUse1)->raw_allocate / raw_deallocate
};
using DeviceGridBuffer = nanovdb::cuda::Buffer<std::byte, TorchDeviceResource>;

// src/fvdb/GridStorage.{h,cu}
class GridStorage {
    std::variant<nanovdb::GridHandle<nanovdb::HostBuffer>,
                 nanovdb::GridHandle<DeviceGridBuffer>> mHandle;
    torch::Device mDevice;  // kCPU | CUDA:i | PrivateUse1
    // device(), isEmpty(), bufferSize(), gridCount(), gridSize(i), gridType(i)
    // hostBytes() / deviceBytes()  (PrivateUse1 returns the unified pointer from both)
    // hostGridAt<T>(off) / deviceGridAt<T>(off), stream()
    // to(torch::Device, cudaStream_t)  -> cuda::copyTo
    // static deviceProto(device, stream) -> 0-byte DeviceGridBuffer; replaces the zero-size "guide"
    // static empty(device)
};
```
The device index travels inside proto.resource() through createDeviceStorage, copyTo and Buffer::copy(), so the guide-buffer hack becomes principled and allocations are device-correct even if a caller forgets a CUDAGuard. BuilderResource/TorchResource stay as the stateless scratch resource; the tools take storage BufferT and scratch ResourceT independently. GridBatchData::mGridHdl becomes std::shared_ptr<GridStorage>; nanoGridHandle() is replaced by gridStorage(), deviceGridPtrAt(i), hostGridPtrAt(i).
Kernel-free assembly. Constructing a device handle from raw bytes costs a parse kernel plus syncs. Only the per-item op.getHandle(proto) pays that. Everything we assemble ourselves adopts known metadata:
mergeDeviceGridHandles(handles, proto, stream): one allocation, cudaMemcpyAsync per grid, header-fixup kernel, host-built GridHandleMetaData, HandleFactory::make. Replaces nanovdb::cuda::mergeGridHandles, which is enable_if<hasDeviceDual> and syncs once per grid.
makeDeviceHandleFromLayout for MakeContiguous / ConcatenateGrids, which know their layout.
Hoist the duplicated updateGridCountAndZeroChecksum kernel into one header. Checksums stay disabled on merge/concat as today.

Risks
Stream ordering. DeviceGridBuffer frees on its retained stream; TorchDeviceResource::deallocate_async ignores the stream and relies on torch's alloc-time record, same as TorchResource today. GridStorage::to orders the destination stream after the source stream with an event before copyTo.
Multi-GPU. Single-space storage ignores createDeviceStorage's device argument; the resource guards internally, so allocations are correct. Kernels still need the callers' existing CUDAGuards; a debug assert in deviceProto() catches omissions.
Default-constructibility. TorchDeviceResource defaults to the current CUDA device so DeviceGridBuffer, its handle, the variant, and copyTo of empty handles stay default-constructible.
Out of scope

Suggestion for tightening three contracts that came from a design review:
Order source lifetime after asynchronous reads. Having the destination stream wait for source writes covers readiness, but the source allocation must also remain valid until the copy finishes. This is particularly relevant when .to() transfers from a temporary compacted handle. A small probe using PyTorch’s native caching allocator reproduced the failure mechanism: after only the readiness dependency, deleting and reallocating the source reused its address, and the delayed copy read replacement bytes. Specify allocator stream recording, ownership retained until completion, or a completion event back to the allocation stream. Changing the buffer’s retained stream alone is insufficient while deallocate_async ignores that argument. Apply the same contract to merge/concatenation inputs when streams differ.
Preserve the requested resource on empty transfers. At 31d1e596, cuda::copyTo returns a default-constructed destination handle when the source has zero bytes, ignoring the supplied prototype. Since TorchDeviceResource defaults to the current CUDA device, an empty transfer targeting cuda:1 while cuda:0 is current could leave the buffer resource inconsistent with GridStorage::device(). Have GridStorage::to explicitly construct its empty destination using the requested device/resource and stream.
Distinguish an omitted stream from explicit legacy stream zero. TorchDeviceBuffer currently treats null as “use torch’s current stream,” making explicit stream zero indistinguishable from omission. This is pre-existing, but the replacement API should avoid carrying it forward. Use overloads or an optional stream: omission resolves to the target device’s current PyTorch stream; an explicitly supplied stream, including zero, is honored. Convert the remaining default-stream voxelsToGrid sites to the explicit-stream class API during the builder migration.
These details are consistent with NanoVDB’s transfer contract and empty-copy behavior at the proposed pin.
Add targeted tests for immediate source destruction and allocation reuse after an asynchronous transfer, empty transfers to a noncurrent GPU, and explicit stream zero while a nondefault PyTorch stream is current. Run the lifetime tests with caching enabled as well as the existing no-caching configuration; allocation reuse is essential to exposing this failure mode.

Reviewing #773 (steps 1–2) against this plan turned up one design point the plan needs to settle, and a few items that should be added to later steps so they are not lost.
1. Which stream owns grid storage allocations
The design records grid storage against whatever stream allocate_async receives, and the Risks section says deallocate_async ignores its stream and relies on that alloc-time record. That is fine for streams fvdb owns, but upstream DistributedPointsToGrid creates its output storage on mDeviceMesh[0].stream (HandleStorage.h createDeviceStorage), and DeviceMesh has no constructor that accepts caller streams. BuildGridFromIjk.cu and BuildDenseGrid.cu build a loop-local DeviceMesh, so the returned GridBatch block ends up recorded against a cudaStreamDestroy'd stream. c10 pools freed blocks by exact cudaStream_t, so the block is never reusable by any torch stream (reserved memory grows one segment per build until an OOM release), and with expandable_segments:True the eventual unmapHandles syncs on the dead handle and throws.
#773 introduces this today because the old pin dropped the stream in create() (noted on the PR). The TorchDeviceResource design carries it forward unchanged, and @swahtz's item 3 (honor every explicitly supplied stream, including zero) would lock it in. The plan should pick one and say so:
cache a long-lived per-device DeviceMesh so the recorded stream stays valid, or
have the storage resource accept only torch pool streams and fall back to the device's current torch stream for anything else (needs reconciling with item 3: honor explicit streams that torch knows about), or
ask upstream for a storage-stream parameter on DistributedPointsToGrid separate from the mesh streams.
2. Items to add to the step lists
Step 2 or 4 — patchGridWithBlindShape checksum. It rewrites checksum-covered header fields (mGridSize, index/count, blind metadata, mVoxelSize, mMap, mGridName) after updateChecksum has run, so batch-size-1 exports of Partial-checksum grids (anything built via setChecksum(CheckMode::Default): dilate, pad, prune, merge, nearest-voxels) fail nanovdb_validate. Batches >1 are incidentally repaired by mergeGrids' updateGridCount, which is why tests pass. One line at the end of the function (mChecksum.disable(), matching the rule Advance NanoVDB pin to openvdb #2319 and adopt single-space cuda::Buffer where it now fits (#770 steps 1-2) #773 applies in LoadNanovdb.cpp) fixes it and lets the earlier updateChecksum go. Advance NanoVDB pin to openvdb #2319 and adopt single-space cuda::Buffer where it now fits (#770 steps 1-2) #773 lists it as follow-up; nothing here picks it up.
Step 4 — empty grids in the CUDA export path. Upstream IndexToGrid::getHandle launches processRootTilesKernel<<<0, 1>>> unguarded for an empty grid, and cudaCheckError calls exit(). The copyTo<HostBuffer> rewrite of SaveNanoVDB.cu does not reach this because it happens before the output buffer exists. Skip indexToGrid for numVoxelsBi == 0 and build the empty typed grid host-side. Advance NanoVDB pin to openvdb #2319 and adopt single-space cuda::Buffer where it now fits (#770 steps 1-2) #773 adds two more hand-rolled "make this header standalone" sites (LoadNanovdb.cpp, SaveNanoVDB.cu indexToGridHost), making six in fvdb that each write a different subset of {mGridIndex, mGridCount, mGridSize, mBlindMetadata*, mChecksum}.
