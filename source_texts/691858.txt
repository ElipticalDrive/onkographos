Summary
The shape diameter function loses its rays at facets that stand nearly perpendicular to a coordinate axis. A facet that loses all of its rays gets a thickness of 0. The octree then reads a false thin feature and refines around it.
This PR adds BoundingVolumeHierarchy::intersect_excluding, a nearest-hit query that skips one triangle, and uses it in the shape diameter function. intersect does not change.
On an Octa-Loop level 7 sphere (131,072 facets), the octree goes from 5 levels to 3, and the mesh from 1,415 elements to 111. The octree refined the six poles of the sphere unequally before, and it refines them alike now. The Octa-Loop level 3 mesh and a 964,568-triangle marching cubes mesh come out exactly as before.
v0.7.8 has the same defect. I checked the released crate, and it gives the same numbers.
The problem
At origin/main, each ray starts at the face centroid, and the code discards any hit on the face itself:
```
bvh.intersect(&ray, coordinates, elements)
    .filter(|hit| hit.index() != face)
    .map(|hit| (hit.distance(), weight))
```
intersect returns only the nearest hit. So the filter can only discard the ray. It cannot move on to the next hit.
The watertight ray test in intersects_triangle accepts a hit only if t > reach * REL_TOL. Here reach is the largest distance of the triangle's vertices from the ray origin along the ray's dominant axis. When a facet stands nearly perpendicular to that axis, reach is tiny, and so is the threshold. The origin is the centroid, which sits on the facet's own plane up to rounding. The test then accepts the facet's own plane at t of about 4e-17. That self-hit is the nearest hit. The filter discards it, and the real hit, 2.0 away, is never reported.

Sizing::new takes the octree depth from the smallest positive nodal value, 0.4713 here, divided by the scale. The true thickness is about 1.9. So the octree gets 5 levels where 3 suffice. The facets near the +x and -x poles carry the small targets, so the octree also refines most around them. With conspire 0.7.7, the mesh has 231 elements within 25 degrees of +x and of -x, and 39 to 40 within 25 degrees of each of the other four poles.
The defect needs small facets. A midpoint-subdivided octahedron of 32,768 facets is fine. One of 131,072 facets shows it. The facets at the poles are about 2e-3 across.
The change
BoundingVolumeHierarchy::intersect_excluding(ray, coordinates, elements, excluded) returns the nearest hit on any triangle but excluded. It shares its traversal with intersect through a small private Nearest struct, so intersect_node does not gain an argument. intersect calls the same code with nothing excluded.
shape_diameter_function calls intersect_excluding(..., face). The origin face is never a candidate, so no ray can be lost to it.
Alternatives I tried
Move the ray origin slightly inside the surface (1e-6 of an edge length). This also fixes the poles. It shifts every ray, though, and it changed the octree of a marching cubes surface, which the exclusion does not. I could not tell a correction from a perturbation, so I dropped it.
intersect_all, then skip the origin face. This works. It allocates a vector per ray and walks the whole ray, not just to the first hit.
Change the tolerance in intersects_triangle. This reaches every caller of the ray test. I did not want to change that in a PR about the shape diameter function.

The mirror mismatch is the largest distance from a mirrored node to the nearest node. This PR does not target it, and the fit asymmetry stays. #222 and #223 deal with it.
The Octa-Loop level 3 mesh does not change. The level 7 mesh changes because the shape diameter, and with it the octree, changes. It is now as coarse as the level 3 mesh, because the two surfaces ask for the same cell size. That costs some accuracy in volume. In a build that combines the three PRs, the level 7 mesh encloses 4.3067, which is 2.8% above the exact sphere. It enclosed 4.2036 before, which is 0.36% above. The extra refinement had improved the volume by accident.

Tests
intersect_excluding_finds_the_far_side_from_a_perpendicular_facet puts a small facet perpendicular to each axis, in both directions, with a far triangle behind it. At facet size 0.01 the plain intersect returns the facet itself, at t of 1.1e-16, in all six orientations. intersect_excluding returns the far triangle at distance 2 in all of them. This test fails without the change. I checked by disabling the exclusion.
intersect_excluding_matches_intersect_when_nothing_is_excluded checks that excluding another triangle changes nothing, and that excluding the nearest one returns the next. It fails with the exclusion disabled too.
rays_from_a_perpendicular_facet_are_not_lost_to_the_facet_itself runs the shape diameter function on the same scene. It guards the result. It also passes on the old code for this scene, because one ray out of 31 survives and gives a plausible thickness. I could not build a small scene that loses all 31 rays. The real case needs 131,072 facets, which is too slow for a debug build.

Reproducibility
The surface is the Octa-Loop level 7 STL from the Subdivision page of the automesh book. The investigation is written up in the Unit Sphere page, Update 4: https://github.com/autotwin/automesh/blob/dev-isosurface/book/examples/gallery/academic/unit_sphere.md
The check is short. Load the STL with Tessellation::try_from, call shape_diameter_function(FRAC_PI_4, 3, 10), and look at the values near the six poles.
Notes for review
The change adds a public method. intersect and intersect_all keep their signatures and behavior.
Any caller that relied on the old thickness near axis-aligned facets sees different sizing. The octree is the only caller I know of.
Only the origin face is excluded. A neighbor of the origin face could, in principle, show the same near-zero hit on a concave surface. The marching cubes surface has concave corners and meshes identically, so I saw no sign of it.
Related: #222 fixes ties in the fit targets, and #223 keeps the fit on mirror symmetry. #223 is stacked on #222. Both are independent of this PR.
