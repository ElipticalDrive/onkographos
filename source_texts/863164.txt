We're hitting this too, and it reproduces reliably for us. Engine 2.21.3, Firefox 153.0 on Windows 11.
Our app runs WebGPU with the renderer explicitly set to GSPLAT_RENDERER_RASTER_CPU_SORT, rendering streamed SOG LOD sets. On Firefox every splat comes out stretched into long thin streaks across the scene. Same machine, same build in Chrome (WebGPU + CPU sort) renders correctly. Switching Firefox to GPU sort also renders correctly.
We can't just use GPU sort, because for us it consistently drops far-field/environment splats on streamed SOG LOD sets (holes in the sky, same pattern every time — happy to file that separately if useful). So for now we've gated Firefox back to WebGL2, which renders fine.

Root cause found, and it's a Firefox/Windows WGSL compiler bug rather than anything specific to gaussian splats.
Filed upstream: https://bugzilla.mozilla.org/show_bug.cgi?id=2059727
A mat4x4f stored into a member of a function-scope struct is returned transposed when it's read back through ptr<function, T> in another function. Only the D3D12/HLSL backend is affected — Chrome on the same machine and Firefox on macOS (Metal) are both fine — so it looks like a row-major vs column-major mismatch in the shader translation.
Where the engine hits it: initCenter() computes modelView = matrix_view * matrix_model into a local, uses that local for the splat centres, and stores it into SplatCenter.modelView. initCornerCov() then reads it back by column to build the view basis W for the covariance projection. Because the matrix comes back transposed, W is wrong, the Jacobian (whose third column is zero, i.e. it drops depth) discards the wrong axis, flat gaussian disks project edge-on, and the 2D covariance collapses to near-rank-1 — lambda2 pins at its max(..., 0.1) floor and every splat rasterises as a ~1px-wide needle. The centres stay correct throughout because they come from the local copy, which is what made this so hard to pin down.
That also explains the rest of the symptoms: it's structural rather than numerical (forcing the covariance math to f32 is pixel-identical), it's stable and purely a function of camera orientation (the transposed matrix carries the view rotation), GPU sort is unaffected because the projector passes the view matrix as a function parameter instead of through a struct member, and WebGL2 is unaffected because GLSL has no pointers.
Note the same read pattern is used in three other places, so the SH and 2DGS paths are latently affected on this platform too — they just don't show in the reported scenes:
vert/gsplatCorner.js — W for the covariance (the reported needles)
vert/gsplat.js — SH view direction, and the 2DGS corner position
frag/gsplatCopyToWorkbuffer.js — SH direction in the work-buffer copy pass
An engine-side workaround is straightforward and doesn't depend on Mozilla shipping a fix: recompute matrix_view * matrix_model at the point of use instead of reading it back out of the struct. Confirmed on the affected machine that this makes the artifact disappear.
