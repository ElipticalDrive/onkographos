Description
Every Gaussian splat snapshot rebuild allocates four fresh staging copies of the attribute arrays (~44 bytes/splat) because GaussianSplatTextureGenerator.generateFromAttributes transfers the buffers to the worker, and the snapshot's own arrays must stay readable (sorting, hard-cap truncation). On large tilesets with a moving camera those allocations repeat until the heap fragments and rendering stops with RangeError: Array buffer allocation failed.
This keeps the copy but drops the allocations: the worker now pushes the four buffers into its return transfer list and echoes attributes in its result, and each primitive reuses a single staging set sized to its high-water splat count. Steady state allocates nothing; output is byte-identical. The set is released with the primitive, and a lost worker task (buffers transferred out, no result back) is detected via the detached buffer and simply costs one re-allocation later.
Two notes:
If the task processor is saturated (scheduleTask returns undefined), nothing was posted, so the staging set is returned to the pool and the rebuild retries as before.
This touches the same files as Optionally move WebAssembly to workers #13669; the changes are orthogonal (the copy site and the scheduleTask contract both survive that refactor), but whichever lands second will need a rebase.

Testing plan
New spec: reuses texture staging buffers across snapshot rebuilds — spies on generateFromAttributes, echoes the attributes back the way the worker does, and asserts the second rebuild reuses the first rebuild's buffers, that the staging copy neither aliases nor detaches the snapshot's arrays, and that destroy() drops the set.
Full GaussianSplatPrimitive suite passes locally (Chrome 152 / macOS).
The original crash reproduces by flying a free camera over a multi-million-splat tileset for an extended session; with this change the staging allocations flatline after the high-water mark is reached. The fix has also been soak-tested on a downstream fork rendering 4.2M-splat regions.
