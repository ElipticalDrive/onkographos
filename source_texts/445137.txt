RAY_FLAG_SKIP_TRIANGLES and RAY_FLAG_SKIP_PROCEDURAL_PRIMITIVES reach optixTrace as undefined flag bits, with no diagnostic.
Reproduction (v2026.14.1)
```
RaytracingAccelerationStructure gScene;
RWStructuredBuffer<float4> gOut;

struct Payload { float4 color; };

[shader("raygeneration")]
void rayGenMain()
{
    RayDesc ray;
    ray.Origin = float3(0, 0, 0);
    ray.Direction = float3(0, 0, 1);
    ray.TMin = 0.0f;
    ray.TMax = 1000.0f;

    Payload payload;
    payload.color = float4(0, 0, 0, 0);

    TraceRay(gScene,
             RAY_FLAG_FORCE_OPAQUE | RAY_FLAG_SKIP_PROCEDURAL_PRIMITIVES,
             0xff, 0, 1, 0, ray, payload);

    gOut[0] = payload.color;
}
```
```
slangc -target cuda -stage raygeneration -entry rayGenMain rayflags.slang
```
What happens
slangc exits 0. The flag argument is emitted verbatim, including bit 9, which OptixRayFlags does not define:
```
optixTrace(globalParams_0->gScene_0, 513U, 255U, 0U, 1U, 0U, ray_0, &payload_0);
```
513 is 0x201: RAY_FLAG_FORCE_OPAQUE (0x01) OR RAY_FLAG_SKIP_PROCEDURAL_PRIMITIVES (0x200). RAY_FLAG_SKIP_TRIANGLES on its own emits 256U, i.e. 0x100.
OptixRayFlags in optix_types.h (OptiX 9.0) defines bits 0 through 7 only:
```
OPTIX_RAY_FLAG_DISABLE_ANYHIT               = 1u << 0,   // 0x01
OPTIX_RAY_FLAG_ENFORCE_ANYHIT               = 1u << 1,   // 0x02
OPTIX_RAY_FLAG_TERMINATE_ON_FIRST_HIT       = 1u << 2,   // 0x04
OPTIX_RAY_FLAG_DISABLE_CLOSESTHIT           = 1u << 3,   // 0x08
OPTIX_RAY_FLAG_CULL_BACK_FACING_TRIANGLES   = 1u << 4,   // 0x10
OPTIX_RAY_FLAG_CULL_FRONT_FACING_TRIANGLES  = 1u << 5,   // 0x20
OPTIX_RAY_FLAG_CULL_DISABLED_ANYHIT         = 1u << 6,   // 0x40
OPTIX_RAY_FLAG_CULL_ENFORCED_ANYHIT         = 1u << 7,   // 0x80
```
The HLSL flags below 0x100 survive the pass-through only because they happen to share bit values with their OptiX counterparts.
Reproduces identically on 2026.5.2.
Expected outcome
optixTrace receives flag bits outside the range OptixRayFlags defines, and the compile succeeds, so nothing indicates it at build time.
Because the compile succeeds, the problem first appears at runtime. In one case it surfaced as a GPU fault rather than a wrong image, and the reported address reads like a null pointer dereference:
```
Invalid __global__ read of size 4 bytes
  at __raygen__rayGenMain+0xa0
  Access to 0xb6c is out of bounds
  and is 8,589,931,668 bytes before the nearest allocation
```
That sends you into resource binding and parameter layout, because the trace call compiled cleanly and reads as ordinary HLSL. The shader is valid; only the lowering is wrong. A compile-time diagnostic for ray flags with no OptiX equivalent would be far more useful than the runtime failure.

Input on the open question of how to handle RAY_FLAG_SKIP_TRIANGLES / RAY_FLAG_SKIP_PROCEDURAL_PRIMITIVES on CUDA/OptiX:
A hard error for these two flags breaks shader code shared across targets that sets the flag unconditionally. D3D12 and Vulkan honor it; on OptiX the shader is otherwise valid, and the filtering has to come from the pipeline or SBT setup instead. With an error, every such TraceRay needs a target guard.
Suggestion: on CUDA/OptiX, clear the two bits from the value passed to optixTrace, and warn when they are set in a compile-time constant. Clearing the bits also covers runtime flag values, since 0x100 and 0x200 are not defined OptixRayFlags bits. Users who want the strict behavior can use -warnings-as-errors.
On v2026.20, TraceRay with RAY_FLAG_SKIP_TRIANGLES still emits optixTrace(..., 256U, ...) with no diagnostic.
