📝 Walkthrough
The changes add a shared 8 MiB limit for LUT source text, reject oversized LUTs during import, project loading, and rendering, and update render-cache keys to distinguish built-in LUTs from library LUT text identities and formats.
Changes: LUT source handling
Layer / File(s)
Summary
Shared limit and ingestion checks
crates/project/src/lib.rs, crates/engine/src/color.rs, crates/format/src/lib.rs
Adds the public 8 MiB limit. LUT imports above the limit return an error with the path and limit. Project loading drops and logs embedded LUT entries above the limit; a test covers an entry one byte over the limit.
Render cache identity and size validation
crates/render/src/luts.rs
Uses typed cache keys for built-in IDs and library text identity plus format. Rejects oversized library LUT text. Tests cover shared versus separately allocated text identities and oversized text rejection.

Merge Risk: 🟡 Moderate · up to 16997
Large LUT imports or project files can still cause excessive memory use, and rendering many distinct LUTs can retain substantial memory after projects close. Address these bounds before merging unless that risk is explicitly accepted.
Security architecture risk: 🟡 Moderate · up to 16997
The size checks reduce oversized-LUT processing, but the new cache keys can keep approximately 520 MiB of source text alive after its project entries are released. This creates a process-level memory-pressure risk despite the per-entry limit.
Retained concerns
Medium · security · inferred: The process-global cache now owns entire accepted LUT sources rather than small hash keys. Resolving 65 near-limit sources can retain approximately 520 MiB of source text independently of project ownership, including after library removal. Valid comment-padded LUTs can have small parsed tables but large retained sources. The per-entry limit and entry-count eviction constrain this exposure, but there is no aggregate source-byte budget or project-lifecycle release; hot cache hits and failed misses do not clear it.
Security review details
Security Blast Radius
inferred — The demonstrated exposure is memory retention in the rendering process, shared across resolutions through a static cache. Triggering it requires accepted LUT sources to be successfully resolved; merely loading unused entries does not populate this cache. The inspected path establishes no additional privilege or cross-service authority.
Security Findings and Attack Paths
inferred — A crafted project can supply many accepted, near-limit LUT sources whose comments inflate text without inflating parsed tables. Successful rendering can make the global cache retain those sources after project entries are released. Unlike the base's small hash keys, 65 owning source keys can preserve approximately 520 MiB of source buffers until later eviction, creating the introduced memory-lifecycle concern.
Trust Boundaries and Controls
observed — The shared limit is enforced at import acceptance, persisted-library retention, and render resolution, including projects supplied directly to the resolver. Oversized or unsuccessfully parsed entries cannot become successful library cache entries. These are per-entry controls, not an aggregate library or cache memory budget.
Hardening Proposals
proposed — Give retained cache sources an explicit aggregate byte budget and lifecycle-aware eviction policy while preserving safe immutable identity. This would bound continued source ownership independently of project lifetime and entry count.

Enforce the LUT limit during decoding
decode deserializes EnvelopeIn before validate_loaded, and ProjectLut.text is an owned Arc<str>. An oversized LUT can therefore be materialized before retain drops it, so the new load bound does not protect against memory use proportional to the input and can still allow memory exhaustion.
Do not add a whole-project read cap. Project.luts is a per-entry Vec, so valid projects with many LUTs can exceed such a cap. Use a bounded per-entry streaming decode or preflight that skips oversized project.luts entries before creating their owned text, while preserving the remaining project and LUT entries. Apply it to both current-schema and migration load paths.
