Split out of #792, item 4 of its "What to do here" list. #956 landed items 2 and 3 (the QA oracle is now categorical) and deliberately left this one for its own decision. All line references below were read at origin/master = 8be4a476b65.
What the caveat claims
modules/gaussian_splatting/shaders/tile_binning.glsl:316-323, inside the GS_SORT_KEY_BITS == 32 branch:
CAVEAT: at >5000 splats per active tile and 256 tie values per depth bucket, birthday-collision math gives ~56% chance of at least one within-bucket tie collision per (tile, bucket) pair, so some residual flicker remains. The proper fix is rebalancing the bit budget — reducing GS_SORT_TILE_BITS (16) to 13 frees 3 bits for tie, raising tie precision to 2048 distinct values (~10% collision).
Reachability question, which comes first
Before spending an R2 change on that rebalance, the branch it describes needs to be shown reachable. What I read suggests it is not:
renderer/tile_renderer.cpp:2252-2258 — tie_bits starts at 0 and is only assigned inside if (key_config.key_bits > 32). A 32-bit key therefore always compiles with GS_SORT_TIE_BITS 0.
shaders/tile_binning.glsl:332 — the 8-bit tie packing at line 334 is guarded by #if GS_SORT_TIE_BITS > 0 && GS_SORT_DEPTH_BITS > 8. With tie_bits == 0 the #else at line 337 wins and depth_key = depth_quant, i.e. no tie-break at all on that path.
renderer/gpu_sorting_constants.h:29-31 — defaults are key_bits 64, tile_bits 32, depth_bits 32, so the shipped path is the 64-bit one at tile_binning.glsl:351-355.
shaders/compile_shaders.py:134-137 pins GS_SORT_KEY_BITS=32 together with GS_SORT_TIE_BITS=0, and the tie permutation at line 121 extends TILE_GLOBAL_SORT_DEFINES, which pins GS_SORT_KEY_BITS=64. So no shader-compile CI permutation appears to build the 32-bit tie branch either.
If that holds, the caveat and its remedy describe a branch that neither runtime nor CI compiles, and the GS_SORT_TILE_BITS 16 -> 13 rebalance would be work spent on dead code.
What to decide
Confirm or refute the reachability reading above — including whether any project-setting combination can produce key_bits <= 32 with a nonzero tie_bits.
If unreachable: the correct change is to fix or remove the misleading caveat (and decide the fate of the dead branch), not to rebalance the bit budget. Note that modules/gaussian_splatting/shaders/** is R2 by .agentic/policy.json, so even this needs the R2 deterministic + GPU evidence set.
If reachable: the original question stands — GS_SORT_TILE_BITS 16 -> 13 raises tie precision from 256 to 2048 values (~56% -> ~10% within-bucket collision) at the cost of 3 tile bits, which caps the addressable tile grid. Quantify that cap against the largest supported resolution before changing it.
Independently, bound the 64-bit path's tie precision: tile_renderer.cpp:2254-2256 derives tie_bits = MIN(16, 32 - MIN(_required_tile_bits(total_tiles), 32)), so tie precision shrinks as the tile grid grows. Confirm the worst supported resolution / tile-size combination still leaves enough distinct tie values for the determinism claim the QA scene now asserts.
Carry over the leftover half of The equal-depth tie-break order is unwritten: QA can detect a change but not a wrong answer #792 item 1: that issue asked for the equal-depth contract to be documented next to the key packing. The traced contract — equal depths sort by ascending global index, the rasterizer traverses the sorted range from index zero upward, and front-to-back remaining-alpha accumulation gives index 0 priority — currently lives only in tests/examples/godot/test_project/scenes/qa/qa_sort_tie_breaker.gd:13-24. A pointer beside tile_binning.glsl:334 and :351-355 is comment-only but still R2 by path, so it should ride along with whichever change above already pays the R2 evidence cost rather than becoming its own PR.
Out of scope
Do not re-pin, relax, or remove the QA baseline, the asserted winner, or the 5.0 / 255.0 margin floor landed by #956. Those are the guard that makes a wrong tie-break order fail.
