The approach I use in my game is to split a model into 'sub models' based on the faces orientation.
A cube block would have six quadratic (two triangles making a square) sub models for up, forward, left, etc.. Then, as I loop over a chunk of voxels, I merge the appropriate models (with an offset based on the blocks position) into a single mesh for the chunk.
More detailed models like stairs, leaves, torches, etc., can write in their own sub models with custom rules for when to render. Stairs, for example, have a quadratic backside and bottom, but the 'steps' sub model is always rendered due to not being flush with the bounds of the voxel.
As a bonus, sub models can do things besides adding to the chunks mesh. Torches can add a light/particle source to the chunk, and doors spawn an animated game object that replaces their model during their opening animation. These extra functionalities are triggered when specific sub models are triggered by the renderer.

Given that you're doing 6 sided block version of voxels, here's 2 ways about going for it and it depends on how much variation your cells have from each other:
-Create a model for each permutation of faces (64 in total assuming it's a 6 sided voxel) and put them in a fast look up table. When a cell determines what faces it needs, it can then generate the id and then just request the mesh. I'd do the ids for this using bit-wise flags so it can be fast.
-Create variations of the triangle list of the mesh that you have. Depending upon what type of system you're using to manage it, you likely have a triangle list (ids that say what order to render vertexes) associated with it. You could reference the same vertex data that you'd have for one block and simply just change what triangle list you give it that matches the visible faces. This list could also be precalculated as there would only be 64 possible variations given 6 faces, and use a similar look up table as mentioned above.
The key thing is to minimize how much work is needed per block. The precomputing of the table data and then just using look ups makes it so there's very little work to be done. Avoid allocating as much as possible and preallocate instead.

How many vertices does your model have? Voxel games usually don’t go for very detailed blocks, but I’ve seen a few that do (e.g. Eco.) If you can settle for low detail (I.e. two triangles per face), then your rendering will undoubtedly go much faster. Otherwise, I suppose you could instance your detailed block, and maybe go low detail for chunks at a further distance. In any case, you’ll want that model to be fairly low detail, or possibly have different LODs of the model used at different distances.
You may consider having different models for different block adjacency cases - this would greatly reduce your vertex count and look more seamless, at the cost of implementation complexity and more instanced draws per chunk. It’s likely you’ll need to create these models yourself, or pay someone to do it, however. (Could be a fun project, though!)
Checklist:
Code is GPU bound. If you’re CPU bound, you’re probably doing something wrong.
Meshes only contain visible blocks
Chunks outside the viewing frustum are culled
Meshes are submitted to the GPU once, not every frame
Mesh updates are not interspersed with mesh draws. This gives the GPU time to receive the mesh before rendering with it, thus avoiding a “pipeline stall.” This means the CPU is stuck waiting on the GPU.
