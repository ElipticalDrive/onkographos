Abstract
ANARI is a Khronos standard API for describing renderable scenes to rendering engines, allowing applications to access advanced rendering functionality without embedding a renderer-specific integration. As ANARI adoption grows among 3D applications across various domains, new users need a practical path from the specification-level object model to working application code. This course provides that path through a sequence of complete, self-contained C API checkpoints. Students begin with rendering a single triangle to a PNG, then progressively build up to an interactive application. The course emphasizes the transferable skills around ANARI mental model: devices create and configure objects, worlds contain scene objects, frames connect renderer, camera, world, ultimately for applications consume rendered pixels through frame mapping output channels. By the end of the course, students have a concrete understanding of how ANARI works and the skills to bring it to their own applications and use cases.
The skills acquired from this course give students the ability to render various kinds of scenes using ANARI, such as these shown above: (left) car [Wire Wheels Club 2020] rendered with Cycles [Amstutz 2024; Blender 2011], (middle) bathroom scene [PBRT-v4 Scenes 2023] rendered with OSPRay [Intel Corporation 2016], and (right) cloud [Walt Disney Animation Studios 2017] rendered with Barney [NVIDIA Corporation 2025]. Applications can trivially mix-and-match scene and renderer without changing any code.
1 Introduction
Modern 3D applications increasingly need high-quality rendering, interactive exploration, and portability across hardware platforms and rendering engines. Low-level graphics and ray tracing APIs provide powerful building blocks, but they require application developers to manage substantial rendering infrastructure before they can display a 3D scene. ANARI addresses this gap by standardizing a higher-level scene description API: the application builds and updates an in-memory object hierarchy for a frame, while an ANARI implementation is responsible for rendering that description [The Khronos Group 2023a; 2023b].
This course introduces ANARI from the perspective of an application developer who wants to use a renderer rather than implement one from scratch. It is designed for students with no prior ANARI experience, including graphics programmers, visualization tool developers, researchers, and students who need a compact starting point into the API. The course is also intended to be useful as a fully self-contained and self-paced resource after SIGGRAPH, so the supporting repository is organized as a set of complete, readable checkpoints rather than as partial live-coding fragments.
The central goal is for students to leave with a working mental model of the way ANARI works (i.e., the types of ANARI Objects a user can create, and how they interact); and a small but fully functional ANARI based model viewer they can use as a template or starting point for their own ANARI applications. One common issue with learning APIs that offer lots of different functionality is students getting overwhelmed, and struggling to understand where to start. To address this we intentionally decided to not provide a single large example, but instead, to split this course into multiple smaller steps that build on each other. We start this with the simplest possible ANARI example; then each additional step adds one new application capability while preserving the same ANARI concepts: objects are configured with named parameters, committed before use, connected through typed relationships, and eventually rendered into a frame whose pixels can be mapped by the application.
2 Course Structure
The 90-minute course begins with a short primer on ANARI API basics before moving into eight code checkpoints and an extensions discussion. This opening mental-model module establishes the API model: an ANARI library creates a device, then the device creates and configures geometry, material, surface, world, camera, renderer, and frame objects. Students also see the basic render lifecycle:
```
anariRenderFrame(device, frame)
 anariFrameReady(device, frame, )
 pixels = anariMapFrame(device, frame, )
 consume(pixels)
 anariUnmapFrame(device, frame, )
```
The first checkpoint, Render Your First Triangle, renders a vertex-colored triangle to a PNG file. This familiar graphics milestone is used to teach the complete ANARI path with minimal application infrastructure: loading a library, creating a device, configuring triangle geometry with mapped arrays, assigning a required matte material, connecting the surface to a world, and rendering one RGBA color channel. PNG writing is intentionally treated as an output adapter, not as the lesson.
The second and third checkpoints move from a single primitive to a small scene and then to shared scene data. Build A Small Scene introduces multiple surfaces into one world by rendering a colored box on a floor, using per-vertex color for one material and a constant material color for the other. Instance The Cube moves the cube surface into an ANARI group, creates several transform instances that share that group, and combines the floor through world.surface with the cubes through world.instance. This introduces instancing as a compact extension of the same object graph instead of a separate application pattern.
The fourth checkpoint, Control The Image And Camera, exposes output resolution and camera aspect ratio as explicit parameters. This prepares students for later resize handling while keeping the camera hard-coded long enough for the object model to remain the focus.
The next three checkpoints transition from offline rendering into an interactive viewer and then into imported scene content. Put ANARI Pixels In A Window keeps the same scene and render path but copies mapped frame pixels into a fixed-size window. This demonstrates that ANARI still renders into a frame; only the application’s pixel destination has changed. Connect Interaction To The Camera then adds an application-side orbit manipulator. The course uses ANARI world bounds to initialize the manipulator, converts its output into ANARI camera parameters, commits the updated camera, and renders another frame. Load An Asset replaces the hard-coded course scene with a loader boundary that returns an ANARI world. This keeps the viewer independent from scene import code and gives students a more general path for bringing external assets into the same rendering loop.
The final checkpoint, Turn It Into An Extensible Viewer, places the same rendering model and asset-loading boundary inside a GLFW and ImGui application shell. It adds framebuffer resize handling, texture upload, non-blocking frame readiness polling, and user interface controls for renderer parameters. This checkpoint is the course’s bridge from tutorial examples to a reusable application starting point: students can add lights, load different scene data, expose device-specific controls through capability discovery, or factor repeated code into their own application architecture.
Lastly, the course ends with a brief discussion on where students can continue their journey with ANARI. Various demonstrations of more complete, production-class ANARI applications strives to give ideas and inspiration for where to go next.
3 Teaching Approach
The course is intentionally incremental. ANARI has a compact object model, but new users must learn several ideas at once: device-mediated object creation, named parameters, explicit commits, array parameters for scene data, reference-counted lifetimes, asynchronous frames, and mapped output channels. Presenting these concepts through one large viewer would obscure which code is ANARI-specific and which code belongs to the surrounding application. The checkpoint sequence keeps that boundary visible.
Several design choices support this goal. The course begins with the ANARI C API because it is the common foundation for the standard and makes object lifetime, handles, and commits explicit. C++ wrappers and application abstractions are deferred until students understand the underlying model. The early examples use blocking ANARI_WAIT rendering so that frame lifecycle is easy to read; non-blocking polling is introduced only in the final viewer, where responsiveness motivates the added complexity. The examples also duplicate small amounts of ANARI setup code across checkpoints. This is a deliberate teaching tradeoff: each checkpoint remains complete and readable in isolation, which is valuable for recorded and self-paced use.
The scene content is similarly constrained. After the introductory triangle, the course uses the same box-and-floor scene through the first interactive camera checkpoint. That continuity makes each new application feature easier to isolate. The later asset-loading checkpoint then changes how scene content enters the application without changing the rendering model. Students can see that window display, camera interaction, asset loading, resizing, and UI controls do not require a different rendering architecture; they require updates to, or replacement of, the same ANARI objects and parameters.
4 Expected Outcomes
After completing the course, students should be able to create a basic ANARI device, build geometry and materials, assemble surfaces into a world, configure a camera and renderer, render a frame, and consume the resulting color channel. They should also understand where ANARI stops and application code begins: window systems, UI toolkits, camera manipulators, file formats, and scene loaders remain application choices that feed or consume ANARI objects.
The final viewer is intentionally modest, but it is not a throwaway example. It contains the essential loop used by many interactive rendering applications: process input, update application state, commit changed ANARI objects, request or poll a frame, map completed pixels, and display the latest result. That structure gives students a practical base for experimenting with explicit lights, additional asset loading, renderer-specific parameters, capability queries, and larger application designs.
5 Conclusion
ANARI gives 3D applications a portable, renderer-neutral way to describe scenes and request rendered images. This course lowers the barrier to using that standard by connecting its object model to complete working programs in small, inspectable steps. Rather than surveying every feature of the API, the course teaches the core habits students need to continue independently: construct objects through a device, set parameters, commit changes, connect the object graph, render frames, and decide how the surrounding application should use the resulting pixels.
