Geometry materials whose shader is one of the presets copied from the base game (InterscopeConcrete,
BillieWater, WaterfallMirror, ...) keep the game material's enableInstancing = false. Chroma's own presets
(Standard, OpaqueLight, TransparentLight, Glowing, BaseWater) are already created with
enableInstancing = true in InstantiateMaterialFromShader. So every geometry object with a copied material is
its own draw call, in every camera pass that draws it: the eye pass, the camera depth texture (smoke), and the
mirror.
This PR sets enableInstancing = true on the material copy that MaterialsManager.CreateMaterialInfo makes
anyway (one line). The shader, its keywords and properties are unchanged; Unity just draws objects that share
mesh and material with one instanced draw call instead of one call each. Every geometry material goes through
CreateMaterialInfo (named materials and inline ones), and the copy is Chroma's own, so the game's original
materials (and environment objects that use them) are not touched.
Why it matters
Draw calls are expensive on tile-based GPUs (standalone headsets, and PC VR on mobile chips): the frame is
rendered in screen tiles ("bins"), and the command stream is replayed for every bin, so each draw's setup is
paid again in every bin it touches. A few hundred extra draws that a desktop GPU hardly notices cost
milliseconds there.

native ARM64 via bs-arm64, Chroma 2.9.23 from dev), 2736² per eye, 72 Hz, floor mirror on, headset still (pinned pose),
30 s per run, game GPU time from the kernel's per-client DRM counters:

Same image
Instancing changes how draws are submitted, not what is drawn, and I checked that with a frozen frame: a test
harness stops the level at 1:10 of A Cookie From Space (song time paused, Time.timeScale = 0, the per-frame
dithering random value and the notes held), then captures both eyes' full-resolution XR eye textures
(2736×2736 each) and the mirror's reflection texture (3240×1620), with these materials' enableInstancing off,
off, on, on, off (several frames apart). All shots are bit-identical (max abs difference 0, every pixel),
while the GPU time of that same frozen frame drops from 19.8–20.2 to 15.95 ms/frame while instancing is on. The
same comparison on a copy of the map with added rows of cubes and spheres using BTSPillar, BillieWater (light
geometry with light IDs and ParametricBoxController property blocks), InterscopeCar, InterscopeConcrete
and WaterfallMirror, looking straight ahead and 30° down at the mirror, is also bit-identical. (In that build
the materials with instancing off were Concrete2, WaterfallMirror and WaterfallFalling; BTSPillar's and
InterscopeCar's game materials already have it on.) With this PR, no geometry material has instancing off.
Risks considered
Per-renderer MaterialPropertyBlocks (light-type geometry: ParametricBoxController sets _Color,
_AlphaStart/_AlphaEnd and widths per renderer). Light presets already had instancing on, so this only
changes BillieWater. It is in the frozen-frame test (eight objects with different sizes, hence different
width properties, and different light IDs), bit-identical; in that frame those lights were dark, so differing
colours in the blocks were not exercised.
Lightmaps / light and reflection probes: geometry is created at runtime and has no baked lightmap; probe
data is per renderer, and Unity batches only renderers whose per-instance data it can carry. No difference in
the test (the copied Concrete2 uses the game's own LIGHTMAP/REFLECTION_PROBE keywords).
Shaders without instancing variants fall back to normal draws; nothing breaks.
Draw order among identical mesh+material objects could change; they have the same shader and colour, so
only exact coplanar overlaps could show it, and none showed in the test.
Older game versions: the copy is made the same way on every supported version (PRE_V1_37_1 included), so
the game's own materials are never modified.
Tested on 1.44.1 only (the device above); built with Release-1.44.1.
