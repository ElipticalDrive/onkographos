# Encoding Occupancy in Memory Location for Efficient and Compact High-Resolution Voxel Structures

Jaina Modisett and Markus Billeter

School of Computer Science, University of Leeds, Leeds, UK {sc22jm, m.billeter}@leeds.ac.uk

#### Abstract

Compressed voxel structures make it possible to store, interact with and display detailed and complex geometry. The Sparse Voxel DAG (directed acyclic graph) is such a compressed representation that supports real-time rendering and interactive editing of high-resolution voxel geometry. We present a novel encoding of the Sparse Voxel DAG that utilises the memory location of data to encode information about the structure of the voxel geometry. This encoding is not only more compact but also makes it possible to avoid memory accesses. In turn, this improves traversal performance, which we can observe in terms of increased ray tracing speed. Our new encoding retains compatibility with other existing methods. We demonstrate an adaption to the HashDAG data structure and show that our proposed encoding also results in better editing speed at similar memory requirements in this framework. Further, we demonstrate its compatibility with existing methods for storing voxel attributes such as colours.

Keywords: hierarchical structure, octree, ray tracing, sparse voxel DAG, SVDAG, volumetric model

#### 1. Introduction

There is an increased need to handle highly detailed and large 3D scenes. Compressed voxel structures provide a compelling alternative for representing such data. Voxels represent 3D data as a regular grid, where each cell encodes information about the space it occupies. The regular structure has several advantages, including, for example, supporting easy manipulation of 3D data. However, when stored naively, voxels suffer from cubic scaling in size with respect to their resolution. Compressed voxel representations provide a way to overcome this problem. Hierarchical representations can exploit sparsity to achieve significant reductions in data size, while maintaining the ability to render their contents without requiring an explicit decompression step [CNLE09, GMIG08, LK10].

Extending this approach, Kämpe et al. [KSA13] introduce the sparse voxel directed acyclic graph (SVDAG), which additionally uses similarity to reduce the size even further. The authors demonstrate the ability to store and render voxel geometry of resolutions as high as (128*k*) 3 in real time. Their implementation transforms a sparse voxel octree [Mea82] into a directed graph by finding identical nodes in the tree and replacing them with a single unique instance. This requires a pointer-based representation. Each of the nodes in their graph structure store a mask representing the geometric structure of the node, followed by a number of pointers to nodes on the next finer level of detail. The original implementation only considers binary static geometry. It is later extended to support attributes such as colours [Wil15, DKB\\*16, DSKA17] and the ability to interactively edit the compressed data directly [CBE20, ME23, ME24]. Nevertheless, throughout these advancements, the representation of the SVDAG nodes with a (padded) child mask and a set of pointers has remained fundamentally unchanged.

In this paper, we present and evaluate a novel representation for the SVDAG nodes that is both more compact and performant than existing approaches. Our new encoding utilises the memory location of nodes to carry data about their internal geometric structure and thereby eliminates the need for an explicit mask to define the node's geometric structure (Figure 1\). This approach not only reduces the size of the geometric data by 13%–18% compared to the SVDAG [KSA13], but also improves rendering time by around 10%–12% for static models and by up to 20%–25% for editable voxel models. We show that the new representation is compatible with many existing methods, specifically demonstrating its use with colour attributes and with dynamic editing of the structure. We further demonstrate that other methods, for example, for editing, benefit from our novel encoding through its more compact nature.

# 2. Related Work

While voxel representations afford many benefits, naively storing these presents a cubic scaling in size with increasing resolution. Exploiting sparsity in voxel data has proven highly effective in reducing the memory requirements. Sparse voxel octrees (SVOs) [Mea82] represent each voxel as a binary value, filled or empty. These form the leaves in an octree [Mea80]. Interior, that is, non-leaf, nodes in the octree exploit sparsity by omitting pointers to fully empty children. SVOs can be traversed in place as they are, meaning they can be rendered directly by ray tracing against their hierarchical structure [LK10]. This has been utilised in many methods, including for 3D reconstruction [ZZZL13], for indirect illumination [CNS\\*11], and for cases where the SVO is too large to fit in memory [CNLE09, CNSE10, RN24].

# 2.1. Sparse Voxel Directed Acyclic Graphs

SVDAGs exploit similarity in addition to sparsity. Kämpe et al. [KSA13] identified subtrees that encode identical geometry and de-duplicate these, reducing them to a single instance in memory. Pointers in the structure point to this single shared instance, transforming the data structure from a tree into a directed acyclic graph (DAG). In their implementation, each node in the SVDAG contains an 8-bit mask, the child mask, describing which of its eight possible child nodes exist, followed by up to eight child pointers, one for each active child. While only requiring eight bits, the child mask is commonly padded to occupy 32 bits, the same size as the pointers in the structure, to maintain memory alignment. The last two levels depart from this coding, and are instead built from a set of 64-bit leaf bricks, representing a 43 voxel volume. This is more efficient than storing two to nine 32-bit words for the node on the second last level, plus up to eight 8-bit child masks for the finest level. Kämpe et al. showed that the SVDAG scales extremely well, demonstrating reductions in node count of up to 576× in their comparisons to SVOs.

Later work improves compression rates further. Van der Laan et al. [vdLSE20] considered a lossy compression scheme, where the underlying voxel geometry is minimally modified to generate more matching subtrees. Villanueva and colleagues' symmetry-aware SVDAGs [VMG16, VMG17], find structures that are transforms of each other (e.g., mirrored versions) and deduplicate these as well. The transformation is encoded in the top bits of the child pointers in each node. Villanueva et al. additionally explored pointer compression, where common pointers are stored at lower addresses and encoded with fewer bits in the data structure. Molenaar and Eisemann [ME25] expanded on this work with their transformation-aware method. In addition to symmetry-based transformations, they introduced translation and permutation of the axes for subtrees. The transformation data is stored alongside child pointers in their implementation. To keep the increased per-node data compact, they also compress pointer data, resulting in variable length elements in each node. Kämpe et al. [KRB\\*16] used variable pointer sizes to serialise time-varying voxel data. This results in an SVDAG structure with multiple root nodes, one for each frame of animation. Common subtrees are de-duplicated across all animation steps. In their work, Kämpe et al. decompressed the variable size pointers into fixed sizes during loading, which minimises storage size while permitting efficient rendering.

Careil et al. [CBE20] extended the SVDAG to a dynamic structure that can be edited interactively. Their HashDAG embeds the directed acyclic graph into a hash table. The hash of a node is computed from its contents, meaning that identical nodes will receive the same hash. With this, it is possible to efficiently find an existing node. Editing utilises this by forming nodes bottom-up: first, a leaf node is computed, then the method searches for it in the existing data. If found, the existing leaf is reused and passed on to the next higher level. Otherwise, a new leaf is inserted into the table, and then passed to the next higher level. The next higher level collects all nodes from the leaf level, constructs its nodes, and then checks for the node's existence. This process repeats up until it creates a new root node, representing the edited version of the geometry. The HashDAG uses a fixed-size table, large enough to accommodate both the original data and future edits. To support this large static table, the method utilises a virtual memory scheme. This is the only aspect that affects rendering of the HashDAG: following a pointer in the HashDAG requires a virtual memory translation step. The HashDAG implementation performs edits on the CPU. Molenaar and Eisemann later demonstrated editing on the GPU [ME24]. Their approach uses dynamic hash tables optimised for parallel processing on the GPU, based on the Slab Hash [AFCO18]. The implementation uses a separate hash table for each node size, meaning that nodes of the same size are stored together. This simplifies some operations on the data as the size of each node is fixed within each table, rather than varying between two and nine words in length.

The high compression rates of the SVDAG have resulted in its use in different applications. Molenaar and Eisemann improved ray batching ray-tracing using SVDAGs as proxy geometry [ME20]. Several approaches use SVDAGs to store highly-detailed shadowmaps [SKOA14, KSA15, SE22]. Werner et al. used SVDAGs in a hybrid BVH-approach for storing finer geometry of segmentation volumes [WPD24]. Fang et al. [FWW25] presented the Aokana framework for rendering open worlds. They divide the scene into chunks and introduce support for different levels of detail (LOD) by pre-computing LODs for the chunks. Different LODs are streamed into VRAM as needed, to control total memory use.

### 2.2. Memory Efficient Hierarchies

Efficient hierarchical structures are widely researched. In particular, both optimising memory size and reducing the amount of memory accesses are crucial to performance in acceleration structures [YM06, Gut14]. To increase efficiency, BVHs embed information about bounding boxes of the children in the parent nodes [YH23]. For example, Ylitie et al. [YKL17] introduced an eight-wide bounding volume hierarchy (BVH) with a compressed node representation, demonstrating the importance of memory efficiency and child ordering to traversal performance. This makes it possible to perform intersection tests against the children without accessing the child node data, which is often elsewhere in memory. Our encoding enables a similar optimisation. By keeping the information about the children of an octree node in its memory location, we can perform intersection tests with a node's grandchildren based on the child pointers stored in the node.

#### 2.3. Voxel Attributes

SVDAGs are particularly well suited to compressing binary voxel geometry. To support attributes, such as per-voxel colours, a mechanism of associating extra attributes independent of the underlying geometry to each voxel must be found. Multiple approaches exist. The most popular ones identify voxels uniquely by how they are reached through the SVDAG structure. Dado et al. [DKB\\*16] and Williams [Wil15] each introduced methods of calculating a unique index for each voxel by introducing additional data to pointers within the structure. Dado et al. stored each child node's offset from its parent in terms of what index a depth-first search would assign each when traversing the equivalent SVO. Williams' MoxelDAGs store counts of empty voxels within each subtree, calculating each voxel's index as if it was in a filled octree, then subtracting the total empty voxels in proceeding subtrees. Dolonius et al. [DSKA17] take a different approach, and store values with each node rather than each pointer, making their implementation significantly more memory efficient. They store the size of each subtree in each node, allowing counts of preceeding nodes to be summed as they traverse the structure. Furthermore, they are able to utilise the 24 bits of padding around the child mask in the original SVDAG to store most of the counts; counts for levels closer to the root may exceed the 24 bits and are instead stored in an external 64-bit count table. Dolonius et al. and Dado et al. both explored compressing the attribute data itself for use with SVDAGs. Nevertheless, per-voxel colours still use more memory than the SVDAG structure itself.

The HashDAG [CBE20] supports editing of the colour data, but uses a naive CPU-based colour compression method. Molenaar and Eisemann [ME23] improved this and introduce two methods, a lossy and a lossless one, for interactively compressing colour data during editing. Their lossless method is GPU accelerated. Later, in their GPU-editing implementation [ME24], Molenaar et al. additionally introduced material information into the SVDAG nodes, showing a trade-off that increases node size and decreases SVDAG compression rates, in return for much simpler voxel and material editing.

### 2.4. Encoding Information in Location

Our approach encodes information in the memory location of nodes. Conceptually, this bears some similarity to the work of Peters et al. [PKM22]. Their approach encodes information into the ordering, that is, the relative location, of vertex blend weights, to further compress mesh data.

# 3. Encoding Node Occupancy in Memory Location

The SVDAG is a pointer-based structure, where a parent node contains pointers to its children. To traverse the structure, one follows these pointers. The encoding of the pointers themselves depends on the application. A common encoding uses fixed-sized indices, typically 32 bits. Traditionally, the value of a pointer only depends on where in memory the target node was placed during construction. Nevertheless, the memory location of a node, and therefore its pointer value, is arbitrary. We can rearrange nodes as long as we update the corresponding pointers accordingly. The HashDAG [CBE20] data structure uses this property to locate nodes such that they can be found efficiently based on their contents.



Figure 2: Our method encodes a voxel grid (bottom left) hierarchically as a sparse directed acyclic graph (middle). In this example, the root node (blue) contains three children. It is stored in table 0xB as the first entry 0xB000 (right hand side of the figure). Here, 1011 = 0xB describes the structure of the node's contents. The node contains a pointer for each of its children (green level). The topmost bits of the pointers encode the geometry of the node they point to (yellow level). Therefore, when processing the node at the blue level, we can inspect the pointers (green level) and check if there is an intersection with the target node (yellow level). This is done without following the pointer and reading the memory. We only need to follow the pointer (to the green level) if we know that we intersect with any of its children (yellow level).

We propose to use the location of a node to additionally carry data about the node itself. Specifically, we encode the node's child mask in its location, and thereby in its pointer. Consequently, knowing a node's pointer means that we also know its child mask. It is therefore possible to perform computations on the node, such as intersection tests, without incurring additional memory fetches, as all the required information is encoded in the pointer. In practice, we arrange pointers such that the child mask occupies the topmost eight bits in the pointer (Figure 1\). A child mask c can be recovered by shifting a pointer p to the right:

$$c = p \gg 24$$
. (1)

Importantly, the pointers remain full 32 bits in length, meaning that the child mask forms a part of the pointer. Consequently, the two pointers p*0 and *p*1 refer to different nodes if *c*0 = *c*1 with *c*0 = *p*0 *>> 24 and c*1 = *p*1 *>> 24, even if they share the same lower 24 bits. If this were not the case, we would be limited to 224 unique pointers, which is insufficient for many sparse voxel scenes.

Nodes with the same configuration of children, and thus the same size, end up in compact ranges. This makes operations such as iterating over nodes more efficient [ME24]. Additionally, nodes no longer need to store their own child mask, meaning they need only contain pointers to their children. Further, we can identify nodes by a node index in each range, rather than the node's starting address (Figure 2). This makes it possible to support even larger models with more nodes using the same 32-bit pointer size.

This encoding has additional advantages. First, we reduce the number of memory loads during traversal, as we do not need to follow a pointer to get a node's child configuration. This improves performance. Second, we no longer need to store child masks explicitly, making the structure even more compact. The latter eliminates problems with alignment, where 32-bit pointers would be aligned differently from the 8-bit child mask without padding.

While leaf bricks store a full 43 subvolume with no separate child mask, they still benefit from our encoding. The pointer to the leaf brick carries the geometric configuration of the upper level of the leaf brick, meaning we can perform intersections against this upper 23 level before loading the leaf brick's data from memory.

We present two variants of our location-aware encoding. The first one considers the traditional SVDAG structure [KSA13], which provides efficient storage for static geometry. Second, we adapt the idea to the HashDAG structure, which enables interactive editing of the voxel data. After this, we discuss the methods in the context of additional voxel attributes such as colours [DSKA17].

### 3.1. Static Geometry

Including the child mask in the topmost bits of a pointer means that we have pointers across the whole 32-bit address space. We could solve this with a virtual memory scheme similar to the one used with the HashDAG. However, in the case of static geometry, there is a simpler solution. Interior nodes and leaf bricks are separately grouped by their child mask. Only nodes with one or more children exist, meaning these form 2 × 255 = 510 unique groups of nodes. We store the groups of nodes in a compact array, starting with all leaf bricks, followed by all interior nodes. We introduce two 256 word segment offset tables B and T that store the starting location of each group in this array for the leaf bricks and interior nodes, respectively. Given a pointer p to an interior node, we can find the node's starting location a inside the array as

$$a = \mathcal{T}[c] + \text{popcount}(c) \cdot (p \% 2^{24}), \quad (2)$$

where c is the child mask (calculated with Equation 1). The popcount counts the number of set bits in the child mask, which determines the number of child pointers in, and hence the size of, the node. The lookup is illustrated in Figure 3. Leaf bricks are decoded similarly, using table B and a fixed size of 2, since all leaf

bricks are exactly two 32-bit words in size:

$$a = \mathcal{B}[c] + 2 (p \% 2^{24}). \quad (3)$$

For simpler models with less than 224 leaf bricks, it is possible to omit the table B and simply store all leaf bricks in a single segment. This segment can be placed at the beginning of the node array, simplifying the computation of their address to masking the top eight bits and multiplying by two.

With this approach, the offset tables T and B are of fixed size and always use 256 32-bit words, regardless of the size of the voxel structure. Although each access to a node requires an indirection through one of these offset tables, they are small (2 KiB together), and are therefore likely to be cached efficiently during traversal.

#### 3.2. Extending to Editable Geometry

The HashDAG [CBE20] places nodes in a hash table. This makes it possible to efficiently check if a certain node already exists, and, if so, find it. This is important during editing where nodes are created as part of the editing process and must be efficiently de-duplicated. A node's location is derived from the level it is at in the DAG; a hash of its contents, specifically its child mask and its pointers; and an offset into a bucket determined by the level and hash. Buckets contain multiple nodes. The offset disambiguates nodes that fall into the same bucket (i.e., nodes at the same level, with the same hash).

We adapt the HashDAG method to our encoding by changing the way a node's location is computed. We embed the node's child mask in the topmost eight bits of the pointer as before. The hash of the node, specifically of its child pointers, form the next set of bits in the pointer. The final bits identify a node index i inside the hash table's bucket. Hence, a virtual pointer p is formed as

$$p = (c \ll 24) \mid H_n(q_0, \dots, q_j) \mid i. \quad (4)$$

The child mask c and the hash Hn together identify a bucket in the hash table. The hash function Hn hashes one to eight child pointers qj and returns n bits following the child mask (bit 24 and down):

Hn(x) = (hash(x) %2*n* ) << (24 − n). (5)

Figure 4: The pages used by the HashDAG structure (top) are allocated one at a time and store nodes of varying sizes. This can leave gaps at the ends of pages as nodes are not permitted to span across multiple pages. Subtree counts are stored in the top 24 bits of each node. Our pages (bottom) are allocated in sets of N pages. N is the number of children in the node plus optional space for extra data such as subtree counts (Section 3.3). The above example shows a nearly full page set, storing nodes of size three, each with an associated 32-bit subtree count.

In practice, we let n vary based on the child mask, as some child configurations are more common than others. We use the same underlying hash function, MurmurHash3 [App16], as the HashDAG implementation. Similar to the static variant, our approach guarantees that each bucket in the hash table contains nodes of equal size. As shown by Molenaar et al. [ME24], we use this to optimise linear searches for nodes inside a bucket.

Like the HashDAG, we also employ a virtual memory scheme to translate virtual pointers into an actual location inside a memory pool for our editable variant. Similar to our static variant, we utilise two page tables: one for interior nodes and one for leaf bricks. In our scheme, an interior node's address a is calculated as

a = P[p >> s] + popcount(c) · (p %2*s* ), (6)

where P is the page table for interior nodes with page size s. The pages of both page tables are of size s. Here we introduce another small optimisation. Nodes with uneven child counts would potentially span across multiple pages. The HashDAG moves them to the next page, leaving small unoccupied spaces in each bucket. We instead always allocate a page set of popcount(c) consecutive pages for each page table entry. While a node may span across a page boundary, it is guaranteed to be contained in the page set. Figure 4 compares the HashDAG's page layout and our page layout. Leaf bricks have a fixed size of two 32-bit words, making their address calculation simpler:

$$a' = \mathcal{P}[p \gg s] + 2(p \% 2^s). \quad (7)$$

The page set for leaf bricks is similarly fixed to two pages.

# 3.3. Voxel Attributes

To support per-voxel attributes, we need to be able to uniquely identify voxels in the scene. We follow the overall approach from Dolonius et al. [DSKA17]. Here, each node in the SVDAG stores the total number of leaf voxels in its subtree. To determine the unique index of a specific voxel in the scene, the SVDAG is traversed from root to the specific voxel, accumulating the voxel counts of preceeding sibling nodes in each level. To facilitate this, a specific ordering of children in a node is required, which normally just matches the storage order. We refer to the paper by Dolonius et al. for a more detailed description of the method. However, unlike them, we are not able to use the extra padding around child masks in the existing SVDAG structure to store nodes' subtree voxel counts. We instead store the counts out of the DAG structure, in a completely separate array (static variant) or in separate pages (dynamic variant).

For the static variant, we can simply use an additional segment offset table T , which stores offsets into a separate array with the counts. Looking up a count based on a voxel pointer is similar to the lookup in Section 3.1, except that all counts have the same size:

$$a = \mathcal{T}[c] + (p \% 2^{24}). \quad (8)$$

We could easily extend this to support additional geometrydependent data without affecting the main DAG structure by introducing additional offset tables. The editable variant could follow a similar approach, with an additional page table for each additional set of data. However, the page tables are comparatively large (e.g., 64 MiB for a page size of 256 words), and we therefore devise a method to avoid the additional page tables, but without extending the nodes to include the additional data. In this scheme, when allocating pages to a page table entry, we can simply insert one or more extra pages for the additional data before the pages for the node data (see Figure 4\). For this to work, the amount of storage required for the additional data must be known up-front when first constructing the DAG. However, it is possible to combine both methods. For example, subtree counts, which are commonly required, could use this scheme, while other less common data could use a separate page table and thereby be kept in separate storage.

Keeping additional data out of the nodes is also advantageous during editing. The linear searches inside each bucket are typically memory bound. Increasing the node size would therefore impact editing performance negatively.

#### 3.4. Traversal

The traversal of the DAG does not change significantly with our method. The presentations by Assarsson et al. [ABD\\*18] covered the method for ray tracing an SVDAG in some detail; it is based on earlier work for rendering SVOs [LK10]. The main advantage of our method is the ability to perform intersection tests directly with a child pointer, before loading data from the pointer. For example, while processing a node at level N (e.g., the blue level in Figure 2\) that contains pointers to level N + 1 (green level), we can already perform intersection tests with the geometry at level N + 2 (yellow level geometry), before loading any data from the nodes at levels N + 1 and N + 2.

The other change that our encoding requires is the introduction of address translations when following a child pointer, similar to those required by the HashDAG. We can avoid repeated address translations by storing the translated address on the stack used during traversal (rather than the virtual address).

#### 4. Results

We evaluate our proposed encodings with a prototype implementation. Our prototype further implements existing methods for comparison. Aside from an evaluation of traversal performance in the context of ray tracing (Section 4.1), we also include tests with dynamic editing (Section 4.2\) and voxel attributes (Section 4.3\), to show that these are feasible in our proposed encoding without significant performance overheads (and, in fact, often with better performance). We ran all measurements on an Intel Core i7- 12700K with 32GB of DDR5 memory clocked at 4800 MT/s and an NVIDIA GeForce RTX 4080 Super GPU under Linux. We used GCC 14.2 and NVCC 12.9 to build our code. Images are rendered at 1920 × 1080.

Only the Bistro (64*k*) scene strictly requires this, as the other scenes use fewer than 224 leaf bricks. The performance impact of this is quite small, as most of the time is spent on intersection tests with interior nodes (Figure 6\). The geometry uses between 13% (Bistro) and 18% (Epic Citadel) less space with our encoding (including both offset tables). # 4.2. Editing Performance

Editing performance and memory usage for both the HashDAG and our editable variant based on it depend on a number of parameters. These include the page size and the number of buckets in the hash table for each level or child configuration, respectively. Generally, using more memory results in better editing performance as the number of hash collision is reduced. For a meaningful comparison, we therefore select cases where the total memory usage is similar and compare editing performance of these configurations. For the HashDAG, we use the settings proposed by Careil et al. [CBE20]: a page size of 512 words with 216 buckets for lower levels (≥ 10) and 1024 buckets for levels closer to the root.

For our editable variant, we found that page sizes of 128 and 256 words both performed well, providing a trade-off between memory use and performance. Hash collisions are resolved with a linear search through existing nodes in a bucket. We determine the number of buckets each child configuration receives based on their expected occupancy in bytes. The linear search is ultimately memory bound, and we therefore want to distribute nodes with more children or more common child configurations across more buckets to keep the linear search cost constant. We empirically determined an initial target bucket occupancy of 3072 words to work well in our tests. We require a minimum of 16 buckets for a child configuration. We permit at most 214 buckets per configuration, except for full nodes, that is, with all eight children, for which we allocate a full 216 buckets. These parameters were determined through tests. The same parameters were used for the leaf brick and interior node tables. We include additional comparisons with different configurations in the supplementary document.

#### 5. Conclusion

We present a novel encoding method for the SVDAG data structure. The encoding embeds information about the geometric structure of nodes in their memory location. When encountering a pointer to a node, we can extract the information of the target node's geometric structure from the pointer, without having to follow the pointer and access the node's memory. This reduces the number of memory accesses required during traversals such as ray tracing significantly; however, each memory access requires address translation, making accesses slightly more expensive. Despite this, we show that the total number of memory accesses, including those required for address translation, is reduced, resulting in an overall performance increase of up to 25%. As the geometric structure is encoded in the memory location, we no longer need to store it explicitly, which also results in a more compact representation in memory.

The proposed encoding is compatible with existing methods for, for example, attribute storage and editing. It retains its benefits for traversal performance and geometry storage. In particular, our encoding works well with the HashDAG, which already requires address translation to take place. Here, our proposed encoding does not add any new overheads and instead provides the full benefit of the reduced memory accesses. We believe our proposed encoding to provide benefits to most of the existing SVDAG-based approaches, and should be able to serve as a more efficient dropin replacement for the traditional SVDAG. Nevertheless, it would be interesting to extend our prototype implementation to other recent work, such as the GPU-based voxel editing, including better support for editing with attributes [ME24, ME23]. Our encoding additionally affords contiguous and cheap (i.e., not requiring traversal of the DAG) indices for nodes within the structure, meaning it would scale well with the inclusion of further geometry-dependent or geometry-bound [ME24] attributes in addition to subtree counts.

We would like to explore an extension of our idea to other pointerbased hierarchical data structures. For example, existing techniques employ voxel proxies in acceleration structures [YH23, ME20], at the cost of storing extra voxel data in nodes. Encoding such data in the memory location may reduce the extra storage requirements and avoid memory accesses during traversal.
