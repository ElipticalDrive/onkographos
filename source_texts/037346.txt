Summary
Phase 4 of #96. Add raymarching of participating media -- clouds, heterogeneous fog, godrays. Independent of Phases 1-3 (different sampling math: delta / ratio tracking on density instead of sphere tracing on distance) but shares the step-loop pattern and Slang module structure. Pairs directly with #51 spherical-Earth atmosphere if we extend that to heterogeneous density.
Why
Clouds and godrays are signature path-tracer wins. Homogeneous volumes are simple; heterogeneous (clouds with density fields, layered fog with altitude falloff) require ray-marching the medium with delta tracking. Plays directly into #51's curved-atmosphere story if we go non-uniform.
Scope (in)
New shape variant SHAPE_VOLUME in BVH leaf -- a bounded medium with an AABB and a density-field reference.
Density-field representation: 3D texture or procedural (FBM noise + worley) -- API supports both behind a single sampler interface.
Delta tracking + ratio tracking along the ray in new Slang module VolumeRaymarch.slang.
Single-scatter + multi-scatter through the medium (multi-scatter via Russian roulette through repeated delta tracking).
Henyey-Greenstein phase function with optional dual-lobe (forward + back-scatter lobes -- canonical for clouds).
Sun + envmap inscatter via NEE through media: at a scattering event, sample a light direction, ratio-track transmittance back along that ray.
Cvars: r_vol_max_steps (default 64), r_vol_density_scale (default 1.0), r_vol_phase_g (default 0.8 for clouds, configurable), r_vol_multiscatter_bounces (default 2).
Showcase scene: cumulus cloud layer + sun + ground.
Scope (out)
Adaptive temporal upsampling of clouds (later -- pairs with REBLUR for volumes).
Animated clouds / wind advection (later).
Voxelized cloud asset import (later).
Cloud-shadow on ground tile-based approximation (rasterizer-style trick; we don't need it, NEE handles it).
Plan
Medium representation API on the host: a Medium lives in a bounded volume, registered in AnalyticBvh as SHAPE_VOLUME.
VolumeRaymarch.slang -- delta + ratio tracking, HG phase, sampler abstraction over 3D-texture vs. procedural.
Wire NEE through media: light-sample + transmittance-ratio-track to that light.
Phase function (HG single + dual-lobe option).
Cvars + logging on medium registration.
Acceptance scene: cumulus layer with sun and ground.
Acceptance
Cloud demo renders with correct silver-lining around the sun-edge (HG forward lobe signature).
NEE through medium produces visible godray volumetric shadow-shafts when sun is occluded by cloud.
Frame budget: <= 6 ms at 1080p for a single cloud layer, target hw (RTX-class), 1 spp.
Cross-backend match.
Plays correctly with sky: spherical-Earth atmospheric model + curved aerial perspective #51 atmosphere when both are active -- no double-attenuation, no double-scatter.

Overlap with the planetary epic #253 — P3 (#257) and P6 (#260)
Recording an overlap, not a closure. This issue's own summary already anticipates it: "Pairs directly with #51 spherical-Earth atmosphere if we extend that to heterogeneous density." #253 is where that extension happens, and two of its phases land pieces that sit next to this one.
#257 (P3) — the medium model goes physical and spherical
#257 rebuilds the atmospheric medium as three species with real constants: Rayleigh (Bodhaine, Wood, Dutton & Slusser 1999, (5.802, 13.558, 33.100) x 10⁻⁶ m⁻¹, H = 8 000 m), Mie scattering and absorption (Hillaire 2020, 3.996e-6 / 4.40e-6 m⁻¹, H = 1 200 m — the absorption term is absent from the engine entirely today, and kHmie at PathTrace.slang:4974 is currently 1500), and ozone on a tent profile peaking at 25 km ((0.650, 1.881, 0.085) x 10⁻⁶ m⁻¹, Serdyuchenko et al. 2014 / Gorshelev et al. 2014). It also makes the cloud layer a spherical shell at all four sites that currently assume a flat slab — PathTrace.slang:7233-7250, CloudsRaymarch.slang:319-327 + :393-406, PathTraceCloud.slang:188-190, plus the shadow-ray optical-depth marches around PathTrace.slang:4750-4900.
The relevant point for this issue: #257 does not introduce a SHAPE_VOLUME BVH leaf, a delta/ratio tracker, or a general bounded-medium API. It works entirely in the existing closed-form/marched atmosphere path. So the two are additive rather than competing — but if this issue lands first, its sampler abstraction over "3D texture or procedural" is the natural home for #257's tent-profile ozone and for the cloud density field, and #257 should consume it rather than growing a parallel one.
One constraint this issue should know about: the RHI has no 3D textures. src/rhi/Resources.h:21-27 is TextureDesc { width, height, format, usage, debug_name } — no depth field, no TextureType enum, and no 3D texture anywhere in the codebase. It also has no samplers at all — every texture is read by integer index and bilinear is hand-written (see PathTrace.slang:3409-3421). This issue's "Density-field representation: 3D texture or procedural" therefore costs ~400 LOC of RHI across both backends before any shader work, plus RWTexture3D lowering that is unproven on both Slang targets. #253 deliberately routes around it (the froxel AP volume from #51 phase 4 is dropped for exactly this reason), so if this issue wants the 3D-texture path it owns that RHI work. The procedural path has no such cost.
#260 (P6) — an emissive species in the same march
#260 adds emissive terms to the shell march: the aurora, re-sited out of shaders/AuroraComposite.slang's post-denoise view-direction overlay into a real volumetric integral with three real emission lines (O I 557.7 nm at 100-150 km, O I 630.0 nm at 200-400 km, N₂⁺ 427.8 nm at 90-120 km) over a corrected-geomagnetic-latitude oval; and airglow at 87-100 km (557.7 nm ≈ 250 Rayleigh zenith, plus the OH Meinel bands). Both are emission without extinction, so they are simpler than this issue's delta-tracking scope, but they exercise the same step-loop pattern and would sit naturally on this issue's VolumeRaymarch.slang module if it exists first.
#260 also fixes a sampling problem this issue will hit independently. A ray grazing a 300 m thick cloud shell at the limb has a chord of 2·sqrt(2·R·Δh) = 2·sqrt(2·6.371e6·300) ≈ 124 km. r_clouds_raymarched_samples defaults to 32 (Engine.cpp:1452), so dt ≈ 3.9 km against a ~200 m feature size at r_clouds_freq 0.005 (Engine.cpp:1392) — undersampled by ~20x, producing pure aliased noise that the denoiser smears into a grey smudge. The fix reuses the ray-cone reasoning from 18f28ec: cone-footprint stepping (dt = clamp(t · pixel_cone_angle, dt_min, dt_max)) coupled with density LOD — drop FBM octaves proportionally to log2(dt / feature_size), so a 3.9 km step samples a 3.9 km-smoothed density field and 32 steps becomes correct rather than undersampled. That is the same disease 18f28ec cured for textures, in the volume, and it applies to any heterogeneous medium marched at a footprint larger than its feature size — i.e. to this issue's clouds too.
One thing worth carrying into this issue's scope regardless
r_volumetric_density and r_rayleigh are two fudge factors tuned against each other. r_volumetric_density defaults to 0.002 (Engine.cpp:1348) against a real-Earth sea-level aerosol range its own doc string gives as 1e-4 to 5e-4, and r_rayleigh then defaults to 30.0 (Engine.cpp:1774) explicitly to cancel it — that doc string says so outright. Any heterogeneous-medium work that reuses r_volumetric_density as a density scale inherits the fudge. #257 retires the pair for real coefficients; if this issue lands first it should either use physical values from the start or note the dependency.
Also relevant to this issue's "Frame budget: <= 6 ms at 1080p": three subsystems in this engine are compile-gated purely because their presence in the megakernel costs milliseconds even when unused — PT_SDF_PROCEDURAL_OPS (~6 ms/frame, cmake/Slang.cmake:21-25), PT_WATER_ENABLED (+2.99 ms, CMakeLists.txt:147), and PT_LIGHT_TREE. A new marching loop in the hot path pays that tax on every existing scene. Ship behind a PT_*_ENABLED gate from the first commit.
Nothing here changes this issue's scope. It stays Phase 4 of #96.
