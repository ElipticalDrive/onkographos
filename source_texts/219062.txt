The Rerun Viewer is currently limited to only being able to display ~two million points at a time, and will have pretty terrible frame rate at 1 million points already.
The reason for this is that we upload the point cloud every frame. This is very simple, but obviously very wasteful.
A solution is to detect if the same points are being rendered this frame as the previous, and if so not re-upload them. This is similar to how we already handle tensors.

Only partially upload the point cloud and render it progressively using random or weighted subsets of the cloud: https://publik.tuwien.ac.at/files/publik_282669.pdf

We should be a bit more specific with the "huge" part. From what we learned so far most users are more than happy in the region of <8mio points which seems to be in the region where we don't need acceleration structures for rendering.
We need typically 24bytes per point right now (position, radius, color, index - could compress away the index!), so 8mio points would be merely 184Mb.
Given that upload speeds can be assumed to be at the very least 16GB/s (that's PCIe 3.0 16x; 5.0 is common and has 64GB/s and integrated GPUs are off the chart there) we get 273Mb/frame for 60fps.
So even if we upload ever frame we should still hit at least 30fps at that size if we do everything correctly.
Right now we have a hardcoded limited 4mio; point cloud renderer should be dynamic with this!

The current state is around 1.5M points @30 fps on my M1 MacBook Pro.
We are bounded primarily by
CPU (upload)
overdraw when zoomed out a lot
A rough roadmap:
Remove limit on line and point count #3076 - allowing bigger point cloud (without speeding them up)
Optimizing our current code - we should be able to get to 2x-5x larger point clouds with a few days work
Arrow deser: Add zero-copy happy path #3109
Optimize the joining iterator
Related: Optimize out unnecessary joins across autogenerated instance keys #3107
Cache uploads, so we only upload when the points change
Will move us completely to be GPU bound (memory and overdraw mostly). Maybe 100M points?
Acceleration structures, streaming uploads etc: billions of points.

Hi!
I took a stab at the "cache uploads, so we only upload when the points change" item from @emilk's roadmap above: draft PR #12904.
The shape: re_renderer gets a persistent GpuPointCloud (the three data textures, split out of PointCloudDrawData::new), and the Points3D visualizer stores it in the existing query_result_hash-keyed Points3DCpu memoization, so upload happens only on cache miss. Per-frame work drops to batch uniforms/bind groups (transforms, highlights, sort data). It also fixes the existing TODO where N instance transforms re-uploaded the same cloud N times.
Measured on an RTX 5070 (methodology in the PR): full frame at 10M static points goes 28.4 → 8.9 ms (~3.2×), and the per-frame CPU/upload phase becomes flat in point count (~0.9 ms at 10M vs ~18.5 ms before). Best case scenario admittedly — static scene, one opaque entity; per-frame-changing data pays the same upload as today.
Since this is a larger change than I'd normally send undiscussed, I've kept it in draft — would appreciate a sanity check on the design before I polish further. Full disclosure per your agent policy: the implementation was written by a coding agent (Claude) under my direction; benchmarks and tests are described in the PR. points2d and gaussian_splats3d have the same re-upload structure and would be natural follow-up PRs if the approach lands.
Thanks for your time.
