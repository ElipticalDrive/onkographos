Point clouds are capped by how they're held and drawn, not by the readers: MAX_CLOUD_POINTS (5 million in a whole project), MAX_BYTES (2 GiB a file, read whole into memory), a project file that holds every point (deflated, base64), and every picture projecting every n-th point on the processor (DRAWN, 2 million), since the graphics card refuses a view that shows a scan. Past the cap a scan is thinned at import, so the detail walls are traced over is lost for good.
The approach is the one Potree made standard: an octree of levels of detail, a point budget a frame, and a scan streamed from a file of its own.
Phases
B: an octree in memory. cloud/octree.rs: an additive octree a scan (a 64³ grid a node, first come first kept, the rest to its children; capped in depth and size), built when first needed and shared, as the snapping grid is. One selection (frustum, section box or view range, screen-space size, a budget) for 3D, plans, sections and snapping. Import no longer thins to a stride; MAX_CLOUD_POINTS rises.
A: the graphics card draws scans. gpu::Mesh takes a view with a scan: point batches a node, squares facing the camera sized by spacing, the section box in the shader, picking by slot. A point budget in Settings > Graphics, shared by the processor's pictures.
C: linked scans, streamed. An octree file of its own (.bcoct: hierarchy, point blocks with CRCs, written atomically, keyed by the source's hash) built without holding the source in memory (counted, bucketed on disk, each bucket built alone). A project holds a linked scan as its source, hash, cache and its top levels, so it draws with no cache; nodes come from a reader thread into a bounded cache. FORMAT 7. point_cloud takes link; reload_cloud. (Done as format 6 on this branch, 7 once Import CAD and Link CAD: DXF drawings in plans (fork issue 4) IPedrax/BIMCraft#121 lands; nodes load on demand into a bounded LRU, blocking, so headless pictures are whole; the desktop builds the cache on a thread.)
D: smaller points. Positions as 16-bit steps of 0.25 mm across each node's cube (nodes up to ~16 m; larger ones keep f32): 100M points 1430 → 860 MB, a 2M-point view loads in 18 ms.
LAZ (deferred). The laz crate is Apache-2.0 only, so it can't enter the dual-licensed core; it belongs in an optional crate like crates/rvt, handed to the session as the DWG bridge hands its reader (Read DWG drawings in Import CAD and Link CAD #5), once that hook is upstream.
Each phase is a commit with its tests, on branch point-clouds-huge (on section-box, since the section box cuts scans); one upstream PR when all four are done.
