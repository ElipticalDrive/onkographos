For my final project of my CENG 795: Advanced Ray Tracing course, I have tried to implement volume rendering in my ray tracer using OpenVDB to store volume data and ray marching to sample color contributions of a volume along a direction. In this blog post, I will be explaining my implementation process and the problems I encountered along the way.
Installing and Linking OpenVDB
The most arduous and time consuming part of my implementation was getting OpenVDB to finally work. At a certain point I even considered skipping this part and trying to create the volume data myself. Luckily, I did manage to get it to work in the end.
OpenVDB has heavy dependencies (Boost, TBB, Zlib, Blosc) and is generally meant to be built separately using CMake. The main problem I came across while installing OpenVDB was that it uses specific TBB types (like tbb::split), but the newer version of TBB (TBB 2021 / oneTBB) installed by my system (Ubuntu 22.04) has reorganized its header files. As a result, OpenVDB’s header TreeIterator.h could not find the definition for tbb::split because it wasn’t including the necessary TBB header explicitly. To circumvent this issue, I tried to forcefully including the missing TBB definitions in my code before I included OpenVDB to no avail. I considered reverting TBB to an older version, but apparently it could create some issues with the OS. So as a last resort, I installed an older Ubuntu version (Ubuntu 20.04) on WSL and thankfully this worked.
Once I managed to get OpenVDB to work, reading the VDB files was quite simple. I stored the volume in a float grid and sampled the density value at a given point using OpenVDB’s quadratic sampler, which uses trilinear interpolation to calculate the density value. I could have used box sampler instead (which uses nearest neighbor), but for this project I believed it was more important to get smoother results rather than faster ones. Although, considering the results I got, perhaps box sampler would have been better.
Volume Intersection
To determine whether a ray was passing through a volume or not, I needed to calculate if a ray intersected the bounding box of a volume. VDB volumes contain bounding boxes themselves, so I simply calculated the intersection the same way I did for BVH nodes. For some reason though, there seems to be a problem with the intersection logic this time. Some of the rays that should intersect the volume are calculated as not intersecting, and this lead to most of my renders being weird. Unfortunately, I couldn’t solve this issue, so some of my scenes are not rendered properly. However, when the intersection testing (at lines 428–430 in raytracer.cpp) is turned off and ray marching is applied at every point, it creates a foggy effect and results in much better renders.
Ray Marching
Once a ray passed through a volume, I needed to calculate how much of the light passed through the volume and how much of it got scattered or absorbed by the volume. I calculated this using the Ray Marching algorithm.
In Ray Marching, the line on which the ray is passing through a volume is divided into segments and compute each segments contribution to the overall color accumulation and transmittance depending on the sampled density value and the volume’s scattering and absorption coefficients.
First I set the accumulated color to 0 (no color) and the transmittance to 1 (fully transparent). I accumulate the color and transmittance during the ray marching loop. At each segment I first sample the density, then calculate the scattering and extinction (out scattering + absorption) effects by multiplying the coefficients with the density value. Unfortunately, I could not implement proper volume rendering. My intersection testing does not work properly and my scattering calculation seems to have some problems as well. I also could not implement emmissions and Henyey-Greenstein phase calculation in time. Still, disregarding intersection did provide some interesting results and the effects of changing the absorption and scattering coefficients is clearly visible.
