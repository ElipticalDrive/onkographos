Status
This is a physical intuition and a proposed experiment, not a settled DOM architecture. The story deliberately assumes away allocation, contention, malformed HTML, crashes, and device behavior so that the sequential shape remains visible.
The brick-track story
Assume a completely fresh, empty track. Nothing important is in the way, and I never have to search for free space.
Mr Network stands behind me and hands me a brick, or perhaps a batch of bricks. I put each batch down, advance, wait when Mr Network is not ready, and continue. I do not stop to write down every location. I record only the street sign beside the first brick.
When the stream ends, I return to that starting marker and walk forward through what I laid down. I now distinguish what I want to retain from what I do not. In the most physical version, there are neighboring tracks: kick wanted bricks to the right; perhaps kick rejected bricks to the left; later tell the street sweeper that the original track is yard waste. A backpack represents bounded working memory. If the backpack is too small for the whole structure, I should still be able to proceed a bounded amount at a time.
This suggests an append-first, scan-later, compact-into-a-new-copy model:
```
Mr Network
    → immutable raw byte stream
    → file-backed document record stream
    → selected/compacted document record stream
```
The new copy is not an edit of the first copy. It is a later arrangement containing only the material the next stage wants, while the original remains recoverable until the new copy has been checked.
What the story gets right
Sequential append can be the simplest storage operation.
Remembering one start offset is cheaper than recording a separate physical location for every byte.
A later sequential scan can construct a more useful representation.
Keeping the source immutable and writing a new selected copy gives a clean recovery boundary.
The amount of live parser state need not equal the size of the entire document.
Network arrival, parsing, writing, and later compaction are distinct rates and may want distinct buffers.
Where the story cheats
The network supplies byte chunks, not DOM nodes. A token or character can cross chunk boundaries.
HTML is not merely balanced parentheses. Error recovery, implied elements, void elements, optional end tags, character references, tables, namespaces, and scripts make a standards-compatible browser DOM a stronger claim.
A file offset is not a physical disk address. A filesystem maps it to blocks; flash storage adds another translation layer and may move data internally.
Seeking back to file offset zero does not make the process physically walk backward over the medium. It normally changes a logical offset; the kernel and device schedule the later reads.
Ordinary files do not promise an adjacent left and right track. The useful analogue is two append-only output streams or regions, not physically neighboring sectors.
A successful write can mean "accepted into a cache," not "survived on stable media." Crash boundaries require an explicit durability and commit protocol.
The libc, kernel, and raw-device boundary
Bypassing libc is ordinary and narrow: issue Linux openat, read, write, pread, pwrite, lseek, mmap, and related system calls directly. GCC is not the component doing I/O buffering. libc's stdio layer may add a user-space buffer, while the kernel separately supplies socket buffers, the page cache, readahead/writeback, the filesystem, and device drivers.
Bypassing libc does not bypass the kernel.
Opening a raw block device bypasses the mounted filesystem, but still uses kernel permission checks, system calls, the block layer, and a device driver. Writing filesystem allocation tables behind the mounted kernel filesystem would create two unsynchronized owners of the same metadata and can corrupt it.
O_DIRECT can avoid much of the page cache under alignment and filesystem constraints, but it is still kernel I/O and is not automatically faster. io_uring can amortize submission/completion overhead, but it is also a kernel interface.
A more literal kernel data-path bypass exists only after taking on much more of the kernel's job: bare metal / a private operating system, or a user-space driver arrangement such as VFIO/SPDK after the kernel has granted and isolated the device. That means owning queues, DMA, IOMMU mappings, synchronization, recovery, allocation, persistence ordering, and the on-disk format. On ordinary Android storage this is not a plausible first route.
A first IB experiment without pretending it is the final DOM
Use a few ordinary large files, not one filesystem entry per node:
Append the response bytes to an immutable raw file, optionally while parsing them.
Stream-parse into a flat append-only document log. Records can carry node ID, parent ID, document order, source span, and start/text/end events. The parser keeps only unfinished-token state and a stack of open elements in memory, subject to an explicit depth bound.
Sequentially scan that log and append selected records to a second compact log. Preserve source spans or provenance so the selection remains inspectable.
Mark the old log disposable only after validating and committing the new one.
Closing an element need not require rearranging earlier bytes. Either append an end record, or patch one known fixed-size field with pwrite. A flat record stream can encode a tree without demanding that the host filesystem itself be the tree.
Until the required browser semantics are chosen and tested, call this a file-backed document log or document snapshot rather than claiming it is the Web DOM.
What to measure before removing layers
bytes received, parsed, and written;
read/write batch sizes and partial operations;
peak live parser memory and maximum open-element depth;
number of system calls and seeks;
time to first document record and time to selected copy;
bytes copied versus referenced by source span;
behavior when killed between append, flush, validation, and commit;
buffered stdio versus direct system calls only after the ordinary path is correct.
Working boundary
The initial way to get direct control is not to write unowned sectors. It is to define a small, inspectable, append-only format inside a preallocated ordinary file. That preserves the brick-track experiment while letting the existing filesystem own allocation, permissions, device diversity, and crash-sensitive metadata. If measurements later identify the filesystem or page cache as the actual bottleneck, then narrower alternatives can be tested against the same record format and oracle.
