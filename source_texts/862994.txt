Contributor
Phase B of the Vulkan engine campaign. Stacked on Phase A (#19); review only the diff against vk-campaign/phase-a.
Changes
Subgroup size from the device (6a004ff):
The engine queries subgroupSize and the subgroup-size-control properties, then pins subgroup-dependent pipelines with requiredSubgroupSize where the device supports it.
multi_radixsort_warp{16,32,64}.comp are merged into one multi_radixsort.comp, with the subgroup size as a specialization constant.
devices/*.json gpu.subgroup_size is now only a cross-check: a mismatch logs a warning.
BT_VK_SUBGROUP_SIZE=<n> (5e7d320) pins another supported size. That's how subgroup 32 stays covered: no fleet GPU defaults to it.
Workgroup size (5491c54, bd59780): work_group_size() now feeds local_size_*_id spec constants, and sizes beyond the device limits are rejected. maintenance4 joins the required features, because SPIR-V 1.6 LocalSizeId needs it (VUID-RuntimeSpirv-LocalSizeId-06434). Vulkan 1.3 mandates support for it.
Docs (a9e57d2): the subgroup size is a runtime query, and the phones are on the build box's adb, not rocky.
Finding
The Samsung's Xclipse 940 reports a default subgroup of 64 (range 32..64), not the 32 in devices/R5CY21Y3VEV.json. The JSON and the specs are corrected.
Verification
The tree suites match the OMP oracle exactly at subgroup 16 (Pixel), 32 (rocky and Samsung, pinned) and 64 (rocky and Samsung default), with one shader source.
ctest -L vulkan passes 7/7 on rocky, and validation reports 0 errors.
Radix-sort time on rocky: 0.78308 → 0.78311 ms, within noise. Pinning to 32 would cost +24%, so it isn't used.
Codex review: DONE.

The queried fleet has no GPU that defaults to subgroup 32: rocky-ryzen's 780M and the
Samsung's Xclipse 940 both report 64 (range 32..64), the Pixel 7a's Mali-G710 16. So the
device-default policy alone would never run the radix sort at 32. BT_VK_SUBGROUP_SIZE=<n>
pins n instead, when pinning is available and n is a power of two in [min, max];
otherwise Engine() throws (applied in Engine, so the has_integrated_gpu() probe cannot
turn a bad value into a silent skip). It is also design D5's "pin to minSubgroupSize"
mitigation knob.

Artifacts corrected in the same commit: the pipeline-config "Every fleet subgroup width"
scenario and proposal.md listed the Samsung as sg32 (the devices/R5CY21Y3VEV.json value);
design D5 now records the measured fleet values and the hook, and the spec gains the
"Another supported size is pinned for testing" scenario.

… 6.3)

The Phase B gate's validation run on rocky-ryzen reported
VUID-RuntimeSpirv-LocalSizeId-06434 three times in test-kiss-vk: glslc's SPIR-V 1.6
output turns `local_size_*_id` into OpExecutionModeId LocalSizeId, which needs the
Vulkan 1.3 maintenance4 feature enabled. Only engine_test_workgroup_size.comp uses it
today, but it is the path work_group_size() specializes. maintenance4 joins the
required-feature table (a 1.3 table next to the 1.2 one; 1.3 mandates support, and
the SPIR-V 1.6 shaders already need 1.3), and the 3.2 feature test also checks that
a missing maintenance4 is named. design D3 and proposal.md updated.
