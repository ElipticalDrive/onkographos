src/evaluation/eval_recon.py calls
```
eval_result = calc_3d_mesh_metric(mesh_gt, mesh_rec)
```
but the signature in third_parties/neural_slam_eval/eval_recon.py is
```
def calc_3d_mesh_metric(mesh_rec, mesh_gt, align=False):
```
so the reconstruction is passed where the ground truth is expected and vice
versa. The effect: the printed comp / comp% are computed in the
accuracy direction (reconstruction → GT) and acc in the completion
direction (GT → reconstruction).
At full budget (2000 iterations) this is nearly invisible — the
reconstruction covers essentially the whole scene, so the two directions
almost coincide (we reproduce your published Replica numbers within noise
either way). But for any truncated-budget or partial-coverage run the
swap is catastrophic: a reconstruction that covers only part of the scene
still scores near-perfect "completion", because most reconstructed points lie
close to some GT surface. We hit this while running budget-matched
comparisons against NARUTO (e.g. at 90 observations, corrected comp%@5cm on
room_2 is ~21, whereas the swapped-order value reads >90).
Fix (one line):
```
-    eval_result = calc_3d_mesh_metric(mesh_gt, mesh_rec)
+    eval_result = calc_3d_mesh_metric(mesh_rec, mesh_gt)
```
Happy to open a PR if useful. (We also carry a small companion patch adding a
comp%@10cm output next to the default 5 cm threshold, and two environment
fixes for newer toolchains: #include <limits> in NumpyMarchingCubes for
gcc-13, and clamping the trilinear-interpolation upper indices in
src/planner/rrt.py.)
