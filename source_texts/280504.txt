Related: #42 and #1.
Could SplatRenderer expose an opt-in encoded-RGB accumulation mode, while preserving the current default?
I compared Brush 0.3.0's color accumulation with MetalSplatter at 2b965de1934de38dda1c71cf90bf798aa948a14c. The same hardwired conversion remains in upstream main 464eb37c55d90d7362a79120fdf8b50d4ae03296:
SplatProcessing.metal applies pow(srgb, 2.2) to evaluated SH color.
SplatRenderer.swift exposes the attachment format but no choice of evaluated-color conversion.
Brush 0.3.0's rasterizer accumulates evaluated RGB directly using alpha/transmittance. Its image-sample path uses decoded image channels without an explicit gamma decode.
Synthetic test
I used two broad, overlapping SH0 Gaussians and read an opaque center pixel after the native renderer settled:
World positions: (0,0,3) and (0,0,4); camera at origin looking along COLMAP +Z, converted to Metal's right-handed camera convention.
Scale: (0.8,0.8,0.8) for each; identity rotations.
Front RGB 0.1, opacity logit 0 (alpha 0.5).
Back RGB 0.9, opacity logit 12 (nearly opaque).
DC coefficients per channel: (RGB - 0.5) / 0.28209479177387814.
100×100 output, fx=fy=100, principal point (50,50), black background, .bgra8Unorm_srgb output, native Apple M5 Pro Metal.
I waited for three identical consecutive pixel buffers after warmup and sampled pixel (50,50).
Calculation / run
Center RGB, normalized
Brush direct-RGB formula: 0.5*0.1 + 0.5*0.9
0.500000
Convert each layer with pow(2.2), blend, then sRGB encode
0.664967
Actual native MetalSplatter output
170/255 = 0.666667
The native result matches the conversion/blending calculation within one byte. I have not run Brush's GPU rasterizer on this fixture; the Brush value above is an analytic reference. Finite Gaussian footprint and half precision explain the need for a small tolerance.
Requested API behavior
Please consider an opt-in GPU color contract that can accumulate evaluated RGB in encoded space without the pre-blend conversion, paired with a suitable non-sRGB accumulation target and explicit presentation/export handling. Dynamic SH, geometry, opacity and sorting should keep their existing behavior.
Preserving the current default would avoid changing existing applications. Tests should cover single-stage and multi-stage rendering, transparency/background composition, and offscreen output. Changing the attachment format alone leaves the shader conversion in place.
Linear-light compositing is a valid choice. This request concerns matching a producer's training contract; it does not propose removing the current path or treating PLY colors as having one universal interpretation.
Would you support this as an upstream option, or is there an existing supported integration path I missed?
