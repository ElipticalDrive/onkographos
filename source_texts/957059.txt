Parent epic: #39
Goal
Provide GPU resources and rendering contracts for velocity generation and temporal resolve in both raster techniques.
Implementation tasks
Choose a velocity pass/MRT route and supported format from device capabilities. Account for attachment-count limits rather than unconditionally adding another G-buffer target.
Create velocity and agreed validity/rejection resources at render resolution, with zero/invalid clears and well-defined depth correlation. Preserve raw velocity outside [0,1]; do not encode it as unsigned color.
Wire images, views, samplers, descriptors, RenderingPass/RenderingTarget descriptions, dynamic-rendering formats, and pipeline/secondary-command inheritance consistently.
Declare producer/consumer usage and record synchronization2 transitions for attachment writes and shader reads. Avoid descriptor references to destroyed/recreated images.
Implement the contract's TAA/MSAA policy. If multisampled velocity is supported, select motion correlated with visible depth rather than averaging unrelated foreground/background samples.
Handle resize, zero extent, sample-count changes, technique changes, and partial creation failures with correct RAII/VMA lifetime management.
Acceptance criteria
Both forward and deferred routes expose velocity/rejection resources in the documented formats, with valid first-frame clears.
No unsupported attachment/format/sample combination reaches pipeline creation; diagnostics or the documented fallback are explicit.
Synchronization validation passes resource creation, repeated resize, and raster/MSAA mode switches.
Disabled TAA preserves existing outputs and does not perform unnecessary temporal passes.
Report added memory per resolution and render-pass bandwidth implications.
Relevant code and documentation
include/Container/renderer/resources/FrameResources.h
src/renderer/resources/FrameResourceManager.cpp
src/renderer/resources/FrameResourceRegistry.cpp
src/renderer/pipeline/GraphicsPipelineBuilder.cpp
include/Container/renderer/core/RenderGraph.h
src/renderer/core/FrameRecorder.cpp
Validation evidence
Provide native Debug/Release builds and GPU validation captures at two resolutions with the supported AA/sample-count combinations.
Engineering requirements
Use Vulkan 1.4 dynamic rendering/synchronization2, Vulkan-Hpp RAII for engine-owned Vulkan objects, VMA for allocations, and Slang for engine-owned shaders. Follow docs/coordinate-conventions.md: reverse-Z, a negative-height scene viewport, and column-major matrices. Preserve raster fallbacks and existing GPU indirect drawing. Keep feature resources in focused managers and use the render graph for ordering and declared resource access. Include meaningful validation evidence and document any supported-mode limitations.
Dependencies and delivery order
Blocked by #48. Implementation exploration can proceed earlier, but these contracts/resources must be available for completion.
Delivery phase: 2 of 5 for epic #39.
Implementation complete; awaiting merge
Implemented and pushed in PR #60, now ready for review. A separate three-MRT dynamic-rendering velocity pass uses signed RGBA32F motion/expected depth/validity, R32_UINT identity and R8_UNORM reactivity. Required formats and 1x AA are checked explicitly, attachments/history use engine RAII/VMA ownership, and synchronization validation passes supported resize/AA combinations. At three swapchain images there are 21 added images and 151 payload bytes/pixel; actual allocations are recorded.
Measured report and reproduction commands · Captures and result JSON · Downloadable Windows preview
The implementation checklists are complete. This issue remains open until PR #60 merges; its closing reference is included in the PR. Initial support is native-resolution 1x TAA, with documented current-frame fallbacks for unsupported motion and layered transparency.
