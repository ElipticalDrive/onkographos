Tips for culling inner faces?
Hey all,
I was curious if anybody else has had this problem and was wondering if anybody has implemented any solutions to it.
After I run my greedy meshing, there will be many "inner" faces which cannot be seen, but yet still rendered due to both the mesh boundaries and the chunk boundaries. These inner faces, other than causing extra work to be done, cause big problems when processing water reflections since the water will "reflect" the inner faces. (At least with the simple water material I'm using).
So when drawing a quad for my greedy meshing I attempted to determine if the face was visible and simply not draw it. For example, if this voxel face is facing NORTH, and the NORTH voxel is not air, then this face should be culled.
This almost worked, however there were problems. Due to only working with a single chunk at a time, and due to the fact that neighboring chunks may not be loaded, it wasn't possible to know if a face was visible or not until the neighboring chunk loaded.
I currently only calculate the mesh once, but would this approach be viable by recalculating the mesh? If so, when would I do this and how should I treat these 'unknown' voxel faces in the meantime?
Thanks.

My 'engine' (the voxel part, I'm actually using Unity) is multi-threaded for the most part, base Unity functionality must be on the main thread unfortunately, but I create the voxel data on separate threads. I currently only calculate the mesh once, but would this approach be viable by recalculating the mesh? If so, when would I do this and how should I treat these 'unknown' voxel faces in the meantime?
This is your problem. Whenever an update happens (loading new chunks, block updates, etc.) you need to be marking affected chunks as needing a remesh, and then remesh them during whichever process you normally perform the meshing in.
EDIT: I would implement this by having a seperate thread that handles meshing of your voxel geometry in the scene, and tag chunks as needing to be remeshed. They can then be picked up by the mesher thread and remeshed as necessary.
Generally I treat 'unknown' voxels as air. This makes it so only edge-chunks render slightly incorrect, which is not really an issue when you load in enough chunks at once.

So the way I handle the unloaded chunk issue is by checking for prerequisites before I start generation. So I check to see if all of the neighboring chunks are loaded (Logical representation only), if they aren't then I load them up first, and then I'll come back to generate the mesh for this chunk, once all of its pre-req chunks are done. This helps reduce the re-calculating I have to do, at the expense of doing the checks before loading.
Unfortunately I have to propagate lighting so I don't avoid them completely.

I've got a "world" function where I can access any block by asking for the coordinates -- return the block ID, or 0 for air, or -2 for not a part of the world (out of bounds, for example). It computes the chunk coordinates of the block, then checks that chunk for the block you're asking for -- pretty simple! For the boundaries of chunks, you just call the world function, rather than checking in your own chunk. It doesn't require much computation, and you only need to add a couple of if statements -- no need to collect and re-store 2 blocks around the chunk in each direction. Hopefully this approach would be an easy fix :) It also helps for chunk updates and such too, when updating blocks next to the one being updated.
EDIT: Also, the "-2" value you get at the end of the worlds makes sure you don't mesh the sides of those chunks -- it's an easy check :)
```
Speaking about Sleake's comment below too, :
Something else you can do is generate the chunks coming next (but don't mesh them). That way, you don't need to re-mesh just when you get close; the first time you mesh the far chunks is the only time you mesh it, until the player updates it -- the farthest chunks are loaded but not meshed, so you can greedy mesh the second-to-farthest chunks without having to re-mesh them when you get closer. This is a time-or-memory issue you'd have to weigh in.
```

I use a system where i can guarantee that chunks are in a state where you can determine if chunk edge block faces are visible when they build their mesh. If you queue generate/tessellate tasks in a spiral out from the view position with tessellate tasks queued behind generate ones by one rotation. ie player moves into a new chunk, so queue all the x-1,z-1,x+1,z+1 chunks (8 of em assuming only 2D chunks) for generate - we can skip most of them since they're likely to be already generated apart from the ones in the direction of travel, then queue x-2,z-2,x+2,z+2 for generate (most of them agian we can skip since they're already generated), then queue x-1,z-1,x+1,z+1 for tessellate. This means that you can only have a single thread for generate/tessellate on top of your main render thread, but also means that you never have to worry about neighbor chunks being generated when you do your culling
