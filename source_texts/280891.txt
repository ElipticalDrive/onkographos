Proposal and scope
Add an optional CPU raytracing module to SolidCraft's integrated Render path, followed by an optional GPU implementation if the CPU result and measurements justify it. This refines the progressive/final integrator slice R6 in #620; it does not propose a competing Render workspace or replace the Design viewport.
The first useful output is an opaque product image with traced visibility and cast shadows. Progressive opaque light transport follows in another review unit. Glass, HDRI, textures and GPU acceleration have separate acceptance gates; a ray hit or an existing PBR field is not evidence that they work.
This is a source-based design proposal, not an implemented renderer, benchmark, CI result or maintainer-approved schedule. Render remains deferred in the public roadmap's owner scope. The intention here is to agree a bounded interface and deliver small opt-in contributions without making modelling, opening or saving slower.
Findings on current main
Inspected canonical main 5fa8e7d, 2026-10-15. The private plan/ documents are unavailable in this checkout; the public rules and contracts were used.
ProductScene / ProductMesh already provide immutable mesh references, effective body/face appearances and world-space geometry. Applying occurrence transforms a second time would be a bug. This is a suitable kernel-neutral boundary: the tracer should consume triangles, not truck topology, B-rep serialization or kernel internals.
The integrated opaque consumer uses fixed directional lights and the original GGX/Smith/Schlick BRDF. It explicitly has no cast shadows, indirect bounces, environment lighting or transmission. Existing alpha blending is not glass optics. The BRDF evaluator is reusable; a sampling distribution and matching PDF still need implementation and tests.
The job protocol and host already own cancellation, document/session/generation identity, retained PNGs, file scope and atomic export. The current host runs a concrete raster ImageTask; an interchangeable task boundary is work to do, not an adapter that already exists.
Capability resolution chooses a complete executor profile, currently in lexicographic executor-ID order. Registering another overlapping profile can therefore change routing accidentally. Adding CPU/GPU executors must not silently redirect existing preview exports.
The current 48-byte/output-pixel raster admission estimate does not cover path accumulation, BVH nodes, traversal state, resource leases or progressive display copies. Raytracing needs its own complete admission estimate while sharing the host's overall memory accounting.
L1 solidcraft-render has no wgpu dependency. GPU work belongs at the existing GPU/application boundary; introducing GPU types into the CPU/core scene contract would break the layering rule.
Proposed module and execution contract
Start with a private crates/render/src/raytrace/ module behind a proposed raytrace-cpu Cargo feature, disabled by default, forwarded explicitly by participating apps. Names remain provisional until the interface PR. No dynamic plugin ABI, external executable, Bevy dependency or second scene/material database.
The core should provide bounded preparation and incremental stepping: validated scene/camera/options → prepared acceleration data → work-budgeted steps using the existing cancellation token → linear accumulation → completed frame. Core types are device-independent Rust data. CPU/GPU may share the contract and fixtures without sharing a binary node layout or requiring identical floating-point arithmetic.
Adapt the existing host through a small task abstraction, retaining one queue, one ownership model and shared admission accounting. Do not create a second unaccounted worker/cache. Start on one bounded native worker; parallel tile execution is a measured follow-up. Browser feature-enabled builds must compile, but runtime availability is advertised only after cooperative preparation/tracing/encoding and actual browser interaction are validated. No blocking thread assumption in wasm.
Keep builtin as the engine family. A proposed cpu-raytrace executor is an implementation detail. Pure core availability must not add a selectable placeholder or advertise final, progressive, HDRI or refraction. Integrate through existing render.preflight/start/status/cancel/export commands, with validated ray options added only in the PR that executes them. Before RT2 registers any overlapping preview profile, add/test an explicit integrator opt-in in the versioned runtime command contract (proposed integrator: "raytrace"; absent retains the existing raster path). This is a new interface to review, not a currently accepted parameter. Before RT5 adds GPU execution, define a separate explicit execution preference or equivalent unambiguous routing rule. ID spelling is neither an integrator choice nor a CPU/GPU preference.
Initial options: bounded output dimensions, sample count, path depth, seed and total work/memory budgets. Keep them runtime-only initially. Persisted presets, if later needed, go through existing render settings and the next coordinated format change on actual main; no document-format number is reserved here. Compiled-out or unavailable requests fail clearly, preserving the design and last successful image. Existing quick/preview raster paths retain their routing and output.
Geometry, light and safety rules
Build a bounded flat BVH over the captured tessellation; use a brute-force triangle implementation as a test oracle. Define closest-hit/any-hit intervals, edge/tie policy, degeneracy handling, geometric versus shading normals and finite-coordinate admission. Handle parallel/zero-direction ray components without NaNs. Test very small/large models and grazing/shared-edge rays. Ray-origin offsets must be scale-aware and must not erase thin geometry through a fixed world-space epsilon. These are tessellation-based images, not exact CAD intersection or metrology.
Preserve mm, radians, camera up-axis, face-override precedence and imported colours. Start with the established world mesh. Definition-local instancing/TLAS is a later optimisation only after identity/placement contracts and measurements justify it. No topology changes, face re-identification by triangle ordinal, inferred mechanical axes or density edits.
First trace direct visibility against the existing fixed studio, with explicit opaque-only admission. Use geometric normals for ray-side decisions. Then add progressive opaque path sampling with matching BRDF/PDF, bounded depth, next-event estimation and tested weighting; document finite-depth bias and the existing single-scattering material approximation. Do not claim measured real-material optics. Soft shadows require a separately defined area-light model; directional lights alone do not produce them.
Accumulate in linear light and apply the display transform once at output. Specify sample indexing by seed/pixel/sample so worker scheduling does not change the reference stream. Fixed-seed CPU repeatability is a same-build test, not a cross-device bit-exact promise. Explicitly define background/alpha semantics; a transparent output background does not imply transmissive objects.
Check arithmetic and reserve memory before allocation, including BVH build temporaries, accumulated radiance/counters, stacks, conversion/encoding, progressive copies and retained resources/results. Bound triangle/node counts, BVH depth/visits, rays, samples and bounces. A work-limit breach is a structured error, not an unreported approximation. Cancellation must be checked during preparation, traversal, tile/sample work and encoding; a large tile or BVH build cannot hide an unbounded monolithic step.
Publish only complete bounded updates tagged with job/session/generation. Keep progressive frames transient and bounded; cancellation/failure preserves the last successful image. Camera/material/geometry/resource changes invalidate the appropriate new-job inputs; selection and panel layout do not change captured product shading. Closing/replacing a document never admits a late frame into another document.

RT1 and RT2 can proceed without waiting for HDRI, texture persistence, a GPU choice or advanced optics. Every implementation PR must remain independently reviewable and run repository licence/attribution/layer/native/wasm gates. No perceptible output exists in this planning-only change, so no prototype screenshots or new test results are claimed.
Reuse #1135 for Render preview
I would also like to build on #1135, rather than duplicate its graphics-quality work. Static inspection here is pinned to d60cab5; the PR is still open. This is a proposed integration, not runtime validation or an approval of that PR.
That revision combines optional screen-space AO, display tessellation quality and adaptive supersampling into Performance / Quality / Custom presets. Its Design defaults keep AO and supersampling off; its documented timing comparison isolates AO and must not be relabelled as a measurement of the combined Quality preset or Render. The Render callback explicitly supplies ao_radius: 0.0 and ssaa: 1.0. The current AO implementation and shader therefore do not constitute a Render PBR AO consumer.
Proposed separate preview unit, after #1135 lands: reuse its preset interaction pattern, Custom detection, adaptive settling/device/memory limits and disabled-path resource release where applicable. Define a Render-owned preview policy instead of making a Design preference silently alter product images. Verify which code can be shared after integration; the Render product mesh preparation is not the same as Design display-plan tessellation, so a Fine display setting must not be assumed to refine a captured product mesh.
For optional AO in the GPU product preview, add the actual PBR shader consumer with an explicit, documented approximate ambient/indirect-light term. The present fixed studio sums direct-light BRDF terms: simply multiplying the final PBR colour by the Design AO factor would darken direct illumination and change the established material/parity contract. A callback flag alone does not implement this consumer. Share depth-pass/resource infrastructure where compatible, while checking product geometry, viewport offsets, target dimensions, supersampling and actual attachment conventions.
Keep three controls distinct:
Raster preview quality: AO approximation, display/mesh policy and supersampling, with truthful effective settings and limits.
Raytraced image quality: samples, path depth, output resolution and work budget. These are not aliases for the Design Quality preset.
Execution: CPU now; optional GPU later. A preview preset cannot silently switch integrators or make an unavailable GPU route appear supported.
Screen-space AO misses hidden/off-screen occluders and is not traced shadowing or global illumination. Final/path-traced radiance must not receive an additional SSAO darkening pass; use traced visibility and the delivered light-transport model. A future raytraced AO diagnostic may be useful as its own explicitly approximate output, but is not a substitute for that model. Legacy CPU preview/export must refuse an explicitly requested AO capability it cannot execute, rather than export a different image silently. Actual-window screenshots and completed image exports remain different evidence.
Acceptance for this preview unit: original native Render captures with AO off/on; opaque PBR and legacy scalar looks; cavities and deliberately off-screen occluders showing the approximation's limits; perspective/orthographic views; transparent exclusions; resizing and adaptive-SSAA settling; supported native backends and actual WebGPU behaviour where advertised; two-document ownership and unchanged geometry, mass, camera and modelling history. Check linear/sRGB output and preserve the existing CPU/GPU comparison when AO is off; measure any intended difference when on. Confirm the disabled path skips its depth prepass and large AO resources. Measure AO-only, supersampling-only and the combined Render preset separately on both a small and heavier scene, including allocation/first-frame costs. No Render timings are inferred from #1135's Design-only results.
This unit is complementary to RT1/RT2 and does not block the optional CPU core. Coordinate with #1135's author and the existing Render owners before touching shared gpu.rs, shader or workspace integration. No edits to their branches are included in this planning update.
GPU and dependency evaluation
For a first GPU investigation, evaluate compute-based triangle/BVH traversal using the installed wgpu device rather than requiring hardware RT. Keep wgpu/WGSL resources at the GPU host boundary and bound dispatches/readbacks so rendering remains usable. Do not assume WebGL2 compute support or that a WebGPU build proves device availability. Never silently use CPU for an explicitly requested GPU render.
The repository currently uses wgpu 30. Its experimental ray-query documentation identifies native Vulkan support and unstable semantics. Hardware acceleration is therefore a separate later feasibility decision, not a portable GPU prerequisite or promise.
For BVH infrastructure, compare a small original implementation against a pinned, audited permissive Rust component. The bvh manifest declares MIT, but that alone is not a transitive-dependency, unsafe-code, wasm, memory or cancellation audit. No dependency is selected by this issue. Follow the Rust-only/no-unsafe rules and prohibition on GPL/LGPL/AGPL source; preserve notices and attribution for any permitted adaptation. Use original procedural fixtures first.
Performance evidence and coordination
Benchmark an original small enclosure, a glossy opaque scene and transformed repeated parts. Record cold scene capture/tessellation, BVH build, time to first completed update, trace throughput, encoding, peak/retained memory and cancellation latency separately, with source revision, platform, resolution, samples, depth and seed. Compare default-feature startup/open/save against the unchanged baseline. Agree numerical release budgets from the baseline before advertising performance; no speedup or target hardware certification is claimed now.
This work must reuse, not take over, #1237 (design-owned resources/preparation lifetime), #1345 (opaque wood texture consumer), #1214/#1223 (mapping), #1218/#1267 (normalisation), #813 (environment consumer) and #1060/#1086 (engineering-card/library work). Inspect their actual landed interfaces before integration. Feedback on unpublished overlapping work is welcome. The first proposed contribution is only RT1's optional CPU core; no changes to those contributors' branches or a parallel resource/import pipeline.
Keep #620 and the broader material/environment issues open until their own acceptance criteria are met. This issue tracks the optional raytracing contract and phased delivery, not completion of the entire Render roadmap.

Adding my voice here — a photorealistic render path is the feature I'd most like to see in SolidCraft.
Coming from Fusion 360, what makes a render feel "real" to me: global illumination with soft contact shadows, proper transmission/refraction for glass and clear resin, roughness/metallic PBR under an HDRI environment, and a denoiser so previews converge in seconds. Blender's Cycles is my reference for that experience — I mention it only as a feature benchmark, not as something to embed: its GPL licence and C++ core don't fit a pure-Rust, MIT/Apache, clean-room project, so a first-party Rust integrator (as proposed in this issue) looks like the right call.
Two things that would make it concretely useful for me:
a progressive preview that converges fast on a typical part, not only final quality;
an opt-in offline path, so everyday modelling, opening and saving stay as fast as they are today.
As a licence-safe stopgap in the meantime, an optional scene export (glTF / .blend) would already let people render in Cycles externally.
If a small first unit is agreed (opaque traced visibility + cast shadows, reusing the existing ProductScene boundary), I'm glad to test it on real parts and report what I see.

Thank you @petitwilly for the concrete requirements and for offering to test this on real parts. I have included both of your priorities in the acceptance criteria: a progressive preview with measured time to a useful image, and an explicit offline render path that leaves ordinary modelling, opening and saving unchanged. We will measure convergence on stated hardware and scenes rather than promise a fixed number of seconds in advance.
Your suggested feature order is also useful. The implementation sequence will be:
Close the existing resource/wood integration and its gates; its current CPU and supplementary editor evidence is in #1345.
Deliver opt-in traced opaque visibility and cast shadows, then area lights/soft shadows and a progressive opaque integrator. These will reuse the captured product scene and existing job ownership/cancellation/budget system.
Connect the richer material maps and actual HDRI illumination, followed by explicit dielectric transmission/refraction and thickness-dependent absorption. Existing alpha blending will not be relabelled as glass.
Add bounded denoising after we have a reproducible progressive baseline; GPU acceleration remains a separate measured path.
We are also taking the external-render suggestion forward: a focused glTF/GLB scene-export contribution first, with a separate .blend handoff investigation. We will follow the public glTF specification, preserve representable appearance data and refuse unsupported conversions rather than silently dropping wood mapping or optics. Blender’s licence guidance distinguishes created data files from Blender’s own GPL code; that does not by itself approve a bundled converter or direct .blend writer. No Cycles/Blender GPL source will be read, copied, linked or shipped.
The first useful test request will be a small original native scene with a completed shadowed CPU output, clear limitations, timings and cancellation/memory results. Your offer to test that milestone would be valuable. If you have preferred part types and typical hardware, those details would help us choose representative public-safe cases. This is a proposed implementation sequence, not a claim that these effects are already implemented or that a maintainer-approved release date exists.
The bounded scene-export proposal is now tracked in #1553. The consolidated effects/lighting/optics delivery plan connects that work to the existing material/environment owners. Separate isolated units are prepared for E1 export and RT1. E1 export tests and interoperability checks remain pending. RT1 now passes its focused checks on the isolated 845f4913 base: 110 default render tests, 124 feature-enabled tests including all 14 new ray/BVH cases, strict Clippy in both modes, and a feature-enabled wasm library check. Source implementation is proceeding in parallel for image tracing, existing-host/job integration and bounded directional lighting, with independent memory/cancellation review and original acceptance scenes. The implementation is not published yet: the draft currently contains only its claim commit. We will keep raster defaults, job ownership and the shared admission pool; no document-format change or unsupported optics will be advertised. Heavy validation remains serialized while the existing exact-base geometric diagnosis runs. This scheduling keeps that CI blocker visible without stopping independent feature work.
