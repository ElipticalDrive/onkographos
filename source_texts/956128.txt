Fog dims light too hard in the main game: carry the demo's LIGHT_FOG_PASS across
The lighting demo raised LIGHT_FOG_PASS from the shipped 0.45 to 0.86 and
Brian judged the result clearly better on screen (2026-09-06, The Lit Deep, SDL
build); his exact words are in the notes. Master still carries 0.45. This bead is to make the same adjustment in
the main game, after deciding the questions below.
What the constant does
inc/Light.h:95 defines the fraction of light that survives ONE cell of fog.
It has exactly one use site, src/Light.cpp:353, which pushes it into the
passes[] array that CellFilter applies. FilterAlong
(src/Light.cpp:388-398) walks every cell between the source and the lit cell
and multiplies by that fraction ONCE PER FOG CELL CROSSED. So the loss is
exponential in the depth of the fog, not linear.
Survival by depth:
```
          1 cell   3 cells  5 cells  8 cells  12 cells  20 cells
pass=0.45  45.0%     9.1%     1.8%     0.2%      0.0%      0.0%
pass=0.72  72.0%    37.3%    19.3%     7.2%      1.9%      0.1%
pass=0.86  86.0%    64.0%    47.0%    30.0%     17.0%      5.0%
```
There is also a cliff, not just a fade: FilterAlong returns false once the
strongest channel falls under LIGHT_FILTER_MIN (8/255, src/Light.cpp:402),
and the light is then discarded rather than dimmed. At 0.45 that happens at
about 4 cells, at 0.72 about 11, at 0.86 about 22.
The open question this bead must answer before it changes anything
The demo and the main game do not have the same fog. The demo fills whole
cavern regions with it (BLOB_WITH $"fog", lib/dungeon.irh:3194, and
acid fog at :3239), so rays cross many cells and 0.45 read as a wall one
square in. The main game's fog is more often a spell cloud a few cells across,
plus the fog-filled corridor room (lib/dungeon.irh:2739-2740) and the Misty
region. At 3 cells, 0.45 passes 9% and 0.86 passes 64%.
So 0.86 may make a Fog Cloud stop reading as fog at all. Decide whether the
main game wants:
a. the same 0.86 everywhere, accepting a thin-looking spell cloud;
b. an intermediate value (0.72 was the previous demo step);
c. a per-terrain pass value, so a cavern blob and a spell cloud differ.
Option (c) is the only one that serves both, and it is the largest change:
CellFilter reads one constant, so it would need the value to come from the
terrain rather than the macro.
REJECTED on 2026-09-06: adding a floor to the accumulated attenuation, so fog
tints but never blacks out. Brian's ruling — fog SHOULD block light; the
complaint was the distance, not the existence of the blocking.
Constraint the fix must respect
tools/check_light_fog.sh asserts that ONE cell of fog dims the light
(lit_after < lit_before) and does not extinguish it (lit_after >= 0). A
value close enough to 1.0 that a single cell no longer changes the rendered
level trips its "Light crosses the cloud undimmed" failure. 0.86 costs 14% at
one cell and passes; something like 0.95 may not.
Blast radius
LIGHT_FOG_PASS has one use site, so nothing else reads it. But FilterAlong
is shared with ice (LIGHT_ICE_PASS, src/Light.cpp:351) and the two multiply
together in CellFilter, so any change to the walk itself — as option (c) would
need — reaches ice as well. Both binaries need rebuilding; the gate checks that
touch this area are check_light_fog.sh, check_light_filter.sh and
check_wall_opacity.sh.
Evidence tier
Observed for the demo look (Brian on screen, 0.45 -> 0.72 -> 0.86). Traced for
the mechanism and the line numbers. The survival table is arithmetic on the
constant, not measurement.
Where the demo value lives
spike/lighting-demo in the Incursion-lighting-demo worktree, uncommitted,
and that branch never goes to remote. This bead is the only route the value has
into master.
