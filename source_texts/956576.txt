In traditional serving, you reserve a huge contiguous chunk of memory per request sized for the maximum sequence length. Imagine a request on a 40 GB GPU. You allocate 30 GB just in case. In practice, the model only uses about 12 GB of that space. 18 GB sit unused inside the allocation, 60% wasted. Across workloads, typical LLM inference wastes 60 to 80% of memory. You must allocate for a long tail of sequence lengths. Average usage is far lower and the gaps create fragmentation that the allocator can't reuse effectively. This is why requests get rejected even when there appears to be free memory. We need a better way to manage the KV cache. That better way is paged detention, a memory management system for LLMs. It borrows the idea of virtual memory from operating systems and applies it to the KV cache. Instead of reserving one big contiguous array for each request, we divide the cache into fixed-siz pages, blocks, and store them non-ontiguously. Because blocks are small and uniform, we can share them across requests and avoid large internal gaps. The result is near zero waste and much higher throughput. With the same GPU, you can serve up to four times more users and you unlock continuous batching because memory moves in small predictable units. This idea comes straight from operating systems. Programs need variable amounts of RAM and the OS cannot predict the size in advance. The OS solves this by breaking RAM into fixed 4 kilobyte pages, allocating pages on demand, and using a page table to map from logical addresses to physical addresses. The program sees a contiguous address space, but the OS can scatter those pages anywhere in physical memory. The key insight is that nothing requires contiguous physical memory. Pages can be anywhere, which eliminates external fragmentation. VLM applies the same strategy to the KV cache. a virtual memory system purpose-built for attention. Concretely, paged detention breaks the KV cache into fixed blocks, commonly 16 tokens per block. Imagine a sequence split into blocks B 0 through B7. A block table records the mapping from logical block order to physical block locations. Logical blocks 0 through 7 might map to physical positions 5 270 12 3 9 and 15. In other words, the data is non-ontiguous in physical memory, and that's fine because the table translates for us. This simple change eliminates fragmentation, allows dynamic growth as tokens generate, and makes sharing straightforward. Let's walk a single request. The user asks to generate 64 tokens. Dividing by 16, we need four blocks, ceiling of 64 over 16. As tokens are produced, we fill block zero for tokens 1 to 16. then block one for tokens 17 to 32, then block two, then block three. When the request completes, we return all four blocks to the free pool immediately. We only allocated what we needed. We never pre-reserved a giant region, and the memory is ready for the next request right away. Now, the real superpower, prefix sharing. Suppose three users share the same prompt, explain quantum computing in, and then diverge. One asks for simple terms, another for technical terms, another for a single sentence. Without sharing, we would store that prompt three separate times, three times the memory waste. With paged detention, we store the shared prefix once. All three chats reference the same physical blocks for that prefix with pointers from each request to the shared region. When a chat diverges, it continues by writing new tokens into new blocks, leaving the shared prefix intact. The memory savings are dramatic, about 67% saved in this example, and they scale with the number of concurrent requests. Continuous batching delivers the other half of the speed up. In static batching, you start four requests together and wait for all of them to finish before you add new ones. If one request finishes early, it sits idle while the others catch up, must wait for others, and the GPU waste cycles. With continuous batching, as soon as a request finishes, a new one takes its place in the very next iteration. You can add and remove requests at any time, so the GPU stays busy.
