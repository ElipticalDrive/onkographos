Goal
Implement tools extract.surface (currently a stub raising "not yet implemented" in cli/tools/extract_surface.py), producing a real textured mesh from a GaussianCloud via the MeshExporter port already defined for it.
Background
ports/mesh.py's MeshExporter protocol (export(cloud, path, *, format, **params)) has existed since #54 specifically for this stub, deliberately kept when splat mesh (TripoSR) was removed as unrelated. cli/tools/extract_surface.py accepts input/output/--to obj|gltf|usdz and immediately exits.
Two reference pipelines exist for "Gaussian splat -> clean textured mesh": SuGaR (Anttwo/SuGaR, CVPR'24, arXiv:2311.12775) regularizes Gaussians to align with an implicit surface, extracts a triangle mesh via Poisson reconstruction, then re-binds Gaussians to mesh triangles for further refinement; Gaussian Opacity Fields (GOF) (arXiv:2404.10772) extracts meshes directly from Gaussian opacity fields via ray-marching-based marching tetrahedra, generally cleaner on complex/unbounded scenes than SuGaR. Both reference implementations depend on a CUDA training/regularization loop (the standard 3DGS rasterizer) that splat doesn't have yet (see #62) — but the mesh-extraction step itself (Poisson reconstruction, a standard Open3D/CGAL-class algorithm) is CPU-feasible independent of that loop. 2DGS (arXiv:2403.16188, already a candidate representation via gsplat-mlx per #62) produces surfels that align to the true surface far better than volumetric 3DGS, making mesh extraction meaningfully easier if adopted as the training representation — this issue's difficulty is substantially lower if #62 lands with 2DGS support first.
Scope
Design decision: gate this on train: implement per-scene Gaussian optimization backend, clarify overlap with gaussian's mlx3d-capture #62 (train stub) landing with a regularized/2DGS-capable representation, vs. attempt extraction directly on today's mlx3d-capture output (likely lower quality, unregularized Gaussians).
Study SuGaR's and GOF's mesh-extraction algorithms specifically (not their training loops) as the reference technique to reimplement.
Implement Poisson-surface-reconstruction-based extraction (or ray-marching/marching-tetrahedra per GOF) against GaussianCloud.means/opacities/scales in Python (Open3D or an equivalent CPU-side library).
Bake per-vertex or UV-mapped color from sh_dc/sh_rest onto the extracted mesh.
Wire the real implementation into ports/mesh.py's MeshExporter protocol, replacing the stub in cli/tools/extract_surface.py.
Support the already-declared output formats (obj, gltf, usdz).
Notes
This is a substantial, high-effort epic — scope as its own longer-running project, not a quick win. License review needed on SuGaR/GOF reference repos (INRIA-lineage likely) before vendoring anything; reimplement the extraction algorithm from the papers independently. Depends conceptually on #62; consider deferring until that lands.
