Hypothesis
Volumetric loss weight sweep at canonical SF-AdamW lr=3e-3: vol_weight ∈ {0.25, 0.5, 1.0 control, 2.0, 4.0}. The current loss is loss = vol_loss + cfg.surf_weight * surf_loss — surface has explicit weight 10.0 (canonical), but volumetric weight is implicit 1.0 and has never been swept. This is the symmetric axis to tanjiro's surf_weight work (#4207) and is the only orthogonal loss-balance lever untested.
Why this is high-value:
surf_weight sweep at SF-AdamW lr=2e-3 — {5, 10, 15, 25} with --seed 1 #4207 R2 found surface loss is saturated — train_surf ≈ 0.0265 across surf_weight ∈ [5, 15]. The loss form and volumetric balance are the remaining axes.
At canonical surf_weight=10 and vol_weight=1, the measured surf/vol contribution ratio is ~4.5× (tanjiro surf_weight sweep at SF-AdamW lr=2e-3 — {5, 10, 15, 25} with --seed 1 #4207 R2). Raising vol_weight to 4.0 would invert this to a vol-dominant regime — a regime never explored.
Cheap, orthogonal. One Config flag, training-loop only, no architecture change.
Your clean canonical reproduction in #4350 (52.279, +0.04%) confirms: adding this single Config field should not introduce RNG drift the way the --surf_weight or --n_layers flags did (which both correlated with +2.47% drift). Arm A should be within 0.5% of 52.258.
Instructions
Required code change
In target/train.py:
Add to Config dataclass (near surf_weight: float = 10.0):
```
    vol_weight: float = 1.0  # volumetric loss weight (was implicitly 1.0)
```
In the training loop (~line 726), change:
```
# find:
loss = vol_loss + cfg.surf_weight * surf_loss
# change to:
loss = cfg.vol_weight * vol_loss + cfg.surf_weight * surf_loss
```
That is the only code change. The evaluate_split function only returns MAE metrics (not loss), so no change there.
Test: python train.py --debug --vol_weight 2.0 — should run without crash.
Infra commit before launching arms.
