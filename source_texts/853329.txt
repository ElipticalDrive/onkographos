Task
After #7251 establishes the correct production f32/f64 -> u64 high-half lowering and scratch plan, migrate that selected sequence into typed post-register-allocation machine records consumed by both assembly and object serializers.
This issue owns only the float-to-integer direction. It must encode #7251's reviewed production semantics rather than independently inventing a second correction, and it does not retire the global direct-object Cast gate.

Acceptance criteria
First land/consume backend: fix high-half float-to-u64 runtime casts #7251's production tests and exact selected sequence. Machine-record selection has no separate high-half algorithm or threshold policy.
Runtime f32/f64 -> u64 returns truncation toward zero for every representable finite input in [0, 2^64), with focused cases immediately below/at/above 2^63 and the greatest source-representable value below 2^64.
Negative, NaN, infinity, and out-of-range inputs preserve backend: fix high-half float-to-u64 runtime casts #7251/SPEC 3.8's unspecified-but-defined, non-trapping behavior. Assembly and object serializers agree without strengthening the portable numeric contract.
Production emits stable typed labels/branches, exact threshold data identity/payload, compare/subtract/conversion/high-bit restoration records, and explicit def/use/clobber facts using backend: fix high-half float-to-u64 runtime casts #7251's planned GP/XMM homes.
Neither serializer chooses the 2^63 split, condition, precision, scratch register, threshold encoding, restoration operation, or branch targets. No formatted label parsing or serializer-side high-half decision remains.
Direct-register and every forced-spill source/result shape preserve live inputs, threshold, working value, and result. Invalid alias/class/width/precision combinations fail before serialization.
Assembly serialization is byte-identical to the corrected backend: fix high-half float-to-u64 runtime casts #7251 output on Linux and Windows. Exact ELF/COFF byte/data/local-fixup goldens cover f32/f64, both paths, low/extended registers, displacement boundaries, prefix/REX order, and threshold alignment/order.
Optimized and non-optimized runtime differentials use an opacity barrier, compare assembly versus shared-record object results at opt0/1/2, and cover CTFE/runtime agreement for all in-range boundaries.
Do not remove the global Cast exclusion here; final whole-matrix eligibility and fallback retirement are a separate backend: migrate bidirectional u64-float high-half cast records #7254 child.
Report record/data bytes, allocations, backend time, code size, and peak memory before/after. Run typelisp fmt, focused tests under the repository cap, backend: fix high-half float-to-u64 runtime casts #7251 gates, bootstrap/fixpoint, and hosted Linux/Windows CI.

Active PR #7573 head 82c114a30e6b now supplies the measured production shape this migration must consume if it lands unchanged. I did not modify or review the moving PR; both CI jobs are still running, so re-check its merged head before implementation.
Exact current selection
For both source precisions the PR collects one canonical 2^63 literal through the existing float-rodata collection:
f32 bits: 1593835520 (0x5f000000);
f64 bits: 4890909195324358656 (0x43e0000000000000).
The post-regalloc selected control sequence is:
copy/load the source into one disposable XMM scratch;
ucomiss/ucomisd threshold(%rip), scratch;
jae high;
low predecessor: cvttss2siq/cvttsd2siq scratch, result, then unconditional jump to done;
high predecessor: destructively subss/subsd threshold(%rip), scratch, perform the same signed conversion, then btsq $63, result;
done, followed by the existing destination store when spilled.
The two threshold operands are two distinct semantic RIP-relative reference sites to the same canonical data identity. The conditional branch is unsigned jae after ucomi; do not substitute a signed condition or compare operand order. NaN/negative/out-of-range behavior remains the non-trapping unspecified-but-defined result inherited from #7251/SPEC, not a new trap or clamp.
Exact scratch and record handoff
A float-to-u64 cast always requests one disposable XMM role even when the source is register-homed, because the high path mutates it. The direct fixture copies %xmm2 into planned %xmm4; a spilled source loads directly into that scratch.
A register-homed destination is the result GP directly (fixture %r12), so the direct case has one scratch slot total. A spilled destination requests one planned GP (fixture %r8) and stores it afterward, so both-spilled source/destination has two scratch slots total: one XMM plus one GP.
Emit two stable local labels (high, done) and two control edges. Both predecessor conversions define the same result GP; the high path then read/modifies it with btsq. Record flags explicitly: ucomi defines the condition consumed by jae, while btsq clobbers CF on only the high path and no post-join flag fact may escape the cast.
Preserve the source XMM/home as live input, the destructive scratch lifetime through the selected predecessor, result definition on both paths, and the optional spill store after the join. Invalid aliasing must fail before serialization rather than silently mutate the source or threshold.
Assembly parity should pin exactly two conversion opcodes in the rendered sequence, two threshold references/fixups, one jae, one unconditional join jump, and one btsq $63; threshold data is emitted once per precision through backend: migrate scalar physical moves, float rodata, and RIP-relative fixups #7301 identity/deduplication.
#7354 remains blocked even after #7251 merges because #7055/#7202/#7253/#7301/#7345 are still open. No additional implementation issue or label change is appropriate. When #7573 closes #7251, update only that dependency state and use the final merged sequence as the authoritative baseline.
