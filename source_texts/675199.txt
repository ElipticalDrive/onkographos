Introduction: lossy compression in science and data integrity
1.1
Lossy vs lossless codecs
A lossy codec allows a controlled deviation of the output data from the input data in exchange for a
smaller size. In a scientific context, the key is an explicitly defined error model, not subjective
quality.
Typical models:
• Bounded L∞ (absolute error bound): maxi |xi − x̂i | ≤ ε.
i|
• Relative bound: maxi |x|xii−x̂
|+δ ≤ εrel .
• Energy measures: RMSE, L2, PSNR as additional characterization.
Note on “rounding after the 12th decimal place”. In many scientific applications, an error on
the order of 10−12 (for data scaled around ≈ 1) is acceptable. One must remember, however, that
the meaningfulness of such a tolerance depends on the scale and units of the data: for values on the
order of 106 or 107 , the float64 representation precision (ULP) may be larger than 10−12 .
1.2
Engine vs application (the role of the client)
SZY v8 is an engine. This means:
• the engine provides the mechanics (format, pipeline, integrity, threads, decode-into),
• the client selects parameters (e.g., eps, block B, number of workers, quantization mode,
event policy),
• “scientific” correctness is evaluated in the context of real data and the client’s requirements,
• for data classes not matching the model, the engine may explicitly refuse to satisfy the requested
bounded-error instead of returning a result that violates the guarantee.
The tests in this document show that with sensibly chosen parameters for image-like and noisy data
classes, SZY meets quality expectations (controlled error) and offers favorable trade-offs relative
to reference codecs. At the same time, the benchmark also includes stress-test / out-of-domain
cases whose purpose is not to prove the superiority of the model but to establish the boundaries of
applicability.
1.3
Why integrity is part of the format
In practice, there is a risk of silent data corruption. In SZY v8, integrity is part of the container:
• data_sha: SHA-256 of the data section (index + tile records),
• container_sha: SHA-256 of the entire container.
This makes it possible to detect damage and unambiguously return errors: SZY_E_SHA_DATA and
SZY_E_SHA_CONT.

3
SZY v8 as an engine and format: applications and niches
3.1
What SZY v8 is (engineering definition)
SZY v8 is a tile-based bounded-error codec for 2D data and a container with integrity and an
index, exposed as a C library / DLL.
Key engine features:
• Tile independence: the image is split into B × B tiles; each tile record is independent. This
enables:
– local compression/decompression (region-of-interest),
– straightforward parallelism over tiles,
– resilience to local damage (damage to one tile does not invalidate the whole).
• Index blob: a list of tile lengths (varuint), enabling fast computation of tile offsets and
balanced work distribution across threads.
• Parallel decode: tile decoding in parallel based on the index, with control of worker count
and parallel_min_tiles threshold.
• Decode-into: decompress directly into a user-provided buffer (without allocating an additional
output image) — important for HPC/FORTRAN codes that manage memory themselves.
• Integrity: SHA-256 of data and container as part of the format; the user does not need to
implement checksums.
• Type support: float64, float32, uint16 — covers typical scientific data (climate fields, sensors,
image intensities).
• Cross-platform: little-endian format, C implementation, can run on x86-64 and ARM
(including edge/embedded).
3.2
Where SZY v8 makes scientific/technical sense
The engine is especially useful in the following scenarios:
4
Climate and oceanography (NetCDF, geophysical grids).
• 2D fields (SST, near-surface temperature, pressure) from climate models or reanalyses,
• horizontal slices from 3D simulations (ROMS, NEMO, ICON),
• data streams from catalog services (THREDDS, pyDAP) after conversion into RAW C-ordered
blocks.
For such data, the key is:
• preserving field shape (gradients, mesoscale structures),
• error control (so as not to break sensitive assimilation/diagnostics),
• throughput (HBM/SSD/ethernet).
The benchmark shows that on a synthetic climate field (f32) SZY reaches a ratio of 103 at eps=10–20
and meets the bound.
Satellite imagery and optical sensors.
• GeoTIFF/CCSDS extracted as uint16,
• optical sensors (Landsat, Sentinel) reduced to a single band,
• downlink and archiving at ground stations.
For this data class, SZY v8:
• yields ratio ∼8–16x at eps=5–20, while Zstd/Blosc2 ∼4.4x,
• provides a hard error bound (important for downstream processing, e.g., vegetation indices),
• allows partial image decode (tile-based).
Medical (CT) and astronomical (CCD) data.
• Example synthetic CT/CCD in uint16 format (simulating HU or ADU),
• Zstd/Blosc2 offer ∼1.7–1.8x, while SZY at eps=20 reaches 5–6x (with error control).
SZY is a natural candidate for long-term archiving: eps can be chosen so that the error is substantially
smaller than the noise/instrument variance.
Sensor streams (UCI: AirQuality, Energy) and time series.
• For sensor_energy_uci at eps=20, B=128: SZY gives 532x at max_err≈19.6; SZ3 gives 470x,
ZFP ∼126x, Zstd ∼38x.
• For sensor_airquality_uci at eps=20, B=128: SZY and SZ3 are in the same ratio class
(196x vs 206x), SZY is faster.
This suggests potential for SZY as a building block in IoT/telemetry pipelines where:
• streams are larger than raw storage capacity,
• a small explicit measurement error is acceptable,
• encoder/decoder speed on laptop/edge-class CPU is important.
5
HPC simulations (CFD, turbulence, mesoscale phenomena).
• 2D cross-sections from HDF5/NetCDF files (e.g., Hurricane, Miranda),
• checkpoint dumps into an archive (tile-encoded),
• partial reads via decode-into (an MPI rank reads only its own fragment).
Here SZY v8 provides not only ratio but also an engine: easy integration into existing Fortran/C++
codes (C library, decode-into buffer).
3.3
Why comparisons to leaders are necessary even for a niche
Even if you build a niche, you still need comparisons to leaders, because:
• the market understands SZ3 and ZFP as reference points (scientific codec vs “image codec”),
• a benchmark establishes the trade-off map: bitrate vs error vs time,
• comparisons reveal data classes where it is worth adding optional modes (e.g., trend, other
predictors).
Note on out-of-domain benchmarks. The tests also include synthetic data with structure that
is extremely unfavorable for the current model (e.g., sharp discontinuities at tile boundaries). These
are not target data, but they are useful as a boundary benchmark: they show when the method
loses effectiveness or should explicitly return a bounded-error failure rather than pretending success.
3.4
Differences vs SZ3 and ZFP (what we compare and what we do not)
ZFP (a specialized solution). ZFP [2] is specialized for compressing FP arrays (block-based, with
fixed-rate/fixed-precision/fixed-accuracy modes). It is an excellent reference as a pure floating-point
codec, but:
• it is not a container-engine (no SHA, no index, no decode-into as standard),
• it does not support uint16 as a first-class type (conversion required).
In benchmarks, SZY v8 very often beats ZFP at the same eps in ratio, especially on sensor and
image-like data.
SZ3 (a framework / often maximizes bitrate). SZ3 [3] is a modular framework that often
achieves very high ratios on data classes matching its strategy (especially very smooth fields). It is a
good reference as an “upper bound” on bitrate under a given error model. On the other hand:
• it is complex to configure and integrate (multiple modes, pipelines),
• it does not include a built-in container with SHA and tile index,
• it can be slower than SZY v8 on the same datasets at the same eps.
SZY v8 (positioning). SZY v8 optimizes simultaneously:
• bounded L∞ (controlled error),
• encode/decode speed and MT decode,
• integrity and robustness (SHA),
• integration ergonomics (decode-into, peek-shape, C API, Python wrapper),
6
• uint16 support (important for images).
From benchmarks:
• on smooth climate fields, SZ3 has better bitrate (2–3×),
• on real sensor data, SZY can beat SZ3 in ratio at the same eps (e.g., sensor_energy_uci),
• SZY consistently beats ZFP at the same eps and is much better than the lossless baseline for
most datasets.
3.5
Lossless as a baseline, not a goal
The tests include lossless codecs (Zstd, Blosc2) as a baseline:
• they show how much redundancy is present without loss,
• they help decide whether lossy compression is worth it for a given data class,
• they are not a design target of SZY v8 (SZY is designed for lossy scientific).

Portable specification: types, endianness, varuint
6.1
Endianness
In the container and tile record, fixed-width numbers are encoded in little-endian: u8, u16le,
u32le, u64le, i16le, f32le, f64le. Floats are IEEE-754.
6.2
Varuint
Varuint encodes uint64 as a sequence of bytes:
• each byte carries 7 bits of payload,
• MSB=1 indicates continuation,
• MSB=0 terminates the integer.

Tile record v8 format — full specification
Note: format specification vs current C encoder implementation. The tile record v8
specification includes fields and modes that the reference decoder understands for compatibility and
extensibility. This does not mean that the current C encoder generates all variants. In particular,
the current C encoder:
• uses the Lorenzo2D predictor,
• does not generate trends other than TREND_NONE,
• includes infrastructure for shuffle16 and bitplane shuffle for qbits=16, but the v8 DLL uses
shuffle16 by default; bitplane can be enabled in experimental builds,
• no longer generates amp_mode=2 (float16) for new streams (the decoder still accepts mode 2
only for backward compatibility).

Events: indices and amplitudes
Indices. Encoded as varuint deltas (delta coding) over indices in the flattened tile (row-major).
Amplitudes. amp_mode defines the representation of event amplitudes:
• 0: scale (f64le) + ne int8 bytes,
• 1: scale (f64le) + ne int16le values,
• 2: ne float16 values (u16le) — legacy, decode-only,
• 3: ne float32le values.
Current state of the v8 C encoder. The current implementation no longer generates mode
2 (float16) for new streams, because for large amplitudes it could lead to non-finite values and
unstable reconstruction. The decoder still accepts amp_mode=2 solely for backward compatibility
with older files.
Meaning of events for bounded-error. Events represent local deviations that cannot be
efficiently handled by quantization and prediction alone under the requested eps. If the number of
required events exceeds the budget imposed by client configuration, the engine should not “pretend
success”; it should return a bounded-error failure (see the error-code section).

Algorithm: encode/decode (in detail)
9.1
Encode: per-tile steps
For a B × B tile (npix=B 2 ):
1. Compute the mean µ and center the tile: ci = xi − µ.
13
2. (Optional) events: extract sparse deviations |ci | above a threshold into a list (idx+amp), if they
fit within the event budget imposed by configuration.
3. Choose inv_scale for quantization (depending on mode and eps).
4. Quantize to int8/int16: qi = round(ci · inv_scale), with clipping.
5. Lorenzo2D prediction on q → deltas d (mod 2qbits ).
6. Median bias of deltas: d′i = di − bias (bias computed as signed median).
7. (Optional) zigzag: signed → unsigned.
8. (For qbits=16) shuffle16 or bitplane shuffle (if enabled).
9. Entropy coding: ZSTD/ZLIB/NONE.
10. Write tile record: header + parameters + events + payload.
Important property of the current implementation. If in bounded-error mode the number
of required events exceeds limits (events_max_per_tile, events_max_frac), the encoder returns
SZY_E_BOUNDS. Additionally, the implementation contains an internal per-tile fallback mechanism
(e.g., relax eps, disable events), but from the perspective of the external contract, bounded-error
comes first: if it cannot be maintained, it is better to return an error than to violate the bound.
9.2
Decode: per-tile steps
1. Read the tile record.
2. Decompress payload (ZSTD/ZLIB/NONE) → body of size expected.
3. Undo shuffle16 or bitplane (if flagged).
4. Undo zigzag (if flagged).
5. Bias: di = d′i + bias.
6. Inverse predictor (Lorenzo2D) → qi .
7. Dequantize: ci ≈ qi /inv_scale.
8. Reconstruct: x̂i = ci + µ + trend(i, j).
9. Add events (if present): x̂idxk += ampk .
10
Parallelism: tile-based decode and encode
10.1
Parallel decode
If the index is present, the engine computes tile offsets based on lengths and launches workers. In
the reference implementation:
• POSIX: a simple thread-pool (pthreads),
• Windows: a fixed worker pool, not “thread per tile”.
10.2
Parallel encode
Encode can be done in parallel over tiles; then tile records are concatenated in deterministic order
(ti=0..ntiles-1) to preserve a repeatable container.

11.2
Memory rules (ABI)
• The output buffer from compress is allocated in the DLL and must be freed via
szy_free_buffer().
• decode-into writes directly into the user buffer without extra copies (requires a buffer of the
correct size).
11.3
Threading policy
• szy_hw_threads() returns the number of available hardware threads.
• The *_ex API takes num_workers:
– 0 = auto,
– > 0 = forced.
• If the requested number exceeds available: SZY_E_THREADS.
11.4
API error semantics
Not all errors returned by the API mean a corrupted file or an implementation bug. In practice:
• SZY_E_SHA_*, SZY_E_INDEX, SZY_E_TILE indicate integrity/stream correctness problems,
• SZY_E_THREADS indicates an invalid execution configuration,
• SZY_E_BOUNDS indicates that with the current settings the bounded-error cannot be satisfied
for the input.
From a systems perspective, SZY_E_BOUNDS is desirable behavior: it is better to explicitly refuse
compression than to return a stream that violates the declared error bound.

11.6
DLL function descriptions (what they do and how to use them)
The description below refers to the listing above (selected exports). The goal is to unambiguously
explain parameter semantics, memory, and return codes.
szy_hw_threads(). Returns the number of available hardware threads (at least 1). Useful for
setting num_workers=0 (auto) or validating that the application does not request too many threads.
szy_free_buffer(ptr). Frees a buffer allocated by the DLL (e.g., compress output). Contract:
this pointer must come from SZY; do not free it by other means (e.g., free() in the application) to
avoid mixing allocators.
szy_strerror(code). Returns a static string describing the error code. Useful for logs and diagnostics.
szy_peek_shape_v8(buf,n,H,W,B). Reads only the container header and returns dimensions (H,W)
and block (B) without decoding data. The function verifies container integrity (SHA) just like a
full unpack.
szy_decompress_into_buffer_ex2(...) (decode-into). Decodes a container into a user buffer:
• out points to a double array of at least H*W elements,
• out_elems is the number of elements in out (not bytes),
• num_workers: 0=auto, >0=requested thread count (strict mode),
• parallel_min_tiles specifies from how many tiles it is worth switching to parallel mode.
On decoder error, the contents of out should be considered invalid.
szy_compress_buffer_ex(...), szy_compress_f32_ex(...), szy_compress_u16_ex(...). Encode a double, float, or uint16 matrix into an SZ2D v8 container buffer.
• eps is the bounded-error parameter (absolute bound),
• B is tile size (e.g., 64 or 128),
• num_workers: 0=auto, >0=requested thread count (strict mode),
• out_buf/out_n are filled on success; out_buf must be freed via szy_free_buffer().
The encoder may return SZY_E_BOUNDS if with the given eps and internal configuration it cannot
maintain the bounded-error guarantee.

Main conclusions (v8 state after tests)
17.1
What works and what is the engine value
• Integrity: SHA-256 of container and data works and is reported unambiguously.
• Threads: the engine exposes external thread control and validation (SZY_E_THREADS).
• Performance: fast decode; tile index enables efficient MT decode and decode-into.
• Position vs ZFP: in many bounded-error cases SZY provides better ratio than ZFP while
maintaining max_err.
• Real image-like and sensor data: on UCI/jbrownlee/SST-synthetic, SZY meets the bound
and is competitive with SZ3, often faster.
• Safe bounded-error semantics: when the current model cannot meet requested eps, the
engine can explicitly refuse (SZY_E_BOUNDS) rather than returning a stream that violates the
guarantee.
17.2
What comparisons to SZ3/ZFP teach (without changing the niche)
• On super-smooth fields, SZ3 can achieve much better bitrate — motivating evolution of SZY
toward optional trends (the decoder already anticipates trend_id; the specification allows it).
• ZFP, despite its mathematically sophisticated construction, often has weaker ratio at the same
eps on practical 2D scientific data; SZY fills a gap between “pure ZFP” and heavier SZ3, while
also providing a full engine (container, SHA, index).
17.3
Development recommendations (consistent with the tile-based engine philosophy)
• Optional trend encoding (plane3/poly) for very smooth data classes: would help where SZ3
currently has an advantage.
• Expand client-side configuration (e.g., explicit control over event policy and quantization
mode) while keeping simple defaults.
• Strict vs best-effort mode:
22
– strict — always bounded-error or SZY_E_BOUNDS,
– best-effort — experimental mode where the encoder may slightly exceed eps if the client
accepts it.
• Add eps_over_range as a default metric in reports to better show eps aggressiveness across
datasets.
• CI + CMake + regression tests (golden files) + fuzz decode as a permanent test suite
(decoder robustness verification).
17.4
Scientific potential and practical advantages
Based on the entire documentation and results, the following scientific/technical theses can be stated:
• SZY v8 is a full-fledged scientific lossy codec for 2D data with:
– a hard L∞ bounded-error model,
– a portable specification (container, tile, SHA),
– an open C implementation (no exotic dependencies).
• In benchmarks on real data (UCI sensors, time series, GeoTIFF imagery) SZY achieves:
– ratios in the hundreds (sometimes thousands) at eps around 5–20,
– encoder/decoder times of single to tens of milliseconds,
– full error control.
• SZY fills the gap between:
– “classic” lossless (Zstd, Blosc2),
– ZFP (excellent mathematically, but no engine),
– and heavier SZ3 (in terms of configuration/overhead).
In many scenarios (telemetry, scientific archiving, HPC pipelines with on-the-fly decoding) SZY
offers the most balanced compromise.
• Therefore SZY v8 has real potential as a component:
– in climate/ocean codes (NetCDF/HDF5 → SZY),
– in imaging pipelines (satellite, medical, astronomy),
– in edge/IoT applications where speed and simplicity matter and a small controlled error
is acceptable.

B
Appendix B: Minimal compliance specification (must-pass)
A v8-compliant implementation should:
• recognize magic="SZ2D" and version=8,
• use little-endian for fixed-width types,
• implement varuint as specified,
• verify SHA-256 (data_sha, container_sha),
• correctly parse the index blob (if flags&1),
• decode tile records and validate payload length after decompression.
