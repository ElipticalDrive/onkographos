Description
src/world/chunk_mesh.zig (704 lines) mixes greedy meshing, ambient occlusion calculation, lighting sampling, and biome color blending. This violates Single Responsibility Principle and makes testing individual stages difficult.
Current Problems
SRP Violation: Handles greedy meshing, AO calculation, lighting sampling, biome color blending, subchunk management, AND GPU upload
OCP Violation: New meshing features require modifying meshSlice() or addGreedyFace()
DIP Violation: Direct dependency on TextureAtlas, block_registry, biome_mod
Technical Details
Current mixed structure:
```
pub const ChunkMesh = struct {
    // Meshing stages all mixed together
    fn meshSlice(...) !void {  // Greedy meshing
        // Builds 16x16 masks
        // Greedy rectangle expansion
        // Calls addGreedyFace()
    }
    
    fn addGreedyFace(...) void {
        // AO calculation (lines 546-619)
        // Lighting integration (lines 600-618)
        // Biome coloring (lines 621-704)
        // Vertex emission
    }
    
    fn getAOAt(...) f32;  // AO sampling
    fn getLightAtBoundary(...) PackedLight;  // Lighting
    fn getBlockColor(...) [3]f32;  // Biome colors
};
```
Proposed Solution
Extract each meshing stage to dedicated module:
meshing/greedy_mesher.zig - Mask building, rectangle expansion, quad emission
meshing/ao_calculator.zig - Ambient occlusion sampling and vertex AO calculation
meshing/lighting_sampler.zig - Sky/block light extraction and vertex lighting
meshing/biome_color_sampler.zig - 3x3 biome sampling and color blending
meshing/chunk_mesher.zig - Orchestrates above stages (current ChunkMesh becomes coordinator)
Pass Criteria
chunk_mesh.zig reduced to <300 lines (orchestrator only)
Each meshing stage extracted to standalone module <250 lines
Each stage independently testable with mock data
ChunkMesh delegates to stage modules, contains no direct logic
All existing tests pass: nix develop --command zig build test
No visual changes to rendered chunks (pixel-perfect verification)
No performance regression (mesh generation speed maintained)

This is a well-structured refactoring proposal that addresses legitimate architectural concerns in the codebase. Here's my analysis:
Classification: Refactoring/Feature Request (not a bug)
Assessment:
Scope: Appropriately scoped. All changes are confined to the meshing pipeline within src/world/, making this a cohesive refactor suitable for a single PR
Technical merit: The SRP violations described are real. chunk_mesh.zig at 704 lines handling 5 distinct concerns makes testing and extension difficult
Pass criteria: Clear and measurable, including the critical "no visual changes" and "no performance regression" requirements
Concerns to address during implementation:
Memory ownership: When extracting stages, clarify allocator responsibilities - who owns temporary buffers (masks, intermediate vertices)?
Performance: The greedy meshing loop is performance-critical. Ensure extracted modules don't add function call overhead in hot paths. Consider inline hints where appropriate
Testing strategy: Each stage will need mock data - consider creating tests/meshing/ fixtures (mock chunks, known AO patterns, fixed biome data)
Code pointers for the refactor:
Current meshing logic lives in src/world/chunk_mesh.zig:1-704
Key functions to extract: meshSlice() (greedy algorithm), addGreedyFace() (vertex emission), getAOAt() (AO sampling), getBlockColor() (biome blending)
The ChunkMesh struct should become a thin coordinator, delegating to injected stage modules
Recommendation: Approve this refactor. It's a clean separation of concerns that will make future meshing optimizations easier to test and integrate.
