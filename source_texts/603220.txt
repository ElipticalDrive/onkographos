Goal
Replace render's v1 flat, opaque, unoriented point splats with real ellipsoid-shaped, alpha-blended Gaussian rendering, and default the camera to a real captured viewpoint (#59) instead of the current auto-fit synthetic camera.
Background
This is the second of two independent sub-problems #58 explicitly called out for a split. Today's adapters/render/_blender_script.py builds a Blender point cloud colored by the flattened SH DC term only, with a single scalar radius per point (median_radius * 0.03, uniform across every point regardless of that point's actual scales) rendered via an opaque Emission shader — no ellipsoid orientation from rotations, no anisotropic scale, no opacity blending. This was a deliberate v1 scope cut (see #50). _frame_camera() frames the shot via a median-center/robust-radius auto-fit heuristic, landing at an angle unrelated to the actual capture geometry — with only 3-10 input photos, a Gaussian reconstruction is only photorealistic from viewpoints close to the real capture cameras, so this auto-fit angle is the dominant reason renders look worse than a reference viewer (e.g. macOS Quick Look, whose default angle happens to land near the original capture) more than the flat-splat shading technique itself.
Two independent upgrades, matching GaussianCloud's existing (already computed, currently unused by the renderer) fields:
Orient/scale each point as a true ellipsoid using rotations (quaternion -> rotation matrix) and to_linear_scales() per-axis, alpha-blended by to_activated_opacities().
Default to a real captured camera pose (gaussian: expose SfM camera poses from mlx3d-capture reconstruction (splits #58) #59) when present on the input GaussianCloud, falling back to today's median-center auto-fit heuristic otherwise.
For the rendering-technique question specifically, Blender's own official native Gaussian-splat design task (dev design #159470, Sergey Sharybin, via radiancefields.com) is the most authoritative reference to study before inventing an approach from scratch: splats as native Point Cloud objects with position/scale/quaternion/opacity/SH attributes, initial rendering in Workbench/EEVEE via dithered opacity + mip-splatting anti-aliasing (their answer to order-independent transparency without full OIT cost), with Cycles support via ellipsoid primitives + proper depth sorting documented as the follow-up phase for correct transparency. _blender_script.py currently sets scene.eevee.taa_render_samples — i.e. it renders via EEVEE today. Per Blender's own 4.2 EEVEE Next release notes, EEVEE still doesn't do full order-independent transparency for many overlapping semi-transparent surfaces, which is exactly this renderer's use case — meaning Cycles (path tracing) is the architecturally correct target for genuinely accurate alpha-blended ellipsoid splatting, with EEVEE retained only as a fast/approximate preview mode. Community prior art worth reading before implementing: BlendSplat (a geometry-nodes-based Gaussian-splat toolkit for Blender) for node-graph technique, and SkySplat (skysplat.org, presented at BlenderCon 2025) as a working proof that a similar video-to-splat-to-Blender pipeline already runs end-to-end inside Blender's UI in practice (notably using the Rust Brush trainer as its optimization backend).
Scope
Instance oriented, per-axis-scaled ellipsoids via geometry nodes (rotation quaternion -> matrix, to_linear_scales()) instead of uniform-radius points, in _blender_script.py.
Alpha-blend by to_activated_opacities() per Gaussian.
Switch the render engine target to Cycles for the true alpha-blended path (keep EEVEE as an optional fast-preview mode, e.g. --engine eevee|cycles).
Consume gaussian: expose SfM camera poses from mlx3d-capture reconstruction (splits #58) #59's captured camera pose in _frame_camera() (or its replacement) when present on the input GaussianCloud, falling back to the current median-center auto-fit heuristic when absent.
Benchmark visually against the current v1 output and a reference viewer (e.g. macOS Quick Look) on the same capture.
Notes
Depends on #59 (needs a real pose to consume) and benefits from #55 if the pose ends up as a first-class contract input rather than metadata. registry/render.py's own docstring already flags that a second render backend (e.g. a native mlx3d/gsplat rasterizer) would warrant adding the ModelDescriptor/catalog pattern currently skipped for the single-backend case — out of scope here but worth remembering if a non-Blender renderer is added later. Relates to #58, which this issue splits.
