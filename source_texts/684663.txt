Summary
The RHI test texture-shared-cuda.vulkan (CUDA↔Vulkan shared-texture interop) intermittently fails a CHECK_GE numeric-tolerance assertion (in the test harness around tests/testing.h:228). It appears to be a PR-agnostic numeric-tolerance flake, not a real regression.
Observed in shader-slang/slang CI (which runs the vendored slang-rhi test suite) on 3 unrelated PRs over ~1 week:
Emit conservative-depth layout qualifier for SV_DepthGreaterEqual/LessEqual on GLSL targets slang#11693 (2026-06-24)
Fix #11731: emit UniformMemory semantics for atomics on legacy Uniform storage class slang#11735 (2026-06-25)
Add diagnostic warning levels (-Wall/-Wextra/-Wpedantic) slang#11812 (2026-07-01)
Each occurrence: 965/966 rhi cases pass, only texture-shared-cuda.vulkan fails, and only on windows-release-gpu-rhi — the same rhi suite passes on windows-debug-gpu-rhi and every other platform. A rerun clears it. The three PRs are unrelated (varied frontend / CI / refactor changes that cannot affect CUDA↔Vulkan interop), which is what confirms it's a flake rather than a regression.
Impact
Recurring windows-release-gpu-rhi reruns across unrelated shader-slang/slang PRs — each occurrence costs a rerun cycle.
Suggested fix
Either widen the CHECK_GE numeric tolerance for the CUDA↔Vulkan interop comparison (if the intermittent miss is within acceptable numeric error), or quarantine / mark-flaky texture-shared-cuda.vulkan on that config until the tolerance is right-sized. A maintainer familiar with the expected interop numeric bounds should choose the tolerance.
Notes
Surfaced from CI-health monitoring of shader-slang/slang; the specific failing runs are on the referenced PRs' test-slang-rhi / windows-release-gpu-rhi jobs.

Good questions — I dug into the RHI surface. Short version: RHI already has the right synchronization primitive (IFence, a shareable timeline-valued fence), and Vulkan/D3D12 already implement it end-to-end. There are really two distinct gaps: (a) the CUDA fence gap — CUDA's IFence is a host-value stub and can't import a shared handle; and (b) a cross-API resource-ownership gap — the generic shared-texture path performs no Vulkan queue-family ownership transfer to/from VK_QUEUE_FAMILY_EXTERNAL, and RHI exposes no API for it. So the fix is mostly reuse of IFence for (a), plus new surface for the import direction and for (b).
1. What already exists
IFence (include/slang-rhi.h:1640) is a timeline-valued fence with cross-API sharing baked into its contract:
FenceDesc.isShared (:1635) + IFence::getSharedHandle() (:1652) — create an exportable fence and get an OS handle for it.
getCurrentValue/setCurrentValue (:1646,:1649) — the timeline value (Vulkan backs this with a VK_SEMAPHORE_TYPE_TIMELINE semaphore, D3D12 with an ID3D12Fence).
SubmitDesc.waitFences / signalFences (+ values) (:2828–:2833) — GPU-side wait/signal at submit time.
IDevice::createFence (:3699), host-side IDevice::waitForFences (:3710).
And both graphics backends already implement it fully:
Vulkan — isShared creates an exportable VK_SEMAPHORE_TYPE_TIMELINE semaphore (src/vulkan/vk-fence.cpp:32,:44,:56), getSharedHandle exports it via vkGetSemaphoreWin32HandleKHR/vkGetSemaphoreFdKHR (:112), and submit does a real timeline vkQueueSubmit wait/signal.
D3D12 — D3D12_FENCE_FLAG_SHARED (src/d3d12/d3d12-fence.cpp:32), CreateSharedHandle (:82), queue Wait/Signal.
So on the producer (Vulkan) side there's nothing to add to the fence implementation itself (the ownership-transfer piece below is separate).
2. Why the CUDA path can't use it today
Three concrete synchronization gaps on the CUDA side (the ownership gap in §3 is separate):
CUDA IFence is a host-value stub, not a real GPU semaphore. getSharedHandle returns SLANG_E_NOT_AVAILABLE (src/cuda/cuda-fence.cpp:38); getCurrentValue/setCurrentValue just read/write an in-process m_currentValue under a mutex (:17–:29). There is no backing CUexternalSemaphore.
CUDA submit doesn't actually wait on the GPU. CommandQueueImpl::submit has a literal // TODO: wait for fence (src/cuda/cuda-command.cpp:1249) that only compares the host value and SLANG_FAILs if unmet; the signal path just calls setCurrentValue (:1306). No cuWaitExternalSemaphoresAsync/cuSignalExternalSemaphoresAsync (both are loaded in cuda-driver-api.cpp but never called in production; the surface path uses cuImportExternalSemaphore + a host-side cuStreamSynchronize workaround rather than the async wait — see below).
No import entry point in the public API. Textures and buffers have createTextureFromSharedHandle / createBufferFromSharedHandle (include/slang-rhi.h:3417,:3444), but there is no createFenceFromSharedHandle — so even a correctly-exported Vulkan timeline fence has no way to become a CUDA-side IFence.
(Corroboration this is known-unfinished: tests/test-buffer-shared.cpp:40 — // TODO: Implement actual synchronization (and not this hacky solution).)
3. Proposed RHI-level fix
Shape: reuse the existing IFence for the synchronization half; the new surface is a fence-import entry point plus a decision on how ownership transfer is exposed. No new fence concept is needed.
(sync — mostly reuse) Fence import + wire CUDA's existing SubmitDesc fence fields. Add a fence-import entry point (createFenceFromSharedHandle(NativeHandle, const FenceDesc&, IFence**)) — textures/buffers already have the analogous method, fences don't — implemented on CUDA via cuImportExternalSemaphore (the surface path does exactly this at src/cuda/cuda-surface.cpp:636), storing a real CUexternalSemaphore. Then make CUDA's submit honor waitFences/signalFences for such fences by calling cuWaitExternalSemaphoresAsync / cuSignalExternalSemaphoresAsync on the imported semaphore + value, replacing the // TODO: wait for fence host-value check. Vulkan/D3D12 already do the timeline wait/signal, so this is CUDA-only for the sync direction.
(ownership transfer — a genuine second gap, not just a detail). The shared image is VK_SHARING_MODE_EXCLUSIVE + VK_IMAGE_TILING_OPTIMAL, so correctness also needs a Vulkan queue-family release barrier to VK_QUEUE_FAMILY_EXTERNAL (with CUDA's external-memory access coordinated by that transfer + the semaphore). RHI's generic texture-barrier surface does not currently express queue-family ownership, and the only place this is done is the surface path's hand-written Vulkan barriers (src/cuda/cuda-surface.cpp:847/:1043/:1107) — it is not reachable through the public shared-texture path today. So this needs either (i) a small RHI ownership-transfer/import contract on the shared texture, or (ii) to be handled internally by the shared-texture creation/interop path. I'd want your steer on which. The semaphore wait is the load-bearing part for the observed flake, but leaving ownership unresolved would be technically incomplete under the spec.
With both, the shared-texture path (and test-texture-shared.cpp) would replace the host-only srcDevice->…->waitOnHost() hand-off with: Vulkan signals a shared timeline IFence after the upload → CUDA imports it and submits its readback with that fence in waitFences, with the ownership transfer applied around the shared image. The test-buffer-shared.cpp TODO is retired by the same primitives.
ABI note (matters for the API shape): IDevice/IFence are COM-style interfaces keyed by a fixed UUID, so appending a method to IDevice in place is not transparently ABI-safe — an older implementation queried by the same UUID won't have the new slot. The clean options are a new versioned/derived interface (e.g. IDevice1 / a small interop interface with its own UUID) carrying createFenceFromSharedHandle, or — if you'd rather not touch the public vtable yet — a test-only helper that does the CUDA import to unblock the flake first and defers the public API. My recommendation is the real (versioned) API, since this is a genuine cross-backend capability gap rather than a test artifact — but the interface-versioning choice is yours.
Next-action: tell me which shape you want — (A) versioned/derived interface with createFenceFromSharedHandle + CUDA cuWait/SignalExternalSemaphoresAsync + an ownership-transfer contract, or (B) test-only helper first — and how you want ownership transfer surfaced, and I'll hand a concrete implementation brief to the fixer. @jhelferty-nv Here is the explicit Shared→External transition proposal we discussed — the separate alternative to #812's register-all. Proposal only, no PR/branch/draft. The four questions at the end are genuinely yours to decide; #812's green HEAD stays untouched and held as the parallel option.
Sketch — explicit Shared→External ownership API (slang-rhi #787 alternative)
Status: PROPOSAL awaiting @jhelferty-nv's confirmation. No PR, branch, or draft exists. This is the "separate alternative" from comment 5782267774 — a design to compare against PR #812's internal register-all (which stays as-is at 6e040d1, held). Nothing here touches #812.
1. Problem restated
A Shared Vulkan resource is VK_SHARING_MODE_EXCLUSIVE; the external API (CUDA) sees the producer's writes only after a queue-family ownership transfer (QFOT) to VK_QUEUE_FAMILY_EXTERNAL, and the producer sees CUDA's writes only after transferring back. In #812 this transfer is implicit — waitOnHost() releases everything owned, submit()/readBuffer() reacquire. The ask: make the transfer (and acquire-back) an explicit public API so the app says exactly when and what transfers, rather than inferring it from waitOnHost/submit.
2. Proposed surface (recommended: Approach A)
A brand-new COM interface with its own SLANG_COM_INTERFACE(...) GUID, queried from ICommandQueue via queryInterface — the standard slang-rhi COM extension mechanism (ISlangUnknown::queryInterface + a fresh interface GUID; the SLANG_COM_INTERFACE macro generates the matching getTypeGuid()). Because it is a new interface, no existing vtable, enum, or struct is touched. It is present only on backends with exclusive-family semantics (Vulkan); queryInterface returns SLANG_E_NO_INTERFACE elsewhere (D3D12/Metal/CUDA need no transfer), and the debug-layer queue forwards the query.
```
// New interface — its own GUID, obtained via ICommandQueue::queryInterface. Not implemented by clients.
class IExternalMemoryQueue : public ISlangUnknown
{
    SLANG_COM_INTERFACE(/* fresh GUID */);
public:
    // Transfer the given Shared resources from this producer queue's family to the external consumer
    // (VK_QUEUE_FAMILY_EXTERNAL). The QFOT barrier is submitted on THIS queue and this call WAITS for
    // it to complete before returning; when it returns, the release has executed and the external API
    // may access the memory (no further Vulkan host wait is needed). Every resource must be a
    // same-device IBuffer/ITexture created with BufferUsage/TextureUsage::Shared; a null, duplicate,
    // non-Shared, or other IResource subtype is rejected with SLANG_E_INVALID_ARG and ownership is
    // left unchanged (all-or-nothing). Batched: one queue submission for the whole list.
    virtual SLANG_NO_THROW Result SLANG_MCALL releaseToExternal(IResource* const* resources, uint32_t count) = 0;

    // Reclaim the given Shared resources from the external consumer back to this producer queue's
    // family. Submitted on THIS queue and WAITS for completion; when it returns the producer owns them
    // again and may read/submit. The caller MUST have ordered the external work before calling this
    // (the consumer's own completion, e.g. a CUDA host sync, or the fenced variant below). Same input
    // rules as releaseToExternal.
    virtual SLANG_NO_THROW Result SLANG_MCALL acquireFromExternal(IResource* const* resources, uint32_t count) = 0;
};
```
Rationale for the shape: IResource* (shared base of IBuffer/ITexture, slang-rhi.h:727) lets one pair of methods cover buffers and textures with no duplication; queue-level because the QFOT is recorded + submitted on a queue and its ordering is relative to that queue's submit/waitOnHost; batched list because the internal impl already coalesces all barriers into one submission (one queue submission per hand-off, not per resource); synchronous (wait-for-completion) so the app doesn't need a separate waitOnHost to know the transfer landed.
Fence-ordered variant — a v1 decision I need from you
The core above orders the acquire against the consumer via the app's host sync (the app ensures CUDA finished before calling acquireFromExternal). The deferred fence-signal idea maps onto a variant that folds the release into the submission that signals a shared fence (and an acquire that waits one) — letting the hand-off order by a FenceDesc::isShared fence with no host stall:
```
virtual ... releaseToExternal(IResource* const* resources, uint32_t count, IFence* signalFence, uint64_t signalValue) = 0;
virtual ... acquireFromExternal(IResource* const* resources, uint32_t count, IFence* waitFence,  uint64_t waitValue)  = 0;
```
ABI constraint (important): methods can only be added to IExternalMemoryQueue before it first ships — appending to a released COM interface breaks older implementations against newer callers. So the fence surface must be decided now (included in v1, e.g. as these overloads), or shipped later as a separate new-GUID interface (e.g. IExternalMemoryQueueFenced). Question: fence variant in v1, or wait-for-completion core first + a versioned fenced interface later? I lean toward deciding it now.
3. Composition with existing concepts (no parallel "shared")
Reuses BufferUsage::Shared / TextureUsage::Shared unchanged — still how a resource opts into exportable, EXCLUSIVE-mode memory. The new methods reject a non-Shared resource.
getSharedHandle / create*FromSharedHandle unchanged — the export/import path is orthogonal; the new API governs only ownership timing, not handle plumbing.
FenceDesc::isShared is the natural ordering primitive for the fenced variant — no new fence concept.
No new enum, no new struct, no change to getQueue/submit/waitOnHost signatures.
4. Usage example — buffer-shared-cuda ping-pong, explicit
```
auto queue = srcDevice->getQueue(QueueType::Graphics);
ComPtr<IExternalMemoryQueue> ext;
queue->queryInterface(IExternalMemoryQueue::getTypeGuid(), (void**)ext.writeRef());   // null on non-Vulkan

IResource* res[] = { srcBuffer };
if (ext) ext->releaseToExternal(res, 1);   // producer -> EXTERNAL; returns only after the transfer has executed
srcBuffer->getSharedHandle(&handle);        // hand off to CUDA — it may access immediately (no extra waitOnHost)

// ... CUDA imports handle, reads {0,1,2,3}, writes {1,2,3,4}, and the app host-syncs CUDA ...

if (ext) ext->acquireFromExternal(res, 1);  // EXTERNAL -> producer; returns owning it again
srcDevice->readBuffer(srcBuffer, 0, size, out);   // now observes {1,2,3,4}
```
Contrast #812 (same result, implicit): waitOnHost() alone releases, readBuffer() alone reacquires — the app never names the resource or the transfer. (With the fenced variant, the release would take (sharedFence, value) and the app would order CUDA on that fence instead of a host sync.)
5. Relationship to #812's register-all
The explicit API is the lower-level primitive; register-all is a consumer of it, not a competitor. #812's implicit hooks (releaseSharedToExternal on waitOnHost, acquireSharedForSubmit on submit, per-buffer acquire in readBuffer) call the same internal QFOT-barrier helpers this interface would expose.
Why the explicit API is correct-by-construction on the exact axis where implicit register-all is a standing bet. #812's register-all-vs-precise-acquire discussion exists entirely because RHI is inferring which resources to reacquire before the producer touches them — and that inference has to enumerate every way a Shared resource can be referenced. Each probe grew that set (direct submit args → tracked objects → and it would extend again to any new formation path, e.g. native handles / bindless), so its correctness rests on the inferred set staying complete forever. The explicit API removes the inference: the app names exactly what transfers, so RHI enumerates nothing and there is no completeness set to keep whole. The fragility that drives the #812 fork simply does not exist in this design. The honest counterweight: explicit-only moves the "don't touch an externally-owned resource" obligation onto the app, enforced by documentation rather than by RHI — you trade an inference RHI can silently get wrong for a contract the app can visibly violate.
Two shippable shapes, your choice:
(a) Explicit-only: ship IExternalMemoryQueue; drop the implicit register-all. Apps name transfers precisely; no hidden waitOnHost side-effect, no device registry, and — per the argument above — no inferred acquire set whose completeness RHI must guarantee. The device-address/bindless prohibition from Fix #787: ping-pong queue-family ownership for shared resources #812 is then no longer required for correctness (there is no implicit reacquire to keep complete), though the contract must still document that accessing a resource while it is externally-owned is invalid — including via a baked device address or bindless handle — since in this mode nothing in RHI enforces it.
(b) Both layers: ship the explicit primitive and keep register-all as the implicit default built on top (the waitOnHost/submit hooks call the primitive internally). Convenience for apps that don't manage it; explicit control for those that do — but (b) keeps the inferred-completeness bet for the implicit path.
My read: (a) is the cleaner "explicit" answer and dissolves #812's completeness burden entirely; (b) preserves the zero-code-change ergonomics #812 gives existing apps at the cost of retaining that bet for the default path. Product call for you.
