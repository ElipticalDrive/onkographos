Purpose and Scope
This page documents the depth buffer integration added to the sphere tracing implementation in Assets/045_SphereTracingDepth/SphereTracingDepth.shader. The core problem addressed here is that a sphere-traced surface hit point exists at a world position that differs from the proxy mesh vertex positions used to invoke the fragment shader. Without writing the correct depth value, the GPU's depth buffer records the depth of the proxy mesh face—not the actual ray-marched surface—causing incorrect occlusion when sphere-traced objects are mixed with rasterized geometry.
For the foundational ray marching loop see Sphere Tracing Basics. For the surface normal and diffuse lighting model that this tutorial extends, see Sphere Tracing with Shading.
The Depth Buffer Problem
In a standard rasterized pipeline, each fragment's hardware depth is derived automatically from the interpolated clip-space position of the mesh triangle being drawn. In sphere tracing, the proxy mesh (a cube) is only a vessel for invoking the fragment shader. The actual surface point samplePoint is found by marching along the ray inside the fragment shader. That point lives at a different position—and therefore a different depth—than the proxy mesh face.
Without explicitly writing SV_Depth, the depth buffer contains the depth of the cube face, not the sphere surface. This causes:
Rasterized objects behind the sphere-traced surface to incorrectly appear in front of it.
Rasterized objects in front of the sphere-traced surface to be incorrectly occluded.

Fragment Shader: Dual Output
The key change relative to previous tutorials is the frag function signature:
Assets/045_SphereTracingDepth/SphereTracingDepth.shader91-122
Instead of returning a single fixed4 color, frag is declared void with two explicit out parameters bound to system-value semantics:
out fixed4 color : SV_TARGET — the rendered color written to the render target
out float depth : SV_Depth — the depth value written to the depth buffer
Fragment Shader Output Pipeline
```
no hit after MAX_STEPShitfrag(v2f i)ray march loop(MAX_STEPS iterations)distance < THICKNESS?discardsamplePoint = pos + dir * progressrenderSurface(samplePoint)→ color : SV_TARGETUnityObjectToClipPos(float4(samplePoint, 1.0))→ tracedClipPosdepth = tracedClipPos.z / tracedClipPos.w→ depth : SV_Depth
```

Depth Value Calculation
Assets/045_SphereTracingDepth/SphereTracingDepth.shader120-121
After the ray march loop finds samplePoint (the surface hit in object space), the depth is computed in two steps:
Transform to clip space: UnityObjectToClipPos(float4(samplePoint, 1.0)) converts the object-space surface point through the model-view-projection matrix, yielding tracedClipPos as a homogeneous clip-space vector.
Perspective divide: tracedClipPos.z / tracedClipPos.w performs the perspective divide, producing the normalized device coordinate (NDC) depth value in the range [0, 1] (on Direct3D / Metal) that the depth buffer expects.
Depth Calculation Data Flow
```
float4(samplePoint, 1.0)tracedClipPos.ztracedClipPos.wsamplePoint(object space float3)UnityObjectToClipPos()tracedClipPos(float4, clip space)/depth : SV_Depth(NDC depth, written to depth buffer)
```
Sources: Assets/045_SphereTracingDepth/SphereTracingDepth.shader:120-121
Note: Writing SV_Depth disables the GPU's early-Z optimization for the affected pixels, since the hardware cannot know the depth before the fragment shader runs.
Hit / Miss Handling
Assets/045_SphereTracingDepth/SphereTracingDepth.shader113-115
When no surface is found within MAX_STEPS, the shader calls discard rather than clip(-1). Both discard the pixel, but discard is the semantically correct instruction and avoids potential driver differences. When discard executes, neither SV_TARGET nor SV_Depth are written.
