# Abstract

To create a hierarchical voxel traversal algorithm can be confusing and hard. There also seems to be problems with other solutions which also seemingly haven't been discussed in the literature before. This work presents three different ways to design a hierarchical voxel traversal algorithm: H4T, HP4T and HP8T. H4T was inspired from a method called HERO and it was modified with an ID so that a property that gets the name 4-connectivity in the work is fulfilled. HP4T and HP8T uses �� + ���� but they are modified so that they use the position of the planes that are used in these methods for the new position. The results show that H4T algorithm that agrees with the reference data 100% of the time, the other two algorithms that don't have 100% correctness never showed in the worst-case bigger margin of error than 2.5%. The conclusion is that there are different ways to design a hierarchical voxel traversal algorithm and if one is careful about designing the algorithm it is possible to avoid the problems with depth in the depth buffer and the surface normal problems in the normal buffer presented in the work. More work must be done to prove that an algorithm is showing correct behaviour for surface normals in the applications where those are needed, to test these algorithms on a graphics processor and a more detailed and intricate analysis needs to be done on the algorithms.

# 1 Introduction

# 1.1 Problem statement

This project was inspired by Teardown [1]. The game has procedural destruction where the player takes on dubious demolition jobs to earn fictional money. Teardown uses voxels a "tool in the toolbox" of computer graphics for its graphics. Now what a voxel is depends, but in this thesis they are essentially cubes [2]. In Teardown all objects are made up of these voxels, like the voxelized fire extinguisher spraying foam in the lower right part of the image, in figure 1.1.



Figure 1.1: A picture of the game from the Steam page of Teardown, the game uses voxels as an artstyle

One of the tasks that the game must tackle is to draw these voxels on the screen. This is done by using voxel ray traversal: shooting a ray at a grid of voxels and stopping if it hits a voxel. They refer to the work "A Fast Voxel Traversal Algorithm for Ray Tracing" by Amanatides & Woo [3]. A problem is that there are errors in the output of Teardowns algorithm and for the sake of brevity only one of these errors are shown and explained in the introduction, see figure 1.2





Figure 1.2: Render from Teardown with a zoomed in part of its depth buffer shown separately to the left, the situation is that the player is looking down at a floor. The part of the depth buffer shown to the left corresponds with the area in the black box in the render to the right

In figure 1.2 the player is looking down at the ground, and there are white outliers in the depth buffer in the zoomed in area of the image. The depth buffer as its name suggests keeps track of the depth from the "eyes" of the player to the point on the surface for every pixel. Darker colours are closer and whiter colours are farther away. This means that the white outliers are errors in figure 1.2 since it is expected that points near each other on a plane would have a similar depth value.

The problem with these outliers is that they cause errors in lightning calculations, reconstructing the surface position and probably more. Fortunately for Teardown these issues are mostly imperceptible but one could argue that these potential errors are unacceptable as they could lead to extra debugging work and a lot of confusion when a developer intends to implement voxel traversal and then potentially detects this error in their implementation.

Another tool that is used in Teardown is hierarchical traversal [4]. Hierarchies like Octree and SVO which stands for Sparse Voxel Octree (removes unnecessary information) helps with ray traversal by enabling the algorithm to skip large sections of empty space in the grid [5]. Based on the authors experience existing explanations of hierarchical voxel traversal often contain one or more problems: They don't explain their theory and math behind their methods in a clear and direct way or have problems like in Teardown.

Thereby the question: how to do hierarchical voxel traversal algorithm for ray tracing?

# 1.2 Goals of the project

The goal of this project is to document theory and different design approaches for an algorithm tackling hierarchical voxel traversal. It will also deal with issues that can appear from these design choices and provide ideas for what causes those issues. Then methods are tested to see if it is possible to construct an algorithm for hierarchical voxel traversal where these issues are non-existent.

Performance of different methods will be measured on the CPU through randomly generated voxel models and some exact cases to cover edge cases.

# 2.1 Tracing ray through grid

What a non-empty cell or occupied cell is depends on what a person defines it to be, but it is used for checking if a ray should stop traversal, because it hits something solid. One example already encountered in this thesis is Teardown where the occupied voxels are cubes, another example is Amanatides & Woo where a cell being occupied means that at least one triangle is intersecting that cell [3, 4]. See figure 2.2 for an example where triangles indicate occupancy.



Figure 2.2: Amanatides & Woo interpretation: Cells are occupied (grey) if they have at least one triangle intersecting them

With occupied cells being explained, the basic problem is introduced. In figure 2.3 there is a ray intersecting a grid and the problem is to find out if the ray hits any occupied cell in that grid.



Figure 2.3: A ray with an origin O and normalized direction vector d going through a grid with some occupied cells.

Finding out if the ray hits any occupied cell can be achieved by successively walking through the cells that the ray intersects in the order which the ray travels. Walking through the grid checking each cell, the ray traversal ends if the ray hits any occupied cell or when the ray exits the grid. Checking for when the ray exits is easily done by checking if the position of the ray in the grid is outside the bounds of that grid. # 2.2 Non-hierarchical method: DDA

An algorithm that tackles how to do non-hierarchical traversal and therefore finds if the ray intersects anything is the DDA algorithm which stands for Digital differential analyser [3, 6, 7]. The algorithm does this by keeping tabs on which cell is "closest" relative to the ray in its current cell and then walks to that cell, this is repeated until the ray hits an occupied cell or if the ray leaves the grid. See figure 2.5 for an example of this process.





Figure 2.5: DDA algorithm where it has a current cell and then calculates the next cell to go to

But to really understand the algorithm the code and the math will be explained, C code for the inner loop of an DDA algorithm could look like this:

1 while (grid\_position.x >= 0 && grid\_position.x < grid\_width && grid\_position.y >= 0 && grid\_position.y < grid\_height) { /\* Some code for reading the grid using current grid position \*/ 2 if(total\_t.x <= total\_t.y) { // moving in x direction 3 grid\_position.x += sign\_dir.x; 4 total\_t.x += abs\_inv\_dir.x; 5 t = total\_t.x; } else { // moving in y direction 6 grid\_position.y += sign\_dir.y; 7 total\_t.y += abs\_inv\_dir.y; 8 t = total\_t.y; } } Code Listing 2.1: C code of DDA

#### 2.2.1 DDA ray traversal explained with planes

Explaining the C code in code listing 2.1 for DDA will be done by referring to the line numbers that has been given to each line of interest, but lines 3-5 and 6-8 function similarly so any explanation for lines 3-5 applies to lines 6-8.

To explain the names, t is part of parametric form of a ray ��(��) = �� + ���� where O stands for the origin of the ray and d is the ray direction and t is parametric value between [0, ∞] which "selects" a position on the ray. Line 1 is a check that the ray has not exited the bounds of the grid. The vector total\_t is the accumulated t value thus far, grid\_position is the cell position of the ray in the grid which follows the convention in figure 2.4, sign\_dir is the sign of each ray direction component where sign is defined as follows:

$$\text{sign}(x) = \begin{cases} 1, & x \geq 0 \\ -1, & x < 0 \end{cases} \quad (1)$$

Finally, `abs_inv_dir` is the absolute value of the inverse of ray direction or in other words:

$$\left( \left| \frac{1}{d_x} \right|, \left| \frac{1}{d_y} \right| \right) \quad (2)$$

To explain the math in lines 2-8 and how the algorithm chooses the closest cell: the big picture here is that where the ray is supposed to go is decided by axis aligned planes that are moved when the ray crosses them, look at figure 2.6.



Figure 2.6: Intersection of planes visual demonstration and how it can help where the ray is supposed to go

Figuring out which plane the ray crosses first is done through ray-plane intersection. In addition, the planes are axis aligned so ray intersection can be calculated in the following way:

$$t_x = \frac{x_{\text{plane}} - O_x}{d_x} \quad (3)$$

$$t_y = \frac{y_{\text{plane}} - O_y}{d_y}$$

Where the ray goes is decided by which  $t$  ( $t_x$  and  $t_y$ ) is smallest which is what is calculated in line 2 of the code. But an observation can be made to simplify the plane intersection calculation, which is used in lines 3-8, see figure 2.7.



Figure 2.7: Image showing steps of the algorithm in two scenarios. Top part shows a ray moving in positive direction in both x and y, bottom part shows a ray moving in negative direction in both x and y.

In figure 2.7 the main observation is that between steps of the algorithm the positions of the planes and the grid position only move by sign of ray direction each time the ray crosses them. This means that if the value of  $t_x$  at a step is equal to this:

$$t_x = \frac{x_{plane} - O_x}{d_x} \quad (4)$$

And then if the ray crosses the x plane first, then the next  $t_x$  value would be equal to:

$$\begin{aligned} t_x &= \frac{x_{plane} + \text{sign}_{\text{dir}_x} - O_x}{d_x} \rightarrow \\ &\rightarrow t_x = \frac{x_{plane} - O_x}{d_x} + \frac{\text{sign}_{\text{dir}_x}}{d_x} \rightarrow \\ &\rightarrow t_x = \frac{x_{plane} - O_x}{d_x} + \left| \frac{1}{d_x} \right| \end{aligned} \quad (5)$$

This also applies to the y direction, but this simplification in equation 5 is why at lines 4 and 7 total\_t is incremented by absolute value of the inverse of the ray direction.

Some more things to note is that if the cell implementation is like Teardown in other words, they are squares (since this is 2d) then to calculate the surface normal one could use the following C code if the ray hits a cell in code listing 2.2

vec2 compare = total\_t.x <= total\_t.y ? vec2(1.0,0.0) : vec2(0.0,1.0); normal.x = compare.x \* -sign\_dir.x; normal.y = compare.y \* -sign\_dir.y; Code Listing 2.2: Method to calculate surface normal

Compare is a vector where each component is one or zero depending on if the ray hit that plane first (the variable compares which plane was hit first). This is used in Teardown and other places and is a technique inspired from the practice of branchless programming [1, 8, 9].

Another interesting note is that in this DDA algorithm code the distance to the individual planes (or total\_t) is calculated through successive summation through the trick in equation 5, when just recalculating the whole value by using the plane intersection in equation 3 is possible. This difference is important because in floating point arithmetic doing summation like this leads to error [10]. Doing it in the way of the DDA algorithm will be referred to as successive summation and recalculating it will be referred to as total summation.

# 2.3 Hierarchical methods

Hierarchical methods use hierarchical data structures to speed up traversal by taking advantage of large empty sections of space that can exist in grids.

#### 2.3.1 Octree and SVO

Now that the non-hierarchical case has been covered, hierarchical traversal can now be dealt with, Octree and SVO data structures will be used to get an understanding of what hierarchical traversal is. Octree is where a hierarchy of grids is constructed, this is done by continually decreasing the number of cells by half, basically each cell in a higher-level covers 2x2 cells in the level below, the occupancy of the higher-level cells then indicate if there is any occupied cell in the 2x2 area below [5]. See figure 2.9 to see an Octree for the running example from figure 2.3.



Figure 2.9: Octree of the example in figure 2.3, halved until 2x2 in level 2 is reached and black lines showing how each cell in a higher level covers a 2x2 area in the level below

A convention to refer to these different cells is to use the area they take up in level 0 so referring to the level 0 cells as 1x1, the level 1 as 2x2 and level 2 as 4x4. The cell position convention for this hierarchy is in figure 2.10.

#### 2.3.2 Hero-like approaches

What is meant by "Hero-like approaches" is approaches similar to the "The HERO Algorithm for Ray-Tracing Octrees" [11, 12]. The approach is to do a depth first search of the tree which is made possible by a 2x2x2 voxel test (as their papers deals with 3d) where they find out which voxels the ray hits and in which order the ray hits them. It starts from the "root" and then goes down if a cell is occupied and it stops if it hits an occupied leaf of the tree look at figure 2.13 to see a part of this process but with 2d.



Figure 2.13: 2x2 test that finds out which cells it hits and which order, then finds out if the any cell is occupied and goes down in the tree. Note that the number in the grid indicate traversal order

# 2.4 Issues and requirements (or things that need to be avoided)

In this chapter some issues existing in Teardowns work is presented in detail and one of the reasons why it happens, there is also one more main issue to be shown figure 2.17



Figure 2.17: Render from Teardown, looking down at a floor showing zoomed parts (the area in the black box) of image from normal buffer, depth buffer, the output render itself and a modified version of the rendered image itself respectively.

This is a scene from Teardown where the player is looking down at a continuous floor that covers the whole screen except for the cable tool the player is holding. The issues are the outlying dots in the normal buffer and depth buffer.

The depth buffer stores the depth value for each pixel; the depth value is the distance between the surface in a pixel and the position from which rendering is done, now if there isn't any surface in front of a pixel then the value is infinity. The way that the depth buffer is usually visualised is with a black-white gradient where darker colours are closer and whiter colours are farther away, so the reason why there is an issue with these outliers is because nearby positions on a plane/floor would have similar depth values.

The normal buffer stores surface normals for each pixel, the surface normal is stored as a (x,y,z) tuple with the convention where y is "up" direction and they are visualised with RGB which means that looking at a floor one would expect to see a green colour throughout the image, which by the non-green dots is clearly not seen in figure 2.17.

An explanation of why those outliers happen in the depth buffer is that there is a fundamental flaw with using �� + ���� to switch between levels, in a closely related topic hierarchical screen space tracing as covered by Jean-Philippe Grenier [14], he notes that using the �� value from plane intersection to get the position through �� + ���� does not guarantee that ray crosses the plane, he attributes this to floating point issues.

An explanation of why those outliers happen in the normal buffer wasn't found in the literature and there will be theory provided which was created in this thesis in chapter 3 for possible explanations of those issues.

Despite that it is now possible to establish some abstract requirements for some hypothetical algorithms and how these requirements will be tested will be specified in chapter 3:

- To not use �� + ���� completely in the algorithm since there is no guarantee of the new position being different from the old position, and therefore no guaranteed progress
- To not get errors with normals
- To get a correct position

### 3.1 Additional theory

A question that is important but seemingly has not been paid much attention before in the literature is "where does the ray traverse when it is intersecting a corner?" and allowing the ray to go through corners can cause problems with surface normals (if the implementation is like Teardown) given the right circumstances. Investigating how the �� + ���� method deals with the question can be shown through example look at figure 3.1 showing a ray intersection with a corner.



Figure 3.1: The value for t to all grey cells is the same

In figure 3.1 the ray direction �� is the inverse of the square root of 2 in both x and y:

#### 3.1.1 Connectivity

The Connectivity property is the options of cells that a given ray with any given direction could walk to from the cell that it is currently in. In 2D there is 4- and 8 connectivity visualized respectively in figure 3.2.

To put connectivity on more rigorous foundations Taxicab metric and Chebyshev metric which will be explained. Defining two points in 2d space ��1 = (��1, ��1) and ��2 = (��2, ��2). In Taxicab metric the distance between ��2 and ��1 is defined as |��1 − ��2 | + |��1 − ��2 |. In Chebyshev metric the distance between ��2 and ��1 is defined as ������(|��1 − ��2 |, |��1 − ��2 |). See figure 3.3 for a visual demonstration of the metrics.

From figure 3.3 it is seen that 4-connectivity is ray traversal restricted to a taxicab distance difference of one, 8-connectivity is ray traversal restricted to a Chebyshev distance difference of one. This could be used to test if an algorithm has 4- or 8 connectivity.

This is HP8T. This method is different from 4-connectivity in that it tries to simplify the calculation for the other axis that the ray does not hit first, by not using clamping. C code of this method in code listing 3.2.

Lines 4 and 6 in code listing 3.2 are the only lines different from the ones in code listing 3.1 of method HP4T. #### 3.3.3 Method Hero-like 4-Connectivity

This is H4T. This method works by doing a 2x2 cell test to find out which cell the ray goes through first and works very differently from the two previous methods, the C code of this method will not be shown as it would cover multiple pages because that this method even could work was discovered late in the project.

Another thing that is different from chapter 2.3.2 is that an axis number is used alongside the t-value which denotes which plane axis the t-value belongs to is stored zero for x axis and 1 for y axis. So, what is done is that a sorting algorithm sorts these t-values according to this axis number then the actual t-values are sorted with a stable sorting algorithm so that the ordering from the first sort of axis number is preserved for equal values of t. The reason this is done, is that if in the case of a tie between t-values between x and y planes the x plane is chosen first and therefore 4 connectivity is preserved.

#### 3.4 Testing methodology

A testing program was created for testing correctness and performance, programmed in the C programming language and compiled with GCC which is the GNU Compiler Collection, it is the tool that turns code into machine code for the computer. The compiler was version 12.2.0 (by MSYS2) with compiler flags: "-mrdrnd -Wall mrdseed -O2". The way that the requirements was tested was to use DDA as ground truth solution and then check if an algorithm got the same end position and same surface normal as the DDA algorithm with total summation in random cases. The requirement that progress was to be guaranteed was not checked with tests as this requirement didn't lend itself to testing instead it was done continually when writing the program. Testing with DDA was done for random cases and specific cases.

Random cases were 10000 random grids with 10000 random rays each. The grids were generated through choosing a length between the powers of two 2, 4, 8, 16, 32, 64, 128 and 256. The height and width of the grid would become this length and then

cells in the grid would be chosen to be occupied with a 1/8 chance. The ray position was randomly chosen from the edges of a rectangle one unit away from the original grid so if the grid was 4x4 the positions would be between the edges of (-1,-1), (-1,5), (5,5) and (5,-1). The ray direction was then decided by randomly choosing a position inside of the grid and taking the difference between the ray position and that random position and then normalizing that ray this was done to guarantee a hit with the grid.

When a position check failed the following normal check wasn't performed as if the position is wrong then whatever the normal is doesn't matter as the algorithms didn't end up in the same place anyway. This also means that the percentage of correct answers with normals is the conditional probability of the normal being correct given the position is correct.

There are also some exact/edge cases that were tested for using the following rays in figure 3.5

# 4 Analysis and discussion

In this chapter, the results will be analysed and the different choices that was made for testing and the thesis in general will be discussed.

### 4.1 Analysis

H4T was realized only late in the project and so it was not expected to be the fastest method, it probably has potential to be improved upon. H4T main strength is that it had no errors which was expected and the reason why it was added despite it being late in the project.

HP8T was expected to get errors since it was an 8-connectivity method, it is the fastest one by a little, another interesting thing is that no post process was used for the normals in HP8T to solve normal problems and despite that it is still pretty accurate. This is probably why in the game Teardown errors are not widely seen as they are very rare just like in the HP8T method.

HP4T was not expected to get errors since it was a 4-connectivity method. But the errors seen in HP4T (and HP8T somewhat) may not be problems. Looking at the testing data where the position does not match it was seen that the problems occur in situations seen in figure 4.1 where the ray is simultaneously passing through a corner and between boundaries in higher cell levels.





Figure 4.1: hierarchical method goes through cells 1 and 2 between the boundaries of two 2x2 cells and dda non-hierarchical method goes through cells a, b and c

From figure 4.1 the failure that happens with HP4T is that even though the method has 4-connectivity it can still go through cell corners between cell boundaries which results in a different position therefore an error in the test. Now one could conclude that this is an error, but it is not that simple since the test used is to compare the result to the DDA algorithm where equal t-values are resolved by stepping in the xdirection, and an DDA algorithm that instead resolves such equal t-values by stepping in the y-direction would be wrong with this test.

#### 4.1.1 Discussion

Another approach or testing method for testing correct normals is to "sweep" the ray. If sweeping a ray doesn't result in outliers, then the algorithm can't have incorrect normals see figure 4.2.



Figure 4.2: Sweep the ray between α1 and α2 to see normal

In figure 4.2 the ray is swept from the angle α1 to α2 and plotting this as a graph where the x-axis is the angle and the function on the y-axis is equal to 1.0 if it hits the left side of the voxel and 0 otherwise. Correct behaviour of surface normal is when the function graph has an equal amount of jump discontinuities as to how many corners the ray passes between the two angles, so the following in figure 4.3 is desired.



Figure 4.3: If the function plot that has one jump discontinuity, then it is showing correct behaviour

The reason why this sweeping test was not used, was because of how to even implement this test when the real number line is continuous and coding it in practice would make use of floating point which is finite and not continuous.

Another choice that was made in this thesis was that only stack-less approaches were tested as the focus was on how to do traversal between nodes of the hierarchy and not on traversal between different levels of the hierarchy. But the reason H4T was discovered so late and how to do it was because making it into a stack-less method wasn't self-evident. Therefore, the approach of ignoring stack-less vs stack designs is flawed, even though it was done in the project to limit scope.

Another thing that could have been analysed but was not, is top-down vs bottom-up designs since H4T clearly is a top-down method. The problem was that a clear determination could not be made in time with HP4T and HP8T.

Another choice that was made is that only rays that start outside the grid was tested. This was mainly done because of the problem of what should the potential surface normal be if a ray starts in an occupied voxel. Now those cases could be rejected because a ray shouldn't start inside of an occupied cell but clipping through objects is possible in video games so it would be good to fall back to some answer for rays inside of the grid in occupied cells.

In the exact cases there are duplicates since checking for grids that are just rotations of other grids is not done; this means that some errors and correct answers are probably counted twice or even more.

The difference in the visuals will be that all computer graphics techniques that rely on surface normals and depth will work correctly so for example light calculations, getting the surface position using depth and so on.

# Appendix A - A trick to reduce the cost of memory reads

There is a trick with grids that is not relevant to this thesis but was discovered by the author that the author also didn't see being done elsewhere. When the grid is saved as a structure in memory there are some different ways to do so, the approach of interest where this trick also applies was seen in Teardown where each individual voxel in a grid is saved as an 8-bit unsigned integer (byte).

This integer is then used as an index to a palette array (could be seen as CLUT colour lookup table) that stores 256 colors where 255 can be chosen freely as one entry is used to denote empty space/air. This is done to minimize the memory a grid takes up: Assuming that all grid dimensions are the same then the memory usage of the grid grows cubically as a function of dimension size.

Now a consequence of this approach is that when traversing the grid then a lookup needs to be done to check if the current voxel is transparent or not (if the grid allows transparent voxels that is) to terminate traversal correctly.

The trick makes it possible to switch from this lookup to what probably is a faster memory read: For example, a lookup doesn't have to be performed with the empty voxel at index 0 since its properties are known ahead of time. It is possible to allow this for all colours in the palette by partitioning the palette array by opaque-ness and transparency, then using two extra indexes stored as 8-bit unsigned integers to indicate where each block ends, where transparency starts at 0 and opaqueness starts at 255. The transparency index indicates "the colours from 0 to this index are transparent colors", the opaqueness index indicates "this is the next spot for a new possible opaque colour", this makes it possible to not get overflow and underflow with the indices in 8-bits. The transparency index can start at 0 and that works because again a spot is always used for empty space that is placed at 0.

Therefore, instead of looking up if the colour being indexed is transparent in the CLUT a comparison between the transparency index and the fetched index can be done to determine whether the underlying voxel is transparent or not. This in theory should be faster as this transparency index should probably be in cache as it is being used during traversal. See figure 29.
