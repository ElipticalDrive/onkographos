1 – Context
3 – A new pipeline for interactive visualization of 3D+t+w datasets
Datasets have reached unprecedented sizes, often spanning several hundred terabytes to dozens of
petabytes, particularly in computational fluid dynamics (CFD) and gas captures. Tools like Paraview [1]
and VTK [2] remain widely used, but face limitations in efficiently managing simultaneous multivariate
and temporal datasets without HPC systems, especially with Volume Rendering. Its full potential for gas
and fluid visualization remains underutilized through multivariate and temporal exploration.
We believe that significant improvements in Out-of Core volume rendering capabilities and
computational performance can enable more efficient and interactive visualizations for large-scale gas
and fluid simulations. Recent works like [3, 4, 5] have explored improving accessibility to graphical
information without significant compromises, even on consumer-grade hardware such as laptops.

We propose an adaptive pipeline (Fig. 2), composed of independent modules, following the out-of-core approach. This pipeline is
structured into three main steps.
(a) Preprocessing : During the bricking process (1), the 3D + t + w input data is subdivided into structured bricks, grouping voxels into
fixed-size blocks (e.g., 64³ in [6]). Users must select d from w variables to be visualized in module (b). Bricks are normalized, converting
values into a standardized range. The Rendering Interface (3) receives the preprocessed data, loaded onto the CPU or GPU for
processing by the Rendering Engine (4). Our pipeline handles the implementation of variants, through additional rendering modes ((3) +
(4)) and data preprocessing.
Fig. 1 : Out-of-core rendering [5,6]
Out-of-core rendering proposed by [6], illustrated in fig. 1, provides an effective strategy for managing
large-scale data uploads using virtual page tables and on-demand brick transfers. Volumes are
preprocessed, mipmapped and bricked to be then uploaded to GPU with dynamic requests throughout
the visualization. Initially demonstrated for 3D datasets on GPUs [6], this method has since been adapted
for Adaptive Mesh Refinement (AMR) data in 3D + t contexts [5]. These implementations are however
designed for simultaneous single-variable dataset visualization 3D + t + w, with a fixed monovariate
storage per voxel. This limits their flexibility for multivariate support.
We propose to integrate the temporal aspect present in [5] into [6] and to add the multivariate aspect,
enabling broader applications in scientific visualization.
(b) Visualization : The Rendering Engine (4) receives tasks as specific rendering. Memory mode requests are handled by a CPU request
manager [5,6]. This distinction is crucial for GPU memory management as an added d dimension can exceed VRAM capacity. The
challenge is to join brick-based rendering with GPU-efficient data access, while maintaining unawareness from underlying data
structures and formats, as well as accommodating visualization modes. The interactions between Rendering Interface and Engine (blue
arrow) also include interoperability mechanisms. The Rendering Interface (3) acts as a virtual controller, managing interactions and data
from preload to final rendering, before interpreting and passing them to the Rendering Engine (4). This abstraction layer facilitates
external connections and avoid implementation-locked contributions.. For instance, through ANARI [7],
The User Interface (UI) (5) allows for interactions with the Rendering Interface (3) (red arrow), enabling camera control, temporal navigation,
and visualization settings. The UI never directly interacts with the Rendering Engine (4) ; all communication passes through the Rendering
Interface (3) to ensure modularity and separation of concerns.

Current limits
Our implementation is still a Work in Progress. An
Out-of-core base structure is implemented, and we
are adding novel temporal and multivariate full
support for structure grids based on [6].
However, the rendering system currently does not
fully support Level of Details [9] modes and will
only access the finest possible value if the brick is
not empty. Though, preprocessing does this,
forming bricks of a defined size (64³ by default)
with LOD, timestep and variables.

Perspectives
Our current investigation focuses on improving
out-of-core loading of our application FRIGAS
both in preprocessing and visualization. Building
on [6], we are enhancing the multi-resolution page
directory’s (MRPD) temporal structure, Unlike
AMR-based bricking, our approach leverages prestructured datasets, allowing us to explore a new
format that enables parallel brick loading with a
shared id across different variables, extending
beyond the existing 128 bits per-brick limitation.
Key areas of experimentation include data loading
performance and benchmarking using out-of-core
strategies and CUDA Zero Copy [10]. Additionally,
we are investigating new page table flags to
improve the flexibility and scalability of our
system.
To further extend our approach, we actively
collaborate on preprocessing support for
additional data formats and welcome discussions
on custom dataset integration.

Our application FRIGAS (Fluid Rendering Infrastructure for Gas and
Atmospheric Simulations) implements the pipeline (cf. Fig 2) through a
2-step visualization process.
Firstly, the user imports the dataset. We developed a 3D+t+w bricking
from the works of [6]. These dimensions are now supported across
NSDF, NetCDF, DICOM and other file formats. The user chooses d
variables from the w available, which are then encoded into bricks.
The brick’s size and number of variables are configurable.
Secondly, the application retrieves the processed bricks. The User
Interface (5) is handled through ImGUI and GLFW. The rendering
interface (4) is established between ImGUI, OpenGL and CUDA as a
"CuGLcontext". This structure retrieves the PBO’s texture for result
frames. It also handles the CPU Request Manager, interacting with
the GPU Cache Manager [5,6].
Our CUDA rendering engine (4) is built from scratch and uses
standard ray traversal algorithms to request virtual positions, with
CPU-GPU transfers [5,6]. The CUDA structures are exposed through
the "CuGLContext" with complete control for the user, with
interactive frame generation.
The User Interface (5), shown in fig. 3, includes Transfer Functions
[kog22], sampling values or temporal exploration for 3D + t. The
current system relies on various rendering algorithms (DVR, MIP,
MeanIP, MIDA [13], …) to handle the available variables, as illustrated
in fig. 4 and 5.

6 – Conclusion
We showcased our application FRIGAS with its versatile pipeline and our current progress in its implementation. Through its conception,
we aim for better flexibility and scalability in visualization of temporal multivariate large-scale data. Now, FRIGAS handles an out-of-core
temporal navigation and contributes with 3D + t + w data processing and visualization, as well as regular 3D + t and 3D + w, albeit with a
128 bits limit for multivariate bricks. Out-of-core rendering shows great opportunities to enhance visualization in a CFD context and we
are investigating the structure’s current limits. Implementation and codes will be made available alongside FRIGAS once our benchmarks
and tests are completed.
