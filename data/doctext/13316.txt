Summary
PR #2 of the WebGPU raymarcher direction. Replaces the dense voxel buffer
used by the Step 0 spike (PR #66 / 1e837af) with a sparse brick-map
representation that the marcher walks hierarchically — empty top-level
cells stride 8 voxels at a time, occupied bricks are descended into for
fine DDA.
Drone airspace is overwhelmingly empty (>99% sky), so this is the storage
shape later PRs will need (sensor primitive in PR #3, terrain streaming
in PR #4+). For the heightmap stand-in, brick count is roughly top²
(~256 bricks at N=128) instead of the worst-case top³ (4096) — the
memory win grows with sparsity.
Zero impact on the production viz: still hidden behind /spike.html,
not built into production output.
Files added
client/webgpu/brickmap.ts — host-side brick map allocation
(createBrickMap) and one-shot build dispatch (buildBrickMap)
client/webgpu/shaders/build_brickmap.wgsl — compute pass that
scans each top-level cell, atomically allocates a pool slot, and
copies the brick's voxels in
Files modified
client/webgpu/shaders/march.wgsl — hierarchical DDA. Top-level
walk strides BRICK voxels at a time; descent re-derives fv from
the actual ray position in the occupied brick; ascent recomputes
c_tmax for the new top cell. Reuses the AABB clip + safe-rd
primitives from PR docs(AGENTS): add git-hooks contract + dotnet pre-push #1 (so axis-aligned and outside-grid rays still
work correctly). Grid struct's reserved word becomes top_size.
client/spikeMain.ts — wires createBrickMap + buildBrickMap,
binds top_grid + brick_pool instead of the dense voxel buffer,
fills the new top_size slot of the Grid uniform.
Test plan
npm run typecheck passes
npm run build passes
dotnet build -c Release passes (pre-push hook validation)
Visit /spike.html via npm run dev in a WebGPU-capable
browser; confirm the heightmap renders identically to PR docs(AGENTS): add git-hooks contract + dotnet pre-push #1's
Step 0 output (same camera orbit, same surface)
Toggle camera viewing angles to verify the hierarchical DDA
handles boundary-crossing transitions cleanly (no popping or
missing voxels at brick edges)
Optional: bump N to 256 in spikeMain.ts and confirm it
still renders smoothly — the brick map's stride wins should
become more visible at larger grid sizes
Why this matters for ResQ Viz
This is the same storage structure the eventual mesh-link line-of-sight
sensor query (PR #4) will use: same compute kernel, just dispatched
from a different ray source. PR #3 will introduce that ray-batch API
on top of this DDA.
