Abstract
Isosurface extraction is a fundamental operation for the analysis and visualization of 3D scalar fields, and the marching cubes technique is the de facto standard to implement it. The processing of large datasets can be a very time-consuming task, and for this reason a number of parallel implementations have been proposed in the literature. In this paper we present a parallel implementation of the marching cubes algorithm that is able to exploit multiple CUDA devices without the need of any preprocessing operation for the dataset partitioning. The output format is suitable for direct visualization as well as for efficient storage; therefore it can be effectively used as a software component in visualization pipelines. Results obtained on a real GPU cluster show speedups of over 230 for the full algorithm (including file I/O and initializations) and of close to 1490 when considering only actual computations and data movements between hosts and devices.

1. Introduction
Isosurface extraction is a fundamental operation for many scientific applications. For example isosurfaces enable the inspection of tissue features and shapes of organs in medical analysis, shape of – and interaction between – molecules in bioinformatics applications and local rainfall from weather radar measurements.
Marching cubes [1] is the most widely used technique for isosurface extraction from 3D scalar fields, also called volumetric datasets. A volumetric dataset is a three-dimensional array of cubic elements, the cells, with values associated at the eight corners. An isosurface is a surface where all the points have a value equal to a user-specified threshold, the isovalue. A cell is intersected by an isosurface if it presents both values above and below the isovalue. The marching cubes algorithm extracts the isosurface piecewise by processing the cells one by one.
The original algorithm has been widely studied, and many efficient implementations have been presented in the literature (e.g., see [2]; for a survey see [3], [4]). In particular parallel processing represents a suitable approach to tackle the impressive growth of data size, and the devices equipped with Graphics Processing Units (GPUs) represent a suitable platform to run data analysis in parallel over structured data as the volumetric datasets. Besides the performance, the desiderable features of a parallel implementation of the marching cubes algorithm for GPUs are the scalability in the input datasets that can be handled, the high quality of the resulting isosurfaces, and the possibility to plug the software into different visualization pipelines of any type of (complex) applications.
In this paper we discuss the development of an effective parallel software component that, apart from direct rendering, allows the efficient storage of isosurfaces and that can exploit multiple CUDA devices concurrently.
The developed software component has the following characteristics.
-
The programming interface (API) is identical to the sequential algorithm.
-
The quality and size of the produced isosurface are identical to that of the sequential algorithm; to this end we exploit a smart vertex interpolation strategy, which is not adopted in related works.
-
Very large datasets can be processed, due to a combination of data buffering and optimized use of device memory.
-
Speedups of close to 1490 are obtained on a moderate-size GPU cluster.
The remainder of this paper is structured as follows. In Section 2 the marching cubes algorithm is introduced. Section 3 presents related works, followed by the description of the algorithm for multi-GPU execution. Experimental results are discussed in Section 5, while Section 6 concludes.
2. The marching cubes algorithm
A volumetric dataset is a pair (𝑃,𝑊), where 𝑃 ={𝑝𝑖∈ℝ3,𝑖=1…𝑛} is a finite set of points spanning a domain 𝛺 ⊂ℝ3, and 𝑊 ={𝑤𝑖∈ℝ,𝑖=1…𝑛} is a corresponding set of values of a scalar field 𝑓, sampled at the points of 𝑃, i.e. 𝑤𝑖 =𝑓⁡(𝑝𝑖). A mesh 𝛴 subdividing 𝛺 into polyhedral cells having their vertices at the points of P is given. We assume 𝛴 to be made up of parallelepipeds, such that a cell 𝜎𝑗 ∈𝛴 is defined by eight points, 𝑝𝑗⁢0,…,𝑝𝑗⁢7.
The datasets are normally stored as a set of planes (slices). Here we assume datasets to comprise 𝑍⁢𝑚⁢𝑎⁢𝑥 slices, each being made up of 𝑋⁢𝑚⁢𝑎⁢𝑥 ∗𝑌⁢𝑚⁢𝑎⁢𝑥 values. Cells consist of a pair of neighboring slices, such that each of the 𝑍⁢𝑚⁢𝑎⁢𝑥 −1 pairs of slices determines (𝑋⁢𝑚⁢𝑎⁢𝑥−1) ∗(𝑌⁢𝑚⁢𝑎⁢𝑥−1) cells.
Given an isovalue 𝑞 ∈ℝ, the set 𝑆⁡(𝑞) ={𝑝∈𝛺∣𝑓⁡(𝑝)=𝑞} is called the isosurface of field 𝑓 for the value q. The isosurface is normally approximated by a triangular mesh. An efficient mode to represent a triangular mesh is by way of two tables, the vertex table and the triangle table. The vertex table represents the geometry (i.e. the coordinates of the vertices), while the triangle table represents the connectivity (i.e. the indices of the three vertices forming each triangle with respect to their position in the vertex table). This format is well suited for visualization as well as for further processing.
Regarding visualization, it is straightforward to convert the tables to the most common file formats for 3D visualization, such as OFF (Object File Format [5]) and VRML (Virtual Reality Model Language [6]). With respect to further processing, it should be noted that the incidence relations represented by the triangle table implicitly contain all other incidence relations among vertices, edges, and triangles. As such, it is possible to derive any other mesh representation from the two tables. The work described in this paper is independent of a specific format, both for input and output data. We assume that considered datasets are composed only of the values of the cell points (so without any header) and that the isosurfaces are represented by the vertex and the triangle tables.
The marching cubes algorithm [1] is the most popular method for extracting triangulated isosurfaces from volumetric datasets. Its approach is to define the triangular mesh representing the isosurface piecewise over the cells of 𝛴. A cell 𝜎𝑗 ∈𝛴 is referred to as an active cell if it is intersected by the isosurface represented by isovalue 𝑞. In this case, the isovalue is between the extrema of the eight cell points, that is min𝑖⁡(𝑤𝑗⁢𝑖) ≤𝑞 ≤max𝑖⁡(𝑤𝑗⁢𝑖). An active cell contributes to the approximation of the isosurface by way of a patch of triangles. The union of all the patches represents the isosurface. Two are the main operations of the algorithm, called Cell Classification and Active Cell Triangulation. Cell Classification determines whether a cell is intersected by the isosurface. For this purpose, a bit vector of eight 1-bit fields is used, each bit corresponding to one cell point. Points with values greater than or equal to the isovalue are set to 1, otherwise to 0. Hence, a cell is an active cell if the bit vector is not 0 (all point values lower than the isovalue) and not 255 (all point values greater than or equal to the isovalue).
For active cells, Active Cell Triangulation approximates the intersection with the isosurface, by using a triangular patch. Considering that a surface may intersect a cell in 254 ways (all possible values of the bit vector except 0 and 255), a look-up table is used to enumerate all possible connectivities. The vertices of the triangles are computed as a linear interpolation of the values of the field 𝑓 in the intersected edges. For example the coordinates of the vertex 𝑝𝑎 belonging to the edge (𝑝𝑏,𝑝𝑐) are 𝑝𝑎 =𝑝𝑏 +𝑞−𝑓⁡(𝑝𝑏)𝑓⁡(𝑝𝑐)−𝑓⁡(𝑝𝑏)⁢(𝑝𝑐−𝑝𝑏).
The original algorithm as proposed by Lorensen and Cline [1] presents three problems that have been widely discussed in the literature [3], [7]. We briefly describe these problems and present the solutions applied in the sequential algorithm that we used as a basis for our implementation with CUDA.
The first problem concerns the correctness of the results. It was demonstrated that the use of the original look-up table introduces topological inconsistencies in certain configurations of shared faces between cubes [7], [8]. Proposed modifications aim at producing either consistent isosurfaces (avoiding holes and cracks) or correct isosurfaces (such that the extracted isosurface corresponds to the real one). We used the solution based on the modified look-up table proposed in [9], which produces consistent triangulations efficiently.
The second problem concerns the performance of the algorithm. Considering the cost of a single operation, Active Cell Triangulation is one order of magnitude more expensive than Cell Classification. However, in many datasets less than 10% of all cells are active cells, such that most of the execution time is spent examining non-active cells. To reduce the execution time, a preprocessing step could be introduced that (based on one of many possible search structures) allows us to disregard parts of the volume that do not contain active cells [3]. In general, however, a solution of this kind is suitable only when the same dataset is queried multiple times. This is because the time necessary to create and access such a search structure must be also taken into account. Hence, if a dataset is considered once or only a few times, the most efficient solution is simply the original exhaustive processing of all cells, as discussed in [2]. For this reason, in this paper we disregarded the use of such search structures or heuristics both to subdivide the volume among the GPUs and to speed up the process.
The third problem concerns the fact that each active cell is processed independently. As such, a vertex may be calculated up to four times in adjacent cells, resulting in a considerable negative impact on the computing time as well as on the size of the vertex table. The best solution to this problem, proposed in [10], only computes the coordinates of a vertex the very first time the vertex is found. The coordinates are then inserted in the vertex table and the corresponding index is stored in one of the auxiliary data structures required by the technique. In this way, cells sharing the same vertex will use the stored index to form triangles. This approach was adopted in our algorithm as well. As it is one of the key aspects of our CUDA-based implementation, the remainder of this section briefly presents the applied solution.
2.1. Smart vertex interpolation
The marching cubes algorithm processes each cell independently, and the effect is that the same vertex may be computed up to four times in adjacent cells (see Fig. 2(a)). Duplicate vertex calculation is a serious drawback, as the duplication of data increases the size of the isosurface without adding any useful information. The duplication may cause significant performance problems in the visualization of the isosurface and in subsequent processing steps.

In [10] a solution was proposed to efficiently tackle this issue by using several auxiliary data structures. The coordinates of a vertex are computed only the first time the corresponding active edge is considered. The coordinates are inserted in the vertex table and the index corresponding to the vertex position in the table is stored in the correct position of one of the five auxiliary array data structures: Xedge, Yedge, Zedge, Topedge, or Ledge. Fig. 2(b) shows the subdivision of the edges among these data structures. As indicated in the figure, in a generic cell (i.e., a cell which is not on the border of the volume) nine edges have been previously considered. A generic active cell therefore can produce at most three new vertices.
The values in the auxiliary data structures are updated during the subsequent processing of all cells. For example, considering Fig. 2(a), the vertex is computed by the bottom left cell and its index is inserted in the corresponding position of the 𝐿⁢𝑒⁢𝑑⁢𝑔⁡𝑒 array structure. The next cell being processed is the bottom right one. This cell uses the stored index and moves it to the proper position in the 𝑌⁢𝑒⁢𝑑⁢𝑔⁡𝑒 array. When the next pair of slices is considered, the top left cell uses the index without needing to modify 𝑌⁢𝑒⁢𝑑⁢𝑔⁡𝑒. Finally, the top right cell uses the index for the last time.
It is important to note that with this technique the processing order of the cells, as well as the order for computing the vertices, must be properly defined such that the treatment of active edges and the replacement of values in the auxiliary data structures are performed correctly.

3. Related works
A key aspect to the efficient parallelization of isosurface extraction is to subdivide the cells such that active and non-active cells are spread in a balanced manner among all the parallel processes/threads. This is difficult to achieve because active cells are generally distributed unevenly in the volumetric dataset. In the literature, two different classes of approaches to the data partitioning problem are proposed.
The first class represents approaches that use data parallelism or the master–worker paradigm without any previous knowledge of the isosurface distribution within the volume. Examples include approaches that aim at providing a parallel module for isosurface extraction to an existing visualization system, as proposed in [11] for the Visualization Toolkit (VTK) [12] and in [13] for the IRIS Explorer [14].
The second class represents approaches that do use knowledge of the isosurface distribution to avoid the processing of large regions of non-active cells, and to evenly distribute the remaining regions. Examples include approaches based on a fast pre-processing step [15], approaches that use pre-computed search structures for dynamic partitioning (see also [3], [4]), and approaches that use a static subdivision of the dataset valid for a specific isovalue [16].
The abovementioned works focused on the use of HPC clusters, while several other implementations are aimed at the CUDA architecture. Porting the original algorithm by Lorensen and Cline to CUDA architectures is straightforward: a thread is created for each cell of the volume to process. This solution is provided as a C-code example in the NVIDIA CUDA SDK [17]. Obviously this code has many limitations: for example, it can only process input volumes of relatively small size. Alternative approaches have been published with the main aim of speeding up the extraction and visualization of very large isosurfaces [18], [19], [20], [21], [22], [23], [24], [25]. It is worthwhile to note that [21], [23], [25] exploit the use of search structures to disregard regions of non-active cells to further speed up the process and that [25] is the only work that is able to exploit multiple GPUs at a time.
These implementations provide good performance but present two important drawbacks. First, the implementations focus on direct rendering of the resulting isosurface, but do not allow proper storage for subsequent processing. Second, the implementations are designed for execution on a single device only and cannot exploit multi-device systems such as GPU clusters. The only work with this characteristics, presented in [25], was implemented by using OpenCL [26] that exploits a preprocessing step to assure a load balanced subdivision of the data among the cluster nodes. However, the focus of this work is on the triangle production in parallel, disregarding some optimizations as the aspects related to the duplication of vertices.
As discussed in [2], when taking into account input dataset characteristics as well as the visualization pipeline in which the isosurface extraction is performed, none of the above approaches is a perfect fit for all possible scenarios. A suitable solution, however, would be to provide the operation as a set of components that can be dynamically assembled at runtime.
4. Marching cubes for multi-GPU systems
The algorithm proposed in this paper is based on two levels of parallelism. The first level performs the partitioning of the input volume among multiple parallel processes by using MPI and – if required – combines the partial results into a single triangular mesh. The second level performs the actual isosurface extraction on every single CUDA device. Following the CUDA naming convention, we defined host to represent the workstation (or cluster node) and device to represent the card equipped with the GPU.
4.1. The MPI-based level of parallelism
Given the inherent complexities of a balanced partitioning of the active cells of a dataset we adopted a data parallel approach, in which the input volume is partitioned into a set of chunks of contiguous slices, each for a different process, that reads from the input file only the slices belonging to its chunk. The output result is written as a scattered set of binary files that can be sewed together in a fast way to obtain the full result identical to that of the original sequential approach.
The sewing consists in an update of the triangle table (obtained as the concatenation of the partial triangle tables produced by the parallel processes), in which the indices of vertices forming each triangle have to be modified in consequence of the union of the vertex tables. It is important to note that the sewing is an optional step, because the files can be used as input for subsequent (parallel) processing steps, as they represent a partitioning of the mesh.
4.2. The CUDA-based level of parallelism
The key issue in this level of parallelism is the need to address the problem of duplicate vertex calculation. Each thread can mark the presence of a vertex by using the auxiliary data structures, but it cannot determine its index. This is because it does not know how many vertices have been found by threads associated with “previous” cells in the volume, given the adopted processing order.
Obviously, the vertices can be merged by using a post-processing step, but this would reduce the overall obtained speedup. The solution we adopted is based on the exclusive prefix sum operation, also known as exclusive scan or, in short, scan. Given a vector of numbers, the scan returns a vector in which each element is the sum of the elements in the input vector up to its index. An example is provided below. INPUT{5,6,2,4,0,2,0,1}OUTPUT{0,5,11,13,17,17,19,19}.
In this example the first thread founded 5 vertices, the second one 6, the third one 2 and so on. These values are inserted in the vector representing the input of the scan operation. The resulting output is then used to compute the correct index value for each vertex. For example, the third thread knows that the previous two threads founded 11 vertices; therefore the two vertices it founded will be indicated with indexes 11 and 12 (considering that in C the first element has index 0). It is also to note that, to obtain the number of the vertices founded by all threads, it is sufficient to sum the last elements of the input and output vectors (i.e. 1+19).
The amount of memory of a device is limited, while the implementation of this technique requires many auxiliary data structures. Therefore, we considered the processing of one pair of slices at a time. We used five matrices to store the coordinates of the vertices, one for each kind of edge in the cell, i.e. the edges along the X and Y axes of the lower slice (called xvert and yvert) and of the upper slice (called Xvert and Yvert), as well as the edges along the Z axis (called zvert). We also used five corresponding matrices to store labels, called xlabel … zlabel. As a thread does not know how many vertices have been found in previous cells, all vertices are initially represented by label 1. The label matrices serve as input for the scan operation; the output is represented by xscan … zscan. The storing of triangles is simpler. A triangle is computed in only a single cell and the look-up table we used [9] shows that at most 5 triangles will be created for each cell. Therefore, the size of the array used for storing the triangles is proportional to the slice size.
It is important to note that the effective number of vertices and triangles produced is much lower than the size of the data structures we used, which results in overly expensive data transfers within and among devices. For this reason, we used a stream compaction step that processes result vectors to produce smaller vectors containing only the non-empty elements. This step also uses the scan operation. It requires two further data structures, trinumvect and restrinumvect, to store the number of created triangles for each cell. For vertices we exploited the previously computed xscan … zscan arrays. This technique is also used in [25], but only for triangles, without addressing the problem of duplicate vertex calculation.
As stated before, the sizes of the additional data structures depend on the size of the volume slices. For the most common datasets this size varies between 512×512 and 2048×2048, resulting in a memory occupancy on the device from 78 to 1168 MB. As a result, it is possible to process volumes comprising slices of size 512×512 on most common CUDA devices, which – in general – are equipped with at least 512 MB of memory. The memory limitation is another reason that enforces to disregard the use of search structures by using GPU devices, because they have also to be stored on the GPU.

Data transfers between host and device form a considerable part of the time spent in performing isosurface extraction on a device, even when applying stream compaction. A major optimization of CUDA-based codes is to overlap data transfers and kernel executions. For devices with compute capability 1.1 or higher, host-device memory copies of memory blocks of 64 KB or less are asynchronous. In other words, all modern devices provide such latency hiding capabilities (i.e. by way of streams [28]). 5. Experimental results
We performed experiments by using the DAS-4 cluster [29] located at VU University, Amsterdam, The Netherlands. The complete DAS-4 system contains roughly 200 dual-quad-core compute nodes (primarily SuperMicro 2U-twins with Intel E5620 CPUs), spread out over six clusters located at five sites in The Netherlands. The VU cluster has 74 nodes (totaling 592 cores), 2 of them are equipped with the Nvidia Tesla C2050 device and 16 with the Nvidia Fermi GTX480 device [30].
At first we used one of the largest freely available volumetric datasets, i.e. a 512×512×1734 grid of 16-bit short values representing the computed tomography (CT) scan of a female cadaver [31], the size of which is 867 MB. The isosurface corresponding to isovalue 1000 is a mesh of 69,600,216 triangles and 35,594,711 vertices, shown in Fig. 1(b), and the size of the corresponding triangle and vertex binary files is, respectively, of 797 MBs and 408 MBs. The isosurface extraction operation requires a large amount of I/O time, and this limits the speedup achievable considering the whole execution time. For this reason we focused our evaluation on the performance obtained for the actual isosurface extraction, TIso, for which we achieved a speedup value of 45 with the GTX480 device. This is also motivated by the fact that isosurface extraction can be part of a visualization pipeline, as described in [2], [32]. In such cases, the input dataset may already reside in main memory, and the output data may be left in memory for subsequent processing.
Another issue to take into account is the time required for device initialization. This initialization is performed with the first call to a CUDA function which, for the considered devices, is about 4 s. This time is nearly negligible for the considered dataset (relative to the total execution time). However, for smaller datasets (as the CT scans of the Volume Library [33], the sizes of which are lower than 100 MB) the cost of initialization may be greater than the time required to process the dataset. In cases where previous steps of a complete pipeline have already exploited the device, or in scenarios in which sequences of datasets must be processed e.g., as in time-varying datasets resulting from turbulent combustion simulations [34], [35] or earth shaking simulations [36], the initialization is performed only once and its impact on the total processing time is limited.
For many real datasets the use of a single GPU is sufficient, but larger datasets are common in scientific and industrial applications, as for example in the oil and gas industry, or in chemical and astrophysical research. These data are not freely available; therefore we considered a synthetic dataset obtained from the female cadaver by interpolating 3 intermediate points for each pair of original points, obtaining a 2048×2048×6936 grid, for a total size of 23 GB. We measured extraction of two differently sized isosurfaces. The first corresponds to isovalue 1000 and results in a mesh of about 1.3 billion vertices and 2.5 billion triangles. The size of the corresponding vertex and triangle binary files is 41 GB. The second, smaller, isosurface corresponds to isovalue 4000 and results in a mesh of 62,559 vertices and 106,164 triangles, for a total size of the binary files of 3 MB.

Also in this case the overall speedup achievable by the isosurface extraction is limited by a possibly huge amount of I/O. Moreover, the DAS-4 cluster is not equipped with a parallel file system or SAN solutions. Hence, I/O times often are significantly affected by concurrent reads performed by many processes at a time.
The results of Table 2 show that a single GPU device outperforms 64 CPU cores (8 nodes) for both isovalues, if we consider the actual isosurface extraction only. The total execution time (Total) is better in the latter case, because of the parallel (and partial) I/O performed by the 8 nodes, while CUDAIso performs sequential I/O for all data by using a single disk. Similarly, the results show that, for both isosurfaces, the use of 4 devices outperforms the use of 512 CPU cores, when considering TIso only. Due to the impact of I/O, the speedup for the full algorithm is – in some cases – only one-sixth compared to the speedup obtained for the isosurface extraction itself.
The highest speedup values for CUDAIso and ParCUDAIso are obtained when processing the smaller isosurface, corresponding to isovalue 4000. First, this is because the small isosurface requires a much smaller amount of data to be copied between host memory and device memory (about one-third in comparison with the large isosurface). Because of the better overlap between data movement and kernel execution, this even results in superlinear speedups for TIso (in the number of devices used). Second, for smaller isosurfaces a possible imbalance in the spread of active cells – in the case of parallel execution exploiting multiple devices – only has a limited impact on execution time.
As described in Section 2, our algorithm consists of two main operations, Cell Classification and Active Cell Triangulation. The cost of Cell Classification ignores the size of the isosurface and, for the considered dataset, this operation takes 1,414 s. For the small isosurface, the processing of the very few active cells (about 0.003% of all cells) requires only 1 s. In contrast, the impact of load imbalances for larger isosurfaces may be more significant. However the production of 1.3 billion vertices and 2.5 billion triangles associated with isovalue 1000 represents only a 10% increase of TIso with respect to the time spent for isovalue 4000. Therefore the possible unbalancing of active cells will result in a limited performance degradation. In our tests we verified that with this huge isosurface, the difference between the lowest and highest numbers of active cells received by each processes is, in the worst case, a factor 4, and using ParCUDAIso this unbalancing has only a limited impact. On the contrary ParIso was more penalized due to the much larger number of parallel processes, and the use of 2 GPUs outperforms the use of 512 CPU cores.
The peak performance of the NVIDIA Fermi GTX480 is 1.35 TFLOPS for single precision operations, two-third of which is maximally obtainable for (normal) applications without dual-issue. Disregarding the use of the CUDPP library and the overlap between computation and data transfer, the kernels in CUDAIso and ParCUDAIso achieve an average performance of 370.3 GFLOPS. This deviation from the realistically obtainable peak clearly is due to the large data movements between host and device memory, and due to the overhead induced by smart vertex interpolation and stream compaction. Nevertheless, our results are entirely in line with reports for other complex CUDA-implemented algorithms in the literature.
6. Conclusions
In this paper we presented an implementation of the marching cubes algorithm which exploits a cluster of CUDA devices.1 This implementation provides two main advantages over the related works. The former consists of developing a component for visualization pipelines, allowing for efficient storage of the resulting isosurfaces for subsequent processing. The latter comprises its scaling up to very large data sizes, whilst obtaining very good performance. In part, this is due to the use of a smart vertex interpolation technique not adopted by others.
Specifically, for a moderate-size GPU cluster comprising 16 CUDA devices, we obtained speedups of close to 1,490 relative to purely sequential execution on a single core in the same cluster. At the same time, our results showed linear speedups in the number of devices used for large isosurfaces, while they highlighted superlinear speedups for smaller isosurfaces because of a better overlapping between data movement and kernel executions.
When considering these results, principally also the additional overheads induced by I/O and device initialization (not included in the 1490× speedup mentioned above), we concluded that the use of a CUDA device, or a simultaneous combination of several devices, can be highly beneficial – but it may be unsuitable in all application scenarios. In particular, the efficiency of execution depends on the size of the data to be processed and on the possibility of the isosurface extraction to be applied as part of a much larger pipeline. This conclusion re-enforces our considerations presented previously in [2]: there is not a single, optimal implementation for the isosurface extraction operation that perfectly fits all the possible execution scenarios.
A feasible solution to this problem can be the availability of a set of alternative (but otherwise equivalent) implementations of the isosurface extraction operation, and integrate such equi-kernels in a software system that can automatically select the proper implementation to be used. Currently, we have six of such alternative equi-kernel implementations achievable: a sequential version, a CUDA-implemented version, three parallel versions implemented by using MPI [2], and the version based on the combined use of MPI and CUDA presented in this paper. Clearly, choosing the best implementation depends on a number of issues, including (a) the specific quality-of-service requirements of the application at hand, a.o. in terms of absolute performance; (b) the characteristics of the dataset and, if known, of the resulting isosurface; (c) the configuration of the pipeline in which the isosurface extraction is performed; (d) the computational resources available for execution of the isosurface extraction. For this reason, as a future direction, we will focus on the implementation of a software architecture that indeed incorporates all of these issues, and that can make the proper choice automatically. The system will be based on the notion of Jungle Computing, the foundations of which have been laid out in [37].

Show abstract
In recent years, Jungle Computing has emerged as a distributed computing paradigm based on simultaneous combination of various hierarchical and distributed computing environments which are composed by large number of heterogeneous resources. In such a computing environment, the resources and the underlying computation and communication infrastructures are highly-hierarchical and heterogeneous. This creates a lot of difficulty and complexity for finding the proper resources in a precise way in order to run a particular job on the system efficiently. This paper proposes Hybrid Adaptive Resource Discovery (HARD), a novel efficient and highly scalable resource-discovery approach which is built upon a virtual hierarchical overlay based on self-organization and self-adaptation of processing resources in the system, where the computing resources are organized into distributed hierarchies according to a proposed hierarchical multi-layered resource description model. The proposed approach supports distributed query processing within and across hierarchical layers by deploying various distributed resource discovery services and functionalities in the system which are implemented using different adapted algorithms and mechanisms in each level of hierarchy. The proposed approach addresses the requirements for resource discovery in Jungle Computing environments such as high-hierarchy, high-heterogeneity, high-scalability and dynamicity. Simulation results show significant scalability and efficiency of the proposed approach over highly heterogeneous, hierarchical and dynamic computing environments.
