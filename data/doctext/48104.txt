Description
I got (re-)inspired to play around with a signed distance field based raymarch algorithm by a gamedev video on youtube. With that you can compose various 3D shapes with operations like union, difference/subtraction, intersection, xor as well as smooth variants of the former. You can also modify shapes, e.g. by applying rounding, bending or twisting.
Here's a gear as an example:
```
sdf_tree = CSG.diff(
    CSG.intersect(
        CSG.smooth_union(
            CSG.Cylinder(0.2, 0.7, color = :lightgray),
            CSG.union(
                map(1:4) do n
                    CSG.Rect(
                        Vec3f(0.1, 0.07, 0.2),
                        color = :lightgray,
                        translation = 0.8 * Vec3f(cos(n * pi/8 - pi/16), sin(n * pi/8 - pi/16), 0),
                        rotation = qrotation(Vec3f(0, 0, 1), -n * pi/8 + pi/16),
                    )
                end...,
                mirror = (true, true, false)
            ),
            smooth = 0.02
        ),
        CSG.Cylinder(0.1, 1, color = :orange)
    ),
    CSG.Cylinder(0.2, 0.4),
)

csgplot(-1..1, -1..1, -1..1, sdf_tree)
```
The code is currently quite messy because it contains leftovers multiple prototypes.
The first is an attempt to compute signed distance fields on the GPU directly, by encoding the operations on CPU and then decoding and processing them on the GPU. I got this to work, but it was very expensive on GPU. (I'd guess this is a combination of needing a lot of branching to determine what each operation is (e.g. if (operation == op_translation) ...) running for multiple operations that need to be evaluated multiple times as the raymarching gets evaluated.) This is currently still available as sdfscatter().
The second prototype moved the SDF generation to the CPU, evaluating distances once and storing them in a 3D array. That array is then passed to volume where the distances are used in ray marching. On the GPU side, this is should be faster and higher quality than the other volume algorithms. The conversion for this is currently disabled.
The third and current prototype builds on the second. Loosely following the gamedev video, I implemented a Brickmap to compress the signed distance data. This typically compresses the data by a factor of 10-100, which can then be used for more quality. From that point on, I added another compressing procedure for colors and tried optimizing the initial SDF generation.
Some stats for the example above:
32 operations total, evaluated in an effective 512^3 grid in a -1..1 box
dense array:
512^3 * 2 byte for each distance: 256MB
512^3 * 3 byte RGB color: 384MB (not implemented)
total 640MB
time: 19.3s (unoptimized)
Brickmap: (memory rounded)
1.5MB brick indices (73^3 * 4 byte)
7.6MB 10MB distances in bricks (14716 14716/19683 bricks ¹, each 8^3 * 1 byte, depends on the amount of surface area)
0.06MB index remapping for colors (14716 14716/16384 * 4 byte indices ¹, one per brick)
4.0MB color (2312 2312/2744 bricks ¹, each 8^3 * 3 byte, depends on the number of mixed color bricks)
¹ these are dynamically resizing arrays with n_used / n_available elements
total: 13.2MB 15.5MB
time: 2.2s 0.77s 0.60s 0.28s (with optimizations to skip empty regions and locally irrelevant SDF nodes)
