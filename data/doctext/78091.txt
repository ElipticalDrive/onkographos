Owner
A second voxel mesher alongside marching cubes, selected per volume via TerrainComponent::m_VoxelMesher. Marching cubes stays the right tool for organic isosurfaces and is functionally untouched; this one treats the SDF as solid/empty and merges co-planar visible faces into maximal axis-aligned quads with bitwise operations, drawn instanced from an 8-byte packed record.
The two deliberate divergences from the reference
Ported from D:\repos\VoxelEngine (MIT, same stack). Two things are done differently on purpose, each fixing a limitation of the original — both are documented at the code and pinned by tests:
Extents are stored biased-by-one. The reference masks width/height with 0x1F unbiased, which is why it documents "the 2-byte quad encoding cannot express 32³ chunks". VoxelChunk::CHUNK_SIZE here is 32, so the quads that would silently vanish are exactly the largest ones greedy meshing exists to produce (a flat chunk face is the best case). Biasing costs nothing and removes the limitation. Pinned by VoxelQuadEncoding.FullSpanExtentSurvivesTheRoundTrip.
Padding is uniform on all three axes — u64 columns over a 34-bit padded span — instead of padding X/Z in the array dimensions and special-casing ±Y against the neighbour chunk's edge bit (the reference has to, because a u32 column has no room for the two Y padding bits). All six directions then run identical code, which is why the chunk-boundary cases are not a separate bug surface. Pinned by VoxelGreedyMesherBoundary.EveryAxisCullsAgainstItsNeighbour.
Encoding decision
32-bit geometry word, 28 bits used: x/y/z 5 bits each, width-1/height-1 5 bits each, face direction 3 bits, 4 reserved. Material is a separate u32 (8 bits used) rather than stuffed into the spare 4 bits — 16 materials is not enough for a terrain palette and the instance stride is 8 bytes either way once the pair is aligned. The bit layout is derived from CHUNK_SIZE, with a static_assert that turns a future chunk-size increase into a loud compile error instead of silent truncation.
The chunk origin and voxel size ride the model matrix, which is what keeps the per-quad record at 32 bits.

Both figures are reported because they behave differently. The triangle ratio is entirely terrain-dependent: a high-frequency noise field at coarse voxels gives almost every column its own height, so top faces cannot merge and the mesh is dominated by one-voxel-wide cliff strips — close to the worst case. The byte ratio is not terrain-dependent, and it is what the packed-quad encoding actually claims. Silhouette overlap against marching cubes is 0.77 IoU, measured on the entity-ID attachment.
I originally asserted >4× on triangles by guesswork and it failed at 1.88×. Rather than tune the threshold to pass, I added the byte measurement and a terraced measurement (the shape a cubic world really has), and set floors well below the measured values so the test cannot lie in either direction.
2 — no seams or double-drawn faces at chunk boundaries. Verified from four angles including one sitting exactly on the x = 64 chunk-border plane looking straight down it, and one from underneath (−Y faces exist nowhere else in a heightfield volume). Screenshots committed under OloEditor/assets/tests/visual/VoxelGreedy_*.png. Also verified live in the editor over MCP against the new sandbox scene, with olo_shader_errors returning 0.
3 — meshing runs on the task system. VoxelGreedyMeshBuilder snapshots a padded neighbourhood on the game thread and dispatches the merge to a worker (Tasks::Launch, BackgroundNormal); the game thread only uploads finished buffers. The snapshot is the thread-safety seam — everything downstream is a pure function of an immutable blob, so a concurrent CarveSphere cannot race the mesher.
Two behaviours gated on the cubic mesher
Both are load-bearing and worth arguing with if you disagree:
The voxel volume is seeded from the height field. Marching cubes deliberately leaves it sparse (it is a carve-only override there), but a cubic world's voxels are the terrain, so there has to be a way to fill the extent. Only an auto-seeded volume is dropped when the mesher switches back; a user-carved one is never touched.
The heightmap surface stops drawing, gated on cubic geometry actually existing (not merely on the mesher being selected — the streaming branch never creates m_TerrainData, so selection alone would hide the tiles and draw nothing).
Review guide
Where I'd look hardest
OloEditor/assets/shaders/include/VoxelQuadUnpack.glsl ↔ Terrain/Voxel/VoxelQuad.h — the same contract (bit layout, face numbering, per-face U/V basis) written twice with nothing linking them. A mismatch compiles, passes every CPU test, and silently transposes/offsets/inside-outs the quads. VoxelFaceBasisContract.* pins the C++ half only.
Terrain/Voxel/VoxelGreedyMesher.cpp MeshDirection — the kWidthIsInnerExtent table is not uniform across the six faces (it follows from the U/V ordering). Getting it wrong does not lose a quad, it transposes one: a 1×8 strip renders as 8×1, which still merges and still draws.
Scene.cpp — the two gated behaviours above, and VoxelGreedyMeshBuilder::DispatchDirty's neighbour ring (editing one chunk invalidates the six that touch it; rebuilding rather than dirtying them is what stops a cascade).
What I verified, and how
28 CPU contract tests. The load-bearing one expands every merged quad back into unit faces and compares that multiset against an independently written per-voxel mesher, in both directions plus per-key counts, over 7 volume shapes. A size-only comparison passes on exactly the bug it exists to catch (one face emitted twice, another dropped), and MeshNaive shares no code with Mesh so a face-culling bug cannot hide behind common code.
Full suite: 6,001 passed / 1 failed / 45 skipped. The failure is AssetContentValidity.SandboxAssetRegistryDeserialisesAndPathsResolve, pre-existing and environmental: it wants generated Assets/cache/embedded/*.png files, that path is gitignored (0 tracked files), AssetRegistry.oar is unmodified by this branch, and the untouched base repo on master has the same 0 files, so it fails there identically.
Live editor over MCP on Scenes/VoxelGreedyMeshTest.olo: scene opens, 0 shader errors, four poses shot including down a chunk border.
Least confident about
The Vulkan path. The three greedy shaders declare the two-stream vertex pull (bindings 57/63) exactly like Foliage_Instance.glsl, and the block name at 63 is OloInstancePull rather than OloBonePull (the backend matches on the binding number, not the name — but I have not run it). Vulkan's deferred editor frame is separately known-frozen (#823), so I verified on GL only. If the Vulkan nightly goes red here, that is the first thing to check.
Deliberately not tested
Deferred/G-Buffer path — the G-Buffer variant compiles and mirrors the forward one, but every screenshot is from the forward path.
Shadow casting from packed quads — Terrain_VoxelGreedyDepth.glsl unpacks through the same shared include as the lit shader (which is the point: a divergent depth stage is how peter-panning happens), but I have no shot that isolates a voxel shadow.
Non-32 chunk sizes — the static_assert makes that a compile error rather than a silent truncation, which is the intended behaviour, not a tested one.
Notes for the reviewer
A pre-existing bug I did not fix: Terrain_Voxel.glsl and Terrain_Voxel_GBuffer.glsl (the marching-cubes voxel shaders) decode the triplanar normal map before checking whether the array is bound, so an unbound array yields a unit-length (-1,-1,-1) that rotates the normal ~55° off true. The greedy shaders had the same defect inherited by copy — it rendered the whole terrain black — and are fixed here; the MC ones are left alone to avoid moving goldens in an unrelated path. Worth a follow-up.
The MCP registry emits VoxelMesher as a clamping ranged field while both loaders reject. An out-of-range MCP write becomes GreedyCubic rather than the default. That is generator behaviour driven by OLO_SERIALIZE(Reject, Min, Max); I left it because an MCP write is an interactive editor action with visible feedback, not untrusted disk data.

Three things, all from review follow-up.

* VoxelGreedyMeshBuilder retires WITHOUT waiting. Dropping the Ref (mesher
  switch, terrain regenerate, scene copy) went through ~VoxelGreedyMeshBuilder
  -> Clear() -> Task.Wait(), stalling the game thread on a worker. It is safe to
  simply abandon: the task body captures one shared_ptr to its own MeshJob and
  never `this`, so an in-flight job holds no reference to the builder, its mesh
  map or its GPU buffers. DispatchDirty already relied on exactly that when
  abandoning a snapshot an edit had invalidated. FlushPending still waits; that
  is the deterministic path tests use.

* Terrain_Voxel.glsl and Terrain_Voxel_GBuffer.glsl get the same two fixes the
  greedy shaders got. They decoded the triplanar normal map BEFORE checking

  true. They also built the tangent frame with `normalize(cross(N, +Z))`, which
