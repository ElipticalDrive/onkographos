Description
Sample matching for extinction gradients in volumetric inverse rendering, as
a new integrator plugin, plus the medium-side machinery it needs.
Ruihan Yu, Yu-Chen Wang, Jingwang Ling, Feng Xu, Shuang Zhao.
Sample Matching for Joint Extinction Gradient Estimation in Differentiable
Volume Rendering. ACM Transactions on Graphics 45(4), 2026.
paper
· supplementary
· project page
· doi:10.1145/3811329
Differentiating volumetric transport with respect to the extinction
coefficient produces two contributions of opposite sign: a scattering
term, because denser media scatter more light toward the camera, and a
transmittance term, because denser media attenuate everything passing
through. Existing estimators evaluate the two at unrelated points, so their
negative correlation does nothing for you. This integrator evaluates both at
shared locations along each path segment, which turns that correlation
into a variance reduction.
New plugin
prbvolpath_sm — sample-matching volumetric PRB. Primal rendering is
identical to prbvolpath; all of the new machinery runs in the adjoint pass.

Segment j of a lane goes to slot min(j, segment_slots - 1). The first
segment_slots - 1 are always kept; everything from there on shares one
reserved row per lane and is resolved by a weighted reservoir. Both halves
are unbiased on their own, so the estimator is unbiased at every slot count —
the count only moves the split between segments sampled exactly and segments
pooled into one. Nothing is ever dropped.
Two megakernels, not one. In the adjoint pass the path tracing and the
dr.backward that follows it run as two separate megakernels. The reason is
OptiX: the gradient sampling on a segment traces rays of its own, and every
trace inside a loop saves and restores whatever is still alive across the
iteration. Keeping a segment's record in loop state — named variables or
dr.alloc_local, measured identical — cost +2.5 KiB/thread of continuation
spills and +45% adjoint time on the bunny, and nothing at all under analytic
intersection. So the path loop does no gradient sampling. It writes one small
record per segment with a masked scatter, the values die at the end of the
iteration, and the second kernel reads them back and does the sampling there,
one lane per record. Only one scalar stays in loop state: the reservoir's
running weight.
Spectral and RGB. Both are supported, including an extinction that varies
across channels. Deferred record fields are generated from the variant's
spectrum size, and each record carries the path's wavelengths so the second
kernel evaluates the medium at the right ones.
What was tried and dropped: reconnection (paper Sec. 5.1, Eq. 32-34). The
the gradient samples on a segment can reuse the path's own continuation
instead of tracing a fresh sub-path each, which is much cheaper. It was implemented and
verified unbiased by finite differences. It is not in this branch: at equal
iteration count its variance is worse than tracing the sub-paths. The shift
mapping connects two points with different visibility, so the reuse weight
carries a transmittance ratio that ranged over 1e-9 to 356 in
measurements, and only 4.8% of the samples could reuse at all. The archived branch
keeps the measurements.
Changes to existing code
Medium: a majorant supergrid, on by default
(majorant_resolution_factor 8, majorant_factor 1.2), traversed with a
DDA. Empty and thin regions are crossed in far fewer null collisions
instead of paying for the densest voxel in the volume. homogeneous
rejects the parameter explicitly, since it cannot honour it.
Medium::sample_real_interaction: consumes null collisions in one
fused C++ walk instead of iterating them in Python. With a supergrid the
DDA traversal and the null-collision walk share a single loop.
heterogeneous takes either parameterization. The scattering
coefficient can be given as an albedo volume or as sigma_s directly;
the two are mutually exclusive and the plugin says so. This follows the DRT
implementation, which pairs albedo with sigma_t to decouple the two and
keep optimization gradients stable — with sigma_s given independently the
derivative involves sigma_s / sigma_t and goes unstable as the extinction
goes to zero.
The integrators always query sigma_s; what is differentiable is a
separate matter, handled the way the rest of Mitsuba handles it. traverse
exposes whichever of the two the scene gave — never both — alongside
sigma_t, each marked ParamFlags::Differentiable, and scale marked
NonDifferentiable. That declares what may carry a gradient; nothing does
until the caller enables one, exactly as Mesh declares vertex_positions
differentiable and faces not. So the query surface is fixed and the
parameterization you optimize is a scene-authoring choice.
Medium::get_albedo: a direct albedo lookup, no production caller in
this branch. It is a cheaper and better-conditioned query than rebuilding
sigma_s / sigma_t, which is 0/0 wherever the extinction vanishes.
prbvolpath.py is untouched.

The append region is sized by slot count times wavefront, so a slot per
segment costs about 4.6 GB more than prbvolpath at this wavefront, while
one slot per lane costs 32 MiB more. gradient_samples_per_segment does not
enter into it -- 1 and 4 give the same figure.
Sample matching is faster per step here because it consumes null collisions
inside one fused C++ walk, where prbvolpath spends one symbolic-loop
iteration on each of them and pays an optixTrace for every one. That is
visible without any of the gradient machinery: rendering the same frame at 64
spp with no AD graph at all, prbvolpath takes 104.5 s and this plugin
72.1 s, running the identical estimator in primal mode.
The same measurement shows the gradient sampling never runs in the primal
pass: 72.09 s at gradient_samples_per_segment 1 against 72.16 s at 4.
On a smaller microbenchmark that stresses the gradient sampling instead, it
is 1.2-1.55x slower in RGB and 0.74-0.82x in spectral variants.
