Describe the proposal
We can "convexify" the MultiFabs (remove parts of boxes covered by coarse cells, and split boxes into multiple pieces if they have become topologically disconnected), call Viskores' GPU volume renderer separately for each FAB, then add together the images from all of the local FABs.
Then we do an MPI reduction to sum all images and finally write a PNG file from rank 0.

If there is only attenuation, the naive solution described above works.
However, if there is color or emissivity, then the boxes need to be topologically sorted and then the partial images (associated with each box) need to be merged ("alpha blended") in back-to-front topological order (which can be done with a binary tree, since the merge operator is associative: https://vis.cs.ucdavis.edu/papers/00291532.pdf).
When boxes are allowed to be different sizes, it's possible there is no topological ordering, in which case the problem boxes need to be split along any one of the Cartesian axes (but most efficiently along the axis most nearly orthogonal to the viewing plane):
In 3D AMR meshes it is possible to form dependency loops, where each grid in a
loop depends on one of the others. It is always possible to break such loops by
splitting some grids into smaller pieces, and indeed it is always possible to do so
using cutting planes perpendicular to the z-axis. (To see this, consider that with
enough such cuts, any 3D grid layout may be reduced to a series of 2D layers, and
no dependency loops are possible in 2D.) I have taken this approach in the present
code since splitting a BoxLib grid in the z direction leaves two contiguous chunks of
data and is therefore more efficient for the underlying numerical routines.
Octree meshes do not have this problem.

If we sort the boxes by maximum distance from the viewer (assuming this is an orthogonal projection, not perspective), then A and C will be tied to go first, and then B will be rendered on top: ((A merge C) merge B) or ((C merge A) merge B). We can pick A or C arbitrarily.
