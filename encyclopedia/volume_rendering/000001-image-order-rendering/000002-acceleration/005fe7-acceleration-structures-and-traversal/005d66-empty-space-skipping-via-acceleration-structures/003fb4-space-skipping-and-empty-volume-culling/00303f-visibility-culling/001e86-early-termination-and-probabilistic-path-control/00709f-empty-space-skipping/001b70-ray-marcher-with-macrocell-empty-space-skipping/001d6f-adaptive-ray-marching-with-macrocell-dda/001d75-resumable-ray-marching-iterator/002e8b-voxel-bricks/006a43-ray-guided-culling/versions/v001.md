# Ray-Guided Culling

Also called: Dynamic Working Set Culling, On-the-Fly Brick Culling, Ray-Guided Culling Implementations

## Overview
Ray-guided culling is a dynamic memory management strategy for volume rendering that constructs the set of active data structures (bricks) during the rendering pass itself, rather than pre-computing it on the CPU. It solves the problem of memory bandwidth and cache inefficiency in large-scale volume rendering by ensuring that only bricks actually intersected by rays are downloaded to GPU memory. Unlike traditional culling methods which compute the working set prior to rendering, this approach implicitly handles view frustum and occlusion culling because rays are only generated within the visible region, and missing bricks are handled via on-demand requests.

## How it works
The method operates on a hierarchical voxel structure (e.g., Voxel Bricks) where data is stored in fixed-size blocks. The core principle is that the working set starts empty and grows dynamically.

**Inputs and Outputs:**
- Input: Ray marching parameters (origin, direction), hierarchical volume data structure (octree/brickmap), transfer function.
- Output: Rendered image, updated working set of active bricks in GPU memory.

**Data Structures:**
1.  **Brickmap:** A hierarchical structure (e.g., octree) where leaf nodes represent bricks. Each node may have a flag indicating if the brick is present in GPU memory.
2.  **Working Set:** A collection of brick IDs currently resident in GPU memory.
3.  **Missing Brick Queue/Buffer:** A data structure to store requests for bricks not currently in memory. Implementation varies:
    -   Multiple Render Targets (MRT) [S1].
    -   GPU Hash Tables (per tile) [S1].
    -   Lock-free Hash Tables [S1].

**Steps:**
1.  **Initialization:** Start with an empty working set. No bricks are pre-loaded.
2.  **Ray Traversal:** For each pixel/ray, traverse the hierarchical structure.
3.  **Brick Access Check:** When a ray enters a brick's bounding box:
    -   If the brick is in the working set, proceed with ray marching through the brick's voxels.
    -   If the brick is **not** in the working set (missing), record a request for this brick.
4.  **Request Handling:**
    -   The recorded requests are processed between frames or during specific synchronization points.
    -   Requests are sent to the CPU or a memory manager to fetch the missing brick data from storage.
    -   The fetched brick is uploaded to GPU memory and added to the working set.
5.  **Rendering Loop:** Repeat steps 2-4 for subsequent frames. Over time, the working set converges to include all bricks necessary for the current view.

**Pseudocode:**
```python
# Global state
working_set = set()  # Set of brick IDs currently in GPU memory
missing_requests = [] # List of brick IDs needed but not present

def render_frame(rays, volume_structure):
    global working_set, missing_requests
    
    # 1. Process any pending missing brick requests from previous frame
    # This step may happen asynchronously or in a separate pass
    process_missing_requests()
    
    # 2. Ray Marching
    for ray in rays:
        current_brick = None
        while not ray_terminated(ray):
            # Determine which brick the ray is currently inside
            current_brick = get_brick_id_at_ray_position(ray, volume_structure)
            
            if current_brick is None:
                break # Ray left the volume
            
            if current_brick not in working_set:
                # Brick is missing
                add_to_missing_requests(current_brick)
                # Skip marching through this brick; continue ray to next brick
                ray_advance_to_next_brick_boundary(ray, current_brick)
            else:
                # Brick is present, march through it
                march_through_brick(ray, current_brick)
                
    # 3. Report missing bricks for next frame
    # Implementation detail: could use MRT, hash tables, etc.
    report_missing_bricks(missing_requests)
    missing_requests.clear()

def process_missing_requests():
    # Fetch bricks from storage and upload to GPU
    for brick_id in missing_requests:
        data = fetch_brick_from_storage(brick_id)
        upload_to_gpu(brick_id, data)
        working_set.add(brick_id)
```

**Parameters:**
-   **Tile Size:** In tile-based implementations (e.g., Hadwiger et al. [S1]), the viewport is divided into tiles. The size affects the granularity of the hash table and cache misses. Not given in the sources.
-   **Frames to Convergence:** The number of frames allowed for the working set to stabilize. Not given in the sources.

**Edge Cases and Pitfalls:**
-   **Missing Brick Detection:** The ray caster must reliably detect when a brick is not in memory. This is often done by checking a flag in the brickmap or page table entry [S1].
-   **Stale Data:** If the camera moves rapidly, the working set may become outdated, leading to many cache misses. Temporal coherence helps mitigate this [S1].
-   **Concurrency:** When using GPU hash tables, concurrent writes from multiple threads must be handled (e.g., using lock-free structures) [S1].

## Subtopics

### CPU-Guided Hybrid Culling
Combines traditional CPU culling (transfer function, frustum) with ray-guided refinement. Visible nodes from the previous pass are refined, and GPU occlusion queries check visibility against depth [S1].

### MRT-Based Reporting
Uses Multiple Render Targets to report visited bricks over several frames, exploiting spatial and temporal coherence [S1].

### Tile-Based Hash Reporting
Divides the viewport into tiles and uses a GPU hash table per tile to report cache misses, ensuring all missing bricks are eventually reported [S1].

## Operating characteristics
-   **Time Complexity:** Depends on the frequency of missing brick requests. In steady state, it is efficient as only necessary bricks are processed. Initial frames may have high overhead due to frequent misses.
-   **Memory Complexity:** Proportional to the number of visible bricks, not the total volume size. This allows rendering of datasets larger than GPU memory.
-   **Performance:** Reduces memory bandwidth usage by avoiding loading empty or occluded bricks. Performance is highly dependent on the efficiency of the missing brick request mechanism (e.g., hash table contention) [S1].
-   **Strengths:** Implicit frustum and occlusion culling; scalable to very large datasets; adaptive to camera movement.
-   **Limitations:** Requires handling of missing bricks; potential for cache thrashing if camera moves too fast; synchronization overhead between CPU and GPU for brick fetching.

## Background
Ray-guided culling was introduced as an alternative to traditional pre-computed working sets. Key implementations include:
-   Gobbetti et al. [GMG08]: Early hybrid approach using CPU culling and GPU occlusion queries.
-   Crassin et al. [CN09, CNSE10]: Pioneered the use of MRT and later CUDA for efficient visitation reporting.
-   Hadwiger et al. [HBJP12]: Introduced tile-based GPU hash tables for reporting cache misses.
-   Fogal et al. [FSK13]: Improved upon Hadwiger et al. with lock-free hash tables.
