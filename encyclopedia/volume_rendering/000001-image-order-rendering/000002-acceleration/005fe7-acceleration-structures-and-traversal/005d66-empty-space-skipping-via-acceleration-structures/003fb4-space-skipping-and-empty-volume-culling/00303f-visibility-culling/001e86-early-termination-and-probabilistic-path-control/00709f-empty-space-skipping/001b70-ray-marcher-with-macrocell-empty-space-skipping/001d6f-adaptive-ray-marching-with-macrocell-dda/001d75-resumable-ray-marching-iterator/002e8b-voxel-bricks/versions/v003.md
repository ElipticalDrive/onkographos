# Voxel Bricks

Also called: Brickmap Traversal, Brickmap approach

## Overview
Voxel Bricks is a space-skipping acceleration structure for voxel ray marching that groups voxels into fixed-size $8 \times 8 \times 8$ blocks (bricks) and maintains a sparse index (brickgrid) to reference only non-empty bricks [S1, unofficial][S2, unofficial]. It solves the problem of excessive memory bandwidth and traversal overhead in dense or sparse voxel volumes by skipping entire empty regions without visiting individual voxels [S2, unofficial]. Unlike [Adaptive Ray Marching with Voxel Skipping](3870-adaptive-ray-marching-with-voxel-skipping.md) which may use variable-sized blocks or different culling criteria, Voxel Bricks relies on a strict two-level hierarchy: a sparse grid of pointers/references and fixed $8^3$ bricks, offering minimal structural overhead suitable for interactive, dynamic voxel worlds [S2, unofficial].

## How it works
**Inputs:**
- A 3D voxel volume where each voxel has a density/value.
- A ray defined by origin $\mathbf{o}$ and direction $\mathbf{d}$.
- A brick size $B = 8$ (fixed in standard implementations) [S1, unofficial][S2, unofficial].

**Outputs:**
- A rendered pixel color/intensity via ray marching, skipping empty space.

**Data Structures:**
1.  **Brickgrid:** A sparse, potentially infinite 3D grid that references bricks. It does not store voxel data, only references to existing bricks [S1, unofficial]. The grid size is not fixed; it expands as needed to cover the volume of interest [S1, unofficial].
2.  **Brickmap (Brick):** A fixed-size block containing $8 \times 8 \times 8 = 512$ voxels [S1, unofficial][S2, unofficial].
3.  **Occupancy Flag:** Each brick has a boolean flag indicating if it is empty (all voxels are air/background) [S2, unofficial].

**Algorithm Steps:**
1.  **Brickgrid Traversal:** Perform a 3D-DDA (Digital Differential Analyzer) traversal on the brickgrid to find the sequence of bricks intersected by the ray [S1, unofficial].
2.  **Empty Check:** For each brick visited by the DDA, check its occupancy flag [S2, unofficial].
3.  **Skip or Traverse:**
    -   If the brick is marked empty, skip to the next brick in the DDA sequence [S2, unofficial].
    -   If the brick is occupied, retrieve the brickmap and perform standard ray marching on the $8 \times 8 \times 8$ voxels within that brick [S2, unofficial].
4.  **Termination:** Continue until the ray exits the volume or a termination condition (e.g., opacity threshold) is met.

**Pseudocode:**
```python
def ray_march_voxel_bricks(ray_origin, ray_direction, brickgrid, brick_size=8):
    # 1. Determine the bounding box of the brickgrid to traverse
    #    This requires mapping ray_origin and ray_direction to brick coordinates
    brick_start = floor(ray_origin / brick_size)
    brick_end = floor((ray_origin + ray_direction * max_dist) / brick_size)
    
    # 2. 3D-DDA on the brickgrid
    #    Initialize DDA state for brick coordinates
    dda = BrickGridDDA(brick_start, brick_end, ray_direction)
    
    while dda.has_next():
        brick_coords = dda.next()
        
        # 3. Check if brick exists and is non-empty
        #    Note: brickgrid may return None if no brick is stored at this location
        brick = brickgrid.get(brick_coords)
        
        if brick is None or not brick.is_occupied:
            continue  # Skip empty brick
            
        # 4. Ray march within the occupied brick
        #    Map global ray to local brick coordinates
        local_origin = ray_origin - (brick_coords * brick_size)
        local_ray = Ray(local_origin, ray_direction)
        
        # Perform standard ray marching on the 8x8x8 voxel data in brick
        color = ray_march_brick(local_ray, brick.voxels, brick_size)
        
        if color.is_opaque():
            return color
            
    return background_color
```

**Edge Cases and Pitfalls:**
-   **Precision:** Floating-point precision errors in DDA traversal may cause missed bricks or double visits. Use epsilon adjustments when comparing brick boundaries [G].
-   **Sparse Volumes:** If the volume is extremely sparse, the brickgrid itself may consume significant memory if not implemented as a hash map or sparse array. The sources note the brickgrid is "infinite" and has "no particular size," implying a dynamic allocation strategy [S1, unofficial].
-   **Brick Size:** The $8 \times 8 \times 8$ size is fixed in the cited sources. Changing this size requires adjusting the DDA step and brick data layout [S1, unofficial][S2, unofficial].

## Subtopics

### [Ray-Guided Culling](20572-ray-guided-culling.md)
A dynamic memory management strategy that constructs the set of active bricks during the rendering pass, ensuring only intersected bricks are loaded. It differs from static brickmap approaches by handling culling implicitly via ray generation, reducing memory bandwidth for large scenes.

### [Brick Tree (THC Tree)](21103-brick-tree-thc-tree.md)
A hierarchical acceleration structure using a 4x4x4 subdivision (64 children) and a 64-bit bitmask for occupancy. It differs from Voxel Bricks by using a deeper tree structure with bitmasks instead of a sparse grid of fixed $8^3$ bricks, reducing memory reads during traversal.

## Operating characteristics
-   **Time Complexity:** Worst-case scenario for brickgrid traversal is $O(n\sqrt{2})$ for an $n \times n$ grid, where $n$ is the number of bricks along the ray path [S1, unofficial]. Actual performance depends on the sparsity of the volume.
-   **Memory Complexity:** Proportional to the number of occupied bricks. The brickgrid overhead is minimal if implemented as a sparse structure, but can grow with volume size if not managed [S1, unofficial][S2, unofficial].
-   **Strengths:** Minimal structural overhead, suitable for dynamic/interactive voxel worlds where voxels change frequently [S2, unofficial]. Drastically reduces render times by skipping empty space [S2, unofficial].
-   **Limitations:** Fixed brick size ($8^3$) may not be optimal for all volumes. The brickgrid can become large for very sparse volumes if not sparse-encoded. Does not handle occlusion culling automatically unless combined with ray-guided strategies [S1, unofficial].

## Background
The Voxel Bricks method was proposed in the context of optimizing voxel ray-tracing for interactive applications. It was introduced by Uygar B. in a blog post detailing a simple solution to sparse voxel traversal [S1, unofficial]. It was also adopted by Joris Rijsdijk for a ray-marched voxel simulation, prioritizing interactivity and minimal structure overhead for dynamic voxel edits [S2, unofficial]. The approach is often contrasted with more complex structures like SVOs (Sparse Voxel Octrees) or distance fields, offering a simpler alternative for specific use cases [S1, unofficial].
