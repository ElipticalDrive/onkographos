# View Dependent Preprocessing

Also called: Hypergraph-based Preprocessing, Screen Cell Partitioning

## Overview
View Dependent Preprocessing is a parallel volume rendering optimization technique that dynamically partitions the screen and volume data to balance computational load across processors for each visualization instance [S1, unofficial]. It differs from static partitioning by recalculating the workload distribution based on the current camera view and volume projection, using hypergraph partitioning to minimize communication overhead during cluster migration [S1, unofficial].

## How it works
**Inputs:**
*   Current camera view parameters.
*   Volume dataset (partitioned into clusters).
*   Target total screen cell count $C$.

**Outputs:**
*   Mapping of volume clusters to processors.
*   Screen cell grid definition.

**Data Structures:**
*   **Local Hypergraph:** An intermediate structure per processor containing vertices for local volume clusters and screen cells, and hyperedges representing intersections (load) between them.
*   **Global Hypergraph:** A unified structure containing all screen cells with rendering load and all volume clusters, plus special processor vertices.

**Steps:**

1.  **Calculate Grid Granularity:**
    Determine the screen cell size $g$ (pixels per side) using the projection area $A$ and target cell count $C$:
    $$ g = \sqrt{ \frac{ -2 + \sqrt{ (C - 1) A - 2C\sqrt{A} + 2C } }{ A } } $$
    where $A$ is the projection area of the volume on the screen in pixels, and $C$ is the total number of screen cells with associated rendering load [S1, unofficial].

2.  **Impose Grid:**
    Overlay a grid of $g \times g$ pixel cells onto the screen. Identify which cells have non-zero rendering load [S1, unofficial].

3.  **Local Hypergraph Creation:**
    Each processor constructs a local hypergraph for its subset of the volume.
    *   Vertices: Local volume clusters and screen cells intersecting the local volume.
    *   Hyperedges: Represent the intersection (load) between a cluster and a screen cell.
    *   This tracks connectivity between local data clusters and screen regions [S1, unofficial].

4.  **Global Hypergraph Creation:**
    *   Perform an all-to-all communication where each processor sends its local hypergraph to all other processors.
    *   Merge local hypergraphs into a global hypergraph.
    *   Discard screen cell vertices with no rendering load.
    *   Add special processor vertices required for the remapping model (one-phase or two-phase) [S1, unofficial].

5.  **Hypergraph Partitioning:**
    *   Each processor executes the PaToIl hypergraph partitioning tool sequentially on the global hypergraph.
    *   **Two-phase model:** The partition result is input to a graph bipartitioning code to calculate cluster-processor mappings.
    *   **One-phase model:** The mapping is calculated directly by checking the locations of special processor vertices in the partition returned by PaToIl [S1, unofficial].

**Parameters:**
*   $C$ (Total screen cell count): Empirically determined to be between 400 and 500 [S1, unofficial].

**Edge Cases:**
*   If $A = 0$ (volume not visible), the formula is undefined. The implementation must handle this by skipping preprocessing or using a default grid.
*   If a screen cell has no load, it is discarded from the global hypergraph to reduce partitioning complexity [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Dominated by the all-to-all communication and hypergraph partitioning. PaToIl is executed sequentially on each processor, making the preprocessing time dependent on the global hypergraph size and partitioning algorithm efficiency.
*   **Memory Complexity:** Requires storing local and global hypergraphs. The global hypergraph size is proportional to the number of screen cells and volume clusters.
*   **Strengths:** Adapts to view changes, balancing load dynamically. Reduces idle time by ensuring each processor handles a proportional share of the visible volume.
*   **Limitations:** Preprocessing overhead must be small compared to rendering time to be effective. Communication overhead for all-to-all exchange can be significant on large clusters.
*   **When to use:** Parallel volume rendering with dynamic views or complex datasets where static partitioning leads to load imbalance.
*   **When not to use:** Static views with uniform data distribution, or when preprocessing overhead exceeds the benefits of load balancing.

## Background
This method was developed as part of a hypergraph-partitioning based remapping model for image-space parallel volume rendering. It addresses the inefficiency of static partitioning in parallel volume rendering by introducing a view-dependent preprocessing phase that recalculates workload distribution for every visualization instance [S1, unofficial]. The approach uses adaptive screen sub-division and hypergraph partitioning to optimize cluster migration and load balancing.
