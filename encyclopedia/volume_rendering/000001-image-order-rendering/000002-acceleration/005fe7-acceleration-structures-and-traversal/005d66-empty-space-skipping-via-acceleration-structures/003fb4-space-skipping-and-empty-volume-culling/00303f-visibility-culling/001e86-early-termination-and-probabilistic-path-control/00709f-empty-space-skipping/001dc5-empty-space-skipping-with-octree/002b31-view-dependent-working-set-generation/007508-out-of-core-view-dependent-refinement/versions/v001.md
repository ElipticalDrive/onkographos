# Out-of-Core View-Dependent Refinement

Also called: Adaptive octree refinement, Run-time refinement

## Overview
Out-of-core view-dependent refinement is a run-time component of an out-of-core renderer that pages in only the active nodes of a level-of-detail hierarchy using memory mapping, allowing asynchronous refinement and rendering [S1]. It solves the problem of rendering large datasets that exceed available memory by dynamically constructing a view-dependent working set (the "front") from a static on-disk octree, hiding I/O latency through asynchronous, breadth-first traversal [S1]. Unlike explicit paging systems, it relies on the operating system's memory-mapped file access to fetch data on demand, which is particularly effective when refinement and rendering tasks are decoupled [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A static external octree $H$ stored on disk, a viewpoint $e$, a view frustum, a screen resolution $\lambda$ (pixels per radian), and an error threshold $\tau$.
*   **Output:** A dynamic in-core octree $H'$ (the "front") containing only visible and necessary nodes, and a list of triangles to be rendered.

**Data Structures:**
The in-core octree node structure (Table 4 in [S1]) contains the following fields:
*   **Vertex Data:**
    *   `K`: $3 \times 3$ curvature matrix.
    *   `n̂`: $3$-vector vertex normal.
    *   `p`: $3$-vector vertex position.
    *   `ε`: Scalar quadric error (volumetric error mapped to length).
    *   `r`: Scalar bounding sphere radius.
*   **Triangle Data:**
    *   `n_T`: Count of triangles assigned to this node.
    *   `T`: List of triangles (vertex indices).
    *   `n_R`: Count of references from child nodes.
    *   `R`: List of references to this node (from children).
*   **Octree Data:**
    *   `leaf`: Boolean, is this node a leaf in the static on-disk octree $H$?
    *   `front`: Boolean, is this node a leaf in the dynamic in-core octree $H'$?
    *   `l`: Index, octree level.
    *   `s`: Pointer to the static external node on disk.
    *   `C`: Array of 8 pointers to children.
    *   `prev`: Pointer to the previous node in the refinement queue $Q$.
    *   `next`: Pointer to the next node in the refinement queue $Q$.

**Refinement Queue:**
A linear circular queue $Q$ orders active nodes roughly in a breadth-first manner. This ordering allows preemption for paging large data blocks and ensures detail is paged in evenly over the visible surface. A pointer tracks the "tail" of the queue to resume refinement where it left off [S1].

**Screen Space Error Metric:**
The screen space error $\rho$ determines if a node requires refinement. It is defined as:
$$ \rho = \lambda \eta \frac{\epsilon}{d} = \lambda \epsilon \frac{\sqrt{\mathbf{v}^T \mathbf{K} \mathbf{v}}}{\sqrt{\mathbf{v}^T \mathbf{v}}} $$
Where:
*   $\lambda$: Screen resolution in pixels per radian.
*   $\epsilon$: Quadric error (volumetric error converted to length).
*   $d = \|\mathbf{v}\|$: Distance from the viewpoint $e$ to the node position $p$.
*   $\mathbf{v} = e - p$: Vector from node to viewpoint.
*   $\mathbf{K}$: Curvature matrix.
*   $\eta$: Directionality factor for silhouette preservation.

For efficiency, the active condition $\rho > \tau$ is rearranged to avoid square roots and division:
$$ \text{active} \iff \epsilon^2 (\mathbf{v}^T \mathbf{K} \mathbf{v}) > \kappa^2 (\mathbf{v}^T \mathbf{v})^2 $$
Where $\kappa = \tau / \lambda$ is the angular error threshold in radians [S1].

**Algorithm Steps:**
1.  **Initialization:** Create a single node for the root of the dynamic octree $H'$. Initialize the refinement queue $Q$ with this root.
2.  **Traversal Loop:** While $Q$ is not empty and refinement budget/time permits:
    a.  Dequeue the next node $p$ from $Q$.
    b.  **Frustum Culling:** Test $p$'s bounding sphere against the six planes of the view frustum.
        *   If not visible, call `node-collapse(p)` and continue to the next node.
    c.  **Error Evaluation:** If visible, compute the screen space error metric $\rho$ (or the rearranged active condition).
    d.  **Refinement Decision:**
        *   If $\rho > \tau$ (active) AND `front(p)` is true (node is a leaf in $H'$), call `node-expand(p)`.
        *   If $\rho \le \tau$ (inactive) AND `front(p)` is false (node is not a leaf in $H'$), call `node-collapse(p)`.
3.  **Rendering Preparation:** After refinement, traverse the nodes in $H'$. Collect triangles from nodes and append vertex positions/normals from proxy nodes to form the final render list.

**Pseudocode:**

```python
def out_of_core_refinement(root_node, viewpoint, frustum_planes, lambda_val, tau_val):
    """
    Performs out-of-core view-dependent refinement.
    root_node: The root node of the dynamic octree H'.
    viewpoint: The camera position e.
    frustum_planes: List of 6 plane equations for the view frustum.
    lambda_val: Screen resolution in pixels per radian.
    tau_val: User-specified screen space error threshold.
    """
    kappa = tau_val / lambda_val
    queue = CircularQueue()
    queue.enqueue(root_node)
    
    # Track progress for preemption
    tail = root_node
    
    while not queue.is_empty():
        node = queue.dequeue()
        
        # 1. Frustum Culling
        if not is_visible(node.bounding_sphere, frustum_planes):
            node_collapse(node)
            continue
            
        # 2. Error Evaluation
        # v = e - p
        v = vector_sub(viewpoint, node.position)
        d_sq = dot(v, v)
        
        # Check active condition: epsilon^2 * (v^T K v) > kappa^2 * (v^T v)^2
        # Note: node.quadric_error is epsilon
        lhs = (node.quadric_error ** 2) * (transpose(v) @ node.curvature_matrix @ v)
        rhs = (kappa ** 2) * (d_sq ** 2)
        
        is_active = lhs > rhs
        
        # 3. Refinement Decision
        if is_active and node.front:
            node_expand(node)
        elif not is_active and not node.front:
            node_collapse(node)
            
        # Update tail for preemption/resumption
        tail = node

def node_expand(p):
    """
    Expands node p by creating its children.
    Valid only if p is a leaf in the dynamic octree H'.
    """
    p.front = False
    
    for child in p.children:
        # Initialize child vertex data from static source or computation
        initialize_vertex_data(child)
        
        # If child is not a leaf in the static octree H, add to queue
        if not child.leaf:
            queue.enqueue(child)
            
    # Update references: triangles assigned to p are now associated with children
    # References from proxy nodes need to be updated
    for triangle in p.triangles:
        for vertex in triangle.vertices:
            # Identify proxy node based on vertex octcode
            proxy = identify_proxy_node(vertex.octcode)
            # Add reference from proxy to this triangle
            proxy.add_reference(triangle)
            
    # Transfer references from p to its children
    for ref in p.references:
        # Identify which child corresponds to this reference
        child = get_child_for_reference(ref)
        # Transfer ref from p to child
        child.add_reference(ref)
        # Update proxy pointer for the reference
        update_proxy_pointer(ref, child)

def node_collapse(p):
    """
    Collapses node p by removing its descendants.
    """
    for child in p.children:
        node_collapse(child)
        
    # Transfer references from children back to p
    for child in p.children:
        for ref in child.references:
            p.add_reference(ref)
            # Remove child from queue and H' if it was not a leaf in H
            if not child.leaf:
                queue.remove(child)
                remove_from_dynamic_octree(child)
                
    # Clean up references from proxy nodes
    for triangle in p.triangles:
        for vertex in triangle.vertices:
            proxy = identify_proxy_node(vertex.octcode)
            proxy.remove_reference(triangle)
            
    p.front = True
```

**Parameters:**
*   $\tau$: User-specified error threshold for screen space error $\rho$ [S1].
*   $\lambda$: Screen resolution in pixels per radians [S1].
*   $\kappa$: Angular error threshold in radians, defined as $\tau/\lambda$ [S1].

**Edge Cases and Pitfalls:**
*   **Nesting Condition Violation:** The direction and length of vector $\mathbf{v}$ vary from node to node. This can potentially violate the property that the parent's projected error is larger than its children's, despite additive quadric errors and increasing curvature [S1].
*   **Preemption:** The breadth-first queue allows preemption. If refinement is interrupted, the system must track the "tail" of the queue to resume correctly [S1].
*   **Memory Mapping Limits:** Explicit paging schemes may offer better scalability and cache replacement policies, but memory mapping leverages OS fetching which is attractive for decoupled/asynchronous tasks [S1].

## Operating characteristics
*   **Time Complexity:** Refinement time depends on the number of visible nodes and the depth of the octree. The breadth-first traversal ensures uniform detail distribution.
*   **Memory Complexity:** Only active nodes (the "front") are kept in memory. The size of the working set is determined by the error threshold $\tau$ and the view frustum.
*   **Performance:** Performance is heavily dependent on I/O latency. Memory mapping allows the OS to handle paging, which can be efficient but lacks explicit control over cache replacement [S1].
*   **Strengths:** Asynchronous refinement and rendering; decoupled tasks; incremental updates; handles very large datasets that do not fit in RAM.
*   **Limitations:** Potential for frame rate spikes if I/O is slow; memory mapping may be limited by OS addressing space (e.g., 32-bit limits); less control over memory usage compared to explicit paging [S1].
*   **When to use:** Large-scale out-of-core visualization where the dataset exceeds available memory and asynchronous processing is acceptable.
*   **When not to use:** Applications requiring strict frame rate control with predictable memory usage (consider explicit paging or priority queues) [S1].

## Background
This method is part of the out-of-core construction and visualization of multiresolution surfaces, described by Lindstrom and Pascucci [S1]. It builds on earlier work in out-of-core rendering of large terrain by Hoppe [1998] and Lindstrom and Pascucci [2001] [S1]. The approach uses memory mapping to associate the on-disk hierarchy with a logically contiguous address space, letting the OS fetch data on first access [S1].
