# View-Dependent Visibility Culling

Also called: Camera-ordered visibility, Livnat and Hansen culling

## Overview
View-dependent visibility culling is an acceleration technique for volume rendering that orders traversal based on camera position to cull nodes occluded by previously traversed nodes closer to the camera [S1, unofficial]. It extends empty-space skipping by pruning empty subtrees and discarding occluded geometry, leveraging the multiresolution nature of hierarchical structures like octrees to adaptively decide extraction resolution [S1, unofficial].

## How it works
**Inputs:** Camera position and orientation; hierarchical data structure (octree or quadtree) representing the volume or heightmap; traversal state [G].
**Outputs:** Set of visible nodes/voxels to be rendered or extracted [G].
**Data Structures:**
*   **Octree/Quadtree:** Nodes store metadata indicating emptiness and potentially maximum values for culling decisions [S1, S2, unofficial].
*   **Occlusion Buffer:** Tracks spatial extents of previously processed nodes to enable fast occlusion tests [G].
**Steps:**
1.  **Initialize Traversal:** Start at the root of the hierarchical structure [G].
2.  **Camera-Ordered Traversal:** Traverse the tree in an order determined by the camera's view direction (e.g., front-to-back) [G].
3.  **Empty Subtree Pruning:** If a node is marked as empty (containing no surface/data), prune its entire subtree and do not traverse its children [S1, unofficial].
4.  **Visibility Culling:** For non-empty nodes, check if the node is occluded by any previously traversed node that is closer to the camera [S1, unofficial].
    *   If occluded, discard the node and its children [S1, unofficial].
    *   If visible, process the node (e.g., extract mesh or render voxels) and mark its spatial extent as occluded for subsequent nodes [G].
5.  **Recursive Descent:** If the node is not a leaf and not culled, recursively traverse its children [G].
6.  **Termination:** Stop when the traversal completes or all reachable nodes have been processed or culled [G].
**Formulas:** Not given in the sources.
**Parameters:**
*   **Occlusion Test:** Not given in the sources. [G] Typically involves bounding box intersection with previously rendered surfaces or depth buffer checks.
*   **Traversal Order:** Front-to-back relative to camera [G].
**Edge Cases:**
*   **Precision:** Occlusion tests must handle floating-point inaccuracies near node boundaries [G].
*   **Degenerate Input:** Nodes with zero volume or coincident geometry may cause incorrect occlusion if not handled [G].
**Pseudocode:**
```python
def view_dependent_culling(node, camera_pos, occlusion_buffer):
    # Step 3: Prune empty subtrees
    if node.is_empty:
        return

    # Step 4: Check occlusion against previously traversed nodes
    if is_occluded(node.bounding_box, occlusion_buffer):
        return

    # Step 4: Process visible node
    if node.is_leaf:
        render_or_extract(node)
        update_occlusion_map(node.bounding_box, occlusion_buffer)
    else:
        # Step 5: Traverse children in camera-ordered manner
        children = get_children_in_camera_order(node, camera_pos)
        for child in children:
            view_dependent_culling(child, camera_pos, occlusion_buffer)
```

## Subtopics

### Livnat and Hansen Culling
Uses an octree to order visibility based on camera position and cull occluded nodes [S1, unofficial]. Choose when using octrees for real-time adaptive surface reconstruction [S1, unofficial]. [Livnat and Hansen, 1998]

### Quadtree Heightmap Culling
Uses a quadtree stored like mipmaps with maximum subpixel values to discard invisible voxels in O(log n) time [S2, unofficial]. Choose for heightmap-based terrain rendering [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** O(log n) in the best cases for discarding invisible voxels using a quadtree [S2, unofficial]. Octree traversal is generally efficient but depends on the density of visible data [S1, unofficial].
*   **Memory Complexity:** Requires storing the hierarchical structure (octree/quadtree) and potentially an occlusion map [S1, S2, unofficial].
*   **Strengths:** Reduces computation by skipping occluded regions; adapts to camera movement [S1, S2, unofficial].
*   **Limitations:** Requires hierarchical data structure; occlusion testing can be costly if not optimized [S1, S2, unofficial].
*   **When to Use:** Real-time rendering with dynamic camera movement; scenes with significant occlusion [S1, S2, unofficial].

## Background
Originated with Livnat and Hansen [LH98] for real-time adaptive surface reconstruction using octrees [S1, unofficial]. Westermann et al. [WKE99] recognized the benefits of exploiting multiresolution for speedups [S1, unofficial]. Also discussed in the context of voxel landscape engines using quadtrees [S2, unofficial].
