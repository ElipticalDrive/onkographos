# Wave Surfing Optimisations

Also called: 2D raycasting, Wave surfing algorithm

## Overview
Wave Surfing Optimisations is a technique for accelerating the rendering of 3D landscapes (terrains) by reducing computation time in the rendering loop when the landscape is flat, specifically by minimizing time spent in interpolation between drawing operations [S1, unofficial][S2]. It is a simplified variant of ray-based approaches used for real-time visualization of 3D models on low-end hardware [S2]. It sets itself apart from general volume rendering acceleration structures by focusing on a 2D height-map traversal strategy that exploits the coherence of terrain geometry, rather than 3D voxel grid traversal [S1, unofficial][S2].

## How it works
**Inputs and Outputs:**
- Input: A height map representing the landscape, a camera position, and a viewing direction.
- Output: A rendered image of the terrain.

**Data Structures:**
- Height Map: A 2D array of elevation values. The specific bit-packing or data type is not given in the sources [S1, unofficial][S2].

**Steps:**
1. **Ray Casting Setup:** For each pixel (or column of pixels) in the screen space, cast a ray into the scene. In the context of terrain rendering, this often involves projecting the ray against the height map [S2].
2. **Traversal with Variable Step Size:** Traverse the height map along the ray's path. To optimize performance, the step size through the height map can be increased as the distance from the camera increases. This discards more information for distant voxels, making them "more vague" [S1, unofficial].
3. **Interpolation Reduction:** The core optimization is to reduce the number of interpolation operations performed between drawing steps. In a naive implementation, every column of voxels might be processed; Wave Surfing aims to skip or batch these operations when the landscape is flat [S1, unofficial].
4. **Rendering:** Draw the visible voxels or terrain segments.

**Formulas:**
- The traversal complexity is stated as $O(n)$, where $n$ is related to the number of steps through the height map [S1, unofficial].
- The sources mention that a hierarchical visibility scheme (e.g., quadtree) could achieve $O(\log n)$ discard of invisible voxels, but Wave Surfing itself is described as taking "nearly constant steps" in the best case for flat landscapes [S1, unofficial].

**Parameters:**
- Step Size: Can be variable, increasing with distance from the camera [S1, unofficial].
- Typical values for step size or terrain resolution are not given in the sources.

**Edge Cases and Pitfalls:**
- **Flat Landscapes:** The rendering loop performs very badly if the landscape is completely flat, because every single column of voxels is higher than the previous and must be drawn [S1, unofficial].
- **Large Mountains:** Variable step sizes can cause problems if large mountains are completely skipped or rendered incorrectly due to the increased step size in the distance [S1, unofficial].
- **Hierarchical Alternative:** A simple quadtree could be stored like mipmaps, containing the maximum value of all subpixels, to allow for $O(\log n)$ discard of invisible voxels, which is considered ideal but not part of the basic Wave Surfing technique [S1, unofficial].

## Subtopics

### Variable Step Size
A sub-technique where step size increases with distance, trading accuracy for speed in the distance. It sets itself apart by dynamically adjusting resolution. Choose it when performance is critical and distant details are less important. [S1, unofficial]

### Hierarchical Visibility (Quadtree)
An alternative optimization mentioned as ideal for $O(\log n)$ performance. It sets itself apart by using a tree structure for culling. Choose it when flat landscapes cause performance issues with basic Wave Surfing. [S1, unofficial]

## Operating characteristics
- **Time Complexity:** The basic technique is $O(n)$, where $n$ is the number of steps through the height map [S1, unofficial]. A hierarchical alternative could achieve $O(\log n)$ [S1, unofficial].
- **Memory Complexity:** Not given in the sources.
- **Measured Performance:** Used in early computer games on low-end hardware, enabling real-time visualization of 3D terrains [S2].
- **Scaling:** Performance degrades on completely flat landscapes where every column must be drawn [S1, unofficial].
- **Strengths:** Reduces interpolation overhead, suitable for low-end hardware [S1, unofficial][S2].
- **Limitations:** Poor performance on flat landscapes; variable step sizes can cause artifacts with large mountains [S1, unofficial].
- **When to use:** Real-time terrain rendering on hardware with limited processing power [S2].
- **When not to use:** When high accuracy in distant terrain is required, or when landscapes are predominantly flat [S1, unofficial].

## Background
- **Origin:** The technique is associated with the development of realtime voxel landscape engines, particularly in the context of early 3D games [S1, unofficial][S2].
- **History:** It was used in games such as Comanche (1992), Delta Force (1998), Armored Fist (1994), Blade Runner (1997), and Hexplore (1998) [S2]. It was also used in early consoles like Amiga, Nintendo, and Gameboy with software rasterization [S2].
- **Usage:** Primarily used for terrain visualization in early 3D games and simulations where polygon-based rendering was not yet feasible or efficient on the target hardware [S2].
