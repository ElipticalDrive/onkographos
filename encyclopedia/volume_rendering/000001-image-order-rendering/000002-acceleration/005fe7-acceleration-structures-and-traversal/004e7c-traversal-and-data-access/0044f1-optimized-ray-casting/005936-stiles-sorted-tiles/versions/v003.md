# STiles (Sorted Tiles)

Also called: Sorted Tiles, Sorting Tiles

## Overview
STiles is a progressive ray casting technique that decomposes the image space into screen-space tiles, sorts them by estimated rendering cost, and renders them in batches across subsequent frames until a fixed time budget is reached [S1, unofficial]. It addresses the problem of interactive volume rendering on mobile and low-performance devices by avoiding the stall caused by rendering high-resolution images in a single frame [S1, unofficial]. Unlike FBSlabs, which renders fixed slabs across the entire image, STiles groups tiles of similar cost to efficiently utilize the GPU within a strict time budget, leveraging 3D texture cache locality by processing tiles rather than individual rays [S1, unofficial].

## How it works
The method operates in three phases: an interaction phase, a sorting phase, and a progressive rendering phase.

### Inputs and Outputs
*   **Input:** High-resolution volume dataset, transfer function, camera parameters, viewport dimensions.
*   **Output:** Final high-resolution rendered image.
*   **Intermediate Data:**
    *   $T_{low}$: A 2D texture storing low-resolution color (RGB) and ray cost (Alpha).
    *   $T_{high}$: A 2D texture storing high-resolution color for rendered tiles.
    *   Correlation Maps: Two 2D textures mapping sorted tile indices to unsorted tile coordinates and vice versa.

### Data Structures
1.  **$T_{low}$**: A 2D texture where:
    *   RGB channels: Low-resolution ray casting color.
    *   Alpha channel: Ray cost, defined as the number of ray samples taken during the low-resolution pass.
2.  **Correlation Maps**: Two textures generated during sorting. They allow translation between the sorted order of tiles and their original screen positions.
3.  **Tile Grid**: The viewport is divided into square tiles of fixed size $S \times S$.

### Parameters
*   **Tile Size ($S$):** 8x8 pixels [S1, unofficial]. This size balances 3D texture cache locality against visual blockiness during the transition from low to high resolution.
*   **Time Budget ($T_{budget}$):** 0.1 seconds per frame [S1, unofficial]. The maximum time allowed for rendering high-resolution tiles in a single frame.

### Algorithm Steps

1.  **Low Resolution Ray Casting (Interaction Phase):**
    While the user interacts (rotates/zooms), perform standard low-resolution ray casting in a fragment shader. For each pixel, store the resulting color in the RGB channels of $T_{low}$ and the number of ray samples taken in the Alpha channel of $T_{low}$ [S1, unofficial]. This alpha value serves as the estimated rendering cost for the corresponding high-resolution tile.

2.  **Tile Sorting (Sorting Phase):**
    Triggered once user interaction stops.
    a.  **Tile Division:** Split the viewport into tiles of size $S \times S$.
    b.  **Cost Estimation:** For each tile, estimate its cost by querying the Alpha channel of $T_{low}$ at the tile's center pixel [S1, unofficial].
    c.  **GPU Radix Sort:** Sort the tiles by their estimated cost using a GPU radix sort implemented in three compute shader steps [S1, unofficial]:
        i.  **Group Counting:** Classify tiles into groups based on cost and count the number of tiles in each group.
        ii. **Group Offset Setting:** Scan the counters to establish start offsets for each group in the output texture.
        iii. **Sorting:** Place tiles into the output texture according to the offsets.
    d.  **Correlation Maps:** Generate two coordinate maps during sorting to translate between sorted tile indices and unsorted screen coordinates [S1, unofficial].

3.  **Progressive High Resolution Ray Casting (Rendering Phase):**
    Render tiles in the sorted order into $T_{high}$.
    a.  **Budget Management:** Determine the number of tiles $N$ to render in the current frame. The algorithm uses a decreasing tile budget per frame to compensate for the non-linear increase in accumulated time (as later tiles may be more expensive or cache misses increase) [S1, unofficial].
    b.  **Rendering Loop:** Render $N$ tiles from the sorted list. After rendering each tile (or batch), measure elapsed time. If the time budget ($0.1$s) is exceeded, stop rendering for that frame [S1, unofficial].
    c.  **Ray Casting:** In the fragment shader for high-resolution tiles, discard rays that do not intersect the proxy geometry. This allows empty or nearly empty tiles to complete instantly, even if their cost estimate was non-zero [S1, unofficial].

4.  **Compositing:**
    For each pixel in the final image:
    *   If the pixel belongs to a tile that has been rendered in $T_{high}$, use the high-resolution color from $T_{high}$.
    *   Otherwise, use the low-resolution color from $T_{low}$ [S1, unofficial].
    This compositing is performed every frame, progressively replacing low-resolution pixels with high-resolution ones.

5.  **Iteration:**
    Repeat steps 3 and 4 in successive frames until all tiles are rendered and $T_{high}$ contains the complete high-resolution image.

### Edge Cases and Pitfalls
*   **Empty Tiles:** Tiles with zero cost (empty regions) are rendered first. The fragment shader discards rays not intersecting proxy geometry, allowing these tiles to complete instantly [S1, unofficial].
*   **Cost Estimation Accuracy:** Tile cost is estimated from a single sample at the tile center in $T_{low}$. This is not perfectly reliable for the entire tile, but the impact is mitigated by the fast completion of empty tiles [S1, unofficial].
*   **Sorting Granularity:** Sorting individual rays yields poorer performance than sorting tiles. Packing rays into tiles leverages the 3D texture cache [S1, unofficial].
*   **Visual Transition:** The transition from low to high resolution is visible. Tile size $8 \times 8$ is a compromise between cache performance and visual blockiness [S1, unofficial].
*   **Time Budget Exceedance:** If the time budget is exceeded, rendering stops for that frame. The next frame resumes from where it left off.

## Operating characteristics
*   **Time Complexity:** The sorting phase is $O(N \log N)$ or $O(N)$ depending on the radix sort implementation, where $N$ is the number of tiles. This is performed once per interaction session. The rendering phase is proportional to the number of tiles rendered per frame, bounded by the time budget.
*   **Memory Complexity:** Requires storage for $T_{low}$, $T_{high}$, and correlation maps. Memory usage is $O(W \times H)$, where $W, H$ are viewport dimensions.
*   **Measured Performance:** On Nexus 6, STiles achieved average completion times of 8.84s (Vix), 9.73s (Head), 8.83s (Obelix), 9.75s (Chamaleon), and 8.65s (Melanix) [S1, unofficial]. This is approximately half the time of FBSlabs [S1, unofficial]. On Nexus 6P, times were 16.52s (Vix), 16.20s (Head), 17.06s (Obelix), 16.89s (Chamaleon), and 19.73s (Melanix) [S1, unofficial].
*   **Strengths:** Maintains interactivity by bounding frame time. Efficiently utilizes GPU cache by processing tiles. Faster completion than slab-based methods.
*   **Limitations:** Requires multiple frames to reach full resolution. Visual transition artifacts. Sorting overhead (though negligible).
*   **When to Use:** Mobile and low-performance devices where interactive frame rates are critical and full-resolution rendering cannot be completed in a single frame.
*   **When Not to Use:** High-performance desktops where full-resolution rendering is feasible in one frame, or where visual continuity is more important than interactivity.

## Background
STiles was introduced in the paper "Progressive Ray Casting for Volumetric Models on Mobile Devices" [S1, unofficial]. The work was motivated by the need to render large medical volume datasets (resolutions $> 512^3$) on mobile devices at full resolution while maintaining interactive frame rates. The method builds on the observation that rendering time increases non-linearly when rendering a fixed number of tiles per frame, necessitating a decreasing tile budget per frame [S1, unofficial]. It was developed as an alternative to Front-to-back Slabs (FBSlabs) and Simple progressive ray casting, offering better performance and cache utilization [S1, unofficial].
