# STiles (Sorted Tiles)

Also called: Sorted Tiles

## Overview
STiles is a progressive rendering technique for volume visualization that decomposes the image space into square tiles, sorts them by estimated rendering cost, and renders them in batches over subsequent frames until a time budget is reached [S1, unofficial]. It addresses the challenge of maintaining interactive frame rates on mobile and low-performance devices while rendering high-resolution medical data (typically $>512^3$) [S1, unofficial]. Unlike [Light Ray Extinction Optimization](15221-light-ray-extinction-optimization.md) which optimizes ray traversal, or [Parallel Volume Rendering for Computational Flow Imaging](16105-parallel-volume-rendering-for-computational-flow-imaging.md) which focuses on data parallelism, STiles optimizes frame delivery by grouping tiles of similar cost [S1, unofficial]. It differs from [Front-to-back Slabs (FBSlabs)](11373-optimized-ray-casting.md) by sorting individual tiles rather than rendering fixed slabs across the entire image [S1, unofficial].

## How it works
**Inputs:** High-resolution volume dataset; viewport dimensions; time budget per frame for high-resolution rendering.
**Outputs:** Progressive high-resolution image.

**Data Structures:**
1.  **$T_{low}$**: A 2D texture storing the low-resolution result.
    *   RGB channels: Low-resolution color.
    *   Alpha channel: Ray cost (number of ray samples) used as a cost estimation [S1, unofficial].
2.  **$T_{high}$**: A 2D texture storing the high-resolution result for rendered tiles.
3.  **Correlation Maps**: Two maps generated during sorting to convert between unsorted and sorted tile coordinates [S1, unofficial].
4.  **Tile List**: An array of tile identifiers sorted by cost [S1, unofficial].

**Parameters:**
*   **Tile Size**: Not given in the sources.
*   **Time Budget**: Fixed duration per frame for high-resolution rendering [S1, unofficial].
*   **Resolution**: Low-resolution is used during interaction; high-resolution is used for final output [S1, unofficial].

**Steps:**

1.  **Low Resolution Ray Casting (Interactive Phase):**
    During user interaction, perform standard low-resolution ray casting in a fragment shader. For each pixel, store the resulting color in the RGB channels of $T_{low}$ and the number of ray samples taken in the Alpha channel of $T_{low}$ [S1, unofficial]. This alpha value serves as the cost estimation [S1, unofficial].

2.  **Tile Sorting (Post-Interaction):**
    Once user interaction stops, split the viewport into square tiles. Use compute shaders to sort these tiles based on the cost stored in $T_{low}$'s alpha channel. The sorting pipeline typically involves a GPU radix sort algorithm implemented via compute shaders, including a group count step [S1, unofficial]. Generate two correlation maps to allow coordinate conversion between unsorted and sorted tile spaces [S1, unofficial].

3.  **Progressive High Resolution Ray Casting (Rendering Phase):**
    Render tiles from the sorted list in order. Render a batch of high-resolution tiles until the fixed time budget for the frame is reached. Store the results in $T_{high}$ [S1, unofficial].

4.  **Progressive High Resolution Ray Casting (Compositing Phase):**
    Composite the current display image. For each pixel, select the high-resolution value from $T_{high}$ if the corresponding tile has been rendered; otherwise, select the low-resolution value from $T_{low}$ [S1, unofficial].

5.  **Iteration:**
    In the next frame, resume rendering tiles from step 3 (starting from the next unrendered tile in the sorted list) until all tiles are rendered [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Cost Estimation Accuracy:** The alpha channel stores the number of ray samples. If the low-resolution sampling is too coarse, the cost estimation may be inaccurate, leading to suboptimal tile sorting [S1, unofficial].
*   **Time Budget Management:** The time budget must be carefully tuned to ensure smooth progressive refinement without stalling the application [S1, unofficial].
*   **Memory Usage:** Storing both $T_{low}$ and $T_{high}$ requires additional memory bandwidth and storage [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Sorting is $O(N \log N)$ or $O(N)$ depending on the radix sort implementation, where $N$ is the number of tiles. Rendering is proportional to the time budget [S1, unofficial].
*   **Memory Complexity:** Requires storage for $T_{low}$, $T_{high}$, and correlation maps [S1, unofficial].
*   **Performance:** Designed for mobile and low-performance devices, achieving interactive frame rates with large datasets ($>512^3$) [S1, unofficial].
*   **Strengths:** Provides immediate visual feedback during interaction; progressively refines the image; efficient use of time budget by rendering expensive tiles first [S1, unofficial].
*   **Limitations:** Requires a post-interaction sorting step; quality depends on the accuracy of the cost estimation [S1, unofficial].
*   **When to use:** Interactive volume rendering on resource-constrained devices where full resolution cannot be rendered in real-time [S1, unofficial].
*   **When not to use:** When real-time full-resolution rendering is possible; when interaction continues indefinitely without a clear "stop" point for sorting [S1, unofficial].

## Background
STiles was developed to address the problem of volume rendering medical data on mobile and low-performance devices [S1, unofficial]. It was introduced in the paper "Progressive Ray Casting for Volumetric Models on Mobile Devices" [S1, unofficial]. The technique was proposed as an alternative to Front-to-back Slabs (FBSlabs) for progressive rendering [S1, unofficial].
