# STiles (Sorted Tiles)

Also called: Sorted Tiles

## Overview
STiles is a progressive rendering technique for volume visualization that decomposes the image space into square tiles, sorts them by estimated rendering cost, and renders them in batches over subsequent frames until a time budget is reached [S1, unofficial]. It addresses the challenge of interactive volume rendering on mobile and low-performance devices by providing immediate low-resolution feedback during interaction and progressively refining the image to full resolution without stalling [S1, unofficial]. Unlike sibling method [Light Ray Extinction Optimization](15221-light-ray-extinction-optimization.md) which optimizes ray traversal, or [Parallel Volume Rendering for Computational Flow Imaging](16105-parallel-volume-rendering-for-computational-flow-imaging.md) which focuses on data parallelism for flow fields, STiles optimizes the *order* of rendering work to fit within frame time constraints [S1, unofficial]. It differs from [Front-to-back Slabs (FBSlabs)](11373-optimized-ray-casting.md) by sorting individual tiles rather than rendering fixed slabs across the entire image [S1, unofficial].

## How it works
The method operates in two phases: an interactive low-resolution phase and a progressive high-resolution refinement phase.

### Inputs and Outputs
*   **Input:** High-resolution volume dataset, viewport dimensions, user interaction state (active/inactive), and a fixed time budget per frame for high-resolution rendering.
*   **Output:** A composited image that transitions from low-resolution interactive view to full-resolution static view.

### Data Structures
1.  **$T_{low}$**: A 2D texture storing the low-resolution rendering result.
    *   **RGB channels**: Store the low-resolution color.
    *   **Alpha channel**: Stores the ray cost, defined as the number of ray samples taken during the low-resolution pass. This serves as an estimation of rendering cost for sorting [S1, unofficial].
2.  **$T_{high}$**: A 2D texture storing the high-resolution rendering result. Initially empty or invalid.
3.  **Correlation Maps**: Two maps generated during the sorting step to allow conversion between unsorted tile coordinates (screen space) and sorted tile coordinates (rendering order) [S1, unofficial].
4.  **Tile List**: A list of tile identifiers sorted by cost.

### Numbered Steps

1.  **Low Resolution Ray Casting (Interactive Phase)**
    *   During user interaction, perform standard low-resolution ray casting in a fragment shader.
    *   For each pixel, compute the color and store it in the RGB channels of $T_{low}$.
    *   Count the number of ray samples taken for that pixel and store this count in the Alpha channel of $T_{low}$ [S1, unofficial]. This value approximates the rendering cost for that pixel.

2.  **Tile Sorting (Post-Interaction)**
    *   Once user interaction stops, divide the viewport into square tiles.
    *   Use compute shaders to sort these tiles based on the cost hint provided by the Alpha channel of $T_{low}$ [S1, unofficial].
    *   The sorting pipeline typically involves a GPU radix sort algorithm implemented via compute shaders. It proceeds in steps such as group count, prefix sum, and scattering to reorder tiles [S1, unofficial].
    *   Generate two correlation maps during this process to map between the original screen-space tile positions and their new sorted positions [S1, unofficial].

3.  **Progressive High Resolution Ray Casting - Render Tiles**
    *   Render tiles in the sorted order (highest cost first, or as determined by the sort).
    *   For each tile, perform high-resolution ray casting.
    *   Store the resulting high-resolution color in the corresponding region of $T_{high}$.
    *   Continue rendering tiles until a fixed time budget is reached [S1, unofficial].

4.  **Progressive High Resolution Ray Casting - Composite**
    *   Composite the final image for display.
    *   For each pixel, check if its corresponding tile has been rendered in $T_{high}$.
    *   If the tile is rendered in $T_{high}$, use the high-resolution color from $T_{high}$.
    *   Otherwise, use the low-resolution color from $T_{low}$ [S1, unofficial].

5.  **Iteration**
    *   In the next frame, resume rendering tiles from step 3, continuing from where the previous frame left off in the sorted list.
    *   Repeat steps 3 and 4 until all tiles are rendered in $T_{high}$ [S1, unofficial].

### Pseudocode

```python
# Global State
T_low = create_2d_texture(width, height, format=RGBA)
T_high = create_2d_texture(width, height, format=RGBA)
tiles = [] # List of tile objects with id, x, y, width, height
sorted_tiles = [] # List of tile objects sorted by cost
correlation_map_unsorted_to_sorted = {} # Map: (x,y) -> sorted_index
correlation_map_sorted_to_unsorted = {} # Map: sorted_index -> (x,y)
time_budget_ms = 100 # Example budget
rendered_tile_indices = set() # Track which sorted indices are done

def on_interaction_start():
    global T_low
    # Reset T_high if necessary
    clear_texture(T_high)
    rendered_tile_indices.clear()

def on_interaction_active():
    # Step 1: Low Resolution Ray Casting
    render_low_res_fragment_shader(T_low)

def on_interaction_stop():
    global tiles, sorted_tiles
    # Step 2: Tile Sorting
    tiles = generate_tiles(viewport_width, viewport_height, tile_size)
    
    # Extract costs from T_low alpha channel for each tile
    tile_costs = []
    for tile in tiles:
        # Average alpha value in the tile region as cost estimate
        cost = compute_average_alpha(T_low, tile.x, tile.y, tile.width, tile.height)
        tile_costs.append((tile, cost))
    
    # Sort tiles by cost (descending or ascending depending on strategy)
    # Assuming descending cost for prioritization
    tile_costs.sort(key=lambda x: x[1], reverse=True)
    sorted_tiles = [item[0] for item in tile_costs]
    
    # Generate correlation maps
    for sorted_idx, tile in enumerate(sorted_tiles):
        correlation_map_unsorted_to_sorted[(tile.x, tile.y)] = sorted_idx
        correlation_map_sorted_to_unsorted[sorted_idx] = (tile.x, tile.y)

def on_frame_render():
    if not sorted_tiles:
        return

    # Step 3: Progressive High Resolution Ray Casting - Render Tiles
    start_time = get_current_time_ms()
    
    # Determine how many tiles can be rendered within the time budget
    # This is an approximation; in practice, you might render one by one and check time
    tiles_to_render_this_frame = []
    for sorted_idx in range(len(sorted_tiles)):
        if sorted_idx in rendered_tile_indices:
            continue
        
        tile = sorted_tiles[sorted_idx]
        
        # Estimate time for this tile or render it and measure
        # For pseudocode, assume we render one tile per iteration check
        render_high_res_tile(T_high, tile)
        rendered_tile_indices.add(sorted_idx)
        
        if get_current_time_ms() - start_time > time_budget_ms:
            break
            
    # Step 4: Progressive High Resolution Ray Casting - Composite
    composite_image(T_low, T_high)

def render_low_res_fragment_shader(T_low):
    # Standard low-res ray casting
    for y in range(T_low.height):
        for x in range(T_low.width):
            color, sample_count = low_res_ray_cast(x, y)
            T_low[x, y].rgb = color
            T_low[x, y].a = sample_count

def render_high_res_tile(T_high, tile):
    # High-res ray casting for the specific tile region
    for y in range(tile.y, tile.y + tile.height):
        for x in range(tile.x, tile.x + tile.width):
            color = high_res_ray_cast(x, y)
            T_high[x, y].rgb = color
            # Alpha can be ignored or set to 1 if fully opaque

def composite_image(T_low, T_high):
    # Create final image buffer
    final_image = create_2d_texture(viewport_width, viewport_height, format=RGBA)
    
    for y in range(viewport_width):
        for x in range(viewport_height):
            # Check if this pixel's tile has been rendered in T_high
            # We need to know which tile (x,y) belongs to
            tile_id = get_tile_id_for_pixel(x, y)
            sorted_idx = correlation_map_unsorted_to_sorted.get(tile_id)
            
            if sorted_idx is not None and sorted_idx in rendered_tile_indices:
                final_image[x, y] = T_high[x, y]
            else:
                final_image[x, y] = T_low[x, y]
    
    display(final_image)
```

### Edge Cases and Pitfalls
*   **Cost Estimation Accuracy**: The Alpha channel stores the number of ray samples. If the low-resolution sampling rate is significantly different from the high-resolution rate, the cost estimation may be inaccurate, leading to suboptimal sorting [S1, unofficial].
*   **Interaction Resumption**: If interaction resumes before all tiles are rendered, the system must handle the transition back to low-resolution mode. The sources imply that interaction stops trigger the sorting, but do not detail the reset mechanism if interaction restarts [S1, unofficial].

## Operating characteristics
*   **Time Complexity**: Sorting is $O(N \log N)$ or $O(N)$ depending on the radix sort implementation, where $N$ is the number of tiles. Rendering is proportional to the number of tiles rendered per frame.
*   **Memory Complexity**: Requires storage for $T_{low}$, $T_{high}$, and correlation maps. $T_{low}$ and $T_{high}$ are full-resolution textures.
*   **Measured Performance**: Designed for mobile and low-performance devices to achieve interactive frame rates with large models (resolutions larger than $512^3$) [S1, unofficial].
*   **Strengths**: Provides immediate visual feedback during interaction. Progressively refines the image without stalling. Efficiently uses time budgets by rendering expensive tiles first.
*   **Limitations**: Requires two passes (low-res and high-res). Sorting overhead exists. Accuracy of cost estimation depends on low-res sampling.
*   **When to use**: When interactive performance is critical on hardware with limited rendering power, and full resolution is needed eventually.
*   **When not to use**: When immediate full resolution is required, or when the cost estimation is highly unreliable.

## Background
STiles was introduced in the context of progressive ray casting for volumetric models on mobile devices. The technique was developed to address the limitations of traditional ray casting on mobile hardware, which often struggles with large datasets and interactive frame rates. The paper "Progressive Ray Casting for Volumetric Models on Mobile Devices" by [S1, unofficial] presents STiles as a solution to provide a smooth user experience by balancing interactivity and image quality.
