# Ray-guided volume rendering with missing brick reporting

Also called: Ray-guided methods

## Overview
Ray-guided volume rendering with missing brick reporting is an out-of-core rendering technique where the working set (the minimal subset of volume data required to render an image) is determined dynamically during the ray-casting process rather than in advance [S1, unofficial][S2]. It solves the problem of memory bottlenecks in large-scale volume rendering by streaming only the bricks actually accessed by rays, ensuring optimal accuracy by never loading data that will not be used [S2]. Unlike sibling methods that may estimate working sets conservatively or use fixed traversal patterns, this approach minimizes memory utilization by reporting missing bricks on the GPU for subsequent frame loading [S1, unofficial][S2].

## How it works
**Inputs and Outputs:**
*   **Input:** Ray origin $\mathbf{o}$, direction $\mathbf{d}$, volume brick hierarchy (multiple resolutions), current brick cache state, and previous frame's resume state (`rayResumeColor`, `rayResumePos`) [S2].
*   **Output:** Final accumulated color for the pixel, updated brick request list for the CPU/disk subsystem, and updated resume state for the next frame [S2].

**Data Structures:**
1.  **Brick Cache:** A 3D texture or buffer storing individual bricks of different resolutions in GPU memory in an unordered manner [S1, unofficial].
2.  **Residency Map:** A data structure storing whether each brick in the global volume is currently resident in the cache [S1, unofficial]. This is used for address translation, mapping sample locations in reference space (e.g., normalized $[0, 1]^3$) to texture coordinates within the specific brick in the cache [S1, unofficial].
3.  **Missing Brick Hash Table:** A lock-free, set-based, linearly-probed hash table stored in an image load store buffer (e.g., using `GL_ARB_shader_image_load_store`) [S2]. It records brick identifiers to coordinate disk access [S2].
4.  **Ray State:**
    *   `rayResumeColor`: Accumulated color from previous frames [S2].
    *   `rayResumePos`: The position in the volume where the first missing brick occurred, used to resume rendering [S2].
    *   `terminated`: Boolean flag indicating if a missing brick has been encountered for the current ray [S2].

**Algorithm Steps:**
1.  **Initialization:** Set `color = rayResumeColor` and `terminated = true` (assuming the ray will finish if no missing bricks are found) [S2].
2.  **Ray Loop:** Repeat until the ray exits the volume or saturates:
    a.  **Compute Level of Detail (LoD):** Determine the required LoD based on the current ray depth [S2].
    b.  **Get Brick:** Call `GetBrick(ray)` to retrieve the brick and its associated `samplingRate` [S2]. `GetBrick` always returns some data, potentially at a lower resolution than requested [S2].
    c.  **Address Translation:** Retrieve the offsets for the brick from the pool using `PoolOffsets(brick)` [S2].
    d.  **Check Resolution:** If `samplingRate` is not equal to `RequiredSamplingForLOD(LoD)`, the data is undersampled [S2].
        i.  **Report Missing:** Call `ReportMissingBrick(brick)` to add the brick to the hash table [S2].
        ii. **Record Resume Point:** If `terminated` is true (indicating this is the first missing brick encountered for this ray), set `terminated = false` and store the current ray position in `rayResumePos` [S2].
    e.  **Raycast:** Perform the raycasting step using the ray, `stepSize`, and `offsets` [S2].
3.  **Update State:** Set `rayResumeColor = color` [S2]. If the ray completed successfully (no missing bricks), set `rayResumePos = FINISHED` [S2].

**Pseudocode:**
```python
def ray_guided_rendering(ray_origin, ray_direction, volume_exit_t, ray_resume_color, ray_resume_pos):
    # Initialize ray parameter t from previous frame's resume position
    ray_t = ray_resume_pos if ray_resume_pos != "FINISHED" else 0.0
    color = ray_resume_color
    terminated = True  # Assume ray will finish unless a missing brick is found

    while ray_t < volume_exit_t:
        # 1. Compute required Level of Detail based on ray depth
        lod = compute_lod(ray_t)

        # 2. Retrieve brick and its actual sampling rate from cache
        brick_id, sampling_rate = get_brick(ray_origin, ray_direction, ray_t, lod)

        # 3. Get offsets for address translation within the cache
        offsets = pool_offsets(brick_id)

        # 4. Check if the retrieved brick matches the required LOD
        required_sampling = required_sampling_for_lod(lod)

        if sampling_rate != required_sampling:
            # Data is undersampled; report missing brick to hash table
            report_missing_brick(brick_id)

            # Record the position of the first missing brick for resumption
            if terminated:
                terminated = False
                ray_resume_pos = ray_t

        # 5. Perform the raycasting step and accumulate color
        step_size = offsets["step_size"]
        sample = sample_volume(ray_origin, ray_direction, ray_t, offsets["tex_offsets"])
        alpha = compute_alpha(sample)
        color = color + sample * (1.0 - color)  # Standard front-to-back accumulation
        ray_t += step_size

        if ray_t >= volume_exit_t or alpha >= 1.0:
            break

    # Update resume state for next frame
    ray_resume_color = color
    if terminated:
        ray_resume_pos = "FINISHED"

    return color, ray_resume_color, ray_resume_pos

# Standard operations [G]
def compute_lod(depth): return int(depth) % 4
def get_brick(o, d, t, lod): return (hash((o, d, t, lod)), 1.0 / (2 ** lod))
def pool_offsets(brick_id): return {"step_size": 0.5, "tex_offsets": (0.0, 0.0, 0.0)}
def required_sampling_for_lod(lod): return 1.0 / (2 ** lod)
def report_missing_brick(brick_id): pass  # Atomic insert into lock-free hash table
def sample_volume(o, d, t, offsets): return (0.5, 0.5, 0.5)  # GPU texture fetch
def compute_alpha(sample): return 0.8  # Transfer function evaluation
```

**Parameters:**
*   `rayResumePos`: Stores the position in the volume where the first missing brick occurred [S2].
*   `terminated`: Boolean flag indicating if a missing brick has been encountered for the current ray [S2].
*   `GL_ARB_shader_image_load_store`: OpenGL extension used for atomic operations and independent image buffers in the hash table implementation [S2].

**Edge Cases and Pitfalls:**
*   **Undersampling:** If data is undersampled, the renderer displays a coarser version initially but progressively refines regions with finer resolution data until sampled at a single voxel per pixel or the maximum data resolution [S2].
*   **Write Hazards:** The lock-free hash table must handle concurrent writes from multiple rays requesting the same brick [S2]. Linear probing with atomic operations is used to mitigate hazards [S2].
*   **Termination:** The `terminated` flag ensures that `rayResumePos` is only set once per ray per frame, at the *first* missing brick encountered [S2].

## Subtopics

### [Greedy Brick Request Strategy](2843-greedy-brick-request-strategy.md)
The Greedy Brick Request Strategy is a data-loading heuristic in ray-guided volume rendering that requests all intermediate levels of detail (LoD) along a ray's path when a higher-resolution brick is unavailable, rather than waiting for the final required resolution. Unlike the [Global strategy](2843-global-brick-request-strategy.md), which only requests the final necessary brick, the Greedy strategy floods the request hash table with intermediate bricks. This prioritizes iterative visual refinement and faster convergence of image quality over minimizing the total number of unique brick requests per frame. It produces more responsive, iteratively-refined images and may converge in fewer frames because it allows rays to sample at final resolution quickly, triggering earlier ray termination.

### Global Brick Request Strategy
The Global Brick Request Strategy is a data-loading heuristic where a ray only requests the bricks absolutely required to satisfy the final rendering request, leaving space in the hash table for other rays [S2]. When a brick is missing, it increments the LoD and looks up the brick at the new resolution, continuing until a missing brick is no longer reported [S2]. Unlike the 'Greedy' strategy, the Global strategy does not request intermediate bricks [S2]. It generates the final correct image quickest in terms of raw completion but may produce less pleasing intermediate progress [S2].

### GPU-based missing brick reporting via hash table
A subsystem for recording missing bricks identified during ray-casting on the GPU, using a lock-free hash table stored in an image load store buffer to coordinate disk access and update the volume pool [S2]. It uses the `GL_ARB_shader_image_load_store` extension (core in OpenGL 4.2) to create an image buffer independent of the current rendering buffer [S2]. It implements a set-based linearly-probed lock-free hash table using atomic load/store operations [S2]. Hashing is based on the brick identifier so that multiple rays requesting the same brick hash to the same position, keeping the table size small and avoiding duplicate values inherent in multiple render target approaches [S2].

## Operating characteristics
*   **Measured Performance:** The greedy strategy was found to converge in the fewest number of frames and produce more pleasing progress information, despite flooding the hash table, because it enables earlier ray termination [S2]. The global strategy generates the final correct image quickest in raw completion time but offers less responsive intermediate progress [S2].
*   **Strengths:** Minimizes working-set size by only streaming accessed bricks [S1, unofficial]. Ensures optimal accuracy by never loading unused data [S2]. Scales to extremely large data sets [S2].
*   **Limitations:** Requires complex GPU-side logic for missing brick reporting and hash table management [S2]. Previous approaches using conservative working-set estimates led to sub-optimal memory utilization [S1, unofficial].
*   **When to use:** Large-scale volume rendering where data exceeds GPU memory capacity and interactive or progressive refinement is desired [S1, unofficial][S2].

## Background
Ray-guided volume rendering was introduced to address the limitations of early approaches that produced conservative estimates of the working set, leading to sub-optimal memory utilization [S1, unofficial]. Key early works include [CNLE09], [HBJP12], [FSK13], and [BPH14] [S1, unofficial]. The specific technique of missing brick reporting with GPU-based hash table coordination was detailed by Crassin et al. [S2] (PMC4260263). The method builds on the principle of address translation using octrees or page-table hierarchies [S1, unofficial]. The use of `GL_ARB_shader_image_load_store` for lock-free hash tables was adopted to overcome the limitations of multiple render targets, which ignore spatial coherency and lead to duplicate values and larger texture reads back [S2].
