# Enforced Coherence
Also called: EC method

## Overview
The Enforced Coherence (EC) method is a ray traversal technique that brings coherence to secondary rays (such as reflection or refraction rays) by rearranging the ray-to-voxel mapping using sorting, enabling simultaneous intersection checks within a cell [S1]. It solves the problem of incoherent secondary rays by reordering rays to process all rays passing through a specific voxel together, allocating a CUDA block to each voxel (or multiple blocks for load balancing) and loading triangle data into shared memory [S1]. It sets itself apart from its sibling [Marching Caches](10066-marching-caches.md) by explicitly enforcing coherence through global sorting and shared-memory batch processing, whereas Marching Caches typically relies on spatial locality without explicit reordering [S1]. It is distinct from the [Independent Voxel Walk](1030-inter-ray-coherency.md) method, which traces rays independently and relies on hardware caches rather than explicit data reordering [S1].

## How it works
**Inputs:**
- Total number of rays ($N_{rays}$).
- Ray origins and directions.
- Scene geometry (triangles) organized in a grid (voxels).
- Grid resolution (e.g., $128 \times 128 \times 128$) [S1].

**Outputs:**
- For each ray, the closest intersection distance (or hit status).

**Data Structures:**
- `rayIDArr`: Array of size $N_{rays}$ storing ray identifiers.
- `tileIDArr` (or `voxelIDArr`): Array of size $N_{rays}$ storing the voxel ID that the ray passes through. Note: In the source, this array is initially allocated for $N_{rays}$ entries, but the algorithm implies a list of (ray, voxel) pairs. The source pseudocode suggests `tileIDArr` and `rayIDArr` are parallel arrays where index $i$ corresponds to a specific ray-voxel pair. The number of pairs is $N_{pairs} = \sum_{r=0}^{N_{rays}-1} (\text{voxels traversed by ray } r)$ [S1].
- `pseudoArr`: Array of size $N_{voxels}$, initialized to 0.
- `scratchArr`: Array of size $N_{voxels}$, initialized to 1.
- `oArr`: Array for compaction output.
- `validArr`: Array for compaction validity flags.
- Shared memory: Buffer for triangle data (vertices/indices) loaded from global memory.

**Parameters:**
- Sorting library: Radixsort from CUDPP is used [S1].
- CUDA block allocation: One block per voxel, or multiple blocks for voxels with high ray counts (load balancing) [S1].
- Typical scene size: Conference room scene has $\approx 10$ million (ray, voxel) pairs, assuming 10 voxels per ray [S1].

**Steps:**
1. **Voxel Enumeration:** For each ray in parallel, determine the voxels it passes through. Store (rayID, voxelID) pairs in `rayIDArr` and `tileIDArr`. The length of these arrays equals the total number of ray-voxel intersections [S1].
2. **Sorting:** Sort `tileIDArr` and `rayIDArr` using `tileIDArr` (voxel ID) as the key. This brings all rays passing through the same voxel together [S1].
3. **Boundary Detection:** Compute boundaries for segmented processing. Initialize `pseudoArr` to 0 and `scratchArr` to 1 for all voxels [S1].
4. **Segmented Scan:** Perform a segmented scan on `pseudoArr` using `scratchArr` to determine chunks/boundaries for each voxel's ray group [S1].
5. **Chunk Determination:** Use `scratchArr` and `validArr` to determine the number of blocks required. Voxels with many rays may require multiple blocks [S1].
6. **Compaction:** Compact the data to determine the exact number of blocks and valid ray ranges [S1].
7. **Intersection Processing:** For all blocks:
   - While all rays in the block are not processed:
     - Load triangles to shared memory. Threads in the CUDA block bring data of one triangle from global memory. If a voxel has more triangles than threads, triangles are brought in batches. Each batch is completely used before loading the next batch [S1].
     - Check for intersection between rays and triangles in shared memory [S1].
8. **Minimum Finding:** For all rays in parallel, get the minimum of all intersections found across all voxels processed for that ray [S1].

**Pseudocode:**
```python
# Algorithm 3. Enforced Coherence Method
# Note: Pseudocode rewritten from [S1] Algorithm 3 and text.
# N_rays: total number of rays
# N_voxels: total number of voxels in the grid

# Step 1: Determine voxels for each ray
# countArr[r] stores the number of voxels ray r passes through
countArr = [0] * N_rays
for ray in range(N_rays) in parallel:
    countArr[ray] = countVoxels(ray)

# Allocate arrays for (rayID, voxelID) pairs
# Total pairs = sum(countArr)
N_pairs = sum(countArr)
rayIDArr = allocate(N_pairs)
tileIDArr = allocate(N_pairs)

# Step 2: Dump voxels into arrays
# We need to fill rayIDArr and tileIDArr sequentially
# This requires a prefix sum or atomic operations to determine offsets
# The source pseudocode simplifies this to "DumpVoxels"
offset = 0
for ray in range(N_rays) in parallel:
    voxels = getVoxelsForRay(ray)
    for v in voxels:
        idx = atomicAdd(&offset, 1) # Or use prefix sum for deterministic order
        rayIDArr[idx] = ray
        tileIDArr[idx] = v

# Step 3: Initialize auxiliary arrays for sorting/segmentation
pseudoArr = [0] * N_voxels
scratchArr = [1] * N_voxels
oArr = allocate(N_voxels) # For compaction output

# Step 4: Sort
# Sort tileIDArr and rayIDArr based on tileIDArr (voxel ID)
# Using radixsort from CUDPP [S1]
sort(tileIDArr, rayIDArr)

# Step 5: Get Boundaries and Segmented Scan
# Determine boundaries where voxel ID changes
getBoundaries(tileIDArr, pseudoArr)
segScan(pseudoArr, scratchArr)

# Step 6: Get Chunks and Compact
# Determine valid blocks and compact data if necessary
getChunks(scratchArr, validArr)
numBlocks = compact(validArr, oArr)

# Step 7: Process Blocks
for block_id in range(numBlocks):
    # Load triangles for the voxel(s) assigned to this block
    # Load triangles to shared memory
    # Threads in the CUDA block bring data of one triangle from global memory
    # For voxels with more triangles than threads, triangles are brought in batches
    while all rays in block are not processed:
        loadTrianglesToSharedMemory()
        checkIntersection()

# Step 8: Find Minimum Intersection
# For each ray, find the minimum distance among all intersections found
minIntersections = [infinity] * N_rays
for ray in range(N_rays) in parallel:
    minIntersections[ray] = getMinimumIntersection(ray)
```

**Edge Cases and Pitfalls:**
- **Loss of Order:** Because rays are reordered by voxel, the start-to-finish ordering of each ray is lost. Rays cannot terminate early upon finding the first intersection; all intersections must be found to determine the closest one [S1].
- **Memory Intensity:** Reordering is computationally and memory intensive. The number of (rayID, voxelID) pairs can be large (e.g., 10 million for a typical conference room scene) [S1].
- **Empty Spaces:** The method performs poorly on models with large empty spaces because the number of ray-voxel pairs is large, requiring more data movement for sorting [S1].

## Operating characteristics
- **Time Complexity:** Dominated by sorting $O(N \log N)$ or $O(N)$ for radix sort, where $N$ is the number of ray-voxel pairs, and the intersection checks. The overhead of reordering (sorting, compaction) must be offset by the coherence obtained [S1].
- **Memory Complexity:** Requires storage for `rayIDArr`, `tileIDArr`, and auxiliary arrays proportional to the number of rays and voxels. The number of pairs can be very large (e.g., 10 million) [S1].
- **Measured Performance:** Achieves 8 fps on the Conference model with one light source and one reflection bounce on an Nvidia GTX480, rebuilding data structures for each stage [S1]. On GTX280 (cache-less), EC is much faster than IVW on Fairy and Happy Buddha models. On GTX480 (cached), EC is slower than IVW (14 fps for IVW vs 8 fps for EC on Conference model) [S1].
- **Strengths:** Works best on older generation GPUs with no caches, while the IVW method is slow on them [S1]. Provides high performance on GPUs with user-managed caches by exploiting shared memory [S1].
- **Limitations:** Poor performance on models with large empty spaces due to high sorting overhead. Slower than IVW on modern GPUs with rich cache architectures (GTX480) [S1].
- **When to use:** When targeting older GPUs without hardware caches or when reflection/refraction rays exhibit high coherence and the overhead of sorting is justified by the reduction in redundant intersection checks [S1].
- **When not to use:** On modern GPUs with large L1/L2 caches where IVW performs better, or on scenes with large empty spaces where the number of ray-voxel pairs is excessively large [S1].

## Background
The Enforced Coherence method was proposed in the paper "Raytracing dynamic scenes on the GPU using grids" [S1]. It is part of a broader study comparing grid-based raytracing techniques on GPUs, specifically focusing on reflection and refraction rays which typically have little coherence. The method was implemented and tested on NVIDIA 280 GTX and 480 GTX cards [S1]. The authors note that ideas presented are likely to give high performance on future GPUs and other manycore architectures [S1].
