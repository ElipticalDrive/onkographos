# Tile-Based Volume Rendering

Also called: Tiling mechanism, Tiling-based approach

## Overview
Tile-Based Volume Rendering is a rendering technique that splits the image plane into tiles of closely related pixels to limit data access and improve cache locality [S1, unofficial]. It addresses the problem of inefficient memory access patterns in stochastic volume rendering by ensuring that voxels and data accessed during the tracing of one ray are reused for other rays close to the first one [S1, unofficial]. Unlike its parent method, Marching Caches, which maintains an explicit shared cache around a ray bundle, Tile-Based Volume Rendering relies on spatial locality within fixed image tiles and sequential processing of frame estimates to prevent cache replacement [S1, unofficial].

## How it works
**Inputs and Outputs**
*   **Input:** A volumetric dataset (e.g., Engine, Manix, Macoessix), camera parameters (position, orientation), and rendering parameters (tile size, number of stochastic estimates) [S1, unofficial].
*   **Output:** A final rendered image generated by integrating multiple stochastic frame estimates [S1, unofficial].

**Data Structures**
*   **Image Plane:** Divided into square tiles. Tile dimensions are selected as powers of two (e.g., $2 \times 2$, $4 \times 4$, ..., $256 \times 256$) to ease division [S1, unofficial].
*   **Tile Buffer:** A temporary storage area holding all frame estimates for a specific tile before integration into the final image [S1, unofficial].

**Parameters**
*   **Tile Size:** The dimensions of the tiles in pixels. Tested sizes include $2, 4, 8, 16, 32, 64, 128, 256$ for serial execution and $64, 128, 256, 512$ for parallel execution [S1, unofficial].
*   **Number of Estimates:** The number of stochastic samples rendered per image. Typically set to 20 [S1, unofficial].

**Algorithm Steps**
1.  **Tile Division:** Split the image plane into non-overlapping square tiles of size $T \times T$ pixels [S1, unofficial].
2.  **Sequential Tile Processing:** Iterate through each tile in the image plane [S1, unofficial].
3.  **Stochastic Estimation:** For the current tile, generate $N$ stochastic frame estimates (where $N=20$) [S1, unofficial].
    *   Cast rays through each pixel in the tile.
    *   Trace rays through the volume, accumulating color and opacity.
    *   Store the resulting frame estimate for the tile [S1, unofficial].
4.  **Integration:** Collect all $N$ frame estimates for the current tile. Integrate them into the final image buffer by performing a cumulative moving average [S1, unofficial].
    *   Let $I_{final}$ be the final image buffer and $I_{tile}^{(k)}$ be the $k$-th frame estimate for the tile.
    *   Update the tile region in $I_{final}$ using the average of the estimates [S1, unofficial].
5.  **Repeat:** Proceed to the next tile until all tiles are processed [S1, unofficial].

**Pseudocode**
```python
def tile_based_volume_rendering(volume, camera, tile_size, num_estimates):
    # Initialize final image buffer with zeros
    final_image = create_zero_image(camera.width, camera.height)
    
    # Determine tile grid dimensions
    tiles_x = ceil(camera.width / tile_size)
    tiles_y = ceil(camera.height / tile_size)
    
    for ty in range(tiles_y):
        for tx in range(tiles_x):
            # Define tile boundaries
            x_start = tx * tile_size
            y_start = ty * tile_size
            x_end = min(x_start + tile_size, camera.width)
            y_end = min(y_start + tile_size, camera.height)
            
            # Initialize accumulator for this tile
            tile_accumulator = create_zero_image(x_end - x_start, y_end - y_start)
            
            # Generate and integrate stochastic estimates
            for k in range(num_estimates):
                # Generate a new stochastic frame estimate for the tile
                # This involves casting rays for each pixel in the tile range
                frame_estimate = render_tile_stochastic(volume, camera, x_start, y_start, x_end, y_end)
                
                # Accumulate the estimate
                tile_accumulator += frame_estimate
            
            # Compute the average for the tile
            tile_average = tile_accumulator / num_estimates
            
            # Write the averaged tile result to the final image
            final_image[y_start:y_end, x_start:x_end] = tile_average
            
    return final_image
```

**Edge Cases and Pitfalls**
*   **Parallelization Contention:** When using Intel TBB for parallelization, tiling can increase render time compared to a non-tiling baseline [S1, unofficial]. Smaller tiles cause higher inter-thread cache contention because multiple threads access shared data [S1, unofficial]. Larger tiles reduce this likelihood [S1, unofficial].
*   **Boundary Conditions:** Tile sizes must be powers of two to ensure clean division of the image plane, though the last tiles may be smaller if the image dimensions are not multiples of the tile size [S1, unofficial].

## Operating characteristics
**Time and Memory Complexity**
*   **Time Complexity:** The method reduces render time in serial execution by improving cache locality. The magnitude of benefit depends on tile size and dataset scale [S1, unofficial].
*   **Memory Complexity:** Requires storage for the final image and temporary buffers for tile estimates. The cache footprint is limited to the data accessed by rays within a single tile [S1, unofficial].

**Measured Performance**
Performance was measured on three datasets: Engine ($128 \times 128 \times 64$), Manix ($256 \times 230 \times 256$), and Macoessix ($512 \times 461 \times 512$) [S1, unofficial]. Ten renderings were performed per test; the first five were warm-ups, and the average of the latter five was used for measurement [S1, unofficial]. I/O times were excluded [S1, unofficial].

*   **Serial Phase:**
    *   **Engine (Close):** Best reduction 3.61% with $2 \times 2$ tile (42.47s vs 44.06s full) [S1, unofficial].
    *   **Engine (Far):** Best reduction 10.96% with $2 \times 2$ tile (13.16s vs 14.78s full) [S1, unofficial].
    *   **Manix (Close):** Best reduction 20.40% with $2 \times 2$ tile (101.51s vs 127.52s full) [S1, unofficial].
    *   **Manix (Far):** Best reduction 7.4% with $4 \times 4$ tile (33.02s vs 35.66s full). This is an exception to the $2 \times 2$ trend [S1, unofficial].
    *   **Macoessix (Close):** Best reduction 22.81% with $2 \times 2$ tile (223.58s vs 289.65s full) [S1, unofficial].
    *   **Macoessix (Far):** Best reduction 14.33% with $2 \times 2$ tile (46.38s vs 54.14s full) [S1, unofficial].
    *   In serial mode, smaller tile sizes (e.g., $2 \times 2$) generally reduce render time by increasing cache locality [S1, unofficial].

*   **Parallel Phase (Intel TBB):**
    *   Tiling with TBB increases render time compared to the non-tiling baseline [S1, unofficial].
    *   Smaller tiles cause higher inter-thread cache contention [S1, unofficial].
    *   Larger tiles reduce contention but overall performance is worse than the non-tiling baseline [S1, unofficial].

**Strengths and Limitations**
*   **Strengths:** Significant reduction in rendering runtime for serial execution, especially for larger datasets (e.g., Macoessix) [S1, unofficial]. Effective at limiting data access and improving cache locality [S1, unofficial].
*   **Limitations:** Poor performance in parallel environments using Intel TBB due to cache contention [S1, unofficial]. Not suitable for scenarios requiring high parallel efficiency without careful tile size tuning [S1, unofficial].

## Background
Tile-Based Volume Rendering was proposed in a thesis titled "A Tile-Based Approach for Photo-Realistic Volume Rendering" [S1, unofficial]. The work focuses on optimizing stochastic volume rendering by exploiting inter-ray coherence through spatial tiling [S1, unofficial]. It is used in contexts where serial execution is dominant or where cache locality is more critical than parallel throughput [S1, unofficial].
