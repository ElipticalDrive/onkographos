# Intra-ray Parallelism

Also called: GPU-acceleration through intra-ray parallelism

## Overview
Intra-ray parallelism is a rendering acceleration scheme that partitions each ray into depth bins to enable efficient parallel accumulation of primitive contributions during rendering [S1, unofficial]. It differs from standard ray marching by decoupling the spatial traversal (handled via tile-based culling and sorting) from the depth-wise integration (handled via bin-parallel blending), allowing GPU threads to process multiple depth segments of a single ray simultaneously [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** Image dimensions $w, h$; number of depth bins $b$; set of ellipsoid primitives $E$ (defined by mean $\mu$ and covariance $\Sigma$); transfer function $TF$; camera view configuration $View$.
*   **Outputs:** Rendered image $I$.

**Data Structures:**
*   **Tiles ($T$):** 3D grid cells defined by image width, height, and bin count. Each tile $t$ has a 3D key and a range $R[t]$ of primitives.
*   **Lists ($L, K$):** $L$ contains duplicated visible ellipsoids; $K$ contains their corresponding 3D keys relative to tiles.
*   **Per-bin Canvas ($I_{bin}$):** A 3D buffer of size $w \times h \times b$, initialized to 0, storing partial ray results for each bin.

**Steps:**
1.  **Tile Creation:** Create tiles $T$ from $w, h, b$. Tiles include depth-wise subdivisions [S1, unofficial].
2.  **Culling:** Cull ellipsoids $E$ based on $View$ to produce visible set $E_{visible}$ [S1, unofficial].
3.  **Key Generation:** Duplicate $E_{visible}$ with 3D keys relative to $T$ to produce lists $L$ and $K$ [S1, unofficial].
4.  **Sorting:** Sort $K$ and $L$ by tile keys. No intra-tile depth sorting is performed [S1, unofficial].
5.  **Range Identification:** Identify ranges $R$ for each tile $t$, defining the range of primitives assigned to that 3D tile [S1, unofficial].
6.  **Initialization:** Initialize per-bin canvas $I_{bin}$ to 0 [S1, unofficial].
7.  **Tile Processing:** Loop over all tiles $t \in T$:
    *   Extract primitives $E_t$ assigned to tile $t$ from $L$ using range $R[t]$ [S1, unofficial].
    *   For all pixels $i$ in $t$:
        *   Compute ray $ray[i, t_z]$ for the current bin $t_z$ [S1, unofficial].
        *   Sample intensity from $E_t$ using $ray[i, t_z]$ and $TF$ [S1, unofficial].
        *   Blend the partial ray result into the per-bin canvas: $I_{bin}[i, t_z] \leftarrow \text{BlendPartialRay}(ray[i, t_z])$ [S1, unofficial].
8.  **Tile Reset:** Reset tile grid $z=1$ by creating new tiles $T$ with bin count 1: $T \leftarrow \text{CreateTiles}(w, h, 1)$ [S1, unofficial].
9.  **Merging:** Loop over all pixels $i$ in image $I$: Merge Z-bins by blending across $b$ bins: $I[i] \leftarrow \text{MergeZBins}(I_{bin}[i, 0:b])$ [S1, unofficial].

**Pseudocode:**
```python
function RENDER(w, h, b, E, TF, View):
    # 1. Tile Creation
    T = CreateTiles(w, h, b)
    
    # 2. Culling
    E_visible = CullEllipsoid(E, View)
    
    # 3. Key Generation
    L, K = DuplicateWithKeys3D(E_visible, T)
    
    # 4. Sorting
    SortByTileKeys(K, L)
    
    # 5. Range Identification
    R = IdentifyTileRanges(K)
    
    # 6. Initialization
    I_bin = InitializeZero(w, h, b)
    
    # 7. Tile Processing
    for t in T:
        # Extract primitives for this tile
        E_t = L[R[t].start : R[t].end]
        
        for i in t.pixels:
            # Compute ray for current bin z
            ray = IntensitySample(i, E_t, TF)
            
            # Blend partial result into bin canvas
            I_bin[i, t.z] = BlendPartialRay(ray)
            
    # 8. Tile Reset (Preparation for merge if needed, or logical step)
    # Note: The source describes resetting tiles with bin count 1.
    # This step likely prepares for the final merge or indicates a 
    # reduction phase structure.
    T_final = CreateTiles(w, h, 1)
    
    # 9. Merging
    I = InitializeZero(w, h)
    for i in range(w * h):
        I[i] = MergeZBins(I_bin[i, 0:b])
        
    return I
```

**Parameters:**
*   $w, h$: Width and height of the image to rasterize [S1, unofficial].
*   $b$: Number of depth bins [S1, unofficial].
*   $TF$: Transfer function to map intensity to color and opacity [S1, unofficial].
*   $View$: View configuration of the current camera [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** Blending operations across bins must handle floating-point precision carefully to avoid artifacts during the final merge [S1, unofficial].
*   **Boundaries:** Tile boundaries must be calculated precisely to ensure no primitive is missed or double-counted [S1, unofficial].
*   **Degenerate Input:** Empty scenes or fully occluded rays should be handled by the culling step to avoid unnecessary computation [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Depends on the number of primitives $N$, image resolution $W \times H$, and bins $B$. Sorting takes $O(N \log N)$. Processing takes $O(N \cdot B)$ or $O(W \cdot H \cdot B)$ depending on implementation density.
*   **Memory Complexity:** $O(W \cdot H \cdot B)$ for the per-bin canvas $I_{bin}$ [S1, unofficial].
*   **Strengths:** Efficient parallel accumulation on GPUs; reduces redundant ray-primitive intersection tests by leveraging tile-based culling [S1, unofficial].
*   **Limitations:** Memory usage scales with bin count $B$; requires careful management of tile ranges and sorting [S1, unofficial].
*   **When to Use:** Suitable for GPU-based rendering of sparse volume data represented by ellipsoids or similar primitives [S1, unofficial].

## Background
Intra-ray parallelism was introduced in the context of 3D Ellipsoid-based Sparse Volume Rendering (ESVR) [S1, unofficial]. It addresses the inefficiency of sequential ray marching by parallelizing the integration step across depth bins [S1, unofficial].
