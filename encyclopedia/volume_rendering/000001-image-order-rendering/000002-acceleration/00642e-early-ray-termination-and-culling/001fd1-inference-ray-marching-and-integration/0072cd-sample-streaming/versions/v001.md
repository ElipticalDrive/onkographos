# Sample Streaming

Also called: Batched Ray Marching, Streaming Renderer

## Overview
Sample Streaming is a rendering execution model that decomposes the volume rendering algorithm into smaller, distinct kernels (ray generation, coordinate computation, and shading) to align with the batch inference execution model of machine learning frameworks [S1]. It reduces control flow divergence and hides high-latency memory accesses by processing rays in batches, where sample coordinates are streamed out for network inference before shading values are retrieved [S1]. Unlike traditional ray marching which computes samples sequentially per ray, this method processes a fixed number of samples $K$ across all active rays simultaneously, optimizing for GPU throughput in neural rendering contexts [S1].

## How it works
The method splits the rendering loop into three primary kernels: ray generation, coordinate computation, and shading. It operates on a batch of rays, managing their validity state to prune inactive rays over time.

**Inputs and Outputs:**
*   **Input:** A batch of $N$ rays, each with state (origin, direction, throughput, status).
*   **Output:** Accumulated pixel color for the frame.
*   **Parameters:** $K$, the number of sample coordinates generated per iteration per ray.

**Data Structures:**
*   **Ray State:** Stored in global memory. Includes ray origin, direction, current position, throughput, and a validity flag.
*   **Sample Buffer:** A buffer of size $N \times K$ storing the next $K$ sample coordinates for each ray.
*   **Inference Output:** A buffer storing the inferred density and color values corresponding to the sample coordinates.

**Numbered Steps:**
1.  **Ray Generation:** Initialize primary rays. Intersect them with the volume bounding box. If no intersection is found, invalidate the ray.
2.  **Stream Compaction:** Remove invalid rays from the active batch to reduce kernel launch overhead in subsequent iterations [S1].
3.  **Coordinate Computation (Loop):**
    a. For each active ray, compute the next $K$ sample coordinates along the ray direction.
    b. Stream these $N \times K$ coordinates out to the inference engine.
    c. Wait for the inference engine to return density and color values for these coordinates.
4.  **Shading:**
    a. Load the ray state and the inferred sample values.
    b. Perform volume integration (e.g., standard volume rendering integral) using the samples.
    c. Update ray throughput and position.
    d. Apply Russian Roulette for termination if necessary.
5.  **Termination Check:** If all rays are invalid (either by exiting the volume or termination), terminate the loop. Otherwise, return to Step 3.

**Formulas:**
The volume rendering integral is approximated using the sampled values. For a ray $r$, the color $C(r)$ is:
$$ C(r) = \sum_{i=1}^{M} T_i \alpha_i c_i $$
where $T_i = \exp\left(-\sum_{j=1}^{i-1} \sigma_j \Delta_j\right)$ is the transmittance, $\alpha_i = 1 - \exp(-\sigma_i \Delta_i)$ is the opacity, $\sigma_i$ is the density, $\Delta_i$ is the step size, and $c_i$ is the emitted color at sample $i$. In Sample Streaming, these samples are computed in batches of $K$.

**Pseudocode:**
The following pseudocode illustrates the kernel structure. Note that `stream_compact` and `inference` are external operations handled by the framework.

```python
def streaming_renderer(params, n_rays):
    # Initialize rays
    rays = initialize_rays(params)
    
    while True:
        # 1. Ray Generation / Intersection (only in first iteration or for new rays)
        # In subsequent iterations, rays are advanced in the shade kernel
        
        # 2. Stream Compaction: Remove invalid rays
        active_count, active_rays = stream_compact(rays)
        
        if active_count == 0:
            break
            
        # 3. Coordinate Computation
        # Generate K samples for each active ray
        # This step is often offloaded or batched for neural inference
        sample_coords = compute_next_k_samples(active_rays, K)
        
        # Stream out for inference
        # The inference engine returns density and color for all samples
        inferred_values = inference_engine(sample_coords)
        
        # 4. Shading
        # Load rays and inferred values
        # Perform integration and update ray state
        updated_rays = []
        for i in range(active_count):
            ray = active_rays[i]
            # Retrieve K values for this ray
            ray_samples = inferred_values[i * K : (i + 1) * K]
            
            # Integrate samples
            ray, valid = shade_and_advance(ray, ray_samples)
            
            if valid:
                updated_rays.append(ray)
            else:
                accumulate_pixel_color(params, ray)
                
        rays = updated_rays

def raygen_kernel(params, n_rays):
    """
    Initializes primary rays and intersects with volume.
    """
    for i in range(n_rays):
        ray = initialize_ray(params, i)
        valid = intersect_volume(ray)
        if valid:
            save_ray(params, ray)
        else:
            accumulate_pixel_color(params, ray)

def shade_kernel(params, n_rays):
    """
    Loads rays, performs shading with pre-computed samples, and advances.
    """
    for i in range(n_rays):
        ray = load_ray(params, i)
        # shade function uses samples already retrieved via inference
        valid = shade(params, ray) and sample(ray)
        if valid:
            save_ray(params, ray)
        else:
            accumulate_pixel_color(params, ray)
```

**Parameters:**
*   $K$: The number of samples generated by each iteration. Tuning results suggest optimal performance when $K$ is around 8 [S1].

**Edge Cases and Pitfalls:**
*   **Large $K$:** If $K$ is too large, more samples are computed than necessary because many rays exit the volume earlier. These unused samples must be discarded, wasting computation time [S1].
*   **Small $K$:** If $K$ is too small, the overhead of kernel launches and data transfers between the renderer and inference engine may dominate execution time [S1].
*   **Memory Access:** High-latency memory accesses are hidden by the batch processing, but insufficient batch size ($K$) may fail to hide this latency effectively [S1].

## Operating characteristics
*   **Time Complexity:** The number of iterations is reduced by a factor of $K$ compared to single-sample marching, reducing CUDA kernel launch overheads [S1]. However, the total number of samples computed may exceed the minimum required due to the batch nature, potentially increasing total compute time if $K$ is poorly tuned [S1].
*   **Memory Complexity:** Requires storage for $N \times K$ sample coordinates and their corresponding inference outputs. The active ray buffer size decreases over time due to stream compaction [S1].
*   **Strengths:** Effectively hides high-latency memory accesses by providing enough data for the processor to work on while waiting for memory requests [S1]. Reduces control flow divergence by processing rays in batches. Compatible with neural network inference engines [S1].
*   **Limitations:** Increases algorithm complexity. Currently only applies to ray marching algorithms, not path tracing with distance sampling (though the paper mentions incorporating path tracing, the sample streaming optimization is explicitly linked to ray marching in the text) [S1]. Requires tuning of $K$ for optimal performance [S1].
*   **When to Use:** Real-time volume rendering with neural networks where inference latency is significant and can be overlapped with computation.
*   **When Not to Use:** Scenes with highly variable ray lengths where $K$ cannot be tuned effectively, or when memory bandwidth is the primary bottleneck and batch overhead is too high.

## Background
Sample Streaming, also referred to as Batched Ray Marching, was introduced in the context of interactive volume visualization using multi-resolution hash encoding [S1]. It adapts the spirit of wavefront path tracers to the constraints of neural volume rendering, where densities are unknown in advance and expensive to compute [S1]. The method was developed to leverage the batch inference execution model of modern machine learning frameworks, addressing the challenge of high-latency memory accesses and control flow divergence in GPU-based volume rendering [S1].
