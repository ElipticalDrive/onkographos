# Object Space Ray Tracing for Remote Volume Rendering

Also called: Object space ray tracing phase, Ray tracing technique rendering object space samples as spheres

## Overview
This method replaces the 2.5D point rasterization phase of the original Zellmann et al. remote volume rendering algorithm with an object space ray tracing phase to eliminate rendering artifacts in volumetric and transparent regions [S1, unofficial]. It sets itself apart from its sibling [Inference Ray Compositing](3790-inference-ray-computing.md) by deferring the final pixel color computation to a client-side ray tracer that treats transmitted samples as geometric spheres, rather than compositing them as fixed-size sprites or warping a pre-rendered image [S1, unofficial].

## How it works
**Inputs:**
*   Server-side volume rendering output: A set of object space samples, each containing position and radius data.
*   Network connection: Used to transmit compacted samples to the client.

**Outputs:**
*   Client-side rendered image: A 2D image generated by ray tracing the received object space samples.

**Data Structures:**
*   **Object Space Sample:** A structure containing position and radius.
    *   Size: 64 bits per sample.
    *   Layout: The source does not specify the exact bit-packing layout of the position and radius fields within the 64 bits [S1, unofficial].
*   **Color Data:** Transmitted alongside samples.
    *   Size: 32 bits per color value [S1, unofficial].

**Steps:**
1.  **Server-Side Rendering:** Perform volume rendering to generate object space samples. Each sample represents a point in the volume with associated position and radius [S1, unofficial].
2.  **Server-Side Compaction:** Compact the generated object space samples to reduce data size before transmission. The source notes that the current implementation uses a serial algorithm, but suggests using `remove_if` from the C++/GPGPU library Thrust for improvement [S1, unofficial].
3.  **Transmission:** Transmit the compacted object space samples and color data to the client over the network. The example configuration sends 32 bits per color and 64 bits per object space sample [S1, unofficial].
4.  **Client-Side Ray Tracing:** Use a software ray tracing implementation (based on NVIDIA CUDA) to render the received samples [S1, unofficial].
5.  **Sphere Rendering:** Render the object space samples as spheres (object space splats) instead of OpenGL points with fixed pixel size. This ensures correct depth compositing per fragment and avoids opacity bias associated with fillrate [S1, unofficial].

**Pseudocode:**
```python
# Server Side
def server_render_and_transmit(volume_data, camera_params):
    # 1. Generate object space samples
    # Each sample has position (3D) and radius (1D)
    samples = volume_render_to_object_space_samples(volume_data, camera_params)
    
    # 2. Compact samples (e.g., remove empty or low-opacity samples)
    # Using a serial implementation as per source, or Thrust's remove_if
    compacted_samples = compact_samples(samples)
    
    # 3. Transmit to client
    # 32 bits per color, 64 bits per sample (position + radius)
    send_to_client(compacted_samples)

# Client Side
def client_render(samples):
    # 4. Initialize software ray tracer (CUDA-based)
    ray_tracer = CUDA_RayTracer()
    
    # 5. Render samples as spheres
    # For each pixel, trace rays through the object space samples
    # Samples are treated as spheres, not fixed-size points
    image = ray_tracer.render_spheres(samples)
    
    return image
```

**Parameters:**
*   **Color Precision:** 32 bits per color value [S1, unofficial].
*   **Sample Precision:** 64 bits per object space sample (position and radius) [S1, unofficial].
*   **Resolution:** Example images are 1024 × 1024 pixels [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **OpenGL Point Rasterization Artifacts:** Using OpenGL point rasterization causes artifacts in volumetric/transparent regions because depth compositing is per-vertex, not per-fragment. Variable point sizes bias results as opacity increases with fillrate [S1, unofficial].
*   **Compaction Performance:** The overall pipeline is currently bound by compaction performance on the server side [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The overall pipeline is currently bound by compaction performance on the server side [S1, unofficial].
*   **Memory Complexity:** Depends on the number of compacted samples. For 1024 × 1024 pixel images, compaction results in 623,584 individual object space samples [S1, unofficial].
*   **Measured Performance:** Measured on an NVIDIA RTX 2080 GPU [S1, unofficial]. The source does not provide specific frame rates but notes that rendering performance is "very high" even without RT Cores [S1, unofficial].
*   **Strengths:** Significantly improves visual quality in volumetric and transparent regions compared to OpenGL point rasterization, even with slight camera movement [S1, unofficial].
*   **Limitations:** Bound by server-side compaction performance. Network bandwidth and latency are not reported as they depend on the individual connection [S1, unofficial].
*   **When to Use:** When high visual quality in transparent/volumetric regions is critical and the client has a capable GPU for software ray tracing.
*   **When Not to Use:** When server-side compaction is too slow or network bandwidth is extremely limited.

## Background
This technique is an extension of the algorithm by Zellmann et al. [ZAL12] titled 'Image-Based Remote Real-Time Volume Rendering - Decoupling Rendering from View Point Updates' (2012) [S1, unofficial]. It was proposed to address the rendering artifacts inherent in the original method's use of 2.5D point rendering. The implementation uses NVIDIA CUDA for ray tracing and C++ Boost Asio for network communication [S1, unofficial].
