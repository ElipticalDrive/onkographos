# Mixed-Resolution Multi-Volume Rendering
Also called: Per-channel resolution selection

## Overview
Mixed-resolution multi-volume rendering is a technique where different channels of a multi-volume dataset are rendered at different spatial resolution levels to save memory and reduce sample evaluation costs [S1, unofficial][S2]. It addresses the inefficiency of rendering all channels at the highest resolution when some channels have lower frequency content or lower visual importance [S1, unofficial][S2]. It is distinct from sibling methods like Level-of-detail (LOD) methods, which typically adjust resolution based on distance for the entire volume, and Dynamic Volume Resolution & Alpha Mask Update, which adjusts resolution based on occupancy or alpha thresholds [1007-level-of-detail-lod-methods.md][2539-dynamic-volume-resolution-alpha-mask-update.md].

## How it works
**Inputs and Outputs:**
*   **Input:** A multi-volume dataset with $N$ channels, where each channel $i$ has a multi-resolution hierarchy (e.g., a brick hierarchy or octree) with resolution levels $l_0$ (highest) to $l_{max}$ (lowest). Viewing parameters (camera position, ray direction).
*   **Output:** A rendered image where each pixel's color is computed by integrating contributions from all channels, sampled at their respective selected resolution levels.

**Data Structures:**
*   **Channel Resolution Constraint Function:** For each channel $i$, a function $f_i(\mathbf{p}, \mathbf{v}, \dots)$ that returns a valid resolution level $l_i \in [l_{min}, l_{max}]$. The inputs $\mathbf{p}$ (position), $\mathbf{v}$ (viewing parameters), and potentially frequency content or transfer function properties [S1, unofficial][S2].
*   **Multi-resolution Hierarchy:** Each channel's data is stored in a hierarchy of resolution levels. Level $l_0$ is the finest, and higher $l$ values represent coarser resolutions [S1, unofficial][S2].

**Steps:**
1.  **Initialize Ray:** For each pixel, cast a ray into the volume.
2.  **Determine Resolution per Channel:** For each channel $i$, evaluate the constraint function $f_i$ using the current ray sample position and viewing parameters to determine the resolution level $l_i$ to use for that channel [S1, unofficial][S2].
    *   *Note:* The function can be user-defined, based on distance to camera, frequency content, or transfer function importance [S1, unofficial][S2].
3.  **Sample Data:** For each channel $i$, sample the volume data at the determined resolution level $l_i$. This may involve different step sizes along the ray for different channels, or simply accessing coarser data structures [S1, unofficial][S2].
    *   *Pitfall:* A channel with high-frequency content may require a higher sampling rate (lower $l$), while another may only need sampling at every second step (higher $l$) [S1, unofficial][S2].
4.  **Integrate:** Compute the volume rendering integral for each channel using the sampled data at their respective resolutions. Combine the contributions from all channels to form the final pixel color [S1, unofficial][S2].
5.  **Memory Management:** Limit the range of resolutions uploaded to the GPU on a per-channel basis to save memory [S1, unofficial][S2].

**Pseudocode:**
```python
def render_mixed_resolution_multi_volume(ray, channels, camera):
    """
    ray: Ray object with origin and direction
    channels: List of Channel objects, each with a multi-resolution hierarchy and a resolution constraint function
    camera: Camera object with position and view parameters
    """
    final_color = [0.0, 0.0, 0.0, 0.0]
    
    # Initialize ray marching parameters
    t = ray.origin
    dt = initial_step_size # Not given in sources, typically based on bounding box or highest resolution
    
    while t is within volume bounds:
        # Determine resolution for each channel at current position
        channel_resolutions = []
        for channel in channels:
            # Evaluate constraint function based on position, camera, etc.
            # f_i can consider distance to camera, frequency content, transfer function
            l_i = channel.constraint_function(t, camera)
            channel_resolutions.append(l_i)
        
        # Sample and integrate each channel at its selected resolution
        for i, channel in enumerate(channels):
            l_i = channel_resolutions[i]
            
            # Sample data at resolution level l_i
            # This may involve accessing a coarser brick or octree node
            # The step size for this channel might be adjusted based on l_i
            # If l_i is coarse, we might sample less frequently or use larger steps
            # However, the core idea is accessing the data at the correct resolution
            
            # Get density and color at current t for channel i at resolution l_i
            # This function handles the specific data structure lookup for level l_i
            density, color = channel.sample_at(t, l_i)
            
            # Accumulate contribution to final color
            # Standard volume rendering accumulation
            alpha = 1.0 - exp(-density * dt)
            final_color = final_color + color * alpha * (1.0 - final_color[3])
            final_color[3] = final_color[3] + alpha * (1.0 - final_color[3])
            
        # Advance ray
        # Note: Step size dt might be adjusted per channel, but for simplicity,
        # we assume a common step size or that the sampling function handles internal stepping
        # In practice, if channels have different resolutions, the effective step size
        # for data access might differ, but the ray position t advances uniformly
        t = t + ray.direction * dt
        
    return final_color
```

**Parameters:**
*   **Resolution Levels:** Discrete levels $l_0, \dots, l_{max}$. $l_0$ is highest resolution [S1, unofficial][S2].
*   **Constraint Function Inputs:** Distance to camera, frequency content, transfer function properties [S1, unofficial][S2].

**Edge Cases and Pitfalls:**
*   **Frequency Mismatch:** A channel with high-frequency content may require a higher sampling rate, while another may only need sampling at every second step [S1, unofficial][S2].
*   **Memory Management:** Limiting the range of resolutions uploaded to the GPU is crucial for out-of-core rendering [S1, unofficial][S2].

## Operating characteristics
*   **Time Complexity:** Depends on the number of channels and the selected resolution levels. Rendering at lower resolutions for some channels reduces the number of samples evaluated [S1, unofficial][S2].
*   **Memory Complexity:** Reduces memory usage by limiting the range of resolutions uploaded to the GPU on a per-channel basis [S1, unofficial][S2].
*   **Strengths:** Saves memory and reduces computational cost for multi-volume datasets where channels have varying importance or frequency content [S1, unofficial][S2].
*   **Limitations:** Requires a multi-resolution hierarchy for each channel and a mechanism to determine the appropriate resolution level per channel [S1, unofficial][S2].
*   **When to Use:** Large-scale multi-volume data where some channels have lower frequency content or are less important for the user [S1, unofficial][S2].

## Background
Mixed-resolution multi-volume rendering was introduced in the context of scalable web-based volume rendering of large biomedicine datasets [S1, unofficial][S2]. It is part of a system that uses out-of-core methods and multi-resolution hierarchies (e.g., OME-Zarr files) to handle large data volumes [S2]. The technique allows for flexible resolution selection per channel based on viewing parameters and data characteristics [S1, unofficial][S2].
