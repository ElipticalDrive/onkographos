# Frustum-based LOD Selection

Also called: Auto Level of Detail (LOD), Distance-based LOD, Frustum Face Distance LOD, Multi-resolution volumes (LOD), Simple LOD

## Overview
Frustum-based LOD Selection is a technique that determines the appropriate resolution level for a volume entity based on the distance from the camera to the frustum faces, ensuring voxel sizes remain smaller than a screen pixel [S1, unofficial]. It selects resolution based on ray distance from the viewer, using lower LODs for distant or peripheral rays to minimize samples [S2]. This distance-driven approach suits large-scale datasets, cutting memory and sample requirements significantly while maintaining perceptual quality [S2].

## How it works
**Inputs and Outputs:**
*   **Inputs:** Camera position, camera view/projection matrices (or MVP), volume transform (position, scale), volume data structure (hierarchical MIP-map pyramid), screen width, depth thresholds.
*   **Outputs:** Selected LOD index (integer).

**Data Structures:**
*   **Volume Data:** Hierarchical representation such as an octree-based voxel MIP-map pyramid where each level reduces resolution [S2].
*   **Depth Thresholds:** An array of floats calculated as $1.0f / 2^{depth}$ for depths 1 to `maxSvoDepth_` [S1, unofficial].

**Steps:**
1.  **Calculate Camera-to-Entity Distance:** Compute the Euclidean distance between the camera position and the transformed voxel position (or entity center) [S1, S3, unofficial].
    $$ d = \| \text{camera\_position} - (\text{model} \cdot [\text{voxel\_position}, 1]) \| $$
2.  **Determine Frustum Face Positions (Optional/Advanced):** To account for perspective, transform Normalized Device Coordinate (NDC) points to view space to define frustum boundaries [S1, unofficial].
    *   Define NDC points, e.g., $A = (-1, 0, 0, 1)$ and $B = (1, 0, 0, 1)$ [S1, unofficial].
    *   Transform to view space: $V_A = M^{-1} A$, $V_B = M^{-1} B$ [S1, unofficial].
    *   Calculate left and right frustum face positions in world space using the camera position and the distance $d$ [S1, unofficial].
3.  **Calculate Projected Size:** Calculate the distance between frustum faces normalized by screen width to determine the projected scale [S1, unofficial].
    $$ \text{distance} = \frac{\| \text{leftFrustumFacePos} - \text{rightFrustumFacePos} \|}{\text{screenWidth}} $$
4.  **Select LOD:** Iterate through the depth thresholds. If the calculated distance exceeds a threshold scaled by the entity's scale, select the corresponding LOD level [S1, unofficial].
    *   Simple heuristic: If $d > 0.5$, return LOD 2; otherwise, return LOD 1 [S3, unofficial].
    *   General heuristic: For $i$ from 0 to `depthThresholds_.size()`:
        *   $depth = i + 1$
        *   If $d > \text{depthThresholds\_}[i] \times \text{scale}$, set LOD to $depth$ and break [S1, unofficial].

**Pseudocode:**
```python
def select_lod(camera_pos, entity_pos, entity_scale, depth_thresholds, screen_width, mvp_matrix):
    """
    Selects LOD based on camera-to-entity distance and frustum geometry.
    """
    # Step 1: Calculate distance
    # Note: entity_pos should be transformed by model matrix if not already in world space
    distance = glm_distance(camera_pos, entity_pos)
    
    # Step 2: Advanced Frustum Calculation (Optional for perspective accuracy)
    # Define NDC points for left and right edges
    point_a = vec4(-1.0, 0.0, 0.0, 1.0)
    point_b = vec4(1.0, 0.0, 0.0, 1.0)
    
    # Transform to view space
    inv_mvp = inverse(mvp_matrix)
    view_vec_a = inv_mvp * point_a
    view_vec_b = inv_mvp * point_b
    
    # Calculate frustum face positions in world space
    # Note: view_vec_a/b are homogeneous; extract direction or use as vectors scaled by distance
    # Assuming view_vec_a/b are normalized directions or need scaling
    left_frustum_pos = camera_pos + (view_vec_a.xyz / view_vec_a.w) * distance
    right_frustum_pos = camera_pos + (view_vec_b.xyz / view_vec_b.w) * distance
    
    # Calculate normalized distance between frustum faces
    frustum_distance = glm_distance(left_frustum_pos, right_frustum_pos) / screen_width
    
    # Step 3: Select LOD based on thresholds
    # Using the distance from camera to entity as the primary driver [S1, S3, unofficial]
    for i in range(len(depth_thresholds)):
        depth = i + 1
        threshold = depth_thresholds[i] * entity_scale
        if distance > threshold:
            return depth
            
    return 0 # Default LOD
```

**Parameters:**
*   `depthThresholds_`: Array of float thresholds, typically $1.0f / 2^{depth}$ [S1, unofficial].
*   `lod`: Uniform variable controlling the selected LOD state [S3, unofficial].
*   `camera_position`: World-space position of the camera [S3, unofficial].
*   `screenWidth`: Resolution width of the viewport [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** Floating-point precision errors in distance calculations may cause flickering between LOD levels. [G] Use a small epsilon or hysteresis when comparing distances to thresholds.
*   **Boundaries:** The simple heuristic ($d > 0.5$) is rigid and may not scale well to different volume sizes without tuning [S3, unofficial].
*   **Degenerate Input:** If the camera is inside the volume, distance-based selection may fail or select the highest LOD incorrectly. [G] Clamp distance to a minimum positive value or handle internal camera positions separately.

## Subtopics

### [Footprint-based LOD Selection](3088-footprint-based-lod-selection.md)
Selects LOD based on the projected footprint of voxels on the screen rather than just camera distance, providing more accurate resolution matching for oblique viewing angles.

## Operating characteristics
*   **Time Complexity:** $O(1)$ for LOD selection if thresholds are precomputed and distance is calculated directly. Traversal cost depends on the selected LOD level.
*   **Memory Complexity:** Requires storing multiple resolution levels of the volume data (MIP-map pyramid), increasing memory usage by a factor of roughly $1.33$ to $2.0$ depending on the number of levels and data structure overhead [S2].
*   **Performance:** Significantly reduces sample requirements for distant or peripheral rays, improving frame rates for large-scale datasets [S2].
*   **Strengths:** Simple to implement; effective for large datasets where distance correlates well with visual importance [S2].
*   **Limitations:** Does not account for viewing angle or local detail density; may result in visible seams between LOD levels if not blended or handled with algorithms like Transvoxel [S3, unofficial].
*   **When to use:** Large-scale volume visualization where interactive frame rates are required and the camera distance is a good proxy for required resolution [S2].
*   **When not to use:** When viewing angles are highly oblique or when local detail density varies significantly independent of distance.

## Background
Frustum-based LOD selection is a common technique in volume rendering to optimize performance. It is often implemented alongside acceleration structures like octrees or MIP-map pyramids [S2]. The method is widely used in geophysical simulations and large-scale scientific visualization [S2]. Variations include "Simple LOD" implementations in educational frameworks [S3, unofficial] and more sophisticated distance-based selection in custom SVO (Sparse Voxel Octree) renderers [S1, unofficial].
