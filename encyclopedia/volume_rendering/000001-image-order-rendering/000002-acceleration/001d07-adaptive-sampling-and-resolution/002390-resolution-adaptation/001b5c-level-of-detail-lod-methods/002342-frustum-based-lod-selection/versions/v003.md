# Frustum-based LOD Selection

Also called: Auto Level of Detail (LOD), Distance-based LOD, Frustum Face Distance LOD, Multi-resolution volumes (LOD), Simple LOD

## Overview
Frustum-based LOD Selection determines the appropriate resolution level for a volume entity by calculating the distance from the camera to the entity relative to the camera's frustum faces [S1, unofficial]. It solves the problem of maintaining responsive frame rates for large-scale datasets by selecting lower resolutions for distant or peripheral rays, thereby minimizing memory bandwidth and sample counts [S2]. Unlike [Footprint-based LOD Selection](3088-footprint-based-lod-selection.md), which relies on the actual projected footprint of the data to select the coarsest level satisfying a pixel threshold, this method uses distance-to-frustum-face metrics to drive LOD selection [S1, unofficial][S2].

## How it works
**Inputs and Outputs:**
*   **Inputs:** Camera world-space position, camera view/projection matrices (or inverse MVP), entity world-space position and scale, and a precomputed array of depth thresholds [S1, unofficial][S3, unofficial].
*   **Outputs:** An integer LOD index (depth level) for the volume entity [S1, unofficial].

**Data Structures:**
*   `depthTresholds_`: An array of floats where `depthTresholds_[i] = 1.0 / 2^(i+1)` for `i` from 0 to `maxSvoDepth_-1`, corresponding to LOD depths 1 through `maxSvoDepth_` [S1, unofficial].
*   `transformComponent`: Contains the entity's world-space position and scale factor [S1, unofficial].
*   `activeCameraTransformComponent`: Contains the camera's world-space position [S1, unofficial].

**Numbered Steps:**
1.  **Calculate Camera-to-Entity Distance:** Compute the Euclidean distance between the camera position and the entity's transformed position [S1, unofficial][S3, unofficial].
    $$ d = \| \mathbf{p}_{camera} - \mathbf{p}_{entity} \| $$
    Where $\mathbf{p}_{camera}$ is the camera position and $\mathbf{p}_{entity}$ is the entity position [S3, unofficial].
2.  **Determine Frustum Face Positions (Optional/Advanced):** Some implementations calculate the specific positions of the left and right frustum faces at the entity's depth to refine the distance metric or for culling [S1, unofficial].
    *   Define Normalized Device Coordinate (NDC) points, e.g., left edge $A = (-1, 0, 0, 1)$ and right edge $B = (1, 0, 0, 1)$ [S1, unofficial].
    *   Transform these NDC points to view space using the inverse Model-View-Projection matrix ($MVP^{-1}$) [S1, unofficial]:
        $$ \mathbf{v}_A = MVP^{-1} \cdot A, \quad \mathbf{v}_B = MVP^{-1} \cdot B $$
    *   Calculate the world-space position of the frustum faces at the entity's distance $d$:
        $$ \mathbf{f}_{left} = \mathbf{p}_{camera} + \mathbf{v}_A \cdot d $$
        $$ \mathbf{f}_{right} = \mathbf{p}_{camera} + \mathbf{v}_B \cdot d $$
    *   Calculate the distance between these faces normalized by screen width $W$:
        $$ \text{face\_dist} = \frac{\| \mathbf{f}_{left} - \mathbf{f}_{right} \|}{W} $$
    *   *Note:* This specific calculation is often used for frustum culling or precise footprint estimation rather than the primary LOD index selection in simpler implementations [S1, unofficial].
3.  **Select LOD Level:** Iterate through the `depthTresholds_` array to find the first threshold that the calculated distance exceeds, adjusted by the entity's scale [S1, unofficial].
    *   For each index $i$ from $0$ to $N-1$:
        *   Calculate the target depth: $L = i + 1$ [S1, unofficial].
        *   Check if the distance exceeds the threshold scaled by the entity's scale $S$:
            $$ \text{if } d > \text{depthTresholds\_}[i] \cdot S $$
        *   If true, set the LOD to $L$ and terminate the search [S1, unofficial].
    *   If no threshold is exceeded, the lowest LOD (highest resolution, typically index 0 or 1 depending on implementation) is selected [G].

**Formulas:**
*   **Distance:** $d = \| \mathbf{p}_{camera} - \mathbf{p}_{entity} \|$ [S3, unofficial].
*   **Thresholds:** $\text{depthTresholds\_}[i] = \frac{1.0}{2^{i+1}}$ for $i \in [0, \text{maxSvoDepth}-1]$ [S1, unofficial].
*   **Simple LOD Decision (Binary Example):**
    $$ LOD = \begin{cases} 2 & \text{if } \| \mathbf{p}_{camera} - (\mathbf{M} \cdot [\mathbf{p}_{voxel}, 1]) \| > 0.5 \\ 1 & \text{otherwise} \end{cases} $$
    Where $\mathbf{M}$ is the model matrix and $\mathbf{p}_{voxel}$ is the voxel position [S3, unofficial].

**Parameters:**
*   `depthTresholds_`: Array of float thresholds [S1, unofficial].
*   `lod`: Integer uniform variable controlling the selected LOD state in the shader [S3, unofficial].
*   `camera_position`: World-space position of the camera [S3, unofficial].
*   `transformComponent.getScale()`: Scale factor of the volume entity [S1, unofficial].

**Pseudocode:**
```python
import math

def select_frustum_lod(camera_pos, entity_pos, entity_scale, depth_thresholds):
    """
    Selects the LOD level for a volume entity based on camera distance.
    
    Args:
        camera_pos: tuple of 3 floats, world-space position of the camera.
        entity_pos: tuple of 3 floats, world-space position of the entity.
        entity_scale: float, scale factor of the entity.
        depth_thresholds: list of floats, precomputed thresholds [0.5, 0.25, 0.125, ...].
        
    Returns:
        int: The selected LOD level (1-based index).
    """
    # Step 1: Calculate Euclidean distance
    dx = camera_pos[0] - entity_pos[0]
    dy = camera_pos[1] - entity_pos[1]
    dz = camera_pos[2] - entity_pos[2]
    distance = math.sqrt(dx*dx + dy*dy + dz*dz)
    
    # Step 2: Iterate through thresholds
    # Note: depth_thresholds[i] corresponds to LOD level i+1
    for i, threshold in enumerate(depth_thresholds):
        # Adjust threshold by entity scale
        adjusted_threshold = threshold * entity_scale
        
        # Check if distance exceeds threshold
        if distance > adjusted_threshold:
            # Return the LOD level (1-based)
            return i + 1
            
    # If distance is smaller than all thresholds, return the highest resolution (LOD 1)
    return 1
```

**Edge Cases and Pitfalls:**
*   **Precision:** Floating-point precision errors in distance calculation may cause flickering between LOD levels if thresholds are very close [G]. Use a small epsilon or hysteresis when switching LODs to prevent visual popping [G].
*   **Boundaries:** If the entity is partially outside the frustum, simple distance-based LOD may not account for the visible portion [G]. Combine with frustum culling to avoid rendering invisible high-res volumes [G].
*   **Degenerate Input:** If `entity_scale` is zero or negative, the threshold adjustment fails [G]. Clamp scale to a minimum positive value (e.g., $10^{-6}$) [G].

## Subtopics

### [Footprint-based LOD Selection](3088-footprint-based-lod-selection.md)
Determines LOD by ensuring the projected voxel size on the screen does not exceed a pixel threshold, preventing aliasing. It uses the actual projected footprint rather than distance to frustum faces.

### [Cone-Footprint LOD and Step Sizing](5178-cone-footprint-lod-and-step-sizing.md)
Uses sample density proportional to screen content and cone footprints, differing from the fixed median footprint or simple distance metrics of this method.

### Pixel-Sized Clipmap LOD for Voxels
A level-of-detail strategy where full-resolution voxels are only kept within a pixel-sized radius, with coarser resolutions arranged in concentric clipmap rings [S4]. At 1440p with a 70° vertical FOV, one pixel spans $8.48 \times 10^{-4}$ rad, so a voxel of size $s$ covers one pixel at distance $d = s / 8.48 \times 10^{-4} \approx 1180 \cdot s$ [S4]. The full-resolution disk radius is $R_0 = 1180 \cdot s$, holding $\pi \cdot R_0^2 / s^2 = \pi \cdot 1180^2 \approx 4.4 \times 10^6$ flat voxels, or $\approx 8.7 \times 10^6$ with roughness $k=2$ [S4]. Clipmap ring $i$ spans $R_0 \cdot 2^{i-1}$ to $R_0 \cdot 2^i$ at voxel size $s \cdot 2^i$, holding $0.75 \times N_0$ voxels per ring, where $N_0$ is the full-resolution count [S4]. Total voxels over $L$ rings is $N_0 \cdot (1 + 0.75 \cdot L)$ [S4]. LOD levels needed to reach 1–5 km: 2 cm $\to$ 5–8, 5 cm $\to$ 4–6, 10 cm $\to$ 3–5, 25 cm $\to$ 2–4 [S4]. Memory resident: 6 rings $\to$ 160 MB compact / 390 MB raw; 8 rings $\to$ 200 MB / 500 MB; 12 rings $\to$ 290 MB / 710 MB [S4]. Quality headroom for sharper path-traced detail at 2 voxels/pixel multiplies resident memory by 4 ($\approx 0.6$–2.8 GB) [S4]. Aokana keeps only $\sim 2$–17% of a scene resident with distance LOD, confirming the bounded memory approach [S4].

## Operating characteristics
*   **Time Complexity:** $O(N)$ for iterating the threshold array, where $N$ is the maximum LOD depth, making it very fast for CPU-side selection [S1, unofficial].
*   **Memory Complexity:** Requires multi-resolution storage such as octree-based voxel MIP-map pyramids [S2].
*   **Measured Performance:** Cuts memory and sample requirements significantly for large-scale datasets like geophysical simulations while maintaining perceptual quality [S2].
*   **Strengths:** Simple to implement; effective for distant objects; reduces bandwidth for peripheral rays [S2].
*   **Limitations:** Does not explicitly account for the projected size of voxels on the screen, which can lead to aliasing or over-sampling if the camera moves laterally without changing distance [S2].
*   **When to Use:** Large volumes where performance is critical and visual artifacts from distance-based LOD are acceptable [S2].
*   **When Not to Use:** When strict aliasing control is required, or when the camera moves primarily laterally relative to the volume [G].

## Background
Frustum-based LOD selection is a technique used in volume ray casting to optimize rendering performance [S2]. It is part of the broader family of Level-of-Detail (LOD) methods for volume rendering [S2]. The method leverages hierarchical representations such as octree-based voxel MIP-map pyramids, where each level reduces resolution [S2]. It is particularly useful for interactive previews and large-scale datasets [S2]. Implementations can be found in various graphics frameworks and research projects, including simple LOD activations in Marching Cubes/Tetrahedra visualizers [S3, unofficial] and SVO (Sparse Voxel Octree) renderers [S1, unofficial].
