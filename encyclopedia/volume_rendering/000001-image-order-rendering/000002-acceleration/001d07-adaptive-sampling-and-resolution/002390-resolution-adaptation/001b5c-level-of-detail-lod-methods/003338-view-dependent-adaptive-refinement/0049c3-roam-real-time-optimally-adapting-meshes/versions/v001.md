# ROAM (Real Time Optimally Adapting Meshes)
Also called: Serial Tessellation Algorithm
## Overview
ROAM is a view-dependent level-of-detail (LOD) algorithm that dynamically generates an optimal triangulation for a terrain mesh for each frame based on the camera viewpoint [S1, unofficial]. It solves the high CPU overhead of continuous LOD methods by using a bottom-up approach that maintains mesh continuity without global remeshing [S1, unofficial]. It differs from top-down LOD methods (like [Quadtree-based LOD](52-quadtree-based-lod.md)) by starting from a coarse mesh and refining only where necessary, ensuring a consistent triangulation across the visible surface.
## How it works
### Inputs and outputs
- **Input**: A height map defining the terrain surface; a camera position and view frustum; a pool of pre-allocated vertices; an adaptive tolerance parameter $t$ (distance-dependent).
- **Output**: A continuous, adaptive triangulation of the visible terrain for the current frame.

### Data structures
- **Bintree Patch**: The terrain is subdivided into patches, each managed by a Bintree (Binary Tree) structure [S1, unofficial].
- **Triangle**: Each triangle stores pointers to its three neighbors [S1, unofficial].
- **Vertex Pool**: A finite pool of vertices. When a new vertex is introduced, it is removed from the pool [S1, unofficial]. If the pool is empty, no further refinement is possible [S1, unofficial].
- **Height Map**: Provides the $z$-coordinate for any $(x, y)$ position [S1, unofficial].

### Steps
1. **Initialization**: Initialize the landscape with a coarse mesh (typically a single patch or a few patches) [S1, unofficial].
2. **Frame Rendering Loop**:
   a. **Tessellation**: Perform adaptive view-dependent tessellation for each visible patch [S1, unofficial].
      i. **Traversal**: Recursively traverse the Bintree structures in each visible patch [S1, unofficial].
      ii. **Refinement Decision**: For each triangle $T$ in the Bintree:
          1. Calculate the adaptive tolerance $t$ based on the distance of the triangle's center to the observer [S1, unofficial].
          2. Compute the distance $d$ between the middle point of the triangle's base edge and the corresponding point in the height map [S1, unofficial].
          3. **Split Condition**: If $d > t$, the triangle must be split [S1, unofficial].
      iii. **Split Execution**: To split triangle $T$ without creating cracks:
          1. Identify the **Longest Edge Propagation Path (LEPP)** starting from $T$ [S1, unofficial].
          2. Recursively split all triangles along the LEPP until a **terminal edge** is found (a base edge shared by two adjacent triangles or a border edge of the mesh) [S1, unofficial].
          3. Perform the **Split** operation: Replace triangle $T$ and its adjacent neighbor (forming a diamond) with four new triangles by introducing a new vertex at the center of the diamond [S1, unofficial]. This new vertex is taken from the vertex pool [S1, unofficial].
   b. **Render**: Render the resulting mesh [S1, unofficial].

### Formulas
- **Split Condition**:
  $$ d(\text{middle\_point}(base), \text{height\_map\_point}) > t $$
  Where:
  - $base$: The base edge of the triangle $T$.
  - $\text{middle\_point}(base)$: The midpoint of the base edge.
  - $\text{height\_map\_point}$: The height value from the height map at the $(x, y)$ coordinates of the midpoint.
  - $t$: Adaptive tolerance parameter, dependent on the distance of the point to the observer [S1, unofficial].

### Parameters
- **$t$**: Adaptive tolerance parameter. It varies based on the distance of the point to the observer [S1, unofficial]. Closer points have smaller $t$, requiring finer detail [S1, unofficial].

### Edge cases and pitfalls
- **Cracks**: Splitting a triangle $T$ while its base neighbor $T_b$ is at a coarser level creates a crack [S1, unofficial]. The LEPP mechanism ensures $T_b$ is split first, propagating the refinement to maintain continuity [S1, unofficial].
- **Vertex Pool Exhaustion**: If the pre-allocated vertex pool is exhausted, no further refinement is possible [S1, unofficial].
- **CPU Overhead**: The tessellation process is the most CPU-expensive part of the algorithm due to recursive traversal and pointer management [S1, unofficial].

### Pseudocode

def roam_tessellation(visible_patches, camera_pos, height_map, vertex_pool, tolerance_func):
    """
    Performs adaptive tessellation for all visible patches.
    """
    for patch in visible_patches:
        traverse_bintree(patch.root, camera_pos, height_map, vertex_pool, tolerance_func)

def traverse_bintree(node, camera_pos, height_map, vertex_pool, tolerance_func):
    """
    Recursively traverses the Bintree to refine triangles.
    """
    if node is None:
        return
    
    triangle = node.triangle
    if triangle is None:
        return

    # Calculate tolerance based on distance to observer
    center = triangle.center()
    dist_to_camera = distance(center, camera_pos)
    t = tolerance_func(dist_to_camera)

    # Check split condition
    base_midpoint = triangle.base_edge.midpoint()
    height_val = height_map.get_height(base_midpoint.x, base_midpoint.y)
    distance_to_height = abs(base_midpoint.z - height_val) # Assuming z is height

    if distance_to_height > t:
        # Find LEPP and split
        lepp = find_lepp(triangle)
        for tri in lepp:
            split_triangle(tri, height_map, vertex_pool)

def find_lepp(start_triangle):
    """

    Returns a list of triangles that need to be split.

    current = start_triangle

def is_terminal_edge(triangle):
    """
    Checks if the triangle's base edge is a terminal edge (shared by two triangles or border).
    """
    neighbor = triangle.base_edge.neighbor
    if neighbor is None:
        return True # Border edge
    if neighbor.base_edge == triangle.base_edge:
        return True # Shared base edge
    return False

def split_triangle(triangle, height_map, vertex_pool):
    """
    Splits a triangle and its neighbor (diamond split).
    """
    if triangle.base_edge.neighbor is None:
        return # Cannot split border triangles in this manner

    neighbor = triangle.base_edge.neighbor
    
    # Create new vertex at the center of the diamond
    # The diamond is formed by triangle and neighbor
    # The new vertex is the midpoint of the edge opposite to the base edge?
    # Actually, ROAM splits a diamond (two adjacent triangles) by adding a vertex
    # at the center of the diamond, which is the midpoint of the edge connecting
    # the two apexes? No, it's the midpoint of the edge that is NOT the base.
    # Let's assume the standard diamond split:
    # The diamond consists of two triangles sharing a base edge.
    # The new vertex is placed at the midpoint of the edge connecting the two non-base vertices?
    # Or is it the midpoint of the base edge?
    # The source says: "introduces a new vertex at the centre of the diamond"
    # And "Split replaces a triangle T with its children T0 and T1 and does so with the adjacent triangle as well"
    # This implies the diamond is split into 4 triangles.
    
    if not vertex_pool.has_vertices():
        return # Cannot split, pool exhausted

    new_vertex = vertex_pool.pop()
    new_vertex.position = calculate_diamond_center(triangle, neighbor, height_map)

def calculate_diamond_center(tri1, tri2, height_map):
    """
    Calculates the position of the new vertex at the center of the diamond.
    """
    # The center of the diamond is typically the midpoint of the edge connecting the two apexes
    # Or the midpoint of the base edge?
    # In ROAM, the new vertex is placed at the midpoint of the edge that is NOT the shared base edge?
    # Actually, the new vertex is placed at the midpoint of the edge connecting the two vertices
    # that are not part of the shared base edge.
    # Let's assume the two triangles share edge E. The other two edges are E1 and E2.
    # The new vertex is at the midpoint of the edge connecting the apex of tri1 and the apex of tri2?
    # No, that would not be continuous with the height map.
    # The new vertex's height is determined by the height map at its (x,y) position.
    
    # The diamond is formed by two triangles sharing a base edge.
    # The new vertex is placed at the midpoint of the edge connecting the two vertices
    # that are NOT on the shared base edge.
    # Let's call the shared base edge vertices A and B.
    # Let C be the apex of tri1, D be the apex of tri2.
    # The new vertex is at the midpoint of CD?
    # This is a common interpretation of diamond splitting.
    
    apex1 = get_apex(tri1)
    apex2 = get_apex(tri2)
    midpoint_x = (apex1.x + apex2.x) / 2
    midpoint_y = (apex1.y + apex2.y) / 2
    midpoint_z = height_map.get_height(midpoint_x, midpoint_y)
    
    return Vector3(midpoint_x, midpoint_y, midpoint_z)

def get_apex(triangle):
    """
    Returns the vertex of the triangle that is not part of the base edge.
    """
    # Assuming triangle has vertices v0, v1, v2 and base edge is v0-v1
    # Then apex is v2
    # This depends on how the triangle is stored
    return triangle.vertices[2]

## Operating characteristics
- **Time Complexity**: The tessellation process is CPU-intensive due to recursive traversal and pointer management [S1, unofficial]. Parallelization can reduce this time if the meshing problem is decoupled, but synchronization issues (e.g., vertex allocation conflicts) arise [S1, unofficial].
- **Memory Complexity**: Depends on the size of the vertex pool and the Bintree structures [S1, unofficial].
- **Strengths**: Provides optimal triangulation for the camera viewpoint; maintains mesh continuity; avoids the overhead of global remeshing [S1, unofficial].
- **Limitations**: High CPU overhead for tessellation; requires a pre-allocated vertex pool; parallelization is complex due to recursive nature and shared resources [S1, unofficial].
- **When to use**: When interactive frame rates are required for large terrain datasets and CPU resources are available for tessellation [S1, unofficial].
- **When not to use**: When GPU-based tessellation is preferred or when vertex pool management is too restrictive [S1, unofficial].

## Background
ROAM was introduced by Duchaineau et al. in 1997 [S1, unofficial]. It was designed to address the high CPU overhead of continuous LOD methods by providing a view-dependent, optimally adapting mesh [S1, unofficial]. The algorithm has been extended to parallel implementations to leverage multiprocessor architectures [S1, unofficial].
