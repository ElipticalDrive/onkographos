# ROAM (Real Time Optimally Adapting Meshes)
Also called: Serial Tessellation Algorithm
## Overview
ROAM is a view-dependent level-of-detail algorithm that dynamically generates an optimal triangulation for a terrain mesh for each frame based on the camera viewpoint [S1, unofficial]. It solves the high CPU overhead of continuous LOD methods by adaptively refining meshes in regions of interest while maintaining a consistent triangulation across the visible surface [S1, unofficial]. It differs from top-down LOD methods by starting from a coarse mesh and refining only where necessary, building on [View-Dependent Adaptive Refinement](6952-view-dependent-adaptive-refinement.md).
## How it works
### Inputs and outputs
- **Input**: A height map defining the terrain surface; a camera position; a pool of pre-allocated vertices; an adaptive tolerance parameter $t$ (distance-dependent) [S1, unofficial].
- **Output**: A continuous, adaptive triangulation of the visible terrain for the current frame [S1, unofficial].

### Data structures
- **Bintree Patch**: The terrain is subdivided into patches, each managed by a Bintree (Binary Tree) structure [S1, unofficial].
- **Triangle**: Each triangle stores pointers to its three neighbors [S1, unofficial].
- **Vertex Pool**: A finite pool of vertices. When a new vertex is introduced, it is removed from the pool [S1, unofficial]. If the pool is empty, no further refinement is possible [S1, unofficial].
- **Height Map**: Provides the $z$-coordinate (height) for any $(x, y)$ position [S1, unofficial].

### Steps
1. **Initialization**: Initialize the landscape with a coarse mesh [S1, unofficial].
2. **Frame Rendering Loop**:
   a. **Tessellation**: Perform adaptive view-dependent tessellation for each visible patch [S1, unofficial].
      i. **Traversal**: Recursively traverse the two Bintree structures in each visible patch [S1, unofficial].
      ii. **Refinement Decision**: For each triangle $T$ in the Bintree:
          1. Calculate the adaptive tolerance $t$ based on the distance of the triangle's center to the observer [S1, unofficial].
          2. Compute the distance $d$ between the middle point of the triangle's base edge and the corresponding point in the height map [S1, unofficial].
          3. **Split Condition**: If $d > t$, the triangle must be split [S1, unofficial].
      iii. **Split Execution**: To split triangle $T$ without creating cracks:
          1. Identify the **Longest Edge Propagation Path (LEPP)** starting from $T$ [S1, unofficial].
          2. Recursively split all triangles along the LEPP until a **terminal edge** is found (a base edge shared by two adjacent triangles or a border edge of the mesh) [S1, unofficial].
          3. Perform the **Split** operation: Replace triangle $T$ and its adjacent neighbor (forming a diamond) with four new triangles by introducing a new vertex at the center of the diamond [S1, unofficial]. This new vertex is taken from the vertex pool [S1, unofficial].
3. **Render**: Render the resulting mesh [S1, unofficial].

### Formulas
- **Split Condition**:
  $$ d(\text{middle\_point}(base), \text{height\_map\_point}) > t $$
  Where:
  - $base$: The base edge of the triangle $T$.
  - $\text{middle\_point}(base)$: The midpoint of the base edge.
  - $\text{height\_map\_point}$: The height value from the height map at the $(x, y)$ coordinates of the midpoint.
  - $t$: Adaptive tolerance parameter, dependent on the distance of the point to the observer [S1, unofficial].

### Parameters
- **$t$**: Adaptive tolerance parameter. It varies based on the distance of the point to the observer [S1, unofficial]. Closer points have smaller $t$, requiring finer detail [S1, unofficial].

### Edge cases and pitfalls
- **Cracks**: Splitting a triangle $T$ while its base neighbor $T_b$ is at a coarser level creates a crack [S1, unofficial]. The LEPP mechanism ensures $T_b$ is split first, propagating the refinement to maintain continuity [S1, unofficial].
- **Vertex Pool Exhaustion**: If the pre-allocated vertex pool is exhausted, no further refinement is possible [S1, unofficial].
- **CPU Overhead**: The tessellation process is the most CPU-expensive part of the algorithm due to recursive traversal and pointer management [S1, unofficial].

import math

class Vec3:
    def __init__(self, x, y, z): self.x, self.y, self.z = x, y, z
    def midpoint(self, other): return Vec3((self.x+other.x)/2, (self.y+other.y)/2, (self.z+other.z)/2)

class Edge:
    def __init__(self, v0, v1, neighbor=None): self.v0, self.v1, self.neighbor = v0, v1, neighbor
    def midpoint(self): return self.v0.midpoint(self.v1)

class Triangle:
    def __init__(self, v0, v1, v2, base_edge=None):
        self.v0, self.v1, self.v2 = v0, v1, v2
        self.base_edge = base_edge if base_edge else Edge(v0, v1)
    def center(self): return Vec3((self.v0.x+self.v1.x+self.v2.x)/3, (self.v0.y+self.v1.y+self.v2.y)/3, (self.v0.z+self.v1.z+self.v2.z)/3)
    def get_apex(self): return self.v2

def roam_tessellation(visible_patches, camera_pos, height_map, vertex_pool, tolerance_func):
    for patch in visible_patches:
        traverse_bintree(patch.root, camera_pos, height_map, vertex_pool, tolerance_func)

def traverse_bintree(node, camera_pos, height_map, vertex_pool, tolerance_func):
    if node is None or node.triangle is None:
        return
    tri = node.triangle
    center = tri.center()
    dist = math.sqrt((center.x-camera_pos.x)**2 + (center.y-camera_pos.y)**2 + (center.z-camera_pos.z)**2)
    t = tolerance_func(dist)
    base_mid = tri.base_edge.midpoint()
    height_val = height_map.get_height(base_mid.x, base_mid.y)
    d = math.sqrt((base_mid.z - height_val)**2)
    if d > t:
        lepp = find_lepp(tri)
        for tri_split in lepp:
            split_triangle(tri_split, height_map, vertex_pool)

def find_lepp(start_tri):
    path = []
    current = start_tri
    while not is_terminal_edge(current):
        path.append(current)
        current = current.base_edge.neighbor
    path.append(current)
    return path

def is_terminal_edge(tri):
    neighbor = tri.base_edge.neighbor
    if neighbor is None:
        return True
    if neighbor.base_edge == tri.base_edge:
        return True
    return False

def split_triangle(tri, height_map, vertex_pool):
    if tri.base_edge.neighbor is None or not vertex_pool.has_vertices():
        return
    neighbor = tri.base_edge.neighbor
    new_vertex = vertex_pool.pop()
    apex1 = tri.get_apex()
    apex2 = neighbor.get_apex()
    new_vertex.x = (apex1.x + apex2.x) / 2
    new_vertex.y = (apex1.y + apex2.y) / 2
    new_vertex.z = height_map.get_height(new_vertex.x, new_vertex.y)

## Operating characteristics
- **Time Complexity**: The tessellation process is the most CPU-expensive part due to recursive traversal and pointer management [S1, unofficial]. Parallelization can reduce time if decoupled, but recursive nature causes vertex allocation conflicts [S1, unofficial].
- **Memory Complexity**: Depends on the pre-allocated vertex pool size and Bintree structures [S1, unofficial].
- **Strengths**: Provides optimal triangulation for the camera viewpoint; maintains mesh continuity via LEPP [S1, unofficial].
- **Limitations**: High CPU overhead; requires a finite pre-allocated vertex pool; parallelization is complex due to synchronization needs [S1, unofficial].
- **When to use**: Interactive frame rates for large terrain datasets where CPU resources are available for tessellation [S1, unofficial].
- **When not to use**: When GPU-based tessellation is preferred or vertex pool management is too restrictive [S1, unofficial].
## Background
ROAM was introduced by Duchaineau et al. in 1997 [S1, unofficial]. It was designed to address the high CPU overhead of continuous LOD methods by providing a view-dependent, optimally adapting mesh [S1, unofficial]. The algorithm has been extended to parallel implementations to leverage multiprocessor architectures [S1, unofficial].
