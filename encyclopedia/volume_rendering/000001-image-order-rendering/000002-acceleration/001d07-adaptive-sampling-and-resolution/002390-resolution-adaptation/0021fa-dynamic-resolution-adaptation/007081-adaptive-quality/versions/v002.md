# Adaptive Quality

Also called: Frame Rate Maintenance via Quality Adjustment, Time-based Quality Control

## Overview
Adaptive Quality is a resolution adaptation technique that dynamically adjusts rendering parameters (such as ray count or sampling distance) to maintain a target frame rate based on measured rendering time [S1]. It differs from sibling methods by focusing on computational budget allocation per frame rather than viewport reduction [Parent](2683-dynamic-resolution-adaptation.md) or spatial foveation [Foveated Rendering](11952-foveated-rendering.md) [G]. It is particularly effective on CPUs where execution time is predictable, whereas GPUs may benefit more from fixed quality settings [S1].

## How it works
**Inputs and Outputs:**
- Input: Current frame rendering time ($T_{current}$), target frame time ($T_{target} = 1/FPS_{target}$), and current quality parameters (number of casted rays, sampling distances, iteration counts) [S1].
- Output: Adjusted quality parameters for the subsequent rendering request [S1].

**Data Structures:**
Not given in the sources. The method relies on scalar timing measurements and quality control flags [S1].

**Steps:**
1. Measure the time taken to render the current frame ($T_{current}$) [S1].
2. Compare $T_{current}$ with the target frame time ($T_{target}$) [S1].
3. If $T_{current} > T_{target}$ (rendering is too slow):
   - Reduce quality parameters for the next frame, such as decreasing the number of casted rays or increasing sampling distances [S1].
   - During interactive scenarios (rotation, setting changes), enforce the target FPS by lowering resolution or quality [S1].
4. If $T_{current} \le T_{target}$ (rendering is within budget):
   - Increase quality parameters for the next frame to improve image fidelity, such as increasing iterations to reduce Monte Carlo noise [S2].
   - Maintain the target frame rate while maximizing visual quality [S2].

**Parameters:**
- Target FPS: User-defined or system-default value [S1].
- Quality Metrics: Number of casted rays, sampling distances, or iteration counts [S1, S2].

**Edge Cases and Pitfalls:**
- **GPU vs. CPU:** The method works very well for CPUs because computation time is predictable [S1]. For GPU volume rendering, fixed quality (“Normal” setting) may be more suitable due to hardware parallelism and scheduling variability [S1].
- **Interaction:** Quality reduction is specifically triggered during user interaction to ensure responsiveness [S1].

**Pseudocode:**
```python
def adaptive_quality_step(target_fps, current_frame_time, current_ray_count, current_sampling_distance, current_iterations):
    """
    Adjusts quality parameters for the next frame based on current render time.
    
    Args:
        target_fps (float): Desired frames per second.
        current_frame_time (float): Time taken to render the current frame in seconds.
        current_ray_count (int): Number of rays cast per pixel.
        current_sampling_distance (float): Distance between samples along rays.
        current_iterations (int): Number of Monte Carlo iterations per sample.
        
    Returns:
        tuple: (next_ray_count, next_sampling_distance, next_iterations)
    """
    target_frame_time = 1.0 / target_fps
    
    if current_frame_time > target_frame_time:
        # Rendering exceeded the time budget; reduce quality [S1]
        # Decrease ray count, increase sampling distance (fewer samples)
        next_ray_count = max(1, current_ray_count // 2)
        next_sampling_distance = current_sampling_distance * 2.0
        next_iterations = max(1, current_iterations // 2)
    else:
        # Rendering within budget; increase quality [S2]
        # Increase iterations to reduce Monte Carlo noise
        next_ray_count = current_ray_count * 2
        next_sampling_distance = current_sampling_distance / 2.0
        next_iterations = current_iterations * 2
        
    return next_ray_count, next_sampling_distance, next_iterations
```

## Subtopics

### Output System Coupling Algorithm
A variant described in the context of remote volume rendering where a Web server and rendering server coordinate to maintain quality [S2]. If the Web server is fast, the rendering server increases the number of iterations per frame to improve image quality (reduce noise in Monte Carlo rendering) while maintaining the target frame rate [S2]. This ensures users receive high-quality images quickly across different network environments [S2].

## Operating characteristics
- **Time Complexity:** Not given in the sources.
- **Memory Complexity:** Not given in the sources.
- **Performance:** Works very well for CPUs due to predictable computation time [S1]. For GPUs, fixed quality may be more suitable, suggesting limitations in GPU-centric pipelines [S1].
- **Strengths:** Maintains interactive frame rates during heavy interaction; improves quality when idle [S1, S2].
- **Limitations:** Less effective on GPUs due to unpredictable execution times; requires accurate timing measurement [S1].

## Background
The method is documented in the 3D Slicer volume rendering module, which provides advanced controls for quality adaptation during interaction [S1]. It is also referenced in research on optimized interactive remote realistic volume rendering, where coupling algorithms between Web and rendering servers are used to balance quality and speed [S2].
