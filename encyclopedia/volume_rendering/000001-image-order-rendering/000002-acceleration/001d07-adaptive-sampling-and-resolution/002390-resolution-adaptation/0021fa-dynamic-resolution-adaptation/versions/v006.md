# Dynamic Resolution Adaptation

Also called: ComputeReductionFactor, Frame Rate Maintenance via Resolution Adjustment

## Overview
Dynamic Resolution Adaptation is a performance-based image-order rendering technique that modulates the render viewport's reduction factor in real-time to maintain a target frame rate [S1, unofficial]. It solves the problem of performance instability in volume rendering, where minor parametric changes (such as transfer function modifications) can cause significant frame rate dips [S1, unofficial]. It sets itself apart from static resolution schemes by continuously shifting the resolution granularity based on the gradient of recent frame times, rather than using fixed blending factors or static thresholds [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** The render viewport reduction factor from the previous frame ($n_{prev}$), the actual time taken to draw the previous frame ($TimeToDraw$), and the allocated time budget for the next frame ($allocatedTime$) [S1, unofficial].
*   **Output:** The new render viewport reduction factor ($n_{new}$) for the current frame [S1, unofficial].

**Data Structures:**
*   $n$: A scalar floating-point value representing the reduction factor.
*   $TimeToDraw$: A scalar floating-point value representing the duration of the previous frame's rendering pass in seconds.
*   $allocatedTime$: A scalar floating-point value representing the target time budget for the next frame in seconds.

**Steps:**
1.  **Validate State:** Ensure the previous reduction factor $n_{prev}$ is within the valid range $(0.0, 1.0]$ and $TimeToDraw \ge 0.0$ [S1, unofficial]. If invalid, the method cannot proceed safely [S1, unofficial].
2.  **Compute Adjustment:** Calculate the new reduction factor $n_{new}$ based on the ratio of the actual render time to the allocated time budget. The goal is to reduce resolution (increase $n$) if the frame was too slow, or increase resolution (decrease $n$) if the frame was too fast [S1, unofficial].
3.  **Clamp:** Ensure $n_{new}$ remains within the valid range $(0.0, 1.0]$ to prevent infinite resolution or invalid states [S1, unofficial].

**Formulas:**
Let $n_{prev}$ be the reduction factor from the previous frame.
Let $TimeToDraw$ be the time taken for the previous frame.
Let $allocatedTime$ be the target time budget for the current frame.

The new reduction factor $n_{new}$ is computed as:

$$
n_{new} = n_{prev} \times \frac{TimeToDraw}{allocatedTime}
$$

Where:
*   $n_{prev} \in (0.0, 1.0]$
*   $TimeToDraw \ge 0.0$
*   $allocatedTime > 0.0$

**Parameters:**
*   $allocatedTime$: The time budget in seconds for the next frame. Typical values depend on the target frame rate (e.g., $1/60 \approx 0.0167$ seconds for 60 FPS) [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Invalid State:** The method requires $n_{prev} > 0.0$ and $n_{prev} \le 1.0$, and $TimeToDraw \ge 0.0$. If these conditions are not met, the calculation is undefined or unstable [S1, unofficial].
*   **Precision:** Floating-point precision errors may accumulate if the ratio $\frac{TimeToDraw}{allocatedTime}$ is consistently slightly above or below 1.0 over many frames. Clamping is essential [S1, unofficial].
*   **Oscillation:** Rapid fluctuations in $TimeToDraw$ can cause $n$ to oscillate between high and low values, leading to visual flickering. A smoothing factor or hysteresis is often required in practice, though not explicitly defined in the source [G].

**Pseudocode:**

```python
def compute_new_reduction_factor(n_prev, time_to_draw, allocated_time):
    """
    Computes the new reduction factor for dynamic resolution adaptation.
    
    Args:
        n_prev (float): The reduction factor from the previous frame. Must be in (0.0, 1.0].
        time_to_draw (float): The time taken to draw the previous frame in seconds. Must be >= 0.0.
        allocated_time (float): The time budget for the next frame in seconds. Must be > 0.0.
        
    Returns:
        float: The new reduction factor n_new, clamped to (0.0, 1.0].
    """
    # Validate inputs
    if not (0.0 < n_prev <= 1.0):
        raise ValueError("Previous reduction factor must be in (0.0, 1.0]")
    if time_to_draw < 0.0:
        raise ValueError("Time to draw must be >= 0.0")
    if allocated_time <= 0.0:
        raise ValueError("Allocated time must be > 0.0")
        
    # Compute new reduction factor
    # The formula scales the previous factor by the ratio of actual time to budget.
    # If time_to_draw > allocated_time, the factor increases (lower resolution).
    # If time_to_draw < allocated_time, the factor decreases (higher resolution).
    n_new = n_prev * (time_to_draw / allocated_time)
    
    # Clamp to valid range (0.0, 1.0]
    # Note: The source specifies the range as (0.0, 1.0]. 
    # We must ensure n_new is strictly greater than 0.0 and at most 1.0.
    if n_new <= 0.0:
        n_new = 1e-9 # Guard against zero or negative due to precision, though mathematically unlikely if n_prev > 0
    if n_new > 1.0:
        n_new = 1.0
        
    return n_new
```

## Subtopics

### [Dynamic Frame Rate Adaptation](8221-dynamic-frame-rate-adaptation.md)
Dynamic Frame Rate Adaptation is a runtime adjustment system that tracks rendering performance and adjusts the distribution of resolution levels on the fly to maintain a consistently high update rate above a set threshold. It solves the problem of performance instability in volume rendering, where small parametric changes (e.g., transfer function modifications) can cause frame rate dips leading to cybersickness. It sets itself apart from static resolution schemes by continuously shifting the "anchor points" between resolution levels based on the gradient of recent frame times, rather than using fixed blending factors. See [Dynamic Frame Rate Adaptation](8221-dynamic-frame-rate-adaptation.md).

### Time-critical level-of-detail selection
Time-critical level-of-detail selection is an algorithm that performs automatic level-of-detail selection to match different parameters like the desired frame rate by predicting rendering time and dynamically selecting the level-of-detail for the next frame [S2, unofficial]. It collects performance statistics to predict rendering time and dynamically selects the level-of-detail for the next frame based on the predicted time [S2, unofficial]. The desired frame rate is a key parameter used to match the level-of-detail selection [S2, unofficial].

## Operating characteristics
**Time and Memory Complexity:**
The adaptation logic itself is $O(1)$ in time and memory, as it involves a simple arithmetic operation on scalar values [S1, unofficial]. The overall rendering complexity depends on the chosen reduction factor $n$, which affects the number of samples or the resolution of the volume grid [S1, unofficial].

**Measured Performance:**
Not given in the sources.

**Scaling:**
The method scales with the target frame rate and the variability of the scene's rendering cost. It is most effective in scenarios where rendering time fluctuates significantly due to user interaction or dynamic content [S1, unofficial].

**Strengths and Limitations:**
*   **Strengths:** Maintains a stable frame rate by dynamically adjusting resolution. Simple to implement.
*   **Limitations:** Can lead to visual quality fluctuations. Requires careful tuning of the $allocatedTime$ parameter. The source notes that it requires existing $ReductionFactor$ to be $>0.0$ and $\le 1.0$, and $TimeToDraw \ge 0.0$ [S1, unofficial].

**When to use it and when not:**
Use it when maintaining a consistent frame rate is more critical than maintaining a consistent visual resolution, such as in interactive volume visualization or virtual reality applications [S1, unofficial]. Do not use it when visual consistency is paramount and frame rate drops are acceptable.

## Background
Dynamic Resolution Adaptation is implemented in the VTKMultiVolumeRayCaster, a component of the Visualization Toolkit (VTK) [S1, unofficial]. The method is designed to handle multiple volumes and adapt their rendering resolution based on performance metrics [S1, unofficial]. The concept of time-critical level-of-detail selection is also discussed in the context of volume visualization on large-scale displays, where automatic level-of-detail selection is used to match desired frame rates [S2, unofficial].
