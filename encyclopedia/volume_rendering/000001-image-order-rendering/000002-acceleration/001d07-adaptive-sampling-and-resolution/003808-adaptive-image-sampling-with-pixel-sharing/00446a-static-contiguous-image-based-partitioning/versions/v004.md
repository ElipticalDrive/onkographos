# Static Contiguous Image-Based Partitioning

Also called: Static image-based partitioning, Image-based partitioning

## Overview
Static Contiguous Image-Based Partitioning is a parallel volume rendering strategy that distributes the final image plane into disjoint, contiguous blocks (tiles) among processors, where each processor independently renders its assigned section [S1][S4, unofficial]. It solves the problem of load imbalance and communication overhead inherent in adaptive image sampling methods by avoiding the replicated ray casting costs associated with shared pixels at partition boundaries [S3, unofficial]. Unlike its parent method, Adaptive Image Sampling with Pixel Sharing, which requires complex synchronization to handle shared pixels between adaptive regions, this method uses static contiguous partitioning to ensure that shared pixels are computed only once by neighboring processors in a specific order, eliminating synchronization overhead [S3, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D volume dataset $V$, a camera configuration (view matrix, projection matrix), and a target image resolution $W \times H$ [G].
*   **Output:** A final composite image $I$ of resolution $W \times H$ [G].

**Data Structures:**
*   **Volume Data:** Distributed across $P$ processors. Each processor $p$ holds a subset of the volume data $V_p$ responsible for rendering its tile [S4, unofficial].
*   **Image Partition:** The image is divided into $P$ contiguous blocks. If adaptive sampling is used, the image is conceptually divided into square sample regions of size $I_{max} \times I_{max}$ pixels [S3, unofficial]. These regions are grouped into $P$ contiguous large blocks with roughly equal amounts of work [S3, unofficial].
*   **Shared Memory/Communication:** In shared-memory architectures, processors communicate via shared memory. In distributed-memory systems, processors communicate via message passing [S4, unofficial].

**Steps:**
1.  **Data Distribution:** Volume data is distributed arbitrarily across processors initially [S4, unofficial]. Each processor determines the ownership of the subvolume required for its assigned tile [S4, unofficial]. Processors keep the data they are responsible for and send all other data to the corresponding processor in charge [S4, unofficial]. This redistribution may happen at the beginning of every frame computation [S4, unofficial].
2.  **Tile Assignment:** The image is partitioned into $P$ contiguous blocks [S3, unofficial]. Each processor $p$ is assigned one block $B_p$ [S3, unofficial].
3.  **Rendering (Scanline Order):** Each processor renders its assigned block $B_p$ in scanline order from top to bottom [S3, unofficial]. For each pixel (or sample region) in the block, the processor casts rays into the volume data it owns ($V_p$) and composites the result [S1]. If adaptive sampling is employed, the processor calculates sample regions within its block [S3, unofficial].
4.  **Handling Shared Pixels (Boundary Condition):** Pixels shared by image sections processed by different processors are located only in the square sample regions at the top and bottom of each image section [S3, unofficial]. **Top Regions:** Each processor calculates the shared pixels in the top sample regions of its section [S2, unofficial]. **Bottom Regions:** When a processor reaches the bottom sample regions, it uses the shared pixel values already available in shared memory (or received from lower neighbors), which were calculated by its lower neighboring processors [S2, unofficial]. This mechanism avoids replicated ray casting for shared pixels [S3, unofficial].
5.  **Result Collection:** The sub-images from all processors are collected onto one processor (or composited in a shared frame buffer) to produce the final image [S1].

**Pseudocode:**
```python
def static_contiguous_partitioning(volume_data, camera, image_width, image_height, num_processors, processor_id):
    # Step 1: Data Distribution
    # [G] In a real system, volume_data is filtered to cells contributing to this tile.
    local_volume = filter_volume_to_tile(volume_data, processor_id, num_processors, image_width, image_height)
    
    # Step 2: Tile Assignment
    tile_height = image_height // num_processors
    tile_start_y = processor_id * tile_height
    tile_end_y = image_height if processor_id == num_processors - 1 else (processor_id + 1) * tile_height
    
    sub_image = [[0.0, 0.0, 0.0, 0.0] for _ in range(tile_end_y - tile_start_y)]
    
    # Step 3 & 4: Rendering with Shared Pixel Handling
    for y in range(tile_start_y, tile_end_y):
        for x in range(image_width):
            is_top_boundary = (y == tile_start_y) and (processor_id > 0)
            is_bottom_boundary = (y == tile_end_y - 1) and (processor_id < num_processors - 1)
            
            if is_top_boundary:
                pixel_value = cast_ray_and_composite(local_volume, camera, x, y)
                sub_image[y - tile_start_y][x] = pixel_value
                # [G] Store in shared memory for lower neighbors
            elif is_bottom_boundary:
                # [G] Retrieve from shared memory, calculated by lower neighbor
                pixel_value = retrieve_shared_pixel(x, y)
                sub_image[y - tile_start_y][x] = pixel_value
            else:
                pixel_value = cast_ray_and_composite(local_volume, camera, x, y)
                sub_image[y - tile_start_y][x] = pixel_value
                
    return sub_image

def filter_volume_to_tile(volume, pid, P, W, H):
    # [G] Projects volume cells to screen space and keeps those within the tile's y-range
    tile_h = H // P
    y_min = pid * tile_h
    y_max = (pid + 1) * tile_h if pid < P - 1 else H
    return [cell for cell in volume if y_min <= cell.screen_y <= y_max]

def cast_ray_and_composite(volume, camera, x, y):
    # [G] Standard front-to-back volume rendering
    ray_origin = camera.unproject(x, y)
    ray_dir = camera.get_direction(x, y)
    ray_dir = normalize(ray_dir)
    
    # [G] Compute step size based on voxel size or fixed value
    step_size = 0.5 
    ray_length = compute_ray_length_in_volume(ray_origin, ray_dir, volume.bounds)
    
    color = [0.0, 0.0, 0.0, 0.0]
    t = 0.0
    while t < ray_length:
        sample = volume.sample(ray_origin + t * ray_dir)
        alpha = sample[3]
        color = [
            color[0] + (1.0 - color[3]) * sample[0] * alpha,
            color[1] + (1.0 - color[3]) * sample[1] * alpha,
            color[2] + (1.0 - color[3]) * sample[2] * alpha,
            color[3] + (1.0 - color[3]) * alpha
        ]
        if color[3] >= 0.99:
            break
        t += step_size
    return color

def compute_ray_length_in_volume(origin, direction, bounds):
    # [G] Standard ray-box intersection to find t_max
    t_min = -float('inf')
    t_max = float('inf')
    for i in range(3):
        if direction[i] == 0:
            if origin[i] < bounds.min[i] or origin[i] > bounds.max[i]:
                return 0.0
        else:
            t1 = (bounds.min[i] - origin[i]) / direction[i]
            t2 = (bounds.max[i] - origin[i]) / direction[i]
            t_min = max(t_min, min(t1, t2))
            t_max = min(t_max, max(t1, t2))
    return max(0.0, t_max)

def normalize(v):
    mag = (v[0]**2 + v[1]**2 + v[2]**2)**0.5
    return [v[0]/mag, v[1]/mag, v[2]/mag]

def retrieve_shared_pixel(x, y):
    # [G] Reads from a shared memory array populated by the processor with ID (processor_id + 1)
    return shared_pixel_buffer[y][x]
```

**Parameters:**
*   $I_{max}$: The side length of square sample regions in pixels, used when adaptive sampling is active. Not given in the sources.
*   $P$: Number of processors.

**Edge Cases and Pitfalls:**
*   **Load Imbalance:** Image order does not guarantee equal cell distribution. If one tile contains more cells (e.g., due to uneven cell sizes in unstructured data or camera focus on a specific region), its processor performs more work, causing load imbalance [S1].
*   **Replicated Loading:** Cells covering more than one tile result in replicated loading of those cells across multiple processors [S1].
*   **Scalability Limits:** In distributed memory systems, as $P$ increases, the image space grows into too many pieces, causing data redistribution and boundary data redundancy to become serious scalability limitations [S4, unofficial].
*   **Per-Frame Coherence:** In real-time volume rendering, user interaction can cause sudden scene changes, breaking per-frame coherence and preventing the use of retained-mode optimizations that reduce transferred data [S4, unofficial].

## Subtopics

### [Hybrid Partitioning Parallel Ray Casting](11261-hybrid-partitioning-parallel-ray-casting.md)
Combines object-based partitioning for boundary cell projection with image-based partitioning for ray traversal to achieve load balancing. It sets itself apart by decoupling the partitioning strategy to avoid replicated ray casting costs at processor boundaries, unlike the purely image-based approach of this method.

## Operating characteristics
*   **Time Complexity:** Depends on the number of pixels in the tile and the number of cells contributing to those pixels. Load imbalance can cause significant variance in execution time across processors [S1].
*   **Memory Complexity:** Each processor must store the volume data contributing to its tile. Replicated loading of cells covering multiple tiles increases memory usage [S1].
*   **Measured Performance:** Scalability depends directly on the size of the final image and indirectly on the size of the underlying dataset [S4, unofficial]. It scales well with increasing image resolutions because only complete pixels are transmitted [S4, unofficial].
*   **Strengths:**
    *   Avoids replicated ray casting costs for shared pixels without extra synchronization overhead [S3, unofficial].
    *   Instantly compatible with all serial rendering algorithms because it executes the full graphics pipeline in each processor [S4, unofficial].
    *   Simpler implementation compared to dynamic partitioning methods [S3, unofficial].
*   **Limitations:**
    *   Does not guarantee load balance [S1].
    *   Replicated cell loading increases memory and communication costs [S1].
    *   Scalability is limited in distributed memory systems due to data redistribution overhead [S4, unofficial].
*   **When to Use:** Suitable for shared-memory architectures where data redistribution is cheap, or when compatibility with existing serial rendering algorithms is a priority [S4, unofficial]. Not ideal for distributed systems with high communication latency or highly uneven data distributions [S1][S4, unofficial].

## Background
Static Contiguous Image-Based Partitioning, also known as static image-based partitioning or image-based partitioning, is a parallelization strategy for volume rendering that divides the image into contiguous blocks assigned to processors [S3, S4, unofficial]. It was proposed as a simpler and more effective solution than dynamic image-based partitioning (e.g., Nieh and Levoy) to avoid the cost of replicated ray casting associated with pixel sharing in adaptive image sampling [S3, unofficial]. The method is compatible with standard APIs like OpenGL, which lack high-performance access to intermediate rendering results, making sort-middle impractical [S4, unofficial]. It has been used in various parallel volume rendering schemes, including those for unstructured volume data [S1]. The underlying sequential renderer can be the Scanline Z-Buffer algorithm, which requires no connectivity information, only a set of unconnected polygons [S5, unofficial].
