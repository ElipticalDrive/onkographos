# Static Contiguous Image-Based Partitioning

Also called: Image Order Volume Rendering, Image-order distribution, Sort-first

## Overview
Static Contiguous Image-Based Partitioning is a parallel volume rendering strategy that divides the final image plane into contiguous blocks (tiles) and assigns each block to a specific processor, which then executes the complete rendering pipeline for that region [S1][S3, unofficial]. It solves the load-balancing and communication overhead issues inherent in adaptive sampling methods by ensuring that pixel-sharing costs are eliminated through static assignment and specific traversal orders [S2, unofficial]. Unlike dynamic image-based partitioning which delays evaluation to handle shared pixels, this method avoids such costs entirely without extra synchronization overhead [S2, unofficial].

## How it works
**Inputs:** Volume dataset, camera parameters, number of processors $P$, image resolution.
**Outputs:** Final composite image.

**Data Structures:**
*   **Image Block:** A contiguous rectangular region of the image assigned to one processor.
*   **Sample Region:** A square sub-region of the image used for adaptive sampling, with side length $I_{max}$ pixels [S2, unofficial].
*   **Volume Data:** Distributed across processors. Each processor stores only the sub-volume data contributing to its assigned image block [S3, unofficial].

**Steps:**
1.  **Data Distribution:**
    *   Volume data is initially distributed arbitrarily across all $P$ processors [S3, unofficial].
    *   Each processor determines which cells contribute to its assigned image block (ownership) [S3, unofficial].
    *   Processors retain their responsible data and send all other data to the processors in charge of the corresponding image blocks [S3, unofficial].
    *   *Note:* This redistribution may occur at the beginning of every frame computation [S3, unofficial].

2.  **Image Partitioning:**
    *   The image is conceptually divided into small square sample regions of size $I_{max} \times I_{max}$ pixels [S2, unofficial].
    *   These sample regions are grouped into $P$ contiguous large blocks, ensuring roughly equal amounts of work per processor [S2, unofficial].

3.  **Rendering (Per Processor):**
    *   Each processor loads the cells contributing to its assigned block [S1].
    *   The processor calculates sample regions in scanline order from top to bottom [S2, unofficial].
    *   **Handling Shared Pixels:** Pixels shared between adjacent image blocks are located only in the square sample regions at the top and bottom of each block [S2, unofficial].
        *   Each processor calculates shared pixels in the **top** sample regions of its block [S2, unofficial].
        *   For the **bottom** sample regions, the shared pixel values are already available in shared memory (or from lower neighboring processors), so they are not recalculated [S2, unofficial].
    *   The processor applies the full rendering pipeline (ray casting/compositing) to its block [S3, unofficial].

4.  **Compositing:**
    *   The sub-images generated by all processors are collected onto one processor (or merged) to produce the final image [S1].

**Pseudocode:**
```python
def static_contiguous_partitioning(volume_data, camera, P, I_max):
    # Step 1: Data Redistribution
    # Determine ownership of volume cells for each processor's image block
    # Send non-owned cells to responsible processors

    # Step 2: Partition Image
    # Divide image into P contiguous blocks
    image_blocks = partition_image_into_contiguous_blocks(P, camera.resolution)

    # Step 3: Render Local Block
    block = image_blocks[my_processor_id]
    sub_image = render_block(local_volume, camera, block, I_max)

    # Step 4: Collect Results
    # In a distributed system, this might be a collective operation
    final_image = collect_sub_images(sub_images_from_all_processors)
    return final_image

def render_block(local_volume, camera, block, I_max):
    sub_image = empty_image_of_size(block.height, block.width)
    
    # Process sample regions in scanline order (top to bottom)
    for y in range(block.top, block.bottom, I_max):
        for x in range(block.left, block.right, I_max):
            # Determine if this is a shared region
            is_top_shared = (y == block.top)
            is_bottom_shared = (y + I_max >= block.bottom)
            
            # Calculate sample region
            sample_region = get_sample_region(x, y, I_max)
            
            # Adaptive sampling logic
            # If top shared, calculate shared pixels
            if is_top_shared:
                render_shared_pixels_top(sample_region, local_volume, camera)
            
            # Render non-shared pixels
            render_non_shared_pixels(sample_region, local_volume, camera)
            
            # If bottom shared, pixels are already available from lower neighbor
            # No action needed for bottom shared pixels
            pass 
            
    return sub_image
```

**Parameters:**
*   $I_{max}$: Side length of square sample regions in pixels. Typical value not given in sources.
*   $P$: Number of processors.

**Edge Cases and Pitfalls:**
*   **Load Imbalance:** Image order does not guarantee equal cell distribution. If one tile contains more cells, its processor performs more work [S1]. Uneven work distribution also occurs if one processor owns larger cells or if the camera view focuses on a region owned by one processor [S1].
*   **Replicated Loading:** Cells covering more than one tile result in replicated loading of those cells across multiple processors [S1].
*   **Scalability Limits:** In distributed memory systems, as $P$ increases, the image space grows into too many pieces, causing data redistribution and boundary data redundancy to become serious scalability limitations [S3, unofficial].
*   **Coherence Break:** In real-time volume rendering, user interaction causes sudden scene changes that break per-frame coherence, preventing the use of retained-mode optimizations [S3, unofficial].

## Subtopics

### Hybrid Partitioning Parallel Ray Casting
A parallel volume rendering algorithm for shared-memory MIMD architectures (e.g., SGI Power Challenge) that combines object-based partitioning for boundary cell projection and image-based partitioning for ray traversal to achieve load balancing [S2, unofficial]. It uses static contiguous object-based partitioning to divide the volume into subsets with an equal number of boundary cells, allowing each processor to project boundary cells and create partial projection buffers [S2, unofficial]. These buffers define bounded intervals for ray integrals. The image is then divided into large blocks of consecutive scanlines (static contiguous image-based partitioning), where each processor performs ray integrals only within the viable pixels and bounded intervals of its block [S2, unofficial]. This approach avoids the cost of replicated ray casting for shared pixels by leveraging the projection buffer information to skip empty scanlines and restrict calculations [S2, unofficial]. However, ray-dependent optimizations like adaptive image sampling require extra attention to avoid replicated costs at shared pixel boundaries [S2, unofficial].

## Operating characteristics
**Time and Memory Complexity:**
*   Scalability depends directly on the size of the final image and indirectly on the size of the underlying dataset [S3, unofficial].
*   Data redistribution cost depends on the volume size and the number of processors [S3, unofficial].

**Measured Performance and Scaling:**
*   Sort-first systems scale well with increasing image resolutions because only complete pixels are transmitted to the frame buffer [S3, unofficial].
*   In shared memory architectures, it is considered an optimal setting with straightforward implementations, but scalability is restricted by built-in memory size [S3, unofficial].
*   In distributed memory systems, scalability is limited by data redistribution and boundary data redundancy as the number of processors increases [S3, unofficial].

**Strengths and Limitations:**
*   **Strengths:** Instantly compatible with all serial rendering algorithms because it executes the full graphics pipeline in each processor, lowering porting effort [S3, unofficial]. Completely avoids the cost of replicated ray casting associated with pixel sharing in adaptive sampling without extra synchronization overhead [S2, unofficial].
*   **Limitations:** Does not guarantee equal cell distribution, leading to potential load imbalance [S1]. Replicated loading of cells spanning multiple tiles [S1]. Per-frame coherence optimizations are ineffective in interactive real-time volume rendering due to sudden scene changes [S3, unofficial].

**When to Use:**
*   When using shared-memory architectures where memory bandwidth is sufficient.
*   When compatibility with existing serial rendering algorithms is a priority.
*   When the image resolution is high, leveraging the scalability of pixel-based transmission.

**When Not to Use:**
*   In distributed memory systems with a very large number of processors, due to redistribution overhead.
*   When the camera is inside the volume, as static partitioning may fail to balance load (as seen in related graph-based methods [S1]).
*   When per-frame coherence is expected to be high and scene changes are minimal (though this is rare in interactive volume rendering).

## Background
Static Contiguous Image-Based Partitioning is a form of sort-first rendering, which follows an image-order distribution approach [S3, unofficial]. It was proposed as a simpler and more effective solution than dynamic image-based partitioning (such as Nieh and Levoy's method) for handling pixel sharing costs in adaptive sampling [S2, unofficial]. The method leverages the static nature of contiguous blocks to eliminate synchronization overhead for shared pixels [S2, unofficial]. It is compatible with various serial rendering optimizations, including early ray termination and adaptive depth sampling [S2, unofficial].
