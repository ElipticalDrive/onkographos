# Interaction Render Scale Damping

Also called: Dynamic Resolution Damping, Interaction-aware Resolution Scaling

## Overview
Interaction Render Scale Damping dynamically reduces the render resolution during camera interaction to maintain frame rate, then restores it after interaction stops [S1, unofficial]. It temporarily overrides the user's intended render scale with a lower multiplier during interaction, reverting to the target scale after a fixed delay [S1, unofficial].

## How it works
**Inputs and Outputs:**
- **Inputs:** Interaction state (active/inactive), timestamp of the last move event, target render scale (`userRenderScale`), interaction render scale (`interactionRenderScale`), and interaction hold duration (`INTERACTION_HOLD_MS`) [S1, unofficial].
- **Outputs:** Effective render scale multiplier applied to the rendering engine [G].

**Data Structures:**
- `interactionRenderScale`: Render scale multiplier during interaction, range $[0, 1]$. A value of $0$ disables scaling [S1, unofficial].
- `userRenderScale`: User-intended render scale, temporarily overridden during interaction [S1, unofficial].
- `lastMoveTime`: Timestamp recording the most recent user interaction event [S1, unofficial].
- `INTERACTION_HOLD_MS`: Constant defining the delay before resolution is restored (e.g., $200$ ms) [S1, unofficial].

**Algorithm Steps:**
1. Detect interaction state. [G]
2. If interaction is active, update `lastMoveTime` to the current time and apply `interactionRenderScale` [S1, unofficial].
3. If interaction is inactive, calculate elapsed time since `lastMoveTime` [G].
4. If elapsed time $<$ `INTERACTION_HOLD_MS`, continue using `interactionRenderScale` [S1, unofficial].
5. Otherwise, revert the effective render scale to `userRenderScale` [S1, unofficial].

**Formulas:**
The effective render scale $S_{\text{eff}}$ at current time $t_{\text{curr}}$ is defined as:
$$
S_{\text{eff}} = \begin{cases} 
S_{\text{int}} & \text{if } t_{\text{curr}} - t_{\text{last}} < T_{\text{hold}} \\
S_{\text{user}} & \text{otherwise}
\end{cases}
$$
where $S_{\text{int}}$ is `interactionRenderScale`, $S_{\text{user}}$ is `userRenderScale`, $t_{\text{last}}$ is `lastMoveTime`, and $T_{\text{hold}}$ is `INTERACTION_HOLD_MS` [S1, unofficial][G].

**Pseudocode:**
```python
INTERACTION_HOLD_MS = 200
interactionRenderScale = 0.25
userRenderScale = 1.0
lastMoveTime = 0

def get_effective_render_scale(current_time, interaction_active):
    if interaction_active:
        lastMoveTime = current_time
        return interactionRenderScale
    else:
        if (current_time - lastMoveTime) >= INTERACTION_HOLD_MS:
            return userRenderScale
        else:
            return interactionRenderScale
```

**Parameters:**
- `interactionRenderScale`: Typical value $0.25$ [S1, unofficial].
- `INTERACTION_HOLD_MS`: Typical value $200$ ms [S1, unofficial].

**Edge Cases:**
- If `interactionRenderScale` is set to $0$, scaling is disabled and the renderer may drop frames during interaction [S1, unofficial].
- Rapid, intermittent interactions may cause the resolution to oscillate if the hold time is too short [G].

## Subtopics

## Operating characteristics
- **Time Complexity:** $O(1)$ for the scale determination logic [G].
- **Memory Complexity:** $O(1)$ additional memory for state tracking [G].
- **Strengths:** Maintains interactive frame rates during navigation; seamless transition back to high quality [G].
- **Limitations:** Requires careful tuning of `INTERACTION_HOLD_MS` to avoid visual popping [G]; does not reduce computational load of volume traversal itself, only the final compositing/resolution [G].

## Background
The technique is documented in the context of web-based, out-of-core volume rendering engines targeting multi-GB datasets [S1, unofficial]. It addresses the latency issues inherent in high-resolution volume rendering during interactive exploration [S1, unofficial].
