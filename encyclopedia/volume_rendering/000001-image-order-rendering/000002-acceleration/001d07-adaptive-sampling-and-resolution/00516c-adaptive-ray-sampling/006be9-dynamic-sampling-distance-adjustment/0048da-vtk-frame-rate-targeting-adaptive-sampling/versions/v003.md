# VTK Frame Rate Targeting & Adaptive Sampling

Also called: AutoAdjustSampleDistances, SetDesiredUpdateRate

## Overview
This method maintains a target frame rate in VTK volume rendering by dynamically adjusting the sampling distance per frame based on the allocated render time budget [S1]. It differs from spatial adaptive methods by using a global temporal constraint rather than local gradient or error metrics to modulate sampling density [S1].

## How it works
**Inputs and Outputs:**
* Input: Desired frame rate target ($F_{target}$), scene props, volume data [S1].
* Output: Adjusted sampling distance per mapper, yielding a rendered image at or above $F_{target}$ [S1].

**Data Structures:**
* `vtkExternalOpenGLRenderWindow`: Manages the render loop and time budgeting [S1].
* `vtkOpenGLGPUVolumeRayCastMapper`: Contains the `AutoAdjustSampleDistances` flag and the current sampling distance parameter [S1].

**Steps:**
1. Set Target: Call `SetDesiredUpdateRate(F_{target})` on the `vtkExternalOpenGLRenderWindow` instance [S1].
2. Calculate Budget: VTK calculates the per-frame time budget $T_{budget} = 1 / F_{target}$ [G].
3. Allocate Time: The total $T_{budget}$ is divided among all props in the scene, reducing each prop's render time as more props are added [S1].
4. Adapt Sampling: For each `vtkOpenGLGPUVolumeRayCastMapper` with `AutoAdjustSampleDistances` enabled, the mapper automatically adjusts its sampling distance to complete rendering within its allocated frame time [S1].
5. Render: Execute volume ray casting with the adjusted sampling distance [S1].

**Parameters:**
* $F_{target}$: The desired frame rate for the VTK render window [S1]. In VR applications with a 90 fps application target and 3 rendered views (headset left, headset right, screen preview), $F_{target}$ is typically set to 300 fps to account for overhead [S1].
* `AutoAdjustSampleDistances`: Boolean flag on `vtkOpenGLGPUVolumeRayCastMapper` [S1]. Must be enabled for adaptation to occur [S1].

**Edge Cases and Pitfalls:**
* Banding Artifacts: Enforcing a frame rate target causes visible banding artifacts due to reduced sampling quality [S1].
* Close Proximity: Without a target, frame rate drops to 40 fps when the volume is very close to the viewer because more pixels are filled, requiring more rays and higher computational cost [S1].
* Overhead Management: The target must account for multiple views and system overhead; setting it too low may cause instability, while setting it too high may not provide the desired quality [S1].

## Operating characteristics
* Time Complexity: The adaptation logic adds negligible overhead; the primary cost is volume rendering, which is reduced by increasing sampling distance [S1].
* Memory Complexity: No additional memory structures are required beyond standard VTK render state [S1].
* Performance: With a 300 fps target, frame rates often exceed 100 fps [S1]. Without a target, frame rates drop to 40–50 fps for CT data at 0.5 m distance [S1].
* Strengths: Guarantees a minimum frame rate, preventing uncomfortable latency in interactive VR applications [S1].
* Limitations: Image quality degrades (banding) as sampling distance increases to meet time constraints [S1].

## Background
This technique is part of the Visualization Toolkit (VTK) library, specifically within its OpenGL rendering backend [S1]. It was documented in research regarding virtual interaction and visualization of 3D medical imaging data using VTK and Unity [S1]. The method addresses the challenge of maintaining interactive frame rates in VR when rendering complex volume data that varies in computational cost based on camera distance and scene complexity [S1].
