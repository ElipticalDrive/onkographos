# FBSlabs

Also called: Fixed Budget Slabs, Front-to-back Slices, Front-to-back Slabs

## Overview
FBSlabs is a progressive ray casting technique that refines a low-resolution volume rendering into high resolution by splitting each ray into segments of fixed length (slabs) and rendering them in front-to-back order over subsequent frames [S1, unofficial]. It addresses the problem of interactive volume rendering on mobile and low-performance devices by distributing the computational workload of high-resolution ray casting across multiple frames, ensuring a constant frame rate during user interaction [S1, unofficial]. Unlike sibling methods such as [STiles](9724-stiles.md), which sort screen-space tiles by cost, FBSlabs distributes work uniformly across all pixels per frame, making it suitable for hardware lacking compute shaders [S1, unofficial].

## How it works
FBSlabs operates by maintaining two render targets: a low-resolution texture ($T_{low}$) for the unrendered or partially rendered volume, and a high-resolution texture ($T_{high}$) for the progressively refined front portion. The method relies on orthographic projection to ensure slabs remain piecewise planar [S1, unofficial].

### Inputs and Outputs
*   **Input:** Volume dataset, proxy geometry bounding the volume, viewport dimensions ($V_w \times V_h$), camera parameters (orthographic).
*   **Output:** Composite image displayed to the user, composed of $T_{high}$ overlaid on $T_{low}$.

### Data Structures
1.  **$T_{low}$**: A 2D texture storing the color of the volume rendered at low resolution. It acts as the background for the high-resolution overlay.
2.  **$T_{high}$**: A 2D texture storing the accumulated color of the high-resolution ray casting. It is cleared at the start of the progressive phase and updated via front-to-back alpha blending.
3.  **Frame Counter**: An integer tracking the number of frames elapsed since the start of the progressive high-resolution rendering. This determines the starting position of the current slab.

### Parameters
*   **$N$**: The fixed number of ray casting samples performed per frame per ray. The source specifies $N = 40$ [S1, unofficial].
*   **Projection**: Orthographic. Perspective projection causes slabs to become pseudo-spherical as they extend from the proxy geometry, complicating the fixed-thickness assumption [S1, unofficial].

### Algorithm Steps
The algorithm proceeds in two phases: Low-Resolution Initialization and Progressive High-Resolution Refinement.

1.  **Low Resolution Ray Casting (Initialization):**
    During user interaction, perform standard ray casting at low resolution. Store the resulting color in $T_{low}$ [S1, unofficial].

2.  **Progressive High Resolution Ray Casting - Initialization:**
    When interaction ceases, clear $T_{high}$. Place the first sampling position for each ray at the entry point on the proxy geometry bounding the volume model [S1, unofficial].

3.  **Progressive High Resolution Ray Casting - Slab Rendering:**
    For the current frame, iterate over all pixels in the viewport. For each pixel:
    a. Calculate the starting position of the ray segment based on the current frame counter and $N$. Since each slab has a fixed thickness defined by $N$ samples, the start position for frame $f$ is offset by $f \times N$ samples from the entry point [S1, unofficial].
    b. Perform a loop of $N$ samples along the ray segment.
    c. Sample the volume and compute the color contribution.
    d. Composite the resulting color with the previous partial result in $T_{high}$ using front-to-back alpha blending. The blending state must be configured to add color in a front-to-back order [S1, unofficial].

4.  **Progressive High Resolution Ray Casting - Low Res Remainder:**
    Render the remaining part of the volume (from the end of the high-resolution slab to the exit of the proxy geometry) using low-resolution ray casting. Start this rendering at the sample position where the high-resolution step finished. Store the result in $T_{low}$, overwriting the previous low-res data for the unrendered portion [S1, unofficial].

5.  **Progressive High Resolution Ray Casting - Composite:**
    Generate the current image by compositing $T_{high}$ on top of $T_{low}$ using alpha blending. The blending time is negligible [S1, unofficial].

6.  **Iteration:**
    In the next frame, increase the frame counter and resume from Step 3. Continue until sampling positions exceed volume boundaries.

### Termination Condition
The algorithm conservatively approximates the end of ray casting by repeating the iterative process until the computed rays are longer than the diagonal of the volume bounding box. This ensures all rays have exited the proxy geometry [S1, unofficial].

### Pseudocode

```python
# Constants
N_SAMPLES_PER_FRAME = 40
SAMPLE_SPACING = 1.0  # Assumed constant spacing for simplicity; in practice, determined by volume resolution and camera

# Global State
frame_counter = 0
t_high = Clear2DTexture() # High-res accumulated color
t_low = 2DTexture()       # Low-res background

def init_low_res():
    """Step 1: Render initial low-res image during interaction."""
    t_low = RayCastLowRes(volume, camera, resolution=LOW_RES)

def start_progressive():
    """Step 2: Initialize high-res texture and frame counter."""
    global frame_counter
    frame_counter = 0
    t_high = Clear2DTexture()

def render_frame():
    """Steps 3-6: Render one frame of progressive refinement."""
    global frame_counter
    
    # Step 3: Render high-res slab
    # Calculate start offset for this frame's slab
    start_offset_samples = frame_counter * N_SAMPLES_PER_FRAME
    start_position = ray_entry_point + (start_offset_samples * SAMPLE_SPACING * ray_direction)
    
    # Render slab for all pixels
    # Note: In a shader, this loop runs per pixel.
    # We accumulate into t_high using front-to-back blending.
    RenderHighResSlab(t_high, volume, camera, 
                      start_position=start_position, 
                      num_samples=N_SAMPLES_PER_FRAME)
    
    # Step 4: Render remaining low-res part
    # The high-res ray casting stopped at:
    end_position = start_position + (N_SAMPLES_PER_FRAME * SAMPLE_SPACING * ray_direction)
    
    # Render the rest of the ray at low res into t_low
    # This overwrites the low-res data for the portion now covered by high-res
    RenderLowResRemainder(t_low, volume, camera, 
                          start_position=end_position)
    
    # Step 5: Composite
    # Display t_high blended over t_low
    DisplayComposite(t_high, t_low)
    
    # Step 6: Increment
    frame_counter += 1

def RenderHighResSlab(target_texture, volume, camera, start_position, num_samples):
    """
    Renders a fixed number of samples along each ray, starting from start_position.
    Accumulates result into target_texture using front-to-back alpha blending.
    """
    for each pixel (x, y) in viewport:
        ray = GetRay(camera, x, y)
        current_pos = start_position + (x, y) offset # Adjusted for pixel ray origin
        
        # Initialize accumulation for this pixel if not already present in target_texture
        # Or read existing value from target_texture for blending
        acc_color = ReadPixel(target_texture, x, y)
        acc_alpha = 0.0
        
        for i from 0 to num_samples - 1:
            sample_pos = current_pos + (i * SAMPLE_SPACING * ray.direction)
            
            # Check if sample is within proxy geometry bounds
            if not IsInsideProxy(sample_pos):
                break
                
            color, alpha = SampleVolume(volume, sample_pos)
            
            # Front-to-back blending
            # C_new = C_old + C_sample * (1 - A_old)
            # A_new = A_old + alpha * (1 - A_old)
            
            weight = alpha * (1.0 - acc_alpha)
            acc_color = acc_color + color * weight
            acc_alpha = acc_alpha + weight
            
            # Early termination per slab (local to this slab)
            if acc_alpha >= 1.0:
                break
        
        WritePixel(target_texture, x, y, acc_color, acc_alpha)

def RenderLowResRemainder(target_texture, volume, camera, start_position):
    """
    Renders the rest of the ray from start_position to exit at low resolution.
    Overwrites target_texture.
    """
    for each pixel (x, y) in viewport:
        ray = GetRay(camera, x, y)
        current_pos = start_position + (x, y) offset
        
        acc_color = vec3(0.0)
        acc_alpha = 0.0
        
        # Low-res sampling loop (fewer samples or larger step)
        while current_pos is inside proxy geometry and acc_alpha < 1.0:
            color, alpha = SampleVolumeLowRes(volume, current_pos)
            
            weight = alpha * (1.0 - acc_alpha)
            acc_color = acc_color + color * weight
            acc_alpha = acc_alpha + weight
            
            current_pos += LOW_RES_STEP * ray.direction
            
        WritePixel(target_texture, x, y, acc_color, acc_alpha)
```

### Edge Cases and Pitfalls
*   **Resolution Mismatch:** Compositing $T_{high}$ over $T_{low}$ mixes viewport resolutions. Rays in the low-resolution image do not perfectly match rays in the high-resolution image, and upsampling the low-resolution image requires interpolation, which can result in slight visual artifacts [S1, unofficial].
*   **Global Early Ray Termination (ERT):** Implementing global ERT (stopping ray casting for a pixel entirely if it becomes opaque) requires an extra pass to copy accumulated opacity to a queryable texture. This extra pass incurs a time penalty larger than the benefits of ERT. Therefore, only per-slab ERT is effective [S1, unofficial].
*   **Termination Approximation:** The termination condition (ray length > bounding box diagonal) is conservative. It may continue rendering for a few frames after the volume is fully traversed to ensure all rays have exited [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The maximum number of samples per frame is $O(V_w \times V_h \times N)$, where $V_w \times V_h$ is the viewport pixel count and $N$ is the fixed samples per ray [S1, unofficial].
*   **Memory Complexity:** Requires storage for two 2D textures ($T_{low}$ and $T_{high}$) and a frame counter. No complex data structures like tile sorting maps are needed [S1, unofficial].
*   **Performance:** Experiments show average completion times under 1 second for tested models [S1, unofficial]. The blending time is negligible [S1, unofficial].
*   **Convergence:** FBSlabs shows a less uniform slope in perceptual convergence compared to tile-based methods. It converges quickly because the front part of the model covers most of the image, but continues executing for several frames after approaching ground truth to render the back part, which has smaller visual impact [S1, unofficial].
*   **Strengths:** High interactivity rate; good average completion times; simple implementation; no need for compute shaders [S1, unofficial].
*   **Limitations:** Perceptual seams between low-resolution and high-resolution models can be more perceivable than in tile-based methods; non-uniform convergence; potential artifacts from resolution mismatch [S1, unofficial].
*   **When to use:** Recommended for less powerful devices that do not provide compute shaders (available from OpenGL ES 3.1) or platforms like WebGL that do not support modern features such as compute shaders [S1, unofficial]. Also suitable for older devices that do not provide 3D textures by using a scheme based on flat 3D textures or stacked 2D textures [S1, unofficial].
*   **When not to use:** When uniform perceptual convergence is critical, or when hardware supports compute shaders and tile-based sorting (STiles) which offers faster completion and smoother transitions [S1, unofficial].

## Background
FBSlabs (Front-to-back Slabs) was proposed in the context of mobile volume rendering, specifically for medical data visualization on devices with limited computational power. The method was introduced alongside "STiles" (Sorted Tiles) as part of a multiresolution architecture aimed at achieving interactive rendering of volumetric models [S1, unofficial]. The technique leverages the fact that in medical imaging, orthographic projection is commonly used, allowing slabs to remain piecewise planar [S1, unofficial].
