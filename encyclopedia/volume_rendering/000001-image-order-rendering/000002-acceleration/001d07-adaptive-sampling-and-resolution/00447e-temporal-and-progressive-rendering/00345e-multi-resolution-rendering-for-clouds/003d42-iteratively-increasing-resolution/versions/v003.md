# Iteratively Increasing Resolution

Also called: Multi-resolution rendering strategy

## Overview
Iteratively Increasing Resolution is a rendering strategy that reduces computation time by starting at a low resolution and gradually increasing it to the target final resolution [S1, unofficial]. It solves the problem of expensive high-resolution ray-surface intersection tests by deferring them until necessary, using cone-tracing to guarantee that no surface points are skipped during the resolution transition [S1, unofficial].

## How it works
**Inputs:**
- A signed distance function (SDF) or SDF lower estimate (SDFE) $f$ [S1, unofficial].
- Camera parameters (position, direction, resolution) [G].
- Target final resolution $(W_{final}, H_{final})$ [G].
- Initial low resolution $(W_{start}, H_{start})$ [G].

**Outputs:**
- Final rendered image at target resolution [G].
- State textures storing intermediate rendering data (e.g., distance traveled) [S1, unofficial].

**Data Structures:**
- **Ping-Pong Textures:** Two screen-sized textures are used to store the state for each pixel, such as the distance traveled along the ray ($t$) or accumulated color [S1, unofficial]. These are swapped (ping-ponged) between passes [S1, unofficial].
- **State Field:** Each pixel stores the current ray parameter $t$ (distance from origin) where the ray currently stands [S1, unofficial].

**Algorithm Steps:**
1. **Initialization:** Start rendering at the lowest resolution $(W_{start}, H_{start})$ [S1, unofficial]. Initialize state textures with $t=0$ (or the ray origin) [G].
2. **Cone-Tracing Pass:** For each pixel, perform sphere tracing using cone-tracing logic [S1, unofficial]. The ray is advanced by a step size determined by the modified SDFE, bounded by the cone termination condition to ensure no surface is missed when resolution increases [S1, unofficial].
3. **Termination Check:** A pixel is considered complete if it intersects the surface (SDF value $\le 0$) or exceeds a maximum distance [S1, unofficial]. Incomplete pixels retain their current $t$ in the state texture [S1, unofficial].
4. **Resolution Increase:** If the target resolution is not reached, increase the resolution (e.g., double width and height) [S1, unofficial]. The starting position for each new pixel in the higher resolution is always the closest pixel in the previous resolution [S1, unofficial].
5. **Incremental Continuation:** In the next frame (or pass), computation continues from the stored $t$ values [S1, unofficial]. If the camera or scene has not changed, the state is preserved [S1, unofficial].
6. **Repeat:** Steps 2-5 are repeated until the target resolution is achieved [S1, unofficial].

**Cone-Tracing Formula:**
To support resolution increase, cone-tracing ensures that no surface point lies inside the cone defined by the pixel's footprint [S1, unofficial]. The terminating condition for the pixel cone, assuming rectangular pixels, is [S1, unofficial]:

$$ f(o + tv) < \frac{p^2}{\text{width}^2 \text{height}^2} $$

where:
- $o$ is the ray origin (pixel center), $v$ is the ray direction, and $t$ is the distance along the ray [S1, unofficial].
- $p$ is the pixel size in world units (or $1$ for normalized coordinates) [S1, unofficial].
- $\text{width} \cdot \text{height}$ is the total number of pixels in the current resolution [S1, unofficial].
- Let $\alpha = \frac{p^2}{\text{width}^2 \text{height}^2}$ [S1, unofficial].

**Modified SDFE for Safe Travel:**
The condition above can be incorporated into the SDFE to avoid special termination checks [S1, unofficial]. Let $\alpha = \frac{p^2}{\text{width}^2 \text{height}^2}$. The modified one-dimensional SDFE $F(t)$ is [S1, unofficial]:

$$ F(t) = \frac{f(o + tv) - \alpha t}{1 + \alpha} $$

This transformation offsets the surface by a value that increases with distance [S1, unofficial]. The Lipschitz constant of $F$ is bounded by $1 + \alpha$, ensuring stability [S1, unofficial]. This allows the algorithm to approximate the safe travel distance without needing a special termination condition for the cone [S1, unofficial].

**Pseudocode:**
```python
def iteratively_increasing_resolution(sdf, camera, start_res, target_res, max_dist):
    """
    Renders a scene using iteratively increasing resolution with cone-tracing.
    sdf: callable returning SDF value at (x,y,z)
    camera: callable get_ray(x, y) -> (origin, direction)
    start_res: (w, h)
    target_res: (w, h)
    max_dist: maximum ray length to prevent infinite loops
    """
    current_w, current_h = start_res
    # Initialize state textures: 2D arrays storing distance t for each pixel [G]
    state_tex = [[0.0] * current_w for _ in range(current_h)]
    next_state_tex = [[0.0] * current_w for _ in range(current_h)]
    
    while current_w <= target_res[0] and current_h <= target_res[1]:
        # Calculate alpha for current resolution [S1, unofficial]
        pixel_size = 1.0  # Normalized pixel size [G]
        alpha = (pixel_size ** 2) / (current_w ** 2 * current_h ** 2)
        
        for y in range(current_h):
            for x in range(current_w):
                t = state_tex[y][x]
                
                # Skip if already completed or exceeded max distance [G]
                if t >= max_dist:
                    next_state_tex[y][x] = t
                    continue
                
                ray_o, ray_d = camera.get_ray(x, y)
                safe_t = t
                
                while safe_t < max_dist:
                    pos = (ray_o[0] + safe_t * ray_d[0],
                           ray_o[1] + safe_t * ray_d[1],
                           ray_o[2] + safe_t * ray_d[2])
                    f_val = sdf(pos)
                    
                    # Modified SDFE value for cone-tracing step size [S1, unofficial]
                    f_mod = (f_val - alpha * safe_t) / (1.0 + alpha)
                    
                    if f_mod <= 0:
                        # Surface hit or cone boundary reached [S1, unofficial]
                        break
                    
                    # Step size is the safe travel distance approximated by F(t) [S1, unofficial]
                    step_size = f_mod
                    safe_t += step_size
                    
                    # Prevent infinite loops on flat/parallel surfaces [G]
                    if step_size < 1e-6:
                        break
                
                next_state_tex[y][x] = safe_t
        
        # Swap textures [S1, unofficial]
        state_tex, next_state_tex = next_state_tex, state_tex
        
        # Increase resolution [S1, unofficial]
        current_w *= 2
        current_h *= 2
        
        # Resize state textures to new resolution using nearest-neighbor mapping [G]
        new_state_tex = [[0.0] * current_w for _ in range(current_h)]
        for y in range(current_h):
            for x in range(current_w):
                src_y = min(y // 2, current_h // 2 - 1)
                src_x = min(x // 2, current_w // 2 - 1)
                new_state_tex[y][x] = state_tex[src_y][src_x]
        state_tex = new_state_tex
        
        if current_w > target_res[0] or current_h > target_res[1]:
            break
```

**Edge Cases and Pitfalls:**
- **Precision:** The transformation $F(t)$ offsets the surface by a value that increases with distance [S1, unofficial]. Floating-point precision errors may accumulate over many steps [G].
- **Boundaries:** The cone-tracing condition assumes rectangular pixels [S1, unofficial]. Non-rectangular pixels or anisotropic scaling may require adjustment of $\alpha$ [G].
- **Degenerate Input:** If the SDF is not a valid lower estimate (Lipschitz constant $> 1$), the sphere tracing may overstep [S1, unofficial]. The source assumes $\text{Lip } f \le 1$ [S1, unofficial].

## Subtopics

### Single-scale Training and Multi-scale Testing Protocol
A training and evaluation protocol designed to simulate zoom-in effects and test anti-aliasing performance across resolutions [S2, unofficial]. It trains a model at a single downsampled resolution and renders at multiple higher scales [S2, unofficial]. Steps: 1) Define dataset's default resolution (e.g., 1352×1014) as full resolution baseline [S2, unofficial]. 2) Downsample training data by a fixed factor (e.g., 4×) and train exclusively on this lower resolution [S2, unofficial]. 3) Evaluate rendering quality at progressively higher resolutions (1×, 2×, and 4× relative to training resolution) [S2, unofficial]. 4) When comparing against baselines like Mip-Splatting, integrate the baseline into the pipeline and ensure consistency in maximum sampling frequency computation between both methods [S2, unofficial].

## Operating characteristics
- **Time Complexity:** Reduces total render time by performing most of the ray-surface intersection work at lower resolutions [S1, unofficial]. The cost is proportional to the sum of pixel counts across all resolution levels, which is less than rendering at full resolution from the start [S1, unofficial].
- **Memory Complexity:** Requires storage for state textures (distance traveled) at the current resolution [S1, unofficial]. Ping-ponging two textures doubles this requirement [S1, unofficial].
- **Measured Performance:** Implemented in GLSL with C++ test application [S1, unofficial]. Used with relaxed and enhanced sphere tracing [S1, unofficial]. Showed reduced render times for 3D fractals and SDF scenes [S1, unofficial].
- **Strengths:** High-quality rendering for stationary scenes; real-time responsiveness when camera/scene changes (by restarting or incrementing) [S1, unofficial]. General applicability to any sphere tracing variant [S1, unofficial].
- **Limitations:** Requires multiple passes or frames to complete [S1, unofficial]. Not suitable for highly dynamic scenes where state cannot be preserved [S1, unofficial]. Precision issues with the modified SDFE transformation over long distances [G].
- **When to Use:** Static or slowly changing scenes where high resolution is needed but initial low-res passes can identify complex areas [S1, unofficial].
- **When Not to Use:** Highly dynamic scenes where state preservation is not feasible [S1, unofficial]. Scenes with very thin structures that might be missed by coarse initial passes (though cone-tracing mitigates this) [G].

## Background
Originated from work on accelerating sphere tracing, introduced by Csaba Bálint and Gábor Valasek in 2018 [S1, unofficial]. Sphere tracing was introduced by Hart in 1994 [S1, unofficial]. The method builds on improvements by Keinert et al. [S1, unofficial]. It is used in real-time rendering of SDF representations, such as 3D fractals, where traditional triangle-based engines are inefficient [S1, unofficial].
