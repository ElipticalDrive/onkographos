# Orthogonal BSP Tree Construction

Also called: BSP tree conversion, Orthogonal BSP

## Overview
Orthogonal BSP Tree Construction converts a set of arbitrarily positioned and sized grown boxes into an orthogonal Binary Space Partitioning (BSP) tree where every splitting plane is object-aligned [S1]. This conversion solves the problem of non-trivial visibility sorting inherent in adaptive partitioning, where arbitrary box positions and potential cyclic ordering from specific viewpoints prevent efficient rendering order determination [S1]. By enforcing object-aligned splitting planes, the method enables trivial visibility sorting for 3D texture rendering [S1]. It sets itself apart from its parent method, [Growing Boxes Partitioning](1065-growing-boxes-partitioning.md), by transforming the adaptive box set into a hierarchical structure suitable for standard ray traversal, and from its child, [K-D Tree Hierarchy Construction](2300-k-d-tree-hierarchy-construction.md), by using object-aligned planes rather than axis-aligned splitting planes that are view-independent [S1].

## How it works
**Inputs:** A list of grown boxes generated by the parent method. Each box has a defined bounding box and a type (uniform, gradient, or other).
**Outputs:** An orthogonal BSP tree where leaf nodes contain exactly one box (either an original grown box or a child box generated from splitting) [S1].

**Data Structures:**
*   **BSP Node:** Contains a list of boxes and a bounding box of their union, referred to as the "room" [S1].
*   **Box:** Defined by its bounding box and type. Boxes may have a parent reference.
*   **Hierarchy Constraint:** No box can be both a child and a parent simultaneously; there is only one level of parent-child hierarchy [S1]. Parent boxes reside on non-leaf nodes; rendering uses only leaf nodes [S1].

**Algorithm Steps:**

1.  **Initialization:** Create a root BSP node. Assign all input grown boxes to the root's box list. The root's room is the bounding box of the union of all these boxes [S1].

2.  **Node Splitting:** Recursively split nodes until leaf conditions are met. For a given node:
    a.  Create two child nodes: `front` and `back` [S1].
    b.  **Choose Partitioning Plane:** Select a plane that coincides with the faces of at least two boxes to minimize the number of boxes that are split [S1]. The criterion is to minimize splits [S1].
    c.  **Split Room:** Split the current node's room into two sub-boxes using the chosen plane. Assign these sub-boxes as the rooms for the `front` and `back` children [S1].
    d.  **Distribute Boxes:** Iterate through each box in the current node's list:
        i.  If the box is completely enclosed in the `front` room, move it to the `front` child's box list [S1].
        ii. If the box is completely enclosed in the `back` room, move it to the `back` child's box list [S1].
        iii. If the box is cut by the partitioning plane:
            1.  Create two new boxes by splitting the original box along the plane [S1].
            2.  Place one new box in the `front` child's list and the other in the `back` child's list [S1].
            3.  **Parentage Management:**
                *   If the original box is an original grown box (has no parent), set the original box as the parent of the two new boxes [S1].
                *   Else (the box is already a child), set the parent of the original box as the parent of the two new boxes [S1].
                *   Delete the original box from the current node's list [S1].
    e.  Recursively apply splitting to `front` and `back` children.

3.  **Bottom-Up Merging:** After the initial split phase, reduce the BSP tree by merging child nodes to control the number of leaf nodes [S1]. Merge `front` and `back` children if any of the following conditions are true:
    a.  Both children contain uniform boxes, and the merged box (union of the two) is still uniform [S1].
    b.  Both children contain "other" boxes or both contain "gradient" boxes [S1].
    c.  One of the boxes is tiny or very thin, defined as having a size along one axis smaller than a threshold [S1].
    d.  **Merge Consequence:** If two child nodes being merged have different parent boxes, delete those parent boxes, and all their children become parentless (i.e., they become new root-level boxes for the next merge consideration or remain as independent leaves depending on implementation context, but effectively they lose their specific parent link) [S1]. The type of the resulting merged box is redetermined according to the enclosed voxel properties [S1].

**Texture Sharing:**
Child boxes share the texture of their parent with their siblings to avoid replicating texels along boundaries, which would increase memory requirements [S1].

## Subtopics

### [K-D Tree Hierarchy Construction](2300-k-d-tree-hierarchy-construction.md)
K-D Tree Hierarchy Construction is a method for building a spatial partitioning structure to accelerate volume rendering by grouping polygons (or volumetric primitives) into a binary tree. It solves the problem of efficiently determining which primitives contribute to a pixel without explicit clipping, by storing polygon IDs in a prefix-order traversal array. It sets itself apart from its parent method, [Orthogonal BSP Tree Construction](1134-orthogonal-bsp-tree-construction.md), by using a standard k-d tree structure where splitting planes are orthogonal to coordinate axes, enabling trivial visibility sorting for 3D texture rendering. Unlike fixed viewpoint partitioning, this method is view-independent, making it suitable for animation sequences where the viewpoint changes.

## Operating characteristics
**Time Complexity:** Not given in the sources.
**Memory Complexity:** Not given in the sources.
**Performance:** The total number of boxes at the leaf nodes after splitting can be significantly greater than the total of the original grown boxes, necessitating the bottom-up merging operation to reduce the tree size [S1].
**Strengths:** Enables trivial visibility sorting for 3D texture rendering by converting arbitrary grown boxes into an orthogonal BSP tree [S1]. The magnitude of the box set remains comparable to the original set after conversion [S1].
**Limitations:** The splitting process can significantly increase the number of leaf nodes before merging [S1]. Texture sharing is required to manage memory, implying a dependency on parent-child texture access patterns [S1].
**When to use:** When adaptive partitioning produces arbitrary boxes that prevent trivial visibility sorting, and an orthogonal BSP structure is desired for rendering acceleration [S1].
**When not to use:** When view-independent partitioning is preferred over object-aligned splitting, or when the overhead of managing parent-child texture sharing is prohibitive [S1].

## Background
The method was introduced by Mueller et al. in the paper "Empty Space Skipping and Occlusion Clipping for Texture-based Volume Rendering" [S1]. It addresses the limitations of adaptive partitioning where arbitrary box sizes and positions lead to cyclic visibility orders from specific viewpoints, making sorting non-trivial [S1]. The conversion to an orthogonal BSP tree allows the use of standard rendering techniques that rely on a well-defined front-to-back or back-to-front traversal order [S1].
