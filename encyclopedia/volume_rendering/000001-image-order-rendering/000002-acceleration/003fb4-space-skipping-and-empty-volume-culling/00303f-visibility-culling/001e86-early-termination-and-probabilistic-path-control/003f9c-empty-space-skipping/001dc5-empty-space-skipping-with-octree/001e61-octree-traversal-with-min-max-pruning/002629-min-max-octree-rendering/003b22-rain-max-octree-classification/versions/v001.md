# Rain-Max Octree Classification

Also called: Rain-max octree

## Overview
Rain-Max Octree Classification is a method for rendering unclassified scalar volumes (fields with no precomputed opacity) that avoids the expensive preprocessing step required by previous spatial data structure algorithms when the opacity transfer function changes [S1]. It extends block-based entry point determination by replacing block-level min/max values with a min-max octree, allowing ray entry points to be determined at a finer resolution than block granularity, thereby reducing the number of rays intersecting transparent regions [S2, unofficial].

## How it works
**Inputs:**
- Unclassified scalar volume data (e.g., 2-byte samples).
- Opacity transfer function (dynamic).
- Viewing transformation parameters.
- Block size (e.g., $32 \times 32 \times 32$) [S2, unofficial].

**Outputs:**
- Rendered image.
- Updated entry point buffer.

**Data Structures:**
1.  **Min-Max Octree:**
    -   Root node stores min/max of all samples in the block.
    -   Each additional level stores min/max for smaller regions [S2, unofficial].
    -   Classification information is stored as linearized octree bit encoding using hierarchy compression [S2, unofficial].
    -   Layout: Linearized array indexed by `index(node)`.
2.  **Entry Point Buffer:**
    -   Stores block index and an index for the corresponding octree node [S2, unofficial].
3.  **Lookup Table:**
    -   Stores precomputed relative translational offsets for octree nodes.
    -   Size: $8^N$ entries, where $N$ is the octree depth [S2, unofficial].

**Parameters:**
-   $N$: Depth of the octree. Typical value: 3 [S2, unofficial].
-   Block size: $32 \times 32 \times 32$ voxels [S2, unofficial].
-   Sample size: 2 bytes [S2, unofficial].
-   Node storage: 4 bytes per node (2 bytes minimum, 2 bytes maximum) [S2, unofficial].

**Steps:**

1.  **Preprocessing (One-time per volume acquisition):**
    -   Construct the min-max octree. The root node contains the min/max of the entire block. Recursively subdivide blocks into octants, storing the min/max of samples in each sub-region [S2, unofficial].
    -   Compute the node index for every node in the octree using the formula:
        $$ \text{index}(\text{node}) = \sum_{i=0}^{N-1} \text{octanti}(\text{node}) \cdot 8^{N - i - 1} $$
        where $N$ is the depth of the octree and $\text{octanti}(\text{node})$ is the octant of level $i$ where the node is located [S2, unofficial].
    -   Precompute relative translational offsets for all $8^N$ possible node indices and store them in a lookup table [S2, unofficial].

2.  **Ray Setup (Per ray):**
    -   Determine the entry point in the entry point buffer.
    -   Translate the depth value in the entry point buffer by the $t_z$ component of the translation vector plus the sum of the relative offsets of the node in the octree, retrieved from the lookup table using the node index [S2, unofficial].

3.  **Projection (Per block):**
    -   Create a template for every octree level (instead of one block template) [S2, unofficial].
    -   Recursively traverse the hierarchical classification information in back-to-front order [S2, unofficial].
    -   For each node, check if it is non-transparent (based on current classification and min/max values).
    -   If non-transparent, project the appropriate template for that octree level [S2, unofficial].

4.  **Classification Update (On transfer function change):**
    -   Recursively evaluate the summed area table for each octree node [S2, unofficial].
    -   Update the classification information stored as linearized octree bit encoding using hierarchy compression [S2, unofficial].

**Edge Cases and Pitfalls:**
-   If the octree depth does not reach cell level, the initial position of a ray might not be its exact intersection point with the visible volume, leaving some transparent regions processed [S2, unofficial]. A cell invisibility cache can be used to skip these remaining transparent regions at cell level [S2, unofficial].
-   Precision issues may arise if the min/max values are not accurately computed for small regions, leading to incorrect transparency decisions.

## Operating characteristics
-   **Time Complexity:** Not given in the sources.
-   **Memory Complexity:** Low. For a min-max octree of depth 3, storing 4 bytes at each node, the structure requires at most 2340 bytes. Classification information requires 66 bytes. For a block size of $32 \times 32 \times 32$ with 2-byte samples, the total memory requirements increase by approximately 10% [S2, unofficial].
-   **Measured Performance:** Renders a $256^3$ voxel medical data set in three seconds on an SGI Indigo workstation when combined with the shear-warp rendering algorithm [S1]. Octree-based entry point determination provides faster render times compared to block granularity [S2, unofficial].
-   **Strengths:** Avoids expensive preprocessing when the opacity transfer function changes. Provides finer resolution for entry point determination than block-based methods.
-   **Limitations:** If the octree depth is insufficient, some transparent regions may still be processed. Requires precomputation of offsets and classification updates.

## Background
-   **Origin:** Introduced in "Fast Volume Rendering Using a Shear-warp Factorization of The Viewing Transformation" (1995) by [S1] and further detailed in "Efficient Volume Visualization of Large Medical Datasets" (2004) by [S2, unofficial].
-   **History:** Developed to address the limitations of previous algorithms that required expensive preprocessing when the opacity transfer function changed. It extends the shear-warp factorization approach to support unclassified volumes with dynamic classification.
-   **Usage:** Used in medical imaging and scientific visualization for real-time volume rendering of large datasets.
