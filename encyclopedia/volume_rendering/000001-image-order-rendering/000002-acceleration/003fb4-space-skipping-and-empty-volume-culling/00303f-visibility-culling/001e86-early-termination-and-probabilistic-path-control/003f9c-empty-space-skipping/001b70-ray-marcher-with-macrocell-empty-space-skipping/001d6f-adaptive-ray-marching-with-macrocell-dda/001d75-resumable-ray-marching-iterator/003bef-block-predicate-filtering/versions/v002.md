# Block Predicate Filtering

Also called: Affine Arithmetic Block Culling, Predicate-based Block Filtering

## Overview
Block Predicate Filtering is a culling technique that evaluates a user-defined predicate on each grid block using affine arithmetic to determine if the block's domain can possibly contain a zero of the scalar field, skipping blocks that cannot before scalar evaluation [S1, unofficial]. Compared to naive block mask extraction, it filters blocks before scalar evaluation, reducing computation [S1, unofficial]. It builds on [Resumable Ray Marching Iterator](1505-resumable-ray-marching-iterator.md) by providing a coarse-grained filtering mechanism that reduces the number of expensive scalar field evaluations required during ray marching [G].

## How it works
The method operates on a grid decomposed into blocks (macrocells) [S1, unofficial]. For each block, it determines whether the scalar field defined over that block's spatial domain can possibly take the value zero [S1, unofficial]. If the predicate returns `false`, the block is culled entirely, avoiding the cost of evaluating the scalar field and its derivatives within that block [S1, unofficial].

### Inputs and Outputs
- **Input**: A `BoundingBox<T, dim>` representing the spatial domain of a grid block, where `T` is the scalar type (e.g., `float`) and `dim` is the dimensionality (typically 3) [S1, unofficial].
- **Output**: A boolean value `true` if the block may contain zeros (must be processed), `false` if it cannot contain zeros (can be skipped) [S1, unofficial].

### Data Structures
- **`BoundingBox<T, dim>`**: A structure defining the axis-aligned bounds of the block. It contains two arrays, `a` and `b`, of size `dim`, representing the minimum and maximum coordinates for each axis [S1, unofficial].
- **Affine Form (`AF`)**: A representation of an interval with first-order error bounds, used to track uncertainty in arithmetic operations [G]. In the reference implementation, this is `cusvna::AF1<T, 3>`, supporting 3-dimensional affine forms [S1, unofficial].
- **Interval**: A standard interval arithmetic type `cusvna::Interval<T>` used to initialize affine forms from bounds [S1, unofficial].

### Steps
1. **Define Predicate Function**: Create a function `may_contain_zeros` that accepts a `BoundingBox<T, dim>` domain [S1, unofficial].
2. **Convert Bounds to Affine Forms**: For each axis $k \in \{0, \dots, dim-1\}$, convert the block's minimum and maximum bounds `domain.a[k]` and `domain.b[k]` into an affine form [S1, unofficial]. This is done by first creating an interval from the bounds and then initializing the affine form from that interval using `AF::template from_interval<k>(Interval(domain.a[k], domain.b[k]))` [S1, unofficial].
3. **Evaluate Shape Function**: Compute the shape function `shape<T>(x, y, z)` using affine arithmetic operations on the affine forms $x, y, z$ [S1, unofficial].
4. **Check for Possible Zeros**: Evaluate the result of the shape function using the `possibly_zero` predicate [S1, unofficial]. This function checks if the affine form's interval contains zero [G]. Return `true` if `possibly_zero(shape_result)` is true, otherwise return `false` [S1, unofficial].

### Parameters
- **Autotuning Rigor**: The method supports autotuning of kernel parameters with different rigor levels: `ESTIMATE` (~8 seconds on RTX 5090), `MEASURE` (~45 seconds on RTX 5090), and `EXHAUSTIVE` (~85 seconds on RTX 5090) [S1, unofficial].

### Edge Cases and Pitfalls
- **Precision**: Affine arithmetic can suffer from overestimation, potentially leading to false positives (blocks that are kept but do not contain zeros) [G].
- **Domain Boundaries**: The bounding box must accurately represent the block's spatial extent; incorrect bounds lead to incorrect culling decisions [G].
- **Scalar Field Definition**: The `shape` function must be compatible with affine arithmetic; non-affine operations may require approximation or may not be supported directly [G].

## Operating characteristics
- **Time Complexity**: Not given in the sources.
- **Memory Complexity**: Not given in the sources.
- **Measured Performance**: On a benchmark with $N=2048$, predicate-based extraction achieved a speedup factor of approximately $2.1\times$ compared to naive block mask extraction [S1, unofficial].
- **Strengths**: Reduces computation by filtering blocks before expensive scalar evaluations [S1, unofficial].
- **Limitations**: Affine arithmetic can be computationally more expensive than simple interval arithmetic, and overestimation may reduce culling efficiency [G].
- **When to Use**: Use when scalar field evaluation is expensive and many blocks can be safely culled [G].
- **When Not to Use**: Avoid if the scalar field is dense (few empty blocks) or if the shape function involves non-affine operations that are costly to approximate [G].

## Background
Block Predicate Filtering was introduced in the context of GPU-accelerated volume rendering and scalar field processing [S1, unofficial]. It leverages affine arithmetic to provide a robust method for early culling of empty or irrelevant blocks [S1, unofficial]. The technique is implemented in the `cupmb` library, which provides CUDA-based utilities for mesh and volume processing [S1, unofficial].
