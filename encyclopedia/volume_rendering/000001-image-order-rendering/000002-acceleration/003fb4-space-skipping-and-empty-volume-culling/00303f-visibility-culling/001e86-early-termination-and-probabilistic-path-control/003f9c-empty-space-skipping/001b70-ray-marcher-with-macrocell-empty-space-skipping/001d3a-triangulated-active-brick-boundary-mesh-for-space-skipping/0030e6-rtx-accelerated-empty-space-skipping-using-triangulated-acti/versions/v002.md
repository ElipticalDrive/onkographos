# RTX-Accelerated Empty Space Skipping using Triangulated Active Bricks

Also called: Active Brick Classification, Boundary BVH method, Boundary Mesh Method, Ours

## Overview
This method accelerates volume rendering by using RTX-accelerated ray tracing to skip empty space [S1]. It constructs a bounding volume hierarchy (BVH) over the boundary surface between active and inactive macrocells, rather than over all active regions, to determine ray integration intervals [S1]. It differs from [Triangulated Active Brick Boundary Mesh for Space Skipping](1426-triangulated-active-brick-boundary-mesh-for-space-skipping.md) by explicitly leveraging hardware-accelerated BVH traversal and triangle intersection via OptiX/OWL to replace costly software intersection tests, and from Ganter and Manzke's method by replacing the BVH over active brick regions with a BVH over only the boundary, resulting in lower depth complexity and fewer rays [S1].

## How it works
**Inputs:**
- 3D volume texture (scalar field) [S1].
- Transfer function (for active brick classification) [S1].
- Macrocell size $K$ (default 16) [S1].
- Sampling rate $dt$ (fixed step size, default 0.5) [S1].
- Ray origin and direction for each pixel [S1].

**Outputs:**
- Final color for each pixel [S1].

**Data Structures:**
- **Active Brick Mask:** A 3D grid indicating which macrocells contain active data. Generated on the GPU [S1].
- **Boundary Triangle Mesh:** Vertices and indices representing the surface between active and inactive macrocells. Stored in OWL buffers [S1].
- **Acceleration Structure:** `OWLTrianglesGeom` for the triangle mesh and `OWLTrianglesGroup` for the BVH [S1].
- **Volume Texture:** Created in CUDA, passed to OptiX as `OWL_USER_TYPE(cudaTextureObject_t)` [S1].

**Algorithm Steps:**

1. **Active Brick Classification:** Determine which macrocells are active based on the transfer function. This is performed entirely on the GPU [S1].
2. **Boundary Mesh Generation:** Extract the boundary geometry (triangles) between active and inactive macrocells. This replaces the clustering step used in prior works [S1].
3. **BVH Construction:** Build a BVH over the boundary triangle mesh. This is the most expensive part of the update phase [S1].
4. **Ray Tracing for Space Skipping:**
   - Trace a ray from the camera into the scene against the boundary BVH [S1].
   - Use a closest-hit program to retrieve hit distance $t_{hit}$ and triangle orientation (normal vs. ray direction) [S1].
   - If no hit is found, the ray does not traverse any active volume; terminate the ray [S1].
   - If a hit is found:
     - If the triangle is facing (ray is inside the volume), the integration interval is $[0, t_{hit}]$ [S1].
     - If the triangle is not facing (ray enters the volume), set $t_0 = t_{hit}$. Trace the same ray again with $ray.tmin = t_0$ to find the exit distance $t_1$ [S1].
5. **Volume Integration:**
   - Integrate over the interval $[t_0, t_1]$ using fixed step size $dt$ [S1].
   - Sample the 3D texture, compute gradients, and apply transfer functions [S1].
   - Use interleaved sampling to reduce aliasing [S1].
   - Apply early ray termination if the accumulated opacity reaches a threshold [S1].
6. **Iteration:**
   - If the ray has not terminated early, trace another ray from $t_1$ to find the next potential segment to integrate [S1].
   - Repeat until the ray terminates or exits the volume bounds [S1].

**Pseudocode:**

```python
def render_pixel(ray_origin, ray_direction, volume_texture, boundary_bvh, dt=0.5):
    """
    Renders a single pixel using RTX-accelerated empty space skipping.
    """
    color = vec3(0.0)
    alpha = 0.0
    t_current = 0.0
    INFINITY = 1e9

    while alpha < 1.0:
        # Trace ray against boundary BVH to find active regions
        hit = trace_ray(boundary_bvh, ray_origin, ray_direction, t_current, INFINITY)

        if hit is None:
            # No active volume encountered
            break

        t_hit = hit.distance
        # "facing" triangle indicates the ray is inside the volume
        is_facing = dot(hit.normal, ray_direction) < 0.0

        if is_facing:
            # Ray is inside volume, integrate from current position to hit
            t0 = t_current
            t1 = t_hit
        else:
            # Ray enters volume at t_hit
            t0 = t_hit
            # Trace again to find exit
            hit_exit = trace_ray(boundary_bvh, ray_origin, ray_direction, t0, INFINITY)
            if hit_exit is None:
                # Ray exits volume bounds without hitting another boundary
                t1 = INFINITY
            else:
                t1 = hit_exit.distance

        # Integrate over [t0, t1]
        sample_color, sample_alpha = integrate_volume(volume_texture, ray_origin, ray_direction, t0, t1, dt)

        # Composite
        color = color + sample_color * (1.0 - alpha)
        alpha = alpha + sample_alpha * (1.0 - alpha)

        # Update current position for next segment
        t_current = t1

        # Early termination check
        if alpha >= 1.0:
            break

    return color

def integrate_volume(volume_texture, origin, direction, t0, t1, dt):
    """
    Integrates volume along ray segment [t0, t1] with fixed step dt.
    """
    accumulated_color = vec3(0.0)
    accumulated_alpha = 0.0
    t = t0

    while t < t1:
        pos = origin + direction * t
        value = sample_3d_texture(volume_texture, pos)

        # Compute gradient and apply transfer function
        color, alpha = apply_transfer_function(value, pos)

        accumulated_color = accumulated_color + color * (1.0 - accumulated_alpha)
        accumulated_alpha = accumulated_alpha + alpha * (1.0 - accumulated_alpha)

        if accumulated_alpha >= 1.0:
            break

        t += dt

    return accumulated_color, accumulated_alpha
```

**Parameters:**
- **Macrocell size $K$:** Grid resolution for active brick classification. Default is 16. Tested values include 8 and 32 [S1].
- **Sampling rate $dt$:** Fixed step size for volume integration. Value is 0.5, resulting in an average of two samples per cell [S1].

**Edge Cases and Pitfalls:**
- **Timings < 1ms:** Timings less than 1ms are considered unreliable and should be interpreted as "less than one millisecond" [S1].
- **BVH Build Cost:** BVH construction is the biggest cost during data structure update [S1].
- **No Hit:** If the space-skipping ray does not hit any geometry, the ray is terminated immediately as it will not traverse any active volume regions [S1].

## Operating characteristics
**Time and Memory Complexity:**
- The total build time remains within an interactive range, though it varies by dataset; for the LLNL model at $K=16$ it is 6.0ms [S1].
- For the LLNL model with $K=16$, the total build time is 6.0ms, comprising 153µs for active cell classification, 119µs for triangle extraction, and 5.4ms for BVH construction [S1].

**Measured Performance:**
- Tests were conducted at a resolution of 3840 × 2160 pixels [S1].
- **HEPTANE model:** 84 fps (with rebuild) compared to 93 fps for Ganter's method with space skip on [S1]. Base off rebuild is 34 fps [S1].
- **FLOWER model:** 83 fps (with rebuild) compared to 111 fps for Ganter's method with space skip on [S1]. Base off rebuild is 14 fps [S1].
- **DNS (4X) model:** 28 fps (with rebuild) compared to 34 fps for Ganter's method with space skip on [S1]. Base off rebuild is 13 fps [S1].
- **LLNL model:** 32 fps (with rebuild) compared to 41 fps for Ganter's method with space skip on [S1]. Base off rebuild is 8 fps [S1].
- For the LLNL model, the method achieves 40 FPS (render time only, no rebuild) compared to 8 FPS for the base method and 27 FPS for Ganter's method [S1].

**Strengths and Limitations:**
- **Strengths:** Avoids CPU-side clustering, performs active brick classification entirely on the GPU, results in lower depth complexity and fewer/cheaper rays for space skipping [S1]. Maintains interactive rates even when data structure rebuilding is forced every frame [S1].
- **Limitations:** BVH build time is the dominant cost during data structure updates [S1].

**When to Use:**
- Use when interactive performance is required and the volume data changes frequently (requiring frequent BVH rebuilds), as the GPU-native classification and boundary mesh generation are more efficient than CPU-side clustering [S1].

**When Not to Use:**

## Background
**Origin:**
- Based on ideas from Ganter and Manzke (2019) 'An Analysis of Region Clustered BVH Volume Rendering on GPU' and Hadwiger et al. (2017) 'SparseLeap' [S1].

**History and Development:**
- The method modifies prior techniques to reduce overhead [S1]. It builds on the macro-cell/active brick mask concept but replaces the BVH over active brick regions with a BVH over only the boundary between active and inactive regions [S1]. This reduces depth complexity and the number of rays traced for space skipping [S1].

**Where it is used:**
- GPU-based large-scale volume rendering [S1].
