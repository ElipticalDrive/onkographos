# Orthogonal Culling Optimization
Also called: Orthogonal Culling, Orthogonal Projection Culling

## Overview
Orthogonal Culling is a pre-computation optimization for sphere tracing that reduces the number of signed distance function (SDF) evaluations per ray by determining which scene objects lie within the ray's path before the marching loop begins [S1, unofficial]. It differs from its parent, [Bounding Spheres Optimization](1567-bounding-spheres-optimization.md), which minimizes distance calculations during traversal, and its sibling, [Frustum Culling (Sphere vs Frustum)](4835-frustum-culling-sphere-vs-frustum.md), which typically relies on CPU-side broad-phase culling; Orthogonal Culling performs a geometric intersection test between the ray and object bounding volumes using orthogonal projection [S1, unofficial].

## How it works
**Inputs and Outputs**
*   **Input:** Ray origin $\mathbf{o}$, ray direction $\mathbf{d}$, and a list of scene objects, each defined by a bounding sphere with center $\mathbf{c}$ and radius $r$ [S1, unofficial].
*   **Output:** A boolean mask or list of indices indicating which objects intersect the ray, allowing the renderer to skip SDF evaluations for non-intersecting objects [S1, unofficial].

**Data Structures**
*   **Ray:** Defined by origin $\mathbf{o} \in \mathbb{R}^3$ and direction vector $\mathbf{d} \in \mathbb{R}^3$ [G].
*   **Bounding Sphere:** Defined by center $\mathbf{c} \in \mathbb{R}^3$ and scalar radius $r \ge 0$ [S1, unofficial].

**Algorithm Steps**
1.  For each object in the scene, retrieve its bounding sphere center $\mathbf{c}$ and radius $r$ [S1, unofficial].
2.  Project the vector from the ray origin to the sphere center onto the ray direction to find the line's closest point to the object [S1, unofficial].
3.  Calculate the distance between the line and the sphere using the sphere's radius [S1, unofficial].
4.  Compare this distance against zero [S1, unofficial].
5.  If the distance is less than zero, the ray intersects the sphere and the object is considered for distance calculation [S1, unofficial].

**Formulas**
Let $\mathbf{v} = \mathbf{c} - \mathbf{o}$ be the vector from the ray origin to the sphere center [G].
The projection of $\mathbf{v}$ onto the ray direction $\mathbf{d}$ is given by the dot product:
$$ t = \mathbf{v} \cdot \mathbf{d} $$
This $t$ represents the distance along the ray to the closest point $\mathbf{p}$ on the line [G]:
$$ \mathbf{p} = \mathbf{o} + t\mathbf{d} $$
The squared distance $D^2$ from the sphere center $\mathbf{c}$ to the point $\mathbf{p}$ is calculated using the Pythagorean theorem:
$$ D^2 = \|\mathbf{v}\|^2 - t^2 = \|\mathbf{c} - \mathbf{o}\|^2 - (\mathbf{v} \cdot \mathbf{d})^2 $$
The distance between the line and the sphere surface is $D - r$ [G].
The intersection condition is $D - r < 0$, which is equivalent to $D^2 < r^2$ [S1, unofficial].

**Pseudocode**
```python
def orthogonal_cull(ray_origin, ray_direction, objects):
    """
    ray_origin: vec3
    ray_direction: vec3
    objects: list of dicts with keys 'center' (vec3) and 'radius' (float)
    returns: list of indices of objects intersecting the ray
    """
    active_objects = []
    for i, obj in enumerate(objects):
        c = obj['center']
        r = obj['radius']
        v = c - ray_origin
        t = dot(v, ray_direction)
        dist_sq = dot(v, v) - t * t
        # Source notes check if distance(line, sphere) < 0 [S1, unofficial]
        if dist_sq < r * r:
            active_objects.append(i)
    return active_objects
```

**Edge Cases and Pitfalls**
*   **Implementation Efficiency:** The described implementation performs this culling check for all objects in the scene for every pixel [S1, unofficial]. This is suboptimal because culling should be done once per object to calculate which rays it intersects, rather than per ray determining which objects it intersects [S1, unofficial].

## Operating characteristics
**Time and Memory Complexity**
*   **Time:** $O(N \cdot R)$, where $N$ is the number of objects and $R$ is the number of rays (pixels), because the implementation checks all objects per pixel [S1, unofficial].
*   **Memory:** $O(1)$ auxiliary space per ray, assuming the object list is read-only [G].

**Measured Performance**
*   Tested on a GeForce GTX 1060M at 1920x1080 resolution [S1, unofficial].
*   Performance gain is significant but varies with object count and scene configuration [S1, unofficial].
*   **Table 5.1 Data (FPS):**
    *   1 Object: 600 FPS (optimized) vs 350 FPS (unoptimized) [S1, unofficial]
    *   10 Objects: 500 FPS (optimized) vs 300 FPS (unoptimized) [S1, unofficial]
    *   20 Objects: 40 FPS (optimized) vs 25 FPS (unoptimized) [S1, unofficial]
    *   30 Objects: 29 FPS (optimized) vs 20 FPS (unoptimized) [S1, unofficial]
    *   40 Objects: 6 FPS (optimized) vs 4 FPS (unoptimized) [S1, unofficial]
    *   45 Objects: 4 FPS (optimized) vs 1.5 FPS (unoptimized) [S1, unofficial]

**Strengths and Limitations**
*   **Strengths:** Provides a consistent performance increase by reducing the number of SDF evaluations per march step [S1, unofficial]. It is particularly effective when objects are not mutually obstructing, such as spheres arranged in a plane, which represents the best-case scenario for the optimization [S1, unofficial].
*   **Limitations:** The naive per-pixel, per-object check is computationally expensive for large $N$ [S1, unofficial]. It does not account for occlusion by other objects in the scene, only geometric intersection with the ray [S1, unofficial].

## Background
**Origin**
Orthogonal Culling was introduced in the context of GPU-based Sphere Tracing implementations to optimize the evaluation of signed distance functions [S1, unofficial]. It was developed as part of a broader set of optimizations including Bounding Spheres and Ray Grouping [S1, unofficial].

**History and Development**
The method was evaluated using a GLSL software shader and simulated on a GPU architecture (C*λ*aSH simulation) [S1, unofficial]. The research highlighted that while the optimization provided high performance gains, the initial implementation was not optimal because it repeated the culling calculation for every ray-object pair per pixel, rather than computing ray-object intersections once per object [S1, unofficial]. The authors suggested that this step could be offloaded to the CPU for better efficiency [S1, unofficial].

**Usage**
The technique is used in real-time ray marching applications, specifically those rendering reflective spheres and mod fields, where reducing the number of distance queries is critical for maintaining high frame rates [S1, unofficial].
