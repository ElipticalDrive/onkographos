# Ray Marching

Also called: jittered ray marching

## Overview
Ray marching is an iterative ray intersection technique used to find intersections with solid geometry or volumetric media when the surface function is too complex for analytical solutions or requires numeric iterative methods [S2, S6, unofficial]. It differs from traditional ray tracing by stepping along a ray and testing for intersections rather than solving for the intersection point directly [S6, unofficial]. It is particularly suited for rendering non-uniform volumetrics, implicit functions, fractals, and parametric surfaces where the intersection is not known ahead of time [S2, S6, unofficial].

## How it works
Ray marching iteratively advances a ray along its direction, querying a scene function at each step to determine proximity to geometry or medium boundaries [S2, S5, S6, unofficial]. The method can use fixed step sizes, distance-based leaps (such as sphere tracing), or root-finding refinements [S2, S3, S6, unofficial].

### Inputs and Outputs
*   **Inputs:**
    *   Ray origin $\mathbf{ro}$ [S5, unofficial].
    *   Ray direction $\mathbf{rd}$ (normalized) [S5, unofficial].
    *   Scene distance function $scene(\mathbf{p})$ returning the distance to the nearest object or medium boundary at point $\mathbf{p}$ [S5, unofficial].
    *   Maximum number of steps $u_{maxSteps}$ [S5, unofficial].
    *   Maximum travel distance $u_{maxDis}$ [S5, unofficial].
    *   Intersection threshold $\epsilon$ (u_eps) [S5, unofficial].
    *   Minimum step length $min\_step\_len$ [S1, book].
    *   Maximum step length $max\_step\_len$ [S1, book].
*   **Outputs:**
    *   Total distance travelled $d$ [S5, unofficial].
    *   Hit position $\mathbf{hp} = \mathbf{ro} + d \cdot \mathbf{rd}$ [S5, unofficial].
    *   Final pixel color, derived from lighting calculations at $\mathbf{hp}$ if a hit occurs, or clear color otherwise [S5, unofficial].

### Data Structures
No specific complex data structures are required for the core algorithm, though acceleration structures like grids or bounding volumes may be used for the scene function evaluation [S1, book][S6, unofficial]. For volumetric integration, samples are distributed along the ray [S4].

### Algorithm Steps
1.  **Initialize:** Set total distance $d = 0$ [S5, unofficial].
2.  **Iterate:** For each step $i$ from $0$ to $u_{maxSteps}-1$:
    a. Calculate current position: $\mathbf{p} = \mathbf{ro} + d \cdot \mathbf{rd}$ [S5, unofficial].
    b. Query scene distance: $cd = scene(\mathbf{p})$ [S5, unofficial].
    c. **Termination Check:**
        i. If $cd < \epsilon$, an intersection is found. Break loop [S5, unofficial].
        ii. If $d \ge u_{maxDis}$, the ray has traveled too far without hitting anything. Break loop [S5, unofficial].
    d. **Step Update:**
        i. If using fixed step size, $d \leftarrow d + step\_size$ [S3, unofficial].
        ii. If using sphere tracing (distance-based), $d \leftarrow d + cd$ [S5, unofficial].
        iii. If using jittered ray marching for volumes, samples are distributed at equal distance with random offsets [S4].
        iv. If using space leaping, advance by a safety distance determined by preprocessing [S6, unofficial].
3.  **Post-Processing:**
    a. If $d < u_{maxDis}$, calculate hit position $\mathbf{hp} = \mathbf{ro} + d \cdot \mathbf{rd}$ [S5, unofficial].
    b. Compute normal $\mathbf{n}$ at $\mathbf{hp}$ [S5, unofficial].
    c. Calculate lighting (diffuse, specular, ambient) using $\mathbf{n}$ and light direction [S5, unofficial].
    d. Output final color [S5, unofficial].
    e. If $d \ge u_{maxDis}$, output clear color [S5, unofficial].

### Pseudocode
```python
def ray_march(ro, rd, scene_func, max_steps, max_dis, epsilon):
    """
    Iteratively march a ray to find intersection or volume samples.
    
    Args:
        ro: Ray origin (vec3)
        rd: Ray direction (vec3, normalized)
        scene_func: Function p -> distance (float)
        max_steps: Integer maximum iterations
        max_dis: Float maximum travel distance
        epsilon: Float intersection threshold
        
    Returns:
        distance: Total distance travelled (float)
    """
    d = 0.0  # total distance travelled
    
    for i in range(max_steps):
        # Calculate current position
        p = ro + d * rd
        
        # Query scene distance
        cd = scene_func(p)
        
        # Check for intersection or max distance
        if cd < epsilon:
            break
        if d >= max_dis:
            break
            
        # Update distance
        # Note: For standard ray marching with SDFs, step by cd.
        # For fixed step size, step by a constant.
        # For jittered volume marching, step by fixed step with jitter.
        # Here we assume the common SDF-based leap (Sphere Tracing) 
        # as described in [S5, unofficial], but fixed step is also common [S2, S3, unofficial].
        d += cd
        
    return d

def render_pixel(ro, rd, scene_func, max_steps, max_dis, epsilon, clear_color, light_dir, 
                 diff_intensity, spec_intensity, shininess, ambient_intensity, scene_color_func, normal_func):
    """
    Full rendering pipeline for a single pixel using ray marching.
    """
    # Normalize ray direction
    rd = normalize(rd)
    
    # Find total distance travelled
    dis_travelled = ray_march(ro, rd, scene_func, max_steps, max_dis, epsilon)
    
    # Determine hit position
    hp = ro + dis_travelled * rd
    
    # Check if hit occurred
    if dis_travelled >= max_dis:
        return clear_color
    else:
        # Calculate normal
        n = normal_func(hp)
        
        # Lighting calculations
        dot_nl = dot(n, light_dir)
        diff = max(dot_nl, 0.0) * diff_intensity
        spec = pow(diff, shininess) * spec_intensity
        ambient = ambient_intensity
        
        # Get scene color at hit point
        sc = scene_color_func(hp)
        
        # Combine lighting
        color = sc * (diff + spec + ambient)
        
        return color
```

### Parameters
*   $min\_step\_len$: Minimum step length for ray marching [S1, book].
*   $max\_step\_len$: Maximum step length for ray marching [S1, book].
*   $u_{eps}$: Intersection threshold [S5, unofficial].
*   $u_{maxDis}$: Maximum distance [S5, unofficial].
*   $u_{maxSteps}$: Maximum number of steps [S5, unofficial].

### Edge Cases and Pitfalls
*   **Precision:** Small $\epsilon$ values may cause missed intersections if the step size is too large [S5, unofficial].
*   **Performance:** Ray marching performs poorly at lower sample counts for volumetric rendering because it fails to distribute samples proportional to transmittance [S4].
*   **Complex Occluders:** The method relies on heuristics and may deviate from the correct solution when dealing with complex occluders, regardless of sample count [S4].
*   **Missing Geometry:** If the step size is too large, the ray may pass through thin geometry without detecting an intersection [S3, S6, unofficial].

## Subtopics

### [Sphere Tracing](5017-sdf-ray-marching-with-grid-lookup.md)
An optimized variant of ray marching that uses Signed Distance Functions (SDFs) to take larger, optimal steps without intersecting geometry. Choose it when SDFs are available for the scene.

### [Jittered Ray Marching](2331-step-size-selection.md)
Distributes samples at equal distances with random offsets. Choose it for volumetric rendering to reduce banding artifacts, though it may perform poorly at low sample counts compared to distance sampling.

### [Space Leaping](1244-iteration-based-coloring.md)
An acceleration technique where preprocessing provides a safety distance to move along the ray without intersecting geometry. Choose it to speed up ray marching in complex scenes.

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of steps $N$. $O(N)$ [S5, unofficial].
*   **Memory Complexity:** Low, primarily storing the ray state and scene function evaluation results. $O(1)$ auxiliary space [S5, unofficial].
*   **Measured Performance:**
    *   On an RTX 8000 GPU at 1024 spp, Ray Marching on a room scene took $11.0 \pm 0.5$ ms [S4].
    *   On a GTX 980 Ti GPU at 256 spp, Ray Marching on a room scene took $10.3 \pm 0.2$ ms [S4].
*   **Scaling:** Performance scales linearly with the number of steps and scene complexity (if the scene function evaluation is constant time).
*   **Strengths:**
    *   Simple to implement [S2, unofficial].
    *   Handles complex, mathematically defined surfaces like fractals and clouds [S5, unofficial].
    *   Effective for non-uniform volumetrics and implicit functions [S2, S6, unofficial].
*   **Limitations:**
    *   Poor performance at low sample counts for volumetric rendering [S4].
    *   Can miss thin geometry if step size is not carefully chosen [S3, unofficial].
    *   Less accurate than analytical ray tracing for simple primitives [S6, unofficial].
*   **When to Use:** Rendering implicit surfaces, fractals, non-uniform volumetrics, and parametric surfaces where intersection is not known ahead of time (e.g., parallax mapping) [S2, S6, unofficial].
*   **When Not to Use:** When analytical intersections are available and efficient, or when high accuracy at low sample counts is required for complex volumetric scattering [S4].

## Background
Ray marching was first encountered by the author in the context of per-pixel displacement mapping techniques, specifically relief mapping of non-height-field surface details [S2, S6, unofficial]. It is a technique used by volume shaders [S1, book]. Sphere tracing, a specific form of ray marching, was introduced by John Hart [S3, S6, unofficial]. The method is commonly used with space leaping acceleration techniques such as cone step mapping and relaxed cone step mapping [S6, unofficial].
