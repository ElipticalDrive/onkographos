# Multi-Material Distance Fields

Also called: Augmented SDF signature, Color-Coded SDFs, Material-Augmented Signed Distance Function, MaterialSDF, SDF with Material Data, SDF with material ID

## Overview
Multi-Material Distance Fields extend standard Signed Distance Functions (SDFs) to return both a geometric distance and a material identifier for every point in space [S1, unofficial][S2, unofficial]. This allows Constructive Solid Geometry (CSG) operations to preserve material assignments during boolean combinations, enabling per-object shading within a single ray-marched scene [S1, unofficial][S2, unofficial]. Unlike [SDF Smooth Union](1817-sdf-smooth-union.md) or [Linear SDF Blend](3004-linear-sdf-blend.md), which blend distance values to create smooth transitions, Multi-Material Distance Fields use hard boolean logic to select the closest object, preserving sharp material boundaries while inheriting the edge-blending properties of the underlying combination operator [S1, unofficial][S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D position vector $\mathbf{p}$ and a CSG tree structure where each leaf node contains an SDF primitive and a material ID [S1, unofficial].
*   **Output:** A tuple or vector containing the signed distance $d$ and the material identifier $m$ [S1, unofficial][S2, unofficial]. In GLSL/HLSL implementations, this is a `float2` where the x-component is the distance and the y-component is the material data (e.g., a color index) [S2, unofficial]. In functional implementations, it is a tuple `(Double, Material.ID)` [S1, unofficial].

**Data Structures:**
1.  **MaterialSDF Type:** A function signature mapping a vector to a pair of values [S1, unofficial].
    *   Functional: `type MaterialSDF = Vector => (Double, Material.ID)` [S1, unofficial].
    *   Shader: `float2` return type [S2, unofficial].
2.  **CSG Leaf Node:** Contains the primitive SDF function and the associated material ID [S1, unofficial].
    *   Structure: `Leaf(sdf: SDF, material: Material.ID)` [S1, unofficial].

**Algorithm Steps:**
The method recursively evaluates the CSG tree [S1, unofficial]. For any node, it evaluates the left and right children to get their respective distance-material pairs, then applies the boolean operator logic to select the correct pair [S1, unofficial].
1.  **Leaf Evaluation:** If the current node is a leaf, evaluate the leaf's SDF at position $\mathbf{p}$ to get distance $d$, and return the pair $(d, \text{material})$ [S1, unofficial].
2.  **Recursive Evaluation:** If the current node is an internal node, recursively evaluate the left child to get $(d_a, m_a)$ and the right child to get $(d_b, m_b)$ [S1, unofficial].
3.  **Operator Application:** Apply the specific boolean operator to select the output pair based on the distance values [S1, unofficial]:
    *   **Union:** Select the pair with the smaller distance. If $d_a \le d_b$, return $(d_a, m_a)$; otherwise, return $(d_b, m_b)$ [S1, unofficial][S2, unofficial].
    *   **Intersection:** Select the pair with the larger distance. If $d_a \ge d_b$, return $(d_a, m_a)$; otherwise, return $(d_b, m_a)$ [S1, unofficial]. The implementation consistently assigns the material of the left operand ($m_a$) regardless of which distance defines the boundary [S1, unofficial].
    *   **Difference:** Subtract the right child from the left. If $d_a \ge -d_b$, return $(d_a, m_a)$; otherwise, return $(-d_b, m_a)$ [S1, unofficial]. The material of the subtracted object ($m_b$) is discarded, and the material of the base object ($m_a$) is retained [S1, unofficial].

**Pseudocode:**
```python
# Type definitions
# Vector: 3D float tuple (x, y, z)
# MaterialID: Integer or float identifier
# Tree node accesses (is_leaf, sdf, left, right, operation) are standard [G]

def evaluate_material_sdf(tree, p):
    """
    Recursively evaluates the CSG tree to return (distance, material_id).
    """
    if tree.is_leaf():
        distance = tree.sdf(p)
        return (distance, tree.material)
    
    left_result = evaluate_material_sdf(tree.left, p)
    right_result = evaluate_material_sdf(tree.right, p)
    
    d_a, m_a = left_result
    d_b, m_b = right_result
    
    operation = tree.operation
    
    if operation == "Union":
        if d_a <= d_b:
            return (d_a, m_a)
        else:
            return (d_b, m_b)
    elif operation == "Intersection":
        if d_a >= d_b:
            return (d_a, m_a)
        else:
            return (d_b, m_a)
    elif operation == "Difference":
        if d_a >= -d_b:
            return (d_a, m_a)
        else:
            return (-d_b, m_a)
    else:
        raise ValueError(f"Unknown operation: {operation}")

# Standard raymarching loop [G]
def raymarch_material_sdf(scene_tree, ro, rd, max_steps=64, max_dist=100.0, epsilon=0.001):
    """
    Ray marches the multi-material SDF.
    Returns (hit_distance, hit_point, material_id) or (None, None, None).
    """
    t = 0.0
    for _ in range(max_steps):
        if t > max_dist:
            break
        p = ro + rd * t
        d, m = evaluate_material_sdf(scene_tree, p)
        if d < epsilon:
            return t, p, m
        # Conservative step guard [G]
        t += max(d, 0.001)
    return None, None, None
```

**Shader Implementation Details:**
In GPU shaders, the `map()` function returns a `float2` [S2, unofficial]. The union operator `opU` compares the x-components (distances) and returns the entire `float2` vector of the closer object [S2, unofficial].
```glsl
float2 opU(float2 d1, float2 d2) {
    return (d1.x < d2.x) ? d1 : d2;
}
```
The final color is determined by sampling a `_ColorRamp` texture using the y-component (material ID) of the hit point's output from `map()` [S2, unofficial].

**Parameters:**
*   **ColorRamp:** A 1D or 2D texture (`sampler2D`) that maps material IDs (y-component) to RGB colors [S2, unofficial].
*   **Precision:** Standard `float` precision is used. Care must be taken with the comparison $d_a \le d_b$ to avoid jittering at exact boundaries, though hard boolean operations are generally stable compared to smooth blends [S1, unofficial][S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Lipschitz Continuity:** As with all SDF combination operators, if the gradients of the two input SDFs are not orthogonal, Lipschitz continuity ($|\nabla d| \le 1$) may be violated, leading to ray marching artifacts like overshooting or jittering [S1, unofficial][S2, unofficial]. If the angle between gradients deviates by more than $30^\circ$, or if surfaces are parallel and close, continuity is lost [S1, unofficial][S2, unofficial].
*   **Material Assignment in Intersection:** The implementation assigns the material of the left operand ($m_a$) when the right distance defines the boundary, which may not match visual expectations for all CSG trees [S1, unofficial].

## Subtopics

### [Material Object Format](1981-material-object-format.md)
A data structure that holds surface shading information, including color, physical properties, and texture descriptors, accessible from both host and device code. It distinguishes itself by explicitly separating geometric displacement (via `heightmapTex`) from shading calculations and by managing texture projection modes and normal deflection scaling.

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Not given in the sources.
*   **Strengths:** Enables complex, multi-material scenes with sharp material boundaries using a single ray marcher. Simple to implement by augmenting the return type of the SDF map function [S1, unofficial][S2, unofficial].
*   **Limitations:** Does not inherently support smooth material blending (e.g., gradients between materials) unless combined with smooth union operators that also blend the material ID, which is not standard in the basic definition [S1, unofficial][S2, unofficial].

## Background
The technique extends standard SDF ray marching to support per-object material assignment within a CSG scene [S1, unofficial][S2, unofficial]. It allows artists to assign distinct visual properties to individual primitives within a CSG composition without requiring multiple render passes or complex shader branching for material selection [S1, unofficial][S2, unofficial]. The implementation details provided in [S1, unofficial] demonstrate a functional programming approach (Scala) for constructing the CSG tree, while [S2, unofficial] provides the GLSL/HLSL shader implementation for real-time rendering.
