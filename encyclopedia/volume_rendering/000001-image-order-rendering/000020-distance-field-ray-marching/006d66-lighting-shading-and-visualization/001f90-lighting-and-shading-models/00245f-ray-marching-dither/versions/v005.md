# Ray Marching Dither

Also called: UV Dithering, Distance-based UV Perturbation

## Overview
Ray Marching Dither is a technique to reduce banding artifacts in ray marching by perturbing the UV coordinates based on the ray distance [S1, unofficial]. It solves the problem of clearly defined intensity bands caused by fixed step sizes or discrete sampling grids in participating media [S1, unofficial]. Unlike fixed stepping, which causes banding, this method removes these artifacts while keeping features like god rays sharp and focused [S1, unofficial]. It differs from [Ray Marching Jittering](5399-ray-marching-jittering.md) by applying perturbation to UV coordinates rather than the step size itself.

## How it works
**Inputs and Outputs:**
*   **Input:** Ray origin $\mathbf{ro}$, ray direction $\mathbf{rd}$, fragment UV coordinates $\mathbf{uv}$ (normalized to $[0,1]$), hit distance $t$ (or current ray length), and a dithering strength factor $c_{fDither}$.
*   **Output:** Perturbed UV coordinates $\mathbf{uv}'$ used to reconstruct the ray.

**Data Structures:**
*   $\mathbf{uv}$: 2D vector $(uv_x, uv_y)$.
*   $t$: Scalar float representing the distance along the ray.
*   $c_{fDither}$: Scalar float, typical value $0.001$ [S1, unofficial].

**Steps:**
1.  **Calculate Dither Amount:** Compute the magnitude of the perturbation based on the squared hit distance and the strength factor:
    $$ dither = t^2 \cdot c_{fDither} $$
    [S1, unofficial]

2.  **Generate Random Offsets:** Generate two independent random values based on the fragment coordinates and fixed offsets. Let $rand(\mathbf{seed})$ be a pseudo-random function returning a value in $[0, 1]$.
    $$ r_x = rand(\mathbf{uv} + (0.12, 0.32)) $$
    $$ r_y = rand(\mathbf{uv} + (0.42, 0.52)) $$
    [S1, unofficial]

3.  **Perturb UVs:** Apply the random offsets scaled by the dither amount, centered around zero:
    $$ uv'_x = uv_x + r_x \cdot dither - \frac{dither}{2.0} $$
    $$ uv'_y = uv_y + r_y \cdot dither - \frac{dither}{2.0} $$
    [S1, unofficial]

4.  **Reconstruct Ray:** Use $\mathbf{uv}'$ to reconstruct the ray origin and direction. Assuming a standard perspective camera setup where $\mathbf{uv}$ maps to the view frustum:
    $$ \mathbf{ro}' = \mathbf{camPos} + \text{ReconstructOrigin}(\mathbf{uv}') $$
    $$ \mathbf{rd}' = \text{normalize}(\mathbf{ro}' - \mathbf{camPos}) $$
    [S1, unofficial]

**Pseudocode:**
```python
def ray_marching_dither(uv, t, c_fDither, cam_pos, cam_center, aspect, fov_scale):
    """
    Perturbs UV coordinates to reduce banding in ray marching.
    
    Args:
        uv: vec2, normalized fragment coordinates [0, 1]
        t: float, hit distance along the ray
        c_fDither: float, dithering strength factor (default 0.001)
        cam_pos: vec3, camera position
        cam_center: vec3, camera look-at point
        aspect: float, aspect ratio
        fov_scale: float, field of view scaling factor (e.g., sqrt(3)/3 for 30 deg)
        
    Returns:
        ro: vec3, perturbed ray origin
        rd: vec3, perturbed ray direction
    """
    # 1. Calculate dither amount
    dither = t * t * c_fDither
    
    # 2. Generate random offsets
    # Note: rand() is a pseudo-random function returning [0, 1]
    # Seeds are offset UVs to ensure spatial variation
    seed_x = uv + vec2(0.12, 0.32)
    seed_y = uv + vec2(0.42, 0.52)
    
    r_x = rand(seed_x)
    r_y = rand(seed_y)
    
    # 3. Perturb UVs
    uv_perturbed = vec2(
        uv.x + r_x * dither - dither / 2.0,
        uv.y + r_y * dither - dither / 2.0
    )
    
    # 4. Reconstruct ray from perturbed UV
    # Standard perspective reconstruction from UV [0,1]
    # Map UV to [-1, 1] range
    uv_norm = vec2(
        (uv_perturbed.x * 2.0 - 1.0),
        (uv_perturbed.y * 2.0 - 1.0)
    )
    
    # Camera basis vectors
    forward = normalize(cam_center - cam_pos)
    # Assuming 'up' is fixed or derived; here we assume a standard right-handed system
    # Right vector
    right = normalize(cross(forward, vec3(0.0, 1.0, 0.0)))
    # Up vector
    up = cross(right, forward)
    
    # Scale by FOV
    # fov_scale is typically sqrt(3)/3 for 30 degrees
    ray_dir = forward + (uv_norm.x * fov_scale * right) + (uv_norm.y * fov_scale * up)
    ray_dir = normalize(ray_dir)
    
    # Ray origin is usually the camera position, but in some ray marching setups
    # (like the source code), the origin is also shifted by the UV mapping if
    # the ray is defined from a plane. However, standard ray marching defines
    # ro = cam_pos. The source code shows:
    # ro = uCamPos + (2.0*vUv.x-1.0)*ROOTTHREE*A + ...
    # This implies ro is on a plane in front of the camera, or the ray starts
    # from the camera but the UVs are used to define the direction.
    # Re-reading source [S1, unofficial]:
    # vec3 ro = uCamPos + (2.0*vUv.x-1.0)*ROOTTHREE*A + (2.0*vUv.y-1.0)*ROOTTHREE*B;
    # vec3 rd = normalize(ro - uCamPos);
    # This is a specific camera model where ro is on a near plane.
    
    ro = cam_pos + (uv_norm.x * fov_scale * right) + (uv_norm.y * fov_scale * up)
    rd = normalize(ro - cam_pos)
    
    return ro, rd

def rand(v):
    """Simple pseudo-random hash for a 2D vector."""
    return fract(sin(dot(v, vec2(12.9898, 78.233))) * 43758.5453)
```

**Edge Cases and Pitfalls:**
*   **Precision:** For very large $t$, $t^2$ may overflow or lose precision. Clamp $t$ or use a smaller $c_{fDither}$ if artifacts appear at long distances.
*   **Boundary Conditions:** If $\mathbf{uv}'$ goes outside $[0, 1]$, the ray reconstruction may produce invalid directions depending on the camera model. The source code does not explicitly clamp $\mathbf{uv}'$, implying the perturbation is small enough relative to the FOV to remain within valid bounds for typical scenes.
*   **Determinism:** The use of `rand` makes the result non-deterministic per frame unless a seed is used. This is desirable for temporal dithering but may cause flickering if not handled over time.

## Subtopics

### [Ray Marching Jittering](5399-ray-marching-jittering.md)
Ray Marching Jittering is a technique to reduce aliasing artifacts, specifically banding, in volume rendering by introducing random variation to the ray marching step size. It solves the problem of clearly defined intensity bands caused by fixed step sizes in participating media. Unlike fixed stepping, which causes banding, jittering removes these artifacts while keeping features like god rays sharp and focused. It builds on [Ray Marching Dither](3269-ray-marching-dither.md) by applying perturbation to the step size rather than just UV coordinates.

## Operating characteristics
*   **Time Complexity:** $O(1)$ per pixel for the dithering calculation itself. The cost is negligible compared to the ray marching loop.
*   **Memory Complexity:** $O(1)$ additional memory. No textures are required for the basic UV dithering method [S1, unofficial].
*   **Strengths:** Simple to implement; effectively breaks up regular banding patterns; no additional texture lookups required for the basic version.
*   **Limitations:** The perturbation is based on UV coordinates, which may not align perfectly with the ray's path through the volume, potentially leaving some artifacts in complex geometries. The basic version may exhibit temporal flickering if not combined with temporal dithering.
*   **When to use:** When banding artifacts are visible due to fixed step sizes or discrete sampling, and performance is a concern (no texture fetches).
*   **When not to use:** When high-quality temporal stability is required without additional temporal logic, or when the banding is caused by other factors (e.g., low step count in depth, not UV).

## Background
The technique is documented in the [WebGL-RayMarch](https://github.com/nopjia/WebGL-RayMarch) repository by nopjia [S1, unofficial]. It is used in real-time ray marching demos to improve visual quality with minimal performance overhead.
