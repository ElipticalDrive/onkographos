# Cone Marching

Also called: Cone Marching in patches, Two-pass Cone Marching

## Overview
Cone Marching is a GPU optimization technique for Signed Distance Field (SDF) ray marching that reduces redundant distance calculations by grouping adjacent rays into cones [S2, unofficial]. It addresses the problem where independent per-pixel ray marching evaluates similar scene distances repeatedly [S2, unofficial]. Unlike standard ray marching, it computes a coarse intersection distance in a lower-resolution pass (or vertex shader) and feeds the starting distance to a fine per-pixel pass [S1, unofficial]. This separates the traversal optimization from shading logic, distinguishing it from sibling methods like [Ray Marching with Reflections](1963-ray-marching-with-reflections.md) [S2, unofficial].

## How it works
**Inputs and Outputs:** The method requires camera position ($ro$), camera orientation, field of view (FOV), screen resolution, an SDF scene function ($scene(p)$), maximum marching distance ($u\_maxDis$), and maximum steps ($u\_maxSteps$) [S2, unofficial]. The output is the final ray distance and hit position for shading; in the two-pass variant, the first pass outputs starting distances and step counts, while the second pass outputs the final color [S1, unofficial].

**Data Structures:** A `March` struct passes data between passes or shader stages, containing `dis` (float: total distance travelled) and `steps` (int: number of steps taken) [S2, unofficial].

**Numbered Steps:**
1. Setup Marching Plane: Create a geometry representing the screen with evenly spaced (square) vertices to avoid aspect ratio artifacts [S2, unofficial]. For a height of 32 subdivisions, the width subdivisions are $\lfloor aspect \times 32 \rfloor$ [S2, unofficial].
2. Compute Ray Direction: For each vertex, transform UV to clip space, unproject using the inverse projection matrix, transform to world space using the camera world matrix, and normalize to obtain the cone ray direction ($crd$) [S2, unofficial].
3. Cone Marching Loop: Initialize total distance $d = 0$ and step counter $i = 0$ [S2, unofficial]. Calculate current position $p = cro + d \cdot crd$ [S2, unofficial]. Get scene distance $cd = scene(p)$ [S2, unofficial]. Calculate cone radius $ccr$ [S2, unofficial]. Break if $cd < ccr \cdot 1.25$ or $d \ge u\_maxDis$ [S2, unofficial]. Advance conservatively by $d \leftarrow d + \max(0.0, cd - ccr)$ and increment $i$ [G].
4. Return Coarse Result: Return the `March` struct with $d$ and $i$ [S2, unofficial].
5. Fine Ray Marching: Receive $vDisTravelled$ and $vSteps$ [S2, unofficial]. Initialize $d = vDisTravelled$ and $i = vSteps$ [S2, unofficial]. Compute per-pixel direction $rd$ from UV [S2, unofficial]. Iterate while $i < u\_maxSteps$: $p = ro + d \cdot rd$, $cd = scene(p)$, break if $cd < u\_eps$ or $d \ge u\_maxDis$, advance $d \leftarrow d + cd$, increment $i$ [S2, unofficial]. Return final $d$ [S2, unofficial].

**Formulas:** The cone radius at distance $d$ is calculated as $ccr = \frac{d \cdot u\_camTanFov \cdot 2.0}{u\_camPlaneSubdivisions}$ [S2, unofficial]. The intersection break condition uses a padded radius: $cd < ccr \cdot 1.25$ [S2, unofficial].

**Parameters:** $u\_camTanFov$ is the tangent of half the camera's FOV, calculated as $\tan(FOV/2)$ [S2, unofficial]. $u\_camPlaneSubdivisions$ defines the marching grid resolution, with a typical value of 32 [S2, unofficial]. A padding factor of 1.25 is applied to the cone radius in the break condition to prevent SDF edge artifacts [S2, unofficial].

**Edge Cases and Pitfalls:** Using rectangular screen vertices without accounting for the camera aspect ratio causes uneven spacing and visual artifacts [S2, unofficial]. The break condition relies on the padding factor rather than a standard epsilon to avoid artifacts at SDF edges [S2, unofficial]. For pixels far from the screen center, using the central focal distance in radius calculations may be inaccurate; using the specific pixel's distance from the camera is more precise [S3, unofficial].

### Pseudocode
```python
class March:
    dis: float
    steps: int

# Uniforms
u_camTanFov: float = 0.0
u_camPlaneSubdivisions: int = 32
u_maxDis: float = 20.0
u_maxSteps: int = 100
u_eps: float = 0.001

def scene(p: list[float]) -> float:
    # Returns signed distance to nearest object
    return 0.0

def cone_march(cro: list[float], crd: list[float]) -> March:
    d = 0.0
    i = 0
    while i < u_maxSteps:
        p = [cro[j] + d * crd[j] for j in range(3)]
        cd = scene(p)
        ccr = (d * u_camTanFov * 2.0) / u_camPlaneSubdivisions
        if cd < ccr * 1.25 or d >= u_maxDis:
            break
        d += max(0.0, cd - ccr)  # Conservative step to prevent overshooting [G]
        i += 1
    return March(dis=d, steps=i)

def ray_march(start_dis: float, steps_taken: int, ro: list[float], rd: list[float]) -> float:
    d = start_dis
    i = steps_taken
    while i < u_maxSteps:
        p = [ro[j] + d * rd[j] for j in range(3)]
        cd = scene(p)
        if cd < u_eps or d >= u_maxDis:
            break
        d += cd
        i += 1
    return d
```

## Subtopics

### Cone Radius Calculation for Raymarching
A method to estimate the radius of the ray cone at any given distance to implement cone-marching and minimize steps [S3, unofficial]. It addresses the inaccuracy of exponential radius growth approximations by using a linear relationship: $radius(distance) = \frac{distance \cdot initialRadius}{focalDistance}$ [S3, unofficial]. This requires recalculating the radius at every step because the distance from the camera changes [S3, unofficial]. For pixels not in the center of the screen, using the distance of the specific pixel on the screen plane from the camera is more accurate than the central focal distance [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** Reduces the number of SDF evaluations in the coarse phase by marching a single cone per patch/vertex instead of per pixel [S2, unofficial]. The fine phase still requires per-pixel marching but starts from a closer distance, reducing total steps [S2, unofficial].
*   **Memory Complexity:** Requires storing intermediate results (distance and steps) between passes or shader stages [S2, unofficial].
*   **Performance:** The simple Three.js approach offers a good balance of complexity and gain, whereas multi-pass approaches (decreasing cone size until it equals pixel size) are theoretically ideal but more complex to implement [S2, unofficial].
*   **Strengths:** Significant reduction in redundant calculations for bundles of rays; easy to implement in vertex shaders or simple multi-pass setups [S2, unofficial].
*   **Limitations:** Requires additional passes or uniform data transfer; less effective if the scene has high-frequency details that cause cones to intersect early and frequently [S2, unofficial].
