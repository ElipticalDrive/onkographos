# Mesh Transformation via Embree RTC

Also called: xformRtcMeshOnly

## Overview
This method updates the geometry of a mesh within an Embree ray tracing context by applying a 4x4 transformation matrix to the vertex buffer while preserving the original source data. It solves the problem of dynamic mesh animation in Embree by allowing the scene graph to reflect current vertex positions without reallocating geometry buffers. It differs from [Inverse Model Matrix Transformation for Distance Fields](1962-inverse-model-matrix-transformation-for-distance-fields.md) by operating on explicit mesh primitives rather than implicit distance fields, and from [Motion-Compensated Block Warping](4613-motion-compensated-block-warping.md) by updating vertex positions directly rather than warping compressed voxel blocks.

## How it works
**Inputs:**
- `rtcGeometry`: The Embree geometry object handle.
- `mat`: A 4x4 transformation matrix ($M$) in column-major or row-major format consistent with Embree's expectations.
- `vertex_count`: The number of vertices in the mesh.
- `original_positions`: An array of 3D vectors storing the initial, undeformed vertex positions.

**Outputs:**
- Updated vertex buffer in `rtcGeometry` reflecting the transformed positions.
- Commitment of the geometry and scene to make changes visible to the ray tracer.

**Data Structures:**
- Vertex buffer: A contiguous array of 3D floats (x, y, z) accessed via `rtcGetGeometryBufferData`.
- Temporary accumulator: `averagePt` (vec4, initialized to 0,0,0,1) and `maxlen` (float, initialized to 0).

**Steps:**
1. Retrieve the mutable vertex buffer pointer from `rtcGeometry` using `rtcGetGeometryBufferData`.
2. Initialize `averagePt = (0.0, 0.0, 0.0, 1.0)` and `maxlen = 0.0`.
3. Iterate through each vertex index $i$ from $0$ to `vertex_count` - 1:
   a. Reset the current vertex `vert[i]` to its original position from `original_positions`.
   b. Transform the vertex: $v = M \times \text{vert}[i]$.
   c. Update `vert[i].x`, `vert[i].y`, `vert[i].z` with $v.x, v.y, v.z$.
   d. Accumulate the transformed position: `averagePt` += $v$.
   e. Compute the running centroid $C_i = \text{averagePt} / \max(1, i+1)$.
   f. Compute the distance $d$ from $v$ to $C_i$.
   g. If $d > \text{maxlen}$, set `maxlen` = $d$.
4. Compute the final centroid $C_{final} = \text{averagePt} / \text{vertex\_count}$.
5. Commit the geometry using `rtcCommitGeometry(rtcGeometry)`.
6. Commit the scene using `rtcCommitScene(scene)` to update acceleration structures.

**Pitfalls:**
- The incremental computation of `maxlen` based on the distance to the running centroid is mathematically incorrect for determining the bounding radius or spread of the mesh [S1, unofficial]. It does not represent the true maximum distance from the final centroid or the bounding sphere radius.

**Pseudocode:**
```python
def transform_mesh_embree(rtc_geometry, mat, original_positions, vertex_count):
    # Get mutable vertex buffer
    vertices = rtcGetGeometryBufferData(rtc_geometry, RTC_BUFFER_TYPE_VERTEX)
    
    average_pt = [0.0, 0.0, 0.0, 1.0]
    maxlen = 0.0
    
    for i in range(vertex_count):
        # Reset to original
        orig = original_positions[i]
        vert = [orig.x, orig.y, orig.z, 1.0]
        
        # Transform
        v = mat_multiply_vec4(mat, vert)
        
        # Update buffer
        vertices[i].x = v[0]
        vertices[i].y = v[1]
        vertices[i].z = v[2]
        
        # Accumulate for centroid
        average_pt[0] += v[0]
        average_pt[1] += v[1]
        average_pt[2] += v[2]
        
        # Incremental centroid
        count = i + 1
        cx = average_pt[0] / count
        cy = average_pt[1] / count
        cz = average_pt[2] / count
        
        # Distance to running centroid
        dx = v[0] - cx
        dy = v[1] - cy
        dz = v[2] - cz
        d = sqrt(dx*dx + dy*dy + dz*dz)
        
        if d > maxlen:
            maxlen = d
            
    # Final centroid calculation (unused in the source logic but noted)
    # centroid = average_pt / vertex_count
    
    rtcCommitGeometry(rtc_geometry)
    rtcCommitScene(rtc_geometry.scene)
```

## Subtopics

### [Mesh Transformation](6214-mesh-transformation.md)
Applies a 4x4 transformation matrix to all vertices and normals of a mesh, updating the source mesh data in place while preserving the original positions in the source buffer. It differs from its parent [Mesh Transformation via Embree RTC](5669-mesh-transformation-via-embree-rtc.md) by operating directly on the mesh vertex array rather than maintaining a separate Embree geometry buffer with internal transformation matrices.

## Operating characteristics
- **Time Complexity:** $O(N)$ where $N$ is the number of vertices, due to the single pass loop over vertices.
- **Memory Complexity:** $O(1)$ auxiliary space, excluding the vertex buffer itself.
- **Performance:** Fast for dynamic meshes as it avoids reallocation. However, the incremental `maxlen` calculation is redundant and potentially misleading if used for bounding volume updates.
- **Limitations:** The method does not automatically update normals; normal transformation must be handled separately if required for lighting. The incorrect `maxlen` metric suggests that bounding box updates should be computed explicitly using `rtcSetGeometryUserBoundsFunction` or by manually computing the AABB of the transformed vertices.

## Background
This method is derived from implementation details in the FLod project, which uses Embree for high-performance rendering [S1, unofficial]. It represents a specific approach to handling dynamic geometry in Embree by directly modifying the vertex buffer rather than relying on Embree's built-in transformation matrices for static updates.
