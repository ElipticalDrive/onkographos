# Progressive View-Dependent Color Baking

Also called: Baked view-dependent color buffer, Progressive SH evaluation, Progressive Spherical Harmonics

## Overview
Progressive View-Dependent Color Baking is an optimization for 3D Gaussian Splatting that reduces memory bandwidth pressure caused by high-degree spherical harmonics (SH) by evaluating view-dependent colors over multiple frames rather than every frame [S1]. It alleviates the bottleneck where loading high-degree SH coefficients consumes more memory than the splat's geometric attributes, storing the evaluated results in a "baked" color buffer [S1]. Unlike standard per-frame SH evaluation, this method trades immediate visual fidelity for rendering performance, converging to the correct view-dependent color within a short, fixed number of frames [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** 3D Gaussian splats with stored SH coefficients (e.g., Degree 3), camera view direction, and a convergence parameter $N$ (number of frames to fully update all splats).
*   **Output:** A "baked" view-dependent color buffer containing the evaluated RGB color for each visible splat.

**Data Structures:**
*   **Splat Attributes:** Position, scale, orientation, base color, flags (52 bytes per splat) [S1].
*   **SH Coefficients:** For Degree 3, 45 additional floating-point values (15 coefficients $\times$ 3 RGB channels) [S1].
*   **Baked Color Buffer:** Stores the evaluated RGB color for each splat. Size depends on the number of visible splats. For Degree 3, the SH data adds 180 bytes per splat ($45 \times 4$ bytes) to the staging memory load, which is more than triple the 52 bytes of geometric data [S1].

**Algorithm:**
1.  **Initialization:** Create a baked color buffer for all visible splats. Initialize the buffer with the base color or previous frame's baked color [G].
2.  **Progressive Update Loop:** For each frame $f$ (where $f=1, 2, \dots, N$):
    a.  Determine the subset of splats to update. The fraction of splats updated per frame is $1/N$. A common setting is $N=10$ [S1].
    b.  Select a subset of splats (e.g., random or sequential) comprising $1/N$ of the total visible splats.
    c.  For each selected splat $i$:
        i.  Evaluate the spherical harmonics function $C(\mathbf{v}_i)$ using the splat's SH coefficients and the view direction $\mathbf{v}_i$ [S1].
        ii. Write the resulting RGB color to the baked color buffer for splat $i$ [S1].
    d.  For splats not selected in this frame, retain their previously baked color value [G].
3.  **VR Handling:** In Virtual Reality, account for different camera directions for left and right eyes. It is sufficient to bake colors for only one eye and reuse them for the other, or evaluate based on the direction to the center of both eyes [S1].
4.  **Rendering:** Use the baked color buffer for shading during the current frame's rasterization [S1].

**Pseudocode:**
```python
def progressive_sh_baking(splats, view_directions, num_frames_to_converge=10):
    """
    splats: List of splat objects, each with .sh_coeffs (Degree 3, 45 floats), .base_color
    view_directions: List of view direction vectors for each splat
    num_frames_to_converge: N, total frames to fully update all splats
    """
    num_splats = len(splats)
    # Initialize baked colors with base color [G]
    baked_colors = [splat.base_color for splat in splats]
    
    # Track how many times each splat has been updated
    update_counts = [0] * num_splats
    
    for frame in range(num_frames_to_converge):
        # Determine subset of splats to update this frame
        # To ensure full convergence in N frames, update 1/N of splats per frame
        # A simple round-robin or random selection works [G]
        splats_to_update = select_subset(splats, num_splats, 1.0 / num_frames_to_converge)
        
        for splat in splats_to_update:
            idx = splats.index(splat)
            # Evaluate SH for the current view direction
            # C(v) = sum_{l=0}^{L} sum_{m=-l}^{l} c_{lm} * Y_{lm}(v)
            # For Degree 3, L=3, 15 coefficients per channel, 45 total [S1]
            evaluated_color = evaluate_spherical_harmonics(splat.sh_coeffs, view_directions[idx])
            baked_colors[idx] = evaluated_color
            update_counts[idx] += 1
            
    return baked_colors

def select_subset(splats, total_count, fraction):

    num_to_update = int(total_count * fraction)
    # Simple sequential selection for determinism [G]
```

**Parameters:**
*   **Convergence Frames ($N$):** Number of frames to fully update all visible splats. Typical value: 10 [S1].
*   **SH Degree:** Degree 3 is common, requiring 45 coefficients per splat [S1].

**Edge Cases and Pitfalls:**
*   **VR Eye Discrepancy:** Left and right eyes have different view directions. Reusing baked colors from one eye for the other may cause slight inaccuracies, but is deemed sufficient [S1].
*   **Motion Artifacts:** Under high frame rates, progressive updates cause little to no apparent lag even under motion [S1].
*   **Memory Bandwidth:** High-degree SH (e.g., Degree 3) adds 180 bytes per splat to staging memory, which is a significant bottleneck compared to 52 bytes of geometric data [S1].

## Operating characteristics
**Time and Memory Complexity:**
*   **Memory:** Storing Degree 3 SH coefficients adds 180 bytes per splat ($45 \times 4$ bytes) to the staging pass memory load [S1]. This is more than triple the 52 bytes used for position, scale, orientation, color, and flags [S1].
*   **Time:** Updating all harmonics per frame is expensive. On the Kinuta scene, updating all harmonics takes 1.6 ms, while updating 1/10th takes 0.6 ms and 1/30th takes 0.5 ms [S1]. On the Campus scene, updating all harmonics takes 4.4 ms, while updating 1/10th takes 1.5 ms and 1/30th takes 1.1 ms [S1].

**Measured Performance:**
*   **Kinuta Scene:** All: 1.6 ms, 1/10th: 0.6 ms, 1/30th: 0.5 ms [S1].
*   **Campus Scene:** All: 4.4 ms, 1/10th: 1.5 ms, 1/30th: 1.1 ms [S1].
*   **Berlin Scene:** All: 0.4 ms, 1/10th: 0.2 ms, 1/30th: 0.1 ms [S1].
*   **Garden Scene:** All: 2.6 ms, 1/10th: 1.9 ms, 1/30th: 1.8 ms [S1].

**Strengths and Limitations:**
*   **Strengths:** Significantly reduces memory bandwidth pressure and staging time for high-degree SH [S1]. Convergence is typically fast enough (e.g., 10 frames) to cause barely noticeable artifacts [S1].
*   **Limitations:** Introduces a temporary lag in view-dependent color updates, which may be visible under rapid motion if frame rates are low [S1]. Requires additional memory for the baked color buffer [G].

**When to Use:**
*   Use when rendering high-degree SH (e.g., Degree 3) and memory bandwidth is a bottleneck [S1].
*   Use in VR where per-eye evaluation is expensive [S1].

**When Not to Use:**
*   Use when immediate, per-frame accurate view-dependent color is critical and frame rates are low [S1].
*   Use when SH degree is low (e.g., Degree 0 or 1) and bandwidth is not a concern [G].

## Background
Progressive View-Dependent Color Baking was introduced in the context of optimizing 3D Gaussian Splatting for large models and VR rendering [S1]. It addresses the performance bottleneck caused by the large memory footprint of high-degree spherical harmonics coefficients [S1]. The technique was developed as part of the Splatshop project, which focuses on efficiently editing large Gaussian Splat models [S1].
