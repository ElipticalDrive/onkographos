# Physics-based Gaussian Simulation

Also called: PhysGaussian, Gaussian Splashing, VR-GS, Spring-Gaus, Feature Splatting

## Overview
Physics-based Gaussian Simulation integrates continuum mechanics or particle dynamics directly into 3D Gaussian Splatting (3DGS), treating each Gaussian kernel as a discrete physical particle with volume [S1][S2, S3, unofficial]. This approach creates a unified simulation-to-rendering pipeline where the geometric representation serves as the simulation mesh, enabling physically accurate dynamics, real-time interaction, and editing of high-fidelity virtual content [S1][S2, S3, unofficial]. Unlike standard 3DGS which optimizes static appearance, these methods decouple or tightly couple physical state (position, velocity, deformation) from radiometric properties to support dynamic scenes [S3, unofficial].

## How it works

### Inputs and Outputs
**Inputs:**
1.  Initial 3DGS representation: A set of $N$ Gaussians $\{G_i\}_{i=1}^N$, where each $G_i$ is defined by mean position $\mu_i$, covariance matrix $\Sigma_i$ (or rotation $R_i$ and scale $S_i$), opacity $\alpha_i$, and spherical harmonic coefficients for color $c_i$ [S1][S2, S3, unofficial].
2.  Physical parameters: Mass $m_i$, damping coefficients, and material properties (e.g., stiffness, viscosity) [S3, unofficial].
3.  External forces: Gravity, collisions, or user interactions [S3, unofficial].

**Outputs:**
1.  Updated Gaussian parameters: New positions $\mu'_i$, covariances $\Sigma'_i$, and potentially updated colors/opacities if coupled with rendering [S1][S2, S3, unofficial].
2.  Rendered image: Computed via standard 3DGS rasterization using the updated physical state [S1][S2, S3, unofficial].

### Data Structures
The core data structure extends the standard 3DGS attribute list with physics-specific fields:
*   **Position ($\mu$):** 3D vector $(x, y, z)$ [S1][S2, S3, unofficial].
*   **Velocity ($v$):** 3D vector $(v_x, v_y, v_z)$ [S3, unofficial].
*   **Mass ($m$):** Scalar value, potentially learned from input video or assigned based on volume [S3, unofficial].
*   **Covariance ($\Sigma$):** $3 \times 3$ symmetric positive-definite matrix, often parameterized by rotation $R$ and scale $S$ [S1][S2, S3, unofficial].
*   **Physical State Flags:** Boolean or integer flags indicating if a Gaussian is part of the active simulation domain (e.g., fluid vs. solid) [S1][S2, unofficial].

### Steps
1.  **Initialization:**
    *   Reconstruct initial 3DGS from input images/video using standard 3DGS optimization [S1][S2, unofficial].
    *   Assign physical properties:
        *   Mass $m_i$ is learned from input video dynamics or estimated from Gaussian volume [S3, unofficial].
        *   Velocity $v_i$ is initialized to zero or estimated from temporal changes in position [S3, unofficial].
        *   Define material parameters (stiffness, damping) based on object type (solid, fluid) [S1][S3, unofficial].

2.  **Physics Simulation Step:**
    *   Compute forces $F_i$ acting on each Gaussian $i$:
        $$ F_i = F_{gravity} + F_{collision} + F_{interaction} + F_{internal} $$
        *   $F_{gravity} = m_i \cdot g$ [S3, unofficial].
        *   $F_{collision}$: Derived from contact detection with other Gaussians or static meshes [S1][S3, unofficial].
        *   $F_{internal}$: Depends on the chosen physics model:
            *   *Continuum Mechanics (PhysGaussian):* Uses continuum deformation of Gaussian kernels, treating the cloud as a deformable body [S3, unofficial].
            *   *Position-Based Dynamics (Gaussian Splashing):* Uses Position-Based Fluids (PBD) constraints to enforce incompressibility and cohesion [S1][S2, unofficial].
            *   *Spring-Mass (Spring-Gaus):* Applies spring forces between neighboring Gaussians based on a spring-mass model [S3, unofficial].
    *   Update velocity and position using a numerical integrator (e.g., Verlet or Euler):
        $$ v_i^{t+1} = v_i^t + \frac{F_i}{m_i} \Delta t $$
        $$ \mu_i^{t+1} = \mu_i^t + v_i^{t+1} \Delta t $$
        [S3, unofficial].
    *   Update covariance $\Sigma_i$ to reflect deformation:
        *   For continuum deformation, $\Sigma_i$ is transformed by the local deformation gradient [S3, unofficial].
        *   For PBD, $\Sigma_i$ may be adjusted to maintain volume consistency [S1][S2, unofficial].

3.  **Rendering Step:**
    *   Rasterize the updated Gaussians using standard 3DGS alpha blending [S1][S2, S3, unofficial].
    *   *Deferred Shading:* Some methods (e.g., VR-GS) use deferred shading to avoid blending artifacts from multiple shading calculations [S3, unofficial].
    *   *Material Rendering:* For fluids/solids, material parameters (diffusiveness, specularity, roughness, normals) are applied to each Gaussian to enhance physical appearance [S1][S2, unofficial]. Normals are aligned with surface normals to improve reflection accuracy [S3, unofficial].

### Pseudocode
```python
def physics_based_gaussian_simulation(gaussians, dt, external_forces):
    """
    Simulate physics for a set of 3D Gaussians.
    
    Args:
        gaussians: List of Gaussian objects with attributes:
            - mu: (3,) position vector
            - v: (3,) velocity vector
            - m: float mass
            - Sigma: (3,3) covariance matrix
            - type: str ('solid', 'fluid', 'particle')
        dt: float time step
        external_forces: dict of force functions, e.g., {'gravity': lambda m: m * 9.81}
        
    Returns:
        Updated list of Gaussians
    """
    for g in gaussians:
        # 1. Compute Forces
        F = np.zeros(3)
        
        # Gravity
        if 'gravity' in external_forces:
            F += external_forces['gravity'](g.m)
            
        # Internal Forces (Model-dependent)
        if g.type == 'solid':
            # Continuum mechanics or Spring-Mass
            # Example: Spring-Mass with neighbors
            for neighbor in get_neighbors(g, gaussians):
                displacement = g.mu - neighbor.mu
                distance = np.linalg.norm(displacement)
                if distance > 0:
                    # Hooke's Law
                    F += -k * (distance - rest_length) * (displacement / distance)
        elif g.type == 'fluid':
            # Position-Based Dynamics (PBD)
            # Compute density and pressure
            density = compute_density(g, gaussians)
            pressure = compute_pressure(density)
            # Apply pressure force
            F -= pressure * gradient_of_density(g, gaussians)
            
        # Collision Forces
        for other in gaussians:
            if g is other: continue
            dist = np.linalg.norm(g.mu - other.mu)
            if dist < collision_radius:
                # Repulsive force
                F += repulsion_force(g, other, dist)
                
        # 2. Integrate
        # Verlet integration or Euler
        a = F / g.m
        g.v += a * dt
        g.mu += g.v * dt
        
        # 3. Update Covariance (Deformation)
        if g.type == 'solid':
            # Update Sigma based on deformation gradient
            # Simplified: Rotate and scale based on velocity gradient
            g.Sigma = update_covariance(g, g.v, dt)
            
    return gaussians
```

### Parameters
*   **Time Step ($\Delta t$):** Typically $1/60$ s for real-time VR [S3, unofficial].
*   **Stiffness ($k$):** For spring-mass models, tuned to prevent oscillation [S3, unofficial].
*   **Collision Radius:** Determines interaction range between Gaussians [S3, unofficial].
*   **Mass ($m$):** Learned from input video or estimated from volume [S3, unofficial].

### Edge Cases and Pitfalls
*   **Precision:** High-velocity simulations may require double precision to avoid numerical instability [G].
*   **Boundaries:** Gaussians near scene boundaries may experience incorrect collision forces if not handled with boundary conditions [G].
*   **Degenerate Input:** If initial Gaussians are poorly distributed, physics simulation may produce unrealistic artifacts (e.g., clumping) [S3, unofficial].
*   **Performance:** Computing neighbor interactions for large $N$ is $O(N^2)$ without spatial hashing [G].

## Subtopics

### OTS Marching Ray Marching Algorithm
*   **What it is:** A ray-marching algorithm for distance fields.
*   **Difference:** Focuses on efficient ray traversal for implicit surfaces, not physics simulation.
*   **When to choose:** When rendering static or deforming distance fields without explicit particle dynamics.
*   **Link:** [OTS Marching Ray Marching Algorithm](1073-ots-marching-ray-marching-algorithm.md)

### View-dependent color with Spherical Harmonics
*   **What it is:** Technique to encode view-dependent appearance using spherical harmonics.
*   **Difference:** Handles radiometric properties, not physical dynamics.
*   **When to choose:** When view-dependent effects (specularity) are needed but physics is not.
*   **Link:** [View-dependent color with Spherical Harmonics](1369-view-dependent-color-with-spherical-harmonics.md)

### Weighted Blending (Fuzzy Metaballs)
*   **What it is:** Blending technique for smooth volume rendering.
*   **Difference:** Focuses on visual blending, not physical forces.
*   **When to choose:** When smooth, blobby appearance is desired without physics.
*   **Link:** [Weighted Blending (Fuzzy Metaballs)](3691-weighted-blending-fuzzy-metaballs.md)

### Two-Stage Optimization Pipeline
*   **What it is:** Optimization strategy for 3DGS.
*   **Difference:** Focuses on training convergence, not runtime simulation.
*   **When to choose:** When training static 3DGS models.
*   **Link:** [Two-Stage Optimization Pipeline](15284-two-stage-optimization-pipeline.md)

## Operating characteristics

### Time and Memory Complexity
*   **Time:** Physics simulation is $O(N)$ for simple forces but $O(N^2)$ for neighbor interactions without spatial acceleration structures [G]. Rendering remains $O(N)$ per pixel [S1][S2, unofficial].
*   **Memory:** Additional memory for velocity, mass, and neighbor lists [S3, unofficial].

### Measured Performance
*   **Hardware:** Tested on VR headsets and GPUs [S3, unofficial].
*   **Resolution:** Real-time at 1080p for moderate $N$ [S3, unofficial].
*   **Scene:** Dynamic scenes with interacting objects [S3, unofficial].

### Scaling
*   Scales with number of Gaussians; spatial hashing can reduce neighbor search to $O(N)$ [G].

### Strengths and Limitations
*   **Strengths:** Physically accurate dynamics, real-time interaction, high-fidelity rendering [S3, unofficial].
*   **Limitations:** Computationally expensive for large scenes, requires careful tuning of physical parameters [S3, unofficial].

### When to Use
*   Use for dynamic, interactive scenes requiring physical realism [S3, unofficial].
*   Do not use for static scenes or when performance is critical and physics is not needed [S3, unofficial].

## Background

### Origin
*   **PhysGaussian:** Integrates physics-based continuum mechanics directly within 3DGS [S1][S2, unofficial].
*   **Gaussian Splashing:** Combines 3DGS with Position-Based Dynamics (PBD) for fluids [S1][S2, unofficial].
*   **VR-GS:** Physical dynamics-aware interactive Gaussian Splatting for VR [S3, unofficial].
*   **Spring-Gaus:** Applies spring-mass model to dynamic 3DGS [S3, unofficial].

### History
*   Developed as extensions to 3DGS to enable animation and dynamic content [S1][S2, S3, unofficial].
*   Addresses the gap between generated and manually crafted 3D content in VR/AR [S3, unofficial].

### Applications
*   VR/AR environments, robotics, autonomous driving, and dynamic scene editing [S3, unofficial].
