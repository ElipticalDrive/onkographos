# Multi-Material Distance Fields

Also called: Augmented SDF signature, Color-Coded SDFs, Material-Augmented Signed Distance Function, MaterialSDF, SDF with Material Data, SDF with material ID

## Overview
Multi-Material Distance Fields extend standard Signed Distance Functions (SDFs) to return both a geometric distance and a material identifier, enabling per-object material assignment within Constructive Solid Geometry (CSG) scenes [S1, unofficial][S2, unofficial]. Unlike sibling operators like [SDF Smooth Union](1817-sdf-smooth-union.md) which focus on geometric blending, this method preserves the sharp boolean logic of CSG while propagating shading data, allowing the renderer to determine surface color based on the closest object's material ID rather than just its depth [S1, unofficial][S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A position vector $p$ in world space.
*   **Output:** A pair $(d, m)$, where $d$ is the signed distance to the nearest surface and $m$ is the material identifier (e.g., an integer index or a normalized color value) associated with that surface [S1, unofficial][S2, unofficial].

**Data Structures:**
The scene is represented as a CSG tree. Each leaf node contains:
1.  An SDF function $SDF_i(p)$ returning a scalar distance.
2.  A material identifier $M_i$ [S1, unofficial].

In shader implementations, the output is typically a `float2` (or `vec2`):
*   `x` component: Distance $d$.
*   `y` component: Material data $m$ (e.g., color index or direct color value) [S2, unofficial].

**Algorithm:**
The evaluation is recursive. For a leaf node, the SDF is evaluated directly. For internal nodes (Union, Intersection, Difference), the results of the left and right children are combined. The combination logic compares the distance components ($d$) to determine the closest surface, then selects the corresponding material component ($m$) from the winning child.

1.  **Leaf Evaluation:**
    For a leaf node with SDF function $f$ and material ID $m_{leaf}$:
    $$ (d, m) = (f(p), m_{leaf}) $$

2.  **Union Operation:**
    Given left result $(d_a, m_a)$ and right result $(d_b, m_b)$:
    *   If $d_a \le d_b$: Return $(d_a, m_a)$.
    *   Else: Return $(d_b, m_b)$.
    *   *Logic:* The union takes the minimum distance. The material of the closest object is preserved [S1, unofficial][S2, unofficial].

3.  **Intersection Operation:**
    Given left result $(d_a, m_a)$ and right result $(d_b, m_b)$:
    *   If $d_a \ge d_b$: Return $(d_a, m_a)$.
    *   Else: Return $(d_b, m_a)$.
    *   *Logic:* The intersection takes the maximum distance (deepest inside both). The material is taken from the left child ($m_a$) if the left child is the limiting factor ($d_a \ge d_b$), otherwise it takes the right child's distance but *still* uses the left child's material. This specific behavior ensures the material corresponds to the "primary" object in the CSG tree structure, or specifically, the source code dictates that in the `else` branch (where $d_b > d_a$), the returned material is $m_a$ [S1, unofficial]. *Note: Standard CSG intersection usually implies the material of the object being intersected into, but the provided source explicitly assigns $m_a$ in the else case.*

4.  **Difference Operation:**
    Given left result $(d_a, m_a)$ and right result $(d_b, m_b)$:
    *   If $d_a \ge -d_b$: Return $(d_a, m_a)$.
    *   Else: Return $(-d_b, m_a)$.
    *   *Logic:* Difference is $A \setminus B$. The distance is $\max(d_a, -d_b)$. If the left object is closer to the surface (or outside the right object), keep left material. If the right object cuts into the left, the distance becomes $-d_b$ (inside the cut), but the material remains $m_a$ (the material of the object being carved) [S1, unofficial].

**Pseudocode:**
```python
import math

# Type definitions for clarity
# Vector: (x, y, z) float3
# MaterialID: float or int

def evaluate_material_sdf(tree: dict, p: tuple) -> tuple:
    """
    Recursively evaluates the MaterialSDF for a CSG tree node.
    
    Args:
        tree: A dictionary representing a CSG node.
              Structure:
              - If leaf: {'type': 'leaf', 'sdf_func': callable, 'material': MaterialID}
              - If internal: {'type': 'internal', 'left': tree, 'right': tree, 'op': 'union'|'intersection'|'difference'}
        p: The 3D position vector (x, y, z).
        
    Returns:
        A tuple (distance: float, material: MaterialID).
    """
    
    # Base case: Leaf node
    if tree['type'] == 'leaf':
        sdf_func = tree['sdf_func']
        material = tree['material']
        distance = sdf_func(p)
        return (distance, material)
    
    # Recursive case: Internal node
    left_tree = tree['left']
    right_tree = tree['right']
    operation = tree['op']
    
    # Evaluate children
    d_a, m_a = evaluate_material_sdf(left_tree, p)
    d_b, m_b = evaluate_material_sdf(right_tree, p)
    
    if operation == 'union':
        # Union: min distance, keep material of closest
        if d_a <= d_b:
            return (d_a, m_a)
        else:
            return (d_b, m_b)
            
    elif operation == 'intersection':
        # Intersection: max distance, material logic from source
        if d_a >= d_b:
            return (d_a, m_a)
        else:
            # Source: case ((_, am), (b, _)) => (b, am)
            # Distance is d_b, material is m_a
            return (d_b, m_a)
            
    elif operation == 'difference':
        # Difference: max(d_a, -d_b), material logic from source
        if d_a >= -d_b:
            return (d_a, m_a)
        else:
            # Source: case ((_, am), (b, _)) => (-b, am)
            # Distance is -d_b, material is m_a
            return (-d_b, m_a)
            
    else:
        raise ValueError(f"Unknown operation: {operation}")

def raymarch_material_scene(scene_tree: dict, ray_origin: tuple, ray_direction: tuple, color_ramp: list) -> tuple:
    """
    Standard raymarching loop using Multi-Material SDF.
    
    Args:
        scene_tree: The root of the MaterialSDF CSG tree.
        ray_origin: Ray origin (x, y, z).
        ray_direction: Ray direction (x, y, z).
        color_ramp: A list/array mapping material IDs to colors.
        
    Returns:
        A color tuple (r, g, b, a).
    """
    
    max_steps = 64
    t = 0.0
    hit_material = None
    
    for i in range(max_steps):
        p = (
            ray_origin[0] + ray_direction[0] * t,
            ray_origin[1] + ray_direction[1] * t,
            ray_origin[2] + ray_direction[2] * t
        )
        
        # Sample the augmented SDF
        d, m = evaluate_material_sdf(scene_tree, p)
        
        # Hit condition
        if d < 0.001:
            hit_material = m
            break
            
        # Advance ray
        t += d
        
    if hit_material is not None:
        # Sample color ramp using material ID
        # Assuming color_ramp is indexed by integer material IDs
        # If material is float color, use directly
        if isinstance(hit_material, (int, float)) and hit_material < len(color_ramp):
            color = color_ramp[hit_material]
        else:
            # Fallback or direct color usage if material is already a color value
            color = hit_material if isinstance(hit_material, tuple) else (1.0, 1.0, 1.0)
        
        # Calculate lighting (simplified)
        # Normal calculation would require gradient of SDF
        # For brevity, returning flat color
        return (*color, 1.0)
    else:
        return (0.0, 0.0, 0.0, 1.0) # Background
```

**Parameters:**
*   **ColorRamp:** A texture or array mapping material IDs (the $y$-component of the map output) to colors [S2, unofficial].
*   **Max Steps:** Typically 64 or more, depending on scene complexity and required precision [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Lipschitz Continuity:** While the distance combination logic preserves the geometric properties of the underlying SDFs, the *material* assignment is discrete. At the boundary where $d_a = d_b$, the material may flip abruptly between $m_a$ and $m_b$. This is expected for boolean CSG but can cause aliasing if the camera moves rapidly across these boundaries [S1, unofficial].
*   **Intersection/Difference Material Logic:** The specific material assignment in Intersection and Difference operations (always taking $m_a$ from the left child in the source code) is a design choice. It implies the "primary" object's material is retained even when the surface is defined by the secondary object's geometry. This may not be desired for all visual styles (e.g., if cutting a hole in a red box with a blue sphere, the hole's interior might be expected to be blue, but the source code returns red) [S1, unofficial].
*   **Precision:** Comparing floating-point distances $d_a$ and $d_b$ for equality can be unstable. Using a small epsilon for the hit condition ($d < 0.001$) is standard, but the branch decision in Union/Intersection should use strict inequalities as defined to avoid infinite loops or incorrect material selection at exact boundaries [S1, unofficial][S2, unofficial].

## Subtopics

### [Material Object Format](1981-material-object-format.md)
A data structure that holds surface shading information, including color, physical properties, and texture descriptors, accessible from both host and device code. It distinguishes itself by explicitly separating geometric displacement (via `heightmapTex`) from shading calculations and by managing texture projection modes and normal deflection scaling.

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the depth of the CSG tree, per ray step. The raymarching loop adds a factor of $K$ (number of steps). Total complexity is $O(K \cdot N)$ per pixel.
*   **Memory Complexity:** $O(N)$ to store the CSG tree structure. The material data is stored per leaf.
*   **Performance:** The addition of material tracking adds negligible computational overhead compared to standard SDF raymarching, as it involves only passing an extra scalar/vector component through the same comparison logic [S2, unofficial].
*   **Strengths:** Enables complex multi-material scenes with CSG operations without requiring multiple render passes or complex shader branching for material selection. Shadows are straightforward to calculate using the depth buffer and the same SDF [S1, unofficial].
*   **Limitations:** Material boundaries are sharp (discrete). The material assignment logic in Intersection/Difference is fixed by the tree structure (left-child dominance in the provided implementation), which may not match all artistic requirements.

## Background
The technique was popularized in the context of real-time raymarching shaders, notably by Jamie Wong and Iñigo Quilez. It allows for the creation of complex, multi-colored geometric scenes using simple SDF primitives and CSG operations. The approach is detailed in tutorials on raymarching signed distance functions and is implemented in various open-source projects and educational resources [S1, unofficial][S2, unofficial].
