# Multi-Material Distance Fields

Also called: Color-Coded SDFs, SDF with Material Data

## Overview
Multi-Material Distance Fields extend standard Signed Distance Functions (SDFs) by associating material properties, such as color or texture indices, with geometric primitives. This method solves the problem of rendering composite scenes with distinct visual materials using a single raymarching pass, avoiding the need for separate rendering passes or complex shader branching for material selection. It differs from [SDF Smooth Union](1817-sdf-smooth-union.md) by prioritizing correct material attribution and sharp material boundaries over the smooth blending of distance values, although it often utilizes similar combination operators for spatial union.

## How it works
The method modifies the standard SDF evaluation pipeline to return a vector containing both the geometric distance and material metadata.

**Inputs and Outputs:**
*   **Input:** Ray origin $ro$, ray direction $rd$, maximum travel distance.
*   **Output:** Final pixel color determined by the material of the closest intersected object.

**Data Structures:**
*   **Map Return Type:** A vector (e.g., `float2` in GLSL/HLSL) where:
    *   Component 0 ($x$): The signed distance value $d$.
    *   Component 1 ($y$): Material identifier $m$ (e.g., a float in $[0, 1]$ representing an index into a color ramp).

**Numbered Steps:**

1.  **Define Primitive Maps:** Each primitive function (e.g., sphere, box) returns a vector. The distance component is the result of the primitive's SDF calculation. The material component is a constant or interpolated value unique to that primitive.
    $$ \text{map}_{\text{prim}}(p) = \begin{bmatrix} \text{SDF}_{\text{prim}}(p) \\ m_{\text{prim}} \end{bmatrix} $$
    Where $m_{\text{prim}}$ is the material ID for that primitive [S1].

2.  **Combine with Modified Union:** Use a modified union operator `opU` that accepts two material vectors. It compares only the distance components ($x$) to determine the closest surface but returns the entire vector (distance and material) of the closer object.
    $$ \text{opU}(d_1, d_2) = \begin{cases} d_1 & \text{if } d_1.x < d_2.x \\ d_2 & \text{otherwise} \end{cases} $$
    This ensures that the material ID corresponds to the object that actually intersects the ray [S1].

3.  **Raymarch Loop:**
    *   Initialize ray position $p = ro$ and distance traveled $t = 0$.
    *   Iterate up to a maximum step count.
    *   Evaluate $d = \text{map}(p)$, where $\text{map}(p)$ is the result of combining all primitive maps using `opU`.
    *   Check hit condition: if $d.x < \epsilon$ (a small threshold, e.g., $0.001$), a surface is hit.
    *   If hit, break the loop. Otherwise, advance $t \leftarrow t + d.x$ and update $p \leftarrow ro + rd \cdot t$.

4.  **Material Sampling:** Upon intersection, use the material component $d.y$ to sample a color ramp texture (or lookup table) to determine the base color of the surface.
    $$ C_{\text{base}} = \text{Texture2D}(\text{ColorRamp}, d.y) $$
    The final color is then computed using standard lighting models (diffuse, specular) based on $C_{\text{base}}$ and the surface normal [S1].

**Pseudocode:**

```python
# GLSL/HLSL-style pseudocode for the core logic

# Union operator for multi-material SDFs
# d1, d2: float2 where x=distance, y=material_id
float2 opU(float2 d1, float2 d2) {
    return (d1.x < d2.x) ? d1 : d2;
}

# Primitive map functions return float2
float2 map_torus(float3 p) {
    float dist = sd_torus(p, float2(1.0, 0.2));
    float mat_id = 0.5; // Example material ID
    return float2(dist, mat_id);
}

float2 map_box(float3 p) {
    float dist = sd_box(p - float3(-3.0, 0.0, 0.0), float3(0.75, 0.5, 0.5));
    float mat_id = 0.25; // Example material ID
    return float2(dist, mat_id);
}

float2 map_sphere(float3 p) {
    float dist = sd_sphere(p - float3(3.0, 0.0, 0.0), 1.0);
    float mat_id = 0.75; // Example material ID
    return float2(dist, mat_id);
}

// Combined map function
float2 map(float3 p) {
    float2 d_torus = map_torus(p);
    float2 d_box = map_box(p);
    float2 d_sphere = map_sphere(p);
    
    float2 ret = opU(d_torus, d_box);
    ret = opU(ret, d_sphere);
    
    return ret;
}

// Raymarching step
float4 raymarch(float3 ro, float3 rd) {
    float t = 0.0;
    float2 d;
    bool hit = false;
    
    for (int i = 0; i < 64; i++) {
        float3 p = ro + rd * t;
        d = map(p);
        
        if (d.x < 0.001) {
            hit = true;
            break;
        }
        t += d.x;
    }
    
    if (hit) {
        // Sample color from ramp using material ID
        float color_val = d.y;
        float3 base_color = texture2D(_ColorRamp, float2(color_val, 0.5)).rgb;
        
        // Calculate normal and lighting [G]
        float3 n = calc_normal(p);
        float3 light_dir = normalize(float3(1.0, 1.0, -1.0));
        float diff = max(dot(n, light_dir), 0.0);
        
        return float4(base_color * diff, 1.0);
    } else {
        return float4(0.0, 0.0, 0.0, 1.0); // Background
    }
}
```

**Parameters:**
*   **ColorRamp:** A `sampler2D` texture mapping material IDs (y-component) to RGB colors [S1].
*   **Threshold:** A small epsilon value (e.g., $0.001$) for hit detection [S1].

**Edge Cases and Pitfalls:**
*   **Precision:** If two objects are extremely close, floating-point precision errors in the distance comparison $d_1.x < d_2.x$ may cause flickering or incorrect material assignment.
*   **Material ID Range:** Ensure material IDs are normalized to $[0, 1]$ if using a standard 1D color ramp texture, or adjust texture coordinates accordingly [S1].

## Subtopics

### [Material Object Format](1981-material-object-format.md)
A data structure for encapsulating PBR properties and texture descriptors in distance-field ray marching, distinguishing itself by separating geometric displacement from shading calculations.

## Operating characteristics
*   **Time Complexity:** $O(N)$ per pixel, where $N$ is the number of raymarching steps. The cost of evaluating the material ID is negligible compared to the SDF evaluation.
*   **Memory Complexity:** $O(1)$ additional memory per primitive for material IDs. The color ramp texture requires additional VRAM.
*   **Strengths:** Efficient single-pass rendering of multi-material scenes; no need for complex branching or multiple render passes.
*   **Limitations:** Material boundaries are sharp unless explicitly blended; does not handle subsurface scattering or complex material interactions natively.
*   **When to use:** Ideal for real-time rendering of composite objects with distinct materials (e.g., toys, mechanical parts) where performance is critical.
*   **When not to use:** When smooth material transitions or physically accurate light transport between materials is required.

## Background
The technique was popularized by Inigo Quilez in his articles on distance functions and later implemented in real-time engines like Unity by Adrian Ball [S1, unofficial]. It builds on the concept of SDF primitives and boolean operations, extending them to carry semantic information (material) alongside geometric data.
