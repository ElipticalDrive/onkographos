# Dynamic SDF Ray Marching with Structured Buffers

Also called: Procedural Geometry Ray Marching, SDF Ray Marching with Dynamic Object Buffers, SDF Ray Marching with GPU Buffers

## Overview
This method renders dynamic, complex scenes by streaming object definitions from the CPU to the GPU in structured buffers, allowing for per-pixel evaluation of multiple objects without hardcoding the scene geometry in the shader [S1, S2, unofficial]. Unlike static SDF implementations where the scene is hardcoded in GLSL, this approach enables dynamic worlds with many moving characters and objects by replacing CPU-side ray termination logic with a GPU-side buffer of object structs that return a composite type (distance, color, ID) from the distance function [S1, S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A subset of scene objects (culled from the full scene), passed as a structured buffer on the GPU. Each element defines the object's type, position, rotation, scale, and average color [S1, S2, unofficial].
*   **Output:** For each pixel, the final color and depth, derived from the closest object hit by the ray [S1, S2, unofficial].

**Data Structures:**
1.  **Render Input Buffer (GPU Structured Buffer):**
    *   Layout: Array of `ObjectDefinition` structs.
    *   `ObjectDefinition` fields:
        *   `id`: Integer identifier (inferred from buffer index during search) [S1, S2, unofficial].
        *   `type`: Enum or integer indicating the SDF primitive type (e.g., sphere, box) [S1, S2, unofficial].
        *   `position`: `float3` (world space position) [S1, S2, unofficial].
        *   `rotation`: `float3` or `quat` (orientation) [S1, S2, unofficial].
        *   `scale`: `float3` (uniform or non-uniform scaling) [S1, S2, unofficial].
        *   `color`: `float3` (average/base color) [S1, S2, unofficial].
2.  **Distance Function Return Struct:**
    *   Layout: `struct { float distance; float3 color; int id; }` [S2, unofficial].
    *   `distance`: The local signed distance to the object's surface [S1, S2, unofficial].
    *   `color`: The color associated with the hit object [S1, S2, unofficial].
    *   `id`: The ID of the object in the input buffer that produced this distance [S1, S2, unofficial].

**Numbered Steps:**
1.  **Culling:** Cull the scene into a manageable subset of objects visible in the view frustum. Ray-marching performs automatic partial occlusion culling, and frustum/occlusion culling are partly automatic [S1, S2, unofficial].
2.  **Buffer Preparation:** Pass the subset of objects into a render input buffer on the CPU. Create a typed buffer (e.g., C-style struct) where each element defines the object's function type, position, rotation, scale, and average color [S1, S2, unofficial].
3.  **Upload:** Transfer the buffer to the GPU if it is not already present [S1, S2, unofficial].
4.  **Ray Marching Loop (Per Pixel):**
    *   Initialize ray $r(t) = \mathbf{o} + t\mathbf{d}$ [G].
    *   For each iteration $k$:
        *   **Buffer Search:** Perform a per-step search through the input buffer to evaluate which item is closest to the current ray position $\mathbf{p} = \mathbf{o} + t\mathbf{d}$ [S1, S2, unofficial].
        *   **Transform Application:** Apply transforms to either the rays (inverting figure rotations before GPU upload) or the distance functions (moving function origin for position changes, adjusting side lengths for scale changes) [S1, S2, unofficial]. The simplest approach is to modify the rays before passing them to the core distance function [S1, S2, unofficial].
        *   **SDF Evaluation:** Evaluate the SDF for each object. The distance function returns a complex type (struct) containing the local distance, local color, and an ID tied to the input buffer element [S1, S2, unofficial].
        *   **ID Inference:** The ID is inferred from the loop counter of the buffer search, as the mapping function loops through the input buffer to find the closest figure [S1, S2, unofficial].
        *   **Color Determination:** Determine the color from the average color of the buffer element corresponding to the ID, or procedurally (e.g., mapping iteration count to a palette weighted towards the stored average) [S1, S2, unofficial].
        *   **Step Size:** Use the minimum distance found across all objects in the buffer as the step size for the next iteration [S1, S2, unofficial].
        *   **Termination:** If the minimum distance $< \epsilon$ (convergence threshold), the ray has hit the closest object. Terminate the loop [G].
5.  **Shading:** Pass the output color directly to the screen or into lighting code based on the collision point and the returned ID/color [S1, S2, unofficial].

**Pseudocode:**
```python
import math

def vec3_sub(a, b):
    return [a[0]-b[0], a[1]-b[1], a[2]-b[2]]

def vec3_len(v):
    return math.sqrt(v[0]**2 + v[1]**2 + v[2]**2)

class ObjectDefinition:
    def __init__(self, obj_id, obj_type, position, rotation, scale, color):
        self.id = obj_id
        self.type = obj_type
        self.position = position
        self.rotation = rotation
        self.scale = scale
        self.color = color

class SDFResult:
    def __init__(self, distance, color, obj_id):
        self.distance = distance
        self.color = color
        self.id = obj_id

def sdf_sphere(p, center, radius):
    return vec3_len(vec3_sub(p, center)) - radius

def evaluate_object_sdf(p, obj):
    # Transform point to local object space
    # Rotation transformation omitted; apply inverse rotation matrix to local_p [G]
    local_p = [(p[i] - obj.position[i]) / obj.scale[i] for i in range(3)]

    dist = float('inf')
    if obj.type == 0: # Sphere
        dist = sdf_sphere(local_p, [0.0, 0.0, 0.0], 1.0)
    elif obj.type == 1: # Box
        d = [abs(local_p[0]) - 1.0, abs(local_p[1]) - 1.0, abs(local_p[2]) - 1.0]
        dist = max(d[0], max(d[1], d[2]))
    return SDFResult(distance=dist, color=obj.color, obj_id=obj.id)

def ray_march(ray_origin, ray_direction, objects, max_steps=64, epsilon=0.001, max_dist=100.0):
    t = 0.0
    hit_color = [0.0, 0.0, 0.0]

    for _ in range(max_steps):
        current_pos = [ray_origin[i] + t * ray_direction[i] for i in range(3)]

        min_result = SDFResult(distance=float('inf'), color=[0.0, 0.0, 0.0], obj_id=-1)

        for i in range(len(objects)):
            obj = objects[i]
            result = evaluate_object_sdf(current_pos, obj)
            if result.distance < min_result.distance:
                min_result = result

        if min_result.distance < epsilon:
            hit_color = min_result.color
            break
        elif t > max_dist:
            break

        t += min_result.distance

    return hit_color
```

**Parameters:**
*   **Transform Strategy:** Either transform rays (requires inverting rotations on CPU) or transform distance functions (adjust origin for position, side lengths for scale) [S1, unofficial].
*   **Color Generation:** Can use average color from buffer element or procedural color weighted towards stored average [S1, S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Performance:** The method requires a per-step search through the input buffer for every ray iteration, which can be computationally expensive compared to static scenes [S1, unofficial].
*   **Precision:** Transforming points to local space for SDF evaluation requires careful handling of rotation and scale to avoid precision issues, especially with large scenes or extreme scales [G].
*   **Buffer Size:** The number of objects in the buffer directly impacts performance. Culling is essential to keep the buffer size manageable [S1, S2, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N \cdot M)$ per pixel, where $N$ is the number of objects in the buffer and $M$ is the number of ray-marching steps. This is significantly slower than static SDF rendering where $N$ is effectively constant or hardcoded [G].
*   **Memory Complexity:** $O(N)$ for the structured buffer on the GPU. Not given in the sources.
*   **Strengths:** Dynamic scenes, easy to add/remove objects, no need to recompile shaders for scene changes. Not given in the sources.
*   **Limitations:** Performance degrades linearly with the number of objects. Not suitable for very large numbers of objects without additional acceleration structures (e.g., BVH, which is not covered in the basic structured buffer approach). Not given in the sources.
*   **When to Use:** Real-time rendering of dynamic scenes with a moderate number of objects where procedural geometry is desired. Not given in the sources.
*   **When Not to Use:** Scenes with thousands of objects, or where maximum performance is critical and the scene is static. Not given in the sources.

## Background
This method was described in the context of implementing Signed Distance Field (SDF) ray marching for dynamic worlds, specifically addressing how to stream objects to the GPU and handle multiple colors without hardcoding the scene in GLSL [S1, S2, unofficial]. It is used in procedural geometry engines and real-time SDF rendering, such as in the Claybook engine [S2, unofficial]. The approach leverages GPU structured buffers (or equivalent typed buffers in HLSL/GLSL) to pass complex object data to the shader, allowing the distance function to return a composite type including distance, color, and ID [S1, S2, unofficial].
