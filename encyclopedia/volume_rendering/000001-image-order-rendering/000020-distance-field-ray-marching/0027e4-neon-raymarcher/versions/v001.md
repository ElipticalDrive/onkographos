# Neon Raymarcher

Also called: Procedural Synthwave City Renderer, SDF Ray Marching in WebGL2

## Overview
Neon Raymarcher is a real-time WebGL2 renderer that generates an infinite procedural synthwave city using signed-distance fields (SDFs) within a single fullscreen fragment shader, requiring no meshes, textures, or scene graph [S1, unofficial]. It distinguishes itself from general-purpose SDF renderers by employing a deterministic integer hashing contract shared between CPU and GPU to generate building footprints and materials, and by defining the scene geometry via an analytic road centerline curve rather than static primitives [S1, unofficial].

## How it works
The method renders a scene by shooting rays from a camera through a fullscreen quad and sphere-tracing a procedural environment defined by a road curve and domain-repeated building blocks.

**Inputs and Outputs:**
*   **Inputs:** Camera state (position, orthonormal basis vectors: right, up, forward), time, resolution.
*   **Outputs:** A color buffer representing the rendered frame.

**Data Structures:**
The scene is not stored in memory structures but is defined by constants and functions evaluated per-pixel.
*   **Road Constants:**
    *   `RD_A1 = 6.0`, `RD_A2 = 3.0`, `RD_A3 = 1.2` (Amplitudes)
    *   `RD_F1 = 0.03141593` ($2\pi/200$), `RD_F2 = 0.06613879` ($2\pi/95$), `RD_F3 = 0.11424174` ($2\pi/55$) (Frequencies)
    *   `RD_P2 = 1.7`, `RD_P3 = 4.2` (Phases)
*   **Building Grid Constants:**
    *   `BLOCK_WIDTH = 13.0`, `BLOCK_DEPTH = 14.0`
    *   `MARGIN = 1.5`
    *   `MAX_STEPS = 128`
    *   `MAX_DIST = 180.0`
*   **Hashing Contract:** A deterministic 32-bit integer hash function `uhash` and cell hash `hashCell` implemented identically in TypeScript (CPU) and GLSL (GPU) to ensure consistency between rendering and game logic [S1, unofficial].

**Step-by-Step Method:**

1.  **Initialization:**
    *   Create a WebGL2 context with antialiasing disabled and alpha disabled [S1, unofficial].
    *   Generate a fullscreen triangle using `gl_VertexID` and compile/link vertex and fragment shaders [S1, unofficial].
    *   Cache uniform locations for `uResolution`, `uTime`, `uCamPos`, `uCamRight`, `uCamUp`, `uCamForward` [S1, unofficial].
    *   On each frame, resize the canvas to `clientSize * devicePixelRatio * renderScale` and set the viewport [S1, unofficial].

2.  **Camera Basis Calculation:**
    *   The camera follows the road centerline. Let $z$ be the camera's longitudinal position.
    *   Calculate current position: $p_{cam} = [\text{roadX}(z), \text{height}, z]$ [S1, unofficial].
    *   Calculate target position: $p_{target} = [\text{roadX}(z + \text{lookAhead}), \text{lookHeight}, z + \text{lookAhead}]$ [S1, unofficial].
    *   Compute forward vector: $v = \text{normalize}(p_{target} - p_{cam})$ [S1, unofficial].
    *   Compute right vector: $r = \text{normalize}(\text{cross}(v, [0, 1, 0]))$ [S1, unofficial].
    *   Compute up vector: $u = \text{normalize}(\text{cross}(r, v))$ [S1, unofficial].
    *   Pass $p_{cam}, r, u, v$ to the shader uniforms [S1, unofficial].

3.  **Ray Generation (Fragment Shader):**
    *   For each pixel with normalized coordinates $uv \in [-1, 1]$, compute the ray direction:
        $$ d = \text{normalize}(v + uv.x \cdot r + uv.y \cdot u) $$
    *   Set ray origin $ro = \text{uCamPos}$ [S1, unofficial].

4.  **Sphere Tracing Loop:**
    *   Initialize $p = ro$ and $t = 0$.
    *   Iterate $i$ from 0 to `MAX_STEPS` (128):
        1.  Evaluate the scene SDF at $p$: $dist = \text{sceneSDF}(p)$ [S1, unofficial].
        2.  If $dist < 0$, the ray has penetrated the surface; return hit [S6, unofficial].
        3.  If $dist \le \text{HIT\_THRESHOLD}$ (e.g., 0.001), the ray has hit the surface; return hit [S1, unofficial].
        4.  If $t > \text{MAX\_DIST}$ (180.0), the ray has escaped; return miss [S1, unofficial].
        5.  Advance position: $p \leftarrow p + dist \cdot d$ and $t \leftarrow t + dist$ [S10, unofficial].

5.  **Scene SDF Evaluation (`sceneSDF`):**
    *   The scene consists of a ground plane and buildings.
    *   **Ground Plane:** The distance to the plane $y=0$ is $d_{ground} = p.y$ [S1, unofficial].
    *   **Road Space Transformation:**
        *   Calculate the road's lateral offset at the ray's current $z$: $road\_x = \text{roadX}(p.z)$ [S1, unofficial].
        *   Transform point to "road space" where the road is straight along the Z-axis:
            $$ p_{road} = [p.x - road\_x, p.y, p.z] $$
    *   **Building SDF:**
        *   Determine the cell coordinates $(cx, cy, cz)$ for the building grid. The grid is tiled with `BLOCK_WIDTH` and `BLOCK_DEPTH` [S1, unofficial].
        *   Hash the cell coordinates using the deterministic hash function to get a seed:
            $$ seed = \text{hashCell}(cx, cy, cz) $$
        *   Use the seed to determine building properties (footprint, height, material) [S1, unofficial].
        *   Construct the SDF for the building box in road space, applying the margin of 1.5 units to prevent overlap [S1, unofficial].
        *   Combine with ground: $d_{scene} = \min(d_{ground}, d_{building})$ [S1, unofficial].

6.  **Hashing Implementation Details:**
    *   The `uhash` function uses 32-bit integer operations to ensure bit-identical results between JavaScript and GLSL [S1, unofficial]:
        ```python
        def uhash(x):
            x = x & 0xFFFFFFFF
            x ^= x >> 16
            x = (x * 0x7feb352d) & 0xFFFFFFFF
            x ^= x >> 15
            x = (x * 0x846ca68b) & 0xFFFFFFFF
            x ^= x >> 16
            return x & 0xFFFFFFFF
        ```
    *   The `hashCell` function mixes 3D coordinates:
        ```python
        def hashCell(cx, cy, cz):
            h = uhash((cx * 0x9e3779b9) & 0xFFFFFFFF)
            h = uhash(h ^ ((cy * 0x85ebca6b) & 0xFFFFFFFF))
            h = uhash(h ^ ((cz * 0xc2b2ae35) & 0xFFFFFFFF))
            return h & 0xFFFFFFFF
        ```
    *   To get a float in $[0, 1)$, use the top 24 bits: `hashToFloat(h) = (h >> 8) / 16777216` [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Hash Drift:** If the CPU and GPU hash implementations diverge, game logic (e.g., collision) will not match the rendered scene [S1, unofficial].
*   **Precision:** The road curve uses floating-point sine functions. The hash function uses integer arithmetic to avoid precision drift between platforms [S1, unofficial].
*   **Overshoot:** Sphere tracing guarantees no overshoot if the SDF is a valid distance field [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(\text{MAX\_STEPS} \times \text{Resolution})$. Each pixel performs up to 128 SDF evaluations [S1, unofficial].
*   **Memory Complexity:** $O(1)$ auxiliary memory. The scene is procedural and defined by constants; no geometry or texture buffers are stored [S1, unofficial].
*   **Performance:** Runs in real-time on WebGL2-capable hardware. Performance depends on GPU fragment shader throughput and the complexity of the SDF evaluation (trigonometric functions for the road curve) [S1, unofficial].
*   **Strengths:** Zero asset loading; infinite procedural world; deterministic consistency between rendering and logic [S1, unofficial].
*   **Limitations:** Limited to simple geometric primitives (boxes, planes); no complex lighting or shadows beyond basic SDF shading; resolution-dependent quality [S1, unofficial].

## Background
Neon Raymarcher is a WebGL2 experiment created by PIGJET, demonstrating real-time raymarching of a procedural synthwave city [S1, unofficial]. It was developed as a technical demo to showcase the capabilities of SDF raymarching in a browser environment without relying on traditional graphics assets [S1, unofficial]. The project emphasizes the synchronization of procedural generation between CPU and GPU using deterministic integer hashing [S1, unofficial].
