# Depth Rendering

Also called: Depth Map Rendering, Z-Buffer Visualization

## Overview
Depth Rendering is a visualization technique that maps the depth (z-coordinate or distance) of the first surface hit by a ray to grayscale intensity, producing a depth map where brightness corresponds to distance from the viewer or image plane [S1, S3, unofficial]. Unlike [Iteration-Based Coloring](1244-iteration-based-coloring.md), which visualizes computational effort (step count), Depth Rendering visualizes geometric proximity [S1, unofficial]. It serves as a foundational method for debugging ray tracers and preparing inputs for subsequent shading passes [S3, unofficial].

## How it works
**Inputs:**
- A voxel data structure (e.g., Octree) containing spatial bounds (`tree->min`, `tree->max`) and leaf nodes with occupancy data [S1, S3, unofficial].
- A ray generation function `rc.getRayForPixel(x, y)` providing origin and direction for each pixel [S1, unofficial].
- Image dimensions `rc.n_x` and `rc.n_y` [S1, unofficial].

**Outputs:**
- A texture array `texture_array` of size `n_x * n_y * 4` (RGBA), where R=G=B represent normalized depth and A=1 [S1, unofficial].

**Data Structures:**
- `TreeTraverser`: Manages the traversal state of the voxel tree.
  - `isTerminated()`: Returns true if the ray has exited the volume or hit a boundary.
  - `getCurrentNode()`: Returns the current node in the traversal.
  - `getCurrentPosition()`: Returns the 3D position of the ray at the current step.
  - `step()`: Advances the ray to the next node or intersection.
  - `stepcount`: (Optional, used in [S1, unofficial] variant) Tracks the number of steps taken.
- `VoxelData`: (Contextual, from [S1, unofficial]) Contains `morton` code, `color`, and `normal`. Used to determine if a leaf has valid data.

**Algorithm Steps:**
1.  **Initialize Parallel Execution:** Set the number of OpenMP threads to the number of available CPU cores [S1, unofficial].
    ```python
    num_threads = omp_get_num_procs()
    omp_set_num_threads(num_threads)
    ```
2.  **Parallel Pixel Loop:** Iterate over all pixels $(x, y)$ in parallel [S1, unofficial].
    ```python
    for y in range(rc.n_y):
        for x in range(rc.n_y): # Note: Source uses rc.n_y for x loop limit [S1, unofficial]
            # Calculate index in RGBA array
            index = y * (rc.n_y * 4) + x * 4
    ```
3.  **Ray Initialization:** Create a `TreeTraverser` instance for the current pixel's ray [S1, unofficial].
    ```python
    t = TreeTraverser(tree, rc.getRayForPixel(x, y))
    ```
4.  **Tree Traversal:** Traverse the tree until termination or data hit [S1, unofficial].
    ```python
    while not t.isTerminated():
        current_node = t.getCurrentNode()
        if current_node.isLeaf():
            if current_node.hasData():
                break # Hit a surface/voxel
        t.step()
    ```
5.  **Depth Calculation:**
    There are two distinct implementations in the sources:
    
    *Method A: Normalized Z-Coordinate [S1, unofficial]*
    - Get the 3D position of the hit point: $pos = t.getCurrentPosition()$.
    - Compute the depth factor $f$ by normalizing the absolute Z-coordinate against the tree's Z-bounds:
      $$ f = \frac{|pos_z|}{|max_z| - |min_z|} $$
      where $pos_z$ is `pos[2]`, $max_z$ is `tree->max[2]`, and $min_z$ is `tree->min[2]` [S1, unofficial].
    - Compute grayscale intensity $I$:
      $$ I = 255 - (255 \times f) $$
      Brighter pixels correspond to smaller $f$ (closer to origin/min bound if normalized differently, but here $255-255f$ implies darker for larger Z if $pos_z$ is positive and large). *Note: The formula $255 - 255 \times factor$ inverts the depth, making closer objects (smaller factor) brighter if factor is derived from distance from min, or vice versa depending on coordinate system.* [S1, unofficial].
    
    *Method B: Step Count Normalization [S1, unofficial]*
    - Compute depth factor $f$ based on step count:
      $$ f = \frac{stepcount}{\log_2(size)} $$
      where $size$ is `tree->gridlength` [S1, unofficial].
    - Intensity:
      $$ I = f \times 255 $$
      This maps step count directly to brightness [S1, unofficial].

    *Method C: Z-Buffer Inverse [S3, unofficial]*
    - Store the distance to the closest non-empty voxel in a 2D Z-buffer.
    - Intensity is inversely proportional to the depth value $D(x,y)$:
      $$ I(x,y) \propto \frac{1}{D(x,y)} $$
      Features far from the image plane appear dark; close features appear bright [S3, unofficial].

6.  **Color Assignment:**
    Using Method A/B logic for the final pixel color [S1, unofficial]:
    ```python
    texture_array[index] = int(I)       # R
    texture_array[index+1] = int(I)     # G
    texture_array[index+2] = int(I)     # B
    texture_array[index+3] = 1          # A
    ```

**Parameters:**
- `tree->min[2]`, `tree->max[2]`: Z-bounds of the voxel volume [S1, unofficial].
- `tree->gridlength`: Total size of the grid, used for log2 normalization in [S1, unofficial] variant [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Termination:** If the ray terminates without hitting a leaf with data, the depth value is undefined. The sources do not specify a default background color for missed rays [S1, unofficial].
- **Precision:** Floating-point comparisons for `hasData()` and boundary checks may suffer from precision issues in degenerate cases [G].
- **Orientation Loss:** Standard depth rendering ignores surface orientation, causing loss of details such as surface discontinuities and object boundaries [S3, unofficial].

## Subtopics

### Logarithmic Depth Rendering
A variant that normalizes the logarithm of the distance traveled by the ray to the range [0, 1], where brighter pixels indicate further travel distance [S2, unofficial]. It handles large depth ranges better than linear mapping by compressing distant values [S2, unofficial]. The distance $d = |p_i - p_0|$ is computed, then $\log(d)$ is normalized using min/max clamping (e.g., clamp to $10^{-2}$) and gamma correction (pow 1/2.33) in some implementations [S2, unofficial].

### Depth Shading
A 2D discrete shading technique that uses only the Z-buffer (depth values) to compute intensity, making features far from the image plane appear dark and close features bright [S3, unofficial]. It computes output intensity as inversely proportional to the depth value stored in the Z-buffer for that pixel [S3, unofficial]. A key pitfall is that surface orientation is not considered, causing loss of details such as surface discontinuities and object boundaries [S3, unofficial].

## Operating characteristics
- **Time Complexity:** $O(N \cdot S)$, where $N$ is the number of pixels and $S$ is the average number of steps per ray [S1, unofficial]. Parallelized across pixels using OpenMP [S1, unofficial].
- **Memory Complexity:** $O(N)$ for the output texture array, plus the memory for the voxel tree [S1, S3, unofficial].
- **Strengths:** Simple to implement; provides immediate visual feedback on ray traversal success and depth distribution; useful for debugging [S1, S3, unofficial].
- **Limitations:** Lacks geometric detail (no normals/lighting); sensitive to depth range scaling; linear mapping may waste dynamic range for deep scenes [S1, S3, unofficial].
- **When to use:** Debugging ray tracers, generating depth maps for post-processing, or as a base for more complex shading techniques like gradient shading [S3, unofficial].

## Background
Depth rendering is a fundamental technique in volume visualization and ray marching. It originates from the need to visualize the spatial extent of volumetric data without full shading computations. The concept of using a Z-buffer for discrete shading was formalized in early volume visualization literature, such as Arie Kaufman's work on volume visualization principles [S3, unofficial]. The specific implementation using OpenMP and CPU-based octree traversal is documented in the `cpu_voxel_raycaster` project [S1, unofficial]. Logarithmic depth mapping is a common extension in graphics programming to handle wide depth ranges [S2, unofficial].
