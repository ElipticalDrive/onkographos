# Sphere Tracing

Also called: Hart's Sphere Tracing, SDF Sphere Tracing, SDF Tracing

## Overview
Sphere Tracing is an iterative ray-marching algorithm for rendering implicit surfaces defined by Signed Distance Functions (SDFs) or Lipschitz continuous implicit functions [S2][S3, S17]. It solves the problem of finding the intersection between a camera ray and a complex, analytically defined geometry without explicit polygonal meshes [S17][S39, unofficial]. Unlike standard ray marching which uses fixed steps, Sphere Tracing uses the SDF value at the current position as a safe lower bound for the distance to the nearest surface, allowing the ray to "jump" forward by that exact distance [S12, S31, unofficial]. This guarantees that the ray never overshoots or penetrates the surface, provided the function satisfies the Lipschitz condition [S2][S39, unofficial]. It is distinguished from its siblings, such as [Standard Constant Step Ray Marching](1080-standard-constant-step-ray-marching.md), by its adaptive step sizing which significantly reduces the number of function evaluations required to converge on a surface [S3][S31, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Ray origin $\mathbf{o}$, normalized ray direction $\mathbf{d}$, scene function $f(\mathbf{p})$ returning the signed distance to the nearest surface, maximum traversal distance $t_{max}$, maximum iteration count $N_{max}$, and convergence threshold $\epsilon$ [S2][S19, S35, unofficial].
*   **Output:** Intersection distance $t_{hit}$ (or boolean hit status) and optionally the intersection point $\mathbf{p}_{hit} = \mathbf{o} + t_{hit}\mathbf{d}$ [S10, S19, unofficial].

**Data Structures:**
The method maintains a scalar accumulator $t$ for the total distance traveled along the ray [S35, unofficial]. No complex data structures are required for the core algorithm, though acceleration structures (like bounding spheres or grids) may be used to optimize the evaluation of $f(\mathbf{p})$ [S37, unofficial][S43].

**Mathematical Foundation:**
The core safety guarantee relies on the Lipschitz condition [S3][S40, unofficial]. A function $f$ is Lipschitz continuous with constant $\lambda$ if $|f(\mathbf{x}) - f(\mathbf{y})| \le \lambda \|\mathbf{x} - \mathbf{y}\|$ for all $\mathbf{x}, \mathbf{y}$ [S2][S40, unofficial]. For a general Lipschitz function, the safe step size is $s = \frac{|f(\mathbf{x})|}{\lambda}$ [S2]. If $f$ is a true Signed Distance Function (SDF), then $\lambda = 1$ and the step size is exactly $f(\mathbf{x})$ [S2]. The value $f(\mathbf{x})$ represents the radius of an "unbounding sphere" centered at $\mathbf{x}$ that is guaranteed not to contain any part of the surface [S2][S40, unofficial].

**Algorithm Steps:**
1.  Initialize accumulated distance $t = 10^{-4}$ (a small epsilon to avoid starting exactly on the surface) [S5, S19, unofficial].
2.  Loop for $i$ from $0$ to $N_{max}$:
    a.  Calculate current position: $\mathbf{p} = \mathbf{o} + t\mathbf{d}$ [S19, S35, unofficial].
    b.  Evaluate the scene function: $d = f(\mathbf{p})$ [S19, S35, unofficial].
    c.  **Termination Check (Inside):** If $d < 0$, the ray is inside the surface. Return hit [S1, S19, unofficial].
    d.  **Termination Check (Hit):** If $|d| < \epsilon$ (or $d < \epsilon$ for unsigned distance fields), the surface has been hit. Return $t$ as the intersection distance [S19, S35, unofficial][S40, unofficial].
    e.  **Termination Check (Miss):** If $t > t_{max}$, the ray has escaped the scene. Return failure/no hit [S19, S35, unofficial].
    f.  **Step Update:** Advance the ray by the distance value: $t \leftarrow t + d$ [S19, S35, unofficial].
3.  If the loop completes without hitting the surface, return failure/no hit [S19, S35, unofficial].

**Pseudocode:**
```python
def sphere_trace(ray_origin, ray_direction, scene_sdf, max_dist, max_steps, epsilon):
    """
    Performs sphere tracing to find the intersection of a ray with an SDF surface.
    
    Args:
        ray_origin (vec3): The starting point of the ray.
        ray_direction (vec3): The normalized direction of the ray.
        scene_sdf (function): A function f(p) returning the signed distance to the nearest surface.
        max_dist (float): The maximum distance the ray can travel.
        max_steps (int): The maximum number of iterations allowed.
        epsilon (float): The convergence threshold for hit detection.
        
    Returns:
        tuple: (hit: bool, distance: float)
    """
    t = 1e-4  # Initialize to small epsilon to avoid starting exactly on surface [S5, S19, unofficial]
    
    for i in range(max_steps):
        # Check if ray has exceeded maximum distance
        if t > max_dist:
            return False, t
        
        # Calculate current position on the ray
        p = ray_origin + ray_direction * t
        
        # Evaluate the Signed Distance Function at the current position
        dist = scene_sdf(p)
        
        # Check if ray is inside the surface
        if dist < 0:
            return True, t
            
        # Check for surface hit
        if abs(dist) < epsilon:
            return True, t
            
        # Advance the ray by the distance to the surface
        t += dist
        
    # Max steps reached without hitting surface
    return False, t
```

**Parameters and Typical Values:**
*   $\epsilon$ (Convergence Threshold): Typically $0.001$ to $0.0001$ [S11, unofficial][S17][S35, unofficial]. Some implementations use a relative threshold like $0.001 \times t$ [S20, unofficial].
*   $N_{max}$ (Max Steps): Typically $10$ to $128$ for simple scenes, up to $1024$ for complex or deep volumes [S12, S19, S35, unofficial].
*   $t_{max}$ (Max Distance): Scene-dependent, often $100.0$ or determined by the camera's far plane [S19, S35, unofficial].

**Edge Cases and Pitfalls:**
*   **Lipschitz Violation:** If the scene function is not Lipschitz continuous with constant $\lambda=1$ (i.e., it is not a true SDF), the step size $d$ may be larger than the actual distance to the surface, causing the ray to overshoot and miss the intersection [S2].
*   **Flat Surfaces:** When the ray grazes a surface or moves parallel to a flat region, the SDF value remains large, leading to large steps that may skip over the surface if the surface is not perfectly planar or if numerical precision issues arise [S1, unofficial][S5, unofficial].
*   **Inside the Surface:** If the ray starts inside the object ($f(\mathbf{p}) < 0$), the step size becomes negative, moving the ray backward. The algorithm must handle this, often by checking for sign changes or using absolute values for step sizing in specific variants [S1, S19, unofficial].
*   **Precision:** Floating-point precision errors can cause the ray to oscillate near the surface or fail to converge within $\epsilon$. Using a relative epsilon or a minimum step size helps mitigate this [S20, S38, unofficial].

## Subtopics

### [Zeno Implementation](1544-zeno-implementation.md)
The Zeno implementation is a specific software architecture for sphere tracing that prioritizes ease of extension for new implicit surfaces over raw shading performance. It solves the problem of rapidly prototyping mathematical implicit surfaces by allowing new primitives to be added by defining only a signed distance bound, while avoiding the manual derivation of surface normals. It sets itself apart from standard sphere tracing implementations by replacing the explicit normal function with a fixed six-sample numerical gradient approximation, accepting the minor performance cost as negligible compared to ray intersection overhead.

### [Cone Intersection](1553-cone-intersection.md)
Cone intersection is an antialiasing technique for sphere tracing that represents a pixel as a viewing cone rather than a point ray, allowing symbolic prefiltering to eliminate aliasing artifacts at grazing angles. It differs from standard sphere tracing by detecting intersections with an "inner cover" surface and computing the fractional coverage of the pixel by the implicit surface, whereas siblings like [Segment Tracing](1675-segment-tracing.md) or [Quadric Tracing](1866-quadric-tracing.md) focus on varying step sizes or bounding volumes without necessarily computing area-based coverage fractions.

### [Segment Tracing](1675-segment-tracing.md)
Segment Tracing is a ray marching algorithm that computes local Lipschitz bounds on candidate segments to determine adaptive step sizes, reducing the number of field function queries compared to global Lipschitz bound methods like Sphere Tracing. It works for a particular class of hierarchical skeletal implicit surfaces, leveraging the composition of distance functions and kernel functions to compute directional Lipschitz bounds. Unlike Sphere Tracing, which uses a global bound that limits step size efficiency, Segment Tracing allows larger, safer steps by adapting to the local gradient and field values.

### [Enhanced Sphere Tracing](3811-enhanced-sphere-tracing.md)
Enhanced Sphere Tracing is a family of ray-marching optimizations that accelerate convergence toward implicit surfaces defined by Signed Distance Functions (SDFs) by taking steps larger than the strict Lipschitz bound or by predicting optimal step sizes based on local surface geometry. It solves the performance bottleneck of standard sphere tracing, which becomes prohibitively slow when rays graze surfaces at shallow angles or when the surface is locally planar. Unlike standard sphere tracing, which uses the queried distance value as the step size, enhanced variants either over-relax the step size by a constant factor or infer the next step size from the previous two distance queries to approximate the surface as locally flat.

### [Uniform Sphere Tracing](4406-uniform-sphere-tracing.md)
Uniform Sphere Tracing is a volume rendering technique that uses ray marching along a Signed Distance Field (SDF) to detect volume boundaries and applies Beer's Law for optical depth integration under a uniform density assumption. It solves the problem of rendering participating media with constant optical properties by stepping through the volume, accumulating absorption and scattering, and blending the result with the background. It is distinguished from its parent [Sphere Tracing](1674-sphere-tracing.md) by its specific application to uniform density volume rendering and its reliance on fixed or clamped step sizes for the marching phase, while using SDF evaluation primarily for surface detection rather than purely adaptive step sizing for optical integration.

### [Synchronized-tracing](8552-synchronized-tracing.md)
Synchronized-tracing is a tile-based rendering pipeline for implicit volumes (blobtrees) that synchronizes threads within a subfrustum to allow coherent field evaluation, using sparse bottom-up tree traversal to prune the blobtree on-the-fly. It is designed for interactive modeling scenarios where no preprocessing is required when primitive parameters are updated. It sets itself apart from standard sphere tracing by introducing a synchronization mechanism via a low-resolution A-buffer to manage thread coherence within workgroups, and by using compact, smooth CSG operators to compute tight bounding volumes for approximate signed distance fields.

### [Relaxed Sphere Tracing](9463-relaxed-sphere-tracing.md)
Relaxed sphere tracing is a ray marching technique that accelerates the convergence of standard sphere tracing by scaling the conservative step size by a relaxation factor, allowing the ray to traverse empty space more quickly. It solves the performance bottleneck of standard sphere tracing in large empty volumes by reducing the number of iterations required to reach a surface, while maintaining safety by reverting to the standard step size if the unbounding spheres of consecutive steps become disjoint. It is distinguished from [Standard Constant Step Ray Marching](1080-standard-constant-step-ray-marching.md) by its adaptive, distance-field-driven step sizing, and from [Enhanced Sphere Tracing](1674-sphere-tracing.md) by its simpler geometric fallback logic which may result in smaller steps near complex geometry.

### [Cone-Traced Supersampling](9466-cone-traced-supersampling.md)
Cone-Traced Supersampling (CTSS) is an efficient spatial antialiasing solution for Signed Distance Field (SDF) rendering that performs supersampling along the traced ray near surfaces with partial visibility. It identifies object contours by evaluating cone intersections within a pixel's view frustum, avoiding the need for casting additional rays per pixel or offline prefiltering. Subpixel Edge Reconstruction (SER) extends CTSS to locate and resolve complex pixels with geometric edges in relatively flat regions that are otherwise undetected by cone intersections. Unlike conventional supersampling, CTSS minimizes shading computations, and unlike post-processing filters, it avoids undesirable blurriness and ghosting.

### [Kernel-Reflection Sequences](10186-kernel-reflection-sequences.md)
Kernel-Reflection Sequences (KRS) are a procedural modeling technique for generating complex, fractal-like geometries using Signed Distance Functions (SDFs) and reflection transformations. It solves the problem of evaluating global distance functions for recursive structures without recursion, enabling real-time sphere tracing on parallel hardware like GPUs. Unlike standard Iterated Function Systems (IFS) which require recursive traversal and cause divergent control flow, KRS uses a fixed operation count logarithmic time algorithm, allowing efficient parallelization.

### [Analytical and Differentiable Methods](13369-analytical-and-differentiable-methods.md)

### Cube-tracing
An algorithm using the chessboard metric (or Manhattan metric) for distance computation, potentially resulting in more efficiently computed distances and ray intersection. Left as further research [S42, unofficial].

### Bounding Sphere Optimization
An optimization that decreases the number of calculations made in each march by enclosing several objects into one bounding sphere [S37, unofficial]. Objects should be bound in an adaptive way, enclosing objects depending on how they are grouped per frame, approximating the sphere definition for increased performance rather than computing it exactly [S37, unofficial]. Performance gain increases as the number of objects inside the sphere increases, with a gain occurring when >3 objects are enclosed (e.g., 25% FPS increase at 10 enclosed objects) [S37, unofficial]. Performance decreases if <4 objects are enclosed [S37, unofficial]. Bounding Spheres can work together with Orthogonal Culling by culling bounding spheres instead of single objects, decreasing the number of orthogonal projections made [S37, unofficial]. Implemented and tested in the GLSL shader [S37, unofficial].

### Hybrid Ray Marching
Integrates ray marching with distance-based empty space leaping for complex scenes, using coarse SDFs to compute large skips in low-density regions before switching to fine-grained tracing near features [S13, unofficial]. Balances speed and accuracy in multi-material volumes [S13, unofficial].

### Acceleration Structures for SDF Evaluation
A set of optimization nodes embedded directly in hierarchical construction trees to reduce the computational cost of field function evaluation while preserving Lipschitz or conservative properties [S43]. Avoids external accompanying data structures such as octrees by embedding acceleration nodes directly in the construction tree [S43]. Applies a normal warping technique to enhance surface details with negligible computational overhead [S43]. Speeds up signed distance field evaluation by up to three orders of magnitude compared to standard evaluation [S43]. Applies to both ray-surface intersection computation in sphere tracing applications and polygonization algorithms [S43].

### Harnack Tracing
A method for visualizing surfaces encoded by harmonic functions (including angle-valued functions and those with singularities) by using conservative Harnack bounds on the growth of harmonic functions to determine step sizes, avoiding numerical issues common to generic root finding methods [S33, unofficial]. Uses conservative Harnack bounds on the growth of harmonic functions to determine the step size for each iteration, ensuring the step does not cross a level set boundary [S33, unofficial]. Performs pointwise evaluation of the harmonic function at the current position to check for convergence to the target level set [S33, unofficial]. Unlike sphere tracing which uses distance bounds, Harnack tracing uses bounds on the growth of harmonic functions; it avoids numerical issues common to generic root finding methods and can visualize surfaces directly from point clouds or polygon soup without linear solves or mesh extraction [S33, unofficial].

### Claybook SDF Construction
A method for fully real-time deformable SDF-based worlds, using a global dense SDF with mip levels for acceleration [S44]. Constructs a global SDF, builds 5 mip levels where each level encodes distance values twice as great as the previous, uses sphere-tracing sampling coarser mip levels to travel greater distances conservatively, and ascends/descends mip levels based on sampled distance magnitude [S44]. Modification: Apply pre-defined 'brushes' to the world SDF. Only nearby affected areas are re-evaluated due to brush locality [S44]. Uses a global SDF volume of resolution 1024x1024x512 with five mip levels [S44]. Compact data structures (like SVOs) are incompatible with this modification method because surface-intersecting voxel counts are not static, requiring slow insertions and indirection tables [S44]. Used in Claybook (Aaltonen, 2018) [S44].

## Operating characteristics
*   **Time Complexity:** The number of iterations depends on the distance to the surface and the local geometry [S5, unofficial]. In empty space, steps are large, leading to $O(1)$ or very few iterations [S19, S35, unofficial]. Worst-case scenarios occur when rays graze surfaces or pass close to parallel surfaces, requiring many iterations to move forward [S5, unofficial].
*   **Memory Complexity:** $O(1)$ auxiliary memory for the core algorithm [S33, unofficial].
*   **Measured Performance:** Performance varies significantly by scene complexity [S2]. In simple scenes with few primitives, sphere tracing is very fast [S14, unofficial]. In complex scenes with many primitives, the cost of evaluating the SDF for each step becomes dominant [S2]. Bounding sphere optimizations can increase FPS by 25% when >3 objects are enclosed [S37, unofficial].
*   **Strengths:** No preprocessing required for implicit surfaces; easy to combine primitives using CSG operations; adaptive step size reduces evaluations in empty space [S17][S31, unofficial].
*   **Limitations:** Requires the scene to be representable as an SDF or Lipschitz function; can be slow for complex scenes with many primitives if no acceleration structure is used; sensitive to the Lipschitz constant; may require many iterations near flat or grazing surfaces [S2][S5, unofficial][S31, unofficial].
*   **When to Use:** Ideal for rendering procedural geometry, fractals, and smooth CSG combinations where explicit mesh generation is undesirable or too costly [S17][S31, unofficial].
*   **When Not to Use:** Not suitable for scenes with explicit polygonal meshes unless converted to SDFs; may be inefficient for highly detailed, non-procedural geometry without acceleration structures [S2][S37, unofficial].

## Background
Sphere Tracing was introduced by John Hart in 1996 in the paper "Sphere Tracing: A Geometric Method for the Antialiased Ray Tracing of Implicit Surfaces" [S14, unofficial][S40, unofficial]. It was developed as a method to render implicit surfaces defined by distance functions without the need for explicit polygonal meshes or complex intersection algorithms [S14, unofficial][S40, unofficial]. The method leverages the geometric property of distance functions to provide safe stepping distances, ensuring accurate and antialiased rendering of complex implicit shapes [S14, unofficial][S40, unofficial]. It has since become a fundamental technique in procedural rendering, real-time graphics, and neural rendering [S17][S31, unofficial]. Variants and optimizations, such as relaxed sphere tracing and enhanced sphere tracing, have been developed to address performance bottlenecks in specific scenarios [S1, unofficial][S5, unofficial][S39, unofficial].
