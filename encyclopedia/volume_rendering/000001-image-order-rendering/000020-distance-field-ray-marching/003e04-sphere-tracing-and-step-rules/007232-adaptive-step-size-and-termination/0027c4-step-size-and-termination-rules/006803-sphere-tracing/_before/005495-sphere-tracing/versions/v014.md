# Sphere Tracing

Also called: Hart's Sphere Tracing, SDF Sphere Tracing, SDF Tracing

## Overview
Sphere Tracing is an iterative ray-marching algorithm for finding the intersection of a ray with an implicit surface defined by a Signed Distance Function (SDF) or a Lipschitz continuous function [S2][S3, S14, unofficial]. It solves the problem of rendering complex, analytic geometry without explicit polygonal meshes by stepping along a ray by a distance guaranteed not to cross the surface, ensuring convergence to the first intersection [S4, S12, unofficial]. It sets itself apart from standard constant-step ray marching by using the local distance value as the step size, allowing for adaptive, larger steps in empty space and smaller steps near surfaces, which significantly reduces the number of function evaluations required [S3, S17, unofficial].

## How it works
Sphere Tracing relies on the geometric property that a sphere of radius $r$ centered at point $\mathbf{p}$ does not intersect the surface if $r$ is less than or equal to the distance from $\mathbf{p}$ to the surface [S14, unofficial][S40]. For a function $f(\mathbf{x})$ that is Lipschitz continuous with constant $\lambda$, the value $|f(\mathbf{x})|/\lambda$ provides a safe lower bound on the distance to the zero-level set (the surface) [S2]. If $f$ is a true SDF, then $\lambda=1$ and the bound is exact [S2].

### Inputs and Outputs
*   **Inputs:**
    *   Ray origin $\mathbf{o}$ and normalized direction $\mathbf{d}$ [S37, unofficial].
    *   Scene function $f(\mathbf{p})$ returning the signed distance to the nearest surface [S21, unofficial].
    *   Maximum traversal distance $t_{max}$ (or clipping sphere radius $D$) [S40].
    *   Maximum iteration count $N_{max}$ [S1, S12, unofficial].
    *   Convergence threshold $\epsilon$ (precision) [S37, unofficial].
*   **Outputs:**
    *   Intersection distance $t$ along the ray [S10, unofficial].
    *   Boolean hit status [S10, unofficial].

### Data Structures
The method maintains a scalar parameter $t$ representing the distance traveled along the ray, and a current position $\mathbf{p} = \mathbf{o} + t\mathbf{d}$ [S37, unofficial]. No complex data structures are required for the core algorithm, though acceleration structures (like bounding spheres or grids) may be used to optimize the evaluation of $f(\mathbf{p})$ [S37, unofficial][S43, abstract only, unofficial].

### Numbered Steps
1.  **Initialization:** Set the ray parameter $t = 0$ (or a small epsilon to avoid starting exactly on a surface if necessary) [S4, S35, unofficial][S40]. Initialize iteration counter $i = 0$ [S35, unofficial].
2.  **Termination Check (Max Distance):** If $t > t_{max}$, terminate and return miss [S40].
3.  **Termination Check (Max Iterations):** If $i \ge N_{max}$, terminate and return miss [S1, S12, unofficial].
4.  **Position Evaluation:** Compute the current 3D position $\mathbf{p} = \mathbf{o} + t\mathbf{d}$ [S37, unofficial].
5.  **SDF Query:** Evaluate the scene function $d = f(\mathbf{p})$ [S37, unofficial].
6.  **Convergence Check:** If $|d| < \epsilon$ (or $d < \epsilon$ for unsigned distance fields), the ray has hit the surface. Terminate and return $t$ as the hit distance [S37, S17, unofficial]. Note: Some implementations use a relative threshold, e.g., $d < 0.001 \cdot t$ [S20, unofficial].
7.  **Step Size Calculation:** The step size $\Delta t$ is determined by the SDF value. For a true SDF, $\Delta t = d$ [S31, unofficial]. For a general Lipschitz function with constant $\lambda$, $\Delta t = d / \lambda$ [S2].
    *   *Safety Clamp:* In practice, $\Delta t$ is often clamped to a minimum value to prevent infinite loops in flat regions or numerical instability, and potentially a maximum value to prevent overshooting in highly curved regions if the Lipschitz constant is not strictly global [S4, S38, unofficial].
8.  **Advance:** Update $t \leftarrow t + \Delta t$ [S31, unofficial]. Increment $i \leftarrow i + 1$ [S35, unofficial].
9.  **Repeat:** Go to Step 2.

### Formulas
*   **Ray Equation:** $\mathbf{p}(t) = \mathbf{o} + t\mathbf{d}$ [S40].
*   **Safe Step (SDF):** $\Delta t = f(\mathbf{p})$ [S31, unofficial].
*   **Safe Step (Lipschitz):** $\Delta t = \frac{f(\mathbf{p})}{\lambda}$, where $\lambda = \max_{\mathbf{x}, \mathbf{y}} \frac{|f(\mathbf{x}) - f(\mathbf{y})|}{\|\mathbf{x} - \mathbf{y}\|}$ [S2].
*   **Convergence:** Stop when $f(\mathbf{p}) \le \epsilon$ [S37, unofficial].

### Parameters
*   **$\epsilon$ (Convergence Threshold):** Typical values range from $0.0001$ to $0.01$ [S9, S17, S30, unofficial]. Some implementations use a relative threshold $0.001 \cdot t$ [S20, unofficial].
*   **$N_{max}$ (Max Steps):** Typical values are 10, 32, 100, 128, or 1024 depending on the desired precision and scene complexity [S1, S12, S30, S32, S35, unofficial].
*   **$t_{max}$ (Max Distance):** Scene-dependent, e.g., 100.0 or 60.0 [S12, S19, S35, unofficial].
*   **$\lambda$ (Lipschitz Constant):** 1.0 for true SDFs [S2].

### Edge Cases and Pitfalls
*   **Overshooting:** If the function is not a true SDF (i.e., $\lambda > 1$) and the global Lipschitz constant is not used, the step size $f(\mathbf{p})$ may be too large, causing the ray to jump over the surface [S2].
*   **Flat Surfaces:** Near planar surfaces, the SDF value changes slowly, leading to small steps and many iterations [S1, unofficial].
*   **Numerical Precision:** Starting exactly on the surface ($t=0, f(\mathbf{p})=0$) may cause immediate termination or infinite loops if not handled with an epsilon offset [S4, unofficial].
*   **Inside the Surface:** If the ray starts inside the object ($f(\mathbf{p}) < 0$), the standard algorithm may march backwards or fail to converge if not designed to handle negative distances (e.g., by using absolute value or specific inside/outside logic) [S6, S30, unofficial].

### Pseudocode
```python
def sphere_trace(ray_origin, ray_direction, scene_sdf, max_dist, max_steps, epsilon):
    """
    Performs sphere tracing to find the intersection of a ray with an SDF surface.
    
    Args:
        ray_origin (vec3): The starting point of the ray.
        ray_direction (vec3): The normalized direction of the ray.
        scene_sdf (function): A function that returns the signed distance to the nearest surface.
        max_dist (float): The maximum distance the ray can travel.
        max_steps (int): The maximum number of iterations allowed.
        epsilon (float): The convergence threshold for surface hit detection.
        
    Returns:
        tuple: (hit: bool, distance: float)
    """
    t = 0.0
    for i in range(max_steps):
        # Check maximum distance
        if t > max_dist:
            return False, t
        
        # Calculate current position
        p = ray_origin + ray_direction * t
        
        # Evaluate SDF
        d = scene_sdf(p)
        
        # Check for surface hit
        # Using absolute value to handle both inside and outside hits, 
        # or just d < epsilon if only outside is considered.
        if abs(d) < epsilon:
            return True, t
        
        # Step size is the distance to the surface (SDF property)
        # For Lipschitz functions with constant lambda, use d / lambda
        step = d
        
        # Safety clamp: ensure step is at least a small positive value
        # to avoid infinite loops in flat regions or numerical noise
        min_step = 1e-6
        if step < min_step:
            step = min_step
            
        # Advance ray
        t += step
        
    # Max steps reached
    return False, t
```

## Subtopics

### [Zeno Implementation](1544-zeno-implementation.md)
The Zeno implementation is a specific software architecture for sphere tracing that prioritizes ease of extension for new implicit surfaces over raw shading performance. It solves the problem of rapidly prototyping mathematical implicit surfaces by allowing new primitives to be added by defining only a signed distance bound, while avoiding the manual derivation of surface normals. It sets itself apart from standard sphere tracing implementations by replacing the explicit normal function with a fixed six-sample numerical gradient approximation, accepting the minor performance cost as negligible compared to ray intersection overhead.

### [Cone Intersection](1553-cone-intersection.md)
Cone intersection is an antialiasing technique for sphere tracing that represents a pixel as a viewing cone rather than a point ray, allowing symbolic prefiltering to eliminate aliasing artifacts at grazing angles. It differs from standard sphere tracing by detecting intersections with an "inner cover" surface and computing the fractional coverage of the pixel by the implicit surface, whereas siblings like [Segment Tracing](1675-segment-tracing.md) or [Quadric Tracing](1866-quadric-tracing.md) focus on varying step sizes or bounding volumes without necessarily computing area-based coverage fractions.

### [Segment Tracing](1675-segment-tracing.md)
Segment Tracing is a ray marching algorithm that computes local Lipschitz bounds on candidate segments to determine adaptive step sizes, reducing the number of field function queries compared to global Lipschitz bound methods like Sphere Tracing. It works for a particular class of hierarchical skeletal implicit surfaces, leveraging the composition of distance functions and kernel functions to compute directional Lipschitz bounds. Unlike Sphere Tracing, which uses a global bound that limits step size efficiency, Segment Tracing allows larger, safer steps by adapting to the local gradient and field values.

### [Quadric Tracing](1866-quadric-tracing.md)
Quadric tracing is a method to accelerate sphere tracing by precomputing an augmented distance field using quadric surfaces (second-degree algebraic surfaces) to bound or unbound scene geometry, reducing the number of Signed Distance Function (SDF) evaluations. It solves the slowdown of sphere tracing near surfaces and with increasing scene complexity, where function evaluation time and convergence slow drastically. Unlike relaxed sphere tracing (which uses a scalar to determine step size and reverts if too large) or enhanced sphere tracing (which uses previous two radii to approximate planar surfaces), quadric tracing uses precomputed geometric bounds to accelerate convergence. It stops when the computed distance value dips below a threshold, switching to enhanced sphere tracing for final convergence.

### [Enhanced Sphere Tracing](3811-enhanced-sphere-tracing.md)
Enhanced Sphere Tracing is a family of ray-marching optimizations that accelerate convergence toward implicit surfaces defined by Signed Distance Functions (SDFs) by taking steps larger than the strict Lipschitz bound or by predicting optimal step sizes based on local surface geometry. It solves the performance bottleneck of standard sphere tracing, which becomes prohibitively slow when rays graze surfaces at shallow angles or when the surface is locally planar. Unlike standard sphere tracing, which uses the queried distance value as the step size, enhanced variants either over-relax the step size by a constant factor or infer the next step size from the previous two distance queries to approximate the surface as locally flat.

### [Uniform Sphere Tracing](4406-uniform-sphere-tracing.md)
Uniform Sphere Tracing is a volume rendering technique that uses ray marching along a Signed Distance Field (SDF) to detect volume boundaries and applies Beer's Law for optical depth integration under a uniform density assumption. It solves the problem of rendering participating media with constant optical properties by stepping through the volume, accumulating absorption and scattering, and blending the result with the background. It is distinguished from its parent [Sphere Tracing](1674-sphere-tracing.md) by its specific application to uniform density volume rendering and its reliance on fixed or clamped step sizes for the marching phase, while using SDF evaluation primarily for surface detection rather than purely adaptive step sizing for optical integration.

### [Synchronized-tracing](8552-synchronized-tracing.md)
Synchronized-tracing is a tile-based rendering pipeline for implicit volumes (blobtrees) that synchronizes threads within a subfrustum to allow coherent field evaluation, using sparse bottom-up tree traversal to prune the blobtree on-the-fly. It is designed for interactive modeling scenarios where no preprocessing is required when primitive parameters are updated. It sets itself apart from standard sphere tracing by introducing a synchronization mechanism via a low-resolution A-buffer to manage thread coherence within workgroups, and by using compact, smooth CSG operators to compute tight bounding volumes for approximate signed distance fields.

### [Cone-Traced Supersampling](9466-cone-traced-supersampling.md)
Cone-Traced Supersampling (CTSS) is an efficient spatial antialiasing solution for Signed Distance Field (SDF) rendering that performs supersampling along the traced ray near surfaces with partial visibility. It identifies object contours by evaluating cone intersections within a pixel's view frustum, avoiding the need for casting additional rays per pixel or offline prefiltering. Subpixel Edge Reconstruction (SER) extends CTSS to locate and resolve complex pixels with geometric edges in relatively flat regions that are otherwise undetected by cone intersections. Unlike conventional supersampling, CTSS minimizes shading computations, and unlike post-processing filters, it avoids undesirable blurriness and ghosting.

### [Kernel-Reflection Sequences](10186-kernel-reflection-sequences.md)
Kernel-Reflection Sequences (KRS) are a procedural modeling technique for generating complex, fractal-like geometries using Signed Distance Functions (SDFs) and reflection transformations. It solves the problem of evaluating global distance functions for recursive structures without recursion, enabling real-time sphere tracing on parallel hardware like GPUs. Unlike standard Iterated Function Systems (IFS) which require recursive traversal and cause divergent control flow, KRS uses a fixed operation count logarithmic time algorithm, allowing efficient parallelization.

### Cube-tracing
An algorithm using the chessboard metric (or Manhattan metric) for distance computation, potentially resulting in more efficiently computed distances and ray intersection. Left as further research [S42].

### Bounding Sphere Optimization
An optimization that decreases the number of calculations made in each march by enclosing several objects into one bounding sphere [S37, unofficial]. Objects should be bound in an adaptive way, enclosing objects depending on how they are grouped per frame, approximating the sphere definition for increased performance rather than computing it exactly [S37, unofficial]. Performance gain increases as the number of objects inside the sphere increases, with a gain occurring when >3 objects are enclosed (e.g., 25% FPS increase at 10 enclosed objects), but performance decreases if <4 objects are enclosed [S37, unofficial]. Bounding Spheres can work together with Orthogonal Culling by culling bounding spheres instead of single objects, decreasing the number of orthogonal projections made [S37, unofficial]. Implemented and tested in the GLSL shader [S37, unofficial].

### Hybrid Ray Marching
Integrates ray marching with distance-based empty space leaping for complex scenes, using coarse SDFs to compute large skips in low-density regions before switching to fine-grained tracing near features [S13]. Balances speed and accuracy in multi-material volumes [S13].

### Acceleration Structures for SDF Evaluation
A set of optimization nodes embedded directly in hierarchical construction trees to reduce the computational cost of field function evaluation while preserving Lipschitz or conservative properties [S43, abstract only, unofficial]. Avoids external accompanying data structures such as octrees by embedding acceleration nodes directly in the construction tree [S43, abstract only, unofficial]. Uses proxy and continuous level of detail nodes to reduce the overall evaluation cost [S43, abstract only, unofficial]. Applies a normal warping technique to enhance surface details with negligible computational overhead [S43, abstract only, unofficial]. Speeds up signed distance field evaluation by up to three orders of magnitude compared to standard evaluation [S43, abstract only, unofficial]. Applies to both ray-surface intersection computation in sphere tracing applications and polygonization algorithms [S43, abstract only, unofficial].

### Harnack Tracing
A method for visualizing surfaces encoded by harmonic functions (including angle-valued functions and those with singularities) by using conservative Harnack bounds on the growth of harmonic functions to determine step sizes, avoiding numerical issues common to generic root finding methods [S33, unofficial]. Uses conservative Harnack bounds on the growth of harmonic functions to determine the step size for each iteration, ensuring the step does not cross a level set boundary [S33, unofficial]. Performs pointwise evaluation of the harmonic function at the current position to check for convergence to the target level set [S33, unofficial]. Unlike sphere tracing which uses distance bounds, Harnack tracing uses bounds on the growth of harmonic functions; it avoids numerical issues common to generic root finding methods and can visualize surfaces directly from point clouds or polygon soup without linear solves or mesh extraction [S33, unofficial].

### Claybook SDF Construction
A method for fully real-time deformable SDF-based worlds, using a global dense SDF with mip levels for acceleration [S44, unofficial]. Constructs a global SDF, builds 5 mip levels where each level encodes distance values twice as great as the previous, uses sphere-tracing sampling coarser mip levels to travel greater distances conservatively, and ascends/descends mip levels based on sampled distance magnitude [S44, unofficial]. Applies pre-defined 'brushes' to the world SDF, re-evaluating only nearby affected areas due to brush locality [S44, unofficial]. Uses a global SDF volume of resolution 1024x1024x512 with five mip levels. Compact data structures (like SVOs) are incompatible with this modification method because surface-intersecting voxel counts are not static, requiring slow insertions and indirection tables; dense volumes allow direct spatial indexing [S44, unofficial]. Used in Claybook (Aaltonen, 2018) [S44, unofficial].

## Operating characteristics
*   **Time Complexity:** The number of iterations depends on the scene geometry and the Lipschitz constant. In empty space, steps are large, leading to $O(1)$ or $O(\log N)$ behavior relative to distance. Near surfaces, steps shrink, leading to $O(1/\epsilon)$ iterations for precision $\epsilon$ [S2][S17, unofficial].
*   **Memory Complexity:** $O(1)$ for the core algorithm, excluding the storage of the SDF function or acceleration structures [S17, unofficial].
*   **Measured Performance:** Performance varies by scene. In tests comparing Grid Sphere Tracing (GST) and Sphere Tracing (ST), ST showed varying performance depending on the scene (e.g., 22.6 vs 15.4 for GST in one test case) [S1, unofficial]. Bounding sphere optimizations can increase FPS by 25% with 10 enclosed objects [S37, unofficial].
*   **Scaling:** Scales well with parallelization (e.g., GPU) as each ray is independent [S17, unofficial].
*   **Strengths:** No preprocessing required for simple primitives; perfect geometry representation; easy to combine primitives via CSG [S17, S37, unofficial].
*   **Limitations:** Slow convergence near flat surfaces or grazing angles; requires a valid SDF or Lipschitz function; can be computationally expensive for complex scenes without acceleration [S1, S17, unofficial].
*   **When to Use:** Real-time rendering of analytic geometry, procedural modeling, antialiased rendering (with cone tracing) [S14, S17, unofficial].
*   **When Not to Use:** Scenes with highly complex, non-analytic geometry where polygonal meshes are more efficient; scenes where the SDF is expensive to evaluate and no acceleration structure is used [S17, unofficial].

## Background
Sphere Tracing was introduced by John Hart in 1996 in the paper "Sphere Tracing: A Geometric Method for the Antialiased Ray Tracing of Implicit Surfaces" [S14, unofficial][S40]. It is based on the geometric property of distance functions and has become a fundamental technique in real-time graphics for rendering implicit surfaces [S17, S41, unofficial]. It is widely used in shader programming, particularly on platforms like Shadertoy, for creating procedural 3D art [S4, S24, unofficial]. The method has been extended and optimized in various ways, including enhanced sphere tracing, cone tracing, and integration with neural networks [S33, unofficial][S43, abstract only, unofficial][S44, unofficial].
