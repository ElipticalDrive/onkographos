# Sphere Tracing

Also called: Hart's Sphere Tracing, SDF Sphere Tracing, SDF Tracing

## Overview
Sphere Tracing is a ray marching algorithm for rendering implicit surfaces defined by Signed Distance Functions (SDFs) [S3, S14, unofficial]. It solves the problem of finding the intersection between a ray and a continuous surface without explicit polygonal geometry by iteratively stepping along the ray by the distance to the nearest surface [S4, S12, unofficial]. Unlike standard constant-step ray marching, which samples at fixed intervals and risks missing thin geometry or requiring excessive samples for precision, Sphere Tracing uses the SDF value as a guaranteed lower bound on the distance to the surface [S12, S18, unofficial]. This allows the ray to "leap" over empty space efficiently while guaranteeing no surface is skipped, provided the function satisfies the Lipschitz condition with constant $\lambda=1$ [S2, S13]. It sets itself apart from its siblings by relying strictly on the geometric distance property of SDFs for step sizing, whereas variants like [Enhanced Sphere Tracing](3811-enhanced-sphere-tracing.md) relax this bound for speed, and [Interval Raymarching](13020-interval-raymarching.md) handles uncertainty in function evaluation.

## How it works
**Inputs:**
*   Ray origin $\mathbf{o}$ and normalized direction $\mathbf{d}$ [S37, unofficial].
*   Scene function $f(\mathbf{p})$: An SDF returning the signed distance from point $\mathbf{p}$ to the nearest surface (positive outside, negative inside) [S2][S30, unofficial].
*   Maximum travel distance $t_{max}$ (or $D$) [S40][S19, unofficial].
*   Maximum iteration count $N_{max}$ [S1, S12, unofficial].
*   Convergence threshold $\epsilon$ (e.g., $0.001$) [S17, S35, unofficial].

**Outputs:**
*   Intersection distance $t$ along the ray [S10, unofficial].
*   Hit status (boolean or mask) [S10, unofficial].
*   (Optional) Intersection point $\mathbf{p} = \mathbf{o} + t\mathbf{d}$ and normal $\mathbf{n} = \nabla f(\mathbf{p})$ [S19, unofficial].

**Data Structures:**
*   Scalar $t$: Accumulated distance along the ray, initialized to $0$ or a small epsilon (e.g., $0.001$) to avoid self-intersection at the camera [S4, S35, unofficial].
*   Integer $i$: Iteration counter, initialized to $0$.
*   Point $\mathbf{p}$: Current position on the ray, computed as $\mathbf{o} + t\mathbf{d}$ [S20, unofficial].

**Step-by-Step Algorithm:**
1.  **Initialization:** Set $t \leftarrow \epsilon$ (or $0$) and $i \leftarrow 0$ [S4, S35, unofficial].
2.  **Position Update:** Compute current position $\mathbf{p} \leftarrow \mathbf{o} + t\mathbf{d}$ [S20, unofficial].
3.  **SDF Evaluation:** Query the scene function $d \leftarrow f(\mathbf{p})$ [S6, S22, unofficial].
4.  **Termination Check (Hit):** If $d < \epsilon$, the ray has converged to the surface. Terminate and return $t$ as the hit distance [S8, S37, unofficial].
    *   *Note:* Some implementations use a relative threshold, such as $d < \epsilon \cdot t$, to maintain precision at large distances [S20, unofficial].
5.  **Termination Check (Miss):** If $t \ge t_{max}$, the ray has exited the scene. Terminate and return failure/miss [S19, S35, unofficial].
6.  **Termination Check (Stall):** If $i \ge N_{max}$, terminate to prevent infinite loops [S1, S12, unofficial].
7.  **Step Advancement:** Advance the ray by the distance $d$.
    *   Standard Step: $t \leftarrow t + d$ [S20, S31, unofficial].
    *   *Safety Note:* If $d \le 0$, the ray is inside the object. Depending on the application, this may be treated as a hit, or the ray may be clamped to step by a small minimum value to escape [S38, unofficial][S15].
8.  **Increment:** $i \leftarrow i + 1$.
9.  **Loop:** Repeat from Step 2.

**Pseudocode:**
```python
def sphere_trace(ray_origin, ray_direction, scene_sdf, max_dist=100.0, max_steps=128, epsilon=0.001):
    """
    Performs sphere tracing to find the intersection of a ray with an SDF surface.
    
    Args:
        ray_origin (vec3): The starting point of the ray.
        ray_direction (vec3): The normalized direction vector of the ray.
        scene_sdf (function): A function f(p) returning the signed distance to the nearest surface.
        max_dist (float): Maximum distance the ray can travel.
        max_steps (int): Maximum number of iterations allowed.
        epsilon (float): Convergence threshold for surface hit.
        
    Returns:
        float: Distance to intersection, or max_dist if no hit.
        bool: True if hit, False otherwise.
    """
    t = epsilon  # Initialize with small epsilon to avoid self-intersection [S4, S35, unofficial]
    
    for i in range(max_steps):
        # 1. Calculate current position on the ray
        p = ray_origin + ray_direction * t
        
        # 2. Evaluate the Signed Distance Function
        d = scene_sdf(p)
        
        # 3. Check for convergence (Hit)
        # If distance is less than epsilon, we consider it a hit [S8, S37, unofficial]
        if d < epsilon:
            return t, True
            
        # 4. Check for escape (Miss)
        # If we have traveled too far, we missed the object [S19, S35, unofficial]
        if t >= max_dist:
            return max_dist, False
            
        # 5. Advance the ray
        # The step size is the distance to the nearest surface [S20, S31, unofficial]
        t = t + d
        
    # 6. Max steps reached
    return t, False
```

**Parameters and Typical Values:**
*   $\epsilon$: $0.001$ to $0.0001$ [S17, S35, unofficial].
*   $t_{max}$: $100.0$ to $1000.0$ [S11, S19, unofficial].
*   $N_{max}$: $10$ to $128$ for simple scenes; up to $1024$ for complex or deep volumes [S12, S32, unofficial].
*   Lipschitz Constant $\lambda$: For strict SDFs, $\lambda=1$. If the function is not a true SDF but only a Lipschitz function, the step size must be scaled: $\Delta t = \frac{|f(\mathbf{p})|}{\lambda}$ [S2][S29, unofficial].

**Edge Cases and Pitfalls:**
*   **Lipschitz Violation:** If the scene function does not satisfy the Lipschitz condition with $\lambda=1$ (i.e., the gradient magnitude exceeds 1), the step size $d$ is no longer a safe lower bound, and the ray may overshoot the surface [S2][S29, unofficial].
*   **Inside Geometry:** If $f(\mathbf{p}) < 0$, the ray is inside the object. Standard sphere tracing may step backwards or stall. Implementations often clamp negative distances to a small positive value or treat them as immediate hits [S38, unofficial][S15].
*   **Precision:** At large distances, absolute epsilon thresholds may fail to detect intersections. A relative threshold ($d < \epsilon \cdot t$) is more robust [S20, unofficial].
*   **Oscillation:** Near grazing angles or flat surfaces, the ray may oscillate near the surface if the step size is not handled carefully. Enhanced variants or smaller epsilons may be required [S1, S39, unofficial].

## Subtopics

### [Zeno Implementation](1544-zeno-implementation.md)
A software architecture prioritizing ease of extension for new implicit surfaces over raw shading performance. It replaces explicit normal derivation with a fixed six-sample numerical gradient approximation.

### [Cone Intersection](1553-cone-intersection.md)
An antialiasing technique representing a pixel as a viewing cone to allow symbolic prefiltering, eliminating aliasing at grazing angles by computing fractional coverage.

### [Segment Tracing](1675-segment-tracing.md)
Computes local Lipschitz bounds on candidate segments to determine adaptive step sizes, reducing field function queries compared to global bounds.

### [Quadric Tracing](1866-quadric-tracing.md)
Accelerates tracing by precomputing an augmented distance field using quadric surfaces to bound geometry, reducing SDF evaluations near surfaces.

### [Enhanced Sphere Tracing](3811-enhanced-sphere-tracing.md)
A family of optimizations that take steps larger than the strict Lipschitz bound or predict optimal step sizes based on local geometry to accelerate convergence.

### [Uniform Sphere Tracing](4406-uniform-sphere-tracing.md)
Combines ray marching with optical depth integration for volume rendering, using fixed or clamped step sizes for optical integration while using SDF for surface detection.

### [Synchronized-tracing](8552-synchronized-tracing.md)
A tile-based pipeline for implicit volumes that synchronizes threads within a subfrustum using a low-resolution A-buffer to manage coherence.

### [Cone-Traced Supersampling](9466-cone-traced-supersampling.md)
An efficient spatial antialiasing solution that performs supersampling along the traced ray near surfaces with partial visibility, avoiding additional rays per pixel.

### [Kernel-Reflection Sequences](10186-kernel-reflection-sequences.md)
A procedural modeling technique for generating fractal geometries using SDFs and reflection transformations, enabling real-time sphere tracing on GPUs without recursion.

### [Analytical and Differentiable Methods](13369-analytical-and-differentiable-methods.md)
Methods that extend sphere tracing to support differentiability for optimization and gradient-based rendering.

### Cube-tracing
An algorithm using the chessboard (Manhattan) metric for distance computation instead of Euclidean distance. It potentially results in more efficiently computed distances and ray intersection, though it is noted as further research [S42].

### Bounding Sphere Optimization
An optimization that groups multiple objects into a single bounding sphere to decrease calculation counts per march. Performance gain increases with the number of enclosed objects (e.g., >3 objects), with gains up to 25% FPS at 10 objects. It works with orthogonal culling [S37, unofficial].

### Hybrid Ray Marching
Integrates ray marching with distance-based empty space leaping for complex scenes, using coarse SDFs to compute large skips in low-density regions before switching to fine-grained tracing near features [S13].

### Acceleration Structures for SDF Evaluation
Optimization nodes embedded directly in hierarchical construction trees to reduce computational cost of field function evaluation while preserving Lipschitz properties. Uses proxy and continuous level-of-detail nodes, speeding up evaluation by up to three orders of magnitude [S43, abstract only, unofficial].

### Harnack Tracing
A method for visualizing surfaces encoded by harmonic functions using conservative Harnack bounds on the growth of harmonic functions to determine step sizes, avoiding numerical issues common to generic root finding [S33, unofficial].

### Claybook SDF Construction
A method for real-time deformable SDF-based worlds using a global dense SDF with 5 mip levels. Sphere tracing samples coarser mip levels for larger conservative steps, ascending/descending based on distance magnitude. Requires dense volumes, not compact structures like SVOs [S44, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$, where $N$ is the number of iterations required for convergence. $N$ depends on the scene complexity and the ratio of step size to surface curvature. In empty space, $N$ is small; near complex surfaces, $N$ increases [S1, S39, unofficial].
*   **Memory Complexity:** $O(1)$ per ray, as it only stores the current position and distance. No auxiliary data structures are required for the core algorithm, though acceleration structures (like the bounding spheres or mipmaps mentioned in subtopics) may add memory overhead [S37, S44, unofficial].
*   **Measured Performance:** In tested scenes, sphere tracing achieves real-time performance on GPUs. For example, combining sphere tracing with voxel traversal (GST) showed competitive frame rates compared to analytic and Newton-Raphson methods for specific geometries [S1, unofficial]. Bounding sphere optimizations can increase FPS by 25% when enclosing 10 objects [S37, unofficial].
*   **Scaling:** Performance scales linearly with the number of iterations. It is highly parallelizable across pixels/rays on GPUs [S1, S28, unofficial].
*   **Strengths:**
    *   **Robustness:** Guarantees no surface intersection is missed if the SDF is valid (Lipschitz $\lambda=1$) [S12, S18, unofficial].
    *   **Simplicity:** Easy to implement in shaders; no need for explicit mesh data or complex intersection tests [S24, S30, unofficial].
    *   **Smoothness:** Naturally handles smooth unions and CSG operations via SDF composition [S2][S19, unofficial].
*   **Limitations:**
    *   **Slow Convergence:** Rays grazing surfaces or moving parallel to them may require many small steps, leading to performance bottlenecks [S1, unofficial][S5].
    *   **SDF Requirement:** Requires a valid, differentiable (for normals) SDF for the entire scene. Constructing SDFs for complex, non-analytic geometry can be difficult [S14, S24, unofficial].
    *   **Precision Issues:** Near-zero distances can cause oscillation or premature termination if epsilon is not chosen carefully [S20, S39, unofficial].
*   **When to Use:** Ideal for real-time rendering of procedural geometry, implicit surfaces, and scenes defined by mathematical functions where polygonal meshes are unavailable or undesirable [S24, S30, unofficial].
*   **When Not to Use:** Not suitable for scenes with highly complex, non-analytic geometry where SDFs are expensive to compute or unavailable. Also less efficient than polygonal ray tracing for scenes with large empty spaces and simple, distant objects where acceleration structures like BVHs are more effective [S1, unofficial][S5].

## Background
Sphere Tracing was introduced by John Hart in 1996 in the paper "Sphere Tracing: A Geometric Method for the Antialiased Ray Tracing of Implicit Surfaces" [S14, unofficial][S40]. It was developed as a robust method for rendering implicit surfaces without explicit polygonal representation. The method leverages the geometric property of distance functions to ensure safe stepping. It has since become a foundational technique in procedural rendering, shader-based graphics, and neural rendering (e.g., NeRFs, SDF-based neural fields) [S10, unofficial][S15][S34, unofficial]. Variants and optimizations have been developed to address its limitations, such as enhanced sphere tracing for faster convergence and cone tracing for antialiasing [S1, S14, unofficial].
