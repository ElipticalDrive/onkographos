# Sphere Tracing

Also called: Aggressive Ray Marching with SDF, Ray Marching with SDF, Ray Marching with SDF and Ray Marching Ratio, Sphere Tracing with SDFs

## Overview
Sphere Tracing is a ray-marching algorithm that renders implicit surfaces defined by Signed Distance Functions (SDFs) by stepping along a ray by the distance returned by the SDF evaluation at the current position [S1, S2, S3, unofficial]. It solves the problem of efficiently intersecting complex, procedural, or fractal geometry without explicit mesh data by guaranteeing that no surface is missed, provided the SDF is Lipschitz continuous with a constant of 1 [S2, S5, S9643]. It sets itself apart from fixed-step ray marching by using adaptive, optimal step sizes that allow large jumps in empty space and fine precision near surfaces, and from [FBM Sphere Tracing with BVH Acceleration](1728-fbm-sphere-tracing-with-bvh-acceleration.md) by relying purely on the mathematical properties of the distance field rather than spatial acceleration structures for the core traversal.

## How it works
**Inputs and Outputs:**
*   **Inputs:** Camera origin $\mathbf{o}$, normalized ray direction $\mathbf{d}$, maximum ray distance $t_{max}$, convergence threshold $\epsilon$ (e.g., $0.001$), and the scene SDF function $f(\mathbf{p})$.
*   **Outputs:** Hit distance $t$, hit position $\mathbf{p}$, surface normal $\mathbf{n}$, and accumulated color/lighting.

**Data Structures:**
*   **SDF Function:** A scalar function $f: \mathbb{R}^3 \to \mathbb{R}$ mapping a 3D point to the shortest Euclidean distance to the nearest surface. $f(\mathbf{p}) < 0$ indicates inside, $f(\mathbf{p}) = 0$ on the surface, and $f(\mathbf{p}) > 0$ outside [S2, S5, S9643].
*   **Ray State:** Accumulated distance $t$ (initialized to $0$ or a near-plane value) [S1, S3, unofficial].

**Algorithm Steps:**
1.  **Initialization:** Set accumulated distance $t \leftarrow 0$ (or $t_{near}$) [S1, S3, unofficial].
2.  **Loop:** For a maximum number of iterations $N_{max}$ (e.g., 1024):
    a.  **Position Calculation:** Compute current world position $\mathbf{p} = \mathbf{o} + t\mathbf{d}$ [S1, S34, unofficial].
    b.  **SDF Evaluation:** Evaluate $d = f(\mathbf{p})$ [S1, S33, unofficial].
    c.  **Termination Check:**
        *   If $d < \epsilon$, the ray has hit the surface. Break loop [S1, S39, unofficial].
        *   If $t > t_{max}$, the ray has escaped. Break loop [S1, S34, unofficial].
    d.  **Step:** Advance the ray: $t \leftarrow t + d$ [S1, S33, unofficial]. This step is "safe" because the SDF guarantees no geometry exists within distance $d$ of $\mathbf{p}$ [S50, unofficial].
3.  **Shading:** Upon hit, estimate the surface normal $\mathbf{n}$ using finite differences: $\mathbf{n} = \frac{\nabla f(\mathbf{p})}{\|\nabla f(\mathbf{p})\|}$ [S2055, S4619]. Compute lighting based on $\mathbf{n}$, $\mathbf{p}$, and material properties [S1, unofficial].

**Scene Composition:**
*   **Union:** $\min(d_1, d_2)$ [S35, S38, unofficial].
*   **Intersection:** $\max(d_1, d_2)$ [S35, S38, unofficial].
*   **Subtraction:** $\max(-d_1, d_2)$ [S35, S38, unofficial].
*   **Transformations:** Apply rotation, translation, and scaling to the query point $\mathbf{p}$ before evaluation or to the SDF function itself [S3850].

**Parameters:**
*   $\epsilon$: Convergence threshold. Typical value: $0.001$ [S1, S39, unofficial].
*   $N_{max}$: Maximum iterations. Typical value: 1024 [S1, S34, unofficial].
*   $t_{max}$: Maximum ray distance. Scene-dependent.

**Pitfalls and Edge Cases:**
*   **Scaling Errors:** Scaling the input position vector passed to the SDF (e.g., `v * 10.`) breaks the tracing logic because the SDF value no longer represents the true Euclidean distance, causing the ray to step too far and pass through the collision surface [S1, unofficial].
*   **Clamping vs. Tracing:** Clamping the maximum step size (e.g., to $0.001$) turns the algorithm into standard "ray marching" rather than true sphere tracing. While this prevents tracing past collisions, it limits efficiency by removing the benefit of large empty-space leaps [S1, unofficial].
*   **Precision:** In empty regions, SDFs may return extremely large values (e.g., $10^{14}$), which can cause interpolation errors or overflow if not clamped [S9, unofficial].

```python
def sphere_trace(ray_origin, ray_direction, sdf_function, max_iterations=1024, epsilon=0.001, max_distance=100.0):
    """
    Performs sphere tracing for a given ray and SDF.
    
    Args:
        ray_origin (vec3): Camera origin.
        ray_direction (vec3): Normalized ray direction.
        sdf_function (callable): Function f(p) returning signed distance.
        max_iterations (int): Maximum number of steps.
        epsilon (float): Convergence threshold for hit detection.
        max_distance (float): Maximum ray distance to trace.
        
    Returns:
        tuple: (hit, hit_point, hit_distance, normal)
    """
    t = 0.0
    hit = False
    hit_point = None
    normal = None
    
    for i in range(max_iterations):
        # Calculate current position
        current_pos = ray_origin + ray_direction * t
        
        # Evaluate SDF
        dist = sdf_function(current_pos)
        
        # Check for hit
        if dist < epsilon:
            hit = True
            hit_point = current_pos
            # Estimate normal via finite differences (central difference)
            # Note: In practice, analytical normals are preferred if available
            h = 0.001
            dx = sdf_function(current_pos + vec3(h, 0, 0)) - sdf_function(current_pos - vec3(h, 0, 0))
            dy = sdf_function(current_pos + vec3(0, h, 0)) - sdf_function(current_pos - vec3(0, h, 0))
            dz = sdf_function(current_pos + vec3(0, 0, h)) - sdf_function(current_pos - vec3(0, 0, h))
            normal = normalize(vec3(dx, dy, dz))
            break
        
        # Check for escape
        if t > max_distance:
            break
            
        # Step forward
        t += dist
        
    return hit, hit_point, t, normal
```

## Subtopics

### [Zeno Implementation](1544-zeno-implementation.md)
A software architecture minimizing the interface for new implicit surfaces by relying on distance bound functions and optional numerical gradients. Chosen for rapid prototyping of mathematical visualizations.

### [Differentiable Sphere Tracing](2316-differentiable-sphere-tracing.md)
Enables gradient back-propagation through the tracing process for neural SDFs. Chosen when optimizing 3D scene parameters (latent codes, poses) from 2D observations.

### [Raymarched SDF Volume Rendering](3663-raymarched-sdf-volume-rendering.md)
Focuses on the marching loop and shading for implicit surfaces without rasterization. Chosen for infinite sharpness in CAD and procedural design.

### [Pyramid Recursive Ray Marching](3802-pyramid-recursive-ray-marching.md)
Multi-scale acceleration initializing depth at low resolution and refining recursively. Chosen for large scenes with varying detail levels.

### [Sphere Tracing with Composite SDF and Adaptive Sampling](3867-sphere-tracing-with-composite-sdf-and-adaptive-sampling.md)
Handles complex text/arcs alongside diffuse geometry with variance-based adaptive sampling. Chosen for decorative or typographic scenes.

### [Uniform Sphere Tracing](4406-uniform-sphere-tracing.md)
Combines ray marching with optical depth integration for uniform density volumes. Chosen for fog/smoke rendering where SDFs define boundaries.

### [Menger Sponge Raymarching](4875-menger-sponge-raymarching.md)
Implements a specific recursive SDF for fractal geometry with fixed-step iteration. Chosen for fractal visualization.

### [Synchronized-tracing](8552-synchronized-tracing.md)
Tile-based pipeline with thread synchronization for implicit blobtrees. Chosen for interactive modeling with dynamic primitive updates.

### [Cone-Traced Supersampling](9466-cone-traced-supersampling.md)
Spatial antialiasing via cone intersections near surfaces. Chosen for high-quality antialiasing without post-processing blur.

### [Kernel-Reflection Sequences](10186-kernel-reflection-sequences.md)
Non-recursive procedural modeling for fractals. Chosen for real-time GPU rendering of complex fractals without divergent control flow.

### Cube-tracing
An algorithm using the chessboard or Manhattan metric for distance computation instead of Euclidean distance [S4]. It is left as further research but potentially offers more efficiently computed distances and ray intersections [S4].

### Hybrid Ray Marching
Integrates ray marching with distance-based empty space leaping for complex scenes, using coarse SDFs for large skips in low-density regions before switching to fine-grained tracing [S5]. Chosen to balance speed and accuracy in multi-material volumes.

### Acceleration Structures for SDF Evaluation
Optimization nodes embedded directly in hierarchical construction trees to reduce field function evaluation cost while preserving Lipschitz properties [S6, abstract only, unofficial]. Speeds up evaluation by up to three orders of magnitude [S6, abstract only, unofficial]. Chosen for complex CSG trees where external structures like octrees are undesirable.

### Harnack Tracing
Uses conservative Harnack bounds on the growth of harmonic functions to determine step sizes, avoiding numerical issues of generic root finding [S7, unofficial]. Chosen for visualizing surfaces encoded by harmonic functions, including angle-valued functions and singularities, directly from point clouds or polygon soup.

### Claybook SDF Construction
A method for real-time deformable SDF worlds using a global dense SDF with 5 mip levels, where each level encodes distances twice as great as the previous [S8, unofficial]. Chosen for real-time editing with "brushes" that only affect nearby areas. Pitfall: Dense volumes are required; compact structures like SVOs are incompatible due to static voxel count assumptions [S8, unofficial].

### Aeva Analytical SDF Rendering
Avoids discretization by sphere-tracing analytical SDFs at render time, using offline compilation of CSG trees into optimized shaders [S8, unofficial]. Chosen for minimum SDF evaluations per ray. Pitfall: Not suited for real-time modification due to shader recompilation costs [S8, unofficial].

### Conservative Sphere Tracing Step Sizing
A fix for volumetric cloud rendering where aggressive step sizes skip cloud boundaries [S9, unofficial]. Uses a conservative SDF max clamp ($30000.0 \times \text{WorldScale}$), a step size multiplier of $0.4$ (reduced from $0.8$), and a step size max clamp ($2000.0 \times \text{WorldScale}$) [S9, unofficial]. Chosen to eliminate scalloped density artifacts in cloud rendering.

### Analytical Derivatives for Normals and Slopes
Uses analytical derivatives of noise to compute fast normals and slopes, adjusting step size based on slope (Lipschitz constant) [S10, unofficial]. Chosen to speed up raymarching of terrain with heavy noise displacement.

## Operating characteristics
*   **Time Complexity:** $O(N)$ per ray, where $N$ is the number of iterations until hit or escape. $N$ depends on scene complexity and SDF smoothness.
*   **Memory Complexity:** $O(1)$ auxiliary memory per ray, excluding the storage of the SDF function (which may be procedural or stored in a texture/volume).
*   **Performance:** Highly efficient for simple primitives and smooth SDFs due to large empty-space leaps. Performance degrades for highly detailed or noisy SDFs requiring small steps [S10, unofficial].
*   **Strengths:** No preprocessing required for procedural SDFs; infinite sharpness; easy composition via CSG [S3, unofficial].
*   **Limitations:** Requires a valid Lipschitz-continuous SDF; sensitive to scaling errors [S1, unofficial]; may require many iterations for complex details [S10, unofficial].
*   **When to Use:** Procedural geometry, fractals, CAD, and scenes where mesh generation is prohibitive.
*   **When Not to Use:** Scenes with highly discontinuous or non-Lipschitz functions; when explicit mesh topology is required for complex shading models not supported by SDF normals.

## Background
Sphere Tracing was introduced by John Hart in 1996 [S2, S9643]. It leverages the mathematical properties of Signed Distance Functions to provide a safe and efficient method for ray-surface intersection. The method has become a staple in procedural rendering, shader art (e.g., Shadertoy), and implicit surface visualization. Variants and extensions continue to be developed for differentiable rendering, acceleration, and specific geometric primitives [S1, S3, S8, S9, S10, unofficial].
