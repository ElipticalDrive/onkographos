# Sphere Tracing

Also called: Hart's Sphere Tracing, SDF Sphere Tracing, SDF Tracing

## Overview
Sphere Tracing is an iterative ray-marching algorithm for rendering implicit surfaces defined by Signed Distance Functions (SDFs) [S17, S18, unofficial]. It solves the problem of finding the intersection between a camera ray and a continuous geometric surface without explicit polygonal representation by stepping along the ray by a distance guaranteed not to overshoot the surface [S12, S39, unofficial]. Unlike standard ray marching which uses fixed or heuristic step sizes, Sphere Tracing uses the SDF value itself as the step size, ensuring that the "unbounding sphere" at each step contains no geometry [S2, S40]. This guarantees convergence to the surface if the function is Lipschitz continuous, distinguishing it from siblings like [Standard Constant Step Ray Marching](1080-standard-constant-step-ray-marching.md) which may miss thin features [S24, unofficial].

## How it works
**Inputs:**
*   Ray origin $\mathbf{o}$ and normalized direction $\mathbf{d}$ [S37, unofficial].
*   Scene function $f: \mathbb{R}^3 \to \mathbb{R}$, an SDF where $f(\mathbf{p})$ is the signed distance to the nearest surface (positive outside, negative inside) [S30, S33, unofficial].
*   Maximum traversal distance $t_{max}$ (or $D$) [S40][S19, unofficial].
*   Maximum iteration count $N_{max}$ [S1, S12, unofficial].
*   Convergence threshold $\epsilon$ (precision) [S37, S11, unofficial].

**Outputs:**
*   Intersection distance $t$ along the ray [S10, unofficial].
*   Hit status (boolean or mask) [S10, S20, unofficial].

**Data Structures:**
*   Scalar float $t$: current accumulated distance along the ray, initialized to $0.0$ or a small epsilon (e.g., $0.001$) to avoid self-intersection at the origin [S4, S35, unofficial].
*   Integer $i$: iteration counter, initialized to $0$.
*   Vector $\mathbf{p}$: current position in world space, computed as $\mathbf{o} + t\mathbf{d}$ [S37, unofficial].

**Step-by-Step Algorithm:**
1.  Initialize $t = \epsilon_{start}$ (typically $0.001$) and $i = 0$ [S4, S35, unofficial].
2.  Loop while $i < N_{max}$ and $t < t_{max}$:
    a.  Compute current position: $\mathbf{p} = \mathbf{o} + t\mathbf{d}$ [S37, unofficial].
    b.  Evaluate the SDF: $d = f(\mathbf{p})$ [S22, unofficial].
    c.  **Termination Check (Hit):** If $|d| < \epsilon$ (or $d < \epsilon$ for unsigned, or $d < 0$ for inside check), the surface is hit. Return $t$ and hit status [S17, S37, S20, unofficial]. Note: Some implementations use a relative threshold like $0.001 \cdot t$ [S20, unofficial].
    d.  **Termination Check (Miss):** If $t \ge t_{max}$, the ray has escaped. Return miss status [S19, S35, unofficial].
    e.  **Step Size Calculation:** The step size $\Delta t$ is set to $d$. For a true SDF, $d$ is the exact distance to the nearest surface, so moving forward by $d$ places the ray exactly on the surface boundary or past it if the surface is concave relative to the ray path? No, the property of the SDF is that the ball of radius $d$ centered at $\mathbf{p}$ contains no surface points. Therefore, moving forward by $d$ is safe and will not cross the surface [S2, S40].
    f.  **Update:** $t \leftarrow t + d$ [S31, S35, unofficial].
    g.  Increment $i \leftarrow i + 1$ [S35, unofficial].
3.  If the loop terminates without a hit, return miss status [S19, unofficial].

**Formulas:**
*   Ray parameterization: $\mathbf{p}(t) = \mathbf{o} + t\mathbf{d}$ [S37, unofficial].
*   SDF Definition: $f(\mathbf{p}) = \text{dist}(\mathbf{p}, \{f \le 0\})$ if $\mathbf{p}$ is outside, and $- \text{dist}(\mathbf{p}, \{f \le 0\})$ if inside [S33, unofficial].
*   Lipschitz Condition (Generalization): If $f$ is not a strict SDF but a Lipschitz function with constant $\lambda$, the safe step size is $\Delta t = \frac{|f(\mathbf{p})|}{\lambda}$ [S2]. This is called a Signed Distance Bound (SDB) [S2].
*   Sphere Tracing Update: $\mathbf{p}_{n+1} = \mathbf{p}_n + f(\mathbf{p}_n)\mathbf{d}$ [S31, unofficial].

**Parameters:**
*   $\epsilon$: Convergence threshold. Typical values: $0.001$ [S17, S30, unofficial], $0.00001$ [S11, unofficial], $10^{-4}$ [S9, unofficial].
*   $N_{max}$: Maximum steps. Typical values: $128$ [S12, S35, unofficial], $1024$ [S4, S9, unofficial], $255$ [S19, unofficial].
*   $t_{max}$: Maximum distance. Typical values: $100.0$ [S19, S35, unofficial], $60.0$ [S12, unofficial].

**Edge Cases and Pitfalls:**
*   **Lipschitz Violation:** If the scene function is not Lipschitz continuous with constant $\lambda=1$ (i.e., not a true SDF), using $f(\mathbf{p})$ as the step size may cause the ray to overshoot the surface, leading to missed intersections or infinite loops [S2][S4, unofficial]. Scaling by $\lambda$ is required for general implicit functions [S2].
*   **Precision Errors:** Near the surface, floating-point inaccuracies can cause the ray to oscillate or fail to converge if $\epsilon$ is too small relative to the ray's scale [S20, unofficial].
*   **Inside Geometry:** If the ray starts inside an object ($f(\mathbf{o}) < 0$), the standard algorithm steps forward by a negative distance (backwards) if not handled, or steps forward by $|f(\mathbf{p})|$ if using absolute value. Standard sphere tracing assumes starting outside or handles the sign to move towards the boundary [S33, unofficial]. If $f(\mathbf{p}) < 0$, the ray is inside; stepping by $f(\mathbf{p})$ moves it away from the surface in the direction of $\mathbf{d}$? No, $f(\mathbf{p})$ is negative, so $t$ decreases? No, $t$ is accumulated distance. The update $t \leftarrow t + f(\mathbf{p})$ would decrease $t$ if $f(\mathbf{p}) < 0$, which is incorrect for forward marching. Standard implementations often use $t \leftarrow t + |f(\mathbf{p})|$ or check for sign change to detect exit [S1, S19, unofficial]. However, most real-time shaders assume the camera is outside or use $t += d$ where $d$ is the distance to the *nearest* surface, implying $d \ge 0$ for the step size magnitude [S12, S39, unofficial]. If $f(\mathbf{p})$ is negative, the distance to the surface is $|f(\mathbf{p})|$. The ray should step by $|f(\mathbf{p})|$ to reach the boundary. If it crosses to the other side, the sign of $f$ will change, allowing detection of exit [S1, unofficial].
*   **Grazing Angles:** Sphere tracing can require many steps when a ray grazes a surface at a shallow angle, as the SDF value remains small but non-zero for many iterations [S5][S1, unofficial].

**Pseudocode:**
```python
def sphere_trace(ray_origin, ray_direction, scene_sdf, max_dist, max_steps, epsilon):
    """
    Performs sphere tracing to find the intersection of a ray with an SDF surface.
    
    Args:
        ray_origin (vec3): The starting point of the ray.
        ray_direction (vec3): The normalized direction of the ray.
        scene_sdf (function): A function f(p) returning the signed distance to the nearest surface.
        max_dist (float): Maximum distance the ray can travel.
        max_steps (int): Maximum number of iterations allowed.
        epsilon (float): Convergence threshold for surface hit detection.
        
    Returns:
        tuple: (hit: bool, distance: float)
    """
    t = 0.001  # Small initial offset to avoid self-intersection at origin [S4, S35, unofficial]
    
    for i in range(max_steps):
        if t > max_dist:
            return False, t  # Miss: exceeded maximum distance [S19, S35, unofficial]
        
        # Current position on the ray
        p = ray_origin + ray_direction * t
        
        # Evaluate Signed Distance Function
        d = scene_sdf(p)
        
        # Check for surface hit
        # Using absolute value to handle both inside and outside convergence [S28, S37, unofficial]
        # Some implementations use d < epsilon for outside-only [S17, unofficial]
        if abs(d) < epsilon:
            return True, t
        
        # Step forward by the distance to the nearest surface
        # For a true SDF, this step is guaranteed not to cross the surface [S2][S39, unofficial]
        # If d is negative (inside), we step by |d| to reach the boundary
        t += abs(d)
        
    return False, t  # Miss: exceeded maximum steps [S19, unofficial]
```

## Subtopics

### [Zeno Implementation](1544-zeno-implementation.md)
A specific software architecture for sphere tracing that prioritizes ease of extension for new implicit surfaces over raw shading performance. It solves the problem of rapidly prototyping mathematical implicit surfaces by allowing new primitives to be added by defining only a signed distance bound, while avoiding the manual derivation of surface normals. It sets itself apart from standard sphere tracing implementations by replacing the explicit normal function with a fixed six-sample numerical gradient approximation, accepting the minor performance cost as negligible compared to ray intersection overhead.

### [Cone Intersection](1553-cone-intersection.md)
Cone intersection is an antialiasing technique for sphere tracing that represents a pixel as a viewing cone rather than a point ray, allowing symbolic prefiltering to eliminate aliasing artifacts at grazing angles. It differs from standard sphere tracing by detecting intersections with an "inner cover" surface and computing the fractional coverage of the pixel by the implicit surface, whereas siblings like [Segment Tracing](1675-segment-tracing.md) or [Quadric Tracing](1866-quadric-tracing.md) focus on varying step sizes or bounding volumes without necessarily computing area-based coverage fractions.

### [Segment Tracing](1675-segment-tracing.md)
Segment Tracing is a ray marching algorithm that computes local Lipschitz bounds on candidate segments to determine adaptive step sizes, reducing the number of field function queries compared to global Lipschitz bound methods like Sphere Tracing. It works for a particular class of hierarchical skeletal implicit surfaces, leveraging the composition of distance functions and kernel functions to compute directional Lipschitz bounds. Unlike Sphere Tracing, which uses a global bound that limits step size efficiency, Segment Tracing allows larger, safer steps by adapting to the local gradient and field values.

### [Quadric Tracing](1866-quadric-tracing.md)
Quadric tracing is a method to accelerate sphere tracing by precomputing an augmented distance field using quadric surfaces (second-degree algebraic surfaces) to bound or unbound scene geometry, reducing the number of Signed Distance Function (SDF) evaluations. It solves the slowdown of sphere tracing near surfaces and with increasing scene complexity, where function evaluation time and convergence slow drastically. Unlike relaxed sphere tracing (which uses a scalar to determine step size and reverts if too large) or enhanced sphere tracing (which uses previous two radii to approximate planar surfaces), quadric tracing uses precomputed geometric bounds to accelerate convergence. It stops when the computed distance value dips below a threshold, switching to enhanced sphere tracing for final convergence.

### [Enhanced Sphere Tracing](3811-enhanced-sphere-tracing.md)
Enhanced Sphere Tracing is a family of ray-marching optimizations that accelerate convergence toward implicit surfaces defined by Signed Distance Functions (SDFs) by taking steps larger than the strict Lipschitz bound or by predicting optimal step sizes based on local surface geometry. It solves the performance bottleneck of standard sphere tracing, which becomes prohibitively slow when rays graze surfaces at shallow angles or when the surface is locally planar. Unlike standard sphere tracing, which uses the queried distance value as the step size, enhanced variants either over-relax the step size by a constant factor or infer the next step size from the previous two distance queries to approximate the surface as locally flat.

### [Uniform Sphere Tracing](4406-uniform-sphere-tracing.md)
Uniform Sphere Tracing is a volume rendering technique that combines ray marching along a Signed Distance Field (SDF) with optical depth integration to render participating media. It solves the problem of rendering volumetric effects like fog, smoke, or clouds by stepping through a volume, accumulating absorption and scattering, and blending the result with the background. It is distinguished from its parent [Sphere Tracing](2326-sphere-tracing.md) by its specific application to volume rendering with uniform density assumptions and its reliance on fixed or clamped step sizes rather than purely adaptive SDF-driven steps for the optical integration phase, though it uses SDF for surface detection. It differs from [Zeno Implementation](1544-zeno-implementation.md) and [Differentiable Sphere Tracing](2316-differentiable-sphere-tracing.md) by not focusing on differentiability or specific engine integration, but rather on the fundamental algorithmic structure of uniform density volume rendering via ray marching.

### [Synchronized-tracing](8552-synchronized-tracing.md)
Synchronized-tracing is a tile-based rendering pipeline for implicit volumes (blobtrees) that synchronizes threads within a subfrustum to allow coherent field evaluation, using sparse bottom-up tree traversal to prune the blobtree on-the-fly. It is designed for interactive modeling scenarios where no preprocessing is required when primitive parameters are updated. It sets itself apart from standard sphere tracing by introducing a synchronization mechanism via a low-resolution A-buffer to manage thread coherence within workgroups, and by using compact, smooth CSG operators to compute tight bounding volumes for approximate signed distance fields.

### [Cone-Traced Supersampling](9466-cone-traced-supersampling.md)
Cone-Traced Supersampling (CTSS) is an efficient spatial antialiasing solution for Signed Distance Field (SDF) rendering that performs supersampling along the traced ray near surfaces with partial visibility. It identifies object contours by evaluating cone intersections within a pixel's view frustum, avoiding the need for casting additional rays per pixel or offline prefiltering. Subpixel Edge Reconstruction (SER) extends CTSS to locate and resolve complex pixels with geometric edges in relatively flat regions that are otherwise undetected by cone intersections. Unlike conventional supersampling, CTSS minimizes shading computations, and unlike post-processing filters, it avoids undesirable blurriness and ghosting.

### [Kernel-Reflection Sequences](10186-kernel-reflection-sequences.md)
Kernel-Reflection Sequences (KRS) are a procedural modeling technique for generating complex, fractal-like geometries using Signed Distance Functions (SDFs) and reflection transformations. It solves the problem of evaluating global distance functions for recursive structures without recursion, enabling real-time sphere tracing on parallel hardware like GPUs. Unlike standard Iterated Function Systems (IFS) which require recursive traversal and cause divergent control flow, KRS uses a fixed operation count logarithmic time algorithm, allowing efficient parallelization.

### Cube-tracing
An algorithm using the chessboard metric (or Manhattan metric) for distance computation, potentially resulting in more efficiently computed distances and ray intersection. Left as further research [S42].

### Bounding Sphere Optimization
An optimization that decreases the number of calculations made in each march by enclosing several objects into one bounding sphere [S37, unofficial]. Objects should be bound in an adaptive way, enclosing objects depending on how they are grouped per frame, approximating the sphere definition for increased performance rather than computing it exactly [S37, unofficial]. Performance gain increases as the number of objects inside the sphere increases, with a gain occurring when >3 objects are enclosed (e.g., 25% FPS increase at 10 objects), but performance decreases if <4 objects are enclosed [S37, unofficial]. Bounding Spheres can work together with Orthogonal Culling by culling bounding spheres instead of single objects, decreasing the number of orthogonal projections made [S37, unofficial]. Implemented and tested in GLSL shaders, requiring FPS measurement against unoptimized scenes [S37, unofficial].

### Hybrid Ray Marching
Integrates ray marching with distance-based empty space leaping for complex scenes, using coarse SDFs to compute large skips in low-density regions before switching to fine-grained tracing near features [S13]. Balances speed and accuracy in multi-material volumes [S13].

### Acceleration Structures for SDF Evaluation
A set of optimization nodes embedded directly in hierarchical construction trees to reduce the computational cost of field function evaluation while preserving Lipschitz or conservative properties [S43, abstract only, unofficial]. Avoids external accompanying data structures such as octrees by embedding acceleration nodes directly in the construction tree [S43, abstract only, unofficial]. Uses proxy and continuous level of detail nodes to reduce the overall evaluation cost [S43, abstract only, unofficial]. Applies a normal warping technique to enhance surface details with negligible computational overhead [S43, abstract only, unofficial]. Speeds up signed distance field evaluation by up to three orders of magnitude compared to standard evaluation [S43, abstract only, unofficial]. Applies to both ray-surface intersection computation in sphere tracing applications and polygonization algorithms [S43, abstract only, unofficial].

### Harnack Tracing
A method for visualizing surfaces encoded by harmonic functions (including angle-valued functions and those with singularities) by using conservative Harnack bounds on the growth of harmonic functions to determine step sizes, avoiding numerical issues common to generic root finding methods [S33, unofficial]. Uses conservative Harnack bounds on the growth of harmonic functions to determine the step size for each iteration, ensuring the step does not cross a level set boundary [S33, unofficial]. Performs pointwise evaluation of the harmonic function at the current position to check for convergence to the target level set [S33, unofficial]. Unlike sphere tracing which uses distance bounds, Harnack tracing uses bounds on the growth of harmonic functions; it avoids numerical issues common to generic root finding methods and can visualize surfaces directly from point clouds or polygon soup without linear solves or mesh extraction [S33, unofficial].

### Claybook SDF Construction
A method for fully real-time deformable SDF-based worlds, using a global dense SDF with mip levels for acceleration [S44, unofficial]. Constructs a global SDF, builds 5 mip levels where each level encodes distance values twice as great as the previous, uses sphere-tracing sampling coarser mip levels to travel greater distances conservatively, and ascends/descends mip levels based on sampled distance magnitude [S44, unofficial]. Applies pre-defined 'brushes' to the world SDF, re-evaluating only nearby affected areas due to brush locality [S44, unofficial]. Uses a global SDF volume of resolution 1024x1024x512 with five mip levels. Compact data structures (like SVOs) are incompatible with this modification method because surface-intersecting voxel counts are not static, requiring slow insertions and indirection tables; dense volumes allow direct spatial indexing [S44, unofficial]. Used in Claybook (Aaltonen, 2018) [S44, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of iterations to convergence. $N$ depends on the distance to the surface and the local curvature. In the best case (perpendicular approach to flat surfaces), $N$ is small. In the worst case (grazing angles or concave features), $N$ can be large [S5].
*   **Memory Complexity:** $O(1)$ auxiliary memory per ray, as only the current position and distance are stored. The SDF evaluation itself may require memory if the scene is stored in a texture or grid, but the algorithm itself is stateless between steps [S2][S12, unofficial].
*   **Measured Performance:** Performance varies by scene complexity. In tests comparing traversal methods, Sphere Tracing (ST) showed varying frame rates depending on the scene (e.g., 22.6 FPS vs 15.4 FPS for Grid Sphere Tracing in one benchmark) [S1, unofficial]. Bounding Sphere Optimization can increase FPS by 25% when enclosing 10 objects [S37, unofficial].
*   **Scaling:** Scales well with parallelization (GPU) as each ray is independent. Performance degrades with increasing scene complexity if the SDF evaluation cost increases [S1, unofficial].
*   **Strengths:** Guaranteed convergence for Lipschitz functions; no need for explicit geometry or acceleration structures (BVH/Octree) for the marching phase itself; supports complex CSG operations naturally [S2][S17, unofficial].
*   **Limitations:** Slow convergence at grazing angles; requires the scene to be representable as an SDF; SDF evaluation can be expensive for complex scenes [S5][S1, unofficial].
*   **When to Use:** Ideal for procedural geometry, implicit surfaces, and real-time rendering where explicit meshes are unavailable or too complex [S17, S24, unofficial].
*   **When Not to Use:** When the scene is best represented by explicit polygons and acceleration structures (BVH) are more efficient; when high precision is required at grazing angles without additional techniques like Cone Intersection [S5][S1, unofficial].

## Background
Sphere Tracing was introduced by John Hart in 1996 in the paper "Sphere Tracing: A Geometric Method for the Antialiased Ray Tracing of Implicit Surfaces" [S14, unofficial][S40]. It is based on the geometric property that a sphere centered at a point on a ray, with a radius equal to the distance to the nearest surface, cannot contain any surface points (the "unbounding sphere" property) [S40]. This allows the ray to safely leap forward by that distance. The method is a specific case of ray marching where the step size is derived from the Lipschitz constant of the implicit function [S2]. It has become a foundational technique in real-time graphics for rendering implicit surfaces, particularly in shader-based rendering and procedural modeling [S17, S24, unofficial].
