# Raymarching with Depth Buffer Occlusion

Also called: Depth-buffered Raymarching, Raymarching with Mesh Interaction, Z-Buffer Occlusion

## Overview
Raymarching with Depth Buffer Occlusion is a technique that allows raymarched Signed Distance Field (SDF) objects to correctly occlude and be occluded by standard mesh-based geometry in a scene [S2, unofficial]. It solves the problem where raymarched objects typically float on top of all other geometry because the raymarching loop ignores the depth of existing meshes [S2, unofficial]. By sampling the scene's depth buffer to determine the distance to the nearest mesh surface, the raymarcher can terminate early if it passes that distance, ensuring proper layering [S2, unofficial]. This method is distinct from pure SDF rendering as it integrates explicit rasterized depth information into the iterative raymarching process.

## How it works
The method integrates the scene's depth buffer into the sphere tracing loop defined in [Distance-field ray marching](21-distance-field-ray-marching.md). It requires access to the camera's view matrix, inverse view matrix, and the rendered depth texture.

### Inputs and Outputs
*   **Inputs**:
    *   Ray origin $\mathbf{o}$ (camera position in world space).
    *   Ray direction $\mathbf{d}$ (normalized direction in world space).
    *   Depth buffer texture $\mathcal{D}$ (containing linear or non-linear depth values).
    *   View matrix $V$ and Inverse View Matrix $V^{-1}$.
    *   SDF function $f(\mathbf{p})$.
*   **Outputs**:
    *   Final color $C$ for the pixel, blending the raymarched SDF result with the background mesh color.

### Data Structures
1.  **Depth Buffer**: A 2D texture (e.g., `sampler2D`) storing depth values. In Unity, this is accessed via `_CameraDepthTexture` [S2, unofficial]. The values are typically non-linear (logarithmic) and must be converted to linear eyespace depth [S2, unofficial].
2.  **Vertex Shader Output**: A structure containing the world-space ray direction. To facilitate depth calculation, the ray direction is transformed from eyespace to worldspace and normalized in the Z-axis [S2, unofficial].

### Algorithm Steps

1.  **Ray Direction Normalization (Vertex Shader)**:
    The ray direction $\mathbf{r}_d$ is computed in eyespace (view space). In eyespace, the camera looks down the negative Z-axis ($z < 0$ is forward) [S2, unofficial]. To calculate the true distance from the depth buffer, the ray direction is normalized such that its Z-component is $1.0$ (or $-1.0$ depending on convention, but magnitude in Z is 1) [S2, unofficial].
    
    Let $\mathbf{r}_n$ be the Z-normalized ray direction in eyespace:
    $$ \mathbf{r}_n = \frac{\mathbf{r}_d}{|r_d.z|} $$
    Note: The absolute value $|r_d.z|$ is used to prevent flipping the ray direction if $r_d.z$ is negative [S2, unofficial].
    
    Transform $\mathbf{r}_n$ from eyespace to worldspace using the inverse view matrix $V^{-1}$:
    $$ \mathbf{r}_{world} = V^{-1} \cdot \begin{bmatrix} \mathbf{r}_n \\ 0 \end{bmatrix} $$
    (Treating $\mathbf{r}_n$ as a direction vector, the w-component is 0) [S2, unofficial].

2.  **Depth Sampling (Fragment Shader)**:
    Sample the depth buffer at the current pixel's UV coordinates to get the non-linear depth value $d_{nonlinear}$ [S2, unofficial]. Convert this to linear eyespace depth $d_{eye}$ using a helper function (e.g., `LinearEyeDepth`) [S2, unofficial].
    
    Calculate the true Euclidean distance $s$ from the camera origin to the mesh surface along the ray. Using similar triangles, the ratio of the true distance $|r|$ to the eyespace depth $d_{eye}$ is equal to the ratio of the length of the Z-normalized ray $|\mathbf{r}_n|$ to 1:
    $$ s = d_{eye} \times |\mathbf{r}_n| $$
    where $|\mathbf{r}_n| = \sqrt{r_{n,x}^2 + r_{n,y}^2 + r_{n,z}^2}$ [S2, unofficial].

3.  **Raymarching Loop**:
    Perform standard sphere tracing starting from the camera origin $\mathbf{o}$ with direction $\mathbf{r}_{world}$ [S2, unofficial].
    
    For each step $i$:
    *   Current position $\mathbf{p} = \mathbf{o} + t \cdot \mathbf{r}_{world}$.
    *   Evaluate SDF: $dist = f(\mathbf{p})$.
    *   **Occlusion Check**: If the accumulated distance $t \ge s$, the ray has passed the mesh surface. Terminate the loop and return a transparent color (or the background color) to allow the mesh to show through [S2, unofficial].
    *   **Surface Hit Check**: If $dist < \epsilon$ (convergence threshold), the ray hit the SDF surface. Compute shading and return the color.
    *   **Step**: Advance $t \leftarrow t + dist$.
    *   **Max Steps**: If $i$ exceeds a maximum step count, terminate [S2, unofficial].

4.  **Blending**:
    The final pixel color is a blend of the background mesh color (from the depth-buffered render) and the raymarched SDF color [S2, unofficial]. If the raymarcher returns transparent (due to occlusion), the background mesh color is used. If it returns an opaque SDF color, it is composited over the background [S2, unofficial].

```python
# Vertex Shader Logic
def compute_ray_direction(vertex_position, view_matrix, inv_view_matrix):
    # 1. Compute ray direction in eyespace (view space)
    # Assuming standard projection, ray direction is derived from vertex position or screen UV
    # rd_eyespace is the direction vector in view space
    rd_eyespace = normalize(...) 
    
    # 2. Normalize in Z-axis
    # Use absolute value to handle negative Z (forward direction in eyespace)
    rn_eyespace = rd_eyespace / abs(rd_eyespace.z)
    
    # 3. Transform to worldspace
    # Treat rn_eyespace as a direction (w=0)
    ray_world = inv_view_matrix * vec4(rn_eyespace, 0.0)
    
    return ray_world.xyz

# Fragment Shader Logic
def raymarch_with_depth(ro_world, rd_world, depth_texture, uv, view_matrix):
    # 1. Sample Depth Buffer
    # Get non-linear depth from texture
    depth_nonlinear = texture(depth_texture, uv).r
    
    # Convert to linear eyespace depth
    # Note: LinearEyeDepth implementation depends on projection matrix
    depth_eye = linear_eye_depth(depth_nonlinear)
    
    # 2. Calculate True Distance to Mesh (s)
    # We need the length of the Z-normalized ray in worldspace? 
    # Actually, the derivation in [S2, unofficial] uses the length of the Z-normalized ray 
    # which is constant for a given view direction. 
    # However, the ray passed to the fragment shader is already in worldspace.
    # The length of the Z-normalized ray in EYESPACE is |rn_eyespace|.
    # But we need the scaling factor for the WORLDSPACE ray?
    # Let's re-read [S2, unofficial]: "depth *= length(i.ray.xyz)" where i.ray is the 
    # transformed Z-normalized ray.
    # So we pass the Z-normalized ray (transformed to world) to the fragment shader.
    
    # i.ray.xyz is the Z-normalized ray in worldspace.
    # Its length is NOT 1.0. It is the scaling factor.
    scale_factor = length(i.ray.xyz)
    
    true_distance_to_mesh = depth_eye * scale_factor
    
    # 3. Raymarch
    t = 0.0
    max_steps = 64
    hit_color = vec4(0, 0, 0, 0) # Transparent
    
    for i in range(max_steps):
        # Occlusion Check: If we passed the mesh, stop
        if t >= true_distance_to_mesh:
            break
            
        # Evaluate SDF
        p = ro_world + t * rd_world
        dist = sdf(p)
        
        # Surface Hit
        if dist < 0.001:
            # Compute normal, lighting, etc.
            hit_color = compute_shading(p, dist)
            break
            
        # Step
        t += dist
        
    return hit_color

def fragment_shader(uv, ro_world, rd_world, i_ray_world, depth_texture):
    # Background color from depth-buffered pass (not shown here, assumed available)
    bg_color = get_background_color(uv)
    
    # Raymarch
    sdf_color = raymarch_with_depth(ro_world, rd_world, depth_texture, uv, ...)
    
    # Blend
    # If sdf_color is transparent (alpha 0), show background
    # If sdf_color is opaque, blend
    final_color = bg_color * (1.0 - sdf_color.a) + sdf_color.rgb * sdf_color.a
    
    return final_color
```

### Parameters
*   **Max Steps**: Typically 64 or higher, depending on scene complexity [S2, unofficial].
*   **Convergence Threshold ($\epsilon$)**: Typically $0.001$ or smaller [S2, unofficial].
*   **Depth Texture**: Platform-specific sampler (e.g., `_CameraDepthTexture` in Unity) [S2, unofficial].

### Edge Cases and Pitfalls
*   **Ray Direction Flip**: In eyespace, $z < 0$ is forward. Dividing the ray direction by $r_d.z$ without taking the absolute value will flip the ray direction if $r_d.z$ is negative, causing the raymarched scene to appear inverted [S2, unofficial].
*   **Depth Precision**: The depth buffer may have limited precision. Using `LinearEyeDepth` is crucial to convert non-linear depth values to linear distances for accurate comparison [S2, unofficial].
*   **Near Plane Clipping**: The depth buffer only contains information for pixels within the view frustum and beyond the near plane. Rays hitting the near plane or outside the view should be handled appropriately [G].
*   **Transparency**: If the mesh in the depth buffer is transparent, the depth value may not represent the true front-most surface. This method assumes the depth buffer contains the front-most opaque geometry [G].

## Subtopics

### Radii Scaling for Sphere-Cone Occlusion
This variant addresses the occlusion of scale-invariant integral surfaces (like skeleton-based sphere-cones) in the depth buffer [S3]. It computes a scaling factor for the radii of sphere-cone primitives to guarantee correct occlusion [S3]. The worst-case configuration for this scaling is two segment primitives aligned with the viewing direction $-\mathbf{v}$, both having radius $\tau$ at point $q$ [S3]. Due to surface scale invariance, the scaling factor is computed numerically for a unit radius case, representing the distance from $q$ to the isosurface in direction $\mathbf{v}$ [S3]. This worst-case configuration is independent of the actual skeleton layout, requiring no additional skeleton processing [S3].

## Operating characteristics
*   **Time Complexity**: Adds $O(1)$ overhead per pixel for depth sampling and distance calculation. The raymarching loop may terminate earlier, potentially reducing the number of SDF evaluations if the mesh is closer than the SDF surface [S2, unofficial].
*   **Memory Complexity**: Requires storage for the depth buffer texture, which is typically already present in the rendering pipeline [S2, unofficial].
*   **Performance**: The method is efficient as it leverages existing hardware depth buffers. The primary cost is the additional arithmetic for depth conversion and the early exit check [S2, unofficial].
*   **Strengths**: Enables seamless integration of raymarched SDF objects with traditional mesh-based geometry, allowing for correct occlusion and interaction [S2, unofficial].
*   **Limitations**: Only works with opaque mesh geometry in the depth buffer. Transparent meshes or SDF objects rendered after the depth pass may not occlude correctly [G]. Requires access to the depth buffer, which may not be available in all rendering contexts (e.g., deferred rendering without depth pre-pass) [G].

## Background
The technique was popularized by Adrian Booth in a blog post detailing the implementation of raymarched distance fields in Unity [S2, unofficial]. It addresses a common issue in hybrid rendering pipelines where raymarched objects fail to interact with rasterized geometry [S2, unofficial]. The method relies on standard graphics API features (depth buffers, view matrices) and does not require specialized hardware beyond standard GPU capabilities [S2, unofficial].
