# Sparse Distance-Field Cache for Interactive Camera Moves

Also called: SDF brick cache, Sparse distance-field cache for interactive 3D camera moves, sparse brick volume cache

## Overview
This method optimizes interactive camera navigation (orbit/dolly) over static fractal surfaces by baking the expensive analytical Distance Estimator (DE) into a sparse 3D brick volume, allowing the renderer to sample precomputed distances instead of re-evaluating the fractal formula every frame [S1, unofficial]. It sets itself apart from standard raymarching by decoupling the geometric query cost from the frame rate during camera motion, trading bounded spatial precision for significant interactive performance gains [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** The analytical Distance Estimator function $DE(x, y, z)$ for the fractal surface, the current camera view volume, and a maximum brick count limit.
*   **Output:** A sparse 3D texture (brick volume) containing precomputed distance values, used for raymarching during interactive preview.

**Data Structures:**
1.  **Brick Volume:** A sparse 3D grid where each active cell is a "brick."
    *   **Brick Layout:** Each brick is a small 3D texture (e.g., $N \times N \times N$ voxels).
    *   **Voxel Content:** A single floating-point value representing the signed distance to the surface.
    *   **Sparsity:** Only bricks where the surface exists (defined by $DE < \text{brick size}$) are allocated. Empty space is represented by the coarse-level empty-space distance.
2.  **Coarse Level:** A lower-resolution representation of the brick volume storing the empty-space distance for regions outside the active surface boundary.

**Parameters:**
*   **Brick Count:** Must be capped to control GPU memory usage [S1, unofficial].
*   **Brick Resolution:** Determines the bounded detail level; suitable for preview, not final output [S1, unofficial].
*   **Bake Time:** Must be less than a few frames' worth of computation to be beneficial [S1, unofficial].

**Algorithm Steps:**
1.  **Progressive Baking:**
    *   Start by baking the coarse level of the brick volume.
    *   Iterate through the 3D space around the surface.
    *   For each potential brick location, evaluate the analytical $DE(x, y, z)$ at the brick center.
    *   If $DE < \text{brick size}$, allocate the brick and populate its voxels by sampling the analytical $DE$ at each voxel center within the brick.
    *   Store the empty-space distance at the coarse level for regions where no bricks are allocated.
    *   Continue until the brick count limit is reached or the surface boundary is fully covered.
2.  **Interactive Raymarching:**
    *   When the camera moves, perform raymarching using the sparse brick volume.
    *   For each ray step, sample the distance from the brick volume using trilinear interpolation.
    *   Utilize hardware texture filtering on the GPU for efficient trilinear distance sampling [S1, unofficial].
    *   Use the sampled distance to advance the ray.
3.  **Cache Rebuild:**
    *   Rebuild the cache only when fractal parameters change, not on every frame [S1, unofficial].
4.  **Final Render:**
    *   Once the camera interaction settles, run the full-detail DE render using the analytical formula to produce the final high-quality frame [S1, unofficial].

**Pseudocode:**

```python
def bake_sparse_sdf_cache(de_function, camera_view_volume, max_brick_count, brick_size, brick_resolution):
    """
    Bakes the distance field into a sparse brick volume.
    """
    brick_volume = Sparse3DTexture()
    coarse_level = CoarseLevelTexture()
    
    # Define the bounding box of the camera view volume
    bounds = camera_view_volume.get_bounds()
    
    # Iterate through the volume in brick-sized steps
    # Note: In practice, this might use a hierarchical traversal or spatial hashing
    # to efficiently find active bricks.
    brick_count = 0
    for x in range(bounds.min_x, bounds.max_x, brick_size):
        for y in range(bounds.min_y, bounds.max_y, brick_size):
            for z in range(bounds.min_z, bounds.max_z, brick_size):
                # Check if this brick is near the surface
                center = Vector3(x + brick_size/2, y + brick_size/2, z + brick_size/2)
                dist = de_function(center)
                
                if dist < brick_size:
                    # Allocate brick and populate
                    brick = Brick(brick_resolution)
                    for i in range(brick_resolution):
                        for j in range(brick_resolution):
                            for k in range(brick_resolution):
                                voxel_pos = center + Vector3(
                                    (i - brick_resolution/2) * (brick_size / brick_resolution),
                                    (j - brick_resolution/2) * (brick_size / brick_resolution),
                                    (k - brick_resolution/2) * (brick_size / brick_resolution)
                                )
                                voxel_dist = de_function(voxel_pos)
                                brick.set_voxel(i, j, k, voxel_dist)
                    
                    brick_volume.set_brick(x, y, z, brick)
                    brick_count += 1
                    
                    if brick_count >= max_brick_count:
                        break
            if brick_count >= max_brick_count:
                break
        if brick_count >= max_brick_count:
            break
            
    # Populate coarse level with empty space distance
    # This is a simplified representation; in reality, it might store
    # the distance to the nearest brick or a conservative bound.
    coarse_level.populate_empty_space_distance(brick_volume, brick_size)
    
    return brick_volume, coarse_level

def raymarch_with_cache(brick_volume, coarse_level, ray_origin, ray_direction, brick_size, brick_resolution):
    """
    Raymarches using the sparse SDF cache.
    """
    t = 0.0
    max_steps = 1000
    
    for step in range(max_steps):
        current_pos = ray_origin + ray_direction * t
        
        # Determine which brick contains the current position
        brick_coords = get_brick_coords(current_pos, brick_size)
        
        # Sample distance from brick volume
        # Use trilinear interpolation for smooth distance estimation
        if brick_volume.has_brick(brick_coords):
            dist = brick_volume.sample_trilinear(brick_coords, current_pos, brick_size, brick_resolution)
        else:
            # Fallback to coarse level empty space distance
            dist = coarse_level.sample_empty_space_distance(current_pos)
            
        # Advance ray
        t += dist
        
        # Check for surface intersection (distance is very small)
        if dist < 1e-4:
            return t, True
            
        # Check if ray has left the view volume (simplified)
        if not is_inside_view_volume(ray_origin + ray_direction * t):
            return t, False
            
    return t, False
```

**Edge Cases and Pitfalls:**
*   **Precision:** The cached-distance error is $\le$ half a voxel diagonal near the surface [S1, unofficial]. This is acceptable for preview but not final output.
*   **Memory:** The brick count must be capped; otherwise, memory usage can explode for complex fractals [S1, unofficial].
*   **Bake Time:** If the bake time exceeds a few frames, the performance gain is lost [S1, unofficial].
*   **Degenerate Input:** If the fractal parameters change, the cache must be rebuilt; using stale data leads to incorrect geometry [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Baking is $O(N)$ where $N$ is the number of voxels in the active surface region. Interactive raymarching is $O(1)$ per step for distance queries (assuming hardware texture sampling), compared to $O(K)$ for analytical DE evaluation where $K$ is the number of iterations in the fractal formula.
*   **Memory Complexity:** $O(B \cdot R^3)$ where $B$ is the number of bricks and $R$ is the brick resolution. Capped by `max_brick_count`.
*   **Measured Performance:** Reduces frame time from seconds to near real time for heavy User Bulb maps and KIFS on interactive camera moves [S1, unofficial].
*   **Strengths:** Significant speedup for interactive camera navigation on expensive fractal formulas; works well on weak and strong hardware for heavy maps [S1, unofficial].
*   **Limitations:** Bounded detail level makes it unsuitable for final output; requires rebuild on parameter changes; memory usage can be high if not capped.
*   **When to Use:** Interactive preview, orbit/dolly camera moves over static fractals.
*   **When Not to Use:** Final rendering, dynamic fractal parameters, scenes requiring high-precision distance estimates.

## Background
This technique was proposed in an issue on the FracturingFog repository, drawing inspiration from games, offline renderers, and GPU computing [S1, unofficial]. It addresses the performance bottleneck of re-evaluating expensive fractal Distance Estimators (DE) every frame during camera movement, a common issue in real-time fractal rendering applications like Dreams/Claybook [S1, unofficial]. The method is part of Phase 3b of issue #1298, focusing on GPU/rendering performance improvements [S1, unofficial].
