# SDF-Accelerated Volumetric Cloud Rendering

Also called: Ray marching with Signed Distance Fields

## Overview
A technique to accelerate real-time volumetric cloud rendering by using a Signed Distance Field (SDF) to skip empty space and determine step sizes, allowing for high sample counts without performance loss [S1, unofficial]. It solves the problem of wasting GPU cycles calculating zero-value samples in sparse cloud volumes, which previously led to 'soft, undefined volumes' or 'horrible banding/noisy output' if sample counts were low [S1, unofficial]. Unlike uniform sampling, this method spends samples only where clouds exist, avoiding expensive calculations for empty space [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A static cloud volume represented by an SDF texture and a density/coverage texture. A ray origin and direction [S1, unofficial].
*   **Output:** The final color and alpha of the ray, integrating scattering and transmittance [S1, unofficial].

**Data Structures:**
1.  **SDF Texture:** A signed, half-precision floating point 3D texture [S1, unofficial].
    *   **Resolution:** $128 \times 32 \times 128$ [S1, unofficial].
    *   **Layout:** Each entry contains the distance to the nearest point of the cloud volume shell. Inside the volume, values are negative [S1, unofficial].
    *   **Scaling:** The texture is stretched by a factor of 6 horizontally to cover a larger area and must tile horizontally for an infinitely extending cloud plane [S1, unofficial].
2.  **Cloud Volume Texture:** An RG16 3D texture of the same resolution as the SDF [S1, unofficial].
    *   **Red Channel:** Coverage [S1, unofficial].
    *   **Green Channel:** Density [S1, unofficial].

**Pre-computation:**
The SDF is pre-computed using a layered system where a compute shader runs for each cloud layer, adding to the RG16 3D texture [S1, unofficial]. The method for generating cloud shapes is similar to the method described by Sébastien Hillaire [S1, unofficial]. Recalculating the distance field texture is expensive (takes about 200ms using a 3-pass compute shader on a GTX1070), so the system is limited to a static cloud volume [S1, unofficial]. Movement is achieved by scrolling the volume itself [S1, unofficial].

**Ray Marching Algorithm:**
The ray marcher operates in two modes [S1, unofficial]:
1.  **SDF Mode:** Used when outside the cloud volume. The step size is determined by the SDF value [S1, unofficial].
2.  **Regular Mode:** Used when inside the cloud volume. The step size is fixed [S1, unofficial].
Areas outside of the cloud volume are skipped entirely [S1, unofficial].

**Pseudocode:**
```python
import math

# Constants
SDF_RESOLUTION = (128, 32, 128)
HORIZONTAL_SCALE = 6.0
FIXED_STEP_SIZE = 0.1  # Uniform variable _StepSize [S1, unofficial]
MAX_RAY_DIST = 1000.0  # [G] Standard ray marching bound

def world_to_sdf_coords(world_pos):
    # Apply horizontal stretch and tiling to map to [0, 1)
    x = ((world_pos[0] * HORIZONTAL_SCALE) % SDF_RESOLUTION[0]) / SDF_RESOLUTION[0]
    y = (world_pos[1] % SDF_RESOLUTION[1]) / SDF_RESOLUTION[1]
    z = (world_pos[2] % SDF_RESOLUTION[2]) / SDF_RESOLUTION[2]
    return (x, y, z)

def density_function(sdf_value):
    # Inside volume (negative SDF), density is positive distance to shell
    return max(-sdf_value, 0.0)

def ray_march(ray_origin, ray_direction):
    accumulated_color = [0.0, 0.0, 0.0]
    accumulated_alpha = 0.0
    current_pos = list(ray_origin)
    ray_t = 0.0

    # Sample initial SDF value
    sdf_val = sample_sdf(current_pos)
    is_inside = sdf_val < 0

    while ray_t < MAX_RAY_DIST and accumulated_alpha < 1.0:
        if is_inside:
            step_size = FIXED_STEP_SIZE
        else:
            step_size = sdf_val
            if step_size < 1e-6:
                break

        # Advance ray
        ray_t += step_size
        current_pos = [current_pos[i] + ray_direction[i] * step_size for i in range(3)]

        # Sample SDF at new position
        next_sdf_val = sample_sdf(current_pos)
        next_is_inside = next_sdf_val < 0

        if is_inside:
            extinction = density_function(sdf_val)
            transmittance = math.exp(-extinction * step_size)
            luminance = get_luminance(current_pos)
            scattered_light = [l * (1.0 - transmittance) for l in luminance]

            # Front-to-back blending
            accumulated_color = [accumulated_color[i] + scattered_light[i] * (1.0 - accumulated_alpha) for i in range(3)]
            accumulated_alpha += (1.0 - accumulated_alpha) * (1.0 - transmittance)

        sdf_val = next_sdf_val
        is_inside = next_is_inside

    return accumulated_color, accumulated_alpha

def sample_sdf(pos):
    coords = world_to_sdf_coords(pos)
    return texture_3d(sdf_texture, coords)

def get_luminance(pos):
    # Sample cloud volume texture for density/coverage and compute luminance
    return [0.0, 0.0, 0.0]  # [G] Implementation-specific
```

**Parameters:**
*   **SDF Texture Resolution:** $128 \times 32 \times 128$ [S1, unofficial].
*   **Horizontal Stretch Factor:** 6 [S1, unofficial].
*   **SDF Texture Format:** Signed, half-precision floating point 3D texture [S1, unofficial].
*   **Fixed Step Size:** Uniform variable `_StepSize` [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** The SDF texture uses half-precision floats, which may introduce quantization artifacts in distance calculations [S1, unofficial].
*   **Static Volume:** The SDF pre-computation is expensive (~200ms on GTX1070), so the cloud volume must be static [S1, unofficial]. Dynamic clouds are not supported without significant performance cost or alternative techniques [S1, unofficial].
*   **Tiling:** The SDF texture must tile horizontally to support an infinitely extending cloud plane [S1, unofficial].
*   **Inside/Outside Transition:** The switch between SDF and Regular modes must be handled carefully to avoid gaps or overlaps in the ray march [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Pre-computation is $O(N)$ where $N$ is the number of voxels in the SDF texture, but is done offline [G]. Ray marching is $O(M)$ where $M$ is the number of samples taken [G]. The SDF allows skipping large empty spaces, reducing $M$ significantly compared to uniform sampling [S1, unofficial].
*   **Memory Complexity:** $O(R^3)$ for the SDF texture, where $R$ is the resolution [G]. For $128 \times 32 \times 128$, this is $524,288$ half-floats, which is relatively small [G].
*   **Measured Performance:** Pre-computation takes ~200ms on a GTX1070 [S1, unofficial]. Real-time rendering is possible with changing time of day and directional shadows [S1, unofficial].
*   **Strengths:** High visual fidelity with well-defined cloud shapes. Efficient use of sample budget by skipping empty space [S1, unofficial].
*   **Limitations:** Static cloud volume only. Pre-computation cost. Requires careful tuning of step sizes and texture resolution [G].
*   **When to Use:** Real-time rendering of static volumetric clouds where visual quality is prioritized over dynamic cloud formation [G].
*   **When Not to Use:** Dynamic cloud simulations, mobile platforms with very limited memory, or scenes requiring frequent updates to the cloud volume [G].

## Background
This technique was developed by the author of the blog post "Rendering volumetric clouds using signed distance fields" [S1, unofficial]. It was implemented in the author's game engine 'UHawk' and demonstrated in a video of the game [S1, unofficial]. The author was inspired by observing sparse but dense cumulus cloud formations and the frustration of achieving well-defined shapes with uniform sampling [S1, unofficial]. The concept of using SDFs for ray marching is based on the work of Jamie Wong, who provided a full overview of signed distance fields [S1, unofficial]. The cloud shape generation method is similar to the method described by Sébastien Hillaire [S1, unofficial].
