# Vertical Buffer Terrain Rendering

Also called: 2D Heightmap Projection, Heightmap Scanline Rasterization

## Overview
Vertical Buffer Terrain Rendering is a software rendering technique that projects a 2D heightmap onto a vertical screen buffer to handle occlusion, drawing horizontal terrain slices from near to far depth [S1, unofficial]. It differs from its parent [Heightfield Rendering](1634-heightfield-rendering.md) by iterating depth intervals and computing screen-space Y positions for terrain heights to draw vertical lines, whereas this method explicitly manages a vertical occlusion buffer (`ybuf`) per column to determine visible segments, effectively rasterizing the terrain surface against a horizon [S1, unofficial].

## How it works
**Inputs and Outputs:**
- **Inputs:** A heightmap image (`height`), a color map image (`color`), a camera state (`cam`) containing position, height, angle, pitch, and tilt, and a vertical occlusion buffer (`ybuf`).
- **Outputs:** A rendered frame displayed on screen, generated via an intermediate render target.

**Data Structures:**
The implementation relies on the following structures [S1, unofficial]:

1.  `struct Camera`:
    -   `Vec2f pos`: Camera position in world space (X, Y).
    -   `float height`: Camera elevation above terrain.
    -   `float angle`: Camera heading in radians.
    -   `float pitch`: Camera vertical tilt in radians.
    -   `float tilt`: Post-render screen tilt in degrees.

2.  `struct Image`:
    -   `int w`: Image width in pixels.
    -   `int h`: Image height in pixels.
    -   `png_bytep *rows`: Array of row pointers to pixel data (RGBA).
    -   `png_structp ptr`: PNG structure pointer.
    -   `png_infop info`: PNG info pointer.

3.  `struct Prog`:
    -   `bool running`: Loop control flag.
    -   `SDL_Window *win`: Window handle.
    -   `SDL_Renderer *rend`: Renderer handle.
    -   `struct Image *color`: Color map.
    -   `struct Image *height`: Height map.
    -   `struct Camera *cam`: Camera state.
    -   `int ybuf[1400]`: Vertical occlusion buffer.
    -   `float target_tilt`: Target tilt value for interpolation.

**Parameters:**
-   Screen Width ($W$): 1400 pixels (internal render target width).
-   Screen Height ($H$): 1400 pixels (internal render target height).
-   Initial `ybuf` value: 1400 (representing "off-screen" or maximum depth).
-   Max Depth Factor: 600.0.
-   Depth Step Increment: 0.01.
-   FOV Half-Angle: $\pm 45^\circ$ ($\pm \pi/4$ radians).

**Algorithm Steps:**

1.  **Initialization:**
    -   Create a 1400×1400 render target and clear it to black.
    -   Initialize `ybuf` array of size 1400 with value 1400 for each column index $i \in [0, 1399]$.
    -   Compute the camera direction vector `dir` from `cam->angle` using a 2D rotation matrix:
        $$ \text{dir} = \begin{pmatrix} \cos(\text{cam->angle}) & -\sin(\text{cam->angle}) \\ \sin(\text{cam->angle}) & \cos(\text{cam->angle}) \end{pmatrix} \begin{pmatrix} 1 \\ 0 \end{pmatrix} $$

2.  **Depth Loop Setup:**
    -   Calculate maximum visible depth: $dist = 600.0 / \cos(\text{cam->pitch})$.
    -   Initialize depth step $dz = dist / 600.0$.
    -   Initialize depth $z = 1.0$.

3.  **Depth Iteration:**
    -   Loop while $z \le dist$:
        -   Compute left and right world positions `lp` and `rp` at $\pm 45^\circ$ from the camera direction, relative to the camera position.
        -   Calculate per-column world step:
            $$ dx = \frac{rp.x - lp.x}{1400.0}, \quad dy = \frac{rp.y - lp.y}{1400.0} $$
        -   Initialize `lp` to the left edge position.

4.  **Column Rasterization:**
    -   Loop screen column $i$ from 0 to 1399:
        -   Sample heightmap at `lp` coordinates. Note: Coordinates are wrapped using `img->w` for both X and Y modulo operations [S1, unofficial].
        -   Let $H_{map}$ be the sampled height value (0-255 range).
        -   Apply pitch offset and depth normalization:
            $$ height = \frac{H_{cam} + (255 - H_{map}) - z \cdot \sin(\text{cam->pitch})}{z} $$
            Where $H_{cam}$ is the camera height. *Note: The source code applies `height -= z * sin(cam->pitch); height /= z;` after initial height calculation, effectively approximating perspective projection with a fixed vertical offset [S1, unofficial].*
        -   Scale to screen Y coordinate:
            $$ Y_{screen} = (height + 0.5) \times 800.0 $$
        -   **Occlusion Check:**
            -   If $Y_{screen} < ybuf[i]$:
                -   Set `bottom = ybuf[i]`.
                -   Update $ybuf[i] = Y_{screen}$.
                -   Sample color from color map at `lp` coordinates.
                -   Draw a vertical line from $(i, Y_{screen})$ to $(i, bottom)$ on the render target.
        -   Advance `lp` by $(dx, dy)$.

5.  **Depth Step Update:**
    -   Increment $dz$ by 0.01.
    -   Increment $z$ by $dz$.

6.  **Final Presentation:**
    -   Copy the 1400×1400 render target to the screen.
    -   Apply a tilt rotation around the center point $(550, 550)$.
    -   Apply an offset of $(-300, -300)$ to the destination rectangle.

**Pseudocode:**

```python
import math

def render_terrain(prog):
    # Constants
    W = 1400
    H = 1400
    MAX_DEPTH_FACTOR = 600.0
    FOV_HALF_ANGLE = math.pi / 4.0
    
    # Initialize render target (conceptual)
    render_target = create_render_target(W, H)
    clear(render_target, (0, 0, 0))
    
    # Initialize vertical buffer
    ybuf = [W] * W  # Size 1400, initialized to 1400
    
    cam = prog.cam
    height_map = prog.height
    color_map = prog.color
    
    # Camera direction
    dir_x = math.cos(cam.angle)
    dir_y = math.sin(cam.angle)
    
    # Max depth
    dist = MAX_DEPTH_FACTOR / math.cos(cam.pitch)
    dz = dist / MAX_DEPTH_FACTOR
    z = 1.0
    
    while z <= dist:
        # Compute left and right world positions
        # Left vector: rotate dir by -45 degrees
        left_rot_x = math.cos(-FOV_HALF_ANGLE) * dir_x - math.sin(-FOV_HALF_ANGLE) * dir_y
        left_rot_y = math.sin(-FOV_HALF_ANGLE) * dir_x + math.cos(-FOV_HALF_ANGLE) * dir_y
        
        # Right vector: rotate dir by +45 degrees
        right_rot_x = math.cos(FOV_HALF_ANGLE) * dir_x - math.sin(FOV_HALF_ANGLE) * dir_y
        right_rot_y = math.sin(FOV_HALF_ANGLE) * dir_x + math.cos(FOV_HALF_ANGLE) * dir_y
        
        # World positions (assuming unit distance for direction vectors, scaled by depth implicitly in projection)
        # Note: The source code calculates lp and rp based on camera pos and direction vectors
        lp_x = cam.pos.x + left_rot_x * z  # Approximation based on source logic
        lp_y = cam.pos.y + left_rot_y * z
        
        rp_x = cam.pos.x + right_rot_x * z
        rp_y = cam.pos.y + right_rot_y * z
        
        # Per-column step
        dx = (rp_x - lp_x) / W
        dy = (rp_y - lp_y) / W
        
        current_lp_x = lp_x
        current_lp_y = lp_y
        
        for i in range(W):
            # Sample heightmap
            # Wrap coordinates using width for both axes
            map_x = int(current_lp_x) % height_map.w
            map_y = int(current_lp_y) % height_map.w
            
            # Get height value (0-255)
            # Assuming image_at returns SDL_Color with r,g,b,a
            h_color = image_at(height_map, map_x, map_y)
            H_map = h_color.r
            
            # Calculate screen Y
            # Formula from source: height = (H_cam + (255 - H_map) - z * sin(pitch)) / z
            # Then scaled: Y = (height + 0.5) * 800
            # Note: Source code does: height -= z * sin(pitch); height /= z;
            # And initial height calculation involves H_cam and H_map.
            # Reconstructing from source logic:
            
            # Base height calculation from source context:
            # height = H_cam + (255 - H_map)
            # Then: height -= z * sin(pitch)
            # Then: height /= z
            # Then: Y = (height + 0.5) * 800
            
            # However, the source formula snippet says:
            # Y = (H_cam + (255 - H_map) - z * tan(pitch)) / z * 800 + 400
            # But code uses sin(pitch) and different scaling.
            # We follow the code steps strictly:
            
            temp_height = cam.height + (255 - H_map)
            temp_height -= z * math.sin(cam.pitch)
            temp_height /= z
            Y_screen = (temp_height + 0.5) * 800.0
            
            # Occlusion check
            if Y_screen < ybuf[i]:
                bottom = ybuf[i]
                ybuf[i] = Y_screen
                
                # Sample color
                c_map_x = int(current_lp_x) % color_map.w
                c_map_y = int(current_lp_y) % color_map.w
                col = image_at(color_map, c_map_x, c_map_y)
                
                # Draw line
                draw_line(render_target, i, Y_screen, i, bottom, col)
            
            # Advance
            current_lp_x += dx
            current_lp_y += dy
            
        dz += 0.01
        z += dz
        
    # Final presentation
    center = (550, 550)
    dst_rect = (-300, -300, 1400, 1400)
    copy_and_rotate(render_target, prog.rend, dst_rect, center, cam.tilt)
```

**Edge Cases and Pitfalls:**
-   **Heightmap Wrapping:** The implementation uses `img->w` for both X and Y modulo operations when sampling the heightmap. If the image height differs from the width, Y sampling will be incorrect [S1, unofficial].
-   **Subterranean Viewing:** Camera height is clamped to prevent viewing from below the terrain. If the camera height drops below `terrain_height - 10`, it is set to `-(terrain_height - 10)` [S1, unofficial].
-   **Precision:** Floating point precision in depth calculations and coordinate transformations may cause artifacts at extreme pitches or distances.

## Operating characteristics
-   **Time Complexity:** $O(W \times D / \bar{z})$, where $W=1400$ is screen width, $D$ is max depth, and $\bar{z}$ is average depth step [S1, unofficial]. The depth step $dz$ increases linearly, so the number of depth iterations is proportional to $D^2$.
-   **Memory Complexity:** $O(W)$ for `ybuf` plus image storage [S1, unofficial].
-   **Strengths:** Simple implementation, efficient occlusion handling via vertical buffer, suitable for real-time 2D terrain visualization [S1, unofficial].
-   **Limitations:** Fixed resolution internal buffer (1400x1400), potential Y-sampling errors if heightmap is not square, limited perspective accuracy due to pitch approximation [S1, unofficial].
-   **When to Use:** Real-time 2D terrain visualization where simplicity and speed are prioritized over geometric precision [S1, unofficial].
-   **When Not to Use:** 3D terrain rendering, high-precision scientific visualization, or scenes with significant vertical complexity requiring accurate perspective projection.

## Background
Vertical Buffer Terrain Rendering was developed as part of the `voxel-space` project by longwatermelon [S1, unofficial]. It is used for real-time 2D terrain visualization with SDL2 [S1, unofficial]. The technique is a specific implementation of heightmap projection, adapted for software rendering constraints.
