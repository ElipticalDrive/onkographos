# Vertical Buffer Terrain Rendering

Also called: 2D Heightmap Projection, Comanche-style renderer, Heightmap Renderer, Heightmap Scanline Rasterization, VoxelSpace heightmap rasterizer

## Overview
Vertical Buffer Terrain Rendering is a software rasterization technique that projects a 2D heightmap onto a screen by iterating through depth planes and drawing horizontal terrain slices from near to far [S1, S2, unofficial]. It solves the hidden surface problem for terrain by maintaining a per-column vertical occlusion buffer (`ybuf`), ensuring that only the closest visible terrain segment is drawn in each screen column [S1, S2, unofficial]. Unlike standard ray marching, it avoids per-pixel ray casting by using screen-space coordinate stepping and bitwise heightmap indexing, making it highly efficient for fixed-resolution 2D visualizations [S1, S2, unofficial].

## How it works
### Inputs and Outputs
- **Inputs**:
  - Heightmap image: 2D grid of altitude values (typically 8-bit grayscale, square, power-of-two dimensions) [S1, S2, unofficial].
  - Color map image: 2D grid of diffuse colors, matching heightmap dimensions [S1, S2, unofficial].
  - Camera state: position $(pos_x, pos_y)$, height $H_{cam}$, viewing angle $\theta$, pitch $\phi$, and tilt $\tau$ [S1, S2, unofficial].
  - Screen dimensions: Width $W=1400$ pixels, Height $H=1400$ pixels (internal render target) [S1, unofficial].
- **Outputs**:
  - Rendered terrain image displayed on screen, optionally rotated by tilt $\tau$ [S1, unofficial].

### Data Structures
1. **Vertical Buffer (`ybuf`)**:
   - Array of integers, size $W=1400$.
   - Stores the lowest drawn Y-coordinate for each screen column.
   - Initialized to $1400$ (screen bottom) [S1, unofficial].
2. **Camera Structure**:
   - `pos`: 2D vector $(pos_x, pos_y)$ [S1, unofficial].
   - `height`: float $H_{cam}$ [S1, unofficial].
   - `angle`: float $\theta$ [S1, unofficial].
   - `pitch`: float $\phi$ [S1, unofficial].
   - `tilt`: float $\tau$ [S1, unofficial].
3. **Image Structure**:
   - `w`, `h`: integer width and height [S1, unofficial].
   - `rows`: array of byte pointers, each pointing to a row of pixel data (RGBA) [S1, unofficial].
   - Note: Heightmap and color map must be square and power-of-two in width [S2, unofficial].

### Algorithm Steps
1. **Initialization**:
   - Allocate `ybuf` of size 1400, fill with 1400 [S1, unofficial].
   - Create a 1400×1400 render target texture, clear to black [S1, unofficial].
   - Compute projection constants:
     - $scale = \frac{maxhorizon}{2.5}$ [S2, unofficial].
     - $sinang = \sin(\theta)$, $cosang = \cos(\theta)$ [S1, S2, unofficial].
     - $dist = \frac{600.0}{\cos(\phi)}$ [S1, unofficial].
     - $dz = \frac{dist}{600.0}$ [S1, unofficial].
   - Precompute `shift` = $\lfloor \log_2(W_{map}) \rfloor$ for bitwise wrapping [S2, unofficial].

2. **Depth Loop**:
   - Iterate depth $z$ from $1.0$ to $dist$ with step $dz$.
   - **Adaptive Stepping**: If optimization is enabled and $z > optdist$, increase $dz$ by $cam.zstep \times (z / 2.0)$ to reduce fill rate at distance [S2, unofficial].
   - Increment $dz$ by $0.01$ each iteration [S1, unofficial].

3. **Screen-Space Coordinate Setup**:
   - Compute camera direction vector $\vec{dir} = (\cos(\theta), \sin(\theta))$ [S1, unofficial].
   - Compute left and right world-space points at current $z$ (±45° from camera direction):
     - $p_{left} = (-cosang \cdot z - sinang \cdot z, \ sinang \cdot z - cosang \cdot z)$ [S2, unofficial].
     - $p_{right} = (cosang \cdot z - sinang \cdot z, \ -sinang \cdot z - cosang \cdot z)$ [S2, unofficial].
   - Calculate screen-space delta per pixel:
     - $pDelta.x = \frac{p_{right}.x - p_{left}.x}{pitch}$ [S2, unofficial].
     - $pDelta.y = \frac{p_{right}.y - p_{left}.y}{pitch}$ [S2, unofficial].
   - Offset $p_{left}$ by $pDelta \times start$ and add camera position to align with column range [S2, unofficial].

4. **Column Loop**:
   - Loop screen column $i$ from $0$ to $1399$.
   - **Heightmap Indexing**:
     - Compute offset using bitwise wrapping:
       - $offset = ((\lfloor p_{left}.y \rfloor \ \& \ (W_{map}-1)) \ll shift) + (\lfloor p_{left}.x \rfloor \ \& \ (H_{map}-1))$ [S2, unofficial].
     - Note: This assumes square power-of-two maps. Using $W_{map}$ for Y modulo causes errors if height $\neq$ width [S1, unofficial].
   - **Screen Y Calculation**:
     - Get altitude $H_{map} = altitude[offset]$ [S1, S2, unofficial].
     - Apply pitch offset and normalization:
       - $height = \frac{H_{cam} + (255 - H_{map}) - z \sin(\phi)}{z}$ [S1, S2, unofficial].
       - Note: Source [S1, unofficial] formula uses $\tan(\phi)$ but code uses $\sin(\phi)$ [S1, unofficial].
     - Scale to screen Y:
       - $Y = (height + 0.5) \times 800.0$ [S1, unofficial].
       - Alternative formulation [S2, unofficial]: $top = \frac{H_{cam} - H_{map}}{z} \times scale + horizon$.
   - **Clipping**:
     - If $top < 0$, clamp to $0$ [S2, unofficial].
     - If $top > bottom$ (where $bottom$ is current `ybuf[i]`), skip drawing [S2, unofficial].
   - **Drawing**:
     - If $Y < ybuf[i]$:
       - Set $bottom = ybuf[i]$ [S1, unofficial].
       - Update $ybuf[i] = Y$ [S1, unofficial].
       - Sample color from color map at $p_{left}$ coordinates [S1, unofficial].
       - Draw vertical line from $(i, Y)$ to $(i, bottom)$ using sampled color [S1, unofficial].
   - **Advance**:
     - $p_{left}.x += dx$, $p_{left}.y += dy$, where $dx = \frac{p_{right}.x - p_{left}.x}{1400}$, $dy = \frac{p_{right}.y - p_{left}.y}{1400}$ [S1, unofficial].
     - Advance $p_{left}$ by $pDelta$ for next column [S2, unofficial].

5. **Final Output**:
   - Copy render target to screen with tilt rotation around center $(550, 550)$ and offset $(-300, -300)$ [S1, unofficial].

### Pseudocode
```python
def render_terrain(heightmap, colormap, camera, screen_width=1400, screen_height=1400):
    # Initialize vertical buffer
    ybuf = [screen_height] * screen_width
    
    # Projection constants
    maxhorizon = camera.maxhorizon
    scale = maxhorizon / 2.5
    sinang = sin(camera.angle)
    cosang = cos(camera.angle)
    dist = 600.0 / cos(camera.pitch)
    dz = dist / 600.0
    
    # Precompute shift for bitwise wrapping (assuming power-of-two width)
    shift = floor(log2(heightmap.width))
    width_mask = heightmap.width - 1
    
    # Depth loop
    z = 1.0
    while z < dist:
        # Adaptive stepping
        if z > optdist:
            dz += camera.zstep * (z / 2.0)
        
        # Compute left and right points at current depth
        p_left_x = -cosang * z - sinang * z
        p_left_y = sinang * z - cosang * z
        p_right_x = cosang * z - sinang * z
        p_right_y = -sinang * z - cosang * z
        
        # Screen-space deltas
        p_delta_x = (p_right_x - p_left_x) / screen_width
        p_delta_y = (p_right_y - p_left_y) / screen_width
        
        # Column loop
        for i in range(screen_width):
            # Bitwise wrapping for heightmap index
            offset = ((int(p_left_y) & width_mask) << shift) + (int(p_left_x) & width_mask)
            
            # Get altitude
            h_map = heightmap.get_value(offset)
            
            # Calculate screen Y
            # Note: Source uses sin(pitch) in code, tan(pitch) in formula description
            height_val = (camera.height + (255 - h_map) - z * sin(camera.pitch)) / z
            y_screen = (height_val + 0.5) * 800.0
            
            # Clipping
            if y_screen < 0:
                y_screen = 0
            
            if y_screen < ybuf[i]:
                bottom = ybuf[i]
                ybuf[i] = y_screen
                
                # Sample color
                color = colormap.get_color(p_left_x, p_left_y)
                
                # Draw vertical line
                draw_line(i, y_screen, i, bottom, color)
            
            # Advance left point
            p_left_x += (p_right_x - p_left_x) / screen_width
            p_left_y += (p_right_y - p_left_y) / screen_width
        
        z += dz
        dz += 0.01  # Increment step size
    
    # Final tilt rotation and display
    render_target_to_screen(tilt=camera.tilt, center=(550, 550), offset=(-300, -300))
```

### Parameters
- `ybuf[1400]`: Vertical occlusion buffer, initialized to 1400 [S1, unofficial].
- `dist = 600.0 / cos(pitch)`: Maximum render distance [S1, unofficial].
- `shift`: Precomputed $\log_2(width)$ for fast indexing [S2, unofficial].
- `pitch`: Camera pitch angle, affects max distance and projection [S1, unofficial].
- `maxhorizon`: Camera's maximum horizon distance [S2, unofficial].
- `horizon`: Vertical screen offset of the horizon line [S2, unofficial].

### Edge Cases and Pitfalls
- **Heightmap Dimensions**: Must be square and power-of-two. Non-power-of-two widths trigger `ERROR_MAPLOAD_WIDTHINVALID` [S2, unofficial]. Mismatched diffuse/height dimensions trigger `ERROR_MAPLOAD_MAPSMISMATCH` [S2, unofficial].
- **Y-Coordinate Wrapping**: Using image width for both X and Y modulo causes incorrect Y sampling if height $\neq$ width [S1, unofficial].
- **Camera Height**: Clamped to terrain height to prevent subterranean viewing: `if (-cam.height > height - 10) cam.height = -(height - 10)` [S1, unofficial].
- **Vertical Line Clipping**: Top < 0 is clamped to 0; top > bottom skips drawing to prevent out-of-bounds writes [S2, unofficial].

## Operating characteristics
- **Time Complexity**: $O(W \times D / \bar{z})$, where $W=1400$ is screen width, $D$ is max depth, and $\bar{z}$ is average depth step [S1, unofficial].
- **Memory Complexity**: $O(W)$ for `ybuf` plus image storage [S1, unofficial].
- **Performance**: Efficient for real-time 2D terrain visualization due to fixed-resolution screen-space stepping and bitwise indexing [S1, unofficial]. Adaptive depth stepping reduces fill rate at distance [S2, unofficial].
- **Strengths**: Simple implementation, low memory footprint, fast rendering for 2D heightmaps [S1, S2, unofficial].
- **Limitations**: Limited to 2D heightmaps, requires square power-of-two maps, occlusion handling is column-based (no sub-pixel accuracy) [S1, S2, unofficial].
- **When to Use**: Real-time 2D terrain visualization, retro-style graphics, constrained hardware [S1, unofficial].
- **When Not to Use**: 3D terrain with complex geometry, non-square maps, high-precision occlusion requirements [S1, S2, unofficial].
