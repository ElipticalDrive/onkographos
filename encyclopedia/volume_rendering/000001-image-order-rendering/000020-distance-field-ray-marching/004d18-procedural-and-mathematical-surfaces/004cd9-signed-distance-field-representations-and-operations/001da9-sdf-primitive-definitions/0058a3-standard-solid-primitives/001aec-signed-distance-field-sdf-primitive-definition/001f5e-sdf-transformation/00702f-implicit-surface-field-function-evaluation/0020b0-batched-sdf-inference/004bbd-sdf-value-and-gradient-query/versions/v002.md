# SDF Value and Gradient Query

Also called: Live Cursor Measurement Caliper, ObjectFrameSDF query, Step Ruler Caliper, measureSdfRayCaliper

## Overview
This method provides real-time inspection of Signed Distance Field (SDF) properties at specific 3D coordinates, typically under a user cursor or for a batch of query points. It outputs the signed distance value, the analytical gradient (normal), and hit classification (e.g., surface, sky, abyss) [S1, S2, unofficial]. It distinguishes itself from [SDF Value Computation](6443-sdf-value-computation.md) by explicitly exposing the gradient for normal verification and from [Batched SDF Inference](2329-batched-sdf-inference.md) by focusing on interactive, single-point or small-batch debug inspection rather than large-scale memory-managed inference [S1, S2, unofficial].

## How it works
**Inputs:**
1.  A set of query points $\mathbf{P} = \{\mathbf{p}_1, \dots, \mathbf{p}_N\}$ in 3D space (World Frame or Object Frame) [S1, S2, unofficial].
2.  A boolean flag `compute_grad` indicating whether to calculate the gradient [S2, unofficial].

**Outputs:**
1.  Signed distance values $d(\mathbf{p})$ for each point [S1, S2, unofficial].
2.  Gradient vectors $\nabla d(\mathbf{p})$ (normals) if `compute_grad` is True [S1, S2, unofficial].
3.  Hit classification (e.g., COURSE SURFACE, GLASS MARBLE, ABYSS, SKY RAY) [S1, unofficial].
4.  Debug metrics: Raymarch step counts (optimized vs. legacy) and CSG latency [S1, unofficial].

**Data Structures:**
*   **Query Points:** Array of shape $(N, 3)$ or $(B, N, 3)$ for batched inputs [S2, unofficial].
*   **SDF Values:** Array of shape $(N)$ or $(B, N)$ [S2, unofficial].
*   **SDF Gradients:** Array of shape $(N, 3)$ or $(B, N, 3)$ [S2, unofficial].

**Steps:**
1.  **Point Acquisition:** Determine the 3D world point $\mathbf{p}$ under the cursor or generate points using a grid resolution and query range [S1, S2, unofficial].
2.  **SDF Evaluation:** Query the SDF primitive or scene for the distance $d(\mathbf{p})$ [S1, S2, unofficial].
    *   *Note:* A +1m Free-Space Probe offset may be applied to the distance value for debugging purposes [S1, unofficial].
3.  **Gradient Computation (Optional):**
    *   If `compute_grad` is True, compute the analytical normal $\nabla d(\mathbf{p})$ [S1, unofficial].
    *   For mesh-based SDFs (ObjectFrameSDF), the gradient is derived from the vector pointing from the query point to the closest point on the mesh surface, normalized [S2, unofficial].
    *   Verify that $\|\nabla d(\mathbf{p})\| = 1.000$ [S1, unofficial].
4.  **Hit Classification:** Classify the point based on $d(\mathbf{p})$ and raymarch results (e.g., if the ray hits a surface, it is a surface hit; otherwise, it is sky or abyss) [S1, unofficial].
5.  **Step Optimization Analysis:** Compare the number of steps taken by an optimized raymarcher (using bounds and $\kappa$-March) against a legacy raymarcher to calculate the percentage reduction in steps [S1, unofficial].
6.  **CSG Latency Measurement:** Measure the time taken for Constructive Solid Geometry operations, if applicable [S1, unofficial].

*   **Precision:** Ensure $\|\nabla d(\mathbf{p})\| = 1.000$ for analytical normals [S1, unofficial].

## Subtopics

### [Cached SDF](13075-cached-sdf.md)
Accelerates SDF queries by storing values in a voxel grid, falling back to a ground truth SDF for points outside the cache [13075-cached-sdf.md].

### SDF Snapping
Queries the VoxelGenerator at floating-point positions to approximate the surface using SDF values, snapping instances closer to the surface [S3].
*   **Definition:** Uses at least 2 nearby SDF samples to interpolate the surface distance [S3].
*   **Formula:** $P_{snapped} = P_{mesh} + \text{interpolation}(SDF(P_{mesh}), \text{samples})$ [S3].
*   **Pitfalls:**
    *   **Terrain Modification:** Snapping fails if the terrain is modified after initial generation, as generator estimations won't account for edited areas. Workaround: Set instances as persistent to save positions and avoid regeneration [S3].
    *   **Far Distance Artifacts:** Snapping can cause instances to 'bury' or 'float' far away when low-resolution meshes are active, as they are moved closer to the high-resolution surface estimate [S3].
*   **Comparison:** Snapping improves positioning significantly but is slower. No snapping is faster but less precise. Snapping is preferably used when `lod_index > 0`, as LOD0 already has maximum precision [S3].

## Operating characteristics
*   **Time Complexity:** $O(N)$ for $N$ query points, assuming constant-time SDF evaluation [S1, S2, unofficial].
*   **Memory Complexity:** $O(N)$ to store query results [S2, unofficial].
*   **Performance:** Real-time inspection is feasible with optimized raymarching (e.g., $\kappa$-March) [S1, unofficial]. CSG latency is reported as low as 0.0018 ms for simple cases [S1, unofficial].
*   **Strengths:** Provides exact analytical normals and hit classification, useful for debugging and interactive tools [S1, unofficial].
*   **Limitations:** Gradient computation can be expensive if not optimized [S2, unofficial]. Snapping variants are slower than non-snapping [S3].

## Background
The method originates from interactive SDF debugging tools, specifically the "Live Cursor Measurement Caliper" and "Step Ruler" implemented in the `sdf-wizard` feature [S1, unofficial]. It is also used in volumetric structure libraries like `pytorch_volumetric` for querying ObjectFrameSDFs [S2, unofficial]. The concept of SDF snapping for instancing is documented in Voxel Tools for terrain generation [S3].
