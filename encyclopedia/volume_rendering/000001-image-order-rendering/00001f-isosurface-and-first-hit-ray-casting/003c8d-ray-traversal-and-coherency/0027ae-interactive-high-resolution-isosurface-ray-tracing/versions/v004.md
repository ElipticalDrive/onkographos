# Interactive High Resolution Isosurface Ray Tracing

Also called: BONO-based ray tracing, Two-phase isosurface ray tracing

## Overview
Interactive High Resolution Isosurface Ray Tracing is a two-phase algorithm for rendering isosurfaces in volumetric data on multi-core processors [S1, unofficial]. It solves the performance bottleneck of high-resolution ray casting by decoupling the search for the isosurface into a coarse, projection-based culling phase and a fine, ray-intersection phase [S1, unofficial]. Unlike standard packet ray casting which relies on SIMD instructions for parallelism, this method uses high-level algorithmic techniques—specifically, maintaining a short, front-to-back ordered list of candidate blocks per pixel—to achieve coherence and efficiency without instruction-level parallelism dependencies [S1, unofficial]. It builds on [Ray Traversal and Coherency](9272-ray-traversal-and-coherency.md) by using a BONO tree for hierarchical culling and list-based restriction to limit the search space [S1, unofficial].

## How it works
The method operates in two distinct phases [S1, unofficial]. Phase I traverses a coarse BONO tree to build a short, front-to-back ordered list of visible, isosurface-intersecting data blocks for each pixel (or packet) [S1, unofficial]. Phase II shoots rays through these lists to find the first isosurface intersection, performing trilinear interpolation and shading [S1, unofficial].

### Inputs and Outputs
**Inputs:**
*   Volumetric scalar field data $f(\mathbf{p})$ [S1, unofficial].
*   Isovalue $\tau$ [S1, unofficial].
*   Camera parameters (viewpoint, projection matrix) [S1, unofficial].
*   Maximum list size $k$ (typically $k \le 20$) [S1, unofficial].
*   Adaptive block size configuration (e.g., $8\times8\times8$ for far views, $4\times4\times4$ for close views) [S1, unofficial].

**Outputs:**
*   For each pixel, the 3D intersection point $\mathbf{p}$ on the isosurface and its normal $\mathbf{n}$, used for shading [S1, unofficial].

### Data Structures
**Block Organization:**
The volumetric data is organized into a coarse grid of equal-sized blocks [S1, unofficial]. Scalar field values within each block are stored contiguously [S1, unofficial]. Each block is identified by the coordinates of a pre-specified corner [S1, unofficial]. The data within a block is indexed by an octree where leaves correspond to $2\times2\times2$ cells, containing a pointer to such a cell [S1, unofficial]. Each octree node stores the minimum and maximum scalar values of voxels in its region [S1, unofficial].

**BONO Tree:**
A BONO (Branch-On-Need Octree) tree indexes the coarse grid of blocks [S1, unofficial]. It is augmented with value ranges (min/max) at each node [S1, unofficial]. Unlike a standard octree, BONO avoids allocating nodes for empty subtrees when data resolution is not a power of two, making it more space-efficient [S1, unofficial].

**Pixel Lists:**
For each pixel (or packet), a list of pointers to data blocks is maintained [S1, unofficial]. The list is organized in front-to-back order relative to the viewpoint [S1, unofficial]. The list size is capped at $k$. Each list also stores a "resume point" indicating where the BONO tree traversal stopped if the list reached size $k$ [S1, unofficial].

### Algorithm Steps

**Phase I: List Generation**
1.  Traverse the BONO tree starting from the root [S1, unofficial].
2.  For a node $v$, check if its stored value range $[min_v, max_v]$ contains the isovalue $\tau$ (i.e., $min_v \le \tau \le max_v$) [S1, unofficial].
3.  If the range contains $\tau$, project the minimum axis-aligned bounding box (AABB) of node $v$ onto the screen [S1, unofficial]. The 3D AABB is computed from the coordinates of a pre-specified corner and the level of $v$ [S1, unofficial].
4.  Identify all pixels falling within the projected area of node $v$ [S1, unofficial].
5.  For each such pixel:
    *   If the size of the pixel's block list is less than $k$, traverse $v$'s children in front-to-back order relative to the viewpoint [S1, unofficial].
    *   Otherwise, skip the subtree rooted at $v$ [S1, unofficial].
6.  When a leaf is reached, augment the list of each pixel falling within the projection of the leaf's block with a pointer to this block, unless the list already has $k$ blocks [S1, unofficial]. The lists remain in front-to-back order due to the traversal order [S1, unofficial].
7.  **Adaptive Block Size (Close Views):** For close views, after traversing the BONO tree, continue traversing the octree of the BONO leaves until the desired block size is reached [S1, unofficial]. Then compute the minimum bounding box and construct lists for the resulting blocks [S1, unofficial].

**Phase II: Ray Casting and Shading**
1.  For each pixel with a non-empty list, shoot a ray from the pixel through the list of blocks in order [S1, unofficial].
2.  If the list is empty, the ray does not intersect the isosurface [S1, unofficial].
3.  For each block in the list:
    *   Compute the ray-voxel intersection using the method from [10] (not detailed in sources) [S1, unofficial].
    *   If the ray intersects a voxel on the isosurface within the block:
        *   Perform trilinear interpolation using the unit cell containing the voxel to refine the intersection point.
        *   Compute the normal using forward difference.
        *   Apply diffuse shading.
        *   Stop further processing for this ray [S1, unofficial].
4.  If the ray reaches the end of the list without finding an intersection:
    *   If the list size is $k$, resume the traversal of the BONO tree from the resume point indicated at the end of the list. Continue searching for intersections in the remaining subtrees [S1, unofficial].
    *   If the list size is less than $k$, the ray does not intersect the isosurface [S1, unofficial].

def interactive_isosurface_ray_tracing(data, isovalue, camera, k, block_size_config):
    """
    Main entry point for the two-phase isosurface ray tracing algorithm.
    """
    bono_tree = _build_bono_tree(data, block_size_config)
    num_pixels = camera.resolution[0] * camera.resolution[1]
    pixel_lists = [[] for _ in range(num_pixels)]
    resume_points = [None for _ in range(num_pixels)]
    
    _traverse_bono_for_lists(bono_tree.root, camera, isovalue, k, pixel_lists, resume_points)
    
    image = [[None for _ in range(camera.resolution[0])] for _ in range(camera.resolution[1])]
    
    for y in range(camera.resolution[1]):
        for x in range(camera.resolution[0]):
            pixel_idx = y * camera.resolution[0] + x
            ray = camera.get_ray(x, y)
            block_list = pixel_lists[pixel_idx]
            
            if not block_list:
                continue
                
            intersection_found = False
            for block in block_list:
                if _ray_intersects_block(ray, block):
                    voxel_intersection = _ray_voxel_intersection(ray, block, isovalue)
                    if voxel_intersection is not None:
                        point = _trilinear_interpolate(voxel_intersection, block)
                        normal = _compute_normal_forward_diff(point, block)
                        color = _diffuse_shading(point, normal, data)
                        image[y][x] = (color, point, normal)
                        intersection_found = True
                        break
            
            if not intersection_found and len(block_list) == k:
                resume_node = resume_points[pixel_idx]
                if resume_node is not None:
                    _continue_traversal_and_cast(ray, resume_node, isovalue, image, pixel_idx, camera)
    return image

def _traverse_bono_for_lists(node, camera, isovalue, k, pixel_lists, resume_points):

        return
    projected_area = _project_aabb_to_screen(node.aabb, camera)

### Parameters
*   **$k$**: The maximum size of the list of data blocks associated with each pixel. Typical value: $k \le 20$ gives the most efficient implementation. The algorithm remains correct for any $k$ [S1, unofficial].
*   **Block Size**: Adaptive based on view distance. For far views, large blocks (e.g., $8\times8\times8$) are used. For close views, smaller blocks (e.g., $4\times4\times4$) are used to reduce the number of BONO nodes visited and projected blocks [S1, unofficial].

### Edge Cases and Pitfalls
*   **Precision**: Ray-voxel intersection and trilinear interpolation require careful handling of floating-point precision to avoid gaps or overlaps in the isosurface [S1, unofficial].
*   **Boundaries**: The BONO tree structure handles non-power-of-two resolutions by avoiding empty subtree nodes, but care must be taken in computing the AABB for nodes near the data boundaries [S1, unofficial].
*   **List Fullness**: If a pixel's list reaches size $k$ before the isosurface is found, the algorithm must correctly resume traversal. Failure to store and use the resume point correctly will result in missed intersections [S1, unofficial].

## Operating characteristics
*   **Time Complexity**: Phase I is efficient due to the compact BONO tree and projection-based culling. Phase II is efficient due to the limited number of blocks per ray [S1, unofficial].
*   **Memory Complexity**: The BONO tree is more space-efficient than a standard octree for non-power-of-two resolutions. Pixel lists are small ($k \le 20$), keeping memory overhead low [S1, unofficial].
*   **Measured Performance**: On a Clovertown platform (two Quad-Core Intel Xeon Processors 5320, 1.86 GHz, 8MB L2 cache per dual-core, 8GB main memory) with a 1024x1024 screen:
    *   Far view, $k=3$ (single pixel lists): List generation time is 273 msec [S1, unofficial].
    *   Far view, $k=6$ (2x2 pixel packets): List generation time is 110 msec (2.48x speedup) [S1, unofficial].
    *   Close view, $k=3$ (single pixel lists): List generation time is 228 msec [S1, unofficial].
    *   Close view, $k=6$ (2x2 pixel packets): List generation time is 68 msec (3.35x speedup) [S1, unofficial].
*   **Strengths**: High performance on multi-core processors due to efficient memory hierarchy usage and algorithmic coherence. Adaptive block size optimizes for different view distances [S1, unofficial].
*   **Limitations**: The method avoids performance drops on highly incoherent scenes by not relying on SIMD instructions, but may trade off peak performance on highly coherent scenes where SIMD-based packet ray casting could be more effective [S1, unofficial].
*   **When to Use**: Interactive rendering of high-resolution volumetric data on multi-core CPUs where coherence can be exploited [S1, unofficial].
*   **When Not to Use**: Hardware without multi-core capabilities, or scenarios where SIMD-based packet ray casting is preferred for highly coherent scenes [S1, unofficial].

## Background
The method was introduced in a paper by researchers at the University of Maryland (UMD) [S1, unofficial]. It was designed to leverage multi-core processor architectures and their memory hierarchies for efficient isosurface rendering. The BONO (Branch-On-Need Octree) structure is a key component, providing a compact indexing structure for the volumetric data [S1, unofficial]. The approach differs from standard packet ray casting by avoiding SIMD instructions, instead relying on list merging and projection-based culling to handle coherence [S1, unofficial].
