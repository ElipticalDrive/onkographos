# Upson-Keller Polygon Method

Also called: Early hardware work, Rasterization Isosurfacing (Alpha-Test/Stencil), Scan plane intersection method

## Overview
The Upson-Keller Polygon Method is an early image-order volume rendering technique that rasterizes intersection polygons derived from volume elements to extract isosurfaces, leveraging fixed-function graphics hardware features such as alpha testing and stencil buffers [S2, unofficial]. It distinguishes itself from sibling methods by avoiding explicit mesh generation or programmable shaders, instead relying on hardware-accelerated depth and stencil operations to resolve visibility and opacity through a two-pass process [S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A volume dataset defined by scalar values at grid nodes; an isovalue threshold; a predetermined front-to-back rendering order of volume elements [S1, unofficial][S2, unofficial].
*   **Output:** A 2D image with opacity and color information for the isosurface [S1, unofficial].

**Data Structures:**
*   **Stencil Buffer:** Tracks the parity of front/back face intersections to mark entry and exit regions [S2, unofficial].
*   **Alpha Component:** Stores the interpolated scalar value of each fragment for alpha testing [S2, unofficial].
*   **Scan Planes:** Virtual planes parallel to the image plane (the z-extension of scan lines) used to intersect volume elements [S1, unofficial].

**Steps:**
1.  **Intersection:** For each volume element in the predetermined front-to-back order, intersect the scan planes with the volume element to form intersection polygons [S1, unofficial].
2.  **Span Generation:** Break the resulting intersection polygons into spans [S1, unofficial].
3.  **Rasterization (Pass 1 - Stencil Setup):** Draw the back and front faces of the volume element in order. Configure the graphics hardware to store the interpolated scalar value in the alpha component of the fragment. Apply an alpha test to reject fragments where the scalar value is less than the desired isovalue [S2, unofficial].
4.  **Stencil Operation:** Use a XOR operation on the stencil buffer to combine the results of the back and front face draws [S2, unofficial].
5.  **Integration:** Integrate the pixels of each span front-to-back to generate opacity [S1, unofficial].

**Formulas:**
*   Alpha test condition: $\alpha_{\text{frag}} \geq \text{isovalue}$ [S2, unofficial].
*   Stencil update: $S_{\text{new}} = S_{\text{old}} \oplus 1$ [G].

**Parameters:**
*   **Isovalue:** The scalar threshold for surface extraction [S2, unofficial].
*   **Rendering Order:** Front-to-back order of volume elements to ensure correct visibility calculation [S1, unofficial].
*   **Average Triangles:** The algorithm renders 5 to 7 triangles per volume element on average [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Degenerate Cases:** If the intersection polygon is degenerate (e.g., a line or point), span generation may produce empty spans or require decomposition into smaller tetrahedra [S2, unofficial].
*   **Precision:** Alpha testing relies on the precision of the interpolated scalar value in the alpha component [S2, unofficial].
*   **Hardware Limitations:** The method depends on specific fixed-function hardware features (alpha test, stencil buffer) that may not be available or performant on modern programmable pipelines [S2, unofficial].

## Subtopics

### Revised Version (Checkerboard Texture)
An alternate solution that decomposes tetrahedra into smaller tetrahedra, reducing the number of faces rendered. It uses 2D texturing hardware with a checkerboard texture to handle degenerate cases and simplify intersection computation [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** The algorithm runs in two passes (the first step sets the stencil buffer) and on average renders 5 to 7 triangles per volume element [S2, unofficial].
*   **Memory Complexity:** Requires a stencil buffer and alpha channel for each fragment [S2, unofficial].
*   **Strengths:** Efficient use of early fixed-function graphics hardware; avoids complex per-pixel gradient evaluation by computing lighting per-vertex or via pre-computed normal maps [S1, unofficial][S2, unofficial].
*   **Limitations:** Dependent on specific hardware features; limited flexibility compared to shader-based methods; potential precision issues with alpha testing [S2, unofficial].
*   **When to Use:** Early hardware environments where programmable shaders are unavailable [S2, unofficial].
*   **When Not to Use:** Modern hardware with programmable pipelines; scenes requiring high precision or complex lighting [S2, unofficial].

## Background
The method was introduced by Upson and Keller in 1988 [S1, unofficial]. It was one of the early attempts to leverage graphics hardware for volume rendering, specifically targeting the extraction of isosurfaces using rasterization primitives [S2, unofficial]. A revised version was discussed in [58], and the method is frequently cited in surveys of GPU-based volume rendering of unstructured grids [S2, unofficial].
