# Parallax Occlusion Mapping

Also called: Voxel Displacement Renderer

## Overview
Parallax Occlusion Mapping (POM) is a technique used to reveal Signed Distance Field (SDF) iso-surfaces within rasterized brick bounding boxes, providing depth detail without the computational cost of full raymarching [S1, unofficial]. In the context of the Voxel Displacement Renderer, it is a real-time rendering method that applies voxel-scale surface details to conventional low-poly triangle meshes using displacement maps, producing a retro 3D aesthetic without converting the entire scene into a voxel grid [S2, unofficial]. Unlike conventional displacement mapping, which struggles with hard edges and requires high polygon counts, this method produces voxel-like results even along sharp edges of the original mesh [S2, unofficial]. It differs from standard POM by physically changing the silhouette and geometry, thereby avoiding the illusion breakdown at object edges that plagues texture-based parallax techniques [S2, unofficial].

## How it works
The method operates in two distinct phases: a CPU-based pre-processing stage and a GPU-based rendering stage.

### Inputs and Outputs
**Inputs:**
*   Conventional low-poly triangle meshes with shading normals [S2, unofficial].
*   Albedo maps and displacement maps (height fields) [S2, unofficial].
*   SDF brick data (in the SDF context) [S1, unofficial].

**Outputs:**
*   Rasterized geometry with voxel-scale displacement [S2, unofficial].
*   Anti-aliased SDF iso-surface representation [S1, unofficial].

### Data Structures
1.  **Displacement Map:** A texture where rescaled height values represent the number of voxels inward or outward to move the surface [S2, unofficial].
2.  **Normal Map:** Generated from the exact (non-quantized) height values of the displacement map to allow features less than a voxel tall to affect lighting [S2, unofficial].
3.  **Geometry Data:** Pre-processed mesh data loaded onto the GPU, including information about sharp edges and smooth surfaces derived from shading normals [S2, unofficial].
4.  **Bounding Boxes:** For SDF bricks, bounding boxes are adjusted to maintain a constant screen-space size [S1, unofficial].

### Steps
1.  **Pre-processing (CPU):**
    *   Convert triangle meshes and displacement map information into geometry data for the GPU [S2, unofficial]. This can be baked to disk [S2, unofficial].
    *   Generate normal maps from the displacement textures. This process is slow and should be baked [S2, unofficial].
    *   Identify sharp edges and smooth regions using the input mesh's shading normals [S2, unofficial].

2.  **Rendering (GPU):**
    *   **Rasterization:** Draw the voxel-displacement geometry using the pre-processed mesh and texture state [S2, unofficial]. For SDF bricks, rasterize the bounding boxes of the bricks [S1, unofficial].
    *   **Displacement Application:** Displace vertices to the nearest whole number of voxels based on the displacement map [S2, unofficial].
    *   **Lighting:** Use the pre-computed normal maps for shading. The renderer performs extra work for sharp edges to ensure correct lighting transitions [S2, unofficial].
    *   **SDF Context (Optional):** If used with SDF bricks, perform parallax occlusion mapping after rasterization to reveal the iso-surface within each brick [S1, unofficial].

### Parameters
*   **Bounding Box Dimensions:** Adjusted to maintain a constant screen-space size to ensure appropriate filtering of distance field data for anti-aliasing [S1, unofficial].
*   **Displacement Units:** The rescaled height values in the displacement map define the magnitude of displacement in voxel units [S2, unofficial].
*   **Mesh Normals:** Input meshes must include shading normals to distinguish between smoothly curving surfaces and sharp edges [S2, unofficial].

### Edge Cases and Pitfalls
*   **Sharp Edges:** The renderer must handle sharp edges differently from smooth surfaces to maintain visual fidelity [S2, unofficial].
*   **Precision:** While geometry is quantized to whole voxels, lighting relies on exact height values, requiring high-precision normal map generation [S2, unofficial].
*   **Performance:** Normal map generation is computationally expensive and must be pre-computed [S2, unofficial].

### Pseudocode
```python
# Pre-processing Phase (CPU)
def preprocess_mesh(mesh, displacement_map):
    """
    Converts mesh and displacement data into GPU-ready format.
    """
    # Generate normal map from exact displacement heights
    normal_map = generate_normal_map(displacement_map)
    
    # Identify sharp edges based on shading normals
    sharp_edges = detect_sharp_edges(mesh.shading_normals)
    
    # Create geometry data structure
    geometry_data = {
        'vertices': mesh.vertices,
        'indices': mesh.indices,
        'normal_map': normal_map,
        'sharp_edges': sharp_edges,
        'displacement_scale': 1.0 # Rescale factor for voxel units
    }
    return geometry_data

# Rendering Phase (GPU)
def render_voxel_displacement(geometry_data, albedo_map, camera_view):
    """
    Renders the displaced geometry.
    """
    # Rasterize the base mesh
    rasterized_pixels = rasterize(geometry_data.vertices, geometry_data.indices)
    
    for each pixel in rasterized_pixels:
        # Sample displacement height
        height = sample_displacement(geometry_data, pixel.uv)
        
        # Quantize to nearest whole voxel
        voxel_displacement = round(height * geometry_data.displacement_scale)
        
        # Displace vertex position
        displaced_position = pixel.position + voxel_displacement * normal
        
        # Sample normal map for lighting
        normal = sample_normal_map(geometry_data.normal_map, pixel.uv)
        
        # Handle sharp edges if necessary
        if geometry_data.sharp_edges.contains(pixel):
            normal = adjust_normal_for_sharp_edge(normal, geometry_data)
        
        # Compute lighting
        color = compute_phong_lighting(displaced_position, normal, albedo_map, camera_view)
        
        write_color(pixel, color)
```

## Subtopics

### SDF Brick Rendering
Uses POM to reveal SDF iso-surfaces within rasterized bricks, avoiding raymarching [S1, unofficial].

### Voxel Displacement Renderer
Applies voxel-scale details to low-poly meshes, handling sharp edges better than conventional displacement mapping [S2, unofficial].

## Operating characteristics
*   **Performance:** On a Radeon RX 5700 XT, the demo renders at 1440p with frame times of 4 to 9 ms (250 to 110 FPS) [S2, unofficial]. On a Steam Deck OLED at 800p, it stays above 60 FPS, with many areas locked at 90 FPS [S2, unofficial].
*   **Pre-processing Time:** Converting the entire demo scene on a single thread takes half a second [S2, unofficial].
*   **Strengths:** Produces voxel-like results with sharp edges; avoids illusion breakdown at object edges; real-time performance on modern hardware [S2, unofficial].
*   **Limitations:** Requires pre-processing (baking) of normal maps and geometry; displacement is quantized to whole voxels for geometry, though lighting uses exact heights [S2, unofficial].
*   **When to Use:** When a retro 3D voxel aesthetic is desired from low-poly assets, or when SDF bricks need efficient depth rendering without raymarching [S1, unofficial][S2, unofficial].
*   **When Not to Use:** When dynamic, per-frame normal map generation is required, or when sub-voxel geometric displacement is needed (only lighting benefits from sub-voxel precision) [S2, unofficial].

## Background
The technique was used in the game *Dreams* (Evans, 2015) for rendering SDF bricks [S1, unofficial]. A standalone implementation, the Voxel Displacement Renderer, was developed by Daniel Schroeder and documented in 2024 [S2, unofficial]. It is implemented as a C++/Vulkan project, with assets authored as albedo and displacement maps, and meshes exported as OBJ files from Blender [S2, unofficial].
