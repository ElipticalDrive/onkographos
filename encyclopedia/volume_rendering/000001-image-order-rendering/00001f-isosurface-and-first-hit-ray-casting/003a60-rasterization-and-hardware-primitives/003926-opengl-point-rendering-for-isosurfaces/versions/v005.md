# OpenGL Point Rendering for Isosurfaces

Also called: Hardware accelerated point rendering

## Overview
This method renders isosurfaces by projecting volume elements as point primitives (`GL_POINTS`) onto the screen, where points are rasterized as discs [S1, unofficial]. It is distinguished from sibling methods by its use of single-vertex primitives, which eliminates backface culling and causes overlap, making it prone to fill-rate limitations but offering lower geometry pipeline requirements [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A 3D volume dataset, an isovalue threshold, and camera parameters (projection matrix, viewport) [S1, unofficial].
- Output: A 2D image of the isosurface [S1, unofficial].

**Data Structures:**
- **Dirty Cell List:** A list of cells marked for regeneration [S1, unofficial]. The number of cells marked dirty per frame is selected so that primitives are recomputed for roughly four cells on average per frame [S1, unofficial].
- **Point Primitives:** Generated from the active cells [S1, unofficial]. Each point represents a location on the isosurface [S1, unofficial].

**Steps:**
1. **Identify Active Cells:** Determine which volume cells intersect the isosurface [S1, unofficial].
2. **Generate Points:** For each active cell, compute the point position on the isosurface [S1, unofficial]. If a cell is marked "dirty" (based on the regeneration rate), regenerate its primitive [S1, unofficial].
3. **Setup Distance Attenuation:** Configure OpenGL to scale point size based on distance to maintain consistent visual coverage [S1, unofficial].
4. **Render:** Issue `glDrawArrays(GL_POINTS, ...)` to render the points as discs [S1, unofficial].

**Formulas and Parameters:**
To set up perspective scaling of points as discs, distance attenuation is configured using the following parameters derived from the projection matrix and viewport [S1, unofficial]:

$$ H = \text{viewport\_width} $$
$$ h = \frac{2.0}{\text{projection\_matrix}[0]} $$
$$ D_0 = \sqrt{2.0} \cdot \frac{H}{h} $$
$$ k = \frac{1.0}{1.0 + 2 \cdot \sqrt{\frac{1}{\text{projection\_matrix}[0]}}} $$
$$ \text{atten} = \left[ 0, 0, \sqrt{\frac{1}{D_0}} \cdot k \right] $$

The attenuation vector is applied via `glPointParameterfvEXT(GL_DISTANCE_ATTENUATION_EXT, atten)` and point size is set to 1.0 [S1, unofficial].

**Pseudocode:**
```python
import math

def setup_point_attenuation(projection_matrix, viewport_width):
    m00 = projection_matrix[0]
    h = 2.0 / m00
    H = viewport_width
    D0 = math.sqrt(2.0) * (H / h)
    k = 1.0 / (1.0 + 2.0 * math.sqrt(1.0 / m00))
    atten_c = math.sqrt(1.0 / D0) * k

def render_isosurface(volume, isovalue, dirty_cells):
    cells_to_render = []
```

**Edge Cases and Pitfalls:**
- **Backface Culling:** Not possible for points because a point is a single vertex with no orientation, leading to more filling than polygons [S1, unofficial].
- **Dilation Artefact:** Points are rendered as discs even if they lie on the silhouette, causing the surface to appear dilated. This is visible in areas of high curvature [S1, unofficial].
- **Fill-Rate Limitation:** The method is prone to being fill-rate limited because points overlap to cover the surface [S1, unofficial].

## Subtopics

### Software Point Rendering
Draws points as ellipses whose main axes depend on the normal, alleviating dilation artefacts but lacking hardware acceleration [S1, unofficial].

### Marching Cubes (MC)
Generates triangle meshes. Offers superior visual quality when zooming in or using small datasets, but has higher geometry generation costs [S1, unofficial].

## Operating characteristics
**Time and Memory Complexity:**
- Geometry generation is faster than Marching Cubes for any volume size [S1, unofficial].
- Performance advantage increases with the size and complexity of the volumes [S1, unofficial].

**Measured Performance:**
- Test hardware: Not explicitly named, though recent hardware like Radeon 9700 and NV30 are mentioned for potential future features [S1, unofficial].
- Scene: Cube (32x32x32).
- Viewport 800x800: Points render at 76 fps, triangles at 146 fps [S1, unofficial].
- Viewport 100x100: Points render at 773 fps, triangles at 161 fps [S1, unofficial].
- Performance threshold: On the test hardware, OpenGL point rendering overtakes triangle strips at around 500k polygons [S1, unofficial].

**Scaling:**
- The method becomes fill-rate limited when few, large primitives are rendered [S1, unofficial].
- Performance increases with smaller viewports because the total number of pixels to fill decreases, reducing fill-rate pressure [S1, unofficial].

**Strengths and Limitations:**
- Strengths: Lower bandwidth and geometry pipeline requirements; faster primitive generation; similar quality to MC for large volumes [S1, unofficial].
- Limitations: Inferior visual quality when zooming in or using small datasets; dilation artefacts; fill-rate limited [S1, unofficial].

**When to Use:**
- Large volumes where geometry generation cost is prohibitive [S1, unofficial].
- When performance is critical and fill rate is not the bottleneck [S1, unofficial].

**When Not to Use:**
- Small datasets or when zooming in, where visual quality of MC is superior [S1, unofficial].
- Scenes with high curvature where dilation artefacts are objectionable [S1, unofficial].

## Background
This method was presented in the paper "Hardware Accelerated Point Rendering of Isosurfaces" [S1, unofficial]. It compares OpenGL point rendering to software point rendering and triangle rendering using Marching Cubes [S1, unofficial]. The authors note that recent hardware (Radeon 9700, NV30) might enable hardware-based point rendering techniques similar to software methods, such as computing reciprocal values or using point sprites to render ellipses [S1, unofficial].
