# GPU-based Slice Rendering with SculptBuffer

Also called: Interactive visualization pipeline, SculptBuffer rendering

## Overview
This method is a rendering technique that uses a 3D texture, called the SculptBuffer, stored on the GPU to store distances to a Surface of Reference Point (SRP) or a modified volume boundary [S1]. It enables interactive sculpting operations such as clipping, erasing, and digging by allowing fragment shader operations to access these distance values [S1]. Unlike standard volume rendering which visualizes the entire dataset, this approach renders only the slices contained in a `ClippedImage` (generated by a prior clipping algorithm) as convex polygons, discarding fragments based on their distance to the sculpted boundary [S1]. It sets itself apart by integrating real-time geometric modification (sculpting) directly into the rendering pipeline via GPU-based distance lookups, building on the [GPU-based Volume Sculpting System](13711-gpu-based-volume-sculpting-system.md) which provides the mechanism for generating the 3D mask.

## How it works
**Inputs and Outputs:**
*   **Input:** A `ClippedImage` containing slices generated by a clipping algorithm; a `SculptBuffer` (3D texture) storing distances to the SRP; transfer functions for shading; a `radius-of-interest` threshold.
*   **Output:** A rendered image in the frame buffer.

**Data Structures:**
*   **SculptBuffer:** A 3D texture stored in GPU memory. It stores distance values to the SRP or modified boundary. It is accessed via 3D coordinates derived from fragment positions [S1]. The buffer is generated from memory location data (e.g., CPU-side calculations of distances) and passed to the GPU as a pointer to memory, requiring no further processing of the data itself [S1].
*   **ClippedImage:** A collection of slices corresponding to convex polygons in 3D space [S1].

**Numbered Steps:**
1.  **Generate SculptBuffer:** Create the `SculptBuffer` as a 3D texture in GPU memory from memory location data (distances to SRP) [S1].
2.  **Render Slices:** Render the slices contained in the `ClippedImage` as convex polygons in 3D, approximated by 2D fragments [S1].
3.  **Maintain 3D Position:** For each fragment, maintain the 3D position of the point that generated it. For fragments internal to the polygon, use interpolated positions of the polygon vertices [S1].
4.  **Index SculptBuffer:** Use the 3D position from Step 3 as an index into the `SculptBuffer` [S1].
5.  **Compute Distance:**
    *   If the position lies exactly on the center of a voxel, return the exact distance to the SRP [S1].
    *   Otherwise, use linear interpolation of the distances of the closest voxels to allow a smooth transition and reduce aliasing artifacts [S1].
6.  **Discard Fragments:** Run a fragment program on the GPU to discard fragments with computed distances smaller than the `radius-of-interest` [S1].
7.  **Compute Shading:** For visible fragments (those not discarded), compute shading by accessing the look-up table generated by transfer functions [S1].
8.  **Render:** Render the result into the frame buffer [S1].

**Pseudocode:**

```python
# Fragment Shader Program for SculptBuffer Rendering

# Inputs:
#   frag_pos_3d: vec3, the 3D position of the fragment (interpolated for internal fragments)
#   sculpt_buffer: sampler3D, the 3D texture storing distances to SRP
#   radius_of_interest: float, threshold to discard fragments
#   lookup_table: sampler1D, texture for transfer function shading

# Output:
#   color: vec4, the final fragment color

void main() {
    # Step 5: Compute distance to SRP
    # Check if position is exactly on voxel center.
    # In practice, exact equality is rare; linear interpolation is the robust path.
    # Let dist be the distance value retrieved from the SculptBuffer.
    dist = texture(sculpt_buffer, frag_pos_3d).r;

    # Step 6: Discard fragments based on radius-of-interest
    # Fragments with distances smaller than the radius are discarded.
    if (dist < radius_of_interest) {
        discard;
    }

    # Step 7: Compute shading
    # Access the look-up table generated by transfer functions.
    # The intensity or color is determined by the distance or original volume value.
    # Assuming the transfer function maps the distance or volume value to color.
    # Note: The source specifies accessing the LUT for shading.
    # We assume a standard volume value 'val' is available or derived.
    # If shading depends on distance:
    shade_value = dist; 
    # Or if shading depends on original volume data at frag_pos_3d:
    # shade_value = texture(volume_texture, frag_pos_3d).r;
    
    # For this implementation, we follow the source's emphasis on the LUT.
    # Typically, the LUT is indexed by the volume value, not distance, 
    # but the source says "shading is computed by accessing the look-up table".
    # We assume standard volume rendering shading logic here.
    color = texture(lookup_table, shade_value);

    # Step 8: Render to frame buffer
    gl_FragColor = color;
}
```

**Parameters:**
*   **Radius-of-interest:** A threshold distance value used in the fragment program to discard fragments. Fragments with computed distances smaller than this radius are discarded [S1]. Typical values are not specified in the sources.

**Edge Cases and Pitfalls:**
*   **Aliasing:** Aliasing artifacts during rendering can occur if exact voxel distances are used without interpolation. This is handled by using linear interpolation of distances of the closest voxels when the fragment position does not lie exactly on a voxel center [S1].
*   **Data Transfer:** The method relies on sending the `SculptBuffer` data back to the GPU as a 3D texture. The source notes that this currently requires passing a pointer to memory location data, which may be a limitation on older graphics boards, though future generations are expected to improve this [S1].

## Operating characteristics
**Time and Memory Complexity:**
*   **Time:** On a PC Pentium 4 (2 GHz, 512 MB RAM) with an ATI 9800 graphics board, rendering a 512x512 image from a VOI of size 512x512x100 took approximately 2.18 msec/image (458 images/sec) for simple GPU rendering. With the eraser/digger tools (SculptBuffer method), it took 4.38 msec/image (228 images/sec) [S1].
*   **Memory:** The `SculptBuffer` is stored in GPU memory as a 3D texture. The size depends on the resolution of the volume data [S1].

**Scaling:**
*   The method guarantees real-time rates despite the performance impact of interactive sculpting tools [S1].

**Strengths and Limitations:**
*   **Strengths:** Enables real-time interactive visualization and manipulation of volumetric data, including clipping, erasing, and digging [S1].
*   **Limitations:** Performance is impacted by the additional processing for sculpting tools (roughly double the time of simple rendering) [S1]. The method currently requires sending data back to the GPU as a 3D texture, which may be inefficient on older hardware [S1].

**When to Use:**
*   Use when interactive sculpting (clipping, erasing, digging) of volumetric data is required in real-time, particularly in medical visualization contexts such as liver surgery planning [S1].

**When Not to Use:**
*   Use when high-performance simple volume rendering is sufficient and no interactive sculpting is needed, as the simple GPU rendering is faster [S1].

## Background
The method was developed as part of an interactive visualization pipeline for volumetric data, specifically targeting medical imaging applications such as liver surgery planning [S1]. It was presented in a paper by the authors of [S1] in 2004. The technique builds upon the [GPU-based Volume Sculpting System](13711-gpu-based-volume-sculpting-system.md) to provide real-time interaction with volumetric data using GPU-based methods [S1].
