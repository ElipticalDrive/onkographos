# Material Override Hierarchy

Also called: Material Override Order, VoxelTerrain Material Priority

## Overview
Material Override Hierarchy defines the precedence rules for assigning surface materials to geometry in voxel-based rendering systems. It solves the problem of conflicting material definitions by establishing a strict override chain, ensuring that high-level terrain or block definitions take precedence over lower-level mesh defaults. It differs from [Deferred Shading for Isosurfaces](867-deferred-shading-for-isosurfaces.md) by focusing on material assignment logic rather than rendering pipeline optimization, and from [Isosurface Color Enhancement](7670-isosurface-color-enhancement.md) by handling discrete material selection rather than continuous color mapping.

## How it works
The method operates on the intersection point $\mathbf{p}$ and the associated geometry context. It determines the final material by evaluating a hierarchy of sources.

### Inputs and Outputs
- **Input**: The geometric primitive (Mesh, VoxelBlock, or Terrain chunk) intersected by the ray at $\mathbf{p}$.
- **Output**: The concrete Material instance to be used for shading at $\mathbf{p}$.

### Data Structures
The hierarchy relies on three primary data containers, ordered by precedence:
1.  **Mesh Material**: The material explicitly assigned to the mesh resource (e.g., `VoxelBlockyModelMesh`).
2.  **VoxelBlockyModel Material**: A material property defined at the `VoxelBlockyModel` level.
3.  **VoxelTerrain Material**: A material property defined at the `VoxelTerrain` level.

### Steps
1.  **Identify Geometry Context**: Determine if the hit geometry is a standard mesh, a voxel block model, or part of a voxel terrain.
2.  **Evaluate Hierarchy**:
    -   If a material is explicitly defined on the `VoxelTerrain` associated with the geometry, select it. This is the highest priority.
    -   Else, if a material is defined on the `VoxelBlockyModel`, select it. This overrides mesh defaults.
    -   Else, select the material assigned to the mesh resource itself. This is the default fallback.
3.  **Apply Material**: Pass the selected material to the shading model [G] for evaluation at $\mathbf{p}$.

### Pseudocode
```python
def get_material_override(geom_context):
    """
    Determines the material for a given geometry context based on override hierarchy.
    
    Args:
        geom_context: Object containing references to Mesh, VoxelBlockyModel, and VoxelTerrain.
        
    Returns:
        Material: The concrete material instance to use.
    """
    # Step 1: Check highest priority: VoxelTerrain
    if geom_context.voxel_terrain is not None:
        terrain_material = geom_context.voxel_terrain.get_material()
        if terrain_material is not None:
            return terrain_material

    # Step 2: Check medium priority: VoxelBlockyModel
    if geom_context.voxel_blocky_model is not None:
        block_model_material = geom_context.voxel_blocky_model.get_material()
        if block_model_material is not None:
            return block_model_material

    # Step 3: Default: Mesh Material
    # Meshes are the default if no higher-level override exists.
    mesh_material = geom_context.mesh.get_material()
    return mesh_material
```

### Parameters and Edge Cases
-   **Precedence**: The order is strictly Terrain > BlockModel > Mesh.
-   **Null Handling**: If a higher-level source (Terrain/BlockModel) has no material defined, the system falls back to the next level. It does not default to a global "null" material unless all levels are empty.
-   **Mesh Reuse**: Reusing materials across different meshes reduces draw calls and improves performance [S1].

## Subtopics

### Material Palette and Slot Mapping
A system for binding concrete materials to named semantic slots on a Model, allowing per-occurrence material assignment without a global catalog [S2].

-   **Definition**: Each Model declares named slots (e.g., 'skin', 'cloth') used by its polygons. Shapes possess local geometric slots, and immutable Definitions associate these with semantic Model slots. A `MaterialPalette` binds concrete materials to these slot names per occurrence [S2].
-   **Data Structure**:
    ```cpp
    namespace spk::Voxel {
      struct MaterialSlot {
        std::string name;
        // Implicit fields: renderCategory, occlusionContract
      };
    }
    ```
-   **Workflow**:
    1.  Define named slots on the Model.
    2.  Create a `MaterialPalette` Factory for the Model.
    3.  Bind concrete materials to slot names (e.g., `bind("skin", skinMaterial)`).
    4.  Validate that the concrete material respects the slot's render category (opaque, cutout, translucent) and occlusion contract [S2].
    5.  Each `Assembly Part` holds a lightweight copy of the Model and its own `MaterialPalette` association. Multiple Parts can share the same palette instance [S2].
-   **Pitfalls**: Cutout materials are NOT considered fully opaque for occlusion purposes. Translucent materials generally do not occlude back faces. Identical transparent interfaces may be suppressible if visually correct [S2].
-   **Comparison**: Differs from the previous V0.1.3 approach which used a single unique palette for the entire Assembly. Now each Model occurrence has its own palette association [S2].

## Operating characteristics
-   **Time Complexity**: $O(1)$ for material selection, as it involves a fixed number of pointer checks against the hierarchy.
-   **Memory Complexity**: $O(1)$ additional memory per geometry context for storing references to the hierarchy levels.
-   **Performance**: Reusing materials across meshes reduces the number of draw calls, making rendering faster [S1].
-   **Strengths**: Simple, deterministic override logic. Decouples material assignment from geometry definition.
-   **Limitations**: Requires careful management of the hierarchy to avoid unintended overrides. The palette system adds complexity to the model definition phase [S2].

## Background
The concept originates from voxel engine design specifications, particularly in systems like Voxel Tools and Sparkle [S1, S2]. The hierarchy ensures that high-level terrain definitions can uniformly override local mesh details, which is crucial for consistent visual style in voxel-based games. The Material Palette system was introduced in V0.1.4 of the Sparkle engine to replace a global assembly-wide palette, allowing more granular control over material assignment per model occurrence [S2].
