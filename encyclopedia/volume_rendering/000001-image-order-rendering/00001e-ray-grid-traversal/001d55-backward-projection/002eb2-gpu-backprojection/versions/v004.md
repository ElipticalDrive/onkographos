# GPU Backprojection

Also called: FDK Backprojection CUDA Kernel, Scale field rendering, Scale-Space Backprojection, Weighted blob blending

## Overview
GPU Backprojection is a rendering pass that visualizes detected scale-space blobs by generating small slices for each blob, computing weighted contributions, and blending them to form the final image, followed by normalization [S2][S3, unofficial]. It is distinct from standard ray-casting as it operates on a sparse abstraction of the volume (scale maxima) rather than the full voxel grid, decoupling the expensive scale-space computation from the frequent backprojection step [S3, unofficial]. It builds on [Backward Projection](1491-backward-projection.md).

## How it works
**Inputs:**
*   `projections`: A tensor of shape `[batch, views, rows, columns]` containing the projection data or scale-space blob parameters.
*   `matrices`: A tensor of shape `[batch, views, 3, 4]` (or similar) containing the projection matrices for each view.
*   `volume_shape`: A tuple `(depth, height, width)` defining the output volume dimensions.
*   `batch`: The number of independent volumes to process.

**Outputs:**
*   `out`: A tensor of shape `[batch, 1, depth, height, width]` containing the backprojected volume.

**Data Structures:**
*   `PanelStencil`: A structure used in the CUDA kernel to store the four corners of the projected pixel footprint and their corresponding weights.
    *   `index[4]`: Unsigned integers representing the linear indices of the four pixels in the projection plane.
    *   `weight[4]`: Floats representing the interpolated weights for each pixel.
*   `ViewColumn`: A structure storing precomputed linear coefficients for a voxel's position relative to a view matrix.
    *   `column`, `column_z`: Linear coefficients for the column coordinate.
    *   `row`, `row_z`: Linear coefficients for the row coordinate.
    *   `depth`, `depth_z`: Linear coefficients for the depth (panel distance) coordinate.

**Steps:**

1.  **Preprocessing:**
    *   Detach and convert input matrices to contiguous float tensors: `matrices = matrices.detach().float().contiguous()` [S1, unofficial].
    *   Reshape projections to a flat tensor: `flat = projections.reshape(batch, -1)` [S1, unofficial].
    *   Extract dimensions: `depth, height, width` from `volume_shape`; `views, rows, columns` from `projections.shape[2:]` [S1, unofficial].
    *   Create output tensor `out` of shape `[batch, 1, *volume_shape]` [S1, unofficial].

2.  **Kernel Execution (Per Batch Group):**
    *   Iterate over batches in groups defined by `_GROUP` [S1, unofficial].
    *   For each group, load the specific kernel function `f"fdk_backproject_c{group}"` [S1, unofficial].
    *   Execute the kernel with grid `_volume_grid(volume_shape)` and block `_VOLUME_BLOCK` [S1, unofficial].
    *   Arguments passed to the kernel include:
        *   `flat`: The flattened projection data.
        *   `start`, `count`: The range of the current batch group.
        *   `group`: The group identifier.
        *   `matrices`: The projection matrices.
        *   `out[start]`: The output slice for this batch group.
        *   `width, height, depth`: Volume dimensions.
        *   `views, rows, columns`: Projection dimensions.
        *   `count`: The number of batches in the group.
        *   `depth * height * width`: Total number of voxels per volume [S1, unofficial].

3.  **Kernel Logic (Per Voxel):**
    *   Each thread processes a subset of voxels (e.g., `TT_FDK_DEPTH` voxels along z) [S1, unofficial].
    *   For each voxel $(x, y, z)$ and each view:
        *   Compute `ViewColumn` using the projection matrix and voxel $(x, y)$ [S1, unofficial].
        *   Compute the panel distance $w = fmaf(v.depth_z, z, v.depth)$ [S1, unofficial].
        *   If $w \le 0$, skip the view (voxel is behind the panel) [S1, unofficial].
        *   Compute inverse depth $inverse = 1/w$ [S1, unofficial].
        *   Compute normalized coordinates:
            *   $column = fmaf(v.column_z, z, v.column) \times inverse$
            *   $row = fmaf(v.row_z, z, v.row) \times inverse$
        *   Check if $(column, row)$ is within the projection bounds $[-1, columns]$ and $[-1, rows]$ (or $[0, columns]$ and $[0, rows]$ depending on implementation, but the stencil code checks $>-1$ and $<rows$) [S1, unofficial].
        *   If within bounds, compute the `PanelStencil`:
            *   Determine floor coordinates $c0 = \lfloor column \rfloor$, $r0 = \lfloor row \rfloor$ [S1, unofficial].
            *   Compute deltas $dc = column - c0$, $dr = row - r0$ [S1, unofficial].
            *   Compute weights using bilinear interpolation factors scaled by $inverse^2$:
                *   $wc0 = (c0 \ge 0) ? (1 - dc) : 0$
                *   $wc1 = (c0 + 1 < columns) ? dc : 0$
                *   $wr0 = (r0 \ge 0) ? (1 - dr) \times inverse^2 : 0$
                *   $wr1 = (r0 + 1 < rows) ? dr \times inverse^2 : 0$
            *   Store indices and weights in `PanelStencil` [S1, unofficial].
        *   Scatter the weighted contribution to the output volume. The weight applied is proportional to $(D/l)^2$, where $l$ is the voxel depth along the panel normal and $D$ is the panel depth. In the code, this is implemented as $inverse^2$ [S1, unofficial].

4.  **Normalization:**
    *   In a separate pass, normalize the accumulated result by dividing by the sum of weights, which is stored in a separate channel [S2][S3, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** The use of `float32` for weights and coordinates may lead to precision issues in large volumes or high-resolution projections [S1, unofficial].
*   **Boundaries:** The stencil code checks for bounds $>-1$ and $<rows/columns$, which implies a coordinate system where the projection plane extends slightly beyond the integer pixel grid. Care must be taken to handle edge pixels correctly [S1, unofficial].
*   **Zero Weight:** If $w \le 0$, the voxel is behind the projection panel and should be skipped to avoid division by zero or invalid weights [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The backprojection step is significantly faster than the scale-space computation. The scale-space computation is done once, while backprojection can be done frequently [S3, unofficial].
*   **Memory Complexity:** Requires temporary volume storage for the scale field. The output volume size is $O(N^3)$ where $N$ is the volume dimension [S3, unofficial].
*   **Performance:** On an Intel Core 2 Duo 2.4 GHz with 2GB RAM and an nVidia GeForce 8800 GTX with 768 MB texture memory, the GPU implementation showed an improvement of about two orders of magnitude over the CPU version for data set sizes of $64^3$, $128^3$, and $256^3$ [S2][S3, unofficial].
*   **Strengths:** Decouples the expensive scale-space computation from the backprojection, allowing for interactive visualization where the user can change smoothness and visibility parameters frequently [S3, unofficial].
*   **Limitations:** Relies on a temporary volume to compute the scale field. Real-time implementation may be limited by GPU memory as the volume size increases [S3, unofficial].

## Background
GPU Backprojection is part of the "Size-based Transfer Functions" technique for volume exploration [S2][S3, unofficial]. It was developed to address the computational cost of interactive volume visualization by leveraging the GPU for the backprojection step. The method was evaluated on an nVidia GeForce 8800 GTX [S2][S3, unofficial].
