# Octree-based Volume Rendering

Also called: Chamberlain's algorithm, LaMar's algorithm, Weiler's smoothing

## Overview
Octree-based volume rendering accelerates image-order ray casting by traversing a hierarchical spatial subdivision of the volumetric data, skipping empty or sufficiently uniform regions to reduce computational cost [S1, unofficial]. It differs from sibling methods like [Point Plane Test Traversal](982-point-plane-test-traversal.md) by using a tree structure for adaptive level-of-detail (LOD) selection rather than fixed coarse meshes or plane tests, and unlike [CPU Sparse Voxel Octree Traversal](2455-cpu-sparse-voxel-octree-traversal.md) which often focuses on explicit sparse storage, this method traditionally assumes the octree resides in main memory [S1, unofficial].

## How it works
**Inputs:** Volumetric dataset (density $\sigma$ and color $c$); camera parameters (view matrix, projection matrix, field-of-view).
**Outputs:** Rendered image.

**Data Structures:**
*   **Octree Node:** Contains a bounding box (min/max coordinates), a pointer to children (if not a leaf), and leaf data (density/color values or coefficients).
*   **Leaf Data:** For traditional methods, scalar density and color values. For PlenOctree, density and spherical harmonic (SH) coefficients.

**Steps:**
1.  **Preprocessing:** Subdivide the volumetric data into an octree. Empty or uniform regions are merged into higher-level nodes [S1, unofficial].
2.  **Ray Casting:** For each pixel, cast a ray through the scene.
3.  **Traversal & Selection:** Recursively traverse the octree. At each node, compute selection criteria to decide whether to visit children or render the node as a leaf approximation [S1, unofficial]:
    *   **Chamberlain’s Criterion:** Compute the projected size of the node on the view plane. If the projected size is smaller than a predefined threshold, the node is considered sufficiently accurate to approximate all nodes below it [S1, unofficial].
    *   **LaMar’s Criteria:** Use two filters:
        1.  **Distance:** Similar to Chamberlain, based on projected size/distance.
        2.  **Field-of-View (FOV):** Discard nodes that do not intersect the view frustum. Select nodes whose projected angle is less than half the FOV angle [S1, unofficial].
4.  **Rendering:** If a node is selected as a leaf approximation, accumulate its contribution to the ray. If not, recurse into its children.
5.  **Smoothing (Weiler):** Apply smoothing techniques at LOD boundaries to reduce visual artifacts caused by inconsistencies in the view plane at different levels of detail [S1, unofficial].

**PlenOctree Variant:**
1.  **Intersection:** Determine ray-voxel intersections in the octree, producing segments of constant density and color with lengths $\{\delta_i\}$ [S2, unofficial].
2.  **Accumulation:** Apply NeRF’s volume rendering model [S2, unofficial]:
    $$ C(\mathbf{r}) = \sum_{i=0}^{N} T_i (1 - \exp(-\sigma_i \delta_i)) \mathbf{c}_i $$
    where transmittance $T_i = \exp(-\sum_{j=0}^{i-1} \sigma_j \delta_j)$ [S2, unofficial].
3.  **Early Stopping:** Stop rendering when accumulated transmittance $T_i < \gamma$, where $\gamma = 0.01$ [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **LOD Artifacts:** Substantial visual artifacts appear at boundaries of different LODs due to view-plane inconsistencies [S1, unofficial].
*   **Memory Limitation:** Traditional implementations cannot reduce volumetric data size in main memory, limiting rendering of datasets larger than RAM [S1, unofficial].

## Subtopics

### PlenOctree Rendering
A variant that converts a trained NeRF-SH model into a sparse octree representation for real-time rendering [S2, unofficial]. It stores density and SH coefficients modeling view-dependent appearance at each node [S2, unofficial]. It achieves significant speedups (e.g., ~42 FPS on Tanks and Temples) compared to standard NeRF while maintaining comparable image quality metrics (PSNR/SSIM) [S2, unofficial]. It uses early stopping when transmittance drops below 0.01 [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** Depends on octree depth and data sparsity. LaMar’s algorithm provides considerable speedup over Chamberlain’s by using FOV culling [S1, unofficial].
*   **Memory Complexity:** Traditional methods require the entire octree in main memory, limiting scalability to datasets larger than RAM [S1, unofficial]. PlenOctree uses sparse storage, reducing memory footprint [S2, unofficial].
*   **Strengths:** Adaptive LOD reduces computation in empty or uniform regions; FOV culling improves performance [S1, unofficial].
*   **Limitations:** LOD boundary artifacts require smoothing; memory-bound for large datasets in traditional implementations [S1, unofficial].
*   **When to Use:** Real-time rendering of volumetric data with significant empty space or uniform regions; when memory allows loading the octree.
*   **When Not to Use:** Datasets exceeding main memory size without sparse storage extensions; scenes requiring seamless LOD transitions without post-processing smoothing.

## Background
The octree spatial hierarchy was first proposed by Chamberlain et al. for rendering surface geometry, later adapted for volume data [S1, unofficial]. LaMar et al. improved selection criteria with distance and FOV filters [S1, unofficial]. Weiler et al. addressed LOD artifacts with smoothing extensions [S1, unofficial]. PlenOctree extends this to neural radiance fields, enabling real-time rendering of NeRFs [S2, unofficial].
