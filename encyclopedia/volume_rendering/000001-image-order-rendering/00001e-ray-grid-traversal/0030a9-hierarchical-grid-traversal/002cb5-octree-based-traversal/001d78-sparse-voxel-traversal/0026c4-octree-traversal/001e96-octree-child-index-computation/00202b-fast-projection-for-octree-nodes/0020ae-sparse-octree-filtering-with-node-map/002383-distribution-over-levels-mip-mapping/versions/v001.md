# Distribution over Levels (MIP-mapping)
Also called: Octree MIP-map filtering, Three-pass MIP-mapping filtering

## Overview
Distribution over Levels is a hierarchical filtering technique used to propagate radiance values from the leaf nodes of a sparse voxel octree to its internal nodes, creating a MIP-map pyramid. It solves the problem of efficiently computing approximate illumination at coarser resolutions for cone tracing [S1, S2]. It is distinguished from standard isotropic downsampling by its use of a three-pass strategy to balance thread cost and its specific handling of shared boundary voxels in a 3x3x3 brick structure [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A sparse voxel octree with $n$ levels, where leaf nodes contain initial radiance values (e.g., from photon splatting).
*   **Output:** An octree where internal nodes at levels $1$ to $n-1$ contain filtered radiance values derived from their children.

**Data Structures:**
*   **Octree Node:** Contains a 3x3x3 brick of voxels.
*   **Voxel:** Stores radiance (energy) and potentially directional information (e.g., Gaussian-Lobes).
*   **Multiplicity Map:** Implicitly handled by weighting; each voxel in a 3x3x3 brick is shared with up to 8 neighboring bricks.

**Parameters:**
*   **Kernel:** 3x3x3 Gaussian weighting kernel. This is considered an optimal reconstruction filter [FP02].
*   **Levels:** $n-1$ filtering steps for an octree of $n$ levels.

**Steps:**
1.  **Initialization:** Build the octree structure and write initial values into leaf nodes.
2.  **Iterative Filtering:** For each level from $n-1$ down to $1$:
    a.  Launch threads to compute filtered values for the current level based on the previous (finer) level.
    b.  To balance thread cost and avoid redundant computation on shared boundaries, execute three distinct passes:
        i.  **Pass 1 (Center):** Compute the center voxel of the 3x3x3 brick. This involves averaging the 27 voxel values from the lower level.
        ii. **Pass 2 (Face Centers):** Compute half of the filtered response for the 6 voxels situated in the center of the node's faces. Each of these involves 18 voxel values from the lower level. The result is stored as half the final value.
        iii. **Pass 3 (Corners):** Launch threads for the 8 corner voxels. Each computes a partial filtering of voxels from a single octant (9 values). The result is stored as a partial value.
    c.  **Value Transfer:** Apply the "Value Transfer to Neighboring Bricks" step (described in [Sparse Octree Filtering with Node Map](2337-sparse-octree-filtering-with-node-map.md)) to sum the partial values across adjacent bricks, finalizing the filtered result for each voxel.
3.  **Weighting:** When averaging values from the previous level, weight each voxel by the inverse of its multiplicity. Because a 3x3x3 brick's boundary voxels are shared with neighboring bricks, they are counted multiple times if summed directly. The Gaussian kernel implicitly handles this distribution [S1].

**Pseudocode:**
```python
def distribute_over_levels(octree, levels):
    """
    Perform MIP-mapping on a sparse voxel octree.
    octree: The octree structure with leaf values populated.
    levels: Total number of levels in the octree (n).
    """
    # Iterate from the finest internal level up to the root
    for level in range(levels - 1, 0, -1):
        current_level_nodes = get_nodes_at_level(octree, level)
        previous_level_nodes = get_nodes_at_level(octree, level + 1)
        
        # Pass 1: Center Voxels
        for node in current_level_nodes:
            center_voxel = node.voxels[1, 1, 1]
            # Gather 27 voxels from the 8 child bricks in the previous level
            source_voxels = gather_27_voxels(node, previous_level_nodes)
            # Apply Gaussian weights (inverse multiplicity)
            center_voxel.value = weighted_average(source_voxels)
            node.voxels[1, 1, 1] = center_voxel

        # Pass 2: Face Center Voxels (Half Value)
        for node in current_level_nodes:
            for face_idx in range(6):
                face_voxel = node.voxels[get_face_coords(face_idx)]
                # Gather 18 voxels from the previous level
                source_voxels = gather_18_voxels(node, previous_level_nodes, face_idx)
                # Compute half the filtered response
                face_voxel.value = 0.5 * weighted_average(source_voxels)
                node.voxels[get_face_coords(face_idx)] = face_voxel

        # Pass 3: Corner Voxels (Partial Value)
        for node in current_level_nodes:
            for corner_idx in range(8):
                corner_voxel = node.voxels[get_corner_coords(corner_idx)]
                # Gather 9 voxels from the single relevant octant in the previous level
                source_voxels = gather_9_voxels(node, previous_level_nodes, corner_idx)
                # Compute partial filtering
                corner_voxel.value = weighted_average(source_voxels)
                node.voxels[get_corner_coords(corner_idx)] = corner_voxel

    # Finalize by summing contributions across brick boundaries
    apply_value_transfer(octree)

def weighted_average(voxels):
    """
    Computes the weighted average using a 3x3x3 Gaussian kernel.
    The weights account for the inverse multiplicity of shared voxels.
    """
    total_weight = 0.0
    weighted_sum = 0.0
    for v in voxels:
        w = get_gaussian_weight(v.position) # Implicitly handles boundary sharing
        weighted_sum += v.value * w
        total_weight += w
    return weighted_sum / total_weight
```

**Edge Cases and Pitfalls:**
*   **Sparse Octrees:** If the octree is sparse, launching threads for all nodes (including empty ones) is inefficient. The method assumes a complete structure for the base algorithm; for sparse structures, thread launch must be optimized (e.g., per light-view-map pixel) to avoid filtering zero values [S1].
*   **Shared Voxels:** Failure to account for multiplicity (shared boundary voxels) leads to incorrect energy conservation. The Gaussian kernel and inverse multiplicity weighting are critical [S1].
*   **Precision:** Accumulating partial values across bricks requires careful handling of floating-point precision to avoid artifacts in the final sum.

## Subtopics

### Gaussian-Lobes Representation for Radiance Filtering
A compact representation used to store the filtered distribution of incoming light directions in the octree MIP-map levels. It allows for view-dependent treatment of the Normal Distribution Function (NDF) and Bidirectional Reflectance Distribution Function (BRDF) [S2]. Instead of storing single scalar values, it stores directional distributions, enabling more accurate cone tracing and indirect illumination calculation [S2].

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of nodes in the octree, as each node is processed a constant number of times (3 passes). However, for sparse octrees, naive implementation is $O(L^3)$ where $L$ is the depth, which is inefficient. Optimized implementations reduce this by only processing non-empty nodes.
*   **Memory Complexity:** Requires storage for the MIP-map levels, effectively doubling or tripling the memory usage of the leaf-only octree depending on implementation.
*   **Performance:** The three-pass approach balances thread cost, ensuring that all threads have roughly the same computational load, which improves GPU scheduling efficiency [S1].
*   **Strengths:** Efficiently propagates illumination data to coarser levels for cone tracing; handles directional information via Gaussian-Lobes; balances parallel workload.
*   **Limitations:** Computationally expensive for dense octrees; requires careful handling of sparse structures to avoid wasting resources on empty nodes; requires additional memory for MIP-map levels.
*   **When to use:** When performing voxel cone tracing for indirect illumination in real-time or interactive applications, especially when directional information is important.
*   **When not to use:** For simple direct illumination or when memory is extremely constrained and MIP-maps cannot be afforded.

## Background
The method originates from the work on Interactive Indirect Illumination Using Voxel Cone Tracing by Jaroslav Krivánek et al. (2011) [S1, S2]. It was developed to enable efficient real-time global illumination by approximating indirect lighting through cone tracing in a sparse voxel octree. The three-pass MIP-mapping strategy was introduced to address the imbalance in thread costs and the redundancy of computing shared boundary voxels multiple times [S1]. The Gaussian-Lobes representation was introduced to handle directional lighting data more accurately than scalar values [S2].
