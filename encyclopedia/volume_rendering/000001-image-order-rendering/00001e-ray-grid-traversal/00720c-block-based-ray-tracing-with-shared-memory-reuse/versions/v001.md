# Block-based Ray Tracing with Shared Memory Reuse

Also called: CUDA Block-based Ray Tracing with Shared Memory Reuse, Coherent ray tracing, Packet ray tracing

## Overview
This method accelerates volume rendering by grouping rays into fixed-size screen-space blocks (warps) and reusing traversal state from previously processed rays within the same block to reduce redundant memory accesses [S1, unofficial]. It differs from standard [Uniform Grid Traversal](9652-uniform-grid-traversal.md) by exploiting spatial coherence among primary camera rays, and from [Hierarchical Grid Traversal](2560-hierarchical-grid-traversal.md) by avoiding tree-based culling in favor of shared memory caching [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A screen divided into blocks of pixels (e.g., 8x8), a volume dataset, and ray origins/directions for each pixel.
- Output: Rendered color/opacity values for each pixel.

**Data Structures:**
- **Shared Memory:** A 16 KB region allocated per block, accessible by all threads in the block [S1, unofficial].
- **Block State:** Stores the traversal state (current voxel index, $t_{max}$ values) of the "previous" or "neighboring" ray processed in the block [S1, unofficial].

**Steps:**
1. **Block Division:** Divide the image into fixed-size blocks (e.g., 8x8 pixels) [S1, unofficial].
2. **Ray Generation:** Generate primary rays for each pixel in the block.
3. **Coherence Check:** For each ray, check if a valid traversal state exists in shared memory from a previously processed ray in the same block (e.g., the neighbor above or to the left) [S1, unofficial].
4. **State Reuse:** If a valid state exists, initialize the current ray's traversal variables ($t_{max}$, current voxel index) using the reused state instead of computing them from scratch [S1, unofficial].
5. **Traversal:** Perform the standard [Ray-grid traversal](17-ray-grid-traversal.md) (e.g., DDA) starting from the reused state [S1, unofficial].
6. **State Update:** After traversal, store the final state or relevant intermediate state back into shared memory for potential reuse by subsequent rays in the block [S1, unofficial].
7. **Rendering:** Integrate the volume along the ray and store the result.

**Pseudocode:**
```python
def block_based_ray_tracing(block_size, shared_memory, volume_data):
    # Allocate shared memory for block state
    # shared_memory[state] = {voxel_index, t_max_x, t_max_y, t_max_z, valid}
    
    for block in image_blocks(size=block_size):
        # Load previous state from shared memory if available
        prev_state = shared_memory.get(block.id)
        
        for ray in block.rays:
            if prev_state and prev_state.valid:
                # Reuse state from neighbor/previous ray
                current_voxel = prev_state.voxel_index
                t_max = prev_state.t_max
                t_entry = prev_state.t_entry
            else:
                # Initialize from scratch
                current_voxel = compute_voxel_index(ray.origin)
                t_max = compute_initial_t_max(ray.origin, ray.direction, voxel_size)
                t_entry = 0.0
            
            # Perform traversal loop (see DDA)
            while in_volume(current_voxel):
                # ... DDA steps ...
                pass
            
            # Render pixel
            color = integrate_volume(ray, current_voxel, t_max)
            store_result(ray.pixel_id, color)
            
            # Update shared memory for next ray in block
            # Note: In practice, only update if coherence is likely beneficial
            shared_memory[block.id] = {
                'voxel_index': current_voxel,
                't_max': t_max,
                't_entry': t_entry,
                'valid': True
            }
```

**Edge Cases:**
- **Invalid Reuse:** If the reused state is invalid (e.g., ray started outside the volume), fall back to full initialization [G].
- **Precision:** Reusing floating-point $t_{max}$ values may accumulate error; consider re-normalizing or re-computing $t_{max}$ periodically [G].

## Subtopics

### [Perspective Grid for Primary Rays](22973-perspective-grid-for-primary-rays.md)
Uses a perspective-aligned grid to maximize coherence for primary rays, leveraging shared memory reuse but unsuitable for secondary rays.

## Operating characteristics
- **Time Complexity:** Depends on the underlying traversal (e.g., DDA is $O(N)$ per ray), but the constant factor is reduced by skipping initialization steps for coherent rays [S1, unofficial].
- **Memory Complexity:** Requires 16 KB of shared memory per block [S1, unofficial].
- **Performance:** Significant speedup on GPUs due to reduced memory latency and increased coherence [S1, unofficial].
- **Strengths:** High performance for primary rays with strong spatial coherence.
- **Limitations:** Less effective for secondary rays (reflections, shadows) which lack coherence. Requires careful management of shared memory state.
