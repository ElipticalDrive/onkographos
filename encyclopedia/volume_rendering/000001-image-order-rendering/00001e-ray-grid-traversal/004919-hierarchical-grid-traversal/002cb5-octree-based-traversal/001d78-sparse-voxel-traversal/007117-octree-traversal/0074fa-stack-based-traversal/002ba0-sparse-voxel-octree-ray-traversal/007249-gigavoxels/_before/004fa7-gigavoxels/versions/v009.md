# GigaVoxels

Also called: Dynamic Sparse Octree, GigaVoxels rendering, GigaVoxels: A Voxel-Based Rendering Pipeline For Efficient Exploration Of Large And Detailed Scenes, Ray-Guided Streaming, Sparse Voxel Octree with Hierarchical Volume Ray-Casting, Voxel Ray-Tracing with GPU Cache

## Overview
GigaVoxels is a real-time voxel-based rendering pipeline designed for the efficient exploration of large and detailed scenes containing billions of voxels [S1, unofficial][S2][S3, S4, unofficial]. It solves the problem of rendering volumetric data that exceeds GPU memory capacities by using a sparse voxel octree structure, GPU caching, and ray-guided streaming to load only the necessary data at the required resolution [S1, unofficial][S2][S3, S4, unofficial]. Unlike sibling methods such as [Sparse Voxel Octree Ray Traversal](2451-sparse-voxel-octree-ray-traversal.md) which may assume in-core data or simpler traversal, GigaVoxels integrates a unified out-of-core cache management system on the GPU, combining hierarchical volume ray-casting with cone tracing to provide inherent anti-aliasing and smooth level-of-detail transitions [S1, unofficial][S2][S3, S4, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** Sparse voxel data (geometry/density), camera parameters (position, projection), and optional procedural definitions (e.g., noise functions, distance fields).
*   **Outputs:** Final color buffer (and optionally depth/normal buffers).

**Data Structures:**
The method uses a unified data structure consisting of three main components [S1, S3, S6, unofficial]:
1.  **Sparse Voxel Mipmap Pyramid (SVMP):** A hierarchy of downsampled voxel data. Each level represents a lower resolution version of the volume, built by iteratively downsampling and averaging neighbors [S4, unofficial]. This allows for cone tracing approximation [S3, S4, unofficial].
2.  **Generalized N3-tree (Octree):** A space-partitioning structure that handles empty space compaction. Nodes point to either child nodes or a "brick" [S1, S6, unofficial].
3.  **Bricks:** Regular, constant-sized blocks of voxels (typically $8^3$) [S2][S5, unofficial]. Bricks store opacity, color, and normal information. Non-leaf nodes may also own bricks to facilitate mip-mapping [S6, unofficial]. Bricks are stored in a "brick pool" [S6, unofficial].

**GPU Cache:**
A unified LRU (Least Recently Used) cache manages both the node pool and brick pool on the GPU [S3, unofficial]. Cache elements track usage via 'Oldest' and 'Newest' pointers and a 'Used nodes mask' [S3, unofficial]. Stream compaction is used to manage the "New data Stream" and concatenate the Octree/Bricks Pool [S3, unofficial].

**Algorithm Steps:**
1.  **Ray Traversal & LOD Selection:** For each pixel, a ray is cast. The ray traverses the octree. A KD-restart algorithm is used to descend the node tree without stack usage [S6, unofficial]. The traversal determines the appropriate Level of Detail (LOD) based on the cone footprint radius relative to the ray distance [S5, unofficial].
2.  **Data Request & Streaming:** If the required node or brick is not in the GPU cache, the ray tracer emits a request [S1, unofficial]. The Central Memory/Cache Manager loads the missing data from mass storage or generates it procedurally [S1, unofficial]. Data can be loaded level-by-level (coarse to fine) for speed or directly at max resolution for quality [S1, unofficial].
3.  **Cone Tracing / Brick Marching:**
    *   The renderer performs hierarchical volume ray-casting [S1, unofficial].
    *   Instead of simple ray accumulation, it uses approximate cone tracing [S5, unofficial]. The step size is proportional to the distance from the observer, approximating the cone integral defined by the eye and pixel extent [S4, unofficial].
    *   Reading from the SVMP delivers the integrated value of a small volume [S4, unofficial].
    *   Shading (e.g., Blinn-Phong) is computed per sample [S3, unofficial]. Normals can be derived on-the-fly using finite differences or stored directly [S3, unofficial].
    *   Accumulation follows the front-to-back model [S3, unofficial]:
        $$ C = \text{Color intensity} + \text{Alpha} $$
        (Specifically, $\text{AccumulatedColor} = \text{AccumulatedColor} + (1.0 - \text{AccumulatedColor}.w) \times \text{SampleColor}$) [S1, S3, unofficial].
    *   Marching terminates when the volume becomes opaque (e.g., accumulated alpha $\ge 0.98$) or when a descent criterion is met [S1, unofficial][S2][S6, unofficial].
4.  **Occlusion Handling:** Opaque objects are rendered first to the depth buffer to skip occluded parts [S1, unofficial]. Intravolume occlusion is taken into account by stopping rays when opaque [S2].
5.  **Procedural Generation (Optional):** For hypertextures or fractals, noise is computed on-the-fly. To optimize, only one octave of noise is computed per LOD level and stored in the cache. The total noise is reconstructed as $F(\text{level } N) = \text{currentNoise}(\text{level } N) + \text{previousNoise}(\text{level } N-1)$ [S1, unofficial].

**Pseudocode:**
```python
# Simplified CUDA Kernel for GigaVoxels Rendering
# One thread per pixel/ray

def GigaVoxelsRenderKernel(ray, cache_manager, svmp, octree):
    accumulated_color = float4(0.0, 0.0, 0.0, 0.0)
    current_pos = ray.origin
    ray_direction = ray.direction
    
    # Traverse Octree and March Bricks
    while accumulated_color.w < 0.98f: # Stop when opaque [S1, unofficial]
        
        # 1. Determine LOD and Fetch Node/Brick
        # Calculate cone aperture based on distance and pixel footprint [S5, unofficial]
        cone_aperture = getConeAperture(current_pos, ray)
        
        # Traverse octree to find the appropriate brick at the correct LOD
        # Returns the brick data if available, or triggers a cache request [S2]
        brick_data = octree.traverse_and_fetch(current_pos, cone_aperture, cache_manager)
        
        if brick_data is None:
            # Data not available, break or handle request (implementation dependent)
            break
            
        # 2. Sample Brick (Cone Tracing Approximation)
        # Sample the brick using the calculated aperture
        # brickSampler.getValue retrieves color (channel 0) and alpha [S1, unofficial]
        sample = brick_sampler.sample(brick_data, current_pos, cone_aperture)
        
        # 3. Shading (Optional: Blinn-Phong per sample)
        # Normal can be fetched from brick or computed via finite differences [S3, unofficial]
        normal = compute_normal(brick_data, current_pos)
        color = compute_shading(sample.color, normal, ray)
        
        # 4. Accumulate Color (Front-to-Back)
        # C = C + (1 - C.w) * sample_color [S1, unofficial]
        if sample.alpha > 0.0f:
            accumulated_color = accumulated_color + (1.0 - accumulated_color.w) * color
            
        # 5. Advance Ray
        # Step size is determined by the brick size or LOD level [S4, unofficial]
        step_size = get_step_size(brick_data.lod_level)
        current_pos = current_pos + ray_direction * step_size
        
        # Check if ray has exited the volume bounds
        if not octree.contains(current_pos):
            break
            
    return accumulated_color
```

**Parameters:**
*   **Cone Aperture:** Controls the trade-off between quality and performance [S1, S5, unofficial].
*   **Stop Criterion:** e.g., `accumulatedColor.w >= 0.98f` [S1, unofficial].
*   **Descent Criterion:** Used during visit traversal to decide when to stop descending the octree [S1, unofficial].
*   **Brick Pool Size:** Adjustable to match available hardware; smaller pools consume less video memory but store fewer bricks [S6, unofficial].
*   **CUDA Compute Capability:** SM at least 2.0 [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Aliasing:** Caused by defining pixel value by ray accumulation rather than cone integration. Addressed by mipmapping and cone tracing [S4, unofficial].
*   **Memory Limits:** Out-of-core rendering is essential for vast worlds; the method relies on the cache to manage this [S6, unofficial].
*   **Procedural Noise:** Reusing noise computation requires careful management of cache levels to ensure $F(\text{level } N)$ correctly sums octaves [S1, unofficial].

## Subtopics

### [Distributed Multi-Level Out-Of-Core Volume Rendering](6238-distributed-multi-level-out-of-core-volume-rendering.md)
Distributed Multi-Level Out-Of-Core Volume Rendering is a distributed image-order rendering technique designed to visualize volume datasets significantly larger than the aggregate memory of a GPU cluster, targeting scalable high-resolution display arrays. It solves the problem of out-of-core data access by combining a multi-level cache hierarchy (GPU texture memory, CPU RAM, and distributed shared memory) with a display-aware LOD selection mechanism that bounds the working set size. Unlike sibling methods such as GigaVoxels which stream data to a single GPU, this method distributes the volume across cluster nodes, using a unique data management scheme to relocate bricks between nodes based on view transformation, thereby avoiding the data replication required by systems like Vol-a-Tile or Volume Visualizer.

#### Dense 3D Texture Voxelization
Dense 3D Texture Voxelization is an alternative to GigaVoxels where the entire scene (empty space and all) is encoded into a very large mip-mapped 3D texture [S7, unofficial]. The octree is implicit in the mipmap levels of the 3D texture, and rays traverse the mip-map chain instead of an octree [S7, unofficial]. Rays index into the voxel data directly because the 3D texture is a world space representation of the scene [S7, unofficial]. Quadrilinear interpolation is automatically achieved with texture() calls because of the mip map chain [S7, unofficial]. Bricks are spatially aligned in the scene rather than existing in an amorphous memory pool, so redundant neighbor voxels do not need to be stored, and the filtering stage (mip map generation) is straightforward [S7, unofficial]. However, dense 3D textures are impractical because of how much memory they consume, especially the empty space that must be backed by physical memory [S7, unofficial].

## Operating characteristics
*   **Time Complexity:** Real-time to interactive rates (20-90 fps) on current generation hardware [S4, unofficial]. Performance depends on the density of the volume and the efficiency of the cache hits [S4, unofficial].
*   **Memory Complexity:** Out-of-core; memory usage is bounded by the GPU cache size and the brick pool, which can be adjusted to fit available hardware [S6, unofficial]. It respects the limited GPU memory budget [S4, unofficial].
*   **Scaling:** Fully scalable (infinite resolution) due to the procedural generation and LOD mechanisms [S3, unofficial].
*   **Strengths:** Handles billions of voxels; inherent anti-aliasing via cone tracing; smooth LOD transitions; supports semi-transparent volumes; efficient GPU cache management with zero CPU intervention during rendering [S1, unofficial][S2][S3, S4, unofficial].
*   **Limitations:** Requires CUDA Compute Capability SM 2.0 or higher [S1, unofficial]; complex to implement due to the unified cache and streaming logic; out-of-core rendering adds complexity [S6, unofficial].
*   **When to use:** Real-time exploration of large, detailed voxel scenes (e.g., 3D scans, hypertextured meshes, fractals) where memory exceeds GPU capacity [S4, unofficial].
*   **When not to use:** Scenes with very small, sparse details that do not benefit from hierarchical streaming, or when hardware does not support the required CUDA features.

## Background
GigaVoxels was introduced in 2009 by Crassin et al. [S4, S3, unofficial]. It was developed as a response to the limitations of previous volume rendering techniques in handling massive datasets in real-time. The method builds on the concept of sparse voxel octrees [LHN05a] and brick maps [LKS*06], combining them with a novel ray-guided streaming approach [S4, unofficial]. It differs from view-independent structures by continuously adapting resolution, making discontinuities disappear and ensuring smooth temporal transitions [S4, unofficial]. It also differs from Gobbetti et al. [GMAG08] by providing better quality/performance, procedural content generation, and level-of-detail management [S4, unofficial]. The technique has been used in various applications, including planetariums (RSA Cosmos project) and video games [S1, unofficial][S2].
