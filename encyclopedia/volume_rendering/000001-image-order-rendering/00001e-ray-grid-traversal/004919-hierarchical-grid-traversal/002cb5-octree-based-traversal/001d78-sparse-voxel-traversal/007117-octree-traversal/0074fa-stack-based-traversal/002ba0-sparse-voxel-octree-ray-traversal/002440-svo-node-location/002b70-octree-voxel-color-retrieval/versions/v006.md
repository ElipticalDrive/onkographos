# Octree Voxel Color Retrieval

Also called: Color Lookup with Shading, Voxel Lighting and Color Retrieval, lookupColor

## Overview
Octree Voxel Color Retrieval computes the final color of a hit voxel by retrieving its stored color and normal data from a sparse voxel octree and applying a directional lighting model. It builds on [SVO Node Location](3249-svo-node-location.md) by using the node location to index into the octree's data structures to fetch per-voxel attributes. It differs from [Octree Node Lookup by Voxel](5120-octree-node-lookup-by-voxel.md) by explicitly performing lighting calculations and handling the retrieval of both color and normal vectors, often storing the resulting color into a texture array for subsequent rendering stages.

## How it works
The method retrieves the color of a voxel from the octree data structure, applying lighting if the renderer is not in shadeless mode. It navigates the tree to find the leaf node containing the color data, extracts the normal and color, applies a directional light model, and stores the result.

### Inputs and Outputs
*   **Inputs**:
    *   Ray traversal state from [SVO Node Location](3249-svo-node-location.md), including hit position, node index, child index, and scale/level.
    *   Octree data structure (`octree.data`), containing packed node information, block info, and color/normal data.
    *   Uniform Buffer Object (UBO) or global parameters: `shadeless` flag, `ambientStrength`, `lightColor`, `lightPos`, `transformCount`, `pageBytes`, `blockInfoEnd`, `renderList.offsets`.
    *   Render context: `rc.n_x`, `rc.n_y`, `pixel_radius`, `frustum_width`.
*   **Outputs**:
    *   Final color vector (RGB) and alpha (1.0).
    *   In 4D variants, stored into a `texture_array` of size `rc.n_y * rc.n_x * 4`.

### Data Structures and Layouts
*   **Octree Data (`octree.data`)**: An array of `uint` (or `int`) values.
    *   **Page Header**: The upper bits of a node index (`node & 0xFFFFF800`) point to a page header in `octree.data`.
    *   **Block Info**: Located at `pageHeader + octree.data[pageHeader]`.
    *   **Attach Data**: Offset calculated as `int(blockInfo) + ubo.blockInfoEnd`.
    *   **Palette Node**: Located at `octree.data[attachData + int(node) - renderList.offsets[index] / 4 - 1]`.
    *   **Color Component**: Located at `attachOffset`, where `attachOffset = attachData + int(paletteNode >> 8) + bitCount(paletteNode & (1 << cidx) - 1)`. The value is a 24-bit RGB integer packed as `(R << 16) | (G << 8) | B`.
*   **Texture Array**: Unsigned char array of size `rc.n_y * rc.n_x * 4`. Layout is RGBA per pixel, contiguous. Index computed as `partial_index_in_texture_array + x * 4` where `partial_index_in_texture_array = y * (rc.n_y * 4)`.
*   **Transformation Matrix**: 16 floats read from `octree.data` at offset `int(renderList.offsets[index] + ubo.pageBytes) / 4 - ubo.transformCount * 4`. Constructed into a `mat4 octreeToWorld`.

### Steps
1.  **Extract Position and Tree State**:
    From the ray traversal result (`castRes`):
    ```python
    px = floatBitsToInt(castRes.pos.x)
    node = castRes.node
    cidx = castRes.childIdx
    level = castRes.scale
    ```

2.  **Calculate Page Header and Block Info**:
    ```python
    pageHeader = node & 0xFFFFF800
    blockInfo = pageHeader + octree.data[pageHeader]
    attachData = int(blockInfo) + ubo.blockInfoEnd
    ```

3.  **Get Palette Node**:
    ```python
    paletteNode = octree.data[attachData + int(node) - renderList.offsets[index] / 4 - 1]
    ```

4.  **Traverse to Color Leaf**:
    Loop while the current node does not have color (bit `cidx` is 0):
    ```python
    while ((int(paletteNode >> cidx) & 1) != 1):
        level += 1
        # Check bounds, update node, cidx, pageHeader, blockInfo, attachData, and paletteNode
        # This step involves navigating up or down the tree structure based on the specific SVO implementation.
        # If sources do not give the exact navigation logic for non-color nodes, it is assumed to follow standard SVO traversal rules.
        pass 
    ```
    *Note: In 4D variants, this step is part of a broader traversal loop checking `isTerminated()`, `dataLeafNodeHasBeenFound`, `nodeIsToSmall`, and `reachedMaxLevelToRender`.*

5.  **Extract RGB Color**:
    ```python
    c = int(octree.data[attachOffset]) # attachOffset calculated as above
    r = (c >> 16) & 0xFF
    g = (c >> 8) & 0xFF
    b = c & 0xFF
    # Normalize to [0, 1]
    octreeColor = vec3(r / 255.0, g / 255.0, b / 255.0)
    ```

6.  **Load Transformation and Normalize Normal**:
    ```python
    offset = int(renderList.offsets[index] + ubo.pageBytes) / 4 - ubo.transformCount * 4
    v = octree.data[offset : offset + 16] # Read 16 floats
    octreeToWorld = mat4(v)
    hitNormalWorld = normalize(octreeToWorld * vec4(castRes.normal, 0.0)).xyz
    ```
    *In 4D variants, the normal is retrieved directly from the leaf node data: `normal = normalize(tree->data_ptrs[treeTraverser.getCurrentNode()->data]->normal)`.*

7.  **Calculate Lighting**:
    If `ubo.shadeless == 1`, return `vec4(octreeColor, 1.0)`.
    Otherwise, apply directional lighting:
    ```python
    ambient = ubo.ambientStrength * vec3(ubo.lightColor)
    lightDir = normalize(vec3(ubo.lightPos))
    diffuse = max(dot(hitNormalWorld, lightDir), 0.0) * vec3(ubo.lightColor)
    color = (ambient + diffuse) * octreeColor
    ```
    *Alternative Formula (S1)*:
    Some implementations compute brightness using the dot product of the normalized normal and light direction:
    $$ \text{brightness} = \frac{\arccos\left( \frac{N_x}{128.0} L_x + \frac{N_y}{128.0} L_y + \frac{N_z}{128.0} L_z \right)}{\pi} $$
    Where $N$ is the voxel normal (stored as 8-bit integers divided by 128) and $L$ is the light direction.
    Final color components:
    $$ R = G = \text{unsigned int}(V_{\text{color}}[1] \times \text{brightness}) $$
    $$ B = \text{unsigned int}(V_{\text{color}}[0] \times \text{brightness}) $$
    Packed into `uint32_t` as `(R << 16) | (G << 8) | B`.

8.  **Store Result**:
    For 4D variants, store RGB and alpha=1 into `texture_array`:
    ```python
    texture_array[index] = (unsigned char)r
    texture_array[index+1] = (unsigned char)g
    texture_array[index+2] = (unsigned char)b
    texture_array[index+3] = (unsigned char)1
    ```

### Parameters
*   **Light Direction**: Typically defined as `{-0.039030f, -0.866792f, 0.497139f}` [S1, unofficial].
*   **Pixel Size Threshold**: Used to determine if a node is too small to render. Calculated as `pixel_radius * pixel_radius` where `pixel_radius = 0.5 * (frustum_width / rc.n_x)` [S3, unofficial].
*   **Max Level**: Maximum depth of the tree to traverse. Static member variable `LODColorTree4DRenderer::max_level` [S3, unofficial].
*   **Max Stack Size**: Maximum possible stack depth, calculated as `log(size) / log(2) + 1` where `size = max(tree->gridsize_T, tree->gridsize_S)` [S3, unofficial].

### Edge Cases and Pitfalls
*   **Precision**: Normal vectors stored as 8-bit integers require division by 128 for normalization. Floating-point precision issues may arise when converting between integer and float representations of normals.
*   **Boundaries**: Ensure `cidx` and `level` are within bounds during the palette node traversal loop.
*   **Shadeless Mode**: If `shadeless` is enabled, skip lighting calculations and return the raw octree color.
*   **Node Too Small**: If the projected size of the current node is less than or equal to the pixel size, terminate traversal for that pixel to avoid aliasing or unnecessary computation [S3, unofficial].

## Subtopics

### Hierarchical Octree Voxel Coloring
Starts with a low-resolution voxel structure and refines it to higher resolutions. This approach speeds up reconstruction by processing coarse data first. Processing time is approximately 15 seconds to generate a reconstruction with 3,256 voxels [S4, unofficial]. Unlike uniform resolution methods, it introduces a perceptual saliency component to represent information hierarchically [S4, unofficial].

## Operating characteristics
*   **Time Complexity**: Depends on the depth of the octree and the number of nodes traversed. Hierarchical variants reduce time by starting with low resolution [S4, unofficial].
*   **Memory Complexity**: Proportional to the number of voxels and the size of the octree data structure.
*   **Performance**: Approximately 15 seconds for 3,256 voxels in hierarchical variants [S4, unofficial].
*   **Strengths**: Efficient retrieval of color and normal data; supports lighting calculations; hierarchical refinement improves performance for large scenes [S4, unofficial].
*   **Limitations**: Requires careful handling of tree traversal and data layout; precision issues with normal storage [S1, unofficial].
*   **When to Use**: When lighting effects are required for voxel-based rendering and the scene has varying levels of detail.
*   **When Not to Use**: When shadeless rendering is sufficient, or when memory bandwidth is a critical bottleneck and lighting calculations can be deferred.

## Background
The method originates from sparse voxel octree rendering techniques, where color and normal data are stored in leaf nodes. The hierarchical variant was proposed by Prock and Dyer to speed up voxel coloring by starting with low resolution and refining [S4, unofficial]. The specific implementation details, such as the 4D traversal and texture array storage, are found in modern SVO renderers [S3, unofficial].
