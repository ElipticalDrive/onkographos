# Ray Casting with Octrees

Also called: AMR octree ray tracer, Octree Ray Tracing, Octree volume ray casting, Ray tracing directly on the octree structure, SVO Ray Marching, Tree based ray tracing

## Overview
Ray Casting with Octrees is a volume rendering technique that casts rays through an octree data structure to sample a 3D dataset, reconstructing data values along the ray for shader application [S1, unofficial]. It solves the problem of high memory costs and computing time associated with projecting Adaptive Mesh Refinement (AMR) or sparse voxel data onto a dense Cartesian grid [S3, unofficial]. Unlike standard mip projection which can be used for simple maximum density projections, this method explicitly traverses the octree structure, allowing for more complex shaders and AMR data handling [S1, unofficial]. It builds on [Sparse Voxel Octree Ray Traversal](2451-sparse-voxel-octree-ray-traversal.md) by performing ray casting directly on the octree structure without projecting to a Cartesian grid, avoiding high memory costs and computing time [S3, unofficial].

## How it works
**Inputs:** A 3D dataset (`ad`) representing the active domain containing values associated with octree cells, an octree data structure representing the spatial subdivision of the domain, a ray definition (origin and direction) for each pixel, and a shader function to apply to the extracted data vectors [S1, unofficial].

**Outputs:** A rendered image where each pixel value is the result of the shader applied to the data sampled along the corresponding ray [S1, unofficial].

**Data Structures:** An octree where internal nodes may represent groups of transparent voxels, minimizing the number of samples needed during accumulation [S2, unofficial]. A mapping from oct and cell index (in-memory index) to the index within the data source, computed once per domain [S1, unofficial].

**Algorithm Steps:**

1. **Preprocessing (Mapping):** Compute the mapping from oct and cell index (in-memory index) to the index within the data source (`ad`) [S1, unofficial].
2. **Ray Casting:** Cast a ray through the entire domain, yielding a list of oct and cell indices, as well as $t$-values (coordinate along the line of sight) for the intersections [S1, unofficial]. Find the coordinates of the intersections between the ray and the grid cells [S3, unofficial]. Traverse down the octree tree structure until every leaf cell intersected by the ray is found [S3, unofficial].
3. **Data Extraction:** Reconstruct the index of the data in the data source using the mapping from Step 1 [S1, unofficial]. Extract the data values corresponding to the intersected cells [S1, unofficial]. This produces two vectors: $t$ (distances along the ray) and `data` (values), both of size $k$ (where $k$ is the number of leaf cells intersected by the ray) [S1, unofficial]. The size differs per ray [S1, unofficial].
4. **Shading:** Apply a shader function to the extracted data vectors along the ray [S1, unofficial].
5. **Display:** Display the resulting image [S1, unofficial].

**Pseudocode:**

```python
def ray_cast_with_octrees(dataset, octree, rays, shader, background_color=0.0):
    """
    Render a volume using ray casting on an octree structure.
    
    Args:
        dataset: The active dataset object containing cell values.
        octree: The octree data structure.
        rays: A list or array of rays, each defined by origin and direction.
        shader: A function that takes an array of data values and returns a scalar.
        background_color: Value returned when a ray hits no leaf cells.
        
    Returns:
        An image array.
    """
    # Step 1: Compute mapping from oct/cell index to dataset index
    index_mapping = compute_index_mapping(octree, dataset)
    
    image = []
    
    for ray in rays:
        # Step 2: Cast ray through domain
        intersections = cast_ray_through_domain(ray, octree)
        
        # Step 3: Extract data
        t_values = []
        data_values = []
        
        for oct_idx, cell_idx, t_val in intersections:
            ds_idx = index_mapping.get((oct_idx, cell_idx))
            if ds_idx is not None:
                val = dataset[ds_idx]
                t_values.append(t_val)
                data_values.append(val)
                
        # Step 4: Apply shader
        if not data_values:
            pixel_value = background_color
        else:
            pixel_value = shader(data_values)
            
        image.append(pixel_value)
        
    return image

def compute_index_mapping(octree, dataset):
    """
    Compute the mapping from oct/cell index to dataset index.
    """
    mapping = {}
    # [G] Traverse octree nodes and record correspondence to dataset indices
    for oct_idx in octree.all_oct_indices():
        for cell_idx in octree.cells_in_oct(oct_idx):
            ds_idx = dataset.get_index_for(oct_idx, cell_idx)
            mapping[(oct_idx, cell_idx)] = ds_idx
    return mapping

def cast_ray_through_domain(ray, octree):
    """
    Cast a ray through the octree domain.
    Returns list of (oct_idx, cell_idx, t_value) for intersected leaf cells.
    """
    intersections = []
    # [G] Standard slab method to find ray bounds and step through cells
    # Handle negative directions by computing inverse direction
    inv_dir = [1.0 / d if d != 0.0 else float('inf') for d in ray.direction]
    
    # Compute intersection with domain bounding box
    t_min = max(
        (ray.origin[0] - octree.bounds[0][0]) * inv_dir[0],
        (ray.origin[1] - octree.bounds[0][1]) * inv_dir[1],
        (ray.origin[2] - octree.bounds[0][2]) * inv_dir[2]
    )
    t_max = min(
        (ray.origin[0] - octree.bounds[1][0]) * inv_dir[0],
        (ray.origin[1] - octree.bounds[1][1]) * inv_dir[1],
        (ray.origin[2] - octree.bounds[1][2]) * inv_dir[2]
    )
    
    if t_min > t_max or t_max < 0.0:
        return intersections
        
    # Traverse octree to find intersected leaf cells
    stack = [(octree.root, t_min, t_max)]
    while stack:
        node, t_enter, t_exit = stack.pop()
        if t_enter > t_exit:
            continue
            
        if node.is_leaf():
            # Intersect with leaf cell bounding box
            cell_t_enter = max(t_enter, max(
                (ray.origin[0] - node.cell_bbox[0][0]) * inv_dir[0],
                (ray.origin[1] - node.cell_bbox[0][1]) * inv_dir[1],
                (ray.origin[2] - node.cell_bbox[0][2]) * inv_dir[2]
            ))
            cell_t_exit = min(t_exit, min(
                (ray.origin[0] - node.cell_bbox[1][0]) * inv_dir[0],
                (ray.origin[1] - node.cell_bbox[1][1]) * inv_dir[1],
                (ray.origin[2] - node.cell_bbox[1][2]) * inv_dir[2]
            ))
            if cell_t_exit > cell_t_enter:
                intersections.append((node.oct_idx, node.cell_idx, cell_t_enter))
        else:
            # Push children to stack
            for child in node.children:
                child_t_enter = max(t_enter, max(
                    (ray.origin[0] - child.bbox[0][0]) * inv_dir[0],
                    (ray.origin[1] - child.bbox[0][1]) * inv_dir[1],
                    (ray.origin[2] - child.bbox[0][2]) * inv_dir[2]
                ))
                child_t_exit = min(t_exit, min(
                    (ray.origin[0] - child.bbox[1][0]) * inv_dir[0],
                    (ray.origin[1] - child.bbox[1][1]) * inv_dir[1],
                    (ray.origin[2] - child.bbox[1][2]) * inv_dir[2]
                ))
                if child_t_enter < child_t_exit:
                    stack.append((child, child_t_enter, child_t_exit))
                    
    return intersections
```

**Parameters:** A shader function applied to the data vectors along the ray, such as maximum intensity projection via `lambda data: data.max()` [S1, unofficial]. The resolution (e.g., $256^2$ pixels) determines the number of rays cast [S1, unofficial].

**Edge Cases and Pitfalls:** Low-order integration causes a boxy appearance at higher resolutions because interpolation is performed only along the line of sight, ignoring neighboring cell values [S1, unofficial]. This can be mitigated by using trilinear interpolation with vertex values obtained from ghost zones [S1, unofficial]. The initial implementation does not support sparse octrees, multiple domains, unselected leaf cells, or rays sent in negative directions (-x, -y, -z) [S1, unofficial].

## Subtopics

### [Algorithmic Multi-Octree Render](20634-algorithmic-multi-octree-render.md)
A rendering strategy for dynamic scenes that decouples static backgrounds from moving foreground assets using a multi-octree representation. It uses explicit ray-box intersections to pre-order ray intervals, allowing independent moving objects to be processed in their local canonical frames while guaranteeing mathematically correct multi-volume occlusion.

## Operating characteristics
*   **Time Complexity:** The computation time scales linearly with the number of pixels [S1, unofficial]. The algorithm scales as $O(N \log N)$, where $N$ is the number of octs in the whole domain; this is reducible to $O(n \log n)$ where $n$ is the number of octs in the active dataset [S1, unofficial].
*   **Memory Complexity:** Octrees provide more efficient memory usage for volume rendering compared to dense grids [S2, unofficial].
*   **Performance:** Rendering $256^2$ pixels on a dataset with 500,000 octs (~2,000,000 leaf cells) takes 3 seconds [S1, unofficial].
*   **Implementation Speed:** A Cython implementation of a single Hilbert lookup takes $4.34 \mu s \pm 164 ns$, while a Python implementation takes $187 \mu s \pm 8.98 \mu s$ (4x slower) [S1, unofficial].
*   **Strengths:** Avoids high memory cost and computing time associated with grid projection [S3, unofficial]. Allows for complex shaders and AMR data handling [S1, unofficial]. Minimizes the number of transparent voxels during accumulation [S2, unofficial].
*   **Limitations:** Low-order integration leads to a boxy appearance at high resolutions [S1, unofficial]. Initial implementation lacks support for sparse octrees, multiple domains, unselected leaf cells, and negative ray directions [S1, unofficial].

## Background
This method is implemented in the yt-project/yt repository for volume rendering of RAMSES AMR datasets [S1, unofficial]. It was developed to handle AMR data structures directly without projecting them to a Cartesian grid, which is computationally expensive for high-resolution datasets [S3, unofficial]. The approach leverages the hierarchical nature of octrees to efficiently traverse and sample sparse or adaptive data [S2, unofficial].
