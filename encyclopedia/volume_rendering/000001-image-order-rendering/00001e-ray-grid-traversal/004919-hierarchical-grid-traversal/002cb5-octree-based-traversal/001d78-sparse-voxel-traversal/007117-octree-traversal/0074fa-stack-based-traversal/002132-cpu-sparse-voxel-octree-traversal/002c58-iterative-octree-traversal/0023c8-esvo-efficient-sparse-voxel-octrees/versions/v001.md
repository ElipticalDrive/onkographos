# ESVO (Efficient Sparse Voxel Octrees)

Also called: Efficient Sparse Voxel Octree

## Overview
ESVO is a GPU-based ray casting algorithm that uses a Sparse Voxel Octree (SVO) to reduce voxel storage costs and enable real-time rendering of large scenes [S2]. It sets itself apart from sibling methods by using a compact 4-byte node encoding with a depth-first (z-curve) memory layout, which optimizes for localized memory access patterns on the GPU [S1, unofficial]. Unlike [Hierarchical Ray Marching](5238-hierarchical-ray-marching.md) which may use larger leaf nodes or different traversal strategies, ESVO relies on a near 1:1 port of the original implementation with specific pointer encoding changes to facilitate buffer-less tree construction [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A Sparse Voxel Octree structure representing the voxel scene, camera parameters (origin, direction, near/far planes), and optionally a lower-resolution distance image for beam optimization.
- Output: A rendered image (color and/or depth) for the given camera view.

**Data Structures:**
The SVO consists of nodes stored in a linear array.
- **Node Layout**: Each node is 4 bytes (32 bits) [S1, unofficial].
- **Content**: The node contains pointers to child nodes and potentially voxel data (density/color) if it is a leaf. The exact bit-field layout for children vs. data is not fully specified in the provided notes, but the total size is fixed at 4 bytes [S1, unofficial].
- **Pointer Encoding**:
    - Pointers are relative [S1, unofficial].
    - "Backwards" relative pointers are used, meaning parent nodes appear after their children in the memory layout. This allows the tree to be built without intermediate buffers [S1, unofficial].
    - Far pointers (pointing to nodes outside the immediate local range) are signaled by a reserved upper range of pointer values, rather than using a dedicated bit flag [S1, unofficial].
- **Memory Layout**: The nodes are stored in a depth-first order, resulting in a Z-curve (Morton code) layout [S1, unofficial]. This locality helps mitigate memory bandwidth issues despite the small node size [S1, unofficial].

**Algorithm Steps:**
1. **Beam Optimization (Optional)**: If enabled, render a lower-resolution distance image first [S2].
2. **Ray Initialization**: For each pixel, compute the ray origin and direction [S2].
3. **Ray Start Adjustment**: If beam optimization was performed, adjust the ray's starting position based on the distance image to skip empty space and begin marching closer to surfaces [S2].
4. **Octree Traversal**:
    - Start at the root node.
    - Use a DDA-like approach to traverse the octree [S1, unofficial].
    - At each node, determine which child (if internal) or voxel (if leaf) the ray intersects.
    - Update the ray position and continue traversal until a leaf is reached or the ray exits the scene [S1, unofficial].
    - Note: The traversal involves ascending and descending the tree, which can require many iterations [S1, unofficial].
5. **Voxel Sampling**: At leaf nodes, sample the voxel data (density/color) and accumulate the result along the ray [S2].
6. **Image Composition**: Composite the accumulated color and depth into the final image [S2].

    return image

**Parameters:**
- **Beam Optimization**: Boolean flag to enable/disable the two-pass rendering [S2].
- **Node Size**: Fixed at 4 bytes [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Performance**: The traversal can be slow due to the many iterations required to ascend and descend the tree and advance positions by DDA [S1, unofficial].
- **Memory Bandwidth**: Although nodes are small (4 bytes), the performance can be underwhelming on integrated GPUs due to memory bandwidth limitations [S1, unofficial].
- **Pointer Encoding**: The use of "backwards" relative pointers and reserved upper ranges for far pointers requires careful implementation to avoid invalid memory accesses [S1, unofficial].

## Operating characteristics
- **Time Complexity**: Traversal time depends on the scene density and tree depth. Editing cost is approximately $O(\log m)$, leveraging path copying for persistent data structures [S1, unofficial].
- **Memory Complexity**: Memory cost is approximately 4 bytes per node [S1, unofficial].
- **Measured Performance**:
    - On Sponza 2k (499k * $8^3$ voxels) on an integrated GPU:
        - Primary rays: 95.0 Mrays/s [S1, unofficial].
        - Primary + 1 diffuse bounce: 66.2 Mrays/s [S1, unofficial].
        - Iterations per ray: 46.9 [S1, unofficial].
        - Clocks per iteration: 148.3 [S1, unofficial].
    - On Eco House 2k (448k * $8^3$ voxels) on an integrated GPU:
        - Primary rays: 67.1 Mrays/s [S1, unofficial].
        - Primary + 1 diffuse bounce: 52.7 Mrays/s [S1, unofficial].
        - Iterations per ray: 147.1 [S1, unofficial].
        - Clocks per iteration: 147.1 [S1, unofficial].
    - On Forest Lake 2k (807k * $8^3$ voxels) on an integrated GPU:
        - Primary rays: 60.6 Mrays/s [S1, unofficial].
        - Primary + 1 diffuse bounce: 31.4 Mrays/s [S1, unofficial].
        - Iterations per ray: 119.7 [S1, unofficial].
        - Clocks per iteration: 101.1 [S1, unofficial].
- **Scaling**: Performance is expected to improve 5-10x on real hardware compared to integrated GPUs [S1, unofficial].
- **Strengths**: Low memory footprint (4 bytes/node), localized memory access (Z-curve layout), supports real-time rendering [S2].
- **Limitations**: High iteration count due to tree traversal overhead, performance sensitive to memory bandwidth [S1, unofficial].
- **When to use**: Suitable for real-time rendering of large voxel scenes where memory bandwidth is not the primary bottleneck and a compact representation is needed [S2].
- **When not to use**: When higher throughput is required and memory bandwidth is limited, or when the scene is primarily smooth surfaces where other octree traversal methods might perform better [S1, unofficial].

## Background
ESVO was proposed by Samuli Laine and Tero Karras in 2010 [S2]. It was designed to address the high storage costs of dense voxel representations and to enable real-time ray casting on the GPU [S2]. The method has been implemented and analyzed in various contexts, including the VoxelRT repository [S1, unofficial].
