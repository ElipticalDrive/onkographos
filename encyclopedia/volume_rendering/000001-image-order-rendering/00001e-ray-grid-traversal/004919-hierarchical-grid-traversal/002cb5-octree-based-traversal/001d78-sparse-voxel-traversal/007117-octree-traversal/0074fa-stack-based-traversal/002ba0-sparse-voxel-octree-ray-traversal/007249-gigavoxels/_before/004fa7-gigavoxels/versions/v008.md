# GigaVoxels

Also called: Dynamic Sparse Octree, GigaVoxels rendering, GigaVoxels: A Voxel-Based Rendering Pipeline For Efficient Exploration Of Large And Detailed Scenes, Ray-Guided Streaming, Sparse Voxel Octree with Hierarchical Volume Ray-Casting, Voxel Ray-Tracing with GPU Cache

## Overview
GigaVoxels is a real-time voxel-based rendering pipeline designed for the efficient exploration of large and detailed scenes containing billions of voxels [S1, S4, S6, unofficial]. It solves the problem of rendering volumetric data that exceeds GPU memory capacities by using a sparse voxel octree data structure, GPU caching, and ray-guided streaming to load only the necessary data at the required resolution [S1, S4, unofficial]. Unlike sibling methods such as [Sparse Voxel Octree Ray Traversal](2451-sparse-voxel-octree-ray-traversal.md) which may assume static or fully resident data, GigaVoxels employs a hybrid update/ray-casting process where the GPU feeds back data usage requests to manage an out-of-core cache, enabling dynamic subdivision and streaming with minimum CPU intervention [S2][S3, unofficial]. It differs from view-independent structures by continuously adapting resolution based on view and occlusion, ensuring smooth temporal transitions and inherent anti-aliasing via cone tracing [S4, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** Sparse voxel data (static or procedural), camera parameters (position, projection), transfer functions (for color/opacity), and optional procedural definitions (e.g., noise functions, distance fields).
*   **Outputs:** Final 2D image (color and alpha), data usage requests (subdivision/loading) for the cache manager.

**Data Structures:**
1.  **Sparse Voxel Mipmap Pyramid (SVMP):** A hierarchy of voxel data.
    *   **Nodes:** Part of a Generalized N3-tree (octree) for space partitioning and empty space compaction [S1, unofficial]. Nodes point to either a 'brick' or a constant value for homogeneous regions [S6, unofficial]. Sibling nodes are stored adjacently; children are accessed via the pointer to the first child [S6, unofficial].
    *   **Bricks:** Low-resolution regular grids of voxels, typically $8^3$ [S5, unofficial]. Non-leaf nodes own bricks to allow mip-mapping [S6, unofficial]. Bricks store opacity, color, and normal information [S1, unofficial].
    *   **Brick Pool:** A separate storage area for bricks, managed by the cache [S6, unofficial].
2.  **GPU Cache:**
    *   Implements an LRU (Least Recently Used) mechanism to maintain temporal coherence [S1, unofficial].
    *   **Cache Elements:** Structure containing 'Oldest' and 'Newest' pointers, 'Usage sorted nodes addresses', and a 'Used nodes mask' [S3, unofficial].
    *   **Implementation:** Uses 3D textures for reading and bound surfaces for writing data [S1, unofficial].
    *   **Stream Compaction:** Used to concatenate the Octree/Bricks Pool and manage the 'New data Stream' of newly accessed elements [S3, unofficial].

**Algorithm Steps:**

1.  **Ray Traversal and LOD Selection:**
    *   For each pixel, a ray is cast into the scene [S3, unofficial].
    *   The ray traverses the sparse voxel octree. A KD-restart algorithm is used to descend the node tree without stack usage until the desired level of detail is reached [S6, unofficial].
    *   **Cone Tracing:** To determine the intersected maximum voxel size, the method uses approximate cone tracing based on the radius of the cone footprint defined by the eye and pixel extent [S5, unofficial]. This determines the appropriate LOD level [S4, unofficial].
    *   **Descent Criterion:** The traversal continues if the node does not meet the descent criterion (e.g., if it is not a leaf or if higher resolution is needed) [S1, unofficial].

2.  **Brick Marching and Accumulation:**
    *   Once a brick is reached, the ray marches through the voxels within the brick [S6, unofficial].
    *   **Hardware Filtering:** Tri-linear interpolation is used for semi-transparent volumes [S2].
    *   **Accumulation:** Color and alpha are accumulated using front-to-back rendering [S3, unofficial]. The emission/absorption model for each ray is:
        $$ C = \text{Color intensity} + \text{Alpha} $$
        (Specifically, the standard front-to-back compositing equation is implied by the accumulation logic described in [S1, unofficial] and [S3, unofficial]).
    *   **Termination:** Marching terminates when the volume becomes opaque (e.g., accumulated alpha $\ge 0.98$) or when a stop criterion is met [S1, unofficial][S2]. This accounts for intravolume occlusion [S2].

3.  **Data Usage Feedback and Streaming:**
    *   During traversal, the ray records information about traversed octree nodes [S2].
    *   If visited nodes are not present at the correct resolution (missing bricks or un-subdivided nodes), the ray returns a **subdivision request** or **data loading request** instead of just a color value [S2].
    *   These requests are sent to the **Central Memory/Cache Manager** [S1, unofficial].

4.  **Cache Management and Production:**
    *   The Cache Manager handles structure updates and loads data from mass storage or the GPU cache [S1, unofficial].
    *   **Subdivision:** If a node needs subdivision, a GPU kernel is launched (1 block/node, 1 thread/child_node) to test if children are inside the object (e.g., analytically for a sphere) and write new nodes to the cache [S1, unofficial].
    *   **Brick Production:** If a brick is needed, a GPU kernel (1 block/brick) is launched to populate the voxels (user-defined producer) and write them to the data cache [S1, unofficial].
    *   **Data Loading Modes:** Data can be loaded level-by-level (coarse to fine) for speed or directly at max resolution for quality [S1, unofficial].

5.  **Shading:**
    *   Standard Blinn-Phong illumination is computed per sample [S3, unofficial].
    *   Normals are derived on-the-fly using finite differences or stored directly [S3, unofficial].
    *   For opaque objects, deferred shading is used [S3, unofficial].

**Pseudocode:**

```python
# Simplified representation of the GigaVoxels rendering loop and cache interaction

def gigavoxels_render(camera, scene_producer):
    # 1. Initialize Cache Manager (LRU, 3D textures)
    cache = CacheManager()
    
    # 2. For each pixel/ray
    for pixel in screen_pixels:
        ray = cast_ray(camera, pixel)
        accumulated_color = vec4(0.0)
        accumulated_alpha = 0.0
        
        # 3. Traverse Octree
        node = scene_root
        while node is not None:
            # Determine LOD based on cone footprint
            lod_level = get_cone_aperture(ray, node)
            
            # Check if node is in cache
            if not cache.contains(node.id, lod_level):
                # Request subdivision/loading
                request = cache.request_subdivision(node.id, lod_level)
                if request.type == SUBDIVISION:
                    # GPU Kernel: Subdivide node
                    # Input: node.id, lod_level
                    # Output: child nodes in cache
                    gpu_subdivide_node(node.id, lod_level, scene_producer)
                elif request.type == BRICK_LOAD:
                    # GPU Kernel: Load/Produce Brick
                    # Input: node.id, lod_level
                    # Output: brick voxels in cache
                    gpu_produce_brick(node.id, lod_level, scene_producer)
            
            # Get node from cache
            node = cache.get_node(node.id, lod_level)
            
            # If node is a leaf (brick) or homogeneous
            if node.is_leaf or node.is_homogeneous:
                # March through brick
                step_size = get_step_size(ray, lod_level)
                while ray_t < node.boundary_end:
                    voxel = sample_brick(node.brick, ray.position)
                    color = voxel.color
                    alpha = voxel.alpha
                    
                    # Front-to-back accumulation
                    # C = C_prev + (1 - A_prev) * C_voxel
                    # A = A_prev + (1 - A_prev) * A_voxel
                    weight = (1.0 - accumulated_alpha) * alpha
                    accumulated_color += weight * color
                    accumulated_alpha += weight
                    
                    # Stop if opaque
                    if accumulated_alpha >= 0.98:
                        break
                    
                    ray.position += ray.direction * step_size
                
                break # Brick traversal done
            else:
                # Descend to child
                # Children are stored adjacently
                child_index = get_child_index(ray, node)
                node = node.children[child_index]
        
        # 4. Write result
        pixel.color = accumulated_color

def gpu_subdivide_node(node_id, lod_level, producer):
    # Kernel: 1 block per node, 1 thread per child
    child_id = get_child_id(node_id, lod_level)
    if producer.is_inside(child_id):
        cache.write_node(child_id, lod_level)

def gpu_produce_brick(node_id, lod_level, producer):
    # Kernel: 1 block per brick
    brick = producer.generate_voxels(node_id, lod_level)
    cache.write_brick(brick)
```

**Parameters:**
*   **Cone Aperture:** Modifiable via `getConeAperture()` to adjust the trade-off between quality and performance [S1, unofficial].
*   **Stop Criterion:** e.g., `accumulatedColor.w >= 0.98f` [S1, unofficial].
*   **Descent Criterion:** Used during visit traversal to decide when to stop descending [S1, unofficial].
*   **Brick Pool Size:** Adjustable to match hardware capabilities; smaller pools consume less video memory but store fewer bricks [S6, unofficial].
*   **CUDA Compute Capability:** Requires SM at least 2.0 [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Aliasing:** Occurs because pixel value should be defined by integration along a cone, not just ray accumulation. Addressed by mipmapping and cone tracing [S4, unofficial].
*   **Popping:** Discrete mipmap levels can cause popping. Addressed by smooth transitions and continuous adaptation [S4, unofficial].
*   **Memory Budget:** The method respects limited GPU memory by streaming, but out-of-core rendering is essential for vast worlds [S6, unofficial].

## Subtopics

### [Distributed Multi-Level Out-Of-Core Volume Rendering](6238-distributed-multi-level-out-of-core-volume-rendering.md)
Distributed Multi-Level Out-Of-Core Volume Rendering is a distributed image-order rendering technique designed to visualize volume datasets significantly larger than the aggregate memory of a GPU cluster, targeting scalable high-resolution display arrays. It solves the problem of out-of-core data access by combining a multi-level cache hierarchy (GPU texture memory, CPU RAM, and distributed shared memory) with a display-aware LOD selection mechanism that bounds the working set size. Unlike sibling methods such as GigaVoxels which stream data to a single GPU, this method distributes the volume across cluster nodes, using a unique data management scheme to relocate bricks between nodes based on view transformation, thereby avoiding the data replication required by systems like Vol-a-Tile or Volume Visualizer.

### [Dense 3D Texture Voxelization](7286-dense-3d-texture-voxelization.md)
Dense 3D Texture Voxelization is an alternative to GigaVoxels [GigaVoxels](3057-gigavoxels.md) where the entire scene, including empty space, is encoded into a very large mip-mapped 3D texture. It solves the problem of sparse data management by replacing the explicit octree structure with an implicit one derived from the texture's mipmap levels. Unlike GigaVoxels, which uses a dynamic sparse octree to stream only necessary data, this method relies on direct world-space indexing and automatic hardware filtering, trading memory efficiency for implementation simplicity.

## Operating characteristics
*   **Time Complexity:** Real-time to interactive rates (20-90 fps) on current generation hardware [S4, unofficial]. Complexity depends on the number of visible voxels and the depth of the octree traversal.
*   **Memory Complexity:** Out-of-core. Memory usage is bounded by the GPU cache size (brick pool + node pool) and the visible working set [S6, unofficial]. It respects limited GPU memory budgets [S4, unofficial].
*   **Performance:** Achieves rendering of billions of voxels (e.g., $8192^3$ for 3D scans, $16384^3$ for hypertextured meshes) [S4, unofficial].
*   **Strengths:**
    *   Handles scenes larger than GPU memory [S4, unofficial].
    *   Inherent anti-aliasing via cone tracing and mipmapping [S4, unofficial].
    *   Smooth temporal transitions and view-dependent LOD [S4, unofficial].
    *   Efficient handling of semi-transparent volumes [S2].
    *   Supports procedural generation and complex effects (soft shadows, depth of field) via mipmapping [S3, unofficial].
*   **Limitations:**
    *   Requires GPU Compute Capability 2.0 or higher [S1, unofficial].
    *   Mipmapping increases memory consumption and makes tree updates more challenging [S4, unofficial].
    *   Out-of-core rendering is essential but adds complexity to data management [S6, unofficial].
*   **When to use:** Real-time exploration of large, detailed voxel scenes, scientific visualization of massive datasets, procedural generation of complex environments.
*   **When not to use:** Scenes with very small, sparse details that do not benefit from hierarchical streaming, or when hardware does not support the required CUDA capabilities.

## Background
GigaVoxels was introduced in 2009 by Chabert, Neyret, Lefebvre, and Eisemann in the paper "Ray-Guided Streaming for Efficient and Detailed Voxel Rendering" (I3D 2009) [S4, S3, unofficial]. It was developed as a dynamic sparse octree approach to render complex scenes consisting of billions of voxels in real time [S2]. The method builds on earlier work in sparse voxel octrees [LHN05a] and brick maps [LKS*06], combining them with a GPU-based cache and ray-guided streaming mechanism [S4, unofficial]. It differs from view-independent structures by continuously adapting resolution, making discontinuities disappear and ensuring smooth temporal transitions [S4, unofficial]. It was further detailed in subsequent presentations and library documentation (e.g., Guehl and Neyret, 2013) [S1, unofficial].
