# N^3-Tree with Mipmapped Bricks

Also called: GigaVoxels Improved, Hybrid Structure

## Overview
This method renders large volumetric datasets by combining an adaptive $N^3$-tree (a generalized octree) with mipmapped 3D texture bricks, enabling high-quality filtering and efficient GPU traversal [S1]. It distinguishes itself from earlier GigaVoxels implementations by storing a single pointer per node in a 3D texture block rather than eight child pointers and neighbor pointers, reducing memory usage by 16 times and improving cache coherence [S1].

## How it works
### Inputs and Outputs
*   **Inputs:** A volumetric dataset, a camera position, and a view direction. The structure consists of a Node Pool (3D texture) and a Brick Pool (3D texture) [S1].
*   **Outputs:** A 2D image with accumulated color and opacity [S1].

### Data Structures
The structure is mirrored on the CPU for updates but rendered entirely on the GPU [S1].

**1. Node Pool**
A 3D texture storing all tree nodes [S1]. It is organized into blocks of $N^3$ nodes [S1]. A single pointer accesses all children of a node due to this grouping [S1].

**2. Node Data Structure (64 bits total)**
Each node is stored as a 64-bit value with the following layout [S1]:
*   **Bits 0–29 (30 bits):** Child pointer. Used for non-leaf nodes. Value `0` indicates no children exist [S1].
*   **Bit 30 (1 bit):** Refinement flag. Indicates if the node is refined to maximum or if the original volume contains more data [S1].
*   **Bit 31 (1 bit):** Content type. `0` indicates a constant RGBA8 value (e.g., empty or core regions); `1` indicates the content is described by a brick [S1].
*   **Bits 32–63 (32 bits):** Payload. If Content Type is Brick: 30 bits for a pointer to an $M^3$ brick in the Brick Pool [S1]. If Content Type is Constant: 32 bits representing the average constant value (4 $\times$ 8 bits for RGBA8) [S1].

**3. Brick Pool**
A large 3D texture storing the voxel data [S1]. Bricks are small voxel grids of predefined size $M^3$ (typically $M=32$) [S1]. The pool is limited in size; the algorithm ensures bricks of all visible leaf nodes are present in the pool, updating content as the viewpoint changes [S1].

### Algorithm Steps

**1. Initialization**
Rasterize proxy geometry to deliver ray origins and directions to the fragment shader [S1]. Compute entry and exit points of the ray in the volume's bounding box using a pre-rendering pass with alpha blending (front-facing depth in luminance, back-facing depth inverted in alpha) or tiling two depth buffers [S1].

**2. Iterative Descent (Traversal)**
Recursive DDA is inefficient on GPUs due to lack of fast indexable memory; thus, an iterative descent is used [S1].
1.  Start at the ray origin [S1].
2.  Locate the current point $x$ in the $N^3$-tree top-down [S1].
3.  Calculate the offset to the child node: $offset = \lfloor x \cdot N \rfloor$, where $x \in [0, 1]^3$ is the point's local coordinate in the bounding box and $N$ is the branching factor [S1].
4.  Fetch the child node at index $c + offset$, where $c$ is the pointer to the current node's children block [S1].
5.  Update the local coordinate: $x_{new} = x \cdot N - offset$ [S1].
6.  Repeat steps 2–5 until a node with the appropriate Level of Detail (LOD) is reached [S1]. The LOD is determined in the shader such that a voxel projects to at most one pixel; this node is not necessarily a leaf [S1].

**3. Node Processing**
*   **Constant Node:** If the reached node indicates a constant value, integrate the value analytically along the distance traversed within the node [S1].
*   **Brick Node:** If the node contains a brick, perform standard ray-marching through the $M^3$ brick data using quadrilinear filtering (mipmapping) until the ray leaves the current node's spatial extent [S1].
*   **Next Step:** Use the new position (where the ray exited the current node) as the origin for the next descent [S1].

**4. Rendering**
The ray-casting is performed using one big fragment shader for both top-down traversal and brick sampling, which proved more efficient than separate passes [S1].

### Pseudocode
```python
def render_volume(ray_origin, ray_direction, entry_t, exit_t, node_pool, brick_pool, N, M):
    current_ptr = 0  # Root pointer
    current_local = normalize(ray_origin)  # [G] Normalize to [0,1]^3 relative to volume bounds
    t = entry_t
    accumulated_color = vec4(0.0)
    accumulated_alpha = 0.0

    while t < exit_t:
        temp_ptr = current_ptr
        temp_local = current_local

        # Iterative descent to find appropriate LOD node
        while True:
            offset = floor(temp_local * N)
            node_val = node_pool.fetch(temp_ptr + offset)
            child_ptr = node_val & 0x3FFFFFFF
            is_brick = (node_val >> 31) & 1

            # [G] Standard LOD check: node spatial extent <= pixel footprint
            # (Implementation detail handled by shader hardware)
            if True:
                break
            if child_ptr == 0:  # Leaf reached
                break

            # Descent step
            temp_ptr = child_ptr
            temp_local = temp_local * N - offset

        # Process node
        if is_brick:
            brick_ptr = (node_val >> 32) & 0x3FFFFFFF
            # [G] Ray-AABB intersection for node's local bounds [0,1]^3
            node_exit_t = t + 1.0 / max(abs(ray_direction))
            # [G] Standard ray-marching through M^3 brick data with quadrilinear filtering
            step = (node_exit_t - t) / M
            brick_color = vec4(0.0)
            brick_alpha = 0.0
            pos_t = t
            for _ in range(M):
                local_brick_coord = (pos_t - t) / step
                sample = brick_pool.sample(brick_ptr, local_brick_coord)
                brick_color += sample * (1.0 - brick_alpha)
                brick_alpha += sample.a * (1.0 - brick_alpha)
                pos_t += step
            accumulated_color += brick_color * (1.0 - accumulated_alpha)
            accumulated_alpha += brick_alpha * (1.0 - accumulated_alpha)
            t = node_exit_t
        else:
            # Constant value integration
            val = vec4(float(node_val & 0xFF), float((node_val >> 8) & 0xFF),
                       float((node_val >> 16) & 0xFF), float((node_val >> 24) & 0xFF))
            # [G] Ray-AABB intersection for node's local bounds [0,1]^3
            node_exit_t = t + 1.0 / max(abs(ray_direction))
            dist = node_exit_t - t
            accumulated_color += val * dist * (1.0 - accumulated_alpha)
            accumulated_alpha += dist * (1.0 - accumulated_alpha)
            t = node_exit_t

    return accumulated_color
```

### Parameters
*   **Branching Factor $N$:** The number of children per node is $N^3$. $N=2$ is a standard octree. Trade-off: low $N$ for memory efficiency (deep tree), large $N$ for traversal efficiency (shallow tree) [S1].
*   **Brick Size $M$:** The side length of the voxel grid in a brick. Typically $M=32$ [S1].

### Edge Cases and Pitfalls
*   **Recursive DDA:** Recursive DDA traversal is inefficient on GPUs due to lack of fast indexable memory in shader processors. The iterative descent is used instead [S1].
*   **LOD Determination:** The traversal does not need the structure to indicate correct level-of-details (as done in previous work like Gobbetti et al.). The LOD is determined in the shader, which minimizes update operations [S1].
*   **Neighbor Pointers:** The structure does not exhibit neighbor pointers between adjacent nodes. An efficient traversal remains possible without them due to the iterative descent and cache coherence [S1].

## Operating characteristics
*   **Time Complexity:** Traversal is efficient due to the iterative descent and hardware texture caching. The cost is dominated by ray-marching within bricks and the overhead of re-descending the tree for each node exit [S1].
*   **Memory Complexity:** Memory requirements are largely reduced compared to Gobbetti et al. [GMAG08] because only a single pointer is used per node (stored in a 3D texture block) instead of eight child pointers and neighbor pointers, reducing storage by 16 times [S1].
*   **Performance:** The method enables high-quality filtering via mipmapping and efficient GPU rendering [S1].
*   **Strengths:** High memory efficiency, cache coherence, high-quality filtering, unified rendering and visibility on GPU [S1].
*   **Limitations:** Limited brick pool size requires careful management and updates as viewpoint changes [S1].

## Background
The method was introduced in the "GigaVoxels" paper by Laine et al. [S1]. It builds upon the concept of adaptive space subdivision and $N^3$-trees (similar to [LHN05a]) [S1]. The specific "Improved" variant with mipmapped bricks and the single-pointer node structure was presented to address the memory and cache inefficiencies of earlier GigaVoxels implementations [S1].
