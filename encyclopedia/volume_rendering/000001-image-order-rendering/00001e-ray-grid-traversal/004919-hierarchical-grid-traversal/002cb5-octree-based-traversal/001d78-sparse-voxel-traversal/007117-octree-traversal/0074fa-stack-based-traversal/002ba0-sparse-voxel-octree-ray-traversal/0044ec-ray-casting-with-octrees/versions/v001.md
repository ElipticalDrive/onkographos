# Ray Casting with Octrees

Also called: AMR octree ray tracer, Octree Ray Tracing, Octree volume ray casting, Ray tracing directly on the octree structure, SVO Ray Marching, Tree based ray tracing

## Overview
Ray Casting with Octrees is a volume rendering technique that casts rays through an octree data structure to sample a 3D dataset, reconstructing data values along the ray for shader application [S1, unofficial]. It solves the problem of high memory costs and computing time associated with projecting Adaptive Mesh Refinement (AMR) or sparse voxel data onto a dense Cartesian grid [S3, unofficial]. Unlike standard mip projection which can be used for simple maximum density projections, this method explicitly traverses the octree structure, allowing for more complex shaders and AMR data handling [S1, unofficial]. It builds on [Sparse Voxel Octree Ray Traversal](2451-sparse-voxel-octree-ray-traversal.md) by providing a specific algorithmic implementation for direct traversal without grid projection.

## How it works
**Inputs:**
*   A 3D dataset (`ad`) representing the active domain, containing values associated with octree cells.
*   An octree data structure representing the spatial subdivision of the domain.
*   A ray definition (origin and direction) for each pixel.
*   A shader function to apply to the extracted data vectors.

**Outputs:**
*   A rendered image where each pixel value is the result of the shader applied to the data sampled along the corresponding ray.

**Data Structures:**
*   **Octree:** A hierarchical structure where nodes represent spatial volumes. Internal nodes may represent groups of transparent voxels, minimizing the number of samples needed during accumulation [S2, unofficial].
*   **Mapping:** A mapping from oct and cell index (in-memory index) to the index within the data source (`ad`). This mapping is computed once per domain [S1, unofficial].

**Algorithm Steps:**

1.  **Preprocessing (Mapping):** Compute the mapping from oct and cell index (in-memory index) to the index within the data source (`ad`). This step is performed once per domain [S1, unofficial].
2.  **Ray Casting:** Cast a ray through the entire domain. This yields a list of oct and cell indices, as well as $t$-values (coordinate along the line of sight) for the intersections [S1, unofficial].
    *   Find the coordinates of the intersections between the ray and the grid cells [S3, unofficial].
    *   Traverse down the octree tree structure until every leaf cell intersected by the ray is found [S3, unofficial].
3.  **Data Extraction:** Reconstruct the index of the data in the data source using the mapping from Step 1. Extract the data values corresponding to the intersected cells. This produces two vectors: $t$ (distances along the ray) and `data` (values), both of size $k$ (where $k$ is the number of leaf cells intersected by the ray). The size differs per ray [S1, unofficial].
4.  **Shading:** Apply a shader function to the extracted data vectors along the ray. For example, a maximum intensity projection can be implemented as `lambda data: data.max()` [S1, unofficial].
5.  **Display:** Display the resulting image [S1, unofficial].

**Pseudocode:**

```python
def ray_cast_with_octrees(dataset, octree, rays, shader):
    """
    Render a volume using ray casting on an octree structure.
    
    Args:
        dataset: The active dataset object containing cell values.
        octree: The octree data structure.
        rays: A list or array of rays, each defined by origin and direction.
        shader: A function that takes an array of data values and returns a scalar.
        
    Returns:
        An image array.
    """
    # Step 1: Compute mapping from oct/cell index to dataset index
    # This is done once per domain.
    # Note: The exact implementation of this mapping depends on the specific 
    # octree representation (e.g., Hilbert ordering).
    index_mapping = compute_index_mapping(octree, dataset)
    
    image = []
    
    for ray in rays:
        # Step 2: Cast ray through domain
        # Yields list of (oct_index, cell_index, t_value)
        intersections = cast_ray_through_domain(ray, octree)
        
        # Step 3: Extract data
        # Reconstruct indices and get values
        t_values = []
        data_values = []
        
        for oct_idx, cell_idx, t_val in intersections:
            # Map to dataset index
            ds_idx = index_mapping[oct_idx, cell_idx]
            # Extract value from dataset
            val = dataset[ds_idx]
            t_values.append(t_val)
            data_values.append(val)
            
        # Step 4: Apply shader
        # If no intersections, handle appropriately (e.g., background color)
        if not data_values:
            pixel_value = background_color
        else:
            pixel_value = shader(data_values)
            
        image.append(pixel_value)
        
    return image

def compute_index_mapping(octree, dataset):
    """
    Compute the mapping from oct/cell index to dataset index.
    Implementation detail: This typically involves traversing the octree 
    and storing the correspondence between the tree structure and the 
    flat dataset array.
    """
    mapping = {}
    # Traverse octree and populate mapping
    # [G] Specific traversal logic depends on octree implementation (e.g., recursive descent)
    for oct_idx in octree.all_oct_indices():
        for cell_idx in octree.cells_in_oct(oct_idx):
            ds_idx = dataset.get_index_for(oct_idx, cell_idx)
            mapping[(oct_idx, cell_idx)] = ds_idx
    return mapping

def cast_ray_through_domain(ray, octree):
    """
    Cast a ray through the octree domain.
    Returns list of (oct_idx, cell_idx, t_value) for intersected leaf cells.
    """
    intersections = []
    # Find initial intersection with domain bounds
    t_min, t_max = ray.intersect_domain_bounds()
    
    # Traverse octree
    # [G] Standard octree ray traversal algorithm
    # Start from root, descend to leaves intersected by ray
    current_nodes = [octree.root]
    t_current = t_min
    
    while current_nodes:
        next_nodes = []
        for node in current_nodes:
            # Check intersection of ray with node bounding box
            t_enter, t_exit = ray.intersect_box(node.bbox)
            
            if t_exit < t_current:
                continue
                
            if node.is_leaf():
                # Intersect with leaf cell
                # [G] Assuming leaf cells are axis-aligned boxes
                cell_t_enter, cell_t_exit = ray.intersect_box(node.cell_bbox)
                if cell_t_exit > t_current:
                    intersections.append((node.oct_idx, node.cell_idx, cell_t_enter))
                    t_current = cell_t_exit
            else:
                # Add children to traversal
                next_nodes.extend(node.children)
                
        current_nodes = next_nodes
        
    return intersections
```

**Parameters:**
*   **Shader:** A function applied to the data vectors along the ray. Example: maximum intensity projection `lambda data: data.max()` [S1, unofficial].
*   **Resolution:** The number of pixels (e.g., $256^2$) determines the number of rays cast.

**Edge Cases and Pitfalls:**
*   **Boxy Appearance:** Low-order integration causes a boxy appearance at higher resolutions because interpolation is performed only along the line of sight, ignoring neighboring cell values [S1, unofficial]. This can be mitigated by using trilinear interpolation with vertex values obtained from ghost zones [S1, unofficial].
*   **Sparse Octrees:** The initial implementation does not support sparse octrees [S1, unofficial].
*   **Multiple Domains:** The initial implementation does not support multiple domains [S1, unofficial].
*   **Unselected Leaf Cells:** The initial implementation does not handle leaf cells that are not selected [S1, unofficial].
*   **Negative Directions:** The initial implementation does not support rays sent in negative directions (-x, -y, -z) [S1, unofficial].

## Subtopics

### [Algorithmic Multi-Octree Render](20634-algorithmic-multi-octree-render.md)
A rendering strategy for dynamic scenes that decouples static backgrounds from moving foreground assets using a multi-octree representation. It uses explicit ray-box intersections to pre-order ray intervals, allowing independent moving objects to be processed in their local canonical frames while guaranteeing mathematically correct multi-volume occlusion.

## Operating characteristics
*   **Time Complexity:** The computation time scales linearly with the number of pixels. The algorithm scales as $O(N \log N)$, where $N$ is the number of octs in the whole domain; this is reducible to $O(n \log n)$ where $n$ is the number of octs in the active dataset [S1, unofficial].
*   **Memory Complexity:** Octrees provide more efficient memory usage for volume rendering compared to dense grids [S2, unofficial].
*   **Performance:** Rendering $256^2$ pixels on a dataset with 500,000 octs (~2,000,000 leaf cells) takes 3 seconds [S1, unofficial].
*   **Implementation Speed:** A Cython implementation of a single Hilbert lookup takes $4.34 \mu s \pm 164 ns$, while a Python implementation takes $187 \mu s \pm 8.98 \mu s$ (4x slower) [S1, unofficial].
*   **Strengths:** Avoids high memory cost and computing time associated with grid projection [S3, unofficial]. Allows for complex shaders and AMR data handling [S1, unofficial]. Minimizes the number of transparent voxels during accumulation [S2, unofficial].
*   **Limitations:** Low-order integration leads to a boxy appearance at high resolutions [S1, unofficial]. Initial implementation lacks support for sparse octrees, multiple domains, unselected leaf cells, and negative ray directions [S1, unofficial].

## Background
This method is implemented in the yt-project/yt repository for volume rendering of RAMSES AMR datasets [S1, unofficial]. It was developed to handle AMR data structures directly without projecting them to a Cartesian grid, which is computationally expensive for high-resolution datasets [S3, unofficial]. The approach leverages the hierarchical nature of octrees to efficiently traverse and sample sparse or adaptive data [S2, unofficial].
