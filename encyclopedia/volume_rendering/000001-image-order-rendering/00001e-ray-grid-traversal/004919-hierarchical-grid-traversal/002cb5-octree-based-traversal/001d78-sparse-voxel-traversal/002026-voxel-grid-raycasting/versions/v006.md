# Voxel Grid Raycasting

Also called: DDA Ray Tracing, Ray Marching through Voxel Grid, Uniform Grid Raycasting, Voxel Ray Tracing with Voxel Marching, Voxel-Volume-Raycasting, Voxelization Raycasting, raycastVoxels

## Overview
Voxel Grid Raycasting is a rendering technique that stores scene geometry in a 3D voxel grid and traces rays through the grid by stepping from voxel to voxel to determine intersections and surface normals [S1, S2, S5, unofficial]. It solves the problem of efficiently determining ray-voxel intersections without performing explicit geometric intersection tests against primitives [S2, unofficial]. Unlike hierarchical methods such as [Sparse Voxel Traversal](1525-sparse-voxel-traversal.md) or [Octree Traversal](1587-octree-traversal.md) which skip empty space using tree structures, this method assumes a uniform grid and traverses every voxel boundary along the ray path, making it simpler to implement but potentially slower in sparse scenes [S2, S3, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** Ray origin $O$, ray direction $D$ (normalized), voxel grid dimensions ($W, H, D$), voxel size $v_{size}$, and the voxel data buffer.
*   **Outputs:** Hit position, hit voxel coordinates, surface normal, and optionally material/color data.

**Data Structures:**
The voxel grid is typically stored in a 1D array or buffer.
*   **Layout (Standard):** A 1D array `blocks` of size $W \times H \times D$. Indexing is calculated as $index = (x \cdot H + z) \cdot W + y$ or similar permutations depending on memory layout [S2, unofficial].
*   **Layout (Chunked):** A 1D storage buffer `voxels: array<u32>`. Each `u32` represents a single voxel. The index is calculated as $index = x + y \cdot W + z \cdot (W \cdot H)$, where $W$ is chunk width and $H$ is chunk height [S1, unofficial]. A value of `0u` indicates an empty voxel; non-zero values indicate occupied voxels, often encoding color via `unpack4x8unorm` [S1, unofficial].

**Algorithm Steps:**
The traversal uses a Digital Differential Analyzer (DDA) approach [S2, S3, unofficial].

1.  **Initialization:**
    *   Normalize ray direction: $ray = \text{normalize}(ray\_end - ray\_start)$ [S2, unofficial].
    *   Calculate starting voxel coordinates: $current\_voxel = \lfloor ray\_start / v_{size} \rfloor$ [S2, unofficial].
    *   Determine step directions for each axis: $step_i = \text{sign}(ray_i)$ [S1, S2, unofficial].
    *   Calculate distance to traverse one full voxel width: $tDelta_i = v_{size} / |ray_i|$ [S1, S2, unofficial].
    *   Calculate distance to the next voxel boundary:
        $$tMax_i = \frac{(current\_voxel_i + step_i) \cdot v_{size} - ray\_start_i}{ray_i}$$
        If $ray_i = 0$, set $tMax_i = \infty$ (or `FLT_MIN` in implementation to exclude from min-check) [S2, unofficial].
    *   Handle negative ray direction edge case: If the ray starts in a voxel different from the target end voxel and moves in a negative direction, decrement the corresponding voxel coordinate to ensure correct traversal start [S2, unofficial].

2.  **Traversal Loop:**
    While the ray has not exited the grid bounds and no hit is found:
    *   Find the axis with the minimum $tMax$: $axis = \text{argmin}(tMax_x, tMax_y, tMax_z)$ [S1, unofficial].
    *   Increment the grid position on that axis: $current\_voxel_{axis} += step_{axis}$ [S1, unofficial].
    *   Update the distance traveled: $dist = tMax_{axis}$ [S1, unofficial].
    *   Advance the $tMax$ for that axis to the next boundary: $tMax_{axis} += tDelta_{axis}$ [S1, unofficial].
    *   **Intersection Check:** Load voxel data at $current\_voxel$. If occupied:
        *   Calculate surface normal using the axis of entry: $normal = axis\_dir\_normal(axis, ray\_dir)$ [S1, unofficial].
        *   Return hit data (position, normal, voxel index) [S1, S5, unofficial].

3.  **Ray Bouncing (Optional):**
    *   If a hit is found, spawn a new ray from $start\_pos + dist \cdot ray\_dir + \epsilon \cdot normal$ to prevent self-intersection [S1, unofficial].
    *   Re-initialize traversal state for the new ray [S1, unofficial].
    *   Repeat until max bounces or ray leaves scene [S1, unofficial].

**Pseudocode:**
```python
def raycast_voxel_grid(ray_origin, ray_direction, voxel_grid, voxel_size, grid_dims):
    # 1. Normalize and prepare
    ray = normalize(ray_direction)
    bin_size = voxel_size
    
    # 2. Initial voxel position
    current_voxel = floor(ray_origin / bin_size)
    
    # 3. Step directions
    step = vec3(1 if ray.x >= 0 else -1, 
                1 if ray.y >= 0 else -1, 
                1 if ray.z >= 0 else -1)
    
    # 4. Calculate tMax and tDelta
    # Distance to next boundary
    next_boundary = (current_voxel + step) * bin_size
    
    # Avoid division by zero for axis-aligned rays
    t_delta = vec3(
        bin_size / ray.x if ray.x != 0 else float('inf'),
        bin_size / ray.y if ray.y != 0 else float('inf'),
        bin_size / ray.z if ray.z != 0 else float('inf')
    )
    
    t_max = vec3(
        (next_boundary.x - ray_origin.x) / ray.x if ray.x != 0 else float('inf'),
        (next_boundary.y - ray_origin.y) / ray.y if ray.y != 0 else float('inf'),
        (next_boundary.z - ray_origin.z) / ray.z if ray.z != 0 else float('inf')
    )
    
    # 5. Traverse
    while is_within_bounds(current_voxel, grid_dims):
        # Check occupancy
        if voxel_grid[current_voxel] != 0:
            # Hit found
            axis = argmin(t_max)
            normal = get_normal_for_axis(axis)
            hit_pos = ray_origin + t_max[axis] * ray
            return HitResult(position=hit_pos, normal=normal, voxel=current_voxel)
        
        # Advance to next voxel
        axis = argmin(t_max)
        t_max[axis] += t_delta[axis]
        current_voxel[axis] += step[axis]
        
    return None
```

**Parameters:**
*   `voxel_size`: Physical size of each voxel (e.g., 0.1 world units) [S1, unofficial].
*   `epsilon`: Small offset (e.g., $voxel\_size \times 0.01$) to prevent self-intersection when spawning new rays [S1, unofficial].
*   `max_dist`: Maximum ray length before termination [S1, S5, unofficial].

**Edge Cases and Pitfalls:**
*   **Zero Ray Component:** If a ray component is 0, $tMax$ and $tDelta$ are set to infinity (or `FLT_MIN` in some implementations to effectively remove the axis from comparison) to avoid division by zero [S2, unofficial].
*   **Negative Direction Start:** Explicit adjustment of `current_voxel` is required if the ray starts in a voxel that is not the 'last' voxel and moves negatively, ensuring traversal coordinates align with the entry point [S2, unofficial].
*   **Out of Bounds:** The traversal must check bounds after every step. If the ray leaves the defined grid, it breaks and returns miss/sky color [S1, unofficial].

## Subtopics

### [Voxel-Cell Duality Mapping](2240-voxel-cell-duality-mapping.md)
Voxel-Cell Duality Mapping is a technique for ray tracing isosurfaces defined within cells of 8 voxels using an octree that stores scalar values at voxel centers. It establishes a dual relationship between voxels and cells by logically shifting scalar positions backward by half a voxel width, allowing the ray tracer to intersect 8-voxel cell primitives defined by the stored leaf values. Unlike methods that expand storage to hold complete cell data, this method retrieves forward neighbors at intersection time, maintaining single scalar storage per leaf.

### [Spherical Volume Ray Walking](3865-spherical-volume-ray-walking.md)
Spherical Volume Ray Walking is a fast voxel traversal algorithm for rendering volumetric data defined on a spherical coordinate grid. It extends the cartesian fast voxel traversal method by Amanatides and Woo to non-cartesian grids, iterating through radial, polar, and azimuthal voxel boundaries to determine the sequence of voxels intersected by a ray. Unlike [Voxel Grid Raycasting](2218-voxel-grid-raycasting.md) which assumes axis-aligned bounding boxes, this method handles the curved boundaries of spherical sectors, using line-sphere intersection for radial steps and 2D segment intersection for angular boundaries.

### [Plane Marching](3959-plane-marching.md)
Plane Marching is a raymarching technique for voxel grids that advances a ray by stepping to the nearest intersection with the integer grid planes separating voxel layers. It solves the problem of traversing a dense voxel volume to find the first solid voxel by checking occupancy at each plane boundary. Unlike shape-assisted siblings such as [Sphere Assisted Raymarching](3865-sphere-assisted-raymarching.md) or [Optimised Voxel Ray Marching](4240-optimised-voxel-ray-marching.md), it does not store auxiliary distance fields or shape metadata, relying solely on the geometric structure of the grid. This makes it simple to implement but fragile in empty space, as it never skips more than one voxel per step.

### [RLE4 Ray Tracing](5228-rle4-ray-tracing.md)
RLE4 Ray Tracing is a ray-marching algorithm designed to traverse volume data compressed using Run-Length Encoding (RLE) in the Y-dimension, specifically structured as a "Map4" layout. It solves the problem of efficiently locating the first occupied voxel along a ray or coloring a voxel based on its position within sparse volumetric data. It distinguishes itself from sibling methods by avoiding full decompression of the volume; instead, it uses a texture-based lookup system to determine if a sample point lies in an uncompressed surface region, an "inside" region, or an "outside" region, returning special markers for the latter two. This approach is particularly suited for scenarios where the volume geometry is sparse or has large uniform interior/exterior regions, allowing the renderer to skip volumetric integration in those areas.

### [Sparse Shadow Volume Raycast](5632-sparse-shadow-volume-raycast.md)
A hierarchical raycasting algorithm that traverses a sparse shadow volume texture to find the first intersection with a shadow-casting volume. It dynamically adjusts its traversal step size and level of detail (LOD) based on occupancy bits, allowing it to skip empty space efficiently compared to fixed-step hierarchical variants. It differs from siblings such as [Voxel-Cell Duality Mapping](2240-voxel-cell-duality-mapping.md), [Spherical Volume Ray Walking](3865-spherical-volume-ray-walking.md), [Plane Marching](3959-plane-marching.md), [RLE4 Ray Tracing](5228-rle4-ray-tracing.md), [Regular Grid Traversal](5939-regular-grid-traversal.md), [Voxel Raytracer](6403-voxel-raytracer.md), and [DirectVoxGO Volume Rendering](6412-directvoxgo-volume-rendering.md) by using a multi-level occupancy-bit search that refines or coarsens traversal granularity on the fly.

### [Regular Grid Traversal](5939-regular-grid-traversal.md)
Regular Grid Traversal is a ray-scene intersection acceleration technique that partitions the scene's Axis-Aligned Bounding Box (AABB) into a fixed-size 3D grid of uniform cells (voxels). It solves the problem of $O(N)$ ray-primitive intersection tests by allowing rays to skip empty cells, testing only primitives stored in intersected voxels . Unlike hierarchical structures (e.g., BVH, Octree) that partition primitives into disjoint sets, the Regular Grid partitions space into disjoint sub-blocks, meaning a single primitive can belong to multiple cells . It is distinguished by its constant-time cell access, simple traversal logic, and suitability for dynamic scenes due to its linear build time, though it suffers from high memory overhead in sparse scenes .

### [Voxel Raytracer](6403-voxel-raytracer.md)
A voxel raytracer renders 3D voxel models by marching rays through a 3D grid of voxels, supporting multiple bounces for diffuse reflection and a ground plane. It differs from standard voxel grid raycasting by implementing a full path-tracing loop with diffuse scattering and anti-aliasing, rather than simple direct illumination or single-pass raymarching.

### [DirectVoxGO Volume Rendering](6412-directvoxgo-volume-rendering.md)
DirectVoxGO is a volume rendering method that accelerates neural radiance field training and inference by sampling points directly on a structured voxel grid rather than uniformly along rays. It solves the problem of inefficient ray marching in sparse scenes by using a mask cache to skip free space and a direct lookup of density and color features from the voxel grid. It sets itself apart from standard NeRF by replacing uniform sampling with grid-based point selection and from other sparse voxel methods by using a dense voxel grid with a binary mask cache for acceleration.

### [Voxel Grid Accelerated Ray-Point Intersection](16937-voxel-grid-accelerated-ray-point-intersection.md)
This method accelerates the identification of the $k$ nearest points within a cylinder of radius $\delta$ around a query ray in a point cloud, specifically optimized for parallel GPU execution and dynamic scenes where the point cloud changes frequently. Unlike static acceleration structures such as octrees, which require $O(n \log n)$ construction time, this voxel grid approach achieves $O(n)$ construction, making it superior for inverse rendering and dynamic scenarios where the structure must be rebuilt every iteration.

### Voxel Resolve Search
A search algorithm used by voxel resolve and GI update to find the pixel's voxel again in the brick named by the visibility buffer [S7, unofficial]. It finds the cell holding the ray's point at the stored depth, then the two cells along each axis whose centers lie nearest that point (which hold the point regardless of rounding), stopping at the first cell whose hit gives the stored depth again, bit for bit [S7, unofficial]. A voxel's test depends only on the ray and the voxel, ensuring every pass meets it at the same t [S7, unofficial].

### Narrow Band Voxelization
A narrow band strategy that does not use any solver [S8]. When the algorithm reaches a narrow band voxel, it immediately returns a hit, resulting in a voxelization of the scene [S8].

### Dense Octree Accelerated Raymarching
An acceleration structure using a dense octree stored in a 3D texture to skip empty space during ray traversal [S9, unofficial]. The raymarcher first traverses the octree texture; once it hits a leaf node (occupied octant), it switches to the fine-grained voxel texture for detailed collision detection [S9, unofficial]. The octree is stored as a 3D texture (`texture_3d<u32>`), with data for different levels interleaved in the Z dimension [S9, unofficial]. The 3D texture approach is significantly faster for ray traversal than linear buffers with Morton curve ordering because graphics hardware is optimized for spatially local texture access [S9, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of voxels intersected by the ray. In the worst case (ray passing through the entire grid), this is proportional to the grid dimension in the ray's direction.
*   **Memory Complexity:** $O(W \times H \times D)$ for the voxel grid storage.
*   **Performance:** Fast for dense, uniform volumes. Performance degrades significantly in sparse scenes compared to hierarchical methods like [Sparse Voxel Traversal](1525-sparse-voxel-traversal.md) because it cannot skip empty space [S2, unofficial].
*   **Strengths:** Simple implementation, no build time for acceleration structures, constant-time access to any voxel, suitable for dynamic scenes where the grid changes frequently [S2, S6, unofficial].
*   **Limitations:** High memory usage for large sparse volumes, inability to skip empty space, precision issues near voxel boundaries if not handled carefully (e.g., epsilon offsets) [S1, S2, unofficial].
*   **When to use:** Dense voxel data, real-time applications with limited preprocessing time, or when the scene is fully occupied [S2, unofficial].
*   **When not to use:** Sparse scenes, large worlds with significant empty space, or when memory bandwidth is a bottleneck [S2, unofficial].

## Background
The method is based on the Digital Differential Analyzer (DDA) algorithm for ray traversal, originally described by Amanatides and Woo in 1987 [S3, unofficial]. It is widely used in voxel-based games (e.g., *Teardown*, *Minecraft* rendering optimizations) and real-time ray tracing demos [S1, unofficial]. The distinction between Voxel-Volume-Raycasting and general Volume-Raycasting is that voxels are defined as integer-coordinate functions $f: \mathbb{N}^3 \to U$, whereas general volume raycasting may use floating-point sampling and interpolation [S3, unofficial].
