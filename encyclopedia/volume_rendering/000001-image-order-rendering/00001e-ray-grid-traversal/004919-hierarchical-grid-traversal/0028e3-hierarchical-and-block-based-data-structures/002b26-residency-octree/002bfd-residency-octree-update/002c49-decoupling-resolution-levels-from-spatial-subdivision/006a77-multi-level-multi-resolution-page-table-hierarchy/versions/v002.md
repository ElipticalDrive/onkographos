# Multi-level, multi-resolution page table hierarchy

Also called: Multi-Level, Multi-Resolution Page Tables, Orthogonal page table hierarchy, Separate page tables per resolution, Single-Level

## Overview
This method decouples the down-sampling ratio of volume data from the hierarchy level count for address translation scalability [S1]. Unlike single-level page tables or tree structures where traversal depth and data resolution are coupled, it employs a separate page table hierarchy for each resolution level, allowing independent optimization of rendering quality and memory scalability [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** Ray sample position $(x, y, z)$, current ray direction, desired resolution level $L$ (determined by projected screen size), and the multi-resolution page directory structure resident in GPU memory [S1].
*   **Output:** Physical address of the voxel brick containing the sample, allowing access to the voxel data cache texture [S1].

**Data Structures:**
The structure consists of two orthogonal hierarchies: the resolution hierarchy (data resolutions) and the page table hierarchy (page table resolutions) [S1].
1.  **Resolution Hierarchy:** A set of discrete resolution levels $L \in \{0, 1, \dots, N_{res}\}$ [S1].
2.  **Page Table Hierarchy:** For each resolution level $L$, a tree of page tables [S1].
    *   **Multi-Resolution Page Directory:** The top-level page table for each resolution level [S1]. It is an array of pointers, one entry per resolution level [S1]. This is the only structure required to be resident in GPU memory [S1].
    *   **Page Tables:** Virtualized structures below the directory that map virtual page indices to physical brick indices [S1]. One or more additional levels of page tables are added to each resolution level [S1].
    *   **Cache Textures:**
        *   **Voxel Cache Texture:** Stores active voxel bricks [S1]. All bricks, regardless of resolution level, must have the same physical resolution (number of voxels) to share this single texture [S1].
        *   **Page Table Cache Texture:** Stores active page table bricks (the virtualized page tables) [S1].

**Address Layout:**
A virtual address is decomposed into fields [S1]. Let $B_v$ be the brick size in voxels for data, and $B_p$ be the brick size in entries for page tables [S1].
1.  **LOD Selection:** Determine resolution level $L$ based on sample distance or projected size [S1].
2.  **Directory Lookup:** Access the $L$-th entry in the Multi-Resolution Page Directory to get the root of the page table hierarchy for level $L$ [S1].
3.  **Page Table Traversal:** Traverse the page table hierarchy for level $L$ [S1].
    *   Let the virtual address be $A$.
    *   For each level $k$ in the page table hierarchy (from top to bottom):
        *   Extract the page index $P_k$ from $A$ using bit shifts/masks determined by $B_p$ [S1].
        *   Look up $P_k$ in the current page table brick [S1].
        *   If the entry is valid, proceed to the next level [S1].
        *   If invalid, a page fault occurs (handled by CPU/GPU driver to load the page table brick into the Page Table Cache Texture) [S1].
4.  **Voxel Lookup:** The final page table entry provides the physical brick index. Combine this with the offset within the brick (derived from the lower bits of $A$) to index into the Voxel Cache Texture [S1].

**Pseudocode:**
```python
# Constants (values not given in the sources)
NUM_RES_LEVELS = 4
PAGE_TABLE_DEPTH = 2
B_V = 16  # Brick size in voxels for data bricks
B_P = 1024  # Brick size in entries for page table bricks

# Resident Data (only multi_res_page_directory is resident in GPU memory [S1])
multi_res_page_directory = [None] * NUM_RES_LEVELS
voxel_cache_texture = None  # Texture storing active voxel bricks [S1]
page_table_cache_texture = None  # Texture storing active page table bricks [S1]

# Cached State (per ray)
cached_res_level = -1
cached_page_table_ptrs = [None] * PAGE_TABLE_DEPTH

def translate_address(sample_pos):
    # 1. LOD Selection: Determine resolution level L based on projected screen size [S1]
    lod = sample_pos.z / 100.0  # Standard operation: compute based on distance/screen size

    # 2. Look-up Caching: Exploit spatial coherence [S1]
    if lod == cached_res_level and cached_page_table_ptrs[0] is not None:
        current_ptr = cached_page_table_ptrs[0]
        start_level = 1
    else:
        current_ptr = multi_res_page_directory[lod]
        cached_res_level = lod
        start_level = 0
        cached_page_table_ptrs = [None] * PAGE_TABLE_DEPTH

    # 3. Address Decomposition & Page Table Traversal [S1]
    virtual_address = sample_pos.x * 1000000 + sample_pos.y * 1000 + sample_pos.z  # Standard linearization

    for level in range(start_level, PAGE_TABLE_DEPTH):
        # Extract page index P_k from virtual_address using bit shifts/masks determined by B_P
        page_index = (virtual_address >> (level * 10)) & (B_P - 1)

        # Load page table brick if not in cache
        page_table_brick = page_table_cache_texture.lookup(current_ptr, page_index)

        entry = page_table_brick[page_index]

        if entry.is_valid:
            if level < PAGE_TABLE_DEPTH - 1:
                current_ptr = entry.pointer_to_next_level
                cached_page_table_ptrs[level] = current_ptr
            else:
                physical_brick_index = entry.physical_brick_index
                break
        else:
            # Page fault: Load required page table brick into page_table_cache_texture
            page_table_cache_texture.fetch_and_store(current_ptr, page_index)
            # Retry logic required in practice
            raise Exception("PageFaultException")

    # 4. Voxel Lookup
    brick_offset = virtual_address & (B_V**3 - 1)
    voxel_data = voxel_cache_texture[physical_brick_index][brick_offset]
    return voxel_data
```

**Parameters:**
*   **Brick Size (Voxel):** All active voxel bricks must have the same physical resolution (e.g., $16 \times 16 \times 16$ voxels) to share the single cache texture [S1].
*   **Brick Size (Page Table):** Can be chosen independently of voxel brick size [S1].
*   **Page Table Levels:** Two levels support volumes up to several hundred terabytes; three levels are sufficient for exa-scale data [S1].

**Edge Cases and Pitfalls:**
*   **Precision:** Virtual address bit-width must be sufficient to address the entire volume space across all resolution levels [G].
*   **Cache Coherence:** The page table cache texture must be kept coherent with the resident directory [G].
*   **Degenerate Input:** If a ray sample falls outside the volume bounds, address translation should fail gracefully or return a transparent value [G].

## Subtopics

### Single-Level, Multi-Resolution Page Tables
The simpler variant where each resolution level has only one page table level. It is easier to implement but scales poorly to very large data compared to the multi-level variant. Use when data size is moderate and implementation simplicity is prioritized. See [Single-Level, Multi-Resolution Page Tables](5252-single-level-multi-resolution-page-tables.md).

### Hash Tables
An alternative address translation structure using spatial hashing. Not discussed in detail here but mentioned as an alternative for GPU-based translation. See [Hash Tables](5253-hash-tables.md).

## Operating characteristics
*   **Time Complexity:** Address translation is $O(D)$ where $D$ is the page table depth (typically 2-3) [G]. Due to spatial coherence, the number of actual texture lookups for page tables is very low, as cached pointers are reused across samples along a ray [S1].
*   **Memory Complexity:** The resident memory is proportional to the number of resolution levels (size of the multi-resolution page directory) [S1]. Virtualized page tables are loaded on demand [S1].
*   **Performance:** Scales well to extreme-scale data (hundreds of terabytes to exabytes) [S1]. The performance difference between single-level and multi-level page tables is negligible due to caching [S1].
*   **Strengths:** Decouples resolution quality from traversal scalability. Supports very large datasets. Efficient caching due to coherence [S1].
*   **Limitations:** Requires two cache textures (voxel and page table). More complex implementation than single-level page tables [G].
*   **When to Use:** Rendering extreme-scale volume data (e.g., electron microscopy) where single-level page tables or octrees are insufficient for scalability [S1].
*   **When Not to Use:** Small to moderate datasets where simpler structures suffice [G].

## Background
The multi-level, multi-resolution page table hierarchy was described by Hadwiger et al. [HBJP12] and used for rendering extreme-scale electron microscopy data [BHL* 11, HBJP12]. It addresses the limitations of single-level page tables and tree structures by completely decoupling the address translation hierarchy from the multi-resolution rendering hierarchy. This allows independent optimization of data down-sampling (for quality) and page table size reduction (for scalability) [S1].
