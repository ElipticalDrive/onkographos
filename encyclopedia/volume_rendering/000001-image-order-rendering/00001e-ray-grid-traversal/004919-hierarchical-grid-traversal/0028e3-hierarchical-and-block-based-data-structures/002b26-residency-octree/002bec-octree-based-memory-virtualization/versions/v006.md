# Octree-based memory virtualization

Also called: Crassin et al. Octree-based memory virtualization, Interactive Visualization via Memory Mapping

## Overview
An out-of-core rendering approach for multi-channel volume datasets where octree nodes and bricks store information on up to $n$ channels [S1, unofficial]. It solves the problem of limited physical memory by using OS-level memory mapping to load only the parts of the data structure actually rendered during tree traversals [S2, unofficial]. Unlike the [Residency Octree](4950-residency-octree.md), which decouples cache residency from spatial subdivision and allows partial subtree residency, this method enforces that the whole subtree is resident in the cache for high-resolution rendering, leading to a higher memory footprint and worse performance for multiple channels [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Multi-channel volume dataset stored on disk; octree structure defining spatial subdivision; current camera view and rendering parameters.
*   **Output:** Rendered image with alpha-blended channels.

**Data Structures:**
*   **Octree Nodes:** Store pointers to bricks and culling metadata. For multi-channel data, a node is marked homogeneous only if its corresponding bricks in *all* channels are homogeneous [S1, unofficial].
*   **Bricks:** Store voxel data for up to $n$ channels.
*   **Memory Mapping:** Binary data files are mapped to virtual memory using the OS-provided `mmap` function [S2, unofficial].

**Parameters:**
*   **$n$ (Number of channels):** Implementation-defined and cannot be changed at run-time. In practice, limited to 4 because GPU texture formats are limited to four components [S1, unofficial].

**Steps:**
1.  **Memory Mapping:** Map the binary data files containing the octree and bricks to virtual memory using `mmap` [S2, unofficial].
2.  **Tree Traversal:** Traverse the octree from the root.
    *   If the current frame-rate is too low, smoothly increase the minimum regular splat size $\delta_r$ and minimum boundary splat size $\delta_b$ [S2, unofficial].
    *   For each child of the current node:
        *   If the child does not pass culling tests, ignore it [S2, unofficial].
        *   Calculate $S$, the screen size of the bounding sphere of the child [S2, unofficial].
        *   If the child is a leaf node, render it as a splat (implementation detail not fully specified in sources, but implied by "TetSplat" context) [S2, unofficial].
        *   If the child is not a leaf, recursively traverse it [S2, unofficial].
3.  **Homogeneous Optimization:** If a node corresponds to homogeneous bricks (all voxels contain the same value up to a user-defined threshold), store the average value in the brick instead of a pointer to the brick’s location in the brick cache [S1, unofficial].
4.  **Channel Mixing:** Combine multiple channels using accumulation-level intermixing (alpha blending) [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Channel Limit:** The number of channels $n$ is limited to 4 due to GPU texture format constraints [S1, unofficial].
*   **Homogeneity Check:** A node can only be marked homogeneous if its corresponding bricks in *all* channels are homogeneous [S1, unofficial].
*   **Occlusion:** Image-level intermixing (alpha blending) cannot handle occlusions between different channels correctly due to missing depth information in accumulated intermediate results [S1, unofficial].

## Subtopics

### [Octree-based out-of-core volume rendering](5171-octree-based-out-of-core-volume-rendering.md)
Extends this method to support multiple visible channels by storing pointers and culling metadata in each node. Unlike the [Residency Octree](4950-residency-octree.md), it enforces whole subtree residency, leading to higher memory footprint and worse performance for multiple channels.

### [Virtual Memory Volume Rendering](16077-virtual-memory-volume-rendering.md)
Uses a virtual memory scheme with arbitrary packing and no pre-computed 3D hierarchy, avoiding the need to hold the entire path from leaf to root in GPU memory.

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Depends on the number of nodes and bricks actually traversed and rendered. Memory mapping allows efficient use of physical memory by only loading parts of the data structure [S2, unofficial].
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Progressive loading gives fast recursive refinements due to breadth-first storage [S2, unofficial].
*   **Strengths:** Efficient use of physical memory; fast recursive refinements; supports multi-channel data.
*   **Limitations:** Higher memory footprint and worse performance for multiple channels compared to the [Residency Octree](4950-residency-octree.md); limited to 4 channels; cannot handle occlusions between channels correctly [S1, unofficial].
*   **When to use:** When rendering multi-channel volume datasets that exceed available texture memory and interactive exploration is required.
*   **When not to use:** When occlusions between channels are critical or when more than 4 channels are needed.

## Background
Originated with Crassin et al. [CNLE09] and extended by Brix et al. [BPH14] for multi-channel data. Implemented in Voreen [DLJL22] [S1, unofficial].
