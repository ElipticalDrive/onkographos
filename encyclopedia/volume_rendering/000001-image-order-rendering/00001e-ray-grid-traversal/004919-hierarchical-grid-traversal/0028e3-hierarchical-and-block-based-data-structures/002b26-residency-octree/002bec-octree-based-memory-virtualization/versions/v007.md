# Octree-based memory virtualization

Also called: Crassin et al. Octree-based memory virtualization, Interactive Visualization via Memory Mapping

## Overview
Octree-based memory virtualization is an out-of-core rendering technique for multi-channel volume datasets that utilizes operating system memory mapping to load octree nodes and bricks on demand [S1, unofficial][S2, unofficial]. It distinguishes itself from sibling methods like [Residency Octree](4950-residency-octree.md) by enforcing full subtree residency in the cache for high-resolution rendering, whereas the Residency Octree allows partial subtree residency [S1, unofficial]. Unlike [Virtual Memory Volume Rendering](16077-virtual-memory-volume-rendering.md), which uses a multi-resolution page table hierarchy to avoid pre-computed 3D hierarchies, this method relies on an explicit octree structure [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Multi-channel volume dataset stored on disk; octree structure where nodes and bricks store information for up to $n$ channels.
*   **Output:** Rendered image with channels mixed via alpha blending.

**Data Structures:**
*   **Octree Nodes:** Store culling metadata and pointers to bricks. For multi-channel data, a node is marked homogeneous only if its corresponding bricks in *all* channels are homogeneous [S1, unofficial].
*   **Bricks:** Store voxel data for up to $n$ channels.
*   **Homogeneous Optimization:** If a brick is homogeneous (all voxels contain the same value up to a user-defined threshold), the node stores the average value of the brick instead of a pointer to the brick’s location in the brick cache [S1, unofficial].

**Parameters:**
*   **$n$ (Number of Channels):** Implementation-defined and cannot be changed at run-time [S1, unofficial]. In practice, limited to 4 because GPU texture formats are limited to four components [S1, unofficial].

**Algorithm Steps:**
1.  **Memory Mapping:** Map the binary data files containing the octree and bricks to virtual memory using the OS-provided `mmap` function [S2, unofficial]. This avoids loading the entire structure into physical memory, ensuring efficient use of physical memory by only loading parts actually rendered during tree traversals [S2, unofficial].
2.  **Tree Traversal:** Traverse the octree. Since the trees are stored breadth-first, this progressive loading enables fast recursive refinements [S2, unofficial].
3.  **Culling:** For each child of the current node, perform culling tests. Ignore children that do not pass [S2, unofficial].
4.  **Homogeneity Check:** Determine if the current node's bricks are homogeneous across all $n$ channels [S1, unofficial].
5.  **Data Access:**
    *   If homogeneous: Retrieve the stored average value [S1, unofficial].
    *   If not homogeneous: Load the brick from the mapped virtual memory into the brick cache [S1, unofficial][S2, unofficial].
6.  **Rendering:** Render the leaf nodes (e.g., as splats or rays) using the loaded data [S2, unofficial].
7.  **Adaptive Refinement:** If the current frame rate is too low, smoothly increase the minimum regular splat size ($\delta_r$) and minimum boundary splat size ($\delta_b$) to reduce rendering load [S2, unofficial].

**Pseudocode:**
```python
def render_volume_octree(root_node, n_channels):
    # Map files to virtual memory using OS mmap
    virtual_memory = os_mmap(data_files)
    
    # Global parameters for adaptive refinement
    delta_r = initial_min_regular_splat_size
    delta_b = initial_min_boundary_splat_size
    
    traverse_tree(root_node, virtual_memory, n_channels, delta_r, delta_b)

def traverse_tree(node, virtual_memory, n_channels, delta_r, delta_b):
    # Adaptive refinement check
    if current_frame_rate < threshold:
        delta_r = smooth_increase(delta_r)
        delta_b = smooth_increase(delta_b)
        
    for child in node.children:
        # Culling test
        if not passes_culling(child):
            continue
            
        # Calculate screen size of bounding sphere
        screen_size = calculate_screen_size(child.bounding_sphere)
        
        if child.is_leaf:
            # Render leaf node
            render_leaf(child, virtual_memory, n_channels, delta_r, delta_b)
        else:
            # Recurse
            traverse_tree(child, virtual_memory, n_channels, delta_r, delta_b)

def render_leaf(leaf, virtual_memory, n_channels, delta_r, delta_b):
    # Check homogeneity for all n channels
    is_homogeneous = True
    average_values = []
    
    for c in range(n_channels):
        brick = leaf.bricks[c]
        if not is_brick_homogeneous(brick):
            is_homogeneous = False
            break
        average_values.append(brick.average_value)
        
    if is_homogeneous:
        # Use stored average values
        data = average_values
    else:
        # Load brick from virtual memory into cache
        data = load_brick_from_virtual_memory(leaf.brick_pointers, virtual_memory)
        
    # Render using data (e.g., splatting or ray marching)
    render_data(data, delta_r, delta_b)
```

## Subtopics

### [Octree-based out-of-core volume rendering](5171-octree-based-out-of-core-volume-rendering.md)
Extends this method to support multiple visible channels by storing pointers and culling metadata in each node. Enforces whole subtree residency, leading to higher memory footprint and worse performance for multiple channels compared to the Residency Octree.

### [Virtual Memory Volume Rendering](16077-virtual-memory-volume-rendering.md)
Uses a virtual memory scheme with arbitrary packing and no pre-computed 3D hierarchy, avoiding the need to hold the entire path from leaf to root in GPU memory required by this method.

## Operating characteristics
*   **Memory Efficiency:** High efficiency for physical memory usage because only parts of the data structure actually rendered during tree traversals are loaded into physical memory [S2, unofficial].
*   **Performance:** Fast recursive refinements are enabled by the breadth-first storage of the trees [S2, unofficial].
*   **Limitations:** The number of channels is limited to 4 due to GPU texture format constraints [S1, unofficial]. The method requires explicit octree traversal and holding the entire path from leaf to root in memory, which can be a drawback compared to page-table methods [S1, unofficial].
*   **Adaptivity:** Supports adaptive refinement by adjusting splat sizes based on frame rate [S2, unofficial].

## Background
The method was introduced by Crassin et al. [CNLE09] as a scheme for out-of-core rendering. It has been implemented in the Voreen volume rendering framework [DLJL22]. Brix et al. [BPH14] extended this approach to multi-channel data sets.
