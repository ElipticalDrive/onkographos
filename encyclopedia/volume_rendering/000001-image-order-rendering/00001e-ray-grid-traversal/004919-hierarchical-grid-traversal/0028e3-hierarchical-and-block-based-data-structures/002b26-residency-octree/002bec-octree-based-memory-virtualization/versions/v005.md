# Octree-based memory virtualization

Also called: Crassin et al. Octree-based memory virtualization, Interactive Visualization via Memory Mapping

## Overview
Octree-based memory virtualization is an out-of-core rendering technique for multi-channel volume datasets that exceed available texture memory by storing octree nodes and bricks on disk and loading them on demand [S1, unofficial][S2, unofficial]. It extends single-channel approaches to support multiple visible channels by storing pointers and culling metadata in each node [S1, unofficial]. Unlike the [Residency Octree](4950-residency-octree.md), which uses an octree for hierarchical culling but allows partial subtree residency, this method enforces that the whole subtree is resident in the cache for high-resolution rendering, leading to higher memory footprint and worse performance for multiple channels compared to the author's page-table method [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: Multi-channel volume dataset (up to $n$ channels), camera parameters, current frame-rate metric.
- Output: Rendered image with alpha-blended channels.

**Data Structures:**
- **Octree Nodes:** Store culling metadata and pointers to bricks for up to $n$ channels.
- **Bricks:** Voxel data blocks. For homogeneous bricks (all voxels contain the same value up to a user-defined threshold), the node stores the average value instead of a pointer to the brick’s location in the brick cache [S1, unofficial]. A node is marked homogeneous only if its corresponding bricks in all channels are homogeneous [S1, unofficial].
- **Memory Mapping:** Binary data files are mapped to virtual memory using the OS-provided `mmap` function [S2, unofficial].

**Parameters:**
- $n$: Number of channels. Implementation-defined and cannot be changed at run-time. In practice, limited to 4 because GPU texture formats are limited to four components [S1, unofficial].
- $\delta_r$: Minimum regular splat size in pixels.
- $\delta_b$: Minimum boundary splat size in pixels.

**Steps:**
1. **Memory Mapping:** Map the binary data files to virtual memory using `mmap` to avoid loading the entire structure into physical memory [S2, unofficial].
2. **Tree Traversal:** Traverse the octree. Only load parts of the data structure actually rendered during tree traversals, making efficient use of physical memory [S2, unofficial].
3. **Culling:** For each child of the current node, if the child doesn't pass culling tests, ignore it [S2, unofficial].
4. **Screen Size Calculation:** Calculate $S$, the screen size of the bounding sphere of the child [S2, unofficial].
5. **Leaf Rendering:** If the child is a leaf node, render it as a splat [S2, unofficial].
6. **Adaptive Refinement:** If the current frame-rate is too low, increase $\delta_r$ and $\delta_b$ smoothly [S2, unofficial].
7. **Channel Mixing:** Combine multiple channels using accumulation-level intermixing [S1, unofficial]. Note: Image-level intermixing is avoided because occlusions between different channels cannot be handled correctly due to missing depth information in accumulated intermediate results [S1, unofficial].

**Pseudocode:**
```python
# Global variables
delta_r = 1.0  # Minimum regular splat size in pixels
delta_b = 1.0  # Minimum boundary splat size in pixels
n_channels = 4 # Implementation-defined, max 4

def traverse_tree(node):
    """
    Recursively traverse the octree, loading bricks on demand via mmap.
    """
    # Check frame rate and adaptively increase splat sizes if needed
    if current_frame_rate_is_too_low():
        delta_r = smooth_increase(delta_r)
        delta_b = smooth_increase(delta_b)

    # Process children
    for child in node.children:
        # Culling test
        if not passes_culling_tests(child):
            continue

        # Calculate screen size of bounding sphere
        S = screen_size_of_bounding_sphere(child)

        if child.is_leaf():
            # Render leaf as splat
            render_splat(child, S, delta_r, delta_b)
        else:
            # Recurse
            traverse_tree(child)

def render_splat(leaf_node, S, delta_r, delta_b):
    """
    Render a leaf node as a splat.
    If the node is homogeneous, use stored average value.
    Otherwise, load brick data via mmap and render.
    """
    if leaf_node.is_homogeneous():
        # Use stored average value for all channels
        render_homogeneous_splat(leaf_node.average_values)
    else:
        # Load brick data from disk via mmap
        brick_data = load_brick_via_mmap(leaf_node.brick_pointer)
        render_bricks_splat(brick_data, S, delta_r, delta_b)

def load_brick_via_mmap(pointer):
    """
    Load brick data from disk using memory mapping.
    Only the required portion is loaded into physical memory.
    """
    # Implementation depends on OS mmap specifics
    # Returns brick data for all n_channels
    return mmap_read(pointer)

def current_frame_rate_is_too_low():
    # Check if frame rate dropped below threshold
    return get_current_fps() < threshold

def smooth_increase(value):
    # Increase value smoothly
    return value * 1.1
```

**Edge Cases and Pitfalls:**
- **Homogeneity Threshold:** A node is marked homogeneous only if its corresponding bricks in all channels are homogeneous [S1, unofficial].
- **Channel Limit:** The number of channels $n$ is limited to 4 due to GPU texture format constraints [S1, unofficial].
- **Occlusion Handling:** Image-level intermixing is not used because it cannot handle occlusions between different channels correctly due to missing depth information [S1, unofficial].

## Operating characteristics
- **Time Complexity:** Not given in the sources.
- **Memory Complexity:** Efficient use of physical memory by only loading parts of the data structure actually rendered during tree traversals [S2, unofficial]. However, enforcing whole subtree residency leads to a higher memory footprint compared to partial subtree methods [S1, unofficial].
- **Measured Performance:** Not given in the sources.
- **Scaling:** Progressive loading advantage: fast recursive refinements due to breadth-first storage [S2, unofficial].
- **Strengths:** Efficient use of physical memory, fast recursive refinements, support for multi-channel data.
- **Limitations:** Higher memory footprint for multiple channels compared to page-table methods, limited to 4 channels due to GPU texture formats, cannot handle occlusions between channels with image-level intermixing.
- **When to use:** When rendering multi-channel volume datasets that exceed available texture memory and require interactive visualization.
- **When not to use:** When occlusions between channels need to be handled correctly with image-level intermixing, or when more than 4 channels are required.
