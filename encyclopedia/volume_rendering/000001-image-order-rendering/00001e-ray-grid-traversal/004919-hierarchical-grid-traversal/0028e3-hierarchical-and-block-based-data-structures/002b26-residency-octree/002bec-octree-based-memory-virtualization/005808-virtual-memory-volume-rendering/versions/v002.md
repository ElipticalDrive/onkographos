# Virtual Memory Volume Rendering

Also called: Multi-Resolution Virtual Memory Scheme, Virtual Memory Architecture for Volume Rendering, Visualization-Driven Virtual Memory Volume Rendering

## Overview
Virtual Memory Volume Rendering is an out-of-core rendering architecture that virtualizes 3D volumes by subdividing them into small 3D blocks and mapping them to a physical block cache using a multi-resolution page table hierarchy [S1]. It solves the problem of interactive exploration of petascale microscopy data streams by decoupling the construction of the 3D multi-resolution representation from data acquisition and decoupling sample access time during ray-casting from the size of the multi-resolution hierarchy [S1]. Unlike sibling methods such as [Octree-based out-of-core volume rendering](5171-octree-based-out-of-core-volume-rendering.md) which require explicit octree traversal and holding the entire path from leaf to root in GPU memory, this method avoids these drawbacks by using a virtual memory scheme with arbitrary packing and no pre-computed 3D hierarchy [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A stream of 2D microscope image tiles (raw or processed into 2D mipmaps) and a camera/view state for ray-casting [S1].
*   **Output:** A rendered image from single-pass ray-casting [S1].

**Data Structures:**
1.  **Virtual Volume:** The logical 3D volume subdivided into small 3D blocks of size $B \times B \times B$ voxels, where $B=32$ [S1].
2.  **Multi-Resolution Page Directory:** A hierarchy of page tables corresponding to resolution levels $l$, serving as the top-level structure in the virtual memory hierarchy [S1].
3.  **Page Table Cache:** A cache storing page table entries (PTEs), where each PTE maps a virtual block position to a physical position in the Block Cache or is flagged as unmapped [S1].
4.  **Block Cache:** A large 3D texture resident in GPU memory containing the working set of currently required 3D blocks, packed arbitrarily [S1].
5.  **Cache Miss Hash Table:** A structure used to track requested voxel blocks to manage cache updates [S1].

**Numbered Steps:**
1.  **Ray-Casting in Virtual Space:** For each sample along a ray, the algorithm determines the multi-resolution level $l$ and the page table entry $p$ corresponding to the virtual voxel address [S1].
2.  **Address Translation:** The algorithm performs address translation using the Multi-Resolution Page Directory and the Page Table Cache to find the physical location in the Block Cache [S1].
3.  **Cache Miss Detection:** The system checks if the block is unmapped (not resident in the cache). Unmapped blocks produce cache misses [S1].
4.  **Backward Propagation:** Cache misses are propagated backwards to trigger on-demand out-of-core processing [S1].
5.  **On-Demand Construction:** The system fetches the required 2D sub-tiles from the input stream and stitches/resamples them into 3D blocks [S1].
6.  **Cache Update:** The constructed 3D blocks are stored in the Block Cache, and the Page Table Cache is updated to map the virtual address to the new physical location [S1].

**Formulas:**
*   Virtual block coordinates at level $l$: $v_x = \lfloor x / (B \cdot 2^l) \rfloor$, $v_y = \lfloor y / (B \cdot 2^l) \rfloor$, $v_z = \lfloor z / (B \cdot 2^l) \rfloor$ [G].
*   Ray marching step: $P(t) = O + t \cdot D$, where $O$ is origin, $D$ is direction, $t$ is distance [G].
*   Alpha compositing: $C_{out} = C_{in} + (1 - C_{in}.a) \cdot C_{sample}.a \cdot C_{sample}.rgb$ [G].

# input_tiles: Stream of 2D microscope image tiles

def ray_casting_loop(ray_origin, ray_direction, volume_min, volume_max, step_size):
    # Initialize compositing state
    accumulated_color = [0.0, 0.0, 0.0, 0.0]
    
    # Calculate ray entry and exit distances
    inv_dir = [1.0 / d if d != 0.0 else float('inf') for d in ray_direction]
    t_min = max((volume_min[i] - ray_origin[i]) * inv_dir[i] for i in range(3))
    t_max = min((volume_max[i] - ray_origin[i]) * inv_dir[i] for i in range(3))
    
    # Handle degenerate directions and out-of-bounds rays
    if t_min > t_max or t_max < 0.0:
        return accumulated_color
    
    t = t_min
    current_pos = ray_origin + ray_direction * t
    
    # Ray marching loop
    while t <= t_max:
        # 1. Determine virtual address components
        level_l = determine_resolution_level(current_pos)
        virtual_block_id = get_virtual_block_id(current_pos, level_l)
        
        # 2. Address Translation
        physical_block_index = translate_address(
            page_directory, page_table_cache, level_l, virtual_block_id
        )
        
        # 3. Cache Miss Detection
        if physical_block_index is None:
            # 4. Propagate Cache Miss & 5. On-Demand Construction
            handle_cache_miss(level_l, virtual_block_id)
            
            # Retry translation after miss handling
            physical_block_index = translate_address(
                page_directory, page_table_cache, level_l, virtual_block_id
            )
        
        # 5. Texture Fetch & Compositing
        if physical_block_index is not None:
            sample_color = fetch_block_color(
                block_cache, physical_block_index, current_pos
            )
            # Standard front-to-back alpha compositing
            if sample_color.a > 0.0:
                accumulated_color.rgb += (1.0 - accumulated_color.a) * sample_color.a * sample_color.rgb
                accumulated_color.a += (1.0 - accumulated_color.a) * sample_color.a
            if accumulated_color.a >= 0.99:
                break
        
        # Advance ray
        t += step_size
        current_pos = ray_origin + ray_direction * t
        
    return accumulated_color

## Operating characteristics
*   **Time Complexity:** Not given in the sources. [S1]
*   **Memory Complexity:** The system only stores the working set of currently required blocks in the Block Cache, avoiding the storage of the entire hierarchy in GPU memory [S1].
*   **Measured Performance:** The system is evaluated for scalability and performance on petascale microscopy data streams [S1].
*   **Scaling:** The architecture handles missing data naturally and does not pre-compute any 3D multi-resolution representation, allowing it to accept a constant stream of 2D image tiles [S1].
*   **Strengths:** Decouples construction of the 3D multi-resolution representation from data acquisition; decouples sample access time during ray-casting from the size of the multi-resolution hierarchy; avoids explicit octree traversal and holding the entire path from leaf to root in GPU memory; supports arbitrary packing of blocks in the cache [S1].
*   **Limitations:** Not given in the sources. [S1]
*   **When to use:** Interactive exploration of petascale microscopy data streams where data is acquired as a stream of 2D image tiles [S1].
*   **When not to use:** Not given in the sources. [S1]

## Background
Virtual Memory Volume Rendering was introduced in a paper by Hadwiger et al. [S1]. It is designed for real microscopy data from neuroscience, enabling interactive exploration of petascale volume data [S1]. The system is visualization-driven, restricting most computations to the visible volume data [S1]. It compares favorably to previous best-of-breed systems like Gigavoxels and CERA-TVR, which use explicit octree traversal [S1].
