# Residency Octree

Also called: Residency-Octree Hierarchy, hybrid data structure for out-of-core volume rendering, multi-resolution page tables combined with a special octree data structure

## Overview
The Residency Octree is a hybrid data structure for out-of-core direct volume rendering (DVR) of multi-volume datasets that decouples the cache residency of multi-resolution data from the spatial subdivision determined by the octree [S1, unofficial][S2]. Unlike standard octrees where each node represents exactly one brick (one-to-one node-to-brick correspondence), each residency octree node represents a resolution-independent spatial region and references all resolution levels in a bricked volume hierarchy [S1, unofficial][S2]. This decoupling enables efficient mixing of channel resolutions, cache-miss compensation by substituting missing bricks with available resolutions, and fine-grained empty-space skipping independent of the underlying bricking granularity [S2]. It combines the flexible mixed-resolution access of page-table hierarchies with the efficient empty-space skipping of octrees [S1, unofficial][S2].

## How it works
**Inputs and Outputs:**
*   **Input:** A multi-volume dataset with $n$ channels, organized into a bricked hierarchy with multiple resolution levels. The brick size in voxels (e.g., $32^3$) is fixed and identical across all resolution levels [S2].
*   **Output:** A residency octree data structure stored in GPU memory, tracking spatial regions, metadata for culling, and residency bitmaps for $m \le n$ visualized channels [S1, unofficial][S2].

**Data Structures:**
The residency octree is implemented as a full, pointerless octree where all nodes are pre-allocated with fixed locations in a storage buffer to remove indirection [S1, unofficial].
*   **Node Layout:** Each node consists of $m$ unsigned 32-bit integers, where $m$ is the number of simultaneously visualized channels [S1, unofficial].
*   **Per-Channel Fields (16 bits + 8 bits + 8 bits):**
    *   **Partially Mapped Bitmap (16 bits):** Tracks which resolution levels the node is at least partially mapped in [S1, unofficial].
    *   **Minimum Scalar Value (8 bits):** Transfer-function independent metadata for empty-space skipping [S1, unofficial][S2].
    *   **Maximum Scalar Value (8 bits):** Transfer-function independent metadata for empty-space skipping [S1, unofficial][S2].
*   **Multi-Channel Extension:** For each of the $m$ channels, the node stores whether the channel information is initialized. If invalid (marked `INVALID`), it stores a pointer to the next lower subdivision level node with valid information for that channel, or `UNKNOWN` if none exists [S1, unofficial]. This pointer replaces the metadata for that channel to reduce memory [S1, unofficial].
*   **Backing Store:** Internally backed by a multi-channel page table hierarchy and a brick cache [S1, unofficial][S2].

**Node States:**
For a given resolution level, a node can be:
1.  **Fully Mapped:** Cache-resident bricks of that level fully cover the node's spatial extent [S1, unofficial][S2].
2.  **Partially Mapped:** At least one brick of that level spatially overlaps with the node's extent and is resident [S1, unofficial][S2].
3.  **Not Mapped:** No resident bricks overlap [S1, unofficial].
*   If a node is fully mapped in a resolution level, all its children are also fully mapped in that level [S1, unofficial][S2].
*   If a node is partially mapped in a resolution level, its parent is also partially mapped [S1, unofficial][S2].
*   If a node is empty or homogeneous, it is implicitly considered fully mapped in all resolution levels, meaning its bricks do not need to be resident [S1, unofficial].

**Algorithm Steps:**

1.  **Initialization:**
    *   Set the maximum number of channels $m$ [S2].
    *   Define leaf-node size in voxels to determine subdivision depth [S1, unofficial].
    *   Pre-allocate the pointerless octree buffer [S1, unofficial].

2.  **Incremental Construction (Metadata):**
    *   When new metadata for a volume region is received, create or update the corresponding octree node [S2].
    *   Initialize metadata as `INVALID` for all channels except the one for which metadata was received [S2].
    *   For the valid channel, initialize residency info by checking if the node is partially mapped in each resolution level [S2].
    *   Compute parent metadata from children: $min_{parent} = \min(min_{children})$, $max_{parent} = \max(max_{children})$ [S1, unofficial]. This allows parallel bottom-up construction [S1, unofficial].
    *   *Pitfall:* If computing metadata from brick data on the client (server lacks metadata queries), ensure a minimum number of voxels is used to avoid inaccuracies from coarse resolution [S1, unofficial][S2].

3.  **Residency Update (Brick Arrival):**
    *   When a new brick is received, select an available slot in the brick cache [S2].
    *   Identify all residency octree leaf nodes whose spatial extent overlaps the brick's spatial extent [S2].
    *   Mark these leaf nodes as **partially mapped** in the brick's resolution level and channel [S2].
    *   Propagate this update up the tree to the root node [S2].

4.  **Ray Traversal:**
    *   Traverse the octree for spatial regions corresponding to octree nodes, independent of the number of channels [S2].
    *   Start traversal at the third level instead of the root, and resume from the parent node of the last visited node rather than restarting per sample [S2].
    *   Traverse the octree only once per sample to minimize hierarchy traversal cost [S2].
    *   Check the bitmap to see which resolution levels are mapped for the current node [S1, unofficial].
    *   If metadata indicates empty/homogeneous space, skip the subtree [S1, unofficial].
    *   If data is missing, generate a request to the server during ray traversal (ray-guided) [S2].
    *   Substitute missing high-resolution data with available lower-resolution data using the partial mapping information [S2].

**Pseudocode:**

```python
# Node structure in GPU buffer (simplified for single channel logic, extended to m channels in practice)
struct OctreeNode {
    uint16_t partially_mapped_resolutions; # Bitmap of resolution levels
    uint8_t min_scalar;
    uint8_t max_scalar;
    # For multi-channel: additional fields for INVALID/pointer logic per channel
}

# Pre-allocated array of nodes
OctreeNode[] octree_nodes;

function update_residency(brick, resolution_level, channel):
    # 1. Find overlapping leaf nodes
    leaf_nodes = find_leaf_nodes_overlapping(brick.spatial_extent)
    
    # 2. Mark as partially mapped
    for node in leaf_nodes:
        node.partially_mapped_resolutions |= (1 << resolution_level)
        
    # 3. Propagate up to root
    current = node.parent
    while current is not null:
        # Update parent state based on children if necessary
        # In this implementation, partial mapping propagates up automatically
        # if any child is partially mapped.
        current = current.parent

function traverse_ray(ray):
    # Start at level 3, resume from last parent
    current_node = get_last_visited_parent()
    
    while current_node is not null:
        # Check empty space skipping
        if is_empty_or_homogeneous(current_node.min_scalar, current_node.max_scalar):
            break # Skip subtree
            
        # Check residency
        mapped_levels = get_mapped_levels(current_node, ray.channel)
        
        if mapped_levels is empty:
            # Request missing data
            request_data(ray, current_node.spatial_extent)
            # Continue traversal or wait for data
            continue
            
        # Select best resolution from mapped_levels
        best_level = select_best_resolution(mapped_levels)
        
        # Sample data
        sample = sample_volume(ray, best_level)
        
        # Move to next node
        current_node = get_next_node_in_traversal(current_node, ray)
        
    return sample

function compute_metadata_from_children(parent_node, children_nodes):
    parent_node.min_scalar = min(child.min_scalar for child in children_nodes)
    parent_node.max_scalar = max(child.max_scalar for child in children_nodes)
```

## Subtopics

### [Octree-based memory virtualization](5140-octree-based-memory-virtualization.md)
Octree-based memory virtualization is an out-of-core rendering technique for multi-channel volume datasets that exceed available texture memory by storing octree nodes and bricks on disk and loading them on demand. It extends single-channel approaches to support multiple visible channels by storing pointers and culling metadata in each node. Unlike the Residency Octree, which uses an octree for hierarchical culling but allows partial subtree residency, this method enforces that the whole subtree is resident in the cache for high-resolution rendering, leading to higher memory footprint and worse performance for multiple channels compared to the author's page-table method.

### [Residency Octree Update](5181-residency-octree-update.md)
Residency Octree Update is a fully GPU-implemented parallel method for maintaining the spatial residency state of volumetric data bricks within a hierarchical octree structure. It solves the problem of keeping the residency octree consistent with the dynamic brick cache during both data loading and cache eviction, enabling efficient culling of non-resident volume regions during rendering. It differs from static octree construction by being fully parallel and event-driven, updating nodes only when bricks are added or removed from the cache. It differs from simple flat caches by maintaining a hierarchical bitmap representation of partial residency across multiple resolution levels and channels.

### [Mixed-Resolution Multi-Volume Renderer](5215-mixed-resolution-multi-volume-renderer.md)
A ray-guided renderer that accesses metadata and cached volume data through the Residency Octree to enable efficient mixing of resolutions across different channels in multi-volume datasets. It is implemented as a WebGPU compute shader that evaluates each visible channel at every sample along a ray, even when channels have different resolutions, to reduce shader divergence.

### Residency Octree with Channel-Agnostic Brick Cache
Uses accumulation-level intermixing to combine different channels [S1, unofficial]. The residency octree is backed by a channel-agnostic brick cache where each cache entry only contains data belonging to a single channel [S1, unofficial]. The number of channels is not limited by the texture format used by the brick cache implementation, unlike Brix et al.'s approach [S1, unofficial]. Residency octrees support changes to the selection of visible channels at run-time by replacing only the parts of their nodes related to the affected channels [S1, unofficial].

### Residency-Octree Node Classification
Classification of octree nodes based on cache residency of bricks covering their spatial extent at a given resolution level [S1, unofficial]. A node is fully mapped in a resolution level if cache-resident bricks of that level fully cover the node's spatial extent [S1, unofficial]. A node is partially mapped if at least one brick of that level overlaps with the node's spatial extent and is resident in the cache [S1, unofficial]. Fully mapped implies partially mapped, but not vice versa [S1, unofficial]. If a node is fully mapped in a resolution level, all child nodes are also fully mapped in that level [S1, unofficial]. If a node is partially mapped in a resolution level, its parent node is also partially mapped [S1, unofficial].

### Multi-Channel Residency Octree
An extension where all channels share the same octree structure, but each node stores culling and residency information for up to $m \le n$ channels [S1, unofficial]. This allows using the same spatial subdivision for empty-space skipping while rendering each channel in a different resolution [S1, unofficial]. When a channel is replaced by another one, all nodes storing valid data for the old channel are marked as INVALID for the new channel [S1, unofficial]. Each node stores for each of the $m$ channels whether the channel information is initialized or not using a special INVALID value [S1, unofficial]. If invalid, it stores a pointer to the node in the next lower subdivision level that has valid information for that channel, or a special UNKNOWN value if no such node exists [S1, unofficial]. The pointer replaces the metadata for that channel to reduce memory [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Ray traversal is performed for spatial regions corresponding to octree nodes instead of bricks, and this traversal is independent of the number of channels [S2]. The octree is traversed only once per sample to minimize hierarchy traversal cost during multi-channel rendering [S2].
*   **Memory Complexity:** Memory usage scales linearly with the number of simultaneously visualized channels $m$ [S1, unofficial][S2]. Each node stores one bitmask per channel [S2]. This can be mitigated by combining channels via dimensionality reduction, interleaving channels in four-component textures, or using compressed texture formats [S2]. The bit-width of the brick ID data type (e.g., 32-bit or 64-bit) constrains the maximum volume size and the maximum number of channels representable by the multi-channel page table hierarchy [S2].
*   **Performance:** The method is faster than prior approaches and efficient for many data channels with a flexible and adaptive choice of data resolution [S2]. It enables efficient mixing of channel resolutions and substituting alternative resolutions on cache misses [S2].
*   **Strengths:** Decouples cache residency from spatial subdivision, allowing adaptive resolution mixing and cache-miss compensation [S2]. Supports fine-grained empty-space skipping independent of data subdivision [S2]. Allows partial mapping to avoid loading all bricks of a resolution level when only a subset is needed [S1, unofficial][S2].
*   **Limitations:** Memory scales with channel count [S2]. Requires careful management of partial vs. full mapping states [S1, unofficial]. If server does not support metadata queries, client must fetch bricks to compute metadata, potentially uploading unnecessary data [S2].
*   **When to use:** Out-of-core DVR of large-scale volumetric data sets with a large number of channels, such as Immunofluorescence (IF) imaging data [S2].
*   **When not to use:** When the number of channels is very large and memory bandwidth is a bottleneck, or when the server cannot support the required metadata/brick streaming protocols.

## Background
The Residency Octree was introduced as a hybrid data structure for out-of-core multi-volume rendering, combining the advantages of page-table hierarchies and octrees [S1, unofficial][S2]. It addresses the limitations of standard octrees (intrinsically coupled tree traversal and resolution selection, costly fine-grained empty-space skipping) and page tables (lack of efficient strategy for substituting missing high-resolution data) [S2]. The method was implemented as a web-based, pure client-side renderer using WebGPU and WebAssembly to facilitate collaboration and eliminate local data storage [S2]. It is particularly suited for multi-channel immunoﬂuorescence data, where unimodal transfer functions make minima/maxima effective for empty-space skipping [S1, unofficial].
