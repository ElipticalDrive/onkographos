# Multiresolution with Octree Bricking

Also called: Octree-based multiresolution, Octree-based multresolution encoding

## Overview
Multiresolution with Octree Bricking encodes volumetric data at varying resolutions into a spatial octree hierarchy to enable adaptive, high-fidelity rendering of large datasets [S1, unofficial][S2]. It solves the problem of limited memory and rendering performance by allowing the system to selectively query and render nodes at resolutions appropriate to their distance from the viewer or their visual importance [S1, unofficial]. Unlike sibling methods that may use fixed brick sizes or hardware-accelerated BVH traversal for static structures, this method explicitly links octree depth to resolution levels, subsampling children to form parent nodes, and relies on a software-managed out-of-core loading strategy for datasets exceeding texture memory [S1, unofficial][S2].

## How it works
**Inputs and Outputs:**
- Input: A volumetric dataset (scalar or vector field).
- Output: A rendered image using adaptive resolution nodes.

**Data Structures:**
The core structure is an octree.
- **Resolution Association:** Each octree level $L$ corresponds to a specific resolution. Level $L$ has half the resolution (linear dimension) of level $L+1$ [S1, unofficial].
- **Leaf Nodes:** Represent the original, highest-resolution data [S1, unofficial].
- **Internal Nodes:** Store data at a lower resolution, derived from their eight children [S1, unofficial].
- **Root Node:** Represents the coarsest resolution [S1, unofficial].
- **Out-of-Core Storage:** For datasets larger than texture memory, nodes are stored on disk, with a hierarchy file storing connectivity information [S1, unofficial].

**Construction (Preprocessing):**
1. **Bricking:** Partition the volume into bricks (hierarchical volume bricking) [S2].
2. **Tree Construction:** Build the octree in a single preprocessing step [S1, unofficial].
3. **Leaf Assignment:** Assign the original high-resolution data to the leaf nodes [S1, unofficial].
4. **Bottom-Up Subsampling:** For each internal node, compute its data by subsampling its eight children to progressively lower resolutions [S1, unofficial].
5. **Root Assignment:** The root node contains the coarsest resolution data [S1, unofficial].

**Rendering (Per Frame):**
1. **Node Selection:** Traverse the octree to select nodes matching parameters like display resolution, distance, or importance [S1, unofficial].
2. **Selection Criteria:** High-resolution nodes are selected for areas of interest or close to the center of attention; low-resolution nodes are selected for distant regions [S1, unofficial].
3. **Quality Parameter:** Image quality is defined by a combination of importance metrics or user-specified bias parameters [S1, unofficial].
4. **Loading:** Load selected nodes from disk if not in memory (out-of-core) [S1, unofficial].
5. **Sorting:** Sort selected nodes in back-to-front order relative to the camera [S1, unofficial].
6. **Rendering:** Render the sorted nodes [S1, unofficial].
7. **Artifact Mitigation:** Mitigate artifacts at resolution boundaries by modifying transfer functions in lower-resolution nodes [S1, unofficial].

## Subtopics

### [Bricked Multiresolution Tensor Approximation](7469-bricked-multiresolution-tensor-approximation.md)
Combines offline tensor-based compression (Tucker decomposition) with an adaptive, view-dependent loader. It sets itself apart by using rank-reduced approximations for bricks and maintaining a GPU cache for on-demand reconstruction, enabling stack-less ray-casting. Choose this when working memory is severely limited and interactive frame rates are required for very large datasets.

## Operating characteristics
- **Time Complexity:** Construction is $O(N)$ where $N$ is the number of voxels, assuming constant-time subsampling. Not given in the sources.
- **Memory Complexity:** The octree structure itself is small. Not given in the sources.
- **Performance:** Enables rendering of large datasets that would otherwise not fit in texture memory [S1, unofficial]. Performance scales with the efficiency of the out-of-core loading and the selectivity of the node selection criteria. Not given in the sources.
- **Strengths:** Adaptive resolution improves performance for distant objects; out-of-core support handles massive datasets. Not given in the sources.
- **Limitations:** Requires preprocessing; potential artifacts at resolution boundaries if transfer functions are not adjusted [S1, unofficial]; disk I/O latency if node selection is poor. Not given in the sources.
- **When to Use:** Large volumetric datasets where interactive or near-interactive rendering is needed, and memory is constrained. Not given in the sources.
- **When Not to Use:** Small datasets that fit entirely in memory; scenes requiring uniform high resolution everywhere. Not given in the sources.

## Background
This technique was introduced by LaMar et al. [S2] for large dataset rendering, employing an octree to encode hierarchical volume "bricking" [S2]. A similar approach was presented by Boada and colleagues [S2]. The method is described in detail in [S1, unofficial], which discusses its application in volume visualization on large-scale displays. It builds on the general principle of multiresolution techniques where data is encoded in a spatial hierarchy (e.g., octree) for selective querying [S1, unofficial].
