# Supercursor

Also called: cursor with neighborhood information

## Overview
A supercursor is a compound structure that extends a standard hypertree cursor by maintaining real-time neighborhood information for the cell it references [S1, unofficial]. It solves the problem of efficiently accessing adjacent cells in an Adaptive Mesh Refinement (AMR) hypertree grid, where neighbors may reside in different hypertrees or exist at varying refinement levels [S1, unofficial]. Unlike a standard cursor that only tracks a single vertex path, the supercursor aggregates references to all immediate neighbors, enabling algorithms like outside boundary extraction that require checking cell adjacency [S1, unofficial].

## How it works
**Inputs and Outputs:**
- **Input:** A hypertree grid structure containing multiple hypertrees.
- **Output:** A supercursor instance pointing to a specific cell and holding a set of references to its neighbors.

**Data Structures:**
The supercursor is a compound structure containing:
1.  **Central Cursor:** A standard hypertree cursor [S1, unofficial]. It holds a reference to the hypertree and the vertex identifier of the current cell.
2.  **Neighborhood Information:** A collection of references to neighbor cells. These references may point to cells within the same hypertree or in adjacent hypertrees. The structure must handle cases where a single neighbor is referenced multiple times [S1, unofficial].

**Numbered Steps:**

1.  **Initialization:**
    When a supercursor is created for a specific hypertree:
    - The central cursor is initialized to reference the **cell root** of the considered hypertree [S1, unofficial].
    - The neighborhood information is populated with references to the **root cells** of all neighbor hypertrees [S1, unofficial].

2.  **Traversal (Descending):**
    When the central cursor moves (descends) from a parent cell to a child cell:
    - The supercursor must update its neighborhood information to reflect the neighbors of the new child cell [S1, unofficial].
    - Neighbors of the new cell can be of two types:
        - **Same Level:** Cells at the same refinement level as the new cell (either coarse or leaf cells) [S1, unofficial].
        - **Previous Levels:** Cells from a coarser level (which are necessarily leaf cells relative to the current finer grid) [S1, unofficial].

3.  **Neighbor Reference Management:**
    - The supercursor maintains references to all immediate neighbors.
    - **Pitfall/Edge Case:** A neighbor may be referenced **multiple times** by the same supercursor. This occurs specifically when the neighbor is a leaf cell at the level immediately above (coarser than) the supercursor's current level [S1, unofficial]. For example, if a cell has two edges adjacent to the same coarser leaf cell, that leaf cell will appear twice in the neighborhood list [S1, unofficial].

## Operating characteristics
**Time and Memory Complexity:**
- **Memory:** The supercursor requires additional memory compared to a standard cursor to store the neighborhood references. The size of the neighborhood list depends on the dimensionality of the grid (e.g., 4 neighbors in 2D, 6 in 3D for same-level, plus potential coarser neighbors) [S1, unofficial].
- **Time:** Initialization is $O(N_{neighbors})$ where $N_{neighbors}$ is the number of adjacent hypertrees. Traversal updates depend on the complexity of resolving cross-hypertree and cross-level references. The source does not provide explicit Big-O notation for the update step [S1, unofficial].

**Strengths and Limitations:**
- **Strengths:** Enables efficient implementation of algorithms requiring local topology, such as boundary extraction, without repeatedly querying the global grid structure [S1, unofficial].
- **Limitations:** The structure must handle non-conforming meshes (T-junctions) and cross-hypertree references, which adds complexity to the update logic [S1, unofficial]. Duplicate neighbor references must be handled by the consuming algorithm (e.g., deduplication during boundary face generation) [S1, unofficial].

**When to Use:**
- Use when implementing visualization filters or analysis algorithms that require checking cell adjacency, such as outside boundary extraction [S1, unofficial].
- Do not use if only single-cell traversal is needed, as a standard cursor is sufficient and lighter [S1, unofficial].

## Background
The supercursor was devised and implemented to support visualization algorithms on hypertree grids, which are a representation of Adaptive Mesh Refinement (AMR) simulations with rectilinear geometry [S1, unofficial]. It addresses the gap in hypertree grid-aware filters, which historically had less coverage than unstructured mesh filters [S1, unofficial]. The concept is defined in the context of the "Hypertree Grid" data structure, where the grid is decomposed into multiple hypertrees to manage large-scale AMR data [S1, unofficial].
