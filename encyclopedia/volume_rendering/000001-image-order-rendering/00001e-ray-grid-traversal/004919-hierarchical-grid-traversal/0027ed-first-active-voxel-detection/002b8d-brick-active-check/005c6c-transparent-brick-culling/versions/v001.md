# Transparent Brick Culling

Also called: Histogram-based culling, Value histogram technique

## Overview
Transparent Brick Culling discards bricks that contain no visible data by comparing encoded brick histograms against encoded transfer functions using bitwise operations [S1]. It sets itself apart from parent methods by operating on the *content* of the brick (value distribution) rather than just its *presence* in the world tile occupancy mask [S1, 5061-brick-active-check.md]. Unlike Global Attribute-Based Culling, which relies on pre-computed min/max bounds, this method uses full value histograms to detect transparency more accurately [S1, S2].

## How it works
**Inputs and Outputs:**
- Input: A brick's value histogram (encoded) and the current transfer function (encoded).
- Output: A boolean indicating whether the brick should be culled (discarded) or processed.

**Data Structures:**
- **Encoded Transfer Function:** A bit vector where each bit corresponds to a specific value range or opacity threshold in the transfer function. If a value range is transparent, the corresponding bit is 0; otherwise, it is 1.
- **Encoded Brick Histogram:** A bit vector of the same size as the encoded transfer function. Each bit is set to 1 if the brick contains at least one voxel value falling into the corresponding range; otherwise, it is 0.

**Steps:**
1. **Encode Transfer Function:** Convert the current transfer function into a bit mask $T$. For each value bin $i$, $T_i = 1$ if the opacity is non-zero, else $T_i = 0$.
2. **Encode Brick Histogram:** For the current brick, compute its value histogram and convert it into a bit mask $H$. For each value bin $i$, $H_i = 1$ if the count of values in bin $i$ is $>0$, else $H_i = 0$.
3. **Bitwise AND:** Compute $R = T \ \& \ H$.
4. **Check Result:** If $R = 0$, the brick contains no values that are visible under the current transfer function. Discard the brick. Otherwise, process the brick.

**Parameters:**
- Histogram resolution: Determined by the number of bits in the encoding. Not given in the sources.

**Edge Cases and Pitfalls:**
- **Precision:** The accuracy depends on the binning of the histogram. If the binning is too coarse, a brick with visible values might be incorrectly culled if those values fall into a bin that is considered transparent or if the binning does not align with the transfer function's critical regions.
- **Updates:** The encoded histogram must be updated whenever the brick's data changes. The encoded transfer function must be updated whenever the user modifies the transfer function.

**Pseudocode:**
```python
def is_brick_visible(brick_histogram_bits, transfer_function_bits):
    """
    brick_histogram_bits: int, bitmask where bit i is 1 if brick has values in bin i
    transfer_function_bits: int, bitmask where bit i is 1 if bin i is visible
    Returns: True if brick should be processed, False if it should be culled
    """
    # Bitwise AND between the brick's value presence and the transfer function's visibility
    visible_bits = brick_histogram_bits & transfer_function_bits
    
    # If no bits are set, the brick is completely transparent
    if visible_bits == 0:
        return False
    else:
        return True
```

## Subtopics

### Global Attribute-Based Culling
Culls bricks based on global properties such as the transfer function, iso-value, or segmented object states [S2]. It differs from Transparent Brick Culling by using pre-computed min/max values for each brick instead of full histograms [S2]. It is chosen when memory bandwidth is limited and pre-computed bounds are available, but it requires updating these bounds whenever the transfer function changes [S2]. It is used for culling against iso-surfaces and enabled/disabled objects in segmented volume rendering [S2].

## Operating characteristics
**Time and Memory Complexity:**
- Time: $O(1)$ per brick for the bitwise AND operation, assuming the histogram and transfer function are pre-encoded. Encoding the histogram takes $O(N)$ where $N$ is the number of voxels in the brick.
- Memory: Requires storing the encoded histogram for each brick. The size depends on the histogram resolution.

**Measured Performance:**
- In a distributed volume visualization system (DViz/DHCS) with 1024x768 resolution, using this technique allowed efficient culling of transparent bricks during roaming [S1]. Specific frame rate improvements are not isolated from other optimizations in the source [S1].

**Strengths and Limitations:**
- Strengths: Efficient bitwise operations; accurate detection of transparency based on actual value distribution.
- Limitations: Requires pre-computation and storage of histograms; sensitive to histogram binning resolution.

**When to use:**
- Use when the transfer function changes frequently and accurate culling is needed based on value distribution.
- Use when memory allows storing histograms for all bricks.

**When not to use:**
- Do not use if memory is extremely constrained and only min/max bounds are feasible.
- Do not use if the transfer function is static and min/max culling is sufficient.

## Background
Originated in the context of distributed volume visualization systems, specifically mentioned in the work on Distributed Shared Memory for Roaming Large Volumes [S1]. The technique is based on the value histogram technique introduced in [17] (which corresponds to a source not listed in the provided references, but the method is described in [S1]). It is used in large-scale volume rendering to reduce network and memory bandwidth by avoiding the transfer and processing of invisible bricks.
