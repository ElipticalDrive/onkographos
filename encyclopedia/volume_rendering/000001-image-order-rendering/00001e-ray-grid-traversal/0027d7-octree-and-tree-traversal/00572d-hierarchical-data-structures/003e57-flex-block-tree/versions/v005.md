# Flex-block tree

Also called: Cell-tree, Flex-block partition

## Overview
The flex-block tree is a hierarchical data structure derived from a kd-tree partition, designed primarily for load balancing and efficient data distribution in distributed volume rendering [S1, unofficial]. It partitions a volume into "flex-blocks," which are cells containing tightly cropped subvolumes that do not necessarily occupy the entire cell volume [S1, unofficial]. Unlike traditional space subdivision methods, it does not restrict partition cuts to alternate between axes, allowing it to handle scenes with disproportionate dimensions effectively [S1, unofficial]. It serves as a dependency graph that determines the deterministic depth order for ray casting compositing and accelerates ray traversal in ray tracing by indicating potential neighbor cells [S1, unofficial].

## How it works
The method constructs a partition that balances computational load across render nodes while minimizing empty space and network communication overhead.

### Inputs and Outputs
**Inputs:**
1.  Raw volume data (slices or voxels).
2.  A mask volume (optional; if not provided, out-of-core region growing is used to create one) [S1, unofficial].
3.  View directions (typically eight quantized view directions) [S1, unofficial].
4.  Render-node configuration (number of nodes, network topology) [S1, unofficial].

**Outputs:**
1.  A flex-block tree (dependency graph) representing the partition [S1, unofficial].
2.  Cropped volume data (bricks) distributed to render nodes [S1, unofficial].
3.  A look-up table storing image priority order for the eight quantized view directions [S1, unofficial].

### Data Structures

**Flex-block Tree Node:**
*   **Type:** Internal node (non-leaf).
*   **Fields:**
    *   `cut_plane`: The plane equation or coordinate defining the split.
    *   `child_nodes`: References to the two child nodes (left and right).
*   **Layout:** Structurally identical to a traditional binary tree node [S1, unofficial].

**Flex-block (Leaf Node):**
*   **Type:** Leaf node in the tree.
*   **Fields:**
    *   `cell_id`: Identifier for the cell in the partition.
    *   `subvolume`: The tightly cropped subvolume data.
    *   `bounding_box`: The tight axis-aligned bounding box (AABB) enclosing the non-empty data within the cell.
*   **Layout:** Represents a cell that contains a tightly cropped subvolume, which may not occupy the whole cell volume [S1, unofficial].

**Cell-tree (Compact Dependency Representation):**
*   **Type:** Graph structure.
*   **Fields:**
    *   `cells`: List of flex-blocks.
    *   `dependencies`: Compact representation of ray dependencies between cells.
*   **Layout:** Several orders of magnitude smaller than the full dependency set; used for ray-task scheduling [S1, unofficial].

### Construction Algorithm
The construction involves preprocessing, partitioning, and tree extraction.

1.  **Data Reduction (Cropping):**
    *   Read raw data slices.
    *   Generate a mask volume using out-of-core region growing if a mask is not provided [S1, unofficial].
    *   Align a tight axis-aligned bounding box around cohesive non-empty areas of the volume.
    *   Crop slices to these bounding rectangles to remove empty space [S1, unofficial].

2.  **Partitioning (Moving Walls):**
    *   Apply a "moving walls" algorithm to partition the scene.
    *   Move partition walls to simultaneously accommodate non-empty subvolume boundaries and render-node constraints for load balancing [S1, unofficial].

3.  **kd-tree Extraction:**
    *   Extract a kd-tree from the output of the moving walls procedure [S1, unofficial].
    *   Note: The partition cuts do not alternate between axes [S1, unofficial].

4.  **Dynamic Programming (Load Balancing):**
    *   Apply a Dynamic Programming (DP) algorithm (based on the Multipass Partition Problem) to create load-balanced network distributions [S1, unofficial].
    *   This step defines the flex-blocks within the kd-tree partition [S1, unofficial].

5.  **Tree Construction:**
    *   Construct the flex-block tree where internal nodes are kd-tree split nodes and leaf nodes are flex-blocks [S1, unofficial].
    *   For each leaf (flex-block), store the tight AABB of its subvolume [S1, unofficial].

6.  **Dependency Graph Generation:**
    *   For each of the eight quantized view directions, traverse the tree to determine the image priority order (depth order).
    *   Store these orders in a look-up table [S1, unofficial].
    *   Generate the cell-tree (compact dependency graph) from the flex-block tree [S1, unofficial].

### Ray Traversal and Scheduling (Runtime)

**For Ray Casting (Compositing):**
1.  Traverse the flex-block tree to determine the compositing order based on the precomputed look-up table for the current view direction [S1, unofficial].
2.  Render bricks on render nodes.
3.  Composite images using alpha blending, respecting the determined depth order [S1, unofficial].

**For Ray Tracing (Traversal):**
1.  **Initialization:** Distribute data using the flex-block partition. Initialize a ray queue for each cell [S1, unofficial].
2.  **Traversal Loop:**
    *   Process one cell at a time.
    *   If a cell is in main memory, trace each ray in the corresponding ray queue through that cell [S1, unofficial].
    *   **Space Skipping:** Automate space skipping within each cell by advancing the ray forward according to the data extents (tight AABB) of the flex-block [S1, unofficial].
    *   **Ray Queue Management:** When a spawned ray exits the current cell, place it on the queue of the next cell it intersects (determined by the dependency graph/cell-tree) [S1, unofficial].
3.  **Dynamic Scheduling:** Update ray-task scheduling dynamically within the local partition of each render node [S1, unofficial].

### Parameters
*   **View Directions:** Eight quantized view directions are typically used to extract image priority orders [S1, unofficial].
*   **Load Balancing Cost Function:** The DP algorithm evaluates a cost function to minimize end-to-end rendering time, which is a function of the slowest render-node, image composition time, and network communication time [S1, unofficial].

### Edge Cases and Pitfalls
*   **NP-Completeness:** Determining the optimum order in which cells are cached for ray tracing is NP-Complete; optimizations are required [S1, unofficial].
*   **Multiple Fetches:** It is not generally possible to create a schedule which fetches each cell only once for ray tracing algorithms; rays may need to revisit cells or rely on caching [S1, unofficial].
*   **Disproportionate Scenes:** Traditional alternating-axis partitions fail here; the flex-block partition's lack of axis alternation restriction is critical [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Construction involves KD-tree partitioning and Dynamic Programming, which is computationally intensive but done offline. Runtime traversal is accelerated by space skipping via tight AABBs and optimized scheduling.
*   **Memory Complexity:** The cell-tree representation is several orders of magnitude smaller than the full dependency graph, reducing memory overhead for dependency tracking [S1, unofficial].
*   **Strengths:**
    *   Effective load balancing in distributed rendering by accommodating render-node boundaries and non-empty subvolume shapes simultaneously [S1, unofficial].
    *   Significant reduction in empty space through tight cropping, reducing data movement and preprocessing time [S1, unofficial].
    *   Deterministic depth order for ray casting compositing [S1, unofficial].
*   **Limitations:**
    *   Ray tracing scheduling is complex due to the NP-Complete nature of optimal caching; dynamic updates are required [S1, unofficial].
    *   Requires significant preprocessing (region growing, cropping, DP) before rendering can begin [S1, unofficial].
*   **When to use:** Ideal for massive volume visualization in distributed clusters where load balancing and network communication costs are critical bottlenecks.
*   **When not to use:** For single-node rendering or scenes where preprocessing time outweighs rendering benefits, or where simple uniform grids suffice.

## Background
The flex-block tree was introduced in the context of massive data management for distributed volume visualization [S1, unofficial]. It addresses the "Load Balanced Network Distribution" (LBND) problem, which optimizes data partitioning to minimize end-to-end rendering time in a cluster [S1, unofficial]. The method was developed to overcome the limitations of traditional space subdivision methods that do not account for load balancing or non-axis-aligned data distributions [S1, unofficial]. It builds on concepts from kd-trees and dynamic programming for multipass partitioning [S1, unofficial].
