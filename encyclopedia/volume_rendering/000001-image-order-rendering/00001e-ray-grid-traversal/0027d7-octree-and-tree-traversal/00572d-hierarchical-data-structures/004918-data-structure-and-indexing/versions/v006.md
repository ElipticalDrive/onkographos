# Data Structure and Indexing


## Overview
This family defines how hierarchical spatial data (such as octrees, KD-trees, or patch hierarchies) is organized in memory and indexed to enable efficient ray-grid traversal in volume rendering. It solves the problem of navigating complex, view-dependent, or multi-resolution data structures without excessive memory overhead or traversal latency. What sets this family apart from its siblings is the focus on the low-level encoding, pointer management, and array indexing schemes that underpin higher-level acceleration structures, rather than the traversal algorithm itself or the specific spatial partitioning logic.

## Shared principles
The core mechanism across all variants is the mapping of a hierarchical tree structure into a linear or texture-based memory layout that supports fast random access during rendering.

1.  **Hierarchical Indexing**: Nodes are identified by unique IDs or offsets. In array-based schemes (e.g., binary tree indexing), a fixed-size 1D array maps parent-child relationships implicitly or explicitly [S3]. In texture-based schemes (e.g., octree with neighbor pointers), nodes are encoded into texels, where specific components (RGB/A) store pointers, tags, or data offsets [S2, unofficial].
2.  **Node Tagging**: Each node carries metadata indicating its type. Common tags include:
    *   **Inner/Non-Leaf**: Indicates the node has children [S2, unofficial].
    *   **Leaf/Data**: Indicates the node contains actual volume data or surface information [S2, unofficial].
    *   **Empty**: Indicates the node contains no relevant data, allowing traversal to skip it [S2, unofficial].
3.  **Pointer Encoding**: To minimize memory footprint, pointers are often encoded as offsets relative to a base address or as indices into a compact array. In GPU-friendly encodings, these pointers are stored in texture channels (e.g., RGB) to allow parallel access [S2, unofficial].
4.  **View-Dependence**: Many structures support dynamic refinement. The data structure must support on-the-fly construction or update, often using breadth-first or bottom-up propagation to maintain consistency between parent and child nodes [S1][S2, unofficial].

## Subtopics

### [Octree with Neighbor Pointers](5699-octree-with-neighbor-pointers.md)
This method augments a branch-on-need octree with explicit links to adjacent nodes, enabling direct traversal to neighboring spatial regions without backtracking through the parent hierarchy. It solves the latency penalty of recursive ascent in sparse octrees by allowing rays to jump horizontally across node boundaries. Unlike structures that maintain full 26-neighbor connectivity, this variant typically restricts pointers to the X-axis (or specific face directions) to minimize memory overhead, distinguishing it from comprehensive adjacency graphs.

### Perspective-Correct AMR Patch Traversal
*   **Definition**: A hybrid CPU-GPU traversal strategy where the CPU traverses the KD-tree of AMR patches back-to-front, and the GPU traverses cells within a patch. Sub-patches are generated to ensure perspective-correct sorting of cells relative to the observer [S1].
*   **Step**:
    1.  The CPU traverses the KD-tree hierarchy in a back-to-front fashion, choosing the appropriate order at each internal node until a leaf node (patch) is found [S1].
    2.  A series of consecutive indices matching the number of cells in the current patch is sent to the vertex shader [S1].
    3.  The vertex shader modifies each index according to the current observer position to generate proper cell ordering, ensuring perspective-correct sorting [S1].
    4.  The modified index is used to access a vertex texture holding cell data, which is then passed to the geometry shader for visibility checks [S1].

### Gradient Octree Transfer
*   **Step**: Transfers gradient octrees computed on the server side to a rendering client to reduce network traffic and avoid the need to compute gradients on the client [S2, unofficial].

### Binary Tree Indexing
*   **Definition**: A simple binary tree indexing scheme to identify and organize patches in a breadth-first manner (coarse to fine). It allows quick identification of cousin patches. View-dependent mesh generation uses recursive traversal over the patch hierarchy by indexing into a fixed-size 1D array of patches, accumulating patch IDs for later decompression and rendering [S3].

### Point Octree
*   **Definition**: A recursive octree data structure for managing 3D points, supporting insertion, removal, retrieval, movement, and spatial queries (nearest neighbor, radius search) [S4, unofficial].
*   **Step**:
    *   **Insertion (`set`)**: Recursively finds the leaf octant containing the point. If the leaf is full and depth < maxDepth, it calls `split()` and `redistribute()`. If the point already exists, it updates the data array. Otherwise, it appends the point and data to the leaf arrays [S4, unofficial].
    *   **Radius Search (`findPoints`)**: Recursively traverses child octants that intersect the query sphere. In leaf nodes, it computes squared distance `dSq` and compares against `radius * radius` to filter points [S4, unofficial].
*   **Parameter**:
    *   `bias`: Octant boundary bias. Values > 0 make the octree "loose" to handle points near boundaries [S4, unofficial].
    *   `maxPoints`: Maximum number of distinct points allowed per leaf octant before triggering a split [S4, unofficial].
    *   `maxDepth`: Maximum recursion depth for the tree. Prevents infinite subdivision [S4, unofficial].
*   **Layout**: `PointData<T>` stores two parallel arrays: `points: Vector3[]` for coordinates and `data: T[]` for associated user data [S4, unofficial].
*   **Pitfall**: `maxDepth` acts as a hard limit to prevent infinite recursion and poor performance from infinitely small octants [S4, unofficial].

## Background
The need for efficient data structures in volume rendering stems from the exponential growth of multi-resolution datasets (e.g., AMR, adaptive meshes) and the computational cost of ray traversal. Early approaches relied on simple grid structures, but as data became sparse and hierarchical, tree-based structures like octrees and KD-trees became standard. The specific encoding of these trees into GPU textures (e.g., 3D RGBA textures for neighbor pointers) emerged to leverage parallel hardware for traversal [S2, unofficial]. Hybrid CPU-GPU strategies were developed to handle view-dependent refinement, where the CPU manages the coarse hierarchy and the GPU handles fine-grained cell traversal [S1]. The use of binary tree indexing for terrain and patch-based rendering provided a simple, memory-efficient alternative for view-dependent LOD systems [S3]. Point octrees, while less common in pure volume rendering, offer a flexible structure for particle-based or sparse point-cloud volumes [S4, unofficial].
