# Data Structure and Indexing

Also called: Hierarchical Indexing, Spatial Indexing for Ray Tracing

## Overview
Data Structure and Indexing defines the memory layout and access mechanisms for hierarchical volume representations, enabling efficient ray traversal by mapping spatial relationships to linear or texture-based addresses. It distinguishes itself from sibling methods by focusing on the low-level encoding of node connectivity (such as neighbor pointers or binary tree arrays) rather than high-level traversal heuristics or specific compression algorithms.

## Shared principles
The core mechanism involves mapping a multi-dimensional spatial hierarchy (typically octrees or binary trees) into a linear data structure suitable for GPU or CPU access. Common mathematical properties include:
1.  **Linearization:** Spatial coordinates $(x, y, z)$ and depth $d$ are mapped to a 1D index $I$. For Morton-order (Z-order) curves, this is often achieved via bit-interleaving:
    $$ I = \text{interleave}(x, y, z) $$
2.  **Node Encoding:** Each node in the hierarchy is represented by a fixed-size record containing:
    *   **Type/Tag:** Indicates if the node is empty, inner, or leaf.
    *   **Children Pointer:** Offset or index to child nodes.
    *   **Data Pointer:** Offset to voxel data or gradient information.
    *   **Neighbor Pointers:** (Optional) Offsets to adjacent nodes to avoid parent backtracking.
3.  **Traversal Logic:** Ray traversal uses the index to determine the next node. If a ray exits a node, the index is updated based on the exit face and neighbor pointers, or by incrementing/decrementing the Morton index to find the next occupied node.

## Subtopics

### [Octree with Neighbor Pointers](5699-octree-with-neighbor-pointers.md)
Augments a branch-on-need octree with explicit links to adjacent nodes, enabling direct traversal to neighboring spatial regions without backtracking through the parent hierarchy. It solves the latency penalty of recursive ascent in sparse octrees by allowing rays to jump horizontally across node boundaries. Unlike structures that maintain full 26-neighbor connectivity, this variant typically restricts pointers to the X-axis (or specific face directions) to minimize memory overhead, distinguishing it from comprehensive adjacency graphs.

### Perspective-Correct AMR Patch Traversal
A hybrid CPU-GPU traversal strategy where the CPU traverses the KD-tree of AMR patches back-to-front, and the GPU traverses cells within a patch. Sub-patches are generated to ensure perspective-correct sorting of cells relative to the observer [S1]. The CPU traverses the KD-tree hierarchy in back-to-front fashion, choosing the appropriate order at each internal node until a leaf node (patch) is found [S1]. The vertex shader modifies each index according to the current observer position to generate proper cell ordering, ensuring perspective-correct sorting [S1].

### Gradient Octree Transfer
Transfers gradient octrees computed on the server side to a rendering client to reduce network traffic and avoid the need to compute gradients on the client [S2, unofficial].

### Binary Tree Indexing
A simple binary tree indexing scheme to identify and organize patches in a breadth-first manner (coarse to fine). Allows quick identification of cousin patches. View-dependent mesh generation uses recursive traversal over the patch hierarchy by indexing into a fixed-size 1D array of patches, accumulating patch IDs for later decompression and rendering [S3].

### Point Octree
A recursive octree data structure for managing 3D points, supporting insertion, removal, retrieval, movement, and spatial queries (nearest neighbor, radius search) [S4, unofficial].
*   **Insertion (`set`):** Recursively finds the leaf octant containing the point. If the leaf is full and depth < maxDepth, it calls `split()` and `redistribute()`. If the point already exists, it updates the data array. Otherwise, it appends the point and data to the leaf arrays [S4, unofficial].
*   **Radius Search (`findPoints`):** Recursively traverses child octants that intersect the query sphere. In leaf nodes, computes squared distance `dSq` and compares against `radius * radius` to filter points [S4, unofficial].
*   **Parameters:**
    *   `bias`: Octant boundary bias. Values > 0 make the octree "loose" to handle points near boundaries [S4, unofficial].
    *   `maxPoints`: Maximum number of distinct points allowed per leaf octant before triggering a split [S4, unofficial].
    *   `maxDepth`: Maximum recursion depth for the tree. Prevents infinite subdivision [S4, unofficial].
*   **Layout:** `PointData<T>` stores two parallel arrays: `points: Vector3[]` for coordinates and `data: T[]` for associated user data [S4, unofficial].
*   **Pitfall:** `maxDepth` acts as a hard limit to prevent infinite recursion and poor performance from infinitely small octants [S4, unofficial].

## Background
Hierarchical data structures for volume rendering originated with the need to handle large, sparse datasets efficiently. Early work focused on octrees for sparse voxel grids [G]. The concept of neighbor pointers to accelerate traversal was introduced to mitigate the cost of tree traversal in sparse volumes [S1]. AMR (Adaptive Mesh Refinement) structures were adapted for volume rendering to handle varying resolutions, requiring hybrid CPU-GPU traversal strategies [S1]. Binary tree indexing for terrain and patches was developed to allow efficient view-dependent loading and decompression [S3]. Point octrees are widely used in physics simulations and particle rendering, with implementations like `sparse-octree` providing efficient spatial queries [S4, unofficial]. Gradient octree transfer was proposed to offload expensive gradient computations to the server in web-based rendering contexts [S2, unofficial].
