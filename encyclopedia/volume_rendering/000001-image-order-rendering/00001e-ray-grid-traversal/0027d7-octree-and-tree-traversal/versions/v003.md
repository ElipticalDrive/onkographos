# Octree and Tree Traversal

Also called: Sparse Voxel Octree (SVO) Traversal, Hierarchical Ray Traversal, Tree Marching

## Overview
Octree and Tree Traversal methods solve the problem of efficiently rendering volumetric data stored in hierarchical spatial structures (such as Sparse Voxel Octrees or generic hierarchical grids) by skipping empty space and avoiding unnecessary sampling of uniform regions [S2, S4, S6, S8, unofficial]. Unlike fixed-grid traversal methods like [Digital Differential Analyzer (DDA) Traversal](3061-digital-differential-analyzer-dda-traversal.md) which step through every voxel, these methods descend the tree hierarchy to locate occupied cells, significantly reducing computational cost for sparse data [S1, S6, S8, unofficial]. They set themselves apart from sibling methods like [Hierarchical Grid Traversal](2560-hierarchical-grid-traversal.md) by explicitly managing the octree topology (internal vs. leaf nodes) and often requiring stack-based or pointer-based mechanisms to handle the non-uniform depth of the hierarchy [S4, S6, S8, unofficial].

## Shared principles
All methods in this family share the core mechanism of hierarchical descent and ascent. The traversal begins at the root of the octree and determines which of the eight children (octants) the ray intersects. This is typically done by comparing the ray's position relative to the center of the current node's bounding box [S1, S2][S6, S8, unofficial].

1.  **Child Selection:** For a node with center $\mathbf{c}$ and half-extent $s$, the ray position $\mathbf{p}$ determines the child index $k \in \{0, \dots, 7\}$:
    $$
    k = 4 \cdot \mathbb{I}(p_x \ge c_x) + 2 \cdot \mathbb{I}(p_y \ge c_y) + 1 \cdot \mathbb{I}(p_z \ge c_z)
    $$
    where $\mathbb{I}(\cdot)$ is the indicator function [S1, S2][S6, S8, unofficial].

2.  **Empty Space Skipping:** If the selected child is marked as empty (or uniform), the traversal skips the subtree. This is achieved by advancing the ray parameter $t$ to the exit of the current node or using neighbor pointers to jump to the next potentially occupied node [S1, S6, S8, unofficial][G].

3.  **Leaf Handling:** Upon reaching a leaf node, the method typically switches to a fixed-step traversal (like DDA) within the leaf's voxel grid to sample the volume data [S1, S6, S8, unofficial][G].

4.  **Backtracking:** Because octrees are sparse and irregular, traversal often requires backtracking to the parent node when a ray exits a subtree or encounters an empty branch. This is implemented using an explicit stack (on GPU) or recursion (on CPU) [S4, S6, S8, unofficial].

## Subtopics

### [Hermite Data Computation via Bisection](822-hermite-data-computation-via-bisection.md)
This method computes precise intersection points and surface normals (Hermite data) for an implicit function on the edges of an adaptive octree's leaf cells. It solves the problem of geometric inaccuracy in surface extraction (such as Dual Contouring) where linear interpolation between cell corners introduces visible jaggedness on curved or sharp features. Unlike [Octree Path Computation](897-octree-path-computation.md) which focuses on traversal efficiency, or [Rational Ray Parameterization for Octree Traversal](3875-rational-ray-parameterization-for-octree-traversal.md) which handles ray-cube intersections, this method refines the geometric location of the isosurface crossing within each leaf cell to sub-cell accuracy.

### [Octree Path Computation](897-octree-path-computation.md)
Octree Path Computation is the method of encoding the spatial location of a node within an octree hierarchy into a compact bit-vector (path) based on the ray's traversal coordinates. It solves the problem of efficiently identifying which child node a ray enters at each depth level without performing repeated geometric intersection tests against child bounding boxes. It sets itself apart from [Hermite Data Computation via Bisection](822-hermite-data-computation-via-bisection.md) by using direct coordinate comparison rather than iterative refinement, and from [Rational Ray Parameterization for Octree Traversal](3875-rational-ray-parameterization-for-octree-traversal.md) by operating in grid-space rather than ray-parameter space.

### [Sparse Voxel Octree Ray Traversal](2451-sparse-voxel-octree-ray-traversal.md)
Sparse Voxel Octree (SVO) Ray Traversal is a hierarchical ray-casting technique that renders 3D voxel data stored in a sparse octree structure by traversing the tree along ray paths to find occupied cells. It solves the problem of efficiently rendering large, complex voxel scenes by skipping empty space using axis-aligned slab intersection logic, avoiding the need to sample every voxel. Unlike standard rasterization which requires mesh generation and draw calls per chunk, SVO ray tracing renders the entire scene with a single draw call (e.g., a fullscreen triangle) and no vertex buffers. It differs from its siblings, such as [Hermite Data Computation via Bisection](822-hermite-data-computation-via-bisection.md) or [Octree Path Computation](897-octree-path-computation.md), by explicitly managing hierarchical descent and backtracking to handle the sparse nature of the data, often using parallel arrays or explicit stacks to simulate recursion on the GPU.

### [SVO Ray Tracing](3451-svo-ray-tracing.md)
SVO Ray Tracing is a depth-first ray traversal algorithm for Sparse Voxel Octrees (SVO) that visits nodes in a specific order relative to the eye position. It differs from pure SVO traversal by explicitly managing a stack to control visitation order based on eye position, and from BVH-based approaches by operating directly on the octree structure without an intermediate bounding volume hierarchy.

### [Rational Ray Parameterization for Octree Traversal](3875-rational-ray-parameterization-for-octree-traversal.md)
Rational Ray Parameterization is a method for tracing rays through an octree using exact rational arithmetic to avoid floating-point precision errors during cell boundary crossing and neighbor finding. It solves the problem of determining the next cell intersected by a ray when the ray parameters are not integers, ensuring robust traversal without tolerance-based comparisons. Unlike sibling methods that calculate explicit geometric intersections or rely on pre-computed structures, this method uses integer-based neighbor finding and rational parameter comparisons to guarantee correctness. It builds on [Octree and Tree Traversal](4134-octree-and-tree-traversal.md) by providing a specific, exact mechanism for child selection and boundary crossing.

### [Ray-Occlusion Traversal in Octree](5121-ray-occlusion-traversal-in-octree.md)
Ray-Occlusion Traversal in Octree is a method for intersecting rays with an octree-represented scene to determine visibility, primarily used for shadow ray calculations and early termination in volume rendering. It solves the problem of efficiently determining if a ray intersects any solid voxel or leaf node within a hierarchical structure by recursively descending the tree and culling empty subtrees. It differs from its parent [Octree and Tree Traversal](4134-octree-and-tree-traversal.md) by explicitly handling the logic for rays starting inside or outside the root bounding box and managing the transition from hierarchical descent to voxel stepping when empty leaves are encountered. It differs from [Sparse Voxel Octree Ray Traversal](2451-sparse-voxel-octree-ray-traversal.md) by focusing on a specific recursive implementation pattern often found in compute shader contexts, and from [Bottom-up Neighbor-Finding Ray Traversal](5610-bottom-up-neighbor-finding-ray-traversal.md) by relying on top-down hierarchical descent rather than lateral neighbor lookups.

### [GPU Octree Volume Rasterization with Shadow Mapping](5209-gpu-octree-volume-rasterization-with-shadow-mapping.md)
This method renders volumetric data stored in a Sparse Voxel Octree (SVO) by decoupling the hierarchical traversal from the raycasting loop, using rasterization to cull empty space and shadow mapping for occlusion. It solves the performance bottleneck of branch-intensive octree traversal on GPUs by rasterizing proxy geometry of a view-dependent cut of octree nodes to identify occupied bricks, then casting rays only through the resulting tight segments. Unlike sibling methods that traverse the tree per-ray, this approach uses a rasterization pass to generate per-pixel lists of bricks, enabling two levels of empty space skipping (brick and macrocell) and achieving 2 to 4 times faster rendering than state-of-the-art algorithms on large out-of-core datasets.

### [Presence Acceleration](5753-presence-acceleration.md)
Presence Acceleration is a ray traversal acceleration technique for volume rendering that uses a binary pyramid to skip empty regions by identifying cells containing at least one opaque voxel. It solves the problem of inefficiently traversing large transparent volumes by allowing the ray to jump over empty space hierarchically. It sets itself apart from siblings like [Sparse Voxel Octree Ray Traversal](2451-sparse-voxel-octree-ray-traversal.md) by using a fixed, pointerless complete octree structure (the pyramid) rather than a sparse linked structure, and from [Homogeneity Acceleration](822-hermite-data-computation-via-bisection.md) by using binary occupancy flags rather than value ranges for skipping.

### [Compositing Tree Rendering](5860-compositing-tree-rendering.md)
Compositing Tree Rendering is a time-domain optimization strategy for volume rendering that avoids re-rendering unmodified data by retaining and reusing partial images from previous frames. It solves the high computational cost of rendering time-varying volume data by identifying modified subtrees in a compressed octree and composing them with cached partial images of unchanged regions to form the final image. Unlike standard ray casting which re-evaluates the entire volume for every frame, this method leverages spatial coherence in time, significantly reducing rendering time when only small portions of the volume change between timesteps.

### [Bounding-Sphere Tree Traversal with Frame-Rate Control](7227-bounding-sphere-tree-traversal-with-frame-rate-control.md)
This method renders hierarchical Shell and Solid tree structures by traversing bounding-sphere nodes and projecting them as splats, using adaptive refinement to maintain real-time performance. It distinguishes itself from standard octree traversal by decoupling geometric precision from rendering cost through dynamic pixel-size thresholds ($\delta_r, \delta_b$) and employing specific culling tests (view-frustum, back-face, occlusion) optimized for point-based primitives rather than ray-marching.

### [Tree Marcher](7534-tree-marcher.md)
The Tree Marcher is a ray traversal algorithm for generic hierarchical grids, specifically designed to integrate with the OpenVDB data structure. It solves the problem of efficiently stepping through sparse voxel data by combining hierarchical empty-space skipping with Digital Differential Analyzer (DDA) logic at the leaf level. Unlike sibling methods that may rely on geometric intersection tests for child selection, Tree Marcher utilizes a hierarchical DDA (HDDA) approach to determine traversal order, making it distinct from [Octree Path Computation](897-octree-path-computation.md) and [Sparse Voxel Octree Ray Traversal](2451-sparse-voxel-octree-ray-traversal.md).

### Photon Splatting for Direct Illumination
- **Definition:** Store incoming radiance from a light source in the octree leaves by rendering the scene from the light's view using standard rasterization to output a world position map (light-view map), where each pixel represents a photon [S1].
- **Steps:** Splat photons using a fragment shader with one thread per light-view-map pixel, storing them as a direction distribution and energy proportional to the subtended solid angle of the pixel as seen from the light [S1]. Assume light-view map resolution is higher than the lowest level of the voxel grid to splat photons directly into leaf nodes without gaps [S1]. Store photons at the finest level of the voxel structure because they are stored at the surface [S1]. Use atomic add to handle multiple photons ending up in the same voxel [S1].
- **Pitfalls:** Atomic add operations are currently only available for integer textures. Use a 16-bit normalized texture format, denormalized when accessing the value later [S1]. Voxels are repeated for adjacent bricks for fast hardware-supported filtering. Copying photons directly to all required locations in adjacent bricks leads to many thread collisions and bandwidth issues [S1].

### Octree with Neighbor Pointers
- **Definition:** A spatial index structure that augments a branch-on-need octree with links to allow direct traversal to adjacent nodes, used to accelerate ray traversal in volume rendering [S2].
- **Steps:** Construction: Create the structure on-the-fly at each frame directly from the view-dependent octree. Encode it into a 3D texture acting as a spatial index. Update the GPU texture using a glTexSubImage call [S2].
- **Layout:** Encoded into a 3D texture. Each octree node is encoded in 8 consecutive texels arranged in the x direction. The layout uses an 8-bit RGBA texture. The A component of the tagged pointer determines node kind: A=1.0 for inner nodes, A=0.5 for data nodes, A=0.0 for empty nodes. Inner nodes use RGB to point to the first of 8 children arranged consecutively in x. Leaf nodes use RGB to point to leaf info: a data pointer (if not empty) and 6 consecutive texels storing neighbor pointers. The last leaf data texel contains a NULL pointer. Neighbor pointers use their A value to encode the octree level of the neighbor [S2].

### Selective Rendering with Tree Representation
- **Definition:** A rendering strategy that uses the tree representation to perform selective rendering efficiently, reducing I/O costs and enabling distribution of data and calculations to multiple workstations [S3, unofficial].
- **Steps:** Examine the encoded data to identify partial images built from subtrees which have not changed [S3, unofficial]. Reuse the identified unchanged partial images in the following time steps [S3, unofficial].

### Tile-based Octree Traversal
- **Pitfalls:** A smaller leaf-node size leads to less overlap of node lists between image tiles, but increases storage and traversal overhead [S4, unofficial].

### Gradient Octree Transfer

## Background
The concept of using octrees for volume rendering originated in the early 1990s as a way to handle sparse volumetric data more efficiently than uniform grids. Early work by Levoy and others demonstrated that skipping empty space could significantly speed up ray casting [G]. The introduction of Sparse Voxel Octrees (SVOs) in the mid-2000s, particularly for real-time rendering on GPUs, popularized the use of linearized octree structures and stackless traversal techniques [S6, S8, unofficial]. The method has since evolved to include hybrid approaches like rasterization-based culling [S2] and time-domain optimizations like compositing trees [S1, S2]. It is widely used in scientific visualization, medical imaging, and real-time volumetric rendering engines.
