# Octree Path Computation

Also called: Octree Path Encoding, Octree Traversal Path, Octree Bit-Path

## Overview
Octree Path Computation is the algorithmic process of determining the sequence of child nodes (the "path") traversed by a ray or frustum as it descends from the root of an octree to a specific leaf or target node. It solves the problem of efficiently identifying which spatial subdivisions a ray intersects without performing redundant geometric intersection tests at every level. It sets itself apart from sibling methods like [Sparse Voxel Octree Ray Traversal](2451-sparse-voxel-octree-ray-traversal.md) by focusing on the explicit encoding and decoding of the traversal sequence itself, often for purposes such as neighbor finding, path caching, or coordinate reconstruction, rather than just the final sampling step.

## How it works
The method operates by encoding the hierarchical descent into a compact bit-stream or integer path, or by decoding such a path back into spatial coordinates. The core mechanism relies on the binary representation of the octant index at each level.

### Inputs and Outputs
- **Inputs**: 
  - Ray parameters (origin $\mathbf{o}$, direction $\mathbf{d}$) or target grid coordinates $(rx, ry, rz)$.
  - Octree metadata: bounding box (min/max), maximum depth $D$, and current level $lv$.
  - Optional: Pre-computed path from root to a reference node (e.g., u,v-minimal ray).
- **Outputs**: 
  - A path vector or integer representing the sequence of octant indices from root to leaf.
  - Voxel coordinates $(i, j, k)$ at a specific level.

### Data Structures
- **Path Vector**: A list or array of integers, where each element $p_l \in \{0, \dots, 7\}$ represents the octant index at level $l$.
- **Bit-Path Integer**: A single integer where 3 bits are allocated per level. The total size is $3 \times D$ bits.
- **Voxel Coordinates**: 3D integer vector $(i, j, k)$ representing the position within the voxel grid at level $lv$.

### Steps

#### 1. Path Encoding (Forward Computation)
To compute the path for a ray or point:
1. Initialize an empty path vector $P$ and a scale variable $s = 2^{D-1}$ [S1, unofficial].
2. For each depth level $l$ from $0$ to $D-1$:
   a. Determine the octant bits by comparing the current grid coordinates $(rx, ry, rz)$ against the scale $s$ [S1, unofficial].
   b. The octant index $k$ is calculated as:
      $$ k = 4 \cdot \mathbb{I}(rx \ge s) + 2 \cdot \mathbb{I}(ry \ge s) + 1 \cdot \mathbb{I}(rz \ge s) $$
      where $\mathbb{I}(\cdot)$ is the indicator function [S1, unofficial].
   c. Subtract $s$ from the coordinate if the bit is set (to normalize for the next level):
      $$ rx \leftarrow rx - s \cdot \mathbb{I}(rx \ge s) $$
      $$ ry \leftarrow ry - s \cdot \mathbb{I}(ry \ge s) $$
      $$ rz \leftarrow rz - s \cdot \mathbb{I}(rz \ge s) $$
   d. Append $k$ to $P$.
   e. Right-shift the scale: $s \leftarrow s / 2$ (or $s \gg 1$) [S1, unofficial].

#### 2. Path Decoding (Coordinate Reconstruction)
To reconstruct voxel coordinates from a stored path integer or vector:
1. Let $lv$ be the target level and $MAX\_NUM\_LEVELS$ be the maximum depth (typically 16) [S3, unofficial].
2. Shift the octpath right by $3 \times (MAX\_NUM\_LEVELS - lv)$ bits to remove irrelevant higher-level bits [S3, unofficial].
3. Iterate $l$ from $0$ to $lv-1$:
   a. Extract the lowest 3 bits of the current path to get the octant index $k$.
   b. Decode $k$ into local coordinates $(dx, dy, dz)$ using bit masks:
      $$ dx = (k \gg 2) \& 1 $$
      $$ dy = (k \gg 1) \& 1 $$
      $$ dz = k \& 1 $$
   c. Accumulate the global coordinates:
      $$ i = (i \ll 1) + dx $$
      $$ j = (j \ll 1) + dy $$
      $$ k = (k \ll 1) + dz $$
   d. Shift the path right by 3 bits [S3, unofficial].

### Formulas
- **Voxel Size**: The physical size of a voxel at level $lv$ is computed as:
  $$ s = \text{scene\_extent} \times 2^{-lv} $$
  where $\text{scene\_extent}$ is the side length of the root bounding box [S3, unofficial].

### Parameters
- $MAX\_NUM\_LEVELS$: Maximum depth of the octree, typically 16 [S3, unofficial].
- $D$: The depth of the current node or target leaf.

### Edge Cases and Pitfalls
- **Precision**: Floating-point comparisons in Step 1a must handle boundary cases where the ray passes exactly through a node center. Using epsilon comparisons or integer arithmetic is recommended [G].
- **Degenerate Input**: If the ray origin is outside the bounding box, the path computation may yield invalid indices. A pre-check for ray-bbox intersection is required [G].
- **Bit Overflow**: When using integer path encoding, ensure the integer type is large enough to hold $3 \times D$ bits. For $D=16$, 48 bits are needed, fitting in a 64-bit integer.

### Pseudocode
```python
def compute_octree_path(rx, ry, rz, max_depth):
    """
    Computes the octree path for a given grid coordinate.
    rx, ry, rz: Normalized coordinates in [0, 1] or integer grid coords.
    max_depth: Maximum depth of the octree.
    Returns: List of octant indices [k_0, k_1, ..., k_{max_depth-1}]
    """
    path = []
    scale = 1 << (max_depth - 1)  # 2^(max_depth - 1)
    
    for _ in range(max_depth):
        # Determine octant index k
        k = 0
        if rx >= scale:
            k += 4
            rx -= scale
        if ry >= scale:
            k += 2
            ry -= scale
        if rz >= scale:
            k += 1
            rz -= scale
        
        path.append(k)
        scale >>= 1  # Right shift by 1
        
    return path

def decode_voxel_from_path(path_int, lv, max_num_levels=16):
    """
    Decodes voxel coordinates from a bit-packed path integer.
    path_int: Integer containing the path bits.
    lv: Target level to decode to.
    max_num_levels: Maximum depth of the octree.
    Returns: Tuple (i, j, k)
    """
    # Shift to remove higher-level bits
    shift = 3 * (max_num_levels - lv)
    path_int >>= shift
    
    i, j, k = 0, 0, 0
    
    for _ in range(lv):
        # Extract lowest 3 bits
        octant = path_int & 0x7
        path_int >>= 3
        
        # Decode octant to local coordinates
        dx = (octant >> 2) & 1
        dy = (octant >> 1) & 1
        dz = octant & 1
        
        # Accumulate global coordinates
        i = (i << 1) + dx
        j = (j << 1) + dy
        k = (k << 1) + dz
        
    return (i, j, k)
```

## Subtopics

### [Octree Neighbor Search](7782-octree-neighbor-search.md)
An algorithm to find the adjacent cell $a$ sharing a specific face $f$ with a given cell $c$ in a generalized octree, handling cases where the neighbor might be at a different subdivision level. It sets itself apart from sibling methods like [SVO Pathfinder with Lazy Theta* and LOS Recovery](7910-svo-pathfinder-with-lazy-theta-and-los-recovery.md) by focusing on immediate geometric adjacency verification rather than pathfinding or access prediction.

### [SVO Pathfinder with Lazy Theta* and LOS Recovery](7910-svo-pathfinder-with-lazy-theta-and-los-recovery.md)
This method performs 3D pathfinding on a Sparse Voxel Octree (SVO) by combining A* search with Lazy Theta* logic, where line-of-sight (LOS) checks are performed optimistically during neighbor expansion to allow straight-line shortcuts, with a recovery step if LOS fails. It differs from standard A* on octrees by reducing path length and node visits through direct parent-to-current-node connections when possible, and differs from pure ray-casting pathfinding by caching collision results to avoid expensive per-step ray-marching. It builds on [Octree Path Computation](897-octree-path-computation.md) and operates alongside [Octree Neighbor Search](7782-octree-neighbor-search.md) and [Access Path Predictor](11650-access-path-predictor.md).

### [Access Path Predictor](11650-access-path-predictor.md)
The Access Path Predictor (APP) is a knowledge-based out-of-core data management algorithm designed to reduce disk I/O latency in volume rendering by predicting and pre-caching the next octree node required for sampling. It solves the problem of inefficient random access patterns in large datasets by learning local access traffic, specifically the frequent appearance of predecessor-current-successor node sequences. Unlike the Ray Driven Predictor (RDP), which assumes spatial continuity along a ray, APP does not require nodes to be on the same line or in the same neighborhood, allowing it to accommodate diverse rendering features such as refraction and space leaping.

### Mapping Macrocells to Octree Nodes
#### Definition
A method to map implicit macrocell coordinates to the deepest corresponding octree child node to perform isovalue culling using the parent's min/max pair [S2, unofficial].

#### Steps
1. Store the path from the octree root to the current node along the u,v-minimal ray of the frustum to avoid costly lookups [S2, unofficial].
2. Use neighbor-finding to traverse inexpensively from one node to the next [S2, unofficial].
3. Hierarchically recurse from a parent node to a child with a single lookup step in the octree [S2, unofficial].

### Octree Path Decoding & Voxel Coordinate Calculation
#### Steps
1. Shift the octpath right by $3 \times (MAX\_NUM\_LEVELS - lv)$ to remove irrelevant higher-level bits [S3, unofficial].
2. Iterate $l$ from $0$ to $lv-1$: extract the lowest 3 bits of the current path, decode them into $i, j, k$ coordinates using bit masks and shifts, then shift the path right by 3 bits [S3, unofficial].

#### Formula
Voxel size at level $lv$ is computed as: $s = \text{scene\_extent} \times 2^{-lv}$ [S3, unofficial].

#### Parameter
$MAX\_NUM\_LEVELS = 16$, the maximum depth of the octree used for bit shifting and coordinate scaling [S3, unofficial].

## Operating characteristics
- **Time Complexity**: Encoding/Decoding is $O(D)$ where $D$ is the depth of the octree. This is significantly faster than geometric intersection tests at each level, which are $O(1)$ but involve more expensive floating-point operations and branching.
- **Memory Complexity**: $O(1)$ auxiliary space if using integer path encoding, or $O(D)$ if storing the path vector.
- **Strengths**: Extremely fast for neighbor finding and coordinate reconstruction; enables efficient caching of traversal paths; reduces redundant geometric calculations.
- **Limitations**: Requires the octree to be well-aligned and cubic; precision issues can arise with floating-point ray origins; not directly applicable to non-hierarchical or irregular grids.
- **When to Use**: When traversing large sparse voxel octrees, performing neighbor searches, or reconstructing voxel coordinates from traversal history.
- **When Not to Use**: For simple uniform grids where direct indexing is sufficient; for highly irregular meshes where octree structure is not beneficial.

## Background
Octree Path Computation is a fundamental technique in hierarchical spatial data structures, particularly in volume rendering and isosurface extraction. It originated with the development of Sparse Voxel Octrees (SVOs) for efficient ray tracing and volume visualization. The method is widely used in modern real-time rendering engines and scientific visualization tools to accelerate ray traversal and neighbor queries. Key implementations can be found in research on isosurface extraction from implicit surfaces and large-scale volume rendering.
