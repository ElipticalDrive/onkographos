# Access Path Predictor
Also called: APP
## Overview
The Access Path Predictor (APP) is a knowledge-based out-of-core data management algorithm designed to predict and pre-cache the next octree node required for sampling [S1]. It solves the problem of inefficient random access patterns in large datasets by learning local access traffic, specifically the frequent appearance of predecessor-current-successor node sequences [S1]. Unlike the Ray Driven Predictor (RDP), which assumes spatial continuity along a ray, APP does not require nodes to be on the same line or in the same neighborhood, allowing it to accommodate diverse rendering features such as refraction and space leaping [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A new sample point $s$; two recent octree nodes $N_{last}$ (the node accessed before $N_{cur}$) and $N_{cur}$ (the node currently being accessed) [S1].
*   **Output:** The predicted next node $N_{new}$ and cache precaching instructions [S1].

**Data Structures:**
*   **Octree Node Metadata:** Each octree node stores four pairs of predecessor-successor records, where each record consists of a predecessor node identifier ($N_{p,i}$) and a successor node identifier ($N_{s,i}$) [S1].
*   **Storage Constraint:** Knowledge acquisition and storage are limited to leaf nodes only, which reduces computational costs and utilizes the eight unused child addresses in each leaf node [S1].

**Algorithm Steps:**
1.  **Initialization:** Set $N_{new} \leftarrow \text{NULL}$ [S1].
2.  **Check Current Node:** If $s$ is in $N_{cur}$, set $N_{new} \leftarrow N_{cur}$ and terminate prediction [S1].
3.  **Phase I: Access Path Prediction:** If $N_{new}$ is NULL, iterate through each recorded predecessor $N_{p,i}$ of $N_{cur}$. If $N_{last} == N_{p,i}$ and $s$ is in $N_{p,i}$, set $N_{new} \leftarrow N_{p,i}$ [S1].
4.  **Phase II: Historical Successor Prediction:** If $N_{new}$ is NULL, iterate through each recorded successor $N_{s,i}$ of $N_{cur}$. If $s$ is in $N_{s,i}$, set $N_{new} \leftarrow N_{s,i}$ and return $N_{new}$ [S1].
5.  **Phase III: Fallback Navigation:** If $N_{new}$ is NULL, set $N_{new} \leftarrow \text{OctreeNavigation}(N_{cur}, s)$ [S1].
6.  **Update Knowledge:** Replace the oldest $(N_{p,i}, N_{s,i})$ pair in $N_{cur}$ with $(N_{last}, N_{new})$ [S1].
7.  **Precaching:** If $N_{cur}$ is a recorded predecessor of $N_{new}$, set $N_{next}$ to the corresponding successor in $N_{new}$ and precache $N_{next}$ with high priority. Otherwise, precache all four successors in $N_{new}$ with low priority [S1].

def contains(node, point):
    """Returns True if point is within the spatial bounds of the node."""
    return all(node.min[k] <= point[k] < node.max[k] for k in range(3))

def OctreeNavigation(current_node, target_point):
    """Standard octree traversal to find the leaf node containing target_point."""
    if current_node.is_leaf():
        return current_node
    child_index = get_child_index(current_node, target_point)
    if current_node.children[child_index] is not None:
        return OctreeNavigation(current_node.children[child_index], target_point)
    return current_node

def get_child_index(node, point):
    """Determines the index (0-7) of the child containing the point."""
    mid = node.center
    index = 0
    if point.x >= mid.x: index |= 1
    if point.y >= mid.y: index |= 2
    if point.z >= mid.z: index |= 4
    return index

**Parameters:**
*   **History Depth:** Each node stores four predecessor-successor pairs [S1].
*   **Storage Scope:** Leaf nodes only [S1].

**Edge Cases and Pitfalls:**
*   **Leaf Node Limitation:** Knowledge is restricted to leaf nodes to reduce computational costs and utilize the eight unused child addresses in each leaf node [S1].

## Subtopics

### History-based Access Predictor
A knowledge-based algorithm that removes the assumption of specific predecessor-current-successor patterns, relying entirely on historic records of nodes required immediately after a visit [S1]. It utilizes the eight unused child addresses in each leaf node to store up to eight potential successors [S1]. When visiting a node, it pre-caches all known potential successors [S1]. If more than eight successors are identified, the oldest is replaced [S1]. A key pitfall is that pre-caching up to eight nodes to load one may generate excessive disk traffic [S1].

### Ray Driven Predictor
A prediction-based algorithm closely coupled with a discrete ray-tracing engine [S1]. It assumes that octree nodes following the ray and along its path will likely be accessed subsequently [S1]. Given a ray and current sampling position $s_c$, it determines a predicted sampling point $s_p$ on the ray just outside the current octree node [S1]. It then navigates the octree to reach the node containing $s_p$, instructing the lower layer to prefetch any nodes not already in the cache during this navigation [S1]. This process repeats for each sampling point [S1].

## Operating characteristics
*   **Time Complexity:** Prediction phases run in $O(1)$ time relative to the fixed history size of four pairs [S1]. Octree navigation complexity is not given in the sources [S1].
*   **Memory Overhead:** Four predecessor-successor pairs per leaf node [S1].
*   **Performance:** Effective for applications with regular access patterns such as ray tracing, marching cubes, and feature tracking [S1].
*   **Limitations:** Less effective for highly irregular or random access patterns where historical patterns do not repeat [S1].
*   **Comparison:** Unlike RDP, APP does not assume spatial continuity, making it more robust for refraction and space leaping [S1]. Unlike HAP, APP uses specific path patterns rather than immediate successors, potentially reducing unnecessary pre-caching [S1].

## Background
The Access Path Predictor was introduced by D. Chisnall, M. Chen, and C. Hansen in 2006 as part of their work on knowledge-based out-of-core algorithms for data management in visualization [S1]. It is part of a suite of predictors including the Ray Driven Predictor and History-based Access Predictor, designed to work within a discrete ray-tracing engine [S1].
