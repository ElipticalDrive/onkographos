# Ray-Occlusion Traversal in Octree

Also called: Octree Ray Traversal, Ray-Octree Traversal

## Overview
Ray-Occlusion Traversal in Octree is a method for intersecting rays with an octree-represented scene to determine visibility, primarily used for shadow ray calculations and early termination in volume rendering. It solves the problem of efficiently determining if a ray intersects any solid voxel or leaf node within a hierarchical structure by recursively descending the tree and culling empty subtrees. It differs from its parent [Octree and Tree Traversal](4134-octree-and-tree-traversal.md) by explicitly handling the logic for rays starting inside or outside the root bounding box and managing the transition from hierarchical descent to voxel stepping when empty leaves are encountered. It differs from [Sparse Voxel Octree Ray Traversal](2451-sparse-voxel-octree-ray-traversal.md) by focusing on a specific recursive implementation pattern often found in compute shader contexts, and from [Bottom-up Neighbor-Finding Ray Traversal](5610-bottom-up-neighbor-finding-ray-traversal.md) by relying on top-down hierarchical descent rather than lateral neighbor lookups.

## How it works
**Inputs and Outputs:**
- **Input:** A ray defined by origin $\mathbf{o}$ and direction $\mathbf{d}$ (normalized); an octree data structure stored in a flat array; the root node index; maximum traversal depth $D_{max}$; maximum traversal steps $N_{max}$.
- **Output:** A boolean indicating intersection, or the hit point/material index if a leaf is reached.

**Data Structures:**
The octree is stored in a flat array `octreeArray` of `OctreeNode` structs [S1, unofficial].
- `OctreeNode`: Contains 8 integer child pointers `p0` through `p7` [S1, unofficial].
  - If `p_i >= 0`, it points to the index of the child node in `octreeArray`.
  - If `p_i == -1`, the child is empty or the node is a leaf [S1, unofficial].
  - Indices are adjusted by a `pointerOffset` to be relative to the start of the flat array [S1, unofficial].
- The nodes are stored in reverse depth order (deepest layers first) [S1, unofficial].
- Auxiliary arrays may track `child_bit_depth` and `child_mins/maxs` for isovalue checks in some variants [S2].

**Algorithm Steps:**

1. **Initialization:**
   - Set `curDepth = 0`.
   - Set `nodeIndices[0]` to the root node index.
   - Set `parentVoxels[0]` to the root voxel coordinates.
   - Set `voxelSize` to half the root voxel size (or initial voxel size depending on root definition) [S1, unofficial].
   - Handle ray origin position:
     - If the ray origin is outside the root bounding box, compute intersection distances ($t_x, t_y, t_z$) with the six planes of the root voxel [S1, unofficial].
     - Calculate candidate collision points: $\mathbf{p}_x = \mathbf{o} + t_x \mathbf{d}$, etc. [S1, unofficial].
     - Validate collision points by checking if they lie within the root voxel bounds [S1, unofficial].
     - Add a small epsilon offset ($\epsilon_{entry} = 0.001 \cdot \mathbf{d}$) to the collision point along the intersecting axis to avoid self-intersection [S1, unofficial].
     - Select the minimum valid distance $t_{min}$. If no valid intersection, return miss [S1, unofficial].
     - Update ray origin to $\mathbf{o} + t_{min} \mathbf{d}$ and determine the entry voxel index (0-5) based on the axis and direction sign [S1, unofficial].
     - If the ray origin is inside, use the rounded voxel coordinates of the origin [S1, unofficial].

2. **Descent Loop:**
   - Iterate `i` from 0 to $N_{max} - 1$ [S1, unofficial].
   - Get the current node `node = octreeArray[nodeIndices[curDepth]]` [S1, unofficial].
   - Calculate the center of the current voxel: $\mathbf{c} = \mathbf{curVoxel} + \frac{1}{2} \mathbf{voxelSize}$ [S1, unofficial][S2].
   - Determine the child index `child` based on the ray's position relative to the center:
     - For each axis $k \in \{x, y, z\}$, if $\mathbf{p}_{enter}.k \ge c.k$, set bit $k$ [S1, unofficial][S2].
     - `child = (bit_x << 2) | (bit_y << 1) | bit_z` [S1, unofficial][S2].
   - Retrieve the child pointer `subNodeValue = node.p_child` [S1, unofficial].
   - **Leaf/Empty Handling:**
     - If `subNodeValue < -1`: The node is a material leaf. Compute shadow factor or return hit [S1, unofficial].
     - If `subNodeValue == -1`: The node is an empty leaf. Break descent loop to proceed to stepping [S1, unofficial].
     - If `curDepth + 1 == D_{max}`: Max depth reached. Check `subNodeValue`. If material, return hit; else, break [S1, unofficial].
   - **Internal Node Handling:**
     - If `subNodeValue >= 0`:
       - Update `nodeIndices[curDepth + 1] = subNodeValue` [S1, unofficial].
       - Increment `curDepth` [S1, unofficial].
       - Halve `parentVoxelSize` and `voxelSize` [S1, unofficial].
       - Continue loop.
     - If `subNodeValue == -1` (empty): Break descent [S1, unofficial].

3. **Voxel Stepping (Post-Descent):**
   - If the descent loop breaks due to an empty leaf or max depth without hit:
   - Calculate deltas to the next voxel boundaries for x, y, z axes using `getDelta` with current `voxelSize` [S1, unofficial].
     - Note: `getDelta` returns $\infty$ if the direction component is 0 [S1, unofficial].
   - Determine the minimum distance to the next boundary `minDelta` [S1, unofficial].
   - Advance the ray position: $\mathbf{p}_{new} = \mathbf{p}_{cur} + minDelta \cdot \mathbf{d}$ [S1, unofficial].
   - Update current voxel index by rounding the new position, adding a small epsilon ($\epsilon_{step} = 0.01 \cdot \mathbf{d}$) to the axis of `minDelta` to prevent re-entering the same voxel [S1, unofficial].
   - Determine the collision type (0-5) based on the axis crossed and direction sign [S1, unofficial].
   - **Parent Boundary Check:**
     - While the new voxel is outside the current parent voxel bounds:
       - Decrement `curDepth` [S1, unofficial].
       - Double `parentVoxelSize` and `voxelSize` [S1, unofficial].
       - If `curDepth < 0`, return miss [S1, unofficial].
   - Re-evaluate the node at the new `curDepth` and continue traversal or stepping.

4. **Termination:**
   - If a material leaf is hit, return the hit point and material data [S1, unofficial].
   - If $N_{max}$ iterations are exceeded, return miss/black color [S1, unofficial].

**Parameters:**
- `MAX_TRAVERSALS`: Maximum number of outer loop iterations, typically 300 [S1, unofficial].
- `MAX_DEPTH`: Maximum octree depth, typically 100 [S1, unofficial].
- `INF`: Large constant for infinity [S1, unofficial].
- `EPS_ENTRY`: Epsilon for entry point, 0.001 [S1, unofficial].
- `EPS_STEP`: Epsilon for stepping, 0.01 [S1, unofficial].
- `shadow_attenuation`: Multiplier for shadow rays, 0.3 [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Zero Direction:** If a ray direction component is 0, `getDelta` returns $\infty$, preventing infinite loops in that axis [S1, unofficial].
- **Infinite Loops:** A counter `j` inside the descent loop checks `if (j++ > MAX_DEPTH)` to prevent infinite loops in malformed octrees [S1, unofficial].
- **Precision Errors:** Epsilon offsets are critical at voxel boundaries to avoid self-intersection or re-entering the same voxel [S1, unofficial].
- **Ray Origin Outside Root:** Requires explicit AABB intersection calculation before traversal begins [S1, unofficial].

## Subtopics

### [Bottom-up Neighbor-Finding Ray Traversal](5610-bottom-up-neighbor-finding-ray-traversal.md)
Bottom-up neighbor-finding ray traversal is a method for intersecting rays with an octree-represented scene by determining the sequence of cells the ray passes through via neighbor lookups rather than hierarchical descent. It solves the problem of efficiently stepping from one occupied or relevant cell to the next along a ray path, avoiding the overhead of traversing empty space from the root. Unlike top-down traversal methods that descend from the root for every step, this approach starts at the first intersected cell and moves laterally or vertically through the tree structure to find the subsequent cell, offering a trade-off between implementation complexity and traversal speed depending on the density of the scene.

### [Octree-based Raycasting](5707-octree-based-raycasting.md)
Octree-based Raycasting is a volume rendering technique that accelerates ray traversal by skipping empty space regions using an octree data structure. It solves the performance bottleneck of naive voxel raycasting, which has $O(n)$ complexity relative to the number of voxels, by reducing traversal cost to depend only on occupied space. It differs from its parent [Ray-Occlusion Traversal in Octree](5121-ray-occlusion-traversal-in-octree.md) by explicitly managing dynamic voxel updates and concurrency, and from [Bottom-up Neighbor-Finding Ray Traversal](5610-bottom-up-neighbor-finding-ray-traversal.md) by relying on hierarchical empty-space skipping rather than neighbor-based stepping.

### Octree Traversal via Voxel Grid
A method to traverse an octree by mapping ray origin/direction to chunk coordinates and checking if the ray stays within the current chunk bounds, using a loop condition based on distance from center [S1, unofficial]. It defines the voxel center as `voxelCenter = vec3(octreeSize / 2, octreeSize / 2, octreeSize / 2)` and computes the current voxel position as `curVoxel = octreeSize * floor(rayOrigin / octreeSize)` [S1, unofficial]. It loops while the squared distance from the center to the ray origin is greater than the squared distance from the center to the ray end: `dot(rayOrigin - voxelCenter, rayOrigin - voxelCenter) > dot(rayOrigin + rayDir - voxelCenter, rayOrigin + rayDir - voxelCenter)` [S1, unofficial]. If the current voxel is within valid bounds `[0, octreeSize)`, it returns success; otherwise, it advances the ray origin [S1, unofficial].

### Hero-like Octree Traversal
A depth-first search approach for ray-tracing octrees that uses a 2x2x2 voxel test to determine the order of cell hits and descend into occupied nodes [S5, unofficial]. It starts from the root of the octree and performs a 2x2 test to find which cells the ray hits and their order [S5, unofficial]. It uses intersection values for middle planes ($t_{mx}, t_{my}$) and exit planes ($t_{ex}, t_{ey}$) to determine the ray's position and path within the 2x2 area [S5, unofficial]. If any top cells in the 2x2 area are occupied, it descends into the tree by calculating new plane positions based on the cell position [S5, unofficial].

## Operating characteristics
- **Time Complexity:** $O(k)$ where $k$ is the number of nodes visited, which depends on the tree depth and the number of occupied leaves intersected. In the worst case (dense scene), it approaches $O(N)$ where $N$ is the number of voxels, but typically much faster for sparse data [S1, unofficial][S2].
- **Memory Complexity:** $O(N)$ for storing the octree structure, where $N$ is the number of nodes. The flat array storage is efficient for cache coherence [S1, unofficial].
- **Measured Performance:** Performance improvements are observed when using a low-resolution depth pass to initialize rays closer to collision points, reducing the number of octree node traversals [S1, unofficial].
- **Strengths:** Efficiently skips empty space; recursive structure is simple to implement; handles rays starting inside or outside the root [S1, unofficial].
- **Limitations:** Recursion depth can be limited by stack size; precision issues at boundaries require careful epsilon handling; performance degrades in very dense scenes [S1, unofficial].
- **When to Use:** Shadow ray calculations, early termination in volume rendering, sparse voxel scenes [S1, unofficial].
- **When Not to Use:** Dense uniform volumes where simple ray marching is faster; scenes with high frequency detail requiring very deep trees [S1, unofficial].

## Background
The method originates from implementations in Vulkan-based raymarching applications, specifically the `vkEngine` project by sebbooth [S1, unofficial]. It is also referenced in academic works on interactive isosurface ray tracing of large octree volumes [S2]. The technique is widely used in real-time rendering engines for shadow mapping and volume visualization [S1, S3, S4, unofficial].
