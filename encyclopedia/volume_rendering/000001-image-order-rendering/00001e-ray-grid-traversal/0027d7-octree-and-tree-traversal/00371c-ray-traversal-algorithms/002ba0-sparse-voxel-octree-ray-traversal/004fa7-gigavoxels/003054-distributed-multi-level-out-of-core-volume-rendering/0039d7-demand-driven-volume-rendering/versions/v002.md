# Demand-Driven Volume Rendering

Also called: Demand-Driven Data Back-End, Virtual Octree Rendering

## Overview
Demand-Driven Volume Rendering is a GPU ray-casting technique that renders a "virtual octree" where physical voxel data is computed on demand, driven by visibility and screen-projection size, allowing interactive rendering of terascale electron microscopy (EM) data without pre-computing a 3D multi-resolution hierarchy [S1]. It differs from sibling methods like GigaVoxels by decoupling the ray-caster from the data reconstruction backend, using a two-level page table hierarchy to translate virtual sample positions to physical data on the fly, enabling interactive frame rates for volumes exceeding GPU memory [S1].

## How it works
**Inputs and Outputs:**
- **Input:** A stream of 2D image tiles (potentially of different resolution, scale, and orientation) representing the source volume data [S1].
- **Output:** A rendered 2D image frame [S1].

**Data Structures:**
The system relies on a multi-level paged virtual memory management system consisting of three cache levels [S1]:
1.  **Top-level Page Directory:** Fully resident in GPU memory. For a 1 TB volume, this is 48 KB [S1].
2.  **2nd-level Page Table Cache:** Resides in a small cache (GPU or CPU). For a 1 TB volume, this is 32 MB [S1]. Entries map to physical octree nodes [S1].
3.  **Physical Texture Cache:** Contains physical octree nodes. Size ranges from 1 GB (single GPU) to several gigabytes (multi-GPU) [S1].

**Octree Node Layout:**
- Each octree node contains $32^3$ physical voxels [S1].
- Nodes are addressed via the page table hierarchy [S1].

**Parameters:**
- Octree node size: $32^3$ voxels [S1].
- Top-level page directory size: 48 KB (for 1 TB volume) [S1].
- 2nd-level page table cache size: 32 MB (for 1 TB volume) [S1].
- Physical texture cache size: 1 GB to several GB [S1].

**Algorithm Steps:**
1.  **Initialization:** Load the top-level page directory into GPU memory [S1]. Initialize the 2nd-level page table cache and physical texture cache [S1]. Start the demand-driven data back-end in a separate background thread [S1].
2.  **Ray Casting Loop (per frame):**
    a. For each pixel, cast a ray into the virtual volume space [S1].
    b. Compute sample positions in virtual volume space along the ray [S1].
    c. Translate virtual sample positions to physical addresses using the two-level page table hierarchy: look up the top-level page directory (resident in GPU) to find the relevant 2nd-level page table, then look up the 2nd-level page table cache to find the physical octree node address [S1].
    d. Check if the physical octree node is resident in the Physical Texture Cache [S1].
    e. **If resident:** Retrieve the node data and perform front-to-back volume rendering [S1].
    f. **If not resident (Cache Miss):**
        i. Generate a cache miss signal [S1].
        ii. Substitute missing data with lower resolution data to maintain interactive frame rates [S1].
        iii. Trigger the demand-driven data back-end to reconstruct the physical data of matching resolution from the stream of 2D image tiles [S1].
        iv. Continue rendering with lower resolution data while reconstruction proceeds in the background [S1].
3.  **Data Reconstruction (Background Thread):**
    a. Receive requests for physical octree nodes from the ray-caster [S1].
    b. If the required 2D image tiles are in memory, reconstruct the 3D block (e.g., $512 \times 512 \times 32$) in as fast as 30 ms [S1].
    c. If 2D image tiles are not in memory, read them from disk (latency up to a few seconds) [S1].
    d. Populate the Physical Texture Cache with the reconstructed nodes [S1].
    e. Update the 2nd-level page table cache entries to point to the new physical nodes [S1].

**Formulas:**
- Sample position along ray: $P(t) = O + t \cdot D$, where $O$ is ray origin, $D$ is direction vector, $t$ is distance along ray [G].
- Front-to-back compositing: $C_{out} = C_{in} + (1 - A_{in}) \cdot C_{sample} \cdot \alpha_{sample}$, $A_{out} = A_{in} + (1 - A_{in}) \cdot \alpha_{sample}$, where $C$ is color, $A$ is accumulated opacity, $C_{sample}$ and $\alpha_{sample}$ are voxel color and opacity [G].
- Page table translation: Virtual address $\rightarrow$ Top-level directory index $\rightarrow$ 2nd-level page table pointer $\rightarrow$ Physical node address [S1].

**Pseudocode:**
```python
def render_frame(pixels, ray_origins, ray_directions, step_size, max_distance):
    for i, pixel in enumerate(pixels):
        o = ray_origins[i]
        d = ray_directions[i]
        color = [0.0, 0.0, 0.0]
        alpha = 0.0
        t = 0.0
        while t < max_distance:
            # Compute sample position in virtual volume space
            sample_pos = [o[j] + t * d[j] for j in range(3)]
            # Translate virtual position to physical address via two-level page table
            physical_addr = lookup_page_table(sample_pos)
            if physical_addr is not None and physical_addr in physical_texture_cache:
                node = physical_texture_cache[physical_addr]
                # Sample voxel color and opacity
                v_color, v_alpha = sample_voxel(node, sample_pos)
                # Front-to-back compositing
                contrib = (1.0 - alpha) * v_alpha
                color = [color[k] + contrib * v_color[k] for k in range(3)]
                alpha += contrib
                if alpha >= 1.0:
                    break
            else:
                # Cache miss: use lower resolution fallback or zero
                pass
            t += step_size
        set_pixel_color(pixel, color, alpha)

def lookup_page_table(virtual_pos):
    # Map virtual position to top-level page directory index
    level0_idx = compute_level0_index(virtual_pos)
    # Get 2nd-level page table pointer from top-level directory
    level1_ptr = top_level_page_directory[level0_idx]
    # Map virtual position to 2nd-level page table index
    level1_idx = compute_level1_index(virtual_pos)
    # Look up physical address in 2nd-level cache
    if level1_ptr in page_table_cache:
        return page_table_cache[level1_ptr].get(level1_idx)
    return None

def sample_voxel(node, pos):
    # Standard trilinear interpolation or nearest-neighbor lookup [G]
    return node.get_value_at(pos), node.get_alpha_at(pos)
```

**Edge Cases and Pitfalls:**
- **Reconstruction Latency:** If 2D image tiles are not in memory, reconstruction may take up to a few seconds [S1]. This is handled by substituting missing data with lower resolution data while reconstruction proceeds in the background [S1].
- **Spatial Coherence:** Performance relies on spatial coherence along rays to make page table lookups fast [S1].
- **Cache Size Scaling:** The system scales to very large volumes because the top-level page directory is small (48 KB for 1 TB) and the working set is bounded by display resolution, not volume resolution [S1].

## Operating characteristics
- **Time Complexity:** Page table lookups are extremely fast when spatial coherence is exploited [S1]. Reconstruction latency varies from 30 ms (tiles in memory) to seconds (tiles from disk) [S1].
- **Memory Complexity:** Top-level page directory: 48 KB for 1 TB volume [S1]. 2nd-level page table cache: 32 MB for 1 TB volume [S1]. Physical texture cache: 1 GB to several GB [S1].
- **Measured Performance:** Interactive frame rates for volumes up to 1 TB [S1]. Mouse cortex volume (955 GB) rendered interactively [S1].
- **Strengths:** Interactive rendering of terascale data without pre-computation; decoupled backend allows progressive reconstruction; small memory footprint for page tables [S1].
- **Limitations:** Latency in data reconstruction if tiles are not in memory; requires a stream of 2D image tiles [S1].
- **When to use:** Interactive exploration of very large volumes (e.g., EM data) where pre-computation is infeasible or too slow [S1].
- **When not to use:** When low latency is critical and tiles are not pre-loaded; when the volume is small enough to fit in GPU memory without paging [S1].

## Background
Demand-Driven Volume Rendering was presented at SIGGRAPH 2011 [S1]. It was developed to enable 3D volume rendering of large electron microscopy (EM) datasets, such as the mouse cortex (955 GB) and hippocampus (43 GB, 92 GB) volumes acquired by the Harvard Center for Brain Science [S1]. The method builds on the concept of virtual octrees but differs from prior systems like GigaVoxels by using a simpler, faster scheme for volume traversal based on arbitrary direct access to the full virtual octree in virtual memory, driven by a decoupled data back-end [S1].
