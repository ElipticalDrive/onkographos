# GigaVoxels

Also called: Dynamic Sparse Octree, Ray-Guided Streaming

## Overview
GigaVoxels is a dynamic sparse octree approach for efficient and detailed voxel rendering that achieves real-time to interactive rates on volumes exceeding GPU memory capacities by using ray-guided streaming [S1, unofficial]. The volume is only used at the resolution needed to produce the final image, providing memory/speed gains and inherent anti-aliasing [S1, unofficial]. It differs from its siblings and nearest alternatives by guiding data production and streaming directly based on information extracted during rendering, exploiting the fact that details in CG scenes are concentrated at interfaces between free space and clusters of density [S1, unofficial]. Unlike view-independent structures like [Sparse Voxel Octree Ray Traversal](2451-sparse-voxel-octree-ray-traversal.md) which may overrefine or lack smooth temporal transitions, GigaVoxels continuously adapts resolution, making discontinuities disappear and ensuring smooth temporal transitions to different subdivision levels [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A volumetric dataset (e.g., 3D scans, hypertextured meshes, or fractals) potentially exceeding GPU memory.
*   **Output:** A rendered image with real-time to interactive frame rates (20-90 fps) [S1, unofficial].

**Data Structures:**
The method combines an adaptive version of the structure from [LHN05a] with regular constant-sized memory blocks [LKS*06] for efficient hardware-based filtering [S1, unofficial].
*   **Sparse Voxel Octree:** Organizes data to exploit "sparse-twice" structures (dense clusters in free space) [S1, unofficial].
*   **Mipmap Hierarchy:** A hierarchy is built by iteratively downsampling and averaging neighbors [S1, unofficial].
*   **Streaming Buffer:** Manages data transfer based on ray-guided requests.

**Parameters:**
*   **Resolution:** Examples include $8192^3$ for 3D scans, $16384^3$ for hypertextured meshes, and theoretically infinite for fractals [S1, unofficial].
*   **Quality/Performance Trade-off:** The system allows a trade-off between quality and performance, exploiting temporal coherence [S1, unofficial].
*   **Opacity Threshold:** Rays stop when a certain opacity level is reached [S1, unofficial].

**Algorithm Steps:**
1.  **View-Dependent Adaptation:** Determine the required resolution based on the current view and occlusion information [S1, unofficial].
2.  **Ray-Guided Streaming:** Extract information during rendering to guide data production and streaming. Only the necessary parts of the volume are loaded into GPU memory [S1, unofficial].
3.  **Mipmap Construction:** Build a hierarchy by iteratively downsampling and averaging neighbors. This creates a mipmapping-like structure where reading from a mipmap delivers the integrated value of a small volume [S1, unofficial].
4.  **Ray Casting with Cone Approximation:** Perform ray casting where the step size is chosen proportionally to the distance from the observer. Reading from the appropriate mipmap level approximates the cone integral defined by the eye and pixel extent, addressing aliasing and accelerating computations [S1, unofficial].
5.  **Early Termination:** Stop rays when a certain opacity level is reached or when traversing empty space [S1, unofficial].
6.  **Procedural Enrichment (Optional):** Use procedural methods to create additional details to enrich the data set [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Aliasing:** Appears because pixel value should be defined by integration along a cone, not just ray accumulation. Mipmapping addresses this by smoothing results and allowing larger step sizes proportional to distance [S1, unofficial].
*   **Memory Budget:** The system must respect the limited GPU memory budget, streaming only necessary data [S1, unofficial].
*   **Temporal Discontinuities:** Without adaptive resolution, transitions between subdivision levels can be discontinuous. GigaVoxels ensures smooth temporal transitions by continuously adapting resolution [S1, unofficial].

## Subtopics

### [Distributed Multi-Level Out-Of-Core Volume Rendering](6238-distributed-multi-level-out-of-core-volume-rendering.md)
A distributed GPU volume rendering system that uses a multi-level hierarchy of caches and data streaming to render volumes larger than GPU memory, maintaining a 1:1 pixel-to-voxel ratio for interactive exploration. Display-awareness selects a target resolution and corresponding octree level to bound the working set size required for ray-casting. It differs from its parent [GigaVoxels](3057-gigavoxels.md) by distributing the rendering workload across multiple GPU nodes via MPI, where each node independently streams and renders its assigned portion of the volume, rather than relying on a single node's memory hierarchy.

## Operating characteristics
*   **Performance:** 20-90 fps on current generation hardware, respecting limited GPU memory budget [S1, unofficial].
*   **Memory:** Handles volumes exceeding GPU memory capacities by far, thanks to efficient streaming based on a ray-casting solution [S1, unofficial].
*   **Quality:** Inherently anti-aliased due to mipmapping-like process [S1, unofficial].
*   **Scalability:** Supports resolutions up to $16384^3$ for hypertextured meshes and theoretically infinite for fractals [S1, unofficial].
*   **Strengths:** Real-time to interactive rates, inherent anti-aliasing, efficient memory usage, smooth temporal transitions.
*   **Limitations:** Increases memory consumption due to mipmap hierarchy, makes tree updates more challenging [S1, unofficial].

## Background
GigaVoxels was developed by Sylvain Lefebvre (INRIA Sophia-Antipolis) and Elmar Eisemann (MPI Informatik / Saarland University) [S1, unofficial]. The paper was published in the I3D 2009 conference proceedings [S1, unofficial]. It was developed in parallel to the work of Gobbetti et al. [GMAG08], sharing similarities in out-of-core voxel rendering but providing better quality/performance, procedural content generation, and level-of-detail management [S1, unofficial]. The approach is inspired by earlier works like [LHN05a] and [LKS*06], combining an adaptive version of the former with regular constant-sized memory blocks of the latter [S1, unofficial].
