# Dense 3D Texture Voxelization

Also called: Dense 3D Texture, Mip-mapped 3D Texture Voxelization

## Overview
Dense 3D Texture Voxelization is an alternative to GigaVoxels where the entire scene, including empty space, is encoded into a very large mip-mapped 3D texture [S1, unofficial]. It solves the problem of sparse data management by replacing the explicit octree structure with an implicit one defined by the mipmap levels of the 3D texture. Unlike GigaVoxels, which uses a dynamic sparse octree to stream only necessary data, this method relies on direct world-space indexing and automatic filtering, trading memory efficiency for simplified traversal and interpolation logic.

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D volume dataset (density and color/scalar fields) defined in world space.
*   **Output:** A mip-mapped 3D texture resource compatible with the graphics API (e.g., OpenGL, DirectX).

**Data Structures:**
*   **3D Texture:** A dense, hierarchical 3D texture array. The resolution decreases by a factor of 2 at each mipmap level.
*   **Implicit Octree:** The octree structure is not stored explicitly. Instead, the hierarchy is implied by the mipmap chain. Level $L$ of the texture corresponds to node depth $L$ in the conceptual octree.

**Steps:**
1.  **Voxelization:** Convert the input geometry or volume data into a dense 3D grid. Every voxel in the defined world bounds is assigned a value, even if it represents empty space.
2.  **Mipmap Generation:** Generate the mipmap chain for the 3D texture. Since bricks are spatially aligned and there are no redundant neighbor voxels (unlike sparse brick-based approaches), the filtering stage is straightforward [S1, unofficial]. Standard downsampling filters (e.g., box filter) are applied to generate lower-resolution levels.
3.  **Ray Traversal:** For each pixel, cast a ray into the scene. The ray traverses the mipmap chain rather than an explicit octree.
    *   Start at the highest resolution level (finest detail).
    *   Determine the current voxel index based on the ray's position in world space.
    *   Sample the texture at the current level.
    *   If the sample indicates empty space or if the ray has exited the volume, terminate or skip.
    *   Move to the next level of detail (coarser mipmap) as the ray travels further or to maintain a constant world-space step size relative to the resolution.
4.  **Sampling:** Use hardware texture sampling functions (e.g., `texture()` in GLSL/HLSL) to retrieve values.
    *   **Direct Indexing:** Rays index into voxel data directly because the 3D texture is a world-space representation [S1, unofficial].
    *   **Interpolation:** Quadrilinear interpolation is automatically achieved by the texture hardware due to the mip-map chain and standard texture filtering modes [S1, unofficial].

**Parameters:**
*   **Texture Resolution:** Determined by the desired maximum detail and available GPU memory.
*   **Mipmap Levels:** $\lceil \log_2(\max(W, H, D)) \rceil + 1$, where $W, H, D$ are the dimensions of the dense grid.

**Edge Cases and Pitfalls:**
*   **Memory Consumption:** Dense 3D textures are impractical for large scenes because they consume significant memory, especially for empty space that must be backed by physical memory [S1, unofficial].
*   **Empty Space:** Most scenes are sparse; storing empty voxels wastes memory and bandwidth [S1, unofficial].

## Subtopics

### Solid Texturing
Solid texturing refers to the application of procedural noise or patterns directly within the 3D texture space, often used in conjunction with dense voxelization to create complex material appearances without relying on surface geometry. In the context of dense 3D textures, this allows for consistent material definition across all mipmap levels, as the procedural function is evaluated in world space or local object space before being baked or sampled. This approach avoids texture seams and provides infinite detail theoretically, though limited by the highest resolution mipmap level. It is chosen when procedural consistency is more important than memory efficiency.

### Sparse Textures
Sparse Textures (or partially-resident textures) address the memory inefficiency of dense 3D textures by allowing certain regions of the texture to remain unbacked by physical memory. Volumes of empty space or constant-color space can be marked as non-resident, consuming no physical memory [S1, unofficial]. This capability is exposed via extensions such as `AMD_sparse_texture` on Southern Island GPUs [S1, unofficial]. When a ray accesses a non-resident region, the hardware handles the fault, typically returning a default value (e.g., zero density) without loading data into VRAM. This hybrid approach retains the simplicity of dense texture sampling while mitigating the memory footprint of empty space.

## Operating characteristics
*   **Time Complexity:** Traversal is $O(1)$ per step for indexing and sampling, but the number of steps depends on the ray length and the chosen mipmap levels. Hardware-accelerated texture sampling is highly efficient.
*   **Memory Complexity:** $O(N^3)$ where $N$ is the linear dimension of the dense grid. This is the primary limitation. The memory usage is proportional to the volume of the bounding box, regardless of scene sparsity.
*   **Measured Performance:** Not given in the sources.
*   **Strengths:**
    *   Simplified implementation: No explicit octree traversal logic or brick management required.
    *   Automatic quadrilinear interpolation via hardware texture units.
    *   Straightforward mipmap generation due to spatial alignment and lack of redundant neighbors.
*   **Limitations:**
    *   High memory consumption for large bounding boxes, especially with sparse scenes.
    *   Inefficient for scenes with large empty volumes.
*   **When to use:** Small to medium-sized dense volumes where memory is not a constraint, or when implementation simplicity is prioritized over scalability.
*   **When not to use:** Large-scale scenes with significant empty space, or when GPU memory is limited.

## Background
Dense 3D Texture Voxelization was presented as an alternative to the GigaVoxels system, which uses a sparse octree. The concept highlights the trade-off between explicit sparse data structures and dense hardware-accelerated texture sampling. It is discussed in the context of real-time voxel rendering and out-of-core techniques.
