# GigaVoxels

Also called: Dynamic Sparse Octree, GigaVoxels rendering, GigaVoxels: A Voxel-Based Rendering Pipeline For Efficient Exploration Of Large And Detailed Scenes, Ray-Guided Streaming, Sparse Voxel Octree with Hierarchical Volume Ray-Casting, Voxel Ray-Tracing with GPU Cache

## Overview
GigaVoxels is a real-time voxel-based rendering pipeline designed for the efficient exploration of large, detailed scenes containing billions of voxels [S1, unofficial][S2][S3, S4, unofficial]. It solves the problem of rendering volumetric data that exceeds GPU memory capacities by using a sparse voxel octree structure combined with GPU caching and ray-guided streaming to load only the necessary data at the required resolution [S1, unofficial][S2][S3, S4, unofficial]. Unlike sibling methods such as [Sparse Voxel Octree Ray Traversal](2451-sparse-voxel-octree-ray-traversal.md) which may assume in-core data, GigaVoxels manages out-of-core data access via a unified GPU cache, and unlike [Dense 3D Texture Voxelization](7286-dense-3d-texture-voxelization.md) which encodes empty space, it exploits sparsity to minimize memory footprint while providing inherent anti-aliasing through cone tracing [S1, S4, S5, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Sparse voxel data (static or procedural), camera parameters, transfer functions.
*   **Output:** Rendered image (color and alpha).

**Data Structures:**
The method uses a unified data structure consisting of:
1.  **Sparse Voxel Mipmap Pyramid (SVMP):** A hierarchy built by iteratively downsampling and averaging neighbors [S4, unofficial].
2.  **Generalized N3-tree (Octree):** Used for space partitioning and empty space compaction [S1, S4, unofficial]. Nodes point to either a 'brick' or a constant value for homogeneous regions [S6, unofficial]. Sibling nodes are stored adjacently so children are accessed via the pointer to the first child [S6, unofficial].
3.  **Bricks:** Low-resolution regular grids of voxels, typically $8^3$ [S5, unofficial]. Non-leaf nodes own bricks to allow mip-mapping [S6, unofficial]. Bricks store opacity, color, and normal information [S1, unofficial].
4.  **GPU Cache:** Implements an LRU (Least Recently Used) mechanism. Cache elements contain 'Oldest' and 'Newest' pointers, 'Usage sorted nodes addresses', and a 'Used nodes mask' [S3, unofficial]. New elements are added to a 'New data Stream' which is concatenated with the Octree/Bricks Pool using stream compaction [S3, unofficial].

**Algorithm Steps:**
1.  **Ray Tracing & Request Emission:** The GPU Voxel RayTracer performs hierarchical volume ray-casting. For each ray, it traverses the octree. If a node is not present at the correct resolution or a brick is missing, the ray records this information and returns a subdivision/loading request instead of just a color value [S2][S3, unofficial].
2.  **Data Streaming:** The Central Memory/Cache Manager handles structure updates. It loads requested bricks and nodes from mass storage or the GPU cache into the brick pool/node pool [S1, S3, unofficial]. This is driven by the ray-tracer's feedback, involving minimum CPU intervention [S2].
3.  **Hierarchical Volume Ray-Casting:**
    *   **Tree Descent:** The ray descends the node tree using a KD-restart algorithm to avoid stack usage [S6, unofficial].
    *   **Cone Tracing:** To determine the intersected maximum voxel size (LOD), the method uses approximate cone tracing based on the radius of the cone footprint defined by the eye and pixel extent [S5, unofficial]. This mitigates aliasing and allows larger step sizes [S4, unofficial].
    *   **Brick Marching:** If the node contains a homogeneous value, the method integrates along the ray length. Otherwise, it fetches the associated brick from the brick pool and ray-marches to accumulate density [S6, unofficial].
    *   **Accumulation:** The standard front-to-back accumulation model is used [S3, unofficial]:
        $$ C = C + (1 - \alpha) \cdot \text{Color} $$
        $$ \alpha = \alpha + (1 - \alpha) \cdot \text{Alpha} $$
        Marching terminates when the volume becomes opaque (e.g., accumulated alpha $\ge 0.98$) or when intravolume occlusion is detected [S2][S6, unofficial].
4.  **Shading:** Standard Blinn-Phong illumination is computed per sample. Normal information is derived on-the-fly using finite differences or stored directly [S3, unofficial].
5.  **Procedural Generation (Optional):** For hypertextures, noise computation is optimized by reusing previous resolution levels: $F(\text{level } N) = \text{currentNoise}(\text{level } N) + \text{previousNoise}(\text{level } N-1)$ [S1, unofficial].

**Parameters:**
*   **CUDA Compute Capability:** SM at least 2.0 [S1, unofficial].
*   **Brick Size:** Typically $8^3$ voxels [S5, unofficial].

**Edge Cases and Pitfalls:**
*   **Aliasing:** Caused by defining pixel value by ray accumulation rather than cone integration. Addressed by mipmapping and cone tracing [S4, unofficial].
*   **Popping:** Discrete mipmap levels can cause popping. Addressed by smooth transitions and continuous adaptation of resolution [S4, unofficial].
*   **Memory Budget:** The method respects limited GPU memory by streaming only visible data [S4, unofficial].

## Subtopics

### [Distributed Multi-Level Out-Of-Core Volume Rendering](6238-distributed-multi-level-out-of-core-volume-rendering.md)
A distributed variant that scales across GPU clusters using a multi-level cache hierarchy and display-aware LOD selection, avoiding data replication by relocating bricks between nodes.

### [Dense 3D Texture Voxelization](7286-dense-3d-texture-voxelization.md)
An alternative that encodes the entire scene into a large mip-mapped 3D texture, trading memory efficiency for implementation simplicity by using implicit octree structures.

## Operating characteristics
*   **Time Complexity:** Real-time to interactive rates (20-90 fps) on current generation hardware [S4, unofficial]. Complexity depends on the number of visible voxels and the depth of the octree traversal.
*   **Memory Complexity:** Out-of-core; memory usage is bounded by the GPU cache size and the brick pool, which can be adjusted to fit available hardware [S6, unofficial].
*   **Performance:** Achieves rendering of billions of voxels (e.g., $8192^3$ for 3D scans, $16384^3$ for hypertextured meshes) [S4, unofficial].
*   **Strengths:** Inherent anti-aliasing via cone tracing, smooth temporal transitions, support for procedural generation, and efficient handling of semi-transparent volumes [S4, S5, unofficial].
*   **Limitations:** Requires CUDA-compatible GPU (SM 2.0+); out-of-core rendering is essential for vast worlds but adds complexity [S1, S6, unofficial].
*   **When to use:** Real-time exploration of large, detailed voxel scenes where memory is a constraint.
*   **When not to use:** When scene is small enough to fit entirely in GPU memory without streaming, or when hardware does not support CUDA.

## Background
GigaVoxels was introduced by Sylvain Lefebvre, Elmar Eisemann, and others in 2009 (I3D 2009) [S4, S3, unofficial]. It was developed to address the limitations of previous voxel rendering methods that struggled with memory capacity and performance for large datasets. The method builds on earlier work in sparse voxel octrees [LHN05a] and brick maps [LKS*06], combining them with ray-guided streaming and GPU caching [S4, unofficial]. It has been used in applications such as the RSA Cosmos project for visualizing galaxies [S1, unofficial] and in video games for complex visual effects [S2].
