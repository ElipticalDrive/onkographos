# Sparse Voxel Octree Ray Tracing

Also called: Octree Ray Casting, Octree Raymarching, SVO Ray Marching, SVO traversal, SVO::getHit, Sparse Voxel Octree (SVO) Ray Traversal, Sparse Voxel Octree Ray Marching

## Overview
Sparse Voxel Octree (SVO) Ray Tracing is a ray traversal algorithm that finds the first intersection with a solid voxel in a 3D sparse voxel octree [S1, S2, S3, S6, unofficial]. It solves the problem of efficiently rendering complex voxel-based geometry by skipping empty space using axis-aligned slab intersection logic, avoiding the need to sample every voxel [S1, S6, unofficial]. Unlike rasterization, which requires draw calls per chunk, SVO ray tracing renders the entire scene with a single draw call (e.g., a fullscreen triangle) by firing one ray per pixel [S6, unofficial]. It sets itself apart from sibling methods like [GigaVoxels](3057-gigavoxels.md) by operating directly on the hierarchical octree structure without pre-filtering into fixed-resolution grids, and from [SVO Ray Marching with Stack-Based Navigation](2454-svo-ray-marching-with-stack-based-navigation.md) by often using implicit or fixed-point scale representations to step through tree levels rather than explicit stack-based backtracking for every pixel [S1, S4, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** Ray origin $\mathbf{r}_o$ and direction $\mathbf{r}_d$ (normalized), SVO root node index, world bounds (origin, size), and SVO metadata (max depth, root radius).
*   **Outputs:** Hit position $\mathbf{p}$, hit normal $\mathbf{n}$, hit distance $t$, and status (hit, miss, out-of-bounds).

**Data Structures:**
*   **SVO Node:** Stored in a flat array or buffer. A node is a 32-bit integer. Bit 31 (MSB) indicates if it is a solid leaf. Bits 0–23 store RGB color (8 bits per channel). If bit 31 is 0, bits 0–23 are an index to a children array [S6, unofficial].
*   **Ray Struct:** Contains `origin` (vec3), `direction` (vec3) [S4, unofficial].
*   **Hit Struct:** Contains `position` (vec3), `normal` (vec3), `distance` (float), `status` (uint) [S1, S4, unofficial].
*   **Stack (Optional):** Used in some variants for backtracking. `ParentElement` struct contains `pos` (float3), `scale` (float), `exit` (float), `index` (uint), `childIndex` (uint) [S2, unofficial]. Fixed size (e.g., 16 or 64 elements) [S2, unofficial].

**Algorithm Steps:**

1.  **Initialization:**
    *   Calculate inverse ray direction: $\mathbf{inv\_rd} = 1.0 / \mathbf{r}_d$ [S6, unofficial].
    *   Handle near-zero direction components to avoid division by zero: if $|d_i| < \epsilon$ (e.g., $10^{-4}$), clamp to $\epsilon$ or $-\epsilon$ based on sign [S5, S6, unofficial].
    *   Precompute coefficients for slab intersection:
        $$ t_{coef} = 1.0 / -|\mathbf{r}_d| $$
        $$ t_{bias} = t_{coef} \cdot \mathbf{r}_o $$
        [S4, S5, unofficial]
    *   Determine initial octant index and position based on ray direction signs. For each axis $i \in \{x, y, z\}$:
        *   If $r_{d,i} > 0$, set `octant_mask` bit $i$ (1, 2, or 4) and adjust bias: $t_{bias,i} = 3.0 \cdot t_{coef,i} - t_{bias,i}$ [S4, S5, unofficial].
        *   Initialize `pos` to 1.5 if the ray starts in the upper half of the root cube, else 0.5 (or 1.0 depending on coordinate system alignment) [S4, S5, unofficial].
    *   Calculate initial t-span for the root cube (typically [1, 2] in normalized space or world bounds):
        $$ t_{min} = \max(2.0 \cdot t_{coef,x} - t_{bias,x}, \max(2.0 \cdot t_{coef,y} - t_{bias,y}, 2.0 \cdot t_{coef,z} - t_{bias,z})) $$
        $$ t_{max} = \min(t_{coef,x} - t_{bias,x}, \min(t_{coef,y} - t_{bias,y}, t_{coef,z} - t_{bias,z})) $$
        Clamp $t_{min}$ to 0.0. If $t_{min} > t_{max}$ or $t_{max} < 0$, the ray misses the root [S4, S5, unofficial].

2.  **Traversal Loop:**
    *   While not hit and within max steps/iterations:
        *   **Check Node Validity:** Determine if the current node is valid and active. For a leaf, check if the MSB is set. For an internal node, check if it has valid children (e.g., `valid_count > 0` or specific bit masks) [S3, S6, unofficial].
        *   **Hit Condition:** If the node is a leaf and active, or if the traversal depth meets a target LOD threshold:
            *   Compute hit position: $\mathbf{p} = \mathbf{r}_o + \mathbf{r}_d \cdot t_{min}$ [S7, unofficial].
            *   Compute normal: Determine which face of the node's bounding box was hit. Calculate $\mathbf{c} = \mathbf{p} - \mathbf{node\_pos}$. Find the component with the maximum absolute normalized value. Set the normal component to $\pm 1.0$ based on the sign of $\mathbf{c}$ [S7, unofficial].
            *   Return hit [S1, S7, unofficial].
        *   **Descend:** If the node is not a leaf or active:
            *   Identify the child octant to visit next. This is often done by finding the minimum component of the t-span or using the `octant_mask` to permute child indices [S1, S4, unofficial].
            *   Update `idx` (child index) and `pos` (position in the next level) based on which axis the ray exits the current slab first [S4, S5, unofficial].
            *   Update $t_{min}$ and $t_{max}$ for the next level. The new $t_{min}$ is the exit time of the current slab, and $t_{max}$ is updated by adding the delta translation for the stepped axis [S1, unofficial].
            *   If using a stack (e.g., [SVO Ray Marching with Stack-Based Navigation](2454-svo-ray-marching-with-stack-based-navigation.md)), push the current node's state (position, scale, exit time) onto the stack before descending [S2, unofficial].
            *   If the ray exits the current node's bounds without hitting a child, pop from the stack (if available) or terminate [S2, unofficial].

3.  **Termination:**
    *   If a hit is found, return the hit struct.
    *   If the ray escapes the world bounds (checked via `worldSizeInOctants` or root box exit), return status "out of bounds" or "miss" [S1, S6, unofficial].
    *   If max iterations/steps are reached, return status "max iterations" [S1, unofficial].

    if ray_direction.y > 0:

**Parameters:**
*   `MAX_STEPS`: Maximum number of march steps per ray (e.g., 200) [S6, unofficial].
*   `MAXIMUM_TREE_DEPTH`: Maximum depth of the SVO (e.g., 30) [S3, unofficial].
*   `mRootRadius`: Default root radius of the SVO (e.g., 256.0f) [S2, unofficial].
*   `s_max`: Maximum scale (number of float mantissa bits, e.g., 23) [S4, S5, unofficial].
*   `EPS`: Epsilon for ray origin nudging (e.g., 0.0004) [S6, unofficial].
*   `Reflectivity`: Attenuation factor for reflections (e.g., 0.5f) [S5, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** Floating-point precision issues in position updates can cause self-intersection or missed hits. Use epsilon to nudge ray origin [S5, S6, unofficial].
*   **NaN/Inf:** Handle NaN and Inf in Qv (exit point calculation) by coalescing to positive infinity [S3, unofficial].
*   **Ray Direction:** Ray direction signs affect traversal order and bias calculation. Mirroring technique (octant_mask) is used to simplify math [S4, unofficial].
*   **Empty Space:** Efficiently skip empty nodes. If a node is not active, skip to the next valid node or exit [S1, S2, unofficial].
*   **Boundary Conditions:** Check if ray position is out of world bounds [S1, unofficial]. Handle rays starting inside the root cube [S3, unofficial].

## Subtopics

### [SVO Ray Marching with Stack-Based Navigation](2454-svo-ray-marching-with-stack-based-navigation.md)
SVO Ray Marching with Stack-Based Navigation is a ray traversal algorithm for Sparse Voxel Octrees (SVO) that uses an explicit stack to manage traversal state, enabling efficient navigation through the hierarchical structure to find voxel intersections. It differs from parent methods by decoupling the traversal logic from the ray's parametric distance, using a fixed-point-like scale representation to step through the tree levels, and explicitly managing node validity and corner positions via a stack of `node_info_t` elements. This approach allows for robust handling of empty space and early termination based on pixel error thresholds.

### [Octree Ray Marching with Brick Interpolation and Early Termination](4147-octree-ray-marching-with-brick-interpolation-and-early-termi.md)
This method performs volume rendering by traversing a Sparse Voxel Octree (SVO) using a hybrid approach that combines coarse space-skipping via precomputed "bricks" (sub-cubes of voxels) with fine-grained interpolation within those bricks. It solves the performance bottleneck of standard SVO traversal by reducing the number of node fetches and memory accesses required to traverse empty or uniform regions. It sets itself apart from [SVO Ray Marching with Stack-Based Navigation](2454-svo-ray-marching-with-stack-based-navigation.md) by utilizing brick interpolation to handle view-dependent sampling rates more efficiently, avoiding the overhead of maintaining a full traversal stack for every pixel.

### Octree Voxel Raycasting for Hover (Closest Active Voxel)
This variant is designed for interaction (e.g., hover effects) rather than rendering. It traverses the SVO to find the closest active voxel to the ray origin, rather than just the first hit. It maintains `closestHitDistance` and `closestEmptyDistance` to track the best hit and empty space encountered. If `depth >= currentDepth` and `hitDistance < closestEmptyDistance`, it updates the hover info to point to the empty space node, allowing for precise interaction with the voxel surface [S7, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(d)$ where $d$ is the depth of the octree, as the ray traverses from root to leaf. In practice, it is much faster than dense voxel traversal because it skips empty space.
*   **Memory Complexity:** $O(N)$ where $N$ is the number of nodes in the SVO. The SVO is stored in a flat array or buffer.
*   **Measured Performance:** Real-time performance is achievable on modern GPUs. A single draw call (fullscreen triangle) is used to render the entire scene [S6, unofficial]. Performance scales with resolution and scene complexity (number of occupied voxels).
*   **Strengths:** Efficient handling of sparse data, single draw call, no need for mesh generation, supports dynamic updates.
*   **Limitations:** Performance degrades with very dense scenes or deep octrees. Precision issues can cause artifacts. Requires careful handling of ray-box intersections and node validity checks.
*   **When to Use:** Ideal for voxel-based games, terrain rendering, and scenes with high sparsity. Not suitable for highly dense, continuous geometry where ray tracing might be slower than rasterization.

## Background
Sparse Voxel Octree Ray Tracing originated from the need to efficiently render large-scale voxel worlds, such as those in Minecraft-like games. It builds on the concept of Sparse Voxel Octrees, which provide a hierarchical representation of 3D space. The method was popularized by real-time voxel rendering techniques that leverage GPU parallelism to traverse the octree structure. Key developments include the use of fixed-point arithmetic for efficient traversal, stack-based navigation for complex scenes, and brick interpolation for volume rendering [S1, S2, S3, S4, S5, S6, unofficial].
