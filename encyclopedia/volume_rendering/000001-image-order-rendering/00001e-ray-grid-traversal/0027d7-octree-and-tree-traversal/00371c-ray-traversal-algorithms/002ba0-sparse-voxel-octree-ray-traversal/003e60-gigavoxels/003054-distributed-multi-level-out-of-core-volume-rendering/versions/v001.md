# Distributed Multi-Level Out-Of-Core Volume Rendering

Also called: Display-Aware Multi-Resolution Volume Streaming and Ray-Casting, Distributed Volume Rendering

## Overview
A distributed GPU volume rendering system that uses a multi-level hierarchy of caches and data streaming to render volumes larger than GPU memory, maintaining a 1:1 pixel-to-voxel ratio for interactive exploration [S1, unofficial]. Display-awareness selects a target resolution and corresponding octree level to bound the working set size required for ray-casting [S1, unofficial]. It differs from its parent [GigaVoxels](3057-gigavoxels.md) by distributing the rendering workload across multiple GPU nodes via MPI, where each node independently streams and renders its assigned portion of the volume, rather than relying on a single node's memory hierarchy [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: Large volumetric dataset (e.g., EM volumes > 40 GB), camera parameters, target display resolution.
- Output: Compositing of partial images from cluster nodes into a final image [S1, unofficial].

**Data Structures:**
The system employs a two-level hierarchy of 3D page caches for Virtual Volume Texturing [S1, unofficial]:
1.  **Top-Level Page Directory Texture:** Fully resident in GPU memory. For a 92 GB volume, this is $32 \times 32 \times 1$ entries [S1, unofficial]. Each entry refers to a block of $32^3$ second-level page table entries.
2.  **Page Table Cache Texture:** Stores second-level page table entries. For the 92 GB volume, this is a $64^3$ texture containing $563 \times 563 \times 10$ entries [S1, unofficial]. Each entry refers to a small block of $32^3$ physical voxels [S1, unofficial].
3.  **Physical 3D Cache Texture:** The actual voxel data cache in GPU RAM. For the 92 GB volume, this is $1,024^3$ voxels [S1, unofficial].
4.  **CPU Cache:** A superset of the current working set kept in CPU RAM to minimize disk traffic when blocks are reused in future frames [S1, unofficial].

**Steps:**
1.  **Target Resolution Selection:** Determine the target pixel-to-voxel ratio (approximately 1:1) based on the output display resolution [S1, unofficial]. This display-aware approach bounds the working set size [S1, unofficial].
2.  **Octree Level Selection:** Select the corresponding octree level that matches the target resolution [S1, unofficial].
3.  **View Frustum Culling:** Determine the list of volume blocks required for the current view by the ray-caster via view frustum culling [S1, unofficial].
4.  **Cache Check:** Check whether all required blocks fit into the physical texture cache [S1, unofficial].
5.  **Coarsening (if needed):** If the required blocks do not fit into the physical texture cache, use a coarser octree level [S1, unofficial].
6.  **Streaming:** Stream all needed blocks into the single 3D cache texture in GPU RAM [S1, unofficial]. Each GPU node independently streams in voxel data on demand, guided by the render resolution [S1, unofficial].
7.  **CPU Caching:** Keep a larger subset of the required blocks in CPU RAM to minimize overall disk traffic when blocks are reused in a future frame [S1, unofficial].
8.  **Ray-Casting:** Perform volume rendering by ray-casting using CUDA [S1, unofficial]. Sample positions are computed in virtual volume space. Physical data voxels are fetched from the large 3D cache texture [S1, unofficial].
9.  **Mixed Resolution:** While streaming in higher-resolution data, lower-resolution data can be freely mixed in by the ray-caster [S1, unofficial].
10. **Compositing:** After compositing the partial images produced by the cluster nodes, the final image is compressed and then transmitted to the client [S1, unofficial].

**Pseudocode:**
```python
# Pseudocode for a single GPU node in the cluster
def render_node(node_id, volume_data, camera, target_resolution):
    # 1. Determine target resolution and octree level
    # Target pixel-to-voxel ratio is ~1:1
    octree_level = select_octree_level(target_resolution)
    
    # 2. View Frustum Culling
    required_blocks = view_frustum_culling(volume_data, camera, octree_level)
    
    # 3. Check Cache Capacity
    # Physical cache size is fixed (e.g., 1024^3 voxels)
    if not fits_in_cache(required_blocks, physical_cache_size):
        # 4. Coarsen if necessary
        octree_level = coarsen_octree_level(octree_level)
        required_blocks = view_frustum_culling(volume_data, camera, octree_level)
        
    # 5. Stream Data
    # Stream required blocks into GPU 3D cache texture
    # Use CPU cache to minimize disk traffic for reused blocks
    stream_blocks_to_gpu(required_blocks, cpu_cache, gpu_cache)
    
    # 6. Ray-Casting
    # Initialize output buffer
    partial_image = initialize_buffer(target_resolution)
    
    for each pixel in partial_image:
        # Compute ray in virtual volume space
        ray = compute_ray(camera, pixel)
        
        # Traverse octree and fetch voxels
        color = ray_cast(ray, octree_level, gpu_cache)
        
        # Composite into partial image
        partial_image[pixel] = color
        
    # 7. Return partial image for cluster compositing
    return compress(partial_image)
```

**Parameters:**
- Target pixel-to-voxel ratio: Approximately 1:1 [S1, unofficial].
- Block size: $32^3$ physical voxels per second-level page table entry [S1, unofficial].
- Physical cache size: Varies by node, but examples use $1,024^3$ voxels [S1, unofficial].

**Edge Cases and Pitfalls:**
- If the total physical texture memory across all nodes is insufficient for the target resolution, the system automatically coarsens the octree level, resulting in reduced resolution [S1, unofficial].
- Precision issues may arise when mapping virtual volume coordinates to physical cache indices if the page table hierarchy is not carefully managed [G].

## Subtopics

### Virtual Volume Texturing
A technique using a two-level hierarchy of 3D page caches (page directory and page table) to map virtual volume coordinates to physical cache locations, enabling large volumes to be rendered with limited GPU memory [S1, unofficial].

### Display-Aware Streaming
A strategy that selects the octree level based on the target display resolution to bound the working set size, ensuring efficient memory usage and consistent visual quality [S1, unofficial].

## Operating characteristics
- **Time Complexity:** Rendering time depends on the number of nodes and the volume size. For a 43 GB volume, render times range from 0.12 sec to 1.28 sec on a single node, depending on the octree level and view [S1, unofficial].
- **Memory Complexity:** The working set size is bounded by the target resolution and the physical cache size. More nodes increase the total working set, allowing full resolution rendering [S1, unofficial].
- **Measured Performance:**
    - Dataset #1 (43 GB): Render times on 1 node: 1.28, 0.34, 0.27, 0.70, 0.28, 0.18, 0.19, 0.15, 0.12, 0.7, 0.33, 0.34 sec [S1, unofficial].
    - Dataset #2 (92 GB): Rendered on 1 to 8 Tesla nodes [S1, unofficial].
- **Scaling:** More nodes increase the working set and thus allow full resolution rendering. Fewer nodes can render the entire volume but with reduced resolution [S1, unofficial].
- **Strengths:** Enables interactive exploration of very large volumes (e.g., 92 GB) that exceed single GPU memory. Display-awareness ensures consistent visual quality.
- **Limitations:** Requires a cluster of GPU nodes. Performance is limited by network bandwidth and disk I/O for streaming [S1, unofficial].

## Background
This method was presented by NVIDIA researchers (including Dave Luebke) in a 2010 poster [S1, unofficial]. It was used for interactive exploration of neuroscience EM volumes, specifically mouse hippocampus data from the Harvard Center for Brain Science [S1, unofficial]. The system was implemented on Tesla GPU nodes and used MPI for distributed rendering [S1, unofficial].
