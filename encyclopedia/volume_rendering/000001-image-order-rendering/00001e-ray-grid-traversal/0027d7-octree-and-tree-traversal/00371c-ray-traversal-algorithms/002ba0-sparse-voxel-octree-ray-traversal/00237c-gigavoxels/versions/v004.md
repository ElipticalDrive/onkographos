# GigaVoxels

Also called: Dynamic Sparse Octree, Ray-Guided Streaming
## Overview
GigaVoxels is a real-time voxel-based rendering pipeline for efficient exploration of large and detailed scenes, using a sparse voxel octree data structure, GPU caching, and ray-guided streaming to load only needed data at the needed resolution [S1, unofficial][S2, unofficial]. It differs from its parent [Sparse Voxel Octree Ray Traversal](2451-sparse-voxel-octree-ray-traversal.md) by introducing a hierarchical mipmap-like structure and a centralized cache manager that streams data on demand based on rendering requests, enabling out-of-core rendering of volumes exceeding GPU memory [S1, unofficial][S2, unofficial]. Unlike view-independent structures, it continuously adapts resolution based on the current view and occlusion, ensuring smooth temporal transitions and inherent anti-aliasing via cone tracing [S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Large volumetric datasets (e.g., 3D scans, hypertextured meshes, fractals), camera parameters, and optional procedural definitions (e.g., noise functions, distance fields) [S1, unofficial][S2, unofficial].
*   **Output:** Final rendered image with accumulated color and opacity [S1, unofficial].

**Data Structures:**
The system uses a unified data structure consisting of:
1.  **Sparse Voxel Mipmap Pyramid:** A hierarchy built by iteratively downsampling and averaging neighbors. Each level represents a coarser resolution of the volume [S2, unofficial].
2.  **Generalized N3-tree (Octree):** Used for space partitioning and empty space compaction. It is a "node pointer based" structure that links bricks of voxels [S1, unofficial].
3.  **Bricks of Voxels:** Regular constant-sized memory blocks storing opacity, color, and normals. These are linked by octree nodes [S1, unofficial].
4.  **Data Cache:** Implemented as a 3D texture for reading and bound with surfaces for writing data. It uses an LRU (Least Recently Used) mechanism to maintain temporal coherence [S1, unofficial].

**Pipeline Steps:**
The rendering pipeline operates in a sequence of frames:
1.  **Voxel RayTracer:** Emits data usage requests based on the current view and ray-casting needs [S1, unofficial].
2.  **Central Memory/Cache Manager:** Handles structure updates and loads data from mass storage or GPU cache. It manages two loading modes:
    *   Level by level (coarse to fine) for speed trade-off [S1, unofficial].
    *   Directly max level of resolution for quality first [S1, unofficial].
3.  **Renderer:** Performs hierarchical volume ray-casting, cone tracing, and brick marching [S1, unofficial].

**Procedural Data Generation (On-Demand):**
Procedural methods (e.g., Mandelbulb, hypertextures) are used to enrich the dataset. Data production occurs on the GPU via custom kernels:
*   **Nodes Subdivision:** A kernel uses 1 block per node and 1 thread per child node. It tests if the child node is inside the object (e.g., analytically for a sphere) and writes node data to the cache [S1, unofficial].
*   **Bricks of Voxels Production:** A kernel uses 1 block per brick. The user populates the voxels based on localization info (LOD depth, spatial index) and writes them to the data cache [S1, unofficial].

**Noise Optimization for Hypertextures:**
To mimic LOD, noise computation is reused from previous resolution levels. Only one octave of noise is computed per level of resolution and stored in the GPU cache. The total noise value is reproduced by summing the current and previous octave:
$$ F(\text{level } N) = \text{currentNoise}(\text{level } N) + \text{previousNoise}(\text{level } N-1) $$
This replaces expensive noise computation with cache fetches [S1, unofficial].

**Rendering Algorithm (Cone Tracing):**
The renderer uses a custom shader kernel for ray casting. It samples data using a brick sampler and accumulates color. Key parameters are exposed via shader entry points:
*   `getConeAperture()`: Modifies the cone aperture for depth of field or filtering [S1, unofficial].
*   `getStopCriterion()`: Stops ray marching when a certain opacity is reached (e.g., `accumulatedColor.w >= 0.98f`) [S1, unofficial].
*   `getDescentCriterion()`: Used during visit traversal to decide whether to descend into finer levels [S1, unofficial].

The core accumulation step in the shader is:
```python
# Retrieve first channel element: color
color = brickSampler.getValue<0>(coneAperture)
# channel 0 is color
if color.w > 0.0f:
    _accumulatedColor = _accumulatedColor + (1.0f - _accumulatedColor.w) * color
```
This approximates the cone integral defined by the eye and pixel extent, addressing aliasing and allowing larger step sizes proportional to distance [S2, unofficial].

**OpenGL Interoperability:**
To mix triangles and voxels, opaque objects are rendered first to the depth buffer to skip occluded parts. GigaVoxels registers textures, render buffers, and PBOs with optimized flags (e.g., `cudaGraphicsRegisterFlagsReadOnly`, `cudaGraphicsRegisterFlagsWriteDiscard`) [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Aliasing:** Appears because pixel value should be defined by integration along a cone, not just ray accumulation. Mipmapping addresses this by smoothing results [S2, unofficial].
*   **Sparse-Twice Data:** Scenes with dense clusters in free space require compaction and fast traversal of empty space to avoid performance degradation [S2, unofficial].
*   **Precision:** The system requires CUDA Compute Capability SM at least 2.0 for clock cycle measurement and efficient execution [S1, unofficial].

## Subtopics

### [Distributed Multi-Level Out-Of-Core Volume Rendering](6238-distributed-multi-level-out-of-core-volume-rendering.md)
A distributed GPU volume rendering system that uses a multi-level hierarchy of caches and data streaming to render volumes larger than GPU memory, maintaining a 1:1 pixel-to-voxel ratio for interactive exploration. Display-awareness selects a target resolution and corresponding octree level to bound the working set size required for ray-casting. It differs from its parent [GigaVoxels](3057-gigavoxels.md) by distributing the rendering workload across multiple GPU nodes via MPI, where each node independently streams and renders its assigned portion of the volume, rather than relying on a single node's memory hierarchy.

## Operating characteristics
*   **Time and Memory Complexity:** The method achieves real-time to interactive rates (20-90 fps) on current generation hardware by respecting limited GPU memory budgets [S2, unofficial]. It loads only needed data at the needed resolution, providing memory and speed gains [S2, unofficial].
*   **Measured Performance:** Demonstrated on volumes exceeding GPU memory capacities, including 8192^3 resolution for 3D scans, 16384^3 for hypertextured meshes, and theoretically infinite for fractals [S2, unofficial].
*   **Scaling:** The system allows a trade-off between quality and performance by exploiting temporal coherence and adaptive resolution [S2, unofficial].
*   **Strengths:** Inherent anti-aliasing via cone tracing, smooth temporal transitions, support for procedural content, and efficient handling of sparse-twice data structures [S2, unofficial].
*   **Limitations:** Increases memory consumption due to mipmapping and makes tree updates more challenging [S2, unofficial]. Requires CUDA Compute Capability SM 2.0 or higher [S1, unofficial].
*   **When to Use:** For real-time exploration of large, detailed volumetric scenes that exceed GPU memory, especially when procedural generation or dynamic LOD is required [S1, unofficial][S2, unofficial].
*   **When Not to Use:** When static, view-independent rendering is sufficient and procedural generation is not needed, simpler structures like [LHN05a] or [LKS*06] might be more appropriate [S2, unofficial].

## Background
GigaVoxels was developed by Sylvain Lefebvre, Elmar Eisemann, and others at INRIA Sophia-Antipolis and MPI Informatik/Saarland University [S2, unofficial]. The approach was presented in the I3D 2009 conference proceedings and further detailed in a 2013 NVIDIA GTC talk by Pascal Guehl and Fabrice Neyret [S1, unofficial][S2, unofficial]. It was developed in parallel to the work of Gobbetti et al. [GMAG08], offering better quality/performance and procedural content generation [S2, unofficial]. The method builds on earlier sparse voxel octree structures [LHN05a] and brick maps [LKS*06], adapting them for dynamic, view-dependent streaming [S2, unofficial].
