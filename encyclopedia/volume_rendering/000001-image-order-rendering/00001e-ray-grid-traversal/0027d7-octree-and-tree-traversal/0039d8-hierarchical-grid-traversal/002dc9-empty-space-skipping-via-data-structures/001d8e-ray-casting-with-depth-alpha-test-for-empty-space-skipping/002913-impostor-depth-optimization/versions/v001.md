# Impostor Depth Optimization

Also called: Nearest-point quad impostors, Depth-test culling for impostors

## Overview
Impostor Depth Optimization is a rendering acceleration technique that uses camera-facing quads placed at the nearest point of volumetric primitives (such as spheres) to leverage the GPU's depth test for early culling. It solves the performance bottleneck in deep piles of overlapping objects where full shading (including ray tracing) is prohibitively expensive. It sets itself apart from standard ray casting by replacing per-object ray-volume intersection logic with a fixed-screen-space primitive that triggers hardware depth discard, effectively skipping the fragment shader for occluded layers [S1, unofficial].

## How it works
**Inputs and outputs:**
- Input: A set of volumetric primitives (e.g., spheres) with known positions and radii.
- Input: A camera view matrix and projection matrix.
- Output: A rendered image where occluded primitives are skipped without executing their fragment shaders.

**Data structures:**
- `sorted_positions_buffer`: Array of primitive centers, sorted front-to-back relative to the camera.
- `sorted_indices_buffer`: Array of indices corresponding to `sorted_positions_buffer`.
- `cell_offsets_buffer`: Offsets for grid-based access (if applicable).
- `cell_size`: Size of grid cells.
- `grid_origin`: Origin of the grid.

**Steps:**
1. **Sort Primitives:** Sort all primitives based on their distance to the camera plane, ensuring front-to-back ordering. This relies on stable sorting to maintain initial lattice order if needed [S1, unofficial].
2. **Compute Nearest Point:** For each primitive, calculate the point on its surface closest to the camera. For a sphere with center $C$ and radius $R$, and a camera position $P$, the nearest point $N$ is:
   $$ N = C + R \cdot \frac{P - C}{\|P - C\|} $$
   [G] This assumes the camera is outside the sphere. If the camera is inside, the nearest point is undefined for culling purposes; such cases should be handled separately or treated as fully visible.
3. **Generate Quads:** Create a quad (two triangles) centered at $N$ and oriented to face the camera. The quad's size should be sufficient to cover the sphere's silhouette from the camera's perspective.
4. **Render Quads:**
   - Enable the depth test.
   - **Do not write to the depth buffer** (`frag_depth`) in the fragment shader. Writing `frag_depth` forces the fragment shader to execute before the depth test, negating the culling benefit [S1, unofficial].
   - Render the quads in the sorted front-to-back order.
   - The depth test will discard fragments of quads that are behind already-rendered (closer) quads.
5. **Skip Shading:** For discarded fragments, the fragment shader (including any expensive ray tracing or volume sampling) is not executed.

**Parameters:**
- Sorting order: Front-to-back is critical for effective culling [S1, unofficial].
- Quad size: Must be large enough to cover the primitive's projection.

**Edge cases and pitfalls:**
- **Overlapping Artifacts:** Overlapping spheres rendered via this method meet along flat lines (the edges of the quads) instead of smooth curves. This visual artifact is often negligible at typical scene scales [S1, unofficial].
- **Depth Buffer Writing:** Writing `frag_depth` must be avoided. If written, the depth test occurs after shading, causing all layers in a deep pile to run full shading, including ray tracing [S1, unofficial].
- **Camera Inside Primitive:** If the camera is inside a sphere, the nearest point logic fails. This case requires special handling or fallback to standard rendering.

**Pseudocode:**
```python
def render_impostors(primitives, camera_pos, view_matrix, proj_matrix):
    # Step 1: Sort primitives front-to-back
    # Calculate distance from camera to each primitive's center
    distances = [distance(camera_pos, p.center) for p in primitives]
    sorted_indices = argsort(distances) # Stable sort
    sorted_primitives = [primitives[i] for i in sorted_indices]

    # Step 2 & 3: Generate and render quads
    for p in sorted_primitives:
        # Calculate nearest point on sphere surface to camera
        direction = normalize(camera_pos - p.center)
        nearest_point = p.center + p.radius * direction

        # Generate quad at nearest_point, facing camera
        # Quad size should cover sphere's silhouette
        quad = generate_camera_facing_quad(nearest_point, p.radius * 2)

        # Step 4: Render quad
        # Enable depth test
        # Disable depth buffer writing (do not write frag_depth)
        render(quad)
```

## Subtopics

## Operating characteristics
- **Time Complexity:** Sorting is $O(N \log N)$ where $N$ is the number of primitives. Rendering is $O(K)$ where $K$ is the number of visible (non-occluded) primitives.
- **Memory Complexity:** $O(N)$ for storing sorted positions and indices.
- **Performance:** In headless Chrome, ray-traced scenes with deep piles of spheres saw frame times drop from ~92 ms to the 16.7 ms vsync cap [S1, unofficial].
- **Strengths:** Significant performance gains for deep piles of overlapping objects; leverages hardware depth test.
- **Limitations:** Visual artifacts at overlaps (flat lines); requires front-to-back sorting; not suitable for transparent blending without additional care.

## Background
This technique was implemented in the `kansei` project, specifically in the `voxel-gi-particles` example, to optimize ray-traced particle rendering [S1, unofficial]. It addresses the performance issues encountered when rendering deep piles of spheres with ray tracing enabled.
