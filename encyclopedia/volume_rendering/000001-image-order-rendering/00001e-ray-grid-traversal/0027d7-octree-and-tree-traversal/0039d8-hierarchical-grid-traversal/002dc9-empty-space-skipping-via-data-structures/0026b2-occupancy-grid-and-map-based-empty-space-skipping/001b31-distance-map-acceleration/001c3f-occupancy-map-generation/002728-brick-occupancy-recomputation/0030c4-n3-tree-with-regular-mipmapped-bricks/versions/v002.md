# N3-tree with regular mipmapped bricks

Also called: N3-tree with regular voxel bricks, N3-tree+briques de voxels

## Overview
The N3-tree with regular mipmapped bricks is a two-level hierarchical data structure for procedural volume exploration that combines an N-ary tree (N3-tree) for hierarchy with regular voxel bricks stored in the leaves [S1, unofficial]. It links the compactness of a hierarchical structure with the efficient traversal and trilinear/quadrilinear filtering capabilities of regular grids on GPU [S1, unofficial]. It generalizes the original octree-based Brick Maps to allow arbitrary subdivision of nodes (N-ary instead of binary octree) to enable efficient GPU traversal [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A procedural volume defined by a total maximum resolution $R_t$ on each axis, a maximum brick resolution $R_b$, and a node subdivision resolution $N$ [S1, unofficial].
*   **Output:** A GPU-accessible structure consisting of an indirection texture (the tree), a brick storage texture (the data), and a brick indirection storage (mip-level mapping) [S1, unofficial].

**Data Structures:**
1.  **Indirection Storage (The Tree):**
    *   **Format:** 3D texture using an unsigned integer RGBA format with 32 bits per component [S1, unofficial].
    *   **Layout:** Each node in the N3-tree is stored as a small $N^3$ grid of indirection cells within this texture [S1, unofficial].
    *   **Spatial Locality:** The $N^3$ grids are organized using a Peano curve (Swizzled Walk) layout to maximize cache efficiency during tree traversal [S1, unofficial].
    *   **Cell Encoding (Sub-node information):** Each cell contains 32 bits packed as follows [S1, unofficial]:
        *   **Red (R):** 3D address (X, Y, Z) of the child node or the regular brick in the brick storage [S1, unofficial].
        *   **Green (G):** 3D address of the parent node [S1, unofficial].
        *   **Blue (B):** Reserved for future use [S1, unofficial].
        *   **Alpha (A):** Average value of all voxels in the node's covered space [S1, unofficial].
    *   **Flags:** 1 bit identifies the sub-node type (brick or tree node) and 1 bit identifies an empty node flag (no descendants) [S1, unofficial].
    *   **Addressable Dimension:** The 10-bit address per coordinate allows addressing elements in a storage of maximum dimension $1024^3$ [S1, unofficial].

2.  **Brick Storage (The Data):**
    *   **Format:** 3D texture storing regular scalar density data or gradients [S1, unofficial].
    *   **Layout:** Divided into zones grouping bricks of identical resolution [S1, unofficial].
    *   **Brick Structure:** Each brick includes its data plus a 1-voxel border surrounding the data to allow trilinear filtering without artifacts from adjacent bricks [S1, unofficial].
    *   **Filtering:** Accessed in the shader by floating-point coordinates; integer coordinates from the indirection storage are transformed on the fly [S1, unofficial].

3.  **Brick Indirection Storage:**
    *   **Purpose:** Links the hierarchical tree to brick data [S1, unofficial].
    *   **Content:** A list of addresses for each brick's data for every mip-mapping level in the brick storage [S1, unofficial].
    *   **Unloaded Data:** Entries marked with a negative value indicate unloaded data [S1, unofficial].

**Manual Mip-mapping:**
Hardware mip-mapping requires duplicating the 1-voxel border $2^n$ times for a stack of $n$ levels and halving it at each sub-level, which is memory expensive [S1, unofficial]. This method implements 3D mip-mapping manually to achieve identical performance cost but with lower memory overhead [S1, unofficial].

**Number of Nodes:**
In the worst case (full resolution, no empty space skipping), the number of nodes to store in the tree is calculated as [S1, unofficial]:
$$ \sum_{i=0}^{n} \left( \frac{Nb}{N^i} \right)^3 $$
Where:
*   $n = \frac{\log(Nb)}{\log N}$
*   $Nb = \frac{R_t}{R_b}$
*   $R_t$: Total maximum resolution on each axis [S1, unofficial].
*   $R_b$: Maximum resolution of a brick [S1, unofficial].
*   $N$: Resolution of each node (e.g., $N=2$ for octree) [S1, unofficial].

**Parameters:**
*   **Example:** $R_t = 1024^3$, $N = 4$, $R_b = 16$ [S1, unofficial].
*   **Result:** An indirection storage of $64^3$ is nearly sufficient [S1, unofficial].
*   **Recommended Size:** A practical recommended size is $128^3$ [S1, unofficial].
*   **Degrees of Freedom:** Node subdivision resolution ($N$) and regular brick resolution [S1, unofficial]. These impact traversal performance and update efficiency [S1, unofficial].

**Pseudocode:**
```python
import math

def encode_address_3d(x, y, z):
    """Encodes a 3D address into a 30-bit integer (10 bits per coordinate)."""
    return (x << 20) | (y << 10) | z

def pack_subnode(child_addr_30bit, parent_addr_30bit, node_type_bit, empty_flag):
    """Packs sub-node information into a 32-bit integer for the Red channel.
    30 bits address, 1 bit type, 1 bit empty."""
    return (child_addr_30bit << 2) | (node_type_bit << 1) | empty_flag

def generate_peano_coords(dim):
    """Generates Peano curve coordinates for a dim x dim x dim grid [G]."""
    coords = []
    def peano_recursive(level, x, y, z, orientation):
        if level == 0:
            coords.append((x, y, z))
            return
        step = 1 << (level - 1)
        if orientation == 0:
            peano_recursive(level - 1, x, y, z, 1)
            peano_recursive(level - 1, x + step, y, z, 0)
            peano_recursive(level - 1, x + step, y + step, z, 0)
            peano_recursive(level - 1, x, y + step, z, 3)
        elif orientation == 1:
            peano_recursive(level - 1, x, y, z, 0)
            peano_recursive(level - 1, x, y + step, z, 0)
            peano_recursive(level - 1, x + step, y + step, z, 1)
            peano_recursive(level - 1, x + step, y, z, 2)
        elif orientation == 2:
            peano_recursive(level - 1, x + step, y + step, z, 3)
            peano_recursive(level - 1, x + step, y, z, 2)
            peano_recursive(level - 1, x, y, z, 2)
            peano_recursive(level - 1, x, y + step, z, 1)
        else:
            peano_recursive(level - 1, x + step, y + step, z, 2)
            peano_recursive(level - 1, x, y + step, z, 2)
            peano_recursive(level - 1, x, y, z, 3)
            peano_recursive(level - 1, x + step, y, z, 0)
    peano_recursive(int(math.log2(dim)), 0, 0, 0, 0)
    return coords

def calculate_tree_size(Rt, Rb, N):
    """Calculates the worst-case number of nodes in the N3-tree."""
    Nb = Rt / Rb
    n = math.log(Nb) / math.log(N)
    total_nodes = 0
    for i in range(int(n) + 1):
        total_nodes += (Nb / (N ** i)) ** 3
    return total_nodes

def build_indirection_texture(Rt, Rb, N):
    """Constructs the indirection texture structure."""
    nodes_count = calculate_tree_size(Rt, Rb, N)
    tex_dim = 128  # Recommended practical size
    peano_coords = generate_peano_coords(tex_dim)
    
    # Initialize texture as a flat list of 32-bit integer tuples
    texture = [None] * (tex_dim ** 3)
    
    # Precompute brick address for root leaf if needed, or use 0
    root_brick_addr = encode_address_3d(0, 0, 0)
    
    # Populate texture using Peano order
    for idx, (px, py, pz) in enumerate(peano_coords):
        # For simplicity, assume root node covers the whole volume
        # In a real traversal, this would be recursive based on data density
        child_addr = root_brick_addr
        parent_addr = 0
        node_type = 1  # Brick
        empty_flag = 0
        
        r_channel = pack_subnode(child_addr, parent_addr, node_type, empty_flag)
        g_channel = encode_address_3d(parent_addr >> 20, (parent_addr >> 10) & 0x3FF, parent_addr & 0x3FF)
        b_channel = 0
        a_channel = 0  # Average value placeholder
        
        texture[px * tex_dim ** 2 + py * tex_dim + pz] = (r_channel, g_channel, b_channel, a_channel)
        
    return texture

def build_brick_storage(Rt, Rb):
    """Constructs the brick storage texture and brick indirection storage."""
    num_bricks = Rt / Rb
    brick_indirection = []
    
    for x in range(int(num_bricks)):
        for y in range(int(num_bricks)):
            for z in range(int(num_bricks)):
                brick_addr = encode_address_3d(x, y, z)
                mip_levels = int(math.log2(Rb)) + 1
                brick_entry = [-1] * mip_levels
                brick_entry[0] = brick_addr
                brick_indirection.append(brick_entry)
                
    return brick_indirection
```

### Hierarchical Grid Traversal
The broader category of ray-grid traversal techniques that use hierarchical structures to skip empty space. [Hierarchical Grid Traversal](52-name.md)

## Operating characteristics
*   **Time Complexity:** Traversal is efficient on GPU due to the regular grid structure of leaves and the use of 3D textures which exploit hardware cache spatial locality (via Peano curve layout) [S1, unofficial].
*   **Memory Complexity:** The indirection storage size is determined by the worst-case node count [S1, unofficial]. For $R_t=1024^3, N=4, R_b=16$, a $64^3$ texture is nearly sufficient, but $128^3$ is recommended for practical scenes [S1, unofficial]. The manual mip-mapping reduces memory overhead compared to hardware mip-mapping by avoiding border duplication [S1, unofficial].
*   **Strengths:** Combines hierarchical compactness with regular grid filtering efficiency [S1, unofficial]. Manual mip-mapping saves memory [S1, unofficial]. Peano curve layout optimizes cache hits [S1, unofficial].
*   **Limitations:** Worst-case memory usage can be high if the volume is dense [S1, unofficial]. Update efficiency is secondary to traversal performance but impacted by the choice of $N$ and brick resolution [S1, unofficial].
*   **When to use:** Procedural volume exploration on GPU where memory bandwidth and cache efficiency are critical [S1, unofficial].
*   **When not to use:** If hardware mip-mapping memory overhead is not a concern and the volume is sparse enough that a simpler octree suffices [S1, unofficial].

## Background
The method was developed by Sylvain Lefebvre et al. as an adaptation of the hierarchical volumetric textures model proposed by Sylvain Lefebvre [LHN05] for GPU implementation [S1, unofficial]. It generalizes the Brick Maps proposed by Christensen and Batali [CB04] for global illumination [S1, unofficial]. The work is part of the thesis "Représentation et algorithmes pour l'exploration interactive de volumes procéduraux étendus et détaillés" [S1, unofficial].
