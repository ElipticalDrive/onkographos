# Residency Octree

Also called: Residency-Octree Hierarchy, hybrid data structure for out-of-core volume rendering, multi-resolution page tables combined with a special octree data structure

## Overview
The Residency Octree is a hybrid data structure for out-of-core direct volume rendering (DVR) of large-scale, multi-channel volumetric datasets [S2]. It solves the problem of limited GPU memory and inefficient cache usage by decoupling the spatial subdivision of the octree from the resolution levels of the underlying bricked volume hierarchy [S1, unofficial]. Unlike standard octrees where each node maps to exactly one brick (one-to-one correspondence), a Residency Octree node represents a geometric spatial region and maps to a set of bricks across all resolution levels [S1, unofficial]. This allows the renderer to adaptively mix resolutions, substitute missing high-resolution data with available lower-resolution data, and perform fine-grained empty-space skipping independent of the data's bricking granularity [S2]. It combines the flexible, multi-resolution access of page-table hierarchies with the efficient traversal and culling of octrees [S1, unofficial].

## How it works
### Inputs and Outputs
*   **Input:** A multi-resolution, multi-channel bricked volume dataset (typically stored on a server or file system), a brick cache (GPU memory), and a user-defined approximate leaf-node size in voxels [S1, unofficial].
*   **Output:** A fully or partially constructed Residency Octree in GPU memory, containing metadata and residency bitmaps, used to guide ray traversal and data streaming [S2].

### Data Structures
The Residency Octree is implemented as a **full, pointerless octree** [S1, unofficial]. All nodes are pre-allocated in a contiguous storage buffer with fixed locations, removing indirection from child pointers [S1, unofficial].

**Node Layout:**
Each node consists of $m$ unsigned 32-bit integers, where $m$ is the number of simultaneously visualized channels ($m \le n$, where $n$ is the total available channels) [S1, unofficial]. For each channel, the 32-bit integer is structured as follows:
*   **16 bits:** Bitmap indicating which resolution levels the node is at least *partially mapped* in [S1, unofficial].
*   **8 bits:** Minimum scalar value in the node's spatial extent [S1, unofficial].
*   **8 bits:** Maximum scalar value in the node's spatial extent [S1, unofficial].

For multi-channel support, if a node's data for a specific channel is not yet initialized (INVALID), it stores a pointer to the nearest lower subdivision level node that has valid information for that channel, or a special `UNKNOWN` value if none exists [S1, unofficial]. This pointer replaces the metadata for that channel to save memory [S1, unofficial].

**Residency States:**
For a given resolution level, a node is:
1.  **Fully mapped:** Cache-resident bricks of that level fully cover the node's spatial extent [S2].
2.  **Partially mapped:** At least one brick of that level spatially overlaps with the node's extent and is resident [S2].
3.  **Not mapped:** No bricks of that level are resident [S1, unofficial].

*Note:* If a node is fully mapped in a resolution level, all its children are also fully mapped in that level. If a node is partially mapped, its parent is also partially mapped [S2]. If a node is empty or homogeneous (determined by min/max metadata), it is implicitly considered fully mapped in all resolution levels, meaning no bricks need to be resident [S1, unofficial].

### Algorithm Steps

1.  **Initialization:**
    *   Determine the number of subdivision levels based on the user-defined approximate leaf-node size in voxels [S1, unofficial].
    *   Pre-allocate the pointerless octree buffer [S1, unofficial].
    *   Initialize the brick cache and the backing multi-channel page table hierarchy [S2].

2.  **Ray Traversal and Request Generation:**
    *   Traverse the octree for each ray sample. Start traversal at the third level (or a level appropriate for the current view) and resume from the parent of the last visited node to minimize traversal cost [S2].
    *   For each node visited, check the residency bitmap for the required channels and resolution levels [S1, unofficial].
    *   If the required brick data is missing (cache miss), generate a request to the server/file system [S2]. This request is generated during ray traversal, making the method ray-guided [S1, unofficial].

3.  **Data Streaming and Cache Management:**
    *   When a brick is received, select an available slot in the brick cache [S1, unofficial].
    *   Identify all residency octree leaf nodes whose spatial extent overlaps the brick's spatial extent [S2].
    *   Mark these nodes as **partially mapped** in the brick's resolution level and channel [S2].
    *   Propagate this update up the tree to the root node [S2].
    *   If the node was not previously mapped in that level, update the bitmap [S1, unofficial].

4.  **Metadata Construction (Bottom-Up):**
    *   Metadata (min/max values) for a parent node is computed from its children:
        $$ \text{min}_{parent} = \min(\text{min}_{child_1}, \dots, \text{min}_{child_8}) $$
        $$ \text{max}_{parent} = \max(\text{max}_{child_1}, \dots, \text{max}_{child_8}) $$
    *   This allows parallel bottom-up construction [S1, unofficial].
    *   *Pitfall:* If computing metadata from brick data on the client (because the server lacks metadata queries), ensure a **minimum number of voxels** is used to avoid inaccuracies from too few voxels (e.g., a single voxel in a coarse brick) [S1, unofficial]. If bricks must be fetched for this purpose, they are uploaded to the GPU and residency info is updated [S2].

5.  **Channel Replacement:**
    *   If a channel is replaced by another at runtime, all nodes storing valid data for the old channel are marked as `INVALID` for the new channel [S1, unofficial].
    *   Nodes with `INVALID` status use the pointer mechanism to find valid data in lower subdivision levels [S1, unofficial].

### Pseudocode

```python
# Node structure in GPU memory (simplified for illustration)
# Each node has m channels. Each channel has a 32-bit integer.
# Bits 0-15: Partially mapped resolution bitmap
# Bits 16-23: Min value (8-bit)
# Bits 24-31: Max value (8-bit)

def traverse_octree(ray_origin, ray_direction, octree_buffer, brick_cache, page_table):
    # Start at a specific level to optimize traversal
    current_node = get_node_at_level(octree_buffer, level=3)
    
    while current_node is not None:
        # Check if node is empty/homogeneous using min/max metadata
        if is_empty_or_homogeneous(current_node):
            # Implicitly fully mapped, skip subtree
            current_node = get_next_node_in_traversal_order(current_node)
            continue
            
        # Check residency for required channels/resolutions
        required_resolutions = get_required_resolutions(ray, current_node)
        missing_bricks = []
        
        for channel in visualized_channels:
            node_data = get_node_channel_data(current_node, channel)
            mapped_resolutions = get_mapped_resolutions(node_data)
            
            for res in required_resolutions:
                if res not in mapped_resolutions:
                    # Cache miss: request brick
                    brick_id = page_table.get_brick_id(current_node, channel, res)
                    if not brick_cache.contains(brick_id):
                        missing_bricks.append((brick_id, channel, res))
        
        # Stream missing bricks
        for brick_id, channel, res in missing_bricks:
            brick_data = server.request(brick_id)
            brick_cache.store(brick_id, brick_data)
            update_residency_octree(current_node, channel, res, brick_data)
            
        # Perform ray-marching step if data is available
        if has_sufficient_data(current_node):
            sample_value = ray_march(ray, current_node)
            accumulate(sample_value)
            
        current_node = get_next_node_in_traversal_order(current_node)

def update_residency_octree(node, channel, resolution, brick_data):
    # Mark node as partially mapped for this resolution
    node_data = get_node_channel_data(node, channel)
    set_bit(node_data.partial_map_bitmap, resolution)
    
    # Update min/max if this is the first time or if it improves bounds
    new_min, new_max = compute_min_max(brick_data)
    node_data.min = min(node_data.min, new_min)
    node_data.max = max(node_data.max, new_max)
    
    # Propagate up to parent
    parent = get_parent(node)
    if parent:
        update_residency_octree(parent, channel, resolution, brick_data)
```

### Parameters and Edge Cases
*   **Leaf-node size:** Defined indirectly by the user at initialization as an approximate leaf-node size in voxels [S1, unofficial].
*   **Minimum voxels for metadata:** A parameter specifying the minimum number of voxels to consider when computing metadata to avoid inaccuracies from coarse resolutions [S2].
*   **Channel count ($m$):** The maximum number of channels referenced simultaneously. Memory scales linearly with $m$ [S2].
*   **Brick size:** Fixed and identical across all resolution levels in the bricked volume hierarchy (e.g., $32^3$ voxels) [S2].
*   **Pitfall - Metadata Accuracy:** If the server does not support metadata queries, the client must fetch bricks to compute min/max. If the resolution is too coarse, only a single voxel might be sampled, leading to inaccurate culling. A minimum voxel count must be enforced [S1, unofficial].
*   **Pitfall - Bit-width:** The bit-width of the brick ID data type (e.g., 32-bit or 64-bit) constrains the maximum volume size and the number of channels representable by the page table [S2].

## Subtopics

### [Octree-based memory virtualization](5140-octree-based-memory-virtualization.md)
Octree-based memory virtualization is an out-of-core rendering technique that decouples physical memory footprint from logical data size by mapping data files directly to virtual memory. It solves the problem of limited RAM when rendering massive multi-channel volume data by using an octree structure to progressively load only the necessary bricks and metadata into physical memory during traversal. Unlike the Residency Octree, which manages cache residency explicitly via bitmaps and pointers, this method relies on the operating system's memory manager to handle page faults, resulting in a simpler implementation but potentially higher memory overhead due to the requirement that entire subtrees be resident for high-resolution rendering.

### [Residency Octree Update](5181-residency-octree-update.md)
Residency Octree Update is a fully GPU-implemented parallel method for the incremental construction and maintenance of a multi-channel residency octree during out-of-core direct volume rendering. It solves the problem of keeping hierarchical occupancy and culling data consistent with dynamic cache additions and evictions without CPU intervention. Unlike static octree construction, this approach updates nodes only when bricks are added or removed from the brick cache, using bitmap propagation to minimize redundant writes. It sets itself apart from [Octree-based memory virtualization](5140-octree-based-memory-virtualization.md) by focusing on the specific mechanism of updating the residency metadata itself, and from [Mixed-Resolution Multi-Volume Renderer](5215-mixed-resolution-multi-volume-renderer.md) by handling the data structure maintenance rather than the ray sampling logic.

### [Mixed-Resolution Multi-Volume Renderer](5215-mixed-resolution-multi-volume-renderer.md)
A ray-guided renderer that accesses metadata and cached volume data through the [Residency Octree](4950-residency-octree.md), enabling efficient mixing of resolutions across different channels in multi-volume datasets. It differs from per-channel sampling approaches by evaluating all visible channels at each sample along a ray, using a global step size determined by the highest-resolution channel to reduce shader divergence.

### Residency Octree with Channel-Agnostic Brick Cache
Uses accumulation-level intermixing to combine different channels, where the illumination model is evaluated separately for each channel at each ray sample and then combined [S1, unofficial]. The residency octree is backed by a channel-agnostic brick cache where each cache entry only contains data belonging to a single channel [S1, unofficial]. This allows the number of channels to be unlimited by the texture format used by the brick cache implementation, unlike Brix et al.'s approach [S1, unofficial]. The residency octree supports changes to the selection of visible channels at run-time by replacing only the parts of their nodes related to the affected channels [S1, unofficial].

### Residency-Octree Node Classification
Classification of octree nodes based on cache residency of bricks covering their spatial extent at a given resolution level [S1, unofficial]. A node is **fully mapped** in a resolution level if cache-resident bricks of that level fully cover the node's spatial extent [S1, unofficial]. A node is **partially mapped** if at least one brick of that level overlaps with the node's spatial extent and is resident in the cache [S1, unofficial]. Fully mapped implies partially mapped, but not vice versa [S1, unofficial]. If a node is fully mapped in a resolution level, all child nodes are also fully mapped in that level [S1, unofficial]. If a node is partially mapped in a resolution level, its parent node is also partially mapped [S1, unofficial].

### Multi-Channel Residency Octree
An extension where all channels share the same octree structure, but each node stores culling and residency information for up to $m \le n$ channels [S1, unofficial]. This allows using the same spatial subdivision for empty-space skipping while rendering each channel in a different resolution [S1, unofficial]. When a channel is replaced by another one, all nodes storing valid data for the old channel are marked as `INVALID` for the new channel [S1, unofficial]. Each node stores for each of the $m$ channels whether the channel information is initialized or not using a special `INVALID` value [S1, unofficial]. If invalid, it stores a pointer to the node in the next lower subdivision level that has valid information for that channel, or a special `UNKNOWN` value if no such node exists [S1, unofficial]. The pointer replaces the metadata for that channel to reduce memory [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Ray traversal is performed once per sample, independent of the number of channels [S2]. The decoupling allows fine-grained empty-space skipping, which is costly in standard octrees where traversal and resolution selection are coupled [S2].
*   **Memory Complexity:** Memory usage scales linearly with the number of simultaneously visualized channels ($m$) [S2]. This can be mitigated by combining channels via dimensionality reduction, interleaving channels in four-component textures, or using compressed texture formats [S2].
*   **Performance:** The method enables efficient mixing of channel resolutions and substituting alternative resolutions on cache misses [S2]. It is faster than prior page-table or standard octree approaches for large-scale, multi-channel datasets like Immunofluorescence (IF) imaging data [S2].
*   **Strengths:** Decouples resolution from spatial subdivision, allowing adaptive resolution mixing and cache-miss compensation [S2]. Supports fine-grained empty-space skipping independent of bricking granularity [S2].
*   **Limitations:** Memory scales with channel count [S2]. Requires a backing multi-channel page table hierarchy and brick cache [S2].
*   **When to use:** Out-of-core DVR of large-scale volumetric datasets with a large number of channels (e.g., IF imaging) where adaptive resolution and efficient cache usage are critical [S2].
*   **When not to use:** When the dataset fits entirely in memory and does not require multi-channel resolution mixing, or when the hardware lacks support for the required GPU features (e.g., WebGPU for the web-based implementation) [S2].

## Background
The Residency Octree was introduced as a novel hybrid data structure for out-of-core volume rendering [S2]. It combines the advantages of page-table hierarchies (flexible multi-resolution access) with those of octrees (efficient traversal and culling) [S1, unofficial]. The method was developed to address the limitations of previous octree-based out-of-core approaches, which used a one-to-one mapping between bricks and nodes, intrinsically coupling resolution levels to spatial subdivision [S1, unofficial]. The approach was implemented as a web-based, pure client-side renderer using WebGPU and WebAssembly to facilitate collaboration and eliminate local data storage [S2]. It is particularly suited for multi-channel immunoﬂuorescence data, where unimodal transfer functions make min/max metadata effective for empty-space skipping [S1, unofficial].
