# Octree-based out-of-core volume rendering

Also called: Octree approach, Octree reference implementation

## Overview
An out-of-core rendering approach based on an octree structure, extending the single-channel method of Crassin et al. to support multiple visible channels by storing pointers and culling metadata in each node [S1, unofficial]. It differs from the [Multi-Channel Page-Table Hierarchy](5196-multi-channel-page-table-hierarchy.md) by using a hierarchical tree traversal for every channel to ensure subtree residency, whereas the page-table approach uses direct indexing [S1, unofficial].

## How it works
**Inputs and outputs:**
*   **Input:** Multi-channel volume data set; camera parameters; transfer function; cache size limit.
*   **Output:** Rendered image.

**Data structures:**
*   **Octree Node:**
    *   `m` pointers to bricks (one per visible channel, $m$).
    *   Culling metadata: minimum and maximum scalar values for each of the $m$ channels.
    *   Child pointers (for non-leaf nodes).
*   **Brick:** $32^3$ voxels per channel.
*   **Mapping:** One-to-one mapping between octree nodes and bricks [S1, unofficial].

**Parameters:**
*   Cache size: 4 GB [S1, unofficial].
*   Brick size (and approximate leaf-node size): $32^3$ voxels [S1, unofficial].
*   Traversal start level: Third subdivision level counting from the root node [S1, unofficial].

**Algorithm:**
1.  **Initialization:** Load the root of the octree. Start traversal at the third subdivision level [S1, unofficial].
2.  **Ray Casting Loop:** For each pixel, cast a ray.
3.  **Sample Traversal:**
    *   Determine the current node in the octree for the ray sample. Access the correct node for a ray sample in each subdivision level directly using a full octree implementation [S1, unofficial].
    *   If the traversal does not start at the root for each sample, start from the parent node’s subdivision level in the tree structure of the last node visited for the last sample [S1, unofficial].
    *   For each visible channel $c \in \{1, \dots, m\}$:
        *   Traverse the subtree for channel $c$ to ensure the whole subtree is resident in the cache [S1, unofficial].
        *   Check culling metadata (min/max values) for channel $c$ in the current node. If the ray sample is outside the range, skip the brick [S1, unofficial].
        *   If the brick for channel $c$ is missing in the desired resolution, render the next lower resolution instead [S1, unofficial].
        *   If the brick is present, load it into the cache if not already resident.
        *   Perform volume integration for channel $c$ using the loaded brick data.
4.  **Cache Management:** Ensure that the whole subtree is resident in the cache for high-resolution rendering [S1, unofficial]. Bricks containing at least one non-zero value are not considered EMPTY and must be kept in memory even if transparent under current viewing conditions [S1, unofficial].

**Pseudocode:**
```python
def render_octree_out_of_core(volume_data, camera, cache, num_channels):
    # Initialize octree traversal state
    # Start at third subdivision level from root
    current_node = get_node_at_level(root_octree, level=3)
    last_visited_node = current_node
    
    for pixel in pixels:
        ray = cast_ray(camera, pixel)
        sample_pos = ray.origin
        
        # Start traversal from last visited node's parent level
        # to avoid restarting from root for every sample
        node_level = get_level(last_visited_node)
        
        for channel in range(num_channels):
            # Traverse subtree for this channel to ensure residency
            node = current_node
            while node is not None:
                # Check culling metadata for this channel
                min_val = node.culling_min[channel]
                max_val = node.culling_max[channel]
                
                if not is_in_range(sample_pos, min_val, max_val):
                    # Skip this branch for this channel
                    break
                
                # Check if brick is resident
                brick = cache.get_brick(node, channel)
                if brick is None:
                    # Load brick or use lower resolution if missing
                    if node.has_children:
                        node = get_child(node, ray.direction)
                        continue
                    else:
                        # Leaf node, brick missing in desired resolution
                        # Render next lower resolution
                        brick = load_lower_resolution_brick(node, channel)
                
                # Integrate sample
                color = integrate_sample(brick, sample_pos, channel)
                accumulate_color(pixel, color)
                
                # Move to next sample along ray
                sample_pos = ray.step(sample_pos)
                
                # Update last visited node for optimization
                last_visited_node = node
                node_level = get_level(node)
```

**Edge cases and pitfalls:**
*   **Multiple channels:** The octree has to be traversed for each channel to ensure that all subtrees are resident in the cache, leading to worse performance compared to single-channel rendering [S1, unofficial].
*   **Memory footprint:** Whole subtrees have to be resident in the cache for rendering the volume in high resolution, resulting in a higher memory footprint in terms of the number of bricks in the working set compared to the residency octree [S1, unofficial].
*   **Empty space:** Bricks containing at least one non-zero value are not considered EMPTY and thus have to be kept in memory even though they might be completely transparent under the current viewing conditions [S1, unofficial].

## Subtopics

### [Multi-Channel Page-Table Hierarchy](5196-multi-channel-page-table-hierarchy.md)
A data structure that virtualizes a bricked multi-volume hierarchy by implementing a paged 3D address space. It uses one page-table hierarchy per channel to keep track of brick locations in a shared brick cache, allowing direct access to any brick without traversing a tree structure. Choose this when performance on multi-channel data is critical and cache locality can be managed via page tables rather than tree traversal.

## Operating characteristics
**Time and memory complexity:**
*   **Time:** $O(N \cdot m)$ where $N$ is the number of ray samples and $m$ is the number of visible channels, due to traversing the tree for each channel [S1, unofficial].
*   **Memory:** Higher memory footprint than the residency octree because whole subtrees must be resident in the cache [S1, unofficial].

**Measured performance:**
*   Hardware: Not given in the sources.
*   Resolution: Varies by dataset (see below).
*   Scene: See Table 1.
*   Scaling: Performance degrades with increasing number of channels due to repeated tree traversal [S1, unofficial].

**Strengths and limitations:**
*   **Strengths:** Comparable performance to the author's method for single-channel rendering due to similar empty-space skipping strategy [S1, unofficial].
*   **Limitations:** Performs worse than the author's method for multiple channels due to the need to restart tree traversal for each channel [S1, unofficial].

**When to use it and when not:**
*   Use for single-channel or low-channel count out-of-core rendering where simplicity of implementation is preferred.
*   Do not use for high-channel count biomedical data sets where performance is critical, as it is significantly slower than the page-table hierarchy approach [S1, unofficial].

## Background
Origin: Based on the out-of-core renderer presented by Crassin et al. [CNLE09] and similar to the octree-based method discussed by Brix et al. [BPH14] [S1, unofficial]. Extended by the author to support multiple visible channels [S1, unofficial].
