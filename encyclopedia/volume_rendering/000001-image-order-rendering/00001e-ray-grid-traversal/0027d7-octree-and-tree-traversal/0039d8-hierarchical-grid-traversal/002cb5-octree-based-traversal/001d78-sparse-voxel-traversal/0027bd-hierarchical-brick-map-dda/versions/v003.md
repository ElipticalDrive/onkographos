# Hierarchical Brick-Map DDA

Also called: Multi-level DDA with brick map, Sparse brick-map ray marching

## Overview
Hierarchical Brick-Map DDA is a ray traversal technique that replaces a dense voxel buffer with a sparse hierarchical structure (brick-map) to skip empty regions [S1, unofficial]. It sets itself apart from its parent [Sparse Voxel Traversal](1525-sparse-voxel-traversal.md) by using a fixed-depth, bit-packed hierarchy with exact cell-boundary snapping, and from its sibling [Octree Traversal](1587-octree-traversal.md) by relying on a fixed 2-level grid-of-bricks rather than a variable-depth tree, which simplifies traversal logic at the cost of potential wasted space in moderately sparse regions [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A dense voxel grid of dimensions $N \times N \times N$ (where $N$ is a multiple of `BRICK`), ray origin $\mathbf{o}$, ray direction $\mathbf{d}$, and maximum step count `MAX_STEPS`.
*   **Output:** A rendered image or accumulated color/transmittance along the ray path.

**Data Structures:**
The structure consists of three main GPU buffers [S1, unofficial]:
1.  **`topGrid`**: A sparse 3D grid of top-level cells. Each cell stores a pointer (index) to a brick in the `brickPool` or a null value (e.g., -1) if the cell is empty. The dimensions of `topGrid` are $T \times T \times T$, where $T = N / \text{BRICK}$.
2.  **`brickPool`**: A contiguous array of occupied bricks. Each brick contains $\text{BRICK}^3$ voxels. The size of the pool is determined dynamically during the build phase based on the number of occupied top-level cells.
3.  **`counter`**: An atomic counter used during the build phase to allocate slots in the `brickPool`.
4.  **Uniforms**: A `Grid` uniform containing `top_size` (dimensions of `topGrid`) and `BRICK` (side length of a brick, typically 8) [S1, unofficial].

**Parameters:**
*   `BRICK`: The side length of a voxel brick in voxels. Typical value is 8 [S1, unofficial].
*   `MAX_STEPS`: Maximum number of ray marching steps. Increased from 512 to 1024 to accommodate hierarchical traversal overhead [S1, unofficial].

**Build Phase (Compute Shader):**
1.  For each top-level cell $(i, j, k)$ in the `topGrid`:
    a.  Scan the corresponding $\text{BRICK}^3$ voxels in the dense input buffer.
    b.  Check if any voxel is non-zero (solid). An optimization is to break early upon finding the first solid voxel [S1, unofficial].
    c.  If solid, atomically increment `counter` to allocate a slot `idx` in `brickPool`.
    d.  Copy the $\text{BRICK}^3$ voxel data from the dense buffer into `brickPool[idx]`.
    e.  Set `topGrid[i][j][k] = idx`.
    f.  If empty, set `topGrid[i][j][k] = -1` (null).

**Traversal Phase (Ray Marching Shader):**
The traversal operates in two modes: Top-Level (Coarse) and Brick-Level (Fine).

1.  **Initialization:**
    *   Compute initial ray parameters for the global coordinate system.
    *   Calculate `c_tmax` (distance to the next top-level cell boundary) along each axis.
    *   Determine the initial top-level cell indices $(i, j, k)$ containing the ray origin.

2.  **Top-Level Traversal:**
    *   While `steps < MAX_STEPS` and ray is within bounds:
        a.  Check if `topGrid[i][j][k]` is null.
        b.  If null (empty):
            i.  Advance the ray by `c_tmax` (the distance to the next top-level boundary).
            ii. Update `c_tmax` for the new top-level cell.
            iii. Increment the top-level cell index in the direction of the ray's leading edge.
        c.  If occupied:
            i.  **Descent:** Enter the brick.
                *   Let `brick_idx = topGrid[i][j][k]`.
                *   Calculate the local ray origin $\mathbf{o}_{local}$ and direction $\mathbf{d}_{local}$ within the brick's coordinate system. The direction $\mathbf{d}_{local}$ is the same as $\mathbf{d}$, but the origin is offset to the brick's local space. Specifically, $\mathbf{o}_{local} = \mathbf{o} - \mathbf{p}_{brick\_origin}$, where $\mathbf{p}_{brick\_origin}$ is the global position of the brick's minimum corner [S1, unofficial].
                *   Compute local ray parameters: `t_max_local` (distance to brick boundary) and `t_min_local` (distance to brick entry).
                *   Switch to **Brick-Level Traversal**.

3.  **Brick-Level Traversal (Fine DDA):**
    *   Perform standard DDA within the $\text{BRICK} \times \text{BRICK} \times \text{BRICK}$ volume.
    *   Sample voxels from `brickPool[brick_idx]`.
    *   Accumulate color/transmittance.
    *   If a solid voxel is hit or the ray exits the brick (distance traveled > `t_max_local`):
        i.  **Ascent:** Exit the brick.
        ii. Calculate the global distance traveled within the brick.
        iii. Update the global ray position.
        iv. Recompute `c_tmax` for the new top-level cell.
        v.  Determine the new top-level cell indices $(i, j, k)$ based on the updated global position.
        vi. Switch back to **Top-Level Traversal**.

4.  **Boundary Handling:**
    *   Reuse AABB (Axis-Aligned Bounding Box) clipping and safe-ray-distance primitives to handle axis-aligned rays and rays outside the grid volume correctly [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Brick Edge Transitions:** Visual popping or missing voxels can occur at brick boundaries if the transition between top-level cells and brick interiors is not handled smoothly. Validation requires toggling camera angles to ensure clean boundary-crossing transitions [S1, unofficial].
*   **Precision:** Re-deriving the ray direction and origin for the brick's local coordinate system must be done carefully to avoid precision errors, especially for rays nearly parallel to axes.
*   **Empty Bricks:** The build phase must correctly identify and skip empty bricks to maintain sparsity benefits.

## Subtopics

### [Hierarchical DDA](5710-hierarchical-dda.md)
Hierarchical DDA is a ray traversal technique that accelerates sparse volume rendering by navigating a 3-level occupancy-bit pyramid (chunk → tile → brick) to skip empty space. It sets itself apart from its parent [Hierarchical Brick-Map DDA](4105-hierarchical-brick-map-dda.md) by using a fixed-depth, bit-packed hierarchy with exact cell-boundary snapping, and from its sibling [Sparse Ray Marching with Nested Axis-Aligned Distance Fields (NAADF)](6260-sparse-ray-marching-with-nested-axis-aligned-distance-fields.md) by relying on discrete occupancy masks rather than continuous distance fields for empty-space skipping.

### [Sparse Ray Marching with Nested Axis-Aligned Distance Fields (NAADF)](6260-sparse-ray-marching-with-nested-axis-aligned-distance-fields.md)
Sparse Ray Marching with Nested Axis-Aligned Distance Fields (NAADF) is a technique for traversing sparse voxel grids by skipping over empty space using precomputed distance fields, replacing traditional brick coordinate rasterization with a simpler pipeline suitable for g-buffer and path tracing. It differs from its sibling [Hierarchical Brick-Map DDA](4105-hierarchical-brick-map-dda.md) by calculating the largest empty region along the ray's path via axis-aligned bounds, allowing it to step over multiple cells at once rather than advancing one cell boundary per iteration.

## Operating characteristics
*   **Time Complexity:** The traversal time is proportional to the number of occupied bricks and voxels visited. In sparse scenes, the top-level traversal skips large empty regions, reducing the number of DDA steps significantly compared to dense traversal. The build phase is $O(N^3)$ but is a one-time cost.
*   **Memory Complexity:** Memory usage is proportional to the number of occupied bricks times $\text{BRICK}^3$. For a heightmap stand-in with $N=128$, the brick count is roughly $T^2$ (~256 bricks) instead of the worst-case $T^3$ (4096), with memory savings growing as sparsity increases [S1, unofficial].
*   **Measured Performance:** In drone airspace scenarios (>99% empty), this method significantly reduces memory footprint and traversal time compared to dense voxel buffers [S1, unofficial].
*   **Strengths:** Significant memory savings in sparse volumes; simplified traversal logic compared to variable-depth octrees; efficient skipping of empty space.
*   **Limitations:** Potential for wasted space if sparsity is not high enough to justify the brick overhead; visual artifacts at brick boundaries if not implemented carefully; fixed hierarchy depth limits adaptability to varying density scales.
*   **When to Use:** Sparse volumes with large empty regions, such as drone airspace or terrain with significant sky.
*   **When Not to Use:** Dense volumes where the overhead of managing the brick map outweighs the benefits; scenes with highly variable density where a fixed brick size is inefficient.

## Background
Hierarchical Brick-Map DDA was introduced as part of the ResQ Viz project, specifically in PR #67, to optimize ray marching for sparse volumes like drone airspace [S1, unofficial]. It builds on the concept of sparse voxel traversal by introducing a fixed two-level hierarchy (top-level grid of bricks) to simplify implementation and improve performance in highly sparse scenarios. The method was developed by the ResQ software team, with contributions from WomB0ComB0 and reviewed by coderabbitai [S1, unofficial].
