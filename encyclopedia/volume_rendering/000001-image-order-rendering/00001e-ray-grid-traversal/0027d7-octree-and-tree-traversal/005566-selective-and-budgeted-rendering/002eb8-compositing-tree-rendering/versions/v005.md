# Compositing Tree Rendering

Also called: Incremental Compositing, Modified subtree rendering, Partial image compositing, Selective Subtree Rendering

## Overview
Compositing Tree Rendering is a time-varying volume rendering strategy that avoids re-rendering the entire volume for every frame by retaining and reusing partial images of unmodified data [S1, S2, unofficial]. It constructs a pointer-based octree (the compositing tree) mirroring the compressed data structure, where leaves store rendered partial images and interior nodes store the composite of their children [S1, S2, unofficial]. Unlike [Octree-based Entropy Rendering](13580-octree-based-entropy-rendering.md), which selects nodes based on visual information density, this method selects nodes based on temporal data modification, splicing in new branches only where the underlying volume data has changed [S1, S2, unofficial].

## How it works

### Inputs and Outputs
**Inputs:**
1. A sequence of compressed octree structures representing time-varying volume data [S1, S2, unofficial].
2. A transfer function mapping data values to color and opacity [S1, S2, unofficial].
3. Camera parameters (viewing position, orientation, projection) [S1, S2, unofficial].
4. The original uncompressed volume data (required for boundary handling) [S1, S2, unofficial].

**Outputs:**
1. A final composite image for the current time step [S1, S2, unofficial].
2. An updated compositing tree structure for the next time step [S1, S2, unofficial].

### Data Structures

**Compositing Tree:**
A pointer-based octree with the same hierarchical structure as the compressed input octree [S1, S2, unofficial].
*   **Interior Node:**
    *   `children`: Array of 8 pointers to child nodes (or null if the node is a leaf in the compressed tree, though typically interior nodes in the compositing tree correspond to interior nodes in the compressed tree) [S1, S2, unofficial].
    *   `image`: A 2D image buffer (partial image) representing the front-to-back compositing result of all rays passing through this node's spatial domain, derived from its children [S1, S2, unofficial].
*   **Leaf Node:**
    *   `data_ref`: Reference or pointer to the corresponding leaf in the compressed octree [S1, S2, unofficial].
    *   `image`: A 2D image buffer (partial image) rendered directly from the volume data represented by this leaf [S1, S2, unofficial].

**Compressed Octree (Input):**
*   Nodes indicate spatial subdivision.
*   Leaves represent uniform blocks or modified regions [S1, S2, unofficial].
*   Metadata indicates which subtrees have changed between time steps [S1, S2, unofficial].

### Algorithm Steps

1.  **Initialization (Time Step $t=0$):**
    *   Render the entire compressed octree completely using standard ray casting [S1, S2, unofficial].
    *   Construct the initial compositing tree. Each leaf in the compositing tree contains the partial image rendered from its corresponding leaf in the compressed octree [S1, S2, unofficial].
    *   For each interior node, compute its partial image by compositing the images of its 8 children [S1, S2, unofficial].
    *   The image at the root of the compositing tree is the final image for $t=0$ [S1, S2, unofficial].

2.  **Update (Time Step $t > 0$):**
    *   Identify modified subtrees in the compressed octree by comparing the current compressed tree with the previous one [S1, S2, unofficial].
    *   For each modified subtree:
        *   Create a new compositing branch. This involves rendering the modified leaves and compositing them up to the root of the new branch [S1, S2, unofficial].
        *   Splice this new branch into the existing compositing tree, replacing the old branch corresponding to the modified data [S1, S2, unofficial].
    *   For unmodified subtrees:
        *   Retain the existing partial images from the previous compositing tree [S1, S2, unofficial].
        *   *Approximation:* Due to opacity accumulation obscuring back details, subtrees representing the back portion of the data may not be completely sampled in front-to-back rendering. As an approximation, these unchanged subtrees are not re-rendered even if they are in the back [S1, S2, unofficial].
    *   Recomposite ancestors:
        *   Starting from the spliced branches, traverse up to the root.
        *   For each interior node on the path, update its partial image by compositing the images of its 8 children (some of which may be from the new branch, others from the retained old tree) [S1, S2, unofficial].
    *   The image at the root of the compositing tree is the final image for time step $t$ [S1, S2, unofficial].

### Formulas

**General Discretized Volume Rendering Integral:**
The accumulated color $C$ up to $n$ sample points on a ray is given by the front-to-back compositing equation [S1, S2, unofficial]:

$$
C = \sum_{i=1}^{n} C_i \alpha_i \prod_{j=1}^{i-1} (1 - \alpha_j)
$$

Where:
*   $C_i$ is the color at sample point $i$.
*   $\alpha_i$ is the opacity at sample point $i$.
*   The term $\prod_{j=1}^{i-1} (1 - \alpha_j)$ represents the transmittance from the camera to sample $i$.

**Simplified Compositing for Constant Subvolumes:**
When an octree leaf represents a uniform block where all sample points have identical color $C$ and opacity $\alpha$, the rendering can be optimized. The calculations for sample coordinates and trilinear interpolation are avoided; only the number of samples $n$ is required [S1, S2, unofficial].

The accumulated color $C_{total}$ is derived from the geometric series:

$$
C_{total} = C \alpha \frac{1 - (1 - \alpha)^{n-1}}{1 - (1 - \alpha)} = C \frac{1 - (1 - \alpha)^n}{1 - (1 - \alpha)}
$$

Note: Source [S1, unofficial] presents the formula as $C \alpha (1 - (1-\alpha)^{n-1}) / (1 - (1-\alpha))$ [S1, unofficial], while Source [S2, unofficial] presents it as $C \frac{1-(1-a)^n}{1-(1-a)}$ [S2, unofficial]. Both represent the sum of a geometric series of opacity contributions. The sources use $a$ and $\alpha$ interchangeably for opacity [S1, S2, unofficial].

### Edge Cases and Pitfalls

1.  **Boundary Rendering:** Octree leaves represent uniform blocks, but boundaries between blocks must be rendered carefully. To avoid the overhead of traversing the tree to obtain boundary values, the original data is kept uncompressed, and the octree serves as a map into this volume data [S1, S2, unofficial].
2.  **Viewing Position Changes:** The optimization is based on a fixed viewing position. Changing the view requires rerendering the entire tree and creating a new compositing tree [S1, S2, unofficial]. Random temporal navigation requires saving complete trees at regular intervals [S1, S2, unofficial].
3.  **Back Subtree Approximation:** Due to opacity accumulation obscuring back details in front-to-back rendering, subtrees representing the back portion of the data may not be completely sampled. As an approximation, unchanged subtrees are not re-rendered [S1, S2, unofficial].
4.  **Rendering Overhead:** Rendering from the tree structure incurs overhead compared to direct volume data rendering. This is offset by optimizations like front-to-back rendering, caching ray coordinates in object space, and skipping transparent space [S1, S2, unofficial].

## Operating characteristics

**Time Complexity:**
*   **Initial Render:** $O(N)$, where $N$ is the number of voxels or samples, as the entire tree is rendered [S1, S2, unofficial].
*   **Subsequent Renders:** Proportional to the amount of modified data. If $M$ is the number of modified samples/leaves, the complexity is $O(M)$ plus the cost of compositing the ancestors [S1, S2, unofficial]. The savings are significant when $M \ll N$ [S1, S2, unofficial].

**Memory Complexity:**
*   Requires storing the compositing tree, which includes partial images for every node in the octree structure [S1, S2, unofficial].
*   Memory usage is proportional to the number of nodes in the octree times the image resolution [S1, S2, unofficial].
*   Requires storing the uncompressed volume data for boundary handling [S1, S2, unofficial].

**Measured Performance:**
*   Source [S1, unofficial] reports that rendering only modified data accounts for the largest savings in the time domain.
*   Tree merging produces the most significant amount of savings in rendering cost [S1, S2, unofficial].
*   Time to read encoded data is reduced in proportion to the compression rate [S1, S2, unofficial].
*   Specific performance numbers are not given for Compositing Tree Rendering itself, but related resolution coarsening strategies show 40-90% savings in storage and 10-30% in rendering time [S1, S2, unofficial].

**Strengths:**
*   Significant performance gains for time-varying data with localized changes [S1, S2, unofficial].
*   Leverages existing compression schemes [S1, S2, unofficial].
*   Optimizations for constant subvolumes avoid interpolation costs [S1, S2, unofficial].

**Limitations:**
*   Fixed viewing position required for incremental updates [S1, S2, unofficial].
*   Overhead from tree traversal [S1, S2, unofficial].
*   Approximation in back subtree rendering may affect visual accuracy [S1, S2, unofficial].

## Background

Compositing Tree Rendering was introduced in the context of efficient encoding and rendering of time-varying volume data. It was developed by researchers associated with NASA and DTIC, as indicated by the sources [S1, S2, unofficial]. The method was presented in a technical report from 1998 [S1, S2, unofficial]. It is designed to work with compressed octree representations of volume data, allowing for efficient incremental updates in time-varying scenarios.
