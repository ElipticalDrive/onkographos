# Frustum-Occlusion Culling for Octree Traversal

Also called: Frustum-octant traversal, Voxel LOD selection, Voxel LOD selection via Frustum Culling, Voxel Rasterization via Frustum Culling and Instancing

## Overview
This method identifies a set of visible voxels by traversing an octree hierarchy and culling nodes that do not intersect the camera's view frustum or whose projected screen area is smaller than a single pixel [S1, unofficial]. It serves as a visibility pre-pass for voxel rasterization, automatically determining the Level of Detail (LOD) for rendering [S1, unofficial]. Unlike standard ray-marching which samples volume density, this approach outputs a list of 3D bounding boxes (voxels) to be rasterized as geometry using hardware instancing [S1, unofficial]. It is distinct from [Bounding-Sphere Tree Traversal with Frame-Rate Control](7227-bounding-sphere-tree-traversal-with-frame-rate-control.md) by using explicit frustum intersection tests rather than frame-rate driven depth limits, and from [Frustum Culling Integration](8798-frustum-culling-integration.md) by specifically targeting octree structures for voxel-based rendering pipelines.

## How it works
**Inputs:**
*   Camera view frustum defined by six planes.
*   Octree hierarchy where each node has an axis-aligned bounding box (AABB).
*   Global AABB enclosing the entire octree.
*   Screen resolution $(W, H)$.

**Outputs:**
*   A buffer of visible voxels, where each entry contains the voxel's position and size (derived from its AABB).

**Data Structures:**
*   **Octree Node:** Contains a bounding box (AABB) and a child mask (8 bits, one bit per child octant) indicating occupancy [S1, unofficial].
*   **Voxel Buffer:** A dynamic array of structures `{position: vec3, size: float}`.

**Algorithm:**
The traversal is recursive or iterative, starting from the root. For each node, two conditions are checked to determine if traversal should continue or if the node should be added to the output buffer.

1.  **Frustum Intersection Test:**
    To optimize performance, the intersection between the view frustum and the octant's AABB is approximated by a frustum-sphere intersection [S1, unofficial]. The sphere's diameter is the diagonal of the octant's AABB. If the sphere does not intersect the frustum, the node and all its descendants are culled.

2.  **Projected Area Test (LOD Selection):**
    If the node intersects the frustum, its projected area on the screen is calculated. If this area is less than the area of one pixel (or a threshold equivalent to one pixel), the node is considered too small to contribute visible detail. Traversal stops for this branch, and the node's AABB is added to the voxel buffer [S1, unofficial].

3.  **Termination:**
    Traversal also stops if the node is a leaf (no further subdivisions) [S1, unofficial]. In this case, the node's AABB is added to the voxel buffer.

4.  **Buffer Population:**
    When a node is added to the buffer (due to LOD cutoff, leaf status, or frustum exit), its position and size are recorded. These attributes are implicit based on the node's AABB within the global coordinate space [S1, unofficial].

5.  **Rasterization:**
    After the full octree traversal, the buffer is passed to a hardware instancing pipeline. Each entry in the buffer generates a voxel geometry instance [S1, unofficial].

**Pseudocode:**
```python
def traverse_octree(node, frustum, screen_width, screen_height, voxel_buffer):
    """
    Recursively traverse the octree to find visible voxels.
    
    Args:
        node: The current octree node, containing 'aabb' (min, max) and 'children' (list of nodes or None).
        frustum: Object with method 'intersects_sphere(center, radius)'.
        screen_width: int, width of the viewport.
        screen_height: int, height of the viewport.
        voxel_buffer: List to append visible voxel data.
    """
    # 1. Frustum Culling via Sphere Approximation
    # Calculate sphere center and radius from AABB
    center = (node.aabb.min + node.aabb.max) / 2.0
    radius = length(node.aabb.max - node.aabb.min) / 2.0
    
    # If sphere does not intersect frustum, cull this branch
    if not frustum.intersects_sphere(center, radius):
        return

    # 2. Projected Area / LOD Check
    # Calculate projected area of the AABB on the screen.
    # Note: Exact projection requires view/projection matrices.
    # Simplified check: if projected area < 1 pixel, stop traversal.
    projected_area = calculate_projected_area(node.aabb, frustum.view_matrix, frustum.proj_matrix, screen_width, screen_height)
    
    if projected_area < 1.0 or node.is_leaf():
        # Add voxel to buffer
        voxel_buffer.append({
            'position': center,
            'size': length(node.aabb.max - node.aabb.min)
        })
        return

    # 3. Recurse into children
    for child in node.children:
        if child is not None:
            traverse_octree(child, frustum, screen_width, screen_height, voxel_buffer)

def calculate_projected_area(aabb, view_matrix, proj_matrix, w, h):
    """
    Approximate the projected area of an AABB in screen space.
    Returns area in pixels.
    """
    # Transform AABB corners to clip space
    corners = [
        vec4(aabb.min.x, aabb.min.y, aabb.min.z, 1.0),
        vec4(aabb.max.x, aabb.max.y, aabb.max.z, 1.0)
    ]
    
    # Apply view and projection matrices
    clip_corners = []
    for c in corners:
        view_pos = view_matrix * c
        clip_pos = proj_matrix * view_pos
        clip_corners.append(clip_pos)
        
    # Convert to normalized device coordinates (NDC)
    ndc_corners = []
    for c in clip_corners:
        ndc_corners.append(vec3(c.x/c.w, c.y/c.w, c.z/c.w))
        
    # Calculate bounding box in NDC [-1, 1]
    min_ndc = min(ndc_corners, key=lambda p: p.x) # Simplified: assume min/max logic applies to all dims
    max_ndc = max(ndc_corners, key=lambda p: p.x) # Simplified
    
    # More robust: compute min/max for x and y separately
    min_x = min(c.x for c in ndc_corners)
    max_x = max(c.x for c in ndc_corners)
    min_y = min(c.y for c in ndc_corners)
    max_y = max(c.y for c in ndc_corners)
    
    # Convert NDC to screen pixels
    # NDC x: -1 to 1 maps to 0 to w
    # NDC y: -1 to 1 maps to 0 to h
    screen_min_x = (min_x + 1.0) * 0.5 * w
    screen_max_x = (max_x + 1.0) * 0.5 * w
    screen_min_y = (min_y + 1.0) * 0.5 * h
    screen_max_y = (max_y + 1.0) * 0.5 * h
    
    width_px = max(0.0, screen_max_x - screen_min_x)
    height_px = max(0.0, screen_max_y - screen_min_y)
    
    return width_px * height_px
```

**Parameters:**
*   **Canonical Voxel Template:** The geometry for each voxel is a cube with extreme vertices $c_{min} = (-1, -1, -1)$ and $c_{max} = (+1, +1, +1)$ [S1, unofficial].
*   **LOD Threshold:** The traversal stops when the projected area is less than the area of a pixel [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Numeric Precision:** At very deep subdivision levels, numeric precision issues may arise during coordinate calculations [S1, unofficial].
*   **Over-subdivision:** Allocating nodes for extremely deep levels where LOD traversal would naturally halt due to screen size is inefficient. The depth should be limited or the LOD criterion should be tuned to prevent unnecessary allocation [S1, unofficial].
*   **Frustum Approximation:** Using a sphere to approximate the AABB for frustum culling is an optimization that may result in false positives (culling fewer nodes than strictly necessary) but never false negatives (if the sphere is inside the frustum, the AABB might still intersect, but if the sphere is outside, the AABB is definitely outside) [S1, unofficial].

## Operating characteristics
**Time Complexity:**
The traversal time depends on the number of nodes visited. In the worst case (full octree), it is $O(N)$ where $N$ is the number of nodes. However, due to frustum culling and LOD stopping, the average case visits significantly fewer nodes, proportional to the visible surface area of the volume [S1, unofficial].

**Memory Complexity:**
The memory usage is dominated by the octree structure itself. The octree can be stored compactly in breadth-first order using a single 8-bit mask per node [S1, unofficial]. The output buffer size is proportional to the number of visible voxels at the selected LOD.

**Performance:**
Profiled on an Intel Core i5-2540M CPU and NVIDIA Quadro 3000M GPU at 1920x1280 resolution, with 25% to 85% pixel coverage [S1, unofficial].
*   **Voxel Rasterization Times (ms) for 'basketball' dataset at octree depth 10:**
    *   Geometry Shader: 3.454 ms
    *   Uniform Buffer: 2.549 ms
    *   Hardware Texture Buffer: 2.773 ms
    *   Instancing Vertex Buffer: 5.599 ms [S1, unofficial]

**Strengths and Limitations:**
*   **Strengths:** Automatic LOD selection; efficient culling of non-visible regions; compatible with standard hardware instancing pipelines.
*   **Limitations:** The Geometry Shader approach for rasterizing voxels is slower than other instancing methods, likely due to hardware optimization for quadrilaterals rather than cubes [S1, unofficial]. Uniform buffers provide the fastest rasterization performance among tested methods [S1, unofficial].

## Background
This method was described in the context of hardware-accelerated geometry instancing for surfel and voxel rendering of scanned 4D media [S1, unofficial]. It leverages the sparse nature of octrees to optimize voxel rendering by avoiding the rasterization of invisible or insignificant voxels. The approach highlights the trade-offs between different GPU instancing techniques for rendering complex 3D voxel data [S1, unofficial].
