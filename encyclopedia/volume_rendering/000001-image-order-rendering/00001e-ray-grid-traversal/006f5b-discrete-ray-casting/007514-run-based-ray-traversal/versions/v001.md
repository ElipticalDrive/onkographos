# Run-based ray traversal
Also called: Intercept sequence traversal, Run-based Ray Traversal for Height Fields, Run-based traversal

## Overview
Run-based ray traversal is a method for efficiently determining the path of a ray through a discrete height field grid by grouping contiguous cells with identical y-coordinates into "runs," thereby reducing the number of traversal steps from $O(n)$ to $O(n/r)$, where $n$ is the total number of cells and $r$ is the average run length [S1]. It differs from standard cell-based algorithms (like DDA) by calculating the length of entire segments of the ray path in a single step using an intercept sequence derived from the ray's slope, rather than stepping through individual lattice points [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** Ray parameters $\alpha$ (slope) and $\beta$ (intercept) in the height field's coordinate system, assuming $0 \le \alpha \le 1$ and $0 \le \beta < 1$ [S1]. The height field samples are distributed over an integer lattice [S1].
*   **Output:** A sequence of runs, where each run is defined by its start position $(x_j, y_j)$ and length $r_j$ [S1].

**Data Structures:**
*   **Run:** A tuple or struct containing `start_x` (integer), `start_y` (integer), and `length` (integer) [S1].
*   **Intercept Sequence:** A sequence of real numbers $\beta_j$ representing the fractional component of the line's intercept at the start of each run [S1].

**Constants and Derived Values:**
*   Short run length: $r = \lfloor 1/\alpha \rfloor$ [S1].
*   Long run length: $r + 1 = \lceil 1/\alpha \rceil$ [S1].
*   Threshold for run type: $v = 1 - \alpha r$ [S1].
*   Ratio of short runs: $\mu = \alpha - v = \alpha(r + 1) - 1$ [S1].

**Algorithm Steps:**

1.  **Symmetry Handling:** If the ray slope $\alpha$ is outside $[0, 1]$, transform the ray coordinates to map the slope into this range using 8-way symmetry, process the runs, and transform the resulting run positions back to the original coordinate system [S1].

2.  **Initialization:**
    *   Set current position $(x_0, y_0)$ to the integer part of the ray's start point [S1].
    *   Set initial intercept $\beta_{curr} = \beta$ [S1].
    *   Check for initial truncation: If $\beta \ge \alpha + v$, the first run is truncated. This condition only applies if $0 < \alpha < 1/2$ [S1].

3.  **Optimization via Translation:**
    *   To simplify logic, translate the intercept sequence by subtracting $v$ from the initial $\beta$. Let $\beta' = \beta - v$ [S1].
    *   If $\beta' < \alpha$, the first run is not truncated. Set $r_0 = 0$ and $\beta_1 = \beta'$ [S1].
    *   If $\beta' \ge \alpha$, the first run is truncated. Calculate the truncated length $r_0 = \lceil (1-\beta)/\alpha \rceil = r - \lfloor \beta - v \rfloor$ [S1]. Calculate the next intercept $\beta_1 = (\beta - v) - \lfloor \beta - v \rfloor \alpha$ [S1]. Update current position $x_0 \leftarrow x_0 + r_0$ [S1].

4.  **Iterative Run Generation:**
    *   While the ray has not exited the height field boundary:
        *   Determine run type based on current intercept $\beta_{curr}$:
            *   If $\beta_{curr} < v$, the run is **long** ($r_j = r + 1$) [S1].
            *   If $\beta_{curr} \ge v$, the run is **short** ($r_j = r$) [S1].
            *   *Note:* The decision can be implemented as a sign check against zero if using the translated intercept $\beta'$ [S1].
        *   Record the run: Start $(x_j, y_j)$, Length $r_j$ [S1].
        *   Update position for the next run:
            $$x_{j+1} = x_j + r_j$$
            $$y_{j+1} = y_j + 1$$
            [S1]
        *   Update intercept for the next run:
            *   If the current run was **long**: $\beta_{j+1} = \beta_j + \mu$ [S1].
            *   If the current run was **short**: $\beta_{j+1} = \beta_j - v$ [S1]
            *   *Note:* In the optimized version using $\beta'$, if the run is long, $\beta'_{next} = \beta'_{curr} + \mu$. If short, $\beta'_{next} = \beta'_{curr} - v$. The threshold for determining long/short becomes 0 [S1].

5.  **Connectivity Correction (4-Connected Path):**
    *   The algorithm generates an 8-connected path. To convert to a 4-connected path required for ray tracing, extend the beginning of each run by one cell (backwards in x) [S1].
    *   **Exception:** Do not extend if a corner intersection occurs. A corner intersection corresponds to an intercept value of exactly 0 (or $-v$ in the translated system) [S1].

**Pseudocode:**

```python
def run_based_ray_traversal(alpha, beta, width, height):
    """
    Traverses a height field grid using run-based ray traversal.
    Assumes 0 <= alpha <= 1 and 0 <= beta < 1.
    Returns a list of runs: [(x, y, length), ...]
    """
    runs = []
    
    # Derived constants
    r_short = floor(1.0 / alpha)
    r_long = r_short + 1
    v = 1.0 - alpha * r_short
    mu = alpha - v
    
    # Initial position
    x = 0
    y = 0
    
    # Optimization: Translate intercept
    beta_prime = beta - v
    
    # Check for initial truncation
    # Truncation happens if beta >= alpha + v
    # In translated terms: if beta_prime >= alpha
    if beta_prime >= alpha:
        # Truncated first run
        # r0 = ceil((1 - beta) / alpha)
        # Using integer arithmetic: ceil(a/b) = (a + b - 1) // b for positive integers
        # But beta is real. Formula: r0 = r_short - floor(beta - v)
        delta_r = floor(beta_prime) # floor(beta - v)
        r0 = r_short - delta_r
        
        # Calculate next intercept beta_1
        # beta_1 = (beta - v) - delta_r * alpha
        beta_prime = beta_prime - delta_r * alpha
        
        # Add the truncated run if length > 0
        if r0 > 0:
            runs.append((x, y, r0))
            x += r0
            
        # If r0 was 0, we haven't moved, but we have a valid beta_prime for the next step
        # The loop below will handle the first full run
    else:
        # Not truncated
        # r0 = 0, beta_1 = beta_prime
        pass

    # Iterative traversal
    while y < height and x < width:
        # Determine run type based on beta_prime
        # If beta_prime < 0 (which corresponds to beta < v in original), it's long
        # If beta_prime >= 0, it's short
        if beta_prime < 0:
            run_len = r_long
            # Update beta_prime for next run: beta_{j+1} = beta_j + mu
            beta_prime = beta_prime + mu
        else:
            run_len = r_short
            # Update beta_prime for next run: beta_{j+1} = beta_j - v
            beta_prime = beta_prime - v
            
        # Check bounds for the run
        # We need to ensure we don't exceed width/height
        # Since runs are horizontal, we only check x bound
        if x + run_len > width:
            run_len = width - x
            if run_len <= 0:
                break
        
        # Add run
        runs.append((x, y, run_len))
        
        # Move to next run position
        x += run_len
        y += 1
        
        # Check if we've exited the grid vertically
        if y >= height:
            break

    # Note: The 4-connected extension (backwards by 1 cell) is a post-processing step
    # or applied during rendering, not strictly part of the traversal path generation
    # unless the path itself must be 4-connected.
    return runs
```

**Edge Cases and Pitfalls:**
*   **Initial Truncation:** The first run may be shorter than the standard short run length. This must be calculated separately using $r_0 = \lceil (1-\beta)/\alpha \rceil$ [S1].
*   **Corner Intersections:** When converting to a 4-connected path, runs must not be extended backwards if the intercept is exactly 0 (or $-v$), as this indicates a corner intersection where the ray passes through a vertex rather than crossing an edge [S1].
*   **Slope Range:** The algorithm assumes $0 \le \alpha \le 1$. Slopes outside this range require coordinate transformation [S1].
*   **Precision:** The intercept sequence values are real numbers. Accumulation errors in $\beta_j$ may occur over long rays. Using the optimized translation method and checking against zero helps mitigate some logic errors, but fixed-point arithmetic or careful floating-point handling is recommended [S1].

## Operating characteristics
*   **Time Complexity:** $O(n/r)$, where $n$ is the number of cells in the ray path and $r$ is the average run length [S1]. Cell-based algorithms (DDA) have $O(n)$ complexity [S1].
*   **Memory Complexity:** $O(1)$ auxiliary space for traversal state (current position, intercept), plus $O(k)$ for storing the output runs, where $k$ is the number of runs [S1].
*   **Performance:** Measured average acceleration of 125% over all orientations compared to cell-based traversal [S1]. Improvement is 110% for average run length 2, and 180% for average run length 25 [S1]. No improvement is measured when average run length is close to 1 [S1].
*   **Strengths:** Significant reduction in the number of steps for rays with shallow angles relative to the grid axes (long runs) [S1]. Provides structural information useful for accelerating intersection testing [S1].
*   **Limitations:** Performance gain diminishes as run length approaches 1 (steep rays) [S1]. Requires handling of corner intersections and initial truncation [S1].

## Background
*   **Origin:** The method was introduced by Stephenson and Litow in 2001 [S1].
*   **History:** It was developed to accelerate ray tracing of height fields, which are common in geographic information systems, scientific visualization, and terrain rendering [S1]. The mathematical foundation relies on properties of digital lines described by Wu (1982) and Rosenfeld (1974) [S1].
*   **Usage:** Primarily used in terrain rendering and height field visualization [S1].
