# Front-to-Back Layer Traversal

Also called: Layer-based Front-to-Back Traversal

## Overview
Front-to-Back Layer Traversal is a rendering order strategy for Matryoshka-like hierarchical data structures that processes cells in front-to-back order along the viewing direction to handle occlusion correctly [S1, unofficial]. It operates on pre-defined layers composed of six planes, classifying them into closest and furthest groups relative to the camera to ensure outer cells occlude inner cells without per-ray depth sorting [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A Matryoshka layer $l_m$ defined by six planes, a viewing direction (camera position), and an auxiliary buffer for marking drawable cells [S1, unofficial].
- Output: A sequence of cell processing instructions ordered front-to-back [S1, unofficial].

**Data Structures:**
- **Layer Definition:** A layer consists of six planes classified into two groups based on the camera position [S1, unofficial].
- **Closest Planes:** The three planes closest to the camera, defined by binary indices $k_x, k_y, k_z \in \{0, 1\}$ [S1, unofficial].
- **Furthest Planes:** The three planes furthest from the camera, defined by the opposite indices $k'_x, k'_y, k'_z$ [S1, unofficial].
- **Auxiliary Buffer:** A memory structure used to mark cells as "drawable" during a first pass, allowing them to be processed in the correct order during a second pass [S1, unofficial].

**Parameters:**
- $k_x, k_y, k_z$: Binary values (0 or 1) determined by the viewing camera to define which planes are closest to the camera position [S1, unofficial].
- $k'_x, k'_y, k'_z$: The opposite values of $k_x, k_y, k_z$ (i.e., $1-k_x$, etc.), defining the furthest planes [S1, unofficial].

**Steps:**
1. **Classify Planes:** Determine $k_x, k_y, k_z$ based on the camera's viewing direction to identify the closest planes [S1, unofficial].
2. **Process Closest Planes:** Identify planes $X=X_{kx}$, $Y=Y_{ky}$, $Z=Z_{kz}$ [S1, unofficial]. Within this group, apply intra-plane ordering: cells from $X=X_{kx}$ that also belong to $Y=Y_{ky}$ are treated before any cells from $Y=Y_{ky}$, and plane $Z=Z_{kz}$ is processed last among the three closest planes [S1, unofficial]. Mark these cells as drawable in the auxiliary buffer [S1, unofficial].
3. **Process Inner Layers:** If $l_m$ is not the last layer, process the next inner layer $l_{m+1}$ using the same logic [S1, unofficial].
4. **Process Furthest Planes:** Identify planes $X=X_{k'x}$, $Y=Y_{k'y}$, $Z=Z_{k'z}$ [S1, unofficial]. Within this group, apply inverted intra-plane ordering: plane $Z=Z_{k'z}$ is processed first because it may occlude cells in $Y=Y_{k'y}$, which in turn may occlude cells in $X=X_{k'x}$ [S1, unofficial]. Process the cells marked in the auxiliary buffer in this specific order [S1, unofficial].

        self.drawables = set()
    def clear(self):
        self.drawables.clear()
    def mark(self, cell):
        self.drawables.add(cell)
    def is_drawable(self, cell):
        return cell in self.drawables

    auxiliary_buffer.clear()
    # Pass 1: Mark cells as drawable
    for plane in [layer.plane_z[kpz], layer.plane_y[kpy], layer.plane_x[kpx]]:
        for cell in plane:
            auxiliary_buffer.mark(cell)
    # Pass 2: Process buffer in specified plane order
    for plane in [layer.plane_z[kpz], layer.plane_y[kpy], layer.plane_x[kpx]]:
        for cell in plane:
            if auxiliary_buffer.is_drawable(cell):
                render(cell)

**Edge Cases and Pitfalls:**
- **Shared Cells:** Cells at the intersection of planes (edges/corners) must be handled carefully to avoid double processing or incorrect occlusion [S1, unofficial]. The intra-plane ordering rules specifically address this [S1, unofficial].
- **Camera Position:** The values of $k_x, k_y, k_z$ depend on the camera position [S1, unofficial]. If the camera moves, these values may change, requiring a re-evaluation of the plane grouping [S1, unofficial].
- **Auxiliary Buffer:** Requires sufficient memory to store the drawable cells for each layer [S1, unofficial].

## Subtopics

### Intra-Plane Rendering Order
A specific ordering rule for processing cells within the same plane group to handle shared cells (edges/corners) correctly, ensuring correct occlusion between planes [S1, unofficial]. For closest planes, cells from $X=X_1$ belonging to $Y=Y_1$ are processed before $Y=Y_1$, and $Z=Z_1$ is last [S1, unofficial]. For furthest planes, $Z=Z_0$ is first, occluding $Y=Y_0$, which occludes $X=X_0$ [S1, unofficial].

## Operating characteristics
The sources do not provide measured performance, hardware specifics, or explicit time/memory complexity formulas [S1, unofficial]. Strengths include correct occlusion handling for nested Matryoshka structures without per-ray depth sorting, and efficiency for parallel projections with fixed viewing directions [S1, unofficial]. Limitations include the requirement for an auxiliary buffer and dependency on camera position for plane classification, which may require re-evaluation if the camera moves frequently [S1, unofficial]. It is suitable for rendering Matryoshka-like data structures with parallel projection where correct occlusion is required, but not for structures that do not fit the Matryoshka layer model or when auxiliary buffer memory is constrained [S1, unofficial].

## Background
The method is described in the context of the Matryoshka algorithm for visualizing active cells in hierarchical data structures [S1, unofficial]. It addresses the challenge of maintaining correct front-to-back rendering order for occlusion by leveraging the geometric properties of layer planes relative to the camera position [S1, unofficial].
