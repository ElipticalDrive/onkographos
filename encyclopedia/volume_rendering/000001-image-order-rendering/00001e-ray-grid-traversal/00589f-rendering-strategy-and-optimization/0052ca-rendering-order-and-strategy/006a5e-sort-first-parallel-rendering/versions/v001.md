# Sort-first Parallel Rendering

Also called: Sort-First Parallel Rendering Architecture, Sort-first rendering, WireGL-like architecture

## Overview
Sort-first parallel rendering is a distributed volume rendering strategy where the viewport is decomposed into spatial tiles, and each process or node is responsible for rendering a specific part of the image rather than a part of the volume [S1][S2, unofficial]. Unlike sort-last approaches that require a final compositing pass to merge results from volume partitions, sort-first rendering eliminates the need for compositing because each node renders its assigned image region directly to a local framebuffer [S1]. This method is distinct from its siblings, such as [Front-to-Back Layer Traversal](1212-front-to-back-layer-traversal.md) and [Backward Projection](1491-backward-projection.md), by shifting the parallelism bottleneck from data distribution to image-space load balancing [S2, unofficial]. It is particularly advantageous for algorithms relying on ray coherence, such as visibility culling or volumetric shadows, where grouping rays by screen space improves performance [S2, unofficial].

## How it works
The method operates on a cluster of render nodes, each equipped with graphics hardware. The core principle is to sort the rendering workload from an object-parallel distribution (where each node holds a chunk of data) to an image-parallel distribution (where each node renders a chunk of the screen) [S3, unofficial].

### Inputs and Outputs
*   **Input:** A volumetric dataset (often partitioned into bricks for scalability [S2, unofficial]), a camera configuration (view and projection matrices), and a viewport definition.
*   **Output:** A single composite image assembled from the tiles rendered by individual nodes.

### Data Structures
1.  **Tile Map:** A mapping that assigns specific rectangular regions of the viewport (tiles) to specific render nodes. This map is dynamic and updated based on load balancing [S2, unofficial].
2.  **Brick Index:** A spatial index of the volume data, organized into bricks to facilitate efficient data transfer and caching [S2, unofficial].
3.  **Render Stream:** A sequence of rendering commands (draw calls) generated by the client application, which is intercepted and sorted by the architecture [S3, unofficial].

### Steps
1.  **Stream Interception and Sorting:** The rendering pipeline intercepts the command stream. A `tilesort` component analyzes the geometry and camera parameters to determine which tiles (viewport regions) each object or ray contributes to [S3, unofficial].
2.  **Distribution:** The sorted streams are distributed to the intermediate render nodes responsible for the corresponding tiles [S3, unofficial].
3.  **Data Preloading (Caching):** To address the weak point of sort-first decompositions regarding data scalability, a bricking approach is used. A caching strategy exploits frame-to-frame coherence to preload volume bricks close to the current frustum of each render node [S2, unofficial].
4.  **Local Rendering:** Each intermediate server serializes its incoming streams and renders them using locally housed graphics hardware. The rendering follows the standard front-to-back accumulation required for correct opacity transfer [G].
5.  **Framebuffer Extraction:** At the end of the frame, a `readback` component extracts the framebuffer from the local graphics hardware. This is achieved by providing a custom implementation of `SwapBuffers` that triggers the extraction [S3, unofficial].
6.  **Tile Transmission:** The extracted pixel arrays are passed to a `send` component. Each pixel array is transmitted to a final server (or a designated reassembly node) for tile reassembly [S3, unofficial].
7.  **Reassembly:** The final server receives the tiles and assembles them into the complete image. The coordinates for each tile are known from the initial configuration, often passed via `glRasterPos` to ensure correct placement during the `glDrawPixels` operation used for transmission [S3, unofficial].

### Pseudocode
The following pseudocode illustrates the high-level flow of a single frame in a sort-first architecture, focusing on the distribution and reassembly logic.

```python
def sort_first_render_frame(camera, volume_data, viewport):
    # 1. Determine tile assignment based on current load and geometry
    # This step involves per-pixel cost estimation to dynamically balance load [S2, unofficial]
    tile_map = compute_tile_map(camera, volume_data, viewport)
    
    # 2. Distribute rendering tasks to nodes
    for node_id, tile_region in tile_map.items():
        # Preload necessary bricks for this node's frustum [S2, unofficial]
        preload_bricks(node_id, camera, volume_data)
        
        # Render the assigned tile region
        # The node renders its specific part of the viewport [S1]
        framebuffer = render_tile(node_id, tile_region, camera, volume_data)
        
        # 3. Extract and send the tile
        # Custom SwapBuffers extracts the framebuffer [S3, unofficial]
        tile_data = extract_framebuffer(framebuffer)
        
        # Send tile data to the reassembly server [S3, unofficial]
        send_tile_to_reassembly_server(node_id, tile_data, tile_region.coordinates)

    # 4. Reassemble the final image
    # The final server collects tiles and places them correctly [S3, unofficial]
    final_image = reassemble_tiles(tile_map)
    
    return final_image

def render_tile(node_id, tile_region, camera, volume_data):
    """
    Renders a specific tile of the viewport.
    Uses local graphics hardware [S3, unofficial].
    """
    # Set up the viewport for this specific tile
    set_viewport(tile_region)
    
    # Perform standard volume rendering (e.g., ray marching)
    # for the rays passing through this tile [G]
    image = ray_march_volume(camera, volume_data)
    
    return image
```

### Parameters and Edge Cases
*   **Load Balancing:** The system must dynamically reorganize the image decomposition based on per-pixel cost estimation [S2, unofficial]. Static partitioning leads to inefficiencies.
*   **Viewport Movement:** A significant pitfall is load balancing when moving the viewport. As the view changes, the data required for specific tiles may shift between processes, necessitating data movement between nodes [S1].
*   **Data Scalability:** Sort-first decompositions can suffer from weak data scalability if the volume data is not partitioned efficiently. The bricking approach mitigates this [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** The rendering time is dominated by the slowest node in the cluster. Dynamic load balancing attempts to minimize this by redistributing tiles based on computational cost [S2, unofficial].
*   **Memory Complexity:** Each node must store the volume bricks relevant to its assigned tiles. The bricking approach helps manage memory by only loading necessary data [S2, unofficial].
*   **Strengths:** Eliminates the compositing bottleneck inherent in sort-last approaches [S1]. Exploits spatial coherence for optimizations like visibility culling [S2, unofficial].
*   **Limitations:** Load balancing is challenging, especially during viewport navigation, due to the need to move data between processes [S1]. Data scalability can be an issue without proper bricking [S2, unofficial].
*   **When to Use:** Suitable for GPU-based cluster systems where compositing overhead is prohibitive and ray coherence can be exploited [S2, unofficial].
*   **When Not to Use:** Not ideal for scenarios with highly dynamic viewports where data movement overhead outweighs rendering benefits, or when the volume data cannot be effectively partitioned into bricks.

## Background
Sort-first parallel rendering was formalized as a distributed rendering algorithm for GPU-based cluster systems. The approach functions identically to the WireGL architecture, where data is sorted from an object-parallel distribution to an image-parallel distribution early in the pipeline [S3, unofficial]. The specific paper "Sort First Parallel Volume Rendering" was published in IEEE Transactions on Visualization and Computer Graphics in 2011 [S2, unofficial]. It addresses the limitations of earlier parallel volume rendering methods by introducing dynamic load balancing and a bricking approach for improved data scalability [S2, unofficial]. The architecture is often implemented using frameworks like Chromium, which provides a stream processing framework for interactive rendering on clusters [S3, unofficial].
