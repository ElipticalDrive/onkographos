# Sort-first Parallel Rendering

Also called: Sort-First Parallel Rendering Architecture, Sort-first rendering, WireGL-like architecture

## Overview
Sort-first parallel rendering is a distributed volume rendering strategy where the viewport is decomposed into spatial tiles, and each process or node is responsible for rendering a specific part of the image rather than a part of the volume [S1][S2]. Unlike sort-last approaches that require a final compositing pass to merge results from volume partitions, sort-first rendering eliminates the need for compositing because each node renders its assigned image region directly to a local framebuffer [S1]. Sort-first partitioning is preferable to parallelize algorithms that depend on ray coherence, such as visibility culling or volumetric shadows [S3, unofficial].

## How it works
The method operates on a cluster of render nodes, each equipped with graphics hardware [S3, unofficial]. The core principle is to sort the rendering workload from an object-parallel distribution to an image-parallel distribution early in the pipeline [S4, unofficial].

### Inputs and Outputs
*   **Input:** A volumetric dataset (often partitioned into bricks for scalability [S3, unofficial]), a camera configuration, and a viewport definition [S2].
*   **Output:** A single composite image assembled from the tiles rendered by individual nodes [S4, unofficial].

### Data Structures
1.  **Tile Map:** A mapping that assigns specific rectangular regions of the viewport (tiles) to specific render nodes, dynamically updated based on per-pixel cost estimation [S3, unofficial].
2.  **Brick Index:** A data structure organizing the volume into bricks to improve data scalability, addressing a known weakness of sort-first decompositions [S3, unofficial].
3.  **Render Stream:** A sequence of rendering commands intercepted and sorted by the architecture [S4, unofficial].

### Steps
1.  **Stream Interception and Sorting:** The rendering pipeline intercepts the command stream. A `tilesort` component analyzes the geometry and camera parameters to determine which tiles each object or ray contributes to [S4, unofficial].
2.  **Distribution:** The sorted streams are distributed to the intermediate render nodes responsible for the corresponding tiles [S4, unofficial].
3.  **Data Preloading (Caching):** To address the weak point of sort-first decompositions regarding data scalability, a bricking approach is used. A caching strategy exploits frame-to-frame coherence to preload volume bricks close to the current frustum of each render node [S3, unofficial].
4.  **Local Rendering:** Each intermediate server serializes its incoming streams and passes the result to a `readback` SPU, which inherits from the `render` SPU to render streams on locally housed graphics hardware [S4, unofficial]. The rendering follows the standard front-to-back accumulation required for correct opacity transfer [G].
5.  **Framebuffer Extraction:** At the end of the frame, the `readback` SPU provides a custom implementation of `SwapBuffers` to extract the framebuffer [S4, unofficial].
6.  **Tile Transmission:** The extracted pixel arrays are passed to a `send` SPU, which transmits the data to a final server for tile reassembly [S4, unofficial].
7.  **Reassembly:** The final server receives the tiles and assembles them into the complete image. Each `readback` SPU is configured at startup to know where its tiles should end up in the final display; these coordinates are passed to the `send` SPU using `glRasterPos` to ensure correct placement during the `glDrawPixels` operation used for transmission [S4, unofficial].

### Parameters and Edge Cases
*   **Load Balancing:** The system must dynamically reorganize the image decomposition based on per-pixel cost estimation [S3, unofficial]. Static partitioning leads to inefficiencies [S3, unofficial].
*   **Viewport Movement:** A significant pitfall is load balancing when moving the viewport. As the view changes, the data required for specific tiles may shift between processes, necessitating data movement between nodes [S1].
*   **Data Scalability:** Sort-first decompositions can suffer from weak data scalability if the volume data is not partitioned efficiently. The bricking approach mitigates this [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** The rendering time is dominated by the slowest node in the cluster. Dynamic load balancing attempts to minimize this by reorganizing the image decomposition based on per-pixel cost estimation [S3, unofficial].
*   **Memory Complexity:** Each node must store the volume bricks relevant to its assigned tiles. The bricking approach helps manage memory by only loading necessary data [S3, unofficial].
*   **Strengths:** Eliminates the compositing bottleneck inherent in sort-last approaches [S1].
*   **Limitations:** Load balancing is challenging, especially during viewport navigation, due to the need to move data between processes [S1]. Data scalability can be an issue without proper bricking [S3, unofficial].
*   **When to Use:** Suitable for GPU-based cluster systems where compositing overhead is prohibitive and ray coherence can be exploited [S3, unofficial].
*   **When Not to Use:** Not ideal for scenarios with highly dynamic viewports where data movement overhead outweighs rendering benefits, or when the volume data cannot be effectively partitioned into bricks [S1][S3, unofficial].

## Background
Sort-first parallel rendering was formalized as a distributed rendering algorithm for GPU-based cluster systems [S3, unofficial]. The approach functions identically to the WireGL architecture, where data is sorted from an object-parallel distribution to an image-parallel distribution early in the pipeline [S4, unofficial]. The specific paper "Sort First Parallel Volume Rendering" was published in IEEE Transactions on Visualization and Computer Graphics in 2011 [S3, unofficial]. It addresses the limitations of earlier parallel volume rendering methods by introducing dynamic load balancing and a bricking approach for improved data scalability [S3, unofficial]. The architecture is often implemented using frameworks like Chromium, which provides a stream processing framework for interactive rendering on clusters [S4, unofficial].
