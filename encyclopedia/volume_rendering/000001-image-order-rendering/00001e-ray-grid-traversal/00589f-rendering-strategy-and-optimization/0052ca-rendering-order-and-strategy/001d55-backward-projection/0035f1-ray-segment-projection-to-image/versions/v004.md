# Ray Segment Projection to Image

Also called: Ray Bounding Box Computation in Image Space, Ray Segment Projection, Ray-Image Frame Intersection with Near/Far Clipping

## Overview
Ray Segment Projection to Image computes the bounding segment of a 3D ray (defined by origin and direction) that overlaps with a canonical image frame, returning the parameter range $[t_{min}, t_{max}]$ and the 2D image coordinates $(xy_{min}, xy_{max})$ at the entry and exit points [S2, unofficial]. It solves the problem of determining which parts of a ray are visible within the camera's field of view and clipping planes, which is a prerequisite for subsequent rasterization or sampling in image-order volume rendering [S2, unofficial]. Unlike [Pixel-Weighted Line Integration](8503-pixel-weighted-line-integration.md), which approximates line integrals using pixel weights, this method explicitly computes the geometric bounding box of the ray segment within the image plane to provide necessary bounds for sampling [S2, unofficial]. It differs from [GPU Backprojection](5843-gpu-backprojection.md) by operating on individual ray segments rather than aggregating contributions into a volume grid, and from [Cone Beam Forward Projection with Trilinear Interpolation](8247-cone-beam-forward-projection-with-trilinear-interpolation.md) by handling general perspective rays rather than parallel or cone-beam specific geometries.

## How it works
**Inputs:**
- `origins`: Tensor of shape `(*batch, 3)`, ray origins in world space.
- `directions`: Tensor of shape `(*batch, 3)`, ray directions in world space.
- `extrinsics`: $4 \times 4$ matrix (or tensor) transforming world space to camera space.
- `near`: Optional scalar or tensor specifying the near clipping plane distance in camera space. If `None`, defaults to $t=0$ (origin).
- `far`: Optional scalar or tensor specifying the far clipping plane distance in camera space. If `None`, defaults to $t=\infty$.
- `epsilon`: Small float for numerical stability checks (e.g., $10^{-6}$).

**Outputs:**
- `RaySegmentProjection`: A TypedDict containing:
  - `t_min`: Tensor of shape `(*batch,)`, minimum parameter $t$ of the valid segment.
  - `t_max`: Tensor of shape `(*batch,)`, maximum parameter $t$ of the valid segment.
  - `xy_min`: Tensor of shape `(*batch, 2)`, 2D image coordinates $(x, y)$ at $t_{min}$.
  - `xy_max`: Tensor of shape `(*batch, 2)`, 2D image coordinates $(x, y)$ at $t_{max}$.
  - `overlaps_image`: Tensor of shape `(*batch,)`, boolean flag indicating if the segment overlaps the image frame $[0,1] \times [0,1]$.

**Data Structures:**
The image frame is defined in camera space as $x \in [0, 1]$ and $y \in [0, 1]$. The ray is parameterized as $P(t) = O + t \cdot D$, where $O$ is the origin and $D$ is the direction in camera space.

**Steps:**

1. **Transform to Camera Space:**
   Transform ray origins and directions from world space to camera space using the inverse extrinsics matrix.
   Let $M_{world2cam}$ be the $4 \times 4$ extrinsics matrix.
   For each ray $i$:
   $$
   O_i^{cam} = M_{world2cam}[0:3, 3] + M_{world2cam}[0:3, 0:3] \cdot O_i^{world}
   $$
   $$
   D_i^{cam} = M_{world2cam}[0:3, 0:3] \cdot D_i^{world}
   $$
   [S1, unofficial]

2. **Compute Frame Intersections:**
   Compute the intersection parameters $t$ with the four image frame boundaries: $x=0, x=1, y=0, y=1$.
   For a ray $O + tD$, the intersection with a plane $x=c$ is $t_x = (c - O_x) / D_x$ (if $D_x \neq 0$). Similarly for $y=c$.
   Let $t_{x0}, t_{x1}, t_{y0}, t_{y1}$ be the $t$ values for $x=0, x=1, y=0, y=1$ respectively.
   Use a helper `_intersect_image_coordinate` to compute these, handling division by zero or near-zero directions.
   [S1, unofficial][S2, unofficial]

3. **Determine Min/Max Frame Bounds:**
   Find the minimum and maximum $t$ values among the four frame intersections.
   $$
   t_{frame\_min} = \min(t_{x0}, t_{x1}, t_{y0}, t_{y1})
   $$
   $$
   t_{frame\_max} = \max(t_{x0}, t_{x1}, t_{y0}, t_{y1})
   $$
   This step uses `_compare_projections` with reduction "min" and "max" respectively. Note that these $t$ values are valid only if the corresponding intersection point lies within the other coordinate's range $[0,1]$. However, the algorithm simplifies this by combining with near/far bounds later.
   [S1, unofficial]

4. **Compute Near and Far Projections:**
   - **Near:**
     - If `near` is provided, compute $t_{near} = \text{near}$.
     - If `near` is `None`, compute $t_{near} = 0$.
     - Check validity: If $t_{near} = 0$, check if the origin depth $O_z^{cam}$ is near zero (i.e., $|O_z^{cam}| < \epsilon$).
       - If $|O_z^{cam}| < \epsilon$, the ray origin is at the camera position. Use the direction for projection (valid).
       - If $|O_z^{cam}| \ge \epsilon$, the origin is on the zero-depth plane but not at the camera. Mark as invalid.
     [S2, unofficial][S1, unofficial]
   - **Far:**
     - If `far` is provided, compute $t_{far} = \text{far}$.
     - If `far` is `None`, compute $t_{far} = \infty$.
     - Validity: Always valid if finite, or valid if $\infty$ (ray extends to infinity).
     [S2, unofficial][S1, unofficial]

5. **Combine Bounds and Determine Validity:**
   Iterate through all 4 combinations of validity for near and far projections to assign the correct bounds.
   Let $valid_{near}$ be the boolean validity of the near projection.
   Let $valid_{far}$ be the boolean validity of the far projection.
   
   For each combination $(valid_{near}, valid_{far})$:
   - Create a mask for rays where this combination holds.
   - Determine $t_{min}$ and $t_{max}$:
     - If $valid_{near}$ and $valid_{far}$:
       - $t_{min} = \min(t_{near}, t_{frame\_min})$
       - $t_{max} = \max(t_{far}, t_{frame\_max})$

6. **Compute 2D Coordinates:**
   For the valid segment, compute $xy_{min}$ and $xy_{max}$ by projecting the points $P(t_{min})$ and $P(t_{max})$ onto the image plane.
   In camera space, the image plane is at $z=1$ (or similar, depending on convention). However, the output is $xy$ coordinates.
   If the image frame is $[0,1] \times [0,1]$, then $x = O_x + t D_x$ and $y = O_y + t D_y$ are not the final image coordinates if the image plane is at $z=1$.
   Usually, perspective projection maps $(X,Y,Z)$ to $(X/Z, Y/Z)$.
   The sources say "xy_min (Float[Tensor, "*batch 2"])".
   If the frame is defined in normalized device coordinates (NDC) or similar, the $x$ and $y$ values at the intersection with the frame boundaries are already in $[0,1]$.
   Wait, the frame intersections are with $x=0, x=1, y=0, y=1$. These are planes in camera space.
   The intersection point $P(t)$ has coordinates $(x(t), y(t), z(t))$.
   The "xy" coordinates in the output likely refer to the normalized coordinates on the image plane.
   If the image plane is at $z=1$, then $x_{img} = x(t)/z(t)$ and $y_{img} = y(t)/z(t)$.
   However, the frame boundaries $x=0,1$ and $y=0,1$ are in camera space.
   If the ray intersects $x=0$, the point is $(0, y(t), z(t))$. The image coordinate $x$ is $0/z(t) = 0$.
   So, if the output is the normalized image coordinates, we compute:
   $$
   xy_{min} = \left( \frac{O_x^{cam} + t_{min} D_x^{cam}}{O_z^{cam} + t_{min} D_z^{cam}}, \frac{O_y^{cam} + t_{min} D_y^{cam}}{O_z^{cam} + t_{min} D_z^{cam}} \right)
   $$
   $$
   xy_{max} = \left( \frac{O_x^{cam} + t_{max} D_x^{cam}}{O_z^{cam} + t_{max} D_z^{cam}}, \frac{O_y^{cam} + t_{max} D_y^{cam}}{O_z^{cam} + t_{max} D_z^{cam}} \right)
   $$
   [S2, unofficial]

**Pseudocode:**

```python
import torch
import math

def ray_segment_projection_to_image(
    origins: torch.Tensor,
    directions: torch.Tensor,
    extrinsics: torch.Tensor,
    near: float = None,
    far: float = None,
    epsilon: float = 1e-6
) -> dict:
    """
    Compute the bounding segment of a ray that overlaps with the image frame.
    
    Args:
        origins: (B, 3) ray origins in world space.
        directions: (B, 3) ray directions in world space.
        extrinsics: (4, 4) matrix transforming world to camera space.
        near: Optional near clipping distance.
        far: Optional far clipping distance.
        epsilon: Numerical stability threshold.
        
    Returns:
        Dict with t_min, t_max, xy_min, xy_max, overlaps_image.
    """
    B = origins.shape[0]
    
    # Step 1: Transform to Camera Space
    # M_world2cam is extrinsics
    # O_cam = M[0:3, 3] + M[0:3, 0:3] @ O_world
    # D_cam = M[0:3, 0:3] @ D_world
    rot = extrinsics[:3, :3]
    trans = extrinsics[:3, 3]
    
    origins_cam = origins @ rot.T + trans.unsqueeze(0)
    directions_cam = directions @ rot.T
    
    # Step 2: Compute Frame Intersections
    # Frame boundaries: x=0, x=1, y=0, y=1
    # t = (c - O) / D
    
    def intersect_plane(O, D, c, axis):
        # axis: 0 for x, 1 for y
        denom = D[:, axis]
        # Avoid division by zero
        valid = torch.abs(denom) > epsilon
        t = torch.zeros_like(denom)
        t[valid] = (c - O[valid, axis]) / denom[valid]
        # If denom is zero, t is infinity if O != c, else undefined (handled by validity)
        t[~valid] = torch.inf
        return t, valid

    t_x0, valid_x0 = intersect_plane(origins_cam, directions_cam, 0.0, 0)
    t_x1, valid_x1 = intersect_plane(origins_cam, directions_cam, 1.0, 0)
    t_y0, valid_y0 = intersect_plane(origins_cam, directions_cam, 0.0, 1)
    t_y1, valid_y1 = intersect_plane(origins_cam, directions_cam, 1.0, 1)
    
    # Step 3: Determine Min/Max Frame Bounds
    # We need the min and max t among the valid intersections
    # However, the standard slab method uses min/max of all 4, then checks if the interval is valid.
    # Here, we just take min and max of the 4 t values.
    t_frame_candidates = torch.stack([t_x0, t_x1, t_y0, t_y1], dim=-1) # (B, 4)
    
    # Find min and max, ignoring infinities if possible, but torch.min/max handles inf
    # We need to be careful with validity. If all are inf, min/max are inf.
    t_frame_min = torch.min(t_frame_candidates, dim=-1).values
    t_frame_max = torch.max(t_frame_candidates, dim=-1).values
    
    # Step 4: Compute Near and Far Projections
    # Near
    if near is None:
        t_near = torch.zeros(B, device=origins.device)
        # Check validity: origin depth near zero?
        # If origin z < epsilon, check if origin is at camera position (norm < epsilon)
        # Actually, source says: "If origin z < epsilon, check if origin is at camera position (norm < epsilon). If so, use direction for projection; otherwise mark as invalid."
        # This implies if origin is at camera (0,0,0), it's valid. If origin is on z=0 plane but not at (0,0,0), it's invalid.
        origin_norm = torch.norm(origins_cam, dim=-1)
        origin_z = origins_cam[:, 2]
        
        # Valid if origin is not at camera position? No, "If so, use direction for projection" -> valid.
        # "otherwise mark as invalid" -> invalid.
        # So if |origin_z| < epsilon:
        #   if origin_norm < epsilon: valid_near = True
        #   else: valid_near = False
        # Else: valid_near = True (origin is not on z=0 plane, so t=0 is fine)
        
        valid_near = torch.ones(B, dtype=torch.bool, device=origins.device)
        mask_near_zero_z = torch.abs(origin_z) < epsilon
        mask_at_camera = origin_norm < epsilon
        valid_near[mask_near_zero_z & ~mask_at_camera] = False
    else:
        t_near = torch.full((B,), near, device=origins.device)
        valid_near = torch.ones(B, dtype=torch.bool, device=origins.device)
        
    # Far
    if far is None:
        t_far = torch.full((B,), torch.inf, device=origins.device)
        valid_far = torch.ones(B, dtype=torch.bool, device=origins.device)
    else:
        t_far = torch.full((B,), far, device=origins.device)
        valid_far = torch.ones(B, dtype=torch.bool, device=origins.device)
        
    # Step 5: Combine Bounds
    # Effective near/far
    # If valid_near is False, t_near is effectively -inf (or ignored)
    # If valid_far is False, t_far is effectively +inf (or ignored)
    # But if either is invalid, the segment is invalid.
    
    # Let's follow the source: "Set overlaps_image to True only if both the min and max projections are valid."
    # This implies valid_near and valid_far must be True.
    
    # Also, the frame intersection must be valid.
    # If t_frame_min > t_frame_max, the ray does not intersect the frame.
    
    # Compute final t_min and t_max
    # t_min = max(t_near, t_frame_min)
    # t_max = min(t_far, t_frame_max)
    
    # But we must handle the case where t_near or t_far are invalid.
    # If valid_near is False, the segment is invalid.
    # If valid_far is False, the segment is invalid.
    
    # So, first check validity
    valid_segment = valid_near & valid_far & (t_frame_min < t_frame_max)
    
    # Compute bounds
    t_min = torch.maximum(t_near, t_frame_min)
    t_max = torch.minimum(t_far, t_frame_max)
    
    # If the segment is invalid, set t_min > t_max to indicate no overlap
    # Or just set overlaps_image to False.
    
    # Step 6: Compute 2D Coordinates
    # xy = (x/z, y/z)
    # P(t) = O + tD
    # x(t) = O_x + t D_x
    # y(t) = O_y + t D_y
    # z(t) = O_z + t D_z
    
    # t_min and t_max might be invalid. We still compute xy, but they will be ignored if overlaps_image is False.
    
    # Compute z at t_min and t_max
    z_min = origins_cam[:, 2] + t_min * directions_cam[:, 2]
    z_max = origins_cam[:, 2] + t_max * directions_cam[:, 2]
    
    # Avoid division by zero
    # If z is near zero, the point is at the camera, which is invalid for projection.
    # But we already checked validity.
    
    x_min = (origins_cam[:, 0] + t_min * directions_cam[:, 0]) / z_min
    y_min = (origins_cam[:, 1] + t_min * directions_cam[:, 1]) / z_min
    
    x_max = (origins_cam[:, 0] + t_max * directions_cam[:, 0]) / z_max
    y_max = (origins_cam[:, 1] + t_max * directions_cam[:, 1]) / z_max
    
    xy_min = torch.stack([x_min, y_min], dim=-1)
    xy_max = torch.stack([x_max, y_max], dim=-1)
    
    # Final overlaps_image
    overlaps_image = valid_segment
    
    return {
        "t_min": t_min,
        "t_max": t_max,
        "xy_min": xy_min,
        "xy_max": xy_max,
        "overlaps_image": overlaps_image
    }
```

## Subtopics

### [Pixel-Weighted Line Integration](8503-pixel-weighted-line-integration.md)
Pixel-Weighted Line Integration is a forward projection technique that computes a sinogram by approximating line integrals over a 2D image using pixel weights. It determines which pixels a line passes through and their intersection lengths using a Bresenham-like rasterization approach. It differs from matrix-based forward projection by computing the transformation manually to avoid constructing and inverting a large matrix.

### [Ray-to-Image Projection with Near/Far Plane Handling](15852-ray-to-image-projection-with-near-far-plane-handling.md)
This method projects 3D camera rays into 2D image space to determine their intersection with the image frame boundaries, computing bounding segments $(t_{min}, t_{max})$ and pixel coordinates $(xy_{min}, xy_{max})$ along with a validity flag. It specifically handles near/far clipping planes and degenerate camera origins (where the ray origin is at the camera position or on the zero-depth plane). It differs from [Pixel-Weighted Line Integration](8503-pixel-weighted-line-integration.md) by explicitly computing the geometric bounding box of the ray segment within the image plane rather than integrating weights directly, providing the necessary bounds for subsequent rasterization or sampling.

## Operating characteristics
- **Time Complexity:** $O(N)$ for $N$ rays, as each ray is processed independently with a constant number of arithmetic operations.
- **Memory Complexity:** $O(N)$ to store the output tensors.
- **Measured Performance:** Not given in the sources.
- **Scaling:** Scales linearly with the number of rays. Suitable for GPU parallelization.
- **Strengths:** Explicitly handles near/far clipping and degenerate cases. Provides precise geometric bounds for sampling.
- **Limitations:** Requires careful handling of numerical stability (division by zero, near-zero depths).
- **When to use:** When precise ray-segment bounds are needed for image-order rendering, such as in volume splatting or ray marching.
- **When not to use:** When approximate line integrals are sufficient (use [Pixel-Weighted Line Integration](8503-pixel-weighted-line-integration.md)) or when working with parallel rays (use [Cone Beam Forward Projection with Trilinear Interpolation](8247-cone-beam-forward-projection-with-trilinear-interpolation.md)).

## Background
The method is derived from implementations in modern volume rendering libraries, specifically [VolSplat](https://github.com/ziplab/VolSplat) and [VoLoDSplat](https://github.com/pulangk97/VoLoDSplat), which are used for 3D Gaussian Splatting and volume rendering tasks [S1, unofficial][S2, unofficial]. It is part of the image-order rendering pipeline, following backward projection and preceding rasterization or sampling.
