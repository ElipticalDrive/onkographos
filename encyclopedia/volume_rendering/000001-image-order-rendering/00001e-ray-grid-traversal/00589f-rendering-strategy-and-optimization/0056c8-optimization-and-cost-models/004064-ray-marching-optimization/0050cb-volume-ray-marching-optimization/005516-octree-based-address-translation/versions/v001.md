# Octree-based Address Translation

Also called: GigaVoxels

## Overview
Octree-based address translation is a method for managing multi-resolution volume data during ray-guided rendering by tightly coupling the spatial subdivision of an octree with the resolution levels of the volume data [S1, unofficial]. It solves the problem of efficiently accessing high-resolution bricks while minimizing memory bandwidth by ensuring that each octree node corresponds to exactly one brick in the data set [S1, unofficial]. Unlike page-table hierarchies which decouple spatial and resolution indices, this approach simplifies address calculation but requires keeping the entire path from root to leaf in cache, leading to potential memory overhead [S1, unofficial].

## How it works
**Inputs:** Multi-resolution volume dataset; ray origin and direction for each sample.
**Outputs:** Transmittance and color for the ray sample; list of missing bricks for CPU request.

**Data Structures:**
1.  **Brick Cache:** Stores the actual voxel data (bricks) for active nodes.
2.  **Node Pool:** A cache for octree nodes. Only nodes with bricks resident in the Brick Cache are stored here. These are considered "active" nodes [S1, unofficial].
3.  **Octree Node Layout:** Each entry in the Node Pool represents a group of eight sibling nodes sharing the same parent. Each individual node stores:
    *   A pointer to its corresponding entry in the Brick Cache.
    *   A pointer to the Node Pool entry storing its children (if the node is not a leaf).
    *   Metadata describing the region (e.g., a boolean flag indicating if the region contains only zero values) [S1, unofficial].

**Algorithm Steps:**
1.  **Initialization:** Load the root node of the octree into the Node Pool and its corresponding brick into the Brick Cache.
2.  **Ray Traversal:** For each ray sample, traverse the octree from the root node downwards.
3.  **Node Access:** At each level, check if the current node is in the Node Pool.
    *   If the node is present (active), access its children pointers and the corresponding brick.
    *   If the node is missing from the Node Pool, it implies the corresponding brick is not in the Brick Cache.
4.  **Brick Request:** If a brick is missing, record the request. Crassin et al. [CNLE09] use multiple render targets to record up to one missing brick per ray and report these requests to the CPU for asynchronous loading [S1, unofficial].
5.  **Subtree Requirement:** To reach a high-resolution brick, the entire subtree from the root node to the target node must be kept in both the Node Pool and the Brick Cache [S1, unofficial].
6.  **Rendering:** Use the metadata (e.g., zero-value check) to skip translucent or empty regions during the ray march [S1, unofficial].

**Pseudocode:**
```python
def traverse_octree(ray, root_node, node_pool, brick_cache):
    """
    Traverses the octree for a given ray, ensuring cache residency.
    Returns the final color/transmittance and a list of missing bricks.
    """
    missing_bricks = []
    current_node = root_node
    
    # Ensure root is in cache
    if current_node not in node_pool:
        load_node_to_cache(current_node, node_pool, brick_cache, missing_bricks)
        if current_node not in node_pool:
            return 0.0, 1.0, missing_bricks # Could not load root

    while current_node is not None:
        # Check if current node's brick is in cache
        if current_node.brick not in brick_cache:
            # Request brick from CPU
            missing_bricks.append(current_node.brick_id)
            # Attempt to load immediately or proceed with low-res if available
            # For simplicity, assume we proceed if not loaded, or block
            # In GigaVoxels, missing bricks are reported and rendering continues
            # with lower resolution or previous data if available.
            pass 
        
        # Access brick data for shading/ray marching
        brick_data = brick_cache.get(current_node.brick)
        
        # Use metadata to skip empty regions
        if current_node.metadata.is_zero:
            # Skip this node's contribution
            break 
            
        # Move to children if not leaf
        if not current_node.is_leaf:
            # Determine which child the ray enters
            child_index = get_ray_child_index(ray, current_node)
            child_node = current_node.children[child_index]
            
            # Ensure child is in cache
            if child_node not in node_pool:
                load_node_to_cache(child_node, node_pool, brick_cache, missing_bricks)
            
            if child_node not in node_pool:
                # Child not loaded, cannot go deeper
                break
                
            current_node = child_node
        else:
            break
            
    return color, transmittance, missing_bricks

def load_node_to_cache(node, node_pool, brick_cache, missing_bricks):
    """
    Loads a node and its brick into the respective caches.
    """
    # Load brick from storage
    brick = load_brick_from_storage(node.brick_id)
    brick_cache[node.brick_id] = brick
    
    # Load node structure
    node_pool[node] = True
```

**Parameters:**
*   **Brick Size:** Not given in the sources.
*   **Missing Brick Limit:** Up to one missing brick per ray is recorded per frame [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Memory Utilization:** Because the entire subtree from root to leaf must be kept in memory to reach a high-resolution brick, potentially unused low-resolution bricks are stored in the cache. This leads to sub-optimal GPU memory utilization due to the tight coupling of the multi-resolution hierarchy and spatial subdivision [S1, unofficial].
*   **Cache Thrashing:** If the working set of active bricks exceeds GPU memory, frequent swapping between CPU and GPU may occur.

## Subtopics

### GigaVoxels
The original system by Crassin et al. [CNLE09] that introduced this method. It uses multiple render targets to report missing bricks to the CPU. Choose this when simplicity of address translation is prioritized over optimal memory usage. [CNLE09]

### Multi-channel Extension
Brix et al. [BPH14] extended the structure to support multi-channel data. Choose this when rendering volumetric data with multiple attributes (e.g., density, temperature, color) simultaneously. [BPH14]

## Operating characteristics
*   **Time Complexity:** Traversal is $O(\log N)$ where $N$ is the number of voxels, assuming a balanced octree. However, cache misses may stall execution.
*   **Memory Complexity:** Memory usage is proportional to the number of active nodes and their entire subtrees. This can be significantly higher than necessary because low-resolution bricks for unused parts of the scene may remain in cache to maintain path integrity [S1, unofficial].
*   **Strengths:** Straightforward address calculation; easy to substitute missing high-resolution data with low-resolution data; efficient skipping of empty regions via metadata [S1, unofficial].
*   **Limitations:** Sub-optimal GPU memory utilization due to the requirement of keeping the full subtree in cache; tight coupling of resolution and spatial subdivision limits flexibility [S1, unofficial].
*   **When to Use:** Suitable for scenes with moderate memory requirements where simplicity of implementation is key.
*   **When Not to Use:** When GPU memory is constrained and the scene has large empty spaces or highly variable density, as the subtree requirement wastes memory on unused low-resolution bricks.

## Background
The method was introduced by Crassin et al. in 2009 as part of the GigaVoxels system [S1, unofficial]. It was one of the first methods to use an octree structure for address translation in ray-guided rendering. Brix et al. [BPH14] later extended the structure to multi-channel data. The approach is part of the broader category of octree-based ray-guided rendering, contrasting with page-table hierarchies [S1, unofficial].
