# UltraVis Cache Optimization

Also called: Knittel's Ray Casting, Optimized CPU Ray-Casting, Pentium III Optimized Ray Casting, UltraVis, UltraVis Cache Management, UltraVis System

## Overview
UltraVis is a software-based volume rendering system designed to maximize cache performance on Intel Pentium III processors by addressing cache thrashing through specific memory layouts and cache partitioning [S1][S2, unofficial][S3, book]. Unlike general ray-casting methods, it partitions the CPU cache into four dedicated blocks to prevent volume data from being evicted by competing structures like transfer functions or image buffers [S2, unofficial][S3, book]. It achieves this by combining bricked volume decomposition with a cubic interleaved address function for voxel storage, ensuring that neighboring rays accessing the same brick benefit from high cache reuse [S1][S3, book].

## How it works
**Inputs and Outputs:**
- Input: A 3D volumetric dataset (typically $256^3$ or similar), a transfer function, and camera parameters (view direction, image plane resolution).
- Output: A 2D image (e.g., $256 \times 256$ pixels) with semi-transparent volume rendering.

**Data Structures and Layout:**
1.  **Cache Partitioning:** The CPU cache is divided into four non-overlapping blocks [S2, unofficial][S3, book]:
    -   Block 1: Volume bricks.
    -   Block 2: Transfer function tables.
    -   Block 3: Image blocks (framebuffer tiles).
    -   Block 4: Temporary buffers.
    This ensures volume data maps to a private cache block and is never swapped out by competing data structures [S2, unofficial][S3, book].
2.  **Voxel Memory Layout:** Voxel data is stored using a cubic interleaved address function. For a cube of $n^3$ voxels (where $n$ is a power of two and $n^3$ is smaller than the cache size), the data occupies $n \times n \times n$ cache locations [S1]. This layout is achieved by placing voxel data in the first quarter of memory pages, leaving the remaining parts unused to prevent mapping conflicts [S1].
3.  **Brick Decomposition:** The volume is decomposed into bricks. A "flock" of rays is traced simultaneously across a single brick [S3, book].

**Algorithm Steps:**
1.  **Initialize Cache Management:** Configure the memory allocator to reserve distinct address ranges for the four cache blocks. Ensure volume data addresses map exclusively to the volume brick block [S2, unofficial][S3, book].
2.  **Load Brick:** Bring a volume brick into memory. Due to the private cache block, this data remains resident until explicitly discarded [S3, book].
3.  **Trace Ray Flock:** For the current brick, identify all rays that intersect it. Trace these rays simultaneously [S3, book].
    -   For each ray in the flock, traverse the brick using the interleaved address function to access voxel values [S1].
    -   Perform volume integration (compositing) for the ray segment within the brick.
4.  **Discard Brick:** Once all rays in the flock have finished traversing the current brick, discard the brick data from the cache to free the private block for the next brick [S3, book].
5.  **Repeat:** Proceed to the next brick until the volume is fully rendered.
6.  **Finalize:** Write the accumulated image data to the image block cache and then to the framebuffer [S2, unofficial][S3, book].

**Formulas:**
-   **Interleaved Addressing:** The source describes a "cubic interleaved address function" but does not provide the explicit mathematical formula for the index mapping. It states that for $n^3$ voxels, they occupy $n \times n \times n$ cache locations [S1].
-   **Memory Footprint:** The main memory footprint is four times higher than standard storage because volume data cannot be stored in address spaces that would map outside the private cache slots [S3, book].

**Parameters:**
-   $n$: Side length of the voxel cube in the interleaved layout. Must be a power of two. $n^3$ must be smaller than the cache size [S1].
-   Performance Target: Renders $256^3$ volume at 10 frames/s [S2, unofficial][S3, book].
-   Hardware: Intel Pentium III 500MHz [S1].

**Edge Cases and Pitfalls:**
-   **Cache Thrashing:** If the interleaved layout is not used or if $n$ is too large, cache thrashing occurs due to the non-local memory access pattern of diverging rays [S1].
-   **Memory Usage:** The requirement for a private cache block increases main memory footprint by a factor of four compared to standard contiguous storage [S3, book].
-   **Hardware Specificity:** The optimization relies on concrete details of the Pentium III cache replacement strategy (specifically, the mapping of data to cache sets and pages) [S1].

**Pseudocode:**
```python
def ultravis_render(volume_data, transfer_function, camera, image_buffer):
    # 1. Setup Cache Blocks
    # Allocate memory regions for:
    # - volume_bricks_block
    # - transfer_function_block
    # - image_blocks_block
    # - temp_buffers_block
    # Ensure volume data addresses map ONLY to volume_bricks_block
    cache_blocks = setup_cache_partitioning()

    # 2. Decompose Volume into Bricks
    bricks = decompose_volume_into_bricks(volume_data)

    # 3. Process Each Brick
    for brick in bricks:
        # Bring brick data into the private cache block
        # This data will not be evicted by other blocks
        current_brick_data = load_brick_into_cache(brick, cache_blocks.volume_bricks_block)

        # Identify rays intersecting this brick
        ray_flock = get_intersecting_rays(brick, camera)

        # Trace rays simultaneously across the brick
        for ray in ray_flock:
            # Traverse the brick using interleaved addressing
            # The interleaved layout ensures neighboring rays hit cached data
            accumulated_color = 0.0
            accumulated_opacity = 0.0
            
            # Ray traversal within the brick boundaries
            while ray_inside_brick(ray, brick):
                # Get voxel value using cubic interleaved address function
                # Note: Exact formula not provided in sources [S1]
                voxel_value = get_voxel_interleaved(current_brick_data, ray.position)
                
                # Sample transfer function
                color, opacity = sample_transfer_function(voxel_value, transfer_function)
                
                # Front-to-back compositing
                accumulated_color, accumulated_opacity = composite(
                    accumulated_color, accumulated_opacity,
                    color, opacity
                )
                
                # Advance ray
                ray.advance()

            # Write result to image buffer
            write_to_image_buffer(ray.pixel_coord, accumulated_color, image_buffer)

        # Discard brick data from cache when all rays have finished
        unload_brick_from_cache(current_brick_data, cache_blocks.volume_bricks_block)

    return image_buffer
```

## Subtopics

### Bricked Volume Rendering
A technique where the volume is divided into smaller chunks (bricks) to improve cache locality and enable out-of-core rendering. UltraVis uses this to bring data in once and discard it after all rays in a flock have processed it [S3, book].

### Interleaved Memory Layout
A storage scheme that reorders voxel data to match cache line access patterns, reducing cache misses for neighboring rays. UltraVis uses a cubic interleaved function for this [S1].

## Operating characteristics
-   **Time Complexity:** Not explicitly defined in terms of Big-O, but performance is measured in frames per second (fps).
-   **Memory Complexity:** The main memory footprint is four times higher than standard contiguous storage due to the private cache block requirement [S3, book].
-   **Measured Performance:**
    -   Renders a $256^3$ volume at 10 frames/s on an Intel Pentium III 500MHz [S2, unofficial][S3, book].
    -   Renders a $256 \times 256 \times 110$ UNC MRI-head volume at 1.7 to 7.0 fps on a PIII 500MHz with $256 \times 256$ image resolution [S1].
-   **Strengths:**
    -   Significantly reduces cache thrashing through interleaved addressing and cache partitioning [S1][S2, unofficial].
    -   High performance on specific hardware (Pentium III) [S1].
-   **Limitations:**
    -   Hardware-specific: Relies on Pentium III cache replacement strategies [S1].
    -   Increased memory usage: 4x main memory footprint [S3, book].
    -   Limited to semi-transparent volume rendering [S1].
-   **When to Use:** When rendering on older CPU architectures with limited cache and memory bandwidth, and when hardware-specific optimizations are acceptable.
-   **When Not to Use:** On modern GPUs or CPUs with different cache hierarchies, or when memory usage is a critical constraint.

## Background
UltraVis was introduced by Knittel [S4, unofficial]. It is a comprehensive system for accelerated software-based volume rendering [S2, unofficial][S3, book]. The system was designed to address the limitations of memory bandwidth and cache thrashing in ray-tracing-based volume rendering on commodity hardware, specifically the Intel Pentium III [S1]. It builds on the principles of bricked volume decomposition and ray flocking [S3, book].
