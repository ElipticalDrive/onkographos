# UltraVis Cache Optimization

Also called: Knittel's Ray Casting, Optimized CPU Ray-Casting, Pentium III Optimized Ray Casting, UltraVis, UltraVis Cache Management, UltraVis System

## Overview
UltraVis Cache Optimization is a software-based volume rendering method designed to maximize cache hit rates on Intel Pentium III processors by restructuring memory layout and managing cache partitions [S1][S2, unofficial][S3, book]. It solves the problem of cache thrashing caused by the irregular memory access patterns of ray-tracing volume rendering, where neighboring rays often access distant memory locations [S1]. Unlike general optimization techniques, it specifically targets the Pentium III's cache replacement strategy by enforcing private cache blocks for volume data and using cubic interleaved addressing to ensure spatial locality [S1][S3, book].

## How it works
**Inputs and Outputs**
- Input: A volumetric dataset (typically decomposed into bricks), a transfer function, ray origins and directions, and the target image buffer.
- Output: A 2D rendered image with semi-transparent compositing.

**Data Structures and Layout**
The method relies on three key structural modifications:

1.  **Cache Partitioning**: The CPU cache is divided into four distinct, non-overlapping blocks:
    -   Volume bricks
    -   Transfer function tables
    -   Image blocks
    -   Temporary buffers [S2, unofficial][S3, book].
    Volume data is restricted to its private block to prevent eviction by competing structures like transfer function tables or image tiles [S2, unofficial][S3, book].

2.  **Bricked Volume Decomposition**: The volume is decomposed into bricks. Rays are processed in "flocks" (groups) that traverse the same brick simultaneously [S3, book]. This ensures that once a brick is loaded into the cache, it is used by all rays in the flock before being discarded [S3, book].

3.  **Cubic Interleaved Addressing**: To reduce cache thrashing within the volume block, the linear memory order of voxels is altered using a cubic interleaved address function [S1]. This function maps a 3D coordinate $(x, y, z)$ to a linear address such that a cube of $n^3$ voxels occupies $n \times n \times n$ cache locations, assuming $n$ is a power of two and $n^3$ is smaller than the cache size [S1]. This ensures that neighboring rays, which access spatially adjacent voxels, hit the same cache lines [S1].

**Algorithm Steps**
1.  **Initialize Cache Management**: Configure the memory allocator to reserve four separate cache blocks. Ensure volume data is allocated only in the volume brick block [S2, unofficial][S3, book].
2.  **Decompose Volume**: Split the volume dataset into bricks [S3, book].
3.  **Interleave Data**: Reorder the voxel data in memory using the cubic interleaved address function [S1].
4.  **Ray Flock Processing**:
    a. Group rays into flocks that share a common brick traversal path [S3, book].
    b. For each flock:
        i. Load the required brick data into the private volume cache block [S3, book].
        ii. Trace all rays in the flock through the brick [S3, book].
        iii. Discard the brick data from the cache when all rays in the flock have finished traversing it [S3, book].
5.  **Composite and Write**: Composite the ray contributions into the image block and write to the final image buffer [S2, unofficial][S3, book].

**Formulas**
The cubic interleaved address function maps 3D coordinates $(x, y, z)$ to a linear index. While the exact polynomial coefficients are not provided in the sources, the property is defined as:
$$ \text{Address}(x, y, z) \text{ maps an } n \times n \times n \text{ cube to } n \times n \times n \text{ cache locations} $$
where $n$ is a power of two and $n^3 < \text{Cache Size}$ [S1].

**Parameters**
-   **Interleaving Size ($n$)**: Must be a power of two. The volume of the interleaved cube ($n^3$) must be smaller than the L1 cache size [S1].
-   **Brick Size**: Not explicitly defined in sources, but must fit within the private cache block [S3, book].

**Edge Cases and Pitfalls**
-   **Memory Footprint**: The main memory footprint of the volume is four times higher than standard storage because no volume data may be stored in address spaces that map outside the volume's private cache slots [S3, book].
-   **Cache Thrashing**: If the interleaving size $n$ is not chosen correctly relative to the cache size, cache thrashing will persist [S1].
-   **Hardware Specificity**: The optimization is heavily dependent on the concrete details of the Pentium III cache replacement strategy [S1]. It may not be optimal for other architectures.

**Pseudocode**
```python
def ultravis_render(volume_data, transfer_function, rays, image_buffer):
    # Step 1: Cache Partitioning [S2, unofficial][S3, book]
    cache_blocks = {
        'volume_bricks': allocate_private_cache_block(),
        'transfer_functions': allocate_private_cache_block(),
        'image_blocks': allocate_private_cache_block(),
        'temporary_buffers': allocate_private_cache_block()
    }
    
    # Step 2: Decompose Volume into Bricks [S3, book]
    bricks = decompose_into_bricks(volume_data)
    
    # Step 3: Interleave Data [S1]
    interleaved_volume = apply_cubic_interleaved_addressing(volume_data)
    
    # Step 4: Process Ray Flocks [S3, book]
    for flock in group_rays_into_flocks(rays):
        # Identify bricks needed by this flock
        needed_bricks = get_bricks_for_flock(flock)
        
        for brick in needed_bricks:
            # Load brick into private cache block [S3, book]
            cache_blocks['volume_bricks'].load(brick)
            
            # Trace all rays in the flock through this brick [S3, book]
            for ray in flock:
                if ray_intersects_brick(ray, brick):
                    # Perform ray casting with interleaved access [S1]
                    contribution = cast_ray_through_brick(ray, brick, interleaved_volume, transfer_function)
                    accumulate_into_image(ray, contribution, image_buffer)
            
            # Discard brick when all rays have finished [S3, book]
            cache_blocks['volume_bricks'].discard(brick)
            
    return image_buffer
```

## Operating characteristics
-   **Time Complexity**: Not explicitly defined in sources. Performance is measured in frames per second (fps) [S1][S2, unofficial][S3, book].
-   **Memory Complexity**: The main memory footprint is four times higher than standard storage due to the private cache block requirement [S3, book].
-   **Measured Performance**:
    -   Renders a $256^3$ volume at 10 frames/s [S2, unofficial][S3, book].
    -   Renders a $256 \times 256 \times 110$ UNC MRI-head volume at 1.7 to 7.0 fps on a Pentium III 500MHz processor with a $256 \times 256$ image resolution [S1].
-   **Strengths**: Significantly reduces cache thrashing for semi-transparent volume rendering on Pentium III hardware [S1]. Enables high-quality rendering on single PCs without quality limitations [S1].
-   **Limitations**: Highly specific to Intel Pentium III cache architecture [S1]. Increases main memory footprint by 4x [S3, book]. May not be optimal for other CPUs or modern cache hierarchies.
-   **When to Use**: When rendering semi-transparent volumes on legacy Intel Pentium III hardware where cache thrashing is the primary bottleneck [S1].
-   **When Not to Use**: On modern hardware with different cache architectures, or when memory bandwidth is not the limiting factor.

## Background
-   **Origin**: Introduced by Knittel in 2000 [S1].
-   **History**: The method was developed to address the limited memory bandwidth and cache thrashing issues in software-based volume rendering on commodity hardware, specifically the Intel Pentium III [S1]. It was part of the UltraVis system, a comprehensive system for accelerated software-based volume rendering [S2, unofficial][S3, book].
-   **Usage**: Used in software-based volume rendering systems targeting high-performance CPU rendering in the early 2000s [S2, unofficial][S3, book].
