# UltraVis Cache Optimization

Also called: Knittel's Ray Casting, Optimized CPU Ray-Casting, Pentium III Optimized Ray Casting, UltraVis, UltraVis Cache Management, UltraVis System

## Overview
UltraVis is a software-based ray casting system for semi-transparent volume rendering that addresses cache thrashing on Intel Pentium III processors by combining bricked volume decomposition with a cubic interleaved memory layout [S1][S2, unofficial][S3, book]. It sets itself apart from standard ray casting by enforcing a private cache block for volume data, ensuring that voxel data is never swapped out by competing structures like transfer functions or image buffers [S2, unofficial][S3, book]. This approach trades a fourfold increase in main memory footprint for significantly higher cache hit ratios during traversal [S1][S3, book].

## How it works
**Inputs and Outputs**
- **Input:** A volumetric dataset (typically $256^3$ or similar dimensions), a transfer function, and camera parameters (view direction, image resolution).
- **Output:** A rendered 2D image (e.g., $256 \times 256$ pixels).

**Data Structures and Layout**
1.  **Bricked Volume Decomposition:** The volume is divided into cubic bricks. Rays are processed in "flocks" that traverse a single brick simultaneously [S3, book].
2.  **Cache Partitioning:** The CPU cache is divided into four distinct, non-overlapping blocks:
    -   Volume bricks
    -   Transfer function tables
    -   Image blocks
    -   Temporary buffers [S2, unofficial][S3, book]
3.  **Interleaved Memory Layout:** Voxel data is stored in main memory using a cubic interleaved address function. This alters the linear order of voxel values so that spatially adjacent voxels in 3D space map to cache locations that are also spatially close or identical, reducing conflict misses [S1].
    -   Let $n$ be the side length of the interleaving cube.
    -   $n$ must be a power of two.
    -   The volume of the interleaving cube $n^3$ must be smaller than the cache size [S1].
    -   The layout ensures that a cube of $n^3$ voxels occupies exactly $n \times n \times n$ cache locations [S1].
4.  **Private Cache Mapping:** Volume data is allocated such that it maps exclusively into the "volume bricks" cache block. This is achieved by placing voxel data only in the first quarter of memory pages, leaving the remaining three-quarters empty to prevent mapping conflicts [S1]. Consequently, volume data is never swapped out by transfer functions or image tiles [S2, unofficial][S3, book].

**Algorithm Steps**
1.  **Initialization:**
    -   Allocate main memory for the volume data with a footprint four times larger than the raw data size to accommodate the private cache slot constraints [S3, book].
    -   Partition the CPU cache into the four specified blocks [S2, unofficial][S3, book].
    -   Load transfer functions into the transfer function cache block [S3, book].
2.  **Brick Selection:**
    -   Determine which bricks intersect the view frustum or ray paths.
    -   Group rays into flocks that will traverse the same brick [S3, book].
3.  **Data Loading:**
    -   Bring the required brick data from main memory into the private volume cache block [S3, book].
    -   Because of the private block guarantee, this data remains resident until explicitly discarded [S3, book].
4.  **Ray Traversal (Flock Processing):**
    -   For each ray in the flock:
        -   Trace the ray through the loaded brick.
        -   Access voxel values using the interleaved address function.
        -   Perform shading and compositing (semi-transparent accumulation) [S1][S3, book].
    -   Since all rays in the flock share the same brick, the brick data is loaded once and reused by all rays in the flock [S3, book].
5.  **Cache Eviction:**
    -   Once all rays in the flock have finished traversing the current brick, discard the brick data from the cache block [S3, book].
    -   Load the next brick if necessary.
6.  **Image Composition:**
    -   Write the final pixel values to the image block in the cache [S3, book].

**Parameters**
-   **Interleaving Cube Size ($n$):** Must be a power of two. The volume $n^3$ must be smaller than the CPU cache size [S1].
-   **Brick Size:** Determined by the interleaving strategy and cache constraints [S3, book].
-   **Memory Footprint:** Four times the raw volume data size [S3, book].

**Edge Cases and Pitfalls**
-   **Cache Thrashing:** If the interleaving parameter $n$ is not chosen correctly (e.g., $n^3$ exceeds cache size or does not align with cache line sizes), cache thrashing will occur, negating performance gains [S1].
-   **Memory Pressure:** The requirement for a private cache block forces the main memory footprint to be four times larger than the raw data. This may cause out-of-core issues on systems with limited RAM [S3, book].
-   **Hardware Specificity:** The optimization relies on specific cache replacement strategies of the Intel Pentium III processor. Performance may degrade on architectures with different cache hierarchies or replacement policies [S1].

## Operating characteristics
-   **Time Complexity:** Not explicitly defined in terms of Big-O, but the method aims to reduce memory access latency, which is the primary bottleneck in ray casting [S1][S2, unofficial].
-   **Memory Complexity:** Main memory footprint is $4 \times$ the raw volume data size due to the private cache slot requirement [S3, book].
-   **Measured Performance:**
    -   Renders a $256^3$ volume at 10 frames/s [S2, unofficial][S3, book].
    -   Renders a $256 \times 256 \times 110$ UNC MRI-head volume at 1.7 to 7.0 fps on a Pentium III 500MHz processor with a $256 \times 256$ image resolution [S1].
-   **Strengths:**
    -   Significantly reduces cache thrashing through interleaved addressing [S1].
    -   Guarantees volume data residency in cache via private block allocation [S3, book].
    -   Efficient reuse of brick data across ray flocks [S3, book].
-   **Limitations:**
    -   High memory consumption (4x raw size) [S3, book].
    -   Hardware-specific (optimized for Pentium III cache behavior) [S1].
    -   Limited to software-based rendering on CPUs [S2, unofficial].
-   **When to Use:** When rendering semi-transparent volumes on older Intel Pentium III hardware where cache thrashing is the primary performance bottleneck and memory bandwidth is limited [S1].
-   **When Not to Use:** On modern hardware with larger caches, different cache architectures, or GPU-based rendering where hardware acceleration and different optimization strategies (e.g., texture caching) are more effective [S1][S2, unofficial].

## Background
UltraVis was introduced by Knittel in 2000 (cited as [Kni00] in [S1], though [S4, unofficial] lists "Optimized CPU ray-casting [Knoll et al. ’11]" which may refer to a later survey or related work; the primary source [S1] attributes it to Knittel [Kni00]) [S1][S4, unofficial]. It was designed specifically for the Intel Pentium III processor, addressing the limitations of standard ray casting memory access patterns on that hardware [S1]. The system was one of the early comprehensive software-based volume rendering systems to explicitly manage cache blocks to prevent thrashing [S2, unofficial][S3, book].
