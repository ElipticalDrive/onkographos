# DDA

Also called: Digital Differential Analyzer, DDA Algorithm, Three-Dimensional Digital Differential Analyzer, Three Dimensional Digital Differential Analyser, 3D Digital Differential Analyzer, 3D DDA method, 3DDA

## Overview

The Digital Differential Analyzer (DDA) is a grid traversal algorithm used in volume rendering and ray tracing to efficiently determine the sequence of voxels or grid cells intersected by a ray [S4][S5, unofficial]. It solves the problem of locating geometry in a dense uniform grid without performing expensive per-voxel intersection tests or suffering from the precision errors and missed voxels inherent in naive fixed-step ray marching [S5, unofficial]. It sets itself apart from its siblings by using incremental arithmetic to step through adjacent grid cells along the ray direction, often eliminating branching paths to optimize for GPU execution [S4]. Unlike [Amanatides-Woo Voxel Traversal](3132-amanatides-woo-voxel-traversal.md) which explicitly tracks parametric distances ($t$-values) and deltas, standard DDA implementations often utilize an Origin-Inverse Direction (OOD) formulation or a `sideDist` approach to drive integer-step traversal [S3][S4].

## How it works

**Inputs and Outputs:**
*   **Input:** A ray defined by origin $\mathbf{o}$ and direction $\mathbf{d}$ (typically normalized), and a uniform voxel grid [S5, unofficial].
*   **Output:** A sequence of voxel indices $(i, j, k)$ visited by the ray, or a boolean hit status if a specific cell is encountered [S4].

**Data Structures:**
The core state is typically held in a structure containing:
*   `pos`: Current voxel coordinates, usually `vec3<i32>` or `vec3<int>`. Initialized to $\lfloor \mathbf{o} \rfloor$ [S4][S5, unofficial].
*   `step_dir`: Direction of movement per axis, `vec3<i32>`, derived from $\text{sign}(\mathbf{d})$ [S4].
*   `delta_dist`: Distance along the ray to cross one grid cell, `vec3<f32>`. Calculated as $|\mathbf{d}^{-1}|$ (absolute value of inverse direction) [S4].
*   `side_dist`: Distance to the next grid boundary along the ray, `vec3<f32>` [S4].

**Initialization:**
1.  Compute inverse direction $\mathbf{d}^{-1} = 1/\mathbf{d}$. Handle zero components by setting inverse to infinity or handling separately [S14].
2.  Set current position $\mathbf{pos} = \lfloor \mathbf{o} \rfloor$ [S4][S5, unofficial].
3.  Set step direction $\mathbf{step\_dir} = \text{sign}(\mathbf{d})$ [S4].
4.  Set delta distance $\mathbf{delta\_dist} = |\mathbf{d}^{-1}|$ [S4].
5.  Calculate initial side distances. A common robust formulation (avoiding explicit ceiling/floor logic for boundaries) is:
    $$ \mathbf{side\_dist} = (\text{sign}(\mathbf{d}) \cdot (\lfloor \mathbf{o} \rfloor - \mathbf{o}) + (\text{sign}(\mathbf{d}) \cdot 0.5 + 0.5)) \cdot \mathbf{delta\_dist} $$
    *Note: The exact formula varies by implementation. A simpler geometric derivation for the first boundary is:*
    If $d_x > 0$: $t_{next} = (\lceil o_x \rceil - o_x) / d_x$ [S10, unofficial].
    If $d_x < 0$: $t_{next} = (o_x - \lfloor o_x \rfloor) / |d_x|$ (distance to lower bound) [S5, unofficial][S8].
    The `side_dist` represents the parametric distance $t$ to the next crossing [S4].

**Stepping Loop:**
1.  Determine which axis to step by finding the minimum `side_dist` [S5, unofficial].
2.  Update `side_dist` for the stepped axis by adding `delta_dist` [S5, unofficial].
3.  Update `pos` for the stepped axis by adding `step_dir` [S5, unofficial].
4.  Repeat until the ray exits the grid or a hit is found [S5, unofficial].

**Pseudocode:**
```python
def init_dda(ray_origin, ray_direction):
    # 1. Inverse direction
    inv_dir = 1.0 / ray_direction
    
    # 2. Handle zero direction components to avoid division by zero
    # If a component is 0, the ray never crosses a grid line in that axis.
    inv_dir = where(ray_direction == 0.0, float('inf'), inv_dir)
    
    # 3. Current voxel position
    pos = floor(ray_origin)
    
    # 4. Step direction
    step_dir = sign(ray_direction)
    
    # 5. Delta distance (distance along ray to cross 1 unit in grid)
    delta_dist = abs(inv_dir)
    
    # 6. Side distance (distance to next grid boundary)
    # Formula derived from evidence [S5, unofficial]
    side_dist = (step_dir * (vec3<f32>(pos) - ray_origin) + (step_dir * 0.5 + 0.5)) * delta_dist
    
    # Guard against zero-length initial segments (rays starting exactly on boundaries)
    side_dist = where(side_dist <= 0.0, delta_dist, side_dist)
    
    return {
        'pos': pos,
        'step_dir': step_dir,
        'delta_dist': delta_dist,
        'side_dist': side_dist
    }

def step_dda(state):
    # Find the axis with the minimum side_dist
    # Using a mask to avoid branching
    # mask[i] is true if side_dist[i] <= side_dist[j] and side_dist[i] <= side_dist[k]
    # Cyclic comparison: x vs y,z; y vs z,x; z vs x,y
    mask = (state['side_dist'].xyz <= min(state['side_dist'].yzx, state['side_dist'].zxy))
    
    # Update side_dist for the stepped axis(es)
    # If multiple axes are equal (rare, degenerate), all are stepped
    state['side_dist'] += mask * state['delta_dist']
    
    # Update position for the stepped axis(es)
    state['pos'] += mask * state['step_dir']
    
    # Return the normal of the face crossed (optional, for shading)
    # Normal is opposite to step_dir for the stepped axis
    normal = mask * -state['step_dir']
    
    return state, normal
```

**Parameters:**
*   `ray_origin`: `vec3<f32>` [S4].
*   `ray_direction`: `vec3<f32>`, usually normalized [S5, unofficial].
*   `grid_size`: `vec3<i32>` representing the dimensions of the voxel array [S4].

**Edge Cases and Pitfalls:**
*   **Zero Direction Components:** If a ray direction component is zero, the ray is parallel to the grid lines in that axis. The inverse direction is infinite. The algorithm must handle this to avoid NaNs or infinite loops. A common fix is to set `delta_dist` to infinity for that axis, ensuring it is never selected as the minimum `side_dist` [S14].
*   **Rays on Boundaries:** If the ray origin lies exactly on a grid line, the initial `side_dist` calculation might yield 0. This can cause the ray to "stutter" or process the same cell twice. Guarding against `dt > 0` or adding a small epsilon can prevent this [S17, unofficial].
*   **GPU Branching:** Standard implementations using `if` statements for determining the next axis can be inefficient on GPUs due to divergence. The mask-based approach described above eliminates branching [S4].
*   **Precision:** Floating-point precision errors can accumulate over long traversals. Using integer arithmetic for voxel indices (as done in `pos`) mitigates this, while `side_dist` remains floating-point [S3].

## Subtopics

### [TRFRay3 (DDA Ray Representation)](2104-trfray3-dda-ray-representation.md)
TRFRay3 is a data structure and traversal algorithm for performing Digital Differential Analyzer (DDA) ray marching through a voxel grid. It solves the problem of efficiently determining which voxels a ray intersects by stepping through adjacent grid cells along a ray direction. It sets itself apart from its siblings by encapsulating the ray state (origin, direction, inverse direction, and signs) into a contiguous, SIMD-friendly structure that precomputes division-heavy terms to avoid runtime division. Unlike [Amanatides-Woo Voxel Traversal](3132-amanatides-woo-voxel-traversal.md) which explicitly tracks `tMax` and `tDelta` per axis, TRFRay3 often utilizes an Origin-Inverse Direction (OOD) formulation or a `sideDist` approach to drive the integer-step traversal.

### [Differentiable DDA Loop](2474-differentiable-dda-loop.md)
A differentiable Digital Differential Analyzer (DDA) loop that traverses a grid along a ray, invoking a callback function for each visited cell. It extends standard DDA traversal by maintaining differentiable state variables, allowing gradients to flow back through the ray marching steps [G].

### [Amanatides-Woo Voxel Traversal](3132-amanatides-woo-voxel-traversal.md)
Amanatides-Woo is a fast, branch-minimal algorithm for traversing a uniform 3D voxel grid along a ray, visiting only the voxels intersected by the ray in $O(n_x + n_y + n_z)$ time. It solves the problem of efficiently locating geometry in a dense grid without performing expensive per-voxel intersection tests or suffering from the precision errors and missed voxels inherent in naive fixed-step ray marching. It sets itself apart from its siblings by using floating-point parametric distances ($t$-values) to determine the next voxel boundary crossing based on the minimum time to cross any axis boundary, guaranteeing that the ray stops and tests a voxel index at exactly one of the x, y, or z dividing planes.

### [3D Bresenham Voxel Traversal](3951-3d-bresenham-voxel-traversal.md)
3D Bresenham Voxel Traversal is a discrete line algorithm used to determine the sequence of integer voxel coordinates intersected by a line segment in a 3D grid. It rasterizes a line between two integer coordinates by iterating along the dominant axis and updating the other two axes based on accumulated error terms. It differs from its parent [DDA](2323-dda.md) and siblings like [Amanatides-Woo Voxel Traversal](3132-amanatides-woo-voxel-traversal.md) by operating entirely in integer arithmetic rather than floating-point plane intersections, making it computationally lighter but topologically distinct: it does not consider every block the ray passes through, skipping those where the ray does not get close enough to the block center.

### [Amanatides–Woo grid traversal](5003-amanatides-woo-grid-traversal.md)
This method traverses the grid cells intersected by a line segment defined by two points, calling a visitor function for each cell in traversal order. It is a 2D floating-point implementation designed for uniform grid traversal.

### [Hierarchical DDA Traversal](17026-hierarchical-dda-traversal.md)
Hierarchical DDA Traversal extends standard DDA [DDA](2323-dda.md) to efficiently traverse sparse, multi-resolution volume structures by adapting step sizes to the current tree level . Unlike sibling methods that step voxel-by-voxel [Amanatides-Woo Voxel Traversal](3132-amanatides-woo-voxel-traversal.md) or use fixed-resolution grids [3D Bresenham Voxel Traversal](3951-3d-bresenham-voxel-traversal.md), this family skips empty internal nodes or adjusts mip-levels dynamically to balance speed and precision .

### Safe Inverse for DDA
A safe inverse function for ray direction components to handle near-axis-aligned rays in DDA, preventing division by zero or infinity while maintaining correct stepping behavior [S19, unofficial]. If `abs(x) < 1e-8`, return `select(-1e20, 1e20, x >= 0.0)`. Otherwise, return `1.0 / x` [S19, unofficial].

### Multi-Ray Field of View Casting
Sweeps a full field of view by casting one ray per screen column, evenly distributed across the angular range [S20, unofficial]. Iterate $i$ from 0 to `rayCount`-1. Calculate the angle for each ray using the formula $\theta_i = \text{facing} - \text{FOV}/2 + i \cdot (\text{FOV}/(\text{rayCount} - 1))$, where facing is the base angle in radians, FOV is the field of view in radians, and rayCount is the total number of rays [S20, unofficial]. Cast each ray using the DDA algorithm with the calculated angle and store the result (angle, distance, side, hit coordinates) [S20, unofficial].

### Forward Stepping Enforcement
A macro definition, likely used to enforce forward stepping behavior in the DDA/HDDA implementations [S14].

### LoD-aware Ray Traversal with Cone Aperture
A rendering procedure that associates each ray with a cone aperture covering the pixel footprint to determine the appropriate Level-of-Detail (LoD) level during traversal, switching to coarser LoDs at voxel boundaries for efficiency [S21, unofficial]. Loop while $t < t_{\text{max}}$: Calculate LoD level using formula: $\text{level} = \lfloor \log_2(\tan(0.5 \cdot \theta) \cdot t / s) \rfloor$, where $s$ is base voxel size and $\theta$ is cone aperture [S21, unofficial]. Switch to a coarser LoD only at the boundary of the coarser voxels for efficiency [S21, unofficial]. Continuous LoD blending is possible but more costly than boundary-only switching [S21, unofficial].

### DDA-Octree Traversal
An octree traversal algorithm for ray tracing that uses Digital Differential Analysis (DDA) principles, cited as an alternative to recursive bintree traversal (ARVO) [S22, unofficial]. Compared against recursive bintree traversal (called ARVO by Sung). Sung's initial implementation was found to be not optimal by Erik Jansen, leading to a better ARVO implementation published in Graphics Gems [S22, unofficial]. Introduced by Kelvin Sung in the paper 'A DDA Octree Traversal Algorithm for Ray Tracing', published in Eurographics'91 Proceedings, North Holland-Elsevier, ISBN 0444 89096 3, pages 73-85 [S22, unofficial].

### Oversampled DDA
Oversample the DDA by a factor of two in each dimension. Trace and average over four rays per detector pixel to approximate a finite beam extent [S1, unofficial]. On a GTX 970, DDA 2x takes 15.2 ms with 143 GB/s memory access rate [S1, unofficial]. On a GTX 1080, DDA 2x takes 6.74 ms with 323 GB/s memory access rate [S1, unofficial]. Resulting projection residuals become comparable to non-oversampled GJPspl, but GJPspl further shows a considerable reduction of high frequency artifacts [S1, unofficial].

## Operating characteristics

**Time and Memory Complexity:**
*   **Time:** $O(n)$ where $n$ is the number of voxels intersected by the ray. This is optimal as every intersected voxel must be visited [S11, unofficial][S13, unofficial].
*   **Memory:** $O(1)$ auxiliary memory for the traversal state (position, distances, directions) [S4].

**Measured Performance:**
*   The DDA method is well-suited for hardware implementation and can be pipelined for maximized throughput [S3].
*   On GPUs, branchless implementations (using masks) significantly outperform branching versions by avoiding instruction divergence [S4].
*   Compared to naive ray marching (fixed small steps), DDA reduces the number of iterations from thousands to the number of intersected voxels, resulting in significantly fewer computations [S6, unofficial].

**Strengths and Limitations:**
*   **Strengths:** Fast, branch-minimal (with mask optimization), simple to implement, works well on uniform grids [S4][S13, unofficial].
*   **Limitations:** Performance degrades on sparse grids where many empty voxels are visited. Not suitable for non-uniform grids without modification (e.g., [Hierarchical DDA Traversal](17026-hierarchical-dda-traversal.md)). Precision issues can arise with very long rays or very small voxels if floating-point precision is insufficient [G].

**When to Use:**
*   Use for uniform voxel grids in volume rendering or ray tracing where performance is critical and the grid is dense enough that the overhead of hierarchical structures is not justified [S5, unofficial].
*   Use when GPU efficiency is a priority and branchless code is required [S4].

**When Not to Use:**
*   Do not use for sparse grids; use [Hierarchical DDA Traversal](17026-hierarchical-dda-traversal.md) or [Voxel Occupancy Mask](5242-voxel-occupancy-mask.md) instead [S13, unofficial].
*   Do not use if the grid is non-uniform; use [Amanatides-Woo Voxel Traversal](3132-amanatides-woo-voxel-traversal.md) with adaptive step sizes or a different acceleration structure [S13, unofficial].

## Background

The Digital Differential Analyzer (DDA) algorithm originated as a hardware or software method for interpolation of variables over an interval between start and end points, used for rasterization of lines, triangles, and polygons [S3]. In the context of 3D grid traversal, it was adapted to efficiently determine which voxels a ray intersects. The specific branchless GPU-optimized version is often cited from work by Xiao et al., which eliminates branching paths for faster GPU execution [S4]. It is an acceleration technique for grid traversal in image-order rendering [S13, unofficial].
