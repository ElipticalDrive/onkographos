# Voxel Polygon Rendering


## Overview
Voxel Polygon Rendering is a hybrid rendering technique that fills the screen with vertical bars representing heights from a voxel map, effectively projecting a 2D area of the map onto the screen as a flat landscape [S1, unofficial]. It solves the problem of rendering high-detail terrain at constant speed by avoiding traditional 6DOF polygon operations such as rotation matrix calculations and clipping [S1, unofficial]. Unlike its sibling [Voxel Raycasting with DDA and Vertical Stripe Rendering](2206-voxel-raycasting-with-dda-and-vertical-stripe-rendering.md), which casts rays per screen column to find the first occupied voxel, Voxel Polygon Rendering maps screen pixels directly to map locations and draws spans from close to far, using an s-buffer (vertical c-buffer) to handle floating bars and prevent overdraw [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A voxel map (array of height and color per location), screen resolution, camera position, and camera yaw (y-axis rotation).
- Output: A rendered image with vertical bars representing terrain height.

**Data Structures:**
- `VoxelMap`: A 2D array where each cell stores `height` (float/int) and `color` (RGB).
- `ColumnHeights`: An array of size `screen_width`, storing the current drawn height for each screen column to enable clipping.
- `S-Buffer` (Vertical C-Buffer): A data structure managing floating voxel bars that do not start at the bottom of the screen. It stores the top and bottom height of each bar per column to handle occlusion correctly [S1, unofficial].

**Steps:**
1. **Map Pixels to Voxel Space:** For each pixel on the screen, determine its corresponding location on the voxel map based on the camera's y-axis rotation and position. Calculate the distance of the pixel from the camera to apply perspective correction, ensuring distant "mountains" appear smaller [S1, unofficial].
2. **Retrieve Voxel Data:** Fetch the height and color data from the voxel map. To reduce blockiness, apply bilinear filtering by retrieving four adjacent voxels (texels) [S1, unofficial].
3. **Calculate Span Height and Color:**
   - Compute the weighted average of the heights of the four fetched texels to determine the height of the single one-pixel wide span [S1, unofficial].
   - Compute the weighted average of the colors of the four fetched texels to determine the span's color [S1, unofficial].
4. **Clip Against Column Height:** Compare the calculated span height against the current height stored in `ColumnHeights` for that column. If the span is behind the existing bar, clip it. If it is in front, update `ColumnHeights` with the new height [S1, unofficial].
5. **Draw Span:** Draw the vertical bar (span) for the pixel. If the bar is floating (not starting at the bottom), use the `S-Buffer` to manage its visibility and occlusion against other floating bars [S1, unofficial].
6. **Repeat for All Columns:** Process all screen columns from the bottom of the screen up to the horizon (approximately halfway up the screen) [S1, unofficial].
7. **Fill Backdrop:** Fill the screen space above the horizon with a backdrop image [S1, unofficial].

**Formulas:**
- **Bilinear Height Interpolation:**
  $$ H_{span} = \frac{H_1 + H_2 + H_3 + H_4}{4} $$
  Where $H_1, H_2, H_3, H_4$ are the heights of the four adjacent voxels [S1, unofficial].
- **Bilinear Color Interpolation:**
  $$ C_{span} = \frac{C_1 + C_2 + C_3 + C_4}{4} $$
  Where $C_1, C_2, C_3, C_4$ are the colors of the four adjacent voxels [S1, unofficial].

**Parameters:**
- **Rotation Constraint:** The scene can only be rotated around the y-axis. Looking up/down (x-axis) is limited to about 10 degrees; looking down by 45 degrees wastes the picture because voxel bars must be perfectly vertical [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Flat Floor Performance:** Worst-case performance occurs on a completely flat floor. Every column of the screen becomes one higher every time a new line is processed. For the single pixel drawn, significant work is done: comparing to current column height, clipping, drawing, and updating column height. This is likely more expensive than drawing a single perspective-correct texture map [S1, unofficial].
- **Floating Bars:** The usual voxel algorithm assumes bars start at the bottom screen line. Floating bars (e.g., bridges, ceilings) require an s-buffer (vertical c-buffer) to handle correctly, as they have both a top and bottom side [S1, unofficial].
- **Blockiness:** Without bilinear filtering, voxels look blocky. Small details tend to flicker when the camera moves [S1, unofficial].

## Subtopics

### [Triangle Strip Voxel Projection](15933-triangle-strip-voxel-projection.md)
A hardware-accelerated rendering method for voxel landscapes that replaces software span rendering with triangle strips. It projects voxels onto the screen in columns and constructs geometry based on the visibility of adjacent columns to minimize polygon count and utilize hardware interpolation. Unlike software span rendering, this method buffers column projections to construct triangle strips, reducing draw calls and leveraging hardware interpolation for texture coordinates, lightmap colors, and heights.

## Operating characteristics
- **Time Complexity:** Virtually constant speed regardless of scene detail, as it processes each screen pixel once. However, worst-case performance occurs on a completely flat floor, where every column's height is updated for every line, leading to significant clipping and drawing overhead per pixel [S1, unofficial].
- **Memory Complexity:** Requires a large voxel map. Memory usage can be mitigated by tiling pre-built tiles of voxels [S1, unofficial].
- **Strengths:** Constant rendering speed; no 6DOF rotation matrix calculations or clipping required; allows for high detail; bilinear filtering reduces blockiness; supports floating structures via s-buffer [S1, unofficial].
- **Limitations:** Limited to y-axis rotation (approx. 10 degrees up/down); cannot handle significant x-axis rotation; blockiness without filtering; flickering of small details; worst-case performance on flat terrain [S1, unofficial].
- **When to Use:** Rendering high-detail terrain at constant speed where y-axis rotation is sufficient.
- **When Not to Use:** When full 6DOF rotation is required; when performance on flat terrain is critical; when memory is severely constrained without tiling support.

## Background
Voxel Polygon Rendering was introduced by Jacco Bikker (a.k.a. "THE PHANTOM") in 1999 on Flipcode [S1, unofficial]. It was developed as an alternative to traditional 6DOF polygon engines, aiming to provide high-detail graphics with constant speed. The technique was considered for inclusion in the "Focus" engine [S1, unofficial].
