# Voxel Polygon Rendering


## Overview
Voxel Polygon Rendering is a hybrid rendering technique that fills the screen with vertical bars representing heights from a voxel map, effectively projecting a 2D heightfield onto the screen as a flat landscape [S1, unofficial]. It solves the problem of rendering high-detail terrain at constant speed by avoiding traditional 6DOF polygon operations like rotation matrices and clipping [S1, unofficial]. Unlike its siblings, which rely on pure software span rendering or hardware acceleration via triangle strips, Voxel Polygon Rendering uses a specific "vertical c-buffer" (s-buffer) to handle floating bars and bilinear filtering to smooth blockiness, while strictly limiting camera rotation to the Y-axis [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A voxel map (2D array of height and color values), camera position, and Y-axis rotation angle.
*   **Output:** A rasterized screen image with vertical bars representing terrain height.

**Data Structures:**
1.  **Voxel Map:** A 2D array where each cell contains a `height` (float/int) and `color` (RGB).
2.  **Column Height Buffer (C-Buffer):** An array of size $W$ (screen width), storing the current drawn height for each screen column. Initialized to the bottom of the screen (or 0, depending on coordinate system).
3.  **Floating Bar Buffer (S-Buffer):** A structure or array used to store "floating" voxel bars that do not start at the bottom of the screen, allowing them to be clipped against existing geometry [S1, unofficial].

**Steps:**

1.  **Map Screen to Voxel Space:**
    For each pixel column $x$ on the screen, determine the corresponding location on the voxel map based on camera position and rotation. Calculate the distance $d$ of the pixel from the camera [S1, unofficial].

2.  **Fetch Voxels (Bilinear Filtering):**
    To reduce blockiness, retrieve four adjacent voxels (texels) from the voxel map surrounding the calculated map location [S1, unofficial].
    *   Let the four voxels be $V_{00}, V_{01}, V_{10}, V_{11}$ with heights $h_{ij}$ and colors $c_{ij}$.
    *   Calculate the weighted average height $H$ for the span:
        $$ H = \frac{\sum w_{ij} h_{ij}}{\sum w_{ij}} $$
    *   Calculate the weighted average color $C$:
        $$ C = \frac{\sum w_{ij} c_{ij}}{\sum w_{ij}} $$
    *   Where $w_{ij}$ are interpolation weights based on the sub-pixel offset [S1, unofficial].

3.  **Perspective Correction:**
    Adjust the calculated height $H$ based on the distance $d$ to ensure distant "mountains" appear smaller and perspective is maintained [S1, unofficial].

4.  **Render Close to Far:**
    Iterate through screen rows from the bottom (closest) to the horizon (approximately halfway up the screen) [S1, unofficial].
    *   For each row $y$ and column $x$:
        *   Determine the voxel height $H_{voxel}$ at this screen position.
        *   Compare $H_{voxel}$ with the current height stored in the Column Height Buffer $H_{col}[x]$.
        *   If $H_{voxel} > H_{col}[x]$:
            *   Draw the vertical bar segment from $H_{col}[x]$ to $H_{voxel}$ using color $C$.
            *   Update $H_{col}[x] = H_{voxel}$.
        *   If $H_{voxel} \le H_{col}[x]$:
            *   The bar is occluded by a closer bar; do not draw.

5.  **Handle Floating Bars (S-Buffer):**
    For voxels that represent floating structures (e.g., bridges, ceilings), store a `depth` value in addition to height [S1, unofficial].
    *   Use a vertical c-buffer (s-buffer) to manage these bars.
    *   Clip floating bars against the height buffer to prevent overdraw, similar to solid terrain but allowing gaps at the bottom [S1, unofficial].

6.  **Render Horizon and Backdrop:**
    Fill the screen space above the horizon with a backdrop color or texture [S1, unofficial].

7.  **Voxel Polygons (Optional Detail):**
    To vary detail locally, use "voxel polygons" (horizontally oriented polygons) to define hills or structures.
    *   Add the local height of the polygon to the base voxel height.
    *   Interpolate polygon heights fluently (similar to Gouraud shading) to create smooth shapes like round hills using few polygons [S1, unofficial].

**Parameters:**
*   **Rotation Constraint:** The scene can only be rotated around the Y-axis. X-axis rotation (looking up/down) is limited to approximately 10 degrees [S1, unofficial]. Looking down by 45 degrees wastes the picture because voxel bars must be perfectly vertical [S1, unofficial].
*   **Bilinear Filtering:** Always enabled to overcome blockiness [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Flat Floor Performance:** Worst-case performance occurs on a completely flat floor. Every column of the screen becomes one height unit higher every time a new line is processed. For each single pixel drawn, significant work is done: comparing to current column height, clipping, drawing, and updating column height. This is likely more expensive than drawing a single perspective-correct texture map [S1, unofficial].
*   **Flickering:** Small details tend to flicker when the camera moves, though bilinear filtering reduces this [S1, unofficial].
*   **Vertical Bars:** The technique requires voxel bars to be perfectly vertical. Any significant X-axis rotation breaks the rendering model [S1, unofficial].

## Subtopics

### [Triangle Strip Voxel Projection](15933-triangle-strip-voxel-projection.md)
A hardware-accelerated rendering method for voxel landscapes that replaces software span rendering with triangle strips. It projects voxels onto the screen in columns and constructs geometry based on the visibility of adjacent columns to minimize polygon count and utilize hardware interpolation. Unlike Voxel Polygon Rendering, which uses a vertical c-buffer for software span rendering, this method buffers column projections to construct triangle strips, reducing draw calls and leveraging hardware interpolation for texture coordinates, lightmap colors, and heights.

## Operating characteristics
*   **Time Complexity:** Virtually constant speed regardless of scene detail, as it processes each screen pixel/column once [S1, unofficial]. However, worst-case performance (flat floor) involves significant per-pixel overhead for clipping and updating the column height buffer [S1, unofficial].
*   **Memory Complexity:** High memory usage for the voxel map. "Huge map problem" requires tiling or voxel polygons to manage memory efficiently [S1, unofficial].
*   **Strengths:** Constant rendering speed; no 6DOF rotation matrix calculations or clipping required; high detail possible; smooth terrain via bilinear filtering and polygon interpolation [S1, unofficial].
*   **Limitations:** Limited to Y-axis rotation (approx. ±10 degrees); blocky appearance without filtering; flickering details; high memory usage for large maps; vertical bars only [S1, unofficial].
*   **When to Use:** Real-time terrain rendering where Y-axis rotation is sufficient and high detail is needed without complex 3D geometry.
*   **When Not to Use:** Scenes requiring full 6DOF camera movement, significant up/down viewing angles, or where memory is severely constrained.

## Background
Voxel Polygon Rendering was introduced by Jacco Bikker (a.k.a. "THE PHANTOM") in 1999 on Flipcode [S1, unofficial]. It was developed as part of the "Focus engine" to allow graphics with much more detail than any 3D accelerator could handle at the time, with a great natural look [S1, unofficial]. The technique was influenced by earlier voxel engines like "Comanche Total Overkill," which required 4MB of memory for its voxel map [S1, unofficial]. The method combines traditional voxel heightfield rendering with polygon-based detail (voxel polygons) and bilinear filtering to smooth the appearance.
