# CUDA Execution Configuration Optimization

Also called: Block Size and Grid Size Tuning, GPU Occupancy Optimization

## Overview
CUDA Execution Configuration Optimization is the process of selecting thread block dimensions, grid dimensions, and shared memory allocation to maximize GPU occupancy and rendering performance for volume raycasting [S1, S2, unofficial]. It addresses the problem that performance varies significantly (up to 265%) based on block size, with the optimal configuration depending on the specific dataset and algorithmic optimizations like Early Ray Termination (ERT) [S2, unofficial]. It differs from general occupancy tuning by explicitly accounting for the high branch divergence and load imbalance inherent in ray-grid traversal, where threads within a warp often execute different code paths or terminate at different times [S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Volume dataset dimensions, raycasting algorithm characteristics (e.g., presence of ERT, empty-space skipping), target GPU architecture.
*   **Output:** Optimal `blockDim.x`, `blockDim.y`, `blockDim.z` (total threads per block), and `gridDim.x`, `gridDim.y` (total blocks).

**Data Structures:**
The execution configuration is defined by three runtime variables passed to the CUDA kernel launch:
1.  `blockDim`: A `dim3` structure specifying threads per block.
2.  `gridDim`: A `dim3` structure specifying blocks per grid.
3.  `sharedMemSize`: Bytes of shared memory per block (if used).

**Occupancy Definition:**
Occupancy is defined on a per-multiprocessor basis as:
$$ \text{Occupancy} = \frac{\text{Number of active warps}}{\text{Maximum number of warps allowed per multiprocessor}} $$
Maximizing occupancy aims to hide latency and increase utilization [S1, unofficial].

**Parameters and Benchmarked Sizes:**
*   **Minimum Threads:** CUDA thread blocks require a minimum of 32 threads to saturate computational throughput in a standard SIMT model [S2, unofficial].
*   **Exclusion Threshold:** Configurations with fewer than 4 threads per block were excluded from benchmarks because a warp (32 threads) must be scheduled across at least four clock cycles, guaranteeing under-utilization for very small blocks [S2, unofficial].
*   **Benchmarked Block Sizes:** Common sizes tested include $4\times4$, $4\times8$, $4\times16$, $4\ttimes32$, $8\times8$, $8\times16$, $8\times32$, and $16\times16$ [S1, unofficial].
*   **Optimal Size:** Empirically, the sweet spot is 16 or 32 threads per block, depending on memory ordering and whether ERT is enabled [S2, unofficial].

**Numbered Steps:**
1.  **Map Pixels to Threads:** Map a single pixel to a single thread in the raycasting algorithm [S1, unofficial].
2.  **Estimate Occupancy:** Use the CUDA occupancy calculator to determine suitable performance configurations based on register usage and shared memory requirements [S1, unofficial].
3.  **Define Search Space:** Select a range of block sizes. Exclude sizes with $<4$ threads per block [S2, unofficial].
4.  **Benchmark:** Run the kernel with different block sizes on the target hardware.
5.  **Analyze Trade-offs:** Evaluate performance against L2 cache misses and branch divergence. Note that L2 cache misses rise uniformly with total threads, while smaller blocks may have fewer misses but higher divergence overhead [S2, unofficial].
6.  **Select Optimal:** Choose the block size that yields the highest FPS, acknowledging that the optimal size for one problem may not be optimal for another on the same platform [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Load Imbalance:** Larger thread blocks may exhibit greater load imbalance because the variation in ray lengths tends to increase with block size [S2, unofficial].
*   **Branch Divergence:** Threads in a warp (32 threads) are executed in subsets of eight. If threads do not share a common instruction (e.g., due to conditionals like ERT or empty-space skipping), they diverge and execute serially [S2, unofficial]. This is prevalent in raycasting [S2, unofficial].
*   **Cache vs. Throughput Trade-off:** Small thread blocks may display the fewest L2 cache misses but perform poorly due to insufficient warp saturation. Conversely, optimal block sizes do not necessarily show the most L2 cache misses. The best performance is a trade-off between saturating a warp and maintaining good cache utilization [S2, unofficial].
*   **Problem Dependency:** The optimal block size for one problem is not the same as for another on the same platform [S2, unofficial].

## Operating characteristics
**Time and Memory Complexity:**
The optimization process itself is an offline or startup-time benchmarking step. The runtime complexity of the raycasting kernel is $O(N)$ where $N$ is the number of pixels, but the constant factor is heavily influenced by the execution configuration.

**Measured Performance:**
Tests on an NVIDIA GTX280 GPU with an Intel Core 2 Quad 2.33GHz processor and 4GB memory [S1, unofficial]:
*   **Bucky (32x32x32):** 61 FPS with block sizes 4x16, 4x32, 8x8, 8x16, 8x32. 31 FPS with 4x4. 59 FPS with 4x8. 60 FPS with 16x16.
*   **Engine (256x256x256):** 31 FPS with block sizes 4x32, 8x8, 8x16, 8x32. 16 FPS with 4x4. 21 FPS with 4x8, 4x16, 16x16.
*   **Porsche (559x1024x347):** 21 FPS with block sizes 4x16, 4x32, 8x8, 8x16, 8x32. 12 FPS with 4x4. 18 FPS with 4x8. 20 FPS with 16x16 [S1, unofficial].

**Scaling:**
Performance varies by as much as 265% depending on thread block size [S2, unofficial].

**Strengths and Limitations:**
*   **Strengths:** Can significantly improve FPS by aligning thread execution with hardware warps and cache hierarchies.
*   **Limitations:** No universal optimal block size exists; it depends on the dataset, transfer function, and algorithmic optimizations (like ERT) [S2, unofficial]. Larger blocks increase load imbalance [S2, unofficial].

**When to Use:**
Use when tuning a new raycasting kernel for a specific GPU architecture and dataset. It is essential when branch divergence is high or when memory access patterns are irregular.

**When Not to Use:**
Not necessary for simple, uniform kernels with minimal branching where occupancy is already high and performance is memory-bandwidth bound in a predictable way.

## Background
**Origin:**
The concept is rooted in CUDA programming best practices, specifically the recommendation to experiment with execution configurations due to the complex interaction between the CUDA runtime, warp scheduler, and algorithmic characteristics [S2, unofficial].

**History and Development:**
Early CUDA programming guides recommended experimentation for execution configuration [S2, unofficial]. Specific benchmarks for volume rendering demonstrated that block sizes of 16 or 32 threads were often optimal, challenging the assumption that larger blocks (closer to warp size) are always better due to divergence [S2, unofficial]. The use of the CUDA occupancy calculator became a standard first step in this optimization process [S1, unofficial].

**Where it is used:**
High-performance volume rendering, particularly raycasting algorithms that employ empty-space skipping and early ray termination, which introduce significant branch divergence [S2, unofficial].
