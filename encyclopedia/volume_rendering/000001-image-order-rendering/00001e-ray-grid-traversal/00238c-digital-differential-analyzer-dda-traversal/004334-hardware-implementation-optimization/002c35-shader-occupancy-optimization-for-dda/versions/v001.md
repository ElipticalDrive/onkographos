# Shader Occupancy Optimization for DDA

Also called: DDA Shader Register Optimization, Optimizing 2-Level DDA Shader, Shader Occupancy Optimization

## Overview
This method optimizes the Digital Differential Analyzer (DDA) traversal shader to increase GPU occupancy by reducing register allocation and minimizing state carried across loops [S1, unofficial]. It addresses the performance degradation caused by high register pressure in complex nested-loop traversal logic, which limits the number of concurrent warps and leads to memory stalls [S1, unofficial]. Unlike [Parallel 3D-DDA](6247-parallel-3d-dda.md), which focuses on algorithmic parallelism, or [GPU Screen-Space Ray Tracing via DDA](10121-gpu-screen-space-ray-tracing-via-dda.md), which focuses on screen-space coherence, this method focuses purely on compiler-friendly variable management and deduplication within the shader code to maximize hardware utilization [S1, unofficial].

## How it works
The optimization targets the "2-level DDA" shader structure, where ray traversal involves nested loops for brick-level and voxel-level traversal. The primary cause of low occupancy is the excessive number of registers required to store intermediate state (such as `min_cell`, `max_cell`, and `tdelta`) across these loops [S1, unofficial].

### Inputs and Outputs
*   **Input:** The unoptimized DDA shader source code, specifically the traversal kernel containing nested loops for brick and voxel iteration.
*   **Output:** An optimized shader source code with reduced register footprint and higher occupancy metrics.

### Data Structures
The method modifies the local variable layout within the shader.
*   **`local_cell`**: A single `int3` variable replaces the pair `min_cell` and `max_cell`. This variable tracks the current voxel coordinate within the current brick.
*   **`VX_BRICK_EXT`**: A constant defining the brick dimensions (e.g., $8 \times 8 \times 8$).
*   **`voxel_mask`**: An array of `uint` values used for sparse voxel access.

### Steps
1.  **Variable Consolidation:** Replace the dual variable tracking (`min_cell`, `max_cell`) with a single `local_cell` variable. This reduces the number of live variables in the loop scope [S1, unofficial].
2.  **Bounds Checking:** Implement bounds checking using the single `local_cell` variable. The check verifies if any component of `local_cell` exceeds the brick extent [S1, unofficial]:
    ```cpp
    if (any((uint3)local_cell >= (uint)VX_BRICK_EXT))
    ```
3.  **Deduplication:** Identify and remove duplicate calculations of `tdelta` (time delta for ray traversal) and other redundant operations within the middle commits of the traversal loop [S1, unofficial].
4.  **State Minimization:** Ensure that no unnecessary state is carried over the loop boundaries. This involves moving variable declarations inside the loop if they are only used within it, or reusing registers for temporary values [S1, unofficial].

### Pseudocode
The following pseudocode illustrates the optimized bounds check and variable usage compared to the unoptimized version.

```python
# Unoptimized approach (for reference)
# int3 min_cell, max_cell;
# if (any(cell < min_cell) || any(cell > max_cell)) { ... }

# Optimized approach
int3 local_cell; # Single variable replaces min/max

# Check bounds using unsigned comparison to handle negative indices safely
if any((uint3)local_cell >= (uint)VX_BRICK_EXT):
    # Out of bounds, handle termination or skip
    continue

# Calculate voxel index
voxel_idx = local_cell.x + local_cell.y * VX_BRICK_EXT + local_cell.z * VX_BRICK_EXT * VX_BRICK_EXT

# Access sparse voxel data
word = voxel_mask[voxel_idx >> 5u]
bit = 1u << (voxel_idx & 31u)

if (word & bit) != 0u:
    # Load voxel value
    return voxels.Load(int4(brick_min + local_cell, 0)).r
```

### Parameters
*   **`VX_BRICK_EXT`**: Brick extent. Typical value: $8$ (for $8^3$ bricks). Not given in the sources for other values.
*   **Target Occupancy:** The goal is to increase occupancy from ~35% to >40% [S1, unofficial].

### Edge Cases and Pitfalls
*   **Low Occupancy:** Unoptimized shaders may exhibit occupancy as low as 35.43% with register allocation of 92, leading to memory stalls despite high ALU usage [S1, unofficial].
*   **Register Pressure:** High register allocation (>90) prevents the GPU from scheduling enough warps to hide memory latency [S1, unofficial].
*   **Precision:** The bounds check uses unsigned comparison `(uint3)local_cell >= (uint)VX_BRICK_EXT` to correctly handle potential negative indices or wrap-around issues in signed integers [S1, unofficial].

## Subtopics

### CUDA Execution Configuration Optimization
This variant focuses on selecting block size, grid size, and shared memory size to maximize GPU occupancy [S2, unofficial]. Occupancy is defined as the number of warps being executed divided by the number of warps allowed per multiprocessor [S2, unofficial]. Benchmarked block sizes include 4x4, 4x8, 4x16, 4x32, 8x8, 8x16, 8x32, and 16x16 [S2, unofficial]. On an NVIDIA GTX280 GPU, block sizes of 8x8, 8x16, and 8x32 yielded the best performance (31 FPS on Engine dataset), while 16x16 yielded lower performance (21 FPS) [S2, unofficial]. The 4x16 block size also performed well (61 FPS on Bucky dataset) [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** The algorithmic complexity of DDA traversal remains $O(N)$ where $N$ is the number of voxels traversed. The optimization reduces the constant factor by improving hardware utilization.
*   **Memory Complexity:** Register usage is reduced by 20 registers (from 92 to 72) [S1, unofficial].
*   **Measured Performance:**
    *   **monu2-1 (128³):** FPS increased from 143.20 to 144.00 (+0.56%); Walltime decreased from 6.58 ms to 5.37 ms (-18.32%) [S1, unofficial].
    *   **sponza-256-1 (256³):** FPS increased from 59.78 to 72.83 (+21.83%); Walltime decreased from 28.39 ms to 22.51 ms (-20.71%) [S1, unofficial].
    *   **sponza-256-2 (256³):** FPS increased from 109.53 to 143.94 (+31.42%); Walltime decreased from 13.40 ms to 7.32 ms (-45.33%) [S1, unofficial].
*   **Strengths:** Significant reduction in walltime for complex scenes; improved occupancy leads to better hiding of memory latency.
*   **Limitations:** The gains are hardware-dependent and rely on the compiler's ability to optimize the reduced register footprint. The improvement in FPS for simpler scenes (monu2) was modest compared to complex scenes (sponza) [S1, unofficial].
*   **When to Use:** Use when the DDA shader is the bottleneck and profiler data indicates high register allocation and low occupancy.
*   **When Not to Use:** If the bottleneck is memory bandwidth or ALU throughput rather than occupancy, this optimization may yield diminishing returns.

## Background
The optimization was developed as part of a voxel raytracer development log, specifically targeting the "2-level DDA" shader [S1, unofficial]. The author observed low occupancy (35.43%) and high register allocation (92) in the Metal profiler, which negatively impacted performance despite high ALU usage [S1, unofficial]. The optimization was implemented through a series of commits (5d70988, c6e6210, c94b224, 9a1a107) that reduced register allocation by 20 and improved occupancy to 42.37% [S1, unofficial]. The work builds on general GPU programming principles regarding occupancy and register pressure [S1, unofficial].
