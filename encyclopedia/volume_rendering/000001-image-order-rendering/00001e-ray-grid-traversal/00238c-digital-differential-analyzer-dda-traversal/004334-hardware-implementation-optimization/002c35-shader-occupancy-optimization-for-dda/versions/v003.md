# Shader Occupancy Optimization for DDA

Also called: DDA Shader Register Optimization, Optimizing 2-Level DDA Shader, Shader Occupancy Optimization

## Overview
This method reduces register pressure and increases GPU shader occupancy in Digital Differential Analyzer (DDA) ray traversal by minimizing state carried across nested loops and deduplicating calculations [S1, unofficial]. It addresses the performance degradation caused by low occupancy (e.g., 35.43%) and high register allocation (e.g., 92 registers) in unoptimized 2-level DDA shaders, which leads to memory stalls despite high ALU usage [S1, unofficial]. It sets itself apart from general execution configuration tuning by focusing specifically on the internal register layout and variable lifecycle within the shader code itself [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** An unoptimized 2-level DDA shader implementation containing nested loops for voxel traversal, typically using separate `min_cell` and `max_cell` variables and redundant `tdelta` calculations.
*   **Output:** An optimized shader with reduced register allocation and higher occupancy.

**Data Structures:**
*   `local_cell`: A single `int3` variable replacing separate `min_cell` and `max_cell` structures.
*   `VX_BRICK_EXT`: A constant defining the brick extent (dimensions of the voxel brick).
*   `voxel_mask`: An array or buffer containing voxel occupancy data.
*   `voxels`: A texture or buffer for loading voxel values.

**Numbered Steps:**
1.  **Variable Consolidation:** Replace the dual-variable approach (`min_cell`, `max_cell`) with a single `local_cell` variable (`int3`) used in both nested loops. This reduces the number of registers required to track traversal state [S1, unofficial].
2.  **Bounds Checking:** Implement bounds checking using a unified condition that casts `local_cell` to unsigned integers to prevent signed integer overflow issues during comparison. The condition checks if any component of `local_cell` exceeds the brick extent [S1, unofficial]:
    $$ \text{if } (\text{any}((\text{uint3})\text{local\_cell} \ge (\text{uint})\text{VX\_BRICK\_EXT})) $$
3.  **Index Calculation:** Calculate the linear index for the voxel mask using the consolidated `local_cell` coordinates:
    $$ \text{voxel\_idx} = \text{local\_cell}.x + \text{local\_cell}.y \times \text{VX\_BRICK\_EXT} + \text{local\_cell}.z \times \text{VX\_BRICK\_EXT} \times \text{VX\_BRICK\_EXT} $$
4.  **Bitwise Masking:** Determine the word and bit position within the voxel mask to check for voxel existence:
    $$ \text{word} = \text{voxel\_mask}[\text{voxel\_idx} \gg 5u] $$
    $$ \text{bit} = 1u \ll (\text{voxel\_idx} \& 31u) $$
5.  **Conditional Load:** If the bit is set, load the voxel value. Otherwise, the traversal continues or terminates based on the specific DDA logic [S1, unofficial]:
    ```python
    if ((word & bit) != 0u):
        return voxels.Load(int4(brick_min + local_cell, 0)).r
    ```
6.  **Deduplication:** Remove redundant calculations of `tdelta` (time delta for ray traversal) and other unnecessary work identified in intermediate commits to further reduce register pressure [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Signed Integer Overflow:** Using signed integers for bounds checking can lead to incorrect results if `local_cell` components become negative or exceed the maximum signed integer value. Casting to `uint3` before comparison avoids this [S1, unofficial].
*   **Register Pressure:** Failing to deduplicate `tdelta` calculations or keeping unnecessary state across loops can lead to high register allocation (e.g., 92 registers), causing low occupancy and memory stalls [S1, unofficial].

## Subtopics

### CUDA Execution Configuration Optimization
This variant focuses on selecting block size, grid size, and shared memory size to maximize GPU occupancy and performance [S2, unofficial]. Occupancy is defined as the number of warps being executed divided by the number of warps allowed per multiprocessor [S2, unofficial]. Benchmarked block sizes include 4x4, 4x8, 4x16, 4x32, 8x8, 8x16, 8x32, and 16x16 [S2, unofficial]. On an NVIDIA GTX280 GPU, block sizes of 4x16, 4x32, 8x8, 8x16, and 8x32 yielded higher performance (e.g., 31 FPS on the Engine dataset) compared to 16x16 (21 FPS) [S2, unofficial].

## Operating characteristics
**Time and Memory Complexity:**
*   **Time Complexity:** The optimization reduces the constant factor in the traversal loop by minimizing register spills and redundant calculations. The asymptotic complexity remains dependent on the number of voxels traversed [S1, unofficial].
*   **Memory Complexity:** Register usage is reduced from 92 to 72 registers per thread, allowing for higher occupancy [S1, unofficial].

**Measured Performance:**
*   **Hardware:** MacBook Air (M2) with a 144 Hz ultrawide monitor at 3840 x 1600 resolution [S1, unofficial].
*   **monu2-1 (128³ resolution):** FPS increased from 143.20 to 144.00 (+0.56%); Walltime decreased from 6.58 ms to 5.37 ms (-18.32%) [S1, unofficial].
*   **sponza-256-1:** FPS increased from 59.78 to 72.83 (+21.83%); Walltime decreased from 28.39 ms to 22.51 ms (-20.71%) [S1, unofficial].
*   **sponza-256-2:** FPS increased from 109.53 to 143.94 (+31.42%); Walltime decreased from 13.40 ms to 7.32 ms (-45.33%) [S1, unofficial].

**Scaling:**
*   Performance gains are more significant in scenes with higher complexity or larger voxel counts (e.g., sponza-256-2) where register pressure and memory stalls have a greater impact [S1, unofficial].

**Strengths and Limitations:**
*   **Strengths:** Significant reduction in walltime and improvement in FPS for complex scenes; reduced register allocation allows for higher occupancy [S1, unofficial].
*   **Limitations:** The optimization is specific to the 2-level DDA shader structure; benefits may be less pronounced in simpler scenes (e.g., monu2-1) where other bottlenecks dominate [S1, unofficial].

**When to Use:**
*   Use when profiling reveals low shader occupancy and high register allocation in DDA traversal shaders [S1, unofficial].
*   Use when rendering complex scenes where memory stalls are a bottleneck [S1, unofficial].

**When Not to Use:**
*   Use with caution in very simple scenes where the overhead of optimization might not justify the gains [S1, unofficial].

## Background
The method originated from development logs of a voxel raytracer, specifically addressing performance issues in the 2-level DDA shader [S1, unofficial]. The low occupancy (35.43%) and high register allocation (92) were identified as bottlenecks compared to a naive DDA implementation (71.39% occupancy, 42 registers) [S1, unofficial]. The optimization was implemented through a series of commits that consolidated variables and deduplicated calculations [S1, unofficial].
