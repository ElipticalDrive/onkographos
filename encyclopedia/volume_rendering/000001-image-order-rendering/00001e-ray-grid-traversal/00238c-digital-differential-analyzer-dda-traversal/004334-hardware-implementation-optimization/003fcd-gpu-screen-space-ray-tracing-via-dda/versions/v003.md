# GPU Screen-Space Ray Tracing via DDA

Also called: Efficient GPU Screen-Space Ray Tracing via DDA, Linear 2D Iteration, Perspective-Correct DDA Ray Tracing, Thin-line Rasterization for Ray Casting

## Overview
This method provides an efficient GPU solution for screen-space 3D ray tracing against a depth buffer by adapting the perspective-correct Digital Differential Analyzer (DDA) line rasterization algorithm [S1, unofficial]. It solves the inefficiency and missing intersections inherent in linear 3D marching by ensuring that sampled pixels form a contiguous set with no oversampling [S1, unofficial]. Unlike [Parallel 3D-DDA](6247-parallel-3d-dda.md), which projects 3D points to screen space and may skip pixels or oversample the same pixel multiple times, this method places each sampled pixel adjacent (in x, y, or diagonally) to the previous one and samples each pixel at most once [S1, unofficial].

## How it works
### Inputs and Outputs
**Inputs:**
*   `csOrig`: Camera-space ray origin (vec3) [S1, unofficial].
*   `csDir`: Camera-space ray direction (vec3) [S1, unofficial].
*   `proj`: Projection matrix (mat4) [S1, unofficial].
*   `nearPlaneZ`: Negative near plane Z value (float) [S1, unofficial].
*   `csZBuffer`: Depth buffer texture (sampler2D) [S1, unofficial].
*   `csZBufferSize`: Depth buffer dimensions (vec2) [S1, unofficial].
*   `csZBufferIsHyperbolic`: Boolean flag indicating if the depth buffer stores hyperbolic (perspective-correct) depth values [S1, unofficial].
*   `csZThickness`: Camera-space z-thickness ascribed to each point in the depth buffer (float) [S1, unofficial].
*   `maxDistance`: Maximum trace distance in camera-space (float) [S1, unofficial].
*   `maxSteps`: Maximum number of steps allowed during the trace (int) [S1, unofficial].
*   `stride`: Controls spacing between samples. `stride = 1.0` produces thin-line rasterization [S1, unofficial].
*   `jitter`: Value in range `[0, 1]` used to bump the ray in pixels to conceal banding artifacts [S1, unofficial].

**Outputs:**
*   `hitPixel`: Coordinates of the hit pixel (vec2) [S1, unofficial].
*   `hitLayer`: Index of the hit layer in the depth buffer (int) [S1, unofficial].
*   `csHitPoint`: Camera-space hit point (vec3) [S1, unofficial].
*   Return value: Boolean indicating if a surface was hit [S1, unofficial].

### Data Structures
The method operates on standard GPU primitives. The depth buffer is accessed via `texelFetch`, which returns a zero value for out-of-bounds samples to facilitate implicit clipping [S1, unofficial].

### Steps
1.  **Unify DDA Cases:** The classic DDA suffers from divergent execution due to eight cases (4 quadrants × 2 iteration directions). These are unified by permuting axes and taking derivatives relative to the sign of `delta.x`, ensuring iteration is always performed along the x-axis [S1, unofficial]. A matrix permutation compensates for this in the vertical case, allowing all subsequent code to assume iteration in x [S1, unofficial].
2.  **Clip Far End:** Clip only the far end of the ray against the near plane. The caller ensures the ray origin lies within the view frustum, eliminating the need for complex frustum clipping logic [S1, unofficial].
3.  **Implicit Viewport Clipping:** Structure the test so that a zero value returned by `texelFetch` for an out-of-bounds depth-buffer sample terminates iteration [S1, unofficial].
4.  **Calculate Screen Endpoints:** Compute the screen-space pixel endpoints $P_0$ and $P_1$ of the line segment corresponding to the ray [S1, unofficial].
5.  **Iterate:** Perform the DDA loop. For each step, calculate the 3D point $Q'$ corresponding to the current 2D screen point $(x, y)$ using perspective-correct interpolation [S1, unofficial].
6.  **Check Intersection:** Sample the depth buffer at the current screen coordinates. If the sampled depth indicates an intersection (considering `csZThickness`), record the hit and break the loop [S1, unofficial].
7.  **Termination:** The loop terminates if a hit is found, `maxSteps` is reached, or the ray goes out of bounds (detected by the zero-depth sentinel) [S1, unofficial].

### Formulas
The 3D point $Q'$ corresponding to a 2D screen point $(x, y)$ is calculated as [S1, unofficial]:

$$
Q'(x,y) = \frac{(Q \otimes k)(x,y)}{k(x,y)}
$$

Where:
*   $k = 1/(H \otimes (0,0,0,1))$ is the reciprocal of the homogeneous w component [S1, unofficial].
*   $H$ is the homogeneous coordinate transformation [S1, unofficial].
*   $Q \otimes k$ interpolates linearly in 2D [S1, unofficial].

### Parameters
*   `stride`: Default `1.0`. Larger values space samples for efficiency at the cost of quality [S1, unofficial].
*   `jitter`: Range `[0, 1]`. Used to conceal banding artifacts introduced by `stride > 1.0` [S1, unofficial].
*   `csZBufferIsHyperbolic`: Boolean. Determines depth buffer interpretation [S1, unofficial].
*   `csZThickness`: Float. Used for robustness in intersection testing [S1, unofficial].
*   `maxDistance`: Float. Maximum trace distance [S1, unofficial].
*   `maxSteps`: Int. Maximum iteration count [S1, unofficial].

### Edge Cases and Pitfalls
*   **Branch Divergence:** Classic DDA implementations suffer from divergent execution on GPUs due to branching for different quadrants and iteration directions. This method avoids this by unifying cases via axis permutation [S1, unofficial].
*   **Banding Artifacts:** Using `stride > 1.0` for efficiency introduces banding artifacts. This is handled by applying a `jitter` value in `[0, 1]` to the ray [S1, unofficial].
*   **Out-of-Bounds Access:** The method relies on `texelFetch` returning zero for out-of-bounds samples to terminate iteration. Implementations must ensure this behavior is consistent with the hardware/driver [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of steps (`maxSteps`) and the number of pixels traced. The inner loop is optimized for instruction caching and minimal register usage [S1, unofficial].
*   **Memory Complexity:** Constant space per thread, plus access to the depth buffer [S1, unofficial].
*   **Measured Performance:** Achieved 2 ms at 1080p on a GeForce 650M for reflections in ripply water [S1, unofficial].
*   **Strengths:** No oversampling, contiguous pixel sampling, efficient GPU implementation due to branch unification and simple arithmetic operations (FMUL) [S1, unofficial].
*   **Limitations:** Quality loss with `stride > 1.0` (mitigated by jitter), relies on depth buffer availability and correctness [S1, unofficial].
*   **When to Use:** Reflections, refractions, and other screen-space effects where performance is critical and the depth buffer is available [S1, unofficial].
*   **When Not to Use:** When high-quality, artifact-free sampling is required without jitter, or when the depth buffer is not available or unreliable [S1, unofficial].

## Background
The underlying method of 2D iteration is about 20 years old, evolving from Bresenham's algorithm through DDA [S1, unofficial]. Recent games brought details for reflection tracing and GPU optimizations [S1, unofficial]. Wronski [2014a, 80][2014b] and Valient [2014b, 90][2014a] sketched algorithms in presentations [S1, unofficial]. The full implementation details were provided by McGuire and Mara [S1, unofficial]. It is used in production for reflections in ripply water [S1, unofficial].
