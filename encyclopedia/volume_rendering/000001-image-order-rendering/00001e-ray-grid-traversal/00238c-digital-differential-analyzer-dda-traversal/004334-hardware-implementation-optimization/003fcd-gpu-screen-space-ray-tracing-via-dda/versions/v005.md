# GPU Screen-Space Ray Tracing via DDA

Also called: Efficient GPU Screen-Space Ray Tracing via DDA, Linear 2D Iteration, Perspective-Correct DDA Ray Tracing, Thin-line Rasterization for Ray Casting

## Overview
This method provides an efficient GPU solution for screen-space 3D ray tracing against a depth buffer by adapting the perspective-correct Digital Differential Analyzer (DDA) line rasterization algorithm [S1, unofficial]. It solves the inefficiency and missing intersections inherent in linear 3D marching by ensuring that sampled pixels form a contiguous set with no oversampling [S1, unofficial]. Unlike linear 3D ray marching, which projects 3D points to screen space and can skip pixels or oversample the same pixel multiple times, this method places each sampled pixel adjacent (in x, y, or diagonally) to the previous one and samples each pixel at most once [S1, unofficial].

## How it works
### Inputs and Outputs
**Inputs:**
*   `csOrig`: Camera-space ray origin [S1, unofficial].
*   `csDir`: Camera-space ray direction [S1, unofficial].
*   `proj`: Projection matrix [S1, unofficial].
*   `nearPlaneZ`: Negative near plane Z value [S1, unofficial].
*   `csZBuffer`: Depth buffer texture [S1, unofficial].
*   `csZBufferSize`: Dimensions of the depth buffer [S1, unofficial].
*   `csZBufferIsHyperbolic`: Boolean flag indicating if the depth buffer stores hyperbolic (perspective-correct) depth values [S1, unofficial].
*   `csZThickness`: Camera-space z-thickness ascribed to each point in the depth buffer [S1, unofficial].
*   `maxDistance`: Maximum trace distance in camera-space [S1, unofficial].
*   `maxSteps`: Maximum number of steps allowed during the trace [S1, unofficial].
*   `stride`: Controls spacing between samples. `stride = 1.0` produces thin-line rasterization [S1, unofficial].
*   `jitter`: A value in the range $[0, 1]$ used to bump the ray in pixels to conceal banding artifacts introduced by spaced samples [S1, unofficial].

**Outputs:**
*   Boolean indicating if a surface was hit [S1, unofficial].
*   `hitPixel`: Coordinates of the hit pixel [S1, unofficial].
*   `hitLayer`: Index of the hit layer in the depth buffer (if multiple layers are supported) [S1, unofficial].
*   `csHitPoint`: Camera-space position of the hit [S1, unofficial].

### Data Structures
The method operates on a depth buffer (`csZBuffer`) accessed via `texelFetch` [S1, unofficial]. The depth buffer stores depth values which may be hyperbolic (perspective-correct) or linear, determined by `csZBufferIsHyperbolic` [S1, unofficial]. The algorithm assumes a right-handed camera space where $+z$ is out of the screen [S1, unofficial].

### Steps
1.  **Unify DDA Cases:** The classic DDA has eight cases (4 quadrants $\times$ 2 iteration directions) [S1, unofficial]. These are unified by permuting axes and taking derivatives relative to the sign of $\Delta x$, ensuring iteration is always performed along the x-axis [S1, unofficial]. A matrix permutation compensates for this in the vertical case, allowing all subsequent code to assume iteration in x [S1, unofficial]. This eliminates divergent execution on GPUs [S1, unofficial].
2.  **Clip Far End:** Clip only the far end of the ray against the near plane [S1, unofficial]. The caller ensures the ray origin lies within the view frustum, eliminating the need for complex frustum clipping logic [S1, unofficial].
3.  **Implicit Viewport Clipping:** Structure the test so that a zero value returned by `texelFetch` for an out-of-bounds depth-buffer sample terminates iteration [S1, unofficial].
4.  **Iterate and Sample:** Perform the DDA iteration [S1, unofficial]. At each step, calculate the 3D point corresponding to the current 2D screen point and test for intersection with the depth buffer [S1, unofficial].

### Formulas
The 3D point $Q'$ corresponding to a 2D screen point $(x, y)$ is calculated as [S1, unofficial]:

$$
Q'(x,y) = \frac{(Q \otimes k)(x,y)}{k(x,y)}
$$

where $k = 1/(H \otimes (0,0,0,1))$ is the reciprocal of the homogeneous w component, and $Q \otimes k$ interpolates linearly in 2D [S1, unofficial].

### Pseudocode
The following pseudocode implements the core DDA loop [S1, unofficial]. It assumes the axis permutation has already been applied so that iteration proceeds along the x-axis [S1, unofficial]. It uses conditional assignment instead of branches to maintain SIMD efficiency [S1, unofficial].

```python
def traceRay(csOrig, csDir, proj, nearPlaneZ, csZBuffer, csZBufferSize, 
             csZBufferIsHyperbolic, csZThickness, maxDistance, maxSteps, 
             stride, jitter):
    # Standard math/vector operations
    def projectToScreen(pos, matrix):
        # Homogeneous projection followed by perspective division
        h = matrix * pos
        return (h.x / h.w, h.y / h.w, h.w)
    
    def texelFetch(tex, ix, iy):
        # Returns depth value; returns 0.0 for out-of-bounds coordinates
        if 0 <= ix < tex.width and 0 <= iy < tex.height:
            return tex[ix, iy]
        return 0.0
    
    def sign(v):
        return 1 if v >= 0 else -1
    
    def length(v):
        return (v.x**2 + v.y**2 + v.z**2)**0.5

    # 1. Project ray endpoints to screen space
    P0 = projectToScreen(csOrig, proj)
    P1 = projectToScreen(csOrig + csDir * maxDistance, proj)

    # 2. DDA parameters (iteration always along x-axis after permutation)
    dx = P1[0] - P0[0]
    dy = P1[1] - P0[1]
    step_x = sign(dx) * stride
    step_y = (dy / dx) * step_x

    # 3. Initialize position with jitter to conceal banding
    x = P0[0] + jitter * step_x
    y = P0[1] + jitter * step_y

    # 4. Perspective-correct interpolation setup
    # k = 1/w. Interpolate k and Q*k linearly in 2D.
    k0 = 1.0 / P0[2]
    k1 = 1.0 / P1[2]
    dk = k1 - k0
    Qk0 = P0[0] * k0
    Qk1 = P1[0] * k1
    dQk = Qk1 - Qk0

    # Track camera-space distance along ray
    camDist = 0.0
    stepCamDist = length(csDir) * stride

    # 5. Iterate
    for step in range(maxSteps):
        camDist += stepCamDist
        if camDist > maxDistance:
            break

        # Perspective-correct interpolation for current screen point
        t = (x - P0[0]) / dx
        k = k0 + t * dk
        Qk = Qk0 + t * dQk

        # Reconstruct 3D point from interpolated values: Q' = Qk / k
        screenPoint = (Qk / k, 0.0, 0.0) # y,z handled similarly in full impl

        # Calculate ray depth at this screen point in camera space
        rayDepth = csOrig.z + csDir.z * (camDist / length(csDir))

        # Implicit viewport clipping: out-of-bounds texelFetch returns 0
        depthSample = texelFetch(csZBuffer, int(x), int(y))
        if depthSample == 0.0:
            break

        # Intersection test with z-thickness for robustness
        if rayDepth <= depthSample + csZThickness:
            return True, (int(x), int(y)), 0, screenPoint

        # Advance DDA
        x += step_x
        y += step_y

    return False, (0, 0), 0, (0, 0, 0)
```

### Parameters
*   `stride`: Controls spacing between samples. `stride = 1.0` produces thin-line rasterization. Larger values space samples for efficiency at the cost of quality [S1, unofficial].
*   `jitter`: A value in the range $[0, 1]$ used to bump the ray in pixels to conceal banding artifacts introduced by spaced samples (stride > 1.0) [S1, unofficial].
*   `csZBufferIsHyperbolic`: Boolean encoding flag for the depth buffer. Determines if the depth buffer stores hyperbolic (perspective-correct) depth values [S1, unofficial].
*   `csZThickness`: Camera-space z-thickness ascribed to each point in the depth buffer, used for robustness in intersection testing [S1, unofficial].
*   `maxDistance`: Maximum trace distance in camera-space [S1, unofficial].
*   `maxSteps`: Maximum number of steps allowed during the trace [S1, unofficial].

### Edge Cases and Pitfalls
*   **Branch Divergence:** Classic DDA implementations suffer from divergent execution on GPUs due to branching for different quadrants and iteration directions [S1, unofficial]. This method avoids this by unifying cases via axis permutation [S1, unofficial].
*   **Banding Artifacts:** Banding artifacts appear when using `stride > 1.0` for efficiency [S1, unofficial]. This is handled by applying a `jitter` value in $[0, 1]$ to the ray [S1, unofficial].
*   **Out-of-Bounds Access:** The method relies on implicit clipping to the viewport [S1, unofficial]. If the depth buffer does not return zero for out-of-bounds accesses, the iteration may not terminate correctly [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The method performs a fixed number of steps up to `maxSteps` or `maxDistance` [S1, unofficial]. The inner loop contains simple fused multiply-add (FMUL) instructions and a single texture lookup per step [S1, unofficial].
*   **Memory Complexity:** Minimal additional memory is required beyond the depth buffer [S1, unofficial]. The algorithm is designed to minimize peak register count and instruction cache pressure [S1, unofficial].
*   **Measured Performance:** Used in production for reflections in ripply water, achieving 2 ms at 1080p on GeForce 650M [S1, unofficial].
*   **Strengths:** Ensures sampling at a contiguous set of pixels with no oversampling, addressing the inefficiency and missing intersections of linear 3D marching [S1, unofficial]. Efficient on GPUs due to branch unification and simple arithmetic [S1, unofficial].
*   **Limitations:** Quality decreases with larger `stride` values, requiring jitter to mitigate banding [S1, unofficial]. Relies on the caller to ensure the ray origin is within the view frustum [S1, unofficial].
*   **When to Use:** Suitable for screen-space effects like reflections in ripply water where performance is critical and the depth buffer is available [S1, unofficial].
*   **When Not to Use:** Not suitable for scenes requiring global illumination or complex ray-object intersections beyond the depth buffer [S1, unofficial].

## Background
The underlying method of 2D iteration is about 20 years old, evolving from Bresenham's algorithm through DDA [S1, unofficial]. Recent games brought details for reflection tracing and GPU optimizations [S1, unofficial]. Wronski [2014a, 80][2014b] and Valient [2014b, 90][2014a] sketched algorithms in presentations [S1, unofficial]. The method has been proven in production of recent major game titles [S1, unofficial].
