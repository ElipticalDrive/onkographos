# Ray Structure

Also called: Ray Data Structure, Ray Representation, Ray3D

## Overview
The Ray Structure is a fundamental data object in volume rendering and ray tracing that represents a geometric ray in 3D space, defined by an origin point and a direction vector [S1, S2, S3, unofficial]. It serves as the primary query primitive for traversing volume data structures and computing intersections [S1, S2, S3, unofficial]. Unlike higher-level containers that manage batches or bundles of rays, the Ray Structure encapsulates the state of a single ray, providing methods to evaluate points along its path and manage its parameter range [S1, S2, S3, unofficial]. It differs from the [Ray Bundle](2179-ray-bundle.md) by focusing on individual ray geometry rather than batched sampling metadata, and from the [Hit Record Structure](4953-hit-record-structure.md) by representing the input query rather than the output intersection result [G].

## How it works
**Inputs and Outputs:**
The Ray Structure is initialized with an origin $\mathbf{o}$ and a direction $\mathbf{v}$. It outputs points on the ray at a given parameter $t$ and provides access to its geometric components.

**Data Structures:**
The core layout consists of two primary fields [S2, unofficial]:
1.  `orig`: A 3D point representing the ray origin. In some implementations, this is an alias for a `vec3` type [S2, unofficial].
2.  `dir`: A 3D vector representing the ray direction [S2, unofficial].

**Parameters:**
*   `RAY_MIN_T`: The minimum valid parameter value for the ray. Default value is $10^{-5}$ [S3, unofficial].
*   `RAY_MAX_T`: The maximum valid parameter value for the ray. Default value is $10^{30}$ [S3, unofficial].

**Steps and Formulas:**
1.  **Initialization:** The ray is constructed with an origin and direction. The direction vector is normalized to unit length [S3, unofficial]. If a specific length is required, the direction is scaled: $\mathbf{v}_{scaled} = \frac{\mathbf{v}}{\|\mathbf{v}\|} \times \text{length}$ [S2, unofficial].
2.  **Point Evaluation:** To find the point on the ray at parameter $t$, the following linear interpolation is used [S1, S2, S3, unofficial]:
    $$ P(t) = \mathbf{o} + t \cdot \mathbf{v} $$
    where $\mathbf{o}$ is the origin and $\mathbf{v}$ is the normalized direction vector [S1, S2, S3, unofficial].

**Pseudocode:**
```python
class Ray:
    def __init__(self, origin=None, direction=None):
        # Default constructor initializes origin to (0,0,0) and direction to (0,0,-1) [S1, unofficial]
        # or (0,0,0) for both if not specified [S3, unofficial].
        if origin is None:
            self.orig = Vec3(0.0, 0.0, 0.0)
        else:
            self.orig = origin
            
        if direction is None:
            self.dir = Vec3(0.0, 0.0, -1.0) # Default direction [S1, unofficial]
        else:
            self.dir = direction
            
        # Normalize direction [S3, unofficial]
        self.dir = self.dir / self.dir.length()
        
        # Set range parameters [S3, unofficial]
        self.range_min = 1e-5f # RAY_MIN_T
        self.range_max = 1e+30f # RAY_MAX_T

    def at(self, t):
        """
        Computes the point on the ray at distance t.
        Formula: origin + t * direction [S1, S2, S3, unofficial]
        """
        return self.orig + (t * self.dir)

    def set_ray_length(self, length):
        """
        Normalizes direction and sets its magnitude to the specified length [S2, unofficial].
        """
        normalized_dir = self.dir / self.dir.length()
        self.dir = normalized_dir * length
```

**Edge Cases and Pitfalls:**
*   **Zero Direction:** The direction vector must not be zero-length before normalization. If the input direction is zero, normalization fails [G].
*   **Precision:** Using `double` for coordinates and parameters is recommended to avoid precision issues during intersection tests, as seen in standard implementations [S2, unofficial].
*   **Range Clipping:** Intersections with $t < \text{RAY\_MIN\_T}$ are typically treated as inside the volume or invalid to avoid self-intersection artifacts near the origin [S3, unofficial].

## Subtopics

### [Ray Bundle](2179-ray-bundle.md)
A Ray Bundle is a container data structure that groups ray origins, directions, and associated sampling parameters (sample points and lengths) into a single object, typically implemented as a collection of aligned tensors. It solves the problem of managing batched ray data for volume rendering and neural rendering pipelines, allowing efficient vectorized operations and memory transfers. It differs from a [RayBatch container](4187-raybatch-container.md) by explicitly bundling sampling metadata (sample points/lengths) alongside geometric ray data, and from a [Hit Record Structure](4953-hit-record-structure.md) by focusing on input ray generation rather than output intersection results.

### [RayBatch container](4187-raybatch-container.md)
The RayBatch container is a NumPy-style data structure for storing and sampling ray batches during training, supporting efficient indexing, slicing, and conversion to Mitsuba tensor types. It provides batch-level operations and explicit conversion logic to Mitsuba 3, distinguishing it from the generic [Ray Structure](4026-ray-structure.md) and the [Ray Bundle](2179-ray-bundle.md) [G].

### [Hit Record Structure](4953-hit-record-structure.md)
A hit record structure stores the geometric and material properties of a ray-surface intersection. It passes intersection context (position, normal, distance, and material reference) from traversal to shading. It is distinguished from sibling structures like the [Ray Bundle](2179-ray-bundle.md) or [RayBatch container](4187-raybatch-container.md) by focusing on the state of a single intersection event rather than the propagation or batching of rays themselves [G].

### [Plücker Ray Embedding](5132-pl-cker-ray-embedding.md)
Plücker Ray Embedding parameterizes a 3D ray using Plücker coordinates to create a scale-, position-, and focal-length-independent representation. It maps a ray defined by origin $\mathbf{o}$ and direction $\mathbf{v}$ into a 16-dimensional multivector, enabling robust modulation of camera poses to image features in neural rendering frameworks. Unlike extrinsic/intrinsic matrix parameterizations, this method relies on the cross product $\mathbf{o} \times \mathbf{v}$.

### [Ray Segments Spec](12496-ray-segments-spec.md)
Ray Segments Spec is a data structure designed to represent ray segments efficiently, particularly in the context of volume rendering and neural radiance fields. It stores segment values, endpoint flags, validity, chunking information, and ray mappings. It differs from sibling structures like [Ray Bundle](2179-ray-bundle.md) by focusing on explicit segment-level metadata rather than raw ray parameters, and from [RayBatch container](4187-raybatch-container.md) by providing granular control over segment validity and chunking.

### Z-list-buffer Ray Representation
A data structure storing volume data as an array of rays, where each ray contains a list of sample points (position and normal) defining regions, replacing traditional scalar fields to reduce storage and preserve sharp features [S4].

**Definition:**
The Z-list-buffer representation uses arrays of rays to store samples of volume data. Each sample is a point located at the surface of the volume data, storing its position and normal direction [S4]. This replaces traditional scalar fields to reduce storage and preserve sharp features [S4].

**Steps:**
1.  Acquire Hermite data at a fine resolution $n_k \times n_k \times n_k$ [S4].
2.  Shoot axis-aligned rays along the x, y, and z axes [S4].
3.  For each ray, store intersection points and normals [S4].
4.  Use orthographic projection and a Z-buffer with a Z-list for faster scan conversion than modified ray tracing [S4].

**Layout:**
*   **Structure:** An array of Rays. Each Ray contains a list of Samples.
*   **Sample:** Stores 1) Position (3D point) and 2) Normal direction (3D vector) [S4].
*   **Array Resolution:** $(n_k + 1) \times (n_k + 1)$, where $n_k$ is the finest resolution. Three such arrays are used (one for each axis: x, y, z) [S4].
*   **1D Ray Structure:** A ray contains pairs of sample points to represent regions. The first sample marks the left boundary, and the second marks the right boundary [S4]. Samples are classified as 'left bounding' or 'right bounding' [S4].

**Parameters:**
*   Average number of samples per ray: ~2.86 for a dragon model, ~2.05 for a fandisk model [S4].
*   Contrast with 512 samples for a $512^3$ distance field [S4].

## Operating characteristics
**Time and Memory Complexity:**
*   **Standard Ray Structure:** $O(1)$ time for point evaluation and construction. Memory is $O(1)$ per ray (typically 6-8 floats for origin and direction) [S1, S2, S3, unofficial].
*   **Z-list-buffer:** Memory usage scales with the number of surface intersections. The average number of samples per ray is significantly lower than the volume resolution (e.g., ~2-3 samples vs. 512 for a dense grid), offering substantial memory savings for sparse or sharp-edged volumes [S4].

**Strengths and Limitations:**
*   **Standard Ray Structure:** Simple to implement and efficient for basic ray casting. Limited in expressive power for complex neural rendering or batched operations [S1, S2, S3, unofficial].
*   **Z-list-buffer:** Excellent for preserving sharp features and reducing storage for complex geometries. However, it requires pre-processing (ray shooting/scan conversion) and is less flexible for arbitrary ray directions compared to standard ray structures [S4].

**When to Use:**
*   Use the standard [Ray Structure](4026-ray-structure.md) for general-purpose ray tracing and volume rendering where simplicity and speed are paramount [S1, S2, S3, unofficial].
*   Use the [Z-list-buffer Ray Representation](12496-ray-segments-spec.md) when dealing with high-resolution volume data with sharp features, where memory efficiency and feature preservation are critical [S4].

## Background
The Ray Structure is a foundational concept in computer graphics, originating from early ray tracing algorithms [S1, S2, S3, unofficial]. The specific implementation details, such as the `ray` class with `orig` and `dir` fields and the `at(t)` method, are commonly found in educational and open-source ray tracers [S1, S2, S3, unofficial]. The Z-list-buffer variant was introduced in the context of detail sculpting and volumetric Boolean operations to improve performance over scalar field representations [S4].
