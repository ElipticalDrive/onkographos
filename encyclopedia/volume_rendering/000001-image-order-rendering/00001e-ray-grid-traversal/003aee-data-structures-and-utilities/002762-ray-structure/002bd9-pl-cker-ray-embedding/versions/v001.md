# Plücker Ray Embedding


## Overview
Plücker Ray Embedding parameterizes a 3D ray using Plücker coordinates to create a scale-, position-, and focal-length-independent representation [S1, unofficial]. It maps a ray defined by origin $\mathbf{o}$ and direction $\mathbf{v}$ into a 16-dimensional multivector, enabling robust modulation of camera poses to image features in neural rendering frameworks [S1, unofficial]. Unlike extrinsic/intrinsic matrix parameterizations, this method relies on the cross product $\mathbf{o} \times \mathbf{v}$ [S1, unofficial].

## How it works
**Inputs:**
- `pluecker_ray`: Tensor of shape `[..., 6]`. The last dimension contains the ray parameters. Based on the extraction logic in [S2, unofficial], the input layout is `[o_x, o_y, o_z, v_x, v_y, v_z]` (indices 0-2 are origin, 3-5 are direction).

**Outputs:**
- `multivector`: Tensor of shape `[..., 16]`.

**Data Structures:**
- The multivector is a 16-element vector. The specific mapping of Plücker coordinates to indices is defined by the extraction inverse in [S2, unofficial].

**Steps:**
1. Initialize `mv` as a zero tensor with the same shape `[..., 16]`, device, and dtype as `pluecker_ray`.
2. Extract direction $\mathbf{v}$ from `pluecker_ray` indices 3:6. Assign $\mathbf{v}$ to `mv` indices 5:8.
   - $mv[..., 5] = v_x$
   - $mv[..., 6] = v_y$
   - $mv[..., 7] = v_z$
3. Extract origin $\mathbf{o}$ from `pluecker_ray` indices 0:2. Compute the cross product components $\mathbf{o} \times \mathbf{v}$ and assign them to `mv` indices 8, 9, 10.
   - The source [S2, unofficial] specifies the assignment as:
     - $mv[..., 8] = pluecker\_ray[..., 2]$ (which is $o_z$)
     - $mv[..., 9] = -pluecker\_ray[..., 1]$ (which is $-o_y$)
     - $mv[..., 10] = pluecker\_ray[..., 0]$ (which is $o_x$)
   - *Note:* This assignment does not correspond to the standard cross product $\mathbf{o} \times \mathbf{v} = (o_y v_z - o_z v_y, o_z v_x - o_x v_z, o_x v_y - o_y v_x)$. It appears to be a specific embedding convention or a simplified/incorrect mapping in the cited source [S2, unofficial]. The implementation must follow the source's explicit index mapping.
4. (Indices 0-4 and 11-15 remain zero as per the initialization and lack of assignment in [S2, unofficial]).

**Extracting Plücker Ray from Multivector:**
To reverse the embedding (if the multivector was constructed this way):
1. Concatenate `mv[..., 10]`, `-mv[..., 9]`, `mv[..., 8]`, and `mv[..., 5:8]`.
   - $o_x = mv[..., 10]$
   - $o_y = -mv[..., 9]$
   - $o_z = mv[..., 8]$
   - $\mathbf{v} = mv[..., 5:8]$

**Pseudocode:**

```python
import torch

def embed_pluecker_ray(pluecker_ray: torch.Tensor) -> torch.Tensor:
    """
    Embeds a ray [o_x, o_y, o_z, v_x, v_y, v_z] into a 16D multivector.
    Based on [S2, unofficial].
    """
    # Initialize zero tensor
    mv = torch.zeros_like(pluecker_ray)
    # Expand shape to [..., 16]
    # Note: torch.zeros_like preserves shape. We need to reshape/expand.
    # Assuming pluecker_ray is [..., 6]
    shape = pluecker_ray.shape[:-1]
    mv = torch.zeros(*shape, 16, device=pluecker_ray.device, dtype=pluecker_ray.dtype)
    
    # Assign direction v (indices 3:6 of input) to multivector indices 5:8
    mv[..., 5] = pluecker_ray[..., 3] # v_x
    mv[..., 6] = pluecker_ray[..., 4] # v_y
    mv[..., 7] = pluecker_ray[..., 5] # v_z
    
    # Assign cross product components (specific mapping from [S2, unofficial])
    # Index 8 gets input index 2 (o_z)
    mv[..., 8] = pluecker_ray[..., 2]
    # Index 9 gets negative input index 1 (-o_y)
    mv[..., 9] = -pluecker_ray[..., 1]
    # Index 10 gets input index 0 (o_x)
    mv[..., 10] = pluecker_ray[..., 0]
    
    return mv

def extract_pluecker_ray(mv: torch.Tensor) -> torch.Tensor:
    """
    Extracts ray [o_x, o_y, o_z, v_x, v_y, v_z] from 16D multivector.
    Based on [S2, unofficial].
    """
    o_x = mv[..., 10]
    o_y = -mv[..., 9]
    o_z = mv[..., 8]
    v_x = mv[..., 5]
    v_y = mv[..., 6]
    v_z = mv[..., 7]
    
    # Concatenate: o_x, o_y, o_z, v_x, v_y, v_z
    return torch.stack([o_x, o_y, o_z, v_x, v_y, v_z], dim=-1)
```

**Parameters:**
- Not given in the sources.

**Edge Cases:**
- Zero direction vector: The cross product becomes zero, but the embedding remains valid as a point at infinity or degenerate ray.
- Precision: Standard float32/float64 applies. No specific numerical stability notes provided [S1, unofficial][S2, unofficial].

## Subtopics

### Ray Bundle
A collection of rays sharing a common origin or structure. Chosen when processing multiple rays simultaneously for batched rendering. See [Ray Bundle](2179-ray-bundle.md).

### RayBatch container
A data structure for batching ray parameters for efficient GPU processing. Chosen for high-throughput rasterization or ray marching. See [RayBatch container](4187-raybatch-container.md).

### Hit Record Structure
Stores intersection details (point, normal, distance) for a ray. Chosen when ray-object intersection results need to be retained for shading. See [Hit Record Structure](4953-hit-record-structure.md).

### Ray Segments Spec
Defines sub-segments of a ray for adaptive traversal. Chosen when ray length varies significantly or adaptive sampling is required. See [Ray Segments Spec](12496-ray-segments-spec.md).

## Operating characteristics
- **Time Complexity:** $O(1)$ per ray for embedding/extraction (constant number of assignments).
- **Memory Complexity:** $O(1)$ auxiliary memory per ray (16 floats vs 6 floats input).
- **Strengths:** Invariant to camera scale, position, and focal length [S1, unofficial]. Facilitates feature fusion in multi-view transformers [S1, unofficial].
- **Limitations:** The specific mapping in [S2, unofficial] does not match standard Plücker cross-product formulas, which may cause confusion or errors if standard geometric interpretations are assumed. The 16D vector is sparse (only 6 elements used in the cited implementation).
- **When to use:** When integrating camera rays into neural networks that require geometric invariance [S1, unofficial].
- **When not to use:** When standard geometric ray operations (intersection, distance) are needed directly from the embedding without decoding.

## Background
Plücker coordinates provide a homogeneous representation of lines in 3D space. In computer vision and rendering, they are used to parameterize rays independently of the camera's intrinsic and extrinsic parameters [S1, unofficial]. This allows for robust feature fusion across multiple views in neural reconstruction models, such as the Fusion ViT described in [S1, unofficial]. The specific 16D multivector embedding and index mapping described here originates from the GAI-GS repository [S2, unofficial], while the theoretical motivation for using Plücker rays for scale/position invariance is detailed in X-GRM [S1, unofficial].
