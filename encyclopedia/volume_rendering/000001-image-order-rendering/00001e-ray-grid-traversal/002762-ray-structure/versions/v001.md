# Ray Structure

Also called: Ray Data Structure, Ray Representation, Ray3D

## Overview
A Ray Structure is a data container that encapsulates the geometric definition of a ray in 3D space, consisting of an origin point and a direction vector [S1, S2, S3, unofficial]. It serves as the fundamental primitive for ray marching and tracing in volume rendering, providing methods to evaluate points along the ray and manage traversal bounds [S1, S2, S3, unofficial]. It differs from sibling methods like [Camera Matrix Ray Generation](2172-camera-matrix-ray-generation.md) by focusing on the storage and manipulation of the ray entity itself rather than the computation of its initial parameters from camera matrices.

## How it works
**Inputs:** Origin point $\mathbf{o}$ (3D vector), Direction vector $\mathbf{d}$ (3D vector), and optionally traversal bounds $t_{min}$ and $t_{max}$.
**Outputs:** A ray object capable of returning points at parameter $t$ and managing its internal state.

**Data Structures:**
The ray is represented by a class or struct containing:
1.  `orig`: A 3D vector representing the ray origin. In some implementations, this is aliased as `point3`, which is structurally identical to `vec3` [S2, unofficial].
2.  `dir`: A 3D vector representing the ray direction [S2, unofficial].
3.  `range_min`: A scalar representing the minimum valid parameter $t$ for the ray [S3, unofficial].
4.  `range_max`: A scalar representing the maximum valid parameter $t$ for the ray [S3, unofficial].

**Numbered Steps:**
1.  **Initialization:**
    *   The default constructor initializes `orig` to $(0, 0, 0)$ and `dir` to $(0, 0, -1)$ [S1, unofficial].
    *   Alternatively, a parameterized constructor accepts `orig` and `dir`. It normalizes `dir` to unit length and sets `range_min` to $10^{-5}$ and `range_max` to $10^{30}$ [S3, unofficial].
    *   If a specific length is required, the direction is scaled: $\mathbf{d} = \frac{\mathbf{d}}{\|\mathbf{d}\|} \times \text{length}$ [S2, unofficial].
2.  **Point Evaluation:**
    *   To find the point on the ray at distance $t$, compute: $\mathbf{p}(t) = \mathbf{o} + t \cdot \mathbf{d}$ [S1, S2, S3, unofficial].
    *   This operation assumes $t$ is within $[range\_min, range\_max]$ [S3, unofficial].

**Formulas:**
*   Ray Point: $\mathbf{p}(t) = \mathbf{o} + t \mathbf{d}$
*   Normalized Direction: $\hat{\mathbf{d}} = \frac{\mathbf{d}}{\|\mathbf{d}\|}$
*   Scaled Direction: $\mathbf{d}_{scaled} = \hat{\mathbf{d}} \times L$

**Parameters:**
*   `RAY_MIN_T`: Default minimum $t$ value, typically $10^{-5}$ [S3, unofficial].
*   `RAY_MAX_T`: Default maximum $t$ value, typically $10^{30}$ [S3, unofficial].

**Edge Cases and Pitfalls:**
*   **Zero Direction:** If the input direction vector is zero, normalization fails. Implementers should guard against this or ensure input directions are non-zero [G].
*   **Precision:** Using `double` for coordinates and parameters is common in CPU implementations to avoid precision loss over long distances, while `float` is used in GPU implementations [S2, S3, unofficial].
*   **Bounds:** Failing to clamp $t$ to $[range\_min, range\_max]$ may result in sampling behind the camera or at infinite distance, causing artifacts or crashes [S3, unofficial].

**Pseudocode:**
```python
class Ray:
    def __init__(self, origin=None, direction=None, range_min=1e-5, range_max=1e30):
        if origin is None:
            self.orig = [0.0, 0.0, 0.0]
        else:
            self.orig = list(origin)
        
        if direction is None:
            self.dir = [0.0, 0.0, -1.0]
        else:
            # Normalize direction
            length = math.sqrt(sum(c**2 for c in direction))
            if length == 0:
                self.dir = [0.0, 0.0, 0.0] # Guard against zero vector
            else:
                self.dir = [d / length for d in direction]
        
        self.range_min = range_min
        self.range_max = range_max

    def at(self, t):
        """Compute point on ray at parameter t."""
        return [
            self.orig[0] + t * self.dir[0],
            self.orig[1] + t * self.dir[1],
            self.orig[2] + t * self.dir[2]
        ]

    def set_ray_length(self, length):
        """Scale the direction vector to a specific length."""
        current_length = math.sqrt(sum(c**2 for c in self.dir))
        if current_length > 0:
            scale = length / current_length
            self.dir = [d * scale for d in self.dir]
```

## Subtopics

### [Ray Bundle](2179-ray-bundle.md)
A Ray Bundle is a container data structure that groups ray origins, directions, and associated sampling parameters (sample points and lengths) into a single object, typically implemented as a collection of aligned tensors. It solves the problem of managing batched ray data for volume rendering and neural rendering pipelines, allowing efficient vectorized operations and memory transfers. It differs from a [RayBatch container](4187-raybatch-container.md) by explicitly bundling sampling metadata (sample points/lengths) alongside geometric ray data, and from a [Hit Record Structure](4953-hit-record-structure.md) by focusing on input ray generation rather than output intersection results.

### [RayBatch container](4187-raybatch-container.md)
The RayBatch container is a NumPy-style data structure designed for efficient storage, indexing, and sampling of ray batches during neural volume rendering training. It serves as an intermediate representation that bridges raw NumPy arrays and differentiable rendering engine tensors (specifically Mitsuba 3), enabling batched ray generation and color sampling. It distinguishes itself from the generic [Ray Structure](4026-ray-structure.md) by providing batch-level operations (slicing, random sampling) and explicit conversion logic to Mitsuba tensor types, while differing from the [Ray Bundle](2179-ray-bundle.md) by focusing on training-time batch management rather than just spatial grouping.

#### Plücker Ray Embedding
Plücker Ray Embedding embeds a ray defined by origin $\mathbf{o}$ and direction $\mathbf{v}$ into a 16-dimensional multivector using Plücker coordinates $(\mathbf{v}, \mathbf{o} \times \mathbf{v})$ [S4, unofficial]. The input tensor has shape $[..., 6]$ and the output has shape $[..., 16]$ [S4, unofficial].
**Steps:**
1.  Initialize a zero tensor `mv` of shape $[..., 16]$ with the same device and dtype as the input `pluecker_ray` [S4, unofficial].
2.  Assign the direction vector $\mathbf{v}$ (indices 3:6 of input) to multivector indices 5:8 [S4, unofficial].
3.  Assign the cross product component $\mathbf{o} \times \mathbf{v}$ to multivector indices 8, 9, 10. Specifically: index 8 gets input index 2; index 9 gets negative input index 1; index 10 gets input index 0 [S4, unofficial].
4.  Extract Plücker ray from multivector by concatenating: multivector index 10, negative multivector index 9, multivector index 8, and multivector indices 5:8 [S4, unofficial].

## Operating characteristics
**Time and Memory Complexity:**
*   **Memory:** $O(1)$ per ray, storing two 3D vectors and two scalars.
*   **Time:** Point evaluation is $O(1)$, involving 3 multiplications and 3 additions.

**Measured Performance:**
Not given in the sources.

**Scaling:**
Not given in the sources.

**Strengths and Limitations:**
*   **Strengths:** Simple, lightweight, and efficient for storing individual rays. Supports basic geometric queries.
*   **Limitations:** Does not handle batching or parallelism inherently. Lacks metadata for complex sampling strategies unless extended (e.g., via Ray Bundle).

**When to use it and when not:**
*   Use for single-ray operations, debugging, or as a base component for more complex structures.
*   Do not use for large-scale batched rendering where vectorized operations are required; use [Ray Bundle](2179-ray-bundle.md) or [RayBatch container](4187-raybatch-container.md) instead.

## Background
The Ray Structure is a fundamental concept in computer graphics, originating from ray tracing and ray marching techniques. It is widely used in CPU-based voxel raycasters [S1, unofficial] and GPU-based volume renderers [S3, unofficial]. The specific implementation details, such as default bounds and normalization, are common in educational and open-source graphics codebases [S2, unofficial].
