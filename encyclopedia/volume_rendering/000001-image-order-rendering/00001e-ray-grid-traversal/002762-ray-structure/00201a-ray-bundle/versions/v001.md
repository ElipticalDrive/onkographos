# Ray Bundle

Also called: Ray Bundle Data Structure, Ray Bundle Generation

## Overview
A Ray Bundle is a container data structure that groups ray origins, directions, and associated sampling parameters (sample points and lengths) into a single object, typically implemented as a collection of aligned tensors. It solves the problem of managing batched ray data for volume rendering and neural rendering pipelines, allowing efficient vectorized operations and memory transfers. It differs from a [RayBatch container](4187-raybatch-container.md) by explicitly bundling sampling metadata (sample points/lengths) alongside geometric ray data, and from a [Hit Record Structure](4953-hit-record-structure.md) by focusing on input ray generation rather than output intersection results.

## How it works
### Inputs and Outputs
- **Inputs**: Tensors for ray origins, ray directions, sample points along rays, and distances of sample points from origins.
- **Outputs**: A structured object (class instance) containing these tensors, supporting indexing, reshaping, and device transfer.

### Data Structures
The `RayBundle` class wraps four per-ray tensors [S2, S3, unofficial]:
1.  `origins`: Tensor of shape $(N, 3)$, where $N$ is the number of rays. Stores the 3D coordinates of ray origins [S1, S3, unofficial].
2.  `directions`: Tensor of shape $(N, 3)$. Stores the normalized direction vectors of the rays [S1, S3, unofficial].
3.  `sample_points`: Tensor of shape $(N, n_{pts}, 3)$, where $n_{pts}$ is the number of sample points per ray. Stores the 3D coordinates of sample points along each ray [S1, S3, unofficial].
4.  `sample_lengths`: Tensor of shape $(N, n_{pts}, 1)$. Stores the distance of each sample point from the ray origin [S1, S3, unofficial].

### Numbered Steps
1.  **Initialization**: Create a `RayBundle` instance by passing the four tensors (`origins`, `directions`, `sample_points`, `sample_lengths`) to the constructor [S1, S3, unofficial].
2.  **Indexing**: Access a subset of rays using `__getitem__(idx)`. This returns a new `RayBundle` with sliced tensors for all four fields at index `idx` [S3, unofficial].
3.  **Reshaping**: Use the `reshape` method to change the batch dimensions while preserving the last dimensions: origins and directions to `(*args, 3)`, sample points to `(*args, n_{pts}, 3)`, and sample lengths to `(*args, n_{pts}, 1)` [S1, S3, unofficial].
4.  **Viewing**: Use the `view` method to return a new `RayBundle` with viewed tensors, preserving the same last dimension constraints as `reshape` [S3, unofficial].
5.  **Replacement**: Use `_replace(**kwargs)` to update specific attributes (e.g., origins) and return the modified bundle [S3, unofficial].
6.  **Device Transfer**: Use `to(device)` to move all tensors to a specified device (e.g., GPU) [S2, unofficial].
7.  **Property Access**:
    -   `shape`: Returns `origins.shape[:-1]`, representing the batch dimensions [S3, unofficial].
    -   `sample_shape`: Returns `sample_points.shape[:-1]`, representing the batch and sample dimensions [S3, unofficial].
    -   `device`: Returns `sample_points.device` [S3, unofficial].

### Formulas
-   **Camera-Space Directions**: For a camera with width $W$, height $H$, and focal length $f$, pixel coordinates $(i, j)$ are used to compute camera-space directions:
    $$ x = \frac{i - W/2}{f} $$
    $$ y = -\frac{j - H/2}{f} $$
    $$ z = -1 $$
    [S4, unofficial]
-   **World-Space Directions**: Transform camera-space directions to world space using the rotation matrix $R$ from the camera-to-world transform, then normalize:
    $$ \mathbf{d}_{world} = \text{normalize}(R \cdot [x, y, z]^T) $$
    [S4, unofficial]
-   **Ray Origins**: Set to the camera position extracted from the camera-to-world matrix [S4, unofficial].

### Parameters
-   $N$: Number of rays (batch size). Not given in the sources.
-   $n_{pts}$: Number of sample points per ray. Not given in the sources.
-   $W, H$: Image width and height. Not given in the sources.
-   $f$: Focal length. Not given in the sources.

### Edge Cases and Pitfalls
-   **Precision**: Tensor operations assume standard floating-point precision. No specific pitfalls mentioned.
-   **Boundaries**: The `reshape` and `view` methods must preserve the last dimensions (3 for origins/directions/sample points, 1 for sample lengths). Mismatched dimensions will cause errors [S1, S3, unofficial].
-   **Degenerate Input**: Empty tensors or mismatched batch sizes between origins, directions, sample points, and sample lengths will cause initialization or indexing failures [S3, unofficial].

### Pseudocode
```python
import torch

class RayBundle:
    def __init__(self, origins: torch.Tensor, directions: torch.Tensor, 
                 sample_points: torch.Tensor, sample_lengths: torch.Tensor):
        """
        Initialize a RayBundle with ray data.
        
        Args:
            origins: Tensor of shape (N, 3)
            directions: Tensor of shape (N, 3)
            sample_points: Tensor of shape (N, n_pts, 3)
            sample_lengths: Tensor of shape (N, n_pts, 1)
        """
        self.origins = origins
        self.directions = directions
        self.sample_points = sample_points
        self.sample_lengths = sample_lengths

    @property
    def shape(self):
        """Returns the batch dimensions."""
        return self.origins.shape[:-1]

    @property
    def sample_shape(self):
        """Returns the batch and sample dimensions."""
        return self.sample_points.shape[:-1]

    @property
    def device(self):
        """Returns the device of the sample_points tensor."""
        return self.sample_points.device

    def __getitem__(self, idx):
        """Returns a new RayBundle with sliced tensors."""
        return RayBundle(
            origins=self.origins[idx],
            directions=self.directions[idx],
            sample_points=self.sample_points[idx],
            sample_lengths=self.sample_lengths[idx]
        )

    def reshape(self, *args):
        """Reshapes tensors, preserving last dimensions."""
        new_origins = self.origins.reshape(*args, 3)
        new_directions = self.directions.reshape(*args, 3)
        new_sample_points = self.sample_points.reshape(*args, self.sample_points.shape[-2], 3)
        new_sample_lengths = self.sample_lengths.reshape(*args, self.sample_lengths.shape[-2], 1)
        return RayBundle(new_origins, new_directions, new_sample_points, new_sample_lengths)

    def view(self, *args):
        """Views tensors, preserving last dimensions."""
        new_origins = self.origins.view(*args, 3)
        new_directions = self.directions.view(*args, 3)
        new_sample_points = self.sample_points.view(*args, self.sample_points.shape[-2], 3)
        new_sample_lengths = self.sample_lengths.view(*args, self.sample_lengths.shape[-2], 1)
        return RayBundle(new_origins, new_directions, new_sample_points, new_sample_lengths)

    def _replace(self, **kwargs):
        """Updates attributes based on kwargs."""
        for key, value in kwargs.items():
            if hasattr(self, key):
                setattr(self, key, value)
        return self

    def to(self, device):
        """Moves all tensors to the specified device."""
        return RayBundle(
            origins=self.origins.to(device),
            directions=self.directions.to(device),
            sample_points=self.sample_points.to(device),
            sample_lengths=self.sample_lengths.to(device)
        )
```

## Subtopics

### 2D Skewed Buffer
A 2D temporary buffer used to store slanted Projection Ray Planes (PRPs), allowing parallel access for storing horizontal beams and parallel retrieval of vertical viewing rays [S5]. It is physically divided into $n$ modules and diagonally skewed to allow conflict-free writing of an entire horizontal beam and conflict-free retrieval of an entire vertical ray [S5]. The slanted PRP is loaded one beam at a time, from closest to furthest, with each beam shifted left or right to align viewing rays vertically [S5]. Retrieved vertical rays are transferred to the Ray Projection Tree (RPT), shifting rays during transfer to position the closest voxel correctly [S5]. Pitfalls include neighborhood access (requiring multiple parallel 2DSBs and processing rays only after the succeeding slanted PRP is loaded) and pipeline overlap (using a fourth plane to load the next slanted PRP while three extract the 27-voxel cube) [S5].

## Operating characteristics
-   **Time Complexity**: Not given in the sources.
-   **Memory Complexity**: Linear in the number of rays $N$ and sample points per ray $n_{pts}$, specifically $O(N \cdot n_{pts})$ for sample points and lengths, and $O(N)$ for origins and directions [S1, S3, unofficial].
-   **Measured Performance**: Not given in the sources.
-   **Scaling**: Scales with batch size $N$ and number of samples $n_{pts}$ [S1, S3, unofficial].
-   **Strengths**: Efficient vectorized operations, easy indexing and reshaping, device transfer support [S2, S3, unofficial].
-   **Limitations**: Requires careful dimension management during reshape/view operations [S1, S3, unofficial].
-   **When to Use**: When managing batched ray data for volume rendering or neural rendering pipelines [S1, S3, unofficial].
-   **When Not to Use**: When individual ray processing is required without batching, or when memory constraints are tight and $N \cdot n_{pts}$ is very large [G].

## Background
The Ray Bundle data structure is commonly used in modern neural rendering and volume rendering frameworks, such as those based on VolSDF and NeRF [S1, S3, unofficial]. It facilitates the efficient handling of ray data for differentiable rendering [S3, unofficial]. The 2D Skewed Buffer variant originates from hardware-based volume visualization systems for arbitrary parallel projection, designed to handle slanted projection ray planes efficiently [S5].
