# Octree-based Volume Rendering

Also called: Chamberlain's algorithm, LaMar's algorithm, Octree Approach (Baseline), Weiler's smoothing

## Overview
Octree-based Volume Rendering is a baseline image-order rendering method that uses a hierarchical octree structure to subdivide volumetric data for spatial culling and level-of-detail (LOD) selection [S1, unofficial][S2]. It solves the problem of efficiently rendering large volumetric datasets by skipping empty space and approximating distant or small regions with coarser nodes [S1, unofficial][S2]. Unlike residency-based methods that manage cache explicitly, this approach relies on a one-to-one mapping of data bricks to octree nodes, requiring entire subtrees to be resident in memory for high-resolution regions [S2].

## How it works
**Inputs:** Volumetric dataset (often pre-bricked), camera parameters (position, field-of-view), transfer functions, and a predefined projection size threshold.
**Outputs:** Rendered image.

**Data Structures:**
*   **Octree:** A tree where each internal node has 8 children (2x2x2 subdivision).
*   **Bricks:** Blocks of volumetric data mapped one-to-one to octree nodes [S2].
*   **Cache:** Memory holding the currently active octree nodes and their associated bricks [S2].

**Steps:**

1.  **Preprocessing:** Perform octree subdivision of the volumetric data. Assign bricks to nodes such that each node corresponds to a specific block of the volume [S1, unofficial][S2].
2.  **Rendering Loop (Per Sample/Ray):**
    1.  **Traversal Start:** Begin traversal at the third level of the octree. Resume from the parent node of the last visited sample's node to optimize performance, rather than restarting at the root [S2].
    2.  **Selection (Chamberlain):** Compute the projected size of each octree node on the fly. If the projected size is smaller than a predefined threshold, consider the node sufficiently accurate to approximate all nodes below it [S1, unofficial].
    3.  **Selection (LaMar):** Apply two criteria:
        *   **Distance:** Similar to Chamberlain, based on projected size.
        *   **Field-of-View:** Discard nodes that do not intersect the view frustum. Select nodes whose projected angle is less than half the field-of-view angle [S1, unofficial].
    4.  **Culling:** Skip nodes that fail the selection criteria or are outside the view frustum [S1, unofficial].
    5.  **Rendering:** For selected nodes, perform volume integration (e.g., ray marching) through the associated brick data [S1, unofficial].
    6.  **Multi-Channel Handling:** If rendering multiple channels, traverse the octree separately for each channel to guarantee all required subtrees remain cache resident [S1, unofficial][S2].
3.  **Smoothing (Optional):** Apply Weiler's smoothing technique to reduce discontinuity artifacts at LOD boundaries caused by inconsistencies of the view-plane at different levels of detail [S1, unofficial].

**Pseudocode:**
```python
def render_octree_volume(scene, camera, transfer_functions):
    # scene.octree: Root of the octree structure
    # scene.bricks: Dictionary mapping node_id to voxel data block
    # cache: Set of currently resident node_ids
    
    # Preprocessing is assumed complete; octree is built and bricks assigned
    
    for each pixel (x, y):
        ray = camera.generate_ray(x, y)
        accumulated_color = 0.0
        accumulated_transmittance = 1.0
        
        # Start traversal from the parent of the last visited node for this ray
        # or from level 3 if first visit
        current_node = get_start_node(ray, last_visited_node)
        
        while current_node is not None:
            # Compute projected size of the node
            projected_size = compute_projected_size(current_node, camera)
            
            # Chamberlain/LaMar Selection Criteria
            if projected_size > threshold:
                # Node is too large; traverse children
                children = get_children(current_node)
                if children:
                    current_node = children[0] # Pick first child to descend
                    continue
                else:
                    # Leaf node, render it
                    render_brick(current_node, ray, accumulated_color, accumulated_transmittance)
                    current_node = get_next_node(current_node, ray)
            else:
                # Node is small enough to approximate
                render_approximation(current_node, ray, accumulated_color, accumulated_transmittance)
                current_node = get_next_node(current_node, ray)
                
            # Ensure subtree residency for multi-channel if needed
            if multi_channel:
                ensure_subtree_resident(current_node, cache)

def ensure_subtree_resident(node, cache):
    # Load all descendants of node into cache if not present
    for child in get_all_descendants(node):
        if child.id not in cache:
            load_bricks_for_node(child, cache)
```

**Parameters:**
*   **Threshold:** Predefined threshold for projected size. Not given in the sources.
*   **Start Level:** 3 (third level of octree) [S2].
*   **FOV Criterion:** Projected angle < half field-of-view angle [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **LOD Artifacts:** Substantial visual artifacts appear at boundaries of different levels of detail due to inconsistencies of the view-plane at different levels of detail [S1, unofficial].
*   **Memory Overhead:** Rendering high-resolution regions requires entire subtrees to be resident in cache, increasing memory overhead. This is exacerbated by anisotropic volumes or 2D downsampling, where the overhead ratio is 1/3 vs 1/7 for isotropic cases [S2].
*   **Multi-Channel Cost:** Higher computational cost and memory footprint in multi-channel scenarios due to per-channel tree traversal and subtree residency requirements [S2].
*   **Memory Limit:** Inability to reduce volumetric data size in main memory limits rendering of datasets larger than main memory size [S1, unofficial].

## Subtopics

### [Octree-based Volume Rendering with Wavelet Leaves](6683-octree-based-volume-rendering-with-wavelet-leaves.md)
A volume rendering technique using an octree data structure for space subdivision, where leaf nodes store volume data in a multi-resolution wavelet format to enable efficient traversal, early termination, and progressive refinement.

### PlenOctree Rendering
A method for real-time rendering of Neural Radiance Fields (NeRFs) by converting a trained NeRF-SH model into a sparse octree representation [S3, unofficial].
*   **Mechanism:** For each ray, determine ray-voxel intersections in the octree structure, producing a sequence of segments between voxel boundaries with constant density and color, of lengths $\{\delta_i\}$ [S3, unofficial].
*   **Early-Stopping:** Stop rendering when the accumulated transmittance $T_i$ is less than $\gamma = 0.01$ [S3, unofficial].
*   **Rendering Formula:** Apply NeRF's volume rendering model:
    $$ C(r) = \sum_{i=0}^{N} T_i (1 - \exp(-\sigma_i \cdot \delta_i)) c_i $$
    where $T_i = \exp(-\sum_{j=0}^{i-1} \sigma_j \cdot \delta_j)$ [S3, unofficial].
*   **Performance:** Fine-tuned PlenOctree models achieve significantly faster rendering times (e.g., 42.22 ms/frame) compared to existing methods while maintaining comparable image metrics on scenes like Tanks and Temples [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** Depends on the tree traversal and the density of the volume. For dense volumes, the overhead of traversing a tree is not compensated by empty space skipping, leading to performance comparable to or worse than non-hierarchical methods [S2].
*   **Memory Complexity:** High memory footprint for high-resolution regions due to the requirement of keeping entire subtrees resident in cache [S2]. Overhead ratio is 1/3 for 2D downsampling/anisotropic volumes and 1/7 for isotropic cases [S2].
*   **Performance:** Outperforms other approaches for sparse volumes (e.g., Kingsnake, Beechnut, 3DNeurons) and large numbers of channels (e.g., CyCIF Small) when combined with residency management [S2]. For dense volumes, it may suffer from higher computational cost [S2].
*   **Strengths:** Effective for sparse volumes; simple hierarchical culling; supports LOD via projection size/FOV criteria [S1, unofficial][S2].
*   **Limitations:** Poor performance on dense volumes; high memory usage for multi-channel rendering; visual artifacts at LOD boundaries; limited by main memory size [S1, unofficial][S2].
*   **When to Use:** Sparse volumetric datasets; single-channel rendering; scenarios where empty space skipping is effective [S2].
*   **When Not to Use:** Dense volumetric datasets; multi-channel rendering with high memory constraints; datasets larger than main memory [S1, unofficial][S2].

## Background
The octree spatial hierarchy was first proposed by Chamberlain et al. for rendering surface geometry, later adapted for volume rendering [S1, unofficial]. LaMar et al. developed a similar technique with improved selection criteria based on distance and field-of-view [S1, unofficial]. Weiler et al. proposed extensions to smooth discontinuity artifacts at LOD boundaries [S1, unofficial]. The method is a baseline for comparing newer residency-based and hybrid approaches [S2]. Wavelet-based leaf storage has been explored as a frequency domain analysis method for volumetric data [S1, unofficial].
