# Hierarchical and Block-Based Data Structures

Also called: Block-based Data Structures, Hierarchical Grid Structures, Spatial Subdivision Hierarchies

## Overview
Hierarchical and Block-Based Data Structures provide a spatial subdivision framework for volume rendering, enabling efficient traversal and culling of empty or inactive regions during ray marching. Unlike flat voxel grids, these structures organize data into a tree where internal nodes store aggregate properties (e.g., occupancy, scalar ranges) derived from their children, allowing rays to skip large inactive subtrees [4133-hierarchical-data-structures]. This family encompasses methods that vary in their spatial representation (octrees, pyramids, image-space mipmaps) and traversal order (image-order, object-order, or hybrid). It sets itself apart from sibling methods by focusing on the *data organization* strategy (hierarchical blocks/trees) rather than the specific traversal algorithm (e.g., HDDA) or hardware acceleration mechanism (e.g., RTX BVH) used to navigate it.

## Shared principles
All methods in this family rely on a spatial subdivision hierarchy where internal nodes store aggregate information derived from their children or leaf voxels. The core mechanism is:
1.  **Aggregation:** Leaf nodes encode voxel properties. Internal nodes aggregate these properties (e.g., binary occupancy, min/max scalar ranges) from their children.
2.  **Pruning:** During ray traversal, if a node indicates an empty or inactive region (e.g., occupancy flag is 0, or min/max bounds are outside the transfer function's opacity range), the entire subtree is skipped.
3.  **Construction:** The hierarchy is typically constructed bottom-up. The depth is determined by data dimensions, often requiring padding to powers of two or specific size constraints to maintain regular subdivision [2560-hierarchical-grid-traversal].

## Subtopics

### [Ray-marching reference (min-max octree accelerated)](1554-ray-marching-reference-min-max-octree-accelerated.md)
This method is an accelerated direct isosurface visualization technique that uses a min-max octree to facilitate empty space skipping during ray marching [1554-ray-marching-reference-min-max-octree-accelerated]. It serves as a performance baseline for general volumes, offering negligible memory overhead for the input volume and low auxiliary data requirements [1554-ray-marching-reference-min-max-octree-accelerated]. Unlike Sphere Tracing, which requires precomputed signed distance functions, or Segment Tracing, which is limited to hierarchical skeletal implicit surfaces, this approach is applicable to a wide range of scalar volumes [1554-ray-marching-reference-min-max-octree-accelerated]. It guarantees continuous isosurfaces that locally interpolate the input data, unlike mesh extraction techniques (e.g., marching cubes) which may produce topologically different piecewise linear meshes [1554-ray-marching-reference-min-max-octree-accelerated].

### [ExaBricks Rendering with RTX BVH](2577-exabricks-rendering-with-rtx-bvh.md)
ExaBricks Rendering with RTX BVH is a method for rendering Adaptive Block-Refined (ABR) volume data that leverages hardware-accelerated ray-tracing cores (RT Cores) to traverse a Bounding Volume Hierarchy (BVH) of data regions [2577-exabricks-rendering-with-rtx-bvh]. It solves the problem of efficiently navigating hierarchical AMR structures by replacing software-based k-d tree traversal with dedicated hardware traversal, thereby avoiding complex control flow in shaders [2577-exabricks-rendering-with-rtx-bvh]. It sets itself apart from sibling methods like [Ray-marching reference (min-max octree accelerated)](1554-ray-marching-reference-min-max-octree-accelerated.md) by using a BVH of pre-computed regions rather than an octree of voxels, and from [Hierarchical Data Structures](4133-hierarchical-data-structures.md) by offloading the traversal logic to GPU hardware [2577-exabricks-rendering-with-rtx-bvh].

### [Residency Octree](4950-residency-octree.md)
The Residency Octree is a hybrid data structure for out-of-core direct volume rendering (DVR) of large-scale, multi-channel volumetric datasets [4950-residency-octree]. It solves the problem of limited GPU memory and inefficient cache usage by decoupling the spatial subdivision of the octree from the resolution levels of the underlying bricked volume hierarchy [4950-residency-octree]. Unlike standard octrees where each node maps to exactly one brick (one-to-one correspondence), a Residency Octree node represents a geometric spatial region and maps to a set of bricks across all resolution levels [4950-residency-octree]. This allows the renderer to adaptively mix resolutions, substitute missing high-resolution data with available lower-resolution data, and perform fine-grained empty-space skipping independent of the data's bricking granularity [4950-residency-octree]. It combines the flexible, multi-resolution access of page-table hierarchies with the efficient traversal and culling of octrees [4950-residency-octree].

### [Multiresolution with Octree Bricking](6106-multiresolution-with-octree-bricking.md)
Multiresolution with Octree Bricking is a data representation and rendering technique for large volumetric datasets that provides high-fidelity results in regions of interest while maintaining the context of the whole volume at a lower resolution [6106-multiresolution-with-octree-bricking]. It sets itself apart from siblings like [Ray-marching reference (min-max octree accelerated)](1554-ray-marching-reference-min-max-octree-accelerated.md) by explicitly structuring the volume into hierarchical "bricks" (sub-volumes) rather than just using occupancy flags for pruning, allowing for adaptive resolution based on spatial locality [6106-multiresolution-with-octree-bricking].

### [Brick Size and Octree Limit Tuning](4263-brick-size-and-octree-limit-tuning.md)
Brick Size and Octree Limit Tuning is a method for optimizing GPU-based volume rendering by selecting optimal parameters for spatial subdivision and hardware texture storage. It addresses the trade-off between rasterization overhead, triangle throughput, and cache efficiency inherent in hierarchical grid traversal. It differs from sibling methods by focusing specifically on the empirical selection of brick dimensions and octree depth limits to mitigate hardware-specific bottlenecks, such as ATi's 3D texture sampling penalties [4263-brick-size-and-octree-limit-tuning].

## Background
The concept of hierarchical data structures for volume rendering emerged in the early 2000s as a response to the memory and computational demands of large volumetric datasets. Early work focused on octrees and min-max structures to enable empty space skipping [1554-ray-marching-reference-min-max-octree-accelerated]. The introduction of GPU hardware accelerated the adoption of block-based rendering, where volumes are subdivided into bricks to optimize texture cache usage [4263-brick-size-and-octree-limit-tuning]. More recent developments leverage hardware ray-tracing cores (RTX) to traverse these hierarchical structures more efficiently, moving traversal logic from software shaders to dedicated hardware [2577-exabricks-rendering-with-rtx-bvh]. These methods are widely used in medical imaging (e.g., CT datasets) and scientific visualization where large, multi-resolution datasets are common [4950-residency-octree][4263-brick-size-and-octree-limit-tuning].
