# Residency Octree Update

Also called: Incremental Construction

## Overview
Residency Octree Update is a fully GPU-implemented parallel method for the incremental construction and maintenance of a multi-channel residency octree during out-of-core direct volume rendering. It solves the problem of keeping hierarchical occupancy and culling data consistent with dynamic cache additions and evictions without CPU intervention. Unlike static octree construction, this approach updates nodes only when bricks are added or removed from the brick cache, using bitmap propagation to minimize redundant writes. It sets itself apart from [Octree-based memory virtualization](5140-octree-based-memory-virtualization.md) by focusing on the specific mechanism of updating the residency metadata itself, and from [Mixed-Resolution Multi-Volume Renderer](5215-mixed-resolution-multi-volume-renderer.md) by handling the data structure maintenance rather than the ray sampling logic.

## How it works
The method operates on a multi-channel residency octree where nodes store culling metadata (min/max values) and a bitmask of partially mapped resolution levels. The update process is triggered after the frame's brick-cache update is completed.

### Inputs and Outputs
*   **Inputs:**
    *   List of added brick IDs (newly resident).
    *   List of removed brick IDs (evicted from cache).
    *   Current state of the brick cache (residency status).
    *   Scalar voxel data for new bricks (for culling metadata).
*   **Outputs:**
    *   Updated residency octree nodes (culling metadata and partial residency bitmasks).
    *   Update-candidate buffer (cleared or populated for next iteration).

### Data Structures
*   **Residency Octree Node:**
    *   `min_value`: Scalar minimum of all voxels in the node's spatial extent across all channels/resolutions.
    *   `max_value`: Scalar maximum of all voxels in the node's spatial extent across all channels/resolutions.
    *   `partial_residency_mask`: Bitmask where each bit represents a resolution level. A bit is set if at least one brick at that resolution level is resident in the cache within the node's spatial extent.
*   **Update-Candidate Buffer:**
    *   A dynamic list or buffer storing node indices that require recomputation in the next level up.
*   **Brick Cache:**
    *   Maps brick IDs to their residency status and spatial location.

### Numbered Steps
1.  **Initialization:** Start timing. Identify all added and removed brick IDs from the previous frame's cache update. Initialize an empty update-candidate buffer.
2.  **Process Removed Bricks:**
    *   For each removed brick ID, determine the corresponding leaf nodes in the residency octree whose spatial extent overlaps the brick's extent.
    *   For each such leaf node, check if it is still partially mapped in the removed brick's resolution level. This is done by verifying if any other brick at that resolution level within the node's extent is still resident.
    *   If the node is no longer partially resident in that resolution, update its `partial_residency_mask` (clear the corresponding bit).
    *   Mark the parent node of the updated leaf node as an update candidate in the buffer.
3.  **Compute Culling Metadata for New Bricks:**
    *   For each scalar value in each newly added brick, determine the corresponding leaf node in the residency octree.
    *   Compare the scalar value with the node's current `min_value` and `max_value`.
    *   If the value is lower than `min_value`, update `min_value` using `atomicMin`. If greater than `max_value`, update `max_value` using `atomicMax`. Concurrent updates to the same node are handled by these atomic operations.
    *   Mark the parent node of the updated leaf node as an update candidate in the buffer.
4.  **Process Added Bricks:**
    *   For each added brick, determine all corresponding leaf nodes in the residency octree whose spatial extent overlaps the brick's extent.
    *   Mark these leaf nodes as partially mapped in the brick's resolution level by setting the corresponding bit in their `partial_residency_mask`.
    *   If the `partial_residency_mask` of a leaf node changed due to this operation, mark its parent node as an update candidate in the buffer.
5.  **Compile Candidates:**
    *   Process the update-candidate buffer to compile a unique list of all nodes marked as candidates for the next level up.
    *   Clear the update-candidate buffer for subsequent iterations.
    *   If the candidate list is empty, terminate the update process.
    *   Use the count of candidates to control the number of workgroups dispatched for the next indirect compute pass.
6.  **Process Update Candidates (Upward Propagation):**
    *   For each candidate node, recompute its `min_value`, `max_value`, and `partial_residency_mask` from its child nodes.
    *   `partial_residency_mask` is updated via bitwise OR of the child node bitmasks: $B_{parent} = B_{child1} \lor B_{child2} \lor ... \lor B_{child8}$.
    *   `min_value` is updated via `atomicMin` of child `min_value`s.
    *   `max_value` is updated via `atomicMax` of child `max_value`s.
    *   If any of the node's values (`min_value`, `max_value`, or `partial_residency_mask`) changed by this operation, mark the node's parent as an update candidate in the buffer.
7.  **Repeat:** Repeat Steps 5 and 6 until the root node is reached or no update candidates remain.

### Pseudocode
```python
def residency_octree_update(added_bricks, removed_bricks, brick_cache, octree):
    # Step 1: Initialize
    candidate_buffer = []
    
    # Step 2: Process Removed Bricks
    for brick_id in removed_bricks:
        leaf_nodes = get_leaf_nodes_for_brick(brick_id, octree)
        for leaf in leaf_nodes:
            resolution = brick_id.resolution
            if not is_partially_resident(leaf, resolution, brick_cache):
                clear_bit(leaf.partial_residency_mask, resolution)
                add_parent_to_candidates(leaf.parent, candidate_buffer)
                
    # Step 3: Compute Culling Metadata for New Bricks
    for brick_id in added_bricks:
        leaf_nodes = get_leaf_nodes_for_brick(brick_id, octree)
        for leaf in leaf_nodes:
            # Update min/max using atomic operations
            atomic_min(leaf.min_value, brick_id.min_scalar)
            atomic_max(leaf.max_value, brick_id.max_scalar)
            add_parent_to_candidates(leaf.parent, candidate_buffer)
            
    # Step 4: Process Added Bricks
    for brick_id in added_bricks:
        leaf_nodes = get_leaf_nodes_for_brick(brick_id, octree)
        for leaf in leaf_nodes:
            resolution = brick_id.resolution
            old_mask = leaf.partial_residency_mask
            set_bit(leaf.partial_residency_mask, resolution)
            if leaf.partial_residency_mask != old_mask:
                add_parent_to_candidates(leaf.parent, candidate_buffer)
                
    # Step 5: Compile Candidates
    unique_candidates = deduplicate(candidate_buffer)
    candidate_buffer.clear()
    
    if not unique_candidates:
        return
        
    # Step 6 & 7: Process Candidates Upward
    current_level_candidates = unique_candidates
    while current_level_candidates:
        next_level_candidates = []
        
        for node in current_level_candidates:
            # Recompute from children
            old_min = node.min_value
            old_max = node.max_value
            old_mask = node.partial_residency_mask
            
            # Recompute min/max
            node.min_value = min(child.min_value for child in node.children)
            node.max_value = max(child.max_value for child in node.children)
            
            # Recompute bitmask
            node.partial_residency_mask = 0
            for child in node.children:
                node.partial_residency_mask |= child.partial_residency_mask
                
            # Check for changes
            if (node.min_value != old_min or 
                node.max_value != old_max or 
                node.partial_residency_mask != old_mask):
                if node.parent is not None:
                    add_parent_to_candidates(node.parent, next_level_candidates)
                    
        current_level_candidates = deduplicate(next_level_candidates)
```

### Parameters
*   **Brick Size:** Typically $32^3$ voxels [S1, unofficial].
*   **Leaf-Node Size:** Can be decoupled from brick size. Tested sizes include $32^3$, $16^3$, $8^3$, and anisotropic $8 \times 8 \times 4$ [S1, unofficial].

### Edge Cases and Pitfalls
*   **Concurrent Updates:** Multiple threads may update the same node's culling metadata concurrently. Atomic operations (`atomicMin`, `atomicMax`) are required for min/max values [S1, unofficial].
*   **Early Termination:** Upwards propagation terminates early if a node's bitmask remains unchanged by the OR operation, preventing unnecessary recomputation of parent nodes [S2].
*   **Boundary Conditions:** Ensure that leaf nodes are correctly identified for bricks at the boundaries of the volume. The spatial extent overlap check must be robust to avoid missing updates or processing non-overlapping nodes.
*   **Resolution Mismatch:** If the residency octree's leaf-node size is decoupled from the brick size, the mapping from brick to leaf nodes must account for the different granularities [S1, unofficial].

## Subtopics

### [Residency-Octree Updates](5552-residency-octree-updates.md)
This method manages the parallel construction and maintenance of a multi-channel residency octree on the GPU, ensuring that spatial culling information accurately reflects the current state of the brick cache. It solves the problem of keeping hierarchical occupancy data consistent with dynamic cache additions and evictions without CPU intervention. Unlike static octree construction, this approach updates nodes only when bricks are added or removed, using bitmap propagation to minimize redundant writes.

### Decoupling Resolution Levels from Spatial Subdivision
An optimization technique where the spatial subdivision granularity (leaf-node size) of the residency octree is decoupled from the resolution levels of the bricked volume hierarchy, allowing finer empty-space skipping than the bricking granularity. It uses a brick size of $32^3$ voxels but allows different approximate leaf-node sizes for the residency octree ($32^3$, $16^3$, $8^3$, or $8 \times 8 \times 4$). This allows efficient empty-space skipping with finer granularity than bricking, potentially achieving higher frame rates, and is beneficial for anisotropic volumes. [S1, unofficial]

## Operating characteristics
*   **Time Complexity:** The update process is proportional to the number of changed bricks and the height of the octree. The breadth-first propagation with early termination ensures that only affected paths are updated. The use of atomic operations for culling metadata adds some overhead but ensures correctness.
*   **Memory Complexity:** Requires storage for the octree nodes (min, max, bitmask) and the update-candidate buffer. The buffer size is bounded by the number of changed bricks and the octree height.
*   **Measured Performance:** The method is fully GPU-implemented, leveraging parallel compute shaders. Performance scales with the number of visible channels and the efficiency of the brick cache. Decoupling leaf-node size from brick size can improve frame rates by enabling finer empty-space skipping [S1, unofficial].
*   **Strengths:** Fully GPU-based, no CPU intervention, efficient incremental updates, early termination reduces redundant work.
*   **Limitations:** Requires atomic operations for culling metadata, which can cause contention. The effectiveness depends on the spatial locality of brick changes.
*   **When to Use:** Suitable for out-of-core direct volume rendering where the brick cache is dynamic and updates are frequent. Particularly useful when the spatial subdivision can be optimized independently of the data resolution.
*   **When Not to Use:** If the volume is static and fits entirely in memory, a static octree construction may be simpler. If the brick cache is rarely updated, the overhead of incremental updates may not be justified.

## Background
The Residency Octree Update method was introduced as part of the Residency Octree framework for scalable web-based volume rendering of large biomedicine datasets. It addresses the challenges of out-of-core rendering by maintaining an efficient hierarchical data structure for spatial culling and residency management. The method was evaluated on datasets such as CyCIF Small and CyCIF Medium, demonstrating its effectiveness in handling multi-channel volumes with varying resolutions. The decoupling of spatial subdivision from resolution levels was shown to provide performance benefits, particularly for anisotropic volumes.
