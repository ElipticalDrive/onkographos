# Residency Octree

Also called: Residency-Octree Hierarchy, hybrid data structure for out-of-core volume rendering, multi-resolution page tables combined with a special octree data structure

## Overview
The Residency Octree is a hybrid data structure for out-of-core direct volume rendering (DVR) of multi-volume datasets that decouples the cache residency of multi-resolution data from the spatial subdivision determined by the octree tree structure [S1, unofficial][S2]. Unlike standard octrees where each node represents exactly one brick (one-to-one node-to-brick correspondence), each residency octree node represents a resolution-independent spatial region and references all resolution levels in a bricked volume hierarchy [S2]. This allows efficient mixing of channel resolutions and substituting alternative resolutions on cache misses by adaptively choosing and mixing resolutions, adapting sampling rates, and compensating for cache misses [S2]. It combines the advantages of page-table hierarchies (flexible mixed-resolution access) with octrees (efficient empty-space skipping) [S1, unofficial][S2].

## How it works
**Inputs and Outputs:**
*   **Input:** A bricked multi-resolution multi-volume hierarchy with $n$ channels. The brick size in voxels (e.g., $32^3$) is fixed and identical across all resolution levels in the bricked volume hierarchy, independent of the brick's spatial extent [S2].
*   **Output:** A residency octree data structure stored in GPU memory, enabling ray-guided traversal for rendering [S2].

**Data Structures:**
The residency octree is implemented as a full, pointerless octree where all nodes are pre-allocated with fixed locations in a storage buffer to remove indirection and simplify data management [S1, unofficial].

*   **Node Layout:** Each node consists of $m$ unsigned 32-bit integers, where $m$ is the number of channels currently visualized ($m \le n$) [S1, unofficial].
    *   For each channel, the 32-bit integer is structured as follows:
        *   **16 bits:** Bitmap indicating which resolution levels the node is at least partially mapped in [S1, unofficial].
        *   **8 bits:** Minimum scalar value in the spatial region represented by the node [S1, unofficial].
        *   **8 bits:** Maximum scalar value in the spatial region represented by the node [S1, unofficial].
    *   *Note:* In multi-channel extensions, if channel information is invalid (not yet initialized), the metadata is replaced by a pointer to the next lower subdivision level node with valid info for that channel, or a special `UNKNOWN` value [S1, unofficial].
*   **Backing Store:** Internally, the data structure is backed by a multi-channel page table hierarchy and a brick cache [S2]. The page table hierarchy references bricks of different resolution levels and channels [S1, unofficial].

**Node States:**
For a given octree node and a given resolution level, the node can be in one of three states [S1, unofficial]:
1.  **Fully mapped:** Cache-resident bricks of that level fully cover the node's spatial extent. If a node is fully mapped, all its children are also fully mapped in that level [S2].
2.  **Partially mapped:** At least one brick of that level spatially overlaps with the node's extent and is resident in the cache. If a node is partially mapped, its parent is also partially mapped [S2].
3.  **Not mapped:** No bricks of that level are resident [S1, unofficial].

**Algorithm Steps:**

1.  **Initialization:**
    *   The user specifies an approximate leaf-node size in voxels at initialization [S1, unofficial].
    *   The system iteratively subdivides the volume until a subdivision level is reached where the size of a node in voxels is lower or equal to the given leaf-node size in each dimension [S1, unofficial].
    *   At each subdivision level, each dimension is halved, resulting in eight children per node [S1, unofficial].
    *   The maximum number of channels $m$ that can be referenced simultaneously is set at initialization [S2].

2.  **Incremental Construction (Metadata):**
    *   When new metadata for a volume region is received, the corresponding octree node is created or updated [S2].
    *   If created, metadata is initialized as `INVALID` for all channels except the one for which metadata was received [S2].
    *   Residency info is initialized for that channel by checking if the node is partially mapped in each resolution level [S2].
    *   Metadata for a parent node is computed from its children: the parent's minimum and maximum are the minimum and maximum values of its children's respective values [S1, unofficial]. This allows parallel bottom-up construction [S1, unofficial].
    *   *Pitfall:* If the server does not support metadata queries, metadata must be computed on the fly from brick data. A minimum number of voxels must be specified to avoid inaccuracies from too few voxels (e.g., only a single voxel taken into account due to coarse resolution) [S1, unofficial].

3.  **Incremental Construction (Residency):**
    *   When a new brick is received, an available slot in the brick cache is selected [S2].
    *   All residency octree leaf nodes whose spatial extent overlaps the brick's spatial extent are marked as partially mapped in the brick's resolution level and channel [S2].
    *   This update is propagated up the tree to the root node [S2].

4.  **Ray Traversal:**
    *   Ray traversal is performed for spatial regions corresponding to octree nodes instead of bricks, and this traversal is independent of the number of channels [S2].
    *   The renderer traverses the octree. If metadata or brick data is missing for a node, it generates a request to the server. This request is generated during ray traversal, making the method ray-guided [S2].
    *   At each subdivision level, the system checks the bitmap to see which resolution levels are mapped [S1, unofficial].
    *   If a node is empty or homogeneous (based on min/max metadata), it is implicitly considered fully mapped in all resolution levels during octree traversal, meaning its corresponding bricks do not need to be resident in the cache [S1, unofficial].
    *   The system keeps bricks of high-resolution levels resident if needed, without requiring lower-resolution bricks in the same region to be resident if unused [S1, unofficial].
    *   Optimization: Start traversal at the third level instead of the root, and resume from the parent node of the last visited node rather than restarting per sample [S2]. Traverse the octree only once per sample to minimize hierarchy traversal cost during multi-channel rendering [S2].

5.  **Channel Replacement:**
    *   If a channel is replaced by another one, all nodes storing valid data for the old channel are marked `INVALID` for the new channel [S1, unofficial].
    *   Residency octrees support changes to the selection of visible channels at run-time by replacing only the parts of their nodes related to the affected channels [S1, unofficial].

**Pseudocode:**

```python
# Data Structure Definition
class ResidencyOctreeNode:
    # Pre-allocated in a buffer. Index determines position.
    # m is the number of visualized channels.
    # Each channel uses 32 bits: 16 for resolution bitmap, 8 for min, 8 for max.
    channel_data: array[m] of uint32

    def get_min(self, channel_idx: int) -> uint8:
        return (self.channel_data[channel_idx] >> 8) & 0xFF

    def get_max(self, channel_idx: int) -> uint8:
        return self.channel_data[channel_idx] & 0xFF

    def get_resolution_bitmap(self, channel_idx: int) -> uint16:
        return (self.channel_data[channel_idx] >> 16) & 0xFFFF

    def set_metadata(self, channel_idx: int, min_val: uint8, max_val: uint8, resolution_bitmap: uint16):
        # Clear lower 24 bits, keep upper bits if needed for pointers in invalid state
        self.channel_data[channel_idx] = (self.channel_data[channel_idx] & 0xFF000000) | \
                                         (resolution_bitmap << 16) | \
                                         (max_val << 8) | \
                                         min_val

# Traversal Logic
def traverse_octree(ray: Ray, root_node: ResidencyOctreeNode, brick_cache: BrickCache):
    # Optimization: Start at level 3 if available, else root
    current_node = get_node_at_level(root_node, level=3)
    
    while current_node is not None:
        # Check empty space skipping using min/max metadata
        # Assuming single channel for simplicity of example, or loop over m channels
        min_val = current_node.get_min(0)
        max_val = current_node.get_max(0)
        
        if is_empty_or_homogeneous(min_val, max_val, transfer_function):
            # Implicitly fully mapped, skip subtree
            break
            
        # Check residency
        bitmap = current_node.get_resolution_bitmap(0)
        
        # Determine which resolution levels are available
        available_levels = get_set_bits(bitmap)
        
        if not available_levels:
            # Request missing bricks from server (ray-guided)
            request_bricks(current_node.spatial_extent, ray)
            # Continue traversal or wait for data
            continue
            
        # Select best resolution level (e.g., highest available)
        level = max(available_levels)
        
        # Access bricks via backing page table hierarchy
        bricks = brick_cache.get_bricks_for_node(current_node, level)
        
        if bricks are empty:
            # Cache miss, request specific bricks
            request_bricks(current_node.spatial_extent, level)
            continue
            
        # Render samples within this node's extent
        render_samples(ray, bricks, level)
        
        # Move to children if not leaf
        if not is_leaf(current_node):
            current_node = get_first_child(current_node)
        else:
            # Move to next sibling or parent's next sibling
            current_node = get_next_node_in_traversal_order(current_node)
```

## Subtopics

### [Octree-based memory virtualization](5140-octree-based-memory-virtualization.md)
An out-of-core rendering approach for multi-channel volume data sets where octree nodes and bricks store information on up to $n$ channels. It extends the single-channel scheme of Crassin et al. [CNLE09] by supporting multiple visible channels, solving the problem of managing brick residency and performing address translation for out-of-core volume rendering using a hierarchical tree structure. Unlike the Residency Octree, which uses a more compact representation, this method enforces that the whole subtree is resident in the cache for high-resolution rendering, leading to a higher memory footprint but comparable performance for single-channel data.

### [Residency Octree Update](5181-residency-octree-update.md)
Residency Octree Update is a fully GPU-implemented parallel method for the incremental construction and maintenance of a multi-channel residency octree during out-of-core direct volume rendering. It solves the problem of keeping hierarchical occupancy and culling data consistent with dynamic cache additions and evictions without CPU intervention. Unlike static octree construction, this approach updates nodes only when bricks are added or removed from the brick cache, using bitmap propagation to minimize redundant writes. It sets itself apart from [Octree-based memory virtualization](5140-octree-based-memory-virtualization.md) by focusing on the specific mechanism of updating the residency metadata itself, and from [Mixed-Resolution Multi-Volume Renderer](5215-mixed-resolution-multi-volume-renderer.md) by handling the data structure maintenance rather than the ray sampling logic.

### [Mixed-Resolution Multi-Volume Renderer](5215-mixed-resolution-multi-volume-renderer.md)
A ray-guided renderer that accesses metadata and cached volume data through the [Residency Octree](4950-residency-octree.md), enabling efficient mixing of resolutions across different channels in multi-volume datasets. It differs from per-channel sampling approaches by evaluating all visible channels at each sample along a ray, using a global step size determined by the highest-resolution channel to reduce shader divergence.

### Residency Octree with Channel-Agnostic Brick Cache
Uses accumulation-level intermixing to combine different channels [S1, unofficial]. The residency octree is backed by a channel-agnostic brick cache where each cache entry only contains data belonging to a single channel [S1, unofficial]. The number of channels is thus not limited by the texture format used by the brick cache implementation, unlike Brix et al.'s approach [S1, unofficial]. Residency octrees support changes to the selection of visible channels at run-time by replacing only the parts of their nodes related to the affected channels [S1, unofficial].

### Residency-Octree Node Classification
Classification of octree nodes based on cache residency of bricks covering their spatial extent at a given resolution level [S1, unofficial]. A node is fully mapped in a resolution level if cache-resident bricks of that level fully cover the node's spatial extent [S1, unofficial]. A node is partially mapped if at least one brick of that level overlaps with the node's spatial extent and is resident in the cache [S1, unofficial]. Fully mapped implies partially mapped, but not vice versa [S1, unofficial]. If a node is fully mapped in a resolution level, all child nodes are also fully mapped in that level [S1, unofficial]. If a node is partially mapped in a resolution level, its parent node is also partially mapped [S1, unofficial].

### Multi-Channel Residency Octree
An extension where all channels share the same octree structure, but each node stores culling and residency information for up to $m \le n$ channels [S1, unofficial]. This allows using the same spatial subdivision for empty-space skipping while rendering each channel in a different resolution [S1, unofficial]. When a channel is replaced by another one, all nodes storing valid data for the old channel are marked as `INVALID` for the new channel [S1, unofficial]. Each node stores for each of the $m$ channels whether the channel information is initialized or not using a special `INVALID` value [S1, unofficial]. If invalid, it stores a pointer to the node in the next lower subdivision level that has valid information for that channel, or a special `UNKNOWN` value if no such node exists [S1, unofficial]. The pointer replaces the metadata for that channel to reduce memory [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Ray traversal is performed only once per sample to minimize hierarchy traversal cost during multi-channel rendering [S2]. Traversal starts at the third level instead of the root to reduce overhead [S2].
*   **Memory Complexity:** Memory usage scales linearly with the number of simultaneously visualized channels $m$ [S2]. Each node stores one bitmask per channel [S2]. This can be mitigated by combining channels via dimensionality reduction, interleaving channels in four-component textures, or using compressed texture formats [S2]. The bit-width of the brick ID data type (e.g., 32-bit or 64-bit) constrains the maximum volume size and the maximum number of channels representable by the multi-channel page table hierarchy [S2].
*   **Performance:** The method is faster than prior approaches and efficient for many data channels with a flexible and adaptive choice of data resolution [S2]. It enables fine-grained empty-space skipping independent of the data subdivision used for bricking [S2].
*   **Strengths:** Decouples cache residency from spatial subdivision, allowing adaptive resolution mixing and cache-miss compensation [S2]. Supports efficient empty-space skipping unlike page tables [S2]. Allows substituting missing bricks with available resolutions without requiring all lower resolutions to be resident [S2].
*   **Limitations:** Memory scales linearly with channel count [S2]. Requires careful management of metadata computation if server-side queries are not supported [S1, unofficial].
*   **When to use:** Out-of-core DVR of large-scale volumetric data sets with a large number of channels, such as Immunofluorescence (IF) imaging data [S2].
*   **When not to use:** When the number of channels is very large and memory is constrained, or when the hardware does not support the required bit-width for brick IDs [S2].

## Background
The Residency Octree was introduced as a hybrid data structure for out-of-core multi-volume rendering that combines page-table hierarchies with octrees [S1, unofficial]. It addresses the limitations of previous octree-based out-of-core approaches [CNLE09, BPH14] where each node corresponds to one brick, intrinsically coupling resolution levels to octree subdivision levels [S1, unofficial]. The method was implemented as a web-based, pure client-side renderer using WebGPU and WebAssembly to facilitate collaboration and eliminate local data storage [S2]. It is particularly used for multi-channel immunoﬂuorescence data, where unimodal transfer functions make minima/maxima suitable for empty-space skipping [S1, unofficial].
