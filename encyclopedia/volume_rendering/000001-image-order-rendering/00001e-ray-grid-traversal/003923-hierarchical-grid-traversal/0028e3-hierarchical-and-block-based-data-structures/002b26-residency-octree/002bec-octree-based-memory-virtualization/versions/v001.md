# Octree-based memory virtualization

Also called: Crassin et al. Octree-based memory virtualization

## Overview
An out-of-core rendering approach for multi-channel volume data sets where octree nodes and bricks store information on up to $n$ channels [S1, unofficial]. It extends the single-channel memory virtualization scheme of Crassin et al. [CNLE09] by supporting multiple visible channels, differing from the [Multi-Channel Page-Table Hierarchy](5196-multi-channel-page-table-hierarchy.md) by using hierarchical tree traversal for every channel to ensure subtree residency [S1, unofficial].

## How it works
**Inputs and outputs:**
*   Input: Multi-channel volume dataset with $n$ channels.
*   Output: Composite image via alpha blending.

**Data structures:**
*   **Octree Nodes:** Store metadata for $n$ channels.
*   **Bricks:** Store voxel data for $n$ channels.
*   **Homogeneity Optimization:** If all voxels in a brick contain the same value (up to a user-defined threshold), the node stores the average value instead of a pointer to the brick cache [S1, unofficial]. A node is marked homogeneous only if its corresponding bricks in *all* channels are homogeneous [S1, unofficial].

**Parameters:**
*   $n$: Number of channels. Implementation-defined and cannot be changed at run-time [S1, unofficial].
*   Typical value: $n \le 4$, limited by GPU texture formats which are restricted to four components [S1, unofficial].

**Algorithm:**
1.  Traverse the octree for each of the $n$ channels.
2.  For each node, check if it is marked homogeneous.
    *   If homogeneous, use the stored average value for all channels.
    *   If not, access the brick cache for the specific channel data.
3.  Accumulate color and opacity for each channel.
4.  Mix channels using accumulation-level intermixing (alpha blending) [S1, unofficial].

**Edge cases and pitfalls:**
*   **Occlusion:** Image-level intermixing cannot handle occlusions between different channels correctly due to missing depth information in accumulated intermediate results [S1, unofficial].
*   **Channel Limit:** The number of channels is fixed at compile/implementation time; runtime switching is not supported in this specific scheme [S1, unofficial].

## Subtopics

### [Octree-based out-of-core volume rendering](5171-octree-based-out-of-core-volume-rendering.md)
Extends this method to support multiple visible channels by storing pointers and culling metadata in each node. It differs from the [Multi-Channel Page-Table Hierarchy](5196-multi-channel-page-table-hierarchy.md) by using hierarchical tree traversal for every channel to ensure subtree residency, whereas the page-table approach uses direct indexing.

## Operating characteristics
*   **Memory:** Out-of-core capable, limited by GPU texture bind points and component limits (typically 4 channels) [S1, unofficial].
*   **Performance:** Not explicitly quantified in sources.
*   **Limitations:** Cannot handle inter-channel occlusions correctly due to accumulation-level intermixing [S1, unofficial].

## Background
Originated from Crassin et al. [CNLE09] for single-channel data, extended by Brix et al. [BPH14] for multi-channel data [S1, unofficial]. Implemented in Voreen [DLJL22] [S1, unofficial].
