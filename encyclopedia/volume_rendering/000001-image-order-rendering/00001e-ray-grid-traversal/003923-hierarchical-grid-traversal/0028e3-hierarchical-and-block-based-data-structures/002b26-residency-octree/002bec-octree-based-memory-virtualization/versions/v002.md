# Octree-based memory virtualization
Also called: Crassin et al. Octree-based memory virtualization

## Overview
An out-of-core rendering approach for multi-channel volume data sets where octree nodes and bricks store information on up to $n$ channels [S1, unofficial]. It extends the single-channel scheme of Crassin et al. [CNLE09] by supporting multiple visible channels, solving the problem of managing brick residency and performing address translation for out-of-core volume rendering using a hierarchical tree structure [S1, unofficial]. Unlike its sibling [Residency Octree](4950-residency-octree.md), which uses a more compact representation, this method enforces that the whole subtree is resident in the cache for high-resolution rendering, leading to a higher memory footprint but comparable performance for single-channel data [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   Input: Multi-channel volume dataset (up to $n$ channels), camera parameters, transfer functions.
*   Output: Composite image with channels mixed via alpha blending.

**Data Structures:**
*   **Octree Nodes:** Store pointers to child nodes or bricks. For homogeneous bricks, nodes store the average value instead of a pointer [S1, unofficial]. A node is marked homogeneous only if its corresponding bricks in *all* channels are homogeneous [S1, unofficial].
*   **Bricks:** Store voxel data for up to $n$ channels. Each brick-cache entry stores $n$ channels [S1, unofficial].

**Parameters:**
*   $n$: Number of channels. Implementation-defined and cannot be changed at run-time [S1, unofficial]. Limited to 4 in practice due to GPU texture format constraints (4 components) [S1, unofficial].

**Steps:**
1.  Traverse the octree to identify visible bricks for all $n$ channels.
2.  Load bricks into the brick cache. Each cache entry holds data for $n$ channels [S1, unofficial].
3.  Perform ray traversal. If a node corresponds to a homogeneous brick, use the stored average value instead of fetching the brick [S1, unofficial].
4.  Accumulate color and opacity along the ray.
5.  Combine multiple channels using accumulation-level intermixing [S1, unofficial]. This avoids image-level intermixing issues where occlusions between different channels cannot be handled correctly due to missing depth information in accumulated intermediate results [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Channel Limit:** $n$ is hard-limited to 4 on typical GPU hardware [S1, unofficial].
*   **Homogeneity Check:** A node can only be optimized (average value storage) if *all* $n$ channels are homogeneous [S1, unofficial].
*   **Occlusion:** Accumulation-level intermixing is required to correctly handle occlusions between channels [S1, unofficial].

## Subtopics

### [Octree-based out-of-core volume rendering](5171-octree-based-out-of-core-volume-rendering.md)
Extends this method to support multiple visible channels by storing pointers and culling metadata in each node. Enforces whole-subtree residency, leading to higher memory footprint but comparable performance for single-channel data compared to [Residency Octree](4950-residency-octree.md).

## Operating characteristics
*   **Memory Footprint:** Higher than [Residency Octree](4950-residency-octree.md) because it enforces that the whole subtree is resident in the cache for high-resolution rendering [S1, unofficial].
*   **Performance:** Comparable to [Residency Octree](4950-residency-octree.md) for single-channel data [S1, unofficial].
*   **Hardware Constraints:** Limited by GPU texture bind points and component limits (max 4 channels) [S1, unofficial].

## Background
Originated from Crassin et al. [CNLE09] for single-channel data, extended by Brix et al. [BPH14] to multi-channel data sets [S1, unofficial]. Implemented in Voreen [DLJL22] [S1, unofficial].
