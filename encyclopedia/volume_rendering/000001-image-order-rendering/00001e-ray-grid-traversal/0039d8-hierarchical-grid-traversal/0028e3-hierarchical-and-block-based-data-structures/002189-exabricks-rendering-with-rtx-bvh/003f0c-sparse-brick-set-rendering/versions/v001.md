# Sparse Brick Set Rendering

Also called: Raytraced SDF rendering with bricks

## Overview
Sparse Brick Set Rendering is a method for rendering Signed Distance Fields (SDFs) using hardware-accelerated raytracing against a Bounding Volume Hierarchy (BVH) of leaf bricks, where each brick contains SDF data and is intersected via software shaders and sphere-tracing [S1, unofficial]. It differs from its parent [ExaBricks Rendering with RTX BVH](2577-exabricks-rendering-with-rtx-bvh.md) by specifically utilizing SDF sphere-tracing within leaf nodes rather than general volume integration, and from [RTX BVH Ray Tracing](2957-rtx-bvh-ray-tracing.md) by relying on software intersection shaders for the SDF geometry rather than hardware-native triangle or primitive intersection.

## How it works
**Inputs and Outputs:**
*   **Input:** A set of leaf bricks, each containing a 3D texture of distance values. A BVH constructed from AABBs enclosing these bricks. A camera ray defined by origin $\mathbf{o}$ and direction $\mathbf{d}$.
*   **Output:** The intersection distance $t$ to the nearest isosurface (typically $d=0$), the surface normal $\mathbf{n}$, and the object-space position $\mathbf{p}$.

**Data Structures:**
*   **Brick:** A 3D texture of size $8^3 = 512$ samples.
    *   **Inner Data:** The central $6^3 = 216$ samples (indices 1 to 6 in each dimension, assuming 0-based indexing for the full 8) contain the actual SDF data for sphere-tracing [S1, unofficial].
    *   **Padding:** The outer layer of voxels (indices 0 and 7 in each dimension) is duplicated from the adjacent inner voxels. This padding ensures that trilinear sampling does not cross brick boundaries, which would otherwise access invalid or discontinuous data from neighboring bricks [S1, unofficial].
    *   **Note:** 58% of the brick's memory is dedicated to this adjacency/padding data [S1, unofficial].
*   **BVH:** A hierarchy of AABBs. Only leaf nodes (representing individual bricks) are stored in the final structure used for traversal; internal nodes are discarded after construction [S1, unofficial].

**Algorithm Steps:**
1.  **BVH Traversal:** Perform hardware-accelerated ray-BVH traversal. When a ray potentially intersects a leaf brick's AABB, invoke a software intersection shader [S1, unofficial].
2.  **AABB Intersection:** Calculate the entry ($t_{min}$) and exit ($t_{max}$) distances of the ray with respect to the brick's AABB. This defines the interval $[t_{min}, t_{max}]$ for sphere-tracing [S1, unofficial].
3.  **Local Coordinate Transformation:** Transform the ray origin $\mathbf{o}$ and direction $\mathbf{d}$ into the brick's local coordinate system, where the brick spans $[0, 1]^3$. Let the local ray be $\mathbf{o}'$ and $\mathbf{d}'$ [S1, unofficial].
4.  **Sphere-Tracing:** Iteratively step along the local ray to find the intersection with the isosurface ($d=0$):
    *   Initialize current position $\mathbf{p}' = \mathbf{o}'$ and step count $k=0$.
    *   Loop while $k < K_{max}$ and distance $> \epsilon$:
        *   Sample the distance value $d_{val}$ at $\mathbf{p}'$ from the brick's texture using trilinear filtering [S1, unofficial].
        *   Transform $d_{val}$ from its stored format to the physical distance in the local space. Let this be $d_{local}$ [S1, unofficial].
        *   If $d_{local} \le 0$, an intersection has been found (or the ray is inside the surface). Terminate and record $\mathbf{p}'$ [S1, unofficial].
        *   Advance $\mathbf{p}' \leftarrow \mathbf{p}' + d_{local} \cdot \mathbf{d}'$.
        *   Increment $k$.
    *   *Note:* Sphere-tracing is used for simplicity, despite analytical intersections being potentially faster [S1, unofficial].
5.  **Object-Space Transformation:** If an intersection is found at local position $\mathbf{p}'$, transform $\mathbf{p}'$ back to object-space to get $\mathbf{p}$ [S1, unofficial].
6.  **Distance Calculation:** Calculate the final intersection distance $t$ as the distance between the original object-space ray origin $\mathbf{o}$ and the object-space intersection point $\mathbf{p}$:
    $$ t = \| \mathbf{p} - \mathbf{o} \| $$
    (Or more precisely, the scalar projection if the ray is normalized, but the text specifies "distance between... origin and... position", implying Euclidean distance or parameter $t$ if $\mathbf{d}$ is unit length) [S1, unofficial].
7.  **Normal Calculation:** Calculate the surface normal $\mathbf{n}$ at $\mathbf{p}$ using central differencing on the SDF in object-space:
    $$ \mathbf{n} = \nabla d(\mathbf{p}) \approx \left( \frac{d(\mathbf{p} + \Delta \mathbf{x}) - d(\mathbf{p} - \Delta \mathbf{x})}{2\Delta x}, \frac{d(\mathbf{p} + \Delta \mathbf{y}) - d(\mathbf{p} - \Delta \mathbf{y})}{2\Delta y}, \frac{d(\mathbf{p} + \Delta \mathbf{z}) - d(\mathbf{p} - \Delta \mathbf{z})}{2\Delta z} \right) $$
    Normalize $\mathbf{n}$ to unit length [S1, unofficial].
    *   *Pitfall:* Central differencing requires 6 samples. The tetrahedron technique requires only 4 samples but is not implemented in this specific method [S1, unofficial].

**Parameters:**
*   **Brick Size:** $8^3$ voxels. The inner $6^3$ are used for tracing [S1, unofficial].
*   **Sphere-Trace Max Steps:** Not given in the sources.
*   **Epsilon:** Not given in the sources.

**Pseudocode:**
```python
def sparse_brick_set_render(ray_origin, ray_direction, bvh, brick_textures):
    # 1. Hardware BVH traversal to find potential leaf brick intersection
    # Returns the brick ID and the t_min, t_max of the AABB intersection
    brick_id, t_min, t_max = bvh.intersect_aabb(ray_origin, ray_direction)
    
    if brick_id is None:
        return None # No intersection with any brick

    # 2. Get the brick data
    brick = brick_textures[brick_id]
    
    # 3. Transform ray to brick local space [0,1]^3
    # Assume brick has a known transformation matrix M_inv from object to local
    local_ray_origin = transform(ray_origin, M_inv)
    local_ray_dir = transform_direction(ray_direction, M_inv)
    
    # 4. Sphere-tracing in local space
    current_pos = local_ray_origin
    max_steps = 100 # Not given in sources, typical value
    epsilon = 1e-4  # Not given in sources, typical value
    
    for i in range(max_steps):
        # Sample distance using trilinear filtering
        # The texture handles the padding, so we can sample directly
        dist_val = brick.sample_trilinear(current_pos)
        
        # Transform stored distance value to local space distance
        # This depends on the specific encoding/format of the distance values
        local_dist = transform_distance_format(dist_val)
        
        # Check for intersection
        if local_dist <= epsilon:
            # Intersection found
            break
            
        # Advance along the ray
        current_pos = current_pos + local_dist * local_ray_dir
        
        # Safety check for leaving the brick (though t_min/t_max should handle this)
        if distance(current_pos, local_ray_origin) > t_max:
            return None # Missed the surface within this brick
            
    else:
        return None # Max steps reached or no intersection

    # 5. Transform intersection point back to object space
    object_pos = transform(current_pos, M) # M is inverse of M_inv
    
    # 6. Calculate t-value
    # Assuming ray_direction is normalized, t is the dot product
    # Or Euclidean distance if not normalized, but standard ray tracing uses t
    t = dot(object_pos - ray_origin, ray_direction)
    
    # 7. Calculate normal using central differencing in object space
    # We need to sample the SDF at object_pos. 
    # Note: The brick texture is in local space, so we must transform the offset points
    # back to local space to sample, or have a world-space SDF access function.
    # Assuming we have a function to get SDF value at any object-space point via the brick:
    
    delta = 1.0 / 512.0 # Approximate voxel size in object space? 
    # Actually, central differencing usually uses a small epsilon in world space.
    # Let's assume we can query SDF at object space points.
    
    dx = (sdf_at(object_pos + vec3(delta, 0, 0)) - sdf_at(object_pos - vec3(delta, 0, 0))) / (2 * delta)
    dy = (sdf_at(object_pos + vec3(0, delta, 0)) - sdf_at(object_pos - vec3(0, delta, 0))) / (2 * delta)
    dz = (sdf_at(object_pos + vec3(0, 0, delta)) - sdf_at(object_pos - vec3(0, 0, delta))) / (2 * delta)
    
    normal = normalize(vec3(dx, dy, dz))
    
    return t, normal, object_pos
```

## Operating characteristics
*   **Time Complexity:** BVH traversal is $O(\log N)$ where $N$ is the number of bricks. Sphere-tracing steps depend on the distance to the surface and the minimum step size (epsilon), typically $O(D/\epsilon)$ where $D$ is the distance to the surface.
*   **Memory Complexity:** Each brick uses $8^3$ samples, with 58% being padding. This is significantly higher memory usage than a pure $6^3$ brick but avoids boundary checks and divergent reads [S1, unofficial].
*   **Performance:** Rendering is generally much faster than construction, so optimization efforts in the source focused on construction rather than rendering [S1, unofficial]. Sphere-tracing is noted as simpler but potentially slower than analytical intersections [S1, unofficial].
*   **Strengths:** Simple implementation, leverages hardware BVH traversal, avoids boundary issues with texture sampling via padding.
*   **Limitations:** High memory overhead due to padding (58%). Sphere-tracing may be slower than analytical methods. Central differencing for normals requires 6 samples, whereas the tetrahedron technique requires 4 [S1, unofficial].

## Background
The method is based on the "sparse brick set" approach described by Evans (2022) [S1, unofficial]. The use of $8^3$ bricks matches the wavefront size of targeted GPU hardware, allowing efficient processing by thread groups of $8^3 = 512$ threads [S1, unofficial]. The rendering technique is similar to hardware-accelerated raytracing methods, but specifically applies to SDFs using software shaders for the intersection logic [S1, unofficial].
