# Brick Size and Octree Limit Tuning

Also called: Hardware-specific Bricking, Performance Optimization via Brick Size and Octree Limit Tuning, Sampling Direction Optimization

## Overview
Brick Size and Octree Limit Tuning optimizes GPU-based volume rendering by balancing texture memory constraints, rasterization overhead, and hardware-specific sampling penalties. It differs from sibling methods by treating brick size and octree depth as orthogonal variables that must be tuned specifically for the target graphics hardware's texture unit behavior and memory hierarchy, rather than relying solely on algorithmic space-skipping.

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D volume dataset, target graphics hardware specifications (texture memory size, 3D texture sampling behavior), and rendering parameters (view direction, transfer function).
*   **Output:** An optimized rendering configuration consisting of a specific brick size ($B$) and octree limit ($L$), along with potentially alternating texture orientations for bricks.

**Data Structures:**
*   **Bricks:** The volume is partitioned into cubic blocks of size $B \times B \times B$.
*   **Octree:** A hierarchical structure where leaf nodes represent bricks or sub-bricks down to the limit $L$. Internal nodes store aggregate information (e.g., occupancy flags) to skip empty regions.
*   **Texture Orientation:** For hardware with directional sampling penalties, the orientation of the 3D texture coordinates within each brick may be alternated.

**Parameters:**
*   **Brick Size ($B$):** The side length of the cubic bricks. Must be a power of 2 to fit optimal texture sizes. Typical values range from $32^3$ to $64^3$ voxels, depending on memory and hardware [S1, unofficial].
*   **Octree Limit ($L$):** The smallest cube size allowed in the octree before switching to flat brick representation. Typical values are small powers of 2 (e.g., $8^3$ or $16^3$) [S1, unofficial].
*   **Sample Rate:** Number of samples per voxel. Typical value: 1.5 samples per voxel [S1, unofficial].

**Steps:**
1.  **Analyze Hardware Constraints:** Determine the maximum texture memory available and the optimal texture dimensions (usually powers of 2). Identify if the hardware treats 3D textures as a stack of 2D slices with directional performance penalties (e.g., ATi FireGL X1) [S1, unofficial].
2.  **Determine Optimal Brick Size ($B$):**
    *   Select $B$ such that $B^3$ fits within available texture memory, accounting for overlap overhead required for interpolation [S1, unofficial].
    *   If the hardware has directional sampling penalties, consider alternating the texture orientation for consecutive bricks to mitigate z-direction traversal penalties when the view direction is not aligned with the texture axes [S1, unofficial].
    *   Tune $B$ empirically: smaller bricks reduce cache trashing but increase overhead; larger bricks benefit from linear traversal if aligned with the view [S1, unofficial].
3.  **Determine Optimal Octree Limit ($L$):**
    *   Select $L$ to balance rasterization load and triangle throughput. Smaller $L$ increases CPU overhead and triangle count; larger $L$ increases rasterization overhead [S1, unofficial].
    *   Tune $L$ empirically while keeping $B$ constant [S1, unofficial].
4.  **Construct Octree:** Build the octree bottom-up from the bricks. Leaf nodes represent regions of size $L \times L \times L$ or larger bricks. Internal nodes store aggregate flags [S1, unofficial].
5.  **Render:** Traverse the octree and render bricks using the optimized parameters. Apply Early Ray Termination (ERT) if applicable [S1, unofficial].

**Formulas:**
*   **Early Ray Termination (Front-to-Back):**
    $$C_{i+1} = (1 - A_i) \cdot \alpha_i \cdot c_i + C_i$$
    $$A_{i+1} = (1 - A_i) \cdot \alpha_i + A_i$$
    Where $C$ is accumulated color, $A$ is accumulated opacity, $\alpha_i$ is sample opacity, and $c_i$ is sample color [S1, unofficial].

**Pitfalls:**
*   **Directional Sampling Penalty:** On hardware like ATi FireGL X1, traversing 3D textures in the z-direction (when treated as 2D slices) is significantly slower than x or y directions. If the view direction differs from the texture z-axis by >45°, z-traversal is inevitable, causing performance drops [S1, unofficial].
*   **Overlap Overhead:** Smaller bricks require more overlap for interpolation, increasing memory usage and bandwidth [S1, unofficial].
*   **CPU Overhead:** Very small octree limits lead to excessive triangle counts and CPU processing time for octree traversal [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Octree build time is bounded by CPU and main memory performance. For a $512^3$ volume (256MB), build times were 6.5ms on a Xeon 1.7GHz and 3.5ms on a Xeon 3.0GHz [S1, unofficial].
*   **Memory Complexity:** Depends on brick size and overlap. Larger bricks consume more texture memory but reduce overhead.
*   **Performance:** Significant acceleration is possible. On a QuadroFX 3400, optimized bricking and octrees yielded 73.5 fps vs 9.6 fps (7.66x). On an ATi FireGL X1, optimized performance reached 83.3 fps (xy-aligned) vs 0.23 fps (non-optimized), a 362x acceleration [S1, unofficial].
*   **Strengths:** High acceleration on specific hardware; effective space-skipping and cache optimization.
*   **Limitations:** Performance is highly hardware-dependent; requires empirical tuning; directional sampling penalties can negate benefits if not managed.

## Background
This method was presented by Danny Ruijters in "Optimizing GPU Volume Rendering" [S1, unofficial]. It addresses bottlenecks in the graphics pipeline for GPU-based volume rendering, specifically targeting texture memory constraints and hardware-specific sampling behaviors.
