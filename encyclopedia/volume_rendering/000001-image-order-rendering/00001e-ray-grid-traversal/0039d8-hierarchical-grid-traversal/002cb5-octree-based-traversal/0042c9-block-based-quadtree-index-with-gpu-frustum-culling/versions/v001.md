# Block-based Quadtree Index with GPU Frustum Culling

Also called: Compute shader culling, GPU-side quadtree traversal

## Overview
This method organizes terrain or volumetric data into a block-based quadtree index where node metadata (bounding boxes, centers, hierarchy levels, and data offsets) is packed into a compact structure array residing entirely in GPU video memory. It solves the CPU traversal and assembly overhead by executing frustum culling and occlusion determination in parallel on the GPU via compute shaders, with each thread processing one node to output a list of visible nodes and their Level of Detail (LOD) levels. It differs from CPU-side hierarchical traversal by moving the culling logic to the GPU, leveraging parallelism for large-scale datasets.

## How it works
**Inputs:**
*   Global terrain size in samples: $2^L \times 2^L$.
*   Leaf node size in samples: $2^K \times 2^K$.
*   Camera frustum parameters.
*   GPU-accessible buffers: Index Structure (metadata), Tile Data Buffer (elevation), Texture Atlas (color).

**Outputs:**
*   List of visible nodes and their computed LOD levels.

**Data Structures:**
1.  **Quadtree Node Index Structure:** A packed structure array in GPU memory. Each node entry contains:
    *   Bounding box (AABB).
    *   Center coordinates.
    *   Hierarchy level (depth).
    *   Offset within the data buffer.
    *   Storage order: Z-order curve (Morton code) for cache friendliness.
2.  **Tile Data Buffer:** Elevation data written in Z-order curve order. Within each tile, values are stored contiguously in row-major order.
3.  **Texture Atlas:** Aligned one-to-one with elevation data blocks. Elevation and texture for the same tile have a deterministic mapping relationship in buffer offsets, avoiding secondary lookup tables.

**Parameters:**
*   $L$: Logarithm of total terrain dimension.
*   $K$: Logarithm of leaf node dimension. Typical value $K=9$ (512×512 samples per tile) [S1].
*   $D$: Quadtree depth, calculated as $D = L - K$ [S1].

**Algorithm Steps:**
1.  **Index Construction:**
    *   Divide the terrain region into fixed-size tile blocks of $2^K \times 2^K$ samples.
    *   Compute the quadtree depth $D = L - K$.
    *   Calculate total number of nodes: $N_{total} = \sum_{i=0}^{D} 4^i = \frac{4^{D+1}-1}{3}$ [S1].
    *   Pack bounding boxes, center coordinates, hierarchy levels, and data buffer offsets into the Index Structure array.
    *   Store the array in Z-order curve order.
2.  **Parallel Culling (Compute Shader):**
    *   Launch a compute shader with one thread per node in the Index Structure.
    *   For each thread $i$:
        *   Retrieve node $i$'s bounding box from the Index Structure.
        *   Perform frustum culling test against the camera frustum.
        *   If the node is visible, compute its LOD level based on distance or screen-space error (implementation detail not specified in source, but implied by "dynamic LOD" [S1]).
        *   Output the visible node index and LOD level to an output buffer.
3.  **Rendering:**
    *   Use the output buffer to drive the rendering pipeline.
    *   Fetch elevation data from the Tile Data Buffer using the node's offset.
    *   Fetch texture data from the Texture Atlas using the deterministic mapping offset.

**Pseudocode:**
```python
# Compute Shader Kernel: ProcessOneNode
# Input: node_index, frustum_planes, index_buffer, output_buffer
# Output: visible_nodes_list

def process_one_node(node_index, frustum_planes, index_buffer, output_buffer):
    # 1. Fetch Node Metadata
    node = index_buffer[node_index]
    bbox = node.bounding_box
    center = node.center
    level = node.hierarchy_level
    data_offset = node.data_offset
    
    # 2. Frustum Culling
    # Check if bbox intersects with any of the 6 frustum planes
    is_visible = True
    for plane in frustum_planes:
        if is_bbox_behind_plane(bbox, plane):
            is_visible = False
            break
            
    # 3. LOD Computation (Generic placeholder as specific formula not in source)
    # [G] Typically involves distance from camera center to node center
    # or screen-space error estimation.
    lod_level = compute_lod(center, level) 
    
    # 4. Output
    if is_visible:
        output_buffer.append({
            'node_index': node_index,
            'lod_level': lod_level,
            'data_offset': data_offset
        })

# Helper: Check if AABB is behind a plane
def is_bbox_behind_plane(bbox, plane):
    # Determine the corner of the bbox most likely to be behind the plane
    # based on the plane normal direction.
    # If that corner is behind the plane, the entire bbox is behind.
    corner = get_corner(bbox, plane.normal)
    return dot(plane.normal, corner) + plane.d < 0

# Helper: Get corner of bbox based on normal
def get_corner(bbox, normal):
    # bbox.min and bbox.max are vectors
    corner = vec3(0.0)
    for i in range(3):
        if normal[i] > 0:
            corner[i] = bbox.max[i]
        else:
            corner[i] = bbox.min[i]
    return corner
```

**Edge Cases and Pitfalls:**
*   **Memory Capacity:** For global SRTM30m data ($1.66 \times 10^{11}$ samples), with $K=9$, the number of leaf nodes is $\approx 6.3 \times 10^5$ and total nodes $\approx 8.4 \times 10^5$. This fits in GPU memory [S1]. Smaller regions (e.g., $2^\circ \times 2^\circ$ Rocky Mountains) have far fewer nodes ($\approx 341$) [S1].
*   **Cache Friendliness:** Storing nodes and data in Z-order curve order improves cache locality for spatially adjacent tiles [S1].
*   **Deterministic Mapping:** Ensuring elevation and texture offsets are deterministically mapped avoids secondary lookups [S1].

## Operating characteristics
*   **Time Complexity:** Culling is $O(N)$ where $N$ is the number of nodes, but executed in parallel on the GPU. The constant factor is low due to simple bounding box tests.
*   **Memory Complexity:** $O(N)$ for the index structure. The source notes that for global data, the index fits in GPU memory [S1].
*   **Performance:** Parallel processing on the GPU avoids CPU traversal and assembly overhead, which becomes significant as data scales [S1].
*   **Strengths:** Efficient for large-scale terrain data; leverages GPU parallelism; cache-friendly storage.
*   **Limitations:** Requires GPU memory for the entire index; LOD computation logic is not detailed in the source.
