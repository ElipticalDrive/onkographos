# Hierarchical Brick-Map DDA

Also called: Multi-level DDA with brick map, Sparse brick-map ray marching

## Overview
Hierarchical Brick-Map DDA is a ray traversal technique that replaces dense voxel buffers with a sparse, hierarchical structure to skip empty regions in volumetric data [S1, unofficial]. It operates by marching a ray through a top-level grid of coarse cells (stride 8 voxels) to quickly identify occupied "bricks," then descending into those specific bricks for fine-grained DDA [S1, unofficial]. This approach significantly reduces memory footprint and traversal time for sparse volumes, such as drone airspace which is >99% empty, compared to dense storage or flat sparse structures [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A dense voxel grid (or raw voxel data), a ray origin $O$ and direction $D$, and the grid dimensions $N \times N \times N$.
*   **Output:** A ray-marched image or hit distance, traversing only occupied regions.

**Data Structures:**
The method relies on three main GPU buffers and a uniform structure [S1, unofficial]:
1.  **`topGrid`**: A sparse 3D grid of top-level cells. Each cell stores a pointer (index) to a brick in the `brickPool` or a null value if the cell is empty. The dimensions are $TOP \times TOP \times TOP$, where $TOP = N / BRICK$.
2.  **`brickPool`**: A contiguous array of occupied bricks. Each brick is a $BRICK \times BRICK \times BRICK$ block of voxels. The size is determined by the number of occupied top-level cells.
3.  **`counter`**: An atomic counter used during the build phase to allocate slots in the `brickPool`.
4.  **`Grid` Uniform**: Contains `top_size` (the dimensions of the `topGrid`) and other traversal parameters [S1, unofficial].

**Parameters:**
*   **`BRICK`**: The side length of a voxel brick in voxels. Default value is 8 [S1, unofficial].
*   **`MAX_STEPS`**: Maximum number of ray marching steps. Increased to 1024 to accommodate hierarchical traversal overhead [S1, unofficial].

**Build Phase (Compute Shader):**
Before traversal, the sparse structure is built from dense voxel data [S1, unofficial]:
1.  For each top-level cell in the `topGrid`, the build shader scans its $BRICK^3$ constituent voxels.
2.  If any voxel is non-zero (solid), the shader atomically allocates a slot in the `brickPool` using the `counter`.
3.  The voxel data for that brick is copied into the allocated slot.
4.  The `topGrid` entry for that cell is updated to point to the new brick index.
5.  Optimization: The scan can early-exit upon finding the first solid voxel to reduce unnecessary reads [S1, unofficial].

**Traversal Phase (Ray Marching Shader):**
The ray traversal follows a three-step cycle: Top-level traversal, Descent, and Ascent [S1, unofficial].

1.  **Top-level Traversal:**
    The ray marches through the `topGrid`. Instead of stepping one voxel, it strides by `BRICK` voxels at a time. The ray's distance to the next top-level cell boundary is tracked using $c\_tmax$. If the current top-level cell is empty (pointer is null), the ray skips the entire cell volume by advancing $c\_tmax$ and recomputing the next boundary.

2.  **Descent:**
    When the ray enters an occupied top-level cell, it descends into the corresponding brick.
    *   The ray's position and direction are transformed into the brick's local coordinate system.
    *   The fine-grained DDA is performed within this local space.
    *   The ray direction vector $fv$ is re-derived based on the actual ray position within the occupied brick to ensure correct sampling [S1, unofficial].

3.  **Ascent:**
    When the ray exits a brick (either by hitting a voxel or leaving the brick boundary), it ascends back to the top-level grid.
    *   The ray's global position is updated.
    *   $c\_tmax$ (distance to the next top-level cell boundary) is recomputed for the new top cell to continue the coarse traversal correctly [S1, unofficial].

**Boundary Handling:**
The method reuses Axis-Aligned Bounding Box (AABB) clipping and safe-ray-distance primitives from dense implementations. This ensures that axis-aligned rays and rays outside the grid volume are handled correctly without artifacts [S1, unofficial].

## Subtopics

### [Sparse Ray Marching with Nested Axis-Aligned Distance Fields (NAADF)](6260-sparse-ray-marching-with-nested-axis-aligned-distance-fields.md)
Sparse Ray Marching with Nested Axis-Aligned Distance Fields (NAADF) is a technique for traversing sparse voxel grids by skipping over empty space using precomputed distance fields, replacing traditional brick coordinate rasterization with a simpler pipeline suitable for g-buffer and path tracing. It differs from its sibling Hierarchical Brick-Map DDA by calculating the largest empty region along the ray's path via axis-aligned bounds, allowing it to step over multiple cells at once rather than advancing one cell boundary per iteration.

## Operating characteristics
*   **Time Complexity:** Depends on sparsity. In sparse volumes, the top-level traversal skips large empty regions, reducing the number of descent/ascent operations. The complexity is proportional to the number of occupied bricks intersected by the ray.
*   **Memory Complexity:** Significantly reduced compared to dense storage. For a grid of size $N$, the memory usage is proportional to the number of occupied bricks, which is roughly $TOP^2$ for heightmap-like structures instead of $N^3$ [S1, unofficial].
*   **Measured Performance:** In drone airspace scenarios (>99% empty), the method provides substantial performance gains due to the high sparsity [S1, unofficial].
*   **Strengths:** Efficient memory usage for sparse data; reduces traversal overhead by skipping empty top-level cells; reuses existing AABB clipping logic.
*   **Limitations:** Requires a build phase to create the sparse structure; potential for visual popping or missing voxels at brick boundaries if transitions are not handled smoothly [S1, unofficial]; increased `MAX_STEPS` may be required due to traversal overhead.
*   **When to use:** Sparse volumetric data where memory is a constraint and empty space is prevalent.
*   **When not to use:** Dense volumetric data where the overhead of hierarchy management outweighs the benefits of skipping empty space.

## Background
The Hierarchical Brick-Map DDA was introduced as part of the ResQ Viz project, specifically in PR #67, to optimize ray marching for sparse volumes like drone airspace [S1, unofficial]. It builds upon the concept of sparse voxel traversal by introducing a two-level hierarchy (top-level grid and bricks) to improve cache efficiency and reduce memory bandwidth. The method was developed to support future features like sensor primitives and terrain streaming, which require efficient ray queries on sparse data [S1, unofficial].
