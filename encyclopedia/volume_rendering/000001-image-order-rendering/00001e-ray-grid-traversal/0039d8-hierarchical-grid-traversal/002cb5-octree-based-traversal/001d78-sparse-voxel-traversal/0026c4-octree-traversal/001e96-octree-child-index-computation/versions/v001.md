# Octree Child Index Computation

Also called: Octant Offset Calculation, Child Index Derivation

## Overview
Octree Child Index Computation determines the 0–7 octant offset (and thus the linear index) of the child node that contains a specific target coordinate within the current parent node. It solves the problem of efficiently mapping a 3D position to a specific branch in a hierarchical grid without arbitrary bit shifts. It sets itself apart from generic tree traversal by relying on precomputed bit masks and constant-time bitwise operations to derive the child index [S1, S2, unofficial][S3].

## How it works
**Inputs:**
- `origin`: The starting 3D coordinate vector $(x_o, y_o, z_o)$ [S1, unofficial].
- `destination`: The target 3D coordinate vector $(x_d, y_d, z_d)$ [S1, unofficial].
- `depth`: The current depth level in the octree [S1, unofficial].
- `max_depth`: The maximum depth of the octree [S1, unofficial].

**Outputs:**
- `child_index`: An integer in the range $[0, 7]$ representing the octant offset of the child containing the destination [S1, unofficial].

**Data Structures:**
- `child_bit_depth`: A precomputed array where `child_bit_depth[d]` stores the bit mask for depth $d$.
  - Layout: Array of integers.
  - Size: `max_depth + 1`.
  - Formula: `child_bit_depth[d] = 1 << (max_depth - d - 1)` [S1, unofficial].

**Steps:**
1. **Precompute Masks:** Calculate `child_bit_depth` for all depths $d \in [0, \text{max\_depth}]$ using the formula above [S1, unofficial].
2. **Extract Components:** Isolate the X, Y, and Z components of the `destination` coordinate.
3. **Mask and Shift:**
   - For each axis, apply the `child_bit_depth[depth]` mask to the corresponding `destination` component using bitwise AND (`&`) [S1, unofficial].
   - Shift the masked result by constants corresponding to the X, Y, and Z components to align them into a single integer [S1, unofficial].
4. **Combine:** Combine the shifted components using bitwise OR (`|`) to form the 0–7 octant offset [S1, unofficial].
5. **Return:** Return the scalar value. If the current node is a leaf, this index identifies the specific voxel or scalar value within the cap node [S1, unofficial].

**Pseudocode:**
```python
def compute_child_index(origin, destination, depth, max_depth, child_bit_depth):
    # Precompute bit depth mask if not already done
    # child_bit_depth[d] = 1 << (max_depth - d - 1)
    
    # Extract destination components
    x_d = destination.x
    y_d = destination.y
    z_d = destination.z
    
    # Get the bit mask for the current depth
    mask = child_bit_depth[depth]
    
    # Apply mask to destination coordinates
    # This isolates the relevant bits for the current subdivision level
    x_masked = x_d & mask
    y_masked = y_d & mask
    z_masked = z_d & mask
    
    # Determine octant bits
    # Assuming standard Morton order or similar mapping where
    # X, Y, Z bits are interleaved or mapped to specific bit positions.
    # The source mentions "bit-shift by constants corresponding to the X,Y and Z components".
    # In a standard 3D Morton code or octant index, the bits are typically:
    # bit 0: X, bit 1: Y, bit 2: Z (for a single level)
    # However, the source implies a specific constant shift.
    # We assume the mask isolates the single bit relevant for the child selection at this depth.
    
    # Calculate octant index
    # The source states: "compute the target child octant with binary & and integer inequality operations"
    # and "&-mask this value with the destination coordinates and bit-shift by constants".
    # This implies:
    # octant = (x_masked >> shift_x) | (y_masked >> shift_y) | (z_masked >> shift_z)
    # Where shifts align the isolated bit to position 0, 1, 2 respectively.
    
    # Standard octant index calculation from a single bit per axis:
    # If mask isolates the MSB or LSB, we shift it to the least significant bit.
    # Let's assume the mask isolates the bit that determines the child in that axis.
    # We shift each to its respective position in the 3-bit octant index.
    
    # Note: The exact shift constants depend on the coordinate system and Morton ordering.
    # A common approach for octant index from coordinates (x,y,z) at a specific level:
    # bit_x = (x_d >> (max_depth - depth)) & 1
    # bit_y = (y_d >> (max_depth - depth)) & 1
    # bit_z = (z_d >> (max_depth - depth)) & 1
    # octant = bit_x | (bit_y << 1) | (bit_z << 2)
    
    # Re-interpreting source [S1, unofficial]: "left-shifting by constants" suggests the mask might be applied differently.
    # However, the result is the 0-7 offset.
    
    # Implementation based on standard interpretation of "bit-shift by constants":
    # We assume the mask isolates the relevant bit, and we shift it to the correct position.
    
    # Let's use the standard bit extraction for clarity, as the source's "constants" are not explicitly defined numerically.
    # The source emphasizes avoiding arbitrary shifts by precomputing the mask.
    
    # Extract bits
    bit_x = (x_d >> (max_depth - depth)) & 1
    bit_y = (y_d >> (max_depth - depth)) & 1
    bit_z = (z_d >> (max_depth - depth)) & 1
    
    # Combine into octant index
    octant = bit_x | (bit_y << 1) | (bit_z << 2)
    
    return octant
```

**Parameters:**
- `max_depth`: The maximum depth of the octree. Typical values depend on the volume resolution [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Leaf Nodes:** When a leaf is encountered, the function returns the scalar value or voxel index directly [S1, unofficial].
- **Precision:** Floating-point precision issues may arise when comparing coordinates to bit masks. Integer arithmetic is preferred for index computation [S1, unofficial].
- **Boundary Conditions:** Ensure that the destination coordinate is within the bounds of the current parent node to avoid incorrect octant selection [S1, unofficial].

## Subtopics

### [Point Location](2076-point-location.md)
Point Location maps a continuous 3D coordinate vector to a specific leaf node or voxel within a canonical octree. It solves the problem of efficiently retrieving data associated with a spatial position by traversing the tree from a given starting node to the target leaf. What sets this method apart from generic tree traversal is its reliance on precomputed bit masks to determine child indices using constant-time bitwise operations, avoiding the computational cost of arbitrary bit shifts. It builds on [Octree Child Index Computation](1807-octree-child-index-computation.md) to derive the 0-7 octant offset.

### [Fast Projection for Octree Nodes](2178-fast-projection-for-octree-nodes.md)
Fast Projection for Octree Nodes accelerates the mapping of 3D octree nodes to 2D screen space during sparse voxel octree rendering. It solves the problem of efficiently determining which pixels are affected by a node's projection without per-pixel ray casting for every node. It sets itself apart from sibling methods by using a hierarchical 2D node map to terminate redundant thread execution, achieving a speedup of > 2x compared to naive per-pixel launching.

### [Direction-dependent Morton Order Mapping](2662-direction-dependent-morton-order-mapping.md)
Direction-dependent Morton Order Mapping is a remapping function that converts a standard Octree Morton code into a sorting key aligned with the near-to-far rendering order for a specific ray direction. It solves the problem of correct occlusion culling and blending order in sparse voxel rasterization by ensuring that voxels are processed from closest to furthest relative to the camera, regardless of the viewing angle. Unlike [Point Location](2076-point-location.md) which determines spatial containment, or [Fast Projection for Octree Nodes](2178-fast-projection-for-octree-nodes.md) which estimates bounding volumes, this method specifically addresses the topological sorting requirement for volume rendering by adapting the Morton space-filling curve to the ray's sign vector.

### Voxel Child Address Calculation
Voxel Child Address Calculation determines the linear address of a specific child octant within a block of children, based on a valid mask [S2, unofficial]. It calculates the index by creating a mask `mask = ~(0xff << octant)` to isolate the bit corresponding to the octant, and then returns `child + popcount(mask & valid)`, where `valid` is a bitmask of existing children [S2, unofficial]. This method assumes children are stored in order of their octant index, but only valid children are present in the block [S2, unofficial].

### Ordered Child Traversal
Ordered Child Traversal iterates over the children of a voxel in a specific order, typically front-to-back relative to the ray direction [S3]. It uses a precomputed 8x8 table `ORDERED_CHILDREN` that maps the ray direction and the current voxel's octant to the sequence of child indices to visit [S3]. This ensures correct occlusion culling and blending order in volume rendering [S3].

## Operating characteristics
- **Time Complexity:** $O(1)$ per node visit for index computation, assuming precomputed masks [S1, unofficial].
- **Memory Complexity:** $O(\text{max\_depth})$ for storing the `child_bit_depth` array [S1, unofficial].
- **Strengths:** Efficient bitwise operations avoid expensive arbitrary bit shifts [S1, unofficial].
- **Limitations:** Requires precomputation of bit masks [S1, unofficial].

## Background
The method originates from interactive isosurface ray tracing of large octree volumes [S1, unofficial]. It was developed to optimize the traversal of sparse voxel octrees by reducing the computational cost of child index determination [S1, unofficial].
