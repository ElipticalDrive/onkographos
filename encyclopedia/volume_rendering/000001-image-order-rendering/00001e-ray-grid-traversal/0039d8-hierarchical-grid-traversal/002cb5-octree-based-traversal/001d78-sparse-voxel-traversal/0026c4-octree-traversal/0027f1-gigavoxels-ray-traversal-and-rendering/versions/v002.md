# GigaVoxels Ray Traversal and Rendering

Also called: GigaVoxels, Brick-based Volume Rendering

## Overview
GigaVoxels is a GPU-based volume rendering technique that uses an octree structure to manage data at the brick level, traversing the tree to sample voxel data and performing front-to-back blending [S1, unofficial]. It distinguishes itself from standard sparse voxel octree traversal by decoupling the geometric hierarchy from the volumetric data storage in a global brick pool, enabling efficient memory residency management and level-of-detail culling based on brick occupancy [S1, unofficial].

## How it works

### Inputs and Outputs
*   **Input:** A ray defined by origin and direction; an octree structure where each node contains metadata and pointers to bricks; a global brick pool storing the actual voxel color and gradient data [S1, unofficial].
*   **Output:** A final color and opacity value for the ray, accumulated via front-to-back blending [S1, unofficial].

### Data Structures

**Octree Node Layout**
Each octree node is stored as a `uvec4` (four unsigned 32-bit integers) [S1, unofficial]. The layout is as follows [S1, unofficial]:
*   `.r` (32 bits):
    *   Bit 31 (MSB): Node Type Flag. If set (`0x40000000`), the node is constant [S1, unofficial].
    *   Bits 30-20 (11 bits): Child Node Pointer Index (offset into the child node pool) [S1, unofficial].
    *   Bit 31 (MSB of this field, distinct from Node Type): Brick Is Loaded Flag. If set (`0x80000000`), the brick data is resident in the GPU memory [S1, unofficial].
*   `.g` (32 bits):
    *   Bits 31-20 (12 bits): Brick Pointer S-coordinate (index into brick pool) [S1, unofficial].
    *   Bits 19-10 (10 bits): Brick Pointer T-coordinate [S1, unofficial].
    *   Bits 9-0 (10 bits): Brick Pointer R-coordinate [S1, unofficial].
    *   If the node is constant, these bits store the constant color/alpha values packed as 8-bit integers (R, G, B, A) [S1, unofficial].
*   `.b` and `.a`: Not given in the sources.

**Brick Pool**
*   **Color Texture:** A 3D texture (`BrickSampler`, `sampler3D`) containing RGBA voxel data [S1, unofficial].
*   **Gradient Texture:** A 3D texture containing RGB gradient data (used for lighting) [S1, unofficial].
*   **Dimensions:** Defined by `BrickPoolDimension` (total texels in the pool) and `BrickDimension` (texels per brick side) [S1, unofficial].
*   **Border Voxels:** Bricks include border voxels to facilitate seamless sampling across brick boundaries [S1, unofficial].

**Samplers**
*   `OctTreeSampler`: `usampler3D` (unsigned int 3D texture) representing the octree structure [S1, unofficial].
*   `BrickSampler`: `sampler3D` (float 3D texture) for color data [S1, unofficial].
*   `JitterTexSampler`: `sampler2D` [S1, unofficial].

### Parameters
*   `RayStepSize`: Step size of the ray in world coordinates [S1, unofficial].
*   `BrickStepVector`: Step size of the ray in brick pool coordinates [S1, unofficial].
*   `BrickDimension`: Number of texels in a brick [S1, unofficial].
*   `RootVoxelHalfSize`: Size of a voxel in the root node [S1, unofficial].
*   `BrickPoolDimension`: Total dimensions of the brick pool texture [S1, unofficial].
*   `OctTreeDepthMinusOne`: Depth of the octree minus one [S1, unofficial].
*   `MaxTreeTraversals`: Maximum number of tree traversals allowed per ray [S1, unofficial].
*   `MaxNodesToPushThisFrame`: Limit on nodes pushed to the usage list per frame [S1, unofficial].
*   `LodScalar`: Scalar for Level of Detail calculations [S1, unofficial].

### Algorithm Steps

1.  **Ray-Node Intersection:** Compute the minimum ray-box intersection time ($t_{min}$) by iterating over the 6 planes of the current node's extent. Update plane $D$ values based on `nodeExtentMin` and `nodeExtentMax`. Only consider intersections where the dot product of the ray direction and plane normal is positive ($dirDotN > 0$) [S1, unofficial].
2.  **Advance Ray to Node Boundary:** Calculate the number of steps required to reach the node boundary: $numSteps = \lfloor distToNodeBoundary / rayStepSize \rfloor + 1$. Update the ray world position: $rayWorldPosition += rayDir \times (numSteps \times rayStepSize)$ [S1, unofficial].
3.  **Traverse Node:** Check if the node is constant using `NodeIsConstant` [S1, unofficial].
    *   **If Constant:** Retrieve the constant value using `GetConstantValue` [S1, unofficial]. If `constValue.a < 0.005`, advance the ray to the exit of the current volume segment and return [S1, unofficial]. Otherwise, loop `numSteps` times. In each step, advance `rayWorldPosition` by `worldRayStep` [S1, unofficial]. If destination opacity `dst.a > 0.995`, advance remaining steps and return [S1, unofficial]. Update $src.a = 1.0 - (1.0 - src.a)^{sampleRatio}$ and $src.rgb *= sampleRatio$ [S1, unofficial]. Update $dst = (1.0 - dst.a) \times src + dst$ [S1, unofficial].
    *   **If Non-Constant:** Check if the brick is loaded using `BrickIsLoaded` [S1, unofficial]. If loaded, retrieve the brick pointer using `GetBrickPointer` [S1, unofficial], sample the brick data from `BrickSampler`, and apply front-to-back blending [S1, unofficial]. Determine child nodes using `GetChildNodePointer` and traverse them [S1, unofficial].

### Pseudocode

```python
def NodeIsConstant(octTreeNode):
    nodeTypeBits = octTreeNode[0]
    return (nodeTypeBits & 0x40000000) != 0

def GetChildNodePointer(octTreeNode):
    childNodePtrBits = octTreeNode[0]
    x_ptr = (childNodePtrBits >> 20) & 0x3FF
    y_ptr = (childNodePtrBits >> 10) & 0x3FF
    z_ptr = childNodePtrBits & 0x3FF
    return (x_ptr, y_ptr, z_ptr)

def BrickIsLoaded(octTreeNode):
    brickIsLoadedBits = octTreeNode[0]
    return (brickIsLoadedBits & 0x80000000) != 0

def GetBrickPointer(octTreeNode):
    brickPtrBits = octTreeNode[1]
    uiS = (brickPtrBits >> 20) & 0x3FF
    uiT = (brickPtrBits >> 10) & 0x3FF
    uiR = brickPtrBits & 0x3FF
    return (float(uiS) / BrickPoolDimension[0], float(uiT) / BrickPoolDimension[1], float(uiR) / BrickPoolDimension[2])

def GetConstantValue(octTreeNode):
    constValueBits = octTreeNode[1]
    red = constValueBits & 0xFF
    constValueBits >>= 8
    green = constValueBits & 0xFF
    constValueBits >>= 8
    blue = constValueBits & 0xFF
    constValueBits >>= 8
    alpha = constValueBits & 0xFF
    return (float(red), float(green), float(blue), float(alpha)) / 255.0

def ComputeRayBoxIntersection(rayOrigin, rayDir, extentMin, extentMax):
    tMin = -float('inf')
    tMax = float('inf')
    for i in range(3):
        if rayDir[i] != 0.0:
            invDir = 1.0 / rayDir[i]
            t1 = (extentMin[i] - rayOrigin[i]) * invDir
            t2 = (extentMax[i] - rayOrigin[i]) * invDir
            if rayDir[i] > 0:
                tMin = max(tMin, t1)
                tMax = min(tMax, t2)
            else:
                tMin = max(tMin, t2)
                tMax = min(tMax, t1)
        else:
            if rayOrigin[i] < extentMin[i] or rayOrigin[i] > extentMax[i]:
                return -1.0
    if tMin > tMax:
        return -1.0
    return tMin

def TraverseConstant(rayWorldPosition, rayDir, numSteps, sampleRatio, dst, RayStepSize, currentNode):
    constValue = GetConstantValue(currentNode)
    if constValue[3] < 0.005:
        rayWorldPosition = rayWorldPosition + rayDir * (numSteps * RayStepSize)
        return rayWorldPosition, dst

    worldRayStep = rayDir * RayStepSize
    for i in range(numSteps):
        rayWorldPosition = rayWorldPosition + worldRayStep
        if dst[3] > 0.995:
            rayWorldPosition = rayWorldPosition + rayDir * ((numSteps - i - 1) * RayStepSize)
            return rayWorldPosition, dst

        src = constValue
        src_a = 1.0 - pow(1.0 - src[3], sampleRatio)
        src_rgb = (src[0] * sampleRatio, src[1] * sampleRatio, src[2] * sampleRatio)
        dst = ((1.0 - dst[3]) * src_rgb[0] + dst[0], (1.0 - dst[3]) * src_rgb[1] + dst[1], (1.0 - dst[3]) * src_rgb[2] + dst[2], (1.0 - dst[3]) * src_a + dst[3])
    return rayWorldPosition, dst

def RenderRay(rayOrigin, rayDir):
    dst = (0.0, 0.0, 0.0, 0.0)
    rayWorldPosition = rayOrigin
    currentNode = GetRootNode() # Assumed available from octree structure

    tMin = ComputeRayBoxIntersection(rayOrigin, rayDir, currentNode.extentMin, currentNode.extentMax)
    if tMin < 0:
        return dst

    distToNodeBoundary = tMin
    numSteps = int(distToNodeBoundary / RayStepSize) + 1
    rayWorldPosition = rayWorldPosition + rayDir * (numSteps * RayStepSize)

    dst = TraverseConstant(rayWorldPosition, rayDir, numSteps, 1.0, dst, RayStepSize, currentNode)
    return dst
```

### Edge Cases and Pitfalls
*   **Precision:** Bit-packing requires careful handling of unsigned integer shifts to avoid sign extension errors [S1, unofficial].
*   **Boundary Conditions:** The `numSteps` calculation must account for floating-point inaccuracies at node boundaries to prevent gaps or overlaps [G].
*   **Unloaded Bricks:** If a brick is not loaded, the traversal must handle the missing data gracefully, either by skipping or triggering a load request. The provided sources do not detail the asynchronous loading mechanism [S1, unofficial].

## Operating characteristics

### Time and Memory Complexity
*   **Time Complexity:** Depends on the depth of the octree and the density of the volume. In the worst case, it is proportional to the number of voxels along the ray. However, constant nodes and empty space skipping significantly reduce the average case [S1, unofficial].
*   **Memory Complexity:** Proportional to the number of nodes in the octree plus the number of resident bricks. The brick pool size is fixed based on `BrickPoolDimension` [S1, unofficial].

### Measured Performance
*   Not given in the sources.

### Scaling
*   Scales with the resolution of the brick pool and the depth of the octree. Larger brick dimensions reduce the number of nodes but increase memory per node [S1, unofficial].

### Strengths and Limitations
*   **Strengths:** Efficient memory usage through brick-based storage; supports LOD; GPU-friendly traversal [S1, unofficial].
*   **Limitations:** Requires complex bit-packing; asynchronous loading adds complexity; fixed brick size may lead to inefficiencies for very small or very large features [S1, unofficial].

### When to Use
*   Suitable for large-scale volume rendering on GPUs where memory bandwidth is a bottleneck and the volume data has varying density [S1, unofficial].

### When Not to Use
*   Not suitable for real-time applications with extremely high-frequency details that cannot be captured by the brick resolution [S1, unofficial].
