# RLE4 Ray Tracing

Also called: Map4 Traversal

## Overview
RLE4 Ray Tracing is a ray-marching and voxel-intersection algorithm that traverses an RLE4 (Run-Length Encoded 4D) compressed volume structure, also known as Map4, to locate the first occupied voxel along a ray or to colorize a voxel based on its position [S1, unofficial]. It distinguishes itself from standard voxel grid traversal by using slab-based RLE encoding to skip empty space efficiently, reducing the number of memory accesses required to find occupied regions [S1, unofficial].

## How it works
**Inputs and Outputs:**
- **Input:** A ray defined by a target voxel coordinate $(x, y, z)$ within the volume bounds, and the RLE4 compressed volume data structure (`map4`).
- **Output:** The color value of the voxel at $(x, y, z)$ if occupied, or termination if empty.

**Data Structures:**
The `map4` structure contains:
- `sx`: The width of the volume in voxels (X dimension).
- `slabs`: A pointer to an array of `ushort` (16-bit unsigned integers) representing the slab map. The layout is indexed by `x + z * sx`.
- `texture`: A pointer to the start of the texture/color data, which follows the slab map in memory.

Each entry in the `slabs` array for a specific $(x, z)$ coordinate consists of a sequence of `ushort` values:
1. `len1`: The number of slab segments in the first run.
2. `len2`: The number of slab segments in the second run (if applicable, though the algorithm primarily iterates through `len1`).
3. `len1` slab entries, each encoded as a `ushort`.

**Slab Entry Encoding:**
Each slab entry `slab` is a `ushort` packed with Y-range information:
- Lower 10 bits (`slab & 1023`): The starting Y coordinate ($y_{start}$) of the slab segment.
- Upper 6 bits (`slab >> 10`): The length of the slab segment in Y.
- The ending Y coordinate is $y_{end} = y_{start} + \text{length}$.

**Numbered Steps:**
1. **Coordinate Conversion:** Calculate integer voxel coordinates $x, y, z$ from the ray's float position, scaled by the volume dimensions $v_x, v_y, v_z$.
2. **Bounds Check:** Verify that $0 \le x < v_x$, $0 \le y < v_y$, and $0 \le z < v_z$. If any coordinate is out of bounds, terminate the search [S1, unofficial].
3. **Slab Pointer Access:** Compute the index into the slab map: $idx = x + z \cdot v_x$. Access the slab pointer: $p = \text{map4.slabs} + idx$.
4. **Read Lengths:** Read the first two `ushort` values from $p$:
   - $len1 = *p$
   - $p \leftarrow p + 1$
   - $len2 = *p$
   - $p \leftarrow p + 1$
5. **Initialize Variables:**
   - Set $y_1 = 0$, $y_2 = 0$.
   - Set texture pointer $pt = p + len1$. (Note: The source implies skipping the first `len1` slab entries in the map to align with the texture data start, or this is a specific implementation detail where texture data follows the map. The source says `pt = p + len1` after reading lengths, but then iterates `len1` times reading from `p`. This suggests `p` points to the start of the slab entries for this $(x,z)$, and `pt` is calculated relative to the end of the slab map or a specific offset. Based on the loop, `p` is used to read slab entries, and `pt` is used to write color. The source states `pt = p + len1` initially, but then inside the loop, it reads from `p`. This implies `pt` might be an offset into the texture array, not a pointer to memory. Let's re-read carefully: `ushort *pt = p+len1;` then `pt[texture+y-y1]`. This suggests `pt` is a pointer to the texture data, and `texture` is an index. The source is slightly ambiguous on memory layout. We will follow the source's variable usage: `pt` is a pointer to the texture data buffer, and `texture` is an integer offset into that buffer.)
   - Initialize `texture = 0`.
6. **Iterate Slabs:** Loop $s$ from $0$ to $len1 - 1$:
   a. Read slab entry: $slab = *p$; $p \leftarrow p + 1$.
   b. Decode Y-range:
      - $y_1 \leftarrow y_1 + (slab \ \& \ 1023)$
      - $y_2 \leftarrow y_1 + (slab \gg 10)$
   c. Check if target $y$ is in $[y_1, y_2)$:
      - If $y_2 > y$ and $y_1 \le y$:
        - The voxel is found.
        - Retrieve the color value `col` from the texture data at `pt[texture + y - y1]`. (Note: The source does not specify how `col` is retrieved from `pt`. It assumes `col` is available. We will assume `col` is a 32-bit integer or similar packed color value stored in the texture array.)
        - Decode color components (5 bits per channel, range 0-31):
          - $r = \text{clamp}((col \ \& \ 0x1F) \cdot 15 + 16, 0, 31)$
          - $g = \text{clamp}(((col \gg 5) \ \& \ 0x1F) \cdot 15 + 16, 0, 31)$
          - $b = \text{clamp}(((col \gg 10) \ \& \ 0x1F) \cdot 15 + 16, 0, 31)$
        - Store packed RGB back into the texture array:
          - $pt[\text{texture} + y - y_1] = (r \ | \ (g \ll 5) \ | \ (b \ll 10))$
        - Return.
   d. If not found, advance:
      - $\text{texture} \leftarrow \text{texture} + (y_2 - y_1)$
      - $y_1 \leftarrow y_2$
7. **Termination:** If the loop completes without finding the voxel, the voxel is empty or out of bounds (though bounds were checked).

**Pseudocode:**
```python
def rle4_traverse(map4, x, y, z, vx, vy, vz):
    # 1. Bounds Check
    if x < 0 or x >= vx or y < 0 or y >= vy or z < 0 or z >= vz:
        return None

    # 2. Access Slab Map
    idx = x + z * vx
    p = map4.slabs[idx]
    
    # 3. Read Lengths
    len1 = p[0]
    len2 = p[1]
    p = p[2:] # Move pointer past lengths
    
    # 4. Initialize
    y1 = 0
    y2 = 0
    pt = map4.texture # Assuming map4.texture points to the start of color data
    texture_offset = 0
    
    # 5. Iterate Slabs
    for s in range(len1):
        slab = p[0]
        p = p[1:]
        
        # Decode Y-range
        y_start = slab & 1023
        y_len = slab >> 10
        
        y1 = y1 + y_start
        y2 = y1 + y_len
        
        # Check if y is in [y1, y2)
        if y2 > y and y1 <= y:
            # Voxel found
            # Retrieve color from texture data
            # Note: The source implies col is read from pt[texture_offset + y - y1]
            # We assume pt is an array of uint32 or similar
            col = pt[texture_offset + y - y1]
            
            # Decode 5-bit RGB
            r_raw = col & 0x1F
            g_raw = (col >> 5) & 0x1F
            b_raw = (col >> 10) & 0x1F
            
            # Quantize to 0-31 range (source formula: val * 15 + 16, clamped)
            r = clamp(r_raw * 15 + 16, 0, 31)
            g = clamp(g_raw * 15 + 16, 0, 31)
            b = clamp(b_raw * 15 + 16, 0, 31)
            
            # Store packed RGB back
            new_col = r | (g << 5) | (b << 10)
            pt[texture_offset + y - y1] = new_col
            
            return new_col
        
        # Advance
        texture_offset += (y2 - y1)
        y1 = y2
        
    return None

def clamp(val, min_val, max_val):
    if val < min_val: return min_val
    if val > max_val: return max_val
    return val
```

**Parameters:**
- **Color Quantization:** 5 bits per channel (RGB), resulting in a 31-level intensity range (0-31) [S1, unofficial].
- **Slab Encoding:** 10 bits for Y-start, 6 bits for Y-length [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Bounds:** The algorithm assumes the target Y is within volume bounds, checked at the start. If the ray passes through multiple slabs, it iterates until the Y range is found [S1, unofficial].
- **Precision:** The Y-coordinate decoding uses integer arithmetic. Ensure that the accumulation of $y_1$ does not overflow if the volume is very large, though `ushort` limits the max Y-length to 64 (6 bits) and Y-start to 1024 (10 bits), suggesting a limited Y-range per slab or a specific encoding scheme. The source uses `int` for $y_1, y_2$, so overflow is unlikely for typical volume sizes.
- **Empty Space:** The RLE4 structure efficiently skips empty space by only storing occupied slab segments. If a voxel is not found in the loop, it is considered empty.

## Operating characteristics
- **Time Complexity:** $O(k)$, where $k$ is the number of slab segments along the ray's path in the XZ plane. In sparse volumes, $k$ is much smaller than the total number of voxels, providing significant speedup over dense grid traversal.
- **Memory Complexity:** $O(N)$, where $N$ is the number of occupied slab segments. The RLE4 compression reduces memory footprint compared to a full 3D grid.
- **Strengths:** Efficiently handles sparse volumes by skipping empty space. Simple implementation with minimal branching.
- **Limitations:** Performance degrades in dense volumes where most slabs are occupied. The fixed 5-bit color quantization may lead to color banding.
- **When to Use:** Ideal for sparse voxel volumes where empty space is prevalent.
- **When Not to Use:** Not suitable for dense volumes or when high-precision color is required.

## Background
RLE4 Ray Tracing, also known as Map4 Traversal, was introduced in the context of OpenGL voxel splatting and real-time volume rendering. It is associated with the work by sp4cerat on GitHub, which provides an unofficial implementation for real-time voxel rendering using OpenGL [S1, unofficial]. The method leverages run-length encoding to optimize ray traversal in 3D voxel grids.
