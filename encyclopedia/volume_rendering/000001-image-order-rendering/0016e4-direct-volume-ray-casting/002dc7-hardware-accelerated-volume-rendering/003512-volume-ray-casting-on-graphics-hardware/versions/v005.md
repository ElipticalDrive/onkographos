# Volume Ray-Casting on Graphics Hardware

Also called: Stream model for volumetric ray-casting

## Overview
This method implements direct volume ray casting on programmable graphics hardware (specifically DirectX 9-level architectures like the ATI 9700) using a multi-pass stream model [S1, unofficial]. It solves the performance bottleneck of CPU-based volume rendering by exploiting the intrinsic parallelism of fragment processors and efficient inter-pass communication via texture render targets [S1, unofficial]. Unlike single-pass rasterization, this approach explicitly manages ray traversal state across multiple rendering passes, enabling hardware-accelerated early ray termination and empty-space skipping through an early z-test mechanism [S1, unofficial].

## How it works
The method relies on a multi-pass rendering pipeline where the output of one pass serves as the input texture for the next. It utilizes specific hardware features available in Pixel Shader 2.0 environments: per-fragment texture fetches (up to 8 textures, with limited dependent fetches), texture render targets (allowing rendering to 2D textures aligned with the viewport), texture coordinate generation, per-fragment arithmetic, and depth replace capabilities [S1, unofficial].

### Inputs and Outputs
- **Input**: A 3D scalar volume texture, a pre-computed 2D texture storing ray direction vectors in local texture coordinates for each pixel, and a 2D texture storing accumulated color and opacity from previous passes [S1, unofficial].
- **Output**: A final 2D color texture representing the rendered image [S1, unofficial].

### Data Structures
1.  **Volume Texture**: 3D texture containing the scalar field data [S1, unofficial].
2.  **Direction Texture**: 2D texture storing the ray direction vector $(\mathbf{d}_x, \mathbf{d}_y, \mathbf{d}_z)$ for each pixel in local texture space [S1, unofficial].
3.  **Accumulation Texture**: 2D texture storing the accumulated color $(C_r, C_g, C_b)$ and accumulated opacity $\alpha$ from the previous pass. Floating-point textures are used to support negative values if required [S1, unofficial].
4.  **Z-Buffer**: Used for the early z-test. The depth replace feature allows fragments to write arbitrary depth values [S1, unofficial].

### Algorithm Steps
1.  **Pre-computation**: For each pixel, compute the direction of the ray of sight in local texture coordinates. Store these directions in the Direction Texture [S1, unofficial].
2.  **Initialization**: Render the initial state (zero color, zero opacity) into the Accumulation Texture [S1, unofficial].
3.  **Main Passes**: Execute a fixed number of main rendering passes. In each pass:
    a.  Bind the Accumulation Texture from the previous pass as a texture unit.
    b.  Bind the Direction Texture and the Volume Texture.
    c.  Execute the fragment shader to perform one step of ray traversal:
        i.  Sample the volume at the current ray position.
        ii. Apply the transfer function to obtain color $C_i$ and opacity $\alpha_i$.
        iii. Update accumulated color and opacity using the front-to-back compositing equations:
        $$
        C'_{i} = C'_{i-1} + (1 - \alpha'_{i-1}) \alpha_i C_i
        $$
        $$
        \alpha'_{i} = \alpha'_{i-1} + (1 - \alpha'_{i-1}) \alpha_i
        $$
        iv. Advance the ray position along the direction vector [S1, unofficial].
    d.  Write the new accumulated color and opacity to the Accumulation Texture [S1, unofficial].
4.  **Termination Check Pass**: Between main passes, execute an additional pass to test for termination:
    a.  Read the accumulated opacity $\alpha'$ from the Accumulation Texture.
    b.  If $\alpha'$ exceeds a specified threshold OR an iso-surface is hit:
        i.  Set the fragment's depth value to the maximum possible value (using depth replace) [S1, unofficial].
    c.  Otherwise:
        i.  Set the fragment's depth value to zero [S1, unofficial].
5.  **Early Z-Test Filtering**: Configure the depth test to `GREATER`.
    a.  Because fragments that triggered termination have depth set to the maximum, and the test is `GREATER`, these fragments will fail the depth test in subsequent main passes (assuming the z-buffer is cleared or managed appropriately to discard them) [S1, unofficial].
    b.  Fragments that have not terminated (depth set to zero) will pass the depth test and continue processing [S1, unofficial].
6.  **Final Pass**: If an iso-surface hit was detected, use the coordinates stored in a separate 2D texture to restrict gradient and shading computations to those specific points in a final pass [S1, unofficial].

### Edge Cases and Pitfalls
-   **Dependent Texture Fetches**: The ATI hardware limits the number of dependent texture fetches. The algorithm must minimize dependencies to avoid performance degradation [S1, unofficial].
-   **Floating Point Precision**: Floating-point textures are required to store negative values and high-precision accumulation results [S1, unofficial].
-   **Z-Buffer Management**: The early z-test relies on correct depth buffer configuration. If the depth test is not set to `GREATER` or if the depth values are not correctly set via depth replace, termination will not work [S1, unofficial].

## Operating characteristics
-   **Time Complexity**: Linear with respect to the number of samples per ray and the number of pixels, but reduced by early termination [S1, unofficial].
-   **Memory Complexity**: Requires storage for the volume texture, direction texture, and accumulation textures [S1, unofficial].
-   **Performance**: Demonstrated performance gains up to a factor of 3 for typical renditions of volumetric data sets on the ATI 9700 graphics card [S1, unofficial].
-   **Strengths**: Exploits hardware parallelism, enables early ray termination and empty-space skipping, efficient communication between passes [S1, unofficial].
-   **Limitations**: Limited to specific hardware capabilities (Pixel Shader 2.0), dependent texture fetch limits, requires multiple passes [S1, unofficial].
-   **When to Use**: When rendering large volumetric datasets on hardware with Pixel Shader 2.0 support and requiring real-time or interactive performance [S1, unofficial].
-   **When Not to Use**: On hardware without texture render targets or depth replace capabilities, or when single-pass rendering is required [S1, unofficial].

## Background
The method was proposed in 2003 by researchers at the Technical University of Munich (TUM) [S1, unofficial]. It was developed to address the challenge of real-time volume rendering for large scalar fields, which was difficult to achieve on CPUs at the time [S1, unofficial]. The work leveraged the emerging programmable graphics hardware (DirectX 9 level) to implement a stream model for volumetric ray-casting [S1, unofficial].
