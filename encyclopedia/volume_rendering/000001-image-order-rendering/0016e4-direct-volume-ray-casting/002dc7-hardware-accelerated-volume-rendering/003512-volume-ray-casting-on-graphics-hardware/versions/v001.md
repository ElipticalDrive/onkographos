# Volume Ray-Casting on Graphics Hardware

Also called: Stream model for volumetric ray-casting

## Overview
This method implements direct volume ray casting on programmable graphics hardware (specifically DirectX 9-level architectures like the ATI 9700) using a multi-pass stream model [S1, unofficial]. It solves the problem of integrating the volume rendering integral efficiently by exploiting intrinsic parallelism and communication between rendering passes via texture render targets [S1, unofficial]. It sets itself apart from sibling methods by explicitly using an "early z-test" combined with depth replacement to terminate ray traversal or skip empty space, rather than relying solely on fixed-step iteration or geometry-based resampling [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** 3D scalar volume data (stored in 3D textures), transfer functions, camera parameters, and an opacity threshold for early termination.
*   **Output:** A 2D color image (frame buffer).

**Data Structures:**
1.  **Volume Texture:** 3D texture containing scalar density values.
2.  **Ray Direction Textures:** Two 2D textures storing the pre-computed ray direction vectors in local texture coordinates for each pixel.
3.  **Accumulation Textures:** Two 2D textures (render targets) used to store accumulated color and opacity values between passes. These must support floating-point formats to handle negative intermediate values if required by the specific accumulation logic [S1, unofficial].
4.  **Iso-surface Texture:** A 2D texture used to store local texture coordinates of iso-surface intersection points, if applicable.

**Parameters:**
*   **Opacity Threshold:** The accumulated opacity value at which ray traversal terminates. Typical values depend on the transfer function but are often set to allow full visibility of dense structures (e.g., 0.95–0.99) [S1, unofficial].
*   **Fixed Number of Steps:** The algorithm uses a fixed number of rendering passes corresponding to the maximum number of steps along the ray [S1, unofficial].

**Algorithm Steps:**
1.  **Pre-computation:** For each pixel, compute the direction of the ray of sight through the volume in local texture coordinates. Store these directions in two 2D textures [S1, unofficial].
2.  **Initialization:** Initialize the accumulation textures (color and opacity) to zero.
3.  **Main Passes:** Execute a fixed number of rendering passes. In each pass:
    *   Sample the volume texture at the current ray position using the ray direction textures and accumulated position.
    *   Compute the color and opacity contribution using the transfer function and shading model.
    *   Update the accumulated color and opacity in the render target textures using front-to-back compositing:
        $$ C_{new} = C_{old} + c \cdot \alpha \cdot (1 - \alpha_{old}) $$
        $$ \alpha_{new} = \alpha_{old} + \alpha \cdot (1 - \alpha_{old}) $$
        where $c$ and $\alpha$ are the color and opacity of the current sample [S1, unofficial].
    *   Advance the ray position for the next pass.
4.  **Termination Check Pass:** Between main passes, execute an additional pass to test for early termination:
    *   Read the accumulated opacity from the accumulation texture.
    *   If the accumulated opacity exceeds the threshold OR an iso-surface is hit (if iso-surface rendering is enabled):
        *   Set the fragment's depth value ($z$) to the maximum possible value (far plane).
    *   Otherwise:
        *   Set the fragment's depth value ($z$) to zero (near plane).
    *   Set the depth test function to `GREATER`.
    *   This ensures that if the termination condition is met, the fragment's depth is set such that subsequent main passes (which use a standard depth test, typically `LESS`) will fail the early z-test and be discarded, skipping unnecessary computation [S1, unofficial].
5.  **Iso-surface Optimization (Optional):** If an iso-surface is hit, store the intersection coordinates in a 2D texture. A final pass can use this texture to restrict expensive gradient and shading computations to these specific points [S1, unofficial].

**Pseudocode:**
```python
# Pre-computation
ray_directions = compute_ray_directions(camera, volume_bounds)

# Initialization
accum_color = zeros(width, height, 3)
accum_opacity = zeros(width, height, 1)

# Main passes
for step in range(num_steps):
    # Sample volume and compute contribution
    sample_pos = current_ray_position
    density = sample_volume(sample_pos)
    color, opacity = apply_transfer_function(density)
    
    # Update accumulation
    new_color = accum_color + color * opacity * (1 - accum_opacity)
    new_opacity = accum_opacity + opacity * (1 - accum_opacity)
    
    # Write to render target
    write_accumulation_texture(new_color, new_opacity)
    
    # Advance ray
    current_ray_position += ray_direction * step_size

# Termination check pass
for step in range(num_steps - 1): # Check after each main pass except the last
    # Read accumulated opacity
    current_opacity = read_accumulation_opacity()
    
    # Determine depth replacement
    if current_opacity > threshold or iso_surface_hit:
        depth = MAX_DEPTH
    else:
        depth = 0.0
        
    # Set depth test to GREATER so that if depth is MAX_DEPTH,
    # subsequent passes (with LESS test) will fail early z-test
    set_depth_test(GREATER)
    set_depth_replace(depth)
    
    # Execute pass to update depth buffer
    render_termination_check()
    
    # Reset depth test for next main pass
    set_depth_test(LESS)
```

**Edge Cases and Pitfalls:**
*   **Precision:** Floating-point textures are required for accumulation to avoid precision loss with negative values or small increments [S1, unofficial].
*   **Dependent Texture Fetches:** The ATI 9700 has a limited number of dependent texture fetches. Care must be taken to minimize dependencies in the pixel shader to avoid performance degradation [S1, unofficial].
*   **Early Z-Test Enablement:** The early z-test is only effective if all other per-fragment tests (like stencil or alpha tests) are disabled or configured to pass, as the early z-test is applied before the shader execution [S1, unofficial].

## Subtopics

### Hardware-Accelerated Volume Rendering via 3D Texturing
Uses 3D textures directly for ray traversal without explicit multi-pass accumulation textures, relying on hardware texture filtering. Choose when hardware supports efficient 3D texture sampling and when memory bandwidth for 2D texture ping-ponging is a bottleneck. [Link](2799-hardware-accelerated-volume-rendering-via-3d-texturing.md)

### Hardware-based Geometry Unit Resampling
Projects volume slices onto geometry primitives (quads) and uses the geometry unit for resampling. Choose when the scene has sparse volume data or when geometry-based culling is beneficial. [Link](3139-hardware-based-geometry-unit-resampling.md)

### 3D Pixel Texture Classification
Uses 3D textures for classification and shading, often combined with other acceleration techniques. Choose when complex classification is needed and hardware supports 3D texture access. [Link](6055-3d-pixel-texture-classification.md)

### Hardware Shading via Pixel Texture
Focuses on shading computations using pixel textures. Choose when shading complexity is the primary bottleneck. [Link](6056-hardware-shading-via-pixel-texture.md)

### Entry Point Adjustment
Adjusts the starting point of rays to optimize traversal. Choose when the volume has significant empty space near the camera. [Link](7406-entry-point-adjustment.md)

## Operating characteristics
*   **Time Complexity:** $O(N \cdot S)$, where $N$ is the number of pixels and $S$ is the number of steps per ray. Early termination reduces the effective $S$ for opaque regions.
*   **Memory Complexity:** $O(N)$ for accumulation textures, plus storage for volume data and ray directions.
*   **Measured Performance:** Performance gains up to a factor of 3 were demonstrated for typical renditions of volumetric data sets on the ATI 9700 graphics card [S1, unofficial].
*   **Strengths:** Efficient early termination and empty-space skipping via early z-test; exploits hardware parallelism; flexible communication between passes via texture render targets.
*   **Limitations:** Requires multiple rendering passes; dependent texture fetch limits on older hardware (ATI 9700); floating-point texture support required for accumulation.
*   **When to Use:** When running on DirectX 9-level hardware with programmable pixel shaders and floating-point texture support; when early termination is critical for performance.
*   **When Not to Use:** On hardware without floating-point texture support or limited dependent texture fetches; when fixed-step traversal is sufficient and early termination overhead is not justified.

## Background
This method was proposed in 2003 by researchers at the Technical University of Munich (TUM) as part of their work on acceleration techniques for GPU-based volume rendering [S1, unofficial]. It was designed to leverage the emerging programmable graphics hardware (DirectX 9 level) to achieve real-time volume rendering. The approach builds on the observation that CPU-based methods were insufficient for large data sets and that graphics hardware offered significant parallelism and memory bandwidth [S1, unofficial].
