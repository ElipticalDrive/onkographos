# Hardware-Accelerated Volume Rendering via 3D Texturing

Also called: 3D Texture Mapping Volume Rendering, Polygon Resampling with 3D Texturing, RealityEngine 3D Texture Volume Rendering, RealityEngine Volume Rendering

## Overview
This method leverages 3D texturing hardware, specifically the Silicon Graphics RealityEngine, to perform volume reconstruction and resampling in a ray-parallel fashion [S1, unofficial][S2]. It solves the performance bottleneck of software ray casting by embedding resampling polygons within a 3D texture representation of the volume data, allowing the hardware to perform trilinear interpolation automatically [S1, unofficial]. Unlike [Shear-Warp](52-shear-warp.md), which requires a final warp step and performs classification before resampling, this method performs trilinear interpolation followed by classification/compositing without a warp, offering higher image quality and consistent performance for perspective projections [S1, unofficial]. It builds on [Direct volume ray casting](19-direct-volume-ray-casting.md) by delegating the expensive resampling integral evaluation to the graphics pipeline [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** 3D volume data (scalar field), viewing parameters (view matrix, projection), and rendering mode (Radiograph or Opacity-based).
*   **Output:** 2D image in the frame buffer.

**Data Structures:**
*   **3D Texture:** The volume data is loaded into the hardware's 3D texture memory. The RealityEngine supports a maximum of 1,000,000 (1M) 12-bit data points [S1, unofficial]. If the volume exceeds this limit, it must be split into slabs [S1, unofficial].
*   **Resampling Polygons:** 2D polygons defined in either object-space or image-space that traverse the volume. The hardware interpolates the 3D texture values at the vertices and fragments of these polygons [S1, unofficial].
*   **Spacing Texture (2D):** A 2D texture containing the spacing factor $d$ for each pixel, used to account for perspective-dependent sample spacing [S1, unofficial].
*   **Lookup Tables (LUTs):** Used for opacity mapping and exponential computation (radiographs) [S1, unofficial].

**Parameters:**
*   **Exposure ($e$):** A user-controlled scaling factor applied to resampled values to prevent overflow in the 12-bit frame buffer. Range: $[0, 1]$ [S1, unofficial].
*   **Spacing Factor ($d$):** The distance between sample values along the ray. It is constant for all samples behind a specific pixel but varies from pixel to pixel due to perspective [S1, unofficial].

**Algorithm Steps:**

1.  **Load Volume Data:**
    *   Load the volume data into the 3D texture memory.
    *   If the volume size $> 1,000,000$ voxels, split into slabs. Render slabs in succession. The reload time for a new slab is approximately 0.1 seconds [S1, unofficial].

2.  **Define Resampling Polygons:**
    *   Choose an alignment strategy: Object-Space or Image-Space [S1, unofficial].
    *   **Object-Space Alignment:**
        *   Define polygons within the volume coordinate system.
        *   Reorient polygons to lie in the plane most parallel to the view-plane as the viewpoint changes. This requires examining the view matrix and explicitly creating polygons for the six possible view orientations [S1, unofficial].
        *   *Advantage:* Polygon size can be minimized based on feature extent to reduce texturing time [S1, unofficial].
    *   **Image-Space Alignment:**
        *   Define polygons in image space.
        *   Transform polygons by the inverse viewing matrix into object space.
        *   Clip polygons to the boundaries of the volume to ensure valid texture coordinates [S1, unofficial].
        *   *Constraint:* If using slabs, polygons must be rendered multiple times, clipped to the currently loaded volume slab each time [S1, unofficial].

3.  **Render Polygons (Hardware Resampling):**
    *   Issue GL library calls to render the polygons.
    *   The 3D texture hardware performs trilinear interpolation of the volume data at each point on the polygon [S1, unofficial].
    *   Let $u_i$ be the resampled scalar value at the $i$-th sample point behind a pixel.

4.  **Scale and Sum:**
    *   Scale each resampled value $u_i$ by the exposure value $e$: $u'_i = u_i \cdot e$ [S1, unofficial].
    *   Sum the scaled values at each pixel: $S = \sum u'_i$ [S1, unofficial].
    *   Clamp the sum $S$ if it exceeds the 12-bit range (max value 4095) to prevent overflow [S1, unofficial].

5.  **Apply Spacing Factor:**
    *   Multiply the summation results by the spacing factor $d$ for each pixel. This is achieved by rendering an additional full-screen polygon with a 2D texture containing the $d$ values [S1, unofficial].
    *   Result: $P = S \cdot d$ [S1, unofficial].

6.  **Combine to Final Color:**
    *   Apply the combining operation based on the rendering mode [S1, unofficial]:
        *   **Radiographs (Attenuation):** Compute the exponential of the summed attenuation integral.
            $$ I = 1.0 - \exp(-P) $$
            Use a lookup table to compute the exponential at each pixel if the hardware does not support it directly [S1, unofficial].
        *   **Opacity-Based Rendering:**
            *   Use two 8-bit texture components: raw data and a precomputed shading coefficient.
            *   Use the resampled data component values as indices into an opacity lookup table (using texture hardware for speed) to get sample opacity $\alpha_i$ [S1, unofficial].
            *   Multiply sample opacity by the shading coefficient $s$ (a function of the original data gradient) to produce shaded features: $\alpha_{final} = \alpha_i \cdot s$ [S1, unofficial].
            *   Composite the shaded samples using front-to-back accumulation into the frame buffer [S1, unofficial].

**Pseudocode:**

    """
    Renders volume data using 3D texture hardware.
    
    Args:
        volume_data: 3D array of voxel values.
        view_matrix: 4x4 view transformation matrix.
        exposure: Scaling factor e in [0, 1].
        mode: 'radiograph' or 'opacity'.
        
    Returns:
        Image buffer.
    """
    
    # 1. Load Volume into 3D Texture
    # Check if volume fits in 1M 12-bit points
    if volume_data.size > 1000000:
        slabs = split_into_slabs(volume_data, max_size=1000000)
        for slab in slabs:
            load_texture_3d(slab)
            render_slab(view_matrix, exposure, mode)
    else:
        load_texture_3d(volume_data)
        render_slab(view_matrix, exposure, mode)

    polygons = define_object_space_polygons(view_matrix)
    
    # 3. Render Polygons

        # Hardware performs trilinear interpolation at each fragment
        # Let u_i be the interpolated values
        u_samples = hardware_trilinear_interpolate(poly)
        
        # 4. Scale and Sum
        scaled_samples = [u * exposure for u in u_samples]
        sum_s = sum(scaled_samples)
        
        # Clamp to 12-bit range
        sum_s = clamp(sum_s, 0, 4095)

            intensity = 1.0 - lookup_exp(-p)
            write_to_frame_buffer(intensity)
            
        elif mode == 'opacity':
            # Get opacity from LUT using raw data value
            opacity = lookup_opacity(u_samples[0]) # Assuming first sample index
            # Get shading coefficient (precomputed)
            shading = get_shading_coefficient(poly)
            # Composite

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of pixels processed and the number of resampling polygons [S1, unofficial]. Doubling screen pixels or resampling polygons halves the frame rate [S1, unofficial].
*   **Memory Complexity:** Limited by the hardware's 3D texture memory capacity (1M 12-bit points on RealityEngine) [S1, unofficial]. Large volumes require slabbing, adding overhead for texture reloading (~0.1 seconds per slab) [S1, unofficial].
*   **Measured Performance:**
    *   Small Volume (128x128x64): 10 frames/second into a 512x512 window using 128 object-space polygons. Processing rate: 10 million voxels/second. Measured: ~160 million pixel operations/second (each op: trilinear interpolation, multiplication, summation/composite) [S1, unofficial].
    *   Large Volume (256x256x64): 2.5 frames/second into a 512x512 window using 256 resampling polygons. Requires four 256x256x16 texture slabs [S1, unofficial].
    *   Large Volume (512x512x512): Can be rendered several times a second, achieving quality close to software ray casting [S2].
*   **Strengths:** High performance for interactive visualization; leverages existing 3D texturing hardware; simple implementation [S1, unofficial].
*   **Limitations:** Precision limited to 12 bits per frame buffer and texture component, requiring careful exposure control to prevent overflow [S1, unofficial]. Object-space method requires explicit polygon reorientation for different views [S1, unofficial]. Image-space method requires clipping and potentially multiple renders per slab [S1, unofficial]. Lighting is fixed or precomputed unless extended (e.g., PixelFlow) [S1, unofficial].
*   **When to use:** When high-performance volume rendering is needed on hardware with 3D texturing support, and lighting requirements are static or can be precomputed.
*   **When not to use:** When dynamic, view-dependent lighting is required without CPU offloading, or when the volume exceeds hardware texture memory significantly and slabbing overhead is unacceptable.

## Background
This method was introduced by Timothy J. Cullip and Ulrich Neumann in 1993, specifically designed for the Silicon Graphics RealityEngine workstations [S1, unofficial]. It was one of the first methods to exploit 3D texture mapping hardware for volume rendering, moving away from software-based ray casting. The approach was also proposed for the PixelFlow graphics system to overcome lighting and volume size limitations of the RealityEngine [S1, unofficial]. It is used in the production of digitally reconstructed radiographs and opacity-based volume rendered images [S1, unofficial].
