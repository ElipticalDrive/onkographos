# Hardware-Accelerated Volume Rendering via 3D Texturing

Also called: 3D Texture Mapping Volume Rendering, 3D Texturing Example, Planar Texture Resampling, Polygon Resampling with 3D Texturing, RealityEngine 3D Texture Volume Rendering, RealityEngine Volume Rendering, Texture Mapping for Volume Rendering

## Overview
This method leverages 3D texture mapping hardware to perform reconstruction and resampling of volumetric data in a ray-parallel fashion [S2, unofficial][S4]. It solves the performance bottleneck of software ray casting by offloading the trilinear interpolation and resampling steps to the graphics hardware's texture engine [S1][S2, unofficial]. Unlike [Shear-Warp](5616-hardware-accelerated-volume-rendering.md), which performs classification before bilinear resampling and requires a final warp step, this method performs trilinear interpolation followed by classification and requires no final warp, resulting in higher image quality and consistent performance for perspective projections [S1]. It builds on the standard ray casting pipeline defined in [Hardware-Accelerated Volume Rendering](5616-hardware-accelerated-volume-rendering.md) but replaces the software-based sampling loop with hardware-accelerated polygon rasterization [S2, unofficial].

## How it works
**Inputs:** A scalar volume dataset $V$, camera parameters (origin $\mathbf{o}$, direction $\mathbf{d}$), and transfer function parameters.
**Outputs:** A 2D image frame buffer.

**Data Structures:**
1.  **3D Texture:** The volume data is stored in 3D texture memory. For high-performance systems like the SGI Reality Engine, an 8-way interleaved memory layout is used to allow fetching any tri-linear cell (8 adjacent voxels) in one memory access [S1]. A voxel with address $a = [zyx]$ is stored in memory module $k$ at index $i$ as follows [S1]:
    $$
    k = (x \bmod 2) + 2 (y \bmod 2) + 4 (z \bmod 2)
    $$
    $$
    i = \lfloor x/2 \rfloor + 2 \lfloor y/2 \rfloor + 4 \lfloor z/2 \rfloor
    $$
2.  **Resampling Polygons:** Planar polygons are defined to intersect the volume. These polygons define the sampling planes. Two alignment strategies exist:
    *   **Object-Space:** Polygons are defined within the volume coordinate system. They must be reoriented in the plane most parallel to the view-plane as the viewpoint changes, explicitly creating polygons for six cases arising from view orientation [S2, unofficial].
    *   **Image-Space:** Polygons are defined in image-space and transformed by the inverse viewing matrix into object-space. They must be clipped to the boundaries of the volume to ensure valid texture coordinates [S2, unofficial].
3.  **Lookup Tables (LUT):** Maps scalar values to RGBA color and opacity [S1].

**Steps:**
1.  **Load Volume:** Load the volume data into 3D texture memory. If the volume exceeds the texture memory limit (e.g., 1M 12-bit data points on RealityEngine), split it into slabs and render them in succession [S2, unofficial].
2.  **Define Polygons:** Define resampling polygons based on the chosen alignment strategy (Object-Space or Image-Space) [S2, unofficial].
3.  **Configure Texture Engine:**
    *   Set the global texture environment mode to `GL_MODULATE` [S3, unofficial].
    *   Enable 3D texturing [S3, unofficial].
    *   Bind the 3D texture object [S3, unofficial].
    *   Switch the matrix mode to `GL_TEXTURE` [S3, unofficial].
    *   Apply a translation of $(0.5, 0.5, 0.5)$ to the texture matrix to correct for texture coordinate centering [S3, unofficial].
    *   Reset the texture matrix to identity [S3, unofficial].
4.  **Render Polygons:**
    *   Switch matrix mode back to `GL_MODELVIEW` [S3, unofficial].
    *   For each vertex $i$ of the polygon, set the 3D texture coordinate to $(x_i, y_i, z_i)$ and the vertex position to $(x_i, y_i, z_i)$ [S3, unofficial].
    *   The hardware rasterizer connects to the texture engine, which resamples the texture data using tri-linear interpolation at each point on the polygon [S1].
5.  **Apply Spacing Factors:** The resampled values $u'_i$ behind a pixel are summed. The spacing factor $d$ (constant for all samples behind a pixel but varying per pixel due to perspective) is applied using an additional full-screen polygon with a 2D texture corresponding to the $d$ values [S2, unofficial].
6.  **Combine and Composite:**
    *   **Radiographs:** Compute the exponential of the summed attenuation integral: $\text{pixel intensity} = 1.0 - \exp(-\sum u_i d)$ [S2, unofficial]. This can be done via a lookup table.
    *   **Opacity-Based Rendering:** Use two 8-bit texture components: raw data and precomputed shading coefficient. Use resampled data component values as indices into an opacity lookup table (using texture hardware for speed). Multiply sample opacity by the shading coefficient to produce shaded features [S2, unofficial].
    *   **General Compositing:** Sum the scaled resampled values. Scale each resampled value by an 'exposure' value (0 to 1) to prevent overflow in the 12-bit frame buffer. Clamp the sum if it exceeds the 12-bit range [S2, unofficial].
7.  **Cleanup:** Unbind the 3D texture and disable 3D texturing [S3, unofficial].

**Pseudocode:**
```python
def render_3d_texture_volume(volume_data, camera, transfer_function, alignment='object_space'):
    # 1. Load Volume
    if volume_data.size > TEXTURE_MEMORY_LIMIT:
        slabs = split_into_slabs(volume_data)
        for slab in slabs:
            load_texture(slab)
            render_slab(camera, transfer_function, alignment)
    else:
        load_texture(volume_data)
        render_slab(camera, transfer_function, alignment)

def render_slab(camera, transfer_function, alignment):
    # 2. Define Polygons
    if alignment == 'object_space':
        polygons = define_object_space_polygons(camera.view_matrix)
    else:
        polygons = define_image_space_polygons(camera.view_matrix)
        polygons = clip_to_volume_boundaries(polygons)

    # 3. Configure Texture Engine
    set_texture_env_mode(GL_MODULATE)
    enable_texture_3d()
    bind_texture(volume_texture_id)
    
    glMatrixMode(GL_TEXTURE)
    glLoadIdentity()
    glTranslated(0.5, 0.5, 0.5)
    glMatrixMode(GL_MODELVIEW)

    # 4. Render Polygons
    for poly in polygons:
        glBegin(GL_QUADS)
        for i in range(4):
            vertex = poly.vertices[i]
            glTexCoord3f(vertex.x, vertex.y, vertex.z)
            glVertex3d(vertex.x, vertex.y, vertex.z)
        glEnd()

    # 5. Apply Spacing Factors (via full-screen quad with 2D texture)
    apply_spacing_factors(camera)

    # 6. Combine and Composite
    # Handled by hardware compositing into frame buffer
    # For radiographs: pixel_intensity = 1.0 - exp(-sum(u_i * d))
    # For opacity: opacity = LUT(resampled_value) * shading_coefficient

    # 7. Cleanup
    bind_texture(0)
    disable_texture_3d()
```

**Edge Cases and Pitfalls:**
*   **Overflow:** The RealityEngine has a maximum precision of 12 bits per frame buffer and texture component. Summation can overflow this limit. Solution: Scale samples by an 'exposure' value (0 to 1) and clamp [S2, unofficial].
*   **Clipping:** Image-space polygons must be clipped to volume boundaries to ensure valid texture coordinates. This requires transforming to object-space, clipping, and then rendering [S2, unofficial].
*   **Slab Rendering:** When using image-space method with slabs, polygons must be rendered multiple times, clipped to the currently loaded volume slab each time [S2, unofficial].
*   **Shading:** Hardware does not directly support estimation of gradients or per-sample illumination. Gradients must be pre-computed and stored in an additional volume or computed on-the-fly using multi-pass methods, which greatly reduce achievable frame rate [S1]. An alternative is to use a shading approximation by pairwise subtracting coplanar texture slices, one shifted in direction of the light source [S1].

## Subtopics

### [Planes Method](3027-planes-method.md)
The Planes Method is a hardware-accelerated volume rendering technique that leverages 3D texture mapping hardware to resample volumetric data into planes coplanar with rays ending in a row of pixels, then performs shading and front-to-back compositing on the CPU. It solves the problem of view-dependent shading and interactive classification in texture-mapped rendering by offloading the computationally intensive Phong shading and compositing logic to the processor, allowing for optimization techniques like early ray termination and low-opacity skipping. Unlike [Shear-Warp](5616-hardware-accelerated-volume-rendering.md), which performs classification before bilinear resampling and requires a final warp step, the Planes method performs trilinear interpolation followed by classification and requires no final warp, resulting in higher image quality and consistent performance for perspective projections.

### BVH-accelerated 3D Texture Volume Rendering
A method to accelerate 3D texture-based volume rendering using hierarchical bounding volumes (BVH) to skip rendering of empty or occluded sub-volumes during tree traversal [S5, abstract only, unofficial]. It realizes post-classification 3D texture volume rendering using GPU fragment shaders. The original volume data is divided based on space position layer by layer according to the height of the BVH tree. In each layer, the volumes corresponding to BVH tree nodes are subdivided into eight sub-volumes along three orthogonal coordinate axes. Bounding volumes are established for the sub-volumes and correlative information is stored in the corresponding BVH tree nodes. When rendering the volume by traversing the BVH tree, information of BVH tree nodes is read to judge whether the corresponding sub-volume should be rendered or jumped [S5, abstract only, unofficial]. The method obtains good accelerating effects when combined with 3D texture volume rendering based on GPU [S5, abstract only, unofficial].

## Operating characteristics
**Time and Memory Complexity:**
*   Performance is linear with respect to the number of pixels processed. Doubling screen pixels or resampling polygons halves the frame rate [S2, unofficial].
*   Quality vs Speed Trade-off: Using more resampling polygons yields higher quality images at the expense of lower rendering speed [S2, unofficial].
*   Texture memory is limited (e.g., 1M 12-bit data points on RealityEngine). Larger volumes require slab loading, which adds overhead (~0.1 seconds per slab reload) [S2, unofficial].

**Measured Performance:**
*   SGI Reality Engine 2 with two Rasters Managers (RMs) renders a 256x256x32 volume at 12 frames per second [S1].
*   SGI Reality Engine 2 with four RMs renders a 512x512x64 dataset at 10 frames per second [S1].
*   128x128x64 volume rendered into 512x512 window at 10 frames/second using 128 object-space polygons. Processing rate: 10 million voxels/second. Measured: ~160 million pixel operations/second (each op: trilinear interpolation, multiplication, summation/composite) [S2, unofficial].
*   256x256x64 volume rendered into 512x512 window at 2.5 frames/second using 256 resampling polygons. Requires four 256x256x16 texture slabs. Slab load time: <0.1 seconds/slab [S2, unofficial].
*   This method can render volume data about 512 x 512 x 512 voxels in size several times a second, achieving results very close in quality to software ray casting [S4].

**Strengths and Limitations:**
*   **Strengths:** High performance for large volumes; leverages existing hardware; simple implementation [S2, unofficial].
*   **Limitations:** Limited by texture memory size; shading is difficult to implement in hardware; image-space method requires clipping and multiple renders per slab [S2, unofficial].

**When to Use:**
*   When interactive frame rates are required for large volumes on hardware with 3D texture support (e.g., SGI RealityEngine) [S2, unofficial].
*   For production of digitally reconstructed radiographs and opacity-based volume rendered images [S2, unofficial].

**When Not to Use:**
*   When complex per-sample shading or lighting is required, as hardware does not support gradient estimation directly [S1].
*   When the volume size exceeds texture memory limits and slab loading overhead is unacceptable [S2, unofficial].

## Background
This method was developed in the mid-1990s, primarily associated with the Silicon Graphics RealityEngine workstations [S2, unofficial]. It was proposed as a way to accelerate volume reconstruction by leveraging the 3D texturing hardware available in these systems [S2, unofficial]. The technique was applied to the production of digitally reconstructed radiographs and opacity-based volume rendered images [S2, unofficial]. It was also proposed for the PixelFlow graphics system to overcome lighting and volume size limitations of the RealityEngine [S2, unofficial]. The method builds on the concept of planar texture resampling [CCF94] and uses lookup tables to map density to RGBA color and opacity [S1].
