# Hardware-Accelerated Volume Rendering via 3D Texturing

Also called: 3D Texture Mapping Volume Rendering, 3D Texturing Example, Planar Texture Resampling, Polygon Resampling with 3D Texturing, RealityEngine 3D Texture Volume Rendering, RealityEngine Volume Rendering, Texture Mapping for Volume Rendering

## Overview
This method leverages 3D texture mapping hardware to perform reconstruction and resampling of volumetric data by embedding polygons within the texture space [S2, unofficial]. It evaluates the classic ray casting volume rendering formula in a ray-parallel fashion, using the graphics hardware's texture engine to perform trilinear interpolation on textured planes parallel to the image plane [S1, S4]. Unlike software ray casting, it offloads the expensive interpolation and resampling steps to dedicated hardware, enabling interactive frame rates for large datasets [S4]. It differs from [Shear-Warp](link-to-shear-warp) by performing trilinear interpolation followed by classification without requiring a final warp step, and from [Back-face rasterized volume rendering](1296-back-face-rasterized-volume-rendering.md) by using 3D texture memory rather than 2D slice accumulation [S1].

## How it works
### Inputs and Outputs
**Inputs:**
*   Scalar volume data $V$ stored in 3D texture memory.
*   Camera parameters (origin $\mathbf{o}$, direction $\mathbf{d}$) defining the view.
*   Transfer function mapping scalar values to color $C$ and opacity $\alpha$.
*   Resampling polygons defining the sampling planes.

**Outputs:**
*   Final image in the frame buffer, composited from the resampled texture slices.

### Data Structures
**3D Texture Memory:**
*   The volume is stored as a 3D texture object.
*   **Memory Layout:** High-performance engines (e.g., SGI Reality Engine) use 8-way interleaved texture memory to allow fetching any tri-linear cell (8 adjacent voxels) in one memory access [S1].
*   **Voxel Addressing:** For a voxel with address $a = [zyx]$, the memory module $k$ and index $i$ within the module are calculated as [S1]:
    $$
    k = (x \bmod 2) + 2 (y \bmod 2) + 4 (z \bmod 2)
    $$
    $$
    i = \lfloor x/2 \rfloor + 2 \lfloor y/2 \rfloor + 4 \lfloor z/2 \rfloor
    $$
*   **Capacity:** The RealityEngine texture memory is limited to 1,000,000 (1M) 12-bit data points [S2, unofficial]. Larger volumes are split into slabs.

**Resampling Polygons:**
*   Polygons are defined to lie within the volume. Two alignment strategies exist:
    1.  **Object-Space:** Polygons are defined within the volume coordinate system. They must be reoriented in the plane most parallel to the view-plane as the viewpoint changes, explicitly creating polygons for six cases arising from view orientation [S2, unofficial][S1].
    2.  **Image-Space:** Polygons are defined in image-space, transformed by the inverse viewing matrix into object-space, and clipped to the volume boundaries to ensure valid texture coordinates [S2, unofficial].

### Steps
1.  **Load Volume:** Load volume data into 3D texture memory. If the volume exceeds 1M 12-bit points, split into slabs and load them successively [S2, unofficial].
2.  **Define Polygons:** Define resampling polygons using either Object-Space or Image-Space alignment [S2, unofficial].
3.  **Configure Texture Engine:**
    *   Set global texture environment mode to `GL_MODULATE` [S3, unofficial].
    *   Enable 3D texturing [S3, unofficial].
    *   Bind the specific 3D texture object identified by `texid` [S3, unofficial].
    *   Switch matrix mode to `GL_TEXTURE` [S3, unofficial].
    *   Apply a translation of $(0.5, 0.5, 0.5)$ to the texture matrix to correct for texture coordinate centering [S3, unofficial].
    *   Reset the texture matrix to identity if necessary before defining polygon vertices [S3, unofficial].
4.  **Render Polygons:**
    *   Switch matrix mode back to `GL_MODELVIEW` [S3, unofficial].
    *   For each vertex $i$ (0 to 3) of a quad:
        *   Set the 3D texture coordinate to $(x_i, y_i, z_i)$ [S3, unofficial].
        *   Set the vertex position to $(x_i, y_i, z_i)$ [S3, unofficial].
    *   Render the quad using `GL_QUADS` [S3, unofficial].
    *   The 3D texture hardware performs trilinear interpolation of the volume data at each point on the polygon [S2, unofficial].
5.  **Scale and Sum:**
    *   Scale each resampled value by an 'exposure' value $E$ (range 0 to 1) to prevent overflow in the 12-bit frame buffer [S2, unofficial].
    *   Sum the scaled resampled values at each pixel [S2, unofficial].
    *   Clamp the sum if it exceeds the 12-bit range [S2, unofficial].
    *   Apply spacing factors $d$ to the summation results. Since $d$ is constant for all samples behind a pixel but varies from pixel to pixel due to perspective, use an additional full-screen polygon with a 2D texture corresponding to the $d$ values [S2, unofficial].
6.  **Combine and Composite:**
    *   **Direct Summation:** Use the summed values directly [S2, unofficial].
    *   **Radiographs:** Compute the exponential of the summed attenuation integral:
        $$
        \text{pixel intensity} = 1.0 - \exp\left(-\sum u_i d\right)
        $$
        where $u_i$ are the resampled values [S2, unofficial]. This can be computed using a lookup table at each pixel [S2, unofficial].
    *   **Opacity-Based Rendering:** Use two 8-bit texture components: raw data and precomputed shading coefficient. Use resampled data component values as indices into an opacity lookup table (using texture hardware for speed). Multiply sample opacity by the shading coefficient (function of original data gradient) to produce shaded features [S2, unofficial].
7.  **Cleanup:**
    *   Unbind the 3D texture by binding texture ID 0 [S3, unofficial].
    *   Disable 3D texturing [S3, unofficial].

### Pseudocode
```python
def render_volume_3d_texturing(volume_data, camera, transfer_function, polygons):
    # 1. Load volume into 3D texture memory
    tex_id = load_3d_texture(volume_data)
    
    # 2. Configure texture engine
    set_texture_env_mode(GL_MODULATE)
    enable_texture_3d()
    bind_texture(tex_id)
    
    switch_matrix_mode(GL_TEXTURE)
    load_identity()
    translate(0.5, 0.5, 0.5)
    switch_matrix_mode(GL_MODELVIEW)
    
    # 3. Render resampling polygons
    for poly in polygons:
        begin(GL_QUADS)
        for i in range(4):
            vertex = poly.vertices[i]
            # Set texture coordinates to vertex position for 3D texturing
            tex_coord3f(vertex.x, vertex.y, vertex.z)
            vertex3d(vertex.x, vertex.y, vertex.z)
        end()
        
    # 4. Apply spacing factors and compositing (handled by hardware/compositor)
    # Note: Specific compositing logic (opacity vs radiograph) depends on application
    # For opacity-based:
    #   - Use precomputed shading coefficients in texture
    #   - Lookup opacity from resampled values
    #   - Composite into frame buffer
    
    # 5. Cleanup
    bind_texture(0)
    disable_texture_3d()
    delete_texture(tex_id)
```

### Parameters
*   **Interpolation:** Tri-linear interpolation is used by the texture engine [S1].
*   **Exposure Value:** User-controlled scaling factor $E \in [0, 1]$ applied to resampled values to prevent overflow [S2, unofficial].
*   **Data Size:** Typical data size for interactive performance is $512 \times 512 \times 512$ voxels [S4].
*   **Memory Interleaving:** 8-way interleaved texture memory is used [S1].
*   **Texture Memory Limit:** 1M 12-bit data points [S2, unofficial].
*   **Reload Time:** ~0.1 seconds to reload texture memory with a new slab subset [S2, unofficial].

### Edge Cases and Pitfalls
*   **Gradient Estimation:** Hardware does not directly support estimation of gradients or per-sample illumination. Gradients must be pre-computed and stored in an additional volume or computed on-the-fly using multi-pass methods, which greatly reduce achievable frame rate [S1]. An alternative is to use a shading approximation by pairwise subtracting coplanar texture slices, one shifted in direction of the light source [S1].
*   **Overflow:** The RealityEngine has a maximum precision of 12 bits per frame buffer and texture component. Summation can overflow this limit. Solution: Scale samples by 'exposure' value and clamp [S2, unofficial].
*   **Image-Space Clipping:** Image-space polygons must be clipped to volume boundaries to ensure valid texture coordinates. This requires transforming to object-space, clipping, and then rendering [S2, unofficial].
*   **Slab Rendering:** When using image-space method with slabs, polygons must be rendered multiple times, clipped to the currently loaded volume slab each time [S2, unofficial].

## Subtopics

### [Planes Method](3027-planes-method.md)
The Planes Method is a hardware-accelerated volume rendering technique that leverages 3D texture mapping hardware to resample volumetric data into planes coplanar with rays ending in a row of pixels, then performs shading and front-to-back compositing on the CPU. It solves the problem of view-dependent shading and interactive classification in texture-mapped rendering by offloading the computationally intensive Phong shading and compositing logic to the processor, allowing for optimization techniques like early ray termination and low-opacity skipping. Unlike [Shear-Warp](link-to-shear-warp), which performs classification before bilinear resampling and requires a final warp step, the Planes method performs trilinear interpolation followed by classification and requires no final warp, resulting in higher image quality and consistent performance for perspective projections.

### BVH-accelerated 3D Texture Volume Rendering
A method to accelerate 3D texture-based volume rendering using hierarchical bounding volumes (BVH) to skip rendering of empty or occluded sub-volumes during tree traversal [S5, abstract only, unofficial]. It realizes post-classification 3D texture volume rendering using GPU fragment shaders [S5, abstract only, unofficial]. The original volume data is divided based on space position layer by layer according to the height of the BVH tree [S5, abstract only, unofficial]. In each layer, volumes corresponding to BVH tree nodes are subdivided into eight sub-volumes along three orthogonal coordinate axes [S5, abstract only, unofficial]. Bounding volumes are established for the sub-volumes and correlative information is stored in the corresponding BVH tree nodes [S5, abstract only, unofficial]. When rendering the volume by traversing the BVH tree, information of BVH tree nodes is read to judge whether the corresponding sub-volume should be rendered or jumped [S5, abstract only, unofficial]. The method obtains good accelerating effects when combined with 3D texture volume rendering based on GPU [S5, abstract only, unofficial].

## Operating characteristics
*   **Time Complexity:** Performance is linear with respect to the number of pixels processed. Doubling screen pixels or resampling polygons halves the frame rate [S2, unofficial].
*   **Memory Complexity:** Limited by texture memory capacity (1M 12-bit points on RealityEngine) [S2, unofficial]. Larger volumes require slab loading, adding overhead (~0.1s per slab) [S2, unofficial].
*   **Measured Performance:**
    *   SGI Reality Engine 2 with two Rasters Managers (RMs) renders a $256 \times 256 \times 32$ volume at 12 frames per second [S1].
    *   SGI Reality Engine 2 with four RMs renders a $512 \times 512 \times 64$ dataset at 10 frames per second [S1].
    *   $128 \times 128 \times 64$ volume rendered into $512 \times 512$ window at 10 frames/second using 128 object-space polygons. Processing rate: 10 million voxels/second. Measured: ~160 million pixel operations/second (each op: trilinear interpolation, multiplication, summation/composite) [S2, unofficial].
    *   $256 \times 256 \times 64$ volume rendered into $512 \times 512$ window at 2.5 frames/second using 256 resampling polygons. Requires four $256 \times 256 \times 16$ texture slabs [S2, unofficial].
    *   Can render volume data about $512 \times 512 \times 512$ voxels in size several times a second, achieving results very close in quality to software ray casting [S4].
*   **Strengths:** High performance for large datasets; leverages existing 3D graphics hardware; simple implementation [S2, unofficial].
*   **Limitations:** Limited by texture memory size; no direct hardware support for gradient-based shading; perspective distortion requires careful polygon definition [S1][S2, unofficial].
*   **When to use:** Interactive visualization of large volumetric datasets on hardware with 3D texturing support [S2, unofficial].
*   **When not to use:** When high-quality gradient-based shading is required without pre-computation; when texture memory is insufficient and slab loading overhead is prohibitive [S1][S2, unofficial].

## Background
This method was developed by Timothy J. Cullip and Ulrich Neumann at the University of North Carolina at Chapel Hill and published in 1993 [S2, unofficial]. It was designed to leverage the 3D texturing hardware in Silicon Graphics RealityEngine workstations [S2, unofficial]. The technique builds on the concept of planar texture resampling [CCF94] and was applied to the production of digitally reconstructed radiographs and opacity-based volume rendered images [S2, unofficial]. It was also proposed for the PixelFlow graphics system to overcome lighting and volume size limitations of the RealityEngine [S2, unofficial].
