# Hardware-based Direct Volume Ray Casting

Also called: VIRIM DSP shading, VIRIM Ray-Casting Unit

## Overview
This method implements direct volume ray casting using dedicated programmable Digital Signal Processors (DSPs) to handle the computationally intensive tasks of shading and compositing, decoupled from the geometry generation stage. It solves the bottleneck of real-time volume visualization by offloading the per-voxel light-material interaction calculations from a general-purpose CPU or generic graphics hardware to specialized hardware units. Unlike [Hardware-based Geometry Unit Resampling](3139-hardware-based-geometry-unit-resampling.md), which focuses on data transformation, this method focuses on the optical model execution, specifically supporting the Heidelberg Raytracing algorithm.

## How it works
The system consists of a geometry unit that generates sample data and a ray-casting unit containing DSPs that process this data into the final image.

**Inputs and Outputs:**
*   **Input:** Sample density values and gradient vectors for volume elements, transmitted from the geometry unit.
*   **Output:** Final image scanlines stored in local DSP memory, subsequently collected by a master CPU.

**Data Structures and Layout:**
*   **Sample Data:** 16-bit precision for both density and gradient values [S1].
*   **FIFO Buffer:** Asynchronous first-in-first-out buffer receiving data from the geometry unit bus [S1].
*   **Local Memory:** Stores calculated scanlines per DSP [S1].
*   **LUTs:** Look-up tables accessible by the host system for real-time reloading [S1].

**Numbered Steps:**
1.  **Data Transmission:** The geometry unit transmits sample density and gradient values to the ray-casting units over a dedicated bus. The peak transfer rate is 240 MBytes/sec at a clock speed of 40 MHz [S1].
2.  **Buffering:** Each DSP receives these values from its associated FIFO buffer. This mechanism decouples the fast geometry unit from the slower DSPs; for the Heidelberg Raytracing algorithm, the geometry unit is approximately 16 times faster than a DSP [S1].
3.  **Computation:** Within 15 clock cycles, the DSP computes the interaction of light and material for each volume element. This involves applying shading models (e.g., using Sobel filters for gradients) and compositing [S1].
4.  **Storage:** One or more scanlines of the resulting projection are calculated per DSP and stored in the DSP's local memory [S1].
5.  **Collection:** A local master CPU on the board collects all scanlines from the DSP memories and transfers the final image results to the host system [S1].

**Formulas and Parameters:**
*   **Precision:** All calculations for density and gradient values are performed with 16-bit data resolution [S1].
*   **Throughput:** Bus peak rate = 240 MBytes/sec; Clock = 40 MHz [S1].
*   **Latency:** DSP computation time $\le$ 15 clock cycles per volume element [S1].
*   **Performance Ratio:** Geometry unit speed $\approx$ 16 $\times$ DSP speed [S1].

**Pseudocode:**
```python
# Pseudocode representing the hardware pipeline flow
# Note: This describes the data flow and timing constraints rather than shader code

function hardware_ray_casting_pipeline():
    # 1. Geometry Unit generates data
    # Density and Gradient (16-bit) are generated
    geometry_data = geometry_unit.generate_samples()
    
    # 2. Transmission over Bus
    # Peak rate: 240 MB/s at 40 MHz
    bus_transfer(geometry_data, fifo_buffer)
    
    # 3. DSP Processing
    # Each DSP reads from FIFO asynchronously
    for each dsp in ray_casting_units:
        # Decoupling ensures DSPs are not stalled by geometry speed
        samples = fifo_buffer.read()
        
        # Computation: Light and material interaction
        # Takes <= 15 clock cycles per voxel
        # Uses 16-bit precision for density and gradients
        scanline = dsp.compute_shading_and_compositing(samples)
        
        # Store result in local memory
        dsp.local_memory.write(scanline)
        
    # 4. Master CPU Collection
    # No inter-DSP communication is required
    final_image = []
    for each dsp in ray_casting_units:
        scanline = dsp.local_memory.read()
        final_image.append(scanline)
        
    # 5. Transfer to Host
    host_system.receive(final_image)
```

**Edge Cases and Pitfalls:**
*   **Precision:** The reliance on 16-bit data for density and gradients may limit dynamic range compared to 32-bit floating-point implementations [S1].
*   **Decoupling Overhead:** The asynchronous FIFO buffer is critical; if the geometry unit stalls or the DSPs are overloaded, the buffer must handle the disparity (geometry is ~16x faster) [S1].

## Subtopics

### Ray Projection Tree
A hardware mechanism structured as a hierarchical binary tree of Voxel Combination Units (VCUs) that accepts $n$ voxels along a viewing ray at the leaves and produces the final pixel color at the root. It differs from the DSP-based approach by using a fixed-function pipelined tree structure rather than programmable DSPs. It supports various projection schemes including first/last opaque, max/min voxel value, weighted summation, and compositing, unlike the original beam projection mechanism which was limited.
*   **Steps:**
    1.  Feed $n$ input voxels comprising a ray into $n/2$ VCUs.
    2.  Each VCU combines two input voxels into an output voxel value in 7 time units, producing $n/2$ results.
    3.  Feed the $n/2$ results into the next stage of the tree (containing $n/4$ VCUs) while simultaneously feeding the next ray of $n$ voxels into the first stage.
    4.  After an initialization time of $7 \log n$ time units, the tree processes $\log n$ rays simultaneously in a pipeline fashion, producing a new pixel color every 7 time units.
*   **Parameters:** VCU Latency: 7 time units per combination. Initialization Time: $7 \log n$ time units.
*   **Layout:** Hierarchical binary tree of $n-1$ VCUs.
*   **Source:** [S2]

## Operating characteristics
*   **Performance:** Estimated at 2.5 Hz for a $256 \times 256 \times 128$ dataset using one VIRIM module (four boards, 36x39 cm² each) [S1].
*   **Complexity:** The geometry unit operates at a speed factor of ~16 relative to the DSPs, requiring careful buffering [S1].
*   **Strengths:** High flexibility via programmable DSPs allowing any shading model implementation, provided data remains in one sample plane. Decoupled architecture allows independent optimization of geometry and shading [S1].
*   **Limitations:** Requires dedicated hardware (VIRIM boards). Inter-DSP communication is not supported in the current model, relying on the master CPU for any necessary coordination [S1].
*   **When to use:** Real-time visualization of large volume datasets where custom hardware is available.
*   **When not to use:** When flexibility for arbitrary shading models on standard GPUs is preferred, or when inter-processor communication between shading units is required.

## Background
The method was developed as part of the VIRIM (Volume Rendering Image Machine) project. It was described in the paper "Three Architectures for Volume Rendering" by Westermann et al. (1995) [S1]. The architecture was designed to address the performance limitations of software-based volume rendering by utilizing specialized hardware components, specifically programmable DSPs for the ray-casting phase.
