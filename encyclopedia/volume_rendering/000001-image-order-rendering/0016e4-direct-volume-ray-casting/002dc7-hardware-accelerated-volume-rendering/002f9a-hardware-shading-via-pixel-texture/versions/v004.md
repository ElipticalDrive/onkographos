# Hardware Shading via Pixel Texture

Also called: Quantized Normal Shading

## Overview
This method integrates surface shading into texture-memory based volume rendering by encoding quantized surface normals into a 2D pixel texture, thereby avoiding hardware interpolation redundancy and truncation errors [S1, S2]. It distinguishes itself from standard hardware-accelerated approaches by explicitly managing normal precision through software-generated pixel textures and nearest-neighbor lookups, adding significant visual quality with negligible rendering cost [S1].

## How it works
The method extends the standard direct volume ray casting pipeline by introducing a shading stage that utilizes pixel textures to apply lighting to the volume data.

### Inputs and Outputs
*   **Inputs:** Scalar volume data $V$, gradient information $\nabla V$ (derived from $V$), view direction, light direction, and transfer function parameters.
*   **Outputs:** A final composited image with shaded volume structures.

### Data Structures
1.  **Shading Pixel Texture:** A 2D texture used to store quantized normals.
    *   **Layout:** The texture stores 16-bit quantized normals.
    *   **Encoding:** The first 8 bits of the quantized normal are stored in the Red channel, and the second 8 bits are stored in the Green channel. The Blue and Alpha channels are unused or set to zero [S1, S2].
    *   **Interpolation Mode:** Nearest-neighbor interpolation is strictly required for this texture to prevent redundancy and truncation artifacts associated with hardware linear interpolation of quantized values [S1, S2].

### Steps
1.  **Gradient Estimation:** Compute the gradient $\nabla V$ at each voxel using central differences or Sobel operators on the scalar volume [S14, S30, unofficial][S54].
2.  **Normal Quantization:** Normalize the gradient vector to obtain the surface normal $\mathbf{n}$. Quantize $\mathbf{n}$ using a 16-bit scheme [S1, S2].
3.  **Texture Generation (Per-View):**
    *   Generate the shading pixel texture on a per-view basis in software [S1, S2].
    *   Alternatively, render the quantized normals as points with hardware lighting and copy the result from the frame buffer to the pixel texture, though this is hardware-dependent [S2].
    *   The performance cost of software generation is minimal [S1].
4.  **Volume Rendering with Shading:**
    *   Render the volume slice to a scratch/auxiliary buffer [S2].
    *   During rasterization, sample the shading pixel texture using nearest-neighbor interpolation to retrieve the quantized normal for the current fragment [S1, S2].
    *   Light the quantized normal using the 2D pixel texture (equivalent to a 16-bit 1D nearest-neighbor lookup) [S1].
    *   Modulate the volume slice with the shaded result [S2].
5.  **Compositing:**
    *   Copy the slice from the scratch buffer and blend it with previously rendered slices in the frame buffer using the standard front-to-back compositing equation [S12, S43, S50, unofficial].
    *   If using the SGI Octane2 platform, use `glCopyPixels()` to pixel texture the slice, as pixel texture operations do not occur directly on a per-fragment basis during rasterization on this hardware [S2].

### Formulas
The compositing equation remains the standard front-to-back over operator [S12, S43, S50, unofficial]:

$$
C'_{i} = C'_{i-1} + (1 - \alpha'_{i-1}) \alpha_i C_i
$$
$$
\alpha'_{i} = \alpha'_{i-1} + (1 - \alpha'_{i-1}) \alpha_i
$$

Where $C_i$ and $\alpha_i$ are the color and opacity of the current sample, derived from the transfer function and modulated by the shading result [S2].

### Parameters
*   **Quantization:** 16-bit encoding for normals [S2].
*   **Interpolation:** Nearest-neighbor for the shading pixel texture [S1, S2].

### Edge Cases and Pitfalls
*   **Hardware Flexibility:** Some hardware implementations (e.g., specific configurations of the SGI Octane2 or early GeForce cards) are not flexible enough to support rendering quantized normals as points with hardware lighting and copying them to a pixel texture [S2].
*   **Interpolation Artifacts:** Using linear interpolation on quantized normals causes redundancy and truncation errors; nearest-neighbor must be used [S1, S2].
*   **View Dependency:** The shading pixel texture must be regenerated when the view point changes, as normals are view-dependent in the context of the lighting model [S1, S2].

## Subtopics

### Quantized Normal Shading via Pixel Texture
A specific implementation variant that encodes surface normals into a 2D pixel texture to avoid hardware interpolation redundancy and truncation, using nearest-neighbor interpolation [S2]. It is chosen when high-fidelity shading is required in texture-memory based rendering without the overhead of complex normal interpolation hardware. It differs from standard shading by explicitly managing the 16-bit quantization in a 2D texture format (8 bits per channel) [S2].

### Line Bundles
A technique relying on graphics hardware to create texture by rendering and compositing many semitransparent line segments to produce an anisotropic volume rendering result [S3, unofficial]. It is used for flow visualization to clearly evidence directionality while viewing velocity magnitude, unlike standard volume rendering which may lack clear directionality [S3, unofficial]. It differs by using pre-computed sets of rendered line segments per data point with slightly perturbed colors, composited back-to-front [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** The shading texture generation is performed per-view in software, but the cost is described as minimal [S1]. The rendering cost increase is negligible compared to unshaded texture-memory based volume rendering [S1].
*   **Memory Complexity:** Requires an auxiliary scratch buffer for each slice and the shading pixel texture [S2].
*   **Strengths:** Dramatically increases rendering quality by adding shading with negligible cost; avoids hardware interpolation artifacts for normals [S1, S2].
*   **Limitations:** Requires per-view texture regeneration; dependent on specific hardware capabilities for point rendering and pixel texture operations (e.g., SGI Octane2 limitations) [S1, S2].
*   **When to use:** When using texture-memory based volume rendering and shading is desired to enhance shape perception, particularly on hardware where efficient normal interpolation is not available [S1].

## Background
The method was developed as part of interactive volume rendering systems using multi-dimensional transfer functions, specifically implemented on SGI Octane 2 and nVidia GeForce3 platforms [S1, S2]. It addresses the lack of shading in previous texture-memory based volume rendering work [S1]. The approach leverages the observation that when the transfer function is manipulated, the viewpoint is static, and vice versa, allowing the pixel texture operation to be limited to the changing portion of the volume [S2].
