# Hardware Shading via Pixel Texture

Also called: Quantized Normal Shading

## Overview
Hardware Shading via Pixel Texture is a method for adding surface shading to texture-memory based volume rendering by encoding quantized surface normals into a 2D pixel texture [S1]. It solves the problem of poor structural clarity in volume renderings caused by the lack of shading, which was common in previous hardware-accelerated approaches [S1]. It sets itself apart from siblings like [Hardware-Accelerated Volume Rendering via 3D Texturing](2799-hardware-accelerated-volume-rendering-via-3d-texturing.md) by explicitly decoupling the shading calculation from the volume compositing pipeline, using a separate pixel texture lookup to modulate the color, thereby increasing visual quality with negligible performance cost [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A volume dataset (scalar values), a view direction, and a lighting model.
*   **Output:** A shaded, composited image.

**Data Structures:**
*   **Shading Pixel Texture:** A 2D texture where each texel represents a quantized normal.
    *   **Layout:** 16-bit quantized normal encoded into two 8-bit channels.
    *   **Red Channel:** First 8 bits of the quantized normal.
    *   **Green Channel:** Second 8 bits of the quantized normal.
    *   **Interpolation:** Nearest-neighbor interpolation is used for lookups to avoid redundancy and truncation errors associated with hardware linear interpolation [S1, S2].

**Steps:**
1.  **Normal Quantization:** Compute surface normals for the volume data. Encode each normal using a 16-bit quantization scheme [S1, S2].
2.  **Texture Encoding:** Encode the first 8 bits of the quantized normal into the Red channel and the second 8 bits into the Green channel of a 2D pixel texture [S1, S2].
3.  **Texture Generation:** Generate the shading pixel texture on a per-view basis in software [S1, S2].
    *   *Alternative Hardware Method:* Render quantized normals as points with hardware lighting and copy the result from the frame buffer to the pixel texture [S2].
4.  **Slice Rendering:** Render the current volume slice to a scratch/auxiliary buffer [S2].
5.  **Shading Modulation:** If shading is enabled, render the matching slice from the shading volume (containing the encoded normals) and modulate (multiply) it with the current slice in the scratch buffer [S2].
    *   Note: The lighting of quantized normals is performed via a 2D pixel texture lookup, which is equivalent to a 16-bit 1D nearest-neighbor lookup [S1].
6.  **Compositing:** Copy the slice from the scratch buffer and blend it with previously rendered slices in the frame buffer [S2].

**Parameters:**
*   **Quantization Scheme:** 16-bit encoding for normals [S2].
*   **Interpolation Mode:** Nearest-neighbor for the shading texture [S1, S2].

**Edge Cases and Pitfalls:**
*   **Hardware Flexibility:** Some hardware implementations (e.g., SGI Octane2) do not support rendering quantized normals as points with hardware lighting and copying to a pixel texture directly during rasterization [S2]. In such cases, the software generation method or `glCopyPixels()` to an auxiliary buffer is required [S2].
*   **Redundancy/Truncation:** Using standard hardware interpolation (linear) on the encoded normals causes redundancy and truncation errors, degrading shading quality [S1, S2].

## Subtopics

### Quantized Normal Shading via Pixel Texture
A specific implementation variant that emphasizes the encoding of normals into a 2D pixel texture to avoid hardware interpolation redundancy [S2]. It differs from general shading by strictly using nearest-neighbor interpolation for the normal lookup [S2]. It is chosen when high-quality shading is needed on hardware that lacks flexible per-fragment lighting or when the cost of software texture generation is negligible compared to the visual gain [S1, S2].

### Line Bundles
A technique for anisotropic volume rendering that relies on graphics hardware to create texture by rendering and compositing many semitransparent line segments [S3, unofficial]. It differs from standard volume rendering by clearly evidencing directionality, which is often lost in isotropic rendering [S3, unofficial]. It is chosen for flow visualization where both velocity magnitude and direction are critical [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** The shading texture generation is performed in software on a per-view basis, but the cost is described as minimal [S1]. The rendering pipeline adds a modulation step (multiplication) per slice [S2].
*   **Memory Complexity:** Requires an auxiliary/scratch buffer for each slice rendering and a 2D pixel texture for shading [S2].
*   **Performance:** Adds negligible cost to the rendering pipeline while dramatically increasing quality [S1].
*   **Strengths:** Simple to implement, low performance overhead, improves structural clarity [S1].
*   **Limitations:** Dependent on hardware support for pixel textures (e.g., `glCopyPixels` limitations on SGI Octane2) [S2]. Requires software generation of the shading texture per view [S1].

## Background
The method was developed as part of the Interactive Volume Rendering system using multi-dimensional transfer functions, primarily implemented on SGI Octane 2 and nVidia GeForce3 hardware [S1, S2]. It addresses the gap in previous texture-memory based volume rendering work which often lacked shading [S1]. The Line Bundles variant was developed by Crawfis, Shen, and Max for flow visualization [S3, unofficial].
