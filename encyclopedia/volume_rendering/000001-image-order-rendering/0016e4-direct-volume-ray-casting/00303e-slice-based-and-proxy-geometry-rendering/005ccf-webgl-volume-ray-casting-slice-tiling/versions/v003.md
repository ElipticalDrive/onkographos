# WebGL Volume Ray Casting (Slice Tiling)

Also called: 2D slice tiling volume rendering, Mosaic Volume Rendering, Volume Ray Casting in WebGL, Volume Ray Casting with Mosaic Texture and Post-Classification

## Overview
WebGL Volume Ray Casting (Slice Tiling) is a direct volume rendering method adapted for web browsers that replaces native 3D volume textures with a 2D tiling map of volume slices to simulate 3D data while preserving tri-linear interpolation [S1, book]. It solves the problem of rendering volumetric data in environments lacking hardware support for 3D textures by running entirely on the client side, leveraging the GPU's accelerated graphics pipeline while avoiding server-side rendering overhead [S1, book].

## How it works
The method builds on [Direct volume ray casting](19-direct-volume-ray-casting.md) but modifies the data structure and sampling mechanism to accommodate WebGL's texture limitations [S1, book].

**Inputs and Outputs**
*   **Input**: A 3D scalar volume dataset $V$ of dimensions $W \times H \times D$, a 2D tiling map texture $T_{tile}$ constructed from the slices of $V$, camera parameters (origin $\mathbf{o}$, direction $\mathbf{d}$), transfer function $T(V) \rightarrow (\mathbf{c}, \alpha)$, mosaic dimensions (total slices $S$, images per row $M_x$, rows $M_y$), and step count $S$ [S1, book].
*   **Output**: A 2D image buffer containing the composited color $\mathbf{C}_{out}$ and opacity $\alpha_{out}$ for each pixel [S1, book].

**Data Structures**
1.  **2D Tiling Map ($T_{tile}$)**: A 2D texture where the volume slices are arranged in a matrix configuration [S1, book]. Not given in the sources. Typical sizes are $4096 \times 4096$ for PC and $1024 \times 1024$ for handheld devices [S1, book].
2.  **Ray Parameters**: For each pixel, the entry $t_{near}$ and exit $t_{far}$ parameters of the ray intersecting the volume bounding box, extracted from a two-pass color cube render [S1, book].

**Numbered Steps**
1.  **Data Preprocessing**: Tile all slices of the 3D volume dataset beside each other in a matrix configuration to form a single 2D texture object [S1, book]. Medical datasets are typically reduced to 8 bits per pixel to match WebGL format limitations [S1, book].
2.  **Ray Coordinate Identification (Geometry Pass)**: Render a unit cube with coordinates $(0,0,0)$ to $(1,1,1)$ representing the volume boundary in two passes with modified depth functions [S1, book]. The first pass captures the closest region to the camera (ray start), and the second captures the far region (ray end) [S1, book]. Coordinates are stored in the $r, g, b$ color components of each pixel as 24-bit RGB values [S1, book].
3.  **Ray Generation**: Extract the start and end positions of the ray for each pixel from the previous render passes [S1, book]. Divide the ray interval into $S$ equi-parametric steps [S1, book].
4.  **Volume Value Interpolation**: For each sample point, calculate the slice indices and fractional parts to map the 3D coordinate to the 2D tiling map texture coordinates [S1, book]. Sample the two adjacent slices and perform linear interpolation between them [S1, book].
5.  **Transfer Function Application (Post-Classification)**: Apply the transfer function to the interpolated raw scalar value to obtain color $\mathbf{V}_{rgb}$ and opacity $S_a$ [S1, book]. Post-classification interpolates raw data first, then applies the transfer function, which is considered correct for continuous scalar fields despite higher computational cost [S1, book].
6.  **Compositing and Early Termination**: Accumulate the color and opacity using the front-to-back composition function [S1, book]. The ray is interrupted when the composition reaches the end of the cube or the accumulated alpha $A_a$ reaches its maximum value of 1 [S1, book].

**Formulas**
The algorithm complexity is:
$$
O(M \times S)
$$
where $M$ is the number of pixels to be drawn (resolution width $\times$ height) and $S$ is the number of steps of the ray that traverses the volume [S1, book].

Slice index and coordinate mapping:
$$
s_1 = \lfloor z \cdot S \rfloor, \quad s_2 = s_1 + 1
$$
$$
dx_1 = \text{fract}(s_1/M_x), \quad dy_1 = \text{fract}(s_1/M_y)
$$
$$
dx_2 = \text{fract}(s_2/M_x), \quad dy_2 = \text{fract}(s_2/M_y)
$$
$$
tx_1 = dx_1 + x/M_x, \quad ty_1 = dy_1 + y/M_y
$$
$$
tx_2 = dx_2 + x/M_x, \quad ty_2 = dy_2 + y/M_y
$$
where $x, y$ are the normalized coordinates within the slice ($0 \le x, y \le 1$), and $\text{fract}(\cdot)$ returns the fractional part [S1, book].

Texture sampling and scalar interpolation:
$$
v_1 = \text{tex2D}(tx_1, ty_1), \quad v_2 = \text{tex2D}(tx_2, ty_2)
$$
$$
V_a(x,y,z) = \text{mix}(v_1, v_2, (z \cdot S) - s_1)
$$
where the source uses $(x \cdot S) - s_1$ but $x$ is a typo for the slice coordinate $z$ [S1, book].

Accumulation and transfer function:
$$
S_a = V_a \cdot O_f, \quad S_{rgb} = V_{rgb} \cdot S_a \cdot L_f
$$
$$
A_{rgb}^k = A_{rgb}^{k-1} + (1 - A_a^{k-1}) \cdot S_{rgb}
$$
$$
A_a^k = A_a^{k-1} + S_a
$$
where $O_f$ and $L_f$ are general opacity and light factors, and the final pixel alpha $A_a$ is set to 1 at the end of the render process [S1, book]. (Note: The source includes a factor $(1/s)$ in $S_a$, which is treated as a typo for $1$ or omitted for standard compositing [S1, book].)

**Parameters**
*   $M$: Number of pixels to be drawn. Typical resolutions tested: 512px, 1024px, 2048px, 4096px [S1, book].
*   $S$: Number of ray steps. Typical values tested: 30, 80, 140, 200 [S1, book].
*   Texture Size: $4096 \times 4096$ for PC, $1024 \times 1024$ for handheld devices [S1, book].
*   Bit Depth: 8 bits per pixel [S1, book].
*   Mosaic Dimensions: Total slices $S$, images per row $M_x$, rows $M_y$ [S1, book].

**Pitfalls and Edge Cases**
*   **Precision**: Storing ray coordinates in 24-bit RGB color components provides sufficient precision for ray coordinates despite the seemingly small range, due to color interpolation [S1, book].
*   **Shader Compilation Limits**: Browser shader compilers may fail to compile larger shader programs due to inadequate or restricted shader language implementations [S1, book].
*   **Interpolation Overhead**: The use of 2D slice tiling introduces a slight interpolation overhead compared to native 3D textures, though it is minimal and imperceptible in browser environments [S1, book].

**Pseudocode**
```python
def intersect_ray_box(o, d, box_min, box_max):
    # Standard slab method; handles grazing cases and zero direction components correctly
    t_min = (box_min - o) / d
    t_max = (box_max - o) / d
    t1 = min(t_min, t_max)
    t2 = max(t_min, t_max)
    t_near = max(t1)
    t_far = min(t2)
    if t_near > t_far:
        return None
    return t_near, t_far

def get_slice_coords(x_norm, y_norm, z, S, Mx, My):
    s1 = int(z * S)
    s2 = s1 + 1
    dx1 = (s1 / Mx) % 1.0
    dy1 = (s1 / My) % 1.0
    dx2 = (s2 / Mx) % 1.0
    dy2 = (s2 / My) % 1.0
    tx1 = dx1 + x_norm / Mx
    ty1 = dy1 + y_norm / My
    tx2 = dx2 + x_norm / Mx
    ty2 = dy2 + y_norm / My
    return (tx1, ty1), (tx2, ty2)

def sample_2D(texture, u, v):
    # Standard 2D texture lookup with tri-linear interpolation
    return texture.lookup(u, v)

def render_webgl_volume(ray_origin, ray_direction, volume_bounds, t_tile, transfer_function, num_steps, S, Mx, My):
    t_near, t_far = intersect_ray_box(ray_origin, ray_direction, volume_bounds.min, volume_bounds.max)
    if t_near is None:
        return (0.0, 0.0, 0.0), 0.0

    step_size = (t_far - t_near) / num_steps
    acc_color = (0.0, 0.0, 0.0)
    acc_alpha = 0.0

    for i in range(num_steps):
        t = t_near + i * step_size
        p = ray_origin + ray_direction * t
        x_norm, y_norm, z = p

        coords1, coords2 = get_slice_coords(x_norm, y_norm, z, S, Mx, My)
        u1, v1 = coords1
        u2, v2 = coords2

        v1_val = sample_2D(t_tile, u1, v1)
        v2_val = sample_2D(t_tile, u2, v2)
        frac_z = (z * S) - int(z * S)
        Va = mix(v1_val, v2_val, frac_z)

        color, alpha = transfer_function(Va)

        weight = alpha * (1.0 - acc_alpha)
        acc_color = tuple(acc_color[k] + weight * color[k] for k in range(3))
        acc_alpha = acc_alpha + alpha

        if acc_alpha >= 1.0:
            break

    return acc_color, 1.0
```

## Subtopics

### 2D Visualization from 3D Grid (Slow)
A software-based approach that iterates through slices in CPU memory. Choose this method when GPU acceleration is unavailable or for debugging [G]. [1507-2d-visualization-from-3d-grid-slow.md]

### Surface Rendering Pipeline
Extracts isosurfaces using marching cubes or similar algorithms instead of compositing volumetric data. Choose this method when opaque boundary visualization is prioritized over internal structure transparency [G]. [2614-surface-rendering-pipeline.md]

### Two-Pass Volume Rendering with Shadows
Adds shadow casting to volume rendering by separating light transport from view-dependent compositing. Choose this method when accurate lighting and shadows are prioritized over interactive frame rates [G]. [6520-two-pass-volume-rendering-with-shadows.md]

### Image-based rendering integration
Combines ray casting with image-space techniques like splatting or screen-space ray marching. Choose this method for hybrid performance and quality needs in complex scenes [G]. [6969-image-based-rendering-integration.md]

### Vector Icon Volume Rendering
Renders vector fields within volumes using icon-based glyphs or streamline integration. Choose this method for flow and directional data visualization [G]. [7693-vector-icon-volume-rendering.md]

### Image-Based Volume Rendering
Uses screen-space techniques like splatting or ray marching to render volumes. Choose this method for interactive frame rates on complex scenes where geometric accuracy is secondary [G]. [11273-image-based-volume-rendering.md]

### Key View Generation
Precomputes and caches specific viewpoints for rapid navigation and fly-throughs. Choose this method when rapid view changes are required without real-time recomputation [G]. [11291-key-view-generation.md]

### Hybrid and Mixed Geometry
Combines volume primitives with surface meshes and other geometric representations. Choose this method when rendering mixed data types that require both volumetric and boundary visualization [G]. [15423-hybrid-and-mixed-geometry.md]

### Proxy Geometry and Slicing

### Slicing Plane Volume Rendering

## Operating characteristics
*   **Time Complexity**: $O(M \times S)$, where $M$ is the number of pixels and $S$ is the number of ray steps [S1, book].
*   **Memory Complexity**: Proportional to the size of the 2D tiling map, which is $O(W \times H \times D)$ pixels, stored in 2D texture memory [S1, book].
*   **Measured Performance**: Achieved approximately 2 to 3 frames per second on Samsung Galaxy Tab and Galaxy S smartphones using the Fennec mobile browser with a half-resolution Aorta dataset [S1, book].
*   **Strengths**: Runs entirely in the client browser, avoiding server-side rendering overhead and allowing more simultaneous clients. Uses the same accelerated graphic pipeline as native applications [S1, book].
*   **Limitations**: Requires more powerful client hardware. Browser shader compilers may fail to compile larger shader programs. Performance is sensitive to browser implementation details [S1, book].
*   **When to Use**: Web-based volume rendering systems for medical (e.g., Aorta) and radar datasets where server-side rendering is not feasible or desirable [S1, book].
*   **When Not to Use**: When high frame rates are required on low-end devices, or when native 3D texture support is available (use standard GPU ray casting instead) [S1, book].

## Background
The method was introduced in a book chapter titled "Volume Ray Casting in WebGL" by John Edgar Congote et al., published in 2012 [S1, book]. It was implemented in a web-based volume rendering system for medical (Aorta) and radar datasets, tested on the Mozilla Firefox/Fennec mobile browser [S1, book]. The work demonstrated the possibility of rendering volume datasets on handheld devices using web standard technology, re-igniting interest in visualization functions previously reserved for high-end desktop applications [S1, book].
