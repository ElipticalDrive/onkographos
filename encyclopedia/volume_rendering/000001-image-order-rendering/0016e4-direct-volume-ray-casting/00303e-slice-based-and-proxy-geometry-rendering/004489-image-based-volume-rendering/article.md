# Image-Based Volume Rendering

Also called: Image-Based Volume Rendering (IBVR) with Opacity Light Fields, Opacity Light Field Rendering

## Overview
Image-Based Volume Rendering (IBVR) is a technique for interactively exploring arbitrarily large volumetric datasets on standard graphics hardware by decoupling the expensive volume integration from the interactive viewing phase [S1, unofficial]. It solves the performance bottleneck of direct ray casting on large datasets by precomputing "ray slices" from multiple viewpoints and compositing them as opacity light fields during interaction [S1, unofficial]. Unlike previous image-based methods that restricted viewpoints to a limited cone or lacked opacity for internal structure, IBVR allows unrestricted external viewpoints and arbitrary clipping surfaces to reveal interior details without re-rendering the volume [S1, unofficial].

## How it works
The method operates in three distinct phases: Volume Rendering (preprocessing), Key View Generation, and Interactive Viewing [S1, unofficial]. It is independent of the underlying volume rendering system and dataset representation (e.g., rectilinear or irregular grids) [S1, unofficial].

### Inputs and Outputs
*   **Inputs:**
    *   Volumetric dataset (scalar field) [S1, unofficial].
    *   Geometric proxy surface bounding the volume (initially a bounding sphere or isosurface) [S1, unofficial].
    *   Set of original viewpoints for preprocessing [S1, unofficial].
    *   User-defined parameters: number of ray slices per viewpoint, slice spacing [S1, unofficial].
*   **Outputs:**
    *   Interactive 3D visualization allowing camera movement and dynamic clipping surface modification [G].

### Data Structures

**1. Ray Slice**
A Ray Slice is a 2D image where each pixel represents a partial ray projected from a specific slice location through the volume [S1, unofficial].
*   **Layout:** A 2D array of RGBA values [S1, unofficial].
*   **Content:** The color and opacity at each pixel correspond to the accumulated values generated by the volume integral along a viewing ray starting at the slice plane and extending through the remainder of the volumetric data towards the original viewpoint [S1, unofficial].
*   **Storage:** Stored as compressed images (e.g., PNG for lossless, JPEG 2000 for lossy) [S1, unofficial].

**2. Geometric Proxy Surface**
A surface bounding the volume used to define clipping planes during interactive viewing [S1, unofficial].
*   **Layout:** Standard triangle mesh or implicit surface representation [G].
*   **Function:** Defines the boundary between the pre-rendered interior (behind the proxy relative to the camera) and the interactive exterior [G]. The user can modify this surface (e.g., add clipping planes) to reveal internal structure [S1, unofficial].

**3. Key View**
A composite image generated from a set of ray slices and the proxy surface for a specific viewing location [S1, unofficial].

### Numbered Steps

**Step 1: Volume Rendering (Preprocessing)**
1.  Select a set of original viewpoints from which to pre-render the volume [S1, unofficial].
2.  For each viewpoint, define a series of image-aligned clipping planes moving back-to-front through the volume [S1, unofficial].
3.  For each clipping plane position (slice):
    a. Clip the volume between the clipping plane and the viewpoint [S1, unofficial].
    b. Render the remaining volume (from the clipping plane to the far end of the data) using a standard volume rendering algorithm with back-to-front compositing [S1, unofficial].
    c. Store the resulting RGBA image as a Ray Slice [S1, unofficial].
    *   *Note:* The number of slices per viewpoint is adjustable and dataset-dependent [S1, unofficial]. Anisotropic data may require more slices along one axis [S1, unofficial]. Spacing can be adapted to skip empty space or capture detail [S1, unofficial].
4.  Define a Geometric Proxy Surface bounding the volume [S1, unofficial].

**Step 2: Key View Generation**
1.  Input: The set of Ray Slices, their associated viewpoint parameters, and the Geometric Proxy Surface [S1, unofficial].
2.  For each desired interactive viewing location (Key View):
    a. Determine the intersection of the viewing rays with the Geometric Proxy Surface [G].
    b. Identify which Ray Slices are "behind" the proxy surface relative to the new viewpoint [G].
    c. Composite the relevant Ray Slices and the proxy surface to generate a Key View image [S1, unofficial]. This image represents the volume intersected by the proxy surface from that specific location [S1, unofficial].

**Step 3: Interactive Viewing**
1.  Load the Key Views and the Geometric Proxy Surface into the graphics hardware [S1, unofficial].
2.  Render the scene interactively:
    a. Render the Geometric Proxy Surface [G].
    b. Render the Key Views as Opacity Light Fields behind the proxy surface [S1, unofficial].
    c. Allow the user to modify the Geometric Proxy Surface (e.g., via clipping planes) to reveal interior structure [S1, unofficial].
    d. Because the interior structure is pre-computed in the Ray Slices/Key Views, changes to the proxy do not require volumetric re-rendering [S1, unofficial].

### Pseudocode

```python
def ibvr_pipeline(volume_data, transfer_function, proxy_surface, viewpoints, slice_params):
    ray_slices = {}
    for viewpoint in viewpoints:
        ray_slices[viewpoint] = []
        # Determine slice positions along the view direction [G]
        view_dir = normalize(viewpoint.position - volume_data.center)
        num_slices = slice_params.get('num_slices', 10)
        spacing = slice_params.get('spacing', 1.0)
        slice_positions = [viewpoint.position + view_dir * (i * spacing) for i in range(num_slices)]
        for pos in slice_positions:
            # [S1, unofficial] Delegate to any arbitrary volume rendering system that computes RGBA images with back-to-front compositing for arbitrary image-aligned clipping planes.
            rgba_image = render_volume_back_to_front(volume_data, transfer_function, pos, viewpoint)
            # [G] Standard lossless image compression (e.g., PNG).
            compressed_slice = compress_to_png(rgba_image)
            ray_slices[viewpoint].append({'position': pos, 'image': compressed_slice})
    return ray_slices

def generate_key_views(ray_slices, proxy_surface, key_viewpoints):
    key_views = {}
    for kv in key_viewpoints:
        relevant_slices = []
        for vp, slices in ray_slices.items():
            for s in slices:
                # [G] Determine if slice position is occluded by proxy surface from key viewpoint.
                if is_behind_proxy(s['position'], kv.position, proxy_surface):
                    relevant_slices.append(s)
        # [G] Back-to-front alpha compositing of selected ray slices.
        key_views[kv] = composite_slices(relevant_slices, kv)
    return key_views

def render_interactive(key_views, proxy_surface, current_camera):
    # [G] Rasterize proxy surface geometry.
    rasterize(proxy_surface, current_camera)
    # [G] Render key view images as textured quads behind the proxy surface.
    for kv, image in key_views.items():
        if is_in_frustum(kv.position, current_camera):
            render_quad(image, kv.position, kv.orientation, current_camera)
```

### Parameters and Edge Cases
*   **Number of Ray Slices:** User-adjustable. Dataset-dependent. Anisotropic data may need more slices along one axis. Can range from 1 to memory limits [S1, unofficial].
*   **Compression:** PNG (lossless) or JPEG 2000 (lossy) [S1, unofficial].
*   **Proxy Surface:** Initial proxy can be a bounding sphere or isosurface [S1, unofficial].
*   **Edge Case:** Sparse pre-computed ray slices may cause interpolation artifacts when the camera moves significantly between key viewpoints [G].
*   **Pitfall:** The quality of the interactive view depends on the density of the pre-computed ray slices.

## Operating characteristics
*   **Time Complexity:** Not given in the sources. Preprocessing scales with volume size, number of viewpoints, and slices [G]. Interactive viewing is constant relative to volume size, dependent only on key views and proxy geometry [G].
*   **Memory Complexity:** Not given in the sources. Scales with the number of pre-computed views and slices [G].
*   **Measured Performance:** Tested on arbitrarily large datasets (e.g., terabyte-scale seismic data) on low-cost PC graphics hardware, achieving interactivity where direct ray casting fails [S1, unofficial].
*   **Strengths:**
    *   Handles arbitrarily large datasets [S1, unofficial].
    *   Unrestricted viewpoints (unlike prior methods [22]) [S1, unofficial].
    *   Allows arbitrary clipping surfaces to reveal interior structure without re-rendering [S1, unofficial].
    *   Independent of volume rendering system and dataset representation (works with irregular grids) [S1, unofficial].
*   **Limitations:**
    *   Requires significant preprocessing time and memory [G].
    *   Interactivity is limited to the pre-computed key views; significant camera movement may require interpolation or new key views [G].
    *   Not suitable for dynamic volumes (data changes over time) due to static preprocessing [G].

## Background
Image-Based Volume Rendering with Opacity Light Fields was introduced by Miriah Meyer, Hanspeter Pfister, Charles Hansen, and Chris Johnson from the Scientific Computing and Imaging Institute at the University of Utah and Mitsubishi Electric Research Labs [S1, unofficial]. The method was presented in a technical report (UUSCI-2005-002) in 2005 [S1, unofficial]. It addresses the limitations of earlier IBVR methods [4, 22] which either lacked opacity for internal views or restricted viewpoints to a limited cone [S1, unofficial].
