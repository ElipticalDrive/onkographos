# Texture-Based Volume Rendering

Also called: Geometry-based volume visualization, Proxy Geometry Rendering, Slice-based rendering, TBVR, Texture Based Ray Casting

## Overview
Texture-Based Volume Rendering (TBVR) is a direct volume rendering technique that accelerates image-order ray casting by decomposing the 3D volume into a set of 2D planar slices [S1, S2, S7, unofficial]. These slices are treated as geometric primitives (proxy geometry) that are rasterized by the GPU, with the volumetric data stored in 3D or 2D texture memory [S2, S7, unofficial]. Unlike [View-Aligned Slicing](6530-view-aligned-slicing.md), which dynamically computes slice geometry to maintain constant sampling distance, TBVR typically relies on fixed object-aligned slices or view-aligned slices that may vary in sampling density, trading memory efficiency and artifact susceptibility for rendering speed [S2, unofficial][S3, book].

## How it works
The method operates in three stages: Initialize, Update, and Draw [S3, book].

### Inputs and Outputs
*   **Input:** Volumetric scalar field data (regular grid), transfer function (TF), camera parameters (view/projection matrices), and rendering mode (transparent/solid).
*   **Output:** 2D color buffer with composited volume image.

### Data Structures
1.  **Volume Texture:**
    *   **3D Texture:** Stores the entire volume in GPU memory. Format: `GL_RGBA` or `GL_RED` (for scalar data). Type: `GL_UNSIGNED_BYTE` or `GL_FLOAT`. Filters: `GL_LINEAR` (trilinear interpolation) [S3, book][S5, unofficial].
    *   **2D Texture Stack:** Stores slices as a stack of 2D textures. Requires replication along X, Y, and Z axes for object-aligned rendering, consuming 3x memory [S2, unofficial][S3, book].
2.  **Transfer Function Texture:**
    *   1D texture mapping scalar values to RGBA color/opacity [S3, book].
3.  **Proxy Geometry:**
    *   Array of vertices defining planar polygons (quads or triangle fans) intersecting the volume bounding box.
    *   **Object-Aligned:** Rectangles aligned with principal axes (X, Y, Z) [S2, unofficial][S3, book].
    *   **View-Aligned:** Polygons orthogonal to the viewing direction, constructed by intersecting slicing planes with the volume bounding box [S2, S6, unofficial].
4.  **Uniforms/Constants:**
    *   `u_slices`: `vec3` containing texture dimensions $(D_x, D_y, D_z)$ for coordinate normalization [S5, unofficial].
    *   `u_thresh`: `float` threshold for fragment discard [S5, unofficial].
    *   `u_alphaScale`: `float` multiplier for opacity [S5, unofficial].
    *   `u_clipPlaneX/Y/Z`, `u_clipCubeMax/Min`: Clipping parameters [S5, unofficial].

### Numbered Steps

1.  **Initialize:**
    *   Load volume data into CPU memory.
    *   Process data (e.g., compute gradients, downsample) if required [S3, book].
    *   Create transfer function lookup tables (1D textures) [S3, book].
    *   Download volume data to GPU as 3D texture or 2D texture stack [S2, unofficial][S3, book].
    *   Compile fragment shaders [S3, book].

2.  **Update (Per Frame):**
    *   Compute proxy geometry:
        *   For **View-Aligned**: Intersect slicing planes with the volume bounding box. Sort resulting vertices in counter-clockwise order. Construct polygon primitives (e.g., triangle fan from centroid) [S2, S6, unofficial].
        *   For **Object-Aligned**: Select the texture stack (X, Y, or Z) closest to the camera viewpoint [S2, unofficial].
    *   Update vertex arrays with proxy geometry vertices and their corresponding 3D texture coordinates [S3, book]. Texture coordinates are assigned to vertices, either on CPU or via vertex shader [S2, unofficial][S3, book].
    *   Refresh textures if rendering mode or transfer function parameters change [S3, book].
    *   Perform opacity correction of transfer function textures if sampling rate changed [S3, book].

3.  **Draw:**
    *   Set up rendering state:
        *   Disable lighting and culling [S3, book][S9].
        *   Enable alpha blending. For Over operator (back-to-front): Source = 1, Destination = 1 - Source Alpha [S2, unofficial]. For Under operator (front-to-back): Source = 1 - Destination Alpha, Destination = 1 [S2, unofficial].
        *   Disable depth testing or disable depth buffer writing if blending with opaque geometry [S9].
    *   Bind volume texture and transfer function texture [S3, book][S9].
    *   Specify shader input parameters (matrices, uniforms) [S9].
    *   Draw slice polygons in sorted order (back-to-front for Over operator) [S2, unofficial][S3, book].
    *   Restore rendering state [S3, book].

### Fragment Shader Execution
For each fragment of a proxy polygon:
1.  **Interpolate Texture Coordinates:** Receive interpolated 3D texture coordinates from vertex attributes [S3, book].
2.  **Data Lookup:** Sample the volume texture at the interpolated coordinates to retrieve the scalar value $v$ [S3, book].
    *   *Note:* If using 2D textures, bilinear interpolation is used within slices, causing artifacts at slice boundaries [S8, unofficial]. 3D textures use trilinear interpolation [S1, unofficial].
3.  **Transfer Function Lookup:** Use the scalar value $v$ as a texture coordinate for a dependent lookup into the 1D transfer function texture to retrieve color $C$ and opacity $\alpha$ [S3, book].
4.  **Illumination (Optional):**
    *   Compute surface normal using central differences (finite differences) between neighboring voxels [S2, S6, unofficial].
    *   Apply lighting model (e.g., Blinn-Phong) to modify color [S2, S5, unofficial].
5.  **Compositing:** The resulting color and alpha are sent to the hardware compositing stage (alpha blending) [S2, unofficial][S3, book].

### Pseudocode

```python
# Vertex Shader
# Inputs: position (vec3), modelMatrix (mat4), viewMatrix (mat4), projectionMatrix (mat4)
# Outputs: gl_Position (vec4), texPosition (vec4), vCam (vec3)

varying vec4 texPosition;
varying vec3 vCam;

void main() {
    // Transform vertex to world space for texture coordinate calculation
    texPosition = modelMatrix * vec4(position, 1.0);
    
    // Camera position in world space
    vCam = vec3(viewMatrix * vec4(0.0, 0.0, 0.0, 1.0)); // Assuming view matrix transforms world to camera, inverse gives camera pos in world? 
    # Note: Standard OpenGL view matrix transforms world to camera. 
    # To get camera position in world, we need inverse of view matrix. 
    # However, source [S5, unofficial] uses cameraPosition directly. 
    # We assume vCam is passed as uniform or computed correctly.
    # For self-contained pseudocode, we assume vCam is available.
    
    gl_Position = projectionMatrix * viewMatrix * modelMatrix * vec4(position, 1.0);
}

# Fragment Shader (Transparent Mode)
# Inputs: texPosition (vec4), vCam (vec3)
# Uniforms: u_data (sampler3D), u_slices (vec3), u_thresh (float), u_alphaScale (float)
#           u_clipCubeEnabled (bool), u_clipCubeMax (vec3), u_clipCubeMin (vec3)
#           u_clipPlaneXEnabled (bool), u_clipPlaneX (float), etc.

void main() {
    // Normalize texture coordinates based on volume dimensions
    # Source [S5, unofficial] uses (texPosition / u_slices) + 0.5. 
    # This assumes texPosition is in voxel space or similar.
    vec3 texCoords = vec3(
        (texPosition.x / u_slices.x) + 0.5,
        (texPosition.y / u_slices.y) + 0.5,
        (texPosition.z / u_slices.z) + 0.5
    );
    
    // Sample volume data
    vec4 color = texture(u_data, texCoords);
    
    // Discard if below threshold
    if (color.r < u_thresh) {
        discard;
    }
    
    // Clipping logic
    if (u_clipCubeEnabled) {
        if (texPosition.x > u_clipCubeMax.x || texPosition.x < u_clipCubeMin.x) discard;
        if (texPosition.y > u_clipCubeMax.y || texPosition.y < u_clipCubeMin.y) discard;
        if (texPosition.z > u_clipCubeMax.z || texPosition.z < u_clipCubeMin.z) discard;
    }
    if (u_clipPlaneXEnabled) {
        if (texPosition.x > u_clipPlaneX) discard;
    }
    # Note: Source [S5, unofficial] has specific axis mappings for clip planes which may depend on rotation.
    # We implement generic checks.
    
    # Apply alpha scale
    color.a *= u_alphaScale;
    
    # For solid rendering, normal calculation and lighting would be added here.
    # For transparent, we output the sampled color/alpha.
    gl_FragColor = color;
}

# Fragment Shader (Solid Mode with Lighting)
# Additional Uniforms: lightPos (vec3), lightPos2 (vec3), Ka, Kd, Ks, shininess, ambientLight, lightColour

vec3 shading(vec3 N, vec3 V, vec3 L) {
    vec3 Ka = vec3(0.1, 0.1, 0.1);
    vec3 Kd = vec3(0.6, 0.6, 0.6);
    vec3 Ks = vec3(0.2, 0.2, 0.2);
    float shininess = 100.0;
    vec3 lightColour = vec3(1.0, 1.0, 1.0);
    vec3 ambientLight = vec3(0.3, 0.3, 0.3);
    
    vec3 H = normalize(L + V);
    vec3 ambient = Ka * ambientLight;
    
    float diffuseLight = max(dot(L, N), 0.0);
    vec3 diffuse = Kd * lightColour * diffuseLight;
    
    float specularLight = pow(max(dot(H, N), 0.0), shininess);
    if (diffuseLight <= 0.0) {
        specularLight = 0.0;
    }
    vec3 specular = Ks * lightColour * specularLight;
    
    return ambient + diffuse + specular;
}

void main() {
    vec3 texCoords = vec3(
        (texPosition.x / u_slices.x) + 0.5,
        (texPosition.y / u_slices.y) + 0.5,
        (texPosition.z / u_slices.z) + 0.5
    );
    
    vec4 color = texture(u_data, texCoords);
    if (color.r < u_thresh) discard;
    
    # Compute Normal via Central Differences
    float delta = 1.0 / 256.0; # Assuming 256 dimension or normalized space
    # Note: Delta should be based on actual voxel spacing or texture resolution
    vec3 sample1, sample2;
    
    sample1 = texture(u_data, texCoords - vec3(delta, 0.0, 0.0));
    sample2 = texture(u_data, texCoords + vec3(delta, 0.0, 0.0));
    vec3 N_x = sample2.x - sample1.x;
    
    sample1 = texture(u_data, texCoords - vec3(0.0, delta, 0.0));
    sample2 = texture(u_data, texCoords + vec3(0.0, delta, 0.0));
    vec3 N_y = sample2.x - sample1.x;
    
    sample1 = texture(u_data, texCoords - vec3(0.0, 0.0, delta));
    sample2 = texture(u_data, texCoords + vec3(0.0, 0.0, delta));
    vec3 N_z = sample2.x - sample1.x;
    
    vec3 N = normalize(vec3(N_x, N_y, N_z));
    
    vec3 L1 = normalize(lightPos - vec3(texPosition));
    vec3 L2 = normalize(lightPos2 - vec3(texPosition));
    vec3 V = normalize(vCam - vec3(texPosition));
    
    vec3 shade1 = shading(N, V, L1);
    vec3 shade2 = shading(N, V, L2);
    
    color.rgb = shade1 + shade2;
    gl_FragColor = color;
}
```

### Parameters
*   **PLANE_INC:** Increment value for plane slicing, typically initialized as 1.0 (voxel spacing) [S5, unofficial].
*   **u_slices:** Uniform `vec3` containing texture dimensions $(TEXTURE\_SIZE\_X, TEXTURE\_SIZE\_Y, TEXTURE\_SIZE\_Z)$ [S5, unofficial].
*   **u_thresh:** Uniform `float` threshold for discarding fragments [S5, unofficial].
*   **u_alphaScale:** Uniform `float` multiplier for fragment alpha [S5, unofficial].
*   **Lighting Constants (Phong):** $K_a=(0.1,0.1,0.1)$, $K_d=(0.6,0.6,0.6)$, $K_s=(0.2,0.2,0.2)$, shininess=100.0, ambientLight=(0.3,0.3,0.3), lightColour=(1.0,1.0,1.0) [S5, unofficial].

### Edge Cases and Pitfalls
*   **Precision:** Trilinear interpolation in 3D textures is slightly slower than bilinear in 2D but provides better quality [S1, S8, unofficial].
*   **Boundaries:** Object-aligned slices suffer from "pop-up" artifacts when switching between texture stacks (X, Y, Z) due to changes in sampling points [S2, S8, unofficial].
*   **Intensity Variations:** As the camera moves, the sampling distance changes in object-aligned rendering, causing intensity variations [S2, unofficial][S3, book].
*   **Viewing Angle:** 2D texture stacks suffer from sampling artifacts when the viewing angle approaches 45 degrees relative to the slices, as the viewer sees between slice gaps [S1, unofficial].
*   **Memory:** Object-aligned slices require 3x memory consumption due to data replication along principal directions [S2, unofficial][S3, book].

## Subtopics

### Object-Aligned Slices
Uses fixed proxy geometry aligned with the principal axes (X, Y, Z) of the volume. Requires storing the volume as three stacks of 2D textures (replicated data), consuming 3x memory. Fast and simple to implement but suffers from memory overhead, image popping artifacts during stack swaps, and intensity variations as the camera moves [S2, unofficial][S3, book][S6, unofficial].

### View-Aligned Slices
Uses proxy geometry that is orthogonal to the viewing direction. Requires 3D textures (or on-the-fly reconstruction from 2D stacks). Slower to compute geometry but more memory efficient (no replication) and provides consistent sampling distance, eliminating 45-degree viewing artifacts [S2, unofficial][S3, book][S7, unofficial].

### 2D Slice Replication Approach
A variant of object-aligned rendering where data is stored as a set of 2D texture slices. Proxy polygons are simple rectangles aligned with slices. To avoid data replication, slices can be reconstructed on the fly, incurring performance overhead. Sampling rate depends on volume resolution, which can be mitigated by adding intermediate slices and using trilinear interpolation [S9].

## Operating characteristics
*   **Time Complexity:** Rendering time is proportional to the number of slices and the resolution of the image. Fragment shader execution is parallelized on the GPU [S4, unofficial].
*   **Memory Complexity:**
    *   **3D Textures:** $O(N)$ where $N$ is the number of voxels. No replication [S3, book].
    *   **2D Textures (Object-Aligned):** $O(3N)$ due to replication along X, Y, Z axes [S2, unofficial][S3, book].
*   **Measured Performance:** Achieves interactive frame rates on modern GPUs by leveraging hardware texture sampling and alpha blending [S1, S4, unofficial]. 2D textures are faster than 3D textures due to simpler bilinear interpolation, but 3D textures provide better image quality [S1, S8, unofficial].
*   **Strengths:** High performance on GPUs; simple implementation; leverages standard graphics pipeline [S1, S2, unofficial].
*   **Limitations:** Artifacts at slice boundaries (2D); memory usage (2D replication); sampling artifacts at oblique angles (2D); dependency on sampling rate [S1, S2, unofficial][S3, book][S7, unofficial].
*   **When to Use:** Interactive visualization where performance is critical and artifacts are acceptable or mitigated (e.g., view-aligned slices).
*   **When Not to Use:** High-quality offline rendering requiring precise sampling (use ray casting); memory-constrained environments with large volumes using 2D textures.

## Background
Texture-Based Volume Rendering was developed to accelerate volume rendering on graphics hardware. Early implementations used 2D textures due to hardware limitations, leading to object-aligned slicing techniques [S7, unofficial]. The advent of 3D texture support in GPUs allowed for view-aligned slicing and trilinear interpolation, significantly improving image quality and eliminating viewing angle artifacts [S1, S7, unofficial]. The technique is widely used in medical imaging and scientific visualization for interactive exploration of volumetric data [S3, book][S5, unofficial].
