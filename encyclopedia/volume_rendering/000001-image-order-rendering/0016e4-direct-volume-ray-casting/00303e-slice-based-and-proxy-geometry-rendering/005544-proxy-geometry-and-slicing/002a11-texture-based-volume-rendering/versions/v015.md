# Texture-Based Volume Rendering

Also called: Geometry-based volume visualization, Proxy Geometry Rendering, Slice-based rendering, TBVR, Texture Based Ray Casting

## Overview
Texture-Based Volume Rendering (TBVR) is a forward-projection technique that renders volumetric data by rasterizing a set of 2D proxy geometry primitives (slices) through the volume, which are textured with the volumetric data and composited in sorted order using fragment shaders [S2, unofficial][S3, book][S7, unofficial]. It solves the problem of interactive volume visualization on GPUs by exploiting the hardware's texture sampling and blending capabilities, avoiding the need for explicit ray-marching loops in the shader [S1, S4, unofficial]. Unlike [Image-Based Volume Rendering](11273-image-based-volume-rendering.md) which projects pixels back into the volume, TBVR projects geometry forward into the image space [S1, unofficial]. It differs from [Hybrid Ray Tracing](2308-hybrid-ray-tracing.md) by relying on standard rasterization and alpha blending rather than ray intersection logic [S6, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D scalar volume dataset (regular grid), a transfer function (mapping scalar values to color/opacity), and camera parameters (view and projection matrices).
*   **Output:** A 2D image composited in the frame buffer.

**Data Structures:**
1.  **Volume Texture:** The scalar data is stored in GPU texture memory. It can be implemented as:
    *   A single 3D texture (`sampler3D`) [S2, unofficial][S3, book][S5, unofficial].
    *   A stack of 2D textures (`sampler2D` array or multiple units) [S2, unofficial][S3, book][S7, unofficial].
    *   *Layout (3D Texture):* Typically `RedFormat` (or `R8UI`/`R32F` depending on precision), `UnsignedByteType` or `FloatType`, with `LinearFilter` enabled for trilinear interpolation [S5, unofficial]. Dimensions are $(W, H, D)$ corresponding to $(TEXTURE\_SIZE\_X, TEXTURE\_SIZE\_Y, TEXTURE\_SIZE\_Z)$ [S5, unofficial].
2.  **Transfer Function Texture:** A 1D texture (`sampler1D`) mapping scalar values to RGBA color/opacity [S3, book][S5, unofficial].
3.  **Proxy Geometry:** A set of polygons (typically triangles or quads) representing planar slices through the volume bounding box.
    *   *Vertex Layout:* Each vertex contains 3D position $(x, y, z)$ and 3D texture coordinates $(u, v, w)$ [S2, unofficial][S3, book].
    *   *Bounding Box:* Defined by 8 vertices, e.g., $(\pm 80, \pm 128, \pm 110.5)$ [S5, unofficial].

**Numbered Steps:**

1.  **Initialize:**
    *   Load volume data into CPU memory. Process if necessary (e.g., compute gradients, downsample) [S3, book][S9].
    *   Create the transfer function lookup table (1D texture) [S3, book][S9].
    *   Download the volume data to GPU memory as a 3D texture or a stack of 2D textures [S2, unofficial][S3, book][S5, S8, unofficial].
    *   Compile and link fragment shaders [S3, book][S9].

2.  **Update (Per Frame or Parameter Change):**
    *   **Compute Proxy Geometry:** Determine the intersection of slicing planes with the volume bounding box.
        *   *View-Aligned:* Planes are orthogonal to the viewing direction. Intersect planes with the bounding box, sort resulting vertices in counter-clockwise order, and construct a polygon primitive (e.g., triangle fan from centroid) [S2, S6, unofficial].
        *   *Object-Aligned:* Planes are aligned with principal axes (x, y, z). Requires three stacks of 2D textures if arbitrary viewing is needed [S2, S6, unofficial].
    *   **Assign Texture Coordinates:** Calculate 3D texture coordinates for each slice vertex. These map the geometry to the volume data space [S2, unofficial][S3, book].
    *   **Refresh Textures:** If rendering mode, transfer function, or sampling rate changes, update the transfer function texture (potentially applying opacity correction) [S3, book][S9].

3.  **Draw:**
    *   Set up rendering state:
        *   Disable lighting and culling [S3, book][S9].
        *   Enable alpha blending. For the Over operator (back-to-front): Source = 1, Destination = 1 - Source Alpha [S2, unofficial][S3, book]. For the Under operator (front-to-back): Source = 1 - Destination Alpha, Destination = 1 [S2, unofficial].
        *   Disable depth testing or disable depth buffer writing if blending with opaque geometry [S3, book][S9].
        *   Bind the volume data texture to a texture unit [S3, book][S9].
        *   Bind the transfer function texture [S3, book][S9].
    *   **Render Slices:** Draw the proxy geometry polygons in sorted order (back-to-front for Over operator) [S2, unofficial][S3, book][S9].

**Fragment Shader Execution:**
For each fragment generated by the rasterized slice:
1.  **Interpolate Texture Coordinates:** Receive interpolated 3D texture coordinates $(u, v, w)$ from vertex attributes [S3, book][S9].
2.  **Data Lookup:** Sample the volume data texture at $(u, v, w)$ to retrieve the scalar value $v$ [S2, unofficial][S3, book][S9].
    *   *Pseudocode:* `float v = texture(volumeTex, texCoord).r;`
3.  **Transfer Function Lookup:** Use $v$ as the texture coordinate to sample the 1D transfer function texture, retrieving color $C$ and opacity $\alpha$ [S3, book][S9].
    *   *Pseudocode:* `vec4 color = texture(tfTex, v);`
4.  **Illumination (Optional):** Modify the color using local illumination models (e.g., Blinn-Phong) [S2, unofficial][S3, book].
    *   Compute surface normal $N$ via finite differences of neighboring voxels [S2, S5, unofficial].
    *   Compute lighting contribution (Ambient + Diffuse + Specular) [S2, S5, unofficial].
    *   *Pseudocode:* `color.rgb = color.rgb * shading(N, V, L);`
5.  **Compositing:** The fragment color and alpha are sent to the hardware compositing stage, which blends them with the existing frame buffer content based on the configured blend function [S2, unofficial][S3, book].

**Pseudocode (Fragment Shader):**
```python
# Inputs:
# uniform sampler3D volumeTex;
# uniform sampler1D tfTex;
# uniform float u_thresh;
# uniform float u_alphaScale;
# varying vec3 texCoord; # Interpolated 3D texture coordinates

void main() {
    # 1. Sample volume data
    float v = texture(volumeTex, texCoord).r;

    # 2. Thresholding (Pitfall guard)
    if (v < u_thresh) {
        discard;
    }

    # 3. Transfer function lookup
    vec4 tfColor = texture(tfTex, v);
    vec3 color = tfColor.rgb;
    float alpha = tfColor.a;

    # 4. Optional Illumination (Blinn-Phong)
    # Compute normal N from gradients of volumeTex at texCoord
    # Compute light vector L and view vector V
    # color = color * (Ka + Kd * max(dot(N, L), 0) + Ks * pow(max(dot(H, N), 0), shininess))

    # 5. Apply alpha scaling and output
    gl_FragColor = vec4(color, alpha * u_alphaScale);
}
```

**Parameters:**
*   `PLANE_INC`: Increment value for plane slicing, typically 1.0 [S5, unofficial].
*   `u_slices`: Uniform `vec3` containing texture dimensions $(W, H, D)$ used to normalize coordinates [S5, unofficial].
*   `u_thresh`: Uniform `float` threshold for discarding fragments below a certain scalar value [S5, unofficial].
*   `u_alphaScale`: Uniform `float` multiplier for fragment alpha in transparent mode [S5, unofficial].
*   Shading Constants (Phong): $K_a=(0.1,0.1,0.1)$, $K_d=(0.6,0.6,0.6)$, $K_s=(0.2,0.2,0.2)$, shininess=100.0 [S5, unofficial].

**Edge Cases and Pitfalls:**
*   **Object-Aligned Artifacts:** Using 2D texture stacks aligned with object axes causes 3x memory consumption due to data replication along x, y, and z directions [S2, unofficial][S3, book][S6, unofficial][S9]. It also causes "image popping" artifacts when the viewpoint changes and the active texture stack swaps, and intensity variations as the sampling distance changes with the camera angle [S2, S6, S8, unofficial][S9].
*   **Viewing Angle Artifacts:** With 2D textures, sampling artifacts appear when the viewing angle approaches 45 degrees relative to the slices, as the viewer sees between slice gaps [S1, S8, unofficial].
*   **Sampling Rate Dependency:** The rendering quality depends on the volume's resolution. This can be mitigated by adding intermediate slices and using trilinear interpolation [S3, book][S7, unofficial][S9].
*   **Coordinate System Rotation:** If the model is rotated (e.g., y-axis maps to z-axis), clipping plane logic must be adjusted accordingly (e.g., `clipPlaneY` checks `texPosition.z`) [S5, unofficial].

## Subtopics

### 2D Slice Replication Approach
Stores data as a set of 2D texture slices. Proxy polygons are simple rectangles aligned with the slices. It is faster but requires three times more memory due to data replication along principal directions. It suffers from sampling artifacts at 45-degree viewing angles and intensity variations as the camera moves. Data replication can be avoided by reconstructing slices on the fly, but this incurs performance overhead [S9].

### View-Aligned Slices
Uses proxy geometry (parallel polygons) orthogonal to the viewing direction. This allows the use of 3D textures, eliminating the need for data replication and the associated memory/artifact issues of object-aligned slices. It provides consistent sampling distance and excellent image quality but is slightly slower due to trilinear interpolation and the computational cost of generating the proxy geometry for arbitrary views [S1, S2, unofficial][S3, book][S7, unofficial].

### Object-Aligned Slices
Uses proxy geometry aligned with the principal axes (x, y, z) of the volume. Requires storing the volume as three stacks of 2D textures (one for each axis) to support arbitrary viewing directions. It is fast and simple but suffers from 3x memory consumption, data replication, image popping artifacts during stack swaps, and intensity variations as the sampling distance changes with the viewpoint [S2, S6, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N \cdot S)$, where $N$ is the number of pixels and $S$ is the number of slices. The complexity is dominated by the rasterization of the proxy geometry and the fragment shader execution per slice.
*   **Memory Complexity:**
    *   *3D Texture:* $O(V)$, where $V$ is the volume size. No replication required [S3, book].
    *   *2D Texture Stack (Object-Aligned):* $O(3V)$ due to replication along three axes [S2, unofficial][S3, book][S6, unofficial][S9].
*   **Measured Performance:** Achieves interactive frame rates on modern GPUs by leveraging parallel texture sampling and hardware blending [S1, S4, unofficial]. 2D textures are faster to render than 3D textures on older hardware but suffer from artifacts [S1, S8, unofficial]. 3D textures provide better image quality and eliminate 45-degree artifacts but are slightly slower [S1, unofficial][S3, book].
*   **Strengths:** Interactive performance, simple implementation using standard graphics pipeline, good image quality with 3D textures, easy integration of transfer functions and illumination [S1, S2, unofficial][S3, book].
*   **Limitations:** Artifacts with 2D textures (popping, intensity variation), high memory usage for object-aligned approaches, dependency on sampling rate [S2, unofficial][S3, book][S6, S7, unofficial][S9].
*   **When to Use:** Interactive visualization where frame rate is critical and hardware supports 3D textures.
*   **When Not to Use:** When memory is extremely constrained and 3D textures are not supported, or when exact ray-marching accuracy is required without approximation artifacts [S2, S6, unofficial].

## Background
Texture-Based Volume Rendering was developed to leverage the texture sampling capabilities of early graphics hardware for interactive visualization. It emerged as a key technique in GPU-based volume rendering, shifting from software-based ray casting to hardware-accelerated rasterization. The NVIDIA GPU Gems Chapter 39 provides a comprehensive overview of the technique, detailing the transition from 2D to 3D textures and the implementation of fragment shaders for compositing [S3, book]. It is widely used in medical imaging and scientific visualization applications [S5, S7, unofficial].
