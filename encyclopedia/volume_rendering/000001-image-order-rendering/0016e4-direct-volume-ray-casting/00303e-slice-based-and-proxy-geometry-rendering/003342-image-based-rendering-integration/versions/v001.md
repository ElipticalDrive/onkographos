# Image-based rendering integration
Also called: Image-Based Rendering with Impostors, Impostor rendering, Image-based volume rendering

## Overview
This method integrates volume rendering into a polygonal virtual environment by treating rendered volume images as image-based primitives (impostors) within the scene [S1, unofficial]. It decouples the computationally expensive volume rendering process from the interactive client, distributing it to a separate server and transmitting the resulting images over a network [S1, unofficial]. Unlike direct ray casting or texture-based methods that render the volume locally, this approach uses 2D quads textured with pre-rendered volume slices to represent 3D data, enabling seamless mixing of volume and polygonal rendering [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Volume dataset (stored on server), camera viewing directions (stereo pair), head-tracker position data, polygonal scene geometry.
*   **Output:** Final composite image containing polygonal geometry and volume impostors.

**Data Structures:**
*   **Impostor:** A 2D quad primitive.
*   **Texture:** The rendered volume image for a specific viewing direction.
*   **Network Message:** Contains viewing direction vectors and request timestamps.

**Steps:**
1.  **Distribution Setup:** Deploy the volume rendering engine on a dedicated server with sufficient memory for the volume dataset [S1, unofficial]. The client runs a visualization application (e.g., Studierstube) [S1, unofficial].
2.  **View Direction Acquisition:** The client determines the required viewing directions for the current frame. For stereoscopic rendering, two directions are computed, one for each eye [S1, unofficial].
3.  **Request Transmission:** The client sends the viewing directions to the server via a Local Area Network (LAN) [S1, unofficial].
4.  **Volume Rendering (Server):** The server renders the volume data for the requested directions. This is typically done using direct volume ray casting or similar methods [S1, unofficial]. The rendering time varies from 20ms to 500ms depending on data complexity and mode [S1, unofficial].
5.  **Image Transmission:** The server sends the resulting 2D images back to the client [S1, unofficial].
6.  **Impostor Configuration:** The client creates two impostor quads, one for each eye [S1, unofficial].
7.  **Orientation Update:** Upon receiving head-tracker data indicating a user position change, the client updates the impostors' orientation [S1, unofficial]. Each quad is rotated around its center so that its surface normal faces the respective eye [S1, unofficial].
8.  **Texture Mapping:** The received volume images are applied as textures to the respective impostor quads [S1, unofficial].
9.  **Polygonal Rendering:** The client renders the polygonal virtual environment, including the textured impostors, using standard OpenGL or similar hardware-accelerated rasterization [S1, unofficial]. Perspective projection is applied to the quads normally [S1, unofficial].
10. **Asynchronous Update:** The request-response cycle runs in a background thread to prevent the virtual environment from freezing during the server's rendering delay [S1, unofficial].

**Parameters:**
*   **Network Latency:** A critical factor; high lag causes delayed response when manipulating volume data [S1, unofficial].
*   **Impostor Size:** Fixed; does not need to be varied as perspective rendering of the quads handles scaling [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Quick Rotation:** Rapidly turning the volume object causes visible artifacts because the displayed impostor image is delayed relative to the new viewing angle [S1, unofficial].
*   **Freezing:** If the update process is not asynchronous, the environment freezes during the 20ms–500ms rendering time [S1, unofficial].
*   **Network Delay:** Lag results in a delayed response to user interactions [S1, unofficial].

## Operating characteristics
*   **Performance:** Interactive frame rates for the volume component depend on data complexity. Up to 25fps for 128^3 resolution and approximately 11fps for 256^3 resolution are achievable [S1, unofficial]. The polygonal environment itself can maintain 60fps independently [S1, unofficial].
*   **Memory:** Requires sufficient memory on the server to hold the volume dataset [S1, unofficial].
*   **Strengths:** Flexibility and scalability due to distributed architecture; seamless integration of volume and polygonal rendering; non-blocking client interaction [S1, unofficial].
*   **Limitations:** Network latency causes visual lag during rapid head movements; decoupling of image update and display leads to artifacts when turning quickly [S1, unofficial].
*   **When to use:** Suitable for virtual environments where volume data is large, rendering is expensive, and the user interacts with a polygonal scene, provided network latency is manageable.
*   **When not to use:** Unsuitable for applications requiring strict real-time synchronization between head movement and volume appearance without network delay, or where local hardware is insufficient for the server role.

## Background
This method was developed for the "Studierstube" virtual environment, integrating the Real Time Volume Rendering Library (RTVR) [S1, unofficial]. It addresses the challenge of providing real-time volume visualization within virtual environments by leveraging image-based rendering techniques to mix volume and polygonal rendering seamlessly [S1, unofficial]. The approach distributes rendering to a separate server to add flexibility and scalability [S1, unofficial].
