# Parallel Domain-Decomposed Ray Casting

Also called: 3D Grid Process Distribution, Distributed Ray Casting, Distributed Volume Rendering via Subvolume Partitioning, MPI Ray Casting, Subvolume Parallelization

## Overview
Parallel Domain-Decomposed Ray Casting accelerates direct volume rendering by partitioning the 3D volume dataset into subvolumes and distributing them across multiple processing nodes in a distributed-memory environment [S1, S2, unofficial]. Each node independently performs front-to-back ray casting on its local subvolume, eliminating the need for global shared memory or inter-node ray passing during the sampling phase [S1, unofficial]. Unlike image-order or geometric subdivision methods that require complex synchronization of ray traversal, this method isolates computation per subvolume, compositing results only at the end to form the final image [S1, unofficial]. It is distinguished from sibling methods like [Parallel Volume Rendering with Local Ray Tracing and Parallel Compositing](7841-parallel-volume-rendering-with-local-ray-tracing-and-paralle.md) by its explicit 3D grid process distribution and post-rendering compositing strategy, making it suitable for large datasets exceeding single-node memory [S1, S2, unofficial].

## How it works
The method implements the standard direct volume ray casting pipeline [Parent](19-direct-volume-ray-casting.md) but distributes the data domain. The process assumes a distributed computing environment (e.g., MPI) where a host node coordinates data distribution and result aggregation [S1, S2, unofficial].

### Inputs and Outputs
**Inputs:**
- Volume data file (e.g., `.raw`), typically a 3D grid of scalar values [S2, unofficial].
- Transfer function files defining opacity and color mappings [S2, unofficial].
- Grid dimensions: $px, py, pz$ (integers defining the process grid) [S2, unofficial].
- Sampling step size $\Delta t$ (float) [S2, unofficial].

**Outputs:**
- Final composited image (e.g., PNG) [S2, unofficial].

### Data Structures
The volume data is partitioned into a 3D grid of subvolumes.

1.  **Volume Data (`data`)**:
    -   Layout: 3D NumPy array of shape $(z_{Total}, y_{Total}, x_{Total})$ [S2, unofficial].
    -   Type: `float32` [S2, unofficial].
    -   Partitioning: For a process at grid index $(k, j, i)$, the local data is a slice:
        $$
        data_{local} = data[z_k:z_{k+1}, y_j:y_{j+1}, x_i:x_{i+1}]
        $$
        where segment sizes are calculated as:
        $$
        x_{seg} = \lfloor x_{Total} / px \rfloor, \quad y_{seg} = \lfloor y_{Total} / py \rfloor, \quad z_{seg} = \lfloor z_{Total} / pz \rfloor
        $$
        Boundary adjustments ensure the last segment covers the remainder of the total dimension [S2, unofficial].

2.  **Opacity Transfer Function (`opacityData`)**:
    -   Layout: 2D array with 2 rows [S2, unofficial].
    -   Row 0: Indices (or positions) of transfer function stops [S2, unofficial].
    -   Row 1: Opacity values $\alpha$ corresponding to the positions [S2, unofficial].
    -   Type: `float32` [S2, unofficial].

3.  **Color Transfer Function (`colorData`)**:
    -   Layout: 2D array with 5 rows [S2, unofficial].
    -   Row 0: Indices (or positions) of transfer function stops [S2, unofficial].
    -   Rows 1-3: Red, Green, Blue color values respectively [S2, unofficial].
    -   Type: `float32` [S2, unofficial].

4.  **Intermediate Results (`colorMesh`, `opacityMesh`)**:
    -   `colorMesh`: 3D array storing the accumulated color contribution for each sample point along the ray within the subvolume [S2, unofficial].
    -   `opacityMesh`: 2D array storing the accumulated opacity for each sample point [S2, unofficial].
    -   *Note*: In the reference implementation [S2, unofficial], these are used to store per-sample contributions before final compositing, though standard ray casting accumulates into a single pixel color. The reference implementation aggregates these meshes spatially after ray casting.

### Numbered Steps

1.  **Initialization and Data Distribution**:
    -   Rank 0 loads the full volume data and transfer functions [S2, unofficial].
    -   Rank 0 calculates segment sizes based on $px, py, pz$ [S2, unofficial].
    -   Rank 0 iterates through the 3D process grid $(k, j, i)$ from $0$ to $pz-1$, $0$ to $py-1$, $0$ to $px-1$ [S2, unofficial].
    -   For each rank $count = k \cdot (py \cdot px) + j \cdot px + i$, Rank 0 sends the local subvolume slice, `opacityData`, `colorData`, and grid dimensions $(px, py, pz)$ to that rank using `comm.send()` [S2, unofficial].
    -   Other ranks receive their data using `comm.recv(source=0)` [S2, unofficial].

2.  **Local Ray Casting**:
    -   Each rank executes the ray casting algorithm on its local `data` using its local transfer functions [S2, unofficial].
    -   For each pixel in the image (mapped to the subvolume's spatial extent or the full image depending on implementation; the reference [S2, unofficial] implies full image rays are cast but only samples within the local subvolume contribute to the local mesh, or rays are restricted to the subvolume's view), rays are generated [S1, S2, unofficial].

However, standard domain decomposition for ray casting usually implies each node renders a portion of the image or the volume is split such that rays only intersect the local volume. The source [S1, unofficial] states "casting rays... through each subvolume independently". Source [S2, unofficial] sends the whole TF to all ranks. The compositing step `comm.send([colorMesh, opacityMesh], dest=surfaceProcess)` where `surfaceProcess = rank % t` suggests a specific aggregation strategy.
    -   *Standard Interpretation*: Rays are cast. If a ray intersects the local subvolume, samples are taken. The optical properties are computed via the transfer function.
    -   **Classification**: The scalar value $d$ at sample point $\mathbf{p}$ is mapped to opacity $\alpha$ and color $C$ using linear interpolation on the transfer function tables [S2, unofficial].
        -   Opacity interpolation:
            $$
            \alpha = \text{lerp}(opacityData[1][n], opacityData[1][n+1], \frac{d - opacityData[0][n]}{opacityData[0][n+1] - opacityData[0][n]})
            $$
        -   Color interpolation:
            $$
            C = \text{lerp}(colorData[row][n], colorData[row][n+1], \dots) \quad \text{for R, G, B}
            $$
    -   **Compositing**: The standard front-to-back over operator is applied [S1, S2, unofficial].
        $$
        C'_{i} = C'_{i-1} + (1 - \alpha'_{i-1}) \alpha_i C_i
        $$
        $$
        \alpha'_{i} = \alpha'_{i-1} + (1 - \alpha'_{i-1}) \alpha_i
        $$
        In the reference implementation [S2, unofficial], `colorMesh` and `opacityMesh` store the accumulated color and opacity for the ray segment passing through the subvolume.

3.  **Result Aggregation**:
    -   Ranks with index $\ge px \cdot py$ (the "back" layers in the z-dimension) send their `colorMesh` and `opacityMesh` to the corresponding rank $< px \cdot py$ (the "front" layers) [S2, unofficial].
    -   Specifically, `dest = rank % (px * py)` [S2, unofficial].
    -   The receiving ranks (front layers) collect meshes from the back layers.
    -   Rank 0 gathers all composited meshes, concatenates them spatially according to the $px/py$ structure, converts to `uint8`, and saves as an image [S2, unofficial].

### Parameters and Typical Values
-   **Process Grid ($px, py, pz$)**: Defines the 3D grid of MPI processes. Typical value: $2, 2, 2$ (8 processes) [S2, unofficial].
-   **Step Size ($\Delta t$)**: Fixed sampling interval along the ray direction. Controls sampling density. Typical value: $0.5$ [S2, unofficial].
-   **Workstations**: Historically 8 workstations arranged in an octant partitioning scheme [S1, unofficial].

### Edge Cases and Pitfalls
-   **Network Reliability**: The REX (Remote Execution) service on older Sun SPARC workstations was unreliable, necessitating the use of the slower `rsh` command [S1, unofficial].
-   **Boundary Conditions**: When dividing the volume, the last segment in each dimension must account for the remainder of the total size to avoid data loss [S2, unofficial].
-   **Interpolation**: Linear interpolation is used for transfer functions. Care must be taken with indices to avoid out-of-bounds access when the sample value exceeds the transfer function range [S2, unofficial].

## Subtopics

### [Parallel Volume Rendering with Local Ray Tracing and Parallel Compositing](7841-parallel-volume-rendering-with-local-ray-tracing-and-paralle.md)
A method that distributes both volume data and computation to individual processing units, using data-space subdivision. It is distinguished by using a binary-swap compositing method for the final image, whereas Parallel Domain-Decomposed Ray Casting typically uses a grid-based aggregation or spatial concatenation. Choose this when deep integration of compositing across nodes is required during the rendering pass.

## Operating characteristics
-   **Time Complexity**: $O(N \cdot P)$ where $N$ is the number of samples per ray and $P$ is the number of processes, assuming perfect load balancing. The communication overhead is $O(P)$ for data distribution and result aggregation [S1, S2, unofficial].
-   **Memory Complexity**: $O(V/P)$ per node, where $V$ is the total volume size. This allows rendering datasets larger than the memory of a single node [S1, unofficial].
-   **Measured Performance**: Achieved a 75% speedup compared to single-processor rendering while maintaining image quality [S1, unofficial].
-   **Strengths**:
    -   Scalability to large datasets that do not fit in single-node memory [S1, unofficial].
    -   Simplicity of the ray casting logic on each node (no inter-node ray passing) [S1, unofficial].
    -   Effective use of distributed-memory environments (MPI) [S2, unofficial].
-   **Limitations**:
    -   Requires data distribution and result aggregation, which can become a bottleneck if not optimized [S2, unofficial].
    -   Load imbalance may occur if the volume density or ray traversal depth varies significantly across subvolumes [S1, unofficial].
    -   Not suitable for interactive rendering on very large datasets due to communication latency [S1, unofficial].
-   **When to Use**: Large static volume datasets where interactive frame rates are not required, and a cluster of workstations is available [S1, unofficial].
-   **When Not to Use**: Interactive visualization requiring low latency, or when the volume fits comfortably in a single node's memory [S1, unofficial].

## Background
The method originated in the early 1990s as a solution to the speed limitations of volume rendering on single processors. It was proposed by researchers at the Air Force Institute of Technology (AFIT) to demonstrate that ray casting could be parallelized at the subvolume level on distributed systems without global shared memory [S1, unofficial]. The work was implemented on Sun SPARC-2 and Sun-4/260 workstations running SunOS 4.1.1, connected via AFITNET [S1, unofficial]. It contrasts with earlier geometric ray tracing parallelization methods (like Dippe and Swensen's) by dividing object space (volume) rather than world space or screen space [S1, unofficial].
