# Volumetric Spherical Harmonics Precomputed Radiance Transfer

Also called: Pre-computed Volume Radiance Transfer, Precomputed Radiance Transfer, Spherical Harmonics PRT, Volume Radiance Transfer, Volumetric PRT

## Overview
Volumetric Spherical Harmonics Precomputed Radiance Transfer (VSH-PRT) is a technique for rendering semi-transparent volumetric datasets with dynamic lighting by precomputing the scene's response to illumination [S2, unofficial]. It solves the problem of expensive real-time volume rendering by compressing the 6D Volume Radiance Transfer function into spherical harmonic coefficients stored on a surface mesh, allowing for fast runtime evaluation under arbitrary distant lighting [S2, unofficial]. It sets itself apart from direct volume rendering by performing the volume integration offline and compressing the result, and from standard surface PRT by explicitly handling the volumetric scattering process to determine the exit radiance [S2, unofficial].

## How it works
**Inputs:**
- A volumetric dataset (e.g., electronic density function) [S2, unofficial].
- A set of distant light sources (direction and intensity) [S1, unofficial].
- A surface representation (isosurface) extracted from the volume data [S2, unofficial].

**Outputs:**
- A rendered image of the volumetric object under the specified lighting [S2, unofficial].
- Precomputed spherical harmonic coefficients associated with each vertex of the surface mesh [S2, unofficial].

**Data Structures:**
- **Surface Mesh:** A triangle mesh extracted from the volume data [S2, unofficial]. Each vertex $v$ stores a vector of spherical harmonic coefficients [S2, unofficial].
- **SH Coefficients:** For a given vertex, the coefficients represent the Volume Radiance Transfer function compressed into the spherical harmonic basis [S2, unofficial]. The size of this vector depends on the number of basis functions used in the compression stage [S2, unofficial].
- **Volume Radiance Transfer (VRT):** Defined as a 6D function: two dimensions for incoming light direction, two dimensions for the location of the exiting radiance point, and two dimensions for the viewing direction [S2, unofficial].

**Parameters:**
- $L$: The order of the spherical harmonic basis. The number of basis functions is $N = (L+1)^2$ [G]. Typical tested values include 49, 100, 196, and 400 basis functions [S2, unofficial].
- $N_{views}$: The number of view directions sampled during precomputation. Example: 4000 directions [S2, unofficial].

**Steps:**

1. **Surface Extraction & Ray Recording:** Generate a surface representation of the volume data and associate the volume radiance transfer function for every extracted surface point [S2, unofficial]. For objects with a well-defined boundary, record the ray at the surface point where it exits, noting that the ray will not change after it exits the surface [S2, unofficial].
2. **Volume Radiance Sampling:** For each vertex on the extracted surface, sample the volume-scattered radiance along a sufficient number of directions using direct volume rendering algorithms [S2, unofficial].
3. **Spherical Harmonic Compression:** Compress the sampled volume radiance transfer function for each vertex using spherical harmonic basis functions [S2, unofficial].
4. **Runtime Rendering:** At runtime, render the scene by re-sampling the surface-mapped volume radiance transfer for a given viewing direction [S2, unofficial]. The final radiance $L(p)$ for a point $p$ is computed by combining the precomputed coefficients with the current light intensities [S1, unofficial].
$$ L(p) = \sum_{i} W_i \cdot L_i(p) $$
Where $W_i$ is the brightness of light $i$ and $L_i(p)$ is the precomputed unit contribution of light $i$ [S1, unofficial].

**Pseudocode:**

```python
def precompute_vrt(volume_data, surface_mesh, num_bands):
    """Precompute VRT coefficients for a surface mesh."""
    vertex_sh_coeffs = {}
    num_samples = 4000
    directions = generate_uniform_sphere_directions(num_samples)
    
    for vertex in surface_mesh.vertices:
        sampled_radiance = []
        for d in directions:
            # Standard volume integration along direction d from vertex position
            radiance = ray_march_volume(volume_data, vertex.position, d)
            sampled_radiance.append(radiance)
        # Project sampled radiance onto SH basis functions
        coeffs = project_to_sh_basis(sampled_radiance, directions, num_bands)
        vertex_sh_coeffs[vertex.id] = coeffs
    return vertex_sh_coeffs

def render_runtime(surface_mesh, vertex_sh_coeffs, light_intensities, view_direction):
    """Render scene using precomputed VRT coefficients."""
    image = allocate_image_buffer()
    for triangle in surface_mesh.triangles:
        c0 = vertex_sh_coeffs[triangle.v0.id]
        c1 = vertex_sh_coeffs[triangle.v1.id]
        c2 = vertex_sh_coeffs[triangle.v2.id]
        bary = compute_barycentric_coordinates(triangle, current_uv)
        interp_coeffs = bary[0]*c0 + bary[1]*c1 + bary[2]*c2
        
        radiance = 0.0
        for i, intensity in enumerate(light_intensities):
            sh_val = evaluate_sh_function(interp_coeffs, view_direction, directions[i])
            radiance += intensity * sh_val
        image.set_pixel(triangle, radiance)
    return image

# Standard helper definitions [G]
def generate_uniform_sphere_directions(n):
    return [uniform_sample_on_sphere() for _ in range(n)]

def ray_march_volume(vol, origin, dir):
    # Standard direct volume rendering integration
    return standard_volume_integration(vol, origin, dir)

def project_to_sh_basis(radiance_samples, directions, bands):
    # Solve linear system or apply precomputed SH projection matrix
    return standard_sh_projection(radiance_samples, directions, bands)

def allocate_image_buffer():
    return empty_array()

def compute_barycentric_coordinates(tri, uv):
    return standard_barycentric_calculation(tri, uv)

def evaluate_sh_function(coeffs, view_dir, light_dir):
    return standard_sh_evaluation(coeffs, view_dir, light_dir)
```

**Edge Cases and Pitfalls:**
- **Ringing Artifacts:** The method exhibits ringing artifacts due to the truncation of the spherical harmonic series [S1, unofficial]. Prefiltering can mitigate this but leads to undesirable smoothening of the lighting [S1, unofficial].
- **Precision Loss:** If two triangles cover the same texel and have significantly different tangent spaces, there is a lack of precision in the reconstructed signal [S1, unofficial].
- **High Costs:** The method presents relatively high memory and bandwidth costs, as well as high runtime cost compared to simpler interpolation methods [S1, unofficial].

## Operating characteristics
**Time and Memory Complexity:**
- **Memory:** The memory requirement per vertex scales with the number of spherical harmonic basis functions [S2, unofficial]. For the Neghip dataset (64^3 volume), memory per vertex ranges from 294 bytes (49 SHs) to 12K bytes (Interpolated method) [S2, unofficial].
- **Runtime:** The rendering speed declines as the number of SH basis functions increases [S2, unofficial]. The run-time algorithm has lower time complexity than direct volume rendering algorithms [S2, unofficial].

**Measured Performance:**
Test results on the Neghip dataset (64^3 volume, 70569 triangles, 35435 vertices) on a 2GHz Pentium 4 PC with nVIDIA GeForceFX 5900:
- OpenSplat (Direct Volume Rendering): 0.042 fps [S2, unofficial].
- 49 SHs: 15.8 fps [S2, unofficial].
- 100 SHs: 12.5 fps [S2, unofficial].
- 196 SHs: 7.9 fps [S2, unofficial].
- 400 SHs: 4.5 fps [S2, unofficial].
- Interpolated (No SH compression): 31.5 fps [S2, unofficial].

**Strengths and Limitations:**
- **Strengths:** Allows for efficient synthesis of the appearance of volumetric objects at runtime for any given view direction under arbitrary lighting [S2, unofficial]. Provides consistent lighting between static and dynamic geometry [S1, unofficial].
- **Limitations:** High memory and bandwidth costs [S1, unofficial]. High runtime cost compared to interpolation [S1, unofficial]. Ringing artifacts require prefiltering, which smooths lighting [S1, unofficial].

**When to Use:**
- Use when dynamic lighting is required for volumetric data and direct volume rendering is too slow [S1, unofficial].
- Use when the volume has a well-defined boundary [S2, unofficial].

**When Not to Use:**
- Do not use if memory bandwidth is a critical bottleneck [S1, unofficial].
- Do not use if high-frequency lighting details are required and ringing artifacts are unacceptable without smoothing [S1, unofficial].

## Background
The concept of Precomputed Radiance Transfer (PRT) was introduced by Sloan et al., who stored the scene's response to light with a distribution defined by spherical harmonic basis functions, allowing rendering of scenes with arbitrary lighting setups [S1, unofficial]. Lehtinen et al. described a volumetric approach to calculate precomputed transfer, allowing querying at any location in 3D space and providing consistent lighting between static and dynamic geometry [S1, unofficial]. The specific application of Spherical Harmonics to Volumetric Radiance Transfer was detailed in research on fast volume visualization, demonstrating the compression of the 6D VRT function [S2, unofficial].
