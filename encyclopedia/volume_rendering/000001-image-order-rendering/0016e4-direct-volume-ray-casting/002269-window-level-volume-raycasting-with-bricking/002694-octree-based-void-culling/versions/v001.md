# Octree-based Void Culling

Also called: Brick Octree, Void Culling Octree

## Overview
Octree-based void culling is a spatial acceleration technique used in direct volume ray casting to reduce rasterization load by skipping empty regions within volume bricks [S1, unofficial]. It builds on [Window/Level Volume Raycasting with Bricking](2775-window-level-volume-raycasting-with-bricking.md) by introducing a per-brick octree structure that describes only the geometry of visible data, allowing the renderer to bypass void areas before invoking the GPU [S1, unofficial]. Unlike sibling methods that may rely on global spatial structures or GPU-side culling, this approach generates and traverses the octree on the CPU to minimize GPU workload, while the GPU handles the actual interpolation, transfer function application, and blending [S1, unofficial].

## How it works

### Inputs and Outputs
*   **Input:** A volume brick (texture), a transfer function mapping scalar values to opacity ($\alpha$) and color, and an octree level limit.
*   **Output:** A set of rasterized slices (cuboid boxes) representing the visible portion of the brick, blended into the frame buffer.

### Data Structures
The octree is stored in main memory. Each node in the octree represents a cuboid sub-region of the brick.
*   **Node Fields:**
    *   `ratio` ($r$): A float representing the ratio of visible data to total data within the node's cube.
    *   `children`: An array of 8 child nodes (if not a leaf).
    *   `is_leaf`: Boolean indicating if the node represents a single cell.
*   **Leaf Nodes:** At the final octree level, each node represents a unique cell.
    *   If the cell is completely void, $r = 0$.
    *   If the cell is completely filled (visible), $r = 1$.

### Definitions
*   **Cell:** The smallest unit of void detection.
    *   For trilinear interpolation, a cell is a cube defined by 8 corner adjacent voxel values.
    *   A cell is **completely void** if all 8 corner values are transparent ($\alpha = 0$) after applying the transfer function.
    *   For other interpolation kernels, the cell size is defined as $(kernelsize - 1)^3$ [S1, unofficial].

### Algorithm Steps

1.  **Octree Construction (CPU):**
    *   Initialize leaf nodes for the brick.
    *   For each leaf node, determine if it is void or filled based on the cell definition. Set $r=0$ or $r=1$ accordingly.
    *   Recursively calculate $r$ for higher-level nodes by averaging the $r$ values of their 8 children:
        $$ r_{parent} = \frac{1}{8} \sum_{i=1}^{8} r_{child_i} $$
    *   This calculation is performed only when the transfer function changes [S1, unofficial].

2.  **Rendering Preparation (CPU):**
    *   Sort bricks in front-to-back order relative to the camera.
    *   For each brick, traverse its octree starting from the root node.

3.  **Octree Traversal and Culling (CPU):**
    *   For each node, evaluate its ratio $r$ against a threshold $T$ (where $0 < T \le 1$).
    *   **Case $r = 0$:** The node is completely void. Do not draw and do not traverse further [S1, unofficial].
    *   **Case $0 < r < T$:** The node contains mixed data. Sort its 8 children in front-to-back order. There are 8 possible valid orders due to axis alignment constraints (not $8!$) [S1, unofficial]. Recursively apply this strategy to each child.
    *   **Case $r \ge T$:** The node is sufficiently filled. Draw the node completely as a cuboid box. Do not traverse further [S1, unofficial].
    *   **Level Limit:** To prevent excessive overhead at deep levels, an octree level limit is set. Nodes below this level that are not void ($r > 0$) are drawn completely without further traversal [S1, unofficial].

4.  **Rendering (GPU):**
    *   When a node is selected for drawing (Case $r \ge T$ or leaf nodes), the corresponding cuboid box is sliced.
    *   Slices can be axis-aligned or viewport-aligned.
    *   The brick texture is interpolated on each slice.
    *   The transfer function is applied.
    *   Slices are rasterized and blended into the previously drawn slices [S1, unofficial].

### Pseudocode

```python
def render_brick_octree(brick_texture, transfer_function, threshold, max_depth, current_depth, node, camera_direction):
    """
    Recursively traverse the octree for a single brick.
    
    Args:
        brick_texture: The texture data for the brick.
        transfer_function: Function mapping voxel value to (color, alpha).
        threshold: Float T. If node.r >= T, draw node.
        max_depth: Integer. Stop traversal if current_depth >= max_depth.
        current_depth: Integer. Current depth in the octree.
        node: The current octree node.
        camera_direction: Vector. Direction of view for sorting.
    """
    
    # Base case: Leaf node or max depth reached
    if node.is_leaf or current_depth >= max_depth:
        if node.r > 0:
            # Draw the cuboid box corresponding to this node
            render_cuboid_box(node.cuboid, brick_texture, transfer_function, camera_direction)
        return

    # Case 1: Completely void
    if node.r == 0:
        return

    # Case 2: Mixed data, below threshold
    if node.r < threshold:
        # Sort children in front-to-back order
        # There are 8 valid orders due to axis alignment
        sorted_children = sort_children_front_to_back(node.children, camera_direction)
        
        for child in sorted_children:
            render_brick_octree(brick_texture, transfer_function, threshold, max_depth, current_depth + 1, child, camera_direction)
        
    # Case 3: Sufficiently filled, draw completely
    else:
        render_cuboid_box(node.cuboid, brick_texture, transfer_function, camera_direction)

def render_cuboid_box(cuboid, texture, transfer_function, camera_direction):
    """
    Render a cuboid box by slicing it.
    """
    # Determine slice orientation (axis-aligned or viewport-aligned)
    slices = generate_slices(cuboid, camera_direction)
    
    for slice_plane in slices:
        # Interpolate texture on the slice
        slice_data = interpolate_texture_on_slice(slice_plane, texture)
        
        # Apply transfer function
        rendered_slice = apply_transfer_function(slice_data, transfer_function)
        
        # Rasterize and blend
        rasterize_and_blend(rendered_slice)
```

### Parameters
*   **Threshold ($T$):** Determines the trade-off between void culling and triangle throughput.
    *   $T=1$: Draws only fully filled cells. Results in high triangle count at boundaries [S1, unofficial].
    *   $T < 1$: Allows some void data to be drawn, reducing overhead from small cubes [S1, unofficial].
*   **Octree Level Limit:** Prevents traversal beyond a certain depth, drawing non-void nodes completely to avoid overhead [S1, unofficial].

### Edge Cases and Pitfalls
*   **Boundary Artifacts:** Setting the threshold too high (close to 1) creates many tiny cubes at the boundaries of visible data, increasing triangle throughput load [S1, unofficial].
*   **Transfer Function Changes:** The octree ratios must be recalculated whenever the transfer function changes, as void definitions depend on $\alpha$ [S1, unofficial].
*   **Sorting Complexity:** While there are 8 children, the number of valid front-to-back sorting orders is limited to 8 due to axis alignment, not $8!$ [S1, unofficial].

## Operating characteristics

*   **Time Complexity:** Octree construction is $O(N)$ where $N$ is the number of cells in the brick. Traversal is proportional to the number of visible nodes.
*   **Memory Complexity:** $O(N)$ for storing the octree in main memory.
*   **Performance:** Reduces GPU workload by avoiding rasterization of void regions. The CPU handles the traversal, offloading the GPU to pure rendering tasks [S1, unofficial].
*   **Strengths:** Effective for datasets with large void regions. Reduces rasterization bottleneck.
*   **Limitations:** Requires CPU-side processing. Overhead from small cubes if threshold is not tuned.
*   **When to use:** When rendering large volume bricks with significant empty space and when CPU resources are available for traversal.
*   **When not to use:** When the dataset is dense with little void space, or when CPU overhead outweighs the rasterization savings.

## Background

*   **Origin:** Described by Danny Ruijters in "Optimizing GPU Volume Rendering" [S1, unofficial].
*   **History:** Developed as part of a suite of optimizations for GPU volume rendering, specifically targeting the rasterization bottleneck in direct volume ray casting with bricking.
*   **Usage:** Used in high-performance volume rendering systems where large datasets are divided into bricks and efficient culling is required to maintain frame rates.
