# Object-Order Ray-Casting

Also called: Data-parallel volume rendering

## Overview
Object-order ray-casting is a volume rendering technique that transforms the volumetric data to align with the view direction, allowing rays to sample at integer grid points. It combines the high-quality trilinear interpolation of image-order ray-casting with the cache-friendly, regular memory access patterns of object-order methods [S1, S2]. Unlike image-order ray-casting, which suffers from cache misses due to irregular voxel access, or Shear-Warp, which introduces artifacts and blurring, this method maintains interactive frame rates (up to 10 fps) while preserving image quality [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D scalar volume dataset $V$ of size $N_x \times N_y \times N_z$, a view direction, and an orthogonal projection matrix.
*   **Output:** A 2D image (frame buffer) with accumulated color and opacity values.

**Data Structures:**
*   **Volume Data:** A 3D array of scalar values (and optionally gradients) representing density or intensity.
*   **Frame Buffer:** A 2D array storing accumulated color $C$ and opacity $\alpha$ for each pixel. Initialized to $(0, 0)$.

**Method Steps:**

1.  **Transformation Decomposition:**
    Decompose the transformation from the volume's local coordinate system to the view-aligned coordinate system into a sequence of affine transforms. These transforms typically consist of shear and scale operations along orthogonal axes [S2]. This decomposition ensures that the resampling locations coincide with integer grid points in the transformed space [S2].

2.  **Resampling:**
    Perform a 3D resampling of the volume using the decomposed affine transforms. This step generates a regular data access pattern where voxels are accessed in a cache-friendly manner [S2]. The resampling uses trilinear interpolation to estimate values at non-integer coordinates if necessary, but the primary goal is to align the volume with the view direction [S1, S2].

3.  **Ray-Cell Intersection and Sampling:**
    For every voxel cell that is not transparent and not hidden:
    a. Load the values and gradients of the 8 vertices of the cell [S1].
    b. Determine the rays intersecting the cell. In the transformed space, these rays are aligned with the grid axes, simplifying intersection tests [S1].
    c. For each intersecting ray, sample colors $C_s$ and opacities $\alpha_s$ along the ray within the cell using trilinear interpolation [S1].

4.  **Compositing:**
    Update the frame buffer for the pixels corresponding to the intersected rays. The compositing follows the front-to-back accumulation model defined by Kajiya's low albedo form [S1].

**Formulas:**

The optical model is based on Kajiya's low albedo form [S1]:

$$I_\lambda = \int_0^t C_\lambda(s) \times \tau(s) \times \exp\left(-\int_0^s \tau(t) \, dt\right) ds \quad (1)$$

Where:
*   $I_\lambda$: Light intensity of wavelength $\lambda$ reaching the viewpoint.
*   $C_\lambda(s)$: Color contribution at position $s$.
*   $\tau(s)$: Extinction coefficient at position $s$.
*   $t$: Total length of the ray through the volume.

This integral is approximated using a Riemann sum with even sampling distance $\Delta s$. The accumulated color $C_{i+1}$ and opacity $\alpha_{i+1}$ are updated recursively in front-to-back order [S1]:

$$C_{i+1} = C_i + (1-\alpha_i) \alpha_s C_s \quad (2)$$
$$\alpha_{i+1} = \alpha_i + (1 - \alpha_i) \alpha_s \quad (3)$$

Where:
*   $C_i, \alpha_i$: Accumulated color and opacity before step $i$.
*   $C_s, \alpha_s$: Sampled color and opacity at step $i$.
*   $\Delta s$: Sampling distance.

**Parameters:**
*   **Sampling Distance ($\Delta s$):** Critical for quality vs. speed trade-off. Large $\Delta s$ accelerates rendering but reduces quality [S1]. Not given in the sources.
*   **Target Performance:** Up to 10 frames per second on current workstations [S1].

**Pseudocode:**

```python
def object_order_ray_casting(volume, view_transform, frame_buffer):
    """
    volume: 3D array of scalar values (density/intensity)
    view_transform: Decomposed affine transforms (shear/scale) to align volume with view
    frame_buffer: 2D array of (color, opacity) tuples, initialized to (0, 0)
    """
    
    # Step 1 & 2: Transform and Resample
    # The volume is transformed to align with the view direction.
    # This is done via decomposed affine transforms (shear/scale).
    # The result is a resampled volume where voxel access is regular.
    transformed_volume = resample_volume(volume, view_transform)
    
    # Step 3: Ray-Cell Intersection and Sampling
    # Iterate over all cells in the transformed volume
    for cell in transformed_volume.cells:
        if cell.is_transparent():
            continue
        if cell.is_hidden():
            continue
            
        # Load vertex data
        vertex_values = cell.get_vertex_values()
        
        # Determine intersecting rays
        # In the transformed space, rays are aligned with grid axes
        intersecting_rays = cell.get_intersecting_rays()
        
        for ray in intersecting_rays:
            # Sample along the ray within the cell
            # Use trilinear interpolation for high quality
            samples = ray.sample_cell(cell, vertex_values)
            
            # Step 4: Compositing
            # Update frame buffer using front-to-back accumulation
            for sample in samples:
                pixel = frame_buffer.get_pixel(ray.pixel_coordinates)
                c_i, a_i = pixel.color, pixel.opacity
                c_s, a_s = sample.color, sample.opacity
                
                # Kajiya's low albedo form approximation
                new_alpha = a_i + (1 - a_i) * a_s
                new_color = c_i + (1 - a_i) * a_s * c_s
                
                pixel.color = new_color
                pixel.opacity = new_alpha

    return frame_buffer
```

**Edge Cases and Pitfalls:**
*   **Sampling Distance:** Large $\Delta s$ leads to low-quality images [S1].
*   **Cache Misses:** Image-order ray-casting suffers from cache misses because every ray step loads eight samples for trilinear interpolation, which cannot be stored in memory order [S1]. Object-order ray-casting avoids this by accessing voxels a limited number of times [S1].
*   **Hidden Volume Removal:** Object-order methods traditionally struggle with skipping empty regions, especially with interactive classification [S1]. An efficient hidden volume removal technique is required to compensate for the loss of early ray termination inherent in image-order algorithms [S1].

## Operating characteristics
*   **Time Complexity:** The method aims for interactive performance, targeting up to 10 fps on current workstations [S1]. In a two-pass implementation, it achieved approximately 3 fps on a 256^3 bonsai dataset [S1].
*   **Memory Complexity:** Depends on the volume size and the frame buffer. The transformation and resampling steps require additional memory for the transformed volume [S2].
*   **Strengths:**
    *   Combines speed of object-order methods (optimized volume run, easy space leaping) with high-quality image generation of ray-casting (trilinear interpolation) [S1].
    *   Avoids cache misses associated with image-order ray-casting [S1].
    *   Avoids low sampling rates on the z-axis (1 to 1.73), pre-classification blurring, and artifacts at 45-degree viewing angles associated with Shear-Warp [S1].
    *   Avoids blurring of small details inherent to Gaussian low-pass filters in Splatting [S1].
*   **Limitations:**
    *   Requires efficient hidden volume removal to compensate for the loss of early ray termination [S1].
    *   Accuracy depends critically on the sampling distance $\Delta s$ and the evaluation of sampled values [S1].
*   **When to Use:** When high-quality interactive volume rendering is required, and the hardware supports efficient 3D resampling and orthogonal projection [S1, S2].
*   **When Not to Use:** When early ray termination is critical and hidden volume removal is not efficiently implemented, or when the view direction changes frequently and the transformation overhead is prohibitive.

## Background
Object-order ray-casting was introduced as an efficient and accurate volume rendering technique to overcome the limitations of existing methods [S1]. It was developed to achieve interactive high-quality rendering (up to 10 fps) on workstations [S1]. The method builds on the idea that the projection of a parallelepipedic shape can be efficiently performed under orthogonal projection, enabling object-order traversal while maintaining ray-casting quality [S1]. It is also known as data-parallel volume rendering because operations on the volume semantically involve all voxels at once [S2]. The technique has been implemented in hardware architectures like VIRIM, which uses lookup tables for interpolation and programmable lighting/viewing parameters [S2].
