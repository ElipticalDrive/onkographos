# Front-to-Back Rendering with Dynamic Screen

Also called: Front-to-Back (FTB) Volume Viewing, Front-to-Back Rendering, Goldwasser et al. Front-to-Back

## Overview
Front-to-Back Rendering with Dynamic Screen is a direct volume ray casting method that accelerates image-order rendering by combining front-to-back voxel traversal with a dynamic screen data structure to track un-lit pixels [S1, S2, unofficial]. It sets itself apart from standard front-to-back volume rendering by explicitly managing pixel occupancy via free runs, thereby ignoring voxels that project to already-lit areas and eliminating the need for a Z-buffer for hidden voxel removal [S1, S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D scalar volume dataset and camera parameters including position, orientation, and transformation matrices for rotation, scaling, and slice planes [S1, unofficial].
*   **Output:** A 2D image buffer containing accumulated color and depth information for each pixel [S1, unofficial].

**Data Structures:**
1.  **Image Buffer:** Stores the accumulated color and the depth of the projected voxel for each pixel [S1, unofficial].
2.  **Dynamic Screen:** A data structure that stores, for each scanline, the free (unused) runs of pixels that can make up the image [S1, unofficial]. This allows the algorithm to identify which pixels have not yet been lit by a voxel [S2, unofficial].

**Algorithm Steps:**
1.  **Preprocessing:** Apply rotational transformations such that projected line segments of the object are parallel to image scanlines [S1, unofficial]. This choice leverages object and scan-line coherence [S1, unofficial].
2.  **Voxel Traversal:** Traverse the volume data in increasing distance order from the observer (front-to-back) [S1, S2, unofficial]. This order implicitly eliminates hidden structures and supports semi-transparent materials by simulating light passage through materials in the correct order [S2, unofficial].
3.  **Projection and Culling:** For each voxel, project it onto the image plane [S1, unofficial]. Check the dynamic screen to determine if the voxel projects to any free (un-lit) pixel runs [S1, unofficial].
4.  **Compositing:** If the voxel projects to free areas, compute the voxel's color and opacity [S2, unofficial]. Composite the voxel's color and opacity onto the corresponding pixels in the image buffer using front-to-back blending [S2, unofficial]. Update the image buffer with the depth of the projected voxel [S1, unofficial].
5.  **Dynamic Screen Update:** Remove the newly-lit pixels from the dynamic screen's free runs [S2, unofficial].
6.  **Shading:** Apply gradient and depth shading to the resulting image using the stored depth of each projected voxel [S1, unofficial].

    # 1. Pre-transform volume so projected segments align with scanlines [S1, unofficial]
    # 2. Sort voxels by distance to camera origin (front-to-back) [S1, S2, unofficial]
    sorted_voxels = sorted(volume.voxels, key=lambda v: distance(v.center, camera.origin))

    for voxel in sorted_voxels:
        # 3. Project voxel footprint to pixel coordinates
        projected_pixels = set()
        for scanline in range(camera.height):
            for col in range(camera.width):
                if voxel_projects_to_pixel(voxel, col, scanline, camera):
                    projected_pixels.add((col, scanline))

        # 4. Intersect with dynamic screen free runs
        free_pixels = []
        for scanline, runs in dynamic_screen.items():
            for run in runs:
                for p in projected_pixels:
                    if run.contains(p):
                        free_pixels.append(p)

        if not free_pixels:
            continue

        # 5. Compute voxel color and opacity
        color, opacity = transfer_function(voxel.value)

        # 6. Composite onto free pixels and store depth
        for p in free_pixels:
            old_color, old_depth = image_buffer[p]
            # Front-to-back blending: C_out = C_in * (1 - alpha) + C_voxel * alpha
            new_color = old_color * (1.0 - opacity) + color * opacity
            image_buffer[p] = (new_color, voxel.depth)

        # 7. Remove newly lit pixels from dynamic screen
        for p in free_pixels:
            remove_pixel_from_screen(p, dynamic_screen)

    # 8. Apply gradient and depth shading to the resulting image [S1, unofficial]
    shaded_image = apply_shading(image_buffer, volume.gradients)
    return shaded_image

**Edge Cases and Pitfalls:**
*   **Precision:** Depth must be stored per pixel to support gradient and depth shading [S1, unofficial].
*   **Boundaries:** The dynamic screen must correctly merge free runs when pixels become lit [S2, unofficial].
*   **Degenerate Input:** If the volume is empty or the camera is invalid, no voxels are processed [G].

## Operating characteristics
*   **Time Complexity:** Depends on the number of voxels and the efficiency of dynamic screen updates, with the dynamic screen reducing processed pixels by ignoring lit areas and leveraging coherence [S1, unofficial].
*   **Memory Complexity:** Requires storage for the volume data, image buffer, and dynamic screen structure [S1, S2, unofficial].
*   **Measured Performance:** Implemented by Goldwasser et al. on a special multiprocessor architecture to produce shaded graphics displays in real time with rotation, scaling, slice planes, and shading transformations on grey-scale data [S1, unofficial].
*   **Strengths:** Efficiently handles semi-transparent materials; eliminates hidden voxel removal via front-to-back order; reduces processing by ignoring lit pixels [S1, S2, unofficial].
*   **Limitations:** Requires a special multiprocessor architecture for real-time performance as originally implemented; dynamic screen management adds complexity [S1, S2, unofficial].
*   **When to Use:** When real-time rendering of semi-transparent volumes is required and hardware supports the necessary parallelism [S1, unofficial].
*   **When Not to Use:** When hardware lacks the required multiprocessor architecture or when simplicity is preferred over performance [S1, unofficial].

## Background
The front-to-back rendering algorithm was developed by Goldwasser et al. and implemented on a special multiprocessor architecture [S1, unofficial]. It merges three techniques: front-to-back traversal, dynamic screen data structure, and rotational transformations [S1, unofficial]. The algorithm was designed to produce shaded graphics displays in real time for medical data visualization, specifically for stereotactic neurosurgery planning [S1, unofficial]. The approach avoids the need for a Z-buffer by using the painter's algorithm with front-to-back compositing [S2, unofficial].
