# Local Rendering Phase

## Overview
The Local Rendering Phase is the core computation step in the Object-Space (OS) parallel implementation of Koyamada's Algorithm [S1, unofficial]. It solves the problem of redundant ray-segment generation that occurs when local clusters on a single processor are treated as independent subvolumes [S1, unofficial]. By treating the set of local clusters assigned to a processor as a single local subvolume, it ensures that ray-segments crossing pseudo-boundary faces (shared between local clusters) are composed into a single continuous segment rather than being recomputed [S1, unofficial]. This phase builds on [Koyamada's Algorithm](4148-koyamada-s-algorithm.md) by handling the spatial decomposition constraints within a single processing unit [S1, unofficial].

## How it works
**Inputs:**
*   The set of local clusters $C_p$ assigned to processor $P_i$ [S1, unofficial].
*   The `CellArray` structures containing cell geometry and connectivity for these clusters [S1, unofficial].
*   The `RayBuffer` structure for the current pixel row/column being processed [S1, unofficial].

**Outputs:**
*   Composited color and opacity values for ray-segments exiting the local subvolume, stored in the `RayBuffer` [S1, unofficial].

**Data Structures:**
*   **CellArray**: Contains cell data with neighbor references [S1, unofficial].
*   **ClusterData**: Preserves connectivity information between cells despite clustering [S1, unofficial].
*   **RayBuffer**: A linked-list structure indexed by pixel location, where each entry stores a list of ray-segments sorted by their exit $z$-value [S1, unofficial].

**Steps:**
1.  **Concurrent Traversal**: Each processor $P_i$ concurrently traverses the cells of the `CellArray` structures of its local clusters $C_p$ [S1, unofficial].
2.  **Face Classification**: For each cell $c_i$ in $C_p$, check each face $f$ [S1, unofficial]. Identify $f$ as an **external face** if cell $c_i$ does not have a neighbor cell through face $f$ [S1, unofficial]. Identify $f$ as a **boundary face** if cell $c_i$ is neighbor to a cell $c_j$ through face $f$ such that $c_j$ belongs to a non-local cluster of $P_i$ [S1, unofficial]. Faces shared between two local clusters of $P_i$ are **pseudo-boundary faces** and are skipped for ray generation [S1, unofficial].
3.  **Ray-Segment Generation**: Scan-convert each identified external and boundary face [S1, unofficial]. Generate a ray-segment for each pixel covered by the face [S1, unofficial].
4.  **Ray Traversal**: Follow each generated ray-segment through the local subvolume according to Koyamada's algorithm [S1, unofficial]. The traversal uses the connectivity information preserved in `ClusterData` structures, allowing the ray to pass through multiple local clusters seamlessly [S1, unofficial]. The ray continues until it exits from a boundary-external face or a boundary-boundary face [S1, unofficial].
5.  **Buffer Insertion**: When a ray-segment exits the local subvolume, insert its composited color and opacity values into the linked-list of the respective pixel location in the `RayBuffer` structure [S1, unofficial]. Insertion must be in sorted order according to the ray-segment's exit $z$-value [S1, unofficial].

**Pseudocode:**
```python
def local_rendering_phase(processor_id, local_clusters, cell_arrays, ray_buffer):
    """
    Renders the local subvolume defined by local_clusters for processor_id.
    """
    # Step 1 & 2: Traverse cells and classify faces
    ray_origins = []
    for cluster in local_clusters:
        for cell in cell_arrays[cluster]:
            for face in cell.faces:
                if not face.has_neighbor():
                    ray_origins.append((cell, face, 'external'))
                elif face.neighbor.cluster_id not in local_clusters:
                    ray_origins.append((cell, face, 'boundary'))
                # Pseudo-boundary faces (neighbor in local_clusters) are skipped

    # Step 3, 4 & 5: Generate, trace, and buffer ray-segments
    for cell, face, face_type in ray_origins:
        pixels = scan_convert_face(face)
        for pixel in pixels:
            # Initialize ray-segment parameters
            ray_origin = face.center
            ray_direction = face.normal
            step_size = cell.edge_length
            alpha = 0.0
            color = [0.0, 0.0, 0.0]

            current_cell = cell
            exit_z = 0.0

            # Step 4: Trace through local subvolume
            while True:
                # Sample cell data and perform front-to-back compositing
                density = current_cell.sample(ray_origin, ray_direction)
                alpha_cell = density * step_size
                color_cell = current_cell.color(density)

                alpha_out = alpha + (1.0 - alpha) * alpha_cell
                color_out = color + (1.0 - alpha) * color_cell * alpha_cell
                alpha = alpha_out
                color = color_out

                # Move to next cell along ray direction
                next_cell = current_cell.get_neighbor_in_direction(ray_direction)
                if next_cell is None:
                    exit_z = ray_origin.z + step_size
                    break
                if next_cell.cluster_id not in local_clusters:
                    exit_z = ray_origin.z + step_size
                    break
                current_cell = next_cell
                ray_origin += ray_direction * step_size

            # Step 5: Insert into RayBuffer sorted by exit z-value
            ray_buffer.insert_sorted(pixel, exit_z, color, alpha)

def scan_convert_face(face):
    """
    Rasterizes a polygonal face to return a list of covered pixel coordinates.
    """
    return face.bounding_box.rasterize()
```

**Edge Cases and Pitfalls:**
*   **Virtual Non-Convexities**: Object-Space (OS) decomposition may create local subvolumes with virtual non-convexities, even if the global dataset is convex [S1, unofficial]. This increases the number of ray-segments generated per pixel compared to the sequential algorithm [S1, unofficial].
*   **RayBuffer Necessity**: Due to virtual non-convexities, multiple ray-segments may exit the local subvolume for a single pixel [S1, unofficial]. The `RayBuffer` structure is crucial for handling this multiplicity and maintaining correct depth sorting [S1, unofficial].

## Operating characteristics
*   **Time Complexity**: Not given in the sources.
*   **Memory Complexity**: Depends on the `RayBuffer` size, which scales with the number of ray-segments per pixel [S1, unofficial]. Virtual non-convexities can increase this number [S1, unofficial].
*   **Strengths**: Eliminates redundant computation on pseudo-boundary faces by treating local clusters as a single subvolume [S1, unofficial].
*   **Limitations**: Virtual non-convexities from decomposition can lead to more ray-segments per pixel than in the sequential case, requiring robust `RayBuffer` management [S1, unofficial].
*   **When to use**: When implementing OS parallel direct volume rendering using Koyamada's Algorithm [S1, unofficial].

## Background
The Local Rendering Phase was introduced in the context of parallel direct volume rendering of unstructured grids based on object-space decomposition [S1, unofficial]. It addresses the inefficiencies of rendering local clusters independently by recognizing that clusters on the same processor are highly interacting and should be rendered as a unified local subvolume [S1, unofficial].
