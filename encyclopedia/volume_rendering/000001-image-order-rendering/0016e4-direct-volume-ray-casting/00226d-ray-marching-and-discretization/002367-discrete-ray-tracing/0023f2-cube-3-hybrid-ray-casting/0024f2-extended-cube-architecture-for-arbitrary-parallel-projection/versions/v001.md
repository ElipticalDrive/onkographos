# Extended Cube Architecture for Arbitrary Parallel Projection

Also called: Arbitrary Parallel Viewing Architecture

## Overview
The Extended Cube Architecture is a special-purpose computer architecture designed to enable real-time arbitrary parallel projection of volumetric data, overcoming the distortion limitations of rotating the Cubic Frame Buffer (CFB) for non-orthographic views [S1, unofficial]. It extends the original Cube architecture, which only supported orthographic projection, by introducing a 2D Skewed Buffer (2DSB) and a Ray Projection Tree (RPT) to fetch and process slanted planes of projection rays without pre-processing [S1, unofficial]. Unlike the original Cube, which accesses axial beams directly, this method handles arbitrary viewing directions by shearing the data into a 2D memory structure, aligning rays, and projecting them in parallel [S1, unofficial].

## How it works
The method transforms arbitrary parallel projection rays into a format suitable for parallel hardware processing. It operates on a dataset stored in a Cubic Frame Buffer (CFB) and produces a 2D projected image.

### Inputs and Outputs
*   **Input:** A volumetric dataset of size $n \times n \times n$ voxels stored in the CFB. The viewing direction is arbitrary (parallel projection).
*   **Output:** A 2D image where each pixel corresponds to a projection ray passing through the volume.

### Data Structures

**1. Cubic Frame Buffer (CFB)**
*   **Layout:** A 3D modular memory organization.
*   **Size:** For a $512^3$ dataset, the CFB holds 128M voxels [S1, unofficial].
*   **Access:** Supports conflict-free access to full beams of $n$ voxels in any orthographic direction [S1, unofficial].

**2. 2D Skewed Buffer (2DSB)**
*   **Purpose:** Stores the slanted Projection Ray Plane (PRP) and performs de-skewing.
*   **Layout:** Physically divided into $n$ modules, diagonally skewed to allow conflict-free writing of horizontal beams and reading of vertical rays [S1, unofficial].
*   **Dimensions:** Width is at least $2n-1$ columns to accommodate parallel rays entering the slanted PRP [S1, unofficial].
*   **Modules:** Contains $n$ modules. Each module connects to neighbors via conveyors (barrel shifters) with 256 lines (16 bits $\times$ 16 shift places) [S1, unofficial].
*   **Pipelining:** Uses multiple planes (e.g., 4 planes) to allow concurrent loading of the next PRP while processing the current one [S1, unofficial].

**3. Ray Projection Tree (RPT)**
*   **Purpose:** Parallel processing of viewing rays to compute pixel values.
*   **Layout:** A hierarchical binary tree of $n-1$ Voxel Combination Units (VCUs) [S1, unofficial].
*   **Leaves:** Accept $n$ voxels along a viewing ray.
*   **Root:** Produces the final color for the corresponding pixel.

**4. Voxel Combination Unit (VCU)**
*   **Input:** Two voxel values.
*   **Operation:** Combines inputs into an output voxel value.
*   **Latency:** 7 time units per combination [S1, unofficial].

### Steps

1.  **Retrieve Projection Ray Plane (PRP):** Identify the set of projection rays belonging to the same scan line of the projected 2D frame buffer. These rays form a slanted plane (PRP) within the CFB [S1, unofficial].
2.  **Fetch Beams:** Retrieve the PRP from the CFB as $n$ beams parallel to a primary axis. This takes $O(n)$ cycles [S2, book].
3.  **Store in 2DSB:** Store the slanted PRP into the 2DSB one beam at a time, from closest to furthest [S1, unofficial].
4.  **De-skew (Shear):** Shift each beam left or right within the 2DSB to align all viewing rays vertically (parallel to a 2D axis). This is performed using a barrel shifter (Conveyor) [S1, unofficial]. The 2DSB width ($2n-1$) accommodates the shear [S1, unofficial].
5.  **Retrieve Rays:** Retrieve vertical viewing rays from the 2DSB in parallel [S1, unofficial].
6.  **Transfer to RPT:** Transfer rays to the RPT. Shift rays during transfer to ensure the closest voxel appears at the desired position in the tree [S1, unofficial].
7.  **Process Rays:** Process rays in parallel through the RPT.
    *   *Standard:* Each VCU combines two voxels in 7 time units. The tree processes $\log n$ rays simultaneously in a pipeline fashion after initialization [S1, unofficial].
    *   *Neighborhood (Optional):* For algorithms requiring a 27-voxel neighborhood (central voxel + 26 neighbors), use multiple parallel 2DSBs. Extract the 27-voxel cube and transfer it to the RPT in parallel [S1, unofficial].
8.  **Pipeline:** Use a fourth plane in the 2DSB to load the next slanted PRP while three planes are used for extracting the 27-voxel cube for concurrent projection [S1, unofficial].

### Parameters and Typical Values
*   **CFB Size:** 128M voxels for a $512^3$ dataset [S1, unofficial].
*   **2DSB Width:** At least $2n-1$ columns [S1, unofficial].
*   **2DSB Modules:** $n$ modules [S1, unofficial].
*   **VCU Latency:** 7 time units [S1, unofficial].
*   **Intermodule Communication:** Each conveyor connects to neighbors by 256 lines (16 bits $\times$ 16 shift places) [S1, unofficial].

### Edge Cases and Pitfalls
*   **Implementation Scale:** A $512^3$ system requires 512 parallel processing units, 512 memory modules, ~18,000 lines of information operating in parallel, and up to 1,024 chips for memory alone [S1, unofficial].
*   **Routing Difficulties:** Module data lines are grouped by module, while conveyor data lines are grouped by bit position, creating complex routing requirements [S1, unofficial].
*   **Precision:** Not given in the sources.
*   **Boundaries:** The 2DSB width ($2n-1$) must be sufficient to handle the shear of the slanted PRP [S1, unofficial].

## Subtopics

### Extended Viewing Architecture for Arbitrary Projections
An architecture variant using three additional 2D buffers to accommodate arbitrary parallel and perspective projections [S2, book]. Unlike the rotation technique which distorts the CFB image, this method generates arbitrary projections without distortion but requires fetching a whole projection ray plane and rearranging it [S2, book]. It fetches $n$ beams in $O(n)$ cycles, stores them in a 2D temporary buffer, and rearranges them into 26-connected discrete ray representations using a $O(\log n)$ barrel shifter twice [S2, book]. Each ray is fed into the VMWB for selection of the first opaque voxel in $O(\log n)$ time [S2, book]. Total time is $O(n^2 \mod n \log n)$, allowing real-time arbitrary projection [S2, book].

## Operating characteristics
*   **Time Complexity:** $O(n^2 \log n)$ for arbitrary parallel projection, same as orthographic projection in the original Cube architecture, compared to conventional $O(n^3)$ [S1, unofficial].
*   **Memory Complexity:** High. Requires significant hardware resources (e.g., 1,024 chips for memory in a $512^3$ system) [S1, unofficial].
*   **Performance:** Enables interactive rendering rates for $512^3$ datasets [S1, unofficial].
*   **Strengths:** Supports real-time arbitrary parallel projection without image distortion; conflict-free access to beams and rays; pipeline-friendly.
*   **Limitations:** Extremely high hardware complexity and intermodule communication requirements; difficult routing; not suitable for perspective projection without more complex architecture [S1, unofficial].
*   **When to Use:** When real-time arbitrary parallel projection of high-resolution volumes is required and hardware resources are available.
*   **When Not to Use:** When hardware simplicity is preferred, or for perspective projection (requires more complex architecture) [S1, unofficial].

## Background
The Extended Cube Architecture was developed as an extension of the original Cube architecture, which was a special-purpose computer architecture for volume visualization supporting only orthographic projection [S1, unofficial]. The original Cube used a Cubic Frame Buffer (CFB) and beam projection mechanisms [S1, unofficial]. Arbitrary parallel projections were previously created by rotating the scene and viewing it through a principal orthographic direction, but this distorted the CFB image [S1, unofficial]. The extended architecture was presented to support real-time arbitrary viewing without distortion [S1, unofficial]. It builds on the Cube-3 Hybrid Ray-Casting method [3143-cube-3-hybrid-ray-casting.md].
