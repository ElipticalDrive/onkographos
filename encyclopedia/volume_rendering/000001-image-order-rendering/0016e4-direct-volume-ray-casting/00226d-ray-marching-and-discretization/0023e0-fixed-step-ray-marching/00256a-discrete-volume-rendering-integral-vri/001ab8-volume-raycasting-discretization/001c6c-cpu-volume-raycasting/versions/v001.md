# CPU Volume Raycasting

Also called: CPU Ray Casting, Interactive DVR System, Pure CPU direct volume rendering, Ray Casting with Trilinear Interpolation

## Overview
CPU Volume Raycasting is a direct volume rendering technique that computes the volume rendering integral by casting rays from the camera through each pixel into a voxel grid, accumulating color and opacity using front-to-back compositing [S2, unofficial]. It is distinguished from GPU-based raycasting by its explicit multithreaded pixel processing on the CPU and from sibling discretization methods by its specific implementation of trilinear interpolation and early ray termination [S1, S2, unofficial]. Unlike [Eye Align](849-eye-align.md) which optimizes sampling positions, or [Partial Pre-Integration](1148-partial-pre-integration.md) which approximates integration over steps, this method performs per-sample evaluation with standard compositing [S2, unofficial].

## How it works
### Inputs and Outputs
**Inputs:**
*   **Volume Data:** A 3D grid of scalar values (density/intensity).
*   **Transfer Functions:** Two 1D lookup tables mapping scalar values to RGBA color and opacity [S1, S2, unofficial].
*   **Camera Parameters:** Position, orientation (Euler angles or quaternion), and field of view [S1, S2, unofficial].
*   **Lighting:** Light direction and Phong lighting coefficients (ambient + diffuse) [S1, unofficial].
*   **Rendering Settings:** Step size, opacity multiplier, and alpha threshold for early termination [S2, unofficial].

**Outputs:**
*   **Image Buffer:** A 2D array of RGB pixels (8-bit per channel) [S2, unofficial].

### Data Structures
**Volume Data Layout:**
The volume is stored as a 3D array. Two distinct layouts are observed in source implementations:
1.  **Slice-based (S1):** `int[zSize][]` where `volumes[z]` is a 1D array of size `width * width`. Values are extracted from a 2D source image by masking the alpha channel: `0x00ffffff & imageInPixels[i + id_i]` [S1, unofficial].
2.  **Flat Row-Major (S2):** A `std::vector<uint8_t>` within a `Volume` struct containing `width`, `height`, and `depth`. Data is stored in row-major order: `data[x + y * width + z * width * height]` [S2, unofficial].

**Transfer Function Layout:**
Stored as two 1D integer arrays: `int[] transfer_rgb` and `int[] transfer_a`, typically loaded from 2D PNG images [S1, unofficial]. In the S2 implementation, a lookup function `transferFunction->lookup(val)` returns a struct with `.rgb` and `.a` fields [S2, unofficial].

**Ray Structure:**
A `Ray` struct contains `origin` (Vector3) and `direction` (Vector3), where Vector3 has fields `x`, `y`, `z` (float) [S2, unofficial].

**Pixel Buffer:**
A `std::vector<uint8_t>` with 3 components per pixel (RGB). The index for pixel `(i, j)` in an image of `width` is `(j * width + i) * 3` [S2, unofficial].

### Precomputation
**Rotation Matrix:**
Camera orientation is defined by Euler angles (roll, pitch, yaw). These are converted to a quaternion `q[4]` [S1, unofficial]:
$$
\begin{aligned}
c_1 &= \cos(\text{yaw}/2), & s_1 &= \sin(\text{yaw}/2) \\
c_2 &= \cos(\text{pitch}/2), & s_2 &= \sin(\text{pitch}/2) \\
c_3 &= \cos(\text{roll}/2), & s_3 &= \sin(\text{roll}/2)
\end{aligned}
$$
$$
\begin{aligned}
q[0] &= c_1 c_2 c_3 - s_1 s_2 s_3 \\
q[1] &= c_1 c_2 s_3 + s_1 s_2 c_3 \\
q[2] &= s_1 c_2 c_3 + c_1 s_2 s_3 \\
q[3] &= c_1 s_2 c_3 - s_1 c_2 s_3
\end{aligned}
$$
The quaternion is then converted to a 3x3 rotation matrix `M[3][3]` [S1, unofficial]:
$$
\begin{aligned}
M[0][0] &= 2(q_0^2 + q_1^2) - 1, & M[0][1] &= 2(q_1 q_2 - q_0 q_3), & M[0][2] &= 2(q_1 q_3 + q_0 q_2) \\
M[1][0] &= 2(q_1 q_2 + q_0 q_3), & M[1][1] &= 2(q_0^2 + q_2^2) - 1, & M[1][2] &= 2(q_2 q_3 - q_0 q_1) \\
M[2][0] &= 2(q_1 q_3 - q_0 q_2), & M[2][1] &= 2(q_2 q_3 + q_0 q_1), & M[2][2] &= 2(q_0^2 + q_3^2) - 1
\end{aligned}
$$

**Intensity Mapping (S1 Specific):**
Precomputed squared and cubed values for intensity mapping are stored in arrays `squared[256]` and `cubed[256]` [S1, unofficial]:
$$
\text{squared}[i] = \frac{(i/256.0)^2}{3.0}, \quad \text{cubed}[i] = (i/256.0)^3 \quad \text{for } i \in [0, 255]
$$

### Algorithm Steps
1.  **Initialization:**
    *   Split the image into tiles for multithreading. A common configuration is a 4x4 grid of tiles [S1, unofficial].
    *   For each tile `(a, b)`, define bounds: `startA = a * width / 4`, `endA = startA + width / 4`, `startB = b * height / 4`, `endB = startB + height / 4` [S1, unofficial].
    *   Initialize ray origin and direction for each pixel `(i, j)` within the tile [S2, unofficial].
    *   Check intersection with the volume's bounding sphere. If no intersection, skip the pixel [S2, unofficial].
    *   Set ray parameter `t` to the entry point `t0` [S2, unofficial].

2.  **Ray Marching Loop:**
    *   Iterate while `t < t1` (exit point) and `accumulated_alpha < 0.99f` (early termination threshold) [S2, unofficial].
    *   Calculate sample point `p = ray.origin + ray.direction * t` [S2, unofficial].
    *   **Sampling:**
        *   If using S1's nearest-neighbor approach: Map `p` to voxel coordinates, apply rotation matrix, and clamp to bounds. Retrieve value `v` from `volumes[z][x + y * width]` [S1, unofficial].
        *   If using S2's trilinear interpolation: Calculate fractional offsets `dx, dy, dz` from `p`. Retrieve the 8 corner voxel values `a` through `h` [S2, unofficial].
        *   Perform trilinear interpolation [S2, unofficial]:
            $$
            \begin{aligned}
            ab &= a(1-dx) + b(dx) \\
            cd &= c(1-dx) + d(dx) \\
            ef &= e(1-dx) + f(dx) \\
            gh &= g(1-dx) + h(dx) \\
            abc &= ab(1-dy) + cd(dy) \\
            def &= ef(1-dy) + gh(dy) \\
            val &= abc(1-dz) + def(dz)
            \end{aligned}
            $$
        *   Handle out-of-bounds coordinates by returning 0 (S2) or clamping indices (S1) [S1, S2, unofficial].
    *   **Transfer Function Lookup:**
        *   Map `val` to color `c` and opacity `a_{sample}` using the transfer function [S2, unofficial].
        *   Apply global opacity multiplier: `a_sample = a_sample * settings.opacity` [S2, unofficial].
    *   **Lighting (S1 Specific):**
        *   Compute gradient using central differences of neighboring voxels [S1, unofficial].
        *   Normalize gradient.
        *   Compute diffuse lighting: `diffuse = max(dot(normal, light_dir), 0)` [S1, unofficial].
        *   Combine ambient and diffuse to modulate color [S1, unofficial].
    *   **Compositing (Front-to-Back):**
        *   Update accumulated color `C_out` and alpha `alpha_out` [S2, unofficial]:
            $$
            \begin{aligned}
            C_{out} &= C_{in} + (1 - \alpha_{in}) \cdot a_{sample} \cdot c \\
            \alpha_{out} &= \alpha_{in} + (1 - \alpha_{in}) \cdot a_{sample}
            \end{aligned}
            $$
            where $C_{in}$ and $\alpha_{in}$ are the accumulated values before this step [S2, unofficial].
    *   **Step Advance:**
        *   Increment `t` by `settings.stepSize` [S2, unofficial].
        *   Note: S1 uses a fixed step of `0.75` in its loop `c += 0.75` [S1, unofficial]. S2 uses `settings.stepSize`, typically derived from `rayLength / (samplingRate * rayLength)` [S1, unofficial].

3.  **Finalization:**
    *   Clamp final color components to `[0, 1]` [S2, unofficial].
    *   Convert to 8-bit integers: `pixel[idx + k] = (uint8_t)(min(color[k], 1.0f) * 255)` for `k \in \{0, 1, 2\}` [S2, unofficial].

### Pseudocode
```python
def cpu_volume_ray_casting(volume, transfer_func, camera, light, width, height):
    # Initialize output buffer
    pixels = [0] * (width * height * 3)
    
    # Precompute rotation matrix from camera orientation (Euler to Quaternion to Matrix)
    rot_matrix = euler_to_rotation_matrix(camera.roll, camera.pitch, camera.yaw)
    
    # Multithreading setup: split image into 4x4 tiles
    tile_size_x = width // 4
    tile_size_y = height // 4
    
    threads = []
    for a in range(4):
        for b in range(4):
            start_x = a * tile_size_x
            end_x = start_x + tile_size_x
            start_y = b * tile_size_y
            end_y = start_y + tile_size_y
            
            # Create worker task
            task = lambda sx, ex, sy, ey: render_tile(
                volume, transfer_func, camera, light, 
                sx, ex, sy, ey, width, height, pixels, rot_matrix
            )
            threads.append(task(start_x, end_x, start_y, end_y))
            
    # Execute threads (conceptually parallel)
    for t in threads:
        t()
        
    return pixels

def render_tile(volume, transfer_func, camera, light, start_x, end_x, start_y, end_y, width, height, pixels, rot_matrix):
    for j in range(start_y, end_y):
        for i in range(start_x, end_x):
            # 1. Initialize Ray
            ray_origin, ray_direction = get_ray_for_pixel(i, j, camera, width, height)
            
            # 2. Intersect with Bounding Sphere
            t0, t1 = intersect_sphere(ray_origin, ray_direction, volume.bounding_sphere)
            if t0 is None:
                continue
                
            t = t0
            acc_color = [0.0, 0.0, 0.0]
            acc_alpha = 0.0
            
            # 3. Ray Marching
            while t < t1 and acc_alpha < 0.99:
                # Sample point
                p = ray_origin + ray_direction * t
                
                # 4. Trilinear Interpolation
                val = volume.sample_trilinear(p)
                
                # 5. Transfer Function Lookup
                sample = transfer_func.lookup(val)
                sample_color = sample.rgb
                sample_alpha = sample.a * camera.opacity_multiplier
                
                # 6. Lighting (Optional, based on S1)
                if use_lighting:
                    normal = volume.compute_gradient(p)
                    normal = normalize(normal)
                    diffuse = max(dot(normal, light.direction), 0.0)
                    sample_color = sample_color * (light.ambient + light.diffuse * diffuse)
                
                # 7. Front-to-Back Compositing
                weight = (1.0 - acc_alpha) * sample_alpha
                acc_color[0] += weight * sample_color[0]
                acc_color[1] += weight * sample_color[1]
                acc_color[2] += weight * sample_color[2]
                acc_alpha += weight
                
                # 8. Advance Step
                t += camera.step_size
                
            # 9. Write Pixel
            idx = (j * width + i) * 3
            pixels[idx] = int(min(acc_color[0], 1.0) * 255)
            pixels[idx+1] = int(min(acc_color[1], 1.0) * 255)
            pixels[idx+2] = int(min(acc_color[2], 1.0) * 255)

def volume_sample_trilinear(volume, p):
    # Get voxel coordinates
    x, y, z = p
    ix, iy, iz = floor(x), floor(y), floor(z)
    dx, dy, dz = x - ix, y - iy, z - iz
    
    # Handle boundaries: return 0 if out of bounds
    if not volume.is_inside(ix, iy, iz):
        return 0.0
        
    # Fetch 8 corners
    # Note: volume.data is row-major: x + y*w + z*w*h
    def get_val(x, y, z):
        if not volume.is_inside(x, y, z):
            return 0.0
        return volume.data[x + y * volume.width + z * volume.width * volume.height]
        
    a = get_val(ix, iy, iz)
    b = get_val(ix+1, iy, iz)
    c = get_val(ix, iy+1, iz)
    d = get_val(ix+1, iy+1, iz)
    e = get_val(ix, iy, iz+1)
    f = get_val(ix+1, iy, iz+1)
    g = get_val(ix, iy+1, iz+1)
    h = get_val(ix+1, iy+1, iz+1)
    
    # Interpolate
    ab = a * (1-dx) + b * dx
    cd = c * (1-dx) + d * dx
    ef = e * (1-dx) + f * dx
    gh = g * (1-dx) + h * dx
    
    abc = ab * (1-dy) + cd * dy
    def_val = ef * (1-dy) + gh * dy
    
    result = abc * (1-dz) + def_val * dz
    return result
```

### Parameters
*   **Step Size (`settings.stepSize`):** Distance between samples. In S1, calculated as `1.0` when `samplingRate=1` [S1, unofficial]. In S2, a configurable setting [S2, unofficial].
*   **Opacity Multiplier (`settings.opacity`):** Global scalar applied to sample opacity from the transfer function [S2, unofficial].
*   **Alpha Threshold:** Termination condition for early ray casting. Typically `0.99f` [S2, unofficial].
*   **Ray Length:** Diagonal length of the volume bounding box. In S1, approximated as `width * sqrt(2)` [S1, unofficial].

### Edge Cases and Pitfalls
*   **Volume Distortion:** If the source image is not square or height is not a multiple of width, the derived volume shape (`zSize = height / width`) may be distorted or truncated [S1, unofficial].
*   **Out-of-Bounds Sampling:** If coordinates fall outside the volume bounds, implementations vary: S1 clamps indices, while S2 returns 0 [S1, S2, unofficial]. This affects interpolation weights at edges [S2, unofficial].
*   **Aliasing:** S1 explicitly states "no pixel interpolation," relying on nearest-neighbor access which causes aliasing/blocky artifacts at oblique angles [S1, unofficial]. S2 uses trilinear interpolation to mitigate this [S2, unofficial].
*   **Color Overflow:** Final color values must be clamped to `[0, 1]` before 8-bit conversion to prevent overflow [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N \cdot M \cdot S)$, where $N$ is the number of pixels, $M$ is the number of samples per ray (determined by volume depth and step size), and $S$ is the cost of sampling/compositing per sample. Multithreading reduces wall-clock time proportionally to the number of cores [S1, unofficial].
*   **Memory Complexity:** $O(V)$ for the volume data, where $V$ is the number of voxels. Transfer functions and pixel buffers add $O(1)$ and $O(P)$ overhead respectively [S1, S2, unofficial].
*   **Performance:** Performance is limited by CPU memory bandwidth and cache efficiency due to the random access pattern of ray marching through the voxel grid [S1, S2, unofficial].
*   **Strengths:** Full control over rendering pipeline on CPU; supports complex transfer functions and lighting models without GPU shader constraints; suitable for interactive systems where GPU resources are unavailable or insufficient [S1, S2, unofficial].
*   **Limitations:** Slower than GPU-based raycasting for high-resolution volumes; prone to aliasing if step size is large or interpolation is poor; no built-in acceleration structures (like BVH) in the basic implementations described, leading to uniform sampling [S1, S2, unofficial].
*   **When to Use:** Interactive direct volume rendering on CPU-only systems; educational implementations; scenarios requiring custom lighting or transfer function logic not easily expressible in shaders [S1, S2, unofficial].
*   **When Not to Use:** High-performance real-time rendering of large volumes; scenes requiring complex light transport (e.g., full in-scattering) without approximation [S2, unofficial].

## Background
CPU Volume Raycasting originated as a foundational technique in Direct Volume Rendering (DVR), allowing visualization of 3D scalar fields on standard hardware before GPU compute shaders became prevalent. The specific implementations cited here represent independent open-source projects:
*   **Pure CPU Direct Volume Rendering:** Developed by Tomasz Hachaj, this implementation emphasizes a pure CPU approach with quaternion-based rotation and Phong lighting, explicitly avoiding 3rd party libraries and GPU acceleration [S1, unofficial].
*   **Interactive DVR System:** Developed by Manishaa1704, this system focuses on multithreaded pixel processing and trilinear interpolation for smoother visuals, serving as an educational example of CPU-based DVR [S2, unofficial].

These methods build upon the theoretical framework of the Volume Rendering Integral discretization [831-volume-raycasting-discretization.md], applying it via explicit ray marching loops on the CPU.
