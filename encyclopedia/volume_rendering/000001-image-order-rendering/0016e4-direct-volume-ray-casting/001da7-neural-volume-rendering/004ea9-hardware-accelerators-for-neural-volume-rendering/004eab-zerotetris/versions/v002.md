# ZeroTetris

Also called: Spacial Feature Similarity-based Sparse MLP Engine, Sparse MLP Engine for Neural Volume Rendering

## Overview
ZeroTetris is a hardware accelerator for Neural Volume Rendering (NVR) that exploits spatial feature similarity between adjacent sampling points to identify and bypass computation of zero activations in Multilayer Perceptrons (MLPs) [S1]. Unlike general sparse matrix multiplication accelerators that handle large matrices with complex encoding, ZeroTetris targets the specific sparsity patterns (60–90%) and small matrix dimensions inherent to NVR, using row-level sparsity skipping to enhance energy efficiency [S1]. It builds on the NVR pipeline defined in [Parent](13789-hardware-accelerators-for-neural-volume-rendering.md) by optimizing the MLP Evaluation step [S1].

## How it works
### Inputs and Outputs
*   **Inputs:** Spatial coordinates $x=(x,y,z)$, viewing directions $d=(\theta,\phi)$, and MLP weights $W$ [S1].
*   **Outputs:** RGB color $C=(r,g,b)$ and opacity $\sigma$ for each sampling point, which are integrated into the final pixel color [S1].

### Data Structures and Layout
The system consists of multiple ZeroTetris cores [S1]. A single core contains [S1]:
1.  **Sparsity Encoder (SE):** Encodes sparsity information from the ReLU-activated result [S1].
2.  **Processing Element (PE) Module:** Comprises four PE Tiles [S1]. Each Tile houses $16 \times b$ Processing Elements (PEs), where $b$ is the batch size [S1].
3.  **Partial Result Merger (PM):** Accumulates partial results from the PE Tiles [S1].
4.  **Memories:**
    *   **Input Memory (IMEM):** Stores activation data [S1].
    *   **L1 Weight Memory (L1 WMEM):** Private L1 cache per core for weight data [S1].
    *   **Activation Memory (AMEM):** Shared memory for caching partial results when output dimensions exceed 64 [S1]. Supports double buffering [S1].
    *   **L2 Weight Memory (L2 WMEM):** Shared L2 cache for all weight data to mitigate access conflicts [S1].

**Sparsity Vector ($n_{zrow}$):**
Each activation row is encoded into a binary vector $n_{zrow}$ [S1].
*   $n_{zrow}[i] = 1$: The $i$-th row contains at least one non-zero (nz) value [S1].
*   $n_{zrow}[i] = 0$: The $i$-th row consists entirely of zeros [S1].
This vector serves as the sparsity mask for skipping weight fetches and computations [S1].

### Algorithm Steps
The NVR pipeline and ZeroTetris optimization proceed as follows [S1]:

1.  **Encoding:** Spatial coordinates $x$ and viewing directions $d$ are encoded into a feature vector using fixed (e.g., Fourier) or trainable (hash) functions [S1].
2.  **Sparsity Detection:** The SE analyzes the ReLU-activated activation vector [S1]. It generates $n_{zrow}$ by identifying rows with entirely zero values [S1].
3.  **Prefetching and Scheduling:**
    *   The L1 cache invalidates the current cache line [S1].
    *   It calculates the next prefetch address based on $n_{zrow}$ [S1].
    *   It calculates `required_time` by counting the number of 1s in $n_{zrow}$ between the current address and the prefetch address [S1].
    *   It sends a prefetch request to the L2 cache [S1]. If $n_{zrow}$ is not received, the L1 cache treats the data as entirely zeros and clears superfluous requests [S1].
4.  **Weight Selection:** L1 WMEM selects relevant weight data based on $n_{zrow}$ [S1]. Columns corresponding to rows where $n_{zrow}=0$ are skipped, reducing memory access [S1].
5.  **Multiplication Round:**
    *   **Initialization:** A `START` signal is issued [S1]. The bias is written to the Temporary Result Register (T-Reg) [S1].
    *   **Computation:** Each cycle, the PE module receives $b$ activation data items and 64 weight data items (distributed as 16 per Tile) [S1]. Each PE computes the product and accumulates it in T-Reg [S1].
    *   **Completion:** A `DONE` signal activates [S1]. The result is stored in the Partial Result Register (P-Reg) [S1].
6.  **Result Merging (Condition Handling):**
    Let $N$ be the number of weight rows (output dimension) [S1].
    *   **Condition 1 ($N < 64$):** The four PE Tiles produce partial results $P_0, P_1, P_2, P_3$ [S1]. The PM uses a two-level adder tree to accumulate them:
        *   Level 1: $P'_{01} = P_0 + P_1$, $P'_{23} = P_2 + P_3$ [S1].
        *   Level 2: $P''_{0123} = P'_{01} + P'_{23}$ [S1].
        *   The final result is output directly [S1].
    *   **Condition 2 ($N = 64$):** The four PE Tiles produce the final result directly [S1]. No PM processing is required [S1].
    *   **Condition 3 ($N > 64$):** The PE Tiles produce partial results that are cached in AMEM [S1]. Multiple rounds are required [S1]. The results are retrieved from AMEM for the next layer's computation [S1]. AMEM uses double buffering to ensure sustainable calculation [S1].

### Pseudocode
The following pseudocode describes the core multiplication round and sparsity handling. It assumes standard vector/matrix operations.

```python
def zerotetris_core_multiply(activations, weights, n_zrow, batch_size, output_dim):
    """
    Simulates one multiplication round in a ZeroTetris core.
    
    Args:
        activations: List of activation vectors for the batch, shape (batch_size, input_dim).
        weights: Weight matrix for the layer, shape (output_dim, input_dim).
        n_zrow: Binary vector indicating non-zero rows (1) or zero rows (0), shape (output_dim,).
        batch_size: Number of activations processed per cycle (b).
        output_dim: Number of rows in the weight matrix (N).
        
    Returns:
        result: The computed output vector.
    """
    # 1. Prefetch & Scheduling (Algorithm 1)
    current_addr = 0
    L1_cache = {}
    L2_cache = {}
    while current_addr < len(weights):
        L1_cache.invalidate(current_addr)
        next_prefetch_addr = n_zrow.next_prefetch_addr(current_addr)
        required_time = count_ones(n_zrow, current_addr, next_prefetch_addr)
        L1_cache.send_prefetch(next_prefetch_addr, required_time)
        if n_zrow.received():
            L1_cache.clear_loaded_lines()
            L2_cache.clear_requests()
        current_addr = next_prefetch_addr

    # 2. Determine Data Flow Path based on Output Dimension
    if output_dim < 64:
        # Condition 1: Need Partial Result Merger (PM)
        tile_results = []
        for tile_id in range(4):
            # Each Tile handles 16 rows of weights
            tile_weights = select_weights(weights, tile_id * 16, 16, n_zrow)
            tile_activations = activations
            # Compute partial result for this tile
            partial_result = compute_tile(tile_weights, tile_activations, batch_size)
            tile_results.append(partial_result)
        # Merge partial results using two-level adder tree
        P0, P1, P2, P3 = tile_results
        P_prime_01 = P0 + P1
        P_prime_23 = P2 + P3
        result = P_prime_01 + P_prime_23
        
    elif output_dim == 64:
        # Condition 2: Direct Result
        tile_results = []
        for tile_id in range(4):
            tile_weights = select_weights(weights, tile_id * 16, 16, n_zrow)
            tile_activations = activations
            partial_result = compute_tile(tile_weights, tile_activations, batch_size)
            tile_results.append(partial_result)
        # Concatenate tile outputs to form final 64-dim result
        result = concatenate(tile_results)
        
    else:
        # Condition 3: Output Dim > 64
        # Cache partial results in AMEM
        partial_results = []
        rounds = (output_dim + 63) // 64
        for r in range(rounds):
            chunk_weights = select_weights(weights, r * 64, 64, n_zrow)
            chunk_activations = activations
            partial_result = compute_tile(chunk_weights, chunk_activations, batch_size)
            partial_results.append(partial_result)
            # AMEM double buffering handles storage/retrieval transparently
        result = concatenate(partial_results)
        
    return result

def compute_tile(tile_weights, activations, batch_size):
    """
    Computes the dot product for a single PE Tile.
    Tile contains 16 PEs. Each PE has its own T-Reg.
    """
    # Initialize 16 T-Regs (one per PE) with bias
    T_Regs = [0.0] * 16
    # Hardware accumulates over cycles; abstracted here as direct accumulation
    for pe_id in range(16):
        for k in range(len(activations[0])):
            for b in range(batch_size):
                T_Regs[pe_id] += activations[b][k] * tile_weights[pe_id][k]
    # DONE signal activates, results stored in P-Reg
    P_Reg_Tile = T_Regs
    return P_Reg_Tile

def select_weights(weights, start_row, num_rows, n_zrow):
    """
    Selects weights for a specific tile, skipping rows where n_zrow is 0.
    """
    selected_weights = []
    for i in range(start_row, start_row + num_rows):
        if n_zrow[i] == 1:
            selected_weights.append(weights[i])
    return selected_weights

def count_ones(n_zrow, start_idx, end_idx):
    """Counts the number of 1s in n_zrow between start_idx and end_idx."""
    return sum(1 for i in range(start_idx, end_idx) if n_zrow[i] == 1)
```

### Parameters and Typical Values
*   **Batch Size ($b$):** 1, 4, 16, 64. Typical tested value: 16 [S1].
*   **Output Dimensions:** 16, 32, 64, 128, 192, 256 [S1].
*   **PE Tile Size:** 16 PEs per Tile [S1].
*   **Weight Data per Cycle:** 64 items (16 per Tile) [S1].
*   **Technology:** 28nm CMOS [S1].
*   **Frequency:** 200 MHz [S1].
*   **Area:** 3.18 mm² per core [S1].
*   **Power:** 123.7 mW per core [S1].

### Edge Cases and Pitfalls
*   **Batch Size Trade-off:** Smaller batch sizes increase sparsity utilization (finer resolution for zero detection) but lower weight reuse rates, potentially reducing throughput [S1].
*   **Missing $n_{zrow}$:** If $n_{zrow}$ is not received during prefetching, the L1 cache treats the data as entirely zeros, which may lead to incorrect results if the assumption is violated [S1].
*   **Precision:** The source does not specify floating-point precision (e.g., FP16, FP32) [G: Standard NVR accelerators often use FP16 or FP32; implementers should verify target precision].

## Operating characteristics
*   **Time Complexity:** Not explicitly given in terms of Big-O, but speedup is measured relative to a dense accelerator [S1].
*   **Memory Complexity:** Not explicitly given [S1]. Uses L1/L2 cache hierarchy and AMEM [S1].
*   **Measured Performance:**
    *   **Sparsity Utilization:** 83.0% for NeRF, 76.5% for Instant-NGP [S1].
    *   **Speedup:** 3.1x for NeRF, 2.3x for Instant-NGP compared to a dense accelerator [S1].
    *   **Reconstruction Quality:** PSNR of 42.59 compared to GPU ground truth [S1].
*   **Strengths:** Superior area and power efficiency compared to NeuRex, OuterSPACE, and SIGMA due to lower overhead and effective bypassing of sparse patterns [S1].
*   **Limitations:** Lower zero utilization ratio compared to OuterSPACE and SIGMA (which achieve ~100%), but compensates with lower overhead [S1].
*   **When to Use:** Ideal for NVR applications (NeRF, Instant-NGP) where spatial similarity creates high row-level sparsity in MLP activations and energy efficiency is critical [S1].
*   **When Not to Use:** Not suitable for general-purpose sparse matrix multiplication with large matrices or non-NVR workloads where weight sparsity (rather than activation sparsity) is the primary target [S1].

## Background
ZeroTetris was proposed by H. Wan, L. Ma, A. Li, P. Zhou, J. Yu, and X. Lou in 2024 [S1]. It addresses the computational challenges of Neural Volume Rendering (NVR), which has grown significantly in recent years [S1]. Existing dedicated accelerators for neural networks struggle with NVR's unique requirements, such as small matrix dimensions and high activation sparsity (60-90%) derived from spatial feature similarity [S1]. The design is implemented in 28nm CMOS technology [S1].
