# Volume Ray-Casting on Graphics Hardware

Also called: Stream model for volumetric ray-casting

## Overview
This method implements direct volume ray casting on programmable graphics hardware (specifically DirectX 9-level architectures like the ATI 9700) using a multi-pass stream model [S1, unofficial]. It solves the problem of integrating early ray termination and empty-space skipping into 3D texture-based rendering by exploiting intrinsic parallelism and efficient communication between rendering passes [S1, unofficial]. It is distinguished from single-pass hardware approaches by its use of a feedback loop where the render target of one pass serves as the input texture for the next, allowing the accumulation state to be checked and modified between steps [S1, unofficial].

## How it works
The method uses a multi-pass approach where ray traversal is split across several rendering passes. The core mechanism relies on the "early z-test" to discard fragments that have already met the termination criteria, thereby skipping unnecessary shader execution for subsequent passes [S1, unofficial].

### Inputs and Outputs
*   **Inputs:**
    *   Volumetric scalar field data (3D texture).
    *   Ray direction vectors for each pixel, stored in two 2D textures (one for each axis component) [S1, unofficial].
    *   Accumulated color and opacity values, stored in a 2D texture render target [S1, unofficial].
*   **Outputs:**
    *   Final rendered image (accumulated color and opacity).
    *   If an iso-surface is hit, the local texture coordinates of the intersection point are written to a 2D texture for a final shading pass [S1, unofficial].

### Data Structures
*   **Ray Direction Textures:** Two 2D textures storing the direction of the ray through each pixel in local texture coordinates. These are computed prior to ray traversal and remain constant across passes [S1, unofficial].
*   **Accumulation Texture:** A 2D texture render target (aligned with the viewport) storing the accumulated color and opacity values. Floating-point textures are used to support negative values if required [S1, unofficial].
*   **Z-Buffer:** Used for the early z-test. The fragment shader can replace the depth value of a fragment using the "depth replace" feature [S1, unofficial].

### Steps
1.  **Initialization:** Compute the ray direction for each pixel in local texture coordinates and store them in two 2D textures. Initialize the accumulation texture with zero color and opacity [S1, unofficial].
2.  **Main Pass (Ray Marching):**
    *   Render a full-screen quad.
    *   In the fragment shader, fetch the accumulated color and opacity from the accumulation texture.
    *   Fetch the ray direction from the direction textures.
    *   Perform a fixed number of ray steps (or a single step per pass, depending on implementation details not fully specified, but the text implies a "fixed number of rendering steps" distributed across passes) [S1, unofficial].
    *   Sample the volume data using trilinear interpolation.
    *   Apply the transfer function to determine opacity $\alpha$ and color $C$.
    *   Update the accumulated color $C'$ and opacity $\alpha'$ using the front-to-back compositing equations:
        $$
        C'_{i} = C'_{i-1} + (1 - \alpha'_{i-1}) \alpha_i C_i
        $$
        $$
        \alpha'_{i} = \alpha'_{i-1} + (1 - \alpha'_{i-1}) \alpha_i
        $$
    *   Write the updated $C'$ and $\alpha'$ to the accumulation texture [S1, unofficial].
3.  **Termination Test Pass:**
    *   Render a full-screen quad.
    *   In the fragment shader, fetch the accumulated opacity $\alpha'$ from the accumulation texture.
    *   Test if $\alpha'$ exceeds a specified threshold (e.g., 0.95 or 1.0) or if an iso-surface has been hit.
    *   If the test succeeds, set the fragment's depth value to the maximum possible value (using depth replace).
    *   If the test fails, set the fragment's depth value to zero [S1, unofficial].
4.  **Early Z-Test Filtering:**
    *   Set the depth test function to `GREATER`.
    *   Because fragments that met the termination criteria have their depth set to the maximum, they will fail the `GREATER` test in subsequent passes and be discarded. Fragments that have not met the criteria have depth zero and will pass the test, allowing the shader to execute [S1, unofficial].
5.  **Repeat:** Steps 2-4 are repeated for the required number of passes.
6.  **Final Pass (Optional):** If an iso-surface was hit, use the stored intersection coordinates to perform gradient-based shading and lighting calculations [S1, unofficial].

### Parameters
*   **Threshold:** The opacity value at which a ray is considered terminated. Typical values are 0.95 or 1.0 [S1, unofficial].
*   **Hardware:** ATI 9700 graphics card [S1, unofficial].
*   **API:** Pixel Shader 2.0 API (DirectX 9-level) [S1, unofficial].
*   **Texture Limits:** Up to 8 different textures can be accessed, but dependent texture fetches are limited on the ATI architecture [S1, unofficial].

### Edge Cases and Pitfalls
*   **Dependent Texture Fetches:** The ATI 9700 has a limited number of dependent texture fetches. The algorithm must be designed to minimize these to avoid performance degradation or incorrect behavior [S1, unofficial].
*   **Floating Point Precision:** Floating-point textures are required to store negative values if the volume data or intermediate calculations produce them [S1, unofficial].
*   **Z-Test Logic:** The correctness of the early termination relies on the precise setting of the depth test to `GREATER` and the correct use of depth replace. If the depth test is not set correctly, fragments will not be discarded, leading to incorrect accumulation [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The method reduces the number of fragment shader executions by discarding fragments that have reached the termination threshold. This results in performance gains of up to a factor of 3 for typical renditions of volumetric data sets on the ATI 9700 [S1, unofficial].
*   **Memory Complexity:** Requires additional 2D textures for storing ray directions and the accumulation buffer. The use of texture render targets allows communication between passes without CPU-GPU synchronization overhead [S1, unofficial].
*   **Strengths:** Effective integration of early ray termination and empty-space skipping on hardware that supports texture render targets and depth replace. Exploits intrinsic parallelism of fragment processors [S1, unofficial].
*   **Limitations:** Relies on specific hardware features (Pixel Shader 2.0, depth replace, texture render targets) that may not be available on all modern GPUs. The multi-pass nature can introduce overhead if the number of passes is large or if the termination threshold is not reached frequently [S1, unofficial].
*   **When to use:** When targeting older DirectX 9-level hardware where single-pass ray casting is too slow and hardware supports texture render targets and depth replace. Not suitable for modern architectures that support more advanced ray tracing or single-pass volume rendering techniques [S1, unofficial].

## Background
The method was proposed in a 2003 paper titled "Acceleration Techniques for GPU-based Volume Rendering" [S1, unofficial]. It was developed to address the challenge of achieving real-time volume rendering for large scalar fields on general-purpose CPUs, which were insufficient for the task. The work leveraged the emerging programmable graphics hardware (specifically the ATI 9700 and Pixel Shader 2.0) to offload the computation to the GPU. The "stream model" concept was introduced to manage the state of ray casting across multiple rendering passes, enabling efficient communication between passes via texture render targets [S1, unofficial].
