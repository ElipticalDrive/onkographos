# Volume Ray-Casting on Graphics Hardware

Also called: Stream model for volumetric ray-casting

## Overview
This method implements direct volume ray casting on programmable graphics hardware (specifically DirectX 9-level architectures like the ATI 9700) using a multi-pass stream model [S1, unofficial]. It solves the performance bottleneck of CPU-based ray casting by exploiting the intrinsic parallelism of fragment processors and efficient inter-pass communication via texture render targets [S1, unofficial]. Unlike single-pass rasterization techniques, this approach explicitly manages ray traversal state across multiple rendering passes, enabling hardware-accelerated early ray termination and empty-space skipping through the early z-test mechanism [S1, unofficial]. It differs from [Direct volume rendering](1184-direct-volume-rendering.md) by decoupling the ray integration steps into discrete, communicable passes rather than attempting to compute the full integral in a single shader invocation.

## How it works
The method relies on a multi-pass rendering pipeline where the output of one pass serves as the input texture for the next. It utilizes specific hardware features available in Pixel Shader 2.0 APIs: per-fragment texture fetches (up to 8 textures, with limited dependent fetches), texture render targets (allowing rendering to 2D textures aligned with the viewport), texture coordinate generation, per-fragment arithmetic, and depth replace capabilities [S1, unofficial].

### Inputs and Outputs
- **Input Volume:** A 3D scalar texture representing the volumetric data.
- **Ray Direction Textures:** Two 2D textures storing the pre-computed ray direction vectors in local texture coordinates for each pixel [S1, unofficial].
- **Accumulation Textures:** 2D textures (typically floating-point) storing the accumulated color and opacity from previous passes [S1, unofficial].
- **Output:** The final rendered image stored in the frame buffer or a target texture.

### Data Structures
1.  **Ray Direction Textures ($T_{dir}$):** Two 2D textures, one for the x-component and one for the y-component of the ray direction vector in texture space. These are computed prior to ray traversal for each pixel [S1, unofficial].
2.  **Accumulation Buffer ($T_{acc}$):** A 2D floating-point texture storing the accumulated color $C'$ and opacity $\alpha'$ for each pixel. The layout typically interleaves or separates these values, allowing access in subsequent passes [S1, unofficial].
3.  **Z-Buffer:** Used for the early z-test. The depth value is manipulated to control fragment processing [S1, unofficial].

### Algorithm Steps
1.  **Pre-computation:** For each pixel, compute the ray direction in local texture coordinates. Store these directions in two 2D textures ($T_{dir}$) [S1, unofficial].
2.  **Initialization:** Initialize the accumulation texture $T_{acc}$ with zero color and zero opacity. Set the z-buffer to allow processing.
3.  **Main Passes (Ray Traversal):** Perform a fixed number of rendering passes. In each pass:
    a.  Bind the current accumulation texture $T_{acc}$ and ray direction textures $T_{dir}$ as inputs.
    b.  Execute a fragment shader that performs one step of ray integration:
        -   Sample the volume data at the current ray position.
        -   Apply the transfer function to obtain color $C_i$ and opacity $\alpha_i$.
        -   Update accumulated color and opacity using the front-to-back compositing equations:
            $$ C'_{new} = C'_{old} + (1 - \alpha'_{old}) \alpha_i C_i $$
            $$ \alpha'_{new} = \alpha'_{old} + (1 - \alpha'_{old}) \alpha_i $$
        -   Advance the ray position using the pre-computed direction.
    c.  Write the updated $C'_{new}$ and $\alpha'_{new}$ to the accumulation texture $T_{acc}$ for the next pass [S1, unofficial].
4.  **Termination Check Pass:** Between main passes, execute an additional pass to test for early termination:
    a.  Read the accumulated opacity $\alpha'$ from the accumulation texture.
    b.  Check if $\alpha'$ exceeds a specified threshold or if an iso-surface has been hit (if applicable).
    c.  If the condition is met, set the fragment's depth value to the maximum possible z-value using the depth replace feature.
    d.  If the condition is not met, set the depth value to zero (or the current ray depth) [S1, unofficial].
5.  **Early Z-Test Filtering:** Configure the graphics hardware to use a GREATER depth test. Because fragments that have reached the opacity threshold have their depth set to the maximum, they will fail the GREATER test in subsequent passes and be discarded, effectively skipping empty space and terminating rays early [S1, unofficial].
6.  **Final Pass (Optional):** If an iso-surface was hit, a final pass may be executed to restrict gradient and shading computations to the intersection points identified in previous steps [S1, unofficial].

### Pseudocode
```python
# Pre-computation
for each pixel (x, y):
    ray_dir = compute_ray_direction(x, y, camera_params)
    dir_texture_x[x, y] = ray_dir.x
    dir_texture_y[x, y] = ray_dir.y

# Initialization
accum_texture = zeros(width, height, 4) # RGBA, initialized to 0

# Main Loop
for pass_index in range(num_passes):
    # Bind textures
    bind_texture(accum_texture, unit=0)
    bind_texture(dir_texture_x, unit=1)
    bind_texture(dir_texture_y, unit=2)
    bind_volume(volume_data, unit=3)
    
    # Set render target to a temporary accumulation texture
    bind_render_target(temp_accum_texture)
    
    # Execute fragment shader for one ray step
    # Shader logic:
    # 1. Read current C', alpha' from unit 0
    # 2. Read ray direction from unit 1, 2
    # 3. Compute sample position p = current_pos + direction * step_size
    # 4. Sample volume at p to get scalar value d
    # 5. Apply transfer function T(d) to get C_i, alpha_i
    # 6. Update C', alpha' using compositing equations
    # 7. Write new C', alpha' to temp_accum_texture
    
    render_pass()
    
    # Swap accumulation textures
    swap(accum_texture, temp_accum_texture)
    
    # Termination Check Pass
    bind_texture(accum_texture, unit=0)
    bind_render_target(z_buffer_control_texture)
    
    # Execute termination shader
    # Shader logic:
    # 1. Read alpha' from unit 0
    # 2. If alpha' > threshold OR iso-surface hit:
    #      depth = MAX_DEPTH
    #    Else:
    #      depth = 0.0
    # 3. Write depth to z-buffer (using depth replace)
    render_pass()
    
    # Configure depth test for next main passes
    set_depth_test(GREATER)
    # Fragments with MAX_DEPTH will fail the GREATER test and be discarded

# Final Output
bind_render_target(framebuffer)
bind_texture(accum_texture, unit=0)
render_pass() # Final copy/compositing if needed
```

### Parameters and Edge Cases
-   **Opacity Threshold:** The threshold for early termination must be chosen carefully. Too high, and visual artifacts appear; too low, and performance gains are reduced [S1, unofficial].
-   **Floating Point Textures:** Essential for storing negative values and high dynamic range accumulated data. Not all hardware supports this, but it is required for this method on the target architecture [S1, unofficial].
-   **Dependent Texture Fetches:** Limited on ATI hardware. The method minimizes dependent fetches by pre-computing ray directions and using fixed-step traversal [S1, unofficial].
-   **Iso-surface Hit:** If an iso-surface is hit, the coordinates are written to a 2D texture. This requires additional logic to detect the hit and store the coordinates, which may complicate the simple opacity-threshold termination [S1, unofficial].

## Operating characteristics
-   **Performance:** Demonstrates performance gains up to a factor of 3 for typical volumetric data sets on the ATI 9700 graphics card compared to non-accelerated or less optimized methods [S1, unofficial].
-   **Complexity:** The method introduces overhead due to multiple rendering passes and texture swaps. The number of passes is fixed, which may lead to unnecessary computation for rays that terminate early if the threshold is not optimally set.
-   **Hardware Dependency:** Strictly dependent on hardware features available in Pixel Shader 2.0 era GPUs, specifically texture render targets, depth replace, and early z-test support [S1, unofficial].
-   **Scalability:** Scales with the number of fragments processed in parallel. The fixed number of passes limits the maximum ray length that can be accurately represented without adaptive stepping, which is not explicitly detailed in the source [S1, unofficial].

## Background
This method was proposed in 2003 by researchers at the Technical University of Munich (TUM) as part of their work on acceleration techniques for GPU-based volume rendering [S1, unofficial]. It was designed to leverage the emerging programmable graphics hardware (DirectX 9 level) to achieve real-time or interactive rendering of large volumetric datasets, which was previously challenging for CPUs [S1, unofficial]. The stream model approach was a novel contribution at the time, exploiting the parallelism of fragment processors and the communication capabilities of texture render targets [S1, unofficial].
