# Parallel Domain-Decomposed Ray Casting

Also called: 3D Grid Process Distribution, MPI Ray Casting

## Overview
Parallel Domain-Decomposed Ray Casting is a distributed-memory parallelization strategy for direct volume ray casting that distributes a 3D volume dataset across a 3D grid of MPI processes [S1, unofficial]. Each process independently performs front-to-back ray casting on its assigned sub-volume chunk, after which intermediate results are gathered and composited by a subset of ranks to produce the final image [S1, unofficial]. It sets itself apart from sibling methods by explicitly partitioning the spatial data domain across networked nodes rather than partitioning the image plane or using shared-memory threading, making it suitable for large datasets exceeding single-node memory [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D volume dataset stored as a raw binary file of `float32` values, a transfer function file for opacity, a transfer function file for color, and MPI process grid dimensions $(p_x, p_y, p_z)$ [S1, unofficial].
*   **Output:** A composited 2D image saved as a PNG file [S1, unofficial].

**Data Structures:**
1.  **Volume Data:** A 3D NumPy array of shape $(z_{Total}, y_{Total}, x_{Total})$ with `dtype=float32` [S1, unofficial].
2.  **Opacity Transfer Function (`opacityData`):** A 2D array with 2 rows and `dtype=float32` [S1, unofficial].
    *   Row 1: Scalar value positions (input to TF).
    *   Row 2: Corresponding opacity values (output of TF) [S1, unofficial].
3.  **Color Transfer Function (`colorData`):** A 2D array with 5 rows and `dtype=float32` [S1, unofficial].
    *   Row 1: Scalar value positions.
    *   Row 2: Red channel values.
    *   Row 3: Green channel values.
    *   Row 4: Blue channel values [S1, unofficial].

**Parameters:**
*   $p_x, p_y, p_z$: Integer dimensions of the 3D process grid. Typical value: $2, 2, 2$ [S1, unofficial].
*   $step\_size$: Fixed sampling interval along the ray direction. Typical value: $0.5$ [S1, unofficial].

**Algorithm Steps:**
1.  **Initialization:** Rank 0 loads the volume data, opacity transfer function, and color transfer function from disk [S1, unofficial].
2.  **Domain Decomposition:** Rank 0 calculates segment sizes for each dimension:
    $$ x_{seg} = \lfloor x_{Total} / p_x \rfloor, \quad y_{seg} = \lfloor y_{Total} / p_y \rfloor, \quad z_{seg} = \lfloor z_{Total} / p_z \rfloor $$
    Rank 0 iterates over the 3D process grid indices $(k, j, i)$ where $k \in [0, p_z), j \in [0, p_y), i \in [0, p_x)$ [S1, unofficial].
3.  **Data Distribution:** Rank 0 sends each sub-volume chunk `data[z_index:z_next, y_index:y_next, x_index:x_next]` along with `opacityData`, `colorData`, and grid dimensions to the corresponding MPI rank using `comm.send()` [S1, unofficial]. Boundary conditions apply: if $i = p_x - 1$, $x_{next} = x_{Total}$; similarly for $j$ and $k$ [S1, unofficial].
4.  **Local Ray Casting:** Each rank receives its data chunk via `comm.recv(source=0)` [S1, unofficial]. Each rank then executes the ray casting kernel on its local data [S1, unofficial].
    *   The ray casting kernel iterates over the local volume dimensions.
    *   For each sample, it performs linear interpolation on the transfer functions to determine color and opacity [S1, unofficial].
    *   It accumulates color and opacity using front-to-back compositing [S1, unofficial].
    *   The kernel outputs a local `colorMesh` and `opacityMesh` [S1, unofficial].
5.  **Result Aggregation:**
    *   Ranks with index $rank \ge p_x p_y$ send their `colorMesh` and `opacityMesh` to a "surface process" with index $surfaceProcess = rank \pmod{p_x p_y}$ [S1, unofficial].
    *   Ranks with index $rank < p_x p_y$ receive meshes from ranks corresponding to their $z$-layer offsets. Specifically, rank $r < p_x p_y$ receives from destPrc $(c \cdot p_x p_y) + r$ for $c \in [1, p_z)$ [S1, unofficial].
6.  **Final Composition:** Rank 0 gathers all composited meshes, concatenates them spatially according to the $p_x/p_y$ structure, converts the result to `uint8`, and saves it as a PNG image [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Boundary Handling:** The last segment in each dimension must extend to the total dimension size to avoid data loss [S1, unofficial].
*   **Process Count:** The total number of MPI processes must equal $p_x \times p_y \times p_z$ [S1, unofficial].
*   **Precision:** Data is stored as `float32`; transfer function interpolation uses linear interpolation which may introduce artifacts if the TF is sparse [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N/P)$ for ray casting, where $N$ is the total number of samples and $P$ is the number of processes, plus communication overhead $O(N^{2/3})$ for gathering results [S1, unofficial].
*   **Memory Complexity:** $O(V/P)$ per process, where $V$ is the volume size, allowing rendering of datasets larger than single-node memory [S1, unofficial].
*   **Performance:** Scales with the number of processes $p_x p_y p_z$ [S1, unofficial].
*   **Strengths:** Enables rendering of very large volumes on clusters [S1, unofficial].
*   **Limitations:** Communication overhead can become significant if the volume chunks are small or the network is slow [S1, unofficial].
