# Parallel Domain-Decomposed Ray Casting

Also called: 3D Grid Process Distribution, MPI Ray Casting

## Overview
Parallel Domain-Decomposed Ray Casting is a distributed-memory parallelization strategy for direct volume ray casting that partitions the 3D volume dataset into a 3D grid of sub-volumes, assigning each sub-volume to a separate MPI process [S1, unofficial]. Each process independently performs front-to-back ray casting on its local chunk and composites the resulting color and opacity meshes, which are then gathered and concatenated by a root process to form the final image [S1, unofficial]. It differs from sibling methods like [Hardware-Accelerated Volume Rendering](5616-hardware-accelerated-volume-rendering.md) by relying on CPU-based MPI communication and explicit domain decomposition rather than GPU texture memory and hardware ray traversal, making it suitable for large datasets that exceed single-node memory constraints [S1, unofficial].

## How it works
**Inputs and Outputs:**
- **Input:** A 3D scalar volume dataset (typically `.raw` format), transfer function files for opacity and color, and MPI process grid dimensions $(p_x, p_y, p_z)$.
- **Output:** A composited 2D image (e.g., PNG) representing the volume rendering.

**Data Structures:**
1.  **Volume Data:** A 3D NumPy array of shape $(z_{Total}, y_{Total}, x_{Total})$ with `dtype=float32` [S1, unofficial]. Distributed as slices: `data[z_index:z_next, y_index:y_next, x_index:x_next]` [S1, unofficial].
2.  **Opacity Transfer Function:** A 2D array with 2 rows and $N$ columns. Row 1 contains scalar positions; Row 2 contains corresponding opacity values [S1, unofficial].
3.  **Color Transfer Function:** A 2D array with 5 rows and $M$ columns. Row 1 contains scalar positions; Rows 2, 3, and 4 contain R, G, B color values respectively [S1, unofficial].

**Algorithm Steps:**
1.  **Initialization:** The MPI communicator is established. Rank 0 loads the volume data and transfer functions. The total number of processes is $S = p_x \times p_y \times p_z$ [S1, unofficial].
2.  **Domain Decomposition:** Rank 0 calculates segment sizes:
    $$
    x_{seg} = \lfloor x_{Total} / p_x \rfloor, \quad y_{seg} = \lfloor y_{Total} / p_y \rfloor, \quad z_{seg} = \lfloor z_{Total} / p_z \rfloor
    $$
    Boundary adjustments are made for the last segments to cover the full volume [S1, unofficial].
3.  **Data Distribution:** Rank 0 iterates over the 3D process grid $(k, j, i)$ for $k \in [0, p_z), j \in [0, p_y), i \in [0, p_x)$. It sends the corresponding volume slice, along with the opacity and color transfer functions and grid dimensions, to the process with rank $count = k \cdot p_x \cdot p_y + j \cdot p_x + i$ using `comm.send()` [S1, unofficial].
4.  **Local Ray Casting:** Each rank receives its data and executes the ray casting kernel [S1, unofficial].
    -   **Ray Generation:** Rays are generated for the image pixels. The step size $\Delta t$ is a parameter (typical value: 0.5) [S1, unofficial].
    -   **Sampling:** For each sample point, the scalar value is retrieved from the local volume chunk.
    -   **Classification:** The scalar value is mapped to color $(C_r, C_g, C_b)$ and opacity $\alpha$ using linear interpolation on the transfer function arrays [S1, unofficial].
    -   **Compositing:** Front-to-back compositing is performed using the standard over operator:
        $$
        C'_{i} = C'_{i-1} + (1 - \alpha'_{i-1}) \alpha_i C_i
        $$
        $$
        \alpha'_{i} = \alpha'_{i-1} + (1 - \alpha'_{i-1}) \alpha_i
        $$
        The result is stored in local `colorMesh` and `opacityMesh` arrays [S1, unofficial].
5.  **Result Aggregation:**
    -   Processes with rank $\ge p_x p_y$ send their `colorMesh` and `opacityMesh` to the process with rank `surfaceProcess = rank % (p_x p_y)` [S1, unofficial].
    -   Processes with rank $< p_x p_y$ receive meshes from higher ranks (specifically from ranks $(c \cdot p_x p_y) + rank$ for $c \in [1, p_z)$) [S1, unofficial].
    -   Rank 0 gathers all composited meshes, concatenates them spatially according to the $p_x \times p_y$ structure, converts to `uint8`, and saves the image [S1, unofficial].

**Edge Cases and Pitfalls:**
-   **Boundary Precision:** The last segment in each dimension must extend to the total volume size to avoid missing data [S1, unofficial].
-   **Communication Overhead:** The method requires significant MPI communication for data distribution and result aggregation, which can become a bottleneck for small chunks or high process counts [S1, unofficial].
-   **Ray-Volume Intersection:** The pseudocode assumes a specific ray traversal logic. In a general implementation, rays must be intersected with the local chunk's bounding box to determine valid sample ranges, or the global ray must be sampled with local data lookups (which requires ghost zones or global indexing) [S1, G, unofficial]. The provided source [S1, unofficial] uses a simplified approach where the local data is processed directly.

## Operating characteristics
-   **Time Complexity:** $O(N \cdot S)$ for data distribution and $O(N \cdot S / S) = O(N)$ for local computation per process, where $N$ is the number of samples per ray and $S$ is the number of processes. Total time is dominated by $O(N)$ computation plus communication overhead $O(S)$ [S1, unofficial].
-   **Memory Complexity:** $O(V/S)$ per process, where $V$ is the total volume size. This allows rendering of volumes larger than a single node's memory [S1, unofficial].
-   **Performance:** Scaling is linear with the number of processes for large datasets, but communication latency can degrade performance for small chunks or high $p_x p_y p_z$ configurations [S1, unofficial].
-   **Strengths:** Scalability to large datasets; simple implementation using standard MPI primitives [S1, unofficial].
-   **Limitations:** Communication overhead; load imbalance if the volume has non-uniform density or if the domain decomposition does not match the data distribution; lack of hardware acceleration [S1, unofficial].
