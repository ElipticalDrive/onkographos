# Parallel Domain-Decomposed Ray Casting

Also called: MPI Ray Casting, Distributed Ray Casting

## Overview
Parallel Domain-Decomposed Ray Casting is a data-space subdivision technique that accelerates direct volume ray casting by distributing both the volume dataset and the computation across multiple processing units (nodes) in a distributed-memory environment [S1, S2, S3, unofficial]. It solves the scalability problem of rendering high-resolution datasets that exceed the memory of a single processor by partitioning the 3D volume into subvolumes, allowing each node to perform local front-to-back ray tracing independently without inter-node communication during the rendering phase [S1, S2, unofficial]. Unlike image-space subdivision methods, which distribute pixels to processors, this method assigns computation associated with specific spatial regions to processors, making it suitable for distributed systems where data partitioning is natural [S1, S2, unofficial]. The final image is constructed by compositing the partial images (subimages) generated by each node in a determined depth order [S1, S2, unofficial].

## How it works
The method implements the emission-absorption optical model described in [Direct volume ray casting](19-direct-volume-ray-casting.md). The pipeline consists of data distribution, local ray casting, and parallel compositing.

### Inputs and Outputs
*   **Inputs:**
    *   Volume data $V$: A 3D scalar grid of shape $(Z, Y, X)$, typically stored as `float32` [S3, unofficial].
    *   Transfer functions:
        *   Opacity map $T_\alpha$: A 2D array with 2 rows. Row 1 contains scalar positions; Row 2 contains corresponding opacity values [S3, unofficial].
        *   Color map $T_c$: A 2D array with 5 rows. Row 1 contains scalar positions; Rows 2, 3, 4 contain R, G, B color values respectively [S3, unofficial].
    *   Grid dimensions: Integers $p_x, p_y, p_z$ defining the 3D grid of MPI processes (e.g., $2 \times 2 \times 2$) [S3, unofficial].
    *   Step size $\Delta t$: Fixed sampling interval along the ray direction (e.g., 0.5) [S3, unofficial].
*   **Outputs:**
    *   Final image: A 2D color buffer (e.g., PNG) [S3, unofficial].

### Data Structures
Each processing node $P_{ijk}$ (where $i \in [0, p_x-1], j \in [0, p_y-1], k \in [0, p_z-1]$) holds:
1.  **Local Data:** A subvolume chunk $V_{ijk}$ of shape $(Z/p_z, Y/p_y, X/p_x)$ [S3, unofficial].
2.  **Transfer Functions:** Copies of $T_\alpha$ and $T_c$ [S2, S3, unofficial].
3.  **Local Image Buffers:**
    *   `colorMesh`: 3D array of shape $(H, W, 3)$ storing accumulated color $C'$ [S3, unofficial].
    *   `opacityMesh`: 2D array of shape $(H, W)$ storing accumulated opacity $\alpha'$ [S3, unofficial].
    *   $H, W$ are the image height and width.

### Numbered Steps

1.  **Data Partitioning and Distribution:**
    The master process (Rank 0) loads the full volume $V$ and splits it into $p_x \times p_y \times p_z$ chunks. The chunk for process $(i, j, k)$ covers the spatial range:
    $$
    x \in [i \cdot \frac{X}{p_x}, (i+1) \cdot \frac{X}{p_x}), \quad y \in [j \cdot \frac{Y}{p_y}, (j+1) \cdot \frac{Y}{p_y}), \quad z \in [k \cdot \frac{Z}{p_z}, (k+1) \cdot \frac{Z}{p_z})
    $$
    Rank 0 sends each chunk along with metadata (transfer functions, grid dimensions) to the corresponding rank using point-to-point communication (e.g., `MPI_Send`) [S3, unofficial]. Alternatively, nodes may access the data via NFS, but explicit distribution is preferred for performance [S1, S2, unofficial].

2.  **Local Ray Casting:**
    Each rank $P_{ijk}$ independently executes the ray casting algorithm for its assigned subvolume $V_{ijk}$:
    *   For each pixel $(u, v)$ in the image, generate a ray $r(t) = \mathbf{o} + t\mathbf{d}$ [S2, unofficial].
    *   Intersect the ray with the bounding box of the local subvolume to determine entry $t_{start}$ and exit $t_{end}$ [S2, unofficial].
    *   Sample the local volume at equidistant intervals $\Delta t$ along the ray segment $[t_{start}, t_{end}]$ [S2, unofficial].
    *   At each sample point $\mathbf{p}$, perform trilinear interpolation on the 8 nearest voxels of $V_{ijk}$ to get scalar value $d$ [S2, unofficial].
    *   Map $d$ to color $C$ and opacity $\alpha$ using $T_c$ and $T_\alpha$ [S2, unofficial].
    *   Composite front-to-back using the over operator:
        $$
        C'_{new} = C'_{old} + (1 - \alpha'_{old}) \alpha C
        $$
        $$
        \alpha'_{new} = \alpha'_{old} + (1 - \alpha'_{old}) \alpha
        $$
    *   Terminate the ray if $\alpha'$ exceeds a threshold (e.g., 1.0) [S2, unofficial].
    *   Store the final $C'$ and $\alpha'$ for each pixel in `colorMesh` and `opacityMesh` [S3, unofficial].

3.  **Parallel Compositing:**
    Since the subvolumes are spatially partitioned, the subimages they generate have a fixed spatial relationship. The compositing order is determined a priori based on the depth of the subvolumes relative to the camera [S2, unofficial].
    *   The compositing process uses a binary-swap (or tree-based) reduction strategy to merge partial images [S1, S2, unofficial].
    *   Nodes exchange their `colorMesh` and `opacityMesh` with partners.
    *   The receiving node composites the incoming subimage with its local buffer using the over operator. Because the over operator is associative ($a \text{ over } (b \text{ over } c) = (a \text{ over } b) \text{ over } c$), the order of combination does not affect the final result, provided the spatial overlap is handled correctly [S2, unofficial].
    *   Specifically, in the MPI implementation, ranks with index $\ge p_x p_y$ send their results to ranks $< p_x p_y$ (surface processes), which accumulate the results [S3, unofficial].
    *   The root process gathers the final composited image and saves it [S3, unofficial].

### Edge Cases and Pitfalls
*   **Load Imbalance:** If the volume contains many empty voxels (e.g., head or vessel data), some subvolumes may require less computation than others, reducing speedup [S2, unofficial]. Dense data (e.g., vorticity) exhibits nearly linear speedup [S2, unofficial].
*   **Communication Overhead:** On networked workstations, communication accounts for ~97% of compositing time [S2, unofficial]. Compression of subimages can reduce this by 80% [S2, unofficial]. On massively parallel supercomputers (CM-5), communication is a smaller fraction (3-10%) [S2, unofficial].
*   **Small Image Sizes:** For small images (e.g., 64x64), overhead costs dominate, leading to poor speedup [S2, unofficial].
*   **Ordering:** Subvolumes must be partitioned such that an unambiguous front-to-back ordering can be determined for compositing [S2, unofficial].

## Subtopics

### [Parallel Volume Rendering with Local Ray Tracing and Parallel Compositing](7841-parallel-volume-rendering-with-local-ray-tracing-and-paralle.md)
This method is a parallel volume rendering algorithm that distributes both volume data and computation to individual processing units to render high-resolution datasets that exceed the memory of a single processor. It solves the scalability problem of direct volume ray casting by dividing the data space into subvolumes, allowing each node to perform local ray tracing independently without inter-processor communication during the rendering phase. It is distinguished from image-space subdivision methods (like [Parallel Domain-Decomposed Ray Casting](3625-parallel-domain-decomposed-ray-casting.md)) by using data-space subdivision, which is better suited for distributed-memory environments where data can be partitioned. The final image is constructed by compositing the subimages in a determined depth order using a binary-swap method.

## Operating characteristics
*   **Time Complexity:** Theoretical speedup is linear with the number of processors $N$, assuming perfect load balance and negligible communication [S2, unofficial]. In practice, speedup is limited by load imbalance and communication overhead [S2, unofficial].
*   **Memory Complexity:** Each node stores only its assigned subvolume, allowing the rendering of datasets larger than the memory of a single node [S1, S2, unofficial].
*   **Measured Performance:**
    *   On Sun SPARC workstations, a 75% speedup was achieved with 8 nodes [S1, unofficial].
    *   On CM-5, nearly linear speedup was observed for dense data (vorticity) [S2, unofficial].
    *   On networked workstations, communication dominates compositing time (~97%) [S2, unofficial].
*   **Strengths:**
    *   Scalable to very large datasets.
    *   No global shared memory required [S1, unofficial].
    *   Simple parallelization model (no inter-node communication during ray casting) [S2, unofficial].
*   **Limitations:**
    *   Communication bottleneck during compositing on slow networks [S2, unofficial].
    *   Load imbalance due to data sparsity [S2, unofficial].
    *   Requires a priori knowledge of subvolume ordering for compositing [S2, unofficial].
*   **When to Use:** Large datasets that do not fit in a single node's memory, on distributed-memory clusters or networks of workstations [S1, S2, unofficial].
*   **When Not to Use:** Small datasets, shared-memory multiprocessors (where image-space subdivision is simpler), or scenarios with extremely slow network bandwidth [S2, unofficial].

## Background
The method was developed in the mid-1990s to address the computational intensity of volume rendering. Key works include Hansen and Krogh's "A data distributed parallel algorithm for ray-traced volume rendering" (1994) [S2, unofficial], which implemented the algorithm on the Connection Machine CM-5 and networked workstations, and a thesis by an unnamed author (DTIC ADA248167) which demonstrated the technique on Sun SPARC workstations [S1, unofficial]. The approach builds on Levoy's front-to-back ray casting [S2, unofficial] and Porter and Duff's over operator [S2, unofficial]. It contrasts with earlier geometric ray tracing parallelization methods (e.g., Dippe and Swensen) that divided world space and passed rays between neighbors [S1, unofficial].
