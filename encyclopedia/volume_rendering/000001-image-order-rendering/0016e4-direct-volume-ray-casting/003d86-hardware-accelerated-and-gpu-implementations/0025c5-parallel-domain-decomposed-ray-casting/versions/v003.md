# Parallel Domain-Decomposed Ray Casting

Also called: 3D Grid Process Distribution, Distributed Ray Casting, Distributed Volume Rendering via Subvolume Partitioning, MPI Ray Casting, Subvolume Parallelization

## Overview
Parallel Domain-Decomposed Ray Casting accelerates volume rendering by partitioning the 3D volume dataset into subvolumes and assigning each subvolume to an independent process in a distributed computing cluster [S1, S2, unofficial]. Each process performs front-to-back ray casting on its local data chunk independently, eliminating the need for global shared memory or inter-process ray passing [S1, unofficial]. This method solves the performance bottleneck of single-processor ray casting by leveraging object-space parallelism, achieving significant speedups (e.g., 75%) while maintaining image quality [S1, unofficial]. It differs from world-space decomposition methods (like Dippe and Swensen's) by dividing the data rather than the viewing space, and from pixel-level parallelization by operating at the subvolume level [S1, unofficial].

## How it works
The method distributes a 3D volume dataset across a 3D grid of MPI processes. The process involves data partitioning, distribution, independent ray casting, and result aggregation.

### Inputs and Outputs
**Inputs:**
- Volume data file (e.g., `.raw` format containing scalar values).
- Transfer function files:
  - Opacity transfer function: 2D array, shape $(2, N_{opacity})$, dtype `float32`. Row 1: scalar positions; Row 2: opacity values [S2, unofficial].
  - Color transfer function: 2D array, shape $(5, N_{color})$, dtype `float32`. Row 1: scalar positions; Rows 2-4: R, G, B values respectively [S2, unofficial].
- Parallelization parameters: $px, py, pz$ (integer dimensions of the process grid) [S2, unofficial].
- Sampling parameter: `step_size` (fixed sampling interval along the ray direction) [S2, unofficial].

**Outputs:**
- Final composited image (e.g., PNG file) [S2, unofficial].

### Data Structures
1. **Volume Data:** 3D numpy array of shape $(z_{Total}, y_{Total}, x_{Total})$, dtype `float32` [S2, unofficial].
2. **Subvolume Chunk:** Slice of the volume data: `data[z_index:z_next, y_index:y_next, x_index:x_next]` [S2, unofficial].
3. **Transfer Functions:**
   - `opacityData`: 2D array $(2, N_{opacity})$ [S2, unofficial].
   - `colorData`: 2D array $(5, N_{color})$ [S2, unofficial].
4. **Intermediate Results:**
   - `colorMesh`: 3D array storing accumulated color for the subvolume's pixel grid [S2, unofficial].
   - `opacityMesh`: 2D array storing accumulated opacity for the subvolume's pixel grid [S2, unofficial].

### Numbered Steps

1. **Initialization and Data Loading (Rank 0):**
   - Rank 0 loads the volume data, opacity transfer function, and color transfer function [S2, unofficial].
   - The volume data is reshaped to $(z_{Total}, y_{Total}, x_{Total})$ [S2, unofficial].
   - Calculate segment sizes:
     $$ x_{seg} = \lfloor x_{Total} / px \rfloor $$
     $$ y_{seg} = \lfloor y_{Total} / py \rfloor $$
     $$ z_{seg} = \lfloor z_{Total} / pz \rfloor $$
   - [S2, unofficial]

2. **Data Distribution:**
   - Rank 0 iterates over the 3D process grid $(k, j, i)$ where $k \in [0, pz-1], j \in [0, py-1], i \in [0, px-1]$ [S2, unofficial].
   - For each rank `count` ($0 \le count < px \cdot py \cdot pz$), calculate the subvolume boundaries:
     $$ z_{index} = k \cdot z_{seg}, \quad z_{next} = \min((k+1) \cdot z_{seg}, z_{Total}) $$
     $$ y_{index} = j \cdot y_{seg}, \quad y_{next} = \min((j+1) \cdot y_{seg}, y_{Total}) $$
     $$ x_{index} = i \cdot x_{seg}, \quad x_{next} = \min((i+1) \cdot x_{seg}, x_{Total}) $$
   - Rank 0 sends the subvolume chunk, transfer functions, and grid dimensions $(px, py, pz)$ to the corresponding rank using `comm.send()` [S2, unofficial].
   - Other ranks receive their data using `comm.recv(source=0)` [S2, unofficial].

3. **Local Ray Casting:**
   - Each rank performs front-to-back ray casting on its local subvolume [S1, S2, unofficial].
   - For each pixel in the subvolume's projection:
     - Generate ray $r(t) = \mathbf{o} + t\mathbf{d}$ [S1, unofficial].
     - Intersect with the subvolume's bounding box to find $t_{start}$ and $t_{end}$ [S1, unofficial].
     - Discretize the ray segment into samples with interval `step_size` [S2, unofficial].
     - For each sample point $\mathbf{p}_i$:
       - Sample the scalar value $V(\mathbf{p}_i)$ from the local volume data [S2, unofficial].
       - Apply transfer functions to get color $C_i$ and opacity $\alpha_i$ [S2, unofficial].
         - Opacity interpolation: Linear interpolation between opacity values based on scalar value [S2, unofficial].
         - Color interpolation: Linear interpolation between R, G, B values based on scalar value [S2, unofficial].
       - Composite using front-to-back over operator:
         $$ C'_{i} = C'_{i-1} + (1 - \alpha'_{i-1}) \alpha_i C_i $$
         $$ \alpha'_{i} = \alpha'_{i-1} + (1 - \alpha'_{i-1}) \alpha_i $$
       - [S1, S2, unofficial]
   - Store the final accumulated color and opacity for the pixel in `colorMesh` and `opacityMesh` [S2, unofficial].

4. **Result Aggregation:**
   - Let $t = px \cdot py$ [S2, unofficial].
   - Ranks with index $rank \ge t$ send their `colorMesh` and `opacityMesh` to the rank $surfaceProcess = rank \% t$ [S2, unofficial].
   - Ranks with index $rank < t$ receive meshes from ranks $(c \cdot t) + rank$ for $c \in [1, pz-1]$ [S2, unofficial].
   - Rank 0 gathers all composited meshes, concatenates them spatially according to the $px \times py \times pz$ structure, converts to `uint8`, and saves as an image [S2, unofficial].

### Parameters
- $px, py, pz$: Integer dimensions of the 3D process grid. Typical value: 2, 2, 2 [S2, unofficial].
- `step_size`: Fixed sampling interval along the ray direction. Typical value: 0.5 [S2, unofficial].
- Network protocol: TCP/IP [S1, unofficial].
- Remote execution: `rsh` (due to unreliability of REX) [S1, unofficial].

### Edge Cases and Pitfalls
- **Network Reliability:** The REX service on Sun SPARC workstations was unreliable, requiring the use of the slower `rsh` command [S1, unofficial].
- **Data Partitioning Boundaries:** When dividing the volume into subvolumes, ensure that the last segment in each dimension includes any remaining voxels to avoid data loss (e.g., using `min((k+1)*z_seg, z_Total)`) [S2, unofficial].
- **Precision:** Use `float32` for volume data and transfer functions to balance precision and memory usage [S2, unofficial].

## Operating characteristics
- **Time Complexity:** $O(N \cdot P)$, where $N$ is the number of samples per ray and $P$ is the number of processes. The total work is distributed across $P$ processes, so the time per process is $O(N \cdot V / P)$, where $V$ is the volume of the subvolume [S1, S2, unofficial].
- **Memory Complexity:** $O(V / P)$ per process, where $V$ is the total volume size [S1, S2, unofficial].
- **Measured Performance:** 75% speedup achieved while maintaining image quality compared to single processor rendering on 8 workstations [S1, unofficial].
- **Strengths:**
  - No global shared memory required [S1, unofficial].
  - Simple implementation using MPI [S2, unofficial].
  - Maintains image quality [S1, unofficial].
- **Limitations:**
  - Requires data distribution and result aggregation overhead [S2, unofficial].
  - Load balancing may be uneven if the volume has varying density [S1, unofficial].
  - Network communication can become a bottleneck [S1, unofficial].
- **When to Use:**
  - Large volume datasets that do not fit in the memory of a single processor [S1, unofficial].
  - Distributed computing environments with fast interconnects [S1, unofficial].
- **When Not to Use:**
  - Small volume datasets where the overhead of distribution outweighs the benefits [S1, unofficial].
  - Environments with slow or unreliable network connections [S1, unofficial].
