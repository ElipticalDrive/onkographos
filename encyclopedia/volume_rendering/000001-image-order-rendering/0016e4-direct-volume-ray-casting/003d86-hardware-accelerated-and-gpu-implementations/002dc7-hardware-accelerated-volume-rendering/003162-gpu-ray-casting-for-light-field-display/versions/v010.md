# GPU Ray Casting for Light Field Display

Also called: Direct Volume Rendering on Light Field Display, Interactive Light Field Volume Rendering, MCOP Ray Casting with Adaptive Mipmap Level Selection, MCOP projection, Multi-viewer 3D Volume Rendering

## Overview
This method performs interactive direct volume rendering on a multi-projector light field display by computing rays from projector positions through screen pixels into the volume using Multi-Camera Optical Projection (MCOP) [S1]. It differs from standard GPU ray casting by explicitly modeling the discrete projector geometry to generate correct per-pixel ray parameters, avoiding the interpolation errors inherent in standard vertex attribute interpolation, and employs depth-dependent mipmap level selection to maintain spatial resolution relative to the display screen [S1].

## How it works
**Inputs and Outputs**
*   **Inputs**:
    *   Volume data $V$ stored in a 4-component 3D texture (RGB: unscaled precomputed gradient; A: voxel value) [S1].
    *   A 1D RGBA lookup table (LUT) for transfer function mapping [S1].
    *   Uniform parameters: Projector position $\mathbf{E}_w$, virtual observer distance $V_d$, virtual observer height $V_h$, log2 voxel size $\log_2 V$, step size $DL$, screen pixel size $S_0$, angular spread factor $\tan \Phi$, and maximum opacity threshold $a_{max}$ [S1].
    *   Model-view inverse matrix $M_{inv}$ for world-to-texture coordinate transformation [S1].
*   **Outputs**:
    *   A fragment color and opacity pair $(C, \alpha)$ for each projector pixel [S1].

**Data Structures**
The method uses two primary structures defined in the shader code [S1]:
1.  `ray_t`: Contains `org` (float3, ray origin in texture coordinates), `dir` (float3, normalized ray direction), and `len` (float3, integration length).
2.  `fragment_out`: Contains `color` (float4, RGBA output).

**Numbered Steps**

1.  **Proxy Geometry Setup**: Render a coarsely tessellated proxy geometry (8x8 quads) representing a slightly enlarged bounding volume [S1]. This geometry is used to drive the fragment shader, ensuring that ray parameters are computed per-fragment rather than interpolated from vertices [S1].

2.  **Ray Origin and Direction Computation**:
    *   The vertex shader computes the unnormalized projected screen position $\mathbf{S}$ for each fragment using MCOP projection equations [S1].
    *   The fragment shader receives $\mathbf{S}$ and computes the ray direction $\mathbf{d}$ in world coordinates using the projector position $\mathbf{E}_w$ and virtual viewer parameters $V_d, V_h$ [S1]:
        $$
        \mathbf{d}_{world} = \left[ \frac{S_x - E_x}{E_z}, \frac{S_y - V_y}{V_z}, -1 \right]
        $$
        *(Note: The source formula uses $V_y$ and $V_z$ derived from $V_h$ and $V_d$, but the code snippet explicitly uses `Vh` and `Vd` in the calculation `(Vh-y)/Vd`)* [S1].
    *   The ray origin $\mathbf{o}_{world}$ is set to $(x, y, 0)$ in world coordinates, where $x, y$ are the pixel coordinates [S1].

3.  **Coordinate Transformation and Clipping**:
    *   Transform the ray origin $\mathbf{o}_{world}$ and a point $\mathbf{e}_{world} = \mathbf{o}_{world} + \mathbf{d}_{world}$ into texture coordinates using the inverse model-view matrix $M_{inv}$ [S1]:
        $$
        \mathbf{o}_{tex} = M_{inv} \cdot \mathbf{o}_{world}
        $$
        $$
        \mathbf{e}_{tex} = M_{inv} \cdot \mathbf{e}_{world}
        $$
    *   Compute the normalized direction in texture space: $\mathbf{d}_{tex} = \text{normalize}(\mathbf{e}_{tex} - \mathbf{o}_{tex})$ [S1].
    *   Clip the line segment $(\mathbf{o}_{tex}, \mathbf{d}_{tex})$ against the unit box $[0,1]^3$ to find entry distance $t_{min}$ and exit distance $t_{max}$ [S1].
    *   Calculate the ray length $L = t_{max} - t_{min}$ and the entry point $\mathbf{o}_{final} = \mathbf{o}_{tex} + \mathbf{d}_{tex} \cdot t_{min}$ [S1].

4.  **Ray Validation**:
    *   If $L < \epsilon$ (where $\epsilon$ is a small epsilon value), discard the fragment as it lies outside the volume bounds [S1].

5.  **Ray Marching Loop**:
    *   Initialize compositing variables: accumulated color $I = (0,0,0)$, accumulated opacity $a = 0.0$, current texture coordinate $\mathbf{uvw} = \mathbf{o}_{final}$, and step vector $\Delta \mathbf{d} = \mathbf{d}_{tex} \cdot DL$ [S1].
    *   Calculate the number of steps $N = \lfloor L / DL \rfloor$ [S1].
    *   Iterate $i$ from $0$ to $N-1$:
        1.  **Mipmap Level Selection**:
            *   Compute the depth $z$ of the current sample $\mathbf{uvw}$ from the screen. This is done by transforming $\mathbf{uvw}$ to world space and taking the absolute value of the z-component, approximated by a dot product with the model-view matrix's third row (representing the view direction) [S1]:
                $$
                z = | \mathbf{m}_{view}[2] \cdot \mathbf{uvw}_{homogeneous} |
                $$
                *(Specifically: `abs(dot(glstate.matrix.modelview[0][2], float4(uvw.xyz, 1.0)))`)* [S1].
            *   Compute the mipmap level $l$ using the variable step size $s(z)$ (implicitly handled by the depth-dependent resolution logic) and the formula [S1]:
                $$
                l = \text{median}\left(0, L_{max}, \left\lfloor \log_2 \left( \frac{s(z)}{v_0} \right) \right\rfloor \right)
                $$
                *(The code implementation uses a simplified approximation based on screen distance: `log2(S0 + 2*tanPhi*z) - log2V`)* [S1].
        2.  **Texture Sampling**:
            *   Sample the volume texture at $\mathbf{uvw}$ using the computed mipmap level $l$ via `tex3Dlod` (or equivalent intrinsic) [S1]. Let the result be $g_{gggv}$ [S1].
        3.  **Transfer Function and Shading**:
            *   Map the sampled value to color $C_i$ and opacity $\alpha_i$ using the 1D LUT and precomputed gradient for shading [S1]. *(Implementation details omitted in source code, marked as `...`)* [S1].
        4.  **Front-to-Back Compositing**:
            *   Update accumulated color and opacity [S1]:
                $$
                I = I + (1.0 - a) \cdot C_i
                $$
                $$
                a = a + (1.0 - a) \cdot \alpha_i
                $$
        5.  **Step Forward**:
            *   Advance the texture coordinate: $\mathbf{uvw} = \mathbf{uvw} + \Delta \mathbf{d}$ [S1].
        6.  **Termination Check**:
            *   If $a \ge a_{max}$, break the loop (Early Ray Termination) [S1].

6.  **Output**:
    *   Return the final accumulated color $I$ and opacity $a$ as the fragment output [S1].

**Parameters and Typical Values**
*   **Proxy Tessellation**: 8x8 quads [S1].
*   **Step Size ($DL$)**: Reduced during interaction (e.g., doubled) to improve frame rates; full resolution uses 1 sample/voxel [S1].
*   **Screen Precision**: 2.5mm precision on screen during interaction [S1].
*   **Display Update**: 96 projectors updated in batches of 16 [S1].

**Edge Cases and Pitfalls**
*   **Vertex Interpolation Error**: Standard vertex attribute interpolation produces incorrect per-pixel ray parameters for MCOP projection. This is mitigated by using the coarse proxy geometry and computing projections in the vertex shader [S1].
*   **Tile Misalignment**: If the refresh rate is too slow relative to object movement, misalignment artifacts become visible between the 16-projector batches [S1].
*   **Out of Bounds**: Rays with length less than epsilon are discarded [S1].

## Subtopics

### MCOP Projection
A projection model that maps screen pixels to projector positions, providing a continuous perceived image unlike discrete multiview technologies. It avoids fixed viewing zones and abrupt view changes [S1].

### Depth-Dependent Mipmap Selection
A sampling strategy where the mipmap level is chosen based on the sample's distance from the screen ($z$) and angular spread, ensuring voxel size matches spatial resolution requirements at that depth [S1].

## Operating characteristics
*   **Performance**: The method is limited by the single GPU's volume rendering performance. At full resolution (1 ray/pixel, 1 sample/voxel), millions of rays require hundreds of steps, leading to low frame rates [S1].
*   **Optimization**: Interactive frame rates are improved by lowering the sampling rate (reducing pixel count to 2.5mm precision and doubling step size) [S1].
*   **Strengths**: Provides fully continuous perceived image with parallax, accommodation, and stereo cues. Good registration between object space and physical space [S1].
*   **Limitations**: Performance degrades with high resolution and complex volumes. Tile misalignment artifacts can occur during fast motion due to batched projector updates [S1].
*   **When to Use**: Interactive visualization on multi-projector light field displays where continuous viewing zones are required.
*   **When Not to Use**: When high frame rates with full resolution are critical, or when the display hardware does not support the specific MCOP projection geometry [S1].

## Background
The method was introduced by Agus et al. in 2008 for the "Chameleon" light field display, a system using 96 projectors to create a large, interactive 3D display space [S1]. It builds upon earlier work in GPU-accelerated volume rendering and multi-view displays, addressing the specific challenge of generating correct ray parameters for non-standard projection geometries (MCOP) that cannot be represented by traditional homogeneous matrices [S1]. The approach contrasts with contemporary multiview technologies that suffer from discrete viewing zones [S1].
