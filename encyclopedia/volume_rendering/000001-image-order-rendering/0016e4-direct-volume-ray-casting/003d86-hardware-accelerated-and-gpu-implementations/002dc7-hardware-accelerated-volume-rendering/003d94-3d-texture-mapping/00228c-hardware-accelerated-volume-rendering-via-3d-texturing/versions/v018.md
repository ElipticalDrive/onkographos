# Hardware-Accelerated Volume Rendering via 3D Texturing

Also called: 3D Texture Mapping Volume Rendering, 3D Texturing Example, Planar Texture Resampling, Polygon Resampling with 3D Texturing, RealityEngine 3D Texture Volume Rendering, RealityEngine Volume Rendering

## Overview
Hardware-Accelerated Volume Rendering via 3D Texturing is a direct volume ray casting method that leverages 3D texture mapping hardware to resample volumetric data into textured planes parallel to the image plane, then composites these slices into the frame buffer [S1][S2, unofficial]. It solves the problem of interactive volume visualization by offloading the computationally intensive trilinear interpolation and reconstruction steps to dedicated graphics hardware, allowing for frame rates significantly higher than software-based ray casting [S4]. Unlike [Shear-Warp](9530-shear-warp.md), which performs classification before bilinear resampling and requires a final warp step, the Planar Texture Resampling variant of this method performs trilinear interpolation followed by classification and requires no final warp, resulting in higher image quality and consistent performance for perspective projections [S1]. It differs from [3D Pixel Texture Classification](6055-3d-pixel-texture-classification.md) by using explicit geometry (polygons) to define resampling planes rather than relying solely on pixel-level texture coordinate generation for classification.

## How it works
**Inputs and Outputs:**
*   **Input:** A volumetric dataset $V$ of density or attenuation values, stored in 3D texture memory. A viewing matrix defining the camera position and orientation.
*   **Output:** A 2D image in the frame buffer, where each pixel contains a color and opacity value derived from the accumulated volume samples along the view ray.

**Data Structures:**
*   **3D Texture Memory:** The volume data is stored as a 3D texture object. In high-performance hardware like the SGI RealityEngine, memory is 8-way interleaved to allow fetching any tri-linear cell (8 adjacent voxels) in a single memory access [S1]. A voxel with address $a = [z, y, x]$ is stored in memory module $k$ at index $i$ as follows [S1]:
    $$ k = (x \bmod 2) + 2 (y \bmod 2) + 4 (z \bmod 2) $$
    $$ i = \lfloor x/2 \rfloor + 2 \lfloor y/2 \rfloor + 4 \lfloor z/2 \rfloor $$
*   **Resampling Polygons:** Geometry (typically quads) embedded in the texture space. These polygons define the planes along which the volume is resampled. Two alignment strategies exist:
    *   **Object-Space:** Polygons are defined within the volume coordinate system. They must be reoriented in the plane most parallel to the view-plane as the viewpoint changes, requiring explicit creation of polygons for six view orientation cases [S2, unofficial].
    *   **Image-Space:** Polygons are defined in image-space (screen coordinates) and transformed by the inverse viewing matrix into object-space. They must be clipped to the boundaries of the volume to ensure valid texture coordinates [S2, unofficial].

**Parameters:**
*   **Exposure Value:** A user-controlled scaling factor $e \in [0, 1]$ applied to resampled values to prevent overflow in the 12-bit frame buffer [S2, unofficial].
*   **Spacing Factor ($d$):** The distance between sample values along the ray. $d$ is constant for all samples behind a pixel but varies from pixel to pixel due to perspective [S2, unofficial].
*   **Interpolation:** Tri-linear interpolation is used by the texture engine to resample texture data [S1].

**Steps:**
1.  **Load Volume:** Load the volume data into 3D texture memory. If the volume exceeds the hardware limit (e.g., 1M 12-bit points on RealityEngine), split it into slabs and render them in succession [S2, unofficial].
2.  **Configure Texture:** Enable 3D texturing and set the global texture environment mode to `GL_MODULATE` [S3, unofficial]. Bind the specific 3D texture object [S3, unofficial].
3.  **Setup Texture Matrix:** Switch the matrix mode to `GL_TEXTURE`, reset to identity, and apply a translation of $(0.5, 0.5, 0.5)$ to correct for texture coordinate centering [S3, unofficial].
4.  **Generate Resampling Geometry:** Define resampling polygons based on the chosen alignment strategy (Object-Space or Image-Space) [S2, unofficial].
    *   *Object-Space:* Reorient polygons to be parallel to the view plane.
    *   *Image-Space:* Transform polygons by the inverse view matrix and clip them to volume boundaries.
5.  **Render Slices:** Switch back to `GL_MODELVIEW`. For each resampling polygon (quad):
    *   Set the 3D texture coordinates for each vertex $i$ to $(x_i, y_i, z_i)$ and the vertex position to $(x_i, y_i, z_i)$ [S3, unofficial].
    *   The hardware rasterizer and texture engine perform trilinear interpolation of the volume data at each point on the polygon [S1][S2, unofficial].
    *   Scale each resampled value by the exposure value $e$ [S2, unofficial].
6.  **Accumulate:** The resampled values are accumulated into the frame buffer.
    *   *Summation:* Sum the scaled resampled values at each pixel. Clamp the sum if it exceeds the 12-bit range [S2, unofficial].
    *   *Spacing Application:* Apply spacing factors $d$ to the summation results. This is often done using an additional full-screen polygon with a 2D texture corresponding to the $d$ values required for each pixel [S2, unofficial].
7.  **Final Compositing:** Combine resampled values to produce the final pixel color based on the visualization goal [S2, unofficial]:
    *   *Direct Summation:* For simple density visualization.
    *   *Radiographs:* Compute the exponential of the summed attenuation integral: $I = 1.0 - \exp(-\sum u_i d)$, where $u_i$ are the resampled values [S2, unofficial]. This may be done via a lookup table.
    *   *Opacity-Based Rendering:* Use two 8-bit texture components (raw data and precomputed shading coefficient). Use resampled data component values as indices into an opacity lookup table. Multiply sample opacity by the shading coefficient to produce shaded features [S2, unofficial].
8.  **Cleanup:** Unbind the 3D texture and disable 3D texturing [S3, unofficial].

**Pseudocode:**
```python
def render_volume_3d_texturing(volume_data, view_matrix, exposure, target_resolution):
    """
    Renders a volume using 3D texture mapping hardware.
    Assumes hardware supports 3D texturing and compositing.
    """
    # 1. Load Volume
    if volume_data.size > MAX_TEXTURE_MEMORY:
        slabs = split_into_slabs(volume_data)
        for slab in slabs:
            load_texture_3d(slab)
            render_slab(view_matrix, exposure, target_resolution)
    else:
        load_texture_3d(volume_data)
        render_slab(view_matrix, exposure, target_resolution)

def render_slab(view_matrix, exposure, target_resolution):
    # 2. Configure Texture
    set_texture_env_mode(GL_MODULATE)
    enable_texture_3d()
    bind_texture_3d(volume_texture_id)
    
    # 3. Setup Texture Matrix
    switch_matrix_mode(GL_TEXTURE)
    load_identity()
    translate(0.5, 0.5, 0.5)
    switch_matrix_mode(GL_MODELVIEW)
    
    # 4. Generate Resampling Geometry (Image-Space Example)
    # Define polygons in image space, transform to object space, clip to volume bounds
    polygons = generate_image_space_polygons(view_matrix, volume_bounds, target_resolution)
    
    # 5. Render Slices
    for poly in polygons:
        begin_polygon(GL_QUADS)
        for i in range(4):
            # Set texture coordinates and vertex position
            # Hardware performs trilinear interpolation
            set_texture_coord_3d(poly.vertices[i].x, poly.vertices[i].y, poly.vertices[i].z)
            set_vertex_3d(poly.vertices[i].x, poly.vertices[i].y, poly.vertices[i].z)
        end_polygon()
        
        # Scale by exposure during hardware processing or post-process
        # Note: Hardware typically accumulates directly; exposure scaling 
        # might be applied via texture environment or post-compositing step
        apply_exposure(exposure)

    # 6. Accumulate and Composite
    # Hardware accumulates into frame buffer. 
    # For radiographs, apply exponential lookup table if not done in hardware
    if rendering_mode == RADIographs:
        apply_radiograph_lookup_table()
    elif rendering_mode == OPACITY_BASED:
        apply_opacity_lookup_table_and_shading()
    
    # 7. Cleanup
    bind_texture_3d(0)
    disable_texture_3d()
```

## Subtopics

### [Planes Method](3027-planes-method.md)
The Planes Method is a hardware-accelerated volume rendering technique that leverages 3D texture mapping hardware to resample volumetric data into planes coplanar with rays ending in a row of pixels, then performs shading and front-to-back compositing on the CPU. It solves the problem of view-dependent shading and interactive classification in texture-mapped rendering by offloading the computationally intensive Phong shading and compositing logic to the processor, allowing for optimization techniques like early ray termination and low-opacity skipping. Unlike [Shear-Warp](9530-shear-warp.md), which performs classification before bilinear resampling and requires a final warp step, the Planes method performs trilinear interpolation followed by classification and requires no final warp, resulting in higher image quality and consistent performance for perspective projections.

### BVH-accelerated 3D Texture Volume Rendering
A method to accelerate 3D texture-based volume rendering using hierarchical bounding volumes (BVH) to skip rendering of empty or occluded sub-volumes during tree traversal [S5, abstract only, unofficial]. It realizes post-classification 3D texture volume rendering using GPU fragment shaders. The original volume data is divided based on space position layer by layer according to the height of the BVH tree. In each layer, volumes corresponding to BVH tree nodes are subdivided into eight sub-volumes along three orthogonal coordinate axes. Bounding volumes are established for sub-volumes and stored in corresponding BVH tree nodes. When rendering, the BVH tree is traversed to judge whether the corresponding sub-volume should be rendered or jumped, obtaining good accelerating effects when combined with 3D texture volume rendering based on GPU [S5, abstract only, unofficial].

## Operating characteristics
*   **Time Complexity:** Performance is linear with respect to the number of pixels processed. Doubling screen pixels or resampling polygons halves the frame rate [S2, unofficial].
*   **Memory Complexity:** Limited by the 3D texture memory capacity. For the SGI RealityEngine, the limit is 1M 12-bit data points [S2, unofficial]. Larger volumes require slabbing, adding a reload time of ~0.1 seconds per slab [S2, unofficial].
*   **Measured Performance:**
    *   SGI Reality Engine 2 with two Rasters Managers (RMs) renders a 256x256x32 volume at 12 frames per second [S1].
    *   SGI Reality Engine 2 with four RMs renders a 512x512x64 dataset at 10 frames per second [S1].
    *   A 128x128x64 volume rendered into a 512x512 window at 10 frames/second using 128 object-space polygons. Processing rate: 10 million voxels/second. Measured: ~160 million pixel operations/second (each op: trilinear interpolation, multiplication, summation/composite) [S2, unofficial].
    *   A 256x256x64 volume rendered into a 512x512 window at 2.5 frames/second using 256 resampling polygons [S2, unofficial].
    *   Modern hardware can render volume data about 512 x 512 x 512 voxels in size several times a second, achieving results very close in quality to software ray casting [S4].
*   **Strengths:** High performance for interactive visualization; leverages existing 3D graphics hardware; simple implementation compared to full ray casting.
*   **Limitations:** Hardware does not directly support gradient estimation or per-sample illumination, requiring pre-computation or multi-pass methods which reduce frame rate [S1]. Precision is limited by hardware (e.g., 12-bit frame buffer), requiring careful exposure control to prevent overflow [S2, unofficial]. Image-space methods require complex clipping logic [S2, unofficial].
*   **When to Use:** Interactive visualization of moderate-sized volumes on hardware with 3D texturing support.
*   **When Not to Use:** When high-precision gradient-based lighting is required without pre-computation, or when volumes exceed texture memory limits and slab reloading latency is unacceptable.

## Background
This method originated with the development of 3D texture mapping hardware in the early 1990s, specifically on Silicon Graphics RealityEngine workstations [S2, unofficial]. It was proposed as a way to accelerate volume reconstruction by leveraging parallel texturing hardware to perform reconstruction and resampling on polygons embedded in the texture [S2, unofficial]. The technique was applied to the production of digitally reconstructed radiographs and opacity-based volume rendered images [S2, unofficial]. It was also proposed for the PixelFlow graphics system to overcome lighting and volume size limitations of the RealityEngine [S2, unofficial]. The underlying concept of planar texture resampling was described by Cullip et al. [CCF94] and further analyzed in architectural studies [S1].
