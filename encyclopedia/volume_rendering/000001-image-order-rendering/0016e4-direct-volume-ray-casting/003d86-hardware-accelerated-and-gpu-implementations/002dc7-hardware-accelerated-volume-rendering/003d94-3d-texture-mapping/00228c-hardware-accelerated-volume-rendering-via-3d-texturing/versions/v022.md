# Hardware-Accelerated Volume Rendering via 3D Texturing

Also called: Volume Rendering via 3D Textures, 3D Texture-Based Volume Rendering, 3D Texture-Mapped Volume Rendering, 3D Texture Mapping Volume Rendering, 3D Texture Approach, Cabral 9

## Overview
Hardware-Accelerated Volume Rendering via 3D Texturing renders volumetric data by storing it as a 3D texture in GPU memory and sampling it using polygonal planes parallel to the image plane [S1][S2, S7, unofficial]. It solves the problem of interactive volume visualization by offloading the computationally intensive trilinear interpolation and per-pixel blending operations to dedicated graphics hardware [S7, unofficial][S12, book]. Unlike [Shear-Warp](shear-warp.md), which requires a final warp step and performs classification before resampling, this method performs trilinear interpolation followed by classification (or direct compositing) and requires no final warp, resulting in consistent performance for perspective projections and higher image quality [S1]. It differs from [3D Pixel Texture Classification](6055-3d-pixel-texture-classification.md) by treating the volume as a solid texture sampled by geometry rather than classifying pixels directly, and from [Hardware Shading via Pixel Texture](6056-hardware-shading-via-pixel-texture.md) by relying on hardware interpolation of the volume data itself rather than shading techniques applied to pixel textures [S1][S7, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D scalar volume dataset (voxel array), a viewing direction, and a transfer function (mapping scalar values to RGBA).
*   **Output:** A 2D image in the frame buffer.

**Data Structures:**
*   **3D Texture:** The volume is stored as a single 3D texture object in GPU memory. The dimensions must typically be powers of two due to hardware limitations [S14]. The data is interpreted as a texture defined over the domain $[0,1]^3$ [S7, unofficial].
*   **Transfer Function (TF):** Stored as a 1D or 2D texture (lookup table) mapping scalar intensity to RGBA color and opacity [S1][S13, unofficial].
*   **Resampling Polygons:** Polygonal slices (typically triangles or quads) representing the intersection of equidistant planes parallel to the image plane with the volume domain [S5, S13, unofficial].

**Steps:**
1.  **Texture Loading:** Download the entire volume into 3D texture memory. If the volume exceeds available texture memory (e.g., >1M 12-bit points on older hardware like SGI RealityEngine), split it into slabs or bricks [S9, unofficial][S12, book].
2.  **Polygon Generation:** Generate a series of planes parallel to the image plane. These planes are clipped against the volume boundaries to form valid polygons [S12, book][S14]. Two alignment strategies exist:
    *   *Object-Space:* Polygons are defined within the volume and reoriented as the viewpoint changes [S9, unofficial].
    *   *Image-Space:* Polygons are defined in image-space, transformed by the inverse viewing matrix into object-space, and clipped to volume boundaries [S9, unofficial].
3.  **Sorting:** Sort the polygons in back-to-front order relative to the viewer [S1][S5, S13, unofficial]. For parallel projection, order is determined by the angle between the view vector and the Z-axis; for perspective, the order is calculated per slice [S14].
4.  **Rendering Loop (for each polygon):**
    a.  **Texture Coordinate Computation:** Compute the 3D texture coordinates for each vertex of the polygon. This involves transforming the vertex positions from camera/world space to volume-local space [S3, S13, unofficial].
    b.  **Rasterization:** Rasterize the polygon. The hardware interpolates the 3D texture coordinates across the polygon surface using barycentric interpolation [S2, unofficial][S6].
    c.  **Texture Sampling:** The texture engine performs trilinear interpolation of the 3D volume texture at each fragment's interpolated texture coordinates [S1][S7, unofficial].
    d.  **Transfer Function Application:** The sampled scalar value is mapped to RGBA color and opacity using the transfer function. This can be done via a lookup table (pre-shading) or in the fragment shader (post-shading) [S7, S13, unofficial].
    e.  **Compositing:** The resulting RGBA fragment is blended into the frame buffer using the "over" operator (alpha compositing) in back-to-front order [S1, S8].

**Formulas:**
*   **Memory Interleaving (SGI Reality Engine):** For an 8-way interleaved system, a voxel at address $a = [z, y, x]$ is stored in memory module $k$ at index $i$:
    $$ k = (x \bmod 2) + 2 (y \bmod 2) + 4 (z \bmod 2) $$
    $$ i = \lfloor x/2 \rfloor + 2 \lfloor y/2 \rfloor + 4 \lfloor z/2 \rfloor $$
    This allows fetching any tri-linear cell (8 adjacent voxels) in one memory access [S1].
*   **Coordinate Transformation (Equalizer):** To map original texture coordinates $(X, Y, Z)$ to new 3D texture coordinates $(X_n, Y_n, Z_n)$:
    $$ X_n = X \cdot W, \quad Y_n = Y \cdot H, \quad Z_n = D_b + (Z - D_s) \cdot D $$
    where $W = W_d / W_h$, $H = H_d / H_h$, $D_b = DBT / D_h$, $D = (D_d / D_h) / (D_e - D_s)$ [S14].
*   **Voxel Center Alignment:** In shader implementations, an offset of $0.5$ is added to the position to align voxel centers with texture coordinates: `sample_pos = cam_rel_pos + vec3(0.5)` [S3, unofficial].

**Pseudocode:**
```python
def render_volume_3d_texture(volume_data, transfer_function, view_matrix, num_slices):
    # 1. Load volume into 3D texture
    tex_id = create_3d_texture(volume_data)
    
    # 2. Generate and sort polygons
    # Planes are parallel to the image plane
    planes = generate_planes(num_slices, view_matrix)
    clipped_polygons = []
    for plane in planes:
        poly = clip_polygon_to_volume(plane, volume_bounds)
        if poly is not None:
            clipped_polygons.append(poly)
    
    # Sort back-to-front based on view direction
    clipped_polygons.sort(key=lambda p: depth(p, view_matrix), reverse=True)
    
    # 3. Render
    set_texture_mode(GL_MODULATE)
    enable_3d_texturing()
    bind_texture(tex_id)
    
    # Set texture matrix to map object space to texture space [0,1]^3
    setup_texture_matrix(volume_bounds)
    
    for poly in clipped_polygons:
        # Compute texture coordinates for vertices
        for vertex in poly.vertices:
            # Transform vertex to volume-local space
            local_pos = transform_to_volume_local(vertex, view_matrix)
            # Set 3D texture coordinate
            set_texture_coordinate_3d(local_pos)
        
        # Rasterize polygon
        # Hardware performs trilinear interpolation of the 3D texture
        # and blends the result into the frame buffer
        draw_polygon(poly)
        
    disable_3d_texturing()
    unbind_texture()
    return frame_buffer
```

**Parameters:**
*   `num_slices`: Number of resampling planes. Default is often 64 [S3, unofficial]. Higher values increase quality but reduce speed [S2, unofficial].
*   `exposure`: Scaling factor (0 to 1) applied to resampled values to prevent overflow in limited-precision frame buffers (e.g., 12-bit) [S9, unofficial].
*   `maxThreads`: Maximum number of threads for the render action (implementation-specific) [S8].

**Edge Cases and Pitfalls:**
*   **Gradient Estimation:** Hardware does not support direct gradient estimation for shading. Gradients must be pre-computed or approximated by pairwise subtraction of shifted slices, which reduces frame rate [S1].
*   **Precision Artifacts:** Limited frame buffer precision (e.g., 8-bit) causes color-bleeding and staircasing artifacts, especially with highly transparent classifications [S7, unofficial].
*   **Boundary Artifacts:** Incorrect handling of brick boundaries can cause interpolation errors. A voxel slice must be duplicated across brick boundaries to ensure correct trilinear interpolation [S2, unofficial].
*   **Non-linear Transfer Functions:** Non-linear TFs are not interpolated correctly by hardware texture mapping; they must be sampled via lookup tables [S4, unofficial].

## Subtopics

### [Planes Method](3027-planes-method.md)
The Planes Method is a variant that leverages 3D texture mapping to resample volumetric data into planes coplanar with rays ending in a row of pixels, then performs shading and front-to-back compositing on the CPU. It solves the problem of view-dependent shading and interactive classification by offloading Phong shading and compositing logic to the processor, allowing for optimizations like early ray termination. Unlike [Shear-Warp](shear-warp.md), it performs trilinear interpolation followed by classification and requires no final warp, resulting in higher image quality and consistent performance for perspective projections.

### BVH-accelerated 3D Texture Volume Rendering
A method to accelerate 3D texture-based volume rendering using hierarchical bounding volumes (BVH) to skip rendering of empty or occluded sub-volumes during tree traversal [S15, abstract only, unofficial]. It realizes post-classification 3D texture volume rendering using GPU fragment shaders. The volume is divided layer by layer according to the BVH tree height, and sub-volumes are subdivided into eight parts. Bounding volumes are established for these sub-volumes. During rendering, the BVH tree is traversed to judge whether a sub-volume should be rendered or skipped, obtaining good accelerating effects when combined with GPU-based 3D texture rendering [S15, abstract only, unofficial].

## Operating characteristics
*   **Time Complexity:** Theoretical complexity is $O(n^3)$, similar to standard ray casting, but performance is linear with respect to the number of pixels processed [S9, unofficial][S12, book]. Doubling screen pixels or resampling polygons halves the frame rate [S9, unofficial].
*   **Memory Complexity:** Requires one large contiguous texture block in memory. Consumer graphics cards have limited memory (e.g., 64 MB on GeForce 3), limiting volume size to $256 \times 256 \times 256$ [S2, unofficial][S6]. Larger volumes require bricking/swapping [S7, unofficial].
*   **Performance:** On SGI Reality Engine 2 with four Raster Managers, a $512 \times 512 \times 64$ dataset renders at 10 fps [S1]. On a GeForce 3, a $512^3$ volume can render several times a second [S11]. Performance is approximately 160 million unshaded tri-linear texture samples per second [S1].
*   **Strengths:** High speed for unshaded rendering; exploits dedicated hardware for interpolation and blending; consistent performance for perspective views [S1][S7, unofficial].
*   **Limitations:** No hardware support for gradients/shading; limited by texture memory size; precision artifacts in blending; non-linear transfer functions not interpolated correctly [S1][S4, S7, unofficial].
*   **When to Use:** Interactive visualization of moderate-sized volumes where shading is not critical or pre-computed.
*   **When Not to Use:** Large volumes exceeding texture memory without bricking support; scenes requiring complex per-sample lighting; high-precision scientific visualization requiring exact integration.

## Background
The method was proposed by Akeley [S4, unofficial] and popularized by Cabral et al. [S1][S7, unofficial] (often referred to as "Cabral 9") for non-shaded volume rendering. It was implemented on Silicon Graphics RealityEngine workstations [S9, unofficial]. The technique interprets a 3D scalar voxel array as a 3D texture defined over $[0,1]^3$ and uses 3D texture mapping as trilinear interpolation [S7, unofficial]. It was chosen over other algorithms (like van Gelder and Kim's) because it avoids inaccuracies in vertex clipping and texture coordinate generation [S5, unofficial]. It is used in production for digitally reconstructed radiographs and opacity-based volume rendered images [S9, unofficial].
