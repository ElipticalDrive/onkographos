# Hardware-Accelerated Volume Rendering via 3D Texturing

Also called: 3D Texture Mapping Volume Rendering, 3D Texturing Example, Planar Texture Resampling, Polygon Resampling with 3D Texturing, RealityEngine 3D Texture Volume Rendering, RealityEngine Volume Rendering, Texture Mapping for Volume Rendering

## Overview
This method leverages 3D texture mapping hardware to perform reconstruction and resampling of volumetric data in a ray-parallel fashion [S2, unofficial][S4]. It solves the problem of interactive volume rendering on early graphics hardware by storing the volume in 3D texture memory and extracting textured planes parallel to the image plane, which are then composited [S1]. Unlike [Shear-Warp](5616-hardware-accelerated-volume-rendering.md), which performs classification before bilinear resampling and requires a final warp step, the Planar Texture Resampling variant of this method performs trilinear interpolation followed by classification and requires no final warp, resulting in higher image quality and consistent performance for perspective projections [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A scalar volume $V$ stored in 3D texture memory; viewing parameters (view matrix, projection); resampling polygon definitions (Object-Space or Image-Space); transfer function parameters (opacity lookup table, shading coefficients).
*   **Output:** A 2D image in the frame buffer with accumulated color and opacity.

**Data Structures:**
*   **3D Texture Memory:** Stores the volume data. In high-performance engines like the SGI RealityEngine, 8-way interleaved memory is used to allow fetching any tri-linear cell (8 adjacent voxels) in one memory access [S1]. A voxel with address $a = [zyx]$ is stored in memory module $k$ at index $i$ as follows [S1]:
    $$
    k = (x \bmod 2) + 2 (y \bmod 2) + 4 (z \bmod 2)
    $$
    $$
    i = \lfloor x/2 \rfloor + 2 \lfloor y/2 \rfloor + 4 \lfloor z/2 \rfloor
    $$
*   **Resampling Polygons:** Defined either in Object-Space (within the volume) or Image-Space (transformed to object-space) [S2, unofficial].
*   **Lookup Tables:** Maps density to RGBA color and opacity [S1]. For opacity-based rendering, two 8-bit texture components may be used: raw data and precomputed shading coefficient [S2, unofficial].

**Steps:**
1.  **Load Volume:** Load volume data into 3D texture memory. If the volume exceeds the texture memory limit (e.g., 1M 12-bit points on RealityEngine), split into slabs and render them in succession [S2, unofficial].
2.  **Define Polygons:** Define resampling polygons.
    *   *Object-Space:* Define polygons within the volume. Reorient polygons in the plane most parallel to the view-plane as the viewpoint changes by examining the view matrix. Explicitly create polygons for the six cases arising from view orientation [S2, unofficial][S1].
    *   *Image-Space:* Define polygons in image-space. Transform them by the inverse viewing matrix into object-space. Clip polygons to the boundaries of the volume to ensure valid texture coordinates [S2, unofficial].
3.  **Configure Hardware:**
    *   Enable 3D texturing [S3, unofficial].
    *   Bind the specific 3D texture object identified by `texid` [S3, unofficial].
    *   Set the global texture environment mode to `GL_MODULATE` [S3, unofficial].
    *   Switch the matrix mode to `GL_TEXTURE` [S3, unofficial].
    *   Apply a translation of $(0.5, 0.5, 0.5)$ to the texture matrix to correct for texture coordinate centering [S3, unofficial].
    *   Reset the texture matrix to identity if necessary before applying transformations [S3, unofficial].
4.  **Render Slices:** For each resampling polygon (slice):
    *   Switch the matrix mode back to `GL_MODELVIEW` [S3, unofficial].
    *   Begin rendering a quad using `GL_QUADS` [S3, unofficial].
    *   For each vertex $i$ (0 to 3), set the 3D texture coordinate to $(x_i, y_i, z_i)$ and set the vertex position to $(x_i, y_i, z_i)$ [S3, unofficial].
    *   The 3D texture hardware performs trilinear interpolation of the volume data at each point on the polygon [S2, unofficial].
    *   End the quad [S3, unofficial].
5.  **Post-Processing & Compositing:**
    *   Scale each resampled value by an 'exposure' value (range 0 to 1) to prevent overflow in the 12-bit frame buffer [S2, unofficial].
    *   Sum the scaled resampled values at each pixel [S2, unofficial].
    *   Apply spacing factors ($d$) to the summation results. Use an additional full-screen polygon with a 2D texture corresponding to the $d$ values required for each pixel. Note: $d$ is constant for all samples behind a pixel but varies from pixel to pixel due to perspective [S2, unofficial].
    *   Clamp the sum if it exceeds the 12-bit range [S2, unofficial].
    *   Combine resampled values to produce final pixel color based on the visualization goal [S2, unofficial]:
        *   *Direct Summation:* For simple density visualization.
        *   *Radiographs:* Compute the exponential of the summed attenuation integral: $\text{pixel intensity} = 1.0 - \exp(-\sum u_i d)$. Use a lookup table to compute the exponential at each pixel if not done directly [S2, unofficial].
        *   *Opacity-Based Rendering:* Use resampled data component values as indices into an opacity lookup table. Multiply sample opacity by the shading coefficient (function of original data gradient) to produce shaded features [S2, unofficial].
6.  **Cleanup:** Unbind the 3D texture by binding texture ID 0 [S3, unofficial]. Disable 3D texturing [S3, unofficial]. Switch the matrix mode back to `GL_MODELVIEW` [S3, unofficial].

**Parameters:**
*   **Interpolation:** Tri-linear interpolation [S1].
*   **Exposure:** User-controlled scaling factor (0 to 1) to prevent overflow [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Gradient Estimation:** Hardware does not directly support estimation of gradients or per-sample illumination. Gradients must be pre-computed and stored in an additional volume or computed on-the-fly using multi-pass methods, which greatly reduce frame rate [S1]. An alternative is shading approximation by pairwise subtracting coplanar texture slices [S1].
*   **Overflow:** The RealityEngine has a maximum precision of 12 bits per frame buffer and texture component. Summation can overflow this limit. Solution: Scale samples by 'exposure' value and clamp [S2, unofficial].
*   **Image-Space Clipping:** Image-space polygons must be clipped to volume boundaries to ensure valid texture coordinates. This requires transforming to object-space, clipping, and then rendering [S2, unofficial].
*   **Slab Rendering:** When using image-space method with slabs, polygons must be rendered multiple times, clipped to the currently loaded volume slab each time [S2, unofficial].

## Subtopics

### [Planes Method](3027-planes-method.md)
The Planes Method is a hardware-accelerated volume rendering technique that leverages 3D texture mapping hardware to resample volumetric data into planes coplanar with rays ending in a row of pixels, then performs shading and front-to-back compositing on the CPU. It solves the problem of view-dependent shading and interactive classification in texture-mapped rendering by offloading the computationally intensive Phong shading and compositing logic to the processor, allowing for optimization techniques like early ray termination and low-opacity skipping. Unlike [Shear-Warp](5616-hardware-accelerated-volume-rendering.md), which performs classification before bilinear resampling and requires a final warp step, the Planes method performs trilinear interpolation followed by classification and requires no final warp, resulting in higher image quality and consistent performance for perspective projections.

### BVH-accelerated 3D Texture Volume Rendering
A method to accelerate 3D texture-based volume rendering using hierarchical bounding volumes (BVH) to skip rendering of empty or occluded sub-volumes during tree traversal [S5, abstract only, unofficial]. It realizes post-classification 3D texture volume rendering using GPU fragment shaders [S5, abstract only, unofficial]. The original volume data is divided based on space position layer by layer according to the height of the BVH tree. In each layer, volumes corresponding to BVH tree nodes are subdivided into eight sub-volumes along three orthogonal coordinate axes. Bounding volumes are established for the sub-volumes and correlative information is stored in the corresponding BVH tree nodes. When rendering the volume by traversing the BVH tree, information of BVH tree nodes is read to judge whether the corresponding sub-volume should be rendered or jumped [S5, abstract only, unofficial]. The method obtains good accelerating effects when combined with 3D texture volume rendering based on GPU [S5, abstract only, unofficial].

## Operating characteristics
*   **Time Complexity:** Performance is linear with respect to the number of pixels processed. Doubling screen pixels or resampling polygons halves the frame rate [S2, unofficial]. Quality vs Speed Trade-off: Using more resampling polygons yields higher quality images at the expense of lower rendering speed [S2, unofficial].
*   **Memory Complexity:** Limited by texture memory capacity (e.g., 1M 12-bit points on RealityEngine) [S2, unofficial]. Larger volumes require slabbing, adding reload overhead (~0.1s/slab) [S2, unofficial].
*   **Measured Performance:**
    *   SGI Reality Engine 2 with two Rasters Managers (RMs) renders a 256x256x32 volume at 12 frames per second [S1].
    *   SGI Reality Engine 2 with four RMs renders a 512x512x64 dataset at 10 frames per second [S1].
    *   128x128x64 volume rendered into 512x512 window at 10 frames/second using 128 object-space polygons. Processing rate: 10 million voxels/second. Measured: ~160 million pixel operations/second (each op: trilinear interpolation, multiplication, summation/composite) [S2, unofficial].
    *   256x256x64 volume rendered into 512x512 window at 2.5 frames/second using 256 resampling polygons. Requires four 256x256x16 texture slabs [S2, unofficial].
    *   Can render volume data about 512 x 512 x 512 voxels in size several times a second, achieving results very close in quality to software ray casting [S4].
*   **Strengths:** Interactive performance for moderate-sized volumes; leverages existing 3D graphics hardware; simple implementation [S2, unofficial].
*   **Limitations:** Limited by texture memory size; gradient estimation is difficult/expensive; performance degrades linearly with pixel count and polygon count; 12-bit precision limits on older hardware [S1][S2, unofficial].
*   **When to use:** When using hardware with 3D texture support (e.g., SGI RealityEngine) and interactive feedback is required for volumes that fit in texture memory or can be slabbed efficiently [S2, unofficial].
*   **When not to use:** For very large volumes that cannot be effectively slabbed; when high-precision gradient-based lighting is required without multi-pass overhead; on modern GPUs where ray-marching or ray-casting shaders are more efficient [S1][S2, unofficial].

## Background
This method was developed in the mid-1990s, notably by Cullip and Neumann for the Silicon Graphics RealityEngine workstations [S2, unofficial]. It builds on the concept of planar texture resampling [CCF94] and leverages the 3D texture mapping capabilities of newer-generation graphics hardware to evaluate the classic ray casting volume rendering formula in a ray-parallel fashion [S4]. It was applied to the production of digitally reconstructed radiographs and opacity-based volume rendered images [S2, unofficial]. The generality of the approach was also demonstrated in the context of the proposed PixelFlow graphics system [S2, unofficial].
