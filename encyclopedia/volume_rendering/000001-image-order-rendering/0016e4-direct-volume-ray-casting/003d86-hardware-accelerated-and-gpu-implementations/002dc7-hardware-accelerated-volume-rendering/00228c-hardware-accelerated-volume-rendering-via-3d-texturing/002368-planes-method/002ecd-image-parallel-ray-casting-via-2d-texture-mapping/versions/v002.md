# Image-Parallel Ray Casting via 2D Texture Mapping

Also called: 2D Texture Mapping Volume Rendering, Object-space technique, Slice-based Volume Rendering, Texture-Based Volume Rendering, Texture-Mapped Volume Rendering (2D)

## Overview
Image-Parallel Ray Casting via 2D Texture Mapping is an object-space volume rendering technique that accelerates direct volume rendering by projecting parallel slices of volumetric data onto the image plane and compositing them using graphics hardware rasterization and blending [S1, unofficial][S2]. It replaces standard ray casting by treating the volume as a stack of 2D texture-mapped rectangles, leveraging hardware-accelerated texture sampling and alpha blending to achieve rendering speeds dependent only on image size rather than scene complexity [S1, unofficial][S3]. Unlike its sibling [Texture-Mapped Volume Rendering with CPU Shading](3423-texture-mapped-volume-rendering-with-cpu-shading.md), this method performs the compositing entirely within the GPU pipeline using standard blending operators [S2].

## How it works
The method approximates the continuous ray casting integral by discretizing the volume into a stack of parallel planes (slices). These slices are treated as proxy geometry, as graphics hardware lacks native volumetric primitives [S1, unofficial]. The core equivalence to standard ray casting holds provided that precision is not lost due to integer arithmetic in the compositing step [S2].

### Inputs and Outputs
*   **Input:** A volumetric dataset defined on a rectilinear grid.
*   **Output:** A 2D image (framebuffer) with color and opacity values.

### Data Structures
The volume is represented as a stack of 2D texture images. Each texture image corresponds to a slice of the volume.
*   **Slice Geometry:** A polygon (typically a rectangle or complex polygon depending on viewpoint) representing the cross-section of the volume at a specific depth.
*   **Texture Image:** A 2D array of color and opacity values sampled from the volume data. The resolution of the texture matches the resolution of the slice in the volume grid.

### Steps
1.  **Slice Generation:**
    *   The volumetric data set is sliced into parallel planes.
    *   *Pre-computed Slices:* Slices are generated orthogonal to a primary axis (e.g., x, y, or z) of the data volume during a pre-processing step [S2].
    *   *View-Orthogonal Slices:* Slices are generated orthogonal to the current viewing direction for each frame [S2].
2.  **Projection:**
    *   Each slice is projected onto the image plane.
    *   If using pre-computed slices, a projection matrix maps the object-space slice to the image space [S2].
    *   If using view-orthogonal slices, the slice geometry is defined directly in view space [S2].
3.  **Rasterization and Texture Sampling:**
    *   The projected slice geometry is sent to the graphics pipeline.
    *   During rasterization, the graphics hardware resamples the color and opacity values from the 2D texture image onto the discrete pixel buffer [S1, unofficial].
    *   Values are calculated using bi-linear interpolation of the 2D texture image representing the slice [S2].
    *   *Note:* The sources indicate that using only trilinear interpolation on 3D data results in low image quality; however, this specific method uses 2D texture mapping on pre-sliced data, relying on the 2D bi-linear interpolation of the slice textures [S2, S3].
4.  **Compositing:**
    *   All texture-mapped slices are blended onto the image plane.
    *   The blending order is either front-to-back or back-to-front [S2].
    *   The standard compositing operator (alpha blending) provided by the graphics library (e.g., OpenGL) is used [S2].
    *   The result is a semi-transparent view of the volume [S1, unofficial].

```python
# Rendering Loop
for frame in frames:
    clear_framebuffer()
    
    if use_precomputed_slices:
        # Sort slices by depth relative to camera
        # Note: Pre-computed slices are object-aligned, so sorting requires 
        # transforming slice centers to view space

            setup_projection_matrix(slice_data.geometry, camera)
            
            # Bind the 2D texture representing the slice
            bind_texture(slice_data.texture)
            
            # Rasterize the geometry. Hardware interpolates texture values.
            # Blending is enabled to composite with existing framebuffer
            enable_blending()
            set_blend_function(SRC_ALPHA, ONE_MINUS_SRC_ALPHA) # Standard compositing
            draw_geometry(slice_data.geometry)
            
    else:
        # View-orthogonal approach
        # Generate slices orthogonal to viewing direction
        view_slices = generate_view_orthogonal_slices(volume, camera)
        
        # Sort slices front-to-back or back-to-front
        sorted_slices = sort_slices_by_depth(view_slices, camera)
        
        for slice_data in sorted_slices:
            # Geometry is already in view space or easily projected
            bind_texture(slice_data.texture)
            enable_blending()
            set_blend_function(SRC_ALPHA, ONE_MINUS_SRC_ALPHA)
            draw_geometry(slice_data.geometry)
```

### Parameters and Typical Values
*   **Slice Spacing:** Determined by the volume resolution. For a $512 \times 512 \times 512$ volume, there are 512 slices [S3].
*   **Interpolation:** Bi-linear interpolation is used for 2D texture sampling [S2]. Trilinear interpolation is noted as insufficient for high quality if applied directly to 3D data without pre-slicing [S3].
*   **Blending Function:** Standard alpha blending ($C_{out} = C_{src} \alpha_{src} + C_{dst} (1 - \alpha_{src})$) [S2].

### Edge Cases and Pitfalls
*   **View Direction Parallel to Slices:** If the view direction is parallel to the primary axes of pre-computed slices, the projection distorts the slice views, degrading image quality. In the extreme case where the view direction is parallel to the slices, no image is generated (the slices appear as lines or points) [S2].
*   **Complex Slice Shapes:** If slices are generated orthogonal to the viewing direction for each frame, they may have complex shapes (triangles to hexagons) and require regeneration every frame [S2].
*   **Precision Loss:** The method is exactly equivalent to standard ray casting unless precision is lost due to integer arithmetic in the compositing step [S2].
*   **Image Quality:** Using only trilinear interpolation on 3D data results in relatively low image quality, even when rendering many texture-mapped slices. Supersampling with a high-quality reconstruction filter in a pre-processing step can improve quality [S3].

## Operating characteristics
*   **Time Complexity:** Rendering speed depends only on image size, not scene complexity [S1, unofficial]. The cost is proportional to the number of slices and the image resolution.
*   **Memory Complexity:** Requires storing the volume data and potentially a stack of 2D textures. If slices are pre-computed, memory usage increases with the number of slices.
*   **Performance:** Can render large data sets (e.g., $512 \times 512 \times 512$ voxels) at interactive rates using 3D graphics hardware [S3].
*   **Strengths:** No complex hand-made geometric models are required [S1, unofficial]. Leverages highly optimized hardware routines for texture mapping and blending [S2].
*   **Limitations:** Pre-computed slices suffer from distortion at arbitrary viewpoints [S2]. View-orthogonal slices require expensive per-frame regeneration and handling of complex polygon shapes [S2]. Image quality may be lower than software ray casting if interpolation is not carefully managed [S3].

## Background
*   **Origin:** The technique is described in the context of texture-based volume rendering, an object-space technique that uses graphics hardware functionality like Rasterization, Texturing, and Blending [S1, unofficial].
*   **Development:** It is presented as a method to replace standard ray casting by projecting parallel slices of the volumetric data onto the image plane [S2]. The approach is highlighted as a simple accelerated renderer for rectilinear grids [S3].
*   **Usage:** Used for direct volume rendering of large datasets, such as the "electron density" of a C-60 Buckminsterfullerene molecule [S3].
