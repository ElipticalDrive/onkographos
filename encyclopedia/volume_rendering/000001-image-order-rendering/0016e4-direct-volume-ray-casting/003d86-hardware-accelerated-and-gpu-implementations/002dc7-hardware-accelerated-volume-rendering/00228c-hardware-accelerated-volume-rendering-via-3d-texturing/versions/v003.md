# Hardware-Accelerated Volume Rendering via 3D Texturing

Also called: 3D Texture Mapping Volume Rendering, 3D Texturing Example, Planar Texture Resampling, Polygon Resampling with 3D Texturing, RealityEngine 3D Texture Volume Rendering, RealityEngine Volume Rendering, Texture Mapping for Volume Rendering

## Overview
This method leverages 3D texture mapping hardware to evaluate the volume rendering integral in a ray-parallel fashion by resampling volumetric data into textured planes [S1][S2, unofficial]. It solves the performance bottleneck of software ray casting by offloading the computationally intensive trilinear interpolation and resampling steps to the graphics hardware, while typically delegating shading and compositing to the CPU or frame buffer [S1][S2, unofficial]. Unlike [Shear-Warp](link-to-shear-warp), which performs classification before bilinear resampling and requires a final warp step, this method performs trilinear interpolation followed by classification and requires no final warp, resulting in higher image quality and consistent performance for perspective projections [S1]. It builds on [Direct volume ray casting](19-direct-volume-ray-casting.md) by using the front-to-back accumulation model but delegates the execution to hardware units [Parent].

## How it works
**Inputs and Outputs:**
*   **Input:** 3D volume data (scalar field), viewing parameters (camera position, orientation, projection), and transfer function parameters (opacity, color, exposure).
*   **Output:** 2D image in the frame buffer.

**Data Structures:**
*   **3D Texture Memory:** The volume data is stored in hardware 3D texture memory. In high-performance engines like the SGI Reality Engine, this uses 8-way interleaved memory to allow fetching any tri-linear cell (8 adjacent voxels) in one memory access [S1].
    *   **Memory Layout:** For a voxel with address $a = [zyx]$ in an 8-way interleaved system, the memory module number $k$ and index $i$ within the module are calculated as [S1]:
        $$k = (x \bmod 2) + 2 (y \bmod 2) + 4 (z \bmod 2)$$
        $$i = \lfloor x/2 \rfloor + 2 \lfloor y/2 \rfloor + 4 \lfloor z/2 \rfloor$$
*   **Resampling Polygons:** Planar polygons embedded in the texture define the sampling planes. Two alignment strategies exist:
    *   **Object-Space:** Polygons are defined within the volume coordinate system. They must be reoriented in the plane most parallel to the view-plane as the viewpoint changes, requiring explicit creation for six view orientation cases [S2, unofficial].
    *   **Image-Space:** Polygons are defined in image space and transformed by the inverse viewing matrix into object space. They must be clipped to the volume boundaries to ensure valid texture coordinates [S2, unofficial].
*   **Lookup Tables (LUTs):** Used to map resampled density values to RGBA color and opacity [S1].

**Parameters:**
*   **Interpolation:** Tri-linear interpolation is used by the texture engine [S1].
*   **Exposure:** A user-controlled scaling factor (range 0 to 1) applied to resampled values to prevent overflow in the 12-bit frame buffer [S2, unofficial].
*   **Spacing ($d$):** The distance between sample values. $d$ is constant for all samples behind a pixel but varies from pixel to pixel due to perspective [S2, unofficial].
*   **Texture Memory Limit:** The RealityEngine supports up to 1,000,000 (1M) 12-bit data points. Larger volumes are split into slabs [S2, unofficial].

**Steps:**
1.  **Load Volume:** Load volume data into 3D texture memory. If the volume exceeds 1M 12-bit points, split into slabs and render them in succession [S2, unofficial].
2.  **Configure Texture:**
    *   Set global texture environment mode to `GL_MODULATE` [S3, unofficial].
    *   Enable 3D texturing [S3, unofficial].
    *   Bind the 3D texture object `texid` [S3, unofficial].
    *   Switch matrix mode to `GL_TEXTURE` [S3, unofficial].
    *   Apply a translation of $(0.5, 0.5, 0.5)$ to the texture matrix to correct for texture coordinate centering [S3, unofficial].
    *   Reset texture matrix to identity if necessary before applying view-dependent transforms [S3, unofficial].
3.  **Define and Render Polygons:**
    *   For each resampling plane (slice):
        *   Define polygon vertices $(x_i, y_i, z_i)$ for $i=0..3$ [S3, unofficial].
        *   Set 3D texture coordinates for each vertex to $(x_i, y_i, z_i)$ [S3, unofficial].
        *   Set vertex positions to $(x_i, y_i, z_i)$ [S3, unofficial].
        *   Render the polygon using standard graphics library calls (e.g., `GL_QUADS`) [S2, unofficial]. The hardware performs trilinear interpolation at each point on the polygon [S2, unofficial].
4.  **Scale and Accumulate:**
    *   Scale each resampled value by the 'exposure' value [S2, unofficial].
    *   Sum the scaled resampled values at each pixel [S2, unofficial].
    *   Clamp the sum if it exceeds the 12-bit range [S2, unofficial].
    *   Apply spacing factors ($d$) to the summation results. This is often done using an additional full-screen polygon with a 2D texture corresponding to the $d$ values for each pixel [S2, unofficial].
5.  **Final Compositing/Shading:**
    *   Combine resampled values to produce final pixel color. Options include:
        *   **Direct Summation:** For simple attenuation.
        *   **Radiographs:** Compute $1.0 - \exp(-\sum u_i d)$ using a lookup table for the exponential [S2, unofficial].
        *   **Opacity-Based Rendering:** Use two 8-bit texture components (raw data and precomputed shading coefficient). Use resampled data as indices into an opacity LUT. Multiply sample opacity by the shading coefficient (function of original data gradient) [S2, unofficial].
6.  **Cleanup:**
    *   Switch matrix mode back to `GL_MODELVIEW` [S3, unofficial].
    *   Unbind the 3D texture (bind texture ID 0) [S3, unofficial].
    *   Disable 3D texturing [S3, unofficial].

**Pseudocode:**

**Edge Cases and Pitfalls:**
*   **Overflow:** The RealityEngine has a maximum precision of 12 bits per frame buffer and texture component. Summation can overflow this limit. Solution: Scale samples by 'exposure' value and clamp [S2, unofficial].
*   **Clipping:** Image-space polygons must be clipped to volume boundaries to ensure valid texture coordinates. This requires transforming to object-space, clipping, and then rendering [S2, unofficial].
*   **Slab Rendering:** When using image-space method with slabs, polygons must be rendered multiple times, clipped to the currently loaded volume slab each time [S2, unofficial].
*   **Shading Limitations:** Hardware does not directly support estimation of gradients or per-sample illumination. Gradients must be pre-computed and stored in an additional volume or computed on-the-fly using multi-pass methods, which greatly reduce achievable frame rate [S1]. An alternative is pairwise subtraction of coplanar texture slices [S1].

## Subtopics

### [Planes Method](3027-planes-method.md)
The Planes Method is a hardware-accelerated volume rendering technique that leverages 3D texture mapping hardware to resample volumetric data into planes coplanar with rays ending in a row of pixels, then performs shading and front-to-back compositing on the CPU. It solves the problem of view-dependent shading and interactive classification in texture-mapped rendering by offloading the computationally intensive Phong shading and compositing logic to the processor, allowing for optimization techniques like early ray termination and low-opacity skipping. Unlike [Shear-Warp](link-to-shear-warp), which performs classification before bilinear resampling and requires a final warp step, the Planes method performs trilinear interpolation followed by classification and requires no final warp, resulting in higher image quality and consistent performance for perspective projections.

### BVH-accelerated 3D Texture Volume Rendering
A method to accelerate 3D texture-based volume rendering using hierarchical bounding volumes (BVH) to skip rendering of empty or occluded sub-volumes during tree traversal [S5, abstract only, unofficial]. It realizes post-classification 3D texture volume rendering using GPU fragment shaders. The original volume data is divided based on space position layer by layer according to the height of the BVH tree. In each layer, volumes corresponding to BVH tree nodes are subdivided into eight sub-volumes along three orthogonal coordinate axes. Bounding volumes are established for the sub-volumes and stored in the BVH tree nodes. When rendering, the BVH tree is traversed to judge whether the corresponding sub-volume should be rendered or jumped [S5, abstract only, unofficial].

## Operating characteristics
*   **Time Complexity:** Performance is linear with respect to the number of pixels processed. Doubling screen pixels or resampling polygons halves the frame rate [S2, unofficial].
*   **Memory Complexity:** Limited by hardware texture memory capacity (e.g., 1M 12-bit points on RealityEngine). Larger volumes require slab loading, adding overhead (~0.1 seconds per slab reload) [S2, unofficial].
*   **Measured Performance:**
    *   SGI Reality Engine 2 with two Rasters Managers (RMs) renders a 256x256x32 volume at 12 frames per second [S1].
    *   SGI Reality Engine 2 with four RMs renders a 512x512x64 dataset at 10 frames per second [S1].
    *   128x128x64 volume rendered into 512x512 window at 10 frames/second using 128 object-space polygons (10 million voxels/second, ~160 million pixel operations/second) [S2, unofficial].
    *   256x256x64 volume rendered into 512x512 window at 2.5 frames/second using 256 resampling polygons [S2, unofficial].
    *   Can render volume data about 512 x 512 x 512 voxels in size several times a second, achieving results very close in quality to software ray casting [S4].
*   **Strengths:** High performance for large volumes; leverages existing 3D graphics hardware; simple implementation [S2, unofficial].
*   **Limitations:** Limited by texture memory size; shading is restricted (no per-sample illumination without pre-computation); quality vs. speed trade-off (more polygons = higher quality, lower speed) [S2, unofficial].
*   **When to use:** Interactive visualization of large medical or scientific datasets on hardware with 3D texturing support (e.g., SGI RealityEngine, PixelFlow) [S2, unofficial].
*   **When not to use:** When complex per-sample lighting is required without pre-computation; when texture memory limits prevent loading the entire volume without excessive slab reloading [S2, unofficial].

## Background
This method was developed in the mid-1990s, notably by Cullip and Neumann at the University of North Carolina at Chapel Hill, and implemented on Silicon Graphics RealityEngine workstations [S2, unofficial]. It builds on the concept of planar texture resampling [CCF94] and utilizes the 3D texturing capabilities of early 3D graphics accelerators [S4]. The approach was also proposed for the PixelFlow graphics system to overcome lighting and volume size limitations of the RealityEngine [S2, unofficial]. It represents a significant step in hardware-accelerated volume rendering by delegating resampling to the texture unit [S1][S2, unofficial].
