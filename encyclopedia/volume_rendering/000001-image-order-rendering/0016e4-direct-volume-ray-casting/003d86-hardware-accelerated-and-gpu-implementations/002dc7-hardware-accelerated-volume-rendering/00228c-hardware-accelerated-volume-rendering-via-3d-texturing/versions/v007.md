# Hardware-Accelerated Volume Rendering via 3D Texturing

Also called: 3D Texture Mapping Volume Rendering, 3D Texturing Example, Planar Texture Resampling, Polygon Resampling with 3D Texturing, RealityEngine 3D Texture Volume Rendering, RealityEngine Volume Rendering, Texture Mapping for Volume Rendering

## Overview
This method accelerates direct volume ray casting by storing volumetric data in 3D texture memory and using graphics hardware to resample the volume along textured polygons [S1][S2, unofficial]. It solves the computational bottleneck of per-sample interpolation and shading by offloading the reconstruction and resampling steps to the texture engine, which performs trilinear interpolation in parallel across the polygon [S4]. Unlike software ray casting, it achieves interactive frame rates by evaluating the ray casting formula in a ray-parallel fashion, though it is limited by the fixed precision and memory capacity of the underlying 3D texture hardware [S2, unofficial][S4].

## How it works
**Inputs and Outputs**
*   **Input:** A 3D volume dataset (density/attenuation values), a viewing matrix, and rendering parameters (exposure, classification tables).
*   **Output:** A 2D image in the frame buffer, where each pixel contains the accumulated color and opacity from the volume samples along the corresponding ray.

**Data Structures**
*   **3D Texture Memory:** The volume is stored as a 3D texture object. In high-performance architectures like the SGI RealityEngine, memory is 8-way interleaved to allow fetching any tri-linear cell (8 adjacent voxels) in a single memory access [S1].
    *   **Voxel Addressing:** For a voxel with address $a = [zyx]$ in an 8-way interleaved system, the memory module number $k$ and index $i$ are calculated as [S1]:
        $$k = (x \bmod 2) + 2 (y \bmod 2) + 4 (z \bmod 2)$$
        $$i = \lfloor x/2 \rfloor + 2 \lfloor y/2 \rfloor + 4 \lfloor z/2 \rfloor$$
*   **Lookup Tables (LUT):** Maps density values to RGBA color and opacity. For opacity-based rendering, two 8-bit components are often used: raw data and a precomputed shading coefficient [S2, unofficial].
*   **Resampling Polygons:** Planar polygons embedded in the texture define the sampling planes. Two alignment strategies exist [S2, unofficial]:
    *   **Object-Space:** Polygons are defined within the volume coordinate system. They must be reoriented in the plane most parallel to the view-plane as the viewpoint changes, requiring explicit creation for six view orientation cases [S2, unofficial].
    *   **Image-Space:** Polygons are defined in image-space and transformed by the inverse viewing matrix into object-space. They must be clipped to the volume boundaries to ensure valid texture coordinates [S2, unofficial].

**Parameters**
*   **Interpolation:** Tri-linear interpolation is used by the texture engine [S1][S2, unofficial].
*   **Exposure:** A user-controlled scaling factor (range 0 to 1) applied to resampled values to prevent overflow in the 12-bit frame buffer [S2, unofficial].
*   **Spacing Factor ($d$):** The distance between sample values. It is constant for all samples behind a pixel but varies per pixel due to perspective [S2, unofficial].
*   **Memory Limit:** The RealityEngine texture memory is limited to 1,000,000 (1M) 12-bit data points [S2, unofficial].

**Algorithm Steps**
1.  **Load Volume:** Load the volume data into 3D texture memory. If the volume exceeds 1M points, split it into slabs and render them in succession [S2, unofficial].
2.  **Configure Texture:** Enable 3D texturing and set the global texture environment mode to `GL_MODULATE` [S3, unofficial]. Bind the 3D texture object [S3, unofficial].
3.  **Setup Texture Matrix:** Switch to the texture matrix mode, apply a translation of $(0.5, 0.5, 0.5)$ to align texture coordinates with voxel centers, and switch back to the modelview matrix [S3, unofficial].
4.  **Define Resampling Polygons:** Create polygons based on the chosen alignment strategy (Object-Space or Image-Space) [S2, unofficial].
    *   *Note:* For Image-Space, transform polygons by the inverse view matrix and clip them to volume boundaries [S2, unofficial].
5.  **Render Polygons:** Render the polygons using standard graphics library calls. The hardware resamples the volume data at each point on the polygon using tri-linear interpolation [S2, unofficial].
    *   *Vertex Setup:* For each vertex $i$ (0 to 3), set the 3D texture coordinate to $(x_i, y_i, z_i)$ and the vertex position to $(x_i, y_i, z_i)$ [S3, unofficial].
6.  **Scale and Sum:** Scale each resampled value by the exposure value. Sum the scaled values at each pixel [S2, unofficial].
    *   *Spacing Application:* Apply spacing factors ($d$) to the summation results. This is typically done by rendering an additional full-screen polygon with a 2D texture containing the $d$ values for each pixel [S2, unofficial].
7.  **Combine and Output:** Combine resampled values to produce the final pixel color. Options include:
    *   **Direct Summation:** For simple density visualization.
    *   **Radiographs:** Compute the exponential of the summed attenuation integral: $\text{Intensity} = 1.0 - \exp(-\sum u_i d)$, where $u_i$ are resampled values [S2, unofficial]. This can be done via a lookup table [S2, unofficial].
    *   **Opacity-Based:** Use the resampled data as indices into an opacity LUT. Multiply sample opacity by a precomputed shading coefficient (derived from data gradients) to produce shaded features [S2, unofficial].
8.  **Cleanup:** Unbind the 3D texture and disable 3D texturing [S3, unofficial].

**Pseudocode**
```python
def render_volume_3d_texturing(volume_data, view_matrix, exposure, num_polygons):
    # 1. Load volume into 3D texture memory
    # If volume size > 1M voxels, split into slabs and iterate
    texture_id = load_3d_texture(volume_data)
    
    # 2. Configure texture environment
    set_texture_env_mode(GL_MODULATE)
    enable_texture_3d()
    bind_texture(texture_id)
    
    # 3. Setup texture matrix for voxel center alignment
    switch_matrix_mode(GL_TEXTURE)
    load_identity()
    translate(0.5, 0.5, 0.5)
    switch_matrix_mode(GL_MODELVIEW)
    
    # 4. Generate resampling polygons
    # Strategy: Object-Space or Image-Space
    polygons = generate_resampling_polygons(view_matrix, volume_bounds, num_polygons)
    
    # 5. Render polygons
    for polygon in polygons:
        # Hardware performs tri-linear interpolation at each vertex/fragment
        begin_polygon()
        for vertex in polygon.vertices:
            set_texture_coord_3d(vertex.x, vertex.y, vertex.z)
            set_vertex_3d(vertex.x, vertex.y, vertex.z)
        end_polygon()
        
    # 6. Apply spacing factors and exposure
    # Note: In fixed-function hardware, this is often done via a second pass
    # with a full-screen quad using a 2D texture for 'd' values and 
    # multiplying by 'exposure' in the fragment shader or texture env.
    apply_spacing_and_exposure(exposure)
    
    # 7. Composite/Combine
    # For radiographs: Intensity = 1.0 - exp(-sum(u_i * d))
    # For opacity: Use LUTs for color/alpha, multiply by shading coeff
    composite_into_framebuffer()
    
    # 8. Cleanup
    bind_texture(0)
    disable_texture_3d()
    return frame_buffer
```

## Subtopics

### [Planes Method](3027-planes-method.md)
The Planes Method is a specific implementation of 3D texturing volume rendering that resamples volumetric data into planes coplanar with rays ending in a row of pixels, then performs shading and front-to-back compositing on the CPU. It solves the problem of view-dependent shading and interactive classification by offloading Phong shading and compositing logic to the processor, allowing for optimizations like early ray termination and low-opacity skipping. Unlike Shear-Warp, which performs classification before bilinear resampling and requires a final warp step, the Planes method performs trilinear interpolation followed by classification and requires no final warp, resulting in higher image quality and consistent performance for perspective projections.

### BVH-accelerated 3D Texture Volume Rendering
A method to accelerate 3D texture-based volume rendering using hierarchical bounding volumes (BVH) to skip rendering of empty or occluded sub-volumes during tree traversal [S5, abstract only, unofficial]. It realizes post-classification 3D texture volume rendering using GPU fragment shaders, divides the volume data layer by layer according to the BVH tree height, and subdivides nodes into eight sub-volumes along orthogonal axes [S5, abstract only, unofficial]. Bounding volumes are established for these sub-volumes, and during rendering, the BVH tree is traversed to judge whether a sub-volume should be rendered or skipped, obtaining good accelerating effects when combined with GPU-based 3D texture rendering [S5, abstract only, unofficial].

## Operating characteristics
*   **Time Complexity:** Performance is linear with respect to the number of pixels processed and the number of resampling polygons. Doubling the screen pixels or the number of polygons halves the frame rate [S2, unofficial].
*   **Memory Complexity:** Limited by the texture memory capacity (e.g., 1M 12-bit points on RealityEngine) [S2, unofficial]. Larger volumes require slabbing, adding a reload overhead of ~0.1 seconds per slab [S2, unofficial].
*   **Measured Performance:**
    *   SGI Reality Engine 2 with two Rasters Managers (RMs): 256x256x32 volume at 12 fps [S1].
    *   SGI Reality Engine 2 with four RMs: 512x512x64 dataset at 10 fps [S1].
    *   RealityEngine: 128x128x64 volume into 512x512 window at 10 fps using 128 object-space polygons (10 million voxels/sec, ~160 million pixel ops/sec) [S2, unofficial].
    *   RealityEngine: 256x256x64 volume into 512x512 window at 2.5 fps using 256 polygons and four slabs [S2, unofficial].
    *   Modern hardware can render ~512x512x512 voxels several times a second with quality close to software ray casting [S4].
*   **Strengths:** High performance for interactive visualization; leverages existing 3D graphics hardware; simple implementation [S2, unofficial].
*   **Limitations:** Fixed precision (12-bit) leads to overflow risks; no direct hardware gradient estimation for per-sample illumination; limited texture memory requires slabbing for large volumes; image-space method requires complex clipping [S1][S2, unofficial].
*   **When to use:** Interactive visualization of moderate-sized volumes on hardware with 3D texturing support; production of digitally reconstructed radiographs [S2, unofficial].
*   **When not to use:** When high-precision per-sample lighting is required without pre-computation; when volumes exceed hardware memory significantly and slabbing overhead is prohibitive; when arbitrary ray paths (not planar slices) are needed for maximum accuracy [S1][S2, unofficial].

## Background
This method originated with the development of 3D texture mapping hardware in the early 1990s, specifically on Silicon Graphics RealityEngine workstations [S2, unofficial]. It was formalized as "Planar Texture Resampling" by Cullip and Neumann [S2, unofficial] and further analyzed by Westover [S1]. The technique was proposed for future graphics systems like PixelFlow to overcome lighting and volume size limitations [S2, unofficial]. It represents one of the earliest successful applications of general-purpose 3D graphics hardware to scientific visualization [S4].
