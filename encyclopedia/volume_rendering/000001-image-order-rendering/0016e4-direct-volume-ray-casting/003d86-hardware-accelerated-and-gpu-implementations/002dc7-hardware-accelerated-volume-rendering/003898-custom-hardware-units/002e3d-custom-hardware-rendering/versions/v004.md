# Custom Hardware Rendering
## Overview
Custom Hardware Rendering is a direct volume rendering technique implemented via custom hardware rather than general-purpose processors [S2, unofficial]. It addresses the historical demand for real-time volume rendering systems when CPUs and GPUs lacked sufficient throughput [S1]. Unlike software-based approaches, these systems offload the rendering pipeline to fixed-function hardware, achieving interactive frame rates for regular data sets through highly parallel computation [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** 3D scalar volume data (regular grids), transfer functions, and camera parameters [G].
*   **Output:** 2D color image frame buffer [G].

**Data Structures:**
*   **Volume Data:** Stored in on-chip memory or high-bandwidth external memory [S1]. Voxel processors traverse the data slice-by-slice in memory order [S1].
*   **On-chip Buffers:** Used to store intermediate voxel slices or sample results between processing stages [S1].
*   **Exact Layouts:** Fields, sizes, and bit packing are not given in the sources.

**Algorithm Steps:**
1.  **Pipeline Configuration:** The hardware is configured with a specific number of identical rendering pipelines [S1]. For example, the Cube architecture utilized eight identical pipelines [S1].
2.  **Voxel Processing (Traversal):** Voxel processors traverse the volume data slice-by-slice in memory order, fetching voxel values and performing initial classification or filtering [S1].
3.  **Sample Processing (Compositing):** Sample processors traverse the on-chip buffers to perform illumination, filtering, and compositing [S1].
4.  **Image Warping/Rendering:** In hybrid-order algorithms like Cube, the hardware computes only the shear step on-board, while a graphics board handles the warp and final image rendering [S1].

**Formulas:**
Exact compositing equations are not given in the sources. The compositing step combines sample color and opacity to update the accumulated pixel color and opacity [G].

**Parameters:**
*   **Pipeline Count:** The number of parallel pipelines determines throughput [S1]. Cube used 8 pipelines [S1].
*   **Resolution Support:** Systems were designed for specific resolutions, e.g., Cube rendered a $256^3$ volume [S1].
*   **Frame Rate:** Cube achieved 30 fps for the specified resolution [S1].

**Edge Cases and Pitfalls:**
*   **Memory Limitations:** Custom hardware shares the limited memory constraint of GPUs [S1]. Out-of-core solutions are generally not viable due to the high memory bandwidth required for real-time rendering [S1].
*   **Rigidity:** Changing or extending the hardware logic is tedious and costly, as it requires physical redesign or reconfiguration of the hardware [S1].
*   **Perspective Limitations:** Early systems like Cube and VolumePro did not support perspective rendering, limiting their applicability to orthographic views [S1].

## Operating characteristics
*   **Performance:** Achieved real-time frame rates (e.g., 30 fps for a $256^3$ volume on Cube) due to highly regular computation and parallel pipelines [S1].
*   **Scalability:** Scalability was enhanced in later generations (VolumePro), but perspective rendering remained unsupported in early custom hardware [S1].
*   **Memory:** Limited by on-chip or dedicated high-bandwidth memory; not suitable for out-of-core rendering [S1].
*   **Flexibility:** Low. Hardware is fixed-function, making updates expensive and difficult [S1].
*   **Use Case:** Best suited for static, regular grid data where maximum throughput is required and perspective viewing is not critical [S1]. Not suitable for irregular data or dynamic algorithm changes [G].

## Background
Custom hardware rendering emerged in the late 1990s when CPUs and GPUs could not meet the real-time requirements for volume rendering [S1]. Key systems included Cube [KK99], Vizard [KS97], and VolumePro [PHK* 99] [S1]. Cube, based on a Shear-Warp hybrid algorithm, was the predecessor to VolumePro [S1]. VolumePro evolved to include separate sample and voxel processing pipelines, improving scalability but still lacking perspective support in its earlier generations [S1]. These systems were developed for rendering regular data sets [S1].
