# Hardware Shading via Pixel Texture

Also called: Quantized Normal Shading

## Overview
This method accelerates direct volume ray casting by integrating surface shading into texture-memory based rendering pipelines, addressing the common lack of shading in early hardware-accelerated volume renderers [S1]. It distinguishes itself from sibling methods by encoding surface normals into a 2D pixel texture using 16-bit quantization and nearest-neighbor interpolation, thereby avoiding hardware interpolation redundancy and truncation errors [S1, S2]. Unlike [3D Pixel Texture Classification](6055-3d-pixel-textification.md) which may use different classification strategies, this approach specifically targets the shading stage to enhance shape perception with negligible performance cost [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A volume dataset (scalar values $V$, gradients $G$, and potentially hue $H$), a view direction, and a lighting model.
*   **Output:** A shaded, composited image where surface normals are derived from the volume gradient and shaded using a pre-computed pixel texture.

**Data Structures:**
*   **Shading Pixel Texture:** A 2D texture where each texel stores a quantized surface normal.
    *   **Layout:** The normal vector $\mathbf{n}$ is quantized to 16 bits.
    *   **Channel Packing:** The first 8 bits of the quantized normal are stored in the Red channel ($R$), and the second 8 bits are stored in the Green channel ($G$). The Blue and Alpha channels are unused or reserved for other metadata depending on the specific hardware implementation [S1, S2].
*   **Scratch/Auxiliary Buffer:** A temporary frame buffer used to render individual slices before compositing, required because pixel texture operations often do not occur directly on a per-fragment basis during rasterization on older hardware (e.g., SGI Octane2) [S2].

**Steps:**
1.  **Normal Quantization:** For each sample point in the volume, compute the surface normal $\mathbf{n}$ from the gradient. Encode $\mathbf{n}$ using a 16-bit quantization scheme [S1, S2].
2.  **Texture Generation (Per-View):** Generate the shading pixel texture on a per-view basis in software. This involves mapping the quantized normals to the 2D texture coordinates [S1, S2].
    *   *Alternative Hardware Method:* Render quantized normals as points with hardware lighting and copy the result from the frame buffer to the pixel texture. Note: Some hardware implementations are not flexible enough to support this operation [S2].
3.  **Slice Rendering:** Render a slice of the volume data to the scratch/auxiliary buffer.
    *   If shading is enabled, render the corresponding slice from the shading volume (containing the quantized normals) and modulate (multiply) it with the current data slice [S2].
4.  **Pixel Texture Operation:** Use a `glCopyPixels()` operation to copy the slice from the scratch buffer to the pixel texture. This step applies the lighting lookup using the 2D pixel texture, which is equivalent to a 16-bit 1D nearest-neighbor lookup [S1, S2].
5.  **Compositing:** Copy the shaded slice from the scratch buffer and blend it with previously rendered slices in the frame buffer using the standard front-to-back compositing equation defined in the parent article [S2].

**Formulas:**
The shading lookup is effectively a texture lookup where the quantized normal serves as the coordinate. There is no explicit lighting formula provided in the sources, as the shading is pre-computed into the pixel texture [S1, S2]. The compositing follows the parent's optical model:
$$
C'_{i} = C'_{i-1} + (1 - \alpha'_{i-1}) \alpha_i C_i
$$
$$
\alpha'_{i} = \alpha'_{i-1} + (1 - \alpha'_{i-1}) \alpha_i
$$
where $C_i$ is the shaded color of the current sample [S1, S2].

**Parameters:**
*   **Quantization Scheme:** 16-bit encoding for normals [S2].
*   **Interpolation:** Nearest-neighbor interpolation for pixel texture lookup to avoid redundancy/truncation [S1, S2].

**Edge Cases and Pitfalls:**
*   **Hardware Flexibility:** Some hardware implementations (e.g., specific configurations of the SGI Octane2) do not support rendering quantized normals as points with hardware lighting and copying to a pixel texture, necessitating the software-based generation of the shading texture [S2].
*   **Performance Cost:** While the shading generation is minimal, it must be done per-view if the viewpoint changes [S1].
*   **Transfer Function Manipulation:** When the transfer function is manipulated, the view point is typically static. In this case, the pixel texture operation only needs to be applied to the portion of the volume currently changing, using raw data values ($VGH$) for the volume texture and a pre-computed RGBA shade volume [S2].

## Subtopics

### Quantized Normal Shading via Pixel Texture
A specific implementation variant that explicitly encodes surface normals into a 2D pixel texture to avoid hardware interpolation redundancy and truncation, using nearest-neighbor interpolation [S2]. It differs from general shading methods by relying on a 2D pixel texture lookup for lighting, which is mathematically equivalent to a 16-bit 1D nearest-neighbor lookup [S1]. Choose this variant when using older graphics hardware (like SGI Octane2 or early GeForce3) that lacks efficient hardware normal interpolation but supports pixel texture operations via `glCopyPixels` [S2]. It is linked to [Hardware Shading via Pixel Texture](7444-hardware-shading-via-pixel-texture.md).

### Line Bundles
A technique relying on graphics hardware to create texture by rendering and compositing many semitransparent line segments to produce an anisotropic volume rendering result [S3, unofficial]. Unlike the normal-based shading of the parent method, Line Bundles render pre-computed sets of line segments for each data point (splatting analogy) and slightly perturb their colors to provide a colored pattern [S3, unofficial]. It is chosen when visualizing flow fields where directionality is as important as magnitude, as it clearly evidences directionality unlike standard volume rendering [S3, unofficial]. It is linked to [Hardware Shading via Pixel Texture](7444-hardware-shading-via-pixel-texture.md).

## Operating characteristics
*   **Time Complexity:** The shading texture generation is performed per-view in software, but the cost is described as minimal [S1]. The rendering pipeline involves standard slice rendering and compositing, with an additional `glCopyPixels` operation [S2].
*   **Memory Complexity:** Requires an auxiliary scratch buffer for each slice and a 2D pixel texture for shading [S2].
*   **Measured Performance:** Implemented on SGI Octane 2 with V series graphics cards and nVidia GeForce3 series [S2]. The performance cost of adding shading is negligible [S1].
*   **Strengths:** Dramatically increases rendering quality by expressing shape information with negligible cost [S1]. Avoids hardware interpolation artifacts [S1, S2].
*   **Limitations:** Dependent on hardware support for pixel texture operations; some hardware cannot support the point-rendering alternative [S2]. Requires per-view texture generation if the viewpoint changes [S1].
*   **When to Use:** When using texture-memory based volume rendering and shading is desired to improve shape perception, particularly on older hardware [S1].
*   **When Not to Use:** When hardware does not support the required pixel texture operations or when real-time per-fragment shading is available and preferred [S2].

## Background
The method originated from work on Interactive Volume Rendering Using Multi-Dimensional Transfer Functions, specifically addressing the lack of shading in texture-memory based volume rendering [S1]. It was implemented on SGI Octane 2 and nVidia GeForce3 hardware [S2]. The Line Bundles variant was developed by Crawfis, Shen, and Max for flow visualization, allowing the viewing of velocity magnitude with clear directionality [S3, unofficial].
