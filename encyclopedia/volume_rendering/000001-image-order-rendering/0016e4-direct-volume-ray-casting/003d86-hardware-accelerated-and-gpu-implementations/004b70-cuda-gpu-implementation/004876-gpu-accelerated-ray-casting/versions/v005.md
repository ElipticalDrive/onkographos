# GPU-accelerated ray casting

Also called: CUDA Raycasting Kernel, GPU raycasting algorithm, CUDA Grid/Block Raycasting, Many-Core GPU Implementation

## Overview
GPU-accelerated ray casting is a direct volume rendering method that offloads ray traversal and compositing to a graphics processing unit (GPU) to achieve real-time frame rates [S2]. It differs from CPU-based approaches by leveraging massive parallelism, where each thread handles a single pixel, making it an embarrassingly parallel standard image-order approach [S4, unofficial]. It builds on [CUDA GPU Implementation](13016-cuda-gpu-implementation.md) by explicitly mapping the image grid to CUDA thread blocks and utilizing hardware features like context switching to hide memory latency [S2].

## How it works
**Inputs and Outputs:**
- Input: A 3D volumetric data set $V$, a camera view (eye point, direction), and a transfer function mapping scalar values to color and opacity [G].
- Output: A 2D image of resolution $W \times H$ [G].

**Data Structures:**
- **Thread Block Layout:** The image is treated as a 2D CUDA grid divided into thread blocks [S2]. An $M \times N$ thread block corresponds to an $M \times N$ pixel image tile [S2].
- **Memory Layout:** The source volume $S$ can be stored in array-order or Z-order [S2].
    - Array-order: $S[i, j, k]$ is at memory location $i + j \cdot xsize + k \cdot xsize \cdot ysize$ [S2].
    - Z-order: A 1D layout of a $2^n$ tree where nearby index space points are nearby in physical memory, computed via the formulation by Pascucci and Frank [S2].

**Steps:**
1. **Ray-Bounding Box Intersection:** Calculate the entry ($p_{in}$) and exit ($p_{out}$) points of the ray intersecting the volume bounding box by rendering the bounding box twice: once culling front faces and once culling back faces [S2].
2. **Thread Assignment:** The CUDA runtime dynamically schedules thread blocks, assigning up to eight blocks at a time to each of the GPU’s multiprocessors [S2].
3. **Ray Marching and Compositing:** Each individual CUDA thread performs raycasting for a single pixel [S2].
4. **Resampling and Shading:** Perform resampling and compositing on the shader to reduce running time [S2].
5. **Optimizations:** The method uses parallelization, empty space skipping, early ray termination, and pre-integration for quality [S1].

**Pseudocode:**
```python
def gpu_ray_cast_kernel(thread_id, block_id, block_dims, image_dims, volume_texture, transfer_function, camera_matrix, bounding_box, resolution, framebuffer):
    block_width, block_height = block_dims
    image_width, image_height = image_dims
    pixel_x = block_id.x * block_width + thread_id.x
    pixel_y = block_id.y * block_height + thread_id.y

    if pixel_x >= image_width or pixel_y >= image_height:
        return

    # [G] Standard camera setup
    ray_origin = (0.0, 0.0, 0.0)
    ray_direction = normalize(camera_matrix * (pixel_x, pixel_y, 0.0))

    # [S2] Calculate ray-bounding box intersections
    p_in, p_out = calculate_ray_bbox_intersection(ray_origin, ray_direction, bounding_box)

    # [G] Initialize compositing
    accumulated_color = (0.0, 0.0, 0.0, 0.0)
    t = 0.0
    step_size = distance(p_in, p_out) / resolution

    # [S2] Ray march and compositing
    while t < distance(p_in, p_out):
        current_pos = ray_origin + ray_direction * t
        scalar_value = sample_volume(volume_texture, current_pos)
        color, opacity = apply_transfer_function(scalar_value, transfer_function)
        accumulated_color = composite(accumulated_color, color, opacity)
        t += step_size

    # [G] Write result
    framebuffer[pixel_y * image_width + pixel_x] = accumulated_color

def calculate_ray_bbox_intersection(ray_origin, ray_direction, bounding_box):
    # [S2] Render bounding box twice: front culling for p_in, back culling for p_out
    p_in = render_bbox_front_culled(ray_origin, ray_direction, bounding_box)
    p_out = render_bbox_back_culled(ray_origin, ray_direction, bounding_box)
    return p_in, p_out

def normalize(v):
    length = sqrt(v[0]**2 + v[1]**2 + v[2]**2)
    return (v[0]/length, v[1]/length, v[2]/length)

def distance(a, b):
    return sqrt((a[0]-b[0])**2 + (a[1]-b[1])**2 + (a[2]-b[2])**2)

def sample_volume(texture, pos):
    # [G] Tri-linear interpolation
    return texture.trilinear_sample(pos)

def apply_transfer_function(scalar, tf):
    # [G] Transfer function lookup
    return tf.lookup(scalar)

def composite(acc, color, opacity):
    # [G] Front-to-back compositing
    alpha_out = acc[3] + (1.0 - acc[3]) * opacity
    color_out = acc[:3] + (1.0 - acc[3]) * opacity * color
    return color_out + (0.0,) + (alpha_out,)
```

**Parameters:**
- **CUDA Version:** 3.2 compiler and runtime [S2].
- **NVIDIA Driver:** Version 270.41.19 [S2].
- **Compute Capability:** Targeted at 2.0 (Fermi-series) for additional optimizations [S2].
- **Shared Memory:** Configured to be used as L1 cache for global memory requests [S2].
- **ECC Support:** Enabled [S2].

**Edge Cases and Pitfalls:**
- **Memory Latency:** The GPU uses hardware context switches between blocks within a multiprocessor to hide memory latency [S2].
- **Data Size Scaling:** While computational complexity for interpolation and compositing is approximately constant for the same viewpoint, processing time shows a slowly wavelike rising trend as data set size increases due to increased RAM/graphics card memory addressing time and varying computing resources [S2].
- **Performance Variance:** Final speed is dependent on the nature of volumetric data and classification settings [S1].

## Operating characteristics
- **Time Complexity:** The computational complexity for tri-linear interpolation and compositing is approximately constant regardless of data set size increase, as the number of resampling points does not grow with data set size for the same viewpoint [S2].
- **Performance:** In experiments with a $101 \times 101 \times 250$ seismic data volume at 10 viewpoints (50 trials each, removing max/min), the GPU average time was 14.9947 ms (range [14.1886, 15.7046]), compared to a CPU average of 9486.24 ms (range [9250.04, 9737.42]) [S2].
- **Scaling:** When the data set size increased ten times (increment $10 \times 28 \times 25$) at the same viewpoint, both GPU and CPU processing times showed a slowly wavelike rising trend due to increased memory addressing time and varying computing resources, despite constant computational complexity for interpolation and compositing [S2].
- **Strengths:** Significantly faster than CPU algorithms due to lower computational complexity for intersection calculation, resampling, and compositing [S2]. It is an embarrassingly parallel standard image-order approach that supports many performance and quality enhancements [S4, unofficial].
- **Limitations:** Processing time can fluctuate based on the number of resampling points required for different viewpoints and intersections [S2].

## Background
GPU-accelerated ray casting was introduced by Röttger et al. in 2003 and Krüger and Westermann in 2003 [S4, unofficial]. It emerged as a standard image-order approach to overcome the limitations of earlier texture slicing methods, which suffered from visual artifacts and less flexibility [S4, unofficial]. It is widely used in interactive visualization and real-time applications requiring high frame rates [S2].
