# GPU-accelerated ray casting

Also called: CUDA Grid/Block Raycasting, CUDA Raycasting Kernel, GPU raycasting algorithm, Many-Core GPU Implementation, Standard image order approach

## Overview
GPU-accelerated ray casting is a direct volume rendering method that offloads ray traversal and compositing to a graphics processing unit (GPU) to achieve real-time frame rates [S1]. It differs from CPU-based approaches by leveraging massive parallelism, where each thread handles a single pixel, making it an embarrassingly parallel standard image-order approach [S3, unofficial]. It builds on [CUDA GPU Implementation](13016-cuda-gpu-implementation.md) by explicitly mapping the 2D image grid to CUDA thread blocks and utilizing hardware context switches to hide memory latency [S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** 3D volumetric data (scalar field), transfer function, camera parameters (eye point, view direction), and a bounding box defining the volume extent.
*   **Output:** A 2D image (color and opacity) where each pixel corresponds to a ray cast through the volume.

**Data Structures:**
*   **Thread Hierarchy:** The image is treated as a 2D CUDA grid divided into 2D thread blocks [S2, unofficial].
    *   An $M \times N$ thread block corresponds to an $M \times N$ pixel image tile [S2, unofficial].
    *   Each individual CUDA thread within a block is responsible for raycasting a single pixel [S2, unofficial].
*   **Memory Layout:** Source data can be laid out in:
    *   **Array-order:** $S[i, j, k]$ is at memory location $i + j \cdot xsize + k \cdot xsize \cdot ysize$ [S2, unofficial].
    *   **Z-order:** A 1D layout of a $2^n$ tree where nearby index space points are nearby in physical memory, computed via the formulation by Pascucci and Frank [S2, unofficial].

**Algorithm Steps:**
1.  **Bounding Box Intersection Calculation:** Calculate the entry ($p_{in}$) and exit ($p_{out}$) points of the ray intersecting the volume bounding box. This is achieved by rendering the bounding box twice: once with front-face culling and once with back-face culling [S1].
2.  **Thread Scheduling:** The CUDA runtime dynamically schedules thread blocks onto the GPU's multiprocessors, assigning up to eight blocks at a time to each multiprocessor [S2, unofficial].
3.  **Latency Hiding:** The GPU uses hardware context switches between blocks within a multiprocessor to hide memory latency [S2, unofficial].
4.  **Resampling and Compositing:** For each pixel, the thread performs ray marching from $p_{in}$ to $p_{out}$. At each step, it resamples the volume data (e.g., tri-linear interpolation) and composites the result (e.g., front-to-back alpha blending) on the shader [S1].

**Pseudocode:**
```python
# Kernel launch configuration
# gridDim.x = ceil(image_width / blockDim.x)
# gridDim.y = ceil(image_height / blockDim.y)
# blockDim.x = M
# blockDim.y = N

@cuda.kernel
def raycast_kernel(volume_texture, transfer_function, camera_params, output_image):
    # Calculate global thread indices
    col = cuda.blockIdx.x * cuda.blockDim.x + cuda.threadIdx.x
    row = cuda.blockIdx.y * cuda.blockDim.y + cuda.threadIdx.y
    
    # Check bounds
    if col >= image_width or row >= image_height:
        return

    # 1. Calculate Ray-Bounding Box Intersections
    # Render bounding box twice (front/back culling) to get pin and pout
    # [S1]
    ray_origin = camera_params.eye_point
    ray_direction = normalize(camera_params.view_direction * (col - center_x) + ...) # Simplified projection
    pin, pout = calculate_ray_box_intersection(ray_origin, ray_direction, bounding_box)

    # Initialize compositing variables
    color = (0.0, 0.0, 0.0, 0.0)
    t = 0.0
    step_size = calculate_step_size(pin, pout, num_samples)

    # 2. Ray Marching Loop
    while t < (pout - pin).length():
        current_pos = pin + ray_direction * t
        
        # 3. Resampling (Tri-linear Interpolation)
        # Sample volume at current_pos
        # [S1]
        density = sample_volume(volume_texture, current_pos)
        
        # 4. Compositing
        # Map density to color and opacity using transfer function
        # [S1]
        c, a = apply_transfer_function(transfer_function, density)
        
        # Front-to-back compositing
        # alpha_out = alpha_in + (1 - alpha_in) * alpha_sample
        # color_out = color_in + (1 - alpha_in) * alpha_sample * color_sample
        color = color + (1.0 - color.a) * a * (c.r, c.g, c.b)
        color.a = color.a + (1.0 - color.a) * a
        
        # Early ray termination (optional optimization)
        if color.a > 0.99:
            break
            
        t += step_size

    # 5. Write Output
    output_image[row, col] = color
```

**Parameters:**
*   **CUDA Version:** 3.2 compiler and runtime [S2, unofficial].
*   **NVIDIA Driver:** Version 270.41.19 [S2, unofficial].
*   **Compute Capability:** Targeted at 2.0 (Fermi-series) for additional optimizations [S2, unofficial].
*   **Shared Memory:** Configured to be used as L1 cache for global memory requests [S2, unofficial].
*   **ECC Support:** Enabled [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Memory Addressing:** As dataset size increases, RAM and graphics card memory addressing time increases, causing a slowly wavelike rising trend in processing time despite constant computational complexity for interpolation and compositing [S1].
*   **Viewpoint Dependence:** The number of resampling points varies with viewpoint and intersection geometry, causing fluctuation in response time [S1].

## Operating characteristics
**Time and Memory Complexity:**
*   **Computational Complexity:** The complexity for tri-linear interpolation and compositing is approximately constant regardless of dataset size increase, provided the viewpoint remains the same, because the number of resampling points does not grow with the data volume size [S1].
*   **Memory Scaling:** Processing time shows a slowly wavelike rising trend as dataset size increases due to increased RAM/graphics card memory addressing time and varying computing resources [S1].

**Measured Performance:**
*   **Hardware:** NVIDIA Fermi-series GPU (Compute Capability 2.0) [S2, unofficial].
*   **Dataset:** $101 \times 101 \times 250$ seismic data volume.
*   **Results:** At 10 viewpoints (50 trials each, max/min removed), GPU average time was 14.9947 ms (range [14.1886, 15.7046]), compared to CPU average 9486.24 ms (range [9250.04, 9737.42]) [S1].
*   **Speedup:** The GPU algorithm is significantly faster than the CPU algorithm, primarily because the CPU has higher computational complexity for intersection calculation, resampling, and compositing [S1].

**Strengths and Limitations:**
*   **Strengths:** Embarrassingly parallel, supports many performance and quality enhancements, achieves real-time frame rates (mandatory for high-refresh-rate displays like HTC Vive at 90 Hz) [S3, unofficial][S1].
*   **Limitations:** Performance fluctuates with viewpoint due to varying intersection geometries and resampling point counts [S1]. Memory addressing overhead increases with very large datasets [S1].

## Background
GPU-accelerated ray casting was introduced by Röttger et al. in 2003 and Krüger and Westermann in 2003 [S3, unofficial]. It emerged as a standard image-order approach to overcome the limitations of earlier texture-slicing methods, which suffered from visual artifacts and less flexibility [S3, unofficial]. It is widely used in interactive scientific visualization and virtual reality applications where real-time performance is critical [S1].
