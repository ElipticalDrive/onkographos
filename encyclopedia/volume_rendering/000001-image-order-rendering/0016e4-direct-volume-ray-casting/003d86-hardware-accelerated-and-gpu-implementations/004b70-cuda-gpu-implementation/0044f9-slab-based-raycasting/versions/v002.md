# Slab-based Raycasting

Also called: Slab-based Raycaster

## Overview
Slab-based raycasting is a CUDA GPU optimization for direct volume rendering that caches sampled voxels in shared memory as slabs to improve performance when volume data is accessed multiple times, such as for gradient calculation in Phong lighting [S1, unofficial]. It sets itself apart from basic raycasting by trading increased shared memory overhead and reduced early ray termination granularity for cache hits on repeated voxel access [S1, unofficial]. Unlike hardware texture caches, which benefit from large viewports where adjacent rays hit the same voxels, the slab cache is most efficient when the data set resolution is high compared to the viewport size [S1, unofficial]. For a broader comparison, see [GPU-accelerated ray casting](12256-gpu-accelerated-ray-casting.md).

## How it works
**Inputs and Outputs:**
*   **Input:** Volume dataset, ray origin and direction per pixel, thread block configuration ($bs_x, bs_y$), slab depth ($sd$) [S1, unofficial].
*   **Output:** Rendered image with lighting applied [S1, unofficial].

**Data Structures:**
*   **Shared Memory Cache:** A contiguous block storing $bs_x \times bs_y \times sd$ sampled voxels [S1, unofficial].
*   **Voxel Layout:** The cache stores voxel values and gradients for the slab [G].

**Parameters:**
*   $bs_x, bs_y$: Thread block dimensions [S1, unofficial].
*   $sd$: Slab depth (number of voxels along the ray stored in the cache) [S1, unofficial].
*   $sd_{opt}$: Optimal slab depth, which depends on the specific dataset [S1, unofficial].

**Algorithm Steps:**
1.  **Block Initialization:** Each thread in the block determines its ray parameters and calculates the spatial extent of the current slab along the ray [G].
2.  **Slab Fetch:** Threads cooperatively fetch $bs_x \times bs_y \times sd$ sampled voxels from global memory into the shared memory cache [S1, unofficial].
3.  **Border Handling:** Additional border voxels may be fetched to handle gradient calculations at the edges of the slab, introducing overhead [S1, unofficial].
4.  **Synchronization:** All threads synchronize to ensure the slab is fully loaded into shared memory before processing begins [G].
5.  **Ray Casting Loop:** Threads iterate through the slab depth $sd$. For each step, they read the voxel value and gradient from shared memory, compute lighting (e.g., Phong), and perform volume integration [S1, unofficial].
6.  **Early Termination Check:** The ray checks for termination. Only complete slabs can be terminated, not individual rays, which reduces efficiency for solid data [S1, unofficial].
7.  **Next Slab:** If the ray has not terminated and more volume remains, the block fetches the next slab into shared memory and repeats steps 2–6 [G].
8.  **Write Output:** The final accumulated color and opacity are written to global memory [G].

**Pseudocode:**
```python
def slab_based_raycast(ray_origin, ray_direction, volume_data, bs_x, bs_y, sd, ray_step_size):
    # Shared memory cache: bs_x * bs_y * sd voxels
    shared_voxels = [0.0] * (bs_x * bs_y * sd)
    shared_gradients = [0.0] * (bs_x * bs_y * sd * 3)
    
    # 1. Calculate slab bounds along the ray
    slab_start_t = current_slab_index * sd * ray_step_size
    slab_end_t = (current_slab_index + 1) * sd * ray_step_size
    
    # 2. Cooperative fetch into shared memory
    tid = threadIdx.x + threadIdx.y * bs_x
    for i in range(sd):
        t = slab_start_t + i * ray_step_size
        pos = ray_origin + ray_direction * t
        global_idx = get_volume_index(pos)
        shared_voxels[tid * sd + i] = volume_data[global_idx]
        shared_gradients[(tid * sd + i) * 3 : (tid * sd + i) * 3 + 3] = compute_gradient(volume_data, global_idx)
    __syncthreads()
    
    # 3. Process slab
    for i in range(sd):
        voxel_val = shared_voxels[tid * sd + i]
        grad = shared_gradients[(tid * sd + i) * 3 : (tid * sd + i) * 3 + 3]
        color = apply_phong_lighting(voxel_val, grad)
        alpha = transfer_function(voxel_val)
        out_color = blend(out_color, color, alpha)
        out_alpha = blend(out_alpha, alpha)
        if out_alpha >= TERMINATION_THRESHOLD:
            break
    __syncthreads()
    
    # 4. Advance to next slab
    current_slab_index += 1
```

**Edge Cases and Pitfalls:**
*   **Overhead:** For basic raycasting, caching adds 23–67% overhead because each voxel is accessed only once [S1, unofficial].
*   **Early Termination:** Only complete slabs can be terminated, not individual rays, leading to performance decreases with solid/non-transparent data [S1, unofficial].
*   **Shared Memory Limits:** The cache size is $bs_x \times bs_y \times sd$. For optimal configurations, this requires 15,360 bytes, close to the 16 kB maximum on older GPUs, allowing only one thread block per multiprocessor [S1, unofficial].
*   **Gradient Accuracy:** Gradients computed from slab data are less exact than those from direct global memory access [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources. Measured overhead for basic raycasting is 23–67%, while Phong lighting achieves 12–78% speedup [S1, unofficial].
*   **Memory Complexity:** Not given in the sources. Shared memory usage is $bs_x \times bs_y \times sd$ voxels [S1, unofficial].
*   **Measured Performance:** On the GeForce GTX 280 with the `vmhead` dataset (512²×294, 16-bit) and Phong lighting at 512² viewport, slab-based raycasting achieved 67.9 fps vs 40.7 fps basic, a +78.2% speedup with block size 16×30 and slab depth 16 [S1, unofficial]. On the GeForce GTX 280 with the `engine` dataset (256²×128, 8-bit) and Phong lighting at 512² viewport, it achieved 77.1 fps vs 77.6 fps basic, a -0.6% change with block size 8×16 [S1, unofficial].
*   **Scaling:** Speedup decreases with increasing viewport size because larger viewports increase hardware texture cache hit rates due to spatial locality, reducing the relative benefit of the slab cache [S1, unofficial].
*   **Strengths:** Significant speedup for large, semi-transparent datasets with high resolution relative to viewport size, especially when lighting calculations require multiple voxel accesses [S1, unofficial].
*   **Limitations:** Poor performance for small, solid datasets or basic raycasting due to overhead and inefficient early termination. Limited by shared memory size, potentially reducing occupancy [S1, unofficial].
*   **When to Use:** Direct volume rendering of semi-transparent, high-resolution data with Phong lighting on GPUs with sufficient shared memory [S1, unofficial].
*   **When Not to Use:** Basic raycasting, small solid datasets, or when early ray termination is critical for performance [S1, unofficial].

## Background
Slab-based raycasting was developed as part of CUDA-based direct volume rendering techniques, specifically tested on the GeForce GTX 280 [S1, unofficial]. It was designed to address the inefficiency of repeated volume data access for lighting calculations by leveraging shared memory [S1, unofficial]. The method is particularly relevant for medical imaging applications, where data sets typically have high resolution and are semi-transparent [S1, unofficial].
