# In-shader neural network inference

Also called: Tiny-CUDA-NN in-shader routine, fully fused MLP inference

## Overview
This method performs neural network inference directly within a GPU shader program to eliminate global memory access overhead, specifically by fusing the hash grid encoding layer into the Multi-Layer Perceptron (MLP) calculation [S1]. It differs from standard approaches by managing data locally within threadblocks via shared memory and utilizing GPU tensor cores for acceleration, setting it apart from CPU-based or standard GPU inference pipelines that rely on global memory transfers [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A ray-generation kernel (callback) and network parameters (weights, biases, grid dimensions).
*   **Output:** Rendered image pixels with neural network evaluations integrated into the ray-casting loop.

**Data Structures:**
*   **Shared Memory:** Used to store inputs and outputs locally within each threadblock to avoid global memory latency [S1].
*   **Threadblock Configuration:** Configured to process exactly 16 inputs (feature vectors) per block [S1].
*   **Warp Configuration:** Each warp consists of 32 threads [S1].

**Parameters:**
*   **Group Size:** MLP layers are broken into groups of 16 neurons [S1].
*   **Matrix Dimensions:** Tensor cores accelerate multiplications between two $16 \times 16$ matrices [S1].
*   **Warp Iterations:** In a standard ray tracer where one thread handles one ray, each warp iterates $W/8$ times to compensate for producing only one input coordinate per thread, where $W$ is the total number of 16-neuron groups in the layer [S1].

**Algorithm Steps:**
1.  **Eliminate Global Memory Access:** Remove all global GPU memory reads/writes for network weights and activations. Fuse the hash grid encoding layer fully into the MLP calculation logic [S1].
2.  **Local Management:** Manage inputs and outputs locally within each threadblock. Pass data to the network via shared memory [S1].
3.  **Layer Decomposition:** Break an MLP layer into $W$ groups of 16 neurons each [S1].
4.  **Warp Execution:** Assign each 32-thread warp to compute the operations for one 16-neuron group. The warp processes 16 consecutive feature vectors. This results in the warp handling multiplications between two $16 \times 16$ matrices, leveraging GPU tensor cores [S1].
5.  **Threadblock Aggregation:** Combine all $W$ groups to form a single GPU threadblock. Execute these groups in parallel within the block. Each threadblock processes exactly 16 inputs at a time [S1].
6.  **Iteration Compensation:** If the rendering kernel assigns one ray to one thread (producing one input coordinate), configure each warp to iterate $W/8$ times to cover all $W$ groups [S1].
7.  **Control Flow Management:** GPU tensor cores require all threads in a calling warp to be active. Manage control flow carefully to ensure warp divergence does not stall execution. Use a `block_any` helper function: this function evaluates to true for all threads in a threadblock if any of the thread-local predicates $v$ evaluates to true [S1].
8.  **Kernel Launch:** Use a templated CUDA wrapper function that accepts the ray-generation kernel as a callback. This wrapper initializes the correct threadblock configurations and shared memory sizes, allowing integration into standard GPU volume ray tracing algorithms [S1].

```python
def launch_inference_kernel(ray_gen_kernel, network_params):
    """
    Templated wrapper to launch the rendering kernel with in-shader inference.
    """
    # Determine W: number of 16-neuron groups in the MLP layer
    W = network_params.num_neurons // 16
    
    # Configure threadblock to handle 16 inputs
    # Each warp (32 threads) handles one 16x16 matrix multiplication
    # Total warps per block = W
    threads_per_block = 32 * W
    
    # Shared memory allocation for inputs/outputs
    shared_mem_size = calculate_shared_memory_size(16, network_params)
    
    # Launch kernel with callback
    ray_gen_kernel[threads_per_block, 1](
        network_params,
        shared_mem_size
    )

def ray_gen_kernel(network_params, shared_mem_size):
    """
    Main rendering kernel with fused inference.
    """
    # 1. Manage inputs/outputs in shared memory
    shared_inputs = get_shared_memory_block(0, 16)
    shared_outputs = get_shared_memory_block(16, 16)
    
    # 2. Load input coordinate (one per thread)
    # In standard ray tracing, thread_id maps to one ray
    coord = get_ray_coordinate(thread_id())
    
    # 3. Encode and prepare for MLP
    # Hash grid encoding is fused here
    encoded_features = fuse_hash_encoding(coord, network_params.grid)
    
    # 4. Warp-level iteration
    # Each warp handles one 16-neuron group
    # Warp needs to iterate W/8 times if 1 thread = 1 ray
    # Note: 32 threads / 16 features = 2 threads per feature
    # But the text says "warp handles multiplications between two 16x16 matrices"
    # and "iterate for W/8 times".
    
    warp_id = thread_id() // 32
    lane_id = thread_id() % 32
    
    # Determine if this thread is active for the current iteration
    # Using block_any for control flow management
    active = True
    
    # Iterate through all W groups
    for group_idx in range(W):
        # Check if we need to iterate again (compensation for 1 ray/thread)
        # The text implies the warp itself iterates W/8 times.
        # This suggests a loop structure within the warp or block logic.
        
        # Load 16 features into shared memory for the warp to process
        # Assuming 16 features are loaded per iteration
        load_features_into_shared(shared_inputs, encoded_features, group_idx)
        
        # Tensor Core Operation: 16x16 matrix multiplication
        # Input: 16x16 matrix from shared memory
        # Weight: 16x16 matrix from fused parameters (no global memory)
        output = tensor_core_matmul(shared_inputs, network_params.weights[group_idx])
        
        # Store result
        shared_outputs[group_idx] = output
        
        # Control flow check
        # block_any evaluates true if any thread-local predicate is true
        # This ensures warp synchronization if branching occurs
        if not block_any(active):
            break
            
    # 5. Finalize and write output
    write_pixel(shared_outputs, thread_id())
```

**Edge Cases and Pitfalls:**
*   **Warp Divergence:** GPU tensor cores require all threads in the calling warp to be active. Divergent control flow can stall execution. Use `block_any` to manage predicates [S1].
*   **Memory Limits:** Shared memory usage must be calculated precisely to fit within the hardware limits of the GPU [S1].
*   **Input Mismatch:** If the number of neurons is not divisible by 16, padding or handling of the remainder is required (Not given in the sources).

## Subtopics

### Fully Fused Hash Encoding
*   **What it is:** The integration of the hash grid encoding step directly into the MLP shader code, removing separate memory lookups.
*   **Differentiation:** Eliminates the overhead of fetching encoded features from global memory before MLP computation.
*   **When to choose:** When memory bandwidth is a bottleneck and the encoding scheme is static or can be computed on-the-fly efficiently.
*   **Link:** [Fully Fused Hash Encoding](52-name.md)

### Tensor Core Acceleration
*   **What it is:** Utilizing specialized GPU hardware (tensor cores) for matrix multiplications of specific dimensions ($16 \times 16$).
*   **Differentiation:** Provides significant speedup over standard CUDA cores for dense linear algebra operations.
*   **When to choose:** When running on NVIDIA GPUs with Volta architecture or newer that support tensor cores.
*   **Link:** [Tensor Core Acceleration](52-name.md)

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of neurons and layers, but with a significantly reduced constant factor due to tensor core acceleration and eliminated memory latency [S1].
*   **Memory Complexity:** $O(1)$ per threadblock for shared memory (fixed size for 16 inputs), plus the size of the network weights which are embedded in the shader code [S1].
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Scales with the number of threadblocks. Each block processes 16 inputs independently.
*   **Strengths:** Eliminates global memory access overhead; leverages hardware tensor cores; integrates seamlessly into existing ray tracing pipelines via the wrapper function [S1].
*   **Limitations:** Requires careful control flow management to avoid warp divergence; limited to NVIDIA GPUs with tensor cores; rigid structure (16-neuron groups) [S1].
*   **When to use:** High-performance real-time volume rendering where neural networks are used for density/opacity prediction and memory bandwidth is a constraint [S1].
*   **When not:** When using non-NVIDIA hardware; when the network architecture does not fit the 16-neuron group structure easily; when dynamic control flow is prevalent and cannot be masked by `block_any` [S1].

## Background
This method was developed as part of the Tiny-CUDA-NN framework to enable efficient neural network inference in GPU shaders [S1]. It was concurrently and independently developed by Lovegrove et al. (Deepsdf) and Weiss et al., though based on different network architectures [S1]. The technique addresses the bottleneck of global memory access in neural rendering pipelines [S1].
