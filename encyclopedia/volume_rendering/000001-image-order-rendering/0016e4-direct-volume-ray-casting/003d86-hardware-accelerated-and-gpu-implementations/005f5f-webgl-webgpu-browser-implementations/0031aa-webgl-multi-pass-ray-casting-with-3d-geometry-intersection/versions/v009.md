# WebGL Multi-pass Ray-casting with 3D Geometry Intersection

Also called: Five-pass ray-casting pipeline, VMesh Real-Time Rendering, WebGL volume rendering with intersected 3D geometry

## Overview
This method enables the interactive coexistence of volumetric datasets and 3D triangular meshes in WebGL by using a multi-pass rendering pipeline to handle occlusion, blending, and ray intersection [S1]. It solves the problem of rendering opaque and transparent 3D geometry within or alongside volume data, a key requirement for medical and engineering visualizations, while adhering to WebGL constraints such as the lack of native 3D and float texture support [S1]. Unlike single-pass ray-casting approaches [S1], this method explicitly separates the computation of depth, surface color, and volume traversal into distinct passes to correctly manage back-to-front blending and geometry intersections [S1].

## How it works
**Inputs and Outputs:**
*   **Inputs:** A set of 3D triangular meshes (opaque), a volumetric dataset (represented as a 2D texture atlas), camera matrices, and transfer functions [S1].
*   **Outputs:** A final 2D image composited from volume and mesh data [S1].

**Data Structures:**
*   **Volume Data:** Stored as a 2D texture atlas where 2D slices are stacked in the Z-axis and arranged in a matrix configuration on a single 2D plane [S1].
*   **Depth Data:** Since WebGL 1.0 lacks native float texture support, depth values from intermediate passes are encoded into RGBA color channels of Frame Buffer Objects (FBOs) [S1].
*   **FBOs:** Multiple Frame Buffer Objects are used to store intermediate results: depth maps (Passes 1 and 3), surface colors (Pass 2), and volume back coordinates (Pass 4) [S1].

**Numbered Steps:**
The pipeline consists of five passes (or four in the VMesh variant [S2]), executed in the following order:

1.  **Depth Pass (Meshes):** Render the depth of all 3D meshes in the scene into an FBO [S1]. The fragment shader outputs the current depth encoded in RGBA color channels [S1].
2.  **Surface Color Pass (Meshes):** Render all 3D meshes into a separate FBO to store their color information [S1].
3.  **Back Cube Depth Pass (Volume):** Render the depth of the back side of the volume bounding box into an FBO, encoded in RGBA, using the same shader logic as Pass 1 [S1].
4.  **Back Coordinates Pass (Volume):** Render the back faces of the volume bounding box into a separate FBO [S1]. The 3D texture coordinates are assigned as color on each vertex, so rasterization interpolates these per-vertex colors to represent volume data 3D texture coordinates [S1].
5.  **Ray Traversal and Composition Pass:** Render 3D objects and volume data to the screen buffer [S1]. Objects must be sorted in Z-depth order and rendered from back to front [S1]. In the fragment shader, rays are cast towards the volume [S1]. All outputs from previous passes are sampled as 2D textures [S1]. The shader performs ray marching, checks for 3D geometry intersections using depth data from Passes 1 and 3, and composites the results [S1]. It assumes access to textures generated in previous passes [S1].

**Pseudocode:**
The following pseudocode represents the core ray-casting logic executed in the fragment shader during the final pass (Pass 5), adapted from [S1]. It uses standard graphics operations marked [G].

```python
# Inputs:
# depth_mesh_tex: Texture from Pass 1 (Mesh Depth, RGBA encoded)
# color_mesh_tex: Texture from Pass 2 (Mesh Color)
# depth_vol_tex: Texture from Pass 3 (Volume Back Depth, RGBA encoded)
# volume_atlas_tex: 2D Texture Atlas containing volume slices
# camera_pos: vec3
# screen_pos: vec2 (current fragment coordinate)
# bounding_box_max: vec3

def unpack_rgba_to_float(r, g, b, a):
    # Reverses the packing: value = r * 256^3 + g * 256^2 + b * 256 + a [S1]
    return r * (256.0**3) + g * (256.0**2) + b * 256.0 + a

# 1. Initialize Ray Parameters [G]
ray_direction = compute_ray_direction(camera_pos, screen_pos)
ray_pos = camera_pos

# Sample back volume depth to determine maximum distance D [S1]
back_depth_rgba = texture(depth_vol_tex, screen_pos)
max_distance = unpack_rgba_to_float(back_depth_rgba.r, back_depth_rgba.g, back_depth_rgba.b, back_depth_rgba.a)

# Compute number of steps S and step size s [S1]
S = Not given in the sources.
s = max_distance / S

# 2. Ray Traversal Loop [S1]
accumulated_color = vec3(0.0)
accumulated_alpha = 0.0

for i in range(S):
    # Interpolate sample at current ray_pos [S1]
    volume_value = texture(volume_atlas_tex, ray_pos)

    # Compute color with transfer function [S1]
    color, alpha = transfer_function(volume_value)

    # Accumulate color and opacity [S1]
    accumulated_color = accumulated_color + (1.0 - accumulated_alpha) * alpha * color
    accumulated_alpha = accumulated_alpha + (1.0 - accumulated_alpha) * alpha

    # Check for 3D Geometry Intersection using depth data from Passes 1 and 3 [S1]
    mesh_depth_rgba = texture(depth_mesh_tex, screen_pos)
    mesh_depth_float = unpack_rgba_to_float(mesh_depth_rgba.r, mesh_depth_rgba.g, mesh_depth_rgba.b, mesh_depth_rgba.a)
    current_ray_depth = dot(ray_pos - camera_pos, ray_direction)
    if mesh_depth_float < current_ray_depth:
        mesh_color = texture(color_mesh_tex, screen_pos)
        accumulated_color = accumulated_color + (1.0 - accumulated_alpha) * mesh_color
        accumulated_alpha = 1.0
        break

    # Early Ray Termination [S1]
    if accumulated_alpha >= 1.0 or ray_pos > bounding_box_max:
        break

    # Increment ray_pos with s [S1]
    ray_pos = ray_pos + s * ray_direction

output_color = accumulated_color
```

**Parameters:**
*   **Rendering Order:** Objects (volumes and 3D opaque meshes) must be sorted in z-depth order and rendered from back to front [S1].
*   **Blending Mode:** Back-to-front blending composition is used for the ray-casting shaders in the final rendering pass [S1].
*   **Threshold:** Early ray termination occurs when accumulated opacity $\alpha \ge 1.0$ [S1].

**Edge Cases and Pitfalls:**
*   **Lack of 3D Textures:** WebGL lacks support for 3D textures, requiring the use of a 2D texture atlas workaround to sample volumetric data [S1].
*   **Lack of Float Textures:** WebGL lacks support for Float textures, requiring depth data to be encoded into RGBA color channels for storage in FBOs [S1].
*   **Occlusion Handling:** Correctly determining if a 3D object occludes the volume requires comparing the depth of the mesh (from Pass 1) with the current ray position [S1].

## Operating characteristics
*   **Complexity:** The multi-pass approach requires five rendering passes and multiple Frame Buffer Objects (FBOs), which is a downside in terms of computational overhead and memory usage [S1].
*   **Performance:** The method is designed for interactive visualization on web platforms, balancing quality with the constraints of WebGL [S1].
*   **Strengths:** Supports the coexistence of 3D triangular meshes and volumetric datasets, which is critical for medical and engineering applications [S1].
*   **Limitations:** High memory usage due to multiple FBOs; precision issues due to RGBA depth encoding; complexity of implementation due to multiple passes and sorting requirements [S1].

## Background
This method extends previous WebGL ray-casting efforts by Congote et al. [CSK* 11], Mobeen et al. [MF12], and Noguera and Jiménez [NJ12] by exploring the coexistence of 3D triangular meshes along volume data within the constraints of the Web platform [S1]. It addresses challenges such as the lack of 3D and depth textures in WebGL [S1]. The VMesh variant [S2] implements a similar four-pass process using three.js for VMesh assets.
