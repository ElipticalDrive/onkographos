# WebGL Multi-pass Ray-casting with 3D Geometry Intersection

Also called: Five-pass ray-casting pipeline, VMesh Real-Time Rendering, WebGL volume rendering with intersected 3D geometry

## Overview
This method is a WebGL-based volume rendering algorithm that supports the coexistence of 3D triangular meshes and volumetric datasets by using a multi-pass rendering pipeline to handle occlusion, blending, and ray intersection with 3D geometry within WebGL constraints [S1, S2]. It specifically addresses the lack of 3D textures and limited depth texture support in WebGL by encoding depth data into RGBA color channels and arranging volumetric slices into a 2D texture atlas [S1]. Unlike single-pass ray-casting approaches [S1], this method explicitly separates the computation of 3D surface geometry and volume traversal into distinct passes to correctly handle transparency and occlusion between opaque meshes and semi-transparent volumes [S1].

## How it works
### Inputs and Outputs
**Inputs:**
*   Volumetric dataset: A set of 2D slices stacked in the Z-axis, arranged as a 2D texture atlas [S1].
*   3D Geometry: A set of 3D triangular meshes [S1].
*   Camera parameters: Position, direction, and view frustum [S1].
*   Transfer function: Maps scalar values to color and opacity [S1].

**Outputs:**
*   Final composited image on the screen buffer [S1].

### Data Structures
*   **Volume Data:** Stored as a 2D texture atlas. The 2D slices are arranged in a matrix configuration in the same 2D plane to allow sampling via a single 2D texture [S1].
*   **Depth Data:** Stored in Frame Buffer Objects (FBOs) as RGBA textures. Depth values are encoded into the RGBA color channels because WebGL 1.0 lacks native Float texture support [S1].
*   **Frame Buffer Objects (FBOs):** Multiple FBOs are used to store intermediate results:
    *   Depth of 3D meshes (Pass 1) [S1].
    *   Color of 3D meshes (Pass 2) [S1].
    *   Depth of the back side of the volume bounding box (Pass 3) [S1].
    *   Back coordinates of the volume bounding box (Pass 4) [S1].

### Numbered Steps
The method consists of five rendering passes [S1]. Note that [S2] describes a four-pass variant for VMesh assets, but the primary definition from [S1] details the five-pass pipeline for general 3D geometry intersection. The following steps follow the five-pass structure from [S1], which is the more general case for intersecting arbitrary 3D meshes with volumes.

1.  **Pass 1 (Depth Pass):** Render the depth of all 3D meshes in the scene into an FBO. A simple shader executes per 3D object where the fragment shader outputs the current depth encoded in the color channels as RGBA [S1].
2.  **Pass 2 (Color of Surface Objects):** Render all 3D meshes into a separate FBO to store their color information [S1].
3.  **Pass 3 (Back Cube Depth):** Render the depth of the back side of the volume bounding box into an FBO, encoded in the color channels as RGBA, using the same shader used in the first pass [S1].
4.  **Pass 4 (Back Coordinates of the Cube):** Render the back faces of the volume bounding box into a separate FBO. The 3D texture coordinates are assigned as a color on each vertex of the cube. In the rasterization process, the interpolated per-vertex colors represent the volume data 3D texture coordinates [S1].
5.  **Pass 5 (Ray Traversal and 3D Surfaces):** Render 3D objects in the screen along volume objects computing the ray-casting traversal. Objects must be rendered sorted in Z in back-to-front order. In the fragment shader, rays are cast towards the volume accumulating color and opacity to finally be rendered in the screen buffer. All outputs of the previous passes are 2D texture inputs for the ray-casting fragment shader [S1].

### Formulas and Definitions
*   **Ray Casting Initialization:** For each pixel in the screen:
    *   Initialize the number of steps $S$.
    *   Compute the ray position $ray\_pos$, ray direction $ray\_direction$, and maximum distance $D$ [S1].
    *   Compute interval steps $s$ [S1].
*   **Ray Traversal Loop:**
    *   For $i = 0$ to $S$:
        *   Interpolate sample at current $ray\_pos$ using the 2D texture atlas [S1].
        *   Compute color with transfer function [S1].
        *   Accumulate color $C$ and opacity $\alpha$ [S1].
        *   If $\alpha \ge 1.0$ OR $ray\_pos > bounding\_box$, break [S1].
        *   Increment $ray\_pos$ with $s$ [S1].
*   **3D Geometry Intersection Check:** During the ray traversal in Pass 5, determine at each step if there is a 3D object by accessing depth data produced by Passes 1 and 3 [S1].
*   **Depth Unpacking:** Since depth is stored in RGBA, it must be unpacked to a float value in the fifth pass. The GLSL code for packing/unpacking is provided in [S1]:
    ```glsl
    // Packing function (used in Passes 1 and 3)
    float packFloat(float value) {
        const vec4 bitSh = vec4(256.0*256.0*256.0, 256.0*256.0, 256.0, 1.0);
        const vec4 bitMsk = vec4(0.0, 1.0/256.0, 1.0/256.0, 1.0/256.0);
        return fract(value * bitSh) - bitMsk * fract(value * bitSh * 256.0);
    }
    ```
    The unpacking process reverses this operation in the fragment shader of Pass 5 [S1].

        ray_direction = compute_ray_direction(pixel)

        step_size = max_dist / num_steps

        accumulated_alpha = 0.0
        
        for i from 0 to num_steps:
            # Check for 3D geometry intersection
            current_depth = unpack_rgba_to_float(sample_texture(fbo_depth_meshes, pixel))
            volume_back_depth = unpack_rgba_to_float(sample_texture(fbo_volume_back_depth, pixel))
            
            # Determine if ray hits a 3D mesh or volume boundary
            # This logic is complex and depends on the specific intersection check

            # Sample volume
            sample_coord = compute_volume_sample_coord(ray_pos, fbo_volume_back_coords, pixel)
            volume_value = sample_texture(volume_atlas, sample_coord)

            color, alpha = transfer_function(volume_value)

### Parameters
*   **Rendering Order:** Objects (volumes and 3D opaque meshes) must be sorted in z-depth order and rendered from back to front to correctly handle transparency and occlusion [S1].
*   **Blending Mode:** Back-to-front blending composition is used for the ray-casting shaders in the final rendering pass [S1].
*   **Number of Steps ($S$):** Not given in the sources.

### Edge Cases and Pitfalls
*   **Lack of 3D Textures:** WebGL lacks support for 3D textures, requiring the use of a 2D texture atlas workaround to sample volumetric data [S1].
*   **Lack of Float Textures:** WebGL lacks support for Float textures, requiring depth data to be encoded into RGBA color channels for storage in FBOs [S1].
*   **Precision:** The encoding of depth into RGBA may introduce precision issues, though the specific bit-depth is not detailed in the sources [S1].
*   **Occlusion:** Correctly handling occlusion between opaque meshes and semi-transparent volumes requires careful sorting and blending [S1].

## Operating characteristics
*   **Time Complexity:** The multi-pass approach requires five rendering passes, which increases computational overhead compared to single-pass methods [S1].
*   **Memory Complexity:** The method requires multiple Frame Buffer Objects (FBOs) to store intermediate results, leading to higher memory usage [S1].
*   **Strengths:** Supports the coexistence of 3D triangular meshes and volumetric datasets, which is key for medical and engineering visualization [S1]. Works within the constraints of WebGL, including mobile devices [S1].
*   **Limitations:** High computational overhead due to multiple passes and FBOs. Limited by WebGL's lack of 3D and Float textures [S1].
*   **When to Use:** When interactive volume rendering with 3D geometry intersection is required in a web browser using WebGL [S1].
*   **When Not to Use:** When performance is critical and the overhead of multiple passes is unacceptable, or when 3D textures are available (e.g., desktop OpenGL/Vulkan) [S1].

## Background
This method extends previous WebGL ray-casting efforts by Congote et al. [CSK* 11], Mobeen et al. [MF12], and Noguera and Jiménez [NJ12] by exploring the coexistence of 3D triangular meshes along volume data within the constraints of the Web platform [S1]. It was presented by Arbelaiz, Moreno, and Kabongo in 2016 [S1]. The integration of 3D polygonal elements in volume rendering is a key functionality, especially in the medical field and engineering simulations [S1].
