# Packed Effective Depth Peeling

Also called: Packed EDP

## Overview
Packed Effective Depth Peeling (PEDP) is a memory-optimized variant of Effective Depth Peeling (EDP) that reduces memory consumption by tightly packing sparse valid fragments using a linked list structure on the GPU [S1]. It solves the problem of fixed-size memory scaling in conventional Depth Peeling by removing empty pixels, causing memory consumption to scale directly with peeling efficiency [S1]. Unlike standard EDP, which retains fixed-size buffers for all potential fragment slots, PEDP dynamically allocates storage only for valid fragments, offering significant memory efficiency improvements at the cost of slightly increased warping latency due to pointer dereferencing [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** The set of fragments generated by the previous peeling layer $h-1$ (or the initial ray casting for $h=0$).
*   **Output:** A packed linked list of fragments for layer $h$, stored in a node buffer, and a head texture pointing to the first node of each pixel.

**Data Structures:**
1.  **Node Buffer:** A dynamic array of linked list nodes. Each node consumes 16 bytes in RGBA32F format [S1]:
    *   8 bytes: Color (RGBA32F).
    *   4 bytes: Depth.
    *   4 bytes: Indexed pointer to the next node (an integer index into the node buffer) [S1].
2.  **Head Texture:** A texture of screen resolution holding 4-byte indexes to the first node of the linked list for each pixel. If a pixel has no fragments, the index is null/zero [S1].
    *   Memory consumption: $W \times H \times 4$ bytes, where $W$ and $H$ are screen width and height. For the tested resolutions, this consumes approximately 7.9 MB [S1].

**Algorithm Steps:**
1.  **Peel Layer $h$:** Perform the standard EDP peeling pass for layer $h$, generating a set of valid fragments.
2.  **Post-Peeling Packing:** Immediately after peeling layer $h$, perform fragment packing to convert the sparse fragment buffer into the linked list structure [S1].
    *   This is a per-layer process. It avoids keeping the entire layer in a fixed-size buffer [S1].
    *   Use two working textures (input $h-1$ and output $h$) alternating in a ping-pong fashion to avoid keeping entire layers in memory [S1].
    *   Iterate through the valid fragments generated in step 1.
    *   For each fragment, allocate a new node in the node buffer.
    *   Store the fragment's color and depth in the node.
    *   Set the node's "next" pointer to the current head of the linked list for that pixel's coordinate.
    *   Update the head texture for that pixel to point to the newly allocated node index.
3.  **Warping:** Use the head texture and node buffer to traverse the linked lists during the warping phase.
    *   For each pixel, read the head index.
    *   Dereference the index to get the first node.
    *   Traverse the linked list using the "next" pointers until the end or a stopping condition is met [S1].

class Node:
    color: float[4] # RGBA32F
    depth: float
    next_index: int # Index in node_buffer

def pack_layer_fragments(fragments, width, height):
    """
    Pack sparse fragments into a linked list structure.
    fragments: List of (x, y, color, depth) tuples generated by peeling.
    """
    # Clear head texture for this layer's new fragments
    # Note: In a ping-pong scheme, we might be reading from a previous head texture
    # but for the *new* layer h, we are building a fresh list.
    # The head texture for layer h is initialized to 0 (null).
    current_head_texture = [0] * (width * height)
    
    # Start of new nodes in the buffer
    # In a real implementation, this would be an atomic counter or pre-allocated offset
    next_node_index = len(node_buffer) 
    
    for frag in fragments:
        x, y, color, depth = frag
        
        # Create new node
        node = Node()
        node.color = color
        node.depth = depth
        node.next_index = current_head_texture[y * width + x]
        
        # Append to buffer
        node_buffer.append(node)
        
        # Update head texture to point to this new node
        current_head_texture[y * width + x] = next_node_index
        
        next_node_index += 1
        
    # Store the head texture for this layer
    # In a ping-pong scheme, this texture becomes the input for the next layer's warping
    return current_head_texture

**Parameters and Typical Values:**
*   **Node Size:** 16 bytes [S1].
*   **Head Texture Size:** 4 bytes per pixel [S1].
*   **Packing Time:** For two hidden layers ($L=2$), packing takes 0.6–0.8 ms [S1].

**Edge Cases and Pitfalls:**
*   **Cache Unfriendliness:** Random memory access during node traversal can be cache-unfriendly, making PEDP likely slightly slower than EDP in terms of warping speed [S1].
*   **Dereferencing Overhead:** Additional dereferencing to the first pointer in the head texture is required during warping [S1].
*   **Memory Scaling:** Memory consumption scales directly with the number of valid fragments, not the screen resolution or maximum layer count [S1].

## Operating characteristics
**Time and Memory Complexity:**
*   **Memory:** Scales directly with the number of valid fragments and screen resolution (for the head texture). It avoids fixed-size memory scaling with the number of layers [S1].
*   **Time:** Peeling time is similar to EDP. Packing adds 0.6–0.8 ms for two hidden layers [S1]. Warping is slightly slower than EDP due to cache-unfriendly random memory access during node traversal [S1].

**Measured Performance:**
*   **Memory Efficiency:** PEDP consumes significantly less memory than standard EDP and BDP.
    *   In the Ruins (RU) scene with $E=50$mm, PEDP consumes 17.7 MB compared to 316.4 MB for standard EDP, a 37.5x memory efficiency improvement over BDP [S1].
    *   Overall memory efficiency ranges from 25.1x to 166.1x relative to BDP [S1].
*   **Speedup:** The average speedup factors of PEDP against BDP and UDP are 2.2x and 1.8x respectively for all combinations of $E$ and scenes [S1].
*   **Hardware:** Tested on Intel Core i9-10900 2.8 GHz and NVIDIA GPU (specific model not given in notes) [S1].

**Strengths and Limitations:**
*   **Strengths:** Significant memory reduction, making it suitable for resource-limited environments. Removes empty fragments, reducing warping workload.
*   **Limitations:** Slightly slower warping than EDP due to pointer dereferencing and cache misses. Implementation complexity is higher due to linked list management on GPU.

**When to Use:**
*   Use PEDP when memory is a critical constraint and the scene has sparse valid fragments (high peeling efficiency).
*   Use when the slight increase in warping latency is acceptable for the memory savings.

**When Not to Use:**
*   Use standard EDP if warping speed is more critical than memory usage and the scene has dense fragments.
*   Use BDP or UDP if memory is not a constraint and simpler implementation is preferred.

## Background
PEDP was introduced by Yang et al. in 2010 as part of the research on Potentially Visible Hidden-Volume Rendering (PVHVR) for Multi-View Warping [S1]. It builds on the concept of Effective Depth Peeling (EDP) by adding a fragment packing step to reduce the memory footprint of the depth peeling pipeline. The method was evaluated in the context of Depth-of-Field (DOF) rendering, where it demonstrated significant memory efficiency improvements over Baseline Depth Peeling (BDP) and Unordered Depth Peeling (UDP) [S1].
