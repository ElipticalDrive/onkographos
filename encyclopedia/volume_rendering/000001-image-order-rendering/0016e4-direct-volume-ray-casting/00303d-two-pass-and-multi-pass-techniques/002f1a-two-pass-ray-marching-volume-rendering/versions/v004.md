# Two-Pass Ray Marching Volume Rendering

Also called: INTMeshVolumeRendering

## Overview
Two-Pass Ray Marching Volume Rendering is a GPU-based technique that decouples the determination of ray entry and exit points from the actual volume traversal and color accumulation. It solves the problem of efficiently computing the correct integration bounds for rays intersecting a volumetric bounding box without requiring complex ray-box intersection math in the main rendering pass. It sets itself apart from standard ray casting by using a dedicated first pass to render the back-face depth of the volume box, which is then sampled in the second pass to constrain the marching range. This method builds on [Two-pass and Multi-pass Techniques](6224-two-pass-and-multi-pass-techniques.md) by utilizing an intermediate depth buffer to separate geometric bounds computation from optical compositing.

## How it works
The method operates in two distinct rendering passes using a `THREE.Mesh` object that extends the standard geometry to handle volume data.

**Inputs and Outputs:**
*   **Inputs:** A 3D scalar dataset (volume), a camera, a renderer, the bounding box dimensions ($size_x, size_y, size_z$), the number of marching steps ($N_{steps}$), and an opacity correction factor ($\alpha_{corr}$).
*   **Outputs:** A 2D color buffer containing the final rendered image with accumulated color and opacity.

**Data Structures:**
1.  **Volume Data Texture (`dataTex`):**
    *   Format: `THREE.AlphaFormat` (single channel).
    *   Type: `THREE.FloatType`.
    *   Dimensions: Width $W_{tex} = \min(\text{maxTextureSize}, \text{data.length})$. Height $H_{tex} = \lceil \text{data.length} / W_{tex} \rceil$.
    *   Layout: The 1D array of voxel values is padded with zeros to fill the rectangular texture dimensions.
2.  **Transfer Function Texture (`transfertTex`):**
    *   Format: `THREE.RGBAFormat`.
    *   Dimensions: $8 \times 256$ pixels.
    *   Layout: A linear gradient where the x-coordinate maps to the normalized scalar value (0.0 to 1.0) and the y-coordinate is uniform. Each pixel stores the RGBA color corresponding to that scalar value.
3.  **Intermediate Render Target (`rtTexture`):**
    *   Format: `THREE.RGBAFormat`.
    *   Type: `THREE.FloatType`.
    *   Dimensions: Matches the viewport (e.g., `window.innerWidth` $\times$ `window.innerHeight`).
    *   Purpose: Stores the depth/position of the back-face intersection from the first pass.

**Numbered Steps:**

1.  **Initialization:**
    *   Validate inputs: Ensure `renderer`, `camera`, and `size` are defined. If not, abort with an error [S1, unofficial].
    *   Create a `BoxGeometry` with dimensions $size_x, size_y, size_z$ and set `doubleSided = true`.
    *   Create `rtTexture` with `LinearFilter`, `ClampToEdgeWrapping`, and no mipmaps.
    *   Compute `dataTextureWidth` based on `renderer.capabilities.maxTextureSize`.
    *   Pad the input data array to fit `dataTextureWidth` $\times$ `dataTextureHeight`.
    *   Create `dataTex` from the padded data.
    *   Create `transfertTex` from the user-defined color stops.

2.  **First Pass (Back-Face Depth Rendering):**
    *   Create a temporary scene (`_sceneFirstPass`).
    *   Create a mesh using the `BoxGeometry` and a shader material configured with `side: THREE.BackSide`.
    *   The vertex shader computes the world position of the back face vertices.
    *   The fragment shader outputs the depth (or position) of the back face intersection.
    *   Render this scene to `rtTexture` using the main camera. This captures the depth of the volume's rear boundary relative to the camera.

3.  **Second Pass (Ray Marching and Compositing):**
    *   Create the main material with `side: THREE.FrontSide`.
    *   Uniforms passed to the shader:
        *   `tex`: Reference to `rtTexture`.
        *   `dataTex`: The volume data.
        *   `transfertTex`: The transfer function.
        *   `size`: Bounding box dimensions.
        *   `steps`: Number of marching steps ($N_{steps}$).
        *   `alphaCorrection`: Opacity correction factor ($\alpha_{corr}$).
        *   `minData`, `maxData`: Normalization bounds for the volume data.
    *   For each pixel in the viewport:
        *   Sample `tex` to retrieve the depth/position of the back face ($P_{back}$).
        *   Compute the ray origin ($P_{eye}$) and direction ($\vec{d}$) from the camera.
        *   Determine the entry point ($P_{front}$) by intersecting the ray with the front face of the bounding box (or using the near plane if inside).
        *   Calculate the total ray length inside the volume: $L = \| P_{back} - P_{front} \|$.
        *   Step size: $\Delta s = L / N_{steps}$.
        *   Initialize accumulated color $C_{acc} = (0,0,0,0)$ and accumulated opacity $\alpha_{acc} = 0$.
        *   Loop $i$ from 0 to $N_{steps}-1$:
            *   Current position: $P_i = P_{front} + i \cdot \Delta s \cdot \vec{d}$.
            *   Sample volume data at $P_i$ to get scalar value $v$.
            *   Normalize $v$: $v_{norm} = (v - \text{minData}) / (\text{maxData} - \text{minData})$.
            *   Lookup color $C_{vol}$ and opacity $\alpha_{vol}$ from `transfertTex` using $v_{norm}$.
            *   Apply opacity correction: $\alpha_{vol} = \alpha_{vol} \cdot \alpha_{corr}$ [S1, unofficial].
            *   Composite using front-to-back blending:
                $$ C_{acc} = C_{acc} + C_{vol} \cdot \alpha_{vol} \cdot (1 - \alpha_{acc}) $$
                $$ \alpha_{acc} = \alpha_{acc} + \alpha_{vol} \cdot (1 - \alpha_{acc}) $$
        *   Output $C_{acc}$ as the final pixel color.

**Pseudocode:**

```python
# Pseudocode for the Second Pass Fragment Shader Logic
# Inputs:
#   rt_depth: Texture sampled from rtTexture (contains back-face depth/position)
#   data_tex: Volume data texture
#   tf_tex: Transfer function texture (8x256)
#   size: Vector3(x, y, z) of the bounding box
#   steps: Integer number of marching steps
#   alpha_correction: Float opacity correction factor
#   min_data, max_data: Floats for normalization

def render_second_pass(screen_pos, camera):
    # 1. Get back-face position from first pass result
    # Note: The exact format stored in rtTexture depends on the first pass shader.
    # Assuming it stores the world position or depth along the ray.
    back_pos = sample_rt_texture(screen_pos)
    
    # 2. Determine ray parameters
    ray_origin = camera.position
    ray_direction = normalize(back_pos - ray_origin) # Simplified if back_pos is on ray
    
    # 3. Determine front-face intersection
    # In a simple box, this can be computed analytically or via a separate intersection function
    front_pos = intersect_ray_box(ray_origin, ray_direction, size)
    
    # 4. Calculate step size
    ray_length = distance(front_pos, back_pos)
    step_size = ray_length / steps
    
    # 5. Initialize accumulation
    acc_color = (0.0, 0.0, 0.0, 0.0)
    acc_alpha = 0.0
    
    # 6. Marching loop
    for i in range(steps):
        current_pos = front_pos + (i * step_size * ray_direction)
        
        # Sample volume data
        # Normalize coordinates to [0,1] for texture lookup
        u = (current_pos.x - box_min.x) / size.x
        v = (current_pos.y - box_min.y) / size.y
        w = (current_pos.z - box_min.z) / size.z
        
        raw_value = sample_volume(data_tex, u, v, w)
        
        # Normalize value
        if max_data != min_data:
            norm_value = (raw_value - min_data) / (max_data - min_data)
        else:
            norm_value = 0.0
            
        # Clamp to [0, 1]
        norm_value = clamp(norm_value, 0.0, 1.0)
        
        # Lookup transfer function
        # tf_tex is 8x256, map norm_value.x to x-axis
        tf_color = sample_texture(tf_tex, (norm_value, 0.5))
        vol_color = tf_color.rgb
        vol_alpha = tf_color.a
        
        # Apply opacity correction
        vol_alpha = vol_alpha * alpha_correction
        
        # Front-to-back compositing
        weight = vol_alpha * (1.0 - acc_alpha)
        acc_color = acc_color + (vol_color * weight)
        acc_alpha = acc_alpha + weight
        
    return acc_color
```

**Parameters:**
*   `steps`: Number of marching steps per ray. Default: 50. Higher values improve quality but reduce performance [S1, unofficial].
*   `alphaCorrection`: General opacity correction factor applied during compositing to adjust visual density. Default: 0.2 [S1, unofficial].
*   `size`: Dimensions of the volume bounding box [S1, unofficial].
*   `minData` / `maxData`: Min/max values of the dataset for normalization. Computed automatically if not provided [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Missing Parameters:** If `renderer`, `camera`, or `size` are undefined, the constructor fails silently or throws an error [S1, unofficial].
*   **Data Padding:** The volume data must be padded to fit the rectangular texture dimensions. Failure to pad correctly results in incorrect sampling [S1, unofficial].
*   **Precision:** Using `FloatType` for the render target ensures sufficient precision for depth/position storage, avoiding artifacts in the second pass [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N_{pixels} \cdot N_{steps})$. The first pass is $O(N_{vertices})$ (constant for a box). The second pass dominates, scaling linearly with the number of pixels and marching steps.
*   **Memory Complexity:** $O(N_{data} + N_{pixels})$. Requires storage for the volume data texture, the transfer function texture, and the intermediate render target.
*   **Performance:** The use of a fixed number of steps (default 50) provides consistent performance but may result in aliasing or blockiness if steps are too low. Increasing steps improves quality but lowers FPS [S1, unofficial].
*   **Strengths:** Simple implementation on GPU; decouples geometry intersection from optical calculation; efficient use of hardware blending.
*   **Limitations:** Fixed step size may be inefficient for sparse volumes (marches through empty space); no early ray termination in the basic description; requires the volume to be contained within a simple bounding box.
*   **When to use:** Real-time visualization of dense volumetric data where approximate rendering is acceptable and hardware support for float render targets is available.

## Background
The method is implemented in the `INTMeshVolumeRendering` class, part of the WebGL Volume Rendering library by Interactive Network Technologies. It was authored by Vincent Dumestre and Nathan Krupa. The code is hosted on GitHub [S1, unofficial]. It is designed for use with the Three.js library.
