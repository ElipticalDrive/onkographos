# Locally Adaptive Volume Rendering

Also called: Contribution Map Based Volume Rendering, Implementation of Locally Adaptive Volume Rendering

## Overview
Locally Adaptive Volume Rendering (LAVR) is a two-pass technique that enhances feature visibility and reduces noise in volume rendering by dynamically adjusting fragment opacity based on the local density of contributing voxels [S1]. Unlike standard direct volume rendering which uses a fixed per-voxel opacity, LAVR decouples the classification of relevant data from the final compositing, allowing the renderer to adaptively suppress noise in sparse regions while preserving sharp borders in dense regions [S1]. It sets itself apart from siblings like [Two-pass volume rendering](1292-two-pass-volume-rendering.md) by specifically targeting the statistical distribution of contributions per pixel rather than just splitting light transport or ray marching steps.

## How it works
LAVR operates as a slicing-based approach on graphics hardware using 3D textures, consisting of two distinct passes [S1].

### Inputs and Outputs
*   **Input:** A 3D scalar volume dataset ($V$), a binary classification function ($\delta$) derived from a transfer function, and a 1D lookup texture ($\alpha_{lookup}$).
*   **Output:** A 2D color buffer with adaptively modulated opacity.

### Data Structures
1.  **Contribution Map:** A 2D floating-point texture (Frame Buffer Object) with dimensions matching the screen resolution ($W \times H$). It stores the count of relevant contributions for each pixel.
2.  **Alpha Lookup:** A 1D texture mapping the contribution count (normalized to $[0, 1]$) to a final opacity value.

### Steps

**Pass 1: Contribution Map Generation**
1.  Render the volume dataset using a slicing proxy (e.g., a bounding box or slice planes).
2.  For each fragment, evaluate the binary classification function $\delta(s)$ based on the scalar value $s$ of the voxel at the fragment's position.
3.  If $\delta(s) = 1$ (relevant contribution), add $1.0$ to the pixel's color value using additive blending. If $\delta(s) = 0$, add $0.0$.
4.  The result is a 2D texture where each pixel $(x, y)$ contains the integer count $n(x, y)$ of relevant voxels along the ray passing through that pixel.

**Pass 2: Adaptive Compositing**
1.  Bind the Contribution Map as a 2D texture sampler.
2.  Render the volume dataset again using the same slicing geometry.
3.  In the fragment shader, for each fragment:
    a.  Sample the 3D dataset to retrieve scalar values $s_1$ and $s_2$ at the entry and exit points of the ray segment within the current slice/proxy.
    b.  Sample the Contribution Map at the fragment's normalized screen coordinates $(x_c, y_c)$ to retrieve the total contribution count $n$.
    c.  Sample the transfer function to retrieve the base color $C$ and base opacity $\alpha_{base}$ for the scalar values.
    d.  Calculate the final opacity $\alpha_{final}$ by sampling the $\alpha_{lookup}$ texture with the normalized count $n / N_{max}$ (where $N_{max}$ is the maximum possible contributions, often the volume depth or a fixed constant).
    e.  Set the fragment color to $C$ and opacity to $\alpha_{final}$ if $\alpha_{base} > 0$, otherwise set opacity to 0.

### Pseudocode

```python
# Pass 1: Contribution Map
# Render target: contribution_map (2D float texture, initialized to 0)
# Blending: ADD

def pass1_fragment_shader():
    # Sample scalar value at current ray position
    scalar = sample_3d_texture(dataset, ray_position)
    
    # Binary classification: 1 if relevant, 0 otherwise
    # Typically based on opacity threshold from transfer function
    if transfer_function_opacity(scalar) > 0.0:
        return vec4(1.0, 0.0, 0.0, 0.0) # Add 1 to red channel (or alpha)
    else:
        return vec4(0.0, 0.0, 0.0, 0.0)

# Pass 2: Adaptive Rendering
# Inputs: dataset (3D), contribution_map (2D), alpha_lookup (1D), transfer_function (2D)

def pass2_fragment_shader():
    # 1. Retrieve geometric/scalar data
    scalar_entry = sample_3d_texture(dataset, ray_entry_point)
    scalar_exit = sample_3d_texture(dataset, ray_exit_point)
    
    # 2. Retrieve local contribution count
    # Normalize screen coordinates to [0, 1]
    xc = gl_FragCoord.x / fbo_x_size
    yc = gl_FragCoord.y / fbo_y_size
    
    # Sample the contribution map (stored in Pass 1)
    # Note: The source stores the count in the red channel or similar
    contrib_count = float(texture2D(contribution_map, vec2(xc, yc)))
    
    # 3. Retrieve base color and opacity from transfer function
    # The source uses a 2D lookup for color based on two scalar values
    color_sample = texture2D(transfer_function, vec2(scalar_exit, scalar_entry))
    base_color = color_sample.rgb
    base_alpha = color_sample.a
    
    # 4. Determine final opacity
    if base_alpha > 0.0:
        # Map contribution count to opacity via lookup table
        # The lookup table handles the adaptive scaling
        # Normalization of contrib_count depends on implementation, 
        # often divided by max possible depth or handled by LUT design
        final_alpha = float(texture1D(alpha_lookup, contrib_count))
    else:
        final_alpha = 0.0
        
    return vec4(base_color, final_alpha)
```

### Parameters
*   **$\alpha_{lookup}$**: A 1D texture mapping contribution counts to opacity. The shape of this curve determines the visual style (e.g., suppressing noise in low-count regions).
*   **Binary Threshold**: The threshold used in Pass 1 to determine $\delta(s)$. Typically derived from the transfer function's opacity channel.

### Edge Cases and Pitfalls
*   **Precision**: The contribution map must use sufficient precision (e.g., 32-bit float) to avoid overflow for large volumes or high-resolution slices.
*   **Filtering**: The contribution map may exhibit noise. The source suggests an alternative implementation where the contribution map is rendered at a lower resolution and stretched using bilinear filtering to smooth the count, trading accuracy for performance [S1].
*   **Normalization**: The input to $\alpha_{lookup}$ must be correctly normalized. If the LUT expects $[0, 1]$ but receives raw counts, the mapping will be incorrect.

## Operating characteristics
*   **Time Complexity**: $O(N)$ where $N$ is the number of pixels, performed twice (two passes). The cost is dominated by texture sampling and blending.
*   **Memory Complexity**: Requires one additional 2D texture for the contribution map, sized $W \times H$ (screen resolution).
*   **Performance**: Faster than full ray-marching integration per pixel because it relies on hardware rasterization of slice proxies. The alternative bilinear filtering approach for smoothing the contribution map is faster but less accurate [S1].
*   **Strengths**: Enhances internal high-frequency details, sharpens borders in DVR, and prevents saturation in additive rendering by adapting to local density [S1].
*   **Limitations**: Requires two passes; relies on the quality of the binary classification; may introduce artifacts if the contribution map is not smoothed appropriately.

## Background
Locally Adaptive Volume Rendering was introduced by [S1] (Feature Enhancement using Locally Adaptive Volume Rendering, 2007) as a method to improve the visual quality of volume rendering by adapting the opacity based on the local number of contributing voxels. It builds on the principles of direct volume ray casting but introduces a pre-pass to gather statistical information about the volume density along each ray.
