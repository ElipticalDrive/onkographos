# Binary Swap Compositing

Also called: Binary Split Compositing, Binary Swap, MPI Binary-Swap, binary-swap merging

## Overview
Binary Swap Compositing is a parallel image compositing scheme for distributed-memory volume rendering that reduces network congestion by dividing communication between processors over multiple rounds [S1]. Unlike naive binary compositing where many processors become idle at the top of the tree, Binary Swap ensures every processor participates in all stages of the compositing process by splitting the image plane into two pieces and having each processor take responsibility for one piece during exchange and compositing [S4, unofficial]. It is particularly suitable for massively parallel processing because it keeps all processors busy and decreases the image size for sending/compositing at each stage [S3, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** $N$ processors, where $N$ is the number of processors participating in the compositing tree. Each processor $p$ holds a local sub-image $I_p$ generated by independent ray-tracing of its assigned sub-volume. The number of processors $N$ must be a perfect power of two ($N = 2^K$) for the standard implementation [S2][S3, unofficial][S4, unofficial].
*   **Output:** Each processor holds exactly $1/N$ of the final composited image [S10].

**Data Structures:**
*   **Image Plane:** Represented as a 2D array of pixels. Each pixel contains color $(C_r, C_g, C_b)$ and opacity $\alpha$.
*   **Partner Index:** Calculated using bitwise XOR. For a processor with ID `self` and current `stride`, the partner is `partner = self XOR stride` [S3, unofficial][S4, unofficial].
*   **Pairing Graph (Optional Implementation Detail):** A 3D array `pair[level][zdiv][2]` can be used to store the compositing graph, where `level` is $\log_2(zdiv)$, `pair[l][j][0]` stores the partner rank index for rank `j` at level `l`, and `pair[l][j][1]` stores the role (0 for first/sender, 1 for second/receiver) [S6, unofficial].

**Algorithm Steps:**
1.  **Initialization:** Initialize the image plane on each processor to the entire image area (or the sub-image generated by local ray-tracing) [S3, unofficial][S4, unofficial].
2.  **Loop Setup:** Calculate the number of levels in the binary swap tree: $L = \log_2 N$ [S6, unofficial]. Initialize `stride` to 1.
3.  **Iteration:** Iterate through $L$ phases (or $\log_2(\text{nproc})$ rounds) [S1][S3, unofficial]. In each phase:
    a.  **Partner Calculation:** Calculate the partner processor index: `partner = self XOR stride` [S3, unofficial][S4, unofficial].
    b.  **Subdivision:** Subdivide the current image plane held by the processor into two equal pieces (e.g., left/right halves or top/bottom halves) [S3, unofficial][S4, unofficial]. The subdivision direction alternates between stages (e.g., X-axis in the first stage, Y-axis in the second) [S8].
    c.  **Exchange:** Exchange the relevant half-image data with the calculated partner processor. Each processor sends one half of its image to the partner and receives the partner's corresponding half [S3, unofficial][S4, unofficial].
    d.  **Compositing:** Composite the part of the remaining image plane held by the processor with the image data received from the partner using the standard front-to-back over operator [S3, unofficial][S4, unofficial].
        *   Let $C_{local}, \alpha_{local}$ be the color and opacity of the kept half.
        *   Let $C_{recv}, \alpha_{recv}$ be the color and opacity of the received half.
        *   The new accumulated color and opacity for the kept half are updated as:
            $$ C_{new} = C_{local} + (1 - \alpha_{local}) \alpha_{recv} C_{recv} $$
            $$ \alpha_{new} = \alpha_{local} + (1 - \alpha_{local}) \alpha_{recv} $$
        *   Note: The specific assignment of which half is "kept" and which is "received" depends on the role (0 or 1) defined in the pairing graph or the XOR result [S6, unofficial].
4.  **Stride Update:** Update the stride for the next phase by multiplying it by 2: `stride *= 2` [S3, unofficial][S4, unofficial].
5.  **Termination:** After $\log_2 N$ stages, compositing completes. Each processor holds exactly $1/N$ of the final image [S10].

```python
def binary_swap_compositing(self_id, nproc, local_image):
    """
    Performs Binary Swap Compositing.
    
    Args:
        self_id (int): The unique ID of the current processor (0 to nproc-1).
        nproc (int): Total number of processors (must be a power of 2).
        local_image (Image): The local sub-image generated by ray-tracing.
                             Image is a 2D array of pixels with (color, opacity).
    
    Returns:
        Image: The portion of the final image assigned to this processor.
    """
    # Initialize the image plane to the entire local sub-image
    # Note: In a distributed setting, 'local_image' initially covers the 
    # full image dimensions but contains valid data only for the assigned region.
    # For the purpose of the swap algorithm, we treat the image plane as 
    # the full canvas, but operations are only valid/meaningful within 
    # the bounding box of non-blank pixels [S9].
    current_image = local_image 
    
    stride = 1
    while stride < nproc:
        # Calculate partner using XOR
        partner_id = self_id ^ stride
        
        # Determine subdivision direction based on stride (alternating X/Y)
        # This is a common implementation detail to balance load [S8]
        if (stride & (stride - 1)) == 0: # Power of 2 check for simplicity
            # First stage (stride=1): Split along X-axis (Left/Right)
            split_axis = 'x'
        else:
            # Subsequent stages: Alternate or follow specific pattern
            # For simplicity, we assume alternating or fixed pattern based on level
            # The key is that the split divides the current image held by the processor
            split_axis = 'y' if split_axis == 'x' else 'x'
            
        # Subdivide the current image plane into two pieces
        # Piece A: The part the current processor keeps
        # Piece B: The part to send to the partner
        if split_axis == 'x':
            # Split vertically (Left/Right)
            mid_x = current_image.width // 2
            keep_piece = current_image.crop(0, 0, mid_x, current_image.height)
            send_piece = current_image.crop(mid_x, 0, current_image.width, current_image.height)
        else:
            # Split horizontally (Top/Bottom)
            mid_y = current_image.height // 2
            keep_piece = current_image.crop(0, 0, current_image.width, mid_y)
            send_piece = current_image.crop(0, mid_y, current_image.width, current_image.height)
            
        # Exchange image data with partner
        # In a real MPI implementation, this would be MPI_Sendrecv
        recv_piece = communicate_with_partner(partner_id, send_piece)
        
        # Composite the kept piece with the received piece
        # The compositing order depends on the spatial arrangement of sub-volumes
        # and the role (0 or 1) in the pairing graph [S6, unofficial].
        # Assuming standard front-to-back compositing where 'keep' is 'front' 
        # relative to 'recv' or vice versa based on rank order.
        # Here we assume 'keep' is composited over 'recv' if keep is 'front',
        # or 'recv' is composited over 'keep'. 
        # The standard BS algorithm implies a specific order determined by the 
        # tree structure. We use the standard over operator.
        current_image = composite_over(keep_piece, recv_piece)
        
        # Update stride
        stride *= 2
        
    return current_image

def composite_over(front, back):
    """
    Composites two image pieces using the front-to-back over operator.
    Assumes 'front' is closer to the camera than 'back'.
    """
    result = Image(front.width, front.height)
    for y in range(front.height):
        for x in range(front.width):
            c_f, a_f = front.get_pixel(x, y)
            c_b, a_b = back.get_pixel(x, y)
            
            # Standard front-to-back compositing
            # C_acc = C_acc + (1 - alpha_acc) * alpha_i * C_i
            # alpha_acc = alpha_acc + (1 - alpha_acc) * alpha_i
            
            # Here, 'front' is the new sample, 'back' is the accumulator
            # However, in BS, we are merging two independent halves.
            # The order depends on the specific implementation's role assignment.
            # We assume a consistent order: lower rank is 'front' or 'back'
            # based on the pairing graph role [S6, unofficial].
            # For this generic function, we assume 'front' is composited 
            # over 'back'.
            
            transmittance = 1.0 - a_b
            c_new = c_f * a_f + c_b * a_b * transmittance
            a_new = a_f + a_b * transmittance
            
            # Clip opacity to [0, 1]
            a_new = min(1.0, a_new)
            
            result.set_pixel(x, y, c_new, a_new)
    return result
```

**Parameters:**
*   `nproc`: The total number of processors participating in the compositing tree. Must be a perfect power of two [S2][S3, unofficial][S4, unofficial].
*   `p`: Number of pixels in the final image [S9].
*   `g`: Transmitting time per pixel [S9].
*   `t_c`: Computing time per pixel [S9].
*   `o`: Communication overhead per transmission [S9].

**Edge Cases and Pitfalls:**
*   **Power of Two Restriction:** The algorithm requires the number of processors to be a power of two. If `nproc` is not a perfect power of two, the simple XOR partner calculation fails [S3, unofficial]. The algorithm can be generalized by keeping a full (but not necessarily complete) binary tree, requiring additional complexity in partner computation and leaving some processors idle during the first phase [S3, unofficial].
*   **Synchronization Overhead:** There is a synchronization overhead after each round [S1].
*   **Load Imbalance:** On heterogeneous workstation networks, achieving linear speedup is difficult due to load imbalance [S3, unofficial]. Static load balancing can be addressed by uneven data subdivision based on predicted machine capacity [S3, unofficial].
*   **Sparsity:** Only non-blank pixels affect composited results. The BS method exploits sparsity by using a bounding rectangle enclosing the non-blank region. Every processor composites and transmits only within this bounding rectangle [S9].

## Subtopics

### Local Pixel Merging (LPM)
Local Pixel Merging is a compositing method where the composition operation for each local pixel involves the merging of $k$ sorted ray-segment lists, where $k$ denotes the number of distinct processors that generated ray-segments for that particular pixel [S11, unofficial]. It partitions the screen into $K$ subregions such that each processor is responsible for producing the final image of a distinct subregion through local pixel merging. A binary heap is used for the $k$-way merging of ray-segment lists from the RayBuffer structures [S11, unofficial]. This method is used when projection areas of local subvolumes overlap on the image screen, requiring a global merge operation on ray-segment lists of local RayBuffer structures to composite ray-segments of each pixel in visibility order for the final image [S11, unofficial].

### Reduced Binary Swap
Reduced Binary Swap is a variant of Binary Swap that uses only $2^{K-1}$ processors for compositing when $N$ is not a power-of-two ($2^{K-1} < N < 2^K$) [S10]. It requires extra image data exchange in the reduction stage, sending images from $N - 2^{K-1}$ processors to the remaining $2^{K-1}$ processors [S10]. This variant nearly doubles the image blending workload for a large number of processors compared to standard Binary Swap [S10].

## Operating characteristics
**Time and Memory Complexity:**
*   **Messages:** Reduces the number of messages exchanged from $N \times (N - 1)$ (direct send) to $N \log N$ [S10].
*   **Latency:** $l_{sendrecv} \times \log_2 N$ [S10].
*   **Bandwidth:** $(1/B_{sendrecv}) \times P$ [S10].
*   **Blending:** $(1/B_{blend}) \times 2 \times P \times (1 - 1/N)$ [S10].
*   **Average Compositing Time:** Bounded by $t_{BS} \leq p (g + t_c) \cdot 2.43 n^{-2/3} + o \cdot \log n$, where $n$ is the number of processors, $p$ is the number of pixels, $g$ is transmitting time per pixel, $t_c$ is computing time per pixel, and $o$ is communication overhead per transmission [S9].

**Measured Performance:**
*   On a CM-5 with 512 nodes, rendering a 512x512 head dataset took 36.3685 seconds for rendering and 0.63320 seconds for compositing [S3, unofficial].
*   On a CM-5 with 512 nodes, rendering a 512x512 vessel dataset took 26.0314 seconds for rendering and 0.46060 seconds for compositing [S3, unofficial].
*   On a CM-5 with 512 nodes, rendering a 512x512 vorticity dataset took 48.2005 seconds for rendering and 0.71520 seconds for compositing [S3, unofficial].
*   On a CM-5 with 512 nodes, compositing the vorticity dataset took 0.3310 seconds with 0.0097 seconds spent on communication [S3, unofficial].
*   On a PVM network with 32 workstations, rendering a 512x512 head dataset took 8.4990 seconds for rendering and 4.3550 seconds for compositing [S3, unofficial].
*   On a PVM network with 32 workstations, compositing the vorticity dataset took 4.5180 seconds with 4.4990 seconds spent on communication [S3, unofficial].
*   Compositing speedup from 32 to 512 nodes was only 1.46 for 64x64 images [S3, unofficial].

**Strengths and Limitations:**
*   **Strengths:** Keeps all processors busy, decreasing image size for sending/compositing makes the process efficient, suitable for massively parallel processing [S3, unofficial].
*   **Limitations:** Requires power-of-two processors, synchronization overhead, load imbalance on heterogeneous networks [S1][S3, unofficial].

**When to Use:**
*   Use when running on massively parallel computers with a power-of-two number of processors and when interactive rendering rates are desired [S4, unofficial].
*   Use when network congestion is a concern and a hierarchical communication scheme is preferred over all-to-all patterns [S5, unofficial].

**When Not to Use:**
*   Do not use if the number of processors is not a power of two and the overhead of Reduced Binary Swap or 2-3 Swap is unacceptable [S10].
*   Do not use if the image size is very small (e.g., 64x64) where communication overhead dominates [S3, unofficial].

## Background
Binary Swap Compositing was introduced as a generalization of the binary compositing method to avoid the bottleneck of idle processors in massively parallel processing [S4, unofficial]. It was developed by researchers implementing distributed volume rendering algorithms on systems like the CM-5 and networked workstations [S3, unofficial]. The method is particularly suitable for massively parallel processing because it keeps all processors busy and uses decreasing image sizes for efficiency [S3, unofficial]. It differs from naive binary compositing by keeping all processors active throughout the process, whereas binary compositing leaves many processors idle as the tree height increases [S8].
