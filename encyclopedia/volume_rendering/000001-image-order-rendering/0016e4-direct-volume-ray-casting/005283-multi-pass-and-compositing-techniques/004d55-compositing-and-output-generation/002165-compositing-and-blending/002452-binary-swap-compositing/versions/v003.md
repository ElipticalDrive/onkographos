# Binary Swap Compositing

Also called: Binary-Swap Method, MPI Binary-Swap, Parallel Binary-Swap Compositing, Parallel Compositing, Parallel Image Compositing, Parallel Image Merging, binary-swap merging

## Overview
Binary Swap Compositing is a parallel image merging algorithm used to combine independently rendered sub-images from multiple processors into a final volume-rendered image [S1, S2, S3, unofficial]. It solves the bottleneck problem of naive binary compositing, where processors become idle as the compositing tree narrows, by ensuring every processor participates in every stage of the merge [S1, S2, unofficial]. It sets itself apart from sibling methods like [Compositing](2436-compositing.md) by explicitly managing distributed memory communication via a binary-swap tree structure, and from [Pre-Integration Lookup](2854-pre-integration-lookup.md) by operating on already-composited sub-images rather than raw samples.

## How it works
**Inputs and Outputs:**
*   **Input:** Local sub-images (color $C$ and opacity $\alpha$) generated by each processor from its assigned sub-volume. The total number of processors $nproc$ (or depth partitions $PZ$) is typically a power of two [S1, S2, S3, unofficial].
*   **Output:** The final composited image on all processors (or a designated root, depending on implementation; standard binary-swap usually results in the full image on all nodes or requires a final gather) [S1, S2, unofficial].

**Data Structures:**
*   **Local Image State:** Each processor maintains two arrays: `local_composite_color` (RGB) and `local_composite_opacity` (A), initialized to the result of local ray casting [S4, unofficial].
*   **Pairing Graph (Optional):** A 3D array `pair[level][zdiv][2]` can be precomputed to store partner indices and roles (sender/receiver) for each level of the compositing tree, where `level` ranges from $0$ to $\log_2(zdiv)-1$ [S3, unofficial].

**Algorithm Steps:**
1.  **Initialization:** Each processor initializes its image plane to the full image area (conceptually) or holds its local sub-image which represents the contribution of its sub-volume [S1, S2, unofficial]. In practice, the image size effectively halves in terms of *unique* data contribution at each step, but the buffer size remains constant or is managed via exchange [S1, unofficial].
2.  **Phase Loop:** Iterate through $L = \log_2(nproc)$ phases. Let `stride` start at 1 and double each phase (`stride *= 2`) until `stride >= nproc` [S1, S2, unofficial].
3.  **Partner Calculation:** In each phase, calculate the partner processor index using bitwise XOR:
    $$ partner = self \oplus stride $$
    where $\oplus$ is the bitwise XOR operator [S1, S2, S4, unofficial].
4.  **Image Subdivision:** Subdivide the current image plane held by the processor into two pieces (e.g., left/right or top/bottom halves) [S1, S2, unofficial]. *Note: In many implementations, the "subdivision" refers to the logical split of responsibility, where one half of the image pixels are kept locally and the other half are exchanged, or the image is split spatially to match the data partitioning [S1, S2, unofficial].*
5.  **Communication:** Exchange the relevant half-image data with the calculated partner processor [S1, S2, unofficial].
    *   If `partner > self`, send the local half-image to the partner [S4, unofficial].
    *   If `partner < self`, receive the partner's half-image [S4, unofficial].
    *   *Alternative Implementation (Z-axis only):* If data is partitioned only along the Z-axis, the image is not spatially subdivided. Instead, the entire local composite image is exchanged with the partner along the Z-axis [S4, unofficial].
6.  **Compositing:** Composite the part of the image kept locally with the image data received from the partner using the front-to-back over operator [S1, S2, S4, unofficial].
    *   Let $C_{local}, \alpha_{local}$ be the kept portion and $C_{recv}, \alpha_{recv}$ be the received portion.
    *   Calculate remaining opacity: $\alpha_{rem} = 1 - \alpha_{local}$ [S4, unofficial].
    *   Update color: $C_{new} = C_{local} + \alpha_{rem} \cdot C_{recv}$ [S4, unofficial].
    *   Update opacity: $\alpha_{new} = \alpha_{local} + \alpha_{rem} \cdot \alpha_{recv}$ [S4, unofficial].
    *   Clip $\alpha_{new}$ to $[0, 1]$ [S4, unofficial].
7.  **Update:** Update the local accumulators with $C_{new}$ and $\alpha_{new}$ [S4, unofficial].
8.  **Repeat:** Continue to the next phase with `stride *= 2` [S1, S2, unofficial].

**Pseudocode:**
```python
def binary_swap_compositing(local_color, local_opacity, rank, num_ranks, comm):
    """
    Performs binary-swap compositing along the Z-axis (depth) partitioning.
    Assumes num_ranks is a power of 2.
    """
    # local_color and local_opacity are arrays of shape (H, W, 3) and (H, W)
    
    step = 1
    while step < num_ranks:
        # Calculate partner rank using XOR
        partner_rank = rank ^ step
        
        # Determine if this rank is the sender or receiver
        # Convention: Higher rank sends, lower rank receives
        if partner_rank > rank:
            # Send local composite to partner
            comm.Send(local_color, dest=partner_rank)
            comm.Send(local_opacity, dest=partner_rank)
        else:
            # Receive composite from partner
            recv_color = np.empty_like(local_color)
            recv_opacity = np.empty_like(local_opacity)
            comm.Recv(recv_color, source=partner_rank)
            comm.Recv(recv_opacity, source=partner_rank)
            
            # Composite received data with local data
            # Front-to-back: Local is "front", Received is "back" relative to the 
            # accumulated state if we assume a specific ordering. 
            # However, binary swap typically merges two independent contributions.
            # The order depends on the spatial arrangement. 
            # Standard formula: C_out = C1 + (1 - A1) * C2
            # Here, we treat 'local' as the first part and 'recv' as the second.
            
            remaining_opacity = 1.0 - local_opacity
            
            # Update color
            local_color = local_color + remaining_opacity[:, :, None] * recv_color
            
            # Update opacity
            local_opacity = local_opacity + remaining_opacity * recv_opacity
            
            # Clip opacity to [0, 1]
            local_opacity = np.clip(local_opacity, 0.0, 1.0)
            
        step *= 2
        
    return local_color, local_opacity
```

**Edge Cases and Pitfalls:**
*   **Non-Power-of-Two Processors:** If $nproc$ is not a perfect power of two, the simple XOR partner calculation fails [S1, S2, unofficial]. The algorithm must be generalized to a full (but not necessarily complete) binary tree, requiring additional complexity in partner computation and leaving some processors idle during the first phase [S1, S2, unofficial].
*   **Load Imbalance:** On heterogeneous networks, achieving linear speedup is difficult due to load imbalance [S1, unofficial]. Static load balancing can be addressed by uneven data subdivision or assigning multiple subvolumes to more capable machines [S1, unofficial].
*   **Communication Overhead:** As image size increases, communication time increases [S1, unofficial]. On PVM networks, communication can dominate compositing time (e.g., 4.4990s out of 4.5180s for vorticity data on 32 workstations) [S1, unofficial].

## Subtopics

### Local Pixel Merging (LPM)
Local Pixel Merging is a variant where the screen is partitioned into subregions, and each processor is responsible for producing the final image of a distinct subregion through local merging of ray-segments [S5, unofficial]. It involves three steps: pixel assignment (PA), ray-segment migration (RSM), and local pixel merging (LPM) [S5, unofficial]. In the LPM step, each processor concurrently composites gathered ray-segments for its assigned pixels using a binary heap for k-way merging of sorted ray-segment lists from different processors [S5, unofficial]. It is chosen when ray-segment lists from multiple processors overlap on the same pixel locations, requiring a global merge operation in visibility order [S5, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(\log nproc)$ communication phases [S1, S2, unofficial]. Each phase involves exchanging half the image data (or the full image in Z-only partitioning) and performing pixel-wise compositing [S1, S4, unofficial].
*   **Memory Complexity:** $O(H \times W)$ per processor for storing the local image buffers [S4, unofficial].
*   **Measured Performance:**
    *   On a CM-5 with 512 nodes, compositing a 512x512 vorticity dataset took 0.3310 seconds, with only 0.0097 seconds spent on communication [S1, unofficial].
    *   On a PVM network with 32 workstations, compositing the same dataset took 4.5180 seconds, with 4.4990 seconds spent on communication [S1, unofficial].
    *   Compositing speedup from 32 to 512 nodes was only 1.46 for 64x64 images due to overhead [S1, unofficial].
*   **Strengths:** Keeps all processors busy during compositing, avoiding the idle-time bottleneck of naive binary trees [S1, S2, unofficial]. Efficient for massively parallel processing [S1, unofficial].
*   **Limitations:** Sensitive to network latency and bandwidth; communication can dominate on slow networks [S1, unofficial]. Requires $nproc$ to be a power of two for optimal simplicity [S1, unofficial].

## Background
Binary Swap Compositing was introduced in 1994 by Chen, Johnson, and others in the paper "A Data Distributed Parallel Algorithm for Ray-Traced Volume Rendering" [S1, S2, unofficial]. It was developed to address the performance bottleneck of compositing on massively parallel computers like the CM-5, where naive binary compositing left most processors idle [S1, S2, unofficial]. The method was implemented on both the CM-5 and a network of scientific workstations [S1, unofficial].
