# Feed-Backward Reconstruction

Also called: Gather-based reconstruction, Ray-casting approach

## Overview
Feed-backward reconstruction is a technique for resampling discrete input data into a higher-resolution output grid by treating the reconstruction kernel as a gather operation. It solves the problem of generating smooth, continuous output values from discrete samples by computing each output pixel individually, centering the reconstruction kernel at the output position, and summing the weighted contributions of all input samples lying within the kernel's support [S1, unofficial]. It is distinguished from its sibling [Feed-Forward Reconstruction](2513-feed-forward-reconstruction.md) by its access pattern: it accesses each output sample exactly once while accessing input samples multiple times, making it the natural choice for image-order rendering where output pixels are processed sequentially [S1, unofficial].

## How it works
**Inputs and Outputs:**
- **Input:** A set of discrete input samples $X_j$ (where $j$ indexes the input domain) and a reconstruction kernel $K(u)$ defined by its shape (e.g., linear/triangular, B-spline) and support width.
- **Output:** A set of output samples $A_i$ (where $i$ indexes the output domain, typically the pixel grid).

**Data Structures:**
- **Input Array:** $X$ of size $N_{in}$.
- **Output Array:** $A$ of size $N_{out}$.
- **Kernel:** A function $K(\cdot)$ or a lookup table of weights.

**Algorithm Steps:**
1. Initialize the output array $A$ to zero.
2. Iterate through each output sample index $i$ from $0$ to $N_{out}-1$.
3. For each output sample $i$:
    a. Initialize a temporary accumulator $Acc = 0$.
    b. Identify the set of input indices $J_i$ such that the input sample $X_j$ lies within the support of the kernel centered at output position $i$. Mathematically, $j \in J_i$ if $|pos(i) - pos(j)| \leq \text{support\_width}/2$.
    c. For each $j \in J_i$:
        i. Calculate the relative distance $u = pos(i) - pos(j)$.
        ii. Compute the kernel weight $w = K(u)$.
        iii. Update accumulator: $Acc \leftarrow Acc + X_j \cdot w$.
    d. Assign the result: $A_i = Acc$.

**Pseudocode:**
```python
def feed_backward_reconstruction(input_samples, output_positions, kernel_function):
    """
    Reconstructs output samples by gathering weighted input samples.
    
    Args:
        input_samples: List of (position, value) tuples for input data.
        output_positions: List of positions for output pixels.
        kernel_function: Function K(u) returning weight for distance u.
        
    Returns:
        List of output values.
    """
    # Sort inputs by position for efficient neighbor search if needed
    sorted_inputs = sorted(input_samples, key=lambda x: x[0])
    n_out = len(output_positions)
    output_values = [0.0] * n_out
    
    for i in range(n_out):
        out_pos = output_positions[i]
        accumulator = 0.0
        
        # Find input samples within kernel support
        # In practice, this is often optimized using spatial hashing or bounding boxes
        for in_pos, in_val in sorted_inputs:
            dist = abs(out_pos - in_pos)
            
            # Check if input sample is within kernel support
            # Assuming kernel has finite support defined by kernel_function or a constant
            if dist <= kernel_function.support_width:
                weight = kernel_function(dist)
                accumulator += in_val * weight
                
        output_values[i] = accumulator
        
    return output_values
```

**Parameters:**
- **Kernel Support Width:** Determines how many input samples contribute to each output. For linear reconstruction, this is typically 2 units (in normalized coordinate space).
- **Sampling Rate:** The ratio of output samples to input samples. Higher rates increase accuracy but also computational cost.

**Edge Cases and Pitfalls:**
- **Boundary Conditions:** Input samples near the edges of the domain may have fewer neighbors within the kernel support. The kernel weights must be calculated correctly even if the kernel extends beyond the input data range (usually resulting in zero contribution for out-of-bounds samples) [S1, unofficial].
- **Precision:** Accumulating many small weights can lead to floating-point precision issues. Using double precision for the accumulator is recommended for high dynamic range scenes [G].
- **Degenerate Input:** If input samples are not sorted or have duplicate positions, the neighbor search must handle these cases explicitly [G].

## Subtopics

### [Spatial Convolution](2513-spatial-convolution.md)
Spatial Convolution is the direct application of a reconstruction kernel to discrete input samples in the spatial domain to produce output values. It solves the problem of reconstructing a continuous signal from discrete samples by gathering contributions from neighboring input samples for each output position. It is distinguished from frequency-domain convolution by avoiding Fourier transforms, making it computationally preferred for small, limited-extent kernels typical in volume rendering. Unlike standard convolution, it can be extended to spatially varying kernels where the weighting function depends on the specific output pixel, though this precludes the use of standard FFT-based acceleration.

### [Area-based Pixel Kernel](14355-area-based-pixel-kernel.md)
The Area-based Pixel Kernel is a reconstruction kernel used in feed-backward reconstruction that assigns pixel contributions proportional to the geometric area of intersection between a pixel and a thick projection line. It solves the artifact issues inherent in Dirac and B-Spline kernels, which leave unreconstructed pixels during subsampling, and linear kernels, which fail to fully exploit available data during oversampling. It is distinguished from its sibling [Spatial Convolution](2513-spatial-convolution.md) by its specific geometric interpretation of projection thickness and its optimization via rotation-based approximation.

## Operating characteristics
**Time Complexity:** $O(N_{out} \cdot K)$, where $N_{out}$ is the number of output samples and $K$ is the number of input samples within the kernel support. Since $K$ is constant for a fixed kernel width, the complexity is linear with respect to the output resolution [S1, unofficial].

**Memory Complexity:** $O(N_{in} + N_{out})$ to store the input and output arrays. No additional large temporary buffers are required beyond the accumulator [S1, unofficial].

**Performance:** The method is efficient for image-order rendering because it aligns with the natural loop structure of rasterization. However, it may suffer from cache inefficiency if the input samples are not spatially coherent or if the kernel support is large, leading to random access patterns in the input array [S1, unofficial].

**Strengths:**
- Produces identical results to feed-forward methods [S1, unofficial].
- Natural fit for ray casting and image-order rendering.
- Easy to implement with standard convolution kernels.

**Limitations:**
- Accesses input samples multiple times, which can be cache-unfriendly for large datasets.
- Performance degrades with larger kernel supports or higher sampling rates.

**When to Use:**
- When rendering output pixels in a sequential, image-order manner.
- When the kernel support is small and fixed.
- When memory bandwidth is not the primary bottleneck.

**When Not to Use:**
- When the input data is extremely large and cache misses dominate performance.
- When a feed-forward approach is more suitable for the hardware architecture (e.g., GPU fragment shaders with specific memory layouts).

## Background
Feed-backward reconstruction was introduced in the context of parallel volume rendering algorithms. The method is attributed to Feibush [Feibush 80], as cited in [S1, unofficial]. It is a fundamental technique in computer graphics for resampling data, particularly in volume rendering where high-quality reconstruction is necessary to avoid aliasing artifacts. The method is often contrasted with feed-forward reconstruction, which distributes input sample contributions to neighboring output pixels. Both methods are mathematically equivalent but differ in their data access patterns [S1, unofficial].
