# Stochastic Jittering

Also called: Jittered Ray Sampling, Jittering Sample Positions, Ray Jitter with Random Noise, Ray Jittering, Stochastic Noise, Stochastic Sampling

## Overview
Stochastic jittering reduces aliasing and banding artifacts in volume rendering by perturbing sample positions along the ray with controlled random noise [S1, S2, unofficial][S3][S4, unofficial]. Unlike [Uniform Ray Sampling](1261-uniform-ray-sampling.md), which uses fixed intervals, this method transforms structured "wood-grain" artifacts into visually less noticeable noise [S3][S4, unofficial]. It serves as a lightweight alternative to [Monte Carlo Volume Rendering](2060-monte-carlo-volume-rendering.md) by avoiding complex variance reduction while maintaining real-time performance [S4, unofficial].

## How it works
**Inputs:**
*   Ray origin $O$ and direction $D$.
*   Base step size $h$ (distance between regular sample points) [S2, S4, unofficial].
*   Jitter texture $T$ of size $N \times N$ containing values in $[0, 1]$ [S1, S2, unofficial][S3].
*   Maximum noise factor $\alpha$ controlling jitter magnitude [S3].

**Outputs:**
*   Perturbed sample positions $P_n$ for $n = 0, 1, \dots$ along the ray.

**Data Structures:**
*   **Jitter Texture:** A 2D texture storing pre-generated noise.
    *   Dimensions: $N \times N$ (typically 64) [S3].
    *   Filtering: `GL_NEAREST` for both magnification and minification to preserve sharp noise patterns without interpolation [S1, unofficial].
    *   Wrapping: `GL_REPEAT` on S and T axes [S1, unofficial].
    *   Channel: Red channel used for offset calculation [S2, unofficial].

**Algorithm Steps:**

1.  **Initialize Ray:** Set current position $P = O$ [S2, S4, unofficial].
2.  **Loop:** While inside the volume and not fully opaque:
    a.  **Compute Jitter Offset:**
        Calculate texture coordinates $u, v$ from pixel coordinates $(x, y)$:
        $$ u = (x \pmod N) / N $$
        $$ v = (y \pmod N) / N $$
        Fetch jitter value $j$ from the texture:
        $$ j = T(u, v) $$
        [S1, S2, unofficial]
    b.  **Determine Sample Position:**
        For the $n$-th sample, calculate the base position $P_{base}$ using the step size $h$:
        $$ P_{base} = O + (n + j \cdot \alpha) \cdot h \cdot D $$
        *Note: [S4, unofficial] describes replacing the fixed offset $0.5$ with a random value $rand() \in [0,1]$. [S2, unofficial] scales the jitter by the step size and a max factor. [S3] applies jitter to the ray start. The general implementation combines these: the random component replaces the deterministic fractional offset within the step.*
        $$ P = P_{base} $$
        [S2, S4, unofficial]
    c.  **Sample Volume:** Evaluate volume density/color at $P$.
    d.  **Advance:** Increment $n$ and repeat.

**Parameters:**
*   $N$ (NoiseTextureSize): Size of the jitter texture. Typical value: 64 [S3].
*   $\alpha$ (MaxNoiseFactor): Maximum magnitude of jitter relative to step size. Typical value: 0.75 [S3].
*   $h$ (RayStepSize): Base step size. [S2, unofficial]

**Pseudocode:**
```python
def stochastic_jitter_sample(ray_origin, ray_dir, step_size, noise_texture, noise_size, max_noise_factor):
    """
    Generates a sequence of jittered sample positions along a ray.
    
    Args:
        ray_origin: vec3, starting point of the ray.
        ray_dir: vec3, normalized direction of the ray.
        step_size: float, base distance between regular sample intervals.
        noise_texture: 2D array or texture sampler, size (noise_size, noise_size).
        noise_size: int, dimension of the square noise texture (e.g., 64).
        max_noise_factor: float, scaling factor for jitter magnitude (e.g., 0.75).
        
    Returns:
        Generator yielding (position, step_index) tuples.
    """
    # Precompute inverse size for modulo arithmetic
    inv_noise_size = 1.0 / noise_size
    
    # Initialize sample index
    n = 0
    
    # Loop until ray exits volume (caller handles volume bounds check)
    while True:
        # 1. Calculate jitter offset based on pixel coordinates
        # Assuming pixel coordinates (px, py) are available in the calling context
        # For implementation completeness, we assume a function get_pixel_coords() exists
        px, py = get_pixel_coords()
        
        # Map pixel coordinates to texture coordinates [0, 1)
        u = (px % noise_size) * inv_noise_size
        v = (py % noise_size) * inv_noise_size
        
        # 2. Fetch jitter value from noise texture
        # Using nearest neighbor sampling as per [S1, unofficial]
        jitter_val = noise_texture.sample_nearest(u, v)
        
        # 3. Calculate perturbed position
        # Base position for step n: ray_origin + (n + 0.5) * step_size * ray_dir
        # Jittered position: replace 0.5 with (jitter_val * max_noise_factor)
        # Note: [S4, unofficial] uses rand() directly. [S2, unofficial] scales by step_size.
        # Combined formula: offset = step_size * (n + jitter_val * max_noise_factor)
        
        offset = step_size * (n + jitter_val * max_noise_factor)
        position = ray_origin + offset * ray_dir
        
        yield position, n
        
        n += 1
```

**Edge Cases and Pitfalls:**
*   **Banding vs. Noise:** Stochastic jittering replaces banding artifacts with noise [S4, unofficial]. This noise may require temporal filtering or higher sample counts to reduce [S4, unofficial].
*   **Isosurface Errors:** Without refinement, jittering alone does not fix isosurface rendering errors caused by large sample distances; it only makes them less visible [S3].
*   **Precision:** Using `GL_NEAREST` is critical; interpolation of the noise texture smooths the jitter, reducing its effectiveness [S1, unofficial].

Combines sub-voxel ray jittering with temporal reprojection to reduce spatial banding and noise, leveraging camera motion vectors to blend frame data.

### Slice Artifact Reduction
*   **Definition:** A variant that reduces "wood grain" artifacts (visible slice boundaries) by jittering the ray start and performing a voxel solidity check [S5, unofficial].
*   **Method:** Jitter the ray start position along the view direction by `stepVector * texture(Noise, gl_FragCoord.xy / 256).r` [S5, unofficial]. Inside the raycasting loop, if the voxel value $V$ exceeds a threshold, perform a solidity check: move back by half-step, sample $V$; if $V >$ Threshold, move forward by quarter-step, else backward by quarter-step, and sample $V$ again. Proceed with lighting only if the re-sampled $V$ is still $>$ Threshold [S5, unofficial].
*   **When to choose:** When "wood grain" artifacts are prominent and performance allows for extra voxel lookups per sample [S5, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(1)$ per sample, adding a texture lookup and basic arithmetic to the standard ray marching loop [S1, S2, S4, unofficial].
*   **Memory Complexity:** $O(N^2)$ for the jitter texture, where $N$ is typically 64, resulting in negligible memory overhead (e.g., 16 KB for 8-bit data) [S3].
*   **Performance:** Maintains real-time performance as it avoids the overhead of complex quasi-Monte Carlo sequences or hierarchical sampling [S4, unofficial].
*   **Strengths:** Simple to implement; effectively breaks up regular aliasing patterns; low memory footprint [S1, unofficial][S3][S4, unofficial].
*   **Limitations:** Introduces high-frequency noise which may be visually distracting without temporal filtering; does not improve accuracy for isosurface extraction without refinement [S3][S4, unofficial].
*   **When to use:** Real-time volume rendering where banding artifacts are unacceptable and hardware supports fast 2D texture lookups [S1, unofficial][S3].
*   **When not to use:** Offline rendering requiring high accuracy or when temporal coherence can be leveraged for better noise reduction [S4, unofficial].

## Background
Stochastic jittering originates from Monte Carlo integration techniques applied to volume rendering to mitigate aliasing caused by regular sampling grids [S4, unofficial]. It was adopted in visualization toolkits like VTK, where it is referred to as "Noise" for compatibility with original class nomenclature [S3]. The technique is widely used in GPU-based ray casting implementations to improve visual quality without significant performance penalties [S1, S2, unofficial].
