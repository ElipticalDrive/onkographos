# Multi-Sample Anti-Aliasing via Ray Distribution

Also called: MSAA via Ray Distribution, Multi-ray AA, Multi-sample AA, Multi-sampling for rendering, Ray Distribution AA

## Overview
Multi-Sample Anti-Aliasing via Ray Distribution is an image-order rendering technique that reduces aliasing artifacts by casting multiple rays per pixel, distributed within the pixel area, and averaging the resulting color values [S1, unofficial][S2, unofficial][S3, unofficial][S4, unofficial]. It solves the problem of jagged edges caused by abrupt intensity changes along object silhouettes, which occur when a single ray per pixel fails to capture high-frequency scene details [S4, unofficial]. Unlike post-processing convolution filters, this method performs supersampling directly during ray traversal, offering higher quality at the cost of increased computational load [S2, unofficial]. It differs from [Stochastic Jittering](924-stochastic-jittering.md) by using deterministic, fixed offsets for low sample counts (1x–4x) rather than random patterns, and from [Monte Carlo Volume Rendering](2060-monte-carlo-volume-rendering.md) by relying on simple arithmetic averaging rather than importance-weighted integration [S1, unofficial][S2, unofficial][S4, unofficial].

## How it works
### Inputs and Outputs
**Inputs:**
- Pixel coordinates $(x, y)$ from the rasterizer (e.g., `gl_FragCoord`) [S3, unofficial].
- A uniform integer parameter `AA` selecting the sampling mode (1, 2, 3, or 4) [S3, unofficial].
- A rendering function `render(uv)` that traces a single ray for a given normalized UV offset within the pixel and returns a `vec3` color [S3, unofficial].

**Outputs:**
- A single `vec3` color value representing the averaged result of all distributed rays for the pixel [S1, unofficial][S3, unofficial].

### Data Structures
No complex data structures are required. The method uses scalar arithmetic for offset calculation and accumulation, and stores the `AA` mode selector as an integer uniform [S3, unofficial].

### Steps
1. **Select Mode:** Determine the number of samples $N$ based on the `AA` uniform. If `AA` is not 1, 2, or 3, default to 4 [S3, unofficial].
2. **Generate Offsets:** Calculate 2D UV offsets $(\delta u, \delta v)$ for each of the $N$ rays. The offsets depend on the mode and, for 2x and 3x, the parity of the pixel coordinates [S3, unofficial].
3. **Trace Rays:** For each offset $i \in \{0, \dots, N-1\}$, pass the offset to `getUV` and call `render` to obtain color $C_i$ [S1, unofficial][S3, unofficial].
4. **Average:** Sum all color values $C_i$ and divide by $N$ to produce the final pixel color [S1, unofficial][S3, unofficial][S4, unofficial].

### Formulas and Parameters
**AAx1 ($N=1$):**
- Offset: $(0, 0)$ [S3, unofficial].

**AAx2 ($N=2$):**
- Let $b_{xy} = (x + y) \pmod 2$ [S3, unofficial].
- Let $n_{bxy} = 1 - b_{xy}$ [S3, unofficial].
- Offsets: $(0.33 \cdot n_{bxy}, 0)$ and $(0.33 \cdot b_{xy}, 0.66)$ [S3, unofficial].

**AAx3 ($N=3$):**
- Let $b_{xy} = (x + y) \pmod 2$ [S3, unofficial].
- Let $n_{bxy} = 1 - b_{xy}$ [S3, unofficial].
- Offsets: $(0.66 \cdot n_{bxy}, 0)$, $(0.66 \cdot b_{xy}, 0.66)$, and $(0.33, 0.33)$ [S3, unofficial].

**AAx4 ($N=4$):**
- Define vector $e = (0.125, -0.125, 0.375, -0.375)$ [S3, unofficial].
- Offsets: $(e.x, e.z)$, $(e.y, e.w)$, $(e.w, e.x)$, and $(e.z, e.y)$ [S3, unofficial].

**Averaging:**
$$ C_{final} = \frac{1}{N} \sum_{i=1}^{N} C_i $$
where $C_i$ is the color returned by `render(getUV(offset_i))` [S1, unofficial][S3, unofficial].

### Pseudocode
```python
def render_aa(x: int, y: int, aa_mode: int, render_func) -> tuple:
    if aa_mode not in (1, 2, 3):
        aa_mode = 4

    if aa_mode == 1:
        return render_func((0.0, 0.0))

    elif aa_mode == 2:
        bxy = (x + y) & 1
        nbxy = 1 - bxy
        c1 = render_func((0.33 * nbxy, 0.0))
        c2 = render_func((0.33 * bxy, 0.66))
        return ((c1[0] + c2[0]) / 2.0, (c1[1] + c2[1]) / 2.0, (c1[2] + c2[2]) / 2.0)

    elif aa_mode == 3:
        bxy = (x + y) & 1
        nbxy = 1 - bxy
        c1 = render_func((0.66 * nbxy, 0.0))
        c2 = render_func((0.66 * bxy, 0.66))
        c3 = render_func((0.33, 0.33))
        return ((c1[0] + c2[0] + c3[0]) / 3.0, (c1[1] + c2[1] + c3[1]) / 3.0, (c1[2] + c2[2] + c3[2]) / 3.0)

    elif aa_mode == 4:
        e_x, e_y, e_z, e_w = 0.125, -0.125, 0.375, -0.375
        c1 = render_func((e_x, e_z))
        c2 = render_func((e_y, e_w))
        c3 = render_func((e_w, e_x))
        c4 = render_func((e_z, e_y))
        return ((c1[0] + c2[0] + c3[0] + c4[0]) / 4.0, (c1[1] + c2[1] + c3[1] + c4[1]) / 4.0, (c1[2] + c2[2] + c3[2] + c4[2]) / 4.0)
```

### Edge Cases and Pitfalls
- **Performance:** This technique significantly reduces framerate due to the increased ray count, as rendering time increases linearly with the number of samples [S1, unofficial][S2, unofficial].
- **Optimization:** To mitigate performance loss, an optimization is to only perform AA if the iteration count (e.g., ray marching steps) is above average, as this likely indicates the ray is near an object edge [S1, unofficial].
- **Precision:** The source code uses floating-point literals `0.33` and `0.66` rather than exact fractions like $1/3$ or $2/3$ [S3, unofficial].
- **Boundary Conditions:** The offsets are passed directly to `getUV` for coordinate transformation [S3, unofficial].

## Operating characteristics
- **Time Complexity:** $O(N)$, where $N$ is the number of samples per pixel. Rendering time increases linearly proportional to the number of samples because the same number of interpolations are required for each sample [S2, unofficial].
- **Memory Complexity:** $O(1)$ per pixel, as only the accumulated color sum is stored before averaging [S1, unofficial][S3, unofficial].
- **Measured Performance:** Not given in the sources. However, it is noted that the technique "wrecks your framerate" if not optimized [S1, unofficial].
- **Scaling:** Performance scales linearly with $N$. AAx4 is 4x slower than AAx1 [S2, unofficial].
- **Strengths:** Effective at removing jagged edges and aliasing artifacts, particularly along silhouette edges where intensity changes abruptly [S1, unofficial][S4, unofficial]. Simple to implement [S3, unofficial].
- **Limitations:** High computational cost [S1, unofficial]. Fixed offsets may not adapt to scene complexity, potentially wasting samples in uniform regions [S1, unofficial].
- **When to Use:** When high-quality anti-aliasing is required and performance is not the primary constraint, or when combined with edge-detection optimizations [S1, unofficial].
- **When Not to Use:** In real-time applications with strict performance budgets, or when the scene is largely uniform and aliasing is minimal.

## Background
The technique is described in the context of raymarching distance fields and volume rendering [S1, unofficial][S3, unofficial]. It is a form of supersampling, which is defined as sampling the scene at a higher resolution than displayed to combat aliasing [S4, unofficial]. The specific offset patterns for 2x, 3x, and 4x sampling are derived from implementations in GLSL shaders, as seen in the `kushchevd/RayMarching` repository [S3, unofficial]. The theoretical basis for supersampling as a method to reduce undersampling artifacts is discussed in literature on volume visualization [S2, unofficial][S4, unofficial].
