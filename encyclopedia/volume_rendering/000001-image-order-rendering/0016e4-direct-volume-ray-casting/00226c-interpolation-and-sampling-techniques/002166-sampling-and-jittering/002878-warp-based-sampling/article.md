# Warp-based Sampling

Also called: 1D Warp Marching, 2D Warp Marching, DBShuffle, SBShuffle, Warp Marching

## Overview
Warp-based Sampling is a GPU optimization strategy for direct volume ray casting that improves texture cache performance by reorganizing thread warps to align sampling directions with the volume's memory strides [S1]. Unlike standard sampling where a warp processes a block of pixels, Warp Marching assigns a single warp to a single ray, marching through the volume in chunks equal to the warp size [S1]. This approach minimizes memory stride within the atomic scheduling unit (the warp), making it particularly effective for rendering large dynamic volumes at low resolutions where view-independent performance is critical [S1].

## How it works
**Inputs and Outputs**
*   **Input:** 3D volume texture (density field), transfer function (density to RGBA), viewing parameters (camera position, direction, projection) [S1].
*   **Output:** Final pixel color (RGBA) for each frame [S1].

**Data Structures**
*   **Thread Organization:** Threads are grouped into warps of 32 consecutive threads, which form the atomic scheduling unit in CUDA [S1].
*   **Shared Memory:** Used for intermediate color accumulation [S1].
    *   **SBShuffle (Single Buffer Shared Warp Marching):** Requires 9 `float4` variables per warp (8 for thread-local samples + 1 for intermediate reduction result) [S1].
    *   **DBShuffle (Double Buffer Shared Warp Marching):** Uses a double-buffering accumulation scheme to enhance GPU resource utilization [S1].
*   **Binary Mask:** Each thread maintains a single binary bit indicating if its current sample has non-zero alpha [S1].

**Warp Shapes and Orientations**
A warp of 32 threads can be organized into three shapes: $32 \times 1$, $16 \times 2$, and $8 \times 4$ [S1].
*   **1D Warp Marching:** Uses the $32 \times 1$ shape [S1]. The warp takes 32 samples along the depth ($Z$) direction and 1 sample along the horizontal ($X$) direction, yielding orientation $zx$ [S1].
*   **2D Warp Marching:** Uses $16 \times 2$ or $8 \times 4$ shapes [S1].
*   **Orientation Naming:** Major direction axis followed by minor direction axis (e.g., $zx$, $xz$) [S1].
*   **Generating Orientations:**
    *   $zx$ and $xz$ are generated by changing the marching step (shuffling width) in the depth direction [S1].
    *   For a warp size of 32: marching 8 samples in depth creates $zx$ orientation (8 depth, 4 horizontal) [S1]. Marching 4 samples in depth creates $xz$ orientation (8 horizontal, 4 depth) [S1].
    *   Standard sampling is a special case of Warp Marching with a marching step of 1 in depth, resulting in $xy$ orientation (16 horizontal, 2 vertical for a $16 \times 16$ block) [S1].
*   **Row-Major vs. Column-Major:** Default is row-major sampling [S1]. Changing thread-pixel mapping allows column-major sampling, generating the remaining three orientations [S1].
*   **Optimal Alignment:** The major sampling direction should always be aligned with the $X$ dimension of the volume because the $X$ dimension has the smallest memory stride in 3D textures [S1].

**Algorithm Steps**
1.  **Warp Initialization:** Assign one warp to one ray [S1]. Initialize shared memory buffers [S1].
2.  **Marching Loop:**
    a.  **Sample:** Each thread in the warp samples the volume along the ray [S1]. The step size corresponds to the warp shape dimensions [S1].
    b.  **Transfer Function:** Map density to RGBA color [S1].
    c.  **Pre-integration (Optional):** If using pre-integrated rendering, each thread takes two density values (front and back of a slab) and shuffles the sample to its neighbor using `__shfl_down()` [S1].
    d.  **Binary Masking:** Set binary bit to 1 if alpha > 0, else 0 [S1].
    e.  **Warp Voting:** Use `__ballot()` to determine if any thread in the warp has non-zero alpha [S1].
    f.  **Skip Check:** If `__ballot()` returns 0, skip blending for this step [S1].
    g.  **Reduction Blending:** If not skipped, perform front-to-back alpha blending in a reduction manner within the warp, leveraging the associative property of blending [S1].
    h.  **Accumulation:** Copy the final reduction result to a "safe" place (shared memory or extra memory unit) and accumulate as rays march further [S1].
3.  **Final Output:** After marching through the volume, write the accumulated color to the frame buffer [S1].

```python
from typing import List, Tuple

class Float4:
    def __init__(self, r: float, g: float, b: float, a: float):
        self.r, self.g, self.b, self.a = r, g, b, a

def blend_rgba(c1: Float4, c2: Float4) -> Float4:
    """Front-to-back alpha blending: c1 + c2 * (1 - c1.a)"""
    return Float4(
        c1.r + c2.r * (1.0 - c1.a),
        c1.g + c2.g * (1.0 - c1.a),
        c1.b + c2.b * (1.0 - c1.a),
        c1.a + c2.a * (1.0 - c1.a)
    )

def sample_volume(ray_origin: Tuple[float, float, float], ray_direction: Tuple[float, float, float], t: float, volume: List) -> float:
    """Returns scalar density at parameter t along the ray."""
    idx = int(t) % len(volume)
    return volume[idx]

def transfer_function(density: float) -> Float4:
    """Maps scalar density to Float4 RGBA."""
    return Float4(density, density, density, density)

def warp_ballot(predicate: bool, lane_id: int, warp_size: int) -> int:
    """Simulates __ballot(): returns bitmask of active threads in the warp."""
    mask = 0
    for i in range(warp_size):
        if predicate:
            mask |= (1 << i)
    return mask

def warp_shfl_down(value: Float4, offset: int, lane_id: int, warp_size: int, buffer: List[Float4]) -> Float4:
    """Simulates __shfl_down(): returns value from thread (lane_id + offset)."""
    neighbor_id = lane_id + offset
    if neighbor_id < warp_size:
        return buffer[neighbor_id]
    return Float4(0.0, 0.0, 0.0, 0.0)

def warp_marching_kernel(ray_origin: Tuple[float, float, float], ray_direction: Tuple[float, float, float],
                         ray_length: float, volume: List, transfer_fn, warp_size: int = 32) -> Float4:
    """
    Simulates a single warp processing one ray using Warp Marching.
    lane_id is the thread's index within the warp (0..31).
    """
    lane_id = 0  # Each thread executes this with a unique lane_id
    shared_accumulators = [Float4(0.0, 0.0, 0.0, 0.0)] * 9  # SBShuffle layout [S1]
    
    step_size = ray_length / warp_size
    ray_t = 0.0
    accumulated_color = Float4(0.0, 0.0, 0.0, 0.0)
    
    while ray_t < ray_length:
        # 1. Sample and Transfer (parallel across lanes)
        sample_colors = [transfer_fn(sample_volume(ray_origin, ray_direction, ray_t + i * step_size, volume)) for i in range(warp_size)]
        has_alpha = [c.a > 0.0 for c in sample_colors]
        
        # 2. Warp Voting
        warp_state = warp_ballot(has_alpha[lane_id], lane_id, warp_size)
        
        if warp_state != 0:
            # 3. Reduction Blending
            local_color = sample_colors[lane_id]
            for offset in [16, 8, 4, 2, 1]:
                neighbor_color = warp_shfl_down(local_color, offset, lane_id, warp_size, sample_colors)
                if has_alpha[lane_id]:
                    local_color = blend_rgba(local_color, neighbor_color)
            
            # 4. Accumulate to shared memory
            if lane_id == 0:
                shared_accumulators[0] = local_color
            
            # 5. Read accumulated and blend with current step result
            prev_accum = shared_accumulators[0]
            final_warp_color = blend_rgba(prev_accum, local_color)
            
            if lane_id == 0:
                shared_accumulators[0] = final_warp_color
        
        # 6. Advance ray
        ray_t += step_size
        
    return shared_accumulators[0]
```

**Parameters**
*   **Warp Size:** 32 consecutive threads [S1].
*   **Warp Shapes:** $32 \times 1$ (1D), $16 \times 2$ and $8 \times 4$ (2D) [S1].
*   **Marching Step:** Determines orientation [S1]. E.g., 8 samples depth for $zx$, 4 samples depth for $xz$ [S1].
*   **Dataset Examples:** `vhf_head` (spacing 1:1:1), `vhm_body` (spacing 1:1:3) [S1].
*   **Resolution:** 1024 × 1024 [S1].

**Edge Cases and Pitfalls**
*   **Viewing Direction:** Performance varies significantly with viewing direction [S1]. Standard sampling is best when facing the $XY$ plane, but Warp Marching is superior when facing the $ZY$ plane (up to 4x speedup) [S1].
*   **Cache Coherence:** If the major sampling direction is not aligned with the volume's $X$ dimension, texture cache hit rates drop [S1].
*   **Pre-integration:** Requires two density values per thread (front and back of slab) and specific shuffling logic (`__shfl_down`) [S1].

## Subtopics

### [Dynamic Warp Marching](5297-dynamic-warp-marching.md)
Dynamic Warp Marching is a GPU sampling strategy for direct volume ray casting that optimizes texture cache performance by dynamically aligning the sampling direction of a thread warp with the volume's X-dimension, which has the minimum memory stride. It integrates the Warp Marching concept with a dynamic viewing-direction adjustment, overcoming the limitation of the original Dynamic approach which could only sample along horizontal or vertical directions.

## Operating characteristics
*   **Performance:** Warp Marching is view-independent and outperforms existing empty space skipping techniques in scenarios requiring rendering of large dynamic volumes in low resolution images [S1].
*   **Speedup:** When facing the $ZY$ plane, Warp Marching achieves more than 4 times the speedup of the Standard method [S1]. When facing the $XY$ plane, Standard method achieves higher frame rates, but Warp Marching is not extremely poor [S1].
*   **DBShuffle vs SBShuffle:** DBShuffle performs better than SBShuffle regardless of viewing direction for both tested datasets [S1].
*   **Complexity:** Time complexity is proportional to the number of samples per ray, but with reduced memory latency due to cache optimization [S1]. Memory complexity is low, relying on shared memory for intermediate results [S1].
*   **Strengths:** High texture cache hit rates, stable frame rates during volume exploration, effective for dynamic volumes [S1].
*   **Limitations:** May underperform Standard sampling when viewing direction aligns with the volume's natural memory stride (e.g., $XY$ plane) [S1].

## Background
Warp-based Sampling was introduced to address texture cache performance issues in GPU-based volume rendering [S1]. It builds on the concept of breaking a ray into segments and compositing them, as described by Ma et al. (1993) [S1]. The method leverages warp-level GPU operations (voting and shuffling) introduced in the NVIDIA Kepler architecture [S1]. It is designed to replace the Standard sampling strategy in texture-based volume rendering algorithms [S1].
