# Multi-Sample Anti-Aliasing via Ray Distribution

Also called: MSAA via Ray Distribution, Multi-ray AA, Multi-sample AA, Multi-sampling for rendering, Ray Distribution AA

## Overview
Multi-Sample Anti-Aliasing (MSAA) via Ray Distribution is an image-order rendering technique that reduces aliasing artifacts by casting multiple rays per pixel, distributed within the pixel area, and averaging the resulting color values [S1, S2, S3, S4, unofficial]. It solves the problem of jagged edges caused by abrupt intensity changes along object silhouettes, which occur when a single ray per pixel fails to capture the scene's high-frequency details [S1, S4, unofficial]. Unlike post-processing convolution filters, this method performs supersampling directly during ray traversal, offering higher quality at the cost of increased computational load [S2, unofficial]. It differs from [Stochastic Jittering](924-stochastic-jittering.md) by using deterministic, fixed offsets for low sample counts (1x–4x) rather than random or stratified patterns, and from [Monte Carlo Volume Rendering](2060-monte-carlo-volume-rendering.md) by relying on simple arithmetic averaging rather than importance-weighted integration [S1, S2, S4, unofficial].

## How it works
### Inputs and Outputs
**Inputs:**
- Pixel coordinates $(x, y)$, typically from `gl_FragCoord` or equivalent rasterizer output.
- A uniform integer parameter `AA` selecting the sampling mode (1, 2, 3, or 4) [S3, unofficial].
- A rendering function `render(uv)` that traces a single ray for a given normalized UV offset within the pixel and returns a `vec3` color [S3, unofficial].

**Outputs:**
- A single `vec3` color value representing the averaged result of all distributed rays for the pixel [S1, S3, unofficial].

### Data Structures
No complex data structures are required. The method relies on scalar arithmetic and fixed offset arrays. The core state is the `AA` mode selector [S3, unofficial].

### Steps
1. **Select Mode:** Determine the number of samples $N$ based on the `AA` uniform. If `AA` is not 1, 2, or 3, default to 4 [S3, unofficial].
2. **Generate Offsets:** Calculate 2D UV offsets $(\delta u, \delta v)$ for each of the $N$ rays within the unit square $[0, 1] \times [0, 1]$ representing the pixel area. The offsets depend on the mode and, for 2x and 3x, the parity of the pixel coordinates [S3, unofficial].
3. **Trace Rays:** For each offset $i \in \{0, \dots, N-1\}$, compute the UV coordinate $uv_i = uv_{center} + \delta u_i, \delta v_i$ and call `render(uv_i)` to obtain color $C_i$ [S1, S3, unofficial].
4. **Average:** Sum all color values $C_i$ and divide by $N$ to produce the final pixel color [S1, S3, S4, unofficial].

### Formulas and Parameters
Let $uv_{center} = (0.5, 0.5)$ be the pixel center in normalized device coordinates (or $(0,0)$ if the `render` function expects offsets relative to the center; the source code in [S3, unofficial] uses `getUV(vec2(0))` for AAx1, implying `getUV` handles the centering or expects offsets from center. However, the offsets in AAx2/3/4 are small values like 0.33, suggesting they are added to a base. Let us assume `getUV` takes an offset from the pixel center, where $(0,0)$ is the center. The source `render(getUV(vec2(0)))` for AAx1 confirms the center sample. The offsets in AAx2 are `0.33` and `0.66`. If these are added to 0, they are not centered. Let's look closer at [S3, unofficial].
`render(getUV(vec2(0.33 * nbxy, 0.)))`. If `getUV` maps $[0,1]$ to the pixel, then 0.33 is not centered. However, standard supersampling usually centers samples. The values $0.33, 0.66$ sum to roughly 1. The pattern for AAx4 uses $0.125, -0.125, 0.375, -0.375$. These are clearly offsets from the center $(0,0)$. $0.375 - 0.125 = 0.25$. The range is roughly $\pm 0.5$.
Let us define the offsets relative to the pixel center $(0,0)$.

**AAx1 (N=1):**
- Offset: $(0, 0)$ [S3, unofficial].

**AAx2 (N=2):**
- Let $b_{xy} = (x + y) \pmod 2$ [S3, unofficial].
- Let $n_{bxy} = 1 - b_{xy}$ [S3, unofficial].
- Offsets:
  1. $(0.33 \cdot n_{bxy}, 0)$
  2. $(0.33 \cdot b_{xy}, 0.66)$ [S3, unofficial].
  *Note: The source uses `0.33` and `0.66`. More precise fractions might be $1/3$ and $2/3$, but the source explicitly uses `0.33` and `0.66` [S3, unofficial].*

**AAx3 (N=3):**
- Let $b_{xy} = (x + y) \pmod 2$ [S3, unofficial].
- Let $n_{bxy} = 1 - b_{xy}$ [S3, unofficial].
- Offsets:
  1. $(0.66 \cdot n_{bxy}, 0)$
  2. $(0.66 \cdot b_{xy}, 0.66)$
  3. $(0.33, 0.33)$ [S3, unofficial].

**AAx4 (N=4):**
- Define vector $e = (0.125, -0.125, 0.375, -0.375)$ [S3, unofficial].
- Offsets (using components $e.x, e.y, e.z, e.w$):
  1. $(e.x, e.z) = (0.125, 0.375)$
  2. $(e.y, e.w) = (-0.125, -0.375)$
  3. $(e.w, e.x) = (-0.375, 0.125)$
  4. $(e.z, e.y) = (0.375, -0.125)$ [S3, unofficial].

**Averaging:**
$$ C_{final} = \frac{1}{N} \sum_{i=1}^{N} C_i $$
where $C_i$ is the color returned by `render` for the $i$-th offset [S1, S3, unofficial].

### Pseudocode
```python
def render_aa(x: int, y: int, aa_mode: int, render_func) -> tuple:
    """
    Renders a pixel using Multi-Sample Anti-Aliasing via Ray Distribution.
    
    Args:
        x: Pixel x coordinate (integer).
        y: Pixel y coordinate (integer).
        aa_mode: Integer uniform selecting AA mode (1, 2, 3, or 4).
        render_func: A function that takes a 2D offset (u, v) relative to the pixel center
                     and returns a 3D color tuple (r, g, b).
                     
    Returns:
        A 3D tuple (r, g, b) representing the averaged pixel color.
    """
    
    # Default to AAx4 if mode is not 1, 2, or 3
    if aa_mode not in (1, 2, 3):
        aa_mode = 4

    if aa_mode == 1:
        # AAx1: Single ray at center
        color = render_func((0.0, 0.0))
        return color

    elif aa_mode == 2:
        # AAx2: Two rays
        # bxy = (x + y) & 1
        bxy = (x + y) & 1
        nbxy = 1 - bxy
        
        # Offsets: (0.33 * nbxy, 0) and (0.33 * bxy, 0.66)
        # Note: Source uses 0.33 and 0.66 explicitly [S3, unofficial]
        offset1 = (0.33 * nbxy, 0.0)
        offset2 = (0.33 * bxy, 0.66)
        
        c1 = render_func(offset1)
        c2 = render_func(offset2)
        
        # Average
        r = (c1[0] + c2[0]) / 2.0
        g = (c1[1] + c2[1]) / 2.0
        b = (c1[2] + c2[2]) / 2.0
        return (r, g, b)

    elif aa_mode == 3:
        # AAx3: Three rays
        bxy = (x + y) & 1
        nbxy = 1 - bxy
        
        # Offsets: (0.66 * nbxy, 0), (0.66 * bxy, 0.66), (0.33, 0.33)
        offset1 = (0.66 * nbxy, 0.0)
        offset2 = (0.66 * bxy, 0.66)
        offset3 = (0.33, 0.33)
        
        c1 = render_func(offset1)
        c2 = render_func(offset2)
        c3 = render_func(offset3)
        
        # Average
        r = (c1[0] + c2[0] + c3[0]) / 3.0
        g = (c1[1] + c2[1] + c3[1]) / 3.0
        b = (c1[2] + c2[2] + c3[2]) / 3.0
        return (r, g, b)

    elif aa_mode == 4:
        # AAx4: Four rays
        # e = (0.125, -0.125, 0.375, -0.375)
        e_x = 0.125
        e_y = -0.125
        e_z = 0.375
        e_w = -0.375
        
        # Offsets: (e.x, e.z), (e.y, e.w), (e.w, e.x), (e.z, e.y)
        offset1 = (e_x, e_z)
        offset2 = (e_y, e_w)
        offset3 = (e_w, e_x)
        offset4 = (e_z, e_y)
        
        c1 = render_func(offset1)
        c2 = render_func(offset2)
        c3 = render_func(offset3)
        c4 = render_func(offset4)
        
        # Average
        r = (c1[0] + c2[0] + c3[0] + c4[0]) / 4.0
        g = (c1[1] + c2[1] + c3[1] + c4[1]) / 4.0
        b = (c1[2] + c2[2] + c3[2] + c4[2]) / 4.0
        return (r, g, b)
```

### Edge Cases and Pitfalls
- **Performance:** This technique significantly reduces framerate due to the increased ray count, as rendering time increases linearly with the number of samples [S1, S2, unofficial].
- **Optimization:** To mitigate performance loss, an optimization is to only perform AA if the iteration count (e.g., ray marching steps) is above average, as this likely indicates the ray is near an object edge [S1, unofficial].
- **Precision:** The source code uses floating-point literals `0.33` and `0.66` rather than exact fractions like $1/3$ or $2/3$. Implementers should be aware that this may introduce slight bias compared to ideal stratified sampling, but it matches the reference implementation [S3, unofficial].
- **Boundary Conditions:** The offsets are defined within a local coordinate system relative to the pixel center. If the `render` function expects UVs in $[0,1]$, the offsets must be added to $(0.5, 0.5)$. The pseudocode assumes offsets are relative to the center, consistent with the AAx1 center sample at $(0,0)$ [S3, unofficial].

## Subtopics

### Stochastic Jittering
Uses random offsets to break up regular aliasing patterns. Choose when you need to avoid structured artifacts without the fixed pattern bias of MSAA. [Link](924-stochastic-jittering.md)

### Hierarchical Sampling (Inverse CDF Sampling)
Uses cumulative distribution functions for importance sampling. Choose when the scene has varying density or lighting that benefits from non-uniform sampling. [Link](973-hierarchical-sampling-inverse-cdf-sampling.md)

### Uniform Ray Sampling
Samples at regular grid points. Choose for simplicity and predictability, but it may introduce moiré patterns. [Link](1261-uniform-ray-sampling.md)

### Monte Carlo Volume Rendering
Uses random sampling with statistical integration. Choose for high-quality global illumination or complex media, accepting higher variance. [Link](2060-monte-carlo-volume-rendering.md)

### Random Jitter with Reprojection
Combines jittering with temporal reprojection for temporal anti-aliasing. Choose for dynamic scenes to reduce flickering over time. [Link](2782-random-jitter-with-reprojection.md)

### Supersampling
General term for sampling at higher resolution. MSAA via Ray Distribution is a specific implementation of supersampling with fixed offsets. [Link](3493-supersampling.md)

### Importance Sampling for SPH Rendering
Specialized sampling for Smoothed Particle Hydrodynamics. Choose for particle-based fluid rendering. [Link](3624-importance-sampling-for-sph-rendering.md)

### Ray Casting with Jittered Sampling
Uses jittered offsets to reduce aliasing. Choose when you want a balance between regularity and randomness. [Link](4151-ray-casting-with-jittered-sampling.md)

### Warp-based Sampling
Uses warp-level parallelism for sampling. Choose for GPU optimization in massive parallel contexts. [Link](4298-warp-based-sampling.md)

## Operating characteristics
- **Time Complexity:** $O(N)$, where $N$ is the number of samples per pixel. Rendering time increases linearly proportional to the number of samples because the same number of interpolations and ray traversals are required for each sample [S2, unofficial].
- **Memory Complexity:** $O(1)$ per pixel, as only the accumulated color sum is stored before averaging [S1, S3, unofficial].
- **Measured Performance:** Not given in the sources. However, it is noted that the technique "wrecks your framerate" if not optimized [S1, unofficial].
- **Scaling:** Performance scales linearly with $N$. AAx4 is 4x slower than AAx1 [S2, unofficial].
- **Strengths:** Effective at removing jagged edges and aliasing artifacts, particularly along silhouette edges where intensity changes abruptly [S1, S4, unofficial]. Simple to implement [S3, unofficial].
- **Limitations:** High computational cost [S1, unofficial]. Fixed offsets may not adapt to scene complexity, potentially wasting samples in uniform regions [S1, unofficial].
- **When to Use:** When high-quality anti-aliasing is required and performance is not the primary constraint, or when combined with edge-detection optimizations [S1, unofficial].
- **When Not to Use:** In real-time applications with strict performance budgets, or when the scene is largely uniform and aliasing is minimal.

## Background
The technique is described in the context of raymarching distance fields and volume rendering [S1, S3, unofficial]. It is a form of supersampling, which is defined as sampling the scene at a higher resolution than displayed to combat aliasing [S4, unofficial]. The specific offset patterns for 2x, 3x, and 4x sampling are derived from implementations in GLSL shaders, as seen in the `kushchevd/RayMarching` repository [S3, unofficial]. The theoretical basis for supersampling as a method to reduce undersampling artifacts is discussed in literature on volume visualization [S2, S4, unofficial].
