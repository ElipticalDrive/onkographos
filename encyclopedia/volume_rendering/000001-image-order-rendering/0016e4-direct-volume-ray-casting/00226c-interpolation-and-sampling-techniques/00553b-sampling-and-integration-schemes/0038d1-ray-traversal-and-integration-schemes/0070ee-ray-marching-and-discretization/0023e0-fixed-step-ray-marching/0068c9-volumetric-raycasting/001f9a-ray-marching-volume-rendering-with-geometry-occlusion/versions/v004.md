# Ray Marching Volume Rendering with Geometry Occlusion

Also called: GPU Ray Marching

## Overview
A front-to-back ray marching technique that renders a 3D volume texture by stepping along rays from the camera, compositing color and opacity, and using pre-rendered opaque geometry to occlude the volume and adjust sampling rates [S1, unofficial]. It solves the problem of self-occlusion in volume rendering by decoupling the occlusion estimation from the ray step, using spatial averaging of a pre-rendered occlusion texture to modulate the current slice's contribution [S1, unofficial]. Unlike standard front-to-back ray casting which integrates opacity along the ray, this method stops the volume march at opaque geometry surfaces, preventing the volume from rendering "through" solid objects [S1, unofficial]. It differs from its sibling [Volumetric Raycasting](3462-volumetric-raycasting.md) by explicitly handling geometry occlusion via depth buffer checks, and from [Image-space Volume Ray Marching](20131-image-space-volume-ray-marching.md) by relying on explicit bounding box intersection rather than screen-space ray reconstruction [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** 3D volume texture (`volume_tex`), 2D colormap texture (`colormap_tex`), camera position (`eye_pos`), camera orientation matrices, opaque geometry depth buffer (`depth_tex`), and scene color buffer.
*   **Outputs:** Final composited color and opacity buffer.

**Data Structures:**
*   **Render Targets:** Two textures created via `gl.texStorage2D`.
    *   Target 0: `gl.RGBA8` format, size `WIDTH x HEIGHT`.
    *   Target 1: `gl.DEPTH_COMPONENT32F` format, size `WIDTH x HEIGHT`.
*   **Framebuffers:**
    *   `depthColorFbo`: Attaches Target 0 to `COLOR_ATTACHMENT0` and Target 1 to `DEPTH_ATTACHMENT`.
    *   `colorFbo`: Attaches Target 0 to `COLOR_ATTACHMENT0` only.
*   **Colormap Texture:** 2D texture `gl.SRGB8_ALPHA8` format, size 180x1. Loaded from `colormaps/cool-warm-paraview.png`. Filtered with `LINEAR`.
*   **Volume Dimensions:** `volume_dims` (width, height, depth) as `ivec3`.

**Parameters:**
*   `dt_scale`: A scalar multiplier for the base step size, controlling sampling density. Default value not explicitly stated in code but used as `uniform float dt_scale` [S1, unofficial].
*   `volume_dims`: The dimensions (width, height, depth) of the 3D volume texture [S1, unofficial].

**Algorithm Steps:**

1.  **Ray Direction Calculation:** In the vertex shader, calculate the ray direction: `vray_dir = pos - transformed_eye`. Normalize this vector in the fragment shader [S1, unofficial].
2.  **Ray-Box Intersection:** Intersect the ray with the unit box `[0,1]³` using the slab method to get entry (`t_hit.x`) and exit (`t_hit.y`) distances [S1, unofficial].
    *   Formula:
        $$t_{min} = \frac{box_{min} - orig}{dir}$$
        $$t_{max} = \frac{box_{max} - orig}{dir}$$
        $$t_0 = \max(t_{min}.x, t_{min}.y, t_{min}.z)$$
        $$t_1 = \min(t_{max}.x, t_{max}.y, t_{max}.z)$$
    *   If `t_hit.x > t_hit.y`, discard the pixel [S1, unofficial].
3.  **Step Size Calculation:** Calculate the base step size `dt` [S1, unofficial]:
    $$dt = dt\_scale \times \min\left(\frac{1.0}{volume\_dims \times |ray\_dir|}\right)$$
    *   Note: The source code implies a component-wise minimum or a specific normalization, but the formula provided is `dt_scale * min(1.0/(volume_dims * abs(ray_dir)))`. Given `volume_dims` is a vector, this likely refers to the maximum dimension or a specific normalization factor. The code snippet suggests `min(1.0/(volume_dims * abs(ray_dir)))` might be a simplification for the smallest dimension or a specific scaling. We will use the formula as stated: `dt = dt_scale * min(1.0/(volume_dims * abs(ray_dir)))`. [S1, unofficial].
4.  **Jitter Offset:** Add a jitter offset to `t_hit.x` to reduce banding artifacts. The offset is calculated using a hash function, e.g., `wang_hash(...)`, and added to `t_hit.x` [S1, unofficial].
5.  **Geometry Occlusion Check:** Check for opaque geometry intersection via the depth buffer `z` [S1, unofficial].
    *   If geometry exists (`z < 1.0`), reconstruct the geometry position in world space.
    *   Calculate the distance to the geometry surface, `geom_t`.
    *   Adjust `dt` and `t_hit.y` to stop the volume march at the geometry surface. Specifically, set `t_hit.y = geom_t` [S1, unofficial].
    *   If no geometry is present (`z >= 1.0`), the ray marches through the entire box (`t_hit.y` remains the exit point of the unit box) [S1, unofficial].
6.  **Volume Marching Loop:** Loop from `t_hit.x` to `t_hit.y` with step `dt` [S1, unofficial]:
    *   Sample the volume texture at the current ray position.
    *   Lookup the color from the colormap texture using the sampled value.
    *   Apply opacity correction:
        $$a_{corrected} = 1.0 - (1.0 - a_{sample})^{dt_{correction}}$$
        where `dt_correction` scales the sample opacity based on step size relative to a reference, ensuring consistent appearance regardless of step count [S1, unofficial].
    *   Accumulate color and alpha using front-to-back compositing:
        $$C_{out} = C_{in} + (1.0 - C_{in}.a) \times C_{sample}.a \times C_{sample}.rgb$$
        $$A_{out} = A_{in} + (1.0 - A_{in}.a) \times C_{sample}.a$$
    *   Break if `color.a >= 0.99` [S1, unofficial].
7.  **Final Composite:** If geometry exists, take a final sample at `t_hit.y` (the geometry surface) and composite it. The code composites volume data at the surface location, implying the geometry is just an occluder for the volume march, or the volume data at the surface is used to color the geometry [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Non-uniform volume scaling:** Requires translation adjustment. The code calculates `volume_translation = vec3(0.5) - volume_scale * 0.5` to center the volume in the `[-0.5, 0.5]` or `[0,1]` space depending on interpretation, ensuring correct ray origin transformation [S1, unofficial].
*   **Geometry occlusion handling:** If no geometry is present (`z >= 1.0`), the ray marches through the entire box. If geometry is present, the ray stops at the geometry surface (`t_hit.y = geom_t`) and a final sample is taken at that surface point to composite the geometry color/opacity if needed (though the code composites volume data at the surface location, implying the geometry is just an occluder for the volume march, or the volume data at the surface is used to color the geometry) [S1, unofficial].
*   **Precision:** Floating-point precision issues may arise when `t_hit.x` and `t_hit.y` are very close, or when `dt` is very small. Jittering helps mitigate banding but may introduce noise.

## Subtopics

### [Direct Volume Rendering with Precomputed Occlusion (DOS)](4566-direct-volume-rendering-with-precomputed-occlusion-dos.md)
Direct Volume Rendering with Precomputed Occlusion (DOS) is a single-pass, image-order ray marching technique that approximates volumetric attenuation from behind the current sample using precomputed 2D occlusion maps. It solves the problem of self-occlusion in volume rendering without requiring full volumetric integration or multiple rendering passes. Unlike standard front-to-back ray casting which integrates opacity along the ray, DOS decouples the occlusion estimation from the ray step, using spatial averaging of a pre-rendered occlusion texture to modulate the current slice's contribution.

### [Image-space Volume Ray Marching](20131-image-space-volume-ray-marching.md)
Image-space Volume Ray Marching renders 3D volumetric data (such as nebulae or aurorae) by executing a fragment shader for every pixel on a full-screen quad, rather than using an in-scene geometric primitive like a box to encapsulate the volume. This approach decouples the volume rendering from the scene geometry pipeline, allowing the volume to be treated as a post-processing effect that interacts with the existing frame buffer and depth buffer. It differs from its parent method, [Ray Marching Volume Rendering with Geometry Occlusion](2066-ray-marching-volume-rendering-with-geometry-occlusion.md), by bypassing the explicit bounding box intersection and geometry occlusion steps, relying instead on image-space depth testing and screen-space ray reconstruction.

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of samples per ray, which is determined by the step size `dt` and the length of the ray segment within the volume. The step size is inversely proportional to the volume dimensions and ray direction magnitude.
*   **Memory Complexity:** Proportional to the size of the 3D volume texture and the 2D colormap texture. The render targets and framebuffers add overhead proportional to the screen resolution.
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Performance scales with the resolution of the volume texture and the screen resolution. Higher `dt_scale` values (smaller steps) increase accuracy but reduce performance.
*   **Strengths:** Handles geometry occlusion efficiently by stopping the volume march at opaque surfaces. Simple to implement on the GPU.
*   **Limitations:** Requires pre-rendered geometry depth buffer. May suffer from banding artifacts if jittering is not used. Precision issues may arise with very small or large volumes.
*   **When to use:** When rendering volumetric data that needs to be occluded by opaque geometry, and when performance is a concern.
*   **When not to use:** When high accuracy is required and the volume is complex, or when the geometry is not available or changes frequently.
