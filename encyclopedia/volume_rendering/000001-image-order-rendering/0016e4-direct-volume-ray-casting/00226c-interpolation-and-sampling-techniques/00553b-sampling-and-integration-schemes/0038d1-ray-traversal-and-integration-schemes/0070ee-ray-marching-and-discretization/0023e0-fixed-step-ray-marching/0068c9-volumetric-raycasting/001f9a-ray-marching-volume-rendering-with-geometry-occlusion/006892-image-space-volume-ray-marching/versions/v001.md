# Image-space Volume Ray Marching

Also called: Image-space volume rendering, Post-processing Volume Rendering, Screen-space Volume Rendering

## Overview
Image-space Volume Ray Marching renders 3D volumetric data (such as nebulae or aurorae) by executing a fragment shader for every pixel on a full-screen quad, rather than using an in-scene geometric primitive like a box to encapsulate the volume [S1, unofficial]. This approach decouples the volume rendering from the scene geometry pipeline, allowing the volume to be treated as a post-processing effect that interacts with the existing frame buffer and depth buffer [S1, unofficial]. It differs from its parent method, [Ray Marching Volume Rendering with Geometry Occlusion](2066-ray-marching-volume-rendering-with-geometry-occlusion.md), by bypassing the explicit bounding box intersection and geometry occlusion steps, relying instead on image-space depth testing and screen-space ray reconstruction [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** The current scene frame buffer (color), the current depth buffer, additional textures (e.g., noise textures for density/color variation), and uniform variables for camera position, object position, and orientation [S1, unofficial].
*   **Outputs:** The final composited color for each pixel, blending the volumetric contribution with the background scene [S1, unofficial].

**Data Structures:**
*   **Ray:** Defined by origin (camera position) and direction (computed per-pixel).
*   **Bounding Volume:** Typically a sphere defined by center and radius [S1, unofficial].
*   **Depth Buffer:** A 2D texture mapping screen coordinates to world or view space depth [S1, unofficial].

**Steps:**

1.  **Setup:**
    *   Compute the ray origin as the camera position [S1, unofficial].
    *   Compute the ray direction for the current fragment. This requires mapping the screen coordinate to a view-space direction, accounting for the camera's projection matrix and the object's position in the world [S1, unofficial].
    *   Recover the depth of the existing scene geometry at the current pixel from the depth buffer texture [S1, unofficial].

2.  **Intersection Check:**
    *   Perform a ray-sphere intersection test between the computed ray and the volume's bounding sphere [S1, unofficial].
    *   The function returns the near ($t_{near}$) and far ($t_{far}$) intersection distances if a hit occurs, or indicates no intersection if the ray misses the sphere [S1, unofficial].
    *   If no intersection, the shader outputs the background color from the frame buffer [S1, unofficial].

3.  **Main Loop (Ray Marching):**
    *   Initialize accumulated color ($C_{acc}$) to transparent (0,0,0,0) and accumulated opacity ($\alpha_{acc}$) to 0 [S1, unofficial].
    *   Iterate from $t = t_{near}$ to $t = t_{far}$ with a fixed step size $\Delta t$ [S1, unofficial].
    *   At each step, compute the world position $P = \text{origin} + t \cdot \text{direction}$ [S1, unofficial].
    *   Sample the volume density $\rho$ at $P$ using noise textures or a 3D texture [S1, unofficial].
    *   Accumulate density. The specific accumulation formula depends on the desired optical depth, but typically involves integrating $\rho \cdot \Delta t$ [S1, unofficial].
    *   Compute the color contribution $C_{step}$ based on density and lighting [S1, unofficial].
    *   Apply front-to-back compositing:
        $$ \alpha_{new} = \alpha_{acc} + (1 - \alpha_{acc}) \cdot (1 - e^{-\rho \cdot \Delta t}) $$
        $$ C_{new} = C_{acc} + C_{step} \cdot (1 - \alpha_{acc}) $$
        $$ \alpha_{acc} = \alpha_{new} $$
        $$ C_{acc} = C_{new} $$
    *   [G] If $\alpha_{acc}$ exceeds a threshold (e.g., 0.99), break the loop to save computation [G].

4.  **Blending:**
    *   Blend the accumulated volumetric color $C_{acc}$ and opacity $\alpha_{acc}$ with the background color $C_{bg}$ retrieved from the frame buffer [S1, unofficial].
    *   Standard alpha blending is used:
        $$ C_{final} = C_{acc} + C_{bg} \cdot (1 - \alpha_{acc}) $$
    *   Additive blending is also supported for specific effects (e.g., emissive nebulae) [S1, unofficial].

**Pseudocode:**

```python
def image_space_volume_ray_marching(camera_pos, object_pos, object_radius, 
                                    depth_buffer, frame_buffer, noise_texture, 
                                    step_size, max_steps):
    # 1. Setup
    # Compute ray direction based on screen coordinates, camera projection, and object position
    # This effectively grounds the 3D volume in the 3D world despite the 2D canvas
    ray_origin = camera_pos
    ray_direction = compute_ray_direction_for_pixel() 
    
    # Recover depth of existing scene geometry at this pixel
    scene_depth = depth_buffer.sample(ray_direction.screen_coords)
    
    # 2. Intersection Check
    # Ray-sphere intersection
    hit, t_near, t_far = ray_sphere_intersect(ray_origin, ray_direction, object_pos, object_radius)
    
    if not hit:
        return frame_buffer.sample(ray_direction.screen_coords)
    
    # 3. Main Loop
    acc_color = vec4(0.0)
    acc_alpha = 0.0
    
    t = t_near
    for i in range(max_steps):
        if t > t_far:
            break
            
        # Advance position
        pos = ray_origin + ray_direction * t
        
        # Sample density from noise/texture
        density = sample_volume_density(pos, noise_texture)
        
        # Accumulate
        # Assuming exponential attenuation for density
        alpha_step = 1.0 - exp(-density * step_size)
        
        # Compute step color (simplified, depends on lighting model)
        step_color = compute_volume_color(pos, density)
        
        # Front-to-back compositing
        acc_color = acc_color + step_color * (1.0 - acc_alpha)
        acc_alpha = acc_alpha + alpha_step * (1.0 - acc_alpha)
        
        # Early exit if fully opaque
        if acc_alpha >= 0.99:
            break
            
        t += step_size
        
    # 4. Blending
    bg_color = frame_buffer.sample(ray_direction.screen_coords)
    final_color = acc_color + bg_color * (1.0 - acc_alpha)
    
    return final_color
```

**Parameters:**
*   `step_size`: Distance between samples. Smaller values increase accuracy but reduce performance. Not given in the sources.
*   `max_steps`: Maximum number of iterations. Not given in the sources.
*   `object_radius`: Radius of the bounding sphere. Not given in the sources.

**Edge Cases and Pitfalls:**
*   **Grounding:** The model must be correctly grounded in the 3D world. Since rendering occurs on a flat 2D canvas, incorrect coordinate system selection or ray direction construction will result in the volume appearing detached or misaligned [S1, unofficial].
*   **Depth Buffer Interaction:** The volume must be occluded by closer objects, and opaque parts of the volume must occlude further scene parts. This is handled by sampling the depth buffer at every pixel to determine visibility against existing geometry [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of pixels and the number of steps per ray ($O(N_{pixels} \cdot N_{steps})$).
*   **Memory Complexity:** Low, primarily requiring storage for the depth buffer, frame buffer, and noise textures. No 3D volume texture is strictly required if procedural noise is used [S1, unofficial].
*   **Strengths:** Simple implementation as a post-processing pass; no need for explicit bounding box geometry; easy integration with existing rendering pipelines [S1, unofficial].
*   **Limitations:** Limited to screen-space volumes; cannot render volumes outside the current view frustum; performance depends heavily on resolution and step count [S1, unofficial].
*   **When to use:** Ideal for atmospheric effects, nebulae, and aurorae that are viewed from a fixed camera perspective and do not require complex geometric occlusion beyond standard depth testing [S1, unofficial].

## Background
This technique was popularized in the context of space simulation software, specifically for rendering nebulae and aurorae in Gaia Sky. It draws inspiration from shader-based ray marching examples found on platforms like Shadertoy, such as "Dusty Nebula 4" and "Supernova Remnant" by Duke [S1, unofficial]. The method addresses the challenge of rendering large-scale volumetric phenomena without the overhead of in-scene geometry encapsulation [S1, unofficial].
