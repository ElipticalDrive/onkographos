# EM-Cube Architecture
Also called: Enhanced Memory Cube-4

## Overview
EM-Cube is a VLSI architecture for low-cost, high-quality volume rendering at full video frame rates, derived from the Cube-4 architecture [S1, unofficial]. It computes sample points and gradients on-the-fly to project 3-dimensional volume data onto 2-dimensional images with realistic lighting and shading [S1, unofficial]. The method addresses three major implementation challenges: exploiting SDRAM bandwidth, keeping pin-count between adjacent ASICs tractable, and reducing on-chip storage for intermediate results [S1, unofficial]. It meets the bandwidth and pin-count challenges by using block-skewed memory, and meets the on-chip storage challenge by subdividing the volume in a technique called sectioning [S1, unofficial].

## How it works
### Inputs and Outputs
*   **Input:** 3D volume data stored in SDRAMs. The volume has dimensions $N \times M \times S$ (columns, rows, slices). Voxels are stored in memory with specific field layouts.
*   **Output:** 2D rendered image stored in pixel memory (SRAM).
*   **Configuration:** $C$ rendering chips (ASICs), $m$ 64Mbit SDRAMs per chip, and pixel memory buffers.

### Data Structures and Layouts

**Memory Voxel Format**
A memory voxel consists of the following conceptual components [S1, unofficial]:
1.  **Intensity field:** 8, 12, or 16 bits (indicates intensity or indexes an RGB table).
2.  **Index field:** 4, 8, 12, or 16 bits (for color lookup and material type).
3.  **Gradient coefficient:** 8 bits.
4.  **Opacity field:** 8-bit value or index to an opacity table.
5.  **Arbitrary user fields:** Padded so the total voxel size is a multiple of 16 bits.

**Pipeline Voxel**
The voxel processed in the rendering pipeline can be a simple transformation (e.g., table lookup) of the memory voxel fields. In the simplest case, the pipeline voxel is identical to the memory voxel [S1, unofficial].

**Lookup Tables**
Total storage required is $9 \times 512$ bytes [S1, unofficial]:
*   Two 512-byte opacity tables.
*   One 512-entry table per color component ($3 \times 512$ bytes) for color lookup.
*   Reflectance map: one 512-byte table per axis direction ($3 \times 512$ bytes) [S1, unofficial].
*   Arctangent table: 512 bytes [S1, unofficial].

**Memory Organization: Block-Skewed Memory**
To exploit SDRAM burst bandwidth and eliminate memory access conflicts (view independence) without duplicating data, memory is block-skewed [S1, unofficial].
*   **Blocking:** Uses a hierarchical block size $b$ (typically 8) tiled with miniblocks. This reduces inter-chip bandwidth and pin count compared to pure skewing [S1, unofficial].
*   **Skewing:** Distributes data to avoid conflicts when rays access voxels from different chips [S1, unofficial].

**Volume Organization: Sectioning**
To reduce on-chip buffer size, the volume is divided into $L$ horizontal sections [S1, unofficial].
*   Each section is processed in turn.
*   Results are combined after processing all sections [S1, unofficial].
*   Typical value: $L=8$ [S1, unofficial].

### Numbered Steps

1.  **Initialization:** Load volume data into SDRAMs using block-skewed layout. Initialize lookup tables. Initialize $C$ rendering chips.
2.  **Section Loop:** For each section $s$ from 1 to $L$:
    3.  **Interim Pixel Load:** If $s > 1$, read interim pixels from off-chip pixel memory into the on-chip compositing buffer. These pixels correspond to rays that exited the previous section's face [S1, unofficial].
    4.  **Voxel Plane Load:** Load the current voxel plane slice into the on-chip slice buffer.
        *   If $s > 1$, re-read the bottom two rows of the previous voxel plane to support interpolation and gradient estimation for the current section [S1, unofficial].
    5.  **Ray Casting Loop:** For each ray (pixel) in the current section:
        6.  **Sample Point Computation:** Compute sample point coordinates based on ray origin, direction, and step size [S1, unofficial].
        7.  **Voxel Access:** Access the voxel at the sample point from the slice buffer. Handle block-skewed memory addressing to determine which chip holds the data [S1, unofficial].
        8.  **Interpolation:** Perform tri-linear interpolation using the current voxel and neighbors (including the re-read previous row if necessary) to get the interpolated value [S1, unofficial].
        9.  **Gradient Estimation:** Compute gradient using central differences from samples in the slice ahead and slice behind (requiring $2N^2/C$ storage) [S1, unofficial].
        10. **Shading:** Compute lighting using the gradient and view direction. Use lookup tables for opacity and reflectance [S1, unofficial].
        11. **Classification:** Map intensity/value to color and opacity using lookup tables [S1, unofficial].
        12. **Compositing:** Composite the partial pixel (color, opacity) into the running pixel buffer using front-to-back compositing [S1, unofficial].
    6.  **Interim Pixel Store:** For rays exiting the current section's face, write the running pixel value to off-chip pixel memory as an interim pixel [S1, unofficial].
7.  **Final Output:** After processing all sections, the final pixels are available in the pixel memory (or composited from interim pixels if not fully resolved on-chip) [S1, unofficial].

### Formulas

**Slice Storage per Rendering Chip**
Storage for the slice and previous row interpolation [S1, unofficial]:
$$ \text{Slice Storage} = \frac{N^2 + N}{C} \text{ voxels} $$
Where $N$ is the volume dimension (columns/rows) and $C$ is the number of rendering chips.

**Gradient Estimate Storage per Rendering Chip**
Storage for slice ahead and slice behind [S1, unofficial]:
$$ \text{Gradient Storage} = \frac{2N^2}{C} \text{ samples} $$

**Compositing Storage per Rendering Chip**
Storage for running pixels [S1, unofficial]:
$$ \text{Compositing Storage} = \frac{N^2}{C} \text{ running pixels} $$
(3 to 6 bytes per pixel)

**Lookup Table Storage**
Total storage [S1, unofficial]:
$$ \text{LUT Storage} = 9 \times 512 \text{ bytes} $$

**Bandwidth Overhead from Sectioning**
Re-reading voxels for interpolation/gradient [S1, unofficial]:
$$ \text{Overhead} = \frac{2(L-1)N^2}{N^3} = \frac{2(L-1)}{N} $$
Where $L$ is the number of sections. This is less than 5% if $L \le 8$ [S1, unofficial].

**Memory Capacity Constraint**
Total memory capacity in Mbytes [S1, unofficial]:
$$ \text{Capacity} = \frac{2vNM S}{C \cdot 8m} \text{ Mbytes} $$
Where $v$ is voxel size in 16-bit fields ($v=1$ for 16-bit, $v=2$ for 32-bit), $N, M, S$ are volume dimensions, $C$ is number of chips, and $m$ is number of 64Mbit SDRAMs per chip.

**Frame Rate Constraint**
Determined by rendering chip processing rate [S1, unofficial]:
$$ f = \frac{C}{2vNMS} \times 250 \text{ M/sec} \text{ frames/sec} $$

**Slice Buffer Constraint**
Size of slice buffer per chip in bytes [S1, unofficial]:
$$ \text{Slice Buffer} = \frac{2vNM}{LC} / 4096 \text{ bytes} $$

### Parameters
*   **N:** Volume dimension (columns/rows/slices), typically 256 [S1, unofficial].
*   **b:** Hierarchical block size, typically 8 [S1, unofficial].
*   **L:** Number of horizontal sections, typically 8 [S1, unofficial].
*   **v:** Voxel size in 16-bit fields ($v=1$ for 16-bit, $v=2$ for 32-bit) [S1, unofficial].
*   **C:** Number of rendering chips. Target configuration uses 4 chips [S1, unofficial].
*   **m:** Number of 64Mbit SDRAMs per rendering chip. Target configuration uses 4 [S1, unofficial].

### Edge Cases and Pitfalls
*   **On-chip Buffer Size:** With $N=256, b=8, 16$-bit voxels, buffer storage per chip must be $<200$ Kbits for a $100 \text{ mm}^2$ core. Without sectioning, this would require 32 chips, which is too many. Sectioning ($L=8$) reduces slice buffer size by $1/L$ [S1, unofficial].
*   **Interim Pixel Latency:** Reading interim pixels from off-chip memory can cause latency. This is hidden by the time required to reload the additional two voxels per slice from voxel memory [S1, unofficial].
*   **SDRAM Clock Speed:** Sectioning increases bandwidth requirements. For $L=8$, the SDRAM clock and rendering chip pipelines must run 5% faster (e.g., 132MHz) or the frame rate must be 5% slower (e.g., 28 frames/sec) [S1, unofficial].
*   **Voxel Scaling:** If voxel size $v$ doubles, one must halve the volume size ($N$ or $M$), double the number of chips/SDRAMs, or double $L$ and halve the frame rate to maintain constraints [S1, unofficial].

## Operating characteristics
*   **Performance Target:** Render images from a $256^3 \times 16$ bit data set at 28-30 frames/sec using a configuration of four rendering chips (ASICs), four 64Mbit SDRAMs, and four SRAMs [S1, unofficial].
*   **Processing Rate:** Each rendering chip processes 16-bit voxels at 125MHz [S1, unofficial].
*   **Scalability:** The architecture scales to larger volume datasets and/or higher frame rates by adding additional ASICs, SDRAMs, and pixel memories [S1, unofficial].
*   **Strengths:**
    *   Low-cost implementation suitable for PCI cards in PCs [S1, unofficial].
    *   Exploits SDRAM burst bandwidth via block-skewed memory [S1, unofficial].
    *   Reduces pin count via blocking [S1, unofficial].
    *   Reduces on-chip storage via sectioning [S1, unofficial].
*   **Limitations:**
    *   Sectioning increases bandwidth overhead (re-reading voxels) [S1, unofficial].
    *   Requires faster SDRAM clock or slower frame rate due to sectioning overhead [S1, unofficial].
    *   Does not address supersampling, subvolumes, or perspective projections in the base description [S1, unofficial].
*   **When to Use:** When low-cost, real-time volume rendering is required on hardware with limited pin count and on-chip storage, and the volume data fits within the SDRAM capacity.
*   **When Not to Use:** When supersampling or perspective projections are required without architectural modifications, or when the volume size exceeds the scalable limits of the available chip count.

## Background
EM-Cube is derived from the Cube-4 architecture developed at SUNY at Stony Brook [S1, unofficial]. Cube-4 was found to be impractical for low-cost ASIC implementation because it required too many memory modules (about 20), too many pins per rendering chip (on the order of 512 signal pins), and too much on-chip storage (excess of $100 \text{ mm}^2$ for storage alone) [S1, unofficial]. EM-Cube was developed to address these specific implementation challenges, targeting PCI cards in PCs [S1, unofficial]. The architecture was presented by Rändy Osborne, Hanspeter Pfister, Hugh Lauer, Neil McKenzie, Sarah Gibson, Wally Hiatt, and TakaHide Ohkami from MERL (Mitsubishi Electric Research Lab) [S1, unofficial].
