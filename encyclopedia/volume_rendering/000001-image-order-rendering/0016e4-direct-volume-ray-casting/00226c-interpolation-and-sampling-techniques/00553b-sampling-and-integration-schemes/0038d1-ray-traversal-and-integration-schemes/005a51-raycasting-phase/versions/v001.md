# Raycasting Phase

Also called: Data sampling, Ray integration, Two-Pass Raycasting with Back-Face Depth Buffering

## Overview
The Raycasting Phase is the computational core of image-order volume rendering where optical properties are sampled along camera rays and integrated to produce pixel colors. It solves the problem of mapping discrete volumetric data to continuous screen-space pixels by performing numerical integration of the rendering equation. It is distinguished from sibling methods by its specific reliance on a two-pass geometry-based traversal strategy using back-face depth buffering to determine ray entry and exit points, as well as its sensitivity to decomposition geometry in parallel implementations [S1, S2].

## How it works
The method operates in two distinct passes to determine the integration bounds and then performs the integration.

**Inputs:**
*   Volumetric data grid $V$.
*   Camera parameters (origin $\mathbf{o}$, direction $\mathbf{d}$, field of view).
*   Decomposition geometry (block structure for parallel processing) [S1].
*   Step length parameter $d$ [S2].

**Outputs:**
*   Final pixel color $C_{pixel}$.
*   Intermediate fragment buffers (back-face and front-face coordinates) [S2].

**Data Structures:**
1.  **Auxiliary Buffers:** Two texture buffers bound to distinct texture units. One stores back-face depth/coordinates, the other stores front-face coordinates [S2].
2.  **Fragment Buffer:** Temporary storage for image fragments. Size constraints may require scaling down data volume if the buffer overflows (e.g., at image size $23040^3$) [S1].

**Algorithm Steps:**

1.  **Pass 1: Back-Face Depth Buffering**
    *   Render the volume bounding box or decomposition blocks.
    *   Bind auxiliary buffers for multiple render targets (e.g., using `GL_ARB_draw_buffers`) [S2].
    *   For each fragment generated by a back-facing polygon, store its texture coordinates in the back-face buffer. Front-facing fragments are discarded or ignored in this pass [S2].

2.  **Pass 2: Ray Initialization and Integration Setup**
    *   Bind the two auxiliary buffers to texture units.
    *   Project a viewport-filling quadrilateral.
    *   For each pixel:
        *   Fetch back-face texture coordinates from the first buffer.
        *   If invalid (no back-face hit), discard the fragment [S2].
        *   Otherwise, retrieve the corresponding front-face texture coordinates from the second buffer.
        *   Compute the step vector $\Delta \mathbf{p}$ along the ray based on the predefined step length $d$ and the distance between front and back faces.
        *   Calculate the total number of iterations $N$ required to traverse the ray segment [S2].

3.  **Integration Loop**
    *   Initialize ray position $\mathbf{p}$ at the front-face entry point.
    *   For $i = 0$ to $N-1$:
        *   Sample the volume data $V(\mathbf{p})$ using trilinear interpolation [S1].
        *   Apply shading (e.g., Phong-style shader) to compute optical properties (color, opacity) [S1].
        *   Integrate the contribution into the accumulated color and opacity using a compositing scheme (e.g., front-to-back) [S2].
        *   Advance $\mathbf{p}$ by the step vector $\Delta \mathbf{p}$.
    *   Note: The integration may be structured in slabs. Each slab of thickness $2d$ is defined by three successive samples $(s_f, s_m, s_b)$, with the next slab indexed by $(s_f, s_m, s_b)$ shifted accordingly [S2].

**Pseudocode:**

```python
def raycasting_phase(volume_data, camera, step_length_d, decomposition):
    # Pass 1: Determine entry and exit points via back-face buffering
    back_face_coords = render_back_faces(volume_data, camera, decomposition)
    
    # Pass 2: Initialize rays and integrate
    final_colors = empty_buffer(camera.resolution)
    
    for pixel in camera.viewport:
        # Fetch back-face coordinate
        bf_coord = back_face_coords[pixel]
        
        if bf_coord is invalid:
            continue # Discard fragment
            
        # Fetch front-face coordinate
        ff_coord = get_front_face_coord(pixel)
        
        # Compute ray parameters
        ray_origin = ff_coord
        ray_direction = normalize(camera.direction)
        # Calculate step vector based on step_length_d and geometry
        step_vector = compute_step_vector(ray_direction, step_length_d, ff_coord, bf_coord)
        
        # Determine number of steps
        num_steps = compute_num_steps(ray_origin, bf_coord, step_vector)
        
        # Integration
        accumulated_color = vec3(0, 0, 0)
        accumulated_opacity = 0.0
        current_pos = ray_origin
        
        for i in range(num_steps):
            # Sample volume data
            # Trilinear interpolation is used for data sampling along the ray
            sample_value = trilinear_interpolate(volume_data, current_pos)
            
            # Apply shading (Phong-style)
            color, opacity = apply_phong_shading(sample_value, current_pos, camera)
            
            # Front-to-back compositing
            # C_out = C_in + (1 - A_in) * C_sample * alpha_sample
            # A_out = A_in + (1 - A_in) * alpha_sample
            weight = (1.0 - accumulated_opacity) * opacity
            accumulated_color += weight * color
            accumulated_opacity += weight
            
            # Advance position
            current_pos += step_vector
            
        final_colors[pixel] = accumulated_color
        
    return final_colors
```

**Parameters:**
*   $d$: Predefined step length. Slabs are defined with thickness $2d$ [S2].
*   Interpolation: Trilinear interpolation is the standard method for sampling [S1].
*   Shading: Phong-style shading is applied during integration [S1].

**Edge Cases and Pitfalls:**
*   **Thread Divergence:** The final raycasting time is determined by the slowest thread (the one with the most integration steps). This varies significantly with view and decomposition geometry [S1].
*   **Weak Scaling Degradation:** Perspective projection causes variation in the number of samples per thread. As scale increases, each core handles a smaller portion of the frustum, increasing this variation and causing up to 20% performance degradation [S1].
*   **Memory Overflow:** Increasing image size (e.g., to $23040^3$) can cause temporary fragment buffers to overflow, forcing a reduction in data size (e.g., to $19200^3$) [S1].
*   **Hybrid Memory Performance:** At high concurrency, hybrid-memory implementations may underperform distributed memory by 10% due to irregular block sizes (e.g., aggregated $1 \times 2 \times 3$ blocks) interacting with camera direction [S1].

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of samples per ray and the number of rays (pixels). However, parallel performance is bounded by the maximum integration steps among all threads [S1].
*   **Memory Complexity:** Proportional to the volume data size plus temporary buffers for fragments. Fragment buffer size is critical; insufficient memory forces data downsampling [S1].
*   **Scalability:**
    *   Distributed memory achieves linear scaling up to 216,000-way concurrency for the raycasting phase [S1].
    *   Hybrid-memory implementations maintain ~80% scalability in weak scaling up to 216,000 cores but exhibit sublinear scaling in strong scaling due to irregular decomposition geometry [S1].
*   **Performance:** At 448-way concurrency with a $4608^3$ dataset, the hybrid/CUDA implementation averaged 1.18s for raycasting [S1].
*   **Strengths:** No message passing is involved in the raycasting phase itself, allowing for efficient scaling in distributed memory systems [S1].
*   **Limitations:** Performance is highly sensitive to view direction relative to decomposition geometry. Perspective projection exacerbates load imbalance in weak scaling [S1].

## Background
The method originated in the context of large-scale parallel volume rendering on multi- and many-core systems. It was developed to address the challenges of scaling raycasting across distributed and hybrid memory architectures. The two-pass approach with back-face depth buffering was introduced to efficiently determine ray entry and exit points without complex ray-volume intersection algorithms, leveraging GPU rasterization capabilities [S1, S2].
