# Image-order Rendering Loop

Also called: Image order approach, Image-Order Volume Ray Casting, Image-ordered ray casting, Main Rendering Loop, Octree Rendering Loop

## Overview
The image-order rendering loop is the fundamental control structure for volume ray casting, iterating over each pixel of the output image to generate a camera ray and invoking a raymarcher to compute the final color [S2, unofficial][S3]. It differs from object-order (rasterization) by being more "CPU-like" in its iteration logic, offering correct perspective projection, single-pass ray casting, and full 32-bit compositing precision without requiring intermediate buffers [S1, unofficial].

## How it works
The method operates by mapping 2D screen coordinates to 3D world-space rays and accumulating optical properties along those rays.

**Inputs and Outputs**
*   **Inputs**: Image dimensions ($W \times H$), camera parameters (position, direction, projection mode), volume data structure, and shading mode [S2, unofficial].
*   **Outputs**: A 2D image buffer where each pixel $(x, y)$ contains the accumulated color $C_{out}$ [S3].

**Data Structures**
*   **Camera State**: Contains `cameraPos` (origin), `cameraDir` (direction vector), and `ProjectionMode` (enum: `PERSPECTIVE` or `ORTHOGRAPHIC`) [S2, unofficial].
*   **Shading Mode**: Enum determining the compositing and lighting behavior. Values include `TRACE`, `DEPTH`, `DEPTH_HIT`, `DIFFUSE`, `NORMAL`, and `INDEX` [S2, unofficial].
*   **Ray Structure**: Defined by origin $\mathbf{o}$ and direction $\mathbf{d}$ [S2, unofficial].

**Numbered Steps**
1.  **Initialization**: Set `CompletedSamples = 0`. Calculate light bounds $p_0, p_1$ if necessary for light intersection tests [S2, unofficial].
2.  **Pixel Loop**: Iterate $y$ from $0$ to $vheight-1$ and $x$ from $0$ to $vwidth-1$ [S2, unofficial].
3.  **Ray Generation**:
    *   Calculate normalized pixel coordinates $rx, ry$ from $x, y$ [S2, unofficial].
    *   Transform position `pos` based on projection mode [S2, unofficial]:
        *   If `PERSPECTIVE`: $\mathbf{o} = \text{cameraPos}$, $\mathbf{d} = \text{cameraDir} + \text{pos}$ [S2, unofficial].
        *   If `ORTHOGRAPHIC`: $\mathbf{o} = \text{cameraPos} + \text{pos}$, $\mathbf{d} = \text{cameraDir}$ [S2, unofficial].
4.  **Ray Marching/Tracing**:
    *   If `ShadingMode == TRACE`: Call `ShadePathTrace` with the ray and accumulated previous samples [S2, unofficial].
    *   Else: Call `Raymarch` [S2, unofficial].
5.  **Shading/Compositing**:
    *   If a hit is detected: Shade based on `ShadingMode` (e.g., `DEPTH`, `DIFFUSE`) [S2, unofficial].
    *   If no hit but ray intersects light AABB: Write light color [S2, unofficial].
    *   Else: Write dark color (e.g., 25, 25, 25) [S2, unofficial].
6.  **Output**: Write the resulting color to the display pixel [S3].

**Formulas**
*   **Ray Origin/Direction (Perspective)**:
    $$ \mathbf{o} = \mathbf{C}_{pos}, \quad \mathbf{d} = \mathbf{C}_{dir} + \mathbf{P}_{norm} $$
    Where $\mathbf{C}_{pos}$ is camera position, $\mathbf{C}_{dir}$ is camera direction, and $\mathbf{P}_{norm}$ is the normalized pixel offset [S2, unofficial].
*   **Ray Origin/Direction (Orthographic)**:
    $$ \mathbf{o} = \mathbf{C}_{pos} + \mathbf{P}_{norm}, \quad \mathbf{d} = \mathbf{C}_{dir} $$
    [S2, unofficial].
*   **Depth Shading**:
    $$ C_{out}.g = C_{in}.g \times \frac{\text{depth}}{2.0} $$
    Where `depth` is the distance from camera to hit point [S2, unofficial].
*   **Normal Shading**:
    $$ C_{out}.c = \begin{cases} 1.0 & \text{if } N.c \neq 0 \\ 0.0 & \text{otherwise} \end{cases} $$
    For each component $c \in \{x, y, z\}$ [S2, unofficial].

**Parameters**
*   **ShadingMode**: Determines shading behavior. Common values: `TRACE`, `DEPTH`, `DEPTH_HIT`, `DIFFUSE`, `NORMAL`, `INDEX` [S2, unofficial].
*   **ProjectionMode**: Determines ray generation. Values: `PERSPECTIVE`, `ORTHOGRAPHIC` [S2, unofficial].
*   **Compositing Methods**: MIP, averaging, nearest-point, and alpha compositing are commonly used in the compositing module [S3].

**Pseudocode**
```python
def image_order_rendering_loop(image_width, image_height, camera, volume_data, shading_mode):
    """
    Renders a volume using the image-order loop.
    
    Args:
        image_width (int): Width of the output image.
        image_height (int): Height of the output image.
        camera (Camera): Object containing cameraPos, cameraDir, and ProjectionMode.
        volume_data (VolumeData): The volume dataset to render.
        shading_mode (Enum): One of TRACE, DEPTH, DEPTH_HIT, DIFFUSE, NORMAL, INDEX.
        
    Returns:
        list: 2D list of RGB tuples representing the rendered image.
    """
    # Initialize output buffer
    image = [[(0, 0, 0) for _ in range(image_width)] for _ in range(image_height)]
    
    # Pre-calculate light bounds if needed for light intersection tests
    # light_bounds = calculate_light_bounds() 

    for y in range(image_height):
        for x in range(image_width):
            # 1. Calculate normalized pixel coordinates
            # Note: Exact normalization depends on camera setup; assuming simple linear mapping here
            rx = (x / image_width) * 2.0 - 1.0
            ry = (y / image_height) * 2.0 - 1.0
            
            # 2. Generate Ray based on ProjectionMode
            if camera.ProjectionMode == "PERSPECTIVE":
                ray_origin = camera.cameraPos
                # pos is derived from rx, ry; simplified here as a vector addition
                ray_direction = normalize(camera.cameraDir + vec3(rx, ry, 0.0))
            else: # ORTHOGRAPHIC
                ray_origin = camera.cameraPos + vec3(rx, ry, 0.0)
                ray_direction = camera.cameraDir

            # 3. Ray Marching / Tracing
            hit_color = (0, 0, 0)
            hit = False
            
            if shading_mode == "TRACE":
                # Path tracing logic
                hit_color = shade_path_trace(ray_origin, ray_direction, volume_data, depth=100)
                hit = True # Assume path trace handles hit detection internally
            else:
                # Standard raymarching
                hit, hit_point, hit_normal = raymarch(ray_origin, ray_direction, volume_data)
                
                if hit:
                    # 4. Shading based on mode
                    if shading_mode == "DEPTH":
                        depth_dist = distance(camera.cameraPos, hit_point)
                        # Base color from volume, modulated by depth
                        base_color = volume_data.sample(hit_point)
                        hit_color = (base_color[0], base_color[1] * (depth_dist / 2.0), base_color[2])
                    elif shading_mode == "DEPTH_HIT":
                        depth_dist = distance(camera.cameraPos, hit_point)
                        base_color = volume_data.sample(hit_point)
                        hit_color = (base_color[0], base_color[1] * (depth_dist / 2.0), base_color[2])
                    elif shading_mode == "DIFFUSE":
                        # Simple diffuse shading
                        light_dir = normalize(vec3(1.0, 1.0, -1.0))
                        normal = hit_normal if hit_normal else vec3(0, 1, 0)
                        diff = max(dot(normal, light_dir), 0.0)
                        base_color = volume_data.sample(hit_point)
                        hit_color = (base_color[0] * diff, base_color[1] * diff, base_color[2] * diff)
                    elif shading_mode == "NORMAL":
                        # Encode normal as color
                        n = hit_normal
                        hit_color = (
                            1.0 if n.x != 0 else 0.0,
                            1.0 if n.y != 0 else 0.0,
                            1.0 if n.z != 0 else 0.0
                        )
                    elif shading_mode == "INDEX":
                        # Render volume index
                        hit_color = volume_data.get_index(hit_point)
                    else:
                        # Default or unknown mode
                        hit_color = (0, 0, 0)
                else:
                    # Check for light intersection if no volume hit
                    # Note: Specific light AABB logic from source [S2, unofficial]
                    # If ray intersects light AABB, write light color
                    # Else, write dark color
                    if intersects_light_aabb(ray_origin, ray_direction):
                        hit_color = (255, 255, 255) # Light color
                    else:
                        hit_color = (25, 25, 25) # Dark color

            # 5. Output
            image[y][x] = hit_color
            
    return image
```

**Edge Cases and Pitfalls**
*   **Shader Model Requirements**: Requires Shader Model 3.0 or higher to enable conditional loops (early loop exit) in fragment shaders, which replaces multiple passes and early-z testing [S1, unofficial].
*   **Precision**: Image-order allows for 32-bit compositing precision, avoiding the need for a compositing buffer [S1, unofficial].
*   **Empty Space**: In sparse volumes (e.g., octrees), empty space must be skipped efficiently to avoid performance degradation [S1, unofficial].

## Subtopics

### [Terminal Rendering Pipeline](3434-terminal-rendering-pipeline.md)
The Terminal Rendering Pipeline renders a 3D scene to a text-based terminal buffer by iterating over pixels, mapping them to Normalized Device Coordinates (NDC), casting rays via a raymarcher, and applying ASCII/ANSI styling based on depth and lighting. It differs from standard terminal rendering by explicitly accounting for character aspect ratio when converting pixel indices to NDC and using ANSI escape codes to modulate brightness based on depth percentage, effectively acting as a low-resolution, text-based raymarcher.

### [Diffuse Octree Rendering](4989-diffuse-octree-rendering.md)
Diffuse Octree Rendering is an image-order raycasting technique that traverses an octree to locate the first leaf node containing data for each pixel, then computes surface lighting using a diffuse and Phong specular model with distance attenuation. It differs from sibling methods by relying on a coarse-to-fine octree traversal to skip empty space entirely, rather than marching through a dense voxel grid.

### [Ray Casting Loop with Supersampling](12786-ray-casting-loop-with-supersampling.md)
Renders an image by casting rays per pixel through a scene, with optional multi-sample anti-aliasing using uniform sub-pixel jittering. It extends the basic Image-order Rendering Loop by introducing a sampling loop that averages multiple jittered ray samples per pixel to reduce aliasing artifacts.

### Renderer configuration
The Renderer configuration is a top-level rendering controller managing ray depth, sampling rate, and background color [S4, unofficial].
*   **Parameters**:
    *   `maxDepth`: Maximum recursion depth for ray tracing. Default: 100 [S4, unofficial].
    *   `samplesPerPixel`: Number of samples per pixel for anti-aliasing/noise reduction. Default: 500 [S4, unofficial].
*   **Layout**:
    *   Class `Renderer`.
    *   Fields: `int maxDepth = 100`, `int samplesPerPixel = 500`, `RGB background{0, 0, 0}` [S4, unofficial].
    *   Methods: `RGB rayColor(const Ray &ray, const Scene &scene, int depth) const`, `void render(const Scene &scene, const Camera &camera, Image &image) const` [S4, unofficial].

## Operating characteristics
*   **Time Complexity**: $O(W \times H \times S)$, where $W$ and $H$ are image dimensions and $S$ is the number of samples per pixel (or steps in ray marching) [S3].
*   **Memory Complexity**: $O(W \times H)$ for the output image buffer, plus the memory required for the volume data structure [S1, unofficial].
*   **Performance**: Image-order is described as more "CPU-like" but offers correct perspective and single-pass ray casting with 32-bit compositing [S1, unofficial]. It is flexible, supporting adaptive sampling [S1, unofficial].
*   **Strengths**: Correct perspective, single-pass, 32-bit compositing precision, flexibility (adaptive sampling) [S1, unofficial].
*   **Limitations**: Can be computationally expensive for high-resolution images or complex volumes due to the per-pixel ray casting [S1, unofficial].
*   **When to Use**: When correct perspective and high-quality compositing are required, and when the hardware supports conditional loops in shaders (Shader Model 3.0+) [S1, unofficial].
*   **When Not to Use**: When performance is critical and lower quality (e.g., object-order rasterization) is acceptable, or when the hardware does not support efficient conditional loops in shaders [S1, unofficial].

## Background
The image-order approach is a fundamental technique in volume rendering, often contrasted with object-order (rasterization) methods [S1, unofficial]. It has been widely used in GPU-based volume ray casting, with notable implementations in the NVIDIA SDK and various research papers [S1, unofficial]. The technique is particularly relevant for applications requiring high-quality visualization, such as medical imaging (e.g., endomicroscopic images for oral cancer detection) [S3]. The use of image-order rendering on FPGAs has also been explored for its flexibility and cost-effectiveness in prototype development [S3].
