# Distributed AMR Volume Rendering with Cost-Range Decomposition

Also called: Cost-range Decomposition, Distributed Texture-Based Slicing

## Overview
Cost-range decomposition is a domain decomposition strategy for parallel direct volume ray casting of Adaptive Mesh Refinement (AMR) data that assigns data subsets to processing nodes based on estimated rendering cost to achieve perfect load balancing [S1, unofficial]. It differs from sibling methods like Domain Block Decomposition by prioritizing computational balance over memory efficiency, ensuring that nodes with higher rendering loads receive fewer data patches [S1, unofficial].

## How it works
The method operates on a view-independent kD-tree generated during grid homogenization. It maps the view-dependent rendering order of AMR grid patches to a linear cost interval, allowing for static load balancing without per-frame communication overhead.

### Inputs and Outputs
*   **Inputs**:
    *   AMR dataset.
    *   View-independent kD-tree structure (generated during homogenization).
    *   Number of rendering nodes $n$.
    *   Camera viewpoint (used to determine back-to-front traversal order).
*   **Outputs**:
    *   Assignment of grid patches to nodes $0 \dots n-1$.
    *   Partial images from each node.
    *   Final composite image.

### Data Structures
**kD-Tree Node Layout**:
Each node in the homogenizing kD-tree stores a `cost` field [S1, unofficial].
*   **Leaf Node**: `cost` = estimated rendering cost of the grid patch it represents.
*   **Interior Node**: `cost` = sum of `cost` of its two children [S1, unofficial].

**Cost Interval Representation**:
The total rendering cost is represented as a single interval $[0, C_{total}]$, where $C_{total}$ is the sum of costs of all leaves. This interval is conceptually split into $n$ equal sub-intervals of size $C_{total} / n$ [S1, unofficial].

### Algorithm Steps

1.  **Homogenization and Cost Estimation**:
    Construct the view-independent kD-tree for the AMR data. For each leaf node representing a grid patch, calculate its rendering cost. For interior nodes, set the cost to the sum of its children's costs [S1, unofficial].

2.  **Cost Interval Calculation**:
    Determine the total cost $C_{total}$ by summing the costs of all leaf nodes. Calculate the target cost per node:
    $$ C_{target} = \frac{C_{total}}{n} $$

3.  **Node Assignment (Static)**:
    Assign leaves to nodes based on their position in the back-to-front rendering order. The leaves are conceptually stacked in rendering order, each occupying an interval width equal to its cost.
    *   A leaf $L$ is assigned to node $i$ if at least half of its cost interval falls within the $i$-th sub-interval of the total cost range [S1, unofficial].
    *   Specifically, if the cumulative cost of leaves preceding $L$ is $C_{prev}$ and the cost of $L$ is $C_L$, $L$ is assigned to node $i$ where:
        $$ i = \left\lfloor \frac{C_{prev} + 0.5 \cdot C_L}{C_{target}} \right\rfloor $$
    *   *Note*: The sources state that "all decisions about traversing or skipping parts of the kd-tree are made during back-to-front traversal, without requiring additional communication between nodes" [S1, unofficial]. This implies the assignment logic is embedded in the traversal or pre-computed such that the node responsible for a patch is determined locally by the cost thresholds.

4.  **Distributed Rendering**:
    Each node performs volume rendering (e.g., texture-based slicing or cell projection) on its assigned grid patches.
    *   **Pitfall**: Grid patches belonging to the same original AMR grid may be assigned to multiple nodes. Each node must load the full data for any grid patch it is assigned, leading to potential data replication [S1, unofficial].

5.  **Image Compositing**:
    Composite partial images from all nodes into the final image.
    *   **Ordering**: Composite in increasing order of node index ($0, 1, \dots, n-1$).
    *   **Correctness**: Due to the cost-range assignment, no grid patch rendered by node $i$ can occlude any grid patch rendered by node $i-1$, nor can it be occluded by any patch from node $i+1$ [S1, unofficial]. This allows simple sequential compositing.
    *   **Algorithm**: Use a binary tree compositing algorithm. This requires $\lceil \log_2 n \rceil$ compositing rounds [S1, unofficial].
    *   In each round, a node either sends its image, receives an image and composites it, or is idle.

def cost_range_decomposition(kd_tree, num_nodes, viewpoint):
    """
    Assigns AMR grid patches to nodes based on cost-range decomposition.
    kd_tree: The root of the homogenizing kD-tree.
    num_nodes: Number of rendering nodes n.
    viewpoint: Camera parameters to determine back-to-front traversal order.
    """
    # Step 1: Calculate costs (already stored in nodes per source, but explicit for clarity)
    # Leaf cost is estimated rendering cost. Interior cost is sum of children.
    # This is assumed to be done during homogenization.
    
    # Step 2: Determine total cost
    total_cost = kd_tree.root.cost
    
    # Step 3: Define sub-intervals
    target_cost = total_cost / num_nodes
    
    # Step 4: Assign leaves based on rendering order
    # We simulate the back-to-front traversal to assign nodes.
    # The source states decisions are made during traversal without communication.
    # Here we pre-calculate the assignment for implementation clarity.
    
    assignments = {} # Map: leaf_id -> node_index
    
    # Get leaves in back-to-front order for the current viewpoint
    leaves_in_order = get_leaves_in_back_to_front_order(kd_tree, viewpoint)
    
    current_cumulative_cost = 0.0
    
    for leaf in leaves_in_order:
        leaf_cost = leaf.cost
        
        # Determine which node this leaf belongs to.
        # The leaf occupies the interval [current_cumulative_cost, current_cumulative_cost + leaf_cost]
        # It is assigned to node i if at least half of this interval is in sub-interval i.
        
        # Start of leaf's cost interval
        start_cost = current_cumulative_cost
        # End of leaf's cost interval
        end_cost = current_cumulative_cost + leaf_cost
        
        # Midpoint of leaf's cost interval
        mid_cost = start_cost + 0.5 * leaf_cost
        
        # Calculate node index based on midpoint
        # Node i covers cost range [i * target_cost, (i+1) * target_cost)
        node_index = int(mid_cost / target_cost)
        
        # Clamp to valid range [0, num_nodes - 1]
        if node_index >= num_nodes:
            node_index = num_nodes - 1
            
        assignments[leaf.id] = node_index
        
        current_cumulative_cost = end_cost
        
    return assignments

### Parameters and Typical Values
*   **$n$**: Number of rendering nodes. Typical values depend on cluster size.
*   **Cost Estimation**: Proportional to the number of cells in the grid patch and the projected size of each cell [S1, unofficial].

### Edge Cases and Pitfalls
*   **Memory Efficiency**: Poor. Grid patches from the same original AMR grid may be assigned to multiple nodes, forcing each to load the entire grid's data [S1, unofficial].
*   **Viewpoint Changes**: Changing the viewpoint alters the back-to-front order, causing grid patches to change assigned nodes. This forces incremental data replication between nodes. After several viewpoint changes, the entire dataset may be replicated at every node [S1, unofficial].
*   **Cost Estimate Accuracy**: The strategy relies on accurate cost estimates for "perfect load balancing." Inaccurate estimates lead to imbalance [S1, unofficial].

## Operating characteristics
*   **Time Complexity**:
    *   **Load Balancing**: Aims for perfect load balancing if cost estimates are accurate [S1, unofficial].
    *   **Compositing**: Requires $\lceil \log_2 n \rceil$ rounds for $n$ nodes [S1, unofficial].
*   **Memory Complexity**:
    *   **High**: Due to potential data replication. A single AMR grid may be loaded by multiple nodes if its patches are scattered across different cost ranges [S1, unofficial].
*   **Performance**:
    *   Comparable compositing time to Domain Block Decomposition [S1, unofficial].
    *   Better load balancing than Domain Block Decomposition [S1, unofficial].
*   **Strengths**:
    *   Excellent load balancing for heterogeneous computational loads.
    *   Simple compositing logic due to node-index ordering.
    *   No additional communication required during traversal for assignment decisions [S1, unofficial].
*   **Limitations**:
    *   Poor memory efficiency.
    *   Sensitive to viewpoint changes due to dynamic reassignment and data replication.
*   **When to Use**: When load balancing is critical and memory bandwidth/availability is not the primary bottleneck, or when the dataset is small enough to fit in memory multiple times.
*   **When Not to Use**: When memory is constrained, or when interactive rendering with frequent viewpoint changes is required without incurring high data transfer costs.

## Background
The method was introduced by Kreylos et al. in the context of remote interactive direct volume rendering of AMR data [S1, unofficial]. It is part of a framework that uses homogenization via kD-tree, texture-based slicing, and cost-range decomposition [S2, unofficial]. It was developed to address the difficulty of designing domain decomposition strategies for AMR data that perform optimally across load balancing, memory efficiency, and compositing time [S1, unofficial].
