# Distributed AMR Volume Rendering with Cost-Range Decomposition

Also called: Cost-range Decomposition, Distributed Texture-Based Slicing, Kreylos et al. (2002) method, Remote Interactive AMR Rendering Framework, Remote Interactive Rendering Framework, Slicing-Based AMR Rendering, Texture-Based AMR Volume Rendering

## Overview
Distributed AMR Volume Rendering with Cost-Range Decomposition is a framework for remote, interactive volume rendering of Adaptive Mesh Refinement (AMR) data [S1, S4, unofficial]. It solves the problem of efficiently distributing heterogeneous, view-dependent AMR hierarchies across multiple processing nodes to achieve perfect load balancing [S2, unofficial]. It distinguishes itself from sibling methods like [Domain Block Decomposition](11062-amr-and-hierarchical-data-rendering.md) by prioritizing computational load balance over memory efficiency, using a view-dependent cost interval splitting strategy rather than static spatial partitioning [S2, unofficial]. The framework operates in three phases: data homogenization, cost-range decomposition, and distributed rendering with compositing [S1, S2, S4, unofficial].

## How it works
### Inputs and Outputs
*   **Input:** An AMR dataset (typically Berger-Colella format) and a current camera viewpoint.
*   **Output:** A composite image rendered across $n$ distributed nodes.

### Data Structures
1.  **Homogenized k-d Tree:**
    *   The AMR hierarchy is partitioned into blocks of constant resolution [S1, S4, unofficial].
    *   Each node in the k-d tree stores a `cost` field [S2, unofficial].
    *   **Leaf Node:** Represents a grid patch of constant resolution. `cost` is the estimated rendering cost of that patch [S2, unofficial].
    *   **Interior Node:** `cost` is the sum of the `cost` fields of its two children [S2, unofficial].
    *   Leaves are represented as intervals with width equal to their `cost` [S2, unofficial].
    *   These intervals are stacked in back-to-front rendering order [S2, unofficial].

### Steps
1.  **Resample Data:** Resample the AMR data to a node-centered format [S3, unofficial].
2.  **Homogenize Hierarchy:** Partition the AMR hierarchy into blocks of constant resolution using a k-d tree [S1, S4, unofficial].
3.  **Estimate Cost:** Calculate the estimated rendering cost for each leaf [S2, unofficial]. The cost of rendering a grid patch is roughly proportional to the number of cells it contains and to the projected size of each cell [S2, unofficial]. Formula: $Cost \propto N_{cells} \times S_{projected}$, where $N_{cells}$ is the number of cells and $S_{projected}$ is the projected size [S2, unofficial].
4.  **Decompose Cost Range:** Determine the back-to-front rendering order of the k-d tree leaves based on the current viewpoint [S2, unofficial]. Split the total cost interval into $n$ equal-sized sub-intervals, where $n$ is the number of rendering nodes [S2, unofficial]. Assign a leaf to node $i$ if at least half of its cost interval lies within sub-interval $i$ [S2, unofficial].
5.  **Distribute Data:** Distribute the resulting blocks of constant resolution among the processors according to the assignment [S1, S4, unofficial]. This may result in data duplication if grid patches from the same original grid are assigned to multiple nodes [S2, unofficial].
6.  **Render:** Each node renders its assigned blocks using either texture-based hardware-accelerated slicing [S1, S3, S4, unofficial] or software-based cell-projection rendering [S1, S4, unofficial]. If using texture-based rendering, adapt slice spacing and correct opacity to handle varying resolution levels [S3, unofficial]. During rendering, all decisions about traversing or skipping parts of the k-d tree are made during back-to-front traversal without requiring additional communication between nodes [S2, unofficial].
7.  **Composite:** Composite partial images in order of increasing node index [S2, unofficial]. Because of the cost-range assignment, no grid patch rendered by node $i$ can be occluded by any grid patch rendered by node $i-1$, and no grid patch rendered by node $i$ can occlude any grid patch rendered by node $i+1$ [S2, unofficial]. Use a binary tree compositing algorithm requiring $\lceil \log_2 n \rceil$ compositing rounds for $n$ nodes [S2, unofficial]. In each round, a node either sends its image to another node, receives an image and composites it into its own image, or is idle [S2, unofficial].

### Pseudocode
```python
def distributed_amr_rendering(AMR_data, viewpoint, num_nodes):
    # Step 1: Resample to node-centered format
    node_centered_data = resample_to_node_centered(AMR_data)

    # Step 2: Homogenize hierarchy into constant-resolution blocks using a k-d tree
    kdtree = build_homogenization_kdtree(node_centered_data)

    # Step 3: Calculate costs
    # Cost is proportional to number of cells and projected size, ignoring perspective foreshortening [S2, unofficial]
    for leaf in kdtree.leaves:
        leaf.cost = leaf.num_cells * calculate_projected_size(leaf.bounding_box, viewpoint)
    for node in kdtree.interior_nodes:
        node.cost = node.left_child.cost + node.right_child.cost

    total_cost = kdtree.root.cost
    interval_size = total_cost / num_nodes

    # Step 4 & 5: Distributed traversal and assignment
    # Each node traverses the tree back-to-front, deciding on the fly without communication [S2, unofficial]
    partial_images = {}
    for node_id in range(num_nodes):
        node_start = node_id * interval_size
        node_end = (node_id + 1) * interval_size
        node_mid = (node_start + node_end) / 2.0

        current_cost = 0.0
        leaves_to_render = []

        def traverse_back_to_front(kd_node):
            nonlocal current_cost
            if kd_node.is_leaf():
                leaf_start = current_cost
                leaf_end = current_cost + kd_node.cost
                leaf_mid = (leaf_start + leaf_end) / 2.0
                # Assign if at least half inside node's interval
                if node_start <= leaf_mid < node_end:
                    leaves_to_render.append(kd_node)
                current_cost = leaf_end
            else:
                # Standard back-to-front traversal logic
                if is_further(kd_node.right_child, viewpoint):
                    traverse_back_to_front(kd_node.right_child)
                    traverse_back_to_front(kd_node.left_child)
                else:
                    traverse_back_to_front(kd_node.left_child)
                    traverse_back_to_front(kd_node.right_child)

        traverse_back_to_front(kdtree.root)

        # Step 6: Render assigned leaves
        partial_images[node_id] = render_leaves(leaves_to_render, viewpoint)

    # Step 7: Composite
    return binary_tree_composite(partial_images, num_nodes)

def resample_to_node_centered(AMR_data):
    # Resample AMR data to node-centered format [S3, unofficial]
    return AMR_data.to_node_centered()

def build_homogenization_kdtree(node_centered_data):
    # Partition AMR hierarchy into blocks of constant resolution using a k-d tree [S1, S4, unofficial]
    return kdtree_from_amr(node_centered_data)

def calculate_projected_size(bounding_box, viewpoint):
    # Project bounding box to screen space to estimate pixel coverage [S2, unofficial]
    return bounding_box.project_area(viewpoint)

def is_further(node, viewpoint):
    # Compare distance of node's center to viewpoint [G]
    return node.center.distance_to(viewpoint) > 0.0

def render_leaves(leaves, viewpoint):
    # Render leaves using texture-based slicing or cell-projection [S1, S3, S4, unofficial]
    # Adapt slice spacing and correct opacity for varying resolutions [S3, unofficial]
    image = empty_image()
    for leaf in leaves:
        slice = leaf.generate_slice(viewpoint)
        image = alpha_blend(image, slice)
    return image

def binary_tree_composite(images, num_nodes):
    # Composite partial images in order of increasing node index [S2, unofficial]
    # Requires ceil(log2(num_nodes)) rounds
    current_images = list(images.values())
    while len(current_images) > 1:
        next_round = []
        for i in range(0, len(current_images), 2):
            if i + 1 < len(current_images):
                # Composite in order: earlier node (further back) is destination, later node (closer) is source
                combined = alpha_blend(current_images[i+1], current_images[i])
                next_round.append(combined)
            else:
                next_round.append(current_images[i])
        current_images = next_round
    return current_images[0]

def alpha_blend(src, dst):
    # Standard over compositing: dst = src * alpha + dst * (1 - alpha) [G]
    return src * src.alpha + dst * (1.0 - src.alpha)
```

### Parameters and Edge Cases
*   **Number of Nodes ($n$):** Determines the granularity of cost intervals [S2, unofficial].
*   **Cost Estimation Accuracy:** Perfect load balancing depends on accurate cost estimates [S2, unofficial].
*   **Viewpoint Changes:** Changing viewpoints alters the back-to-front order, causing grid patches to change assignment [S2, unofficial].
*   **Memory Efficiency:** Poor memory efficiency is a known pitfall [S2, unofficial]. Grid patches from the same grid may be assigned to multiple nodes, forcing each to load all associated data [S2, unofficial]. After several viewpoint changes, the entire dataset might be replicated at every node [S2, unofficial].

## Subtopics

### [Heuristic Partitioning for Texture-Based Volume Rendering](17571-heuristic-partitioning-for-texture-based-volume-rendering.md)
This method partitions Berger-Colella AMR data into homogeneous resolution regions to enable texture-based, hardware-accelerated volume rendering. It distinguishes itself from k-d tree-based or cost-range decomposition approaches by using a heuristic based on refining grid placement assumptions to minimize the total number of constant-resolution blocks. This reduction in block count is specifically beneficial for single-machine rendering scenarios where overhead from managing numerous small textures is detrimental.

## Operating characteristics
*   **Load Balancing:** Achieves perfect load balancing during rendering if cost estimates are accurate [S2, unofficial].
*   **Memory Efficiency:** Poor. Data duplication is common, especially with viewpoint changes [S2, unofficial].
*   **Compositing Time:** Comparable to Domain Block Decomposition [S2, unofficial].
*   **Communication:** Minimal during rendering (decisions made locally during traversal). Compositing requires $\lceil \log_2 n \rceil$ rounds of communication [S2, unofficial].
*   **Strengths:** Excellent load balancing, simple compositing logic due to ordered assignment [S2, unofficial].
*   **Limitations:** High memory usage due to data replication, sensitive to viewpoint changes [S2, unofficial].
*   **When to Use:** When load balancing is critical and memory bandwidth/storage is not a bottleneck [S2, unofficial].
*   **When Not to Use:** When memory efficiency is paramount or when viewpoint changes are frequent and data replication is costly [S2, unofficial].

## Background
The method was introduced by Kreylos et al. in 2002 as part of a framework for remote, interactive rendering of AMR data [S1, S4, unofficial]. It builds on earlier work by Weber et al. (2003a, 2003b) who compared various AMR partitioning strategies [S1, S4, unofficial]. The framework consists of a lightweight viewer and a renderer running on remote machines [S1, S4, unofficial]. It has been used in applications such as Virtual Director and CAVE for rendering astrophysical data sets like 'The First Star of the Universe' [S3, unofficial].
