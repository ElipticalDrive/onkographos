# Distributed AMR Volume Rendering with Cost-Range Decomposition

Also called: Cost-range Decomposition, Distributed Texture-Based Slicing, Kreylos et al. (2002) method, Remote Interactive AMR Rendering Framework, Remote Interactive Rendering Framework, Slicing-Based AMR Rendering, Texture-Based AMR Volume Rendering

## Overview
Distributed AMR Volume Rendering with Cost-Range Decomposition is a framework for remote, interactive volume rendering of Adaptive Mesh Refinement (AMR) data [S1, S4, unofficial]. It solves the problem of efficiently distributing heterogeneous, view-dependent AMR hierarchies across multiple processing nodes to achieve perfect load balancing [S2, unofficial]. It distinguishes itself from sibling methods like [Domain Block Decomposition](11062-amr-and-hierarchical-data-rendering.md) by prioritizing computational load balance over memory efficiency, using a view-dependent cost interval splitting strategy rather than static spatial partitioning [S2, unofficial].

## How it works
The method consists of three main phases: data homogenization, cost-range decomposition, and distributed rendering with compositing.

### Inputs and Outputs
*   **Input:** An AMR dataset (typically Berger-Colella format) and a current camera viewpoint.
*   **Output:** A composite image rendered across $n$ distributed nodes.

### Data Structures
1.  **Homogenized k-d Tree:**
    *   The AMR hierarchy is partitioned into blocks of constant resolution.
    *   Each node in the k-d tree stores a `cost` field.
    *   **Leaf Node:** Represents a grid patch of constant resolution. `cost` is the estimated rendering cost of that patch.
    *   **Interior Node:** `cost` is the sum of the `cost` fields of its two children.
    *   **Traversal Order:** The tree is traversed back-to-front relative to the current viewpoint to determine the rendering order of leaves [S2, unofficial].

2.  **Cost Intervals (Logical):**
    *   Leaves are represented as intervals with width equal to their `cost`.
    *   These intervals are stacked in back-to-front rendering order.
    *   The total interval spans from $0$ to $C_{total}$, where $C_{total}$ is the sum of all leaf costs [S2, unofficial].

### Steps

1.  **Resample Data:**
    *   Resample the AMR data to a node-centered format [S3, unofficial].

2.  **Homogenize Hierarchy:**
    *   Partition the AMR hierarchy into blocks of constant resolution using a k-d tree [S1, S4, unofficial].
    *   For each leaf in the k-d tree, calculate the estimated rendering cost [S2, unofficial].
    *   For each interior node, set its cost to the sum of its children's costs [S2, unofficial].

3.  **Estimate Cost:**
    *   The cost of rendering a grid patch is roughly proportional to the number of cells it contains and to the projected size of each cell [S2, unofficial].
    *   Formula: $Cost \propto N_{cells} \times S_{projected}$, where $N_{cells}$ is the number of cells and $S_{projected}$ is the projected size [S2, unofficial].

4.  **Decompose Cost Range:**
    *   Determine the back-to-front rendering order of the k-d tree leaves based on the current viewpoint [S2, unofficial].
    *   Split the total cost interval $[0, C_{total}]$ into $n$ equal-sized sub-intervals, where $n$ is the number of rendering nodes.
    *   Sub-interval $i$ (for node $i$, $0 \le i < n$) covers the range $[\frac{i \cdot C_{total}}{n}, \frac{(i+1) \cdot C_{total}}{n})$ [S2, unofficial].
    *   Assign a leaf to node $i$ if at least half of its cost interval lies within sub-interval $i$ [S2, unofficial].

5.  **Distribute Data:**
    *   Distribute the resulting blocks of constant resolution among the processors according to the assignment [S1, S4, unofficial].
    *   Note: This may result in data duplication if grid patches from the same original grid are assigned to multiple nodes [S2, unofficial].

6.  **Render:**
    *   Each node renders its assigned blocks using either:
        *   Texture-based hardware-accelerated slicing [S1, S3, S4, unofficial].
        *   Software-based cell-projection rendering [S1, S4, unofficial].
    *   If using texture-based rendering:
        *   Adapt slice spacing and correct opacity to handle varying resolution levels [S3, unofficial].
        *   Perform optimized texture packing [S3, unofficial].
    *   During rendering, all decisions about traversing or skipping parts of the k-d tree are made during back-to-front traversal without requiring additional communication between nodes [S2, unofficial].

7.  **Composite:**
    *   Composite partial images in order of increasing node index [S2, unofficial].
    *   Because of the cost-range assignment, no grid patch rendered by node $i$ can be occluded by any grid patch rendered by node $i-1$, and no grid patch rendered by node $i$ can occlude any grid patch rendered by node $i+1$ [S2, unofficial].
    *   Use a binary tree compositing algorithm requiring $\lceil \log_2 n \rceil$ compositing rounds for $n$ nodes [S2, unofficial].
    *   In each round, a node either sends its image to another node, receives an image and composites it into its own image, or is idle [S2, unofficial].

### Pseudocode

```python
def distributed_amr_rendering(AMR_data, viewpoint, num_nodes):
    # Step 1: Resample
    node_centered_data = resample_to_node_centered(AMR_data)
    
    # Step 2: Homogenize and Build k-d Tree
    # Partition AMR hierarchy into constant resolution blocks
    kdtree = build_homogenization_kdtree(node_centered_data)
    
    # Step 3: Estimate Costs
    # Calculate cost for each leaf and propagate up
    for leaf in kdtree.leaves:
        # Cost proportional to number of cells and projected size
        leaf.cost = estimate_patch_cost(leaf, viewpoint)
    
    for node in kdtree.interior_nodes:
        node.cost = node.left_child.cost + node.right_child.cost
    
    total_cost = kdtree.root.cost
    
    # Step 4: Determine Assignment via Cost-Range Decomposition
    # Split total cost into n equal intervals
    interval_size = total_cost / num_nodes
    
    assignments = {} # Map node_id -> list of leaves
    
    # Get leaves in back-to-front order
    leaves_in_order = get_back_to_front_leaves(kdtree, viewpoint)
    
    current_cost_boundary = 0.0
    current_node_id = 0
    
    for leaf in leaves_in_order:
        # Determine which interval this leaf falls into
        # Leaf covers [current_cost_boundary, current_cost_boundary + leaf.cost]
        leaf_start = current_cost_boundary
        leaf_end = current_cost_boundary + leaf.cost
        leaf_midpoint = (leaf_start + leaf_end) / 2.0
        
        # Calculate which node's interval contains the midpoint
        # Node i interval: [i * interval_size, (i+1) * interval_size)
        assigned_node = int(leaf_midpoint / interval_size)
        
        # Clamp to valid node range
        if assigned_node >= num_nodes:
            assigned_node = num_nodes - 1
            
        if assigned_node not in assignments:
            assignments[assigned_node] = []
        assignments[assigned_node].append(leaf)
        
        current_cost_boundary = leaf_end
        
    # Step 5: Distribute Data
    # Send data to nodes based on assignments
    # Note: This may cause data duplication
    for node_id, leaves in assignments.items():
        send_data_to_node(node_id, leaves)
        
    # Step 6: Render
    # Each node renders its leaves
    partial_images = {}
    for node_id in range(num_nodes):
        partial_images[node_id] = render_leaves(assignments.get(node_id, []))
        
    # Step 7: Composite
    # Binary tree compositing
    composite_image = binary_tree_composite(partial_images, num_nodes)
    
    return composite_image

def estimate_patch_cost(leaf, viewpoint):
    # Cost proportional to number of cells and projected size
    # Ignoring perspective foreshortening for simplicity as per source
    num_cells = leaf.num_cells
    projected_size = calculate_projected_size(leaf.bounding_box, viewpoint)
    return num_cells * projected_size

def get_back_to_front_leaves(kdtree, viewpoint):
    # Traverse k-d tree back-to-front relative to viewpoint
    leaves = []
    def traverse(node):
        if node.is_leaf():
            leaves.append(node)
        else:
            # Determine which child is closer to viewpoint
            # Assume standard back-to-front logic for volume rendering
            if is_further(node.right_child, viewpoint):
                traverse(node.right_child)
                traverse(node.left_child)
            else:
                traverse(node.left_child)
                traverse(node.right_child)
    traverse(kdtree.root)
    return leaves

def binary_tree_composite(partial_images, num_nodes):
    # Binary tree compositing algorithm
    # Requires ceil(log2(num_nodes)) rounds
    images = list(partial_images.values())
    while len(images) > 1:
        next_round = []
        for i in range(0, len(images), 2):
            if i + 1 < len(images):
                # Composite image i and i+1
                # Order matters: earlier nodes render further back?
                # Source says composite in order of increasing node index
                # Node i renders patches that are occluded by node i-1?
                # Actually, source says: "no grid patch G rendered by node i 
                # can be occluded by any grid patch rendered by node i-1"
                # This implies node i is in front of node i-1?
                # Let's assume standard alpha blending: src over dst
                # If node i is in front, it should be the source?
                # Or if node i-1 is further back, it is the destination?
                # Standard compositing: dst = src * alpha + dst * (1-alpha)
                # If node i is in front, it is the source.
                combined = alpha_blend(images[i+1], images[i]) 
                next_round.append(combined)
            else:
                next_round.append(images[i])
        images = next_round
    return images[0]
```

### Parameters and Edge Cases
*   **Number of Nodes ($n$):** Determines the granularity of cost intervals.
*   **Cost Estimation Accuracy:** Perfect load balancing depends on accurate cost estimates [S2, unofficial].
*   **Viewpoint Changes:** Changing viewpoints alters the back-to-front order, causing grid patches to change assignment. This forces data replication between nodes [S2, unofficial].
*   **Memory Efficiency:** Poor memory efficiency is a known pitfall. Grid patches from the same grid may be assigned to multiple nodes, forcing each to load all associated data. After several viewpoint changes, the entire dataset might be replicated at every node [S2, unofficial].

## Subtopics

### [Heuristic Partitioning for Texture-Based Volume Rendering](17571-heuristic-partitioning-for-texture-based-volume-rendering.md)
This method partitions Berger-Colella AMR data into homogeneous resolution regions to enable texture-based, hardware-accelerated volume rendering. It distinguishes itself from k-d tree-based or cost-range decomposition approaches by using a heuristic based on refining grid placement assumptions to minimize the total number of constant-resolution blocks. This reduction in block count is specifically beneficial for single-machine rendering scenarios where overhead from managing numerous small textures is detrimental.

## Operating characteristics
*   **Load Balancing:** Achieves perfect load balancing during rendering if cost estimates are accurate [S2, unofficial].
*   **Memory Efficiency:** Poor. Data duplication is common, especially with viewpoint changes [S2, unofficial].
*   **Compositing Time:** Comparable to Domain Block Decomposition [S2, unofficial].
*   **Communication:** Minimal during rendering (decisions made locally during traversal). Compositing requires $\lceil \log_2 n \rceil$ rounds of communication [S2, unofficial].
*   **Strengths:** Excellent load balancing, simple compositing logic due to ordered assignment [S2, unofficial].
*   **Limitations:** High memory usage due to data replication, sensitive to viewpoint changes [S2, unofficial].
*   **When to Use:** When load balancing is critical and memory bandwidth/storage is not a bottleneck [S2, unofficial].
*   **When Not to Use:** When memory efficiency is paramount or when viewpoint changes are frequent and data replication is costly [S2, unofficial].

## Background
The method was introduced by Kreylos et al. in 2002 as part of a framework for remote, interactive rendering of AMR data [S1, S4, unofficial]. It builds on earlier work by Weber et al. (2003a, 2003b) who compared various AMR partitioning strategies [S1, S4, unofficial]. The framework consists of a lightweight viewer and a renderer running on remote machines [S1, S4, unofficial]. It has been used in applications such as Virtual Director and CAVE for rendering astrophysical data sets like 'The First Star of the Universe' [S3, unofficial].
