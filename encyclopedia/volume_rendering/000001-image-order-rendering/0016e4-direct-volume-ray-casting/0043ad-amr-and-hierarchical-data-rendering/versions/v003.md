# AMR and Hierarchical Data Rendering

Also called: AlloVolume CUDA AMR Ray-casting Renderer, Texture-Based AMR Volume Rendering, Hardware-Accelerated AMR Rendering

## Overview
AMR and Hierarchical Data Rendering encompasses techniques for visualizing datasets with non-uniform spatial resolution, such as those generated by adaptive mesh refinement simulations [S2, S3, unofficial]. It solves the computational and memory overhead of uniform sampling by leveraging hierarchical spatial subdivision to group data into homogeneous resolution regions, enabling optimized texture packing, adaptive sampling, and hardware-accelerated compositing [S2, S3, unofficial]. It is distinguished from fixed-resolution methods by its explicit use of AMR grid placement information and hierarchical structures to drive data organization and traversal [S2, S3, unofficial].

## How it works
**Inputs and outputs**: The method takes an AMR dataset, camera/view parameters, a transfer function, and rendering configuration as inputs, and produces a rendered image or frame buffer as output [S1, S2, S3, unofficial].

**Data structures**: The domain is subdivided using a kD-tree to identify homogeneous resolution regions [S2, S3, unofficial]. AMR data is resampled into node-centered arrays [S2, unofficial]. For hardware rendering, uniform data blocks are organized as stacks of axis-aligned 2D textures [S3, unofficial]. Transfer functions are stored as layered configurations with domain bounds and scaling parameters [S1, unofficial].

**Numbered steps**:
1. Resample the AMR dataset to a node-centered format [S2, unofficial].
2. Subdivide the domain into homogeneous resolution regions using a kD-tree, minimizing the number of blocks by utilizing AMR grid placement algorithm information [S2, unofficial].
3. For hardware-accelerated rendering, upload uniform data blocks as stacks of axis-aligned 2D textures [S3, unofficial]. For ray-casting approaches, use the kD-tree to perform fast ray-block intersection [S1, unofficial].
4. Render the textures or slices back-to-front into the frame buffer using the OpenGL compositing operator, or perform ray-marching with adaptive step sizes (e.g., Adaptive Runge-Kutta-Fehlberg method) [S1, S3, unofficial].
5. Adapt slice spacing and correct opacity to account for varying resolution levels across the hierarchy [S2, unofficial].
6. Apply the transfer function to map scalar values to color and opacity, then apply final RGB levels to the output [S1, unofficial].

**Formulas**: Opacity is corrected for step size and resolution variation to approximate continuous attenuation [S2, unofficial]. Final output color is mapped using RGB levels parameters: $\mathbf{C}_{out} = \text{clamp}\left(\frac{\mathbf{C}_{in} - \text{min}}{\text{max} - \text{min}}\right)^{\text{pow}}$, where $\mathbf{C}_{in}$ is the pre-composited color, and min, max, and pow are user-defined bounds and exponent [S1, unofficial].

**Parameters**: Default resolution is 960×640 [S1, unofficial]. Default transfer function uses Gaussian ticks with domain [1e-3, 1e8], log scale, and 16 layers [S1, unofficial]. Default blending coefficient is 1e9 [S1, unofficial]. Default background color is black with alpha 1 [S1, unofficial]. Default lens focal distance is 1e10 [S1, unofficial].

**Edge cases and pitfalls**: Hardware compositing into limited frame buffer precision (typically 8 bits per pixel and color channel) degrades image quality when many texture slices are composited [S3, unofficial]. Switching to 3D textures or view-orthogonal slices yields only marginal quality improvements [S3, unofficial]. Varying resolution levels require careful opacity correction and slice spacing adaptation to prevent visual artifacts [S2, unofficial].

## Subtopics

### [Multiresolution Volume Rendering](3541-multiresolution-volume-rendering.md)
Multiresolution Volume Rendering utilizes hierarchical data decompositions (such as wavelets or Laplacian pyramids) to perform adaptive integration and early termination along rays. It solves the problem of high computational cost in large volume datasets by allowing the renderer to sample at lower resolutions where accuracy requirements are relaxed or occlusion is high, thereby reducing the number of samples needed. It is distinguished from its siblings by its explicit use of mathematical multiresolution transforms to drive the sampling step size and data retrieval, rather than spatial partitioning structures like clusters or AMR grids.

### [Cluster Hierarchy-based Volume Rendering](10972-cluster-hierarchy-based-volume-rendering.md)
Cluster Hierarchy-based Volume Rendering is a method for the interactive visual exploration of multi-variate volume data by mapping hierarchical clusters of data points to transfer function parameters (color, opacity, size) for direct volume rendering. It solves the problem of exploring high-dimensional feature spaces in volumetric datasets by allowing users to interactively define, modify, and filter clusters via a cluster tree widget and parallel coordinates widget, which are then immediately reflected in the 3D visualization. It sets itself apart from standard direct volume rendering by decoupling the classification logic from the rendering loop, performing it on the CPU based on user interaction with a hierarchical structure, while retaining the core ray-casting pipeline for rendering.

### [In-Core Volume Rendering](11164-in-core-volume-rendering.md)
In-core volume rendering, specifically as implemented in the **Srend** system, is a method for visualizing Computational Fluid Dynamics (CFD) simulations using Cartesian grids by embedding the rendering code directly within the simulation application. It solves the problem of high data I/O overhead and latency in large-scale parallel simulations by performing rendering in-core during the simulation run, eliminating the need for external visualization tools or post-processing steps. Unlike general-purpose in-situ renderers that often employ complex load-balancing or supervisory mechanisms, Srend relies on a simple time-partitioning strategy where every simulation process renders its local data, followed by space-partitioned compositing via a user-defined "rendering tree". This approach exploits the embarrassingly parallel nature of ray casting and the associativity of pre-multiplied alpha compositing to achieve scalable, low-overhead visualization.

### Texture-Based AMR Volume Rendering
**Definition**: A texture/slicing-based volume rendering technique for AMR data that resamples to node-centered data, subdivides into homogeneous resolution regions using a kD-tree, and optimizes texture packing [S2, unofficial].
**Steps**:
1. Resample AMR data to node-centered format [S2, unofficial].
2. Subdivide data into homogeneous resolution regions using a kD-tree, minimizing the number of blocks using AMR grid placement algorithm information [S2, unofficial].
3. Perform texture/slicing-based volume rendering with optimized texture packing [S2, unofficial].
4. Adapt slice spacing and correct opacity to handle varying resolution levels [S2, unofficial].
**Usage**: Used in Virtual Director and CAVE for rendering 'The First Star of the Universe' astrophysical data set [S2, unofficial].

## Operating characteristics
Hardware acceleration significantly reduces rendering time but trades off image quality due to frame buffer precision limits [S3, unofficial]. kD-tree subdivision minimizes block count and optimizes texture packing for memory bandwidth [S2, unofficial]. Adaptive integration methods (e.g., Runge-Kutta-Fehlberg) improve high-definition rendering quality at the cost of increased per-ray computation [S1, unofficial].

## Background
Early work by Kähler and Hege (2001/2002) introduced texture-based AMR volume rendering, resampling data to node-centered formats and using kD-trees for homogeneous subdivision [S2, unofficial]. Park et al. (2002) proposed splatting-based rendering using kD-tree and octree domain subdivision [S2, unofficial]. Kreylos et al. (2002) developed direct volume rendering of AMR data using homogenization via kD-trees and distributed rendering with texture-based slicing [S2, unofficial]. These methods were applied to large-scale astrophysical simulations, such as "The First Star of the Universe," which was aired on the Discovery Channel [S2, unofficial]. AlloVolume later extended the paradigm with CUDA-based GPU acceleration, full-surround stereo support, and adaptive Runge-Kutta-Fehlberg integration for high-definition rendering [S1, unofficial].
