# Cluster Hierarchy-based Volume Rendering

Also called: Cluster Tree Widget Rendering, Interactive Visual Exploration of Multi-variate Volume Data

## Overview
Cluster Hierarchy-based Volume Rendering is a method for the interactive visual exploration of multi-variate volume data by mapping hierarchical clusters of data points to transfer function parameters (color, opacity, size) for direct volume rendering [S1, unofficial]. It solves the problem of exploring high-dimensional feature spaces in volumetric datasets by allowing users to interactively define, modify, and filter clusters via a cluster tree widget and parallel coordinates widget, which are then immediately reflected in the 3D visualization [S1, unofficial]. It sets itself apart from standard direct volume rendering by decoupling the classification logic from the rendering loop, performing it on the CPU based on user interaction with a hierarchical structure, while retaining the core ray-casting pipeline for rendering [S1, unofficial].

## How it works
The method extends the standard direct volume ray casting pipeline by introducing a hierarchical clustering stage that drives the transfer function and masking.

**Inputs and Outputs**
*   **Input:** A multi-variate volume dataset where each voxel $\mathbf{v}$ has a feature vector $\mathbf{f} \in \mathbb{R}^d$ (e.g., scalar values, derivatives, physical properties).
*   **Output:** A rendered image where voxels are colored and composited based on their cluster membership and user-defined cluster properties.

**Data Structures**
1.  **Cluster Hierarchy:** A tree structure where each node represents a cluster of data points. Nodes have properties including:
    *   `color`: Default RGB color assigned to the cluster.
    *   `opacity`: Default opacity assigned to the cluster.
    *   `size`: A scalar value controlling the effective density or inclusion threshold of the cluster, modifiable by user sliders.
    *   `children`: List of child nodes (for hierarchical splits).
    *   `mask`: A binary indicator or spatial mask derived from the clustering algorithm and user interaction.
2.  **Parallel Coordinates Widget:** A 2D representation of the multi-variate feature space used for brushing (selecting intervals in feature dimensions) to refine cluster membership.
3.  **Transfer Function:** Mapped from cluster properties. Unlike standard TFs defined per scalar value, this is defined per cluster.

**Numbered Steps**

1.  **Clustering Initialization:**
    *   If pre-clustering exists, construct the cluster hierarchy using an automatic clustering algorithm [S1, unofficial].
    *   If no pre-clustering exists, place all data points into a single root cluster [S1, unofficial].

2.  **User Interaction (CPU-side):**
    *   The user interacts with the **Cluster Tree Widget** to select nodes and adjust `size` parameters using density sliders. Adjusting the size of a cluster effectively filters voxels within that cluster based on density thresholds [S1, unofficial].
    *   The user interacts with the **Parallel Coordinates Widget** to brush specific intervals in the feature space. Data points (voxels) whose feature vectors fall within the selected intervals are marked with a mask value of 1; others are marked with 0 [S1, unofficial].
    *   The mask is combined with the cluster selection. A voxel is active only if it belongs to a selected cluster AND its mask value is 1 [S1, unofficial].

3.  **Reclustering (CPU-side, optional):**
    *   If the user splits or merges nodes in the cluster tree, perform reclustering operations [S1, unofficial].
    *   This operation updates the hierarchy and mask assignments. It is performed on the CPU and typically takes no more than half a second on modern hardware [S1, unofficial].

4.  **Transfer Function Assignment:**
    *   Assign default color and opacity to each cluster based on the clustering output or user customization [S1, unofficial].
    *   Apply color mapping based on physical properties if desired (e.g., blue for fully ionized gas, red for unionized gas) to visualize trends [S1, unofficial].

5.  **Rendering (GPU-side, Direct Volume Ray Casting):**
    *   **Ray Generation:** Cast rays from the camera through each pixel.
    *   **Sampling and Interpolation:**
        *   Sample the volume at positions along the ray.
        *   Retrieve the feature vector $\mathbf{f}$ for the current sample position.
        *   Determine the cluster membership of $\mathbf{f}$ using the pre-computed hierarchy/mask.
        *   **Interpolation:** Use nearest-neighbor interpolation for the feature values or cluster assignment [S1, unofficial].
    *   **Classification:**
        *   If the voxel's mask value is 0, set opacity $\alpha = 0$ (fully transparent/hidden) [S1, unofficial].
        *   If the mask value is 1, retrieve the cluster's assigned color $C$ and opacity $\alpha$ [S1, unofficial].
        *   Note: Pre-classification (computing color/opacity for all voxels on CPU) is rejected due to performance costs; classification is done on-the-fly or via the mask during rendering [S1, unofficial].
    *   **Compositing:**
        *   Perform front-to-back compositing using the Beer-Lambert law:
            $$ C_{out} = C_{in} + C_i \cdot \alpha_i \cdot (1 - \alpha_{in}) $$
            $$ \alpha_{out} = \alpha_{in} + \alpha_i \cdot (1 - \alpha_{in}) $$
        *   Where $C_i$ and $\alpha_i$ are the color and opacity of the current sample derived from its cluster [S1, unofficial].
    *   **Illumination (Optional):**
        *   Use precomputed surface normals for illumination. On-the-fly normal computation is rejected due to significant performance degradation [S1, unofficial].

**Pseudocode**

```python
# Pseudocode for the rendering loop, assuming cluster hierarchy and masks are pre-computed on CPU
# and transferred to GPU textures or buffers.

def render_cluster_hierarchy_volume(ray_origin, ray_direction, volume_texture, cluster_mask_texture, cluster_tf_texture):
    """
    ray_origin: vec3
    ray_direction: vec3
    volume_texture: 3D texture storing feature vectors or primary scalar field
    cluster_mask_texture: 3D texture storing mask values (0 or 1) for each voxel
    cluster_tf_texture: 3D texture or buffer storing cluster color/opacity for each voxel
    """
    # Initialize compositing variables
    accumulated_color = vec3(0.0)
    accumulated_opacity = 0.0
    
    # Ray casting parameters
    step_size = 0.5 # Example step size, adjusted based on resolution
    max_steps = 1000
    
    for i in range(max_steps):
        # 1. Sample position
        t = i * step_size
        sample_pos = ray_origin + t * ray_direction
        
        # Check if sample is within volume bounds
        if not is_inside_volume(sample_pos):
            break
            
        # 2. Retrieve data
        # Get the mask value for this voxel
        mask = sample_3d_texture(cluster_mask_texture, sample_pos)
        
        # If mask is 0, the voxel is hidden (fully transparent)
        if mask == 0.0:
            continue
            
        # Get the cluster transfer function parameters (color, opacity)
        # In this implementation, TF is mapped per-voxel based on cluster membership
        tf_params = sample_3d_texture(cluster_tf_texture, sample_pos)
        color = tf_params.rgb
        opacity = tf_params.a
        
        # 3. Compositing (Front-to-Back)
        # Beer-Lambert law
        contribution = color * opacity * (1.0 - accumulated_opacity)
        accumulated_color += contribution
        accumulated_opacity += opacity * (1.0 - accumulated_opacity)
        
        # 4. Termination
        if accumulated_opacity > 0.99:
            break
            
    return accumulated_color
```

**Parameters**
*   **Screen Resolution:** 1680x1050 pixels [S1, unofficial].
*   **Hardware:** nVIDIA GTX260 graphics card [S1, unofficial].
*   **Performance Target:** 20-30 frames per second [S1, unofficial].
*   **Reclustering Time:** < 0.5 seconds on modern hardware [S1, unofficial].

**Edge Cases and Pitfalls**
*   **Aliasing:** Post-classification with nearest-neighbor interpolation can cause aliasing artifacts at cluster boundaries [S1, unofficial].
*   **Performance:** Pre-classification (computing color/opacity for all voxels on CPU and transmitting to GPU) inhibits interactive frame rates and offers only marginal quality gains [S1, unofficial].
*   **Normals:** On-the-fly surface normal computation significantly slows down rendering; normals must be precomputed [S1, unofficial].
*   **Empty Clusters:** Clusters containing only background information (e.g., the "red cluster" in the Bonsai tree example) should be rendered with zero opacity to avoid visual clutter [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The rendering time per frame depends on the dataset resolution, zoom level, and sampling rate, achieving 20-30 FPS on a GTX260 for the tested datasets [S1, unofficial]. Reclustering operations (CPU-side) take < 0.5 seconds [S1, unofficial].
*   **Memory Complexity:** Requires storing the volume data, cluster hierarchy, and mask textures in GPU memory. The method avoids transmitting pre-classified color/opacity data for all voxels, saving bandwidth compared to pre-classification approaches [S1, unofficial].
*   **Strengths:** Interactive exploration of multi-variate data; intuitive interface via cluster tree and parallel coordinates; immediate visual feedback; handles high-dimensional feature spaces (up to 11 dimensions demonstrated) [S1, unofficial].
*   **Limitations:** Aliasing artifacts at cluster boundaries due to nearest-neighbor interpolation; reliance on precomputed normals; performance limited by ray casting on older hardware (GTX260) [S1, unofficial].
*   **When to use:** When exploring multi-variate volumetric data where users need to interactively define and modify feature-based clusters for visualization.
*   **When not to use:** When high-fidelity anti-aliasing at cluster boundaries is critical without post-processing; when on-the-fly illumination is required without precomputed normals; when hardware is significantly older than the tested GTX260.

## Background
The method was presented by Dobrev et al. in the paper "A Cluster Hierarchy-based Volume Rendering Approach for Interactive Visual Exploration of Multi-variate Volume Data" [S1, unofficial]. It builds on ideas from Daniels II et al. [DANS10] and Park et al. [PBL*04] regarding multi-variate field exploration. The approach was implemented in C++ using QT, OpenGL, and GLSL [S1, unofficial]. It was applied to several datasets including the Bonsai tree (multi-variate with derivatives), ionization front instability simulation (10 scalar fields), medical MRI datasets (256x256x176), tornado flow field (256^3), and a white dwarf/black hole simulation (11-dimensional feature space) [S1, unofficial].
