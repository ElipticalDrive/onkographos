# Distributed AMR Volume Rendering with Cost-Range Decomposition

Also called: Cost-range Decomposition, Distributed Texture-Based Slicing

## Overview
A domain decomposition strategy for parallel volume rendering of Adaptive Mesh Refinement (AMR) data that assigns parts of a dataset to processing nodes based on estimated rendering cost to achieve perfect load balancing [S1, S2, unofficial]. It differs from sibling methods like Domain Block Decomposition by prioritizing computational balance over memory efficiency, ensuring that each node processes an equal share of the total rendering workload regardless of the geometric complexity of the assigned region [S1, unofficial].

## How it works
The method operates on a view-independent kD-tree generated during a grid homogenization phase [S1, S2, unofficial]. It decomposes the rendering task by mapping the back-to-front traversal order of the kD-tree leaves into a 1D cost interval, which is then partitioned among rendering nodes [S1, unofficial].

### Inputs and Outputs
*   **Input**: An AMR dataset, a view-independent kD-tree representing the homogenized grid structure, the number of rendering nodes $n$, and a transfer function.
*   **Output**: A composite image generated by combining partial images from $n$ nodes.

### Data Structures
**kD-Tree Node Layout**:
Each node in the homogenizing kD-tree stores a `cost` field [S1, unofficial].
*   **Leaf Node**: `cost` is the estimated rendering cost of the grid patch it represents.
*   **Interior Node**: `cost` is the sum of the `cost` fields of its two children [S1, unofficial].

**Cost Interval**:
An implicit 1D interval $[0, C_{total}]$, where $C_{total}$ is the cost of the root node. The interval is conceptually divided into sub-intervals corresponding to the rendering nodes [S1, unofficial].

### Parameters
*   $n$: Number of rendering nodes.
*   Cost estimation factors: Proportional to the number of cells in a grid patch and the projected size of each cell [S1, unofficial].

### Steps
1.  **Grid Homogenization**: Construct a view-independent kD-tree for the AMR data. During this process, calculate and store the rendering cost for every node [S1, S2, unofficial].
    *   For a leaf node representing a grid patch, the cost is estimated based on the number of cells and their projected size [S1, unofficial].
    *   For an interior node, the cost is the sum of its children's costs [S1, unofficial].
2.  **Interval Partitioning**: Calculate the total cost $C_{total}$ from the root node. Divide the interval $[0, C_{total}]$ into $n$ equal-sized sub-intervals. The boundaries are at $i \cdot \frac{C_{total}}{n}$ for $i = 0 \dots n$ [S1, unofficial].
3.  **Node Assignment (Implicit)**: Leaves are assigned to nodes based on their position in the back-to-front traversal order. A leaf is assigned to node $k$ if it is at least half inside the $k$-th sub-interval [S1, unofficial].
    *   This assignment is not stored explicitly as a map. Instead, during the rendering traversal, each node determines locally whether a leaf belongs to it by checking if the leaf's cumulative cost range overlaps sufficiently with its assigned sub-interval [S1, unofficial].
4.  **Distributed Rendering**: Each node performs volume rendering (e.g., using texture-based slicing) for the grid patches assigned to it [S1, S2, unofficial].
    *   Nodes traverse the kD-tree in back-to-front order.
    *   Nodes skip or traverse subtrees based on the cost-range logic without communicating with other nodes during traversal [S1, unofficial].
5.  **Compositing**: Partial images are composited in order of increasing node index [S1, unofficial].
    *   Because of the cost-range ordering, no grid patch rendered by node $i$ can be occluded by any grid patch rendered by node $i-1$, nor can it occlude any grid patch rendered by node $i+1$ [S1, unofficial].
    *   A binary tree compositing algorithm is used, requiring $\lceil \log_2 n \rceil$ compositing rounds [S1, unofficial].
    *   In each round, a node either sends its image, receives an image and composites it, or is idle [S1, unofficial].

### Pseudocode

```python
# Assumptions:
# - kD_tree: The homogenized kD-tree with pre-computed 'cost' fields.
# - n: Number of rendering nodes.
# - node_id: The unique ID of the current rendering node (0 to n-1).
# - C_total: Total cost of the root node.
# - render_patch(patch): Renders a single grid patch and returns a partial image.

def distributed_cost_range_rendering(kD_tree, n, node_id):
    # 1. Determine the cost interval boundaries for this node
    # The total interval is [0, C_total].
    # Node i is responsible for the sub-interval [i * C_total/n, (i+1) * C_total/n].
    # However, the assignment rule is: assign leaf to node k if it is at least half inside sub-interval k.
    
    interval_width = C_total / n
    my_start = node_id * interval_width
    my_end = (node_id + 1) * interval_width
    
    # The leaf is assigned to this node if its cumulative cost range overlaps 
    # with [my_start, my_end] by at least 50% of the leaf's cost.
    # This check is performed during traversal.

    # 2. Traverse the kD-tree in back-to-front order
    # The traversal order is determined by the view-dependent sorting of leaves.
    # Since the tree is view-independent, we assume a standard back-to-front 
    # traversal logic where children are visited based on depth/distance.
    
    partial_image = render_empty_image()
    
    # Helper function for recursive traversal
    def traverse(node, cumulative_cost_so_far):
        nonlocal partial_image
        
        # Base case: Leaf node
        if node.is_leaf():
            leaf_cost = node.cost
            # The leaf's cost interval is [cumulative_cost_so_far, cumulative_cost_so_far + leaf_cost]
            leaf_start = cumulative_cost_so_far
            leaf_end = cumulative_cost_so_far + leaf_cost
            
            # Check if this leaf is assigned to this node
            # Condition: The intersection of [leaf_start, leaf_end] and [my_start, my_end]
            # must be at least half the length of the leaf's cost interval.
            intersection_start = max(leaf_start, my_start)
            intersection_end = min(leaf_end, my_end)
            
            if intersection_start < intersection_end:
                intersection_length = intersection_end - intersection_start
                if intersection_length >= leaf_cost / 2.0:
                    # Assign to this node
                    patch_image = render_patch(node.grid_patch)
                    partial_image = composite_images(partial_image, patch_image)
            return

        # Recursive case: Interior node
        # Visit children in back-to-front order.
        # Note: The exact order of children depends on the kD-tree structure and view.
        # We assume a standard traversal where we visit the "front" child first.
        
        # Calculate cost ranges for children to determine traversal order if needed,
        # but primarily we just need to pass the cumulative cost.
        
        # Visit left child (assuming left is front, or determined by view)
        # In a generic kD-tree for AMR, the "front" child is the one closer to the camera.
        # For simplicity in this abstract, we assume a fixed back-to-front order 
        # defined by the homogenization process.
        
        # Let's assume child 0 is front, child 1 is back.
        traverse(node.children[0], cumulative_cost_so_far)
        traverse(node.children[1], cumulative_cost_so_far + node.children[0].cost)

    # Start traversal from root
    # The root's cumulative cost is 0.
    traverse(kD_tree.root, 0.0)
    
    return partial_image

def composite_partial_images(partial_images, n):
    """
    Composite partial images from n nodes using a binary tree algorithm.
    partial_images: List of images from each node, indexed by node_id.
    """
    # Binary tree compositing
    # Round 1: Node 0 composites with Node 1, Node 2 with Node 3, etc.
    # Round 2: Winners composite with next winners.
    
    current_images = list(partial_images)
    active_nodes = list(range(n))
    
    while len(active_nodes) > 1:
        next_active_nodes = []
        for i in range(0, len(active_nodes), 2):
            if i + 1 < len(active_nodes):
                # Composite image from active_nodes[i] and active_nodes[i+1]
                # Order matters: front-to-back or back-to-front?
                # Since node indices are ordered by rendering order (back-to-front cost),
                # and compositing is done in increasing node index, we assume 
                # the result of lower index is "back" and higher index is "front"?
                # Actually, the source says "composite all partial images in order of 
                # (increasing) node index". And "no grid patch G rendered by node i 
                # can be occluded by any grid patch rendered by node i-1".
                # This implies node i-1 is "behind" node i.
                # So when compositing, we composite (i+1) onto (i) or vice versa?
                # Standard front-to-back compositing:
                # If node i is behind node i+1, we composite node i+1's image 
                # into node i's image.
                
                combined = composite_images(current_images[active_nodes[i]], 
                                            current_images[active_nodes[i+1]])
                current_images[active_nodes[i]] = combined
                next_active_nodes.append(active_nodes[i])
            else:
                # Odd node out, passes through
                next_active_nodes.append(active_nodes[i])
        active_nodes = next_active_nodes
        
    return current_images[0]
```

### Edge Cases and Pitfalls
*   **Memory Efficiency**: The method suffers from poor memory efficiency [S1, unofficial]. Grid patches belonging to the same AMR grid may be assigned to multiple rendering nodes, forcing each node to load all data associated with that grid [S1, unofficial].
*   **Viewpoint Changes**: Changing the viewpoint alters the rendering order, causing grid patches to change assignment between nodes [S1, unofficial]. This forces data replication between nodes. After several viewpoint changes, the entire dataset might be replicated at every node [S1, unofficial].
*   **Cost Estimation Accuracy**: The strategy relies on accurate cost estimates for perfect load balancing. If estimates are inaccurate, load imbalance may occur [S1, unofficial].

## Operating characteristics
*   **Load Balancing**: Achieves perfect load balancing if cost estimates are accurate [S1, unofficial].
*   **Memory Usage**: High memory usage due to potential data replication across nodes [S1, unofficial].
*   **Compositing Time**: Comparable to Domain Block Decomposition [S1, unofficial]. Requires $\lceil \log_2 n \rceil$ compositing rounds [S1, unofficial].
*   **Communication**: Minimal communication during traversal; communication is limited to the compositing phase [S1, unofficial].
*   **Strengths**: Excellent load balancing for complex AMR datasets where computational cost varies significantly across regions [S1, unofficial].
*   **Limitations**: Poor memory efficiency and high data replication overhead during interactive viewpoint changes [S1, unofficial].
*   **When to Use**: When load balancing is the primary concern and memory bandwidth/storage is not a bottleneck [S1, unofficial].
*   **When Not to Use**: When memory efficiency is critical or when frequent viewpoint changes are expected in an interactive setting [S1, unofficial].

## Background
The method was introduced by Kreylos et al. in 2002 as part of a distributed rendering framework for AMR data [S1, S2, unofficial]. It utilizes grid homogenization via a kD-tree and texture-based slicing [S2, unofficial]. The approach was developed to address the challenges of parallel volume rendering on irregular AMR structures, specifically aiming to balance computational load across distributed nodes [S1, unofficial].
