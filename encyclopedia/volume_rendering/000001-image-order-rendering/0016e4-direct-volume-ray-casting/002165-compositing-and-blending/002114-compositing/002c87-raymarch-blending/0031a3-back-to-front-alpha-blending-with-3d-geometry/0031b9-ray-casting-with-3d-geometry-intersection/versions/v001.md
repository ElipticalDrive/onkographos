# Ray-Casting with 3D Geometry Intersection

Also called: Volume-Geometry Ray Casting

## Overview
This method extends standard direct volume ray casting by integrating pre-rendered 3D polygonal geometry depth data, allowing volumetric rays to detect intersections with opaque solid objects and terminate or blend correctly [S1]. Unlike standard ray casting which only evaluates volume density, this approach ensures correct occlusion of the volume by solid geometry, solving the problem of rendering transparent volumes over opaque meshes in a single pass or specific pipeline configuration [S1].

## How it works
The algorithm modifies the ray-casting traversal loop to compare the ray's current depth against the depth of 3D surfaces fetched from previous rendering passes. It assumes the scene contains no transparent 3D polygonal objects, though minor adjustments could support them [S1].

**Inputs and Outputs:**
*   **Inputs:** Volume texture, 3D surface depth texture (`uDepthSurface`), back surface depth texture (`uBackDepth`), current fragment coordinates (`texD`, `gl_FragCoord`), number of ray steps (`n_steps`), and object color (`objectColor.rgb`).
*   **Outputs:** Accumulated color (`accum.rgb`), accumulated alpha (`accum.a`), and final depth (`final_depth`).

**Data Structures and Layouts:**
*   `uBackDepth`: Texture storing the depth of the volume's back boundary.
*   `uDepthSurface`: Texture storing the depth of the 3D mesh surface.
*   `gl_FragCoord`: Built-in GLSL variable containing window-relative coordinates, where `.z` is depth and `.w` is typically 1.0 or related to projection.
*   `ray_depth`: The current depth of the ray along its path in scene space.

**Parameters:**
*   `n_steps`: The number of discrete steps the ray takes through the volume.
*   `objectColor`: The RGB color of the opaque 3D object hit by the ray.

**Step-by-Step Procedure:**

1.  **Initialization:** For each pixel, initialize ray parameters (`ray_origin`, `ray_direction`, `ray_step`) [S1]. Fetch depth data from previous passes to establish the depth range in scene space [S1].
2.  **Depth Calculation:** Calculate the specific depth values required for intersection testing using the following formulas [S1]:
    $$ \text{backDepth} = 1.0 - \text{unpackFloat}(\text{texture2D}(uBackDepth, \text{texD})) $$
    $$ \text{frontDepth} = 1.0 - \text{gl\_FragCoord.z} \times \text{gl\_FragCoord.w} $$
    $$ \text{surfDepth} = 1.0 - \text{unpackFloat}(\text{texture2D}(uDepthSurface, \text{texD})) $$
    $$ \text{depthStep} = \frac{\text{backDepth} - \text{frontDepth}}{n\_steps} $$
    *Note: `unpackFloat` converts the stored texture value to a linear depth value. The subtraction from 1.0 suggests the textures may store depth in a non-standard or inverted format, or this is a specific implementation detail of the source [S1].*
3.  **Ray Traversal Loop:** Iterate through the volume from `frontDepth` to `backDepth` in increments of `depthStep`. At each step, update `ray_depth`.
4.  **Intersection Test:** Compare the current `ray_depth` with `surfDepth`. If the ray has intersected the surface thickness, execute the blending and termination logic [S1]:
    $$ \text{if } (\text{ray\_depth} - \text{surfDepth} > -\text{depthStep}) $$
    *Pitfall: The intersection check uses the specific inequality `(ray_depth - surfDepth) > -(depthStep)` to determine if the ray has hit the surface thickness. This accounts for the step size to prevent missing thin surfaces due to discretization [S1].*
5.  **Blending and Termination:** Upon intersection, update the accumulated color and alpha using front-to-back blending, update the final depth, and break the loop [S1]:
    $$ \text{accum.rgb} = (\text{accum.a} \times \text{accum.rgb}) + ((1.0 - \text{accum.a}) \times \text{objectColor.rgb}) $$
    $$ \text{accum.a} = (\text{accum.a} \times \text{accum.a}) + (1.0 - \text{accum.a}) $$
    $$ \text{final\_depth} = \text{surfDepth} $$
    $$ \text{break} $$
    *Note: The alpha update formula `accum.a = accum.a * accum.a + (1.0 - accum.a)` simplifies to `1.0` if `accum.a` is not 0 or 1, effectively making the object fully opaque in the accumulation. This appears to be a specific implementation detail for opaque objects where the volume contribution behind the object is discarded [S1].*

**Pseudocode:**

```python
# Initialization
back_depth = 1.0 - unpack_float(texture_sample(uBackDepth, texD))
front_depth = 1.0 - (gl_FragCoord.z * gl_FragCoord.w)
surf_depth = 1.0 - unpack_float(texture_sample(uDepthSurface, texD))
depth_step = (back_depth - front_depth) / n_steps

ray_depth = front_depth
accum_rgb = vec3(0.0)
accum_a = 0.0
final_depth = back_depth

# Ray Traversal
for i in range(n_steps):
    # Check for intersection with 3D geometry
    # Condition: ray has passed or is within the surface thickness
    if (ray_depth - surf_depth) > -depth_step:
        # Blend volume color with object color
        # Note: Standard alpha blending is (src * srcA) + (dst * (1-srcA))
        # Here, objectColor is the new source, accum is the destination
        accum_rgb = (accum_a * accum_rgb) + ((1.0 - accum_a) * objectColor.rgb)
        
        # Update alpha
        # Source alpha is effectively 1.0 for opaque object, but formula uses accum_a
        # Formula from source: accum.a = accum.a * accum.a + (1.0 - accum.a)
        accum_a = (accum_a * accum_a) + (1.0 - accum_a)
        
        final_depth = surf_depth
```

**Edge Cases and Pitfalls:**
*   **Intersection Precision:** The check `(ray_depth - surfDepth) > -(depthStep)` is critical. If `depthStep` is large, thin surfaces might be missed if the ray jumps over the surface depth entirely. The negative threshold ensures that if the ray is slightly behind the surface (within one step), it is considered a hit [S1].
*   **Opaque Assumption:** The method assumes opaque 3D objects. Transparent objects are not supported without minor adjustments [S1].
*   **Depth Space Consistency:** All depth values (`backDepth`, `frontDepth`, `surfDepth`, `ray_depth`) must be in the same coordinate space (scene space) for the comparison to be valid [S1].

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of ray steps `n_steps` and the number of pixels. The intersection test is a constant-time comparison per step.
*   **Memory Complexity:** Requires storage for the volume texture, the 3D surface depth texture, and the back depth texture. Additional memory for intermediate accumulation buffers.
*   **Strengths:** Correctly handles occlusion of volume by solid geometry, which is difficult to achieve with pure volume ray casting alone without complex depth peeling or multiple passes [S1].
*   **Limitations:** Assumes opaque geometry. Performance depends on the resolution of the depth textures and the number of ray steps. Precision issues may arise with thin geometry or large step sizes [S1].
*   **When to use:** When rendering volumetric data (e.g., medical scans, clouds) over opaque 3D models (e.g., patient anatomy, terrain) where correct occlusion is required.
*   **When not to use:** When the scene contains transparent 3D geometry, or when high-performance real-time rendering with very thin features is required and `n_steps` must be kept low.

## Background
This method was presented in the context of deploying volume rendering interactive visualizations in web platforms, specifically addressing the integration of intersected 3D geometry [S1]. It was published in Eurographics Proceedings in 2016 by A. Arbelaiz, A. Moreno, and L. Kabongo [S1]. The work focuses on enabling efficient volume rendering in web environments where standard GPU features for depth peeling or complex compositing might be limited or inefficient.
