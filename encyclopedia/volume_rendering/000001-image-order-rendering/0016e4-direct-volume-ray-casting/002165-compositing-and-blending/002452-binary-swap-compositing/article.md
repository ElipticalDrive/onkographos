# Binary Swap Compositing

Also called: Binary Split Compositing, Binary-Swap, MPI Binary-Swap, binary-swap merging

## Overview
Binary Swap Compositing is a parallel image merging algorithm used to combine independently rendered sub-images from multiple processors into a final volume-rendered image [S1, S2][S3, unofficial]. It solves the bottleneck problem of naive binary compositing, where processors become idle as the compositing tree narrows, by ensuring every processor participates in every stage of the merge [S1, S2][S4, unofficial]. It sets itself apart from sibling methods like [Compositing and Blending](2515-compositing-and-blending.md) by explicitly managing distributed memory communication via a binary-swap tree structure, and from [Pre-Integration Lookup](2854-pre-integration-lookup.md) by operating on already-composited sub-images rather than raw samples.

## How it works
**Inputs and Outputs:**
*   **Input:** Local sub-images (color $C$ and opacity $\alpha$) generated by each processor from its assigned sub-volume. The total number of processors $nproc$ (or depth partitions $PZ$) is typically a power of two [S1, S2][S3, unofficial].
*   **Output:** The final composited image distributed across all processors [S1, S2].

**Data Structures:**
*   **Local Image State:** Each processor maintains two arrays: `local_composite_color` (RGB) and `local_composite_opacity` (A), initialized to the result of local ray casting [S4, unofficial].
*   **Pairing Graph (Optional):** A 3D array `pair[level][zdiv][2]` can be precomputed to store partner indices and roles (sender/receiver) for each level of the compositing tree, where `level` ranges from $0$ to $\log_2(zdiv)-1$ [S3, unofficial].

**Algorithm Steps:**
1.  **Initialization:** Each processor initializes its image plane to the full image area or holds its local sub-image representing its sub-volume's contribution [S1, S2].
2.  **Phase Loop:** Iterate through $L = \log_2(nproc)$ phases. Let `stride` start at 1 and double each phase (`stride *= 2`) until `stride >= nproc` [S1, S2].
3.  **Partner Calculation:** In each phase, calculate the partner processor index using bitwise XOR:
    $$ partner = self \oplus stride $$
    where $\oplus$ is the bitwise XOR operator [S1, S2][S4, unofficial].
4.  **Image Subdivision:** Subdivide the current image plane held by the processor into two pieces (e.g., left/right or top/bottom halves) [S1, S2].
5.  **Communication:** Exchange the relevant half-image data with the calculated partner processor [S1, S2]. If `partner > self`, the processor sends its half-image to the partner; otherwise, it receives the partner's half-image [S7, unofficial].
6.  **Compositing:** Composite the kept portion of the image with the received portion using the front-to-back over operator [S1, S2][S4, unofficial]. Let $C_{local}, \alpha_{local}$ be the kept portion and $C_{recv}, \alpha_{recv}$ be the received portion. Calculate remaining opacity: $\alpha_{rem} = 1 - \alpha_{local}$ [S4, unofficial]. Update color: $C_{new} = C_{local} + \alpha_{rem} \cdot C_{recv}$ [S4, unofficial]. Update opacity: $\alpha_{new} = \alpha_{local} + \alpha_{rem} \cdot \alpha_{recv}$ [S4, unofficial]. Clip $\alpha_{new}$ to $[0, 1]$ [S4, unofficial].
7.  **Update:** Update the local accumulators with $C_{new}$ and $\alpha_{new}$ [S4, unofficial].
8.  **Repeat:** Continue to the next phase with `stride *= 2` [S1, S2].

def binary_swap_compositing(local_color, local_opacity, rank, num_ranks):
    """
    Performs binary-swap compositing along the Z-axis (depth) partitioning.
    Assumes num_ranks is a power of 2.
    """
    step = 1
    while step < num_ranks:
        partner = rank ^ step
        if partner > rank:
            # Send local composite to partner
            send_data(local_color, local_opacity, partner)
        else:
            # Receive composite from partner
            recv_color, recv_opacity = receive_data(partner)
            # Composite received data with local data
            remaining_opacity = 1.0 - local_opacity
            local_color = local_color + remaining_opacity[:, :, None] * recv_color
            local_opacity = local_opacity + remaining_opacity * recv_opacity
            local_opacity = clip(local_opacity, 0.0, 1.0)
        step *= 2

**Edge Cases and Pitfalls:**
*   **Non-Power-of-Two Processors:** If $nproc$ is not a perfect power of two, the simple XOR partner calculation fails [S1, S2]. The algorithm must be generalized to a full (but not necessarily complete) binary tree, requiring additional complexity in partner computation and leaving some processors idle during the first phase [S1, S2].
*   **Load Imbalance:** On heterogeneous networks, achieving linear speedup is difficult due to load imbalance [S1]. Static load balancing can be addressed by uneven data subdivision or assigning multiple subvolumes to more capable machines [S1].
*   **Communication Overhead:** As image size increases, communication time increases [S1]. On PVM networks, communication can dominate compositing time (e.g., 4.4990s out of 4.5180s for vorticity data on 32 workstations) [S3, unofficial].

## Subtopics

### Local Pixel Merging (LPM)
Local Pixel Merging is a variant where the screen is partitioned into subregions, and each processor is responsible for producing the final image of a distinct subregion through local merging of ray-segments [S10, unofficial]. It involves three steps: pixel assignment (PA), ray-segment migration (RSM), and local pixel merging (LPM) [S10, unofficial]. In the LPM step, each processor concurrently composites gathered ray-segments for its assigned pixels using a binary heap for k-way merging of sorted ray-segment lists from different processors [S10, unofficial]. It is chosen when ray-segment lists from multiple processors overlap on the same pixel locations, requiring a global merge operation in visibility order [S10, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(\log nproc)$ communication phases [S1, S2]. Each phase involves exchanging half the image data (or the full image in Z-only partitioning) and performing pixel-wise compositing [S1][S4, unofficial].
*   **Memory Complexity:** $O(H \times W)$ per processor for storing the local image buffers [S4, unofficial].
*   **Measured Performance:**
    *   On a CM-5 with 512 nodes, compositing a 512x512 vorticity dataset took 0.3310 seconds, with only 0.0097 seconds spent on communication [S3, unofficial].
    *   On a PVM network with 32 workstations, compositing the same dataset took 4.5180 seconds, with 4.4990 seconds spent on communication [S3, unofficial].
    *   Compositing speedup from 32 to 512 nodes was only 1.46 for 64x64 images due to overhead [S3, unofficial].
*   **Strengths:** Keeps all processors busy during compositing, avoiding the idle-time bottleneck of naive binary trees [S1, S2]. Efficient for massively parallel processing [S1].
*   **Limitations:** Sensitive to network latency and bandwidth; communication can dominate on slow networks [S1]. Requires $nproc$ to be a power of two for optimal simplicity [S1].

## Background
Binary Swap Compositing was introduced in 1994 by Chen, Johnson, and others in the paper "A Data Distributed Parallel Algorithm for Ray-Traced Volume Rendering" [S2][S3, S4, unofficial][S8]. It was developed to address the performance bottleneck of compositing on massively parallel computers like the CM-5, where naive binary compositing left most processors idle [S1, S2]. The method was implemented on both the CM-5 and a network of scientific workstations [S1].
