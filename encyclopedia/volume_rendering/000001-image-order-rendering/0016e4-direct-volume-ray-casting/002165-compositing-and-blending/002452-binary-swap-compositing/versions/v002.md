# Binary Swap Compositing

Also called: MPI Binary-Swap, Parallel Binary-Swap Compositing, Parallel Image Merging

## Overview
Binary Swap Compositing is a parallel image merging algorithm used to combine front-to-back compositing results from multiple MPI ranks into a final image [S1, unofficial]. It solves the problem of distributed volume rendering by allowing each process to render its assigned sub-volume independently and then merging these partial results in a tree-based structure [S1, unofficial]. Unlike standard sequential compositing which processes samples along a single ray, this method merges pre-composited image tiles from different spatial partitions [S1, unofficial]. It is distinct from [Compositing](2436-compositing.md) in that it operates on image tiles rather than raw samples, and from [Local Pixel Merging (LPM)](#local-pixel-merging-lpm) in that it uses a fixed binary tree communication pattern along one axis rather than a dynamic k-way merge of ray segments [S3, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** The local composite image tile from the current MPI rank, consisting of an RGB color array and an A (opacity) array. The global decomposition is defined by dimensions $PX, PY, PZ$ (number of partitions along X, Y, Z axes). The current rank's coordinates are $(px, py, pz)$.
*   **Output:** The final composite image tile for the current rank's portion of the screen.

**Data Structures:**
*   `local_composite_color`: A 2D array of shape $(H, W, 3)$ storing the accumulated RGB color for the local tile.
*   `local_composite_opacity`: A 2D array of shape $(H, W)$ storing the accumulated opacity for the local tile.
*   `recv_color`, `recv_opacity`: Temporary buffers of the same shape as the local arrays, used to store data received from partner ranks.

**Algorithm Steps:**
The algorithm performs a binary swap along the Z-axis (depth) partitioning. It assumes the image is partitioned such that ranks with the same $(px, py)$ but different $pz$ contribute to the same pixel column in the final image.

1.  **Initialization:** Extract `local_composite_color` and `local_composite_opacity` from the rendered local tile. Determine global rank coordinates:
    $$ px = \lfloor \frac{rank}{PY \cdot PZ} \rfloor \pmod{PX} $$
    $$ py = \lfloor \frac{rank}{PZ} \rfloor \pmod{PY} $$
    $$ pz = rank \pmod{PZ} $$
    [S2, unofficial]

2.  **Binary Tree Loop:** Iterate with a `step` variable starting at 1, doubling each iteration (`step *= 2`), while `step < PZ`.
    [S2, unofficial]

3.  **Partner Identification:** For the current `step`, calculate the partner's Z-index using bitwise XOR:
    $$ partner\_pz = pz \oplus step $$
    [S2, unofficial]
    Calculate the global rank of the partner:
    $$ partner\_rank = px \cdot PY \cdot PZ + py \cdot PZ + partner\_pz $$
    [S2, unofficial]

4.  **Communication:**
    *   If `partner_pz < PZ` (valid partner exists):
        *   If `partner_rank > rank`: The current rank sends its `local_composite_color` and `local_composite_opacity` to `partner_rank`.
        *   If `partner_rank < rank`: The current rank receives `recv_color` and `recv_opacity` from `partner_rank`.
        [S2, unofficial]

5.  **Compositing (Receiver Side):**
    If the current rank received data (i.e., `partner_rank < rank`), update the local accumulators using the standard front-to-back compositing formula, treating the received data as the "back" contribution and the local data as the "front" contribution.
    
    For each pixel $(x, y)$:
    $$ remaining\_opacity = 1.0 - local\_composite\_opacity[x, y] $$
    $$ local\_composite\_color[x, y] = local\_composite\_color[x, y] + recv\_color[x, y] \cdot remaining\_opacity $$
    $$ local\_composite\_opacity[x, y] = local\_composite\_opacity[x, y] + recv\_opacity[x, y] \cdot remaining\_opacity $$
    $$ local\_composite\_opacity[x, y] = \min(local\_composite\_opacity[x, y], 1.0) $$
    [S2, unofficial]

6.  **Termination:** After the loop completes, the `local_composite_color` and `local_composite_opacity` arrays contain the final composited values for the pixels assigned to this rank.

**Pseudocode:**

```python
def binary_swap_compositing(local_color, local_opacity, rank, PX, PY, PZ, comm):
    """
    Performs binary swap compositing along the Z-axis.
    
    Args:
        local_color: numpy array (H, W, 3), local composite RGB.
        local_opacity: numpy array (H, W), local composite Alpha.
        rank: int, current MPI rank.
        PX, PY, PZ: int, number of partitions in each dimension.
        comm: MPI communicator.
        
    Returns:
        final_color: numpy array (H, W, 3), final composite RGB.
        final_opacity: numpy array (H, W), final composite Alpha.
    """
    # Calculate coordinates
    px = (rank // (PY * PZ)) % PX
    py = (rank // PZ) % PY
    pz = rank % PZ
    
    step = 1
    while step < PZ:
        partner_pz = pz ^ step
        partner_rank = px * PY * PZ + py * PZ + partner_pz
        
        if partner_pz < PZ:
            if partner_rank > rank:
                # Send local data to partner
                comm.Send(local_color, dest=partner_rank)
                comm.Send(local_opacity, dest=partner_rank)
            else:
                # Receive data from partner
                recv_color = np.empty_like(local_color)
                recv_opacity = np.empty_like(local_opacity)
                comm.Recv(recv_color, source=partner_rank)
                comm.Recv(recv_opacity, source=partner_rank)
                
                # Composite received (back) onto local (front)
                remaining = 1.0 - local_opacity
                local_color = local_color + recv_color * remaining[:, :, np.newaxis]
                local_opacity = local_opacity + recv_opacity * remaining
                # Clip opacity to [0, 1]
                local_opacity = np.clip(local_opacity, 0.0, 1.0)
        
        step *= 2
        
    return local_color, local_opacity
```

**Edge Cases and Pitfalls:**
*   **Power of 2 Requirement:** The algorithm requires $PZ$ (the number of partitions along the Z-axis) to be a power of 2. If $PZ$ is not a power of 2, the XOR logic and the loop condition `step < PZ` will fail to pair all ranks correctly or will leave gaps in the visited logic [S1, unofficial].
*   **Axis Selection:** The standard implementation described composites only along the Z-axis. If the data is partitioned differently (e.g., along X or Y), the coordinate calculation and partner finding logic must be adjusted accordingly.
*   **Precision:** Accumulating opacity can lead to floating-point precision errors if many small opacities are summed, though clipping to 1.0 mitigates over-saturation.

## Subtopics

### Local Pixel Merging (LPM)
Local Pixel Merging is a variant used in object-space decomposition where ray segments from multiple processors overlap on the image screen [S3, unofficial]. Unlike Binary Swap which merges pre-composited tiles, LPM merges sorted ray-segment lists for each pixel [S3, unofficial]. It involves three steps: Pixel Assignment (PA), Ray-Segment Migration (RSM), and Local Pixel Merging (LPM) [S3, unofficial]. In the LPM step, each processor composites gathered ray-segments using a binary heap for k-way merging of sorted lists [S3, unofficial]. It is chosen when the partitioning strategy results in significant overlap of projection areas across processors, requiring a global merge of visibility-ordered segments rather than simple tile merging [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** The compositing phase involves $\log_2(PZ)$ communication steps. In each step, all ranks communicate their entire image tile. The computation per pixel is constant time $O(1)$. Total time is $O(\log PZ \cdot \frac{HW}{P_{total}} + \text{communication cost})$.
*   **Memory Complexity:** $O(HW)$ per rank for storing the local tile. No additional large buffers are required beyond temporary receive buffers.
*   **Performance:** Performance is limited by network bandwidth and latency, especially as the number of ranks increases. It scales well with the number of ranks for the ray-casting phase, but the compositing phase becomes a bottleneck if the image resolution is high or the network is slow.
*   **Strengths:** Simple implementation, efficient for large-scale MPI clusters, leverages standard front-to-back compositing logic.
*   **Limitations:** Requires $PZ$ to be a power of 2. Not suitable for non-uniform partitioning along the compositing axis without modification. Communication overhead can dominate for small images or high rank counts.

## Background
Binary Swap Compositing was developed as part of parallel volume rendering systems using MPI to handle large 3D scalar fields [S1, unofficial]. It is based on the principle of dividing the volume into sub-blocks, rendering them independently, and merging the results in a binary tree fashion [S1, unofficial]. The method is commonly used in scientific visualization for datasets like the Isabel Hurricane dataset [S1, unofficial].
