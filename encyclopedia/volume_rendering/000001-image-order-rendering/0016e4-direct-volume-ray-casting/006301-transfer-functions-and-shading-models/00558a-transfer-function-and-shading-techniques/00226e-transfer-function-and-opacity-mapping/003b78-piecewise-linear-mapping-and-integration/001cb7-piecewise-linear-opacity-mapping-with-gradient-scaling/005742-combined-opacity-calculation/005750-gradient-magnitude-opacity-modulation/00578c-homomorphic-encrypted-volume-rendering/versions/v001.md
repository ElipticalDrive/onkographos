# Homomorphic-Encrypted Volume Rendering

Also called: Encrypted Volume Rendering, Paillier Homomorphic Encryption for Volume Rendering, Privacy-Preserving Remote Volume Rendering, Privacy-Preserving Volume Rendering

## Overview
Homomorphic-Encrypted Volume Rendering is a direct volume rendering technique that performs ray casting and compositing entirely on encrypted volume data using the Paillier partially homomorphic encryption (PHE) scheme [S1]. It solves the problem of rendering highly confidential datasets (e.g., medical CT/MRI) on untrusted cloud servers by ensuring that neither the volume data nor the rendered image is interpretable to the server [S1]. Unlike prior approaches that leak structure via obfuscation or require trusted clients with high bandwidth, this method allows a thin client to request renders from an honest-but-curious server, which returns an encrypted image that only the key-holding client can decrypt [S1]. It differs from [Gradient-Magnitude Opacity Modulation](15927-gradient-magnitude-opacity-modulation.md) by operating on raw encrypted scalar values without pre-calculated gradient modulation, relying instead on simplified transfer functions and floating-point encoding to maintain privacy [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** An encrypted volume dataset (Big-Integers), camera parameters (position, projection), and transfer function settings sent by the client.
*   **Output:** An encrypted image buffer (Encrypted Floating-Point numbers) sent to the client.

**Data Structures:**
1.  **Encrypted Volume:** Stored as a 3D grid of Big-Integers. Each voxel value $v$ is encrypted as $\llbracket v \rrbracket$ using Paillier [S1]. Metadata (dimensions, storage order) is plaintext [S1].
2.  **Encrypted Floating-Point Number:** Represented as a tuple $(\langle m \rangle, e)$, where $\langle m \rangle$ is the encrypted mantissa (Big-Integer) and $e$ is the unencrypted plaintext integer exponent [S1]. The value is $m \cdot b^e$, where $b$ is a constant base (e.g., $b=10$) [S1].
3.  **Image Buffer:** A 2D grid of Encrypted Floating-Point numbers, one per pixel channel (e.g., 3 for RGB) [S1].

**Paillier Cryptosystem Parameters:**
*   **Public Key:** Modulus $N = p \times q$, where $p, q$ are large primes [S1].
*   **Private Key:** Primes $p, q$ [S1].
*   **Operations:**
    *   Additive Homomorphism: $\text{Dec}(\llbracket m_1 \rrbracket \oplus \llbracket m_2 \rrbracket) = (m_1 + m_2) \pmod N$ [S1].
    *   Plaintext-Encrypted Multiplication: $\text{Dec}(\llbracket m_1 \rrbracket \otimes d) = (m_1 \times d) \pmod N$, where $d$ is plaintext [S1].
    *   Note: Paillier is probabilistic; one plaintext maps to many possible ciphertexts [S1].

**Algorithm Steps:**

1.  **Encryption and Upload:**
    The acquisition device encrypts every scalar voxel value $v$ of the volume dataset using the public key $N$ to produce $\llbracket v \rrbracket$. The encrypted volume is uploaded to the server [S1].

2.  **Rendering Request:**
    The client sends a request containing camera settings and transfer function parameters to the server [S1].

3.  **Ray Casting and Sampling:**
    For each pixel, the server calculates sample positions along the viewing ray [S1].
    
    *   **Trilinear Interpolation:** To interpolate encrypted values, the server identifies the 8 neighboring voxels. It computes plaintext interpolation weights $\alpha_i$ (distances between sample and voxel positions, summing to 1.0) [S1].
    *   **Exponent Alignment:** To add encrypted floating-point numbers $(\langle m_1 \rangle, e_1)$ and $(\langle m_2 \rangle, e_2)$, their exponents must match. If $e_1 \neq e_2$, the number with the greater exponent is adjusted to the lower exponent. Decreasing the exponent $e_{high}$ to $e_{low}$ requires multiplying the encrypted mantissa by $b^{(e_{low} - e_{high})}$ using $\otimes$ [S1]. Increasing the exponent is impossible as it requires division [S1].
    *   **Weighted Sum:** The interpolated value is calculated as $\bigoplus_i (\langle m_i \rangle \otimes \alpha_i)$, resulting in an encrypted mantissa with the aligned exponent [S1].

4.  **Compositing (X-ray Mode):**
    The method supports "Encrypted X-ray Rendering," where sample values map to white color with monotonically increasing opacity, and compositing is a summation followed by normalization [S1].
    *   **Summation:** The server accumulates sample values along the ray using $\oplus$ [S1].
    *   **Normalization:** Direct division is not supported by Paillier. The server sends the encrypted sum $\langle S \rangle$ and the plaintext sample count $n$ to the client [S1]. The client decrypts $S$ and computes $S/n$ [S1].
    *   *Approximation:* Alternatively, division can be approximated by multiplication with the reciprocal: $\frac{1}{n} \approx \text{Dec}(\sum \otimes \frac{1}{n} \cdot 10^\gamma \cdot 10^{-\gamma})$ [S1].

5.  **Result Delivery:**
    The server sends the encrypted image buffer to the client [S1].

6.  **Client Decryption:**
    The client decrypts each pixel value using the private key. For grayscale, one decryption per pixel; for RGB, three [S1].

**Edge Cases and Pitfalls:**
*   **Exponent Alignment:** Paillier does not support homomorphic division, so the exponent of an encrypted mantissa cannot be increased. When adding values with different exponents, the one with the greater exponent must be decreased to match the lower one [S1].
*   **Division:** Final normalization (division) in X-ray rendering cannot be performed on the server. The server must send the encrypted sum and sample count to the client for post-decryption division [S1].
*   **Interpolation:** Direct integer arithmetic interpolation $(m_1 \alpha_1 + m_2 \alpha_2)/(\alpha_1 + \alpha_2)$ is not feasible due to lack of division. Floating-point encoding is used to allow weight multiplication [S1].
*   **Precision:** Paillier encryption results in large integers (e.g., 1000 bits). Precision loss may occur if exponents are not managed carefully [S1].

## Operating characteristics
*   **Time Complexity:** Not interactive in proof-of-concept implementations due to the computational cost of Paillier operations (modular exponentiation) and large ciphertext sizes [S1].
*   **Memory Complexity:** High. Each voxel is stored as a Big-Integer (e.g., 1000 bits), significantly larger than standard 8/16-bit voxels [S1].
*   **Performance:** Scales linearly with server compute power. The approach is designed to allow scaling with available server resources, though current hardware limits frame rates [S1].
*   **Strengths:** Provides strong cryptographic security (uninterpretable data to server); supports thin clients; no need for trusted clients or high-bandwidth data transfer for intermediate results [S1].
*   **Limitations:** No interactive frame rates currently; limited to additive homomorphic operations (no encrypted-encrypted multiplication); simplified transfer functions (e.g., X-ray mode) to avoid complex operations; exponent alignment constraints [S1].
*   **When to Use:** When rendering highly sensitive data (medical, seismic) on untrusted cloud infrastructure where privacy is paramount and latency is acceptable.
*   **When Not to Use:** When interactive frame rates are required; when complex transfer functions requiring encrypted-encrypted multiplication are needed; when network bandwidth is extremely limited (though this method reduces bandwidth compared to trusted-client models) [S1].

## Background
*   **Origin:** Based on the Paillier cryptosystem developed by Pascal Paillier in 1999 [S1].
*   **Development:** Proposed by Sebastian Mazza, Daniel Patel, and Ivan Viola in 2020 [S1].
*   **History:** Prior attempts at privacy-preserving rendering included Mohanty et al. [22], which used two servers and leaked structure, and Chou and Yang [3], which used obfuscation rather than cryptographic encryption. This method was developed to provide "secure by design" privacy without these weaknesses [S1].
*   **Usage:** Proposed for medical CT/MRI/PET data and hydrocarbon/mineral exploration seismic scans [S1].
