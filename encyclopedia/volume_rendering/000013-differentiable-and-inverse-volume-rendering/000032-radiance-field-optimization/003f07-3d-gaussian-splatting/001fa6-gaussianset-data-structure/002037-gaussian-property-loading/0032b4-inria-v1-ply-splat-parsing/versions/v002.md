# INRIA V1 PLY Splat Parsing

Also called: INRIA PLY Parser, INRIAV1PlyParser, INRIAV1PlyParser.parseToUncompressedSplat, PLY Format Parsing (INRIA), PLY Reader, ParseFilePLY, SplatCloud parsing

## Overview
The INRIA V1 PLY Splat Parsing method decodes the text-based `.ply` files generated by the original INRIA 3D Gaussian Splatting implementation into an uncompressed, contiguous array of Gaussian properties suitable for rendering or further processing [S1, S3, unofficial]. It solves the problem of interpreting variable-length spherical harmonic (SH) fields and applying specific activation functions (sigmoid for opacity, exponential for scale) and coordinate system transformations required by downstream engines [S1, S2, unofficial]. Unlike the standard `.splat` binary format which uses fixed-width records, this method handles the PLY header's variable field counts to dynamically determine the SH degree (0, 1, or 2) and extract the corresponding coefficients [S1, unofficial].

## How it works
**Inputs:** A raw INRIA V1 `.ply` file containing a `vertex` element with properties for position, scale, rotation, opacity, and spherical harmonics.
**Outputs:** An uncompressed array of splats, where each splat contains normalized position, scale, rotation (quaternion), RGB color, opacity, and SH coefficients.

**Data Structures:**
The parser constructs an internal map `vertexData` where keys are property names (e.g., `"x"`, `"scale_0"`) and values are `float*` arrays containing the column data for all vertices. The output is a flat array of `Splat` structures.

**Uncompressed Splat Array Layout:**
Each splat in the output array is laid out contiguously with the following fields (offsets are conceptual indices in a float array):
1. `OFFSET_X`, `OFFSET_Y`, `OFFSET_Z`: Position (3 floats)
2. `OFFSET_SCALE0`, `OFFSET_SCALE1`, `OFFSET_SCALE2`: Scales (3 floats)
3. `OFFSET_ROT0` to `OFFSET_ROT3`: Quaternion components (4 floats)
4. `OFFSET_FDC0`, `OFFSET_FDC1`, `OFFSET_FDC2`: DC Color (RGB) (3 floats)
5. `OFFSET_OPACITY`: Opacity (1 float)
6. `OFFSET_FRC0` to `OFFSET_FRC44`: Spherical Harmonics coefficients (45 floats for Degree 2)

**Numbered Steps:**

1.  **Parse Header and Detect SH Degree:**
    Read the PLY header. Count the number of lines containing the substring `'f_rest_'`.
    - If count $\ge 45$, set `shFieldsToReadCount = 45` (Degree 2).
    - Else if count $\ge 24$, set `shFieldsToReadCount = 24` (Degree 1).
    - Else if count $\ge 9$, set `shFieldsToReadCount = 9` (Degree 0).
    - Else, set `shFieldsToReadCount = 0`.

2.  **Construct Field List:**
    Define `BaseFieldNamesToRead` as: `['scale_0', 'scale_1', 'scale_2', 'rot_0', 'rot_1', 'rot_2', 'rot_3', 'x', 'y', 'z', 'f_dc_0', 'f_dc_1', 'f_dc_2', 'opacity', 'red', 'green', 'blue', 'f_rest_0']` [S1, unofficial].
    Create an array of remaining SH field names: `f_rest_1` through `f_rest_N`, where $N = \text{shFieldsToReadCount} - 1$.
    Concatenate `BaseFieldNamesToRead` with the remaining SH fields to form `fieldNamesToRead` [S1, unofficial].

3.  **Extract Vertex Data:**
    For the `vertex` element, iterate through properties. For each property with `countType != None`, extract column data using a PLY reader (e.g., `reader.extract_properties`). Store the resulting `float*` arrays in `vertexData` keyed by property name [S1, S2, unofficial].

4.  **Check Required Properties:**
    Verify existence of the following groups in `vertexData`:
    - `PositionExists`: keys `"x"`, `"y"`, `"z"` exist.
    - `NormalExists`: keys `"nx"`, `"ny"`, `"nz"` exist.
    - `OrientationExists`: keys `"rot_0"`, `"rot_1"`, `"rot_2"`, `"rot_3"` exist.
    - `ScaleExists`: keys `"scale_0"`, `"scale_1"`, `"scale_2"` exist.
    - `OpacityExists`: key `"opacity"` exists.
    - `ZeroOrderHarmonicsExists`: keys `"f_dc_0"`, `"f_dc_1"`, `"f_dc_2"` exist.

5.  **Iterate and Parse Splats:**
    For each vertex index $i$ from $0$ to `numVertices - 1`:
    
    a. **Position:**
    If `PositionExists`:
    $$ \text{pos}_x = x_i $$
    $$ \text{pos}_y = -z_i $$
    $$ \text{pos}_z = -y_i $$
    Scale by 100.0:
    $$ \text{SplatData.Positions}[i] = 100.0 \times (\text{pos}_x, \text{pos}_y, \text{pos}_z) $$
    [S2, unofficial]. This transforms from PLY coordinates (likely Y-up or Z-up) to the target engine's coordinate system (e.g., Unreal's X-forward, Y-left, Z-up) [S2, unofficial].

    b. **Normals:**
    If `NormalExists`:
    $$ \text{SplatData.Normals}[i] = (nx_i, ny_i, nz_i) $$
    No transformation is applied [S2, unofficial].

    c. **Rotation (Quaternion):**
    If `OrientationExists`:
    Construct quaternion $Q$ from PLY values. The PLY stores quaternions as `(rot_0, rot_1, rot_2, rot_3)`. The code constructs `FQuat(rot_1, rot_2, rot_3, rot_0)`, implying `rot_0` is the W component [S2, unofficial].
    Normalize $Q$.
    Apply coordinate transformation:
    $$ Q_{\text{transformed}} = (\text{Rot}.X, -\text{Rot}.Z, -\text{Rot}.Y, \text{Rot}.W) $$
    Add $Q_{\text{transformed}}$ to `SplatData.Orientations` [S2, unofficial].

    d. **Scale:**
    If `ScaleExists`:
    Compute scale vector using exponential activation and reordering:
    $$ s_x = \exp(\text{scale\_0}_i) $$
    $$ s_y = \exp(\text{scale\_2}_i) $$
    $$ s_z = \exp(\text{scale\_1}_i) $$
    Scale by 100.0:
    $$ \text{SplatData.Scales}[i] = 100.0 \times (s_x, s_y, s_z) $$
    Note the swap: `scale_1` maps to Z, `scale_2` maps to Y [S2, unofficial].
    [G] If `ScaleExists` is false, default scales to 0.01 [S1, unofficial].

    e. **Opacity:**
    If `OpacityExists`:
    Apply sigmoid activation:
    $$ \alpha = \frac{1}{1 + \exp(-\text{opacity}_i)} $$
    Clamp to $[0.0, 1.0]$.
    Add $\alpha$ to `SplatData.Opacity` [S2, unofficial].
    [G] If `OpacityExists` is false, default opacity to 0.0 or 1.0 depending on implementation; standard practice is to ensure valid alpha [S1, unofficial].

    f. **Zero-Order Harmonics (DC Color):**
    If `ZeroOrderHarmonicsExists`:
    Extract `f_dc_0`, `f_dc_1`, `f_dc_2`.
    [S3, unofficial] Note: Some parsers ignore higher-order harmonics entirely if not requested, but this step extracts the DC component regardless of SH degree if present.
    Add $(f\_dc\_0, f\_dc\_1, f\_dc\_2)$ to `SplatData.ZeroOrderHarmonicsCoefficients` [S2, unofficial].

    g. **Higher-Order Harmonics:**
    If `shFieldsToReadCount > 9`:
    Create `HighOrderHarmonicsCoefficients`.
    Iterate $y$ from 0 to 44 with step 3.
    For each $y$, read `f_rest_y`, `f_rest_{y+1}`, `f_rest_{y+2}`.
    Construct `FVector` and add to `HigherOrderHarmonics.Values` [S2, unofficial].
    [S3, unofficial] Note: Some implementations (e.g., SceneView) ignore `f_rest_*` fields entirely, supporting only SH0. This parser supports dynamic detection [S1, S3, unofficial].

    h. **Output Buffer Writing (Alternative Path):**
    If writing to a compressed/optimized buffer (e.g., `.splat` or `.ksplat`):
    1. Initialize `newSplat` with `outSphericalHarmonicsDegree`.
    2. Read raw splat data from `splatData` at `row` offset by `splatDataOffset` into `rawSplat` array [S1, unofficial].
    3. **Scales:** If `rawSplat[SCALE_0]` exists:
       $$ \text{newSplat}[\text{OFFSET\_SCALE0}] = \exp(\text{rawSplat}[\text{SCALE\_0}]) $$
       $$ \text{newSplat}[\text{OFFSET\_SCALE1}] = \exp(\text{rawSplat}[\text{SCALE\_1}]) $$
       $$ \text{newSplat}[\text{OFFSET\_SCALE2}] = \exp(\text{rawSplat}[\text{SCALE\_2}]) $$
       Else, set all scales to 0.01 [S1, unofficial].
    4. **Rotation:** Normalize quaternion:
       $$ Q = (\text{rawSplat}[\text{ROT\_0}], \text{rawSplat}[\text{ROT\_1}], \text{rawSplat}[\text{ROT\_2}], \text{rawSplat}[\text{ROT\_3}]).\text{normalize}() $$
       Assign to `newSplat` offsets `ROT0`-`ROT3` [S1, unofficial].
    5. **Position:**
       $$ \text{newSplat}[\text{OFFSET\_X}] = \text{rawSplat}[X] $$
       $$ \text{newSplat}[\text{OFFSET\_Y}] = \text{rawSplat}[Y] $$
       $$ \text{newSplat}[\text{OFFSET\_Z}] = \text{rawSplat}[Z] $$
       [S1, unofficial].
    6. **Color (DC):**
       If `rawSplat[F_DC_0]` exists, use SH constant $C_0 = 0.28209479177387814$:
       $$ \text{newSplat}[\text{OFFSET\_FDC0}] = (0.5 + C_0 \times \text{rawSplat}[F\_DC\_0]) \times 255 $$
       $$ \text{newSplat}[\text{OFFSET\_FDC1}] = (0.5 + C_0 \times \text{rawSplat}[F\_DC\_1]) \times 255 $$
       $$ \text{newSplat}[\text{OFFSET\_FDC2}] = (0.5 + C_0 \times \text{rawSplat}[F\_DC\_2]) \times 255 $$
       Else if `RED` exists, use `rawSplat[RED] * 255`, etc. Else set RGB to 0 [S1, unofficial].
    7. **Opacity:**
       If `rawSplat[OPACITY]` exists:
       $$ \text{newSplat}[\text{OFFSET\_OPACITY}] = \left( \frac{1}{1 + \exp(-\text{rawSplat}[OPACITY])} \right) \times 255 $$
       [S1, unofficial].
    8. **Higher-Order SH:**
       If `outSphericalHarmonicsDegree >= 1` and `rawSplat[F_REST_0]` exists, copy degree 1 coefficients (indices 0-8).
       If `outSphericalHarmonicsDegree >= 2`, copy degree 2 coefficients (indices 9-23) [S1, unofficial].
    9. **Clamp:**
       Clamp `FDC0`, `FDC1`, `FDC2`, and `OPACITY` to integer range $[0, 255]$:
       $$ \text{value} = \text{clamp}(\lfloor \text{value} \rfloor, 0, 255) $$
       [S1, unofficial].
    10. Write to output buffer at offset $i \times \text{outBytesPerSplat} + \text{toOffset}$ [S1, unofficial].

**Parameters:**
- `outSphericalHarmonicsDegree`: Target SH degree for output. Clamped to $\min(\text{outSphericalHarmonicsDegree}, \text{header.sphericalHarmonicsDegree})$ [S1, unofficial].
- `splatAlphaRemovalThreshold`: Threshold to ignore splats with alpha $< \text{value}$. Range 0-255. Default 1 [S1, unofficial].
- `SH_C0`: Constant $0.28209479177387814$ [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Coordinate System Mismatch:** The PLY format from INRIA may use a different axis convention (e.g., Y-up) than the target renderer (e.g., Z-up). The transformation $(x, -z, -y)$ is specific to Unreal Engine compatibility [S2, unofficial]. Other engines may require different transformations.
- **Quaternion Order:** PLY quaternions are stored as `(rot_0, rot_1, rot_2, rot_3)`. The code interprets `rot_0` as W. Ensure the target engine expects $(W, X, Y, Z)$ or $(X, Y, Z, W)$ order. The transformation $Q_{\text{transformed}} = (X, -Z, -Y, W)$ handles axis flipping [S2, unofficial].
- **Scale Exponentiation:** INRIA stores scales in log-space. Failure to apply $\exp()$ results in incorrect sizes [S2, unofficial].
- **Opacity Sigmoid:** INRIA stores opacity in logit space. Failure to apply sigmoid results in incorrect transparency [S2, unofficial].
- **SH Degree Detection:** Relying on the count of `f_rest_*` fields is robust for INRIA files but may fail if the file is corrupted or uses a non-standard naming convention [S1, unofficial].
- **Missing Fields:** If `ScaleExists` or `OpacityExists` is false, the parser must provide defaults (e.g., scale 0.01, opacity 0.0 or 1.0) to avoid NaNs or crashes [S1, unofficial].

## Subtopics

### [Standard Splat File Parsing](6828-standard-splat-file-parsing.md)
Standard Splat File Parsing is a method for decoding the binary `.splat` file format into an uncompressed, contiguous array of splat properties. It solves the problem of efficiently loading 3D Gaussian Splatting data from disk into a format suitable for immediate rendering or further processing. Unlike the INRIA V1 PLY format, which uses text-based headers and variable-length fields, the standard `.splat` format is a fixed-width binary record, allowing for direct memory mapping and simple offset-based extraction. It differs from lazy parsing methods (such as Antimatter15's chunk-based loader) by eagerly decoding all data into memory, serving as a baseline for correctness testing and simple scene loading.

## Operating characteristics
**Time Complexity:** $O(N \cdot D)$, where $N$ is the number of splats and $D$ is the number of SH coefficients (up to 45). The parsing is linear in the number of vertices and properties.
**Memory Complexity:** $O(N \cdot (3 + 3 + 4 + 3 + 1 + 45))$ floats for the uncompressed splat array, plus overhead for the PLY header parsing.
**Measured Performance:** Not given in the sources.
**Scaling:** Linear scaling with the number of splats. The text-based PLY format is slower to parse than binary formats due to string parsing and header interpretation.
**Strengths:** Handles variable SH degrees dynamically; applies necessary activation functions and coordinate transformations; robust to missing fields with defaults.
**Limitations:** Slower than binary parsers; memory-intensive due to uncompressed output; coordinate system transformations are engine-specific (Unreal) and may need adjustment for other engines.
**When to use:** When loading INRIA-generated `.ply` files for real-time rendering in engines that require specific coordinate/activation conversions (e.g., Unreal Engine).
**When not:** When memory or load time is critical; use binary `.splat` or `.ksplat` formats instead.

## Background
The INRIA V1 PLY format was introduced with the paper "3D Gaussian Splatting for Real-Time Radiance Field Rendering" by Kerbl et al. (2023) [S1, unofficial]. The parser described here is part of unofficial implementations (e.g., GaussianSplats3D, unreal-splat, SceneView) that bridge the gap between the INRIA output and real-time renderers [S1, S2, S3, unofficial]. The specific coordinate and scale transformations are derived from reverse-engineering the INRIA training pipeline and adapting it for game engines like Unreal Engine [S2, unofficial].
