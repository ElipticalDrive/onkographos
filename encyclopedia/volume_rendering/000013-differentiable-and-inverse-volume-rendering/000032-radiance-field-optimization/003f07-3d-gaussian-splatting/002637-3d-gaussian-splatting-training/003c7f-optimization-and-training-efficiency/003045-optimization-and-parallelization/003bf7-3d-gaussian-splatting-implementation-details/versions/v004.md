# 3D Gaussian Splatting Implementation Details

Also called: 3DGS CUDA kernel implementation, GS Implementation Parameters, Gaussian Splatting Training Configuration, Implementation Details, gsplat implementation details, half-precision rasterization implementation

## Overview
This article details the specific hyperparameters, data structures, and optimization strategies required to implement 3D Gaussian Splatting (3DGS) training and rendering pipelines effectively. It addresses common implementation pitfalls such as half-precision instability, incorrect scene extent calculation, and inefficient spherical harmonic (SH) usage. It sets itself apart from general theoretical descriptions by providing concrete values for optimizer settings, loss weights, and memory management techniques (e.g., half-precision fetches) that are critical for stable and fast convergence [S1, S2][S6, unofficial].

## How it works

### Inputs and Outputs
*   **Inputs:**
    *   Sparse point cloud from Structure-from-Motion (SfM) [S3].
    *   Camera poses and intrinsics [S3].
    *   Training images (randomly selected per iteration) [S2].
    *   Hyperparameters: Learning rate, SH degree, background color, loss weights [S2][S6, unofficial].
*   **Outputs:**
    *   Optimized 3D Gaussian parameters: Position ($\mathbf{p}$), Covariance (via scale $\mathbf{s}$ and rotation $\mathbf{r}$), Opacity ($\alpha$), Spherical Harmonics coefficients ($\mathbf{c}_{SH}$) [S7, unofficial].
    *   Rendered images and gradients for backpropagation [S1].

### Data Structures
*   **Gaussian List:** Each Gaussian stores position, scale (3 floats), rotation (quaternion, 4 floats), opacity (1 float), and SH coefficients. For SH degree $D$, the number of coefficients per color channel is $(D+1)^2$ [S6, unofficial].
*   **Volume Grid (Optional):** For large-scale scenes, a voxel grid may be used for initialization or sparse convolution. Example: Height 12.8m, Width 32m, Length 64m, Voxel size 0.1m, resulting in dimensions $128 \times 320 \times 640$ [S2].
*   **Feature Vectors:** Stored in half-precision (FP16) during rasterization to reduce register pressure [S1].

### Parameters and Typical Values
*   **Optimizer:** Adam [S2].
*   **Learning Rate:** $1 \times 10^{-3}$ [S2].
*   **SH Degree:** 1 (for simplicity/efficiency) or 3 (default) [S2][S6, unofficial]. Setting to 0 improves training speed by ~16.25-16.57% with negligible quality loss if higher degrees are static [S6, unofficial].
*   **Background Color:** Default is white (1.0, 1.0, 1.0). Optimal range for speed/quality balance is $0.3 \le bg \le 0.5$ [S6, unofficial]. Setting $bg=0.4$ reduces processing time by ~21.85% on some datasets [S6, unofficial].
*   **Loss Weights:**
    *   $\lambda_1 = 0.1$ (for scale loss $L_{scales}$) [S4, unofficial].
    *   $\lambda_v = 0.2$ (for other loss terms) [S4, unofficial].
*   **Scene Extent:**
    *   Default: $e_{\text{scene}} = 1.1 \cdot \max_{i=1}^{N_{\text{cam}}} \|\bar{C} - C_i\|_2$ [S3].
    *   Corrected: $e'_{\text{scene}} = \frac{1}{N_{\text{SfM}}} \sum_{i=1}^{N_{\text{SfM}}} \|\bar{C} - p_i\|_2$ [S3].

### Numbered Steps

1.  **Initialization:**
    *   Initialize Gaussians from the SfM point cloud [S3].
    *   Calculate scene extent. If cameras are clustered (e.g., orbiting a small object), use the corrected scene extent based on SfM points to avoid bias [S3].
    *   Set SH degree. If using degree 0, remove superfluous operations related to higher degrees in the model code [S6, unofficial].

2.  **Warm-up Phase (Static Optimization):**
    *   For the first 3000 iterations, optimize only the static Gaussians (position, scale, rotation, opacity, SH) [S4, unofficial].
    *   Do not optimize deformation fields or dynamic parameters during this phase [S4, unofficial].

3.  **Joint Optimization:**
    *   After warm-up, jointly optimize Gaussians and any deformation fields [S4, unofficial].
    *   Loss function: $\mathcal{L} = \mathcal{L}_{color} + \lambda_1 \cdot \mathcal{L}_{scales}$ [S4, unofficial].
    *   Use Adam optimizer with learning rate $1 \times 10^{-3}$ [S2].

4.  **Rasterization (Forward Pass):**
    *   Project 3D Gaussians to 2D image plane [S7, unofficial].
    *   Sort Gaussians by depth within each tile [S1].
    *   Render using alpha blending: $\mathbf{C} = \sum_{i=1}^N \mathbf{c}_i \alpha_i T_i$, where $T_i = \prod_{j=1}^{i-1} (1 - \alpha_j)$ [S7, unofficial].
    *   Use half-precision memory fetches for feature vectors to reduce register pressure [S1].
    *   Apply automatic scaling factor to loss values to improve half-precision training stability [S1].

5.  **Backpropagation (Backward Pass):**
    *   Compute gradients of loss with respect to Gaussian parameters [S1].
    *   Use custom CUDA kernels for forward and backward logic if using `gsplat` with 3DGUT formulation [S1].

### Pseudocode

```python
def train_3dgs(sfm_points, cameras, images, hyperparams):
    # 1. Initialization
    gaussians = initialize_gaussians_from_sfm(sfm_points)
    
    # Correct scene extent if cameras are clustered
    avg_camera_pos = mean([cam.pos for cam in cameras])
    if is_camera_clustered(cameras):
        scene_extent = corrected_scene_extent(avg_camera_pos, sfm_points)
    else:
        scene_extent = default_scene_extent(avg_camera_pos, cameras)
    
    gaussians.scene_extent = scene_extent
    
    # Set SH degree
    sh_degree = hyperparams.sh_degree # e.g., 0, 1, or 3
    if sh_degree == 0:
        remove_higher_degree_sh_operations(gaussians)
        
    # Set background color
    bg_color = hyperparams.bg_color # e.g., 0.4
    
    # 2. Optimization Loop
    optimizer = Adam(gaussians.parameters(), lr=hyperparams.lr)
    
    for iteration in range(hyperparams.max_iterations):
        # Randomly select a single image from a random scene
        image, camera = random_selection(images, cameras)
        
        # Forward Pass
        rendered_image = rasterize(gaussians, camera, bg_color)
        
        # Loss Calculation
        loss_color = compute_color_loss(rendered_image, image)
        
        # Add scale loss if in joint optimization phase
        loss_total = loss_color
        if iteration > 3000:
            loss_scales = compute_scale_loss(gaussians)
            loss_total += hyperparams.lambda_1 * loss_scales
            
        # Backward Pass
        optimizer.zero_grad()
        loss_total.backward()
        optimizer.step()
        
        # Densification (e.g., split/prune based on gradients)
        if iteration % densification_interval == 0:
            densify_gaussians(gaussians, hyperparams)
            
    return gaussians

def rasterize(gaussians, camera, bg_color):
    # Project Gaussians
    projected_gaussians = project_to_image(gaussians, camera)
    
    # Sort by depth within tiles
    sorted_gaussians = sort_by_depth_tile_wise(projected_gaussians)
    
    # Alpha Blending with half-precision fetches
    final_color = torch.zeros_like(image_placeholder)
    transmittance = torch.ones_like(image_placeholder)
    
    for gaussian in sorted_gaussians:
        alpha = gaussian.opacity * exp(-0.5 * gaussian.quadratic_form)
        color = evaluate_sh(gaussian.sh_coeffs, gaussian.view_direction)
        
        # Blend
        contribution = alpha * transmittance * color
        final_color += contribution
        transmittance *= (1 - alpha)
        
    # Composite with background
    final_color += transmittance * bg_color
    
    return final_color
```

### Edge Cases and Pitfalls
*   **Scene Extent Bias:** Default scene extent calculation based on camera positions can be too small if cameras are clustered (e.g., orbiting a small object), leading to incorrect splitting/pruning of Gaussians [S3]. Use the corrected formula based on SfM points [S3].
*   **SH Degree:** Using SH degree > 0 when coefficients are static (unchanged during training) wastes computation. Setting degree to 0 and removing related operations improves speed by ~16.57% [S6, unofficial].
*   **Background Color:** Extreme background values can negatively impact learning rate and PSNR. Use $0.3 \le bg \le 0.5$ for optimal balance [S6, unofficial].
*   **Half-Precision Stability:** Use automatic scaling factor for loss values to prevent instability in FP16 training [S1].
*   **POG (Potentially Over-large Gaussians):** Allowing Gaussians to grow too large can degrade PSNR by creating redundant Gaussians in already learned areas [S5].

## Subtopics

### [First-order Spherical Harmonics Distillation](9467-first-order-spherical-harmonics-distillation.md)
First-order Spherical Harmonics (SH) Distillation reduces the parameter count and computational cost of 3D Gaussian Splatting by distilling high-fidelity third-order SH coefficients from a pretrained teacher model into a compact first-order representation for a student model. Unlike standard degree reduction which simply truncates coefficients, this method uses knowledge distillation to preserve rendering quality despite the aggressive reduction from 16 coefficients per color channel to 4. It sets itself apart from sibling methods like [RoofGS](9830-roofgs.md) or [Inverse Multiquadric Splatting](9910-inverse-multiquadric-splatting.md) by specifically targeting the appearance representation's dimensionality rather than the geometric or sorting pipeline.

### [Continuous Attenuation Model for 3D Gaussian Splatting](9624-continuous-attenuation-model-for-3d-gaussian-splatting.md)
The Continuous Attenuation Model reformulates the rasterization-based image formation of 3D Gaussian Splatting into a volumetric ray-marching framework by mapping Gaussian primitives to a continuous attenuation field $\sigma(\mathbf{x}, \mathbf{w})$. This equivalence allows the application of theoretical results from Other-at-Volume (OaV) for surface extraction, ensuring that transmittance isosurfaces remain unbiased and ellipsoidal. It distinguishes itself from prior attenuation approximations like those in GGGS [57] by enforcing geometric constraints that prevent surface erosion and multi-view inconsistency.

### RoofGS
RoofGS is an end-to-end acceleration method for 3D Gaussian Splatting (3DGS) that optimizes the rendering pipeline by aligning software strategies with hardware bottlenecks identified via the Roofline model [S1]. It solves the problem of uncoordinated optimization in 3DGS, where different stages are constrained by different resources (memory bandwidth vs. compute throughput) [S1]. It sets itself apart from generic optimization by explicitly using the Roofline model to identify the "knee" point and applying memory-centric optimizations to stages below it and compute-centric optimizations to stages near it [S1].

### [Inverse Multiquadric Splatting](9910-inverse-multiquadric-splatting.md)
Inverse Multiquadric Splatting is a radiance-field optimization technique that replaces the standard Gaussian radial basis function with an inverse multiquadric function to alter the decay profile of splats during rasterization. It differs from standard 3D Gaussian Splatting by using a slower-decaying tail, which requires a specific correction factor for the covariance matrix to maintain visual fidelity.

### [Tile-Based Comparison-Free Sorting](9991-tile-based-comparison-free-sorting.md)
Tile-Based Comparison-Free Sorting restricts depth sorting operations to individual rendering tiles to avoid global synchronization, reduce hardware complexity, and achieve fixed latency per output. Unlike full-scene sorting which causes excess traffic and latency spikes, this method uses $\langle \text{tile-id}, \text{depth} \rangle$ keys to order Gaussians front-to-back, matching the $\alpha$-blending requirement with deterministic, fixed per-output latency. It is specifically designed for hardware accelerators where variable latency and high memory overhead of radix sort are prohibitive.

### [Explicit Camera Jacobian Derivation](10077-explicit-camera-jacobian-derivation.md)
This method derives analytical Jacobians of the SE(3) camera pose with respect to 3D Gaussian primitives to enable efficient gradient-based camera tracking in SLAM systems. It solves the problem of high computational overhead associated with automatic differentiation during rasterization, ensuring minimal parameterization using Lie algebra. Unlike prior ray-intersection methods that assume fewer Gaussians, this approach is applicable to the EWA splatting and 3D Gaussian Splatting (3DGS) rendering pipeline.

### [Opacity-Independent Gaussian Truncation](10266-opacity-independent-gaussian-truncation.md)
Opacity-Independent Gaussian Truncation is a modification to the fragment culling mechanism in 3D Gaussian Splatting that decouples the visibility threshold from the Gaussian's opacity parameter. It solves the problem where the original implementation prevents consistent truncation at fewer than ~3.03 standard deviations because low-opacity Gaussians are discarded before they can receive gradients, and enforces an upper bound on the transparency threshold due to opacity reset clipping. It sets itself apart from the default 3DGS truncation by evaluating the Gaussian spatial response independently of the opacity scalar, allowing for aggressive truncation (e.g., 1σ) and enabling gradient flow for zero-opacity Gaussians.

### [ASCII-Based Data Compression](11820-ascii-based-data-compression.md)
This method accelerates data transmission during the training of 3D Gaussian Splatting models by compressing floating-point and integer values into ASCII strings. It distinguishes itself from sibling methods by targeting the I/O bottleneck of training speed rather than rendering quality or memory footprint, achieving approximately 6% training speed improvement.

### DAVIGS
DAVIGS is a plug-and-play appearance modeling method for 3D Gaussian Splatting that mitigates appearance variation-induced floaters and color distortions by transforming rendered images at the image level using 3D consistent features [S1]. Unlike coupled methods that manipulate Gaussian properties (slowing rendering) or decoupled methods that only account for mild global variations, DAVIGS decouples global view-dependent appearance variations (e.g., daylight, ISPs) from local spatial changes (e.g., street lamps) by querying multi-resolution hash grids based on back-projected 3D coordinates [S1]. It builds 3D consistency across views implicitly while maintaining real-time rendering speeds by discarding the appearance module after optimization [S1].

### [Sensitivity-Aware Vector Clustering](12167-sensitivity-aware-vector-clustering.md)
Sensitivity-Aware Vector Clustering is a compression scheme for 3D Gaussian Splatting that reduces storage requirements by clustering Spherical Harmonics (SH) coefficients and Gaussian shape features (scale and rotation) into compact codebooks using sensitivity-aware vector quantization. It differs from standard post-training quantization by deriving a sensitivity measure for each scene parameter to guide the clustering process, prioritizing the preservation of parameters that significantly affect image quality.

### Corrected Scene-Extent
A method to calculate scene extent based on the SfM point cloud rather than camera positions to avoid bias from camera distribution (e.g., orbiting a small object in a large environment) [S3]. The default 3DGS scene extent ($e_{\text{scene}}$) is proportional to the distance of the furthest camera from the average camera position, causing bias if cameras are clustered, leading to incorrect splitting/pruning [S3]. The corrected formula is $e'_{\text{scene}} = \frac{1}{N_{\text{SfM}}} \sum_{i=1}^{N_{\text{SfM}}} \|\bar{C} - p_i\|_2$, where $N_{\text{SfM}}$ is the number of SfM points, $\bar{C}$ is the averaged camera position, and $p_i$ is the i-th SfM point [S3].

### Optimization Strategy
Optimize static Gaussians for the initial 3000 iterations as a warm-up phase, then jointly optimize both the Gaussians and the deformation field [S4, unofficial]. The total loss is $\mathcal{L} = \mathcal{L}_{color} + \lambda_1 \cdot \mathcal{L}_{scales}$, where $\lambda_1 = 0.1$ [S4, unofficial]. Another loss term weight $\lambda_v = 0.2$ is also used [S4, unofficial].

### POG (Potentially Over-large Gaussians)
POG (Eq. 8) improves LPIPS slightly but degrades PSNR significantly compared to HG (Eq. 9) [S5]. POG overgrows already learned areas, making them susceptible to redundant Gaussians, which causes PSNR degradation [S5]. In Tanks&Temples ablation, POG yields PSNR 26.26, SSIM 0.879, LPIPS 0.121; HG yields PSNR 26.36, SSIM 0.880, LPIPS 0.126 [S5].

### SH Degree Zero Optimization
Setting the maximum degree of Spherical Harmonics (SH) coefficients to 0 removes superfluous operations and improves training speed, as higher-degree SH coefficients for color remain unchanged during training [S6, unofficial]. Directly changing the max degree to 0 yields a 16.25% improvement compared to the default. With specific code changes, it yields a 16.57% improvement but increases CPU-GPU process time [S6, unofficial].

### Background Color Optimization
Changing the default white background (RGB 1.0) to a gray value improves training speed while maintaining rendering quality [S6, unofficial]. The optimal range is $0.3 \le bg \le 0.5$ [S6, unofficial]. On the truck dataset with 500 training steps, setting $bg=0.4$ reduces processing time by approximately 21.85% compared to the default white background [S6, unofficial]. Extreme values may negatively impact learning rate, training loss, and PSNR states [S6, unofficial].

### Mobile-GS Rendering
Mobile-GS is a sorting-free rendering method that uses a transmittance proxy enriched with view-dependent modulation [S7, unofficial]. Pixel color $C = (1 - T) \sum_{i=1}^N \frac{c_i \alpha_i + T c_i b_g}{\sum_{i=1}^N \alpha_i w_i} + T c_i b_g$. Weight $w_i = \phi_i^2 + \frac{\phi_i}{d_i^2} + \exp \left( \frac{x_{max}}{d_i} \right)$ [S7, unofficial]. Unlike SortFreeGS which uses Gaussian depth but not scale, Mobile-GS exploits both depth and scale attributes to compute importance weight [S7, unofficial]. Unlike GES which uses a two-stage rendering pipeline, Mobile-GS is single-stage and better suited for mobile deployment [S7, unofficial].

## Operating characteristics

*   **Time Complexity:** Dominated by rasterization and sorting. Sorting is $O(N \log N)$ per tile or $O(N)$ with comparison-free sorting [S1]. Rasterization is $O(N \cdot P)$ where $N$ is Gaussians and $P$ is pixels, but optimized via tiling and culling.
*   **Memory Complexity:** $O(N \cdot D^2)$ for SH coefficients, where $D$ is SH degree. Half-precision fetches reduce register pressure and memory bandwidth usage [S1].
*   **Measured Performance:**
    *   SH Degree 0 optimization yields ~16.57% training speed improvement [S6, unofficial].
    *   Background color $bg=0.4$ yields ~21.85% processing time reduction on truck dataset [S6, unofficial].
    *   Mobile-GS achieves real-time rendering on mobile devices, outperforming SortFreeGS and GES in FPS and storage cost [S7, unofficial].
*   **Strengths:**
    *   Fast training and rendering due to efficient rasterization and parallelization [S1].
    *   High fidelity with SH coefficients [S7, unofficial].
    *   Flexible optimization strategies (warm-up, joint optimization) [S4, unofficial].
*   **Limitations:**
    *   Sensitive to scene extent calculation [S3].
    *   High memory usage for large scenes and high SH degrees [S2].
    *   POG can degrade PSNR [S5].
*   **When to Use:**
    *   When training speed is critical (use SH degree 0, optimized background) [S6, unofficial].
    *   When cameras are clustered (use corrected scene extent) [S3].
    *   When deploying on mobile devices (use Mobile-GS) [S7, unofficial].
*   **When Not to Use:**
    *   When high-fidelity view-dependent appearance is required and training time is not a constraint (use higher SH degrees) [S6, unofficial].
    *   When PSNR is the primary metric and POG is used (use HG instead) [S5].

## Background

*   **Origin:** 3D Gaussian Splatting was introduced by Kerbl et al. in 2023 [S1, S2][S6, unofficial].
*   **Development:** Subsequent works have focused on optimization efficiency (SH degree reduction, background color), large-scale rendering (volume setup, sparse convolution), and mobile deployment (Mobile-GS) [S2][S4, S6, S7, unofficial].
*   **Usage:** Widely used in novel view synthesis, 3D reconstruction, and real-time rendering applications [S1, S2][S7, unofficial].
