# 3D Gaussian Data Layout

Also called: 3DGS Parameter Storage, Gaussian Struct Definition, GaussianModel, GaussianModel PyTorch Module

## Overview
The 3D Gaussian Data Layout defines the memory organization and field definitions for a single 3D Gaussian primitive within differentiable volume rendering pipelines. It serves as the fundamental unit of storage for position, scale, orientation, opacity, and color (spherical harmonics) data, enabling efficient GPU access and optimization [S1, unofficial][S2, unofficial]. It differs from the higher-level [GaussianSet Data Structure](2074-gaussianset-data-structure.md) by focusing on the raw parameter representation rather than the container logic, and from [Gaussian Data Packing](3257-gaussian-data-packing.md) by retaining floating-point precision for optimization rather than compacting into fixed-size integer buffers for rendering [S1, unofficial][S3, unofficial].

## How it works
The layout stores per-primitive attributes in contiguous arrays to facilitate batched processing and differentiable updates. Two primary implementations exist: a Rust-based struct for rendering pipelines and a PyTorch module for optimization.

### Inputs and Outputs
*   **Input**: None for the static layout definition. For initialization, inputs may include a point cloud (XYZ, RGB) [S2, unofficial].
*   **Output**: A data structure instance containing raw parameters ready for covariance computation or rendering.

### Data Structures

#### Rust Implementation (Rendering)
Defined in [S1, unofficial], the `Gaussian` struct uses `nalgebra` types. It stores precomputed 3D covariance to avoid recomputation during rasterization.

```rust
#[derive(Clone, Debug)]
pub struct Gaussian {
    pub position: na::Vector3<f32>,  // x, y, z
    pub scale: na::Vector3<f32>,    // scale_0, scale_1, scale_2
    pub opacity: f32,               // Linear opacity [0, 1]
    pub rotation: na::Quaternion<f32>, // w, x, y, z
    pub sh: na::SVector<f32, 48>,   // Spherical Harmonics coefficients
    pub cov3d: na::Matrix3<f32>,    // 3x3 symmetric covariance matrix
}
```

*   **position**: `na::Vector3<f32>` (x, y, z).
*   **scale**: `na::Vector3<f32>` (scale_0, scale_1, scale_2). Represents linear scale factors.
*   **opacity**: `f32`. Linear opacity value.
*   **rotation**: `na::Quaternion<f32>` (w, x, y, z). Unit quaternion.
*   **sh**: `na::SVector<f32, 48>`. Stores up to degree 3 spherical harmonics.
    *   `sh_dim`: The number of coefficients depends on the degree. DC (degree 0) uses 3 coefficients. Degree 1 uses 12. Degree 2 uses 27. Degree 3 uses 48 [S1, unofficial].
*   **cov3d**: `na::Matrix3<f32>`. Precomputed 3D covariance matrix.

#### PyTorch Implementation (Optimization)
Defined in [S2, unofficial], the `GaussianModel` class stores parameters in log-space or raw tensors to ensure valid ranges during gradient descent.

*   `_xyz`: `torch.Tensor` of shape `(N, 3)`. Float tensor for positions.
*   `_features_dc`: `torch.Tensor` of shape `(N, 1, 3)`. Float tensor for 0th degree spherical harmonics (base colors).
*   `_scaling`: `torch.Tensor` of shape `(N, 3)`. Float tensor for **log-scales**.
*   `_rotation`: `torch.Tensor` of shape `(N, 4)`. Float tensor for quaternions.
*   `_opacity`: `torch.Tensor` of shape `(N, 1)`. Float tensor for **log-odds** opacity.

### Numbered Steps for Parameter Access

When accessing parameters from the PyTorch optimization layout [S2, unofficial]:

1.  **Get Scaling**: Compute linear scale from log-space.
    $$ \text{scale} = \text{clamp}(\exp(\text{self._scaling}), \text{max}=10.0) $$
    This converts log-space scaling to linear space with an upper bound of 10.0.
2.  **Get Rotation**: Normalize the quaternion.
    $$ \text{rotation} = \text{normalize}(\text{self._rotation}) $$
    This ensures quaternions are unit-length.
3.  **Get Opacity**: Convert log-odds to probability.
    $$ \text{opacity} = \sigma(\text{self._opacity}) = \frac{1}{1 + e^{-\text{self._opacity}}} $$
    This converts log-odds to probability space $[0, 1]$.

### Initialization from Point Cloud
To create a `GaussianModel` from a COLMAP point cloud [S2, unofficial]:
1.  Input `xyz`: `(N, 3)` numpy array of 3D points.
2.  Input `rgb`: `(N, 3)` numpy array of colors, values between 0 and 1.
3.  Initialize `_xyz` with `xyz`.
4.  Initialize `_features_dc` with `rgb`.
5.  Initialize `_scaling`, `_rotation`, and `_opacity` with default zeros or small random values (implementation details for initialization body are not fully specified in the source, but gradients are applied to these tensors) [S2, unofficial][G].

### Edge Cases and Pitfalls
*   **Quaternion Normalization**: Quaternions must be normalized after every update step to remain valid rotations [S2, unofficial].
*   **Scale Clamping**: Exponential scaling can explode; an upper bound (e.g., 10.0) is applied to prevent numerical instability [S2, unofficial].
*   **Opacity Range**: Log-odds initialization should avoid extreme values that saturate the sigmoid function immediately [S2, unofficial].
*   **SH Dimension**: The size of the `sh` vector must match the active spherical harmonics degree. Using degree 3 requires 48 coefficients, while degree 0 requires only 3 [S1, unofficial].

## Subtopics

### [Gaussian Data Structure](2273-gaussian-data-structure.md)
The Gaussian Data Structure is the primary in-memory container for 3D Gaussian primitives in differentiable volume rendering pipelines, organizing per-primitive attributes into contiguous arrays for efficient GPU access and optimization. It differs from the raw 3D Gaussian Data Layout by providing a flat, list-based abstraction that facilitates dynamic resizing and batched processing, distinct from the tightly packed bit-level formats of [Gaussian Data Packing](3257-gaussian-data-packing.md).

### [Gaussian Data Packing](3257-gaussian-data-packing.md)
Gaussian Data Packing is a method for compacting 3D Gaussian Splatting primitives into a dense, GPU-friendly binary buffer for efficient rendering and sorting. It solves the problem of memory alignment and bandwidth efficiency by interleaving position, covariance, and color data into a fixed-size `uint32_t` array, while storing raw floating-point positions in a separate parallel buffer. It is distinguished from its sibling [Gaussian Data Structure](2273-gaussian-data-structure.md) by its specific bit-packing strategy for covariance matrices and its separation of position data into integer-reinterpreted and raw float formats.

### GeometryState Allocation
GeometryState contains contiguous memory blocks for P Gaussians, used during the rasterization phase. The layout includes:
*   `depths`: `float`, size P.
*   `clamped`: `float`, size P*3.
*   `internal_radii`: `float`, size P.
*   `means2D`: `float`, size P.
*   `cov3D`: `float`, size P*6 (symmetric 3x3 matrix stored as 6 elements).
*   `conic_opacity`: `float`, size P.
*   `rgb`: `float`, size P*3.
*   `tiles_touched`: `uint32_t`, size P.
*   `scanning_space`: Variable size, allocated via `cub::DeviceScan::InclusiveSum`.
*   `point_offsets`: `uint32_t`, size P [S3, unofficial].

## Operating characteristics
*   **Memory**: The Rust struct [S1, unofficial] uses approximately $3 \times 4 + 3 \times 4 + 4 + 4 \times 4 + 48 \times 4 + 9 \times 4 = 12 + 12 + 4 + 16 + 192 + 36 = 272$ bytes per Gaussian (assuming `Quaternion` is 4 floats and `Matrix3` is 9 floats, though `nalgebra` may have alignment padding). The PyTorch layout [S2, unofficial] stores parameters in separate tensors, which may incur overhead due to tensor metadata and potential fragmentation if not managed carefully.
*   **Performance**: Contiguous memory layout (as in Rust struct) facilitates efficient GPU access and vectorized operations [S1, unofficial]. The PyTorch layout [S2, unofficial] is optimized for gradient computation and dynamic resizing during training.
*   **Scalability**: The layout supports N Gaussians. The `scanning_space` in GeometryState [S3, unofficial] scales with P, requiring dynamic allocation.
*   **Strengths**: Simple, direct mapping to mathematical parameters. Precomputed covariance (Rust) saves computation during rendering. Log-space parameters (PyTorch) stabilize optimization.
*   **Limitations**: High memory usage for high-degree spherical harmonics (48 floats per Gaussian). Not optimized for bandwidth during rendering compared to packed formats [S3, unofficial].

## Background
The 3D Gaussian Data Layout originates from the 3D Gaussian Splatting (3DGS) framework for differentiable volume rendering. The Rust implementation [S1, unofficial] is part of an unofficial repository (`thomasantony/splat`) demonstrating efficient rendering pipelines. The PyTorch implementation [S2, unofficial] is part of `metin-yat/mini-splat`, providing a minimal optimization setup. The GeometryState layout [S3, unofficial] is from `NorahCadeJS/GAI-GS`, integrating CUDA-specific optimizations. These implementations adapt the core 3DGS primitives for specific hardware and software constraints.
