# Gaussian Data Structure

Also called: GaussianList

## Overview
The Gaussian Data Structure is the primary in-memory container for 3D Gaussian primitives in differentiable volume rendering pipelines, organizing per-primitive attributes into contiguous arrays for efficient GPU access and optimization [S1, unofficial]. It differs from the raw [3D Gaussian Data Layout](2242-3d-gaussian-data-layout.md) by providing a flat, list-based abstraction that facilitates dynamic resizing and batched processing, distinct from the tightly packed bit-level formats of [Gaussian Data Packing](3257-gaussian-data-packing.md).

## How it works
**Inputs:** A collection of $N$ 3D Gaussian primitives, each defined by position, scale, rotation, opacity, and spherical harmonics (SH) coefficients.
**Outputs:** A structured data object containing contiguous buffers for all primitive attributes, ready for rendering or gradient-based optimization.

**Data Structures:**
The structure consists of two main views: the logical `Gaussian` struct and the physical `GaussianList` container [S1, unofficial].

1.  **Gaussian Struct (Logical Primitive):**
    *   `position`: `Vector3<f32>` (3 floats: $x, y, z$)
    *   `scale`: `Vector3<f32>` (3 floats: $s_x, s_y, s_z$)
    *   `opacity`: `f32` (1 float)
    *   `rotation`: `Quaternion<f32>` (4 floats: $w, x, y, z$)
    *   `sh`: `SVector<f32, 48>` (48 floats, max for degree 3)
    *   `cov3d`: `Matrix3<f32>` (9 floats, symmetric positive definite covariance matrix)

2.  **GaussianList Struct (Physical Container):**
    *   `positions`: `Matrix4xX<f32>` (Size $4 \times N$). Stores $x, y, z$ in rows 0-2; row 3 is unused/padding.
    *   `scales`: `Matrix3xX<f32>` (Size $3 \times N$). Stores $s_x, s_y, s_z$ in rows 0-2.
    *   `opacities`: `DVector<f32>` (Size $N$).
    *   `rotations`: `Matrix4xX<f32>` (Size $4 \times N$). Stores quaternion components $w, x, y, z$ in rows 0-3.
    *   `sh`: `Matrix48xX<f32>` (Size $48 \times N$). Flat array of SH coefficients.
    *   `num_gaussians`: `usize` (Count $N$).
    *   `cov3d`: `Matrix3xX<f32>` (Size $3 \times N$). Stores the 9 elements of the symmetric $3 \times 3$ matrix.

**SH Coefficient Layout:**
The SH coefficients are stored in a flat array of size 48 (for maximum degree 3). The layout interleaves color channels per degree: $C0_R, C0_B, C0_G, C1_R, C1_B, C1_G, \dots$ [S1, unofficial].

**Steps to Construct GaussianList from Primitives:**
1.  Initialize $N$ primitives.
2.  Allocate buffers in `GaussianList` based on $N$.
3.  Iterate through each primitive $i$ from $0$ to $N-1$:
    a.  Write `position[i]` to `positions` at indices $i, i+N, i+2N$.
    b.  Write `scale[i]` to `scales` at indices $i, i+N, i+2N$.
    c.  Write `opacity[i]` to `opacities` at index $i$.
    d.  Write `rotation[i]` (quaternion) to `rotations` at indices $i, i+N, i+2N, i+3N$.
    e.  Write `sh[i]` (48 floats) to `sh` at indices $i$ to $i+47N$ (strided by $N$).
    f.  Compute `cov3d[i]` from `scale` and `rotation` if not precomputed, and write to `cov3d` buffer.
4.  Set `num_gaussians = N`.

**Edge Cases and Pitfalls:**
*   **SH Degree:** The buffer size for SH is fixed at 48 (degree 3). If lower degrees are used, the remaining coefficients are zero-padded [S1, unofficial].
*   **Covariance Storage:** The exact mapping of the 9 elements of the $3 \times 3$ covariance matrix into the `Matrix3xX` buffer is not explicitly detailed in the sources beyond the type name. Implementers should verify if this stores the full matrix (requiring 9 rows) or a compressed form [G].
*   **Precision:** All attributes are stored as `f32` (32-bit float).

### [Dynamic Buffer Management](3753-dynamic-buffer-management.md)
Dynamic Buffer Management handles the lifecycle of 3D Gaussian splat data structures during training by automatically resizing memory buffers when the number of active Gaussians exceeds current capacity. It solves the problem of frequent reallocation and data copying overhead by using a fixed over-allocation factor, differing from static allocation by adapting to scene complexity and from CUDA Virtual Memory management by relying on standard buffer reallocation rather than virtual memory mapping.

### Learnable Scale Modulation for Primitive Compactness
A technique that introduces a learnable per-Gaussian scalar factor to reparameterize effective Gaussian scales, providing an optimization pathway for adapting primitive extent while retaining existing tile-culling rules [S3, unofficial].
*   **Step:** Initialize a learnable scalar $\beta_i \in \mathbb{R}$ to zero for each Gaussian primitive. Optimize $\beta_i$ jointly with other Gaussian attributes using the Adam optimizer [S3, unofficial].
*   **Formula:** The effective 2D covariance is modulated: $\tilde{\Sigma}_i^{2D} = \gamma_i^2 \Sigma_i^{2D}$, where $\gamma_i = \text{sigmoid}(\beta_i)$ [S3, unofficial]. The gradient of the scale factor is $\frac{\partial \gamma_i}{\partial \beta_i} = 2 \cdot \text{sigmoid}(\beta_i) \cdot (1 - \text{sigmoid}(\beta_i))$ [S3, unofficial].
*   **Comparison:** Unlike vanilla 3DGS where covariance is fixed by base scales $S_i$ and rotation $R_i$, this method scales the covariance by $\gamma_i^2$, changing the overall extent while keeping anisotropic axis ratios governed by the base scales [S3, unofficial].

### Splat Data Buffer Layout
*   **Step:** `fromSplats` iterates over a collection of Splat objects, extracts each parameter via getters, and writes them into the corresponding FloatBuffer at indices $i \times \text{stride} + \text{component}$ [S4, unofficial].
*   **Layout:** SplatData stores splat parameters in separate contiguous FloatBuffers: positions (size $N \times 3$), scales (size $N \times 3$), rotations (size $N \times 4$), opacities (size $N$), and spherical harmonics (size $N \times \text{shDimensions} \times 3$) [S4, unofficial].

### Log-Scale Storage
*   **Step:** Scales are stored internally in log-space. When writing to buffers, linear values are converted to log-space via $\log()$. When reading for rendering or optimization, log-space values are converted to linear via $\exp()$ [S4, unofficial].
*   **Formula:** Linear scale is recovered from stored log-scale: $s_{\text{linear}} = \exp(s_{\text{log}})$ [S4, unofficial].

### Spherical Harmonics Coefficient Layout
*   **Step:** Nested loops iterate over splat index $i$ and coefficient index $d$. For each coefficient, the $x, y, z$ components are written to buffer indices $((i \times \text{shDimensions}) + d) \times 3 + 0, +1, +2$ [S4, unofficial].
*   **Parameter:** $\text{shDimensions}$: Total number of SH coefficients for a given degree, calculated via `Splats.dimensionsForDegree(shDegree)` [S4, unofficial].
*   **Layout:** SH coefficients are stored in a FloatBuffer of size $N \times \text{shDimensions} \times 3$. The memory order is grouped by splat, then by coefficient index, then by spatial dimension ($x, y, z$) [S4, unofficial].

## Operating characteristics
*   **Time Complexity:** Construction is $O(N)$ where $N$ is the number of Gaussians. Access is $O(1)$ per attribute due to contiguous memory layout.
*   **Memory Complexity:** $O(N \times C)$ where $C$ is the constant size of attributes per Gaussian (approx. 60-70 floats for degree 3 SH).
*   **Performance:** Contiguous buffers enable efficient vectorized memory access on GPUs, critical for the high-throughput rendering of millions of Gaussians.
*   **Strengths:** Simple to implement, compatible with standard GPU memory allocators, easy to resize dynamically.
*   **Limitations:** Fixed SH size (48) may waste memory for lower degrees. Covariance storage layout ambiguity may require implementation-specific decisions.
*   **When to Use:** General-purpose 3DGS training and rendering where dynamic primitive counts are expected.
*   **When Not to Use:** When memory bandwidth is extremely constrained and bit-packing (see [Gaussian Data Packing](3257-gaussian-data-packing.md)) is required.

## Background
The Gaussian Data Structure, often referred to as `GaussianList`, is a foundational component in 3D Gaussian Splatting implementations, particularly in open-source projects like `splat` by Thomas Antony [S1, unofficial]. It emerged as a practical abstraction to manage the large number of Gaussian primitives generated during the optimization process, allowing for efficient data transfer between CPU and GPU and supporting dynamic operations like densification and pruning.
