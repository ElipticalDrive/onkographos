# Grendel-GS
Also called: Out-of-core and distributed optimization for 3DGS
## Overview
Grendel-GS is an out-of-core and distributed optimization method for 3D Gaussian Splatting that partitions the Gaussian list across multiple GPUs [S1, unofficial]. It solves the memory bottleneck of training large scenes by allowing each GPU to render its own subset of Gaussians and combining results via inter-GPU communication at partition boundaries [S1, unofficial]. It differs from single-GPU out-of-core methods like CLM by leveraging distributed hardware, and from sibling methods like MaskGaussian Gradient Computation by focusing on spatial partitioning rather than gradient masking [S1, unofficial].
## How it works
Inputs: A list of 3D Gaussians (position, covariance, opacity, SH coefficients) and a set of training views.
Outputs: Optimized Gaussian parameters.

Data Structures:
- Gaussian List: Partitioned into $N$ chunks, one per GPU.
- Communication Buffer: Stores intermediate rendering results (color, depth, or gradients) at partition boundaries for aggregation.

Steps:
1. Partition the global Gaussian list into $N$ subsets, assigning one subset to each GPU in the cluster [S1, unofficial].
2. For each training iteration:
   a. Each GPU renders the scene using only its assigned subset of Gaussians [S1, unofficial].
   b. GPUs communicate intermediate results (e.g., color contributions or gradients) at partition boundaries to ensure consistent global gradients [S1, unofficial].
   c. Each GPU updates its local subset of Gaussians using the aggregated gradients [S1, unofficial].
3. Repeat until convergence.

Parameters:
- Number of GPUs ($N$): Determined by available hardware and scene size.
- Partitioning Strategy: Spatial or list-based partitioning. Not given in the sources.

Edge Cases:
- Boundary Artifacts: Inconsistent gradients at partition boundaries if communication is not handled correctly.
- Load Imbalance: Uneven distribution of Gaussians or view complexity across GPUs.

Pseudocode:
```python
# Pseudocode for Grendel-GS distributed optimization
# Assumes N GPUs, each with rank r in [0, N-1]

def initialize_gaussians(global_gaussians):
    # Partition global list into N subsets
    local_gaussians = partition(global_gaussians, rank)
    return local_gaussians

def render_subset(local_gaussians, camera_params):
    # Render scene using only local Gaussians
    color, depth, gradients = rasterize(local_gaussians, camera_params)
    return color, depth, gradients

def communicate_gradients(local_gradients, neighbor_gradients):
    # Exchange gradients at partition boundaries
    # This step ensures global consistency
    aggregated_gradients = aggregate(local_gradients, neighbor_gradients)
    return aggregated_gradients

def update_gaussians(local_gaussians, aggregated_gradients):
    # Update local Gaussians using aggregated gradients
    local_gaussians = optimizer_step(local_gaussians, aggregated_gradients)
    return local_gaussians

def train():
    local_gaussians = initialize_gaussians(global_gaussians)
    for epoch in range(num_epochs):
        for view in training_views:
            color, depth, local_gradients = render_subset(local_gaussians, view)
            aggregated_gradients = communicate_gradients(local_gradients)
            local_gaussians = update_gaussians(local_gaussians, aggregated_gradients)
    return local_gaussians
```
## Subtopics

### TideGS
TideGS is a fully out-of-core optimization method that pushes the frontier to over one billion primitives by streaming Gaussians from disk in a view-dependent order, training on a single machine with only a fraction of the data in GPU memory [S1, unofficial]. It differs from Grendel-GS by operating on a single machine and using disk streaming rather than distributed GPU memory partitioning. Choose TideGS when hardware is limited to a single machine but scene size exceeds GPU memory significantly.

## Operating characteristics
Time Complexity: Linear with respect to the number of Gaussians and views, but with reduced memory footprint.
Memory Complexity: $O(1)$ per GPU for Grendel-GS (constant per partition), $O(1)$ for TideGS (constant in GPU memory).
Measured Performance: Not given in the sources.
Scaling: Scales with the number of GPUs for Grendel-GS. TideGS scales with disk I/O speed.
Strengths: Enables training of billion-primitive scenes.
Limitations: Communication overhead for Grendel-GS; I/O bottleneck for TideGS.
When to use: Large-scale scenes exceeding single-GPU memory.
When not to use: Small scenes where single-GPU training is sufficient.
## Background
Origin: Grendel-GS and TideGS are recent developments in 3D Gaussian Splatting optimization, as surveyed in [S1, unofficial].
History: Part of the ongoing effort to scale 3DGS to larger scenes.
Usage: Used in large-scale 3D reconstruction and dynamic scene modeling.
