# Locality-preserving Densification

Also called: Z-ordering for Gaussians

## Overview
Locality-preserving densification addresses the memory access throttling caused by the standard densification process in 3D Gaussian Splatting, where new primitives are appended to the end of parameter buffers, causing spatially close Gaussians to be stored far apart in memory [S1, unofficial]. By reordering Gaussians in parameter buffers based on their 3D spatial proximity using Z-ordering (Morton order), this method ensures that neighboring Gaussians in 3D space are also close in memory, thereby improving memory access coalescing [S1, unofficial]. It sets itself apart from sibling methods like Score-based Densification by focusing on the data layout and memory efficiency rather than the criteria for splitting or cloning primitives [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** The current set of $N$ Gaussians $\mathcal{G} = \{\mathcal{G}_1, \dots, \mathcal{G}_N\}$, where each Gaussian $\mathcal{G}_i$ has a 3D mean position $\mathbf{p}_i \in \mathbb{R}^3$. The Gaussians are stored in contiguous GPU buffers.
*   **Output:** A permutation of the Gaussian indices such that the spatial locality of the Gaussians is preserved in the memory layout.

**Data Structures:**
*   **Gaussian Buffer:** A contiguous array of structures containing Gaussian parameters (position, covariance, opacity, etc.). The size is dynamic but pre-allocated to handle densification.
*   **Index Array:** An array of integers mapping the logical order of Gaussians to their physical position in the buffer.

**Steps:**
1.  **Trigger Check:** Determine if the current training iteration $t$ satisfies the condition for applying Z-ordering. The method is applied only when densification is active and at regular intervals.
2.  **Compute Z-order Keys:** For each Gaussian $\mathcal{G}_i$ with mean $\mathbf{p}_i = (x_i, y_i, z_i)$, compute a Morton code (Z-order key) $k_i$. The Morton code interleaves the bits of the integer coordinates of $\mathbf{p}_i$.
    *   Let $x'_i, y'_i, z'_i$ be the integer coordinates of $\mathbf{p}_i$ after quantization and offsetting to non-negative values.
    *   $k_i = \text{interleave}(x'_i, y'_i, z'_i)$.
3.  **Sort:** Sort the Gaussians based on their Morton codes $k_i$. This can be done using a radix sort or a standard comparison sort on the keys.
4.  **Reorder Buffers:** Permute the data in the Gaussian parameter buffers according to the sorted order. This ensures that Gaussians with similar Morton codes (and thus similar 3D positions) are stored in adjacent memory locations.
5.  **Update Indices:** Update any index arrays or pointers that reference the Gaussians to reflect the new memory layout.

**Parameters:**
*   **Frequency:** Z-ordering is applied every 5000 iterations [S1, unofficial].
*   **Quantization:** The precision of the Morton code depends on the quantization of the 3D coordinates. Not given in the sources.

**Pitfalls:**
*   **Atomic Contention:** Z-ordering performs effectively only when used with the per-Gaussian backward pass. If the original backward pass with numerous atomic operations is used, Z-ordering can heighten atomic contention [S1, unofficial].
*   **False Sharing:** Repeated Z-ordering can slow down training when the number of Gaussians is small due to a massive increase in atomic contention in the alpha blending backward pass (false sharing) [S1, unofficial].
*   **Computational Cost:** While efficient, Z-ordering adds computational overhead. It costs approximately 4 ms per million Gaussians [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The sorting step dominates the complexity, typically $O(N \log N)$ for comparison sorts or $O(N)$ for radix sort, where $N$ is the number of Gaussians. The computational cost is approximately 4 ms per million Gaussians [S1, unofficial].
*   **Memory Complexity:** $O(N)$ for storing the Morton codes and the permutation indices.
*   **Performance:** Reduces warp divergence and cache misses, resulting in faster training when scenes contain many Gaussians [S1, unofficial]. It reduces memory access costs by ensuring coalesced memory accesses [S1, unofficial].
*   **Strengths:** Improves memory access patterns, leading to significant speedups in training for large scenes. It is computationally efficient compared to other optimization techniques [S1, unofficial].
*   **Limitations:** Can increase atomic contention if not used with the per-Gaussian backward pass. May slow down training for small numbers of Gaussians due to false sharing [S1, unofficial]. Frequent application has diminishing returns [S1, unofficial].
*   **When to Use:** Use when training scenes with a large number of Gaussians and when using the per-Gaussian backward pass. It is particularly beneficial for outdoor scenes which tend to create more Gaussians (e.g., 3.8M vs 1.3M for indoor scenes) [S1, unofficial].
*   **When Not to Use:** Avoid if the number of Gaussians is small, as the overhead may outweigh the benefits. Do not use with the original backward pass that relies heavily on atomic operations [S1, unofficial].

## Background
Locality-preserving densification, also known as Z-ordering for Gaussians, was introduced in the "Faster-GS" paper to improve the optimization speed of 3D Gaussian Splatting [S1, unofficial]. The authors observed that memory layout became a throttling factor during densification, as new Gaussians were added to the end of parameter buffers, causing spatially close Gaussians to be far apart in memory [S1, unofficial]. The method was developed to address this issue by reordering Gaussians based on their 3D spatial proximity [S1, unofficial]. It is part of a broader effort to optimize the training pipeline of 3D Gaussian Splatting, including fusing backward and optimizer steps [S1, unofficial].
