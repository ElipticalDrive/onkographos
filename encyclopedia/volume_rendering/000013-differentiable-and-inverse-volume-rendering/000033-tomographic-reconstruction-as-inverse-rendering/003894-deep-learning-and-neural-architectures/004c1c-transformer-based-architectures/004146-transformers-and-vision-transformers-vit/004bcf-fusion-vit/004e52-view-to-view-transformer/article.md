# View-to-View Transformer

Also called: V2V Transformer, Encoder-Decoder Multi-View Transformer

## Overview
The View-to-View Transformer is a neural module designed to fuse multi-view image features and predict view-dependent appearance for volume rendering or radiance field reconstruction [S1]. It solves the problem of multi-view inconsistency and limited feature representation power in existing methods by leveraging an encoder-decoder architecture that performs self-attention across input views and cross-attention between input views and a query viewpoint [S1]. Unlike standard fusion methods that rely on low-resolution feature maps or simple pooling, this transformer directly ingests high-resolution raw RGB values, enabling robust geometry inference and high-fidelity rendering even in the presence of calibration errors [S1].

## How it works
The method operates on a 3D query point $x$ and a set of $K$ input images $I_1, \dots, I_n$ with known camera poses. The output is a view-dependent color feature $e_c$ and subsequently a color value $c$ for the query point in a specific query direction $d_q$ [S1].

### Data Structures and Inputs
1.  **Input Images**: $I_i \in \mathbb{R}^{H \times W \times 3}$ for $i=1 \dots n$.
2.  **Pixel-aligned Features**: $\phi_i(x, I_i)$, obtained by projecting the 3D point $x$ onto the 2D image plane of view $i$ and sampling the feature map. In the high-resolution variant, these are derived directly from raw RGB values [S1].
3.  **Viewing Directions**: $d_i$, the direction from the camera center to $x$ in the coordinate system of view $i$ [S1].
4.  **Query Direction**: $d_q$, the direction of the query viewpoint relative to the point $x$ [S1].
5.  **Double Embedding**: $e_{db}$, a shared geometry-appearance embedding generated by a preceding surface/radiance field module (e.g., DoubleField) [S1].
6.  **Colored Encoding**: $\gamma(p_i)$, a positional-style encoding mapping raw RGB values $p_i$ to a higher-dimensional space to capture high-frequency appearance variations [S1].

### Formulas and Steps

**1. Initial Feature Aggregation (Pre-Transformer)**
For each view $i$, combine the pixel-aligned feature and viewing direction:
$$ \Phi_i = \oplus(\phi_i(x, I_i), d_i) $$
where $\oplus$ denotes concatenation [S1].

**2. Encoder: Multi-View Feature Fusion**
The encoder fuses features from all $n$ input views using self-attention.
1.  Compute Query, Key, and Value matrices using linear layers $F_{Q,K,V}$:
    $$ Q_e, K_e, V_e = F_{Q,K,V}(\phi_1, \dots, \phi_n) $$
    *Note: The source uses $\phi$ here, implying the input to the attention mechanism is the set of pixel-aligned features [S1].*
2.  Apply Multi-Head Attention:
    $$ \text{Att}_{out} = \text{Att}(Q_e, K_e, V_e) $$
3.  Apply Feed-Forward Network $F_e$:
    $$ \Phi = F_e(\text{Att}_{out}) $$
    The result $\Phi$ is the fused multi-view feature representation [S1].

**3. Double Embedding Generation**
The fused feature $\Phi$ and the 3D position $x$ (encoded via $\gamma(x)$) are passed through a Double MLP $E_{db}$ to generate the double embedding $e_{db}$:
$$ e_{db} = E_{db}(\gamma(x), \Phi) $$
This embedding bridges the surface and radiance fields [S1].

**4. Decoder: View-Dependent Feature Prediction**
The decoder predicts the color embedding $e_c$ using cross-attention between the query view and the input views.
1.  **Query Generation**: Map the query direction $d_q$ to a query vector:
    $$ Q_d = F_{Q_d}(d_q) $$
2.  **Key Generation**: Map the viewing directions of all input views $d_1, \dots, d_n$ to key vectors:
    $$ K_d = F_{K_d}(d_1, \dots, d_n) $$
3.  **Value Generation**: Construct value vectors by concatenating the double embedding $e_{db}$ with the colored encoding of the raw RGB values $\gamma(p_i)$ for each view:
    $$ V_d = F_{V_d}([e_{db}, \gamma(p_1)], \dots, [e_{db}, \gamma(p_n)]) $$
    Here, $[ \cdot, \cdot ]$ denotes concatenation. The raw RGB values $p_i$ are used to preserve high-frequency details [S1].
4.  **Cross-Attention**: Apply Multi-Head Attention:
    $$ \text{Att}_{cross} = \text{Att}(Q_d, K_d, V_d) $$
5.  **Feed-Forward**: Apply feed-forward network $F_d$:
    $$ e_c = F_d(\text{Att}_{cross}) $$
    The result $e_c$ is the view-dependent color embedding [S1].

**5. Color Prediction**
The final color $c$ is predicted by a texture MLP $E_c$:
$$ c = E_c(e_c) $$

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

class ViewToViewTransformer(nn.Module):
    def __init__(self, dim_in, dim_hidden, num_heads, num_layers_encoder=1, num_layers_decoder=1):
        super().__init__()
        # Encoder components
        self.encoder_attn = nn.MultiheadAttention(dim_hidden, num_heads)
        self.encoder_ffn = nn.Sequential(
            nn.Linear(dim_hidden, dim_hidden * 4),
            nn.ReLU(),
            nn.Linear(dim_hidden * 4, dim_hidden)
        )
        self.encoder_proj = nn.Linear(dim_in, dim_hidden)
        
        # Decoder components
        self.decoder_attn = nn.MultiheadAttention(dim_hidden, num_heads)
        self.decoder_ffn = nn.Sequential(
            nn.Linear(dim_hidden, dim_hidden * 4),
            nn.ReLU(),
            nn.Linear(dim_hidden * 4, dim_hidden)
        )
        
        # Linear layers for Q, K, V projections
        self.fc_q_e = nn.Linear(dim_hidden, dim_hidden)
        self.fc_k_e = nn.Linear(dim_hidden, dim_hidden)
        self.fc_v_e = nn.Linear(dim_hidden, dim_hidden)
        
        self.fc_q_d = nn.Linear(dim_hidden, dim_hidden) # For d_q
        self.fc_k_d = nn.Linear(dim_hidden, dim_hidden) # For d_i
        self.fc_v_d = nn.Linear(dim_hidden * 2, dim_hidden) # For [e_db, gamma(p)]
        
        # Positional/Colored encoding functions (assumed external or defined elsewhere)
        # gamma_pos: 3D position -> dim_hidden
        # gamma_rgb: RGB value -> dim_hidden
        
    def forward(self, phi_list, d_list, d_q, e_db, p_list, gamma_pos, gamma_rgb):
        """
        phi_list: List of tensors [phi_1, ..., phi_n], each shape [B, C_phi]
        d_list: List of tensors [d_1, ..., d_n], each shape [B, C_d]
        d_q: Query direction tensor, shape [B, C_d]
        e_db: Double embedding tensor, shape [B, C_e]
        p_list: List of raw RGB values [p_1, ..., p_n], each shape [B, 3]
        gamma_pos: Function to encode 3D position x (not explicitly passed in args but used in e_db generation externally)
        gamma_rgb: Function to encode RGB values
        """
        n = len(phi_list)
        
        # --- Encoder: Self-Attention over Input Views ---
        # 1. Project features to hidden dim
        # Note: Source implies phi_i are the inputs to attention. 
        # We assume phi_list elements are already projected or we project them here.
        # Let's assume phi_list elements are [B, C_phi] and need projection to dim_hidden.
        # If dim_in != dim_hidden, we project.
        phi_proj_list = [self.encoder_proj(phi) for phi in phi_list]
        phi_stack = torch.stack(phi_proj_list, dim=1) # [B, N, D]
        
        # 2. Generate Q, K, V for encoder
        Q_e = self.fc_q_e(phi_stack)
        K_e = self.fc_k_e(phi_stack)
        V_e = self.fc_v_e(phi_stack)
        
        # 3. Multi-head attention
        # Source: Att(Q_e, K_e, V_e)
        # Assuming standard multi-head attention where Q, K, V are [B, N, D]
        attn_out_e, _ = self.encoder_attn(Q_e, K_e, V_e)
        
        # 4. Feed-forward
        Phi = self.encoder_ffn(attn_out_e) # [B, N, D]
        
        # Note: The source equation Phi = F_e(Att(...)) suggests the output of the encoder
        # is the fused feature. In many implementations, this might be averaged or pooled
        # to a single vector per point if the point x is the same for all views.
        # However, the decoder takes V_d constructed from [e_db, gamma(p_i)], implying
        # the decoder attends to specific view properties.
        # The source says "Phi ... will be fed into the double MLP ... to generate e_db".
        # So Phi is likely aggregated (e.g., mean) before e_db generation.
        # But for the transformer module itself, we return the processed features.
        # Let's assume Phi is aggregated to [B, D] for the next step (e_db generation).
        Phi_fused = Phi.mean(dim=1) # [B, D]
        
        # --- Intermediate Step: Double Embedding ---
        # This step is technically outside the transformer but required for Decoder input.
        # e_db = E_db(gamma(x), Phi_fused)
        # We assume e_db is passed in as an argument for this function.
        
        # --- Decoder: Cross-Attention between Query and Input Views ---
        
        # 1. Query from d_q
        # d_q shape [B, C_d]. Need to project to dim_hidden.
        # Assuming d_q is already in a compatible space or projected.
        # Let's assume a linear layer for d_q projection exists or use a shared one.
        # Source: Q_d = F_Qd(d_q)
        Q_d = self.fc_q_d(d_q) # [B, D]
        
        # 2. Keys from d_i
        # d_list contains d_1...d_n.
        d_stack = torch.stack(d_list, dim=1) # [B, N, C_d]
        # Project d_i to dim_hidden
        # Source: K_d = F_Kd(d_1, ..., d_n)
        # We need a projection layer for directions.
        # Let's assume fc_k_d handles the projection from C_d to D.
        K_d = self.fc_k_d(d_stack) # [B, N, D]
        
        # 3. Values from [e_db, gamma(p_i)]
        # e_db is [B, C_e]. gamma(p_i) is [B, D] (output of colored encoding).
        # Concatenate them: [B, C_e + D].
        # Source: V_d = F_Vd([e_db, gamma(p_1)], ..., [e_db, gamma(p_n)])
        
        val_list = []
        for i in range(n):
            p_i = p_list[i] # [B, 3]
            gamma_p_i = gamma_rgb(p_i) # [B, D]
            # Concatenate e_db and gamma(p_i)
            # e_db is same for all views in this context? Source says [e_db, gamma(p_i)].
            # Yes, e_db is per-point, gamma(p_i) is per-view.
            val_input = torch.cat([e_db, gamma_p_i], dim=-1) # [B, C_e + D]
            val_list.append(val_input)
            
        val_stack = torch.stack(val_list, dim=1) # [B, N, C_e + D]
        
        # Project to dim_hidden
        V_d = self.fc_v_d(val_stack) # [B, N, D]
        
        # 4. Cross-Attention
        # Q_d is [B, D], K_d is [B, N, D], V_d is [B, N, D]
        # Expand Q_d to match sequence length for attention? 
        # Standard MultiheadAttention expects Q, K, V to have sequence dim.
        # Q_d represents the query point's view. It attends to N input views.
        # So Q_D should be [B, 1, D] or [B, D] depending on implementation.
        # Let's assume [B, 1, D] for clarity.
        Q_d_expanded = Q_d.unsqueeze(1) # [B, 1, D]
        
        attn_out_d, _ = self.decoder_attn(Q_d_expanded, K_d, V_d) # [B, 1, D]
        
        # 5. Feed-forward
        e_c = self.decoder_ffn(attn_out_d.squeeze(1)) # [B, D]
        
        return e_c
```

### Edge Cases and Pitfalls
*   **Calibration Errors**: The transformer is designed to be robust to geometry inference and calibration errors in real-world multi-view setups by learning attention relationships rather than relying on strict geometric projection [S1].
*   **High-Resolution Cost**: Directly using high-resolution images increases training time. The source suggests a two-phase approach: low-resolution large-scale pre-training and high-resolution fine-tuning [S1].
*   **Feature Alignment**: Pixel-aligned features $\phi_i(x, I_i)$ require accurate camera intrinsics and extrinsics for projection. Misalignment can degrade performance, though attention helps mitigate this [S1].

## Subtopics

### [Multi-View Feature Encoder](13802-multi-view-feature-encoder.md)
Aggregates information from $K$ input images to construct a target volume encoding appearance and geometry. It sets itself apart by combining a per-image 2D CNN with a joint multi-view Transformer and explicitly quantifying multi-view consistency via pairwise cosine similarities. Choose this when efficient 3D context modeling is needed without full 3D CNNs.

## Operating characteristics
*   **Time Complexity**: The transformer involves self-attention and cross-attention operations, which are $O(N^2)$ with respect to the number of views $N$ for the attention mechanism. The encoder processes $N$ views, and the decoder processes $N$ views against 1 query.
*   **Memory Complexity**: Stores features for $N$ views. High-resolution inputs increase memory usage significantly, necessitating the pre-training/fine-tuning strategy [S1].
*   **Strengths**: Handles multi-view inconsistency; robust to calibration errors; utilizes high-resolution raw RGB for high-fidelity rendering; disentangles geometry and appearance [S1].
*   **Limitations**: Expensive training time on high-resolution domains; requires multi-view inputs with known poses [S1].
*   **When to use**: High-fidelity human reconstruction and rendering where multi-view consistency is challenging and high-resolution details are critical [S1].

## Background
The View-to-View Transformer was introduced in the **DoubleField** framework by [S1] in 2022. It was developed to bridge neural surface and radiance fields for high-fidelity human reconstruction. The method addresses limitations in previous approaches that relied on low-resolution feature maps or lacked robustness to multi-view inconsistency. It builds on the concept of using transformers for feature fusion, extending it to an encoder-decoder structure that explicitly models the relationship between input views and a query view [S1].
