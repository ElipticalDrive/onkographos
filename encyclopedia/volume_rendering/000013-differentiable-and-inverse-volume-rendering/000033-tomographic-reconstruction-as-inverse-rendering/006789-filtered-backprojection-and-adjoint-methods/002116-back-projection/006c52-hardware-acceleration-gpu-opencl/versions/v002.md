# Hardware Acceleration (GPU/OpenCL)
Also called: GPU Backprojection, OpenCL Tomography

## Overview
This family accelerates the back-projection step of tomographic reconstruction by mapping projection weights to volume expansion coefficients on parallel hardware . It distinguishes itself from CPU-based siblings by leveraging GPU compute units (OpenCL) to perform the $O(V \cdot P)$ accumulation of voxel contributions, utilizing either global memory buffers or hardware texture caches for data access [G].

## Shared principles
All methods in this family solve the inverse problem of reconstructing a 3D volume from $P$ 2D projections . The core mechanism is the parallel execution of the back-projection kernel, where each work-item (thread) corresponds to a unique voxel in the output volume [G].

**Geometric Mapping:**
For a voxel at physical coordinates $(x, y, z)$ and a projection angle $\theta_p$, the ray is traced back to the detector plane . The detector coordinates $(u, v)$ are computed using the Source-to-Object Distance ($sod$) and Source-to-Detector Distance ($sdd$) . The standard geometric transformation for a rotation around the Y-axis is:
$$
\begin{aligned}
x' &= x \cos(\theta_p) + z \sin(\theta_p) \\
z' &= -x \sin(\theta_p) + z \cos(\theta_p)
\end{aligned}
$$
The projection onto the detector plane yields:
$$
u = sdd \cdot \frac{x'}{sod + z'} \quad \text{and} \quad v = sdd \cdot \frac{y}{sod + z'}
$$
Note: Some implementations use simplified linear approximations or different axis conventions (e.g., [4991-gpu-backprojection-with-global-memory-buffer.md](4991-gpu-backprojection-with-global-memory-buffer.md) uses $u = x_{rot} \cdot \frac{sdd}{sod}$).

**Accumulation:**
The value from the projection image at $(u, v)$ is accumulated into the voxel . A weighting factor $\frac{sod^2}{U^2}$ is often applied to account for cone-beam divergence, where $U$ is the distance from the source to the voxel plane along the ray [5111-gpu-backprojection-using-opencl-image-textures.md](5111-gpu-backprojection-using-opencl-image-textures.md).

**Scaling:**
After all $P$ projections are processed, the volume is scaled by $\frac{\pi}{P}$ [4991-gpu-backprojection-with-global-memory-buffer.md](4991-gpu-backprojection-with-global-memory-buffer.md).

**Data Layout:**
Projections are typically stored in column-major order (`u * H + v`) in host memory but may be transposed to row-major (`v * W + u`) for GPU coalescing or image texture compatibility [5110-gpu-backprojection-using-opencl-buffers.md](5110-gpu-backprojection-using-opencl-buffers.md).

## Subtopics

### [GPU Backprojection with Global Memory Buffer](4991-gpu-backprojection-with-global-memory-buffer.md)
Uses a single kernel launch per angle with a 1D NDRange. Each work-item maps to one voxel, accessing projection data via global memory. Chosen for simplicity and when texture hardware is unavailable or unnecessary.

### [GPU Backprojection using OpenCL Buffers](5110-gpu-backprojection-using-opencl-buffers.md)
Similar to the global memory buffer approach but explicitly includes the FDK ramp filtering step in the pipeline and handles data transposition for memory coalescing. Chosen when pre-filtering is integrated into the GPU workflow.

### [GPU Backprojection using OpenCL Image Textures](5111-gpu-backprojection-using-opencl-image-textures.md)
Uses `image2d_t` objects to leverage hardware-accelerated bilinear interpolation. Chosen for large datasets where interpolation performance is critical and pre-filtering is done on the CPU.

## Background
Originating from the need to accelerate Feldkamp-Davis-Kress (FDK) and parallel-beam reconstruction algorithms, GPU-based back-projection became standard with the advent of OpenCL and CUDA [G]. The specific implementations cited rely on OpenCL for cross-vendor compatibility . The use of image textures for interpolation exploits dedicated GPU hardware units, reducing arithmetic intensity [5111-gpu-backprojection-using-opencl-image-textures.md](5111-gpu-backprojection-using-opencl-image-textures.md).
