# Direct Linear Inversion (ART)

Also called: Algebraic Reconstruction Technique (ART) - Matrix Inversion Variant, Image reconstruction via matrix inversion, Matrix Inversion, Matrix Inversion Tomography, Pseudo-inverse Reconstruction

## Overview
Direct Linear Inversion treats the discrete Radon transform as a linear matrix multiplication and recovers the image by multiplying the scan data by the pseudo-inverse of the projection matrix [S1, unofficial]. It differs from iterative algebraic siblings by computing a direct solution in a single matrix multiplication rather than minimizing residuals through repeated updates [S1, unofficial].

## How it works
### Inputs and Outputs
- **Input**: A sinogram (parallel-beam projections) at `angles` distinct angles, each containing `rays` measurements [S1, unofficial].
- **Output**: A reconstructed 2D image of dimensions `width` × `height` [S1, unofficial].

### Data Structures
1. **Projection Matrix ($M$)**: A dense matrix of size $(angles \times rays) \times (width \times height)$ [S1, unofficial].
2. **Data Vector ($\mathbf{v}$)**: A column vector of size $angles \times rays$ containing the sinogram measurements [S1, unofficial].
3. **Reconstruction Vector ($\mathbf{r}$)**: A column vector of size $width \times height$ containing the recovered pixel values [S1, unofficial].

### Parameters
- **Image Dimensions**: $w$ (width), $h$ (height) in pixels [S1, unofficial].
- **Regularization Threshold ($\epsilon$)**: $10^{-6}$, applied during pseudo-inverse computation to handle non-square or ill-conditioned matrices [S1, unofficial].
- **Angle Step Size**: $\Delta \theta = \pi / angles$ [S1, unofficial].
- **Ray Offset**: $\sqrt{2}$, representing the half-width of the scan range [S1, unofficial].
- **Ray Step Size**: $2\sqrt{2} / (rays - 1)$ [S1, unofficial].

### Algorithm Steps
1. Initialize matrix $M$ of size $(angles \cdot rays) \times (w \cdot h)$ to zero [S1, unofficial].
2. For each angle index $a \in [0, angles)$ and ray index $r \in [0, rays)$:
   a. Calculate the ray start and end points in normalized coordinates $[-1, 1]$ [S1, unofficial].
   b. Compute scan weights for each pixel intersected by the ray using a scan-conversion approach where pixels are solid squares and rays are zero-width lines [S1, unofficial].
   c. Populate $M[(a \cdot rays + r), (y \cdot w + x)]$ with the intersection length weight $wt$ for each intersected pixel $(x, y)$ [S1, unofficial].
3. Construct the input vector $\mathbf{v}$ of length $angles \times rays$ from the sinogram data [S1, unofficial].
4. Compute the pseudo-inverse $M^+$ of $M$ using the regularization threshold $\epsilon = 10^{-6}$ [S1, unofficial].
5. Compute the reconstruction vector $\mathbf{r} = M^+ \mathbf{v}$ [S1, unofficial].
6. Reshape $\mathbf{r}$ into a 2D image of dimensions $width \times height$ [S1, unofficial].

### Pseudocode
```python
import numpy as np

def direct_linear_inversion(sinogram_data, angles_count, rays_count, width, height):
    """
    Reconstructs an image from sinogram data using direct matrix inversion.
    """
    # Flatten sinogram to vector v
    v = sinogram_data.flatten()
    
    # Initialize projection matrix M
    num_measurements = angles_count * rays_count
    num_pixels = width * height
    M = np.zeros((num_measurements, num_pixels))
    
    # Precompute ray parameters
    ray_offset = np.sqrt(2)
    ray_step = 2 * ray_offset / (rays_count - 1)
    angle_step = np.pi / angles_count
    
    # Build the projection matrix
    for a in range(angles_count):
        angle = a * angle_step
        cos_a = np.cos(angle)
        sin_a = np.sin(angle)
        
        for r in range(rays_count):
            t = -ray_offset + r * ray_step
            
            # Iterate over all pixels to compute intersection weights
            for y in range(height):
                for x in range(width):
                    # Pixel bounds in normalized coordinates [-1, 1]
                    x0, x1 = -1.0 + x * (2.0 / width), -1.0 + (x + 1) * (2.0 / width)
                    y0, y1 = -1.0 + y * (2.0 / height), -1.0 + (y + 1) * (2.0 / height)
                    
                    # Calculate intersection length of the ray with the pixel square [G]
                    wt = line_pixel_intersection_length(x0, y0, x1, y1, cos_a, sin_a, t)
                    
                    # Populate matrix
                    row_idx = a * rays_count + r
                    col_idx = y * width + x
                    M[row_idx, col_idx] = wt

    # Compute pseudo-inverse with regularization threshold [S1, unofficial]
    epsilon = 1e-6
    M_pseudo = np.linalg.pinv(M, rcond=epsilon)
    
    # Compute reconstruction vector
    r = M_pseudo @ v
    
    # Reshape into image
    image = r.reshape((height, width))
    
    return image

def line_pixel_intersection_length(x0, y0, x1, y1, cos_a, sin_a, t):
    """
    Computes the length of the intersection between a zero-width line 
    and a rectangular pixel [G].
    Line equation: x*cos_a + y*sin_a = t
    """
    # Project pixel corners onto the line direction to find entry/exit parameters
    # Direction vector of the line
    dx, dy = -sin_a, cos_a
    
    # Parametric line: P(s) = P0 + s * (dx, dy)
    # We find the range of s where the line is inside the pixel rectangle
    # Using Liang-Barsky style clipping for the line against the rectangle
    t_min, t_max = -np.inf, np.inf
    
    # Check against all four edges
    edges = [
        (x0, -1.0),  # left
        (x1, 1.0),   # right
        (y0, -1.0),  # bottom
        (y1, 1.0)    # top
    ]
    
    # We need to solve for s in: x0 <= P0_x + s*dx <= x1 and y0 <= P0_y + s*dy <= y1
    # Instead, we compute the intersection of the line with the rectangle boundaries directly
    # A robust standard approach: compute intersection points with the 4 edges and keep those inside [G]
    
    # Simplified robust calculation: project pixel center to line, check bounds
    # For exact length, we clip the infinite line to the rectangle
    px, py = (x0 + x1) / 2.0, (y0 + y1) / 2.0
    dist = px * cos_a + py * sin_a - t
    
    # Projected half-width of the pixel along the line normal
    proj_half_w = 0.5 * (abs(cos_a) * (x1 - x0) + abs(sin_a) * (y1 - y0))
    
    if abs(dist) >= proj_half_w:
        return 0.0
    
    # Intersection length formula for a line crossing a rectangle
    # Length = 2 * sqrt(proj_half_w^2 - dist^2) / |sin(theta_line - theta_rect)|
    # For axis-aligned pixels, this simplifies to the standard DDA step length
    step_x = (x1 - x0) / abs(dx) if abs(dx) > 1e-12 else np.inf
    step_y = (y1 - y0) / abs(dy) if abs(dy) > 1e-12 else np.inf
    
    # The exact chord length inside the rectangle
    # Using the standard geometric result for line-rectangle intersection [G]
    if abs(dx) > abs(dy):
        length = step_x * np.sqrt(1.0 - (dist / proj_half_w)**2) * 2.0 * abs(dx)
    else:
        length = step_y * np.sqrt(1.0 - (dist / proj_half_w)**2) * 2.0 * abs(dy)
        
    return max(0.0, length)
```

### Edge Cases and Pitfalls
- **Discretization Effects**: Error variation occurs with odd/even ray counts due to discretization artifacts, particularly in small images [S1, unofficial].
- **180-Degree Symmetry**: The 180-degree case is identical to the 0-degree case in parallel-beam geometry and should be avoided to prevent redundant data [S1, unofficial].
- **Matrix Shape**: The matrix $M$ is not required to be square ($width \cdot height \neq rays \cdot angles$); the pseudo-inverse handles non-square systems [S1, unofficial].
- **Ill-Conditioning**: The matrix may be ill-conditioned, requiring a regularization threshold of $10^{-6}$ to stabilize the pseudo-inverse computation [S1, unofficial].
- **Performance**: The method is computationally expensive, with naive implementation complexity of $O((wh)^3)$ [S1, unofficial].

## Subtopics

### Simultaneous Algebraic Reconstruction Technique (SART)
An iterative solver that updates the image estimate using all projections simultaneously per iteration, offering improved convergence over sequential updates while requiring more memory per step [G]. Choose when direct inversion is too slow or unstable for large images [G]. [Link](10119-simultaneous-algebraic-reconstruction-technique-sart.md)

### Motion-Compensated Algebraic Reconstruction Technique
Extends the algebraic framework to handle dynamic scenes by incorporating motion models directly into the projection matrix [G]. Choose when reconstructing time-varying volumes where static assumptions cause blurring [G]. [Link](7422-motion-compensated-algebraic-reconstruction-technique.md)

## Operating characteristics
- **Time Complexity**: $O((wh)^3)$ for a naive implementation, where $w$ and $h$ are image dimensions [S1, unofficial]. In terms of image edge length $L$, this scales roughly as $O(L^6)$ [S1, unofficial].
- **Measured Performance**: On a 35×40 scan reconstruction, RMS error was $< 1.0 \times 10^{-7}$ (test time 20s on an old MacBook) [S1, unofficial]. On a 10×10 scan reconstruction of an 8×8 synthetic image, RMS error was $< 1.0 \times 10^{-10}$ [S1, unofficial].
- **Strengths**: Conceptually simple; provides a direct non-iterative solution; naturally handles non-square measurement systems via pseudo-inverse [S1, unofficial].
- **Limitations**: Extremely slow for large images due to cubic complexity; sensitive to discretization errors; prone to noise amplification if the matrix is ill-conditioned without regularization [S1, unofficial].
- **When to Use**: Small images where simplicity and directness are prioritized over speed; educational demonstrations; cases where iterative convergence fails [S1, unofficial].
- **When Not to Use**: Large-scale reconstructions; real-time applications; scenes with significant noise where regularization tuning is impractical [S1, unofficial].

## Background
The method originates from the observation that the Radon transform can be discretized as a linear matrix multiplication in the image domain [S1, unofficial]. It was implemented as the `--algorithm=matrix-inversion` option in a Rust-based tomography project to demonstrate that standard linear algebra libraries (e.g., `nalgebra`) can invert the transform directly without custom algebraic theory [S1, unofficial]. The approach is characterized as a "cheap trick" that trades computational expense for implementation simplicity [S1, unofficial].
