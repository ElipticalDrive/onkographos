# NeRF-GT Baseline Training Setup
Also called: NeRF-GT, HDR-NeRF Baseline, HDR Training Baseline
## Overview
The NeRF-GT baseline establishes a training protocol for Neural Radiance Fields (NeRF) using High Dynamic Range (HDR) input views to synthesize HDR novel views [S1]. It addresses the limitation of standard NeRF, which typically uses Low Dynamic Range (LDR) inputs and cannot capture the full intensity range of scenes with extreme lighting variations [S1]. Unlike standard LDR training, this method explicitly models HDR radiance, tone-mapping predictions during loss computation to compare against LDR ground truth, though it faces challenges with encoding high-dynamic-range scenes uniformly [S1].
## How it works
**Inputs and Outputs:**
- **Input:** A set of $M$ training views consisting of camera poses $\mathbf{P}_k$ and corresponding HDR pixel values $\mathbf{I}_{gt, k}$ (or consistently exposed LDR views) [S1].
- **Output:** A trained NeRF model $\mathcal{F}_\theta$ capable of rendering HDR images for novel viewpoints [S1].

**Data Structures:**
The NeRF model $\mathcal{F}_\theta$ is a multi-layer perceptron (MLP) that takes a 3D position $\mathbf{x}$ and viewing direction $\mathbf{d}$ as input.
- **Fields:**
  - $\sigma$: Volume density (scalar).
  - $\mathbf{c}$: View-dependent color (vector, typically 3 channels, HDR intensity).
- **Layout:** Standard MLP weights and biases. The output layer produces $\sigma$ and $\mathbf{c}$ [S1].

**Numbered Steps:**
1. **Ray Sampling:** Generate rays $\mathbf{r}$ from the camera poses of the training views. Sample $N$ points along each ray within the scene bounds [S1].
2. **Network Query:** For each sample point $i$ on ray $\mathbf{r}$, query the NeRF model to obtain volume density $\sigma_i$ and HDR color $\mathbf{c}_i$ [S1].
3. **Volume Rendering:** Compute the predicted HDR pixel color $\hat{\mathbf{C}}_{hdr}(\mathbf{r})$ using the discretized volume rendering integral:
   $$ \hat{\mathbf{C}}_{hdr}(\mathbf{r}) = \sum_{i=1}^{N} T_i (1 - \exp(-\sigma_i \delta_i)) \mathbf{c}_i $$
   where $T_i = \exp(-\sum_{j=1}^{i-1} \sigma_j \delta_j)$ is the accumulated transmittance, and $\delta_i$ is the distance between adjacent samples [S1].
4. **Tone-Mapping:** Apply a tone-mapping function $\mathcal{T}(\cdot)$ to convert the predicted HDR pixel value into an LDR value:
   $$ \hat{\mathbf{C}}_{ldr} = \mathcal{T}(\hat{\mathbf{C}}_{hdr}) $$
   Similarly, apply the same tone-mapping function to the ground truth HDR training views to obtain $\mathbf{C}_{gt, ldr}$:
   $$ \mathbf{C}_{gt, ldr} = \mathcal{T}(\mathbf{I}_{gt}) $$
   [S1].
5. **Loss Computation:** Calculate the Mean Squared Error (MSE) loss between the tone-mapped predicted LDR color and the tone-mapped ground truth LDR color for a batch of $B$ rays:
   $$ \mathcal{L} = \frac{1}{B} \sum_{k=1}^{B} \| \hat{\mathbf{C}}_{ldr, k} - \mathbf{C}_{gt, ldr, k} \|^2 $$
   [S1].
6. **Optimization:** Update the network weights $\theta$ using gradient descent (typically Adam) to minimize $\mathcal{L}$ [S1].

**Parameters:**
- **Tone-Mapping Function $\mathcal{T}$:** Not specified in the sources. Standard HDR tone-mapping operators (e.g., Reinhard, ACES) are implied but not defined [S1].
- **Sample Points $N$:** Not specified for the baseline in [S1]. [S2, unofficial] suggests 64 coarse and 128 fine samples for a different context, but [S1] does not mandate this for the HDR baseline specifically.
- **Batch Size $B$:** Not specified in [S1].

**Edge Cases and Pitfalls:**
- **High Dynamic Range Encoding:** Training directly on HDR views can fail to encode all areas of a scene well, even when using tone-mapped colors for loss calculation, due to the high dynamic range of the scenes [S1]. This is a significant limitation compared to using LDR inputs [S1].
- **Tone-Mapping Consistency:** The tone-mapping function must be applied consistently to both predictions and ground truth to ensure valid loss comparison [S1].

**Pseudocode:**
```python
def train_nerf_gt_baseline(nerf_model, training_views, optimizer, num_steps):
    """
    Trains a NeRF model using HDR inputs with tone-mapped loss.
    
    Args:
        nerf_model: The NeRF MLP model.
        training_views: List of tuples (camera_pose, hdr_image).
        optimizer: Optimizer (e.g., Adam).
        num_steps: Number of training steps.
    """
    for step in range(num_steps):
        # 1. Ray Sampling
        rays = generate_rays(training_views) # Returns list of rays with origins and directions
        
        # 2. Network Query & Volume Rendering
        predicted_hdr_colors = []
        for ray in rays:
            samples = sample_along_ray(ray) # Returns list of 3D points and distances
            sigma, color = nerf_model(samples.points, ray.directions)
            hdr_color = volume_render(samples.transmittance, sigma, color, samples.distances)
            predicted_hdr_colors.append(hdr_color)
            
        predicted_hdr_colors = torch.stack(predicted_hdr_colors)
        
        # 3. Tone-Mapping
        # Note: Ground truth HDR images must be tone-mapped similarly
        predicted_ldr = tone_map(predicted_hdr_colors)
        
        # Get ground truth LDR images (tone-mapped from HDR inputs)
        gt_ldr_images = []
        for _, hdr_img in training_views:
            gt_ldr_images.append(tone_map(hdr_img))
        gt_ldr_batch = torch.stack(gt_ldr_images)
        
        # 4. Loss Computation
        loss = mse_loss(predicted_ldr, gt_ldr_batch)
        
        # 5. Optimization
        optimizer.zero_grad()
        loss.backward()
        optimizer.step()
```
[G] `tone_map` is assumed to be a differentiable tone-mapping operator. `volume_render` implements the discretized integral. `generate_rays` and `sample_along_ray` are standard ray-tracing utilities.

## Subtopics

### DBARF
DBARF jointly optimizes Generalizable Neural Radiance Fields (GeNeRFs) and relative camera poses in a self-supervised manner without requiring accurate initial poses [S1]. It differs from BARF, which relies on coarse-to-fine training with positional encodings absent in GeNeRFs, by using a RAFT-like recurrent network to implicitly minimize feature consistency errors, bypassing direct gradient descent on the cost function [S1].

## Operating characteristics
- **Time Complexity:** Not explicitly given for the HDR baseline in [S1]. [S2, unofficial] reports 0.40 sec/iteration for a standard NeRF baseline with 2,048 rays/batch, 800x600 resolution, and 200,000 steps, but this is for a different context (LDR/standard NeRF) [S2, unofficial].
- **Memory Complexity:** Not specified.
- **Measured Performance:** Rendering time for the standard NeRF baseline is 32 sec/frame [S2, unofficial].
- **Strengths:** Enables HDR novel view synthesis [S1].
- **Limitations:** Difficult to ensure all areas of a scene are encoded well due to high dynamic range, even with tone-mapped loss [S1].
- **When to use:** When HDR novel view synthesis is required and HDR training data is available [S1].
- **When not to use:** When LDR inputs are the only option, or when scene dynamic range causes encoding failures [S1].

## Background
The NeRF-GT baseline originates from the HDR-NeRF paper, which introduced the concept of training NeRFs with HDR inputs for HDR novel view synthesis [S1]. The method was evaluated on a custom HDR dataset rendered with Blender's Cycles path-tracer and real-world scenes [S1]. It serves as a baseline to compare against methods that use LDR inputs or other HDR handling strategies [S1].
