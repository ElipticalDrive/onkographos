# DP-based Configuration Selector

Also called: Multiple-Choice Knapsack Configuration Selection, Dynamic-programming-based configuration selection, MCK-based configuration selection, NeRFlex configuration selector

## Overview
The DP-based Configuration Selector is a method for selecting optimal neural radiance field (NeRF) configurations for multiple segmented objects under a strict memory constraint $H$ [S1]. It solves the configuration selection problem by formulating it as a Multiple-Choice Knapsack (MCK) problem, which is NP-hard [S1]. Unlike greedy approaches that rely on feasibility conditions often violated in multi-knob NeRF scenarios, this method uses dynamic programming to guarantee an optimal solution within the memory budget [S1]. It is specifically designed for mobile deployment where exceeding memory limits causes rendering failures or severe performance degradation [S1].

## How it works
**Inputs and Outputs**
*   **Input:**
    *   $I$: The set of segmented objects, with size $n = |I|$.
    *   $C_i$: The configuration space for object $i$, containing possible configuration pairs $\theta_i$.
    *   $f_{si}(\theta_i)$: A prediction model (profiler) estimating the memory size of configuration $\theta_i$ for object $i$ [S1].
    *   $f_{qi}(\theta_i)$: A prediction model estimating the rendering quality of configuration $\theta_i$ for object $i$ [S1].
    *   $H$: The maximum allowed total memory size for all NeRF representations [S1].
*   **Output:**
    *   `configs`: A list of pairs $(i, \theta_i^*)$ representing the selected optimal configuration for each object $i$ [S1].

**Data Structures**
The algorithm maintains three primary data structures [S1]:
1.  `q`: A 1D array of size $H+1$. `q[j]` stores the maximum achievable total quality for a memory capacity of $j$ considering the objects processed so far.
2.  `choices`: A 2D array (or dictionary of dictionaries) where `choices[i][j]` stores the configuration pair $\theta$ selected for object $i$ when the remaining capacity is $j$.
3.  `configs`: An empty list to store the final backtracked results.

**Formulas**
The optimization problem is defined as maximizing total quality subject to the memory constraint [S1]:

$$ \text{maximize} \quad \sum_{i=1}^{n} \sum_{\theta_j \in C_i} f_{qi}(\theta_j) x_{ij} $$

$$ \text{subject to} \quad \sum_{i=1}^{n} \sum_{\theta_j \in C_i} f_{si}(\theta_j) x_{ij} \le H $$

$$ \sum_{\theta_j \in C_i} x_{ij} = 1, \quad i = 1, \dots, n $$

$$ x_{ij} \in \{0, 1\}, \quad i = 1, \dots, n, \quad \theta_j \in C_i $$

where $x_{ij}$ is a binary variable indicating if configuration $\theta_j$ is selected for object $i$ [S1].

A greedy feasibility condition often used in MCK problems is [S1]:

$$ \sum_{\theta_j \in C_i} f_{si}(\theta_j) + \min_{h \neq i} \min_{\theta_t \in C_h} f_{sh}(\theta_t) \le H $$

This condition ensures that at least one valid configuration exists for every object. However, in NeRFlex, this condition is frequently not met due to the presence of two control knobs (geometry and texture), necessitating the DP approach [S1].

**Parameters**
*   **Memory Constraint ($H$):** The fixed memory size available on the target device. Typical values are 240MB for iPhone 13 and 150MB for Pixel 4 [S1].
*   **Configuration Pair ($\theta_i$):** Represented as $(g_i, p_i)$, where $g_i$ is the grid resolution and $p_i$ is the plane parameter [S1]. For baseline comparisons (e.g., Single NeRF, Block-NeRF), the recommended pair is $(128, 17)$ [S1].

**Algorithm Steps**
1.  **Initialization:** For each object $i$, initialize the minimum configuration $\theta_i^* \leftarrow \min(C_i) = (\min(g_i), \min(p_i))$. Initialize `q` as an array of zeros of size $H+1$. Initialize `choices` as an empty 2D structure. Initialize `configs` as an empty list [S1].
2.  **DP Table Construction:** Iterate through each object $i$ in $I$. For each object, iterate through the capacity $j$ from $H$ down to 0. For each configuration $\theta$ in $C_i$:
    a. Calculate the threshold size $r_i = H - \sum_{h \neq i} \min_{\theta_t \in C_h} f_{sh}(\theta_t)$. This represents the minimum memory required by all other objects if they take their smallest configurations [S1].
    b. **Filtering:** If $f_{si}(\theta) \ge r_i$, skip this configuration. This ensures that selecting $\theta$ leaves enough room for the minimal configurations of all other objects, satisfying the feasibility condition implicitly [S1].
    c. **State Transition:** If $j \ge f_{si}(\theta)$, check if selecting $\theta$ improves the quality: if `q[j]` < `q[j - f_{si}(\theta)]` + $f_{qi}(\theta)$, update `q[j]` = `q[j - f_{si}(\theta)]` + $f_{qi}(\theta)$ and record `choices[i][j]` = $\theta$ [S1].
3.  **Backtracking:** Iterate from the last object index $m = n-1$ down to 0. If `choices[m][H]` is not null, add the pair $(m, \text{choices}[m][H])$ to `configs`. Note: In a standard MCK DP, backtracking usually involves updating the remaining capacity $H \leftarrow H - f_{s,m}(\theta_{selected})$. The provided pseudocode in the source does not explicitly show the capacity update during backtracking, but implies retrieving the choice at the full capacity $H$ for the last object. Given the structure of the forward pass (iterating $j$ from $H$ down), the standard backtracking logic applies: retrieve $\theta$ for object $m$ at current capacity, subtract its size from capacity, and proceed to $m-1$ [S1]. *Correction based on standard DP knapsack logic and source Algorithm 1 snippet:* The source Algorithm 1 simply checks `choices[m][H]`. This implies the `choices` array might store the best choice for the *remaining* capacity or the source simplifies the backtracking description. We will implement the standard backtracking logic which is necessary for correctness, noting the source's pseudocode may be simplified [S1].

**Pseudocode**

```python
def dp_configuration_selector(objects, profilers, H):
    """
    objects: List of object IDs or indices.
    profilers: Dict mapping object_id to (f_s, f_q) functions.
    C: Dict mapping object_id to list of configuration pairs theta.
    H: Memory constraint.
    """
    n = len(objects)
    # q[j] stores max quality for capacity j
    q = [0.0] * (H + 1)
    # choices[i][j] stores the theta selected for object i at capacity j
    # Using a list of dicts for sparse storage if needed, or 2D array
    choices = [[None for _ in range(H + 1)] for _ in range(n)]
    
    # Precompute min size for all objects to calculate threshold r_i
    # Note: The source calculates r_i inside the loop. 
    # Optimization: Precompute min sizes for all h != i is O(n^2 * |C|).
    # Source does O(n) per object inside the j loop? No, r_i depends only on i.
    # Let's follow source structure strictly.
    
    for i, obj_id in enumerate(objects):
        f_s, f_q = profilers[obj_id]
        C_i = C[obj_id] # Configuration space for object i
        
        # Calculate r_i: H minus sum of min sizes of all OTHER objects
        min_sizes_others = 0.0
        for k, other_id in enumerate(objects):
            if k == i:
                continue
            f_s_other, _ = profilers[other_id]
            # Find min size in C_other
            min_theta = min(C[other_id], key=lambda t: f_s_other(t))
            min_sizes_others += f_s_other(min_theta)
            
        r_i = H - min_sizes_others
        
        for j in range(H, -1, -1):
            for theta in C_i:
                size = f_s(theta)
                
                # Filter: ensure feasibility for other objects
                if size >= r_i:
                    continue
                
                if j >= size:
                    new_quality = q[j - size] + f_q(theta)
                    if new_quality > q[j]:
                        q[j] = new_quality
                        choices[i][j] = theta
                        
    # Backtracking
    configs = []
    current_capacity = H
    
    # Iterate backwards through objects
    for i in range(n - 1, -1, -1):
        obj_id = objects[i]
        theta_selected = choices[i][current_capacity]
        
        if theta_selected is not None:
            configs.append((obj_id, theta_selected))
            f_s, _ = profilers[obj_id]
            current_capacity -= f_s(theta_selected)
            
    return configs
```

**Edge Cases and Pitfalls**
*   **Memory Limits:** On iPhone 13, exceeding 240MB causes the local WebGL rendering engine to fail to load data. On Pixel 4, exceeding 150MB causes average FPS to drop by ~15, leading to stuttering [S1].
*   **Feasibility:** If the total minimum size of all objects exceeds $H$, no solution exists. The filtering step $f_{si}(\theta) \ge r_i$ handles this by preventing selections that would leave insufficient space for minimal configurations of others [S1].
*   **NP-Hardness:** The problem is NP-hard. The DP solution is pseudo-polynomial, dependent on $H$. If $H$ is very large, the algorithm becomes slow [S1].

## Operating characteristics
*   **Time Complexity:** $O(nhc)$, where $n$ is the number of objects, $h$ is the memory constraint $H$, and $c$ is the size of the configuration space $C$ for an object. The threshold calculation takes $O(n)$ per object, and the DP process takes $O(hc)$ per object [S1].
*   **Memory Complexity:** $O(nh)$ for the `choices` table and $O(h)$ for the `q` array [S1].
*   **Strengths:** Guarantees optimal solution within the memory constraint. Handles multiple control knobs (geometry and texture) where greedy methods fail due to violated feasibility conditions [S1].
*   **Limitations:** Pseudo-polynomial time complexity makes it sensitive to the magnitude of $H$. Not suitable for real-time online selection if $H$ or $n$ is very large. Requires accurate profiling models $f_s$ and $f_q$ [S1].
*   **When to use:** Mobile deployment of multi-NeRF scenes with strict memory budgets where offline or pre-computation is acceptable [S1].

## Background
The DP-based Configuration Selector was introduced in the **NeRFlex** paper [S1]. NeRFlex is a resource-aware real-time high-quality rendering system for complex scenes on mobile devices. The method addresses the challenge of balancing rendering quality and memory usage in multi-NeRF frameworks (like Block-NeRF) where each object is represented by a separate NeRF. Traditional greedy configuration selection methods were found to be sub-optimal or infeasible for NeRFlex due to the complexity of its configuration knobs (grid resolution and plane parameters) [S1]. The method was evaluated on iPhone 13 and Pixel 4 devices, demonstrating its necessity for mobile WebGL rendering constraints [S1].
