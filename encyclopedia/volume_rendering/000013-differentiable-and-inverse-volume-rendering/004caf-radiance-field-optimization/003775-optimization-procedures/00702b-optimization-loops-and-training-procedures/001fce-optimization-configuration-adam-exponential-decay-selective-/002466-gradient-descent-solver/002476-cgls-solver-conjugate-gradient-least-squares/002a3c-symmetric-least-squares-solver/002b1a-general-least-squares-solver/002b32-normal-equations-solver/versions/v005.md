# Normal Equations Solver

Also called: A^T A Solver, Least Squares via Normal Equations

## Overview
The Normal Equations Solver addresses the overdetermined linear system $Ax = b$ by explicitly forming the symmetric positive semi-definite system $A^T A x = A^T b$ and solving it using a standard linear solver [S1, unofficial]. It is distinguished from iterative methods (like CGLS) and direct factorizations of the original matrix (like QR) by its reliance on the explicit construction of the Hessian matrix $A^T A$ [S1, unofficial]. While generally the fastest alternative for small-to-medium systems, it is prone to numerical instability if the system matrix $A$ is ill-conditioned [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: System matrix $A \in \mathbb{R}^{m \times n}$ (where $m \gg n$) and vector $b \in \mathbb{R}^m$ [S1, unofficial].
- Output: Solution vector $x \in \mathbb{R}^n$ [S1, unofficial].

**Data Structures:**
- Matrix $A$: Stored in Compressed Sparse Row (CSR) format to allow efficient sequential querying of non-zero entries for the $i$-th voxel (row) [S1, unofficial].
- Matrix $A^T A$: A band matrix with non-zero entries only on the main diagonal and two diagonals four rows/columns away from the main diagonal [S1, unofficial]. The distance of four arises from the separate handling of RGB*$\alpha$ channels [S1, unofficial]. Due to symmetry, only the upper triangular part is stored [S1, unofficial].
- Vector $A^T b$: Standard dense or sparse vector representation [S1, unofficial].

**Steps:**
1. **Assemble $A^T A$ and $A^T b$**: Compute the sparse matrix-matrix product $A^T A$ and the sparse matrix-vector product $A^T b$ using a linear algebra library (e.g., Eigen on CPU, cuSPARSE on GPU) or custom matrix-free compute code [S1, unofficial].
2. **Solve the Symmetric System**: Solve the ordinary least squares problem $A^T A x = A^T b$ using a dense or sparse linear least squares solver (e.g., QR, LLT, LDLT) [S1, unofficial].
3. **Constraint Handling**: The standard normal equations solver does not enforce box constraints $0 \le x_i \le 1$ [S1, unofficial]. If the unconstrained solution violates these constraints, apply truncation: $x'_i = \max\{\min\{x_i, 1\}, 0\}$ [S1, unofficial]. If explicit constraint enforcement is required, a constrained quadratic programming solver (e.g., ADMM via OSQP) should be used instead [S1, unofficial].

**Pseudocode (Matrix-free GPU Assembly):**
```python
def assemble_normal_equations(voxels, A_T_A_upper_tri):
    # Initialize A_T_A_upper_tri as a band matrix structure
    for i in range(len(voxels)):
        j = compute_column_index(voxels[i])  # From Subsec. 3.2
        w = compute_interpolation_weight(voxels[i])  # From Subsec. 3.2
        # Atomically add to upper triangular part of A^T A
        A_T_A_upper_tri[j, j] += (1 - w)**2
        A_T_A_upper_tri[j+1, j+1] += w**2
        A_T_A_upper_tri[j+1, j] += (1 - w) * w
    # Compute A^T b similarly
    return A_T_A_upper_tri
```

**Formulas:**
- Normal Equations: $A^T A x = A^T b$ [S1, unofficial].
- Condition Number Relationship: $\text{cond}(A^T A) = \text{cond}(A)$ [S1, unofficial]. The source text states this equality, noting that computing $A^T A$ results in many arithmetic additions and potentially very large values, which leads to numerical instability [S1, unofficial].
- Truncation: $x'_i = \max\{\min\{x_i, 1\}, 0\}$ [S1, unofficial].

**Parameters:**
- Precision: 32-bit floating point is typical [S1, unofficial]. For a dataset with $1.76 \cdot 10^6$ voxels, storing $A$ in CSR format requires almost 7 GiB of memory [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Ill-conditioning**: The condition number relationship $\text{cond}(A^T A) = \text{cond}(A)$ leads to potential numerical instability due to accumulated arithmetic operations and large matrix values [S1, unofficial].
- **Rank Deficiency**: $A^T A$ is often nearly rank deficient because certain transfer function values are hardly referenced by voxel values, or rank deficient if no values fall within a certain range [S1, unofficial]. Solvers like QR may require pivoting for stability [S1, unofficial].
- **GPU Atomic Contention**: While atomic additions on GPU for assembling $A^T A$ might theoretically cause write conflicts and slowdowns, in practice this method proved to be one of the fastest solutions [S1, unofficial].

## Subtopics

### [Normal Equations-based Solver](5483-normal-equations-based-solver.md)
Addresses the box-constrained least squares problem ($0 \le x_i \le 1$) by formulating it as a quadratic programming (QP) problem. It differs from direct unconstrained solvers by explicitly handling constraints (often via ADMM) and differs from iterative solvers by relying on the explicit construction of the Hessian $Q = A^T A$.

## Operating characteristics
- **Time Complexity**: Generally the fastest alternative for small-to-medium systems where $A^T A$ is small enough to fit in memory and be solved directly [S1, unofficial].
- **Memory Complexity**: Storing $A$ is expensive (e.g., ~7 GiB for $1.76 \cdot 10^6$ voxels with 32-bit floats), but $A^T A$ is usually quite small and can be stored in dense or sparse format [S1, unofficial].
- **Strengths**: Fast assembly and solution for small systems; leverages highly optimized dense linear algebra libraries for the final solve step [S1, unofficial].
- **Limitations**: Prone to stability issues if $A$ is ill-conditioned due to the condition number relationship; does not natively support box constraints without post-processing or external QP solvers [S1, unofficial].
- **When to Use**: When $A^T A$ is small enough to be stored and solved directly, and numerical stability is not a primary concern or the matrix is well-conditioned [S1, unofficial].
- **When Not to Use**: When $A$ is ill-conditioned (use QR or iterative methods); when explicit box constraints are required (use Normal Equations-based Solver with QP) [S1, unofficial].

## Background
The method originates from the formulation of ordinary least squares problems in volume rendering transfer function optimization [S1, unofficial]. It is discussed in the context of comparing solver strategies for optimizing RGB*$\alpha$ values, where the system matrix $A$ is tall and skinny ($m \gg n$) [S1, unofficial]. The approach is noted as the most straightforward solution, with implementations supporting CPU (Eigen), GPU (cuSPARSE), and matrix-free Vulkan compute [S1, unofficial].
