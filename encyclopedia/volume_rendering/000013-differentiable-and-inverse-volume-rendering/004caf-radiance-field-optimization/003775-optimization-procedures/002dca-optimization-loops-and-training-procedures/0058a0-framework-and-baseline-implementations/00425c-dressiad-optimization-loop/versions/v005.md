# DressiAD Optimization Loop

Also called: Dressi-AD Computational Graph Execution, DressiAD Training Loop, Optimization Loop

## Overview
The DressiAD Optimization Loop is a define-and-run differentiable rendering optimization framework that constructs a computational graph, marks variables for gradient tracking, and executes forward/backward passes using Stochastic Gradient Descent (SGD) [S1]. It distinguishes itself from standard AD libraries by packing the computational graph into Vulkan command buffers for execution, allowing for hardware-agnostic differentiable rendering [S1]. Unlike general-purpose AD which may store $O(kn)$ intermediate states, DressiAD manages graph staticity and rebuilds stages/substages based on dirty flags to optimize execution [S1].

## How it works
The method operates in two phases: initialization (graph construction) and iteration (execution). It relies on the `DressiBasicRenderer` interface to manage scene data and the `DressiAD` class to handle the AD logic [S1].

### Inputs and Outputs
**Inputs:**
*   Scene data files (e.g., `.gltf`, `.png`) loaded into CPU memory [S1].
*   Optimization targets: Variables marked with `requires-gradient` flags (e.g., vertex positions, normal textures) [S1].
*   Hyperparameters: Learning rate ($lr$), HardSoftRas parameters ($K, r, \sigma, \delta$) [S1].

**Outputs:**
*   Optimized scene parameters saved to disk (e.g., `.gltf`) [S1].
*   Rendered images and loss values during iteration [S1].

### Data Structures
**CpuImage**
A simple buffer representing a 2D image used to store scene data on the CPU [S1]. Fields include:
*   Vertex positions, UVs, faces.
*   Matrices (model, view, projection).
*   Textures: Environment map, albedo, metallic, roughness, normal, background [S1].

**Variable**
A data structure representing inputs and outputs of functions in the computational graph [S1]. Fields:
*   `type`: Enum indicating data shape (`VEC3`, `VEC2`, `IVEC3`, `MAT4`, `FLOAT`, `VEC4`) [S1].
*   `size`: Dimensions of the variable [S1].
*   `dirty`: Boolean flag indicating if the variable has changed since the last graph rebuild [S1].
*   `requires_grad`: Boolean flag indicating if gradients should be computed for this variable [S1].

**DressiAD Class State**
*   `m_loss_var`: The variable representing the loss [S1].
*   `m_init_status`: Enum (`BACKWARD`, `STAGE`, `SUBSTAGE`, `FINISHED`) controlling the graph rebuild phase [S1].
*   `m_graph_static_cnt`: Counter tracking iterations without graph changes [S1].
*   `m_input_vars`: List of input variables [S1].
*   `m_vk_cmd_buf`: Vulkan command buffer [S1].

### Parameters
*   $lr$: Learning rate for SGD. Typical value: $0.01$ [S1].
*   $K$: Number of peeling steps for HardSoftRas. Typical value: $2$ [S1].
*   $r$: Radius parameter for HardSoftRas. Typical value: $0.01$ [S1].
*   $\sigma$: Blending parameter for HardSoftRas. Calculated as $r / 7$ [S1].
*   $\delta$: Silhouette edge width for HardSoftRas. Equal to $r$ [S1].
*   `FAST_REBUILD_COUNT`: Threshold for fast graph rebuild. Not given in the sources.
*   `FULL_REBUILD_COUNT`: Threshold for full graph rebuild. Not given in the sources.

### Steps

1.  **Initialization:**
    *   Create a `DressiBasicRenderer` instance [S1].
    *   Load scene data from files into `CpuImage` buffers on CPU memory [S1].
    *   Convert non-image data (e.g., vertex positions) into 2D image representation for efficient rendering [S1].
    *   Create `Variable` objects for scene data and target images [S1].
    *   Call `buildGraph()` to construct the forward computational graph:
        *   Invoke `BuildBasicRenderGraph` with scene variables and HardSoftRas parameters ($K, r, \sigma, \delta$) [S1].
        *   Compute L1 loss: $L = \text{Mean}(|I_{\text{target}} - I_{\text{rendered}}|)$ [S1].
        *   Set the loss variable in `DressiAD` via `setLossVar()` [S1].
        *   Set the optimizer function in `DressiAD` via `setOptimizer()` [S1].
        *   Mark optimization targets (e.g., vertex positions, normals) using `setRequiresGrad()` [S1].
    *   Set `m_init_status` to `InitStatus::BACKWARD` [S1].

2.  **Optimization Loop (per iteration):**
    *   Check if any input variable has changed dirty flags (`IsAnyVariableDirtyChanged`) [S1].
        *   If changed, reset `m_graph_static_cnt` to $0$ [S1].
    *   Check rebuild conditions:
        *   If `m_graph_static_cnt == FAST_REBUILD_COUNT`, set `m_init_status = InitStatus::STAGE` [S1].
        *   If `m_graph_static_cnt == FULL_REBUILD_COUNT`, set `m_init_status = InitStatus::SUBSTAGE` [S1].
    *   Transfer data: Send CPU images to GPU if needed (`sendImg()`), marking variables as dirty if updated [S1].
    *   Execute `execStep()`:
        *   **Backward Pass Construction:**
            *   Initialize `fwd_bwds_map` (mapping forward variables to backward gradient variables) and `func_queue` [S1].
            *   Set loss variable gradient to $1.0$ (`F::Float(1.f)`) [S1].
            *   Push loss variable's creator function to `func_queue` [S1].
            *   While `func_queue` is not empty:
                *   Pop function $F$ from queue [S1].
                *   Call `F::buildBwd()` to generate backward graph nodes [S1].
                *   For each input $x$ of $F$ with gradient $g_x$:
                    *   Add $g_x$ to `fwd_bwds_map[x]` [S1].
                    *   Push $x$'s creator function to `func_queue` if not already processed [S1].
        *   **Graph Traversal & Packing:**
            *   Traverse the graph based on `m_init_status` to pack into Vulkan stages/substages [S1].
            *   Create Vulkan objects from stage/substage graphs [S1].
        *   **Execution:**
            *   Submit commands via `VkQueueSubmit(m_vk_cmd_buf)` [S1].
    *   **Post-Iteration:**
        *   Mark all input variables as clean recursively (`setDirtyRecursively(false)`) [S1].
        *   Set `m_init_status` to `FINISHED` [S1].
        *   Increment `m_graph_static_cnt` [G] (implied by usage of counter for rebuilds).
        *   Collect input variables and their summed gradients from `fwd_bwds_map` [S1].
        *   Apply optimizer: Update variables $x_i$ using gradients $g_{x_i}$ and learning rate $lr$:
            $$ x_i \leftarrow x_i - g_{x_i} \cdot lr $$
            [S1]

### Pseudocode

```python
# Initialization
renderer = DressiBasicRenderer()
renderer.load_scene("initial_scene.gltf", "target_img.png")

# Build Graph
K = 2
r = 0.01
sigma = r / 7.0
delta = r
lr = 0.01

# Build rendering graph
rendered_img = BuildBasicRenderGraph(
    vtx_pos, vtx_uv, faces, model_mat, view_mat, prj_mat,
    env_img, albedo, metallic, roughness, normal, background,
    K, r, sigma, delta
)

# Compute Loss
loss = Mean(Abs(target_img - rendered_img))

# Configure AD
dressi_ad = DressiAD()
dressi_ad.set_loss_var(loss)
dressi_ad.set_optimizer(lambda xs, gxs: [x - g * lr for x, g in zip(xs, gxs)])

# Mark Targets
vtx_pos.set_requires_grad()
normal.set_requires_grad()

# Optimization Loop
for iter in range(1000):
    # Check dirty flags
    if is_any_variable_dirty(m_input_vars):
        m_graph_static_cnt = 0
    
    # Check rebuild conditions
    if m_graph_static_cnt == FAST_REBUILD_COUNT:
        m_init_status = InitStatus.STAGE
    elif m_graph_static_cnt == FULL_REBUILD_COUNT:
        m_init_status = InitStatus.SUBSTAGE
        
    # Transfer Data
    if not m_is_sent:
        send_img_to_gpu(vtx_pos)
        send_img_to_gpu(normal)
        m_is_sent = True
        
    # Execute Step
    dressi_ad.exec_step()
    
    # Post-step
    mark_inputs_clean(m_input_vars)
    m_init_status = InitStatus.FINISHED
    m_graph_static_cnt += 1

# Save Results
renderer.save_scene("optimized_scene.gltf")
```

### Edge Cases and Pitfalls
*   **Dirty Flags:** If input variables change, the graph must be rebuilt. Failure to reset `m_graph_static_cnt` may lead to stale computations [S1].
*   **Rebuild Counts:** The specific values for `FAST_REBUILD_COUNT` and `FULL_REBUILD_COUNT` are not provided in the sources [S1].
*   **Memory Management:** The system relies on Vulkan command buffers. Improper submission or cleanup may lead to GPU hangs or memory leaks [S1].
*   **Gradient Summation:** Gradients from multiple paths to the same variable must be summed pixel-wise before optimization [S1].

## Operating characteristics
*   **Time Complexity:** Depends on the number of samples per ray and the depth of the computational graph. The backward pass traverses the graph once [S1].
*   **Memory Complexity:** DressiAD avoids storing all intermediate states by using a reactive packing strategy. It packs the graph into Vulkan stages/substages, potentially reducing memory overhead compared to standard AD [S1].
*   **Performance:** Performance is hardware-dependent due to Vulkan integration. The use of HardSoftRas allows for differentiable rasterization with soft edges, which may be slower than hard rasterization but provides smoother gradients [S1].
*   **Strengths:** Hardware-agnostic, integrates with Vulkan, supports physically based shading, and allows for optimization of vertex positions and textures [S1].
*   **Limitations:** Requires manual graph construction, limited to defined operators, and may have high overhead for small graphs due to Vulkan command submission [S1].

## Background
DressiAD is part of the Dressi renderer, a hardware-agnostic differentiable rendering system [S1]. It was introduced in 2022 by the authors of "Dressi: A Hardware‐Agnostic Differentiable Renderer with Reactive Shader Packing and Soft Rasterization" [S1]. The system is designed to bridge the gap between differentiable rendering and hardware acceleration by packing computational graphs into Vulkan command buffers [S1].
