# Normal Equations Solver

Also called: A^T A Solver, Least Squares via Normal Equations

## Overview
The Normal Equations Solver addresses the overdetermined linear system $Ax = b$ by explicitly forming the symmetric positive semi-definite matrix $A^T A$ and vector $A^T b$, then solving the resulting square system [S1, unofficial]. It is distinguished from matrix-free iterative methods (like CGLS) by its direct assembly of the normal equations, making it the fastest alternative for small-to-medium systems but prone to numerical instability if the system matrix is ill-conditioned [S1, unofficial].

## How it works
**Inputs:**
- System matrix $A \in \mathbb{R}^{m \times n}$, where $m \gg n$ (tall and skinny). In volume rendering contexts, $m$ is the number of voxels and $n$ is the number of transfer function parameters.
- Target vector $b \in \mathbb{R}^m$.

**Outputs:**
- Solution vector $x \in \mathbb{R}^n$.

**Data Structures:**
- **Matrix $A$**: Stored in Compressed Sparse Row (CSR) format. This allows sequential querying of non-zero entries for the $i$-th voxel (row), which is efficient for assembly [S1, unofficial].
- **Matrix $A^T A$**: A band matrix stored in dense or sparse format. Due to symmetry, only the upper triangular part is stored. The sparsity pattern consists of non-zero entries only on the main diagonal and two diagonals four rows/columns away from the main diagonal. This distance of four arises from the separate handling of RGB$\alpha$ channels [S1, unofficial].
- **Vector $A^T b$**: Dense vector of size $n$.

**Steps:**
1. **Assemble $A^T A$ and $A^T b$**:
   - Compute the sparse matrix-matrix product $A^T A$ and sparse matrix-vector product $A^T b$.
   - On CPU, use libraries like Eigen [S1, unofficial].
   - On GPU, use cuSPARSE [S1, unofficial] or custom matrix-free Vulkan compute shaders [S1, unofficial].
   - **Vulkan Compute Implementation**:
     - Iterate over all voxels $i$.
     - Determine column indices $j(D_i)$ and $j(D_i)+1$ and interpolation weight $w(i)$ (from the underlying radiance field parameterization).
     - Atomically add contributions to $A^T A$:
       - $(1 - w(i))^2$ to entry $(j(D_i), j(D_i))$.
       - $w(i)^2$ to entry $(j(D_i)+1, j(D_i)+1)$.
       - $(1 - w(i))w(i)$ to entry $(j(D_i)+1, j(D_i))$.
     - Note: Atomic additions may cause write conflicts on GPU, but this remains one of the fastest assembly methods [S1, unofficial].
2. **Solve the System**:
   - Use a dense or sparse linear least squares solver (e.g., QR, LLT, LDLT) on the assembled $A^T A$ and $A^T b$ [S1, unofficial].
   - If using QR, pivoting may be required for numerical stability [S1, unofficial].
3. **Handle Constraints (Optional)**:
   - The standard normal equations solver does not enforce box constraints $0 \le x_i \le 1$.
   - If constraints are not explicitly handled by the solver, apply truncation: $x'_i = \max\{\min\{x_i, 1\}, 0\}$ [S1, unofficial].
   - For explicit constraint enforcement, use a Quadratic Programming (QP) solver like ADMM via OSQP [S1, unofficial].

**Pseudocode (Vulkan-style Assembly):**
```python
# Initialize A_T_A as a dense band matrix or sparse structure
# Initialize A_T_b as a zero vector of size n

for each voxel i in voxels:
    # Determine which transfer function entries are affected
    col_idx = get_column_index(D_i)
    w = get_interpolation_weight(i)
    
    # Contribution to A^T A (upper triangular only)
    # Entry (col_idx, col_idx)
    atomic_add(A_T_A[col_idx, col_idx], (1 - w)**2)
    
    # Entry (col_idx + 1, col_idx + 1)
    atomic_add(A_T_A[col_idx + 1, col_idx + 1], w**2)
    
    # Entry (col_idx + 1, col_idx) - symmetric, stored in upper triangle
    # Note: col_idx < col_idx + 1, so this is the off-diagonal term
    atomic_add(A_T_A[col_idx, col_idx + 1], (1 - w) * w)
    
    # Contribution to A^T b
    # Assuming b[i] is the target value for voxel i
    atomic_add(A_T_b[col_idx], (1 - w) * b[i])
    atomic_add(A_T_b[col_idx + 1], w * b[i])

# Solve the system
x = solve_linear_system(A_T_A, A_T_b)

# Apply truncation if constraints are not enforced by the solver
x = clamp(x, 0, 1)
```

**Parameters:**
- **Precision**: 32-bit floating point is common, but memory usage scales with $m$. For $1.76 \cdot 10^6$ voxels, $A$ requires almost 7 GiB [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Ill-conditioning**: The condition number squares: $\text{cond}(A^T A) = \text{cond}(A)^2$. This leads to numerical instability if $A$ is ill-conditioned [S1, unofficial].
- **Rank Deficiency**: $A^T A$ may be nearly rank deficient if certain transfer function values are rarely referenced by voxel values, or rank deficient if no values fall within a certain range. Pivoting (e.g., in QR) is recommended [S1, unofficial].
- **Constraint Violation**: Without explicit handling, solutions may violate physical bounds (e.g., negative opacity). Truncation is a simple fix but may not yield the true constrained optimum [S1, unofficial].

## Subtopics

### [Normal Equations-based Solver](5483-normal-equations-based-solver.md)
Addresses box-constrained least squares ($0 \le x_i \le 1$) via Quadratic Programming (QP) using ADMM. Distinguished by explicit constraint handling, unlike direct solvers that rely on post-hoc truncation. Chosen when strict bounds are required, despite higher computational overhead.

## Operating characteristics
- **Time Complexity**: Assembly of $A^T A$ and $A^T b$ is $O(m \cdot k)$ where $k$ is the number of non-zeros per row (typically small). Solving the dense system is $O(n^3)$ for dense solvers or $O(n^2)$ for sparse solvers. Since $n$ is small (transfer function size), this is fast.
- **Memory Complexity**: $O(m \cdot k)$ for $A$ (if stored) and $O(n^2)$ for $A^T A$. For large $m$, storing $A$ is expensive (e.g., 7 GiB for $1.76 \cdot 10^6$ voxels) [S1, unofficial]. Matrix-free assembly avoids storing $A$ entirely.
- **Performance**: Generally the fastest alternative for small $n$ [S1, unofficial].
- **Strengths**: Simplicity, speed for small systems, well-supported by standard linear algebra libraries.
- **Limitations**: Numerical instability due to squared condition number; does not natively support constraints; memory intensive if $A$ is stored.
- **When to use**: Small to medium-sized transfer function optimization where speed is critical and constraints are not strict or can be handled via truncation.
- **When not to use**: Large-scale problems where memory is constrained, or when high numerical precision is required for ill-conditioned systems (use CGLS or QR with pivoting).

## Background
Originated from the standard approach to solving overdetermined linear least squares problems in numerical linear algebra. In volume rendering, it is applied to transfer function optimization, where the system matrix relates voxel colors to transfer function values. The specific implementation details (Vulkan assembly, band matrix structure) are documented in recent comparative studies on transfer function optimization [S1, unofficial].
