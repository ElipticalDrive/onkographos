# Pool proposer architecture
Also called: Pooling-based proposer
## Overview
The Pool proposer architecture is a trainable network component used in NeRF-ID to generate fine sampling positions from coarse features along a ray [S1, unofficial]. It solves the problem of adaptive ray sampling by learning to propose high-density regions for volume rendering, improving reconstruction quality over uniform sampling [S1, unofficial]. It is distinguished from its sibling MLPMix proposer by using a bottleneck fully connected layer and sinusoidal positional encodings, whereas MLPMix uses a different mixing strategy; the Pool proposer exhibits higher variance and performs significantly worse on specific scenes like Blender: Materials and Blender: Mic compared to MLPMix [S1, unofficial].
## How it works
**Inputs and Outputs:**
- Input: $N_c = 64$ coarse features, one for each coarse sample along the ray [S1, unofficial].
- Output: $N_f = 128$ fine sampling positions (proposals) [S1, unofficial].

**Data Structures:**
- Coarse features: A tensor of shape $(N_c, D)$, where $D$ is the feature dimension (implied by the FC layer input size, typically matching the NeRF backbone feature size, but the source specifies the bottleneck layer size explicitly) [S1, unofficial].
- Bottleneck Layer: A single fully connected (FC) layer with dimensions $256 \times 256$ [S1, unofficial].

**Steps:**
1. **Positional Encoding:** Compute sinusoidal positional encodings for the spatial positions of the $N_c$ coarse samples along the ray [S1, unofficial].
2. **Feature Summation:** Sum the sinusoidal positional encodings with the coarse features [S1, unofficial].
3. **Bottleneck Projection:** Pass the summed features through the single bottleneck fully connected layer of size $256 \times 256$ [S1, unofficial].
4. **Proposal Generation:** The output of the bottleneck layer is used to generate $N_f = 128$ fine proposals [S1, unofficial].

**Parameters:**
- $N_c = 64$: Number of coarse samples [S1, unofficial].
- $N_f = 128$: Number of fine proposals [S1, unofficial].
- Bottleneck size: $256 \times 256$ [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Blind Proposer:** If the network ignores input coarse features and always outputs the same proposals, performance degrades significantly [S1, unofficial].
- **No-position Proposer:** If the network ignores the positions of coarse samples, it becomes insensitive to feature ordering. This leads to poor performance on scenes like Blender (where rays have varied directions) but remains competitive on forward-facing scenes like LLFF-NeRF [S1, unofficial].

## Subtopics

### MLPMix Proposer
The MLPMix proposer is an alternative to the Pool proposer that uses a different mixing mechanism. It is preferred over the Transformer proposer due to the Transformer's inferior performance on scenes like Blender: Ficus, Blender: Lego, and LLFF-NeRF: T-Rex, as well as unstable training curves [S1, unofficial]. MLPMix and Pool are generally on par, but Pool has higher variance and performs significantly worse on Blender: Materials and Blender: Mic [S1, unofficial].

## Operating characteristics
The Pool proposer's most expensive operation is the bottleneck fully connected layer of size $256 \times 256$ applied to each of the $N_c = 64$ coarse features [S1, unofficial]. This cost is considered negligible compared to the NeRF backbone, which applies similar FC layers to $8 \times (N_c + N_c + N_f) = 2048$ vectors [S1, unofficial]. The Pool proposer exhibits higher variance in performance compared to MLPMix and is significantly worse on specific scenes (Blender: Materials, Blender: Mic) [S1, unofficial].

## Background
The Pool proposer architecture was introduced in the NeRF-ID paper, which extends the original NeRF method with adaptive sampling [S1, unofficial]. The original NeRF paper [37] is cited as the baseline for the backbone architecture and sampling parameters ($N_c=64, N_f=128$) [S1, unofficial]. The NeRF-ID paper compares three proposer architectures: Transformer, Pool, and MLPMix [S1, unofficial].
