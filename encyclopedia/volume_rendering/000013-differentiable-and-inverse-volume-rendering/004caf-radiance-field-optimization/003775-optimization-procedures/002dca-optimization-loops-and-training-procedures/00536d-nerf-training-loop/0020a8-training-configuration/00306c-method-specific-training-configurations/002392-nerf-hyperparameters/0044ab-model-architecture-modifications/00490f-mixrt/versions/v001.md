# MixRT

Also called: Mixed Neural Representations For Real-Time NeRF Rendering

## Overview
MixRT is a hybrid neural representation designed to enable real-time Neural Radiance Field (NeRF) rendering on edge devices by leveraging standard graphics hardware pipelines. It solves the conflict between high-fidelity novel view synthesis and the computational constraints of mobile or browser-based environments by decomposing the scene representation into three distinct components: a low-quality triangle mesh for coarse geometry, a view-dependent displacement map for surface detail, and a compressed Instant-NGP hash table for density and color. Unlike pure rasterization methods that sacrifice geometric accuracy or pure ray-marching NeRFs that suffer from low frame rates, MixRT distributes the workload across rasterizers, texture mapping units, and SIMD units to achieve over 30 FPS at 1280x720 resolution while maintaining storage sizes below 80% of state-of-the-art baked representations [S1].

## How it works
**Inputs and Outputs:**
*   **Inputs:** A set of calibrated camera poses and images; a pre-trained or optimized MixRT model consisting of a triangle mesh, a displacement texture map, and an Instant-NGP hash table.
*   **Outputs:** A rendered RGB image for a given camera view.

**Data Structures:**
1.  **Triangle Mesh:**
    *   Stores geometric vertex coordinates $(x, y, z)$, texture coordinates $(u, v)$, and polygonal face indices.
    *   Does **not** store per-vertex appearance parameters (color/density) [S1].
    *   Vertices are ordered to optimize cache hit rates for neighboring triangle access [S1].
2.  **View-Dependent Displacement Map:**
    *   A 2D texture map associated with the mesh vertices.
    *   Stores Spherical Harmonics (SH) coefficients and a scale factor per vertex to compute view-dependent offsets [S1].
3.  **Compressed NeRF Model (Instant-NGP Format):**
    *   A 3D embedding grid stored as a compact 1D hash table [S1].
    *   **Hash Table Configuration:** The number of levels is shrunk, and the hash table size is enlarged to optimize for rendering speed [S1].
    *   **MLP:** A small Multi-Layer Perceptron with 2 hidden layers, each containing 64 units, used to decode embeddings into density and color [S1].

**Scene Configuration:**
The unbounded scene domain is mapped into a finite sphere using the contraction function from [4] for the NeRF model components. The low-quality mesh and displacement map remain in their original coordinate space to leverage standard rasterization pipelines [S1].

**Rendering Pipeline:**
The rendering process follows a specific sequence to utilize hardware units efficiently:

1.  **Mesh Rasterization:** The triangle mesh is rasterized using hardware rasterizers. This determines the ray-mesh intersection point, denoted as $\mathbf{p}$ [S1].
2.  **Displacement Calibration:** Using texture coordinates associated with $\mathbf{p}$, the texture mapping units access the displacement map. This map contains SH coefficients and scale factors. These are used to compute a calibrated point $\mathbf{p}_{cali}$, which corrects the coarse mesh intersection for fine geometric details [S1].
3.  **Feature Retrieval:** The calibrated point $\mathbf{p}_{cali}$ is processed by SIMD units. The system retrieves embeddings for the eight closest vertices from the 3D hash table grid. These embeddings are obtained via trilinear interpolation of the queried hash table entries [S1].
4.  **Color and Density Decoding:** The interpolated embeddings are fed into the small MLP (2 layers, 64 hidden units) to produce the final volume density $\sigma$ and view-dependent color $\mathbf{c}$ [S1].
5.  **Compositing:** Standard volumetric rendering (alpha compositing) is performed using the retrieved $\sigma$ and $\mathbf{c}$ along the ray [S1].

**Pseudocode:**
```python
def render_mixrt(camera_ray, mesh, displacement_map, hash_table, mlp):
    """
    Renders a single ray using the MixRT representation.
    
    Args:
        camera_ray: Ray origin and direction.
        mesh: Triangle mesh with vertices, faces, and texture coordinates.
        displacement_map: Texture map storing SH coefficients and scale.
        hash_table: Instant-NGP style 1D hash table for 3D embeddings.
        mlp: Small MLP (2 layers, 64 hidden units) for density/color.
        
    Returns:
        color: Rendered RGB color.
        depth: Depth of the intersection.
    """
    
    # Step 1: Rasterization / Ray-Mesh Intersection
    # Use hardware rasterizer or efficient ray-AABB/triangle intersection
    # to find the intersection point p on the low-quality mesh.
    p, face_id, uv_coords = ray_mesh_intersect(camera_ray, mesh)
    
    if p is None:
        return background_color, infinity

    # Step 2: View-Dependent Displacement
    # Access displacement map using UV coordinates to get SH coefficients and scale.
    # Compute calibrated point p_cali.
    sh_coeffs, scale = displacement_map.sample(uv_coords)
    
    # Reconstruct view direction from camera ray
    view_dir = normalize(camera_ray.direction)
    
    # Evaluate SH function to get displacement vector
    # Note: Exact SH basis evaluation depends on the degree used.
    # Assuming standard SH basis evaluation function sh_eval.
    displacement_vector = sh_eval(sh_coeffs, view_dir) * scale
    
    p_cali = p + displacement_vector
    
    # Step 3: Feature Retrieval from Hash Table
    # Retrieve embeddings for the 8 closest vertices in the 3D grid.
    # This involves hashing the coordinates of the 8 surrounding grid points.
    embeddings = hash_table.query_trilinear(p_cali)
    
    # Step 4: MLP Decoding
    # Feed embeddings into the small MLP.
    density, color = mlp.forward(embeddings)
    
    # Step 5: Compositing (Simplified for single sample)
    # In a full pipeline, this would be integrated into a volume rendering loop.
    # For the intersection point, we assume this is the primary contribution.
    # Transmittance T is 1 at the surface for the first hit.
    alpha = 1.0 - exp(-density)
    
    return color, depth(p)
```

**Parameters and Typical Values:**
*   **Mesh Complexity:** Approximately 15 MB storage size [S1].
*   **MLP Architecture:** 2 layers, 64 hidden units each [S1].
*   **Hash Table:** Shrunk number of levels, enlarged size [S1].
*   **Resolution:** 1280x720 [S1].
*   **Performance:** > 30 FPS on MacBook M1 Pro [S1].

**Edge Cases and Pitfalls:**
*   **Direct Combination Failure:** Directly combining a low-quality mesh with a standard Instant-NGP hash table retains storage efficiency but fails to achieve real-time rendering speeds due to bottlenecks in the hash table level structure [S1].
*   **Mesh Quality vs. Detail:** A high-quality mesh with 5x more triangles yields ~0.3 lower PSNR than a low-quality mesh equipped with a hash table color field, while consuming 0.26x the storage size [S1]. Therefore, relying solely on mesh geometry for detail is inefficient.
*   **Coordinate Space:** The NeRF model requires the scene to be contracted into a finite sphere, while the mesh and displacement map remain in original space. Mixing these spaces incorrectly will cause misalignment [S1].

## Operating characteristics
*   **Time Complexity:** Rendering speed is optimized to > 30 FPS at 1280x720 on edge devices (e.g., MacBook M1 Pro) [S1]. The bottleneck in standard Instant-NGP is the number of hash table levels; MixRT mitigates this by shrinking levels and enlarging table size [S1].
*   **Memory/Storage Complexity:** Storage size is less than 80% of state-of-the-art baked methods (e.g., BakedSDF, which uses > 300 MB, while MixRT uses ~15 MB for the mesh component) [S1].
*   **Rendering Quality:** Achieves 0.2 PSNR higher than state-of-the-art methods on indoor scenes of the Unbounded-360 dataset [S1].
*   **Strengths:** Maximizes utilization of diverse hardware resources (Rasterizer, Texture Mapping Units, SIMD); cross-platform compatibility via WebGL; suitable for large-scale real-world scenes on edge devices [S1].
*   **Limitations:** Requires a pre-optimized low-quality mesh; relies on specific hardware features (SIMD, texture mapping) accessible via WebGL or similar graphics APIs; not a pure ray-marching solution, so transparency handling may differ from standard NeRF [S1].
*   **When to Use:** Real-time novel view synthesis on edge devices (laptops, mobile, web browsers) where storage and frame rate are critical constraints.
*   **When Not to Use:** Applications requiring explicit, high-fidelity geometric meshes without displacement approximation, or environments lacking standard graphics hardware acceleration (e.g., pure CPU inference without SIMD optimization).

## Background
MixRT was introduced in the paper "MixRT: Mixed Neural Representations For Real-Time NeRF Rendering" [S1]. The work challenges the convention that high-quality geometry (meshes with substantial triangles) is necessary for photorealistic rendering. It observes that a low-quality mesh combined with a hash-table-based color field and displacement map can achieve superior quality and efficiency. The method was developed to address the slow rendering speed of NeRF on edge devices, leveraging the capabilities of existing graphics hardware (rasterizers, texture mapping units, SIMD units) accessible via WebGL APIs. It builds upon Instant-NGP [24] for the compressed NeRF component and uses contraction functions from [4] for scene bounding.
