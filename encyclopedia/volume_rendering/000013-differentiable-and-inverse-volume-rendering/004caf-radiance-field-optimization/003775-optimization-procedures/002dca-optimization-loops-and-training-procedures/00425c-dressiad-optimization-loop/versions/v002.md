# DressiAD Optimization Loop

Also called: Dressi-AD Computational Graph Execution, DressiAD Training Loop

## Overview
The DressiAD Optimization Loop is a define-and-run differentiable rendering optimization procedure that constructs a computational graph, marks variables for gradient tracking, and executes forward and backward passes using Stochastic Gradient Descent (SGD) [S1]. It distinguishes itself from standard AD libraries by packing the backward pass into Vulkan command buffers, allowing the optimization loop to execute directly on the GPU without CPU-side backpropagation overhead [S1].

## How it works
**Inputs and Outputs:**
*   **Inputs:** Scene data (vertex positions, UVs, faces, matrices, environment map, albedo, metallic, roughness, normal, background) loaded into CPU memory as `CpuImage` buffers [S1]. A target image for loss calculation [S1].
*   **Outputs:** Optimized scene parameters (e.g., vertex positions, normal maps) saved as a GLTF file [S1].

**Data Structures:**
*   **CpuImage:** A simple buffer representing a 2D image used to store scene data [S1].
*   **Variable:** A data structure representing inputs and outputs of functions in the computational graph. It contains:
    *   `type`: One of `VEC3`, `VEC2`, `IVEC3`, `MAT4`, `FLOAT`, `VEC4` [S1].
    *   `size`: Size of the data [S1].
    *   `dirty` flag: Indicates if the variable has changed [S1].
    *   `requires_grad` flag: Marks the variable as an optimization target [S1].
    *   `creator`: Reference to the `Function` that generated this variable [S1].

**Parameters:**
*   `lr`: Learning rate for the SGD optimizer. Typical value: $0.01$ [S1].
*   `K`: Number of peeling steps for HardSoftRas. Typical value: $2$ [S1].
*   `r`: Radius parameter for HardSoftRas. Typical value: $0.01$ [S1].
*   `sigma`: Blending parameter for HardSoftRas. Calculated as $r / 7$ [S1].
*   `delta`: Silhouette edge width for HardSoftRas. Equal to $r$ [S1].

**Steps:**
1.  **Initialization:** Create a `DressiBasicRenderer` instance and load scene data from files into CPU memory [S1].
2.  **Graph Construction:** Call `BuildBasicRenderGraph` with scene variables and HardSoftRas parameters ($K, r, \sigma, \delta$) to construct the forward rendering computational graph [S1].
3.  **Target Marking:** Mark vertex positions and normal textures as optimization targets by setting their `requires-gradient` flags [S1].
4.  **Loss Calculation:** Compute the L1 loss between the target image and the rendered image:
    $$
    \text{Loss} = \text{Mean}(|\text{Target} - \text{Rendered}|)
    $$
    [S1].
5.  **Optimizer Setup:** Set the loss variable and an SGD optimizer function to the `DressiAD` instance [S1].
6.  **Iteration Loop:** For each iteration:
    a.  Check if any input variable has changed dirty flags. If so, reset `m_graph_static_cnt` to $0$ [S1].
    b.  If `m_graph_static_cnt` equals `FAST_REBUILD_COUNT`, set `m_init_status` to `InitStatus::STAGE` [S1].
    c.  If `m_graph_static_cnt` equals `FULL_REBUILD_COUNT`, set `m_init_status` to `InitStatus::SUBSTAGE` [S1].
    d.  Execute `execStep()` which performs the forward pass, constructs the backward pass, traverses the graph, packs it into Vulkan stages, and executes commands [S1].
    e.  Increment `m_graph_static_cnt` [G].
7.  **Cleanup:** Mark all input variables as clean recursively and set `m_init_status` to `FINISHED` [S1].

**Pseudocode:**

```python
class InitStatus:
    BACKWARD = 0
    STAGE = 1
    SUBSTAGE = 2
    FINISHED = 3

FAST_REBUILD_COUNT = 10  # Not given in the sources.
FULL_REBUILD_COUNT = 100 # Not given in the sources.

def is_any_variable_dirty_changed(vars):
    return any(v.dirty for v in vars)

def vk_queue_submit(cmd_buf):
    # Submits the Vulkan command buffer for execution
    pass

def Float(val):
    return Variable(type="FLOAT", value=val)

def sum_pixel_wise(vars_list):
    if not vars_list:
        return Variable(type="FLOAT", value=0.0)
    result = vars_list[0]
    for v in vars_list[1:]:
        result = result + v
    return result

class DressiAD:
    def __init__(self):
        self.m_loss_var = None
        self.m_optimizer = None
        self.m_init_status = InitStatus.BACKWARD
        self.m_graph_static_cnt = 0
        self.m_input_vars = []
        self.m_vk_cmd_buf = None

    def set_loss_var(self, loss_var):
        self.m_loss_var = loss_var
        self.m_init_status = InitStatus.BACKWARD

    def set_optimizer(self, optimizer_func):
        self.m_optimizer = optimizer_func

    def exec_step(self):
        if is_any_variable_dirty_changed(self.m_input_vars):
            self.m_graph_static_cnt = 0

        if self.m_graph_static_cnt == FAST_REBUILD_COUNT:
            self.m_init_status = InitStatus.STAGE
        elif self.m_graph_static_cnt == FULL_REBUILD_COUNT:
            self.m_init_status = InitStatus.SUBSTAGE

        input_vars, input_grad_vars = self.build_backward(self.m_loss_var)

        if self.m_optimizer:
            updated_vars = self.m_optimizer(input_vars, input_grad_vars)
            for var, updated in zip(input_vars, updated_vars):
                var.set_value(updated)

        vk_queue_submit(self.m_vk_cmd_buf)

        for v in self.m_input_vars:
            v.set_dirty_recursively(False)

        self.m_init_status = InitStatus.FINISHED
        self.m_graph_static_cnt += 1

    def build_backward(self, loss_var):
        fwd_bwds_map = {}
        func_queue = []

        fwd_bwds_map[loss_var] = [Float(1.0)]
        creator = loss_var.get_creator()
        if creator:
            func_queue.append(creator)

        if self.m_init_status <= InitStatus.BACKWARD:
            while func_queue:
                func = func_queue.pop()
                input_grads = func.build_bwd(fwd_bwds_map[func.output])
                for x, gx in zip(func.inputs, input_grads):
                    if x not in fwd_bwds_map:
                        fwd_bwds_map[x] = []
                    fwd_bwds_map[x].append(gx)
                    x_creator = x.get_creator()
                    if x_creator:
                        func_queue.append(x_creator)

        input_vars = []
        input_grad_vars = []
        for x, gxs in fwd_bwds_map.items():
            input_vars.append(x)
            input_grad_vars.append(sum_pixel_wise(gxs))

        return input_vars, input_grad_vars
```

**Edge Cases and Pitfalls:**
*   **Dirty Flags:** Input variables must correctly update dirty flags so the system can detect changes and reset the static counter [S1].

## Subtopics

### NeRF Training Loop
*   **What it is:** A training loop for NeRF that uses volume rendering and differentiable rendering to optimize neural radiance fields.
*   **Difference:** Uses volume rendering equation and ray marching, whereas DressiAD uses rasterization-based rendering.
*   **When to choose:** When optimizing neural radiance fields for novel view synthesis.
*   **Link:** [NeRF Training Loop](970-nerf-training-loop.md)

### Optimization Configuration (Adam + Exponential Decay + Selective L2)
*   **What it is:** A configuration for optimization using Adam optimizer with exponential decay and selective L2 regularization.
*   **Difference:** Uses Adam optimizer instead of SGD, and includes regularization.
*   **When to choose:** When Adam optimizer and regularization are beneficial for convergence.
*   **Link:** [Optimization Configuration (Adam + Exponential Decay + Selective L2)](2133-optimization-configuration-adam-exponential-decay-selective-.md)

### Neural Volume Rendering Training (MSE)
*   **What it is:** A training loop for neural volume rendering using Mean Squared Error (MSE) loss.
*   **Difference:** Uses MSE loss instead of L1 loss, and focuses on volume rendering.
*   **When to choose:** When MSE loss is preferred for regression tasks in volume rendering.
*   **Link:** [Neural Volume Rendering Training (MSE)](3429-neural-volume-rendering-training-mse.md)

### Stage-based Differentiable Volume/Radiance Field Training
*   **What it is:** A training procedure that divides the optimization process into stages.
*   **Difference:** Uses a stage-based approach for optimization, whereas DressiAD uses a single loop with graph rebuilding.
*   **When to choose:** When a staged optimization approach is beneficial for convergence.
*   **Link:** [Stage-based Differentiable Volume/Radiance Field Training](4241-stage-based-differentiable-volume-radiance-field-training.md)

### Photometric Optimization
*   **What it is:** An optimization method that uses photometric consistency as a loss function.
*   **Difference:** Uses photometric loss instead of pixel-wise loss.
*   **When to choose:** When photometric consistency is important for the task.
*   **Link:** [Photometric Optimization](5790-photometric-optimization.md)

### Staggered Optimization Scheme
*   **What it is:** An optimization scheme that staggers the optimization of different parameters.
*   **Difference:** Staggers parameter optimization, whereas DressiAD optimizes all marked parameters simultaneously.
*   **When to choose:** When staggered optimization improves convergence.
*   **Link:** [Staggered Optimization Scheme](5832-staggered-optimization-scheme.md)

### Optimization Baselines
*   **What it is:** Baseline optimization methods for comparison.
*   **Difference:** Provides baseline methods for evaluation.
*   **When to choose:** When comparing new optimization methods against baselines.
*   **Link:** [Optimization Baselines](6675-optimization-baselines.md)

### Generalized Rendering Models
*   **What it is:** Generalized rendering models that support various rendering techniques.
*   **Difference:** Supports multiple rendering techniques, whereas DressiAD focuses on rasterization-based rendering.
*   **When to choose:** When a generalized rendering model is needed.
*   **Link:** [Generalized Rendering Models](6681-generalized-rendering-models.md)

### Two-Stage Inverse Rendering Optimization
*   **What it is:** An inverse rendering optimization method that uses a two-stage approach.
*   **Difference:** Uses a two-stage approach for inverse rendering.
*   **When to choose:** When a two-stage approach is beneficial for inverse rendering.
*   **Link:** [Two-Stage Inverse Rendering Optimization](7387-two-stage-inverse-rendering-optimization.md)

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Not given in the sources.
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Not given in the sources.
*   **Strengths:** Hardware-agnostic design, efficient GPU execution of backward passes, and reactive shader packing [S1].
*   **Limitations:** Requires Vulkan support, and the define-and-run paradigm may limit flexibility compared to eager execution frameworks [S1].
*   **When to use:** When optimizing differentiable rendering parameters with a focus on GPU efficiency and hardware agnosticism [S1].
*   **When not:** When eager execution or dynamic computational graphs are required [S1].

## Background
The DressiAD Optimization Loop is part of the Dressi system, a hardware-agnostic differentiable renderer with reactive shader packing and soft rasterization [S1]. It was proposed in the paper "Dressi: A Hardware-Agnostic Differentiable Renderer with Reactive Shader Packing and Soft Rasterization" [S1]. The system is designed to provide a flexible and efficient framework for differentiable rendering optimization [S1].
