# 3D Gaussian Data Layout

Also called: 3DGS Parameter Storage, Gaussian Struct Definition, GaussianModel, GaussianModel PyTorch Module

## Overview
The 3D Gaussian Data Layout defines the in-memory representation of a single 3D Gaussian primitive within differentiable volume rendering pipelines, aggregating position, scale, opacity, rotation, spherical harmonics (SH) coefficients, and precomputed covariance into a contiguous structure [S1, unofficial]. It sets itself apart from raw point-cloud representations by explicitly storing the full covariance matrix (or its decomposition) to enable fast tile-culling and analytic gradient propagation during backpropagation [S1, unofficial].

## How it works
### Inputs and Outputs
The layout serves as the fundamental unit of storage for the renderer and optimizer.
- **Input**: None (it is a static data structure definition).
- **Output**: A memory block containing all attributes required for rasterization and gradient computation.

### Data Structures
There are two primary implementations of this layout found in the sources: a Rust-based contiguous struct for rendering pipelines and a PyTorch-based module for optimization.

#### Rust Implementation (Rendering Pipeline)
Defined in `src/gaussians.rs` of the `splat` repository [S1, unofficial]. The struct `Gaussian` uses `nalgebra` types for linear algebra operations.

```rust
#[derive(Clone, Debug)]
pub struct Gaussian {
    pub position: na::Vector3<f32>,  // x, y, z
    pub scale: na::Vector3<f32>,    // scale_0, scale_1, scale_2
    pub opacity: f32,               // opacity
    pub rotation: na::Quaternion<f32>,  // w, x, y, z
    pub sh: na::SVector<f32, 48>,   // f_dc_0..3 and f_rest_0 ... f_rest_44
    pub cov3d: na::Matrix3<f32>,    // 3x3 symmetric covariance matrix
}
```

**Field Details:**
- `position`: 3 floats.
- `scale`: 3 floats.
- `opacity`: 1 float.
- `rotation`: 4 floats (quaternion).
- `sh`: 48 floats. This supports up to degree 3 spherical harmonics (3 DC + 45 rest coefficients) [S1, unofficial]. The number of coefficients is controlled by `sh_dim` (3 for DC, 12 for degree 1, 27 for degree 2, 48 for degree 3) [S1, unofficial].
- `cov3d`: 9 floats (3x3 matrix). Note: While the matrix is 3x3, it is symmetric, so only 6 unique values are strictly necessary, but the layout stores the full matrix [S1, unofficial].

#### PyTorch Implementation (Optimization Module)
Defined in `GaussianModel` of the `mini-splat` repository [S2, unofficial]. This layout stores parameters in log-space or raw tensors to facilitate gradient-based optimization.

**Internal Parameters:**
- `_xyz`: `torch.Tensor` of shape `(N, 3)`, dtype `float`. Stores 3D positions.
- `_features_dc`: `torch.Tensor` of shape `(N, 1, 3)`, dtype `float`. Stores 0th degree SH coefficients (colors).
- `_scaling`: `torch.Tensor` of shape `(N, 3)`, dtype `float`. Stores log-scales.
- `_rotation`: `torch.Tensor` of shape `(N, 4)`, dtype `float`. Stores quaternions.
- `_opacity`: `torch.Tensor` of shape `(N, 1)`, dtype `float`. Stores log-odds opacity.

### Numbered Steps: Accessing Physical Properties
To obtain the physical values from the PyTorch optimization layout, the following transformations are applied [S2, unofficial]:

1.  **Get Scaling**: Compute `scale = torch.clamp(torch.exp(self._scaling), max=10.0)`. This converts log-space scaling to linear space with an upper bound of 10.0.
2.  **Get Rotation**: Compute `rotation = torch.nn.functional.normalize(self._rotation)`. This ensures quaternions are unit-length.
3.  **Get Opacity**: Compute `opacity = torch.sigmoid(self._opacity)`. This converts log-odds to probability space $[0, 1]$.
4.  **Get Color**: If precomputed colors are not provided, compute from SHs. Let `shs_view` be the features transposed and viewed as `(-1, 3, (max_sh_degree+1)^2)`. Let `dir_pp` be the direction from camera center to Gaussian mean. Normalize `dir_pp`. Compute `colors_precomp = torch.clamp_min(sh2rgb(active_sh_degree, shs_view, dir_pp_normalized) + 0.5, 0.0)` [S3, unofficial].

### Formulas
- **Scaling**: $s = \min(\exp(s_{log}), 10.0)$
- **Opacity**: $\alpha = \frac{1}{1 + e^{-\alpha_{log}}}$
- **Rotation Normalization**: $q_{norm} = \frac{q}{\|q\|_2}$

### Parameters
- `sh_dim`: The number of spherical harmonics coefficients. Typical values: 3 (DC only), 12 (degree 1), 27 (degree 2), 48 (degree 3) [S1, unofficial].
- `max_scale`: 10.0 (clamp limit for scaling) [S2, unofficial].

### Edge Cases and Pitfalls
- **Quaternion Normalization**: Quaternions must be normalized after every update step to remain valid rotations [S2, unofficial].
- **Scale Clamping**: Exponential scaling can lead to numerical instability; clamping to a maximum value (10.0) prevents excessively large splats [S2, unofficial].
- **Opacity Bounds**: Sigmoid activation ensures opacity stays within $[0, 1]$ [S2, unofficial].
- **SH Dimension Mismatch**: The layout assumes a fixed maximum SH dimension (48 floats) in the Rust struct, regardless of the actual active degree. This wastes memory if lower degrees are used but simplifies indexing [S1, unofficial].

## Subtopics

### [Gaussian Data Structure](2273-gaussian-data-structure.md)
The Gaussian Data Structure is the primary in-memory container for 3D Gaussian primitives in differentiable volume rendering pipelines. It aggregates per-primitive attributes—position, scale, opacity, rotation, spherical harmonics (SH) coefficients, and precomputed 3D covariance—into contiguous, cache-friendly arrays to enable efficient GPU rendering and optimization. It sets itself apart from raw point-cloud representations by explicitly storing the full covariance matrix (or its decomposition) to allow fast tile-culling and analytic gradient propagation during backpropagation. See [Gaussian Data Structure](2273-gaussian-data-structure.md).

### [Gaussian Data Packing](3257-gaussian-data-packing.md)
Gaussian Data Packing serializes 3D Gaussian Splat attributes into a fixed-width binary buffer to facilitate efficient GPU-side access during rasterization. It differs from sibling methods like [SPZ Packed Format](3926-spz-packed-format.md) by using an interleaved, texture-friendly layout with a fixed width of 8 `uint32_t` per Gaussian, rather than parallel buffers or image-based compression. See [Gaussian Data Packing](3257-gaussian-data-packing.md).

### GeometryState Allocation
GeometryState contains contiguous memory blocks for P Gaussians, used during the rasterization phase. It includes:
- `depths`: `float`, size P
- `clamped`: `float`, size P*3
- `internal_radii`: `float`, size P
- `means2D`: `float`, size P
- `cov3D`: `float`, size P*6 (6 unique elements of symmetric 3x3 matrix)
- `conic_opacity`: `float`, size P
- `rgb`: `float`, size P*3
- `tiles_touched`: `uint32_t`, size P
- `scanning_space`: variable size, allocated via `cub::DeviceScan::InclusiveSum`
- `point_offsets`: `uint32_t`, size P [S3, unofficial]

## Operating characteristics
- **Time Complexity**: Not given in the sources.
- **Memory Complexity**: $O(N \cdot C)$, where $N$ is the number of Gaussians and $C$ is the constant size of the Gaussian struct. For the Rust layout, $C = 3+3+1+4+48+9 = 68$ floats (272 bytes) per Gaussian [S1, unofficial]. For the PyTorch layout, $C = 3+3+3+4+1 = 14$ floats per Gaussian, plus overhead for tensors [S2, unofficial].
- **Measured Performance**: Not given in the sources.
- **Scaling**: The contiguous layout in Rust facilitates efficient GPU transfer and rendering [S1, unofficial]. The PyTorch layout allows for efficient gradient computation via automatic differentiation [S2, unofficial].
- **Strengths**: Explicit covariance storage enables fast culling and accurate gradients. Fixed-size layouts simplify memory management.
- **Limitations**: Fixed SH dimension (48 floats) may waste memory for lower-degree approximations. Log-space parameters require careful handling of gradients and clamping.

## Background
The 3D Gaussian Data Layout originates from the implementation of 3D Gaussian Splatting (3DGS) in various open-source repositories. The Rust implementation is found in `thomasantony/splat` [S1, unofficial], while the PyTorch implementation is found in `metin-yat/mini-splat` [S2, unofficial] and `NorahCadeJS/GAI-GS` [S3, unofficial]. These implementations adapt the original 3DGS paper's concepts into efficient, differentiable data structures for modern rendering pipelines.
