# WASM Data Packing

Also called: DataWorker Packing, Splat Buffer Allocation

## Overview
WASM Data Packing manages WebAssembly memory allocation and data packing for 3D Gaussian splat attributes (positions, rotations, scales, colors, selection) to prepare them for GPU upload or WASM-side processing [S1, unofficial]. It differs from pure GPU-buffer management by handling the intermediate step of serializing JavaScript/TypeScript data structures into contiguous linear buffers within the WebAssembly heap, ensuring alignment and capacity constraints are met before the data leaves the JavaScript runtime [S1, unofficial].

## How it works
**Inputs and Outputs:**
- **Input:** A `Splat` object containing attribute arrays (positions, rotations, scales, colors, selection) and metadata (vertex count, offset).
- **Output:** Contiguous regions in the WebAssembly linear memory (`HEAPF32` and `HEAPU8`) populated with splat data, ready for consumption by WASM functions or GPU upload.

**Data Structures:**
The `Splat` class fields are defined as [S1, unofficial]:
- `offset`: number
- `position`: `Float32Array[3]`
- `rotation`: `Float32Array[4]`
- `scale`: `Float32Array[3]`
- `selected`: boolean
- `vertexCount`: number
- `positions`: `Float32Array`
- `rotations`: `Float32Array`
- `scales`: `Float32Array`
- `colors`: `Uint8Array`
- `selection`: `Uint8Array`

**Memory Layout and Allocation:**
The method allocates specific buffers in WASM memory based on the `allocatedVertexCount` (the next power of 2 greater than or equal to `splat.vertexCount`) [S1, unofficial]. The sizes are:
- `positionsPtr`: $3 \times \text{allocatedVertexCount} \times 4$ bytes
- `rotationsPtr`: $4 \times \text{allocatedVertexCount} \times 4$ bytes
- `scalesPtr`: $3 \times \text{allocatedVertexCount} \times 4$ bytes
- `colorsPtr$: $4 \times \text{allocatedVertexCount}$ bytes
- `selectionPtr`: $\text{allocatedVertexCount}$ bytes
- `dataPtr`: $8 \times \text{allocatedVertexCount} \times 4$ bytes
- `worldPositionsPtr`: $3 \times 4 \times 4$ bytes (fixed size)
- `worldRotationsPtr`: $4 \times 4 \times 4$ bytes (fixed size)
- `worldScalesPtr`: $3 \times 4 \times 4$ bytes (fixed size) [S1, unofficial]

**Numbered Steps:**
1. **Initialization:** Call `initWasm()` which loads the WASM module via `createDataModule()`. If the module is not loaded, `pack()` waits for loading to finish, initializes WASM, and proceeds [S1, unofficial].
2. **Capacity Calculation:** Calculate `targetAllocatedVertexCount` as the smallest power of 2 greater than or equal to `splat.vertexCount`:
   $$ \text{targetAllocatedVertexCount} = 2^{\lceil \log_2(\text{splat.vertexCount}) \rceil} $$
   [S1, unofficial].
3. **Reallocation Check:** If `targetAllocatedVertexCount` is greater than the current `allocatedVertexCount`:
   a. Free old WASM buffers using `wasmModule._free()`.
   b. Update `allocatedVertexCount` to `targetAllocatedVertexCount`.
   c. Allocate new buffers using `wasmModule._malloc()` for each pointer defined above [S1, unofficial].
4. **Data Copying:** Copy splat attribute arrays into the newly allocated WASM memory regions:
   - Use `wasmModule.HEAPF32.set()` for float arrays (`positions`, `rotations`, `scales`, `data`).
   - Use `wasmModule.HEAPU8.set()` for byte arrays (`colors`, `selection`) [S1, unofficial].
5. **Concurrency Handling:** Concurrent calls to `pack()` are serialized via a loading flag and a `while` loop with `setTimeout` to yield to the event loop, preventing race conditions during WASM initialization [S1, unofficial].

**Pseudocode:**
```python
function pack(splat):
    # Ensure WASM module is loaded
    if not wasm_module_loaded:
        init_wasm()
        wait_for_wasm_load()

    # Calculate required capacity (next power of 2)
    target_count = 1
    while target_count < splat.vertex_count:
        target_count *= 2

    # Reallocate if capacity increased
    if target_count > allocated_vertex_count:
        # Free old buffers
        wasm_module._free(positions_ptr)
        wasm_module._free(rotations_ptr)
        wasm_module._free(scales_ptr)
        wasm_module._free(colors_ptr)
        wasm_module._free(selection_ptr)
        wasm_module._free(data_ptr)
        wasm_module._free(world_positions_ptr)
        wasm_module._free(world_rotations_ptr)
        wasm_module._free(world_scales_ptr)

        # Allocate new buffers
        allocated_vertex_count = target_count
        positions_ptr = wasm_module._malloc(3 * allocated_vertex_count * 4)
        rotations_ptr = wasm_module._malloc(4 * allocated_vertex_count * 4)
        scales_ptr = wasm_module._malloc(3 * allocated_vertex_count * 4)
        colors_ptr = wasm_module._malloc(4 * allocated_vertex_count)
        selection_ptr = wasm_module._malloc(allocated_vertex_count)
        data_ptr = wasm_module._malloc(8 * allocated_vertex_count * 4)
        world_positions_ptr = wasm_module._malloc(3 * 4 * 4)
        world_rotations_ptr = wasm_module._malloc(4 * 4 * 4)
        world_scales_ptr = wasm_module._malloc(3 * 4 * 4)

    # Copy data to WASM heap
    # Float32 arrays
    wasm_module.HEAPF32.set(splat.positions, positions_ptr / 4)
    wasm_module.HEAPF32.set(splat.rotations, rotations_ptr / 4)
    wasm_module.HEAPF32.set(splat.scales, scales_ptr / 4)
    # data_ptr copy implied by source but specific content not detailed [S1, unofficial]
    
    # Uint8 arrays
    wasm_module.HEAPU8.set(splat.colors, colors_ptr)
    wasm_module.HEAPU8.set(splat.selection, selection_ptr)

    # Handle concurrency serialization
    # In a real JS environment, this would involve async/await or event loop yielding
    # to prevent race conditions during initialization [S1, unofficial]
```

**Parameters and Typical Values:**
- `allocatedVertexCount`: Dynamic, determined by the next power of 2 of the input vertex count.
- `vertexCount`: The number of active splats in the current batch.

**Edge Cases and Pitfalls:**
- **Concurrent Calls:** Concurrent calls to `pack()` can cause race conditions during WASM initialization. The implementation uses a loading flag and `setTimeout` to serialize access [S1, unofficial].
- **Frequent Reallocation:** Memory is only freed and reallocated when the next power-of-2 capacity exceeds the current `allocatedVertexCount`. This prevents frequent reallocations for incremental vertex count changes [S1, unofficial].
- **Precision:** Float32 precision is used for positions, rotations, and scales. Log-scale storage for scales is handled by the caller before packing, as the packing method itself does not perform the log/exp transformation [S1, unofficial].

## Operating characteristics
- **Time Complexity:** Allocation is $O(1)$ amortized due to power-of-2 growth. Data copying is $O(N)$ where $N$ is the number of splats.
- **Memory Complexity:** $O(N)$ for the WASM heap buffers, where $N$ is the next power of 2 greater than or equal to the number of splats.
- **Measured Performance:** Not given in the sources.
- **Scaling:** Scales linearly with the number of splats. The power-of-2 allocation strategy may waste up to 50% of the allocated memory for non-power-of-2 counts.
- **Strengths:** Simplifies data transfer from JavaScript to WebAssembly/GPU by handling memory management and alignment. Prevents frequent reallocations.
- **Limitations:** Memory overhead due to power-of-2 allocation. Serialization of `pack()` calls may introduce latency in highly concurrent scenarios.
- **When to use:** When using WebAssembly for Gaussian Splatting rendering and needing to transfer data from JavaScript to the WASM module.
- **When not to use:** When direct GPU buffer management is preferred without an intermediate WASM layer, or when memory efficiency is critical and power-of-2 waste is unacceptable.

## Background
WASM Data Packing is part of the `gsplat.js` library, an unofficial JavaScript/TypeScript implementation of 3D Gaussian Splatting for the web [S1, unofficial]. It was developed to facilitate the transfer of Gaussian splat data from JavaScript to WebAssembly for efficient rendering and processing in browser environments.
