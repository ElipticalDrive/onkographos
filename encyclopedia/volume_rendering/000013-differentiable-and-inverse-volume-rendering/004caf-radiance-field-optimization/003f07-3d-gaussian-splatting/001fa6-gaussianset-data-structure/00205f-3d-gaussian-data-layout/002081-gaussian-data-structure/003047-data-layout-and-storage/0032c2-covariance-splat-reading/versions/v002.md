# Covariance Splat Reading

Also called: CovSplat Data Layout and Reading, CovSplat struct, ReadCovSplat, gsplat texture storage, readCovArrays

## Overview
Covariance Splat Reading is a method for decoding a single 3D Gaussian Splat from compressed texture storage into a structured representation suitable for rasterization. It solves the problem of efficiently retrieving and unpacking Gaussian parameters (position, color, opacity, and covariance) from a GPU-friendly texture array format. It differs from raw buffer access by handling the specific packing scheme used in the `gsplat` ecosystem, where covariance data is split across two texture layers and requires explicit unpacking of scale-quaternion derived components [S1, unofficial].

## How it works
**Inputs:**
- `index`: Integer index of the splat to read.
- `numSplats`: Total number of splats in the scene.
- `texture1`: `usampler2DArray` containing the first half of packed splat data.
- `texture2`: `usampler2DArray` containing the second half of packed splat data.
- `splatTexCoord(index)`: Helper function returning the `ivec3` coordinate for a given splat index in the texture array.

**Outputs:**
- `covsplat`: A `CovSplat` struct containing the decoded properties.

**Data Structures:**
The `CovSplat` struct layout is defined as follows [S1, unofficial]:
- `center`: `vec3` (3D position).
- `flags`: `uint` (activity status).
- `rgba`: `vec4` (color and opacity).
- `xxyyzz`: `vec3` (diagonal elements of the covariance matrix).
- `xyxzyz`: `vec3` (off-diagonal elements of the covariance matrix).
- `index`: `int` (original index).

The covariance matrix $\Sigma$ is reconstructed from `xxyyzz` and `xyxzyz`. The values in these fields are derived from a scale-quaternion representation, where scales are typically stored in log-space to ensure positivity [S1, unofficial]. The exact bit-packing of `packed1` and `packed2` into these fields is handled by the `unpackSplatExtCov` function, which is not fully detailed in the source but is implied to decode the `uvec4` textures into the vector components [S1, unofficial].

**Steps:**
1. Initialize `covsplat.flags` to `0u`.
2. Validate the input `index`: if `index < 0` or `index >= numSplats`, set `covsplat.flags` to `0u` and return [S1, unofficial].
3. Compute the texture coordinate: `coord = splatTexCoord(index)`.
4. Fetch the first packed data word: `packed1 = texelFetch(texture1, coord, 0)`.
5. Fetch the second packed data word: `packed2 = texelFetch(texture2, coord, 0)`.
6. Call the unpacking routine: `unpackSplatExtCov(packed1, packed2, covsplat.center, covsplat.rgba, covsplat.xxyyzz, covsplat.xyxzyz)` [S1, unofficial].
7. Determine activity: If `covsplat.xxyyzz` and `covsplat.xyxzyz` are not all zero, set `covsplat.flags = GSPLAT_FLAG_ACTIVE`. Otherwise, set `covsplat.flags = 0u` [S1, unofficial].
8. Set `covsplat.index = index` [S1, unofficial].

## Operating characteristics
- **Time Complexity:** $O(1)$ per splat, as it involves a fixed number of texture fetches and unpacking operations.
- **Memory Complexity:** $O(1)$ auxiliary memory for the `CovSplat` struct.
- **Performance:** Efficient for GPU-based rendering due to texture-based access patterns and Structure-of-Arrays (SoA) compatibility [5568-splat-data-buffer-layout.md].
- **Strengths:** Compact storage via texture arrays; fast random access to individual splats.
- **Limitations:** Requires custom unpacking logic not fully detailed in the source; dependent on specific texture coordinate mapping (`splatTexCoord`) [S1, unofficial].

## Background
This method is part of the `gsplat` ecosystem, specifically used in the `sparkjsdev/spark` project for handling 3D Gaussian Splatting data [S1, unofficial]. It builds on the general principles of SoA data layout and log-scale storage for stability [5568-splat-data-buffer-layout.md, S1, unofficial].
