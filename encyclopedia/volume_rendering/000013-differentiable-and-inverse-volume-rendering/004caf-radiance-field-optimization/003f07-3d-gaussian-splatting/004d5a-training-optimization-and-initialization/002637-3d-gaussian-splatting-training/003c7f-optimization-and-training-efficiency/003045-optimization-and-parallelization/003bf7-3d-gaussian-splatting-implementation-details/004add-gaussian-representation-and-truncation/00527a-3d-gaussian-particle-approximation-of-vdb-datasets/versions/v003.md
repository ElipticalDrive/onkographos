# 3D Gaussian Particle Approximation of VDB Datasets

Also called: Gaussian Particle Approximation, Gaussian Particle Rendering, VDB to Gaussian Conversion

## Overview
This method converts OpenVDB volumetric datasets into a set of non-overlapping 3D Gaussian particles to enable memory-efficient, lossy representation with Level of Detail (LOD) support [S1, unofficial]. It solves the problem of rendering large sparse volumetric data in real-time by mapping voxel regions to Gaussian primitives, which are then rendered via forward ray marching using NVIDIA OptiX [S1, unofficial]. Unlike standard Gaussian Splatting which often uses overlapping primitives for surface reconstruction, this approach leverages the strictly non-overlapping nature of OpenVDB leaf nodes to create a particle-based volume renderer [S1, unofficial]. It differs from [Inverse Multiquadric Splatting](9910-inverse-multiquadric-splatting.md) by using explicit Gaussian density functions rather than implicit radial basis functions, and from [Voxel-based Gaussian Splatting](13071-voxel-based-gaussian-splatting.md) by operating on the VDB tree structure directly rather than a uniform voxel grid.

## How it works

### Inputs and Outputs
**Inputs:**
*   An OpenVDB grid containing scalar field data (density/opacity) or level-set data.
*   A camera configuration (origin, direction, projection matrix).
*   LOD level selection (Low, Medium, High).

**Outputs:**
*   A rendered image with color and opacity accumulation.
*   Device-side buffers containing Gaussian properties (position, covariance, opacity).

### Data Structures

**GaussianModel**
A parent class holding device-side pointers to contiguous arrays for all Gaussian properties [S1, unofficial].
*   `opacity`: Array of scalars (float).
*   `world_position`: Array of 3D vectors (float3).
*   `covariance`: Array of 3D vectors (float3) for ellipsoids, or scalars (float) for spheres.

**HitGroupRecord**
A structure initialized for Gaussian particle rendering that specifies the shaders associated with the Gaussian primitive [S1, unofficial].
*   `gModel`: Pointer to the `GaussianModel` object.

**Acceleration Structures (OptiX)**
*   **Geometry Acceleration Structure (GAS):** Built on a CUDA device-side array of Axis-Aligned Bounding Boxes (AABBs). Each AABB encloses a single Gaussian particle, defined by its minimum and maximum coordinates in OpenVDB Index Space [S1, unofficial].
    *   Build Flags: `OPTIX_BUILD_FLAG_ALLOW_COMPACTION`, `OPTIX_BUILD_INPUT_TYPE_CUSTOM_PRIMITIVES` [S1, unofficial].
*   **Instance Acceleration Structure (IAS):** Stores the GAS instance with the OpenVDB Grid transform. Sets visibility masks for all Gaussians to visible for primary and continuation rays [S1, unofficial].

### Numbered Steps

1.  **Data Generation (CPU):**
    1.  Retrieve all leaf nodes from the OpenVDB Grid Tree using the OpenVDB API [S1, unofficial].
    2.  For each leaf node (or cluster based on LOD), derive three Gaussian properties:
        *   **Position:** The centroid of the voxel region or its bounding box in world space [S1, unofficial].
        *   **Opacity:** The average scalar value of the voxel region to preserve local material characteristics [S1, unofficial].
        *   **Covariance:** The diagonal vector of the 3x3 covariance matrix representing spatial extent. For axis-aligned Gaussians, this is a 3D vector; for isotropic Gaussians, a single scalar [S1, unofficial].
    3.  *LOD Specifics:*
        *   **Low LOD:** Each leaf node is represented by a single Gaussian reflecting the distribution of active voxels [S1, unofficial].
        *   **Medium LOD:** Dense leaf nodes are merged into 4x4x4 groups; sparse into 2x2x2 groups. Remaining voxels are individual Gaussians [S1, unofficial].
        *   **High LOD:** Sparse leaf nodes contribute one Gaussian per active voxel; dense leaf nodes are merged into 2x2x2 blocks [S1, unofficial].
    4.  Exclude leaf nodes marked as "Tiled" (homogeneous regions storing a single value) as they are handled by the parent node's value mask [S1, unofficial].

2.  **Device Transfer:**
    1.  Allocate contiguous device-side buffers using `cudaMalloc` for opacity, world position, and covariance [S1, unofficial].
    2.  Copy data from host to device using `cudaMemcpy` [S1, unofficial].
    3.  Store device pointers in a `GaussianModel` object and add it to the OptiX Shader Binding Table (SBT) [S1, unofficial].

3.  **Acceleration Structure Build:**
    1.  Build the GAS using the array of AABBs derived from Gaussian extents in Index Space [S1, unofficial].
    2.  Build the IAS linking the GAS to the OpenVDB Grid transform [S1, unofficial].

4.  **Ray Tracing (GPU/OptiX):**
    1.  **Ray Generation:** Shoot primary rays from the camera using the `__raygen__` program [S1, unofficial].
    2.  **Intersection Test (`__intersection__`):**
        *   Use the primitive index to retrieve the Gaussian AABB [S1, unofficial].
        *   Perform ray-box intersection with the world AABB. If intersected, retrieve the Gaussian's center ($\mu$) and inverse covariance ($\Sigma^{-1}$) [S1, unofficial].
        *   Transform the ray into the Gaussian's local space using the inverse covariance matrix.
        *   Solve the quadratic equation to find entry ($t_0$) and exit ($t_1$) distances [S1, unofficial].
        *   Store $t_0$ and $t_1$ in the payload and exit early [S1, unofficial].
    3.  **Ray Marching and Density Evaluation:**
        *   Step along the ray using a predefined step size based on the distance between entry and exit points [S1, unofficial].
        *   For each sample point $x_k$, compute the difference $\delta = x_k - \mu$ [S1, unofficial].
        *   Compute the squared Mahalanobis distance $D^2 = \delta^\top \Sigma^{-1} \delta$ [S1, unofficial].
        *   Evaluate density $\rho_k = \exp(-D^2/2)$ [S1, unofficial].
    4.  **Absorption and Transmittance Update:**
        *   Compute `volume_factor` = $1/\det(\Sigma)$ [S1, unofficial].
        *   Calculate absorption $A_k = \rho_k \cdot \Delta t \cdot \text{volume\_factor}$, where $\Delta t$ is the step size [S1, unofficial].
        *   Update color: $C \leftarrow C + T_k \cdot c(\sigma_k) \cdot A_k$, where $c(\sigma_k)$ is the scattering color derived from opacity $\sigma_k$ (via transfer function) [S1, unofficial].
        *   Update transmittance: $T_{k+1} = T_k \cdot \exp(-A_k)$ [S1, unofficial].
    5.  **Ray Continuation:**
        *   Advance the ray origin: $o_{new} = o + d \cdot (t_1 - t_0)$, where $o$ is the current origin, $d$ is the direction, and $t_0/t_1$ are entry/exit points [S1, unofficial].
    6.  **Recursive Loop:**
        *   Initialize color, transmittance $= 1.0$, recursion\_depth $= 0$ [S1, unofficial].
        *   While recursion\_depth $< max\_depth$:
            *   Intersect world AABB; if no intersection, return background [S1, unofficial].
            *   For each Gaussian in AABB: if ray intersects, compute density/absorption, update color/transmittance, break [S1, unofficial].
            *   Update ray\_orig $+= ray\_dir \cdot (t_1 - t_0)$ [S1, unofficial].
            *   Call `optixTrace(payload)` with `RAY_TYPE_RADIANCE` [S1, unofficial].
            *   If recursion\_depth $> 10$, break [S1, unofficial].
        *   Final color $+= transmittance \cdot payload.result$ [S1, unofficial].

### Pseudocode

```python
# GaussianModel: Contains device pointers to opacity, position, covariance arrays
# HitGroupRecord: Contains pointer to GaussianModel

def raygen():
    ray = generate_camera_ray()
    payload = {
        'color': vec3(0, 0, 0),
        'transmittance': 1.0,
        'recursion_depth': 0
    }
    result = recursive_ray_trace(ray, payload)
    payload['color'] += payload['transmittance'] * result
    return payload['color']

def recursive_ray_trace(ray, payload):
    if payload['recursion_depth'] > 10:
        return vec3(0, 0, 0)
    
    t0, t1 = ray.min_t, ray.max_t
    
    # Intersect with world AABB (from IAS)
    if not intersect_world_aabb(ray, t0, t1):
        return vec3(0, 0, 0)
    
    # Intersect with GAS (Gaussian AABBs)
    # Note: In OptiX, this is handled by intersection/closesthit programs.
    # Here we simulate the logic described in the source for clarity.
    
    hit_gaussian = None
    hit_t0, hit_t1 = t0, t1
    
    # Find the first intersecting Gaussian in the path
    # In actual OptiX, this is done via __intersection__ and __closesthit__
    # We assume a function that returns the hit Gaussian and t0/t1
    if intersect_gaussian_aabb(ray, t0, t1):
        hit_gaussian = get_hit_gaussian()
        hit_t0, hit_t1 = get_hit_distances()
    else:
        return vec3(0, 0, 0)

    # Ray Marching within the Gaussian
    # Step size is derived from (t1 - t0)
    step_size = (hit_t1 - hit_t0) / num_samples # num_samples is a parameter
    
    for i in range(num_samples):
        t_sample = hit_t0 + i * step_size
        x_k = ray.origin + ray.direction * t_sample
        
        # Density Evaluation
        delta = x_k - hit_gaussian.position
        D2 = dot(delta, multiply_matrix_vector(hit_gaussian.inverse_covariance, delta))
        density = exp(-D2 / 2.0)
        
        # Absorption Calculation
        volume_factor = 1.0 / determinant(hit_gaussian.covariance)
        absorption = density * step_size * volume_factor
        
        # Radiance Accumulation
        scattering_color = get_scattering_color(hit_gaussian.opacity) # Via transfer function
        payload['color'] += payload['transmittance'] * scattering_color * absorption
        payload['transmittance'] *= exp(-absorption)
        
        if payload['transmittance'] < 0.001:
            break

    # Ray Continuation
    ray.origin = ray.origin + ray.direction * (hit_t1 - hit_t0)
    payload['recursion_depth'] += 1
    
    # Recursive Call
    return recursive_ray_trace(ray, payload)
```

### Parameters
*   **Grid Layout Variant:** The '5-4-3' variant is used for explanations and rendering samples [S1, unofficial].
    *   5-level nodes: $2^5 \times 2^5 \times 2^5 = 32,768$ children.
    *   4-level nodes: $2^4 \times 2^4 \times 2^4 = 4,096$ children.
    *   3-level (leaf) nodes: $2^3 \times 2^3 \times 2^3 = 512$ voxels [S1, unofficial].
*   **Build Flags:** `OPTIX_BUILD_FLAG_ALLOW_COMPACTION`, `OPTIX_BUILD_INPUT_TYPE_CUSTOM_PRIMITIVES` [S1, unofficial].
*   **Ray Type:** `RAY_TYPE_RADIANCE` for all `optixTrace` calls [S1, unofficial].
*   **Max Recursion Depth:** 10 (break condition) [S1, unofficial].

### Edge Cases and Pitfalls
*   **Non-overlapping Constraint:** The implementation uses non-overlapping Gaussians because OpenVDB leaf nodes are strictly non-overlapping cubic regions. This limits the model to three overarching refinement levels and introduces lossiness [S1, unofficial].
*   **NanoVDB Limitation:** NanoVDB does not support device-side traversal of the Grid Tree or device-side iterators/accessors. This creates a bottleneck for random access required in ray-BVH or ray-particle intersections. Therefore, NanoVDB cannot be used for 3D Gaussian generation or rendering in this pipeline; OpenVDB must be used for generation [S1, unofficial].
*   **NanoVDB HDDA Incompatibility:** NanoVDB's built-in HDDA transmittance algorithm only works with regular float grid volumes. It is invalid for overlapping and variable-size particle data with custom ray tracing pipelines [S1, unofficial].
*   **OptiX Register Constraint:** Propagating state via recursive `optixTrace` calls is limited by OptiX’s 8-payload register constraint, causing sub-optimal accumulation and inconsistent resetting of payload values [S1, unofficial].

## Operating characteristics

**Time and Memory Complexity:**
*   **Memory:** The memory footprint depends on the LOD and dataset. For the 'dragon' dataset:
    *   High LOD: 546MB, 23.3M Gaussians [S1, unofficial].
    *   Low LOD: 174.4MB, 7.4M Gaussians [S1, unofficial].
*   **Performance:** The renderer consistently provides above 150 FPS for all tested datasets (bunny_cloud, explosion, fire, utahteapot, venusstatue, dragon) across all LODs, even with millions of Gaussians [S1, unofficial].

**Strengths and Limitations:**
*   **Strengths:** Memory-efficient representation of sparse data; real-time performance via hardware-accelerated ray tracing (OptiX); support for transfer functions (unlike baked-color Gaussian splatting); unified representation of volumes and level-sets [S1, unofficial].
*   **Limitations:** Lossy representation due to non-overlapping constraint; limited to three LOD levels in current implementation; OptiX register constraints limit recursive state propagation; NanoVDB incompatibility requires CPU-side generation [S1, unofficial].

**When to Use:**
*   Scientific visualization (SciVis) of large sparse volumetric datasets.
*   Real-time rendering of VDB data where transfer functions are required.

**When Not to Use:**
*   Photorealistic rendering requiring overlapping Gaussian mixtures (due to non-overlapping constraint and register limits).
*   Scenarios requiring GPU-side VDB tree traversal (NanoVDB cannot be used).

## Background

**Origin:**
The method was introduced in the paper "3D Gaussian Particle Approximation of VDB Datasets: A Study for Scientific Visualization" [S1, unofficial]. It builds on the popularity of Gaussian approximation and mixture models in SciVis [S1, unofficial] and the success of Gaussian Splatting in stereoscopic image to 3D scene conversion [S1, unofficial].

**History and Development:**
The work explores the integration of OpenVDB and NVIDIA OptiX to leverage built-in memory compaction and hardware acceleration. It distinguishes itself from previous Gaussian mixture models in SciVis (e.g., Jang et al. [11]) by focusing on VDB integration and OptiX ray marching [S1, unofficial].

**Usage:**
The renderer is designed for SciVis applications, supporting transfer functions and unified hybrid rendering of volumes and level-sets. It uses the NVIDIA OptiX library for forward ray marching [S1, unofficial].
