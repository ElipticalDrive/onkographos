# 3D Gaussian Splatting Implementation Details

Also called: 3DGS CUDA kernel implementation, GS Implementation Parameters, Gaussian Splatting Training Configuration, Implementation Details, gsplat implementation details, half-precision rasterization implementation

## Overview
This article details the specific implementation parameters, optimization strategies, and variant algorithms used to train and render 3D Gaussian Splatting (3DGS) scenes. It addresses the practical challenges of differentiable volume rendering, including memory management, gradient stability, and handling specific scene conditions such as defocus, noise, or underwater scattering. It sets itself apart from general training pipelines by focusing on the low-level kernel behaviors, hyperparameter configurations, and specialized mathematical formulations required to achieve high-fidelity results in diverse environments.

## How it works

### Standard Training Configuration
The standard training process relies on the `gsplat` library [S2] and typically employs the Adam optimizer with a learning rate of $1 \times 10^{-3}$ [S2]. The spherical harmonic (SH) degree is often set to 1 for simplicity and efficiency [S2]. During each iteration, a single image from a random scene is selected as supervision [S2]. To ensure numerical stability during half-precision training, an automatic scaling factor is applied to the loss values [S1].

### Scene Extent and Initialization
The scene extent $e_{\text{scene}}$ determines the spatial bounds for Gaussian densification and pruning. The default 3DGS formulation calculates extent based on camera positions:
$$
e_{\text{scene}} = 1.1 \cdot \max_{i=1}^{N_{\text{cam}}} \|\bar{C} - C_i\|_2 \quad (9)
$$
$$
\bar{C} = \frac{1}{N_{\text{cam}}} \sum_{i=1}^{N_{\text{cam}}} C_i \quad (10)
$$
where $N_{\text{cam}}$ is the number of camera views, $C_i$ is the position of the $i$-th camera, and $\bar{C}$ is the average camera position [S3].

**Pitfall:** This default formulation is biased if cameras are clustered (e.g., orbiting a small object in a large environment), leading to an underestimated scene extent and incorrect splitting/pruning of Gaussians [S3].

**Correction:** To mitigate this, the scene extent can be calculated based on the Structure-from-Motion (SfM) point cloud:
$$
e'_{\text{scene}} = \frac{1}{N_{\text{SfM}}} \sum_{i=1}^{N_{\text{SfM}}} \|\bar{C} - p_i\|_2 \quad (11)
$$
where $N_{\text{SfM}}$ is the number of SfM points and $p_i$ is the $i$-th SfM point [S3].

### Rasterization and Memory Optimization
To reduce register pressure and memory bandwidth usage, custom CUDA kernels are implemented using the 3DGUT formulation [S1]. Key optimizations include:
1.  **Half-Precision Fetches:** Feature vectors are fetched in half-precision (FP16) during both forward and backward rasterization passes [S1].
2.  **Neural Network Precision:** MLPs used for appearance modeling (e.g., in Neural Harmonic Textures) are JIT-compiled using tiny-cuda-nn and trained/evaluated in FP16 [S1].

### Gradient Threshold Schedule
To control the number of Gaussians split or cloned during densification, an exponentially ascending gradient threshold is applied over the densification interval [S3]. This schedule ensures that the number of densified Gaussians corresponds to an exponential growth pattern, preventing premature saturation or excessive fragmentation [S3].

### Multi-Scale Constraint
For large-scale scenes with varying distances, a position-aware point adaptive control applies different scales to Gaussians based on viewer distance [S8]. The scaling factor $\gamma(\mu)$ is defined as:
$$
\gamma(\mu) = 
\begin{cases} 
1 & \text{if } \|\mu - c\|^2 < 2r \\
\|\mu - c\|^2 / r - 1 & \text{if } \|\mu - c\|^2 \ge 2r
\end{cases}
$$
where $r$ is the scene radius and $c$ is the center of cameras [S8]. The densification protocol is:
1.  If $\max(s) < g \cdot \gamma(\mu)$, perform cloning [S8].
2.  If $\max(s) \ge g \cdot \gamma(\mu)$, execute splitting [S8].
3.  Eliminate Gaussians where $\max(s) > b \cdot \gamma(\mu)$ [S8].
Here, $g$ and $b$ are scale threshold parameters for cloning and elimination, respectively [S8].

### Depth Extraction for Volume Updates
In methods requiring depth-aware updates (e.g., underwater rendering), depth $z$ is extracted from the current scene estimate at each pixel during rendering:
$$
z = \frac{\sum_{i=1}^M d_i \alpha_i T_i}{\sum_{i=1}^M \alpha_i T_i}
$$
where $d_i$ is the depth of Gaussian $i$, $\alpha_i$ is its opacity, and $T_i$ is the transmittance from preceding Gaussians [S7].

## Subtopics

### Corrected Scene-Extent
A method to calculate scene extent based on the SfM point cloud rather than camera positions to avoid bias from camera distribution (e.g., orbiting a small object in a large environment) [S3]. It sets itself apart from the default 3DGS extent calculation by using point cloud density rather than camera bounding boxes, ensuring appropriate Gaussian sizes for large outdoor scenes [S3].

### Selective Defocus Blurring
Predicts a per-Gaussian scale offset $\delta s_j$ to selectively enlarge covariances, creating pixel-wise variable blur kernels that match spatially varying scene blurriness [S4]. It sets itself apart from naive Gaussian blur (which blurs the whole image) or learnable single-kernel approaches by allowing spatially varying blur shapes and magnitudes [S4]. If $\delta s_j$ is predicted as a constant, it degrades to a uniform blur [S4].

### Denoise-GS
A self-supervised denoising method for sparse-view 3DGS that combines unsupervised image denoising with differentiable 3DGS [S5]. It uses Noise2Void (N2V) in two rounds: Round 1 trains a UNet to denoise images, which are then used to initialize and train 3DGS via InstantSplat; Round 2 fine-tunes the UNet using a composite loss on selected viewpoints [S5]. It sets itself apart from supervised methods by requiring no paired clean data and from N2N by not requiring paired noisy images, making it suitable for sparse viewpoints [S5].

### View-Dependent Opacity Kernel
A transparent Gaussian kernel where opacity is view-dependent, modeled by a half-period cosine function to approximate specular reflectance lobes [S6, unofficial]. It adds 5 learnable parameters ($\alpha, \theta, T, \beta$) to the standard configuration [S6, unofficial]. The opacity is:
$$
\hat{\alpha}(\theta, \beta, T, \alpha) = \alpha \cdot \frac{\cos(\max(0, \min(\frac{2\theta}{T}, \pi)))+1}{2}\exp(\beta)
$$
where $\theta$ is the angle between view direction and lobe orientation, $T$ controls angular span, and $\beta$ modulates sharpness [S6, unofficial]. It sets itself apart by enabling specular reconstruction without complex material models [S6, unofficial].

### Backscatter Estimation and Optimization
Adapts 3DGS for underwater scenes by estimating direct attenuation ($B_d$), infinite backscatter ($B_\infty$), and backscatter coefficient ($B_b$) [S7]. Backscatter is re-estimated every 500 steps by dividing the depth map into 10 clusters and fitting the bottom 1st percentile of RGB triplets in each cluster to the backscatter model [S7]. It sets itself apart by explicitly modeling ocean optics within the rendering loop [S7]. **Pitfall:** Camera sensors must have a linear response; gamma-corrected images cannot be used [S7].

### GS-IR Representation
Extends vanilla 3DGS for inverse rendering by adding normal vectors ($n$) and material properties (albedo $a$, roughness $\rho$, metallicity $m$) to the geometric and appearance parameters [S9]. It sets itself apart by enabling photorealistic relighting and material estimation using forward mapping splatting, unlike NeRF-based inverse rendering methods [S9].

## Operating characteristics

### Time and Memory Complexity
The standard implementation uses half-precision (FP16) memory fetches to reduce register pressure and memory bandwidth usage [S1]. The use of `gsplat` and custom CUDA kernels ensures efficient parallelization across pixels and splats [S2]. Memory consumption is managed by voxelizing the scene (e.g., $128 \times 320 \times 640$ for a $12.8\text{m} \times 32\text{m} \times 64\text{m}$ volume with $0.1\text{m}$ voxel size) [S2].

### Measured Performance
On the KITTI-360 dataset, the implementation achieves 81.58 FPS with 16.14 GB memory usage [S2]. On the Waymo dataset, it achieves 83.81 FPS with 10.41 GB memory usage [S2]. These results are compared against methods like MVSNeRF and PixelSplat [S2].

### Strengths and Limitations
**Strengths:** High rendering speed (real-time), efficient memory usage via half-precision, and flexibility in handling various scene conditions (defocus, noise, underwater) through specialized variants [S1, S2, S4, S5, S7].
**Limitations:** Default scene extent calculation is biased by camera distribution [S3]. Standard 3DGS struggles with underwater color distortion and sparse view noise without specific adaptations [S5, S7].

## Background
3D Gaussian Splatting was introduced as a real-time differentiable renderer for 3D scenes [26]. The implementation details described here are based on the `gsplat` library [S2] and various extensions for handling specific challenges such as scene extent [S3], defocus [S4], noise [S5], specular highlights [S6, unofficial], underwater rendering [S7], large-scale scenes [S8], and inverse rendering [S9]. The use of half-precision optimization and custom CUDA kernels is a common theme in high-performance implementations [S1].
