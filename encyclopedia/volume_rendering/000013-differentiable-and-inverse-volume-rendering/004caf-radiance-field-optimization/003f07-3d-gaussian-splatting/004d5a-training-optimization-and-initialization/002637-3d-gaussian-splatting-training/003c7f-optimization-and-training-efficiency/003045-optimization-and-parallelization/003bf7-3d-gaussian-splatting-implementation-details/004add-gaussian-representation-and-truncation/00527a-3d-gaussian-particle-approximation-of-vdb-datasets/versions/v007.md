# 3D Gaussian Particle Approximation of VDB Datasets

Also called: Gaussian Particle Approximation, Gaussian Particle Rendering, VDB to Gaussian Conversion

## Overview
This method converts OpenVDB volumetric datasets into a set of non-overlapping 3D Gaussian particles to enable memory-efficient, lossy representation with Level of Detail (LOD) support [S1, unofficial]. It solves the problem of rendering large sparse volumetric data in real-time by mapping voxel regions to Gaussian primitives that can be accelerated via hardware ray tracing (NVIDIA OptiX) [S1, unofficial]. Unlike standard Gaussian Splatting which often uses overlapping primitives for photorealism, this approach strictly enforces non-overlapping Gaussians derived from OpenVDB's hierarchical tree structure, limiting the model to specific refinement levels but ensuring deterministic node access [S1, unofficial]. It differs from [Voxel-based Gaussian Splatting](13071-voxel-based-gaussian-splatting.md) by explicitly leveraging OpenVDB's grid topology for generation rather than generic voxelization, and from [Directed Distance Field (DDF) for Gaussian Splatting](12854-directed-distance-field-ddf-for-gaussian-splatting.md) by treating both volumes and level-sets as scalar density fields rather than surface approximations [S1, unofficial].

## How it works

### Inputs and Outputs
*   **Input:** An OpenVDB grid containing scalar values (volumes) or signed distance fields (level-sets).
*   **Output:** A set of 3D Gaussian particles defined by mean ($\mu$), covariance ($\Sigma$), and opacity ($\alpha$), stored in contiguous device-side buffers, along with an OptiX Acceleration Structure (GAS/IAS) for ray intersection.

### Data Structures

**1. OpenVDB Grid Layout (5-4-3 Variant)**
The method assumes a fixed-depth tree structure [S1, unofficial]:
*   **5-level (Top-level):** $2^5 \times 2^5 \times 2^5 = 32,768$ children.
*   **4-level (Intermediate):** $2^4 \times 2^4 \times 2^4 = 4,096$ children.
*   **3-level (Leaf):** $2^3 \times 2^3 \times 2^3 = 512$ voxels.
*   **Masks:** Each node has a *Child Mask* (1 bit per child, indicating active sub-tree) and a *Value Mask* (1 bit per child, indicating a "Tile" where all voxels share a single value) [S1, unofficial].

**2. GaussianModel (Device-Side)**
A parent class containing pointers to contiguous arrays for all Gaussians [S1, unofficial]:
*   **Position:** `float3` (world space centroid).
*   **Covariance:** `float3` (diagonal of $\Sigma$) for ellipsoids, or `float` (scalar) for spheres.
*   **Opacity:** `float` (scalar density).
*   **AABB:** Each Gaussian has an associated Axis-Aligned Bounding Box defined by min/max coordinates in OpenVDB Index Space [S1, unofficial].

**3. HitGroupRecord**
Specifies shaders for the Gaussian primitive and holds a pointer to the `GaussianModel` object [S1, unofficial].

### Numbered Steps

**Phase 1: Data Generation (CPU)**
1.  **Retrieve Leaf Nodes:** Use the OpenVDB API to iterate through all leaf nodes of the grid tree [S1, unofficial].
2.  **Skip Tiles:** If a leaf node is marked as a "Tile" (homogeneous region), skip it; its value is stored in the parent's Value Mask [S1, unofficial].
3.  **Apply LOD Clustering:**
    *   *Low LOD:* Each leaf node becomes a single Gaussian.
    *   *Medium LOD:* Dense leaf nodes are merged into $4 \times 4 \times 4$ groups; sparse nodes into $2 \times 2 \times 2$ groups. Remaining voxels become individual Gaussians [S1, unofficial].
    *   *High LOD:* Sparse leaf nodes contribute one Gaussian per active voxel; dense nodes are merged into $2 \times 2 \times 2$ blocks [S1, unofficial].
4.  **Compute Properties:** For each resulting cluster/voxel:
    *   **Position ($\mu$):** Centroid of the voxel region or bounding box in world space [S1, unofficial].
    *   **Opacity ($\alpha$):** Average scalar value of the voxels in the region [S1, unofficial].
    *   **Covariance ($\Sigma$):** Diagonal vector representing spatial extent. If isotropic, a single scalar is used [S1, unofficial].
5.  **Transfer to GPU:** Allocate device memory using `cudaMalloc` and copy properties using `cudaMemcpy` into contiguous buffers [S1, unofficial].

**Phase 2: Acceleration Structure Build (GPU)**
1.  **Build GAS:** Create a Geometry Acceleration Structure using a CUDA device-side array of AABBs. Each AABB encloses one Gaussian particle [S1, unofficial].
    *   *Build Flags:* `OPTIX_BUILD_FLAG_ALLOW_COMPACTION`, `OPTIX_BUILD_INPUT_TYPE_CUSTOM_PRIMITIVES` [S1, unofficial].
2.  **Build IAS:** Create an Instance Acceleration Structure storing the GAS instance with the OpenVDB Grid transform. Set visibility masks for primary and continuation rays [S1, unofficial].

**Phase 3: Rendering Pipeline (OptiX)**
1.  **Ray Generation:** Shoot primary rays from the camera [S1, unofficial].
2.  **Intersection Test (`__intersection__`):**
    *   Retrieve the Gaussian's AABB using the primitive index.
    *   Perform ray-box intersection with the world AABB.
    *   If intersected, retrieve $\mu$ and $\Sigma^{-1}$.
    *   Transform the ray into the Gaussian's local space.
    *   Solve the quadratic equation for entry ($t_0$) and exit ($t_1$) distances.
    *   Store $t_0, t_1$ in the payload and exit early [S1, unofficial].
3.  **Ray Marching & Density Evaluation:**
    *   Step along the ray from $t_0$ to $t_1$ using a predefined step size $\Delta t$ [S1, unofficial].
    *   For each sample point $x_k$:
        *   Compute difference $\delta = x_k - \mu$.
        *   Compute squared Mahalanobis distance $D^2 = \delta^T \Sigma^{-1} \delta$.
        *   Evaluate density $\rho_k = \exp(-D^2 / 2)$ [S1, unofficial].
4.  **Absorption & Transmittance Update:**
    *   Compute volume factor: $V_f = 1 / \det(\Sigma)$ [S1, unofficial].
    *   Compute absorption: $A_k = \rho_k \cdot \Delta t \cdot V_f$.
    *   Update color: $C \leftarrow C + T_k \cdot c(\sigma_k) \cdot A_k$.
    *   Update transmittance: $T_{k+1} = T_k \cdot \exp(-A_k)$ [S1, unofficial].
5.  **Ray Continuation:**
    *   Advance ray origin: $o_{new} = o + d \cdot (t_1 - t_0)$ [S1, unofficial].
6.  **Recursive Tracing:**
    *   Call `optixTrace` with `RAY_TYPE_RADIANCE` to find the next Gaussian [S1, unofficial].
    *   Repeat until transmittance is negligible or max depth is reached [S1, unofficial].

### Pseudocode

```python
# GaussianModel: Contains device pointers to arrays of positions, covariances, opacities
# GAS: Acceleration structure of AABBs for Gaussians

def render_scene(camera_ray):
    # Initialize payload
    color = vec3(0.0)
    transmittance = 1.0
    recursion_depth = 0
    max_depth = 10
    
    # Recursive ray marching loop
    while recursion_depth < max_depth:
        # 1. Intersect with World AABB (GAS)
        t0, t1 = intersect_world_aabb(camera_ray)
        if t0 is None:
            break # No intersection, return background
            
        # 2. Iterate through Gaussians in the hit AABB
        # Note: In this non-overlapping model, typically one Gaussian is processed per segment
        # or the loop breaks after the first hit if strictly non-overlapping logic is enforced
        # per the source's "break" statement in the pseudo-code snippet.
        
        gaussian = get_gaussian_from_primitive_index()
        
        # 3. Intersect with Gaussian AABB
        if not intersect_gaussian_aabb(camera_ray, gaussian.aabb):
            continue
            
        # 4. Compute entry/exit in Gaussian local space
        # Transform ray to local space using inverse covariance
        local_ray = transform_ray_to_local(camera_ray, gaussian.covariance)
        t_local_0, t_local_1 = solve_quadratic_intersection(local_ray)
        
        # 5. March within Gaussian
        step_size = (t_local_1 - t_local_0) / num_samples # Predefined step size
        for i in range(num_samples):
            t_sample = t_local_0 + i * step_size
            x_k = local_ray.origin + t_sample * local_ray.direction
            
            # Density Evaluation
            delta = x_k - gaussian.position_local # Or transform x_k to local relative to mu
            # Note: Source defines delta = xk - mu in world/local context depending on transform
            # Assuming x_k is in local space where mu is origin or transformed appropriately
            D2 = dot(delta, multiply(gaussian.inv_covariance, delta))
            density = exp(-0.5 * D2)
            
            # Absorption Calculation
            volume_factor = 1.0 / determinant(gaussian.covariance)
            absorption = density * step_size * volume_factor
            
            # Radiance Accumulation
            scattering_color = lookup_transfer_function(gaussian.opacity)
            color += transmittance * scattering_color * absorption
            transmittance *= exp(-absorption)
            
        # 6. Ray Continuation
        # Advance ray origin to exit point of current Gaussian
        # Need to transform t_local_1 back to world space or use world coordinates
        exit_point_world = transform_local_to_world(local_ray.origin + t_local_1 * local_ray.direction)
        camera_ray.origin = exit_point_world
        
        recursion_depth += 1
        
        # 7. Recursive Trace for next Gaussian
        # Using OptiX optixTrace with RAY_TYPE_RADIANCE
        next_payload = optixTrace(camera_ray, RAY_TYPE_RADIANCE)
        color += transmittance * next_payload.color
        transmittance *= next_payload.transmittance
        
    return color
```

### Parameters
*   **Grid Layout:** 5-4-3 variant is standard [S1, unofficial].
*   **Build Flags:** `OPTIX_BUILD_FLAG_ALLOW_COMPACTION`, `OPTIX_BUILD_INPUT_TYPE_CUSTOM_PRIMITIVES` [S1, unofficial].
*   **Ray Type:** `RAY_TYPE_RADIANCE` (forward marching only) [S1, unofficial].
*   **Max Recursion Depth:** Typically 10 [S1, unofficial].

### Edge Cases and Pitfalls
*   **Non-overlapping Constraint:** The method relies on non-overlapping Gaussians because OpenVDB leaf nodes are strictly non-overlapping. This limits the model to three overarching refinement levels and introduces lossiness [S1, unofficial].
*   **NanoVDB Incompatibility:** NanoVDB does not support device-side traversal of the Grid Tree or iterators. It cannot be used for Gaussian generation or rendering in this pipeline; OpenVDB must be used for generation on the CPU [S1, unofficial].
*   **OptiX Register Constraint:** Propagating state via recursive `optixTrace` calls is limited by OptiX’s 8-payload register constraint, which can cause sub-optimal accumulation and inconsistent resetting of payload values [S1, unofficial].
*   **Transfer Functions:** Color is not baked into Gaussians. Transfer functions (colormap lookups) must be implemented in the shader, as the renderer supports scalar attributes for opacity/density [S1, unofficial].

## Operating characteristics

*   **Time Complexity:** Rendering performance is consistently above 150 FPS for tested datasets (bunny_cloud, explosion, fire, utahteapot, venusstatue, dragon) across all LODs, even with millions of Gaussians [S1, unofficial].
*   **Memory Complexity:** Memory footprint scales with the number of Gaussians.
    *   *Example (Dragon Dataset):*
        *   High LOD: 546 MB, 23.3M Gaussians.
        *   Low LOD: 174.4 MB, 7.4M Gaussians [S1, unofficial].
*   **Strengths:**
    *   Real-time performance via hardware-accelerated ray tracing (OptiX) [S1, unofficial].
    *   Memory efficiency through sparse OpenVDB representation and LOD clustering [S1, unofficial].
    *   Unified handling of volumes and level-sets [S1, unofficial].
*   **Limitations:**
    *   Lossy representation due to non-overlapping constraint and LOD merging [S1, unofficial].
    *   Limited to specific OpenVDB tree structures (5-4-3) for deterministic access [S1, unofficial].
    *   Cannot use NanoVDB for generation due to lack of device-side iterators [S1, unofficial].
*   **When to use:** Scientific visualization (SciVis) where real-time performance on large sparse volumetric data is required, and photorealistic overlapping Gaussian blending is not necessary [S1, unofficial].
*   **When not to use:** Photorealistic rendering requiring overlapping Gaussian mixtures, or when GPU-side data generation from NanoVDB is required [S1, unofficial].

## Background

*   **Origin:** The method was introduced in a study for Scientific Visualization exploring the integration of OpenVDB and NVIDIA OptiX [S1, unofficial].
*   **History:** It builds upon the popularity of 3D Gaussian approximation in stereoscopic image-to-3D scene conversion (Gaussian Splatting) [12] and earlier Gaussian mixture models in SciVis [11]. The authors aimed to leverage OpenVDB's memory compaction and OptiX's hardware acceleration for real-time ray marching [S1, unofficial].
*   **Usage:** Used in SciVis applications for rendering large challenging datasets like `bunny_cloud`, `explosion`, `fire`, `utahteapot`, `venusstatue`, and `dragon` [S1, unofficial].
