# TideGS
## Overview
TideGS is a fully out-of-core optimization framework for training 3D Gaussian Splatting (3DGS) that enables training with over one billion primitives on a single GPU with limited VRAM [S2, unofficial]. It solves the VRAM bottleneck of standard 3DGS by decoupling memory usage from the total scene size $N$, keeping the full parameter table on SSD and materializing only the per-iteration working set in GPU memory [S2, unofficial]. Unlike [Grendel-GS](7349-grendel-gs.md), which distributes Gaussians across multiple GPUs, TideGS operates on a single machine, treating GPU VRAM as a high-bandwidth working-set cache rather than a persistent parameter store [S2, unofficial].

## How it works
TideGS manages Gaussian parameters across an SSD–CPU–GPU hierarchy [S2, unofficial]. The method relies on the observation that each training iteration touches only a small subset of Gaussians visible from the current camera batch, creating sparsity and temporal locality [S2, unofficial].

### Inputs and Outputs
*   **Inputs:**
    *   Camera batch $\mathcal{B}_t$ at iteration $t$ [S2, unofficial].
    *   Total number of Gaussians $N$.
    *   Spatial block size $B$ (default 4096) [S2, unofficial].
    *   GPU VRAM capacity limit $C$.
    *   CPU cache size (e.g., 16 GB or 32 GB) [S2, unofficial].
*   **Outputs:**
    *   Updated Gaussian parameters $\Theta$ stored on SSD [S2, unofficial].
    *   Rendered images for the batch $\mathcal{B}_t$ [S2, unofficial].

### Data Structures and Layout
**Unified Parameter Layout:**
All learnable per-Gaussian attributes are stored in a logical layout $\Theta \in \mathbb{R}^{N \times D}$, where $D=59$ under the standard degree-3 spherical harmonic (SH) parameterization [S2, unofficial]. Physically, $\Theta$ is stored out-of-core as contiguous block records on SSD [S2, unofficial].

**Blocks:**
Gaussians are Morton-sorted to preserve spatial locality and partitioned into SSD-aligned blocks [S2, unofficial].
*   Block $k$ contains Gaussians indexed by $\text{Block}(k) = \Theta[kB : (k+1)B]$ for $k \in \{0, \dots, K-1\}$, where $K = \lceil N/B \rceil$ [S2, unofficial].
*   Each block is summarized by a bounding sphere for visibility culling [S2, unofficial].

**Sets:**
*   **Gaussian-level active set $I_t$:** The subset of Gaussian indices visible after rasterization for camera batch $\mathcal{B}_t$ at iteration $t$, which receive non-zero gradients [S2, unofficial].
*   **Block-level working set $K_t$:** The set of block indices that conservatively cover the Gaussian-level active set $I_t$, used for staging and caching [S2, unofficial].
*   **VRAM-resident set $R_t$:** The set of blocks currently materialized in GPU VRAM, maintained under capacity $C$ [S2, unofficial].

### Preprocessing
Before training, the block layout is built once:
1.  Morton-sort the $N$ primitives.
2.  Compute block bounds and statistics.
3.  Write the initial base segment to SSD [S2, unofficial].
This step takes 1.9 minutes for $\sim 102$M Gaussians and 21.2 minutes for $\sim 1.1$B Gaussians on MatrixCity, accounting for less than 0.5% of total training time [S2, unofficial].

### Training Loop
Each iteration $t$ follows four coordinated stages, with stages (1), (2), and (4) overlapped with (3) to amortize I/O latency with GPU computation [S2, unofficial].

1.  **Identify working set:** Compute $K_t$ via lightweight CPU-side block visibility tests (6-plane frustum tests against block bounding spheres) [S2, unofficial].
2.  **Prefetch & materialize:** Prefetch needed blocks into the CPU cache and materialize them in VRAM via an asynchronous host-to-device (H2D) stream [S2, unofficial].
3.  **Render & backprop:** Execute the standard 3DGS forward/backward pass on the resident blocks $R_t$ on GPU [S2, unofficial]. Fine-grained Gaussian-level filtering is executed on GPU within the retained blocks to ensure exact 3DGS semantics [S2, unofficial].
4.  **Evict & write back:** Evict cold blocks when VRAM/CPU caches are full; dirty evictions are propagated through the CPU cache and written back to SSD patch segments asynchronously [S2, unofficial].

### Pseudocode

```python
# TideGS Training Loop
# Constants
B = 4096  # Spatial block size (primitives per block)
D = 59    # Parameter dimensionality per Gaussian
C = 24 * 1024**3  # VRAM capacity limit in bytes (e.g., 24 GB)
CPU_CACHE_SIZE = 16 * 1024**3  # CPU cache size in bytes
K = (N + B - 1) // B  # Total number of blocks

# Preprocessing (done once before training)
# 1. Morton-sort N primitives
# 2. Compute block bounds (bounding spheres) and statistics
# 3. Write initial base segment to SSD
# End Preprocessing

# Initialize resident set and CPU cache
R_t = []  # List of block indices currently in VRAM
cpu_cache = {}  # Dictionary mapping block index to data array

for t in range(num_iterations):
    batch = camera_batches[t]
    
    # Stage 1: Identify working set (CPU)
    # Conservative CPU-side block visibility test (6-plane frustum test against bounding spheres)
    K_t = []
    for k in range(K):
        if block_bounding_sphere_intersects_frustum(k, batch):
            K_t.append(k)
            
    # Stage 2: Prefetch & materialize (Async H2D stream)
    # Evict cold blocks from VRAM if capacity C is exceeded
    while len(R_t) * B * D * 4 > C:
        evict_block(R_t, cpu_cache)
        
    for k in K_t:
        if k not in R_t:
            # Fetch from SSD or CPU cache
            if k in cpu_cache:
                data = cpu_cache[k]
            else:
                data = read_ssd_block(k)
                cpu_cache[k] = data
            # Asynchronously copy to GPU VRAM
            async_h2d_copy(k, data)
            R_t.append(k)
            
    # Stage 3: Render & backprop (GPU)
    # GPU-side fine filtering to get exact active Gaussian indices I_t
    I_t = gpu_frustum_culling(R_t, batch)
    # Execute standard 3DGS forward and backward pass
    loss, gradients = standard_3dgs_forward_backward(I_t, batch)
    # Update Adam optimizer states for active Gaussians (standard 3DGS step)
    update_adam_optimizer(I_t, gradients)
    
    # Stage 4: Evict & write back (Async overlap with next stages)
    # Mark modified blocks as dirty and write back to SSD asynchronously
    for k in R_t:
        if block_is_dirty(k):
            async_write_ssd_block(k)
```

### Parameters
*   **$D=59$:** Dimensionality of per-Gaussian parameter vector $\theta_i$ [S2, unofficial].
*   **$B=4096$:** Default spatial block size (primitives per block) [S2, unofficial].
*   **Batch size $|\mathcal{B}_t|$:** 4 for Mip-NeRF 360; 64 (throughput-oriented) or 16 (conservative) for MatrixCity [S2, unofficial].
*   **CPU cache size:** 16 GB (throughput-oriented) or 32 GB (conservative) for MatrixCity [S2, unofficial].
*   **Optimizer:** Adam with the 3DGS learning-rate schedule [S2, unofficial].

### Edge Cases and Pitfalls
*   **OS Page Caching:** OS page caching can skew SSD bandwidth measurements by serving data from DRAM. Mitigation: Use fresh run/cache directories for compared runs and a cold-start protocol to evict cached pages before standalone cold-cache measurements [S2, unofficial].
*   **Naive Offload Failure:** Naive offloading fails at $\sim 102$M Gaussians due to OOM because per-iteration parameters required by rasterization must reside in VRAM. Profiling a 25M-Gaussian model shows 12.13 GB GPU memory for these parameters [S2, unofficial].
*   **CLM Failure:** CLM fails at $\sim 1.1$B Gaussians due to 'Rasterization OOM' because global radix sort and auxiliary buffers exceed available VRAM (>22 GB), as it requires GPU-resident geometry (~45 GB at this scale) [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** Not explicitly given in sources [S2, unofficial].
*   **Memory Complexity:** VRAM scaling is $O(|R_t|)$ or $O(|I_t|)$, where $|R_t|$ is the capacity-bounded resident set and $|I_t|$ is the Gaussian active set after fine filtering. This contrasts with $O(N)$ scaling of other methods [S2, unofficial].
*   **Measured Performance:**
    *   **Mip-NeRF 360 (In-memory regime):** TideGS (Shuffle) achieves 3.24 img/s (309.1 ms/iter). TideGS (Trajectory) achieves 3.50 img/s (285.8 ms/iter). Native 3DGS achieves 3.95 img/s (253.5 ms/iter) [S2, unofficial].
    *   **MatrixCity $\sim 102$M:** TideGS PCIe traffic 0.10 GB/iter, Iter 90.7 ms. CLM PCIe traffic 0.41 GB/iter, Iter 100.8 ms [S2, unofficial].
    *   **MatrixCity $\sim 1.1$B:** TideGS PCIe traffic 0.97 GB/iter, Iter 525.6 ms, GPU Utilization 49.5%. CLM fails with OOM [S2, unofficial].
*   **Quality Consistency:** On Mip-NeRF 360, TideGS PSNR 28.9157 vs Native 3DGS 29.052 (gap 0.11 dB). SSIM 0.8689 vs 0.8694. LPIPS 0.1399 vs 0.1394 [S2, unofficial].
*   **Strengths:** Enables training with >1B Gaussians on a single 24 GB GPU. Reduces PCIe traffic by 4x compared to CLM at $\sim 102$M Gaussians [S2, unofficial].
*   **Limitations:** Incurs modest overhead in the in-memory regime compared to Native 3DGS. Requires SSD storage capacity.
*   **When to use:** When training 3DGS scenes with billions of primitives on a single GPU with limited VRAM [S2, unofficial].
*   **When not to use:** When the scene fits entirely in GPU memory and maximum throughput is required (Native 3DGS is faster) [S2, unofficial].

## Background
TideGS was introduced in the paper "TideGS: Scalable Training of Over One Billion 3D Gaussian Splatting Primitives via Out-of-Core Optimization" [S2, unofficial]. It builds on the insight that 3DGS training is visibility-induced sparse and trajectory-conditioned, allowing GPU memory to serve as a working-set cache [S2, unofficial]. It is implemented in PyTorch 2.6.0 with CUDA 12.4 and evaluated on NVIDIA RTX A5000 GPU (24 GB VRAM), AMD EPYC 7532 CPU, 256 GB DDR4, and Samsung PM9A3 NVMe SSD [S2, unofficial].
