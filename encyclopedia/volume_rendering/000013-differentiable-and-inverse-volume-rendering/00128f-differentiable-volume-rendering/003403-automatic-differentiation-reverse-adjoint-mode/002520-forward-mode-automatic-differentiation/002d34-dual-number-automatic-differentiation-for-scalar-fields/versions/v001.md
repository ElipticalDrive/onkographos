# Dual Number Automatic Differentiation for Scalar Fields

Also called: Exact Normals via Forward Automatic Differentiation, Forward-mode AD via dual numbers, dual_object gradient computation

## Overview
This method computes the exact gradient of a scalar field $f: \mathbb{R}^3 \to \mathbb{R}$ at a specific point by evaluating the field using dual numbers, which automatically propagate derivative information alongside the function value [S1, S2, unofficial]. It is primarily used to compute exact vertex normals for implicit surfaces, avoiding the numerical instability and approximation errors inherent in finite difference methods [S2, unofficial]. Unlike reverse-mode automatic differentiation, which requires storing the entire computation graph, this forward-mode approach computes the gradient simultaneously with the forward evaluation, making it suitable for GPU kernels where memory footprint is critical [S1, S2, unofficial].

## How it works
The method relies on the algebraic properties of dual numbers. A dual number $z$ is defined as $z = a + b\epsilon$, where $a$ is the primal value, $b$ is the dual part (the derivative), and $\epsilon$ is a dual unit satisfying $\epsilon^2 = 0$ [S1, unofficial]. When a differentiable function $f$ is evaluated on a dual number input, the result is $f(a + b\epsilon) = f(a) + f'(a)b\epsilon$ [S1, unofficial]. By setting the dual part $b$ to 1 for the coordinate of interest and 0 for others, the dual part of the output yields the partial derivative with respect to that coordinate.

### Inputs and Outputs
- **Input**: A point $p = (x, y, z)$ in 3D space and a scalar field function $f(x, y, z)$ [S1, S2, unofficial].
- **Output**: The normalized gradient vector $\mathbf{n} = (n_x, n_y, n_z)$, which represents the surface normal at $p$ [S2, unofficial].

### Data Structures
The implementation uses a templated dual number type, typically `autodiff::Real<1, T>` or a custom `dual_object` class [S1, S2, unofficial].
- **Dual Number Layout**: Contains a primal value (scalar type `T`) and a dual vector (gradient components) [S1, unofficial].
- **CRTP Base Class**: The base class `object<Scalar>` declares pure virtual functions `value_grad()` returning the dual type and `value()` returning the scalar type [S1, unofficial]. Derived classes use the Curiously Recurring Template Pattern (CRTP) via a `derived()` method to enable static polymorphism [S1, unofficial].

### Steps
1.  **Initialize Primal Coordinates**: Extract the floating-point coordinates $x, y, z$ from the input point $p$ [S2, unofficial].
2.  **Construct Dual Numbers for Partial Derivatives**: Create three dual number instances, each initialized with the primal coordinate and a dual vector representing the direction of differentiation [S1, unofficial]:
    -   $dx = \text{dual}(x, (1, 0, 0))$
    -   $dy = \text{dual}(y, (0, 1, 0))$
    -   $dz = \text{dual}(z, (0, 0, 1))$
    [S1, unofficial]
3.  **Evaluate Scalar Field**: Pass the dual numbers $dx, dy, dz$ to the scalar field evaluation function $f$ [S1, S2, unofficial]. The function must be implemented to support dual number arithmetic (operator overloading for $+, -, *, /$) [S2, unofficial].
4.  **Extract Derivatives**: Retrieve the dual parts from the resulting dual numbers to obtain the partial derivatives [S2, unofficial]:
    -   $n_x = \text{derivative}(f, \text{wrt}(x), \text{at}(x, y, z))$
    -   $n_y = \text{derivative}(f, \text{wrt}(y), \text{at}(x, y, z))$
    -   $n_z = \text{derivative}(f, \text{wrt}(z), \text{at}(x, y, z))$
    [S2, unofficial]
5.  **Normalize**: Compute the Euclidean norm of the gradient vector and normalize the components [S2, unofficial]:
    $$ \|\mathbf{n}\| = \sqrt{n_x^2 + n_y^2 + n_z^2} $$
    $$ \mathbf{n}_{\text{final}} = \left( \frac{n_x}{\|\mathbf{n}\|}, \frac{n_y}{\|\mathbf{n}\|}, \frac{n_z}{\|\mathbf{n}\|} \right) $$
    [S2, unofficial]

### Pseudocode
The following Python-like pseudocode implements the core logic. It assumes a `Dual` class that supports arithmetic operations and exposes `.value` and `.grad` (a tuple of partial derivatives).

```python
def compute_normal(p: tuple, f: callable) -> tuple:
    """
    Compute the exact normal of a scalar field at point p using forward-mode AD.
    
    Args:
        p: A tuple (x, y, z) of floating point coordinates.
        f: A callable that accepts three Dual numbers and returns a Dual number.
        
    Returns:
        A tuple (nx, ny, nz) representing the normalized gradient.
    """
    x, y, z = p
    
    # Step 1: Construct dual numbers for each axis
    # dx has dual part (1, 0, 0), dy has (0, 1, 0), dz has (0, 0, 1)
    dx = Dual(value=x, grad=(1, 0, 0))
    dy = Dual(value=y, grad=(0, 1, 0))
    dz = Dual(value=z, grad=(0, 0, 1))
    
    # Step 2: Evaluate the scalar field with dual numbers
    # The function f must be implemented to propagate dual parts correctly
    result = f(dx, dy, dz)
    
    # Step 3: Extract partial derivatives from the dual part of the result
    # result.grad contains (df/dx, df/dy, df/dz)
    nx, ny, nz = result.grad
    
    # Step 4: Normalize the gradient vector
    norm = (nx**2 + ny**2 + nz**2)**0.5
    
    # Handle degenerate case where gradient is zero (stationary point)
    if norm == 0:
        return (0.0, 0.0, 0.0)
        
    nn = 1.0 / norm
    return (nx * nn, ny * nn, nz * nn)
```

### Parameters
-   **Vertex Property Registration**: In some implementations, the normal computation is registered as a vertex property using metadata such as `VertexProperty("normal", fname="compute_normal", dtype="T", shape=("dim",))` [S2, unofficial].
-   **Type Parameter**: The scalar type `T` (e.g., `float`, `double`) determines the precision of the primal and dual values [S2, unofficial].

### Edge Cases and Pitfalls
-   **Stationary Points**: If the gradient magnitude is zero (e.g., at a local extremum or saddle point), normalization fails. The implementation must handle this, typically by returning a zero vector or a default normal [G].
-   **Function Differentiability**: The scalar field function $f$ must be differentiable everywhere in the domain of interest. Non-differentiable operations (e.g., `abs`, `max` without subgradient definitions) will break the dual number propagation [S1, unofficial].
-   **Precision**: Dual number arithmetic may introduce slight precision differences compared to standard floating-point arithmetic due to the storage of dual parts, but this is generally negligible for normal computation [S2, unofficial].

## Subtopics

### Exact Normals via Forward Automatic Differentiation
Focuses on the application of this method specifically for computing surface normals for implicit geometry, highlighting its advantage over finite differences in avoiding aliasing and approximation errors [S2, unofficial].

### Forward-mode Automatic Differentiation
The broader category of AD techniques that compute derivatives by propagating tangent vectors forward through the computation graph, suitable for functions with many inputs and few outputs [Parent].

## Operating characteristics
-   **Time Complexity**: $O(1)$ per evaluation point, with a constant factor roughly 2-3 times that of a standard scalar evaluation due to the overhead of dual number arithmetic [S1, S2, unofficial].
-   **Memory Complexity**: $O(1)$ per evaluation point, as dual numbers store only the primal value and a fixed-size gradient vector (3 components for 3D) [S1, S2, unofficial].
-   **Strengths**: Provides exact analytical gradients, avoiding the truncation and round-off errors of finite differences. No need to store a computation graph, making it memory-efficient for GPU kernels [S1, S2, unofficial].
-   **Limitations**: Requires the scalar field function to be implemented with dual number support (operator overloading). Not suitable for functions with non-differentiable points unless subgradients are explicitly defined [S1, unofficial].
-   **When to Use**: When exact normals are required for ray marching or mesh generation from implicit surfaces, and the scalar field is differentiable [S2, unofficial].
-   **When Not to Use**: When the scalar field involves complex control flow or non-differentiable operations that cannot be easily adapted to dual number arithmetic [G].

## Background
The method originates from the use of forward-mode automatic differentiation for computing exact normals in implicit surface rendering [S1, S2, unofficial]. It was implemented in libraries such as `planaria/dmc` and `keckj/cupmb` to provide a robust alternative to finite difference normal estimation [S1, S2, unofficial]. The approach leverages the mathematical property that the derivative of a function evaluated at a dual number is the dual part of the result [S1, unofficial].
