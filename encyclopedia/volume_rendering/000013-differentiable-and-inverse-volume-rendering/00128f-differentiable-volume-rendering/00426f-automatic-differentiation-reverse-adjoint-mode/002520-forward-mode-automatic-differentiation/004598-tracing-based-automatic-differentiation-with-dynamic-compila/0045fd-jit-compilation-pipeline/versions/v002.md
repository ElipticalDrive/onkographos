# JIT Compilation Pipeline

Also called: Dr.Jit Compilation Pipeline, Dr.Jit IR generation, Dr.Jit JIT compilation, Dr.Jit Tracing and Compilation Pipeline

## Overview
The JIT Compilation Pipeline is a computational substrate that captures Python or C++ code execution into an Intermediate Representation (IR) for later compilation into machine code, supporting asynchronous execution on CPU or GPU [S1]. It solves the problem of high compilation overhead and poor runtime performance in dynamic dispatch scenarios common in differentiable rendering [S1]. It sets itself apart from alternatives like JAX/XLA by generating indirect calls to separate subroutines rather than merging all functions into a single large kernel body or committing loop state to memory at every iteration, thereby reducing backend compilation time and register allocation costs [S1].

## How it works
The pipeline consists of five main phases: Tracing, Kernel Assembly, Backend Compilation, and Kernel Execution [S1].

### Inputs and Outputs
*   **Input:** Python or C++ source code using custom arithmetic types (e.g., `Float`, `UInt32`) that represent dynamically sized 1D arrays rather than scalar variables [S1]. These arrays act as scalar variable declarations within a loop (e.g., `for index in range(..)`), where the index typically refers to a Monte Carlo sample [S1].
*   **Output:** Executable machine code (via LLVM for CPU or OptiX/CUDA for GPU) and asynchronous execution results [S1].

### Data Structures
*   **Computation Graph:** A graph data structure recording operations during tracing [S1].
*   **Kernel Cache:** An in-memory and on-disk cache storing previously compiled kernels to avoid redundant backend compilation [S1].
*   **Loop State:** Variables modified in the loop body and accessed in subsequent iterations or after termination [S1].

### Steps

1.  **Tracing:**
    The system executes the program using custom arithmetic types that record operations into the computation graph [S1].
    *   **Local Optimizations:** During tracing, the system performs constant folding/propagation, basic algebraic simplifications (e.g., $fma(a, b, 0) = a \cdot b$; $a \cdot 1 = a$), and local value numbering (reusing equivalent variables based on operation type and input dependencies) [S1].
    *   **Loop Handling:** Standard Python `for` loops unroll the loop body, producing unnecessarily large traces [S1]. Instead, a `Loop` object is instantiated with a lambda function specifying state variables (e.g., random number generator, counter, result) [S1]. The implementation invokes this lambda before and after the loop to catch redefinitions of Python variables [S1]. The loop runs for only one iteration to capture the effect of an individual iteration, wiring it into the generated kernel [S1].
    *   **Dynamic Dispatch (vcall):** For polymorphic methods, Dr.Jit traces all reachable method implementations (scene objects register themselves) [S1]. The operation acts as a demultiplexer-multiplexer [S1].

2.  **Kernel Assembly:**
    This phase removes redundancies at a global level and produces a program in the desired IR (LLVM IR or PTX) [S1].
    *   **Global Optimizations:** Includes dead code elimination, devirtualization (moving identical computations out of calls), and deduplication (identical sub-traces produce a single function definition) [S1].
    *   **Control Flow Preservation:** The generated IR preserves the control flow (loops, subroutines) of the original program, resembling source transformation output [S1]. Dynamic dispatch produces IR performing an indirect branch to one of multiple subroutines [S1].

3.  **Backend Compilation:**
    The generated IR is compiled into executable machine code using LLVM (CPU) or OptiX/CUDA (GPU) [S1].
    *   **Caching:** Backend compilation is relatively costly. The system consults the kernel cache (in-memory and on-disk) to see if the computation was previously encountered [S1]. In typical Path-Based Differentiable Rendering (PBDR) usage, this step is only necessary during the first gradient descent step [S1].

4.  **Kernel Execution:**
    The kernel is launched for asynchronous execution on the CPU (via a thread pool) or GPU (via CUDA/OptiX) [S1]. This allows tracing and kernel execution to continue in parallel [S1].

5.  **Evaluation (Triggered by Access):**
    Accessing array contents (e.g., `print`) triggers evaluation via `dr.eval(..)` [S1]. This compiles and launches a fused kernel to commit requested variables to device memory [S1]. Subsequent references use the stored version, allowing unused trace parts to expire [S1].

### Pseudocode

```python
# Phase 1: Tracing
import drjit as dr
from drjit.cuda import Float, UInt32, Loop, PCG32

# Types represent dynamically sized 1D arrays (scalar declarations in a loop)
x = dr.linspace(Float, -1, 1, num=1024)
y = dr.linspace(Float, -1, 1, num=1024)
x, y = dr.meshgrid(x, y)

# Local optimizations occur here:
# - Local value numbering detects redundant 'y' computation.
# - Constant folding and algebraic simplifications (e.g., fma(a,b,0)=a*b) are applied.

# Loop setup with state variables
rng = PCG32(size=1024 * 1024)
i, result = UInt32(0), Float(0)

# Lambda specifies state variables modified in the body or accessed after termination
loop = Loop(state=lambda: (rng, i, result))

# Loop runs for one iteration to capture the effect of an individual iteration
while loop(si.is_valid() & (i < 128)):
    # Loop body operations are traced
    # Dynamic dispatch (vcall) is traced here for polymorphic scene objects
    pass
    i += 1

# Phase 2: Kernel Assembly
# Global optimizations (dead code elimination, deduplication) are applied.
# IR is generated preserving control flow (loops, indirect branches for vcall).

# Phase 3: Backend Compilation
# Check kernel cache. If not found, compile IR via LLVM/OptiX.
# This is typically only done once per unique computation in PBDR.

# Phase 4: Evaluation (Triggered by print)
# Accessing array contents triggers dr.eval(..)
print(x) 
# This launches a fused kernel to commit 'x' to device memory.
# Subsequent references to 'x' use the stored device memory.
```

### Parameters
*   **Backend Compilation Frequency:** Typically only necessary during the first gradient descent step in typical PBDR usage [S1].
*   **Tracing/Assembly Time:** Highly optimized, taking on the order of 1-15ms in typical cases [S1].

### Edge Cases and Pitfalls
*   **Loop Unrolling:** Standard Python `for` loops unroll the loop body, producing unnecessarily large traces [S1]. Dr.Jit uses a `Loop` object to preserve loop structure instead [S1].
*   **Backend Compilation Cost:** Backend compilation time in OptiX and LLVM grows superlinearly with kernel size [S1]. Preserving control flow (loops/polymorphism) avoids creating an immensely large unrolled program that breaks the backend [S1].
*   **Dynamic Dispatch Boundary:** Dynamic dispatch presents an opaque boundary that breaks interprocedural optimizations in LLVM/OptiX [S1]. Dr.Jit handles this by generating indirect branches to subroutines [S1].

## Subtopics

### [Dr.Jit Optimizations](11680-dr-jit-optimizations.md)
Dr.Jit Optimizations are a set of global transformations applied during the tracing phase to improve code generation, specifically addressing the opaque boundary of dynamic dispatch that breaks interprocedural optimizations in backends like LLVM and OptiX. Unlike ML-centric IR and tensorial optimizations which are costly for rendering, Dr.Jit's optimizations are tailored for the large amount of arithmetic in PBDR workloads.

### [Dr.Jit Tracing and Compilation](11682-dr-jit-tracing-and-compilation.md)
Dr.Jit Tracing and Compilation is a just-in-time (JIT) system that converts traced Python-like computation graphs into optimized kernels for CPUs and GPUs. It solves the problem of high compilation overhead and poor runtime performance in dynamic dispatch scenarios common in differentiable rendering. It sets itself apart from alternatives like JAX/XLA by generating indirect calls to separate subroutines rather than merging all functions into a single large kernel body or committing loop state to memory at every iteration, thereby reducing backend compilation time and register allocation costs.

## Operating characteristics
*   **Time Complexity:** Tracing and kernel assembly are highly optimized, taking on the order of 1-15ms in typical cases [S1]. Backend compilation is relatively costly but cached [S1].
*   **Memory Complexity:** Not given in the sources.
*   **Measured Performance:** In typical PBDR usage, backend compilation is only necessary during the first gradient descent step [S1].
*   **Scaling:** Backend compilation time in OptiX and LLVM tends to grow superlinearly with kernel size [S1].
*   **Strengths:** Preserves control flow (loops, subroutines) of the original program, resembling source transformation output [S1]. Supports asynchronous execution on CPU or GPU [S1]. Effective for the large amount of arithmetic in PBDR workloads where rich ML-centric IR and tensorial optimizations are costly [S1].
*   **Limitations:** Backend compilation is costly if caching misses occur [S1]. Dynamic dispatch presents an opaque boundary for interprocedural optimizations in backends [S1].
*   **When to use:** Differentiable rendering workloads with large amounts of arithmetic, particularly when control flow preservation is needed to avoid excessive kernel size [S1].
*   **When not to use:** Workloads where rich tensorial optimizations are beneficial and the arithmetic intensity is lower (e.g., standard ML neural network training) [S1].

## Background
Dr.Jit is a just-in-time compiler for differentiable rendering [S1]. It was introduced in the paper "Dr.Jit: A Just-In-Time Compiler for Differentiable Rendering" [S1]. The system shares similarities with array programming frameworks like PyTorch, TensorFlow, and JAX, but is tailored for the specific needs of rendering [S1]. It is a hybrid system that ingests computation using tracing but generates kernels that preserve the control flow of the original program [S1].
