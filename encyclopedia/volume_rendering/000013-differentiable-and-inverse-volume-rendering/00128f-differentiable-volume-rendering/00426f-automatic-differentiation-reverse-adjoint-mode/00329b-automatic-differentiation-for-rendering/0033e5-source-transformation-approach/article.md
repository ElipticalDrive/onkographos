# Source Transformation Approach

Also called: Enzyme, Stalin∇, Static compilation approach, Tapenade

## Overview
The Source Transformation Approach is an automatic differentiation (AD) strategy that converts the source code of a program into its derivative at compile-time, treating differentiation as a one-time compilation step rather than a runtime operation [S1, S2]. It solves the problem of runtime overhead and optimization inhibition inherent in tracing-based AD by generating optimized, standalone derivative code [S2]. Unlike tracing approaches, it preserves the original control flow, allowing generated programs to function correctly regardless of loop iteration counts or dynamic branching [S2].

## How it works
**Inputs and Outputs:**
- **Input:** Source code of a primal program (e.g., C, Fortran, Julia, or LLVM IR) and a specification of the differentiation mode (Forward/JVP or Reverse/VJP) [S2].
- **Output:** Source code of the derivative program (JVP or VJP) [S2].

**Data Structures:**
- **Control Flow Graph (CFG):** Used for activity analysis to determine which variables require derivative computation [S2].
- **Stack:** Required in Reverse-mode (VJP) for loops to store intermediate primal states for later consumption during the backward pass [S2].

**Steps:**
1. **Parse and Analyze:** The tool parses the source code into an intermediate representation (IR) or abstract syntax tree [S2].
2. **Activity Analysis:** To avoid unnecessary adjoint evaluations for variables that do not affect the final gradient, the tool performs a data-flow analysis [S2]. This analysis conservatively propagates "derivative liveness" through the control flow graph until a fixed point is reached [S2].
3. **Transformation:** The source code is transformed into derivative code [S2].
   - **Forward Mode (JVP):** Each primal operation is paired with its derivative operation [S2].
   - **Reverse Mode (VJP):** The code is traversed to generate a backward pass [S2]. For loops, the forward pass records intermediate states into a stack, and a reversed loop consumes this stack to compute gradients [S2].
4. **Optimization:** The generated code is optimized by the underlying compiler (e.g., LLVM) [S2].

**Pseudocode (VJP for Integer Power):**
The following Python-like pseudocode illustrates the VJP generation for an integer power function `pow(x, n)`, as generated by tools like Tapenade [S2]. Note that this requires a stack to store intermediate states for the reverse loop [S2].

> **Unverified code.** The code below did not pass a test run against a reference implementation, or no test fits it, so it may contain errors.

```python
def pow_vjp(x: float, n: int, dy: float):
    """
    Computes the gradient of pow(x, n) with respect to x.
    x: primal input
    n: integer exponent (constant for differentiation purposes)
    dy: upstream gradient (d/dy of loss w.r.t output)
    Returns: dx, the gradient of the loss w.r.t x
    """
    y = 1.0
    dx = 0.0
    stack = []

    # Forward pass: record intermediate states
    for i in range(n):
        stack.append(y)
        y = y * x

    # Reverse pass: consume stack to compute gradients
    for i in reversed(range(n)):
        y = stack.pop()
        # Chain rule: dx += (d_output/d_y_current) * y
        # Here, d_output/d_y_current is dy (accumulated from downstream)
        # The local derivative of y_new = y_old * x w.r.t x is y_old
        dx = dx + y * dy
        # Update dy for the previous step: d_loss/d_y_old = d_loss/d_y_new * x
        dy = dy * x

    return dx
```

**Parameters:**
- **Differentiation Mode:** Forward (JVP) or Reverse (VJP) [S2].
- **Target Language/IR:** C, Fortran, Julia, or LLVM IR [S2].

**Edge Cases and Pitfalls:**
- **Loops in Reverse Mode:** Loops require two passes: one to record state and one to reverse it [S2]. This poses difficulties for massively parallel architectures like GPUs because stack or shadow memory must be provisioned for all threads running in parallel, handling worst-case requirements [S2].
- **Complex Control Flow:** While source transformation preserves control flow, handling recursion and complex dynamic branching can be difficult to implement correctly [S1, S2].
- **Subset of Language:** The approach usually can only handle a subset of a general-purpose language, as the transformation must be statically analyzable [S1].

## Operating characteristics
- **Performance:** Generally offers better performance than tracing approaches because the derivative code is compiled once and optimized statically [S1, S2]. Tracing approaches re-compile derivatives on every function evaluation, causing overhead [S2].
- **Implementation Complexity:** Much more difficult to implement than tracing approaches [S1].
- **Language Support:** Usually handles only a subset of a general-purpose language, as it requires static analysis capabilities [S1].
- **Control Flow:** Preserves control flow, allowing generated programs to work regardless of loop iteration counts, unlike unrolled traces [S2].
- **Memory:** Reverse-mode implementations may require significant memory for stack provisioning in parallel architectures (e.g., GPUs) due to the need to store intermediate states for all threads [S2].

## Background
The Source Transformation Approach is one of the two main ends of the spectrum for automatic differentiation, the other being the Tracing/Taping approach [S1]. Notable implementations include Tapenade [Hascoet and Pascual 2013], Stalin∇ [Pearlmutter and Siskind 2008], Zygote [Innes 2019], and Enzyme [Moses and Churavy 2020; Moses et al. 2021] [S2]. TensorFlow 1.0 is cited as a popular example of this approach in the context of machine learning frameworks [S1].
