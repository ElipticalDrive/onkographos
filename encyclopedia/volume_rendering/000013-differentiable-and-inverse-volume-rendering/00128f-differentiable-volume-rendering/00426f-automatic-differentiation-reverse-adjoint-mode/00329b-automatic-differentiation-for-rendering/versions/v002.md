# Automatic Differentiation for Rendering

Also called: Autograd-based Differentiable Rendering, Differentiable Rendering via Computational Graphs

## Overview
Automatic Differentiation (AD) for rendering applies reverse-mode automatic differentiation to the computational graph of a rendering program to compute derivatives of interior rendering integrands [S1]. It solves the problem of obtaining gradients for complex, non-analytic rendering code by treating differentiation as a program transformation rather than an analytical derivation [S1]. Unlike the Adjoint Method, which requires manual derivation of adjoint equations for specific rendering steps, AD automatically generates these gradients from the forward code [S1]. However, it is distinct from general-purpose deep learning frameworks because standard AD implementations are inefficient for rendering due to the unstructured, low-arithmetic-intensity nature of rendering graphs [S1].

## How it works
**Inputs and Outputs:**
- Input: A differentiable rendering program (source code or computational graph) representing the forward pass, and a scalar loss value derived from the rendered output.
- Output: Gradients of the loss with respect to all differentiable inputs (e.g., scene parameters, material properties, camera poses).

**Data Structures:**
The method relies on the computational graph generated by the framework. In the context of general AD compilers, this involves storing intermediate values (primal variables) and their corresponding adjoint variables (gradients) in memory buffers [S1]. The structure is typically a linked list or tree of operations, where each node stores the operation type, input indices, and output indices [G].

**Steps:**
1.  **Forward Pass:** Execute the rendering program to compute the output image and the loss value. During this pass, record the computational graph and store all intermediate primal values required for backpropagation [S1].
2.  **Graph Construction:** Build the reverse-mode computational graph. For each operation $y = f(x)$ in the forward pass, create a corresponding adjoint operation that computes $\frac{\partial L}{\partial x}$ from $\frac{\partial L}{\partial y}$ using the chain rule [S1].
3.  **Reverse Pass (Backpropagation):** Traverse the computational graph in reverse topological order. For each node, compute the local gradients and accumulate them into the adjoint variables of the inputs [S1].
4.  **Gradient Accumulation:** Sum the contributions from all paths in the graph to obtain the final gradients for the input parameters [S1].

**Formulas:**
For a single operation $y = f(x)$, the adjoint update is:
$$
\bar{x} \leftarrow \bar{x} + \bar{y} \cdot \frac{\partial f}{\partial x}
$$
where $\bar{x}$ and $\bar{y}$ are the adjoint variables (gradients of the loss with respect to $x$ and $y$) [S1].

**Parameters:**
- Memory budget: Must accommodate $O(kn)$ intermediate states, where $n$ is the number of pixels and $k$ is the number of samples per ray [S5].
- Precision: Standard floating-point precision (FP32/FP16) used in the forward pass; gradients may require higher precision to avoid vanishing/exploding issues [G].

**Edge Cases and Pitfalls:**
- **Memory Traffic:** Rendering computation graphs are highly unstructured and contain millions of operations with low arithmetic intensity. Implementing this directly in deep learning frameworks (PyTorch, TensorFlow) causes excessive memory traffic because data is repeatedly stored to and read back from memory buffers [S1].
- **Discontinuities:** While discretization commutes with differentiation for interior integrands, discontinuities (e.g., from visibility changes) must be handled carefully, as standard AD may produce incorrect gradients at these points [S1].
- **Graph Size:** The graph size can be extremely large, leading to out-of-memory errors if not optimized [S1].

## Subtopics

### [Source Transformation Approach](7118-source-transformation-approach.md)
The Source Transformation Approach is an automatic differentiation (AD) strategy that converts the source code of a program into its derivative at compile-time, treating differentiation as a one-time compilation step rather than a runtime operation. It solves the problem of runtime overhead and optimization inhibition inherent in tracing-based AD by generating optimized, standalone derivative code. Unlike tracing approaches, it preserves the original control flow, allowing generated programs to function correctly regardless of loop iteration counts or dynamic branching.

### [Dressi-AD](10746-dressi-ad.md)
Dressi-AD is a hardware-agnostic automatic differentiation library for differentiable rendering (DR) built on the Vulkan API. It solves the problem of integrating reverse-mode AD into a graphics pipeline by using 2D images as primitive data structures instead of multi-dimensional tensors, maintaining compatibility with hardware rasterizers. Unlike general-purpose AD libraries that rely on multi-dimensional tensors, Dressi-AD aligns with graphics pipeline constraints and differentiable rendering workflows by utilizing fragment shaders with dummy vertex shaders for computation.

## Operating characteristics
- **Time Complexity:** Linear with respect to the number of operations in the computational graph for both forward and reverse passes [S1].
- **Memory Complexity:** $O(kn)$, where $n$ is the number of pixels and $k$ is the number of samples per ray, due to the need to store intermediate states for backpropagation [S5].
- **Performance:** Standard implementations in deep learning frameworks (PyTorch, TensorFlow) are inefficient for full rendering pipelines due to low arithmetic intensity and high memory traffic [S1]. Specialized AD compilers or libraries (like Dressi-AD) are required for efficient execution [S1].
- **Strengths:** Automatic gradient computation without manual derivation; supports complex, non-analytic rendering code [S1].
- **Limitations:** High memory usage; inefficient in general-purpose frameworks; struggles with discontinuities [S1, S5].
- **When to use:** When the rendering code is complex and non-analytic, and memory is not a critical constraint, or when using specialized AD compilers [S1].
- **When not to use:** When memory is limited, or when the rendering code is simple enough for analytic gradients or the Adjoint Method [S1, S5].

## Background
Automatic Differentiation for rendering was introduced as a technique to compute derivatives of interior rendering integrands by applying existing AD techniques to rendering programs [S1]. The approach leverages the fact that discretization commutes with differentiation for interior integrands [S1]. While widely used deep learning frameworks like PyTorch and TensorFlow provide interfaces for AD, they are not optimized for the specific characteristics of rendering computation graphs [S1]. This has led to the development of specialized AD compilers and libraries for differentiable rendering [S1].
