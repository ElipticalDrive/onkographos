# Automatic Differentiation for Rendering

Also called: Autograd-based Differentiable Rendering, Differentiable Rendering via Computational Graphs

## Overview
Automatic Differentiation (AD) for rendering computes the derivatives of interior rendering integrands by applying reverse-mode automatic differentiation directly to the rendering program [S1]. It solves the problem of efficiently obtaining gradients for optimization-based inverse rendering by leveraging the fact that discretization commutes with differentiation for smooth interior integrands [S1]. Unlike the Adjoint Method, which derives custom adjoint equations for specific rendering paths, AD treats the renderer as a black-box computational graph, allowing the use of existing AD frameworks [G].

## How it works
**Inputs and Outputs:**
- **Input:** A forward rendering program $F$ that maps scene parameters $\theta$ (e.g., material properties, geometry) to pixel values $I$ [G].
- **Output:** The gradient $\frac{\partial L}{\partial \theta}$ of a loss function $L$ (typically a function of $I$) with respect to $\theta$ [G].

**Data Structures:**
The method relies on the computational graph representation provided by the deep learning framework [S1].
- **Forward Tape/Graph:** A record of operations performed during the forward pass [G].
- **Gradient Accumulators:** Memory buffers storing partial derivatives $\frac{\partial L}{\partial x}$ for each variable $x$ in the graph [G].

**Steps:**
1. **Forward Pass:** Execute the rendering program $F(\theta)$ using tensor operations [G].
2. **Loss Computation:** Compute the scalar loss $L$ from the rendered image $I$ [G].
3. **Backward Pass (Reverse AD):** Traverse the recorded computational graph in reverse order [G]. For each operation $y = f(x)$, compute the local gradient $\frac{\partial y}{\partial x}$ and propagate the upstream gradient $\frac{\partial L}{\partial y}$ to $\frac{\partial L}{\partial x}$ using the chain rule:
   $$ \frac{\partial L}{\partial x} = \frac{\partial L}{\partial y} \cdot \frac{\partial y}{\partial x} $$
   [G]

**Pseudocode:**
```python
class Tape:
    def __init__(self):
        self.operations = []
    def record(self, backward_fn, inputs, outputs):
        self.operations.append((backward_fn, inputs, outputs))
    def backward(self, upstream_grad):
        grad = upstream_grad
        for backward_fn, inputs, outputs in reversed(self.operations):
            grad = backward_fn(grad, inputs, outputs)
        return grad

def render_forward(scene_params):
    tape = Tape()
    # Example forward rendering steps
    rays = [scene_params.camera.origin + t * scene_params.camera.direction for t in range(10)]
    tape.record(lambda g, i, o: [x * g for x in i], [scene_params.camera.direction], [rays])
    hits = [ray + 1.0 for ray in rays]
    tape.record(lambda g, i, o: [x + g for x in i], [rays], [hits])
    color = [hit * scene_params.materials.diffuse for hit in hits]
    tape.record(lambda g, i, o: [x * g for x in i], [hits], [color])
    return color, tape

def compute_loss(rendered_image, target_image):
    return sum((r - t) ** 2 for r, t in zip(rendered_image, target_image)) / len(rendered_image)

def optimize_scene(scene_params, target_image, num_iterations):
    for _ in range(num_iterations):
        rendered_image, tape = render_forward(scene_params)
        loss = compute_loss(rendered_image, target_image)
        grad_loss = 1.0
        grad_params = tape.backward(grad_loss)
        scene_params.update(grad_params)
    return scene_params
```

**Edge Cases and Pitfalls:**
- **Memory Usage:** The computational graph for rendering is extremely large (millions of operations) and unstructured [S1]. Storing the forward tape for reverse AD can consume excessive memory, leading to out-of-memory errors [S1].
- **Arithmetic Intensity:** Rendering operations often have low arithmetic intensity (e.g., many additions, few multiplications) [S1]. This causes excessive memory traffic when data are repeatedly stored to and read back from memory buffers, making it significantly slower than high-intensity neural network operations [S1].
- **Discontinuities:** AD applies to interior integrands where discretization commutes with differentiation [S1]. Discontinuities in the rendering integrand (e.g., visibility changes, shadow boundaries) require separate handling, as the derivative is undefined or zero almost everywhere at the discontinuity [G].

## Subtopics

### [Source Transformation Approach](7118-source-transformation-approach.md)
The Source Transformation Approach is an automatic differentiation (AD) strategy that converts the source code of a program into its derivative at compile-time, treating differentiation as a one-time compilation step rather than a runtime operation [G]. It solves the problem of runtime overhead and optimization inhibition inherent in tracing-based AD by generating optimized, standalone derivative code [G]. Unlike tracing approaches, it preserves the original control flow, allowing generated programs to function correctly regardless of loop iteration counts or dynamic branching [G].

### [Dressi-AD](10746-dressi-ad.md)
Dressi-AD is a hardware-agnostic automatic differentiation library for differentiable rendering (DR) built on the Vulkan API [G]. It solves the problem of integrating reverse-mode AD into a graphics pipeline by using 2D images as primitive data structures instead of multi-dimensional tensors, maintaining compatibility with hardware rasterizers [G]. Unlike general-purpose AD libraries that rely on multi-dimensional tensors, Dressi-AD aligns with graphics pipeline constraints and differentiable rendering workflows by utilizing fragment shaders with dummy vertex shaders for computation [G].

## Operating characteristics
- **Time Complexity:** The backward pass is proportional to the forward pass [G]. However, due to low arithmetic intensity, the constant factor is high due to memory bandwidth limitations [S1].
- **Memory Complexity:** Requires storing intermediate values from the forward pass for the backward pass [G]. This is a major bottleneck for large scenes [S1].
- **Measured Performance:** Implementing rendering pipelines directly in frameworks like PyTorch or TensorFlow is extremely inefficient compared to specialized AD compilers or adjoint methods due to the unstructured nature of rendering graphs and the overhead of tensor management [S1].
- **Strengths:** Easy to implement if the rendering primitives are already differentiable; leverages existing AD infrastructure; no need to manually derive adjoint equations [G].
- **Limitations:** High memory consumption; poor performance on GPUs due to low arithmetic intensity [S1].
- **When to Use:** Suitable for small-scale differentiable rendering tasks or when rapid prototyping is prioritized over performance [G]. Not recommended for production-scale inverse rendering with large scenes [S1].

## Background
The technique is based on the principle that for interior rendering integrands, discretization commutes with differentiation, allowing standard automatic differentiation techniques to be applied directly to the rendering program [S1]. Widely used deep learning frameworks such as PyTorch and TensorFlow provide built-in automatic differentiation interfaces [S1]. However, these frameworks were designed for linear algebra and neural networks, which have high arithmetic intensity and structured graphs, unlike rendering algorithms which produce large, unstructured graphs with low arithmetic intensity [S1]. This mismatch necessitates specialized AD compilers for efficient differentiable rendering [S1].
