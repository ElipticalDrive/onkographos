# Tensor Glyphs

Also called: DT-MRI Glyphs, Eigenvalue-based Glyphs, Ellipsoid Glyphs, Superquadric Glyphs, Tensor Axes Glyphs

## Overview
Tensor Glyphs are point-icon visualization techniques that represent scalar, vectorial, or tensorial information (specifically eigenvalues and eigenvectors) at every data point in space, overcoming the limitation of colormaps which can display only three distinct metrics or one direction per point [S1, S2, unofficial]. Unlike [Ellipsoid Glyphs](10535-glyph-based-vector-tensor-visualization.md) which suffer from ambiguity in projection, or [Tensor Axes Glyphs](10535-glyph-based-vector-tensor-visualization.md) which may be hard to distinguish, Tensor Glyphs map the tensor shape space (linear, planar, spherical) to geometric primitives that satisfy continuity, uniqueness, and unambiguity criteria [S1, unofficial]. They are primarily used in Diffusion Tensor Imaging (DTI) to visualize the orientation and anisotropy of diffusion [S1, S2, unofficial].

## How it works
**Inputs:** A 3x3 symmetric diffusion tensor $D$ at each voxel; scalar anisotropy metrics (optional, for color/shape selection).
**Outputs:** A rendered image containing geometric glyphs (ellipsoids, superquadrics, cylinders, boxes, or spheres) positioned at voxel centers.

**Data Structures:**
*   **Tensor Field:** Array of 3x3 symmetric matrices. Stored as 6 floats per voxel (diagonal $D_{xx}, D_{yy}, D_{zz}$ and off-diagonals $D_{xy}, D_{xz}, D_{yz}$).
*   **Eigen Decomposition:** For each tensor, compute eigenvalues $\lambda_1, \lambda_2, \lambda_3$ and eigenvectors $\mathbf{v}_1, \mathbf{v}_2, \mathbf{v}_3$.
    *   Constraint: $\lambda_1 \ge \lambda_2 \ge \lambda_3 \ge 0$.
    *   $\mathbf{v}_1, \mathbf{v}_2, \mathbf{v}_3$ are the major, medium, and minor eigenvectors, respectively.
*   **Scalar Metrics (for shape selection):**
    *   Linear Anisotropy ($C_L$): $C_L = \frac{\lambda_1 - \lambda_2}{\lambda_1 + \lambda_2 + \lambda_3}$
    *   Planar Anisotropy ($C_P$): $C_P = \frac{2(\lambda_2 - \lambda_3)}{\lambda_1 + \lambda_2 + \lambda_3}$
    *   Spherical Anisotropy ($C_S$): $C_S = \frac{3\lambda_3}{\lambda_1 + \lambda_2 + \lambda_3}$
    *   Note: $C_L + C_P + C_S = 1$.

**Steps:**
1.  **Eigen Decomposition:** For each tensor $D$, solve the characteristic equation $\det(D - \lambda I) = 0$ to find eigenvalues $\lambda_i$. Compute corresponding normalized eigenvectors $\mathbf{v}_i$.
2.  **Metric Calculation:** Compute $C_L, C_P, C_S$ using the formulas above.
3.  **Glyph Selection:** Determine the glyph type based on the dominant metric:
    *   If $C_L$ is high (linear diffusion): Render a **Cylinder** oriented along $\mathbf{v}_1$.
    *   If $C_S$ is high (isotropic diffusion): Render a **Sphere**.
    *   If $C_P$ is high (planar diffusion): Render a **Box** (or Cuboid).
    *   *Alternative (Superquadrics):* Use a single superquadric surface parameterized by $C_L, C_P, C_S$ to smoothly interpolate between these shapes [S1, unofficial].
4.  **Transformation:** Transform a base glyph geometry $G$ (e.g., unit sphere or box) to the tensor glyph geometry $G_T$ using the rotation matrix $R$ (formed by eigenvectors) and scaling by eigenvalues:
    $$G_T = R^{-1} \begin{pmatrix} \lambda_1 & 0 & 0 \\ 0 & \lambda_2 & 0 \\ 0 & 0 & \lambda_3 \end{pmatrix} R G$$
    Where $R = [\mathbf{v}_1 | \mathbf{v}_2 | \mathbf{v}_3]$ is the rotation matrix aligning the local coordinate system with the eigenvectors [S1, unofficial].
5.  **Rendering:** Render the transformed glyphs. For superquadrics, use GPU-based raytracing for efficiency [S1, unofficial].

**Pseudocode:**
```python
def compute_tensor_glyph(tensor_D, glyph_type='superquadric'):
    """
    Computes the geometric representation of a 3x3 symmetric tensor.
    tensor_D: 3x3 numpy array, symmetric.
    glyph_type: 'superquadric', 'ellipsoid', 'mixed'.
    Returns: Transformation matrix T, scalar metrics (CL, CP, CS).
    """
    # 1. Eigen Decomposition
    eigenvalues, eigenvectors = np.linalg.eigh(tensor_D)
    # Sort eigenvalues in descending order: lambda1 >= lambda2 >= lambda3
    idx = np.argsort(eigenvalues)[::-1]
    lambda1, lambda2, lambda3 = eigenvalues[idx]
    v1, v2, v3 = eigenvectors[:, idx]
    
    # 2. Calculate Scalar Metrics
    trace = lambda1 + lambda2 + lambda3
    if trace == 0:
        return None, (0, 0, 0) # Isotropic zero tensor
    
    CL = (lambda1 - lambda2) / trace
    CP = 2 * (lambda2 - lambda3) / trace
    CS = 3 * lambda3 / trace
    
    # 3. Construct Rotation Matrix R
    # Columns are the eigenvectors
    R = np.column_stack((v1, v2, v3))
    
    # 4. Construct Scaling Matrix S
    S = np.diag([lambda1, lambda2, lambda3])
    
    # 5. Transformation Matrix T = R * S * R^T (Note: Source [S1, unofficial] uses R^-1 ... R G)
    # Since R is orthogonal, R^-1 = R^T.
    # The formula G_T = R^-1 S R G implies transforming the base geometry G.
    # In standard graphics, we usually transform vertices v by T*v.
    # If G is a set of vertices, the transformation is T = R * S * R^T.
    # Let's verify source [S1, unofficial] notation: G_T = R^-1 S R G.
    # If G is a column vector of vertices, this is a similarity transform.
    # T = R^T @ S @ R.
    T = R.T @ S @ R
    
    return T, (CL, CP, CS)

def render_glyphs(tensor_field, resolution=1.0):
    """
    Renders glyphs for a tensor field.
    """
    for voxel in tensor_field:
        T, metrics = compute_tensor_glyph(voxel)
        if T is None:
            continue
        
        # Select shape based on metrics
        CL, CP, CS = metrics
        if CL > 0.6:
            shape = 'cylinder'
        elif CS > 0.6:
            shape = 'sphere'
        elif CP > 0.6:
            shape = 'box'
        else:
            shape = 'superquadric' # Fallback or primary method
        
        # Render shape at voxel center with transformation T
        render_primitive(shape, T, resolution)
```

**Edge Cases and Pitfalls:**
*   **Unambiguity:** Boxes/cuboids fail criterion (g3) because they are not distinguishable from every view direction [S1, unofficial]. Ellipsoids also suffer from this ambiguity [S1, unofficial]. Superquadrics are preferred as they meet all criteria (g1-g3) [S1, unofficial].
*   **Visual Clutter:** Display density must be kept low to avoid visual clutter when rendering many icons [S2, unofficial].
*   **Continuity:** Minimal changes in neighboring tensors must not cause discontinuities in glyph geometry [S1, unofficial].
*   **Uniqueness:** The mapping from tensor shape to glyph geometry must be unique [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of voxels, for eigen decomposition and glyph placement. Rendering complexity depends on the glyph type; superquadrics require raytracing, which is more expensive than simple ellipsoids but manageable with GPU acceleration [S1, unofficial].
*   **Memory Complexity:** $O(N)$ to store the tensor field and glyph parameters.
*   **Performance:** Hlawitschka et al. [S1, unofficial] introduced a fast, GPU-based raytracing method for superquadrics, allowing real-time rendering of thousands of glyphs.
*   **Strengths:** Can display multiple metrics (direction, anisotropy type) simultaneously; unambiguous shape representation with superquadrics.
*   **Limitations:** Visual clutter at high densities; computationally expensive for raytraced superquadrics compared to simple colormaps; ellipsoids are ambiguous.
*   **When to use:** When understanding the local tensor shape (linear vs. planar vs. spherical) is critical, such as in DTI fiber tractography analysis.
*   **When not to use:** When performance is critical and only dominant direction is needed (use [Arrow Glyphs](2663-arrow-glyphs-for-vector-field-visualization.md) or [Line Glyphs](2569-line-glyphs-for-vector-field-visualization.md)); when data density is very high.

## Background
Tensor Glyphs were introduced to overcome the limitations of colormaps in displaying tensor information. Superquadrics, a specific type of tensor glyph, were introduced by A. H. Barr in 1981 [Bar81] and suggested for DTI visualization by Kindlmann in 2004 [Kin04a]. Hlawitschka et al. [HES08] later optimized their rendering for GPUs.
