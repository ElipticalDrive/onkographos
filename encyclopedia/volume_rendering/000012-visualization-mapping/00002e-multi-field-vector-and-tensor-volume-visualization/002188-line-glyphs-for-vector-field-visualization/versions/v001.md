# Line Glyphs for Vector Field Visualization
Also called: Glyph Lines, Line Glyphs, Vector Field Glyphs

## Overview
Line Glyphs is a visualization technique where vector fields are represented by line segments, with each line's orientation matching the vector field and its length and color determined by the vector magnitude [S1, unofficial]. It is distinguished from sibling methods like [Arrow Glyphs](2663-arrow-glyphs-for-vector-field-visualization.md) by its extreme computational efficiency and memory footprint, allowing for the rendering of millions of glyphs, but suffers from ambiguity regarding vector direction and 3D orientation due to the lack of shading [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D vector field texture (`vectorFieldTex`) storing vectors as `float4` (x, y, z components and magnitude w); a 1D color transfer function texture (`vectorMangitudeCtfTex`) mapping magnitude to color; grid dimensions (`glyphsCount`); world size (`worldSize`); and a fixed X-coordinate (`x`) defining the plane of visualization [S1, unofficial].
*   **Output:** Two arrays of `float3` vertices (`outVertices`) and `float3` colors (`outColors`), where each glyph consumes two consecutive entries (start and end vertex) [S1, unofficial].

**Data Structures:**
*   `vectorFieldTex`: 3D texture, format `float4`. Access via `tex3D`.
*   `vectorMangitudeCtfTex`: 1D texture, format `float4` (RGBA). Access via `tex1D`.
*   `outVertices`: Array of `float3`. Size is $2 \times N$, where $N$ is the number of glyphs [S1, unofficial].
*   `outColors`: Array of `float3`. Size is $2 \times N$ [S1, unofficial].

**Parameters:**
*   `glyphsCount`: `uint2` specifying the number of glyphs in the Y and Z dimensions (grid spacing).
*   `worldSize`: `float2` specifying the physical dimensions of the Y-Z plane [S1, unofficial].
*   `x`: `float` specifying the fixed X-coordinate for the plane of glyphs [S1, unofficial].

**Algorithm Steps:**
1.  Compute the global thread ID `id` from block and thread indices.
2.  Calculate the total number of glyphs `totalCount` as `glyphsCount.x * glyphsCount.y`.
3.  If `id >= totalCount`, terminate the thread.
4.  Compute the Y and Z grid coordinates:
    $$ y = (id \pmod{\text{glyphsCount.x}}) \times \frac{\text{worldSize.x}}{\text{glyphsCount.x}} $$
    $$ z = (\lfloor id / \text{glyphsCount.x} \rfloor) \times \frac{\text{worldSize.y}}{\text{glyphsCount.y}} $$
    *Note: The source code uses `worldSize.x` for Y spacing and `worldSize.y` for Z spacing, implying a specific mapping of world dimensions to grid axes [S1, unofficial].*
5.  Sample the vector field at $(x, y, z)$ to get `vector` (`float4`).
6.  Compute the start vertex:
    $$ \text{start} = (x, y, z) $$
7.  Compute the end vertex:
    $$ \text{end} = \text{start} + \text{normalize}((\text{vector}.x, \text{vector}.y, \text{vector}.z)) \times \text{vector}.w $$
8.  Sample the color from the magnitude transfer function using `vector.w`.
9.  Assign the start vertex to `outVertices[id * 2]` and the end vertex to `outVertices[id * 2 + 1]`.
10. Assign the sampled color to `outColors[id * 2]` and `outColors[id * 2 + 1]`.

**Pseudocode:**
```python
# Assuming standard CUDA-style thread indexing available via blockIdx, blockDim, threadIdx
# Global variables assumed accessible: vectorFieldTex, vectorMangitudeCtfTex, glyphsCount, worldSize, x

def glyph_lines_kernel(out_vertices, out_colors):
    # 1. Calculate global thread ID
    id = blockIdx.x * blockDim.x + threadIdx.x
    
    # 2. Calculate total glyph count
    total_count = glyphsCount.x * glyphsCount.y
    
    # 3. Check bounds
    if id >= total_count:
        return

    # 4. Compute grid coordinates (Y, Z)
    # Note: Source maps worldSize.x to Y-axis spacing and worldSize.y to Z-axis spacing
    y = (id % glyphsCount.x) * (worldSize.x / glyphsCount.x)
    z = (id // glyphsCount.x) * (worldSize.y / glyphsCount.y)
    
    # 5. Sample vector field at (x, y, z)
    # vector is float4: x, y, z components and w magnitude
    vector = sample_3d_texture(vectorFieldTex, x, y, z)
    
    # 6. Compute start vertex
    start_vertex = (x, y, z)
    
    # 7. Compute end vertex
    # Normalize the spatial components (x,y,z) and scale by magnitude (w)
    vec_x, vec_y, vec_z = vector.x, vector.y, vector.z
    mag = vector.w
    
    # Compute normalization factor
    length = sqrt(vec_x**2 + vec_y**2 + vec_z**2)
    if length > 0:
        norm_x, norm_y, norm_z = vec_x / length, vec_y / length, vec_z / length
    else:
        norm_x, norm_y, norm_z = 0.0, 0.0, 0.0
        
    end_vertex = (
        start_vertex[0] + norm_x * mag,
        start_vertex[1] + norm_y * mag,
        start_vertex[2] + norm_z * mag
    )
    
    # 8. Sample magnitude color
    color = sample_1d_texture(vectorMangitudeCtfTex, mag)
    
    # 9. Assign vertices and colors
    # Each glyph uses two consecutive indices
    idx = id * 2
    out_vertices[idx] = start_vertex
    out_vertices[idx + 1] = end_vertex
    
    out_colors[idx] = (color.x, color.y, color.z)
    out_colors[idx + 1] = (color.x, color.y, color.z)
```

**Edge Cases and Pitfalls:**
*   **Zero Vector:** If the vector magnitude is zero or the spatial components are zero, normalization fails. The pseudocode handles this by defaulting to zero displacement [G].
*   **Direction Ambiguity:** Line glyphs do not indicate vector direction (head vs. tail). This makes it difficult to distinguish flow direction without camera movement or color cues [S1, unofficial].
*   **3D Orientation:** Without shading, it is hard to perceive the 3D orientation of lines in space [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$, where $N$ is the number of glyphs. Each glyph requires one texture lookup and simple arithmetic.
*   **Memory Complexity:** $O(N)$ for output vertices and colors. Input memory is dominated by the 3D texture.
*   **Performance:** Extremely fast. Computation time for nearly any amount of glyphs is less than 20 ms [S1, unofficial]. On an NVIDIA Quadro K5000, nearly 13 million glyphs were computed in 26 ms [S1, unofficial].
*   **Strengths:** High performance, low memory consumption (1/3 less than some other methods), capable of rendering huge amounts of lines to create a "solid wall" visualization of magnitude [S1, unofficial].
*   **Limitations:** Ambiguous direction and orientation; hard to read in static views compared to arrows [S1, unofficial].
*   **When to use:** When exploring large vector fields interactively, visualizing magnitude distributions, or when performance is critical.
*   **When not to use:** When precise directionality or 3D orientation is required without camera interaction.

## Background
This method was described by Marek Fiser in the context of real-time visualization of 3D vector fields using CUDA [S1, unofficial]. It was applied to visualize airflow around a delta-wing, demonstrating the ability to reveal vortices and recirculation bubbles [S1, unofficial].
