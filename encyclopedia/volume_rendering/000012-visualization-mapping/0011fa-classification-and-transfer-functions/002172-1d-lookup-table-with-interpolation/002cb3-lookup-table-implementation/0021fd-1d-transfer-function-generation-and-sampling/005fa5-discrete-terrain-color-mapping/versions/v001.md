# Discrete Terrain Color Mapping

Also called: Height-based Terrain Coloring

## Overview
Discrete Terrain Color Mapping assigns specific terrain types and palette indices to volume or surface fragments based on discrete height levels. It solves the problem of mapping scalar elevation data to categorical visual classes (e.g., water, grass, snow) by defining non-overlapping start and end level ranges for each terrain type. It differs from continuous interpolation methods by using strict range checks rather than blending between color ramps.

## How it works
**Inputs and Outputs:**
- Input: A scalar height value (typically normalized or scaled to a specific range, e.g., 0–255).
- Input: A `ColorMap` structure containing a list of `Terrain` bands.
- Output: A `color_index` (u8) identifying the terrain type, or `None` if the height falls outside all defined bands.

**Data Structures:**
The method relies on two primary structures defined in the source implementation [S1, unofficial]:

1.  `Terrain`: Represents a single discrete band.
    -   `name`: String (unused in logic, marked `#[allow(dead_code)]`).
    -   `color_index`: u8. The identifier for the terrain color.
    -   `start_level`: u8. The inclusive lower bound of the height range.
    -   `end_level`: u8. The inclusive upper bound of the height range.

2.  `ColorMap`: The container for all terrain bands.
    -   `width`: u32.
    -   `height`: u32.
    -   `colors`: `Vec<Terrain>`. A vector of `Terrain` structs.

**Parameters and Typical Values:**
The source provides a specific configuration for a planet-like terrain [S1, unofficial]:
-   **Water**: `start_level` = 0, `end_level` = 6, `color_index` = 1, RGB(91, 118, 147).
-   **Dirt**: `start_level` = 7, `end_level` = 7, `color_index` = 2, RGB(199, 191, 168).
-   **Grass**: `start_level` = 8, `end_level` = 26, `color_index` = 3, RGB(83, 96, 66).
-   **Snow**: `start_level` = 27, `end_level` = 150, `color_index` = 4, RGB(217, 213, 221).

**Algorithm Steps:**
1.  Iterate through each `Terrain` object in the `ColorMap.colors` vector.
2.  For each `Terrain`, check if the input `height` satisfies: `start_level <= height <= end_level`.
3.  If the condition is true, return the `Terrain.color_index`.
4.  If the loop completes without a match, return `None`.

**Pseudocode:**
```python
def get_terrain_color(color_map: ColorMap, height: u8) -> Optional[u8]:
    """
    Maps a discrete height level to a terrain color index.
    
    Args:
        color_map: The ColorMap containing terrain bands.
        height: The scalar height value to classify.
        
    Returns:
        The color_index if a matching band is found, otherwise None.
    """
    for terrain in color_map.colors:
        if terrain.start_level <= height <= terrain.end_level:
            return terrain.color_index
    return None
```

**Edge Cases and Pitfalls:**
-   **Gaps:** If there are gaps between `end_level` of one band and `start_level` of the next (e.g., if Dirt ended at 6 and Grass started at 8), heights in the gap (7 in this specific example, though Dirt covers 7) will return `None`. In the provided example, Dirt covers 7, so there is no gap between Water (0-6) and Grass (8-26) because Dirt fills level 7.
-   **Out of Bounds:** Heights below the minimum `start_level` or above the maximum `end_level` return `None`.
-   **Precision:** The implementation uses `u8` for levels, limiting the resolution to 256 discrete levels.

## Operating characteristics
-   **Time Complexity:** $O(N)$ where $N$ is the number of terrain bands, as it iterates through the list until a match is found.
-   **Memory Complexity:** $O(N)$ to store the `ColorMap` structure.
-   **Strengths:** Simple to implement; computationally inexpensive; clear categorical distinction between terrain types.
-   **Limitations:** No smooth transitions between terrain types; discrete jumps in color; limited resolution if using small integer types for levels.
-   **When to use:** When distinct, categorical terrain visualization is desired (e.g., stylized maps, voxel games).
-   **When not to use:** When smooth, continuous color gradients are required.

## Background
This method is derived from the `tellus` project by dsunshi [S1, unofficial], which implements procedural terrain generation. It reflects a common approach in voxel-based and procedural generation contexts where terrain types are defined by strict elevation thresholds.
