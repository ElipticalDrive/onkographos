# Oblivious Lookup Tables

Also called: Wamser et al. approach

## Overview
Oblivious Lookup Tables (OLT) are a cryptographic mapping technique that allows a function $f: X \to Y$ to be evaluated on encrypted data without revealing the input values $X$. Unlike standard lookup tables that rely on array indexing (which requires comparison or equality checks incompatible with probabilistic homomorphic encryption), OLTs use linear algebra—specifically dot products—to perform the lookup [S1][S2, unofficial]. This method enables volume rendering transfer functions to operate on encrypted voxel data, solving the inability to use comparison operators in probabilistic Partially Homomorphic Encryption (PHE) schemes like Paillier [S1][S2, unofficial].

## How it works
**Inputs and Outputs**
*   **Input:** A set of domain values $X = \{x_1, x_2, \dots, x_n\}$ and a corresponding set of target values $Y = \{y_1, y_2, \dots, y_n\}$ (e.g., color channel intensities). The input value $x_i$ may be encrypted.
*   **Output:** The mapped value $y_i = f(x_i)$, encrypted if the input was encrypted.
*   **Precomputed Data:** A lookup vector $\vec{l}$ of size $n$.

**Data Structures**
*   **Vandermonde Matrix ($V$):** An $n \times n$ square matrix where the $i$-th row $\vec{v}_i$ is derived from the domain value $x_i$.
*   **Lookup Vector ($\vec{l}$):** A plaintext vector of size $n$, computed once from unencrypted $X$ and $Y$.
*   **Evaluation Vector ($\vec{v}_i$):** A vector of size $n$ representing the input $x_i$. If $x_i$ is encrypted, $\vec{v}_i$ must also be encrypted component-wise.

**Formulas**
The core relationship is defined by the linear system:
$$ V \cdot \vec{l} = \vec{y} $$
Where:
*   $V$ is the Vandermonde matrix with entries $V_{ij} = x_i^{j-1}$ for $i, j \in \{1, \dots, n\}$.
*   $\vec{y}$ is the column vector of target values $[y_1, y_2, \dots, y_n]^T$.
*   $\vec{l}$ is the solution vector.

The evaluation of the lookup for a specific input $x_i$ is a dot product:
$$ f(x_i) = \vec{v}_i \cdot \vec{l} = y_i $$
Where $\vec{v}_i = (1, x_i^1, x_i^2, \dots, x_i^{n-1})$ [S1][S2, unofficial].

**Steps**
1.  **Define Domain and Range:** Select $n$ distinct domain values $X = \{x_1, \dots, x_n\}$ and their corresponding target outputs $Y = \{y_1, \dots, y_n\}$. For volume rendering, $n$ is typically $2^8 = 256$ for 8-bit voxels [S1][S2, unofficial].
2.  **Construct Vandermonde Matrix:** Build the $n \times n$ matrix $V$ where row $i$ is $\vec{v}_i = (1, x_i, x_i^2, \dots, x_i^{n-1})$ [S1][S2, unofficial].
3.  **Compute Lookup Vector:** Solve the linear system $V \cdot \vec{l} = \vec{y}$ for $\vec{l}$. This step is performed offline using unencrypted data [S1][S2, unofficial].
4.  **Encrypt Input Vector:** For an encrypted input $\llbracket x_i \rrbracket$, compute the encrypted evaluation vector $\llbracket \vec{v}_i \rrbracket = (1, \llbracket x_i \rrbracket, \llbracket x_i^2 \rrbracket, \dots, \llbracket x_i^{n-1} \rrbracket)$. Note: This requires multiplying encrypted numbers, which is **not supported** by Paillier PHE [S1][S2, unofficial].
5.  **Evaluate Lookup:** Compute the dot product $\llbracket y_i \rrbracket = \llbracket \vec{v}_i \rrbracket \cdot \vec{l}$. This involves only addition ($\oplus$) and multiplication by a plaintext constant ($\otimes$), which are supported by Paillier [S1][S2, unofficial].

**Pseudocode**
```python
def compute_lookup_vector(domain_values, target_values):
    """
    Precomputes the lookup vector l for a given mapping.
    domain_values: list of n floats [x1, x2, ..., xn]
    target_values: list of n floats [y1, y2, ..., yn]
    Returns: list of n floats l
    """
    n = len(domain_values)
    # Construct Vandermonde matrix V
    V = []
    for i in range(n):
        x = domain_values[i]
        row = [x**j for j in range(n)]
        V.append(row)
    
    # Solve V * l = y for l
    # Using standard linear algebra solver (e.g., numpy.linalg.solve)
    # This step is done offline with unencrypted data
    l = solve(V, target_values)
    return l

def evaluate_olt(encrypted_x, lookup_vector):
    """
    Evaluates the lookup for an encrypted input x.
    encrypted_x: Encrypted scalar value (e.g., using Paillier)
    lookup_vector: Precomputed plaintext vector l
    Returns: Encrypted result y
    """
    n = len(lookup_vector)
    
    # Construct evaluation vector v = (1, x, x^2, ..., x^(n-1))
    # WARNING: Computing x^k for k > 1 requires multiplying encrypted numbers.
    # Paillier PHE does NOT support multiplication of two encrypted numbers.
    # Therefore, this step is impossible for general encrypted x in Paillier.
    # A theoretical workaround is storing v directly, but it increases storage by factor n.
    
    # If we assume v is available (e.g., pre-stored or computed via alternative means):
    # encrypted_v = [encrypt(1), encrypt(x), encrypt(x**2), ..., encrypt(x**(n-1))]
    
    # Compute dot product: sum(v_i * l_i)
    # This uses multiply-by-constant (supported) and add (supported)
    result = 0
    for i in range(n):
        # l[i] is plaintext, encrypted_v[i] is encrypted
        term = multiply_by_constant(encrypted_v[i], lookup_vector[i])
        result = add(result, term)
        
    return result
```

**Parameters and Pitfalls**
*   **Size ($n$):** Must be large enough to approximate the desired function. For 8-bit voxels, $n=256$ [S1][S2, unofficial].
*   **Storage Overhead:** Storing the evaluation vector $\vec{v}_i$ for every voxel increases storage by a factor of $n$. For a $512^3$ volume with 8-bit voxels, this grows from 128 MB to 16 TB, which is impractical [S1][S2, unofficial].
*   **Encryption Limitations:** The method relies on the ability to compute $\vec{v}_i$ from $x_i$. In Paillier PHE, computing powers of encrypted $x_i$ (i.e., $x_i^2, x_i^3$) is impossible because it requires multiplying two encrypted numbers [S1][S2, unofficial]. This is the primary limitation preventing direct application to general encrypted volumes without massive storage overhead [S1][S2, unofficial].

## Subtopics

### Density Range Emphasizing
A simplified variant of OLT designed to highlight specific density ranges in encrypted volume rendering without full alpha compositing. It encodes voxel density as a vector, encrypts it, and computes a dot product with a plaintext emphasis vector [S2, unofficial].
*   **Definition:** Encodes each voxel's density as a vector (e.g., via HSV-to-RGB conversion), encrypts the vector components, and computes the dot product with a plaintext emphasis vector centered on the user-selected density range [S2, unofficial].
*   **Steps:**
    1.  Encode density $d$ as a vector $\vec{v}$ of length $dim$ (e.g., 3 or 4) using a scheme like Algorithm 3 in [S2, unofficial].
    2.  Encrypt each component of $\vec{v}$ using Paillier [S2, unofficial].
    3.  Define a plaintext emphasis vector $\vec{e}$ corresponding to the target density center [S2, unofficial].
    4.  Compute the dot product $\vec{v}_{encrypted} \cdot \vec{e}$ [S2, unofficial].
    5.  Normalize the result to $[0, 1]$ so that the maximum value (1) occurs at the emphasizing density [S2, unofficial].
*   **Parameters:** $\gamma$ defines the precision for approximating division of an encrypted number by a plaintext number $d$ via multiplication with reciprocal $(1/d \cdot 10^\gamma, -\gamma)$ [S2, unofficial].
*   **Pitfalls:** Cannot use alpha blending sample compositing because it requires multiplying two encrypted values, which is impossible with Paillier. The method only highlights density ranges rather than performing full compositing [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(n)$ per lookup evaluation, where $n$ is the size of the lookup table (domain size). The precomputation of $\vec{l}$ is $O(n^3)$ due to matrix inversion/solving, but done once [S1][S2, unofficial].
*   **Memory Complexity:** $O(n)$ for the lookup vector $\vec{l}$. If evaluation vectors $\vec{v}_i$ are stored per voxel, memory increases by a factor of $n$ [S1][S2, unofficial].
*   **Strengths:** Compatible with probabilistic PHE (Paillier) for addition and multiplication-by-constant. Enables secure evaluation of transfer functions on encrypted data [S1][S2, unofficial].
*   **Limitations:** High storage overhead if evaluation vectors are stored per voxel (16 TB for $512^3$ volume) [S1][S2, unofficial]. Cannot compute powers of encrypted inputs directly in Paillier, limiting general applicability [S1][S2, unofficial]. Not suitable for full alpha compositing in PHE contexts [S2, unofficial].
*   **When to Use:** When secure, encrypted volume rendering is required and the user can accept simplified transfer functions (like density emphasis) or has sufficient storage for precomputed vectors [S1][S2, unofficial].
*   **When Not to Use:** When standard hardware-accelerated lookup tables are sufficient (unencrypted data) or when full alpha compositing is required with Paillier encryption [S2, unofficial].

## Background
The Oblivious Lookup Table method was introduced by Wamser et al. in their work on "Oblivious Lookup-Tables" [S1][S2, unofficial]. It was developed to address the challenges of performing volume rendering on encrypted data using Partially Homomorphic Encryption (PHE), specifically the Paillier cryptosystem [S1][S2, unofficial]. Standard array-based lookup tables fail for encrypted data because encryption obfuscates values, making equality checks and indexing insecure or impossible [S2, unofficial]. The OLT approach leverages the linear properties of PHE to perform lookups via dot products, enabling secure visualization of medical and scientific data [S1][S2, unofficial].
