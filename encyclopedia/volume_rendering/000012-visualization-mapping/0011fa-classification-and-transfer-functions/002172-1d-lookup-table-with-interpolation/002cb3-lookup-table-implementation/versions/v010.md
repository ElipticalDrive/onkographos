# Lookup Table Implementation
Also called: Post-Interpolation Transfer Function Lookup Table, vzParameterLookupTable

## Overview
Lookup Table (LUT) implementation is the mechanism for mapping scalar volume data values to RGBA color and opacity properties using a one-dimensional texture or array applied after texture interpolation in the imaging pipeline [S1]. It solves the problem of visualizing quantitative scalar fields by assigning optical properties based on intensity alone, decoupling the classification logic from the rendering traversal . Unlike [Parametric Function Generation](5349-parametric-function-generation.md) which computes values analytically at runtime, or [2D Transfer Function](7592-2d-transfer-function.md) which incorporates gradient magnitude, this family relies on pre-computed or dynamically generated tables . It differs from [3D Color Cube Interpolation](13036-bipolar-scalar-to-color-mapping-with-level-set-support.md) by interpolating color *indices* (texture coordinates) rather than RGB values directly, ensuring all sampled colors remain within the defined colorbar and avoiding artifacts like purple hues between red and blue regions [S3].

## Shared principles
All implementations in this family share the following mechanism, terms, and mathematical constraints:

**Data Structure and Format**
The transfer function is stored as a contiguous array of 4-component vectors $(R, G, B, \alpha)$ [S2, unofficial].
*   **Format:** Typically `float4` (32-bit floats per component) or 8-bit integers (`uint8_t[4]`) [S1][S2, unofficial][S3].
*   **Size:** The number of entries $N$ must be a power of two (e.g., 256, 4096, 65536) to support hardware texture sampling [S1][S2, unofficial][S3].
*   **Layout:** A 1D array where index $i$ corresponds to the normalized value mapping to entry $i$. In some hardware implementations (e.g., VolumePro), the LUT may be 4096 entries deep with 36-bit entries (8-bit RGB, 12-bit alpha) [S3].

**Normalization and Domain**
The input scalar value $v$ is mapped to a normalized coordinate $x \in [0, 1]$ using a defined domain $[x_{min}, x_{max}]$:
$$ x = \frac{v - x_{min}}{x_{max} - x_{min}} $$
Values outside $[x_{min}, x_{max}]$ are clamped to $[0, 1]$ [S2, unofficial][S3]. The parameters $x_{min}$ and $x_{max}$ (or `window_left` and `window_width`) are passed to the shader as uniforms [S2, unofficial].

**Sampling Methods**
Two primary methods are used to retrieve RGBA values from the LUT:
1.  **Hardware Interpolation:** Use texture units with `LINEAR` filter mode to interpolate between adjacent entries based on $x$ [S1]. This requires the LUT to be uploaded as a texture with appropriate wrap modes (`CLAMP_TO_EDGE`) [S1].
2.  **Direct Lookup:** Compute the integer index for nearest-neighbor sampling:
    $$ idx = \text{clamp}(\lfloor x \cdot (N-1) \rfloor, 0, N-1) $$
    Return the value at `table[idx]` [S3].

**Opacity Correction**
In some hardware pipelines, opacities may require software correction to account for non-unit sample spacing $\Delta$ [S3]. The opacity entry $\alpha_0$ is computed as:
$$ \alpha_0 = 1 - e^{-map[C_i] \Delta_0} $$
If the distance changes to $\Delta_k$, the opacity values must be corrected accordingly [S1].

## Subtopics

### [Hardcoded Transfer Function](1098-hardcoded-transfer-function.md)
The Hardcoded Transfer Function (HTF) maps a single scalar input value directly to a fixed color and opacity tuple using a pre-defined, static lookup table. It solves the problem of visualizing scalar field data by assigning RGBA properties based solely on intensity, without considering local geometric context or multi-channel correlations. Unlike gradient-based or texture-based transfer functions, the HTF relies exclusively on the scalar value itself, making it the simplest and most computationally efficient classification approach, though it cannot distinguish between visually distinct features that share the same intensity.

### [UpdateOpacityTransferFunction](2489-updateopacitytransferfunction.md)
Allocates GPU memory and loads the opacity transfer function (TF) table, or reloads it if the transfer function has changed. It uploads the transfer function LUT to the GPU and checks if the alpha values are monotonically non-decreasing; if not, it applies a Cumulative Distribution Function (CDF) transformation before uploading. This transformation is required for Digital Differential Analyzer (DDA) optimizations. It differs from [Transfer Function Loading](4289-transfer-function-loading.md) by focusing on the memory management, monotonicity enforcement, and state binding rather than file I/O and parsing.

### [1D Transfer Function Generation and Sampling](2689-1d-transfer-function-generation-and-sampling.md)
1D Transfer Function Generation and Sampling maps scalar volume data values to RGBA color and opacity properties using a one-dimensional lookup table (LUT). It solves the problem of visualizing quantitative scalar fields by assigning optical properties based on intensity alone. Unlike [Parametric Function Generation](5349-parametric-function-generation.md) which computes values analytically, or [2D Transfer Function](7592-2d-transfer-function.md) which incorporates gradient magnitude, this method relies on piecewise linear interpolation between user-defined control points. It differs from [3D Color Cube Interpolation](13036-bipolar-scalar-to-color-mapping-with-level-set-support.md) by interpolating color *indices* (texture coordinates) rather than RGB values directly, ensuring all sampled colors remain within the defined colorbar and avoiding artifacts like purple hues between red and blue regions.

### [Shading Lookup Table Computation](3589-shading-lookup-table-computation.md)
Shading Lookup Table Computation is the process of generating the color and opacity entries for a 1D transfer function lookup table (LUT) by applying a shading model to the scalar field values. It solves the problem of how to map raw scalar data to visually meaningful RGBA values that account for lighting, material properties, and view orientation, rather than using static, pre-shaded colors. It differs from [Hardcoded Transfer Function](1098-hardcoded-transfer-function.md) by computing values dynamically based on current scene parameters, and from [UpdateOpacityTransferFunction](2489-updateopacitytransferfunction.md) by encompassing the full color/opacity computation rather than just opacity adjustments.

### Cosine Ramp Table Generation
A helper procedure that generates a cosine-shaped ramp table for smoothly attenuating density values [S2, unofficial]. It is used to ramp off density values that exceed a certain threshold from the center of a volume slab [S2, unofficial].
**Steps:**
1.  Loop $i$ from $0$ to $RAMP\_SIZE-1$ [S2, unofficial].
2.  Compute normalized distance: $dist = i / (RAMP\_SIZE - 1.0)$ [S2, unofficial].
3.  Compute ramp value: $ramp[i] = (\cos(dist \cdot \pi) + 1.0) / 2.0$ [S2, unofficial].

### Oblivious Lookup Tables
A method to map a set of input values $X$ to output values $Y$ using dot products, allowing evaluation on encrypted data without revealing the input value, solving the inability to use comparison operators in probabilistic PHE [S3].
**Formula:**
$$ V \cdot \tilde{l} = \tilde{y} $$
where $V$ is a Vandermonde matrix with rows $\tilde{v}_i = (1, x_i^1, ..., x_i^{n-1})$, $\tilde{l}$ is the lookup vector, and $\tilde{y}$ is the result vector [S3].
$$ f(x_i) = (1, x_i^1, x_i^2, ..., x_i^{n-1}) \cdot \tilde{l} = y_i $$
**Parameters:**
*   $V$: A Vandermonde matrix used to ensure linear independence of vectors $\tilde{v}_i$ [S3].
**Pitfalls:**
*   It is not possible to calculate the vector $\tilde{v}_i$ from an encrypted $[x_i]$ because it requires multiplying two encrypted numbers, which Paillier does not support [S3].
*   Storing vectors $\tilde{v}_i$ instead of scalars $x_i$ increases storage by a factor of $n$ (e.g., 256 for 8-bit voxels), leading to impractical sizes (16TB for a $512^3$ volume) [S3].

## Background
The concept of using lookup tables for volume rendering classification originated with early hardware-accelerated volume rendering systems. The `vzParameterLookupTable` class, part of the SGI OpenGL Volumizer toolkit, implemented transfer functions as post-interpolation lookup tables applied in the imaging pipeline after texture interpolation [S1]. This approach allowed for efficient hardware-accelerated sampling of transfer functions using standard texture units [S1]. The requirement for power-of-two widths was a constraint of the underlying hardware texture units of that era [S1]. Later developments, such as those in VolPack, introduced dynamic shading lookup tables that recomputed LUT entries based on lighting and view parameters [S1, S3]. More recently, oblivious lookup tables have been explored for secure volume rendering using homomorphic encryption, addressing privacy concerns in medical imaging [S3].
