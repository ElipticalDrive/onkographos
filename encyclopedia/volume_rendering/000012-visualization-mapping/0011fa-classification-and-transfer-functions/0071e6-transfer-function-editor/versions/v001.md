# Transfer Function Editor

Also called: Gradient Picker, TransfareFunctionPicker

## Overview
The Transfer Function Editor is an interactive user interface component that allows users to define and modify 1D transfer functions in real-time to classify volumetric data. It solves the problem of manual parameter tuning by providing a visual mechanism to adjust color and opacity mappings for material separation. It is distinguished from static LUT methods by its direct manipulation of handles on a gradient bar, enabling immediate visual feedback during ray casting [S1][S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** User interactions (clicks, drags, double-clicks) on a UI container representing the transfer function domain (typically scalar intensity).
*   **Output:** An updated transfer function definition (set of keypoints with color and opacity values) applied to the rendering shader.

**Data Structures:**
The editor maintains a list of handles. Each handle represents a keypoint in the transfer function and stores:
*   `position`: A normalized float in $[0, 1]$ representing the scalar value domain.
*   `color`: A hex string or RGB vector representing the output color.
*   `opacity`: A float in $[0, 1]$ representing the output opacity.
*   `hard`: A boolean toggle indicating if the gradient interpolation between handles is linear (hard) or smooth [S2, unofficial].

**Numbered Steps:**
1.  **Initialization:** Query the DOM for the slider container and background gradient element [S2, unofficial].
2.  **Handle Addition:** On a double-click event within the container:
    a. Clone a template element for the color handle [S2, unofficial].
    b. Calculate the handle's position percentage $p$ based on the click location relative to the container width $bw$ and handle width $hw$:
       $$ p = \max(0, \min(bw - hw, \text{clientX} - \text{box.left} - hw/2) / bw) $$
    c. Compute the initial color using a linear interpolation scale (e.g., `d3.scaleLinear`) based on $p$ [S2, unofficial].
    d. Set the handle's value attribute to the computed hex color.
3.  **Handle Dragging:** Attach pointer event listeners to each handle:
    a. `pointerdown`: Capture the pointer to track movement across the container.
    b. `pointermove`: Update the handle's `left` CSS position based on the pointer's current coordinates.
    c. `pointerup`: Release the pointer capture.
4.  **Handle Removal:** On a double-click event on an existing handle (detected via `event.detail === 2`), remove the handle element from the DOM and update the gradient representation [S2, unofficial].
5.  **Gradient Update:** After any modification (add, remove, move), recalculate the visual gradient bar and update the transfer function data structure passed to the renderer.

**Parameters:**
*   `hard`: Boolean toggle for gradient interpolation mode. When true, interpolation is linear; when false, it may use smooth curves [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Boundary Clamping:** Handle positions must be clamped to $[0, 1]$ to prevent handles from moving outside the valid domain [S2, unofficial].
*   **Precision:** Floating-point precision in position calculation should be sufficient to distinguish adjacent handles.
*   **Degenerate Input:** If no handles exist, the transfer function defaults to a uniform color/opacity or requires a default handle creation.

**Pseudocode:**

class TransferFunctionEditor:
    def __init__(self, container_element, gradient_element):
        self.container = container_element
        self.gradient = gradient_element
        self.handles = []  # List of Handle objects
        self.hard_mode = False

    def on_double_click(self, event):
        # Check if click is on an existing handle to remove it
        if event.target.is_handle and event.detail == 2:
            self.remove_handle(event.target)
            return

        # Add new handle
        handle = self.create_handle(event)
        self.handles.append(handle)
        self.container.append(handle.element)
        self.update_gradient()

    def create_handle(self, event):
        # Clone template
        element = clone_template("colorHandle")
        
        # Calculate position percentage
        box = self.container.get_bounding_rect()
        bw = box.width
        hw = element.width
        client_x = event.clientX
        left_offset = client_x - box.left
        
        pct = max(0, min(bw - hw, left_offset - hw / 2) / bw)
        
        # Compute color via linear interpolation
        color = d3_scale_linear.interpolate(pct)
        element.value = hex(color)
        element.position = pct
        
        # Attach drag events
        element.on_pointer_down = self.on_pointer_down
        element.on_pointer_move = self.on_pointer_move
        element.on_pointer_up = self.on_pointer_up
        
        return Handle(element, pct, color)

    def on_pointer_down(self, event, handle):
        event.capture_pointer()
        self.dragging_handle = handle

    def on_pointer_move(self, event, handle):
        if self.dragging_handle != handle:
            return
        box = self.container.get_bounding_rect()
        bw = box.width
        hw = handle.element.width
        left_offset = event.clientX - box.left
        
        new_pct = max(0, min(bw - hw, left_offset - hw / 2) / bw)
        handle.position = new_pct
        handle.element.style.left = f"{new_pct * 100}%"
        
        # Update color if needed or just position
        self.update_gradient()

    def on_pointer_up(self, event, handle):
        event.release_pointer()
        self.dragging_handle = None

    def remove_handle(self, handle):

        handle.element.remove()

## Operating characteristics
*   **Time Complexity:** Interaction is $O(1)$ per handle modification. Updating the gradient and LUT is $O(N)$ where $N$ is the number of keypoints.
*   **Memory Complexity:** $O(K)$ where $K$ is the number of handles.
*   **Strengths:** Immediate visual feedback; intuitive for users; allows fine-grained control over material separation.
*   **Limitations:** Manual tuning can be time-consuming; requires user expertise to find optimal parameters; prone to overfitting to specific views.
*   **When to use:** Interactive exploration and debugging; scenarios where user intuition is valuable.
*   **When not to use:** Automated pipelines; large-scale batch processing; complex multi-dimensional transfer functions requiring statistical modeling.

## Background
The Transfer Function Editor originated as a standard component in volume visualization software to facilitate user-driven classification. Early implementations used simple sliders, evolving into gradient-based editors with draggable handles. The method described here is based on a specific implementation using web technologies (Three.js, D3.js) for VR integration [S1][S2, unofficial].
