# Feature Graph

Also called: Feature Graph Construction, Feature Graph building

## Overview
The Feature Graph is a hierarchical data structure for volume rendering that represents classified voxel data as a directed acyclic graph (DAG) [S1, unofficial]. It solves the problem of efficiently managing and rendering complex, multi-label volumetric datasets by clustering voxels into features based on boolean classification criteria and organizing these features into an inclusion hierarchy [S1, unofficial]. Unlike standard transfer functions that map scalar values to optical properties per sample, the Feature Graph groups voxels into spatial clusters (features) and stores their geometry separately, allowing for direct access to voxel sets and native multiresolution support [S1, unofficial]. It is distinguished from sibling methods like [Curvature-based Transfer Function](5452-curvature-based-transfer-function.md) by its explicit graph-based organization of voxel sets rather than continuous function evaluation, and from [Robust Material Graph Deduction](7459-robust-material-graph-deduction.md) by its reliance on user-defined boolean criteria rather than automated material property inference.

## How it works
The method constructs a graph where nodes are features (non-empty clusters of voxels sharing specific label values) and arcs represent the inclusion relationship of voxel sets, directed from larger (ancestor) to smaller (descendant) features [S1, unofficial].

### Inputs and Outputs
**Inputs:**
*   A voxel volume $V$ of resolution $R \times R \times R$ (or varying dimensions).
*   A set of $n_c$ non-exclusive boolean classification criteria (e.g., "bone", "fat", "leg") [S1, unofficial].
*   For each voxel $v$, a label vector $\mathbf{l}(v) = [r_1(v), r_2(v), \dots, r_{n_c}(v)]$ where $r_i(v) \in \{0, 1\}$ indicates if voxel $v$ satisfies criterion $i$ [S1, unofficial].

**Outputs:**
*   A Feature Graph $G = (N, E)$, where $N$ is the set of feature nodes and $E$ is the set of inclusion arcs [S1, unofficial].
*   A Feature Hash Table mapping label combinations to graph nodes [S1, unofficial].
*   Sets of Voxels (SOVs) stored at leaf nodes, representing the geometry of each feature [S1, unofficial].

### Data Structures

**1. Feature Hash Table**
*   **Purpose:** Provides direct index access to feature nodes based on label combinations [S1, unofficial].
*   **Layout:** A hash map where the key is the label vector $\mathbf{l}$ (or a hash of it) and the value is a reference to the corresponding Feature Node.
*   **Size:** At most $2^{n_c}$ entries, though typically much smaller as many combinations are empty [S1, unofficial].

**2. Feature Node**
*   **Fields:**
    *   `id`: Unique identifier for the feature.
    *   `labels`: The boolean vector $\mathbf{l}$ defining this feature.
    *   `children`: List of child nodes (sub-features).
    *   `parent`: Reference to the parent node (optional, for traversal).
    *   `sovs`: List of Sets of Voxels (SOVs) associated with this node at different resolution levels [S1, unofficial].
    *   `optical_properties`: Opacity $\alpha$ and color $C$ assigned to this feature for rendering [S1, unofficial].

**3. Set of Voxels (SOV)**
*   **Definition:** The set of voxels belonging to feature $f_i$, denoted $SOV(f_i)$ [S1, unofficial].
*   **Storage Policy:** SOVs are stored **only** in leaf nodes of the graph to avoid redundancy. The SOV of an intermediate feature is computed by recursively traversing its descendants down to the leaves [S1, unofficial].
*   **Representation:**
    *   **Voxel List:** A list of voxel coordinates. Does not preserve spatial ordering. Suitable for view-aligned splatting [S1, unofficial].
    *   **Submodel (Octree):** An octree representation of the voxel set. Voxels not belonging to the feature are assigned zero value, ensuring a voxel has a non-zero value in only one unique leaf SOV. Preserves spatial ordering. Suitable for compact voxel distributions [S1, unofficial].
    *   **Compact List:** For list-based SOVs, homogeneous regions are compacted using an octree. Only "black" nodes (fully occupied) of the octree are stored with their associated voxel size [S1, unofficial].

### Algorithm: Feature Graph Construction

The construction process consists of three main steps: Clustering, Hierarchy Creation, and Multiresolution Handling [S1, unofficial].

**Step 1: Clustering**
1.  Traverse the labeled voxel model.
2.  For each voxel $v$, compute its label vector $\mathbf{l}(v)$ [S1, unofficial].
3.  Use $\mathbf{l}(v)$ as a hash code to index into the Feature Hash Table.
4.  Add $v$ to the SOV list indexed by this hash code.
    *   *Note:* Initially, SOVs are represented as simple lists of voxels [S1, unofficial].
5.  After traversal, for each non-empty SOV:
    *   Compute the bounding box of the voxels in the SOV.
    *   Create a voxel submodel (octree) for the SOV.
    *   Compress the octree. Optionally, traverse the octree to create a new list-based representation with voxels of various sizes (compact list) [S1, unofficial].

**Step 2: Hierarchy Creation**
1.  Create leaf nodes in the graph for each non-empty SOV computed in Step 1. Associate each leaf node with its SOV [S1, unofficial].
2.  Derive the hierarchy iteratively:
    *   Identify nodes that share common bits in their label hash codes.
    *   Recursively create common ancestor nodes for all nodes sharing a bit in their hash code. An ancestor node represents the union of its descendants' voxel sets [S1, unofficial].
    *   Update the Feature Hash Table to reference these newly created ancestor nodes [S1, unofficial].
3.  If the graph consists of multiple disconnected hierarchies, create a root node `fall` (feature fall) that includes all features that do not have an ancestor. `fall` serves as the entry point to the graph [S1, unofficial].

**Step 3: Multiresolution Handling**
1.  Compute label sets at coarser resolution levels (e.g., by averaging or subsampling the original volume) [S1, unofficial].
2.  Repeat the clustering process (Step 1) for the coarser voxels.
    *   *Note:* Some clusters non-empty at high resolution may become empty at lower resolution. Not all features exist at all levels. Some features may be leaves at one resolution and intermediate nodes at another [S1, unofficial].
3.  Distribute the SOVs computed from these coarser clusters through the existing graph hierarchy.
4.  Attach the coarser SOVs to the corresponding nodes in the graph. Each node can contain SOVs from different resolution levels [S1, unofficial].

### Parameters and Edge Cases
*   **$n_c$ (Number of Criteria):** Determines the potential size of the label space ($2^{n_c}$). Large $n_c$ increases memory for the hash table but allows finer classification [S1, unofficial].
*   **`fall` Node:** The entry point node. If the graph has multiple disconnected components, `fall` connects them. If all features have ancestors, `fall` may not be needed or may be the root of the single hierarchy [S1, unofficial].
*   **Empty Clusters:** Many label combinations may be empty. The algorithm only creates nodes for non-empty clusters [S1, unofficial].
*   **Resolution Changes:** A feature that is a leaf at high resolution may become an intermediate node at lower resolution if its voxel set is a subset of a larger feature at that resolution. SOVs are stored only at leaves for each resolution level [S1, unofficial].
*   **Precision:** When using voxel lists, spatial ordering is lost. This necessitates view-aligned splatting for rendering, as standard ray casting relies on spatial coherence [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Construction is $O(N \cdot n_c)$ for clustering, where $N$ is the number of voxels. Hierarchy creation depends on the number of features and $n_c$. Multiresolution construction adds overhead proportional to the number of resolution levels [S1, unofficial].
*   **Memory Complexity:** Depends on the number of features and the size of SOVs. Storing SOVs only at leaves reduces redundancy. Octree compression helps compact homogeneous regions. The Feature Hash Table size is bounded by $2^{n_c}$ [S1, unofficial].
*   **Performance:** Efficient for datasets with compact voxel distributions when using submodel (octree) representation. For sparse or scattered features, list-based representation with view-aligned splatting is preferred [S1, unofficial].
*   **Strengths:** Native multiresolution support; direct access to voxel sets; avoids aliasing in perspective projection by allowing focused features at higher resolutions; supports out-of-core traversal if SOVs are stored in separate files [S1, unofficial].
*   **Limitations:** Requires pre-computation of labels; view-aligned splatting may be slower than ray casting for dense volumes; loss of spatial ordering in list-based SOVs [S1, unofficial].

## Background
The Feature Graph was introduced in the paper "Splatting multiresolution volume data using the feature graph" [S1, unofficial]. It is designed to address the limitations of traditional volume rendering techniques in handling complex, multi-label data with varying resolution requirements. The method builds on the principles of data feature-based classification, extending them with a graph-based hierarchy for efficient storage and rendering [S1, unofficial].
