# AI-Based Transfer Function Peak Prediction

Also called: AI-Assisted Transfer Function Selection, ONNX Transfer Function Picker, Peak Predictor, usePeakPredictor, usePeakPredictor hook

## Overview
This method automates the selection of the `peak` parameter for a volume rendering transfer function by analyzing rendered frames using a lightweight neural network [S1, unofficial]. It solves the tedious manual tuning required when browsing many volume/surface pairs by predicting the optimal peak value that maximizes feature visibility [S1, unofficial]. It is distinguished from other optimization methods by its reliance on a pre-trained MobileNetV3-Small model running in WebAssembly, rather than iterative gradient-based loss minimization or lookup tables [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A sequence of rendered pixel buffers (color images) corresponding to different trial `peak` values, and a surface-only frame.
*   **Output:** A single scalar value representing the predicted optimal `peak` parameter for the transfer function [S1, unofficial].

**Data Structures:**
1.  **Transfer Function Texture:** Implemented as a `DataTexture` with width 256, height 1, and format `RGBA` (4 bytes per 8-bit data value) [S1, unofficial].
2.  **Input Tensor:** A multi-channel tensor of size $192 \times 192$ pixels [S1, unofficial].
3.  **Tensor Channels:**
    *   Channel 1: Binary mask representing the dilation of the green surface.
    *   Channel 2: Binary mask representing the crop region.
    *   Channel 3: Red channel of the combined render for trial $i$.
    *   Channel 4: Red channel of the combined render for trial $j$ (if multiple trials are batched; otherwise, the method cycles through trials sequentially or the tensor structure adapts to single-frame analysis per prediction) [S1, unofficial]. *Note: The source describes building a tensor from captures of "each combined render," implying the input tensor aggregates data from multiple trial renders or the model processes a single frame per prediction cycle. The pseudocode below assumes a single prediction cycle per call, processing one frame at a time or a batch if defined by the specific implementation.*

**Parameters:**
*   **Model:** MobileNetV3-Small [S1, unofficial].
*   **Runtime:** ONNX Runtime Web (version ^1.24.3) [S1, unofficial].
*   **Input Resolution:** $192 \times 192$ pixels [S1, unofficial].
*   **Transfer Function Shape:** Tent-shaped alpha curve. Alpha rises from `alpha0` (at data value 0) to 255 (at `peak`) and falls to `alpha1` (at data value 255). The rise/fall is controlled by `dataGamma` via $y^{(1.0 / \text{dataGamma})}$, where $y$ is the normalized data value [S1, unofficial].

**Numbered Steps:**
1.  **Initialization:** Load the ONNX Runtime Web library and the MobileNetV3-Small model from a CDN [S1, unofficial].
2.  **Trial Rendering:** Cycle through a range of `peak` values (high to low). For each `peak` value:
    a. Update the transfer function texture with the current `peak` [S1, unofficial].
    b. Render the volume.
    c. Capture the pixel buffer using `gl.readPixels` [S1, unofficial].
    d. Render a surface-only frame to identify the green surface [S1, unofficial].
3.  **Verification:** Write a one-byte watermark into the blue channel of the image center pixel in the fragment shader. Read back the pixel and compare against the expected value to ensure frame integrity [S1, unofficial].
4.  **Tensor Construction:**
    a. Create binary masks for the dilated green surface and the crop region.
    b. Extract the red channel from the captured combined render.
    c. Combine these into a multi-channel tensor.
    d. Crop and resize the tensor to $192 \times 192$ pixels [S1, unofficial].
5.  **Prediction:** Feed the tensor into the ONNX model. The model outputs the predicted optimal `peak` value [S1, unofficial].
6.  **Application:** Apply the predicted `peak` value to the transfer function [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Dependency Failure:** If `onnxruntime-web` is not installed as a peer dependency, the build fails with a Webpack error: "Module not found: Error: Can't resolve 'onnxruntime-web'" [S1, unofficial].
*   **Network Timeout:** The WASM code for ONNX Runtime is fetched from a CDN. If the CDN does not respond within 10 seconds, an exception is thrown [S1, unofficial].
*   **Precision:** The transfer function uses 8-bit data values (0-255) mapped to a 256-width texture [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Depends on the inference time of MobileNetV3-Small on WebAssembly and the cost of `gl.readPixels` and tensor construction. Not given in the sources.
*   **Memory Complexity:** Requires storing the ONNX model in memory and temporary buffers for rendering and tensor construction. Not given in the sources.
*   **Performance:** Designed for web-based volume rendering (Three.js). Performance is constrained by WebAssembly overhead and WebGL readback latency. Not given in the sources.
*   **Strengths:** Automates a tedious manual process; lightweight model suitable for web environments; integrates directly with React hooks.
*   **Limitations:** Requires a CDN connection for WASM loading; dependent on the quality of the training data for the MobileNetV3 model; limited to the specific transfer function shape described (tent-shaped alpha).

## Background
This method is implemented in the `web-vol-viewer` project by JaneliaSciComp [S1, unofficial]. It is designed for fluorescence microscopy data visualization, building on the principles of the FluoRender application described by Wan et al. (2012) [S1, unofficial]. The approach leverages the availability of ONNX Runtime Web to enable machine learning inference in the browser.
