# Brushing and Linking with Hilbert Codes

Also called: Brushing and Linking for DVL and 3D Views, Hilbert code selection

## Overview
This method enables interactive selection in volume rendering by mapping Regions of Interest (ROIs) identified in a 1D data view (such as Dynamic Volume Lines) to corresponding spatial cells in a 3D view. It solves the problem of efficiently linking disparate visualizations by using Hilbert space-filling codes as compact selection ranges, avoiding the transmission of large lists of cell indices. It is distinguished from sibling methods by representing selection boundaries as 1D Hilbert code intervals rather than 3D geometric primitives or explicit cell lists [S1][S2, unofficial].

## How it works
**Inputs:**
*   A set of selected ROIs from the 1D view, defined by their first and last Hilbert codes ($H_{start}, H_{end}$).
*   A 3D volume dataset (structured-regular or AMR).
*   A 3D rendering shader.

**Outputs:**
*   A selection mask applied to the 3D view, highlighting cells whose Hilbert codes fall within the specified ranges.

**Data Structures:**
*   **Selection Range:** A pair of integers $(H_{start}, H_{end})$ representing the inclusive range of Hilbert codes for the selected ROI [S1][S2, unofficial].
*   **Cell Hilbert Code:** An integer index representing the position of a cell in the Hilbert space-filling curve traversal [S1].

**Steps:**
1.  **User Selection:** The user selects a region in the 1D plot. The system identifies the first and last Hilbert codes of the cells comprising this ROI, denoted as $H_{start}$ and $H_{end}$ [S1][S2, unofficial].
2.  **Transmission:** These two values are sent to the 3D rendering context. The ROIs are represented as these Hilbert code ranges, not as lists of world-space coordinates [S1][S2, unofficial].
3.  **Shader Execution:** For each sample or cell processed in the 3D shader:
    a.  Determine the spatial position of the current cell center $C$.
    b.  Compute the Hilbert code $H(C)$ for this position.
    c.  Check if $H_{start} \le H(C) \le H_{end}$ [S1][S2, unofficial].
4.  **Highlighting:** If the condition in step 3c is true, the cell is marked as selected and highlighted (e.g., via opacity or color modification) [S1][S2, unofficial].

**Formulas:**
*   **Selection Test:** A cell with Hilbert code $H$ is selected if:
    $$ H_{start} \le H \le H_{end} $$
    where $H$ is the Hilbert code of the cell center [S1][S2, unofficial].

**Parameters:**
*   **Hilbert Order:** Determined by the resolution of the grid or the depth of the AMR hierarchy. Not given in the sources.

**Edge Cases and Pitfalls:**
*   **Structured-Regular Volumes:** Cell bounds can be derived implicitly from the Hilbert code because all cells have uniform size. No explicit location lookup is needed for size determination [S1][S2, unofficial].
*   **AMR Data:** The Hilbert code of the cell centroid is insufficient to determine the exact size or bounds of the ROI. The implementation must explicitly locate cells to know the ROI's exact size when checking if a sample falls inside an ROI [S1][S2, unofficial].
*   **Performance:** Transforming the cell center to Hilbert space in the shader incurs computational cost, but this is traded for the compactness of the selection representation [S1].

    Determines if a cell is within the selected Hilbert range.
    
    Args:

        h_end: Integer, last Hilbert code of the ROI.
        data_type: String, 'structured' or 'amr'.

        Boolean, True if the cell is selected.
    """
    # Compute Hilbert code for the cell center
    h_code = compute_hilbert_code(cell_center)
    
    # Basic range check
    if h_start <= h_code <= h_end:

## Operating characteristics
*   **Time Complexity:** The selection test is $O(1)$ per cell in the shader, assuming Hilbert code computation is constant time relative to the number of cells. However, for AMR data, the explicit location lookup adds overhead [S1][S2, unofficial].
*   **Memory Complexity:** The selection state is stored as two integers per ROI, which is significantly more compact than storing a list of cell indices [S1].
*   **Strengths:** Compact representation of selection ranges; efficient transmission between 1D and 3D views; suitable for GPU implementation [S1][S2, unofficial].
*   **Limitations:** Hilbert code computation in the shader can be costly; AMR data requires additional logic to handle variable cell sizes [S1][S2, unofficial].
*   **When to use:** When linking 1D data views (like DVL) with 3D volume views, especially for large datasets where transmitting cell lists is prohibitive [S1][S2, unofficial].

## Background
This method was introduced in the context of Visual Analysis of Large Multi-Field AMR Data on GPUs Using Interactive Volume Lines (2023) [S1][S2, unofficial]. It builds on the concept of Dynamic Volume Lines (DVL) and extends it to 3D views using Hilbert space-filling curves for efficient spatial indexing and selection [S1][S2, unofficial].
