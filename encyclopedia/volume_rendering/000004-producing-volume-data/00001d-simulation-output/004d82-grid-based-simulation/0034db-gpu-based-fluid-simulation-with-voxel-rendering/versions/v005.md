# GPU-based Fluid Simulation with Voxel Rendering

Also called: Integrating Real-Time Fluid Simulation with a Voxel Engine, Poxels Fluid Integration

## Overview
This method integrates real-time incompressible fluid simulation with sparse voxel-based rasterization on graphics hardware, specifically leveraging Direct3D geometry shaders for rendering and compute shaders for simulation [S1]. It solves the problem of efficiently visualizing fluid dynamics within a voxel engine by bypassing CPU-GPU data transfer bottlenecks through a GPU-only pipeline [S1]. It sets itself apart from its siblings by utilizing a specific optimization where voxel activation logic and color ramping are moved entirely into the geometry shader, using a dedicated texture of non-zero values to drive stream-out, distinguishing it from [Voxel-based 3D Fire Simulation](3411-voxel-based-3d-fire-simulation.md) which may use different emission models, and [Niagara Fluids Volume Rendering](7739-niagara-fluids-volume-rendering.md) which operates within a different engine architecture [S1].

## How it works
**Inputs and Outputs:**
The input is a 3D spatial domain defined by a chunk size $(N_x, N_y, N_z)$, typically a cube such as $64 \times 64 \times 64$ [S1]. The output is a rendered voxel scene representing the fluid field [S1].

**Data Structures:**
The simulation relies on GPU compute textures composed of single-precision float 4 types (`float4`) [S1].
*   **Velocity Textures:** Three textures store the velocity field (current, previous, and temporary) [S1].
*   **Pressure Textures:** Two textures store pressure values (current and temporary) [S1].
*   **Speed Grid Texture:** The final result of the five GPU compute stages is a 3D speed grid texture filled with single-precision floats, serving as the source fluid field for the rendering engine [S1].
*   **Non-Zero Texture:** A specialized texture containing only values that do not equal zero, used to drive the geometry shader for voxel activation [S1].
*   **Staging Texture:** Used only in the CPU approach to transfer data from GPU memory to CPU memory; it must match the size of the 3D voxel staging texture [S1].

**Navier-Stokes Processing Stages:**
The simulation applies the Navier-Stokes equations through the following stages [S1]:
1.  **Advection:** Transport of the velocity field.
2.  **Pressure Acceleration:** Acceleration caused by pressure gradients.
3.  **Diffusion:** Momentum diffusion resulting from fluid resistance.
4.  **External Forces:** Application of static or dynamic forces.

**Algorithm Steps:**
1.  **Advection:** Perform advection of the velocity field. This includes backward advection and pre-correction, followed by a second-order correction [S1].
2.  **Force Application:** Apply external forces to the velocity field [S1].
3.  **Divergence Calculation:** Calculate the speed divergence of the velocity field [S1].
4.  **Pressure Solve:** Solve the pressure-Poisson system using the Jacobi iteration method [S1].
5.  **Projection:** Subtract the pressure gradient from the velocity field to ensure incompressibility (project the velocity) [S1].
6.  **Voxel Activation (GPU-Optimized Path):**
    *   The compute shader outputs a texture containing only non-zero velocity values [S1].
    *   The geometry shader receives this texture.
    *   The geometry shader determines which voxels should be rendered based on the non-zero values [S1].
    *   The geometry shader applies a color ramp function, taking a float between 0 and 1 (representing concentration or magnitude) and returning an RGB color [S1].
    *   Vertex data is continuously output from the geometry shader stage using stream-out to a cached vertex buffer, guaranteeing deterministic ordering of rendered primitives [S1].
7.  **Rasterization:** Regular triangle geometry is rasterized using the generated vertex buffer [S1].

**Pseudocode (GPU-Optimized Pipeline):**

```python
# Compute Shader: Fluid Simulation Step
def compute_fluid_step(velocity_textures, pressure_textures, forces):
    # 1. Advection
    # Perform backward advection and pre-correction
    advected_velocity = backward_advection(velocity_textures.current, velocity_textures.previous)
    advected_velocity = second_order_correction(advected_velocity)
    
    # 2. Force Application
    velocity_textures.current = advected_velocity + forces
    
    # 3. Divergence Calculation
    divergence = calculate_divergence(velocity_textures.current)
    
    # 4. Pressure Solve (Jacobi Iteration)
    pressure_textures.current = solve_jacobi(divergence, pressure_textures.current)
    
    # 5. Projection
    pressure_gradient = calculate_gradient(pressure_textures.current)
    velocity_textures.current = velocity_textures.current - pressure_gradient
    
    # 6. Generate Non-Zero Mask for Rendering
    # Create a texture containing only non-zero velocity magnitudes
    non_zero_texture = create_non_zero_mask(velocity_textures.current)
    return non_zero_texture

# Geometry Shader: Voxel Rendering Step
def geometry_shader_render(non_zero_texture, chunk_size):
    # Input: Stream of voxel indices or coordinates derived from non_zero_texture
    # The geometry shader iterates over the non-zero values
    
    for each voxel_index in non_zero_texture:
        if non_zero_texture[voxel_index] != 0:
            # Get magnitude for color ramp
            magnitude = non_zero_texture[voxel_index]
            
            # Apply color ramp (float 0-1 to RGB)
            color = apply_color_ramp(magnitude)
            
            # Generate vertex data for the voxel (e.g., 6 faces of a cube)
            vertices = generate_voxel_geometry(voxel_index, color)
            
            # Stream-out to vertex buffer
            stream_out(vertices)

# CPU Approach (Legacy/Comparison)
def cpu_approach_render(speed_grid_texture, chunk_size):
    # 1. Copy data to CPU
    staging_texture = copy_to_staging_texture(speed_grid_texture)
    cpu_memory_buffer = map_staging_texture(staging_texture)
    speed_grid_array = copy_from_staging_texture(cpu_memory_buffer)
    
    # 2. Activate Voxels
    vertex_list = []
    for each voxel in speed_grid_array:
        if voxel.value != 0:
            # Apply color ramp
            color = apply_color_ramp(voxel.value)
            vertex_list.append(generate_voxel_geometry(voxel.index, color))
            
    # 3. Render
    upload_to_vertex_buffer(vertex_list)
    rasterize()
```

**Parameters:**
*   **Chunk Size:** The simulation grid size must match the size of the 3D voxel staging texture (in the CPU approach) or the rendering domain [S1]. Typical tested sizes include $32^3$, $64^3$, $96^3$, and $128^3$ blocks [S1].
*   **Memory Alignment:** The CPU memory buffer requires appropriate memory address alignment when mapping staging textures [S1].

**Edge Cases and Pitfalls:**
*   **Obstacle Detection:** The described simulation does not detect or respond to obstacles [S1].
*   **Data Transfer Bottleneck:** In the CPU approach, copying data from the staging texture to CPU memory is the most significant time consumer, far exceeding other steps [S1].
*   **Single Chunk Limitation:** The simulation is based on a single chunk and needs extension to multiple chunks for larger scenes [S1].

## Operating characteristics
**Time and Memory Complexity:**
*   The simulation scales linearly with the number of voxels [S1].
*   Memory usage is dominated by the five compute textures (three velocity, two pressure) plus the speed grid texture, all using single-precision floats [S1].

**Measured Performance:**
*   **Hardware:** NVIDIA GeForce GTX 950M (GTX 950M) and NVIDIA GeForce GT540M [S1].
*   **CPU Approach (GTX 950M, $64^3$ chunk):**
    *   Total FPS: 100 FPS (10.000 ms frame time) [S1].
    *   "Copy from staging texture to CPU" step: 23,088,969 ns [S1].
    *   "Activate voxels and render" step: 976,276 ns [S1].
    *   Other steps (Advect, Jacobi, etc.) are significantly faster, ranging from 855 ns to 34,637 ns [S1].
*   **GPU-Only Approach (GT540M, $64^3$ chunk):**
    *   Total FPS: 180 FPS (5.556 ms frame time) [S1].
    *   Performance improvement: Up to 1100 FPS observed in optimized scenarios compared to 30 FPS for the original method on similar hardware/configurations [S1].
*   **Scaling (GTX 950M, CPU Approach):**
    *   $32^3$ (32,768 blocks): 401 FPS (2.494 ms) [S1].
    *   $64^3$ (262,144 blocks): 100 FPS (10.000 ms) [S1].
    *   $96^3$ (884,736 blocks): 20 FPS (50.000 ms) [S1].
    *   $128^3$ (2,097,152 blocks): 14 FPS (71.429 ms) [S1].

**Strengths and Limitations:**
*   **Strengths:** The GPU-only optimization eliminates the CPU-GPU bottleneck, resulting in massive performance gains (from 30 FPS to 1100 FPS in reported improvements) [S1]. Deterministic ordering of primitives is guaranteed via stream-out [S1].
*   **Limitations:** No obstacle detection or response is implemented [S1]. Limited to single-chunk simulations in the base description [S1].

**When to Use:**
Use this method when real-time fluid visualization is required within a voxel engine and CPU-GPU synchronization is a bottleneck. It is suitable for water, smoke, and fire effects in game environments [S1].

## Background
This method was proposed to address the hurdles of integrating GPU-accelerated fluid simulation with voxel-based rendering efficiently [S1]. It builds on recent results in GPU-accelerated fluid simulation (Crane et al. 2007 and Harris 2004) and voxel-based rendering (Miller et al. 2014) [S1]. The fluid simulation is based on the Navier-Stokes differential equations (Stam 2003) [S1]. The voxel rendering engine used is Poxels (Miller et al. 2014) [S1]. The paper was published in the *Computational Games Journal* in 2016 [S1].
