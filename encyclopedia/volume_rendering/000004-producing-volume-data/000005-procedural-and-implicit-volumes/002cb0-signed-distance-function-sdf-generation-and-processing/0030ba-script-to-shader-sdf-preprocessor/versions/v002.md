# Script-to-Shader SDF Preprocessor

Also called: SDF Script Compiler, loadTxtFragFile

## Overview
The Script-to-Shader SDF Preprocessor is a C++ utility that parses a custom high-level script language to automatically generate GLSL code for Signed Distance Function (SDF) scene composition [S1, unofficial]. It solves the problem of manually writing verbose, error-prone GLSL for complex boolean operations and material assignments by translating declarative script commands into optimized shader functions [S1, unofficial]. It distinguishes itself from sibling methods like [Constrained Jacobi Smoothing](1583-constrained-jacobi-smoothing-for-sdfs.md) by focusing on procedural scene definition and code generation rather than post-processing existing grid data, and from [SDF Volume Generation & Ping-Pong Buffering](4570-sdf-volume-generation-ping-pong-buffering.md) by operating at the shader source level rather than the voxel data level.

## How it works
**Inputs and Outputs:**
*   **Input:** A "dummy" fragment shader file (`realCode`) containing placeholder markers, and a custom script file (`psCode`) defining the scene geometry, materials, and lights.
*   **Output:** A complete, valid GLSL fragment shader string (`realCode`) with all placeholders replaced by generated SDF evaluation code.

**Data Structures:**
The implementation relies on string manipulation and lambda functions within a C++ context. No complex binary data structures are defined; the core state is managed via string indices and parsed parameters.

**Steps:**
1.  **Load Files:** Read the dummy fragment shader into a mutable string `realCode` and the script file into `psCode` [S1, unofficial].
2.  **Environment Setup (`setUpEnv`):** Define a lambda function `setUpEnv(envName)` that performs the following:
    *   Searches `realCode` for the marker `!(envName)` [S1, unofficial].
    *   Scans `psCode` for the corresponding section marker `#envName` [S1, unofficial].
    *   Extracts the content between the opening `{` and closing `}` of that section in `psCode` [S1, unofficial].
    *   Inserts this extracted content into `realCode` at the location of `!(envName)` [S1, unofficial].
    *   If `envName` is `"light"`, increments a global or local counter `lightCnt` [S1, unofficial].
    *   Call `setUpEnv("material")` and `setUpEnv("light")` to populate material and lighting definitions [S1, unofficial].
3.  **Locate Insertion Point:** Find the marker `!(sceneSDF)` in `realCode`. This index serves as the insertion point for the generated SDF logic [S1, unofficial].
4.  **Function Parser (`findFunc`):** Define a lambda `findFunc` to parse SDF operations. It scans `psCode` for `#` markers indicating function definitions [S1, unofficial]. It handles the following operations:
    *   `opU`: Union.
    *   `opS`: Subtraction.
    *   `opI`: Intersection.
    *   `opUs`: Smooth Union, which requires a smoothness parameter `k` [S1, unofficial].
    *   The parser converts these script commands into GLSL function calls [S1, unofficial].
5.  **Main Generation Loop:** Iterate through `psCode` scanning for specific control markers:
    *   `@i`: Generates `for` loop structures in GLSL [S1, unofficial].
    *   `#`: Triggers function definition parsing via `findFunc` [S1, unofficial].
    *   `!`: Inserts raw lines directly into the output [S1, unofficial].
6.  **Insertion:** Insert the generated code block at the `!(sceneSDF)` position in `realCode` [S1, unofficial].
7.  **Return:** Return the modified `realCode` string [S1, unofficial].

**Formulas:**
The smooth union operation `opUs` uses the following formula [S1, unofficial]:
$$ f = \min(a, b) - k \cdot \max(0, \min(a, b)) $$
Where:
*   $a$ and $b$ are the signed distances of the two primitives.
*   $k$ is the smoothness parameter.

**Parameters:**
*   `k`: A float representing the smoothness for `opUs`. It is parsed from the script using `sscanf(..., "#k%f", &k)` [S1, unofficial].
*   `prefix`: A string defining the directory prefix for shader files, formatted as `shaders/%s/%s.glsl` [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Marker Conflict:** The script parser uses fixed string markers (`@i`, `#`, `!`) which can conflict with standard GLSL syntax if not carefully escaped or structured [S1, unofficial].
*   **Sub-function Parsing:** The `findSubFunc` lambda (referenced in the source code snippet but not fully detailed in the steps) assumes specific marker formats (`m` for matrix, `v` for vector) and may break if the script deviates from these expectations [S1, unofficial].
*   **Nested Parentheses:** The argument splitting logic must correctly handle nested function calls (e.g., `opU(opS(a,b), c)`) to avoid misidentifying argument boundaries.

## Subtopics

### SDF to Density Conversion
Converts the scalar SDF field into a volumetric density field for ray marching. Choose this when you need to render the SDF as a volume rather than a surface. [SDF to Density Conversion](1282-sdf-to-density-conversion.md)

### Constrained Jacobi Smoothing for SDFs
Smooths the SDF field while preserving the distance property and topology. Choose this when the generated SDF has artifacts or non-unit gradients that need correction. [Constrained Jacobi Smoothing for SDFs](1583-constrained-jacobi-smoothing-for-sdfs.md)

### SDF Volume Generation & Ping-Pong Buffering
Generates SDF data on a grid using iterative methods with ping-pong buffers. Choose this when you need a discrete voxel representation of the SDF rather than a procedural shader. [SDF Volume Generation & Ping-Pong Buffering](4570-sdf-volume-generation-ping-pong-buffering.md)

## Operating characteristics
*   **Time Complexity:** Linear with respect to the size of the script file `psCode` and the number of operations, as it involves a single pass string parsing and replacement [S1, unofficial].
*   **Memory Complexity:** Linear with respect to the size of the generated GLSL code, which depends on the complexity of the scene defined in the script [S1, unofficial].
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Scales with the complexity of the boolean operations and the number of materials/lights defined in the script.
*   **Strengths:** Automates the generation of complex SDF compositions, reducing manual coding errors and improving maintainability of scene definitions [S1, unofficial].
*   **Limitations:** Relies on a custom script syntax that must be carefully managed to avoid conflicts with GLSL. The parser is rigid and may break with non-standard script formats [S1, unofficial].
*   **When to use:** When defining complex SDF scenes procedurally in GLSL and wanting to abstract the boolean logic into a higher-level script.
*   **When not to use:** When the scene is static and simple enough to write directly in GLSL, or when a discrete voxel representation is required.

## Background
The Script-to-Shader SDF Preprocessor originates from the `trimesh33/sdf` repository, an unofficial project [S1, unofficial]. It was developed to facilitate the creation of complex SDF scenes in GLSL by providing a script-based interface for composition. The method is part of a broader effort to simplify SDF rendering pipelines by separating scene definition from shader implementation.
