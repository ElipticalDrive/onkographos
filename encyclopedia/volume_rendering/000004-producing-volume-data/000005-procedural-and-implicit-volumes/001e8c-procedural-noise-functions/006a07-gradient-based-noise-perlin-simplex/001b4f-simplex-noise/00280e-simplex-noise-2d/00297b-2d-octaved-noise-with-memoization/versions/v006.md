# 2D Octaved Noise with Memoization

Also called: Multi-octave noise, Octave Noise, Fractal Noise with Caching

## Overview
2D Octaved Noise with Memoization generates complex, self-similar noise patterns by summing multiple layers (octaves) of a base 2D gradient noise function, such as Simplex Noise 2D, with decreasing amplitude and increasing frequency. It solves the problem of repetitive or computationally expensive procedural texture generation by caching previously computed noise values for specific coordinate-octave combinations. Unlike standard octave noise which recomputes base noise for every sample, this method uses a cache to avoid redundant calculations, significantly improving performance for static or slowly varying scenes.

## How it works
**Inputs:**
- Base coordinates $(x, y)$ in 2D space.
- Number of octaves $n_{octaves}$.
- Base amplitude $A_0$ and persistence factor $p$ (amplitude decay).
- Lacunarity $L$ (frequency multiplication factor).
- Scale $S$ (spatial frequency divisor).
- Cache data structure mapping keys to noise values.

**Outputs:**
- A single scalar noise value $N(x, y)$ in a normalized range (typically $[-1, 1]$ or $[0, 1]$ depending on post-processing).

**Data Structures:**
- **Cache:** A hash map or dictionary mapping a composite key to a floating-point value.
  - Key format: A string or tuple representing the quantized input coordinates and octave count. For integer grid-based implementations, the key is often derived from the integer grid cell indices. For continuous implementations, the key may involve quantized floating-point coordinates or the specific octave index if the base noise is cached per-octave.
  - Value: The computed noise result for that key.
- **Noise Grid (for grid-based variants):** A 1D array `std::vector<float>` or similar, accessed via helper functions `get(x, y)` and `set(x, y)` which map 2D coordinates to 1D indices using $index = x \cdot width + y$ [S2, unofficial].

**Parameters:**
- $S$ (Scale): Controls the spatial frequency of the base noise. Default: $0.0001$. Must be $> 0$ [S4, unofficial].
- $p$ (Persistence): Amplitude decay factor per octave. Default: $0.5$ [S4, unofficial].
- $L$ (Lacunarity): Frequency multiplication factor per octave. Default: $2.0$ [S4, unofficial].
- $n_{octaves}$: Number of layers to sum.

**Algorithm Steps:**

1.  **Key Generation:** Create a unique cache key for the current request. If the implementation caches per-octave base noise, the key includes the octave index $o$. If it caches the final summed result, the key includes $x, y, n_{octaves}$ [S3, unofficial].
    - Example key construction: `key = f"{x},{y},{n_octaves}"` [S3, unofficial].

2.  **Cache Check:** Look up `key` in the cache.
    - If found, return the cached value immediately [S3, unofficial].

3.  **Initialization:**
    - Initialize `total_amplitude = 0.0`.
    - Initialize `result = 0.0`.
    - Initialize `current_amplitude = A_0`.
    - Initialize `current_frequency = 1.0 / S` [S4, unofficial].

4.  **Octave Loop:** Iterate $o$ from $0$ to $n_{octaves} - 1$:
    a.  **Coordinate Scaling:** Calculate the scaled coordinates for the current octave.
        $$ sx = \frac{x \cdot current\_frequency}{S} $$
        $$ sy = \frac{y \cdot current\_frequency}{S} $$
        *Note: Some implementations add an octave offset to prevent alignment artifacts [S4, unofficial].*
        $$ sx = \frac{(x + offset_x) \cdot current\_frequency}{S} $$
        $$ sy = \frac{(y + offset_y) \cdot current\_frequency}{S} $$
    b.  **Base Noise Evaluation:** Compute the base noise value $N_o$ at $(sx, sy)$ using the underlying Simplex Noise 2D function.
        - If the base noise function is also cached, use its cache.
        - If using a grid-based approach with bilinear interpolation:
            1.  Determine the grid period $P = 2^o$ (or derived from scale) [S2, unofficial].
            2.  Identify the four surrounding grid points: $(x_0, y_0), (x_1, y_0), (x_0, y_1), (x_1, y_1)$ using modulo arithmetic with the grid dimensions [S2, unofficial].
            3.  Perform bilinear interpolation:
                - Interpolate horizontally between top-left and top-right.
                - Interpolate horizontally between bottom-left and bottom-right.
                - Interpolate vertically between the two horizontal results [S2, unofficial].
    c.  **Accumulation:**
        - Add the weighted noise to the result:
          $$ result += N_o \cdot current\_amplitude $$
        - Add the current amplitude to the total amplitude tracker:
          $$ total\_amplitude += current\_amplitude $$
    d.  **Update for Next Octave:**
        - Update amplitude: $current\_amplitude = current\_amplitude \cdot p$ [S4, unofficial].
        - Update frequency: $current\_frequency = current\_frequency \cdot L$ [S4, unofficial].

5.  **Normalization:**
    - Normalize the result by the total accumulated amplitude to ensure consistent output range regardless of the number of octaves:
      $$ final\_result = \frac{result}{total\_amplitude} $$
    - *Note: Some implementations may apply additional rescaling to $[0, 1]$ or $[-1, 1]$ using linear interpolation [S4, unofficial].*

6.  **Cache Storage:** Store `final_result` in the cache under `key` [S3, unofficial].

7.  **Return:** Return `final_result`.

**Pseudocode:**

```python
def generate_octaved_noise(x, y, n_octaves, scale, persistence, lacunarity, cache):
    """
    Generates 2D octaved noise with memoization.
    
    Args:
        x, y: Input coordinates.
        n_octaves: Number of octaves to sum.
        scale: Spatial scale factor.
        persistence: Amplitude decay factor.
        lacunarity: Frequency multiplication factor.
        cache: Dictionary mapping keys to noise values.
        
    Returns:
        Normalized noise value.
    """
    # 1. Key Generation
    # Quantize coordinates if necessary for cache efficiency, or use exact floats
    # Key includes octave count if caching final result, or just coords if caching base noise
    key = f"{x},{y},{n_octaves}"
    
    # 2. Cache Check
    if key in cache:
        return cache[key]
    
    # 3. Initialization
    total_amplitude = 0.0
    result = 0.0
    current_amplitude = 1.0
    current_frequency = 1.0 / scale
    
    # 4. Octave Loop
    for o in range(n_octaves):
        # a. Coordinate Scaling
        # Using scale directly as divisor for frequency
        sx = x * current_frequency
        sy = y * current_frequency
        
        # b. Base Noise Evaluation
        # Call the underlying Simplex Noise 2D function
        # This function itself may have internal caching or grid interpolation
        noise_value = simplex_noise_2d(sx, sy)
        
        # c. Accumulation
        result += noise_value * current_amplitude
        total_amplitude += current_amplitude
        
        # d. Update for Next Octave
        current_amplitude *= persistence
        current_frequency *= lacunarity
        
    # 5. Normalization
    if total_amplitude == 0:
        final_result = 0.0
    else:
        final_result = result / total_amplitude
        
    # 6. Cache Storage
    cache[key] = final_result
    
    # 7. Return
    return final_result
```

**Edge Cases and Pitfalls:**
- **Division by Zero:** Scale must be strictly greater than zero. If $S=0$, coordinate scaling causes division by zero [S4, unofficial].
- **Negative Weights:** Negative weights cannot cancel energy from a frequency band because noise has random phase. To produce a spectrum with no energy at some frequencies, the primitive noise function must be band-pass rather than merely band-limited [S1].
- **Cache Memory:** Caching every unique coordinate pair can lead to high memory usage. Quantization or limiting cache size may be necessary for large terrains [S3, unofficial].
- **Precision:** Floating-point precision issues may arise with very large coordinates or very small scales. Using integer-based grid coordinates for caching keys can mitigate this [S2, unofficial].

## Subtopics

### Normalized Octave Noise
Scales the octave noise result by the maximum possible amplitude to ensure the output range is consistent regardless of the number of octaves or persistence value. The formula is $result = octave3D(x, y, z, octaves, persistence) / MaxAmplitude(octaves, persistence)$, where $MaxAmplitude$ calculates the sum of amplitudes for the given parameters [S5, unofficial]. This variant is useful when a fixed output range is required independent of the fractal dimension settings.

## Operating characteristics
- **Time Complexity:** $O(n_{octaves})$ per unique coordinate query. With memoization, repeated queries for the same coordinates are $O(1)$.
- **Memory Complexity:** $O(N)$ where $N$ is the number of unique cached coordinate-octave combinations.
- **Performance:** Significantly faster than non-cached octave noise for static scenes or repeated sampling of the same regions. Performance degrades if the cache misses frequently due to high variability in input coordinates.
- **Strengths:** Consistent output range (with normalization), efficient for repeated queries, smooth transitions between octaves.
- **Limitations:** High memory usage for large caches, potential cache thrashing in dynamic scenes.
- **When to Use:** Static terrain generation, procedural texture baking, scenes where noise values are sampled repeatedly.
- **When Not to Use:** Highly dynamic scenes with unique coordinates every frame, memory-constrained environments.

## Background
The concept of summing octaves of noise was introduced by Ken Perlin in 1985 [S1]. The technique was later popularized in tools like the "Perlin Noise" implementation in various graphics libraries. The specific combination with memoization is a practical optimization for real-time applications, as seen in various voxel engine implementations [S2, S3, S4, unofficial]. Goldberg et al. [GZD08] used weighted octave noise to cancel mapping distortions and adapt noise to viewing conditions.
