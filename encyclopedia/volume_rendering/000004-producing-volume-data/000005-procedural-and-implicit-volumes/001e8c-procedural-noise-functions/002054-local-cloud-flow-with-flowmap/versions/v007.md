# Local Cloud Flow with FlowMap

Also called: FlowMap Cloud Movement, Noise Texture Flow Offset

## Overview
Local Cloud Flow with FlowMap simulates localized, non-uniform cloud movement (e.g., swirls) by perturbing noise texture sampling coordinates using a pre-computed FlowMap texture [S1, unofficial]. Unlike Global Cloud Flow, which applies uniform vector offsets for large-scale wind, this method uses per-pixel texture lookups to define complex, spatially varying flow directions and speeds [S1, unofficial]. It mitigates the visual artifact of noise texture stretching caused by divergent flow fields by temporally interpolating between two phase-shifted noise samples [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** World space position $\mathbf{P}_{world}$, time $t$, Shape Noise texture $N_{shape}$, and a FlowMap texture $F$ [S1, unofficial].
*   **Output:** Perturbed noise value for volume density calculation [S1, unofficial].

**Data Structures:**
*   **FlowMap ($F$):** A 2D texture storing 3D flow direction vectors [S1, unofficial]. Typically stored in RGB channels, where each component represents the X, Y, and Z components of the flow vector at that UV coordinate [G]. The vector should be normalized or treated as a directional offset [G].

**Steps:**
1.  **UV Coordinate Calculation:** Compute 2D UV coordinates from the world space horizontal components of the query point [S1, unofficial].
    $$ u = P_{world}.x $$
    $$ v = P_{world}.z $$
    [G] In practice, these coordinates may be scaled or offset to match the FlowMap's tiling, but the source specifies direct XZ mapping [S1, unofficial].

2.  **Flow Direction Sampling:** Sample the FlowMap at $(u, v)$ to retrieve the local flow direction vector $\mathbf{d}$ [S1, unofficial].
    $$ \mathbf{d} = F(u, v) $$
    [G] $\mathbf{d}$ is a 3D vector $(d_x, d_y, d_z)$.

3.  **Temporal Phase Calculation:** To prevent severe stretching of noise features over time due to varying flow speeds, calculate two time phases using the fractional part of time [S1, unofficial].
    $$ t_1 = \text{fract}(t) $$
    $$ t_2 = \text{fract}(t + 0.5) $$
    [G] $\text{fract}(x) = x - \lfloor x \rfloor$. The offset of 0.5 represents a "half-beat" phase shift [S1, unofficial].

4.  **Noise Coordinate Perturbation:** Calculate two perturbed sampling coordinates for the noise texture [S1, unofficial]. The flow vector $\mathbf{d}$ is scaled by the time phases to create the offset [G].
    $$ \mathbf{P}_1 = \mathbf{P}_{world} + t_1 \cdot \mathbf{d} $$
    $$ \mathbf{P}_2 = \mathbf{P}_{world} + t_2 \cdot \mathbf{d} $$
    [G] The source implies the flow vector acts as a velocity or displacement rate. The Y component of $\mathbf{d}$ controls vertical rolling, affecting the overall distribution of clouds over time [S1, unofficial].

5.  **Noise Sampling:** Sample the Shape Noise texture at both perturbed coordinates [S1, unofficial].
    $$ n_1 = N_{shape}(\mathbf{P}_1) $$
    $$ n_2 = N_{shape}(\mathbf{P}_2) $$
    [G] Only the Shape Noise texture is typically perturbed this way to save performance; other noise textures (e.g., detail noise) remain unperturbed [S1, unofficial].

6.  **Interpolation:** Interpolate between the two noise samples to produce the final flowed noise value [S1, unofficial].
    $$ n_{final} = \text{lerp}(n_1, n_2, 0.5) $$
    [G] A standard linear interpolation with a weight of 0.5 is implied by the "smooth flow effect" description, though the exact blend factor is not explicitly defined beyond the half-beat offset [S1, unofficial].

**Pseudocode:**
```python
def local_cloud_flow(P_world, t, N_shape, F):
    # 1. UV Coordinate Calculation
    u, v = P_world.x, P_world.z
    
    # 2. Flow Direction Sampling
    d = F(u, v)
    
    # 3. Temporal Phase Calculation
    t1 = fract(t)
    t2 = fract(t + 0.5)
    
    # 4. Noise Coordinate Perturbation
    P1 = P_world + t1 * d
    P2 = P_world + t2 * d
    
    # 5. Noise Sampling
    n1 = N_shape(P1)
    n2 = N_shape(P2)
    
    # 6. Interpolation
    return lerp(n1, n2, 0.5)
```

**Pitfalls:**
*   **Stretching:** Without the `fract(time)` technique, noise textures will stretch severely over time because flow directions and speeds vary across the texture [S1, unofficial].
*   **Performance:** Applying FlowMap sampling and double noise evaluation to all noise textures is expensive [S1, unofficial]. It is recommended to apply this only to the Shape Noise texture [S1, unofficial].

## Subtopics

### [Global Cloud Flow](2270-global-cloud-flow.md)
Simulates global cloud movement by offsetting noise texture sampling coordinates over time using two global wind speeds. It differs from Local Cloud Flow with FlowMap by applying uniform vector offsets instead of per-pixel texture lookups. Choose when large-scale, coherent wind patterns are needed without local turbulence.

### [Noise Texture Advection](10551-noise-texture-advection.md)
A GPU-based technique for visualizing tensor fields by iteratively advecting a noise texture along eigenvector directions using simple Euler integration. It solves the problem of generating coherent flow-like structures from static tensor data without calculating streamlines at each position. Choose when visualizing complex vector/tensor fields with edge detection, rather than simple procedural cloud flow.

### [Wind-driven Particle Advection](21066-wind-driven-particle-advection.md)
Displaces volumetric particles (voxels) through a static 3D wind vector field to simulate local cloud movement, such as swirls, by sampling the wind based on the particle's normalized position within the volume bounds. It differs from Global Cloud Flow by using a localized, discrete grid-based wind field rather than a global flow, and from Noise Texture Advection by explicitly tracking particle positions against a vector field rather than advecting noise coordinates. Choose when discrete particle-based simulation is preferred over continuous noise advection.

## Operating characteristics
*   **Time Complexity:** $O(1)$ per sample, but effectively doubles the cost of Shape Noise evaluation due to the two-phase sampling and interpolation [S1, unofficial].
*   **Memory Complexity:** Requires storage for the FlowMap texture [S1, unofficial].
*   **Strengths:** Allows for complex, localized flow patterns (swirls) that global vectors cannot achieve [S1, unofficial]. Simple to implement [G].
*   **Limitations:** Computationally expensive if applied to all noise layers [S1, unofficial]. Requires `fract(time)` to prevent severe stretching [S1, unofficial].
*   **When to use:** When local turbulence or swirling cloud structures are desired [S1, unofficial].
*   **When not to use:** When performance is critical and global wind is sufficient, or when detail noise also requires flow (which is usually skipped for performance) [S1, unofficial].

## Background
This method is described in the context of volumetric cloud rendering in games, specifically referencing implementations seen in titles like *Red Dead Redemption 2* (though RDR2 is cited for a different technique regarding cloud distribution, the FlowMap concept is discussed in the same article) and general industry practices for volume clouds [S1, unofficial]. The article also notes industry practices such as using 2D Cloud Maps with multiple channels for different cloud distributions interpolated by time of day [S1, unofficial].
