# Improved Perlin Noise (4D)

Also called: 4D Perlin Noise

## Overview
Improved Perlin Noise (4D) is a procedural noise function that generates smooth, continuous random values in four dimensions by interpolating dot products of gradient vectors at the corners of a 4D hypercube [S1, S2, unofficial]. It extends the 3D Improved Perlin Noise method to support time-varying texture generation and volumetric animation by treating the fourth dimension as time or an additional spatial axis [S1, S2, unofficial]. Unlike the original Perlin noise which used cubic interpolation, this variant employs a quintic fade function to eliminate directional artifacts and ensure C2 continuity [S1, S2, unofficial]. It is distinct from Simplex Noise in that it retains the orthogonal grid structure but optimizes the permutation lookup for GPU execution using texture-based tables [S2, unofficial].

## How it works
### Inputs and Outputs
- **Input:** A 4D query point $P = (x, y, z, w)$, typically representing spatial coordinates $(x, y, z)$ and time $(w)$, or four spatial dimensions.
- **Output:** A scalar noise value $V \in [-1, 1]$ (for standard fBm) or $[0, 1]$ (for turbulence/ridged multifractal).

### Data Structures
The implementation relies on precomputed lookup tables stored in 2D textures to optimize GPU sampling and avoid branching [S1, S2, unofficial].

1.  **Permutation Table 1D (`_PermTable1D`)**:
    -   Format: `Texture2D` of size $256 \times 1$.
    -   Layout: Stores 256 permutation indices in the Alpha channel. The Red, Green, and Blue channels are unused or zero.
    -   Access: Sampled at `float2(x, 0)` where $x$ is the integer coordinate index [S1, S2, unofficial].

2.  **Permutation Table 2D (`_PermTable2D`)**:
    -   Format: `Texture2D` of size $256 \times 256$.
    -   Layout: Stores precomputed 2D permutation sums in RGBA channels. Each texel at $(u, v)$ contains:
        -   $R = \text{perm}(\text{perm}(u) + v)$
        -   $G = \text{perm}(\text{perm}(u) + v + 1)$
        -   $B = \text{perm}(\text{perm}(u + 1) + v)$
        -   $A = \text{perm}(\text{perm}(u + 1) + v + 1)$
    -   Purpose: Accelerates the hashing of 2D coordinates by combining two 1D permutation lookups into one texture fetch [S1, S2, unofficial].

3.  **Gradient Table 4D (`_Gradient4D`)**:
    -   Format: `Texture2D` of size $32 \times 1$ (or similar small width, height 1).
    -   Layout: Stores 32 gradient vectors in RGBA channels. Each texel contains one 4D gradient vector $(g_x, g_y, g_z, g_w)$.
    -   Values: Gradient vectors are normalized or scaled to fit within $[0, 1]$ in the texture, then mapped to $[-1, 1]$ during sampling [S1, S2, unofficial].
    -   Note: The specific set of 32 gradients is not explicitly listed in the sources, but they are standard unit vectors or permutations thereof typical for Perlin noise [S1, S2, unofficial].

### Parameters
-   `_Frequency`: Scaling factor for the input coordinate. Default: $1.0$ or $0.02$ depending on context (e.g., marching cubes scale) [S1, S2, unofficial].
-   `_Lacunarity`: Multiplier for frequency between octaves. Default: $2.0$ [S1, S2, unofficial].
-   `_Gain`: Multiplier for amplitude between octaves. Default: $0.5$ [S1, S2, unofficial].
-   `_NoiseStyle`: Selector for fractal combination method (0=fBm, 1=Turbulence, 2=Ridged Multifractal) [S1, S2, unofficial].
-   `_Time`: Optional uniform for the $w$ coordinate in time-varying noise [S1, S2, unofficial].

### Algorithm Steps

1.  **Grid Localization**:
    Compute the integer coordinates of the unit hypercube containing $P$ and the relative position within that hypercube.
    $$ P_{int} = \text{fmod}(\lfloor P \rfloor, 256.0) $$
    $$ P_{frac} = P - \lfloor P \rfloor $$
    The modulo 256 ensures indices fit within the permutation table size [S1, S2, unofficial].

2.  **Fade Curve Calculation**:
    Compute the quintic fade function for each component of $P_{frac}$ to ensure smooth derivatives.
    $$ f(t) = 6t^5 - 15t^4 + 10t^3 $$
    Applied component-wise: $F = \text{fade}(P_{frac})$ [S1, S2, unofficial].

3.  **Hashing Corners**:
    Map the 16 corners of the 4D hypercube to gradient indices using the permutation tables.
    -   Normalize integer coordinates for texture lookup: $P_{norm} = P_{int} / 256.0$.
    -   Compute base 2D hash: $AA = \text{perm2d}(P_{norm}.xy) + P_{norm}.z$.
    -   Compute 1D hashes for the 16 corners by adding the $w$ component ($P_{norm}.w$) and incrementing $x, y, z, w$ by $1/256.0$ (represented as `one`) where appropriate.
    
    Let $one = 1.0 / 256.0$. The 16 corner indices are:
    -   $AAA = \text{perm}(AA.x) + P_{norm}.w$
    -   $AAB = \text{perm}(AA.x + one) + P_{norm}.w$
    -   $ABA = \text{perm}(AA.y) + P_{norm}.w$
    -   $ABB = \text{perm}(AA.y + one) + P_{norm}.w$
    -   $BAA = \text{perm}(AA.z) + P_{norm}.w$
    -   $BAB = \text{perm}(AA.z + one) + P_{norm}.w$
    -   $BBA = \text{perm}(AA.w) + P_{norm}.w$
    -   $BBB = \text{perm}(AA.w + one) + P_{norm}.w$
    
    And the same set incremented by `one` in the final permutation lookup (representing the $+1$ offset in the $x$ dimension of the permutation table, effectively covering the 16 corners of the hypercube in the hash space) [S1, S2, unofficial].
    
    *Correction based on code*: The code shows `perm(AA.x)+P.w` and `perm(AA.x+one)+P.w`. The `perm` function samples `_PermTable1D`. The `perm2d` function samples `_PermTable2D`. The indices `AA.x`, `AA.y`, etc., are the results of the 2D permutation lookup. The `+ P.w` adds the time/space dimension offset. The `+ one` inside the `perm` call increments the index for the next cell in the permutation table. The 16 corners correspond to the combinations of $\pm 1$ offsets in $x, y, z, w$ relative to the base corner $(0,0,0,0)$ of the hypercube. The code explicitly lists 16 `gradperm` calls with offsets like `float4(-1, 0, 0, 0)` etc. [S1, S2, unofficial].

4.  **Gradient Evaluation**:
    For each corner index $I$, retrieve the gradient vector $G$ and compute the dot product with the relative position vector from the corner to the query point.
    $$ G = (\text{Sample}(\text{\_Gradient4D}, I) \times 2.0 - 1.0) $$
    $$ \text{Contribution} = \text{dot}(G, P_{frac} - C) $$
    where $C$ is the corner coordinate offset (e.g., $(0,0,0,0), (1,0,0,0), \dots$) [S1, S2, unofficial].

5.  **Interpolation**:
    Interpolate the 16 gradient contributions using the fade values $F = (f_x, f_y, f_z, f_w)$ via nested linear interpolations (lerp) along the $x, y, z, w$ axes.
    $$ V = \text{lerp}_w( \text{lerp}_z( \text{lerp}_y( \text{lerp}_x( \text{Corner}_{0000}, \text{Corner}_{1000}, f_x), \dots ), \dots ), f_w ) $$

    """Quintic fade function."""
    return t * t * t * (t * (t * 6 - 15) + 10)

def perm(x):
    """Lookup 1D permutation from texture."""
    # Assumes _PermTable1D is a texture2D with permutation in alpha channel
    return _PermTable1D.sample(x, 0).a

def perm2d(uv):
    """Lookup 2D permutation from texture."""
    # Assumes _PermTable2D is a texture2D with precomputed 2D perms in RGBA
    return _PermTable2D.sample(uv, 0)

def fBm(p, octaves):
    """Fractal Brownian Motion."""
    freq = _Frequency
    amp = 0.5
    sum_val = 0.0
    for i in range(octaves):
        sum_val += inoise(p * freq) * amp
        freq *= _Lacunarity
        amp *= _Gain
    return sum_val

### Edge Cases and Pitfalls
-   **Gradient Normalization**: Gradient vectors must be normalized or scaled appropriately to ensure consistent noise amplitude across the range $[-1, 1]$ [S2, unofficial].
-   **Precision**: Using `fmod` with large coordinates can lead to precision loss. It is recommended to keep input coordinates within a reasonable range or use periodic hashing [S1, S2, unofficial].
-   **Boundary Conditions**: The modulo 256 operation ensures periodicity, but discontinuities can occur if the permutation table is not correctly sized or if the input coordinates are not handled with floating-point precision [S1, S2, unofficial].

## Operating characteristics
-   **Time Complexity**: $O(1)$ per noise evaluation, with a constant number of texture lookups (16 gradient samples, 2 permutation table lookups) and arithmetic operations.
-   **Memory Complexity**: $O(1)$ for the algorithm state, plus $O(N)$ for the permutation and gradient tables (where $N=256$ for permutation, $N=32$ for gradients).
-   **Performance**: GPU-optimized implementations using texture-based lookups avoid branching and improve performance over traditional array-based lookup [S2, unofficial].
-   **Strengths**: Smooth C2 continuity, no directional artifacts, suitable for time-varying volumetric data.
-   **Limitations**: Higher computational cost than Simplex Noise due to the orthogonal grid and 16-corner interpolation. Not given in the sources: specific FPS metrics.
-   **When to use**: When time-varying noise is required, or when the orthogonal grid structure is preferred for compatibility with existing 3D Perlin noise pipelines.
-   **When not to use**: When performance is critical and Simplex Noise is an acceptable alternative, or when 3D-only noise is sufficient.

## Background
Improved Perlin Noise (4D) is based on Ken Perlin's Improved Noise, which replaced the cubic interpolation of the original Perlin noise with a quintic fade function to reduce directional artifacts [S1, S2, unofficial]. The 4D extension allows for the generation of time-varying textures and volumetric animations by treating the fourth dimension as time [S1, S2, unofficial]. The GPU-based implementation using texture-based permutation and gradient tables was popularized in open-source projects such as "Marching Cubes On The GPU" [S1, S2, unofficial].
