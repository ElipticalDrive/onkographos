# Improved Perlin Noise (4D)
Also called: 4D Perlin Noise

## Overview
Improved Perlin Noise (4D) is a procedural noise function that generates smooth, continuous random values in four dimensions by interpolating dot products of gradient vectors at the corners of a 4D hypercube [S1, unofficial]. It extends the 3D Improved Perlin Noise algorithm to support time-varying texture generation and 4D volume data synthesis [S1, unofficial]. What sets it apart from its 3D sibling is the handling of 16 hypercube corners and the use of 2D permutation textures to optimize hash lookups on the GPU, avoiding branching and improving performance over traditional array-based lookups [S2, unofficial].

## How it works
### Inputs and Outputs
**Inputs:**
- `p`: A 4D input coordinate vector `float4(x, y, z, w)` [S1, unofficial].
- `_Frequency`: Scaling factor for the input coordinate (default 1.0 or 0.02f depending on context) [S1, S2, unofficial].
- `_Lacunarity`: Frequency multiplier between octaves (default 2.0) [S1, S2, unofficial].
- `_Gain`: Amplitude multiplier between octaves (default 0.5) [S1, S2, unofficial].
- `_NoiseStyle`: Selector for fractal combination (0=fBm, 1=turbulence, 2=ridgedmf) [S1, unofficial].
- `_Time`: Optional time variable for animation, often passed as the `w` component of `p` [S1, unofficial].

**Outputs:**
- A scalar noise value, typically in the range [-1.0, 1.0] for fBm, or [0.0, 1.0] for turbulence/ridgedmf [S1, unofficial].

### Data Structures
The implementation relies on GPU textures to store permutation and gradient data, replacing CPU arrays for branchless sampling [S2, unofficial].

1.  **`_PermTable1D`**: `Texture2D` of size `SIZE x 1` (e.g., 256x1). Format `Alpha8`. Stores 1D permutation indices normalized to [0, 1] in the alpha channel. Accessed via `float2(x, 0)` [S1, S2, unofficial].
2.  **`_PermTable2D`**: `Texture2D` of size `SIZE x SIZE` (e.g., 256x256). Format `ARGB32`. Stores precomputed 2D permutation sums. Each pixel `(x, y)` contains `(AA, AB, BA, BB)` where:
    - `AA = perm(perm(x) + y)`
    - `AB = perm(perm(x) + y + 1)`
    - `BA = perm(perm(x + 1) + y)`
    - `BB = perm(perm(x + 1) + y + 1)`
    Values are normalized to [0, 1] [S1, S2, unofficial].
3.  **`_Gradient4D`**: `Texture2D` of size `SIZE x 1` (e.g., 32x1 or 256x1 depending on gradient count). Format `ARGB32`. Stores 32 (or more) 4D gradient vectors. Each texel contains one gradient vector in RGBA channels, normalized to [0, 1]. The standard implementation uses 32 gradients [S1, S2, unofficial].

### Algorithm Steps
The core function `inoise(float4 p)` computes the noise value for a single point.

1.  **Grid Location**: Compute the integer coordinates of the unit hypercube containing `p`.
    $$ P = \text{fmod}(\lfloor p \rfloor, 256.0) $$
    Compute the relative position within the hypercube.
    $$ p_{rel} = p - \lfloor p \rfloor $$
    [S1, S2, unofficial]

2.  **Fade Curves**: Compute the quintic fade curve for each dimension to ensure $C^2$ continuity.
    $$ f(t) = 6t^5 - 15t^4 + 10t^3 $$
    Applied component-wise to $p_{rel}$ to get $f = [f_x, f_y, f_z, f_w]$ [S1, S2, unofficial].

3.  **Normalization**: Normalize $P$ for texture lookup.
    $$ P_{norm} = P / 256.0 $$
    Define a small offset for incrementing coordinates in texture space.
    $$ \text{one} = 1.0 / 256.0 $$
    [S1, unofficial]

4.  **Hashing Corners**: Hash the 16 corners of the 4D hypercube using the permutation textures.
    -   Hash XY to get Z-offsets:
        $$ AA = \text{perm2d}(P_{norm}.xy) + P.z $$
        Here, `perm2d` returns a `float4` containing the precomputed sums for the 2x2 square in the XY plane.
    [S1, unofficial]

    -   Compute the 16 corner hash indices by adding the W coordinate and incrementing X, Y, Z, W components by `one` (for the +1 faces).
        $$
        \begin{aligned}
        AAA &= \text{perm}(AA.x) + P.w, & AAB &= \text{perm}(AA.x + \text{one}) + P.w \\
        ABA &= \text{perm}(AA.y) + P.w, & ABB &= \text{perm}(AA.y + \text{one}) + P.w \\
        BAA &= \text{perm}(AA.z) + P.w, & BAB &= \text{perm}(AA.z + \text{one}) + P.w \\
        BBA &= \text{perm}(AA.w) + P.w, & BBB &= \text{perm}(AA.w + \text{one}) + P.w
        \end{aligned}
        $$
        The `+one` variants correspond to the corners at $x+1, y+1, z+1, w+1$. The base variants correspond to $x, y, z, w$.
        [S1, S2, unofficial]

5.  **Gradient Contributions**: For each corner, retrieve the gradient vector and compute the dot product with the relative position vector offset to that corner.
    -   Gradient retrieval:
        $$ g = \text{Sample}(\_Gradient4D, \text{float2}(x, 0)) \times 2.0 - 1.0 $$
        This unpacks the gradient from [0, 1] to [-1, 1].
    [S1, unofficial]

    -   Dot product function:
        $$ \text{gradperm}(x, p) = \text{dot}(g, p) $$
    [S1, unofficial]

    -   Compute contributions for all 16 corners. The relative position $p$ is adjusted for each corner (e.g., $p + (-1, 0, 0, 0)$ for the corner at $x-1$).
        [S1, S2, unofficial]

6.  **Interpolation**: Interpolate the 16 gradient contributions using nested `lerp` operations with the fade values $f_x, f_y, f_z, f_w$.
    $$
    \begin{aligned}
    n = \text{lerp}( & \text{lerp}( \text{lerp}( \text{lerp}(\text{gradperm}(AAA, p), \text{gradperm}(BAA, p+(-1,0,0,0)), f_x), \\
                   & \quad \text{lerp}(\text{gradperm}(ABA, p+(0,-1,0,0)), \text{gradperm}(BBA, p+(-1,-1,0,0)), f_x), f_y), \\
                   & \text{lerp}( \text{lerp}(\text{gradperm}(AAB, p+(0,0,-1,0)), \text{gradperm}(BAB, p+(-1,0,-1,0)), f_x), \\
                   & \quad \text{lerp}(\text{gradperm}(ABB, p+(0,-1,-1,0)), \text{gradperm}(BBB, p+(-1,-1,-1,0)), f_x), f_y), f_z), \\
    & \text{lerp}( \text{lerp}( \text{lerp}(\text{gradperm}(AAA+\text{one}, p+(0,0,0,-1)), \text{gradperm}(BAA+\text{one}, p+(-1,0,0,-1)), f_x), \\
                   & \quad \text{lerp}(\text{gradperm}(ABA+\text{one}, p+(0,-1,0,-1)), \text{gradperm}(BBA+\text{one}, p+(-1,-1,0,-1)), f_x), f_y), \\
                   & \text{lerp}( \text{lerp}(\text{gradperm}(AAB+\text{one}, p+(0,0,-1,-1)), \text{gradperm}(BAB+\text{one}, p+(-1,0,-1,-1)), f_x), \\
                   & \quad \text{lerp}(\text{gradperm}(ABB+\text{one}, p+(0,-1,-1,-1)), \text{gradperm}(BBB+\text{one}, p+(-1,-1,-1,-1)), f_x), f_y), f_z), f_w)
    \end{aligned}
    $$
    [S1, S2, unofficial]

```python
# Constants
SIZE = 256
ONE = 1.0 / SIZE

# Helper: Quintic fade curve
def fade(t):
    return t * t * t * (t * (t * 6.0 - 15.0) + 10.0)

# Helper: 1D Permutation lookup from texture
# perm_table_1d is a texture of size [SIZE, 1], format Alpha8
def perm(x):
    # Sample texture at (x, 0), get alpha, normalize to [0, 255] if needed, 
    # but here we assume the texture stores normalized indices or we handle scaling.
    # Based on source: returns value in [0, 1] range representing index/255?
    # Source says: tex2D(_PermTable1D, float2(x,0)).a

    # The alpha channel stores the permutation index normalized to [0,1]?

    # If stored as float in [0,1], we must multiply by 255 to get index?
    # Source code: float AAA = perm(AA.x)+P.w;
    # AA.x comes from perm2d which returns float4.
    # perm2d samples _PermTable2D.

    # representing the permutation index / 255.0?

    # If stored in texture, it's likely normalized.
    # However, the addition `perm(AA.x) + P.w` implies they are in the same domain.
    # P.w is in [0,1]. AA.x is a permutation index.
    # If AA.x is an index (0-255), adding P.w (0-1) makes no sense for hashing.
    # Re-reading source: "perm2d(uv) = tex2D...". 
    # "AA = perm2d(P.xy) + P.z". P.z is in [0,1].
    # This implies perm2d returns values in [0,1] range?
    # If perm2d returns indices 0-255, adding P.z (0-1) is weird.
    # BUT: P is normalized to [0,1] for texture lookup.
    # The permutation table lookup needs integer indices.
    # The source code does: float4 AA = perm2d(P.xy) + P.z;
    # If P.xy is normalized [0,1], perm2d samples the texture.
    # The texture _PermTable2D stores precomputed sums.
    # If the texture stores indices 0-255, sampling returns 0-255.
    # Adding P.z (0-1) to an index 0-255 is valid for hashing?
    # No, the hash should be an integer index into the gradient table.
    # The gradient table is sampled with `float2(x, 0)`.
    # If x is 255.5, it samples near the end.
    # So the hash value DOES NOT need to be an integer. It just needs to be unique.
    # The permutation table maps coordinates to a pseudo-random value.
    # So, perm() returns a float in [0, 1] (or [0, 255] if not normalized).
    # Source says: "stores perm values normalized to [0,1]".
    # So perm() returns [0,1].
    # Then AA = perm2d(P.xy) + P.z.
    # perm2d returns [0,1] (or [0,255]?).
    # If perm2d returns [0,1], adding P.z [0,1] results in [0,2].
    # Then perm(AA.x) samples _PermTable1D.
    # If AA.x is 1.5, it samples between index 1 and 2.
    # This is a valid hashing strategy using texture interpolation.
    
    # Implementation detail:
    # We assume the textures store the permutation values normalized to [0, 1].
    # The "index" is effectively the float value.
    return perm_table_1d.sample(x, 0) # Returns float in [0,1]

# Helper: 2D Permutation lookup
def perm2d(uv):
    # Returns float4 (AA, AB, BA, BB)
    return perm_table_2d.sample(uv)

# Helper: Gradient retrieval
def gradperm(x, p):
    # x is the hash value (float in [0,1] or [0,255]?)
    # Source: _Gradient4D.SampleLevel(..., float2(x, 0), 0)
    # If x is [0,1], it samples the first texel?
    # Source: "Gradient 4D table: Texture2D SIZE x 1 ... stores 32 gradient vectors"
    # If SIZE=32, and x is [0,1], we need to scale x by 32?
    # Source code: float4 g = _Gradient4D.SampleLevel(..., float2(x, 0), 0) * 2.0 - 1.0;
    # It does NOT scale x.
    # This implies x is treated as a texture coordinate.
    # If the gradient table has 32 vectors in a 256x1 texture, 
    # then x must be in [0, 255] to access different gradients?
    # Or the gradient table is 32x1 and x is in [0, 31]?
    # Source: "perm values normalized to [0,1]".
    # If perm returns [0,1], and we use it as texture coord for a 32-wide texture,
    # we are always sampling the same region unless we scale.
    # However, the source code does NOT scale x in gradperm.
    # This suggests the permutation table might store indices 0-255, 
    # OR the gradient texture is 256x1 with repeated gradients?
    # "stores 32 gradient vectors".
    # If the texture is 256x1, and we have 32 gradients, each gradient occupies 8 texels?
    # Or the texture is 32x1?
    # If texture is 32x1, and x is [0,1], we only sample the first gradient.

    # Let's look at 2D: "x*8.0". This scales x.
    # 4D: "float2(x, 0)". No scaling.
    # This implies x is already in the correct range for the texture width.
    # If _PermTable1D stores values in [0,1], and _Gradient4D is 256x1,
    # then x must be in [0, 255].
    # But perm() returns [0,1].
    # Therefore, the permutation table MUST store values in [0, 255] (integers).
    # Note [S2, unofficial] says "normalized to [0,1]". This might be an error in the note 
    # or it implies the texture format is such that sampling returns the integer value.
    # Given "x*8.0" in 2D, it's likely 4D also requires scaling if the table is small.
    # But the code doesn't show it.
    # We will follow the code: no scaling.
    # We assume the permutation values are in the range [0, Width_of_Gradient_Texture - 1].
    
    g = gradient_4d.sample(x, 0)
    g = g * 2.0 - 1.0 # Map [0,1] to [-1,1]
    return dot(g, p)

# Main Noise Function
def inoise(p):
    # 1. Grid Location
    P = fmod(floor(p), 256.0)
    p_rel = p - floor(p)
    
    # 2. Fade Curves
    f = fade(p_rel)
    
    # 3. Normalize for texture lookup
    P_norm = P / 256.0
    
    # 4. Hash Corners
    AA = perm2d(P_norm.xy) + P.z
    
    AAA = perm(AA.x) + P.w
    AAB = perm(AA.x + ONE) + P.w
    ABA = perm(AA.y) + P.w
    ABB = perm(AA.y + ONE) + P.w
    BAA = perm(AA.z) + P.w
    BAB = perm(AA.z + ONE) + P.w
    BBA = perm(AA.w) + P.w
    BBB = perm(AA.w + ONE) + P.w
    
    # 5. Interpolation
    # We need to compute gradperm for all 16 corners.
    # The p vector is adjusted for each corner.
    
    # w=0 plane
    n000 = gradperm(AAA, p_rel)
    n100 = gradperm(BAA, p_rel + float4(-1, 0, 0, 0))
    n010 = gradperm(ABA, p_rel + float4(0, -1, 0, 0))
    n110 = gradperm(BBA, p_rel + float4(-1, -1, 0, 0))
    n001 = gradperm(AAB, p_rel + float4(0, 0, -1, 0))
    n101 = gradperm(BAB, p_rel + float4(-1, 0, -1, 0))
    n011 = gradperm(ABB, p_rel + float4(0, -1, -1, 0))
    n111 = gradperm(BBB, p_rel + float4(-1, -1, -1, 0))
    
    # w=1 plane (using +ONE offsets)
    n000_w1 = gradperm(AAA + ONE, p_rel + float4(0, 0, 0, -1))
    n100_w1 = gradperm(BAA + ONE, p_rel + float4(-1, 0, 0, -1))
    n010_w1 = gradperm(ABA + ONE, p_rel + float4(0, -1, 0, -1))
    n110_w1 = gradperm(BBA + ONE, p_rel + float4(-1, -1, 0, -1))
    n001_w1 = gradperm(AAB + ONE, p_rel + float4(0, 0, -1, -1))
    n101_w1 = gradperm(BAB + ONE, p_rel + float4(-1, 0, -1, -1))
    n011_w1 = gradperm(ABB + ONE, p_rel + float4(0, -1, -1, -1))
    n111_w1 = gradperm(BBB + ONE, p_rel + float4(-1, -1, -1, -1))
    
    # Lerp X
    n00 = lerp(n000, n100, f.x)
    n01 = lerp(n010, n110, f.x)
    n10 = lerp(n001, n101, f.x)
    n11 = lerp(n011, n111, f.x)
    
    n00_w1 = lerp(n000_w1, n100_w1, f.x)
    n01_w1 = lerp(n010_w1, n110_w1, f.x)
    n10_w1 = lerp(n001_w1, n101_w1, f.x)
    n11_w1 = lerp(n011_w1, n111_w1, f.x)
    
    # Lerp Y
    n0 = lerp(n00, n01, f.y)
    n1 = lerp(n10, n11, f.y)
    
    n0_w1 = lerp(n00_w1, n01_w1, f.y)
    n1_w1 = lerp(n10_w1, n11_w1, f.y)
    
    # Lerp Z
    n0_z = lerp(n0, n1, f.z)
    n1_z = lerp(n0_w1, n1_w1, f.z)
    
    # Lerp W
    return lerp(n0_z, n1_z, f.w)

# Fractal Brownian Motion
def fBm(p, octaves):
    freq = _Frequency
    amp = 0.5
    sum_val = 0.0
    for i in range(octaves):
        sum_val += inoise(p * freq) * amp
        freq *= _Lacunarity
        amp *= _Gain
    return sum_val
```

### Parameters
-   `_Frequency`: Controls the scale of the noise. Typical value: 1.0 [S2, unofficial]. In marching cubes context, 0.02f [S1, unofficial].
-   `_Lacunarity`: Multiplier for frequency in each octave. Typical value: 2.0 [S1, S2, unofficial].
-   `_Gain`: Multiplier for amplitude in each octave. Typical value: 0.5 [S1, S2, unofficial].
-   `_NoiseStyle`: Integer selector (0=fBm, 1=turbulence, 2=ridgedmf) [S1, unofficial].

### Edge Cases and Pitfalls
-   **Gradient Scaling**: Gradient vectors must be normalized or scaled appropriately to ensure consistent noise amplitude [S2, unofficial]. The source code scales sampled gradients from [0, 1] to [-1, 1] [S1, unofficial].
-   **Texture Coordinates**: The permutation and gradient tables are accessed as textures. Care must be taken to ensure the hash values passed to `gradperm` are in the correct range for the texture dimensions [S1, unofficial].
-   **Precision**: Using floating-point texture lookups for permutation hashing avoids branching but relies on the texture filtering mode (typically `Point` or `Clamp`) to prevent interpolation between distinct permutation values [S2, unofficial].

## Operating characteristics
-   **Time Complexity**: $O(1)$ per sample for a single octave. $O(O)$ for $O$ octaves of FBM.
-   **Memory Complexity**: Depends on the size of the permutation and gradient textures. Typically $O(1)$ if textures are fixed size (e.g., 256x256).
-   **Performance**: GPU-based implementation using texture lookups is significantly faster than CPU-based array lookups due to cache coherence and branchless execution [S2, unofficial].
-   **Strengths**: Smooth, continuous noise; supports 4D (time); optimized for GPU via texture-based hashing [S2, unofficial].
-   **Limitations**: Requires pre-computed permutation and gradient textures; 4D computation is more expensive than 3D due to 16 corners vs 8 [S1, unofficial].

## Background
Improved Perlin Noise (4D) is based on Ken Perlin's Improved Noise algorithm, which uses a quintic fade curve to ensure $C^2$ continuity [S1, unofficial]. The 4D extension allows for time-varying textures and volumetric noise generation [S1, unofficial]. The specific GPU-optimized implementation using 2D permutation textures and texture-based gradient lookup is described in the context of GPU-based marching cubes and procedural noise generation [S1, S2, unofficial].
