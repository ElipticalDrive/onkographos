# Cloud Configuration Parameters

Also called: CloudConfig

## Overview
Cloud Configuration Parameters define the physical, geometric, and visual properties required to generate and render volumetric clouds. This method solves the problem of parameterizing procedural cloud fields by providing a structured set of inputs that control density generation, spatial bounds, lighting interaction, and rendering quality. It distinguishes itself from sibling methods by acting as the central data hub: [Volumetric Cloud Raymarching](1248-volumetric-cloud-raymarching.md) consumes these parameters for integration, while [Procedural Volume Cloud Modeling](2256-procedural-volume-cloud-modeling.md) uses them to drive noise functions.

## How it works
The method consists of two distinct parameterization schemes found in the sources: a shader-based configuration for real-time rendering (Scheme A) and a data-class-based validation scheme for volume mask generation (Scheme B).

### Inputs and Outputs
*   **Inputs**: User-defined physical constants, scene geometry bounds, and rendering quality flags.
*   **Outputs**: A validated configuration structure passed to the rendering pipeline or volume generation algorithm.

### Data Structures

**Scheme A: Shader Uniforms (CloudConfig)**
Defined in [S1, unofficial], this structure maps directly to GPU uniforms.

```rust
pub struct CloudConfig {
    pub cloud_type: f32,                  // 0.0 = Stratus, 0.5 = Stratocumulus, 1.0 = Cumulus
    pub coverage_multiplier: f32,         // Modulates weather map threshold
    pub wind_direction: [f32; 3],         // Horizontal wind vector
    pub wind_speed: f32,                  // Wind magnitude
    pub cloud_color: [f32; 3],            // RGB base color
    pub inner_sphere_radius: f32,         // Inner bound of spherical mask
    pub outer_sphere_radius: f32,         // Outer bound of spherical mask
    pub sphere_y_offset: f32,             // Vertical offset of sphere center
    pub max_render_distance: f32,         // Ray march termination distance
    pub cloud_top_offset: f32,            // Vertical extension above base
    pub weather_texture_scale: f32,       // Scale for weather map lookup
    pub base_noise_scale: f32,            // Low-frequency noise scale
    pub high_frequency_noise_scale: f32,  // High-frequency noise amplitude
    pub high_frequency_noise_uv_scale: f32, // UV scale for high-freq noise
    pub high_frequency_noise_h_scale: f32,  // Height scale for high-freq noise
    pub quality: CloudQuality,            // Enum: Low, Medium, High
}
```

**Scheme B: Volume Generation Dataclass**
Defined in [S2, unofficial], this frozen dataclass controls the deterministic generation of volume masks.

```python
@dataclass(frozen=True)
class VolumeParameters:
    cloud_type_id: int = 9
    resolution: int = 128
    seed: int = 42
    shape_strength: float = 1.0
    detail_strength: float = 0.55
    disturbance_strength: float = 0.65
    cartoon_style: bool = False
    allow_boundary_overlap: Optional[bool] = None
```

### Steps

1.  **Initialize Parameters**: Load default values or user overrides into the respective structure.
2.  **Validate Constraints (Scheme B)**:
    *   Verify `resolution` is exactly 64, 128, or 256 [S2, unofficial].
    *   Verify `shape_strength`, `detail_strength`, and `disturbance_strength` are within $[0.0, 2.0]$ [S2, unofficial].
    *   If `allow_boundary_overlap` is `None`, assign the default value from the cloud type catalog [S2, unofficial].
3.  **Configure Spatial Bounds**:
    *   Set the volume box height using the multiplier relative to the weather height layer. The standard multiplier is 4.0 [S2, unofficial].
    *   Define spherical bounds using `inner_sphere_radius`, `outer_sphere_radius`, and `sphere_y_offset` [S1, unofficial].
4.  **Set Lighting and Scattering**:
    *   Apply `cloud_color` as the base albedo.
    *   Configure wind advection using `wind_direction` and `wind_speed` [S1, unofficial].
5.  **Configure Noise**:
    *   Apply `weather_texture_scale` to the base weather map.
    *   Modulate procedural noise using `base_noise_scale`, `high_frequency_noise_scale`, `high_frequency_noise_uv_scale`, and `high_frequency_noise_h_scale` [S1, unofficial].
6.  **Select Quality**: Set `quality` to Low, Medium, or High, which determines internal resolution and step counts [S1, unofficial].

### Formulas
*   **Volume Box Height**: $H_{box} = H_{weather} \times 4.0$ [S2, unofficial].
*   **Cloud Type Interpolation**: $C_{type} \in [0.0, 1.0]$, where $0.0$ is Stratus, $0.5$ is Stratocumulus, and $1.0$ is Cumulus [S1, unofficial].

### Edge Cases and Pitfalls
*   **Invalid Resolution**: If `resolution` is not 64, 128, or 256, the volume generation fails [S2, unofficial].
*   **Strength Bounds**: Strength parameters outside $[0.0, 2.0]$ are invalid [S2, unofficial].
*   **Boundary Overlap**: If `allow_boundary_overlap` is not explicitly set, the system must fallback to the cloud type's default behavior [S2, unofficial].

## Subtopics

### Volume Parameters Validation
A strict validation step for Scheme B parameters. It ensures `resolution` is in $\{64, 128, 256\}$ and strength parameters are in $[0.0, 2.0]$. It also handles the defaulting of `allow_boundary_overlap` if left undefined. This prevents invalid volume masks from being generated [S2, unofficial].

## Operating characteristics
*   **Time Complexity**: Parameter validation is $O(1)$. The cost of using these parameters lies in the downstream [Volumetric Cloud Raymarching](1248-volumetric-cloud-raymarching.md) and noise generation, which scale with `max_render_distance` and `quality` settings.
*   **Memory Complexity**: $O(1)$ for the configuration structure itself. The actual volume data memory depends on `resolution` (Scheme B) or texture size (Scheme A).
*   **Strengths**: Centralized control over complex cloud physics and visuals. Decouples parameter definition from rendering logic.
*   **Limitations**: Requires careful tuning of multiple noise scales and wind vectors to achieve desired visuals. Scheme B is rigid regarding resolution choices.
*   **When to use**: When implementing a procedural cloud system that requires configurable density, shape, and lighting behavior.

## Background
The concept originates from real-time volumetric cloud rendering techniques, specifically those ported to Rust/wgpu engines like AetherEngine [S1, unofficial]. The validation scheme derives from procedural noise cloud generation libraries like Noise-Cloud [S2, unofficial]. The parameters bridge the gap between high-level artistic controls (cloud type, color) and low-level rendering requirements (noise scales, ray march distances).
