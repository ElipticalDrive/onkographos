# Cloud Configuration Parameters

Also called: CloudConfig

## Overview
Cloud Configuration Parameters provide a structured set of inputs to control density generation, spatial bounds, lighting interaction, and rendering quality for procedural volumetric clouds [S1, unofficial][S2, unofficial]. It defines the parameter sets used by [Volumetric Cloud Raymarching](1248-volumetric-cloud-raymarching.md) for integration and [Procedural Volume Cloud Modeling](2256-procedural-volume-cloud-modeling.md) for noise generation [S1, unofficial][S2, unofficial].

## How it works
### Inputs and Outputs
Inputs consist of physical constants, scene geometry bounds, and rendering quality flags [S1, unofficial][S2, unofficial]. Outputs are validated configuration structures passed to the rendering pipeline or volume generation algorithm [S1, unofficial][S2, unofficial].

**Scheme B: Volume Generation Dataclass [S2, unofficial]**
Defined in [S2, unofficial], this frozen dataclass controls the deterministic generation of volume masks.

```python
from dataclasses import dataclass
from typing import Optional

@dataclass(frozen=True)
class VolumeParameters:
    cloud_type_id: int = 9
    resolution: int = 128
    seed: int = 42
    shape_strength: float = 1.0
    detail_strength: float = 0.55
    disturbance_strength: float = 0.65
    cartoon_style: bool = False
    allow_boundary_overlap: Optional[bool] = None
```

### Steps

1. **Initialize Parameters**: Load default values or user overrides into the respective structure [S1, unofficial][S2, unofficial].
2. **Validate Constraints (Scheme B)**: Verify `resolution` is exactly 64, 128, or 256 [S2, unofficial]. Verify `shape_strength`, `detail_strength`, and `disturbance_strength` are within $[0.0, 2.0]$ [S2, unofficial]. If `allow_boundary_overlap` is `None`, assign the default value from the cloud type catalog [S2, unofficial].
3. **Configure Spatial Bounds**: Define spherical bounds using `inner_sphere_radius`, `outer_sphere_radius`, and `sphere_y_offset` [S1, unofficial]. Set the volume box height using a multiplier relative to the weather height layer, with a standard multiplier of 4.0 [S2, unofficial].
4. **Set Lighting and Scattering**: Apply `cloud_color` as the base albedo [S1, unofficial]. Configure wind advection using `wind_direction` and `wind_speed` [S1, unofficial].
5. **Configure Noise**: Apply `weather_texture_scale` to the base weather map [S1, unofficial]. Modulate procedural noise using `base_noise_scale`, `high_frequency_noise_scale`, `high_frequency_noise_uv_scale`, and `high_frequency_noise_h_scale` [S1, unofficial].
6. **Select Quality**: Set `quality` to Low, Medium, or High, which determines internal resolution and step counts [S1, unofficial].

### Formulas
*   **Cloud Type Interpolation**: $C_{type} \in [0.0, 1.0]$, where $0.0$ is Stratus, $0.5$ is Stratocumulus, and $1.0$ is Cumulus [S1, unofficial].
*   **Volume Box Height**: The volume box height uses a multiplier relative to the weather height layer, with a standard multiplier of 4.0 [S2, unofficial].

### Edge Cases and Pitfalls
*   **Invalid Resolution**: If `resolution` is not 64, 128, or 256, the volume generation fails [S2, unofficial].
*   **Strength Bounds**: Strength parameters outside $[0.0, 2.0]$ are invalid [S2, unofficial].
*   **Boundary Overlap**: If `allow_boundary_overlap` is not explicitly set, the system falls back to the cloud type's default behavior [S2, unofficial].

## Subtopics

### Volume Parameters Validation
A strict validation step for Scheme B parameters [S2, unofficial]. It ensures `resolution` is in $\{64, 128, 256\}$ and strength parameters are in $[0.0, 2.0]$ [S2, unofficial]. It also handles the defaulting of `allow_boundary_overlap` if left undefined [S2, unofficial].

## Operating characteristics
*   **Time Complexity**: Not given in the sources.
*   **Memory Complexity**: Not given in the sources.
*   **Strengths**: Centralized control over cloud physics and visuals, and decoupling parameter definition from rendering logic [S1, unofficial][S2, unofficial].
*   **Limitations**: Requires careful tuning of noise scales and wind vectors, and Scheme B has rigid resolution choices [S1, unofficial][S2, unofficial].
*   **When to use**: Use this method when implementing a procedural cloud system requiring configurable density, shape, and lighting behavior [S1, unofficial][S2, unofficial].

## Background
The concept originates from real-time volumetric cloud rendering techniques, specifically those ported to Rust/wgpu engines like AetherEngine [S1, unofficial]. The validation scheme derives from procedural noise cloud generation libraries like Noise-Cloud [S2, unofficial]. The parameters bridge high-level artistic controls and low-level rendering requirements [S1, unofficial][S2, unofficial].
