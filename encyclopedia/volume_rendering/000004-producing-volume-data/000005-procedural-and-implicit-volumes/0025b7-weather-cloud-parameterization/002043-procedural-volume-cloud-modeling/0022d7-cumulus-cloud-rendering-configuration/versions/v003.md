# Cumulus Cloud Rendering Configuration


## Overview
This configuration specifies the procedural noise parameters used to generate the density field for cumulus clouds within the Ray-Guided Streaming framework [S1, unofficial]. It serves as a concrete instantiation of procedural volume cloud modeling, tailored to encode cloud details for multiple scattering simulations [S1, unofficial]. It differs from general gas modeling by focusing on specific fractal noise parameters for cumulus morphology rather than generic turbulence [G].

## How it works
**Inputs:**
- Noise type: Perlin noise [S1, unofficial].
- Octaves: 5 [S1, unofficial].
- Noise dimensions: $N=2$ (2D noise projected or sampled) [S1, unofficial].
- Noise scale/period: $M=32$ [S1, unofficial].
- Target virtual resolution: $2048^3$ [S1, unofficial].

**Outputs:**
- A density field $\rho(x, y, z)$ representing the cumulus cloud structure [S1, unofficial].

**Data Structures:**
The density values are stored in a sparse voxel grid managed by the Ray-Guided Streaming system [S1, unofficial]. The configuration implies a virtual resolution of $2048^3$, but actual memory usage is optimized via the streaming brick pool [S1, unofficial].
- Brick pool size: 430 MB, supporting up to $42^3$ bricks [S1, unofficial].
- Node pool size: Typically 4 MB (corresponding to $64^3$ entries) [S1, unofficial].
- Indexing: $16^3$ bricks can reference $1024^3$ indices [S1, unofficial].

**Steps:**
1. Initialize a Perlin noise generator with 5 octaves [S1, unofficial].
2. Set the base noise dimension to 2D ($N=2$) [S1, unofficial].
3. Set the noise scale parameter to $M=32$ [S1, unofficial].
4. Evaluate the noise function at the query point $(x, y, z)$ to determine the local density contribution [S1, unofficial].
5. Integrate the density into the streaming voxel structure [S1, unofficial].

**Formulas:**
The density is computed via fractal Brownian motion (fBm) accumulation [G]:
$$\rho(x,y,z) = \sum_{i=0}^{4} 0.5^i \cdot \mathcal{P}(M \cdot 2^i \cdot \mathbf{u})$$
where $\mathcal{P}$ is the Perlin noise function, $M=32$ is the base scale, and $\mathbf{u}$ is the 2D input vector derived from the 3D query point $(x,y,z)$ [G]. Since $N=2$, the $z$-coordinate is typically ignored or used as a phase/time variable [G].

```python
    noise_value = 0.0

    frequency = 1.0
    M = 32

    for i in range(5):
        # N=2 implies 2D noise projection; z is used as phase/time [G]
        nx = x * M * frequency
        ny = y * M * frequency
        nz = z * M * frequency

        noise_value += amplitude * perlin_noise(nx, ny, nz)

        amplitude *= 0.5
        frequency *= 2.0

    return noise_value
```

**Edge Cases and Pitfalls:**
- **Precision:** The virtual resolution of $2048^3$ is high; ensuring floating-point precision in the noise evaluation is critical to avoid artifacts at fine scales [G].
- **Performance:** Complex GPU computations result in relatively low frame rates (around 20 FPS for a $1024^3$ volume) [S1, unofficial]. The use of 5 octaves adds computational overhead [S1, unofficial].
- **Memory:** The virtual resolution is high, but actual memory usage is managed by the brick pool. Care must be taken to ensure the brick pool size (430 MB) is sufficient for scene complexity [S1, unofficial].

## Operating characteristics
- **Time Complexity:** Low frame rates (~20 FPS for a $1024^3$ volume) due to complex GPU computations [S1, unofficial]. The use of 5 octaves of Perlin noise adds computational overhead [S1, unofficial].
- **Memory Complexity:** Trades computation time for memory efficiency [S1, unofficial]. Normals are computed on-the-fly [S1, unofficial]. The brick pool used 430 MB, giving room for $42^3$ bricks [S1, unofficial]. The node pool was small (4 MB) corresponding to $64^3$ entries [S1, unofficial]. Using $16^3$ bricks, $1024^3$ indices can be referenced [S1, unofficial].
- **Strengths:** Allows for an increase of detail in cloud simulation, especially when combined with complex shading for multiple scattering [S1, unofficial]. On-the-fly noise creation on the GPU is more efficient than CPU evaluation and transfer [S1, unofficial].
- **Limitations:** Low frame rates due to complex GPU computations [S1, unofficial].
- **When to use:** When high-detail cumulus clouds are required for multiple scattering simulations and memory efficiency is a priority [S1, unofficial].
- **When not to use:** When real-time performance is critical and lower detail is acceptable [G].

This configuration was used to encode cloud details in the work by BNM* 08, which deals with multiple scattering in clouds [S1, unofficial]. The specific parameters ($N=2, M=32, 5$ octaves) were chosen to simulate enhanced cumulus clouds within the Ray-Guided Streaming framework [S1, unofficial].
