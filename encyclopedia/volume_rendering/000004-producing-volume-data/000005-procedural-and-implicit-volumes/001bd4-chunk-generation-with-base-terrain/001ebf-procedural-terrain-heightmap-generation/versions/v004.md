# Procedural Terrain Heightmap Generation

Also called: FBM Heightmap Chunk Generation, Procedural World Generation

## Overview
Procedural Terrain Heightmap Generation creates a 3D voxel volume by sampling a 2D noise function to determine column heights, then filling solid blocks from a base level up to the computed height for each $(x,z)$ position within a chunk [S2, S4, S5, unofficial]. It solves the problem of creating deterministic, pseudo-random terrain geometry by leveraging the property that a fixed input yields the same output, allowing terrain data to be preserved across frames without change . It sets itself apart from [Procedural Terrain Feature Generation](2572-procedural-terrain-feature-generation.md) by focusing on continuous height variation rather than discrete feature placement, and from [Heightmap generation via circular displacements](5186-heightmap-generation-via-circular-displacements.md) by using gradient-based noise functions rather than radial displacement patterns [G].

## How it works
**Inputs:**
- Chunk coordinates $(cx, cz)$ defining the chunk's position in the world grid.
- Chunk dimensions: width $W$, depth $D$, and height $H$ (typically $16 \times 64 \times 16$ blocks) [S2, unofficial].
- Noise function parameters: seed, frequency, and noise type (e.g., OpenSimplex2) [S2, unofficial].
- Scaling factors for height calculation (e.g., amplitude and offset) [S1, unofficial].

**Outputs:**
- A 3D array `block_data` of size $W \times H \times D$ containing integer block types [S2, unofficial].
- Index 0 represents air, 1 represents solid terrain (grass/dirt/stone), and 4 represents water [S1, S2, unofficial].

**Data Structures:**
- `block_data[x][y][z]`: A 3D integer array. In many implementations, the layout is optimized for chunk-based access, often stored as a flat array or a tightly packed 3D structure where $x$ is the fastest varying index or $y$ is the fastest, depending on the rendering pipeline. The source [S2, unofficial] specifies a layout of `[16][64][16]`.

**Steps:**
1. **Initialize Volume:** Set all voxels in `block_data` to 0 (air) [S2, unofficial].
2. **Iterate Chunk Grid:** Loop through each column $(x, z)$ within the chunk bounds, where $x \in [0, W-1]$ and $z \in [0, D-1]$ [S1, S2, unofficial].
3. **Calculate World Coordinates:** Compute the world-space coordinates for the current column:
   $$ wx = cx \times W + x $$
   $$ wz = cz \times D + z $$
   [S1, S2, unofficial].
4. **Sample Noise:** Evaluate a 2D noise function $f(wx, wz)$ at the world coordinates. The noise function should be bounded, typically in $[-1, 1]$ or $[0, 1]$ [S2, unofficial].
5. **Compute Height:** Transform the noise value into a block height $h$:
   $$ h = \lfloor f(wx, wz) \times A \rfloor + O $$
   Where $A$ is the amplitude (e.g., 60) and $O$ is the offset (e.g., 60) [S1, unofficial]. Alternatively, some implementations scale the noise by a factor (e.g., 4) and add an offset (e.g., 5) before casting to an integer [S2, unofficial].
6. **Fill Terrain Columns:** For each $y$ from 0 to $h$:
   - If $y = h$, set `block_data[x][y][z]` to 1 (grass) [S1, unofficial].
   - If $y > h - 4$ (and $y < h$), set `block_data[x][y][z]` to 2 (dirt) [S1, unofficial].
   - Otherwise, set `block_data[x][y][z]` to 3 (stone) [S1, unofficial].
   - *Note:* Some implementations simply fill all blocks from $y=0$ to $h-1$ with a solid type (1) [S2, unofficial].
7. **Fill Water:** For each $y$ from $h+1$ to a water level $L$ (e.g., 70), set `block_data[x][y][z]` to 4 (water) [S1, unofficial]. If $h \ge L$, no water is placed in that column.

**Parameters:**
- `chunk_maxsize_x`, `chunk_maxsize_z`: Chunk width and depth. Typical value: 16 [S2, unofficial].
- `chunk_maxsize_y`: Chunk height. Typical value: 64 [S2, unofficial].
- `noise.frequency`: Controls terrain roughness/scale. Typical value: 0.025 [S2, unofficial].
- `noise.noise_type`: Algorithm used. Typical value: OpenSimplex2 [S2, unofficial].
- `fbm_scale`: Divisor for world coordinates in noise sampling. Typical value: 80 [S1, unofficial].
- `fbm_amplitude`: Multiplier for noise output. Typical value: 60 [S1, unofficial].
- `fbm_offset`: Additive constant for height. Typical value: 60 [S1, unofficial].
- `water_level`: Y-coordinate below which water is placed. Typical value: 70 [S1, unofficial].

**Pitfalls:**
- **Boundary Continuity:** Neighboring chunks must use the same noise seed and scaling to ensure seamless terrain at chunk boundaries [S1, unofficial].
- **Precision:** Using integer arithmetic for height calculation can introduce quantization artifacts if the noise frequency is too high relative to the chunk size [S1, S2, unofficial].
- **Empty Columns:** If the noise function produces heights below the chunk's base Y, the column may be entirely air or water, requiring careful handling of the fill loop [S5, unofficial].

**Pseudocode:**
```python
def generate_chunk(cx, cz, chunk_w, chunk_d, chunk_h, noise_state, water_level=70):
    """
    Generates a voxel chunk based on a 2D noise heightmap.
    
    Args:
        cx, cz: Chunk coordinates in the world grid.
        chunk_w, chunk_d, chunk_h: Dimensions of the chunk (x, z, y).
        noise_state: Object containing noise parameters (seed, frequency, type).
        water_level: Y-coordinate for the water surface.
        
    Returns:
        block_data: 3D list/array of integers representing block types.
    """
    # Initialize all blocks to air (0)
    block_data = [[[0 for _ in range(chunk_d)] for _ in range(chunk_h)] for _ in range(chunk_w)]
    
    # Noise parameters
    freq = noise_state.frequency
    # Amplitude and offset for height calculation
    amp = 60
    offset = 60
    
    for x in range(chunk_w):
        for z in range(chunk_d):
            # Calculate world coordinates
            wx = cx * chunk_w + x
            wz = cz * chunk_d + z
            
            # Sample 2D noise
            # Assuming noise function returns value in [-1, 1] or [0, 1]
            # Adjust scaling based on specific noise implementation
            noise_val = sample_noise(noise_state, wx * freq, wz * freq)
            
            # Compute height
            # Clamp noise to [0, 1] if necessary, or adjust formula
            h = int(noise_val * amp) + offset
            
            # Fill terrain
            for y in range(chunk_h):
                if y <= h:
                    if y == h:
                        block_data[x][y][z] = 1  # Grass
                    elif y > h - 4:
                        block_data[x][y][z] = 2  # Dirt
                    else:
                        block_data[x][y][z] = 3  # Stone
                elif y <= water_level:
                    block_data[x][y][z] = 4  # Water
                else:
                    block_data[x][y][z] = 0  # Air (above water and terrain)
                    
    return block_data

def sample_noise(state, x, y):
    """
    Wrapper for the noise library's 2D noise function.
    Returns a float value.
    """
    # Implementation depends on the specific noise library (e.g., FastNoiseLite)
    # This is a placeholder for the actual noise call
    return state.get_noise_2d(x, y)
```

## Subtopics

### [Terrain Generation via Noise](2412-terrain-generation-via-noise.md)
Terrain Generation via Noise generates a 3D voxel volume from a 2D noise heightmap, extruding terrain-like structures into voxel space. It solves the problem of creating deterministic, pseudo-random terrain geometry by leveraging the property that a fixed input yields the same output, allowing terrain data to be preserved across frames without change. It sets itself apart from [Procedural Terrain Feature Generation](2572-procedural-terrain-feature-generation.md) by focusing on continuous height variation rather than discrete feature placement, and from [Heightmap generation via circular displacements](5186-heightmap-generation-via-circular-displacements.md) by using gradient-based noise functions rather than radial displacement patterns [G].

### [Procedural Terrain Feature Generation](2572-procedural-terrain-feature-generation.md)
Procedural Terrain Feature Generation is a method for creating specific volumetric structures, primarily cliffs and overhangs, by approximating their topology as a bicubic Bézier surface combined with a parabolic plateau function. It produces local delta values (additive blending) applied directly to volumetric data, allowing for nondestructive editing where parameters can be adjusted and transformations applied before surface extraction. It differs from general noise-based terrain generation by focusing on explicit geometric primitives for sharp features rather than stochastic displacement.

### [Smooth Terrain Grid](5026-smooth-terrain-grid.md)
Generates a terrain grid with smoothed heights using interpolation between random sample points.

### [Heightmap generation via circular displacements](5186-heightmap-generation-via-circular-displacements.md)
This method generates a procedural terrain heightmap by iteratively applying overlapping circular displacement functions to a flat vertex grid. It constructs height by accumulating discrete, localized perturbations defined by random centers, radii, and signs.

### [Terrain Skinning via Perturbation Function](13510-terrain-skinning-via-perturbation-function.md)
Terrain Skinning via Perturbation Function represents terrain as a scalar field defined by a base surface $P$ and a 2D altitude map (perturbation function) $h$. It solves the problem of defining complex terrain geometry within a volume rendering pipeline by decoupling the global shape from local details. Unlike [Terrain Generation via Noise](2412-terrain-generation-via-noise.md) which generates height directly, or [Smooth Terrain Grid](5026-smooth-terrain-grid.md) which modifies vertex positions on a fixed grid, this method projects points onto a simple base surface (plane, ellipsoid, cylinder) and displaces them along the surface normal using interpolated values from a discrete table.

### Terrain Generation via Image Sampling
A method to dictate voxel Y-axis height and vertex colors by extracting raw pixel arrays from 2D .png files (grayscale heightmap and RGB colormap) using `getImageData()` [S3, unofficial].
**Steps:**
1. Load `heightmap.png` and `colormap.png` images [S3, unofficial].
2. Extract pixel data using `ctx.getImageData(0, 0, gridSize, gridSize).data` [S3, unofficial].
3. Iterate $x$ from 0 to $gridSize-1$ and $z$ from 0 to $gridSize-1$ [S3, unofficial].
4. Calculate world position: $posX = (x \times spacing) - offset$, $posZ = (z \times spacing) - offset$, where $offset = (gridSize \times spacing) / 2$ [S3, unofficial].
5. Calculate pixel index: $pixelIndex = (z \times gridSize + x) \times 4$ [S3, unofficial].
6. Calculate Y scale from heightmap: $yScale = 1 + (heightData[pixelIndex] / 255.0) \times 100$ [S3, unofficial].
7. Calculate color from colormap: $r = colorData[pixelIndex] / 255.0$, $g = colorData[pixelIndex + 1] / 255.0$, $b = colorData[pixelIndex + 2] / 255.0$ [S3, unofficial].
8. Store instance data: `instancePositions[i3] = posX`, `instancePositions[i3+1] = yScale - 1`, `instancePositions[i3+2] = posZ`; `instanceScales[i1] = yScale`; `instanceColors[i3] = r`, `instanceColors[i3+1] = g`, `instanceColors[i3+2] = b` [S3, unofficial].
**Pitfall:** If local image sampling fails due to CORS restrictions, the engine falls back to a mathematical terrain generation using `Math.sin` and `Math.cos` [S3, unofficial].

### Cliffs Layer
A terrain layer that creates escarpments by stepping into terraces of a specific height, joined by cliffs over the last portion of each step [S4, unofficial].
**Steps:**
1. Implementation uses integer terracing in 32 bits, identical on CPU (`landform::terrace`) and GPU (`landform_terrace`) [S4, unofficial].
2. The riser share rides in the stack layer's kind bits [S4, unofficial].
**Pitfall:** A terrace moves a height by less than a step and is not Lipschitz, so each level's margin grows by two steps to contain it [S4, unofficial].

### Chunk Filling with Height Map
The `FillChunk` function iterates over Y, Z, and X coordinates of the chunk grid. For each voxel, it calculates an index $i$ based on X and Z. If the current Y coordinate is less than the height at $i$ minus the chunk's start Y, the voxel is filled with the result of the provided function `func(x, y, z)` [S5, unofficial].
**Formula:** Voxel fill condition: $y < (heights[i] - chunk\_start.y)$, where $y$ is the current voxel Y coordinate, $heights[i]$ is the height value at index $i$, and $chunk\_start.y$ is the Y coordinate of the chunk's origin [S5, unofficial].
**Pitfall:** The `FillChunk` function with `HeightMapData` includes a boundary check: if the chunk's Y range is completely outside the height map's range (`chunk_start.y + PaddedChunkGrid3D::Dims.y <= height_data.range.x || chunk_start.y >= height_data.range.y`), the function returns early without processing [S5, unofficial].

## Operating characteristics
- **Time Complexity:** $O(W \times D \times H)$ per chunk, where $W, D, H$ are chunk dimensions. The noise sampling is $O(1)$ per column, making the dominant factor the voxel filling loop [S1, S2, unofficial].
- **Memory Complexity:** $O(W \times D \times H)$ for the voxel data structure. For a $16 \times 64 \times 16$ chunk, this is 16,384 integers, which is manageable in memory [S2, unofficial].
- **Performance:** Generating a single chunk is fast enough for real-time generation on the CPU for typical chunk sizes [S1, unofficial]. However, generating many chunks simultaneously may require multithreading [S1, unofficial].
- **Strengths:** Deterministic output, simple implementation, easy to cache and stream chunks [S1, unofficial].
- **Limitations:** Limited to terrain-like structures; cannot easily create overhangs or caves without additional logic (e.g., [Procedural Cave Generation](2579-procedural-cave-generation.md)) [S1, unofficial]. The heightmap approach assumes a single height per $(x,z)$ column, which may not suit all terrain types [G].
- **When to Use:** Ideal for open-world terrain where simplicity and determinism are prioritized over complex geological features [S1, unofficial].
- **When Not to Use:** When complex 3D structures like caves, overhangs, or non-heightmap-based features are required [S1, unofficial].

## Background
Procedural terrain generation using noise functions has been a staple in computer graphics and game development since the early days of voxel-based games. The use of fractal Brownian motion (fBm) to create natural-looking terrain heights is well-established [S1, unofficial]. The specific implementation of chunk-based generation with heightmaps allows for efficient memory management and streaming of large worlds [S1, unofficial]. The method described here is a common pattern in indie game development and educational tutorials on voxel engine construction [S1, S2, unofficial].
