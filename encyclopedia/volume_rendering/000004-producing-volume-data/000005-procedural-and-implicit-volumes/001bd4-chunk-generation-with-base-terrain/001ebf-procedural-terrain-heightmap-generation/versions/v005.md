# Procedural Terrain Heightmap Generation

Also called: FBM Heightmap Chunk Generation, Procedural World Generation

## Overview
Procedural Terrain Heightmap Generation creates a 3D voxel terrain chunk by sampling a 2D noise function to determine column heights, then filling solid blocks from a base level (typically $y=0$) up to the computed height for each $(x,z)$ position within the chunk [S2, S4, 5, unofficial]. It solves the problem of creating deterministic, pseudo-random terrain geometry by leveraging the property that a fixed input yields the same output, allowing terrain data to be preserved across frames without change . It sets itself apart from [Procedural Terrain Feature Generation](2572-procedural-terrain-feature-generation.md) by focusing on continuous height variation rather than discrete feature placement, and from [Heightmap generation via circular displacements](5186-heightmap-generation-via-circular-displacements.md) by using gradient-based noise functions rather than radial displacement patterns [G].

## How it works
**Inputs:**
*   Chunk coordinates $(cx, cz)$ defining the chunk's position in the world grid.
*   Chunk dimensions: width $CX$, depth $CZ$, and height $CY$ (or $chunk\_maxsize\_y$) [S2, unofficial].
*   Noise generator state (seed, frequency, type) [S2, unofficial].
*   Optional: Image files for heightmap and colormap sampling [S3, unofficial].

**Outputs:**
*   A 3D array `block_data` of size $[CX][CY][CZ]$ (or $[16][64][16]$ in typical implementations) where each element represents a voxel type (e.g., 0 for air, 1 for grass, 2 for dirt, 3 for stone, 4 for water) [S1, S2, unofficial].

**Data Structures:**
*   `block_data`: A 3D integer array. Index 0 represents air, index 1 represents solid terrain block (grass), index 2 represents dirt, index 3 represents stone, and index 4 represents water [S1, S2, unofficial].
*   Noise State: Contains parameters such as `seed`, `frequency`, and `noise_type` (e.g., `OPENSIMPLEX2`) [S2, unofficial].

**Parameters:**
*   `chunk_maxsize_x`, `chunk_maxsize_z`: Chunk width and depth in blocks. Typical value: 16 [S2, unofficial].
*   `chunk_maxsize_y`: Chunk height in blocks. Typical value: 64 [S2, unofficial].
*   `noise.frequency`: Controls terrain roughness/scale. Typical value: 0.025f [S2, unofficial].
*   `noise.noise_type`: Noise algorithm used. Typical value: `FNL_NOISE_OPENSIMPLEX2` [S2, unofficial].
*   `fbm_scale`: Scale factor for world coordinates in FBM calculation. Typical value: 80 [S1, unofficial].
*   `fbm_amplitude`: Amplitude multiplier for FBM output. Typical value: 60 [S1, unofficial].
*   `fbm_offset`: Vertical offset added to FBM output. Typical value: 60 [S1, unofficial].
*   `water_level`: The Y-level below which water is placed. Typical value: 70 [S1, unofficial].
*   `dirt_thickness`: Number of dirt layers below the surface. Typical value: 4 [S1, unofficial].

**Steps:**
1.  **Initialize Data:** Create `block_data` of size $[CX][CY][CZ]$ and initialize all elements to 0 (air) [S2, unofficial].
2.  **Iterate Grid:** Loop through each column $(x, z)$ where $x \in [0, CX-1]$ and $z \in [0, CZ-1]$ [S1, S2, unofficial].
3.  **Calculate World Coordinates:** Compute the world-space coordinates $(wx, wz)$ for the current column.
    *   $wx = cx \times CX + x$
    *   $wz = cz \times CZ + z$
    [S1, unofficial]
4.  **Sample Noise:** Calculate the height $h$ using a noise function (typically Fractional Brownian Motion, FBM, or OpenSimplex2) [S1, S2, unofficial].
    *   Using FBM: $h = \lfloor \text{fbm}(wx / 80, wz / 80) \times 60 \rfloor + 60$ [S1, unofficial].
    *   Using OpenSimplex2: $h = \lfloor (\text{noise}(wx, wz) \times 4 + 5) \rfloor$ [S2, unofficial].
    *   Note: The noise function output is typically bounded between -1 and 1 or 0 and 1, requiring scaling and offsetting to fit the desired height range [S2, unofficial].
5.  **Fill Terrain Columns:** For each $y$ from 0 to $h$:
    *   If $y == h$: Set `block_data[x][y][z] = 1` (grass) [S1, unofficial].
    *   Else if $y > h - 4$: Set `block_data[x][y][z] = 2` (dirt) [S1, unofficial].
    *   Else: Set `block_data[x][y][z] = 3` (stone) [S1, unofficial].
    [S1, unofficial]
6.  **Fill Water:** For each $y$ from $h + 1$ to $water\_level$ (e.g., 70):
    *   Set `block_data[x][y][z] = 4` (water) [S1, unofficial].
    *   Note: If $h \ge water\_level$, this step may be skipped or handled to ensure water does not overwrite terrain above the water line [S1, unofficial].
7.  **Handle Image Sampling (Variant):** If using image sampling instead of procedural noise:
    *   Load `heightmap.png` and `colormap.png` [S3, unofficial].
    *   Extract pixel data using `ctx.getImageData()` [S3, unofficial].
    *   Calculate pixel index: $pixelIndex = (z \times gridSize + x) \times 4$ [S3, unofficial].
    *   Calculate Y scale: $yScale = 1 + (heightData[pixelIndex] / 255.0) \times 100$ [S3, unofficial].
    *   Calculate color: $r = colorData[pixelIndex] / 255.0$, $g = colorData[pixelIndex + 1] / 255.0$, $b = colorData[pixelIndex + 2] / 255.0$ [S3, unofficial].
    *   Store instance data for rendering [S3, unofficial].
    *   Fallback to mathematical terrain generation if image sampling fails due to CORS restrictions [S3, unofficial].

**Pseudocode:**
```python
def generate_chunk(cx, cz, chunk_width, chunk_depth, chunk_height, noise_state, water_level=70, dirt_thickness=4):
    # Initialize block data with air (0)
    block_data = [[[0 for z in range(chunk_depth)] for y in range(chunk_height)] for x in range(chunk_width)]
    
    # Iterate over each column in the chunk
    for x in range(chunk_width):
        for z in range(chunk_depth):
            # Calculate world coordinates
            wx = cx * chunk_width + x
            wz = cz * chunk_depth + z
            
            # Sample noise to get height
            # Using FBM example from [S1, unofficial]
            noise_val = fbm(wx / 80.0, wz / 80.0)
            h = int(noise_val * 60) + 60
            
            # Clamp height to chunk bounds if necessary
            h = max(0, min(h, chunk_height - 1))
            
            # Fill terrain column
            for y in range(h + 1):
                if y == h:
                    block_data[x][y][z] = 1  # Grass
                elif y > h - dirt_thickness:
                    block_data[x][y][z] = 2  # Dirt
                else:
                    block_data[x][y][z] = 3  # Stone
            
            # Fill water below water level
            for y in range(h + 1, water_level + 1):
                if y < chunk_height:
                    block_data[x][y][z] = 4  # Water
                    
    return block_data
```

## Subtopics

### [Terrain Generation via Noise](2412-terrain-generation-via-noise.md)
Terrain Generation via Noise generates a 3D voxel volume from a 2D noise heightmap, extruding terrain-like structures into voxel space. It solves the problem of creating deterministic, pseudo-random terrain geometry by leveraging the property that a fixed input yields the same output, allowing terrain data to be preserved across frames without change. It sets itself apart from [Procedural Terrain Feature Generation](2572-procedural-terrain-feature-generation.md) by focusing on continuous height variation rather than discrete feature placement, and from [Heightmap generation via circular displacements](5186-heightmap-generation-via-circular-displacements.md) by using gradient-based noise functions rather than radial displacement patterns [G].

### [Procedural Terrain Feature Generation](2572-procedural-terrain-feature-generation.md)
Procedural Terrain Feature Generation is a method for creating specific volumetric structures, primarily cliffs and overhangs, by approximating their topology as a bicubic Bézier surface combined with a parabolic plateau function. It produces local delta values (additive blending) applied directly to volumetric data, allowing for nondestructive editing where parameters can be adjusted and transformations applied before surface extraction. It differs from general noise-based terrain generation by focusing on explicit geometric primitives for sharp features rather than stochastic displacement.

### [Smooth Terrain Grid](5026-smooth-terrain-grid.md)
Smooth Terrain Grid is a procedural geometry generation technique that converts discrete voxel height data into a continuous, smoothed terrain mesh by computing vertex heights at grid corners via averaging. It solves the problem of jagged, stair-stepped voxel surfaces by replacing flat voxel faces with interpolated planes, allowing for tilted and elevated terrain shapes. It differs from [Terrain Generation via Noise](2412-terrain-generation-via-noise.md) by relying on spatial averaging of existing discrete values rather than continuous noise functions, and from [Procedural Terrain Feature Generation](2572-procedural-terrain-feature-generation.md) by focusing on global surface smoothing rather than local feature placement.

### [Heightmap generation via circular displacements](5186-heightmap-generation-via-circular-displacements.md)
This method generates a procedural terrain heightmap by iteratively applying overlapping circular displacement functions to a flat vertex grid. It constructs height by accumulating discrete, localized perturbations defined by random centers, radii, and signs.

### [Terrain Skinning via Perturbation Function](13510-terrain-skinning-via-perturbation-function.md)
Terrain Skinning via Perturbation Function represents complex terrain as a simple base surface (e.g., a plane) perturbed by a scalar altitude map, eliminating the need for polygonal triangulation. Unlike voxel-based methods that require mesh extraction (e.g., Marching Cubes) or traditional heightmap rendering that suffers from LOD cracking and high depth complexity, this method uses recursive voxel subdivision and direct texture-sampling of the altitude map to modulate the base surface equation, resulting in low depth complexity and seamless rendering.

### [Chunk-based Terrain Generation and Culling](15193-chunk-based-terrain-generation-and-culling.md)
This method generates terrain geometry using a hierarchical octree structure where leaf nodes correspond to terrain chunks. It decouples heightmap generation from mesh creation, using a culling system based on camera distance and Level of Detail (LOD) thresholds to determine which chunks require processing. It differs from flat grid approaches by adapting resolution dynamically based on viewer proximity, ensuring performance scales with scene complexity rather than world size.

### [Heightmap Combination & Seamless Terrain Generation](15472-heightmap-combination-seamless-terrain-generation.md)
This method generates macroscopic terrain by stitching together multiple pre-existing heightmaps into a single seamless composite, using simplex noise to guide the selection and blending of regions. It differs from pure procedural noise generation by leveraging real-world or high-fidelity source data, optimizing memory bandwidth by packing multiple heightmaps into a single RGB/RGBA texture for simultaneous retrieval.

### [Far-Terrain Grid Generation](15837-far-terrain-grid-generation.md)
Generates a coarse grid of terrain vertices and linear-space RGBA colors for far-terrain rendering, using analytic heightfield sampling.

### Terrain Generation via Image Sampling
A method to dictate voxel Y-axis height and vertex colors by extracting raw pixel arrays from 2D .png files (grayscale heightmap and RGB colormap) using `getImageData()` [S3, unofficial].
*   **Steps:** Load `heightmap.png` and `colormap.png` [S3, unofficial]. Extract pixel data using `ctx.getImageData(0, 0, gridSize, gridSize).data` [S3, unofficial]. Iterate $x$ from 0 to $gridSize-1$ and $z$ from 0 to $gridSize-1$ [S3, unofficial]. Calculate world position: $posX = (x \times spacing) - offset$, $posZ = (z \times spacing) - offset$, where $offset = (gridSize \times spacing) / 2$ [S3, unofficial]. Calculate pixel index: $pixelIndex = (z \times gridSize + x) \times 4$ [S3, unofficial]. Calculate Y scale from heightmap: $yScale = 1 + (heightData[pixelIndex] / 255.0) \times 100$ [S3, unofficial]. Calculate color from colormap: $r = colorData[pixelIndex] / 255.0$, $g = colorData[pixelIndex + 1] / 255.0$, $b = colorData[pixelIndex + 2] / 255.0$ [S3, unofficial]. Store instance data: `instancePositions[i3] = posX`, `instancePositions[i3+1] = yScale - 1`, `instancePositions[i3+2] = posZ`; `instanceScales[i1] = yScale`; `instanceColors[i3] = r`, `instanceColors[i3+1] = g`, `instanceColors[i3+2] = b` [S3, unofficial].
*   **Pitfall:** If local image sampling fails due to CORS restrictions, the engine falls back to a mathematical terrain generation using `Math.sin` and `Math.cos` [S3, unofficial].

### Cliffs Layer
A terrain layer that creates escarpments by stepping into terraces of a specific height, joined by cliffs over the last portion of each step [S4, unofficial].
*   **Steps:** Implementation: Integer terracing in 32 bits, identical on CPU (`landform::terrace`) and GPU (`landform_terrace`). The riser share rides in the stack layer's kind bits [S4, unofficial].
*   **Pitfall:** Boundary: A terrace moves a height by less than a step and is not Lipschitz, so each level's margin grows by two steps to contain it [S4, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(CX \times CZ \times CY)$ per chunk, as every voxel in the chunk volume must be potentially set [S1, S2, unofficial].
*   **Memory Complexity:** $O(CX \times CZ \times CY)$ for the `block_data` array [S2, unofficial].
*   **Performance:** Depends heavily on chunk size and noise function complexity. Simple FBM or OpenSimplex2 noise is fast, but domain warping or higher octaves can increase CPU load [S2, unofficial].
*   **Strengths:** Deterministic, easy to implement, low memory overhead for simple terrain, supports infinite world generation via chunking [S1, S2, unofficial].
*   **Limitations:** Limited to vertical extrusion (no overhangs or caves without additional logic), resolution is fixed by chunk size, noise artifacts can be visible at chunk boundaries if not handled [S1, S2, unofficial].
*   **When to use:** Ideal for simple voxel games, terrain visualization, and scenarios where deterministic, continuous height variation is required [S1, S2, unofficial].
*   **When not to use:** When complex geological features, caves, or overhangs are needed (use [Procedural Cave Generation](2579-procedural-cave-generation.md) or [Procedural Terrain Feature Generation](2572-procedural-terrain-feature-generation.md)), or when high-fidelity, non-procedural terrain is required (use [Heightmap Combination & Seamless Terrain Generation](15472-heightmap-combination-seamless-terrain-generation.md)) [S1, S2, unofficial].

## Background
Procedural terrain generation using noise functions has been a staple in computer graphics and game development for decades. The specific implementation of generating voxel chunks from 2D heightmaps via FBM or OpenSimplex2 noise is widely used in indie voxel engines and educational tutorials [S1, S2, unofficial]. The use of image sampling for terrain generation is a variant that leverages existing 2D assets, often used in WebGL-based projects [S3, unofficial]. The concept of terraced cliffs and layered terrain is found in more advanced voxel engines, such as those used in planetary simulation [S4, unofficial].
