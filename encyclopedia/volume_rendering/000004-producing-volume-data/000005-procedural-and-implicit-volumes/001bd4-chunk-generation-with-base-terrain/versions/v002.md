# Chunk Generation with Base Terrain
Also called: Procedural Chunk Generation
## Overview
Chunk Generation with Base Terrain is a method for automatically populating voxel data when a new chunk is created or accessed in a procedural world [S1, unofficial]. It solves the problem of initializing empty spatial containers by defining a deterministic "base" geometry (such as a flat platform) that serves as the foundational layer for further procedural modifications [S1, unofficial]. It sets itself apart from [Procedural Volume Rendering with Noise Perturbation](1370-procedural-volume-rendering-with-noise-perturbation.md) by focusing on discrete block placement logic rather than continuous scalar field evaluation, and from [Cloud Mesh Generation](4822-cloud-mesh-generation.md) by generating solid volumetric data structures rather than surface meshes for translucent media.

## How it works
**Inputs and Outputs:**
*   **Input:** The 3D integer position of the chunk $(C_x, C_y, C_z)$ in world space, and the chunk dimensions (typically $32 \times 32 \times 32$ voxels).
*   **Output:** A 3D array (or hash set) of voxel data representing the chunk's content.

**Data Structures:**
The chunk is represented as a 3D array `voxels` with dimensions $[Y][Z][X]$, where each dimension has size 32. The elements are of type `VoxelKind` (an enumeration, e.g., `Air`, `Dirt`, `Stone`).
*   Layout: `voxels[y][z][x]` where $0 \le y, z, x < 32$.
*   Initialization: All voxels are initialized to `VoxelKind::Air` [S1, unofficial].

**Steps:**
1.  **Check Existence:** Determine if the chunk at position $C$ already exists in the world storage. If it exists, return the existing chunk data [S1, unofficial].
2.  **Initialize Data:** Create a new 3D array `voxels` of size $32 \times 32 \times 32$, filling all entries with `VoxelKind::Air` [S1, unofficial].
3.  **Apply Base Terrain Logic:** Evaluate the chunk's vertical position $C_y$.
    *   If $C_y = 0$ (the base level), iterate through all horizontal coordinates $x \in [0, 31]$ and $z \in [0, 31]$.
    *   Set `voxels[0][z][x]` to `VoxelKind::Dirt` (or the designated base material) [S1, unofficial].
    *   If $C_y \neq 0$, leave the voxels as `Air` (or apply other base logic if defined by higher-level systems) [S1, unofficial].
4.  **Store Chunk:** Insert the new chunk object (containing the initialized `voxels` array) into the world's chunk map keyed by $C$ [S1, unofficial].
5.  **Render Distance Management:** To ensure the world is populated around the viewer, calculate the camera's current chunk position $C_{cam}$ using floor division of the camera's world position by the chunk size (32) [S1, unofficial]. Iterate through a spherical or cubic radius $R$ around $C_{cam}$ and invoke the generation step for each chunk position within that radius [S1, unofficial].

**Pseudocode:**
```python
def get_or_create_chunk(world: World, chunk_pos: Vec3i) -> Chunk:
    # Step 1: Check if chunk exists
    if chunk_pos in world.chunks:
        return world.chunks[chunk_pos]
    
    # Step 2: Initialize 3D array [Y][Z][X] = 32x32x32
    # Using a list of lists of lists for clarity, though a flat array is more efficient
    voxels = [[[VoxelKind.Air for _ in range(32)] for _ in range(32)] for _ in range(32)]
    
    # Step 3: Apply Base Terrain Logic
    # Base terrain is a flat platform at Y=0
    if chunk_pos.y == 0:
        for z in range(32):
            for x in range(32):
                voxels[0][z][x] = VoxelKind.Dirt
    
    # Step 4: Store Chunk
    chunk = Chunk(mesh=None, voxels=voxels)
    world.chunks[chunk_pos] = chunk
    
    return chunk

def update_render_distance(world: World, camera_pos: Vec3f, radius: int = 4):
    # Step 5: Calculate camera chunk position
    # Floor division to find the chunk index containing the camera
    chunk_size = 32
    cam_chunk_x = floor(camera_pos.x / chunk_size)
    cam_chunk_y = floor(camera_pos.y / chunk_size)
    cam_chunk_z = floor(camera_pos.z / chunk_size)
    
    # Iterate through chunks in a cubic radius around the camera
    for dy in range(-radius, radius + 1):
        for dz in range(-radius, radius + 1):
            for dx in range(-radius, radius + 1):
                target_chunk_pos = Vec3i(
                    cam_chunk_x + dx,
                    cam_chunk_y + dy,
                    cam_chunk_z + dz
                )
                get_or_create_chunk(world, target_chunk_pos)
```

**Parameters:**
*   `chunk_size`: The dimension of a chunk in voxels (typically 32) [S1, unofficial].
*   `render_radius`: The number of chunks to generate around the camera (e.g., 4) [S1, unofficial].
*   `base_y`: The Y-level where the base terrain is generated (typically 0) [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** Chunk position calculation must use floor division (or equivalent integer truncation towards negative infinity) to correctly map floating-point camera coordinates to integer chunk indices [S1, unofficial].
*   **Boundaries:** The base terrain logic only applies to $C_y=0$. Chunks above or below this level remain empty (Air) unless extended by other methods like [Procedural Voxel World Generation](3891-procedural-voxel-world-generation.md) [S1, unofficial].
*   **Degenerate Input:** If the camera is exactly on a chunk boundary, floor division ensures consistent chunk assignment, preventing gaps or overlaps in generation [S1, unofficial].

## Subtopics

### [Procedural Terrain Heightmap Generation](1850-procedural-terrain-heightmap-generation.md)
Procedural Terrain Heightmap Generation creates voxel terrain chunks by sampling a 2D noise function to determine column heights, then filling solid blocks from a base level up to the computed height for each $(x,z)$ position within the chunk. It solves the problem of creating deterministic, pseudo-random terrain geometry by leveraging the property that a fixed input yields the same output, allowing terrain data to be preserved across frames without change. It sets itself apart from [Procedural Terrain Feature Generation](2572-procedural-terrain-feature-generation.md) by focusing on continuous height variation rather than discrete feature placement, and from [Heightmap generation via circular displacements](5186-heightmap-generation-via-circular-displacements.md) by using gradient-based noise functions rather than radial displacement patterns.

### [Voxel Evaluation with AABB Culling](2415-voxel-evaluation-with-aabb-culling.md)
Voxel Evaluation with AABB Culling is a GPU-accelerated technique for computing Signed Distance Function (SDF) values for a chunk's voxel grid by restricting computation to voxels intersecting active SDF primitives. It solves the problem of unnecessary GPU computation for voxels far from any terrain geometry.

### [Procedural Cave Generation](2579-procedural-cave-generation.md)
Procedural cave generation creates subsurface voids in voxel terrain using either subtractive particle tracing or threshold-based noise filtering. Unlike [Simplex Noise Chunk Generation](5016-simplex-noise-chunk-generation.md) which generates the base terrain, this method operates as a post-processing or layered feature to carve out complex, organic underground structures. It differs from [Procedural Object Generation](5028-procedural-object-generation.md) by focusing on large-scale, continuous erosion-like voids rather than discrete static meshes.

### [Procedural Voxel World Generation](3891-procedural-voxel-world-generation.md)
Procedural Voxel World Generation is a method for determining the block type at any given 3D integer coordinate in a voxel grid based on height, noise functions, and quality settings, supporting terrain, caves, trees, clouds, and emissive blocks. It differs from [Procedural Terrain Heightmap Generation](1850-procedural-terrain-heightmap-generation.md) by not only computing the surface height but also assigning specific block IDs (grass, dirt, stone, wood, leaves) and handling volumetric features like caves and trees within the same evaluation logic. It builds on [Chunk Generation with Base Terrain](1110-chunk-generation-with-base-terrain.md) by providing the detailed voxel-level content for the chunks generated by that parent method.

### [Chunk-Based Voxel Terrain Generation](4140-chunk-based-voxel-terrain-generation.md)
Chunk-Based Voxel Terrain Generation is a procedural technique that divides a 3D world into fixed-size cubic chunks, populating each with voxel data via multi-octave noise sampling and biome logic, then extracting visible faces for meshing. It differs from raymarching or marching cubes by explicitly generating a dense 3D voxel grid per chunk before mesh extraction, rather than computing surfaces via implicit functions or ray traversal.

### [Spiral Chunk Generation](4271-spiral-chunk-generation.md)
Spiral Chunk Generation produces a queue of 3D chunk positions in a spiral pattern to drive procedural octree and mesh generation. It differs from sibling methods like [Simplex Noise Chunk Generation](5016-simplex-noise-chunk-generation.md) by decoupling spatial traversal order from noise evaluation, ensuring chunks are generated in a contiguous spiral sequence rather than arbitrary spatial locality, which aids in progressive loading and memory management.

### [Simplex Noise Chunk Generation](5016-simplex-noise-chunk-generation.md)
Generates a voxel chunk's geometry and data using a 3D simplex noise function to determine voxel presence/height, allocating vertex and index buffers for rendering. It differs from heightmap-based siblings by evaluating noise in full 3D space to create volumetric terrain rather than surface-only heightmaps, and from cave generation by using a single scalar threshold for solid vs. empty space rather than complex noise blending.

### [Procedural Object Generation](5028-procedural-object-generation.md)
Constructs a basic rectangular house with a floor, roof, walls, a door on a specified side, and supporting legs extending down to solid ground. It differs from sibling methods like [Procedural Terrain Heightmap Generation](1850-procedural-terrain-heightmap-generation.md) by placing discrete, structured architectural primitives rather than continuous terrain surfaces, and from [Procedural Cave Generation](2579-procedural-cave-generation.md) by generating enclosed, man-made geometry rather than voids.

### Procedural Arch Generation
A procedural method to generate arches by sweeping a sphere along a cubic Bézier spline. It uses tapering parameters to simulate greater erosion towards the middle of the arch [S2].
**Steps:**
1.  Define the cubic Bézier spline using four control points [S2].
2.  For each step $t$ of the sweep, calculate the radius using tapering parameters $T_i$ at each end of the arch [S2].
**Formulas:**
Calculate tapering parameter $T_i$ for each end $i$:
$$T_i = r \cdot M_i \cdot (1 - I_i^{E_i})$$
where $M_i$ is the radius multiplier, $E_i$ is the exponent, and $I_i$ is the interpolant defining where tapering occurs [S2].
Calculate the total radius:
$$\text{radius} = r + T_0 + T_1$$
Compute the delta value $D_{Arch}(V, P)$ for voxel $V$ and position $P$ (voxel position after radius application):
$$D_{Arch}(V, P) = \begin{cases} 1, & \text{if } \|P - V\| < \text{radius} \\ 0, & \text{otherwise} \end{cases}$$
**Parameters:**
*   $M_i$: Radius multipliers for optional tapering at each end of the arch [S2].
*   $E_i$: Exponents for optional tapering at each end of the arch [S2].
*   $I_i$: Interpolants defining where the tapering occurs at each end of the arch [S2].
*   $r$: Base radius of the sphere being swept [S2].

## Operating characteristics
*   **Time Complexity:** $O(N)$ per chunk, where $N$ is the number of voxels in the chunk ($32^3 = 32,768$ for standard chunks), as each voxel must be initialized and potentially set [S1, unofficial].
*   **Memory Complexity:** $O(N)$ per chunk to store the voxel data [S1, unofficial].
*   **Performance:** Generating a single flat platform chunk is computationally inexpensive, dominated by memory allocation and initialization [S1, unofficial]. The cost scales linearly with the render distance radius $R$, requiring the generation of $(2R+1)^3$ chunks [S1, unofficial].
*   **Strengths:** Simple to implement; deterministic; provides a stable foundation for more complex procedural generation [S1, unofficial].
*   **Limitations:** Lacks organic variation on its own; requires integration with noise functions or other methods to create interesting terrain [S1, unofficial].
*   **When to use:** When a simple, predictable base world is needed, or as a starting point for more complex procedural systems [S1, unofficial].
*   **When not to use:** When organic, non-repetitive terrain is required without additional noise-based modifications [S1, unofficial].

## Background
Chunk Generation with Base Terrain is a fundamental technique in voxel engine development, often introduced as the first step in procedural world generation [S1, unofficial]. It originates from the need to manage large, infinite worlds by dividing them into manageable, fixed-size units (chunks) [S1, unofficial]. The "base terrain" concept, such as a flat platform, provides a simple, deterministic starting state that can be extended by higher-level procedural systems [S1, unofficial]. This approach is widely used in educational tutorials and early-stage voxel engine implementations due to its simplicity and ease of integration with mesh generation pipelines [S1, unofficial].
