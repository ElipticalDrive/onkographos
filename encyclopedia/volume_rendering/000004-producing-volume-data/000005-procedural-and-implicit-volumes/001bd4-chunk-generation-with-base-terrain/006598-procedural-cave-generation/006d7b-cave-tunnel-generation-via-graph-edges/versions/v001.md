# Cave Tunnel Generation via Graph Edges

Also called: Graph-based Cave Tunnel Generation

## Overview
This method generates cave tunnel networks by instantiating pre-defined tunnel prefabs along the edges of a graph structure, serving as the primary structural component of procedural cave systems. It differs from the parent [Procedural Cave Generation](2579-procedural-cave-generation.md) by using a constructive, graph-driven approach rather than a subtractive, particle-tracing method. While particle tracing carves voids from solid terrain, this method places specific geometric assets (tunnels) to define the cave's topology, ensuring consistent structural integrity and aesthetic control through prefabs.

## How it works
The method constructs a cave network by mapping edges to tunnel instances, processing them in parallel, and merging their geometry into a global cave map. It relies on a height map for surface alignment and a prefab manager for asset instantiation.

**Inputs:**
- `cavePrefabManager`: Manages available tunnel and room prefabs.
- `worldSize`: Dimensions of the world volume.
- `heightMap`: A data structure providing surface elevation $H(x, z)$ for any world coordinate $(x, z)$.
- `seed`: An integer seed for random number generation, derived from the world seed and size.
- `caveGraph`: A graph data structure where nodes represent potential cave locations and edges represent tunnel connections.

**Outputs:**
- `cavemap`: A global data structure storing the final voxel or block data for the cave network.
- `localMinimas`: A set of coordinates representing local minima in the terrain, used for further processing or entity spawning.

**Data Structures:**
- `CaveTunnel`: An instance representing a single tunnel segment. It contains:
  - `edge`: The graph edge defining start and end points.
  - `localMinimas`: A set of coordinates specific to this tunnel's generation.
  - `blocks`: The voxel data generated by the tunnel.
- `Graph`: Contains a list of `Edges`. Each edge likely holds start and end coordinates.

**Parameters:**
- `parallelism_degree`: The number of sub-lists to split the edge list into for parallel processing. Default value: 6 [S1, unofficial].
- `seed`: Derived as `worldBuilder.Seed + worldSize` [S1, unofficial].

**Steps:**
1. **Graph Construction**: Construct the `caveGraph` from the `cavePrefabManager.Prefabs` and `worldSize` [S1, unofficial].
2. **Edge Partitioning**: Split the list of edges from `caveGraph.Edges` into `parallelism_degree` sub-lists using `CaveUtils.SplitList` [S1, unofficial].
3. **Parallel Tunnel Generation**: Iterate over each sub-list using parallel tasks (e.g., `Parallel.ForEach` or `Task`) [S1, unofficial]:
   a. For each `edge` in the sub-list, instantiate a `CaveTunnel` object:
      $$ \text{tunnel} = \text{new CaveTunnel}(edge, \text{cavePrefabManager}, \text{heightMap}, \text{worldSize}, \text{seed}) $$
   b. Add the generated `tunnel` to the global `cavemap` via `cavemap.AddTunnel(tunnel)` [S1, unofficial].
   c. Update the global set of local minima. This operation requires synchronization:
      ```python
      lock(lockObject):
          localMinimas.union_with(tunnel.localMinimas)
      ```
      [S1, unofficial]

**Pseudocode:**
```python
def generate_cave_tunnels(cavePrefabManager, worldSize, heightMap, seed):
    # Step 1: Construct graph
    caveGraph = Graph(cavePrefabManager.prefabs, worldSize)
    
    # Step 2: Split edges for parallelism
    parallelism_degree = 6
    sub_lists = CaveUtils.split_list(caveGraph.edges, parallelism_degree)
    
    # Global state
    cavemap = CaveMap()
    local_minimas = set()
    lock_object = Lock()
    
    # Step 3: Parallel processing
    def process_sub_list(edges):
        for edge in edges:
            # Instantiate tunnel
            tunnel = CaveTunnel(
                edge=edge,
                prefab_manager=cavePrefabManager,
                height_map=heightMap,
                world_size=worldSize,
                seed=seed
            )
            
            # Add to global map
            cavemap.add_tunnel(tunnel)
            
            # Update local minima with synchronization
            with lock_object:
                local_minimas.union_update(tunnel.local_minimas)

    # Execute parallel tasks
    for sub_list in sub_lists:
        # Assuming a parallel execution context like ThreadPool or Task
        process_sub_list(sub_list)

    return cavemap, local_minimas
```

**Edge Cases and Pitfalls:**
- **Concurrency**: Access to `localMinimas` and potentially `cavemap` (if `AddTunnel` is not thread-safe) requires synchronization. The implementation uses a `lock` block around `localMinimas.UnionWith` [S1, unofficial].
- **Height Map Access**: The tunnel generation depends on `heightMap`. If the height map is not accessible or consistent across threads, race conditions or incorrect placement may occur [S1, unofficial].

## Subtopics

### Natural Entrance Generation
A method to generate natural cave entrances connecting the cave network to the surface, based on specific prefabs marked as natural entrances. It iterates over prefabs where `prefab.isNaturalEntrance` is true. For each such prefab, it calculates the center position as `prefab.position + Vector3i.one`. It then creates entrance tunnel blocks using the height map via `CaveTunnel.CreateNaturalEntrance(center, heightMap)`. These blocks are added to the cave map, and a rope is set at the center position using `cavemap.SetRope(center)` [S1, unofficial].

### Cave Room Generation
A method to generate static cave rooms defined by prefabs, executed in a separate task before or during tunnel generation. It iterates over `cavePrefabManager.CaveRooms`. For each room, it retrieves its blocks and adds them to the cave map with a flag indicating it is a room (`roomBlock.isRoom = true`). The number of cave rooms spawned is fixed at 1000, controlled by `cavePrefabManager.SpawnCaveRooms(1000, random, heightMap)` [S1, unofficial].

## Operating characteristics
- **Time Complexity**: Linear with respect to the number of edges in the graph, $O(E)$, where $E$ is the number of edges. Parallelism reduces wall-clock time by a factor related to the number of cores, up to the parallelism degree (6) [S1, unofficial].
- **Memory Complexity**: Linear with respect to the number of edges and the size of the prefabs. Each tunnel instance stores its blocks and local minima [S1, unofficial].
- **Strengths**: Provides structured, predictable cave layouts. Prefab-based generation allows for high-fidelity visual details. Parallel processing enables efficient generation of large cave networks [S1, unofficial].
- **Limitations**: Relies heavily on pre-defined prefabs, limiting organic variation compared to pure procedural carving. Concurrency requires careful synchronization [S1, unofficial].
- **When to use**: When a structured, graph-based cave network is desired, particularly in games or simulations where performance and visual consistency are prioritized over purely organic, noise-driven shapes [S1, unofficial].

## Background
This method is part of the procedural cave generation system in the game 7 Days to Die, specifically implemented in the unofficial modding community repository [S1, unofficial]. It represents a shift from purely noise-based or particle-based cave generation to a graph-driven approach, allowing for more controlled and interconnected cave systems. The implementation details are derived from the `7D2D-Procedural-Caves` repository [S1, unofficial].
