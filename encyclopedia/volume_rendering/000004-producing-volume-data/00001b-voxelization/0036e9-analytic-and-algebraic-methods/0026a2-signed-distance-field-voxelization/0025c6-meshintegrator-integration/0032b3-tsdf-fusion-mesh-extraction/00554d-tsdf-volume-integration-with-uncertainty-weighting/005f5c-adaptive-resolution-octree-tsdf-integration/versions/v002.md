# Adaptive-resolution Octree TSDF Integration

Also called: Adaptive-resolution octree-based volumetric SLAM, KinectFusion supereight adaptation

## Overview
A volumetric SLAM pipeline that integrates and renders depth images at an adaptive level of detail to address aliasing, reconstruction quality, and efficiency simultaneously [S1]. It differs from fixed-resolution grids by dynamically selecting the integration scale based on the effective sensor resolution relative to the distance from the scene, and from other octree methods by using a specific mipmapped block structure that balances multi-scale representation with spatial locality [S1].

## How it works
**Inputs and Outputs:**
- **Inputs:** Current depth map $D_k$ from the sensor, previous synthetic view $D_{k-1}$, camera intrinsics, and the current TSDF octree volume [S1].
- **Outputs:** Updated TSDF octree volume, camera pose estimate, and rendered depth map for visualization/tracking [S1].

**Data Structures:**
The volume is represented as an octree using a specific block structure to optimize memory and access patterns [S1]:
- **Block Storage:** An unordered set of voxel blocks stored in a contiguous, dynamically grown array, indexed via a pointer-based tree structure [S1]. Blocks are allocated at the deepest level (leaves) of the tree, which corresponds to the maximum resolution [S1].
- **Voxel Block Internal Structure:** Each block contains a mipmapped representation with aggregation factors [S1]. The finest level consists of $8^3$ voxels, followed by contiguous blocks of $4^3$ and $2^3$ voxels [S1]. This structure is equivalent to a full 3-level octree per block without pointer overhead, ensuring spatial locality [S1].
- **Memory Overhead:** Compared to single-resolution blocks, this mipmapped structure implies only a 14% increase in memory footprint [S1].

**Numbered Steps:**
The pipeline operates in a closed loop with three stages [S1]:
1. **Tracking:** Estimate camera egomotion by aligning the most recent depth map $D_k$ against a synthetic view $D_{k-1}$ obtained at the previous time step using a variant of Iterative Closest Point (ICP) with point-to-plane distance and projective data-association [S1].
2. **Integration:** Fuse sensor data into the volume by dynamically selecting the level of detail (LOD) at which data is fused based on the effective sensor resolution relative to the distance from the scene [S1]. After fusion, the hierarchy of voxels is maintained consistent across octree levels [S1].
3. **Rendering:** Ray-cast the volume from the most recent camera position and extract surface points at the zero-crossing of the TSDF function [S1]. The appropriate interpolation scale is selected depending on the distance from the camera to exploit multi-resolution information [S1].

**Formulas and Parameters:**
- **Effective Sensor Resolution:** The integration scale is selected based on the effective sensor resolution given the distance from the observed scene [S1]. The specific formula for calculating this resolution is not provided in the sources [S1].
- **TSDF Representation:** The world is discretized in a grid where each voxel holds the distance from the closest surface [S1].
- **Aggregation Factors:** The block structure uses aggregation factors corresponding to $8^3$, $4^3$, and $2^3$ voxels [S1].

**Pseudocode:**
```python
def adaptive_resolution_octree_tsdf_integration(depth_map_k, intrinsics, tsdf_octree, previous_synthetic_view):
    # Stage 1: Tracking
    # Align D_k against D_{k-1} using ICP with point-to-plane distance and projective data-association
    current_pose = icp_point_to_plane_align(depth_map_k, previous_synthetic_view, intrinsics)
    
    # Stage 2: Integration
    # Fuse sensor data at dynamically selected LOD, maintain hierarchy consistency
    updated_octree = integrate_depth_map(depth_map_k, current_pose, intrinsics, tsdf_octree)
    
    # Stage 3: Rendering
    # Ray-cast volume, extract zero-crossing, select interpolation scale by distance
    rendered_depth = render_volume(updated_octree, current_pose, intrinsics)
    
    return updated_octree, current_pose, rendered_depth

def icp_point_to_plane_align(depth_map, reference_view, intrinsics):
    # Convert depth maps to point clouds
    points_k = depth_to_point_cloud(depth_map, intrinsics)
    points_k_minus_1 = depth_to_point_cloud(reference_view, intrinsics)
    # Projective data-association to find correspondences
    correspondences = projective_associate(points_k, points_k_minus_1)
    # Solve for camera pose minimizing point-to-plane distance
    pose = solve_rigid_transform(points_k, points_k_minus_1, correspondences)
    return pose

def depth_to_point_cloud(depth_map, intrinsics):
    points = []
    for y in range(depth_map.height):
        for x in range(depth_map.width):
            z = depth_map[y, x]
            if z > 0:
                u, v = x, y
                # Unproject pixel to 3D using pinhole camera model
                x3d = (u - intrinsics.cx) * z / intrinsics.fx
                y3d = (v - intrinsics.cy) * z / intrinsics.fy
                points.append([x3d, y3d, z])
    return points

def projective_associate(points_src, points_tgt):
    # Associate each source point to nearest target point in projected space
    correspondences = []
    for p in points_src:
        closest = find_nearest_neighbor(p, points_tgt)
        correspondences.append((p, closest))
    return correspondences

def solve_rigid_transform(src_pts, tgt_pts, correspondences):
    # Standard least-squares solution for point-to-plane ICP
    # Returns 4x4 transformation matrix
    return compute_icp_transform(src_pts, tgt_pts, correspondences)

def integrate_depth_map(depth_map, pose, intrinsics, octree):
    points = depth_to_point_cloud(depth_map, intrinsics)
    # Transform to world coordinates
    world_points = transform_points(points, pose)
    for p in world_points:
        # Select LOD based on distance from camera
        dist = vector_length(p - pose.origin)
        lod_level = select_lod_level(dist)
        # Insert point into octree at selected LOD
        octree.insert(p, lod_level)
    # Maintain hierarchy consistency across octree levels
    octree.propagate_hierarchy()
    return octree

def select_lod_level(distance):
    # Select integration scale based on effective sensor resolution relative to distance
    # Not given in the sources. [G] Returns scale index 0 (8^3), 1 (4^3), or 2 (2^3)
    if distance < 1.0: return 0
    elif distance < 2.0: return 1
    else: return 2

def render_volume(octree, pose, intrinsics):
    depth_map = zeros(octree.image_height, octree.image_width)
    for v in range(octree.image_height):
        for u in range(octree.image_width):
            # Construct ray from camera center through pixel
            ray_origin = pose.origin
            ray_dir = normalize(unproject_pixel(u, v, 1.0, intrinsics) - ray_origin)
            # Ray-cast through octree, selecting interpolation scale by distance
            t_hit = cast_ray_through_octree(octree, ray_origin, ray_dir)
            if t_hit is not None:
                surface_point = ray_origin + t_hit * ray_dir
                # Extract surface point at zero-crossing of TSDF
                depth_val = extract_zero_crossing(octree, surface_point, ray_dir)
                depth_map[v, u] = depth_val
    return depth_map

def cast_ray_through_octree(octree, origin, direction):
    # Standard octree ray traversal
    return traverse_octree_ray(octree, origin, direction)

def extract_zero_crossing(octree, point, ray_direction):
    # Find TSDF value of zero along ray direction
    # [G] Linear interpolation between voxel centers along ray
    return point.z
```

**Edge Cases and Pitfalls:**
- **Aliasing Artifacts:** Fusing data at a uniform scale can cause aliasing artifacts due to resolution mismatch between the map and sensor data, degrading map quality and losing fine details from close-up views when observed from greater distances [S1].
- **Loss of Multi-scale Representation:** Aggregating bottom levels of the tree into contiguous blocks (a common solution) causes the multi-scale representation of the bottom levels to be lost [S1]. This method mitigates this by storing mipmapped representations contiguously within blocks [S1].

## Operating characteristics
- **Time Complexity:** The method achieves up to six-fold execution time speed-ups compared to single resolution grids [S1].
- **Memory Complexity:** The mipmapped block structure implies only a 14% increase in memory footprint compared to single resolution blocks [S1].
- **Strengths:** Significantly improved reconstruction quality, preservation of fine details (e.g., mug handles, keyboard keys), and improved runtime [S1]. It addresses aliasing issues and efficiency simultaneously [S1].
- **Limitations:** The specific limits are not detailed beyond the comparison to other methods [S1]. The method is designed for real-time settings such as augmented/virtual reality or mobile robotics [S1].
- **When to use:** When real-time dense reconstruction is required, and there is a need to handle varying distances to the scene without aliasing artifacts [S1]. It is suitable for environments where fine details are important and the camera moves at varying distances from the scene [S1].
- **When not to use:** If memory is extremely constrained and the 14% overhead is unacceptable, or if the scene is static and offline processing is allowed, other methods might be more appropriate [S1]. The method is specifically designed for volumetric SLAM pipelines [S1].

## Background
- **Origin:** The method was introduced by Emanuele Vespa, Nils Funk, Stefan Leutenegger, and Paul H. J. Kelly from Imperial College London [S1].
- **Paper:** "Adaptive-resolution octree-based volumetric SLAM" [S1].
- **History:** It is an extension of the hierarchical representation of [21] (supereight) to support queries at any level of detail [S1]. It was released as an open-source extension to supereight [S1].
- **Usage:** Used as an open-source extension to supereight [21] [S1]. It is applicable to dense Simultaneous Localisation and Mapping (SLAM) systems, particularly in real-time settings like augmented/virtual reality or mobile robotics [S1].
