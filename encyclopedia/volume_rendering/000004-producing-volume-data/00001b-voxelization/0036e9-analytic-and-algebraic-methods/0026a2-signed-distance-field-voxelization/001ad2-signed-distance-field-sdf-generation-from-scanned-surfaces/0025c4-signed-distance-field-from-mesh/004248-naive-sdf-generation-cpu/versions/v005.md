# Naive SDF Generation (CPU)
Also called: Brute-force SDF generation

## Overview
Naive SDF Generation (CPU) computes the Signed Distance Field (SDF) for a triangular mesh by explicitly evaluating the Euclidean distance from every voxel center to the mesh surface on the CPU [S1, unofficial]. It solves the problem of creating a volumetric distance representation for ray marching or volume rendering by iterating through all triangles for every sample point [S1, unofficial]. Unlike [Explicit Surface to TSDF Conversion](2615-explicit-surface-to-tsdf-conversion.md), which relies on volume integration or ray casting from virtual cameras, or [Sparse VDB SDF Generation](4498-sparse-vdb-sdf-generation.md), which uses hierarchical data structures for efficiency, this method performs a direct geometric query [G]. It differs from [GPU-based SDF Generation](10690-gpu-based-sdf-generation.md) by executing the distance calculations sequentially or with limited CPU threading rather than leveraging massive parallelism in shaders [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A triangular mesh defined by a vertex buffer, an index buffer, and a world transformation matrix [S1, unofficial].
- Output: A 3D grid (volume texture) where each voxel stores the signed Euclidean distance to the mesh surface [S1, unofficial].

**Data Structures:**
- **Triangle List:** A list of triangles, where each triangle is defined by three vertices $(v_0, v_1, v_2)$ and a precomputed normal $\mathbf{n}$ [S1, unofficial].
- **Sample Grid:** A 3D array of points covering the bounding volume of interest [S1, unofficial].

**Steps:**
1. **Transform Vertices:** Extract all vertices from the geometry and transform them using the mesh's world matrix to match their actual location in world space [S1, unofficial].
2. **Generate Triangles:** Create a list of triangles from the index and vertex buffer data [S1, unofficial].
3. **Compute Normals:** Calculate the normal for each triangle based on the clockwise arrangement of its edges to determine inside/outside orientation [S1, unofficial].
4. **Iterate Samples:** For each sample point $\mathbf{p}$ in the grid:
    a. Initialize `min_sq_dist` to infinity and `closest_normal` to zero [S1, unofficial].
    b. Iterate through all triangles in the mesh [S1, unofficial].
    c. Compute the squared distance from $\mathbf{p}$ to the current triangle using a point-to-triangle distance function (e.g., 'Triangle Unsigned') [S1, unofficial].
    d. If the computed squared distance is less than `min_sq_dist`, update `min_sq_dist` and store the triangle's normal as `closest_normal` [S1, unofficial].
5. **Determine Sign:** Calculate the dot product between the vector from the closest point on the triangle to $\mathbf{p}$ and `closest_normal` [S1, unofficial]. If the dot product indicates the point is on the opposite direction of the normal, the point is outside; otherwise, it is inside [S1, unofficial].
6. **Compute Final Distance:** Calculate the signed Euclidean distance $SDF$ using the formula:
   $$ SDF = \sqrt{|d^2|} \times \text{sign}(d^2) $$
   where $d^2$ is the squared distance to the closest triangle, and $\text{sign}(d^2)$ is $-1$ if inside, $1$ if outside [S1, unofficial].

**Pseudocode:**
```python
def compute_naive_sdf(mesh, grid_points):
    # Step 1: Transform vertices using world matrix
    transformed_vertices = [transform(v, mesh.world_matrix) for v in mesh.vertices]
    # Step 2 & 3: Generate triangles with normals from clockwise edge arrangement
    triangles = []
    for i in range(0, len(mesh.indices), 3):
        v0 = transformed_vertices[mesh.indices[i]]
        v1 = transformed_vertices[mesh.indices[i+1]]
        v2 = transformed_vertices[mesh.indices[i+2]]
        normal = normalize(cross(v1 - v0, v2 - v0))
        triangles.append((v0, v1, v2, normal))

    results = []
    for p in grid_points:
        min_sq_dist = float('inf')
        closest_normal = None
        closest_point = None

        # Step 4: Iterate all triangles to find minimum distance
        for (v0, v1, v2, n) in triangles:
            sq_dist, cp = point_to_triangle_sq_dist(p, v0, v1, v2)
            if sq_dist < min_sq_dist:
                min_sq_dist = sq_dist
                closest_normal = n
                closest_point = cp

        # Step 5: Determine sign via dot product of distance vector and normal
        vec_to_p = p - closest_point
        dot_product = dot(vec_to_p, closest_normal)
        # Negative dot product indicates inside, positive indicates outside [S1, unofficial]
        sign = -1.0 if dot_product < 0 else 1.0

        # Step 6: Compute final signed Euclidean distance
        distance = sqrt(abs(min_sq_dist)) * sign
        results.append(distance)
    return results

def point_to_triangle_sq_dist(p, v0, v1, v2):
    # [G] Standard point-to-triangle distance algorithm
    e1 = v1 - v0
    e2 = v2 - v0
    b = p - v0
    d1 = dot(e1, e1)
    d2 = dot(e1, e2)
    d3 = dot(e2, e2)
    d4 = dot(e1, b)
    d5 = dot(e2, b)
    denom = d1 * d3 - d2 * d2
    if denom == 0:
        u, v = 0.0, 0.0
    else:
        u = (d3 * d4 - d2 * d5) / denom
        v = (d1 * d5 - d2 * d4) / denom
    if u < 0.0:
        v = dot(b, e2) / d2 if d2 != 0 else 0.0
        u = 0.0
    elif v < 0.0:
        u = dot(b, e1) / d1 if d1 != 0 else 0.0
        v = 0.0
    elif u + v > 1.0:
        d6 = dot(e1, e1)
        d7 = dot(e2, e1)
        d8 = dot(b, e1)
        d9 = dot(e2, e2)
        d10 = dot(b, e2)
        denom = d6 * d9 - d7 * d7
        if denom == 0:
            u, v = 1.0, 0.0
        else:
            u = (d9 * (d7 - d8) + d10 * d7) / denom
            v = (d8 * d7 - d10 * d6) / denom
            if u < 0.0:
                u = 0.0
                v = 1.0 if d10 > 0 else 0.0
            elif v < 0.0:
                v = 0.0
                u = 1.0 if d8 > 0 else 0.0
            elif u + v > 1.0:
                u = 1.0
                v = 0.0
    else:
        u = max(0.0, min(1.0, u))
        v = max(0.0, min(1.0, v))
    closest = v0 + u * e1 + v * e2
    return dot(p - closest, p - closest), closest
```

**Parameters:**
- **Thread Count:** The number of CPU threads used to parallelize the sample iteration. Typical values range from 1 to the number of physical cores, with diminishing returns beyond 4 threads on the tested quad-core CPU [S1, unofficial].
- **Sampling Resolution:** The density of sample points. Decreasing the distance between sampling points by half increases computation cost by 8 times [S1, unofficial].

**Edge Cases and Pitfalls:**
- **High Computational Cost:** The naive approach checks every triangle for every sample point. For a mesh with 280,000 triangles, this results in significant latency [S1, unofficial].
- **Precision:** Floating-point precision errors may occur in the dot product sign determination for points very close to the surface [G].
- **Degenerate Input:** Triangles with zero area or collinear vertices may produce undefined normals or distances [G].

## Subtopics

### [GPU-based SDF Generation](10690-gpu-based-sdf-generation.md)
GPU-based SDF Generation is a technique to compute Signed Distance Fields (SDFs) for a mesh by uploading triangle vertex data to a texture and calculating distances in a pixel or compute shader, offering significant speedup over CPU-based methods. It solves the performance bottleneck of CPU voxelization by leveraging massive parallelism, enabling real-time or near-real-time SDF updates for animated characters. Unlike [Naive SDF Generation (CPU)](10688-naive-sdf-generation-cpu.md), which processes voxels sequentially or with limited threading, this method maps the distance calculation workload directly to the GPU's parallel cores, reducing generation time from seconds to milliseconds.

### [Mesh to SDF via Point Cloud](16282-mesh-to-sdf-via-point-cloud.md)
This method generates a Signed Distance Field (SDF) for a query set of points by first converting a triangular mesh into a discrete point cloud and then computing distances to that cloud. It solves the problem of creating volumetric distance data from polygonal surfaces without requiring complex analytic integration or GPU-based ray marching. It differs from analytic voxelization by relying on nearest-neighbor search in a point cloud, and from GPU-based generation by performing the heavy lifting on the CPU using KD-trees and batched processing.

### [CPU-based SDF Voxelization and Material Assignment](20352-cpu-based-sdf-voxelization-and-material-assignment.md)
This method populates 3D textures with Signed Distance Field (SDF) data and material properties by sampling an SDF surface on the CPU, handling time constraints via a loop, and committing the data to the GPU. It differs from synchronous approaches by allowing partial updates within a frame budget, and from GPU-based methods by performing the sampling logic on the host CPU. It builds on [Naive SDF Generation (CPU)](10688-naive-sdf-generation-cpu.md) by adding material assignment and time-bounded iteration.

## Operating characteristics
- **Time Complexity:** $O(N \cdot M)$, where $N$ is the number of sample points (voxels) and $M$ is the number of triangles in the mesh [G].
- **Memory Complexity:** $O(N)$ for storing the distance field, plus $O(M)$ for the mesh data [G].
- **Measured Performance:** On a quad-core CPU, generating an SDF for a large mesh (Sponza Atrium) took 30,744ms with 1 thread, 15,546ms with 2 threads, and 10,009ms with 8 threads (capped at 4 cores) [S1, unofficial]. High-resolution SDF generation for a large mesh took approximately 1.5 hours (5,636,817ms) with 4 threads [S1, unofficial].
- **Scaling:** Computation cost scales cubically with sampling resolution (halving voxel size increases cost by 8x) [S1, unofficial]. Scaling with thread count is approximately linear up to the number of physical cores, with diminishing returns beyond 4 threads on the tested quad-core CPU [S1, unofficial].
- **Strengths:** Simple to implement; does not require complex data structures like BVHs or KD-trees; works with any watertight mesh [G].
- **Limitations:** Extremely slow for high-resolution grids or complex meshes; does not scale well beyond CPU core counts; prohibitive for real-time applications without GPU acceleration [G].
- **When to use:** Low-resolution previews, static meshes with low triangle counts, or educational purposes [G].
- **When not to use:** High-resolution volume rendering, animated meshes, or real-time applications [G].
