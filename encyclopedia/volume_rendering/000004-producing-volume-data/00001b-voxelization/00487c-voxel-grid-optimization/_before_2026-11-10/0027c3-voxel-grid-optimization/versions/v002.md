# Voxel Grid Optimization

Also called: Voxelization Optimization (family)

## Overview
Voxel Grid Optimization encompasses techniques to reduce the computational cost, memory bandwidth, and storage requirements of generating and using voxel data from 3D geometry. It addresses the bottleneck of high draw call counts, redundant geometric transformations, and empty-space traversal during rasterization and raymarching. Unlike sibling methods that focus on the initial discretization (e.g., [Rasterization-based Voxelization](908-rasterization-based-voxelization.md)) or post-generation compression (e.g., [Binary Voxel RLE Encoding](1071-binary-voxel-rle-encoding.md)), this family focuses on pipeline efficiency, spatial culling, and structural simplification to accelerate rendering and processing.

## Shared principles
All methods in this family operate on the voxel grid generated by the parent [Voxelization](12-voxelization.md) process. They share the following mechanisms:
1.  **Spatial Culling**: Identifying and skipping computations for voxels or primitives that do not contribute to the final image or data structure, often using bounding volumes or heightmaps [S1, S2, unofficial].
2.  **Data Reduction**: Compressing or simplifying the voxel representation to reduce memory footprint and processing time, such as through run-length encoding or structural block detection [S1, S2, unofficial].
3.  **Pipeline Efficiency**: Optimizing the GPU or CPU pipeline during generation, such as through instancing, stream output caching, or LOD selection, to minimize overhead [S1, unofficial].

## Subtopics

### [3D Voxel Grid Smoothing](833-3d-voxel-grid-smoothing.md)
A post-processing step applied to a discrete 3D voxel grid to reduce noise or aliasing artifacts before isosurface extraction. It works by applying a separable 3D convolution using a 1D kernel of size 3 to average voxel values over a local neighborhood. Unlike [Binary Voxel RLE Encoding](1071-binary-voxel-rle-encoding.md) which focuses on storage compression, this method operates directly on the scalar values within the grid cells to produce a smoother field. Choose this when the input grid contains high-frequency noise that degrades downstream isosurface extraction quality.

### [Binary Voxel RLE Encoding](1071-binary-voxel-rle-encoding.md)
Compresses a 3D voxel grid into a binary stream using run-length encoding (RLE) to store occupancy data efficiently. It stores only voxels within the minimal bounding box of the mesh to reduce the output file size. The method packs runs of identical values into pairs of (value, count). Choose this when storage space is the primary constraint and the data is binary (occupied/empty).

### [Occupancy Voxel Creation](2628-occupancy-voxel-creation.md)
Converts a continuous density matrix into a discrete boolean occupancy mask and simplifies the geometry by identifying fully occupied 2x2x2 blocks. It differs from [3D Voxel Grid Smoothing](833-3d-voxel-grid-smoothing.md) by using hard thresholding and structural convolution rather than continuous filtering, and from [Binary Voxel RLE Encoding](1071-binary-voxel-rle-encoding.md) by producing a structural mask rather than a compressed bitstream. It serves as a preprocessing step to reduce voxel grid complexity for rendering or training. Choose this when the goal is to simplify geometry for collision detection or coarse-grained rendering.

### [Voxelization Optimization](3191-voxelization-optimization.md)
Refers to a collection of techniques designed to reduce the computational cost and memory bandwidth requirements of generating voxel data from 3D geometry, particularly in real-time applications. It addresses the bottleneck of high draw call counts and redundant geometric transformations during the rasterization of meshes into voxel grids. It is distinguished from its siblings by focusing on the *generation pipeline* efficiency (e.g., stream output, instancing, LOD selection) rather than post-generation data compression (like RLE) or structural simplification (like smoothing). Choose this when the bottleneck is the generation phase itself, especially for dynamic or high-poly meshes.

### [Bounding Volume Optimization](3583-bounding-volume-optimization.md)
Reduces the effective complexity of voxel data by trimming the voxel array dimensions to the minimal bounding box of the actual data, thereby eliminating empty space traversal during rendering. It also minimizes the computational cost of Signed Distance Field (SDF) evaluation by skipping calculations for objects that do not contribute to the minimal distance field. Unlike [3D Voxel Grid Smoothing](833-3d-voxel-grid-smoothing.md) which reduces noise, or [Binary Voxel RLE Encoding](1071-binary-voxel-rle-encoding.md) which compresses storage, this method focuses on spatial culling and array dimensionality reduction to prevent false positives and redundant computations. Choose this when the scene contains large empty spaces or when rendering sparse volumes.

#### Volume Buffer
- **Definition**: A volume data caching structure that encapsulates functionality, storage, and access similar to a Frame Buffer Object (FBO), but for 3D scalar data. It rasterizes primitives in 3D space and accumulates up to 1024 bits of arbitrary data per voxel [S1, unofficial].
- **Steps**: Generate the final volume by fusing three intermediate passes (one for each perpendicular sweep axis) into a single multi-buffer using the MAX blending operation. Disable face culling and z-test, and do not attach a z-buffer to the frame buffer object. Use the OpenGL extension for layered rendering, writing to `gl_Layer` in the geometry shader to render primitives to arbitrary volume texture layers [S1, unofficial].
- **Parameters**: Max bits per voxel: 1024 bits. Max render targets: 8 floating point render targets (MRTs), as 8 is the current maximum available number of MRTs [S1, unofficial].
- **Comparison**: Uses MAX blending for scalar data fusion instead of the OR operation used in binary voxelization [S1, unofficial].

#### Voxelization Projection Culling
- **Definition**: Optimizes multi-pass voxelization by skipping primitives whose precomputed dominant axis does not match the current projection direction, preventing redundant voxel writes [S2, unofficial].
- **Steps**: In the vertex shader, compute world position. If multi-pass mode is active, read the primitive's dominant axis from `triDominantAxis[vid / 3]`. Compare with `projDir.direction`. If they mismatch, skip the primitive (early return/continue implied) [S2, unofficial].
- **Parameters**: `kVoxelizationMultiPass = !kVoxelizationSinglePass` (compile-time flag controlling pass strategy) [S2, unofficial].
- **Layout**: `VoxelProjectionDir` struct: `uint direction;` (bound to buffer 2). `triDominantAxis` buffer: bound to buffer index 10 (`TRI_DOMINANT_BUFFER_BINDING_IDX`) [S2, unofficial].
- **Pitfall**: Vertex ID to triangle ID mapping uses integer division `vid / 3`, assuming contiguous triangle strips/arrays [S2, unofficial].

#### Bucket-based LBVH construction
- **Steps**: Groups voxels into buckets instead of using a uniform grid with fixed brick size [S3, unofficial].

## Background
Voxel grid optimization techniques have evolved alongside real-time rendering and volume visualization requirements. Early methods focused on simple occupancy grids, but as dynamic scenes and complex attributes became common, the need for efficient generation and culling grew. The "Volume Buffer" concept was introduced to allow multi-channel scalar data accumulation directly on the GPU, leveraging layered rendering extensions [S1, unofficial]. Bounding volume optimization and heightmap techniques are widely used in terrain and voxel-based games to manage large sparse volumes [S1, S3, unofficial]. Bucket-based constructions for Linear Bounding Volume Hierarchies (LBVH) represent a more recent approach to accelerating raymarching in sparse volumes [S3, unofficial].
