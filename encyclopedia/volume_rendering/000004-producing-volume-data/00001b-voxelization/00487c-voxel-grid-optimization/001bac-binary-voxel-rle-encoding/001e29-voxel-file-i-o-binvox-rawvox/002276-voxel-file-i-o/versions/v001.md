# Voxel File I/O

Also called: Output Format Handling, Voxel Export

## Overview
Voxel File I/O is the method for serializing and deserializing voxel grid data to and from persistent storage formats. It solves the problem of converting in-memory voxel representations (such as dense arrays or sparse structures) into standardized file formats for interchange, archiving, or loading into different rendering engines. Unlike the parent method [Voxel File I/O (binvox/rawvox)](1698-voxel-file-i-o-binvox-rawvox.md), which focuses on specific legacy binary formats, this method encompasses a broader set of ASCII, binary, and scientific data formats, including CSV, PLY, VTK, and custom binary layouts. It differs from sibling methods like [MagicaVoxel File Output](1752-magicavoxel-file-output.md) by supporting general-purpose scientific and geometric data structures rather than proprietary artistic voxel engines.

## How it works
The method handles multiple distinct formats, each with specific input requirements, data layouts, and serialization steps. The core inputs are the voxel dimensions ($D_x, D_y, D_z$), the voxel data array (typically `uint32` or `float32`), and optional metadata (such as phase labels or color values). The output is a byte stream written to a file handle.

### CSV Format
**Data Structure:** A text file where each line represents a single voxel coordinate and its associated scalar value.
**Steps:**
1. Write the header string: `"x,y,z,phase\n"`.
2. Iterate through the voxel grid in row-major order (x, then y, then z).
3. For each voxel at $(x, y, z)$ with phase value $P$, write the string: `"{x},{y},{z},{P}\n"`.

### PLY (Polygon File Format) ASCII
**Data Structure:** An ASCII text file describing a polygon mesh. For voxel visualization, voxels are often represented as vertices or points.
**Steps:**
1. Write the header:
   ```
   ply
   format ascii 1.0
   element vertex {vertex_count}
   property float x
   property float y
   property float z
   end_header
   ```
   Where `{vertex_count}` is the total number of active voxels or grid points.
2. For each voxel coordinate $(x, y, z)$, write: `"{x} {y} {z}\n"`.

### VTK (Visualization Toolkit) 3.0 ASCII POLYDATA
**Data Structure:** An ASCII file defining points and associated scalar data.
**Steps:**
1. Write the header:
   ```
   # vtk DataFile Version 3.0
   Voxel Data
   ASCII
   DATASET POLYDATA
   POINTS {point_count} float
   ```
2. Write point coordinates. For each voxel $(x, y, z)$, write: `"{x} {y} {z}\n"`.
3. Write scalar data header:
   ```
   SCALARS phase float 1
   SCALARS_LOOKUP_TABLE_NAME default
   LOOKUP_TABLE default
   ```
4. Write phase values. For each voxel, write the phase value $P$ followed by a newline: `"{P}\n"`.

### BIN (Binary Serialization)
**Data Structure:** A compact binary format using `bincode` serialization (common in Rust ecosystems) or raw binary packing.
**Steps:**
1. Serialize the voxel data structure using the specific binary encoder (e.g., `bincode`).
2. Write the resulting byte buffer to the file.
   *Note: Specific field layouts depend on the serialization schema definition, which is not standardized across all implementations.*

### PFM (Portable FloatMap) Parsing
**Definition:** Reads a PFM image file, handling endianness and color format (grayscale vs. RGB) [S2, unofficial].
**Steps:**
1. Read the header to determine the color format ('PF' for color, 'Pf' for grayscale) and image dimensions.
2. Parse the height and width from the header.
3. Read the pixel data, accounting for endianness if necessary.

### NRRD-like Volume I/O
**Definition:** Exports and imports volumes in a simple NRRD-like format consisting of two header lines followed by raw binary payload [S3, unofficial].
**Data Layout:**
- Line 1: Space-separated integers for width ($W$), height ($H$), and depth ($D$).
- Line 2: The string `"uint32"`.
- Remainder: Raw binary data of $W \times H \times D$ `uint32_t` values.

**Export Steps:**
1. Write `dim_x`, `dim_y`, `dim_z` separated by spaces and a newline.
2. Write `'uint32'` and a newline.
3. Write `m_data` as raw bytes:
   ```python
   fout.write(reinterpret_cast<char *>(m_data.data()), m_data.size() * sizeof(uint32_t))
   ```

**Import Steps:**
1. Read the first line to parse `dim_x`, `dim_y`, `dim_z`.
2. Read the second line and verify it equals `'uint32'`.
3. Resize `m_data` to `dim_x * dim_y * dim_z`.
4. Read raw bytes into `m_data`:
   ```python
   voxel_count = dim_x * dim_y * dim_z
   fin.read(reinterpret_cast<char *>(m_data.data()), static_cast<long>(voxel_count * sizeof(uint32_t)))
   ```
5. Check if the read operation was successful.

### ArrayMesh Byte Reader (Godot)

1. When reading byte values for ArrayMesh, narrow any listed value of `-1` to `255`, as implemented in Godot's `variant_parser.cpp:650` [S4, unofficial].

## Subtopics

### [Binvox File Parsing](2862-binvox-file-parsing.md)
Binvox File Parsing is the method for importing the binary voxel (binvox) file format into a contiguous array or a Sparse Voxel Octree (SVO) structure. It solves the problem of converting a legacy, run-length encoded (RLE) voxel representation into a format suitable for modern ray-casting or rasterization engines. Unlike raw voxel formats that store every voxel explicitly, binvox uses a compact binary RLE scheme, requiring specific handling to decompress the data correctly.

### [IMS File Format & Image Stack Class](3322-ims-file-format-image-stack-class.md)
The IMS file format and `ims_base` class provide a mechanism for persisting and managing 3D image stacks (volumes) with typed pixel storage and extensible metadata segments. It solves the problem of storing volumetric data where pixel types are fixed at compile time via templates and metadata is stored as typed binary segments. It differs from generic binary voxel formats by embedding a rigid 16-byte header, supporting memory-mapped loading on Windows, and using a chunked write strategy to handle large volumes without buffer overflow.

## Operating characteristics
Time and memory complexity depend heavily on the chosen format. ASCII formats (CSV, PLY, VTK) have higher I/O overhead and larger file sizes due to text encoding, but are human-readable and easy to debug. Binary formats (BIN, NRRD-like) offer compact storage and faster I/O speeds. The NRRD-like format provides a balance with its simple two-line header and raw binary payload, suitable for scientific data exchange. The PFM format is optimized for floating-point image data, handling endianness automatically. The ArrayMesh byte reader optimization is a minor constant-time operation for specific engine integration.

## Background
Voxel file I/O methods have evolved alongside voxelization techniques. Early methods relied on simple ASCII formats for debugging. As voxel data sizes grew, binary formats like BIN and specialized scientific formats like NRRD and PFM became necessary for efficient storage and interchange. The integration of voxel data into game engines (e.g., Godot's ArrayMesh) and scientific visualization tools (VTK) has driven the standardization of these I/O methods.
