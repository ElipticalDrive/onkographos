# Voxel File I/O

Also called: Output Format Handling, Voxel Export

## Overview
Voxel File I/O is the method for serializing and deserializing 3D voxel grids to and from persistent storage formats. It solves the problem of persisting volumetric data generated by voxelization or volume rendering pipelines for later use in rendering engines, analysis tools, or interchange between applications. Unlike [Voxel File I/O (binvox/rawvox)](1698-voxel-file-i-o-binvox-rawvox.md), which focuses on specific legacy binary formats, this method encompasses a broader range of serialization strategies including ASCII text formats (CSV, PLY, VTK) and custom binary structures, prioritizing flexibility and interoperability over strict adherence to a single proprietary standard.

## How it works
The method supports multiple output formats, each with distinct data layouts and serialization steps. The core abstraction involves mapping a 3D voxel grid (defined by dimensions $W \times H \times D$ and a coordinate origin) to a linear byte stream or text representation.

### Inputs and Outputs
- **Input**: A 3D voxel grid represented as a structured array or sparse structure, containing voxel values (e.g., phase, intensity, color) and spatial metadata (resolution, bounding box).
- **Output**: A file on disk in one of the supported formats (CSV, PLY, VTK, BIN, PFM, Binary Volume, or Voxel Interchange).

### Data Structures
The internal representation of the voxel data typically includes:
- `grid_dim`: Array of 3 integers $[W, H, D]$ representing the resolution in each axis.
- `voxels`: A 1D array or 3D array of voxel values. For binary formats, these are often packed into bytes or floats.
- `metadata`: Optional fields such as bounding box size, origin coordinates, or phase labels.

### Supported Formats and Steps

#### 1. CSV Format
Exports voxel data as comma-separated values, suitable for tabular processing.
1. Write header line: `"x,y,z,phase"`.
2. Iterate through all voxels $(x, y, z)$ in row-major order (x varying fastest, then y, then z).
3. For each voxel, write the line: `"{x},{y},{z},{phase}"`.

#### 2. PLY (Polygon File Format)
Exports voxel centers as vertices in ASCII PLY format.
1. Write ASCII header:
   ```
   ply
   format ascii 1.0
   element vertex {vertex_count}
   property float x
   property float y
   property float z
   end_header
   ```
2. Calculate `vertex_count` as the total number of voxels.
3. Iterate through all voxels.
4. For each voxel at $(x, y, z)$, write: `"{x} {y} {z}\n"`.

#### 3. VTK Legacy ASCII
Exports voxel data as a `UNSTRUCTURED_GRID` in VTK 3.0 ASCII format.
1. Write header:
   ```
   # vtk DataFile Version 3.0
   Voxel Grid
   ASCII
   DATASET UNSTRUCTURED_GRID
   ```
2. Write `POINTS {count} float`.
3. Write point coordinates for each voxel center.
4. Write `SCALARS phase float 1`.
5. Write `LOOKUP_TABLE default`.
6. Write scalar values for each voxel.

#### 4. Binary (BIN) Format
Uses a compact binary serialization scheme (bincode).
1. Serialize the voxel grid structure using a binary codec (e.g., `bincode` in Rust).
2. Write the resulting byte stream to the file.
3. This format is opaque to text editors but efficient for storage and loading.

#### 5. PFM (Portable FloatMap)
Reads or writes float maps, handling endianness and color format.
1. Read/Write header: `PF` (color) or `Pf` (grayscale), followed by width, height, and negative scale factor (for endianness).
2. Read/Write pixel data as 32-bit floats in row-major order.
3. Handle endianness conversion if the host machine differs from the file's endianness indicator.

#### 6. Binary Volume File Format
A custom binary format for storing volume data from image slices.
1. **Layout**:
   - First 12 bytes: Three `int32` values for `grid_dim[0]`, `grid_dim[1]`, `grid_dim[2]`.
   - Next 12 bytes: Three `float32` values for `bbox_size[0]`, `bbox_size[1]`, `bbox_size[2]`.
   - Remaining bytes: Voxel values as `float32` in row-major order (x fastest, then y, then z).
2. **Steps**:
   - Read input image slices sorted by filename.
   - Determine `grid_dim` from first image shape $(w, h)$ and number of slices $D$.
   - Calculate bounding box size:
     $$
     \begin{aligned}
     bbox\_size[0] &= BBOX\_SIZE\_X \\
     bbox\_size[1] &= \frac{BBOX\_SIZE\_X}{grid\_dim[0]} \times \frac{vol\_size[1]}{vol\_size[0]} \times grid\_dim[1] \\
     bbox\_size[2] &= \frac{BBOX\_SIZE\_X}{grid\_dim[0]} \times \frac{vol\_size[2]}{vol\_size[0]} \times grid\_dim[2]
     \end{aligned}
     $$
     where $BBOX\_SIZE\_X = 5.0$ [S4, unofficial].
   - Write `grid_dim` and `bbox_size` to file.
   - Write voxel values as `float32`.

#### 7. Voxel Interchange Format Serialization
Serializes a 3D voxel region into a flat 1D array with metadata for transport.
1. Initialize `length`, `width`, `depth`, and `start` coordinates.
2. Create an `Int8Array` (or equivalent byte array) of size `length * width * depth`.
3. Initialize `idx = 0`.
4. Loop `z` from `start[2]` to `depth`, `y` from `start[1]` to `height`, `x` from `start[0]` to `length`.
5. Inside the innermost loop, call `getVoxelDataFor(x+start[0], y+start[1], z+start[2])` and assign to `voxels[idx]`.
6. Increment `idx`.
7. Output structure:
   ```json
   {
     "voxels": [packed 1D array of voxels],
     "dimensions": [length, width, height],
     "position": [startX, startY, startZ]
   }
   ```
   [S5, unofficial]

### Pitfalls
- **Loop Bounds**: In Voxel Interchange Format, loop bounds may mix absolute world coordinates with relative dimensions, causing out-of-bounds access if not adapted to local chunk coordinates [S5, unofficial].
- **Endianness**: PFM and binary formats require careful handling of endianness, especially when transferring data between different hardware architectures [S2, unofficial].
- **Data Type Narrowing**: When reading byte arrays, values like -1 may need to be narrowed to 0-255 range for proper color/phase representation, as seen in Godot's ArrayMesh byte reader [S3, unofficial].

## Subtopics

### [Binvox File Parsing](2862-binvox-file-parsing.md)
Binvox File Parsing is the method for importing the binary voxel (binvox) file format into a contiguous array or a Sparse Voxel Octree (SVO) structure. It converts a legacy run-length encoded (RLE) voxel representation into a format suitable for modern ray-casting or rasterization engines [G]. Unlike raw voxel formats that store every voxel explicitly, binvox uses a compact binary RLE scheme, requiring specific handling to decompress the data correctly.

### [IMS File Format & Image Stack Class](3322-ims-file-format-image-stack-class.md)
The IMS file format and `ims_base` class provide a mechanism for persisting and managing 3D image stacks (volumes) with typed pixel storage and extensible metadata segments. It solves the problem of storing volumetric data where pixel types are fixed at compile time via templates and metadata is stored as typed binary segments. It differs from generic binary voxel formats by embedding a rigid 16-byte header, supporting memory-mapped loading on Windows, and using a chunked write strategy to handle large volumes without buffer overflow.

### [NRRD-like Volume I/O](4225-nrrd-like-volume-i-o.md)
Exports and imports volumes in a simple NRRD-like format consisting of two header lines followed by raw binary payload. It differs from [Binvox File Parsing](2862-binvox-file-parsing.md) by storing full 32-bit values rather than binary flags, and from [IMS File Format & Image Stack Class](3322-ims-file-format-image-stack-class.md) by using a single contiguous file rather than a directory of image stacks. It provides a minimal, non-standardized alternative to [VTK Legacy ASCII File Writing](6698-vtk-legacy-ascii-file-writing.md) and [VRDF File Format / VRDF Loader](6906-vrdf-file-format-vrdf-loader.md) by omitting metadata and using binary data for compactness.

### [VTK Legacy ASCII File Writing](6698-vtk-legacy-ascii-file-writing.md)
Exports voxel data to a legacy VTK ASCII `UNSTRUCTURED_GRID` file format, representing each voxel as a hexahedral cell with associated scalar fields. It differs from binary voxel formats (e.g., [Binvox File Parsing](2862-binvox-file-parsing.md)) by using human-readable text and explicit vertex definitions for every cell, prioritizing interoperability with legacy VTK-based viewers over storage efficiency.

### [VRDF File Format / VRDF Loader](6906-vrdf-file-format-vrdf-loader.md)
The VRDF (Volume Rendering Data Format) is a binary file format designed for storing 3D voxel grids alongside associated metadata and transfer functions. It solves the problem of interoperability between medical imaging pipelines and volume rendering engines by packaging geometry, intensity data, and rendering parameters into a single self-describing file. Unlike [Binvox File Parsing](2862-binvox-file-parsing.md), which is limited to binary occupancy grids, VRDF supports continuous floating-point data, multi-channel interleaved data (e.g., label and weight), and embedded JSON metadata. It builds on [Voxel File I/O](2786-voxel-file-i-o.md) by providing a structured schema for complex volume data rather than simple raw bytes.

### PFM File Parsing
Reads a PFM (Portable FloatMap) image file, handling endianness and color format [S2, unofficial]. It reads the header to determine color (PF/Pf) and dimensions, then reads the pixel data as floats, adjusting for endianness if necessary [S2, unofficial].

### ArrayMesh Byte Reader
Narrows a listed -1 to 255 in the ArrayMesh byte reader, as Godot does (variant_parser.cpp:650) [S3, unofficial]. This ensures that byte values are correctly mapped to the 0-255 range for color or phase representation.

### Binary Volume File Format
A binary file format for storing volume data generated from image slices, containing grid dimensions, bounding box size, and voxel values [S4, unofficial]. It reads slices from an input directory, sorted by filename, determines grid dimensions and bounding box size, and writes the data in a specific binary layout [S4, unofficial].

### Voxel Interchange Format Serialization
Serializes a 3D voxel region into a flat 1D array with metadata for transport or storage [S5, unofficial]. It initializes dimensions and start coordinates, loops through the voxel grid, and packs the data into a JSON-like structure with a 1D array of voxels, dimensions, and position [S5, unofficial].

## Operating characteristics
- **Time Complexity**: Linear with respect to the number of voxels $N = W \times H \times D$ for all formats, as each voxel must be visited at least once.
- **Memory Complexity**: Linear with respect to $N$ for storing the voxel grid in memory. Binary formats may require less disk space than ASCII formats due to lack of text overhead.
- **Performance**: Binary formats (BIN, Binary Volume) are faster to read/write than ASCII formats (CSV, PLY, VTK) due to reduced parsing overhead. PFM is efficient for float data but limited to 2D or simple 3D stacks.
- **Strengths**: Flexibility in format choice; support for both ASCII (human-readable) and binary (compact) formats; interoperability with various tools (VTK, PLY viewers, etc.).
- **Limitations**: ASCII formats are verbose and slow for large volumes; custom binary formats may lack widespread tool support; endianness issues can arise in cross-platform scenarios.
- **When to Use**: Use CSV/PLY/VTK for debugging and interoperability with standard tools. Use BIN/Binary Volume for efficient storage and loading in custom pipelines. Use PFM for float-based image stacks.

## Background
Voxel file I/O methods have evolved alongside volume rendering and 3D modeling tools. Early formats like PLY and VTK were designed for mesh data but adapted for voxel grids. Binary formats like binvox and custom formats (e.g., Binary Volume, VRDF) emerged to address the need for compact storage and efficient loading of large voxel datasets. The proliferation of 3D printing and medical imaging has driven the development of specialized formats like IMS and NRRD-like formats.
