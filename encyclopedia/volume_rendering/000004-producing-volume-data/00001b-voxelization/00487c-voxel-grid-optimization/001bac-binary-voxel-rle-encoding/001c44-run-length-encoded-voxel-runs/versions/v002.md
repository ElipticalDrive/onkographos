# Run-length encoded voxel runs


## Overview
A pre-processing optimization for volume rendering that compresses voxel runs via run-length encoding based on pre-classified opacities to skip transparent or opaque regions during rendering [S1, unofficial]. It differs from single-axis methods by constructing a separate encoded volume for each of the three major viewing directions, allowing the renderer to bypass empty space efficiently along the viewing axis [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A dense 3D voxel grid containing scalar values (e.g., density, temperature) and/or material properties.
*   **Output:** Three separate Run-Length Encoded (RLE) volume structures, one for each major viewing direction (X, Y, and Z axes) [S1, unofficial].

**Data Structures:**
Each encoded volume consists of a sequence of runs. Each run contains a start index along the viewing axis, a length representing the number of consecutive voxels, and a pre-classified opacity or material value [G]. Exact bit-packing or memory layout is not given in the sources.

**Steps:**
1.  **Pre-classification:** Iterate through the dense voxel grid. For each voxel, determine its opacity or material class based on the scalar value using pre-classification (mapping scalar values to opacity before encoding) [S1, unofficial].
2.  **Run Construction (Per Axis):** For each of the three major viewing directions (X, Y, Z):
    a. Traverse the voxel grid along lines parallel to the current axis.
    b. Identify consecutive sequences of voxels that share the same pre-classified opacity or material class.
    c. Encode each sequence as a run containing the start position, length, and the shared classification value.
    d. Store these runs in a linear array or linked structure specific to that axis [G].
3.  **Storage:** Save the three encoded volumes. This incurs higher memory overhead compared to methods storing only one direction or uncompressed data [S1, unofficial].

**Rendering Usage:**
During rendering, the ray caster traverses the encoded volume corresponding to the current viewing direction. Instead of sampling every voxel, the renderer reads the run lengths. If a run is classified as transparent, the ray skips the entire length of the run. If a run is opaque, the renderer skips the opaque image region entirely [S1, unofficial].

**Parameters:**
*   **Number of encoded volumes:** 3 (one per major viewing direction) [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Memory Overhead:** Storing three separate encoded volumes increases memory usage significantly compared to single-axis or uncompressed methods [S1, unofficial].
*   **Classification Granularity:** The choice of classification thresholds affects the compression ratio and rendering accuracy. Not given in the sources.
*   **Axis Alignment:** The method is optimized for axis-aligned viewing directions. Not given in the sources.

## Subtopics

### [Volpack Run-Length Encoded Volume Classification and Storage](4325-volpack-run-length-encoded-volume-classification-and-storage.md)
A pre-processing method that converts a dense voxel grid into three axis-aligned Run-Length Encoded (RLE) structures (one for X, Y, and Z viewing axes) to optimize ray casting by skipping transparent regions. It differs from standard RLE by classifying voxel data into opacity categories during construction, enabling the renderer to bypass empty space efficiently. Unlike [Scan Offset Computation](4338-scan-offset-computation.md), which only provides lookup tables for ray entry points, this method fully constructs the compressed data streams for all three orthogonal axes, allowing the renderer to traverse runs sequentially along the viewing axis. Choose it when rendering volume data with large transparent regions along axis-aligned viewing directions.

## Operating characteristics
*   **Time Complexity:** Pre-processing is $O(N)$ where $N$ is the number of voxels, as each voxel is visited once per axis [G]. Rendering time is reduced for scenes with large transparent or opaque regions due to skipping, but overhead exists in run traversal [S1, unofficial].
*   **Memory Complexity:** $O(N)$ in the worst case (no compression), but typically significantly less if runs are long. Storing three separate encoded volumes increases the constant factor compared to single-axis methods [S1, unofficial].
*   **Strengths:** Efficiently skips transparent and opaque regions, reducing fill rate and sampling cost [S1, unofficial]. Pre-classification allows for optimized data structures [G].
*   **Limitations:** Higher memory overhead due to storing three encoded volumes [S1, unofficial]. Less effective for views not aligned with the pre-computed axes [G].
*   **When to use:** Volume rendering where viewing directions are primarily axis-aligned or can be approximated by one of the three axes, and where large regions of transparency or opacity exist [G].
*   **When not to use:** When memory is severely constrained, or when viewing directions are arbitrary and non-axis-aligned, requiring frequent re-computation or interpolation [G].

## Background
This method originates from early volume rendering research as an improvement over basic ray casting, introducing pre-processing steps to optimize traversal by run-length encoding pre-classified voxel runs [S1, unofficial]. It is applied in medical imaging and other fields requiring efficient volume rendering [S1, unofficial].
