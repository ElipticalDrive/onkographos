# CSG and Inter-object Intersection

Also called: Solid Voxel CSG

## Overview
CSG and Inter-object Intersection performs general Constructive Solid Geometry (CSG) operations by voxelizing each object into a separate slicemap and rendering them sequentially with blending to compute the desired boolean operation [S1, unofficial]. It differs from its parent [CSG Model Voxelization](2497-csg-model-voxelization.md) by explicitly leveraging the density computation capabilities of solid voxelization to rapidly recover intersection volumes for applications like collision detection and haptic feedback, while maintaining real-time performance on billions of voxels with low dependence on input geometry complexity [S1, unofficial].

## How it works
**Inputs:**
- A set of geometric primitives (meshes or volume data) to be combined [S1, unofficial].
- A target voxel grid resolution (slicemap dimensions) [S1, unofficial].
- A boolean operation (e.g., Union, Intersection, Difference, XOR) [S1, unofficial].

**Outputs:**
- A voxelized volume representing the result of the CSG operation [S1, unofficial].
- Density information for the resulting volume (optional, for volume recovery) [S1, unofficial].

**Data Structures:**
- **Slicemap:** A 2D buffer (frame buffer) representing a single slice of the voxel grid. Each pixel corresponds to a voxel column. The buffer stores color/depth information used to track primitive coverage and parity [S1, unofficial].
- **3D Texture Memory:** Used to store intermediate voxelized volumes when extending to CSG trees or multi-pass approaches [S2].

**Steps:**
1. **Voxelize Each Object:** Render each geometric primitive into a separate slicemap [S1, unofficial].
2. **Sequential Blending:** Render the slicemap of the first object over the second, using the graphics hardware's blending logic to perform the desired boolean operation [S1, unofficial].
3. **Density Computation (Optional):** If volume recovery is required (e.g., for collision detection), use the density computation method described in the parent article to calculate the intersection's volume rapidly from the voxelized result [S1, unofficial].
4. **CSG Tree Extension (Optional):** For complex CSG trees, store intermediate results. The storage requirement is intuitively $O(\log^* n)$ where $n$ is the height of the tree. Rearranging the tree can optimize this number [S1, unofficial].

**Pseudocode:**
```python
def csg_intersection(primitives, resolution, boolean_op):
    width, height, depth = resolution
    slicemaps = []
    for prim in primitives:
        # Voxelize each object into a separate slicemap (standard rasterization step)
        slicemap = [[False] * width for _ in range(height)]
        # Standard graphics pipeline fills slicemap based on primitive coverage
        slicemaps.append(slicemap)

    result_slicemap = slicemaps[0]
    for i in range(1, len(slicemaps)):
        result_slicemap = blend_slicemaps(result_slicemap, slicemaps[i], boolean_op)
    return result_slicemap

def blend_slicemaps(slicemap_a, slicemap_b, operation):
    height = len(slicemap_a)
    width = len(slicemap_a[0])
    blended = [[False] * width for _ in range(height)]
    for y in range(height):
        for x in range(width):
            a = slicemap_a[y][x]
            b = slicemap_b[y][x]
            if operation == 'union':
                blended[y][x] = a or b
            elif operation == 'intersection':
                blended[y][x] = a and b
            elif operation == 'difference':
                blended[y][x] = a and not b
            elif operation == 'xor':
                blended[y][x] = a ^ b
            else:
                raise ValueError(f"Unsupported boolean operation: {operation}")
    return blended
```

**Parameters:**
- **Resolution:** The dimensions of the voxel grid. The method works at a precision of several billion ($10^9$) voxels in real-time [S1, unofficial].
- **Boolean Operation:** The type of CSG operation to perform (Union, Intersection, Difference, XOR) [S1, unofficial].

**Edge Cases and Pitfalls:**
- **CSG Tree Complexity:** For large CSG trees, the number of intermediate results can grow. The method suggests storing intermediate results with a storage requirement of $O(\log^* n)$, but rearranging the tree may be necessary to optimize this [S1, unofficial].
- **Precision:** While the method is efficient, artifacts may arise from the discretization process, especially with complex geometries [S1, unofficial].

## Subtopics

### Multi-Pass Voxelization for Large CSG Trees
An iterative approach to voxelize CSG trees larger than the frame buffer bit-depth limit (e.g., >8 primitives) by repeatedly voxelizing subtrees of at most 8 primitives and replacing the subtree with the resulting volume primitive [S2]. It differs from the basic single-pass method by handling larger trees through iterative reduction, trading off some memory pressure for scalability [S2]. Choose this when the CSG tree exceeds the hardware's single-pass bit-depth limit [S2].
- **Steps:** Select a subtree with at most 8 primitives from the CSG tree [S2]. Voxelize the selected subtree using the basic algorithm into a texture object in 3D texture memory [S2]. Replace the entire subtree in the CSG tree with the new volume primitive (texture object) [S2]. Repeat the process until the CSG tree is small enough to be directly voxelized [S2].
- **Pitfall:** Texture memory pressure: Multiple intermediate volumes may need to be stored simultaneously, causing texture memory swapping and performance penalties [S2]. To mitigate this, always choose the subtree with the most number of volume primitives so old volumes can be replaced by newly generated ones [S2].
- **Complexity:** Overhead: The multi-pass approach incurs extra traffic between frame buffer and texture memory, but this is described as fairly small because reading from frame buffer to texture memory is a fast direct cache operation that does not take up main memory cycles [S2].

### Region-Based Dynamic Voxelization
A technique to apply voxelization on-the-fly to only a region of interest (e.g., viewing region) to avoid low resolution caused by large volume spaces, enabling multi-resolution rendering [S2]. It differs from the basic method by restricting the voxelization domain to a subregion, requiring special handling of parity for XOR operations [S2]. Choose this when dealing with large spatial domains where full-volume voxelization would be too low-resolution or memory-intensive [S2].
- **Steps:** Generate the 0th slice content by drawing all geometric primitives once using the 0th slice as the viewing volume with the XOR logical operation set for the frame buffer [S2]. Carry over the resulting frame buffer image from the 0th slice to the voxelization process to ensure proper parities for all pixels in subsequent slices [S2].
- **Pitfall:** Parity error in XOR operations: When slicing starts from the front face of a subregion rather than the outside of all primitives, the XOR operation may not work correctly because parity is not guaranteed for every pixel [S2].

### Blended CSG Volume Rendering
A method to generate blended images for CSG models involving volume data sets by using the binary voxelization result as a 3D mask to extract the volumetric portion of the model [S2]. It differs from the basic binary CSG method by combining binary masking with volumetric intensity rendering [S2]. Choose this when visualizing CSG models that include volume data sets (e.g., CT scans) and require smooth blending of intensities [S2].
- **Steps:** For each slice, render all volumetric primitives individually and combine them in the frame buffer using a logical OR operation (or any desired blending function) [S2]. Extract the part of the slice within the spatial region of the CSG model by drawing the same slice from the binary mask (using 3D texture mapping) with a logical AND frame buffer operation [S2].
- **Pitfall:** Background color: A white background must be used when drawing slices for the volumetric primitives to avoid parts of the binary volume being removed by the AND operation [S2].

## Operating characteristics
- **Time Complexity:** Real-time performance is achieved, with complexity directly linked to the voxelization cost rather than the input geometry's complexity [S1, unofficial].
- **Memory Complexity:** Depends on the resolution of the voxel grid. For CSG trees, intermediate results require storage, intuitively $O(\log^* n)$ where $n$ is the tree height [S1, unofficial]. Multi-pass approaches may incur texture memory pressure [S2].
- **Measured Performance:** Works at a precision of several billion ($10^9$) voxels in real-time [S1, unofficial].
- **Scaling:** Scales well with resolution due to the fixed cost per voxel. Multi-pass approaches scale with tree depth but may suffer from texture memory swapping [S2].
- **Strengths:** Simple implementation, real-time performance, low dependence on geometry complexity, rapid volume recovery for collision detection/haptic feedback [S1, unofficial].
- **Limitations:** Limited by frame buffer bit-depth for single-pass operations (typically 8 primitives) [S2]. Potential artifacts from discretization [S1, unofficial]. Texture memory pressure in multi-pass approaches [S2].
- **When to Use:** Real-time CSG operations, collision detection, haptic feedback, visualization of large CSG models [S1, unofficial][S2].
- **When Not to Use:** When high-precision geometric accuracy is required without discretization artifacts, or when the CSG tree is too large for available texture memory in multi-pass scenarios [S2].

## Background
The method originates from the work on single-pass GPU solid voxelization and its applications, particularly in the context of real-time CSG modeling and volume graphics [S1, unofficial][S2]. It was developed to provide an effective tool for interactive CSG modeling and volume graphics environments, leveraging graphics hardware features for fast voxelization [S2]. The approach has been tested on relatively small CSG trees, with plans to investigate full use of frame buffer bits for better performance with larger trees [S2].
