# Hierarchical Binary-Scene Voxelization

Also called: GPU-based Hierarchical Voxelization, Real-Time Hierarchical Binary-Scene Voxelization

## Overview
Hierarchical Binary-Scene Voxelization is a robust, real-time method for computing a multi-resolution binary volumetric representation (octree) of a scene directly on the GPU [S1]. It solves the problem of generating voxel data for fully dynamic scenes by rasterizing geometry from three orthogonal directions and unioning the results, thereby eliminating the boundary holes inherent in single-direction rasterization methods like Eisemann and D´ecoret [S1]. Unlike sibling methods that may require pre-processing or specific primitive types, this approach handles any hardware-supported rasterizable geometry in a single geometry submission pass, leveraging 32-bit integer textures and bitwise operations for high performance [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A set of rasterizable geometric primitives and a defined world-space bounding box for the voxel grid [S1].
*   **Output:** A mipmapped 32-bit integer RGBA texture representing a hierarchical binary octree [S1].

**Data Structures:**
The core data structure is a single mipmapped 32-bit integer RGBA texture attached to a Frame Buffer Object (FBO) [S1].
*   **Base Resolution:** The width ($w$) and height ($h$) of the texture correspond to the viewport dimensions [S1].
*   **Voxel Encoding:** Each texel stores a 32-bit integer across its RGBA channels, representing a column of 32 voxels along the Z-axis, where one bit corresponds to one voxel in the column [S1].
*   **Depth Extension:** By using $N$ Multiple Render Targets (MRTs), the total depth resolution becomes $32 \times N$ [S1]. For example, 8 MRTs provide a depth of 1024 cells [S1].
*   **Hierarchy:** Each mip-level $L$ corresponds to an octree depth level. A texel at level $L$ represents a $2 \times 2$ block of texels from level $L-1$ in the X-Y plane [S1]. The value of a texel at level $L$ is the bitwise OR of its four parent texels from level $L-1$ [S1].

**Parameters:**
*   **Grid Resolution:** Defined by viewport width $w$, height $h$, and depth discretization (32 cells per RGBA channel) [S1]. A typical example is a $128^3$ grid [S1].
*   **Texture Format:** 32-bit integer RGBA [S1].
*   **Projection:** Orthographic camera projection is required to ensure non-deformed voxelization [S1].
*   **Rendering State:** Face culling and z-test are disabled; no z-buffer is attached to the FBO [S1].

**Algorithm Steps:**

1.  **Geometry Transformation (Geometry Shader):**
    The input geometry is processed by a Geometry Shader [S1]. The geometry is transformed and emitted three times, corresponding to three viewing directions: $-X$, $-Y$, and $-Z$ [S1]. These three transformed versions are rendered into three layers of a layered texture in a single draw call to avoid multiple geometry submissions and reduce bandwidth [S1].

2.  **Fragment Program Execution (Per Direction):**
    For each fragment generated by the rasterization of the transformed geometry, the following logic is executed in the Fragment Program:
    
    a. **World Space Z Calculation:**
       Compute the world space Z coordinate ($fPosW.z$) of the fragment by transforming the fragment position using the viewport-to-world matrix [S1].
       
    b. **Grid Index Calculation:**
       Map the world space Z coordinate to the grid's discrete Z-index [S1].
       Let $minZ$ and $maxZ$ be the grid boundaries [S1].
       Let $gridParams.z$ be the scaling factor $\frac{127}{maxZ - minZ}$ [S1].
       $$ index_{local} = (fPosW.z - minZ) \times gridParams.z $$
       [S1]
       
    c. **Channel and Bit Selection:**
       Determine which color channel (Red, Green, Blue, Alpha) and which bit within that channel corresponds to $index_{local}$ [S1].
       The channels represent ranges of 32 bits:
       - Red: indices 0-31
       - Green: indices 32-63
       - Blue: indices 64-95
       - Alpha: indices 96-127
       
       Let $channel\_offset$ be 0, 32, 64, or 96 based on the range containing $index_{local}$ [S1].
       Let $bit\_index = index_{local} - channel\_offset$ [S1].
       
    d. **Mask Generation:**
       Create a 32-bit mask with a single bit set at $bit\_index$ [S1].
       $$ mask = 1 \ll bit\_index $$
       [S1]
       
    e. **Framebuffer Update:**
       Perform a bitwise OR between the generated $mask$ and the existing content of the framebuffer pixel using the GPU's logical operation support for 32-bit integers [S1].

3.  **Union of Directions (GPGPU Pass):**
    After rendering the geometry from the three directions ($-X$, $-Y$, $-Z$), a GPGPU pass unions the three resulting grids into a final grid texture [S1]. This step ensures that voxels intersected by surfaces with slopes close to the grid axes are correctly filled, preventing holes [S1].

4.  **Hierarchical Octree Generation (Mipmapping):**
    The hierarchical structure is generated using standard GPU mipmapping operations [S1].
    For each mip-level $L > 0$:
    $$ Texel(L, x, y, z) = Texel(L-1, 2x, 2y, z) \lor Texel(L-1, 2x+1, 2y, z) \lor Texel(L-1, 2x, 2y+1, z) \lor Texel(L-1, 2x+1, 2y+1, z) $$
    where $\lor$ denotes the bitwise OR operation [S1].
    This process aggregates the binary occupancy from the finest level up to the root [S1]. The Z-resolution remains constant across all mip-levels in this basic representation, though Z-direction mip-reduction is possible by ORing groups of bits within a texel [S1].

```python
def compute_voxel_mask(world_z, min_z, scale):
    # Map world Z to grid index [0, 127]
    idx = (world_z - min_z) * scale
    if idx < 0 or idx >= 128:
        return 0
    # Determine channel offset (0, 32, 64, 96)
    if idx >= 96:
        offset = 96
    elif idx >= 64:
        offset = 64
    elif idx >= 32:
        offset = 32
    else:
        offset = 0
    bit = int(idx - offset)
    return 1 << bit

def hierarchical_voxelization(geometry, min_z, max_z, w, h, num_mrts):
    # Grid: 2D array of 32-bit integers. Each int stores 32 voxels in Z.
    # Total depth = num_mrts * 32.
    grid = [[0] * w for _ in range(h)]
    scale = 127.0 / (max_z - min_z)
    vtw_z_row = [0, 0, 1, 0] # Z-row of viewport-to-world matrix

    # Step 1 & 2: Render from three directions (-X, -Y, -Z)
    # Geometry is transformed by a Geometry Shader into 3 layers.
    directional_grids = []
    for _ in range(3):
        pass_grid = [[0] * w for _ in range(h)]
        # GPU rasterization step produces fragments with screen coords and world-space positions
        for frag in gpu_rasterize(geometry): 
            world_z = (frag.pos[0] * vtw_z_row[0] + frag.pos[1] * vtw_z_row[1] +
                       frag.pos[2] * vtw_z_row[2] + frag.pos[3] * vtw_z_row[3]) * frag.pos[3]
            mask = compute_voxel_mask(world_z, min_z, scale)
            x, y = frag.screen_coords
            pass_grid[y][x] |= mask
        directional_grids.append(pass_grid)

    # Step 3: Union the three grids
    final_grid = [[0] * w for _ in range(h)]
    for y in range(h):
        for x in range(w):
            final_grid[y][x] = directional_grids[0][y][x] | directional_grids[1][y][x] | directional_grids[2][y][x]

    # Step 4: Generate mipmaps (X-Y aggregation only, Z constant)
    mipmaps = [final_grid]
    curr_w, curr_h = w, h
    while curr_w > 1 or curr_h > 1:
        new_w = max(1, curr_w // 2)
        new_h = max(1, curr_h // 2)
        next_level = [[0] * new_w for _ in range(new_h)]
        for y in range(new_h):
            for x in range(new_w):
                val = 0
                for dy in range(2):
                    for dx in range(2):
                        if y * 2 + dy < curr_h and x * 2 + dx < curr_w:
                            val |= mipmaps[-1][y * 2 + dy][x * 2 + dx]
                next_level[y][x] = val
        mipmaps.append(next_level)
        curr_w, curr_h = new_w, new_h

    return mipmaps
```

**Edge Cases and Pitfalls:**
*   **Holes in Boundary Representation:** Single-direction rasterization creates holes where surface slopes are close to the grid's Z-axis [S1]. This method avoids this by rasterizing from three orthogonal directions and unioning the results [S1].
*   **Precision:** The method relies on 32-bit integer arithmetic. Correct mapping from floating-point world coordinates to integer grid indices is required to avoid off-by-one errors [S1].
*   **Depth Range:** The grid depth is limited by the number of MRTs and channels [S1]. For depths exceeding 1024, texture tiling must be used [S1].

## Operating characteristics
*   **Time Complexity:** The voxelization is a hardware rasterization process, making it highly efficient [S1]. Performance is largely independent of the fragment processing complexity, as the bottleneck is the fixed-function rasterizer [S1].
*   **Memory Complexity:** Memory usage is proportional to the grid resolution [S1]. A $512^3$ grid requires 16 MB (using 4 MRTs) [S1]. The theoretical maximum with 8 MRTs and tiling is a $4096^3$ grid (8 GB) [S1].
*   **Measured Performance:** On a G80 GPU, for a $128^3$ grid:
    *   Knot model: 2.5 ms
    *   Tree model: 17.5 ms
    *   Spheres model: 1.5 ms
    *   Disabling fragment processing yields similar times, confirming the fixed-function bottleneck [S1].
*   **Strengths:**
    *   Robustness: No holes in the voxel representation [S1].
    *   Speed: Real-time performance (milliseconds) [S1].
    *   Simplicity: No pre-processing of geometry required; works with any rasterizable primitive [S1].
    *   Dynamic Scenes: Suitable for fully dynamic, animated, or deformed scenes [S1].
*   **Limitations:**
    *   Requires GPU support for 32-bit integer textures, geometry shaders, and logical operations [S1].
    *   Orthographic projection is required for non-deformed voxelization [S1].
*   **When to Use:** Ideal for visibility computations, hierarchical collision detection, and CSG operations in dynamic scenes where speed and robustness are critical [S1].
*   **When Not to Use:** When perspective projection is strictly required without distortion correction, or when the hardware does not support the necessary 32-bit integer texture features [S1].

## Background
The method was introduced in a 2009 publication [S1]. It builds upon earlier work by Eisemann and D´ecoret (2006) and Zhao et al. (Dong et al., 2004) [S1]. Eisemann and D´ecoret used a single slice map which suffered from holes, while Zhao et al. required pre-processing and was limited to triangles [S1]. This method leverages advanced GPU functionalities, such as geometry shaders and 32-bit integer formats, to achieve robust, single-pass voxelization [S1]. It is particularly well-suited for applications like constructive solid geometry (CSG), shape repair, and collision detection [S1].
