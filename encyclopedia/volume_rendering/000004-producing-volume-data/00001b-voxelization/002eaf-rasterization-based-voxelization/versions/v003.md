# Rasterization-based Voxelization

Also called: Cube Mesh Generation, Voxelizing a Triangle Mesh

## Overview
Rasterization-based Voxelization converts continuous triangle meshes into discrete voxel grids by projecting geometry onto a 2D plane and using hardware or software rasterization to determine voxel occupancy [S1][S2, S3, S4, S5, unofficial]. It solves the problem of efficiently generating volumetric representations for rendering or simulation by leveraging the speed of scan-conversion algorithms [S1][S4, unofficial]. Unlike ray-tracing methods that test every voxel against every primitive, this approach iterates over primitives and "pulls" values into overlapping voxels, differing from instantiation-based modeling which "pushes" values [S4, unofficial]. It is distinguished from [Conservative Voxelization](3247-conservative-voxelization.md) by potentially requiring manual expansion or post-processing to avoid edge cracks, and from [GPU Volume Kernel Voxelization](1496-gpu-volume-kernel-voxelization.md) by often relying on the fixed-function graphics pipeline rather than pure compute shaders [S1][S5, unofficial].

## How it works
The method maps triangle vertices to a discrete grid, rasterizes the triangles to identify covered cells, and optionally generates geometry or point clouds from the occupied voxels [S1][S3, unofficial].

### Inputs and Outputs
*   **Inputs**:
    *   Input mesh vertices $V$ and faces $F$ [S1][S3, unofficial].
    *   Voxel size $vs = (voxelsizex, voxelsizey, voxelsizez)$ [S3, unofficial]. Typical values: $0.75, 0.5, 0.2, 0.1$ units [S2, unofficial].
    *   Voxel origin $vox\_origin$, typically $[0, 0, 0]$ [S1].
    *   Precision factor $precision$, typically $0.01f$, to reduce hole artifacts [S2, S3, unofficial].
    *   Gap fraction (optional), typically $0.02$, for spacing between generated cubes [S1].
*   **Outputs**:
    *   Binary occupancy grid (array of integer voxel coordinates $vox\_ijk$) [S1].
    *   Voxelized mesh (vertices, normals, colors, indices) [S2, S3, unofficial].
    *   Point cloud (voxel centers and optional colors) [S3, unofficial].

### Data Structures
The implementation typically uses a hash table to store occupied voxels to handle sparse grids and avoid fixed-size array limits [S3, unofficial].

**Hash Table Node (`vx_voxel_data_t`)**:
*   `position`: 3D vector $(x, y, z)$ representing the voxel center [S3, unofficial].
*   `color`: Optional color data [S3, unofficial].

**Output Mesh (`vx_mesh_t`)** [S3, unofficial]:
*   `vertices`: Array of size $voxels \times 8$ (8 corners per cube) [S3, unofficial].
*   `normals`: Array of size $6$ (predefined face normals) [S3, unofficial].
*   `colors`: Array of size $voxels \times 8$ or NULL [S3, unofficial].
*   `indices`: Array of size $voxels \times VOXELIZER\_INDICES\_SIZE$ [S3, unofficial].
*   `normalindices`: Array of size $voxels \times VOXELIZER\_INDICES\_SIZE$ [S3, unofficial].
*   `nvertices`, `nindices`, `nnormals`: Counters [S3, unofficial].

**Point Cloud (`vx_point_cloud_t`)** [S3, unofficial]:
*   `vertices`: Array of size $voxels$ [S3, unofficial].
*   `colors`: Array of size $voxels$ or NULL [S3, unofficial].
*   `nvertices`: Count of valid points [S3, unofficial].

### Steps
1.  **Load Mesh**: Load input vertices $v$ and faces $f$ [S1].
2.  **Compute Half-Voxel Size**: Calculate $hvs = vs \times 0.5$ [S3, unofficial].
3.  **Rasterize**: Call the internal rasterizer `vx__voxelize(mesh, vs, hvs, precision, &voxels)` [S3, unofficial].
    *   This step iterates over triangles, determines which voxels they intersect, and populates a hash table with occupied voxel data [S3, unofficial].
    *   *Note*: In GPU implementations, this may involve projecting triangles to 2D, using conservative rasterization to fill fragments, and writing to a 3D buffer or texture using atomic operations [S5, unofficial].
4.  **Generate Geometry (Optional)**:
    *   If generating a mesh: Iterate the hash table. For each occupied voxel, extract position and color. Generate 8 cube corner offsets relative to the center using $hvs$ [S3, unofficial]. Populate the output mesh arrays [S3, unofficial].
    *   If generating a point cloud: Iterate the hash table. Copy voxel positions to the point cloud array [S3, unofficial].
5.  **Cleanup**: Free the hash table and intermediate structures [S3, unofficial].

### Pseudocode
```python
def rasterization_based_voxelization(mesh, voxelsizex, voxelsizey, voxelsizez, precision, origin=[0,0,0]):
    # 1. Compute half-voxel sizes
    hvs_x = voxelsizex * 0.5
    hvs_y = voxelsizey * 0.5
    hvs_z = voxelsizez * 0.5
    
    # 2. Rasterize triangles to populate hash table of occupied voxels
    # The internal rasterizer handles triangle-voxel intersection logic
    occupied_voxels = vx__voxelize(mesh.vertices, mesh.faces, 
                                   (voxelsizex, voxelsizey, voxelsizez), 
                                   (hvs_x, hvs_y, hvs_z), 
                                   precision)
    
    # 3. Generate output mesh
    num_voxels = len(occupied_voxels)
    out_vertices = []
    out_indices = []
    
    # Predefined cube corner offsets relative to center
    cube_offsets = [
        (-hvs_x,  hvs_y,  hvs_z), (-hvs_x, -hvs_y,  hvs_z),
         ( hvs_x, -hvs_y,  hvs_z), ( hvs_x,  hvs_y,  hvs_z),
        (-hvs_x,  hvs_y, -hvs_z), (-hvs_x, -hvs_y, -hvs_z),
         ( hvs_x, -hvs_y, -hvs_z), ( hvs_x,  hvs_y, -hvs_z)
    ]
    
    # Standard cube face indices (8 vertices, 12 triangles, 36 indices)
    # Assuming VOXELIZER_INDICES_SIZE covers the full cube definition
    cube_face_indices = [
        0, 1, 2, 0, 2, 3,  # Front
        4, 6, 5, 4, 7, 6,  # Back
        4, 5, 1, 4, 1, 0,  # Left
        2, 6, 7, 2, 7, 3,  # Right
        3, 7, 5, 3, 5, 1,  # Top
        4, 0, 2, 4, 2, 6   # Bottom
    ]

    for voxel_pos in occupied_voxels:
        base_idx = len(out_vertices)
        # Add 8 vertices for this voxel
        for dx, dy, dz in cube_offsets:
            out_vertices.append((voxel_pos.x + dx, voxel_pos.y + dy, voxel_pos.z + dz))
        
        # Add indices for this voxel
        for idx in cube_face_indices:
            out_indices.append(base_idx + idx)
            
    return out_vertices, out_indices
```

### Edge Cases and Pitfalls
*   **Holes/Artifacts**: Standard rasterization only covers pixels/voxels whose centers lie inside the triangle, leading to cracks at edges [S5, unofficial]. Using a precision factor or conservative rasterization helps [S2, S5, unofficial].
*   **Overfilling**: Conservative rasterization may generate too many fragments, incorrectly filling empty cells [S5, unofficial]. Using MSAA render targets can mitigate this [S5, unofficial].
*   **Performance**: The output mesh size scales significantly with voxel density. A torus with 441 vertices can result in >140,000 vertices at small voxel sizes [S2, unofficial].
*   **Precision**: Floating-point precision in triangle clipping and intersection tests can affect accuracy [S3, unofficial].

## Subtopics

### [3D Grid Rasterization](903-3d-grid-rasterization.md)
A CPU-based algorithm that determines which voxels in a fixed-resolution 3D grid are intersected by a triangle mesh, producing a binary occupancy grid or a grid with interpolated colors. It solves the problem of converting continuous polygonal geometry into a discrete volumetric representation without performing surface reconstruction (such as QEF or dual vertex solving). It differs from full o-voxel implementations by omitting the face QEF, boundary QEF, and dual vertex solve steps, focusing solely on the intersect scanline to find occupied voxels. It differs from GPU-based siblings like [GPU Volume Kernel Voxelization](1496-gpu-volume-kernel-voxelization.md) by relying on CPU-side scanline filling and hash-table deduplication rather than parallel fragment shaders.

### [GPU Volume Kernel Voxelization](1496-gpu-volume-kernel-voxelization.md)
GPU Volume Kernel Voxelization is a technique that accelerates the voxelization of triangle meshes by parallelizing the iteration over the 2D XY plane of the voxel grid using a GPU compute shader. It solves the performance bottleneck of CPU-based voxelization, where nested loops over X and Y coordinates are executed sequentially. Unlike rasterization-based alternatives that project geometry into 3D textures, this method retains the explicit triangle-voxel intersection logic of CPU implementations but distributes the workload across GPU threads, achieving significant speedups (e.g., 50x) for high-resolution grids.

### [Implicit Surface Voxelization](2379-implicit-surface-voxelization.md)
Implicit Surface Voxelization converts a mathematical implicit surface definition into a discrete voxel grid by rasterizing 2D rectangles within a Region of Interest (ROI) and evaluating the implicit function in the pixel shader. It differs from triangle-based rasterization methods (e.g., [Rasterization-based Voxelization](908-rasterization-based-voxelization.md)) by operating directly on analytical functions rather than polygonal approximations, allowing for the handling of complex, non-polygonal geometry.

### [GPU Voxelization via Compute Shaders](2549-gpu-voxelization-via-compute-shaders.md)
GPU Voxelization via Compute Shaders converts 3D triangle meshes into a uniform 3D voxel grid by leveraging GPU parallel processing. It solves the problem of generating volumetric data for real-time ray marching or volume rendering with high throughput. Unlike [Rasterization-based Voxelization](908-rasterization-based-voxelization.md), which projects triangles via the fixed-function graphics pipeline, compute shader methods decouple intersection logic from rasterization, allowing custom geometric tests and atomic operations on 3D buffers or textures.

### [GPU Voxelization](2633-gpu-voxelization.md)
GPU Voxelization maps 3D triangle meshes to a voxel grid by leveraging the GPU's hardware rasterization pipeline, projecting triangles onto a 2D plane and using shaders to write occupied voxel indices into a buffer. It solves the performance bottleneck of CPU-based ray-tracing voxelization by parallelizing the rasterization process across thousands of GPU cores. It differs from its parent [Rasterization-based Voxelization](908-rasterization-based-voxelization.md) by specifically utilizing the GPU rendering pipeline (vertex, geometry, fragment shaders) and atomic operations for concurrent writes, distinguishing it from CPU-based or compute-shader-only approaches.

### [CPU Mesh Voxelization](3137-cpu-mesh-voxelization.md)
CPU Mesh Voxelization converts a triangle mesh into a 3D grid of voxels by iterating over the bounding box of each triangle and testing each voxel center against the triangle's plane and edge constraints. It differs from its parent [Rasterization-based Voxelization](908-rasterization-based-voxelization.md) by explicitly rasterizing triangles into a hash table of voxel centers and colors, then generating a cube mesh for each occupied voxel, whereas CPU Mesh Voxelization typically outputs a binary occupancy grid or bit-packed table. It differs from [3D Grid Rasterization](903-3d-grid-rasterization.md) by using exact geometric overlap tests (SAT or plane/projection) rather than simple grid cell intersection, and from [Voxelization via Triangle Scattering](3779-voxelization-via-triangle-scattering.md) by iterating cells against triangles rather than scattering triangles into cells.

### [Voxel Rasterization](3204-voxel-rasterization.md)
Voxel Rasterization converts a triangle mesh into a voxelized representation by rendering the geometry into a 3D voxel buffer, supporting both simple occupancy and normal/color mapping. It differs from its sibling [3D Grid Rasterization](903-3d-grid-rasterization.md) by explicitly iterating over triangle surfaces to calculate interpolated points and normals rather than relying on a pure grid traversal, and from [GPU Volume Kernel Voxelization](1496-gpu-volume-kernel-voxelization.md) by utilizing a Direct3D 11-based rendering pipeline or CUDA kernels for the rasterization step.

### [Conservative Rasterization via Triangle Expansion](3531-conservative-rasterization-via-triangle-expansion.md)
This method eliminates voxelization holes caused by standard rasterization, which only covers pixels whose centers lie inside a triangle, by expanding the triangle in clip space and culling the expanded area in the fragment shader. It differs from sibling methods like [Conservative Voxelization](3247-conservative-voxelization.md) by implementing the expansion logic manually in the geometry shader using homogeneous plane mathematics, rather than relying on hardware-specific conservative rasterization extensions or post-processing hole-filling.

### [Multi-view projection](5937-multi-view-projection.md)
Multi-view projection voxelization converts a triangle mesh into a voxel grid by rasterizing the geometry from multiple orthogonal viewpoints (typically along the X, Y, and Z axes) to ensure complete coverage and prevent cracks. It distinguishes itself from single-view methods by using redundant projections to fill gaps caused by occlusion or thin geometry, and from direct 3D texture rasterization by often employing intermediate 2D buffers to bypass hardware limitations on direct 3D writes.

### [Position Map and Image-Space Transfer](6237-position-map-and-image-space-transfer.md)
This family of techniques converts 3D geometric data into voxel grids by projecting or transferring information into 2D image space (textures) before reconstructing the 3D volume. Unlike direct 3D rasterization, these methods leverage the GPU's fixed-function rasterizer or image load/store operations on 2D textures to determine voxel occupancy, often trading memory bandwidth for computational simplicity. They are distinguished from direct triangle rasterization by operating on pre-computed surface samples or 2D texture slices, ensuring connectivity or enabling real-time performance insensitive to scene complexity.

### Rasterization-based Volume Modeling
The process of building volume data voxel-by-voxel, considered the third layer in the voxel modeling abstraction hierarchy [S4, unofficial]. It solves the problem of assigning density values to voxels based on overlapping primitives [S4, unofficial]. It differs from instantiation-based modeling by pulling values into a voxel (similar to raytracing), whereas instantiation-based modeling pushes values into voxels (similar to micropolygon rendering) [S4, unofficial]. The main rasterization loop iterates over voxels in the discrete bounding box, transforms voxel position to world space, samples the primitive, and adds the value to the buffer if positive [S4, unofficial].

### Single-Pass Voxelization
A voxelization approach that utilizes the geometry shader to reduce draw calls by selecting the axis from which each triangle has the largest overall projection for fragment generation [S5, unofficial]. It solves the problem of multiple draw calls required for multi-axis projection [S5, unofficial]. It differs from standard rasterization by using conservative rasterization to generate fragments as long as there is something inside the pixel, not only if its center is covered [S5, unofficial]. Hardware support for conservative rasterization is available on Nvidia Maxwell architecture and later; RTX driver support is available for Turing and Pascal architecture GPUs [S5, unofficial]. A pitfall is that GPUs only generate fragments if a pixel's center is covered by a triangle, leading to small cracks at the edges of triangles [S5, unofficial]. Another pitfall is that conservative rasterization generates too many fragments, incorrectly filling cells in the voxel grid that should be empty [S5, unofficial].

## Operating characteristics
*   **Time Complexity**: Generally $O(N \cdot M)$ where $N$ is the number of triangles and $M$ is the number of voxels covered by each triangle, but optimized by rasterization to $O(N \cdot A)$ where $A$ is the screen area in voxels [S1][S4, unofficial].
*   **Memory Complexity**: $O(V)$ where $V$ is the number of occupied voxels, typically stored in a hash table for sparse grids [S3, unofficial].
*   **Performance**: GPU-based implementations offer significant speedups (e.g., 50x) for high-resolution grids compared to CPU-based methods [S1].
*   **Strengths**: Fast, leverages existing graphics hardware, suitable for real-time applications [S1][S5, unofficial].
*   **Limitations**: Can produce holes or cracks if not using conservative rasterization [S5, unofficial]. Output mesh size can be very large compared to input [S2, unofficial].
*   **When to use**: When real-time voxelization is required, or when the input is a triangle mesh and a voxelized representation is needed for rendering or simulation [S1][S4, unofficial].
*   **When not to use**: When exact analytical surface representation is needed, or when memory bandwidth is a critical bottleneck and sparse structures are preferred [S4, S5, unofficial].

## Background
Rasterization-based voxelization has been widely used in computer graphics for converting polygonal models into volumetric data for rendering, simulation, and 3D printing [S1][S2, unofficial]. The method leverages the efficiency of scan-conversion algorithms, which are fundamental to raster graphics [S4, unofficial]. Libraries such as Point-Cloud-Utils and various header-only C libraries have popularized efficient implementations [S1][S3, unofficial]. The technique has evolved to include GPU acceleration via compute shaders and hardware rasterization pipelines to handle real-time requirements [S1][S5, unofficial].
