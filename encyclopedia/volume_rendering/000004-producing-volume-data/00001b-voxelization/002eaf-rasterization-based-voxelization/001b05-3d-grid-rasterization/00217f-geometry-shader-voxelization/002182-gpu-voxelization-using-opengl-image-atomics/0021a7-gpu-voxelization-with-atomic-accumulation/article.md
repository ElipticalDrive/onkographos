# GPU Voxelization with Atomic Accumulation

Also called: Atomic Average for Voxelization, Atomic RGBA8 average voxelization, Atomic Running Average Voxelization, Hardware-accelerated voxelization, Voxelization with Atomic Running Average

## Overview
A fragment-shader-based voxelization technique that accumulates per-fragment lighting and material properties into a 3D texture using hardware atomic operations to resolve race conditions and compute a moving average of samples per voxel [S1, S2, unofficial]. It solves the flickering artifact caused by multiple primitives overwriting the same voxel by averaging their outputs, which occurs because the render order of primitives changes every frame [S2, unofficial]. Unlike simple `imageStore` approaches that discard previous values, this method maintains a consistent lighting approximation for voxels hit by multiple surfaces [S2, unofficial].

## How it works
**Inputs:**
*   3D polygonal mesh geometry (vertices, normals, texture coordinates).
*   Material properties (ambient, diffuse, specular, transmittance, emission, shininess, IOR, dissolve, illumination mode, roughness, metallic, sheen, clearcoat, anisotropy) [S1, unofficial].
*   Light sources (position, color, intensity) [S1, unofficial].
*   Scene bounds and voxel grid dimensions (`dim`) [S1, unofficial].
*   `cube_size`: Uniform float scaling factor for light positions [S1, unofficial].
*   `illum`: Integer material illumination mode [S1, unofficial].

**Outputs:**
*   Six 3D textures (`tex3D[6]`), bound as `uimage3D` with `r32ui` format (though the atomic operation packs RGBA8 data, the underlying storage is treated as unsigned integer arrays for atomic access) [S1, unofficial]. *Note: The source describes binding `r32ui` but performing RGBA8 packing and atomic average operations, implying the 32-bit integer is used to store the packed 4x8-bit color + sample count structure or the implementation details vary slightly between the binding declaration and the atomic logic described.* [S1, unofficial].

**Algorithm Steps:**

1.  **Rasterization:** Project the 3D mesh onto the 3D voxel grid. For each fragment generated by the rasterizer, determine its world position `world_pos` and normal `normal`.
2.  **Lighting Calculation:**
    *   Initialize `color = vec3(0.0)`.
    *   Loop over `num_lights = min(point_light_count, MAX_POINT_LIGHTS)`.
    *   For each light:
        *   Calculate direction: `dir = normalize(light_pos - world_pos)`.
        *   Calculate distance: `d = length(light_pos - world_pos)`.
        *   Apply attenuation: `a = 1.0 / (1.0 + d * d)`. *Note: Light positions are divided by `cube_size` before this calculation* [S1, unofficial].
        *   Calculate diffuse contribution: `cos_surf = max(dot(normalize(normal), dir), 0.0f)`.
        *   Accumulate: `color += cos_surf * a * light.color * light.intensity` [S1, unofficial].
3.  **Material Combination:**
    *   Combine lighting with material diffuse color: `diffuse_color = color * material.diffuse`.
    *   Add emission: `final_color = diffuse_color + material.emission` [S1, unofficial].
4.  **Transparency Handling:**
    *   If `illum == 4 || 6 || 7 || 9`:
        *   `final_trans = material.transmittance`
        *   `alpha = material.dissolve`
    *   Else:
        *   `final_trans = vec3(1.0)`
        *   `alpha = 1.0`
    [S1, unofficial]
5.  **Clamping and Coordinate Mapping:**
    *   Clamp color: `final_color = clamp(final_trans * final_color, 0.0, 1.0)`.
    *   Pack alpha: `final_alpha = clamp(alpha, 0.0, 1.0)`.
    *   Map world position to voxel coordinates: `voxel_pos = ivec3(dim * (0.5f * pos + vec3(0.5f)))`. *Note: `pos` is the normalized fragment position in the voxel grid space* [S1, unofficial].
6.  **Atomic Accumulation (Retry Loop):**
    *   For each of the 6 target textures `tex3D[i]` (where `i` from 0 to 5):
        *   Pack `final_color` (RGB) and `final_alpha` (A) into 4 bytes (RGBA8).
        *   Initialize sample counter `n = 1`.
        *   Pack `n` into the least significant bits of the 32-bit integer value using `encUnsignedNibble` (or equivalent bit-packing logic to store the count alongside the color data for the atomic operation). *Note: The exact bit-packing scheme for the 32-bit integer to hold RGBA8 + count is not fully detailed, but `imageAtomicCompSwap` is used on a 32-bit integer texture* [S1, unofficial].
        *   **Loop:**
            *   Call `prev_val = imageAtomicCompSwap(tex3D[i], voxel_pos, new_val)`.
            *   If `prev_val == new_val` (success, no conflict):
                *   Unpack `prev_val` to get `rval` (previous average color) and `n_prev` (previous sample count).
                *   Compute new average: `rval = (rval * n_prev + val) / (n_prev + 1)`.
                *   Round to even: `rval = round(rval / 2) * 2`. *Note: This rounding step is specific to the source implementation* [S1, unofficial].
                *   Repack `rval` and `n_prev + 1` into `new_val`.
                *   Break loop.
            *   Else (conflict):
                *   Reload previous value from texture (or use `prev_val` if supported, but the source says "reload previous value and retry", implying a read or using the returned `prev_val` to compute the new average based on the *new* incoming `val` and the *old* count).
                *   *Correction based on S2:* "check if the voxel we are trying to modify has been modified... keep looping until we exhaust all conflicts." The standard CAS loop retries with the updated average.
                *   Update `new_val` with the newly computed average and incremented count.
                *   Retry `imageAtomicCompSwap`.
    [S1, S2, unofficial]

def pack_rgba8(color, alpha):
    # Convert floats to 0-255 bytes
    r = int(color.r * 255)
    g = int(color.g * 255)
    b = int(color.b * 255)
    a = int(alpha * 255)
    return (r << 24) | (g << 16) | (b << 8) | a

**Edge Cases and Pitfalls:**
*   **Float Atomics:** OpenGL does not support atomic operations on floating-point values, only integers. This prevents direct atomic averaging of HDR (floating-point) voxels. Workarounds include using `RGBA16f` textures with custom software averaging (not atomic) or packing floats into integers (lossy) [S2, unofficial].
*   **Precision:** The use of `RGBA8` limits the dynamic range and precision of the accumulated lighting, potentially causing color banding in low-light areas compared to `RGBA16f` [S2, unofficial].
*   **Concurrency:** The retry loop can lead to livelock if contention is extremely high, though the source notes it produces "very few artifacts" in complex scenes [S2, unofficial].
*   **Rounding:** The specific rounding step (`round(rval / 2) * 2`) is an implementation detail that may affect the final average accuracy [S1, unofficial].

## Subtopics

### GPU Voxelization with Lighting Accumulation
A variant that rasterizes geometry into a 3D texture to store light contribution and opacity for cone tracing. It approximates only indirect diffuse lighting, not specular. For every surface, intersecting voxels are set to fully opaque, and reflected light is calculated. Direct lighting from spotlights uses the Lambertian model, light falloff, and shadow maps. Emissive materials add light directly. The 3D texture is RGBA, where channels 0-2 (RGB) encode light and channel 3 (A) encodes opacity. It uses `imageStore()` to discard fragments and write directly to the texture, without atomic averaging [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** O(N * L) for lighting calculation per fragment, where N is the number of fragments and L is the number of lights. The atomic accumulation adds a retry loop whose complexity depends on the contention rate (number of primitives hitting the same voxel). In high-contention scenarios, this can increase significantly.
*   **Memory Complexity:** O(V) for the 3D texture storage, where V is the number of voxels. Six textures are used in the primary implementation [S1, unofficial].
*   **Measured Performance:** The method is hardware-accelerated via OpenGL image atomics. Using `RGBA16f` textures produces higher quality results but is "not too expensive" in terms of performance, while `RGBA8` suffers from color banding and noise in low-light areas [S2, unofficial].
*   **Strengths:** Resolves flickering artifacts caused by render order dependency. Hardware-accelerated atomic operations ensure consistency.
*   **Limitations:** Limited to diffuse lighting approximation (no specular). Integer-only atomics prevent direct HDR averaging. Precision loss with `RGBA8`.
*   **When to Use:** When flickering in voxelized lighting is unacceptable and the scene has significant overlap of geometry. Suitable for real-time indirect diffuse lighting approximation.
*   **When Not to Use:** When specular indirect lighting is required. When HDR precision is critical and integer packing is not feasible.

## Background
Originating from the Voxel Cone Tracing technique, this method was developed to address the flickering issues inherent in simple rasterization-based voxelization. The technique was implemented in the `voxel_cone_tracing` project by latencyhiding [S1, S2, unofficial]. It builds on the concept of using OpenGL image atomics to write directly to 3D textures without a traditional framebuffer [S1, unofficial].
