# Virtual Voxel


## Overview
Virtual Voxel is a rasterization-based voxel renderer designed for the real-time visualization and modification of large-scale scenes (up to $4^{12}$ resolution) by combining virtual texture and virtual geometry concepts [S1]. It streams appropriate levels of detail into GPU memory using a two-level data structure, storing data linearly to enable efficient real-time scene editing (Union/Subtraction) [S1]. Unlike previous graph-based voxel visualization methods, it employs a rasterization rendering pipeline, resulting in highly efficient modification of large scenes [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A scene defined by a pre-generated Sparse Voxel Octree (STree) structure, camera position, and optional modification primitives (Union/Subtraction cubes).
*   **Output:** A rendered frame (position and albedo) in a 64-bit framebuffer, and an updated voxel pool on the GPU.

**Data Structures:**
1.  **STree (Streaming Tree):** A low-level sparse octree contained within chunks of a high-level 2D uniform grid.
    *   **Node Layout:** Each node (referred to as a "cell") represents a $64 \times 64 \times 64$ resolution voxel data block.
    *   **Storage:** Only existence flags are recorded for each cell to allow efficient storage and access of sparse data [S1].
2.  **GPU Voxel Pool:** A linear memory pool on the GPU.
    *   **Page Layout:** Each streamed cell is allocated a new page. Each page accommodates 16,384 ($128 \times 128$) voxels [S1].
3.  **Visibility Buffer:** A 64-bit buffer used in the first rendering pass.
    *   **Layout:** `depth_bits << 32 | voxel_id << 12 | cell_id` [S1].
4.  **Framebuffer:** A 64-bit buffer for the final result.
    *   **Layout:** `depth_bits << 32 | albedo` [S1].

**Parameters:**
*   **LOD_factor:** A scalar multiplier for the cell size used in the LOD error calculation. Typical value: 8 (for the Berlin Data Set test scene) [S1].

**Algorithm Steps:**

1.  **Streaming (CPU-GPU Interaction):**
    1.  The CPU traverses the STree from the root cell to find the suitable level of detail (LOD).
    2.  Calculate the LOD error using the distance-based metric:
        $$LOD\_error = \|CellCenterPos - CamPos\| - (LOD\_factor \times CellSize)$$
        where $CellCenterPos$ is the center of the current cell, $CamPos$ is the camera position, and $CellSize$ is the physical size of the cell [S1].
    3.  If $LOD\_error > 0$, the CPU evaluates child cells, as the current cell does not meet the LOD metric.
    4.  If $LOD\_error \le 0$ or the cell is a leaf node, a cell-building request is sent to the GPU [S1].

2.  **Cell Building (GPU):**
    1.  Upon receiving a cell-building request, the GPU voxelizes the cell at $64^3$ resolution using the method from Crassin and Green [2012] [S1].
    2.  A page is allocated in the voxel pool for this cell.
    3.  The voxelization result is written into a $64^3$ size buffer.
    4.  The voxelization result is atomically appended to the allocated page in the voxel pool [S1].

3.  **Rendering Pass 1 (Visibility Buffer):**
    1.  Voxels are rendered as points to the 64-bit visibility buffer.
    2.  Frustum culling is applied to cull any invisible cells before rendering [S1].
    3.  Each compute thread renders 64 voxels of a cell [S1].

4.  **Rendering Pass 2 (Reconstruction and Final Frame):**
    1.  The renderer reconstructs voxels from the visibility buffer using a method similar to Nanite [Karis et al. 2021].
    2.  Each compute thread reads one pixel from the visibility buffer to reconstruct the voxel as a geometry cube.
    3.  The voxel is rendered as a cube with 12 triangles.
    4.  The result (position and albedo) is written to the 64-bit framebuffer using an `AtomicMin` operation on the depth channel [S1].

5.  **Real-Time Modification (Union/Subtraction):**
    1.  **Selection:** A screen-pick operation retrieves the depth value from the framebuffer at the mouse click position $P$.
    2.  **World Position:** The world position $wP$ of $P$ is determined using the inverted camera matrix [S1].
    3.  **Cell Identification:** An Axis-Aligned Bounding Box (AABB) is computed around $wP$, and all intersecting STree cells are identified for update [S1].
    4.  **Re-voxelization:** A voxelization shader is executed to re-voxelize the identified cells.
        *   **Subtraction:** A buffer containing subtraction cube positions and scales is used. During voxelization, voxels residing within subtraction cubes are eliminated [S1].
        *   **Union:** A compute shader for the Union operation takes the union cube as input. The Union voxelization result is merged with the regular voxelization result [S1].
    5.  **Update:** The combined voxelization result is atomically appended to the allocated voxel page [S1].

**Pseudocode:**

```python
# Constants
LOD_FACTOR = 8
CELL_RESOLUTION = 64
PAGE_SIZE_VOXELS = 16384 # 128x128 voxels per page in pool

# Data Structures
class STreeNode:
    exists: bool
    children: List[STreeNode] # Sparse list of children
    cell_id: int

class VoxelPool:
    pages: List[Page]
    
    def allocate_page(self) -> Page:
        # Allocate a new page for a cell
        pass

class Page:
    voxels: Array[bool, 64*64*64] # Simplified representation of voxel data

# 1. Streaming Phase
def stream_cells(root_node: STreeNode, camera_pos: Vec3, lod_factor: float):
    if root_node is None:
        return
    
    # Calculate LOD error
    cell_center = get_cell_center(root_node)
    cell_size = get_cell_size(root_node)
    distance = length(cell_center - camera_pos)
    lod_error = distance - (lod_factor * cell_size)
    
    if lod_error > 0:
        # Evaluate children
        for child in root_node.children:
            stream_cells(child, camera_pos, lod_factor)
    else:
        # Send cell-building request to GPU
        gpu_request_cell_building(root_node)

# 2. GPU Cell Building
def gpu_build_cell(node: STreeNode):
    # Voxelize using Crassin and Green method
    voxel_data = voxelize_crassin_green(node.resolution)
    
    # Allocate page in voxel pool
    page = voxel_pool.allocate_page()
    
    # Atomically append to page
    page.append(voxel_data)

# 3. Rendering Pass 1: Visibility Buffer
def render_visibility_buffer(cells: List[Cell], visibility_buffer: Buffer):
    for cell in cells:
        if frustum_cull(cell):
            continue
        
        # Each compute thread renders 64 voxels
        render_voxels_as_points(cell, visibility_buffer)

# 4. Rendering Pass 2: Reconstruction
def render_final_frame(visibility_buffer: Buffer, framebuffer: Buffer):
    # Each compute thread reads one pixel
    for pixel in visibility_buffer:
        voxel_id = pixel.voxel_id
        cell_id = pixel.cell_id
        
        # Reconstruct voxel as geometry cube (12 triangles)
        cube = reconstruct_cube(voxel_id, cell_id)
        
        # Render with AtomicMin for depth
        render_cube_with_atomic_min(cube, framebuffer)

# 5. Real-Time Modification
def modify_scene(mouse_pos: Vec2, framebuffer: Buffer, camera_matrix: Mat4):
    # Screen pick
    depth = framebuffer.get_depth(mouse_pos)
    
    # World position
    wP = invert(camera_matrix) * project_to_world(mouse_pos, depth)
    
    # Identify cells
    aabb = compute_aabb_around(wP)
    intersecting_cells = find_intersecting_stree_cells(aabb)
    
    for cell in intersecting_cells:
        # Re-voxelize
        voxel_data = voxelize_cell(cell)
        
        # Apply Subtraction
        for sub_cube in subtraction_cubes:
            if voxel_in_cube(voxel_data, sub_cube):
                voxel_data.remove(voxel_data)
        
        # Apply Union
        for union_cube in union_cubes:
            voxel_data.add(union_cube)
            
        # Update pool
        voxel_pool.update_page(cell, voxel_data)
```

## Operating characteristics
*   **Time Complexity:** The streaming phase depends on the tree traversal depth and the LOD metric evaluation. The rendering phase is parallelized across compute threads, with each thread handling 64 voxels in Pass 1 and one pixel in Pass 2.
*   **Memory Complexity:** Linear storage in the GPU Voxel Pool. Each page accommodates 16,384 voxels. The STree stores only existence flags, minimizing CPU memory usage.
*   **Measured Performance:** Average frame time of 6.0459 ms at 4K resolution on a Windows 10 desktop with AMD Threadripper 2950X and RTX4090, measured during a camera fly-through of a 16x16 chunk test scene ($4^{12}$ resolution) [S1].
*   **Strengths:** Real-time rendering of large-scale scenes ($4^{12}$ resolution); efficient real-time modification (Union/Subtraction); linear data storage simplifies memory management compared to graph-based structures.
*   **Limitations:** Supports only opaque objects. Transparent rendering is unachievable because the atomic max operation (used for depth/visibility) cannot blend color values [S1].

## Background
Virtual Voxel was introduced by Jinyuan Yang and Abraham G. Campbell from University College Dublin, Ireland [S1]. The method was presented in the paper "VirtualVoxel: Real-Time Large Scale Scene Visualization and Modification" [S1]. It builds on concepts from Virtual Texture and Virtual Geometry, aiming to combine efficient storage with real-time modification capabilities. The voxelization step relies on the method by Crassin and Green [2012], and the reconstruction step uses a technique similar to Nanite [Karis et al. 2021].
