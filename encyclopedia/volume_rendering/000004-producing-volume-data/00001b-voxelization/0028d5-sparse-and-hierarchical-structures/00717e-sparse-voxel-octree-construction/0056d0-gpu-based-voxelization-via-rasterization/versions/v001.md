# GPU-based Voxelization via Rasterization

Also called: Crassin and Green method variant, Voxelization using OpenGL rasterization pipeline

## Overview
This method generates volumetric density 3D textures by rasterizing triangle slices directly into a 3D texture using the standard OpenGL rasterization pipeline [S1]. It solves the problem of on-the-fly voxel generation for interactive navigation by leveraging the user camera's viewport to determine fragment calls, effectively substituting the initial viewport setup steps of the Crassin and Green method [S1]. Unlike Crassin and Green, which raster each triangle to a 3D texture in three discrete steps (choosing max projection axis, creating matching viewport, expand/raster), this approach uses the visualization's existing rastering, allowing free navigation and dynamic voxel resolution adaptation [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A mesh composed of slices (e.g., yarns), a user camera viewport, and a target 3D texture.
*   **Output:** A 3D texture containing voxel data.

**Data Structures:**
*   **Volumetric Texture:** Stores one byte for density and two bytes for orientation (discrete polar coordinates $\theta$ and $\phi$) [S1]. The maximum size is limited by hardware, typically 2GB per texture and 2048 voxels maximum size for any axis [S1].
*   **CPU Memory:** An array storing a 4x4 model-view matrix per slice [S1].

**Numbered Steps:**
1.  **Viewport Utilization:** Render fragments directly called by the viewport of the user camera, bypassing the geometric shader steps of choosing a maximum projection axis and creating a matching viewport [S1].
2.  **World Coordinate Interpolation:** Pass the position in world coordinates of each slice from the vertex shader and interpolate it at each fragment shader [S1].
3.  **Grid Mapping:** Map the raster fragment to the corresponding grid position in the 3D texture using the interpolated world coordinates. This decouples fragment coordinates from the target 3D texture, allowing for on-the-fly changes in voxel resolution and hierarchical structures like octrees [S1].
4.  **Direct Texture Access:** Use `image_load_store` instructions (OpenGL 4.3 GLSL) for direct access to images at arbitrary positions from any shader [S1].
5.  **Mip-map Management:** Deactivate mip-mapping to prevent transparency issues at mid-range distances where interpolated alpha values become blurred, making polygons appear almost transparent [S1].

**Parameters:**
*   **Slice Resolution:** 25 slices between yarn crossings (1mm, 1/40 of the pixel width) for distant views; increased to 50 for closest views [S1].
*   **Texture Resolution:** Can be adapted to the viewport volume; maximum 2GB per texture, 2048 voxels max per axis [S1].

**Pitfalls and Edge Cases:**
*   **Perpendicular Slices:** Slices perpendicular to the camera plane cause wrong voxel positions due to interpolation errors of world coordinates from the vertex shader [S1].
*   **Aliasing:** Aliasing produces wrong voxel positions. This is handled by using antialiasing methods, specifically x32 filtering on the GPU, which has a negligible impact on performance [S1].
*   **Sub-pixel Polygons:** Rastering sub-pixel polygons with alpha blending causes blurred alpha values at mid-range distances. Deactivating mip-mapping is required to maintain coherence, though this may result in yarns looking thinner as they move further away due to the small probability of rastering a fully opaque fragment pixel [S1].

**Pseudocode:**
```python
# Vertex Shader
# Input: Slice geometry, Model-View Matrix from CPU array
# Output: World position interpolated to fragment shader
vec3 world_pos = (model_view_matrix * vec4(position, 1.0)).xyz;
out_world_pos = world_pos;

# Fragment Shader
# Input: Interpolated world_pos
# Output: Write to 3D texture
void main() {
    // Map world coordinates to 3D texture grid coordinates
    // Assuming a known world-to-voxel transformation matrix T
    vec3 voxel_coord = T * out_world_pos;
    
    // Calculate density and orientation (theta, phi)
    float density = compute_density();
    vec2 orientation = compute_orientation();
    
    // Use image_load_store to write directly to 3D texture
    // Format: 1 byte density, 2 bytes orientation
    imageStore(volume_texture, ivec3(voxel_coord), vec4(density, orientation, 1.0));
}
```

## Operating characteristics
*   **Time Complexity:** The depth sorting of slice quads is based on single-CPU `std::sort`, taking around two seconds per frame for dense models [S1]. This step is not required for volume generation but improves interactive navigation [S1].
*   **Memory Complexity:** CPU memory scales with the number of slices (4x4 matrix per slice). GPU memory scales with the 3D texture size (max 2GB, 2048 voxels/axis) [S1].
*   **Measured Performance:**
    *   **Low Density Cloth (2.5M slices):** 1.8GB CPU memory, 2.06GB GPU memory, 2s initialization, 71ms per frame [S1].
    *   **High Density Cloth (17.6M slices):** 7.2GB CPU memory, 3GB GPU memory, 16s initialization, 150ms per frame [S1].
    *   **High Density Close-up (35.2M slices):** 12GB CPU memory, 4GB+2GB shared GPU memory, 35s initialization, 400ms per frame [S1].
*   **Strengths:** Allows free navigation and on-the-fly voxel generation; decouples fragment coordinates from texture resolution [S1].
*   **Limitations:** Depth sorting on CPU can be a bottleneck for dense models; perpendicular slices cause interpolation errors; mip-mapping must be disabled to avoid transparency artifacts [S1].

## Background
This method was proposed by Jorge Lopez-Moreno et al. in 2014 as part of the "GPU Visualization and Voxelization of Yarn-Level Cloth" paper [S1]. It builds on the Crassin and Green voxelization method [S1] but adapts it for interactive visualization by utilizing the existing camera rasterization pipeline. The method was tested on a GeForce GTX 670 graphics card [S1].
