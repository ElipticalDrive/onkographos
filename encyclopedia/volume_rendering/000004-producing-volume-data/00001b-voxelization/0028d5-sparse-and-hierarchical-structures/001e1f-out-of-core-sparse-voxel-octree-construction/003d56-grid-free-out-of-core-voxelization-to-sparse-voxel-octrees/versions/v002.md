# Grid-Free Out-Of-Core Voxelization to Sparse Voxel Octrees

Also called: GPU-based Out-of-Core SVO Builder without Atomics, Grid-free out-of-core voxelization, Morton Queue and Stitch Queue SVO Creation, Out-of-core voxelization to sparse voxel octrees on GPU, Stream-based Out-of-Core SVO Construction, batch-based SVO builder, out-of-core voxelization to SVO

## Overview
This method constructs a Sparse Voxel Octree (SVO) from a triangle mesh on the GPU without using a global 3D voxel grid or atomic operations, enabling out-of-core processing of scenes larger than available memory [S1, S2]. It differs from grid-based approaches by streaming triangles in batches and using a Morton queue to manage voxel-attribute pairs, and from in-core GPU techniques by maintaining unprocessable nodes in a stitch queue buffer to handle order-dependent attribute generation across batch boundaries [S1, S2].

## How it works
### Inputs and Outputs
**Inputs:**
- A triangle mesh (vertices, indices, texture coordinates, normals).
- Target resolution (voxel grid dimensions).
- User-defined parameters: $K_{vox/tri\_max}$ (max voxels per triangle) and $K_{vox/batch\_max}$ (max voxels per batch) [S1].

**Outputs:**
- A Sparse Voxel Octree (SVO) with attributes (color, normals, etc.) stored in a structure similar to Laine and Karras [2010] (bitmasks for non-empty voxels, voxel attributes, and child pointers) [S2].

### Data Structures
1.  **Morton Queue:** Stores voxel-attribute pairs from previous and current batches. Sorted by Morton index. Size varies dynamically [S1, S2].
2.  **Stitch Queue Buffer:** Fixed-size buffer per hierarchy level. Stores voxel-attribute pairs for nodes that cannot be finalized because future batches may create additional children for the same parent. Contains at most 8 nodes per level [S1].
3.  **Per-Triangle Voxel Memory:** Temporary storage for voxels generated by a single triangle batch. Offsets are predicted to avoid atomic operations [S2].
4.  **Voxel Attributes:** Encoded for memory efficiency:
    - Color: 16-bit RGB565 [S1].
    - Normals: 16-bit using octahedron compression [S1].

### Steps

#### 1. Triangle Pre-processing (Homogenization)
To balance GPU workload and limit Morton index ranges, triangles are subdivided if the ratio of the area of the largest face of their bounding box to the area of a voxel face exceeds a user-defined threshold [S2].
-   **Case 1 (Long thin triangles):** Angles $> 90^\circ$ or $< 20^\circ$. Subdivide based on longest edge [S2].
-   **Case 2 & 3 (Other triangles):** Subdivide based on bounding box aspect ratio [S2].
-   **Goal:** Ensure each triangle fits within a manageable voxel count ($K_{vox/tri\_max}$) [S1].

#### 2. Sorting and Batch Creation
1.  Sort triangles by the minimum Morton index of their bounding boxes [S2].
2.  Create batches such that the predicted total voxel count per batch does not exceed $K_{vox/batch\_max}$ [S2].
3.  Record the minimum Morton index of the first triangle in the *next* batch as the `stop_index` for the current batch [S2]. This defines the valid Morton range for SVO node creation for the current iteration [S2].

#### 3. Voxelization (Per-Batch)
1.  For each triangle in the batch, one GPU thread processes it [S2].
2.  Voxelize the triangle into the **Per-Triangle Voxel Memory** using the method of Schwarz and Seidel [2010] (conservative surface voxelization) [S2].
3.  Use the predicted voxel count to write to pre-allocated offsets, avoiding atomic operations [S2].
4.  Create voxel attributes by projecting voxel centers to UV coordinates [S2].
5.  Remove placeholders and copy the resulting voxel-attribute pairs to the **Morton Queue** [S2].

#### 4. Morton Queue Processing
1.  Append the new voxel-attribute pairs from the current batch to the **Morton Queue** (which contains unused pairs from previous batches) [S2].
2.  Sort the **Morton Queue** by Morton index [S1, S2].
3.  Extract the **Voxel Attribute Set** for SVO creation: all pairs with Morton index $< stop\_index$ [S1, S2].
    -   This ensures no future triangle will intersect any voxel in this set, as all future Morton indices are $\ge stop\_index$ [S1].
4.  The remaining pairs (Morton index $\ge stop\_index$) stay in the queue for future iterations [S1].

#### 5. SVO Creation (Bottom-Up)
Process the **Voxel Attribute Set** to create SVO nodes level by level, from leaves to root [S1, S2].
1.  **Parent Index Calculation:** For a child node with index $C$, the parent index $P$ is calculated as $P = \lfloor C / 8 \rfloor$ (for octree) or $\lfloor C / 4 \rfloor$ (for quadtree simplification in examples) [S1].
2.  **Parallel Stream Compaction:** Each GPU thread processes all child nodes of one parent [S2].
3.  **Stitch Queue Handling:**
    -   Identify child nodes belonging to the *last immediate parent* on the current hierarchy level (the parent with the highest index among those being processed) [S1].
    -   Store these child nodes in the **Stitch Queue Buffer** because future batches may create further children for this parent [S1].
    -   All other child nodes are processed and pushed to the next higher level [S1].
4.  **Attribute Creation:**
    -   Parent attributes are created only if *all* child nodes are available [S2].
    -   If a parent is in the **Stitch Queue Buffer**, its attributes are deferred.
    -   Attributes can be determined by multipass operations (e.g., averaging colors) [S2].
5.  **Next Iteration:**
    -   Move the sorted **Stitch Queue** for the respective hierarchy level from the buffer to the front of the current voxel attribute set for that level [S1].
    -   Process these nodes like all other nodes in the next iteration [S1].

#### 6. Finalization
After the last batch is processed, the **Stitch Queue Buffer** holds information for all last nodes on each hierarchy level [S1].
1.  Finish SVO creation on the CPU [S1].
2.  Process all nodes per hierarchy level sequentially [S1].
3.  Copy information of new nodes to the next higher level of the stitch queue buffer until the root is finalized [S1].

# Constants
K_vox_tri_max = 100  # Max voxels per triangle
K_vox_batch_max = 10_000_000  # Max voxels per batch
STITCH_QUEUE_SIZE_PER_LEVEL = 8

# Data Structures
class VoxelAttribute:
    morton_index: int
    color: int  # RGB565
    normal: int  # Octahedron compressed
    # ... other attributes

class MortonQueue:
    items: List[VoxelAttribute]
    
    def sort(self):
        self.items.sort(key=lambda x: x.morton_index)
        
    def extract_below(self, stop_index: int) -> List[VoxelAttribute]:
        # Extract all items with morton_index < stop_index
        # Return them and remove from queue
        extracted = []
        remaining = []
        for item in self.items:
            if item.morton_index < stop_index:
                extracted.append(item)
            else:
                remaining.append(item)
        self.items = remaining
        return extracted

class StitchQueueBuffer:
    # Fixed size per level
    queues: Dict[int, List[VoxelAttribute]] 
    
    def add(self, level: int, items: List[VoxelAttribute]):
        # Append to queue for level
        pass
        
    def get(self, level: int) -> List[VoxelAttribute]:
        # Return and clear queue for level
        pass

def main(mesh, resolution):
    # 1. Pre-processing
    subdivided_triangles = []
    for tri in mesh.triangles:
        if needs_subdivision(tri, resolution):
            subdivided_triangles.extend(subdivide_triangle(tri))
        else:
            subdivided_triangles.append(tri)
            
    # 2. Sorting
    for tri in subdivided_triangles:
        tri.min_morton = get_min_morton_index(tri.bbox, resolution)
    subdivided_triangles.sort(key=lambda t: t.min_morton)
    
    # 3. Batch Creation
    batches = create_batches(subdivided_triangles, K_vox_batch_max)
    
    morton_queue = MortonQueue()
    stitch_buffer = StitchQueueBuffer()
    
    for i, batch in enumerate(batches):
        # Determine stop index from next batch
        if i + 1 < len(batches):
            stop_index = batches[i+1][0].min_morton
        else:
            stop_index = float('inf')
            
        # 4. Voxelization
        per_triangle_voxels = []
        for tri in batch:
            # One thread per triangle
            voxels = voxelize_triangle(tri, resolution, method="SchwarzSeidel")
            for v in voxels:
                v.color = project_to_uv(tri, v.center)
                v.normal = project_normal_to_uv(tri, v.normal)
            per_triangle_voxels.extend(voxels)
            
        # Add to Morton Queue
        morton_queue.items.extend(per_triangle_voxels)
        
        # 5. Morton Queue Processing
        morton_queue.sort()
        voxel_attr_set = morton_queue.extract_below(stop_index)
        
        # 6. SVO Creation (Bottom-Up)
        # Process levels from leaf to root
        for level in range(max_level, -1, -1):
            # Get stitch queue from previous iteration if any
            stitch_items = stitch_buffer.get(level)
            current_level_items = voxel_attr_set.filter(level=level)
            all_items = stitch_items + current_level_items
            
            # Group by parent
            parents = group_by_parent(all_items)
            
            finalized_nodes = []
            stitch_candidates = []
            
            for parent_idx, children in parents.items():
                # Check if this is the last parent on this level
                is_last_parent = (parent_idx == max_parent_idx_on_level)
                
                if is_last_parent:
                    # Store in stitch queue for next iteration
                    stitch_candidates.extend(children)
                else:
                    # Finalize node
                    if all_children_available(children):
                        node = create_node(children)
                        node.attributes = compute_attributes(children)
                        finalized_nodes.append(node)
                        # Push to next level if not root
                        if level > 0:
                            push_to_next_level(node)
                            
            # Add stitch candidates to buffer
            if stitch_candidates:
                stitch_buffer.add(level, stitch_candidates)
                
            # Update voxel_attr_set for next level processing
            # (In practice, this involves moving finalized nodes up)
            voxel_attr_set = finalized_nodes

    # 7. Finalization on CPU
    for level in range(max_level, -1, -1):
        stitch_items = stitch_buffer.get(level)
        # Process sequentially on CPU
        for items in stitch_items:
            finalize_node_sequentially(items)

### Parameters
-   $K_{vox/tri\_max}$: Maximum voxels per triangle. Controls triangle subdivision and memory usage. Recommended mid-range value: 50–100 [S1].
-   $K_{vox/batch\_max}$: Maximum voxels per batch. Acts as a global voxel counter. Large values improve performance but risk memory overflow. Typical value: 10 M [S1].

### Edge Cases and Pitfalls
-   **Overflow:** If a huge number of triangles intersect a single voxel or span very large Morton ranges, the Morton queue or stitch queue may overflow. Subdivision limits Morton ranges but does not guarantee prevention [S1].
-   **Order-Dependent Attributes:** If a huge amount of triangles intersect a single voxel, the list of voxel-attribute pairs can exceed available memory, violating the out-of-core property [S1].
-   **Post-Batch Finalization:** After the last batch, the stitch queue buffer holds information for all last nodes on each hierarchy level. These must be processed sequentially on the CPU [S1].
-   **Memory Overflow:** Setting $K_{vox/batch\_max}$ too high (e.g., 50 M) can cause memory overflow because the global voxel counter does not account for the memory needed for triangle data stored simultaneously [S1].

## Operating characteristics
-   **Time Complexity:** Slower than pure in-core GPU techniques (e.g., Crassin and Green 2012) by one to two orders of magnitude due to maintaining unprocessable voxels and out-of-core triangle handling [S1].
-   **Memory Complexity:** Logarithmic in the size of the SVO. Memory usage is controlled by $K_{vox/batch\_max}$ and $K_{vox/tri\_max}$ [S1].
-   **Performance:** Scales well in terms of resolution for complex scenes with various surface and material attributes [S1]. For the Hairball scene (2.8 M triangles) at resolution 8192, it takes roughly half the time of Laine and Karras [2011] and is nearly four times faster than Baert et al. [2014] [S1].
-   **Strengths:** Handles complex scenes with sophisticated attributes; out-of-core capability; no atomic operations; parallel GPU processing [S1, S2].
-   **Limitations:** Slower than in-core methods; sensitive to parameter tuning; potential for overflow in extreme cases [S1].

## Background
-   **Origin:** The method was presented in 2015 by the authors of [S1] and [S2]. It builds on the concept of out-of-core SVO construction [S1].
-   **History:** It addresses the limitations of in-core GPU techniques (which require large memory) and previous out-of-core methods like Baert et al. [2014] (which lack visual quality due to average triangle color assignment) and Laine and Karras [2011] (which cannot access all triangles at higher levels in an out-of-core setting) [S1].
-   **Usage:** Used for constructing SVOs from triangle meshes for volume rendering, particularly for complex scenes with various surface and material attributes [S1].
