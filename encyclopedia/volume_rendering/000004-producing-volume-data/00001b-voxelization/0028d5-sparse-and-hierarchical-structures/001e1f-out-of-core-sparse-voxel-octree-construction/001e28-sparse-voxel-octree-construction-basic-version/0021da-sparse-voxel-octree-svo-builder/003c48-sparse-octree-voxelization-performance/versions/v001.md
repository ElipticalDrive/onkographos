# Sparse Octree Voxelization Performance

Also called: GPU Voxelization Performance, SVO Construction Performance

## Overview
This article documents the performance characteristics and implementation details of the Sparse Voxel Octree (SVO) construction method used for GPU-based voxelization [S1, unofficial]. It addresses the problem of efficiently converting triangle meshes into a compact hierarchical voxel representation for real-time global illumination [S1, unofficial]. Unlike in-core CPU methods or grid-based GPU approaches, this method generates the SVO directly on the GPU, optimizing for parallel triangle processing and minimizing atomic contention [S1, unofficial]. It is distinct from [Grid-Free Out-Of-Core GPU Voxelization](11494-grid-free-out-of-core-gpu-voxelization.md) by its reliance on preallocated buffers and specific atomic merging strategies for fragment consolidation [S1, unofficial].

## How it works
The method constructs an SVO from a list of voxels using GPU compute shaders, processing the voxel list level-by-level [Parent]. The core performance bottleneck lies in the octree construction phase, specifically the flagging of nodes [S1, unofficial].

**Inputs and Outputs:**
*   **Input:** A list of triangle fragments (voxels) generated from rasterizing triangle meshes.
*   **Output:** A Sparse Voxel Octree structure stored in global memory, typically using `RGBA32F` values for leaf nodes [S1, unofficial].

**Data Structures:**
*   **Octree Buffer:** A preallocated buffer in global memory. The size must be fixed in advance [S1, unofficial].
*   **Voxel Values:** Stored as `RGBA32F` [S1, unofficial].

**Steps:**
1.  **Fragment Generation:** Triangles are rasterized into a list of voxel fragments [S1, unofficial].
2.  **Flagging:** Nodes in the octree are flagged to indicate occupancy. This is identified as the most time-consuming step [S1, unofficial].
3.  **Octree Creation:** Internal nodes are allocated and linked based on the flags [Parent].
4.  **Construction Initialization:** The structure is initialized for rendering or further processing [S1, unofficial].
5.  **Atomic Fragment Merging (Optional):** Conflicting fragments at the same voxel location are merged using atomic operations. This step is optional but significantly impacts performance [S1, unofficial].

**Parameters and Pitfalls:**
*   **Preallocation:** The octree buffer requires preallocation with a fixed size [S1, unofficial]. This is a primary limitation, though it can be managed as a cache [S1, unofficial].
*   **Resolution:** Maximum resolution tested was $512^3$ (9 octree levels) [S1, unofficial].
*   **Atomic Contention:** Atomic fragment merging can be a performance bottleneck if not optimized [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Dominated by the flagging step during octree construction [S1, unofficial].
*   **Memory Complexity:** Requires preallocated buffer of fixed size [S1, unofficial].
*   **Measured Performance:** On a Kepler-based NVIDIA GTX680 with $512^3$ resolution and `RGBA32F` values:
    *   Hand scene: 3.04 ms total (with atomic merging) [S1, unofficial].
    *   Dragon scene: 12.98 ms total [S1, unofficial].
    *   Sponza scene: 15.44 ms total [S1, unofficial].
    *   Breakdown for Hand scene: Frag list 0.17 ms, Flag 0.89 ms, Octree Create 0.18 ms, Construction Init 0.35 ms, Write 0.35 ms, Mipmap 0.55 ms [S1, unofficial].
*   **Hardware Scaling:** Performance is 30% to 58% faster on Kepler (GTX680) compared to Fermi (GTX480) [S1, unofficial]. Atomic fragment merging is up to 80% faster on Kepler [S1, unofficial].
*   **Strengths:** Fast enough to update dynamic objects in real time, keeping update under 15% of frame time in global illumination applications [S1, unofficial].
*   **Limitations:** Requires preallocation of octree buffer with fixed size [S1, unofficial].

## Background
This method was developed for use in voxel-based global illumination techniques, specifically for prevoxelizing static environments and updating dynamic objects in real time [S1, unofficial]. It builds on the [Sparse Voxel Octree (SVO) Builder](2617-sparse-voxel-octree-svo-builder.md) algorithm [Parent]. The performance data was presented in the context of OpenGL Insights on sparse voxelization [S1, unofficial].
