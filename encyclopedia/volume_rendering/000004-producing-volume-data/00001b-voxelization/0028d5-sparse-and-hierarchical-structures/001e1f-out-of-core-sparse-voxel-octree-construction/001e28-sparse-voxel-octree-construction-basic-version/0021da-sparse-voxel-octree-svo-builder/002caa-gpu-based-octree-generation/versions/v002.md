# GPU-based Octree Generation

Also called: Fixed-Partition Octree Generation, GPU Octree Construction

## Overview
This method generates a hierarchical octree data structure directly on the GPU by partitioning the input volume into fixed-size cubes of $32 \times 32 \times 32$ voxels [S1, unofficial]. Unlike standard Sparse Voxel Octrees that only subdivide non-empty regions, this approach uniformly subdivides the entire volume space down to the minimum node size, which simplifies compute shader logic by avoiding dynamic branching for empty regions [S1, unofficial]. It constructs a pre-allocated array-based octree by mapping every non-empty voxel to a hierarchical path [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D voxel grid of size $n \times n \times n$, where each voxel contains a density or occupancy value [S1, unofficial].
*   **Output:** A flat array of `OctreeEntry` structures representing the octree, simulating a linked list where each node points to its children [S1, unofficial].

**Data Structures:**
*   **OctreeEntry:** A 64-bit structure consisting of two 32-bit integers [S1, unofficial].
    *   `data`: A bitmask where the least significant bit indicates the presence of data (non-empty children or leaf data) [S1, unofficial].
    *   `childrenStartIndex`: The index in the output array where the children of this node begin [S1, unofficial].
*   **Parameters:**
    *   `size`: The dimension of the volume $n$ [S1, unofficial].
    *   `minNodeSize` ($\epsilon$): The minimum side length of a node, set to 32 [S1, unofficial].
    *   `maxDepth`: Derived from `size` and `minNodeSize` as $\log_2(\frac{size}{minNodeSize})$ [S1, unofficial].

**Algorithm Steps:**
1.  **Dispatch:** Launch a compute shader with a thread group size of $4 \times 4 \times 4$ (64 threads per group) [S1, unofficial]. The total number of threads dispatched equals the number of voxels in the volume ($n^3$) [S1, unofficial].
2.  **Empty Check:** Each thread identifies its voxel coordinate `currentVoxel` via `SV_DispatchThreadID` and samples the voxel data [S1, unofficial]. If the value is less than 1 (empty), the thread returns immediately [S1, unofficial].
3.  **Update Path:** If the voxel is non-empty, call `updateOctree(currentVoxel)` [S1, unofficial].
4.  **Traverse and Mark:** Inside `updateOctree`:
    *   Calculate the relative octant index at depth 1 using `calculateRelativeOctant` [S1, unofficial].
    *   Mark the root node (`outputOctree[0]`) as having data by setting the first bit of its `data` field [S1, unofficial].
    *   Initialize `nextIndex` as `relativeIndex + 1` [S1, unofficial].
    *   Loop from `depth = 1` to `maxDepth`:
        *   Retrieve the current `OctreeEntry` at `nextIndex` [S1, unofficial].
        *   Mark the current node as having data by setting the first bit of its `data` field [S1, unofficial].
        *   Calculate the relative octant index for the next depth (`depth + 1`) [S1, unofficial].
        *   Update `nextIndex` to `current.childrenStartIndex + relativeIndex` [S1, unofficial].

**Formulas:**
*   **Array Size:** The total number of elements in the octree array for a volume of size $n$ and partition size 32 is given by the geometric series sum [S1, unofficial]:
    $$ \sum_{i=0}^{n/32} \frac{1 - 8^{n/32 + 1}}{1 - 8} $$
    For a $512^3$ volume with $\epsilon=32$, this results in 4681 elements [S1, unofficial].
*   **Octant Mapping:** The mapping from 3D coordinates to an octant index in a $2 \times 2 \times 2$ child array is defined as [S1, unofficial]:
    $$ f_{2,2}(\vec{p}) = p_i + p_j \times 2 + p_k \times 2 \times 2 $$
    where $p_i, p_j, p_k$ are the relative coordinates within the child block [S1, unofficial].
*   **Relative Octant Calculation:** The relative position within a block at depth $d$ is calculated as [S1, unofficial]:
    $$ g(\vec{x}) = \left( \frac{\vec{x}_1}{s} \bmod (2 \times s), \frac{\vec{x}_2}{s} \bmod (2 \times s), \frac{\vec{x}_3}{s} \bmod (2 \times s) \right) $$
    where $s = \frac{size}{2^n}$ [S1, unofficial].

**Pseudocode:**
```python
# Constants
SIZE = 512  # Example volume dimension
MIN_NODE_SIZE = 32
MAX_DEPTH = log2(SIZE / MIN_NODE_SIZE)

# Data Structure
class OctreeEntry:
    data: int       # 32-bit bitmask
    childrenStartIndex: int  # 32-bit index

# Helper Functions
def get_data(pos: int3) -> int:
    # Reads voxel density/occupancy at pos from the input volume grid [G]
    return volume[pos.x][pos.y][pos.z]

def calculate_relative_index(v: int, d: int) -> int:
    # Source divides by (size >> d), not just v >> d
    return v // (SIZE >> d)

def calculate_octant(pos: int3, d: int) -> int:
    # Map 3D coordinates to 0-7 octant index
    # Note: Source uses pos.x, pos.z, pos.y order for i, j, k
    i = calculate_relative_index(pos.x, d)
    k = calculate_relative_index(pos.z, d)
    j = calculate_relative_index(pos.y, d)
    return i + (k * 2) + (j * 4)

def calculate_relative_octant(pos: int3, d: int) -> int:
    # Calculate position modulo block size at previous depth
    block_size = SIZE >> (d - 1)
    relative_pos = pos % block_size
    return calculate_octant(relative_pos, d)

def update_octree(current_voxel: int3, output_octree: list[OctreeEntry]) -> None:
    # Calculate relative octant at depth 1
    relative_index = calculate_relative_octant(current_voxel, 1)
    
    # Mark root node (index 0)
    output_octree[0].data |= 1
    
    # Initialize next index to traverse
    next_index = relative_index + 1
    
    # Traverse down to max depth
    for depth in range(1, MAX_DEPTH + 1):
        current_entry = output_octree[next_index]
        
        # Mark current node as having data
        current_entry.data |= 1
        output_octree[next_index] = current_entry
        
        # Calculate relative octant for next deeper level
        relative_index = calculate_relative_octant(current_voxel, depth + 1)
        
        # Move to child node
        next_index = current_entry.childrenStartIndex + relative_index

# Compute Shader Entry Point
def CS(current_voxel: int3) -> None:
    # Check if voxel is empty
    if get_data(current_voxel) < 1:
        return
    
    # Update octree path for this voxel
    update_octree(current_voxel, output_octree)
```

**Edge Cases and Pitfalls:**
*   **Division Cost:** The algorithm performs divisions with remainders (modulo operations), which are expensive on GPU hardware even though divisions by powers of two are replaced by bit shifts [S1, unofficial].
*   **False Positives:** The fixed-partition approach minimizes false positives during ray traversal by ensuring only non-empty partitions are examined, avoiding the diagonal-empty-voxel worst-case of unpartitioned traversal [S1, unofficial].
*   **Initialization:** The `childrenStartIndex` for all nodes must be initialized to valid offsets before the shader runs, as the shader only sets the `data` bit and traverses existing indices; the source does not specify the exact initialization routine [G].

## Operating characteristics
*   **Time Complexity:** $O(n^3)$, where $n$ is the volume dimension, which is considered inefficient for large volumes [S1, unofficial].
*   **Memory Complexity:** The array size is determined by the fixed partitioning; for a $512^3$ volume with a minimum node size of 32, the array contains 4681 elements, occupying approximately 37 KB [S1, unofficial].
*   **Strengths:** Simplifies GPU implementation by avoiding complex dynamic memory allocation or branching for empty regions, making the traversal logic predictable [S1, unofficial].
*   **Limitations:** High computational cost due to $O(n^3)$ complexity and expensive modulo operations [S1, unofficial].
*   **When to use:** Initial construction of the octree for static volumes; the source recommends running this algorithm only at initialization, while partial updates can be performed if only specific volume regions are modified [S1, unofficial].

## Background
This method was described by Enes Hergül in a thesis on raycasting-based voxel rendering [S1, unofficial]. It is presented as an alternative to standard Sparse Voxel Octree construction, specifically designed to be easier to implement in a GPU compute shader by using fixed-size partitions [S1, unofficial]. The approach contrasts with the basic SVO builder, which dynamically allocates nodes only for non-empty regions [S1, unofficial].
