# Sparse Voxel Octree Construction (Basic Version)

Also called: Basic SVO Construction, SVO Construction, basic version

## Overview
This method constructs a Sparse Voxel Octree (SVO) from a stream of non-empty voxel Morton codes by maintaining per-depth queues and merging nodes when queues fill, writing intermediate results to disk to manage memory constraints [S3]. It differs from its siblings, such as [Brute Force SVO Construction](1704-brute-force-svo-construction.md) and [Sparse Voxel Octree Construction via Morton Code Sorting](2227-sparse-voxel-octree-construction-via-morton-code-sorting.md), by processing the input in a single streaming pass without requiring the entire octree to reside in memory or pre-sorting all points globally [S3]. It is chosen for its out-of-core capability and implementation simplicity, but is limited by the overhead of processing empty nodes compared to optimized variants [S3].

## How it works
**Inputs and Outputs:**
- Input: A stream of non-empty voxel leaf nodes, typically generated by a voxelization step and ordered by Morton code [S3]. Each leaf node contains its Morton code and associated data (e.g., color, normal) [S3].
- Output: A Sparse Voxel Octree written to disk or a flat buffer, where nodes are stored with spatial locality (siblings stored adjacent to each other) [S3].

**Data Structures:**
1. **Queues:** An array of queues, one for each depth level $d$ from $0$ (root) to $D$ (leaf level) [S3].
2. **Node Representation:** The output SVO uses a compact representation of 24 bytes per node: a 64-bit reference to the first child, a 1-byte offset for every child, and a 64-bit reference to the data associated with the node [S3]. (Note: [S2, unofficial] describes an alternative 32-byte layout using eight `u32` children, but the 24-byte layout is specified for this algorithm.)

**Algorithm Steps:**
1. Initialize an empty queue for each depth level $d \in [0, D]$ [S3].
2. While the input stream contains data:
   a. Consume the next leaf node $l$ from the input stream [S3].
   b. Push $l$ onto the queue corresponding to its depth $d$ (`queues[d].push_back(l)`) [S3].
   c. Set a depth counter $d$ to the depth of the pushed leaf node [S3].
   d. While $d > 0$ and `queues[d]` is full:
      i. Create an internal node $p$ [S3].
      ii. Set the children of $p$ to the child offsets or references of the elements currently in `queues[d]` [S3].
      iii. Write the non-empty elements of `queues[d]` to disk/output [S3].
      iv. Clear `queues[d]` [S3].
      v. Push the new internal node $p$ onto `queues[d-1]` [S3].
      vi. Decrement $d$ by 1 [S3].
3. After the input stream is exhausted, flush any remaining nodes in the queues to the output, starting from the deepest non-empty queue up to the root [S3].
4. Write the root node to the output [S3].

**Pseudocode:**
> **Unverified code.** The code below did not pass a test run against a reference implementation, or no test fits it, so it may contain errors.

```python
def build_svo_basic(input_stream, max_depth, queue_capacity):
    """
    Constructs an SVO using the basic out-of-core algorithm.
    
    Args:
        input_stream: Iterator yielding leaf nodes with attributes 'depth' and 'data'.
        max_depth: The maximum depth of the octree (leaf level).
        queue_capacity: The maximum number of nodes each queue can hold before merging.
        
    Returns:
        List of serialized node records written to output.
    """
    queues = [[] for _ in range(max_depth + 1)]
    output_nodes = []

    for leaf in input_stream:
        d = leaf.depth
        queues[d].append(leaf)

        while d > 0 and len(queues[d]) >= queue_capacity:
            internal_node = {'type': 'internal', 'children': queues[d]}
            output_nodes.append(internal_node)
            
            queues[d] = []
            internal_node['depth'] = d - 1
            queues[d - 1].append(internal_node)
            d -= 1

    # Flush remaining nodes to complete the tree structure
    for d in range(max_depth, -1, -1):
        while queues[d]:
            if d == 0:
                output_nodes.append({'type': 'root', 'children': queues[d]})
                break
            internal_node = {'type': 'internal', 'children': queues[d]}
            output_nodes.append(internal_node)
            queues[d] = []
            internal_node['depth'] = d - 1
            queues[d - 1].append(internal_node)
            d -= 1
    return output_nodes
```

**Parameters:**
- `queue_capacity`: Determines the memory footprint of the construction process [S3].
- `max_depth`: The maximum depth of the octree, corresponding to the leaf level [S3].

**Edge Cases and Pitfalls:**
- **Empty Nodes:** The basic version processes empty nodes implicitly through the queue structure; if a queue does not fill with non-empty nodes, the algorithm waits for more input or flushes at the end [S3].
- **Partial Queues:** At the end of the input, queues may not be full; the algorithm must still form parent nodes from the remaining children to complete the tree hierarchy [S3].
- **Memory Constraints:** The method is designed to be out-of-core, but if `queue_capacity` is too small, disk I/O overhead may dominate performance [S3].

## Subtopics

### [Brute Force SVO Construction](1704-brute-force-svo-construction.md)
Builds the entire SVO in main memory recursively, then prunes empty branches. Chosen for implementation simplicity and recursive clarity, but limited by high memory consumption and poor cache coherence.

### [Out-of-Core SVO Construction via Morton Order](1885-out-of-core-svo-construction-via-morton-order.md)
Constructs an SVO by reading voxels in groups of eight, generating parent nodes, and flushing buffers to disk. Leverages Morton order to eliminate the need for a top-down parent search.

### [Sparse Voxel Octree Construction (Optimized Version)](1900-sparse-voxel-octree-construction-optimized-version.md)
Calculates the number of empty nodes between consecutive input leaves and directly inserts empty parent nodes into higher-level queues. Chosen when construction speed is critical, as it reduces queue operations and is over two orders of magnitude faster than the basic version.

### [Sparse Voxel Octree Construction via Morton Code Sorting](2227-sparse-voxel-octree-construction-via-morton-code-sorting.md)
Pre-sorts all points into Morton order for spatial locality, allowing $O(1)$ range queries via binary search instead of tree traversal during construction. Chosen for static SVOs where pre-sorting is feasible.

### [Dynamic Octree Growth Algorithm](2375-dynamic-octree-growth-algorithm.md)
Dynamically increases depth and spatial extent as new voxels are processed, centering the root at the boundary between -1 and 0 to handle negative coordinates. Chosen when the scene bounding box is unknown or highly variable.

### [Sparse Voxel Octree Construction (Queue-Based Collapse)](2457-sparse-voxel-octree-construction-queue-based-collapse.md)
Maintains fixed-size queues per depth level and collapses homogeneous subtrees into single leaf or invalid nodes. Chosen for compressing the structure in a single pass without full in-memory storage or pre-sorting.

### [Sparse Voxel Octree (SVO) Builder](2617-sparse-voxel-octree-svo-builder.md)
Details a GPU compute shader pipeline for level-by-level node allocation, attribute injection, and mipmap generation. Chosen for real-time global illumination and pathfinding on GPUs.

## Operating characteristics
- **Time Complexity:** $O(N)$ for the streaming pass, where $N$ is the number of non-empty voxels, though queue management and disk I/O add constant overhead [S3].
- **Memory Complexity:** $O(D \cdot C)$, where $D$ is the depth and $C$ is the queue capacity, keeping memory usage logarithmic in the size of the SVO [S3].
- **Performance:** On a Dell Precision T7500 (Intel Xeon X5650, 7200 RPM SATA II), the out-of-core method with 128 MB or 1 GB memory is roughly as fast as an in-core method with 8 GB memory, but uses up to 64 times less memory [S3]. The construction process itself consumes only roughly 1.6 MB of memory [S3].
- **Strengths:** Low memory footprint, suitable for large scenes that exceed available RAM, simple streaming logic [S3].
- **Limitations:** Slower than optimized versions due to processing empty nodes and I/O overhead; the optimized version is over two orders of magnitude faster [S3].
- **When to Use:** When memory is constrained and the scene is large, or when a simple out-of-core streaming approach is preferred [S3].
- **When Not to Use:** When real-time construction is required, memory is sufficient, or the scene has significant empty space (use the optimized version) [S3].

## Background
The Sparse Voxel Octree (SVO) is a hierarchical representation of a voxel grid where nodes store 8 child descriptors (empty subtree, solid leaf with packed color, or node index) [S2, unofficial]. The out-of-core construction method was introduced to handle large voxel grids that exceed available memory by processing the grid in Morton order and streaming nodes to disk [S3]. The basic version serves as the foundation for more optimized variants that reduce the overhead of empty node processing [S3]. It is used in out-of-core volume rendering and global illumination pipelines [S3].
