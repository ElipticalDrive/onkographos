# Sparse Voxel Octree Construction (Basic Version)

Also called: Basic SVO Construction, SVO Construction, basic version

## Overview
This method constructs a Sparse Voxel Octree (SVO) from a stream of voxel data (typically Morton codes) by maintaining per-depth queues and merging nodes when queues fill up, writing intermediate results to disk to manage memory constraints [S3]. It differs from its siblings, such as [Brute Force SVO Construction](1704-brute-force-svo-construction.md) and [Sparse Voxel Octree Construction via Morton Code Sorting](2227-sparse-voxel-octree-construction-via-morton-code-sorting.md), by processing the input in a single streaming pass without requiring the entire octree to reside in memory or pre-sorting all points globally [S3]. It is chosen for its out-of-core capability and simplicity, but is limited by the overhead of processing empty nodes compared to optimized variants [S3].

## How it works
**Inputs and Outputs:**
- Input: A stream of non-empty voxel leaf nodes, typically sorted by Morton code (Z-order), generated by a voxelization step [S3]. Each leaf node contains its Morton code and associated data (e.g., color, normal) [S3].
- Output: A Sparse Voxel Octree written to disk (or a flat buffer), where nodes are stored with spatial locality (siblings adjacent) [S3].

**Data Structures:**
1.  **Queues:** An array of queues, one for each depth level $d$ from $0$ (root) to $D$ (leaf level). The size of each queue is fixed and determined by the available memory budget [S3].
2.  **Node Representation:** The output SVO uses a compact representation: 24 bytes per node, consisting of a 64-bit reference to the first child, a 1-byte offset for every child (8 children $\times$ 1 byte = 8 bytes, but the source specifies "1-byte offset for every child" alongside a 64-bit reference and data reference; note: [S3] states "24 bytes per node: a 64-bit reference to the first child of the node, a 1-byte offset for every child of the node, and a 64-bit reference to the data associated with the node." This implies $8 + 8 + 8 = 24$ bytes, where the "offsets" might be packed or the description implies a specific layout. However, [S2, unofficial] describes a different layout: `SvoNode` struct with 8 `u32` children (32 bytes). The basic version algorithm in [S3] is generic. We describe the algorithmic steps from [S3] which are implementation-agnostic regarding the exact byte layout, but rely on the queue mechanism.) [S3].
    - *Note:* [S2, unofficial] provides a specific implementation layout for a different context (GPU uniform buffer), but the core algorithm in [S3] is the primary source for the "Basic Version" logic.

**Algorithm Steps:**
1.  Initialize an empty queue for each depth level $d \in [0, D]$.
2.  Initialize a depth counter $d$ to the maximum depth $D$ (leaf level) [S3].
3.  While the input stream is not empty:
    a. Consume the next leaf node $l$ from the input stream [S3].
    b. Push $l$ onto the queue corresponding to its depth $d$ (i.e., `queues[d].push_back(l)`) [S3].
    c. Set $d$ to the depth of the pushed leaf node [S3].
    d. While $d > 0$ and `queues[d]` is full:
        i. Create a new internal node $p$ [S3].
        ii. Set the children of $p$ to the child offsets (or references) of the elements currently in `queues[d]` [S3].
        iii. Write the non-empty elements of `queues[d]` to disk/output [S3].
        iv. Clear `queues[d]` [S3].
        v. Push the new internal node $p$ onto `queues[d-1]` [S3].
        vi. Decrement $d$ by 1 [S3].
4.  After the input stream is exhausted, flush any remaining nodes in the queues to the output, starting from the deepest non-empty queue up to the root [S3].
5.  Write the root node to the output [S3].

**Parameters:**
- `queue_capacity`: Determines the memory footprint. Smaller capacities increase I/O operations but reduce memory usage [S3].
- `max_depth`: The depth of the octree, determined by the voxelization resolution and world size [S3].

**Edge Cases and Pitfalls:**
- **Empty Nodes:** The basic version processes empty nodes implicitly by the structure of the queues. If a queue does not fill up with non-empty nodes, the resulting internal node may have children that are empty or invalid. The algorithm assumes that if a queue is full, it contains valid children to form a parent [S3].
- **Partial Queues:** At the end of the input, queues may not be full. The algorithm must still form parent nodes from the remaining children to complete the tree [S3].
- **Memory Constraints:** The method is designed to be out-of-core, but if `queue_capacity` is too small, I/O overhead may dominate performance [S3].

## Subtopics

### [Brute Force SVO Construction](1704-brute-force-svo-construction.md)
Builds the entire SVO in main memory recursively, then prunes. Chosen for simplicity, but high memory usage.

### [Out-of-Core SVO Construction via Morton Order](1885-out-of-core-svo-construction-via-morton-order.md)
Reads voxels in groups of eight, generating parents and flushing buffers. Leverages Morton order to avoid top-down search.

### [Sparse Voxel Octree Construction (Optimized Version)](1900-sparse-voxel-octree-construction-optimized-version.md)
Calculates empty nodes between consecutive leaves and inserts empty parents directly, reducing queue operations. Over two orders of magnitude faster than the basic version.

### [Sparse Voxel Octree Construction via Morton Code Sorting](2227-sparse-voxel-octree-construction-via-morton-code-sorting.md)
Pre-sorts points into Morton order for spatial locality, allowing $O(1)$ range queries.

### [Dynamic Octree Growth Algorithm](2375-dynamic-octree-growth-algorithm.md)
Dynamically increases depth and extent, handling negative coordinates by centering the root.

### [Sparse Voxel Octree Construction (Queue-Based Collapse)](2457-sparse-voxel-octree-construction-queue-based-collapse.md)
Maintains fixed-size queues and collapses homogeneous subtrees into single leaves.

### [Sparse Voxel Octree (SVO) Builder](2617-sparse-voxel-octree-svo-builder.md)
GPU compute shader pipeline for level-by-level allocation and mipmap generation.

## Operating characteristics
- **Time Complexity:** $O(N \log N)$ or $O(N)$ depending on input sorting, where $N$ is the number of non-empty voxels. The basic version processes each voxel once, but queue management and I/O add overhead [S3].
- **Memory Complexity:** $O(D \cdot C)$, where $D$ is the depth and $C$ is the queue capacity. This is logarithmic in the size of the SVO if $C$ is small [S3].
- **Performance:** On a Dell Precision T7500 (Intel Xeon X5650, 7200 RPM SATA II), the out-of-core method with 128 MB or 1 GB memory is roughly as fast as an in-core method with 8 GB memory, but uses up to 64 times less memory [S3].
- **Strengths:** Low memory footprint, suitable for large scenes that do not fit in RAM, simple implementation [S3].
- **Limitations:** Slower than optimized versions due to processing empty nodes and I/O overhead. The optimized version is over two orders of magnitude faster [S3].
- **When to Use:** When memory is constrained and the scene is large. When I/O bandwidth is high relative to CPU processing.
- **When Not to Use:** When real-time construction is required and memory is sufficient. When the scene has significant empty space (use optimized version) [S3].

## Background
The Sparse Voxel Octree (SVO) is a hierarchical representation of a voxel grid, where nodes store 8 child descriptors. Each descriptor is either 0 (empty), a solid leaf with packed color, or an index to a node buffer [S2, unofficial]. The out-of-core construction method was introduced to handle large voxel grids that exceed available memory by processing the grid in Morton order and streaming nodes to disk [S3]. The basic version serves as the foundation for more optimized variants that reduce the overhead of empty node processing [S3].
