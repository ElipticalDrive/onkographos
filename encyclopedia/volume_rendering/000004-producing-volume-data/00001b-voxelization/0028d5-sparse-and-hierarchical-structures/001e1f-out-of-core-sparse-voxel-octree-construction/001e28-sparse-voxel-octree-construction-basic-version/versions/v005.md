# Sparse Voxel Octree Construction (Basic Version)

Also called: Basic SVO Construction, SVO Construction, basic version

## Overview
This method constructs a Sparse Voxel Octree (SVO) from a stream of non-empty voxel Morton codes by maintaining fixed-size queues per depth level, merging nodes when a queue fills up, and writing non-empty nodes to disk [S3]. It differs from its siblings, such as [Brute Force SVO Construction](1704-brute-force-svo-construction.md), by avoiding complex sorting or full in-memory tree storage in favor of a streaming, bottom-up approach that keeps memory usage logarithmic in the size of the SVO [S3]. Trade-offs include higher construction time compared to optimized variants due to processing empty nodes, but it offers simplicity and low memory footprint [S3].

## How it works
**Inputs and Outputs:**
- **Input:** A stream of non-empty voxel leaves, sorted by Morton code (Z-order). Each leaf contains its depth and Morton code.
- **Output:** A serialized SVO written to disk (or memory buffer), where nodes are stored in Morton order (siblings adjacent) [S3].

**Data Structures:**
- **Queues:** An array of queues, one for each depth level $d$ from $0$ to $max\_depth$. Each queue holds child descriptors (indices or pointers to children). The size of each queue is fixed, typically 8 or a power of two, sufficient to hold the children of a single internal node before it must be promoted [S3].
- **Node Descriptor:** A 32-bit or 64-bit value representing a child. In the basic version, this is often an index into a node buffer or a special value for empty/solid leaves [S2, unofficial][S3].
- **Node Buffer:** A dynamic array or disk file storing the actual `SvoNode` structures.

**SvoNode Layout:**
- **Basic Version (from [S3]):** 24 bytes per node.
    - 64-bit reference to the first child of the node.
    - 1-byte offset for every child of the node (8 bytes total for 8 children).
    - 64-bit reference to the data associated with the node (e.g., color, density).
- **Alternative Layout (from [S2, unofficial]):** 32 bytes per node.
    - 8 `u32` children array.
    - Each child is either `0` (empty), `0x8000_0000 | packed_color` (solid leaf), or an index into a flat storage buffer [S2, unofficial].

**Algorithm Steps:**
1. Initialize an empty queue for each depth level $d \in [0, max\_depth]$.
2. Initialize a depth counter $d$ to the depth of the input leaves (typically the maximum resolution depth).
3. While input stream is not empty:
    a. Consume the next leaf node $l$ from the input stream.
    b. Push $l$ onto the queue corresponding to its depth $d$ (`queues[d].push_back(l)`).
    c. Set $d$ to the depth of the pushed leaf.
    d. While $d > 0$ and `queues[d]` is full:
        i. Create a new internal node $p$.
        ii. Set the children of $p$ to the child offsets/indices stored in `queues[d]`.
        iii. Write the non-empty elements of `queues[d]` to the output node buffer (if not already written) [S3].
        iv. Clear `queues[d]`.
        v. Push the new internal node $p$ onto `queues[d-1]`.
        vi. Decrement $d$ by 1.
4. After the input stream is exhausted, flush any remaining nodes in the queues up to the root.
5. Write the root node index to the output header.

**Pseudocode:**
```python
def build_svo_basic(input_stream, max_depth):
    # Initialize queues for each depth level
    queues = [Queue() for _ in range(max_depth + 1)]
    
    # Process input leaves
    for leaf in input_stream:
        d = leaf.depth
        queues[d].push_back(leaf)
        
        # Try to merge nodes up the tree
        while d > 0 and queues[d].is_full():
            # Create internal node from full queue
            internal_node = create_internal_node(queues[d])
            
            # Write non-empty children to disk/buffer if needed
            # Note: In basic version, children are written when their parent is formed
            write_nodes_to_output(queues[d])
            
            # Clear the current level queue
            queues[d].clear()
            
            # Push the new internal node to the parent level
            queues[d-1].push_back(internal_node)
            
            # Move up one level
            d -= 1
            
    # Flush remaining nodes at the top
    d = max_depth
    while d > 0 and not queues[d].is_empty():
        internal_node = create_internal_node(queues[d])
        write_nodes_to_output(queues[d])
        queues[d].clear()
        queues[d-1].push_back(internal_node)
        d -= 1
        
    # Handle root if necessary
    if not queues[0].is_empty():
        root = create_internal_node(queues[0])
        write_nodes_to_output(queues[0])
        
    return root
```

**Parameters:**
- `max_depth`: The maximum depth of the octree, determined by the resolution of the input voxel grid. Typical value: 8-12 [S1, unofficial][S3].
- `queue_size`: The capacity of each queue. Must be at least 8 to hold all children of an internal node. Typically 8 or a power of two for efficient memory management [S3].

**Edge Cases and Pitfalls:**
- **Empty Input:** If the input stream is empty, the SVO is empty.
- **Non-Power-of-Two Grids:** The input voxel grid dimensions should be powers of two to simplify Morton code generation and tree alignment [S2, unofficial].
- **Memory Pressure:** If the queue size is too small, frequent disk I/O may occur. If too large, memory usage increases. Balance based on available RAM [S3].
- **Precision:** Morton codes must be generated with sufficient bit depth to avoid collisions at the target resolution. 64-bit Morton codes are recommended for high resolutions [S3].

## Subtopics

### [Brute Force SVO Construction](1704-brute-force-svo-construction.md)
Brute Force SVO Construction is a top-down algorithm that builds a complete octree in memory and subsequently prunes empty branches to form a Sparse Voxel Octree (SVO). It differs from its siblings, such as [Sparse Voxel Octree Construction via Morton Code Sorting](2227-sparse-voxel-octree-construction-via-morton-code-sorting.md), by avoiding complex sorting or streaming logic in favor of a simple recursive subdivision and depth-first search. This method is chosen when implementation simplicity is prioritized over memory efficiency and construction speed.

### [Out-of-Core SVO Construction via Morton Order](1885-out-of-core-svo-construction-via-morton-order.md)
This method constructs a Sparse Voxel Octree (SVO) from voxel grid data sorted in Morton order by reading voxels in groups of eight, generating parent nodes, and flushing buffers to disk to manage memory constraints. It differs from point-based global illumination methods (e.g., Tabellion EGSR2011) by leveraging the fact that voxel data spans the whole grid space, which eliminates the need for a top-down search to find parent nodes.

### [Sparse Voxel Octree Construction (Optimized Version)](1900-sparse-voxel-octree-construction-optimized-version.md)
This method constructs a Sparse Voxel Octree (SVO) from a stream of non-empty voxel Morton codes by optimizing the handling of empty space. Unlike the basic version, which inserts empty child nodes individually, this approach calculates the number of empty nodes between consecutive input leaves and directly inserts empty parent nodes into higher-level queues. This reduces the number of queue operations significantly, as pushing back $2^d$ empty nodes is equivalent to pushing back a single node at the level above. It builds on [Sparse Voxel Octree Construction (Basic Version)](1694-sparse-voxel-octree-construction-basic-version.md).

### [Sparse Voxel Octree Construction via Morton Code Sorting](2227-sparse-voxel-octree-construction-via-morton-code-sorting.md)
This method constructs a static Sparse Voxel Octree (SVO) from a set of 3D points or voxels by converting them to Z-order (Morton) codes, sorting them for spatial locality, and recursively partitioning the sorted array into octree nodes and leaf voxels. It differs from dynamic insertion methods by pre-sorting all points into Morton order, which guarantees spatial locality and allows $O(1)$ range queries via binary search instead of tree traversal during construction.

### [Dynamic Octree Growth Algorithm](2375-dynamic-octree-growth-algorithm.md)
The Dynamic Octree Growth Algorithm constructs a Sparse Voxel Octree (SVO) by dynamically increasing its depth and spatial extent as new voxels are processed, rather than pre-calculating the size from the input data. It handles both positive and negative coordinates by centering the root at the boundary between -1 and 0, ensuring the tree grows to encompass all input data without pre-calculating the scene's bounding box. It differs from static voxelization by adapting resolution locally and handling boundary conditions through recursive growth.

### [Sparse Voxel Octree Construction (Queue-Based Collapse)](2457-sparse-voxel-octree-construction-queue-based-collapse.md)
This method constructs a Sparse Voxel Octree (SVO) from a stream of indexed leaves by maintaining a fixed-size array of queues, one per tree depth level, and collapsing homogeneous subtrees into single leaf or invalid nodes to compress the structure. It differs from brute-force or sorting-based builders by processing leaves in a single pass without requiring full in-memory tree storage or pre-sorting.

### [Sparse Voxel Octree (SVO) Builder](2617-sparse-voxel-octree-svo-builder.md)
The Sparse Voxel Octree (SVO) Builder is a GPU-based algorithm that constructs a hierarchical Sparse Voxel Octree from a list of voxelized geometry fragments using compute shaders. It solves the problem of efficiently converting triangle meshes into a compact, hierarchical voxel representation suitable for real-time global illumination techniques like Voxel Cone Tracing. Unlike in-core CPU methods or grid-based GPU approaches, this method generates the SVO directly on the GPU by processing the voxel list level-by-level, flagging nodes, allocating memory for internal nodes, and storing leaf nodes. It is distinct from [Brute Force SVO Construction](1704-brute-force-svo-construction.md) by its use of compute shaders for parallel level-by-level construction, and from [Out-of-Core SVO Construction via Morton Order](1885-out-of-core-svo-construction-via-morton-order.md) by its reliance on pre-allocated buffers and specific atomic merging strategies for fragment consolidation.

### SSVDAG Construction Algorithm
An out-of-core, bottom-up external-memory algorithm that reduces an SVO to a minimal SSVDAG [S4, unofficial]. The algorithm operates bottom-up, alternating phases at each level of the octree hierarchy [S4, unofficial]. Phase 1: Cluster nodes representing similar subtrees (identical up to a similarity transform) and replace them with a single representative node [S4, unofficial]. Phase 2: Replace pointers in the immediately higher level to the clustered nodes with tagged pointers to the single representative. The tag encodes the required similarity transform [S4, unofficial]. Phase 3: Sort the representatives by their reference count to facilitate variable-bit-rate encoding of the pointers [S4, unofficial]. The method assumes the original scene has geometric redundancy (many subtrees similar with respect to a reflective transformation) [S4, unofficial].

## Operating characteristics
- **Time Complexity:** $O(N \log N)$ or $O(N)$ depending on input sorting, where $N$ is the number of non-empty voxels. The basic version spends significant time processing empty nodes, making it slower than optimized versions [S3].
- **Memory Complexity:** $O(\log M)$, where $M$ is the size of the SVO, because it processes data in a streaming manner and only keeps a small number of queues in memory [S3].
- **Measured Performance:** On a Dell Precision T7500 workstation (Intel Xeon X5650 CPU, 7200 RPM SATA II disk), the out-of-core method using 128 MB or 1 GB memory is roughly as fast as an in-core method using 8 GB memory, but uses up to 64 times less memory [S3]. The optimized version is over two orders of magnitude faster than the non-optimized (basic) version because the non-optimized version spends significant time processing empty nodes [S3].
- **Strengths:** Low memory footprint, suitable for out-of-core processing, simple implementation.
- **Limitations:** Slower construction time compared to optimized or sorting-based methods due to empty node processing.
- **When to Use:** When memory is constrained, or when implementing a simple baseline for SVO construction.
- **When Not to Use:** When construction speed is critical, or when the scene has low geometric redundancy (making optimized empty node handling less effective).

## Background
The Sparse Voxel Octree (SVO) is a hierarchical data structure used in volume rendering and global illumination to efficiently represent sparse 3D voxel data. The basic construction algorithm described here was introduced in the context of out-of-core SVO construction to handle very large scenes that do not fit in main memory [S3]. It builds on the concept of Morton codes (Z-order curves) to ensure spatial locality of voxels, which is crucial for efficient tree construction and traversal [S3]. The method has been extended and optimized in subsequent works, such as the optimized version that handles empty nodes more efficiently [S1, unofficial], and GPU-based builders for real-time applications [S4, unofficial].
