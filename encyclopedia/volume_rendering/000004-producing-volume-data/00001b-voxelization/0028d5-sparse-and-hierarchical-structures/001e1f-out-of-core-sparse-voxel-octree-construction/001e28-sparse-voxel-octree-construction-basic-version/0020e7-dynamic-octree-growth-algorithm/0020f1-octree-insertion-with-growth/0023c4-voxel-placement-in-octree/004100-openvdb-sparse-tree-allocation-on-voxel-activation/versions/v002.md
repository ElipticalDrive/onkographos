# OpenVDB Sparse Tree Allocation on Voxel Activation

Also called: VDB node initialization, VDB tile instantiation

## Overview
This method describes the memory allocation and node initialization behavior of the OpenVDB sparse tree when a new voxel is activated at a specific coordinate [S1, unofficial]. It solves the problem of understanding why activating a single sparse voxel can result in a disproportionately large memory footprint due to the bulk initialization of sibling tiles along the path to the leaf [S1, unofficial]. It is distinct from standard dense voxelization because it allocates full tile structures for inactive siblings at every level of the octree hierarchy, rather than leaving them as null pointers or compact bitfields [G].

## How it works

### Inputs and Outputs
*   **Input**: A 3D integer coordinate `ptIndexCoordinates` (e.g., `{1, 1, 1}`) representing the voxel to activate [S1, unofficial].
*   **Input**: A `DataContainer` object containing the voxel's data, extending `Vec3i` with space for normals, sized at $0.000032$ MB per instance [S1, unofficial].
*   **Output**: An updated OpenVDB grid where the tree structure is modified to include the path to the target leaf, and all sibling nodes at each level are instantiated as tiles holding the background value [S1, unofficial].

### Data Structures and Layout
The OpenVDB tree uses a hierarchical structure where nodes are allocated in powers of 8 per dimension [S1, unofficial]. The allocation follows this layout for the levels involved in the reference experiment: Level 1 allocates $8^3 = 512$ nodes, Level 2 allocates $16^3 = 4096$ nodes, and Level 3 allocates $32^3 = 32768$ nodes [S1, unofficial]. When a path is created, the tree does not just allocate the specific nodes on the path; instead, at each level traversed, all direct children of the current node are instantiated as tiles [S1, unofficial]. These tiles hold the grid's background value for inactive voxels [S1, unofficial].

### Numbered Steps
1.  **Set Value**: Call `acc.setValue(ptIndexCoordinates, std::move(data))` to assign the data to the coordinate [S1, unofficial].
2.  **Mark Active**: Call `acc.setActiveState(ptIndexCoordinates, true)` to mark the voxel as active [S1, unofficial].
3.  **Traverse and Create**: The tree traverses from the root to the leaf node containing `ptIndexCoordinates` [S1, unofficial].
4.  **Initialize Siblings**: At each level of the traversal, all sibling nodes (children of the current node that are not on the path to the target) are instantiated as tiles with the background value [S1, unofficial].

### Pseudocode
The following pseudocode illustrates the allocation logic derived from the source analysis. It implements the traversal and tile instantiation behavior described in the steps.

```python
def allocate_voxel_path(root, coord, tile_sizes, background_value):
    """
    Simulates OpenVDB sparse tree allocation on voxel activation.
    Traverses from root to leaf, creating nodes on the path and
    instantiating all 8 children at each level as tiles.
    """
    current_node = root
    for tile_size in tile_sizes:
        # Calculate child index for the target coordinate at this level
        # Use floor division to correctly handle negative coordinates
        idx_x = coord[0] // tile_size
        idx_y = coord[1] // tile_size
        idx_z = coord[2] // tile_size
        
        # Combine into 3-bit child index (0-7)
        child_idx = ((idx_x & 0x7) << 6) | ((idx_y & 0x7) << 3) | (idx_z & 0x7)

        # Instantiate all 8 children as tiles with the background value
        for i in range(8):
            current_node.children[i] = Tile(value=background_value)

        # Move to the child on the path (create if missing)
        if current_node.children[child_idx] is None:
            current_node.children[child_idx] = InternalNode()
        current_node = current_node.children[child_idx]
    return current_node
```

### Parameters and Typical Values
*   **`ptIndexCoordinates`**: 3D integer coordinate. Example: `{1, 1, 1}` [S1, unofficial].
*   **`DataContainer`**: Custom data type. Size: $0.000032$ MB per instance [S1, unofficial].
*   **Background Value**: The default value stored in the instantiated sibling tiles [S1, unofficial].

### Edge Cases and Pitfalls
*   **Memory Bloat**: Inserting points far from existing allocated regions triggers a broad initialization of sibling tiles, causing a disproportionate memory increase relative to the number of active voxels [S1, unofficial].
*   **Custom Data Types**: Using custom datatypes increases the memory footprint by approximately 5x compared to native types (e.g., `FloatGrid`) for the same single-voxel activation [S1, unofficial].
*   **Leaf Node Reuse**: Adding additional points within the same leaf node (e.g., coordinates below `(8,8,8)`) does not increase the memory footprint, as the tiles are already allocated [S1, unofficial].

## Operating characteristics

### Time and Memory Complexity
*   **Memory Complexity**: The memory cost is not linear with the number of active voxels; it depends on the depth of the octree and the sparsity of the activation [S1, unofficial]. Activating a single voxel at `(1,1,1)` with a custom datatype results in a total memory footprint of $1.50162$ MB [S1, unofficial]. For a native `FloatGrid`, the same activation results in $0.307584$ MB [S1, unofficial].
*   **Scaling**: The memory increase scales with the distance of the new point from the root/allocated regions [S1, unofficial]. Adding `(0,0,7)` (same leaf) adds $0$ MB [S1, unofficial]. Adding `(0,0,8)` (Level 1) adds $0.01648$ MB [S1, unofficial]. Adding `(0,0,16)` (Level 1) adds $0.01648$ MB [S1, unofficial]. Adding `(0,0,128)` (Level 2) adds $0.181356$ MB [S1, unofficial]. Adding `(0,0,4096)` (Level 3) adds $1.50028$ MB [S1, unofficial].

### Strengths and Limitations
*   **Strengths**: Provides a consistent interface for sparse data access; tiles allow for efficient storage of homogeneous regions (background values) [G].
*   **Limitations**: High memory overhead for sparse datasets with points distributed across different octree levels; the initialization of sibling tiles can lead to significant memory waste if points are widely scattered [S1, unofficial].

## Background
This behavior was documented in a GitHub issue discussion regarding the `vdb_mapping` package, where a user observed unexpected memory usage when activating a single voxel with a custom data type [S1, unofficial]. The analysis was provided by a contributor who replicated the results and explained the underlying OpenVDB allocation strategy [S1, unofficial].
