# Dynamic Sparse Voxel Octree with Morton Codes

Also called: rapid-svo

## Overview
A single-header C++ implementation of a dynamic sparse voxel octree using integer coordinates and Morton codes, designed for micro-optimized CPU-based voxel physics simulations in chunked procedural game worlds [S1, unofficial]. It distinguishes itself by providing bulk allocation, point queries, and deallocation operations optimized for high-throughput voxel manipulation rather than static storage [S1, unofficial].

## How it works
**Inputs and Outputs:**
The method takes an array of voxel objects containing integer coordinates as input [S1, unofficial]. It outputs a tree structure supporting batch insertion, point queries returning a pointer or `nullptr`, and removal operations [S1, unofficial].

**Data Structures:**
The tree is templated on three parameters: `<MortonType, VoxelFormat, DetailsInfo>` [S1, unofficial]. The `DetailsInfo` struct (`rapid_svo::details_info`) contains `_discard_overflow` (bool) and `_limit_max_bounds` (array of 3 integers) [S1, unofficial]. `MortonType` specifies the bit-width of the Morton code [S1, unofficial]. `VoxelFormat` defines the voxel data layout [S1, unofficial].

**Morton Code Generation:**
Voxel positions are encoded into Morton codes using lookup tables provided by the `libmorton` dependency [S1, unofficial]. The encoding is performed via `encode_position` on a position array [S1, unofficial].

**Parameters:**
`_limit_max_bounds` defines the maximum spatial extent per dimension, with typical benchmark values of `{16,16,16}`, `{32,32,32}`, `{64,64,64}`, `{128,128,128}`, `{256,256,256}`, `{512,512,512}`, and `{1024,1024,1024}` [S1, unofficial]. `_discard_overflow` is a boolean flag that discards voxels exceeding `_limit_max_bounds` [S1, unofficial].

**Algorithm Steps:**
1. Initialize a `rapid_svo::tree` instance with the desired `MortonType`, `VoxelFormat`, and `DetailsInfo` [S1, unofficial].
2. Prepare a contiguous array of voxel data and call `tree.alloc_bulk(voxels.data(), count)` to insert the batch [S1, unofficial].
3. Query a voxel by calling `tree.get(position)`, which returns a pointer to the voxel if found, or `nullptr` otherwise [S1, unofficial].
4. Remove a voxel by calling `tree.dealloc(position)` [S1, unofficial].

**Edge Cases and Pitfalls:**
If `_discard_overflow` is true, voxels outside `_limit_max_bounds` are silently discarded [S1, unofficial]. The choice of `MortonType` (16-bit vs 32-bit) limits the maximum spatial extent and affects performance [S1, unofficial]. Performance varies significantly between compilers, with Clang yielding considerably faster results than MSVC, though the exact optimizations are undetermined [S1, unofficial].

## Operating characteristics
**Time and Memory Complexity:**
Not given in the sources. The implementation is described as micro-optimized for CPU performance [S1, unofficial].

**Measured Performance:**
Benchmarks conducted on AMD Ryzen 7 1800X, 32GB DDR4, Windows 10 [S1, unofficial]:
- Clang 19.1.6, 16b Morton, 16^3 grid: Alloc 58.28M vox/s, Get 176.50M vox/s, Dealloc 116.97M vox/s [S1, unofficial].
- Clang 19.1.6, 32b Morton, 128^3 grid: Alloc 29.91M vox/s, Get 89.40M vox/s, Dealloc 51.23M vox/s [S1, unofficial].
- MSVC 1937 (VS 17.7), 16b Morton, 16^3 grid: Alloc 22.73M vox/s, Get 42.57M vox/s, Dealloc 84.40M vox/s [S1, unofficial].

**Strengths and Limitations:**
Strengths include high throughput for bulk operations and point queries, making it suitable for dynamic voxel physics in procedural worlds [S1, unofficial]. Limitations include performance sensitivity to compiler choice and CPU-only execution [S1, unofficial].

**When to Use:**
Use for CPU-based voxel physics simulations requiring fast dynamic insertion, removal, and querying of voxels in chunked procedural worlds [S1, unofficial].

## Background
Originated as a single-header C++ implementation by Severi Suominen, prototyped for lightning-fast voxel physics simulations on CPU in chunked procedural game worlds [S1, unofficial]. It relies on `libmorton` for fast Morton code generation via lookup tables and `glm` for math types and functions [S1, unofficial].
