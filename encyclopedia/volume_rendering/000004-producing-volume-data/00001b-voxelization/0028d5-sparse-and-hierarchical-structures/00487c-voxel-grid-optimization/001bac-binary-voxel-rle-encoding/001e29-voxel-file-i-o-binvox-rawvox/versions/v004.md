# Voxel File I/O (binvox/rawvox)

Also called: Binvox File Writing, Sparse Voxel Grid Export, Text-based Voxel Output, WriteBinvox

## Overview
This method serializes a 3D voxel grid into standard legacy file formats, primarily `binvox` and `rawvox`, to enable interoperability with external visualization tools and pipelines. It solves the problem of persisting occupancy data generated by voxelization or sparse voxel structures in a structured, recoverable format. Unlike [MagicaVoxel File Output](1752-magicavoxel-file-output.md) which uses a sparse XYZI representation, or [Voxel File I/O](2786-voxel-file-i-o.md) which covers a broader set of generic formats, this method specifically implements the dense binary RLE encoding of `binvox` and the simple dense binary/text headers of `rawvox` [S1, S3, unofficial].

## How it works
The method supports multiple output variants depending on the target format. The core inputs are the voxel grid data (accessed via `Filled(x,y,z)` or a direct array `_grid`), grid dimensions (`size_x_`, `size_y_`, `size_z_`), bounding box lower bounds (`lb_`), and voxel unit sizes (`unit_`). The outputs are binary or text files containing headers and voxel data.

### Binvox Format
The `binvox` format stores occupancy data using a dense binary run-length encoding (RLE) [S1, unofficial].

**Data Structures:**
*   `size_x_, size_y_, size_z_`: Integer dimensions of the grid.
*   `lb_`: Array of 3 doubles representing the lower bound coordinates of the bounding box.
*   `unit_`: Array of 3 doubles representing the physical size of a voxel.
*   `bound_`: Bounding box object with a `norm()` method returning the maximum dimension magnitude.
*   `Filled(x, y, z)`: Function returning boolean occupancy.

**Steps:**
1.  Open the output file in binary mode.
2.  Calculate dimensions `bx = size_x_`, `by = size_y_`, `bz = size_z_`.
3.  Calculate `norm_translate` from `lb_` and `norm_scale` from `bound_.norm()`.
4.  Write the header lines as ASCII text followed by newlines:
    *   Line 1: `#binvox 1`
    *   Line 2: `dim bx by bz`
    *   Line 3: `translate -norm_translate[0] -norm_translate[2] -norm_translate[1]` (Note: Y and Z coordinates are swapped and negated relative to standard Cartesian, consistent with binvox convention).
    *   Line 4: `scale norm_scale`
    *   Line 5: `data`
5.  Initialize traversal indices `x = lx`, `y = ly`, `z = lz` (where `lx, ly, lz` are the lower bounds of the active grid range).
6.  Loop while `x <= ux` (upper bound):
    *   Get `value = Filled(x, y, z)`.
    *   Initialize `count = 0`.
    *   Inner loop: While `x <= ux` AND `count < 255` AND `value == Filled(x, y, z)`:
        *   Increment `z`.
        *   If `z > uz`, reset `z = lz` and increment `y`.
        *   If `y > uy`, reset `y = ly` and increment `x`.
        *   Increment `count`.
    *   If `value` is true, add `count` to `total_ones` (optional metadata).
    *   Write two bytes to the output stream:
        *   Byte 1: `value` (0 for empty, 1 for filled).
        *   Byte 2: `count` (unsigned char, 1-255).
    *   Increment `bytes_written` by 2.
7.  Close the output stream.

**Pseudocode:**
```python
def write_binvox(filepath, size_x, size_y, size_z, lb, unit, bound, filled_func):
    with open(filepath, 'wb') as f:
        # Calculate normalization parameters
        norm_translate = lb
        norm_scale = bound.norm()
        
        # Write ASCII header
        f.write(b'#binvox 1\n')
        f.write(f'dim {size_x} {size_y} {size_z}\n'.encode('ascii'))
        # Note: binvox convention swaps Y and Z and negates them in translate
        f.write(f'translate {-norm_translate[0]} {-norm_translate[2]} {-norm_translate[1]}\n'.encode('ascii'))
        f.write(f'scale {norm_scale}\n'.encode('ascii'))
        f.write(b'data\n')
        
        # RLE Encoding
        lx, ly, lz = 0, 0, 0 # Assuming 0-indexed internal grid for traversal
        ux, uy, uz = size_x - 1, size_y - 1, size_z - 1
        
        x, y, z = lx, ly, lz
        while x <= ux:
            value = filled_func(x, y, z)
            count = 0
            
            # Run-length encode consecutive identical values
            while x <= ux and count < 255 and filled_func(x, y, z) == value:
                z += 1
                if z > uz:
                    z = lz
                    y += 1
                    if y > uy:
                        y = ly
                        x += 1
                count += 1
            
            # Write value and count
            f.write(bytes([1 if value else 0]))
            f.write(bytes([count]))
            
    return
```

### Rawvox Format
The `rawvox` format is a simple binary dump with a text header describing dimensions and physical properties [S1, unofficial].

**Steps:**
1.  Open the output file in binary mode.
2.  Write the header as ASCII text:
    *   Line 1: `size_x_ size_y_ size_z_` (integers separated by spaces).
    *   Line 2: `lb_[0] lb_[1] lb_[2]` (doubles).
    *   Line 3: `unit_[0] unit_[1] unit_[2]` (doubles).
3.  (Note: The specific voxel data writing step for rawvox is not fully detailed in the source steps, but implies a dense binary dump following the header, often byte-wise as per [S3, unofficial] for material values).

### Voxel Metadata File Output
A companion format that stores voxel indices and flags [S1, unofficial].

**Steps:**
1.  Derive metadata file path by stripping `.rawvox` or `.binvox` extension from the base output path and appending `.meta`.
2.  Open the output file in binary mode.
3.  Write header line 1: literal string `#voxmeta 1`.
4.  Write header line 2: grid dimensions `size_x_ size_y_ size_z_`.
5.  Iterate `voxel_index` from 0 to `TotalVoxelSize() - 1`.
6.  Write `voxel_index` and `flags` separated by a space, followed by a newline.
7.  Close the output stream.

### Raw Compressed Export (Squared)
Exports the voxel grid to a binary file, optionally padding the grid to a cube (squared) [S2, unofficial].

**Steps:**
1.  If `!squared`:
    *   Write `_numDivs` (a `glm::uvec3` containing dimensions).
    *   Write the entire `_grid` array: `_numDivs.x * _numDivs.y * _numDivs.z * sizeof(uint16_t)` bytes.
2.  If `squared`:
    *   Calculate `end = max(_numDivs.x, _numDivs.y, _numDivs.z)`.
    *   Calculate `start = (end - _numDivs) / 2` for each axis.
    *   Write `end` (as `glm::uvec3`).
    *   Loop `x` from 0 to `end.x`, `y` from 0 to `end.y`, `z` from 0 to `end.z`:
        *   Calculate `currentPosition = (x, y, z) - start`.
        *   If `currentPosition` is within `[0, _numDivs)` (i.e., `0 <= px < _numDivs.x`, etc.):
            *   Write the voxel value from `_grid` at `currentPosition`.
        *   Else:
            *   Write `VOXEL_EMPTY` (padding value).

### Raw Voxel Export Format (Material-based)
Exports voxels as a byte-wise binary file where each byte corresponds to a material value defined in the XML configuration (e.g., `material_interior` or `material_shell`) [S3, unofficial].

**Parameters:**
*   `byte_order`: Determines memory layout, either `'row_major'` or `'column_major'`.

**Layout:**
*   The resulting array in the `.raw` file corresponds to the global project bounding box.
*   When loaded in Python/Numpy, it is reshaped to `(wx, wy, wz)` with `order='F'` (Fortran/column-major order) [S3, unofficial].

**Steps:**
1.  Read the raw file into a numpy array of `uint8`: `arr_vox = np.fromfile(args.rawfile, dtype=np.uint8)`.
2.  Reshape the 1D array into a 3D volume using dimensions `wx, wy, wz` read from the `.info` file, ensuring column-major order: `arr_vox_3d = np.reshape(arr_vox, (wx, wy, wz), order='F')`.

## Subtopics

### [MagicaVoxel File Output](1752-magicavoxel-file-output.md)
Exports voxel particle data to the MagicaVoxel `.vox` binary format, handling grid sizing, chunk structure, and coordinate transformation. It differs from [binvox](1698-voxel-file-i-o-binvox-rawvox.md) by using a sparse XYZI representation rather than a dense octree, and from [rawvox](1698-voxel-file-i-o-binvox-rawvox.md) by including a structured chunk hierarchy and palette support.

### [MagicaVoxel File Parsing](2405-magicavoxel-file-parsing.md)
A loader for MagicaVoxel `.vox` files (versions 150 and 200) that parses models, palette, MATL materials, and the nTRN/nGRP/nSHP scene graph, converting visible faces into quads within a BVH. It structures data into chunks containing tags, sizes, and child chunks. Unlike [Voxel File I/O (binvox/rawvox)](1698-voxel-file-i-o-binvox-rawvox.md) which uses dense or simple sparse grids, this method handles the hierarchical scene graph and chunk-based binary format specific to Magica Voxel.

### [PLY File Parsing](2781-ply-file-parsing.md)
This method parses the ASCII header of a Polygon File Format (PLY) file to determine vertex counts, property types, and the byte offset of the subsequent data section. It serves as the initial step in extracting structured mesh geometry (vertices and faces) for voxelization pipelines, specifically targeting the ASCII format used in outputs from 3D Gaussian Splatting tutorials. Unlike binary PLY parsers or OBJ loaders, this implementation assumes triangular topology and ignores quad faces, providing the raw data required for subsequent normal calculation and voxelization.

### [Voxel File I/O](2786-voxel-file-i-o.md)
This method handles the serialization and deserialization of voxel grid data into various file formats for storage, transport, or interoperability with external tools. It solves the problem of persisting 3D volumetric data generated by voxelization or volume rendering pipelines in a structured, recoverable format. Unlike [Voxel File I/O (binvox/rawvox)](1698-voxel-file-i-o-binvox-rawvox.md), which focuses on specific legacy binary encodings, this article covers a broader set of generic and specialized formats including ASCII text, binary grids, and specialized image stacks.

### [FLVC File Format](17392-flvc-file-format.md)
FLVC is a container format for voxel data that supports zlib-compressed content for non-empty volumes. It is designed to store sparse voxel octrees (SVOs) and their associated attributes, providing a structured way to serialize voxel grids with metadata. Unlike raw binary dumps, FLVC includes a header defining volume dimensions, offsets, and attribute schemas, allowing for flexible storage of color, normals, and custom data.

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of voxels $N$ for dense formats (`rawvox`, `rawvox squared`). For `binvox`, it is also linear $O(N)$ but with a constant factor overhead due to RLE encoding logic and boundary checks.
*   **Memory Complexity:** $O(1)$ auxiliary memory for streaming writers, assuming the grid data is already in memory. The output file size for `binvox` is at most $2N$ bytes (2 bytes per voxel in worst-case alternating pattern) and can be significantly smaller for large empty or filled regions. `rawvox` file size is $N \times \text{sizeof(byte)}$ plus header.
*   **Performance:** `binvox` is widely supported by visualization tools (e.g., MeshLab, Blender plugins) but the RLE encoding requires careful iteration logic. `rawvox` is simpler to implement and parse but lacks compression.
*   **Strengths:** `binvox` provides compact storage for sparse or blocky data. `rawvox` is trivial to parse.
*   **Limitations:** `binvox` does not support color or material attributes natively in its standard format (only occupancy). `rawvox` requires external metadata (like `.info` files) to interpret material values or dimensions correctly.
*   **When to use:** Use `binvox` for interoperability with general-purpose voxel viewers. Use `rawvox` for custom pipelines where metadata is managed externally or for debugging.

## Background
The `binvox` format was developed as a standard for sharing 3D voxel models, particularly in computer graphics research and game development. It is supported by tools like MagicaVoxel and various voxelization libraries. The `rawvox` format is a simpler, often custom binary format used in specific voxelization projects (e.g., the `voxelizer` project by topskychen [S1, unofficial] and 3DStuff [S3, unofficial]) to export dense voxel grids with minimal overhead.
