# Voxel File I/O (binvox/rawvox)

Also called: Binvox File Writing, Sparse Voxel Grid Export, Text-based Voxel Output, WriteBinvox

## Overview
This method serializes a 3D voxel grid into legacy file formats, primarily `binvox` and `rawvox`, to enable interoperability with external visualization tools [S1, S3, unofficial]. It persists occupancy data generated by voxelization pipelines in a structured, recoverable format [G]. Unlike [MagicaVoxel File Output](1752-magicavoxel-file-output.md) which uses a sparse XYZI representation, or [Voxel File I/O](2786-voxel-file-i-o.md) which covers a broader set of generic formats, this method specifically implements the dense binary RLE encoding of `binvox` and the simple dense binary/text headers of `rawvox` [S1, S3, unofficial].

## How it works
The core inputs are the voxel grid data (accessed via `Filled(x,y,z)` or a direct array `_grid`), grid dimensions (`size_x_`, `size_y_`, `size_z_`), bounding box lower bounds (`lb_`), and voxel unit sizes (`unit_`) [S1, S2, S3, unofficial]. The outputs are binary or text files containing headers and voxel data [S1, S3, unofficial].

### Binvox Format
The `binvox` format stores occupancy data using a dense binary run-length encoding (RLE) [S1, unofficial].

**Data Structures:**
*   `size_x_, size_y_, size_z_`: Integer dimensions of the grid.
*   `lb_`: Array of 3 doubles representing the lower bound coordinates of the bounding box.
*   `unit_`: Array of 3 doubles representing the physical size of a voxel.
*   `bound_`: Bounding box object with a `norm()` method returning the maximum dimension magnitude.
*   `Filled(x, y, z)`: Function returning boolean occupancy.

**Steps:**
1.  Open the output file in binary mode [S1, unofficial].
2.  Calculate dimensions `bx = size_x_`, `by = size_y_`, `bz = size_z_` [S1, unofficial].
3.  Calculate `norm_translate` from `lb_` and `norm_scale` from `bound_.norm()` [S1, unofficial].
4.  Write the header lines as ASCII text followed by newlines [S1, unofficial]:
    *   Line 1: `#binvox 1`
    *   Line 2: `dim bx by bz`
    *   Line 3: `translate -norm_translate[0] -norm_translate[2] -norm_translate[1]` (Y and Z coordinates are swapped and negated relative to standard Cartesian, consistent with binvox convention) [S1, unofficial].
    *   Line 4: `scale norm_scale`
    *   Line 5: `data`
5.  Initialize traversal indices `x = lx`, `y = ly`, `z = lz` (where `lx, ly, lz` are the lower bounds of the active grid range) [S1, unofficial].
6.  Loop while `x <= ux` (upper bound) [S1, unofficial]:
    *   Get `value = Filled(x, y, z)` [S1, unofficial].
    *   Initialize `count = 0` [S1, unofficial].
    *   Inner loop: While `x <= ux` AND `count < 255` AND `value == Filled(x, y, z)` [S1, unofficial]:
        *   Increment `z` [S1, unofficial].
        *   If `z > uz`, reset `z = lz` and increment `y` [S1, unofficial].
        *   If `y > uy`, reset `y = ly` and increment `x` [S1, unofficial].
        *   Increment `count` [S1, unofficial].
    *   If `value` is true, add `count` to `total_ones` (optional metadata) [S1, unofficial].
    *   Write two bytes to the output stream [S1, unofficial]:
        *   Byte 1: `value` (0 for empty, 1 for filled) [S1, unofficial].
        *   Byte 2: `count` (unsigned char, 1-255) [S1, unofficial].
    *   Increment `bytes_written` by 2 [S1, unofficial].
7.  Close the output stream [S1, unofficial].

**Pseudocode:**
```python
def write_binvox(filepath, size_x, size_y, size_z, lb, bound, filled_func):
    with open(filepath, 'wb') as f:
        # Calculate normalization parameters [S1, unofficial]
        norm_translate = lb
        norm_scale = bound.norm()
        
        # Write ASCII header [S1, unofficial]
        f.write(b'#binvox 1\n')
        f.write(f'dim {size_x} {size_y} {size_z}\n'.encode('ascii'))
        f.write(f'translate {-norm_translate[0]} {-norm_translate[2]} {-norm_translate[1]}\n'.encode('ascii'))
        f.write(f'scale {norm_scale}\n'.encode('ascii'))
        f.write(b'data\n')
        
        # RLE Encoding [S1, unofficial]
        lx, ly, lz = 0, 0, 0
        ux, uy, uz = size_x - 1, size_y - 1, size_z - 1
        
        x, y, z = lx, ly, lz
        total_ones = 0
        while x <= ux:
            value = filled_func(x, y, z)
            count = 0
            while x <= ux and count < 255 and filled_func(x, y, z) == value:
                z += 1
                if z > uz:
                    z = lz
                    y += 1
                    if y > uy:
                        y = ly
                        x += 1
                count += 1
            if value:
                total_ones += count
            f.write(bytes([1 if value else 0]))
            f.write(bytes([count]))
```

### Rawvox Format
The `rawvox` format is a simple binary dump with a text header describing dimensions and physical properties [S1, unofficial].

**Steps:**
1.  Open the output file in binary mode [S1, unofficial].
2.  Write the header as ASCII text [S1, unofficial]:
    *   Line 1: `size_x_ size_y_ size_z_` (integers separated by spaces) [S1, unofficial].
    *   Line 2: `lb_[0] lb_[1] lb_[2]` (doubles) [S1, unofficial].
    *   Line 3: `unit_[0] unit_[1] unit_[2]` (doubles) [S1, unofficial].
3.  Write the dense voxel grid data following the header (implementation details for the dense dump are not fully specified in the sources) [G].

### Voxel Metadata File Output
A companion format that stores voxel indices and flags [S1, unofficial].

**Steps:**
1.  Derive metadata file path by stripping `.rawvox` or `.binvox` extension from the base output path and appending `.meta` [S1, unofficial].
2.  Open the output file in binary mode [S1, unofficial].
3.  Write header line 1: literal string `#voxmeta 1` [S1, unofficial].
4.  Write header line 2: grid dimensions `size_x_ size_y_ size_z_` [S1, unofficial].
5.  Iterate `voxel_index` from 0 to `TotalVoxelSize() - 1` [S1, unofficial].
6.  Write `voxel_index` and `flags` separated by a space, followed by a newline [S1, unofficial].
7.  Close the output stream [S1, unofficial].

### Raw Compressed Export (Squared)
Exports the voxel grid to a binary file, optionally padding the grid to a cube (squared) [S2, unofficial].

**Steps:**
1.  If `!squared`:
    *   Write `_numDivs` (a `glm::uvec3` containing dimensions) [S2, unofficial].
    *   Write the entire `_grid` array: `_numDivs.x * _numDivs.y * _numDivs.z * sizeof(uint16_t)` bytes [S2, unofficial].
2.  If `squared`:
    *   Calculate `end = max(_numDivs.x, _numDivs.y, _numDivs.z)` [S2, unofficial].
    *   Calculate `start = (end - _numDivs) / 2` for each axis [S2, unofficial].
    *   Write `end` (as `glm::uvec3`) [S2, unofficial].
    *   Loop `x` from 0 to `end.x`, `y` from 0 to `end.y`, `z` from 0 to `end.z`:
        *   Calculate `currentPosition = (x, y, z) - start` [S2, unofficial].
        *   If `currentPosition` is within `[0, _numDivs)` (i.e., `0 <= px < _numDivs.x`, etc.):
            *   Write the voxel value from `_grid` at `currentPosition` [S2, unofficial].
        *   Else:
            *   Write `VOXEL_EMPTY` (padding value) [S2, unofficial].

### Raw Voxel Export Format (Material-based)
Exports voxels as a byte-wise binary file where each byte corresponds to a material value defined in the XML configuration (e.g., `material_interior` or `material_shell`) [S3, unofficial].

**Parameters:**
*   `byte_order`: Determines memory layout, either `'row_major'` or `'column_major'` [S3, unofficial].

**Layout:**
*   The resulting array in the `.raw` file corresponds to the global project bounding box [S3, unofficial].
*   When loaded in Python/Numpy, it is reshaped to `(wx, wy, wz)` with `order='F'` (Fortran/column-major order) [S3, unofficial].

**Steps:**
1.  Read the raw file into a numpy array of `uint8`: `arr_vox = np.fromfile(args.rawfile, dtype=np.uint8)` [S3, unofficial].
2.  Reshape the 1D array into a 3D volume using dimensions `wx, wy, wz` read from the `.info` file, ensuring column-major order: `arr_vox_3d = np.reshape(arr_vox, (wx, wy, wz), order='F')` [S3, unofficial].

## Subtopics

### [MagicaVoxel File Output](1752-magicavoxel-file-output.md)
Exports voxel particle data to the MagicaVoxel `.vox` binary format, handling grid sizing, chunk structure, and coordinate transformation. It differs from [binvox](1698-voxel-file-i-o-binvox-rawvox.md) by using a sparse XYZI representation rather than a dense octree, and from [rawvox](1698-voxel-file-i-o-binvox-rawvox.md) by including a structured chunk hierarchy and palette support. Choose it when interoperability with MagicaVoxel or modern voxel art tools is required.

### [MagicaVoxel File Parsing](2405-magicavoxel-file-parsing.md)
A loader for MagicaVoxel `.vox` files (versions 150 and 200) that parses models, palette, MATL materials, and the nTRN/nGRP/nSHP scene graph, converting visible faces into quads within a BVH. It structures data into chunks containing tags, sizes, and child chunks. Unlike [Voxel File I/O (binvox/rawvox)](1698-voxel-file-i-o-binvox-rawvox.md) which uses dense or simple sparse grids, this method handles the hierarchical scene graph and chunk-based binary format specific to Magica Voxel. Choose it for importing MagicaVoxel assets into custom pipelines.

### [PLY File Parsing](2781-ply-file-parsing.md)
Parses the ASCII header of a PLY file to determine vertex counts, property types, and the byte offset of the subsequent data section. It serves as the initial step for extracting structured data from ASCII PLY files. Choose it when importing mesh geometry from PLY sources for voxelization.

### [Voxel File I/O](2786-voxel-file-i-o.md)
Handles the serialization and deserialization of voxel grid data into various file formats for storage, transport, or interoperability with external tools. It solves the problem of persisting 3D volumetric data generated by voxelization or volume rendering pipelines in a structured, recoverable format. Unlike [Voxel File I/O (binvox/rawvox)](1698-voxel-file-i-o-binvox-rawvox.md), which focuses on specific legacy binary encodings, this article covers a broader set of formats including ASCII text, binary grids, and image-slice-based volumes. Choose it for generic voxel data persistence.

### [FLVC File Format](17392-flvc-file-format.md)
FLVC is a container format for voxel data that supports zlib-compressed content for non-empty volumes. It is designed to store sparse voxel octrees (SVOs) and their associated attributes, providing a structured way to serialize voxel grids with metadata. Unlike raw binary dumps, FLVC includes a header defining volume dimensions, offsets, and attribute schemas, allowing for flexible storage of color, normals, and custom data. Choose it for compressing and transporting sparse voxel octrees.

## Operating characteristics
*   **Time Complexity:** Linear $O(N)$ with respect to the number of voxels for all formats, where $N$ is the total grid volume. `binvox` has a slightly higher constant factor due to RLE traversal and boundary checks.
*   **Memory Complexity:** $O(1)$ auxiliary memory for streaming writers, assuming the grid data is already resident in memory.
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** File size for `binvox` is at most $2N$ bytes (worst-case alternating pattern) and compresses significantly for large empty or filled regions. `rawvox` scales linearly as $N \times \text{sizeof(byte)}$ plus a fixed header.
*   **Strengths:** `binvox` provides compact storage for sparse or blocky data and is widely supported by visualization tools. `rawvox` is trivial to parse and write.
*   **Limitations:** `binvox` does not support color or material attributes natively (only occupancy). `rawvox` requires external metadata (like `.info` files) to interpret material values or dimensions correctly.
*   **When to use:** Use `binvox` for interoperability with general-purpose voxel viewers. Use `rawvox` for custom pipelines where metadata is managed externally or for debugging.

## Background
The `binvox` format was developed as a standard for sharing 3D voxel models, particularly in computer graphics research and game development [S1, unofficial]. The `rawvox` format is a simpler binary format used in specific voxelization projects, such as the `voxelizer` project by topskychen [S1, unofficial], to export dense voxel grids with minimal overhead.
