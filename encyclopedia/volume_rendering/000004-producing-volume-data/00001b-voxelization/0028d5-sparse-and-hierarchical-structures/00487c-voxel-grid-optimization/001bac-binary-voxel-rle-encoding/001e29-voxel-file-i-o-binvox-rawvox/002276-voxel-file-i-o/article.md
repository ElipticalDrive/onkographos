# Voxel File I/O

Also called: Output Format Handling, Voxel Export

## Overview
This method handles the serialization and deserialization of voxel grid data into various file formats for storage, transport, or interoperability with external tools [S1, S4, unofficial]. It solves the problem of persisting 3D volumetric data generated by voxelization or volume rendering pipelines in a structured, recoverable format. Unlike [Voxel File I/O (binvox/rawvox)](1698-voxel-file-i-o-binvox-rawvox.md), which focuses on specific legacy binary encodings, this article covers a broader set of generic and specialized formats including ASCII text, binary grids, and specialized image stacks [S1, S4, unofficial].

## How it works
The method supports multiple output formats, each with distinct data layouts and parsing requirements. The core logic involves selecting the target format, serializing the voxel grid (dimensions, bounding box, and values), and handling metadata or auxiliary data (such as phase or color) as required by the specific format specification.

### Inputs and Outputs
- **Inputs**: A 3D voxel grid (typically a 3D array or sparse structure), grid dimensions ($W, H, D$), bounding box parameters (optional), and optional scalar fields (e.g., phase, color).
- **Outputs**: A byte stream or text file conforming to the chosen format specification.

### Data Structures and Layouts

#### 1. Binary Volume File Format [S4, unofficial]
Used for storing volume data generated from image slices.
- **Header (24 bytes)**:
  - `grid_dim[0]` (int, 4 bytes): Width.
  - `grid_dim[1]` (int, 4 bytes): Height.
  - `grid_dim[2]` (int, 4 bytes): Depth.
  - `bbox_size[0]` (float, 4 bytes): Bounding box X size.
  - `bbox_size[1]` (float, 4 bytes): Bounding box Y size.
  - `bbox_size[2]` (float, 4 bytes): Bounding box Z size.
- **Payload**: Voxel values as `float` (4 bytes each), stored in row-major order (x varying fastest, then y, then z).

#### 2. ASCII Text Formats (CSV, PLY, VTK) [S1, unofficial]
- **CSV**: Header line `x,y,z,phase`, followed by rows of `x,y,z,phase` values.
- **PLY**: ASCII PLY header specifying vertex count and properties `x,y,z`, followed by vertex coordinates.
- **VTK**: VTK 3.0 ASCII POLYDATA with `POINTS` and `SCALARS phase`, including point coordinates and phase scalars.

#### 3. Binary Serialization [S1, unofficial]
- Uses `bincode` for compact binary serialization of structured data.

### Numbered Steps

#### Binary Volume File Format [S4, unofficial]
1. Read input image slices from a directory, sorted by filename.
2. Determine grid dimensions:
   - $W, H$ from the shape of the first image.
   - $D = \text{len}(\text{slices\_files})$.
3. Calculate bounding box size:
   - Let $BBOX\_SIZE\_X = 5.0$.
   - $bbox\_size[0] = BBOX\_SIZE\_X$.
   - $bbox\_size[1] = (BBOX\_SIZE\_X / W) \times (vol\_size[1] / vol\_size[0]) \times H$.
   - $bbox\_size[2] = (BBOX\_SIZE\_X / W) \times (vol\_size[2] / vol\_size[0]) \times D$.
   - *Note*: $vol\_size$ refers to the original volume dimensions before grid quantization.
4. Write `grid_dim[0]`, `grid_dim[1]`, `grid_dim[2]` as 3 integers (4 bytes each, little-endian).
5. Write `bbox_size[0]`, `bbox_size[1]`, `bbox_size[2]` as 3 floats (4 bytes each, little-endian).
6. Write voxel values as a contiguous array of floats (4 bytes each) in row-major order.

#### ASCII Formats [S1, unofficial]
1. **CSV**: Write header `x,y,z,phase`. Iterate through voxels, writing `x,y,z,phase` for each active voxel.
2. **PLY**: Write ASCII header with vertex count and property definitions. Write vertex coordinates.
3. **VTK**: Write VTK 3.0 ASCII POLYDATA header. Write POINTS and SCALARS phase data.

### Pseudocode

> **Unverified code.** The code below did not pass a test run against a reference implementation, or no test fits it, so it may contain errors.

```python
import struct
import os
import numpy as np

def write_binary_volume_file(slices_dir: str, output_path: str, vol_size: list):
    """
    Writes a binary volume file format as defined in [S4, unofficial].
    """
    # Step 1: Read slices
    slice_files = sorted([f for f in os.listdir(slices_dir) if f.endswith('.png') or f.endswith('.jpg')])
    if not slice_files:
        raise ValueError("No slices found")
    
    # Load first slice to determine dimensions
    # Assuming helper function load_image returns (width, height)
    first_img = load_image(os.path.join(slices_dir, slice_files[0]))
    W, H = first_img.shape[1], first_img.shape[0]
    D = len(slice_files)
    
    # Step 2: Grid dimensions
    grid_dim = [W, H, D]
    
    # Step 3: Bounding box size
    BBOX_SIZE_X = 5.0
    bbox_size = [0.0, 0.0, 0.0]
    bbox_size[0] = BBOX_SIZE_X
    # vol_size is assumed to be [vol_w, vol_h, vol_d] from input context
    bbox_size[1] = (BBOX_SIZE_X / grid_dim[0]) * (vol_size[1] / vol_size[0]) * grid_dim[1]
    bbox_size[2] = (BBOX_SIZE_X / grid_dim[0]) * (vol_size[2] / vol_size[0]) * grid_dim[2]
    
    # Step 4 & 5: Write Header
    with open(output_path, 'wb') as f:
        # Write grid dimensions (3 ints)
        f.write(struct.pack('<iii', *grid_dim))
        # Write bounding box size (3 floats)
        f.write(struct.pack('<fff', *bbox_size))
        
        # Step 6: Write Voxel Values
        # Collect all voxel values in row-major order
        voxels = []
        for z_idx, filename in enumerate(slice_files):
            img = load_image(os.path.join(slices_dir, filename))
            # Flatten image row-major (y then x)
            # Note: Source says x varying fastest, then y, then z.
            # Standard numpy flatten is C-order (last index fastest).
            # If img is (H, W), img.flatten() is y*W + x.
            # We need x fastest. So we transpose or reshape carefully.
            # Assuming img is (H, W, C) or (H, W).
            # If (H, W), row-major x-fastest is img.T.flatten()
            voxels.extend(img.T.flatten().astype(np.float32))
            
        f.write(np.array(voxels, dtype=np.float32).tobytes())

def write_csv_voxel_grid(voxels: list, output_path: str):
    """
    Writes CSV format as defined in [S1, unofficial].
    voxels: list of tuples (x, y, z, phase)
    """
    with open(output_path, 'w') as f:
        f.write("x,y,z,phase\n")
        for x, y, z, phase in voxels:
            f.write(f"{x},{y},{z},{phase}\n")
```

### Parameters
- `BBOX_SIZE_X`: Fixed width of the bounding box in X dimension, value `5.0` [S4, unofficial].

### Edge Cases and Pitfalls
- **Endianness**: Binary formats must specify endianness. The Binary Volume File Format uses little-endian [S4, unofficial]. PFM files require endianness handling [S2, unofficial].
- **Data Type Consistency**: Ensure voxel values are stored in the correct type (e.g., `float` for Binary Volume, `uint8` or `int32` for others).
- **Ordering**: Row-major order implies x varies fastest. Misinterpreting this leads to corrupted 3D structure [S4, unofficial].
- **Missing Slices**: If slice files are not sorted correctly, the depth dimension $D$ and z-ordering will be incorrect [S4, unofficial].

## Subtopics

### [Binvox File Parsing](2862-binvox-file-parsing.md)
Binvox File Parsing is the method for importing the binary voxel (binvox) file format into a contiguous array or a Sparse Voxel Octree (SVO) structure. It converts a legacy run-length encoded (RLE) voxel representation into a format suitable for modern ray-casting or rasterization engines [G]. Unlike raw voxel formats that store every voxel explicitly, binvox uses a compact binary RLE scheme, requiring specific handling to decompress the data correctly.

### [IMS File Format & Image Stack Class](3322-ims-file-format-image-stack-class.md)
The IMS file format and `ims_base` class provide a mechanism for persisting and managing 3D image stacks (volumes) with typed pixel storage and extensible metadata segments. It solves the problem of storing volumetric data where pixel types are fixed at compile time via templates and metadata is stored as typed binary segments. It differs from generic binary voxel formats by embedding a rigid 16-byte header, supporting memory-mapped loading on Windows, and using a chunked write strategy to handle large volumes without buffer overflow.

### [NRRD-like Volume I/O](4225-nrrd-like-volume-i-o.md)
This method exports and imports volumes in a simple NRRD-like format consisting of two header lines followed by a raw binary payload. It serializes 3D voxel grids by restricting the format to fixed dimensions and a single `uint32_t` data type, prioritizing implementation simplicity and parsing speed over the flexibility of the full NRRD specification. It serves as a lightweight alternative to more verbose formats like [VTK Legacy ASCII File Writing](6698-vtk-legacy-ascii-file-writing.md) or the metadata-rich [NRRD File Parsing and Volume Initialization](7216-nrrd-file-parsing-and-volume-initialization.md).

### [VTK Legacy ASCII File Writing](6698-vtk-legacy-ascii-file-writing.md)
Exports voxel data to a legacy VTK ASCII `UNSTRUCTURED_GRID` file format, representing each voxel as a hexahedral cell with associated scalar fields. It differs from binary voxel formats (e.g., [Binvox File Parsing](2862-binvox-file-parsing.md)) by using human-readable text and explicit vertex definitions for every cell, prioritizing interoperability with legacy VTK-based viewers over storage efficiency.

### [VRDF File Format / VRDF Loader](6906-vrdf-file-format-vrdf-loader.md)
The VRDF (Volume Rendering Data Format) is a binary file format designed for storing 3D voxel grids alongside associated metadata and transfer functions. It supports continuous floating-point data, multi-channel interleaved data (e.g., label and weight), and embedded JSON metadata.

### [Voxel Interchange Format Serialization](7065-voxel-interchange-format-serialization.md)
Serializes a 3D voxel region into a flat 1D array accompanied by metadata for transport or storage. It differs from its sibling [Binvox File Parsing](2862-binvox-file-parsing.md) by using a generic JSON-like structure with explicit dimensions and position rather than a binary header, and from [Hierarchical Sparse Voxel Format (glTF-based)](13799-hierarchical-sparse-voxel-format-gltf-based.md) by storing data in a flat 1D array rather than a hierarchical structure of volumes and primitives.

### [Minecraft Schematic to Voxel Conversion](12823-minecraft-schematic-to-voxel-conversion.md)
Converts a Minecraft `.schematic` file (NBT format) into a `FileToVox` Schematic structure by parsing block IDs, metadata, and colors, then iterating through the voxel grid to populate the output. It differs from generic voxelization methods by directly interpreting Minecraft's specific block ID and metadata system rather than reconstructing geometry from meshes.

### [Qubicle File Parsing](12824-qubicle-file-parsing.md)
This method parses the binary `.qb` file format used by the Qubicle voxel editor to reconstruct a 3D voxel grid. It handles both uncompressed and run-length encoded (RLE) compressed data streams, applying necessary axis orientation and color format transformations to produce a standardized voxel list. It is distinguished from sibling parsers by its specific handling of Qubicle's matrix-based scene structure and its unique compressed bitstream flags.

## Operating characteristics
- **Time Complexity**: Linear with respect to the number of voxels $N$ for serialization/deserialization $O(N)$.
- **Memory Complexity**: Linear with respect to $N$ for storing the voxel grid.
- **Performance**: Binary formats (Binary Volume, Binvox) are significantly faster and smaller than ASCII formats (CSV, PLY, VTK) [S1, S4, unofficial].
- **Strengths**: Supports multiple formats for different use cases (interoperability vs. compactness).
- **Limitations**: ASCII formats are verbose and slow to parse. Binary formats lack human readability.

## Background
Voxel file I/O methods have evolved alongside voxelization and volume rendering techniques. Early methods focused on simple ASCII formats for debugging and visualization [S1, unofficial]. Later, binary formats like Binvox and specialized formats like VRDF were developed for efficiency and metadata support [S1, S2, S4, unofficial]. The Binary Volume File Format [S4, unofficial] and IMS format [S1, unofficial] represent efforts to standardize storage for specific pipelines (e.g., CUDA-based rendering, image stack management).
