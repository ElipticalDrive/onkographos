# VTK Legacy ASCII File Writing

Also called: VTK ASCII UNSTRUCTURED_GRID Export

## Overview
Exports voxel data to a legacy VTK ASCII `UNSTRUCTURED_GRID` file format, representing each voxel as a hexahedral cell with associated scalar fields [S1, unofficial]. It differs from binary voxel formats (e.g., [Binvox File Parsing](2862-binvox-file-parsing.md)) by using human-readable text and explicit vertex definitions for every cell, prioritizing interoperability with legacy VTK-based viewers over storage efficiency [S1, unofficial].

## How it works
**Inputs:** A voxel dataset containing bounding box coordinates (`box_min`, `box_max`), cell count, and multiple scalar fields (e.g., `void_ratio`, `particle_count`).
**Outputs:** A `.vtk` file in ASCII format.

**Data Structures:**
The output is a VTK `UNSTRUCTURED_GRID`.
- **POINTS:** A list of 3D coordinates. Total count = `cell_count * 8`.
- **CELLS:** A flat list defining connectivity. Each cell entry consists of 9 integers: `8` (number of vertices) followed by 8 vertex indices.
- **CELL_TYPES:** A list of integers. Each entry is `11` (VTK_HEXAHEDRON).
- **CELL_DATA:** Scalar arrays associated with each cell.

**Steps:**
1. **Header:** Write the VTK magic number and version:
   ```
   # vtk DataFile Version 2.0
   <title>
   ASCII
   DATASET UNSTRUCTURED_GRID
   ```
2. **POINTS:** Write the point count and type:
   ```
   POINTS {point_count} float
   ```
   Compute the 8 vertices for each cell using the global bounding box (`box_min`, `box_max`) and a local index $i \in [0, 7]$. The local index maps to the 8 corners of the hexahedron. For a cell with bounds $[x_{min}, x_{max}] \times [y_{min}, y_{max}] \times [z_{min}, z_{max}]$, the vertices are:
   - $i=0: (x_{min}, y_{min}, z_{min})$
   - $i=1: (x_{max}, y_{min}, z_{min})$
   - $i=2: (x_{min}, y_{max}, z_{min})$
   - $i=3: (x_{max}, y_{max}, z_{min})$
   - $i=4: (x_{min}, y_{min}, z_{max})$
   - $i=5: (x_{max}, y_{min}, z_{max})$
   - $i=6: (x_{min}, y_{max}, z_{max})$
   - $i=7: (x_{max}, y_{max}, z_{max})$
   
   Write each coordinate formatted as `'{:.17g}'` to preserve double precision [S1, unofficial].

3. **CELLS:** Write the connectivity:
   ```
   CELLS {cell_count} {cell_count * 9}
   ```
   For each cell index $c$ from $0$ to `cell_count - 1`:
   - Calculate `start = c * 8`.
   - Write `8` followed by the 8 vertex indices: `start, start+1, ..., start+7` [S1, unofficial].

4. **CELL_TYPES:** Write the cell type array:
   ```
   CELL_TYPES {cell_count}
   ```
   Write the integer `11` for each cell [S1, unofficial].

5. **CELL_DATA:** Write the scalar fields:
   ```
   CELL_DATA {cell_count}
   ```
   For each scalar field (e.g., `void_ratio`, `particle_count`):
   - Write header: `SCALARS {name} {type} 1`
   - Write: `LOOKUP_TABLE default`
   - Write the values, one per line, in the same order as the cells [S1, unofficial].

**Parameters:**
- `point_count`: Total vertices = `cell_count * 8` [S1, unofficial].
- `cell_count`: Number of voxels [S1, unofficial].

**Edge Cases:**
- Precision: Coordinates must be formatted with high precision (`{:.17g}`) to avoid rounding errors in VTK readers [S1, unofficial].
- Empty Grids: If `cell_count` is 0, the file should still contain valid headers but no data sections.

## Subtopics

### VoxelGrid Serialization (Grasshopper)
A variant used in the Grasshopper environment that serializes VoxelGrid objects into a custom chunk-based format rather than standard VTK ASCII [S2, unofficial]. It removes the 'PersistentData' chunk, writes a 'GridCount' Int32, and iterates through persistent data branches. For each grid, it creates a 'Grid' chunk, converts the voxel grid to bytes, compresses them, converts to a hex string, and writes it to the 'Data' field along with the GH_Path [S2, unofficial]. Reading involves reversing this process: reading the count, finding the 'Grid' chunk by index, reading the hex string, decompressing, and reconstructing the VoxelGrid [S2, unofficial].

## Operating characteristics
- **Time Complexity:** $O(N)$ where $N$ is the number of cells, as each cell and its vertices are written sequentially.
- **Memory Complexity:** $O(N)$ to store the output buffer or file.
- **Performance:** Very slow for large datasets due to ASCII overhead and lack of compression. Suitable for small voxel grids or debugging [S1, unofficial].
- **Strengths:** Human-readable, easy to parse with standard text tools, compatible with legacy VTK pipelines [S1, unofficial].
- **Limitations:** Large file sizes, slow I/O, no support for complex geometries beyond hexahedra [S1, unofficial].
- **When to use:** When interoperability with legacy VTK tools is required and dataset size is small.
- **When not to use:** For large-scale volume rendering or real-time applications where I/O speed is critical.

## Background
The VTK Legacy ASCII format is part of the Visualization Toolkit (VTK) file formats, specifically the `UNSTRUCTURED_GRID` representation. It is used in point-cloud voxelization workflows to export voxel data for visualization [S1, unofficial]. The format relies on the VTK Hexahedron cell type (ID 11) to represent voxels [S1, unofficial].
