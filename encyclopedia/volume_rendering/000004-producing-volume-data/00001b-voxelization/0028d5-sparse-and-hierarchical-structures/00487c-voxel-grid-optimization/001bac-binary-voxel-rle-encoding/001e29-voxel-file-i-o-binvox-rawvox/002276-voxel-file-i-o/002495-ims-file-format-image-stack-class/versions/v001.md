# IMS File Format & Image Stack Class

Also called: .ims

## Overview
The IMS file format and `ims_base` class provide a mechanism for persisting and managing 3D image stacks (volumes) with typed pixel storage and extensible metadata segments [S1, unofficial]. It solves the problem of storing volumetric data where pixel types are fixed at compile time via templates and metadata is stored as typed binary segments [S1, unofficial]. It differs from generic binary voxel formats by embedding a rigid 16-byte header, supporting memory-mapped loading on Windows, and using a chunked write strategy to handle large volumes without buffer overflow [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A volume defined by width ($W$), height ($H$), and depth ($D$); a pixel type $T$; and a map of metadata segments.
- Output: A binary file with the `.ims` extension containing the header, pixel data, and segment data.

**Data Structures:**
The file layout is strictly sequential:

1.  **File Header (16 bytes):**
    -   Bytes 0-2: ASCII `'IMS'`.
    -   Byte 3: Encoding version (uint8, value `1`).
    -   Bytes 4-7: Pixel type identifier (uint32, e.g., `0` for floats).
    -   Bytes 8-9: Width $W$ (uint16).
    -   Bytes 10-11: Height $H$ (uint16).
    -   Bytes 12-13: Depth $D$ (uint16).
    -   Bytes 14-15: Number of segments $S$ (uint16).

2.  **Pixel Data:**
    -   Stored immediately after the header.
    -   Layout: Images sequentially, then rows within each image.
    -   First pixel is top-left, last is bottom-right.
    -   Total size: $W \times H \times D \times \text{TPixelSize}$ bytes.

3.  **Segments (Sequential):**
    -   Each segment consists of a header and data.
    -   **Segment Header (8 bytes):**
        -   Bytes 0-3: Segment type identifier (4 ASCII chars, packed into uint32).
        -   Bytes 4-7: Segment data size in bytes (uint32).
    -   **Segment Data:**
        -   Follows the segment header.
        -   Size matches the uint32 value in the segment header.

**Parameters:**
-   `PixelTypeNo`: Integer identifier for the pixel type (template argument).
-   `TPixelSize`: Byte size of a single pixel (template argument, multiple of 1 byte).
-   `maxBuf`: Chunk size for writing pixel data, set to $1 \ll 30$ (1 GB) [S1, unofficial].

**Steps:**

**Save:**
1.  Open file for binary writing.
2.  Set header segment count to current map size.
3.  Write 16-byte header.
4.  Write pixel data in chunks of `maxBuf` until exhausted.
5.  Iterate segment map, write 8-byte segment header, then write segment data.

**Load:**
1.  Open file with read/write access and no buffering.
2.  Create read-only file mapping.
3.  Map view to memory.
4.  Parse header fields.
5.  Allocate pixel buffer and copy mapped data.
6.  Parse segments sequentially.

**Pseudocode:**

```python
import struct
import sys

class IMSHeader:
    MAGIC = b'IMS'
    VERSION = 1
    
    def __init__(self, width, height, depth, pixel_type_id, num_segments):
        self.width = width
        self.height = height
        self.depth = depth
        self.pixel_type_id = pixel_type_id
        self.num_segments = num_segments

    def pack(self):
        # Little-endian packing as per implementation details
        # Bytes 0-2: 'IMS', Byte 3: 1
        # Bytes 4-7: pixel_type_id (uint32)
        # Bytes 8-9: width (uint16)
        # Bytes 10-11: height (uint16)
        # Bytes 12-13: depth (uint16)
        # Bytes 14-15: num_segments (uint16)
        return (self.MAGIC + 
                struct.pack('<B', self.VERSION) + 
                struct.pack('<I', self.pixel_type_id) + 
                struct.pack('<HHH', self.width, self.height, self.depth) + 
                struct.pack('<H', self.num_segments))

    @staticmethod
    def unpack(data):
        if data[0:3] != b'IMS':
            raise ValueError("Invalid IMS magic")
        version = data[3]
        if version != 1:
            raise ValueError(f"Unsupported version {version}")
        pixel_type_id = struct.unpack_from('<I', data, 4)[0]
        width, height, depth = struct.unpack_from('<HHH', data, 8)
        num_segments = struct.unpack_from('<H', data, 14)[0]
        return IMSHeader(width, height, depth, pixel_type_id, num_segments)

def save_ims(filename, width, height, depth, pixel_data, segments):
    """
    pixel_data: flat array of pixels, size W*H*D*pixel_size
    segments: list of tuples (type_str, data_bytes)
    """
    pixel_size = len(pixel_data) // (width * height * depth)
    if pixel_size == 0:
        raise ValueError("Pixel size cannot be 0")
    
    # Validate dimensions
    if not (0 <= width <= 65536 and 0 <= height <= 65536 and 0 <= depth <= 65536):
        raise ValueError("Dimensions must be within [0, 65536]")

    # Determine pixel type ID (example: 0 for float, adjust as needed)
    # In the C++ template, this is a template argument. 
    # For this generic save, we assume a fixed mapping or pass it.
    # Here we assume 0 for simplicity, matching the source note.
    pixel_type_id = 0 
    
    num_segments = len(segments)
    header = IMSHeader(width, height, depth, pixel_type_id, num_segments)
    header_bytes = header.pack()
    
    with open(filename, 'wb') as f:
        # 1. Write Header
        f.write(header_bytes)
        
        # 2. Write Pixel Data in chunks
        total_pixel_bytes = len(pixel_data)
        max_buf = 1 << 30  # 1 GB
        offset = 0
        while offset < total_pixel_bytes:
            chunk_size = min(max_buf, total_pixel_bytes - offset)
            f.write(pixel_data[offset : offset + chunk_size])
            offset += chunk_size
            
        # 3. Write Segments
        for seg_type_str, seg_data in segments:
            # Pack 4 ASCII chars into uint32
            # Handle endianness: source uses bitwise shifts for little-endian
            if len(seg_type_str) != 4:
                raise ValueError("Segment type must be 4 chars")
            
            # Little-endian packing: char0 is LSB? 
            # Source: "*(uint8_t*)(&v) == 1" checks LE. 
            # "packs 4 ASCII chars into a uint32 using bitwise shifts"
            # Assuming standard little-endian: first char is lowest address.
            # struct.pack('<I', ...) handles this.
            seg_type_id = struct.pack('<4s', seg_type_str.encode('ascii'))
            seg_size = len(seg_data)
            
            seg_header = seg_type_id + struct.pack('<I', seg_size)
            f.write(seg_header)
            f.write(seg_data)

def load_ims(filename):
    with open(filename, 'rb') as f:
        # Read Header
        header_bytes = f.read(16)
        header = IMSHeader.unpack(header_bytes)
        
        # Read Pixel Data
        total_pixel_bytes = header.width * header.height * header.depth
        # Note: TPixelSize is not explicitly in header, assumed known or derived.
        # In the C++ class, TPixelSize is a template parameter.
        # For a generic loader, we might need to know the pixel size.
        # The source code implies the class is templated, so the loader knows TPixelSize.
        # Here we assume pixel_size is passed or known. Let's assume 4 bytes (float) for example.
        pixel_size = 4 
        pixel_data = f.read(total_pixel_bytes * pixel_size)
        
        # Read Segments
        segments = []
        while True:
            seg_header_bytes = f.read(8)
            if not seg_header_bytes:
                break
            if len(seg_header_bytes) < 8:
                raise ValueError("Truncated segment header")
            
            seg_type_bytes = seg_header_bytes[0:4]
            seg_size = struct.unpack_from('<I', seg_header_bytes, 4)[0]
            
            seg_data = f.read(seg_size)
            if len(seg_data) < seg_size:
                raise ValueError("Truncated segment data")
            
            seg_type_str = seg_type_bytes.decode('ascii')
            segments.append((seg_type_str, seg_data))
            
    return header, pixel_data, segments
```

**Edge Cases and Pitfalls:**
-   **Dimension Validation:** Width, height, and depth must be within $[0, 65536]$. Values outside this range throw `std::invalid_argument` [S1, unofficial].
-   **Windows Memory Allocation:** On Windows, the stack size must be strictly less than $1 \ll 30$ bytes. Exceeding this triggers an assertion failure [S1, unofficial].
-   **Endianness:** Segment type strings are packed into uint32. The code detects little-endian architecture via `*(uint8_t*)(&v) == 1` and uses bitwise shifts; otherwise, it uses `memcpy` [S1, unofficial].

## Operating characteristics
-   **Time Complexity:** $O(W \times H \times D)$ for initialization, copying, and file I/O [S1, unofficial].
-   **Memory Complexity:** $O(W \times H \times D)$ for the pixel buffer plus $O(S)$ for segment storage, where $S$ is the number of segments [S1, unofficial].
-   **Strengths:** Supports memory-mapped loading on Windows for efficient access; handles large volumes via chunked writing; extensible metadata via segments.
-   **Limitations:** Windows-specific memory mapping logic; rigid header structure; pixel type must be known at load time (template parameter in C++).
-   **When to Use:** Suitable for tomography image stacks and metadata management where pixel types are homogeneous and known [S1, unofficial].
-   **When Not to Use:** When cross-platform memory mapping is required without platform-specific code; when pixel types vary within the volume.

## Background
The IMS file format and `ims_base` class were developed as part of the chmike/FastFDK project for loading, saving, and managing tomography image stacks and metadata segments [S1, unofficial]. It provides a template-based approach to volume storage, allowing for type safety and efficient memory access.
