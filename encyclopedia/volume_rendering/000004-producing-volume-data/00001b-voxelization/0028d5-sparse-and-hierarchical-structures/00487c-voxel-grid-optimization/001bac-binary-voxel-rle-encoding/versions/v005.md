# Binary Voxel RLE Encoding

Also called: Run-Length Encoding Output Compression, binvox-like RLE, run-length encoded voxel writer

## Overview
Binary Voxel RLE Encoding compresses a 3D voxel grid into a binary stream using run-length encoding (RLE) to store occupancy data efficiently [S1, S2, unofficial]. It solves the problem of excessive storage size for sparse voxel grids by storing only voxels within the minimal bounding box of the mesh [S2, unofficial]. Unlike [Voxel Indexing and Bit Compression](1707-voxel-indexing-and-bit-compression.md) which stores explicit occupancy bits for every possible voxel, this method encodes runs of identical values, making it suitable for sparse data [S1, unofficial]. It differs from [RLE4 Compression](4441-rle4-compression.md) by storing only binary occupancy (0 or 1) rather than per-voxel material and intensity information [S1, unofficial].

## How it works
**Inputs:**
*   A 3D voxel grid defined by dimensions $m\_dimX, m\_dimY, m\_dimZ$ [S1, unofficial].
*   A voxel spacing value $m\_spacing$ [S1, unofficial].
*   A bounding box defined by lower bounds $(x_{vox\_lb}, y_{vox\_lb}, z_{vox\_lb})$ in voxelized space [S2, unofficial].
*   A function $isInside(x, y, z)$ that returns the occupancy value (0 or 1) for a given coordinate [S1, unofficial].

**Outputs:**
*   A binary file or stream containing an ASCII header followed by RLE-encoded data [S1, S3, unofficial].

**Data Structures:**
*   **RLE Pair:** A tuple $(value, count)$ where $value \in \{0, 1\}$ and $count$ represents the number of consecutive voxels with that value [S2, unofficial].
*   **Count Storage:** The count is stored in two bytes, representing a range of $[1, 256]$ (stored as values $0-255$) [S2, unofficial].
*   **RLEData Struct (Variant):** In some implementations, a struct containing `uint16_t value` and `uint32_t repetitions` is used [S3, unofficial].

**Steps:**

1.  **Write Header:** Write the ASCII string `"scale "` followed by the floating-point value of $m\_spacing$, then the string `"data"` [S1, unofficial].
2.  **Initialize:** Set $currentvalue = char(isInside(0, 0, 0))$ and $current\_seen = 1$ [S1, unofficial]. Write $currentvalue$ to the output stream [S1, unofficial].
3.  **Iterate:** Loop through the voxel grid. The iteration order specified in the primary source is $x$ from $0$ to $m\_dimX-1$, $z$ from $0$ to $m\_dimY-1$, and $y$ from $0$ to $m\_dimZ-1$ [S1, unofficial].
4.  **Skip First:** If $x=0, y=0, z=0$, skip the iteration to avoid double-writing the first voxel [S1, unofficial].
5.  **Compute Next:** Calculate $nextvalue = char(isInside(x, y, z))$ [S1, unofficial].
6.  **Check Run:**
    *   If $nextvalue \neq currentvalue$ or $current\_seen == 255$:
        *   Write $current\_seen$ to the output stream [S1, unofficial].
        *   Reset $current\_seen = 1$ [S1, unofficial].
        *   Update $currentvalue = nextvalue$ [S1, unofficial].
        *   Write $currentvalue$ to the output stream [S1, unofficial].
    *   Else:
        *   Increment $current\_seen$ [S1, unofficial].
7.  **Finalize:** After the loops, write the final $current\_seen$ count to the output stream and close the file [S1, unofficial].

**Decoding:**
To retrieve the original voxel coordinate $(x, y, z)$ from the compressed output, add the lower bound of the minimal bounding box: $(x + x_{vox\_lb}, y + y_{vox\_lb}, z + z_{vox\_lb})$ [S2, unofficial].

**Pseudocode:**
```python
def encode_voxel_rle(grid_dims, spacing, is_inside_func, bounds):
    dim_x, dim_y, dim_z = grid_dims
    output_stream = []
    
    # Step 1: Write Header
    output_stream.append(f"scale {spacing}")
    output_stream.append("data")
    
    # Step 2: Initialize
    current_value = 1 if is_inside_func(0, 0, 0) else 0
    current_seen = 1
    output_stream.append(current_value)
    
    # Step 3-6: Iterate
    for x in range(dim_x):
        for z in range(dim_y):
            for y in range(dim_z):
                # Step 4: Skip first
                if x == 0 and y == 0 and z == 0:
                    continue
                
                # Step 5: Compute Next
                next_value = 1 if is_inside_func(x, y, z) else 0
                
                # Step 6: Check Run
                if next_value != current_value or current_seen == 255:
                    output_stream.append(current_seen)
                    current_seen = 1
                    current_value = next_value
                    output_stream.append(current_value)
                else:
                    current_seen += 1
    
    # Step 7: Finalize
    output_stream.append(current_seen)
    
    return output_stream
```

**Parameters:**
*   $m\_spacing$: Voxel grid spacing, written as a floating-point value [S1, unofficial].
*   $m\_dimX, m\_dimY, m\_dimZ$: Grid dimensions in each axis, used as loop bounds [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Maximum Run Length:** The maximum run length is capped at 255 (char type); when reached, the encoder forces a new run to prevent overflow [S1, unofficial].
*   **First Voxel:** The first voxel $(0,0,0)$ is written before the loop to initialize the run, then skipped inside the loop to avoid double-writing [S1, unofficial].

## Subtopics

### [Run-length encoded voxel runs](1209-run-length-encoded-voxel-runs.md)
A pre-processing optimization for volume rendering that compresses voxel runs via run-length encoding based on pre-classified opacities to skip transparent or opaque regions during rendering. It differs from single-axis methods by constructing a separate encoded volume for each of the three major viewing directions, allowing the renderer to bypass empty space efficiently along the viewing axis.

### [Voxel File I/O (binvox/rawvox)](1698-voxel-file-i-o-binvox-rawvox.md)
This method serializes a 3D voxel grid into specific legacy file formats, primarily the `binvox` binary format and the `rawvox` text/binary hybrid format, to enable interoperability with external visualization tools and pipelines. It differs from generic voxel I/O by implementing the strict header structures and data ordering (row-major vs column-major) required by these specific standards, rather than providing a flexible, format-agnostic serialization interface.

### [Voxel Indexing and Bit Compression](1707-voxel-indexing-and-bit-compression.md)
Voxel Indexing and Bit Compression maps 3D voxel coordinates to a 1D binary bitstream and packs these bits into fixed-width integers (typically 64-bit) to minimize memory footprint and enable efficient parallel processing. It differs from Binary Voxel RLE Encoding by storing explicit occupancy bits for every possible voxel in the bounding box rather than run-length encoding sparse data, making it suitable for dense grids or scenarios requiring direct random access to occupancy status via atomic operations.

### [Dense-grid to Voxlap-slab packing](2155-dense-grid-to-voxlap-slab-packing.md)
Converts a dense voxel mask and color grid of size VSID × VSID × MAXZDIM into the Voxlap slab-RLE column format. It seeds an all-solid VXL and carves air voxels using a column function to preserve buried-voxel-aware encoding.

### [RLE4 Compression](4441-rle4-compression.md)
RLE4 Compression converts a dense 3D voxel grid into a sparse, column-oriented structure called **Map4** to solve memory bloat in large volumes with significant empty space. It processes the volume slice-by-slice (XZ planes), encoding runs of empty space (skip) and occupied space (solid) along the Y-axis into 16-bit words, while storing per-voxel color and intensity data in a separate texture buffer. Unlike Binary Voxel RLE Encoding which stores binary occupancy, RLE4 preserves per-voxel material and intensity information for splatting. ## Operating characteristics
**Time Complexity:**
The compression process runs in $O(n)$ time, where $n$ is the number of voxels in the minimal bounding box [S2, unofficial].

**Memory Complexity:**
Memory usage is proportional to the number of runs, which is significantly less than the total number of voxels for sparse grids [S2, unofficial].

**Measured Performance:**
Not given in the sources.

**Scaling:**
The method scales linearly with the number of voxels in the bounding box [S2, unofficial].

**Strengths:**
*   Efficiently compresses sparse voxel data [S1, S2, unofficial].
*   Simple implementation [S2, unofficial].
*   Reduces file size significantly for meshes with large empty spaces [S2, unofficial].

**Limitations:**
*   Only stores binary occupancy, not material properties [S1, unofficial].
*   Run length is limited to 255, which may result in larger files for large homogeneous regions compared to 16-bit or 32-bit counters [S1, S3, unofficial].
*   Requires the minimal bounding box to be known or calculated beforehand [S2, unofficial].

**When to use:**
Use when storage size is a concern and the voxel grid is sparse, and only binary occupancy is needed [S1, S2, unofficial].

**When not to use:**
Do not use when per-voxel material information is required (use [RLE4 Compression](4441-rle4-compression.md) instead) or when the grid is dense and random access is needed (use [Voxel Indexing and Bit Compression](1707-voxel-indexing-and-bit-compression.md) instead) [S1, unofficial].

## Background
Binary Voxel RLE Encoding is a compression scheme for voxel data output, often associated with the `binvox` format [S1, S2, unofficial]. It was implemented in various open-source voxelization projects, such as `kctess5/voxelizer` and `topskychen/voxelizer`, to provide a compact way to store voxelized mesh data [S1, S2, unofficial]. The method is also used in tools like `VoxelFragmentML` for exporting voxel data [S3, unofficial].
