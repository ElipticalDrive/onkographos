# Sparse Voxelization with Oracle and Parallel Scan

Also called: Coarse-to-Fine Voxel Representation, GPU Based Sparse Voxelization, Sparse Voxelization via Coarse-to-Fine Oracle and Scan

## Overview
Sparse Voxelization with Oracle and Parallel Scan is a real-time, high-resolution technique for reconstructing 3D surface models from image-based inputs (calibrated RGB camera streams) using a coarse-to-fine voxel hierarchy [S1]. It solves the problem of on-the-fly surface reconstruction by iteratively refining a sparse list of voxels, using an oracle kernel to cull empty space and a parallel prefix sum scan to compact the list, ensuring that only relevant voxels are subdivided [S1]. Unlike bottom-up approaches or methods designed for static models, this method is top-down and optimized for interactive rates (e.g., >30 fps at 1024^3 resolution) by leveraging GPU parallelism for both computation and rendering [S1].

## How it works
**Inputs and Outputs**
*   **Inputs:** A set of calibrated RGB images from multiple cameras [S1]; the initial voxel hierarchy level $k$ (typically $k=4$) [S1]; the target resolution determined by pixel size [S1].
*   **Outputs:** A sparse list of voxels $\mathcal{V}^k$ at the target resolution, ready for rendering as splats [S1].

**Data Structures**
Voxels are stored as a dynamic array (list) of unsigned integer triples $\{ix, iy, iz\}$ [S1].
*   **Layout:** Each triple represents the integer coordinates of a voxel corner within a 3D grid of dimensions $2^k \times 2^k \times 2^k$ [S1].
*   **Sparse Storage:** The list $\mathcal{V}^k$ contains only existing voxels; space for the full $2^{3k}$ grid is not allocated [S1]. The number of stored voxels $|\mathcal{V}^k|$ is proportional to the surface area of the object [S1].
*   **Decision List:** A parallel array of integers (0 or 1) generated by the Oracle kernel, where 1 indicates "keep" and 0 indicates "cull" [S1].

**Formulas**
Normalized Voxel Coordinates (NVC) map integer grid coordinates to the canonical cube $[-1, 1]^3$ [S1]:
$$
nx = \sigma_k \cdot ix - 1, \quad ny = \sigma_k \cdot iy - 1, \quad nz = \sigma_k \cdot iz - 1
$$
where $\sigma_k = 2^{1-k}$ [S1].

**Parameters**
*   **Initial Level $k$:** $k=4$ is used to start with a $16^3$ grid (4096 voxels) to ensure full GPU core utilization early on [S1].
*   **Block Size:** 1024 voxels for all compute kernels except Generate, which uses 128 [S1].
*   **Render Target:** 1080 × 1920 resolution in performance tests [S1].

**Algorithm Steps**
The pipeline consists of four main stages, repeated iteratively:

1.  **Generate:**
    *   Create an initial list of voxels for level $k$ [S1].
    *   Each thread $t$ computes its voxel coordinates:
        $$
        v.ix = t / 256
        $$
        $$
        v.iy = (t / 16) \% 16
        $$
        $$
        v.iz = t \% 16
        $$
    *   Store $v$ in `VoxelList[t]` [S1].

2.  **Oracle:**
    *   For each voxel in the current list, evaluate an image consistency criterion (e.g., projection across cameras) [S1].
    *   Write a decision value $d$ to a decision list at the corresponding thread index:
        *   $d = 1$ if the voxel (and potentially its children) is consistent with the input images (keep) [S1].
        *   $d = 0$ if the voxel is inconsistent (cull) [S1].

3.  **Scan:**
    *   Perform an exclusive parallel prefix sum scan on the decision list [S1].
    *   The output value at index $i$ is the sum of all input elements less than $i$ [S1].
    *   This scan output provides the new sequential index for each kept voxel in the compacted list, effectively removing culled voxels in parallel [S1].

4.  **Subdivide (or Compactify):**
    *   If the target resolution is not reached:
        *   **Subdivide:** For each kept voxel, generate 8 child sub-voxels at level $k+1$ [S1]. The process returns to **Oracle** with the expanded list [S1].
    *   If the target resolution is reached:
        *   **Compactify:** Finalize the list of voxels for rendering [S1].
    *   **Render:** Draw the final voxels as splats, textured by a weighted combination of the input color images [S1].

## Subtopics

### [Voxel Subdivision Kernel](6013-voxel-subdivision-kernel.md)
The Voxel Subdivision Kernel is a parallel GPU kernel used within the Sparse Voxelization with Oracle and Parallel Scan pipeline to increase the resolution of the voxel grid. It takes a list of active voxels and generates eight child sub-voxels for each, effectively refining the spatial representation. It is distinguished from the Voxel Compactify Kernel by its expansion factor (8:1) and is invoked during intermediate iterations of the adaptive voxelization process, whereas compactification occurs only at the final stage to remove culled voxels.

## Operating characteristics
*   **Time Complexity:** The method is iterative, with complexity proportional to the number of levels and the number of voxels at each level [S1]. The scan and oracle steps are linear in the number of voxels $|\mathcal{V}^k|$ [S1].
*   **Memory Complexity:** Memory usage is proportional to the surface area of the object, not the volume of the grid, as only existing voxels are stored [S1].
*   **Performance:** On an nVidia GeForce Titan, a level 9 model (606,660 voxels) took 9.75 ms (112 fps), and a level 10 model (2,538,713 voxels) took 14.64 ms (83 fps) [S1]. On an AMD Radeon 7970GE, the same levels took 23.86 ms (46 fps) and 35.00 ms (30 fps) respectively [S1]. Rendering is the most costly step, particularly on Radeon hardware [S1].
*   **Strengths:** Real-time performance (giga-voxel resolution at >30 fps); efficient use of GPU parallelism; avoids color/depth buffer write hazards by using the graphics pipeline for rendering [S1].
*   **Limitations:** Hardware rasterization of pixel-sized triangles is inefficient; uniform subdivision is used for simplicity, which may be less optimal than adaptive subdivision for complex geometries [S1].

## Background
The method was introduced in the paper "Real-time high-resolution sparse voxelization with application to image-based modeling" [S1]. It addresses the problem of real-time 3D reconstruction from live image streams, such as in telepresence and free viewpoint performance capture [S1]. It differs from bottom-up approaches like Ajmera et al. (2008) and static model accelerators like Gigavoxels (Laine and Karras, 2011) by being top-down and designed for on-the-fly reconstruction [S1].
