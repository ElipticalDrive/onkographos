# Asynchronous Voxel Update

Also called: Lower-frequency Voxelization, Temporal Voxel Update, Timed Update Logic

## Overview
Asynchronous Voxel Update is a technique that decouples the frequency of voxel grid regeneration from the rendering frame rate to leverage temporal coherency in scenes with static or slowly moving geometry and lighting [S2, unofficial]. Unlike synchronous voxelization methods that recompute the entire volume every frame, this approach updates the voxel data only when specific time or progress thresholds are met, trading geometric accuracy for significant performance gains [S2, unofficial]. It is distinct from view-adaptive voxelization, which adjusts resolution based on camera position, by instead adjusting the *temporal* frequency of updates based on scene dynamics [3313-view-adaptive-voxelization.md].

## How it works
**Inputs and Outputs:**
- **Input:** Current system time or frame timestamp, previous update timestamp, update interval parameter, and the source geometry (mesh/point cloud) to be voxelized.
- **Output:** Boolean flag indicating whether an update should occur; updated voxel grid data if the flag is true.

**Data Structures:**
- `last_update_time`: Float or integer representing the timestamp of the last voxelization pass.
- `update_interval`: Float or integer representing the minimum time (in ms) or frame count between updates.
- `progress`: Float in range $[0, 1]$ representing the completion state of the current update task, if asynchronous processing is used.

**Parameters:**
- `update_interval`: Typical value is 1500 ms (1.5 seconds) or every 5 frames [S1, unofficial][S2, unofficial].
- `progress_threshold`: Threshold to abort or yield if the update takes too long. Typical value is 0.95 [S1, unofficial].

**Steps:**
1. Retrieve the current time $t_{now}$ and the last update time $t_{last}$.
2. Calculate the elapsed time $\Delta t = t_{now} - t_{last}$.
3. If the update process is asynchronous and has a progress metric $p$:
   - If $p \ge 0.95$, return `false` to yield control and prevent blocking [S1, unofficial].
4. Check if the update condition is met:
   - If $\Delta t \ge \text{update\_interval}$, proceed to update.
5. If the update condition is met:
   - Perform voxelization of the source geometry into the voxel grid.
   - Update $t_{last} \leftarrow t_{now}$.
   - Return `true`.
6. Otherwise, return `false`.

**Pseudocode:**
```python
def should_update_voxels(current_time, last_update_time, update_interval_ms, progress=None):
    """
    Determines if the voxel grid should be updated based on time elapsed and progress.
    
    Args:
        current_time (float): Current timestamp in milliseconds.
        last_update_time (float): Timestamp of the last voxel update.
        update_interval_ms (float): Minimum time in ms between updates.
        progress (float, optional): Progress of the current update task [0.0, 1.0].
        
    Returns:
        bool: True if an update should be performed, False otherwise.
    """
    # If an asynchronous update is in progress and nearing completion, yield
    if progress is not None and progress >= 0.95:
        return False
    
    elapsed_time = current_time - last_update_time
    
    # Check if enough time has passed since the last update
    if elapsed_time >= update_interval_ms:
        # Perform voxelization here (implementation depends on voxelization method)
        # update_voxel_grid()
        
        # Update the last update timestamp
        last_update_time = current_time
        return True
    
    return False
```

**Edge Cases and Pitfalls:**
- **Visual Lag:** Updating at a lower frequency causes the voxel model to lag behind the actual triangle mesh, resulting in visible artifacts, especially with fast-moving objects or dynamic lighting [S2, unofficial].
- **Precision:** Ensure timestamp comparisons handle clock drift or non-monotonic time sources if applicable [G].
- **Degenerate Input:** If `update_interval_ms` is set to 0, the method will attempt to update every frame, negating the performance benefit.

## Operating characteristics
- **Time Complexity:** $O(1)$ for the decision logic; $O(N)$ for the actual voxelization, where $N$ is the number of primitives or points. The effective time per frame is reduced by the update frequency factor $f < 1$.
- **Memory Complexity:** $O(V)$, where $V$ is the number of voxels, same as synchronous methods. No additional memory overhead for the timing logic.
- **Measured Performance:** In voxel cone tracing implementations, updating every 5 frames significantly reduces GPU load, allowing for real-time global illumination with dynamic lights [S2, unofficial].
- **Strengths:** Reduces computational load; leverages temporal coherence; suitable for static or slow-moving scenes.
- **Limitations:** Introduces visual artifacts (jitter, lag) with fast-moving geometry or lighting; not suitable for high-fidelity static scenes where temporal coherence is low.
- **When to Use:** Real-time rendering with dynamic lighting where performance is critical and minor visual artifacts are acceptable.
- **When Not to Use:** High-precision offline rendering, scenes with fast-moving objects, or when visual fidelity is paramount.

## Background
Asynchronous Voxel Update was introduced in the context of implementing real-time Voxel Cone Tracing for global illumination [S2, unofficial]. The technique was proposed to mitigate the high computational cost of voxelizing dynamic scenes every frame, allowing for single-bounce indirect lighting with directional lights in real-time applications [S2, unofficial]. It is commonly used in game engines and real-time rendering demos where performance optimization is critical [S1, unofficial].
