# Geometry Shader Voxelization

Also called: Fragment-based Voxelization, GS Voxelization, GeometryVoxelizer, OpenGL Geometry Shader Voxelization, Solid Triangle Voxelization, Triangle-to-Voxel Rasterization

## Overview
Geometry Shader Voxelization rasterizes a polygonal mesh directly into a 3D voxel grid by leveraging the GPU's geometry shader stage to project triangles onto axis-aligned planes and write occupancy or color data into 3D textures [S2, S4, unofficial]. It differs from [A-Buffer Solid Voxelization](1189-a-buffer-solid-voxelization.md) by writing directly to a 3D volume without intermediate accumulation buffers, and from [GPU Mesh Voxelization via AABB-Triangle Intersection](2541-gpu-mesh-voxelization-via-aabb-triangle-intersection.md) by relying on hardware rasterization coverage rather than explicit geometric intersection tests [S2, S4, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A triangle mesh (vertices and indices) and a target 3D grid resolution `voxelResolution` (typically cubic, e.g., $64^3$) [S4, unofficial].
*   **Output:** A 3D texture (or Unordered Access View) representing the voxel grid. Common formats include `GL_R8UI` for occupancy (single channel, 8-bit unsigned int) and `GL_RGBA8` for color (4 channels, 8-bit unsigned int) [S4, unofficial].

**Data Structures:**
*   **Voxel Texture:** A 3D image bound at a specific binding point. For example, `voxelOccupancy` is `layout(r8ui, binding = 0) uniform uimage3D` and `voxelColor` is `layout(rgba8, binding = 1) uniform image3D` [S4, unofficial].
*   **Mesh Data:** Vertices stored in a vertex buffer (e.g., `Eigen::Matrix<float, -1, -1>` for $3 \times N$ floats) and faces in an element buffer (e.g., `Eigen::Matrix<uint32_t, -1, -1>` for $3 \times M$ indices) [S4, unofficial].

**Parameters:**
*   `voxelResolution`: The dimensions of the grid $(N_x, N_y, N_z)$ [S4, unofficial].
*   `THICKNESS`: A compile-time constant selecting between "Thin" (0) or "Fat" (1) voxelization modes [S4, unofficial].
*   `mipLevel`: Optional parameter to reduce the effective viewport and scissor dimensions by `GRID_SIZE >> mipLevel` [S3, unofficial].

**Steps:**

1.  **Mesh Normalization:**
    Compute the axis-aligned bounding box (AABB) of the mesh vertices to find `xmin, xmax, ymin, ymax, zmin, zmax`. Calculate the maximum dimension $d_{max} = \max(x_{max}-x_{min}, y_{max}-y_{min}, z_{max}-z_{min})$. Normalize all vertex coordinates to the $[0, 1]$ range:
    $$ V_{norm} = \frac{V - V_{min}}{d_{max}} $$
    [S4, unofficial]

2.  **Pipeline Setup:**
    Bind the voxelization shaders (Vertex, Geometry, Fragment). Pass `voxelResolution` as a uniform. Bind the output 3D textures as images for writing. Set the primitive topology to `TRIANGLELIST` [S4, unofficial].

3.  **Triangle Processing (Geometry Shader):**
    For each input triangle with vertices $v_0, v_1, v_2$:
    a.  **Swizzling:** Calculate the triangle normal $n = \text{cross}(v_1 - v_0, v_2 - v_1)$. Determine the dominant axis of the normal (the component with the largest absolute value). Permute the vertex coordinates and normal so that the dominant plane aligns with the XY plane. Store the permutation matrix `unswizzle` to reverse the transformation later [S4, unofficial].
    b.  **Edge Normals:** Compute inward-facing 2D edge normals for the XY, YZ, and ZX planes. For an edge $e$ and plane normal component $n_p$, the 2D edge normal $n_e$ is determined by the sign of $n_p$. For example, for the XY plane:
        $$ n_{e,xy} = \begin{cases} (-e_y, e_x) & \text{if } n_z \ge 0 \\ (e_y, -e_x) & \text{if } n_z < 0 \end{cases} $$
        [S4, unofficial]
    c.  **Bounding Box:** Compute the AABB of the triangle vertices in voxel space. Clamp indices to $[0, \text{voxelResolution}]$ [S4, unofficial].
    d.  **Distance Calculation:**
        *   **Thin Mode:** Calculate edge distances $d_e$ and triangle plane distance $d_{Tri}$ using formulas that ensure adjacent voxels are connected by vertices [S4, unofficial].
        *   **Fat Mode:** Calculate edge distances and min/max plane distances using formulas that ensure adjacent voxels share at least a face [S4, unofficial].
    e.  **Overlap Testing:**
        *   Iterate through the projected XY bounding box. For each voxel $(p_x, p_y)$, check if it overlaps the triangle in the XY plane using the edge distances [S4, unofficial].
        *   If XY overlap exists, calculate the Z-intersection range $[z_{min}, z_{max}]$ using the triangle plane distance and the normal's Z component. Apply floor/ceil boundary handling [S4, unofficial].
        *   Iterate through the Z range. For each voxel $(p_x, p_y, p_z)$, check overlaps in the YZ and ZX planes. If all three plane overlaps are true, the voxel is occupied [S4, unofficial].
    f.  **Writing:**
        Write to the occupancy image: `imageStore(voxelOccupancy, ivec3(unswizzle * p), uvec4(1))`.
        Write to the color image: `imageStore(voxelColor, ivec3(unswizzle * p), vec4(unswizzle * p / voxelResolution, 1))` [S4, unofficial].

4.  **Synchronization:**
    Call `glMemoryBarrier(GL_ALL_BARRIER_BITS)` to ensure the 3D texture writes are complete before reading [S4, unofficial].

## Subtopics

### [GPU Mesh Voxelization via AABB-Triangle Intersection](2541-gpu-mesh-voxelization-via-aabb-triangle-intersection.md)
This method voxelizes a polygonal mesh by dispatching one compute shader thread per voxel grid cell, which then tests its Axis-Aligned Bounding Box (AABB) against every triangle in the mesh using the Separating Axis Theorem (SAT). It differs from [Geometry Shader Voxelization](2566-geometry-shader-voxelization.md) by avoiding the overhead of generating geometry primitives and from [GPU Voxelization Using OpenGL Image Atomics](2544-gpu-voxelization-using-opengl-image-atomics.md) by relying on explicit geometric intersection tests rather than rasterization coverage. It is a brute-force approach that does not use spatial acceleration structures.

### [GPU Voxelization Using OpenGL Image Atomics](2544-gpu-voxelization-using-opengl-image-atomics.md)
GPU Voxelization Using OpenGL Image Atomics transforms continuous 3D polygonal meshes into a discrete, regular volumetric grid stored in GPU memory by projecting geometry along its dominant axis, rasterizing fragments without a traditional framebuffer, and utilizing fragment-stage image atomic operations to write directly into 3D textures. It solves the problems of projection loss (degenerate triangles perpendicular to the view plane) and race conditions (concurrent writes to the same voxel) inherent in standard rasterization pipelines. Unlike standard rasterization which projects onto a 2D viewport, this method decouples rasterization from the framebuffer, converting complex geometric meshes into solid or shell voxel structures in a single render pass. It differs from [Geometry Shader Voxelization](2566-geometry-shader-voxelization.md) by explicitly handling concurrency via hardware atomics and dominant-axis projection to ensure watertightness, and from [GPU Mesh Voxelization via AABB-Triangle Intersection](2541-gpu-mesh-voxelization-via-aabb-triangle-intersection.md) by relying on rasterization primitives rather than explicit geometric intersection tests [G].

### [GPU Mesh Voxelization via Axis-Aligned Projection](2561-gpu-mesh-voxelization-via-axis-aligned-projection.md)
GPU Mesh Voxelization via Axis-Aligned Projection converts a triangle mesh into a 3D voxel grid (typically a 3D texture or structured buffer) by projecting each triangle onto a 2D plane aligned with its dominant normal axis, rasterizing it, and writing the resulting fragments into the 3D volume. This method solves the "missing voxel" artifacts common in single-direction rasterization by ensuring that every triangle is viewed from the orientation that maximizes its projected surface area, thereby minimizing gaps caused by edge-on or thin polygons. It differs from [GPU Mesh Voxelization via AABB-Triangle Intersection](2541-gpu-mesh-voxelization-via-aabb-triangle-intersection.md) by relying on hardware rasterization rather than explicit geometric intersection tests, and from [GPU Voxelization Using OpenGL Image Atomics](2544-gpu-voxelization-using-opengl-image-atomics.md) by using a geometry shader to determine projection axes rather than a single fixed view or pure compute shaders.

### [Single-Pass GPU Voxelization](14396-single-pass-gpu-voxelization.md)
Single-Pass GPU Voxelization is a technique that maps 3D mesh vertices directly to a 3D grid (voxel space) in a single rasterization pass using a Frame Buffer Object (FBO), avoiding the multiple passes required by methods like Karabassi et al.. It sets itself apart from its sibling [Geometry Shader Voxelization](2566-geometry-shader-voxelization.md) by encoding voxel indices into vertex attributes and the FBO alpha channel during the vertex shader stage, rather than rasterizing triangles into a 3D texture via a geometry shader. It is distinct from [GPU Voxelization Using OpenGL Image Atomics](2544-gpu-voxelization-using-opengl-image-atomics.md) by relying on standard rasterization depth testing and FBO downloads rather than atomic operations on 3D textures.

## Operating characteristics
*   **Time Complexity:** Proportional to the number of triangles and the surface area of the mesh projected onto the grid. The geometry shader processes each triangle once, but the inner loops over voxel coordinates depend on the triangle's bounding box size [S4, unofficial].
*   **Memory Complexity:** $O(N^3)$ for the output 3D texture, where $N$ is the voxel resolution. The input mesh is stored in standard buffers [S4, unofficial].
*   **Performance:** Efficient for dense meshes where rasterization hardware is utilized effectively. Less efficient for sparse triangles or very large grids compared to compute-based methods that skip empty space [S2, unofficial].
*   **Strengths:** Simple implementation using standard graphics pipeline; leverages GPU rasterization hardware; supports direct color writing [S4, unofficial].
*   **Limitations:** Overwrites voxel values if multiple fragments map to the same voxel (order depends on rasterization depth and draw order); potential for boundary errors if not clamped properly [S2, S4, unofficial].
*   **When to use:** When a quick, hardware-accelerated voxelization is needed and the mesh is not extremely sparse.
*   **When not to use:** When precise control over voxel occupancy (e.g., watertightness without overwrites) is required, or when the grid is very large and sparse [S2, unofficial].

## Background
Geometry Shader Voxelization originated as a method to leverage the OpenGL Geometry Shader stage for direct 3D volume rendering preparation. It was popularized in lightweight libraries such as `Mesh-Voxelization-OpenGL-Geometry-Shader` which demonstrated voxelizing `.ply` and `.obj` meshes directly into 3D textures [S4, unofficial]. It is used in real-time applications where mesh data needs to be converted to voxel data for ray marching or voxel cone tracing [S2, unofficial].
