# Geometry Shader Voxelization

Also called: Fragment-based Voxelization, GS Voxelization, GeometryVoxelizer, OpenGL Geometry Shader Voxelization, Solid Triangle Voxelization, Triangle-to-Voxel Rasterization

## Overview
Geometry Shader Voxelization rasterizes polygonal meshes directly into a 3D voxel grid by leveraging the GPU's geometry shader stage to project triangles onto axis-aligned planes and iterate through occupied grid cells [S4, unofficial]. It solves the problem of converting continuous surface geometry into discrete volumetric data without requiring explicit CPU-side raycasting or compute-shader-based brute-force intersection tests [S2, unofficial]. Unlike sibling methods that rely on hardware rasterization of 2D fragments (e.g., [Image-space Voxelization](14395-image-space-voxelization.md)) or pure compute shaders (e.g., [GPU Mesh Voxelization via AABB-Triangle Intersection](2541-gpu-mesh-voxelization-via-aabb-triangle-intersection.md)), this method explicitly generates 3D voxel primitives or iterates grid bounds within the shader, offering a balance between implementation simplicity and watertightness control [S2, S4, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A triangle mesh defined by vertex positions $V$ (size $3 \times N$) and face indices $F$ (size $3 \times M$) [S4, unofficial].
*   **Output:** A 3D occupancy grid (e.g., `GL_TEXTURE_3D` with format `GL_R8UI`) and optionally a 3D color grid (e.g., `GL_RGBA8`) [S4, unofficial].

**Data Structures:**
*   **Voxel Resolution:** A uniform `ivec3` `voxelResolution` specifying grid dimensions $(D_x, D_y, D_z)$, typically cubic ($D_x=D_y=D_z=dim$) [S4, unofficial].
*   **Bounding Box:** The axis-aligned bounding box (AABB) of the mesh vertices, computed as `min` and `max` vectors [S4, unofficial].
*   **Projection Matrix:** A permutation matrix `unswizzle` used to align the triangle's dominant normal axis with a principal plane (XY, YZ, or ZX) [S4, unofficial].

**Parameters:**
*   `THICKNESS`: Compile-time constant selecting voxel thickness mode. `THIN` (0) ensures vertex connectivity; `FAT` (1) ensures face connectivity [S4, unofficial].
*   `voxelResolution`: Grid dimensions [S4, unofficial].

**Algorithm Steps:**

1.  **Mesh Preprocessing:**
    *   Load mesh vertices $V$ and faces $F$ [S4, unofficial].
    *   Compute the AABB of $V$: $v_{min} = \min(V)$, $v_{max} = \max(V)$ [S4, unofficial].
    *   Calculate the maximum dimension $d_{max} = \max(v_{max} - v_{min})$ [S4, unofficial].
    *   Normalize vertices to $[0, 1]$ range: $V_{norm} = (V - v_{min}) / d_{max}$ [S4, unofficial].

2.  **Pipeline Setup:**
    *   Bind the geometry shader pipeline. The pipeline typically includes a Vertex Shader (pass-through), a Geometry Shader (core logic), and a Fragment Shader (optional, often empty or used for color sampling) [S4, unofficial].
    *   Bind the 3D texture images for occupancy and color output [S4, unofficial].

3.  **Triangle Processing (Geometry Shader):**
    For each input triangle with vertices $v_0, v_1, v_2$:
    
    a.  **Swizzling:**
        *   Compute the triangle normal $n = (v_1 - v_0) \times (v_2 - v_1)$ [S4, unofficial].
        *   Identify the dominant axis of $|n|$ (the component with the largest absolute value) [S4, unofficial].
        *   Permute the vertex coordinates and normal so that the dominant plane aligns with the XY plane. Store the permutation matrix `unswizzle` to reverse coordinates later [S4, unofficial].

    b.  **Edge Normal Calculation:**
        *   Compute edge vectors: $e_0 = v_1 - v_0$, $e_1 = v_2 - v_1$, $e_2 = v_0 - v_2$ [S4, unofficial].
        *   Calculate inward-facing 2D edge normals for the projected plane (XY). The sign depends on the perpendicular normal component (e.g., $n_z$). For edge $e_0$:
            $$n_{e0,xy} = \begin{cases} (-e_{0,y}, e_{0,x}) & \text{if } n_z \ge 0 \\ (e_{0,y}, -e_{0,x}) & \text{if } n_z < 0 \end{cases}$$
        *   Repeat for YZ and ZX planes using the respective perpendicular normal components ($n_x$ for YZ, $n_y$ for ZX) [S4, unofficial].

    c.  **Bounding Box Calculation:**
        *   Compute the AABB of the swizzled triangle vertices [S4, unofficial].
        *   Convert to voxel indices:
            $$idx_{min} = \text{clamp}(\lfloor \text{AABB}_{min} \cdot \text{voxelResolution} \rfloor, 0, \text{voxelResolution} - 1)$$
            $$idx_{max} = \text{clamp}(\lceil \text{AABB}_{max} \cdot \text{voxelResolution} \rceil, 0, \text{voxelResolution} - 1)$$
        *   Determine the loop bounds for $x, y$ (from $idx_{min}$ to $idx_{max}$ in XY) and $z$ (from $idx_{min}$ to $idx_{max}$ in Z) [S4, unofficial].

    d.  **Voxel Iteration and Overlap Test:**
        *   Iterate $p_x$ from $idx_{min,x}$ to $idx_{max,x}$ and $p_y$ from $idx_{min,y}$ to $idx_{max,y}$ [S4, unofficial].
        *   **XY Overlap Check:**
            *   Calculate initial edge distances $d_e$ for each edge. For **Thin** voxelization:
                $$d_e = \text{dot}(n_e, 0.5 - v_{proj}) + 0.5 \times \max(|n_{e,x}|, |n_{e,y}|)$$
                For **Fat** voxelization:
                $$d_e = -\text{dot}(n_e, v_{proj}) + \max(0, n_{e,x}) + \max(0, n_{e,y})$$
            *   Update distances for current voxel coordinate $p_{proj} = (p_x, p_y)$:
                $$dd_e = d_e + \text{dot}(n_e, p_{proj})$$
            *   Check overlap: `xy_overlap = (dd_e0 >= 0) && (dd_e1 >= 0) && (dd_e2 >= 0)` [S4, unofficial].
        
        *   **Z-Range Calculation (if xy_overlap is true):**
            *   Compute triangle plane distance $d_{Tri}$. For **Thin**:
                $$d_{Tri} = \text{dot}(n_{proj}, v_0) - \text{dot}(n_{proj,xy}, 0.5)$$
                For **Fat**:
                $$d_{Tri, min} = \text{dot}(n_{proj}, v_0) - \max(n_{proj,x}, 0) - \max(n_{proj,y}, 0)$$
                $$d_{Tri, max} = \text{dot}(n_{proj}, v_0) - \min(n_{proj,x}, 0) - \min(n_{proj,y}, 0)$$
            *   Calculate Z-intersection range for the plane at $p_{xy}$:
                $$z_{min} = \frac{-\text{dot}(n_{proj,xy}, p_{xy}) + d_{Tri}}{n_{proj,z}}$$
                (Use $d_{Tri, min}$ and $d_{Tri, max}$ for Fat mode) [S4, unofficial].
            *   Determine voxel Z-range indices $z_{min\_idx}, z_{max\_idx}$ using floor/ceil with boundary handling to ensure coverage [S4, unofficial].

        *   **YZ and ZX Overlap Checks:**
            *   Iterate $p_z$ from $z_{min\_idx}$ to $z_{max\_idx}$ [S4, unofficial].
            *   Update edge distances for YZ and ZX planes using the 3D coordinate $p = (p_x, p_y, p_z)$ [S4, unofficial].
            *   Check `yz_overlap` and `zx_overlap` using the same dot-product logic as XY [S4, unofficial].

    e.  **Voxel Write:**
        *   If `xy_overlap`, `yz_overlap`, and `zx_overlap` are all true, the voxel is occupied [S4, unofficial].
        *   Write to the occupancy image: `imageStore(voxelOccupancy, ivec3(unswizzle * p), uvec4(1))` [S4, unofficial].
        *   Write to the color image (optional): `imageStore(voxelColor, ivec3(unswizzle * p), vec4(...))` [S4, unofficial].

4.  **Post-Processing:**
    *   Synchronize GPU with `glMemoryBarrier(GL_ALL_BARRIER_BITS)` [S4, unofficial].
    *   Read back the 3D texture data to CPU if required [S4, unofficial].

## Subtopics

### [GPU Mesh Voxelization via AABB-Triangle Intersection](2541-gpu-mesh-voxelization-via-aabb-triangle-intersection.md)
This method voxelizes a polygonal mesh by dispatching one compute shader thread per voxel in a 3D grid, where each thread performs a brute-force Axis-Aligned Bounding Box (AABB) vs. Triangle intersection test against all mesh triangles. It differs from [Geometry Shader Voxelization](2566-geometry-shader-voxelization.md) by avoiding the overhead of geometry shader primitive generation and from [GPU Voxelization Using OpenGL Image Atomics](2544-gpu-voxelization-using-opengl-image-atomics.md) by using a single-writer-per-voxel model without atomic blending. It is chosen when simplicity of implementation is prioritized over performance, as it lacks spatial acceleration structures.

### [GPU Voxelization Using OpenGL Image Atomics](2544-gpu-voxelization-using-opengl-image-atomics.md)
GPU Voxelization Using OpenGL Image Atomics transforms continuous 3D polygonal meshes into a discrete, regular volumetric grid stored in GPU memory by projecting geometry along its dominant axis, rasterizing fragments without a traditional framebuffer, and utilizing fragment-stage image atomic operations to write directly into 3D textures. It solves the problems of projection loss (degenerate triangles perpendicular to the view plane) and race conditions (concurrent writes to the same voxel) inherent in standard rasterization pipelines. Unlike standard rasterization which projects onto a 2D viewport, this method decouples rasterization from the framebuffer, converting complex geometric meshes into solid or shell voxel structures in a single render pass. It differs from [Geometry Shader Voxelization](2566-geometry-shader-voxelization.md) by explicitly handling concurrency via hardware atomics and dominant-axis projection to ensure watertightness, and from [GPU Mesh Voxelization via AABB-Triangle Intersection](2541-gpu-mesh-voxelization-via-aabb-triangle-intersection.md) by relying on rasterization primitives rather than explicit geometric intersection tests [G].

### [GPU Mesh Voxelization via Axis-Aligned Projection](2561-gpu-mesh-voxelization-via-axis-aligned-projection.md)
GPU Mesh Voxelization via Axis-Aligned Projection converts a triangle mesh into a 3D voxel grid (typically a 3D texture or structured buffer) by projecting each triangle onto a 2D plane aligned with its dominant normal axis, rasterizing it, and writing the resulting fragments into the 3D volume. This method solves the "missing voxel" artifacts common in single-direction rasterization by ensuring that every triangle is viewed from the orientation that maximizes its projected surface area, thereby minimizing gaps caused by edge-on or thin polygons. It differs from [GPU Mesh Voxelization via AABB-Triangle Intersection](2541-gpu-mesh-voxelization-via-aabb-triangle-intersection.md) by relying on hardware rasterization rather than explicit geometric intersection tests, and from [GPU Voxelization Using OpenGL Image Atomics](2544-gpu-voxelization-using-opengl-image-atomics.md) by using a geometry shader to determine projection axes rather than a single fixed view or pure compute shaders.

### [Single-Pass GPU Voxelization](14396-single-pass-gpu-voxelization.md)
A voxelization technique that maps 3D mesh vertices to a 3D grid (voxel space) in a single rasterization pass using a Frame Buffer Object (FBO), avoiding the multiple passes required by methods like Karabassi et al. [9].

## Operating characteristics
*   **Time Complexity:** $O(T \cdot B)$, where $T$ is the number of triangles and $B$ is the average number of voxels in the triangle's bounding box. The geometry shader iterates through the bounding box of each triangle [S4, unofficial].
*   **Memory Complexity:** $O(D^3)$ for the 3D voxel grid, where $D$ is the grid resolution [S4, unofficial].
*   **Performance:** Performance depends heavily on the sparsity of the mesh and the grid resolution. For dense meshes or large grids, the bounding box iteration can be inefficient compared to sparse voxel octrees or compute-based methods with acceleration structures [S2, unofficial].
*   **Strengths:** Simple implementation using standard graphics pipeline; supports both "Thin" and "Fat" voxelization modes for different connectivity requirements [S4, unofficial].
*   **Limitations:** Overwrites voxel values if multiple fragments map to the same voxel (order depends on rasterization depth and draw order) [S2, unofficial]. Requires careful handling of boundary clamping to prevent out-of-bounds access [S4, unofficial].

## Background
Geometry Shader Voxelization was developed as a lightweight method for converting `.ply` or `.obj` meshes into 3D voxel grids using OpenGL Geometry Shaders [S4, unofficial]. It leverages the flexibility of the geometry shader to perform 3D rasterization logic directly on the GPU, avoiding the need for complex compute shader synchronization or CPU-side processing [S4, unofficial]. The method is often cited in the context of real-time voxel cone tracing and other GPU-accelerated rendering techniques [S2, unofficial].
