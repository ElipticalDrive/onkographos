# Slicemap Boundary Voxelization

Also called: GPU Boundary Voxelization, GPU friendly voxel representation, Slicemap

## Overview
Slicemap Boundary Voxelization is a technique to represent a binary 3D grid of voxels using a single 2D texture, where the $k$-th bit of the RGBA representation of pixel $(i, j)$ encodes the occupancy of voxel $(i, j, k)$ [S1, unofficial]. It solves the problem of real-time voxelization by leveraging graphics hardware to test geometry for intersection with an encompassing grid of cells, allowing the tracking of all fragments in a single pass rather than discarding all but the closest [S1, unofficial]. Unlike [Conservative Voxelization via Depth Range](3129-conservative-voxelization-via-depth-range.md), which encodes depth ranges into occupancy bits, slicemaps explicitly map specific depth slices to specific bit positions, enabling efficient accumulation of all intersecting geometry via bitwise operations [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D scene (meshes) and a camera frustum defining the voxel grid's spatial extent ($x, y$) and depth range ($z$) [S1, unofficial].
*   **Output:** A 2D texture (the slicemap) where each texel stores a 32-bit integer representing a column of 32 voxels [S1, unofficial].

**Data Structures:**
*   **Slicemap Texture:** A 2D texture with width $W$ and height $H$ [G].
*   **Texel Layout:** Each texel at pixel coordinates $(i, j)$ stores a 32-bit value derived from the RGBA channels [S1, unofficial]. The bits are interpreted as a concatenated boolean vector where:
    *   Bit 0 corresponds to voxel depth $k=0$ [S1, unofficial].
    *   Bit 1 corresponds to voxel depth $k=1$ [S1, unofficial].
    *   Bit 31 corresponds to voxel depth $k=31$ [S1, unofficial].
    *   The $x$ and $y$ dimensions of the texture define the spatial extent of the voxel grid [S1, unofficial].

**Numbered Steps:**
1.  **Initialize** the slicemap texture with zeros [G].
2.  **Set Blending:** Configure the graphics pipeline to use a bitwise OR blending operation for the color attachment(s) [S1, unofficial].
3.  **Render Loop:** For each fragment generated by rasterizing the scene geometry:
    a.  Determine the fragment's depth $d$ in the voxelization coordinate system [G].
    b.  Map $d$ to a slice index $k$ (where $k$ is an integer representing the depth layer) [G].
    c.  Calculate the output color value $C$ such that only the $k$-th bit is set [S1, unofficial].
    d.  Output $C$ to the framebuffer [G].
4.  **Combine:** The hardware blending unit performs a bitwise OR between the new fragment value and the existing texel value, effectively setting the $k$-th bit to 1 if any fragment intersects that voxel column [S1, unofficial].

**Formulas:**
*   **Slice Index Mapping:** $k = \lfloor (d - z_{\text{near}}) / (z_{\text{far}} - z_{\text{near}}) \times 32 \rfloor$, clamped to $[0, 31]$ [G].
*   **Color Value:** $C = 2^k$ (assuming bit 0 is the least significant bit) [S1, unofficial].

**Parameters:**
*   **Blending Mode:** Bitwise OR. This is critical to combine all fragments projecting to the same pixel without overwriting previous bits [S1, unofficial].
*   **Slices per Pass:** Currently limited by hardware to 4 Multiple Render Targets (MRTs) $\times$ 4 channels $\times$ 32 bits = 128 slices per pass [S2, unofficial]. Future hardware with 32-bit logical operations would allow 512 slices per pass [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Watertightness:** The method requires the object to be watertight to obtain a filled voxel representation without iterative flood fill operations, which is necessary for applications like refraction [S2, unofficial].
*   **Depth Quantization:** Depth is quantized to discrete slices, unlike multi-pass methods (e.g., depth peeling) which have full precision [S1, unofficial].
*   **Hardware Limits:** The number of slices is limited by the number of MRTs and channels [S2, unofficial].
*   **Resolution Limits:** Unlike methods that fuse several views (which reduces cracks but limits resolution), slicemaps do not fuse views, avoiding resolution limits imposed by view fusion [S2, unofficial].

**Pseudocode:**
```python
def slicemap_voxelization(scene_geometry, z_near, z_far, width, height, num_slices=32):
    # Initialize slicemap texture with zeros
    slicemap = [[0] * width for _ in range(height)]
    
    # Simulate rasterization and fragment processing
    for fragment in scene_geometry:
        # 1. Determine depth in voxel space
        depth = fragment.depth
        
        # 2. Map depth to slice index k
        k = int((depth - z_near) / (z_far - z_near) * num_slices)
        k = max(0, min(k, num_slices - 1))
        
        # 3. Calculate output color value with only k-th bit set
        color_value = 1 << k
        
        # 4. Combine using bitwise OR (simulating hardware blending)
        x, y = fragment.screen_coords
        slicemap[y][x] |= color_value
        
    return slicemap
```

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of polygons, as it runs in a single pass [S2, unofficial].
*   **Memory Complexity:** $O(W \times H \times S)$ where $W, H$ are texture dimensions and $S$ is the number of slices (bits per texel). For a single texture, $S=32$ bits per texel [S1, unofficial].
*   **Performance:** Voxelization of millions of polygons can be performed in real-time (order of milliseconds) [S2, unofficial].
*   **Strengths:** Single-pass generation, no need to predefine the number of peeling steps, GPU-friendly, supports deformed grids (local refinement) [S1, S2, unofficial].
*   **Limitations:** Depth is quantized, requires watertight geometry for filled volumes, limited by hardware MRT/channel count [S1, S2, unofficial].
*   **When to Use:** Transmittance shadow maps, shadow volume culling/clamping, refraction/scattering effects [S2, unofficial].
*   **When Not to Use:** When full depth precision per slice is required, or when geometry is not watertight and flood fill is undesirable [S1, S2, unofficial].

## Background
Slicemaps were introduced by [S2, unofficial] as a GPU-friendly voxel representation of a scene. The technique builds upon earlier work in GPU boundary voxelization [S1, unofficial]. It was developed to enable real-time voxelization of complex and dynamic scenes containing more than 1M polygons, with creation and storage performed on the graphics card to avoid unnecessary data transfer [S2, unofficial]. The term "slicemap" was coined by [10] (cited in [S1, unofficial]) to refer to the texture where bits form slices of the 3D grid [S1, unofficial].
