# Simplified Parallel Voxelization

Also called: Bounding Box Corner Voxelization, Fixed-Point Parallel Voxelization

## Overview
Simplified Parallel Voxelization is a method for populating uniform voxel grids by voxelizing only the eight corner points of an object's bounding box [S1, unofficial]. It solves the problem of efficiently assigning objects to grid cells on hardware with limited local storage and high parallelism, such as the PlayStation 3 Cell Processor [S1, unofficial]. Unlike hierarchical methods or complex rasterization-based approaches, it assumes grid cells are larger than the objects being voxelized, ensuring no false negatives while eliminating the need for edge or face traversal [S1, unofficial]. This approach is inherently parallelizable across the eight corners and requires no looping to determine points to process [S1, unofficial].

## How it works
**Inputs:**
- A set of objects, each defined by an axis-aligned bounding box (AABB).
- A uniform voxel grid with a fixed cell size $C$.
- A global object registry where each object has a unique 2-byte index.

**Outputs:**
- A voxel grid where each cell contains a queue of object indices that intersect or reside within that cell.

**Data Structures:**
- **Voxel Grid:** A 3D array of voxels.
- **Voxel Queue:** Each voxel contains a fixed-size queue of 32 bytes. This queue holds up to 16 references (indices). Each reference is a 2-byte unsigned integer pointing to an object in the global registry [S1, unofficial].
- **Object Index:** A 2-byte identifier for each object [S1, unofficial].

**Parameters:**
- **Grid Cell Size ($C$):** Must be strictly larger than the maximum dimension of any object being voxelized [S1, unofficial]. This assumption ensures that if an object intersects a voxel, at least one of its bounding box corners will fall into that voxel, preventing false negatives [S1, unofficial]. Typical values depend on scene scale; in the source implementation, grid cells were sized to fit within 150KB of local storage [S1, unofficial].

**Algorithm Steps:**
1. For each object $O_i$ in the scene:
    a. Compute the axis-aligned bounding box (AABB) of $O_i$. Let the eight corner points be $P_1, P_2, \dots, P_8$.
    b. For each corner point $P_j$ ($j=1 \dots 8$):
        i. Determine the voxel coordinates $(x, y, z)$ that contain $P_j$. This is done by integer division of the point's world coordinates by the cell size $C$:
           $$ x = \lfloor P_{j,x} / C \rfloor, \quad y = \lfloor P_{j,y} / C \rfloor, \quad z = \lfloor P_{j,z} / C \rfloor $$
        ii. Identify the voxel queue $Q_{x,y,z}$ at these coordinates.
        iii. Push the object's 2-byte index $I_i$ onto $Q_{x,y,z}$.

**Push Operation Details:**
The push operation is designed for efficiency on SIMD hardware (e.g., SPEs on the Cell Processor) [S1, unofficial]. To push a 2-byte element $E$ onto a 32-byte queue $Q$:
1. Shift all 32 bytes of $Q$ left by 2 bytes (16 bits). This makes room at the front (lowest addresses) of the queue.
2. Write $E$ into the first two bytes of the shifted queue.
3. This operation requires 6 SIMD logical instructions [S1, unofficial].

**Idempotency and Parallelism:**
- The eight corner points are voxelized independently and in parallel [S1, unofficial].
- If multiple corner points fall into the same voxel, the same object index is pushed to the same queue multiple times. Due to the fixed-size queue logic and the nature of the push operation (shifting and overwriting), repeated pushes of the same value result in the same final queue state. This effectively deduplicates the object within the voxel without explicit checks [S1, unofficial].
- If all eight corners lie in different voxels, the object is added to eight different queues [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Object Size vs. Cell Size:** If an object is larger than the cell size, the assumption that corners define intersection fails, leading to false negatives [S1, unofficial]. The method is invalid in this case.
- **Queue Overflow:** The queue holds only 16 indices. If more than 16 objects intersect a voxel, older objects may be evicted. The source does not specify a replacement policy beyond the shift, implying a simple FIFO-like eviction where the oldest (last) element is dropped [S1, unofficial].
- **Precision:** Floating-point to integer conversion for voxel coordinates must be consistent to avoid jitter or missed voxels.

## Operating characteristics
- **Time Complexity:** $O(N)$ where $N$ is the number of objects. Each object requires constant time (8 corner voxelizations) regardless of scene complexity [S1, unofficial].
- **Memory Complexity:** $O(V)$ where $V$ is the number of voxels. Each voxel stores a fixed 32-byte queue [S1, unofficial].
- **Performance:** Highly efficient on SIMD architectures like the Cell SPU due to fixed-point operations and lack of branching/looping [S1, unofficial]. The push operation is optimized to 6 SIMD instructions [S1, unofficial].
- **Strengths:** Simple implementation, no looping, inherent parallelism, no false negatives (under size assumption) [S1, unofficial].
- **Limitations:** Only works for objects smaller than grid cells. Queue size is limited to 16 objects per voxel. No spatial coherence optimization beyond simple grid lookup [S1, unofficial].
- **When to use:** Scenes with many small objects, limited local storage, and hardware supporting SIMD parallelism (e.g., PlayStation 3 Cell) [S1, unofficial].
- **When not to use:** Scenes with large objects relative to grid cells, or when precise object-voxel intersection is required beyond corner containment [S1, unofficial].

## Background
This method was described in the context of implementing high-definition interactive animated ray tracing on the PlayStation 3's Cell Processor [S1, unofficial]. It was part of a solution for ray acceleration using Coherent Grid Traversal [S1, unofficial]. The design choices were driven by the constraints of the Cell SPE (Synergistic Processing Element), which has limited local storage (150KB) and benefits from fixed-size, loop-free operations [S1, unofficial]. The method is a simplification of more general voxelization techniques, trading accuracy for speed and parallelism under specific scene assumptions [S1, unofficial].
