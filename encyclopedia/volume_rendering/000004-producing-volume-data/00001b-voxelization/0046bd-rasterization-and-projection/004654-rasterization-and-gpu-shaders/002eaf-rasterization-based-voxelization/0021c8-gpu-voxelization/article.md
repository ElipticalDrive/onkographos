# GPU Voxelization
Also called: Basic GPU Voxelization, GPU Rasterization-based Voxelization, GPU Voxelization via GPU Rasterization, GPU Voxelization via Orthogonal Rasterization, GPU-based Voxelization, Voxelization using 3D Texture UAV, Voxelization via GPU Rasterization

## Overview
GPU Voxelization converts a triangle mesh into a regular voxel grid representation by leveraging the GPU's hardware rasterization pipeline [S3, S5, unofficial]. It maps each fragment generated by the rasterizer to a specific cell in the voxel grid and writes data into that cell, typically using a 3D texture bound as an Unordered Access View (UAV) or a Shader Storage Buffer Object (SSBO) [S1, S3, S5, unofficial]. Unlike CPU-based ray-tracing methods which are slow due to serial intersection tests, this method parallelizes the conversion across the GPU [S5, unofficial]. It distinguishes itself from its sibling [3D Grid Rasterization](903-3d-grid-rasterization.md) by using standard orthographic projection and viewport mapping rather than explicit 3D grid traversal, and from [GPU Voxelization via Compute Shaders](2549-gpu-voxelization-via-compute-shaders.md) by relying on the fixed-function rasterizer rather than manual thread dispatch [S1, S3, unofficial].

## How it works
**Inputs and Outputs:**
- **Input:** A triangle mesh (vertices, indices), voxel grid resolution ($W, H, D$), and voxel step size (edge length).
- **Output:** A voxel grid (3D texture or SSBO) marking occupied voxels, optionally with color or density data.

**Data Structures:**
1.  **Voxel Grid:** A 3D texture bound as a UAV [S3, unofficial] or a 1D SSBO `int cnts[]` of size $W \times H \times D$ [S5, unofficial].
2.  **Projection Matrices:**
    -   **Clip-space projection matrix:** Orthographic matrix mapping vertex positions to $[-1, 1]$ for width/height and $[0, 1]$ for depth (Device Normalized Coordinates) [S1, unofficial].
    -   **Voxel-space projection matrix:** Orthographic matrix mapping input coordinates to $[0, W]$ for width, $[0, H]$ for height, and $[0, D]$ for depth [S1, unofficial].
3.  **Camera:** Orthographic camera positioned outside the mesh's Axis-Aligned Bounding Box (AABB) along the projection axis, with a frustum slightly larger than the AABB range (e.g., $1.2 \times$ range) [S5, unofficial].

**Steps:**

1.  **Compute AABB:** Iterate over all mesh vertices to find min/max $x, y, z$ coordinates to determine the mesh's AABB [S5, unofficial].
2.  **Calculate Resolution:** Determine voxel grid resolution based on the AABB range and a fixed step size (voxel edge length):
    $$ \text{Resolution} = \lfloor \text{Range} / \text{step} \rfloor + 1 $$
    where Range is the extent of the AABB along each axis [S5, unofficial].
3.  **Setup Render Target:**
    -   Allocate a 3D texture bound as a UAV [S3, unofficial] or an SSBO of size $W \times H \times D$ initialized to 0 [S5, unofficial].
    -   Disable depth testing and back-face culling to ensure all triangles are processed regardless of orientation or depth [S3, S5, unofficial].
4.  **Transform Vertices:** In the Vertex Shader, transform vertex positions into the voxel grid coordinate system (or clip space for rasterization) [S3, S5, unofficial].
5.  **Rasterize:** Rasterize the transformed primitives using a viewport matching the dimensions of the voxel grid's 2D projection ($W \times H$) [S1, S3, unofficial]. The orthogonal viewport frustum covers the voxel grid exactly, such that rasterized pixel position/depth correspond to the $X, Y, Z$ components of the voxel grid [S3, unofficial].
6.  **Write Voxels (Fragment Shader):**
    -   Map each rasterized fragment to one or more voxels.
    -   Calculate the voxel index from the fragment's world position or rasterized coordinates.
    -   Write data (e.g., increment a counter or set a flag) to the voxel grid using atomic operations to handle concurrent writes [S2, S5, unofficial].

**Formulas:**

*   **Voxel Index Calculation (Fragment Shader):**
    Given fragment world position $FragPos$, box minimum $boxMin$, step size $step$, and resolution $resolution$:
    $$ x = \lfloor (FragPos.x - boxMin.x) / step \rfloor $$
    $$ y = \lfloor (FragPos.y - boxMin.y) / step \rfloor $$
    $$ z = \lfloor (FragPos.z - boxMin.z) / step \rfloor $$
    $$ index = y \times (resolution.z \times resolution.x) + z \times resolution.x + x $$
    [S5, unofficial]

*   **Homogeneous Coordinates (Voxel Space):**
    After applying the voxel-space projection matrix, divide the $x, y, z$ components of the resulting position vector by its $w$-component to map to voxel cell coordinates [S1, unofficial].

**Pseudocode:**

> **Unverified code.** The code below did not pass a test run against a reference implementation, or no test fits it, so it may contain errors.

```python
# Vertex Shader
def vertex_shader(position):
    # Transform to clip space using orthographic projection
    # Maps to [-1, 1] for x/y, [0, 1] for z
    clip_pos = clip_space_projection_matrix * vec4(position, 1.0)
    return clip_pos

# Fragment Shader (SSBO approach)
def fragment_shader(clip_pos, frag_world_pos):
    # Calculate voxel coordinates from world position
    x = floor((frag_world_pos.x - boxMin.x) / step)
    y = floor((frag_world_pos.y - boxMin.y) / step)
    z = floor((frag_world_pos.z - boxMin.z) / step)
    
    # Calculate linear index in SSBO
    index = y * (resolution.z * resolution.x) + z * resolution.x + x
    
    # Atomically increment the voxel counter
    atomic_add(ssbo[index], 1)

# Fragment Shader (3D Texture UAV approach with Conservative Rasterization)
def fragment_shader_uav(clip_pos, prim_min, prim_max):
    # SV_Position.xy are pixel coordinates, SV_Position.z is depth
    # Map to voxel coordinates
    voxel_pos_f = vec3(clip_pos.xy, clip_pos.z * resolution.z)
    voxel_min = voxel_pos_f - 0.5
    voxel_max = voxel_pos_f + 0.5
    
    # AABB Test: Check if voxel AABB intersects primitive AABB
    # If no intersection, discard
    if ((prim_max.x - voxel_min.x) * (prim_min.x - voxel_max.x) >= 0.0 or
        (prim_max.y - voxel_min.y) * (prim_min.y - voxel_max.y) >= 0.0 or
        (prim_max.z - voxel_min.z) * (prim_min.z - voxel_max.z) >= 0.0):
        discard
    
    # Edge-Voxel Condition Test (simplified check for XY plane)
    # Calculate edge vectors in voxel space
    e0 = vox_pos[1] - vox_pos[0]
    e1 = vox_pos[2] - vox_pos[1]
    e2 = vox_pos[0] - vox_pos[2]
    
    # Calculate signed distances and check if primitive intersects voxel
    # (Full implementation requires checking all 3 axes as per [S3, unofficial])
    if not edge_voxel_test(e0, e1, e2, voxel_min, voxel_max):
        discard
        
    # Write to 3D Texture UAV
    write_to_3d_texture(voxel_pos_f, color_data)
```

**Parameters:**
-   **Step:** Voxel edge length. Typical value depends on scene scale [S5, unofficial].
-   **Viewport:** Must be aligned with a face of the voxel grid and have dimensions matching one of the 2D projections of the voxel grid [S3, unofficial].
-   **Scene Normalization Matrix:** Scales the scene to fit in a $1 \times 1 \times 1$ cube centered at the origin, then translates it [S2, unofficial].

**Edge Cases and Pitfalls:**
-   **Cracks:** Occur when the depth gradient of the primitive exceeds 1.0 (calculated via `ddx(depth)` and `ddy(depth)` in the pixel shader). This happens when triangles are parallel to the projection plane, projecting to lines/zero area [S3, S5, unofficial].
-   **Holes:** Changing projection directions per primitive can cause gaps where no primitive covers a pixel center [S3, unofficial].
-   **Extra Voxels:** Manual conservative rasterization (edge expansion) shades extra pixels not covered by the primitive, leading to unnecessary pixel shader calls and incorrect voxels [S3, unofficial].

## Subtopics

### [VoxelPipe](2797-voxelpipe.md)
VoxelPipe is a highly flexible, programmable software pipeline for triangle voxelization implemented in CUDA. It solves the problem of converting triangle meshes into voxel grids with support for fully conservative and thin voxelizations, arbitrary render targets (boolean, floating-point, vector), and user-defined shaders. It distinguishes itself from prior binary voxelizers by supporting arbitrary framebuffer types and programmability via vertex and fragment shaders, tackling load balancing via a tile-based algorithm instead of assigning individual triangles to single threads with global memory atomics, and optimizing the triangle/box overlap test.

### [Conservative Rasterization](2936-conservative-rasterization.md)
Conservative rasterization is a technique used during voxelization to prevent artifacts where small triangles (smaller than the voxel grid resolution) are ignored completely, resulting in holes in the voxelized mesh. It ensures that all voxels potentially intersected by a triangle are covered by rasterization. Two primary implementations exist: **Geometric Dilatation**, which explicitly enlarges triangles in clip space within the geometry shader, and **MSAA Approximation**, which leverages Multi-Sample Anti-Aliasing to invoke the pixel shader if any subsample is covered, approximating conservative behavior without explicit edge expansion. The MSAA approach is often preferred for its simplicity and lack of redundant voxels compared to edge extension.

### Multi-View Voxelization with Normal-Based Selection
An extension of single-view voxelization that uses three orthographic cameras (along X, Y, Z axes) and selects the best view for each triangle based on its normal vector to prevent cracks caused by degenerate projections [S5, unofficial]. It creates three orthographic cameras looking along the negative X, negative Y, and negative Z axes, positioned outside the AABB [S5, unofficial]. In the Geometry Shader, it computes the triangle face normal using the cross product of two edge vectors derived from input vertices [S5, unofficial]. It selects the camera index by comparing the absolute values of the normal's components: $n_{DX} = |n_x|, n_{DY} = |n_y|, n_{DZ} = |n_z|$. Selection is based on $\text{argmax}(n_{DX}, n_{DY}, n_{DZ})$ [S5, unofficial]. The triangle vertices are then transformed using the selected View-Projection matrix and emitted [S5, unofficial].

## Operating characteristics
-   **Time Complexity:** $O(N \cdot F)$, where $N$ is the number of triangles and $F$ is the number of fragments generated per triangle. The rasterization hardware handles the complexity of fragment generation.
-   **Memory Complexity:** $O(W \cdot H \cdot D)$ for the voxel grid storage [S5, unofficial].
-   **Performance:** Extremely fast due to parallelization on the GPU, leveraging existing rasterization hardware [S5, unofficial]. However, it can be memory-intensive for high-resolution grids [S5, unofficial].
-   **Strengths:** High speed, simplicity of implementation using standard graphics APIs, parallel processing [S5, unofficial].
-   **Limitations:** Prone to cracks and holes if not handled with conservative rasterization or multi-view techniques [S3, S5, unofficial]. Single projection direction causes cracks when triangles are parallel to the projection plane [S5, unofficial]. Manual conservative rasterization can produce extra voxels [S3, unofficial].
-   **When to use:** When real-time or near-real-time voxelization of triangle meshes is required, and the hardware supports the necessary features (e.g., UAVs, MSAA, or conservative rasterization) [S3, S5, unofficial].
-   **When not to use:** When exact geometric accuracy is critical and hardware conservative rasterization is unavailable, or when memory bandwidth is a severe bottleneck for very high-resolution grids [S3, S5, unofficial].

## Background
GPU Voxelization was popularized by Michael Schwarz and NVIDIA, leveraging the GPU's rasterization pipeline to convert triangle meshes into voxel grids [S1, unofficial]. It emerged as a solution to the inefficiency of CPU-based ray-tracing voxelization methods, which required serial intersection tests for every voxel [S5, unofficial]. The method is widely used in real-time global illumination techniques like Voxel Cone Tracing [S4, unofficial] and in physics simulations such as Position Based Dynamics [S5, unofficial].
