# Hierarchical Binary-Scene Voxelization

Also called: GPU-based Hierarchical Voxelization, Real-Time Hierarchical Binary-Scene Voxelization

## Overview
Hierarchical Binary-Scene Voxelization is a robust, real-time method for computing a multi-resolution binary volumetric representation (octree) of a scene directly on the GPU [S1]. It solves the problem of generating voxel data for fully dynamic scenes by rasterizing geometry from three orthogonal directions and unioning the results, thereby eliminating the boundary holes inherent in single-direction rasterization methods like Eisemann and D´ecoret [S1]. Unlike sibling methods that may require pre-processing or specific primitive types, this approach handles any hardware-supported rasterizable geometry in a single geometry submission pass, leveraging 32-bit integer textures and bitwise operations for high performance [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A set of rasterizable geometric primitives (triangles, points, etc.) and a defined world-space bounding box for the voxel grid.
*   **Output:** A mipmapped 32-bit integer RGBA texture representing a hierarchical binary octree. The base level stores the binary voxel occupancy; higher mip-levels store the aggregated occupancy of child voxels.

**Data Structures:**
The core data structure is a single mipmapped 32-bit integer RGBA texture attached to a Frame Buffer Object (FBO) [S1].
*   **Base Resolution:** The width ($w$) and height ($h$) of the texture correspond to the viewport dimensions. The depth ($d$) is determined by the number of Multiple Render Targets (MRTs) and channels.
*   **Voxel Encoding:** Each pixel (texel) in the RGBA texture stores 32 bits of voxel data, representing a column of 32 voxels along the Z-axis [S1]. One bit corresponds to one voxel in the column.
*   **Depth Extension:** By using $N$ MRTs, the total depth resolution becomes $32 \times N$ [S1]. For example, 8 MRTs provide a depth of 1024 cells [S1].
*   **Hierarchy:** Each mip-level $L$ corresponds to an octree depth level. A texel at level $L$ represents a $2 \times 2$ block of texels from level $L-1$ in the X-Y plane. The value of a texel at level $L$ is the bitwise OR of its four parent texels from level $L-1$ [S1].

**Parameters:**
*   **Grid Resolution:** Defined by viewport width $w$, height $h$, and depth discretization. A typical example is a $128^3$ grid [S1].
*   **Texture Format:** 32-bit integer RGBA [S1].
*   **Projection:** Orthographic camera projection is required to ensure non-deformed voxelization [S1].
*   **Rendering State:** Face culling is disabled. Z-test is disabled. No Z-buffer is attached to the FBO [S1].

**Algorithm Steps:**

1.  **Geometry Transformation (Geometry Shader):**
    The input geometry is processed by a Geometry Shader. The geometry is transformed and emitted three times, corresponding to three viewing directions: $-X$, $-Y$, and $-Z$ [S1]. These three transformed versions are rendered into three layers of a layered texture (or separate MRTs) in a single draw call to avoid multiple geometry submissions and reduce bandwidth [S1].

2.  **Fragment Program Execution (Per Direction):**
    For each fragment generated by the rasterization of the transformed geometry, the following logic is executed in the Fragment Program:
    
    a. **World Space Z Calculation:**
       Compute the world space Z coordinate ($fPosW.z$) of the fragment. This is done by transforming the fragment position using the viewport-to-world matrix [S1].
       
    b. **Grid Index Calculation:**
       Map the world space Z coordinate to the grid's discrete Z-index.
       Let $minZ$ and $maxZ$ be the grid boundaries.
       Let $gridParams.z$ be the scaling factor $\frac{31}{maxZ - minZ}$ (assuming 32 cells, indices 0-31).
       $$ index_{local} = (fPosW.z - minZ) \times gridParams.z $$
       [S1]
       
    c. **Channel and Bit Selection:**
       Determine which color channel (Red, Green, Blue, Alpha) and which bit within that channel corresponds to $index_{local}$.
       The channels represent ranges of 32 bits:
       - Red: indices 0-31
       - Green: indices 32-63
       - Blue: indices 64-95
       - Alpha: indices 96-127
       
       Let $channel\_offset$ be 0, 32, 64, or 96 based on the range containing $index_{local}$.
       Let $bit\_index = index_{local} - channel\_offset$.
       [S1]
       
    d. **Mask Generation:**
       Create a 32-bit mask with a single bit set at $bit\_index$.
       $$ mask = 1 \ll bit\_index $$
       [S1]
       
    e. **Framebuffer Update:**
       Perform a bitwise OR between the generated $mask$ and the existing content of the framebuffer pixel. This is achieved using the GPU's logical operation support for 32-bit integers [S1].

3.  **Union of Directions (GPGPU Pass):**
    After rendering the geometry from the three directions ($-X$, $-Y$, $-Z$), a GPGPU pass (or subsequent rendering pass) unions the three resulting grids into a final grid texture [S1]. This step ensures that voxels intersected by surfaces with slopes close to the grid axes are correctly filled, preventing holes [S1].

4.  **Hierarchical Octree Generation (Mipmapping):**
    The hierarchical structure is generated using standard GPU mipmapping operations.
    For each mip-level $L > 0$:
    $$ Texel(L, x, y, z) = Texel(L-1, 2x, 2y, z) \lor Texel(L-1, 2x+1, 2y, z) \lor Texel(L-1, 2x, 2y+1, z) \lor Texel(L-1, 2x+1, 2y+1, z) $$
    where $\lor$ denotes the bitwise OR operation [S1].
    This process aggregates the binary occupancy from the finest level up to the root. The Z-resolution remains constant across all mip-levels in this basic representation, though Z-direction mip-reduction is possible by ORing groups of bits within a texel [S1].

**Pseudocode:**

```python
# Fragment Program Logic (simplified for one direction)
# Inputs: fPosW (world space position of fragment), gridParams (minZ, scaleZ)
# Output: oCol (32-bit integer mask)

def voxelize_fragment(fPosW, gridParams):
    # 1. Compute world space Z
    # Assuming vtw[2] is the Z-row of the viewport-to-world matrix
    # and fPos.w is 1.0
    world_z = dot(vtw[2], [fPosW.x, fPosW.y, fPosW.z, 1.0])
    
    # 2. Compute local grid index in Z
    # gridParams.y = minZ
    # gridParams.z = 31.0 / (maxZ - minZ)
    local_z = (world_z - gridParams.y) * gridParams.z
    
    # 3. Determine channel offset and bit index
    # Channels: R=0-31, G=32-63, B=64-95, A=96-127
    # We need to find which 32-bit block local_z falls into
    
    # Check bounds to avoid out-of-bounds access
    if local_z < 0 or local_z >= 128:
        return 0
        
    # Determine channel offset
    if local_z < 32:
        channel_offset = 0
    elif local_z < 64:
        channel_offset = 32
    elif local_z < 96:
        channel_offset = 64
    else:
        channel_offset = 96
        
    # Compute bit index within the channel
    bit_index = local_z - channel_offset
    
    # 4. Generate mask
    # Shift 1 left by bit_index
    mask = 1 << bit_index
    
    return mask

# Main Voxelization Process
def hierarchical_voxelization(geometry, grid_bounds, viewport_size):
    # Setup FBO with 32-bit integer RGBA texture and MRTs if needed
    # Disable face culling and Z-test
    # Attach orthographic projection matrix
    
    # Step 1: Render from -X, -Y, -Z directions using Geometry Shader
    # The geometry shader transforms vertices to face each direction
    # and outputs them to layered texture layers
    
    for direction in [-X, -Y, -Z]:
        set_camera_view(direction, grid_bounds, viewport_size)
        draw_geometry(geometry, voxelize_fragment)
        
    # Step 2: Union the three grids
    # If rendered to separate MRTs/layers, perform a GPGPU pass to OR them
    final_grid = union_grids(grid_neg_x, grid_neg_y, grid_neg_z)
    
    # Step 3: Generate Mipmaps
    # Use GPU hardware mipmap generation with bitwise OR filter
    # This creates the hierarchical octree structure
    hierarchical_grid = generate_mipmaps(final_grid, filter_mode=BITWISE_OR)
    
    return hierarchical_grid
```

**Edge Cases and Pitfalls:**
*   **Holes in Boundary Representation:** Single-direction rasterization (e.g., only $-Z$) creates holes where surface slopes are close to the grid's Z-axis. This method avoids this by rasterizing from three orthogonal directions and unioning the results [S1].
*   **Precision:** The method relies on 32-bit integer arithmetic. Ensure the fragment program correctly handles the mapping from floating-point world coordinates to integer grid indices to avoid off-by-one errors [S1].
*   **Depth Range:** The grid depth is limited by the number of MRTs and channels. For depths exceeding 1024 (8 MRTs $\times$ 4 channels), texture tiling must be used, which adds complexity to the coordinate mapping [S1].

## Operating characteristics
*   **Time Complexity:** The voxelization is a hardware rasterization process, making it highly efficient. Performance is largely independent of the fragment processing complexity, as the bottleneck is the fixed-function rasterizer [S1].
*   **Memory Complexity:** Memory usage is proportional to the grid resolution. A $512^3$ grid requires 16 MB (using 4 MRTs) [S1]. The theoretical maximum with 8 MRTs and tiling is a $4096^3$ grid (8 GB) [S1].
*   **Measured Performance:** On a G80 GPU, for a $128^3$ grid:
    *   Knot model: 2.5 ms
    *   Tree model: 17.5 ms
    *   Spheres model: 1.5 ms
    *   Disabling fragment processing yields similar times, confirming the fixed-function bottleneck [S1].
*   **Strengths:**
    *   Robustness: No holes in the voxel representation [S1].
    *   Speed: Real-time performance (milliseconds) [S1].
    *   Simplicity: No pre-processing of geometry required; works with any rasterizable primitive [S1].
    *   Dynamic Scenes: Suitable for fully dynamic, animated, or deformed scenes [S1].
*   **Limitations:**
    *   Requires GPU support for 32-bit integer textures, geometry shaders, and logical operations (specifically noted for G80 architecture, but applicable to modern GPUs) [S1].
    *   Orthographic projection is required for non-deformed voxelization [S1].
*   **When to Use:** Ideal for visibility computations, hierarchical collision detection, and CSG operations in dynamic scenes where speed and robustness are critical [S1].
*   **When Not to Use:** When perspective projection is strictly required without distortion correction, or when the hardware does not support the necessary 32-bit integer texture features.

## Background
The method was introduced by Forest et al. in 2009 [S1]. It builds upon earlier work by Eisemann and D´ecoret (2006) and Zhao et al. (Dong et al., 2004) [S1]. Eisemann and D´ecoret used a single slice map which suffered from holes, while Zhao et al. required pre-processing and was limited to triangles [S1]. This method leverages the advanced functionalities of the NVIDIA G80 GPU, such as geometry shaders and 32-bit integer formats, to achieve a robust, single-pass voxelization [S1]. It is particularly well-suited for applications like constructive solid geometry (CSG), shape repair, and collision detection [S1].
