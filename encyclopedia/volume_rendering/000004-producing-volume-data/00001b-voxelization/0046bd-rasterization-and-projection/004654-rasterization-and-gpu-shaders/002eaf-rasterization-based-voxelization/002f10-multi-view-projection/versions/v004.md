# Multi-view projection

Also called: Multi-axis rasterization, 3-pass voxelization

## Overview
Multi-view projection voxelization converts a triangle mesh into a voxel grid by rasterizing the geometry from multiple orthogonal viewpoints (typically along the X, Y, and Z axes) to ensure complete coverage and prevent cracks [S1, unofficial]. It distinguishes itself from single-view methods by using redundant projections to fill gaps caused by occlusion or thin geometry, and from direct 3D texture rasterization by often employing intermediate 2D buffers to bypass hardware limitations on direct 3D writes [S2, unofficial].

## Shared principles
All methods in this family share the core mechanism of decomposing 3D occupancy into a series of 2D rasterization problems. The shared mathematical principle is the projection of 3D vertices into 2D screen space for each view axis, followed by the mapping of rasterized fragments back to 3D voxel coordinates.

1.  **Orthographic Projection:** The camera is set to an orthographic projection to preserve parallel lines and ensure uniform scaling across the volume. The frustum bounds are typically expanded slightly (e.g., $1.02\times$ the scene range) to ensure all geometry is captured [S1, unofficial].
2.  **Voxel Space Mapping:** A transformation matrix maps world-space coordinates to discrete voxel indices. This matrix scales the scene bounding box to the target voxel resolution $(V_x, V_y, V_z)$ and translates the bounding box minimum to the origin [S1, unofficial].
3.  **Atomic Writes or Blending:** When multiple fragments map to the same voxel (from different triangles or different views), the method must resolve conflicts. Common approaches include:
    *   **Atomic Operations:** Using hardware atomic add or atomic max to increment an occupancy counter or material ID in a 3D texture or compute buffer [S1, unofficial].
    *   **Blending:** In sheet-buffer approaches, fragments are blended into 2D textures before transcoding to the final 3D representation [S2, unofficial].
4.  **Axis Coverage:** To guarantee 6-connectivity or prevent cracks, the union of voxels generated from all view axes is taken. A voxel is occupied if it is hit by *any* of the projections [S1, unofficial].

## Subtopics

### [Single 2D Projection Voxelization](3482-single-2d-projection-voxelization.md)
*   **What it is:** A method that produces 6-separating voxelization using only one 2D projection along the dominant axis of a triangle's normal vector.
*   **Distinction:** Unlike [Orthographic Multi-View Voxelization](3892-orthographic-multi-view-voxelization.md) which requires three passes, this method relies on the fact that for pixels where the projected triangle contains the pixel center, the dominant axis projection is sufficient to determine the unique voxel, while edge cases are handled by testing crosshair segments perpendicular to the projection axis.
*   **When to choose:** Use when computational cost is critical and the geometry is sufficiently thick or aligned such that single-axis projection covers the majority of voxels, accepting potential edge artifacts or requiring specific edge tests.
*   **Link:** [Single 2D Projection Voxelization](3482-single-2d-projection-voxelization.md)

### [Orthographic Multi-View Voxelization](3892-orthographic-multi-view-voxelization.md)
*   **What it is:** Converts 3D triangle meshes into a volumetric representation by rasterizing geometry along three principal axes (X, Y, Z) using orthographic cameras.
*   **Distinction:** It distinguishes itself from direct 3D texture rasterization by using intermediate 2D "sheet buffers" that are transcoded into a compact 2D "worksheet" texture, avoiding the need for hardware support for direct 3D texture writes. This method solves the problem of generating voxel data for volume rendering or cone tracing while maintaining high performance on standard consumer graphics hardware.
*   **When to choose:** Use when targeting hardware that lacks efficient direct 3D texture write support or when memory bandwidth optimization via 2D sheet buffers is required.
*   **Link:** [Orthographic Multi-View Voxelization](3892-orthographic-multi-view-voxelization.md)

### [Volumetric Representation via Depth Map Registration](6435-volumetric-representation-via-depth-map-registration.md)
*   **What it is:** Constructs a 3D volume from multi-view images by registering estimated depth maps into a voxel grid, specifically handling non-Lambertian reflections through per-view cost minimization rather than global thresholds.
*   **Distinction:** It represents scene geometry as a sparse voxel cloud where voxel values indicate the count of views mapping to that location, distinguishing itself from sibling methods by explicitly refining the volume shape iteratively to remove scattering voxels and smooth sharp corners for improved coding gain.
*   **When to choose:** Use when input data consists of multi-view images with depth estimates rather than a triangle mesh, and when iterative refinement for coding efficiency is prioritized over raw speed.
*   **Link:** [Volumetric Representation via Depth Map Registration](6435-volumetric-representation-via-depth-map-registration.md)

### 3-Pass Voxelization
*   **Definition:** A voxelization approach that fixes cracks and missing data in the voxel grid by voxelizing the scene from each of the 3 major axes, requiring 3 render passes [S1, unofficial].
*   **Steps:**
    1.  For each of the 3 major axes, multiply the clip-space projection matrix by a rotation matrix corresponding to that axis to generate fragments from that view-axis [S1, unofficial].
    2.  Use the voxel-space projection matrix without multiplying it by the rotation matrix, as it already maps all values properly [S1, unofficial].
*   **Pitfalls:**
    *   Requires 3 render calls per rendered object, which becomes expensive as models become more complex [S1, unofficial].
    *   If optimizing by separating dynamic and static objects, the voxel grid of dynamic objects must be cleared every frame, requiring separate voxel grids for dynamic and static objects [S1, unofficial].
*   **Link:** N/A (Minor variant)

## Background
The concept of multi-view voxelization originated in the context of real-time ray-traced global illumination, where efficient voxelization of triangle meshes was required for radiance caching and cone tracing. The specific "3-pass voxelization" technique was documented in *Real-Time Ray Traced Voxel Global Illumination* (2026), which highlighted the issue of cracks in single-axis voxelization and proposed the 3-axis solution as a simple, effective fix [S1, unofficial]. The sheet-buffer approach was developed to address hardware limitations regarding direct 3D texture writes on consumer GPUs, allowing for efficient voxelization on standard graphics pipelines [S2, unofficial].
