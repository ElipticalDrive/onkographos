# 3-Pass Voxelization

Also called: 3-Axis Voxelization, 3D Mesh Voxelization via Axis-Aligned Rasterization, Multi-View Voxelization

## Overview
3-Pass Voxelization is a rasterization-based technique that eliminates geometric cracks and missing data in the voxel grid by rendering the scene from three orthogonal directions (along the X, Y, and Z axes) [S1, S2, unofficial]. Unlike single-view projection methods which suffer from occlusion gaps and perspective distortion, this method ensures complete volumetric coverage by aggregating fragments from all three principal axes [S2, unofficial]. It is chosen when high-fidelity occupancy is required for static or semi-static geometry, accepting the cost of three draw calls per object [S1, unofficial].

## How it works
**Inputs:**
- Triangle mesh geometry (vertices, normals, attributes).
- Scene Axis-Aligned Bounding Box (AABB) defined by $bb_{min}$ and $bb_{max}$.
- Target voxel grid resolution $R = (R_x, R_y, R_z)$.
- Voxel grid data structure (e.g., 3D texture or atomic buffer).

**Outputs:**
- A populated 3D voxel grid where occupied voxels indicate the presence of geometry.

**Data Structures:**
- **Voxel Grid:** A 3D array or texture of size $R_x \times R_y \times R_z$. Each voxel stores occupancy (bit/bool) or attributes (floats).
- **Projection Matrices:**
  - $M_{clip}$: Standard clip-space projection matrix (orthographic).
  - $M_{voxel}$: A matrix mapping clip-space coordinates directly to voxel indices. As noted in [S1, unofficial], this matrix already handles the scaling and offset required for voxel indexing and does *not* require rotation multiplication.
  - $R_x, R_y, R_z$: Rotation matrices aligning the camera with the respective axes.

**Parameters:**
- **Frustum Expansion:** The orthographic frustum should be expanded slightly (e.g., factor 1.02 or fixed offset) to ensure corners of the AABB are covered [Parent].
- **Depth Testing:** Disabled or configured for write-through to capture all intersecting fragments, not just the nearest surface [Parent].

**Steps:**
1. **Coordinate System Setup:** Place the coordinate system at the center of the voxel grid, ensuring axes are parallel to the grid edges [S2, unofficial].
2. **Pass 1 (Axis 1):**
   - Construct the view matrix for the first axis (e.g., +Z).
   - Multiply $M_{clip}$ by the rotation matrix for this axis to generate fragments [S1, unofficial].
   - Render the scene into a 2D buffer or directly into the voxel grid layer corresponding to this view.
3. **Pass 2 (Axis 2):**
   - Construct the view matrix for the second axis (e.g., +X).
   - Multiply $M_{clip}$ by the rotation matrix for this axis [S1, unofficial].
   - Render the scene.
4. **Pass 3 (Axis 3):**
   - Construct the view matrix for the third axis (e.g., +Y).
   - Multiply $M_{clip}$ by the rotation matrix for this axis [S1, unofficial].
   - Render the scene.
5. **Aggregation:**
   - For each voxel hit by any of the three passes, mark it as occupied. This is typically an atomic "OR" operation for occupancy [Parent, G].

**Pseudocode:**
```python
def voxelize_3_pass(mesh, bb_min, bb_max, resolution, voxel_grid):
    """
    Voxelize a mesh using 3 orthogonal passes.
    """
    # Define rotation matrices for X, Y, Z axes
    # Note: Exact rotation matrices depend on coordinate system handedness.
    # Assuming standard right-handed system where views look along -Z, -X, -Y respectively.
    rot_x = rotation_matrix(axis='x', angle=0) # View along X
    rot_y = rotation_matrix(axis='y', angle=0) # View along Y
    rot_z = rotation_matrix(axis='z', angle=0) # View along Z

    # Pre-calculate voxel-space matrix (maps clip space to voxel indices)
    # This matrix includes scale and offset based on bb_min, bb_max, and resolution.
    # It does NOT include rotation [S1, unofficial].
    m_voxel = compute_voxel_matrix(bb_min, bb_max, resolution)

    # List of rotations for the 3 passes
    rotations = [rot_x, rot_y, rot_z]

    for rot in rotations:
        # Multiply clip-space projection matrix by rotation to align view
        # The rotation ensures fragments are generated from this specific axis
        m_view_proj = rot @ m_voxel # Or appropriate matrix multiplication order
        
        # Render scene with this view matrix
        # Depth testing disabled to capture all intersections
        render_scene(mesh, m_view_proj, voxel_grid, depth_test=False)

    # Aggregation is handled during render via atomic OR or direct write
    # If using separate buffers, merge them here:
    # voxel_grid = voxel_grid | buffer_x | buffer_y | buffer_z
```

**Edge Cases and Pitfalls:**
- **Performance:** Requires 3 render calls per object. Cost grows with mesh complexity [S1, unofficial].
- **Dynamic Objects:** If separating dynamic and static objects, dynamic voxel grids must be cleared every frame, requiring separate grids [S1, unofficial].
- **Precision:** Ensure the voxel-space matrix correctly handles the coordinate mapping to avoid off-by-one errors at boundaries [Parent].

## Operating characteristics
- **Time Complexity:** $O(N \cdot P)$, where $N$ is the number of triangles and $P=3$ is the number of passes. Each pass is a standard rasterization operation.
- **Memory Complexity:** $O(R_x \cdot R_y \cdot R_z)$ for the voxel grid. No additional large buffers if rendering directly to the grid.
- **Performance:** Slower than single-pass methods due to 3x draw calls. Suitable for static or infrequently updated geometry. Can be optimized by LOD interleaving or resolution scaling [S1, unofficial].
- **Strengths:** Eliminates cracks and gaps inherent in single-view projection; robust against orientation.
- **Limitations:** High computational cost for complex dynamic scenes; requires separate handling for dynamic/static splits.

## Background
3-Pass Voxelization was introduced as a solution to the "cracks and missing data" problem in single-direction voxelization [S1, unofficial]. It is a foundational technique in real-time ray-traced voxel global illumination pipelines, where accurate occupancy is critical for light transport [S1, unofficial]. The method is widely used in GPU-based voxelizers where multiple render targets or atomic operations are available.
