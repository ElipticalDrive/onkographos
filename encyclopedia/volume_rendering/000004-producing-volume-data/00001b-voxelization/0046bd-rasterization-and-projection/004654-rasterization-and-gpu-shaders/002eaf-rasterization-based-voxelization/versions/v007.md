# Rasterization-based Voxelization

Also called: Cube Mesh Generation, Hash-based Surface Voxelization, Sparse Voxelization with PositionMap Hashing, Voxelizing a Triangle Mesh, madcad Voxelization

## Overview
Rasterization-based Voxelization converts a continuous triangle mesh into a discrete volumetric representation by projecting the mesh geometry onto a 3D grid using rasterization techniques [S1][S3, S4, unofficial]. It solves the problem of generating a voxelized surface (shell) or point cloud from polygonal input without performing complex surface reconstruction or interior filling [S1][S2, S3, unofficial]. It differs from [VoxelGrid from Mesh (Fill Method)](1013-voxelgrid-from-mesh-fill-method.md) by focusing exclusively on surface intersection rather than volumetric filling, and from [Conservative Voxelization](3247-conservative-voxelization.md) by often relying on standard rasterization logic with precision parameters to mitigate holes, rather than hardware-specific conservative rasterization extensions [S2, S4, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A triangle mesh defined by vertices $V$ and faces $F$ (indices), a voxel size $vs = (vs_x, vs_y, vs_z)$, an origin $origin$ (typically $[0,0,0]$), and a precision factor $p$ [S1][S2, S4, unofficial].
*   **Output:** Either a sparse set of occupied voxel coordinates (integer indices $ijk$), a point cloud with per-voxel attributes, or a cube mesh where each occupied voxel is represented by a 3D cube [S1][S4, unofficial].

**Data Structures:**
The method typically employs a sparse hash table to store occupied voxels, avoiding the memory overhead of dense 3D arrays [S3, S4, unofficial].
*   **Hash Table:** Maps voxel center coordinates to a unique key. In C implementations, this is often a linked-list based hash table [S4, unofficial]. In Python, a `set` of coordinate tuples serves as the hash table [S3, unofficial].
*   **Voxel Data:** Stores the position (center) and optionally color/normal attributes for each occupied voxel [S4, unofficial].
*   **Output Mesh Layout (Cube Generation):** If generating a cube mesh, the output structure `vx_mesh_t` contains:
    *   `vertices`: Array of size $N_{voxels} \times 8$, storing the 8 corners of each cube.
    *   `normals`: Array of size 6, storing predefined face normals for the 6 faces of a cube.
    *   `colors`: Array of size $N_{voxels} \times 8$ (or NULL).
    *   `indices`: Array of size $N_{voxels} \times VOXELIZER\_INDICES\_SIZE$ (typically 36 for 6 faces $\times$ 2 triangles).
    *   `normalindices`: Array of size $N_{voxels} \times VOXELIZER\_INDICES\_SIZE$ [S4, unofficial].

**Steps:**
1.  **Initialization:** Define the voxel size $vs$ and compute the half-voxel size $hvs = vs \times 0.5$ [S4, unofficial].
2.  **Rasterization/Intersection:** Iterate through each triangle face in the input mesh. Determine which voxel grid cells intersect with the triangle.
    *   *Hash-based approach:* Use a `PositionMap` hasher to map triangle points to voxel grid keys and update the voxel set [S3, unofficial].
    *   *C Library approach:* Call an internal rasterizer (e.g., `vx__voxelize`) that clips triangles against voxel boundaries and inserts occupied voxel data into a hash table [S4, unofficial].
3.  **Deduplication:** The hash table automatically handles deduplication; if multiple triangles intersect the same voxel, it is stored only once [S3, S4, unofficial].
4.  **Geometry Generation (Optional):** If a cube mesh is required:
    *   Allocate output arrays based on the number of unique voxels $N_{voxels}$ [S4, unofficial].
    *   Define the 8 corner offsets for a cube centered at the origin using $hvs$:
        $$
        \begin{aligned}
        &(-hvs_x, hvs_y, hvs_z), (-hvs_x, -hvs_y, hvs_z), (hvs_x, -hvs_y, hvs_z), (hvs_x, hvs_y, hvs_z), \\
        &(-hvs_x, hvs_y, -hvs_z), (-hvs_x, -hvs_y, -hvs_z), (hvs_x, -hvs_y, -hvs_z), (hvs_x, hvs_y, -hvs_z)
        \end{aligned}
        $$
    *   For each occupied voxel, translate these offsets by the voxel's center position and populate the `vertices` array [S4, unofficial].
    *   Copy predefined normals and indices to the respective arrays [S4, unofficial].
5.  **Cleanup:** Free the temporary hash table and return the result [S4, unofficial].

**Pseudocode (Python-like):**
```python
def rasterization_based_voxelization(mesh_vertices, mesh_faces, voxel_size, origin, precision=0.01):
    """
    Voxelize a triangle mesh into a set of occupied voxel coordinates.
    mesh_vertices: List of [x, y, z] coordinates.
    mesh_faces: List of [i, j, k] vertex indices.
    voxel_size: Tuple (sx, sy, sz).
    origin: Tuple (ox, oy, oz).
    precision: Float tolerance for intersection.
    Returns: Set of (i, j, k) voxel indices.
    """
    occupied_voxels = set()
    
    # Compute half voxel size for boundary checks
    hvs = (voxel_size[0] * 0.5, voxel_size[1] * 0.5, voxel_size[2] * 0.5)
    
    for face in mesh_faces:
        # Get triangle vertices
        v0 = mesh_vertices[face[0]]
        v1 = mesh_vertices[face[1]]
        v2 = mesh_vertices[face[2]]
        
        # Determine bounding box of the triangle in world space
        min_x = min(v0[0], v1[0], v2[0])
        max_x = max(v0[0], v1[0], v2[0])
        min_y = min(v0[1], v1[1], v2[1])
        max_y = max(v0[1], v1[1], v2[1])
        min_z = min(v0[2], v1[2], v2[2])
        max_z = max(v0[2], v1[2], v2[2])
        
        # Map world bounds to voxel grid bounds
        start_i = floor((min_x - origin[0]) / voxel_size[0])
        end_i = floor((max_x - origin[0]) / voxel_size[0])
        start_j = floor((min_y - origin[1]) / voxel_size[1])
        end_j = floor((max_y - origin[1]) / voxel_size[1])
        start_k = floor((min_z - origin[2]) / voxel_size[2])
        end_k = floor((max_z - origin[2]) / voxel_size[2])
        
        # Iterate over candidate voxels
        for i in range(start_i, end_i + 1):
            for j in range(start_j, end_j + 1):
                for k in range(start_k, end_k + 1):
                    # Calculate voxel center in world space
                    center_x = origin[0] + (i + 0.5) * voxel_size[0]
                    center_y = origin[1] + (j + 0.5) * voxel_size[1]
                    center_z = origin[2] + (k + 0.5) * voxel_size[2]
                    
                    # Check if voxel center is inside triangle (or use more robust intersection test)
                    # Note: Simple center-point test may leave holes; precision parameter 
                    # in C libs often adjusts the rasterization bounds to mitigate this [S2, unofficial].
                    if point_in_triangle([center_x, center_y, center_z], v0, v1, v2, precision):
                        occupied_voxels.add((i, j, k))
                        
    return occupied_voxels

def point_in_triangle(p, v0, v1, v2, precision):
    """
    Simple barycentric coordinate check. 
    In practice, libraries use more robust geometric tests or rasterization logic [S4, unofficial].
    """
    # Vector from v0 to p, v1, v2
    v0v1 = [v1[k] - v0[k] for k in range(3)]
    v0v2 = [v2[k] - v0[k] for k in range(3)]
    v0p = [p[k] - v0[k] for k in range(3)]
    
    dot00 = sum(a*b for a,b in zip(v0v1, v0v1))
    dot01 = sum(a*b for a,b in zip(v0v1, v0v2))
    dot02 = sum(a*b for a,b in zip(v0v1, v0p))
    dot11 = sum(a*b for a,b in zip(v0v2, v0v2))
    dot12 = sum(a*b for a,b in zip(v0v2, v0p))
    
    inv_denom = 1 / (dot00 * dot11 - dot01 * dot01)
    u = (dot11 * dot02 - dot01 * dot12) * inv_denom
    v = (dot00 * dot12 - dot01 * dot02) * inv_denom
    
    # Allow small tolerance for precision
    return (u >= -precision) and (v >= -precision) and (u + v <= 1 + precision)
```

**Parameters:**
*   `voxel_size`: Physical dimensions of a voxel. Typical values: 0.75, 0.5, 0.2, 0.1 units [S2, unofficial]. In Point Cloud Utils, a common value is $1/256.0$ [S1].
*   `origin`: The world coordinate of the $(0,0,0)$ voxel corner. Typically $[0,0,0]$ [S1].
*   `precision`: A tolerance factor to reduce "holes" artifacts caused by standard rasterization covering only pixel centers [S2, unofficial]. Typical value: $0.01$ [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Holes:** Standard rasterization only covers pixels/voxels whose centers lie inside the triangle, leading to cracks at edges [S6, unofficial]. Precision parameters or conservative rasterization are used to mitigate this [S2, S6, unofficial].
*   **Performance:** The output mesh size scales significantly with voxel density. A torus mesh (441 vertices, 800 faces) can result in 61,312 vertices and 91,968 faces at voxel size 0.75, or 144,968 vertices at size 0.5 [S2, unofficial].
*   **Sparse vs Dense:** Using a hash table/set is more memory-efficient for sparse meshes than a dense 3D boolean array [S3, unofficial].

## Subtopics

### [3D Grid Rasterization](903-3d-grid-rasterization.md)
3D Grid Rasterization is a CPU-based algorithm that determines which voxels in a fixed-resolution 3D grid are intersected by a triangle mesh, producing a binary occupancy grid or a grid with interpolated colors. It solves the problem of converting continuous polygonal geometry into a discrete volumetric representation without performing surface reconstruction (such as QEF or dual vertex solving). It differs from full o-voxel implementations by omitting the face QEF, boundary QEF, and dual vertex solve steps, focusing solely on the intersect scanline to find occupied voxels. It differs from GPU-based siblings like [GPU Volume Kernel Voxelization](1496-gpu-volume-kernel-voxelization.md) by relying on CPU-side scanline filling and hash-table deduplication rather than parallel fragment shaders.

### [GPU Volume Kernel Voxelization](1496-gpu-volume-kernel-voxelization.md)
GPU Volume Kernel Voxelization is a technique that accelerates the voxelization of triangle meshes by parallelizing the iteration over the 2D XY plane of the voxel grid using a GPU compute shader. It solves the performance bottleneck of CPU-based voxelization, where nested loops over X and Y coordinates are executed sequentially. Unlike rasterization-based alternatives that project geometry into 3D textures, this method retains the explicit triangle-voxel intersection logic of CPU implementations but distributes the workload across GPU threads, achieving significant speedups (e.g., 50x) for high-resolution grids.

### [Implicit Surface Voxelization](2379-implicit-surface-voxelization.md)
Implicit Surface Voxelization converts a mathematical implicit surface definition into a discrete voxel grid by rasterizing 2D rectangles within a Region of Interest (ROI) and evaluating the implicit function in the pixel shader. It differs from triangle-based rasterization methods (e.g., [Rasterization-based Voxelization](908-rasterization-based-voxelization.md)) by operating directly on analytical functions rather than polygonal approximations, allowing for the handling of complex, non-polygonal geometry.

### [GPU Voxelization via Compute Shaders](2549-gpu-voxelization-via-compute-shaders.md)
GPU Voxelization via Compute Shaders converts 3D triangle meshes into a uniform 3D voxel grid by leveraging GPU parallel processing. It solves the problem of generating volumetric data for real-time ray marching or volume rendering with high throughput. Unlike [Rasterization-based Voxelization](908-rasterization-based-voxelization.md), which projects triangles via the fixed-function graphics pipeline, compute shader methods decouple intersection logic from rasterization, allowing custom geometric tests and atomic operations on 3D buffers or textures.

### [GPU Voxelization](2633-gpu-voxelization.md)
GPU Voxelization converts a triangle mesh into a regular voxel grid by leveraging the GPU's hardware rasterization pipeline to map fragments directly to 3D grid cells. It solves the performance bottleneck of CPU-based ray-tracing voxelization by parallelizing the intersection test across the rasterizer. It differs from [3D Grid Rasterization](903-3d-grid-rasterization.md) by using a 3D texture UAV or SSBO as the direct write target rather than a 2D accumulation buffer, and from [GPU Volume Kernel Voxelization](1496-gpu-volume-kernel-voxelization.md) by relying on standard triangle rasterization rather than volume kernels.

### [CPU Mesh Voxelization](3137-cpu-mesh-voxelization.md)
CPU Mesh Voxelization converts a triangle mesh into a 3D grid of voxels by iterating over the bounding box of each triangle and testing each voxel center against the triangle's plane and edge constraints. It differs from its parent [Rasterization-based Voxelization](908-rasterization-based-voxelization.md) by explicitly rasterizing triangles into a hash table of voxel centers and colors, then generating a cube mesh for each occupied voxel, whereas CPU Mesh Voxelization typically outputs a binary occupancy grid or bit-packed table. It differs from [3D Grid Rasterization](903-3d-grid-rasterization.md) by using exact geometric overlap tests (SAT or plane/projection) rather than simple grid cell intersection, and from [Voxelization via Triangle Scattering](3779-voxelization-via-triangle-scattering.md) by iterating cells against triangles rather than scattering triangles into cells.

### [Voxel Rasterization](3204-voxel-rasterization.md)
Voxel Rasterization converts a triangle mesh into a voxelized representation by rendering the geometry into a 3D voxel buffer, supporting both simple occupancy and normal/color mapping. It differs from its sibling [3D Grid Rasterization](903-3d-grid-rasterization.md) by explicitly iterating over triangle surfaces to calculate interpolated points and normals rather than relying on a pure grid traversal, and from [GPU Volume Kernel Voxelization](1496-gpu-volume-kernel-voxelization.md) by utilizing a Direct3D 11-based rendering pipeline or CUDA kernels for the rasterization step.

### [Conservative Rasterization via Triangle Expansion](3531-conservative-rasterization-via-triangle-expansion.md)
This method eliminates voxelization holes caused by standard rasterization, which only covers pixels whose centers lie inside a triangle, by expanding the triangle in clip space and culling the expanded area in the fragment shader. It differs from sibling methods like [Conservative Voxelization](3247-conservative-voxelization.md) by implementing the expansion logic manually in the geometry shader using homogeneous plane mathematics, rather than relying on hardware-specific conservative rasterization extensions or post-processing hole-filling.

### [Multi-view projection](5937-multi-view-projection.md)
Multi-view projection is a family of rasterization-based voxelization techniques that convert triangle meshes into voxel grids by rendering scene geometry from multiple distinct camera viewpoints. The core problem it solves is ensuring topological correctness (specifically 6-separation or tunnel-freedom) and complete coverage of the volume, which single-view methods often fail to achieve due to perspective distortion or degenerate alignments. It sets itself apart from single-view methods by requiring multiple passes (typically 2, 3, or 6) to guarantee that every voxel intersected by a triangle is covered by at least one view, provided the views are sufficiently separated [Parent].

### [Position Map and Image-Space Transfer](6237-position-map-and-image-space-transfer.md)
This family of techniques converts 3D geometric data into voxel grids by projecting or transferring information into 2D image space (textures) before reconstructing the 3D volume. Unlike direct 3D rasterization, these methods leverage the GPU's fixed-function rasterizer or image load/store operations on 2D textures to determine voxel occupancy, often trading memory bandwidth for computational simplicity. They are distinguished from direct triangle rasterization by operating on pre-computed surface samples or 2D texture slices, ensuring connectivity or enabling real-time performance insensitive to scene complexity.

### Rasterization-based Volume Modeling
The process of building volume data voxel-by-voxel, considered the third layer in the voxel modeling abstraction hierarchy [S5, unofficial]. It solves the problem of assigning density values to voxels based on primitive contributions. It differs from instantiation-based modeling by pulling values into a voxel (similar to raytracing), whereas instantiation-based modeling pushes values into voxels (similar to micropolygon rendering) [S5, unofficial]. The main rasterization loop iterates over voxels in the discrete bounding box, transforms voxel position to world space, samples the primitive, and adds the value to the buffer if positive [S5, unofficial].

### Single-Pass Voxelization
A voxelization approach that utilizes the geometry shader to reduce draw calls by selecting the axis from which each triangle has the largest overall projection for fragment generation [S6, unofficial]. It employs conservative rasterization to generate fragments as long as there is something inside the pixel, not only if its center is covered [S6, unofficial]. It uses an MSAA render target during the voxelization process to solve the issue of incorrectly filling empty cells caused by excessive fragment generation from conservative rasterization [S6, unofficial]. Hardware support for conservative rasterization is available on Nvidia Maxwell architecture and later; RTX driver support is available for Turing and Pascal architecture GPUs [S6, unofficial]. A pitfall is that GPUs only generate fragments if a pixel's center is covered by a triangle, leading to small cracks at the edges of triangles, and conservative rasterization can incorrectly fill cells that should be empty [S6, unofficial].

## Operating characteristics
*   **Time Complexity:** Depends on the number of triangles $N_t$ and the number of voxels $N_v$ intersected. For hash-based methods, insertion is $O(1)$ on average, but bounding box iteration can be costly for large triangles.
*   **Memory Complexity:** $O(N_v)$ for sparse storage. Significantly more memory-efficient than dense grids for sparse meshes [S3, unofficial].
*   **Performance:** GPU-based variants offer significant speedups (e.g., 50x) for high-resolution grids compared to CPU implementations [S1].
*   **Strengths:** Simple to implement; generates explicit cube meshes or point clouds suitable for further processing; handles sparse data well [S1][S3, S4, unofficial].
*   **Limitations:** Output mesh size can be very large compared to input (e.g., 100x increase in vertices) [S2, unofficial]. Standard rasterization may leave holes without precision adjustments or conservative rasterization [S2, S6, unofficial].
*   **When to use:** When an explicit surface representation (cube mesh) or point cloud is needed from a triangle mesh, especially for sparse data or when integrating with existing rasterization pipelines [S1][S4, unofficial].
*   **When not to use:** When deep volumetric filling (interior voxels) is required, or when memory bandwidth is extremely constrained and dense grids are not feasible [S2, S3, unofficial].

## Background
Rasterization-based voxelization is a fundamental technique in computer graphics for converting polygonal models into volumetric data. It is widely used in voxel art generation, real-time ray tracing, and volume rendering pipelines [S1][S2, S5, S6, unofficial]. The method leverages the efficiency of hardware rasterization or CPU-based scanline algorithms to determine surface occupancy [S1][S3, S4, unofficial]. Libraries such as Point-Cloud-Utils and the C-based voxelizer library provide efficient implementations for generating cube meshes and point clouds [S1][S2, S4, unofficial]. The technique has evolved to include GPU acceleration via compute shaders and geometry shaders to handle real-time requirements [S1][S6, unofficial].
