# Rasterization-based Voxelization

Also called: Cube Mesh Generation, Hash-based Surface Voxelization, Sparse Voxelization with PositionMap Hashing, Voxelizing a Triangle Mesh, madcad Voxelization

## Overview
Rasterization-based Voxelization converts a triangle mesh into a discrete volumetric representation by projecting the geometry onto a 3D grid using hardware rasterization or hash-based spatial mapping [S1][S3, S4, unofficial]. It solves the problem of generating surface-only (shell) voxel data for real-time rendering or volume modeling without performing expensive ray-tracing or deep interior filling [S2, S5, unofficial]. It differs from [3D Grid Rasterization](903-3d-grid-rasterization.md) by often utilizing sparse hash structures or direct 3D texture writes rather than accumulating 2D projections, and from [GPU Volume Kernel Voxelization](1496-gpu-volume-kernel-voxelization.md) by leveraging the fragment pipeline or geometric hashing rather than explicit CPU-like intersection loops on the GPU [S1][S3, unofficial].

## How it works
The method typically follows one of two primary implementation patterns: a C-library based hash-table approach that generates a cube mesh, or a Python-based sparse set approach. Both rely on rasterizing triangle surfaces to determine occupied voxel coordinates.

### Inputs and Outputs
*   **Input**: A triangle mesh defined by vertices $V$ and faces $F$ (indices).
*   **Parameters**:
    *   `vox_size`: Voxel dimensions $(v_x, v_y, v_z)$ [S4, unofficial]. Typical values: $0.75, 0.5, 0.2, 0.1$ units [S2, unofficial]. In Point-Cloud-Utils, often $1.0/256.0$ [S1].
    *   `vox_origin`: The world-space coordinate of the $(0,0,0)$ voxel corner. Typical: $[0,0,0]$ [S1].
    *   `precision`: A tolerance factor to reduce "holes" artifacts. Typical: $0.01f$ [S2, unofficial].
    *   `gap_fraction`: Spacing between generated cubes. Typical: $0.02$ [S1].
*   **Output**:
    *   **Sparse Grid**: A set of integer voxel coordinates $(i,j,k)$ [S1][S3, unofficial].
    *   **Cube Mesh**: A new mesh where each occupied voxel is represented by a cube (8 vertices, 36 indices) [S4, unofficial].
    *   **Point Cloud**: A set of points at voxel centers with optional colors [S4, unofficial].

### Data Structures
1.  **Hash Table (Sparse Storage)**: Used to store occupied voxels to avoid dense 3D arrays.
    *   **Key**: Voxel center coordinates or integer grid indices.
    *   **Value**: `vx_voxel_data_t` containing `position` (world space) and `color` [S4, unofficial].
    *   **Implementation**: Linked list buckets in a fixed-size array [S4, unofficial].
2.  **Output Mesh (`vx_mesh_t`)**:
    *   `vertices`: Array of size $N_{voxels} \times 8$ [S4, unofficial].
    *   `normals`: Array of size 6 (predefined for cube faces) [S4, unofficial].
    *   `colors`: Array of size $N_{voxels} \times 8$ (optional) [S4, unofficial].
    *   `indices`: Array of size $N_{voxels} \times 36$ (assuming 6 faces per cube) [S4, unofficial].
    *   `nvertices`, `nindices`: Current counts [S4, unofficial].

### Algorithm Steps (Hash-Based Cube Mesh Generation)
This procedure implements the logic found in the `voxelizer` library [S4, unofficial].

1.  **Initialization**:
    *   Define half-voxel size: $hvs = vs \times 0.5$.
    *   Allocate an empty hash table `table` and counter `nvoxels = 0`.

2.  **Rasterization / Intersection**:
    *   For each face $f$ in the input mesh:
        *   Determine the bounding box of the triangle in voxel space.
        *   Iterate through all integer voxel coordinates $(i,j,k)$ within this bounding box.
        *   For each voxel, calculate the center position $C_{voxel}$ in world space.
        *   Perform a geometric test (e.g., ray-triangle intersection or point-in-triangle check with tolerance `precision`) to determine if the triangle intersects the voxel column or covers the voxel center.
        *   *Note*: The source notes describe this as "rasterizing triangles into voxel locations" [S4, unofficial]. In GPU implementations, this is done via fragment shaders writing to 3D textures or position maps [S1][S3, unofficial]. In CPU hash implementations, it involves explicit intersection tests [S4, unofficial].

3.  **Hash Insertion**:
    *   If the voxel is occupied:
        *   Compute hash key: $h = \text{hash}(C_{voxel})$.
        *   Insert $(C_{voxel}, \text{color})$ into `table` at index $h$.
        *   Increment `nvoxels`.

4.  **Mesh Generation**:
    *   Allocate output mesh arrays:
        *   `vertices`: size $nvoxels \times 8$.
        *   `indices`: size $nvoxels \times 36$.
        *   `normals`: size 6 (copy predefined cube normals).
    *   Define cube corner offsets relative to center using $hvs$:
        $$
        \begin{aligned}
        &(-hvs.x, hvs.y, hvs.z), (-hvs.x, -hvs.y, hvs.z), (hvs.x, -hvs.y, hvs.z), (hvs.x, hvs.y, hvs.z), \\
        &(-hvs.x, hvs.y, -hvs.z), (-hvs.x, -hvs.y, -hvs.z), (hvs.x, -hvs.y, -hvs.z), (hvs.x, hvs.y, -hvs.z)
        \end{aligned}
        $$
    *   Iterate through `table` buckets. For each occupied node:
        *   Extract `position` and `color`.
        *   Add 8 vertices to `outmesh->vertices` using the offsets and `position`.
        *   Add 36 indices to `outmesh->indices` referencing the new vertices.
        *   If colors exist, copy `color` to the corresponding vertex colors.

5.  **Cleanup**:
    *   Free the hash table.
    *   Return `outmesh`.

    for face in mesh.faces:

        min_i = floor(min(v0.x, v1.x, v2.x) / voxel_size[0])

### Edge Cases and Pitfalls
*   **Holes**: Standard rasterization only covers pixels/voxels whose centers lie inside the triangle, leading to cracks [S6, unofficial]. Use `precision` parameters or conservative rasterization to mitigate [S2, S6, unofficial].
*   **Overfilling**: Conservative rasterization or large precision values may incorrectly fill empty cells [S6, unofficial].
*   **Memory**: The output mesh size scales with voxel density. A torus (441 verts, 800 faces) with voxel size 0.75 results in 61,312 vertices and 91,968 faces [S2, unofficial].
*   **Sparse vs Dense**: Using a hash set or sparse structure is critical for memory efficiency on sparse meshes, avoiding 3D boolean arrays [S3, S4, unofficial].

## Subtopics

### [3D Grid Rasterization](903-3d-grid-rasterization.md)
Converts a triangle mesh into a discrete 3D occupancy grid by projecting onto three orthogonal planes (XY, YZ, XZ) using hardware rasterization and combining results. It differs from CPU-based bounding-box methods by leveraging GPU fragment shaders and from full surface reconstruction by outputting only binary presence. Choose when a dense or sparse occupancy grid is needed rather than a mesh. Link: [3D Grid Rasterization](903-3d-grid-rasterization.md).

### [GPU Volume Kernel Voxelization](1496-gpu-volume-kernel-voxelization.md)
Accelerates voxelization by parallelizing the iteration over the 2D XY plane of the voxel grid using a GPU compute shader. It retains explicit triangle-voxel intersection logic but distributes it across GPU threads, achieving significant speedups (e.g., 50x) for high-resolution grids. Choose when CPU-based nested loops are the bottleneck and explicit intersection logic is preferred over rasterization artifacts. Link: [GPU Volume Kernel Voxelization](1496-gpu-volume-kernel-voxelization.md).

### [GPU Voxelization via Compute Shaders](2549-gpu-voxelization-via-compute-shaders.md)
Converts 3D triangle meshes into a uniform 3D voxel grid by leveraging GPU parallel processing. Unlike rasterization-based methods that use the fixed-function pipeline, this decouples intersection logic from rasterization, allowing custom geometric tests and atomic operations on 3D buffers. Choose when custom intersection logic or atomic writes to 3D textures are required. Link: [GPU Voxelization via Compute Shaders](2549-gpu-voxelization-via-compute-shaders.md).

### [GPU Voxelization](2633-gpu-voxelization.md)
Converts a triangle mesh into a regular voxel grid by leveraging the GPU's hardware rasterization pipeline to map fragments directly to 3D grid cells. It differs from 3D Grid Rasterization by writing directly to a 3D texture UAV or SSBO instead of a 2D accumulation buffer. Choose for high-performance direct-to-volume rendering pipelines. Link: [GPU Voxelization](2633-gpu-voxelization.md).

### [CPU Mesh Voxelization](3137-cpu-mesh-voxelization.md)
Converts a triangle mesh into a 3D grid by iterating over the bounding box of each triangle and testing each voxel center against the triangle's plane and edge constraints. It differs from Rasterization-based Voxelization by outputting a binary occupancy grid or bit-packed table rather than generating a cube mesh per occupied voxel. Choose for simple, dependency-free implementations where GPU is unavailable. Link: [CPU Mesh Voxelization](3137-cpu-mesh-voxelization.md).

### [Voxel Rasterization](3204-voxel-rasterization.md)
Converts a triangle mesh into a voxelized representation by rasterizing triangles directly into a 3D voxel grid. It focuses on algorithmic steps like iterating over triangle surfaces and interpolating normals/colors, often leveraging GPU acceleration. Unlike 3D Grid Rasterization, it explicitly samples along triangle edges and spans. Choose when per-voxel attributes (normals, colors) are needed. Link: [Voxel Rasterization](3204-voxel-rasterization.md).

### [Conservative Voxelization](3247-conservative-voxelization.md)
A hardware-accelerated algorithm that guarantees conservative correctness: every voxel intersecting the input model is correctly recognized. It differs from standard rasterization-based voxelization by computing the exact depth range of the intersection between the triangle and the voxel column, rather than using a single depth value. Choose when avoiding holes is critical. Link: [Conservative Voxelization](3247-conservative-voxelization.md).

### [Conservative Rasterization via Triangle Expansion](3531-conservative-rasterization-via-triangle-expansion.md)
Eliminates voxelization holes by expanding the triangle in clip space and culling the expanded area in the fragment shader. It differs from Conservative Voxelization by implementing the expansion logic manually in the geometry shader using homogeneous plane mathematics, rather than relying on hardware-specific extensions. Choose when hardware conservative rasterization is unavailable. Link: [Conservative Rasterization via Triangle Expansion](3531-conservative-rasterization-via-triangle-expansion.md).

### [Multi-view projection](5937-multi-view-projection.md)
Generates a volumetric representation by rasterizing the geometry from multiple distinct viewpoints, typically aligned with the principal axes. It solves occlusion and grazing-angle artifacts inherent in single-view projection methods by ensuring every surface element is visible from at least one viewpoint. Choose when single-view methods produce "shadow" voxels. Link: [Multi-view projection](5937-multi-view-projection.md).

### [Position Map and Image-Space Transfer](6237-position-map-and-image-space-transfer.md)
Decouples surface intersection from volume grid population by using intermediate 2D image textures (position maps) to store world-space surface coordinates. It solves the problem of efficiently mapping continuous geometric surfaces to discrete voxel grids by leveraging the GPU's rasterization pipeline to compute visibility and position. Choose when decoupling rasterization from volume writing is beneficial. Link: [Position Map and Image-Space Transfer](6237-position-map-and-image-space-transfer.md).

### Rasterization-based Volume Modeling
The process of building volume data voxel-by-voxel, considered the third layer in the voxel modeling abstraction hierarchy [S5, unofficial]. It instancing primitives, bounding them, and sampling their density function at each overlapping voxel [S5, unofficial]. It pulls values into a voxel (similar to raytracing), whereas instantiation-based modeling pushes values into voxels [S5, unofficial]. Choose when generating density fields from primitives rather than surface meshes [S5, unofficial]. Link: [Rasterization-based Volume Modeling](908-rasterization-based-voxelization.md#rasterization-based-volume-modeling).

### Single-Pass Voxelization
Utilizes the geometry shader to reduce draw calls by selecting the axis from which each triangle has the largest overall projection for fragment generation [S6, unofficial]. It employs conservative rasterization and MSAA render targets to solve cracks and overfilling issues [S6, unofficial]. Choose for single-pass geometry shader implementations on modern GPUs (Maxwell+) [S6, unofficial]. Link: [Single-Pass Voxelization](908-rasterization-based-voxelization.md#single-pass-voxelization).

## Operating characteristics
*   **Time Complexity**: Depends on the number of triangles $N_t$ and the number of voxels $N_v$ in the bounding box. For hash-based methods, it is $O(N_t \cdot B)$ where $B$ is the average number of voxels per triangle bounding box [S4, unofficial]. For GPU rasterization, it is proportional to the number of fragments generated [S1].
*   **Memory Complexity**: $O(N_v)$ for the hash table or output mesh [S4, unofficial]. Sparse storage avoids $O(N_x N_y N_z)$ for large empty volumes [S3, unofficial].
*   **Measured Performance**: For a torus (441 vertices, 800 faces), voxel size 0.75 results in 61,312 vertices and 91,968 faces [S2, unofficial]. Voxel size 0.5 results in 144,968 vertices and 217,452 faces [S2, unofficial].
*   **Strengths**: Fast on GPU; leverages existing rasterization hardware; sparse storage is memory efficient for thin surfaces [S3, S4, unofficial].
*   **Limitations**: Output mesh size can be very large compared to input [S2, unofficial]; prone to holes without conservative rasterization [S6, unofficial]; overfilling with conservative methods [S6, unofficial].
*   **When to Use**: Real-time voxel art, surface-only volume rendering, sparse voxel octrees generation [S2, S4, unofficial].
*   **When Not to Use**: When deep interior filling is required (use [CPU Mesh Voxelization](3137-cpu-mesh-voxelization.md) with flood fill or ray casting) [S2, unofficial]; when exact geometric intersection without rasterization artifacts is critical without conservative extensions [S6, unofficial].

## Background
Rasterization-based voxelization originated from the need to convert polygonal models into voxel data for volume rendering and voxel art. The Point-Cloud-Utils library popularized a Python/C interface for this task [S1]. The `voxelizer` library provided a header-only C implementation using hash tables for sparse storage [S4, unofficial]. The technique is widely used in real-time graphics for generating voxelized meshes from triangle inputs, often as a preprocessing step for ray marching or global illumination [S2, S5, unofficial]. Conservative rasterization extensions in modern GPUs (Nvidia Maxwell+) have further refined the quality of these methods [S6, unofficial].
