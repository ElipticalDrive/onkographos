# Porous Voxelization

Also called: Random Voxel Dropping

## Overview
Porous Voxelization is a technique that generates porous or sponge-like volumetric structures by selectively discarding voxels during the voxelization process based on a deterministic spatial hash of their coordinates [S1, unofficial]. Unlike standard voxelization methods which retain all computed surface or solid voxels, this method introduces controlled porosity while maintaining the spatial distribution properties of the original geometry [S1, unofficial]. It is distinct from procedural noise-based porosity as it relies on a simple, coordinate-dependent hash function for deterministic results across different runs [S1, unofficial].

## How it works
**Inputs and Outputs**
- **Input**: A mesh or point cloud to be voxelized, a target resolution (implied by the parent method [Voxelization](12-voxelization.md)), and a `porosity` parameter.
- **Output**: A voxel grid where a subset of voxels, determined by the porosity parameter, has been removed.

**Data Structures**
The method operates on the voxel coordinates $(x, y, z)$ generated by the parent voxelization algorithm. No additional complex data structures are required beyond the standard voxel grid and the scalar `porosity` parameter.

**Parameters**
- `porosity`: `Option<f64>`
  - If `None`, no voxels are dropped (standard voxelization).
  - If `Some(p)`, where $p \in [0.0, 1.0]$, voxels are kept only if their computed hash value $h \ge p$.
  - Typical values: $0.0$ (no porosity) to $1.0$ (maximum porosity, though effectively $1.0$ keeps no voxels if the condition is strictly $\ge$). A value of $0.5$ retains approximately 50% of the voxels [S1, unofficial].

**Algorithm Steps**
1. For each voxel $(x, y, z)$ identified as part of the surface or solid volume by the parent voxelization method:
2. Compute a spatial hash value $h$ using the voxel coordinates. The hash is derived from a fractional sine-based function:
   $$ h = | \text{fract}( (\mathbf{d} \cdot \mathbf{v}) \times 43758.5453 ) | $$
   Where:
   - $\mathbf{d}$ is a vector derived from the voxel coordinates $(x, y, z)$. The source notes mention `dot.sin()`, implying a dot product is taken before the sine operation. A common implementation for such spatial hashes uses a fixed vector $\mathbf{v}$ (e.g., $(12.9898, 78.233, 45.164)$) or simply the coordinates themselves if treated as a dot product with a unit vector, but the source explicitly states `dot` is derived from coordinates. Given the formula structure `(dot.sin() * ...).fract().abs()`, it implies a scalar input to sine. Let us define $\mathbf{d} = (x, y, z)$ and assume a standard spatial hash vector $\mathbf{v}$ is used, or that `dot` refers to a specific linear combination. However, the source code snippet `dot.sin()` suggests `dot` is a scalar. A robust interpretation of `dot` in this context, given the variable name, is likely a dot product of the coordinate vector with a constant vector, or simply the coordinates themselves if the language treats them as a single entity for the dot product (unlikely). Let us assume the standard "fractional sine" hash where a scalar $s$ is computed from coordinates. The source says `let hash = (dot.sin() * 43758.5453).fract().abs();`. To be precise, we define a scalar $s$ derived from $(x,y,z)$. A common pattern is $s = x \cdot 12.9898 + y \cdot 78.233 + z \cdot 45.164$. The source does not specify the vector $\mathbf{v}$ for the dot product, only that `dot` is derived from coordinates. We will define $s$ as a linear combination of coordinates.
   - $\text{fract}(x) = x - \lfloor x \rfloor$
   - $43758.5453$ is a constant multiplier.
   - $|\cdot|$ is the absolute value.
3. If `porosity` is `Some(p)`:
   - If $h \ge p$, keep the voxel.
   - If $h < p$, discard the voxel.
4. If `porosity` is `None`, keep the voxel.

**Edge Cases and Pitfalls**
- **Invalid Porosity Values**: The library API does not validate `porosity` values outside the range $[0.0, 1.0]$ or `NaN` when called directly.
  - `porosity = Some(1.5)`: Since $h \in [0, 1]$, $h \ge 1.5$ is always false. All voxels are dropped [S1, unofficial].
  - `porosity = Some(-0.5)` or `NaN`: The condition $h \ge -0.5$ is always true (for -0.5), or undefined (for NaN, typically resulting in false or skipping, effectively disabling dropping). This leads to misleading results where no porosity is applied [S1, unofficial].
- **Precision**: The hash function uses floating-point arithmetic. Precision issues are minimal due to the fract operation, but consistent results depend on the exact floating-point behavior of the sine and multiplication operations.

## Operating characteristics
- **Time Complexity**: $O(1)$ per voxel, as the hash computation is a constant-time arithmetic operation.
- **Memory Complexity**: $O(1)$ additional memory per voxel, as no extra data structures are stored.
- **Performance**: The method adds a small constant overhead to the voxelization process. The test case shows that setting `porosity = 0.5` significantly reduces the number of generated voxels [S1, unofficial].
- **Strengths**: Simple to implement, deterministic, and effective for creating porous structures without complex noise functions.
- **Limitations**: The porosity is uniform and random-like, not physically based. Invalid inputs can lead to silent failures.

## Background
Porous Voxelization was implemented in the `voxelizer-rs` project (lhemerly/voxer-rs) as part of Pull Request #179, added to the `MeshProcessor::voxelize` method and CLI interface [S1, unofficial]. It was introduced to allow for the generation of sponge-like meshes by randomly discarding voxels based on a stable, fractional sine-based spatial hash [S1, unofficial].
