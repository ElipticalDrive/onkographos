# Point-in-Box Inclusion Test via Sorted Indices and Bisect

Also called: Efficient Voxel Query via Sorted Indices and Bisect, Range Query via Binary Search on Sorted Coordinates

## Overview
This method performs point-in-box inclusion tests by pre-sorting point cloud coordinates along each axis and using binary search to determine occupancy. It solves the problem of efficiently querying which points lie within an orthogonal bounding box by reducing the search space to $O(\log N)$ per axis. It differs from its parent, [Point-in-Box Inclusion Test](1400-point-in-box-inclusion-test.md), by explicitly leveraging sorted index arrays and bisect operations to handle range queries, rather than generic partitioning logic.

## How it works
**Inputs and Outputs:**
- Input: A set of $N$ 3D points $P = \{p_1, \dots, p_N\}$ where $p_i = (x_i, y_i, z_i)$, and a query box defined by $[x_{min}, x_{max}] \times [y_{min}, y_{max}] \times [z_{min}, z_{max}]$.
- Output: A subset of points $P_{in} \subseteq P$ such that $p_i \in P_{in}$ if and only if $x_{min} \le x_i \le x_{max}$, $y_{min} \le y_i \le y_{max}$, and $z_{min} \le z_i \le z_{max}$.

**Data Structures:**
Three sorted arrays of coordinates are maintained:
- `sorted_x_pc`: Array of $x$-coordinates sorted in ascending order.
- `sorted_y_pc`: Array of $y$-coordinates sorted in ascending order.
- `sorted_z_pc`: Array of $z$-coordinates sorted in ascending order.
*Note: The source implementation [S1, unofficial] stores these as independent sorted arrays of values, not indices. This implies the method returns values or requires a separate mapping to original indices if identity is needed. The source code snippet shows `self.model_list` containing point clouds, but the specific "sorted indices" logic is described in the notes as creating `self.sorted_x_pc`, etc.*

**Steps:**
1. **Initialization**: For a given point cloud, extract all $x$, $y$, and $z$ coordinates. Sort each coordinate list independently to create `sorted_x_pc`, `sorted_y_pc`, and `sorted_z_pc`.
2. **Query Processing**: For a query box $[x_{min}, x_{max}] \times [y_{min}, y_{max}] \times [z_{min}, z_{max}]$:
   a. Find the range of indices in `sorted_x_pc` that fall within $[x_{min}, x_{max}]$.
   b. Find the range of indices in `sorted_y_pc` that fall within $[y_{min}, y_{max}]$.
   c. Find the range of indices in `sorted_z_pc` that fall within $[z_{min}, z_{max}]$.
3. **Intersection**: The points inside the box are those whose coordinates appear in all three ranges. *Note: The source notes [S1, unofficial] describe returning "the slice of points between these indices," which implies a 1D range query on a single sorted array or a simplification. However, for a 3D box, a true intersection of 3D points requires checking all three dimensions. The source code snippet provided [S1, unofficial] shows normalization and loading but not the specific `get_points_in_range` implementation details beyond the description. We assume the standard approach: find indices $i_{min}, i_{max}$ for each axis and intersect the sets of points.*
4. **Return**: Return the identified points.

## Subtopics

### [Searchsorted](7938-searchsorted.md)
Searchsorted finds the indices where query points `v` should be inserted into a sorted reference array `a` to maintain order. It serves as the core lookup mechanism for the parent method, enabling O(log N) point-in-box inclusion tests by determining the range of indices in pre-sorted coordinate arrays that correspond to a query point's coordinate. Unlike standard binary search which returns a single insertion point, this implementation explicitly computes both lower (`idx_lo`) and upper (`idx_hi`) bounds to handle edge cases and range queries robustly.

## Operating characteristics
- **Time Complexity**: $O(N \log N)$ for preprocessing (sorting). $O(\log N)$ for each axis query. Total query time is $O(\log N)$ if the intersection is handled efficiently, or $O(N)$ if naive filtering is used after index retrieval.
- **Memory Complexity**: $O(N)$ to store the sorted arrays.
- **Strengths**: Fast query times for static point clouds. Simple to implement using standard library bisect functions.
- **Limitations**: Preprocessing time is significant for large datasets. Dynamic updates (insertions/deletions) are expensive ($O(N)$). The source [S1, unofficial] does not specify how 3D intersection is handled efficiently, which is a potential pitfall.
- **When to use**: Static point clouds with frequent range queries.
- **When not to use**: Dynamic point clouds or when memory is constrained.
