# 3D Filled Circle Kernel Generation

Also called: 3D Binary Sphere Kernel, 3D Radial Mask Generation, Sampling Mask Generation, Sphere Phantom Generator, Synthetic Phantom, VolumeManager::genSamplingMasks, genSamplingMasks

## Overview
3D Filled Circle Kernel Generation produces binary occupancy masks or synthetic volume data representing a sphere within a voxel grid, primarily to optimize ray casting in volume rendering by precomputing voxel offsets [S1, unofficial]. It differs from its sibling [Point-in-Box Inclusion Test](1400-point-in-box-inclusion-test.md) by using a radial distance threshold rather than axis-aligned bounds, and from [Voxel Filled Check](1705-voxel-filled-check.md) by explicitly generating the kernel data structure rather than querying an existing one. The method supports two distinct output modes: a static binary occupancy field for general sphere representation [S2, S3, unofficial] and directional entry/exit offset arrays for optimized traversal [S1, unofficial].

## How it works
**Inputs:**
1.  `size`: Integer dimension of the cubic kernel grid ($N \times N \times N$). Default: 3 [S2, unofficial].
2.  `radius`: Floating-point or integer radius of the sphere. Default: 1.0 (or 3 for the CLI tool) [S1, S2, unofficial].
3.  `direction` (optional): A 3D vector $(dir_x, dir_y, dir_z)$ specifying the traversal direction for sampling mask generation. If omitted, a static binary kernel is generated [S1, unofficial].

**Outputs:**
*   **Mode A (Static Binary):** A 3D array of shape $(size, size, size)$ where elements are 1.0 if within the sphere and 0.0 otherwise, with the center element explicitly set to 0 [S2, S3, unofficial].
*   **Mode B (Sampling Masks):** Two sets of 3D vector offsets: `idx_add` (entering voxels) and `idx_remove` (leaving voxels), stored as `Vec3Array` or `std::vector<osg::Vec3>` [S1, unofficial].

**Data Structures:**
*   **Binary Kernel:** `float kernel[size][size][size]` or `uint8_t kernel[size][size][size]`.
*   **Sampling Masks:**
    *   `idx_remove`: `osg::Vec3Array` or `std::vector<osg::Vec3>`.
    *   `idx_add`: `osg::Vec3Array` or `std::vector<osg::Vec3>`.
    *   Storage is organized by direction: `idx_remove`/`idx_add` for left->right, `idx_u`/`idx_d` for down->up, `idx_f`/`idx_b` for front->back [S1, unofficial].

**Steps:**

1.  **Initialization:**
    *   If generating sampling masks: Clear `idx_remove` and `idx_add` arrays [S1, unofficial].
    *   If generating binary kernel: Initialize a zero-filled volume of shape $(size, size, size)$ [S3, unofficial].

2.  **Coordinate Generation:**
    *   Create a linear space from $-\lfloor size/2 \rfloor$ to $\lfloor size/2 \rfloor$ [S2, unofficial].
    *   Generate a 3D meshgrid of coordinates $(x, y, z)$ covering the kernel space [S2, unofficial].
    *   Calculate the center coordinates: $c_x = c_y = c_z = \lfloor size/2 \rfloor$ [S3, unofficial].

3.  **Distance Calculation and Masking:**
    *   Compute the squared radial distance from the center for each voxel:
        $$ d^2 = (x - c_x)^2 + (y - c_y)^2 + (z - c_z)^2 $$
    *   **For Binary Kernel:**
        *   Set voxel value to 1.0 if $d^2 < (size/4)^2$ (equivalent to $d < size/4$) [S3, unofficial].
        *   *Note:* Some implementations use a direct radius parameter: set to 1 if $d \le radius$, else 0 [S2, unofficial].
        *   Explicitly set the center element $(c_x, c_y, c_z)$ to 0 [S2, S3, unofficial].
    *   **For Sampling Masks:**
        *   Iterate through a grid from $-rad$ to $rad$ with a step size of 4 (e.g., $x, y, z \in \{-rad, -rad+4, \dots, rad\}$) [S1, unofficial]. This step size reduces sample count for performance [S1, unofficial].
        *   Let $pos = (x, y, z)$.
        *   If `direction` has an x-component ($dir_x \neq 0$):
            *   If $x == -rad$, add $pos$ to `idx_remove` (leaving face) [S1, unofficial].
            *   If $x == rad$, add $pos$ to `idx_add` (entering face) [S1, unofficial].
        *   If `direction` has a z-component ($dir_z \neq 0$):
            *   If $z == -rad$, add $pos$ to `idx_remove` [S1, unofficial].
            *   If $z == rad$, add $pos$ to `idx_add` [S1, unofficial].
        *   *Note:* The sources do not specify handling for the y-component (up/down) in the iteration logic, though storage structures `idx_u`/`idx_d` exist [S1, unofficial].

**Pseudocode:**

```python
import math
from typing import List, Tuple, Union

def generate_filled_circle_kernel(
    size: int = 3,
    radius: Union[int, float] = 1.0,
    direction: Tuple[float, float, float] = None
) -> Union[List[List[List[float]]], Tuple[List[Tuple[int, int, int]], List[Tuple[int, int, int]]]]:
    """
    Generates a 3D filled circle (sphere) kernel.
    
    Args:
        size: Dimension of the cubic grid.
        radius: Radius of the sphere.
        direction: Optional (x, y, z) vector for sampling mask generation.
        
    Returns:
        If direction is None: 3D list of floats (binary kernel).
        If direction is provided: Tuple of (idx_add, idx_remove) lists of (x,y,z) offsets.
    """
    if direction is None:
        # Mode A: Static Binary Kernel
        half_size = size // 2
        kernel = [[[0.0 for _ in range(size)] for _ in range(size)] for _ in range(size)]
        
        # Determine threshold. Sources vary between size/4 and explicit radius.
        # Using explicit radius if provided, else default logic from S3.
        if radius == 1.0 and size == 3:
            # Fallback to S3 logic: (size//4)^2
            threshold_sq = (size // 4) ** 2
        else:
            threshold_sq = radius ** 2
            
        for z in range(size):
            for y in range(size):
                for x in range(size):
                    # Distance from center
                    dx = x - half_size
                    dy = y - half_size
                    dz = z - half_size
                    dist_sq = dx*dx + dy*dy + dz*dz
                    
                    if dist_sq < threshold_sq:
                        kernel[z][y][x] = 1.0
                    else:
                        kernel[z][y][x] = 0.0
                        
        # Explicitly set center to 0 as per S2 and S3
        kernel[half_size][half_size][half_size] = 0.0
        
        return kernel
    else:
        # Mode B: Sampling Masks
        idx_add = []
        idx_remove = []
        
        # Determine radius for iteration bounds
        # S1 uses 'rad' parameter. If not passed, assume radius or size/2?
        # S1 CLI uses radius=3. We use the provided radius parameter.
        rad = int(radius)
        
        # Iterate with step 4 as per S1
        # Range from -rad to rad inclusive
        coords = list(range(-rad, rad + 1, 4))
        
        dir_x, dir_y, dir_z = direction
        
        for x in coords:
            for y in coords:
                for z in coords:
                    pos = (x, y, z)
                    
                    # Handle X direction
                    if dir_x != 0:
                        if x == -rad:
                            idx_remove.append(pos)
                        elif x == rad:
                            idx_add.append(pos)
                            
                    # Handle Z direction
                    if dir_z != 0:
                        if z == -rad:
                            idx_remove.append(pos)
                        elif z == rad:
                            idx_add.append(pos)
                            
                    # Y direction handling is not specified in S1 iteration logic
                    # [G] Assuming symmetry, one might add logic for dir_y != 0
                    # checking y == -rad and y == rad, but S1 only lists x and z.
                    
        return (idx_add, idx_remove)
```

## Subtopics

### [3D Gaussian Kernel Generation](2297-3d-gaussian-kernel-generation.md)
Generates a 3D Gaussian kernel for smoothing operations, with the center element explicitly set to zero. It differs from its parent [3D Filled Circle Kernel Generation](1520-3d-filled-circle-kernel-generation.md) by using a continuous probability density function for weighted smoothing rather than a binary occupancy mask, and from [Sphere Carving](2377-sphere-carving.md) by providing isotropic (or elliptical via children) decay rather than hard geometric boundaries.

### [Sphere Carving](2377-sphere-carving.md)
Sphere Carving is a voxelization post-processing method that removes solid voxels within a spherical radius from a specified center point in a voxel chunk or Sparse Voxel Octree (SVO). It solves the problem of creating destructible terrain or breakable objects by efficiently identifying and nullifying voxels intersecting a spherical volume. It sets itself apart from its parent [3D Filled Circle Kernel Generation](1520-3d-filled-circle-kernel-generation.md) by operating on existing occupancy data to remove voxels rather than generating a static binary kernel, and from [3D Binary Sphere Kernel Generation](4654-3d-binary-sphere-kernel-generation.md) by focusing on the destructive modification of a scene graph rather than kernel synthesis.

### [3D Binary Sphere Kernel Generation](4654-3d-binary-sphere-kernel-generation.md)
This method procedurally generates a 3D binary scalar field (density texture) representing a sphere centered at the origin of a voxel grid, specifically designed as input for GPU-based Marching Cubes surface extraction. Unlike static voxelization, this implementation features a time-varying radius that oscillates, creating a dynamic volume. It differs from its parent [3D Filled Circle Kernel Generation](1520-3d-filled-circle-kernel-generation.md) by explicitly targeting the `DensityTexture` property of a Marching Cubes component and utilizing a specific oscillating radius formula rather than a static threshold.

### Integer Brush Edit Plans
Deterministic generation of cell write sets for box and sphere shapes, emitting writes in canonical (z, y, x) order [S4, unofficial]. The sphere brush uses `spall_core`'s fixed-point `contains_cell_centre` predicate over the shape's cell bounding box to determine included cells [S4, unofficial]. The write set and order are byte-stable, guarded by pinned BLAKE3 digests and confirmed by a brute-force reference over a wider box [S4, unofficial]. Both brushes are verified to touch exactly eight bricks when centred on the corner where eight bricks meet [S4, unofficial]. A cell centre exactly on the sphere radius is included in the write set [S4, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N^3)$ for full grid evaluation, where $N$ is the kernel size. For sampling masks, the complexity is reduced by the step size (step 4), resulting in approximately $O((N/4)^3)$ iterations [S1, unofficial].
*   **Memory Complexity:** $O(N^3)$ for the binary kernel. For sampling masks, memory depends on the surface area of the sphere intersecting the grid boundaries, significantly less than $N^3$ [S1, unofficial].
*   **Performance:** The step-4 iteration in sampling mask generation is noted as a performance optimization, reducing the number of samples compared to a full voxel grid [S1, unofficial].
*   **Strengths:** Precomputing offsets allows for efficient ray casting by avoiding per-ray distance calculations for every voxel [S1, unofficial]. The binary kernel is simple and fast to generate.
*   **Limitations:** The step-4 approximation in sampling masks may miss voxels or introduce inaccuracies in the sphere boundary representation [S1, unofficial]. The center element is forced to 0, which may be unintuitive for some applications expecting a solid sphere [S2, S3, unofficial].
*   **When to use:** Use for optimizing volume rendering ray casting where the sphere moves along fixed axes [S1, unofficial]. Use binary kernels for simple collision detection or synthetic phantom generation for testing [S2, S3, unofficial].

## Background
The method originates from implementations in volume occlusion editing and rendering optimization, specifically within the `volume-occlusion-editor` project [S1, unofficial]. It is also referenced in the context of Plenoxels [S2, unofficial] and physics-aware CT reconstruction testing [S3, unofficial]. The deterministic brush variant is part of the `spall` project's fixture and edit plan system [S4, unofficial].
