# Octree Data Structure

Also called: CGAL::Octree, CGAL::Orthtree, RFVoxelOctree, RFVoxelOctreeNode, Voxel Octree Data Structure

## Overview
The octree partitions 3D space into a hierarchical grid of voxels to organize point cloud data for volume rendering and surface extraction [S1, unofficial][S2]. It distinguishes itself from flat voxel grids by recursively subdividing space into eight octants, allowing for variable resolution and efficient traversal [S1, unofficial][S2]. Unlike [Octree-based Level of Detail and Culling](1079-octree-based-level-of-detail-and-culling.md), which focuses on rendering optimization, this structure is primarily used for spatial indexing and isosurfacing [S2].

## How it works
**Inputs:** A set of 3D points (point cloud) and a bounding volume defining the spatial extent [S2].
**Outputs:** A tree structure where internal nodes represent empty or partially filled space, and leaf nodes represent occupied voxels or empty space with surface distance metrics [S1, unofficial].

### Data Structures
Two primary implementations are cited: the RFVoxelOctree (from [S1, unofficial]) and CGAL::Orthtree (from [S2]).

**RFVoxelOctreeNode Layout [S1, unofficial]:**
*   `m_pkChildren[8]`: Array of 8 pointers to child nodes.
*   `m_kBuildAabb`: Axis-aligned bounding box (RFAABB3i) for the node in build space.
*   `m_kWorldAabb`: Axis-aligned bounding box (RFAABB3d) in world space.
*   `m_eNodeType`: Enum indicating state: `NT_INTERNAL`, `NT_EMPTY_LEAF`, or `NT_LEAF`.
*   `m_fDistanceToSurface`: Double-precision distance to the nearest surface (for empty leaves).

**RFVoxelOctree Layout [S1, unofficial]:**
*   `m_pkRoot`: Pointer to the root node.
*   `m_kDataDimension`: 3D integer vector (`RFVector3i`) defining the grid dimensions.
*   `m_kOctreeOrigin`: 3D double vector (`RFVector3d`) for the octree origin.
*   `m_fVoxelSize`: Physical size of a single voxel unit (default 1.0f).
*   `m_uiOctreeDim`: Total dimension of the cubic voxel grid. Depth is derived as $\log_2(m\_uiOctreeDim)$.
*   `m_uiOctreeDepth`: Calculated depth.
*   `m_uiNumberOfNodes`, `m_uiNumberOfLeafs`, `m_uiNumberOfEmptyLeafs`, `m_uiNumberOfInternalNodes`: Counters for statistics.

**CGAL::Orthtree Definition [S2]:**
Defined as `CGAL::Orthtree< Orthtree_traits_point< GeomTraits, PointRange, PointMap, cubic_nodes, 3 > >`. This template specialization uses cubic nodes in 3 dimensions.

### Algorithm Steps
1.  **Initialization:** Define the bounding box (e.g., `bbox` in CGAL) and the point range [S2]. Set `m_fVoxelSize` (default 1.0f) and `m_uiOctreeDim` [S1, unofficial].
2.  **Construction:** Recursively subdivide the bounding volume into 8 octants.
    *   If a node contains points (or meets a refinement criterion), it becomes an internal node or a leaf depending on the termination condition [S1, unofficial][S2].
    *   CGAL allows specific splitters, such as `Refine_one_eighth` or `Refine_around_isovalue`, to control refinement density around the isosurface [S2].
3.  **Leaf Classification:**
    *   **Leaf:** Occupied by points.
    *   **Empty Leaf:** No points, but retains `m_fDistanceToSurface` for potential surface extraction [S1, unofficial].
4.  **Traversal:** Use `CGAL::Orthtrees::Leaves_traversal` to iterate over leaf nodes [S2].
5.  **Output:** Nodes can be dumped to polylines via `octree.dump_to_polylines(oo)` or used for Marching Cubes (MC), Topologically Correct Marching Cubes (TMC), or Dual Contouring (DC) [S2].

### Parameters
*   `m_fVoxelSize`: Physical size of a voxel. Default: 1.0f [S1, unofficial].
*   `m_uiOctreeDim`: Total dimension of the voxel grid. Depth = $\log_2(m\_uiOctreeDim)$ [S1, unofficial].
*   `isovalue`: Threshold for isosurfacing (e.g., 0.3 in CGAL examples) [S2].

### Edge Cases and Pitfalls
*   **Cracks:** If nodes are split with uniform size around the surface but varying depths exist around the isosurface, cracks (boundaries) will appear in the resulting mesh [S2].
*   **Refinement Strategy:** Arbitrary refinement can lead to non-manifold surfaces. Dense refinement around the isosurface ensures a manifold surface [S2].
*   **Precision:** CGAL examples use `oo.precision(17)` for output polylines [S2].

## Operating characteristics
*   **Time Complexity:** Construction depends on the number of points and the depth of the tree. Traversal is proportional to the number of leaves [S1, unofficial][S2].
*   **Memory Complexity:** Proportional to the number of nodes. Internal nodes store 8 pointers each [S1, unofficial].
*   **Strengths:** Efficient spatial indexing; supports variable resolution; integrates with CGAL isosurfacing algorithms (MC, TMC, DC) [S2].
*   **Limitations:** Varying depths can cause mesh cracks if not handled by adaptive refinement strategies [S2].
*   **When to use:** When organizing point clouds for surface extraction or spatial queries requiring hierarchical access [S1, unofficial][S2].
*   **When not to use:** When uniform resolution is sufficient and memory overhead of tree structure is prohibitive [S1, unofficial].

## Background
The CGAL::Orthtree implementation originated from the 2022 Google Summer of Code, contributed by Julian Stahl, mentored by Daniel Zint and Pierre Alliez [S2]. It provides first implementations of Marching Cubes, Topologically Correct Marching Cubes, and Dual Contouring using octrees [S2]. The RFVoxelOctree structure is part of the Voxelizer project [S1, unofficial].
