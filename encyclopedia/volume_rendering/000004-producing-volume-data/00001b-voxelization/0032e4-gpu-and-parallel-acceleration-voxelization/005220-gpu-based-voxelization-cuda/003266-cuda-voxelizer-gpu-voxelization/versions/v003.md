# CUDA Voxelizer GPU Voxelization

Also called: CUDA Implementation Details, Implementation Details, GPU Voxelization Implementation, voxelize

## Overview
A GPU-accelerated method to convert polygon meshes into voxel grids using CUDA, supporting both surface voxelization (faces) and solid voxelization (filled volume) [S2, unofficial]. It differs from sibling methods by utilizing a bit-packed voxel table and conservative rasterization techniques adapted for parallel atomic operations, specifically addressing the performance bottlenecks of atomic contention on older GPU architectures [S1, S3].

## How it works
**Inputs and Outputs:**
*   **Input:** An indexed triangle set (vertex buffer and index buffer) in a supported format (e.g., .ply, .obj) [S2, unofficial].
*   **Output:** A voxel grid in formats such as .vox, .binvox, or .obj cubes, optionally Morton-ordered [S2, unofficial].

**Data Structures:**
1.  **`voxinfo`**: A struct passed to the voxelization kernel containing:
    *   `bbox_mesh_cubed`: An axis-aligned bounding box (`AABox<float3>`) of the mesh, padded to form a cube [S2, unofficial].
    *   `gridsize`: A `uint3` defining the length of the cubical voxel grid in each dimension [S2, unofficial].
    *   `num_faces`: A `size_t` indicating the number of triangles [S2, unofficial].
2.  **`vtable` (Voxel Table)**: A bit-packed array stored in CUDA-managed unified memory.
    *   **Size:** $\lceil (N_x \times N_y \times N_z) / 32.0 \rceil \times 4$ bytes, where $N_x, N_y, N_z$ are the grid dimensions [S2, unofficial].
    *   **Layout:** Each voxel is represented by 1 bit. The total number of bits is $N_x \times N_y \times N_z$ [S2, unofficial].
3.  **`device_triangles`**: A flat array of floats on the GPU.
    *   **Layout:** 9 floats per triangle (3 vertices $\times$ 3 coordinates).
    *   **Size:** $\text{sizeof(float)} \times 9 \times \text{num\_faces}$ [S2, unofficial].

**Algorithm Steps:**
1.  **Initialization:** Transform vertices to voxel space and initialize the `vtable` with zeroes [S1, S3].
2.  **Bounding Box Calculation:** Calculate the bounding box of the mesh and pad it to form a cube (`bbox_mesh_cubed`) [S2, unofficial].
3.  **Memory Allocation:** Allocate CUDA-managed unified memory for `device_triangles` and `vtable` [S2, unofficial].
4.  **Data Transfer:** Copy vertex data into `device_triangles` as a flat float array (v0.x, v0.y, v0.z, v1.x, ...) [S2, unofficial].
5.  **Execution:** Call `voxelize()` for surface voxelization or `voxelize_solid()` for solid voxelization, passing `voxinfo`, `device_triangles`, `vtable`, and a `morton_code` flag [S2, unofficial].
    *   *Note:* Solid voxelization requires a watertight input mesh [S2, unofficial].
6.  **Parallel Processing:** Use persistent threads [Aila and Laine 2009] for parallel entities with varying work amounts (e.g., tiles looping over triangles) [S1, S3].
7.  **Atomic Operations:** Perform conservative voxelization by setting voxels for all overlapping triangles. To mitigate atomic contention, warps access triangles with a specific stride to ensure concurrent atomics refer to different memory locations [S1, S3].
8.  **Post-Processing (Optional):** Use `chag::pp` for scan and compaction [S1, S3] and radix sort (e.g., from CUDPP) for sorting, processing only significant bits [S1, S3].

**Edge Cases and Pitfalls:**
*   **Atomic Contention:** Conservative voxelization requires setting a voxel by all overlapping triangles, not just the one covering its center, causing conflicting atomic writes. On GT200-based hardware, atomics are expensive and can dominate runtime [S1, S3].
*   **Hardware Dependency:** Requires CUDA-compatible video card with Compute Capability 2.0 or higher (Nvidia Fermi or better) [S2, unofficial].
*   **Mesh Watertightness:** Solid voxelization fails or produces incorrect results if the input mesh is not watertight [S2, unofficial].

## Subtopics

### [Parallel CPU/GPU Voxelization](7027-parallel-cpu-gpu-voxelization.md)
This method accelerates the voxelization of tetrahedral meshes by distributing the computational workload between CPU cores (using OpenMP) and GPU streams (using CUDA). It addresses the performance bottleneck of iterating over large numbers of tetrahedra and voxel points, which is the core operation in robust voxelization algorithms like Philipp B’s. Unlike pure CPU or pure GPU approaches, this hybrid strategy aims to maximize throughput for high-density meshes while acknowledging the memory transfer overhead that penalizes smaller datasets.

## Operating characteristics
*   **Time Complexity:** Depends on the number of triangles and voxel grid size. The use of persistent threads and optimized atomic operations reduces overhead compared to naive implementations [S1, S3].
*   **Memory Complexity:** Dominated by the `vtable` size, which is $\lceil (N_x \times N_y \times N_z) / 32.0 \rceil \times 4$ bytes, and the `device_triangles` array [S2, unofficial].
*   **Measured Performance:** On a GTX 1050 TI, voxelizing the Stanford Bunny (70k triangles) takes 0.2 ms for a 64³ grid, 0.3 ms for 128³, 0.6 ms for 256³, and 1.8 ms for 512³ [S2, unofficial]. This is significantly faster than CPU implementations (e.g., 39.8 ms for 64³ on an Intel i7 8750H) [S2, unofficial].
*   **Strengths:** High performance for real-time applications; supports both surface and solid voxelization; flexible output formats [S2, unofficial].
*   **Limitations:** Atomic contention can degrade performance on older GPU architectures (GT200); solid voxelization requires watertight meshes [S1, S3][S2, unofficial].
*   **When to Use:** When high-speed voxelization of polygon meshes is required on modern GPUs.
*   **When Not to Use:** For very small models where GPU call overhead is not worth it (use CPU mode) or if the input mesh is not watertight and solid voxelization is needed [S2, unofficial].

## Background
The method is based on the work of M. Schwarz and HP Seidel in their 2010 paper "Fast Parallel Surface and Solid Voxelization on GPU's" [S1, S3]. The morton-encoded table implementation was based on the author's 2013 HPG paper "Out-Of-Core construction of Sparse Voxel Octrees" and the work in libmorton [S2, unofficial]. The implementation focuses on performance, making it viable for per-frame voxelization in real-time applications [S2, unofficial].
