# GPU and Parallel Acceleration Voxelization
## Overview
This family encompasses methods that accelerate the conversion of geometric sources (meshes, point clouds) into discrete volumetric representations by leveraging parallel processing units, primarily GPUs via CUDA or OpenGL/Vulkan, and multi-threaded CPUs [G]. It solves the performance bottleneck of naive, single-threaded voxelization algorithms, enabling real-time or near-real-time processing for complex models [G]. It differs from its siblings by explicitly utilizing hardware parallelism (thread-per-triangle, thread-per-voxel, or rasterization pipelines) and specialized memory structures (atomic counters, bit-packed tables, MSAA coverage) to handle the massive concurrency inherent in volumetric data generation [G].

## Subtopics

### [Per-Pixel Linked List Voxelization](1187-per-pixel-linked-list-voxelization.md)
A GPU-based technique that constructs a linked list of fragment depths per pixel using atomic counters and shader storage buffers, allowing for subsequent sorting and processing of depth-sorted voxels. It solves the problem of variable-depth fragment accumulation in rasterization by deferring the resolution of depth conflicts to a post-processing sort phase, enabling accurate solid voxelization without fixed-depth buffers. It differs from [MSAA Voxelization](7412-msaa-voxelization.md) by using explicit linked lists and atomic operations rather than multisample coverage masks, and from [Atomic Color Averaging in Voxelization](3529-atomic-color-averaging-in-voxelization.md) by preserving individual fragment depths for sorting rather than averaging them immediately [G].

### [Atomic Color Averaging in Voxelization](3529-atomic-color-averaging-in-voxelization.md)
Atomic Color Averaging is a GPU-based technique for compositing multiple fragment colors into a single voxel during parallel voxelization, ensuring time-coherent results despite arbitrary write ordering. It solves the problem of race conditions when multiple triangles rasterize into the same voxel by using integer atomic compare-and-swap operations to incrementally compute the average color, avoiding the need for floating-point atomics which are often unavailable or restricted in standard OpenGL/Vulkan image access. Unlike [Per-Pixel Linked List Voxelization](1187-per-pixel-linked-list-voxelization.md) which defers compositing, or [GPU-based Voxelization (CUDA)](14644-gpu-based-voxelization-cuda.md) which may use native float atomics, this method relies on a packed integer format and a retry loop to maintain correctness.

### [Parallel CPU Voxelization](7135-parallel-cpu-voxelization.md)
Parallel CPU Voxelization is a multi-threaded method for converting polygonal meshes or point clouds into a discrete volumetric representation, serving as a fallback when GPU acceleration (CUDA) is unavailable or explicitly disabled. It differs from sibling methods by leveraging Python's `ThreadPoolExecutor` to distribute voxel computation across available CPU cores, contrasting with the single-threaded or GPU-specific approaches of its alternatives.

### [MSAA Voxelization](7412-msaa-voxelization.md)
MSAA Voxelization is a GPU-based technique that approximates conservative rasterization by leveraging Multi-Sampling Anti-Aliasing (MSAA) coverage tests to determine voxel inclusion, thereby avoiding the computational overhead of explicit primitive edge expansion in the Geometry Shader. It differs from sibling methods like [Per-Pixel Linked List Voxelization](1187-per-pixel-linked-list-voxelization.md) by relying on hardware rasterizer coverage rather than explicit sorting or linked lists, and from [Triangle-Parallel Solid Voxelization](9770-triangle-parallel-solid-voxelization.md) by using a fragment-shader-driven approach rather than triangle-centric parallel processing.

### [Triangle-Parallel Solid Voxelization](9770-triangle-parallel-solid-voxelization.md)
Triangle-Parallel Solid Voxelization is a data-parallel algorithm that maps a triangle mesh into a discrete 3D voxel grid by dedicating one processing thread to each triangle. It solves the problem of converting surface geometry into a volumetric representation suitable for ray marching or volume rendering by determining the interior of the mesh via ray-casting along the primary axis. Unlike sibling methods that parallelize over voxels or tiles, this approach parallelizes over the input primitives, making it highly suitable for GPU architectures where thread count matches triangle count. It differs from [Per-Pixel Linked List Voxelization](1187-per-pixel-linked-list-voxelization.md) by operating in 3D space directly rather than projecting to 2D screens, and from [Compute Shader Triangle Voxelization](12867-compute-shader-triangle-voxelization.md) by using a simpler column-based iteration rather than solving plane equations for every candidate voxel in a 2D footprint.

### [GPU-based Voxel Query via Conditional Histogram Computation](10393-gpu-based-voxel-query-via-conditional-histogram-computation.md)
This method accelerates voxel queries in multivariate volumes by computing joint conditional histograms via GPU volume traversal, avoiding the high memory overhead of spatial hierarchy structures like octrees for data with uniformly high variance. It differs from sibling methods that rely on spatial partitioning or linked lists by projecting multivariate attribute distributions into 2D histogram bins conditioned on a transfer function, enabling efficient statistical exploration of the volume data.

### [GPU-based Voxelization (CUDA)](14644-gpu-based-voxelization-cuda.md)
GPU-based Voxelization accelerates the conversion of polygon meshes or geometric primitives into discrete volumetric representations by leveraging the massive parallelism of CUDA-capable GPUs. It solves the performance bottleneck of CPU-based rasterization, enabling real-time voxelization of high-polygon models. It distinguishes itself from sibling methods by its direct use of CUDA kernels for parallel triangle processing and atomic memory updates, contrasting with CPU parallelization [7135-parallel-cpu-voxelization.md] or specialized structures like linked lists [1187-per-pixel-linked-list-voxelization.md].

### Low-Detail Obstacle Voxelization
Using simplified meshes for obstacles to allow voxelization at every frame with little performance cost [S1, unofficial]. Parameter: Mesh LOD: Use a low level of detail mesh for each obstacle [S1, unofficial].

### Voxelization Engine Workload Distribution
A pipeline architecture distributing voxelization tasks between CPU and GPU to handle ROI computation, classification, and rasterization efficiently [S2, unofficial]. CPU: Compute Region of Interest (ROI) by updating index buffer dynamically. Perform normal-based classification and bucket sorting for polygonal models [S2, unofficial]. GPU: Rasterize classified primitives in streaming mode. Encode and store results as 2D textures in three directional sheet buffers [S2, unofficial]. Create proxy rectangles to texture map patches for rendering/access [S2, unofficial].

### Crack-Free Voxelization via Axis Swizzling
A technique to fix 'cracks' (holes/slots) in voxelization caused by steep primitive slopes relative to the view direction. It selects the projection direction (X, Y, or Z axis) based on the face normal to present the largest face area, avoiding high depth gradients [S3, unofficial]. In the Geometry Shader (GS), per primitive, select the projection direction from the X, Y, and Z axes according to the face normal [S3, unofficial]. Swizzle the X, Y, and Z components of the vertex positions in the Geometry Shader to change the projection direction. This allows rendering from 3 directions without 3 separate render passes [S3, unofficial]. In the Pixel Shader, restore the coordinate components according to the information passed from the Geometry Shader [S3, unofficial]. Crack Condition: If $|ddx(depth)| > 1.0$ or $|ddy(depth)| > 1.0$, cracks occur perpendicular to the depth direction. Calculated in the pixel shader [S3, unofficial].

## Background
The acceleration of voxelization has been driven by the need for real-time simulation and rendering of complex phenomena, such as fluids and deformable objects [G]. Early approaches relied on CPU-based parallelization or simple rasterization techniques [G]. The introduction of GPU-based methods, particularly those utilizing CUDA and advanced OpenGL/Vulkan features like MSAA and atomic operations, allowed for significant performance gains [G]. Key developments include using simplified meshes for obstacles to allow voxelization at every frame with little performance cost [S1, unofficial], distributing workload between CPU and GPU for ROI computation and rasterization to handle complex models efficiently [S2, unofficial], and fixing cracks caused by steep primitive slopes via axis swizzling in the Geometry Shader [S3, unofficial].
