# Atomic Color Averaging in Voxelization

Also called: Atomic Averaging for Voxel Compositing, Atomic RGBA8 average voxelization, Atomic Running Average Voxelization, Atomic Voxel Color Update, Integer Atomic Color Averaging

## Overview
Atomic Color Averaging is a GPU-based technique for compositing fragment colors into a voxel grid when multiple primitives overlap the same voxel cell [S1, unofficial][S2, unofficial]. It solves the write-ordering problem inherent in parallel rasterization, where fragments from different triangles arrive at the same destination voxel in arbitrary order, which would otherwise cause flickering and non-time-coherent results during dynamic revoxelization [S2, unofficial]. It sets itself apart from sibling methods like [Per-Pixel Linked List Voxelization](1187-per-pixel-linked-list-voxelization.md) by avoiding dynamic memory allocation and linked lists, instead using fixed-size integer textures and compare-and-swap loops to maintain a running average directly in the voxel texture [S1, unofficial][S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D voxel grid texture (typically `RGBA8` or `R32UI` for counters) and a stream of fragment colors from the rasterization of input primitives.
*   **Output:** A voxel texture where each occupied cell contains the averaged color of all fragments that contributed to it, along with a count of those fragments.

**Data Structures:**
The voxel grid is stored as a 3D texture with an unsigned integer format to support atomic operations. Specifically, the color components (RGB) and a sample counter are packed into a single 32-bit unsigned integer (`uint`) per voxel [S1, unofficial].
*   **Layout:** The 32-bit integer is composed of four 8-bit unsigned integers.
    *   Bits 0-7: Red component ($C_R$)
    *   Bits 8-15: Green component ($C_G$)
    *   Bits 16-23: Blue component ($C_B$)
    *   Bits 24-31: Counter ($N$), representing the number of samples accumulated [S1, unofficial][S2, unofficial].
*   **Packing:** Colors are normalized to $[0, 1]$ and scaled to $[0, 255]$ before packing. The counter is stored in the alpha channel position (bits 24-31) [S1, unofficial][S2, unofficial].

**Algorithm Steps:**
1.  **Initialization:** For each fragment generated by the rasterizer, obtain its world-space color $\mathbf{c}_{new}$ and the target voxel coordinates $(i, j, k)$.
2.  **Pack Initial Value:** Convert the new fragment's color and an initial count of 1 into a `uint`.
    $$ \text{val}_{new} = \text{packUnorm4x8}(\mathbf{c}_{new} \cdot 255.0, 1.0) $$
    Where $\mathbf{c}_{new} \cdot 255.0$ scales RGB to $[0, 255]$ and $1.0$ is the initial count [S1, unofficial].
3.  **Atomic Compare-and-Swap Loop:**
    *   Read the current value at $(i, j, k)$ using `imageAtomicCompSwap`.
    *   If the returned value (`curVal`) equals the value we just attempted to write (`prevVal`), the write was successful. Exit the loop.
    *   If `curVal != prevVal`, a race condition occurred. Another thread modified the voxel.
    *   **Unpack:** Decode `curVal` into a vector $\mathbf{v}_{curr} = (R, G, B, N_{curr})$.
    *   **Denormalize:** Convert RGB components to floating point $[0, 1]$ and $N_{curr}$ to an integer count.
    *   **Compute New Average:** Calculate the incremental moving average using the formula:
        $$ \mathbf{C}_{avg} = \frac{N_{curr} \cdot \mathbf{C}_{curr} + \mathbf{c}_{new}}{N_{curr} + 1} $$
        $$ N_{new} = N_{curr} + 1 $$
        Where $\mathbf{C}_{curr}$ is the current average color stored in the voxel, and $\mathbf{c}_{new}$ is the incoming fragment color [S1, unofficial][S2, unofficial].
    *   **Re-pack:** Scale $\mathbf{C}_{avg}$ back to $[0, 255]$ and pack $\mathbf{C}_{avg}$ and $N_{new}$ into a new `uint` (`val_next`).
    *   **Retry:** Attempt `imageAtomicCompSwap` again with `val_next`. Update `prevVal` to `curVal` and repeat.
4.  **Final Storage:** Once the loop exits, the voxel contains the correct averaged color and count.

**Pseudocode:**
```python
# Helper functions for packing/unpacking
def pack_rgba8(r, g, b, n):
    # r, g, b are in [0, 255], n is in [0, 255]
    return (int(n) << 24) | (int(b) << 16) | (int(g) << 8) | int(r)

def unpack_rgba8(val):
    r = val & 0xFF
    g = (val >> 8) & 0xFF
    b = (val >> 16) & 0xFF
    n = (val >> 24) & 0xFF
    return r, g, b, n

def atomic_color_average(voxel_texture, coords, new_color_rgb):
    """
    voxel_texture: A coherent volatile uimage3D (or equivalent buffer)
    coords: ivec3 (i, j, k)
    new_color_rgb: vec3 (normalized [0,1])
    """
    
    # 1. Pack initial value: new color (scaled to 0-255) and count 1
    r = int(new_color_rgb.x * 255.0)
    g = int(new_color_rgb.y * 255.0)
    b = int(new_color_rgb.z * 255.0)
    count = 1
    
    new_val = pack_rgba8(r, g, b, count)
    prev_val = 0
    cur_val = 0
    
    # 2. Atomic Compare-and-Swap Loop
    while True:
        # Attempt to swap. Returns the old value at coords.
        cur_val = image_atomic_comp_swap(voxel_texture, coords, prev_val, new_val)
        
        if cur_val == prev_val:
            # Success: no other thread modified the voxel between our read and write
            break
            
        # Conflict detected: another thread modified the voxel.
        # We must recompute the average based on the NEW current value.
        prev_val = cur_val
        
        # Unpack the current state of the voxel
        r_curr, g_curr, b_curr, n_curr = unpack_rgba8(cur_val)
        
        # Denormalize current color to [0, 1]
        c_curr_rgb = vec3(r_curr / 255.0, g_curr / 255.0, b_curr / 255.0)
        
        # Compute incremental moving average
        # C_new = (n_curr * C_curr + c_new) / (n_curr + 1)
        n_new = n_curr + 1
        c_avg_rgb = (c_curr_rgb * n_curr + new_color_rgb) / n_new
        
        # Renormalize and pack
        r_avg = int(c_avg_rgb.x * 255.0)
        g_avg = int(c_avg_rgb.y * 255.0)
        b_avg = int(c_avg_rgb.z * 255.0)
        
        # Ensure count does not exceed 255 (limit of 8-bit counter)
        if n_new > 255:
            n_new = 255
            
        new_val = pack_rgba8(r_avg, g_avg, b_avg, n_new)

    return unpack_rgba8(image_atomic_load(voxel_texture, coords))
```

**Parameters:**
*   **Combination Scheme:** Simple arithmetic averaging is the default [S2, unofficial]. Coverage-based combination is mentioned as a sophisticated alternative but is not implemented in the standard atomic averaging approach [S2, unofficial].
*   **Counter Limit:** The counter is stored in 8 bits, limiting the maximum number of samples per voxel to 255. If more fragments collide, the count saturates, and the average continues to be computed but with a fixed denominator weight relative to the saturated count [S1, unofficial][S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Overflow:** Using `RGBA8` prevents direct summation because 8 bits per component overflow quickly. The incremental average formula avoids this by normalizing after each addition [S2, unofficial].
*   **Precision:** The use of 8-bit integers for color components introduces quantization errors. Repeated averaging may lead to slight drift compared to floating-point accumulation [S2, unofficial].
*   **Collision Rate:** Lower resolution voxelization increases the number of collisions per voxel, causing the compare-and-swap loop to retry more frequently, significantly degrading performance [S2, unofficial].
*   **Atomic Support:** OpenGL 4.2 restricts image atomics to 32-bit signed/unsigned integers. Direct `imageAtomicAdd` on floating-point textures is not available, necessitating the emulation via `imageAtomicCompSwap` [S2, unofficial].

## Subtopics

### Temporal Synchronization for Voxel Coloring
A hardware-specific variant used in volumetric displays (e.g., laser-excited graphics) where voxel coloring is synchronized with a spatial light modulator. Instead of computing averages in software, the system temporally synchronizes the spatial position of generated voxels with the switching state of an LC color filter [S3]. The femtosecond laser repetition frequency is set to 1 kHz, and the LC color filter (refresh rate 60 Hz) switches colors (e.g., cyan, magenta, yellow) every 17 pulses. This allows voxel-by-voxel coloring without computational averaging, as seen in rendering spheres with 472 voxels and flowers with 1206 voxels [S3].

### Sparse Voxel List and Indirect Commands
An optimization layer often used in conjunction with atomic voxelization. During the voxelization pass, a sparse voxel list is filled to track which voxels were actually occupied by atomic writes. This list is then used to generate an indirect command buffer for the compute shader. This restricts subsequent reads/writes (such as unpacking the final texture or conetracing) to only occupied voxels, reducing thread usage and improving performance [S1, unofficial].

## Operating characteristics
**Time and Memory Complexity:**
*   **Memory:** $O(N)$ where $N$ is the number of voxels in the grid. Each voxel stores 4 bytes (32-bit uint).
*   **Time:** The base cost is $O(1)$ per fragment for a successful atomic write. However, in the presence of collisions, the cost is proportional to the number of retries in the compare-and-swap loop. In worst-case scenarios with high collision rates, the effective complexity can approach $O(K)$ per fragment, where $K$ is the average number of retries.

**Measured Performance:**
*   On NVIDIA hardware, using `atomicCompSwap64` on global memory (NV shader buffer store) provides a 2x speedup over the cross-vendor path, but this is not exposed for image access, requiring the voxel grid to be stored in global memory instead of texture memory for optimal performance [S2, unofficial].
*   The FP32 atomicAdd emulation (using compare-and-swap) is up to 25 times slower than the native `atomicAdd` operation when many collisions occur [S2, unofficial].
*   Performance drops dramatically for `RGBA8` formats using atomic moving average compared to simple writes. For example, on the Stanford Dragon mesh at 512 resolution, the execution time for `RGBA8` with rasterization merge was 31.40 ms, compared to 1.47 ms for standard write [S2, unofficial].
*   Paradoxically, lower resolution voxelization can be slower than higher resolution due to the increase in the number of collisions encountered per voxel [S2, unofficial].

**Strengths and Limitations:**
*   **Strengths:** No dynamic memory allocation; deterministic memory usage; works well for real-time revoxelization where flickering must be avoided; simple to implement on standard OpenGL/Vulkan hardware without specialized atomic float extensions.
*   **Limitations:** Slow under high collision rates; limited precision due to 8-bit color storage; counter saturation at 255 samples; requires careful handling of atomic loops to avoid deadlocks or excessive GPU usage.

**When to Use:**
*   Use when dynamic revoxelization is required and flickering artifacts from unordered writes are unacceptable.
*   Use when hardware does not support native floating-point atomics (e.g., older OpenGL contexts).
*   Avoid when high precision is required or when the scene has extremely high triangle density leading to massive voxel collisions.

## Background
The method originates from the need to handle parallel fragment compositing in GPU-based sparse voxelization. It was detailed in *OpenGL Insights: Octree-Based Sparse Voxelization Using the GPU Hardware Rasterizer* by Cyril Crassin and Simon Green [S2, unofficial]. The technique addresses the limitation of OpenGL 4.2, which only supports 32-bit integer atomics for image load/store operations, forcing developers to pack color and counter data into integers to emulate atomic addition via compare-and-swap loops [S1, unofficial][S2, unofficial]. It has been implemented in various real-time voxel cone tracing renderers and portfolio projects [S1, unofficial].
