# Double-Buffering für konfliktfreie Voxel-Modifikation

Also called: Ping-Pong Buffering, Puffer-Alternierung, Shared Memory Double-Buffered Volume Buffer, Volumeold/Volumenew Swap, Vortex Double Buffer

## Overview
Double-buffering for conflict-free voxel modification prevents visual artifacts such as flickering and data corruption caused by concurrent read and write accesses to the same voxel data during simulation or rendering updates [S1, unofficial]. By maintaining two separate volume buffers and swapping them between computation phases, it ensures that every thread operates on a consistent, untainted state from the previous time step, thereby eliminating race conditions inherent in single-buffered parallel voxel movement [S2, unofficial]. This approach is distinct from synchronization-heavy methods by trading increased memory consumption for simplified, lock-free parallel execution [S1, unofficial][S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A voxel grid representing the current state of the volume, a set of voxel movement vectors defined by position $\vec{p}_i$ and direction $\vec{h}_i$, and a double-buffered memory structure [S1, unofficial].
*   **Output:** A voxel grid representing the updated state for the next time step, stored in the destination buffer [S1, unofficial].

**Data Structures:**
The core data structure is a double-buffered volume container [S3, unofficial]. Based on the shared memory implementation, the layout is defined as:
```c
struct voxel_double_buffer_t {
    pixel_t volume[2][VOXELS_COUNT]; // Two pages of voxel data
    uint8_t page;                    // Index of the active buffer (0 or 1)
    uint8_t bits_per_channel;        // Color depth configuration
    uint16_t debug_flags;            // Debugging state
    uint16_t revolutions_per_minute; // Metadata (context-specific)
    uint16_t microseconds_per_frame; // Timing metadata
};
```
The essential fields for the method are `volume[2]` and `page` [S3, unofficial].

**Numbered Steps:**
1.  **Initialization:** Initialize two volume buffers, `Volumeold` and `Volumenew` [S1, unofficial].
2.  **Read and Delete:** For each voxel $i$ at position $\vec{p}_i$ with movement vector $\vec{h}_i$, read the voxel data from `Volumeold` and delete the voxel at $\vec{p}_i$ from `Volumeold` [S1, unofficial].
3.  **Write:** Write the voxel to the new position $\vec{p}_i + \vec{h}_i$ in `Volumenew` [S1, unofficial].
4.  **Swap:** Swap the buffers (`Volumeold` $\rightleftharpoons$ `Volumenew`) before each modification phase to prevent race conditions [S1, unofficial]. In shared memory implementations, this is achieved by toggling the page index: `page = !page` [S3, unofficial].

**Pseudocode:**
```python
def allocate_volume(size):
    return [None] * size

def clear_buffer(buffer):
    for i in range(len(buffer)):
        buffer[i] = None

def process_voxel_step(volume, active_page, voxels):
    src_idx = active_page
    dst_idx = 1 - active_page
    src_vol = volume[src_idx]
    dst_vol = volume[dst_idx]
    clear_buffer(dst_vol)
    for voxel in voxels:
        p_i = voxel.position
        h_i = voxel.direction
        if src_vol[p_i] is not None:
            src_vol[p_i] = None
            new_pos = p_i + h_i
            dst_vol[new_pos] = voxel
    return dst_idx

def initialize_double_buffer(size, initial_voxels):
    buffer0 = allocate_volume(size)
    buffer1 = allocate_volume(size)
    clear_buffer(buffer0)
    clear_buffer(buffer1)
    for voxel in initial_voxels:
        buffer0[voxel.position] = voxel
    return [buffer0, buffer1], 0
```

**Parameters and Typical Values:**
*   **Buffer Count:** Always 2 [S1, unofficial][S2, unofficial].
*   **Memory Allocation:** Requires $2 \times N \times C$ bytes, where $N$ is the number of voxels and $C$ is the size of a voxel [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Memory Usage:** The method doubles the required graphics memory compared to single-buffering [S1, unofficial].
*   **Write-Write Conflicts:** Double-buffering prevents read-write conflicts between time steps but does not inherently prevent two threads from writing to the same voxel in the same destination buffer simultaneously [S2, unofficial].
*   **Synchronization:** In shared memory contexts, the swap operation is performed by toggling the `page` index [S3, unofficial].

## Subtopics

### Ping-Pong Buffering
A general term for the technique of using two buffers and alternating between them as source and destination [G]. It is the fundamental mechanism enabling the conflict-free updates described here [G]. Choose this when you need to decouple reading from writing in iterative algorithms [G].

### Shared Memory Double-Buffered Volume Buffer
An implementation variant using POSIX shared memory (`shm_open`, `mmap`) to allow multiple processes to access the double-buffered volume [S3, unofficial]. It adds system-level synchronization and memory mapping overhead but enables cross-process consistency [S3, unofficial]. Choose this when rendering and display are decoupled into separate processes [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$ per time step, where $N$ is the number of voxels [G].
*   **Memory Complexity:** $O(2N)$, doubling the memory footprint compared to a single buffer [S1, unofficial].
*   **Performance:** Eliminates the need for complex locking mechanisms per voxel [S2, unofficial].
*   **Strengths:** Simple implementation and consistent state per thread [S2, unofficial].
*   **Limitations:** High memory cost and the need for additional synchronization for intra-buffer write conflicts [S1, unofficial][S2, unofficial].
*   **When to Use:** When concurrent voxel modification is required and memory is sufficient [G].
*   **When Not to Use:** When memory is extremely constrained [S1, unofficial].

## Background
The technique originated in real-time voxel visualization to resolve flickering artifacts from simultaneous read/write operations [S1, unofficial]. It was formalized in academic work on raycasting-based voxel rendering and GPU-based voxel simulations to ensure algorithmic correctness without sacrificing parallelism [S1, unofficial][S2, unofficial]. The specific shared memory implementation was developed for embedded volumetric display systems to synchronize rendering and display controllers [S3, unofficial].
