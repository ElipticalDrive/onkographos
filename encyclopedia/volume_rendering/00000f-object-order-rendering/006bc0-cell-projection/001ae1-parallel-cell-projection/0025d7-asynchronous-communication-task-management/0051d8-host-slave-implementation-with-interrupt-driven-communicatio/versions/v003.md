# Host-Slave Implementation with Interrupt-Driven Communication

Also called: Host-Slave partition, Interrupt-driven host-slave

## Overview
This method is a parallel processing scheme for volume rendering where a host node handles I/O and data preparation, while slave nodes handle the computationally intensive fitting and polygon generation [S1, unofficial]. It solves the idle time and communication overhead problems of standard host-slave partitions by using asynchronous, interrupt-driven communication to overlap computation with data transfer [S1, unofficial]. It sets itself apart from its sibling [Asynchronous Communication with Double-Buffering](4280-asynchronous-communication-with-double-buffering.md) by specifically employing an interrupt handler on the host to manage background subcube transmission and by implementing specific strategies like exponential subcube reduction and early communication requests to minimize latency [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Volume data slices and rendering parameters (e.g., approximation order (3,3,3)) [S1, unofficial].
*   **Output:** Rendered image composed of polygons sent from slaves to the host [S1, unofficial].

**Data Structures:**
*   **C3 Data:** Computed by the host. Requires 27 pixel values to compute the C3 data of a single pixel [S1, unofficial].
*   **Subcubes:** Chunks of volume data transferred from host to slaves [S1, unofficial].
*   **Polygons:** Computed by slaves, stored in local memory, and sent to the host [S1, unofficial].
*   **Communication Buffers:** Two buffers alternate for asynchronous message passing [S1, unofficial].

**Parameters:**
*   **Preload Slices:** Preload the group host with two images for (1,1,1) approximation or three images for (3,3,3) approximation to reduce idle time dominance [S1, unofficial].
*   **Buffer Count:** 2 buffers for asynchronous communication [S1, unofficial].

**Numbered Steps:**
1.  Host reads slice $i$ and computes its C3 data [S1, unofficial].
2.  Host starts interrupt handler for background subcube transmission [S1, unofficial].
3.  Host reads new slice $i+1$ and computes its C3 data [S1, unofficial].
4.  Host waits for all subcubes of the "old" slice $i$ to be transferred by the interrupt handler, while helping process additional subcubes to utilize idle time [S1, unofficial].
5.  Slaves request and get subcubes from the host [S1, unofficial].
6.  Slaves fit (3,3,3) functions to the subcube data [S1, unofficial].
7.  Slaves compute polygons [S1, unofficial].
8.  Slaves send polygons to the host [S1, unofficial].

**Communication Strategies:**
*   **Asynchronous Communication:** Alternates between two buffers. When `send_message` is called, the node returns immediately and packs data into the other buffer, waiting only if the previous message is not completed [S1, unofficial].
*   **Early Communication:** When a slave is almost finished processing subcubes, it sends a request to the host to process newly arrived subcubes without delay, reducing communication latency [S1, unofficial].
*   **Message Packing:** The host packs a couple of rows of subcubes into one transmission packet. Shared boundary pixels are sent only once instead of four times (since a pixel can be shared by 4 subcubes) [S1, unofficial].
*   **Exponential Subcube Reduction:** The host sends large quantities of subcubes at the beginning of a slice and reduces the number sent exponentially when the slice is almost done to avoid long idle time waiting for a slave [S1, unofficial].
*   **Local Memory Management:** Slaves store calculated polygons in local memory and empty them to the host when they accumulate to a certain level [S1, unofficial].

        self.busy = True

        self.busy = False

    """Asynchronous send. Returns immediately. Packs into buf_idx, waits only if previous send in that buffer is incomplete."""
    if not buffers[buf_idx].is_ready():
        buffers[buf_idx].wait_completion()
    buffers[buf_idx].pack(data)
    buffers[buf_idx].send()

        slice_next = read_slice(slice_idx)
        c3_data_next = compute_c3_data(slice_next)
        wait_for_subcube_transfer(slice_idx - 1)
        process_additional_subcubes()
        queue_subcubes(c3_data_next)

def slave_algorithm():

        polygon_buffer.append(polygons)
        if len(polygon_buffer) >= threshold:
            send_message(polygon_buffer, current_buf)
            polygon_buffer.clear()
        if almost_finished():
            send_request_to_host()

## Subtopics

### [Multi-Host Partition Scheme](14583-multi-host-partition-scheme.md)
A parallel volume rendering strategy that divides processing nodes into independent groups, each containing one host and multiple slaves, to process subsets of volume slices. It solves the load imbalance and I/O bottlenecks of pure symmetry partitions and the single-host computing bottleneck of pure host-slave schemes by allowing dynamically reassigning idle nodes from finished groups to busy ones.

## Operating characteristics
*   **Time Complexity:** The host performs I/O and C3 data computation, which is relatively fast compared to polygon generation [S1, unofficial]. The slaves perform the heavy computation [S1, unofficial]. The asynchronous nature overlaps communication with computation, reducing total time [S1, unofficial].
*   **Memory Complexity:** Requires local memory on slaves to store polygons until a threshold is reached [S1, unofficial]. Two buffers are used for communication [S1, unofficial].
*   **Performance:** Preloading slices reduces idle time dominance [S1, unofficial]. For (3,3,3) approximation, communication time becomes less important compared to computation time [S1, unofficial]. Near linear speed up is achieved with preloading [S1, unofficial].
*   **Strengths:** Minimizes idle time for both host and slaves [S1, unofficial]. Reduces communication overhead through message packing and asynchronous transfer [S1, unofficial].
*   **Limitations:** Complex implementation due to interrupt-driven software [S1, unofficial]. Critical section violations can cause hard-to-trace bugs [S1, unofficial].
*   **When to use:** When communication overhead is significant and the host can be utilized for data preparation and background communication management [S1, unofficial].
*   **When not to use:** When the implementation complexity is prohibitive or when the communication latency is negligible compared to computation time [S1, unofficial].

## Background
This method originates from the work on Scalar Field Modeling & Visualization on the Intel Delta [S1, unofficial]. It was developed to alleviate problems associated with the host-slave partition in parallel volume rendering, specifically idle time and communication overhead [S1, unofficial]. The approach uses an interrupt handler to manage background subcube transmission, allowing the host to remain productive while waiting for slaves [S1, unofficial].
