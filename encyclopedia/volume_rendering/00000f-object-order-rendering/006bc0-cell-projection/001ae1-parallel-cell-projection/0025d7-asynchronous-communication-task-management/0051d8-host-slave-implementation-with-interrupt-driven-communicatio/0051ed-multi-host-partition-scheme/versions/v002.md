# Multi-Host Partition Scheme

Also called: Hybrid Host-Slave/Symmetry Partition

## Overview
The Multi-Host Partition Scheme is a parallel volume rendering strategy that divides processing nodes into independent groups, each containing one host and multiple slaves, to process subsets of volume slices [S1, unofficial]. It solves the load imbalance and I/O bottlenecks of pure symmetry partitions and the single-host computing bottleneck of pure host-slave schemes by allowing dynamically reassigning idle nodes from finished groups to busy ones [S1, unofficial].

## How it works
**Inputs and Outputs**
- **Input:** A set of processing nodes and a volume dataset defined by a sequence of slices [S1, unofficial].
- **Output:** The rendered image and the total count of generated polygons [S1, unofficial].

**Data Structures**
- **Group:** A collection of nodes consisting of exactly one host and several slave nodes [S1, unofficial].
- **Slice Assignment:** Each group is assigned a specific subset of slices from the volume [S1, unofficial].
- **Boundary Overlap:** The boundary slices of every group are overlapped to provide proper boundary conditions for volume calculation [S1, unofficial].

**Parameters**
- **Group Size:** In the reported implementation, each group consists of 8 nodes [S1, unofficial].
- **Threshold:** A group broadcasts a "full" status when it has less than half a slice of work remaining [S1, unofficial].

**Algorithm Steps**
1. **Initialization:** Divide all nodes into several groups. Each group contains one host and some slave nodes [S1, unofficial].
2. **Slice Allocation:** Assign a disjoint subset of slices to each group. Ensure that the boundary slices of every group are overlapped with adjacent groups to provide proper boundary conditions for volume calculation [S1, unofficial].
3. **Independent Processing:** Each group processes its assigned slices independently using the Host-Slave Implementation with Interrupt-Driven Communication [S1, unofficial]. There is no synchronization between groups during processing [S1, unofficial].
4. **Progress Broadcasting:** When a group finishes processing a slice, its host broadcasts a message to all other group hosts. This allows every group to maintain an awareness of the remaining work in other groups [S1, unofficial].
5. **Capacity Broadcasting:** When a group has only half a slice of work remaining, its host broadcasts a message to other group hosts indicating that the group is nearly full. This prevents other groups from reassigning nodes to it [S1, unofficial].
6. **Completion and Reassignment:**
    - When a group finishes all its assigned slices, its host sends the total amount of calculated polygons to a designated specific node (for final aggregation) and registers that the group is done [S1, unofficial].
    - The nodes of the finished group are re-assigned as slave nodes to other unfinished groups. The number of nodes assigned to a target group is proportional to the unfinished work load of that target group [S1, unofficial].
    - The host of the receiving group sends messages to other group hosts to inform them of the new slaves [S1, unofficial].
7. **Cleanup:** The very last group host to finish performs cleanup: it obtains the total amount of generated polygons from the designated node and releases all nodes [S1, unofficial].

import threading

class Node:
    def __init__(self, node_id):
        self.id = node_id
        self.role = "idle"
        self.group_id = None
        self.is_full = False
        self.remaining_slices = 0
        self.slaves = []
        self.polygon_count = 0

class Group:
    def __init__(self, group_id, host_node, slave_nodes, slice_indices):
        self.id = group_id
        self.host = host_node
        self.slaves = slave_nodes
        self.slice_indices = slice_indices
        self.host.role = "host"
        self.host.group_id = group_id
        self.host.remaining_slices = len(slice_indices)
        for s in slave_nodes:
            s.role = "slave"
            s.group_id = group_id

def initialize_groups(nodes, group_size):
    """Divides nodes into groups of one host and several slaves [S1, unofficial]."""
    groups = []
    for i in range(0, len(nodes), group_size):
        host = nodes[i]
        slaves = nodes[i+1 : i+group_size]
        groups.append(Group(i, host, slaves, []))
    return groups

def assign_slices(groups, total_slices, overlap):
    """Assigns disjoint slice subsets with boundary overlap [S1, unofficial]."""
    slices_per_group = total_slices // len(groups)
    for i, group in enumerate(groups):
        start = i * slices_per_group
        end = (i + 1) * slices_per_group
        indices = list(range(start, end))
        if i < len(groups) - 1:
            indices.extend(range(end, end + overlap))
        if i > 0:
            indices = list(range(start - overlap, end))
        group.slice_indices = indices
    return groups

def process_slices(group, all_hosts, designated_node, lock):
    host = group.host
    # Step 3: Independent processing with no synchronization [S1, unofficial]
    while group.slice_indices:
        slice_id = group.slice_indices.pop(0)
        # Host-Slave processing step (delegated to parent scheme) [G]
        host.dispatch_to_slaves(group.slaves, slice_id)
        host.wait_for_slaves(group.slaves)

        # Step 4: Progress broadcasting
        with lock:
            for other_host in all_hosts:
                if other_host.id != host.id:
                    other_host.remaining_slices -= 1

        # Step 5: Capacity broadcasting
        if host.remaining_slices <= 0.5:
            host.is_full = True
            with lock:
                for other_host in all_hosts:
                    if other_host.id != host.id:
                        other_host.is_full = True

    # Step 6: Completion and reassignment
    host.is_full = True
    with lock:
        designated_node.polygon_count += host.polygon_count

    # Reassign finished group's slaves proportionally to unfinished work
    with lock:
        unfinished_hosts = [h for h in all_hosts if not h.is_full]
        total_remaining = sum(h.remaining_slices for h in unfinished_hosts)
        for other_host in unfinished_hosts:
            proportion = other_host.remaining_slices / total_remaining if total_remaining > 0 else 0
            num_to_assign = max(1, int(len(group.slaves) * proportion))
            assigned = group.slaves[:num_to_assign]
            group.slaves = group.slaves[num_to_assign:]

            other_host.slaves.extend(assigned)
            for s in assigned:
                s.group_id = other_host.group_id
                s.role = "slave"

            # Step 6c: Inform other hosts of new slaves [S1, unofficial]
            for h in all_hosts:
                if h.id != other_host.id:
                    pass  # Broadcast message

    # Step 6d: Discard remaining slaves to avoid deadlock [S1, unofficial]
    for orphan in group.slaves:
        orphan.role = "orphan"
        orphan.group_id = None

def cleanup(last_host):
    """Final aggregation and resource release [S1, unofficial]."""
    last_host.collect_polygon_counts()
    last_host.release_all_nodes()

**Edge Cases and Pitfalls**
- **Deadlock:** In message-passing systems (e.g., Intel iPSC), communication delays can cause two finished groups to reassign their nodes to each other simultaneously, resulting in deadlock [S1, unofficial].
- **Solution:** Discard newly assigned slave nodes if the receiving group has already finished its work. These discarded nodes become "orphans" with no host and perform no further work [S1, unofficial].
- **I/O Overhead:** Unlike symmetry partitions, this scheme avoids high I/O overhead because each slice is read by only one group (except for the necessary boundary overlaps), preventing redundant reads of compressed data [S1, unofficial].

## Operating characteristics
- **Time Complexity:** The scheme reduces idle time by dynamically balancing load. Without reassignment, the speed/node ratio drops significantly (e.g., from 0.564 to 0.481 for 256 nodes in the reported results) [S1, unofficial]. With reassignment, performance is closer to linear scaling, though slight imbalance remains due to the discrete nature of node reassignment [S1, unofficial].
- **Memory Complexity:** Memory usage scales with the number of nodes and the slice subsets assigned to each group [G].
- **Strengths:**
    - Reduces the bottleneck of insufficient host computing power found in single-host schemes by having multiple hosts [S1, unofficial].
    - Avoids the high I/O overhead of symmetry partitions, where slices might be read multiple times or where reading a small region from a compressed slice takes as long as reading the whole slice [S1, unofficial].
    - Provides dynamic load balancing through node reassignment [S1, unofficial].
- **Limitations:**
    - Implementation complexity is higher due to the need for inter-group communication and deadlock avoidance [S1, unofficial].
    - Load imbalance is alleviated but not totally eliminated, especially when there are many groups [S1, unofficial].
    - Extra slave nodes can become a burden for an already busy host if not managed carefully, slightly increasing total processing time as node count grows [S1, unofficial].
- **When to use:** Suitable for large volume datasets where slice processing times vary significantly and the data is stored in compressed form, making symmetry partitions inefficient due to I/O overhead [S1, unofficial].

## Background
The Multi-Host Partition Scheme was introduced in the context of scalar field modeling and visualization on the Intel Delta supercomputer [S1, unofficial]. It was developed to address the limitations of static partitioning strategies (symmetry and host-slave) in distributed memory environments [S1, unofficial]. The scheme is a hybrid approach, combining the simplicity of host-slave models with the parallelism of symmetry partitions, specifically tailored to mitigate the I/O bottlenecks associated with compressed volume data [S1, unofficial].
