# Parallel Projected Tetrahedra with KD-Tree Partitioning

Also called: Parallel Unstructured Volume Rendering in ParaView, Parallel Volume Rendering in ParaView, kd-tree based parallel volume rendering

## Overview
This method enables parallel volume rendering of unstructured tetrahedral grids by partitioning the data using a kd-tree to facilitate a traditional sort-last compositing algorithm [S1]. It renders unstructured grids natively without sampling into a regular grid, avoiding the oversampling/undersampling issues and large sample counts required by grid-based approaches [S1]. Unlike other parallel rendering approaches that require further transfer of cells after distribution, this method requires no further cell transfer once cells are distributed; only image data is communicated between processes [S1].

## How it works
The method operates on a distributed-memory parallel computer. It partitions the unstructured grid data to assign regions to different processes, renders the assigned tetrahedra using the projected tetrahedra method, and composites the resulting images [S1].

### Inputs and Outputs
- **Input**: An unstructured tetrahedral grid (defined by vertices and connectivity).
- **Output**: A final composited image.

### Data Structures
The primary data structure is the unstructured grid itself, represented as a collection of tetrahedra. Each tetrahedron is defined by its four vertices and associated scalar values. The partitioning structure is a kd-tree, which recursively splits the bounding box of the data [S1].

### Steps
1.  **Partitioning**: Partition the unstructured grid data using a kd-tree to create regions assigned to different processes [S1].
2.  **Splitting**: Split any tetrahedra that intersect with kd-tree region boundaries. This causes the data set size (number of tetrahedra) to grow [S1].
3.  **Distribution**: Distribute and clip the rendered tetrahedra among processes. This partitioning is performed whenever a change is made to the data, not every render frame [S1].
4.  **Rendering**: Render the distributed tetrahedra using the projected tetrahedra method to generate images for each process [S1].
5.  **Compositing**: Perform parallel image compositing (sort-last) by transferring only image data between processes for final composition [S1].

### Parameters
- **Image Resolution**: 800x800 pixels used in the experiments [S1].
- **Data Growth**: On average, data size grows by about 15% when adding a single level to the kd-tree, with variance between 5% and 30% [S1].

### Edge Cases and Pitfalls
- **Memory Usage**: Data redistribution requires holding at least two copies of the data simultaneously. If hardware memory is insufficient, rendering rates can drop impractically low [S1].
- **Geometry Changes**: Changes in viewable geometry require lengthy redistribution of the data [S1].
- **Data Growth Variance**: The first cuts usually have smaller growth than later ones. Larger data sets have smaller growth, suggesting sub-linear growth with respect to original data size [S1].

### Pseudocode

```python
def parallel_projected_tetrahedra_rendering(tetrahedra, num_processes, image_width, image_height):
    """
    Renders unstructured tetrahedral grid in parallel using kd-tree partitioning.
    
    Args:
        tetrahedra: List of tetrahedra, each defined by 4 vertices and scalar values.
        num_processes: Number of parallel processes.
        image_width: Width of the output image in pixels.
        image_height: Height of the output image in pixels.
        
    Returns:
        Final composited image.
    """
    # Step 1: Partitioning
    # Build a kd-tree to partition the data.
    # The kd-tree recursively splits the bounding box of the data.
    # The number of partitions is determined by num_processes (power of 2).
    kd_tree = build_kd_tree(tetrahedra, num_partitions=num_processes)
    
    # Step 2: Splitting
    # Split tetrahedra that intersect with kd-tree region boundaries.
    # This increases the number of tetrahedra.
    split_tetrahedra = []
    for tet in tetrahedra:
        if intersects_boundary(tet, kd_tree):
            split_tetrahedra.extend(split_tetrahedron(tet, kd_tree))
        else:
            split_tetrahedra.append(tet)
    
    # Step 3: Distribution
    # Assign split tetrahedra to processes based on kd-tree regions.
    # This step is performed when data changes, not every frame.
    process_assignments = assign_to_processes(split_tetrahedra, kd_tree)
    
    # Each process renders its assigned tetrahedra
    local_images = []
    for process_id in range(num_processes):
        assigned_tetrahedra = process_assignments[process_id]
        
        # Step 4: Rendering
        # Render using projected tetrahedra method.
        # This generates an 800x800 image (or specified resolution).
        local_image = render_projected_tetrahedra(assigned_tetrahedra, image_width, image_height)
        local_images.append(local_image)
        
    # Step 5: Compositing
    # Perform sort-last compositing.
    # Only image data is transferred between processes.
    final_image = sort_last_composite(local_images)
    
    return final_image
```

## Operating characteristics
- **Time Complexity**: The partitioning time reduces with larger jobs, but changes in viewable geometry require lengthy redistribution [S1]. Rendering speed increases with the number of processors, but shows diminishing returns when adding more processors than necessary for a given data set [S1].
- **Memory Complexity**: Requires holding at least two copies of the data during redistribution [S1].
- **Measured Performance**: Tested on a Dell Precision 530 workstation with dual 2.0 GHz Pentium-4 Xeon processors, 1 GB RDRAM, GeForce FX 5900 Ultra graphics card, and Myrinet 2000 interconnect [S1]. Data sets ranged from 44,832 to 14,094,684 tetrahedra [S1]. The system has a bigger speedup for larger data sets even if the overall frame rate is lower [S1].
- **Strengths**: Renders unstructured grids natively; no further cell transfer after distribution; only image data is communicated; allows code reuse and variety of algorithms [S1].
- **Limitations**: Data redistribution requires significant memory; changes in viewable geometry require lengthy redistribution; rendering rates can be too low for user interaction without level of detail rendering [S1].
- **When to Use**: For visualizing large unstructured grid simulations from supercomputers where native rendering is preferred over grid sampling [S1].
- **When Not to Use**: When hardware memory is insufficient for holding two copies of the data during redistribution, or when frequent changes in viewable geometry occur [S1].

## Background
This method was developed for ParaView and deployed at Sandia National Laboratories for visualizing simulations from supercomputers like Red Storm [S1]. It was presented in a paper by Kenneth Moreland et al. [S1]. The approach focuses on handling large quantities of data from high-fidelity physical simulations [S1].
