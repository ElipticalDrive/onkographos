# ZSWEEP

Also called: ZSWEEP mapper, ZSweep, ZSweep Algorithm

## Overview
ZSWEEP is an exact, object-order cell projection algorithm for volume rendering on unstructured grids that sweeps a plane parallel to the viewing plane through the data in order of increasing z to sort and render cells [S2, S3, unofficial][S4]. It differs from its parent [A-buffer visibility sort for non-convex grids](1057-a-buffer-visibility-sort-for-non-convex-grids.md) by optimizing specifically for memory usage and sorting efficiency through a sweep-based approach rather than a general A-buffer intersection list management, and it is substantially faster than its sibling [k*-Buffer Analysis](3932-k-buffer-analysis.md) while using much less memory than ray-casting [S3, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** An unstructured dataset containing tetrahedral and/or hexahedral cells [S3, unofficial]. A viewing direction defining the z-axis for the sweep [S3, unofficial].
*   **Output:** A rendered image with correct visibility and opacity accumulation.

**Data Structures:**
*   **Active Cell Set:** A data structure holding only the cells currently intersected by the sweep plane [S2, unofficial]. This keeps the memory footprint low [S2, unofficial].
*   **Face Intersection List:** A short list of ordered face intersections for each pixel, known to be correct and complete at the instant each stage of computation is completed [S3, unofficial].
*   **Auxiliary Data Structures:** Store partial information taken from a small number of "slices" of the dataset [S3, unofficial].

**Steps:**
1.  **Sweep:** Sweep a plane parallel to the viewing plane through the data in order of increasing z [S3, unofficial][S4].
2.  **Exploit Ordering:** Exploit the implicit (approximate) global ordering that the z-ordering of the vertices induces on the cells incident to them [S3, unofficial].
3.  **Project Faces:** As vertices are encountered by the sweep plane, project the faces of cells incident to those vertices [S3, unofficial].
    *   Special care is taken to avoid double projection of internal faces [S3, unofficial].
    *   Correctness in the projection order is assured [S3, unofficial].
4.  **Rasterize:** Rasterize cell faces as they are encountered by the sweep plane [S2, unofficial].
5.  **Compute Contribution:** Compute the contribution for each pixel in stages during the sweep, using the short list of ordered face intersections [S3, unofficial].
    *   Ensure the list of face intersections is correct and complete at the instant that each stage of the computation is completed [S3, unofficial].
6.  **Integrate:** Use a pre-integrated table for integration [S4].

**Pseudocode:**
```python
def zsweep_render(mesh, view_direction, pre_integration_table):
    # 1. Sort vertices by their coordinate along the view direction (z)
    sorted_vertices = sorted(mesh.vertices, key=lambda v: dot(v.position, view_direction))
    
    # 2. Initialize active cell set and auxiliary data structures
    active_cells = set()
    pixel_intersections = {}  # Maps pixel_id to list of (face, depth, cell_data)
    
    # 3. Sweep plane moves from front to back (increasing z)
    for vertex in sorted_vertices:
        # Identify cells incident to the current vertex
        incident_cells = mesh.get_cells_incident_to(vertex)
        
        # Add incident cells to the active set if not already present
        for cell in incident_cells:
            active_cells.add(cell)
            
        # 4. Project faces of cells incident to the current vertex
        # Avoid double projection of internal faces
        projected_faces = []
        for cell in active_cells:
            for face in cell.faces:
                if face.is_boundary or face.owner == cell:
                    projected_faces.append(face)
                    
        # 5. Rasterize and update pixel intersection lists
        for face in projected_faces:
            screen_coords = project_to_screen(face, view_direction)
            pixel_id = get_pixel_id(screen_coords)
            if pixel_id not in pixel_intersections:
                pixel_intersections[pixel_id] = []
            pixel_intersections[pixel_id].append((face, face.center_depth, cell.data))
            
        # 6. Compute pixel contributions using the ordered intersection lists
        # The list is guaranteed to be correct and complete at this stage
        for pixel_id in list(pixel_intersections.keys()):
            intersections = pixel_intersections[pixel_id]
            intersections.sort(key=lambda x: x[1])  # Sort front-to-back
            color, opacity = 0.0, 0.0
            for face, depth, cell_data in intersections:
                sample_color, sample_opacity = pre_integration_table.lookup(cell_data)
                alpha = 1.0 - opacity
                color += sample_color * sample_opacity * alpha
                opacity += sample_opacity * alpha
                if opacity >= 1.0:
                    break
            del pixel_intersections[pixel_id]  # Clear after processing
            
        # Remove cells from active set if they are no longer intersected by the sweep plane
        active_cells = {c for c in active_cells if c.is_behind_sweep_plane(vertex)}
        
    return pixel_intersections

# Helper definitions (standard operations)
def dot(a, b): return sum(x * y for x, y in zip(a, b))
def project_to_screen(face, view_dir): return [v - dot(v, view_dir) * view_dir for v in face.vertices]
def get_pixel_id(coords): return (int(coords[0]), int(coords[1]))
```

**Parameters:**
*   **Cell Types:** Handles datasets containing tetrahedral and/or hexahedral cells [S3, unofficial].
*   **Integration:** Uses a pre-integrated table for integration [S4].

**Edge Cases and Pitfalls:**
*   **Hardware Compatibility:** There is no simple way to map this algorithm into currently available graphics hardware [S1][S5, unofficial]. It is a software rendering technique [S4].
*   **Internal Faces:** Double projection of internal faces must be avoided to ensure correctness [S3, unofficial].
*   **Ordering:** The algorithm relies on the implicit global ordering induced by vertex z-ordering; correctness in projection order must be assured [S3, unofficial].

## Subtopics

### [Out-of-Core ZSWEEP](2134-out-of-core-zsweep.md)
Out-of-Core ZSWEEP is a direct volume rendering technique for large unstructured grids that extends the in-core ZSWEEP algorithm to handle datasets exceeding available RAM by processing data in tiles and loading meta-cells from disk only when needed. It differs from its sibling [MIR](1281-mir.md) by being substantially faster and leveraging the ZSWEEP optimization of front-to-back sorting, at the cost of more complex preprocessing and higher main-memory requirements.

### X-Bucket and X-Actives Processing
This variant involves processing scanlines from bottom to top [S6]. For each scanline, a 'critical section' of code is entered, where only one processor can run at a time [S6]. The surviving polygons of the previous pixel's x-actives list must be updated with newly interpolated values of field data and screen-z [S6]. New screen-z values may require rearrangement of polygons among survivors to maintain screen-z order [S6]. Taking into account the line-of-sight distance between the two polygons, the color-opacity contribution for that inter-polygon region is calculated and composited into a software floating point frame buffer using standard equations [S6].

## Operating characteristics
*   **Performance:** The method is up to 5 times faster than the best previously-known exact algorithms that use comparable amounts of memory [S3, unofficial].
*   **Memory Usage:** It has excellent memory efficiency, using much less memory than ray-casting [S2, S3, unofficial]. The memory footprint is kept low by holding only the active cell set in memory [S2, unofficial]. Auxiliary data structures only store partial information from a small number of "slices" of the dataset [S3, unofficial].
*   **Hardware Mapping:** There is no simple way to map this algorithm into currently available graphics hardware [S1][S5, unofficial]. It is implemented as a software rendering technique [S4].
*   **Strengths:** Fast, memory-efficient, exact rendering of unstructured datasets, simple enough to be readily adaptable to general (non-tetrahedral) cell formats [S3, unofficial].
*   **Limitations:** Hardware incompatibility, potential bottleneck in parallel implementations due to critical sections [S6].

## Background
ZSWEEP was developed by Ricardo Farias, Joseph S. B. Mitchell, and Claudio Silva, combining the approaches of sweeping, projection, and A-buffers [S4]. It was presented in a conference paper in January 2000 [S3, unofficial]. The algorithm is an example of an A-Buffer technique that optimizes for sorting and memory usage [S1][S5, unofficial].
