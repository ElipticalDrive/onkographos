# Cell-based AMR volume rendering via front/back-face subtraction

Also called: AMR cell kernel, Cube intersection length via signed texcoord.z

## Overview
This method renders Adaptive Mesh Refinement (AMR) datasets by representing each cell as a geometric cube and computing the line-of-sight integral via front/back-face subtraction [S1, unofficial]. It solves the problem of perspective-correct volume integration for piecewise-constant cubic cells, distinguishing itself from the "cell kernel" texture approach by supporting arbitrary camera projections without requiring mipmapped texture lookups [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** AMR cell data (position, weight, quantity) passed as instance attributes; camera projection matrix [S1, unofficial].
*   **Output:** Accumulated density and quantity values per fragment [S1, unofficial].

**Data Structures:**
*   **Cell Geometry:** Each cell is defined by 8 vertices and 12 triangles forming a cube [S1, unofficial].
*   **Instance Data:** One set of attributes (location, weight, quantity) is stored per instance (cell), not per vertex, minimizing memory overhead [S1, unofficial].
*   **Vertex Shader Output:**
    *   `texcoord.z`: The interpolated z-component of the texture coordinate, which corresponds to the distance $t$ along the ray [S1, unofficial].
    *   `weight`: The scalar weight of the cell [S1, unofficial].
    *   `quantity`: The scalar quantity associated with the cell [S1, unofficial].

**Numbered Steps:**
1.  Render each AMR cell as a cube consisting of 8 vertices and 12 triangles [S1, unofficial].
2.  For each fragment generated by the rasterizer, determine if the current face is front-facing or back-facing using the `front_facing` builtin [S1, unofficial].
3.  Retrieve the interpolated `texcoord.z` value, which represents the distance $t$ along the ray to the fragment [S1, unofficial].
4.  Compute the signed contribution for the fragment:
    *   Calculate the base value: $v = \text{weight} \times \text{texcoord.z} \times dx$ [S1, unofficial].
    *   Determine the sign: $-1$ if front-facing, $+1$ if back-facing [S1, unofficial].
5.  Accumulate the signed value into the output density buffer [S1, unofficial].

**Formula:**
The integral along the line-of-sight for a given ray is computed as:
$$ \sum_i (t_{i+1} - t_i) w_i $$
where $t_i, t_{i+1}$ are the entrance and exit distances along the ray to a given cell, and $w_i$ is the weight [S1, unofficial].

In the shader implementation, this is achieved by summing:
*   $- \text{texcoord.z} \times \text{weight} \times dx$ for front-facing faces [S1, unofficial].
*   $+ \text{texcoord.z} \times \text{weight} \times dx$ for back-facing faces [S1, unofficial].

**Parameters:**
*   **Cell Size ($dx$):** The physical size of the cell [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Missing Cell Size Factor:** The implementation may be missing factors of `dx` (cell size), which could affect the accuracy of the density calculation [S1, unofficial].
*   **Performance:** Increasing the number of vertices per instance (8 vertices/cell) has performance implications compared to point-based methods [S1, unofficial].

**Pseudocode:**
```python
def fragment_main(texcoord_z: float, weight: float, quantity: float, front_facing: bool, dx: float) -> tuple[float, float]:
    # Compute the base value using texcoord.z as the distance t
    # NOTE: The source implementation may be missing factors of `dx` for physical accuracy [S1, unofficial]
    value = weight * texcoord_z * dx

    # Determine sign based on face orientation
    # Front-facing faces contribute negatively, back-facing faces contribute positively
    # to compute (t_exit - t_entrance) * weight [S1, unofficial]
    sign = -1.0 if front_facing else 1.0

    # Compute signed contributions
    density_contribution = sign * value
    quantity_contribution = sign * value * quantity

    return density_contribution, quantity_contribution
```

## Subtopics

### Exact perspective projection of AMR cells
Renders AMR cells using exact perspective projection geometry [G]. Sets itself apart by handling perspective distortion explicitly in geometry rather than relying on rasterizer interpolation [G]. Choose when high geometric accuracy under perspective is required [G]. [Link](4428-exact-perspective-projection-of-amr-cells.md)

## Operating characteristics
*   **Time Complexity:** Linear in the number of cells, but with a higher constant factor due to 12 triangles per cell [S1, unofficial].
*   **Memory Complexity:** Low per-instance overhead (one location per cell), but higher vertex count per instance (8 vertices) compared to point-based methods [S1, unofficial].
*   **Measured Performance:** On a laptop with an NVIDIA Quadro GPU, the method handles up to 20,000,000 cells at approximately 1fps [S1, unofficial].
*   **Strengths:** Works with non-orthographic (perspective) cameras, unlike the "cell kernel" texture approach [S1, unofficial].
*   **Limitations:** Performance implications due to increased vertices per instance; potential accuracy issues if cell size factors (`dx`) are omitted [S1, unofficial].
*   **When to use:** When perspective camera support is required for AMR volume rendering [S1, unofficial].
*   **When not to use:** When performance is critical and orthographic projection is sufficient (use cell kernel texture instead) [S1, unofficial].

## Background
This method was proposed as an alternative to creating a "cell kernel" texture for AMR datasets [S1, unofficial]. It was implemented and tested by cphyc in April 2023 using three.js, demonstrating feasibility on consumer hardware [S1, unofficial]. The approach leverages the rasterizer's ability to distinguish front/back faces and interpolate texture coordinates to compute ray-cell intersection lengths implicitly [S1, unofficial].
