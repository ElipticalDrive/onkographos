# BCC Grid Rendering

Also called: Body-Centered Cartesian Grid Rendering, BCC Splatting

## Overview
BCC Grid Rendering is a volume rendering technique that utilizes a Body-Centered Cartesian (BCC) lattice for spatial sampling instead of the standard Cubic Cartesian (CC) grid [S1, unofficial]. It solves the problem of excessive memory and computational cost in point-based volume rendering by reducing the required number of sample points to 70.3% of a CC grid while maintaining lossless compression for spherically bandlimited signals [S1, unofficial]. It is distinct from CC rendering by its higher packing efficiency for isotropic signals and is best suited for point-based object-order methods that employ spherical filters, whereas CC grids are more common in general-purpose rendering [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A volumetric dataset defined on a BCC lattice, camera parameters (view and projection matrices), and a rendering kernel (typically Gaussian or similar spherical filter).
*   **Output:** A 2D raster image.

**Data Structures:**
The data is stored in a BCC lattice structure. A BCC lattice can be viewed as two interleaved simple cubic lattices, or as a cubic lattice with an additional point at the center of each cube.
*   **Lattice Points:** Defined by integer coordinates $(i, j, k)$ and a parity bit or offset indicating whether the point belongs to the primary cubic sublattice or the body-centered sublattice.
*   **Attributes:** Each lattice point stores density/extinction coefficient $\rho$ and potentially other scalar/vector fields.

**Steps:**
1.  **Lattice Generation:** Construct the BCC grid from the input data. If the input is on a CC grid, resample or interpolate onto the BCC lattice. The BCC lattice density is higher than CC for the same bounding box, but the number of points required for equivalent signal reconstruction is lower [S1, unofficial].
2.  **Transformation:** Transform the BCC lattice points from world space to clip space using the standard Model-View-Projection (MVP) matrix, identical to CC rendering [S1, unofficial].
3.  **Slicing/Sorting:** Sort the transformed points by depth (Z-buffer) to ensure correct front-to-back or back-to-front compositing.
4.  **Rasterization (Splatting):** For each point, project its 3D footprint onto the 2D image plane.
    *   **Shift:** When rendering BCC grids, slices must be shifted by $1/2$ relative to the CC grid alignment to account for the body-centered offset [S1, unofficial]. This ensures that the sampling pattern aligns correctly with the screen pixels during rasterization.
    *   **Footprint:** Compute the 2D footprint $F(x,y)$ for each point. Since BCC assumes spherically bandlimited signals, the kernel should ideally be isotropic/spherical to preserve the lossless compression property [S1, unofficial].
    *   **Weighting:** Calculate the weight $w$ based on the distance from the pixel center to the point's projected center, modulated by the point's density $\rho$ [S1, unofficial].
5.  **Compositing:** Accumulate the splatted contributions into the frame buffer using alpha blending. The order of accumulation (front-to-back or back-to-front) depends on the specific compositing strategy, but the BCC structure itself does not change the compositing formula [S1, unofficial].

**Pseudocode:**
```python
def render_bcc_grid(points, camera, image_width, image_height):
    """
    points: List of BCC lattice points. Each point has:
        - pos: (x, y, z) in world space
        - density: scalar value
        - type: 'primary' or 'center' (indicating BCC sublattice)
    camera: Object with view_proj_matrix and shift_offset (0.5 for BCC)
    """
    image = zeros((image_height, image_width, 4)) # RGBA
    
    # 1. Transform points to clip space
    transformed_points = []
    for p in points:
        # Standard MVP transformation
        clip_pos = camera.view_proj_matrix * p.pos
        if clip_pos.w > 0: # Visible
            transformed_points.append({
                'pos': clip_pos,
                'density': p.density,
                'type': p.type
            })
    
    # 2. Sort by depth (Z)
    # Note: BCC rendering requires shifting slices by 1/2.
    # This is typically handled by adjusting the projected coordinates or the rasterization grid.
    # Here we assume the rasterization step accounts for the shift.
    transformed_points.sort(key=lambda p: p.pos.z / p.pos.w)
    
    # 3. Rasterize and Composite
    for p in transformed_points:
        # Project to screen space
        sx = (p.pos.x / p.pos.w + 1) * 0.5 * image_width
        sy = (1 - (p.pos.y / p.pos.w + 1) * 0.5) * image_height
        
        # Apply BCC shift: The lattice points are offset by 0.5 in screen space relative to CC
        # This shift ensures the sampling pattern matches the BCC geometry
        sx += camera.shift_offset # shift_offset = 0.5
        sy += camera.shift_offset
        
        # Determine footprint radius (depends on kernel, e.g., Gaussian sigma)
        radius = get_footprint_radius(p.density)
        
        # Iterate over affected pixels
        for dy in range(-radius, radius + 1):
            for dx in range(-radius, radius + 1):
                px = int(sx + dx)
                py = int(sy + dy)
                
                if 0 <= px < image_width and 0 <= py < image_height:
                    # Compute 2D footprint weight
                    dist_sq = dx*dx + dy*dy
                    weight = compute_kernel_weight(dist_sq, radius)
                    
                    # Modulate by density
                    alpha = weight * p.density
                    
                    # Alpha blend into image
                    # Assuming pre-multiplied alpha or standard over operator
                    src_color = p.color * alpha # Assuming p has color
                    dst_alpha = image[py, px, 3]
                    
                    # Simple over compositing
                    new_alpha = alpha + dst_alpha * (1 - alpha)
                    if new_alpha > 0:
                        image[py, px, 0] = (src_color[0] * alpha + image[py, px, 0] * dst_alpha * (1 - alpha)) / new_alpha
                        image[py, px, 1] = (src_color[1] * alpha + image[py, px, 1] * dst_alpha * (1 - alpha)) / new_alpha
                        image[py, px, 2] = (src_color[2] * alpha + image[py, px, 2] * dst_alpha * (1 - alpha)) / new_alpha
                        image[py, px, 3] = new_alpha

    return image
```

**Parameters:**
*   **Shift Offset:** $0.5$ in normalized screen coordinates or lattice units [S1, unofficial].
*   **Kernel:** Spherical/Gaussian, optimized for isotropic signals [S1, unofficial].

**Edge Cases:**
*   **Non-Spherical Signals:** If the signal is not spherically bandlimited, the BCC grid may not provide lossless compression, and artifacts may appear [S1, unofficial].
*   **Boundary Conditions:** The shift by $1/2$ must be handled consistently at image boundaries to avoid edge artifacts [S1, unofficial].

BCC Grid Sampling uses a Body-Centered Cartesian (BCC) lattice to store volume data, requiring fewer sample points than a standard Cubic Cartesian (CC) grid while maintaining lossless compression for spherically bandlimited signals. It is distinct from CC sampling by its higher packing efficiency for isotropic signals and is best suited for point-based object-order methods that employ spherical filters, whereas CC grids are more common in general-purpose rendering.

## Operating characteristics
*   **Time Complexity:** Rendering time is proportional to the number of sample points. Since BCC reduces the number of required points to 70.3% of a CC grid, the theoretical rendering time is reduced by a similar factor, assuming constant cost per point [S1, unofficial].
*   **Memory Complexity:** Memory usage is reduced by approximately 29.7% compared to CC grids for the same spatial resolution and signal fidelity [S1, unofficial].
*   **Measured Performance:** In the Turbulent Jet 4D example, BCC rendering took 1.01s (71% of CC time) with 138 time steps, compared to 1.23s for CC with 99 time steps [S1, unofficial]. The BCC grid had 87M total points vs 168M for CC, but only 7.4M relevant voxels vs 9.4M for CC [S1, unofficial].
*   **Strengths:** Significant reduction in memory and computation for isotropic, spherically bandlimited signals. Lossless compression under the spherical bandlimit assumption [S1, unofficial].
*   **Limitations:** Only optimal for spherically bandlimited signals. Requires careful handling of the 1/2 shift during rasterization. Less common in general-purpose rendering pipelines compared to CC [S1, unofficial].
*   **When to Use:** Point-based volume rendering of isotropic data where memory and performance are critical.
*   **When Not to Use:** Non-isotropic signals, or when compatibility with standard CC-based tools is required.

## Background
The BCC grid was introduced as an alternative to the Cubic Cartesian (CC) grid for volumetric data representation. The concept is based on the work of Theussl ('01) and Neophytou ('02) [S1, unofficial]. The BCC lattice is known in mathematics and signal processing for its optimal packing density for spheres, which translates to fewer sample points needed for reconstruction of bandlimited signals [S1, unofficial]. It has been applied to time-varying datasets such as turbulent jets and flows [S1, unofficial].
