# Splat Data Structure (ISplatSource)
Also called: ISplatSource
## Overview
The `ISplatSource` is an abstract interface designed to load splat cloud data asynchronously, decoupling file I/O from the rendering thread to prevent UI freezes [S1, unofficial]. It differs from synchronous loading methods by returning a `LoadResult` object only upon completion, allowing the caller to manage memory and error states explicitly. It serves as the primary entry point for populating the GPU-ready splat buffers described in [Splat Texture Layout & Mapping](7089-splat-texture-layout-mapping.md).
## How it works
**Inputs and Outputs:**
- Input: A callback function `Callback` of type `std::function<void(LoadResult)>`.
- Output: A `LoadResult` struct containing the loaded splats, spherical harmonic degree, and error status.

**Data Structures:**
The core data structure returned is `LoadResult`, defined as follows:
- `splats`: `std::vector<SplatGPU>` — A vector of GPU-ready splat objects. The exact layout of `SplatGPU` is defined in [Splat Texture Layout & Mapping](7089-splat-texture-layout-mapping.md).
- `sh_degree`: `int` — The degree of spherical harmonics used for the splats.
- `error`: `std::string` — Non-empty if loading failed; empty if successful.
- `ok()`: `bool` — Returns `true` if `error` is empty.

**Steps:**
1. Instantiate the `ISplatSource` implementation.
2. Call `start(Callback cb)`, passing a callback function that accepts a `LoadResult`.
3. The implementation loads the splat data (e.g., from `.spz` or `.ply` files) on a background thread.
4. Upon completion, the callback is invoked with the `LoadResult`.
5. The caller checks `result.ok()`. If false, handle `result.error`. If true, use `result.splats` and `result.sh_degree`.

    def ok(self):
        return len(self.error) == 0

**Edge Cases and Pitfalls:**
- **Memory Usage:** The `splats` vector holds all splats in CPU memory before GPU upload. Large clouds may cause out-of-memory errors if the system RAM is insufficient [S1, unofficial].
- **Error Handling:** The `error` string must be checked. Ignoring it may lead to rendering artifacts or crashes if `splats` is empty or malformed.
- **Thread Safety:** The callback is invoked on the background thread. The caller must ensure thread-safe access to shared resources or marshal updates to the main thread.

## Operating characteristics
- **Time Complexity:** Loading time depends on file size and disk I/O speed. Asynchronous execution prevents blocking the main thread.
- **Memory Complexity:** O(N) where N is the number of splats, for CPU-side storage in `LoadResult.splats`.
- **Strengths:** Non-blocking I/O, explicit error handling, clean separation of loading and rendering.
- **Limitations:** Requires sufficient CPU memory to hold all splats temporarily. Not suitable for extremely large clouds without chunking or streaming.
- **When to use:** When real-time UI responsiveness is critical and splat clouds are too large for synchronous loading.
- **When not to use:** For small splat clouds where the overhead of asynchronous management is unnecessary, or in environments with strict memory constraints.

## Background
The `ISplatSource` interface is part of the `RVizSplat` project, an unofficial implementation for visualizing 3D Gaussian Splatting data in ROS (Robot Operating System) [S1, unofficial]. It was developed to address the need for efficient, non-blocking loading of splat clouds in interactive visualization tools. The design reflects common patterns in graphics programming for handling large datasets asynchronously.
