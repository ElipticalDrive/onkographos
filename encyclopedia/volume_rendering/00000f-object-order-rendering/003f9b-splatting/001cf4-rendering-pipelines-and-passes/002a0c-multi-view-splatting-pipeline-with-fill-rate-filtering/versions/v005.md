# Multi-View Splatting Pipeline with Fill-Rate Filtering

Also called: Multi-View Splatting Pipeline

## Overview
This method generates multi-view 2D images from a 3D point cloud by splatting points onto image planes and filtering out sparse views based on fill rate to ensure structured, high-quality outputs [S1, unofficial]. It differs from standard splatting by integrating a post-rendering quality control step that discards views with insufficient pixel coverage, making it suitable for dataset generation where consistent view density is required [S1, unofficial].

## How it works
**Inputs:**
- Point cloud data: A tuple of $(xyz, rgb, label)$ loaded from a `.pt` file [S1, unofficial].
- Camera configuration: Trajectory generation parameters and intrinsic/extrinsic matrices [S1, unofficial].
- Rendering parameters: `splat_radius` (default 2, covering a $5 \times 5$ pixel disk) and `min_fill_rate` (default 0.30) [S1, unofficial].

**Outputs:**
- For each kept view: JPEG color image, 16-bit PNG label, PNG color-mapped label, `.npy` index map, and camera pose/intrinsics [S1, unofficial].

**Data Structures:**
- `CameraPose`: Contains `extrinsics` (torch.Tensor $[4,4]$), `intrinsics` (torch.Tensor $[4]$), `position` (tuple), `target` (tuple), and `pitch_deg` (float) [S1, unofficial].
- `SplattingRenderer`: Manages the point cloud and rendering state.

**Algorithm:**
1.  **Data Loading:** Load point cloud $(xyz, rgb, label)$ using `torch.load` [S1, unofficial].
2.  **Pose Generation:** Generate camera poses using `generate_trajectory(xyz, config, device)` [S1, unofficial].
3.  **Batching:** Extract intrinsics and extrinsics into batches via `poses_to_batch(poses)` [S1, unofficial].
4.  **Initialization:** Initialize `SplattingRenderer` with `cam_batch`, `splat_radius`, and device [S1, unofficial]. Load point cloud into renderer via `renderer.load_pointcloud(xyz, rgb, label)` [S1, unofficial].
5.  **Rendering:** Render all views by iterating through camera batches. For each view, project points to screen space $(u,v)$, compute depths, and determine visibility [S1, unofficial].
    -   **Projection:** Points are projected using intrinsic and extrinsic matrices [S1, unofficial].
    -   **Splatting:** Points are expanded into splats with radius `splat_radius` [S1, unofficial].
    -   **Compositing:** For each pixel, the point with the minimum depth is selected to resolve occlusions. This is achieved by sorting expanded points by pixel index and depth, then keeping the first entry per pixel [S1, unofficial].
    -   **Assembly:** Construct color, label, and index maps from the winning points [S1, unofficial].
6.  **Fill-Rate Calculation:** Compute fill rate for each view as the fraction of valid pixels (where index map $\ge 0$) [S1, unofficial]:
    $$ \text{fill\_rate} = \frac{\text{count}(index\_map \ge 0)}{\text{total\_pixels}} $$
7.  **Filtering:** Keep only views where `fill_rate` $\ge$ `min_fill_rate` [S1, unofficial].
8.  **Saving:** Save outputs for kept views. If no views meet the threshold, print a warning and skip saving [S1, unofficial].

            W, H: Image dimensions
            point_ids: [N] original point indices

            color_img: [H, W, 3] uint8
            label_img: [H, W] uint8
            index_map: [H, W] int32

        flat_visible = visible.squeeze(-1)
        
        # Filter visible points

        flat_uv = flat_uv[valid_mask]

        if flat_uv.numel() == 0:

        # Convert to integer pixel coordinates
        pixel_x = torch.clamp(flat_uv[:, 0].long(), 0, W - 1)
        pixel_y = torch.clamp(flat_uv[:, 1].long(), 0, H - 1)
        
        # Create flat pixel indices
        flat_pixel_idx = pixel_y * W + pixel_x
        
        # Sort by pixel index, then by depth (ascending) to find closest point
        # Combine pixel index and depth for sorting
        # Note: This logic assumes a single point per pixel for simplicity in this pseudocode

        sorted_depths = flat_depths[order]
        sorted_point_ids = flat_point_ids[order]
        
        # Keep only the first point for each unique pixel (the one with min depth)
        keep = torch.ones(len(order), dtype=torch.bool, device=self.device)
        if len(order) > 1:
            keep[1:] = sorted_pixel_idx[1:] != sorted_pixel_idx[:-1]
        
        final_pixel_idx = sorted_pixel_idx[keep]
        final_point_ids = sorted_point_ids[keep]
        
        # Initialize canvases
        color_img = np.zeros((H, W, 3), dtype=np.uint8)
        label_img = np.zeros((H, W), dtype=np.uint8)
        index_map = np.full((H, W), -1, dtype=np.int32)

        final_x = final_pixel_idx % W
        final_y = final_pixel_idx // W
        
        # Assign colors and labels

## Operating characteristics
- **Time Complexity:** Dominated by the projection and sorting steps. Sorting $N$ points per pixel is $O(N \log N)$, but with the pixel-index-based sort key, it can be optimized to $O(N)$ using radix sort or similar techniques on GPU [S1, unofficial].
- **Memory Complexity:** Requires storing the point cloud and intermediate buffers for projection and compositing. Memory usage scales with the number of points and the number of views [S1, unofficial].
- **Performance:** The method is designed for GPU acceleration, leveraging CUDA for efficient projection and compositing [S1, unofficial]. The EWA variant is more expensive due to kNN search and covariance estimation [S1, unofficial].
- **Strengths:** Ensures high-quality, dense views by filtering out sparse ones. Suitable for dataset generation [S1, unofficial].
- **Limitations:** Dependent on the `min_fill_rate` threshold; setting it too high may result in no views being saved [S1, unofficial].

## Background
This pipeline is used in the DALA-CitywallV3 dataset generation process [S1, unofficial]. It builds on the principles of splatting, treating points as geometric primitives that are rasterized and composited [S1, unofficial].
