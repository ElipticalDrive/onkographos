# Rendering Pipelines and Passes

Also called: Render Forward Pass

## Overview
Rendering Pipelines and Passes refers to the structural organization of GPU stages required to render volumetric data as splatted primitives, managing the transition from 3D point attributes to 2D screen-space accumulation [S1, unofficial]. It solves the problem of correctly handling transparency, occlusion, and attribute interpolation for large point sets by decomposing the rendering task into distinct, hardware-accelerated passes [S1, unofficial]. Unlike monolithic ray-marching shaders or single-pass implementations, this family explicitly separates concerns (e.g., geometry traversal, shading, compositing) into sequential logical or physical stages to enable complex lighting, deferred shading, or differentiable training [S1, unofficial][S2, unofficial].

## Shared principles
The rendering pipeline family shares the fundamental mechanism of treating volumetric data as a set of geometric or parametric primitives that are transformed and rasterized [S1, S3, S4, unofficial].

1.  **Primitive Representation:** The volume is decomposed into primitives. These may be explicit geometric shapes (cubes, cells, splats) or implicit functions sampled via texture hardware [S1, S3, S4, unofficial]. Each primitive $k$ is defined by its position $\mathbf{p}_k$, density/extinction coefficient $g_k$ or $\rho_k$, and a reconstruction kernel $h$ (typically a Gaussian) [S1, unofficial][S6, unofficial][S10, abstract only, unofficial].
2.  **Transformation:** Primitives are transformed from volume space to screen space using the Model-View-Projection (MVP) matrix or specific factorizations (e.g., shear-warp) [S2, S3, S4, unofficial]. For perspective projections, the kernel shape may be distorted (e.g., EWA splatting) to account for foreshortening [S6, unofficial][S10, abstract only, unofficial].
3.  **Rasterization:** The transformed primitives are projected onto the 2D image plane. This step leverages hardware-accelerated scan-conversion, depth testing, and blending [S1, S2, S3, S4, unofficial]. The contribution of a voxel $D$ to a screen point $(x,y)$ is determined by the footprint function $F(x,y)$, which is the integral of the 3D kernel along the view direction [S2, unofficial][S6, unofficial][S10, abstract only, unofficial]:
    $$ F(x,y) = \int h(x-x_D, y-y_D, z) \, dz $$
    The intensity written to the pixel is modulated by the voxel density:
    $$ P(x,y) = \text{weight}(x,y) \cdot \rho(D) $$
    where $\text{weight}(x,y) = F(x-x_D, y-y_D)$ [S10, abstract only, unofficial].
4.  **Compositing:** Contributions are accumulated to form the final image. This is typically done using alpha blending in back-to-front or front-to-back order to handle transparency correctly [S1, S2, S3, unofficial][S7]. Splatting compositing is performed along sheets (all pixels at once for a set of voxels), whereas ray-casting composites along rays (one sample at a time) [S10, abstract only, unofficial].
5.  **Hardware Acceleration:** Most methods in this family rely on GPU rasterization pipelines for performance, enabling real-time interactivity [S1, S2, S3, unofficial].

## Subtopics

### [Plug-and-Play Ray Marching and Rendering](981-plug-and-play-ray-marching-and-rendering.md)
A modular pipeline interface that decouples ray marching and volumetric accumulation from the specific radiance field representation, allowing efficient differentiable rendering to be integrated into any user-defined neural radiance field. It solves the problem of boilerplate rendering code by standardizing the input/output contract for density and color queries, enabling acceleration of existing NeRF methods with minimal code changes. Unlike specialized, monolithic implementations such as Instant-NGP which rely on custom CUDA kernels, this method provides a Python API built on PyTorch, prioritizing ease of extension for dynamic and unbounded scenes over raw kernel-level optimization.

### [Time-Sliced Pipelined Architecture](1435-time-sliced-pipelined-architecture.md)
A hardware design methodology for volume rendering systems that achieves real-time performance by time-slicing functional blocks to allow simultaneous processing of multiple tasks. It solves the bottleneck of sequential pipeline execution by overlapping stages, enabling continuous hardware-software communication and interactive user interfaces. Unlike standard pipelining where stages execute sequentially, this architecture uses a multi-core structure where independent sub-cores are configured or replicated to execute specific operations concurrently.

### [Slice-by-Slice (Sheet Buffer) Splatting](2110-slice-by-slice-sheet-buffer-splatting.md)
A volume rendering optimization that organizes splats into cache-sheets aligned parallel to the volume face most closely parallel to the image plane, then composites these sheets slice-by-slice. It sets itself apart from its siblings, such as [Plug-and-Play Ray Marching and Rendering](981-plug-and-play-ray-marching-and-rendering.md) and [Screen Quad Rendering](2435-screen-quad-rendering.md), by leveraging hardware-accelerated rasterization for bulk accumulation within 2D planes rather than per-voxel or per-ray processing. Unlike [Screen Quad Rendering](2435-screen-quad-rendering.md) which may suffer from "sparkling" artifacts due to incorrect visibility determination in animated viewing, slice-based composition produces brighter, more accurate images by correctly handling occlusion, though it is slower due to the overhead of per-slice additions.

### [Screen Quad Rendering](2435-screen-quad-rendering.md)
The final compositing stage in a multi-pass volume rendering pipeline, responsible for displaying the accumulated volume data (stored in intermediate framebuffers) onto the screen. It solves the problem of transferring rendered results from off-screen render targets to the default framebuffer while allowing for post-processing effects such as cross-section slicing or debug overlays. It differs from sibling methods like [DirectXSplat Renderer API](8504-directxsplat-renderer-api.md) by explicitly separating the volume traversal/compositing logic from the final screen presentation, and from [Plug-and-Play Ray Marching and Rendering](981-plug-and-play-ray-marching-and-rendering.md) by relying on hardware-accelerated rasterization of a fullscreen primitive rather than software-based ray traversal for the final image generation.

### [Rendering Pipeline Architecture](3059-rendering-pipeline-architecture.md)
Defines the structural organization of GPU stages required to render volumetric data as splatted primitives, managing the transition from 3D point attributes to 2D screen-space accumulation. It solves the problem of correctly handling transparency, occlusion, and attribute interpolation for large point sets by decomposing the rendering task into distinct, hardware-accelerated passes. It differs from [Single-Pass Splat Rendering Pipeline](1254-single-pass-splat-rendering-pipeline.md) by separating concerns (depth, color, normalization) to ensure correct blending, and from [Splat Attributes Pass](1066-splat-attributes-pass.md) by explicitly handling weight normalization in a dedicated final stage rather than embedding it in attribute computation.

### [Custom Pass Rendering](3629-custom-pass-rendering.md)
A multi-pass, object-order rendering pipeline designed for high-performance visualization of large-scale volumetric data (specifically NanoVDB) and octree-based geometry within a modern graphics API context. It solves the problem of efficiently computing surface attributes (position, normal, material ID) and lighting effects (SSAO, shadows) for sparse volumetric datasets by decoupling geometric traversal from shading. Unlike monolithic ray-marching shaders, this method uses a sequence of specialized FullScreenPass stages to build intermediate G-buffers (hit position, filtered normals, ambient occlusion) before a final shading pass. It is distinct from [Plug-and-Play Ray Marching and Rendering](981-plug-and-play-ray-marching-and-rendering.md) by its explicit separation of traversal and lighting into discrete render passes, and from [Fragment List-Based Rendering Pipeline](3488-fragment-list-based-rendering-pipeline.md) by its reliance on screen-space fragment buffers rather than explicit primitive lists.

### [Multi-View Splatting Pipeline with Fill-Rate Filtering](4689-multi-view-splatting-pipeline-with-fill-rate-filtering.md)
A method that generates multi-view 2D images from a 3D point cloud by splatting points onto image planes and filtering out sparse views based on fill rate to ensure structured, high-quality outputs. It differs from standard splatting by integrating a post-rendering quality control step that discards views with insufficient pixel coverage, making it suitable for dataset generation where consistent view density is required.

### [DirectXSplat Renderer API](8504-directxsplat-renderer-api.md)
A C++/Direct3D 12 library for rendering 3D Gaussian Splats, providing a rasterization pipeline that handles scene upload, preparation, rendering, and frame submission with explicit resource management. It differs from general-purpose ray-marching or CPU-based splatting implementations by leveraging native D3D12 hardware acceleration for high-performance, real-time rendering, achieving up to 2.4x faster throughput than `gsplat` in matched-quality benchmarks. It is designed for host-owned device architectures where the application manages command lists, fences, and render targets, offering fine-grained control over memory residency and upload budgets.

### [Ray-Centric and Hardware-Accelerated Rendering](8936-ray-centric-and-hardware-accelerated-rendering.md)
A family of volume rendering techniques that compute pixel colors by tracing rays from the camera through the volume data, leveraging GPU hardware acceleration for performance. Unlike splatting methods that rasterize primitives, ray-centric methods sample the volume along the view direction, offering higher fidelity for complex lighting and transparency. It distinguishes itself from sibling methods like [Slice-by-Slice Splatting](2110-slice-by-slice-sheet-buffer-splatting.md) by processing rays individually or in batches rather than projecting sheets, and from [Batched Ray Rendering](1547-batched-ray-rendering.md) by focusing on the general hardware-accelerated execution model rather than just memory management.

### [Multi-Pass and Sequential Stage Architectures](10539-multi-pass-and-sequential-stage-architectures.md)
Architectures that decompose volume rendering into distinct, ordered operations executed across multiple rendering passes or shader stages to manage complexity, memory, or differentiability. This family solves the problem of coupling geometry processing, shading, and compositing, which is difficult to optimize in a single pass for complex lighting or large datasets. It sets itself apart from single-pass methods by explicitly separating concerns (e.g., geometry vs. shading in deferred rendering, or differentiability vs. rasterization in Jrender) into sequential logical or physical stages.

#### Image-order Splatting
An approach that improves accuracy when using a perspective projection by processing pixels rather than primitives [S2, unofficial].

## Background
The concept of splatting was introduced by Westover in 1989, who proposed mapping view-dependent footprints to a generic footprint table to improve rendering speed [S2, unofficial]. Mueller and Yagel later used an image-order splatting approach to improve accuracy with perspective projections [S2, unofficial]. While early implementations used Gaussian reconstruction kernels, other kernel types such as quadratic spline functions have been proposed for higher quality images under certain conditions [S2, unofficial]. The evolution of these pipelines has been driven by the need for real-time interactivity, leading to the adoption of GPU rasterization pipelines and multi-pass architectures for handling complex lighting and transparency [S1, S2, S3, unofficial].
