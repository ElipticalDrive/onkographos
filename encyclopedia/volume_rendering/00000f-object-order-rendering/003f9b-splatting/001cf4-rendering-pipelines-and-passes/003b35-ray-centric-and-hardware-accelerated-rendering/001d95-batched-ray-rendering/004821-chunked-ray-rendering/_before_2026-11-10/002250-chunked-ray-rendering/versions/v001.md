# Chunked Ray Rendering

Also called: Batched Rendering, Batched Volume Rendering, Chunked Ray Processing, Memory-Bounded Rendering, Ray Batching, Staged Ray Rendering

## Overview
Chunked Ray Rendering is a memory-management strategy for object-order volume rendering that processes large batches of rays in smaller, fixed-size chunks to prevent Out-Of-Memory (OOM) errors on the GPU [S1, S2, S3, S4, unofficial]. It is primarily used during validation and inference phases where full-resolution images must be generated without the training-time optimizations like CUDA-accelerated raymarching [S3, S4, unofficial]. It builds on [Batched Ray Rendering](1547-batched-ray-rendering.md) by explicitly managing the batch size relative to available VRAM, and differs from [Chunked Trilinear Volume Rendering](2557-chunked-trilinear-volume-rendering.md) by chunking the *rays* (the query set) rather than the *volume data* (the lookup grid) [S2, S5, unofficial].

## How it works
**Inputs:**
- `rays_o`: Tensor of ray origins, shape $[B, N, 3]$ or $[N, 3]$, where $B$ is batch size (often 1 for image rendering) and $N$ is total number of rays (pixels).
- `rays_d`: Tensor of ray directions, shape $[B, N, 3]$ or $[N, 3]$.
- `chunk_size` (or `max_ray_batch`): Integer specifying the number of rays to process per forward pass.
- `render_rays`: The underlying volume rendering function (e.g., NeRF forward pass) that accepts ray origins, directions, and model parameters, returning RGB and depth tensors.

**Outputs:**
- `rgb`: Concatenated RGB images, shape $[B, H, W, 3]$ or $[N, 3]$.
- `depth`: Concatenated depth maps, shape $[B, H, W]$ or $[N]$.

**Data Structures:**
- Lists `rgbs` and `depths` to store intermediate results from each chunk.
- Pre-allocated tensors `image` and `depth` of final shape on the target device to store results if direct assignment is preferred over list concatenation.

**Parameters:**
- `chunk_size`: Typical values range from 1024 to 4096 rays, depending on VRAM capacity and model complexity [S2, S3, unofficial]. A common default is 1024 [S2, unofficial] or 4096 [S3, unofficial]. Some implementations use $1024 \times 32$ [S1, unofficial] or $1024 \times 8$ [S5, unofficial].
- `perturb`: Boolean, typically `False` during inference to ensure deterministic, noise-free results [S2, unofficial].
- `white_bkgd`: Boolean, typically `True` for background compositing [S2, unofficial].

**Algorithm:**
1. Initialize an empty list `chunk_results` to store dictionaries or tuples of outputs from each chunk.
2. Determine the total number of rays $N$.
3. Iterate through the rays in steps of `chunk_size`:
   a. Calculate the start index `start` and end index `end = min(start + chunk_size, N)`.
   b. Slice the ray origins and directions: `rays_o_chunk = rays_o[:, start:end]` (or `rays_o[start:end]` if batch dimension is handled separately).
   c. Move `rays_o_chunk` and `rays_d_chunk` to the GPU device.
   d. Call the rendering function: `result = render_rays(rays_o_chunk, rays_d_chunk, perturb=False, white_bkgd=True)`.
   e. Move the result tensors (e.g., `result['rgb']`, `result['depth']`) to CPU memory if VRAM is constrained, or keep on GPU if memory allows.
   f. Append the result tensors to `chunk_results`.
4. Concatenate all tensors in `chunk_results` along the ray dimension (dimension 0 or 1 depending on layout).
5. Reshape the concatenated tensors to the image dimensions $[H, W, 3]$ and $[H, W]$.

**Pseudocode:**
```python
def chunked_render(rays_o, rays_d, render_rays, chunk_size=1024):
    """
    Render rays in chunks to manage GPU memory.
    
    Args:
        rays_o: Tensor of ray origins [N, 3] or [B, N, 3]
        rays_d: Tensor of ray directions [N, 3] or [B, N, 3]
        render_rays: Function that takes (rays_o, rays_d, **kwargs) and returns dict with 'rgb', 'depth'
        chunk_size: int, number of rays per batch
        
    Returns:
        rgb: Tensor [N, 3] or [B, N, 3]
        depth: Tensor [N] or [B, N]
    """
    # Determine total number of rays
    if rays_o.dim() == 3:
        B, N, _ = rays_o.shape
    else:
        B = 1
        N, _ = rays_o.shape
        
    all_rgbs = []
    all_depths = []
    
    # Iterate in chunks
    for i in range(0, N, chunk_size):
        end = min(i + chunk_size, N)
        
        # Slice rays
        rays_o_chunk = rays_o[:, i:end] if B > 1 else rays_o[i:end]
        rays_d_chunk = rays_d[:, i:end] if B > 1 else rays_d[i:end]
        
        # Move to device (assuming device is handled by render_rays or passed explicitly)
        # In practice, ensure tensors are on the same device as the model
        rays_o_chunk = rays_o_chunk.to(device)
        rays_d_chunk = rays_d_chunk.to(device)
        
        # Render chunk
        # perturb=False for deterministic inference
        result = render_rays(rays_o_chunk, rays_d_chunk, perturb=False, white_bkgd=True)
        
        # Collect results
        # Move to CPU if necessary to free GPU memory for next chunk
        rgb_chunk = result['rgb'].cpu()
        depth_chunk = result['depth'].cpu()
        
        all_rgbs.append(rgb_chunk)
        all_depths.append(depth_chunk)
        
    # Concatenate results
    rgb = torch.cat(all_rgbs, dim=1 if B > 1 else 0)
    depth = torch.cat(all_depths, dim=1 if B > 1 else 0)
    
    return rgb, depth
```

**Edge Cases and Pitfalls:**
- **VRAM Exhaustion:** If `chunk_size` is too large, the intermediate feature maps and gradients (if training) will cause OOM. The value must be tuned per hardware [S4, unofficial].
- **Precision Loss:** Moving tensors to CPU between chunks introduces overhead and potential precision issues if not handled carefully, though usually negligible for inference [S2, unofficial].
- **CUDA Raymarching:** If CUDA-accelerated raymarching is enabled (`cuda_ray=True`), staging/chunking is often disabled because the CUDA kernel handles memory more efficiently [S3, unofficial].
- **Boundary Conditions:** Ensure the last chunk handles the remainder correctly using `min(i + chunk_size, N)` [S3, unofficial].

## Subtopics

### Minibatch Splitting
A specific implementation of chunked ray rendering that splits a huge tensor (ray bundle) into a list of minibatches using a list comprehension. It is characterized by its simplicity and direct use of Python slicing. It is chosen when a quick, library-agnostic memory split is needed without custom C++/CUDA kernels. Typical `chunksize` is $1024 \times 8$ [S5, unofficial].

## Operating characteristics
- **Time Complexity:** $O(N)$, where $N$ is the total number of rays. The constant factor increases slightly due to Python loop overhead and tensor concatenation.
- **Memory Complexity:** $O(C \cdot M)$, where $C$ is `chunk_size` and $M$ is the memory footprint per ray (including intermediate activations). This is significantly lower than $O(N \cdot M)$ required for processing all rays at once.
- **Performance:** Throughput is lower than unchunked rendering due to kernel launch overheads for each chunk. However, it enables rendering of high-resolution images that would otherwise crash the GPU.
- **Strengths:** Prevents OOM errors; allows full-resolution rendering on consumer hardware; simple to implement.
- **Limitations:** Slower than batched rendering due to overhead; not suitable for real-time training loops where speed is critical (unless `chunk_size` is small enough to fit in memory).
- **When to use:** Validation, testing, and inference on high-resolution scenes or large datasets where VRAM is limited [S2, S4, unofficial].
- **When not to use:** Training with `cuda_ray=True` (staging is disabled) [S3, unofficial]; real-time applications requiring high FPS.

## Background
Chunked Ray Rendering originated as a practical necessity in the early NeRF implementations to handle the memory demands of dense ray sampling during evaluation. It is widely adopted in open-source NeRF repositories such as `nerf-from-scratch` [S1, unofficial], `nerf-3d-vision` [S2, unofficial], and `IDDR-NGP` [S3, unofficial]. The technique is particularly relevant for scenes with large pixel counts (e.g., 4K images) where the number of rays exceeds GPU memory capacity for intermediate feature storage. It is a standard post-processing step in many NeRF pipelines to generate test-set metrics and videos [S3, S4, unofficial].
