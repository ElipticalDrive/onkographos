# Rendering Pipelines and Passes

Also called: Render Forward Pass

## Overview
Rendering Pipelines and Passes define the structural organization and execution sequence for generating volumetric images, decomposing the complex process of volume rendering into logical, sequential stages such as data traversal, interpolation, shading, and compositing [S1, S3, unofficial]. This family solves the problem of managing complex visual effects and geometric projections by isolating computational requirements into distinct passes, enabling optimized memory access patterns and flexible appearance control [S3, unofficial]. It differs from monolithic rendering approaches by explicitly separating geometric projection (e.g., depth testing, splatting) from visual appearance (e.g., shading, classification), allowing for techniques like deferred shading or multi-pass accumulation [S3, unofficial].

## Shared principles
The rendering pipeline family operates on the principle of stage separation, where each stage performs a specific transformation on the data or image state. Common mechanisms include:

1.  **Stage Decomposition:** The rendering process is divided into logical stages such as Data Traversal, Interpolation, Gradient Computation, Classification, Shading, and Compositing [S1, S3, unofficial]. This allows for independent optimization of visual appearance (shading/classification) and geometric projection (compositing) [S3, unofficial].
2.  **Intermediate Storage:** Pipelines utilize intermediate framebuffers or data structures (e.g., fragment lists, G-buffers) to store per-pixel or per-voxel attributes (color, normal, depth, opacity) between stages [S1, S2, unofficial]. For example, [Custom Pass Rendering](3629-custom-pass-rendering.md) uses multiple FBOs to store hit positions, normals, and material IDs [S1, unofficial].
3.  **Sequential Execution:** Stages are executed in a defined order. For instance, [Fragment List-Based Rendering](3488-fragment-list-based-rendering-pipeline.md) follows a Clear, Construction, Insertion, and Evaluation sequence [S1, unofficial].
4.  **Accumulation and Blending:** Final image generation involves accumulating contributions from multiple samples or primitives, often using alpha blending or weighted summation [S1, S3, unofficial].

## Subtopics

### [Plug-and-Play Ray Marching and Rendering](981-plug-and-play-ray-marching-and-rendering.md)
This method provides a modular interface for efficient ray marching and differentiable volumetric rendering, allowing users to plug any user-defined radiance field into a standardized acceleration pipeline. It distinguishes itself from specialized implementations like Instant-NGP by offering a Python API built on PyTorch, which facilitates easier extension to dynamic and unbounded scenes while maintaining high performance. Choose this when you need a flexible, differentiable rendering loop that separates the radiance field query logic from the rendering loop, handling optimization of sample selection (skipping empty/occluded regions) and accumulation of color and opacity automatically.

### [Volume Rendering Pipeline](1318-volume-rendering-pipeline.md)
The Volume Rendering Pipeline is a standard implementation structure for direct volume rendering that decomposes the image formation process into logical, sequential stages: data traversal, interpolation, gradient computation, classification, shading, and compositing. Unlike methods that fit geometric primitives to the data, this pipeline forms images by directly shading each sample and projecting it onto the picture plane, using local gradient vectors as surface normals for shading and separate classification operators for opacity. It treats each volume sample as a reflective, light-emitting, semi-transparent cloud, assuming every sample point acts as both an absorber and an emitter. Choose this for traditional direct volume rendering where explicit control over the shading and classification functions is required.

### [Time-Sliced Pipelined Architecture](1435-time-sliced-pipelined-architecture.md)
The Time-Sliced Pipelined Architecture is a hardware design methodology for volume rendering that achieves real-time performance by time-slicing functional blocks to allow simultaneous processing of multiple tasks. It solves the bottleneck of sequential pipeline execution by overlapping stages, enabling continuous hardware-software communication and interactive user interfaces. It distinguishes itself from standard pipelining by emphasizing component reusability and sub-core replication, where independent vertical cores are configured or replicated based on specific processing requirements rather than fixed linear stages. Choose this for hardware implementation or simulation of high-throughput, real-time volume rendering systems.

### [Batched Ray Rendering](1547-batched-ray-rendering.md)
Batched Ray Rendering is a memory-management pipeline for volume rendering that splits large ray batches into fixed-size chunks to prevent GPU Out-Of-Memory (OOM) errors. It orchestrates the sequential execution of coarse and fine network passes per chunk, distinguishing itself from full pipeline descriptions by isolating the batching mechanism (`batchify_rays`) and per-chunk rendering logic (`render_rays`). Choose this when rendering large scenes with neural radiance fields (NeRF) or similar implicit representations that exceed GPU memory limits.

### [GPU Implementation Pipeline](2385-gpu-implementation-pipeline.md)
A GPU-accelerated rendering technique that traces rays from the camera through each pixel into a 3D volume to compute color and opacity, implemented in a single pass using fragment shaders. It solves the problem of visualizing volumetric data directly on the GPU without generating intermediate polygonal meshes. It differs from isosurface extraction (e.g., [Marching Cubes](53-marching-cubes.md)) by preserving internal volume information, and from splatting ([Splatting](10-splatting.md)) by avoiding sorting and blending overheads for dense volumes, though it is computationally heavier per pixel than texture-based splatting [G]. Choose this for direct, high-performance visualization of dense volumetric data on modern GPUs.

### [Screen Quad Rendering](2435-screen-quad-rendering.md)
Screen Quad Rendering is the final presentation stage in a volume rendering pipeline, responsible for transferring computed volume data from off-screen render targets to the default framebuffer or current context texture for display. It differs from standard blits by explicitly managing multiple draw buffers and allowing fragment shaders to sample intermediate textures for final compositing or debugging overlays. Choose this as the final step in a multi-pass deferred rendering pipeline to composite intermediate results (e.g., depth, normals, color) into the final image.

### [Rendering Pipeline Architecture](3059-rendering-pipeline-architecture.md)
Rendering Pipeline Architecture defines the structural organization of rendering stages, decomposing the image generation process into sequential, independent phases such as data traversal, interpolation, shading, and compositing. It solves the problem of managing complex visual effects and geometric projections by isolating their computational requirements into distinct passes, allowing for optimized memory access patterns and flexible appearance control. It differs from monolithic rendering approaches by explicitly separating geometric projection (e.g., depth testing, splatting) from visual appearance (e.g., shading, classification), enabling techniques like deferred shading or multi-pass accumulation. Choose this as a general architectural pattern for organizing complex rendering tasks.

### [Fragment List-Based Rendering Pipeline](3488-fragment-list-based-rendering-pipeline.md)
The Fragment List-Based Rendering Pipeline is a four-stage object-order rendering method designed for real-time smoke volume visualization. It processes geometry through Clear, Construction, Insertion, and Evaluation stages to maintain high accuracy while circumventing the self-intersection and global intersection artifacts common in raytracing approaches. It is distinguished from sibling pipelines by its explicit separation of fragment storage (Insertion) from final image synthesis (Evaluation), using fragment lists to accumulate per-pixel data before compositing. Choose this for real-time visualization of complex, self-intersecting volumetric geometry like smoke or fire.

### [Custom Pass Rendering](3629-custom-pass-rendering.md)
Custom Pass Rendering is a multi-pass, object-order rendering pipeline designed for high-performance visualization of large-scale volumetric data (specifically NanoVDB) and octree-based geometry within a modern graphics API context. It solves the problem of efficiently computing surface attributes (position, normal, material ID) and lighting effects (SSAO, shadows) for sparse volumetric datasets by decoupling geometric traversal from shading. Unlike monolithic ray-marching shaders, this method uses a sequence of specialized FullScreenPass stages to build intermediate G-buffers (hit position, filtered normals, ambient occlusion) before a final shading pass. It is distinct from [Plug-and-Play Ray Marching and Rendering](981-plug-and-play-ray-marching-and-rendering.md) by its explicit separation of traversal and lighting into discrete render passes, and from [Fragment List-Based Rendering Pipeline](3488-fragment-list-based-rendering-pipeline.md) by its reliance on screen-space fragment buffers rather than explicit primitive lists. Choose this for high-quality, real-time rendering of sparse, hierarchical volumetric data with complex lighting.

### Eye/Light/Composite Pass Pipeline
Renders volumetric data in three sequential passes: eye pass (direct lighting/color), light pass (opacity accumulation for shadows), and composite pass (blends results) [S2, unofficial]. The eye pass renders the volume to `m_eyeBuffer` with direct lighting using `m_eyePipeline` and `m_eyeSet`. The light pass accumulates opacity into `m_lightBuffer` using `m_lightPipeline` and `m_volSet`, transitioning layout from `ColorAttachmentOptimal` to `ShaderReadOnlyOptimal`. The composite pass binds `m_compositePipeline` and `m_compSet`, drawing a full-screen quad using `m_eyeBuffer` as a sampled texture. Buffers include `m_eyeBuffer`, `m_lightBuffer`, `m_volumeTex` (3D volume data, R8G8Unorm), and `m_tfTex` (transfer function) [S2, unofficial].

### OptiX Volume Rendering Pipeline
A volume rendering method implemented using NVIDIA OptiX. It uses a Ray Generation shader, Miss shaders for radiance and shadow, and Hit/Any-Hit/Intersection shaders for volume traversal and shading [S3, unofficial]. Shaders are initialized with `__raygen__default` for ray generation, `__miss__radiance` and `__miss__shadow` for miss shaders. The volume object group is configured with `group.type = VOLUME_STRUCTURED_REGULAR`, assigning hit group shaders: Closest Hit `__closesthit__volume_radiance` and `__closesthit__volume_shadow`, Any Hit `__anyhit__volume_radiance` and `__anyhit__volume_shadow`, and Intersection `__intersection__volume` [S3, unofficial].

## Background
The concept of decomposing rendering into passes has evolved from early direct volume rendering pipelines that processed voxels sequentially to modern deferred and multi-pass architectures that leverage GPU parallelism and intermediate framebuffers. The "Shading and Classification Pipeline" described in [S2, unofficial] represents an early standard for direct volume rendering, emphasizing the separation of color and opacity computation. Modern implementations, such as those using NanoVDB [S1, S2, unofficial] or OptiX [S3, unofficial], have adapted these principles to handle sparse data structures and hardware-accelerated ray tracing, respectively. The "msplat_render" alias [S1, unofficial] reflects the integration of these pipeline concepts into modern 3D Gaussian Splatting frameworks, where efficient forward passes are critical for training and inference.
