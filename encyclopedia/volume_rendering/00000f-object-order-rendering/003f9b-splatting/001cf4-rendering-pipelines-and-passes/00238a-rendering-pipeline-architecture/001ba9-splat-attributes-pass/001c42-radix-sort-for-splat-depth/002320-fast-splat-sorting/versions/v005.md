# Fast Splat Sorting

Also called: Depth and TileID Sorting, Split Radix Sort for Splatting, Separating Depth and Tile Sorting, Splat Sorting Dispatch

## Overview
Fast Splat Sorting is an optimization for volume rendering pipelines that replaces the single 48-bit combined tileID+depth radix sort with two sequential, smaller-key sorts: a 32-bit depth sort of visible splats followed by a 16-bit tileID sort of generated fragments [S2]. It sets itself apart from its parent [Radix Sort for Splat Depth](1207-radix-sort-for-splat-depth.md) by decoupling depth ordering from tile assignment, and from [Gaussian Sorting](2845-gaussian-sorting.md) by relying on explicit fragment duplication rather than implicit spatial partitioning. This separation reduces VRAM usage and computational complexity by leveraging the fact that the number of visible splats ($n$) is typically smaller than the number of fragments ($m$) [S2].

## How it works
The method replaces the standard 48-bit radix sort (used in 3DGS) which sorts fragments by a combined key of tileID and depth. Instead, it performs two distinct sorting passes.

**Inputs and Outputs:**
*   **Input:** A set of $n$ visible splats, each with a 32-bit depth value.
*   **Intermediate:** A set of $m$ fragments, where each fragment corresponds to a splat intersecting a specific tile. Each fragment carries a 16-bit tileID.
*   **Output:** An `ordering` array of indices, sorted such that splats are ordered by depth within each tile, and tiles are processed in raster order.

**Data Structures:**
1.  **Splat Data:** Each visible splat $i$ has a depth value $d_i$ (stored as `f32`).
2.  **Fragment Data:** Each fragment $j$ has a tileID $t_j$ (stored as `u16`).
3.  **Ordering Array:** `Uint32Array` of size $m$, storing indices to the fragment list.

**Steps:**
1.  **Depth Sort (Visible Splats):**
    *   Collect all $n$ visible splats.
    *   Perform a radix sort on the 32-bit depth values.
    *   Since the depth is a positive `f32`, its bit pattern preserves ordering when reinterpreted as `u32` [S2].
    *   This step produces a list of splats sorted by depth.
2.  **Fragment Generation:**
    *   For each splat in the depth-sorted list, determine which tiles it intersects.
    *   Generate a fragment for each intersected tile. Each fragment inherits the splat's depth and is assigned the tile's 16-bit ID.
    *   *Note:* The sources mention using tighter AABBs and approximate tile-ellipse intersection tests to reduce false-positive fragments, but the sorting logic itself assumes the fragments are already generated [S2].
3.  **TileID Sort (Fragments):**
    *   Perform a radix sort on the $m$ fragments using their 16-bit tileID as the key.
    *   Because the splats were already sorted by depth in Step 1, and radix sort is stable, the resulting list is sorted primarily by tileID (raster order) and secondarily by depth (front-to-back) [S2].

**Formulas:**
The total complexity is split as follows:
$$ T_{total} = T_{32-bit}(n) + T_{16-bit}(m) $$
Where $T_{48-bit}(m) \approx 3 \times T_{16-bit}(m)$ assuming linear scaling of radix sort runtime with the number of bits [S2].

**Parameters:**
*   `num_splats` ($u32$): Total number of visible splats $n$ [S1, unofficial].
*   `camera_x, camera_y, camera_z` ($f64$): Camera position [S1, unofficial].
*   `direction_x, direction_y, direction_z` ($f32$): Camera viewing direction [S1, unofficial].
*   `front_sort` ($bool$): Selects between 16-bit front sort and 32-bit sort [S1, unofficial].
*   `radial` ($bool$): Enables radial sorting mode [S1, unofficial].
*   `fast_sort` ($bool$): Enables fast sorting mode [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** The depth values must be positive `f32` for the bit-pattern reinterpretation trick to work correctly for sorting [S2].
*   **Fragment Count:** The number of fragments $m$ can be significantly larger than $n$. The 16-bit sort must handle this larger dataset efficiently [S2].
*   **False Positives:** Without tight bounding boxes, the fragment generation step may create unnecessary fragments, increasing $m$ and slowing down the 16-bit sort. The sources recommend using tight AABBs and approximate tile-ellipse intersection tests to mitigate this [S2].
*   **Validation:** The implementation must validate that range arrays and update arrays have consistent lengths and bounds to prevent out-of-bounds memory access [S1, unofficial].

## Subtopics

### [Two-Stage Sorting](9581-two-stage-sorting.md)
A variant that explicitly splits the generation of depth-sorted per-tile splat lists into two separate radix sort routines. It sets itself apart by decoupling depth ordering from tile assignment, allowing the use of smaller key sizes (32-bit and 16-bit) instead of a single large key. Choose this when VRAM usage is a constraint or when the hardware benefits from smaller key sorts.

## Operating characteristics
*   **Time Complexity:** The total sorting time is the sum of a 32-bit sort on $n$ splats and a 16-bit sort on $m$ fragments. Assuming linear scaling with bit-width, the 48-bit sort is approximately three times as expensive as the 16-bit sort [S2].
*   **Measured Performance:**
    *   **Berlin Scene:** 0.24 ms total (0.11 ms depth + 0.13 ms tileID) vs. 0.39 ms for 48-bit sort [S2].
    *   **Campus Scene:** 1.00 ms total (0.38 ms depth + 0.62 ms tileID) vs. 1.86 ms for 48-bit sort [S2].
*   **Scaling:** Performance improves significantly when the majority of splats contribute to the rendered image across multiple tiles, as the depth sort operates on a smaller set of visible splats [S2].
*   **Strengths:** Reduced computational complexity, lower VRAM usage due to smaller key sizes, and better GPU utilization by avoiding large 48-bit sorts.
*   **Limitations:** Requires an additional fragment generation step. Performance depends on the ratio of fragments to splats ($m/n$). If $m$ is very large, the 16-bit sort may become a bottleneck.
*   **When to Use:** Use when rendering large Gaussian Splat models where the 48-bit sort is a bottleneck and the number of visible splats is significantly smaller than the number of fragments.
*   **When Not to Use:** Avoid if the fragment generation step is already expensive or if the scene has a very high ratio of fragments to splats.

## Background
Fast Splat Sorting was introduced in the "Splatshop" paper (2025) as part of an efficient CUDA-based splat editing system [S2]. It was developed to address the performance limitations of the original 3DGS rendering pipeline, which used a combined 48-bit tileID+depth radix sort. The method leverages the observation that sorting visible splats by depth first, and then sorting the resulting fragments by tileID, is more efficient than sorting all fragments by a combined key. This approach is particularly beneficial for VR applications where workload imbalances can underutilize the GPU [S2].
