# Radix Sort for Splat Depth

Also called: 16-bit Radix Sort for Splatting, Depth Sorting via Radix Sort, Tsplat depth sort

## Overview
This method sorts projected splats by depth to establish the correct front-to-back rendering order required for alpha blending in object-order splatting. It leverages the property that positive 32-bit floating-point bit patterns preserve numerical ordering when reinterpreted as unsigned 32-bit integers, allowing the use of a 2-pass 16-bit radix sort on the depth values. This approach is chosen over comparison-based sorts because it achieves $O(n)$ time complexity with small constants and is consistently faster for typical splat counts (~100k–200k elements) [S1, unofficial].

## How it works
### Inputs and Outputs
- **Input**: An array of `n` projected splats. Each splat contains a `depth` field (f32) representing its distance from the camera.
- **Output**: The same array of splats, reordered such that splats with smaller depth values appear first (front-to-back).
- **Auxiliary Data**: Two histogram arrays `counts_lo` and `counts_hi` of size 65,536 each (u32), and an `offsets` array of size 65,536 (u32). An auxiliary buffer `aux` of size `n` to hold splats during the sort.

### Data Structures
- `counts_lo`: Histogram for the lower 16 bits of the depth bit pattern.
- `counts_hi`: Histogram for the upper 16 bits of the depth bit pattern.
- `offsets`: Prefix sum (scan) of the histogram counts, determining the starting index for each bucket.
- `projected`: The input/output array of splats.
- `aux`: Temporary storage for splats during the scatter phase.

### Algorithm Steps
1. **Edge Case**: If $n \le 1$, return immediately as the array is already sorted.
2. **Histogram Initialization**: Initialize `counts_lo` and `counts_hi` to zero.
3. **Histogram Population**: Iterate through each splat $i$ from $0$ to $n-1$:
   - Let $k$ be the bit pattern of `projected[i].depth` interpreted as a `u32`.
   - Increment `counts_lo[k & 0xFFFF]`.
   - Increment `counts_hi[k >> 16]`.
4. **Pass 1 (Low 16 bits)**:
   - Compute the prefix sum of `counts_lo` into `offsets`. The prefix sum should be exclusive or inclusive depending on scatter implementation; typically, the prefix sum gives the start index for each bucket.
   - Scatter splats from `projected` to `aux` based on the low 16 bits of their depth. For each splat $i$:
     - Let $k$ be the bit pattern of `projected[i].depth` as `u32`.
     - Let $idx = offsets[k \& 0xFFFF]$.
     - Set `aux[idx] = projected[i]`.
     - Increment `offsets[k & 0xFFFF]`.
5. **Pass 2 (High 16 bits)**:
   - Compute the prefix sum of `counts_hi` into `offsets`.
   - Scatter splats from `aux` to `projected` based on the high 16 bits of their depth. For each splat $i$:
     - Let $k$ be the bit pattern of `aux[i].depth` as `u32`.
     - Let $idx = offsets[k >> 16]$.
     - Set `projected[idx] = aux[i]`.
     - Increment `offsets[k >> 16]`.

### Pseudocode
```python
def sort_splats_by_depth(projected: list[Splat], aux: list[Splat], counts_lo: list[int], counts_hi: list[int], offsets: list[int]):
    n = len(projected)
    if n <= 1:
        return

    # Initialize histograms
    for i in range(65536):
        counts_lo[i] = 0
        counts_hi[i] = 0

    # Populate histograms
    for i in range(n):
        k = projected[i].depth.to_bits()  # Reinterpret f32 as u32
        counts_lo[k & 0xFFFF] += 1
        counts_hi[k >> 16] += 1

    # Pass 1: Sort by low 16 bits
    # Compute prefix sums for offsets
    current_sum = 0
    for i in range(65536):
        temp = counts_lo[i]
        counts_lo[i] = current_sum
        current_sum += temp
    
    # Scatter based on low bits
    for i in range(n):
        k = projected[i].depth.to_bits()
        idx = counts_lo[k & 0xFFFF]
        aux[idx] = projected[i]
        counts_lo[k & 0xFFFF] += 1

    # Pass 2: Sort by high 16 bits
    # Compute prefix sums for offsets
    current_sum = 0
    for i in range(65536):
        temp = counts_hi[i]
        counts_hi[i] = current_sum
        current_sum += temp

    # Scatter based on high bits
    for i in range(n):
        k = aux[i].depth.to_bits()
        idx = counts_hi[k >> 16]
        projected[idx] = aux[i]
        counts_hi[k >> 16] += 1
```

### Parameters
- **Parallel Sort Threshold**: If the number of splats is less than 50,000 or no thread pool is available, use a sequential radix sort. Otherwise, use a parallel unstable sort by key (e.g., `par_sort_unstable_by_key`) on the depth bits [S1, unofficial].

### Edge Cases and Pitfalls
- **Negative Depths**: The method relies on positive float bit patterns preserving order. Ensure depths are positive (e.g., by using view space z or clip space w) before converting to bits.
- **Precision**: Reinterpreting f32 as u32 works for positive numbers. If negative numbers are present, the bit pattern order is reversed for negatives, requiring special handling (e.g., flipping bits) which is not described in the primary source [S1, unofficial].
- **Boundaries**: The histogram size is fixed at 65,536 (16 bits). Ensure the bit masking and shifting operations correctly isolate the lower and upper 16 bits of the 32-bit integer.

## Subtopics

### Gaussian Sorting
Sorts Gaussians by their depth (z-coordinate) in camera space for front-to-back rendering. It transforms all Gaussian positions to camera space using the view matrix and then sorts the indices based on the z-component (index 2) of the camera-space positions [S2, unofficial].

### Fast Splat Sorting
A sorting optimization that splits the 48-bit radix sort of $m$ splat fragments into a 32-bit radix sort of $n$ splats and a 16-bit radix sort of $m$ fragments. It replaces the original 3DGS combined tileID+depth 48-bit radix sort with two sequential sorts: first by 32-bit depth values for visible splats, then by 16-bit tileIDs for tile-wise fragments. The implementation stops after sorting two 8-bit digits of the key, effectively performing a 16-bit sort instead of the full 48-bit sort used in 3DGS. The total sort complexity is split as: $48\text{-bit sort of } m \text{ fragments} = 32\text{-bit sort of } n \text{ splats} + 16\text{-bit sort of } m \text{ fragments}$. On the Berlin scene, this takes 0.24 ms (0.11 ms depth + 0.13 ms tileID) compared to 0.39 ms for the 48-bit sort. On the Campus scene, it takes 1.00 ms (0.38 ms depth + 0.62 ms tileID) compared to 1.86 ms [S3].

### Gaussian Splat Sorting
Sorts Gaussian splats front-to-back within tiles for correct alpha blending, using clip-space $w$ as a monotonic distance proxy to handle reverse-z projection. The steps are:
1. Calculate view depth: `float view_depth = max(0.0, clip_pos.w);`
2. Normalize depth to 0-1 range: `float depth01 = view_depth / (1.0 + view_depth);`
3. Quantize depth to 16-bit integer: `uint depth = uint(depth01 * 65535.0) & 0xFFFF;`
4. Create sort key by combining tile ID and depth: `uint key = (tile_id << 16) | depth;`
5. Store key and splat ID in sort buffers for the current tile iteration: `sort_keys[sort_buffer_offset] = key; sort_values[sort_buffer_offset] = id;` [S4, unofficial].

## Operating characteristics
- **Time Complexity**: $O(n)$ for the radix sort, where $n$ is the number of splats. The constant factor is small due to the fixed 16-bit pass structure.
- **Memory Complexity**: $O(n)$ for the auxiliary buffer `aux` and $O(1)$ for the histogram arrays (fixed size 65,536).
- **Performance**: Consistently 2 times faster than comparison-based sorts for ~100k–200k elements [S1, unofficial].
- **Strengths**: Linear time complexity, efficient for large numbers of splats, leverages GPU-friendly parallel operations.
- **Limitations**: Requires positive depth values for correct bit-pattern ordering. Not suitable for negative depths without modification.

## Background
This method is used in Gaussian Splatting rendering pipelines to ensure correct alpha blending by sorting splats by depth. It is implemented in projects like Tsplat [S1, unofficial] and is a standard technique in object-order splatting to handle the large number of primitives efficiently.
