# Fast Splat Sorting
Also called: Depth and TileID Sorting, Split Radix Sort for Splatting, Separating Depth and Tile Sorting

## Overview
Fast Splat Sorting is an optimization for the rendering pipeline of 3D Gaussian Splatting that replaces the original combined 48-bit radix sort with two sequential, narrower sorts: a 32-bit depth sort followed by a 16-bit tileID sort [S1]. It solves the performance bottleneck of sorting all splat fragments by their combined tile identifier and depth, which requires processing 48-bit keys for every fragment generated [S1]. By separating the visibility check (depth) from the spatial grouping (tileID), it reduces the computational cost of the sorting phase, leveraging the fact that the number of visible splats is typically smaller than the total number of fragments, and that radix sort runtime scales linearly with key width [S1].

## How it works
The method replaces the single 48-bit radix sort used in standard 3DGS [S1]. The 48-bit key in the original method consists of a combined tile identifier and depth component [S1]. Fast Splat Sorting decomposes this into two distinct passes [S1].

**Inputs and Outputs:**
*   **Input 1:** A list of $n$ visible splats, each with a 32-bit floating-point depth value $d$ [S1].
*   **Input 2:** A list of $m$ splat fragments (duplicates), each with a 16-bit unsigned integer tileID $t$ [S1].
*   **Output:** A list of $m$ fragments sorted first by depth (implicitly via the fragment's parent splat's depth) and then by tileID [S1].

**Data Structures:**
The algorithm operates on two separate arrays or buffers [S1]:
1.  **Visible Splats Buffer:** Contains $n$ entries [S1]. Each entry holds the splat's depth as a 32-bit float [S1].
2.  **Fragments Buffer:** Contains $m$ entries [S1]. Each entry holds the splat's tileID as a 16-bit unsigned integer [S1]. The fragments are generated after the depth sort, associated with their parent splat's depth [S1].

**Steps:**
1.  **Depth Sort:** Perform a radix sort on the $n$ visible splats using their 32-bit depth values as the key [S1]. This sorts the splats by depth [S1].
2.  **Fragment Generation:** For each sorted splat, determine which tiles it intersects [S1]. Create a fragment for each intersected tile [S1]. Store the fragment's tileID (16-bit) and a reference to the splat's depth [S1].
3.  **TileID Sort:** Perform a radix sort on the $m$ fragments using their 16-bit tileID as the key [S1]. This groups fragments by tile, allowing for efficient per-tile rasterization [S1].

**Formulas:**
The total complexity of the sorting phase is split as follows [S1]:
$$ T_{48\text{-bit}}(m) = T_{32\text{-bit}}(n) + T_{16\text{-bit}}(m) $$
Where:
*   $T_{32\text{-bit}}(n)$ is the time to sort $n$ items with 32-bit keys [S1].
*   $T_{16\text{-bit}}(m)$ is the time to sort $m$ items with 16-bit keys [S1].
*   The original 3DGS approach uses $T_{48\text{-bit}}(m)$, where the key width is 48 bits [S1].

**Parameters:**
*   **Depth Key Width:** 32 bits (float) [S1].
*   **TileID Key Width:** 16 bits (unsigned int) [S1].
*   **Radix Sort Implementation:** The 16-bit sort is implemented by stopping the radix sort after processing two 8-bit digits, effectively performing a 16-bit sort instead of the full 48-bit sort [S1].

**Edge Cases and Pitfalls:**
*   **Fragment Count:** The number of fragments $m$ is typically larger than the number of visible splats $n$ because one splat can intersect multiple tiles [S1]. However, the 16-bit sort is faster per item than the 48-bit sort [S1].
*   **False Positives/Negatives:** The fragment generation step may use an approximate tile-ellipse intersection test to reduce false positives (unnecessary fragments) [S1]. False negatives (missing fragments) are acceptable if they occur near the splat's edge where opacity is low [S1].

def radix_sort_32bit(items, key):
    # LSD radix sort for 32-bit keys (4 passes of 8-bit digits)
    buckets = [[] for _ in range(256)]
    for shift in (0, 8, 16, 24):
        for item in items:
            digit = (key(item) >> shift) & 0xFF
            buckets[digit].append(item)
        items = []
        for b in buckets:
            items.extend(b)
        buckets = [[] for _ in range(256)]
    return items

def radix_sort_16bit(items, key):
    # LSD radix sort for 16-bit keys (2 passes of 8-bit digits)
    buckets = [[] for _ in range(256)]
    for shift in (0, 8):
        for item in items:
            digit = (key(item) >> shift) & 0xFF
            buckets[digit].append(item)
        items = []
        for b in buckets:
            items.extend(b)
        buckets = [[] for _ in range(256)]
    return items

## Operating characteristics
*   **Time Complexity:** The sorting time is reduced because the 48-bit sort is replaced by a 32-bit sort and a 16-bit sort [S1]. Radix sort runtime scales linearly with the number of bits in the sorting key [S1].
*   **Measured Performance:** On the Berlin scene, the separated sort takes 0.24 ms total (0.11 ms depth + 0.13 ms tileID) compared to 0.39 ms for the 48-bit sort [S1]. On the Campus scene, it takes 1.00 ms total (0.38 ms depth + 0.62 ms tileID) compared to 1.86 ms for the 48-bit sort [S1].
*   **Strengths:** Significant performance improvement, especially when the majority of splats contribute to the rendered image across multiple tiles [S1].
*   **Limitations:** Requires two separate sorting passes and fragment generation between them. The implementation must handle the data movement between the depth-sorted splats and the tile-sorted fragments [S1].
*   **When to Use:** When rendering 3D Gaussian Splatting models and the sorting phase is a bottleneck [S1]. It is particularly effective when the number of visible splats is significantly smaller than the total number of fragments [S1].

## Background
Fast Splat Sorting was introduced in the paper "Splatshop: Efficiently Editing Large Gaussian Splat Models" [S1]. It is an optimization for the rendering pipeline of 3D Gaussian Splatting, which was originally proposed by Kerbl et al. in 2023 [S1]. The method addresses the inefficiency of the original 3DGS rendering pipeline, which uses a combined 48-bit radix sort for tileID and depth [S1].
