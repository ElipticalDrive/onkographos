# Gaussian Splat Sorting

Also called: Clip-space w depth sorting, Tile-based sorting using clip-space w

## Overview
Gaussian Splat Sorting is a tile-based sorting method used in 3D Gaussian Splatting (3DGS) to order splats front-to-back within each screen-space tile, ensuring correct alpha blending [S1, unofficial]. It differs from general radix sort approaches by using a single-pass key generation that packs tile ID and quantized clip-space $w$ depth into a 32-bit integer, leveraging the monotonicity of clip-space $w$ as a distance proxy [S1, unofficial].

## How it works
**Inputs:**
- View and projection matrices (via push constants or uniform buffer).
- Splat attributes: position, covariance (for projection), and unique ID.
- Screen resolution (to determine tile dimensions).

**Outputs:**
- Two parallel buffers: `sort_keys` (32-bit integers) and `sort_values` (splat IDs).
- `sort_keys` contains the composite sort key.
- `sort_values` contains the corresponding splat index.

**Data Structures:**
- `sort_keys`: Array of `uint32_t`. Layout: `(tile_id << 16) | depth_quantized`.
- `sort_values`: Array of `uint32_t` or `uint16_t` (depending on max splat count). Layout: Splat ID.

**Steps:**
1. **Project Splat:** Transform the 3D Gaussian center to clip space using the view-projection matrix. Let the clip-space position be $p_c = (x_c, y_c, z_c, w_c)$.
2. **Calculate View Depth:** Compute a monotonic depth proxy using clip-space $w$. Since $w_c$ increases with distance from the camera in standard right-handed clip space, it serves as a valid depth metric [S1, unofficial].
   $$ d_{view} = \max(0.0, w_c) $$
3. **Normalize Depth:** Map the view depth to the range $[0, 1)$ to prepare for quantization. The normalization function used is:
   $$ d_{01} = \frac{d_{view}}{1.0 + d_{view}} $$
   This function maps $[0, \infty)$ to $[0, 1)$ monotonically [S1, unofficial].
4. **Quantize Depth:** Convert the normalized depth to a 16-bit unsigned integer.
   $$ d_{16} = \text{uint32}(d_{01} \times 65535.0) \ \& \ 0xFFFF $$
5. **Determine Tile ID:** Calculate the tile ID for the splat based on its screen-space coordinates (after perspective division) and the tile resolution (e.g., $16 \times 16$ pixels). Let $t_x, t_y$ be the tile coordinates.
   $$ t_{id} = t_y \times N_{tiles\_x} + t_x $$
6. **Create Sort Key:** Combine the tile ID and quantized depth into a single 32-bit key. The tile ID occupies the upper 16 bits, and the depth occupies the lower 16 bits.
   $$ key = (t_{id} \ll 16) \ | \ d_{16} $$
   This packing ensures that sorting by `key` first groups splats by tile, then sorts them by depth within each tile [S1, unofficial].
7. **Store Results:** Write the key and the splat ID to the respective buffers at the current offset.
   $$ sort\_keys[offset] = key $$
   $$ sort\_values[offset] = splat\_id $$

**Pseudocode:**
```python
def gaussian_splat_sort(splats, view_matrix, projection_matrix, tile_size=16):
    """
    Sorts splats by tile and depth for alpha blending.
    splats: list of dicts with 'pos' (vec3), 'id' (int)
    Returns: keys (list of uint32), values (list of uint32)
    """
    keys = []
    values = []
    
    # Pre-calculate combined matrix
    vp_matrix = multiply_matrices(projection_matrix, view_matrix)
    
    # Determine tile grid dimensions (assuming standard viewport)
    # Note: Exact viewport dimensions are assumed to be known or passed
    # For this implementation, we assume a standard NDC to screen conversion
    # is handled implicitly by the tile ID calculation logic below.
    
    for splat in splats:
        # 1. Project to clip space
        pos_h = vec4(splat['pos'], 1.0)
        clip_pos = multiply_matrix_vector(vp_matrix, pos_h)
        w_c = clip_pos.w
        
        # 2. Calculate view depth
        view_depth = max(0.0, w_c)
        
        # 3. Normalize depth to 0-1
        depth01 = view_depth / (1.0 + view_depth)
        
        # 4. Quantize to 16-bit
        depth16 = uint32(depth01 * 65535.0) & 0xFFFF
        
        # 5. Calculate Tile ID
        # Perspective divide to get NDC
        if w_c == 0:
            continue # Degenerate case
        ndc_x = clip_pos.x / w_c
        ndc_y = clip_pos.y / w_c
        
        # Convert NDC [-1, 1] to screen coordinates [0, width/height]
        # Assuming standard OpenGL/DirectX viewport mapping
        # width and height are assumed to be known context variables
        screen_x = (ndc_x + 1.0) * 0.5 * viewport_width
        screen_y = (1.0 - ndc_y) * 0.5 * viewport_height # Y-flip for screen coords
        
        tile_x = uint32(screen_x) // tile_size
        tile_y = uint32(screen_y) // tile_size
        
        # Calculate total tiles per row
        tiles_per_row = viewport_width // tile_size
        tile_id = tile_y * tiles_per_row + tile_x
        
        # 6. Create Key
        key = (tile_id << 16) | depth16
        
        # 7. Store
        keys.append(key)
        values.append(splat['id'])
        
    return keys, values
```

**Parameters:**
- `tile_size`: Typically 16 or 32 pixels. Smaller tiles increase sorting overhead but improve cache locality for blending.
- `viewport_width`, `viewport_height`: Screen resolution.

**Edge Cases:**
- **$w_c \le 0$:** Splat is behind the camera or degenerate. Skip or handle as occluded.
- **Precision:** The normalization $d_{view} / (1.0 + d_{view})$ prevents overflow for large $w_c$ but compresses distant depth values. This is acceptable as relative depth ordering is preserved.
- **Tile Boundaries:** Ensure tile ID calculation matches the tiling strategy used in the subsequent sorting and blending passes.

## Subtopics

## Operating characteristics
- **Time Complexity:** $O(N)$ for key generation, where $N$ is the number of splats. The subsequent sorting step (typically radix sort or tile-based sort) is $O(N)$ or $O(N \log N)$ depending on the implementation, but the key generation is linear.
- **Memory Complexity:** $O(N)$ for storing keys and values.
- **Strengths:** Simple key generation; leverages hardware-friendly integer sorting; clip-space $w$ is already computed during projection.
- **Limitations:** Uses clip-space $w$ as a proxy for depth, which is monotonic but not linear with Euclidean distance. This is generally acceptable for alpha blending but may cause slight depth inaccuracies in extreme cases. The 16-bit depth quantization may lead to depth collisions for very distant splats.

## Background
This method is derived from implementations of 3D Gaussian Splatting in real-time renderers, such as the Godot engine port by ReconWorldLab [S1, unofficial]. It adapts the sorting requirements of 3DGS to fit within tile-based rendering architectures, where splats are processed per tile to optimize memory access patterns for alpha blending.
