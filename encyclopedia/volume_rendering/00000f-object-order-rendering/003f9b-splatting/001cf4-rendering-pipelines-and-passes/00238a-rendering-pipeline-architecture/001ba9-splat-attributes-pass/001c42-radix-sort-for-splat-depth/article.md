# Radix Sort for Splat Depth

Also called: 16-bit Radix Sort for Splatting, Depth Sorting via Radix Sort, Tsplat depth sort

## Overview
Sorts projected splats by depth to establish a front-to-back rendering order, which is critical for correct alpha blending in splatting pipelines. It sets itself apart from comparison-based sorts by leveraging the monotonic property of IEEE 754 floating-point bit patterns when reinterpreted as unsigned integers, achieving $O(n)$ time complexity with small constants [S1, unofficial]. This method is specifically optimized for the depth values generated by the [Splat Depth Pass](1078-splat-depth-pass.md) and serves as the foundational sorting mechanism for [Gaussian Sorting](2845-gaussian-sorting.md) and [Fast Splat Sorting](2953-fast-splat-sorting.md).

## How it works
**Inputs:**
- `projected`: An array of $n$ splat structures, each containing at least a `depth` field (f32).
- `scratch`: A temporary buffer of size $n$ for intermediate storage.

**Outputs:**
- `projected`: The same array, sorted in ascending order of depth (front-to-back).

**Data Structures:**
- `counts_lo`: Array of 65,536 `u32` integers, initialized to zero.
- `counts_hi`: Array of 65,536 `u32` integers, initialized to zero.
- `offsets`: Array of 65,536 `u32` integers, used for prefix sums.

**Algorithm Steps:**

1. **Edge Case:** If $n \le 1$, return immediately. [S1, unofficial]
2. **Bit Reinterpretation:** For each splat $i$ in `projected`, reinterpret its `depth` (f32) as a `u32` bit pattern $k$. This preserves the relative ordering for positive depths (standard view-space or clip-space depths where $w > 0$). [S1, unofficial]
3. **Histogram Construction:**
   - Extract low 16 bits: $k_{lo} = k \ \& \ 0xFFFF$.
   - Extract high 16 bits: $k_{hi} = k \gg 16$.
   - Increment `counts_lo[k_{lo}]` and `counts_hi[k_{hi}]`. [S1, unofficial]
4. **Pass 1 (Low 16 bits):**
   - Compute prefix sums of `counts_lo` into `offsets`. `offsets[x]` stores the starting index for bucket $x$. [S1, unofficial]
   - Scatter splats from `projected` to `scratch` based on $k_{lo}$. The destination index for splat $i$ is `offsets[k_{lo}]`, which is then incremented. [S1, unofficial]
5. **Pass 2 (High 16 bits):**
   - Reset `counts_hi` to zero (or use a new offset array). [G]
   - Compute prefix sums of `counts_hi` into `offsets`. [S1, unofficial]
   - Scatter splats from `scratch` back to `projected` based on $k_{hi}$. The destination index is `offsets[k_{hi}]`, incremented after placement. [S1, unofficial]

**Pseudocode:**

> **Unverified code.** The code below did not pass a test run against a reference implementation, or no test fits it, so it may contain errors.

```python
def radix_sort_splat_depth(projected: list[Splat], scratch: list[Splat]):
    n = len(projected)
    if n <= 1:
        return

    # Initialize histograms
    counts_lo = [0] * 65536
    counts_hi = [0] * 65536

    # Step 1: Build histograms
    for i in range(n):
        # Reinterpret f32 bits as u32
        k = float_to_bits(projected[i].depth)
        k_lo = k & 0xFFFF
        k_hi = (k >> 16) & 0xFFFF
        counts_lo[k_lo] += 1
        counts_hi[k_hi] += 1

    # Step 2: Pass 1 - Sort by low 16 bits
    # Compute prefix sums for offsets
    offsets = [0] * 65536
    current_sum = 0
    for i in range(65536):
        offsets[i] = current_sum
        current_sum += counts_lo[i]

    # Scatter to scratch
    for i in range(n):
        k = float_to_bits(projected[i].depth)
        k_lo = k & 0xFFFF
        idx = offsets[k_lo]
        scratch[idx] = projected[i]
        offsets[k_lo] += 1

    # Step 3: Pass 2 - Sort by high 16 bits
    # Reset counts_hi for prefix sum calculation (or use fresh offsets)
    # Note: counts_hi already holds the counts from Step 1.
    # We need to compute prefix sums on counts_hi.
    offsets = [0] * 65536
    current_sum = 0
    for i in range(65536):
        offsets[i] = current_sum
        current_sum += counts_hi[i]

    # Scatter back to projected
    for i in range(n):
        k = float_to_bits(scratch[i].depth)
        k_hi = (k >> 16) & 0xFFFF
        idx = offsets[k_hi]
        projected[idx] = scratch[i]
        offsets[k_hi] += 1

def float_to_bits(f: float) -> int:
    # Standard IEEE 754 reinterpretation
    import struct
    return struct.unpack('>I', struct.pack('>f', f))[0]
```

**Parameters:**
- **Parallel Threshold:** If $n < 50,000$ or no thread pool is available, use the sequential radix sort described above. Otherwise, use a parallel unstable sort (e.g., `par_sort_unstable_by_key`) on the depth bits. [S1, unofficial]

**Edge Cases and Pitfalls:**
- **Negative Depths:** The bit-pattern reinterpretation assumes positive floats. If depths are negative (e.g., standard clip-space $z$ before perspective divide or reverse-z without adjustment), the ordering is inverted or incorrect. Ensure depths are transformed to a positive, monotonic range (e.g., distance from camera) before sorting. [G]
- **Precision:** The 16-bit radix sort operates on the full 32-bit integer representation. It preserves the exact ordering of the floating-point values, avoiding precision loss associated with fixed-point quantization. [S1, unofficial]

## Subtopics

### [Gaussian Sorting](2845-gaussian-sorting.md)
Gaussian Sorting is the process of ordering 3D Gaussians by their distance from the camera to ensure correct alpha blending during rasterization. It solves the problem of rendering transparency correctly by establishing a front-to-back draw order, which is critical because Gaussians with non-zero opacity accumulate color based on their depth relative to the viewer. It sets itself apart from its parent [Radix Sort for Splat Depth](1207-radix-sort-for-splat-depth.md) by focusing on the specific application of 3D Gaussian Splatting, where the sorting is performed on a global index buffer of Gaussian attributes rather than just projected splat depths, and it differs from [Fast Splat Sorting](2953-fast-splat-sorting.md) by relying on explicit compute-shader-based radix sorting of indices rather than optimized spatial partitioning heuristics.

### [Fast Splat Sorting](2953-fast-splat-sorting.md)
Fast Splat Sorting is an optimization for volume rendering pipelines that replaces the single 48-bit combined tileID+depth radix sort with two sequential, smaller-key sorts: a 32-bit depth sort of visible splats followed by a 16-bit tileID sort of generated fragments. It sets itself apart from its parent [Radix Sort for Splat Depth](1207-radix-sort-for-splat-depth.md) by decoupling depth ordering from tile assignment, and from [Gaussian Sorting](2845-gaussian-sorting.md) by relying on explicit fragment duplication rather than implicit spatial partitioning. This separation reduces VRAM usage and computational complexity by leveraging the fact that the number of visible splats ($n$) is typically smaller than the number of fragments ($m$).

### [Gaussian Splat Sorting](3372-gaussian-splat-sorting.md)
Sorts Gaussian splats front-to-back within tiles for correct alpha blending, using clip-space w as a monotonic distance proxy to handle reverse-z projection.

### [32-bit Tile-Depth Pair Sorting](9408-32-bit-tile-depth-pair-sorting.md)
This method compresses the conventional 64-bit depth sorting key into 32 bits to reduce sorting traffic and the number of radix passes required for splat sorting. It differs from popular CUDA implementations that use 64-bit keys by mapping depth to a specific range where only the lower 23 mantissa bits vary, allowing tile IDs to occupy the minimum necessary higher bits. This optimization is particularly beneficial for Vulkan sorting implementations, which are often slower than CUDA's built-in sorting, while maintaining quality metrics comparable to 64-bit approaches.

## Operating characteristics
- **Time Complexity:** $O(n)$ for the radix sort, where $n$ is the number of splats. The constant factor is small due to the fixed 2-pass structure. [S1, unofficial]
- **Memory Complexity:** $O(n)$ for the scratch buffer and $O(1)$ (65,536 entries) for the histogram/offset arrays. [S1, unofficial]
- **Performance:** Consistently 2 times faster than comparison-based sorts for $n \approx 100,000–200,000$ elements. [S1, unofficial]
- **Strengths:** Deterministic performance, no recursion depth issues, efficient on GPUs and multi-core CPUs. [S1, unofficial]
- **Limitations:** Requires a scratch buffer of size $n$. Not suitable for negative depths without transformation. [S1, unofficial]
- **When to Use:** When sorting large numbers of splats for alpha blending. [S1, unofficial]
- **When Not to Use:** When $n$ is very small ($< 50$), where overhead dominates, or when parallel hardware is unavailable and $n$ is large (use sequential fallback). [S1, unofficial]

## Background
The method originates from the Tsplat project, which implements Gaussian splatting in a terminal environment. It was developed to provide a fast, CPU-friendly sorting mechanism that avoids the overhead of GPU-specific sorting libraries while maintaining correctness for alpha blending. The approach leverages the well-known property of IEEE 754 floats that their bit patterns are lexicographically ordered for positive values. [S1, unofficial]
