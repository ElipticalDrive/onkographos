# Fast Splat Sorting
Also called: Depth and TileID Sorting, Split Radix Sort for Splatting, Separating Depth and Tile Sorting

## Overview
Fast Splat Sorting is an optimization for the rendering pipeline of 3D Gaussian Splatting that replaces the original combined 48-bit radix sort with two sequential, narrower sorts: a 32-bit depth sort followed by a 16-bit tileID sort. It solves the performance bottleneck of sorting all splat fragments by their combined tile identifier and depth, which requires processing 48-bit keys for every fragment generated. By separating the visibility check (depth) from the spatial grouping (tileID), it reduces the computational cost of the sorting phase, leveraging the fact that the number of visible splats is typically smaller than the total number of fragments, and that radix sort runtime scales linearly with key width.

## How it works
The method replaces the single 48-bit radix sort used in standard 3DGS [S1]. The 48-bit key in the original method consists of a 32-bit tileID and a 16-bit depth component (or vice versa, depending on implementation, but the total width is 48 bits) [S1]. Fast Splat Sorting decomposes this into two distinct passes [S1].

**Inputs and Outputs:**
*   **Input 1:** A list of $n$ visible splats, each with a 32-bit floating-point depth value $d$.
*   **Input 2:** A list of $m$ splat fragments (duplicates), each with a 16-bit unsigned integer tileID $t$.
*   **Output:** A list of $m$ fragments sorted first by depth (implicitly via the fragment's parent splat's depth) and then by tileID.

**Data Structures:**
The algorithm operates on two separate arrays or buffers:
1.  **Visible Splats Buffer:** Contains $n$ entries. Each entry holds the splat's depth as a 32-bit float.
2.  **Fragments Buffer:** Contains $m$ entries. Each entry holds the splat's tileID as a 16-bit unsigned integer. The fragments are generated after the depth sort, associated with their parent splat's depth.

**Steps:**
1.  **Depth Sort:** Perform a radix sort on the $n$ visible splats using their 32-bit depth values as the key. This sorts the splats from front to back (or back to front, depending on the compositing order required).
2.  **Fragment Generation:** For each sorted splat, determine which tiles it intersects. Create a fragment for each intersected tile. Store the fragment's tileID (16-bit) and a reference to the splat's depth.
3.  **TileID Sort:** Perform a radix sort on the $m$ fragments using their 16-bit tileID as the key. This groups fragments by tile, allowing for efficient per-tile rasterization.

**Formulas:**
The total complexity of the sorting phase is split as follows [S1]:
$$ T_{total} = T_{32-bit}(n) + T_{16-bit}(m) $$
Where:
*   $T_{32-bit}(n)$ is the time to sort $n$ items with 32-bit keys.
*   $T_{16-bit}(m)$ is the time to sort $m$ items with 16-bit keys.
*   The original 3DGS approach uses $T_{48-bit}(m)$, where the key width is 48 bits.

**Parameters:**
*   **Depth Key Width:** 32 bits (float).
*   **TileID Key Width:** 16 bits (unsigned int).
*   **Radix Sort Implementation:** The 16-bit sort is implemented by stopping the radix sort after processing two 8-bit digits [S1].

**Edge Cases and Pitfalls:**
*   **Precision:** The depth sort uses 32-bit floats. Standard float bit-pattern reordering (reinterpreting as uint) works for positive depths, which is standard in view-space rendering [S1].
*   **Fragment Count:** The number of fragments $m$ is typically larger than the number of visible splats $n$ because one splat can intersect multiple tiles. However, the 16-bit sort is faster per item than the 48-bit sort.
*   **False Positives/Negatives:** The fragment generation step may use an approximate tile-ellipse intersection test to reduce false positives (unnecessary fragments) [S1]. False negatives (missing fragments) are acceptable if they occur near the splat's edge where opacity is low [S1].

## Operating characteristics
*   **Time Complexity:** The sorting time is reduced because the 48-bit sort is replaced by a 32-bit sort and a 16-bit sort. Radix sort runtime scales linearly with the number of bits in the sorting key [S1].
*   **Measured Performance:** On the Berlin scene, the separated sort takes 0.24 ms total (0.11 ms depth + 0.13 ms tileID) compared to 0.39 ms for the 48-bit sort. On the Campus scene, it takes 1.00 ms total (0.38 ms depth + 0.62 ms tileID) compared to 1.86 ms for the 48-bit sort [S1].
*   **Strengths:** Significant performance improvement, especially when the majority of splats contribute to the rendered image across multiple tiles [S1].
*   **Limitations:** Requires two separate sorting passes and fragment generation between them. The implementation must handle the data movement between the depth-sorted splats and the tile-sorted fragments.
*   **When to Use:** When rendering 3D Gaussian Splatting models and the sorting phase is a bottleneck. It is particularly effective when the number of visible splats is significantly smaller than the total number of fragments.

## Background
Fast Splat Sorting was introduced in the paper "Splatshop: Efficiently Editing Large Gaussian Splat Models" [S1]. It is an optimization for the rendering pipeline of 3D Gaussian Splatting, which was originally proposed by Kerbl et al. in 2023 [S1]. The method addresses the inefficiency of the original 3DGS rendering pipeline, which uses a combined 48-bit radix sort for tileID and depth. The separation of the sort allows for more efficient use of GPU resources, particularly in VR contexts where workload imbalance can be mitigated by concurrent CUDA streams [S1].
