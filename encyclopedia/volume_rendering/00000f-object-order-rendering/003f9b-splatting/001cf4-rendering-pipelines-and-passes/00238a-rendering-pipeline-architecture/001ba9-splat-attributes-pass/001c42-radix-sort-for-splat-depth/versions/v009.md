# Radix Sort for Splat Depth

Also called: 16-bit Radix Sort for Splatting, Depth Sorting via Radix Sort, Tsplat depth sort

## Overview
This method sorts projected 3D Gaussian splats by their depth values to establish a front-to-back rendering order, which is critical for correct alpha blending of translucent splats [S1, unofficial]. It distinguishes itself from comparison-based sorts by leveraging the bit-pattern ordering of IEEE 754 floating-point numbers to achieve $O(n)$ time complexity with small constants, resulting in performance that is consistently 2 times faster for ~100k–200k elements [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A list of `projected` splats, where each splat contains a `depth` field (f32).
- Output: The `projected` list sorted in ascending order of `depth` (front-to-back).
- Auxiliary: `aux` buffer of same size as `projected`; `counts_lo`, `counts_hi` histogram arrays; `offsets` prefix sum array.

**Data Structures:**
- `projected`: Array of splat structs. Each struct has `depth: f32`.
- `counts_lo`, `counts_hi`: Arrays of `u32` with size 65,536 (2^16).
- `offsets`: Array of `u32` with size 65,536.
- `aux`: Array of splat structs, same size as `projected`.

**Parameters:**
- Parallel sort threshold: 50,000 splats. If splat count < 50,000 or no thread pool is available, use sequential radix sort. Otherwise, use `par_sort_unstable_by_key` on depth bits [S1, unofficial].

**Algorithm Steps:**
1. **Edge Case:** If the number of splats is $\le 1$, return immediately.
2. **Histogram Initialization:** Initialize `counts_lo` and `counts_hi` to zero.
3. **Histogram Population:** Iterate through each splat in `projected`:
   - Let $k$ be the bit pattern of `splat.depth` reinterpreted as a `u32`.
   - Increment `counts_lo[(k & 0xFFFF)]`.
   - Increment `counts_hi[(k >> 16)]`.
4. **Pass 1 (Low 16 bits):**
   - Compute prefix sums of `counts_lo` into `offsets`. The prefix sum at index $i$ represents the starting position for bucket $i$.
   - Scatter splats from `projected` to `aux` based on the low 16 bits of their depth bit pattern ($k \& 0xFFFF$). Use `offsets` to determine the destination index, then increment the offset for that bucket.
5. **Pass 2 (High 16 bits):**
   - Compute prefix sums of `counts_hi` into `offsets`.
   - Scatter splats from `aux` back to `projected` based on the high 16 bits of their depth bit pattern ($k >> 16$). Use `offsets` to determine the destination index, then increment the offset for that bucket.

**Pseudocode:**
```python
def sort_by_depth(projected: List[Splat], scratch: ScratchBuffers) -> None:
    n = len(projected)
    if n <= 1:
        return

    # Check for parallel execution threshold
    if n >= 50000 and thread_pool_available():
        # Use parallel unstable sort on bit patterns
        # This is a library call; implementation details depend on the parallel runtime
        par_sort_unstable_by_key(projected, key=lambda s: s.depth.to_bits())
        return

    # Sequential 16-bit Radix Sort
    aux = scratch.aux_buffer
    counts_lo = scratch.counts_lo  # size 65536
    counts_hi = scratch.counts_hi  # size 65536
    offsets = scratch.offsets      # size 65536

    # Reset histograms
    for i in range(65536):
        counts_lo[i] = 0
        counts_hi[i] = 0

    # Populate histograms
    for splat in projected:
        k = splat.depth.to_bits()  # Reinterpret f32 bits as u32
        counts_lo[k & 0xFFFF] += 1
        counts_hi[k >> 16] += 1

    # Pass 1: Sort by low 16 bits
    # Compute prefix sums for offsets
    offsets[0] = 0
    for i in range(1, 65536):
        offsets[i] = offsets[i-1] + counts_lo[i-1]

    # Scatter to aux
    for splat in projected:
        k = splat.depth.to_bits()
        bucket = k & 0xFFFF
        idx = offsets[bucket]
        aux[idx] = splat
        offsets[bucket] += 1

    # Pass 2: Sort by high 16 bits
    # Compute prefix sums for offsets
    offsets[0] = 0
    for i in range(1, 65536):
        offsets[i] = offsets[i-1] + counts_hi[i-1]

    # Scatter back to projected
    for splat in aux:
        k = splat.depth.to_bits()
        bucket = k >> 16
        idx = offsets[bucket]
        projected[idx] = splat
        offsets[bucket] += 1
```

**Edge Cases and Pitfalls:**
- **Float Bit Pattern:** This method relies on positive float bit patterns preserving ordering when reinterpreted as `u32`. If negative depths are possible, they must be handled separately (e.g., by flipping the sign bit) to maintain order [S1, unofficial].
- **Precision:** The method uses the full 32-bit float representation. No precision loss occurs during the bit reinterpretation, but sorting stability is not guaranteed unless the secondary key (e.g., original index) is included, which is not done in this basic variant [S1, unofficial].

## Subtopics

### [Gaussian Sorting](2845-gaussian-sorting.md)
Gaussian Sorting orders 3D Gaussians by their distance from the camera to ensure correct alpha blending during rasterization. It solves the transparency accumulation problem by establishing a front-to-back draw order, which is critical because Gaussians with non-zero opacity must be rendered in depth order. It builds on [Radix Sort for Splat Depth](1207-radix-sort-for-splat-depth.md) by applying the radix sort to a global index buffer of Gaussian attributes rather than just projected splat depths.

### [Fast Splat Sorting](2953-fast-splat-sorting.md)
Fast Splat Sorting is an optimization for volume rendering pipelines that replaces the single 48-bit combined tileID+depth radix sort with two sequential, smaller-key sorts: a 32-bit depth sort of visible splats followed by a 16-bit tileID sort of generated fragments. It sets itself apart from its parent [Radix Sort for Splat Depth](1207-radix-sort-for-splat-depth.md) by decoupling depth ordering from tile assignment, and from [Gaussian Sorting](2845-gaussian-sorting.md) by relying on explicit fragment duplication rather than implicit spatial partitioning. This separation reduces computational complexity by leveraging the fact that the number of visible splats ($n$) is typically smaller than the number of fragments ($m$).

### [Gaussian Splat Sorting](3372-gaussian-splat-sorting.md)
Gaussian Splat Sorting sorts projected 3D Gaussian splats front-to-back within screen-space tiles to enable correct alpha blending. It differs from its parent [Radix Sort for Splat Depth](1207-radix-sort-for-splat-depth.md) by operating on a per-tile basis using a combined tile-ID and depth key, and from [Gaussian Sorting](2845-gaussian-sorting.md) by relying on a simple monotonic depth proxy rather than complex geometric comparisons.

### [Default Camera Sort](7960-default-camera-sort.md)
Default Camera Sort is a compositing technique for oriented Gaussian ellipses (splats) that sorts them back-to-front relative to a specific camera viewpoint to ensure correct translucent blending. It differs from its siblings by automatically binding the sort order to the active scene camera without requiring explicit provider configuration, whereas [Radix Sort for Splat Depth](1207-radix-sort-for-splat-depth.md) provides the underlying low-level sorting primitive and [Fast Splat Sorting](2953-fast-splat-sorting.md) or [Gaussian Splat Sorting](3372-gaussian-splat-sorting.md) may offer alternative optimization strategies for specific hardware or scene densities.

### [32-bit Tile-Depth Pair Sorting](9408-32-bit-tile-depth-pair-sorting.md)
This method compresses the conventional 64-bit depth sorting key into 32 bits to reduce sorting traffic and the number of radix passes required for splat sorting. It differs from popular CUDA implementations that use 64-bit keys by mapping depth to a specific range where only the lower 23 mantissa bits vary, allowing tile IDs to occupy the minimum necessary higher bits. This optimization is particularly beneficial for Vulkan sorting implementations, which are often slower than CUDA's built-in sorting, while maintaining quality metrics comparable to 64-bit approaches.

### DistWar
DistWar is a method that accelerates sorting by exploiting hardware-accelerated visibility ordering in the rasterizer to perform a fast depth test and bypass the CUDA radix sort [S2, unofficial].

## Operating characteristics
- **Time Complexity:** $O(n)$ for the radix sort passes, where $n$ is the number of splats. The constant factor is small due to the fixed 2-pass structure.
- **Memory Complexity:** $O(n)$ for the auxiliary buffer `aux` and $O(1)$ for the histogram arrays (fixed size 65,536).
- **Performance:** Consistently 2 times faster than comparison-based sorts for ~100k–200k elements [S1, unofficial].
- **Strengths:** Linear time complexity, predictable performance, no recursion depth issues, efficient use of cache due to sequential memory access in scatter/gather phases.
- **Limitations:** Requires positive depth values or explicit handling of negative depths. Not stable by default. Parallelization threshold must be tuned for specific hardware.
- **When to Use:** When sorting large numbers of splats for front-to-back rendering where performance is critical and depth values are positive.
- **When Not to Use:** When stability is required without additional overhead, or when depth values include negative numbers that are not handled by bit manipulation.

## Background
This method is described in the context of the Tsplat project, which aims to run Gaussian splatting in a terminal environment [S1, unofficial]. It is part of the broader effort to optimize 3D Gaussian Splatting rasterization, as surveyed in recent literature [S2, unofficial]. The use of radix sort for depth sorting in splatting is a common optimization to replace slower comparison-based sorts.
