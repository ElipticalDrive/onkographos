# Three-Pass GPU Point Rendering Pipeline
Also called: Hardware Accelerated Point Splatting Pipeline

## Overview
The Three-Pass GPU Point Rendering Pipeline is a hardware-accelerated method for rendering point clouds by decomposing the splatting process into distinct depth, accumulation, and normalization stages [S1, unofficial]. It solves the problem of correctly blending overlapping point contributions with proper occlusion handling, which is difficult to achieve in a single pass due to the non-linear nature of depth sorting and alpha blending [S1, unofficial]. It differs from the Single-Pass Splat Rendering Pipeline by explicitly separating the depth test from the color accumulation to ensure correct occlusion, and from the Splat Attributes Pass by performing the final weighted sum and normalization in dedicated framebuffer operations rather than deferred attribute computation [S1, unofficial].

## How it works
**Inputs:**
*   A set of 3D points, each defined by position $\mathbf{p}_i$, radius $r_i$, and color $\mathbf{c}_i$.
*   Camera parameters (projection matrix $\mathbf{M}$, view matrix).
*   Framebuffer attachments: Depth buffer, Color buffer (RGBA), and optionally a Weight buffer (if not combined with Color).

**Outputs:**
*   A final 2D image where each pixel contains the accumulated color of visible splats.

**Data Structures:**
*   **Depth Buffer:** Stores the minimum depth $z$ of rendered fragments. Initialized to $+\infty$ (or max float).
*   **Color Buffer:** Stores the accumulated weighted color $\sum \mathbf{c}_i w_i$. Initialized to $(0,0,0,0)$.
*   **Weight Buffer (Implicit or Explicit):** Stores the accumulated filter weights $\sum w_i$. In the standard implementation described in [S1, unofficial], this is often stored in the Alpha channel of the Color Buffer or a separate buffer.

**Steps:**

1.  **Pass 1: Depth Offset Rendering**
    *   Render the scene using a simple depth-only shader.
    *   The depth value written to the depth buffer is slightly offset along the viewing ray to prevent z-fighting and ensure correct occlusion culling in subsequent passes. The offset is typically small and positive along the view direction.
    *   No color or weight updates occur.

2.  **Pass 2: Splat Accumulation**
    *   Render splats using **OpenGL points** (or equivalent GPU primitive) instead of quads or triangles [S1, unofficial].
    *   **Vertex Shader:** Computes the 2D screen-space position and the variance matrix (or radius) of the splat. The variance matrix $\mathbf{R}$ is approximated using the projective mapping $\mathbf{M}_k$ [S1, unofficial]. Note: Inversion of $\mathbf{M}_k$ can be numerically ill-conditioned if the splat degenerates into a line segment [S1, unofficial].
    *   **Fragment Shader:**
        *   Compute the radial distance $d$ from the fragment to the splat center.
        *   Compute the weight $w_i$ based on the distance $d$ and the splat radius $r_i$ (e.g., using a Gaussian or box filter).
        *   Perform a depth test against the depth buffer from Pass 1.
        *   If the test passes, accumulate the weighted color into the Color Buffer: $\mathbf{C}_{new} = \mathbf{C}_{old} + \mathbf{c}_i w_i$.
        *   Accumulate the weight into the Weight Buffer (or Alpha channel): $W_{new} = W_{old} + w_i$.
        *   **Crucially:** Do not update the depth buffer in this pass (depth writes disabled) to allow all overlapping splats to contribute to the accumulation, relying on the depth test for occlusion culling.

3.  **Pass 3: Normalization**
    *   Render a full-screen quad (or iterate over pixels).
    *   For each pixel, retrieve the accumulated color $\mathbf{C}$ and accumulated weight $W$.
    *   Compute the final color: $\mathbf{C}_{final} = \frac{\mathbf{C}}{W}$.
    *   Handle the case where $W \approx 0$ (no splats covered the pixel) by setting $\mathbf{C}_{final}$ to a background color or transparent.

**Pseudocode:**

```python
# Pass 1: Depth Offset
def pass1_depth_offset(points, camera):
    for point in points:
        # Project point to screen space
        screen_pos = camera.project(point.position)
        # Calculate depth offset along viewing ray
        depth_offset = calculate_viewing_ray_offset(point.position, camera)
        # Write to depth buffer
        depth_buffer[screen_pos] = min(depth_buffer[screen_pos], point.depth + depth_offset)

# Pass 2: Accumulation
def pass2_accumulate(points, camera, color_buffer, weight_buffer):
    # Enable depth test, disable depth write, enable blending
    for point in points:
        # Compute splat radius and variance in screen space
        # This involves inverting the projective mapping Mk [S1, unofficial]
        radius = compute_splat_radius(point, camera)
        
        # Rasterize splat as a point/quad
        for fragment in splat_fragments(point, radius):
            # Compute weight based on distance from center
            dist = distance(fragment.pos, point.screen_center)
            weight = filter_function(dist, radius)
            
            # Depth test against Pass 1 depth buffer
            if fragment.depth < depth_buffer[fragment.pos]:
                # Accumulate color and weight
                color_buffer[fragment.pos] += point.color * weight
                weight_buffer[fragment.pos] += weight

# Pass 3: Normalization
def pass3_normalize(color_buffer, weight_buffer, background_color):
    for pixel in all_pixels:
        accumulated_color = color_buffer[pixel]
        accumulated_weight = weight_buffer[pixel]
        
        if accumulated_weight > epsilon:
            final_color[pixel] = accumulated_color / accumulated_weight
        else:
            final_color[pixel] = background_color
```

**Parameters:**
*   **Filter Function:** Typically a Gaussian $w = e^{-d^2 / 2\sigma^2}$ or a box filter. Not given in the sources.
*   **Depth Offset:** Small value along the viewing ray. Not given in the sources.
*   **Epsilon:** Small value to prevent division by zero in Pass 3. Not given in the sources.

**Edge Cases and Pitfalls:**
*   **Numerical Instability:** Inverting the projective mapping $\mathbf{M}_k$ in the vertex shader can be ill-conditioned if the splat is nearly parallel to the view plane (degenerating into a line segment) [S1, unofficial].
*   **Z-Fighting:** The depth offset in Pass 1 must be carefully chosen to avoid z-fighting while ensuring correct occlusion.
*   **Weight Accumulation Precision:** Accumulating weights in floating-point buffers can lead to precision issues for very large point clouds. Not given in the sources.

## Subtopics

### Standard Point Splatting Assembly
This variant refers to the core assembly step where point colors are written to a canvas based on depth sorting and a fixed or implicit radius [S2, unofficial]. It differs from the GPU pipeline by explicitly sorting points by depth and iterating in ascending order, writing color only if the point's depth is less than the current depth at that pixel [S2, unofficial]. It is chosen when software-based rendering or explicit depth sorting is required. The implementation initializes `depth_canvas` with `inf`, `color_canvas` and `label_canvas` with zeros, and `index_canvas` with -1. It iterates through sorted points, updating the canvas if the depth test passes, and finally masks out unwritten pixels [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N \cdot R^2)$ per pass, where $N$ is the number of points and $R$ is the average splat radius in pixels. The three-pass structure adds a constant factor of 3 to the rendering time.
*   **Memory Complexity:** $O(W \cdot H)$ for the framebuffers (Depth, Color, Weight), where $W$ and $H$ are the image dimensions.
*   **Strengths:** Correctly handles occlusion and overlapping splats with proper depth testing. Leverages hardware rasterization for efficient fragment processing.
*   **Limitations:** Requires three full render passes, which can be slower than a single-pass approach if occlusion is not a major factor. The depth offset in Pass 1 can introduce artifacts if not tuned correctly. Numerical instability in variance matrix computation can occur.
*   **When to Use:** When accurate occlusion and blending of large point clouds are required, and hardware acceleration is available.
*   **When Not to Use:** For simple point rendering with minimal overlap, or when memory bandwidth is a critical bottleneck due to the multiple framebuffer reads/writes.

## Background
The method was described in the paper "Perspective Accurate Splatting" [S1, unofficial]. It builds on previous methods for hardware-accelerated point splatting [1, 6, 22] (cited in [S1, unofficial]). The key innovation is the use of a novel approximation for the variance matrix of the reconstruction kernel, which requires inverting the projective mapping. The pipeline structure (depth, accumulation, normalization) is a common pattern in GPU-based point rendering to handle the complexities of perspective-correct blending.
