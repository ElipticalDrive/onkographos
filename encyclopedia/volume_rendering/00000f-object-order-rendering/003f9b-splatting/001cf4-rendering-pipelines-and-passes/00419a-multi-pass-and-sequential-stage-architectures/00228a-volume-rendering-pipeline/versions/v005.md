# Volume Rendering Pipeline

Also called: CRIO Process, Classification, Reflection, Illumination, Opacity, Rendering Stages, Shading and Classification Pipeline, VolumeRenderer forward method

## Overview
The Volume Rendering Pipeline is a standard implementation structure for direct volume rendering that decomposes the image formation process into logical, sequential stages: data traversal, interpolation, gradient computation, classification, shading, and compositing [S1, unofficial]. Unlike methods that fit geometric primitives to the data, this pipeline forms images by directly shading each sample and projecting it onto the picture plane, using local gradient vectors as surface normals for shading and separate classification operators for opacity [S2, unofficial]. It treats each volume sample as a reflective, light-emitting, semi-transparent cloud, assuming every sample point acts as both an absorber and an emitter [S4, unofficial][S5, unofficial].

## How it works
The pipeline processes a 3D scalar field to produce a 2D image. The core logic follows a specific order of operations, often referred to as the "Shading and Classification Pipeline" [S2, unofficial].

### Inputs and Outputs
*   **Input:** An array of acquired scalar values $f_0(x_i)$ at voxel locations $x_i = (x_i, y_j, z_k)$ [S3, unofficial].
*   **Output:** A single color $C_\lambda(u_i)$ and opacity $\alpha(u_i)$ for each pixel location $u_i = (u_i, v_j)$ [S3, unofficial].

### Data Structures
1.  **Scalar Field:** A 3D grid of scalar values.
2.  **Prepared Values Array ($f_1$):** An array of the same dimensions as the input, storing processed scalar values after data preparation [S3, unofficial].
3.  **Color Array ($c_\lambda$):** An array storing RGB colors for each voxel, derived from the shading model [S3, unofficial].
4.  **Opacity Array ($\alpha$):** An array storing opacity values for each voxel, derived from the classification procedure [S3, unofficial].
5.  **Ray Bundle:** A collection of rays defined by origin and direction, typically one per pixel [S5, unofficial].

### Numbered Steps

1.  **Data Traversal and Preparation:**
    The process begins with data traversal, which depends on the underlying organization of the 3D scalar field [S1, unofficial]. This step may include corrections for non-orthogonal sampling grids, patient motion, contrast enhancement, and interpolation of additional samples [S3, unofficial]. The output is an array of prepared values $f_1(x_i)$ [S3, unofficial].

2.  **Shading (Color Computation):**
    The prepared values $f_1(x_i)$ are input into a shading model to yield an array of voxel colors $c_\lambda(x_i)$, where $\lambda \in \{r, g, b\}$ [S3, unofficial]. Surface shading calculations are performed at every voxel, using local gradient vectors as surface normals [S2, unofficial].

3.  **Classification (Opacity Computation):**
    In a separate step, the prepared values $f_1(x_i)$ are input into a classification procedure to yield an array of voxel opacities $\alpha(x_i)$ [S3, unofficial]. Classification determines discrete values for primary properties (emitted color, reflected color, opacity) based on sample features such as density value or gradient magnitude [S4, unofficial]. Non-binary classification operators ensure that small or poorly defined features are not lost [S2, unofficial].

4.  **Gradient Computation:**
    The gradient of the scalar field is computed at sample positions to add visual cues, allowing for directional light or Phong shading [S1, unofficial]. This is typically approximated by central differences [S1, unofficial].

5.  **Ray Casting and Resampling:**
    Rays are cast from the observer eyepoint [S3, unofficial]. For each ray, a vector of sample colors $c_\lambda(\tilde{x}_i)$ and opacities $\alpha(\tilde{x}_i)$ is computed by resampling the voxel database at $K$ evenly spaced locations $\tilde{x}_i$ along the ray [S3, unofficial]. The values are obtained by tri-linearly interpolating from the colors and opacities in the eight voxels closest to each sample location $\tilde{x}_i$ [S3, unofficial].

6.  **Compositing:**
    A fully opaque background of color $c_{bkg, \lambda}$ is draped behind the dataset [S3, unofficial]. The resampled colors and opacities are merged with each other and with the background in back-to-front order to yield a single color $C_\lambda(u_i)$ for the ray/pixel [S3, unofficial].

### Formulas

**Transparency Formula (Compositing):**
The color $C_{out, \lambda}(u_i)$ of the ray as it leaves a sample location is related to the color $C_{in, \lambda}(u_i)$ of the ray as it enters and the sample's color $c_\lambda(\tilde{x}_i)$ and opacity $\alpha(\tilde{x}_i)$ by:

$$
C_{out, \lambda}(u_i) = C_{in, \lambda}(u_i)(1 - \alpha(\tilde{x}_i)) + c_\lambda(\tilde{x}_i)\alpha(\tilde{x}_i)
$$

This is applied recursively from back to front [S3, unofficial].

**Initial Conditions:**
*   The ray enters the dataset with color $C_{in, \lambda}(u_i) = c_{bkg, \lambda}$ [S3, unofficial].
*   The background is fully opaque: $\alpha_{bkg} = 1$ [S3, unofficial].

### Parameters
*   **$K$:** The number of evenly spaced sample locations along a viewing ray [S2, unofficial].
*   **Primary Properties:** Emitted color, reflected color, and opacity [S4, unofficial].

### Edge Cases and Pitfalls
*   **Precision:** The transparency formula involves floating-point arithmetic. Accumulating errors over many samples can lead to inaccuracies.
*   **Boundaries:** Ray casting must handle cases where rays do not intersect the volume.
*   **Degenerate Input:** Non-orthogonal sampling grids require specific corrections during data preparation [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of samples $K$ and the number of pixels [S2, unofficial].
*   **Memory Complexity:** Linear with respect to the size of the volume data and the number of samples [S2, unofficial].
*   **Strengths:** Independence of shading and classification calculations ensures an undistorted visualization of 3-D shape [S2, unofficial]. Non-binary classification operators ensure that small or poorly defined features are not lost [S2, unofficial].
*   **Limitations:** Requires significant computational resources for high-resolution volumes and large $K$ [S2, unofficial].
*   **When to use:** When direct visualization of 3D shape is required without fitting geometric primitives [S2, unofficial].
*   **When not to use:** When performance is critical and lower resolution is acceptable [S2, unofficial].

## Background
The volume rendering pipeline was first reported in June 1987 and presented at the SPIE Medical Imaging II conference in January 1988 [S3, unofficial]. It was developed to address the need for visualizing surfaces from sampled scalar functions of three spatial dimensions without fitting geometric primitives [S2, unofficial]. The pipeline has since become a standard approach in direct volume rendering, with various implementations and optimizations proposed in subsequent research [S1, unofficial].
