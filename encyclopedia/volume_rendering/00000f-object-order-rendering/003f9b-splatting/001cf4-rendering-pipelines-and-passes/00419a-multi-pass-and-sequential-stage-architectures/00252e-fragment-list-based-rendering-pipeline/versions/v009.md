# Fragment List-Based Rendering Pipeline

Also called: 4-Stage Rendering Pipeline, Smoker Rendering Pipeline

## Overview
A fragment list-based rendering pipeline that processes smoke volumes through four distinct stages (Clear, Construction, Insertion, Evaluation) using fragment lists to store and evaluate per-pixel data, chosen to maintain accuracy and avoid raytracing/self-intersection problems. It differs from [Volume Rendering Pipeline](1318-volume-rendering-pipeline.md) by explicitly decoupling geometry assembly and fragment storage from final shading, and from [Deferred Rendering Pipeline](10584-deferred-rendering-pipeline.md) by using fragment lists for volumetric density accumulation rather than deferred G-buffers for surface properties.

## How it works
**Inputs:** Smoke volume data (density, flow tangents), geometry primitives (vertices, topology), OpenGL buffer objects for intermediate storage.
**Outputs:** Final rendered image.

**Data Structures:**
- OpenGL Buffer Objects: Used for clearing state, storing intermediate fragment data, and final image. Specific layouts depend on the visualization method (e.g., pixel counter vs. complex storage structure).
- Fragment List: A storage structure for per-pixel fragment information, created during the Insertion stage.

**Steps:**
1. **Clear:** Reset OpenGL buffer objects for the subsequent frame. This is initiated by rendering a single screen-filling quad using the Clear shader program.
2. **Construction:** Vertex shader transforms vertices (perspective transformation) and assigns additional vertex data (density, flow tangents). Geometry shader assembles primitives, processes triangle-related data (orientation, topology, volume information), and forwards results to the Insertion stage. This stage is part of the Render shader program.
3. **Insertion:** Primitives are rasterized and forwarded to the fragment shader. Incoming fragments are processed according to the visualization method, ranging from a simple pixel counter to insertion into a complicated storage data structure (fragment list). Fragment processing must be compatible with the Evaluation step. This stage is part of the Render shader program.
4. **Evaluation:** Render a single screen-filling quad to initiate fragment evaluation. The Display shader program interprets and visualizes per-pixel information prepared by the Insertion stage.

```python
# Clear Stage
def clear_stage():
    # Reset OpenGL buffer objects for the subsequent frame
    # Launch fragment shader threads by rendering a single screen-filling quad
    render_screen_filling_quad(clear_shader)

# Construction Stage (Part of Render Program)
def construction_stage(vertices, volume_data):
    # Vertex Shader
    transformed_vertices = []
    for v in vertices:
        # Perspective transformation
        v_proj = perspective_transform(v)
        # Assign additional vertex data
        v_proj.density = volume_data.get_density(v)
        v_proj.flow_tangents = volume_data.get_flow_tangents(v)
        transformed_vertices.append(v_proj)
    
    # Geometry Shader
    primitives = []
    for tri in triangles_from(transformed_vertices):
        # Process triangle-related data
        tri.orientation = calculate_orientation(tri)
        tri.topology = analyze_topology(tri)
        tri.volume_info = get_volume_info(tri)
        primitives.append(tri)
    
    return primitives

# Insertion Stage (Part of Render Program)
def insertion_stage(primitives, fragment_list):
    # Rasterize primitives
    fragments = rasterize(primitives)
    
    # Fragment Shader: Process incoming fragments
    for frag in fragments:
        # Insertion into storage structure or pixel counter
        # Must be compatible with Evaluation step
        fragment_list.insert(frag)

# Evaluation Stage
def evaluation_stage(fragment_list):
    # Render a single screen-filling quad
    # Interpret and visualize per-pixel information
    final_image = interpret_fragment_list(fragment_list)
    return final_image

# Main Pipeline Execution
def fragment_list_pipeline(volume_data, geometry):
    clear_stage()
    primitives = construction_stage(geometry.vertices, volume_data)
    insertion_stage(primitives, fragment_list)
    final_image = evaluation_stage(fragment_list)
    return final_image
```

**Parameters:**
- Pipeline Stages: Clear, Construction, Insertion, Evaluation.
- Shader Programs: Clear, Render (combines Construction and Insertion), Display (handles Evaluation).
- Typical Values: Not given in the sources.

**Edge Cases and Pitfalls:**
- Concurrent modification of shared memory during the Insertion step causes bottlenecks and inconsistent states if unmanaged, as shader threads cannot check whether a shared address is currently being modified [S1, unofficial].
- The type of fragment processing must be compatible with the Evaluation step [S1, unofficial].

## Subtopics

### Clear Stage
Resets buffers for the next frame. Chosen for its simplicity in managing state between frames. Link to [Multi-Pass and Sequential Stage Architectures](10539-multi-pass-and-sequential-stage-architectures.md).

### Construction Stage
Assembles primitives and assigns volumetric data. Chosen for its ability to preprocess geometry and volume information before rasterization. Link to [Multi-Pass and Sequential Stage Architectures](10539-multi-pass-and-sequential-stage-architectures.md).

### Insertion Stage
Rasterizes and stores fragments. Chosen for its flexibility in handling different visualization methods. Link to [Multi-Pass and Sequential Stage Architectures](10539-multi-pass-and-sequential-stage-architectures.md).

### Evaluation Stage
Interprets and visualizes fragment data. Chosen for its separation of concerns from geometry processing. Link to [Multi-Pass and Sequential Stage Architectures](10539-multi-pass-and-sequential-stage-architectures.md).

## Operating characteristics
- **Time Complexity:** Not given in the sources.
- **Memory Complexity:** Depends on the fragment list storage structure. Not given in the sources.
- **Measured Performance:** Implemented in the Smoker application for real-time smoke volume rendering. Not given in the sources.
- **Scaling:** Not given in the sources.
- **Strengths:** Maintains accuracy and circumvents problems arising from raytracing and self or global intersections.
- **Limitations:** Concurrent modification of shared memory during the Insertion step can cause bottlenecks and inconsistent states.
- **When to Use:** Real-time smoke volume rendering where accuracy is prioritized over the complexity of raytracing.
- **When Not to Use:** When hardware lacks support for complex fragment list storage or when real-time performance is critical and the Insertion stage bottleneck is unacceptable.

## Background
Originated in the Smoker application for real-time smoke volume rendering. The pipeline was chosen to maintain accuracy and avoid problems associated with raytracing and self or global intersections. It is implemented using OpenGL buffer objects and shader programs.
