# Fragment List-Based Rendering Pipeline

Also called: 4-Stage Rendering Pipeline, Smoker Rendering Pipeline

## Overview
The Fragment List-Based Rendering Pipeline is a multi-pass architecture designed for real-time smoke volume rendering that processes geometry through four distinct stages to store and evaluate per-pixel fragment data [S1, unofficial]. It is chosen specifically to maintain high accuracy and circumvent the self-intersection and global intersection problems inherent in raytracing approaches [S1, unofficial]. Unlike the [Volume Rendering Pipeline](1318-volume-rendering-pipeline.md), which typically processes voxels or rays directly, this method rasterizes primitives into fragment lists for deferred evaluation [S1, unofficial].

## How it works
The pipeline consists of four sequential stages executed by three shader programs: Clear, Render (combining Construction and Insertion), and Display (Evaluation) [S1, unofficial].

**Inputs and Outputs:**
*   **Input:** Smoke volume geometry (triangles), vertex attributes (density, flow tangents), and OpenGL buffer objects for storage.
*   **Output:** Final rendered image with per-pixel visualization of smoke properties.

**Data Structures:**
*   **OpenGL Buffer Objects:** Used to store intermediate per-pixel data generated during the Insertion stage. The specific layout depends on the visualization method (e.g., pixel counters or complex storage structures) [S1, unofficial].
*   **Fragment Lists:** Implicitly maintained in GPU memory during the Insertion stage to accumulate fragment data before evaluation [S1, unofficial].

**Steps:**

1.  **Clear Stage:**
    *   Reset OpenGL buffer objects required for the subsequent frame.
    *   Initiated by rendering a single screen-filling quad.
    *   Fragment shader threads are launched to clear the storage buffers [S1, unofficial].

2.  **Construction Stage:**
    *   **Vertex Shader:** Performs perspective transformation of vertices. Assigns additional vertex data such as density and flow tangents.
    *   **Geometry Shader:** Assembles primitives. Processes triangle-related data including orientation, topology, and volume information.
    *   Forwards the processed primitives to the Insertion stage.
    *   This stage is part of the "Render" shader program [S1, unofficial].

3.  **Insertion Stage:**
    *   **Rasterization:** Primitives from the Construction stage are rasterized.
    *   **Fragment Shader:** Processes incoming fragments. The processing logic varies by visualization method, ranging from a simple pixel counter to insertion into a complicated storage data structure.
    *   **Constraint:** The type of fragment processing must be compatible with the subsequent Evaluation step.
    *   This stage is part of the "Render" shader program, sharing the same program object as Construction [S1, unofficial].

4.  **Evaluation Stage:**
    *   Initiated by rendering a single screen-filling quad.
    *   **Fragment Shader:** Interprets and visualizes the per-pixel information that was prepared and stored by the Insertion stage.
    *   This stage is handled by the "Display" shader program [S1, unofficial].

**Pseudocode:**

```python
# Pseudocode representing the pipeline execution flow
# Note: Actual implementation relies on OpenGL state machine and shader programs

def execute_fragment_list_pipeline():
    # 1. Clear Stage
    # Launch a single draw call for a screen-filling quad
    # Shader: Clear
    # Action: Reset OpenGL buffer objects for the next frame
    draw_screen_quad(shader_program="Clear")

    # 2. Construction & Insertion Stage (Render Stage)
    # Launch draw calls for smoke volume geometry
    # Shader: Render (contains Vertex, Geometry, and Fragment shaders)
    # Vertex Shader:
    #   - Transform vertices (perspective)
    #   - Assign density, flow tangents
    # Geometry Shader:
    #   - Assemble primitives
    #   - Process orientation, topology, volume info
    # Fragment Shader:
    #   - Rasterize primitives
    #   - Process fragments (e.g., increment counter or insert into storage)
    #   - Must be compatible with Evaluation
    draw_geometry(geometry="smoke_volume", shader_program="Render")

    # 3. Evaluation Stage
    # Launch a single draw call for a screen-filling quad
    # Shader: Display
    # Action: Interpret and visualize per-pixel info from Insertion
    draw_screen_quad(shader_program="Display")
```

**Parameters:**
*   **Pipeline Stages:** Clear, Construction, Insertion, Evaluation [S1, unofficial].
*   **Shader Programs:** Clear, Render, Display [S1, unofficial].
*   **Typical Values:** Not given in the sources.

**Edge Cases and Pitfalls:**
*   **Concurrent Modification:** The Insertion step is the greatest bottleneck due to simultaneous access to shared indexing mechanisms. Shader threads cannot check if a shared address is currently being modified, leading to bottlenecks and inconsistent states if unmanaged [S1, unofficial].
*   **Compatibility:** Fragment processing in the Insertion stage must be strictly compatible with the Evaluation step; mismatched data structures will result in incorrect visualization [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Depends on the storage data structure used in the Insertion stage (e.g., pixel counters vs. complex lists). Not given in the sources.
*   **Measured Performance:** Implemented in the Smoker application for real-time smoke volume rendering [S1, unofficial].
*   **Strengths:** Maintains high accuracy; circumvents raytracing and self/global intersection problems [S1, unofficial].
*   **Limitations:** The Insertion step is a significant bottleneck due to concurrent memory access issues in OpenGL [S1, unofficial].
*   **When to use:** Real-time smoke volume rendering where accuracy is prioritized over the speed of raytracing and intersection artifacts are unacceptable [S1, unofficial].
*   **When not to use:** Scenes where raytracing intersections are manageable or where the overhead of fragment list management is prohibitive [S1, unofficial].

## Background
The Fragment List-Based Rendering Pipeline was developed as part of the "Smoker" application for real-time smoke volume rendering. It was presented in a master's thesis by Dirk Sowinski in 2012 [S1, unofficial]. The method was chosen to address the limitations of raytracing techniques, specifically self-intersection and global intersection problems, while maintaining accuracy through a four-stage shader-based pipeline [S1, unofficial].
