# Fragment List-Based Rendering Pipeline

Also called: 4-Stage Rendering Pipeline, Smoker Rendering Pipeline

## Overview
The Fragment List-Based Rendering Pipeline is a multi-pass architecture designed for accurate real-time volume rendering of smoke, specifically chosen to circumvent the self-intersection and global intersection artifacts inherent in raytracing approaches [S1, unofficial]. It separates the rendering process into four distinct stages—Clear, Construction, Insertion, and Evaluation—using fragment lists to store and evaluate per-pixel data [S1, unofficial]. Unlike the [Volume Rendering Pipeline](1318-volume-rendering-pipeline.md) which often integrates shading and compositing, or the [Deferred Rendering Pipeline](10584-deferred-rendering-pipeline.md) which relies on G-buffers for geometry, this pipeline explicitly manages fragment accumulation in intermediate storage structures to maintain visual accuracy for participating media [S1, unofficial].

## How it works
The pipeline executes four sequential stages using three shader programs: Clear, Render (combining Construction and Insertion), and Display (Evaluation) [S1, unofficial].

**Inputs and Outputs:**
*   **Input:** Smoke volume data (density, flow tangents), geometry primitives (triangles representing volume slices or particles), and OpenGL buffer objects for intermediate storage [S1, unofficial].
*   **Output:** Final composited image on the screen [S1, unofficial].

**Data Structures:**
*   **Fragment List:** A per-pixel storage structure (e.g., atomic counter-based linked list or append buffer) that accumulates fragment contributions during the Insertion stage [S1, unofficial]. The exact layout depends on the specific implementation variant but must support concurrent writes from multiple fragments [S1, unofficial].
*   **OpenGL Buffers:** Framebuffer objects (FBOs) and buffer objects used to reset state and store intermediate per-pixel information [S1, unofficial].

**Steps:**

1.  **Clear:**
    *   Reset all OpenGL buffer objects required for the subsequent frame. This typically involves resetting atomic counters, clearing fragment lists, or zeroing out accumulation buffers [S1, unofficial].
    *   Initiated by rendering a single screen-filling quad using the **Clear** shader program [S1, unofficial].

2.  **Construction:**
    *   **Vertex Shader:** Performs perspective transformation on input vertices. Assigns additional vertex data such as density values and flow tangents [S1, unofficial].
    *   **Geometry Shader:** Assembles primitives (e.g., triangles) from the transformed vertices. Processes triangle-related data including orientation, topology, and volume information. Forwards the constructed primitives to the Insertion stage [S1, unofficial].
    *   This stage is part of the **Render** shader program [S1, unofficial].

3.  **Insertion:**
    *   **Rasterization:** The primitives constructed in the previous stage are rasterized [S1, unofficial].
    *   **Fragment Shader:** Processes incoming fragments. The specific action depends on the visualization method, ranging from a simple pixel counter to inserting fragment data (e.g., color, opacity, depth) into a complicated storage data structure (the fragment list) [S1, unofficial].
    *   **Constraint:** The type of fragment processing must be compatible with the subsequent Evaluation step [S1, unofficial].
    *   This stage is part of the **Render** shader program [S1, unofficial].

4.  **Evaluation:**
    *   Render a single screen-filling quad using the **Display** shader program [S1, unofficial].
    *   Interpret and visualize the per-pixel information that was prepared and stored by the Insertion stage. This involves reading from the fragment lists and performing final compositing/shading [S1, unofficial].

**Pseudocode:**

```python
# Stage 1: Clear
def clear_stage():
    # Reset OpenGL buffer objects for the subsequent frame
    # e.g., reset atomic counters, clear fragment lists
    reset_buffers()
    # Render a single screen-filling quad with Clear shader
    render_quad(clear_shader)

# Stage 2 & 3: Construction and Insertion (Render Stage)
def render_stage(geometry, volume_data):
    # Vertex Shader: Transform vertices and assign data
    # Output: Transformed vertices with density, flow tangents
    transformed_vertices = vertex_shader(geometry, volume_data)
    
    # Geometry Shader: Assemble primitives and process triangle data
    # Output: Rasterizable primitives with orientation, topology, volume info
    primitives = geometry_shader(transformed_vertices)
    
    # Rasterization happens implicitly in the pipeline
    # Fragment Shader: Process fragments and insert into storage
    # Input: Rasterized fragments
    # Action: Insert fragment data into per-pixel fragment list
    fragment_shader_insert(primitives)

# Stage 4: Evaluation
def evaluation_stage():
    # Render a single screen-filling quad with Display shader
    # Input: Per-pixel fragment lists from Insertion stage
    # Action: Interpret and visualize per-pixel information
    render_quad(display_shader)

# Main Pipeline Execution
def fragment_list_pipeline(geometry, volume_data):
    clear_stage()
    render_stage(geometry, volume_data)
    evaluation_stage()
```

**Parameters:**
*   **Pipeline Stages:** Clear, Construction, Insertion, Evaluation [S1, unofficial].
*   **Shader Programs:** Clear, Render (Construction + Insertion), Display (Evaluation) [S1, unofficial].
*   **Typical Values:** Not given in the sources.

**Edge Cases and Pitfalls:**
*   **Concurrent Modification:** The Insertion step is the greatest bottleneck due to simultaneous access to shared indexing mechanisms. Unmanaged concurrent access to shared memory can leave it in an inconsistent state because shader threads cannot check if a shared address is currently being modified [S1, unofficial].
*   **Compatibility:** The fragment processing method in the Insertion stage must be strictly compatible with the Evaluation stage's interpretation logic [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Depends on the fragment list implementation; requires additional memory for storing per-pixel fragment lists and intermediate buffers [S1, unofficial].
*   **Measured Performance:** Implemented in the Smoker application for real-time smoke volume rendering [S1, unofficial].
*   **Scaling:** Not given in the sources.
*   **Strengths:** Maintains high accuracy for smoke volumes; circumvents problems arising from raytracing, self-intersections, and global intersections [S1, unofficial].
*   **Limitations:** The Insertion step is a significant bottleneck due to concurrent memory access issues; requires careful management of shared memory to avoid inconsistent states [S1, unofficial].
*   **When to use:** Real-time smoke volume rendering where accuracy is prioritized over the simplicity of raytracing and where self-intersection artifacts are unacceptable [S1, unofficial].
*   **When not to use:** Scenes where raytracing artifacts are negligible or where hardware lacks support for the required OpenGL buffer and atomic operations [S1, unofficial].

## Background
The Fragment List-Based Rendering Pipeline was developed as part of the "Smoker" application for real-time smoke volume rendering [S1, unofficial]. It was chosen over raytracing techniques to maintain the best possible accuracy and to circumvent problems arising from raytracing and self or global intersections [S1, unofficial]. The pipeline generalizes the rendering process into four stages executed by three shader programs, providing a flexible framework that allows switching between different rendering strategies during runtime without re-initializing the smoke volume [S1, unofficial].
