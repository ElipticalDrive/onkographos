# Fragment List-Based Rendering Pipeline

Also called: 4-Stage Rendering Pipeline, Smoker Rendering Pipeline

## Overview
The Fragment List-Based Rendering Pipeline is a multi-pass architecture for real-time volume rendering, specifically designed for smoke and fluid simulations. It processes volume data through four distinct stages (Clear, Construction, Insertion, Evaluation) using fragment lists to store per-pixel information, chosen to maintain accuracy and avoid the self-intersection and global intersection problems inherent in raytracing approaches [S1, unofficial]. It builds on [Multi-Pass and Sequential Stage Architectures](10539-multi-pass-and-sequential-stage-architectures.md) by decoupling geometry assembly from pixel evaluation via intermediate storage.

## How it works
The pipeline executes as a sequence of discrete rendering passes, typically implemented via OpenGL shader programs. It is generalized into four stages executed by three shader programs: Clear, Render (combining Construction and Insertion), and Display (handling Evaluation) [S1, unofficial].

### Inputs and Outputs
*   **Input:** Smoke volume data (density, flow tangents), geometry primitives (triangles representing volume slices or particles), and screen resolution.
*   **Output:** Final rendered image buffer.
*   **Intermediate:** Fragment lists or counters stored in GPU memory (e.g., textures, buffer objects) between stages.

### Data Structures
The core data structure is the **fragment list**, which stores per-pixel information prepared by the Insertion stage. The specific layout depends on the visualization method, ranging from a simple pixel counter to a complicated storage data structure [S1, unofficial]. The pipeline relies on OpenGL buffer objects that must be reset for each frame [S1, unofficial].

### Steps
1.  **Clear:** Reset OpenGL buffer objects for the subsequent frame. This stage is initiated by rendering a single screen-filling quad [S1, unofficial].
2.  **Construction:**
    *   **Vertex Shader:** Performs perspective transformation and assigns additional vertex data (e.g., density, flow tangents) [S1, unofficial].
    *   **Geometry Shader:** Assembles primitives, processes triangle-related data (orientation, topology, volume information), and forwards results to the Insertion stage [S1, unofficial].
3.  **Insertion:**
    *   Primitives are rasterized and forwarded to the fragment shader [S1, unofficial].
    *   The fragment shader processes incoming fragments. This may involve a simple pixel counter or insertion into a complicated storage data structure (the fragment list) [S1, unofficial].
    *   **Constraint:** The type of fragment processing must be compatible with the Evaluation step [S1, unofficial].
    *   **Concurrency:** This stage is the greatest bottleneck due to simultaneous access to shared indexing mechanisms. Unmanaged concurrent modification of shared memory can leave it in an inconsistent state because shader threads cannot check if a shared address is currently being modified [S1, unofficial].
4.  **Evaluation:**
    *   Render a single screen-filling quad to initiate fragment evaluation [S1, unofficial].
    *   Interpret and visualize the per-pixel information prepared by the Insertion stage [S1, unofficial].

### Pseudocode
The following pseudocode outlines the logical flow of the three shader programs. Note that the specific implementation of the fragment list storage and the Insertion/Evaluation logic varies by visualization method [S1, unofficial].

```python
# Program 1: Clear
# Called once per frame before rendering geometry
def Clear():
    # Reset all OpenGL buffer objects used for fragment storage
    # This ensures no data from the previous frame persists
    reset_buffer_objects()

# Program 2: Render (Construction + Insertion)
# Called to process volume geometry
def Render(geometry):
    for primitive in geometry:
        # Construction Stage
        # Vertex Shader: Transform and attach data
        transformed_vertices = []
        for vertex in primitive.vertices:
            v_pos = perspective_transform(vertex.position)
            v_density = vertex.density
            v_tangent = vertex.flow_tangent
            transformed_vertices.append({
                'position': v_pos,
                'density': v_density,
                'tangent': v_tangent
            })
        
        # Geometry Shader: Assemble and process
        # Generates fragments from the transformed vertices
        # Attaches triangle orientation, topology, and volume info
        fragments = geometry_shader_assemble(transformed_vertices)
        
        # Insertion Stage
        # Rasterize and process fragments
        for frag in fragments:
            # Determine storage location based on pixel coordinate
            pixel_id = frag.screen_position
            
            # Insert fragment data into shared fragment list
            # This is the critical section prone to race conditions
            insert_into_fragment_list(pixel_id, frag)

# Program 3: Display (Evaluation)
# Called after Render to produce the final image
def Display():
    # Render a screen-filling quad to trigger evaluation for all pixels
    for pixel in screen_resolution:
        # Retrieve stored fragment data for this pixel
        fragment_data = get_from_fragment_list(pixel)
        
        # Interpret and visualize the data
        # (e.g., sorting, blending, shading)
        color = evaluate_fragment_data(fragment_data)
        set_pixel_color(pixel, color)
```

### Parameters and Edge Cases
*   **Shader Programs:** Clear, Render, Display [S1, unofficial].
*   **Concurrency Pitfall:** Concurrent modification of shared memory during the Insertion step causes bottlenecks and inconsistent states if unmanaged. Shader threads cannot check whether a shared address is currently being modified [S1, unofficial].
*   **Compatibility:** The fragment processing method in Insertion must be strictly compatible with the Evaluation step [S1, unofficial].

## Operating characteristics
*   **Accuracy vs. Performance:** Chosen over raytracing to circumvent problems arising from raytracing and self or global intersections, maintaining high accuracy for smoke volumes [S1, unofficial].
*   **Bottlenecks:** The Insertion step is identified as the greatest bottleneck of the entire rendering pipeline due to simultaneous access to shared indexing mechanisms [S1, unofficial].
*   **Hardware Dependency:** Relies heavily on GPU-related functionality, shader application, and memory transactions [S1, unofficial].
*   **Flexibility:** The pipeline allows switching between rendering methods during runtime without re-initializing the smoke volume, facilitating comparison of different approaches using identical configurations [S1, unofficial].

## Background
The Fragment List-Based Rendering Pipeline was implemented in the **Smoker** application for real-time smoke volume rendering [S1, unofficial]. It was developed as part of a master's thesis by Dirk Sowinski in 2012 [S1, unofficial]. The approach generalizes the rendering process into a 4-stage classification to manage the complexity of GPU-based volume rendering and improve performance through specialized stages [S1, unofficial].
