# Fragment List-Based Rendering Pipeline

Also called: 4-Stage Rendering Pipeline, Smoker Rendering Pipeline

## Overview
The Fragment List-Based Rendering Pipeline is a multi-pass architecture designed for real-time smoke volume rendering that processes primitives through four distinct stages to maintain accuracy while avoiding the self-intersection and raytracing artifacts common in other methods [S1, unofficial]. It differs from the [Volume Rendering Pipeline](1318-volume-rendering-pipeline.md) by explicitly decoupling geometry construction from per-pixel evaluation via intermediate fragment lists, and from the [Deferred Rendering Pipeline](10584-deferred-rendering-pipeline.md) by its specific focus on managing concurrent insertion bottlenecks in shared memory structures for volumetric data [S1, unofficial].

## How it works
The pipeline consists of four sequential stages executed by three shader programs: **Clear**, **Render** (combining Construction and Insertion), and **Display** (Evaluation) [S1, unofficial].

**Inputs and Outputs:**
*   **Input:** Smoke volume data (density, flow tangents), geometric primitives (triangles), and OpenGL buffer objects.
*   **Output:** Final composited image on the screen.

**Data Structures:**
*   **OpenGL Buffer Objects:** Used for intermediate storage between stages. Specific layouts depend on the visualization method (e.g., pixel counters or complex storage structures) [S1, unofficial].
*   **Fragment Lists:** Implicit structures populated during the Insertion stage to store per-pixel information [S1, unofficial].

**Numbered Steps:**

1.  **Clear:**
    *   Reset OpenGL buffer objects required for the subsequent frame [S1, unofficial].
    *   Initiated by rendering a single screen-filling quad [S1, unofficial].

2.  **Construction:**
    *   **Vertex Shader:** Performs perspective transformation and assigns additional vertex data, such as density or flow tangents [S1, unofficial].
    *   **Geometry Shader:** Assembles primitives, processes triangle-related data (orientation, topology, volume information), and forwards results to the Insertion stage [S1, unofficial].
    *   This stage is part of the **Render** shader program [S1, unofficial].

3.  **Insertion:**
    *   Primitives are rasterized and forwarded to the fragment shader [S1, unofficial].
    *   The fragment shader processes incoming fragments according to the specific visualization method. This ranges from a simple pixel counter to insertion into a complicated storage data structure [S1, unofficial].
    *   **Constraint:** The type of fragment processing must be compatible with the Evaluation step [S1, unofficial].
    *   This stage is part of the **Render** shader program [S1, unofficial].

4.  **Evaluation:**
    *   Render a single screen-filling quad to initiate fragment evaluation [S1, unofficial].
    *   Interpret and visualize per-pixel information that was prepared by the Insertion stage [S1, unofficial].
    *   This stage is handled by the **Display** shader program [S1, unofficial].

**Parameters:**
*   **Pipeline Stages:** Clear, Construction, Insertion, Evaluation [S1, unofficial].
*   **Shader Programs:** Clear, Render (Construction + Insertion), Display (Evaluation) [S1, unofficial].

**Pitfalls and Edge Cases:**
*   **Concurrent Modification:** The Insertion step is the greatest bottleneck due to simultaneous access to shared indexing mechanisms. Unmanaged concurrent access to shared memory can leave it in an inconsistent state because shader threads cannot check if a shared address is currently being modified [S1, unofficial].
*   **Compatibility:** Fragment processing in the Insertion stage must strictly match the expectations of the Evaluation stage [S1, unofficial].

**Pseudocode:**
```python
# Pseudocode representing the logical flow of the 4-stage pipeline
# Note: Actual implementation relies on OpenGL shader programs and buffer bindings

def fragment_list_pipeline(volume_data, geometry):
    # Stage 1: Clear
    # Launch Clear shader program with a screen-filling quad
    # Resets all necessary OpenGL buffer objects for the new frame
    execute_shader("Clear", quad="screen_filling")

    # Stage 2 & 3: Construction and Insertion (Render Program)
    # Launch Render shader program with the smoke volume geometry
    # Vertex Shader: Transform vertices, assign density/flow tangents
    # Geometry Shader: Assemble primitives, process orientation/topology
    # Fragment Shader: Rasterize and insert fragments into storage/counter
    execute_shader("Render", geometry=geometry)

    # Stage 4: Evaluation (Display Program)
    # Launch Display shader program with a screen-filling quad
    # Reads from intermediate buffers populated by Insertion
    # Interprets and visualizes per-pixel information
    execute_shader("Display", quad="screen_filling")
```

## Subtopics

### Atomic-Based Insertion
Uses atomic operations to handle concurrent writes to shared memory during the Insertion stage, mitigating bottlenecks and inconsistent states [S1, unofficial].

### Pixel Counter Method
A simplified Insertion strategy where fragments are counted rather than stored in complex structures, suitable for basic visualization [S1, unofficial].

## Operating characteristics
*   **Performance:** The Insertion step is identified as the primary bottleneck due to concurrent access to shared indexing mechanisms [S1, unofficial].
*   **Accuracy:** Chosen over raytracing to circumvent problems arising from self or global intersections, maintaining high accuracy for smoke volumes [S1, unofficial].
*   **Flexibility:** Allows switching between rendering methods during runtime without re-initializing the smoke volume [S1, unofficial].
*   **Hardware Dependency:** Heavily relies on GPU functionality, including shader applications and memory transactions [S1, unofficial].

## Background
The method was implemented in the **Smoker** application for real-time smoke volume rendering [S1, unofficial]. It was developed as part of a master's thesis by Dirk Sowinski in 2012, presented as a panel allowing runtime switching between rendering strategies [S1, unofficial].
