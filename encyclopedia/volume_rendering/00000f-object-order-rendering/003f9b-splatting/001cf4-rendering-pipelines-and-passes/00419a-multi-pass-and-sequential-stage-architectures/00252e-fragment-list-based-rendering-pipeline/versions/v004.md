# Fragment List-Based Rendering Pipeline

Also called: 4-Stage Rendering Pipeline, Smoker Rendering Pipeline

## Overview
The Fragment List-Based Rendering Pipeline is a four-stage object-order rendering method designed for real-time smoke volume visualization [S1, unofficial]. It processes geometry through Clear, Construction, Insertion, and Evaluation stages to maintain high accuracy while circumventing the self-intersection and global intersection artifacts common in raytracing approaches [S1, unofficial]. It is distinguished from sibling pipelines by its explicit separation of fragment storage (Insertion) from final image synthesis (Evaluation), using fragment lists to accumulate per-pixel data before compositing [S1, unofficial].

## How it works
The pipeline executes four distinct logical stages managed by three shader programs: Clear, Render (combining Construction and Insertion), and Display (Evaluation) [S1, unofficial].

### Inputs and Outputs
*   **Inputs:** Smoke volume geometry (vertices, density, flow tangents) and OpenGL buffer objects (framebuffers, atomic counters, fragment lists) [S1, unofficial].
*   **Outputs:** Final rendered image frame [S1, unofficial].

### Data Structures
*   **Fragment Lists:** Per-pixel storage structures populated during the Insertion stage to accumulate fragment data for later evaluation [S1, unofficial].
*   **OpenGL Buffers:** Used for clearing state and storing intermediate per-pixel attributes between pipeline stages [S1, unofficial].

### Steps
1.  **Clear:** Reset OpenGL buffer objects required for the subsequent frame [S1, unofficial]. This stage is executed by rendering a single screen-filling quad using the **Clear** shader program [S1, unofficial].
2.  **Construction:** The **Vertex Shader** performs perspective transformation on input vertices and assigns additional vertex data, such as density or flow tangents [S1, unofficial]. The **Geometry Shader** assembles primitives from vertices and processes triangle-related data including orientation, topology, and volume information [S1, unofficial]. The results are forwarded to the Insertion stage [S1, unofficial].
3.  **Insertion:** Primitives constructed in the previous stage are rasterized [S1, unofficial]. The **Fragment Shader** processes incoming fragments, which may involve a simple pixel counter or insertion into a complicated storage data structure [S1, unofficial]. This stage belongs to the **Render** shader program, which combines Construction and Insertion [S1, unofficial]. The type of fragment processing must be strictly compatible with the Evaluation step [S1, unofficial].
4.  **Evaluation:** A single screen-filling quad is rendered using the **Display** shader program [S1, unofficial]. The shader interprets and visualizes the per-pixel information prepared by the Insertion stage [S1, unofficial].

### Edge Cases and Pitfalls
*   **Concurrent Modification:** The Insertion step is the greatest bottleneck due to simultaneous access to shared indexing mechanisms [S1, unofficial]. Shader threads cannot check whether a shared address is currently being modified, leading to bottlenecks and inconsistent states if unmanaged [S1, unofficial].
*   **Compatibility:** Fragment processing in the Insertion stage must be strictly compatible with the Evaluation step's interpretation logic [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Depends on the fragment list implementation; concurrent access to shared memory requires careful management to avoid inconsistent states [S1, unofficial].
*   **Performance:** Implemented in the Smoker application for real-time smoke volume rendering [S1, unofficial].
*   **Strengths:** Maintains high accuracy and circumvents problems arising from raytracing, self-intersections, and global intersections [S1, unofficial].
*   **Limitations:** The Insertion step is a significant bottleneck due to concurrent modification of shared memory [S1, unofficial].
*   **When to use:** Real-time smoke volume rendering where accuracy is prioritized and raytracing artifacts are unacceptable [S1, unofficial].
*   **When not to use:** Scenes requiring global illumination effects that are better handled by raytracing, or when hardware lacks support for the required OpenGL buffer and atomic operations [S1, unofficial].

## Background
The method was developed for the "Smoker" application, a real-time smoke volume rendering system [S1, unofficial]. It was presented in a master's thesis by Sowinski in 2012 [S1, unofficial]. The pipeline was chosen to provide a flexible framework allowing runtime switching between different rendering strategies without re-initializing the smoke volume, facilitating comparison of approaches under identical configurations [S1, unofficial].
