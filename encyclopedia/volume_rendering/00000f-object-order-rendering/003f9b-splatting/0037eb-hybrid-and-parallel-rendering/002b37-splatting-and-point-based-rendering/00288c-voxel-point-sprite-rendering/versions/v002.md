# Voxel Point Sprite Rendering

Also called: GL_POINTS voxel rendering, OpenGL Voxel Splatting, Point-based Voxel Rendering, Voxel Splatting

## Overview
Voxel Point Sprite Rendering is a technique that represents occupied voxels as geometric points (splatting) submitted to the graphics pipeline, typically utilizing a geometry shader to expand these points into screen-space primitives [S2, unofficial]. It solves the problem of rendering dense volumetric data by avoiding the overhead of generating and rasterizing explicit 3D mesh geometry for every voxel [S1, S2, unofficial]. Unlike sibling methods that rasterize ray-box intersections via quads [2253-ray-box-intersection-via-quad-rasterization.md] or use sparse octree structures [2993-sparse-voxel-octree-rendering-via-square-splats.md], this method relies on a flat buffer of point primitives, often employing mipmapping to manage detail levels and stochastic culling to maintain performance [S1, S2, unofficial].

## How it works
**Inputs and Outputs**
*   **Input:** A voxel grid defined by dimensions $N_x, N_y, N_z$ (e.g., $200 \times 50 \times 200$ or $4 \times 4 \times 4$ logical blocks) [S1, S2, unofficial]. Each occupied voxel contains position data $(x, y, z)$ and color/albedo data [S1, S2, unofficial].
*   **Output:** A rasterized image where voxels are rendered as point sprites, with visibility determined by the depth buffer [S2, unofficial].

**Data Structures**
The implementation varies slightly between source implementations, but both rely on packed integer formats for efficient memory transfer:

1.  **Packed Voxel Format (Source [S1, unofficial]):**
    *   Stored in a flat `uint32_t` array of size `no_of_vertices * 2`.
    *   **Position (`uint32_t`):**
        *   Bits 0-10 (11 bits): $x$
        *   Bits 11-20 (10 bits): $y$
        *   Bits 21-31 (11 bits): $z$
    *   **Albedo (`uint32_t`):**
        *   Bits 0-4 (5 bits): $R$
        *   Bits 5-10 (6 bits): $G$
        *   Bits 11-15 (5 bits): $B$
    *   **Vertex Attribute Binding:** Bound to a VAO using `glVertexAttribIPointer(0, 2, GL_INT, 2 * sizeof(uint32_t), 0)` [S1, unofficial].

2.  **Packed Voxel Format (Source [S2, unofficial]):**
    *   Stored in `std::vector<uint>` representing a `CUBE256::MipMap::voxels` structure.
    *   **Packing Order:** `x | (y << 8) | (z << 16) | (color << 24)`.
        *   $x$: 8 bits
        *   $y$: 8 bits
        *   $z$: 8 bits
        *   Color: 8 bits
    *   **VBO Layout for Geometry Shader:** Four 4-component attributes (`vertex0` to `vertex3`).
        *   Each attribute reads 4 unsigned bytes (`GL_UNSIGNED_BYTE`) with normalization (`GL_TRUE`).
        *   Stride: 16 bytes.
        *   `vertex0`: bytes 0-3, `vertex1`: bytes 4-7, `vertex2`: bytes 8-11, `vertex3`: bytes 12-15 [S2, unofficial].

**Algorithm Steps**

1.  **Voxel Grid Initialization:**
    *   Define grid dimensions. For [S1, unofficial], default is $200 \times 50 \times 200$. For [S2, unofficial], logical blocks are $4 \times 4 \times 4$ cubes, where each cube contains a $256 \times 256 \times 256$ local grid [S1, S2, unofficial].
    *   Populate the grid with voxel data. In [S2, unofficial], voxels are stored in mipmap levels. The local voxel index $(x, y, z)$ within a cube is calculated as $(x \& 255, y \& 255, z \& 255)$ [S2, unofficial]. Boundary checks ensure $0 \le x, y, z \le 255$; otherwise, the voxel is discarded [S2, unofficial].

2.  **Mipmap Level Calculation (Source [S2, unofficial]):**
    *   Determine the mipmap level based on camera distance to the voxel.
    *   Formula:
        $$
        \text{mipmap} = \sqrt{\sqrt{\| \text{screen.pos} + (\text{pos} + \text{vec3f}(0.5, 0.5, 0.5) + \text{add}) \times 16 \|}} - 1
        $$
    *   Clamp mipmap to $\ge 0$ [S2, unofficial].

3.  **Vertex Shader Processing (Source [S1, unofficial]):**
    *   **Unpacking:** Extract coordinates from the packed position `uint32_t` `data.x`:
        $$
        \begin{aligned}
        u_x &= \text{data.x} \ \& \ 2047 \\
        u_y &= (\text{data.x} \ \& \ 2095104) \gg 11 \\
        u_z &= (\text{data.x} \ \& \ (2047 \ll 21)) \gg 21
        \end{aligned}
        $$
    *   **World Space Conversion:** Multiply by voxel size (e.g., $0.1$) [S1, unofficial].
    *   **Camera Culling:** Discard voxels behind the camera ($z \le 0$) by setting position to `vec4(-1, -1, -1, -1)` and `point_size = 0.0` [S1, unofficial].

4.  **Stochastic Culling (Source [S1, unofficial]):**
    *   To maintain performance for distant/small voxels, apply probabilistic discard.
    *   Calculate projected area: $\text{stochasticCoverage} = \text{point\_size}^2$.
    *   If $\text{stochasticCoverage} < 0.8$, discard with probability proportional to size:
        $$
        \text{if } ((\text{stochasticCoverage} < 0.8) \ \&\& \ ((\text{gl\_VertexID} \ \& \ 0xffff) > \text{stochasticCoverage} \times (0xffff / 0.8))) \{
        \text{position} = \text{vec4}(-1, -1, -1, -1); \ \text{point\_size} = 0.0;
        \}
        $$
    *   [S1, unofficial]

5.  **Point Sprite Sizing:**
    *   **Sphere Radius Approximation:** To approximate the voxel's spatial extent, calculate the sphere radius:
        $$
        \text{sphereRadius} = \text{voxelSize} \times 1.732051
        $$
        (where $1.732051 \approx \sqrt{3}$, the diagonal of a unit cube) [S1, unofficial].
    *   **Quadric Projection:** Calculate coefficients for projecting the voxel as a quadric surface in screen space:
        $$
        \text{eqCoefs} = \frac{\text{vec4}(\text{dot}(\text{matD}[0], \text{matT}[2]), \text{dot}(\text{matD}[1], \text{matT}[2]), \text{dot}(\text{matD}[0], \text{matT}[0]), \text{dot}(\text{matD}[1], \text{matT}[1]))}{\text{dot}(\text{matD}[2], \text{matT}[2])}
        $$
        where $\text{matT}$ and $\text{matD}$ are derived from the Model-View-Projection matrix scaled by $\text{sphereRadius}$ [S1, unofficial].

6.  **Rendering:**
    *   Enable `GL_PROGRAM_POINT_SIZE` [S1, unofficial].
    *   Draw using `glDrawArrays(GL_POINTS, 0, no_of_vertices)` [S1, unofficial].
    *   In [S2, unofficial], bind the appropriate VBO for the calculated mipmap level, set uniforms (projection matrix, `block_pos`, `scale`), and draw [S2, unofficial]. The scale is calculated as:
        $$
        \text{scale} = 0.1f \times (1 \ll \text{mipmap})
        $$
        [S2, unofficial].

**Pseudocode**

```python
# Initialization
voxel_grid = create_grid(width=200, height=50, depth=200) # [S1, unofficial]
# OR
cubes_x, cubes_y, cubes_z = 4, 4, 4 # [S2, unofficial]
voxel_data = []

# Populate Voxel Data (Simplified for [S1, unofficial] packed format)
for i in range(no_of_vertices):
    # Generate random or specific voxel data
    x, y, z = get_voxel_coordinates(i)
    r, g, b = get_voxel_color(i)
    
    # Pack Position: x(11b), y(10b), z(11b)
    pos_packed = (x & 0x7FF) | ((y & 0x3FF) << 11) | ((z & 0x7FF) << 21)
    
    # Pack Albedo: R(5b), G(6b), B(5b)
    albedo_packed = (r & 0x1F) | ((g & 0x3F) << 5) | ((b & 0x1F) << 11)
    
    voxel_data.append((pos_packed, albedo_packed))

# Upload to GPU
vbo = create_buffer(voxel_data, usage=GL_STATIC_DRAW)
vao = create_vao()
bind_attribute(vao, index=0, size=2, type=GL_INT, stride=2*sizeof(uint32_t), offset=0)

# Rendering Loop
enable(GL_PROGRAM_POINT_SIZE)
set_uniform("voxelSize", 0.05) # [S1, unofficial]
set_uniform("halfScreenSize", screen_size * 0.5) # [S1, unofficial]

for voxel in voxel_data:
    pos_packed, albedo_packed = voxel
    
    # Vertex Shader Logic (Simulated)
    u_x = pos_packed & 0x7FF
    u_y = (pos_packed >> 11) & 0x3FF
    u_z = (pos_packed >> 21) & 0x7FF
    
    # Convert to world space
    world_pos = vec3(u_x, u_y, u_z) * 0.1 # [S1, unofficial]
    
    # Check if behind camera
    if world_pos.z <= 0.0:
        continue # Discard [S1, unofficial]
        
    # Calculate Point Size / Mipmap
    # For [S2, unofficial], mipmap is calculated based on distance
    # mipmap = sqrt(sqrt(length(...))) - 1
    # scale = 0.1f * (1 << mipmap)
    
    # For [S1, unofficial], stochastic culling
    point_size = calculate_point_size(world_pos)
    stochastic_coverage = point_size * point_size
    
    if stochastic_coverage < 0.8:
        vertex_id = get_vertex_id()
        threshold = stochastic_coverage * (0xFFFF / 0.8)
        if (vertex_id & 0xFFFF) > threshold:
            continue # Stochastic discard [S1, unofficial]
            
    # Transform to clip space
    clip_pos = mvp_matrix * vec4(world_pos, 1.0)
    
    # Rasterize Point
    rasterize_point(clip_pos, point_size, albedo_packed)

disable(GL_PROGRAM_POINT_SIZE)
```

## Subtopics

### [Hybrid Voxel Rendering (Mesh/Splatting)](5766-hybrid-voxel-rendering-mesh-splatting.md)
Combines OpenGL splatting for distant voxels with mesh rendering for nearby voxels to reduce vertex count and mitigate slow fragment shader performance inherent to pure splatting when close to the camera.

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of voxels $N$, $O(N)$, as each voxel generates a single point primitive [S1, S2, unofficial].
*   **Memory Complexity:** Linear with respect to $N$, storing packed voxel data in buffers [S1, S2, unofficial].
*   **Performance:** Performance is heavily dependent on fragment shader cost for large point sprites. Pure splatting can suffer from overdraw and expensive fragment processing when voxels are close to the camera [S1, unofficial]. Stochastic culling [S1, unofficial] and mipmapping [S2, unofficial] are used to mitigate this.
*   **Strengths:** Simple implementation using standard OpenGL point primitives; efficient for large, distant volumes; low vertex count compared to mesh-based voxel rendering.
*   **Limitations:** Poor performance for close-up views due to fragment shader load; potential aliasing artifacts if point sizing is not carefully managed; requires geometry shader or specific point sprite handling for proper 3D appearance [S1, S2, unofficial].
*   **When to use:** Rendering large-scale volumetric data where distant details are less critical, or as a fallback for simple visualization.
*   **When not to use:** High-fidelity close-up rendering where mesh geometry [5766-hybrid-voxel-rendering-mesh-splatting.md] or ray-traced methods are preferred.

## Background
Voxel Point Sprite Rendering is an unofficial technique demonstrated in open-source experiments [S1, S2, unofficial]. It leverages OpenGL's point sprite capabilities and geometry shaders to render volumetric data efficiently. The approach was explored in repositories such as `clayjohn/voxel-renderer` [S1, unofficial] and `sp4cerat/OpenGL-Voxel-Splatting` [S2, unofficial] as alternatives to traditional mesh-based voxel rendering.
