# Ray-Box Intersection via Quad Rasterization


## Overview
A voxel rendering technique where each voxel is represented by a single point primitive sized to cover the voxel's projected area, with the actual voxel geometry (cube) intersected with a ray in the fragment shader using an optimized ray-box intersection test [S1, unofficial]. It differs from sibling methods like [Sparse Voxel Octree Rendering via Square Splats](2993-sparse-voxel-octree-rendering-via-square-splats.md) by avoiding explicit cube face rasterization, instead relying on GPU point primitives and fragment-shader ray tracing to determine visibility [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A 3D grid of voxels defined by dimensions $(W, H, D)$ [S1, unofficial].
- Output: A rendered image where voxels are drawn as cubes if they intersect the view ray [S1, unofficial].

**Data Structures:**
The vertex data is packed into a single array of 32-bit unsigned integers [S1, unofficial]. For a grid of size $W \times H \times D$, there are $N = W \times H \times D$ vertices [S1, unofficial]. Each vertex is represented by two 32-bit integers:
1. `pos` (32 bits): Encodes the voxel coordinates [S1, unofficial].
   - Bits 0-10: $x$ coordinate (11 bits, range 0-2047) [S1, unofficial].
   - Bits 11-16: $y$ coordinate (6 bits, range 0-63) [S1, unofficial].
   - Bits 17-31: $z$ coordinate (15 bits, range 0-32767) [S1, unofficial].
   - Layout: `pos = x | (y << 11) | (z << 21)` [S1, unofficial].
2. `albedo` (32 bits): Encodes color [S1, unofficial].
   - Bits 0-4: Red (5 bits) [S1, unofficial].
   - Bits 5-10: Green (6 bits) [S1, unofficial].
   - Bits 11-15: Blue (5 bits) [S1, unofficial].
   - Bits 16-31: Unused/Alpha [S1, unofficial].
   - Layout: `albedo = r | (g << 5) | (b << 11)` [S1, unofficial].

**Shader Data Structures:**
- `Box`: `vec3 center`, `vec3 radius`, `vec3 invRadius`, `mat3 rotation` [S1, unofficial].
- `Ray`: `vec3 origin`, `vec3 direction` [S1, unofficial].

**Steps:**
1. **Vertex Generation:** For each voxel index $i$ from $0$ to $N-1$, compute $x = i \pmod W$, $y = \lfloor i / (W \times D) \rfloor$, and $z = \lfloor (i / W) \pmod D \rfloor$ [S1, unofficial]. Pack `pos` and `albedo` as described above [S1, unofficial]. Upload to a Vertex Buffer Object (VBO) bound to `GL_ARRAY_BUFFER` [S1, unofficial].
2. **Rendering Setup:** Enable `GL_PROGRAM_POINT_SIZE` [S1, unofficial]. Bind the vertex array object [S1, unofficial]. Issue a single `glDrawArrays(GL_POINTS, 0, N)` call [S1, unofficial].
3. **Vertex Shader:** The vertex shader receives the packed `pos` and `albedo` [S1, unofficial]. It reconstructs the voxel center in world space (or eye space, depending on pipeline design) [S1, unofficial]. The source code implies the point size is set to cover the cube's projected area [S1, unofficial]. Output `gl_Position` and pass `albedo` to the fragment shader [S1, unofficial].
4. **Fragment Shader:** Reconstruct the ray origin and direction [S1, unofficial]. Ray origin is the camera position in eye space (typically $(0,0,0)$ if camera is at origin) [S1, unofficial]. Fragment screen coordinates are `gl_FragCoord.xy` [S1, unofficial]. Eye-space position is obtained by unprojecting `gl_FragCoord` using the inverse projection matrix to get a point on the near plane, then transforming to eye space [S1, unofficial]. Ray direction is computed as the normalized vector from the eye-space position to the camera origin: $\text{ray.direction} = -\frac{\text{camera\_origin} - \text{eyePos}}{||\text{camera\_origin} - \text{eyePos}||}$ [S1, unofficial]. Define the voxel box with the center derived from vertex data and radius hardcoded to $0.05$ [S1, unofficial]. Call the intersection function with `rayCanStartInBox = false` and `oriented = false` to optimize for axis-aligned boxes where the ray starts outside [S1, unofficial]. If intersection fails, discard the fragment [S1, unofficial]. If intersection succeeds, compute the depth at the intersection point and write to `gl_FragDepth` to ensure correct depth testing [S1, unofficial].

**Pseudocode:**

```python
import math

def intersect_box(origin, direction, box_min, box_max, ray_can_start_in_box=False, oriented=False):
    """
    Optimized slab method for axis-aligned box intersection.
    Matches the MODE_QUAD implementation: oriented=False, ray_can_start_in_box=False.
    Handles zero direction components safely to prevent 0.0 * inf = nan.
    """
    t_min = -math.inf
    t_max = math.inf

    for i in range(3):
        # Guard against division by zero; 1e30 acts as infinity for slab constraints
        inv_dir = 1.0 / direction[i] if direction[i] != 0.0 else 1e30
        
        t1 = (box_min[i] - origin[i]) * inv_dir
        t2 = (box_max[i] - origin[i]) * inv_dir
        
        t_min = max(t_min, min(t1, t2))
        t_max = min(t_max, max(t1, t2))
        
        if t_max < t_min:
            return None

    if t_max < 0.0:
        return None

    if not ray_can_start_in_box and t_min < 0.0:
        t_min = 0.0

    return t_min

def compute_ray_direction(camera_origin, eye_pos):
    # Formula from [S1, unofficial]: ray.direction = -(camera_origin - eyePos) / ||camera_origin - eyePos||
    dx = camera_origin[0] - eye_pos[0]
    dy = camera_origin[1] - eye_pos[1]
    dz = camera_origin[2] - eye_pos[2]
    length = math.sqrt(dx*dx + dy*dy + dz*dz)
    return (-dx/length, -dy/length, -dz/length)
```

**Parameters:**
- Voxel radius: $0.05$ [S1, unofficial].
- `rayCanStartInBox`: `false` [S1, unofficial].
- `oriented`: `false` [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Division by Zero:** When computing distance to plane, if a ray direction component is zero, division by zero occurs. The code precomputes `invRayDirection = 1.0 / ray.direction` and passes it to avoid runtime division, assuming finite values [S1, unofficial]. The implementation must guard against `direction[i] == 0.0` to prevent `0.0 * inf = nan` during slab intersection [G].
- **Point Size:** The point size must be large enough to cover the voxel's projected area. If too small, voxels may be missed. If too large, overdraw increases [S1, unofficial].

## Operating characteristics
- **Time Complexity:** $O(N)$ for vertex processing, where $N$ is the number of voxels [S1, unofficial]. Fragment shader cost depends on the number of fragments generated by point rasterization [S1, unofficial].
- **Memory Complexity:** $O(N)$ for vertex storage [S1, unofficial].
- **Performance:** On dedicated graphics cards, MODE_QUAD is approximately twice as fast as MODE_CUBE (which rasterizes 3 cube faces per voxel) [S1, unofficial]. On Intel Integrated graphics, performance is similar [S1, unofficial].
- **Strengths:** Reduced vertex processing overhead compared to cube rasterization [S1, unofficial]. Single draw call [S1, unofficial].
- **Limitations:** Overdraw can be high if point size is large [S1, unofficial]. Precision issues in ray-box intersection if not handled carefully [S1, unofficial].

## Background
This method is described in a test project by Clay John, titled "A short test project in efficient voxel rendering" [S1, unofficial]. It references an optimized ray-box intersection test from the Journal of Computer Graphics Techniques (JCGT) [S1, unofficial]. The technique is part of a broader exploration of voxel rendering optimizations, contrasting with explicit cube face rasterization [S1, unofficial].
