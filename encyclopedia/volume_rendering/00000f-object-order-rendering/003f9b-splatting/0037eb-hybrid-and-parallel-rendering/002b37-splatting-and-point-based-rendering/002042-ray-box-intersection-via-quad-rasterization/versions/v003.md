# Ray-Box Intersection via Quad Rasterization


## Overview
A voxel rendering technique where each voxel is represented by a single point primitive sized to cover the voxel's projected area, with the actual voxel geometry (cube) intersected with a ray in the fragment shader using an optimized ray-box intersection test. It differs from sibling methods like [Sparse Voxel Octree Rendering via Square Splats](2993-sparse-voxel-octree-rendering-via-square-splats.md) by avoiding explicit cube face rasterization, instead relying on GPU point primitives and fragment-shader ray tracing to determine visibility.

## How it works
**Inputs and Outputs:**
- Input: A 3D grid of voxels defined by dimensions $(W, H, D)$. Each voxel is identified by integer coordinates $(x, y, z)$.
- Output: A rendered image where voxels are drawn as cubes if they intersect the view ray.

**Data Structures:**
The vertex data is packed into a single array of 32-bit unsigned integers. For a grid of size $W \times H \times D$, there are $N = W \times H \times D$ vertices. Each vertex is represented by two 32-bit integers:
1. `pos` (32 bits): Encodes the voxel coordinates.
   - Bits 0-10: $x$ coordinate (11 bits, range 0-2047).
   - Bits 11-16: $y$ coordinate (6 bits, range 0-63).
   - Bits 17-31: $z$ coordinate (15 bits, range 0-32767).
   - Layout: `pos = x | (y << 11) | (z << 17)` [S1, unofficial].
2. `albedo` (32 bits): Encodes color.
   - Bits 0-4: Red (5 bits).
   - Bits 5-10: Green (6 bits).
   - Bits 11-15: Blue (5 bits).
   - Bits 16-31: Unused/Alpha.
   - Layout: `albedo = r | (g << 5) | (b << 11)` [S1, unofficial].

**Shader Data Structures:**
- `Box`: `vec3 center`, `vec3 radius`, `vec3 invRadius`, `mat3 rotation` [S1, unofficial].
- `Ray`: `vec3 origin`, `vec3 direction` [S1, unofficial].

**Steps:**
1. **Vertex Generation:** For each voxel index $i$ from $0$ to $N-1$:
   - Compute $x = i \pmod W$.
   - Compute $y = \lfloor i / (W \times D) \rfloor$.
   - Compute $z = \lfloor (i / W) \pmod D \rfloor$.
   - Pack `pos` and `albedo` as described above.
   - Upload to a Vertex Buffer Object (VBO) bound to `GL_ARRAY_BUFFER`.
2. **Rendering Setup:**
   - Enable `GL_PROGRAM_POINT_SIZE`.
   - Bind the vertex array object.
   - Issue a single `glDrawArrays(GL_POINTS, 0, N)` call [S1, unofficial].
3. **Vertex Shader:**
   - The vertex shader receives the packed `pos` and `albedo`.
   - It reconstructs the voxel center in world space (or eye space, depending on pipeline design). The source code implies the point size is set to cover the cube's projected area. The exact point size calculation is not provided in the source, but it must be large enough to encompass the voxel's projection [S1, unofficial].
   - Output `gl_Position` and pass `albedo` to the fragment shader.
4. **Fragment Shader:**
   - **Ray Reconstruction:** Reconstruct the ray origin and direction.
     - Ray origin: Camera position in eye space (typically $(0,0,0)$ if camera is at origin).
     - Fragment screen coordinates: `gl_FragCoord.xy`.
     - Eye-space position: Unproject `gl_FragCoord` using the inverse projection matrix to get a point on the near plane, then transform to eye space.
     - Ray direction: Compute the normalized vector from the eye-space position to the camera origin.
       $$ \text{ray.direction} = -\frac{\text{camera\_origin} - \text{eyePos}}{||\text{camera\_origin} - \text{eyePos}||} $$
       [S1, unofficial].
   - **Ray-Box Intersection:**
     - Define the voxel box. The voxel center is derived from the vertex data. The radius is hardcoded to $0.05$ [S1, unofficial]. The box is axis-aligned, so rotation is identity.
     - Call the intersection function with `rayCanStartInBox = false` and `oriented = false` to optimize for axis-aligned boxes where the ray starts outside [S1, unofficial].
     - If intersection fails, discard the fragment.
     - If intersection succeeds, compute the depth at the intersection point and write to `gl_FragDepth` to ensure correct depth testing [S1, unofficial].

```python
    vec3 voxel_center = vec3(float(x), float(y), float(z));
    
    // Set point size to cover the voxel's projected area
    // Exact formula not provided in source, assumed to be calculated based on view frustum
    gl_PointSize = ...; 
    
    gl_Position = projection_matrix * view_matrix * vec4(voxel_center, 1.0);
    frag_albedo = vec4(float(albedo_r)/255.0, float(albedo_g)/255.0, float(albedo_b)/255.0, 1.0);
}

# Fragment Shader (GLSL-like)
void main() {
    // Reconstruct ray
    vec2 ndc = (gl_FragCoord.xy / viewport_size) * 2.0 - 1.0;
    vec4 eye_pos = inverse_projection_matrix * vec4(ndc, 0.0, 1.0);
    eye_pos /= eye_pos.w;
    
    vec3 ray_origin = vec3(0.0, 0.0, 0.0); // Camera at origin in eye space
    vec3 ray_direction = normalize(ray_origin - eye_pos.xyz);
    
    // Define box
    vec3 center = ...; // From vertex data
    vec3 radius = vec3(0.05); // Hardcoded
    vec3 inv_radius = 1.0 / radius;
    
    // Optimized ray-box intersection for axis-aligned box, ray outside
    bool hit = intersect_box(ray_origin, ray_direction, center, radius, inv_radius, false, false);
    
    if (!hit) {
        discard;
    }
    
    // Compute depth at intersection
    float t = ...; // Distance to intersection
    vec3 hit_point = ray_origin + t * ray_direction;
    float depth = -hit_point.z; // Assuming right-handed eye space, z is negative
    
    gl_FragDepth = depth;
    gl_FragColor = frag_albedo;
}
```

**Parameters:**
- Voxel radius: $0.05$ [S1, unofficial].
- `rayCanStartInBox`: `false` [S1, unofficial].
- `oriented`: `false` [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Division by Zero:** When computing distance to plane, if a ray direction component is zero, division by zero occurs. The code precomputes `invRayDirection = 1.0 / ray.direction` and passes it to avoid runtime division, assuming finite values [S1, unofficial].
- **Point Size:** The point size must be large enough to cover the voxel's projected area. If too small, voxels may be missed. If too large, overdraw increases.

## Operating characteristics
- **Time Complexity:** $O(N)$ for vertex processing, where $N$ is the number of voxels. Fragment shader cost depends on the number of fragments generated by point rasterization.
- **Memory Complexity:** $O(N)$ for vertex storage.
- **Performance:** On dedicated graphics cards, MODE_QUAD is approximately twice as fast as MODE_CUBE (which rasterizes 3 cube faces per voxel) [S1, unofficial]. On Intel Integrated graphics, performance is similar [S1, unofficial].
- **Strengths:** Reduced vertex processing overhead compared to cube rasterization. Single draw call.
- **Limitations:** Overdraw can be high if point size is large. Precision issues in ray-box intersection if not handled carefully.

## Background
This method is described in a test project by Clay John, titled "A short test project in efficient voxel rendering" [S1, unofficial]. It references an optimized ray-box intersection test from the Journal of Computer Graphics Techniques (JCGT) [S1, unofficial]. The technique is part of a broader exploration of voxel rendering optimizations, contrasting with explicit cube face rasterization.
