# 3D Gaussian Splatting Rendering (CPU-Sorted, Instanced)

Also called: 3DGS Weekend Renderer, Filament SplatNode Renderer

## Overview
A display-only rendering pipeline for trained 3D Gaussian Splatting (3DGS) scenes that projects 3D Gaussian distributions into 2D screen-space quads, sorts them by camera-space depth on the CPU, and renders them using hardware instancing with standard alpha blending [S1, S4, S5, unofficial]. It solves the problem of correct transparency compositing in 3DGS without requiring GPU compute shaders or writable GPU buffers (SSBO), which are often unavailable in constrained environments like WebGL or specific engine versions (e.g., Filament 1.71.5) [S4, unofficial]. Unlike the official tile-based CUDA rasterizer, this method relies on a CPU-side back-to-front sort and generic instanced drawing, trading raw performance for broad compatibility and implementation simplicity [S1, S4, unofficial].

## How it works
**Inputs:**
*   A set of $N$ 3D Gaussians defined by mean position $\mu \in \mathbb{R}^3$, covariance $\Sigma_{3D} \in \mathbb{R}^{3 \times 3}$ (or scale/rotation), opacity $\alpha \in [0,1]$, and spherical harmonic (SH) coefficients for color [S1, S5, unofficial].
*   Camera view matrix $V$ and projection matrix $P$ [S1, S4, unofficial].
*   Image resolution $(W, H)$ [S1, unofficial].

**Outputs:**
*   A 2D image buffer containing the composited RGB color and alpha channel [S3, S5, unofficial].

**Data Structures:**
1.  **Gaussian Attributes:** Stored in flat arrays or textures.
    *   *CPU/Upload Format:* Struct `GpuGaussian` containing `centroid` (vec3, 12 bytes), `opacity` (float, 4 bytes), `scale` (vec3, 12 bytes), `rotation` (vec4, 16 bytes), total 44 bytes [S1, unofficial].
    *   *GPU Texture Format (Filament/Web):* Two square RGBA16F textures of width $T_{width}$ [S4, S5, unofficial].
        *   `splatPositionScale`: Per-splat $xyz$ = center position (model space), $w$ = billboard half-extent (scale) [S4, S5, unofficial].
        *   `splatColorOpacity`: Per-splat $rgb$ = SH0 color (linear), $a$ = straight opacity [S4, S5, unofficial].
2.  **Sort Buffer:**
    *   *CPU:* Array of `SplatSortEntry` structs: `cameraZ` (float, 4 bytes), `splatIndex` (size_t, 8 bytes) [S1, unofficial].
    *   *JS/Web:* `depthMix` (BigInt64Array/Float32Array/Uint32Array view). Each splat occupies two consecutive floats: index at even offset $2j$, depth at odd offset $2j+1$ [S2, unofficial].
3.  **Geometry:** A single unit quad with vertices at $(-1,-1), (1,-1), (-1,1), (1,1)$ [S1, S4, unofficial].

**Steps:**

1.  **Frustum Culling:** Transform Gaussian means to camera space $\mu_{cam} = V \mu$. Project to image plane $\mu_{img}$. Discard Gaussians outside the image bounds or near/far planes (typically with a FOV margin ratio of 0.3) [S3, S5, unofficial].
2.  **Covariance Projection:** For each visible Gaussian, compute the 2D covariance $\Sigma_{2D}$ by projecting the 3D covariance $\Sigma_{3D}$ to screen space using the local affine approximation of the projective transformation (Jacobian $J$) [S1, S2, unofficial].
    *   Compute eigenvalues $\lambda_1, \lambda_2$ and eigenvectors of the upper $2 \times 2$ block of $\Sigma_{2D}$ [S1, unofficial].
    *   Apply jitter to diagonal elements: $a = \Sigma_{2D}[0,0] + 0.3$, $d = \Sigma_{2D}[1,1] + 0.3$ [S1, unofficial].
    *   Clamp eigenvalues: $\lambda_{1,2} = \max(\dots, 0.01)$ [S1, unofficial].
3.  **Bounding Box Calculation:** Determine the 3-sigma extent in pixels:
    $$ b_1 = 3.0 \sqrt{\lambda_1} e_1, \quad b_2 = 3.0 \sqrt{\lambda_2} e_2 $$
    where $e_1, e_2$ are the principal axes [S1, unofficial]. The bounding box in pixels is $[u_{min}, v_{min}, u_{max}, v_{max}]$ derived from $\mu_{img} \pm b_{1,2}$ [S3, unofficial].
4.  **Depth Sorting:**
    *   Compute camera-space depth $z_{cam}$ for each Gaussian mean [S1, S3, unofficial].
    *   Sort Gaussians in back-to-front order (increasing $z_{cam}$, assuming camera looks down negative Z) [S1, S3, unofficial].
    *   *Optimization:* Re-sort only when camera direction changes by >1% of the bounding radius or view-projection matrix changes significantly [S2, S4, unofficial].
5.  **Data Upload/Reordering:** Reorder Gaussian attributes (position, scale, color, opacity) according to the sorted indices. If using textures, upload sorted data to `splatPositionScale` and `splatColorOpacity` using NEAREST filtering and CLAMP_TO_EDGE wrapping [S1, S4, S5, unofficial].
6.  **Instanced Rendering:**
    *   Disable depth testing. Enable alpha blending: `glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA)` [S1, unofficial].
    *   Issue `glDrawArraysInstanced` (or equivalent) for the unit quad.
    *   *Batching:* If $N > 65535$, split into multiple draw calls (batches) due to 16-bit index buffer limits [S4, S5, unofficial].
7.  **Vertex Shader Execution:**
    *   For each instance $i$, fetch attributes from textures using `gl_InstanceID` [S4, unofficial].
    *   Compute clip space position: $clip = P V \mu_{cam}$ [S1, unofficial].
    *   Compute vertex offset in NDC:
        $$ \delta_{pixel} = quadCorner.x \cdot b_1 + quadCorner.y \cdot b_2 $$
        $$ \delta_{ndc} = \delta_{pixel} / (viewportSize \cdot 0.5) $$
    *   Set final position: $gl\_Position = vec4(ndc.xy + \delta_{ndc}, ndc.z, 1.0)$ [S1, unofficial].
    *   Pass `splatCoord` (quadCorner), `splatColor` (SH evaluation), and `splatOpacity` (sigmoid of raw opacity) to fragment shader [S1, unofficial].
8.  **Fragment Shader Execution:**
    *   Compute power term: $power = -4.5 \cdot (p_x^2 + p_y^2)$, where $(p_x, p_y)$ is the interpolated `splatCoord` [S1, unofficial].
    *   Discard if $power < -9.0$ (approx $e^{-9}$) [S1, unofficial].
    *   Compute final alpha: $\alpha = \min(0.99, \text{splatOpacity} \cdot \exp(power))$ [S1, unofficial].
    *   Discard if $\alpha < 0.001$ [S1, unofficial].
    *   Output `FragColor = vec4(splatColor, alpha)` [S1, unofficial].

def project_covariance_3d_to_2d(cov_3d, mean_cam, camera):
    """
    Projects 3D covariance to 2D screen space.
    Uses the Jacobian of the projection function.
    """
    # J is the 2x3 Jacobian of the projection at mean_cam
    J = compute_projection_jacobian(mean_cam, camera)
    # Sigma_2D = J * Sigma_3D * J^T
    cov_2d = J @ cov_3d @ J.T
    return cov_2d[:2, :2] # Return 2x2

def sigmoid(x):
    return 1.0 / (1.0 + np.exp(-x))

def eval_sh0(sh_coeffs):
    """Evaluate SH degree 0 (constant color)."""
    return sh_coeffs[0] # Assuming first coeff is base color

def get_scale_from_cov(cov_2d):
    """Extract max-axis scale for isotropic billboard."""
    # Simplified: use trace or max eigenvalue
    return np.sqrt(np.max(np.linalg.eigvals(cov_2d))) * 3.0 # 3-sigma

## Subtopics

### [Tiled 2D Gaussian Splatting Rasterization](2061-tiled-2d-gaussian-splatting-rasterization.md)
Tiled 2D Gaussian Splatting Rasterization is a highly optimized, GPU-parallel method for rendering 3D Gaussian Splatting scenes in real-time. It partitions the image plane into macro-tiles (typically 16x16 or 32x32 pixels) and assigns CUDA thread blocks to each tile, allowing threads to cooperatively fetch sorted Gaussians and accumulate pixel color via iterative alpha-blending. Unlike parent methods that sort on the CPU, this approach performs device-side sorting and rasterization, enabling differentiable gradient computation for training. It sets itself apart from non-tiled approaches by managing memory and processing load through spatial partitioning, and from screen-space quad methods by explicitly handling tile-boundary data and depth-sorted accumulation.

### [Gaussian Splat Rendering (Screen-Space Quad)](2075-gaussian-splat-rendering-screen-space-quad.md)
This method renders 3D Gaussian splats as screen-space quads using a pre-sorted order buffer and view-space projection data, handling transparency via alpha blending and discarding fragments behind the camera or with negligible alpha. It projects voxels as 2D quads identical in geometry generation to Circle Splat, used for Gaussian Splat visualization. Unlike its parent [3D Gaussian Splatting Rendering (CPU-Sorted, Instanced)](2058-3d-gaussian-splatting-rendering-cpu-sorted-instanced.md), which relies on generic instanced drawing, this method explicitly constructs screen-space deltas in the vertex shader to ensure correct perspective projection of the elliptical splat shapes. It differs from sibling [Tiled 2D Gaussian Splatting Rasterization](2061-tiled-2d-gaussian-splatting-rasterization.md) by using a global depth-sorted list rather than tile-based sorting.

### [Depth-First Splat Sorting](2850-depth-first-splat-sorting.md)
Depth-First Splat Sorting is a preprocessing step for 3D Gaussian Splatting rendering that sorts visible Gaussian splats by camera-space depth before they are expanded into per-tile fragments. It solves the problem of high sorting overhead inherent in the original 3DGS pipeline, where fragments (one per tile a splat touches) are sorted using a combined 48-bit key. By sorting the smaller set of visible splats first, this method reduces the number of items to sort by a factor of 1.5 to 4, significantly lowering computational cost while maintaining correct depth ordering for subsequent rasterization.

### [Splatapult Gaussian Splat Renderer](6749-splatapult-gaussian-splat-renderer.md)
Splatapult is a CPU-sorted, instanced renderer for 3D Gaussian Splatting (3DGS) scenes that performs depth sorting on the GPU using a multi-radix sort algorithm or falls back to a CPU-based radix sort. It projects 3D Gaussians into screen-space quads and renders them using standard alpha blending, supporting VR via OpenXR and optional full spherical harmonic (SH) color evaluation. It distinguishes itself from sibling renderers by providing a complete, standalone implementation of the GPU-based sorting pipeline required for correct depth ordering in instanced rendering, rather than relying on external libraries or CPU-only sorting.

### [SortFree Weighting](8006-sortfree-weighting.md)
An Order-Independent Transparency (OIT) approximation that replaces depth sorting with a commutative weighted-sum blending scheme, weighting Gaussians by depth and view direction.

### Unity Mobile Implementation
A variant implementation for Unity mobile platforms that sorts all Gaussians by z-axis in camera coordinates from near to far and draws one front-parallel quad primitive for every visible Gaussian centered at its position [S6, unofficial]. The fragment shader emits color with alpha pre-multiplication and uses blend function `(ONE, ONE_MINUS_SRC_ALPHA)` [S6, unofficial]. It supports an export pipeline converting canonical meshes to .obj (for Mixamo autorigging), .ply (Gaussians), .json (embedding), and .fbx (from Mixamo) [S6, unofficial]. Performance reports over 300 FPS on modern GPUs and steady 30 FPS on iPhone 13 [S6, unofficial].

## Operating characteristics
**Time Complexity:**
*   Sorting: $O(N \log N)$ on CPU. Radix sort of ~500k depth keys takes a few milliseconds on a worker thread [S4, unofficial].
*   Rendering: $O(N)$ for upload and draw calls. Instanced draw call is $O(1)$ in terms of vertex processing overhead per frame, but dominated by fragment shading [S4, unofficial].
*   Re-sorting is gated on camera motion (>1% bounding radius delta) to avoid per-frame overhead [S4, unofficial].

**Memory Complexity:**
*   Storage: ~28 bytes/splat in RGBA16F textures for SH0. A 500k splat scene uses ~14 MB VRAM [S4, unofficial].
*   Sort Buffer: $O(N)$ for depth/index arrays [S1, S2, unofficial].

**Performance:**
*   Mobile-GS reports up to 127 FPS on modern mobile GPUs using first-order SH distillation and OIT [S4, unofficial].
*   CPU sort is significantly slower than GPU tile-based rasterization but avoids the need for compute shaders [S1, S4, unofficial].
*   Blending validation on 8k splats shows stable performance with low mean-abs-diff [S4, unofficial].

**Strengths:**
*   Compatible with engines lacking compute shaders (e.g., Filament 1.71.5, WebGL) [S4, unofficial].
*   Simple implementation using standard instanced rendering [S1, unofficial].
*   Works well for mid-range mobile and web targets [S4, S5, unofficial].

**Limitations:**
*   Less efficient than tile-based GPU rasterization [S1, unofficial].
*   Limited to SH0 or SH1 on mid-range Android due to VRAM constraints (SH3 is prohibitive) [S4, unofficial].
*   P1 scope often limited to isotropic billboards (max-axis scale) rather than full anisotropic 2D covariance ellipses [S5, unofficial].
*   Requires batching for $N > 65535$ due to 16-bit index limits [S4, unofficial].

**When to Use:**
*   When GPU compute shaders are unavailable.
*   For web-based viewers or mobile apps where simplicity and compatibility are prioritized over maximum FPS.
*   For debugging or display-only tools [S1, unofficial].

**When Not to Use:**
*   For real-time training where differentiable GPU rasterization is required [S2, unofficial].
*   For very large scenes ($>1$ million splats) on low-end hardware where CPU sorting becomes a bottleneck [S1, unofficial].

## Background
Originating from the paper "3D Gaussian Splatting for Real-Time Radiance Field Rendering" by Kerbl et al. (2023) [S1, unofficial], this rendering method was adapted to work within the constraints of specific graphics engines like Google Filament. The CPU-sorted, instanced approach was developed as a practical solution for Android and Web platforms where GPU compute shaders were not available in the target engine version (Filament 1.71.5) [S4, unofficial]. It is implemented in `sceneview-core`, `sceneview` (Android), and `sceneview-web` (Kotlin/JS + Filament.js) [S4, unofficial].
