# Text Embedding Generation with Directional Views


## Overview
This method generates semantic text embeddings conditioned on specific camera viewpoints to enable view-dependent semantic understanding in 3D Gaussian Splatting. It solves the problem of static text features failing to capture directional appearance variations by appending view descriptors (e.g., "front view") to text prompts before encoding [S1, unofficial][S2]. Unlike standard semantic splatting which uses a single global text embedding per Gaussian, this approach generates distinct embeddings for different viewing angles, allowing the renderer to match visual content with directional textual descriptions [S1, unofficial][S2].

## How it works
The method consists of two phases: offline embedding generation and runtime prompt conditioning.

### Inputs and Outputs
- **Inputs**: A base text prompt string (e.g., "a chair"), a list of view directions, and a frozen CLIP text encoder.
- **Outputs**: A dictionary of pre-computed text embeddings mapping view keys to tensors.

### Data Structures
The embeddings are stored in a dictionary `self.embeddings` [S1, unofficial].
- **Keys**: `'pos'`, `'neg'`, `'front'`, `'side'`, `'back'` [S1, unofficial].
- **Values**: Tensors of shape `[1, 77, 768]` representing `[batch_size, sequence_length, embedding_dimension]` [S1, unofficial].
- **Note**: The sequence length 77 and dimension 768 correspond to the standard CLIP ViT-L/14 text encoder configuration [S1, unofficial].

### Steps

1. **Initialize Tokenizer and Encoder**: Load the frozen CLIP text encoder and tokenizer [S1, unofficial].
2. **Generate Base Embeddings**:
   - Tokenize the base prompt with padding to the maximum length:
     $$ \text{inputs} = \text{tokenizer}(\text{prompt}, \text{padding}="max\_length", \text{max\_length}=77, \text{return\_tensors}="pt") $$
   - Pass token IDs through the text encoder:
     $$ \text{embeddings} = \text{text\_encoder}(\text{inputs.input\_ids})[0] $$
   - Store these as the `'pos'` (positive) embedding [S1, unofficial].
3. **Generate Directional Embeddings**:
   - For each view direction $d \in \{\text{'front'}, \text{'side'}, \text{'back'}\}$:
     - Append the view descriptor to the prompt: $\text{prompt}_d = \text{prompt} + \text{', ' + d + ' view'}$ [S1, unofficial].
     - Tokenize and encode $\text{prompt}_d$ using the same process as Step 2.
     - Store the result in `self.embeddings[d]` [S1, unofficial].
4. **Runtime Conditioning (Optional Variant)**:
   - In some implementations (e.g., Blended-NeRF), instead of pre-computing all views, the view-dependent suffix is concatenated to the prompt dynamically during training iterations based on the current camera position [S2].
   - Available suffixes: `', top-down view'`, `', front view'`, `', side view'`, `', back view'` [S2].
   - For forward-facing scenes (e.g., LLFF dataset), only `', top-down view'`, `', front view'`, and `', side view'` are used [S2].

### Pseudocode

```python
import torch
from transformers import CLIPTextModel, CLIPTokenizer

def generate_directional_embeddings(base_prompt, device="cuda"):
    """
    Generate text embeddings for a base prompt and specific directional views.
    
    Args:
        base_prompt (str): The core semantic description (e.g., "a chair").
        device (str): Device to run the model on.
        
    Returns:
        dict: Dictionary mapping view keys to embedding tensors.
    """
    # Load frozen CLIP model and tokenizer
    # Note: In a real implementation, these are loaded once globally.
    # model_name = "openai/clip-vit-large-patch14"
    # tokenizer = CLIPTokenizer.from_pretrained(model_name)
    # text_encoder = CLIPTextModel.from_pretrained(model_name).to(device).eval()
    
    # Placeholder for loaded components [G]
    tokenizer = None 
    text_encoder = None
    
    # 1. Tokenize base prompt
    # Max length for CLIP text encoder is typically 77 tokens
    inputs = tokenizer(
        base_prompt, 
        padding="max_length", 
        max_length=77, 
        return_tensors="pt"
    ).to(device)
    
    # 2. Encode base prompt
    with torch.no_grad():
        base_embed = text_encoder(inputs.input_ids)[0]
        
    embeddings = {
        "pos": base_embed,
        "neg": -base_embed # Negative embedding for contrastive loss [G]
    }
    
    # 3. Generate directional embeddings
    directions = ['front', 'side', 'back']
    
    for d in directions:
        # Append view descriptor
        directional_prompt = f"{base_prompt}, {d} view"
        
        # Tokenize
        dir_inputs = tokenizer(
            directional_prompt, 
            padding="max_length", 
            max_length=77, 
            return_tensors="pt"
        ).to(device)
        
        # Encode
        with torch.no_grad():
            dir_embed = text_encoder(dir_inputs.input_ids)[0]
            
        embeddings[d] = dir_embed
        
    return embeddings

def get_runtime_prompt(base_prompt, camera_view_direction):
    """
    Get the appropriate prompt suffix for runtime conditioning.
    
    Args:
        base_prompt (str): The core semantic description.
        camera_view_direction (str): One of 'top-down', 'front', 'side', 'back'.
        
    Returns:
        str: The full prompt string.
    """
    suffixes = {
        "top-down": ", top-down view",
        "front": ", front view",
        "side": ", side view",
        "back": ", back view"
    }
    
    if camera_view_direction in suffixes:
        return f"{base_prompt}{suffixes[camera_view_direction]}"
    else:
        return base_prompt
```

### Parameters and Edge Cases
- **Max Length**: 77 tokens [S1, unofficial].
- **Embedding Dimension**: 768 [S1, unofficial].
- **Forward-Facing Scenes**: When using datasets like LLFF, the `'back'` view suffix is omitted, and only `'top-down'`, `'front'`, and `'side'` are utilized [S2].
- **Pitfall**: The view descriptors must be appended exactly as strings (e.g., `', front view'`) to ensure the tokenizer produces the correct semantic shift [S1, unofficial][S2].

## Subtopics

### [TexGS-VolVis Representation and Optimization](11105-texgs-volvis-representation-and-optimization.md)
TexGS-VolVis is a method for representing and editing volume visualization (VolVis) scenes using textured 2D Gaussian Splatting (2DGS). It solves the problem of decoupling geometry from appearance in text-driven non-photorealistic style editing (NPSE), allowing for geometry-consistent stylization without the elliptical artifacts common in coupled representations. Unlike methods that freeze geometry to prevent distortion, TexGS-VolVis uses explicit 2D texture maps to store appearance, preserving geometric fidelity while enabling rich visual expressiveness.

## Operating characteristics
- **Time Complexity**: Embedding generation is $O(V \cdot L)$, where $V$ is the number of views and $L$ is the sequence length (77). This is a one-time offline cost or per-iteration cost if done dynamically [S1, unofficial][S2].
- **Memory Complexity**: Stores $V$ embeddings of size $[1, 77, 768]$. For 4 views, this is negligible compared to Gaussian attributes [S1, unofficial].
- **Strengths**: Enables fine-grained control over semantic content based on viewing angle, improving alignment in multi-view generation tasks [S1, unofficial][S2].
- **Limitations**: Requires pre-computation or dynamic prompt construction, adding slight overhead to the training loop [S2].

## Background
The method originates from DreamGaussian, which introduced directional view embeddings to improve text-to-3D generation by conditioning the text encoder on camera viewpoints [S1, unofficial]. It was further adapted in Blended-NeRF for zero-shot object generation and blending, where directional prompts are concatenated dynamically during training [S2].
