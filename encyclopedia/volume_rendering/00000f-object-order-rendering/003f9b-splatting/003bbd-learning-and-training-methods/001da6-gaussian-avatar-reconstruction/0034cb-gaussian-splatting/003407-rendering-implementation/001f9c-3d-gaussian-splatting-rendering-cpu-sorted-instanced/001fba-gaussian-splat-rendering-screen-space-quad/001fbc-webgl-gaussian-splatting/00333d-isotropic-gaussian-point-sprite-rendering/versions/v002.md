# Isotropic Gaussian Point-Sprite Rendering

Also called: Gaussian-opacity point sprites, Soft Gaussian primitives

## Overview
A rendering technique using isotropic 3D point primitives with a Gaussian alpha falloff in screen space, rendered via custom GLSL shaders [S1, unofficial]. It demonstrates soft Gaussian opacity and transparency but does not implement full 3D Gaussian Splatting (no anisotropic covariance, no spherical harmonics, no GPU tile-based rasterization) [S1, unofficial]. It sets itself apart from its sibling [WebGL Gaussian Splatting](2084-webgl-gaussian-splatting.md) by explicitly implementing a CPU-side back-to-front sort to correct the arbitrary alpha blending order inherent in `THREE.Points`, whereas the parent article describes the general bounding quad approach without detailing the specific sorting mechanism for isotropic sprites [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A `THREE.Points` object containing attributes: `position` (vec3), `aColor` (vec3), and `aRadius` (float) [S1, unofficial].
*   **Uniforms:** `uScale` (float), `uPixelRatio` (float), `uPointMode` (float, 0.0 for Gaussian, 1.0 for hard-edged), `uOpacity` (float) [S1, unofficial].
*   **Output:** Screen-space pixels with color and alpha, composited using standard source-over blending [S1, unofficial].

**Data Structures:**
*   `THREE.BufferGeometry` with `Float32Array` attributes for positions, colors, and radii [S1, unofficial].
*   CPU-side index array for sorting [S1, unofficial].

**Numbered Steps:**

1.  **Vertex Shader Execution:**
    For each point primitive:
    a.  Compute the model-view position: `mv = modelViewMatrix * vec4(position, 1.0)` [S1, unofficial].
    b.  Calculate screen-space radius in pixels:
        $$ \text{radiusPixels} = \text{aRadius} \times \text{uScale} \times 220.0 \times \text{uPixelRatio} / \max(1.0, -\text{mv.z}) $$ [S1, unofficial].
    c.  Set `gl_PointSize` by clamping the radius scaled by the point mode factor:
        $$ \text{gl\_PointSize} = \text{clamp}(\text{radiusPixels} \times \text{mix}(1.0, 0.22, \text{uPointMode}), 1.0, 150.0 \times \text{uPixelRatio}) $$ [S1, unofficial].
    d.  Pass color to fragment shader: `vColor = aColor` [S1, unofficial].

2.  **Fragment Shader Execution:**
    For each fragment covered by the point sprite:
    a.  Compute normalized sprite coordinates: `p = gl_PointCoord * 2.0 - 1.0` [S1, unofficial].
    b.  Calculate squared distance from center: `r2 = dot(p, p)` [S1, unofficial].
    c.  Discard fragment if `r2 > 1.0` [S1, unofficial].
    d.  Compute alpha:
        $$ \alpha = \text{mix}(\exp(-4.5 \times r^2), 1.0, \text{uPointMode}) \times \text{uOpacity} $$ [S1, unofficial].
        Where $r = \sqrt{r2}$ [S1, unofficial].
    e.  Discard fragment if $\alpha < 0.008$ [S1, unofficial].
    f.  Output `gl_FragColor = vec4(vColor, alpha)` [S1, unofficial].

3.  **CPU-Side Back-to-Front Sorting:**
    To ensure correct transparency compositing:
    a.  Trigger sort when camera changes (`dirtySort = true`) [S1, unofficial].
    b.  Compute camera depth for each point $i$ using the inverse world matrix $M$:
        $$ z_i = M_{2}x_i + M_{6}y_i + M_{10}z_i + M_{14} $$ [S1, unofficial].
        Where $M$ is the 16-element array of `camera.matrixWorldInverse.elements`, and $(x_i, y_i, z_i)$ are the world-space coordinates of point $i$ [S1, unofficial].
    c.  Sort indices by $z_i$ ascending (more negative is farther) [S1, unofficial].
    d.  Reorder `position`, `aColor`, and `aRadius` arrays in the `THREE.BufferGeometry` attributes according to the sorted indices [S1, unofficial].
    e.  Set `needsUpdate = true` on the attributes [S1, unofficial].

**Pseudocode:**

```python
import math

def mix(a, b, t):
    return a + t * (b - a)

def clamp(x, lo, hi):
    return max(lo, min(x, hi))

def dot(a, b):
    return sum(x * y for x, y in zip(a, b))

def vec4(x, y, z, w):
    return [x, y, z, w]

def vertex_shader(position, aColor, aRadius, modelViewMatrix, uScale, uPixelRatio, uPointMode):
    # position is vec3, aColor is vec3, aRadius is float
    mv = [sum(modelViewMatrix[r][c] * (position[c] if c < 3 else 1.0) for c in range(4)) for r in range(4)]
    mv_z = mv[2]

    vColor = aColor
    gl_Position = [sum(mv[c] * (projectionMatrix[c][r] if False else 0) for c in range(4)) for r in range(4)]

    radius_pixels = aRadius * uScale * 220.0 * uPixelRatio / max(1.0, -mv_z)
    scale_factor = mix(1.0, 0.22, uPointMode)
    gl_PointSize = clamp(radius_pixels * scale_factor, 1.0, 150.0 * uPixelRatio)

    return vColor, gl_Position, gl_PointSize

def fragment_shader(vColor, uOpacity, uPointMode, point_coord):
    # point_coord is vec2 in [0, 1]
    p = [point_coord[0] * 2.0 - 1.0, point_coord[1] * 2.0 - 1.0]
    r2 = dot(p, p)

    if r2 > 1.0:
        return None  # discard

    gaussian_alpha = math.exp(-4.5 * r2)
    alpha = mix(gaussian_alpha, 1.0, uPointMode) * uOpacity

    if alpha < 0.008:
        return None  # discard

    return [vColor[0], vColor[1], vColor[2], alpha]  # gl_FragColor

def sort_back_front(m_flat, positions, colors, radii, count):
    indices = list(range(count))

    def get_depth(idx):
        i3 = idx * 3
        return m_flat[2]*positions[i3] + m_flat[6]*positions[i3+1] + m_flat[10]*positions[i3+2] + m_flat[14]

    indices.sort(key=get_depth)

    for attr_name, attr in [("position", positions), ("aColor", colors), ("aRadius", radii)]:
        if attr_name in ("position", "aColor"):
            new_data = [attr[i*3 + k] for i in indices for k in range(3)]
        else:
            new_data = [attr[i] for i in indices]
        attr[:] = new_data
        needsUpdate = True
```

**Parameters:**
*   `uOpacity`: Peak opacity multiplier. Typical value: 1.0 [S1, unofficial].
*   `uPointMode`: Switch between Gaussian (`0.0`) and hard-edged (`1.0`) [S1, unofficial].
*   `uScale`: Global scale factor for point sizes [S1, unofficial].
*   `uPixelRatio`: Device pixel ratio (e.g., 1.0 or 2.0) [S1, unofficial].
*   Sorting Cadence: Performed approximately every 150 ms while the camera is moving [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Alpha Blending Order:** Three.js does not automatically sort individual points inside a `THREE.Points` object [S1, unofficial]. Without sorting, alpha blending order is arbitrary, leading to incorrect transparency [S1, unofficial].
*   **Depth Calculation:** The depth $z_i$ is computed in view space using the inverse world matrix [S1, unofficial]. More negative values indicate points farther from the camera [S1, unofficial].
*   **Precision:** The alpha discard threshold is `0.008` [S1, unofficial]. Values below this are discarded to optimize rendering [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Sorting is $O(N \log N)$ where $N$ is the number of points [G]. This is performed on the CPU, causing overhead [S1, unofficial].
*   **Memory Complexity:** $O(N)$ for storing positions, colors, radii, and the index array [G].
*   **Measured Performance:** The CPU sort introduces latency, especially with large $N$ [S1, unofficial]. The approximate update cadence (150 ms) mitigates this but results in visual jitter if the camera moves rapidly [S1, unofficial].
*   **Strengths:** Simple implementation using standard WebGL point sprites; visually demonstrates Gaussian opacity; works in browsers via Three.js [S1, unofficial].
*   **Limitations:** No anisotropic covariance (sprites are always circular); no spherical harmonics (view-independent color); no GPU-based tile rasterization; CPU sorting bottleneck [S1, unofficial].
*   **When to use:** Educational demos, simple browser-based visualizations where high performance is not critical [S1, unofficial].
*   **When not to use:** Production 3DGS rendering, scenes with millions of points, or when anisotropic splats are required [S1, unofficial].

## Background
Originating from an interactive browser-based experiment exploring Gaussian point-sprite rendering with Three.js and custom GLSL shaders [S1, unofficial]. Built as an educational graphics demo to understand the basic visual effect of soft Gaussian primitives and transparency, not as a full 3D Gaussian Splatting (3DGS) implementation [S1, unofficial]. It references Kerbl et al. for the underlying 3DGS concept but explicitly states it does not reconstruct scenes from photos or implement production 3DGS [S1, unofficial].
