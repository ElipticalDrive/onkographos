# Backpropagation with Per-Splat Parallelization

Also called: Per-splat backward, Per-splat parallelization, Recursive Per-Splat Parallelization for Backward Propagation, Splat-parallel backprop, Warp-level gradient accumulation

## Overview
This method is a GPU kernel optimization for the backward pass of 3D Gaussian Splatting that eliminates atomic contention by parallelizing over 2D splats rather than pixels [S1][S2, unofficial]. It solves the bottleneck where multiple threads contend for the same memory locations when atomically adding gradients to Gaussian attributes [S2, unofficial]. Unlike the original 3DGS approach which maps threads to pixels and requires strict depth-sorted traversal, this method allows threads to maintain per-splat state and exchange smaller per-pixel states (transmittance and color) via intra-warp shuffling, enabling order-independent processing and avoiding redundant computations [S1][S2, unofficial].

## How it works
**Inputs and Outputs:**
- **Input:** A tile of pixels (typically 256 pixels), a set of depth-sorted 3D Gaussians projected to 2D splats covering the tile, and stored intermediate states from the forward pass.
- **Output:** Accumulated gradients for all Gaussian parameters (position, scale, rotation, opacity, spherical harmonics coefficients) within the tile.

**Data Structures:**
- **Per-Pixel State:** A tuple $(T_j, C_j)$ for each pixel $j$, where $T_j$ is the accumulated transmittance and $C_j$ is the accumulated color. Size: $2 \times 4$ bytes (float32) per pixel, or 8 bytes.
- **Per-Splat State:** Maintained by the thread processing the splat. Includes current gradient accumulators for the splat's attributes.
- **Autodiff Context (Forward Pass):** Stores one per-pixel state every $N$ splats (where $N$ is the bucket size, typically 32) for each pixel in the tile. Layout: Array of size $\lceil \text{NumSplats} / N \rceil \times \text{NumPixels}$, storing $(T, C)$ pairs.

**Parameters:**
- **Bucket Size ($N$):** 32. Matches the CUDA warp size. Splats are divided into buckets of this size [S1].
- **Tile Size:** 256 pixels. Partitioned into 8 groups of 32 pixels [S2, unofficial].

**Numbered Steps:**

1.  **Forward Pass Storage:** During the forward rasterization, for each pixel $j$ in the tile, store the per-pixel state $(T_j, C_j)$ after every $N$-th splat (where $N=32$) into the autodiff context. This provides starting states $(0, j), (N, j), \dots$ for all pixels $j$ [S1].

2.  **Backward Pass Initialization:** For each tile, partition the 256 pixels into 8 groups of 32 pixels, matching the warp size. Each thread in the warp (lane $l \in [0, 31]$) is responsible for one pixel in the group [S2, unofficial]. Each thread generates the initial pixel state $(i, j)$ for the current backward bucket from the stored starting states [S1].

3.  **Warp-Level State Fetching:** Within a warp, every lane $l$ fetches the per-pixel state for its corresponding pixel $j_l$ from global memory or shared memory. Crucially, each group of 32 pixels is fetched only once per warp [S2, unofficial].

4.  **Recursive State Circulation (Inner Loop):**
    For each bucket of $N=32$ splats:
    a.  **State Exchange:** Threads exchange per-pixel states via fast intra-warp shuffling (e.g., `__shfl_sync`). Each thread sends its current pixel state to other lanes and receives states for other pixels in the group [S1][S2, unofficial].
    b.  **Gradient Accumulation:** For each splat $s$ in the bucket:
        i.  Thread $i$ (associated with splat $i$) receives the per-pixel state $(T_j, C_j)$ for pixel $j$ from the previous splat in the blending order (or from the stored state if $i=0$).
        ii. Thread $i$ applies the alpha blending logic to compute the contribution of splat $s$ to pixel $j$. The new state $(T'_j, C'_j)$ is computed as:
        $$ T'_j = T_j \cdot (1 - \alpha_s) $$
        $$ C'_j = C_j + \alpha_s \cdot c_s \cdot T_j $$
        where $\alpha_s$ is the opacity of splat $s$ at pixel $j$, and $c_s$ is the color of splat $s$.
        iii. Thread $i$ computes the gradient of the loss with respect to the splat's parameters using the chain rule, incorporating the change in transmittance and color.
        iv. Thread $i$ updates the per-pixel state for the next splat: $(T_j, C_j) \leftarrow (T'_j, C'_j)$.
        v. Thread $i$ atomically adds the computed gradients to the global Gaussian attribute buffers. *Note: In this per-splat parallelization, each thread handles one splat, so atomic contention is reduced to one thread per splat, avoiding the many-to-one contention of the pixel-parallel approach* [S1][S2, unofficial].
    c.  **Shuffle:** After processing the splat, threads shuffle the updated per-pixel states to prepare for the next splat in the bucket [S1].

5.  **Repeat:** Repeat step 4 for all 8 groups of pixels (since 256 pixels / 32 pixels per group = 8 groups). This completes the tile-internal gradient computation [S2, unofficial].

6.  **Optimization: Last Contributor Tracking:** Track the last contributing splat for each pixel during the forward pass. In the backward pass, skip entire groups of splat-tile pairings where the splat is fully occluded (i.e., transmittance $T_j \approx 0$) [S1].

7.  **Optimization: Tighter Culling:** Apply tighter culling strategies (e.g., as proposed by Radl et al. [2024]) to minimize redundant splats in both forward and backward passes [S1].

**Pseudocode:**

```python
# Assumptions:
# - Warp size W = 32
# - Tile has P = 256 pixels, partitioned into G = 8 groups of W pixels
# - Splats are sorted by depth (front-to-back)
# - bucket_size = 32
# - stored_states[pixel_idx][bucket_idx] = (T, C) from forward pass

def backward_per_splat_parallelization(tile_splats, stored_states, loss_gradients):
    # tile_splats: list of splats covering the tile, sorted front-to-back
    # stored_states: dict mapping (pixel_idx, bucket_idx) -> (T, C)
    
    num_splats = len(tile_splats)
    num_buckets = (num_splats + bucket_size - 1) // bucket_size
    
    # Initialize gradient accumulators for all splats in the tile
    splat_gradients = {splat_id: zeros_like(splat_params) for splat_id in tile_splats}
    
    for bucket_idx in range(num_buckets):
        start_splat = bucket_idx * bucket_size
        end_splat = min(start_splat + bucket_size, num_splats)
        current_bucket_splats = tile_splats[start_splat:end_splat]
        
        # Process each group of 32 pixels
        for group_idx in range(8):
            pixel_indices = [group_idx * 32 + lane for lane in range(32)]
            
            # Fetch initial states for this group from stored_states
            # Each lane l fetches state for pixel_indices[l] at bucket_idx
            lane_states = [None] * 32
            for l in range(32):
                p_idx = pixel_indices[l]
                if (p_idx, bucket_idx) in stored_states:
                    lane_states[l] = stored_states[(p_idx, bucket_idx)]
                else:
                    # Default state if not stored (e.g., first bucket)
                    lane_states[l] = (1.0, (0.0, 0.0, 0.0)) # T=1, C=0
            
            # Intra-warp shuffle to distribute states
            # Each thread now has the state for its assigned pixel
            # But we need to process all splats in the bucket for all pixels
            
            # For each splat in the current bucket
            for splat in current_bucket_splats:
                # Compute splat contribution for each pixel in the group
                # This part is done in parallel by the 32 threads
                # Thread l computes for pixel_indices[l]
                
                # Get current state for pixel l
                T, C = lane_states[l]
                
                # Compute alpha and color for splat at pixel l
                alpha, color = compute_splat_contribution(splat, pixel_indices[l])
                
                # Compute new state
                new_T = T * (1 - alpha)
                new_C = C + alpha * color * T
                
                # Compute gradient for this splat at this pixel
                # dL/dParams = dL/dC * dC/dParams + dL/dT * dT/dParams
                # ... (standard chain rule for alpha compositing)
                grad = compute_gradient(loss_gradients[pixel_indices[l]], alpha, color, T, C)
                
                # Accumulate gradient for the splat
                # Since each thread handles one splat, no atomic contention for this splat
                splat_gradients[splat.id] += grad
                
                # Update state for next splat
                lane_states[l] = (new_T, new_C)
                
                # Shuffle updated states to other lanes? 
                # Actually, each thread maintains its own pixel's state for the next splat
                # No need to shuffle between threads for different pixels, 
                # but we might need to ensure all threads have the correct state for the next splat
                # In this design, each thread is responsible for one pixel across all splats
                # So lane_states[l] is updated in place for the next splat iteration
                
            # After processing all splats in the bucket, the final states are in lane_states
            # These can be used for the next bucket or for final accumulation
            
    return splat_gradients
```

**Edge Cases and Pitfalls:**
- **Precision:** Floating-point precision issues may arise when transmittance $T$ becomes very small. Use epsilon guards if necessary [G].
- **Boundaries:** Handle splats that partially cover the tile. The culling optimization must correctly identify splats that contribute to no pixels in the tile [S1].
- **Degenerate Input:** If a splat has zero opacity or is completely outside the tile, it should be skipped in both forward and backward passes [S1].

## Operating characteristics
- **Time Complexity:** $O(N_{splats} \cdot N_{pixels})$ per tile, but with reduced constant factors due to avoided atomic contention and redundant computations.
- **Memory Complexity:** $O(N_{pixels})$ for storing per-pixel states in shared memory/warp registers. Forward pass storage is $O(N_{splats} \cdot N_{pixels} / N)$ for checkpointing [S1].
- **Measured Performance:** Significantly faster than original 3DGS backward pass, especially for high-resolution scenes with many Gaussians. Avoids the serialization caused by atomic operations [S1][S2, unofficial].
- **Scaling:** Scales well with the number of Gaussians and pixels. The per-splat parallelization ensures that each thread does useful work without waiting for atomic locks [S1].
- **Strengths:** Eliminates atomic contention, avoids redundant computations from strict depth-order traversal, leverages warp-level shuffling for efficient state exchange [S1][S2, unofficial].
- **Limitations:** Requires storing intermediate states during the forward pass, increasing memory usage. May be complex to implement correctly due to warp-level synchronization [S1][S2, unofficial].
- **When to Use:** When training 3D Gaussian Splatting models and backward pass time is a bottleneck. When atomic contention is observed in profiling [S1][S2, unofficial].
- **When Not to Use:** When memory is extremely constrained and cannot afford the checkpointing overhead. When the scene is very small and the overhead of the complex kernel outweighs the benefits [G].

## Background
Originated from the need to accelerate the training of 3D Gaussian Splatting. The original 3DGS backward pass suffered from severe atomic contention [S1]. Taming 3DGS [S1] introduced per-splat parallelization to mitigate this. SparseOIT [S2, unofficial] further refined the approach with recursive per-splat parallelization and order-independent transparency, eliminating the need for strict depth-order traversal and redundant computations.
