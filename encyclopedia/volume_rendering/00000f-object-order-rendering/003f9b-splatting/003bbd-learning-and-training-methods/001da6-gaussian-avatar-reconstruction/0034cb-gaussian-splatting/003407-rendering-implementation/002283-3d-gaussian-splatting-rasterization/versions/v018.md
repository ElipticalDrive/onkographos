# 3D Gaussian Splatting Rasterization

Also called: 3D Gaussian Splatting (3DGS), 3DGS Rasterization, Differentiable Gaussian Rasterization, TrimGS, gsplat.rasterization

## Overview
3D Gaussian Splatting Rasterization is a differentiable rendering technique that represents a scene as a collection of anisotropic 3D Gaussians and projects them onto a 2D image plane for real-time rendering [S1][S3, S4, unofficial]. It solves the problem of efficiently rendering continuous volumetric representations by converting each primitive into a 2D splat, sorting them by depth, and accumulating color via alpha compositing [S4, unofficial]. It differs from its siblings by providing the core differentiable forward and backward passes for 3D Gaussians, often implemented as optimized GPU kernels (e.g., CUDA or MLX) for performance, whereas alternatives like [Perspective-Correct 3D Gaussian Splatting via Plücker Coordinates](3403-perspective-correct-3d-gaussian-splatting-via-pl-cker-coordi.md) focus on specific projection corrections or [Analytic-Splatting Forward Shading](3459-analytic-splatting-forward-shading.md) on shading models.

## How it works
**Inputs and Outputs:**
*   **Inputs:**
    *   $N$ Gaussians defined by mean position $\mu \in \mathbb{R}^3$, rotation quaternion $q \in \mathbb{R}^4$, scale $s \in \mathbb{R}^3$, opacity $\alpha \in \mathbb{R}$, and color coefficients (direct RGB or Spherical Harmonics).
    *   Camera parameters: View matrix $V \in \mathbb{R}^{4 \times 4}$, Projection matrix $K \in \mathbb{R}^{3 \times 3}$, image dimensions $W \times H$, and camera model (pinhole, ortho, fisheye) [S2, S3, unofficial].
    *   Parameters: `tile_size` (default 16), `near_plane` (default 0.01), `far_plane` (default $10^{10}$), `sh_degree` (default 3 or None) [S2, unofficial].
*   **Outputs:**
    *   Rendered image $C_{pixel} \in \mathbb{R}^{H \times W \times 3}$ (RGB).
    *   Alpha mask $A \in \mathbb{R}^{H \times W \times 1}$.
    *   Optional depth $D \in \mathbb{R}^{H \times W \times 1}$ and normal maps depending on `render_mode` [S2, unofficial].

**Data Structures:**
*   **Gaussian Attributes:** Stored in contiguous arrays/tensors.
    *   `means`: $[N, 3]$ float32.
    *   `quats`: $[N, 4]$ float32 (normalized).
    *   `scales`: $[N, 3]$ float32.
    *   `opacities`: $[N]$ float32.
    *   `colors`: $[N, 3]$ float32 (if `sh_degree` is None) or $[N, K, 3]$ float32 (Spherical Harmonics coefficients, where $K = (sh\_degree+1)^2$) [S2, S3, unofficial].
*   **Intermediate Projections:**
    *   `cov_3D`: $[N, 3, 3]$ covariance matrix.
    *   `means_2D`: $[N, 2]$ screen-space centers.
    *   `conics`: $[N, 3]$ inverse 2D covariance components $[\Sigma^{-1}_{00}, \Sigma^{-1}_{01}, \Sigma^{-1}_{11}]$ [S2, S3, unofficial].
    *   `radii`: $[N, 2]$ bounding box half-extents in pixels.
    *   `depths`: $[N]$ camera-space depth.

**Steps:**

1.  **Input Validation and Setup:**
    Validate `render_mode`, `rasterize_mode`, and `camera_model` [S2, unofficial]. Initialize background color $C_{bg}$ (e.g., white) [S3, unofficial].

2.  **Covariance Construction:**
    Compute the 3D covariance matrix $\Sigma_{3D}$ from rotation $R$ (derived from $q$) and scale $S$ (derived from $s$):
    $$ \Sigma_{3D} = R S S^T R^T $$
    where $S = \text{diag}(s_x, s_y, s_z)$ and $R$ is the rotation matrix [S1][S3, unofficial].

3.  **Projection to 2D:**
    Transform means to camera space and project to screen space using the local affine approximation of the projective transformation. Compute the 2D covariance $\Sigma_{2D}$ using the Jacobian $J$ of the projection function:
    $$ \Sigma_{2D} = J \Sigma'_{3D} J^T $$
    where $\Sigma'_{3D}$ is the projected 3D covariance [S3, unofficial].
    Compute the conic vector $C = [\Sigma_{2D}^{-1}[0,0], \Sigma_{2D}^{-1}[0,1], \Sigma_{2D}^{-1}[1,1]]$ for efficient evaluation [S2, S3, unofficial].
    Calculate bounding radii for tile culling [S2, unofficial].

4.  **Spherical Harmonics Evaluation (Optional):**
    If `sh_degree` is not None, compute view directions $d_i = \text{normalize}(\mu_i - \text{campos})$. Evaluate SH coefficients to get RGB color $c_i$ for each Gaussian [S2, S3, unofficial].
    $$ c(d) = \sum_{\ell=0}^{N} \sum_{m=-\ell}^{\ell} \beta_{\ell m} Y_{\ell m}(d) $$
    Clamp colors to valid range [S2, unofficial].

5.  **Tile Intersection and Sorting:**
    Divide the image into tiles of size `tile_size` $\times$ `tile_size`.
    Identify which Gaussians intersect which tiles using their 2D bounding boxes [S2, unofficial].
    Sort Gaussians by camera-space depth within each tile to ensure correct front-to-back compositing order [S2, S3, S4, unofficial]. The original implementation uses CUB device radix sort for efficiency [S4, unofficial].

6.  **Alpha Compositing:**
    For each pixel, iterate over the sorted Gaussians that cover it.
    Compute the alpha value $\alpha_i$ for each Gaussian at the pixel center (or integrated over pixel area if antialiased) based on the 2D Gaussian PDF, opacity, and conic [S3, unofficial].
    Compute transmittance $T_i = \prod_{j=1}^{i-1} (1 - \alpha_j)$ [S3, unofficial].
    Compute weight $w_i = \alpha_i T_i$ [S3, unofficial].
    Accumulate color:
    $$ C_{pixel} = \sum_{i} w_i c_i + \left(1 - \sum_{i} w_i\right) C_{bg} $$
    Accumulate alpha:
    $$ A_{pixel} = \sum_{i} w_i $$
    [S2, S3, unofficial].

7.  **Post-Processing:**
    If depth is requested, compute weighted average depth [S3, unofficial].
    If expected depth is required, normalize accumulated depth by alpha [S2, unofficial].
    Handle memory constraints by splitting Gaussians into mini-batches if necessary, passing transmittance between batches [S3, unofficial].

def rasterize_gaussians(means, quats, scales, opacities, colors, viewmats, Ks, width, height, backgrounds, sh_degree=None, tile_size=16, near_plane=0.01, far_plane=1e10):
    """
    Rasterize 3D Gaussians to 2D image.
    
    Args:
        means: [N, 3]
        quats: [N, 4]
        scales: [N, 3]
        opacities: [N]
        colors: [N, 3] or [N, K, 3]
        viewmats: [C, 4, 4]
        Ks: [C, 3, 3]
        width, height: int
        backgrounds: [C, 3]
        sh_degree: int or None
        tile_size: int
        near_plane, far_plane: float
        
    Returns:
        render_colors: [C, H, W, 3]
        render_alphas: [C, H, W, 1]
    """
    C = viewmats.shape[0]
    N = means.shape[0]
    
    # 1. Covariance Construction
    # Compute 3D covariance from quats and scales
    # R is rotation matrix from quat, S is diag(scales)
    # cov_3D = R @ S @ S.T @ R.T
    cov_3D = compute_cov_3D(quats, scales) # [N, 3, 3]
    
    # 2. Projection
    # Transform to camera space and project to 2D
    # means_2D, cov_2D = linearized_project(means_3D, cov_3D, camera, img_size)
    # Compute conics from cov_2D inverse
    means_2D, conics, radii, depths = fully_fused_projection(
        means, cov_3D, viewmats, Ks, width, height, near_plane, far_plane
    ) # means_2D: [C, N, 2], conics: [C, N, 3], radii: [C, N, 2], depths: [C, N]
    
    # 3. SH Evaluation (if applicable)
    if sh_degree is not None:
        # Compute view directions

        colors_for_raster = rgb
    else:
        # Broadcast direct colors
        colors_for_raster = mx.broadcast_to(colors[None, :, :], (C, N, 3))

    # Broadcast opacities to [C, N]

    # Rasterize to pixels
    # rasterize_to_pixels(means_2D, conics, colors_for_raster, opacities_cn, width, height, tile_size, isect_offsets, flatten_ids, backgrounds)

    """Compute 3D covariance matrix from quaternions and scales."""
    # Convert quat to rotation matrix R
    R = quat_to_rot_matrix(quats) # [N, 3, 3]
    # S is diagonal matrix of scales
    S = mx.diag(scales) # [N, 3, 3] (conceptually, implemented via broadcasting)

    cov_3D = mx.einsum('nij,nj,nkj->nik', R, S2, R)
    return cov_3D

**Edge Cases and Pitfalls:**
*   **Sorting Bottleneck:** Sorting millions of Gaussians is the primary bottleneck. The original implementation uses CUB device radix sort, which is highly optimized but CUDA-specific [S4, unofficial].
*   **VRAM Usage:** High VRAM usage, approximately 4GB to view and 12GB to train [S4, unofficial].
*   **Disk Size:** Large disk size, 1GB+ for a scene [S4, unofficial].
*   **Precision:** Numerical stability in projection and conic computation is critical, especially for degenerate ellipsoids [S1][S3, unofficial].
*   **Boundary Artifacts:** Chunked training may require boundary support (e.g., Ghost Ellipsoids) to avoid artifacts [S1].

## Subtopics

### [3D Gaussian Splatting Differentiable Rasterizer](2813-3d-gaussian-splatting-differentiable-rasterizer.md)
The 3D Gaussian Splatting Differentiable Rasterizer is a rendering method that projects a set of 3D Gaussian primitives onto a 2D image plane and accumulates color per pixel using alpha compositing, allowing gradients to flow back to Gaussian parameters (position, scale, rotation, opacity, color) and camera view matrices. It solves the problem of differentiable rasterization for continuous volumetric representations by converting each rasterized surface point into a splat centered at the corresponding pixel, colored by the shaded color, and handling splat overlap via depth-sorted accumulation. It differs from its siblings by providing the core differentiable forward and backward passes for 3D Gaussians, often implemented as CUDA kernels for performance, whereas alternatives like [Perspective-Correct 3D Gaussian Splatting via Plücker Coordinates](3403-perspective-correct-3d-gaussian-splatting-via-pl-cker-coordi.md) focus on specific projection corrections or [Analytic-Splatting Forward Shading](3459-analytic-splatting-forward-shading.md) on shading models.

### [Perspective-Correct 3D Gaussian Splatting via Plücker Coordinates](3403-perspective-correct-3d-gaussian-splatting-via-pl-cker-coordi.md)
This method computes the value of a 3D Gaussian primitive for a given viewing ray in screen space without performing matrix inversion, utilizing Plücker coordinates to represent the ray and calculate the distance to the Gaussian's center. It sets itself apart from standard 3D Gaussian Splatting rasterization by providing a closed-form, numerically stable solution for perspective-correct splat evaluation that handles degenerate ellipsoids and avoids the computational cost of matrix inversions.

### [Analytic-Splatting Forward Shading](3459-analytic-splatting-forward-shading.md)
Analytic-Splatting Forward Shading computes the color contribution of 3D Gaussians to a pixel by analytically integrating the Gaussian probability density function over the pixel area, rather than sampling the center. It solves the aliasing artifacts inherent in point-sampling approaches by approximating the pixel area integral using a conditioned logistic function. It sets itself apart from vanilla 3DGS by providing anti-aliased results and from Mip-Splatting by using a different analytical approximation that maintains higher detail fidelity, albeit with a slight computational overhead.

### [Speedy-Splat Rendering Pipeline](3543-speedy-splat-rendering-pipeline.md)
The Speedy-Splat Rendering Pipeline is a GPU-accelerated rasterization method for 3D Gaussian Splatting that replaces coarse bounding-box tile intersection tests with precise Gaussian-tile intersection checks and sorting-based depth ordering. It addresses the inefficiency of standard 3-GS rasterization, which overestimates Gaussian extents and processes non-intersecting pixels, by generating a sparse set of Gaussian-tile pairs and sorting them for efficient pixel-wise compositing.

### [Ghost Ellipsoids for Chunked Training](3559-ghost-ellipsoids-for-chunked-training.md)
Ghost Ellipsoids for Chunked Training resolves boundary artifacts in chunked volume training by including ellipsoids from neighboring chunks in the loss computation without updating their parameters, providing boundary context without requiring a global volume or merged model. Unlike chunk-based 3DGS methods that resolve boundary inconsistencies by merging chunks into a global coarse model or through post-training stages, this method requires boundary support during training itself without access to a global volume.

### [Ref-Gaussian Deferred Surfel Rendering with Split-Sum IBL](4464-ref-gaussian-deferred-surfel-rendering-with-split-sum-ibl.md)
Ref-Gaussian Deferred Surfel Rendering with Split-Sum IBL is a real-time deferred shading method for relighting 3D Gaussian Splatting (3DGS) models on mobile hardware (specifically iOS/Metal). It solves the problem of dynamic environment lighting in Gaussian splats by decomposing splats into physically-based rendering (PBR) materials (albedo, normal, roughness, reflectance) and computing lighting via a deferred pipeline with split-sum environment map integration. Unlike forward-shading Gaussian splatters that bake lighting into spherical harmonics or use analytic approximations, this method separates the material definition from the lighting environment, allowing the environment map to be swapped or rotated in real-time without retraining or re-rasterizing the splats. It differs from standard PBR deferred renderers by adapting the splat-based rasterization and surfel accumulation to the deferred G-buffer workflow.

### [3D Gaussian Splatting Self-Shadowing (T_light)](4487-3d-gaussian-splatting-self-shadowing-t-light.md)
Calculates the self-shadowing transmittance $T_{light}$ for each Gaussian along a directional sun direction, representing the 'front occlusion transmittance' to model self-shadowing effects in volume rendering. It differs from standard alpha blending by explicitly tracking accumulated occlusion from the light source's perspective rather than the camera's, enabling physically plausible shadows within the Gaussian volume.

### [Light Space Rasterization for T_light](4489-light-space-rasterization-for-t-light.md)
Light Space Rasterization computes $T_{light}$, the front-facing occlusion transmittance for each 3D Gaussian along a directional sun direction. It differs from voxel-based fallbacks by providing full continuous gradients and zero parameter expansion, enabling differentiable relighting without requiring specific training hyperparameters.

### [2D Gaussian Splatting Rasterization](4815-2d-gaussian-splatting-rasterization.md)
2D Gaussian Splatting Rasterization renders a scene represented by 3D Gaussian surfels by projecting them to 2D screen-space ellipses and performing tile-based, front-to-back alpha compositing. It differs from its parent [3D Gaussian Splatting Rasterization](2812-3d-gaussian-splatting-rasterization.md) by treating primitives as planar surfels with explicit normal vectors, enabling the accumulation of normal maps alongside color and depth, and by using a specific ray-surfel intersection logic to determine the contribution of each surfel to a pixel. It serves as a differentiable rendering kernel for 2D Gaussian Splatting, allowing gradients to flow from the rendered image back to the Gaussian parameters.

### [Hardware-Accelerated Gaussian Rasterization](7329-hardware-accelerated-gaussian-rasterization.md)
Hardware-Accelerated Gaussian Rasterization is a hardware-algorithm co-design that augments standard triangle rasterizers with dedicated units for Gaussian projection and blending, achieving an order of magnitude speedup in the rasterization stage. It solves the bottleneck of processing millions of 3D Gaussians on general-purpose hardware by isolating specific computational phases into fixed-function pipelines. Unlike software-based differentiable rasterizers [Sibling: 3D Gaussian Splatting Differentiable Rasterizer](2813-3d-gaussian-splatting-differentiable-rasterizer.md) which rely on GPU kernels, this method uses a four-stage hardware pipeline to handle culling, projection, sorting, and blending in parallel.

### [AdR-Gaussian](8365-adr-gaussian.md)
AdR-Gaussian is a rendering acceleration method for 3D Gaussian Splatting that optimizes the rasterization pipeline by moving serial culling operations to a parallel preprocessing stage and balancing computational loads across pixel threads. It achieves significant speedups without reducing the total number of Gaussians, thereby avoiding the quality degradation associated with pruning-based acceleration methods.

### [3D Half-Gaussian Splatting](9011-3d-half-gaussian-splatting.md)
3D Half-Gaussian Splatting (3D-HGS) is a reconstruction kernel for 3D Gaussian Splatting that replaces the standard isotropic Gaussian with a half-space truncated Gaussian to resolve shape and color discontinuities (Gibbs phenomenon) at object boundaries and texture-rich areas. It achieves state-of-the-art rendering quality on standard benchmarks without compromising the real-time performance of the underlying rasterizer, distinguishing itself from 2D-GS by retaining volumetric rendering and from GES by explicitly modifying the kernel function rather than just scaling factors.

### [QuadBox](9231-quadbox.md)
QuadBox is a Gaussian-tile intersection method that uses four axis-aligned bounding boxes (AABBs) to tightly encapsulate projected 2D Gaussians, reducing tile over-approximation and redundant computations in the rasterizer preprocess stage. It sets itself apart from its sibling [3D Gaussian Splatting Rasterization](2812-3d-gaussian-splatting-rasterization.md) by replacing the conservative single AABB with a geometry-aware QuadBox, and from [AdR-Gaussian](8365-adr-gaussian.md) by using four adaptive sub-boxes to better capture anisotropic shapes, thereby suppressing residual redundancy along the minor axis.

### [Transparency and Blending Models](9274-transparency-and-blending-models.md)
Transparency and Blending Models define how 3D Gaussian primitives are composited into a 2D image, addressing the fundamental problem of order-dependent alpha blending in splatting-based rendering. Standard 3D Gaussian Splatting uses approximate per-primitive sorting and 2D projection, which can introduce popping artifacts and inaccuracies in transmittance [2812-3d-gaussian-splatting-rasterization.md]. This family provides alternatives that either correct depth ordering for real-time performance, replace projection with analytic ray-space integration for physical accuracy, or eliminate sorting entirely via Order-Independent Transparency (OIT) [3294-hybrid-transparency.md], [4440-analytic-transmittance-3dgs.md], [7562-sparseoit-rasterizer.md].

### [Projection Geometry and Coordinate Systems](9313-projection-geometry-and-coordinate-systems.md)
This article defines the coordinate transformations and projection mappings required to render 3D Gaussian primitives onto a 2D image plane within the 3D Gaussian Splatting framework. It solves the problem of accurately mapping 3D spatial covariance and position into 2D screen space for alpha blending or density integration. It differs from standard perspective projection by supporting alternative camera models (panoramic, equidistant) and specialized geometries (cone-beam X-ray) while maintaining the core affine approximation of the Gaussian covariance.

### [Point-Based Ray Tracing for Visibility](10934-point-based-ray-tracing-for-visibility.md)
Point-Based Ray Tracing for Visibility serves as a sparse visibility oracle that evaluates transmittance along sampled light directions using a bounding volume hierarchy (BVH) of Gaussian proxies, enabling evaluation from any point in space in any direction. Unlike the camera-tied rasterizer, it decouples visibility estimation from screen-space projection, allowing it to act as a drop-in companion to standard 3D Gaussian Splatting (3DGS) by reusing the same EWA-splatting formulation for consistent blending without requiring training mismatch.

### [Bézier Gaussian Triangle](11816-b-zier-gaussian-triangle.md)
The Bézier Gaussian Triangle (BG-Triangle) is a hybrid representation primitive that combines Bézier triangle surfaces for geometry with 3D Gaussian sub-primitives for appearance, enabling differentiable rendering with sharp boundaries. It solves the problem of blurry or aliased boundaries common in purely Gaussian splatting methods by defining geometry explicitly via parametric surfaces while retaining the efficient, differentiable rasterization pipeline of Gaussian Splatting. Unlike [3D Gaussian Splatting Rasterization](2812-3d-gaussian-splatting-rasterization.md), which relies solely on point-based Gaussians, BG-Triangle tessellates curved surfaces into flat triangles to align with the pixel grid, allowing for discontinuity-aware blending at primitive edges.

### Temporal Marginal Probability Filtering
Pre-rasterization culling step that removes 4D Gaussians with negligible temporal support at the current frame timestamp, stabilizing rendering speed across video length [S6, unofficial]. It computes the marginal probability $p_i(t)$ for each 4D Gaussian $i$ at the current frame's timestamp $t$ and discards Gaussians with negligible $p_i(t)$ before executing standard frustum culling. Unlike methods where Gaussian count scales with video length, this filtering keeps active Gaussians constant, making the approach friendly to long videos in terms of rendering speed [S6, unofficial].

### t-distribution truncation for splatting
A projection truncation technique that replaces the fixed three-sigma rule used in vanilla 3DGS with a $\nu$-dependent critical value interpolation to handle fat-tailed Student's t-distributions [S7]. For t-distributions with thin tails (high $\nu$), it applies the standard three-sigma rule directly. For fat-tailed distributions (low $\nu$), it obtains critical values for different $\nu$ degrees from reference [9] and interpolates between them to compute the appropriate truncation threshold. Using a fixed three-sigma threshold on fat-tailed t-distributions causes excessive truncation or leakage, which interpolation resolves [S7].

### Gaussian Opacity Fields (GOF)
Uses ray-tracing-style intersection for accurate depth and derives a level-set surface from accumulated opacity [S5, unofficial].

### Progressive Normal Propagation
Uses progressive propagation along normals to fill texture-less regions [S5, unofficial].

### Gaussian Surfels
Uses zero-thickness oriented surfels [S5, unofficial].

### Splat TBO Upload & Layout
Packs per-splat data (center, covariance, DC color/alpha, optional SH) into Texture Buffer Objects (TBOs) for GPU consumption [S8, unofficial]. It iterates over splats, copying center.xyz as raw float bits to `d[0..2]`, packing covariance upper-triangle to `d[3..5]` using `packHalf2x16`, and packing DC color/alpha to `d[6]` using `packDCColor`. It creates a GL_TEXTURE_BUFFER buffer with GL_RGBA32UI format. For non-DC SH coefficients, it packs each coefficient's RGB into RGBA16F texels (B=0), with layout `[splat0_c1, splat0_c2, …, splat1_c1, splat1_c2, …]`. Memory usage is 32 B/splat for base TBO + 8 B $\times$ sh_coeffs_per_splat_ $\times$ splat_count_ for SH TBO, where sh_coeffs_per_splat_ = $(active\_sh\_degree\_ + 1)^2 - 1$ [S8, unofficial].

## Operating characteristics
*   **Time Complexity:** Dominated by sorting $N$ Gaussians, typically $O(N \log N)$ or $O(N)$ with radix sort [S4, unofficial]. Rasterization is $O(P)$ where $P$ is the number of pixel-splat intersections.
*   **Memory Complexity:** $O(N)$ for Gaussian attributes. High VRAM usage (4GB to view, 12GB to train) [S4, unofficial]. Large disk size (1GB+ for a scene) [S4, unofficial].
*   **Measured Performance:** Real-time rendering rates (60+ FPS) on modern GPUs for scenes with millions of Gaussians [S1][S4, unofficial].
*   **Scaling:** Scales well with GPU parallelism but is limited by VRAM and sorting overhead [S4, unofficial].
*   **Strengths:** High-quality, photorealistic scenes; fast, real-time rasterization; relatively fast to train [S4, unofficial].
*   **Limitations:** High VRAM usage; large disk size; incompatible with existing rendering pipelines (requires custom rasterizer); primarily static (for now) [S4, unofficial].
*   **When to Use:** Real-time rendering of high-fidelity static or dynamic scenes where training time and storage are acceptable.
*   **When Not to Use:** When strict compatibility with existing rendering pipelines (Vulkan, DirectX, WebGPU) is required without custom shaders, or when storage/VRAM is severely constrained.

## Background
3D Gaussian Splatting was introduced in the paper "3D Gaussian Splatting for Real-Time Radiance Field Rendering" [S4, unofficial]. It represents a breakthrough in static scene rendering by representing scenes as collections of 3D Gaussian primitives, enabling real-time rendering rates while maintaining high visual fidelity [S1]. The method is analogous to triangle rasterization but uses Gaussians instead of triangles [S4, unofficial]. It is widely used in computer graphics for novel view synthesis, 3D reconstruction, and real-time rendering of learned radiance fields [S1][S4, unofficial].
