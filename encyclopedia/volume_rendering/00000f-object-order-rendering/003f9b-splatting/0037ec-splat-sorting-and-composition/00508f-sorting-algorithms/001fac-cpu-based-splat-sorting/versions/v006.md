# CPU-Based Splat Sorting

Also called: Splat Sort, WebWorker Splat Sort

## Overview
CPU-Based Splat Sorting is a method for reordering 3D Gaussian splats by depth on the central processing unit to enable correct front-to-back alpha blending [S2, unofficial]. It solves the problem of order-dependent transparency in splat rendering by ensuring that closer splats are composited before further ones [S2, unofficial]. It differs from GPU-based alternatives like [Bitonic Sort](14217-bitonic-sort.md) by offloading the $O(N \log N)$ sorting workload to the CPU, allowing the GPU to dedicate its cycles entirely to rendering, which avoids the overhead and latency associated with GPU compute sorting [S1, unofficial].

## How it works
The method transforms splat positions into view space, extracts depth, and sorts the resulting indices.

**Inputs:**
*   `viewProj`: A $4 \times 4$ view-projection matrix ($glm::mat4$) [S2, unofficial].
*   `positions`: A pointer to an array of interleaved $xyz$ coordinates (float) [S2, unofficial].
*   `vertexCount`: The number of splats ($uint32_t$) [S2, unofficial].

**Outputs:**
*   `depthIndex`: A vector of $uint32_t$ indices, sorted such that the splat at `depthIndex[0]` is closest to the camera [S2, unofficial].

**Data Structures:**
*   `SplatDepth`: A struct or pair containing:
    *   `depth`: `float` representing the projected depth.
    *   `original_index`: `uint32_t` representing the index in the original `positions` array.

**Steps:**
1.  **Project and Extract Depth:** For each splat $i$ from $0$ to `vertexCount` - 1:
    *   Retrieve position $P_i = (x, y, z)$ from `positions`.
    *   Compute the homogeneous clip-space coordinate:
        $$ V = \text{viewProj} \times \begin{bmatrix} x \\ y \\ z \\ 1 \end{bmatrix} $$
    *   Extract depth using perspective division:
        $$ d_i = \frac{V_z}{V_w} $$
        [S2, unofficial]
    *   Store the pair $(d_i, i)$ in a temporary list.
2.  **Sort:** Sort the list of pairs based on $d_i$ in ascending order (smallest depth first, i.e., front-to-back) [S2, unofficial].
3.  **Extract Indices:** Iterate through the sorted list and extract the `original_index` from each pair into the output `depthIndex` vector [S2, unofficial].

**Pseudocode:**
```python
def cpu_splat_sort(view_proj_matrix, positions, vertex_count):
    """
    Sorts splats by depth on the CPU.
    
    Args:
        view_proj_matrix: 4x4 matrix (list of lists or similar structure)
        positions: List of 3-element lists [x, y, z]
        vertex_count: Integer number of splats
        
    Returns:
        depth_index: List of integers representing sorted indices
    """
    splat_depths = []
    
    # Step 1: Project and extract depth
    for i in range(vertex_count):
        pos = positions[i]
        x, y, z = pos[0], pos[1], pos[2]
        
        # Transform position to clip space
        # Assuming view_proj_matrix is a 4x4 structure accessible by row/col
        # V = viewProj * [x, y, z, 1]
        vx = (view_proj_matrix[0][0] * x + view_proj_matrix[0][1] * y + 
              view_proj_matrix[0][2] * z + view_proj_matrix[0][3] * 1.0)
        vy = (view_proj_matrix[1][0] * x + view_proj_matrix[1][1] * y + 
              view_proj_matrix[1][2] * z + view_proj_matrix[1][3] * 1.0)
        vz = (view_proj_matrix[2][0] * x + view_proj_matrix[2][1] * y + 
              view_proj_matrix[2][2] * z + view_proj_matrix[2][3] * 1.0)
        vw = (view_proj_matrix[3][0] * x + view_proj_matrix[3][1] * y + 
              view_proj_matrix[3][2] * z + view_proj_matrix[3][3] * 1.0)
        
        # Perspective divide to get depth
        if vw == 0.0:
            depth = float('inf') # Handle division by zero
        else:
            depth = vz / vw
            
        splat_depths.append((depth, i))
        
    # Step 2: Sort by depth ascending (front-to-back)
    # Using a standard comparison sort
    splat_depths.sort(key=lambda item: item[0])
    
    # Step 3: Extract sorted indices
    depth_index = [item[1] for item in splat_depths]
    
    return depth_index
```

**Parameters:**
*   `integerBasedSort`: A boolean viewer parameter. If `false`, forces a slower floating-point based splat sort. This is used to handle scenes with large dimensions or high splat density where integer-based sorting precision fails [S3, unofficial].
*   `splatSortDistanceMapPrecision`: A viewer parameter that adjusts the precision for the distance map in splat sort. Larger values reduce performance but can alleviate visual artifacts caused by low precision [S3, unofficial].

**Edge Cases and Pitfalls:**
*   **Rapid Camera Movement:** Rapid camera movement (e.g., jumping between opposite sides) causes momentary transparency artifacts because the Z-order does not update fast enough relative to the render loop [S1, unofficial][S3, unofficial].
*   **Large Dimensions:** Scenes with very large dimensions may crash with an "Index out of bounds" error from the splat sort. Changing `splatSortDistanceMapPrecision` or `integerBasedSort` usually does not help in these cases [S3, unofficial].
*   **Precision:** Low precision in the distance map can lead to visual artifacts [S3, unofficial].

## Subtopics

### [Splat Sorting Key Calculation](2106-splat-sorting-key-calculation.md)
This method calculates a scalar key for each 3D Gaussian splat to determine the rendering order, typically for front-to-back alpha blending. It combines the splat's projected size and opacity to prioritize "important" splats (large and opaque) to be drawn first, ensuring correct accumulation of color and alpha.

### [CPU Fallback Sort Path](5586-cpu-fallback-sort-path.md)
The CPU Fallback Sort Path is a rendering strategy for volume splatting that executes splat sorting on the CPU rather than the GPU. It provides a CPU-side sorting and rendering fallback when GPU compute sorting is disabled or unavailable, using a shader-readable structured buffer instead of append or UAV buffers. It differs from GPU-based sorting methods by relying on CPU-side sorting algorithms to produce a sorted order buffer, which is necessary on platforms like the Android Filament Java API that lack compute shader support.

### WASM/SIMD CPU Splat Sorting
This variant implements splat sorting in C++ using WebAssembly SIMD instructions for CPU acceleration, or uses transform feedback for partial GPU acceleration [S3, unofficial]. It sorts splats by distance from the camera for correct alpha blending [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** The sorting step is $O(N \log N)$ for standard comparison sorts (e.g., Quicksort/Mergesort) [S1, unofficial].
*   **Performance:** Sorting ~1 million splats on a CPU takes approximately 150ms [S1, unofficial]. This results in a sorting throughput of roughly 4fps, while the main render loop runs at 60fps [S1, unofficial].
*   **Memory:** Requires storage for the position array, the view-projection matrix, and a temporary array of depth-index pairs of size $N$ [S2, unofficial].
*   **Strengths:** Allows the GPU to focus exclusively on rendering, avoiding the overhead of GPU sorting algorithms like Bitonic Sort which require many iterations and split GPU time [S1, unofficial].
*   **Limitations:** High latency (4fps sort rate) leads to visual artifacts during rapid camera movement [S1, unofficial][S3, unofficial]. Performance is sub-optimal on mobile devices [S3, unofficial]. Scenes with very large dimensions may cause crashes [S3, unofficial].

## Background
CPU-based splat sorting was explored as an alternative to GPU-based sorting (such as Bitonic Sort) for rendering 3D Gaussian Splatting in web browsers [S1, unofficial]. The approach was implemented using WebWorkers to allow asynchronous sorting, preventing the main thread from blocking [S1, unofficial]. It was noted that while GPU sorting is common in reference implementations, CPU sorting was deemed plausible to keep the GPU focused on rendering [S1, unofficial]. Variants using WASM SIMD were also developed to optimize this CPU-bound task [S3, unofficial].
