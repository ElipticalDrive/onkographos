# Bitonic Sort

Also called: ABisort, Bitonic Sort for GPGPU, Govindaraju et al. Bitonic Sort, Particle Sorting (Bitonic Sort)

## Overview
Bitonic Sort is a data-independent network sorting algorithm used on the GPU to achieve exact ordering of splatted voxels or particles at each frame [S1, unofficial]. It is chosen over data-driven algorithms like Quicksort, which are unsuitable for GPU stream processors, and over Odd-Even Merge Sort, which only provides partial ordering [S1, unofficial]. While Adaptive Bitonic Sort (ABisort) offers optimal complexity, Govindaraju et al.'s implementation is often preferred for its accessibility and ease of adaptation [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** An array of `<key, value>` pairs. In the context of volume splatting, the key is the depth voxel value $b$, and the value is the voxel index [S1, unofficial]. The data is assumed to be already transformed into view space on the GPU [S1, unofficial].
*   **Output:** A depth-sorted array of voxels/particles.

**Data Structures:**
The algorithm uses the Multiple Render Target (MRT) extension to store keys and values in separate textures with a one-to-one correspondence [S1, unofficial]. This allows packing four `<key, value>` instances into a single RGBA texel [S1, unofficial]. Ping-pong buffering is used between two render targets (textures) to swap read/write roles between passes [S1, unofficial].

**Parameters:**
*   $uHalfVector$: The half-angle vector used for sorting particles [S2, unofficial].
*   $uPass$: The current pass number in the sort algorithm [S2, unofficial].
*   $uStage$: The current stage number in the sort algorithm [S2, unofficial].
*   $N$: The number of elements to sort (must be a power of 2).

**Algorithm Steps:**
1.  **Initialization:** If the input is on the CPU, a fragment shader fills the initial render targets with the depth value $b$ as the key and the voxel index as the value [S1, unofficial].
2.  **Sorting Passes:** The sort consists of $\log_2 N$ passes. Each pass consists of $\log_2 N$ stages.
3.  **Comparison Logic:** For each element at index $i$, determine the comparison direction and partner.
4.  **Swap Decision:** Compare the element with its partner. If the order is incorrect, swap them.
5.  **Finalization:** After sorting, a fragment shader fills the final Depth-Sorted Voxels Texture from the sorted render targets [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Power of 2:** The number of elements must be a power of 2. If not, padding is required [G].
*   **Precision:** Floating-point comparisons for depth values may suffer from precision issues near boundaries [G].
*   **Memory Access:** Cache-efficient memory accesses are crucial for performance, as highlighted by Govindaraju et al. [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N \log^2 N)$ comparisons [S1, unofficial]. Adaptive Bitonic Sort (ABisort) achieves $O((N \log N) / P)$ where $P$ is the number of stream processors [S1, unofficial].
*   **Memory Complexity:** $O(N)$ for storing keys and values [S1, unofficial].
*   **Performance:** On an NVIDIA GeForce 7800, Govindaraju's Bitonic Sort is approximately twice as fast as the best CPU QuickSort implementation [S1, unofficial].
*   **Strengths:** Provides exact ordering at each frame, which is critical for splatting [S1, unofficial]. Highly parallelizable on GPU [S1, unofficial].
*   **Limitations:** Data-independent, so it performs the same number of operations regardless of input order [S1, unofficial]. Not suitable for variable-sized datasets without padding [G].
*   **When to Use:** When exact ordering is required per frame and GPU performance is prioritized over CPU-based sorting [S1, unofficial].
*   **When Not to Use:** When partial ordering is sufficient (use Odd-Even Merge Sort) or when data is highly structured and CPU-based sorts are preferred [S1, unofficial].

## Background
Bitonic Sort was originally developed for network sorting architectures [S1, unofficial]. It was adapted for GPGPU by researchers such as Govindaraju et al. [GRHM05] and Kim et al. [KW05], who improved cache efficiency [S1, unofficial]. It has been adapted for sorting large databases [GGKM06]. Adaptive Bitonic Sort (ABisort) was later designed by Gress and Zachmann [GZ06] to optimize complexity [S1, unofficial]. In volume rendering, it is used for splat sorting to ensure correct depth ordering of voxels [S1, unofficial].
