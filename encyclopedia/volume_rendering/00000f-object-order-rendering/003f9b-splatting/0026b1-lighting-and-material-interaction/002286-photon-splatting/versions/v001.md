# Photon Splatting

Also called: Capturing Direct Illumination (Photon Splatting)

## Overview
Photon Splatting is a method for capturing direct illumination into a sparse voxel octree by rasterizing a light-view map and accumulating photon data into leaf nodes. It solves the problem of efficiently storing incoming radiance as a direction distribution and energy proportional to the subtended solid angle of the light source. It differs from [Per-Splat Relighting](3371-per-splat-relighting.md) by focusing on the initial capture of direct light into the voxel structure rather than relighting existing splats.

## How it works
**Inputs:**
- Light-view map: A world position map rendered from the light's perspective using standard rasterization. Each pixel represents a photon.
- Sparse Voxel Octree: A hierarchical data structure where empty voxels are collapsed. Photons are stored at the finest level (leaf nodes) on surfaces.

**Outputs:**
- Updated octree leaves containing photon data (direction distribution and energy).

**Data Structures:**
- **Light-View Map:** 2D texture. Resolution is typically higher than the lowest level of the voxel grid.
- **Octree Leaves:** 3D voxel grid. Voxels are repeated for adjacent bricks to support hardware filtering.
- **Photon Data:** Stored per voxel. Due to hardware limitations, atomic additions are performed on 16-bit normalized textures, which are denormalized upon access.

**Steps:**
1. **Render Light-View Map:** Render the scene from the light's view to generate a world position map. Each pixel corresponds to a photon.
2. **Splat Photons:** Use a fragment shader with one thread per light-view-map pixel.
   - Determine the leaf node in the octree corresponding to the world position of the pixel.
   - Calculate the energy proportional to the subtended solid angle of the pixel as seen from the light.
   - Accumulate the photon's direction and energy into the leaf node.
3. **Handle Atomic Operations:** Since atomic adds are only available for integer textures, use a 16-bit normalized texture format for accumulation. Denormalize values when reading.
4. **Transfer to Neighboring Bricks:** To avoid thread collisions and bandwidth issues caused by voxel repetition at brick boundaries, perform a value transfer scheme (see [Value Transfer to Neighboring Bricks](#value-transfer-to-neighboring-bricks)).

**Formulas:**
- Energy $E$ is proportional to the subtended solid angle $\Omega$ of the pixel as seen from the light:
  $$ E \propto \Omega $$
- Direction distribution is stored per voxel.

**Parameters:**
- Light-view map resolution: Typically higher than the lowest level of the voxel grid.
- Texture format: 16-bit normalized.

**Edge Cases and Pitfalls:**
- **Atomic Add Limitations:** Atomic operations are restricted to integer textures. Using 16-bit normalized formats requires careful denormalization.
- **Thread Collisions:** Direct copying of photons to all required locations in adjacent bricks causes significant thread collisions and bandwidth issues. The value transfer scheme mitigates this.
- **Empty Voxels:** Only non-empty voxels (surfaces) are considered for photon storage.

**Pseudocode:**
```python
# Fragment shader for one thread per light-view-map pixel
def splat_photon(light_view_pixel, octree):
    # 1. Get world position from light-view map
    world_pos = light_view_pixel.world_position
    
    # 2. Find leaf node in octree
    leaf_node = octree.find_leaf(world_pos)
    
    # 3. Calculate energy proportional to subtended solid angle
    # Omega is the solid angle of the pixel as seen from the light
    energy = calculate_subtended_solid_angle(light_view_pixel, light_source)
    
    # 4. Accumulate photon data
    # Direction is stored as a vector, energy as a scalar
    # Use atomic add on 16-bit normalized texture
    atomic_add(leaf_node.direction, light_view_pixel.direction)
    atomic_add(leaf_node.energy, energy)
    
    # 5. Transfer to neighboring bricks (handled in separate passes)
    # This step is deferred to avoid thread collisions
    pass
```

## Subtopics

### Value Transfer to Neighboring Bricks
This variant addresses the issue of voxel repetition at brick boundaries. It performs six passes, two for each axis (x, y, z). In the first x-axis pass, each thread adds voxel data from the current node to the corresponding voxels of the brick to its right (three values per thread). In the next x-axis pass, data is transferred from the right to the left by copying values. This ensures coherence along the x-axis. The process is repeated for y and z axes. This approach avoids atomic operations and thread collisions by using neighbor pointers for quick access, making it more efficient than direct copying to adjacent bricks [S2].

## Operating characteristics
- **Time Complexity:** Linear with respect to the number of light-view map pixels and octree leaves. The value transfer adds a constant factor (6 passes).
- **Memory Complexity:** Proportional to the number of photons stored in the octree.
- **Performance:** Efficient due to the use of neighbor pointers and avoidance of atomic operations in the transfer phase. However, initial splatting may suffer from thread collisions if not handled properly.
- **Strengths:** Efficient capture of direct illumination; handles sparse voxel structures well.
- **Limitations:** Requires careful handling of atomic operations and brick boundary transfers.

## Background
Photon Splatting was introduced in the context of interactive indirect illumination using voxel cone tracing. It builds on the idea of using a light-view map to capture direct illumination, inspired by [DS05]. The method is part of the GIVoxels algorithm, which aims to provide real-time global illumination effects.
