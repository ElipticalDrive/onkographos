# Footprint Evaluation
Also called: Footprint evaluation for volume rendering, Splatting (Westover), Westover 1990, Westover splatting, Westover's Footprint Evaluation

## Overview
Footprint Evaluation is a forward-mapping object-order volume rendering algorithm that projects each voxel independently onto the 2D image plane, distributing its energy via a reconstruction kernel to form a "splat" or footprint [S1, S2, S4, S6, unofficial]. It solves the problem of efficiently rendering regular volumetric grids by avoiding the per-pixel ray traversal of image-order methods, instead building the image voxel-by-voxel [S2, S6, unofficial]. It sets itself apart from ray-casting by pre-computing the integration of the 3D kernel into a 2D footprint, reducing the per-voxel computational overhead from $O(k^3)$ to $O(k^2)$, where $k$ is the filter dimension [S2, unofficial].

## How it works
**Inputs:** A regular 3D volume grid with voxel values $\rho(s)$, a viewing transformation (orthographic or perspective), and a 3D reconstruction kernel $h(x,y,z)$.
**Outputs:** A 2D image with accumulated color and opacity values.

**Data Structures:**
1.  **Volume Grid:** 3D array of voxel densities $\rho(s)$ at positions $(x_s, y_s, z_s)$.
2.  **Footprint Table:** A 2D lookup table storing the discrete integration of the footprint function $F(x,y)$. For orthographic projection with symmetric kernels, one table suffices for the entire view [S2, S6, unofficial]. For perspective or asymmetric kernels, a view-transformed table or per-voxel table is required [S2, S6, unofficial].
3.  **Sheet Buffer:** A 2D accumulator buffer aligned with the volume axis most parallel to the image plane. It stores intermediate $(R,G,B,\alpha)$ values for a slice of voxels [S1, S4, S6, unofficial].
4.  **Compositing Buffer:** The final working image buffer where sheet buffers are composited [S4, S6, unofficial].

**Formulas:**
The contribution of a data sample $s$ to a point in space $(x,y,z)$ is defined by the volume reconstruction kernel $h$ and sample value $\rho(s)$:
$$ C_s(x,y,z) = h(x-x_s, y-y_s, z-z_s) \rho(s) $$
[S6, unofficial]

The footprint function $F(x,y)$ is the integral of the 3D reconstruction kernel along the ray direction (perpendicular to the screen, typically $z$):
$$ F(x,y) = \int h(x,y,w) dw $$
[S2, S6, unofficial]

The contribution of sample $s$ to an image plane pixel $p(x,y)$ is:
$$ I_s(p) = \rho(s) F(x-x_s, y-y_s) $$
[S6, unofficial]

The total intensity for pixel $p$ is the sum over all samples:
$$ I(p) = \sum_s I_s(p) = \sum_s \rho(s) F(x-x_s, y-y_s) $$
[S6, unofficial]

For a Gaussian reconstruction kernel $h(x,y,z) = \exp(-x^2/a^2 - y^2/b^2 - z^2/c^2)$, if $a=b=c$, the footprint is isotropic [S6, unofficial].

**Steps:**
1.  **Preprocessing:**
    *   Select the reconstruction kernel $w$. A 3D Gaussian $w(x,y,z) = d \exp(-x^2/a^2 - y^2/b^2 - z^2/c^2)$ is commonly used, ideally spherically symmetric to avoid directional bias [S4, unofficial].
    *   Pre-compute the 2D footprint function $F(x,y)$ by integrating the 3D kernel along one axis. Store this as a finely sampled 2D lookup table [S2, S6, unofficial].
    *   If using perspective projection or non-uniform scaling, calculate the view-transformed footprint extent and the mapping $T^{-1}$ from the view-transformed footprint to the generic footprint [S6, unofficial].

2.  **Sheet Selection:**
    *   Determine the stack of volume slices most parallel to the image plane based on the viewing angle (e.g., x-axis aligned for ~30 degrees, y-axis for ~70 degrees) [S4, S6, unofficial].

3.  **Voxel Processing (Per Sheet):**
    *   Iterate through voxels in the selected sheet.
    *   **Transform:** Map each voxel from input grid space $(i,j,k)$ to screen space $(x,y,z)$ [S6, unofficial].
    *   **Shade:** Classify and shade the voxel to produce attributes $(R,G,B,A)$ [S3, S6, unofficial]. This can be done pre-shading (before projection) or post-shading (after projection) [S3, S6, unofficial].
    *   **Project (Splat):**
        *   Determine the screen-space extent of the footprint centered at the projected voxel position $(x_s, y_s)$ [S6, unofficial].
        *   Identify all pixels within this extent [S6, unofficial].
        *   For each pixel in the extent, retrieve the weight from the footprint table. If using a view-transformed table, apply the reverse mapping $T^{-1}$ to find the corresponding value in the generic footprint table [S6, unofficial].
        *   Accumulate the weighted contribution into the Sheet Buffer [S4, S6, unofficial].

4.  **Compositing:**
    *   Composite the Sheet Buffer into the Compositing Buffer using alpha blending [S4, S6, unofficial].
    *   If using front-to-back compositing, the process can stop for a pixel when it becomes fully opaque [S4, unofficial].
    *   If using back-to-front compositing, correct visibility is guaranteed [S4, unofficial].

5.  **Finalization:**
    *   Repeat steps 3-4 for all sheets in the selected stack.
    *   The Compositing Buffer becomes the final image [S6, unofficial].

**Parameters:**
*   **Kernel Shape/Size:** Critical for quality. Gaussian is common. Size must be tuned for pixel-to-voxel ratio; large footprints cause blurring, small ones cause gaps [S4, unofficial].
*   **Footprint Table Resolution:** Finer sampling improves accuracy [S2, unofficial].
*   **Compositing Order:** Front-to-back (faster, early exit) or back-to-front (correct visibility) [S4, unofficial].

**Edge Cases and Pitfalls:**
*   **Overlapping Splats:** Overlapping footprints lead to incorrect mixture of integration (3D to 2D) and compositing, causing aliasing [S4, unofficial].
*   **Perspective Distortion:** Orthographic footprints are independent of viewpoint; perspective footprints are elliptical and require orientation computation [S4, S6, unofficial].
*   **Anisotropic Grids:** If volume spacings differ or viewing transform has non-uniform scaling, the footprint becomes elliptical, not circular [S6, unofficial].
*   **Blurring:** Gaussian kernels cut high frequencies, resulting in blurry images for zoomed views [S4, unofficial].

## Subtopics

### [Antialiased Splatting with Footprint Alignment](1288-antialiased-splatting-with-footprint-alignment.md)
Antialiased Splatting with Footprint Alignment is a forward-mapping volume rendering technique that prevents sample-rate aliasing in perspective views by dynamically scaling splat sizes and attenuating splat energy for voxels beyond a critical distance. It sets itself apart from standard splatting by varying the kernel size and energy as a function of depth to match the diverging integration grid rays, ensuring the integration grid sampling frequency remains above twice the maximum volume raster frequency.

### Separable Footprint (SF) Projector
A projector model that accounts for the finite width of detector pixels and volume voxels, providing higher accuracy than methods that do not model finite widths (like Siddon or Joseph), though at higher computational cost [S7, unofficial]. SF models finite detector/voxel widths, whereas Siddon and Joseph do not. SF is more accurate and avoids artifacts produced by Siddon/Joseph in some cases, but is more computationally expensive [S7, unofficial].

### Footprint Function Mechanism
A 2D reconstruction kernel used to implement the 3D spherically symmetric splat kernel by integrating it along one dimension, represented as a pre-computed 2D lookup table [S2, unofficial]. The 2D footprint function is pre-computed by integrating the 3D spherically symmetric kernel along one axis and stored as a finely sampled 2D lookup table [S2, unofficial]. The table is centered at the voxel's projected point on the image plane, and pixels within its extent sample the table to composite their values [S2, unofficial]. The footprint table is recomputed once if volume grid spacing is regular, view projection is orthographic, and the splat kernel is radially symmetric; it must be recomputed per view for non-symmetric kernels and per voxel for perspective projections [S2, unofficial].

## Operating characteristics
**Time Complexity:** Splatting has a complexity of at most $O(k^2 n^3)$, where $k$ is the filter dimension and $n^3$ is the voxel count [S2, unofficial]. This is faster than ray-casting, which has a complexity of at least $O(k^3 n^3)$ because splatting precomputes the convolution and splats each voxel exactly once, requiring $k^2$ compositing operations per splat [S2, unofficial].

**Memory Complexity:** Requires storage for the volume grid, the footprint table (size depends on kernel support and resolution), and the sheet/compositing buffers [S4, S6, unofficial].

**Performance:** Splatting is inherently faster than ray-casting for large volumes [S2, unofficial]. However, good splatting results may require as much CPU computing time as ray casting if high-quality kernels and large footprints are used [S4, unofficial]. It supports perspective projection without excessive cost [S5, unofficial].

**Strengths:**
*   Inherently faster than ray-casting due to precomputed footprints [S2, unofficial].
*   Supports perspective projection efficiently [S5, unofficial].
*   Simple static parallel decomposition [S4, unofficial].
*   Can handle scattered data (e.g., SPH) with sorting [S4, unofficial].

**Limitations:**
*   Poor quality in the original algorithm; requires tuning for quality [S4, unofficial].
*   Blurry images for zoomed views due to Gaussian kernel properties [S4, unofficial].
*   High fill-rate for zoomed splats [S4, unofficial].
*   Overlapping splats cause aliasing [S4, unofficial].
*   Sheet orientation changes can cause popping artifacts [S1, unofficial].

**When to Use:**
*   When rendering regular volumetric grids on CPU or GPU where speed is prioritized over perfect anti-aliasing.
*   When perspective projection is needed.
*   When adaptive resampling is required [S5, unofficial].

**When Not to Use:**
*   When high-frequency detail preservation is critical (Gaussian blurring).
*   When exact visibility is required without sorting or careful compositing order (back-to-front is slow).

## Background
Footprint Evaluation was introduced by Lee Westover in "Footprint evaluation for volume rendering," published in *Computer Graphics*, vol 24, no. 4, August 1990 [S6, unofficial]. It was the first described splatting algorithm, intended for rendering regular grids on a CPU [S1, unofficial]. The method was later extended to improve quality and performance, including sheet-buffer methods by Mueller et al. [S1, S6, unofficial] and perspective splatting [S2, unofficial]. It is applicable to scattered data such as SPH, requiring sorting of sample points [S4, unofficial].
