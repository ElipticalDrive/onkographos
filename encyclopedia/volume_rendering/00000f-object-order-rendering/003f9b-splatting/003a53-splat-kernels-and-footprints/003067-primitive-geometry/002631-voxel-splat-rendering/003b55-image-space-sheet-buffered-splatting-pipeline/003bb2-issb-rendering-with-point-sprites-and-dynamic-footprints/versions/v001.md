# ISSB Rendering with Point Sprites and Dynamic Footprints

Also called: GPU Image-Space Sheet-Buffered Splatting Rendering

## Overview
This method defines the final rendering stage of the Image-Space Sheet-Buffered (ISSB) splatting pipeline, where depth-sorted voxels are rasterized using `glPoint` primitives and the Point Sprites extension [S1, unofficial]. It distinguishes itself from prior ISSB implementations by computing and storing distinct kernel footprints for each voxel across all intersecting slabs, rather than storing a single footprint modulated by a slab coefficient [S1, unofficial]. This approach provides finer tuning of the splat appearance at the cost of increased texture memory for footprint storage.

## How it works
**Inputs and Outputs:**
*   **Input:** A `Bucket Texture` (2D texture containing bucket sizes and distribution), a `VBO` (Vertex Buffer Object) containing all depth-sorted voxels, and a `Footprint Texture` (2D texture storing pre-computed kernel footprints).
*   **Output:** The final rendered image on the GPU framebuffer.

**Data Structures:**
1.  **Bucket Texture:** A small 2D texture where each texel represents a bucket (slab). The size corresponds to the number of buckets. The transfer from GPU to CPU is low-cost due to this small size [S1, unofficial].
2.  **VBO:** Created using the R2VB (Render to Vertex Buffer) extension, containing all voxels processed by the preceding ISSB stages [S1, unofficial].
3.  **Footprint Texture:** A 2D texture storing multiple kernel footprints. Each voxel may have a different footprint depending on the slab it intersects [S1, unofficial].

**Parameters:**
*   **Kernel Radius ($r$):** The radius of the voxel's kernel. It determines the range of buckets that must be processed for each slab [S1, unofficial].

**Algorithm Steps:**
1.  **Transfer Bucket Data:** Transfer the `Bucket Texture` from GPU to CPU to obtain bucket sizes and distribution [S1, unofficial].
2.  **Create VBO:** Use the R2VB extension to create a VBO containing all voxels from the depth-sorted data [S1, unofficial].
3.  **Compute Footprints:** For each voxel, compute all different kernel footprints across all intersecting slabs. Store these footprints in the `Footprint Texture` [S1, unofficial].
4.  **Render Slabs:** For each slab $i$:
    a.  Determine the range of buckets to process: from $bucket_{i-r}$ to $bucket_{i+r}$, where $r$ is the kernel radius [S1, unofficial].
    b.  For each bucket in this range, use `DrawArrays` with the first voxel's position and the number of voxels in the bucket to render them [S1, unofficial].
5.  **Vertex Shader Processing (Point Sprites):**
    a.  The primitive type is `glPoint`. The Point Sprites extension automatically generates a quad from a single point, reducing vertex instances from four to one [S1, unofficial].
    b.  Since Point Sprites compute texture coordinates automatically, the vertex shader must compute the correct texture coordinates manually to access the specific footprint sub-texture [S1, unofficial].
    c.  Compute an index to the specific footprint based on the slab intersection. Use this index to determine the coordinates of the sub-texture containing the corresponding footprint [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Texture Size Limitations:** The method's limitations can arise from texture size limits, which may not fit an entire volume [S1, unofficial].
*   **Automatic Texture Coordinates:** With Point Sprites, texture coordinates are computed automatically. Failing to compute the correct coordinates in the vertex shader will result in incorrect footprint sampling [S1, unofficial].
*   **Bucket Boundary Rejection:** Non-bucket boundary voxels may be rejected if their z-value does not align with the bucket boundary in the auxiliary texture (e.g., a bucket boundary voxel has a 0.5 z value, while a non-boundary voxel is rejected) [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Rendering time depends on the number of slabs and the number of voxels per slab. The bucket range processing is $O(r)$ per slab, where $r$ is the kernel radius.
*   **Memory Complexity:** Requires storage for the `Bucket Texture` (small), `VBO` (all voxels), and `Footprint Texture` (multiple footprints per voxel). The footprint texture size can be significant if many distinct footprints are stored.
*   **Strengths:** Reduces vertex instances from four to one using Point Sprites, improving rendering efficiency. Dynamic footprints allow for better tuning of splats compared to single footprint modulation.
*   **Limitations:** Texture size limitations may restrict volume size. The need to compute and store multiple footprints increases memory usage. The manual computation of texture coordinates in the vertex shader adds complexity.
*   **When to Use:** Suitable for GPU-based volume visualization where rendering efficiency is critical and sufficient texture memory is available.
*   **When Not to Use:** Not suitable if texture memory is severely constrained or if the overhead of computing and storing multiple footprints is prohibitive.

## Background
This method is part of the Image-Space Sheet-Buffered (ISSB) splatting pipeline, which processes voxels through texture-based stages including viewing transform, GPGPU sorting, bucket size computation, and rendering [S1, unofficial]. It builds on previous GPU implementations of ISSB Splatting [S1, unofficial]. The approach of storing a single footprint and modulating it with a slab coefficient was proposed by Neophytou and Mueller [14], but this method improves upon it by computing and storing all different kernel footprints for better tuning [S1, unofficial].
