# ISSB Rendering with Point Sprites and Dynamic Footprints

Also called: GPU Image-Space Sheet-Buffered Splatting Rendering

## Overview
This method defines the final rendering stage of the Image-Space Sheet-Buffered (ISSB) splatting pipeline, where depth-sorted voxels are rasterized using `glPoint` primitives and the Point Sprites extension [S1, unofficial]. It distinguishes itself from prior ISSB implementations by computing and storing distinct kernel footprints for each voxel across all intersecting slabs, rather than storing a single footprint modulated by a slab coefficient [S1, unofficial]. This approach provides finer tuning of the splat appearance [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A `Bucket Texture` (2D texture containing bucket sizes and distribution), a `VBO` (Vertex Buffer Object) containing all depth-sorted voxels, and a `Footprint Texture` (2D texture storing pre-computed kernel footprints) [S1, unofficial].
*   **Output:** The final rendered image on the GPU framebuffer.

**Data Structures:**
1.  **Bucket Texture:** A small 2D texture where each texel represents a bucket (slab) [S1, unofficial]. The transfer from GPU to CPU is low-cost due to this small size [S1, unofficial].
2.  **VBO:** Created using the R2VB (Render to Vertex Buffer) extension, containing all voxels processed by the preceding ISSB stages [S1, unofficial].
3.  **Footprint Texture:** A 2D texture storing multiple kernel footprints, where each voxel may have a different footprint depending on the slab it intersects [S1, unofficial].

**Parameters:**
*   **Kernel Radius ($r$):** The radius of the voxel's kernel. It determines the range of buckets that must be processed for each slab [S1, unofficial].

**Algorithm Steps:**
1.  **Transfer Bucket Data:** Transfer the `Bucket Texture` from GPU to CPU to obtain bucket sizes and distribution [S1, unofficial].
2.  **Create VBO:** Use the R2VB extension to create a VBO containing all voxels from the depth-sorted data [S1, unofficial].
3.  **Compute Footprints:** For each voxel, compute all different kernel footprints across all intersecting slabs and store them in the `Footprint Texture` [S1, unofficial].
4.  **Render Slabs:** For each slab $i$, determine the range of buckets to process: from $bucket_{i-r}$ to $bucket_{i+r}$, where $r$ is the kernel radius [S1, unofficial].
5.  **Draw Buckets:** For each bucket in this range, render all voxels using `DrawArrays` with the first voxel's position and the number of voxels in the bucket [S1, unofficial].
6.  **Vertex Shader Processing (Point Sprites):** Use `glPoint` primitives with the Point Sprites extension to create automatic quads, reducing vertex instances from four to one [S1, unofficial].
7.  **Texture Coordinates:** Since Point Sprites compute texture coordinates automatically, compute the correct texture coordinates manually in the vertex shader [S1, unofficial].
8.  **Footprint Indexing:** Compute an index to the specific footprint based on the slab intersection and use it to determine the coordinates of the sub-texture containing the corresponding footprint [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Texture Size Limitations:** The method's limitations can arise from texture size limits, which may not fit an entire volume [S1, unofficial].
*   **Automatic Texture Coordinates:** With Point Sprites, texture coordinates are computed automatically. Failing to compute the correct coordinates in the vertex shader will result in incorrect footprint sampling [S1, unofficial].
*   **Bucket Boundary Rejection:** Non-bucket boundary voxels may be rejected if their z-value does not align with the bucket boundary in the auxiliary texture (e.g., a bucket boundary voxel has a 0.5 z value, while a non-boundary voxel is rejected) [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources. The bucket range processed per slab spans $2r+1$ buckets, where $r$ is the kernel radius [S1, unofficial].
*   **Memory Complexity:** Requires storage for the `Bucket Texture` (small), `VBO` (all voxels), and `Footprint Texture` (multiple footprints per voxel) [S1, unofficial].
*   **Strengths:** Reduces vertex instances from four to one using Point Sprites, improving rendering efficiency [S1, unofficial]. Dynamic footprints allow for better tuning of splats compared to single footprint modulation [S1, unofficial].
*   **Limitations:** Texture size limitations may restrict volume size [S1, unofficial]. The need to compute and store multiple footprints increases memory usage [S1, unofficial]. The manual computation of texture coordinates in the vertex shader adds complexity [S1, unofficial].
*   **When to Use:** Suitable for GPU-based volume visualization where rendering efficiency is critical and sufficient texture memory is available [G].
*   **When Not to Use:** Not suitable if texture memory is severely constrained or if the overhead of computing and storing multiple footprints is prohibitive [G].

## Background
This method is part of the Image-Space Sheet-Buffered (ISSB) splatting pipeline [S1, unofficial]. It builds on previous GPU implementations of ISSB Splatting [S1, unofficial]. The approach of storing a single footprint and modulating it with a slab coefficient was proposed by Neophytou and Mueller [14], but this method improves upon it by computing and storing all different kernel footprints for better tuning [S1, unofficial].
