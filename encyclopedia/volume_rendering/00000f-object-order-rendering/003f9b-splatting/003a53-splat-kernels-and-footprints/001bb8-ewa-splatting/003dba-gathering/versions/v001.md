# Gathering

Also called: Gather-based rendering, Pixel-parallel splatting

## Overview
Gathering is a rendering technique where, for each output pixel, contributions are gathered from neighboring pixels to compute the new value. It solves the parallelization inefficiency of splatting on GPUs by ensuring that each iteration writes to a single pixel, allowing for efficient parallel execution. It is the conceptual inverse of splatting, which distributes contributions from source pixels to neighboring target pixels.

## How it works
**Inputs:**
- $L$: Input image (or volume projection buffer) where $L(x')$ is the value at pixel position $x'$.
- $w_{x'}$: Spatially varying weighting function associated with source pixel $x'$.
- $N$: The neighborhood radius or set of neighboring pixels.

**Outputs:**
- $L'$: Output image where $L'(x)$ is the accumulated value for target pixel $x$.

**Data Structures:**
- $L$: 2D array of pixel values.
- $L'$: 2D array of pixel values, initialized to zero.

**Steps:**
1. Initialize an empty image $L'$ of the same dimensions as $L$.
2. Iterate over all target pixel positions $x$ in the output image.
3. For each target pixel $x$, iterate over all source pixel positions $x'$ in the neighborhood of $x$.
4. Calculate the total weight for the source pixel $x'$ to ensure correct normalization of the spatially varying kernel. This requires an additional inner loop:
   - Initialize $totalWeight \leftarrow 0$.
   - Let $w_{x'}$ be the weighting function of $x'$.
   - Iterate over all pixel positions $x''$ in the neighborhood of $x'$.
   - Accumulate weights: $totalWeight \leftarrow totalWeight + w_{x'}(x' - x'')$.
5. Compute the normalized weight for the specific contribution from $x'$ to $x$:
   $$ weight = \frac{w_{x'}(x' - x)}{totalWeight} $$
6. Accumulate the contribution to the target pixel:
   $$ L'(x) \leftarrow L'(x) + weight \cdot L(x') $$
7. Return $L'$.

**Pseudocode:**
```python
def NormalizedGather(L):
    # L is the input image, L' is the output image
    height, width = L.shape
    L_prime = zeros_like(L)
    
    # Define neighborhood function to get neighbors within radius R
    # For simplicity, assume a square neighborhood of size (2R+1)x(2R+1)
    R = 1 # Example radius, depends on kernel support
    
    for x in range(height):
        for y in range(width):
            target_pixel = (x, y)
            for x_prime in get_neighbors(target_pixel, R):
                # x_prime is a source pixel coordinate
                # Get the weighting function w_x' associated with this source pixel
                # In many contexts, w_x' is defined by the kernel shape centered at x'
                w_x_prime = get_weighting_function(x_prime)
                
                # Step 4: Calculate total weight for normalization
                total_weight = 0.0
                for x_double_prime in get_neighbors(x_prime, R):
                    # Calculate weight of x_double_prime relative to x_prime
                    # w_x'(x' - x'') represents the kernel value at offset (x' - x'')
                    offset = vector_subtract(x_prime, x_double_prime)
                    total_weight += w_x_prime(offset)
                
                # Step 5: Compute normalized weight for the specific target pixel
                offset_to_target = vector_subtract(x_prime, target_pixel)
                raw_weight = w_x_prime(offset_to_target)
                
                if total_weight > 0:
                    normalized_weight = raw_weight / total_weight
                else:
                    normalized_weight = 0.0
                
                # Step 6: Accumulate contribution
                L_prime[target_pixel] += normalized_weight * L[x_prime]
                
    return L_prime

def get_neighbors(pixel, radius):
    """Returns list of pixel coordinates within radius of pixel."""
    neighbors = []
    px, py = pixel
    for dx in range(-radius, radius + 1):
        for dy in range(-radius, radius + 1):
            nx, ny = px + dx, py + dy
            if is_valid_pixel(nx, ny):
                neighbors.append((nx, ny))
    return neighbors

def vector_subtract(v1, v2):
    return (v1[0] - v2[0], v1[1] - v2[1])

def is_valid_pixel(x, y):
    return 0 <= x < height and 0 <= y < width
```

**Parameters:**
- $R$: Neighborhood radius. Not given in the sources.
- $w_{x'}$: Weighting function. Typically a Gaussian or similar low-pass filter kernel. Not given in the sources.

**Edge Cases and Pitfalls:**
- **Normalization Error:** If the inner loop for calculating `totalWeight` is omitted, the normalization is incorrect because spatially varying kernels have different total weights for different source pixels. This leads to visual artifacts or intensity errors [S1, unofficial].
- **Performance:** The additional inner loop for normalization significantly increases computational cost.
- **Boundary Conditions:** Pixels near the image boundary have fewer neighbors. The neighborhood function must handle boundary checks to avoid out-of-bounds access [G].

## Operating characteristics
- **Time Complexity:** $O(n^2 m^4)$, where $n$ is the number of pixels and $m$ is the neighborhood size (radius). This is due to the additional inner loop required for correct normalization of spatially varying kernels [S1, unofficial].
- **Memory Complexity:** $O(n^2)$ for storing the input and output images.
- **Strengths:** Fits GPUs better than splatting because it writes to a single pixel per iteration, allowing for efficient parallel execution without atomic operations or complex memory coalescing issues associated with scatter writes [S1, unofficial].
- **Limitations:** The $O(n^2 m^4)$ complexity is high. For large neighborhoods or high resolutions, this can be prohibitively slow.
- **When to use:** When correct normalization of spatially varying kernels is required and GPU parallelization is a priority.
- **When not to use:** When performance is critical and the neighborhood size is large, or when an approximation (fast gathering) is acceptable.

## Background
Gathering was introduced as an alternative to splatting in the context of real-time light transport in participating media and volume rendering. It is cited from Elek et al. [2013] and Shinya et al. [2016] [S1, unofficial]. The technique is particularly relevant for GPU-based rendering where write conflicts in splatting (scatter) can degrade performance.
