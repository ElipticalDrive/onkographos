# Gathering

Also called: Gather-based rendering, Pixel-parallel splatting

## Overview
Gathering is a rendering technique where, for each output pixel, contributions are gathered from neighboring pixels to compute the new value [S1, unofficial]. It fits GPUs better than splatting because it writes to a single pixel per iteration, allowing parallel execution [S1, unofficial].

## How it works
**Inputs:**
- $L$: Input image or volume projection buffer.
- $w_{x'}$: Spatially varying weighting function associated with source pixel $x'$.
- $m$: Neighborhood radius or size defining the set of neighboring pixels.

**Outputs:**
- $L'$: Output image where $L'(x)$ is the accumulated value for target pixel $x$.

**Data Structures:**
- $L$: 2D array of pixel values.
- $L'$: 2D array of pixel values, initialized to zero.

**Steps:**
1. Initialize an empty image $L'$ of the same dimensions as $L$ [S1, unofficial].
2. Iterate over all target pixel positions $x$ in the output image [S1, unofficial].
3. For each target pixel $x$, iterate over all source pixel positions $x'$ in the neighborhood of $x$ [S1, unofficial].
4. Calculate the total weight for the source pixel $x'$ to ensure correct normalization of the spatially varying kernel [S1, unofficial]:
   - Initialize $totalWeight \leftarrow 0$ [S1, unofficial].
   - Let $w_{x'}$ be the weighting function of $x'$ [S1, unofficial].
   - Iterate over all pixel positions $x''$ in the neighborhood of $x'$ [S1, unofficial].
   - Accumulate weights: $totalWeight \leftarrow totalWeight + w_{x'}(x' - x'')$ [S1, unofficial].
5. Compute the normalized weight for the specific contribution from $x'$ to $x$:
   $$ weight = \frac{w_{x'}(x' - x)}{totalWeight} $$ [S1, unofficial].
6. Accumulate the contribution to the target pixel:
   $$ L'(x) \leftarrow L'(x) + weight \cdot L(x') $$ [S1, unofficial].
7. Return $L'$ [S1, unofficial].

**Pseudocode:**
```python
def NormalizedGather(L, m):
    height, width = L.shape
    L_prime = [[0.0] * width for _ in range(height)]
    for x in range(height):
        for y in range(width):
            target_pixel = (x, y)
            for dx_prime in range(-m, m + 1):
                for dy_prime in range(-m, m + 1):
                    x_prime = (x + dx_prime, y + dy_prime)
                    if 0 <= x_prime[0] < height and 0 <= x_prime[1] < width:
                        # w_x_prime is the spatially varying weighting function of x'
                        # Not given in the sources. [G] Standard implementation uses a distance-based kernel.
                        def w_x_prime(offset):
                            dist = (offset[0]**2 + offset[1]**2)**0.5
                            return max(0.0, 1.0 - dist)
                        total_weight = 0.0
                        for dx_double_prime in range(-m, m + 1):
                            for dy_double_prime in range(-m, m + 1):
                                x_double_prime = (x_prime[0] + dx_double_prime, x_prime[1] + dy_double_prime)
                                if 0 <= x_double_prime[0] < height and 0 <= x_double_prime[1] < width:
                                    offset = (x_prime[0] - x_double_prime[0], x_prime[1] - x_double_prime[1])
                                    total_weight += w_x_prime(offset)
                        offset_to_target = (x_prime[0] - target_pixel[0], x_prime[1] - target_pixel[1])
                        raw_weight = w_x_prime(offset_to_target)
                        if total_weight > 0:
                            normalized_weight = raw_weight / total_weight
                        else:
                            normalized_weight = 0.0
                        L_prime[target_pixel[0]][target_pixel[1]] += normalized_weight * L[x_prime[0]][x_prime[1]]
    return L_prime
```

**Parameters:**
- $m$: Neighborhood radius. Not given in the sources.
- $w_{x'}$: Weighting function. Not given in the sources.

**Edge Cases and Pitfalls:**
- **Normalization Error:** If the inner loop for calculating `totalWeight` is omitted, the normalization is incorrect because spatially varying kernels have different total weights for different source pixels [S1, unofficial].
- **Boundary Conditions:** Pixels near the image boundary have fewer neighbors; the neighborhood iteration must handle boundary checks to avoid out-of-bounds access [G].

## Operating characteristics
- **Time Complexity:** $O(n^2 m^4)$, where $n$ is the number of pixels and $m$ is the neighborhood size, due to the additional inner loop required for correct normalization of spatially varying kernels [S1, unofficial].
- **Memory Complexity:** $O(n^2)$ for storing the input and output images [G].
- **Strengths:** Fits GPUs better than splatting because it writes to a single pixel per iteration, allowing parallel execution [S1, unofficial].
- **Limitations:** The $O(n^2 m^4)$ complexity is high, making it slow for large neighborhoods or high resolutions [S1, unofficial].
- **When to use:** When correct normalization of spatially varying kernels is required and GPU parallelization is a priority [S1, unofficial].
- **When not to use:** When performance is critical and the neighborhood size is large, or when an approximation (fast gathering) is acceptable [S1, unofficial].

## Background
Gathering was introduced as an alternative to splatting in the context of real-time light transport in participating media and volume rendering [S1, unofficial]. It is cited from Elek et al. [2013] and Shinya et al. [2016] [S1, unofficial]. The technique is particularly relevant for GPU-based rendering where write conflicts in splatting (scatter) can degrade performance [S1, unofficial].
