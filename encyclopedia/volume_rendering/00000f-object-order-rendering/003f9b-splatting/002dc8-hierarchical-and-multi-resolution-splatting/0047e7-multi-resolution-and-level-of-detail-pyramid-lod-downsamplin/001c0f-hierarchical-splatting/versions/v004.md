# Hierarchical Splatting

Also called: Progressive refinement splatting, Pyramid Splatting, Pyramidal volume splatting

## Overview
Hierarchical Splatting is a progressive refinement algorithm for volume rendering that uses a pyramidal volume representation to achieve real-time interactive rendering [S1, unofficial]. It solves the performance bottleneck of rendering high-resolution volumetric data by decomposing the volume into a hierarchy of cells with varying sizes based on homogeneity, approximating each cell with a single large splat projected onto the image plane [S3, unofficial]. Unlike standard splatting which treats all voxels equally, Hierarchical Splatting adapts the resolution of the rendering primitives to the visual complexity of the data, allowing for coarse approximations in homogeneous regions and fine detail in complex areas [S3, unofficial]. It distinguishes itself from sibling methods like Octree-based Splatting by using a fixed-resolution pyramid structure (where each level is 1/8th the resolution of the previous) rather than an adaptive octree, although an octree can be fit to the pyramid for traversal [S1, unofficial][S4, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D volume dataset of size $N^3$ samples, a user-specified error threshold $\epsilon$ (measuring desired homogeneity), and a viewing transformation.
*   **Output:** A 2D image rendered via alpha compositing of splats approximated as polygons.

**Data Structures:**
1.  **Pyramid Data Structure:** A sequence of $\log_2 N$ volumes.
    *   Level 0: The original $N^3$ dataset.
    *   Level $k$ ($k > 0$): A volume with resolution $(N/2^k)^3$. Each voxel at level $k$ is the average of the $2 \times 2 \times 2$ group of voxels from level $k-1$ that it covers [S2, unofficial][S4, unofficial].
    *   For binary data, bits can be packed into bytes to accelerate the creation of lower-resolution levels, where a byte represents a $2 \times 2 \times 2$ portion [S2, unofficial].
2.  **Node Properties:** Each node (voxel) in the pyramid stores:
    *   Average RGB color and alpha value of its children [S3, unofficial].
    *   Estimated error $E$, representing the approximation cost if the region is rendered with one average splat instead of the original data [S1, unofficial][S3, unofficial].
3.  **Footprint Tables:** Pre-calculated tables for each pyramid level defining the proper-sized footprint (polygon shape and size) used for projecting and compositing cells of that specific level [S3, unofficial].

**Algorithm Steps:**

1.  **Pyramid Construction:**
    *   Construct the pyramid by iteratively averaging $2 \times 2 \times 2$ groups of samples from the previous level to create the next lower-resolution level [S4, unofficial].
    *   For each node, compute the aggregate average color/alpha and the error metric $E$. The error metric quantifies the deviation of the children's values from the node's average value [S3, unofficial].
    *   *Note: The exact formula for $E$ is not explicitly provided in the sources, but it is described as the "average error" or "approximation cost" [S3, unofficial].*

2.  **Octree Fitting (Optional/Implicit):**
    *   Fit an octree to the pyramid based on the user-supplied precision threshold $\epsilon$ [S1, unofficial]. This step determines which nodes are "leaves" in the rendering hierarchy. A node is selected as a leaf if its error $E \le \epsilon$ [S3, unofficial].

3.  **Traversal and Selection:**
    *   Traverse the pyramid from the root to the leaves.
    *   For each node, compare its error $E$ to the threshold $\epsilon$.
    *   If $E \le \epsilon$, the node is selected as a leaf. The algorithm stops descending into its children for this branch [S3, unofficial].
    *   If $E > \epsilon$, the algorithm recurses to the node's children [S3, unofficial].
    *   *Note: The sources mention scanning the "appropriate level" of the pyramid [S4, unofficial], but also describe a traversal down the pyramid based on error [S3, unofficial]. The error-based traversal is the defining characteristic of the "progressive refinement" aspect [S1, unofficial].*

4.  **Splat Generation:**
    *   For each selected leaf node, generate a splat.
    *   The splat is a polygon approximating the projection of the volume cell corresponding to the leaf node [S1, unofficial].
    *   The size of the splat is scaled to match the size of the projection of the corresponding volume cell [S1, unofficial]. The footprint table for the specific pyramid level of the leaf node provides the base shape and size [S3, unofficial].
    *   The color and alpha of the splat are taken from the node's stored average RGB and alpha values [S3, unofficial].

5.  **Rasterization:**
    *   Approximate the splats as RGBA Gouraud-shaded polygons [S1, unofficial][S3, unofficial].
    *   Render the polygons using standard graphics hardware.
    *   Composite the splats in back-to-front order to ensure correct alpha blending [S4, unofficial][S2, unofficial].

    volume_data: 3D array of shape (N, N, N)
    epsilon: float, user-specified error threshold
    view_transform: function or matrix defining the camera view

    # pyramid[k] is a 3D array of shape (N/2^k, N/2^k, N/2^k)
    pyramid = [volume_data]
    current_level_data = volume_data
    level_errors = [] # List of 3D arrays storing error for each level
    
    # Pre-calculate footprint tables for each level

    for k in range(int(math.log2(len(volume_data))) + 1):
        footprint_tables.append(generate_footprint_table(k, view_transform))

    # Build pyramid levels and compute errors
    while len(current_level_data) > 1:
        next_level_shape = (len(current_level_data) // 2, 
                            len(current_level_data) // 2, 
                            len(current_level_data) // 2)
        next_level_data = np.zeros(next_level_shape)
        next_level_error = np.zeros(next_level_shape)
        
        for x in range(0, len(current_level_data), 2):
            for y in range(0, len(current_level_data), 2):
                for z in range(0, len(current_level_data), 2):
                    # Average 2x2x2 group
                    group = current_level_data[x:x+2, y:y+2, z:z+2]
                    avg_value = np.mean(group)
                    next_level_data[x//2, y//2, z//2] = avg_value
                    
                    # Compute error (approximation cost)
                    # Note: Exact formula not given in sources, using variance as proxy for error metric
                    # E = sqrt(mean((children - avg)^2))
                    error = np.sqrt(np.mean((group - avg_value)**2))
                    next_level_error[x//2, y//2, z//2] = error
        
        pyramid.append(next_level_data)
        level_errors.append(next_level_error)
        current_level_data = next_level_data

    # Step 2 & 3: Traverse and Select Leaves

            # However, the algorithm typically stops at pyramid leaves
            # If epsilon is very small, we might reach here.

            add_splat(level_idx, x, y, z, pyramid[level_idx][x, y, z])

        # Note: The error stored in level_errors[level_idx] corresponds to the 
        # approximation cost of the node AT level_idx+1 (its children).
        # If we are at level_idx, we look at the error of the node we are considering.
        # The sources say: "move down the pyramid until the error in a node is less equal than the desired error"
        # This implies we check the error of the CURRENT node against epsilon.
        # But the error is computed from children. So we check the error of the PARENT

        # Standard interpretation: If the error of the current node (representing the 
        # deviation of its children from its average) is <= epsilon, we stop and use 
        # the current node's average.
        
        # In our pyramid structure, level_errors[k] stores the error for nodes at level k+1?
        # No, level_errors[k] is computed when creating level k+1 from level k.
        # So level_errors[k][x,y,z] is the error of the node at pyramid[k+1][x,y,z]
        # based on its children in pyramid[k].

        # We want to know if we should split it. We split if its error > epsilon.

**Parameters:**
*   **Error Threshold ($\epsilon$):** A user-specified value that measures the desired homogeneity. Selecting a larger error results in fewer subvolumes (coarser decomposition), while decreasing the error increases the number of subvolumes (finer decomposition) [S3, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** The error metric must be computed accurately to avoid over-segmentation or under-segmentation. The sources do not specify the exact numerical precision required, but note that for binary data, bit-packing can be used for efficiency [S2, unofficial].
*   **Boundaries:** The pyramid construction assumes the volume dimensions are powers of 2. If not, padding or truncation may be required [G].
*   **Degenerate Input:** If the volume is entirely homogeneous, the entire volume may be represented by a single splat at the root level [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** The construction of the pyramid takes $O(N^3)$ time, as each level is derived from the previous one in linear time relative to the number of voxels. The traversal and rendering time depends on the error threshold $\epsilon$. In the worst case (very small $\epsilon$), it approaches $O(N^3)$ splats. In the best case (large $\epsilon$), it approaches $O(1)$ splats.
*   **Memory Complexity:** The pyramid requires $O(N^3)$ memory, as it stores $\log N$ levels, each with $1/8$ the size of the previous. The total memory is $N^3 (1 + 1/8 + 1/64 + ...) \approx \frac{8}{7} N^3$, which is a constant factor overhead over the original data [S2, unofficial][S4, unofficial].
*   **Measured Performance:** For binary data, using bit-packing to generate lower-resolution images can produce an image with half the linear resolution in approximately one-eighth the time [S2, unofficial]. The algorithm is designed for real-time interactive rendering on modern graphics workstations by leveraging hardware-accelerated polygon rasterization [S1, unofficial].
*   **Strengths:** Real-time performance, adaptive resolution based on data homogeneity, efficient use of graphics hardware via polygon approximation.
*   **Limitations:** Fixed pyramid structure may not be optimal for all data distributions compared to adaptive octrees. The error metric is a simplification and may not always correlate perfectly with visual quality.
*   **When to use:** Interactive volume rendering applications where performance is critical and the data has regions of varying homogeneity.
*   **When not to use:** When the data has complex, non-homogeneous structures that require fine resolution everywhere, or when the overhead of building the pyramid is prohibitive.

## Background
Hierarchical Splatting was introduced by David Laur and Pat Hanrahan in 1991 [S1, unofficial]. It was one of the early algorithms to combine hierarchical data structures with splatting for volume rendering, aiming to achieve real-time performance on the graphics workstations of that era. The method builds on the concept of pyramidal data structures, which were previously used in image processing for multi-resolution analysis. The algorithm was notable for its use of Gouraud-shaded polygons to approximate splats, allowing it to leverage the rasterization capabilities of existing graphics hardware [S1, unofficial][S2, unofficial]. It has been cited in subsequent works on volume rendering and multi-resolution visualization [S2, unofficial][S4, unofficial].
