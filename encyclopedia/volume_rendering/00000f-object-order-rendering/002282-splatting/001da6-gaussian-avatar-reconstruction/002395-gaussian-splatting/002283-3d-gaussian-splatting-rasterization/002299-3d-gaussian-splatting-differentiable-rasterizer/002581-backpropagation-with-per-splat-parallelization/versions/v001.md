# Backpropagation with Per-Splat Parallelization

Also called: Per-splat backward, Splat-parallel backprop

## Overview
This method is a parallelization scheme for the backward pass of 3D Gaussian Splatting rasterization that maps CUDA threads to 2D splats rather than pixels to eliminate atomic contention on gradient accumulation [S1]. It differs from the original 3DGS approach, which maps threads to pixels and suffers from serialized atomic operations when multiple threads contend for the same Gaussian's gradient, by having threads maintain per-splat state and exchange smaller per-pixel states (transmittance $T$ and accumulated color $RGB$) via intra-warp shuffling [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** Depth-sorted list of splats per tile, forward pass intermediate states (specifically per-pixel states stored at intervals), tile dimensions, and the number of threads per tile (typically equal to the number of pixels in the tile).
*   **Output:** Gradients for Gaussian parameters (position, scale, rotation, opacity, spherical harmonics coefficients) accumulated per splat.

**Data Structures:**
*   **Autodiff Context:** Stores per-pixel state snapshots. Specifically, it stores the state $(T, RGB)$ for every pixel $j$ after blending every $N$ splats (where $N=32$).
*   **Per-Splat State:** Maintained by each thread, containing the gradient contributions for the specific splat assigned to that thread.
*   **Per-Pixel State:** Contains transmittance $T$ and accumulated color $RGB$. This is exchanged between threads.

**Parameters:**
*   **Bucket Size ($N$):** Splats are divided into buckets of size 32. Each bucket is scheduled to a single CUDA warp [S1].
*   **Threads per Tile:** Typically equal to the number of pixels in the tile, but the logic assumes a simplified setting where $\#threads = \#pixels = \#splats = N$ for explanation [S1].

**Steps:**

1.  **Forward Pass Storage:** During the forward pass, for each tile, store the per-pixel state $(T, RGB)$ for all pixels $j$ after blending every $N$-th splat (e.g., splats $0, N, 2N, \dots$). This creates available starting states $(0, j), (N, j), \dots$ for all pixels $j$ in the autodiff context [S1].
2.  **Backward Pass Initialization:** Each thread $i$ in a tile initializes its local per-pixel state for pixel $j$ by interpolating or computing the state $(i, j)$ from the stored starting states. Specifically, if $i$ falls between stored indices $k \cdot N$ and $(k+1) \cdot N$, the thread reconstructs the state at index $i$ using the state at $k \cdot N$ and the splats in between [S1].
3.  **State Exchange:** Threads within a warp exchange their current per-pixel states $(T, RGB)$ using fast intra-warp shuffling operations. This allows each thread to access the necessary pixel states for the current splat iteration without global memory contention [S1].
4.  **Gradient Computation:** For each splat $i$ in the bucket:
    a. Thread $i$ receives the per-pixel state $(i, j)$ from the exchange.
    b. Thread $i$ applies the default alpha blending logic to compute the state $(i+1, j)$ from $(i, j)$ and the properties of splat $i$.
    c. Thread $i$ computes the gradient portion for splat $i$ based on the difference between the received state $(i, j)$ and the updated state $(i+1, j)$, incorporating this into the splat's accumulated gradient [S1].
5.  **Optimization - Last Contributor Tracking:** Track the last contributing splat for each pixel across the tile during the forward pass. In the backward pass, skip entire groups of splat-tile pairings where the pixel is already saturated (transmittance $T \approx 0$), exploiting occlusion observed in the forward pass [S1].
6.  **Optimization - Tighter Culling:** Apply tighter culling techniques (as proposed by Radl et al. [2024]) to minimize redundant splats in both forward and backward passes [S1].

# - Tile has P pixels and S splats.
# - N = 32 (bucket size).
# - Threads per warp = 32.
# - Each warp handles one bucket of N splats.
# - Thread index i corresponds to pixel i (in simplified model).

    """
    tile_splats: List of splats sorted by depth for the tile.
    forward_states: Dict mapping splat_index -> {pixel_states: [T, RGB] for each pixel}

        bucket_splats = tile_splats[bucket_start : bucket_start + 32]
        
        # Each thread in the warp handles one splat in the bucket
        # and one pixel (in the simplified model)
        for thread_idx, splat in enumerate(bucket_splats):
            # 3. Initialize per-pixel state for this thread's pixel

            # 4. Exchange states with other threads in the warp
            # In CUDA, this is done via __shfl_down_sync or similar intrinsics.
            # Here, we simulate the exchange by making states available to all threads.
            # Each thread needs the pixel states for all pixels to compute gradients?

**Edge Cases and Pitfalls:**
*   **Precision:** Floating-point precision issues may arise during the reconstruction of intermediate states from stored snapshots.
*   **Boundaries:** Handling splats that partially cover a tile or pixels at the tile boundary requires careful culling and state management.
*   **Degenerate Input:** Splats with zero opacity or very small covariance matrices may lead to numerical instability; culling should handle these.

## Operating characteristics
*   **Time Complexity:** Reduces the time complexity of the backward pass by eliminating atomic contention. The original 3DGS has $O(P \cdot S)$ with high constant factors due to atomics, where $P$ is pixels and $S$ is splats. This method maintains $O(P \cdot S)$ but with much lower constant factors due to warp-level parallelism and shuffling [S1].
*   **Memory Complexity:** Requires storing per-pixel states at intervals of $N=32$ splats, increasing memory usage slightly compared to storing no intermediate states, but less than storing all states [S1].
*   **Measured Performance:** Significantly faster backward pass compared to original 3DGS and DISTWAR [S1].
*   **Strengths:** Eliminates atomic contention, leverages fast intra-warp communication, exploits occlusion.
*   **Limitations:** Requires careful state management and reconstruction, may have higher memory overhead for storing intermediate states.
*   **When to Use:** When training 3D Gaussian Splatting models and backward pass performance is a bottleneck.
*   **When Not to Use:** If memory is extremely constrained and the overhead of storing intermediate states is prohibitive.

## Background
This method was introduced in "Taming 3DGS: High-Quality Radiance Fields with Limited Resources" (2024) to address the performance bottleneck in the backward pass of 3D Gaussian Splatting [S1]. It builds on the original 3DGS rasterization method by Kerbl et al. [2023] and addresses the atomic contention issues identified in concurrent work like DISTWAR [Durvasula et al. 2023] [S1].
