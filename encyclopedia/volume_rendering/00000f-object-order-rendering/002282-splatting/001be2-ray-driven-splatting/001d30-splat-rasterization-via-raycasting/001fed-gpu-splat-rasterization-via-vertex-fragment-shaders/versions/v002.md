# GPU Splat Rasterization via Vertex/Fragment Shaders

Also called: Point Primitive Splatting, Shader-based Splatting

## Overview
This method implements splat rasterization on GPUs by simulating a dedicated rasterization unit using standard graphics pipeline stages: vertex shaders for transformation and bounding box calculation, point primitives for fragment generation, and fragment shaders for kernel evaluation and depth computation [S1, unofficial]. It solves the problem of efficiently projecting 3D splats onto the screen while maintaining accurate depth values and filtering weights, optimizing for minimal instruction count in the fragment shader [S1, unofficial]. It is more efficient than previous GPU splatting implementations because the fragment shader requires only three computational instructions (two MADs and one texture fetch), whereas previous approaches were more expensive [S1, unofficial].

## How it works
**Inputs and Outputs:**
Splats are sent to the GPU using the standard point primitive [S1, unofficial]. The output is a rasterized image with accumulated attributes and depth values, where each fragment corresponds to a pixel covered by a splat [S1, unofficial].

**Data Structures:**
Each splat $k$ is represented by its inverse mapping matrix $\mathbf{N}_k$ and its center position [S1, unofficial]. A 2D texture stores the precomputed 2D reconstruction kernel weights $r_0(x)$ [S1, unofficial].

**Steps:**
1. The vertex shader computes the inverse mapping matrix $\mathbf{N}_k$ for each splat [S1, unofficial].
2. The vertex shader computes a conservative 2D axis-aligned bounding box of the projected splat [S1, unofficial].
3. The position of the point primitive is set to the center of this bounding box [S1, unofficial].
4. The size of the point primitive is set to the largest dimension of the bounding box [S1, unofficial].
5. The fragment shader receives the matrix $\mathbf{N}_k$ transmitted as three column vectors [S1, unofficial].
6. The fragment shader performs the matrix multiplication to transform the fragment's screen-space coordinates into the splat's local space using only two MAD (Multiply-Add) instructions [S1, unofficial].
7. The weight $r_0(x)$ is retrieved from the 2D kernel texture via a single projective texture fetch [S1, unofficial].
8. The accurate window-space depth value is extracted from the fourth component of the matrix product result [S1, unofficial].
9. Fragments outside the splat are discarded using the alpha test unit [S1, unofficial].
10. Attributes are multiplied by the weight and accumulated using the blending unit [S1, unofficial].

**Formulas:**
Let $\mathbf{N}_k$ be the inverse mapping matrix for splat $k$ [S1, unofficial]. Let $\mathbf{p}$ be the screen-space position of the fragment [S1, unofficial]. The transformed local coordinate $\mathbf{u}$ is computed as $\mathbf{u} = \mathbf{N}_k \mathbf{p}$ [S1, unofficial]. The weight is $w = r_0(\mathbf{u})$ [S1, unofficial]. The depth is $z = (\mathbf{N}_k \mathbf{p})_4$ [S1, unofficial].

**Parameters:**
Kernel texture resolution: Not given in the sources. Alpha test threshold: Not given in the sources.

**Edge Cases and Pitfalls:**
In cases of minification and high frequencies, resampling filters may miss pixels leading to aliasing artifacts [S1, unofficial]. This is addressed by band-limiting reconstruction kernels via convolution with a screen-space pre-filter, as in the original EWA splatting framework [S1, unofficial]. The conservative bounding box ensures all fragments are generated, which is necessary for correct coverage but may include fragments that are ultimately discarded by the alpha test [S1, unofficial].

**Pseudocode:**
```python
def mad(a, b, c):
    return a * b + c

def compute_inverse_mapping_matrix(splat):
    # Computes the inverse mapping matrix N_k from splat parameters
    return [[1, 0, 0], [0, 1, 0], [0, 0, 1]]

def compute_2d_aabb(N_k, center):
    # Computes conservative 2D axis-aligned bounding box of projected splat
    return type('Box', (), {'center': (0, 0), 'width': 1, 'height': 1})()

def vertex_shader(splat):
    N_k = compute_inverse_mapping_matrix(splat)
    bbox = compute_2d_aabb(N_k, splat.center)
    point_position = bbox.center
    point_size = max(bbox.width, bbox.height)
    return point_position, point_size, N_k

def fragment_shader(point_position, point_size, N_k, fragment_screen_pos, kernel_texture, alpha_threshold, fragment_attributes):
    # N_k is transmitted as three column vectors
    c1, c2, c3 = N_k[0], N_k[1], N_k[2]
    # Matrix multiplication using two MAD instructions for 2D coordinates
    u_x = mad(c1[0], fragment_screen_pos[0], mad(c2[0], fragment_screen_pos[1], c3[0]))
    u_y = mad(c1[1], fragment_screen_pos[0], mad(c2[1], fragment_screen_pos[1], c3[1]))
    # Depth is the fourth component of the matrix product
    depth = mad(c1[2], fragment_screen_pos[0], mad(c2[2], fragment_screen_pos[1], c3[2]))
    # Retrieve weight from precomputed 2D kernel texture
    weight = kernel_texture[u_x, u_y]
    # Discard fragments outside the splat using alpha test
    if weight < alpha_threshold:
        return None
    # Multiply attributes by weight and accumulate via blending unit
    accumulated = fragment_attributes * weight
    return accumulated, depth
```

## Subtopics

### GPU Splatting and Voxelization
This variant focuses on voxelizing particle data by rendering screen-aligned bounding quads using an OpenGL geometry shader to project particle spheres onto the screen [S2, unofficial]. For each generated fragment, the particle sphere is intersected with the corresponding camera ray, and all overlapped voxels in the corresponding column are marked using atomic bitwise operations [S2, unofficial]. For particles with radius < 7 pixels on NVIDIA GTX Titan, a simple splatting CUDA kernel can be used for parallel processing, which projects particles onto the screen and loops over all pixels in an axis-aligned bounding quad sequentially [S2, unofficial]. CUDA does not expose atomics on textures directly; they are accessible via the 'sured' instruction using inline PTX code [S2, unofficial]. On GTX 970, pure OpenGL-based rendering is always faster than CUDA splatting [S2, unofficial].

## Operating characteristics
The fragment shader complexity is very low, requiring only three computational instructions (two MADs and one texture fetch) [S1, unofficial]. Memory usage depends on the number of splats and the kernel texture size [S1, unofficial]. On NVIDIA GTX 970, splatting performance for 1024x1024 tile size is 76 ms, compression is 28 ms [S2, unofficial]. On NVIDIA GTX 970, splatting performance for 512x512 tile size is 80 ms, compression is 28 ms [S2, unofficial]. On NVIDIA GTX 970, splatting performance for 256x256 tile size is 182 ms, compression is 32 ms [S2, unofficial]. On NVIDIA GTX 970, splatting performance for 128x128 tile size is 546 ms, compression is 47 ms [S2, unofficial]. On NVIDIA GTX 970, splatting performance for 1024x512 tile size is 58 ms, compression is 28 ms [S2, unofficial]. Performance scales with tile size and number of particles [S2, unofficial]. SIMT efficiency is improved when particles are partially sorted by the simulation, grouping particles of approximately equal distance and size [S2, unofficial]. The method offers high efficiency due to minimal fragment shader instructions and simple implementation using standard graphics pipeline stages [S1, unofficial]. Aliasing artifacts may occur in minification without pre-filtering [S1, unofficial]. CUDA-based splatting is slower than OpenGL-based rendering on GTX 970 [S2, unofficial].

## Background
This method was introduced in the paper "Splat/Mesh Blending, Perspective Rasterization and Transparency for Point-Based Rendering" [S1, unofficial]. It builds on previous GPU-based splatting implementations by optimizing the fragment shader to use only three computational instructions [S1, unofficial]. The approach is part of the broader field of point-based rendering and splatting techniques [S1, unofficial].
