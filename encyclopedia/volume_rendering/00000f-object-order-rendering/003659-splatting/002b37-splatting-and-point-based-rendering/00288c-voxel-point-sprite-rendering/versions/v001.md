# Voxel Point Sprite Rendering

Also called: GL_POINTS voxel rendering, OpenGL Voxel Splatting, Point-based Voxel Rendering, Voxel Splatting

## Overview
Voxel Point Sprite Rendering is a technique that represents a 3D voxel grid as a stream of points (`GL_POINTS`) submitted to the graphics pipeline, where each point is expanded into a screen-space primitive (sprite) by a geometry shader or fixed-function logic to approximate the voxel's volume [S1, S2, unofficial]. It solves the problem of rendering large, dense voxel datasets with minimal CPU-side geometry generation overhead by leveraging the GPU's point rasterization capabilities [S2, unofficial]. Unlike sibling methods that rasterize explicit quads or cubes, this method relies on point sprites, often combined with stochastic culling and mipmapping to manage performance at varying distances [S1, S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D grid of voxel data (position, color/albedo). The grid dimensions are defined by $N_{dim}$ (e.g., $4 \times 4 \times 4$ or $200 \times 50 \times 200$) [S1, S2, unofficial].
*   **Output:** A rasterized image where voxels are rendered as point sprites, potentially with mipmapped detail levels based on camera distance [S1, S2, unofficial].

**Data Structures:**
The implementation varies slightly between source implementations regarding data packing, but both use compact 32-bit integers to store voxel attributes.

1.  **Packed Position/Albedo (Source [S1, unofficial]):**
    *   Stored in a flat `uint32_t` array of size `no_of_vertices * 2`.
    *   **First `uint32_t` (Position):**
        *   Bits 0–10 (11 bits): $x$ coordinate.
        *   Bits 11–20 (10 bits): $y$ coordinate.
        *   Bits 21–31 (11 bits): $z$ coordinate.
    *   **Second `uint32_t` (Albedo):**
        *   Bits 0–4 (5 bits): Red channel.
        *   Bits 5–10 (6 bits): Green channel.
        *   Bits 11–15 (5 bits): Blue channel.
    *   *Note:* This format is bound to a VAO using `glVertexAttribIPointer` with `GL_INT` and a stride of `2 * sizeof(uint32_t)` [S1, unofficial].

2.  **Mipmap Voxel Storage (Source [S2, unofficial]):**
    *   Stored in `std::vector<uint>` within a `CUBE256::MipMap::voxels` structure.
    *   **Packing Order:** $x$ (8 bits) | $(y \ll 8)$ (8 bits) | $(z \ll 16)$ (8 bits) | $(color \ll 24)$ (8 bits).
    *   This forms a single 32-bit unsigned integer per voxel [S2, unofficial].
    *   The VBO layout for the geometry shader consists of four 4-component attributes (`vertex0` to `vertex3`), each reading 4 unsigned bytes (`GL_UNSIGNED_BYTE`) with normalization (`GL_TRUE`) from a stride of 16 bytes. `vertex0` reads bytes 0–3, `vertex1` reads 4–7, etc. [S2, unofficial].

**Algorithm Steps:**

1.  **Voxel Grid Initialization:**
    *   Define grid dimensions $Cubes_x, Cubes_y, Cubes_z$ (default $4 \times 4 \times 4$) [S2, unofficial].
    *   Resize the voxel storage container to hold $Cubes_x \times Cubes_y \times Cubes_z$ elements [S2, unofficial].
    *   For each voxel index $(i, j, k)$, compute the packed position and albedo/color values [S1, S2, unofficial].

2.  **Mipmap Level Calculation (Source [S2, unofficial]):**
    *   For each voxel, calculate the distance from the camera.
    *   Determine the mipmap level $L$ based on screen-space projection:
        $$
        L = \sqrt{\sqrt{\| \text{screen.pos} + (\text{pos} + \vec{3}(0.5, 0.5, 0.5) + \text{add}) \times 16 \|}} - 1
        $$
    *   Clamp $L \ge 0$ [S2, unofficial].
    *   The rendering scale for the splat is calculated as:
        $$
        \text{scale} = 0.1 \times (1 \ll L)
        $$
        where $L$ is the mipmap level [S2, unofficial].

3.  **Stochastic Culling (Source [S1, unofficial]):**
    *   To maintain performance for distant/small voxels, apply stochastic culling in the vertex shader.
    *   Calculate projected area: $\text{stochasticCoverage} = \text{point\_size}^2$ [S1, unofficial].
    *   If $\text{stochasticCoverage} < 0.8$, discard the vertex with probability proportional to its size:
        ```glsl
        if (stochasticCoverage < 0.8 && ((gl_VertexID & 0xffff) > stochasticCoverage * (0xffff / 0.8))) {
            position = vec4(-1, -1, -1, -1);
            point_size = 0.0;
        }
        ```
    *   This effectively removes voxels that would render as sub-pixel noise [S1, unofficial].

4.  **Vertex Shader Processing (Source [S1, unofficial]):**
    *   Unpack voxel coordinates from the packed `uint32_t` position using bitmasks:
        ```glsl
        u_x = data.x & uint(2047);
        u_y = (data.x & uint(2095104)) >> uint(11);
        u_z = (data.x & (uint(2047) << uint(21))) >> uint(21);
        ```
    *   Convert to world space by multiplying by a scaling factor (e.g., $0.1$) [S1, unofficial].
    *   **Pitfall:** Explicitly discard voxels behind the camera ($position.z \le 0.0$) by setting `position = vec4(-1,-1,-1,-1)` and `point_size = 0.0` to prevent rendering artifacts [S1, unofficial].

5.  **Point Sprite Sizing (Source [S1, unofficial]):**
    *   Approximate the sphere radius of the voxel for proper projection:
        $$
        \text{sphereRadius} = \text{voxelSize} \times 1.732051
        $$
        where $1.732051 \approx \sqrt{3}$, representing half the diagonal of a unit cube [S1, unofficial].
    *   Calculate quadric projection coefficients for the fragment shader to render the voxel as a square/quad:
        $$
        \text{eqCoefs} = \frac{\vec{4}(\text{dot}(\text{matD}[0], \text{matT}[2]), \text{dot}(\text{matD}[1], \text{matT}[2]), \text{dot}(\text{matD}[0], \text{matT}[0]), \text{dot}(\text{matD}[1], \text{matT}[1]))}{\text{dot}(\text{matD}[2], \text{matT}[2])}
        $$
        where $\text{matT}$ and $\text{matD}$ are derived from the Model-View-Projection matrix scaled by $\text{sphereRadius}$ [S1, unofficial].
    *   Pass `halfScreenSize` (viewport dimensions $\times 0.5$) to scale the projected AABB to screen space [S1, unofficial].

6.  **Rendering:**
    *   Enable `GL_PROGRAM_POINT_SIZE` [S1, unofficial].
    *   Bind the shader and set uniforms (projection matrix, block position, scale) [S2, unofficial].
    *   Draw using `glDrawArrays(GL_POINTS, 0, no_of_vertices)` [S1, unofficial] or `glDrawArrays(GL_POINTS, 0, voxels.size()/4)` for mipmap-based VBOs [S2, unofficial].

**Pseudocode:**

```python
# Initialization
cubes_x, cubes_y, cubes_z = 4, 4, 4
voxel_grid = [] # List of packed voxel data

# Step 1: Generate Voxel Data
for x in range(cubes_x):
    for y in range(cubes_y):
        for z in range(cubes_z):
            # Pack position and color into uint32_t

            pos_packed = (x & 0x7FF) | ((y & 0x3FF) << 11) | ((z & 0x7FF) << 21)
            color_packed = (r & 0x1F) | ((g & 0x3F) << 5) | ((b & 0x1F) << 11)
            voxel_grid.append((pos_packed, color_packed))

# Step 2: Upload to GPU (Conceptual)
vbo_id = create_buffer(voxel_grid)
vao_id = create_vao()
bind_attribute(vao_id, location=0, count=2, type=GL_INT, stride=8, offset=0)

# Step 3: Render Loop
for frame in frames:
    # Calculate camera distance and mipmap levels for each voxel (S2)
    # Determine scale = 0.1 * (1 << mipmap_level)
    
    # Set uniforms
    set_uniform("projection_matrix", camera.get_projection())
    set_uniform("scale", current_scale)
```

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of voxels, as each voxel generates one point primitive. The cost is dominated by the vertex shader and geometry shader (if used for sprite expansion) [S1, S2, unofficial].
*   **Memory Complexity:** $O(N)$ for storing the voxel data. The packed format (32-bit per voxel) is memory efficient [S1, S2, unofficial].
*   **Performance:** Highly dependent on the number of active voxels and the complexity of the fragment shader (e.g., quadric projection) [S1, unofficial]. Stochastic culling significantly improves performance for distant views by reducing the number of fragments processed [S1, unofficial].
*   **Strengths:** Low CPU overhead for geometry generation; simple data structure; effective for large, dense grids when combined with mipmapping and culling [S1, S2, unofficial].
*   **Limitations:** Transparency handling can be complex (requires back-to-front sorting or alpha blending); point sprites may alias or appear pixelated if not properly sized; performance degrades with very high-resolution voxels close to the camera due to fragment shader cost [S1, S2, unofficial].
*   **When to use:** Real-time visualization of large voxel datasets where approximate volume representation is sufficient, and CPU-side mesh generation is a bottleneck [S1, S2, unofficial].
*   **When not to use:** When precise geometric boundaries are required, or when transparency sorting is too expensive for the target frame rate [S1, S2, unofficial].

## Background
Voxel Point Sprite Rendering is an implementation of the broader splatting technique applied to voxel data. It leverages OpenGL's point sprite capabilities to render voxels as screen-aligned quads or circles. The specific implementations cited originate from open-source experiments in high-performance voxel rendering [S1, S2, unofficial]. The technique is part of the evolution of point-based rendering methods, adapting the concept of splatting from surface reconstruction to volumetric data visualization.
