# CPU Radix Sort for Face Centroids

Also called: Floating Point Radix Sort, LSD Radix Sort

## Overview
This method sorts face centroids on the CPU using an out-of-place algorithm that achieves linear time complexity at the expense of auxiliary memory [S1, unofficial]. It converts IEEE 754 floating-point numbers to 32-bit unsigned integers and performs a Least Significant Digit (LSD) radix sort using counting sort on 8-bit blocks [S1, unofficial]. It is chosen over general-purpose sorts or re-sorting-optimized algorithms like mergesort because viewing direction changes significantly alter the ordering, making frequent full re-sorting more efficient than adaptive re-sorting overhead [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: An array of $N$ face centroids, represented as IEEE 754 single-precision (32-bit) floating-point numbers [S1, unofficial].
- Output: The array sorted in ascending order, using an auxiliary array of size $N$ for intermediate storage [S1, unofficial].

**Data Structures:**
- `float* input`: Pointer to the array of floating-point centroids [S1, unofficial].
- `float* output`: Pointer to the auxiliary array of the same size [S1, unofficial].
- `unsigned int counts[256]`: A lookup table to store frequency counts for each 8-bit block [S1, unofficial].

**Transformation:**
Floating-point numbers must be converted to unsigned integers for integer-based radix sorting [S1, unofficial]. The transformation preserves the ordering of IEEE 754 floats (excluding NaN values) by treating the sign bit appropriately [S1, unofficial]. The conversion function is:
$$ \text{fint}(f) = f \oplus ((-(f \gg 31)) \mid 0x80000000) $$
Where $f$ is the bit-cast of the float to an unsigned 32-bit integer [S1, unofficial]. This maps negative floats to large unsigned integers and positive floats to small unsigned integers, maintaining correct numerical order [S1, unofficial].

**Algorithm Steps:**
The sort operates on four 8-bit blocks (bytes) of the 32-bit integer representation [S1, unofficial]. It performs five passes total: one initial pass to prepare counts, followed by four sorting passes [S1, unofficial].
1. **Initialize Counts:** For the current block (starting with bits 0-7), iterate through the input array [S1, unofficial]. For each element, extract the relevant 8-bit byte [S1, unofficial]. Increment the corresponding index in the `counts` array [S1, unofficial].
2. **Compute Prefix Sums:** Transform the `counts` array into prefix sums [S1, unofficial]. This determines the starting position for each value in the output array [S1, unofficial].
3. **Distribute:** Iterate through the input array again [S1, unofficial]. For each element, extract the byte, look up its position in the prefix sum array, place the element in the `output` array at that position, and increment the position counter [S1, unofficial].
4. **Swap Buffers:** If this is not the final pass (bits 24-31), swap the roles of `input` and `output` [S1, unofficial]. The `output` from this pass becomes the `input` for the next pass [S1, unofficial].
5. **Repeat:** Repeat steps 1-4 for the next byte (bits 8-15, then 16-23, then 24-31) [S1, unofficial].

**Pseudocode:**
```python
def cpu_radix_sort_face_centroids(input_array, n):
    # Convert floats to unsigned 32-bit integers via IEEE 754 bit-cast [G]
    int_array = [float_to_uint32(x) for x in input_array]
    output_array = [0] * n
    counts = [0] * 256

    # Pass 1: Count occurrences for all four 8-bit blocks in a single pass
    for i in range(n):
        val = int_array[i]
        for b in range(4):
            byte_val = (val >> (b * 8)) & 0xFF
            counts[byte_val] += 1

    # Pass 2: Sort bits 0-7 (LSD)
    _counting_sort_pass(int_array, output_array, counts, n, 0)
    int_array, output_array = output_array, int_array

    # Pass 3: Sort bits 8-15
    _counting_sort_pass(int_array, output_array, counts, n, 8)
    int_array, output_array = output_array, int_array

    # Pass 4: Sort bits 16-23
    _counting_sort_pass(int_array, output_array, counts, n, 16)
    int_array, output_array = output_array, int_array

    # Pass 5: Sort bits 24-31
    _counting_sort_pass(int_array, output_array, counts, n, 24)
    # Final result is in output_array
    return [uint32_to_float(x) for x in output_array]

def _counting_sort_pass(src, dst, counts, n, shift):
    # Reset counts
    for i in range(256): counts[i] = 0
    # Count
    for i in range(n):
        byte_val = (src[i] >> shift) & 0xFF
        counts[byte_val] += 1
    # Prefix sum
    total = 0
    for i in range(256):
        temp = counts[i]
        counts[i] = total
        total += temp
    # Distribute
    for i in range(n):
        byte_val = (src[i] >> shift) & 0xFF
        pos = counts[byte_val]
        dst[pos] = src[i]
        counts[byte_val] += 1

def float_to_uint32(f):
    # Standard IEEE 754 bit-cast [G]
    return int.from_bytes(f.to_bytes(4, 'little'), 'unsigned')

def uint32_to_float(u):
    # Standard IEEE 754 bit-cast [G]
    return float.from_bytes(u.to_bytes(4, 'little'), 'little')
```

**Parameters:**
- Block size: 8 bits [S1, unofficial].
- Bucket size: 256 entries [S1, unofficial].
- Passes: 4 sorting passes after the initial counting pass [S1, unofficial].

**Edge Cases and Pitfalls:**
- **NaN Values:** The transformation does not correctly order NaN values [S1, unofficial]. NaNs should be handled separately or filtered out before sorting [S1, unofficial].
- **Precision:** The method relies on the specific bit layout of IEEE 754 [S1, unofficial]. It is not portable to non-IEEE floating-point formats without modification [S1, unofficial].
- **Memory:** The algorithm is out-of-place, requiring auxiliary memory equal to the size of the input array [S1, unofficial].

## Subtopics

### LSD Block Sorting (Radix Sort)
This variant sorts bits 0-7, 8-15, 16-23, and 24-31 sequentially using counting sort [S1, unofficial]. It requires five passes through the array (one to count, four to sort) and establishes linear complexity [S1, unofficial]. It is chosen for its ability to sort upwards of 15 million faces per second on the tested hardware [S1, unofficial].

## Operating characteristics
- **Time Complexity:** Linear $O(N)$, where $N$ is the number of faces [S1, unofficial].
- **Memory Complexity:** $O(N)$ auxiliary space for the output array and $O(1)$ for the count array (size 256) [S1, unofficial].
- **Performance:** On the test hardware, this method sorts one million floating-point numbers in 64 ms [S1, unofficial]. This is significantly faster than shellsort (584 ms), heapsort (507 ms), and quicksort (281 ms) [S1, unofficial]. The implementation can sort upwards of 15 million faces per second [S1, unofficial].
- **Strengths:** High throughput for large datasets and predictable performance [S1, unofficial].
- **Limitations:** Requires auxiliary memory and is not suitable for in-place constraints [S1, unofficial].
- **When to use:** When GPU sorting is unavailable and high throughput is required for dynamic scenes where viewing direction changes frequently [S1, unofficial].
- **When not to use:** When memory is extremely constrained or when NaN handling is critical without pre-filtering [S1, unofficial].

## Background
This method originates from the "K-Buffer and Its Applications to Volume Rendering" thesis by Steve Callahan (2006) [S1, unofficial]. It was developed as a CPU fallback for volume splatting rendering, where face centroids need to be sorted for correct depth ordering [S1, unofficial]. The choice of LSD radix sort over other algorithms was based on extensive testing showing its superior performance for the specific workload of sorting face centroids in interactive volume rendering [S1, unofficial].
