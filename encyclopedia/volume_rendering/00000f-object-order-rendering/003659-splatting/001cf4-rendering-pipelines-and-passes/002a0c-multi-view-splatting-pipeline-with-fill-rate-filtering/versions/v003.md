# Multi-View Splatting Pipeline with Fill-Rate Filtering

Also called: Multi-View Splatting Pipeline

## Overview
This method generates multi-view 2D images from a 3D point cloud by projecting splatted primitives onto camera planes, then filters the resulting views based on pixel coverage density [S1, unofficial]. It distinguishes itself from standard splatting by integrating a post-projection fill-rate validation step to ensure only views with sufficient geometric sampling are retained for downstream tasks [S1, unofficial].

## How it works
**Inputs:**
- Point cloud data: Tuple $(\mathbf{xyz}, \mathbf{rgb}, \mathbf{label})$ loaded from a `.pt` file [S1, unofficial].
- Camera configuration: Trajectory parameters and intrinsic/extrinsic definitions [S1, unofficial].
- Parameters: `splat_radius` (default 2, representing a 5x5 disk expansion) and `min_fill_rate` (default 0.30) [S1, unofficial].

**Outputs:**
- For each valid view: Camera pose, color image (JPEG), label image (16-bit PNG), color-mapped label (PNG), and index map (`.npy`) [S1, unofficial].
- Intrinsic parameters from the first valid view saved to `intrinsic.txt` [S1, unofficial].

**Data Structures:**
- `CameraPose`: Contains `extrinsics` (torch.Tensor `[4,4]`), `intrinsics` (torch.Tensor `[4]`), `position` (tuple), `target` (tuple), and `pitch_deg` (float) [S1, unofficial].
- `SplattingRenderer`: Holds the point cloud and rendering configuration [S1, unofficial].

**Algorithm:**

1.  **Data Loading:** Load point cloud $(\mathbf{xyz}, \mathbf{rgb}, \mathbf{label})$ using `torch.load` [S1, unofficial].
2.  **Pose Generation:** Generate camera poses using `generate_trajectory(xyz, config, device)` [S1, unofficial].
3.  **Batching:** Extract intrinsics and extrinsics into batches via `poses_to_batch(poses)` [S1, unofficial].
4.  **Initialization:** Initialize `SplattingRenderer` with `cam_batch`, `splat_radius`, and `device` [S1, unofficial].
5.  **Cloud Upload:** Load point cloud into renderer via `renderer.load_pointcloud(xyz, rgb, label)` [S1, unofficial].
6.  **Rendering:** Render all views by calling `renderer.render_all(intr_batch, extr_batch, width, height)`. This returns `color_list`, `label_list`, and `index_list` [S1, unofficial].
    -   The rendering process projects points to screen space $(u,v)$ and computes depths.
    -   To handle visibility and occlusion deterministically on CUDA, points are expanded and sorted by pixel index and depth. The first entry per pixel (minimum depth) is kept [S1, unofficial].
    -   Canvases are written without duplicate indices to ensure deterministic output [S1, unofficial].
7.  **Fill Rate Calculation:** Compute fill rate for each view $i$ as the mean of valid pixels:
    $$ \text{fill\_rate}_i = \frac{1}{W \times H} \sum_{x,y} \mathbb{I}(\text{index}_i[x,y] \ge 0) $$
    where $\mathbb{I}$ is the indicator function and $\text{index}_i$ is the index map for view $i$ [S1, unofficial].
8.  **Filtering:** Identify kept indices:
    $$ \text{kept\_indices} = \{ i \mid \text{fill\_rate}_i \ge \text{min\_fill\_rate} \} $$
    [S1, unofficial].
9.  **Saving:**
    -   If `kept_indices` is empty, print a warning and skip saving [S1, unofficial].
    -   Save intrinsics from the first kept view to `intrinsic.txt` [S1, unofficial].
    -   For each $i \in \text{kept\_indices}$, save pose, color (JPEG), label (16-bit PNG), color-mapped label (PNG), and index map (`.npy`) [S1, unofficial].

## Operating characteristics
- **Time Complexity:** Dominated by the projection and sorting of points for each view. The sorting step ensures $O(N \log N)$ per view where $N$ is the number of points, though CUDA optimizations may reduce constant factors [S1, unofficial].
- **Memory Complexity:** Requires storing the point cloud and intermediate buffers for each camera batch. Memory usage scales with the number of points and the batch size of cameras processed [S1, unofficial].
- **Strengths:** Deterministic output due to explicit depth sorting and duplicate index handling; effective filtering of sparse or occluded views [S1, unofficial].
- **Limitations:** Computationally expensive for large point clouds due to per-pixel sorting; dependent on GPU memory for batch processing [S1, unofficial].
- **When to use:** When generating training data for multi-view learning tasks where view quality (coverage) is critical, such as in the DALA-CitywallV3 dataset pipeline [S1, unofficial].

## Background
This pipeline was developed for the DALA-CitywallV3 dataset to generate high-quality multi-view splatting data [S1, unofficial]. It integrates standard splatting techniques with a specific fill-rate filtering mechanism to ensure data consistency [S1, unofficial].
