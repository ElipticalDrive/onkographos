# GPU Implementation Pipeline
Also called: Single-pass GPU Raycasting, Volumetric Raycasting

## Overview
A GPU-accelerated rendering technique that traces rays from the camera through each pixel into a 3D volume to compute color and opacity, implemented in a single pass using fragment shaders [S2, unofficial].

## How it works
**Inputs:**
- 3D volume texture (scalar field, typically `GL_RED` format) [S2, unofficial].
- Camera parameters: View Matrix, Model-View-Projection (MVP) Matrix, Ray Origin, Ray Direction (derived from screen coordinates) [S2, unofficial].
- Rendering parameters: Step length, bounding box (`top`/`bottom`), background color, gamma, transfer function coefficients [S2, unofficial].
- Optional: Jitter texture for anti-aliasing [S2, unofficial].

**Outputs:**
- Final color buffer (RGBA) [S2, unofficial].

**Data Structures:**
- **Volume Texture:** 3D texture object storing scalar intensity values. In multi-resolution variants, this may be a reduced structure (e.g., $256 \times 256 \times 128$ for a $512^3$ dataset) [S1].
- **Bounding Box (AABB):** Defined by `top` and `bottom` vectors in texture coordinates or world space [S2, unofficial].
- **Ray Structure:** Contains `origin` (vec3) and `direction` (vec3) [G].

**Initialization Steps:**
1. Create OpenGL state and volume data structure [S2, unofficial].
2. Compute the view matrix by translating along the Z-axis: $T_z = -4.0 \cdot \exp(\frac{distExp}{600.0})$ [S2, unofficial].
3. Compute the MVP matrix using perspective projection with FOV ($m_{fov}$), aspect ratio ($\frac{scaled\_width}{scaled\_height}$), near plane $0.1$, and far plane $100.0$ [S2, unofficial].
4. Compute ray origin in world space by inverting the view matrix and transforming $(0,0,0)$ [S2, unofficial].
5. Bind shader program and set uniforms: `ViewMatrix`, `ModelViewProjectionMatrix`, `aspect_ratio`, `focal_length`, `viewport_size`, `ray_origin`, `top`, `bottom`, `background_colour`, `step_length`, `gamma`, `volume` (texture unit 0), `jitter` (texture unit 1) [S2, unofficial].
6. Clear color buffer with `background_colour` [S2, unofficial].

**Pseudocode (Fragment Shader Core):**
```python
def raycast(frag_coord, viewport_size, aspect_ratio, focal_length, view_matrix, ray_origin, top, bottom, step_length, gamma, background_colour, volume_tex, jitter_tex):
    # 1. Ray generation
    ray_dir_xy = 2.0 * (frag_coord / viewport_size) - 1.0
    ray_dir_xy.x *= aspect_ratio
    ray_dir = vec3(ray_dir_xy.x, ray_dir_xy.y, -focal_length)
    ray_direction = (view_matrix @ vec4(ray_dir, 0.0)).xyz

    # 2. Ray-box intersection (slab method)
    direction_inv = 1.0 / ray_direction
    t_top = direction_inv * (top - ray_origin)
    t_bottom = direction_inv * (bottom - ray_origin)
    t_min = min(t_top, t_bottom)
    t_max = max(t_top, t_bottom)
    t0 = max(0.0, max(t_min.x, t_min.y))
    t1 = min(t_max.x, t_max.y)

    # 3. Ray marching setup
    ray_start = (ray_origin + ray_direction * t0 - bottom) / (top - bottom)
    ray_stop = (ray_origin + ray_direction * t1 - bottom) / (top - bottom)
    ray_vec = ray_stop - ray_start
    ray_length = length(ray_vec)
    step_vector = step_length * ray_vec / ray_length

    # Random jitter
    ray_start += step_vector * jitter_tex[frag_coord / viewport_size].r
    position = ray_start
    colour = vec4(0.0)

    # 4. Marching loop (front-to-back alpha blending)
    while ray_length > 0 and colour.a < 1.0:
        intensity = volume_tex[position].r
        # Transfer function
        alpha_c = (exp(intensity) - 1.0) / (exp(1.0) - 1.0)
        c_rgb = intensity * vec3(1.0) + (1.0 - intensity) * vec3(0.0)
        c = vec4(c_rgb, alpha_c)

        # Composite
        colour.rgb = c.a * c.rgb + (1.0 - c.a) * colour.a * colour.rgb
        colour.a = c.a + (1.0 - c.a) * colour.a

        ray_length -= step_length
        position += step_vector

    # 5. Final compositing
    colour.rgb = colour.a * colour.rgb + (1.0 - colour.a) * pow(background_colour, vec3(gamma)).rgb
    colour.a = 1.0
    output = vec4(pow(colour.rgb, vec3(1.0 / gamma)), colour.a)
    return output
```

**Parameters:**
- `step_length`: Controls sampling density. In multi-resolution variants, piecewise segment lengths of 8-16 voxels provide significant performance gains [S1].
- `gamma`: Gamma correction value (e.g., 2.2) [S2, unofficial].
- `focal_length`: Determines field of view [S2, unofficial].
- `distExp`: Exponential distance exponent for camera translation [S2, unofficial].

**Edge Cases and Pitfalls:**
- **Empty Blocks:** In multi-resolution structures, if a sample point falls in an empty block, the ray must be advanced to the next non-empty block to avoid losing occlusion from neighboring blocks [S1].
- **Interpolation Artifacts:** Flat blocking multi-resolution data management can cause interpolation problems if blocks are not handled correctly [S1].
- **Precision:** Ray-box intersection precision affects entry/exit points, especially for grazing angles [G].

## Subtopics

### [Volume Rendering with 3D Textures and Ray Marching](2584-volume-rendering-with-3d-textures-and-ray-marching.md)
This method performs object-order volume rendering by ray marching through a 3D texture stored in GPU memory, applying a transfer function to map scalar values to color and opacity, and compositing the result front-to-back. It solves the problem of visualizing volumetric data directly on the GPU without generating intermediate polygonal meshes. It differs from isosurface extraction (e.g., [Marching Cubes](53-marching-cubes.md)) by preserving internal volume information, and from splatting ([Splatting](10-splatting.md)) by avoiding sorting and blending overheads for dense volumes, though it is computationally heavier per pixel than texture-based splatting [G].

## Operating characteristics
- **Time Complexity:** Linear with respect to the number of samples per ray and the number of pixels [G]. Performance is heavily influenced by the step length and volume resolution [G].
- **Memory Complexity:** Proportional to the size of the 3D volume texture [S2, unofficial]. Multi-resolution structures can reduce storage by factors of 8 or more (e.g., $256^3$ for a $512^3$ dataset) [S1].
- **Measured Performance:** On an Nvidia GeForce 8800 Ultra with 768 MB graphics texture memory, for a $512^3$ volume with 8.9:1 data reduction and SVR size $256^3$: Global light integration (A) takes 284-552 ms, first order scattering incremental refinements (B) take 62-233 ms, and high frame rates (15-22 fps) are reached after light updates [S1].
- **Strengths:** Single-pass implementation allows for real-time interaction [S2, unofficial]. Simple to implement on modern GPUs [G]. Preserves full volumetric information [S2, unofficial].
- **Limitations:** Computationally intensive per pixel compared to splatting [G]. Performance degrades with large step sizes or high-resolution volumes without multi-resolution acceleration [S1]. Artifacts can occur with improper handling of empty blocks in multi-resolution structures [S1].
- **When to use:** Real-time visualization of dense volumetric data where internal structure is important [S2, unofficial].
- **When not to use:** When extreme performance is required for very large volumes without multi-resolution support, or when surface-only visualization is sufficient (use Marching Cubes) [G].

## Background
The technique is based on GPU-accelerated single-pass volumetric raycasting, implemented in GLSL and C++ with the Qt framework [S2, unofficial]. It aims to provide a basic skeleton for a visualiser that can be easily extended with a feature-rich GUI [S2, unofficial]. The approach of using multi-resolution data structures and piecewise integration for global light propagation was introduced in "Interactive Global Light Propagation in Direct Volume Rendering using Local Piecewise Integration" [S1]. This work demonstrated that reducing the volume size via flat blocking multi-resolution data management allows for significant performance improvements without significant loss in visual quality [S1].
