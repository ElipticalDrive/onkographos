# Time-Sliced Pipelined Architecture

Also called: Multi-core time-sliced pipeline, Time-slicing

## Overview
The Time-Sliced Pipelined Architecture is a hardware design methodology for volume rendering that achieves real-time performance by time-slicing functional blocks to allow simultaneous processing of multiple tasks [S1, unofficial]. It solves the bottleneck of sequential pipeline execution by overlapping stages, enabling continuous hardware-software communication and interactive user interfaces [S1, unofficial]. It distinguishes itself from standard pipelining by emphasizing component reusability and sub-core replication, where independent vertical cores are configured or replicated based on specific processing requirements rather than fixed linear stages [S1, unofficial].

## How it works
The architecture decomposes the rendering process into independent, reusable functional blocks (sub-cores) that are time-sliced to execute concurrently [S1, unofficial].

**Inputs and Outputs:**
*   **Input:** Raw voxel data, classification parameters, shading models, and transformation matrices.
*   **Output:** Final rendered pixel values.

**Data Structures:**
*   **Context RAM:** Shared memory used to store intermediate results (e.g., dot products) for several clock cycles, allowing different components to access the same data without recomputation [S1, unofficial].
*   **Normal Mode Registers:** Hardware registers that define the operational mode of the components [S1, unofficial].
*   **Sub-cores:** Independent hardware blocks (multipliers, adders, inner product processors) that can be replicated or configured [S1, unofficial].

**Steps:**
1.  **Decomposition:** Divide the rendering pipeline into functional blocks: classifier, gradient calculator, shearing-warping block, shader, and composer [S1, unofficial].
2.  **Component Implementation:** Implement these blocks as independent reusable components or sub-cores. These sub-cores are built from basic functional blocks such as multipliers, adders, or inner product processors [S1, unofficial].
3.  **Configuration/Replication:** Based on the type of processing required by the calling module, the embedded sub-core is configured or replicated to execute a specific operation [S1, unofficial]. This allows a variety of functions to be executed using a single component type, resulting in efficient systems [S1, unofficial].
4.  **Time-Slicing Execution:** Use time-slicing to overlap execution stages. This allows simultaneous processing of several tasks within the pipeline [S1, unofficial].
5.  **Data Sharing:** Utilize a context address snooping mechanism and Context RAM to allow components to share calculated data (e.g., a dot product computed once is stored and called up by another component) [S1, unofficial].

**Pseudocode:**
```python
# Conceptual representation of the time-sliced multi-core architecture
# Note: This is a logical description of hardware behavior, not executable software.

class SubCore:
    def __init__(self, type):
        self.type = type # e.g., 'multiplier', 'adder', 'inner_product'
        self.configured = False

    def configure(self, operation):
        """Configure the sub-core for a specific operation."""
        self.operation = operation
        self.configured = True

    def execute(self, input_data):
        """Execute the configured operation."""
        if not self.configured:
            raise Error("Sub-core not configured")
        # Hardware-specific execution logic
        return perform_hardware_operation(self.type, self.operation, input_data)

class TimeSlicedPipeline:
    def __init__(self):
        # Define functional blocks
        self.blocks = {
            'classifier': SubCore('logic'),
            'gradient': SubCore('inner_product'),
            'shader': SubCore('multiplier'),
            'composer': SubCore('adder')
        }
        self.context_ram = {} # Shared storage for intermediate values
        self.normal_mode_registers = {}

    def process_voxel(self, voxel_data, current_cycle):
        """
        Process a voxel through the time-sliced pipeline.
        Multiple tasks are processed simultaneously via time-slicing.
        """
        # Step 1: Gradient Calculation
        # The gradient calculator computes dot products.
        # Result is stored in Context RAM for reuse.
        dot_product = self.blocks['gradient'].execute(voxel_data.gradient)
        self.context_ram['dot_product'] = dot_product
        
        # Step 2: Shading (Time-sliced overlap)
        # The shader accesses the dot product from Context RAM
        # instead of recomputing it.
        shaded_color = self.blocks['shader'].execute({
            'voxel': voxel_data,
            'dot_product': self.context_ram['dot_product']
        })
        
        # Step 3: Classification and Compositing
        classified = self.blocks['classifier'].execute(voxel_data)
        final_pixel = self.blocks['composer'].execute({
            'color': shaded_color,
            'opacity': classified.opacity
        })
        
        return final_pixel

    def configure_pipeline(self, requirements):
        """
        Replicate or configure sub-cores based on processing requirements.
        """
        for req in requirements:
            if req.type == 'high_throughput_gradient':
                # Replicate gradient sub-core
                self.blocks['gradient'] = SubCore('inner_product')
                self.blocks['gradient'].configure('dot_product')
```

**Parameters:**
*   **Clock Frequency:** Not explicitly defined for the general architecture, but specific implementations (vg500) use 133 MHz [S2, unofficial].
*   **Context RAM Size:** Not given in the sources.

**Edge Cases and Pitfalls:**
*   **Data Hazards:** Components must have a common interface provided by Context RAM and normal mode registers to ensure data consistency when sharing information [S1, unofficial].
*   **Complexity:** The hierarchical design and component reusability simplify layout but require careful management of sub-core replication and configuration [S1, unofficial].

## Subtopics

### Vg500 Parallel Pipeline Architecture
The vg500 chip architecture uses four parallel rendering pipelines to achieve real-time rendering rates by processing adjacent voxel values in the x-direction [S2, unofficial]. It is an ASIC with approximately 3.2 million transistors and 2 Mbits of on-chip SRAM, fabricated in 0.35 technology [S2, unofficial]. Each pipeline operates at 133 MHz and can accept a new voxel every cycle [S2, unofficial]. Pipelines are connected to neighbors by shift registers in each major unit, providing values to neighbors in the same cycle [S2, unofficial]. The shift registers of the rightmost pipeline recirculate values needed in the next cycle and send them to the leftmost pipeline [S2, unofficial]. Off-chip Voxel Memory supplies data to all pipelines, and they write pixel values to off-chip Pixel Memory [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** The architecture enables real-time rendering by overlapping stages. For example, the vg500 implementation processes approximately 532 million voxels per second (4 pipelines * 133 MHz) [S2, unofficial].
*   **Memory Complexity:** Requires Context RAM for shared intermediate data and off-chip Voxel/Pixel Memory [S1, unofficial][S2, unofficial]. The vg500 uses 2 Mbits on-chip SRAM and external SDRAM (e.g., 128 MB for 64-megabit modules) [S2, unofficial].
*   **Strengths:** Enables real-time rendering and continuous hardware-software communication; simplifies layout through component reusability; allows interactive user interfaces [S1, unofficial].
*   **Limitations:** Complex hardware design due to multi-core structure and time-slicing logic; requires careful management of shared resources (Context RAM) [S1, unofficial].
*   **When to use:** When real-time performance is critical and hardware resources allow for complex, replicated sub-cores [S1, unofficial].
*   **When not to use:** When software flexibility is prioritized over hardware speed, or when memory bandwidth is severely constrained [G].

## Background
The Time-Sliced Pipelined Architecture was developed as part of the Shear-warp factorization volume rendering system research, specifically detailed in theses and reports related to the VolumePro system [S1, unofficial][S2, unofficial]. It was designed to overcome the limitations of sequential rendering pipelines by leveraging hardware parallelism and time-slicing to achieve real-time frame rates [S1, unofficial]. The vg500 chip, a key implementation of this architecture, was developed by MERL and integrated into the VolumePro real-time ray-casting system [S2, unofficial].
