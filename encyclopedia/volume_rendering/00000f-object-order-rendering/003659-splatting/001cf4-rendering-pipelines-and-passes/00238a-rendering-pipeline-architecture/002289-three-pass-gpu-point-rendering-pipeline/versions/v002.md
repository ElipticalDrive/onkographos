# Three-Pass GPU Point Rendering Pipeline
Also called: Hardware Accelerated Point Splatting Pipeline

## Overview
The Three-Pass GPU Point Rendering Pipeline is a method for rendering point-based geometry by decomposing the splatting process into three distinct rendering stages to handle depth occlusion and attribute accumulation correctly [S1, unofficial]. It solves the problem of correctly blending overlapping splats with varying depths on modern graphics hardware, which lacks native support for arbitrary-order alpha blending [S1, unofficial]. It differs from the [Single-Pass Splat Rendering Pipeline](1254-single-pass-splat-rendering-pipeline.md) by explicitly separating the depth culling, color accumulation, and normalization steps, and from the [Splat Attributes Pass](1066-splat-attributes-pass.md) by handling the full rendering pipeline including final color normalization [S1, unofficial].

## How it works
**Inputs:** A set of 3D points with attributes (position, radius, color) and camera parameters.
**Outputs:** A final color image.
**Rendering Primitive:** OpenGL points are used instead of quads or triangles [S1, unofficial].

**Data Structures:**
1.  **Depth Buffer:** Stores depth values for occlusion testing.
2.  **Color Framebuffer:** Accumulates weighted color contributions.
3.  **Weight Framebuffer:** Accumulates filter weights (optional, or derived from color blending if using specific blend modes, but typically requires a separate pass or buffer for normalization as per the description) [S1, unofficial]. *Note: The source [S1, unofficial] states normalization is done by dividing through accumulated filter weights, implying a weight buffer is available or computed.*

**Steps:**

1.  **Pass 1: Depth Offset Rendering**
    Render a depth image of the scene. The depth values are slightly offset along the viewing rays [S1, unofficial]. This pass establishes the occlusion boundaries for the splats.

2.  **Pass 2: Accumulation**
    Draw the splats using only depth tests (no updates to the depth buffer itself, or updates are handled such that only visible splats contribute) with color blending enabled [S1, unofficial].
    *   The fragment shader computes the splat contribution based on the distance from the splat center.
    *   Color values are accumulated in the framebuffer, effectively computing the weighted sum $\sum C_i w_i$ [S1, unofficial].
    *   The weight values $w_i$ must also be accumulated. This is typically done by rendering the weights into a separate floating-point framebuffer or using a specific blend function if the hardware supports it, though [S1, unofficial] implies a separate accumulation of weights for normalization.

3.  **Pass 3: Normalization**
    Normalize the accumulated color values by dividing them through the accumulated filter weights [S1, unofficial].
    $$ C_{final}(x,y) = \frac{\sum C_i w_i}{\sum w_i} $$
    This pass reads the accumulated color and weight buffers and performs the division to produce the final image.

**Pseudocode:**

```python
def three_pass_pipeline(points, camera, width, height):
    # Initialize buffers
    depth_buffer = create_buffer(width, height, dtype=float)
    color_buffer = create_buffer(width, height, dtype=float3, init=0)
    weight_buffer = create_buffer(width, height, dtype=float, init=0)

    # Pass 1: Render depth image with offset
    # The offset is along the viewing ray to ensure splats are not occluded by themselves
    render_depth_pass(points, camera, depth_buffer, offset=True)

    # Pass 2: Accumulate color and weights
    # Use depth test to discard fragments behind already rendered splats
    # Enable blending to accumulate
    for point in points:
        # Project point to screen
        screen_pos = project(point, camera)
        radius = get_radius(point, camera)
        
        # Determine splat coverage
        coverage = get_splat_coverage(screen_pos, radius)
        
        # For each fragment in coverage:
        for frag in coverage:
            # Depth test against depth_buffer
            if frag.depth < depth_buffer[frag.x, frag.y]:
                # Compute weight based on distance from center
                w = compute_weight(frag, screen_pos, radius)
                
                # Accumulate color and weight
                # Note: Hardware blending might handle this, but explicit accumulation is safer
                color_buffer[frag.x, frag.y] += point.color * w
                weight_buffer[frag.x, frag.y] += w
                
                # Update depth buffer to prevent further writes behind this splat
                depth_buffer[frag.x, frag.y] = frag.depth

    # Pass 3: Normalize
    final_image = create_buffer(width, height, dtype=float3)
    for y in range(height):
        for x in range(width):
            w = weight_buffer[x, y]
            if w > epsilon:
                final_image[x, y] = color_buffer[x, y] / w
            else:
                final_image[x, y] = 0.0
                
    return final_image
```

**Edge Cases and Pitfalls:**
*   **Numerical Ill-conditioning:** Computing the variance matrix for the resampling filter may require inversion of the projective mapping, which can be numerically ill-conditioned if the splat degenerates into a line segment [S1, unofficial].
*   **Depth Offset:** The offset in Pass 1 must be carefully chosen to avoid z-fighting or incorrect occlusion [S1, unofficial].

## Subtopics

### Standard Point Splatting Assembly
This variant initializes canvases for depth, color, label, and index. It sorts points by depth and iterates in ascending order, writing color to the pixel if the point's depth is less than the current depth at that pixel. After processing, a written mask is created, and unwritten pixels are set to default values [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N \cdot R^2)$ where $N$ is the number of points and $R$ is the splat radius in pixels, due to the rasterization of each splat. The normalization pass is $O(W \cdot H)$.
*   **Memory Complexity:** $O(W \cdot H)$ for the framebuffers (depth, color, weight).
*   **Strengths:** Correctly handles depth occlusion and alpha blending for point sprites. Hardware accelerated.
*   **Limitations:** Requires multiple passes. Performance depends on the number of overlapping splats. Numerical stability issues with projective mapping inversion [S1, unofficial].
*   **When to use:** When correct depth ordering and blending of point sprites is required on GPU.
*   **When not to use:** When performance is critical and approximate blending is acceptable (consider single-pass).

## Background
The method is based on the approximation of projective mapping using vertex and fragment programs of modern GPUs [S1, unofficial]. It follows previous methods for hardware-accelerated point splatting [S1, unofficial]. The specific implementation described uses OpenGL points and a three-pass approach for depth offset, accumulation, and normalization [S1, unofficial].
