# Radix Sort for Splat Depth

Also called: 16-bit Radix Sort for Splatting, Depth Sorting via Radix Sort, Tsplat depth sort

## Overview
Radix Sort for Splat Depth sorts projected 3D Gaussian splats by their depth in camera space to enable correct front-to-back alpha compositing during rasterization [S1, unofficial]. It differs from comparison-based sorts by leveraging the monotonic property of IEEE 754 float bit patterns when reinterpreted as unsigned integers, achieving $O(n)$ time complexity with small constants [S1, unofficial]. This method serves as the global depth ordering prerequisite for tile-based sorting variants like [Tile Binning for Splatting](1214-tile-binning-for-splatting.md) and [Gaussian Sorting](2845-gaussian-sorting.md) [S1, unofficial].

## How it works
**Inputs:**
- `projected`: Array of $N$ splat structures, each containing at least a `depth` field (f32).
- `scratch`: Buffer for intermediate storage and histogram counts.

**Outputs:**
- `projected`: The same array, reordered such that splats are sorted by `depth` in ascending order (front-to-back).

**Data Structures:**
- `counts_lo`: Array of 65,536 `u32` integers, initialized to zero.
- `counts_hi`: Array of 65,536 `u32` integers, initialized to zero.
- `offsets`: Array of 65,536 `u32` integers, used for prefix sums.
- `aux`: Temporary array of $N$ splat structures, same layout as `projected`.

**Steps:**
1. **Base Case:** If $N \le 1$, return immediately.
2. **Histogram Initialization:** Zero out `counts_lo` and `counts_hi`.
3. **Bit Extraction and Counting:** For each splat $i$ in `projected`:
   - Let $k$ be the bit pattern of `projected[i].depth` interpreted as a `u32`.
   - Increment `counts_lo[k & 0xFFFF]`.
   - Increment `counts_hi[(k >> 16) & 0xFFFF]`.
4. **Pass 1 (Low 16 bits):**
   - Compute prefix sums of `counts_lo` into `offsets`. `offsets[x]` stores the starting index for bucket $x$.
   - Scatter splats from `projected` to `aux` based on the low 16 bits of their depth. For splat $i$:
     - Let $k$ be the bit pattern of `projected[i].depth` as `u32`.
     - Let $idx = offsets[k \& 0xFFFF]$.
     - Set `aux[idx] = projected[i]`.
     - Increment `offsets[k & 0xFFFF]`.

**Pseudocode:**

```python
def sort_splat_depth(projected: list[Splat], scratch: ScratchBuffers) -> None:
    N = len(projected)
    if N <= 1:
        return

    counts_lo = [0] * 65536
    counts_hi = [0] * 65536
    offsets = [0] * 65536
    aux = [None] * N

    # Step 1: Histogram low 16 bits
    for i in range(N):
        k = float_to_bits(projected[i].depth)
        counts_lo[k & 0xFFFF] += 1

    # Step 2: Prefix sum for low bits
    offsets[0] = 0
    for i in range(1, 65536):
        offsets[i] = offsets[i-1] + counts_lo[i-1]

    # Step 3: Scatter by low bits to aux
    for i in range(N):
        k = float_to_bits(projected[i].depth)
        idx = offsets[k & 0xFFFF]
        aux[idx] = projected[i]
        offsets[k & 0xFFFF] += 1

    # Step 4: Histogram high 16 bits from aux
    # Reset counts_hi if not already zeroed (source [S1, unofficial] initializes them at start)
    # We must recount because the order in aux is different
    for i in range(65536):
        counts_hi[i] = 0
    
    for i in range(N):
        k = float_to_bits(aux[i].depth)
        counts_hi[(k >> 16) & 0xFFFF] += 1

    # Step 5: Prefix sum for high bits
    offsets[0] = 0
    for i in range(1, 65536):
        offsets[i] = offsets[i-1] + counts_hi[i-1]

    # Step 6: Scatter by high bits back to projected
    for i in range(N):
        k = float_to_bits(aux[i].depth)
        idx = offsets[(k >> 16) & 0xFFFF]
        projected[idx] = aux[i]
        offsets[(k >> 16) & 0xFFFF] += 1

def float_to_bits(f: float) -> int:
    # Reinterpret f32 bits as u32
    # In Python, struct module or numpy can do this. 
    # For pseudocode clarity:
    import struct
    return struct.unpack('I', struct.pack('f', f))[0]
```

**Parameters:**
- **Parallel Threshold:** If $N < 50,000$ or no thread pool is available, use the sequential radix sort described above. Otherwise, use a parallel unstable sort (e.g., `par_sort_unstable_by_key`) on the depth bits [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Negative Depths:** The method relies on positive float bit patterns preserving order. If splats have negative depths (behind the camera in some projections), the bit pattern interpretation as `u32` will not preserve numerical order. Ensure depths are positive or handled via a bias/offset before bit extraction [S1, unofficial].
- **Precision:** Reinterpreting `f32` bits to `u32` is exact. No precision loss occurs in the bit extraction.
- **Stability:** The sequential radix sort described is stable if the scatter uses the offsets correctly (incrementing after placement). This is crucial if splats with identical depths need to maintain their original relative order for subsequent attribute interpolation [S1, unofficial].

## Subtopics

### [Gaussian Sorting](2845-gaussian-sorting.md)
Gaussian Sorting is the process of ordering 3D Gaussian primitives by their depth in camera space to enable correct front-to-back alpha compositing during splatting. It transforms the spatial positions of Gaussians into the view frustum and sorts them based on their z-coordinate. Unlike general-purpose sorting, this method is tightly coupled with the rasterization pipeline, often serving as a prerequisite for tile-based sorting. It differs from [Fast Splat Sorting](2953-fast-splat-sorting.md) by focusing on the initial global depth sort rather than optimized tile-local reordering.

### [Fast Splat Sorting](2953-fast-splat-sorting.md)
Fast Splat Sorting is an optimization for the rendering pipeline of 3D Gaussian Splatting (3DGS) that replaces the original combined 48-bit radix sort of tile IDs and depth with two sequential, smaller sorts: a 32-bit depth sort of visible splats followed by a 16-bit tile ID sort of generated fragments. It solves the performance bottleneck of sorting large numbers of duplicate splat fragments by leveraging the fact that the majority of splats contribute to the rendered image across multiple tiles, allowing the expensive depth sorting to be performed on the smaller set of unique visible splats rather than the larger set of tile-wise duplicates. This approach is significantly faster than the original 3DGS method, which sorts all fragments together in a single 48-bit pass.

## Operating characteristics
- **Time Complexity:** $O(n)$ for the radix sort, where $n$ is the number of splats. The constant factor is small due to the fixed 2-pass structure [S1, unofficial].
- **Memory Complexity:** $O(n)$ for the auxiliary array `aux` and $O(1)$ for the histogram arrays (fixed size 65,536) [S1, unofficial].
- **Performance:** Consistently 2 times faster than comparison-based sorts for ~100k–200k elements [S1, unofficial].
- **Scalability:** Scales linearly with the number of splats. Parallelization is recommended for $N \ge 50,000$ [S1, unofficial].
- **Strengths:** Deterministic performance, no worst-case degradation like quicksort, hardware-friendly memory access patterns.
- **Limitations:** Requires positive depths for correct bit-pattern ordering. Not suitable for negative depth values without preprocessing.

## Background
Radix Sort for Splat Depth is used in terminal-based Gaussian Splatting renderers like Tsplat to efficiently sort splats for compositing [S1, unofficial]. It was developed to address the performance bottleneck of sorting large numbers of splats in real-time rendering pipelines. The method leverages the properties of IEEE 754 floating-point representation to avoid expensive comparison operations.
