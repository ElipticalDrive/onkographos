# Splat Depth Pass

Also called: Front-Face Depth Pass, Visibility Pass

## Overview
The Splat Depth Pass computes the front-facing depth of each splat fragment to populate the depth buffer, ensuring correct visibility ordering for subsequent compositing. It differs from the parent [Splat Attributes Pass](1066-splat-attributes-pass.md) by focusing exclusively on geometric occlusion rather than color or opacity accumulation, and from [Radix Sort for Splat Depth](1207-radix-sort-for-splat-depth.md) by performing depth calculation per-fragment in the shader rather than sorting primitives in a pre-pass.

## How it works
**Inputs and Outputs:**
- Input: Fragment position in screen space (`gl_FragCoord.z`), splat radius (`i.radius`), and a small epsilon value (`epsilon`).
- Output: Updated depth buffer value (`gl_FragDepth`).

**Data Structures:**
- The splat attributes are passed via vertex/point shader varying `i`, containing at least:
  - `radius`: float, the radius of the splat in screen space.

**Steps:**
1.  **Local Coordinate Calculation:** Compute the vector from the center of the point sprite in screen space.
    $$ \text{from\_center\_pt\_spc} = \text{gl\_PointCoord} - \begin{bmatrix} 0.5 \\ 0.5 \end{bmatrix} $$
2.  **Circular Boundary Check:** Calculate the squared magnitude of the offset. If the fragment lies outside the unit circle (radius 0.5), discard it.
    $$ \text{mag\_sq} = \|\text{from\_center\_pt\_spc}\|^2 $$
    $$ \text{if } \text{mag\_sq} > 0.25 \text{ then discard} $$
3.  **World-Space Offset:** Scale the local offset by the splat's screen-space radius to determine the offset in world space (assuming linear depth mapping for the offset calculation).
    $$ \text{from\_center\_wld\_spc} = \text{from\_center\_pt\_spc} \times 2 \times i.\text{radius} $$
4.  **Depth Offset Calculation:** Compute the z-offset from the front surface of the sphere to the current fragment position on the sphere's surface. This uses the Pythagorean theorem on the splat's radius.
    $$ \text{depth\_offset} = \sqrt{i.\text{radius}^2 - \text{dot}(\text{from\_center\_wld\_spc}, \text{from\_center\_wld\_spc})} $$
5.  **Final Depth Computation:** Shift the linear depth of the splat's center (derived from `gl_FragCoord.z`) by the negative depth offset (moving towards the camera) and add an epsilon bias.
    $$ \text{depth} = \text{depthSample}(\text{linearDepth}(\text{gl\_FragCoord}.z) - \text{depth\_offset} + \epsilon) $$
    Where `depthSample` converts the linear depth back to the clip-space depth required by the framebuffer, and `linearDepth` converts clip-space Z to linear view-space Z.
6.  **Write Depth:** Write the computed depth to the fragment shader output.
    $$ \text{gl\_FragDepth} = \text{depth} $$

**Parameters:**
- `epsilon`: A small bias added to prevent z-fighting and ensure correct blending of overlapping splats. Typical value: $0.25$ (scaled by an `_epsilonMultiplier` if applicable) [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Z-fighting/Gaps:** Without the epsilon shift, splats at similar depths may fail depth tests incorrectly, causing gaps or flickering [S1, unofficial].
- **Precision:** The calculation assumes `gl_FragCoord.z` can be accurately converted to linear depth. Standard OpenGL depth buffer precision must be considered [S1, unofficial].

**Pseudocode:**
```python
# Fragment Shader Logic for Splat Depth Pass
# Inputs: gl_FragCoord (vec4), i.radius (float), epsilon (float)
# Outputs: gl_FragDepth (float)

def splat_depth_pass(i_radius, epsilon):
    # 1. Calculate distance from center in point sprite coordinates
    from_center_pt_spc = vec2(gl_FragCoord.x, gl_FragCoord.y) - vec2(0.5, 0.5)
    
    # Note: gl_PointCoord is typically normalized [0,1]. 
    # If using standard point sprites, gl_PointCoord is available.
    # Assuming gl_PointCoord is provided by the rasterizer for point sprites.
    from_center_pt_spc = gl_PointCoord - vec2(0.5, 0.5)
    
    # 2. Discard if outside circle
    mag_sq = dot(from_center_pt_spc, from_center_pt_spc)
    if mag_sq > 0.25:
        discard()
        
    # 3. Calculate world-space offset (scaled by radius)
    # The factor 2 scales the [0,1] offset to [-1,1] range relative to diameter
    from_center_wld_spc = from_center_pt_spc * 2.0 * i_radius
    
    # 4. Calculate depth offset (z-distance from front of sphere to current fragment)
    depth_offset = sqrt(i_radius * i_radius - dot(from_center_wld_spc, from_center_wld_spc))
    
    # 5. Calculate final depth
    # linearDepth converts clip-space Z to view-space Z
    # We subtract depth_offset because we want the front surface (closer to camera)
    # We add epsilon to bias towards the camera
    linear_center_depth = linear_depth(gl_FragCoord.z)
    final_linear_depth = linear_center_depth - depth_offset + epsilon
    
    # depthSample converts linear view-space Z back to clip-space Z for gl_FragDepth
    gl_FragDepth = depth_sample(final_linear_depth)
```

## Subtopics

### Single-Layer Ternary Depth Test
A prior approach [Weyrich et al. 2007] cited in [S2, unofficial] that maintains only a single surface layer per pixel. It applies a ternary depth test: if an incoming fragment's depth falls within an $\epsilon$-band of the stored value, it is blended into the running EWA sum; otherwise, it is replaced or discarded. This method produces hard, opaque fringes at silhouettes because normalized output is always fully opaque where any surfel contributes, and exacerbates self-occlusion artifacts at concavities by incorrectly rejecting deeper surfels [S2, unofficial].

## Operating characteristics
- **Time Complexity:** $O(1)$ per fragment. The calculation involves basic arithmetic and square roots.
- **Memory Complexity:** $O(1)$ auxiliary memory. Only the depth buffer is written.
- **Strengths:** Simple to implement in hardware shaders; provides correct visibility for front-facing surfaces.
- **Limitations:** Does not handle multiple surface layers per pixel (see [Single-Layer Ternary Depth Test](#single-layer-ternary-depth-test) pitfall); relies on accurate depth buffer precision.

## Background
The method is derived from point-sprite rendering techniques for point clouds. The specific implementation details, including the epsilon bias and depth offset calculation, are documented in the [PointCloudRendering](https://github.com/arminkz/PointCloudRendering) repository [S1, unofficial]. The comparison with the single-layer ternary depth test is detailed in the 3DSS paper [S2, unofficial].
