# Fragment List-Based Rendering Pipeline

Also called: 4-Stage Rendering Pipeline, Smoker Rendering Pipeline

## Overview
The Fragment List-Based Rendering Pipeline is a four-stage object-order rendering method designed for real-time smoke volume visualization. It processes geometry through distinct Clear, Construction, Insertion, and Evaluation stages to store per-pixel fragment data in shared memory structures, thereby maintaining high accuracy while circumventing the self-intersection and global occlusion problems inherent in raytracing approaches [S1, unofficial]. It differs from sibling pipelines by explicitly decoupling the accumulation of fragment attributes (Insertion) from their final visual interpretation (Evaluation), using fragment lists as the intermediate storage mechanism.

## How it works
**Inputs and Outputs:**
*   **Input:** 3D smoke volume geometry (vertices, density, flow tangents, orientation, topology) [S1, unofficial].
*   **Output:** Final rendered image with per-pixel visualization of smoke attributes [S1, unofficial].

**Data Structures:**
*   **OpenGL Buffer Objects:** Used to store state and intermediate data between stages. Specific layouts for fragment lists are not detailed in the sources, but they must support concurrent modification and be compatible with the Evaluation step [S1, unofficial].
*   **Shared Memory:** Used during the Insertion stage for indexing and storing fragment data. Access is managed via atomics to prevent inconsistent states [S1, unofficial].

**Numbered Steps:**
1.  **Clear:** Reset OpenGL buffer objects required for the subsequent frame. This stage is initiated by rendering a single screen-filling quad using the Clear shader program [S1, unofficial].
2.  **Construction:**
    *   **Vertex Shader:** Performs perspective transformation on vertices. Assigns additional vertex data such as density and flow tangents [S1, unofficial].
    *   **Geometry Shader:** Assembles primitives from the transformed vertices. Processes triangle-related data including orientation, topology, and volume information. Forwards the processed primitives to the Insertion stage [S1, unofficial].
    *   *Note:* Construction and Insertion belong to the same shader program, referred to as the **Render** stage [S1, unofficial].
3.  **Insertion:**
    *   Primitives constructed in the previous stage are rasterized and forwarded to the fragment shader.
    *   The fragment shader processes incoming fragments. The specific processing depends on the visualization method, ranging from a simple pixel counter to inserting fragments into a complicated storage data structure (fragment list) [S1, unofficial].
    *   **Constraint:** The type of fragment processing must be compatible with the subsequent Evaluation step [S1, unofficial].
    *   **Critical Section:** This stage is the primary bottleneck due to simultaneous access to shared indexing mechanisms. Unmanaged concurrent modification of shared memory leads to inconsistent states because shader threads cannot check if a shared address is currently being modified [S1, unofficial].
4.  **Evaluation:**
    *   Render a single screen-filling quad using the **Display** shader program.
    *   Interpret and visualize the per-pixel information that was prepared and stored during the Insertion stage [S1, unofficial].

**Pseudocode:**
```python
# Stage 1: Clear
def clear_stage():
    # Reset OpenGL buffer objects for the next frame
    reset_opengl_buffers()
    # Launch fragment shader threads by rendering a screen-filling quad
    render_screen_quad(clear_shader)

# Stage 2 & 3: Construction and Insertion (Render Stage)
def render_stage(geometry):
    # Vertex Shader: Transform and assign data
    transformed_vertices = []
    for vertex in geometry.vertices:
        pos = perspective_transform(vertex.position)
        density = vertex.density
        tangents = vertex.flow_tangents
        transformed_vertices.append({
            'position': pos,
            'density': density,
            'tangents': tangents
        })
    
    # Geometry Shader: Assemble primitives and process triangle data
    primitives = []
    for triangle in geometry.triangles:
        # Process orientation, topology, volume info
        orientation = compute_orientation(triangle)
        topology = compute_topology(triangle)
        volume_info = compute_volume_info(triangle)
        
        # Assemble primitive
        primitive = {
            'vertices': [transformed_vertices[v] for v in triangle.vertices],
            'orientation': orientation,
            'topology': topology,
            'volume_info': volume_info
        }
        primitives.append(primitive)
    
    # Rasterization and Fragment Shader (Insertion)
    for primitive in primitives:
        fragments = rasterize(primitive)
        for fragment in fragments:
            # Process fragment based on visualization method
            # Example: Insert into fragment list
            insert_fragment_into_list(fragment, primitive)

# Stage 4: Evaluation
def evaluation_stage():
    # Render screen-filling quad to interpret per-pixel info
    render_screen_quad(display_shader)
```

**Parameters:**
*   **Pipeline Stages:** Clear, Construction, Insertion, Evaluation [S1, unofficial].
*   **Shader Programs:** Clear, Render (combines Construction and Insertion), Display (handles Evaluation) [S1, unofficial].
*   **Typical Values:** Not given in the sources.

**Edge Cases and Pitfalls:**
*   **Concurrent Modification:** The Insertion step is the greatest bottleneck. Concurrent modification of shared memory causes bottlenecks and inconsistent states if unmanaged. Shader threads cannot check whether a shared address is currently being modified [S1, unofficial].
*   **Compatibility:** The fragment processing method in the Insertion stage must be strictly compatible with the Evaluation step [S1, unofficial].

## Subtopics

### Atomics
A technique used to alleviate bottlenecks in the Insertion stage by managing concurrent access to shared indexing mechanisms. Critical sections must be treated with caution to avoid inconsistent states in shared memory [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Not given in the sources.
*   **Measured Performance:** Implemented in the Smoker application for real-time smoke volume rendering [S1, unofficial].
*   **Scaling:** Not given in the sources.
*   **Strengths:** Maintains best possible accuracy; circumvents problems arising from raytracing, self-intersections, and global intersections [S1, unofficial].
*   **Limitations:** The Insertion step is a significant bottleneck due to simultaneous access to shared indexing mechanisms and the inability of shader threads to check for ongoing modifications to shared addresses [S1, unofficial].
*   **When to use:** Real-time smoke volume rendering where accuracy is prioritized and raytracing artifacts are undesirable [S1, unofficial].
*   **When not:** When hardware does not support the required OpenGL buffer objects or shader functionality for concurrent memory management [S1, unofficial].

## Background
The Fragment List-Based Rendering Pipeline was developed as part of the "Smoker" application for real-time smoke volume rendering. It was chosen over raytracing techniques to maintain accuracy and avoid issues related to self-intersections and global intersections [S1, unofficial]. The pipeline generalizes the rendering process into four distinct stages executed by three shader programs (Clear, Render, Display) [S1, unofficial].
