# Ray-Box Intersection via Quad Rasterization

Also called: Point-based Ray-Box Intersection

## Overview
This method renders a voxel grid by submitting a single point per occupied voxel to the graphics pipeline, deferring the geometric intersection test to the fragment shader. It solves the problem of efficient voxel visibility and depth testing by replacing explicit cube rasterization with a ray-casting step, allowing for a single draw call per frame. It differs from sibling methods like [Sparse Voxel Octree Rendering via Square Splats](2993-sparse-voxel-octree-rendering-via-square-splats.md) and [Voxel Point Sprite Rendering](4307-voxel-point-sprite-rendering.md) by explicitly computing the exact entry and exit distances of the ray against the voxel's axis-aligned bounding box (AABB) in screen space, rather than relying solely on point sprite coverage or octree traversal for culling.

## How it works
The technique relies on a vertex buffer containing one entry per voxel, rendered as `GL_POINTS`. The fragment shader reconstructs a ray from the camera to the fragment's screen position and tests it against the voxel's geometry.

### Inputs and Outputs
*   **Input**: A vertex array where each vertex represents one voxel. The vertex data typically encodes the voxel's 3D grid coordinates $(i, j, k)$ and optional attributes like color or density.
*   **Output**: A depth-buffered image. Fragments that fail the ray-box intersection test are discarded. Fragments that succeed write their depth to the depth buffer to ensure correct occlusion.

### Data Structures
The vertex buffer layout for `MODE_QUAD` is a packed integer format to minimize memory bandwidth. Each voxel is represented by two 32-bit unsigned integers:
1.  **Position**: A 32-bit integer packing the $x, y, z$ coordinates.
    *   $x$: bits 0–7 (8 bits)
    *   $y$: bits 8–18 (11 bits)
    *   $z$: bits 19–29 (11 bits)
    *   *Note: The specific bit allocation depends on the grid dimensions. In the reference implementation, $x$ is 8 bits, $y$ is 11 bits, and $z$ is 11 bits, supporting grids up to $256 \times 2048 \times 2048$.*
2.  **Attributes**: A 32-bit integer packing color/albedo (e.g., 5 bits R, 6 bits G, 5 bits B).

In the fragment shader, the voxel geometry is represented by a `Box` struct:
```glsl
struct Box {
    vec3 center;
    vec3 radius;
    vec3 invRadius;
    mat3 rotation; // Identity for axis-aligned boxes
};
```
The ray is represented by a `Ray` struct:
```glsl
struct Ray {
    vec3 origin;
    vec3 direction;
};
```

### Steps
1.  **Vertex Setup**: Generate a vertex buffer with one vertex per voxel. The vertex position attribute is not used for geometry; instead, the packed integer is decoded in the vertex shader or passed to the fragment shader to reconstruct the voxel's world-space center.
2.  **Point Size**: Enable `GL_PROGRAM_POINT_SIZE`. Set the point size in the vertex shader to cover the projected area of the voxel's cube. This ensures the fragment shader is invoked for all fragments that fall within the voxel's bounding box projection.
3.  **Ray Reconstruction**: In the fragment shader, reconstruct the ray origin and direction.
    *   **Origin**: The camera position in world space.
    *   **Direction**: Calculated from the fragment's screen coordinates (`gl_FragCoord`) and the camera's projection/view matrices. The direction is the normalized vector from the eye position to the reconstructed world position of the fragment.
4.  **Ray-Box Intersection**: Perform an optimized ray-AABB intersection test.
    *   The test assumes the ray starts outside the box (`rayCanStartInBox = false`) and the box is axis-aligned (`oriented = false`).
    *   Compute the intersection distances $t_{min}$ and $t_{max}$ for each axis.
    *   If the ray does not intersect the box (i.e., $t_{max} < t_{min}$ or the intervals do not overlap), discard the fragment.
5.  **Depth Writing**: If the intersection is valid, calculate the depth of the entry point (or exit point, depending on the desired shading model) and write it to `gl_FragDepth` to ensure correct depth testing against previously rendered voxels.

### Formulas
**Ray Direction**:
The ray direction $d$ is computed as:
$$
d = -\frac{P_{eye} - C_{cam}}{\|P_{eye} - C_{cam}\|}
$$
Where $P_{eye}$ is the reconstructed world position of the fragment and $C_{cam}$ is the camera origin. The negative sign accounts for the direction being from the camera to the scene.

**Ray-Box Intersection (Slab Method)**:
For an axis-aligned box centered at $c$ with radius $r$ (half-extents), and a ray with origin $o$ and direction $d$:
1.  Compute $t_{min} = -\infty$ and $t_{max} = \infty$.
2.  For each axis $i \in \{x, y, z\}$:
    *   Compute $invD_i = 1.0 / d_i$.
    *   Compute $t_1 = (c_i - r_i - o_i) \times invD_i$.
    *   Compute $t_2 = (c_i + r_i - o_i) \times invD_i$.
    *   Update $t_{min} = \max(t_{min}, \min(t_1, t_2))$.
    *   Update $t_{max} = \min(t_{max}, \max(t_1, t_2))$.
3.  If $t_{max} < t_{min}$, there is no intersection.

### Parameters
*   **Voxel Radius**: In the reference implementation, the voxel radius is hardcoded to `0.05` in the fragment shader, assuming unit-sized voxels or a specific normalization. [S1, unofficial]
*   **Point Size**: Set to cover the cube area. The exact value depends on the projection matrix and distance from the camera.

### Edge Cases and Pitfalls
*   **Division by Zero**: If a ray direction component is zero, $1/d_i$ is undefined. The implementation precomputes `invRayDirection` assuming finite values, which can lead to incorrect results or crashes if the ray is perfectly aligned with an axis. [S1, unofficial]
*   **Ray Origin Inside Box**: The intersection test assumes the ray starts outside the box. If the camera is inside a voxel, the test may fail or return incorrect distances. [S1, unofficial]
*   **Precision**: Using integer packing for vertex positions can lead to precision loss if the grid dimensions exceed the bit limits. [S1, unofficial]

### Pseudocode
```python
# Vertex Shader (GLSL-like)
void main() {
    // Decode voxel position from packed integer
    uint packed_pos = vertex_buffer[gl_VertexID].x;
    uint x = packed_pos & 0xFF;
    uint y = (packed_pos >> 8) & 0x7FF;
    uint z = (packed_pos >> 19) & 0x7FF;
    
    // Convert to world space
    vec3 voxel_center = vec3(float(x), float(y), float(z)) * voxel_size;
    
    // Set point size to cover the voxel's projected area
    // This is a simplification; in practice, it depends on the projection matrix
    gl_PointSize = calculate_point_size(voxel_center);
    
    // Pass voxel center to fragment shader
    frag_voxel_center = voxel_center;
    
    gl_Position = projection_matrix * view_matrix * vec4(voxel_center, 1.0);
}

# Fragment Shader (GLSL-like)
void main() {
    // Reconstruct ray origin and direction
    vec3 ray_origin = camera_position;
    vec3 frag_world_pos = reconstruct_world_position(gl_FragCoord);
    vec3 ray_direction = normalize(frag_world_pos - ray_origin);
    
    // Define the box
    vec3 center = frag_voxel_center;
    vec3 radius = vec3(0.05); // Hardcoded radius
    vec3 inv_radius = 1.0 / radius;
    
    // Compute ray-box intersection
    vec3 t0 = (center - radius - ray_origin) * (1.0 / ray_direction);
    vec3 t1 = (center + radius - ray_origin) * (1.0 / ray_direction);
    
    float t_min = max(max(min(t0.x, t1.x), min(t0.y, t1.y)), min(t0.z, t1.z));
    float t_max = min(min(max(t0.x, t1.x), max(t0.y, t1.y)), max(t0.z, t1.z));
    
    // Check for intersection
    if (t_max < t_min) {
        discard;
    }
    
    // Write depth
    float depth = t_min; // Use entry point depth
    gl_FragDepth = depth_to_gl_depth(depth);
    
    // Output color
    frag_color = vec4(1.0, 1.0, 1.0, 1.0);
}
```

## Subtopics

### Sparse Voxel Octree Rendering via Square Splats
Uses octree traversal to cull empty space and renders visible voxels as square splats. It is more efficient for sparse data but requires complex traversal logic. [Link](2993-sparse-voxel-octree-rendering-via-square-splats.md)

### Voxel Point Sprite Rendering
Renders voxels as point sprites without explicit ray-box intersection, relying on the graphics pipeline's point rasterization. It is simpler but less accurate for depth testing and occlusion. [Link](4307-voxel-point-sprite-rendering.md)

## Operating characteristics
*   **Time Complexity**: $O(N)$ where $N$ is the number of voxels. Each voxel requires a constant-time ray-box intersection test in the fragment shader.
*   **Memory Complexity**: $O(N)$ for the vertex buffer. The packed integer format minimizes memory usage.
*   **Performance**: On dedicated graphics cards, `MODE_QUAD` is approximately twice as fast as `MODE_CUBE` (which rasterizes 3 faces per voxel). On Intel Integrated graphics, performance is similar. [S1, unofficial]
*   **Strengths**: Single draw call, efficient for dense grids, accurate depth testing.
*   **Limitations**: High fragment shader load, potential division by zero issues, less efficient for very sparse data compared to octree-based methods.

## Background
The method is described in a test project by Clay John, which implements two rendering modes: `MODE_QUAD` (this method) and `MODE_CUBE`. The `MODE_QUAD` approach is based on the ray-box intersection algorithm described in "Efficient Ray-Box Intersection for Voxel Rendering" (JCGT 2018). [S1, unofficial]
