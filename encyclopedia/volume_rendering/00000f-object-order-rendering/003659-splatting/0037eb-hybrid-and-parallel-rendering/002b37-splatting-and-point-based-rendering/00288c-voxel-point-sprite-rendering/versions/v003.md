# Voxel Point Sprite Rendering

Also called: GL_POINTS voxel rendering, OpenGL Voxel Splatting, Point-based Voxel Rendering, Voxel Splatting

## Overview
Voxel Point Sprite Rendering is a technique that stores voxels as points (splatting) in a buffer and renders them using a geometry shader, allowing for mipmapped voxel data to be drawn as points with a specific scale [S2, unofficial]. It addresses the performance bottleneck of slow fragment shaders in pure splatting methods when rendering voxels close to the camera, a problem inherent to its parent method, [Splatting and Point-based Rendering](4975-splatting-and-point-based-rendering.md) [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A voxel grid defined by dimensions $width \times height \times depth$ (default 200x50x200 in [S1, unofficial] or 4x4x4 cubes in [S2, unofficial]). Each voxel contains position and color/albedo data.
*   **Output:** A rendered image where voxels are drawn as point sprites, with size and LOD determined by camera distance.

**Data Structures:**
Two distinct packing layouts are cited in the sources:

1.  **Layout A (Source [S1, unofficial]):** Voxel data is packed into pairs of `uint32_t`.
    *   **Position (`uint32_t`):**
        *   Bits 0-10 (11 bits): $x$
        *   Bits 11-20 (10 bits): $y$
        *   Bits 21-31 (11 bits): $z$
    *   **Albedo (`uint32_t`):**
        *   Bits 0-4 (5 bits): $R$
        *   Bits 5-10 (6 bits): $G$
        *   Bits 11-15 (5 bits): $B$
    *   Stored in a flat `uint32_t` array of size `no_of_vertices * 2`.

2.  **Layout B (Source [S2, unofficial]):** Used within `CUBE256::MipMap::voxels` (`std::vector<uint>`).
    *   Single `uint32_t` per voxel: $x$ (8 bits) | $(y \ll 8)$ (8 bits) | $(z \ll 16)$ (8 bits) | $(color \ll 24)$ (8 bits).
    *   The VBO layout for the geometry shader consists of four 4-component attributes (`vertex0` to `vertex3`), each reading 4 unsigned bytes (`GL_UNSIGNED_BYTE`) with normalization (`GL_TRUE`) from a stride of 16 bytes. `vertex0` reads bytes 0-3, `vertex1` reads bytes 4-7, etc.

**Parameters:**
*   `voxelSize`: Physical size of a single voxel in world units (e.g., 0.05) [S1, unofficial].
*   `halfScreenSize`: Half of the viewport dimensions, used to scale projected AABB to screen space [S1, unofficial].
*   `cubes_x, cubes_y, cubes_z`: Grid dimensions for the voxel space (default 4, 4, 4) [S2, unofficial].
*   `scale`: Rendering scale of splats, calculated as $0.1f \times (1 \ll \text{mipmap})$ [S2, unofficial].

**Steps:**

1.  **Initialize Voxel Grid:**
    *   Resize the cubes vector to `cubes_x * cubes_y * cubes_z` (default 64 cubes) [S2, unofficial].
    *   For each voxel index $i$, compute packed position and albedo using bitwise shifts and random color generation [S1, unofficial].

2.  **Set Voxel Position and Mipmap:**
    *   Shift $x, y, z$ by mipmap level: $x \ll= \text{mipmap}$ [S2, unofficial].
    *   Calculate cube ID: $\text{cubeID} = (x \gg 8) + (y \gg 8) \times \text{cubes\_x} + (z \gg 8) \times \text{cubes\_x} \times \text{cubes\_y}$ [S2, unofficial].
    *   Store local voxel $(x \& 255, y \& 255, z \& 255)$ in the corresponding cube's mipmap [S2, unofficial].
    *   Boundary check: If $x, y,$ or $z$ exceed 255, discard the voxel [S2, unofficial].

3.  **Calculate Mipmap Level:**
    *   Determine mipmap based on camera distance:
        $$ \text{mipmap} = \sqrt{\sqrt{(\text{screen.pos} + (\text{pos} + \text{vec3f}(0.5, 0.5, 0.5) + \text{add}) \times 16).\text{length()}}} - 1 $$
    *   Clamp mipmap to $\ge 0$ [S2, unofficial].

4.  **Generate VBOs:**
    *   For each mipmap with voxels, create a `GL_ARRAY_BUFFER`, bind it, and upload voxel data with `GL_STATIC_DRAW_ARB` [S2, unofficial].
    *   Bind to a VAO using `glVertexAttribIPointer(0, 2, GL_INT, 2 * sizeof(uint32_t), 0)` for Layout A [S1, unofficial].

5.  **Vertex Shader Processing:**
    *   Unpack voxel coordinates from the packed position `uint32_t` using bitmasks:
        $$ u_x = \text{data.x} \& \text{uint}(2047) $$
        $$ u_y = (\text{data.x} \& \text{uint}(2095104)) \gg \text{uint}(11) $$
        $$ u_z = (\text{data.x} \& (\text{uint}(2047) \ll \text{uint}(21))) \gg \text{uint}(21) $$
    *   Convert to world space by multiplying by 0.1 [S1, unofficial].

6.  **Stochastic Culling:**
    *   Apply stochastic culling for distant/small voxels to maintain performance [S1, unofficial].
    *   Calculate projected area: $\text{stochasticCoverage} = \text{point\_size} \times \text{point\_size}$.
    *   If $\text{stochasticCoverage} < 0.8$, discard vertex with probability proportional to size:
        ```glsl
        if ((stochasticCoverage < 0.8) && ((gl_VertexID & 0xffff) > stochasticCoverage * (0xffff / 0.8))) {
            position = vec4(-1, -1, -1, -1);
            point_size = 0.0;
        }
        ```
    *   Discard voxels behind the camera ($\text{position.z} \le 0.0$) by setting `position = vec4(-1,-1,-1,-1)` and `point_size = 0.0` [S1, unofficial].

7.  **Sphere Radius and Quadric Projection:**
    *   Approximate sphere radius: $\text{sphereRadius} = \text{voxelSize} \times 1.732051$ (where $1.732051 \approx \sqrt{3}$) [S1, unofficial].
    *   Calculate quadric projection coefficients:
        $$ \text{eqCoefs} = \frac{\text{vec4}(\text{dot}(\text{matD}[0], \text{matT}[2]), \text{dot}(\text{matD}[1], \text{matT}[2]), \text{dot}(\text{matD}[0], \text{matT}[0]), \text{dot}(\text{matD}[1], \text{matT}[1]))}{\text{dot}(\text{matD}[2], \text{matT}[2])} $$
        where $\text{matT}$ and $\text{matD}$ are derived from the model-view-projection matrix scaled by $\text{sphereRadius}$ [S1, unofficial].

8.  **Draw:**
    *   Enable `GL_PROGRAM_POINT_SIZE` [S1, unofficial].
    *   Draw with `glDrawArrays(GL_POINTS, 0, no_of_vertices)` [S1, unofficial].
    *   For Layout B: Bind shader, set projection matrix uniform, enable 4 vertex attributes pointing to VBO with stride 16, set `block_pos` and `scale` uniforms, draw `GL_POINTS` with count `voxels.size()/4`, then disable attributes and unbind buffer [S2, unofficial].

**Pseudocode:**

```python
# Initialization
cubes_x, cubes_y, cubes_z = 4, 4, 4
voxel_size = 0.05
half_screen_size = screen_size * 0.5

# Step 1 & 2: Initialize Grid and Set Voxel Position
cubes = resize_vector(cubes_x * cubes_y * cubes_z)
for mipmap_level in range(max_mipmaps):
    for cube_id in range(len(cubes)):
        cube = cubes[cube_id]
        cube.mipmaps[mipmap_level].voxels = []
        
        for voxel in cube.mipmaps[mipmap_level].voxels:
            x, y, z = voxel.position
            # Shift by mipmap level
            x_shifted = x << mipmap_level
            y_shifted = y << mipmap_level
            z_shifted = z << mipmap_level
            
            # Boundary check
            if x_shifted > 255 or y_shifted > 255 or z_shifted > 255:
                continue
                
            # Store local voxel
            local_x = x_shifted & 255
            local_y = y_shifted & 255
            local_z = z_shifted & 255
            cube.mipmaps[mipmap_level].voxels.append((local_x, local_y, local_z, voxel.color))

# Step 3: Calculate Mipmap Level for each voxel based on camera distance
def calculate_mipmap(screen_pos, voxel_pos_world, add_offset):
    # Formula from [S2, unofficial]
    # Note: 'screen.pos' and 'pos' need to be in compatible coordinate systems
    length_sq = (screen_pos + (voxel_pos_world + vec3(0.5, 0.5, 0.5) + add_offset) * 16).length_squared()
    mipmap = sqrt(sqrt(length_sq)) - 1
    return max(0, int(mipmap))

# Step 4: Generate VBOs
vbo_list = []
for cube in cubes:
    for mipmap_level in range(len(cube.mipmaps)):
        voxels = cube.mipmaps[mipmap_level].voxels
        if not voxels:
            continue
            
        # Create VBO
        vbo = create_buffer(GL_ARRAY_BUFFER)
        bind_buffer(vbo)
        
        # Upload data (Layout B: 4 attributes of 4 bytes each, stride 16)
        # Each voxel is 4 bytes (x,y,z,color packed)
        # We need to interleave or structure for 4 vertex attributes per voxel?
        # Source [S2, unofficial] says "four 4-component attributes... vertex0 reads bytes 0-3..."
        # This implies the VBO contains interleaved data for a single voxel's representation
        # or the geometry shader processes 4 voxels at once? 
        # Given "count = voxels.size()/4", it seems 4 voxels are packed into one draw call unit.
        
        data = []
        for i in range(0, len(voxels), 4):
            # Pack 4 voxels into 16 bytes per attribute? 
            # Actually, source says "stride 16 bytes" and "vertex0 reads bytes 0-3".
            # This suggests the VBO layout is: [v0.x, v0.y, v0.z, v0.c, v1.x, ...]
            # But "vertex0" is an attribute. 
            # Let's assume the VBO stores the 4 voxels sequentially.
            for j in range(4):
                if i + j < len(voxels):
                    vx, vy, vz, vc = voxels[i+j]
                    data.append(vx)
                    data.append(vy)
                    data.append(vz)
                    data.append(vc)
                else:
                    data.append(0) # Padding
                    
        upload_data(vbo, data, GL_STATIC_DRAW_ARB)
        vbo_list.append((vbo, len(voxels)//4, mipmap_level))

# Step 5 & 6: Vertex Shader Logic (Conceptual)
def vertex_shader(packed_data):
    # Unpack position (Layout A example)
    data_x = packed_data[0]
    u_x = data_x & 2047
    u_y = (data_x & 2095104) >> 11
    u_z = (data_x & (2047 << 21)) >> 21
    
    # Convert to world space
    world_pos = vec3(u_x, u_y, u_z) * 0.1
    
    # Check behind camera
    if world_pos.z <= 0.0:
        return vec4(-1, -1, -1, -1), 0.0
        
    return world_pos, point_size

# Step 7: Sphere Radius and Quadric Projection
def calculate_quadric_coefs(model_view_proj, sphere_radius):
    # Derive matT and matD from MVP scaled by sphere_radius
    # This is a simplified representation of the GLSL logic
    matT = model_view_proj * sphere_radius

    eq_coefs = vec4(
        dot(matD[0], matT[2]),
        dot(matD[1], matT[2]),
        dot(matD[0], matT[0]),
        dot(matD[1], matT[1])
    ) / dot(matD[2], matT[2])
    return eq_coefs

# Step 8: Draw Loop
for vbo, count, mipmap_level in vbo_list:
    bind_shader()
    set_uniform("projection_matrix", camera.projection)
    set_uniform("block_pos", cube_position)
    set_uniform("scale", 0.1f * (1 << mipmap_level))
    
    enable_vertex_attributes() # 4 attributes, stride 16, GL_UNSIGNED_BYTE, normalized
```

## Subtopics

### [Hybrid Voxel Rendering (Mesh/Splatting)](5766-hybrid-voxel-rendering-mesh-splatting.md)
Hybrid Voxel Rendering is a strategy that combines OpenGL splatting for distant voxels with mesh rendering for nearby voxels to reduce vertex count while maintaining visual quality. It addresses the performance bottleneck of slow fragment shaders in pure splatting methods when rendering voxels close to the camera, a problem inherent to its parent method, Voxel Point Sprite Rendering.

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of voxels, $O(N)$, where $N$ is the number of active voxels. Stochastic culling reduces the effective $N$ for distant voxels.
*   **Memory Complexity:** Linear with respect to the voxel grid size. Packing data into `uint32_t` arrays minimizes memory footprint.
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Scales well with voxel count due to point sprite efficiency. Mipmapping allows distant voxels to be rendered with lower resolution, reducing fragment shader load.
*   **Strengths:** Efficient rendering of large voxel datasets; hardware-accelerated point sprites; stochastic culling improves performance for distant objects.
*   **Limitations:** Potential artifacts from point sprite blending; requires geometry shader support; precision issues with large coordinate values if not packed carefully.
*   **When to use:** Real-time rendering of large voxel datasets where performance is critical and visual quality can be approximated by splats.
*   **When not to use:** When precise geometric boundaries are required, or when hardware does not support geometry shaders or point sprites.

## Background
Voxel Point Sprite Rendering is an implementation technique found in open-source voxel rendering experiments. It is associated with the "OpenGL-Voxel-Splatting" project by sp4cerat [S2, unofficial] and the "voxel-renderer" by clayjohn [S1, unofficial]. These projects demonstrate the use of OpenGL point sprites and geometry shaders for efficient voxel visualization.
