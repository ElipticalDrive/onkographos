# Splat Rasterization via Raycasting

Also called: GPU-based raycasting of quadric surfaces

## Overview
This method implements splat rasterization on GPUs by simulating a dedicated rasterization unit using standard graphics pipeline stages: vertex shaders for transformation and bounding box calculation, point primitives for fragment generation, and fragment shaders for kernel evaluation and depth computation [S1, unofficial]. It solves the problem of efficiently projecting 3D splats onto the screen while maintaining accurate depth values and filtering weights, optimizing for minimal instruction count in the fragment shader [S1, unofficial]. It is more efficient than previous GPU splatting implementations because the fragment shader requires only three computational instructions (two MADs and one texture fetch), whereas previous approaches were more expensive [S1, unofficial].

## How it works
**Inputs:** A set of 3D splats (quadric surfaces), camera parameters (projection and view matrices), and screen resolution.
**Outputs:** A 2D image with accumulated color and depth values.

**Data Structures:**
*   **Splat:** Defined by a center position $\mathbf{c}$, a $3 \times 3$ covariance matrix $\Sigma$, and attributes (color, opacity).
*   **Point Primitive:** A single vertex representing the splat center, drawn as a point primitive.
*   **Fragment Shader State:** Screen-space coordinates $(x, y)$, depth $z$, and the splat's transformed parameters.

**Steps:**

1.  **Vertex Shader Processing:**
    For each splat:
    a. Transform the splat center $\mathbf{c}$ from world space to clip space using the model-view-projection matrix $M_{vp}$.
    b. Perform view-frustum clipping on the bounding sphere of the splat in clip space using the Sutherland-Hodgman algorithm [S1, unofficial]. If the bounding sphere does not intersect the view frustum, discard the splat.
    c. Perform perspective division to obtain normalized device coordinates (NDC) for the center.
    d. Calculate the screen-space bounding box or extent. This can be done using the exact raycasting method (see Subtopics: Weyrich et al. Splat Extent Calculation) or an approximate polygon bounding method [S1, unofficial].
    e. Determine the size of the point primitive (screen-space square) based on the calculated extent.

2.  **Rasterization:**
    Draw the point primitive as a screen-space square covering the calculated extent. This generates fragments for every pixel within this square.

3.  **Fragment Shader Processing:**
    For each fragment generated by the point primitive:
    a. Cast a ray from the camera origin through the fragment's screen-space position $(x, y)$ into the scene.
    b. Test if the fragment's position lies within the splat's quadric surface in screen space. This involves evaluating the splat's equation at the fragment's coordinates.
    c. If the fragment is inside the splat, compute the contribution to the accumulated color and depth. The contribution is weighted by the splat's kernel function (e.g., Gaussian) evaluated at the fragment's distance from the splat center.
    d. The fragment shader performs this evaluation using minimal instructions: two MADs (Multiply-Add) and one texture fetch (for the splat's attributes or kernel lookup) [S1, unofficial].
    e. Accumulate the result into the frame buffer, typically using alpha blending or depth-based sorting.

**Formulas:**
*   **Splat Equation in Screen Space:** Let the splat be defined by $\mathbf{x}^T \Sigma^{-1} \mathbf{x} \leq 1$ in local space. After transformation to screen space, the equation becomes $\mathbf{u}^T A \mathbf{u} \leq 1$, where $\mathbf{u}$ is the screen-space coordinate vector and $A$ is the transformed covariance matrix.
*   **Raycasting Test:** For a fragment at screen position $\mathbf{u}$, check if $\mathbf{u}^T A \mathbf{u} \leq 1$.

**Parameters:**
*   **Point Primitive Size:** Determined by the screen-space extent of the splat.
*   **Kernel Width:** Typically 3-5 standard deviations for Gaussian splats.

**Edge Cases and Pitfalls:**
*   **Precision:** Floating-point precision issues may arise for very large or very small splats.
*   **Boundaries:** Splats near the near plane may have underestimated extents if approximate methods are used [S1, unofficial].
*   **Degenerate Input:** If the projected ellipse becomes a parabola or hyperbola, the exact raycasting method fails [S1, unofficial].

## Subtopics

### Weyrich et al. Splat Extent Calculation
A method to find screen-space position and extents by finding a plane in screen-space tangent to a quadric in parameter space (unit sphere), exploiting that normal vectors transform by the inverse transpose. It solves the problem of accurately determining the screen-space bounding box of a splat without using the inverse of the projective mapping. It is more accurate than Botsch et al.'s approximation, which can underestimate extents. When to choose it: When exact screen-space extents are required and the splat is not too close to the near plane or viewing frustum boundaries where degenerate projections might occur. Link: [Weyrich et al. Splat Extent Calculation](2152-gpu-splat-rasterization-via-vertex-fragment-shaders.md) (Note: This is a variant of the parent method, not a separate article).

Steps:
1.  Exploit that normal vectors transform by the inverse transpose of a mapping.
2.  Find a plane in screen-space tangent to the quadric in parameter space (unit sphere).
3.  Solve a quadratic equation for each dimension to determine the tangent plane's coefficients.

Pitfalls:
*   Yields results in normalized device coordinates, preventing view-frustum clipping of the bounding box.
*   Fails if the projected ellipse becomes a parabola or hyperbola.

## Operating characteristics
*   **Time Complexity:** $O(N \cdot K)$, where $N$ is the number of splats and $K$ is the average number of fragments per splat (proportional to the screen-space area of the splat).
*   **Memory Complexity:** $O(N)$ for storing splat data, plus frame buffer memory.
*   **Measured Performance:** Optimized for NVIDIA hardware, requiring only three computational instructions in the fragment shader (two MADs and one texture fetch) [S1, unofficial].
*   **Scaling:** Scales well with the number of splats, but performance degrades with high splat density due to overdraw.
*   **Strengths:** High performance on GPUs, accurate depth values, minimal instruction count in fragment shader.
*   **Limitations:** Approximate methods can underestimate extents; exact methods fail for degenerate projections; requires careful handling of view-frustum clipping.
*   **When to use:** Real-time volume rendering on GPUs where performance is critical and splats are well-behaved (not too close to near plane or viewing frustum boundaries).
*   **When not to use:** When exact screen-space extents are required for splats near the near plane or viewing frustum boundaries, or when degenerate projections are likely.

## Background
Origin: This method was developed in the context of GPU-based surface splatting, building on earlier work by Botsch et al. and Sigg et al. [S1, unofficial]. It was adapted by Weyrich et al. for surface splatting [S1, unofficial]. The implementation described in the source is from Sebastian Lipponer's "surface_splatting" project [S1, unofficial].
