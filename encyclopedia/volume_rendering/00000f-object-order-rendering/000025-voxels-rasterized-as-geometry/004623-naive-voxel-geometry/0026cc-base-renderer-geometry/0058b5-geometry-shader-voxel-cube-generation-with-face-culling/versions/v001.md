# Geometry Shader Voxel Cube Generation with Face Culling

Also called: Cube from Points, GS Voxel Rendering

## Overview
This method renders voxel cubes by generating triangle geometry from point primitives using a GPU geometry shader. It solves the problem of rendering large voxel fields efficiently by using an alpha channel in the input vertex color to determine which of the six cube faces to generate, allowing for occlusion culling of faces adjacent to other cubes [S1, unofficial]. It differs from sibling methods like [OpenGL Client State Array Rendering](11008-opengl-client-state-array-rendering.md) by generating geometry on the GPU per-voxel rather than batching static indices, and from [Dynamic VBO with Octree Rendering](13670-dynamic-vbo-with-octree-rendering.md) by not requiring hierarchical data structures or complex culling logic on the CPU [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A stream of `GL_POINTS`. Each point represents a voxel center. The vertex data includes a `vec4 colour`, where the alpha component (`colour[3]`) acts as a bitmask for face visibility.
*   **Output:** A stream of triangles (via `triangle_strip`).
*   **Uniforms:** Three $4 \times 4$ transformation matrices: `modelToWorldMatrix`, `worldToCameraMatrix`, and `cameraToClipMatrix`. Alternatively, a pre-computed MVP matrix can be used [S1, unofficial].

**Data Structures:**
1.  **Cube Vertices (`cubeVerts`):** An array of 8 `vec4` values defining a unit cube centered at the origin with side length 1. Coordinates are $\pm 0.5$.
    *   Index 0: $(-0.5, -0.5, -0.5, 1)$
    *   Index 1: $(-0.5, 0.5, -0.5, 1)$
    *   Index 2: $(0.5, -0.5, -0.5, 1)$
    *   Index 3: $(0.5, 0.5, -0.5, 1)$
    *   Index 4: $(-0.5, -0.5, 0.5, 1)$
    *   Index 5: $(-0.5, 0.5, 0.5, 1)$
    *   Index 6: $(0.5, -0.5, 0.5, 1)$
    *   Index 7: $(0.5, 0.5, 0.5, 1)$
2.  **Cube Indices (`cubeIndices`):** An array of 24 integers defining the 6 faces as quads (4 vertices each). The order ensures correct winding for front-face culling (counter-clockwise).
    *   Front (Z-): `0, 1, 2, 3`
    *   Right (X+): `7, 6, 3, 2`
    *   Back (Z+): `7, 5, 6, 4`
    *   Bottom (Y-): `4, 0, 6, 2`
    *   Left (X-): `1, 0, 5, 4`
    *   Top (Y+): `3, 1, 7, 5`

**Algorithm Steps:**
1.  **Extract Face Mask:** Read the alpha component of the input vertex color and convert it to an integer `a`. This integer represents a bitmask where specific bits correspond to specific faces [S1, unofficial].
2.  **Pre-transform Vertices (Optimization):** Multiply the voxel center position (`gl_in[0].gl_Position`) by the combined MVP matrix and add the local offset of each of the 8 cube vertices. Store these 8 transformed positions in a local array `transVerts` [S1, unofficial]. This avoids redundant matrix multiplications for shared vertices across multiple faces.
3.  **Generate Faces:** Iterate through the 6 faces. For each face, check the corresponding bit in `a`. If the bit is set, emit the 4 vertices of that face using the pre-transformed positions from `transVerts`.
    *   The specific bit checks described in the source use thresholds: `if (a > 31)` for the bottom face and `if (a > 15)` for the top face, implying a binary encoding where bits 0-3 might control one set of faces and 4-5 another, or similar. The source code explicitly subtracts 32 after checking the bottom face, suggesting a greedy bit-clearing approach or specific bit layout [S1, unofficial].
    *   For each vertex of the visible face, set `gl_Position` to the corresponding entry in `transVerts` and call `EmitVertex()`.
4.  **End Primitive:** After emitting all 4 vertices of a face, call `EndPrimitive()` to finalize the triangle strip for that face [S1, unofficial].

**Parameters:**
*   **Face Mask Bits:** The alpha channel of the input vertex color. Typical values are integers 0-63. A value of 63 renders all faces. A value of 0 renders none. The specific bit-to-face mapping in the source is: Bit 0=Front, Bit 1=Right, Bit 2=Back, Bit 3=Left, Bit 4=Top, Bit 5=Bottom [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Matrix Multiplication Order:** OpenGL geometry shaders operate on vertices, not faces. Transformations must be applied to individual vertices. Storing vertices in matrix rows for batch multiplication is not a standard or necessarily faster approach than per-vertex transformation in this context [S1, unofficial].
*   **Precision:** Using a single MVP matrix reduces precision errors compared to sequential multiplication in the shader, but floating-point precision limits may cause z-fighting if voxels are very close or the scene is very large [G].
*   **Degenerate Input:** If the alpha mask is 0, no vertices are emitted, and the point is effectively culled.

## Operating characteristics
*   **Time Complexity:** $O(V \cdot F)$, where $V$ is the number of voxels and $F$ is the number of visible faces per voxel (0-6). With pre-transformation, the constant factor is reduced by avoiding redundant matrix multiplications.
*   **Memory Complexity:** $O(1)$ per voxel in the shader (local arrays of size 8 and 24). The input buffer size is $O(V)$.
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Scales linearly with the number of voxels. Performance is heavily dependent on the GPU's geometry shader throughput and the number of emitted vertices.
*   **Strengths:** Simple implementation, flexible face culling, no CPU-side geometry generation required.
*   **Limitations:** Geometry shader overhead can be significant for very large voxel counts. Not suitable for extremely high-resolution scenes without further optimization (e.g., instancing, texture-based rendering).
*   **When to use:** Small to medium voxel scenes where dynamic face culling is beneficial and CPU-side geometry generation is a bottleneck.
*   **When not to use:** Very large voxel scenes where geometry shader overhead becomes prohibitive, or when static geometry can be pre-generated and stored in a VBO.

## Background
This technique originated from early OpenGL voxel rendering experiments, specifically discussed in a 2013 Stack Overflow post by user laggyluk [S1, unofficial]. It leverages the flexibility of geometry shaders to generate cube geometry on the fly, a common approach in early voxel engines before more advanced techniques like texture-based voxel rendering or GPU-driven rendering became prevalent.
