# Geometry Shader Processing

Also called: Geometry Shader Voxels, GS Voxelization

## Overview
Geometry Shader Processing is a family of GPU-based techniques that generate volumetric or vector geometry primitives dynamically from simple input streams (points, triangles) using the geometry shader stage of the graphics pipeline [S1, S2, S3, unofficial]. It solves the problem of rendering complex volumetric data, velocity fields, or particle systems without pre-computing and storing full mesh geometry on the CPU or in large vertex buffers [S2, S3, unofficial]. Unlike [Naive Voxel Rendering](1103-naive-voxel-rendering.md) which may rely on static geometry, this family computes the primitive topology (cubes, quads, lines) on-the-fly, allowing for flexible visibility culling and adaptive detail [S2, S3, unofficial].

## Shared principles
The family shares the fundamental mechanism of converting scalar field data or point streams into geometric primitives that are submitted to the graphics pipeline.

1.  **Primitive Generation**: Each occupied voxel or data point is represented by one or more geometric primitives. The most common representation is a cube (6 faces, 24 vertices for flat shading, or 8 vertices for shared shading) or a set of quads representing visible faces [S1, S3, S4, unofficial].
2.  **Coordinate Transformation**: Voxel indices $(i, j, k)$ are transformed into world space. For a dense grid with bounds $P_{min}$ and $P_{max}$ and dimension $N_{dim}$, the world position $P_{world}$ of a voxel center is calculated as [S4, unofficial]:
    $$
    P_{world} = P_{min} + \frac{I_{voxel}}{N_{dim}} \times (P_{max} - P_{min})
    $$
    For unit voxels, this simplifies to $P_{world} = I_{voxel} \times V_{size}$, where $V_{size}$ is the voxel dimension [S2, S4, unofficial].
3.  **Rasterization**: The generated primitives are transformed into clip space using the Model-View-Projection (MVP) matrix and rasterized. Visibility is determined by the depth buffer (z-buffer) or a back-to-front painter's algorithm if transparency is required [S2, S3, unofficial].
4.  **Culling**: To manage performance, frustum culling is applied to exclude voxels outside the camera view [S2, S4, unofficial]. Back-face culling is often enabled to discard faces oriented away from the camera, calculated by the dot product of the view-space normal and the view vector [S2, unofficial].

## Subtopics

### [Geometry Shader Cube Expansion](1074-geometry-shader-cube-expansion.md)
Generates a voxel shell representation by expanding input primitives into cubes composed of 6 faces. It solves the problem of rendering volumetric data without pre-computing full mesh geometry. Unlike [Geometry Shader (Quads)](4369-geometry-shader-quads.md), it typically stores a single point per voxel containing flags for all 6 faces, generating geometry dynamically. It differs from [Active Cell Geometry Generation](3887-active-cell-geometry-generation.md) by deriving positions directly from input triangle centroids or a point stream.

### [Velocity Visualization via Geometry Shader Extrusion](1581-velocity-visualization-via-geometry-shader-extrusion.md)
Visualizes a grid of velocities by rendering short line segments with alpha gradients. It populates a vertex buffer with one point per grid cell and uses a geometry shader to extrude each point into a line segment based on sampled volume data.

### [Geometry Shader Triangle Slicing (Z-Pass)](1681-geometry-shader-triangle-slicing-z-pass.md)
A single-pass GPU method for multi-channel surface voxelization that explicitly clips input triangles against volume slice boundaries within the geometry shader. It differs from [Pixel Shader Fragment Clipping](1685-pixel-shader-fragment-clipping.md) by performing clipping in the geometry shader, avoiding fragment rejection overhead.

### [Geometry Shader (Quads)](4369-geometry-shader-quads.md)
Renders volumetric data by generating exactly one quad per input primitive, where each primitive represents a single visible face. It extends the Geometry Shader Voxels technique by breaking voxels down into constituent faces, trading increased input data density for better GPU architecture compatibility and reduced buffer space.

### [GPU Particle Rendering via Geometry Shader](4444-gpu-particle-rendering-via-geometry-shader.md)
Renders 2D sprite quads from point primitives, allowing for efficient particle rendering without CPU-side mesh generation. It differs from [Geometry Shader Cube Expansion](1074-geometry-shader-cube-expansion.md) by emitting flat 2D quads rather than 3D volumetric primitives.

## Background
The use of geometry shaders for voxel and particle rendering emerged as a solution to the bottleneck of CPU-side geometry generation for dynamic volumetric data. Early implementations focused on shell voxelization, where triangle centroids were expanded into cubes to visualize surfaces [S1, S2, S3, unofficial]. Subsequent developments introduced face-level granularity to optimize vertex output limits and improve compatibility with GPU architectures [S1, S2, unofficial]. The technique has been widely adopted in scientific visualization for velocity fields [S1, unofficial] and real-time particle systems [S1, S2, unofficial].
