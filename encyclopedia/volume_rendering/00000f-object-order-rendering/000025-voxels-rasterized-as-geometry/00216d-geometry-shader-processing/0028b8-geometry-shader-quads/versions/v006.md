# Geometry Shader (Quads)

Also called: GS Quads, Geometry Shader quads generated each frame from faces

## Overview
This method extends the geometry shader voxel rendering approach by decomposing voxels into individual faces, where each input `GL_POINT` represents a single quad rather than a whole voxel [S1, S2, unofficial]. It differs from [Geometry Shader Cube Expansion](1074-geometry-shader-cube-expansion.md) by outputting only 4 vertices per primitive instead of 12, which reduces buffer space requirements and improves compatibility with GPU architectures, at the cost of requiring one input point per face rather than one per voxel [S1, S2, unofficial].

## How it works
**Inputs and Outputs:**
The input is a stream of points, where each point corresponds to a single visible face of a voxel. The output is a stream of triangles forming a quad for each input point.

**Data Structures:**
The input vertex structure is defined as [S1, S2, unofficial]:
```cpp
struct PointQuad {
    vec3 position;      // Center position of the voxel
    uint32_t packedColor; // Color data
    uint8_t faceIdx;    // Index indicating which of the 6 faces to generate
};
```
The `faceIdx` selects one of the 6 possible face orientations.

**Constant Arrays:**
Two constant arrays define the local axis vectors for the 6 face orientations [S1, S2, unofficial]:
```glsl
const vec3 dxs[6] = vec3[6](
    vec3(0, 1, 0),
    vec3(0, 0, 1),
    vec3(0, 0, 1),
    vec3(1, 0, 0),
    vec3(1, 0, 0),
    vec3(0, 1, 0)
);

const vec3 dys[6] = vec3[6](
    vec3(0, 0, 1),
    vec3(0, 1, 0),
    vec3(1, 0, 0),
    vec3(0, 0, 1),
    vec3(0, 1, 0),
    vec3(1, 0, 0)
);
```
*Note: The source code in [S1, unofficial] uses a different logic involving bitmasks and normal culling for all 6 faces. The source code in [S2, unofficial] uses a single `faceIdx` to select one face. This article implements the `faceIdx` approach as it is the defining characteristic of the "Quads" technique described in the notes [S2, unofficial].*

**Parameters:**
- `voxSize`: The side length of the voxel.
- `mvp`: The Model-View-Projection matrix uniform.

**Steps:**
1. Retrieve the center position from `gl_in[0].gl_Position` [S1, S2, unofficial].
2. Retrieve the `faceIdx` from the input vertex attributes [S2, unofficial].
3. Calculate the offset vectors `dx` and `dy` in world space using the selected indices from `dxs` and `dys`, scaled by half the voxel size and transformed by the MVP matrix [S2, unofficial]:
   $$ dx = mvp \times vec4(dxs[faceIdx] \times \frac{voxSize}{2.0}, 0) $$
   $$ dy = mvp \times vec4(dys[faceIdx] \times \frac{voxSize}{2.0}, 0) $$
4. Call `AddQuad` with the center and the calculated offsets [S2, unofficial].

**Pseudocode:**
```python

    uint faceIdx = gl_in[0].gl_VertexID; // Placeholder for actual attribute access if not standard GLSL

        uint faceIdx = gl_in[0].gl_VertexID;
    #else

        // Since this is a point shader input, we access it via the input struct.
        // In GLSL, we would use: uint faceIdx = gl_in[0].faceIdx; 
        // But gl_in is an array of gl_VertexID, gl_Position, etc.
        // We assume the input data is structured such that faceIdx is accessible.
        // For the sake of this implementation, we assume a custom attribute is passed.
        // However, the source [S2, unofficial] shows: mvp * vec4(dxs[gFaceIdx[0]] ...
        // gFaceIdx[0] implies an input array. In GS, gl_in[0] contains the vertex.
        // We assume the vertex shader passes faceIdx as a varying or it is part of the point data.
        // Let's assume it is passed as a varying attribute 'faceIdx'.
        uint faceIdx = faceIdx_in; 
    #endif

    // 3. Define constant arrays
    const vec3 dxs[6] = vec3[6](
        vec3(0, 1, 0),
        vec3(0, 0, 1),
        vec3(0, 0, 1),
        vec3(1, 0, 0),
        vec3(1, 0, 0),
        vec3(0, 1, 0)
    );
    const vec3 dys[6] = vec3[6](
        vec3(0, 0, 1),
        vec3(0, 1, 0),
        vec3(1, 0, 0),
        vec3(0, 0, 1),
        vec3(0, 1, 0),
        vec3(1, 0, 0)
    );

    // 4. Calculate offsets
    vec4 dx = mvp * vec4(dxs[faceIdx] / 2.0f * voxSize, 0);
    vec4 dy = mvp * vec4(dys[faceIdx] / 2.0f * voxSize, 0);

    // 5. Generate Quad
    AddQuad(center, dx, dy);
}

void AddQuad(vec4 center, vec4 dx, vec4 dy) {
    // Generate 4 vertices for the quad
    // Vertex 0: center - dx - dy
    gl_Position = center - dx - dy;
    EmitVertex();
    
    // Vertex 1: center + dx - dy
    gl_Position = center + dx - dy;
    EmitVertex();
    
    // Vertex 2: center + dx + dy
    gl_Position = center + dx + dy;
    EmitVertex();
    
    // Vertex 3: center - dx + dy
    gl_Position = center - dx + dy;
    EmitVertex();
    
    EndPrimitive();
}
```
*Note: The source [S2, unofficial] code snippet shows `AddQuad` being called with `center`, `dx`, and `dy`. The implementation of `AddQuad` is not explicitly detailed in the source, but a standard quad generation is implied. The source [S1, unofficial] provides a more complex `AddQuad` that handles normals and culling, but the "Quads" technique specifically emphasizes the simplicity of generating one quad per point [S2, unofficial].*

**Edge Cases and Pitfalls:**
- **Vertex Output Limit:** The technique is limited to 4 vertices per primitive. This is a constraint of the geometry shader output for this specific optimization [S1, S2, unofficial].
- **Input Data:** Requires one input point per face, which increases the input data size compared to the voxel-based approach [S2, unofficial].
- **Face Indexing:** The `faceIdx` must correctly map to the `dxs` and `dys` arrays. Incorrect indexing will result in distorted geometry [S2, unofficial].

## Operating characteristics
- **Time Complexity:** $O(N)$ where $N$ is the number of input points (faces).
- **Memory Complexity:** $O(N)$ for input data. Output buffer size is $4 \times N$ vertices.
- **Performance:** Reduces buffer space needs compared to the voxel-based technique (4 vertices vs 12) [S1, S2, unofficial]. Plays better with current GPU architectures [S1, S2, unofficial]. Frame times are close to other optimized techniques after significant optimization [S2, unofficial].
- **Strengths:** Low memory usage, good render time, improved GPU compatibility [S1, S2, unofficial].
- **Limitations:** Requires more input data (one point per face) [S2, unofficial].

## Background
Originated as an extension to the geometry shader voxel rendering technique, breaking voxels down into individual faces [S1, S2, unofficial]. The technique was developed to address the high memory usage and setup time of display lists, offering a low-memory alternative with competitive render times [S1, S2, unofficial].
