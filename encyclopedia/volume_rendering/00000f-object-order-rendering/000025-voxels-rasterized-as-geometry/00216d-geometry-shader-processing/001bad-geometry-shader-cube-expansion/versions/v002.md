# Geometry Shader Cube Expansion

Also called: GS Voxels, GS-based voxelizer, Geometry Shader (Voxels), Geometry Shader quads generated each frame from voxels, Point-to-Cube voxelization

## Overview
Geometry Shader Cube Expansion is a GPU technique that generates a voxel shell representation by expanding input primitives into cubes composed of 6 faces [S1, S2, S3, unofficial]. It solves the problem of rendering volumetric data without pre-computing and storing full mesh geometry for every voxel [S2, S3, unofficial]. Unlike [Geometry Shader (Quads)](4369-geometry-shader-quads.md), which may store individual faces, this method typically stores a single point per voxel containing flags for all 6 faces, generating the geometry dynamically [S2, S3, unofficial]. It differs from [Active Cell Geometry Generation](3887-active-cell-geometry-generation.md) by deriving voxel positions directly from input triangle centroids or a point stream, rather than iterating over a pre-computed flag volume [S1, unofficial].

## How it works
The method operates in two primary modes depending on the input: triangle-to-point expansion or direct point expansion [S1, S2, S3, unofficial]. Both modes rely on a geometry shader to generate cube geometry from a single input primitive [S1, S2, S3, unofficial].

### Inputs and Outputs
*   **Input (Triangle Mode):** A stream of triangles (`GL_TRIANGLES`) [S1, unofficial]. Each triangle is processed to compute a centroid [S1, unofficial].
*   **Input (Point Mode):** A stream of points (`GL_POINTS`) [S2, S3, unofficial]. Each point represents a voxel center [S2, S3, unofficial]. The vertex buffer contains a structure `PointVertex` [S2, S3, unofficial].
*   **Output:** A stream of triangle strips (`GL_TRIANGLE_STRIP`) [S1, S2, S3, unofficial]. Each input primitive generates up to 6 quads (24 vertices) if all faces are enabled, or fewer if culling or flags are used [S1, S2, S3, unofficial].

### Data Structures
For Point Mode, the input vertex structure is defined as [S2, S3, unofficial]:
```cpp
struct PointVertex {
    vec3 position;      // Voxel center coordinates
    uint32_t packedColor; // Color information
    uint8_t enabledFaces; // Bitmask for face visibility
};
```
The `enabledFaces` bitmask uses the following bits [S2, S3, unofficial]:
*   Bit 0x01: +dx face
*   Bit 0x02: -dx face
*   Bit 0x04: +dy face
*   Bit 0x08: -dy face
*   Bit 0x10: +dz face
*   Bit 0x20: -dz face

### Parameters
*   `voxSize` (float): The side length of the generated cube [S1, S2, S3, unofficial]. Default value is 0.25 [S2, S3, unofficial].
*   `mvp` (mat4): The Model-View-Projection matrix, used to extract axis vectors [S2, S3, unofficial].
*   `gColor` (vec3): The color to apply to the generated faces [S2, S3, unofficial].

### Steps

#### 1. Triangle-to-Point Conversion (Vertex Shader)
If the input is triangles, the vertex shader computes the centroid of the triangle and passes it to the geometry shader [S1, unofficial].
1.  Receive vertices `gl_in[0]`, `gl_in[1]`, `gl_in[2]` [S1, unofficial].
2.  Compute centroid:
    $$ \text{center} = \frac{\text{gl\_in}[0].\text{gl\_Position}.xyz + \text{gl\_in}[1].\text{gl\_Position}.xyz + \text{gl\_in}[2].\text{gl\_Position}.xyz}{3.0} $$
3.  Pass `center` to the geometry shader as a point primitive [S1, unofficial].

#### 2. Geometry Shader Processing
The geometry shader receives either the computed centroid (from triangles) or the point data (from points) [S1, S2, S3, unofficial].

**A. Extract Extents**
Extract the axis vectors from the MVP matrix columns, scaled by half the voxel size [S2, S3, unofficial]:
$$ dx = \frac{mvp[0]}{2.0} \times \text{voxSize} $$
$$ dy = \frac{mvp[1]}{2.0} \times \text{voxSize} $$
$$ dz = \frac{mvp[2]}{2.0} \times \text{voxSize} $$
Note: `mvp[0]`, `mvp[1]`, `mvp[2]` are the first three columns of the matrix [S2, S3, unofficial]. `dx`, `dy`, `dz` are `vec4` vectors [S2, S3, unofficial].

**B. Face Generation Logic**
For each of the 6 faces, check if the corresponding bit is set in `enabledFaces` and if the face is not culled [S2, S3, unofficial]. If valid, call `AddQuad` with the appropriate offset and axis vectors [S2, S3, unofficial].

The culling function `IsCulled` checks if the normal's Z component in view space is positive (back-facing) [S2, S3, unofficial]:
```python
def IsCulled(normal):
    return normal.z > 0
```

The face checks are [S2, S3, unofficial]:
1.  If `(enabledFaces & 0x01)` and `!IsCulled(dx)`: Call `AddQuad(center + dx, dy, dz)`
2.  If `(enabledFaces & 0x02)` and `!IsCulled(-dx)`: Call `AddQuad(center - dx, dz, dy)`
3.  If `(enabledFaces & 0x04)` and `!IsCulled(dy)`: Call `AddQuad(center + dy, dz, dx)`
4.  If `(enabledFaces & 0x08)` and `!IsCulled(-dy)`: Call `AddQuad(center - dy, dx, dz)`
5.  If `(enabledFaces & 0x10)` and `!IsCulled(dz)`: Call `AddQuad(center + dz, dx, dy)`
6.  If `(enabledFaces & 0x20)` and `!IsCulled(-dz)`: Call `AddQuad(center - dz, dy, dx)`

*Note: The order of arguments to `AddQuad` varies in the source to ensure correct winding order for the specific face orientation [S2, S3, unofficial].*

**C. Emitting Quads**
The `AddQuad` function emits 4 vertices for a triangle strip [S2, S3, unofficial]:
```python
# Standard Geometry Shader built-ins (defined per specification)
# gl_Position: current vertex position in clip space
# fColor: current vertex color
# EmitVertex(): appends (gl_Position, fColor) to the current output primitive
# EndPrimitive(): finalizes the current primitive and resets vertex counter

def AddQuad(center, dy, dx, gColor):
    fColor = gColor[0]
    gl_Position = center + (dx - dy)
    EmitVertex()
    gl_Position = center + (-dx - dy)
    EmitVertex()
    gl_Position = center + (dx + dy)
    EmitVertex()
    gl_Position = center + (-dx + dy)
    EmitVertex()
    EndPrimitive()
```

#### 3. Triangle Mode Normal Calculation (Alternative)
In the triangle-based approach [S1, unofficial], normals are calculated per face within `EmitQuad` rather than using matrix-derived vectors for culling [S1, unofficial].
1.  Define 4 corners `P0, P1, P2, P3` offset from `P` (centroid) by `±voxel_size/2.0` [S1, unofficial].
2.  Compute vectors `V0 = P0 - P1` and `V1 = P2 - P1` [S1, unofficial].
3.  Compute normal `N = normalize(cross(V1.xyz, V0.xyz))` [S1, unofficial].
4.  Transform normal to view space: `v_normal = ModelViewMatrix * vec4(N, 0.0)` [S1, unofficial].
5.  Emit vertices with `gl_Position = ModelViewProjectionMatrix * P_i` and attributes `vertex_normal`, `vertex_eyevec`, `vertex_lightdir` [S1, unofficial].

### Edge Cases and Pitfalls
*   **Interior Filling:** This method performs only shell voxelization [S1, unofficial]. It does not fill the interior of the mesh, making it unsuitable for deep voxelization or solid volume rendering without additional techniques [S1, unofficial].
*   **Aliasing:** Because it approximates the mesh surface with cubes centered on triangle centroids, it can produce aliasing and holes compared to precise ray-casting or rasterization-based voxelizers [S1, unofficial].
*   **Vertex Output Limit:** The point-based method outputs up to 12 vertices per primitive (if `max_vertices` is set to 12 and all faces are drawn) [S3, unofficial]. This may be less efficient on some GPU architectures compared to limiting output to 4 vertices per primitive (as in the [Geometry Shader (Quads)](4369-geometry-shader-quads.md) variant) [S3, unofficial].
*   **Culling:** The simple `IsCulled` check (`normal.z > 0`) assumes a standard view direction [S2, S3, unofficial]. It may fail for non-standard view matrices or if the MVP matrix is not properly constructed [S2, S3, unofficial].

## Subtopics

### [Active Cell Geometry Generation](3887-active-cell-geometry-generation.md)
Generates cube geometry for active voxels in a volume dataset using a flag volume. It handles pre-computed active cells rather than generating geometry from raw triangle input or point streams.

## Operating characteristics
*   **Memory Usage:** The point-based input format requires only 25 bytes per voxel (3 bytes position + 4 bytes color + 1 byte flags, padded to 8 bytes alignment or similar, totaling 25 bytes as cited) [S2, S3, unofficial]. This is significantly lower than previous techniques which required 96–576 bytes per voxel [S2, S3, unofficial].
*   **Performance:** Geometry shaders provide low memory usage and render times close to display lists, though display lists may still be faster in some benchmarks [S2, S3, unofficial].
*   **Scalability:** Performance scales with the number of voxels [S2, S3, unofficial]. The dynamic generation allows for efficient updates if the voxel data changes frequently, as geometry is regenerated each frame [S2, S3, unofficial].
*   **Strengths:** Low memory footprint, simple implementation, dynamic generation of visible faces based on flags [S2, S3, unofficial].
*   **Limitations:** Only supports shell voxelization; potential for aliasing; higher vertex output per primitive compared to face-based geometry shaders [S1, S3, unofficial].

## Background
The technique was developed as part of a series of voxel rendering optimizations [S2, S3, unofficial]. It was introduced in discussions around 2016-2017 by developers exploring efficient GPU-based voxel rendering [S1, S2, S3, unofficial]. It was compared against display lists, vertex array objects, and other geometry shader variants in benchmarks run on a GTX 980 Ti with an Intel i7-4790k [S2, S3, unofficial]. The method was implemented in GeeXLab demos [S1, unofficial].
