# Velocity Visualization via Geometry Shader Extrusion
Also called: Grid Velocity Lines, Velocity Vector Lines

## Overview
This method visualizes a grid of velocity vectors by rendering short line segments where length and direction reflect the velocity in each grid cell [S1, unofficial]. It uses explicit line primitives generated by a geometry shader to provide directional clarity for each sampled point [S1, unofficial].

## How it works
**Inputs and Outputs:**
* Input: A vertex buffer containing one point per grid cell, and a 3D texture volume storing velocity vectors [S1, unofficial].
* Output: A rendered image of red line segments with alpha gradients [S1, unofficial].

**Data Structures:**
* Vertex Buffer: Stores `vec4` positions for each grid cell [S1, unofficial].
* 3D Texture: Stores `vec3` velocity vectors, sampled at normalized coordinates [S1, unofficial].

**Numbered Steps:**
1. Populate a vertex buffer with one point per grid cell [S1, unofficial].
2. Pass each vertex through a vertex shader to compute its clip-space position and pass the original world-space position to the geometry shader [S1, unofficial].
3. In the geometry shader, sample the velocity vector from the 3D texture volume using the normalized world-space position [S1, unofficial].
4. Emit the first vertex of a line strip at the original clip-space position with an alpha value of 0 [S1, unofficial].
5. Emit the second vertex of the line strip at the position offset by the velocity vector, transformed to clip-space, with an alpha value of 1 [S1, unofficial].
6. Finalize the line strip primitive [S1, unofficial].
7. In the fragment shader, output a red color scaled by the interpolated alpha and a uniform brightness factor [S1, unofficial].

**Formulas:**
* Normalized Coordinate: $\text{coord} = 0.5 \times (\text{vPosition}.xyz + 1.0)$ [S1, unofficial].
* Velocity Vector: $\mathbf{V} = \text{texture}(\text{Volume}, \text{coord}).xyz$ [S1, unofficial].
* Second Vertex Position: $\mathbf{P}_{\text{end}} = \text{ModelviewProjection} \times (\mathbf{P}_{\text{start}} + \mathbf{V})$ [S1, unofficial].
* Fragment Color: $\mathbf{C} = \text{Brightness} \times [\alpha, 0, 0, 1]$ [S1, unofficial].

**Parameters:**
* Brightness: A uniform float controlling output intensity, typically set to 0.5 [S1, unofficial].

**Edge Cases and Pitfalls:**
* Blending: Requires `GL_MAX` blending rather than the default `GL_FUNC_ADD` to prevent cancellation of opposing vectors [S1, unofficial].
* Precision: The velocity vector magnitude directly affects line length, requiring sufficient texture precision for small velocities [G].
* Boundaries: Sampling near texture boundaries may require appropriate filtering settings to avoid artifacts [G].

**Pseudocode:**
```python
def vertex_shader(position: tuple, mv_matrix: list) -> tuple:
    clip_pos = [sum(mv_matrix[i][j] * position[j] for j in range(4)) for i in range(4)]
    return clip_pos, position

def geometry_shader(clip_pos: tuple, world_pos: tuple, mv_matrix: list, volume_tex: dict) -> list:
    coord = tuple(0.5 * (p + 1.0) for p in world_pos[:3])
    vel = volume_tex[coord][:3]
    
    verts = []
    # First vertex: original clip position, alpha 0
    verts.append((clip_pos, 0.0))
    
    # Second vertex: offset world position by velocity, transform to clip space, alpha 1
    end_world = [world_pos[i] + vel[i] for i in range(3)]
    end_clip = [sum(mv_matrix[i][j] * end_world[j] for j in range(3)) for i in range(3)]
    verts.append((end_clip, 1.0))
    return verts

def fragment_shader(alpha: float, brightness: float) -> tuple:
    return (brightness * alpha, 0.0, 0.0, 1.0)
```

## Operating characteristics
* Time Complexity: Linear with respect to the number of grid cells, as each cell generates one line primitive [S1, unofficial].
* Memory Complexity: Low, requiring only a vertex buffer for points and a 3D texture for velocities [S1, unofficial].
* Performance: Efficient on modern GPUs due to simple geometry generation, though dense grids can generate a large number of primitives [S1, unofficial].
* Strengths: Simple implementation, clear directional visualization, and easy integration with existing OpenGL pipelines [S1, unofficial].
* Limitations: Line segments may overlap and obscure each other in dense flows, and blending mode must be carefully chosen [S1, unofficial].
* When to Use: When directional information is critical and grid-based velocity data is available [G].
* When Not to Use: For very large datasets where performance is critical, or when continuous streamlines are preferred over discrete vectors [G].

## Background
This technique was described by Philip Rideout in 2010 as part of a blog post series on volumetric rendering [S1, unofficial]. It is presented as a straightforward method for visualizing velocity fields using modern OpenGL geometry shaders, with the accompanying code placed in the public domain [S1, unofficial].
