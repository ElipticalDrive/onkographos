# GPU Particle Rendering via Geometry Shader

Also called: Billboarded Particles, GPU billboarded particles, GPURenderParticles, Sprite Billboarding with GS

## Overview
This method renders 2D sprite quads from point primitives using a Geometry Shader (GS), allowing for efficient particle rendering on the GPU without CPU-side mesh generation [S1, unofficial]. It generates billboarded rectangles that always face the camera, utilizing a single draw call per particle type to enable distance-based culling and rendering optimization [S2, unofficial]. It differs from sibling methods like [Geometry Shader Cube Expansion](1074-geometry-shader-cube-expansion.md) by emitting flat 2D quads rather than 3D volumetric primitives, and from [Velocity Visualization via Geometry Shader Extrusion](1581-velocity-visualization-via-geometry-shader-extrusion.md) by maintaining a fixed orientation relative to the view vector rather than aligning with velocity vectors.

## How it works
**Inputs and Outputs:**
The method takes a stream of point primitives as input. Each point carries position, UV coordinates, size, and color attributes. The output is a stream of triangle strips (or independent triangles) representing 2D quads.

**Data Structures:**
*   **Vertex Shader Input (`vs_in`):**
    *   `pos`: `float4` (Position)
    *   `uv`: `float4` (UV coordinates, typically `xy` used)
    *   `size`: `float4` (Particle size, typically `x` used)
    *   `col`: `float4` (Color)
*   **Geometry Shader Output (`gs_out`):**
    *   `pos`: `float4` (Clip-space position, `SV_POSITION`)
    *   `uv`: `float2` (Interpolated UVs)
    *   `col`: `float4` (Interpolated Color)
*   **Particle State (CPU/Compute Side):**
    *   Particles are updated on the CPU rendering thread before each frame [S2, unofficial].
    *   Each particle references a `TextureAtlas` (a `GLTexture` or 2D texture) [S2, unofficial].
    *   A single integer tracks the current atlas texture index, interpolated with the next index for smooth animation transitions [S2, unofficial].
    *   Alternative storage may use `StructuredBuffer<float3>` for positions and colors in compute-driven pipelines [S1, unofficial].

**Parameters:**
*   `_Size`: Controls the size of the particle sprite. Range: $(0, 0.3)$, Default: $0.1$ [S1, unofficial].
*   `_Sprite`: The 2D texture used for the particle sprite [S1, unofficial].
*   `_ScreenParams`: Screen resolution $(width, height, \dots, \dots)$ used for aspect ratio correction [S1, unofficial].

**Steps:**
1.  **Vertex Shader:** Passes input position, UV, size, and color directly to the output structure. The position is transformed to world/view space as required by the pipeline, but the critical transformation happens in the GS.
2.  **Geometry Shader Input:** Receives a single point primitive (`input[0]`).
3.  **Clip Space Transformation:** Transform the input point position to clip space using the Model-View-Projection matrix ($MVP$).
    $$ corLoc = MVP \times input[0].pos $$
4.  **Screen-Space Offset Calculation:** Calculate screen-space offsets $dx$ and $dy$ based on the `_Size` parameter and screen aspect ratio.
    $$ dx = \_Size $$
    $$ dy = \_Size \times \frac{\_ScreenParams.x}{\_ScreenParams.y} $$
    *Note: $dx$ is not scaled by aspect ratio, while $dy$ is, to maintain square sprites in screen space [S1, unofficial].*
5.  **Quad Vertex Generation:** Generate 4 vertices for a quad by adding/subtracting $dx$ and $dy$ to $corLoc$. The vertices are appended in the following order to form a triangle strip:
    *   Vertex 0: $(-dx, dy)$, UV $(0, 0)$
    *   Vertex 1: $(dx, dy)$, UV $(1, 0)$
    *   Vertex 2: $(-dx, -dy)$, UV $(0, 1)$
    *   Vertex 3: $(dx, -dy)$, UV $(1, 1)$
    *   *Implementation Detail:* The offsets are added to the clip-space position $corLoc$. The UVs are set to $(0,0), (1,0), (0,1), (1,1)$ respectively [S1, unofficial].
6.  **Primitive Emission:** Call `outStream.RestartStrip()` after appending all 4 vertices to form an independent triangle strip (representing two triangles) [S1, unofficial].
7.  **Fragment Shader:** Samples the sprite texture using the interpolated UVs and multiplies by the vertex color.
    $$ col = tex2D(\_Sprite, i.uv) \times i.col $$

**Pseudocode:**

```python
# Vertex Shader Input Structure
struct VS_IN {
    float4 pos : POSITION;
    float4 uv : TEXCOORD0;
    float4 size : TEXCOORD1;
    float4 col : COLOR;
};

# Geometry Shader Output Structure
struct GS_OUT {
    float4 pos : SV_POSITION;
    float2 uv : TEXCOORD0;
    float4 col : COLOR;
};

# Global Parameters
uniform float4x4 UNITY_MATRIX_MVP;
uniform float _Size;
uniform float2 _ScreenParams; // x = width, y = height
uniform sampler2D _Sprite;

# Geometry Shader
[maxvertexcount(4)]
void GS(point VS_IN input[1], inout TriangleStream<GS_OUT> outStream) {
    // 1. Transform input point to clip space
    float4 corLoc = mul(UNITY_MATRIX_MVP, input[0].pos);
    
    // 2. Calculate screen-space offsets
    // dx is not scaled by aspect ratio, dy is scaled to maintain square aspect
    float dx = _Size;
    float dy = _Size * (_ScreenParams.x / _ScreenParams.y);
    
    // 3. Define the four corners of the quad in clip space
    // Offsets are applied to the clip-space position
    float4 v0 = corLoc + float4(-dx, dy, 0, 0);
    float4 v1 = corLoc + float4( dx, dy, 0, 0);
    float4 v2 = corLoc + float4(-dx, -dy, 0, 0);
    float4 v3 = corLoc + float4( dx, -dy, 0, 0);
    
    // 4. Emit vertices with UVs and Color
    GS_OUT p0, p1, p2, p3;
    
    p0.pos = v0; p0.uv = float2(0, 0); p0.col = input[0].col;
    p1.pos = v1; p1.uv = float2(1, 0); p1.col = input[0].col;
    p2.pos = v2; p2.uv = float2(0, 1); p2.col = input[0].col;
    p3.pos = v3; p3.uv = float2(1, 1); p3.col = input[0].col;
    
    // 5. Append to stream to form a triangle strip (2 triangles)
    outStream.Append(p0);
    outStream.Append(p1);
    outStream.Append(p2);
    outStream.Append(p3);
    outStream.RestartStrip();
}

# Fragment Shader
float4 FS(GS_OUT i) : SV_TARGET {
    float4 col = tex2D(_Sprite, i.uv) * i.col;
    return col;
}
```

**Edge Cases and Pitfalls:**
*   **Aspect Ratio Distortion:** The $dy$ calculation uses the screen aspect ratio ($\_ScreenParams.x / \_ScreenParams.y$) to maintain square sprites in screen space, while $dx$ does not. If not handled consistently, this creates rectangular quads if the screen aspect ratio is not 1:1 [S1, unofficial].
*   **Distance Culling:** Since particles are rendered with a single draw call per type, distance-based culling can be implemented on the CPU side by filtering particles before sending them to the GPU [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of particles. The GS expands each point to 4 vertices and 2 triangles.
*   **Memory Complexity:** Minimal GPU memory overhead for the GS itself. CPU memory holds particle state (position, velocity, color, life).
*   **Performance:** Efficient due to single draw call per particle type. Distance-based culling reduces $N$ effectively.
*   **Strengths:** Simple implementation, no CPU-side mesh generation, easy integration with texture atlases for animation.
*   **Limitations:** Billboarding requires rotation calculations in the GS or vertex shader if non-camera-facing quads are needed. Aspect ratio handling is critical for consistent sizing.
*   **When to use:** 2D particle effects, smoke, fire, magic effects where performance is critical and 3D volume is not required.
*   **When not to use:** When particles need to maintain orientation relative to world axes (non-billboarded) or when 3D volumetric interaction is required.

## Background
This technique is a standard approach in real-time graphics for rendering particle systems. It leverages the Geometry Shader stage, introduced in OpenGL 3.2 and DirectX 10, to generate geometry on the fly. The specific implementation details regarding aspect ratio correction and texture atlas interpolation are documented in community implementations [S1, unofficial][S2, unofficial].
