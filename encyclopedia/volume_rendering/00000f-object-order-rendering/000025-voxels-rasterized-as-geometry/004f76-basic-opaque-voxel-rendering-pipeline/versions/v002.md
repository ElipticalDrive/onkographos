# Basic Opaque Voxel Rendering Pipeline
Also called: Basic Opaque Rendering Pipeline, Voxel Chunk Rendering Pipeline

## Overview
This method renders opaque voxel geometry using a fixed WebGPU/WGSL pipeline [S1, unofficial][S2, unofficial]. It converts voxel data into geometric primitives and rasterizes them with a single-pass opaque shading model, distinguishing itself from sibling methods by enforcing a strict CCW front-face winding, `Depth32Float` depth buffer, and back-face culling without dynamic shader compilation or transparency handling [S1, unofficial][S2, unofficial]. It builds on [Voxels rasterized as geometry](27-voxels-rasterized-as-geometry.md).

## How it works
The pipeline converts voxel data into GPU-drawable geometry and renders it using a fixed-function shading model [S1, unofficial].

**Inputs and Outputs:**
- **Input:** Voxel chunk data (block types, positions), camera view/projection matrices, and a 2D texture array containing face textures [S1, unofficial][S2, unofficial].
- **Output:** Rasterized opaque voxel geometry with depth, plus optional normal and linear-depth debug views [S2, unofficial].

**Data Structures:**
1. **Vertex Layout (WGSL):** `position` (`vec3<f32>`, location 0), `normals` (`vec2<u32>`, location 1), `uvs` (`vec2<u32>`, location 2), `index` (`u32`, location 3) [S1, unofficial].
2. **Vertex Output (WGSL):** `clip_position` (`vec4<f32>`, builtin), `normals` (`vec2<u32>`, location 1), `uvs` (`vec2<f32>`, location 2), `index` (`u32`, location 3) [S1, unofficial].
3. **Texture Binding:** Fragment shader binds a `texture_2d_array<f32>` at group 1, binding 0, and a sampler at group 1, binding 1 [S1, unofficial].
4. **Mesh Buffer:** A single growing, reusable vertex/index buffer managed by a `MeshUploader` with an explicit byte budget; over-budget uploads are rejected [S2, unofficial].

**Pipeline Configuration:**
The pipeline is configured with fixed states [S2, unofficial]:
- Front face winding: Counter-Clockwise (CCW).
- Depth buffer: `Depth32Float`.
- Culling: Back-face culling enabled.
- Coordinate system: WebGPU NDC where $z \in [0, 1]$ [S2, unofficial].

**Rendering Steps:**
1. **Geometry Generation:** Voxel chunks are processed into mesh data. Each chunk's block types determine face indices and UV mappings to prevent texture bleeding [S1, unofficial].
2. **Buffer Upload:** Mesh data is uploaded to the `MeshUploader` buffer. If the byte budget is exceeded, the upload is rejected [S2, unofficial].
3. **Culling:** Frustum culling is applied using the Gribb–Hartmann algorithm to exclude voxels outside the camera view [S2, unofficial].
4. **Draw Call:** The GPU executes the pipeline. The vertex shader transforms local positions to clip space using the model matrix, and adjusts UVs to prevent bleeding (if `uvs.x == 0`, set to `0.001`; else subtract `0.001`; same for `uvs.y`) [S1, unofficial].
5. **Fragment Shading:** The fragment shader samples the 2D texture array using the adjusted UVs and the vertex index as the array layer index [S1, unofficial].
6. **Lighting & Debug:** Shading applies sun, sky, and baked-AO lighting models. Debug views output normals and linear depth [S2, unofficial].

## Subtopics

### [Voxel Rendering Pipeline](16079-voxel-rendering-pipeline.md)
A CPU-driven batching and GPU instancing method for rendering voxel geometry within the Sparkle engine. It decouples static geometry baking from per-frame rendering state to efficiently draw dynamic voxel scenes. Unlike renderers that update vertex buffers every frame, this pipeline reconstructs compact draw batches on the CPU and emits instanced draw commands per bucket, avoiding per-instance update commands.

### [Forward Rendering Pipeline Integration](17677-forward-rendering-pipeline-integration.md)
A method for incorporating voxel-based global illumination (VXGI) into a standard forward rendering pipeline by inserting dedicated rendering passes between the opaque and transparent geometry passes. It solves the problem of integrating volumetric lighting data into existing mesh-based renderers without requiring a full deferred rendering architecture. Unlike deferred approaches that decouple shading from lighting via a G-buffer, this method maintains the forward execution order, allowing voxel lighting to be computed and blended directly during the forward pass. It is distinguished by its seamless integration with mesh rendering, enabling developers to mix voxel and mesh representations for different objects within the same scene.

### WBOIT Rendering Pipeline
A graphics pipeline using Weighted Blended Order Independent Transparency (WBOIT) for translucent voxel meshes, sharing lighting and shadow infrastructure with non-voxel 3D rendering [S3]. It collects Model and Assembly components, separates meshes into Opaque/Cutout and Translucent categories, renders Opaque and Cutout meshes with depth testing, lighting, and shadows, renders Translucent meshes using Weighted Blended OIT accumulation, and composes the OIT result with the final frame buffer [S3].

## Operating characteristics
- **Time Complexity:** Meshing is synchronous and occurs during volume construction or explicit bake calls, not per-frame [S2, unofficial]. Rendering is $O(N)$ with respect to the number of visible voxel instances, dominated by draw call overhead and vertex processing [S2, unofficial].
- **Memory Complexity:** The vertex/index buffer grows with the number of visible faces. The `MeshUploader` maintains an explicit byte budget; over-budget uploads are rejected [S2, unofficial].
- **Strengths:** Efficient for static or slowly changing scenes due to immutable models and a fixed pipeline that avoids shader compilation overhead [S1, unofficial][S2, unofficial]. Supports built-in normal and linear-depth debug views [S2, unofficial].
- **Limitations:** Only supports opaque rendering. Lighting is static (sun, sky, baked-AO), limiting dynamic shadowing capabilities [S1, unofficial][S2, unofficial].
- **When to use:** Ideal for voxel-based games or simulations where performance is critical, lighting requirements are simple, and transparency is not needed or handled separately [S1, unofficial][S2, unofficial].
- **When not to use:** When dynamic lighting, complex shadows, or transparency are required [S1, unofficial][S2, unofficial].

## Background
This pipeline originates from the `spall` project, specifically the `spall_render` module, which provides a baseline implementation for WebGPU-based voxel rendering [S2, unofficial]. It is designed as a minimal, reference-quality implementation to validate the meshing and rendering logic before adding more complex features [S2, unofficial].
