# Voxel Rendering Pipeline

Also called: Sparkle Voxel Engine Architecture

## Overview
The Voxel Rendering Pipeline is a CPU-driven batching and GPU instancing method for rendering opaque voxel geometry within the Sparkle engine. It solves the problem of efficiently drawing large, dynamic voxel scenes by decoupling static geometry baking from per-frame rendering state. Unlike generic voxel renderers that may update vertex buffers every frame, this pipeline reconstructs compact draw batches on the CPU and emits single instanced draw commands per bucket, avoiding per-instance update commands [S1].

## How it works
The pipeline operates in two distinct phases: an offline/synchronous baking phase and a per-frame rendering phase.

### Inputs and Outputs
**Inputs:**
- `Voxel::Volume`: A mutable collection of voxel cells with definitions and orientations.
- `Assembly`: A copyable container of `Model` instances with local transforms.
- `Entity3D` registry: Contains `AssemblyRenderingComponent` instances.

**Outputs:**
- GPU draw calls (instanced) via a Metal command buffer.
- Updated SSBOs (Shader Storage Buffer Objects) containing batch data.

### Data Structures
1.  **`Voxel::Definition`**: Immutable, shareable definition of a voxel type (e.g., stone).
2.  **`Voxel::Cell`**: Lightweight copy of a `Definition` plus an orientation.
3.  **`Voxel::Volume::Builder`**: Builder pattern for constructing a `Volume`.
    -   Layout: Internal array of cells, indexed by 3D coordinates.
    -   Size: Configurable (e.g., `{16, 16, 16}`).
4.  **`Voxel::Model`**: Immutable mesh data generated by the mesher. Contains opaque and transparent meshes.
5.  **`Voxel::Assembly`**: Copyable structure containing named parts (e.g., "torso"), each referencing a `Model` and a local transform.
6.  **`AssemblyRenderingComponent`**: Attached to `Entity3D`, binds an `Assembly` without owning it.
7.  **SSBO (Batch Buffer)**: One SSBO created per non-empty bucket per frame. Contains instance data for instanced rendering.

### Steps

1.  **Volume Construction**:
    The game constructs a `Voxel::Volume` using a `Voxel::Volume::Builder`.
    ```python
    # Example construction
    definition = get_definition("stone")
    cell = Cell(definition, orientation)
    builder = VolumeBuilder(size=(16, 16, 16))
    builder.set(position=(2, 4, 1), cell=cell)
    volume = builder.build()
    ```

2.  **Mesh Baking**:
    The `VoxelMesher` synchronously bakes the `Volume` into an immutable `Model`.
    ```python
    model = mesher.bake(volume)
    ```

3.  **Assembly Composition**:
    The game composes `Models` into a copyable `Assembly`.
    ```python
    assembly = Assembly()
    assembly.add_part("torso", model, transform)
    ```
    If transforms change, the assembly state is invalidated.

4.  **Entity Binding**:
    An `AssemblyRenderingComponent` is attached to an `Entity3D`, binding the assembly.

5.  **Frame Rendering (VoxelRenderingSystem)**:
    a.  **Collection**: The system collects `AssemblyRenderingComponent` instances from the Registry.
    b.  **Batch Reconstruction**: Every frame, compact batches are reconstructed.
    c.  **SSBO Creation**: A new SSBO is created for each non-empty bucket.
    d.  **Draw Emission**: Instanced draw commands are emitted. No per-instance update commands are used.

### Parameters
-   **Bucketing Strategy**: Not specified in sources. [G] Typically involves spatial partitioning or material grouping.
-   **SSBO Size**: Determined by the number of instances in the bucket.

### Edge Cases and Pitfalls
-   **Transform Changes**: The assembly state must be invalidated when transforms change to ensure correct rendering [S1].
-   **Synchronous Baking**: The mesher operates synchronously, which may block the main thread during volume updates [S1].
-   **Memory Management**: New SSBOs are created every frame for non-empty buckets. Efficient reuse or pooling is not described and may be a performance pitfall. [G]

## Subtopics

## Operating characteristics
-   **Time Complexity**: Per-frame complexity is dominated by batch reconstruction and SSBO creation. Since no per-instance updates are used, draw call overhead is minimized.
-   **Memory Complexity**: Requires storing `Model` data (immutable) and per-frame SSBOs.
-   **Performance**: Optimized for instanced rendering. Avoids frequent CPU-GPU synchronization for instance data.
-   **Strengths**: Simple CPU-side logic, efficient GPU draw calls, clear separation of static and dynamic data.
-   **Limitations**: Synchronous baking can cause stalls. Per-frame SSBO allocation may lead to memory fragmentation or allocation overhead.
-   **When to Use**: Scenes with moderate dynamic voxel activity where per-frame CPU processing is acceptable.
-   **When Not to Use**: Highly dynamic scenes requiring frequent per-instance updates or extremely large volumes where synchronous baking is prohibitive.

## Background
The Voxel Rendering Pipeline is part of the Sparkle engine, specifically the V0.1.4 branch. It is designed for a voxel-based game, leveraging Metal for GPU rendering. The architecture emphasizes a clear separation between volume construction, mesh baking, and rendering, using an entity-component system for assembly management.
