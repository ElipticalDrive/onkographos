# Voxel Rendering Pipeline

Also called: Sparkle Voxel Engine Architecture

## Overview
The Voxel Rendering Pipeline is a CPU-driven batching and GPU instancing method for rendering voxel geometry within the Sparkle engine [S1]. It decouples static geometry baking from per-frame rendering state to efficiently draw dynamic voxel scenes [S1]. Unlike renderers that update vertex buffers every frame, this pipeline reconstructs compact draw batches on the CPU and emits instanced draw commands per bucket, avoiding per-instance update commands [S1].

## How it works
The pipeline operates in two distinct phases: an offline synchronous baking phase and a per-frame rendering phase [S1].

### Inputs and Outputs
**Inputs:**
- `Voxel::Volume`: A mutable collection of voxel cells with definitions and orientations [S1].
- `Assembly`: A copyable container of `Model` instances with local transforms [S1].
- `Entity3D` registry: Contains `AssemblyRenderingComponent` instances [S1].

**Outputs:**
- GPU instanced draw commands via a Metal command buffer [S1].
- Updated SSBOs (Shader Storage Buffer Objects) containing batch data [S1].

### Data Structures
1. `Voxel::Definition`: Immutable, shareable definition of a voxel type (e.g., stone) [S1].
2. `Voxel::Cell`: Lightweight copy of a `Definition` plus an orientation [S1].
3. `Voxel::Volume::Builder`: Builder pattern for constructing a `Volume` [S1].
   - Layout: Internal array of cells indexed by 3D coordinates [S1].
   - Size: Configurable (e.g., `{16, 16, 16}`) [S1].
4. `Voxel::Model`: Immutable mesh data generated by the mesher, containing opaque and transparent meshes [S1].
5. `Voxel::Assembly`: Copyable structure containing named parts (e.g., "torso"), each referencing a `Model` and a local transform [S1].
6. `AssemblyRenderingComponent`: Attached to `Entity3D`, binds an `Assembly` without owning it [S1].
7. SSBO (Batch Buffer): One SSBO created per non-empty bucket per frame, containing instance data for instanced rendering [S1].

### Steps
1. **Volume Construction**: The game constructs a `Voxel::Volume` using a `Voxel::Volume::Builder` [S1].
```python
# Data structures
class Definition: pass
class Cell:
    definition: Definition
    orientation: int
class Volume:
    cells: dict
class Model:
    opaque_meshes: list
    transparent_meshes: list
class Assembly:
    parts: dict
    valid: bool = True
class AssemblyRenderingComponent:
    assembly: Assembly

# Step 1: Volume Construction
stone_def = Definition()
cell = Cell(definition=stone_def, orientation=0)
volume = Volume()
volume.cells[(2, 4, 1)] = cell
```

2. **Mesh Baking**: The `VoxelMesher` synchronously bakes the `Volume` into an immutable `Model` [S1].
```python
# Step 2: Mesh Baking
model = Model(opaque_meshes=[], transparent_meshes=[])
for pos, c in volume.cells.items():
    model.opaque_meshes.append(generate_mesh(pos, c))
```

3. **Assembly Composition**: The game composes `Models` into a copyable `Assembly` [S1].
```python
# Step 3: Assembly Composition
assembly = Assembly()
assembly.parts["torso"] = (model, identity_matrix())
# If transforms change, assembly.valid = False
```

4. **Entity Binding**: An `AssemblyRenderingComponent` is attached to an `Entity3D`, binding the assembly [S1].

5. **Frame Rendering**: The `VoxelRenderingSystem` collects components via the Registry, reconstructs compact batches every frame, creates a new SSBO for each non-empty bucket, and emits instanced draw commands without per-instance update commands [S1].
```python
# Step 5: Frame Rendering
components = registry.query(AssemblyRenderingComponent)
for comp in components:
    if not comp.assembly.valid: continue
    bucket_instances = []
    for name, (m, t) in comp.assembly.parts.items():
        bucket_instances.append((m, t))
    ssbo = allocate_buffer(bucket_instances)
    draw_instanced(ssbo, len(bucket_instances))
```

### Parameters
- Bucketing Strategy: Not given in the sources. [G] Typically involves spatial partitioning or material grouping.
- SSBO Size: Determined by the number of instances in the bucket. [G]

### Edge Cases and Pitfalls
- Transform Changes: The assembly state must be invalidated when transforms change to ensure correct rendering [S1].
- Synchronous Baking: The mesher operates synchronously, which may block the main thread during volume updates [S1].
- Memory Management: New SSBOs are created every frame for non-empty buckets, which may cause allocation overhead. [G]

It distinguishes itself through CPU-side frustum culling, hardware-aware presets, and instanced rendering, integrating application logic like zone triangulation and agent trajectories. Choose it when targeting Apple Silicon with complex layered scenes.

### [Two-Pass Voxel Shading Pipeline](18311-two-pass-voxel-shading-pipeline.md)
Separates solid opaque geometry from porous translucent geometry to handle alpha blending correctly. It divides draw calls into an opaque AO phase and a translucent custom shader phase, preventing depth buffer ordering issues. Choose it when rendering mixed opacity voxel meshes.

## Operating characteristics
- Time Complexity: Per-frame complexity is dominated by batch reconstruction and SSBO creation. [G]
- Memory Complexity: Requires storing immutable `Model` data and per-frame SSBOs. [G]
- Performance: Optimized for instanced rendering, avoiding frequent CPU-GPU synchronization for instance data. [G]
- Strengths: Simple CPU-side logic, efficient GPU draw calls, and clear separation of static and dynamic data. [G]
- Limitations: Synchronous baking can cause stalls, and per-frame SSBO allocation may lead to memory fragmentation. [G]
- When to Use: Scenes with moderate dynamic voxel activity where per-frame CPU processing is acceptable. [G]
- When Not to Use: Highly dynamic scenes requiring frequent per-instance updates or extremely large volumes where synchronous baking is prohibitive. [G]

## Background
The Voxel Rendering Pipeline is part of the Sparkle engine, specifically the V0.1.4 branch [S1]. It is designed for a voxel-based game, leveraging Metal for GPU rendering [S1]. The architecture emphasizes a clear separation between volume construction, mesh baking, and rendering, using an entity-component system for assembly management [S1].
