# Hardware Instancing (Instance ID Lookup)

Also called: Instancing with Instance ID, SV_InstanceID Lookup

## Overview
Hardware Instancing (Instance ID Lookup) is a rendering technique that draws multiple instances of a geometry using a single draw call by utilizing a system-provided Instance ID to look up instance-specific data (such as transformation matrices) from a buffer or constant buffer within the vertex shader [S1, unofficial]. It differs from standard hardware instancing, which uses a second vertex buffer bound to the draw context to pass per-instance attributes directly to the vertex shader, by performing the data lookup procedurally in the shader [S1, unofficial]. This approach is less efficient than the standard method because the driver cannot inline the data, and hardware precaching on the GPU wavefront is wasted as the hardware must look up the related array entry for each vertex [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A single vertex buffer containing the base geometry (e.g., a voxel block), a buffer containing per-instance data (e.g., world matrices, visibility flags), and an instance count.
*   **Output:** Rasterized fragments for all visible instances.

**Data Structures:**
The input layout must include an element for the system value `SV_InstanceID`. In DirectX 11/12, this is defined as follows [S1, unofficial]:
```cpp
static const D3D12_INPUT_ELEMENT_DESC s_inputElementDesc[] =
{
    { "POSITION", 0, DXGI_FORMAT_R32G32B32_FLOAT, 0, 0, D3D11_INPUT_CLASSIFICATION_PER_VERTEX_DATA, 0 },
    { "NORMAL",   0, DXGI_FORMAT_R32G32B32_FLOAT, 0, D3D11_APPEND_ALIGNED_ELEMENT, D3D11_INPUT_CLASSIFICATION_PER_VERTEX_DATA, 0 },
    { "SV_InstanceID", 0, DXGI_FORMAT_R32_UINT, 0, D3D11_APPEND_ALIGNED_ELEMENT, D3D11_INPUT_CLASSIFICATION_PER_VERTEX_DATA, 0 },
};
```
The vertex shader input structure must include a `uint` field with the `SV_InstanceID` semantic [S1, unofficial]:
```hlsl
struct VS_INPUT
{
    float4 Pos : POSITION;
    float3 Normal : NORMAL;
    uint Instance : SV_InstanceID;
};
```
The per-instance data is stored in a buffer (e.g., `StructuredBuffer` in HLSL or `SSBO` in GLSL) bound to a shader binding point.

**Steps:**
1.  **Define Input Layout:** Add an input layout element for `SV_InstanceID` with format `DXGI_FORMAT_R32_UINT` and classification `D3D11_INPUT_CLASSIFICATION_PER_VERTEX_DATA` [S1, unofficial].
2.  **Modify Shader Input:** Update the vertex shader input structure to include the `SV_InstanceID` semantic [S1, unofficial].
3.  **Lookup Data:** In the vertex shader, use the `Instance` ID to index into the per-instance data buffer and retrieve transformation matrices or other properties [S1, unofficial].
4.  **Transform Vertices:** Apply the retrieved transformations to the vertex positions [S1, unofficial].
5.  **Execute Draw Call:** Issue a single instanced draw call (e.g., `DrawIndexedInstanced`) with the total instance count [S1, unofficial].

**Pseudocode:**
```python
# Vertex Shader Logic (HLSL-like)
struct VS_INPUT {
    float4 Pos : POSITION;
    float3 Normal : NORMAL;
    uint Instance : SV_InstanceID;
};

// Assume g_InstanceData is a buffer of matrices bound to the shader
StructuredBuffer<float4x4> g_InstanceData;

float4 main(VS_INPUT input) : SV_POSITION {
    // Lookup the transformation matrix for this instance
    float4x4 worldMatrix = g_InstanceData[input.Instance];
    
    // Transform the vertex
    float4 worldPos = mul(worldMatrix, input.Pos);
    
    // Return clip-space position
    return mul(ProjectionViewMatrix, worldPos);
}

# Draw Call Logic (C++/DirectX-like)
// Draw indexed instanced with 24 indices, N instances, base vertex 0, base instance 0
// The last argument (vertex buffer increment) is 0 if processing is done on GPU
pImmCtx->DrawIndexedInstanced(24, N, 0, 0, 0);
```

**Parameters:**
*   `Instance Count`: The total number of instances to draw. Must match the size of the per-instance data buffer [S1, unofficial].
*   `Base Instance Index`: Offset into the instance data buffer. Typically 0 [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Performance:** Using `SV_InstanceID` to look up data is less efficient than using a second vertex buffer because the driver cannot inline the data, and hardware precaching/setup on the GPU wavefront is wasted [S1, unofficial].
*   **Semantic Limitation:** The `SV_InstanceID` can only be added to the input layout of a vertex shader (or geometry/tessellation shaders) once per draw call [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N \cdot V)$, where $N$ is the number of instances and $V$ is the number of vertices per instance. The lookup cost is incurred per vertex.
*   **Memory Complexity:** $O(N)$ for the per-instance data buffer.
*   **Performance:** Less efficient than standard instancing with a second vertex buffer. The hardware must perform a memory lookup for each vertex rather than loading the instance data once per vertex shader invocation [S1, unofficial].
*   **Strengths:** Simplifies the draw call setup by avoiding the need to bind a second vertex buffer. Useful when instance data is dynamic or complex.
*   **Limitations:** Higher memory bandwidth usage due to per-vertex lookups. Driver cannot optimize data loading as effectively as with vertex buffers.
*   **When to Use:** When instance data is small or when the overhead of managing a second vertex buffer is undesirable, and performance is not critical.
*   **When Not to Use:** When rendering large numbers of instances with simple transformations (e.g., translation matrices), where standard instancing with a second vertex buffer is significantly more efficient.

## Background
This technique is a variation of hardware instancing, specifically adapted for scenarios where per-instance data is accessed via a shader lookup rather than a dedicated vertex buffer. It is commonly discussed in the context of DirectX 11/12 programming [S1, unofficial].
