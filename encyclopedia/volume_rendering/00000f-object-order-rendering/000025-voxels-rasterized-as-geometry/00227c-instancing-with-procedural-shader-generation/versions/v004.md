# Instancing with Procedural/Shader Generation

Also called: Procedural Instancing, Shader-Driven Instancing, GPU Procedural Voxel Rendering

## Overview
Instancing with Procedural/Shader Generation renders volumetric data by submitting a single base primitive (typically a cube or point) to the GPU and generating per-instance geometry, attributes, or visibility logic within the vertex, geometry, or fragment shaders [S1, S2, S3, unofficial]. It solves the CPU bottleneck associated with generating and uploading millions of individual voxel meshes by moving the computational load to the GPU, allowing for dynamic, data-driven voxel visualization at interactive frame rates [S1, S2, unofficial]. It differs from standard instancing by decoupling the geometric representation from static CPU-side buffers, instead deriving voxel positions, sizes, and materials from procedural noise, grid indices, or GPU-accessible buffers (SSBOs) on-the-fly [S1, S2, S3, unofficial].

## Shared principles
The family shares the fundamental mechanism of converting scalar field data into geometric primitives that are submitted to the graphics pipeline.

1.  **Primitive Generation**: Each occupied voxel is represented by one or more geometric primitives. The most common representation is a cube (6 faces, 24 vertices for flat shading, or 8 vertices for shared shading) or a set of quads representing visible faces [S1, S3, S4, unofficial].
2.  **Coordinate Transformation**: Voxel indices $(i, j, k)$ are transformed into world space. For a dense grid with bounds $P_{min}$ and $P_{max}$ and dimension $N_{dim}$, the world position $P_{world}$ of a voxel center is calculated as [S4, unofficial]:
    $$
    P_{world} = P_{min} + \frac{I_{voxel}}{N_{dim}} \times (P_{max} - P_{min})
    $$
    For unit voxels, this simplifies to $P_{world} = I_{voxel} \times V_{size}$, where $V_{size}$ is the voxel dimension [S2, S4, unofficial].
3.  **Rasterization**: The generated primitives are transformed into clip space using the Model-View-Projection (MVP) matrix and rasterized. Visibility is determined by the depth buffer (z-buffer) or a back-to-front painter's algorithm if transparency is required [S2, S3, unofficial].
4.  **Culling**: To manage performance, frustum culling is applied to exclude voxels outside the camera view [S2, S4, unofficial]. Back-face culling is often enabled to discard faces oriented away from the camera, calculated by the dot product of the view-space normal and the view vector [S2, unofficial].

## Subtopics

### [Surface-based Instancing with Noise Modulation](1582-surface-based-instancing-with-noise-modulation.md)
Generates high-density point clouds from parametric surface primitives to approximate volumetric effects, such as smoke or fire, at interactive or near-real-time frame rates. It differs from standard surface rendering by treating the surface as a distribution of discrete particles rather than a continuous triangle mesh, and from pure particle systems by deriving point positions and attributes from a structured surface parameterization ($s,t$) rather than independent physical simulation.

### [3D Gaussian Splatting via Instancing](1586-3d-gaussian-splatting-via-instancing.md)
Renders volumetric data or 2D Gaussian projections by submitting a single instanced draw call per Gaussian primitive, utilizing the standard hardware vertex/fragment pipeline to avoid the memory traffic and sorting overhead of tile-based rasterizers. It solves the problem of efficiently rendering millions of semi-transparent primitives by dynamically sizing quads based on opacity and computing the Gaussian decay in the fragment shader, setting itself apart from its parent [Instancing with Procedural/Shader Generation](2794-instancing-with-procedural-shader-generation.md) by explicitly handling the spatial extent and opacity cutoff of Gaussian kernels.

### [GPU Instancing with Indirect Draw Calls](2205-gpu-instancing-with-indirect-draw-calls.md)
Efficiently draws millions of identical meshes (voxels) by issuing a single draw command that reads instance counts and parameters from a GPU-accessible buffer, allowing the GPU to generate draw commands itself. Unlike standard GPU instancing which requires CPU-side iteration to set up per-instance data or multiple draw calls, this method batches the rendering of all instances into one or few calls, significantly reducing CPU-GPU synchronization overhead. It rasterizes explicit cube geometry via indirect commands, contrasting with [Surface-based Instancing with Noise Modulation](1582-surface-based-instancing-with-noise-modulation.md) and [3D Gaussian Splatting via Instancing](1586-3d-gaussian-splatting-via-instancing.md).

### [Procedural Particle Rendering](2926-procedural-particle-rendering.md)
Generates particle attributes (position, velocity, color, size) on-the-fly using a seeded random number generator (RNG) rather than storing explicit particle data in memory buffers. This method solves the memory overhead and synchronization issues of traditional particle systems by computing each particle's state deterministically from its ID and time. It is distinct from [Procedural Point Rendering with Billboard Transformation](6422-procedural-point-rendering-with-billboard-transformation.md) in its reliance on temporal interpolation of uniformly distributed attributes and explicit physics simulation for position, rather than static billboard transformations.

### [WebGL 2 Hardware Instancing](3152-webgl-2-hardware-instancing.md)
Sends a single base primitive (typically a 2x2x2 cube) to the GPU and executes `gl.drawElementsInstanced` to render hundreds of thousands of copies simultaneously. It solves the CPU bottleneck associated with issuing individual draw calls for each voxel by packing translation, scaling, and color data into flat typed arrays. Unlike surface-based methods, it renders the full volume geometry directly, relying on depth buffering for visibility.

### [Geometry Shader Advanced Instancing for Cubes](4576-geometry-shader-advanced-instancing-for-cubes.md)
Uses a geometry shader to generate cube meshes from instanced points, optimizing for visibility by emitting at most 12 vertices (3 quads) per cube. It leverages backface culling and frustum culling in projection space to reduce the number of primitives submitted to the rasterizer. Unlike methods that generate full 24-vertex cubes, this approach exploits the fact that backface culling always removes one of two opposite faces, allowing the shader to emit only the visible faces.

### [Procedural Point Rendering with Billboard Transformation](6422-procedural-point-rendering-with-billboard-transformation.md)
Renders a sparse set of surface points as billboards using GPU procedural instancing, transforming grid-based point cloud data into world space and orienting each primitive to face the camera. It differs from standard voxel rasterization by decoupling the geometric representation from the dense grid structure, allowing for efficient rendering of isosurface samples or particle-like data without generating full voxel cubes.

### [Buffer-Based Instancing (SSBO/Instance Buffers)](6501-buffer-based-instancing-ssbo-instance-buffers.md)
Decouples geometric data from the CPU by storing voxel attributes (position, material, shape) in GPU-accessible Shader Storage Buffer Objects (SSBOs) or structured buffers. It solves the performance bottleneck of CPU-side mesh generation by allowing the vertex shader to procedurally generate voxel geometry (typically cubes or blocks) on-the-fly using data fetched directly from these buffers. It differs from [Instancing with Procedural/Shader Generation](2794-instancing-with-procedural-shader-generation.md) by explicitly leveraging large, mutable GPU buffers for instance data rather than relying solely on uniform arrays or texture lookups, and from [GPU Instancing with Indirect Draw Calls](2205-gpu-instancing-with-indirect-draw-calls.md) by focusing on the data layout and vertex-shader-driven primitive assembly rather than just the draw command mechanism.

### Indirect Draw Argument Setting
- [S1, unofficial] A compute shader kernel that sets up indirect draw arguments by multiplying vertex and instance counts and setting start indices.
- [S1, unofficial] Multiply the first element of indirectArgsBuffer by vertexCountMultiplier: `indirectArgsBuffer[0] *= vertexCountMultiplier;`
- [S1, unofficial] Multiply the second element of indirectArgsBuffer by instanceCountMultiplier: `indirectArgsBuffer[1] *= instanceCountMultiplier;`
- [S1, unofficial] Set the third element to startVertex: `indirectArgsBuffer[2] = startVertex;`
- [S1, unofficial] Set the fourth element to startInstance: `indirectArgsBuffer[3] = startInstance;`
- [S1, unofficial] Set the fifth element to 0: `indirectArgsBuffer[4] = 0;`
- [S1, unofficial] Buffers and Constants: indirectArgsBuffer (RWStructuredBuffer<uint>), vertexCountMultiplier (uint), instanceCountMultiplier (uint), startVertex (uint), startInstance (uint).

### Sphere Impostors for DEM Pebbles
- [S3, unofficial] Rendering of Discrete Element Method (DEM) pebble beds using instanced sphere impostors. Each pebble is drawn as a quad with an exact orthographic ray-sphere hit test in the fragment shader, providing sphere shading and depth.
- [S3, unofficial] Draw instanced quads: For each pebble, submit an instance of a quad geometry. The shader performs an exact orthographic ray-sphere intersection test per fragment.
- [S3, unofficial] Render to offscreen target: Draw the impostors into an offscreen target, which egui then displays. This allows interaction (orbit, zoom) while positions stream.
- [S3, unofficial] Scale: 27,000 pebbles are rendered at interactive rates.
- [S3, unofficial] CPU Overhead: Submitting a frame takes 1.2-1.3 ms of CPU time.
- [S3, unofficial] Fallback: If no wgpu device is available, egui discs are used as the fallback rendering method.

## Background
The technique evolved from early GPU instancing APIs (such as OpenGL ARB_vertex_buffer_object and later WebGL 2.0) which allowed batching of identical draw calls [S1, S2, unofficial]. It gained prominence in real-time fluid and particle simulation rendering, where the dynamic nature of the data made CPU-side mesh generation prohibitive [S2, unofficial]. Modern implementations leverage compute shaders to generate instance data and indirect draw calls to minimize driver overhead, enabling the rendering of millions of voxels or particles [S1, S3, unofficial]. It is widely used in scientific visualization, VFX for smoke/fire approximation, and real-time terrain or voxel-based games [S1, S2, S3, unofficial].
