# Intensity-based Sparse Voxel Storage

Also called: Detail Coefficient Representation (8-byte), Histogram-based Voxel Buffer

## Overview
Intensity-based Sparse Voxel Storage is a method for representing volumetric data by sorting voxels according to their intensity values and using a histogram to index contiguous runs of identical intensity. It solves the problem of redundant storage in naive voxel representations by treating intensity as a run-length encoding [S1]. It sets itself apart from sibling methods like [Binary Volume Rendering](1015-binary-volume-rendering.md) by supporting multi-level intensity rather than binary opacity, and from [Naive Voxel Rendering](1103-naive-voxel-rendering.md) by eliminating per-voxel intensity storage through buffer sorting and histogram indexing [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A set of voxels, each defined by spatial coordinates $(x, y, z)$ and an intensity value $I$.
*   **Output:** A sorted voxel buffer and a histogram structure, ready for rendering via `glDrawArrays`.

**Data Structures:**
1.  **Voxel Buffer:** A continuous memory region (created via `ARB_vertex_buffer_object`) storing voxel coordinates.
    *   *Naive Layout:* 8 bytes per voxel. Stores $I, x, y, z$ as shorts (2 bytes each).
    *   *Optimized Layout:* 6 bytes per voxel. Stores $x, y, z$ as shorts (2 bytes each). Intensity is not stored per voxel.
2.  **Histogram:** An array of structures, one per unique intensity level. Each entry contains:
    *   `begin`: Offset (index) in the Voxel Buffer where voxels of this intensity start.
    *   `end`: Offset (index) in the Voxel Buffer where voxels of this intensity end.

**Steps:**
1.  **Sort:** Sort all voxels in the volume by their intensity value $I$ in ascending (or descending) order.
2.  **Build Histogram:** Iterate through the sorted voxel list. For each unique intensity value, record the index of the first voxel (`begin`) and the index of the last voxel (`end`) in the sorted buffer.
3.  **Render Loop:** For each unique intensity value $I_k$:
    a.  Retrieve `begin` and `end` from the histogram for $I_k$.
    b.  Set a shader constant or texture coordinate to the value $I_k$. This value applies to all voxels in the current span.
    c.  Invoke `glDrawArrays` (or equivalent) with the vertex buffer, using `begin` and `end` as the start and count parameters. This sends only the voxels with intensity $I_k$ to the vertex processor.

**Formulas:**
*   Memory per voxel (Optimized): $M = 2 \times 3 = 6$ bytes.
*   Theoretical Volume Support: With 16-bit coordinates ($x, y, z$), the maximum grid dimension is $2^{16} = 65536$. Thus, the theoretical volume support is $65536^3$ voxels [S1].

**Parameters:**
*   Coordinate precision: 16-bit shorts (GL_SHORT) [S1].
*   Intensity precision: Not stored per voxel; determined by the number of unique levels in the histogram [S1].

**Edge Cases and Pitfalls:**
*   **Redundancy:** Storing intensity with each voxel is redundant because the histogram acts as run-length-encoding [S1].
*   **Memory Limits:** While theoretically supporting $65536^3$ voxels, practical limits are lower due to hardware memory constraints [S1].
*   **Bit Packing Alternative:** If 4 bytes per voxel are required, coordinates can be packed into 32 bits (e.g., 12 bits for X, 10 for Y, 10 for Z, allowing $4096 \times 1024 \times 1024$). Unpacking requires bit shifts or emulation via multiplication and floor functions if the GPU lacks bitwise operators [S1].

## Subtopics

### LiteVoxel
LiteVoxel is an extension to SVRaster that introduces three modules to counteract low-frequency underfitting and memory overgrowth [S2, unofficial]. It matches SVRaster’s perceptual quality at 40–60% of peak VRAM, with less than 1% loss in PSNR, SSIM, or LPIPS [S2, unofficial]. Specifically, it reduces peak VRAM by up to 60% (e.g., from 12 GB to 7.9 GB) while maintaining PSNR ≈ 32.13 dB and SSIM ≈ 0.937 [S2, unofficial]. Its components are:
1.  **Inverse-Sobel Reweighted Loss:** The ground-truth image $S$ is filtered with a Sobel operator to produce $S_2$. A per-pixel weight $S_3$ is computed using a gamma-ramped exponent to become low-frequency-sensitive. The schedule shifts gradient focus to flat regions after geometric stabilization [S2, unofficial].
2.  **Depth-Quantile Pruning:** Voxels are partitioned into depth bins $S_5$. Pruning thresholds are set adaptively via empirical quantiles of the maximum blending weight per bin. EMA-hysteresis “guards,” contour dilation, and per-step deletion caps stabilize pruning and prevent VRAM inflation near silhouettes [S2, unofficial].
3.  **Priority-Driven Subdivision:** Ray-footprint eligibility restricts splits to voxels where resolution is warranted. Per-voxel priorities favor far geometry, and subdivision enforces a global growth budget [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** Sorting voxels by intensity is $O(N \log N)$ where $N$ is the number of voxels. Histogram construction is $O(N)$. Rendering requires one draw call per unique intensity level.
*   **Memory Complexity:** $O(N)$ for the voxel buffer. The histogram size is proportional to the number of unique intensity levels.
*   **Measured Performance:** Not given in the sources for this specific method. LiteVoxel (a related variant) achieves 10× speedup compared to uniform-grid ray casting and neural-free voxel methods [S2, unofficial].
*   **Strengths:** Major speedup for large volumes due to reduced memory bandwidth (6 bytes/voxel vs 8+). Efficient culling of empty space via histogram indexing.
*   **Limitations:** Requires sorting, which can be costly for dynamic data. Theoretical volume limits are constrained by coordinate bit-width. Practical memory limits are lower than theoretical maximums [S1].
*   **When to use:** Static or semi-static volumes with discrete or quantized intensity levels where memory bandwidth is a bottleneck.
*   **When not to use:** Highly dynamic volumes where sorting overhead is prohibitive. Continuous intensity fields without quantization may result in many unique levels, reducing the efficiency of the histogram approach.

## Background
Originated in the context of multiresolution MIP rendering of large volumetric data accelerated on graphics hardware [S1]. It leverages the `ARB_vertex_buffer_object` extension to cache voxel data in high-performance graphics memory, allowing static buffers to be filled once and used many times [S1]. The method was proposed to address the inefficiency of storing intensity with every voxel, recognizing that the histogram provides a form of run-length encoding [S1].
