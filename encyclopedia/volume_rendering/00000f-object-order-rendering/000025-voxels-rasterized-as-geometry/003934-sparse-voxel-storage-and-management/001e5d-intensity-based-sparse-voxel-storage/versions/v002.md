# Intensity-based Sparse Voxel Storage

Also called: Detail Coefficient Representation (8-byte), Histogram-based Voxel Buffer

## Overview
Intensity-based Sparse Voxel Storage is a data layout technique for object-order volume rendering that eliminates redundant intensity storage by leveraging histogram-based run-length encoding. It solves the problem of excessive memory bandwidth and storage overhead when transmitting voxel attributes to the graphics pipeline. Unlike [Naive Voxel Rendering](1103-naive-voxel-rendering.md), which stores intensity with every voxel, this method sorts voxels by intensity and uses a histogram to define rendering spans, allowing the shader to retrieve intensity from a constant or texture coordinate rather than per-vertex data.

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D scalar field (volume data) where each voxel has an intensity value and spatial coordinates $(x, y, z)$.
*   **Output:** A GPU vertex buffer containing sorted voxel positions and a host-side histogram structure mapping intensity levels to buffer offsets.

**Data Structures:**
1.  **Voxel Buffer:** A continuous array of vertex attributes stored in GPU memory (via `ARB_vertex_buffer_object`).
    *   *Layout (Naive/8-byte):* Each entry stores intensity, $x$, $y$, and $z$ as 16-bit shorts (`GL_SHORT`). Total: 8 bytes per voxel.
    *   *Layout (Optimized/6-byte):* Voxels are sorted by intensity. The buffer stores only $x$ and $z$ coordinates (or $x, y, z$ packed into fewer bits). Intensity is not stored per voxel.
2.  **Histogram:** An array of structures, one per unique intensity level (or bin).
    *   *Fields:* `begin_offset` (index in voxel buffer), `end_offset` (index in voxel buffer).
    *   *Purpose:* Acts as a run-length encoding index, defining the range of voxels sharing a specific intensity value.

**Steps:**
1.  **Sort:** Sort all voxels in the volume data by their intensity value.
2.  **Build Histogram:** Iterate through the sorted voxels. For each unique intensity value, record the starting and ending indices in the sorted array.
3.  **Pack Coordinates:**
    *   *Option A (8-byte):* Store intensity and coordinates $(x, y, z)$ as shorts.
    *   *Option B (6-byte):* Store only coordinates. If memory is constrained to 4 bytes (two shorts), pack coordinates into a 32-bit integer using bit shifts (e.g., 12 bits for X, 10 for Y, 10 for Z, supporting $4096 \times 1024 \times 1024$). [S1]
4.  **Upload:** Transfer the voxel buffer to GPU memory using `ARB_vertex_buffer_object`.
5.  **Render:**
    *   Iterate through each intensity level in the histogram.
    *   Set a shader constant or texture coordinate to the current intensity value.
    *   Invoke `glDrawArrays` (or equivalent) using the `begin_offset` and `end_offset` from the histogram to draw only the voxels with that intensity.

**Pseudocode:**
```python
# Assume volume_data is a list of (x, y, z, intensity) tuples
# Coordinates are normalized to 0..65535 range for 16-bit storage

def prepare_intensity_storage(volume_data):
    # Step 1: Sort voxels by intensity
    sorted_voxels = sorted(volume_data, key=lambda v: v.intensity)
    
    # Step 2: Build histogram
    histogram = {}
    current_intensity = None
    begin_idx = 0
    
    for i, voxel in enumerate(sorted_voxels):
        if voxel.intensity != current_intensity:
            if current_intensity is not None:
                histogram[current_intensity] = (begin_idx, i)
            current_intensity = voxel.intensity
            begin_idx = i
            
    # Close the last bin
    if current_intensity is not None:
        histogram[current_intensity] = (begin_idx, len(sorted_voxels))
        
    # Step 3: Pack coordinates into buffer
    # Using 6-byte layout: x, y, z as shorts (assuming 16-bit coords)
    # In practice, x, y, z might be packed into fewer bits if 4-byte limit is enforced
    voxel_buffer = []
    for voxel in sorted_voxels:
        # Pack x, y, z into shorts. 
        # Example: 16-bit shorts for each coordinate
        packed = (voxel.x, voxel.y, voxel.z) 
        voxel_buffer.append(packed)
        
    return voxel_buffer, histogram

def render_intensity_buffer(voxel_buffer, histogram, gl_draw_arrays, set_shader_constant):
    # Step 5: Render
    for intensity, (begin, end) in histogram.items():
        # Set intensity as a shader constant for this batch
        set_shader_constant("u_intensity", intensity)
        
        # Draw only the voxels with this intensity
        # count = end - begin
        gl_draw_arrays(
            primitive_type=GL_POINTS, # or GL_QUADS/GL_TRIANGLES depending on parent
            first=begin,
            count=end - begin
        )
```

**Parameters:**
*   **Coordinate Bit Depth:** Typically 16-bit (`GL_SHORT`) per coordinate. Can be reduced to 12/10/10 bit packing for 4-byte total storage if hardware lacks bit-shift instructions, requiring emulation via multiplication and floor functions. [S1]
*   **Intensity Resolution:** Determined by the number of unique values or bins in the histogram.

**Edge Cases and Pitfalls:**
*   **Redundancy:** Storing intensity with each voxel is redundant and wastes memory/bandwidth. The histogram acts as run-length encoding. [S1]
*   **Memory Limits:** Theoretically supports $65536^3$ voxels with 6-byte storage, but practical limits are lower due to VRAM constraints. [S1]
*   **Bit-Packing Emulation:** On GPUs without native bit-shift/logical operators, unpacking packed coordinates requires emulation using multiplication by fractions and `floor` operations, which may impact performance. [S1]

## Subtopics

### LiteVoxel
LiteVoxel is an extension to SVRaster that introduces three modules to counteract low-frequency underfitting and memory overgrowth in sparse voxel rasterization. It uses an Inverse-Sobel Reweighted Loss to shift gradient focus to flat regions after geometric stabilization, Depth-Quantile Pruning with EMA-hysteresis guards to prevent VRAM inflation near silhouettes, and Priority-Driven Subdivision to restrict splits to voxels where resolution is warranted. LiteVoxel matches SVRaster’s perceptual quality at 40–60% of peak VRAM, reducing peak VRAM by up to 60% (down to 7.9 GB from 12 GB) while maintaining PSNR ≈ 32.13 dB and SSIM ≈ 0.937. [S2, unofficial]

## Operating characteristics
*   **Time Complexity:** Sorting voxels is $O(N \log N)$ where $N$ is the number of voxels. Histogram construction is $O(N)$. Rendering time is proportional to the number of unique intensity levels times the number of voxels per level, but batched efficiently via `glDrawArrays`.
*   **Memory Complexity:** $O(N)$ for the voxel buffer. With 6-byte optimization, memory usage is reduced by 25% compared to the naive 8-byte approach.
*   **Performance:** Provides a major speedup for large volumes by reducing data transfer rates and draw call overhead per intensity level. [S1]
*   **Strengths:** Significant reduction in memory footprint and bandwidth; efficient for volumes with discrete or binned intensity values.
*   **Limitations:** Requires sorting and histogram construction on the CPU (or GPU compute) before rendering. Not suitable for dynamic volumes where intensity changes frequently per frame. Practical memory limits are lower than theoretical maximums.

## Background
This method was described in the context of multiresolution MIP rendering of large volumetric data accelerated on graphics hardware. It leverages the `ARB_vertex_buffer_object` extension to cache data in high-performance graphics memory. The approach was proposed to address the inefficiency of storing intensity with every voxel, treating the histogram as a form of run-length encoding. [S1]
