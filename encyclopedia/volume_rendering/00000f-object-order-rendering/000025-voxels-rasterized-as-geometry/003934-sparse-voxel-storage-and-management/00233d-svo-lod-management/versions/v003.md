# SVO LOD Management

Also called: Graphics Component SVO LOD Management

## Overview
SVO LOD Management is a technique for managing the Level of Detail (LOD) of Sparse Voxel Octrees (SVOs) in a graphics rendering pipeline by pre-generating and caching voxelized geometry at multiple octree depths. It solves the performance bottleneck of dynamic voxelization by separating asset preparation from rendering, allowing the system to switch between pre-computed geometric representations (Vertex Buffer Objects) based on camera distance or user preference. It differs from real-time SVO ray-tracing [6811-sparse-voxel-octree-svo-lod-pipeline.md] by relying on rasterization of static geometry caches rather than per-frame ray traversal, and from basic sparse voxel storage [8435-sparse-voxel-storage-and-management.md] by explicitly managing multiple resolution layers of the octree data.

## How it works
**Inputs and Outputs:**
*   **Input:** A pre-processed Sparse Voxel Octree asset defined by a maximum depth $D_{max}$ and associated octree files containing voxel data (position, color, normal).
*   **Output:** A set of OpenGL Vertex Array Objects (VAOs) and Vertex Buffer Objects (VBOs), one for each LOD level from 1 to $D_{max}$, and a bounding sphere radius for culling.

**Data Structures:**
The method maintains a component state for each SVO instance:
*   `maxSvoDepth_`: `uint8_t`, the maximum depth of the octree.
*   `currentSvoLodIdx_`: `uint8_t`, the index of the currently active LOD (0-based).
*   `boundingSphereRadius_`: `float`, the radius of the bounding sphere enclosing the voxel data.
*   `visible_`: `bool`, visibility flag.
*   `VAOs_`: Array of `GLuint`, storing the vertex array object for each LOD level.
*   `octreeFiles_`: Array of pointers to `OctreeFile` objects, each containing header and voxel data.

**Numbered Steps:**

1.  **Initialization:**
    *   Set `boundingSphereRadius_` to $0.0$.
    *   Set `visible_` to `true`.
    *   Retrieve `maxSvoDepth_` from the rendering system configuration.
    *   Set `currentSvoLodIdx_` to `maxSvoDepth_ - 1` (defaulting to the highest resolution).

2.  **Geometry Generation (Per LOD Level):**
    For each depth $d$ from $1$ to `maxSvoDepth_`:
    *   Create an `OctreeFile` object for depth $d$.
    *   Generate a new VAO and VBO.
    *   Bind the VAO and VBO.
    *   Load the voxel data from `OctreeFile::Data` into the VBO using `GL_STATIC_DRAW`.
    *   Configure three vertex attribute arrays (offsets derived from `OctreeFile::Data`):
        *   Position: 3 floats.
        *   Color: 3 floats.
        *   Normal: 3 floats.
    *   Store the resulting VAO ID in `VAOs_[d-1]`.

3.  **Bounding Sphere Calculation:**
    *   Initialize `minX, minY, minZ` to $+\infty$ and `maxX, maxY, maxZ` to $-\infty$.
    *   Iterate through the voxel data of the maximum depth octree (`octreeFiles_[maxSvoDepth_-1]`), starting from index $1$ (skipping the root voxel at index $0$).
    *   For each voxel, if its local position $(x, y, z)$ is not $(-0.5, -0.5, -0.5)$:
        *   Update `minX = min(minX, x)`, `maxX = max(maxX, x)`.
        *   Update `minY = min(minY, y)`, `maxY = max(maxY, y)`.
        *   Update `minZ = min(minZ, z)`, `maxZ = max(maxZ, z)`.
    *   Calculate the center of the bounding box:
        $$
        C_x = \frac{minX + maxX}{2}, \quad C_y = \frac{minY + maxY}{2}, \quad C_z = \frac{minZ + maxZ}{2}
        $$
    *   Calculate the radius as the distance from the center to the maximum corner:
        $$
        boundingSphereRadius_ = \sqrt{(maxX - C_x)^2 + (maxY - C_y)^2 + (maxZ - C_z)^2}
        $$

4.  **LOD Switching:**
    *   To set a specific LOD level $L$ (1-based):
        *   Set `currentSvoLodIdx_` to $L - 1$.
        *   Trigger a recalculation of the total voxel count in the rendering system.
    *   To decrease LOD (coarser):
        *   If `currentSvoLodIdx_` is $0$, wrap around to `maxSvoDepth_ - 1` (finest).
        *   Otherwise, decrement `currentSvoLodIdx_`.
    *   To increase LOD (finer):
        *   If `currentSvoLodIdx_` is `maxSvoDepth_ - 1`, wrap around to $0$ (coarsest).
        *   Otherwise, increment `currentSvoLodIdx_`.

**Pseudocode:**

```python
class SVOLodManager:
    def __init__(self, max_svo_depth: int):
        self.max_svo_depth_ = max_svo_depth
        self.current_svo_lod_idx_ = max_svo_depth - 1
        self.bounding_sphere_radius_ = 0.0
        self.visible_ = True
        self.vaos = [0] * max_svo_depth
        self.octree_files = [None] * max_svo_depth

    def initialize_geometry(self):
        for d in range(1, self.max_svo_depth_ + 1):
            # Create OctreeFile for depth d
            octree_file = OctreeFile(d)
            self.octree_files[d-1] = octree_file
            
            # Generate VAO and VBO
            vao = gl_create_vao()
            vbo = gl_create_vbo()
            gl_bind_vao(vao)
            gl_bind_vbo(vbo)
            
            # Load data
            data = octree_file.get_data()
            gl_buffer_data(vbo, data, gl_static_draw)
            
            # Setup attributes
            # Assuming data layout has position, color, normal as 3 floats each
            gl_enable_vertex_attrib_array(0) # Position
            gl_vertex_attrib_pointer(0, 3, gl_float, False, stride, offset_pos)
            
            gl_enable_vertex_attrib_array(1) # Color
            gl_vertex_attrib_pointer(1, 3, gl_float, False, stride, offset_color)
            
            gl_enable_vertex_attrib_array(2) # Normal
            gl_vertex_attrib_pointer(2, 3, gl_float, False, stride, offset_normal)
            
            self.vaos[d-1] = vao

    def calculate_bounding_sphere(self):
        min_x, min_y, min_z = float('inf'), float('inf'), float('inf')
        max_x, max_y, max_z = float('-inf'), float('-inf'), float('-inf')
        
        # Access max depth data
        max_depth_data = self.octree_files[self.max_svo_depth_ - 1].get_data()
        
        # Iterate starting from index 1
        for i in range(1, len(max_depth_data)):
            voxel = max_depth_data[i]
            x, y, z = voxel.position
            
            # Skip root-like placeholder
            if x == -0.5 and y == -0.5 and z == -0.5:
                continue
                
            min_x = min(min_x, x)
            max_x = max(max_x, x)
            min_y = min(min_y, y)
            max_y = max(max_y, y)
            min_z = min(min_z, z)
            max_z = max(max_z, z)
            
        # Calculate center
        cx = (min_x + max_x) / 2.0
        cy = (min_y + max_y) / 2.0
        cz = (min_z + max_z) / 2.0
        
        # Calculate radius to max corner
        dx = max_x - cx
        dy = max_y - cy
        dz = max_z - cz
        self.bounding_sphere_radius_ = sqrt(dx*dx + dy*dy + dz*dz)

    def set_lod(self, lod: int):
        # lod is 1-based
        self.current_svo_lod_idx_ = lod - 1
        rendering_system.recalculate_voxel_count()

    def decrease_level_of_detail(self):
        if self.current_svo_lod_idx_ == 0:
            self.current_svo_lod_idx_ = self.max_svo_depth_ - 1
        else:
            self.current_svo_lod_idx_ -= 1

    def increase_level_of_detail(self):
        if self.current_svo_lod_idx_ == self.max_svo_depth_ - 1:
            self.current_svo_lod_idx_ = 0
        else:
            self.current_svo_lod_idx_ += 1

    def get_current_lod(self) -> int:
        return self.current_svo_lod_idx_ + 1
```

**Parameters:**
*   `maxSvoDepth_`: Typically determined by the source asset's voxelization resolution. Not given in the sources.
*   `lod`: Integer, 1-based index.

**Edge Cases and Pitfalls:**
*   **Root Voxel Skip:** The algorithm explicitly skips the voxel at index $0$ if its position is $(-0.5, -0.5, -0.5)$. Failure to skip this may result in an incorrect bounding sphere if the root is not part of the visible geometry [S1, unofficial].
*   **Wrap-around Logic:** The `decreaseLevelOfDetail` and `increaseLevelOfDetail` functions implement wrap-around behavior (coarsest to finest and vice versa). This may not be suitable for distance-based LOD where monotonic switching is required [S1, unofficial].
*   **Static Data:** The VBOs are created with `GL_STATIC_DRAW`. If the underlying SVO data changes (e.g., animation), the buffers must be updated or regenerated, which this method does not handle automatically [S1, unofficial].

## Subtopics

### [Sparse Voxel Octree (SVO) LOD Pipeline](6811-sparse-voxel-octree-svo-lod-pipeline.md)
A unified production pipeline that converts complex, animated assets into a consistent SVO representation. It addresses the challenge of efficiently populating, animating, and ray-tracing dynamic scenes by replacing direct geometry processing with a pre-voxelized, LOD-managed cache. Unlike standard real-time SVO ray-tracing which often requires dynamic voxelization per frame, this pipeline separates asset preparation from rendering, using stored surface data and procedural blend shapes to animate static SVOs, thereby reducing memory footprint and voxelization time.

## Operating characteristics
*   **Time Complexity:** Initialization is $O(N \cdot D)$ where $N$ is the number of voxels at max depth and $D$ is the max depth, due to geometry generation for all levels. LOD switching is $O(1)$ as it merely changes the active VAO index.
*   **Memory Complexity:** $O(N \cdot D)$ for storing VBOs for all LOD levels. This is significantly higher than dynamic voxelization which only stores one resolution, but allows for instant LOD switching without runtime computation.
*   **Measured Performance:** Not given in the sources.
*   **Strengths:** Instant LOD switching; no runtime voxelization cost; simplified rendering pipeline (standard rasterization).
*   **Limitations:** High memory usage due to storing multiple LODs; static geometry (no dynamic updates without buffer regeneration); wrap-around LOD logic may be unintuitive for distance-based culling.
*   **When to use:** Static or slowly changing assets where instant LOD switching is critical and memory is not a constraint.
*   **When not to use:** Highly dynamic scenes requiring per-frame voxelization; memory-constrained environments.

## Background
This method originates from the `svo_renderer` project by mmalesadev, an unofficial implementation of a Sparse Voxel Octree renderer [S1, unofficial]. It is designed to streamline lighting and rendering workflows for complex assets by pre-voxelizing them into an SVO structure and managing the LODs via graphics components.
