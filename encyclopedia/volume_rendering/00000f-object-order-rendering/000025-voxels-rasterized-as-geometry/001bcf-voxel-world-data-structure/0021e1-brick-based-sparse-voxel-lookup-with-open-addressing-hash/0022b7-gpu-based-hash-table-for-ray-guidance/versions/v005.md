# GPU-based Hash Table for Ray Guidance

Also called: concurrent brick request table, lock-free hash table

## Overview
This method provides efficient communication of ray guidance information (specifically, brick IDs) from the GPU, where rays are cast, to the CPU I/O layer, which manages volume data residency [S1]. It solves the problem of identifying non-resident bricks required for ray continuation without the overhead of locks or complex synchronization primitives [S1]. Unlike a standard hash map, it functions as a set where keys are values, storing only the presence of requested bricks to trigger data loading [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A stream of ray requests for bricks. Each request consists of a 4D index comprising a 3D spatial coordinate and a Level of Detail (LoD) integer [S1].
*   **Output:** A hash table on the GPU containing unique brick IDs, which is read back to the CPU to populate the volume pool [S1].

**Data Structures:**
*   **Hash Table:** A 1D integer array. The size is implementation-dependent (Not given in the sources).
*   **Entry Layout:** Each slot stores a 1D brick index. The value `0` indicates an empty slot [S1].

**Mapping 4D Index to 1D Index:**
The 4D index $(x, y, z, \text{LoD})$ is mapped to a unique 1D index $I_{\text{raw}}$ as if the 4D space were flattened into a 1D array [S1]. The exact stride dimensions for this flattening are not given in the sources [G]. The final value stored in the table is offset by 1:
$$ I = I_{\text{raw}} + 1 $$
This offset ensures that `0` can represent an empty slot [S1].

**Algorithm:**
1.  **Request:** When a ray encounters a missing brick, it computes the brick's 4D index [S1].
2.  **Hash:** Compute the 1D index $I$ using the flattening formula and add 1 [S1].
3.  **Insert:** Attempt to insert $I$ into the hash table using lock-free atomic primitives (e.g., atomic compare-and-swap) [S1].
    *   If the slot is empty (`0`), write $I$.
    *   If the slot is already occupied by $I$, the brick is already recorded.
    *   If the slot is occupied by a different value or the atomic operation fails due to contention, linearly probe the next slot [S1].
4.  **Probe:** If the initial insert fails or the slot is occupied by a different brick, probe up to 10 times before giving up [S1].
5.  **Readback:** At the end of the frame, read the hash table from GPU memory to the CPU [S1].
6.  **Process:** The CPU processes the table entries to fill the volume pool with new data [S1].

**Pseudocode:**
```python
MAX_PROBES = 10
EMPTY_SLOT = 0

def atomic_cas(array, index, expected, desired):
    """Simulates GPU atomic compare-and-swap."""
    if array[index] == expected:
        array[index] = desired
        return True
    return False

def request_brick(spatial_x, spatial_y, spatial_z, lod, table, table_size):
    # 1. Map 4D index to 1D index (flattening strides not given in sources [G])
    # Standard row-major flattening assumed for implementation:
    i_raw = ((spatial_z * 1000 + spatial_y) * 1000 + spatial_x) * 1000 + lod
    target_val = i_raw + 1  # Offset so 0 indicates empty [S1]

    # 2. Lock-free insert with linear probing
    slot_idx = target_val % table_size
    for probe in range(MAX_PROBES):
        current = table[slot_idx]
        if current == EMPTY_SLOT:
            if atomic_cas(table, slot_idx, EMPTY_SLOT, target_val):
                return  # Successfully recorded
            # CAS failed: another thread claimed it, retry same slot
        elif current == target_val:
            return  # Already recorded
        else:
            # Occupied by different brick, probe next slot
            slot_idx = (slot_idx + 1) % table_size
    # Probe exhaustion is not an error [S1]
```

**Parameters:**
*   **Probe Count:** 10 attempts before giving up on a concurrent insert [S1].

**Edge Cases and Pitfalls:**
*   **GLSL Locks:** GLSL lacks traditional locks, necessitating lock-free structures [S1].
*   **Concurrent Write Hazards:** Multiple rays may request the same brick simultaneously. The probing mechanism handles this by allowing multiple threads to compete for slots [S1].
*   **Missing Records:** It is not an error if a missing brick is not recorded in the hash table due to probe exhaustion [S1]. The system invariant is that volume rendering is either complete or at least one ray can make progress [S1].

## Subtopics

### Sparse Hash Map CPU Index with GPU Shallow Tree
This variant describes a two-tier indexing system: a sparse hash map on the CPU keyed by brick coordinate (int32 in Planet-frame coordinates) for management, and a shallow tree on the GPU for ray traversal [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** Insertion is $O(1)$ amortized with a constant probe limit (10) [S1]. Readback time is not given in the sources.
*   **Memory Complexity:** Proportional to the maximum expected number of concurrent missing brick requests per frame [S1]. Significantly less memory than multiple render target approaches [S1].
*   **Strengths:** Lock-free, low memory footprint, simple set semantics [S1].
*   **Limitations:** Requires GPU-to-CPU readback every frame [S1]. Probe exhaustion can lead to unrecorded missing bricks, though the system invariant ensures progress [S1].
*   **When to Use:** When ray guidance data needs to be communicated from GPU to CPU for dynamic data loading in volume rendering [S1].
*   **When Not to Use:** When strict completeness of missing brick recording is required for every single ray in a single frame, or when GPU-CPU synchronization overhead is prohibitive [S1].

## Background
Originating from research on scalable GPU-based ray-guided volume rendering, this method addresses the bottleneck of communicating missing brick information from the GPU renderer to the CPU I/O layer [S1]. It was developed as an alternative to multiple render target approaches which required more memory [S1]. The approach leverages the fact that a set of missing bricks is sufficient for the CPU to make progress in loading data, even if not all missing bricks are recorded in a single frame [S1].
