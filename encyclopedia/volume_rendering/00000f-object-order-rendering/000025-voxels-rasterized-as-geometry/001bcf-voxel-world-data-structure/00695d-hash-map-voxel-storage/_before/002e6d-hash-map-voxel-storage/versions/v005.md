# Hash-Map Voxel Storage

Also called: Sparse Voxel Storage, VoxelData

## Overview
Hash-Map Voxel Storage is a sparse data structure that maps 3D voxel coordinates to their attributes using a hash map, enabling efficient storage of non-empty voxels in large volumes [S1, unofficial]. It solves the memory inefficiency of dense grids by only storing occupied cells while maintaining grid alignment through integer-based coordinate keys [S1, unofficial].

## How it works
**Inputs:** A stream or list of voxel definitions, where each definition contains a 3D integer coordinate $(x, y, z)$ and an attribute value (e.g., color) [S1, unofficial].
**Outputs:** A `VoxelData` structure containing a hash map of packed attributes, a count of stored voxels, and the bounding box dimensions [S1, unofficial].

**Data Structures:**
The core structure `VoxelData` consists of the following members [S1, unofficial]:
- `datas`: A hash map mapping a packed 3D coordinate key to a 32-bit integer attribute value [S1, unofficial].
- `count`: An integer representing the total number of voxels stored in `datas` [S1, unofficial].
- `width`, `height`, `depth`: Integers tracking the maximum extent of the grid along each axis, defining the bounding box of the stored data [S1, unofficial].

**Coordinate Packing:**
To serve as a hash key, the 3D integer coordinate $(x, y, z)$ is packed into a single key type for the hash map [S1, unofficial].

**Attribute Packing:**
The voxel attribute (specifically color in the cited implementation) is packed into a 32-bit integer using the layout BGR + alpha [S1, unofficial]. This is stored as a single 32-bit integer value in the hash map [S1, unofficial].

**Algorithm Steps:**
1. Initialize `VoxelData` with an empty `datas` map, `count` = 0, and `width` = `height` = `depth` = 0 [S1, unofficial].
2. Iterate through each incoming voxel definition $(x, y, z, \text{color})$ [S1, unofficial].
3. Compute the packed coordinate key $K = \text{pack\_key}(x, y, z)$ [S1, unofficial].
4. Pack the color attribute into a 32-bit integer $V = (A \ll 24) | (R \ll 16) | (G \ll 8) | B$ [S1, unofficial].
5. Insert or update the entry in `datas` such that `datas[K] = V` [S1, unofficial].
6. Reserve memory for the output size and compute the maximum width, height, and depth by iterating through the received voxels [S1, unofficial].
7. Increment `count` by 1 for each unique voxel processed, ensuring it reflects the number of entries in the hash map [S1, unofficial].

**Pseudocode:**
```python
class VoxelData:
    def __init__(self):
        self.datas = {}
        self.count = 0
        self.width = 0
        self.height = 0
        self.depth = 0

    def pack_key(self, x, y, z):
        return (x, y, z)

    def pack_color(self, r, g, b, a):
        return (a << 24) | (r << 16) | (g << 8) | b

    def add_voxel(self, x, y, z, r, g, b, a):
        key = self.pack_key(x, y, z)
        value = self.pack_color(r, g, b, a)
        if key not in self.datas:
            self.count += 1
        self.datas[key] = value
        if x + 1 > self.width:
            self.width = x + 1
        if y + 1 > self.height:
            self.height = y + 1
        if z + 1 > self.depth:
            self.depth = z + 1

    def get_voxel(self, x, y, z):
        key = self.pack_key(x, y, z)
        return self.datas.get(key)
```

**Edge Cases and Pitfalls:**
- **Duplicate Coordinates:** If the input contains multiple voxels at the same $(x, y, z)$, the hash map will overwrite the previous value [S1, unofficial]. The `count` must track the number of unique keys, not the number of insertions, to remain consistent with `len(datas)` [S1, unofficial].
- **Bounding Box Calculation:** The width/height/depth are calculated as `max_coord + 1`, implying a 1-based or exclusive upper bound interpretation [S1, unofficial].

## Subtopics

### [Voxel Table Registry](10960-voxel-table-registry.md)
The Voxel Table Registry is a centralized lookup structure that provides $O(1)$ access to voxel definitions by both unique identifier and internal name. It solves the problem of redundant disk I/O and inconsistent state by maintaining a static, in-memory map of voxel types, serving as the authoritative source for chunk generation and rendering logic. It differs from sibling hash-grid storage methods by focusing on semantic definition management rather than spatial coordinate mapping.

### [Voxel Hash Chunk Map](12207-voxel-hash-chunk-map.md)
The Voxel Hash Chunk Map (voxlvoxl) is a sparse 3D point cloud representation that partitions space into independent, hash-addressed cubic chunks to mitigate memory overhead for large-scale maps. Unlike sibling structures like Rolling Bonxai that enforce a fixed 3x3x3 active window, voxlvoxl uses a hash function for chunk indexing, allowing unlimited degrees of freedom for dynamic summoning and dismissing of regions.

### [Voxel Hash for Gaussian Splat Indexing](12601-voxel-hash-for-gaussian-splat-indexing.md)
Voxel Hash is a sparse data structure that maps each 3D Gaussian Splat to the voxel cell containing its center $\mu$, enabling efficient lookup of splats within specific voxel regions for operations like carving or stacking. It differs from sibling structures by maintaining a direct bidirectional mapping between splat indices and voxel keys, allowing for rapid identification of splats to remove or modify within a target voxel.

### Online Random Access
This variant, specifically the `[Hash, 5, 4, NN(3)]` configuration from NeuralVDB, supports random access to values directly from in-memory data without full reconstruction, balancing memory footprint and access time for real-time applications [S2]. It uses standard accelerated random access techniques (level {3, 2, 1}) to determine if a query point maps to a tile or a voxel (level 0) [S2]. If the query maps to a tile, it returns the value explicitly encoded in the standard VDB structure [S2]. If it maps to a voxel (level 0), it predicts the voxel value using a regressor [S2]. This configuration has the same performance characteristics as a standard VDB tree, except leaf values require additional regression [S2]. Its in-memory footprint is an order of magnitude smaller than `[Hash, 5, 4, 3]` and it can be trivially reconstructed from `[Hash, 5, NN(4), NN(3)]` by leaving the voxel regressor unchanged, acting as a pre-cached representation [S2].

## Operating characteristics
- **Time Complexity:** Lookup is $O(1)$ on average for hash map operations [S1, unofficial]. Bounding box updates are $O(1)$ per voxel [S1, unofficial].
- **Memory Complexity:** Proportional to the number of non-empty voxels [S1, unofficial].
- **Measured Performance:** Not given in the sources.
- **Strengths:** Efficient storage for sparse volumes; simple implementation; fast random access to individual voxels [S1, unofficial].
- **Limitations:** Hash map overhead (load factor, collisions); bounding box calculation requires iterating all voxels; no inherent spatial coherence for traversal (unlike tree-based structures) [S1, unofficial].
- **When to use:** When the volume is sparse and random access to specific voxel attributes is required [S1, unofficial].
- **When not to use:** When the volume is dense (use dense arrays) or when hierarchical traversal is needed for rendering (use tree-based structures like VDB or Octrees) [S1, unofficial].

## Background
The structure is described in the context of voxel world data management [S1, unofficial]. It serves as a foundational sparse storage mechanism for voxel-based applications [S1, unofficial]. The NeuralVDB paper discusses related hash-based sparse volume representations, particularly in the context of neural network regression for voxel values, highlighting the trade-offs between memory footprint and access speed [S2].
