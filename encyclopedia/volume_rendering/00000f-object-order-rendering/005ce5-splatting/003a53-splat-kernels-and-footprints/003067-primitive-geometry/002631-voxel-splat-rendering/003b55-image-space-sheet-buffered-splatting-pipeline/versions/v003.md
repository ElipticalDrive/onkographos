# Image-Space Sheet-Buffered Splatting Pipeline

Also called: GPU ISBS, GPU-based ISSB Splatting, GPU-based Image-Space Sheet-Buffered Splatting, ISSB Splatting on the GPU, Image-Space Sheet-Buffered Splatting on the GPU

## Overview
Image-Space Sheet-Buffered Splatting on the GPU (GPU ISBS) is a volume rendering technique that processes voxels in slabs parallel to the image plane, performing all bucket construction, voxel transformation, and depth sorting entirely on the GPU to avoid CPU-GPU memory transfer bottlenecks [S1, unofficial][S2, unofficial]. Unlike the CPU-based approach where buckets contain all voxels intersecting a slab, the GPU method defines a bucket as the subset of depth-sorted voxels whose center falls inside a specific slab, allowing each voxel to belong to exactly one bucket while still being splatted for all intersecting slabs [S1, unofficial]. This method accelerates rendering by a factor of 2 to 2.5 compared to implementations that compute buckets on the CPU [S1, unofficial].

## How it works
The pipeline processes voxels through texture-based stages: loading, viewing transform, GPGPU sorting, bucket size computation, and rendering [S1, unofficial].

**Inputs and Outputs**
*   **Input:** A set of selected non-empty voxels, each defined by 3D coordinates $(x, y, z)$ and a property value $v$ [S2, unofficial].
*   **Output:** A composited 2D image buffer.

**Data Structures**
1.  **Voxels Texture:** A 2D texture storing the input voxels. Each voxel is encoded in a texel using `FP32RGBA` format (32-bit floating point per channel). The RGB channels store the voxel coordinates $(x, y, z)$, and the Alpha channel stores the property value $v$ [S2, unofficial].
2.  **View Transformed Voxels Texture:** A 2D texture storing the result of the viewing transform. Each texel stores the 2D raster projection coordinates in the R and G channels, the depth value in the viewing coordinate system in the B channel, and the voxel property value in the Alpha channel, denoted as $(i, j, b, v)$ [S2, unofficial].
3.  **Depth-Sorted Voxels Texture (Z-Sorted Voxels Texture):** A 2D texture containing the voxels from the View Transformed Voxels Texture sorted by depth $b$ [S2, unofficial].
4.  **Buckets Texture:** A 2D texture storing the position (index) of the last voxel of each bucket (bucket boundary voxel) [S1, unofficial].
5.  **Auxiliary Texture:** Used during bucket size computation to mark boundary voxels. It stores bucket coordinates in R and G, an arbitrary z-value inside the viewing frustum for boundary voxels (outside otherwise) in B, and the bucket index in Alpha [S2, unofficial].

**Parameters**
*   **Voxel Kernel Radius:** Determines the number of previous and following buckets that affect a single slab in addition to its own bucket [S1, unofficial].
*   **Texture Memory Limit:** The method assumes a maximum texture size of $4096 \times 4096$, allowing up to 16 million selected voxels [S1, unofficial].

**Steps**
1.  **Load Voxels:** Load the selected non-empty voxels into the `Voxels Texture` on the GPU. Each voxel is encoded as `<x, y, z, v>` in `FP32RGBA` format [S2, unofficial].
2.  **Viewing Transform:** Compute the `View Transformed Voxels Texture` using a fragment shader. For each texel in the `Voxels Texture`, transform the voxel coordinates (RGB) using the viewing matrix. Store the 2D raster projection coordinates in R and G, the depth value in B, and the voxel property value in Alpha [S2, unofficial].
3.  **GPGPU Sorting:** Sort the `View Transformed Voxels Texture` by depth using a GPU Bitonic Sort. The sorting key is the depth value (B channel). The sort uses Multiple Render Targets (MRT) to store keys and values in separate textures, allowing four `<key, value>` instances per RGBA texel. The key is the depth value, and the value is the voxel index in the texture. After sorting, a fragment shader fills the `Depth-Sorted Voxels Texture` from the sorted render targets [S2, unofficial]. This sorting creates an implicit representation of buckets, where slabs correspond to overlapping sorted subsequences of voxels in the texture [S1, unofficial].
4.  **Bucket Size Computation:** Compute the `Buckets Texture` in two steps [S2, unofficial]:
    *   **Step 4a:** Use a fragment shader to identify bucket boundary voxels. Render the `Depth-Sorted Voxels Texture` into an `Auxiliary Texture`. For each voxel, determine if it is a boundary voxel (i.e., its center falls inside a slab but the next voxel in the sorted texture does not). If it is a boundary voxel, store its bucket coordinates in R and G, an arbitrary z-value inside the viewing frustum in B, and the bucket index in Alpha. If not, store a z-value outside the viewing frustum in B [S2, unofficial].
    *   **Step 4b:** Use a vertex shader to construct the `Buckets Texture` from the `Auxiliary Texture`. The vertex shader renders the boundary voxels (identified by the z-value in B) to write the position of the last voxel of each bucket into the `Buckets Texture` [S2, unofficial].
5.  **Transfer Bucket Data:** Transfer the small `Buckets Texture` to the CPU to determine bucket distribution. This is a low-cost operation because the texture size is small (number of buckets/slabs) [S1, unofficial].
6.  **Rendering:** Process slabs sequentially. For each slab $i$, retrieve its bucket from the `Buckets Texture`. The radius of the voxel kernel determines that a slab is affected by its own bucket plus previous and following buckets (from $bucket_{i-radius}$ to $bucket_{i+radius}$) [S2, unofficial].
    *   Use the Render to Vertex Buffer (R2VB) technique to create a Vertex Buffer Object (VBO) containing all voxels from the relevant buckets [S2, unofficial].
    *   Render slabs by splatting voxels from the relevant buckets using `DrawArrays` [S1, unofficial].
    *   Project voxels from the current bucket onto a sheet buffer according to a preintegrated kernel slice. Composite the sheet buffer with the image buffer. No sorting is required inside the buckets as splats are simply added [S2, unofficial].
    *   Use the `glPoint` primitive with the Point Sprites extension to create automatic quads for splats [S1, unofficial].

**Pseudocode**
```python
def load_voxels_to_gpu(voxels):
    """Load selected non-empty voxels into a 2D texture (Voxels Texture).
    Each voxel <x, y, z, v> is encoded in FP32RGBA format."""
    return Voxels_Texture

def viewing_transform(Voxels_Texture, viewing_matrix):
    """Fragment shader: transform voxel coordinates (RGB) using viewing matrix.
    Store 2D raster projection in R/G, depth in B, property value in Alpha."""
    View_Transformed_Texture = empty_texture()
    for texel in Voxels_Texture:
        texel.R, texel.G = project_2d(texel.R, texel.G, texel.B, viewing_matrix)
        texel.B = depth_value(texel.R, texel.G, texel.B, viewing_matrix)
    return View_Transformed_Texture

def gpu_bitonic_sort(View_Transformed_Texture):
    """Sort by depth (B channel) using Bitonic Sort with MRT.
    Key: depth value (B). Value: voxel index in texture.
    Stores keys and values in separate textures, 4 <key, value> per RGBA texel."""
    Sorted_Keys, Sorted_Values = bitonic_sort_network(View_Transformed_Texture.B, range(len(View_Transformed_Texture)))
    return Sorted_Keys, Sorted_Values

def fill_depth_sorted_texture(Sorted_Keys, Sorted_Values):
    """Fragment shader: fill Depth-Sorted Voxels Texture from sorted render targets."""
    Depth_Sorted_Texture = empty_texture()
    for i in range(len(Sorted_Keys)):
        Depth_Sorted_Texture[i] = apply_sort_mapping(View_Transformed_Texture, Sorted_Keys[i], Sorted_Values[i])
    return Depth_Sorted_Texture

def compute_auxiliary_texture(Depth_Sorted_Texture):
    """Fragment shader: identify bucket boundary voxels.
    Render into Auxiliary Texture. Store bucket coords in R/G, bucket index in A.
    Store arbitrary z inside frustum in B if boundary, outside otherwise."""
    Auxiliary_Texture = empty_texture()
    for i in range(len(Depth_Sorted_Texture)):
        is_boundary = check_slab_boundary(Depth_Sorted_Texture[i], Depth_Sorted_Texture[i+1])
        Auxiliary_Texture[i].R, Auxiliary_Texture[i].G = compute_bucket_coords(Depth_Sorted_Texture[i])
        Auxiliary_Texture[i].A = compute_bucket_index(Depth_Sorted_Texture[i])
        Auxiliary_Texture[i].B = z_inside_frustum() if is_boundary else z_outside_frustum()
    return Auxiliary_Texture

def construct_buckets_texture(Auxiliary_Texture):
    """Vertex shader: construct Buckets Texture from Auxiliary Texture.
    Renders boundary voxels (identified by z in B) to write last voxel position per bucket."""
    Buckets_Texture = empty_texture()
    for texel in Auxiliary_Texture:
        if texel.B is inside_frustum():
            write_bucket_boundary(Buckets_Texture, texel.A, texel.R, texel.G)
    return Buckets_Texture

def transfer_buckets_to_cpu(Buckets_Texture):
    """Transfer small Buckets Texture to CPU for bucket distribution."""
    return Buckets_Texture.read_back()

def render_slabs(Buckets_Texture, kernel_radius):
    """Process slabs sequentially. Splat voxels using Point Sprites and R2VB."""
    for slab_i in range(number_of_slabs):
        start_bucket = max(0, slab_i - kernel_radius)
        end_bucket = min(number_of_buckets, slab_i + kernel_radius)
        VBO = render_to_vertex_buffer(Buckets_Texture, start_bucket, end_bucket)
        draw_arrays(VBO, primitive_type="POINTS", extension="POINT_SPRITES")
        composite_sheet_buffer()
```

## Subtopics

### [ISSB Rendering with Point Sprites and Dynamic Footprints](9055-issb-rendering-with-point-sprites-and-dynamic-footprints.md)
This method defines the final rendering stage of the Image-Space Sheet-Buffered (ISSB) splatting pipeline, where depth-sorted voxels are rasterized using `glPoint` primitives and the Point Sprites extension. It distinguishes itself from prior ISSB implementations by computing and storing distinct kernel footprints for each voxel across all intersecting slabs, rather than storing a single footprint modulated by a slab coefficient. This approach provides finer tuning of the splat appearance at the cost of increased texture memory for footprint storage.

## Operating characteristics
*   **Time Complexity:** The most expensive stage of the pipeline is sorting, which uses data-independent network sorting strategies like Bitonic Sort [S2, unofficial].
*   **Memory Complexity:** The method is limited by texture memory size. A $4096 \times 4096$ texture allows up to 16 million selected voxels [S1, unofficial]. For larger models, the volume is subdivided into bricks, each stored as a 2D texture [S1, unofficial].
*   **Measured Performance:** On a Pentium Dual Core 3.2 GHz with 3.2 GB memory and an NVIDIA GeForce 7900 GTX with 512 MB memory, the method accelerates rendering by a factor of 2 to 2.5 compared to an implementation that computes buckets on the CPU [S1, unofficial]. For the "Lobster" dataset (324x301x56, 233K effective voxels), CPU FPS was 13.2 and GPU FPS was 35.4. For the "Engine" dataset (256x128, 1.3M effective voxels), CPU FPS was 2.4 and GPU FPS was 5.6 [S1, unofficial].
*   **Strengths:** Avoids CPU-GPU memory transfer bottlenecks by performing all data management on the GPU. Simplifies bucket structure by assigning each voxel to exactly one bucket [S1, unofficial].
*   **Limitations:** Scattering (random writes) is inefficient on GPUs, necessitating the use of sorting and implicit bucket representation [S1, unofficial]. Determining bucket boundaries in a vertex shader is expensive due to inefficient texture fetches, requiring a two-step computation [S2, unofficial]. The bottleneck is the computation of the buckets [S2, unofficial].
*   **When to use:** When GPU computational resources are available and CPU-GPU memory transfer is a bottleneck. Suitable for static cameras where only the transfer function changes (only the render stage needs to be redone) or moving cameras where the full pipeline is executed [S2, unofficial].
*   **When not to use:** When the number of voxels exceeds the texture memory limit and bricking is not feasible or desirable. When the overhead of sorting outweighs the benefits of GPU-based bucket construction (e.g., very small datasets).

## Background
Image-Space Sheet-Buffered Splatting was originally proposed as a feed-forward algorithm for voxel-based volume datasets [S2, unofficial]. It processes the volume by slabs parallel to the image plane [S1, unofficial]. The GPU-based implementation was proposed to address the memory transfer bottleneck between CPU buckets and GPU slices present in earlier implementations by Neophitou and Mueller [S2, unofficial]. The method uses GPGPU sorting and OpenGL Depth Test to manage buckets on the GPU [S1, unofficial].
