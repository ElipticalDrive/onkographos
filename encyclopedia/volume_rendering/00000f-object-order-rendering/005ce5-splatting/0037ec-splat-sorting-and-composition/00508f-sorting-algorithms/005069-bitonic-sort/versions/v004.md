# Bitonic Sort

Also called: ABisort, Bitonic Sort for GPGPU, Govindaraju et al. Bitonic Sort, Particle Sorting (Bitonic Sort)

## Overview
Bitonic Sort is a data-independent network sorting algorithm used on the GPU to achieve exact depth ordering of splatted voxels for every frame [S1, unofficial]. It is chosen over partial-ordering methods like Odd-Even Merge Sort because the application requires exact ordering at each frame, making sort-while-drawing inconvenient [S1, unofficial]. It is preferred over Adaptive Bitonic Sort (ABisort) in some implementations due to library accessibility and ease of adaptation, despite ABisort having potentially better theoretical complexity [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** An array of view-transformed voxels already resident in GPU memory, typically stored in a texture (View Transformed Voxels Texture) [S1, unofficial]. Each voxel is represented as a `<key, value>` pair, where the key is the depth value $b$ and the value is the voxel index [S1, unofficial].
*   **Output:** A sorted array of voxels stored in a texture (Depth-Sorted Voxels Texture), ordered by depth [S1, unofficial].

**Data Structures:**
The algorithm uses the Multiple Render Target (MRT) extension to store keys and values in separate render targets [S1, unofficial]. A one-to-one correspondence exists between the key texture and the value texture [S1, unofficial]. This correspondence allows keeping four `<key, value>` instances in a single RGBA texel [S1, unofficial].

**Parameters:**
*   $uPass$: Current pass number in the sort algorithm [S2, unofficial].
*   $uStage$: Current stage number within the pass [S2, unofficial].
*   $uHalfVector$: The half-angle vector used for sorting particles [S2, unofficial].
*   $N$: Total number of particles/voxels to sort.

**Algorithm Steps:**
1.  **Initialization:** Reset pass and stage counters if the sorting direction needs to be reversed [S2, unofficial].
2.  **Ping-Pong Buffering:** Use two framebuffers to swap read/write roles between passes [S1, unofficial].
3.  **Index Computation:** Compute the particle index $i$ from texture coordinates [S2, unofficial].
4.  **Direction Determination:** Determine the comparison direction `compare` based on the current pass, stage, and index $i$ [S2, unofficial].
5.  **Partner Calculation:** Calculate the partner address using `adr = i + compare * uPass` and fetch partner data [S2, unofficial].
6.  **Comparison:** Sort based on the dot product with the half vector: output `self` if `selfProjectedLength * compare < partnerProjectedLength * compare`, else output `partner` [S2, unofficial].
7.  **Write:** Write the sorted result to the appropriate render target [S1, unofficial].
8.  **Finalization:** After all passes, a fragment shader fills the Depth-Sorted Voxels Texture from the sorted render targets [S1, unofficial].

**Pseudocode:**
The following pseudocode describes the fragment shader logic for a single comparison step in the Bitonic Sort network [S2, unofficial].

```python
def bitonic_sort_step(i, uPass, uStage, prev_positions, current_positions):
    # [G] Standard bitonic sort direction logic based on stage and index
    compare = 1 if (i >> uStage) & 1 else -1
    
    # Calculate partner address
    adr = i + compare * uPass
    
    # Fetch data from previous render target
    self_data = prev_positions.sample(i)
    partner_data = prev_positions.sample(adr)
    
    self_key = self_data.key      # Depth value b
    self_val = self_data.value    # Voxel index
    partner_key = partner_data.key
    partner_val = partner_data.value
    
    # Perform comparison using direction multiplier
    lhs = self_key * compare
    rhs = partner_key * compare
    
    if lhs < rhs:
        current_positions.write(i, self_key, self_val)
        current_positions.write(adr, partner_key, partner_val)
    else:
        current_positions.write(i, partner_key, partner_val)
        current_positions.write(adr, self_key, self_val)
```

**Edge Cases and Pitfalls:**
*   **Data Independence:** Unlike Quicksort, Bitonic Sort does not branch on data values, making it suitable for GPU SIMD/SIMT architectures but potentially slower for small datasets due to fixed work [S1, unofficial].
*   **Exact Ordering:** Requires all passes to complete for exact ordering; partial results are insufficient for correct compositing [S1, unofficial].
*   **Fixed Operations:** The algorithm performs a predetermined number of comparisons regardless of data distribution, which can be inefficient for partially sorted or small datasets [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N \log^2 N)$ comparisons and swaps [S1, unofficial]. Adaptive Bitonic Sort (ABisort) claims $O((N \log N)/P)$ complexity, where $P$ is the number of stream processors [S1, unofficial].
*   **Performance:** On an NVIDIA GeForce 7800, Govindaraju's Bitonic Sort was approximately twice as fast as the best CPU QuickSort implementation at the time of the source [S1, unofficial].
*   **Strengths:** Provides exact ordering every frame; highly parallelizable; cache-efficient memory access patterns in optimized implementations [S1, unofficial].
*   **Limitations:** Fixed number of operations regardless of data distribution; not suitable for dynamic datasets where partial ordering is acceptable (Odd-Even Merge Sort is preferred there) [S1, unofficial].
*   **When to Use:** When exact depth sorting is required for every frame in volume splatting [S1, unofficial].
*   **When Not to Use:** When partial ordering is sufficient (e.g., particle systems spread over multiple frames) or when adaptive sorting performance is critical and library access permits [S1, unofficial].

## Background
Bitonic Sort was originally developed as a network sorting algorithm. In the context of GPU volume rendering, Govindaraju et al. [GRHM05] improved early implementations [KW05] by introducing cache-efficient memory accesses, leading to high performance on GPUs like the NVIDIA GeForce 7800 [S1, unofficial]. Gress and Zachmann [GZ06] later designed Adaptive Bitonic Sort (ABisort) with optimal complexity [S1, unofficial]. In the specific implementation described in the sources, Govindaraju's method was chosen over ABisort due to the accessibility and adaptability of the library [S1, unofficial].
