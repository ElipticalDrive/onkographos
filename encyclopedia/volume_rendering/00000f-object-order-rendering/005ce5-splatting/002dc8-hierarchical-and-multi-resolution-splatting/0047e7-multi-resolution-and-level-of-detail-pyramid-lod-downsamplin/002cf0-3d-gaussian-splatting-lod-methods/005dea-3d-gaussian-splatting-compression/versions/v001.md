# 3D Gaussian Splatting Compression

Also called: Compact3D, EGGS (Explicitly Granular 3D Gaussian Splatting), Explicitly Granular 3D Gaussian Splatting

## Overview
3D Gaussian Splatting Compression refers to a class of methods designed to reduce the storage footprint of 3D Gaussian Splatting (3DGS) scenes by compressing the geometric and attribute data. Unlike methods that quantize all attributes uniformly, specific implementations like Compact3D and EGGS employ specialized strategies to preserve visual fidelity while achieving high compression ratios. Compact3D avoids quantizing position and opacity to prevent overlapping Gaussians and visual artifacts, while EGGS utilizes Luma-Aware and Volume-Preserving Attribute Factorization. These methods build on [3D Gaussian Splatting LOD methods](5439-3d-gaussian-splatting-lod-methods.md) by focusing on lossy or lossless bitstream reduction rather than hierarchical rendering structures.

## How it works
The implementation details below describe the **EGGS** pipeline, which serves as a concrete example of geometry compression using G-PCC (Geometry-based Point Cloud Compression). The method focuses on compressing the Gaussian means (positions) while handling other attributes separately or via factorization.

### Inputs and Outputs
- **Input**: A set of $N$ 3D Gaussians, each defined by a mean position $\mathbf{p} \in \mathbb{R}^3$, covariance (scale/rotation), opacity $\alpha$, and spherical harmonics coefficients for color.
- **Output**: A binary file containing a compressed geometry stream and a header.

### Data Structures
The output binary file structure is:
1. **Header**: 24 bytes.
   - `means_min`: 3 floats (float32), the minimum x, y, z coordinates of the Gaussian means.
   - `means_max`: 3 floats (float32), the maximum x, y, z coordinates of the Gaussian means.
2. **Length**: 4 bytes (uint32), the size in bytes of the compressed geometry stream.
3. **Compressed Data**: Variable length, the binary stream output from the GPCC encoder.

### Parameters
- **VOXELIZE_SCALE_FACTOR**: 16. This defines the bit depth for voxelizing the Gaussian means. The integer range is $[0, 2^{16}-1]$.
- **GPCC Encoder Flags** (used for `tmc3`):
  - `mode=0` (Encoder)
  - `trisoupNodeSizeLog2=0`
  - `mergeDuplicatedPoints=0`
  - `neighbourAvailBoundaryLog2=8`
  - `positionQuantisationEnabled=1`
  - `intra_pred_max_node_size_log2=3`
  - `positionQuantizationScale=1`
  - `inferredDirectCodingMode=3`
  - `maxNumQtBtBeforeOt=2`
  - `minQtbtSizeLog2=0`
  - `planarEnabled=0`
  - `planarModeIdcmUse=0`
  - `cabac_bypass_stream_enabled_flag=1`
- **GPCC Decoder Flags**:
  - `mode=1` (Decoder)
  - `outputBinaryPly=1`

### Steps

#### Encoding Pipeline
1. **Voxelization of Means**:
   - Calculate the bounding box of all Gaussian means:
     $$ \mathbf{p}_{min} = \min_i (\mathbf{p}_i) $$
     $$ \mathbf{p}_{max} = \max_i (\mathbf{p}_i) $$
   - Normalize each mean $\mathbf{p}_i = [x_i, y_i, z_i]^T$ to the range $[0, 1]$:
     $$ \mathbf{p}'_i = \frac{\mathbf{p}_i - \mathbf{p}_{min}}{\mathbf{p}_{max} - \mathbf{p}_{min}} $$
   - Convert to 16-bit integers:
     $$ \mathbf{v}_i = \text{round}(\mathbf{p}'_i \times (2^{16} - 1)) $$
     where $\mathbf{v}_i = [x'_i, y'_i, z'_i]^T$.

2. **Sorting by Morton Code**:
   - Calculate the Morton code for each voxelized mean $\mathbf{v}_i$. The source defines the Morton code calculation as the dot product of the voxelized coordinates and powers of $(\text{max\_coordinate} + 1)$. Let $M = 2^{16}$. The Morton code $m_i$ for $\mathbf{v}_i = [x'_i, y'_i, z'_i]^T$ is computed. *Note: Standard Morton codes interleave bits; the source description implies a specific mapping or a simplified linearization for sorting purposes.*
   - Sort the voxelized means $\mathbf{v}_i$ in ascending order of their Morton codes.

3. **PLY File Generation**:
   - Write the sorted voxelized means to an ASCII PLY file. The file contains the point cloud data with x, y, z properties.

4. **GPCC Compression**:
   - Execute the external GPCC encoder (`tmc3`) with the flags listed in Parameters.
   - Input: The ASCII PLY file.
   - Output: A binary compressed stream.

5. **File Assembly**:
   - Write the 24-byte header (`means_min`, `means_max`).
   - Write the 4-byte length of the compressed stream.
   - Write the compressed binary stream.

#### Decoding Pipeline
1. **Header and Stream Extraction**:
   - Read the first 24 bytes to extract `means_min` and `means_max`.
   - Read the next 4 bytes to determine the length $L$ of the compressed stream.
   - Read the next $L$ bytes into a temporary binary file.

2. **GPCC Decompression**:
   - Execute the external GPCC decoder (`tmc3`) with flags `mode=1` and `outputBinaryPly=1`.
   - Input: The temporary binary file.
   - Output: A reconstructed binary PLY file containing the voxelized means.

3. **Reading Voxelized Means**:
   - Parse the binary PLY file to retrieve the voxelized means $\mathbf{v}_i$.
   - **Critical Step**: The decoded voxelized means are unsorted. Sort them by their Morton codes to restore the original encoding order.

4. **Devoxelization**:
   - Convert the sorted integer voxelized means $\mathbf{v}_i$ back to float32 coordinates $\mathbf{p}_i$:
     $$ \mathbf{p}_i = \mathbf{p}_{min} + \left( \frac{\mathbf{v}_i}{2^{16} - 1} \right) \times (\mathbf{p}_{max} - \mathbf{p}_{min}) $$

### Edge Cases and Pitfalls
- **Unsorted Decoded Data**: The GPCC decoder does not guarantee that the output points are sorted by Morton code. They must be re-sorted before devoxelization if the subsequent processing relies on the original order (e.g., if attributes are stored in a separate stream aligned with the sorted geometry).
- **Precision**: The voxelization uses 16-bit integers. This limits the positional precision. The source does not specify how this affects the final rendering quality beyond the metrics provided.
- **Empty Scene**: If all Gaussian means are identical, the range is zero. The code must handle division by zero in normalization.
