# System Level Primitive Sharding

Also called: BlitzGS sharding, Distributed rendering, Index parity sharding, Primitive Sharding

## Overview
System Level Primitive Sharding is a distributed rendering and training strategy for 3D Gaussian Splatting that partitions a global Gaussian model across $M$ GPUs to handle city-scale scenes with hundreds of millions of primitives [S1, unofficial]. It ensures that both storage and per-step compute scale linearly with the GPU count by assigning Gaussians via index parity and distributing rendered tiles across the GPU cluster [S1, unofficial]. Unlike spatial block partitioning, which incurs boundary waste, duplicate camera assignments, and merge steps, primitive sharding assigns every camera exactly once and eliminates the need for a final merge [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A global set of 3D Gaussians $G$ with associated parameters (position, covariance, opacity, spherical harmonics coefficients) and optimizer states; a set of training or rendering cameras; the number of GPUs $M$.
*   **Output:** Rendered images for assigned tiles; updated Gaussian parameters and optimizer states distributed across GPUs.

**Data Structures:**
*   **Shard $G^{(m)}$:** A subset of the global Gaussian set $G$ assigned to GPU rank $m$ ($0 \le m < M$). The size is approximately $|G|/M$.
*   **Optimizer State:** Per-Gaussian optimization buffers (e.g., momentum, variance) stored locally on the owning GPU.
*   **Tile Assignment:** A mapping of image tiles to GPU ranks, determined by a cost-aware partitioning algorithm.

**Steps:**
1.  **Initial Sharding:** Partition the global Gaussian set $G$ into $M$ shards $G^{(m)}$ based on index parity. Each GPU $m$ stores its shard $G^{(m)}$ and its corresponding optimizer state [S1, unofficial].
2.  **Tile Partitioning:** Divide the rendered image into tiles. Assign each tile to a specific GPU rank using a cost-aware partitioning strategy to even out rasterization load [S1, unofficial].
3.  **Projection:** Each GPU $m$ projects only the Gaussians in its local shard $G^{(m)}$ into the camera space [S1, unofficial].
4.  **All-to-All Communication:** Perform a single all-to-all communication step to route every projected Gaussian to the GPUs owning the tiles it covers [S1, unofficial]. A Gaussian is sent to GPU $k$ if it overlaps with any tile assigned to GPU $k$ [S1, unofficial].
5.  **Compositing:** Each GPU composites its assigned tiles using the received Gaussians [S1, unofficial].
6.  **Rebalancing (Optional):** If the per-GPU skew in shard size exceeds a threshold, apply index-parity redistribution to rebalance shard sizes [S1, unofficial].

**Formulas:**
*   **Shard Size:** $|G^{(m)}| \approx \frac{|G|}{M}$ [S1, unofficial].
*   **Memory Scaling:** Per-rank peak memory decreases as $M$ increases. For the Rubble scene, memory drops from 17.2 GB at $M=1$ to 2.9 GB at $M=8$ [S1, unofficial].

**Parameters:**
*   $M$: The number of GPUs across which the model is sharded [S1, unofficial].

**Pseudocode:**
```python
def system_level_primitive_sharding(G, cameras, M, tile_partitioner, rebalance_threshold):
    """
    G: List of all Gaussians in the global scene.
    cameras: List of camera parameters.
    M: Number of GPUs.
    tile_partitioner: Function that assigns tiles to GPUs based on cost.
    rebalance_threshold: Threshold for shard size skew.
    """
    # Step 1: Initial Sharding by Index Parity
    shards = [ [] for _ in range(M) ]
    optimizer_states = [ [] for _ in range(M) ]
    
    for i, gaussian in enumerate(G):
        m = i % M
        shards[m].append(gaussian)
        optimizer_states[m].append(get_optimizer_state(gaussian))
        
    # Step 2: Tile Partitioning
    # Assign tiles to GPUs to balance rasterization load
    tile_to_gpu = tile_partitioner(cameras, M)
    
    # Step 3: Projection and Step 4: All-to-All Communication
    # Each GPU projects its own shard and sends Gaussians to tiles they cover
    received_gaussians = [ [] for _ in range(M) ]
    
    for m in range(M):
        # Project local Gaussians
        projected = project_gaussians(shards[m], cameras)
        
        # Determine which tiles each projected Gaussian covers
        for gaussian in projected:
            covered_tiles = get_covered_tiles(gaussian, cameras)
            for tile in covered_tiles:
                target_gpu = tile_to_gpu[tile]
                if target_gpu != m:
                    send_to_gpu(target_gpu, gaussian)
                else:
                    received_gaussians[m].append(gaussian)
                    
    # Receive Gaussians from other GPUs
    for m in range(M):
        received_gaussians[m] += receive_from_other_gpus(m)
        
    # Step 5: Compositing
    for m in range(M):
        assigned_tiles = get_tiles_for_gpu(m, tile_to_gpu)
        render_tiles(assigned_tiles, received_gaussians[m], cameras)
        
    # Step 6: Rebalancing
    if check_skew(shards, rebalance_threshold):
        shards = redistribute_by_index_parity(shards)
        optimizer_states = redistribute_optimizer_states(optimizer_states)
        
    return shards, optimizer_states
```

**Edge Cases and Pitfalls:**
*   **Skew:** If the distribution of Gaussians is highly non-uniform, index parity may lead to imbalanced shards. The rebalancing step mitigates this [S1, unofficial].
*   **Communication Overhead:** The all-to-all step can become a bottleneck if the number of Gaussians or tiles is very large. However, sources indicate this cost is manageable and scales well [S1, unofficial].
*   **Boundary Issues:** Unlike spatial partitioning, there are no spatial boundaries to handle, eliminating duplicate camera assignments and merge steps [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The per-iteration cost scales near-linearly with the number of GPUs for compute-heavy stages like the backward pass. For the Residence scene on A800 80 GB GPUs, the total per-iteration cost drops from 186.9 ms (1 GPU) to 68.6 ms (8 GPUs) [S1, unofficial].
*   **Memory Complexity:** Per-rank peak memory scales inversely with $M$. On the Rubble scene, it drops from 17.2 GB (1 GPU) to 2.9 GB (8 GPUs) [S1, unofficial]. The binding limit is the aggregate capacity across all GPUs [S1, unofficial].
*   **Strengths:** Eliminates boundary waste and merge steps inherent in spatial block partitioning. Assigns every camera exactly once, preventing duplicate processing [S1, unofficial]. Scales storage and compute linearly with GPU count [S1, unofficial].
*   **Limitations:** Requires efficient all-to-all communication. The residual overhead from data loading and optimizer bookkeeping becomes more significant as the iteration time shrinks [S1, unofficial].
*   **When to Use:** Suitable for city-scale scenes with hundreds of millions of primitives that exceed the memory of a single GPU [S1, unofficial].
*   **When Not to Use:** For small scenes that fit on a single GPU, the communication overhead may not be justified [S1, unofficial].

## Background
System Level Primitive Sharding, also known as BlitzGS sharding, was introduced in the paper "BlitzGS: City-Scale Gaussian Splatting at Lightning Speed" [S1, unofficial]. It addresses the limitations of spatial block partitioning, which suffers from cross-block visibility waste, imbalanced shards, and the need for a final merge step [S1, unofficial]. The method is inspired by prior work on distributed rendering [S1, unofficial]. It is used in the context of 3D Gaussian Splatting for large-scale scene reconstruction and rendering [S1, unofficial].
