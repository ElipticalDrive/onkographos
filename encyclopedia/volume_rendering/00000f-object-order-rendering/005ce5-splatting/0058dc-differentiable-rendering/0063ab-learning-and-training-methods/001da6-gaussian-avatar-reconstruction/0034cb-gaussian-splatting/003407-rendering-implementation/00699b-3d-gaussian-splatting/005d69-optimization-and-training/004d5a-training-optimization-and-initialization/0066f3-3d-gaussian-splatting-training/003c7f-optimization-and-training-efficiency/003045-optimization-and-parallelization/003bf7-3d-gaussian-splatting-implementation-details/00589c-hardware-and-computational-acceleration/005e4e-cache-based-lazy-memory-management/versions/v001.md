# Cache-based Lazy Memory Management

Also called: CLM (Cache-based Lazy Memory management)

## Overview
Cache-based Lazy Memory Management (CLM) is a memory offloading system that enables the training of large-scale 3D Gaussian Splatting (3DGS) scenes on a single consumer-grade GPU by exploiting the inherent sparsity of memory access patterns [S1]. Unlike naive offloading strategies that load the entire scene representation to the GPU, CLM keeps Gaussians in CPU memory and loads only the subset accessed by the current view, overlapping communication with computation to hide latency [S1]. This approach allows training scenes with over 100 million Gaussians on hardware with limited VRAM, such as the NVIDIA RTX 4090, without requiring multi-GPU setups or compromising rendering quality [S1].

## How it works
### Inputs and Outputs
*   **Input:** A set of posed training images (views) with known camera parameters; a scene representation consisting of $N$ 3D Gaussians stored in CPU memory.
*   **Output:** Updated Gaussian parameters (position, covariance, spherical harmonics, opacity) and gradients, optimized via the Adam optimizer.

### Data Structures and Layout
Each 3D Gaussian consists of 59 learnable parameters [S1]. During training, each parameter requires storage for the value, its gradient, and two optimizer state variables (Adam moments), totaling 4 floating-point numbers per parameter [S1]. Assuming 4 bytes per float, the memory footprint per Gaussian is:
$$ \text{Memory per Gaussian} = 59 \times 4 \times 4 = 944 \text{ bytes} $$
The total memory for the model state of $N$ Gaussians is:
$$ \text{Total Memory} = N \times 59 \times 4 \times 4 \text{ bytes} $$
The attributes comprising the 59 parameters are [S1]:
*   **3D Position:** 3 parameters.
*   **Covariance (Scale + Rotation):** 3 + 4 = 7 parameters.
*   **Spherical Harmonics (Color):** 48 parameters.
*   **Opacity:** 1 parameter.

### Steps and Algorithm
CLM operates by identifying the sparse subset of Gaussians relevant to each training view and managing their transfer between CPU and GPU memory [S1].

1.  **Pre-compute Access Sets:** For each training view, compute the set of Gaussians that will be accessed (rasterized) during the forward pass. This is done ahead-of-time to enable pipelining [S1].
2.  **Cache Overlapping Gaussians:** Identify Gaussians that are accessed by multiple views. Cache these overlapping Gaussians in GPU memory to reduce redundant communication volume during training iterations [S1].
3.  **Schedule Iterations for Spatial Locality:** Order training iterations such that views in the same spatial region are processed consecutively. This maximizes the reuse of cached Gaussians across successive iterations, minimizing the total communication volume [S1].
4.  **Overlap Communication and Computation:**
    *   Load the required Gaussians for the current iteration while computing the forward pass for the previous iteration.
    *   Overlap gradient computation with a substantial portion of the Gaussian parameter update [S1].
5.  **Update Parameters:** Run the Adam optimizer on the CPU using the computed gradients to update the Gaussian parameters in CPU memory [S1].

### Pseudocode
```python
# Global state
cpu_memory = Array of N Gaussians (59 params each)
gpu_cache = Empty set of Gaussians
gpu_memory = Empty buffer for active Gaussians

# Pre-computation phase
for each view v in training_views:
    v.access_set = compute_gaussians_accessed(v)

# Training loop
for iteration in range(num_iterations):
    # 1. Select view based on spatial locality scheduling
    view = schedule_next_view()
    
    # 2. Identify Gaussians needed for this view
    needed_gaussians = view.access_set
    
    # 3. Manage GPU Cache and Communication
    # Calculate which Gaussians need to be loaded from CPU
    to_load = needed_gaussians - gpu_cache
    
    # Start asynchronous transfer of new Gaussians to GPU
    # This overlaps with the computation of the previous iteration
    if to_load is not empty:
        async_transfer_to_gpu(to_load, from=cpu_memory, to=gpu_memory)
        
    # 4. Forward Pass and Backward Pass
    # Render image using Gaussians currently in gpu_cache + loaded ones
    rendered_image = rasterize(gpu_cache, gpu_memory)
    
    # Compute loss and gradients
    loss = compute_loss(rendered_image, ground_truth)
    gradients = backpropagate(loss)
    
    # 5. Update Cache
    # Add newly accessed Gaussians to cache for future reuse
    gpu_cache = gpu_cache union needed_gaussians
    
    # 6. Parameter Update on CPU
    # Overlap this with the next iteration's communication if possible
    update_adam_optimizer(cpu_memory, gradients)
    
    # Note: Naive offloading would load ALL Gaussians here, causing memory overflow
    # CLM only loads the subset in needed_gaussians
```

### Parameters and Typical Values
*   **Gaussian Parameter Count:** 59 per Gaussian [S1].
*   **Bytes per Parameter:** 16 bytes (4 bytes for parameter, 4 for gradient, 8 for optimizer state) [S1].
*   **Hardware:** Tested on NVIDIA RTX 4090 (24GB VRAM) [S1].
*   **Scene Scale:** Successfully trained scenes with 100–102 million Gaussians [S1].

### Edge Cases and Pitfalls
*   **Naive Offloading Overhead:** Simply offloading all Gaussians to the CPU and loading them per iteration incurs significant performance overhead due to CPU-GPU communication latency and the time required to run the Adam optimizer on the CPU [S1].
*   **Memory Limits:** Without CLM, an RTX 4090 can only store the model state for up to 26 million Gaussians, ignoring activation states and temporary buffers [S1]. Scenes requiring more Gaussians (e.g., Rubble, Alameda, Ithaca, MatrixCity BigCity) cannot be trained on a single consumer GPU without this method [S1].
*   **Communication Volume:** Failure to cache overlapping Gaussians or schedule views by spatial locality results in excessive data transfer between CPU and GPU, negating the benefits of offloading [S1].

## Operating characteristics
*   **Memory Complexity:** Scales linearly with the number of Gaussians in CPU memory ($O(N)$), but GPU memory usage is bounded by the maximum number of Gaussians accessed by any single view or batch of views, rather than the total scene size [S1].
*   **Performance:** Achieves state-of-the-art reconstruction quality for large scenes on a single consumer GPU [S1]. Incurs modest performance overhead compared to baseline systems when rendering small scenes that fit entirely in GPU memory [S1].
*   **Strengths:** Eliminates the need for multi-GPU setups; enables training of very large scenes (100M+ Gaussians) on consumer hardware; maintains high rendering quality [S1].
*   **Limitations:** Performance is dependent on the efficiency of CPU-GPU communication; requires careful scheduling and caching logic to hide latency [S1].
*   **When to Use:** When training large-scale 3DGS scenes on hardware with limited VRAM (e.g., single consumer GPU) and multi-GPU setups are unavailable or too costly [S1].
*   **When Not to Use:** For small scenes that fit entirely within GPU memory, where the overhead of offloading logic may not provide benefits over direct GPU storage [S1].

## Background
3D Gaussian Splatting (3DGS) has become a popular novel view synthesis approach due to its fast rendering time and high-quality output [S1]. However, scaling 3DGS to large or intricate scenes presents a significant memory barrier, as the number of Gaussians required often exceeds the VRAM capacity of consumer-grade GPUs [S1]. Existing solutions either use multiple GPUs (adding cost) or reduce scene fidelity (compromising quality) [S1]. CLM was introduced to address this by leveraging the inherent sparsity of 3DGS memory access patterns, allowing the system to scale to large scenes without multiple GPUs or quality loss [S1]. The method was presented in the paper "CLM: Removing the GPU Memory Barrier for 3D Gaussian Splatting," accepted to ASPLOS ’26 [S1].
