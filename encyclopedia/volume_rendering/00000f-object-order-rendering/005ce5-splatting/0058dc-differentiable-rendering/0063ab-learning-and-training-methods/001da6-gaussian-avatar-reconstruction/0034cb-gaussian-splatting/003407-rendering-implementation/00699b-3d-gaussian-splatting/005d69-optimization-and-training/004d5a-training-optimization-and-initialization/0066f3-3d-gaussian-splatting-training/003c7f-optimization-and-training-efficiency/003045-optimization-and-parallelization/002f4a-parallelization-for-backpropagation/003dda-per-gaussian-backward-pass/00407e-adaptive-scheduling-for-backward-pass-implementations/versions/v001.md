# Adaptive Scheduling for Backward Pass Implementations

Also called: Rasterization backward with adaptive scheduling, Thompson sampling scheduler for backward pass

## Overview
This method optimizes the backward pass of 3D Gaussian Splatting rasterization by dynamically selecting between two distinct parallelization strategies to minimize atomic contention and maximize GPU thread utilization [S1, unofficial]. It addresses the performance variability inherent in fixed implementations, where scene geometry and training configuration determine which strategy is faster [S1, unofficial]. Unlike static approaches, it uses a Thompson sampling scheduler to automatically identify and prefer the lower-latency implementation for each batch [S1, unofficial].

## How it works
The method switches between two rasterization backward implementations based on real-time latency measurements.

**Inputs and Outputs**
*   **Input:** A batch of projected Gaussians binned to a tile, with $N$ Gaussians and $P$ pixels in the tile.
*   **Output:** Accumulated gradients for Gaussian parameters.

**Data Structures**
*   **Shared Memory:** Used in Implementation 2 to store pre-computed transmittance and derivatives for each Gaussian-pixel pair.
*   **Latency Beliefs:** Probability distributions (Beta distributions) tracking the estimated latency of each implementation.

**Parameters**
*   **Batch Size ($S$):** The number of Gaussians processed per thread block. Calculated as $S = \lceil \sqrt{NP} \rceil$, rounded up to a multiple of the subgroup size, and capped at 128 [S1, unofficial]. This value balances performance and hardware occupancy [S1, unofficial].
*   **Gaussian Parameterization:** Projected Gaussians are parameterized following [LDC* 25] to simplify opacity computation into matrix multiplication, enabling efficient parallel computation [S1, unofficial].

**Algorithm Steps**

1.  **Initialize Scheduler:** Initialize latency belief distributions for Implementation 1 and Implementation 2.
2.  **Select Implementation:** For the current batch, use Thompson sampling to randomly select an implementation. The selection probability is higher for implementations with lower estimated latency [S1, unofficial].
3.  **Execute Selected Implementation:**
    *   **If Implementation 1 is selected:**
        1.  Launch one thread block per tile.
        2.  Compute batch size $S = \text{cap}(\text{round\_up}(\sqrt{NP}, \text{subgroup\_size}), 128)$ [S1, unofficial].
        3.  Process Gaussians in batches of size $S$.
        4.  Compute gradients by parallelizing over Gaussians, reducing atomic contention compared to pixel-parallel approaches [S1, unofficial].
    *   **If Implementation 2 is selected:**
        1.  **Forward Pass (Pixel-Parallel):** For the current Gaussian batch, run a forward pass parallelized over pixels. Compute transmittance and its derivative with respect to Gaussian parameters for each Gaussian-pixel pair. Store these values in shared memory [S1, unofficial].
        2.  **Backward Pass (Gaussian-Parallel):** Run a backward pass parallelized over Gaussians. Fetch the pre-computed transmittance and derivatives from shared memory. Compute the accumulated gradient for each Gaussian [S1, unofficial].
4.  **Update Scheduler:** Measure the actual latency of the executed implementation. Update the corresponding latency belief distribution based on the measured time [S1, unofficial].

**Edge Cases and Pitfalls**
*   **Precision:** The closed-form solution for ellipse-tile intersection must be branchless to avoid divergence [S1, unofficial].
*   **Boundaries:** The ellipse range within a tile row is bounded by either the tile boundary or global extreme points of the ellipse, ensuring no false positives or negatives [S1, unofficial].
*   **Hardware Occupancy:** The batch size cap of 128 is chosen to balance performance and hardware occupancy [S1, unofficial].

## Subtopics

### Adaptive View and Pixel Sampling Scheduling
A scheduling mechanism that jointly adjusts the tile-wise pixel sampling rate ($r_{tile}$) and the number of sampled views ($K$) over training iterations to allocate more computation during difficult stages and reduce it as optimization converges [S2, unofficial]. It uses a progress coefficient $\rho_t = 1 - \text{clip}(t/\tau_{until}, 0, 1)$ to anneal sampling after densification [S2, unofficial]. The tile-wise pixel sampling rate is scheduled as $r_{tile}^{(t)} = r_{min} + (r_{max} - r_{min}) (1 - \rho_t \phi(r_t))$, and the sampled view number as $K_t = \text{round}(K_{min} + (K_{max} - K_{min})e^{-\alpha(1-\rho_t \phi(r_t))})$ [S2, unofficial]. A sinusoidal error-ratio scheduling function $\phi(r_t)$ is used, which outperforms linear and exponential variants [S2, unofficial]. Pitfalls include performance degradation with a very small view budget ($K=1$) due to insufficient multi-view constraints, and increased training time without quality gains with a large fixed budget ($K=10$) [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** The method reduces the number of required atomic operations by parallelizing over Gaussians instead of pixels, which can reduce contention by a factor equal to the number of pixels in each tile (256 for 16x16 tiles) [Parent]. The adaptive scheduling further optimizes this by selecting the faster implementation [S1, unofficial].
*   **Memory Complexity:** Implementation 2 requires shared memory to store transmittance and derivatives for each Gaussian-pixel pair [S1, unofficial].
*   **Measured Performance:** On NVIDIA RTX 3090, Implementation 2 is 20%-30% faster than Implementation 1 on the Mip-NeRF 360 bicycle scene, while Implementation 1 is faster on the garden scene [S1, unofficial].
*   **Strengths:** Automatically adapts to scene and training configuration, minimizing latency without manual tuning [S1, unofficial].
*   **Limitations:** Requires Thompson sampling overhead and shared memory management for Implementation 2 [S1, unofficial].
*   **When to Use:** When training 3D Gaussian Splatting on varying scenes where fixed backward implementations show inconsistent performance [S1, unofficial].

## Background
The method originates from the VkSplat paper, which introduces high-performance 3DGS training in Vulkan Compute [S1, unofficial]. It addresses the limitations of existing implementations that launch threads per pixel, resulting in high atomic contention [S1, unofficial]. The approach builds on prior work parallelizing threads over Gaussians [MGK* 24] and optimizing Gaussian parameterization [LDC* 25] [S1, unofficial].
