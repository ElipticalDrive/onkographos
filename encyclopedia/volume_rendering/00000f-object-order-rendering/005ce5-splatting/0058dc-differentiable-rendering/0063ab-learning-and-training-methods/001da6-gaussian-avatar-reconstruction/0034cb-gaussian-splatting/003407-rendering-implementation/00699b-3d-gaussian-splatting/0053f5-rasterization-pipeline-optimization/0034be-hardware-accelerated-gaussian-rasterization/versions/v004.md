# Hardware-Accelerated Gaussian Rasterization

Also called: GauRast, Hardware Architecture Pipeline, Hardware-algorithm co-design for Gaussian rasterization

## Overview
Hardware-Accelerated Gaussian Rasterization is a hardware-algorithm co-design that augments standard triangle rasterizers with dedicated hardware units for Gaussian projection and blending, achieving an order-of-magnitude speedup in the rasterization stage [S1, unofficial][S2]. It solves the computational bottleneck of projecting and compositing 3D Gaussians by replacing general-purpose compute shaders with a specialized four-stage pipeline [S2]. Unlike sibling methods that rely on software-based sorting and blending on GPUs, this approach isolates near-plane culling and projection into point-based preprocessing stages, while handling sorting and rasterization in tile-based rendering stages [S2].

## How it works
The method implements a four-stage hardware pipeline: Stage 0 (Near-plane Culling), Stage 1 (Projection), Stage 2 (Sorting), and Stage 3 (Rasterization) [S2]. The preprocessing steps (0-1) are point-based, while the rendering steps (2-3) are tile-based [S2].

**Inputs and Outputs:**
*   **Input:** 3D Gaussian parameters (position, covariance, opacity, spherical harmonics).
*   **Output:** 2D image pixels with alpha-composited colors.

**Data Structures:**
*   **Tile Assignment:** The image is divided into 16x16 pixel tiles [S2]. Each tile is assigned to an independent SRAM bank [S2].
*   **SRAM Bank Layout:** Each bank has a fixed entry depth and an address offset controller [S2]. An index is used to look up values in a codebook [S2].
*   **Sorting Output:** The sorting unit outputs the current maximum value in a linear sorting delay, aligning with the alpha-blending process [S2].

**Numbered Steps:**

1.  **Stage 0: Near-plane Culling.**
    *   Eliminates parameter access for invisible regions using an AABB (Axis-Aligned Bounding Box) depth-interval test [S2].
    *   This stage is isolated to process the largest number of Gaussian points efficiently [S2].

2.  **Stage 1: Projection.**
    *   Projects 3D Gaussians onto the 2D image plane [S2].
    *   Uses a 6x1 multiplier-accumulator array [S2].
    *   Implements zero-Jacobian skipping to optimize matrix multiplication [S2].

3.  **Stage 2: Gaussian Sorting.**
    *   Sorts Gaussians by depth within each tile to enable front-to-back alpha compositing [S2].
    *   Uses a four-way sub-sorter parallelism design based on a comparison-free sorter [S2].
    *   Each sub-sorter processes 256 data elements at a time [S2].
    *   The design minimizes critical path delay associated with N-input OR gates [S2].
    *   Outputs the current maximum value linearly to support the rasterization stage [S2].

4.  **Stage 3: Rasterization.**
    *   Performs alpha-blending, processing one point at a time aligned with the sorting output [S2].
    *   Uses the sorted order to composite Gaussians onto the 16x16 tile pixels [S2].

**Formulas:**
*   The sources do not provide explicit mathematical formulas for the projection or blending in this specific hardware architecture, referencing Eq. (2) for the projection skipping mechanism [S2].
*   A bitwise operation for frame buffer updates is noted as $FO_{NEW} = Fo \& (\sim Fo + 1'b1)$ [S2].

**Parameters:**
*   **Tile Size:** 16x16 pixels [S2].
*   **Sub-sorter Capacity:** 256 data elements [S2].

**Edge Cases and Pitfalls:**
*   Data dependencies in processing elements (PEs) limit full parallelization, as certain computations must wait for others [S2].
*   The number of Gaussian points $N$ varies depending on the scene or view, affecting timing [S2].

## Subtopics

### Compressed 3D Gaussian Splatting Renderer
A renderer for compressed scenes that uses GPU sorting and hardware rasterization instead of the specialized compute pipeline used in original 3D Gaussian Splatting [S3]. It differs from the original compute pipeline by enabling seamless integration into VR/AR environments or games alongside polygon models [S3]. It is chosen when real-time novel view synthesis is required on low-end devices with limited video memory or when integration with existing polygonal rendering pipelines is necessary [S3].

### LS-Gaussian Hardware Architecture
A dedicated hardware accelerator built upon GSCore that enables early stages to process subsequent frames while later stages execute previous ones, improving parallelism and pipeline efficiency [S4]. It enhances the Culling and Conversion Unit (CCU) by replacing dual OBB Intersection Test Units (OIUs) with square root and logarithmic operators for a two-stage accurate intersection test [S4]. It uses a Viewpoint Transformation Unit (VTU) for sparse rendering, retrieving pixel colors and maximum depths from reference frames and performing three matrix multiplications (map 2D to 3D, transform point cloud, reproject) [S4]. A counter array tracks validly projected pixels per tile; if the count exceeds 56 (of total pixels in a tile), the tile is interpolated; otherwise, it is forwarded to the Volume Rendering Unit (VRU) for full re-rendering [S4]. Components include CCU, LDU, VTU, VRU, Sorting Unit, and Interpolation Unit [S4].

## Operating characteristics
*   **Performance:** Achieves an order-of-magnitude speedup in the rasterization stage compared to standard software implementations [S1, unofficial].
*   **Complexity:** The sorting unit uses a comparison-free sorter with four-way sub-sorter parallelism, processing 256 elements per sub-sorter [S2].
*   **Memory:** Uses independent SRAM banks for each 16x16 tile with fixed entry depth and address offset controllers [S2].
*   **Strengths:** High throughput due to hardware specialization; reduced memory requirements for rasterization due to linear sorting delay alignment with alpha-blending [S2].
*   **Limitations:** Data dependencies in PEs limit full parallelization [S2]. The specific hardware design is not general-purpose and requires custom silicon or FPGA implementation [S2].
*   **Scaling:** The number of Gaussian points $N$ varies, impacting timing [S2].

## Background
The concept of hardware-accelerated Gaussian rasterization emerged as a response to the computational demands of 3D Gaussian Splatting (3DGS) [S1, unofficial]. Original 3DGS relied on specialized compute pipelines that were difficult to integrate with standard graphics APIs and polygonal rendering [S3]. GauRast [116] proposed augmenting standard triangle rasterizers with dedicated units for Gaussian projection and blending [S1, unofficial]. Subsequent work, such as LS-Gaussian, further optimized this by designing dedicated hardware accelerators built upon existing graphics cores (GSCore) to improve pipeline efficiency and reduce stalls [S4].
