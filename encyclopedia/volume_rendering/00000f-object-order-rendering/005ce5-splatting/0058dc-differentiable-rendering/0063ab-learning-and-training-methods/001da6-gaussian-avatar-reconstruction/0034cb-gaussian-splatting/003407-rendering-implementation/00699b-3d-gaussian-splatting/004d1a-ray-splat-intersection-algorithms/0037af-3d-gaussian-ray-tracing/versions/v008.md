# 3D Gaussian Ray Tracing

Also called: 3DGRT, BVH Ray Tracing for 3D Gaussians, Point-based Ray Tracing on 3D Gaussians, Ray-Splat Intersection via BVH, Splat BVH Traversal

## Overview
3D Gaussian Ray Tracing (3DGRT) is a rendering method that evaluates 3D Gaussian splats using hardware-accelerated ray tracing instead of rasterization [S1, unofficial][S4]. It solves the problem of linear scaling in dense scenes by using a Bounding Volume Hierarchy (BVH) to traverse only Gaussians that intersect the viewing ray, enabling logarithmic complexity relative to the number of splats [S1, unofficial][S4]. Unlike rasterization-based splatting which evaluates all Gaussians overlapping a tile, 3DGRT explicitly handles semi-transparency by accumulating transmittance through all intersected Gaussians, avoiding the depth-sorting artifacts inherent in tile-based rasterization [S2, S4].

## How it works
**Inputs:**
*   Camera ray: Origin $\mathbf{o}$, direction $\mathbf{d}$ (normalized).
*   Scene: Set of $N$ 3D Gaussians, each defined by mean $\boldsymbol{\mu}_i$, covariance $\boldsymbol{\Sigma}_i$, opacity $\alpha_i$, and color $c_i$.
*   BVH: A binary radix tree or bounding volume hierarchy storing tight bounding boxes for the Gaussians.

**Outputs:**
*   Pixel color $C(\mathbf{o}, \mathbf{d})$ and accumulated transmittance.

**Data Structures:**
1.  **BVH Nodes:** Each node contains an Axis-Aligned Bounding Box (AABB) defined by min/max coordinates. In texture-based implementations, nodes are stored in a 2D texture where each node is a `uvec4` (ID, min.x/max.x, min.y/max.y, min.z/max.z) [S3, unofficial]. Inner nodes have negative IDs; leaf nodes have positive IDs corresponding to Gaussian indices [S3, unofficial].
2.  **Gaussian Proxy:** Each Gaussian is associated with a proxy triangle mesh or a tight bounding box [S1, unofficial][S4]. In texture-based approaches, Gaussian parameters (position, basis vectors, color, opacity) are stored in a triangle texture, with each splat occupying two texels [S3, unofficial].

**Algorithm Steps:**

1.  **BVH Construction:**
    *   Construct a binary radix tree from the 3D Gaussians [S2].
    *   Leaf nodes represent tight bounding boxes of individual Gaussians.
    *   Internal nodes denote the bounding box of their two children [S2].
    *   *Note:* For static scenes, visibility can be pre-computed to accelerate indirect lighting queries [S2].

2.  **Ray-BVH Traversal:**
    *   Start at the root node.
    *   Perform ray-AABB intersection tests. Compute near ($t_{min}$) and far ($t_{max}$) intersection distances for each axis.
    *   Valid intersection if $\max(t_{min}) \le t_{max}$ and $t_{max} > 0$ [S3, unofficial].
    *   Recursively traverse children.
    *   **Mode Selection:**
        *   *Closest-Hit:* Sort children by near plane ($t_0$). Process the closer child first. Stop after finding the first leaf intersection [S3, unofficial].
        *   *Any-Hit:* Sort children by far plane ($t_1$). Collect all leaf intersections. Insert hits into a sorted array (max size $N_{INT}=32$) by depth [S3, unofficial].

3.  **Gaussian Intersection & Contribution:**
    *   Upon reaching a leaf node (Gaussian $i$), compute the equivalent intersection point $\mathbf{r}_x$ along the ray where the Gaussian's contribution peaks [S2]:
        $$ t_j = \frac {(\boldsymbol {\mu}_i - \mathbf{o})^T \boldsymbol {\Sigma}_i \mathbf{d}}{\mathbf{d}^T \boldsymbol {\Sigma}_i \mathbf{d}} $$
        $$ \mathbf{r}_x = \mathbf{o} + t_j \mathbf{d} $$
    *   Approximate the Gaussian's contribution as its opacity $\alpha_i$ at $\mathbf{r}_x$ [S2].
    *   *Alternative Proxy Method:* If using proxy triangles, solve for intersection parameters $u, v, t$ using the basis vectors and ray direction. Hit if $t > 0$ and $u^2 + v^2 < 1.0$ [S3, unofficial].

4.  **Accumulation:**
    *   Initialize transmittance $T = 1.0$.
    *   Iterate through the sorted list of intersected Gaussians (from closest to farthest).
    *   For each Gaussian $i$ with opacity $\alpha_i$ and color $c_i$:
        $$ C_{accum} += T \cdot \alpha_i \cdot c_i $$
        $$ T \leftarrow T \cdot (1 - \alpha_i) $$
    *   The order of encounter does not affect the final transmittance product, but depth sorting is required for correct alpha blending [S2].
    *   **Early Termination:** If $T < T_{min}$ (threshold), stop traversal [S2].

**Pseudocode:**

```python
def render_ray_3d_gaussian_ray_tracing(ray_origin, ray_dir, bvh_root, gaussians, t_min_threshold=1e-4):
    """
    Renders a single ray using 3D Gaussian Ray Tracing.
    Supports Any-Hit mode for full transparency accumulation.
    """
    # Stack for iterative BVH traversal
    stack = [(bvh_root, 0.0, ray_dir)]
    intersections = []

    while stack:
        node, t_far, _ = stack.pop()

        # Ray-AABB Intersection
        t0, t1 = intersect_aabb(ray_origin, ray_dir, node.aabb)
        
        # If no intersection or behind camera, skip
        if t1 < 0 or t0 > t1:
            continue

        # If leaf node
        if node.is_leaf:
            gaussian_id = node.gaussian_id
            g = gaussians[gaussian_id]
            
            # Compute equivalent intersection parameter t_j
            # t_j = ((mu - o)^T Sigma d) / (d^T Sigma d)
            mu = g.mean
            sigma = g.covariance
            d = ray_dir
            o = ray_origin
            
            numerator = dot(sub(mu, o), multiply(sigma, d))
            denominator = dot(multiply(sigma, d), d)
            
            if abs(denominator) < 1e-8:
                continue
                
            t_j = numerator / denominator
            
            # Only consider if in front of camera
            if t_j > 0:
                intersections.append({
                    't': t_j,
                    'opacity': g.opacity,
                    'color': g.color,
                    'id': gaussian_id
                })
        else:
            # Internal node: push children to stack
            # Sort by t_far for any-hit mode to process closer nodes first?
            # Actually, for any-hit we just need to collect all. 
            # Optimization: push farther child first so closer is processed first (LIFO)
            child_a = node.left
            child_b = node.right
            
            # Calculate t_far for children to determine push order
            _, t_far_a = intersect_aabb(ray_origin, ray_dir, child_a.aabb)
            _, t_far_b = intersect_aabb(ray_origin, ray_dir, child_b.aabb)
            
            if t_far_a > t_far_b:
                stack.append((child_a, t_far_a, ray_dir))
                stack.append((child_b, t_far_b, ray_dir))
            else:
                stack.append((child_b, t_far_b, ray_dir))
                stack.append((child_a, t_far_a, ray_dir))

    # Sort intersections by depth (t)
    intersections.sort(key=lambda x: x['t'])

    # Accumulate color and transmittance
    color = vec3(0.0)
    transmittance = 1.0

    for hit in intersections:
        alpha = hit['opacity']
        c = hit['color']
        
        color += transmittance * alpha * c
        transmittance *= (1.0 - alpha)
        
        # Early termination
        if transmittance < t_min_threshold:
            break

    return color, transmittance
```

## Operating characteristics
*   **Time Complexity:** Logarithmic scaling with respect to the number of Gaussians in dense scenes, $O(\log N)$ per ray, compared to linear $O(N)$ for rasterization when tiles contain many splats [S1, unofficial][S4].
*   **Memory Complexity:** Requires storage for the BVH structure. Texture-based implementations store BVH nodes and Gaussian proxies in large 2D textures (e.g., 4096x4096 for BVH, 2048x2048 for triangles) [S3, unofficial].
*   **Performance:** On tested hardware, 3DGRT was initially ~9× slower than a recent version of 3DGS rasterization [S4]. However, it avoids the linear scaling penalty of rasterization in highly dense scenes with tiny Gaussians [S1, unofficial].
*   **Strengths:** Correct handling of semi-transparency and depth ordering without sorting; efficient culling of non-intersected Gaussians; suitable for hardware-accelerated ray tracing (e.g., OptiX) [S1, unofficial][S2, S4].
*   **Limitations:** Higher overhead per ray compared to rasterization for sparse scenes; precision issues in BVH traversal due to floating-point comparisons; computational complexity for online visibility querying in dynamic scenes [S2][S3, unofficial].
*   **When to use:** Dense scenes with many small Gaussians; scenes requiring physically plausible transparency; hardware with efficient ray-tracing cores.
*   **When not to use:** Sparse scenes where rasterization overhead is lower; dynamic scenes requiring frequent BVH rebuilds without pre-computation [S2].

## Background
3D Gaussian Ray Tracing was first studied by Moenne-Loccoz et al. [2024] as an alternative for rendering 3D Gaussians using hardware-accelerated ray tracing (e.g., OptiX) [S4]. It builds on earlier work in point-based ray tracing and BVH construction for real-time rendering [S2]. The method addresses the limitations of rasterization-based 3D Gaussian Splatting, particularly regarding transparency artifacts and scaling in dense environments [S1, unofficial][S4].
