# Cache-based Lazy Memory Management

Also called: CLM (Cache-based Lazy Memory management)

## Overview
Cache-based Lazy Memory Management (CLM) is a memory offloading technique that enables the training of large-scale 3D Gaussian Splatting (3DGS) scenes on a single consumer-grade GPU by keeping the majority of Gaussians in CPU memory and loading them only when necessary [S1]. It exploits the inherent sparsity of 3DGS memory access patterns, where each training iteration accesses only a small subset of the scene's Gaussians, to minimize GPU memory usage while hiding CPU-GPU communication overhead through pipelining [S1]. Unlike naive offloading strategies that load all Gaussians to the GPU, CLM reduces the memory footprint to the active subset and overlaps communication with computation to maintain performance [S1].

## How it works
CLM operates by partitioning the 3D Gaussian dataset between GPU and CPU memory, dynamically managing the transfer of Gaussians based on the specific view being rendered in each training iteration [S1]. The method relies on four key observations regarding the 3DGS training pipeline: (1) the set of Gaussians accessed by a view can be computed ahead-of-time; (2) there is substantial overlap in Gaussian access between different views; (3) training exhibits spatial locality, meaning views in the same region access similar Gaussians; and (4) gradient computation and parameter updates can be overlapped with communication [S1].

### Inputs and Outputs
*   **Inputs:**
    *   $\mathcal{G}_{total}$: The complete set of $N$ 3D Gaussians stored in CPU memory.
    *   $\mathcal{V}$: The set of training views (images with poses).
    *   $GPU_{mem}$: The available memory on the consumer-grade GPU (e.g., 24 GB on RTX 4090) [S1].
*   **Outputs:**
    *   $\mathcal{G}_{GPU}$: The subset of Gaussians currently resident in GPU memory.
    *   Updated parameters for $\mathcal{G}_{GPU}$ after the training iteration.

### Data Structures
Each 3D Gaussian consists of 59 learnable parameters [S1]. These parameters are stored in a format that includes the parameter value, its gradient, and two additional versions for the Adam optimizer state [S1].

*   **Gaussian Parameter Layout:**
    *   **3D Position:** 3 parameters.
    *   **Covariance (Scale + Rotation):** 3 + 4 = 7 parameters.
    *   **Spherical Harmonics:** 48 parameters.
    *   **Opacity:** 1 parameter.
    *   **Total Parameters per Gaussian:** 59 [S1].

*   **Memory Layout per Parameter:**
    *   Each parameter requires 4 bytes for the value, 4 bytes for the gradient, and 2 additional 4-byte versions for optimizer state [S1].
    *   Total memory per parameter: $4 \times 4 = 16$ bytes [S1].

*   **Total Memory per Gaussian:**
    *   $59 \text{ params} \times 16 \text{ bytes/param} = 944$ bytes [S1].

*   **Total Model State Memory:**
    *   For $N$ Gaussians, the memory required is $N \times 59 \times 4 \times 4$ bytes [S1].

### Numbered Steps
1.  **Pre-compute Access Sets:** For each training view $v \in \mathcal{V}$, compute the set of Gaussians $\mathcal{G}_v$ that will be accessed during the rasterization and back-propagation of that view. This is done ahead-of-time [S1].
2.  **Identify Overlaps:** Analyze the access sets $\mathcal{G}_v$ to identify Gaussians that are accessed by multiple views. These overlapping Gaussians are candidates for caching in GPU memory to reduce repeated communication [S1].
3.  **Schedule Iterations:** Order the training iterations (views) to exploit spatial locality. Views that are spatially close and likely to access the same Gaussians are scheduled consecutively to maximize the reuse of cached Gaussians in GPU memory [S1].
4.  **Pipeline Execution:** For each training iteration $i$ corresponding to view $v_i$:
    a.  **Overlap Communication:** Initiate the transfer of required Gaussians from CPU to GPU for the *next* iteration $v_{i+1}$ while the GPU is computing the current iteration $v_i$. This overlaps GPU computation with CPU-GPU communication [S1].
    b.  **Rasterize:** Perform the 3DGS rasterization on the currently loaded Gaussians $\mathcal{G}_{GPU}$ for view $v_i$ [S1].
    c.  **Back-propagate:** Compute gradients for the loaded Gaussians [S1].
    d.  **Overlap Updates:** Overlap the gradient computation and a substantial portion of the Gaussian parameter update (Adam optimizer step) with the ongoing communication for the next iteration [S1].
5.  **Update Memory:** After the iteration, update the GPU memory cache with the newly accessed Gaussians for the next step, evicting those no longer needed based on the schedule [S1].

### Pseudocode
```python
# Initialize GPU memory cache with empty set
GPU_cache = set()
# Pre-compute access sets for all views
access_sets = {v: compute_access_set(v) for v in views}
# Schedule views to maximize spatial locality and cache reuse
scheduled_views = schedule_views(views, access_sets)

for i in range(len(scheduled_views)):
    current_view = scheduled_views[i]
    next_view = scheduled_views[i+1] if i+1 < len(scheduled_views) else None
    
    # Step 1: Overlap communication for next view with current computation
    if next_view is not None:
        required_next = access_sets[next_view]
        # Identify Gaussians in next view not currently in GPU cache
        to_load = required_next - GPU_cache
        # Initiate asynchronous transfer of to_load from CPU to GPU
        async_transfer_cpu_to_gpu(to_load)
    
    # Step 2: Rasterize current view using currently loaded Gaussians
    # Ensure all required Gaussians for current_view are in GPU_cache
    # (This may involve blocking if previous async transfer is not complete,
    # but ideally pipelined)
    ensure_in_cache(access_sets[current_view])
    
    # Perform forward pass (rasterization) and backward pass (gradient computation)
    rendered_image = rasterize(current_view, GPU_cache)
    gradients = compute_gradients(rendered_image, ground_truth[current_view])
    
    # Step 3: Overlap parameter update with communication
    # Update parameters for Gaussians in current_view
    update_parameters(GPU_cache, gradients)
    
    # Update GPU cache state
    GPU_cache = access_sets[current_view]
```

### Parameters
*   **Gaussian Parameter Count:** 59 per Gaussian [S1].
*   **Memory per Parameter:** 16 bytes (4 bytes for parameter, 4 bytes for gradient, 8 bytes for optimizer state) [S1].
*   **Typical Hardware:** Consumer-grade GPU with 24 GB memory (e.g., NVIDIA RTX 4090) [S1].

### Edge Cases and Pitfalls
*   **Naive Offloading Overhead:** Naively offloading all Gaussians to the CPU and loading them per iteration incurs significant performance overhead due to CPU-GPU communication latency and the time required to run the Adam optimizer on the CPU [S1].
*   **Memory Proportionality:** Naive offloading fails to scale because it still requires loading all Gaussians to the GPU at some point, keeping GPU memory requirements proportional to the total number of Gaussians [S1].
*   **Precision:** Not given in the sources.
*   **Boundaries:** The system must handle cases where the number of Gaussians exceeds the GPU memory capacity (e.g., 102 million Gaussians on an RTX 4090) by strictly limiting the GPU cache to the active subset [S1].

## Operating characteristics
*   **Time Complexity:** The method aims to hide communication overhead by overlapping it with GPU computation and CPU-based parameter updates [S1]. The performance overhead is described as "modest" compared to a baseline without offloading for small scenes [S1].
*   **Memory Complexity:** GPU memory usage is proportional to the number of Gaussians accessed by a single view (or a small batch of views), rather than the total number of Gaussians $N$ [S1]. This allows scaling to scenes with 100-102 million Gaussians on a 24 GB GPU [S1].
*   **Measured Performance:** CLM successfully trains a scene with 102 million Gaussians on a single RTX 4090 [S1]. It achieves state-of-the-art reconstruction quality [S1].
*   **Strengths:** Enables training of large scenes on single consumer GPUs; reduces GPU memory requirements; maintains rendering quality [S1].
*   **Limitations:** Requires careful scheduling and pre-computation of access sets; performance may degrade if spatial locality is poor or if the active subset is too large for the GPU [S1].
*   **When to Use:** When training large-scale 3DGS scenes on hardware with limited GPU memory (e.g., consumer-grade GPUs) [S1].
*   **When Not to Use:** When sufficient GPU memory is available to hold all Gaussians, as naive in-GPU training may be simpler and potentially faster due to lower latency [S1].

## Background
CLM was introduced in the paper "CLM: Removing the GPU Memory Barrier for 3D Gaussian Splatting," accepted to ASPLOS ’26 [S1]. The work addresses the memory barrier that prevents scaling 3DGS to large scenes on single consumer-grade GPUs, which typically have 24 GB of memory [S1]. Prior to CLM, scaling 3DGS required either multiple GPUs (adding significant cost) or reducing scene fidelity through pruning [S1]. The core insight is that 3DGS computation is inherently sparse, allowing for effective memory offloading [S1].
