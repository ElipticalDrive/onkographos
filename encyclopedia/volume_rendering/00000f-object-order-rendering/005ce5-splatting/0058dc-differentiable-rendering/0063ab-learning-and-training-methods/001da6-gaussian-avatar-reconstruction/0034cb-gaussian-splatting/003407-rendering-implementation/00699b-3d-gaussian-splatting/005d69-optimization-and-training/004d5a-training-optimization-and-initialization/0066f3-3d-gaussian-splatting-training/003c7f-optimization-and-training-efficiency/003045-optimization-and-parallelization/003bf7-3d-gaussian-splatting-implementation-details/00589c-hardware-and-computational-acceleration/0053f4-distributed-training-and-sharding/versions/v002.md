# Distributed Training and Sharding

Also called: Primitive Sharding, Index-Parity Sharding

## Overview
Distributed training and sharding techniques enable the training of large-scale 3D Gaussian Splatting (3DGS) models across multiple GPUs by partitioning the global Gaussian set or the rendering workload. Unlike spatial block partitioning, which suffers from boundary redundancy and load imbalance, modern methods like BlitzGS use index-parity sharding to distribute Gaussians evenly across devices [S2, unofficial]. This family addresses the computational bottleneck of processing overly dense primitive sets by combining distributed data parallelism with importance-based pruning and view-level filtering [S1].

## Shared principles
The family shares the goal of reducing the active Gaussian workload per iteration to accelerate training or inference. The core mechanism involves distributing the global set of 3D Gaussians $\mathcal{G}$ across $M$ GPUs. Each GPU maintains a local shard $\mathcal{G}^{(m)}$ and its corresponding optimizer state. The training loop typically follows these distributed steps:
1.  **Local Projection:** Each GPU projects only its local shard into camera space [S1].
2.  **Communication:** Projected Gaussians are routed to the GPUs responsible for the image tiles they cover, often via an all-to-all exchange [S2, unofficial].
3.  **Filtering:** The active set of Gaussians is reduced using importance scoring, pruning, and distance-based Level-of-Detail (LOD) filtering [S1].
4.  **Rasterization and Update:** Each GPU composites pixels for its assigned tiles and updates parameters using gradients reweighted by importance signals [S1].

## Subtopics

### [BlitzGS](15088-blitzgs.md)
BlitzGS is a distributed 3DGS framework designed to accelerate city-scale training by reducing the active Gaussian workload across system, model, and view levels. It addresses the inefficiency of existing methods where every iteration preprocesses, communicates, and rasterizes an overly dense set of primitives, most of which contribute negligibly to the loss. Unlike spatial block partitioning which incurs cross-block visibility waste and imbalanced shards, BlitzGS shards by index parity and couples this with importance-based pruning and distance-based LOD filtering to achieve nearly an order-of-magnitude speedup while maintaining high reconstruction quality. See [BlitzGS](15088-blitzgs.md) for implementation details.

### [GS-Cache Inference Framework](15588-gs-cache-inference-framework.md)
GS-Cache is a holistic rendering framework designed to support real-time rendering of large-scale 3DGS models, specifically targeting city-level scenes. It achieves an average frame rate exceeding 72 FPS at binocular 2K resolution by employing a cache-centric de-redundancy pipeline and elastic parallel scheduling. Unlike native 3DGS or unstructured methods, GS-Cache specifically targets "Structured Gaussian derivation methods" (such as Scaffold-GS and Octree-GS) that use anchors to derive neural Gaussians, addressing the computational bottleneck of the Gaussian Derivation Stage. It sets itself apart from siblings like BlitzGS by focusing on inter-frame redundancy elimination in the anchor decoding phase rather than just intra-frame rasterization optimization. See [GS-Cache Inference Framework](15588-gs-cache-inference-framework.md) for implementation details.

### LS-Gaussian Accelerator Architecture
- **Definition:** A hardware architecture co-designed with the LS-Gaussian algorithm to support workload-aware mapping, featuring a streaming pipeline that allows continuous processing across hardware modules without requiring global synchronization [S1].
- **Step:** The accelerator predicts the workload for each tile based on viewpoint transformation to enable more balanced parallel computation [S1].
- **Comparison:** Unlike naive assignment of tiles to rendering blocks which fails to achieve balanced load distribution, this architecture uses workload prediction to mitigate inter-block idling and intra-block bubbles [S1].

### Spatial Block Partitioning
- **Definition:** Divides the scene into fixed world-space spatial blocks (e.g., uniform grid). Each GPU is bound to a specific block and trains its Gaussians independently [S2, unofficial].
- **Step:** Construct a uniform grid (e.g., 4×5 or 5×6). Assign each block a boundary halo of neighboring Gaussians for cross-block consistency. Train blocks independently across GPUs. During rendering, cameras near block boundaries trigger cross-block visibility overlap and boundary reassignment. Perform a final single-GPU merge to assemble the full scene [S2, unofficial].
- **Pitfall:** Overlapping blocks re-optimize the same surfaces, wasting computation. In a 20-block split, 23.5M Gaussians are optimized but only 5.37M survive merge (77% discarded). Finer partitions increase redundancy and training time with negligible quality gain (<0.2 dB) [S2, unofficial].
- **Number:** On Building (1,920 cameras, 4 GPUs), 86.8% of cameras fall in ≥2 blocks for 20-block partition, and 95.5% for 30-block partition. Wall-clock time for split/make-span/merge reaches 115.6–169.8 min vs 39 min for sharding [S2, unofficial].

### Primitive Sharding (Index-Parity Sharding)
- **Definition:** Distributes a single global Gaussian model across multiple GPUs by assigning Gaussians to ranks based on index parity. Each GPU holds a balanced, scene-wide slice of the model [S2, unofficial].
- **Step:** Assign each Gaussian primitive to a GPU rank using index parity. During rendering, distribute each step through balanced tile allocation across GPUs. Route projected Gaussians to tile owners via all-to-all communication. Train using a single global camera stream. Each camera enters training once per iteration with no cross-block duplication. Only distributed cost is the all-to-all exchange inside each render step [S2, unofficial].
- **Number:** On a 4-GPU setup (Building scene, 1,920 cameras), communication cost for routing projected Gaussians to tile owners is 3–5 ms per iteration, staying under 7% of total iteration time [S2, unofficial].
- **Comparison:** Unlike spatial block partitioning, it eliminates boundary reassignment, cross-block visibility overlap, and the final single-GPU merge step. Storage and per-step rendering remain evenly distributed as GPU count grows [S2, unofficial].

## Background
The need for distributed training in 3DGS arises from the quadratic growth of Gaussian primitives required for high-fidelity city-scale reconstruction, which exceeds the memory and compute capacity of single GPUs. Early attempts at spatial partitioning revealed significant inefficiencies due to boundary effects and redundant optimization [S2, unofficial]. BlitzGS introduced index-parity sharding to solve these issues, demonstrating that distributing the global model by index parity avoids the geometric constraints of spatial blocks [S2, unofficial]. Concurrently, research into inference acceleration, such as GS-Cache and LS-Gaussian, has focused on reducing redundancy in structured Gaussian representations and hardware-aware workload balancing [S1].
