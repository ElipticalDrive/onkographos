# Hardware and Computational Acceleration

Also called: GPU Acceleration for 3D Gaussian Splatting

## Overview
This family addresses the computational bottlenecks in 3D Gaussian Splatting (3DGS) rendering and training, specifically targeting memory bandwidth limits in the front-end (sorting and attribute fetching) and compute throughput limits in the rasterization stage. It sets itself apart from generic optimization by explicitly mapping software strategies to hardware constraints (e.g., using the Roofline model [S1]) or by replacing standard sorting with hardware-friendly, comparison-free logic [S1] and sorting-free approximations .

## Shared principles
The rendering pipeline for 3D Gaussian Splatting consists of two primary stages that this family optimizes:

1.  **Front-End (Memory-Bound):**
    *   **Projection and Sorting:** 3D Gaussians are projected to 2D, and a depth key is generated for each. To ensure correct alpha compositing, Gaussians must be sorted front-to-back (increasing depth) within each image tile.
    *   **Attribute Fetching:** For each Gaussian-pixel pair, attributes (opacity, spherical harmonic coefficients) are fetched from global memory.
    *   **Optimization Goal:** Reduce global memory traffic and bandwidth usage. This is achieved by compressing data (quantization, key compression) and fusing kernels to avoid intermediate writes [S1].

2.  **Rasterization (Compute-Bound):**
    *   **Alpha Compositing:** The final pixel color $C$ is computed via alpha blending :
        $$C = \sum_{i=1}^N c_i \alpha_i T_i, \quad T_i = \prod_{j=1}^{i-1} (1 - \alpha_j)$$
        where $c_i$ is the color, $\alpha_i$ is the opacity, and $T_i$ is the transmittance.
    *   **Gaussian Evaluation:** The opacity $\alpha_i$ for a pixel at $(x,y)$ relative to a Gaussian center $(u,v)$ is computed as [S1]:
        $$\alpha_i = o \exp(p(x, y))$$
        where $o$ is the base opacity and $p(x, y)$ is the Gaussian power:
        $$p(x, y) = -\frac{1}{2} \left( a(x - w)^2 + b(x - u)(y - v) + c(y - v)^2 \right)$$
        Here, $a, b, c$ are derived from the projected 2D covariance matrix, and $(w, v)$ are the center coordinates (note: source [S1] uses $(w, v)$ for center and $(u, v)$ in the formula text, but standard notation aligns center with $(u,v)$ in the quadratic form; we retain the source's variable mapping where $a,b,c$ come from covariance).
    *   **Optimization Goal:** Increase instruction-level parallelism (ILP) and reduce expensive operations (like `exp`) within the per-pixel loop [S1].

### GEMM-GS
**Definition**
An acceleration approach for 3D Gaussian Splatting that utilizes Tensor Cores on GPUs by reformulating the blending process into a GEMM-compatible form [S1].

**Step**
Transform the conventional 3DGS blending process into a GEMM-style formulation equivalently to leverage Tensor Cores [S1]. Develop a CUDA kernel implementing the transformed blending process, designed as a three-stage double-buffered pipeline with asynchronous memory copy to overlap computation and memory access [S1].

**Parameter**
Tile size: The 2D screen is divided into tiles, with 16x16 pixels mentioned as an example [S1]. Thread block size: Rendering a 16x16 tile is assigned to a thread block of 256 threads [S1].

**Layout**
Gaussian features computed in preprocessing include depth $d$ and RGB color $c$ [S1].

**Number**
GEMM-GS achieves an average 1.42× speedup over vanilla 3DGS implementation [S1]. GEMM-GS provides an additional 1.47× speedup when combined with existing acceleration approaches [S1].

**Comparison**
GEMM-GS is orthogonal to existing acceleration methods (compression-based or preprocessing-based), allowing it to provide additional speedup when combined with them [S1].

## Background
The need for hardware acceleration in 3D Gaussian Splatting arises from the high computational cost of the rendering pipeline, which includes preprocessing, duplication, sorting, and blending [S1]. Existing acceleration works often overlook the evolving Tensor Cores of modern GPUs because the standard 3DGS pipeline lacks General Matrix Multiplication (GEMM) operations [S1]. GEMM-GS was proposed to address this by reformulating the blending process to utilize these hardware capabilities [S1].
