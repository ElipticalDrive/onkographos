# Text Embedding Generation with Directional Views


## Overview
This method generates semantic text embeddings conditioned on specific camera viewpoints to enable view-dependent semantic understanding in 3D Gaussian Splatting. It solves the problem of static semantic representations by appending directional view descriptors to text prompts before encoding, allowing the system to distinguish between different perspectives of the same object [S1, unofficial][S2]. Unlike standard text encoding which produces a single static embedding per prompt, this approach generates a set of directional embeddings (e.g., front, side, back) that can be used to modulate features or guide optimization based on the current camera position [S1, unofficial][S2].

## How it works
**Inputs and Outputs:**
*   **Input:** A base text prompt string (e.g., "a chair"), a list of directional view descriptors, and a pre-trained frozen CLIP text encoder.
*   **Output:** A dictionary mapping directional keys to tensor embeddings of shape `[1, 77, 768]` (batch size 1, sequence length 77, embedding dimension 768) [S1, unofficial].

**Data Structures:**
*   `self.embeddings`: A dictionary where keys are strings (`'pos'`, `'neg'`, `'front'`, `'side'`, `'back'`) and values are PyTorch tensors of shape `[1, 77, 768]` [S1, unofficial].

**Steps:**
1.  **Initialize Tokenizer and Encoder:** Load a pre-trained CLIP text tokenizer and text encoder. The encoder is frozen (no gradients computed) [S1, unofficial].
2.  **Define Directional Suffixes:** Identify the set of directional views to encode. Common views include `'front'`, `'side'`, `'back'` [S1, unofficial]. For forward-facing scenes (e.g., LLFF dataset), `'top-down'` may be excluded [S2].
3.  **Construct Prompts:** For each directional view $d$ in the set of views, construct a new prompt string by appending the view descriptor to the base prompt. The format is typically `"{base_prompt}, {d} view"` [S1, unofficial][S2].
    *   Example: If base prompt is "a chair" and $d$ is "front", the prompt becomes "a chair, front view" [S1, unofficial].
4.  **Tokenize:** Tokenize each constructed prompt using the CLIP tokenizer.
    *   Apply padding to `max_length` (typically 77 for CLIP) [S1, unofficial].
    *   Return tensors in PyTorch format [S1, unofficial].
5.  **Encode:** Pass the token IDs through the frozen CLIP text encoder.
    *   Extract the last hidden state or pooled output as the embedding [S1, unofficial].
    *   Store the resulting tensor in `self.embeddings` under the key corresponding to the view $d$ [S1, unofficial].
6.  **Store Embeddings:** Save the computed embeddings in `self.embeddings` for later retrieval during rendering or optimization [S1, unofficial].

**Pseudocode:**
```python
import torch
from transformers import CLIPTextModel, CLIPTokenizer

class DirectionalTextEmbedder:
    def __init__(self, base_prompt, device="cuda"):
        self.base_prompt = base_prompt
        self.device = device
        self.tokenizer = CLIPTokenizer.from_pretrained("openai/clip-vit-large-patch14")
        self.text_encoder = CLIPTextModel.from_pretrained("openai/clip-vit-large-patch14").to(device)
        self.text_encoder.eval() # Freeze encoder
        self.embeddings = {}
        self.directions = ['front', 'side', 'back'] # Default directions [S1, unofficial]

    def encode(self):
        """Encode base prompt and all directional variants."""
        # Encode base prompt (optional, often used as 'pos' or default)
        base_inputs = self.tokenizer(self.base_prompt, padding="max_length", max_length=77, return_tensors="pt")
        with torch.no_grad():
            base_embeds = self.text_encoder(base_inputs.input_ids.to(self.device))[0]
        self.embeddings['pos'] = base_embeds

        # Encode directional views
        for direction in self.directions:
            # Construct prompt: "{base_prompt}, {direction} view" [S1, unofficial][S2]
            prompt = f"{self.base_prompt}, {direction} view"
            inputs = self.tokenizer(prompt, padding="max_length", max_length=77, return_tensors="pt")
            
            with torch.no_grad():
                # Get embeddings [S1, unofficial]
                embeddings = self.text_encoder(inputs.input_ids.to(self.device))[0]
            
            self.embeddings[direction] = embeddings

    def get_embedding(self, direction):
        """Retrieve embedding for a specific direction."""
        if direction in self.embeddings:
            return self.embeddings[direction]
        else:
            raise ValueError(f"Direction {direction} not encoded. Available: {list(self.embeddings.keys())}")
```

**Parameters:**
*   `max_length`: Sequence length for tokenization. Default is 77 for CLIP [S1, unofficial].
*   `directions`: List of view descriptors. Default `['front', 'side', 'back']` [S1, unofficial]. For forward-facing scenes, use `['top-down', 'front', 'side']` [S2].

**Edge Cases and Pitfalls:**
*   **Precision:** Use `torch.no_grad()` during encoding to save memory and prevent unnecessary gradient computation through the frozen encoder [S1, unofficial].
*   **Boundaries:** Ensure the tokenizer's `max_length` matches the encoder's expected input sequence length (77 for standard CLIP) [S1, unofficial].
*   **Degenerate Input:** If the base prompt is empty, the resulting embeddings may be semantically meaningless. Validate input prompts [G].

## Subtopics

### [TexGS-VolVis Representation and Optimization](11105-texgs-volvis-representation-and-optimization.md)
TexGS-VolVis is a method for representing and editing volume visualization (VolVis) scenes using textured 2D Gaussian Splatting (2DGS). It solves the problem of decoupling geometry from appearance in text-driven non-photorealistic style editing (NPSE), allowing for geometry-consistent stylization without the elliptical artifacts common in coupled representations. Unlike methods that freeze geometry to prevent distortion, TexGS-VolVis uses explicit 2D texture maps to store appearance, preserving geometric fidelity while enabling rich visual expressiveness.

### Directional Dependent Prompts
This variant concatenates a text prompt to the input caption depending on the camera location in the scene at each iteration [S2]. It uses specific direction prompts such as `", top-down view"`, `", front view"`, `", side view"`, and `", back view"` [S2]. For forward-facing scenes like the LLFF dataset, only the first three captions (`top-down`, `front`, `side`) are used [S2]. This allows the semantic representation to adapt dynamically to the viewing angle during optimization [S2].

## Operating characteristics
*   **Time Complexity:** Encoding is performed once per prompt/direction set. The cost is dominated by the CLIP text encoder inference, which is negligible compared to 3DGS rendering but scales linearly with the number of directional views [S1, unofficial][S2].
*   **Memory Complexity:** Stores one embedding tensor per direction. For CLIP, this is $N_{views} \times 1 \times 77 \times 768 \times 4$ bytes (float32). For 4 views, this is approximately 96 KB, which is minimal [S1, unofficial].
*   **Strengths:** Enables view-dependent semantic queries and optimization. Simple to implement using standard CLIP libraries [S1, unofficial][S2].
*   **Limitations:** Relies on the semantic quality of the underlying CLIP model. Does not handle occlusion or partial visibility explicitly; it assumes the directional view is visible [G].
*   **When to use:** When view-dependent semantics are required, such as in open-vocabulary segmentation or view-specific style transfer [S1, unofficial][S2].
*   **When not to use:** When computational resources are extremely constrained and semantic conditioning is not needed [G].

## Background
The method originates from the integration of CLIP-based text embeddings into 3D Gaussian Splatting frameworks. DreamGaussian introduced the basic mechanism of encoding text prompts into latent embeddings for 3D generation [S1, unofficial]. Blended-NeRF extended this by introducing directional-dependent prompts to improve view consistency and semantic alignment in NeRF-based generation [S2]. The technique has since been adapted for Gaussian Splatting to support open-vocabulary queries and view-dependent feature modulation [S1, unofficial][S2].
