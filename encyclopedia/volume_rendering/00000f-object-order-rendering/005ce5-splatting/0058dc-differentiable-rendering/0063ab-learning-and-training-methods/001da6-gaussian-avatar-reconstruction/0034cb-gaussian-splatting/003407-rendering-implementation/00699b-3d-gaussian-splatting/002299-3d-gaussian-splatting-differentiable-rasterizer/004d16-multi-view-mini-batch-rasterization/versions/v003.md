# Multi-view Mini-batch Rasterization

Also called: Multi-view mini-batch training for 3D Gaussian Splatting

## Overview
Multi-view mini-batch rasterization is a training strategy that renders multiple viewpoints simultaneously within a single mini-batch to reduce gradient variance and improve convergence speed [S1, unofficial]. It modifies the standard 3D Gaussian Splatting (3DGS) rasterizer pipeline by introducing view-specific frustum culling and a composite sorting ID, allowing the rasterizer to process multiple camera views in parallel while significantly reducing memory consumption compared to naive multi-view rendering [S1, unofficial]. Unlike single-view training, this method increases performance metrics (PSNR/SSIM) but introduces higher memory overhead and preprocessing time [S1, unofficial].

## How it works
**Inputs and Outputs**
*   **Inputs:** A set of $P$ 3D Gaussians; a mini-batch of $B$ viewpoints (camera poses and intrinsics); tile resolution and screen dimensions [S1, unofficial].
*   **Outputs:** Rendered images for all $B$ viewpoints; gradients for Gaussian parameters (position, scale, rotation, opacity, color) propagated back from the loss function [S1, unofficial].

**Data Structures**
The core data structure is an array of projected Gaussian attributes [S1, unofficial]. To support multi-view processing, the sorting identifier is modified from the standard 3DGS implementation:
*   **Standard 3DGS ID:** 64-bit integer composed of a 32-bit tile index and a 32-bit depth value [S1, unofficial].
*   **Multi-view ID:** 64-bit integer composed of:
    *   16-bit tile index
    *   16-bit viewpoint index (identifying which of the $B$ viewpoints the Gaussian belongs to) [S1, unofficial]
    *   32-bit depth value [S1, unofficial]

**Numbered Steps**

1.  **Frustum Culling (Per Viewpoint):**
    For each of the $B$ viewpoints in the mini-batch, determine which of the $P$ total Gaussians are visible within the camera frustum [S1, unofficial]. This step identifies the subset of Gaussians participating in rendering for each specific viewpoint before memory allocation [S1, unofficial].

2.  **Memory Allocation:**
    Allocate memory only for the Gaussians identified in Step 1 [S1, unofficial]. Let $N$ be the total number of Gaussian instances remaining after culling across all viewpoints [S1, unofficial]. Typically, $N \ll B \times P$ because most Gaussians are not visible from every viewpoint [S1, unofficial].

3.  **Projection:**
    Compute the projected 2D Gaussian parameters (mean, covariance) for the participating Gaussians in screen space for their respective viewpoints [S1, unofficial]. Note that a single 3D Gaussian may be projected and appear multiple times in the array if it is visible in multiple viewpoints [S1, unofficial].

4.  **Duplication and ID Assignment:**
    Duplicate projected Gaussians for each tile they cover [S1, unofficial]. Assign each duplicated Gaussian a unique 64-bit ID using the multi-view format (16-bit tile, 16-bit viewpoint, 32-bit depth) [S1, unofficial]. This ensures that projected Gaussians are separated by both tile and viewpoint during sorting [S1, unofficial].

5.  **Sorting:**
    Sort the array of projected Gaussians by their 64-bit ID [S1, unofficial]. This groups Gaussians by tile and viewpoint, ensuring that rendering blocks for different viewpoints do not interfere with each other [S1, unofficial].

6.  **Rendering:**
    The rasterizer allocates multiple rendering blocks per tile—one block for each viewpoint [S1, unofficial]. Each block renders its designated pixels using only the projected Gaussians corresponding to its assigned viewpoint index [S1, unofficial].

**Pseudocode**

```python
def multi_view_rasterize(gaussians_3d, viewpoints, tile_size, screen_width, screen_height):
    """
    gaussians_3d: List of P 3D Gaussian objects (pos, cov, opacity, color)
    viewpoints: List of B camera objects (view_matrix, proj_matrix, intrinsics)
    tile_size: Integer, size of a tile in pixels (e.g., 16)
    screen_width, screen_height: Integer, dimensions of the image
    """
    all_projected = []

    # Step 1 & 2: Frustum Culling and Memory Allocation
    for viewpoint_idx, cam in enumerate(viewpoints):
        # [G] Standard 3DGS frustum culling logic
        visible = [g for g in gaussians_3d if is_in_frustum(g, cam)]
        
        # Step 3: Projection
        for g in visible:
            # [G] Standard 3DGS projection to screen space
            proj = project_gaussian_2d(g, cam)
            # [G] Standard 3DGS tile coverage calculation
            tiles = get_tiles_covered(proj, tile_size, screen_width, screen_height)
            
            # Step 4: Duplication and ID Assignment
            for tile_idx in tiles:
                # Construct 64-bit ID: 16-bit tile | 16-bit viewpoint | 32-bit depth
                id_tile = tile_idx & 0xFFFF
                id_view = viewpoint_idx & 0xFFFF
                id_depth = int(proj.depth) & 0xFFFFFFFF
                composite_id = (id_tile << 48) | (id_view << 32) | id_depth
                
                all_projected.append({
                    'proj': proj,
                    'id': composite_id,
                    'view_idx': viewpoint_idx,
                    'tile_idx': tile_idx
                })

    # Step 5: Sorting
    all_projected.sort(key=lambda x: x['id'])

    # Step 6: Rendering
    images = [[0.0] * (screen_width * screen_height * 3) for _ in viewpoints]
    num_tiles_x = screen_width // tile_size
    num_tiles_y = screen_height // tile_size

    for ty in range(num_tiles_y):
        for tx in range(num_tiles_x):
            tile_idx = ty * num_tiles_x + tx
            
            # Extract Gaussians for this tile (already sorted by composite ID)
            tile_gaussians = [g for g in all_projected if g['tile_idx'] == tile_idx]
            
            # Step 6: Allocate blocks per viewpoint and render
            for viewpoint_idx in range(len(viewpoints)):
                # Filter Gaussians belonging to this specific viewpoint in this tile
                view_gaussians = [g for g in tile_gaussians if g['view_idx'] == viewpoint_idx]
                # [G] Standard 3DGS front-to-back alpha compositing per pixel
                render_tile(images[viewpoint_idx], tx * tile_size, ty * tile_size, tile_size, view_gaussians)
                
    return images

def is_in_frustum(g, cam): # [G] Checks if Gaussian bounding sphere intersects camera frustum planes
    return True

def project_gaussian_2d(g, cam): # [G] Projects 3D mean and covariance to 2D screen space using camera matrices
    return {'mean': [0, 0], 'cov': [[1, 0], [0, 1]], 'depth': 1.0}

def get_tiles_covered(proj, tile_size, width, height): # [G] Computes integer tile coordinates covering the 2D Gaussian ellipse
    return [0]

def render_tile(image, tile_x, tile_y, tile_size, gaussians): # [G] Accumulates pixel colors via front-to-back alpha compositing
    pass
```

**Parameters**
*   **Pruning Threshold:** In standard 3DGS, the threshold for pruning Gaussians is multiplied by the number of images ($B$) in the mini-batch to account for changed learning patterns [S1, unofficial].
*   **Mean Noise Learning Rate:** In 3DGS-MCMC, this rate is divided by the number of images ($B$) when applying multi-view training [S1, unofficial].
*   **Number of Viewpoints ($B$):** The number of viewpoints rendered per mini-batch [S1, unofficial]. Increasing $B$ improves performance but increases memory and time overhead [S1, unofficial].

**Edge Cases and Pitfalls**
*   **Overfitting:** Multi-view mini-batch training can cause overfitting on specific scenes, notably the bicycle/stump scenes in the MipNeRF-360 dataset and scenes in the DeepBlending dataset [S1, unofficial].
*   **Preprocessing Overhead:** While rendering overhead is mitigated, the preprocessing steps (culling, sorting, ID assignment) remain [S1, unofficial]. This prevents the method from achieving constant time complexity with respect to the number of images, unlike NeRF-based methods [S1, unofficial].
*   **Gradient Nullification:** If viewpoints are positioned symmetrically (e.g., opposite each other facing the origin), gradients from different viewpoints can cancel each other out for positional updates if not handled correctly [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Not constant with respect to the number of images due to preprocessing overhead (culling, sorting) [S1, unofficial].
*   **Memory Complexity:** Significantly reduced compared to naive multi-view rendering ($N \ll B \times P$), but still higher than single-view training [S1, unofficial].
*   **Performance:** On the MipNeRF-360 dataset, using 8 viewpoints in the mini-batch achieved a PSNR of 30.56, SSIM of 0.901, and LPIPS of 0.138 for 3DGS-MCMC + Ours, compared to 29.94 PSNR for the base 3DGS [S1, unofficial].
*   **Strengths:** Reduces gradient variance, improves convergence, and lowers memory usage compared to rendering all views independently [S1, unofficial].
*   **Limitations:** Preprocessing overhead remains; potential for overfitting on certain scenes; increased memory/time with more viewpoints [S1, unofficial].
*   **When to Use:** When training speed and convergence are prioritized, and hardware memory allows for multi-view processing [S1, unofficial].
*   **When Not to Use:** When constant time complexity with respect to image count is required, or when dealing with scenes prone to overfitting (e.g., bicycle/stump in MipNeRF-360) [S1, unofficial].

## Background
The method was introduced in "Efficient multi-view training for 3D Gaussian Splatting" [S1, unofficial]. It addresses the limitations of single-view training by leveraging multiple viewpoints per iteration to stabilize gradients [S1, unofficial]. The approach builds on the 3DGS rasterizer [2813-3d-gaussian-splatting-differentiable-rasterizer.md] and modifies its preprocessing and sorting stages to handle multi-view data efficiently [S1, unofficial].
