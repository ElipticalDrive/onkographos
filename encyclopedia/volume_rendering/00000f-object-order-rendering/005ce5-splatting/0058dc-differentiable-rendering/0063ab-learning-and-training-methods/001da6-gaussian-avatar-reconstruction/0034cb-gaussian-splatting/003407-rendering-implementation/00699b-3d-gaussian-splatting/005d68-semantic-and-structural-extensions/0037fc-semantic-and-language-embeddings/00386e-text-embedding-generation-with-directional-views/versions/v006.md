# Text Embedding Generation with Directional Views


## Overview
This method generates semantic text embeddings conditioned on specific camera viewing directions to enable view-dependent semantic understanding in 3D Gaussian Splatting. It solves the problem of static semantic representations by appending directional descriptors to text prompts before encoding, allowing the system to distinguish between different viewpoints of the same object [S1, unofficial][S2]. It differs from standard text encoding by injecting explicit spatial context into the latent space, and from feature vector methods by operating at the prompt level rather than the Gaussian attribute level [S1, unofficial][S2].

## How it works
**Inputs and Outputs:**
*   **Input:** A base text prompt string (e.g., "a dog"), a set of directional descriptors (e.g., "front", "side", "back"), and a frozen CLIP text encoder.
*   **Output:** A dictionary mapping directional keys to 3D tensors of shape `[1, 77, 768]` representing the latent embeddings [S1, unofficial].

**Data Structures:**
*   `self.embeddings`: A dictionary where keys are strings (`'pos'`, `'neg'`, `'front'`, `'side'`, `'back'`) and values are PyTorch tensors of shape `[1, 77, 768]` (batch size 1, sequence length 77, embedding dimension 768) [S1, unofficial].

**Steps:**
1.  **Tokenization:** Tokenize the base prompt using the CLIP tokenizer with padding to the maximum sequence length.
    $$ \text{inputs} = \text{tokenizer}(\text{prompt}, \text{padding}=\text{"max\_length"}, \text{max\_length}=\text{model\_max\_length}, \text{return\_tensors}=\text{"pt"}) $$
    [S1, unofficial]
2.  **Base Encoding:** Pass the token IDs through the frozen CLIP text encoder to obtain the base embedding.
    $$ \text{embeddings} = \text{text\_encoder}(\text{inputs.input\_ids.to(device)})[0] $$
    [S1, unofficial]
3.  **Directional Augmentation:** For each directional descriptor $d$ in the set $\{\text{'front'}, \text{'side'}, \text{'back'}\}$, append the string `', {d} view'` to the base prompt.
4.  **Directional Encoding:** Tokenize and encode the augmented prompts using the same frozen text encoder. Store the resulting tensors in `self.embeddings` under the corresponding keys [S1, unofficial].
5.  **Storage:** Store the base embeddings (often under `'pos'` or `'neg'` depending on training context) and the directional embeddings in `self.embeddings` [S1, unofficial].

**Pseudocode:**
```python
def generate_directional_embeddings(self, base_prompt, device):
    """
    Generates text embeddings for a base prompt and its directional variants.
    """
    # 1. Tokenize base prompt
    inputs = self.tokenizer(
        base_prompt,
        padding="max_length",
        max_length=self.tokenizer.model_max_length,
        return_tensors="pt"
    )
    
    # 2. Encode base prompt
    base_embed = self.text_encoder(inputs.input_ids.to(device))[0]
    
    # 3. Define directional suffixes
    directions = ['front', 'side', 'back']
    
    # 4. Initialize storage dictionary
    self.embeddings = {}
    
    # 5. Store base embedding (mapped to 'pos' as per source convention)
    self.embeddings['pos'] = base_embed
    
    # 6. Generate and store directional embeddings
    for d in directions:
        # Append directional descriptor
        augmented_prompt = f"{base_prompt}, {d} view"
        
        # Tokenize augmented prompt
        aug_inputs = self.tokenizer(
            augmented_prompt,
            padding="max_length",
            max_length=self.tokenizer.model_max_length,
            return_tensors="pt"
        )
        
        # Encode augmented prompt
        aug_embed = self.text_encoder(aug_inputs.input_ids.to(device))[0]
        
        # Store in dictionary
        self.embeddings[d] = aug_embed
        
    return self.embeddings
```

**Parameters:**
*   `model_max_length`: 77 (standard CLIP text context length) [S1, unofficial].
*   `embedding_dimension`: 768 (standard CLIP text encoder output size) [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** The text encoder is frozen; gradients do not flow through it during training [S1, unofficial].
*   **Boundaries:** The method assumes a fixed set of directional views. If a view direction falls outside the predefined set (e.g., 'top-down' in non-forward-facing scenes), it must be explicitly added to the encoding pipeline [S2].

## Subtopics

### [TexGS-VolVis Representation and Optimization](11105-texgs-volvis-representation-and-optimization.md)
TexGS-VolVis is a method for representing and editing volume visualization (VolVis) scenes using textured 2D Gaussian Splatting (2DGS). It solves the problem of decoupling geometry from appearance in text-driven non-photorealistic style editing (NPSE), allowing for geometry-consistent stylization without the elliptical artifacts common in coupled representations. Unlike methods that freeze geometry to prevent distortion, TexGS-VolVis uses explicit 2D texture maps to store appearance, preserving geometric fidelity while enabling rich visual expressiveness.

### Directional Dependent Prompts
This variant concatenates a text prompt to the input caption depending on the camera location in the scene at each iteration [S2]. It uses specific direction prompts: `', top-down view'`, `', front view'`, `', side view'`, and `', back view'` [S2]. For forward-facing scenes like the LLFF dataset, only the first three captions are used [S2]. This approach dynamically adjusts the semantic conditioning based on the rendered viewpoint during optimization [S2].

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of directional views and the sequence length of the text encoder. The encoding is performed once per prompt update or initialization, not per pixel or Gaussian.
*   **Memory Complexity:** $O(N \cdot L \cdot D)$, where $N$ is the number of directional variants (typically 3-4), $L$ is the sequence length (77), and $D$ is the embedding dimension (768). This is negligible compared to the Gaussian attribute storage.
*   **Strengths:** Enables view-dependent semantic queries without modifying the Gaussian attributes themselves. Simple to implement using standard CLIP APIs.
*   **Limitations:** Limited to the predefined set of directions. Does not support continuous directional interpolation without additional interpolation steps.
*   **When to use:** When semantic consistency across views is required, or when performing view-dependent text-guided editing.
*   **When not to use:** When computational resources for the text encoder are unavailable during the rendering loop (though encoding is typically pre-computed).

## Background
The method originates from the DreamGaussian project, which utilizes CLIP embeddings for text-guided 3D generation and editing [S1, unofficial]. It was further adapted in Blended-NeRF for zero-shot object generation and blending, where directional prompts were used to ensure semantic consistency across different viewpoints [S2]. The approach leverages the pre-trained alignment of CLIP's text encoder with visual features, allowing for zero-shot semantic tasks in 3D scenes.
