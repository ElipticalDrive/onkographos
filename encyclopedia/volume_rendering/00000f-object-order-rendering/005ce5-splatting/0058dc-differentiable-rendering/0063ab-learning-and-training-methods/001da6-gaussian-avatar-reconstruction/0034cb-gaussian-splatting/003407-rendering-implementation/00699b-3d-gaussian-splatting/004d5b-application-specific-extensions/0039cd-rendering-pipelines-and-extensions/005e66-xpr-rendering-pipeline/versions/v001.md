# XPR Rendering Pipeline

Also called: Extensible Cross-Platform Point-Based Differentiable Renderer pipeline

## Overview
The XPR (Extensible Cross-Platform Point-Based Differentiable Renderer) pipeline is a modular rendering architecture that decouples method-specific logic from the pipeline structure by exposing four user-defined functions: `project`, `tile_cull`, `pixel_info`, and `evaluate` [S1, unofficial]. It solves the problem of managing parallelization, data layout, and scheduling for point-based differentiable rendering by handling these automatically via JAX/XLA, supporting automatic differentiation without requiring a manual backward pass [S1, unofficial]. It sets itself apart from baseline renderers by exposing hardware-agnostic parallelism via `map_fn`, allowing the compiler to map scalar functions to SIMD on GPUs or batched tensors on TPUs, whereas traditional renderers require the programmer to manage parallelization explicitly [S1, unofficial].

## How it works
The pipeline processes 3D primitives into 2D image pixels through a sequence of parallelizable modules. The core mechanism involves projecting primitives, filtering visible ones, rasterizing them to tiles, and evaluating contributions per pixel [S1, unofficial].

### Inputs and Outputs
*   **Inputs:** A set of $N$ 3D primitives, camera parameters (`cam`), and camera view matrix (`view`).
*   **Outputs:** An image buffer `img` of width $W$ and height $H$.

### Data Structures
*   **Primitives:** 3D data structures representing the scene geometry (e.g., 3D Gaussians, octahedra).
*   **Primitives 2D:** Projected 2D representations of primitives, including bounding boxes and shader data.
*   **Tiles:** Rectangular regions of the image. The image is partitioned into $T$ tiles.
*   **Tile-Primitive Map (`tile_prim_map`):** A mapping from each tile to a list of 2D primitives that intersect that tile.
*   **Pixel Data (`px_data`):** Computed per-pixel information required for evaluation.
*   **Shader Data (`p_sd`):** Primitive-specific data required for evaluation, extracted from the 2D primitive.

### Parameters
*   **Compile-time Upper Bounds:** All tensor dimensions and loop trip counts are fixed at compile time. Dynamic sizes (e.g., number of visible primitives) are handled by padding unused entries and replacing dynamic loops with fixed-trip-count loops that exit early [S1, unofficial].
*   **Trip-count Binning:** Tiles are sorted by primitive count and partitioned into bins. Each bin is processed with a static trip count equal to its bin’s upper bound. Tiles within the same bin are parallelized via a second `map_fn` over tiles [S1, unofficial].

### Steps
1.  **Preprocess (Project):** Apply the user-defined `project` function independently to each of the $N$ primitives using `map_fn` to produce 2D primitive data [S1, unofficial].
2.  **Filter (Visibility):** For each 2D primitive, determine visibility using a framework-provided axis-aligned overlap test (bounding box check) and optionally refine this with the user-defined `tile_cull` function at tile granularity [S1, unofficial].
3.  **Rasterizer (Tile Assignment):** Determine which tiles each visible primitive intersects. Since primitives are distributed unevenly, XPR exploits that each primitive intersects only a small number of tiles bounded by its bounding box area. It enumerates these candidate intersections in a flat array. A `map_fn` over primitives counts tile intersections per primitive. The remaining challenge is that different tiles intersect different numbers of primitives. XPR addresses this with trip-count binning: tiles are sorted by primitive count and partitioned into bins, each processed with a static trip count equal to its bin’s upper bound. Tiles within the same bin are parallelized via a second `map_fn` over tiles [S1, unofficial].
4.  **Shader (Evaluation and Compositing):** For each tile, iterate over its pixels. For each pixel, call `pixel_info(px, cam, view)` once to produce `px_data`. Then, for each primitive in the tile's list, call `evaluate(px_data, p_sd)` to get alpha, validity, and color. Accumulate color via alpha-blending [S1, unofficial].

### Formulas
The accumulation of color for a pixel is defined as [S1, unofficial]:

$$ C = C + c \cdot \alpha \cdot \text{valid} \cdot T $$
$$ T = (1 - \alpha \cdot \text{valid}) \cdot T $$

Where:
*   $C$ is the accumulated color.
*   $c$ is the primitive color.
*   $\alpha$ is the primitive opacity.
*   $\text{valid}$ is a validity flag.
*   $T$ is the accumulated transmittance.

### Edge Cases and Pitfalls
*   **Dynamic Sizes:** The number of visible primitives and primitive-tile intersections varies per frame. XPR handles this by fixing dimensions to compile-time upper bounds, padding unused entries, and using fixed-trip-count loops that exit early [S1, unofficial].
*   **Uneven Load:** Different tiles intersect different numbers of primitives. XPR uses trip-count binning to mitigate this, sorting tiles by primitive count and processing bins with static trip counts [S1, unofficial].

## Operating characteristics
*   **Parallelization:** XPR exposes hardware-agnostic parallelism via `map_fn`, allowing XLA to map to SIMD on GPUs or batched tensors on TPUs [S1, unofficial].
*   **Differentiability:** Because JAX provides automatic differentiation, no backward pass needs to be implemented; gradients flow through the four user-defined functions for free [S1, unofficial].
*   **Performance:** The pipeline is designed to handle large numbers of primitives ($N \sim 10^6$) and tiles ($T \sim 10^5$) by avoiding the infeasible $M \times T$ intersection test and instead enumerating only candidate intersections [S1, unofficial].
*   **Extensibility:** Swapping primitives (e.g., 3D Gaussians for octahedra) or evaluation methods (splatting-based to ray-based) requires only new implementations of the four functions; the pipeline structure remains unchanged [S1, unofficial].

## Background
The XPR pipeline was introduced in the paper "XPR: An Extensible Cross-Platform Point-Based Differentiable Renderer" [S1, unofficial]. It is designed to provide a programming interface for point-based differentiable rendering that is both extensible and cross-platform, leveraging the JAX/XLA ecosystem for automatic differentiation and hardware abstraction.
