# 3D Gaussian Splatting Implementation Details

Also called: 3DGS CUDA kernel implementation, GS Implementation Parameters, GSGEN Implementation Details, Gaussian Splatting Training Configuration, Implementation Details, gsplat implementation details, half-precision rasterization implementation

## Overview
This article details the specific algorithmic steps, hyperparameters, and data structures required to implement the 3D Gaussian Splatting (3DGS) training and rendering pipeline. It addresses the problem of translating the theoretical differentiable volume rendering formulation into a stable, efficient software implementation. It sets itself apart from sibling articles by providing concrete values for optimization schedules, densification thresholds, and memory management strategies (such as half-precision rasterization) rather than high-level architectural descriptions.

## How it works

### Inputs and Outputs
*   **Inputs**: A set of $N$ 3D Gaussian primitives $\mathcal{G} = \{G_1, \dots, G_N\}$, each parameterized by position $\mathbf{p}$, covariance $\Sigma$ (or scale $\mathbf{s}$ and rotation $\mathbf{q}$), opacity $\alpha$, and spherical harmonic coefficients $\mathbf{c}$. A set of camera poses $\mathbf{T}_{cw}$ and intrinsic parameters. Ground-truth images $\mathbf{I}_{gt}$ for supervision.
*   **Outputs**: Rendered images $\mathbf{I}_{pred}$, gradients $\frac{\partial \mathcal{L}}{\partial \theta}$ for all Gaussian parameters, and an updated set of Gaussians $\mathcal{G}'$ after densification/pruning steps.

### Data Structures
The implementation typically maintains the following structures in GPU memory:
1.  **Gaussian Attributes**: A flat array or structure-of-arrays (SoA) layout for batch processing.
    *   Position: `float3` (32-bit).
    *   Rotation: `float4` (quaternion, 32-bit).
    *   Scale: `float3` (32-bit).
    *   Opacity: `float` (32-bit).
    *   SH Coefficients: `float` array, size depends on degree $D$. For $D=1$, size is $3 \times (D+1)^2 = 12$ floats per Gaussian [S3].
2.  **Tile/Bucket Data**: For rasterization, Gaussians are sorted into tiles (e.g., $16 \times 16$ pixels). Each tile contains a list of Gaussian indices sorted by depth.
3.  **Gradient Accumulators**: Separate buffers for position, scale, rotation, opacity, and SH coefficients, initialized to zero at the start of each optimization step.

### Training Loop and Optimization Steps
The training process is an iterative optimization loop. A typical implementation follows these steps [S1, S3]:

1.  **Random View Sampling**: For each iteration, randomly select a single image from the training dataset as supervision [S3].
2.  **Forward Rasterization**:
    *   Project 3D Gaussians to 2D screen space using the camera pose.
    *   Compute 2D covariance matrices $\Sigma_{2D}$ from 3D covariance $\Sigma$ and camera Jacobian [6233-optimization-and-parallelization].
    *   Rasterize Gaussians into tiles. To reduce register pressure and memory bandwidth, use **half-precision (FP16)** memory fetches for feature vectors (SH coefficients) during both forward and backward passes [S2].
    *   Perform alpha blending to compute pixel color $\mathbf{c}(\mathbf{x})$ and opacity $\alpha(\mathbf{x})$.
3.  **Loss Computation**:
    *   Compute loss $\mathcal{L}$ between $\mathbf{c}(\mathbf{x})$ and $\mathbf{I}_{gt}(\mathbf{x})$. Common losses include L1 loss and D-SSIM [S3].
    *   Apply an automatic scaling factor to loss values to improve stability during half-precision training [S2].
4.  **Backward Pass**:
    *   Compute gradients $\frac{\partial \mathcal{L}}{\partial \theta}$ using the differentiable rasterizer.
    *   Accumulate gradients in the respective buffers.
5.  **Optimizer Update**:
    *   Update Gaussian parameters using the Adam optimizer.
    *   Typical learning rate: $1 \times 10^{-3}$ [S3].
6.  **Densification and Pruning (Periodic)**:
    *   **Splitting**: Every 500 iterations, split Gaussians based on view-space position gradient. If the accumulated gradient magnitude exceeds threshold $T_{pos} = 0.02$, split the Gaussian into two [S1].
    *   **Cloning/Compactness**: Every 1000 iterations, perform compactness-based densification (cloning) to fill gaps in geometry [S1].
    *   **Pruning**: Every 200 iterations, remove Gaussians with opacity $\alpha < \alpha_{min} = 0.05$ or those with excessively large world-space or view-space radius [S1].

### Scene Extent Calculation
The default 3DGS implementation calculates scene extent $e_{scene}$ based on camera positions, which can be biased if cameras are clustered (e.g., orbiting a small object in a large environment) [S4]. A corrected implementation uses the Structure-from-Motion (SfM) point cloud:

$$ \bar{C} = \frac{1}{N_{cam}} \sum_{i=1}^{N_{cam}} C_i $$

$$ e'_{scene} = \frac{1}{N_{SfM}} \sum_{i=1}^{N_{SfM}} \|\bar{C} - p_i\|_2 $$

where $\bar{C}$ is the average camera position, $N_{cam}$ is the number of cameras, $N_{SfM}$ is the number of SfM points, and $p_i$ are the SfM points [S4].

### Pseudocode

```python
def train_3dgs(gaussians, cameras, gt_images, optimizer, config):
    """
    Main training loop for 3D Gaussian Splatting.
    """
    # Initialize gradients
    gaussians.zero_grad()
    
    for iteration in range(config.max_iterations):
        # 1. Sample a random view
        cam_idx = random.randint(0, len(cameras) - 1)
        camera = cameras[cam_idx]
        gt_image = gt_images[cam_idx]
        
        # 2. Forward Pass: Rasterize
        # Project Gaussians to 2D
        screen_gaussians = project_to_screen(gaussians, camera)
        
        # Sort into tiles and rasterize
        # Use half-precision for SH coefficients to save memory [S2]
        rendered_image, alpha_map = rasterize(screen_gaussians, camera.resolution)
        
        # 3. Compute Loss
        # Apply loss scaling for FP16 stability [S2]
        loss = compute_loss(rendered_image, gt_image)
        scaled_loss = loss * config.loss_scale
        
        # 4. Backward Pass
        scaled_loss.backward()
        
        # 5. Optimizer Step
        optimizer.step()
        optimizer.zero_grad()
        
        # 6. Periodic Densification and Pruning
        if iteration % config.split_interval == 0:
            split_gaussians(gaussians, threshold=config.t_pos)
            
        if iteration % config.clone_interval == 0:
            clone_gaussians(gaussians)
            
        if iteration % config.prune_interval == 0:
            prune_gaussians(gaussians, alpha_min=config.alpha_min)
            
        # Decay learning rate if necessary
        optimizer.update_lr_schedule(iteration)
```

### Parameters and Typical Values
*   **Split Threshold ($T_{pos}$)**: 0.02 [S1].
*   **Opacity Threshold ($\alpha_{min}$)**: 0.05 [S1].
*   **Split Interval**: 500 iterations [S1].
*   **Clone Interval**: 1000 iterations [S1].
*   **Prune Interval**: 200 iterations [S1].
*   **Optimizer**: Adam [S3].
*   **Learning Rate**: $1 \times 10^{-3}$ [S3].
*   **SH Degree**: 1 (commonly used for real-time applications) [S3].
*   **Loss Scale**: Automatic scaling factor applied [S2].

### Edge Cases and Pitfalls
*   **Scene Extent Bias**: Using camera-based extent calculation for scenes with clustered cameras (e.g., Mip-NeRF 360 Garden scene) leads to incorrect splitting/pruning because the extent is underestimated [S4]. Use SfM-based extent calculation [S4].
*   **Half-Precision Instability**: Training in FP16 can lead to numerical instability. Apply loss scaling and use tiny-cuda-nn's JIT-compiled cooperative vector MLPs if using neural components [S2].
*   **Gradient Vanishing/Exploding**: Ensure gradient accumulation is handled correctly across multiple views or iterations if using distributed training [6233-optimization-and-parallelization].

## Subtopics

### Corrected Scene-Extent
A method to calculate scene extent based on the SfM point cloud rather than camera positions to avoid bias from camera distribution (e.g., orbiting a small object in a large environment). It sets itself apart from standard 3DGS by replacing the camera-distance-based extent formula with an SfM-point-distance-based formula, ensuring the scene volume is accurately represented regardless of camera placement. Choose this when training on datasets with non-uniform camera distributions, such as Mip-NeRF 360. Link: [Corrected Scene-Extent](12926-corrected-scene-extent.md).

### Selective Defocus Blurring
Predicts a per-Gaussian scale offset $\delta s_j$ to selectively enlarge covariances, creating pixel-wise variable blur kernels that match spatially varying scene blurriness. It sets itself apart from naive Gaussian blur (which applies a single kernel to the whole image) or learnable Gaussian kernels (which optimize a single mean/variance) by allowing spatially varying blur shapes and magnitudes. Choose this when training on images with defocus blur or motion blur. Link: [Selective Defocus Blurring](12927-selective-defocus-blurring.md).

### Denoise-GS
A self-supervised denoising method for sparse-view 3D Gaussian Splatting that combines unsupervised image denoising (Noise2Void) with 3DGS to address suboptimal reconstruction in noisy scenes. It sets itself apart from supervised methods (which require clean annotations) and Noise2Noise (which requires paired noisy images) by using Noise2Void, which requires no paired data. Choose this for sparse-view or noisy datasets. Link: [Denoise-GS](12928-denoise-gs.md).

### Multi-Scale Constraint
A technique using position-aware point adaptive control to apply different scales to Gaussians based on viewer distance, improving rendering of distant objects. It sets itself apart from standard densification by using a distance-dependent scaling factor $\gamma(\mu)$ to control cloning, splitting, and elimination thresholds. Choose this for large-scale scenes with varying distances. Link: [Multi-Scale Constraint](12929-multi-scale-constraint.md).

### LS-Gaussian Viewpoint Transformation
An algorithm that leverages inter-frame continuity for efficient sparse rendering by transforming the viewpoint between consecutive frames, rather than rendering each frame separately. It sets itself apart from naive pixel warping by operating at the tile/Gaussian level to reduce preprocessing and sorting costs. Choose this for real-time rendering on resource-constrained edge platforms (e.g., Jetson AGX Orin). Link: [LS-Gaussian Viewpoint Transformation](12930-ls-gaussian-viewpoint-transformation.md).

### Camera Localisation for Convergence Basin
Localizes camera pose by minimizing photometric error against the ground-truth color image of the target view, fixing the initial Gaussians during optimization. It sets itself apart from joint optimization of pose and geometry by decoupling them for faster convergence. Choose this for SLAM or localization tasks. Link: [Camera Localisation for Convergence Basin](12931-camera-localisation-for-convergence-basin.md).

### DiffGS Framework
Applies an optimization process during Gaussian extraction to optimize Gaussians to exact locations, using a truncation function $\lambda$ and projection function $\tau$. It sets itself apart from standard 3DGS by explicitly modeling Gaussian Probability Functions (GauPF) to improve geometric accuracy. Choose this when high geometric fidelity is required. Link: [DiffGS Framework](12932-diffgs-framework.md).

### Opacity Offset Table for DSA
Constructs an opacity offset table to model changes in digital subtraction angiography. It sets itself apart from standard opacity modeling by explicitly accounting for temporal changes in medical imaging. Choose this for dynamic medical imaging applications. Link: [Opacity Offset Table for DSA](12933-opacity-offset-table-for-dsa.md).

### Conditional Splat Approximation
Approximates the influence range of a 3D Gaussian on a slice by using a 2D ellipse splat scaled by the marginal factor, closely matching true iso-probability contours. It sets itself apart from exact 3D Gaussian slicing by providing an efficient approximation for slice-based rendering or tomographic reconstruction. Choose this for applications requiring slice-based processing. Link: [Conditional Splat Approximation](12934-conditional-splat-approximation.md).

Computes an uncertainty attribute for 3D Gaussians based on the negative log-likelihood of the rendered pixel value, interpreted as Fisher information. It sets itself apart from standard 3DGS by providing an explicit uncertainty measure for each Gaussian. Choose this for applications requiring uncertainty quantification. ### Neural Illumination Enhancement
Complements explicit 3DGS representation by predicting a view-dependent color residual using a lightweight MLP to handle non-Lambertian effects. It sets itself apart from standard 3DGS by adding a neural residual to the explicit rendering, specifically for specular highlights. Choose this for scenes with strong non-Lambertian effects. ## Operating characteristics

### Time and Memory Complexity
*   **Time Complexity**: The rasterization step is $O(N \cdot T)$ where $N$ is the number of Gaussians and $T$ is the number of tiles, but optimized to near-linear time with respect to visible Gaussians per tile due to sorting and early termination [6233-optimization-and-parallelization].
*   **Memory Complexity**: $O(N \cdot D)$ where $D$ is the number of SH coefficients. For $D=1$, each Gaussian requires $\approx 12$ floats for SH, plus position, scale, rotation, and opacity. Half-precision rasterization reduces memory bandwidth usage for SH coefficients [S2].

### Measured Performance
*   Performance varies by hardware and resolution. On standard GPUs, 3DGS can achieve real-time rendering (30+ FPS) for scenes with millions of Gaussians at 1080p resolution [6233-optimization-and-parallelization].
*   LS-Gaussian achieves up to 17.3× speedup on Jetson AGX Orin compared to edge GPU baselines [S8].

### Scaling
*   Scales well with the number of Gaussians due to parallel rasterization.
*   Distributed training is possible using data-parallel approaches, but requires synchronization of gradients or intermediate states [6233-optimization-and-parallelization].

### Strengths and Limitations
*   **Strengths**: Real-time rendering, high visual quality, explicit representation allows for easy editing and compression.
*   **Limitations**: High memory usage for large scenes, sensitive to initialization and densification parameters, can suffer from artifacts in sparse-view or noisy settings [S6].

### When to Use and When Not
*   **Use**: Real-time novel view synthesis, high-quality 3D reconstruction from dense multi-view images, applications requiring explicit scene representation.
*   **Do Not Use**: Scenes with extreme sparsity of views without additional denoising/regularization [S6], applications with strict memory constraints without compression [12943-data-compression-and-storage-optimization.md], or when global illumination is critical without additional modules [S14, unofficial].

## Background

### Origin
3D Gaussian Splatting was introduced by Kerbl et al. in 2023 [S1, S2, S3, S4, S5, S6, S7, S8][S9, unofficial][S10, S11][S12, unofficial][S13][S14, unofficial]. It builds on the concept of volume rendering but uses explicit 3D Gaussians as primitives, allowing for differentiable rasterization and real-time rendering.

### History and Development
Since its introduction, numerous variants and optimizations have been proposed, including densification strategies [S1, S4], denoising [S6], defocus handling [S5], and large-scale rendering [S7]. The implementation details have evolved to include half-precision rasterization [S2], corrected scene extent [S4], and various acceleration techniques [S8].

### Where it is Used
3DGS is used in computer graphics, robotics (SLAM), virtual reality, and 3D reconstruction from images or videos. It is particularly popular in applications requiring real-time rendering and high visual fidelity.
