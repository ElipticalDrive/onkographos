# CLM
Also called: CPU-GPU Memory Barrier Removal, Smart Caching Policy for Gaussian States

## Overview
CLM is a training optimization technique for 3D Gaussian Splatting that eliminates the performance bottleneck of GPU memory barriers by dynamically migrating Gaussian states between CPU and GPU memory [S1, unofficial]. It solves the problem of excessive VRAM usage and synchronization stalls during the optimization of large scenes by employing a smart caching policy that retains only the most frequently updated Gaussians on the GPU [S1, unofficial]. Unlike sibling methods that rely on spatial partitioning or fixed memory layouts, CLM adapts the data residency based on gradient activity, enabling efficient training on hardware with limited VRAM without requiring scene decomposition [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A set of 3D Gaussian primitives $\mathcal{G}$ with parameters $\theta$ (position, covariance, opacity, spherical harmonics coefficients) initially residing in GPU memory.
- Output: Optimized Gaussian parameters $\theta^*$ with reduced training time and memory footprint.

**Data Structures:**
1.  **Gaussian State Buffer (GPU):** A contiguous memory block storing the active subset of Gaussians. Layout includes fields for position ($\mathbf{p}$, 3 floats), covariance ($\mathbf{\Sigma}$, 6 floats for symmetric matrix or quaternion+scale), opacity ($\alpha$, 1 float), and SH coefficients ($\mathbf{c}$, variable size).
2.  **Gaussian State Buffer (CPU):** A larger buffer storing the full scene data.
3.  **Cache Map:** A data structure mapping Gaussian IDs to their current residency status (CPU or GPU) and a usage counter or timestamp.

**Steps:**
1.  **Initialization:** Load all Gaussian parameters into CPU memory. Initialize the GPU buffer as empty or with a small seed set.
2.  **Gradient Tracking:** During the backward pass of differentiable rasterization, track which Gaussians contribute to the gradient of the loss function $\mathcal{L}$. Let $U_t$ be the set of Gaussians with non-zero gradients at step $t$.
3.  **Caching Policy Decision:**
    - Calculate a priority score for each Gaussian in $U_t$ based on frequency of update or magnitude of gradient.
    - If the number of active Gaussians exceeds the GPU buffer capacity, evict the least frequently updated Gaussians from GPU to CPU.
    - If new high-priority Gaussians are identified in $U_t$ that reside on CPU, transfer them to GPU.
4.  **Data Migration:** Perform asynchronous memory copies (e.g., `cudaMemcpyAsync`) between CPU and GPU buffers based on the migration decisions. Ensure synchronization barriers are minimized by overlapping computation with data transfer where possible.
5.  **Rasterization and Optimization:** Perform the forward rasterization and backward gradient computation using the current GPU resident set. Accumulate gradients.
6.  **Repeat:** Iterate until convergence.

**Formulas:**
- Let $C_{GPU}$ be the capacity of the GPU buffer in number of Gaussians.
- Let $Score(g)$ be the update frequency or gradient magnitude for Gaussian $g$.
- The set of Gaussians on GPU at step $t$, $G_{GPU}^t$, is determined by:
  $$ G_{GPU}^t = \text{TopK}(G_{active}^t \cup G_{GPU}^{t-1}, K=C_{GPU}, \text{key}=Score) $$
  where $G_{active}^t$ are Gaussians contributing to gradients at step $t$.

**Parameters:**
- GPU Buffer Capacity ($C_{GPU}$): Typically set to fit within available VRAM minus overhead for rasterization intermediates. Not given in the sources.
- Eviction Threshold: Not given in the sources.

**Edge Cases and Pitfalls:**
- **Thrashing:** If the set of active Gaussians changes drastically between steps, frequent CPU-GPU transfers can degrade performance. [G] Mitigation: Use a hysteresis threshold for eviction.
- **Boundary Conditions:** Gaussians near the edge of the view frustum may flicker in and out of the active set. [G] Mitigation: Expand the view frustum slightly when determining active Gaussians.

## Subtopics

### Out-of-Core Training and Rendering
A framework that stores the full scene in CPU RAM and dynamically streams only visible Gaussians to GPU memory, enabling training and rendering of scenes exceeding VRAM on a single consumer GPU [S2, unofficial]. It differs from CLM by explicitly managing visibility and Level-of-Detail (LoD) rather than just update frequency, and by using a hierarchical structure (Sequential Point Trees) for efficient view-dependent selection [S2, unofficial]. Choose this method when training ultra-large-scale scenes (e.g., city-scale) that do not fit in CPU RAM for simple caching, or when interactive rendering of large scenes is required. Link: [A LoD of Gaussians](9598-a-lod-of-gaussians.md).

**Steps:**
1.  Store all Gaussian data in CPU RAM [S2, unofficial].
2.  Dynamically stream only those Gaussians visible from the current training view into GPU memory [S2, unofficial].
3.  Use a lightweight caching system that tracks recently used Gaussians and reuses them across training iterations to reduce CPU-GPU data transfer [S2, unofficial].

**Pitfalls:**
- A single distant view could require access to the full scene, causing high transfer overhead [S2, unofficial].

## Operating characteristics
- **Time Complexity:** Depends on the frequency of CPU-GPU transfers. In the worst case, if all Gaussians are updated every step, complexity approaches that of standard in-memory training plus transfer overhead. In practice, it reduces effective memory bandwidth pressure on the GPU.
- **Memory Complexity:** Reduces peak GPU memory usage to the size of the cached subset, allowing training of scenes larger than VRAM. CPU memory usage remains proportional to the full scene size.
- **Measured Performance:** Not given in the sources.
- **Scaling:** Scales to larger scenes by offloading inactive Gaussians to CPU. Performance may degrade if the active set is too large for the GPU buffer or if transfer bandwidth is a bottleneck.
- **Strengths:** Eliminates GPU memory barriers; enables training on consumer hardware with limited VRAM; reduces memory fragmentation.
- **Limitations:** Requires efficient CPU-GPU data transfer; potential for thrashing if caching policy is not tuned; adds CPU overhead for managing the cache.
- **When to use:** When VRAM is insufficient to hold all Gaussians simultaneously, or when training large scenes on limited hardware.
- **When not to use:** When the scene fits comfortably in VRAM and transfer overhead outweighs the benefits; when real-time rendering is required during training (transfer latency may cause stutter).

## Background
CLM was introduced as part of the broader effort to optimize 3D Gaussian Splatting training. It addresses the memory bottleneck identified in early implementations where all Gaussian states had to reside in GPU memory. The method is cited in surveys of 3D Gaussian Splatting rasterization and optimization techniques [S1, unofficial]. It is distinct from distributed optimization methods like Grendel-GS, which partition data across multiple GPUs, and out-of-core methods like TideGS, which stream from disk [S1, unofficial].
