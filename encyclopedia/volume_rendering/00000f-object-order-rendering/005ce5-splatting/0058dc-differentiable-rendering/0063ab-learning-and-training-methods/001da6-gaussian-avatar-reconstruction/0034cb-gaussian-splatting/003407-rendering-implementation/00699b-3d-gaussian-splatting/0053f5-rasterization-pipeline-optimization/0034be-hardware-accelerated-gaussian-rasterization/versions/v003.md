# Hardware-Accelerated Gaussian Rasterization

Also called: GauRast, Hardware Architecture Pipeline, Hardware-algorithm co-design for Gaussian rasterization

## Overview
Hardware-Accelerated Gaussian Rasterization is a hardware-algorithm co-design that augments standard triangle rasterizers with dedicated units for Gaussian projection and blending, achieving an order of magnitude speedup in the rasterization stage [S1, unofficial]. It solves the bottleneck of rendering 3D Gaussians on general-purpose GPUs by offloading specific computational patterns to specialized hardware pipelines [S1, unofficial]. Unlike general-purpose compute shaders, this method isolates preprocessing and rendering into distinct hardware stages, optimizing data flow and reducing memory bandwidth requirements [S2].

## How it works
The method implements a four-stage hardware pipeline: Stage 0 (Near-plane culling), Stage 1 (Projection), Stage 2 (Sorting), and Stage 3 (Rasterization) [S2]. The preprocessing steps (0-1) are point-based, while the rendering steps (2-3) are tile-based [S2].

**Inputs and Outputs:**
*   **Input:** 3D Gaussian primitives (position, covariance, opacity, spherical harmonics coefficients) and camera parameters.
*   **Output:** 2D image pixels with color and alpha values.

**Data Structures:**
*   **Tile Assignment:** The image is divided into 16x16 pixel tiles [S2]. Each tile is assigned to an independent SRAM bank [S2].
*   **SRAM Bank:** Contains a fixed entry depth and an address offset controller [S2]. An index is used to look up values in a codebook [S2].
*   **Sorting Unit:** Processes data elements in batches (e.g., 256 elements per sub-sorter) using a comparison-free sorter design [S2].

**Numbered Steps:**

1.  **Stage 0: Near-plane Culling.**
    *   Eliminates parameter access for invisible regions using an Axis-Aligned Bounding Box (AABB) depth-interval test [S2].
    *   This stage is isolated to handle the largest number of Gaussian points efficiently [S2].

2.  **Stage 1: Projection.**
    *   Projects 3D Gaussians onto the 2D image plane [S2].
    *   Utilizes a zero-Jacobian skipping mechanism to optimize matrix multiplication [S2].
    *   Implemented using a 6x1 multiplier-accumulator array [S2].
    *   *Note:* The specific formula for the zero-Jacobian skip is not provided in the sources, but it implies skipping multiplication by zero terms in the Jacobian calculation [S2].

3.  **Stage 2: Gaussian Sorting.**
    *   Sorts projected Gaussians by depth for each tile [S2].
    *   Uses a four-way sub-sorter parallelism based on a comparison-free sorter [S2].
    *   Outputs the current maximum value in a linear sorting delay, aligning with the alpha-blending process [S2].

4.  **Stage 3: Rasterization.**
    *   Performs alpha-blending [S2].
    *   Processes one point at a time, aligned with the sorting output [S2].
    *   Each 16x16 tile is processed independently using its assigned SRAM bank [S2].

## Subtopics

### Compressed 3D Gaussian Splatting Renderer
A renderer for compressed scenes using GPU sorting and rasterization, enabling real-time novel view synthesis on low-end devices and integration with polygonal rendering [S3]. It differs from the original compute pipeline by using hardware rasterization, allowing seamless integration into VR/AR environments or games alongside polygon models [S3]. It achieves significant speed-up over the compute pipeline by Kerbl et al. [S3].

### LS-Gaussian Hardware Architecture
A dedicated hardware accelerator designed to accelerate 3DGS by enabling early stages to process subsequent frames while later stages execute previous ones, improving parallelism and pipeline efficiency [S4]. It enhances the Culling and Conversion Unit (CCU) with square root and logarithmic operators, replacing GSCore’s dual OBB Intersection Test Units (OIUs) [S4]. It uses a Viewpoint Transformation Unit (VTU) for sparse rendering and an Interpolation Unit with a threshold of 56 validly projected pixels per tile to trigger interpolation instead of full re-rendering [S4].

## Operating characteristics
*   **Time Complexity:** The hardware pipeline achieves an order of magnitude speedup in the rasterization stage compared to software implementations [S1, unofficial]. The sorting unit provides linear sorting delay, increasing processing speed [S2].
*   **Memory Complexity:** Tile-based processing with independent SRAM banks reduces memory requirements for rasterization [S2]. Compressed variants reduce storage requirements by up to 31x [S3].
*   **Measured Performance:** The accelerator achieves 129 FPS at Full HD resolution [S2].
*   **Strengths:** High throughput, low latency for sorting, efficient memory usage via tiling, and integration with standard graphics pipelines [S1, unofficial][S2, S3].
*   **Limitations:** Hardware-specific implementation requires custom silicon or FPGA design; workload imbalance can reduce utilization if not managed [S4].
*   **When to use:** Real-time rendering on constrained hardware, VR/AR applications requiring integration with polygonal rendering, and scenarios where high frame rates are critical [S1, unofficial][S3].
*   **When not to use:** When flexibility in the rendering pipeline is required, or when hardware resources are not available for the specialized units [S3].

## Background
The concept of hardware-accelerated Gaussian rasterization emerged from the need to render 3D Gaussian Splatting (3DGS) efficiently on standard graphics hardware [S1, unofficial]. The original 3DGS rendering relied on specialized compute pipelines, which were difficult to integrate into existing graphics engines [S3]. GauRast [116] proposed augmenting standard triangle rasterizers with dedicated units for Gaussian projection and blending [S1, unofficial]. Subsequent work, such as LS-Gaussian, further optimized this approach with streaming mechanisms and specialized units like the CCU and VTU [S4]. The method is part of a broader trend of hardware-algorithm co-design for neural rendering [S1, unofficial].
