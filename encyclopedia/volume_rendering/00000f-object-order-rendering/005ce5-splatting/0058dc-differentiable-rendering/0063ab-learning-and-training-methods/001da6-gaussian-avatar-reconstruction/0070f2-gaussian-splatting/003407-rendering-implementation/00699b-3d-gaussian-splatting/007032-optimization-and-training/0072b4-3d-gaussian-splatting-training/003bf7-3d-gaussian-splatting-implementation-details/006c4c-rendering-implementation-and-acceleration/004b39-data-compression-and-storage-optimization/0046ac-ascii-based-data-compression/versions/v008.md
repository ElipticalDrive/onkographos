# ASCII-Based Data Compression
Also called: Anywhere Compression, Base 94 Floating-Point Compression, Base 95 Integer Compression

## Overview
ASCII-Based Data Compression reduces the bitrate of data transmission during the training of 3D Gaussian Splatting by encoding numerical values into ASCII character strings [S1, unofficial]. It sets itself apart from sibling methods like [Sensitivity-Aware Vector Clustering](12167-sensitivity-aware-vector-clustering.md) and [Compact 3D Gaussian Representation (C3DGS)](12927-compact-3d-gaussian-representation-c3dgs.md) by focusing on transmission efficiency rather than storage density or geometric simplification, achieving approximately 6% training speed improvement [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Continuous floating-point numbers (e.g., Gaussian parameters, SH coefficients) or integer indices.
*   **Output:** A string of ASCII characters representing the compressed number.

**Data Structures:**
*   **Integer Encoding:** Maps integers in the range $[0, 95]$ to a single ASCII character.
*   **Floating-Point Encoding:** Maps the integer component of a float to a single ASCII character in the range $[0, 94]$, followed by a separator character, followed by the decimal place representation.

**Steps:**

1.  **Integer Compression (Base 95):**
    *   Select ASCII characters with codes 32 to 126.
    *   Map each integer $n \in [0, 95]$ to the corresponding ASCII character $c = \text{chr}(n + 32)$.
    *   Store the resulting string.

2.  **Floating-Point Compression (Base 94):**
    *   Select ASCII characters with codes 32 to 125 for the integer part.
    *   Select ASCII character 126 (`~`) as the separator between the integer and fractional parts.
    *   Let the floating-point number be $f$.
    *   Extract the integer part $I$ and the decimal places $d$ (number of digits after the decimal point).
    *   Encode $I$ into a single ASCII character $c_I = \text{chr}(I + 32)$.
    *   Encode $d$ as a string of digits (or a single character if $d < 10$, though the source implies $d$ is the *count* of decimal places, not the value itself, see formula below).
    *   Concatenate: $S = c_I + \text{chr}(126) + \text{str}(d)$.
    *   *Note:* The source specifies "decimal places $d$" and the formula $f = I \times 10^{-d}$. This implies $d$ is the exponent magnitude, not the fractional value. For example, if $f=1.5$, $I=1$, and if we assume 1 decimal place, $d=1$. Then $1 \times 10^{-1} = 0.1 \neq 1.5$. There is a logical inconsistency in the source's formula vs. standard decimal representation. However, the source explicitly states: "The final floating-point value $f$ will be gained by $f = I \times 10^{-d}$." This formula is mathematically insufficient to reconstruct a general float from just an integer $I$ and a count $d$. It likely implies a specific quantization scheme where the fractional part is implicitly zero or handled differently, or the source contains an error. Given the constraint to be implementable, we must follow the source's explicit decoding rule, even if it seems flawed for general floats. A more likely interpretation in compression contexts is that $d$ represents the fractional digits themselves, but the source calls it "decimal places". Let's stick to the literal text: "split... into two part... integer part $I$... decimal places $d$... $f = I \times 10^{-d}$." This formula is strictly followed.

3.  **Color Matrix Optimization:**
    *   Quantize each item in the output color matrix to one decimal place.
    *   The range is $[0.0, 2.0]$.
    *   This results in 21 alternative numbers ($0.0, 0.1, ..., 2.0$).
    *   Apply ASCII compression to these quantized values.

4.  **Decoding:**
    *   **Integer:** Convert ASCII string directly to decimal integer.
    *   **Floating-Point:** Split the ASCII string at the separator (ASCII 126). Parse the integer part $I$ and the decimal places $d$. Calculate $f = I \times 10^{-d}$.

**Parameters:**
*   Integer Base: 95.
*   Floating-Point Base: 94 (for integer component).
*   Color Precision: 1 decimal place.

**Pitfalls:**
*   **Matrix Traversal:** Compressing large color matrices via ASCII string traversal is slow. Using PyTorch internal functions like `torch.where` and `torch.index_select` improves speed but is not fast enough to fully replace standard transmission [S1, unofficial].
*   **Line Breaks:** Using line break characters adds overhead in writing and decoding [S1, unofficial].
*   **Formula Ambiguity:** The decoding formula $f = I \times 10^{-d}$ does not reconstruct the original floating-point value if $d$ is merely the *count* of decimal places. It assumes the fractional part is zero or the source text contains a typo (likely meaning $d$ is the fractional value scaled, or the formula is $I + \text{fraction}$). Implementers should verify if $d$ represents the fractional digits string or the exponent. The source text says "decimal places $d$", which usually means count. If $d$ is count, the formula is wrong for non-integers. If $d$ is the fractional value (e.g., 0.5), the formula is still wrong. The most plausible implementation that matches "decimal places" as a count and yields a valid float is that the source meant $f = I + \text{fraction}$, but wrote $I \times 10^{-d}$. However, strict adherence to the source requires using the stated formula. [G] In practice, if $d$ is the number of decimal digits, the fractional part must be transmitted separately or assumed zero. Given the "21 alternative numbers" for color, the values are discrete. For general Gaussians, this method's applicability is limited by this formula.

## Operating characteristics
*   **Time Complexity:** The compression/decompression is $O(N)$ where $N$ is the number of elements. However, the overhead of string conversion and traversal makes it slower than binary transmission for large matrices [S1, unofficial].
*   **Memory Complexity:** Reduces data size significantly for color matrices due to quantization and ASCII encoding, but the string representation may be larger than binary float for small ranges if not carefully managed.
*   **Performance:** Gains approximately 6% or less improvement in training speed [S1, unofficial].
*   **Strengths:** Simple implementation; improves transmission speed for certain data types; reduces color matrix size via quantization.
*   **Limitations:** Slow for large matrix traversal; formula for floating-point decoding is ambiguous or incorrect for general floats; limited gain (6%).
*   **When to use:** When data transmission is the bottleneck and the data can be quantized to the specified ranges (e.g., color matrices).
*   **When not to use:** For high-precision Gaussian parameters where the floating-point decoding formula fails to reconstruct values accurately.

## Background
This method was proposed in the paper "I3DGS: Improve 3D Gaussian Splatting from Multiple Dimensions" by F. Author et al. [S1, unofficial]. It is part of a broader effort to optimize 3D Gaussian Splatting training speed through various dimensions including compression, learning, and structure design.
