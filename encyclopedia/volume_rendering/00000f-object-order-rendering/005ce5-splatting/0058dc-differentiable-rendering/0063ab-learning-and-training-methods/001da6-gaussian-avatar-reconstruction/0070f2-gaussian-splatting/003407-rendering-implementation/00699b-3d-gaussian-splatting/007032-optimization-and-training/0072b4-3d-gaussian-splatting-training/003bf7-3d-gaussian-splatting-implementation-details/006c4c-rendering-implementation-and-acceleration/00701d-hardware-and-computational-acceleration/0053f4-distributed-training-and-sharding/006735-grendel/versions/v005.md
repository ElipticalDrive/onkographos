# Grendel

Also called: distributed 3DGS training system

## Overview
Grendel is a distributed training system for 3D Gaussian Splatting (3DGS) that partitions parameters and parallelizes computation across multiple GPUs to overcome single-GPU memory constraints in high-resolution and large-scale reconstruction [S1]. It distinguishes itself by exploiting mixed parallelism (Gaussian-wise and pixel-wise) and spatial locality to handle dynamic, unbalanced workloads, while supporting batched training with multiple camera views to improve GPU utilization [S1]. Unlike systems that rely on dense weight sharding or divide-and-conquer cell partitioning, Grendel uses sparse all-to-all communication to transfer only relevant Gaussians and employs dynamic load balancing to maintain efficiency [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A set of 3D Gaussians (defined by mean $\mu$, covariance $\Sigma$, opacity $\alpha$, and color/radiance parameters), a batch of $B$ training images (views), and the number of GPUs $G$.
*   **Output:** Optimized 3D Gaussian parameters and reconstructed scene.

**Data Structures:**
*   **Gaussian Parameters:** Distributed uniformly across $G$ GPUs. Each GPU stores a subset of Gaussians, including their parameters and optimizer states (Adam moments) [S1].
*   **Pixel Blocks:** Images are partitioned into $16 \times 16$-pixel blocks [S1].
*   **Runtime Estimates:** A history of rendering times per pixel block is maintained to estimate computational load [S1].

**Steps:**

1.  **Gaussian-wise Distribution (Forward):**
    Partition the 3D Gaussians uniformly across the $G$ GPUs. Each GPU independently computes the Gaussian transformation (projection to screen space) for its assigned subset of Gaussians [S1].

2.  **Sparse All-to-All Communication (Forward):**
    After transformation, each GPU determines which of its transformed Gaussians intersect with the pixels in its assigned image partition. Using spatial locality, each GPU identifies the subset of Gaussians required by its pixel partition. A sparse all-to-all communication operation transfers these intersecting Gaussians to the GPUs responsible for rendering those pixels [S1].

3.  **Pixel-wise Distribution (Rendering):**
    The image is partitioned into $16 \times 16$-pixel blocks. These blocks are distributed to GPUs using an adaptive strategy based on estimated workload. Each GPU renders its assigned blocks, computing the loss and gradients [S1]. Note that a GPU may be assigned blocks from different images within the batch [S1].

4.  **Sparse All-to-All Communication (Backward):**
    A reversed all-to-all communication is performed during the backward pass to aggregate gradients and update the Gaussian parameters [S1].

5.  **Gaussian-wise Rebalancing:**
    After every few densification steps (cloning and splitting), the 3D Gaussians are redistributed uniformly across GPUs. This restores uniformity because newly added Gaussians cause imbalance due to varying densification rates across the scene [S1].

6.  **Pixel-wise Rebalancing:**
    To handle workload imbalances caused by varying Gaussian densities and scene complexity, Grendel dynamically adjusts pixel block assignments.
    *   **Measurement:** Record the rendering time (including image rendering, loss computation, and backward computation) of each pixel block assigned to a GPU during every epoch (after the first few) [S1].
    *   **Estimation:** Compute the average per-pixel computation time for each GPU. Assume that any pixel $p$ assigned to a GPU requires time proportional to this average [S1].
    *   **Re-splitting:** In subsequent iterations, re-split the image into $16 \times 16$ pixel blocks such that the sum of estimated computation times for pixels assigned to all GPUs is equal. This is achieved by calculating division points based on the cumulative sum of estimated runtimes [S1].

**Hyperparameter Scaling for Batched Training:**
Grendel supports batch sizes greater than 1. To maintain stability and efficiency, hyperparameters are scaled based on the batch size $b$ using the Independent Gradients Hypothesis [S1]:
*   **Learning Rate:** $\lambda' = \lambda \times \sqrt{b}$, where $\lambda$ is the original learning rate and $\lambda'$ is the adjusted rate [S1].
*   **Momentum:** $\beta_1' = \beta_1^b$ and $\beta_2' = \beta_2^b$, where $\beta_1, \beta_2$ are the original Adam momentum parameters and $\beta_1', \beta_2'$ are the adjusted parameters [S1].

**Pseudocode for Pixel-wise Rebalancing:**
The following algorithm calculates the division points to split an image into load-balanced subsequences of pixel blocks.

```python
def calculate_division_points(estimated_runtimes, num_gpus):
    """
    Calculate division points to distribute pixel blocks across GPUs
    based on estimated runtimes.

    Args:
        estimated_runtimes (list[float]): Estimated runtime for each pixel block.
        num_gpus (int): Number of GPUs (G).

    Returns:
        list[int]: Division points (indices) to split the blocks.
    """
    import torch

    # B is the number of pixel blocks
    B = len(estimated_runtimes)
    G = num_gpus

    # 1: CT <- torch.cumsum(ET)
    # Cumulative sum of estimated runtimes
    cumulative_times = torch.cumsum(torch.tensor(estimated_runtimes), dim=0)

    # 2: ETgpu <- CT[B-1] / G
    # Estimated total runtime per GPU
    et_gpu = cumulative_times[-1] / G

    # 3: TH <- torch.arange(0, G) * ETgpu
    # Thresholds for Division Points
    thresholds = torch.arange(0, G) * et_gpu

    # 4: DP <- torch.searchsorted(CT, TH)
    # Division Points
    division_points = torch.searchsorted(cumulative_times, thresholds)

    # 5: return DP
    return division_points.tolist()
```

**Edge Cases and Pitfalls:**
*   **Gradient Correlation:** Increasing batch size without adjusting hyperparameters leads to unstable training. The Independent Gradients Hypothesis assumes gradients from different views are independent, but cameras with similar poses produce correlated gradients, changing sparsity and dynamics as batch size increases [S1].
*   **Densification Imbalance:** New Gaussians added via cloning/splitting densify at different rates depending on local scene details, causing immediate imbalance in Gaussian-wise distribution if not rebalanced [S1].
*   **Static Partitioning Failure:** Static workload partitioning becomes suboptimal due to dynamic and unbalanced workloads varying across space and time [S1].

## Operating characteristics
*   **Time Complexity:** Training time scales with the number of Gaussians and images. Grendel achieves near-linear speedup in rendering time with added GPUs. For example, on the Rubble scene (3436x4591), rendering speed increases from 8.8 img/s on 1 GPU to 21.7 img/s on 4 GPUs [S1]. On the Matrixcity Block-all scene (1080x1920), it increases from 29.2 img/s to 76.8 img/s on 4 GPUs [S1].
*   **Memory Complexity:** Memory usage per GPU is reduced by partitioning Gaussians and pixels. This allows handling of high-resolution scenes (e.g., 4K Rubble with 40.4 million Gaussians) that exceed single-GPU memory limits [S1].
*   **Performance:** On the Rubble scene, Grendel training time on 4 A100s is 51 minutes, compared to 2 hours 3 minutes for CityGS Official and 2 hours 18 minutes for CityGS 200K-images [S1]. On the Matrixcity Block-all scene, training time is 54 minutes on 4 A100s, compared to 3 hours 31 minutes and 3 hours 36 minutes for CityGS variants [S1]. On the Bicycle scene (1275x1920), training time is 1 hour 13 minutes on 4 A100s, compared to 1 hour 20 minutes and 1 hour 24 minutes for CityGS variants [S1].
*   **Scalability:** Tested up to 16 GPUs for large scenes (e.g., Rubble with 40.4 million Gaussians) and 4 GPUs for medium scenes [S1]. Maximum tested batch size is 32 [S1].
*   **Strengths:** Handles high-resolution and large-scale scenes; supports batched training for better GPU utilization; dynamic load balancing handles unbalanced workloads; sparse communication reduces overhead compared to dense sharding [S1].
*   **Limitations:** Requires complex communication logic (sparse all-to-all); dynamic rebalancing adds overhead; hyperparameter scaling rules are heuristic and may not generalize to all scenarios [S1].
*   **When to use:** Large-scale, high-resolution 3D reconstruction tasks where single-GPU memory is insufficient and training time is a bottleneck [S1].
*   **When not to use:** Small-scale scenes that fit on a single GPU; scenarios where communication overhead outweighs computation benefits; when strict reproducibility with single-GPU hyperparameters is required without scaling adjustments [S1].

## Background
Grendel was introduced in the paper "On Scaling Up 3D Gaussian Splatting Training" [S1]. It addresses the limitations of single-GPU 3DGS training, which is constrained by memory and unable to handle high-resolution, large-scale scenes effectively [S1]. The system was developed to enable distributed training by leveraging mixed parallelism and spatial locality, allowing 3DGS to be scaled up to multiple GPUs while maintaining reconstruction quality and data efficiency [S1]. It is an open-source project available at https://github.com/nyu-systems/Grendel-GS [S1].
