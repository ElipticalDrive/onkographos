# CLM
Also called: CLM (CPU-Local Memory), Early Adam Update, CLM Pipelining, CPU-GPU Memory Barrier Removal, Smart Caching Policy for Gaussian States

## Overview
CLM is an optimization technique for 3D Gaussian Splatting (3DGS) training that eliminates the GPU memory barrier by offloading Gaussian model states to CPU memory and overlapping CPU-based Adam optimizer updates with subsequent GPU rendering passes [S2]. It addresses the high memory consumption and communication overhead inherent in naive offloading approaches by implementing a smart caching policy and a pipelined execution schedule [S1, unofficial][S2]. Unlike standard in-core training, CLM allows the Adam optimizer to update finalized Gaussians on the CPU before the entire training batch completes, effectively hiding offloading latency behind computation [S2].

## How it works
CLM operates by partitioning the training batch into microbatches and managing the lifecycle of Gaussian parameters across CPU and GPU memory. The method relies on the observation that many Gaussians are finalized (i.e., no longer accessed) in earlier microbatches of a batch, allowing their parameter updates to be computed on the CPU while the GPU processes subsequent microbatches [S2].

### Inputs and Outputs
*   **Inputs:** A batch of $B$ training views (microbatches $S_0, \dots, S_{B-1}$), the current Gaussian parameters $\theta$ (position, covariance, opacity, spherical harmonics), and the Adam optimizer state.
*   **Outputs:** Updated Gaussian parameters $\theta'$ and rendered images for the batch.

### Data Structures
1.  **Gaussian State Storage:** Gaussian attributes are stored in pinned CPU memory. To optimize transfer, attributes are concatenated and padded so that all attributes of a single Gaussian are contiguous and cache-line aligned [S2].
2.  **Finalization Map ($L_g$):** For each Gaussian $g$, a value $L_g$ is computed, representing the index of the last microbatch that accesses $g$. If $g$ is not accessed in the batch, $L_g = 0$ (or undefined, depending on implementation, but effectively not updated) [S2].
    $$ L_g = \max \{ i \mid g \in S_i \} $$
3.  **Double Buffer:** A double buffer design is used in the pipelining stage to enable parameter prefetching and delayed gradient offloading [S2].
4.  **Signal Buffer:** A signal buffer in CPU pinned memory synchronizes the GPU communication stream and the CPU Adam thread [S2].

### Algorithm Steps
1.  **Pre-compute Finalization Indices:** Before training the batch, compute $L_g$ for all Gaussians $g$ in the scene based on the current microbatch schedule [S2].
2.  **Microbatch Scheduling:** Schedule microbatches to maximize spatial locality ($S_{i+1} \cap S_i$ is large) and ensure that more Gaussians are finalized in earlier microbatches to maximize CPU-GPU overlap [S2].
3.  **Iterative Microbatch Processing:** For each microbatch $j$ from $0$ to $B-1$:
    a.  **Prefetch Parameters:** Load the parameters for Gaussians required by microbatch $j$ from CPU memory to GPU memory. This is done using a **Selective Loading Kernel** [S2].
        *   The kernel initiates from the GPU to avoid CPU-GPU coordination overhead.
        *   It loads in-frustum Gaussian parameters from pinned CPU memory to GPU registers and then to GPU memory [S2].
        *   It splits attributes from the contiguous CPU buffer and concatenates only the in-frustum attributes into GPU memory [S2].
    b.  **GPU Forward/Backward:** Perform the differentiable rasterization forward pass and backward pass for microbatch $j$ on the GPU [S2].
    c.  **Gradient Offloading:** Transfer the computed gradients for the updated Gaussians from GPU to CPU memory. A custom kernel handles this transfer efficiently [S2].
    d.  **CPU Adam Update (Early Update):** At the end of microbatch $j$, identify all Gaussians $g$ where $L_g = j$. Use the CPU Adam optimizer to update these Gaussians [S2].
        *   This update occurs on a dedicated CPU thread that releases the Python GIL, allowing concurrent execution with the GPU [S2].
        *   Synchronization is handled via the signal buffer: the GPU sets a gradient completion signal via DMA, triggering the CPU thread [S2].
    e.  **Cache Management:** Gaussians that have been finalized ($L_g = j$) may be evicted from GPU memory or kept in a cache if they are likely to be reused in future batches (smart caching) [S1, unofficial][S2].

### Parameters and Edge Cases
*   **Batch Size ($B$):** Larger batches allow more opportunities for overlap but increase the number of Gaussians finalized in the last microbatch, reducing overlap potential [S2].
*   **Spatial Locality:** The effectiveness of CLM depends heavily on the microbatch schedule. Poor scheduling reduces the intersection between consecutive microbatches, increasing communication overhead [S2].
*   **Last Microbatch Overhead:** Gaussians finalized in the last microbatch ($L_g = B-1$) do not have their CPU Adam computation overlapped with subsequent GPU work, creating a bottleneck [S2].
*   **Memory Usage:** CLM significantly reduces GPU memory usage for model states but slightly increases "other" memory usage due to the double buffer design [S2].

## Subtopics

### [Gaussians Cache Mechanism](17565-gaussians-cache-mechanism.md)
A dynamic store, query, and release mechanism to avoid re-inferencing reference views that share the same relative pose and features across consecutive iterations. It tracks recently used Gaussians and reuses them across training iterations to reduce CPU-GPU data transfer.

### Out-of-Core Training and Rendering
A framework storing the full scene in CPU RAM and dynamically streaming only visible Gaussians to GPU memory, enabling training and rendering of scenes exceeding VRAM on a single consumer GPU. It uses a lightweight caching system and a hierarchical Level-of-Detail (LoD) model to manage data access. A pitfall is that a single distant view could require access to the full scene, causing high transfer overhead [S3, unofficial].

### Selective Loading Kernel
A custom CUDA kernel that loads Gaussian parameters from pinned CPU memory to GPU registers and then to GPU memory, initiated from the GPU to avoid CPU-GPU coordination overhead. It splits Gaussian attributes from the contiguous CPU memory buffer and concatenates only the in-frustum Gaussian attributes together into GPU memory. It also handles the efficient transfer of gradients from GPU to CPU memory [S2].

## Operating characteristics
*   **Time Complexity:** The method reduces overall training time by overlapping communication and CPU Adam computation with GPU computation. The pipeline runtime is notably shorter than the combined computation and communication duration in naive offloading [S2].
*   **Memory Complexity:** Significantly reduces GPU memory usage for Gaussian model states, allowing training on GPUs with limited VRAM. However, it increases CPU memory usage and slightly elevates "other" GPU memory usage due to double buffering [S2].
*   **Performance:** On RTX 2080 Ti and RTX 4090, CLM provides significant speedups over naive offloading. The acceleration results from overlapping communication with computation and reduced communication volume by transferring only in-frustum Gaussians [S2].
*   **Strengths:** Enables training of large scenes on consumer GPUs; reduces memory barrier; overlaps CPU and GPU work.
*   **Limitations:** Requires careful microbatch scheduling for optimal performance; overhead for Gaussians finalized in the last microbatch; increased CPU memory usage [S2].

## Background
CLM was introduced in the paper "CLM: Removing the GPU Memory Barrier for 3D Gaussian Splatting" [S2]. It builds upon the Grendel training framework and gsplat rasterization kernels [S2]. The method addresses the limitations of naive offloading, where communication and CPU Adam overheads account for more than 50% of training time [S2]. It is part of a broader family of optimization techniques for 3D Gaussian Splatting, including Out-of-Core methods like TideGS and A LoD of Gaussians [S1, S3, unofficial].
