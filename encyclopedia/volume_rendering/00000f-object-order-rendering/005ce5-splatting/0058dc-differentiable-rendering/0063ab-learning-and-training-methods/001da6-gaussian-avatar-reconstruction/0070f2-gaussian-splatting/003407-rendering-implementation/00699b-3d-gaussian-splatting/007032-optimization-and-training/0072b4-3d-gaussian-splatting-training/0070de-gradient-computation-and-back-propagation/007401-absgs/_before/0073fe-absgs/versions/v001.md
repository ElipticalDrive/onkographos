# AbsGS

Also called: Absolute Gaussian Splatting, Homodirectional view-space positional gradient

## Overview
AbsGS is a densification strategy for 3D Gaussian Splatting that replaces the standard view-space positional gradient with a homodirectional gradient to prevent gradient collision, allowing large Gaussians in over-reconstructed regions to split and recover fine details [S1]. It addresses the specific failure mode where pixel-wise sub-gradients of the view-space positional gradient have different directions, causing them to cancel each other out during summation, resulting in a small-scale gradient that fails to surpass the densification threshold [S1]. Unlike standard 3D-GS which sums signed gradients, AbsGS sums absolute gradients, ensuring that large Gaussians covering many pixels with varying gradient directions still accumulate a high magnitude value sufficient to trigger splitting [S1].

## How it works
AbsGS modifies the adaptive density control strategy of 3D Gaussian Splatting by changing the criterion used to determine if a Gaussian primitive requires splitting. It retains the original clone operation but replaces the gradient magnitude check for splitting with a homodirectional view-space positional gradient [S1].

### Inputs and Outputs
- **Inputs**: The current set of 3D Gaussian primitives $G_i$, each defined by position $\mu_i$, covariance $\Sigma_i$, opacity $\alpha_i$, and spherical harmonics coefficients for color [S1]. The loss $L$ computed from the rendered image compared to the ground truth [S1].
- **Outputs**: An updated set of Gaussian primitives where those identified as over-reconstructed (large Gaussians in high-error regions) are split into smaller Gaussians [S1].

### Data Structures
The method operates on the existing 3D Gaussian Splatting data structures. No new global data structures are introduced. The key modification is in the calculation of the gradient metric stored or computed during the backward pass for each Gaussian [S1].

### Numbered Steps

1.  **Render and Compute Loss**: Render the scene using the current set of Gaussians and compute the pixel-wise loss $L_j$ for each pixel $j$ [S1].
2.  **Compute View-Space Positional Sub-Gradients**: For each Gaussian $G_i$, identify all pixels $j$ covered by the Gaussian's 2D projection. Compute the partial derivatives of the loss with respect to the view-space position components $\mu_{i,x}$ and $\mu_{i,y}$ for each covered pixel [S1].
3.  **Calculate Homodirectional Gradient**: Compute the homodirectional view-space positional gradient $\hat{g}_i$ for Gaussian $G_i$ by summing the absolute values of the pixel-wise sub-gradients for all $m$ covered pixels [S1].
    $$ \hat{g}_i = \sum_{j=1}^{m} \left( \left| \frac{\partial L_j}{\partial \mu_{i,x}} \right| + \left| \frac{\partial L_j}{\partial \mu_{i,y}} \right| \right) $$
    where:
    - $\hat{g}_i$ is the homodirectional gradient magnitude for Gaussian $G_i$.
    - $m$ is the number of pixels covered by Gaussian $G_i$.
    - $L_j$ is the loss at pixel $j$.
    - $\mu_{i,x}, \mu_{i,y}$ are the x and y components of the Gaussian center in view space [S1].
4.  **Check Densification Threshold**: Compare $\hat{g}_i$ against the densification threshold $\tau_p$ [S1].
5.  **Split or Clone**:
    - If $\hat{g}_i > \tau_p$ AND the scale of $G_i$ exceeds the scale threshold $\tau_S$, perform a **split** operation. The Gaussian is replaced by two children, typically initialized by perturbing the parent's position and scaling down its covariance [S1].
    - If $\hat{g}_i > \tau_p$ AND the scale of $G_i$ is below $\tau_S$, perform a **clone** operation. The Gaussian is duplicated [S1].
    - Note: The clone operation follows the original 3D-GS strategy using the standard gradient, not the homodirectional gradient [S1].
6.  **Pruning**: Remove Gaussians with low opacity or those that do not contribute significantly to the image, as per standard 3D-GS pruning procedures [S1].

### Pseudocode

```python
def compute_homodirectional_gradient(gaussian, pixels_covered, loss_gradients):
    """
    Computes the homodirectional view-space positional gradient for a single Gaussian.
    
    Args:
        gaussian: Object containing view-space position components mu_x, mu_y.
        pixels_covered: List of pixel indices covered by the Gaussian.
        loss_gradients: Dictionary or array mapping pixel index to gradient vector 
                        (dL/dmu_x, dL/dmu_y).
                        
    Returns:
        float: The homodirectional gradient magnitude.
    """
    grad_sum_x = 0.0
    grad_sum_y = 0.0
    
    for pixel_idx in pixels_covered:
        # Get sub-gradients for this pixel with respect to the Gaussian's position
        # Note: In practice, these are accumulated during the backward pass.
        # Here we assume we have access to the partial derivatives.
        dL_dmu_x = loss_gradients[pixel_idx].dL_dmu_x
        dL_dmu_y = loss_gradients[pixel_idx].dL_dmu_y
        
        # Sum absolute values of components separately
        grad_sum_x += abs(dL_dmu_x)
        grad_sum_y += abs(dL_dmu_y)
        
    homodirectional_grad = grad_sum_x + grad_sum_y
    return homodirectional_grad

def densification_step(gaussians, tau_p, tau_S):
    """
    Determines which Gaussians to split or clone based on homodirectional gradient.
    
    Args:
        gaussians: List of Gaussian primitives.
        tau_p: Gradient threshold for densification.
        tau_S: Scale threshold for splitting.
        
    Returns:
        List of new Gaussians to add (children from splits/clones).
    """
    new_gaussians = []
    
    for g in gaussians:
        # 1. Calculate homodirectional gradient
        # Assume get_covered_pixels and get_loss_gradients are helper functions
        # that retrieve the necessary data from the rendering pipeline.
        pixels = get_covered_pixels(g)
        if not pixels:
            continue
            
        grad_mag = compute_homodirectional_gradient(g, pixels, get_loss_gradients())
        
        # 2. Check if densification is needed
        if grad_mag > tau_p:
            current_scale = get_scale(g) # e.g., max eigenvalue or mean scale
            
            # 3. Split or Clone
            if current_scale > tau_S:
                # Split: Create two children
                child1 = split_gaussian(g)
                child2 = split_gaussian(g)
                new_gaussians.extend([child1, child2])
            else:
                # Clone: Duplicate the Gaussian
                # Clone uses standard gradient logic in original 3D-GS, 
                # but AbsGS uses homodirectional for selection. 
                # The clone itself is a copy.
                child = clone_gaussian(g)
                new_gaussians.append(child)
                
    return new_gaussians
```

### Parameters
- **Scale threshold ($\tau_S$)**: Controls the maximum allowed scale for Gaussians before they are eligible for splitting. Values tested: 0.01 and 0.001. Lowering it improves quality but increases memory [S1].
- **Gradient threshold ($\tau_p$)**: The threshold for the homodirectional gradient to trigger densification. Typical values used in evaluation: 0.0008 [S1].

### Edge Cases and Pitfalls
- **Gradient Collision**: The primary pitfall AbsGS addresses is gradient collision, where signed gradients cancel out. Simply lowering the standard gradient threshold $\tau_p$ in 3D-GS to fix over-reconstruction leads to significant memory consumption and selects many Gaussians that do not need splitting (noise) [S1].
- **Memory Overflow**: On a single V100 GPU, lowering $\tau_p$ below 0.0001 in standard 3D-GS results in out-of-CUDA-memory errors [S1].
- **Clone vs. Split**: AbsGS uses the homodirectional gradient only for guiding the split operation. The clone operation follows the original 3D-GS strategy using the standard gradient [S1].

## Operating characteristics
- **Time Complexity**: The additional cost is the computation of absolute values and summation of sub-gradients, which is linear with respect to the number of covered pixels per Gaussian. This is negligible compared to the rendering and backward pass costs [S1].
- **Memory Complexity**: AbsGS achieves similar or lower memory consumption compared to 3D-GS. By accurately identifying Gaussians that need splitting, it avoids the proliferation of unnecessary Gaussians that occurs when lowering $\tau_p$ in 3D-GS [S1].
- **Measured Performance**:
    - **Mip-NeRF360**: AbsGS-0004 ($\tau_S=0.01, \tau_p=0.0008$) achieves SSIM 0.817, PSNR 27.38, LPIPS 0.212, and Memory 374MB. AbsGS-0008 ($\tau_S=0.001, \tau_p=0.0008$) achieves SSIM 0.815, PSNR 27.41, LPIPS 0.211, and Memory 450MB [S1].
    - **Tanks & Temples**: AbsGS-0004 achieves SSIM 0.842, PSNR 23.64, LPIPS 0.190, and Memory 159MB. AbsGS-0008 achieves SSIM 0.845, PSNR 23.54, LPIPS 0.183, and Memory 202MB [S1].
    - **Deep Blending**: AbsGS-0004 achieves SSIM 0.902, PSNR 29.55, LPIPS 0.249, and Memory 265MB. AbsGS-0008 achieves SSIM 0.903, PSNR 29.69, LPIPS 0.241, and Memory 380MB [S1].
- **Strengths**: Recovers fine details in over-reconstructed regions; reduces memory consumption compared to 3D-GS with similar quality; easy to implement and incorporate into other Gaussian Splatting methods [S1].
- **Limitations**: Requires modification of the densification logic; performance depends on appropriate tuning of $\tau_S$ and $\tau_p$ [S1].

## Background
AbsGS was introduced in the paper 'AbsGS: Recovering Fine Details in 3D Gaussian Splatting' by the authors of the provided document, building upon 3D-GS [S1]. It addresses the issue of blurriness and loss of detail stemming from over-reconstruction in 3D Gaussian Splatting, identifying gradient collision in the adaptive density control strategy as a primary cause [S1].
