# Distributed Training and Sharding

Also called: Multi-GPU 3D Gaussian Splatting, Distributed 3DGS, Sharded Gaussian Training

## Overview
Distributed Training and Sharding addresses the single-GPU memory and compute bottlenecks that prevent 3D Gaussian Splatting (3DGS) from scaling to city-scale scenes or high-resolution scientific volumes. It solves this by partitioning the global set of Gaussian primitives and/or the image plane across multiple GPUs, enabling parallel optimization and rendering. It sets itself apart from sibling methods like [RoofGS](9830-roofgs.md) (which focuses on inference acceleration via roofline optimization) and [Tile-Based Comparison-Free Sorting](9991-tile-based-comparison-free-sorting.md) (which optimizes the sorting step within a single GPU) by explicitly distributing the state and computation across a cluster of accelerators.

## Shared principles
The methods in this family share a foundation in 3D Gaussian primitives defined by mean $\mu$, covariance $\Sigma$ (derived from scale $s$ and rotation $q$), opacity $\alpha$, and color/radiance parameters. Rendering involves projecting these 3D primitives to 2D screen space, typically via affine approximation of the projective transformation. The core mathematical operation is the evaluation of the Gaussian density function $P(x|\mu, \Sigma) = \exp\left(-\frac{1}{2}(x - \mu)^\top \Sigma^{-1} (x - \mu)\right)$ and alpha blending. Acceleration often relies on tiling the image plane and sorting primitives by depth.

## Subtopics

### [BlitzGS](15088-blitzgs.md)
BlitzGS is a distributed 3D Gaussian Splatting (3DGS) framework designed to accelerate city-scale reconstruction by reducing the active Gaussian workload at three coupled levels: system, model, and view. Unlike spatial block partitioning which incurs cross-block visibility waste and imbalanced shards, BlitzGS shards Gaussians across GPUs by index parity and employs importance-based pruning and distance-based LOD filtering to minimize redundant computation. It achieves nearly an order-of-magnitude faster training times compared to baselines like Momen.GS and CityGS-X while maintaining high reconstruction quality.

### [GS-Cache Inference Framework](15588-gs-cache-inference-framework.md)
GS-Cache is a holistic rendering framework designed to support real-time rendering of large-scale 3D Gaussian Splatting (3DGS) models, specifically targeting city-level scenes. It achieves an average frame rate exceeding 72 FPS at binocular 2K resolution by employing a cache-centric de-redundancy pipeline and elastic parallel scheduling. Unlike native 3DGS or unstructured methods, GS-Cache specifically targets "Structured Gaussian derivation methods" (such as Scaffold-GS and Octree-GS) which use anchors to derive neural Gaussians, addressing the computational bottleneck of the "Gaussian Derivation Stage". It sets itself apart by caching decoded Gaussian parameters across frames to eliminate inter-frame redundancy in the derivation stage, while leaving the rasterization stage uncached to preserve visual quality against occlusion changes.

### [Distributed 3D Gaussian Splatting](16979-distributed-3d-gaussian-splatting.md)
Distributed 3D Gaussian Splatting is a multi-GPU extension of the 3D-GS pipeline designed for scientific visualization. It solves the problem of single-GPU memory limitations by distributing the optimization of large-scale Gaussian primitives across multiple GPUs, enabling the reconstruction of datasets exceeding the capacity of a single accelerator. Unlike single-GPU methods, it scales training throughput and supports high-resolution rendering of complex scientific isosurfaces by leveraging a distributed training backend adapted from Grendel-GS.

### [Distributed Batched Rendering Loop](18495-distributed-batched-rendering-loop.md)
The Distributed Batched Rendering Loop is a training and evaluation pipeline for 3D Gaussian Splatting (3DGS) that parallelizes the rendering of multiple camera views across multiple GPUs to overcome single-GPU memory limits and accelerate large-scale reconstruction. Unlike single-GPU methods that process one view at a time, this method processes batches of camera views, dividing the workload via dynamic load balancing and sparse all-to-all communication to ensure each GPU composites only the pixels it owns. It is distinguished from sibling methods like [BlitzGS](15088-blitzgs.md) by its explicit support for batched training with multiple views and its integration of dynamic scheduling strategies to balance communication and computation overhead.

### [Online Image Rendering Placement](19195-online-image-rendering-placement.md)
Online Image Rendering Placement is a per-iteration optimization step in distributed 3D Gaussian Splatting training that assigns image patches to GPUs to minimize inter-node communication and balance computational load. Unlike static partitioning methods that assign entire images or fixed regions, this method dynamically determines the optimal GPU owner for each small image patch based on the current batch's frustum culling results. It sets itself apart from siblings like [BlitzGS](15088-blitzgs.md) or [Distributed 3D Gaussian Splatting](16979-distributed-3d-gaussian-splatting.md) by treating placement as a fast, online heuristic problem solved at every training step rather than an offline graph partitioning task.

### [Grendel](19770-grendel.md)
Grendel is a distributed training system for 3D Gaussian Splatting (3DGS) that partitions parameters and parallelizes computation across multiple GPUs to overcome single-GPU memory constraints in high-resolution and large-scale 3D reconstruction. It distinguishes itself from sibling methods like [BlitzGS](15088-blitzgs.md) and [Distributed 3D Gaussian Splatting](16979-distributed-3d-gaussian-splatting.md) by exploiting mixed parallelism (Gaussian-wise and pixel-wise) and spatial locality to handle dynamic, unbalanced workloads, while supporting batched training with multiple camera views. Unlike [CityGaussian](15088-blitzgs.md) which uses a divide-and-conquer approach with coarse training and cell merging, Grendel allows 3DGS to be scaled up on multiple GPUs in the same manner as original single-GPU training.

### LS-Gaussian Accelerator Architecture
- **Definition**: A hardware architecture co-designed with the LS-Gaussian algorithm to support workload-aware mapping, featuring a streaming pipeline that allows continuous processing across hardware modules without requiring global synchronization [S1].
- **Step**: The accelerator predicts the workload for each tile based on viewpoint transformation to enable more balanced parallel computation [S1].
- **Comparison**: Unlike naive assignment of tiles to rendering blocks which fails to achieve balanced load distribution, this architecture uses workload prediction to mitigate inter-block idling and intra-block bubbles [S1].

### Spatial Block Partitioning
- **Definition**: Divides the scene into fixed world-space spatial blocks (e.g., uniform grid). Each GPU is bound to a specific block and trains its Gaussians independently [S2, unofficial].
- **Step**: Construct a uniform grid (e.g., 4×5 or 5×6). Assign each block a boundary halo of neighboring Gaussians for cross-block consistency. Train blocks independently across GPUs. During rendering, cameras near block boundaries trigger cross-block visibility overlap and boundary reassignment. Perform a final single-GPU merge to assemble the full scene [S2, unofficial].
- **Pitfall**: Overlapping blocks re-optimize the same surfaces, wasting computation. In a 20-block split, 23.5M Gaussians are optimized but only 5.37M survive merge (77% discarded). Finer partitions increase redundancy and training time with negligible quality gain (<0.2 dB) [S2, unofficial].
- **Number**: On Building (1,920 cameras, 4 GPUs), 86.8% of cameras fall in ≥2 blocks for 20-block partition, and 95.5% for 30-block partition. Wall-clock time for split/make-span/merge reaches 115.6–169.8 min vs 39 min for sharding [S2, unofficial].

### Primitive Sharding (Index-Parity Sharding)
- **Definition**: Distributes a single global Gaussian model across multiple GPUs by assigning Gaussians to ranks based on index parity. Each GPU holds a balanced, scene-wide slice of the model [S2, unofficial].
- **Step**: Assign each Gaussian primitive to a GPU rank using index parity. During rendering, distribute each step through balanced tile allocation across GPUs. Route projected Gaussians to tile owners via all-to-all communication. Train using a single global camera stream. Each camera enters training once per iteration with no cross-block duplication. Only distributed cost is the all-to-all exchange inside each render step [S2, unofficial].
- **Number**: On a 4-GPU setup (Building scene, 1,920 cameras), communication cost for routing projected Gaussians to tile owners is 3–5 ms per iteration, staying under 7% of total iteration time [S2, unofficial].
- **Comparison**: Unlike spatial block partitioning, it eliminates boundary reassignment, cross-block visibility overlap, and the final single-GPU merge step. Storage and per-step rendering remain evenly distributed as GPU count grows [S2, unofficial].

### Naive Offloading
- **Definition**: A CPU offloading strategy for 3DGS training that transfers all Gaussian attributes to CPU memory before rendering, using pinned memory and CPU Adam [S3].
- **Step**: Adopts pre-rendering frustum culling for efficient kernel computation. Trains each batch one image at a time with gradient accumulation to reduce activation memory usage [S3].

## Background
The need for distributed training in 3D Gaussian Splatting arises from the quadratic growth of Gaussian primitives required for high-fidelity reconstruction of large scenes, which quickly exceeds the memory capacity of single GPUs (e.g., ~11.2M Gaussians on an NVIDIA A100) [S1]. Early attempts at scaling, such as spatial block partitioning, suffered from significant redundancy due to boundary overlaps and imbalanced workloads [S2, unofficial]. Methods like BlitzGS [S2, unofficial] and Grendel [S1] introduced index-parity sharding and mixed parallelism to address these inefficiencies, while specialized frameworks like GS-Cache [S1] and LS-Gaussian [S1] focus on inference-time acceleration and hardware co-design. The field has evolved from simple data parallelism to sophisticated dynamic load balancing and cache-aware scheduling to handle the irregular memory access patterns of Gaussian splatting.
