# Text Embedding Generation with Directional Views


## Overview
This method generates semantic text embeddings for 3D Gaussian Splatting by encoding language prompts into latent vectors using a frozen CLIP text encoder [S1, unofficial]. It distinguishes itself from sibling methods by explicitly generating directional view embeddings—appending view descriptors (e.g., 'front', 'side') to prompts—to condition the generation process on the camera's viewing angle [S1, unofficial][S2, S3]. Unlike [LangSplat](8104-langsplat.md) which focuses on general language grounding, or [Multimodal Object Embedding](21344-multimodal-object-embedding.md) which fuses static object attributes, this approach specifically addresses view-dependent semantic consistency by varying the input prompt based on the rendered viewpoint [S1, unofficial][S2, S3].

## How it works
**Inputs and Outputs:**
*   **Input:** A base text prompt string (e.g., "a panda") and a set of directional view descriptors.
*   **Output:** A dictionary of tensors mapping view keys to CLIP text embeddings.

**Data Structures:**
*   `self.embeddings`: A dictionary where keys are strings (`'pos'`, `'neg'`, `'front'`, `'side'`, `'back'`) and values are tensors of shape `[1, 77, 768]` (batch size 1, sequence length 77, embedding dimension 768) [S1, unofficial].

**Steps:**
1.  **Tokenization:** Tokenize the base prompt using the CLIP tokenizer with padding to the maximum model length.
    $$ \text{inputs} = \text{tokenizer}(\text{prompt}, \text{padding}=\text{"max\_length"}, \text{max\_length}=\text{tokenizer.model\_max\_length}, \text{return\_tensors}=\text{"pt"}) $$
    [S1, unofficial]
2.  **Base Encoding:** Pass the token IDs through the frozen CLIP text encoder to obtain the base embedding.
    $$ \text{embeddings} = \text{text\_encoder}(\text{inputs.input\_ids.to(device)})[0] $$
    [S1, unofficial]
3.  **Directional Augmentation:** For each directional view $d \in \{\text{'front'}, \text{'side'}, \text{'back'}\}$, append the string `', {d} view'` to the base prompt.
    $$ \text{prompt}_d = \text{prompt} + \text{', ' + d + ' view'} $$
    [S1, unofficial]
4.  **Directional Encoding:** Tokenize and encode each augmented prompt $\text{prompt}_d$ using the same frozen text encoder.
    $$ \text{embeddings}_d = \text{text\_encoder}(\text{tokenizer}(\text{prompt}_d, \text{padding}=\text{"max\_length"}, \text{max\_length}=\text{tokenizer.model\_max\_length}, \text{return\_tensors}=\text{"pt"}).\text{input\_ids.to(device)})[0] $$
    [S1, unofficial]
5.  **Storage:** Store the resulting tensors in `self.embeddings` under keys `'front'`, `'side'`, `'back'`. The base prompt is stored under `'pos'` (positive) and a negated or empty version under `'neg'` if required by the downstream loss function [S1, unofficial].

**Pseudocode:**
```python
import torch
from transformers import CLIPTextModel, CLIPTokenizer

class TextEmbeddingGenerator:
    def __init__(self, device="cuda"):
        self.device = device
        self.tokenizer = CLIPTokenizer.from_pretrained("openai/clip-vit-large-patch14")
        self.text_encoder = CLIPTextModel.from_pretrained("openai/clip-vit-large-patch14").to(device)
        self.text_encoder.eval() # Frozen
        self.embeddings = {}

    def generate(self, prompt: str) -> dict:
        # Step 1 & 2: Base encoding
        inputs = self.tokenizer(
            prompt, 
            padding="max_length", 
            max_length=self.tokenizer.model_max_length, 
            return_tensors="pt"
        )
        base_embed = self.text_encoder(inputs.input_ids.to(self.device))[0]
        self.embeddings['pos'] = base_embed

        # Step 3 & 4: Directional encoding
        directions = ['front', 'side', 'back']
        for d in directions:
            directional_prompt = f"{prompt}, {d} view"
            dir_inputs = self.tokenizer(
                directional_prompt, 
                padding="max_length", 
                max_length=self.tokenizer.model_max_length, 
                return_tensors="pt"
            )
            dir_embed = self.text_encoder(dir_inputs.input_ids.to(self.device))[0]
            self.embeddings[d] = dir_embed
        
        # Handle negative prompt if needed (common in diffusion pipelines)
        # [G] Standard practice for CLIP-based diffusion is to use an empty string or "ugly, blurry" for neg
        neg_inputs = self.tokenizer(
            "", 
            padding="max_length", 
            max_length=self.tokenizer.model_max_length, 
            return_tensors="pt"
        )
        neg_embed = self.text_encoder(neg_inputs.input_ids.to(self.device))[0]
        self.embeddings['neg'] = neg_embed

        return self.embeddings
```

**Parameters:**
*   `max_length`: 77 (CLIP standard) [S1, unofficial].
*   `embedding_dim`: 768 (CLIP ViT-L/14 standard) [S1, unofficial].
*   `directions`: `['front', 'side', 'back']` [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Janus Problem:** View-specific prompting does not fully solve the "Janus problem" (generating multiple faces or inconsistent semantics across views), as the loss function still encourages matching the input image appearance across all views [S3].
*   **Resolution Limits:** While rendering at higher resolutions (e.g., >128px) might benefit the prior loss, experiments showed no noticeable quality difference over 96px or 128px rendering resolutions [S3].

## Subtopics

### [TexGS-VolVis Representation and Optimization](11105-texgs-volvis-representation-and-optimization.md)
TexGS-VolVis is a method for representing and editing volume visualization (VolVis) scenes using textured 2D Gaussian Splatting (2DGS). It solves the problem of decoupling geometry from appearance in text-driven non-photorealistic style editing (NPSE), allowing for geometry-consistent stylization without the elliptical artifacts common in coupled representations. Unlike methods that freeze geometry to prevent distortion, TexGS-VolVis uses explicit 2D texture maps to store appearance, preserving geometric fidelity while enabling rich visual expressiveness.

### [View-Dependent Prompting](19229-view-dependent-prompting.md)
View-Dependent Prompting augments text prompts with directional suffixes based on the camera's position relative to the scene to guide diffusion-based 3D generation. It differs from sibling methods like [TexGS-VolVis Representation and Optimization](11105-texgs-volvis-representation-and-optimization.md) by explicitly conditioning the text embedding on the viewing angle rather than relying solely on volumetric or geometric consistency.

### [Multimodal Object Embedding](21344-multimodal-object-embedding.md)
Multimodal Object Embedding creates a unified semantic representation for 3D objects by fusing vision-based CLIP embeddings with optional text-based CLIP embeddings. It solves the problem of limited semantic grounding in open-vocabulary querying by capturing both visual features and high-level attribute descriptions in a single vector space. Unlike its sibling [Text Embedding Generation with Directional Views](8239-text-embedding-generation-with-directional-views.md), which generates directional view embeddings by appending view descriptors to prompts, this method focuses on instance-level fusion of static object attributes. It differs from [TexGS-VolVis Representation and Optimization](11105-texgs-volvis-representation-and-optimization.md) and [View-Dependent Prompting](19229-view-dependent-prompting.md) by explicitly combining a language-free ontology with an LLM-generated attribute channel.

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of directional views $N_v$ and the sequence length $L$. Encoding one prompt takes $O(L \cdot D^2)$ for the transformer encoder, where $D$ is the hidden dimension. Total time is $O(N_v \cdot L \cdot D^2)$.
*   **Memory Complexity:** $O(N_v \cdot B \cdot L \cdot D)$, where $B$ is batch size. For standard settings ($N_v=3, B=1, L=77, D=768$), this is negligible (~700 KB).
*   **Strengths:** Simple to implement; leverages pre-trained, robust semantic features from CLIP; explicitly handles view-dependent semantics.
*   **Limitations:** Does not resolve the Janus problem [S3]; relies on the quality of the frozen CLIP encoder; directional prompts are discrete and may not capture continuous view variations smoothly.
*   **When to use:** When view-dependent semantic consistency is required for 3D generation or editing, and the scene has distinct front/side/back orientations.
*   **When not to use:** For open-vocabulary querying requiring fine-grained instance-level fusion without view dependence, or when continuous view-dependent embeddings are needed.

## Background
The method originates from the integration of CLIP text encoders into 3D Gaussian Splatting pipelines for text-driven generation. The specific technique of appending directional view descriptors to prompts was introduced in [S1, unofficial] (DreamGaussian) and further explored in [S2] (Blended-NeRF) and [S3] (RealFusion). It builds on the principle that text embeddings can guide the optimization of 3D representations via diffusion priors [S1, unofficial][S2, S3].
