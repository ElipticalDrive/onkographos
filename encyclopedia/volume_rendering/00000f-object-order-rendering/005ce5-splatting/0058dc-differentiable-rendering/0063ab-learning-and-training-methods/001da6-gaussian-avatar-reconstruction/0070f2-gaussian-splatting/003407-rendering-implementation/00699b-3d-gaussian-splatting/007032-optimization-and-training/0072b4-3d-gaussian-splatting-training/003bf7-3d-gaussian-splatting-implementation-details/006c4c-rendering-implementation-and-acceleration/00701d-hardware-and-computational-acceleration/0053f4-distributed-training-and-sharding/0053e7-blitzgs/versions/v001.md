# BlitzGS

Also called: BlitzGS: City-Scale Gaussian Splatting at Lightning Speed
## Overview
BlitzGS is a distributed 3D Gaussian Splatting (3DGS) framework designed to accelerate city-scale training by reducing the active Gaussian workload at system, model, and view levels [S1, unofficial]. It solves the problem of excessive storage, communication, and rasterization overhead caused by processing overly dense primitive sets where only a small fraction contributes to the loss [S1, unofficial]. Unlike spatial block partitioning which incurs cross-block visibility waste and imbalanced shards, BlitzGS uses index parity sharding and importance-based filtering to achieve nearly an order-of-magnitude speedup while maintaining high reconstruction quality [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A set of calibrated images, initial 3D Gaussian primitives, and $M$ GPUs.
*   **Output:** Optimized 3D Gaussian parameters (position, covariance, opacity, spherical harmonics coefficients) and a rendered novel view image.

**Data Structures:**
*   **Global Gaussian Set $\mathcal{G}$:** The complete set of Gaussians.
*   **Shard $\mathcal{G}^{(m)}$:** The subset of Gaussians assigned to GPU $m$, where $m \in \{0, \dots, M-1\}$.
*   **Tile Map:** A mapping of image tiles to GPU owners for the all-to-all exchange.

**Numbered Steps:**

1.  **System-Level Sharding (Index Parity):**
    *   Partition the global Gaussian set $\mathcal{G}$ across $M$ GPUs based on index parity rather than spatial coordinates.
    *   GPU $m$ stores shard $\mathcal{G}^{(m)}$ containing approximately $|\mathcal{G}|/M$ Gaussians.
    *   This avoids cross-block redundancy and imbalanced shards inherent in spatial partitioning [S1, unofficial].

2.  **Model-Level Population Control:**
    *   **Importance Scoring:** Perform a pass to score each Gaussian's importance. This signal is used to reweight density control gradients [S1, unofficial].
    *   **Pruning:** Use the importance scores to prune redundant Gaussians that have low contribution [S1, unofficial].
    *   **Spawn Gating:** Apply a lightweight spawn gate to withhold candidate Gaussians predicted not to survive densification before they are spawned, limiting peak population [S1, unofficial].

3.  **View-Level Filtering:**
    *   **Distance-based LOD Gate:** For each camera, drop Gaussians that are too fine (small covariance) for the current camera distance, as they contribute negligibly to the image [S1, unofficial].
    *   **Importance-based Mask:** Skip Gaussians with negligible cross-view contribution based on the importance signal, further trimming the active set per camera [S1, unofficial].

4.  **Distributed Rendering Pipeline:**
    *   Each GPU projects only its own shard $\mathcal{G}^{(m)}$ into the camera space.
    *   The rendered image is divided into tiles. Each tile is assigned to a specific GPU owner.
    *   **Cross-GPU Exchange:** Perform a single all-to-all communication step to route every projected Gaussian to the GPUs owning the tiles it covers [S1, unofficial].
    *   Each GPU composites its assigned tiles using the received Gaussians.
    *   The final output is identical to a single-GPU renderer on the full set [S1, unofficial].

**Parameters:**
*   **Hardware:** 4x NVIDIA A6000 GPUs [S1, unofficial].
*   **Sharding Strategy:** Index parity (even/odd indices) [S1, unofficial].

**Pseudocode:**

```python
def blitzgs_train(images, initial_gaussians, num_gpus=4):
    # 1. System-Level Sharding
    # Shard Gaussians by index parity
    shards = {}
    for m in range(num_gpus):
        shards[m] = [g for i, g in enumerate(initial_gaussians) if i % num_gpus == m]
    
    # 2. Model-Level Population Control (Pre-Iteration)
    # Importance scoring and pruning
    importance_scores = compute_importance(shards)
    for m in range(num_gpus):
        shards[m] = prune_gaussians(shards[m], importance_scores[m])
        
    # Spawn gating for new candidates
    candidates = generate_candidates(shards)
    survival_predictions = predict_survival(candidates)
    valid_candidates = [c for c, pred in zip(candidates, survival_predictions) if pred]
    
    # 3. View-Level Filtering (Per Camera)
    active_gaussians_per_view = {}
    for camera in images:
        active = []
        for g in shards[camera.gpu_id]:
            # Distance-based LOD gate
            if is_too_fine_for_distance(g, camera):
                continue
            # Importance-based mask
            if importance_score(g) < threshold:
                continue
            active.append(g)
        active_gaussians_per_view[camera.id] = active

    # 4. Distributed Rendering
    # Projection
    projected_gaussians = {}
    for m in range(num_gpus):
        projected_gaussians[m] = project_gaussians(shards[m])
        
    # Tile Assignment and All-to-All Exchange
    # Assume tile_map maps tile_id -> gpu_id
    received_gaussians = {m: [] for m in range(num_gpus)}
    for tile_id, owner_gpu in tile_map.items():
        # Collect Gaussians covering this tile from all GPUs
        contributors = []
        for m in range(num_gpus):
            for g in projected_gaussians[m]:
                if covers_tile(g, tile_id):
                    contributors.append(g)
        # Send to owner
        received_gaussians[owner_gpu].extend(contributors)
        
    # Rasterization and Composition
    for m in range(num_gpus):
        render_image(m, received_gaussians[m], tile_map)
        
    # 5. Gradient Update
    # Use importance scores to reweight density control gradients
    update_gradients(shards, importance_scores)
    
    return shards
```

**Edge Cases and Pitfalls:**
*   **Imbalanced Shards:** Spatial partitioning can lead to imbalanced shards; index parity mitigates this [S1, unofficial].
*   **Cross-Block Visibility Waste:** Spatial partitioning causes visibility waste at block boundaries; index parity avoids this [S1, unofficial].
*   **Communication Overhead:** The all-to-all exchange must be efficient; BlitzGS minimizes this by reducing the active set [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Training time is significantly reduced compared to baselines. On the Rubble scene, BlitzGS takes 39 minutes, compared to 5 hours 3 minutes for Momen.GS and 4 hours 45 minutes for CityGS-X [S1, unofficial].
*   **Memory Complexity:** By pruning redundant Gaussians and gating spawns, peak population is limited, reducing memory usage per GPU [S1, unofficial].
*   **Measured Performance:** On 4x NVIDIA A6000 GPUs, BlitzGS achieves a scene-average PSNR of 33.79 dB on the Rubble scene and 24.66 dB on the Residence scene in tens of minutes [S1, unofficial].
*   **Strengths:** Near order-of-magnitude speedup over city-scale baselines; maintains high quality; avoids cross-block redundancy and imbalanced shards [S1, unofficial].
*   **Limitations:** Requires distributed infrastructure (multiple GPUs); relies on accurate importance scoring and survival prediction [S1, unofficial].
*   **When to Use:** City-scale or large-scale 3DGS training where speed is critical and multiple GPUs are available [S1, unofficial].
*   **When Not to Use:** Single-GPU setups or small-scale scenes where the overhead of distribution and complex filtering may not be justified [S1, unofficial].

## Background
BlitzGS was introduced by Zhongtao Wang, Huishan Au, Yisong Chen, Meng Gai, Yilong Li, Fei Zhu, Mai Su, Haojie Jin, and Guoping Wang in the paper "BlitzGS: City-Scale Gaussian Splatting at Lightning Speed" [S1, unofficial]. The work addresses the computational bottleneck of city-scale 3D reconstruction, which underpins applications like aerial survey inspection and digital twins [S1, unofficial]. It builds on insights from prior work on distributed rendering and importance-based simplification [S1, unofficial].
