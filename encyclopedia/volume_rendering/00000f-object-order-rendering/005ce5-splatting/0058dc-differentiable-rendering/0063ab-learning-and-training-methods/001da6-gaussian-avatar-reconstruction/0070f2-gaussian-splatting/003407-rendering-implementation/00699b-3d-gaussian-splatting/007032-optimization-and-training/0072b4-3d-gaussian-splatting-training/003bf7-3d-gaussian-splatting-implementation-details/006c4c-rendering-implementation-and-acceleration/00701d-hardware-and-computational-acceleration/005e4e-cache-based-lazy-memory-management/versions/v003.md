# Cache-based Lazy Memory Management

Also called: CLM (Cache-based Lazy Memory management)

## Overview
Cache-based Lazy Memory Management (CLM) is a memory offloading strategy that enables the training of large-scale 3D Gaussian Splatting (3DGS) scenes on a single consumer-grade GPU by keeping the majority of Gaussian primitives in CPU memory and loading only the subset accessed by the current training view [S1]. It distinguishes itself from naive offloading approaches (like Zero-Offload) by exploiting the inherent sparsity of 3DGS memory access patterns, using ahead-of-time view-Gaussian mapping, caching overlapping primitives between views, and scheduling iterations to maximize spatial locality, thereby overlapping communication with computation to hide CPU-GPU transfer overheads [S1].

## How it works
### Inputs and Outputs
**Inputs:**
- A set of posed training images (views) with known camera parameters.
- A large collection of 3D Gaussians representing the scene, stored primarily in CPU memory.
- The current GPU memory capacity (e.g., 24 GB for RTX 4090).

**Outputs:**
- Updated Gaussian parameters (position, covariance, spherical harmonics, opacity) optimized via gradient descent.
- Rendered images for the current training view.

### Data Structures
The core data structure is the 3D Gaussian primitive. Each Gaussian consists of 59 learnable parameters [S1]. To support gradient-based optimization (Adam), each parameter requires storage for:
1. The parameter value itself.
2. Its gradient.
3. Two additional versions for the optimizer state (momentum and variance) [S1].

This results in 4 floating-point values per parameter. Assuming 4 bytes per float, the memory footprint per Gaussian is:
$$ \text{Memory}_{\text{Gaussian}} = 59 \times 4 \times 4 \text{ bytes} = 944 \text{ bytes} $$

The total memory required for $N$ Gaussians is:
$$ \text{Memory}_{\text{Total}} = N \times 59 \times 4 \times 4 \text{ bytes} $$

For an RTX 4090 (24 GB), this limits the model state to approximately 26 million Gaussians, ignoring activation buffers [S1]. CLM manages these Gaussians in two regions:
- **CPU Memory:** Holds the full set of $N$ Gaussians.
- **GPU Memory:** Holds a dynamic subset $S_{\text{active}}$ of Gaussians currently being processed for the current view.

### Numbered Steps
1. **Pre-compute Access Maps:** For each training view, compute the set of Gaussians that contribute to the rendering of that view. This is done ahead-of-time [S1].
2. **Schedule Iterations:** Order the training iterations to exploit spatial locality. Views that are spatially close in the scene tend to access overlapping subsets of Gaussians. This scheduling maximizes the hit rate of the GPU cache [S1].
3. **Overlap Communication and Computation:**
   - For the current iteration $t$, identify the set of Gaussians $S_t$ required for the view.
   - Identify the set of Gaussians $S_{t-1}$ used in the previous iteration.
   - Calculate the difference: $S_{\text{load}} = S_t \setminus S_{t-1}$ (Gaussians to load) and $S_{\text{unload}} = S_{t-1} \setminus S_t$ (Gaussians to evict).
   - Initiate asynchronous CPU-to-GPU transfers for $S_{\text{load}}$ and GPU-to-CPU transfers for $S_{\text{unload}}$ while the GPU computes the forward pass for the previous iteration's active set [S1].
4. **Cache Overlapping Gaussians:** Maintain a cache on the GPU of Gaussians that are likely to be accessed by subsequent views. If a Gaussian is already in GPU memory, skip the load operation [S1].
5. **Render and Backpropagate:**
   - Once the required Gaussians are loaded, perform the forward pass (rasterization/splatting) and backward pass (gradient computation) on the GPU [S1].
   - Gradients are computed for the active subset $S_t$ [S1].
6. **Parameter Update:**
   - Transfer gradients back to the CPU.
   - Run the Adam optimizer on the CPU to update the parameters of the active Gaussians in CPU memory [S1].
   - Note: CLM overlaps a substantial portion of the parameter update with gradient computation where possible, leveraging spatial locality [S1].
7. **Repeat:** Proceed to the next iteration, repeating steps 3-6.

### Parameters and Typical Values
- **GPU Memory:** 24 GB (RTX 4090) [S1].
- **Gaussian Parameter Count:** 59 per Gaussian [S1].
- **Bytes per Parameter:** 16 bytes (4 floats: value, gradient, 2 optimizer states) [S1].
- **Scene Size:** Up to 102 million Gaussians [S1].

### Edge Cases and Pitfalls
- **Naive Offloading Overhead:** Simply loading all Gaussians to the GPU defeats the purpose of offloading, as GPU memory is insufficient for large scenes. Offloading all Gaussians to CPU and loading them one-by-one incurs significant CPU-GPU communication overhead and slows down the Adam optimizer if run on CPU without overlap [S1].
- **Precision:** Standard 32-bit floating point is used for parameters and gradients [S1].
- **Boundary Conditions:** The access map computation must accurately identify contributing Gaussians to avoid rendering artifacts or missing gradients. Inaccurate culling leads to either wasted memory (loading non-contributing Gaussians) or incorrect gradients (missing contributing Gaussians) [S1].

## Operating characteristics
- **Time Complexity:** The per-iteration time is dominated by the maximum of (communication time, GPU computation time, CPU optimizer time). CLM minimizes communication time by caching and scheduling [S1].
- **Memory Complexity:** GPU memory usage is proportional to the number of Gaussians accessed by a single view, not the total number of Gaussians $N$. This allows scaling to $N$ much larger than GPU capacity [S1].
- **Measured Performance:** CLM successfully trains a scene with 102 million Gaussians on a single RTX 4090 [S1]. It achieves state-of-the-art reconstruction quality comparable to multi-GPU systems [S1].
- **Strengths:** Scales to large scenes on consumer hardware; maintains high rendering quality; hides communication overhead through pipelining [S1].
- **Limitations:** Requires pre-computation of access maps; relies on spatial locality for optimal performance; CPU optimizer adds some latency if not fully overlapped [S1].
- **When to Use:** When training large-scale 3DGS scenes on a single GPU with limited memory.
- **When Not to Use:** For small scenes that fit entirely in GPU memory, the overhead of offloading management may not be justified, though CLM claims modest overhead even in these cases [S1].

## Background
CLM was introduced in the paper "CLM: Removing the GPU Memory Barrier for 3D Gaussian Splatting" presented at ASPLOS ’26 [S1]. It addresses the memory barrier that prevents standard 3DGS implementations from scaling to large scenes on single consumer GPUs, where memory requirements exceed 24 GB [S1]. The method builds on the observation that 3DGS training is inherently sparse, with each view only accessing a small subset of the total Gaussians [S1].
