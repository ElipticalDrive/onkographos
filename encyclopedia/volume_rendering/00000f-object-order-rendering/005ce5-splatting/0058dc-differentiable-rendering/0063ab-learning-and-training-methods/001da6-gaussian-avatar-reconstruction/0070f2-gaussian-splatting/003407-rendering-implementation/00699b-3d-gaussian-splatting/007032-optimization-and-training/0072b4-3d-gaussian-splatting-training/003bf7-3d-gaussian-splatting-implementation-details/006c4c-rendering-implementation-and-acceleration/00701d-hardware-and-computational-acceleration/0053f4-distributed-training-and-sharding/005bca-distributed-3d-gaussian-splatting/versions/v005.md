# Distributed 3D Gaussian Splatting

Also called: Distributed 3D Gaussian Splatting for Scientific Visualization, Distributed 3D-GS, Multi-GPU 3D-GS

## Overview
Distributed 3D Gaussian Splatting is a multi-GPU extension of the 3D Gaussian Splatting (3D-GS) pipeline designed for scientific visualization [S1]. It solves the problem of single-GPU memory limitations by distributing the optimization of large-scale Gaussian primitives across multiple GPUs, enabling the reconstruction of datasets exceeding the capacity of a single accelerator [S1]. Unlike single-GPU methods, it scales training throughput and supports high-resolution rendering of complex scientific isosurfaces by leveraging a distributed training backend adapted from Grendel-GS [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** Scientific volume data (e.g., VTK, HDF5), number of GPUs $M$, image resolution $R \times R$ (e.g., 2048x2048), number of synthetic camera views $V$ (typically 448 for scientific data [S1]).
*   **Output:** Optimized set of 3D Gaussians $\mathcal{G}$ and rendered images matching the synthetic views.

**Data Structures:**
The global set of $N$ Gaussians $\mathcal{G}$ is partitioned into shards $\mathcal{G}^{(m)}$ for each GPU $m \in \{0, \dots, M-1\}$ [S1]. Each GPU $m$ stores:
1.  Local shard $\mathcal{G}^{(m)}$ containing positions, covariances, opacities, and spherical harmonics coefficients.
2.  Corresponding optimizer states (e.g., Adam moments) for the parameters in $\mathcal{G}^{(m)}$ [S1].
3.  Training data subset (camera poses and target images) distributed across workers [S1].

**Steps:**
1.  **Initialization:** Extract isosurface point clouds directly from scientific volume data using external tools (e.g., ParaView) to serve as initializations for Gaussian primitives, bypassing image-based reconstruction [S1].
2.  **Distribution:** Distribute the global point cloud and Gaussian parameters such that each GPU holds a shard of the data [S1]. Distribute the training data (camera views) across workers [S1].
3.  **Forward Pass (Rendering):**
    *   Each GPU projects its local shard $\mathcal{G}^{(m)}$ to screen space for the assigned camera views [S1].
    *   Perform sparse all-to-all communication to route projected Gaussians to the GPUs owning the tiles they cover .
    *   Each GPU composites only the pixels for its owned tiles using the received Gaussians .
4.  **Loss Computation:** Compute the loss (e.g., L1 + D-SSIM) between the rendered images and the target synthetic views [S1].
5.  **Backward Pass & Synchronization:**
    *   Compute gradients locally for the assigned pixels .
    *   Synchronize gradients via a fused all-reduce scheme during training to aggregate gradients for global parameters [S1]. Alternatively, sparse all-to-all communication can be used to aggregate gradients for specific Gaussians .
6.  **Update:** Update the local shards using the aggregated gradients [S1].

**Pseudocode:**
```python
# Distributed 3D Gaussian Splatting Training Step
# Assumes M GPUs, each with rank m
# Global Gaussian set G is sharded: G[m] is local shard
# Training data D is distributed: D[m] is local subset of (camera, target_image)

def train_step(rank, num_gpus, G_shards, optimizer_states, D_local):
    # 1. Local Forward Pass
    # Project local Gaussians to screen space
    local_splats = project_splats(G_shards[rank], D_local.cameras)
    
    # 2. Communication: Route Gaussians to tile owners
    # Determine which tiles each GPU owns (e.g., based on image partitioning)
    # Send local_splats to other GPUs if they cover tiles owned by others
    # Receive splats from other GPUs that cover this GPU's tiles
    all_splats = all_to_all_communication(local_splats, tile_ownership_map)
    
    # 3. Local Rendering and Loss
    # Composite only the pixels for owned tiles
    rendered_images = composite_splats(all_splats, D_local.cameras, tile_ownership_map)
    
    # Compute loss against target images
    loss = compute_loss(rendered_images, D_local.target_images)
    
    # 4. Backward Pass
    # Compute local gradients
    local_grads = compute_gradients(loss, G_shards[rank])
    
    # 5. Synchronization
    # Aggregate gradients using fused all-reduce
    global_grads = fused_all_reduce(local_grads, num_gpus)
    
    # 6. Update
    # Update local optimizer states and Gaussian parameters
    G_shards[rank], optimizer_states[rank] = optimizer_step(
        G_shards[rank], 
        optimizer_states[rank], 
        global_grads
    )
    
    return loss
```

**Parameters:**
*   **Number of synthetic camera views ($V$):** Increased from 250 (prior work [4]) to 448 to better support data complexity [S1].
*   **Image Resolution ($R$):** Benchmarked at 512x512, 1024x1024, and 2048x2048 [S1].
*   **Number of GPUs ($M$):** Typically 4 in reported experiments [S1].

**Edge Cases and Pitfalls:**
*   **Memory Limits:** A single NVIDIA A100 GPU supports up to approximately 11.2M Gaussians [S1]. Datasets larger than this (e.g., Miranda with ~18M Gaussians) are infeasible on a single GPU and require multi-GPU training [S1].
*   **Communication Overhead:** Sparse all-to-all communication must be optimized to avoid bottlenecks when Gaussians cover many tiles .

## Operating characteristics
*   **Time Complexity:** Training time decreases significantly with more GPUs. For the Kingsnake dataset (4M Gaussians) at 2048x2048 resolution, training time drops from 48.00 minutes (1 GPU) to 8.50 minutes (4 GPUs), a 5.6x speedup [S1].
*   **Memory Complexity:** Scales linearly with the number of GPUs, allowing datasets exceeding single-GPU memory (e.g., 18M Gaussians on 4 A100s) [S1].
*   **Performance:** On a Polaris HPC node with four NVIDIA A100 GPUs [S1]:
    *   Kingsnake (4M Gaussians, 2048x2048, 4 GPUs): PSNR 29.32, SSIM 0.97, LPIPS 0.03 [S1].
    *   Miranda (18M Gaussians, 2048x2048, 4 GPUs): PSNR 36.37, SSIM 0.99, LPIPS 0.011 [S1].
*   **Strengths:** Enables high-fidelity reconstruction of large-scale scientific data that exceeds single-GPU capacity; improves training throughput [S1].
*   **Limitations:** Requires distributed infrastructure; communication overhead may limit scaling efficiency for smaller datasets [S1].
*   **When to Use:** For scientific visualization datasets with >11.2M Gaussians or when high-resolution (2048x2048) training on large scenes is required [S1].
*   **When Not to Use:** For small datasets fitting within single-GPU memory, where the overhead of distributed communication may not be justified [S1].

## Background
*   **Origin:** Developed by researchers from the University of Illinois Chicago, Argonne National Laboratory, and Utah State University [S1].
*   **History:** Presented in 2025 at the IEEE International Conference on e-Science [S1]. It builds on prior work by Sewell et al. [4] for isosurface reconstruction and adapts the distributed training design from Grendel-GS [6] [S1].
*   **Usage:** Designed for HPC-based scientific workflows, enabling real-time post hoc and in situ visualization of complex simulations [S1].
