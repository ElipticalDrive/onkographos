# BlitzGS

Also called: BlitzGS: City-Scale Gaussian Splatting at Lightning Speed

## Overview
BlitzGS is a distributed 3D Gaussian Splatting (3DGS) framework designed to accelerate city-scale reconstruction by reducing the active Gaussian workload at system, model, and view levels [S1, unofficial]. Unlike spatial block partitioning which suffers from cross-block visibility waste and imbalance, BlitzGS shards Gaussians by index parity and applies importance-based pruning and distance-based LOD filtering to maintain high quality while training nearly an order of magnitude faster [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A set of calibrated images, initial 3D Gaussian primitives (mean $\mu$, covariance $\Sigma$, opacity $\alpha$, color/radiance), and $M$ GPUs.
*   **Output:** Optimized 3D Gaussian scene representation and rendered novel views.

**Data Structures:**
*   **Global Gaussian Set $\mathcal{G}$:** Partitioned into $M$ shards $\mathcal{G}^{(m)}$ for $m \in \{0, \dots, M-1\}$.
*   **Tile Ownership:** The image plane is divided into tiles. Each tile is assigned to a specific GPU owner.
*   **Importance Score:** A scalar value per Gaussian per camera view, derived from the importance-scoring pass.

**Numbered Steps:**

1.  **System-Level Sharding:**
    *   Partition the global Gaussian index set into $M$ shards based on index parity (even/odd indices) or a similar deterministic hash to ensure balanced distribution [S1, unofficial].
    *   Each GPU $m$ stores its shard $\mathcal{G}^{(m)}$ and corresponding optimizer states [S1, unofficial].
    *   Assign tile ownership such that each tile is owned by exactly one GPU [S1, unofficial].

2.  **Model-Level Population Control:**
    *   **Importance Scoring:** Perform a lightweight pass to compute an importance score for each Gaussian relative to each camera view [S1, unofficial].
    *   **Pruning:** Use the importance scores to prune redundant Gaussians that contribute negligibly to the loss [S1, unofficial].
    *   **Spawn Gating:** Before spawning new Gaussians during densification, predict their survival probability. Withhold candidates predicted not to survive to limit peak population [S1, unofficial].
    *   **Gradient Reweighting:** Use the importance signal to reweight density control gradients during optimization [S1, unofficial].

3.  **View-Level Filtering:**
    *   **Distance-Based LOD:** For each camera, apply a Level-of-Detail (LOD) gate to drop Gaussians that are too fine (small scale) for the current camera distance [S1, unofficial].
    *   **Importance Mask:** Apply an importance-based mask to skip Gaussians with negligible cross-view contribution, further trimming the active set for each camera [S1, unofficial].

4.  **Distributed Rendering:**
    *   Each GPU $m$ projects its local shard $\mathcal{G}^{(m)}$ to screen space [S1, unofficial].
    *   Perform a single cross-GPU all-to-all exchange to route projected Gaussians to the GPUs owning the tiles they cover [S1, unofficial].
    *   Each GPU composites the pixels for its owned tiles using the received Gaussians [S1, unofficial].

**Pseudocode:**

```python
def blitzgs_train(cameras, initial_gaussians, num_gpus, num_iterations):
    # 1. System-Level Sharding
    # Shard Gaussians by index parity
    shards = {}
    for m in range(num_gpus):
        shards[m] = [g for i, g in enumerate(initial_gaussians) if i % num_gpus == m]
    
    # Assign tile owners (simplified assumption: round-robin or fixed mapping)
    tile_owners = assign_tile_owners(num_gpus)

    for iteration in range(num_iterations):
        # 2. Model-Level Population Control
        # Compute importance scores for all Gaussians across all cameras
        importance_scores = compute_importance_scores(shards, cameras)
        
        # Prune redundant Gaussians based on importance
        active_shards = {}
        for m in range(num_gpus):
            active_shards[m] = [g for g in shards[m] if importance_scores[m][g] > threshold]
        
        # Spawn gating: predict survival before spawning new Gaussians
        # (Implementation detail: integrate with densification step)
        new_candidates = predict_and_filter_candidates(active_shards, cameras)
        
        # Gradient reweighting
        gradients = compute_gradients(active_shards, cameras, importance_scores)
        gradients = reweight_gradients(gradients, importance_scores)
        
        # Update Gaussians
        for m in range(num_gpus):
            update_gaussians(active_shards[m], gradients[m])
        
        # 3. View-Level Filtering & 4. Distributed Rendering
        # Prepare for rendering
        projected_gaussians = {}
        for m in range(num_gpus):
            # Project local Gaussians
            projected_gaussians[m] = project_gaussians(active_shards[m], cameras)
            
            # Apply Distance-Based LOD
            projected_gaussians[m] = apply_lod_filter(projected_gaussians[m], cameras)
            
            # Apply Importance Mask
            projected_gaussians[m] = apply_importance_mask(projected_gaussians[m], importance_scores)

        # Cross-GPU Exchange: Route to tile owners
        # Each GPU sends its projected Gaussians to the GPUs owning the tiles they cover
        received_gaussians = all_to_all_exchange(projected_gaussians, tile_owners)
        
        # Composite pixels
        for m in range(num_gpus):
            render_tiles(received_gaussians[m], tile_owners[m])
```

**Parameters:**
*   **Hardware:** 4x NVIDIA A6000 GPUs [S1, unofficial].
*   **Thresholds:** Importance and LOD thresholds are not explicitly defined in the sources [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Imbalanced Shards:** Index parity sharding is chosen specifically to avoid the imbalanced shards common in spatial block partitioning [S1, unofficial].
*   **Cross-Block Visibility:** By sharding by index rather than space, cross-block visibility waste is avoided [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Training time is significantly reduced compared to baselines. On the Residence scene, BlitzGS trains in 38 minutes, compared to 5 hours 3 minutes for Momen.GS and 4 hours 45 minutes for CityGS-X [S1, unofficial].
*   **Memory Complexity:** By pruning redundant Gaussians and gating spawns, the peak population and memory footprint are reduced [S1, unofficial].
*   **Performance:** Achieves scene-average PSNR of 24.66 dB on Residence and 33.79 dB on Rubble [S1, unofficial].
*   **Strengths:** Near order-of-magnitude speedup over baselines while maintaining high quality [S1, unofficial].
*   **Limitations:** Requires distributed infrastructure (multiple GPUs) and careful tuning of importance thresholds [S1, unofficial].

## Background
BlitzGS was introduced by Zhongtao Wang, Huishan Au, Yisong Chen, Meng Gai, Yilong Li, Fei Zhu, Mai Su, Haojie Jin, and Guoping Wang in the paper "BlitzGS: City-Scale Gaussian Splatting at Lightning Speed" [S1, unofficial]. It addresses the high computational cost of city-scale 3DGS training by unifying sharding, importance-based simplification, and LOD filtering [S1, unofficial].
