# Physically-based Gaussian Rendering

Also called: 3DGS PBR Framework, PBR Color Computation

## Overview
This method assigns Physically-Based Rendering (PBR) attributes to Gaussian points and evaluates the rendering equation to produce per-Gaussian PBR colors, replacing view-dependent spherical harmonics with a physical BRDF [S1]. It differs from vanilla 3DGS, which uses $k$-order spherical harmonics for view-dependent effects that lack physical interpretability, by providing physically grounded material representation [S1].

## How it works
**Inputs and Outputs:**
*   **Inputs:** 3D Gaussian points (position $\mu_i$, scale $S_i$, rotation $R_i$), multi-resolution hash grids for material querying, and lighting environment (direct and indirect).
*   **Outputs:** Final rendered images via alpha compositing.

**Data Structures:**
*   **Multi-resolution Hash Grids:** Two distinct grids are used for material querying [S1]:
    *   $\mathcal{E}_d$: Stores diffuse albedo.
    *   $\mathcal{E}_s$: Stores specular properties (roughness and metalness).
    *   *Note:* The specific bit-packing or hash function details are not provided in the sources [S1].

**Numbered Steps:**
1.  **Query PBR Attributes:** For each Gaussian point $i$ with position $\mu_i$, query the hash grids to retrieve material properties [S1]:
    $$ \alpha_i = \mathcal{E}_d(\mu_i) $$
    $$ (\rho_i, m_i) = \mathcal{E}_s(\mu_i) $$
    where $\alpha_i$ is albedo, $\rho_i$ is roughness, and $m_i$ is metalness [S1].

2.  **Evaluate Rendering Equation:** Solve the rendering equation differentiably using Monte Carlo sampling to obtain the outgoing radiance (PBR color) for each Gaussian point [S1]. The outgoing radiance $L_o(x, \omega_o)$ is computed as [S1]:
    $$ L_o(x, \omega_o) = \int_{\mathcal{H}} f_r(x, \omega_i, \omega_o) L_i(x, \omega_i) |\mathbf{n} \cdot \omega_i| d\omega_i $$
    where:
    *   $L_o(x, \omega_o)$ is the outgoing radiance in direction $\omega_o$.
    *   $f_r(x, \omega_i, \omega_o)$ is the BRDF.
    *   $L_i(x, \omega_i)$ is the incoming light.
    *   $\mathbf{n}$ is the surface normal.
    *   $\omega_i$ is the incoming light direction.
    *   $\mathcal{H}$ is the hemisphere.

3.  **Compute BRDF:** The BRDF is modeled using the GGX microfacet model [S1]:
    $$ f_r(x, \omega_i, \omega_o) = (1 - m) \frac{a}{\pi} + \frac{DFG}{4|\mathbf{n} \cdot \omega_i||\mathbf{n} \cdot \omega_o|} $$
    where:
    *   $m$ is metalness.
    *   $a$ is albedo.
    *   $DFG$ is the combined Diffuse and Fresnel-GGX term determined by PBR attributes (albedo $a$, metalness $m$, roughness $\rho$) [S1].

4.  **Rasterize and Composite:** Process the shaded Gaussian points using standard 3DGS rasterization and render final images via alpha compositing [S1].

5.  **Optimize:** Apply backpropagation to progressively optimize the PBR attributes through photometric supervision [S1].

    Computes the PBR color for a single Gaussian point.

        color: RGB vector representing outgoing radiance.
    """

    albedo = hash_grid_diffuse.query(gaussian_point.mu)
    roughness, metalness = hash_grid_specular.query(gaussian_point.mu)
    
    # Step 2 & 3: Evaluate Rendering Equation via Monte Carlo Sampling

    #   1. Query incoming light Li(x, omega_i) from lighting (direct + indirect)
    #   2. Compute BRDF fr using GGX model with albedo, metalness, roughness, n, omega_i, omega_o

    return radiance

**Parameters and Typical Values:**
*   **Albedo ($a$):** Query result from $\mathcal{E}_d$. Range typically [0, 1].
*   **Roughness ($\rho$):** Query result from $\mathcal{E}_s$. Range typically [0, 1].

**Edge Cases and Pitfalls:**
*   **Division by Zero:** The denominator in the specular term $4|\mathbf{n} \cdot \omega_i||\mathbf{n} \cdot \omega_o|$ can approach zero if the normal is perpendicular to the light or view direction. Guard against this [G].
*   **Lighting Occlusion:** Accurately modeling the occlusion term $O(x, \omega_i)$ for indirect illumination is challenging. The source mentions using a BVH-accelerated ray tracing on an extracted mesh to evaluate light transport, but the specific integration with the Gaussian points is not detailed beyond "differentiably solve" [S1].
*   **Geometry Boundaries:** Vanilla 3D Gaussians inherently lack deterministic geometry boundaries. This method relies on a mesh extracted via FlexiCubes to guide Gaussian point generation, which may introduce artifacts if the mesh extraction is inaccurate [S1].

## Operating characteristics
*   **Time Complexity:** Not given in the sources. Depends on the number of Gaussian points, Monte Carlo samples, and hash grid query complexity.
*   **Memory Complexity:** Not given in the sources. Depends on the size of the multi-resolution hash grids and the number of Gaussian points.
*   **Measured Performance:** Not given in the sources.
*   **Strengths:** Provides physical interpretability of materials compared to vanilla 3DGS [S1].
*   **Limitations:** Requires additional geometry extraction (FlexiCubes) and BVH-accelerated ray tracing for light transport, which may increase computational overhead compared to pure rasterization methods [S1].
*   **When to Use:** When physically accurate material representation and inverse rendering are required.
*   **When Not to Use:** When real-time performance is critical and physical accuracy is not required (vanilla 3DGS is preferable).

## Background
*   **Origin:** Introduced in "GeoSplatting: Towards Geometry Guided Gaussian Splatting for Physically-Based Inverse Rendering" [S1].
*   **History:** Builds upon 3D Gaussian Splatting [22] and integrates PBR concepts via GGX microfacet model [46] and rendering equation [19]. It addresses the lack of physical interpretability in vanilla 3DGS spherical harmonics [S1].
*   **Usage:** Used in physically-based inverse rendering tasks where material properties need to be recovered from images [S1].
