# Grendel

Also called: distributed 3DGS training system

## Overview
Grendel is a distributed training system for 3D Gaussian Splatting (3DGS) that partitions parameters and parallelizes computation across multiple GPUs to overcome single-GPU memory constraints in high-resolution and large-scale reconstruction [S1]. It distinguishes itself from single-GPU baselines and divide-and-conquer approaches like CityGS by supporting batched training with multiple views and employing mixed parallelism (Gaussian-wise and pixel-wise) with dynamic load balancing to handle unbalanced workloads [S1].

## How it works
**Inputs and Outputs:**
*   **Inputs:** A set of $N$ 3D Gaussians (defined by mean $\mu$, covariance $\Sigma$, opacity $\alpha$, and color/radiance parameters), a batch of $B$ training images (camera poses and intrinsics), and the number of GPUs $G$.
*   **Outputs:** Optimized 3D Gaussian parameters and reconstructed scene.

**Data Structures:**
*   **Gaussian Parameters:** Stored in contiguous memory. Each Gaussian includes $\mu$ (3 floats), $\Sigma$ (derived from scale $s$ and rotation $q$), $\alpha$ (1 float), and color coefficients. Optimizer states (Adam moments) are stored alongside parameters.
*   **Pixel Blocks:** Images are partitioned into $16 \times 16$ pixel blocks [S1].
*   **Communication Buffers:** Sparse buffers for transferring intersecting Gaussians between GPUs.

**Algorithm Steps:**

1.  **Initialization:**
    *   Distribute the initial set of 3D Gaussians uniformly across $G$ GPUs. Each GPU stores a disjoint subset of Gaussians, including their parameters and optimizer states [S1].
    *   Initialize the estimated runtime per pixel block $ET$ to zero or a small constant [S1].

2.  **Forward Pass (Per Training Step):**
    *   **Gaussian-wise Distribution (Transformation):**
        *   Each GPU $g$ independently computes the Gaussian transformation (projection to screen space) for its assigned subset of Gaussians [S1].
        *   This step exhibits Gaussian-wise parallelism; computation load is roughly uniform per Gaussian [S1].
    *   **Sparse All-to-All Communication (Forward):**
        *   Each GPU determines which of its transformed Gaussians intersect with the pixels in its assigned pixel partition [S1].
        *   GPUs perform sparse all-to-all communication to transfer these intersecting Gaussians to the GPUs responsible for rendering those pixels. This minimizes communication by exploiting spatial locality (only relevant Gaussians are moved) [S1].
    *   **Pixel-wise Distribution (Rendering & Loss):**
        *   Each GPU renders its assigned pixel blocks using the received Gaussians.
        *   Compute the loss for the rendered pixels against the ground truth images [S1].
        *   *Note:* In batched training, a GPU may be assigned blocks from different images in the batch [S1].

3.  **Backward Pass:**
    *   Perform gradient computation for the assigned pixels.
    *   **Sparse All-to-All Communication (Backward):**
        *   A reversed all-to-all communication is performed to aggregate gradients for the Gaussians that contributed to the rendered pixels [S1].
    *   Update the local Gaussian parameters and optimizer states using the aggregated gradients [S1].

4.  **Dynamic Load Balancing (Pixel-wise):**
    *   After the first few epochs, record the rendering time (including loss and backward computation) for each $16 \times 16$ pixel block assigned to each GPU [S1].
    *   Compute the average per-pixel computation time for each GPU based on its assigned blocks. Assume this average applies to any pixel assigned to that GPU [S1].
    *   Re-split the images into subsequences of $16 \times 16$ blocks for the next iteration such that the sum of estimated computation times for pixels assigned to all GPUs is equal [S1].
    *   Use **Algorithm 1** to calculate division points.

5.  **Gaussian-wise Rebalancing:**
    *   After every few densification steps (cloning and splitting), redistribute the 3D Gaussians uniformly across all GPUs to restore balance, as new Gaussians are added at varying rates depending on local scene detail [S1].

6.  **Hyperparameter Scaling:**
    *   Scale the learning rate $\lambda$ and Adam momentum parameters $\beta_1, \beta_2$ based on the batch size $b$ using the rules below [S1].

**Pseudocode:**

```python
import torch

def calculate_division_points(estimated_runtimes: torch.Tensor, num_gpus: int) -> torch.Tensor:
    """
    Algorithm 1: Calculation of Division Points for Pixel-wise Rebalancing.
    
    Args:
        estimated_runtimes: Tensor of shape (B,) containing estimated runtime per pixel block.
        num_gpus: Number of GPUs G.
        
    Returns:
        division_points: Tensor of shape (G-1,) containing indices where image blocks are split.
    """
    # 1. Cumulative sum of estimated runtimes
    cumulative_time = torch.cumsum(estimated_runtimes, dim=0)
    
    # 2. Total time divided by number of GPUs to get target time per GPU
    total_time = cumulative_time[-1]
    target_time_per_gpu = total_time / num_gpus
    
    # 3. Create thresholds for division points
    # Thresholds are multiples of target_time_per_gpu: [0, T, 2T, ..., (G-1)T]
    thresholds = torch.arange(0, num_gpus) * target_time_per_gpu
    
    # 4. Find indices in cumulative_time where thresholds would be inserted
    # searchsorted returns indices such that cumulative_time[i-1] < threshold <= cumulative_time[i]
    division_points = torch.searchsorted(cumulative_time, thresholds)
    
    return division_points
```

**Formulas:**

*   **Learning Rate Scaling:**
    $$ \lambda' = \lambda \times \sqrt{\text{batch\_size}} $$
    Where $\lambda$ is the original learning rate and $\lambda'$ is the adjusted learning rate [S1].

*   **Momentum Scaling (Adam):**
    $$ \beta_1' = \beta_1^{\text{batch\_size}}, \quad \beta_2' = \beta_2^{\text{batch\_size}} $$
    Where $\beta_1, \beta_2$ are the original first and second moment estimates, and $\beta_1', \beta_2'$ are the adjusted parameters [S1].

**Parameters:**
*   **Block Size:** $16 \times 16$ pixels. This is the granularity for splitting images and rebalancing [S1].
*   **Maximum Tested Batch Size:** 32 [S1].
*   **Learning Rate Scaling Rule:** $\sqrt{\text{batch\_size}}$ [S1].

**Edge Cases and Pitfalls:**
*   **Gradient Correlation:** Increasing batch size without adjusting hyperparameters leads to unstable training. The "Independent Gradients Hypothesis" assumes gradients from different views are independent, but cameras with similar poses produce correlated gradients, causing sparsity changes [S1].
*   **Workload Imbalance:** Static partitioning fails due to varying Gaussian densities and scene complexity (e.g., sky vs. detailed foreground). Dynamic rebalancing is required [S1].
*   **Densification Imbalance:** New Gaussians added via cloning/splitting are not uniformly distributed, requiring periodic redistribution [S1].

## Operating characteristics
*   **Time Complexity:** Training time scales sub-linearly with the number of GPUs due to communication overhead, but significantly faster than single-GPU training. On 4 A100s, Grendel achieves 2.5x speedup over 1 GPU for rendering (e.g., 21.7 img/s vs 8.8 img/s on Rubble) [S1].
*   **Memory Complexity:** Memory usage per GPU is reduced by distributing Gaussians, allowing for larger scenes (e.g., 40.4 million Gaussians on 16 GPUs vs 11.2 million on 1 GPU) [S1].
*   **Performance:**
    *   **Rubble (3436x4591):** 21.7 img/s on 4 GPUs vs 8.8 img/s on 1 GPU. Training time on 4 A100s: 51 minutes vs CityGS 2h 3m [S1].
    *   **Matrixcity Block-all (1080x1920):** 76.8 img/s on 4 GPUs vs 29.2 img/s on 1 GPU. Training time on 4 A100s: 54 minutes vs CityGS 3h 31m [S1].
    *   **Bicycle (1275x1920):** 80.3 img/s on 4 GPUs vs 42.6 img/s on 1 GPU. Training time on 4 A100s: 1h 13m vs CityGS 1h 20m [S1].
*   **Strengths:** Handles high-resolution/large-scale scenes; supports batched training for better GPU utilization; dynamic load balancing handles unbalanced workloads; no need for coarse-to-fine divide-and-conquer merging [S1].
*   **Limitations:** Communication overhead from sparse all-to-all; requires dynamic rebalancing logic; hyperparameter tuning still needed for very large batches (though simplified by scaling rules) [S1].

## Background
Grendel was introduced in the paper "On Scaling Up 3D Gaussian Splatting Training" (ICLR 2025) to address the memory limitations of single-GPU 3DGS training [S1]. It builds on the principles of 3D Gaussian Splatting and distributed training techniques, specifically adapting mixed parallelism and sparse communication strategies to the unique characteristics of Gaussian primitives [S1].
