# ASCII-Based Data Compression

Also called: Anywhere Compression, Base 94 Floating-Point Compression, Base 95 Integer Compression

## Overview
ASCII-Based Data Compression is a method for optimizing data transmission speed during the training of 3D Gaussian Splatting models by encoding numerical attributes into compact ASCII strings [S1, unofficial]. It differs from sibling methods like [Sensitivity-Aware Vector Clustering](12167-sensitivity-aware-vector-clustering.md) and [Compact 3D Gaussian Representation (C3DGS)](12927-compact-3d-gaussian-representation-c3dgs.md) by avoiding codebook lookups or neural field substitutions; instead, it relies on direct base-94/base-95 integer encoding of floating-point values to reduce payload size and improve I/O throughput [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Continuous numerical attributes from the 3D Gaussian model (e.g., position, scale, rotation, SH coefficients, color) represented as floating-point numbers or integers.
*   **Output:** A compressed ASCII string representation suitable for transmission or storage, and the corresponding decoding logic to reconstruct the original values.

**Data Structures:**
The method does not define a complex binary structure but operates on character arrays (strings).
*   **Integer Encoding:** Maps values in $[0, 95]$ to a single ASCII character.
*   **Floating-Point Encoding:** Maps the integer component to a single ASCII character (range $[0, 94]$) and uses a delimiter character to separate the integer and fractional parts.

**Steps:**

1.  **Integer Compression:**
    For an integer value $v$ where $0 \le v \le 95$:
    *   Map $v$ to an ASCII character $c$ using the range of ASCII codes 32 to 126.
    *   The mapping is typically a direct offset: $c = \text{chr}(32 + v)$.
    *   Result: A single character string representing the integer.

2.  **Floating-Point Compression:**
    For a floating-point value $f$, decompose it into an integer part $I$ and a decimal place count $d$.
    *   The integer part $I$ must be in the range $[0, 94]$. Map $I$ to an ASCII character $c_I$ using ASCII codes 32 to 125: $c_I = \text{chr}(32 + I)$.
    *   The delimiter is the ASCII character 126 (`~`).
    *   The decimal part is represented by the count $d$ (number of decimal places). Note: The source describes splitting into "integer part $I$" and "decimal places $d$", and calculating $f = I \times 10^{-d}$. This implies $d$ is an integer representing the exponent magnitude, not the fractional digits themselves.
    *   The encoded string is $c_I + \text{chr}(126) + \text{representation of } d$. *Note: The source text is slightly ambiguous on how $d$ is encoded if $d > 94$, but implies a similar base-94 or simple integer encoding for the exponent part, or that $d$ is small enough to fit in the remaining character space. However, the formula $f = I \times 10^{-d}$ suggests $d$ is the precision exponent.*

3.  **Color Matrix Optimization:**
    *   The color matrix values are constrained to the range $[0.0, 2.0]$ with only one decimal place.
    *   This results in 21 possible values: $0.0, 0.1, ..., 2.0$.
    *   These values can be mapped to integers $0..20$ and then encoded using the Base 95 integer compression (since $20 < 95$).
    *   This significantly reduces the data size for color attributes.

4.  **Decoding Integer:**
    *   Given an ASCII character $c$, retrieve the integer $v = \text{ord}(c) - 32$.

5.  **Decoding Floating-Point:**
    *   Split the string at the delimiter `~` (ASCII 126).
    *   Let the left part be $S_I$ and the right part be $S_d$.
    *   Decode $I = \text{ord}(S_I) - 32$.
    *   Decode $d$ from $S_d$. If $S_d$ is a single character, $d = \text{ord}(S_d) - 32$ (assuming similar mapping). If multi-character, apply appropriate base-94 decoding.
    *   Calculate $f = I \times 10^{-d}$.

**Parameters:**
*   **Integer Base:** 95 (ASCII 32-126).
*   **Floating-Point Integer Base:** 94 (ASCII 32-125).
*   **Delimiter:** ASCII 126 (`~`).
*   **Color Precision:** 1 decimal place, range $[0.0, 2.0]$.

**Edge Cases and Pitfalls:**
*   **Matrix Traversal Speed:** Compressing large color matrices via ASCII string conversion is slow due to traversal overhead. Using PyTorch internal functions like `torch.where` and `torch.index_select` improves speed but may not be sufficient for full replacement [S1, unofficial].
*   **Line Breaks:** Avoid using line break characters in the ASCII strings as they add processing overhead during writing and decoding [S1, unofficial].
*   **Range Constraints:** The integer component of the floating-point number must be $\le 94$. Values outside this range require handling (not specified in source, likely clipping or multi-character encoding) [S1, unofficial].
*   **Color Range:** The method assumes color values are within $[0.0, 2.0]$. Values outside this range may need scaling or clipping [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Encoding/decoding is $O(1)$ per number, but matrix traversal for color compression is $O(N)$ where $N$ is the number of color entries. The source notes that even with optimized PyTorch functions, matrix traversal is a bottleneck [S1, unofficial].
*   **Memory Complexity:** Reduces the size of transmitted data. Integer compression reduces 4-8 bytes to 1 byte. Floating-point compression reduces 4-8 bytes to 2+ bytes (depending on $d$). Color matrix compression reduces 3-4 bytes per channel to 1 byte per value (due to 21 quantized levels) [S1, unofficial].
*   **Measured Performance:** Gains approximately 6% or less improvement in training speed [S1, unofficial].
*   **Strengths:** Simple implementation, low overhead for individual numbers, effective for color matrices with limited dynamic range.
*   **Limitations:** Not suitable for arbitrary large integers or floats without multi-character encoding (which increases complexity). Color matrix compression is slow due to traversal. Limited to specific value ranges [S1, unofficial].
*   **When to Use:** When training speed is bottlenecked by data transmission and attributes fit within the specified ranges.
*   **When Not to Use:** When high precision is required for all attributes, or when color values exceed $[0.0, 2.0]$.

## Background
The method was introduced in "I3DGS: Improve 3D Gaussian Splatting from Multiple Dimensions" by F. Author et al. (2024) [S1, unofficial]. It is part of a broader effort to optimize 3D Gaussian Splatting training by improving data transmission speed through compression. The authors found that while compression helps, the overhead of matrix traversal limits its effectiveness for color attributes.
