# MonoGS


## Overview
MonoGS is a monocular RGB-only SLAM method that performs online optimization by representing the scene as 3D Gaussian Splatting (3DGS) primitives [S2, unofficial]. It restricts the joint estimation of camera poses and Gaussian map parameters to a selected set of keyframes [S1]. Unlike RGB-D SLAM methods that use depth sensors, MonoGS estimates pose and geometry from a single camera stream [S2, unofficial].

## How it works
**Inputs and Outputs:**
- **Input:** A stream of monocular RGB images.
- **Output:** Camera poses ($T_k$) for keyframes and a set of 3D Gaussians ($G$) representing the scene.

**Data Structures:**
- **Keyframe Set ($W$):** A union of a covisible local window ($W_k$) and sampled past keyframes ($W_r$) [S1].
- **Gaussians ($G$):** Standard 3DGS representation (position, covariance, opacity, spherical harmonics) optimized over the keyframe set [S1].
- **Poses ($T_k$):** SE(3) transformation matrices for each keyframe in $W$ [S1].

**Algorithm Steps:**
1. **Keyframe Selection:** Maintain a local window of covisible keyframes ($W_k$) and sample a subset of past keyframes ($W_r$) to form the optimization set $W = W_k \cup W_r$ [S1].
2. **Objective Formulation:** Define a joint optimization objective combining photometric, geometric, and isotropy errors [S1].
3. **Joint Optimization:** Minimize the objective with respect to camera poses $T_k$ and Gaussian parameters $G$ [S1].
4. **Online Update:** Incrementally add new keyframes and optimize the map in a streaming fashion [S1].

**Formulas:**
The joint optimization minimizes the following loss function [S1]:

$$
\min_{T_k} \sum_{k \in W} (\lambda_{\text{pho}} E^k_{\text{pho}} + \lambda_{\text{geo}} E^k_{\text{geo}} + \lambda_{\text{iso}} E_{\text{iso}})
$$

Where:
- $W = W_k \cup W_r$ is the set of keyframes.
- $T_k$ are the camera poses for keyframes in $W$.
- $E^k_{\text{pho}}$ is the photometric error for keyframe $k$ [S1].
- $E^k_{\text{geo}}$ is the geometric error for keyframe $k$ [S1].
- $E_{\text{iso}}$ is the isotropy error, encouraging spherical covariance shapes [S1].
- $\lambda_{\text{pho}}, \lambda_{\text{geo}}, \lambda_{\text{iso}}$ are weighting coefficients [S1].

**Pseudocode:**
```python
def monogs_online(rgb_stream):
    gaussians = []  # 3DGS primitives (position, covariance, opacity, SH)
    keyframes = []  # List of keyframe images
    W_k = []        # Covisible local window
    W_r = []        # Sampled past keyframes
    lambda_pho = 1.0
    lambda_geo = 1.0
    lambda_iso = 1.0

    for rgb in rgb_stream:
        # 1. Keyframe selection: maintain W = W_k ∪ W_r
        # [G] Standard covisibility check adds frame to W_k if feature overlap drops
        if len(W_k) > 0 and not feature_overlap(rgb, W_k[-1]):
            keyframes.append(rgb)
            W_k = keyframes[-10:]  # [G] Fixed-size sliding window
            W_r = keyframes[:-10]  # [G] Sampled past keyframes
        W = W_k + W_r

        # 2. Compute joint objective over poses T_k and Gaussians G
        total_loss = 0.0
        for k in W:
            T_k = k.pose
            # Photometric error E^k_pho
            rendered_rgb = project_gaussians(gaussians, T_k)
            E_pho = sum(abs(rendered_rgb - k.rgb)) / len(rendered_rgb)
            # Geometric error E^k_geo
            E_geo = geometric_consistency(rendered_rgb, k.rgb)
            # Isotropy error E_iso
            E_iso = isotropy_penalty(gaussians)
            total_loss += lambda_pho * E_pho + lambda_geo * E_geo + lambda_iso * E_iso

        # 3. Minimize objective
        # [Comment] Sources do not specify the exact optimizer or densification schedule.
        # Standard practice uses gradient descent to update T_k and G parameters.
        T_opt, G_opt = gradient_descent_step(T_k, gaussians, total_loss)

        # 4. Update state
        gaussians = G_opt
        for k in W:
            k.pose = T_opt[k]

    return gaussians, keyframes
```

**Parameters:**
- $\lambda_{\text{pho}}, \lambda_{\text{geo}}, \lambda_{\text{iso}}$: Loss weights. Typical values are not explicitly given in the sources [S1].
- $W_k, W_r$: Window sizes and sampling rates are not explicitly given [S1].

**Edge Cases and Pitfalls:**
- Monocular ambiguity: Scale drift is a common issue in monocular SLAM, though the sources do not specify MonoGS's specific scale-fixing mechanism [S1].

## Operating characteristics
**Time and Memory Complexity:**
- The method is designed for online streaming, with the streaming time dominated by motion tracking, refinement, and structure updates rather than rendering ($t_{\text{stream}} \approx t_{\text{motion}} + t_{\text{refine}} + t_{\text{structure}} \gg t_{\text{render}}$) [S1].
- Measured performance on Replica office0 (12 frames): Wrapped time is 2250.57 ms/frame (0.444 frames/s), trajectory error is 0.000082 m, and model size is 2.14 MiB [S1].

**Strengths and Limitations:**
- **Strengths:** Monocular input reduces hardware requirements; online optimization allows for real-time mapping [S2, unofficial].
- **Limitations:** Lower throughput compared to rendering-only methods; potential for scale drift in monocular settings [S1].

**When to Use:**
- Use when only a monocular camera is available and real-time mapping is required [S2, unofficial].
- Avoid when high-frequency updates or RGB-D input are available, as other methods may offer better stability or accuracy [S2, unofficial].

## Background
MonoGS was introduced as a monocular RGB-only SLAM method using online optimization with Gaussian Splatting [S2, unofficial]. It builds on the 3DGS representation to enable real-time scene reconstruction and tracking from a single camera [S1]. It is part of a family of Gaussian SLAM methods, including SplaTAM (RGB-D), Photo-SLAM, and Gaussian-SLAM [S2, unofficial].
