# 3DGS Radiance Caching

Also called: GSCache Radiance Caching, Radiance caching with 3DGS

## Overview
3DGS Radiance Caching is a real-time variance reduction technique for volume path tracing that uses 3D Gaussian Splatting (3DGS) primitives to store and query cached radiance values [S1, unofficial]. It reduces noise by probabilistically accepting cached samples based on throughput luminance and a scaling parameter [S1, unofficial]. The method optimizes exponentially subsampled Gaussians from noisy path samples to achieve real-time frame rates [S2, unofficial]. Unlike neural radiance caching, which requires large memory footprints, this method leverages the compact representation of 3DGS to store attenuated radiance at multiple path lengths, offering a significantly smaller memory footprint [S2, unofficial].

## How it works
The method integrates a caching mechanism into the path tracing loop, using 3DGS primitives to approximate the radiance field [S2, unofficial]. It operates by querying a cache of radiance samples, accepting or rejecting them based on a probability derived from the current path's throughput, and updating state variables to maintain expectations [S1, unofficial].

### Algorithm Steps
The caching logic is applied during the path tracing loop, typically after computing the contribution of a scattering event or at the end of a path segment [S1, unofficial]. The following pseudocode implements the query and state update logic [S1, unofficial].

```python
def query_radiance_cache(u, v, scatter_index, L, throughput, rand01, sample_factor_c, cache_levels, betas, width):
    # 1. Compute luminance of incoming throughput vector L
    luminance = 0.212671 * L.x + 0.715160 * L.y + 0.072169 * L.z

    # 2. Calculate acceptance probability q
    q = max(0.0, min(1.0, sample_factor_c * luminance))

    # 3. Calculate rejection probability p
    p = 1.0 - q

    result = {"cache_hit": False, "L": L, "throughput": throughput}

    # 4. Conditional caching logic
    if q < 0.9:
        idx = v * width + u
        cached_L = cache_levels[scatter_index][idx]
        beta = betas[idx]

        # 5. Probabilistic acceptance
        if rand01 < p:
            result["cache_hit"] = True
            result["L"] = cached_L / beta
            result["throughput"] = throughput
        else:
            # 6. Rejection: update beta and scale throughput
            betas[idx] = beta * q
            result["throughput"] = throughput / q
            result["L"] = L
    else:
        # 7. Skip caching for high luminance
        result["cache_hit"] = False
        result["L"] = L
        result["throughput"] = throughput

    return result
```

### Parameters
- `sample_factor_c`: A float parameter that scales the luminance to determine the acceptance probability $q$ [S1, unofficial]. Typical values are not explicitly given, but the threshold $q < 0.9$ implies it controls the aggressiveness of caching [S1, unofficial].
- `MAX_NUM_CACHE_LEVELS`: 16 [S1, unofficial].
- `n_levels`: Number of active cache levels, default 3 in the config [S1, unofficial].

### Edge Cases and Pitfalls
- **Division by Zero**: The code divides $L_{cached}$ by $\beta$ [S1, unofficial]. If $\beta$ is zero, this results in infinity [S1, unofficial]. The implementation relies on the update rule $\beta \cdot q$ and the condition $q < 0.9$ to keep $\beta$ non-zero if initialized correctly [S1, unofficial].
- **Bias**: The method introduces bias with no guaranteed error bounds [S2, unofficial].
- **High Throughput Rejection**: If $q$ is close to 1.0 (high luminance), $p$ is close to 0, making cache hits unlikely unless `rand01` is extremely small [S1, unofficial]. The threshold $q < 0.9$ prevents caching in these high-variance scenarios [S1, unofficial].
- **Transfer Function Changes**: The cache requires re-initialization when transfer functions change, as it stores attenuated radiance specific to the current transfer function [S2, unofficial].
- **Zero-Opacity Regions**: The caching mechanism may not reconstruct zero-opacity regions effectively if not handled by the underlying 3DGS representation [S2, unofficial].
- **Write-Back Mechanism**: The exact logic for writing to `cache_levels` or `radiance_samples` is not given in the sources [S1, unofficial].

## Operating characteristics
- **Performance**: Achieves real-time frame rates on scientific datasets at 720p, with total times ranging from 38ms to 186ms [S2, unofficial].
- **Memory Footprint**: 28 MB for the cache, compared to 272 MB for neural radiance caching [S2, unofficial].
- **Scalability**: The method is designed for real-time rendering, leveraging the efficiency of 3DGS rasterization [S2, unofficial]. It does not explicitly address scaling to very large scenes without additional techniques like distributed training, which is a separate extension [S2, unofficial].
- **Strengths**: Real-time performance, low memory footprint, variance reduction for path-traced volume rendering [S2, unofficial].
- **Limitations**: Introduces bias, requires re-initialization for transfer function changes, no guaranteed error bounds, potential issues with zero-opacity regions [S2, unofficial].

## Background
3DGS Radiance Caching, also known as GSCache, was introduced by David Bauer, Qi Wu, Hamid Gadirov, and Kwan-Liu Ma in the paper "GSCache: Real-Time Radiance Caching for Volume Path Tracing using 3D Gaussian Splatting," accepted at IEEE VIS 2025 [S1, unofficial]. The work builds on the principles of 3D Gaussian Splatting for volume rendering, adapting it to serve as a compact, differentiable radiance cache for path tracing [S1, unofficial]. It addresses the high variance and computational cost of path-traced volume rendering by leveraging the spatial coherence and compact representation of 3DGS primitives [S1, S2, unofficial].
