# XPR Rendering Pipeline

Also called: Extensible Cross-Platform Point-Based Differentiable Renderer, Extensible Cross-Platform Point-Based Differentiable Renderer pipeline, XPR Framework, XPR: An Extensible Cross-Platform Point-Based Differentiable Renderer

## Overview
XPR is a framework for point-based differentiable rendering that decouples method-specific logic from the shared rendering pipeline, allowing new rendering methods to be implemented in a few hundred lines of code [S1, unofficial]. It separates the core rasterization mechanics—parallelization, data layout, tiling, and differentiation—from the primitive evaluation logic, enabling portable execution across GPUs, TPUs, and CPUs via the XLA compiler [S1, unofficial]. Unlike traditional CUDA/Vulkan implementations that require thousands of lines and manual backward passes for each new primitive type, XPR exposes a four-function interface that captures only the method-specific math, while the framework handles the rest [S1, unofficial].

## How it works
XPR decomposes the rendering pipeline into modular, statically shaped parallel operations. The pipeline is driven by four user-defined functions that capture method-specific logic: `project`, `tile_cull`, `pixel_info`, and `evaluate` [S1, unofficial]. The framework handles primitive filtering, tile assignment, depth sorting, alpha-blending, and automatic differentiation via JAX/XLA [S1, unofficial].

### Inputs and Outputs
*   **Inputs:** A set of $M$ 3D primitives (e.g., Gaussians), camera parameters (intrinsics/extrinsics), and image dimensions ($W \times H$).
*   **Outputs:** A rendered image tensor of shape $(H, W, C)$ and gradients for the primitive parameters [S1, unofficial].

### Data Structures
*   **Primitives:** Defined by the parent article's Gaussian representation [G].
*   **Tile Map (`tile_prim_map`):** A mapping from tile coordinates to a list of candidate 2D primitives that intersect the tile [S1, unofficial].
*   **Static Bounds:** All tensor dimensions and loop trip counts are fixed at compile time. Dynamic sizes (e.g., number of visible primitives) are handled by padding unused entries and using fixed-trip-count loops with early exits [S1, unofficial].
*   **Trip-Count Bins:** Tiles are sorted by primitive count and partitioned into bins. Each bin is processed with a static trip count equal to its upper bound to optimize parallelization [S1, unofficial].

### Parameters
*   **$P_{max}$:** Maximum number of primitives per tile/pixel. Default is 4096 (XPR-4K). Lowering this increases frame rate but may skip contributions from distant or small primitives [S1, unofficial].
*   **Tile Size:** Standard rectangular tiles (e.g., $16 \times 16$ pixels) [S1, unofficial].

### Numbered Steps

1.  **Preprocess (Project):** Apply `project` to each of the $N$ primitives independently via `map_fn`. This transforms 3D primitives into 2D screen-space representations (e.g., 2D covariance matrices) [S1, unofficial].
2.  **Filter (Cull):**
    *   Perform a conservative bounding-box check (e.g., `intersect_8`) for each primitive against the image bounds [S1, unofficial].
    *   Assign visible primitives to tiles.
    *   For each primitive-tile pair, call `tile_cull` to refine the intersection test. If the primitive does not intersect the tile, discard it [S1, unofficial].
    *   Populate `tile_prim_map` with the surviving primitive-tile pairs [S1, unofficial].
3.  **Rasterizer (Shader):**
    *   Iterate over each tile $t$ in `tile_prim_map`.
    *   Sort tiles by primitive count and bin them to determine static loop bounds [S1, unofficial].
    *   For each pixel $(x, y)$ in tile $t$:
        *   Call `pixel_info(x, y, cam, view)` to generate pixel-specific data `px_data` (e.g., ray direction, view vector) [S1, unofficial].
        *   Initialize accumulated color $C = 0$ and transmittance $T = 1$ [S1, unofficial].
        *   Iterate over each candidate primitive $p_{2D}$ in `tile_prim_map[t]`.
        *   Retrieve shader data `p_sd` for the primitive [S1, unofficial].
        *   Call `evaluate(px_data, p_sd)` to compute opacity $\alpha$, validity `valid`, and color $c$ [S1, unofficial].
        *   Accumulate color: $C = C + c \cdot \alpha \cdot \text{valid} \cdot T$ [S1, unofficial].
        *   Update transmittance: $T = (1 - \alpha \cdot \text{valid}) \cdot T$ [S1, unofficial].
        *   Store $C$ in the output image at $(x, y)$ [S1, unofficial].

### Formulas
The alpha-blending accumulation for each pixel is:
$$ C = C + c \cdot \alpha \cdot \text{valid} \cdot T $$
$$ T = (1 - \alpha \cdot \text{valid}) \cdot T $$
Where:
*   $C$: Accumulated color.
*   $c$: Primitive color (from `evaluate`).
*   $\alpha$: Primitive opacity (from `evaluate`).
*   `valid`: Validity flag (from `evaluate`, typically 1 if the primitive contributes, 0 otherwise) [S1, unofficial].
*   $T$: Accumulated transmittance [S1, unofficial].

    bins = partition_into_bins(sorted_tiles)
    
    for bin in bins:
        # Static trip count for this bin
        max_prims_in_bin = get_bin_upper_bound(bin)
        
        # Parallelize over tiles in the bin
        for t in bin.tiles:
            candidates = tile_prim_map[t]
            # Pad candidates to max_prims_in_bin if necessary
            padded_candidates = pad_to_size(candidates, max_prims_in_bin)
            
            # Parallelize over pixels in the tile
            for (x, y) in t.pixels:
                px_data = pixel_info((x, y), cam, view)
                C = 0
                T = 1
                
                # Fixed trip count loop
                for i in range(max_prims_in_bin):
                    prim_2D = padded_candidates[i]
                    
                    # Early exit if no more primitives
                    if i >= len(candidates):
                        break
                        
                    p_sd = get_shader_data(prim_2D)
                    alpha, valid, c = evaluate(px_data, p_sd)
                    
                    C = C + c * alpha * valid * T
                    T = (1 - alpha * valid) * T
                    
                img[x, y] = C

### Edge Cases and Pitfalls
*   **Dynamic Sizes:** The number of visible primitives and tile intersections varies per frame. XPR handles this by fixing dimensions to compile-time upper bounds and padding unused entries [S1, unofficial].
*   **Performance vs. Quality Trade-off:** Lowering $P_{max}$ (e.g., to 4096) increases frame rate but may skip contributions from primitives that exceed the limit, potentially reducing PSNR [S1, unofficial].
*   **Compiler Overhead:** JAX/XLA kernel launch overhead can be significant at very high frame rates (e.g., synthetic scenes) [S1, unofficial].
*   **Method-Specific Costs:** Methods like 3DGUT, which require per-pixel world-space ray directions, may be slower in XPR than in hand-optimized CUDA because the ray direction computation is exposed via `pixel_info` rather than fused into the blending loop [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The pipeline is decomposed into modules with explicit parallelism dimensions (primitives, tiles, pixels). The complexity is dominated by the rasterization step, which is $O(T \cdot P_{avg})$ where $T$ is the number of tiles and $P_{avg}$ is the average number of primitives per tile [S1, unofficial].
*   **Memory Complexity:** Memory usage is bounded by the static upper bounds of primitives per tile and the number of tiles. Padding unused entries increases memory usage slightly [S1, unofficial].
*   **Performance:** On NVIDIA L40S GPUs, XPR achieves rendering speeds that are, on average, 97.18% of hand-optimized CUDA baselines [S1, unofficial]. It can be up to 208.18% faster than baseline implementations for certain methods (e.g., LinPrim) due to more aggressive culling strategies [S1, unofficial].
*   **Scalability:** XPR scales across hardware platforms (GPUs, TPUs, CPUs) without code changes, though absolute performance depends on the maturity of the XLA backend for each target [S1, unofficial].
*   **Strengths:**
    *   **Portability:** Runs on NVIDIA, AMD, Intel GPUs, TPUs, and CPUs [S1, unofficial].
    *   **Ease of Use:** New methods can be implemented in 260–304 lines of Python, compared to thousands in CUDA [S1, unofficial].
    *   **Automatic Differentiation:** Gradients flow through the four interface functions automatically via JAX [S1, unofficial].
*   **Limitations:**
    *   **Compiler Dependency:** Performance is bounded by the maturity of the XLA backend [S1, unofficial].
    *   **Not for Ray Marching:** Techniques involving ray marching or ray tracing (e.g., NeRFs, physically-based rendering) cannot be expressed with XPR [S1, unofficial].
    *   **Overhead for Complex Pixel Info:** Methods requiring complex per-pixel computations (like 3DGUT) may suffer from overhead compared to fused CUDA implementations [S1, unofficial].

## Background
XPR was introduced in the paper "XPR: An Extensible Cross-Platform Point-Based Differentiable Renderer" [S1, unofficial]. It addresses the limitations of existing frameworks (written in CUDA/Vulkan) that require thousands of lines of code per method and manual backward passes [S1, unofficial]. XPR leverages JAX/XLA to provide a high-level programming interface that separates method-specific logic from the shared rendering pipeline [S1, unofficial]. It was demonstrated with implementations of 3DGS, 3DGUT, and LinPrim [S1, unofficial].
