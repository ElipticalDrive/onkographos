# Gaussian Property Loading

Also called: PLY Property Loading with Fallbacks, PLY Gaussian Loading, PLY Stream Parsing, PLY Parser

## Overview
Gaussian Property Loading is the method for ingesting 3D Gaussian Splatting scene data from Polygon File Format (PLY) files and decoding raw vertex properties into the explicit mathematical parameters (position, scale, rotation, opacity, and spherical harmonics) required by the rasterization pipeline [S1, unofficial][S2, unofficial]. It solves the problem of converting the standardized, often compressed or logarithmically encoded PLY storage format into the structured `GaussianSet` representation [S1, unofficial][S2, unofficial]. It differs from its siblings by focusing on the initial ingestion and decoding of the PLY file into the `GaussianData` structure, whereas [Coordinate System Conversion for Gaussian Splats](3935-coordinate-system-conversion-for-gaussian-splats.md) handles spatial alignment and [INRIA V1 PLY Splat Parsing](6822-inria-v1-ply-splat-parsing.md) addresses specific legacy format variations [S1, unofficial][S2, unofficial].

## How it works
**Inputs:** A PLY file (ASCII or binary, little/big endian) containing vertex elements with properties for position, scale, rotation, opacity, and spherical harmonics (SH) or RGB color.
**Outputs:** A contiguous array or list of Gaussian objects containing decoded means, normalized quaternions, exponential scales, sigmoid opacities, and SH coefficients.

**Data Structures:**
The packed Gaussian structure in memory typically consists of:
1. `position`: 3 floats (x, y, z).
2. `logScale`: 3 floats (log of scale factors).
3. `rotQuat`: 4 floats (quaternion components w, x, y, z).
4. `opacityLogit`: 1 float (logit of opacity).
5. `shCoeffs`: A static array of `nShCoeffs` groups of 3 floats (RGB coefficients for each SH degree).

**Numbered Steps:**

1. **File Ingestion:** Read the PLY file into memory. For binary files, read as an `ArrayBuffer` or byte stream. For ASCII, parse line by line [S2, unofficial]. Detect format (ASCII, binary little-endian, binary big-endian) [S6, unofficial].
2. **Header Parsing:** Parse the PLY header to identify the `vertex` element count and property definitions. Map property names to their types (float, uchar, etc.) [S2, unofficial].
3. **Property Mapping & Fallbacks:** Identify the specific property names used in the file. Apply fallback logic for compatibility:
    - **Scale:** Try `scale_0`, `scale_1`, `scale_2`. If not found, try `scaling_0`, `scaling_1`, `scaling_2` [S5, unofficial].
    - **Rotation:** Try `rot_0`, `rot_1`, `rot_2`, `rot_3`. If not found, try `rotation_0`, `rotation_1`, `rotation_2`, `rotation_3` [S5, unofficial].
    - **Color/SH:** Try `f_dc_0`, `f_dc_1`, `f_dc_2` for DC spherical harmonics. If not found, try `red`, `green`, `blue` for RGB. If neither, default to white [S5, unofficial].
    - **Opacity:** Try `opacity`. If not found, default to full opacity (1.0) [S5, unofficial].
4. **Data Extraction:** Extract the raw values for each vertex.
    - **Position:** Map `x`, `y`, `z` to position components [S3, unofficial]. Stack into shape $(N, 3)$ [S4, unofficial].
    - **Scale:** Extract `scale_*` values. These are stored as log-scale values. Apply exponential activation: $s = \exp(v)$ [S3, unofficial].
    - **Rotation:** Extract `rot_*` values. These form a quaternion. Normalize the quaternion to unit length: $q_{norm} = q / \|q\|$ [S4, unofficial].
    - **Opacity:** Extract `opacity` value. This is stored as a logit. Apply sigmoid activation: $\alpha = \frac{1}{1 + e^{-v}}$ [S3, unofficial].
    - **Spherical Harmonics:**
        - Determine the SH degree by counting properties starting with `f_rest_`. Let $n_{rest}$ be this count. Calculate coefficients per color $n_{coeffs} = n_{rest} / 3$. The degree $L$ is derived from $n_{coeffs} = (L+1)^2 - 1$, so $L = \sqrt{n_{coeffs} + 1} - 1$ [S2, unofficial].
        - Map `f_dc_0`, `f_dc_1`, `f_dc_2` to the first 3 SH coefficients (DC term) [S3, unofficial].
        - Map `f_rest_*` properties to higher-order SH coefficients starting at index 3 [S3, unofficial]. Sort `f_rest` properties by their integer suffix to maintain order [S4, unofficial].
5. **Coordinate System Conversion (Optional but Common):** If the PLY was generated in a different coordinate system (e.g., Right-handed Down-Forward vs. Right-handed Up-Back), apply axis flips and rotations to positions and quaternions to align with the renderer's coordinate space [S1, unofficial].
6. **DC Color Computation:** Compute the base color from the DC SH coefficients. The DC coefficient $c_0$ relates to color $C$ by $C = c_0 \cdot C_0 + 0.5$, where $C_0 \approx 0.28209479177387814$ [S4, unofficial][S6, unofficial]. The final color is often clamped: $C_{final} = \max(C \cdot C_0 + 0.5, 0)$ [S4, unofficial].

**Pseudocode:**

```python
import math
import struct

def load_gaussians_from_ply(file_path):
    """
    Loads 3D Gaussian Splatting data from a PLY file.
    Returns a list of Gaussian dicts with keys: xyz, rot, scale, opacity, shs, dc_colours.
    """
    # 1. Read file content
    with open(file_path, 'rb') as f:
        content = f.read()
    
    # 2. Parse Header
    header_end = content.find(b'end_header')
    if header_end == -1:
        raise ValueError("Invalid PLY file: no end_header found")
    
    header_text = content[:header_end].decode('ascii')
    vertex_count = 0
    properties = {}
    
    for line in header_text.split('\n'):
        if line.startswith('element vertex'):
            parts = line.split()
            vertex_count = int(parts[2])
        elif line.startswith('property'):
            parts = line.split()
            # Format: property <type> <name>
            prop_type = parts[1]
            prop_name = parts[2]
            properties[prop_name] = prop_type
            
    # 3. Identify Property Names with Fallbacks
    pos_names = ['x', 'y', 'z']
    
    # Scale fallback: scale_0/1/2 or scaling_0/1/2
    if 'scale_0' in properties:
        scale_names = ['scale_0', 'scale_1', 'scale_2']
    elif 'scaling_0' in properties:
        scale_names = ['scaling_0', 'scaling_1', 'scaling_2']
    else:
        raise ValueError("No scale properties found")
        
    # Rotation fallback: rot_0..3 or rotation_0..3
    if 'rot_0' in properties:
        rot_names = ['rot_0', 'rot_1', 'rot_2', 'rot_3']
    elif 'rotation_0' in properties:
        rot_names = ['rotation_0', 'rotation_1', 'rotation_2', 'rotation_3']
    else:
        raise ValueError("No rotation properties found")
        
    # SH fallback: f_dc_0..2 or red/green/blue
    if 'f_dc_0' in properties:
        has_sh = True
        sh_dc_names = ['f_dc_0', 'f_dc_1', 'f_dc_2']
        # Count rest coefficients to determine degree
        rest_names = [k for k in properties.keys() if k.startswith('f_rest_')]
        rest_names.sort(key=lambda x: int(x.split('_')[1])) # Sort by suffix
        n_rest = len(rest_names)
        # n_rest = 3 * ((L+1)^2 - 1)
        # (L+1)^2 - 1 = n_rest / 3
        # (L+1)^2 = n_rest / 3 + 1
        # L = sqrt(n_rest / 3 + 1) - 1
        n_coeffs_per_color = n_rest / 3
        sh_degree = math.sqrt(n_coeffs_per_color + 1) - 1
        n_sh_coeffs = int((sh_degree + 1)**2) # Total coeffs per color (including DC)
        # Actually, shs array usually stores all coeffs. 
        # DC is 3 coeffs (R,G,B). Rest is 3 * ((L+1)^2 - 1).
        # Total floats for SH = 3 * (L+1)^2
        total_sh_floats = 3 * int((sh_degree + 1)**2)
    elif 'red' in properties:
        has_sh = False
        sh_dc_names = ['red', 'green', 'blue']
        total_sh_floats = 3 # Just RGB
    else:
        has_sh = False
        sh_dc_names = ['red', 'green', 'blue'] # Default to white if missing
        total_sh_floats = 3
        
    # Opacity fallback
    if 'opacity' in properties:
        opacity_name = 'opacity'
    else:
        opacity_name = None # Default to 1.0
        
    # 4. Parse Data
    # Determine byte offset after header
    data_offset = header_end + len(b'end_header\n') + 1 # +1 for newline
    
    # Determine endianness and type sizes from header or assume little-endian float
    # For simplicity, assuming little-endian floats for binary, or parsing ASCII
    # This pseudocode assumes binary little-endian for brevity, but handles ASCII logic conceptually
    
    gaussians = []
    
    # Helper to read float
    def read_float(data, offset):
        return struct.unpack_from('<f', data, offset)[0]
        
    # Helper to read uchar (0-255)
    def read_uchar(data, offset):
        return struct.unpack_from('B', data, offset)[0] / 255.0
        
    # Helper to read int/short etc if needed, but PLY GS usually uses float/uchar
    
    current_offset = data_offset
    
    for i in range(vertex_count):
        g = {}
        
        # Position
        x = read_float(content, current_offset)
        y = read_float(content, current_offset + 4)
        z = read_float(content, current_offset + 8)
        g['xyz'] = [x, y, z]
        current_offset += 12
        
        # Scale (Log scale)
        s0 = read_float(content, current_offset)
        s1 = read_float(content, current_offset + 4)
        s2 = read_float(content, current_offset + 8)
        # Apply exp()
        g['scale'] = [math.exp(s0), math.exp(s1), math.exp(s2)]
        current_offset += 12
        
        # Rotation (Quaternion)
        w = read_float(content, current_offset)
        x_q = read_float(content, current_offset + 4)
        y_q = read_float(content, current_offset + 8)
        z_q = read_float(content, current_offset + 12)
        # Normalize
        norm = math.sqrt(w*w + x_q*x_q + y_q*y_q + z_q*z_q)
        if norm > 0:
            g['rot'] = [w/norm, x_q/norm, y_q/norm, z_q/norm]
        else:
            g['rot'] = [1.0, 0.0, 0.0, 0.0]
        current_offset += 16
        
        # Opacity (Logit)
        if opacity_name:
            op_logit = read_float(content, current_offset)
            # Apply sigmoid
            g['opacity'] = 1.0 / (1.0 + math.exp(-op_logit))
            current_offset += 4
        else:
            g['opacity'] = 1.0
            
        # SH / Color
        if has_sh:
            sh_data = []
            # Read DC
            for name in sh_dc_names:
                # Find offset of this property in the vertex record
                # In a real parser, we'd map property names to offsets in the header
                # Here we assume contiguous reading based on header order or explicit offsets
                # For pseudocode, we assume we can find the offset for 'f_dc_0' etc.
                # This part is complex in raw binary parsing without a library.
                # We will assume a helper `get_property_offset(name)` exists.
                offset = get_property_offset(name, properties) 
                val = read_float(content, offset) # Simplified: assumes float type
                sh_data.append(val)
            
            # Read Rest
            for name in rest_names:
                offset = get_property_offset(name, properties)
                val = read_float(content, offset)
                sh_data.append(val)
                
            g['shs'] = sh_data
            
            # Compute DC Colour
            # C0 constant
            C0 = 0.28209479177387814
            # DC coeffs are the first 3 values in sh_data (R, G, B)
            dc_vals = sh_data[:3]
            # Formula: dc_colours = max(dc_vals * C0 + 0.5, 0)
            g['dc_colours'] = [max(v * C0 + 0.5, 0.0) for v in dc_vals]
        else:
            # RGB Fallback
            r = read_uchar(content, get_property_offset('red', properties))
            g_val = read_uchar(content, get_property_offset('green', properties))
            b = read_uchar(content, get_property_offset('blue', properties))
            g['shs'] = [r, g_val, b]
            g['dc_colours'] = [r, g_val, b]
            
        gaussians.append(g)
        
    return gaussians

    based on property types and order.
    """

    # 'property <type> <name>' lines to build a layout map.
```

**Edge Cases and Pitfalls:**
- **Precision:** PLY files may use `uchar` for color/opacity. Ensure division by 255.0 is applied correctly [S2, unofficial].
- **Endianness:** Binary PLY files can be little-endian or big-endian. Detect and swap bytes if necessary [S6, unofficial].
- **SH Degree:** The SH degree is not always explicitly stated in the header. It must be inferred from the count of `f_rest_*` properties [S2, unofficial].
- **Coordinate Systems:** Different tools export PLYs in different coordinate systems (e.g., Z-up vs Y-up). Coordinate conversion may be required before or after loading [S1, unofficial].

## Subtopics

### [Gaussian Splat PLY Loader](3254-gaussian-splat-ply-loader.md)
The Gaussian Splat PLY Loader parses 3D Gaussian Splatting scene data from a Polygon File Format (PLY) file, decoding raw vertex properties into a structured Gaussian representation suitable for rendering. It solves the problem of converting the standardized, often compressed or logarithmically encoded PLY storage format into the explicit mathematical parameters (position, scale, rotation, color, opacity) required by the rasterization pipeline. It differs from its siblings by focusing on the initial ingestion and decoding of the PLY file into the `GaussianData` structure, whereas [Coordinate System Conversion for Gaussian Splats](3935-coordinate-system-conversion-for-gaussian-splats.md) handles spatial alignment and [INRIA V1 PLY Splat Parsing](6822-inria-v1-ply-splat-parsing.md) addresses specific legacy format variations.

### [Coordinate System Conversion for Gaussian Splats](3935-coordinate-system-conversion-for-gaussian-splats.md)
This method transforms Gaussian splat attributes (position, rotation, spherical harmonics) between different coordinate systems, such as converting from the Right-handed Up-Back (RUB) format used internally to the Right-handed Down-Forward (RDF) format used in PLY files. It sets apart from sibling loaders by handling the specific axis flips and rotations required for quaternion and spherical harmonic consistency, ensuring that the rendered output remains invariant under coordinate system changes.

### [INRIA V1 PLY Splat Parsing](6822-inria-v1-ply-splat-parsing.md)
The INRIA V1 PLY Splat Parsing method decodes the text-based `.ply` files generated by the original INRIA 3D Gaussian Splatting implementation into an uncompressed, contiguous array of Gaussian properties suitable for rendering or further processing. It solves the problem of interpreting variable-length spherical harmonic (SH) fields and applying specific activation functions (sigmoid for opacity, exponential for scale) and coordinate system transformations required by downstream engines. Unlike the standard `.splat` binary format which uses fixed-width records, this method handles the PLY header's variable field counts to dynamically determine the SH degree (0, 1, or 2) and extract the corresponding coefficients.

### [3D Gaussian Splatting Model Preprocessing and Grid Partitioning](6908-3d-gaussian-splatting-model-preprocessing-and-grid-partition.md)
This method preprocesses a raw 3D Gaussian Splatting model stored in PLY format for use in Unreal Engine. It parses the PLY file, converts coordinate systems and property encodings to match the engine's internal representation, and partitions the Gaussians into a spatial grid for efficient culling and rendering. It differs from generic loaders by applying specific axis swaps, exponential scale decoding, and sigmoid opacity activation required by the target engine's shader pipeline.

### Unreal Engine PLY Gaussian Loader
A method to read standard 3D Gaussian Splatting `.ply` files into Unreal Engine data structures, supporting both ASCII and binary (little/big endian) formats [S6, unofficial]. The parser uses Miniply to load the file. It identifies the file type from constants: `kFileTypes = {"ascii", "binary_little_endian", "binary_big_endian"}` and property types from `kPropertyTypes = {"char", "uchar", "short", "ushort", "int", "uint", "float", "double"}` [S6, unofficial]. The output `FGaussianSplatData` struct contains: `Positions` (TArray<FVector>), `Normals` (TArray<FVector>), `Orientations` (TArray<FQuat>, stored as wxyz from PLY), `Scales` (TArray<FVector>), `Opacity` (TArray<float>), `ZeroOrderHarmonicsCoefficients` (TArray<FVector>), and `HighOrderHarmonicsCoefficients` (TArray<FHighOrderHarmonicsCoefficientsStruct> where `FHighOrderHarmonicsCoefficientsStruct` contains `TArray<FVector> Values`) [S6, unofficial]. The DC color conversion uses the constant $C_0 = 0.28209479177387814$ [S6, unofficial].

## Operating characteristics
**Time Complexity:** $O(N)$ where $N$ is the number of Gaussians, as each vertex property is read and transformed once.
**Memory Complexity:** $O(N \cdot D)$ where $D$ is the dimensionality of the Gaussian properties (position, scale, rotation, opacity, SH coefficients).
**Performance:** Loading is generally fast, dominated by I/O and simple arithmetic operations (exp, sigmoid, normalization). Parsing binary PLY is faster than ASCII.
**Strengths:** Standardized format (PLY) ensures compatibility across many 3D reconstruction tools. Fallbacks for property names increase robustness.
**Limitations:** PLY files can be large, especially with high-degree SH. Loading time increases with file size. Coordinate system mismatches are a common source of visual errors if not handled.

## Background
3D Gaussian Splatting (3DGS) was introduced by Kerbl et al. in 2023 [S1, unofficial][S2, unofficial]. The standard output format for trained 3DGS models is the PLY file. Various implementations (INRIA, WebGPU viewers, Unreal Engine plugins) have developed loaders to interpret these files, leading to the variants described in the Subtopics section. The method described here synthesizes the common practices found in these implementations.
