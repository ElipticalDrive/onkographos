# View Ordering Strategies

Also called: Camera Order, GS Count Order, TSP Order

## Overview
View Ordering Strategies are training-time techniques for 3D Gaussian Splatting that replace randomized view shuffling with deterministic sequences to optimize Gaussian caching and reduce communication overhead [S1]. Unlike [LiTe-GS](13085-lite-gs.md) which focuses on memory-efficient rendering, these strategies specifically target the efficiency of the CPU-based optimizer by structuring the order in which training views are processed [S1].

## How it works
**Inputs:** A set of training views $V = \{v_1, \dots, v_N\}$, each with a camera pose $P_i$ and a precomputed set of visible Gaussians $G_i$.
**Outputs:** A permutation $\pi$ of indices $\{1, \dots, N\}$ defining the training sequence.

**Data Structures:**
*   `views`: List of view objects containing camera pose and visibility mask.
*   `gaussian_count`: Array of size $N$, where `gaussian_count[i]` is the number of Gaussians visible in view $i$.
*   `overlap_matrix`: $N \times N$ matrix where `overlap_matrix[i][j]` is the number of Gaussians visible in both view $i$ and view $j$.

**Steps:**

1.  **Precompute Visibility:** For each view, determine the set of visible Gaussians. This requires frustum culling or ray casting against the Gaussian primitives [S1].
2.  **Select Strategy:** Choose one of the following ordering methods:

    *   **Camera Order:** Sort views based on the spatial position of their camera centers.
        *   Identify the scene’s principal axis (e.g., the direction of maximum variance in camera positions) [S1].
        *   Project each camera center $C_i$ onto this axis.
        *   Sort views by the scalar projection value [S1].

    *   **GS Count Order:** Sort views by the density of Gaussians they contain.
        *   Calculate $c_i = |G_i|$ for each view $i$.
        *   Sort views in descending order of $c_i$ [S1].
        *   Rationale: Prioritizing views with more Gaussians allows the CPU Adam optimizer to update a larger number of parameters earlier, amortizing its overhead [S1].

    *   **TSP Order:** Find a sequence that maximizes continuity between successive views.
        *   Construct a graph where nodes are views and edge weights $w_{ij} = |G_i \cap G_j|$ (the overlap count) [S1].
        *   Solve the Traveling Salesperson Problem (TSP) to find a path that maximizes the sum of weights between consecutive views in the sequence [S1].
        *   Note: TSP is NP-hard; heuristic solvers (e.g., nearest neighbor, 2-opt) are used in practice [S1].

**Parameters:**
*   Principal axis: Not given in the sources. [G] Typically derived via Principal Component Analysis (PCA) on camera positions.
*   TSP Solver: Not given in the sources. [G] Common heuristics include Nearest Neighbor or Christofides’ algorithm.

**Edge Cases:**
*   **Degenerate Camera Layouts:** If camera positions are collinear or symmetric, the principal axis may be ambiguous. [G] Use the axis with the largest variance.
*   **Empty Views:** Views with zero visible Gaussians should be handled gracefully, typically placed at the end or excluded. [G]
*   **TSP Scalability:** Exact TSP is infeasible for large $N$. Heuristics are required. [S1]

## Operating characteristics
*   **Time Complexity:**
    *   Camera Order: $O(N \log N)$ for sorting [S1].
    *   GS Count Order: $O(N \log N)$ for sorting, plus $O(N \cdot M)$ for visibility precomputation where $M$ is the number of Gaussians [S1].
    *   TSP Order: $O(N^2)$ for overlap matrix construction; TSP solution time depends on the solver, typically exponential in worst case but polynomial with heuristics [S1].
*   **Memory Complexity:** $O(N^2)$ for the TSP overlap matrix [S1]. GS Count Order requires $O(N)$ extra space for counts.
*   **Performance:** These strategies reduce training throughput bottlenecks associated with CPU optimizer overhead and cache misses [S1]. TSP Order generally yields the best convergence stability by ensuring high Gaussian overlap between steps [S1].
*   **Strengths:** Deterministic, reproducible training; reduced CPU overhead; better cache locality for Gaussian parameters.
*   **Limitations:** Requires precomputation of visibility; TSP is computationally expensive for very large scenes; Camera Order may not reflect semantic scene structure.

## Background
These strategies were introduced in the context of "CLM: Removing the GPU Memory Barrier for 3D Gaussian Splatting" [S1]. The work addresses the inefficiency of random view shuffling in large-scale 3D Gaussian Splatting training, where frequent cache misses and CPU optimizer overhead degrade performance [S1]. The ablation study in the source paper evaluates these four strategies (Random, Camera, GS Count, TSP) [S1].
