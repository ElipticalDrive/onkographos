# Tile Range Identification

Also called: identifyTileRanges, identifyTileRanges kernel

## Overview
Tile Range Identification is a CUDA kernel that determines the contiguous start and end indices of each tile's Gaussian splats within a globally sorted list of projected 2D Gaussian keys [S1, unofficial]. It solves the problem of mapping the flat, sorted array of (tile, depth) pairs back to per-tile ranges so that subsequent rasterization thread blocks can efficiently iterate only over the splats relevant to their assigned tile [S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** `point_list_keys`, a 1D array of $L$ 64-bit unsigned integers representing the sorted (splat, tile) pairs [S1, unofficial]. Each key is constructed as $(\text{tile\_id} \ll 32) \mid (\text{uint32\_t})Z_c$, where `tile_id` is the 1D tile index and $Z_c$ is the depth [S1, unofficial].
*   **Output:** `ranges`, a 1D array of `uint2` structures of size $N_{tiles}$ [S1, unofficial]. Each entry `ranges[t]` contains `{start, end}` indices into `point_list_keys` for tile $t$ [S1, unofficial].

**Data Structures:**
*   `point_list_keys`: `uint64_t` array of length $L$ [S1, unofficial].
*   `ranges`: `uint2` array of length $N_{tiles}$, where `ranges[t].x` is the start index and `ranges[t].y` is the end index (exclusive) for tile $t$ [S1, unofficial].

**Algorithm Steps:**
The kernel launches one thread per entry in the sorted list $L$ [S1, unofficial]. Each thread `idx` performs the following logic to identify range boundaries:

1.  **Bounds Check:** If `idx >= L`, terminate immediately [S1, unofficial].
2.  **Current Tile Extraction:** Extract the tile ID from the current key by shifting right by 32 bits:
    $$ \text{currtile} = \text{point\_list\_keys}[idx] \gg 32 $$
    [S1, unofficial]
3.  **First Element Handling:** If `idx == 0`, set the start of the current tile's range to 0:
    $$ \text{ranges}[\text{currtile}].x = 0 $$
    [S1, unofficial]
4.  **Boundary Detection:** If `idx > 0`:
    *   Extract the previous tile ID:
        $$ \text{prevtile} = \text{point\_list\_keys}[idx - 1] \gg 32 $$
        [S1, unofficial]
    *   If $\text{currtile} \neq \text{prevtile}$, a tile boundary exists between `idx - 1` and `idx` [S1, unofficial]. Set the end of the previous tile's range to the current index and the start of the current tile's range to the current index:
        $$ \text{ranges}[\text{prevtile}].y = idx $$
        $$ \text{ranges}[\text{currtile}].x = idx $$
        [S1, unofficial]
5.  **Last Element Handling:** If `idx == L - 1`, set the end of the current tile's range to $L$:
    $$ \text{ranges}[\text{currtile}].y = L $$
    [S1, unofficial]

**Pseudocode:**
```python
def identify_tile_ranges_kernel(point_list_keys, ranges, L, thread_id):
    idx = thread_id
    
    if idx >= L:
        return

    currtile = point_list_keys[idx] >> 32

    if idx == 0:
        ranges[currtile].x = 0

    if idx > 0:
        prevtile = point_list_keys[idx - 1] >> 32
        
        if currtile != prevtile:
            ranges[prevtile].y = idx
            ranges[currtile].x = idx

    if idx == L - 1:
        ranges[currtile].y = L
```

**Edge Cases and Pitfalls:**
*   **Empty Tiles:** If a tile has no splats, its range will remain at its default initialization value (typically `{0, 0}` or `{L, L}` depending on initialization strategy) [G]. The rasterizer must check if `start >= end` to skip empty tiles [G].
*   **Concurrent Writes:** Multiple threads may write to the same `ranges` entry (e.g., thread `idx` and `idx+1` both write to `ranges[currtile].x` if they are in the same tile, or thread `idx` writes `ranges[prevtile].y` while thread `idx-1` wrote `ranges[prevtile].x`) [G]. Since these writes are idempotent for the start index (always setting to the first occurrence) and the end index (always setting to the last occurrence + 1), atomic operations are not strictly required if the logic is correct, but race conditions on the *same* field from different threads in the same tile are benign only if they write the same value [G]. Specifically, `ranges[currtile].x` is written by the first thread in that tile, and `ranges[prevtile].y` is written by the last thread in that tile [G]. There is no conflict for a single field from multiple threads unless the logic is flawed [G]. However, `ranges[currtile].x` is written by thread `idx` where `currtile` is first seen [G]. If multiple threads map to the same tile, only the first one (lowest `idx`) sets the start, while the others see `currtile == prevtile` and do not write [G]. Thus, no atomics are needed [G].
*   **Initialization:** The `ranges` array must be initialized to a safe default (e.g., `{0, 0}`) before kernel launch to handle tiles with no splats, or the rasterizer must handle uninitialized ranges [G].

## Operating characteristics
*   **Time Complexity:** $O(L)$, where $L$ is the number of (splat, tile) pairs after assignment, as each element is processed exactly once by one thread [G].
*   **Memory Complexity:** $O(N_{tiles})$ for the output `ranges` array [G].
*   **Performance:** This kernel is extremely lightweight and typically completes in negligible time compared to the sorting and rasterization phases [G]. It is memory-bandwidth bound due to reading `point_list_keys` and writing `ranges`, but the working set is small [G].
*   **Strengths:** Simple parallel logic, no synchronization barriers required between threads, and minimal overhead [G].
*   **Limitations:** Requires the list to be fully sorted by tile ID before execution, and does not handle unsorted input [G].

## Background
Tile Range Identification is a standard component in tile-based rasterization pipelines for Gaussian Splatting, introduced alongside the tiled 2D Gaussian rasterization method [G]. It builds on the global radix sort performed in [Tile-based Rasterization with Radix Sort](7921-tile-based-rasterization-with-radix-sort.md) to enable efficient per-tile processing [G].
