# Distributed Training and Sharding

Also called: Distributed 3D Gaussian Splatting, Multi-GPU Gaussian Splatting, Sharded Gaussian Training

## Overview
Distributed Training and Sharding refers to the family of methods that partition 3D Gaussian primitives and rendering workloads across multiple GPUs to overcome single-device memory limits and accelerate the training and rendering of large-scale scenes [S1][S2, unofficial]. Unlike single-GPU baselines, these methods distribute the global point cloud and Gaussian parameters across multiple accelerators, enabling the processing of datasets exceeding 11.2M Gaussians (e.g., on an NVIDIA A100) [S1]. What sets this family apart from its siblings is the fundamental choice of sharding strategy: while [RoofGS](9830-roofgs.md) focuses on roof-level optimization and [Tile-Based Comparison-Free Sorting](9991-tile-based-comparison-free-sorting.md) optimizes sorting, Distributed Training and Sharding explicitly addresses the *distribution* of the Gaussian model itself, primarily through index-parity sharding or spatial partitioning, to balance load and minimize communication overhead [S2, unofficial].

## Shared principles
The methods in this family share a foundation in distributing the global state of $N$ 3D Gaussians across $M$ GPUs. The global set of Gaussians $\mathcal{G}$ is partitioned into shards $\mathcal{G}^{(m)}$ for $m \in \{0, \dots, M-1\}$, such that $\bigcup_m \mathcal{G}^{(m)} = \mathcal{G}$ and $\mathcal{G}^{(m)} \cap \mathcal{G}^{(n)} = \emptyset$ for $m \neq n$ [S1][S2, unofficial]. Each GPU $m$ stores its local shard $\mathcal{G}^{(m)}$ along with corresponding optimizer states (e.g., Adam moments) [S1][S2, unofficial].

Rendering involves projecting these 3D primitives to 2D screen space. To support distributed rendering, the image plane is typically divided into tiles or pixel blocks (e.g., $16 \times 16$ pixels) [S1][S2, unofficial]. Each tile is assigned to a specific GPU owner [S2, unofficial]. During the forward pass, each GPU projects its local shard to screen space and performs a sparse all-to-all communication exchange to route projected Gaussians to the GPUs owning the tiles they cover [S2, unofficial]. This ensures that each GPU composites only the pixels for its owned tiles using the received Gaussians [S2, unofficial].

In training, gradients are computed locally for the assigned pixels and then synchronized. Common synchronization strategies include fused all-reduce operations to aggregate gradients for the global parameters, ensuring updates incorporate information from all views [S1]. Alternatively, sparse all-to-all communication is used to aggregate gradients for the specific Gaussians that contributed to the rendered pixels [S2, unofficial].

## Subtopics

### [BlitzGS](15088-blitzgs.md)
BlitzGS is a distributed 3D Gaussian Splatting framework designed to accelerate city-scale reconstruction by reducing the active Gaussian workload at system, model, and view levels. Unlike spatial block partitioning which suffers from cross-block visibility waste and imbalance, BlitzGS shards Gaussians by index parity and applies importance-based pruning and distance-based LOD filtering to maintain high quality while training nearly an order of magnitude faster.

### [GS-Cache Inference Framework](15588-gs-cache-inference-framework.md)
GS-Cache is a holistic rendering framework designed to support real-time rendering of large-scale 3D Gaussian Splatting (3DGS) models at the city level, achieving >72 FPS at binocular 2K resolution. It addresses the computational bottleneck of the "Gaussian Derivation Stage" in structured Gaussian methods (e.g., Scaffold-GS, Octree-GS) by employing a cache-centric de-redundancy pipeline. Unlike native 3DGS or unstructured methods, GS-Cache specifically targets structured representations where anchors derive neural Gaussians, optimizing inter-frame redundancy in parameter decoding while maintaining rasterization quality.

### [Distributed 3D Gaussian Splatting](16979-distributed-3d-gaussian-splatting.md)
Distributed 3D Gaussian Splatting is a multi-GPU extension of the 3D Gaussian Splatting (3D-GS) pipeline designed for scientific visualization. It solves the problem of single-GPU memory capacity limits, enabling the scalable processing of large-scale scientific datasets that exceed the memory of a single accelerator (e.g., >11.2M Gaussians on an NVIDIA A100). Unlike standard 3D-GS which operates on a single device, this method distributes the global point cloud and Gaussian parameters across multiple GPUs, allowing for the training and rendering of high-resolution scenes that are otherwise infeasible. It builds on [3D Gaussian Splatting](15108-3d-gaussian-splatting.md) and adapts the distributed training design from [Grendel](19770-grendel.md).

### [Distributed Batched Rendering Loop](18495-distributed-batched-rendering-loop.md)
The Distributed Batched Rendering Loop is a parallel execution strategy for 3D Gaussian Splatting (3DGS) that processes multiple camera views simultaneously across a cluster of GPUs to overcome single-GPU memory and compute limits. Unlike single-view rendering or naive data-parallel approaches, this method explicitly partitions the workload of both the 3D Gaussian primitives and the 2D screen-space pixels across ranks, utilizing sparse all-to-all communication to ensure each GPU receives only the Gaussians relevant to its assigned pixel blocks. It sets itself apart by combining batched camera processing with dynamic load balancing based on pixel blocks, allowing for efficient scaling to high-resolution and large-scale scenes.

### [Online Image Rendering Placement](19195-online-image-rendering-placement.md)
Online Image Rendering Placement is a distributed training optimization method that dynamically assigns image patches to GPUs at each training iteration to minimize inter-node communication and balance computational load. It distinguishes itself from static partitioning schemes by solving an Integer Linear Programming (ILP) problem online using a fast heuristic (Linear Sum Assignment followed by local search) rather than an offline solver, allowing it to adapt to the random batch selection inherent in stochastic gradient descent.

### [Grendel](19770-grendel.md)
Grendel is a distributed training system for 3D Gaussian Splatting (3DGS) that partitions parameters and parallelizes computation across multiple GPUs to overcome single-GPU memory constraints in high-resolution and large-scale reconstruction. It distinguishes itself from single-GPU baselines and divide-and-conquer approaches like CityGS by supporting batched training with multiple views and employing mixed parallelism (Gaussian-wise and pixel-wise) with dynamic load balancing to handle unbalanced workloads.

### LS-Gaussian Accelerator Architecture
- **Definition**: A hardware architecture co-designed with the LS-Gaussian algorithm to support workload-aware mapping, featuring a streaming pipeline that allows continuous processing across hardware modules without requiring global synchronization [S1].
- **Step**: The accelerator predicts the workload for each tile based on viewpoint transformation to enable more balanced parallel computation [S1].
- **Comparison**: Unlike naive assignment of tiles to rendering blocks which fails to achieve balanced load distribution, this architecture uses workload prediction to mitigate inter-block idling and intra-block bubbles [S1].

### Spatial Block Partitioning
- **Definition**: Divides the scene into fixed world-space spatial blocks (e.g., uniform grid). Each GPU is bound to a specific block and trains its Gaussians independently [S2, unofficial].
- **Step**: Construct a uniform grid (e.g., 4×5 or 5×6). Assign each block a boundary halo of neighboring Gaussians for cross-block consistency. Train blocks independently across GPUs. During rendering, cameras near block boundaries trigger cross-block visibility overlap and boundary reassignment. Perform a final single-GPU merge to assemble the full scene [S2, unofficial].
- **Pitfall**: Overlapping blocks re-optimize the same surfaces, wasting computation. In a 20-block split, 23.5M Gaussians are optimized but only 5.37M survive merge (77% discarded). Finer partitions increase redundancy and training time with negligible quality gain (<0.2 dB) [S2, unofficial].
- **Number**: On Building (1,920 cameras, 4 GPUs), 86.8% of cameras fall in ≥2 blocks for 20-block partition, and 95.5% for 30-block partition. Wall-clock time for split/make-span/merge reaches 115.6–169.8 min vs 39 min for sharding [S2, unofficial].

### Primitive Sharding (Index-Parity Sharding)
- **Definition**: Distributes a single global Gaussian model across multiple GPUs by assigning Gaussians to ranks based on index parity. Each GPU holds a balanced, scene-wide slice of the model [S2, unofficial].
- **Step**: Assign each Gaussian primitive to a GPU rank using index parity. During rendering, distribute each step through balanced tile allocation across GPUs. Route projected Gaussians to tile owners via all-to-all communication. Train using a single global camera stream. Each camera enters training once per iteration with no cross-block duplication. Only distributed cost is the all-to-all exchange inside each render step [S2, unofficial].
- **Number**: On a 4-GPU setup (Building scene, 1,920 cameras), communication cost for routing projected Gaussians to tile owners is 3–5 ms per iteration, staying under 7% of total iteration time [S2, unofficial].
- **Comparison**: Unlike spatial block partitioning, it eliminates boundary reassignment, cross-block visibility overlap, and the final single-GPU merge step. Storage and per-step rendering remain evenly distributed as GPU count grows [S2, unofficial].

### Naive Offloading
- **Definition**: A CPU offloading strategy for 3DGS training that transfers all Gaussian attributes to CPU memory before rendering, using pinned memory and CPU Adam [S3].
- **Step**: Adopts pre-rendering frustum culling for efficient kernel computation. Trains each batch one image at a time with gradient accumulation to reduce activation memory usage [S3].

## Background
The need for distributed training in 3D Gaussian Splatting arises from the rapid growth of scene complexity and resolution, which exceeds the memory capacity of single GPUs. Standard 3D-GS can handle up to approximately 11.2M Gaussians on an NVIDIA A100, but scientific datasets or city-scale reconstructions often require millions more [S1]. Early approaches like spatial block partitioning attempted to solve this by dividing the scene into fixed regions, but this led to significant redundancy and imbalance due to cross-block visibility overlaps [S2, unofficial].

The concept of sharding Gaussians by index parity was introduced to address these inefficiencies, allowing for balanced distribution and eliminating the need for complex boundary handling [S2, unofficial]. Systems like Grendel [S1] and BlitzGS [S2, unofficial] have further refined this approach by incorporating dynamic load balancing, sparse communication, and advanced pruning techniques. Additionally, hardware-aware optimizations such as LS-Gaussian [S1] and memory management strategies like CLM [S3] have been developed to complement distributed training, focusing on reducing communication overhead and maximizing hardware utilization.
