# Grendel-GS
Also called: Out-of-core and distributed optimization for 3DGS
## Overview
Grendel-GS is a distributed optimization framework for 3D Gaussian Splatting (3DGS) that partitions the Gaussian primitive list across multiple GPUs to overcome single-device memory limits [S1, unofficial]. It enables the training of scenes with Gaussian counts exceeding the VRAM capacity of a single accelerator by distributing the representation and rendering workload [S1, unofficial]. Unlike [TideGS](7350-tidegs.md), which streams data from disk on a single machine, Grendel-GS distributes the active parameter set across a GPU cluster, leveraging inter-GPU communication to combine partial render results [S1, unofficial].
## How it works
**Inputs and Outputs:**
- Input: A global list of $N$ 3D Gaussians $\mathcal{G} = \{\mathbf{g}_1, \dots, \mathbf{g}_N\}$, where each $\mathbf{g}_i$ contains position $\mathbf{p}_i$, covariance $\mathbf{\Sigma}_i$, opacity $\alpha_i$, and spherical harmonic coefficients for color.
- Input: A set of training views (cameras).
- Input: A partitioning scheme mapping subsets of $\mathcal{G}$ to specific GPUs in a cluster.
- Output: Optimized Gaussian parameters $\mathcal{G}'$ and rendered images.

**Data Structures:**
- **Global Gaussian List:** Stored in a distributed manner. Each GPU $k$ holds a local subset $\mathcal{G}_k$ such that $\bigcup_k \mathcal{G}_k = \mathcal{G}$ and $\mathcal{G}_i \cap \mathcal{G}_j = \emptyset$ for $i \neq j$.
- **Render Buffers:** Per-GPU buffers storing partial color and depth accumulations for pixels affected by $\mathcal{G}_k$.

**Method Steps:**
1. **Partitioning:** The global Gaussian list $\mathcal{G}$ is statically or dynamically partitioned into $K$ subsets $\{\mathcal{G}_1, \dots, \mathcal{G}_K\}$, assigned to $K$ GPUs. [S1, unofficial]
2. **Local Rasterization:** For each training view, every GPU $k$ performs the differentiable alpha-blending rasterization forward pass using only its local subset $\mathcal{G}_k$. This produces a partial color contribution $\mathbf{c}_k(\mathbf{x})$ and depth $d_k(\mathbf{x})$ for each pixel $\mathbf{x}$ [S1, unofficial].
3. **Inter-GPU Communication:** At partition boundaries, partial render results are communicated between GPUs. The specific mechanism involves combining the alpha-blended results from all subsets. Since alpha blending is not linear, the combination requires sharing the accumulated opacity and color states or using a commutative composition strategy if the rasterizer supports it. The source notes "combines the results via inter-GPU communication at partition boundaries" [S1, unofficial].
4. **Gradient Computation:** The total loss $\mathcal{L}$ is computed from the combined render. Gradients $\frac{\partial \mathcal{L}}{\partial \mathbf{g}_k}$ are computed for each local subset.
5. **Parameter Update:** Each GPU updates its local parameters $\mathcal{G}_k$ using an optimizer (e.g., Adam).
6. **Synchronization:** If the partitioning changes or for consistency, parameters may be synchronized across GPUs. [S1, unofficial]

**Pseudocode:**
```python
# Distributed Grendel-GS Training Step
def train_step_distributed(gaussians_global, views, gpu_id, num_gpus):
    # 1. Local subset assignment (static partitioning assumed for simplicity)
    local_gaussians = get_partition(gaussians_global, gpu_id, num_gpus)
    
    # 2. Local Rasterization
    # Each GPU renders its subset independently
    partial_color, partial_alpha, partial_depth = rasterize(
        local_gaussians, views[gpu_id]
    )
    
    # 3. Inter-GPU Communication / Combination
    # Note: Exact combination logic depends on the rasterizer's support for 
    # distributed alpha blending. Standard alpha blending is not commutative 
    # across arbitrary subsets without depth sorting.
    # Grendel-GS likely uses a strategy where partial results are aggregated.
    # This step is described as "combines the results via inter-GPU communication" [S1, unofficial].
    combined_color, combined_alpha = aggregate_partial_results(
        partial_color, partial_alpha, gpu_id, num_gpus
    )
    
    # 4. Loss Computation
    target_image = get_target_image(views[gpu_id])
    loss = compute_loss(combined_color, target_image)
    
    # 5. Backpropagation
    gradients = compute_gradients(loss, local_gaussians)
    
    # 6. Optimization Step
    update_parameters(local_gaussians, gradients)
    
    return local_gaussians
```
**Edge Cases:**
- **Boundary Pixels:** Pixels affected by Gaussians in multiple partitions require careful synchronization to ensure correct alpha blending order. [S1, unofficial]
- **Communication Overhead:** Inter-GPU bandwidth can become a bottleneck if the number of partitions is large or the scene is dense.

## Subtopics
## Operating characteristics
- **Memory Complexity:** Linear with respect to the number of GPUs. Each GPU stores only $N/K$ Gaussians, allowing training of scenes with $N \gg \text{VRAM}_{\text{single}}$. [S1, unofficial]
- **Time Complexity:** Adds communication overhead to the standard rasterization cost. Scaling is sub-linear due to inter-GPU synchronization. [S1, unofficial]
- **Strengths:** Enables training of massive scenes (billions of primitives) that do not fit in a single GPU's VRAM. [S1, unofficial]
- **Limitations:** Requires multi-GPU infrastructure and network connectivity. Communication latency can reduce efficiency compared to single-GPU methods. [S1, unofficial]
- **When to use:** When the scene size exceeds single-GPU memory limits and multi-GPU resources are available. [S1, unofficial]
- **When not to use:** For small scenes where single-GPU efficiency is preferred, or when network bandwidth is limited. [S1, unofficial]

## Background
Grendel-GS was introduced as part of the broader effort to scale 3D Gaussian Splatting to larger scenes. It addresses the memory bottleneck of standard 3DGS by distributing the Gaussian representation across multiple GPUs [S1, unofficial]. It is distinct from out-of-core methods like TideGS, which use disk I/O on a single machine [S1, unofficial].
