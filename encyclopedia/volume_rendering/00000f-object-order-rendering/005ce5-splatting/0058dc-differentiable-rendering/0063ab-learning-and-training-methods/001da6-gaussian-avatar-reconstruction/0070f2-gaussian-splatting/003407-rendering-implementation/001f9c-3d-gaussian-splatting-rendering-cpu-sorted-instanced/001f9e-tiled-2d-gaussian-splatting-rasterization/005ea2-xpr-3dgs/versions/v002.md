# XPR-3DGS

Also called: XPR implementation of 3D Gaussian Splatting

## Overview
XPR-3DGS is a point-based differentiable rendering method that implements 3D Gaussian Splatting within the XPR framework [S1, unofficial]. It projects 3D Gaussians to 2D, culls tiles based on conic bounds, and evaluates alpha blending per pixel [S1, unofficial]. It differs from its siblings by providing a high-level, Python-based implementation within the XPR framework that requires significantly fewer lines of code (260–304) than traditional C++/CUDA implementations [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A list of 3D Gaussian primitives defined by `PrimitiveParams`.
*   **Output:** Rendered image colors and alpha values.

**Data Structures:**
The primitive parameters are defined as follows [S1, unofficial]:

```python
class PrimitiveParams:
    mu: Array  # (3,) mean in world space
    s: Array   # (3,) scales
    q: Array   # (4,) unit quaternion for rotation
    sh: Array  # (C, 3) spherical harmonic coefficients
    o: Array   # (1,) opacity
```

**Parameters:**
*   `alpha_thresh`: Threshold for opacity to determine visibility. Default value is $1/255$ [S1, unofficial].
*   `z_near`: Near plane distance for camera-space depth check [S1, unofficial].
*   `pixel_info`: Set to `None` because per-pixel evaluation depends only on the 2D pixel coordinates [S1, unofficial].

**Steps:**

1.  **Project:** For each primitive $p$, compute the projection onto the image plane [S1, unofficial].
    *   Compute the world-to-camera projection matrix $R_{w2c}$ [S1, unofficial].
    *   Transform the mean $\mu$ to camera space: $\mu_c = R_{w2c} \mu$ [S1, unofficial].
    *   Compute the 2D mean $\mu_{2D}$ and the 2D covariance $\Sigma_{2D}$ using EWA splatting [S1, unofficial].
    *   Compute the determinant $det$ of $\Sigma_{2D}$ [S1, unofficial].
    *   Compute the conic matrix $\Sigma_{2D}^{-1}$, referred to as `conic_2D` [S1, unofficial].
    *   Compute extents $ex, ey$ from $\Sigma_{2D}$ and $det$ [S1, unofficial].
    *   Compute radius $r$ from $ex, ey$ [S1, unofficial].
    *   Compute the axis-aligned bounding box $aabb$ using $\mu_{2D}, ex, ey$ [S1, unofficial].
    *   Compute tile count $tc$ as the area of $aabb$ in tile units: $tc = (aabb.x_{max} - aabb.x_{min}) \times (aabb.y_{max} - aabb.y_{min})$ [S1, unofficial].
    *   Compute visibility flag: $visible = (det > 0) \land (o \ge \alpha_{thresh}) \land (r > 0) \land (tc > 0) \land (\mu_c[2] > z_{near})$ [S1, unofficial].
    *   Adjust tile count: $tc = tc \times float(visible)$ [S1, unofficial].
    *   Compute view-dependent color $c$ from $\mu$ and spherical harmonics $sh$ [S1, unofficial].
    *   Produce Tile Cull Data ($p_{tcd}$): Concatenate `conic_2D[0,0]`, `conic_2D[0,1]`, `conic_2D[1,1]`, opacity $o$, $\mu_{2D}$, and $visible$ [S1, unofficial].
    *   Produce Shader Data ($p_{sd}$): Concatenate $\mu_{2D}[0]$, $\mu_{2D}[1]$, $-0.5 \times \text{conic\_2D}[0,0]$, $-\text{conic\_2D}[0,1]$, $-0.5 \times \text{conic\_2D}[1,1]$, opacity $o$, and color $c$ [S1, unofficial].

2.  **Tile Cull:** For each tile in the primitive's bounding box, determine if the tile needs to be processed [S1, unofficial].
    *   Unpack `conic`, $o$, $\mu_{2D}$, and $visible$ from $p_{tcd}$ [S1, unofficial].
    *   Check if $\mu_{2D}$ is outside the tile bounds $(tile_{min}, tile_{max})$ [S1, unofficial].
    *   Compute the 2D location $point_{2D}$ inside the tile that maximizes the Gaussian response, which is either $\mu_{2D}$ (if inside the tile) or a point along the edges of the tile facing $\mu_{2D}$ [S1, unofficial].
    *   Compute max contribution power: $dx = \mu_{2D}[0] - point_{2D}[0]$, $dy = \mu_{2D}[1] - point_{2D}[1]$, $power = 0.5 \times (dx^2 \times conic[0] + 2 \times dx \times dy \times conic[1] + dy^2 \times conic[2])$ [S1, unofficial].
    *   Determine tile visibility: $tile\_visible = (power \le \log(o / \alpha_{thresh})) \land visible$ [S1, unofficial].

3.  **Evaluate:** For each pixel $px = (x, y)$ in visible tiles, compute the contribution [S1, unofficial].
    *   Unpack $\mu_{2D}$, `conic`, $o$, and $c$ from $p_{sd}$ [S1, unofficial].
    *   Compute $dx = px[0] - \mu_{2D}[0]$, $dy = px[1] - \mu_{2D}[1]$ [S1, unofficial].
    *   Compute power: $power = dx^2 \times conic[0] + dx \times dy \times conic[1] + dy^2 \times conic[2]$ [S1, unofficial].
    *   Compute alpha: $\alpha = o \times \exp(power)$ [S1, unofficial].
    *   Validate result: $valid = (power \le 0)$ [S1, unofficial].

## Operating characteristics
*   **Performance:** XPR-3DGS is slower than the Base implementation on Synthetic datasets (0.76x FPS) due to JAX kernel launch overhead being significant at very high frame rates [S1, unofficial]. On 360 and T&T datasets, it achieves 0.95x and 0.96x FPS respectively [S1, unofficial].
*   **Code Size:** Requires only 260 to 304 lines of Python, significantly fewer than Base implementations (e.g., 2,153 lines for 3DGS) [S1, unofficial].
*   **Strengths:** High-level interface enables rapid prototyping; fewer lines of code reduce implementation complexity [S1, unofficial].
*   **Limitations:** JAX overhead impacts performance at very high frame rates; pixel evaluation depends only on 2D coordinates, which may be less flexible than methods using per-pixel world-space ray directions [S1, unofficial].
