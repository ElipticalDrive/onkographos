# 3D Gaussian Splatting Rendering (CPU-Sorted, Instanced)

Also called: 3DGS Weekend Renderer, Gaussian Splatting Instanced Draw, RViz Splat Cloud, SplatCloud Instanced Rendering

## Overview
This method renders trained 3D Gaussian Splatting (3DGS) scenes by projecting 3D Gaussians into 2D screen-space quads, sorting them by camera-space depth on the CPU, and drawing them using hardware-instanced rendering with standard alpha blending [S1, S2, S3, S5, S6, unofficial]. It solves the problem of visualizing large-scale, photorealistic 3D scenes on client-side hardware (Android, iOS, Web, ROS RViz) without requiring neural network inference or server-side ray tracing [S1, S3, unofficial]. It sets itself apart from its siblings by performing the sorting explicitly on the CPU (often via radix sort or JS native sort) and using a single instanced draw call, whereas [Tiled 2D Gaussian Splatting Rasterization](2061-tiled-2d-gaussian-splatting-rasterization.md) performs sorting and rasterization entirely on the GPU, and [Gaussian Splat Rendering (Screen-Space Quad)](2075-gaussian-splat-rendering-screen-space-quad.md) describes the general mechanism without specifying the CPU-side sorting implementation [S2, S3, S6, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** A set of $N$ 3D Gaussians defined by means $\boldsymbol{\mu}$, covariances $\boldsymbol{\Sigma}_{3D}$ (derived from rotation $q$ and scale $s$), opacities $\alpha$, and spherical harmonic (SH) coefficients. Camera view matrix $\mathbf{V}$ and projection matrix $\mathbf{P}$.
*   **Outputs:** A 2D image with color and alpha channels.

**Data Structures:**
*   **Splat Data:** Stored in textures or buffers. For Filament/WebGL implementations, two square RGBA16F textures are used: `splatPositionScale` (layout: $xyz=$ center position, $w=$ scale) and `splatColorOpacity` (layout: $rgb=$ SH0 color, $a=$ opacity) [S5, S6, unofficial]. For C++ OpenGL, a `GpuGaussian` struct (44 bytes: centroid 12B, opacity 4B, scale 12B, rotation 16B) is used [S1, unofficial].
*   **Index Buffer:** A dynamic write-only vertex buffer (VBO) of size $N \times \text{sizeof(float)}$ containing sorted splat indices (0 to $N-1$) [S2, unofficial].
*   **Sort Entries:** For CPU sorting, a struct `SplatSortEntry` containing `cameraZ` (float, 4 bytes) and `splatIndex` (size_t, 8 bytes) is used [S1, unofficial]. In JavaScript, a `BigInt64Array` (`depthMix`) of size $2 \times N$ is used, where even offsets store the index and odd offsets store the packed depth [S3, unofficial].

**Steps:**

1.  **Frustum Culling and Filtering:**
    Transform 3D means to camera space: $\boldsymbol{\mu}' = \mathbf{V} \boldsymbol{\mu}$ [Parent]. Project to image plane: $\boldsymbol{\mu}_{2D}$ [Parent]. Perform frustum culling to remove off-screen Gaussians (image bounds and near/far planes with a FOV margin ratio of 0.3) [S4, unofficial]. Skip Gaussians with opacity $\alpha_{eff} < 0.05$ (or 0.01 in some implementations) [S4, S1, unofficial].

2.  **CPU Sorting:**
    Compute the camera-space depth for each remaining splat.
    *   *C++:* Extract $z$ from `view * vec4(centroid, 1.0)` [S1, unofficial].
    *   *JavaScript:* Compute `depth = 10000 + viewProj[2]*x + viewProj[6]*y + viewProj[10]*z` [S3, unofficial].
    Sort the splats by increasing camera-space $Z$ (far-to-near order, as the camera looks down the negative $Z$ axis) [S1, unofficial].
    *   *Optimization:* Re-sort only when the camera direction delta exceeds a threshold (e.g., 1% of bounding radius) to avoid redundant computation [S5, S3, unofficial].
    Reorder the Gaussian and SH data arrays based on the sorted indices [S1, unofficial].

3.  **Batching (if necessary):**
    If the number of splats $N$ exceeds the hardware limit for instanced drawing (e.g., 65,535 instances due to 16-bit index buffers), split the sorted list into multiple batches [S5, S6, unofficial].

4.  **Vertex Shader Execution (Per Instance):**
    For each instance $i$ (representing a splat):
    *   Fetch attributes from textures or buffers using `gl_InstanceID` [S5, unofficial].
    *   Compute clip space position: $\mathbf{clip} = \mathbf{P} \mathbf{V} \begin{pmatrix} \boldsymbol{\mu}' \\ 1 \end{pmatrix}$ [S1, unofficial].
    *   Compute the 2D screen-space covariance $\boldsymbol{\Sigma}_{2D}$ using the Jacobian $\mathbf{J}$ of the projection [Parent].
    *   Perform eigen-decomposition of $\boldsymbol{\Sigma}_{2D}$ to find eigenvalues $\lambda_1, \lambda_2$ and eigenvectors $\mathbf{e}_1, \mathbf{e}_2$. Add jitter (0.3) to diagonal elements for stability [S1, unofficial].
        $$ \lambda_1 = \max(\text{mid} + \text{radius}, 0.01), \quad \lambda_2 = \max(\text{mid} - \text{radius}, 0.01) $$
        where $\text{mid} = 0.5(a+d)$, $\text{radius} = \sqrt{\max(\text{mid}^2 - \det, 0)}$, and $a,d$ are diagonal elements of $\boldsymbol{\Sigma}_{2D}$ [S1, unofficial].
    *   Compute 3-sigma principal half-axes: $\mathbf{b}_1 = 3\sqrt{\lambda_1}\mathbf{e}_1$, $\mathbf{b}_2 = 3\sqrt{\lambda_2}\mathbf{e}_2$ [S1, unofficial].
    *   Compute vertex offset in NDC: $\Delta \text{NDC} = \frac{\text{quadCorner}.x \cdot \mathbf{b}_1 + \text{quadCorner}.y \cdot \mathbf{b}_2}{\text{viewportSize} \cdot 0.5}$ [S1, unofficial].
    *   Set final position: $\mathbf{gl\_Position} = \begin{pmatrix} \text{ndc}.xy + \Delta \text{NDC}, \text{ndc}.z, 1.0 \end{pmatrix}$ [S1, unofficial].
    *   Pass `splatCoord` (quadCorner), `splatColor` (SH evaluation), and `splatOpacity` ($\sigma(\alpha)$) to the fragment shader [S1, unofficial].

5.  **Fragment Shader Execution:**
    *   Compute power term: $p = -4.5 \cdot \text{dot}(\text{splatCoord}, \text{splatCoord})$ [S1, unofficial].
    *   Discard if $p < -9.0$ (equivalent to $e^{-9} \approx 0$) [S1, unofficial].
    *   Compute final alpha: $\alpha_{frag} = \min(0.99, \text{splatOpacity} \cdot \exp(p))$ [S1, unofficial].
    *   Discard if $\alpha_{frag} < 0.001$ [S1, unofficial].
    *   Output color: $\text{FragColor} = \begin{pmatrix} \text{splatColor} \\ \alpha_{frag} \end{pmatrix}$ [S1, unofficial].

6.  **Alpha Compositing:**
    Enable blending: `glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA)` [S1, unofficial]. Disable depth test [S1, unofficial]. Draw all splats back-to-front using `glDrawArraysInstanced` [S1, unofficial].

**Pseudocode:**

```python
def render_3dgs_cpu_sorted(gs, camera, viewport_size):
    """
    gs: List of Gaussian objects with means, covariances, opacities, sh_coeffs.
    camera: Object with view_matrix, projection_matrix, width, height.
    viewport_size: (W, H) tuple.
    """
    # 1. Transform and Filter
    view_mat = camera.view_matrix
    proj_mat = camera.projection_matrix
    
    # Transform means to camera space
    means_cam = [view_mat * vec4(g.mean, 1.0) for g in gs]
    
    # Frustum culling and opacity filter
    valid_indices = []
    for i, g in enumerate(gs):
        if g.opacity < 0.05:
            continue
        # Simple frustum check (implementation detail omitted, see S4)
        if not is_in_frustum(means_cam[i], camera):
            continue
        valid_indices.append(i)
        
    # 2. CPU Sorting
    # Create sort entries: (camera_z, original_index)
    sort_entries = []
    for i in valid_indices:
        z = means_cam[i].z # Camera looks down negative Z
        sort_entries.append((z, i))
        
    # Sort by increasing Z (far to near)
    sort_entries.sort(key=lambda x: x[0])
    
    # Reorder GS data based on sorted indices
    sorted_gs = [gs[i] for _, i in sort_entries]
    
    # 3. Batching (if needed)
    MAX_INSTANCES = 65535
    batches = []
    for i in range(0, len(sorted_gs), MAX_INSTANCES):
        batches.append(sorted_gs[i:i+MAX_INSTANCES])
        
    # 4. Rendering Loop
    glDisable(GL_DEPTH_TEST)
    glEnable(GL_BLEND)
    glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA)
    
    for batch in batches:
        # Upload batch data to GPU (textures or VBOs)
        upload_batch_to_gpu(batch)
        
        # Draw instanced quads
        # Vertex shader handles projection, covariance projection, and quad expansion
        # Fragment shader handles Gaussian falloff and alpha
        glDrawArraysInstanced(GL_TRIANGLE_STRIP, 0, 4, len(batch))
```

## Subtopics

### [Tiled 2D Gaussian Splatting Rasterization](2061-tiled-2d-gaussian-splatting-rasterization.md)
A GPU-parallel, tile-based method that sorts splats on the GPU using radix sort, enabling real-time performance for millions of splats. Choose this for high-performance desktop/mobile rendering where GPU compute is available.

### [Gaussian Splat Rendering (Screen-Space Quad)](2075-gaussian-splat-rendering-screen-space-quad.md)
A display-only technique using CPU-side depth sorting and instanced drawing. Choose this for general-purpose visualization where explicit CPU sorting is preferred over GPU compute shaders.

### [Depth-First Splat Sorting](2850-depth-first-splat-sorting.md)
A preprocessing step that sorts visible splats before tile expansion, reducing sorting overhead. Choose this as a drop-in optimization for tiled renderers.

### [Splatapult Gaussian Splat Renderer](6749-splatapult-gaussian-splat-renderer.md)
A standalone renderer with a complete GPU-based multi-radix sorting pipeline and VR support. Choose this for VR applications requiring high performance.

### [SortFree Weighting](8006-sortfree-weighting.md)
An order-independent transparency approximation that eliminates sorting. Choose this when visual stability is less critical than rendering speed, or on hardware without sorting capabilities.

### [Unity Mobile Implementation](9536-unity-mobile-implementation.md)
A Unity-optimized renderer for mobile compatibility. Choose this for game engine integration on mobile devices.

### [CPU-based Gaussian Splatting Thumbnailer](14038-cpu-based-gaussian-splatting-thumbnailer.md)
A pure CPU thumbnail generator using JIT compilation and simplified blending. Choose this for fast preview generation where visual fidelity is secondary.

### [Support Guard](17686-support-guard.md)
A fault-mitigation technique that clamps parameters to prevent corruption. Choose this for spaceborne or robotic hardware where reliability is critical.

## Operating characteristics
*   **Time Complexity:** Sorting dominates the CPU cost. CPU radix sort of ~500k depth keys takes a few milliseconds on a worker thread [S5, unofficial]. JS native sort takes ~1 ms for 8k splats [S5, unofficial]. Re-sorting is gated on camera movement, not every frame [S5, S3, unofficial].
*   **Memory Complexity:** $O(N)$ for storing splat data. SH0 splats require ~28 bytes/splat in RGBA16F textures (~14 MB VRAM for 500k splats) [S5, unofficial].
*   **Performance:** Mobile-GS reports up to 127 FPS on modern mobile GPUs using first-order SH and OIT [S5, unofficial]. However, CPU sorting is less efficient than the official 3DGS renderer's tile-based CUDA rasterizer [S1, unofficial].
*   **Strengths:** Simple implementation, works on hardware without compute shaders (e.g., older WebGL, Filament 1.71.5) [S5, unofficial], compatible with standard alpha blending pipelines.
*   **Limitations:** CPU sorting becomes a bottleneck for very large scenes (>1M splats) [S1, unofficial]. Limited to SH0 or SH1 on mid-range mobile to stay within VRAM budgets [S5, unofficial]. Instance count limited to 65,535 per draw call, requiring batching [S5, unofficial].
*   **When to use:** Display-only visualization on Android, iOS, Web, and ROS RViz [S2, S5, S6, unofficial]. When GPU compute shaders are unavailable or undesirable.
*   **When not to use:** Real-time interactive rendering of massive scenes (>1M splats) where GPU sorting is required [S1, unofficial].

## Background
This method is based on the paper "3D Gaussian Splatting for Real-Time Radiance Field Rendering" by Kerbl et al. (2023) [S1, unofficial]. It was developed as a display-only renderer for trained 3DGS scenes, initially popularized by the "3D Gaussian Splatting in a Weekend" tutorial [S1, unofficial]. It has been implemented in various contexts, including RViz for ROS [S2, unofficial], web viewers [S3, unofficial], Android/iOS via Filament [S5, unofficial], and Unity [S6, unofficial]. The approach was chosen for its simplicity and compatibility with standard graphics APIs when GPU compute shaders were not available or practical [S5, unofficial].
