# Hardware and Computational Acceleration

Also called: Hardware acceleration, Computational optimization, GPU acceleration for 3DGS

## Overview
Hardware and Computational Acceleration encompasses methods that optimize the rendering and training pipelines of 3D Gaussian Splatting (3DGS) to overcome memory bandwidth, compute throughput, and capacity bottlenecks on consumer and professional hardware [S1, S2, S3, unofficial][S4][S5, unofficial][S6]. It sets itself apart from generic algorithmic improvements by explicitly targeting hardware-specific constraints—such as Tensor Core utilization, PCIe bandwidth, and cache hierarchy—through architectural changes like kernel fusion, attribute-wise offloading, and parallelism strategies [S1, unofficial][S4][S5, unofficial].

## Shared principles
The methods share a foundation in 3D Gaussian primitives defined by mean $\mu$, covariance $\Sigma$ (derived from scale $s$ and rotation $q$), opacity $\alpha$, and color/radiance parameters. Rendering involves projecting these 3D primitives to 2D screen space, typically via affine approximation of the projective transformation. The core mathematical operation is the evaluation of the Gaussian density function $P(x|\mu, \Sigma) = \exp\left(-\frac{1}{2}(x - \mu)^\top \Sigma^{-1} (x - \mu)\right)$ and alpha blending. Acceleration often relies on tiling the image plane and sorting primitives by depth.

## Subtopics

### [RoofGS](9830-roofgs.md)
RoofGS is an end-to-end acceleration method for 3D Gaussian Splatting (3DGS) that optimizes the rendering pipeline by aligning software strategies with hardware bottlenecks identified via the Roofline model. It solves the problem of uncoordinated optimization by applying memory-centric reductions to bandwidth-limited front-end stages and compute-centric instruction-level parallelism (ILP) to compute-bound rasterization stages. It sets itself apart from generic optimization by explicitly using the Roofline "knee" to dictate whether a stage should prioritize memory traffic reduction or arithmetic throughput. See [RoofGS](9830-roofgs.md).

### [Tile-Based Comparison-Free Sorting](9991-tile-based-comparison-free-sorting.md)
Tile-Based Comparison-Free Sorting restricts depth sorting operations to individual image tiles to avoid global synchronization, reduce hardware complexity, and achieve fixed latency per output. Unlike full-scene sorting methods that incur high memory overhead and variable latency due to global scans and prefix sums, this method processes Gaussians locally within tiles using a deterministic, comparator-free algorithm. It is specifically designed for hardware accelerators where predictable scheduling and low power consumption are critical, such as in AR/VR rendering pipelines. See [Tile-Based Comparison-Free Sorting](9991-tile-based-comparison-free-sorting.md).

### [Distributed Training and Sharding](15108-distributed-training-and-sharding.md)
Distributed training and sharding partition the global set of 3D Gaussians $\mathcal{G}$ and optimizer states across $M$ GPUs to enable city-scale optimization that exceeds single-GPU memory and compute limits. Unlike spatial block partitioning, which suffers from cross-block visibility waste, imbalanced shards, and expensive merge steps, BlitzGS uses index-parity sharding combined with all-to-all communication to route Gaussians to responsible tiles, ensuring balanced loads without final merging. See [Distributed Training and Sharding](15108-distributed-training-and-sharding.md).

### [Cache-based Lazy Memory Management](17592-cache-based-lazy-memory-management.md)
Cache-based Lazy Memory Management (CLM) is a memory offloading technique that enables the training of large-scale 3D Gaussian Splatting (3DGS) scenes on a single consumer-grade GPU by keeping the majority of Gaussians in CPU memory and loading them only when necessary. It exploits the inherent sparsity of 3DGS memory access patterns, where each training iteration accesses only a small subset of the scene's Gaussians, to minimize GPU memory usage while hiding CPU-GPU communication overhead through pipelining. Unlike naive offloading strategies that load all Gaussians to the GPU, CLM reduces the memory footprint to the active subset and overlaps communication with computation to maintain performance. See [Cache-based Lazy Memory Management](17592-cache-based-lazy-memory-management.md).

### [Cache-Less Memory (CLM)](17594-cache-less-memory-clm.md)
Cache-Less Memory (CLM) is a training and rendering system for 3D Gaussian Splatting (3DGS) that enables large or highly detailed scenes to be processed on a single consumer-grade GPU by offloading Gaussian parameters and optimizer computation to the CPU. It solves the GPU memory capacity bottleneck inherent in standard 3DGS by leveraging attribute-wise offloading, microbatch pipelining, and spatial locality to minimize GPU-CPU communication overhead. Unlike [Cache-based Lazy Memory Management](17592-cache-based-lazy-memory-management.md), which relies on caching strategies for memory reuse, CLM explicitly partitions attributes between CPU and GPU memory and uses precise caching of intersecting Gaussians across microbatches to hide communication latency. See [Cache-Less Memory (CLM)](17594-cache-less-memory-clm.md).

### Optimization Strategy
- **Step:** Optimize static Gaussians for the initial 3000 iterations as a warm-up phase, then jointly optimize both the Gaussians and the deformation field [S1, unofficial].
- **Formula:** Total loss $L = L_{color} + \lambda_1 \cdot L_{scales}$, where $L_{color}$ is the color loss and $\lambda_1$ is a weighting factor [S1, unofficial].
- **Parameter:** $\lambda_1$ (weight for scale loss) is set to 0.1; $\lambda_v$ (weight for another loss term) is set to 0.2 [S1, unofficial].

### Background Color Optimization
- **Definition:** Changing the default white background (RGB 1.0) to a gray value to improve training speed while maintaining rendering quality [S2, unofficial].
- **Parameter:** Background value `bg` (three same values for RGB channels) has an optimal range of $0.3 \le bg \le 0.5$ [S2, unofficial].
- **Pitfall:** Extreme values may negatively impact learning rate, training loss, and PSNR states [S2, unofficial].
- **Number:** On the truck dataset with 500 training steps, setting $bg=0.4$ reduces pc time by approximately 21.85% compared to the default white background [S2, unofficial].

### Mobile-GS Rendering
- **Definition:** A sorting-free rendering method that uses a transmittance proxy enriched with view-dependent modulation [S3, unofficial].
- **Formula:** Pixel color $C = (1 - T) \sum_{i=1}^N \frac{c_i \alpha_i + T c_i b_g}{\sum_{i=1}^N \alpha_i w_i} + T c_i b_g$. Weight $w_i = \phi_i^2 + \frac{\phi_i}{d_i^2} + \exp\left(\frac{x_{max}}{d_i}\right)$. $T$ is transmittance, $c_i$ is color, $\alpha_i$ is opacity, $b_g$ is background color, $d_i$ is depth, $\phi_i$ is auxiliary feature from MLP, $x_{max}$ is a constant [S3, unofficial].
- **Comparison:** Unlike SortFreeGS which uses Gaussian depth but not scale, Mobile-GS exploits both depth and scale attributes to compute importance weight, reflecting that farther Gaussians have lower contribution and larger Gaussians provide more meaningful evidence [S3, unofficial]. Unlike GES which uses a two-stage rendering pipeline (depth image then filtering), Mobile-GS is single-stage and better suited for mobile deployment [S3, unofficial].

### GEMM-GS
- **Definition:** An acceleration approach for 3D Gaussian Splatting that utilizes Tensor Cores on GPUs by reformulating the blending process into a GEMM-compatible form [S4].
- **Step:** Transform the conventional 3DGS blending process into a GEMM-style formulation equivalently to leverage Tensor Cores; develop a CUDA kernel implementing the transformed blending process, designed as a three-stage double-buffered pipeline with asynchronous memory copy to overlap computation and memory access [S4].
- **Parameter:** Tile size is 16x16 pixels; thread block size is 256 threads [S4].
- **Layout:** Gaussian features computed in preprocessing include depth $d$ and RGB color $c$ [S4].
- **Number:** GEMM-GS achieves an average 1.42× speedup over vanilla 3DGS implementation; provides an additional 1.47× speedup when combined with existing acceleration approaches [S4].
- **Comparison:** GEMM-GS is orthogonal to existing acceleration methods (compression-based or preprocessing-based), allowing it to provide additional speedup when combined with them [S4].

### Data Placement at Scale
- **Definition:** Strategies to manage training storage of Gaussian parameters, gradients, optimizer arrays, and rasterization intermediates, especially when exceeding GPU capacity [S5, unofficial].
- **Comparison:** gsplat reduces memory use through its CUDA and PyTorch implementation [S5, unofficial].

### Mixed Parallelism for 3DGS
- **Step:** Distribute Gaussian transformation forward computations Gaussian-wise; distribute Render Backward and Loss Backward computations pixel-wise, similar to Render Forward; save independent states (transformed states, gradients, optimizer states, parameters) for each Gaussian on the GPU that contains their parameters; manage activation states (significant Z-buffers, auxiliary buffers for sorting, loss intermediate activations) pixel-wise along with the image distribution; perform densification (clone, split, prune) locally on the GPU that stores the Gaussians, as it is based on their independent variance [S6].

## Background
The acceleration of 3D Gaussian Splatting has evolved from basic rasterization optimizations to complex hardware-aware strategies. Early work focused on sorting-free rendering and mobile deployment [S3, unofficial], followed by leveraging modern GPU Tensor Cores through GEMM reformulation [S4]. As scene scales increased, memory management became critical, leading to cache-based lazy memory management [S1, unofficial] and cache-less memory systems [S1, unofficial] that offload data to CPU memory. Distributed training methods [S2, unofficial] and mixed parallelism strategies [S6] address the limitations of single-GPU setups, while data placement strategies [S5, unofficial] optimize storage and transfer efficiency.
