# Sparse SH Order Increment

Also called: SOI, Sparse Order Increment of SH

## Overview
Sparse SH Order Increment (SOI) is a training-time optimization strategy for 3D Gaussian Splatting that reduces GPU memory consumption and storage overhead by dynamically increasing the Spherical Harmonics (SH) order only for Gaussians that exhibit significant view-dependent color variation [S1]. Unlike standard 3D Gaussian Splatting which initializes all Gaussians with full SH coefficients (typically order 3), SOI starts with SH order 0 and selectively promotes specific Gaussians to higher orders based on their rendering error, thereby eliminating redundant high-frequency coefficients for static or low-frequency regions [S1]. This method is distinct from random selection strategies for SH promotion, as it guarantees better rendering quality for the same memory budget by prioritizing Gaussians with the highest color deviation from ground truth [S1].

## How it works
**Inputs and Outputs**
*   **Input:** A set of 3D Gaussians $\mathcal{G}$, each defined by position, covariance, opacity, and current SH coefficients; a set of $N$ training images with ground truth colors $C_p^{gt}$; a sparse rate parameter $r_s$; and the current training iteration count.
*   **Output:** Updated SH orders for the Gaussians in $\mathcal{G}$, where a subset of Gaussians has their SH order incremented by one.

**Data Structures**
Each Gaussian $g_k$ maintains:
*   `sh_order`: Integer, current SH order (starts at 0).
*   `sh_coeffs`: Array of coefficients corresponding to `sh_order`.
*   `color_diff`: Float, accumulated view-based color difference metric $d_k$.

**Numbered Steps**
1.  **Initialization:** At the start of training, set the SH order to 0 for all Gaussians in the scene [S1].
2.  **Pruning (Pre-condition):** Before executing SOI, perform Gaussian pruning to remove redundant primitives. This step minimizes GPU memory overhead and ensures that only dominant Gaussians are considered for SH promotion [S1].
3.  **Color Difference Calculation:** For each Gaussian $g_k$, calculate the view-based color difference $d_k$ across all training views. The metric is defined as:
    $$ d_k = \frac{1}{N \cdot H \cdot W} \sum_{p=1}^{N \cdot H \cdot W} \mathbb{1}(k \in \mathcal{N}_p) \cdot w_k^p \cdot |C_p - C_p^{gt}| $$
    Where:
    *   $N$ is the number of training images.
    *   $H$ and $W$ are the image height and width.
    *   The sum iterates over all pixels $p$ in the dataset.
    *   $\mathbb{1}(k \in \mathcal{N}_p)$ is an indicator function that equals 1 if Gaussian $k$ overlaps pixel $p$ (i.e., contributes to the pixel's color), and 0 otherwise.
    *   $w_k^p$ is the contribution weight of Gaussian $k$ to pixel $p$ during alpha blending.
    *   $C_p$ is the rendered color at pixel $p$.
    *   $C_p^{gt}$ is the ground truth color at pixel $p$.
    *   $|C_p - C_p^{gt}|$ is the absolute difference between rendered and ground truth colors [S1].
4.  **Sorting:** Sort all Gaussians in descending order based on their calculated $d_k$ values. Gaussians with higher $d_k$ values exhibit greater view-dependent color variation and thus have a higher demand for higher-order SH representation [S1].
5.  **Selection:** Select the top $r_s$ percentage of Gaussians from the sorted list. The parameter $r_s$ (sparse rate) controls the fraction of Gaussians to be promoted. A typical value is $r_s = 0.2$ (20%) [S1].
6.  **Increment:** Increment the SH order by one for the selected Gaussians. This involves allocating memory for the new SH coefficients and initializing them (typically to zero or inheriting from previous lower-order terms if applicable, though the source specifies simple incrementation) [S1].
7.  **Iteration:** Repeat steps 2-6 every several iterations. In standard implementations for small scenes (30,000 total iterations), SOI is executed at iterations 16,000, 17,000, and 18,000. For large scenes (60,000 total iterations), the steps are scaled proportionately [S1].

**Pseudocode**
```python
def sparse_sh_order_increment(gaussians, training_views, rs, current_iteration, total_iterations):
    """
    Performs Sparse SH Order Increment for 3D Gaussians.
    
    Args:
        gaussians: List of Gaussian objects, each with attributes:
                   - sh_order: int
                   - color_diff: float
        training_views: List of training view data, including:
                        - N: int (number of images)
                        - H: int (height)
                        - W: int (width)
                        - images: list of ground truth images
        rs: float, sparse rate (fraction of Gaussians to promote)
        current_iteration: int, current training step
        total_iterations: int, total training steps
        
    Returns:
        Updated list of Gaussians with potentially incremented SH orders.
    """
    
    # Step 1: Check if SOI should be executed
    # For small scenes (30k iters): 16000, 17000, 18000
    # For large scenes (60k iters): proportional steps
    # Note: Exact step calculation depends on scene scale scaling factor.
    # Assuming a scaling factor 'scale_factor' where large scenes use 2x iterations.
    # If total_iterations <= 30000:
    #     steps = [16000, 17000, 18000]
    # Else:
    #     steps = [int(16000 * scale_factor), int(17000 * scale_factor), int(18000 * scale_factor)]
    # [G] The source does not explicitly define the scaling factor formula, 
    # but states steps are "modified proportionately". We assume linear scaling.
    
    scale_factor = total_iterations / 30000.0
    if total_iterations <= 30000:
        steps = [16000, 17000, 18000]
    else:
        steps = [int(16000 * scale_factor), int(17000 * scale_factor), int(18000 * scale_factor)]
        
    if current_iteration not in steps:
        return gaussians

    # Step 2: Pruning (Pre-condition)
    # Gaussian pruning is performed to minimize GPU memory overhead.
    # [G] Assuming a function `prune_gaussians` exists as per parent context.
    gaussians = prune_gaussians(gaussians)

    # Step 3: Calculate color difference d_k for each Gaussian
    for g in gaussians:
        total_diff = 0.0
        count = 0
        for view in training_views:
            # Render the scene with current Gaussians to get C_p
            # [G] Assuming `render_scene` returns a map of pixel contributions
            # and rendered colors.
            rendered_data = render_scene(gaussians, view.camera)
            
            # Iterate over pixels
            for p in rendered_data.pixels:
                # Check if Gaussian g contributes to pixel p
                if g.id in rendered_data.pixel_contributors[p]:
                    # Get weight w_k^p
                    w_k_p = rendered_data.get_weight(g.id, p)
                    
                    # Get rendered color C_p and ground truth C_p^gt
                    C_p = rendered_data.pixel_color[p]
                    C_gt = view.gt_image[p]
                    
                    # Accumulate weighted absolute difference
                    total_diff += w_k_p * abs(C_p - C_gt)
                    count += 1
        
        # Normalize by N * H * W
        # Note: The sum in the formula is over all pixels in all images.
        # The denominator is N * H * W.
        # [G] The indicator function 1(k in N_p) ensures we only sum over pixels 
        # where the Gaussian is present. The denominator remains constant.
        n_hw = view.N * view.H * view.W
        g.color_diff = total_diff / n_hw

    # Step 4: Sort Gaussians by d_k descending
    gaussians.sort(key=lambda g: g.color_diff, reverse=True)

    # Step 5: Select top r_s percentage
    num_to_promote = int(len(gaussians) * rs)
    selected_gaussians = gaussians[:num_to_promote]

    # Step 6: Increment SH order
    for g in selected_gaussians:
        g.sh_order += 1
        # [G] Allocate new SH coefficients for the new order.
        # Initialize new coefficients to zero.
        allocate_sh_coefficients(g, g.sh_order)

    return gaussians
```

**Parameters**
*   $r_s$ (Sparse Rate): The fraction of Gaussians selected to receive increased SH order. Typical value: 0.2. Higher values (e.g., 0.5) yield quality similar to full SH, proving redundancy, but 0.2 is chosen for storage efficiency [S1].
*   Iteration Steps: For 30,000 total iterations, SOI runs at 16,000, 17,000, and 18,000. For 60,000 iterations, these are scaled proportionately [S1].

**Edge Cases and Pitfalls**
*   **Memory Overflow:** If $r_s$ is too high, memory usage may exceed GPU limits, negating the benefits of SOI. The source notes that pruning must occur before SOI to mitigate this [S1].
*   **Convergence Timing:** Executing SOI too early may promote Gaussians that have not yet converged geometrically, leading to suboptimal SH coefficients. The source specifies starting after 15,500 iterations in a 30k run, ensuring initial densification and pruning have stabilized the geometry [S1].
*   **Large Scenes:** For large scenes, the iteration steps must be scaled. Failure to do so may result in insufficient training time for the promoted SH coefficients to converge [S1].

## Operating characteristics
*   **Time Complexity:** The color difference calculation requires rendering the scene for all training views for each Gaussian, which is computationally expensive. However, it is performed only 3 times during training [S1].
*   **Memory Complexity:** Significantly reduces peak GPU memory and storage compared to full SH. For example, on Mip-NeRF360, SOI with $r_s=0.2$ reduces storage to 98MB and peak GPU memory to 8.8GB, compared to 742MB and 12.8GB for full SH (vanilla 3DGS) [S1].
*   **Performance:** Improves FPS and reduces storage with negligible quality loss. On Mip-NeRF360, SOI with $r_s=0.2$ achieves SSIM 0.817, PSNR 27.38, LPIPS 0.216, FPS 218, and Storage 98MB, compared to vanilla 3DGS SSIM 0.820, PSNR 27.53, LPIPS 0.202, FPS 140, Storage 742MB [S1].
*   **Strengths:** Reduces storage and GPU memory overhead, enabling training of larger scenes. Guarantees better quality than random selection for the same $r_s$ [S1].
*   **Limitations:** Adds computational overhead during the specific SOI iterations due to the color difference calculation. Requires careful tuning of iteration steps for different scene scales [S1].

## Background
Sparse SH Order Increment was introduced in the paper "EfficientGS: Streamlining Gaussian Splatting for Large-Scale High-Resolution Scene Representation" by [S1]. The method addresses the high memory consumption of 3D Gaussian Splatting, particularly in large-scale scenes, by exploiting the redundancy in high-order SH coefficients for many Gaussians. It builds on the standard 3D Gaussian Splatting framework [S1].
