# 3D Gaussian Splatting with Feature Vectors

Also called: Feature-3DGS, LangSplat, Semantic 3DGS

## Overview
This method extends 3D Gaussian Splatting by attaching a high-dimensional feature vector $\mathbf{f}_i$ to each Gaussian primitive, enabling the rendering of semantic, language, or latent feature maps alongside color. It solves the problem of integrating 2D vision-language models (such as CLIP) into 3D representations, allowing for real-time open-vocabulary semantic segmentation and phrase grounding. It differs from standard 3D Gaussian Splatting [3D Gaussian Splatting Rendering (Software)](52-3d-gaussian-splatting-rendering-software.md) by accumulating feature vectors instead of just color, and from sibling methods like [LSeg Feature Encoding](12078-lseg-feature-encoding.md) by relying on the direct differentiable alpha-blending of learned or distilled features without explicit 2D-to-3D lifting networks during inference.

## How it works
**Inputs and Outputs:**
*   **Input:** A set of 3D Gaussians $\mathcal{G} = \{g_i\}$, where each $g_i$ is defined by position $\mathbf{x}_i$, covariance $\mathbf{\Sigma}_i$, opacity $\alpha_i$, and a feature vector $\mathbf{f}_i \in \mathbb{R}^d$ (where $d$ is the feature dimension, e.g., 512 for CLIP). Camera parameters (view/projection matrices) and pixel grid coordinates.
*   **Output:** A 2D feature map $\mathbf{F} \in \mathbb{R}^{H \times W \times d}$, where each pixel $p$ contains the accumulated feature vector $\mathbf{F}(p)$.

**Data Structures:**
*   **Gaussian Attributes:** Each Gaussian stores $\mathbf{f}_i$ as a dense vector. In implementation, this is typically stored as a tensor of shape $(N, d)$, where $N$ is the number of Gaussians.
*   **Sorting:** Gaussians overlapping a pixel must be sorted front-to-back based on depth along the camera ray to ensure correct alpha-blending order.

**Algorithm:**
For each pixel $p$ in the image:
1.  Identify the set of Gaussians $\mathcal{O}_p$ that project onto pixel $p$.
2.  Sort $\mathcal{O}_p$ such that $i=1$ is the closest to the camera and $i=|\mathcal{O}_p|$ is the farthest.
3.  Compute the accumulated feature vector $\mathbf{F}(p)$ using the differentiable alpha-blending formula [S1, unofficial]:

$$
\mathbf{F}(p) = \sum_{i \in \mathcal{O}_p} \mathbf{f}_i \cdot \alpha_i \cdot \prod_{j=1}^{i-1} (1 - \alpha_j)
$$

    *   $\mathbf{f}_i$: The feature vector of the $i$-th Gaussian.
    *   $\alpha_i$: The opacity of the $i$-th Gaussian.
    *   $\prod_{j=1}^{i-1} (1 - \alpha_j)$: The transmittance from all preceding Gaussians $j < i$.
    *   If $\mathcal{O}_p$ is empty, $\mathbf{F}(p) = \mathbf{0}$.

**Pseudocode:**
```python
def render_feature_map(gaussians, camera, image_width, image_height):
    """
    Render a feature map from 3D Gaussians using alpha blending.
    
    Args:
        gaussians: List of Gaussian objects with attributes:
                   - pos: (N, 3) position
                   - cov: (N, 3, 3) covariance matrix
                   - alpha: (N,) opacity
                   - feature: (N, d) feature vector
        camera: Camera object with view and projection matrices.
        image_width: int
        image_height: int
        
    Returns:
        feature_map: (H, W, d) tensor
    """
    N = gaussians.pos.shape[0]
    d = gaussians.feature.shape[1]
    feature_map = torch.zeros((image_height, image_width, d), device=gaussians.feature.device)
    
    # 1. Project Gaussians to 2D and determine overlap
    # This step involves projecting 3D positions to screen space,
    # computing 2D covariance via Jacobian of projection, and
    # determining bounding boxes for each Gaussian.
    # For each pixel, we need the list of overlapping Gaussians sorted by depth.
    # Implementation detail: Use a rasterizer kernel or spatial hashing.
    # Let's assume we have a function `get_pixel_gaussians` that returns
    # a list of lists: pixel_gaussians[y, x] = [(gaussian_index, depth), ...]
    # sorted by depth ascending.
    
    pixel_gaussians = rasterize_gaussians(gaussians, camera, image_width, image_height)
    
    for y in range(image_height):
        for x in range(image_width):
            overlapping = pixel_gaussians[y, x]
            if not overlapping:
                continue
                
            accumulated_transmittance = 1.0
            current_feature = torch.zeros(d, device=gaussians.feature.device)
            
            for idx, depth in overlapping:
                alpha = gaussians.alpha[idx]
                feature_vec = gaussians.feature[idx]
                
                # Contribution of this Gaussian
                weight = alpha * accumulated_transmittance
                current_feature += feature_vec * weight
                
                # Update transmittance for next Gaussian
                accumulated_transmittance *= (1.0 - alpha)
                
                # Optimization: If transmittance is negligible, break
                if accumulated_transmittance < 1e-4:
                    break
            
            feature_map[y, x] = current_feature
            
    return feature_map
```

**Parameters:**
*   **Feature Dimension ($d$):** Typically 512 (matching CLIP ViT-L/14) or 768. Not given in the sources for other dimensions.
*   **Opacity Threshold:** Not given in the sources. [G] A small epsilon (e.g., $10^{-6}$) is often added to alpha to prevent division by zero in gradient computation, though not present in the forward formula.

**Edge Cases and Pitfalls:**
*   **Precision:** Accumulating high-dimensional vectors can suffer from floating-point precision issues if many Gaussians contribute with small weights. [G] Using `float32` is standard; `float64` may be needed for very large scenes but impacts performance.
*   **Degenerate Input:** If a Gaussian has $\alpha_i = 0$, it contributes nothing and can be skipped. If $\alpha_i = 1$, it occludes all subsequent Gaussians completely.
*   **Boundary Conditions:** Gaussians partially outside the image plane must be clipped or ignored.

## Subtopics

### Scale-Aware Semantic Feature Gating
A mechanism to modulate rendered semantic features based on the scale of the Gaussians, using learned or fixed gate vectors derived from sampled scales [S2, unofficial]. It is chosen when semantic consistency needs to be preserved across different levels of detail or when scale-dependent features are required. It differs from standard feature rendering by introducing a multiplicative gate vector $\mathbf{g}$ conditioned on scale [S2, unofficial].
**Steps:**
1.  Map the distribution of sampled scales to a Gaussian distribution using a transformation function `self.q_trans(sampled_scales)` [S2, unofficial].
2.  Determine the gating method based on `scale_aware_dim`:
    *   If `scale_aware_dim <= 0` or `scale_aware_dim >= 32`: Compute gates by passing sampled scales through a learnable layer: `gates = self.scale_gate(sampled_scales.unsqueeze(-1))` [S2, unofficial].
    *   Otherwise: Discretize scales to integers: `int_sampled_scales = ((1 - sampled_scales.squeeze()) * scale_aware_dim).long()`, then lookup pre-computed gates: `gates = self.fixed_scale_gate[int_sampled_scales].detach()` [S2, unofficial].
3.  Repeat rendered features for each sampled scale: `feature_with_scale = rendered_features.unsqueeze(0).repeat([sampled_scales.shape[0], 1, 1, 1])` [S2, unofficial].
4.  Multiply features by gate vectors: `feature_with_scale = feature_with_scale * gates.unsqueeze(-1).unsqueeze(-1)` [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N \cdot d)$ per pixel, where $N$ is the number of overlapping Gaussians and $d$ is the feature dimension. The rasterization cost is dominated by the sorting and blending steps, similar to color rendering but with higher memory bandwidth usage due to larger feature vectors.
*   **Memory Complexity:** $O(N \cdot d)$ to store feature vectors. For $d=512$, this is significantly larger than color (3 channels).
*   **Measured Performance:** Not given in the sources. [G] Real-time performance (30+ FPS) is achievable on modern GPUs if the rasterizer is optimized (e.g., using CUDA kernels), as demonstrated by Feature-3DGS and LangSplat.
*   **Strengths:** Enables real-time open-vocabulary segmentation; leverages existing 3DGS efficiency; supports language-guided editing.
*   **Limitations:** High memory usage for large $d$; feature quality depends on the 2D model used for distillation; occlusion handling is purely depth-based, which may be inaccurate for transparent or semi-transparent objects.
*   **When to use:** When semantic understanding or language interaction is required in a 3D scene.
*   **When not to use:** When memory is constrained or only geometric/color rendering is needed.

## Background
The method was pioneered by Feature-3DGS [102] and LangSplat [103], which demonstrated that the speed of 3DGS rasterization makes it an ideal platform for distilling 2D vision-model features into a 3D representation [S1, unofficial]. Language Embedded 3D Gaussians [104] expanded this to full scene understanding, encoding object-level embeddings for phrase grounding. Subsequent works like SplatTalk [105] and 3D Vision-Language GS [106] further extended these capabilities [S1, unofficial]. The approach builds on the differentiable alpha-blending principles established in [3D Gaussian Splatting Rendering (Software)](52-3d-gaussian-splatting-rendering-software.md).
