# Distributed Batched Rendering Loop

Also called: Distributed 3DGS Rendering Loop

## Overview
A distributed rendering pipeline that processes camera views in batches, divides workload across multiple GPUs, preprocesses 3D Gaussian Splatting data, performs all-to-all communication, renders, and aggregates results across ranks [S1, unofficial]. It sets itself apart from single-GPU rendering by enabling high-resolution and large-scale 3D reconstruction tasks that exceed single GPU memory capacity, and from non-batched distributed systems by supporting parallel processing of multiple camera views to improve GPU utilization [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** A dataset of camera poses and intrinsics, a set of 3D Gaussians (position, covariance, opacity, spherical harmonics coefficients), a rendering pipeline configuration, and background color.
*   **Outputs:** Rendered images for the batched cameras, aggregated across distributed ranks.

**Data Structures:**
*   `batched_screenspace_pkg`: A data structure holding preprocessed 3DGS data and screenspace packages for distributed rendering. It is passed to the rendering function `render_final` [S1, unofficial].
*   `gpuid2tasks`: A dictionary or mapping structure assigning rendering tasks to specific GPU IDs [S1, unofficial].
*   `compute_locally`: A 2D boolean array (used in Pixel Block Scheduling variant) indicating whether the pixel block at the $i$-th row and $j$-th column should be computed by the local GPU [S2].

**Parameters:**
*   `args.bsz`: Batch size for camera processing, controlling how many views are processed per iteration [S1, unofficial].
*   `args.sample_freq`: Sampling frequency for saving renders. If `!= -1`, only saves every `args.sample_freq`-th image [S1, unofficial].
*   `args.generate_num`: Maximum number of images to generate before breaking the loop [S1, unofficial].
*   Block size: 16x16 pixels (used in Pixel Block Scheduling variant) [S2].

**Steps:**
1.  Iterate over cameras in batches of size `args.bsz`: `for idx in range(1, num_cameras + 1, args.bsz):` [S1, unofficial].
2.  Determine the number of cameras to load in the current batch: `num_camera_to_load = min(args.bsz, num_cameras - idx + 1)` [S1, unofficial].
3.  Fetch the next batch of cameras: `batched_cameras = dataset.get_batched_cameras(num_camera_to_load)` [S1, unofficial].
4.  Compute workload division and GPU-to-task mapping: `batched_strategies, gpuid2tasks = start_strategy_final(batched_cameras, strategy_history)` [S1, unofficial].
5.  Transfer camera data from CPU to all GPUs according to the division strategy: `load_camera_from_cpu_to_all_gpu_for_eval(batched_cameras, batched_strategies, gpuid2tasks)` [S1, unofficial].
6.  Preprocess 3DGS data and execute all-to-all communication across GPUs: `batched_screenspace_pkg = distributed_preprocess3dgs_and_all2all_final(batched_cameras, gaussians, pipeline, background, batched_strategies=batched_strategies, mode="test")` [S1, unofficial].
7.  Render the batched images: `batched_image, _ = render_final(batched_screenspace_pkg, batched_strategies)` [S1, unofficial].
8.  Aggregate rendered images across distributed ranks using sum reduction: `if utils.DEFAULT_GROUP.size() > 1: torch.distributed.all_reduce(image, op=dist.ReduceOp.SUM, group=utils.DEFAULT_GROUP)` [S1, unofficial].
9.  Clamp pixel values to valid range and save: `image = torch.clamp(image, 0.0, 1.0)` followed by `torchvision.utils.save_image(image, ...)` [S1, unofficial].

**Pseudocode:**
```python
# Initialize distributed environment and load dataset/gaussians
# Assume utils.DEFAULT_GROUP is initialized for distributed communication

num_cameras = len(dataset)
strategy_history = [] # Track previous strategies for load balancing

for idx in range(1, num_cameras + 1, args.bsz):
    # Calculate number of cameras in this batch
    num_camera_to_load = min(args.bsz, num_cameras - idx + 1)
    
    # Fetch batched cameras
    batched_cameras = dataset.get_batched_cameras(num_camera_to_load)
    
    # Compute workload division and GPU-to-task mapping
    # This step likely involves dynamic load balancing based on scene complexity
    batched_strategies, gpuid2tasks = start_strategy_final(batched_cameras, strategy_history)
    
    # Transfer camera data from CPU to all GPUs
    load_camera_from_cpu_to_all_gpu_for_eval(batched_cameras, batched_strategies, gpuid2tasks)
    
    # Preprocess 3DGS data and perform all-to-all communication
    # This distributes Gaussians to GPUs based on which pixels they affect
    batched_screenspace_pkg = distributed_preprocess3dgs_and_all2all_final(
        batched_cameras, 
        gaussians, 
        pipeline, 
        background, 
        batched_strategies=batched_strategies, 
        mode="test"
    )
    
    # Render the batched images
    batched_image, _ = render_final(batched_screenspace_pkg, batched_strategies)
    
    # Aggregate results across ranks
    if utils.DEFAULT_GROUP.size() > 1:
        # Sum reduction to aggregate contributions from different GPU partitions
        torch.distributed.all_reduce(batched_image, op=dist.ReduceOp.SUM, group=utils.DEFAULT_GROUP)
    
    # Clamp and save if needed
    image = torch.clamp(batched_image, 0.0, 1.0)
    
    # Save images based on sampling frequency
    if args.sample_freq != -1 and (idx % args.sample_freq == 0 or idx == num_cameras):
        torchvision.utils.save_image(image, f"render_{idx}.png")
        
    # Update strategy history for next iteration
    strategy_history.append(batched_strategies)
    
    # Break if maximum number of images generated
    if args.generate_num is not None and (idx // args.bsz) >= args.generate_num:
        break
```

**Edge Cases and Pitfalls:**
*   **Memory Limits:** Single GPU memory capacity limits the number of Gaussians that can be processed. Distributed rendering mitigates this by partitioning parameters [S1, unofficial].
*   **Communication Overhead:** All-to-all communication is required to transfer Gaussians to the relevant pixel partitions. Sparse communication is used to minimize this [S1, unofficial].
*   **Load Imbalance:** Different Gaussians affect different subsets of pixels. Dynamic load balancing is necessary to ensure even workload distribution across GPUs [S1, unofficial].
*   **Precision:** Pixel values must be clamped to [0.0, 1.0] after aggregation to ensure valid image output [S1, unofficial].

## Subtopics

### Pixel Block Scheduling
A load balancing strategy for distributed 3D Gaussian Splatting training that groups pixels into 16x16 blocks to reduce scheduler overhead while maintaining workload balance across GPUs [S2]. It organizes all pixels from all images in a batch into a single row, divides the row into 16x16 pixel blocks, and allocates these blocks to GPUs instead of individual pixels [S2]. After scheduling, it generates a 2D boolean array `compute_locally[i][j]` indicating whether the pixel block at the $i$-th row and $j$-th column should be computed by the local GPU, and renders only the pixels within the blocks where `compute_locally` is true [S2]. This approach trades off scheduler overhead against uneven workloads due to additional blocks [S2].

## Operating characteristics
*   **Time Complexity:** Depends on the number of Gaussians, camera views, and GPU count. The system supports batched training using multiple views, which can improve throughput compared to processing one view at a time [S1, unofficial].
*   **Memory Complexity:** Scales with the number of Gaussians and the number of GPUs. By distributing 3DGS parameters, it allows handling scenes with tens of millions of Gaussians that would not fit in a single GPU's memory [S1, unofficial].
*   **Measured Performance:** On the "Rubble" dataset, distributing 40.4 million Gaussians across 16 GPUs achieved a test PSNR of 27.28, compared to 26.28 PSNR with 11.2 million Gaussians on a single GPU [S1, unofficial].
*   **Scaling:** The system improves rendering quality by scaling up the 3DGS quantity using multiple GPUs [S1, unofficial]. It supports different learning rate scaling strategies, with the simple $\sqrt{\text{batch size}}$ scaling rule identified as highly effective [S1, unofficial].
*   **Strengths:** Enables high-resolution and large-scale 3D reconstruction; improves rendering quality by allowing more Gaussians; supports batched training for better GPU utilization.
*   **Limitations:** Requires complex distributed communication (all-to-all); load balancing is non-trivial due to the sparse and changing nature of Gaussian-pixel interactions; scheduler overhead can be significant if granularity is too fine.
*   **When to use:** Large-scale 3D reconstruction tasks that exceed single GPU memory capacity; scenarios where high rendering quality is prioritized over single-GPU simplicity.
*   **When not to use:** Small-scale scenes that fit in a single GPU; real-time applications where distributed communication overhead is prohibitive.

## Background
3D Gaussian Splatting (3DGS) is gaining popularity for 3D reconstruction due to its superior visual quality and rendering speed [S1, unofficial]. However, training is traditionally done on a single GPU, limiting its ability to handle high-resolution and large-scale tasks [S1, unofficial]. Grendel, a distributed system for 3DGS, was built to partition parameters and parallelize computation across multiple GPUs [S1, unofficial]. It relies on sparse all-to-all communication and dynamic load balancing to manage the sparse and changing subset of pixels affected by each Gaussian [S1, unofficial]. The system was developed by researchers at NYU Systems [S1, unofficial].
