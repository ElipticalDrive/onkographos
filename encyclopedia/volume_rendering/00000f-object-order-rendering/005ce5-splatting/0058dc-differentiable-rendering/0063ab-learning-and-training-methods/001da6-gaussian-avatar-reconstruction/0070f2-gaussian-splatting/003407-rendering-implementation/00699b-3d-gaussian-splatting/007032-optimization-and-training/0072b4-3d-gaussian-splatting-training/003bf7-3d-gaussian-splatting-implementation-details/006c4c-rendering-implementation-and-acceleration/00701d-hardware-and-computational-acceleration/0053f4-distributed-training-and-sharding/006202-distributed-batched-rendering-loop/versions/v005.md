# Distributed Batched Rendering Loop

Also called: Distributed 3DGS Rendering Loop

## Overview
A distributed rendering pipeline that processes camera views in batches, dividing the workload across multiple GPUs to enable high-resolution and large-scale 3D Gaussian Splatting (3DGS) training and inference that exceeds single-GPU memory limits [S1, unofficial]. It differs from single-GPU rendering by introducing a dynamic strategy phase that maps camera views to GPU tasks, followed by sparse all-to-all communication to distribute Gaussian primitives to the GPUs responsible for rendering specific pixel regions [S1, unofficial]. Unlike methods that process one view at a time, this loop supports batched training using multiple views, improving GPU utilization and scaling rendering quality by increasing the total quantity of Gaussians [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** A dataset of camera poses (`dataset`), the global set of 3D Gaussian primitives (`gaussians`), a rendering pipeline configuration (`pipeline`), a background color tensor (`background`), and configuration arguments (`args`).
*   **Outputs:** Rendered images (`batched_image`) aggregated across all distributed ranks.

**Data Structures:**
*   `batched_cameras`: A list or tensor of camera parameters (extrinsics, intrinsics) for the current batch.
*   `batched_strategies`: A data structure defining the partitioning of work (which Gaussians and which pixels are handled by which GPU) for the current batch.
*   `gpuid2tasks`: A mapping from GPU ID to the specific rendering tasks (pixel blocks or camera views) assigned to that GPU.
*   `batched_screenspace_pkg`: A preprocessed data structure holding the subset of 3DGS data and screen-space packages required for rendering, distributed across GPUs.
*   `compute_locally`: A 2D boolean array (used in Pixel Block Scheduling) indicating whether a specific pixel block should be computed by the local GPU.

**Parameters:**
*   `args.bsz`: Batch size for camera processing. Controls how many views are processed per iteration. Typical values depend on GPU memory and scene complexity [S1, unofficial].
*   `args.sample_freq`: Sampling frequency for saving renders. If not `-1`, only saves every `args.sample_freq`-th image [S1, unofficial].
*   `args.generate_num`: Maximum number of images to generate before breaking the loop [S1, unofficial].

**Steps:**
1.  **Iterate over cameras:** Loop through the dataset in chunks of size `args.bsz`.
2.  **Fetch batch:** Retrieve the next batch of camera parameters.
3.  **Compute strategy:** Determine the workload division and GPU-to-task mapping based on the current batch and historical strategy data. This involves calculating which Gaussians need to be communicated to which GPUs to render the assigned pixels [S1, unofficial].
4.  **Transfer camera data:** Move the camera parameters from CPU memory to all GPUs according to the computed strategy [S1, unofficial].
5.  **Preprocess and Communicate:** Preprocess the 3DGS data for the batch and execute sparse all-to-all communication across GPUs. This step transfers the relevant Gaussian primitives to the GPUs that need them for rendering the assigned pixel regions [S1, unofficial].
6.  **Render:** Execute the rendering kernel on each GPU using the locally available Gaussians and camera parameters.
7.  **Aggregate:** If distributed across multiple ranks, perform a sum reduction (`torch.distributed.all_reduce`) to aggregate the rendered images from all GPUs into a single result [S1, unofficial].
8.  **Post-process:** Clamp pixel values to the range $[0.0, 1.0]$ and save the image if the sampling frequency condition is met [S1, unofficial].

**Pseudocode:**
```python
import torch
import torch.distributed as dist
import torchvision.utils

# Assume utils.DEFAULT_GROUP is the initialized distributed group
# Assume dataset, gaussians, pipeline, background are initialized globally or passed

num_cameras = len(dataset)
idx = 1

while idx <= num_cameras:
    # 1. Determine batch size for this iteration
    num_camera_to_load = min(args.bsz, num_cameras - idx + 1)
    
    # 2. Fetch batch of cameras
    batched_cameras = dataset.get_batched_cameras(num_camera_to_load)
    
    # 3. Compute workload division and GPU-to-task mapping
    # This function likely uses heuristic or learned strategies to balance load
    batched_strategies, gpuid2tasks = start_strategy_final(batched_cameras, strategy_history)
    
    # 4. Transfer camera data from CPU to all GPUs
    load_camera_from_cpu_to_all_gpu_for_eval(batched_cameras, batched_strategies, gpuid2tasks)
    
    # 5. Preprocess 3DGS data and execute all-to-all communication
    # This distributes the relevant Gaussians to the GPUs responsible for specific pixel regions
    batched_screenspace_pkg = distributed_preprocess3dgs_and_all2all_final(
        batched_cameras, 
        gaussians, 
        pipeline, 
        background, 
        batched_strategies=batched_strategies, 
        mode="test"
    )
    
    # 6. Render the batched images
    batched_image, _ = render_final(batched_screenspace_pkg, batched_strategies)
    
    # 7. Aggregate rendered images across distributed ranks
    if utils.DEFAULT_GROUP.size() > 1:
        # Sum reduction to combine partial renders from different GPUs
        torch.distributed.all_reduce(batched_image, op=dist.ReduceOp.SUM, group=utils.DEFAULT_GROUP)
    
    # 8. Clamp and save
    image = torch.clamp(batched_image, 0.0, 1.0)
    
    # Check if we should save this image based on sampling frequency
    if args.sample_freq != -1 and (idx % args.sample_freq == 0 or idx == num_cameras):
        torchvision.utils.save_image(image, f"render_{idx}.png")
    
    # Check if we have generated enough images
    if args.generate_num != -1 and (idx // args.bsz) >= args.generate_num:
        break
        
    idx += num_camera_to_load
```

**Edge Cases and Pitfalls:**
*   **Communication Overhead:** The all-to-all communication volume depends on the sparsity of Gaussian-pixel interactions. Inefficient strategies can lead to excessive data transfer, negating the benefits of parallelization [S1, unofficial].
*   **Load Imbalance:** Gaussians affect a small and changing subset of pixels. Static partitioning can lead to significant load imbalance. Dynamic strategies are required to balance the number of Gaussians and pixels per GPU [S1, unofficial].
*   **Memory Limits:** The primary motivation is to overcome single-GPU memory limits. However, the distributed system must still manage the total memory footprint of Gaussians and intermediate buffers across all GPUs [S1, unofficial].
*   **Precision:** Clamping to $[0.0, 1.0]$ is necessary after aggregation to handle potential floating-point inaccuracies or out-of-bounds values from blending [S1, unofficial].

## Subtopics

### Pixel Block Scheduling
A load balancing strategy for distributed 3D Gaussian Splatting training that groups pixels into 16x16 blocks to reduce scheduler overhead while maintaining workload balance across GPUs [S2]. Instead of scheduling individual pixels, which incurs high overhead, or large fixed regions, which may lead to imbalance, this method organizes all pixels from all images in a batch into a single row, divides it into 16x16 blocks, and allocates these blocks to GPUs [S2]. After scheduling, a 2D boolean array `compute_locally[i][j]` is generated, indicating whether the pixel block at the i-th row and j-th column should be computed by the local GPU. Rendering is then restricted to pixels within blocks where `compute_locally` is true [S2]. The block size of 16x16 represents a trade-off between scheduler overhead and uneven workloads due to additional blocks [S2].

## Operating characteristics
*   **Time Complexity:** Dominated by the rendering step and the all-to-all communication. The communication volume is sparse, depending on the number of Gaussians affecting the rendered pixels [S1, unofficial].
*   **Memory Complexity:** Scales with the total number of Gaussians distributed across GPUs, allowing for much larger scenes than single-GPU methods. The memory per GPU is reduced by partitioning the Gaussian set [S1, unofficial].
*   **Measured Performance:** On the "Rubble" dataset, distributing 40.4 million Gaussians across 16 GPUs achieved a test PSNR of 27.28, compared to 26.28 PSNR with 11.2 million Gaussians on a single GPU [S1, unofficial].
*   **Strengths:** Enables high-resolution and large-scale 3D reconstruction by bypassing single-GPU memory limits. Supports batched training, improving GPU utilization.
*   **Limitations:** Requires complex communication and synchronization. Performance is sensitive to the efficiency of the load balancing strategy.
*   **When to use:** For large-scale scenes or high-resolution rendering that exceed single-GPU memory capacity.
*   **When not to use:** For small scenes where single-GPU rendering is sufficient and faster due to lower communication overhead.

## Background
3D Gaussian Splatting (3DGS) was introduced by Kerbl et al. in 2023, offering real-time radiance field rendering with superior visual quality [S1, unofficial]. However, initial implementations were limited to single-GPU training, restricting the scale and resolution of reconstructible scenes [S1, unofficial]. Grendel, a distributed system for 3DGS, was developed to address these limitations by partitioning parameters and parallelizing computation across multiple GPUs [S1, unofficial]. It relies on sparse all-to-all communication and dynamic load balancing to efficiently distribute the workload [S1, unofficial]. The distributed batched rendering loop is a core component of such systems, enabling the processing of multiple camera views in parallel [S1, unofficial].
