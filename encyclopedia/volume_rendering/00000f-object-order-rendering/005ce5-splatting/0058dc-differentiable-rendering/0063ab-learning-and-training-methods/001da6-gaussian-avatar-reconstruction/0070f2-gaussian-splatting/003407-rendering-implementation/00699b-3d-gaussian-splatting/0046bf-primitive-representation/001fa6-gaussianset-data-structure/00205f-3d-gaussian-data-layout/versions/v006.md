# 3D Gaussian Data Layout

Also called: 3DGS Parameter Storage, Gaussian Struct Definition, GaussianModel, GaussianModel PyTorch Module

## Overview
The 3D Gaussian Data Layout defines the memory organization and parameterization of a single 3D Gaussian primitive, storing position, scale, opacity, rotation, spherical harmonics coefficients, and precomputed 3D covariance [S1, S2, unofficial]. It sets itself apart from its parent [GaussianSet Data Structure](2074-gaussianset-data-structure.md) by defining the atomic unit's internal fields rather than the container's aggregation strategy, and from its sibling [Gaussian Data Packing](3257-gaussian-data-packing.md) by focusing on the logical attribute types and their mathematical representations rather than low-level binary serialization [S1, S3, unofficial].

## How it works
### Inputs and Outputs
*   **Input:** Raw geometric data (e.g., from a point cloud or neural network) or optimized parameters [S1, S4, unofficial].
*   **Output:** A structured representation of a single Gaussian primitive ready for covariance computation or rasterization [S1, S2, unofficial].

### Data Structures
Three primary implementation layouts are documented in the sources:

1.  **Native Struct Layout:** Defined in [S2, unofficial], the `Gaussian` struct uses `nalgebra` types. It stores `position: Vector3<f32>`, `scale: Vector3<f32>`, `opacity: f32`, `rotation: Quaternion<f32>`, `sh: SVector<f32, 48>`, and `cov3d: Matrix3<f32>` [S2, unofficial].
2.  **PyTorch Tensor Layout:** Defined in [S4, unofficial], `GaussianModel` stores `_xyz (N, 3)`, `_features_dc (N, 1, 3)`, `_scaling (N, 3)`, `_rotation (N, 4)`, and `_opacity (N, 1)` [S4, unofficial].
3.  **Python Dataclass Layout:** Defined in [S1, unofficial], `GaussianPoint` stores `position`, `color`, `scale`, `opacity`, `rotation`, and `sh_coeffs` [S1, unofficial]. The `Gaussian` class in [S3, unofficial] stores `centroid`, `scale`, `rotation`, `opacity`, `feat_dc`, `feat_extra`, and `max_sh_degree` [S3, unofficial].

### Numbered Steps: Parameter Access and Conversion
1.  **Retrieve Position:** Return `_xyz` directly [S4, unofficial].
2.  **Retrieve Scale:** Compute $s = \text{clamp}(\exp(\text{\_scaling}), \text{max}=10.0)$ [S4, unofficial].
3.  **Retrieve Rotation:** Normalize the quaternion: $q = \text{normalize}(\text{\_rotation})$ [S4, unofficial].
4.  **Retrieve Opacity:** Apply sigmoid: $o = \text{sigmoid}(\text{\_opacity})$, mapping log-odds to $[0, 1]$ [S4, unofficial].
5.  **Retrieve Color:** Extract `feat_dc` from `_features_dc` [S4, unofficial]. Flatten `_features_rest` into `feat_extra` if higher degrees are stored [S4, unofficial].

### Pseudocode: Gaussian Conversion (PyTorch)
```python
import torch
import torch.nn.functional as F

class GaussianLayout:
    def __init__(self, xyz, features_dc, scaling, rotation, opacity):
        self._xyz = xyz
        self._features_dc = features_dc
        self._scaling = scaling
        self._rotation = rotation
        self._opacity = opacity

    def get_position(self):
        return self._xyz

    def get_scaling(self):
        return torch.clamp(torch.exp(self._scaling), max=10.0)

    def get_rotation(self):
        return F.normalize(self._rotation, dim=-1)

    def get_opacity(self):
        return torch.sigmoid(self._opacity)

    def get_features(self):
        return self._features_dc

    @staticmethod
    def from_list(data):
        centroid = data[0:3]
        scale = data[3:6]
        rotation = data[6:10]
        opacity = data[10]
        feat_dc = data[11:14]
        feat_extra = data[14:]
        return GaussianLayout(
            xyz=centroid,
            features_dc=feat_dc,
            scaling=scale,
            rotation=rotation,
            opacity=opacity
        )
```

### Edge Cases and Pitfalls
*   **Quaternion Normalization:** Rotations must be unit quaternions; failure to normalize `_rotation` leads to skewed scaling in the covariance matrix [S4, unofficial].
*   **Scale Clamping:** Scales are clamped at $10.0$ to prevent numerical instability during rendering [S4, unofficial].
*   **SH Degree Mismatch:** The size of `feat_extra` depends on `max_sh_degree`; `sh_dim` evaluates to 3 (DC), 12 (degree 1), 27 (degree 2), or 48 (degree 3) [S2, unofficial].
*   **Log-Space Storage:** The PyTorch layout stores raw log-scales and log-odds, requiring activation functions during access [S4, unofficial].

## Subtopics

### [Gaussian Data Structure](2273-gaussian-data-structure.md)
The Gaussian Data Structure (also known as GaussianList) is the primary in-memory container for 3D Gaussian Splatting primitives, organizing per-Gaussian attributes into column-major arrays to facilitate efficient GPU rendering and optimization. It solves the problem of managing a dynamic, large-scale set of heterogeneous geometric primitives by providing a flat, contiguous memory layout that supports batched processing. It sets itself apart from its parent [3D Gaussian Data Layout](2242-3d-gaussian-data-layout.md) by defining the specific container type (a list of arrays rather than a struct-of-arrays or array-of-structs) and from its sibling [Gaussian Data Packing](3257-gaussian-data-packing.md) by focusing on the logical attribute organization rather than low-level bit-packing or serialization.

### [Gaussian Data Packing](3257-gaussian-data-packing.md)
Gaussian Data Packing serializes 3D Gaussian Splat attributes into a fixed-width binary buffer to facilitate efficient GPU-side access during rasterization. It differs from sibling methods like [SPZ Packed Format](3926-spz-packed-format.md) by using an interleaved, texture-friendly layout with a fixed width of 8 `uint32_t` per Gaussian, rather than parallel buffers or image-based compression.

### [GeometryState Allocation](5166-geometrystate-allocation.md)
GeometryState Allocation is the method for determining the memory footprint and initializing the `GeometryState` structure required for rasterizing $P$ 3D Gaussians. It solves the problem of dynamic buffer sizing for per-primitive auxiliary data (such as depths, radii, and conic matrices) that must be allocated before the rasterization kernel executes. It is distinct from [Gaussian Data Structure](2273-gaussian-data-structure.md) (which defines the primitive's intrinsic attributes) and [Gaussian Data Packing](3257-gaussian-data-packing.md) (which handles color/feature compression), focusing solely on the transient state needed for the rendering pass.

## Operating characteristics
The native struct layout precomputes covariance to accelerate projection [S2, unofficial], while the PyTorch layout stores raw parameters requiring runtime computation [S4, unofficial]. Measured performance, scaling behavior, and hardware-specific metrics are not given in the sources.

## Background
The 3D Gaussian Data Layout originates from the 3D Gaussian Splatting (3DGS) framework. The layout evolved to support differentiable rendering by using log-space parameters for scales and opacities, ensuring gradients flow correctly through positivity constraints [S4, unofficial].
