# BlitzGS

Also called: BlitzGS: City-Scale Gaussian Splatting at Lightning Speed
## Overview
BlitzGS is a distributed 3D Gaussian Splatting (3DGS) framework designed to accelerate city-scale training by reducing the active Gaussian workload across system, model, and view levels [S1, unofficial]. It addresses the inefficiency of existing methods where every iteration preprocesses, communicates, and rasterizes an overly dense set of primitives, most of which contribute negligibly to the loss [S1, unofficial]. Unlike spatial block partitioning which incurs cross-block visibility waste and imbalanced shards, BlitzGS shards by index parity and couples this with importance-based pruning and distance-based LOD filtering to achieve nearly an order-of-magnitude speedup while maintaining high reconstruction quality [S1, unofficial].
## How it works
BlitzGS operates on a global set of 3D Gaussians $\mathcal{G}$ distributed across $M$ GPUs. The method reduces computational load by minimizing the number of Gaussians processed at each stage of the training loop.

### Inputs and Outputs
- **Inputs:** A set of calibrated images with known camera poses; a global set of 3D Gaussian primitives $\mathcal{G}$ (position, covariance, opacity, spherical harmonics coefficients).
- **Outputs:** Optimized Gaussian parameters $\mathcal{G}$ and rendered novel views.

### Data Structures
- **Shard $\mathcal{G}^{(m)}$:** Each GPU $m$ maintains a local shard of Gaussians. The size is approximately $|\mathcal{G}|/M$.
- **Optimizer State:** Each GPU maintains optimizer state (e.g., momentum, variance) for its local shard.
- **Tile Assignment:** The image plane is divided into tiles, each assigned to a specific GPU.

### Steps
1.  **System-Level Sharding (Index Parity):**
    Gaussians are assigned to GPUs based on their index parity (even/odd) rather than spatial location [S1, unofficial]. This avoids the cross-block visibility waste and shard imbalance associated with spatial partitioning [S1, unofficial]. Each GPU $m$ holds shard $\mathcal{G}^{(m)}$ and its corresponding optimizer state [S1, unofficial].

2.  **Projection:**
    Each GPU projects only its local shard $\mathcal{G}^{(m)}$ into the camera space [S1, unofficial]. This distributes the projection cost across all GPUs [S1, unofficial].

3.  **Communication (All-to-All):**
    A single cross-GPU exchange routes every projected Gaussian to the GPUs responsible for the image tiles it covers [S1, unofficial]. This ensures that each device holds a balanced, scene-wide slice of the relevant Gaussians for its assigned tiles [S1, unofficial].

4.  **Model-Level Population Control:**
    -   **Importance Scoring:** A lightweight scoring pass evaluates the importance of Gaussians [S1, unofficial]. This signal is used to reweight density control gradients [S1, unofficial].
    -   **Pruning:** Redundant Gaussians are pruned based on importance scores [S1, unofficial].
    -   **Spawn Gating:** A lightweight spawn gate withholds new Gaussian candidates predicted not to survive densification, limiting peak population [S1, unofficial].

5.  **View-Level Filtering:**
    -   **Distance-Based LOD:** A distance-based Level-of-Detail (LOD) gate drops Gaussians that are too fine for the current camera distance [S1, unofficial].
    -   **Importance Mask:** An importance-based mask skips Gaussians with negligible cross-view contribution, further trimming the active set [S1, unofficial].

6.  **Rasterization and Update:**
    Each GPU composites the pixels for its assigned tiles using the received and filtered Gaussians [S1, unofficial]. Gradients are computed and parameters are updated using the reweighted density control signals [S1, unofficial].

### Pseudocode
```python
def blitzgs_training_loop(G, cameras, M):
    # Initialization
    # G is the global set of Gaussians
    # M is the number of GPUs
    # Each GPU m gets shard G[m] based on index parity
    shards = partition_by_parity(G, M)
    
    for iteration in range(max_iterations):
        # 1. Projection (Distributed)
        projected_shards = []
        for m in range(M):
            projected_shards.append(project_gaussians(shards[m], cameras))
            
        # 2. Communication (All-to-All)
        # Route projected Gaussians to tile owners
        received_gaussians = all_to_all_routing(projected_shards, tile_assignments)
        
        # 3. Model-Level Filtering (Global or Local Importance)
        # Compute importance scores for all active Gaussians
        importance_scores = compute_importance_scores(G)
        
        # Prune redundant Gaussians
        G = prune_gaussians(G, importance_scores)
        
        # Spawn gating (simplified)
        candidates = propose_new_gaussians(G)
        surviving_candidates = spawn_gate(candidates, importance_scores)
        G = G + surviving_candidates
        
        # 4. View-Level Filtering (Per-View)
        active_sets = []
        for m in range(M):
            active_set = received_gaussians[m]
            
            # Distance-based LOD
            active_set = filter_by_distance(active_set, cameras[m].position)
            
            # Importance mask
            active_set = filter_by_importance(active_set, importance_scores)
            
            active_sets.append(active_set)
            
        # 5. Rasterization
        rendered_images = []
        for m in range(M):
            rendered_images.append(rasterize_tiles(active_sets[m], cameras[m], tile_assignments[m]))
            
        # 6. Update
        loss = compute_loss(rendered_images, ground_truth)
        gradients = compute_gradients(loss, G)
        
        # Reweight density control gradients using importance scores
        gradients = reweight_gradients(gradients, importance_scores)
        
        G = update_parameters(G, gradients)
        
    return G
```

### Parameters
-   **Hardware:** 4x NVIDIA A6000 GPUs [S1, unofficial].
-   **Sharding Strategy:** Index parity (even/odd) [S1, unofficial].
-   **Filtering Thresholds:** Not given in the sources.

### Edge Cases and Pitfalls
-   **Imbalanced Shards:** Spatial partitioning can lead to imbalanced shards; index parity avoids this [S1, unofficial].
-   **Cross-Block Visibility Waste:** Spatial partitioning causes visibility waste at block boundaries; index parity avoids this [S1, unofficial].
-   **Peak Population:** Without spawn gating, the Gaussian population can grow excessively; the spawn gate limits this [S1, unofficial].
-   **Precision:** Not given in the sources.

## Operating characteristics
-   **Time Complexity:** Training time is significantly reduced compared to baselines. On the Rubble scene, BlitzGS achieves a scene-average PSNR of 33.79 dB in 39 minutes [S1, unofficial]. On the Residence scene, it achieves 24.66 dB in 38 minutes [S1, unofficial]. This is nearly an order of magnitude faster than Momen.GS (5h 03min, PSNR 31.81) and CityGS-X (4h 45min, PSNR 20.12) [S1, unofficial].
-   **Memory Complexity:** Each GPU stores approximately $|\mathcal{G}|/M$ Gaussians and their optimizer states [S1, unofficial].
-   **Strengths:** Fast training speed, high quality, efficient use of multiple GPUs, avoids cross-block visibility waste.
-   **Limitations:** Requires careful implementation of importance scoring and spawn gating. Performance depends on the effectiveness of the filtering mechanisms.
-   **When to use:** City-scale 3DGS training where speed is critical and high-quality novel views are required.
-   **When not to use:** Small-scale scenes where the overhead of distributed communication may outweigh the benefits.

## Background
BlitzGS was introduced by Zhongtao Wang, Huishan Au, Yisong Chen, Meng Gai, Yilong Li, Fei Zhu, Mai Su, Haojie Jin, and Guoping Wang [S1, unofficial]. The paper "BlitzGS: City-Scale Gaussian Splatting at Lightning Speed" was published on arXiv in August 2026 [S1, unofficial]. It addresses the challenges of city-scale 3D reconstruction, which often involves thousands of calibrated images and requires efficient multi-GPU training [S1, unofficial]. The method builds on insights from prior work on distributed 3DGS [S1, unofficial].
