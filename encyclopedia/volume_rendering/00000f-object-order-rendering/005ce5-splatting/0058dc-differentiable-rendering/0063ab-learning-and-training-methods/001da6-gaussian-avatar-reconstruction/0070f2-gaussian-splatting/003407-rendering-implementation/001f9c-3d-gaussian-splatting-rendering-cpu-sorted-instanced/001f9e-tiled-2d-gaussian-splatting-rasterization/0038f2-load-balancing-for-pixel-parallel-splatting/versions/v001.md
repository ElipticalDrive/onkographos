# Load Balancing for Pixel-parallel Splatting

Also called: Load balancing algorithm, Load balancing loss

## Overview
A strategy to address uneven computational load across pixel threads in Gaussian rasterization by reducing the number of Gaussians rendered for heavy-load pixels and increasing it for light-load pixels [S1]. Uneven load across GPU threads leads to lower rendering efficiency due to thread waiting [S1]. This method differs from hardware-centric approaches like [Load Distribution Unit (LDU) Workload Balancing](#load-distribution-unit-ldu-workload-balancing) by operating as a software-level loss function and adaptive rendering count adjustment within the pixel-parallel execution model.

## How it works
**Inputs and Outputs:**
*   **Input:** The set of $N$ 3D Gaussians, the camera parameters, and the image grid.
*   **Output:** A modified rendering process where the number of Gaussians processed per pixel is adjusted to minimize load variance, potentially at the cost of slight quality changes in light-load areas.

**Data Structures:**
*   **Pixel Load Count ($\ell_i$):** An integer value representing the number of Gaussians contributing to pixel $i$.
*   **Indicator Function ($1_{G_j, p_i}$):** A binary value (1 if Gaussian $j$ contributes to pixel $i$, 0 otherwise).

**Method Steps:**
1.  **Compute Pixel Loads:** Calculate the load $\ell_i$ for each pixel $i$ by summing the contributions of all Gaussians:
    $$
    \ell_i = \sum_{j \in N} 1_{G_j, p_i}
    $$
    where $N$ is the total number of Gaussians [S1].
2.  **Identify Load Imbalance:** Determine heavy-load pixels (high $\ell_i$) and light-load pixels (low $\ell_i$). The rendering efficiency is bottlenecked by the heavy-load threads [S1].
3.  **Apply Load Balancing Loss:** Optimize the Gaussian attributes (such as opacity or radius) using a load balancing loss term. The goal is to reduce $\ell_i$ for heavy-load pixels and increase $\ell_i$ for light-load pixels [S1].
    *   The loss function utilizes the standard deviation of the pixel loads to quantify imbalance [S1].
    *   The weight of the load balancing loss term is denoted as $\lambda_{load}$ [S1].
4.  **Adjust Rendering Count:** During rasterization, the actual number of Gaussians rendered is dynamically adjusted based on the learned attributes. Heavy-load pixels render fewer Gaussians, while light-load pixels render more, effectively balancing the thread execution time [S1].

**Parameters:**
*   **$\lambda_{load}$:** Weight for the load balancing loss term. Typical value: 0.45 [S1].
*   **$\lambda_{L1} + \lambda_{ssim}$:** Sum of weights for remaining losses (L1 and SSIM). Typical value: 0.55 [S1].
*   **Opacity Threshold ($\alpha_{low}$):** A threshold for opacity. A typical value is 255 (likely referring to a normalized integer scale or a specific implementation detail where higher values accelerate rendering, though the text notes higher values could further accelerate) [S1]. *Note: The source text is ambiguous regarding the exact scale of 255, but it is explicitly cited as the value used.* [S1].

**Edge Cases and Pitfalls:**
*   **Quality Degradation:** Reducing the number of Gaussians for heavy-load pixels may cause a decrease in rendering quality [S1]. The method attempts to mitigate this by increasing Gaussians for light-load pixels, but this is a trade-off [S1].
*   **Thread Waiting:** If the load balancing is not effective, GPU thread waiting persists, reducing efficiency [S1].

## Subtopics

### Load Distribution Unit (LDU) Workload Balancing
A workload distribution strategy to address severe imbalance in tile workloads, using early stopping depth prediction and Morton-order traversal to balance load across rasterization blocks [S2]. It differs from the pixel-parallel approach by operating at the tile/block level in hardware [S2].
*   **Preprocessing:** Discard Gaussians beyond predicted early stopping depth. Remaining Gaussians constitute the tile’s effective workload [S2].
*   **Workload Assignment:** Compute ideal average workload $W$. Assign approximately $N$ tiles per block sequentially. If cumulative Gaussian-tile pairs in current block exceed $(1 + 1/N)W$, defer current tile to next block [S2].
*   **Memory Optimization:** Employ Morton-order (Z-order) traversal to group spatially adjacent tiles into the same block, reducing memory access overhead [S2].
*   **Intra-block Sorting:** Sort tiles within each block from light to heavy workload. Reuse Gaussian Sorting Unit (GSU) for this task [S2].
*   **Pitfall:** Rasterization bubbles occur if high-workload tiles take longer to sort than light tiles take to rasterize. Light-to-heavy ordering ensures sorting finishes before rasterization of heavy tiles begins [S2].
