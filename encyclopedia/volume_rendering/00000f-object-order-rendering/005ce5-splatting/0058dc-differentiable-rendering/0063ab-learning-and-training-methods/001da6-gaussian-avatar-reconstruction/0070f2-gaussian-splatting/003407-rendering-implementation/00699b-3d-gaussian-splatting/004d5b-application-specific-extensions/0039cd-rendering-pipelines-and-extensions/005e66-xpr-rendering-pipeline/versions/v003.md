# XPR Rendering Pipeline

Also called: Extensible Cross-Platform Point-Based Differentiable Renderer, Extensible Cross-Platform Point-Based Differentiable Renderer pipeline, XPR Framework, XPR: An Extensible Cross-Platform Point-Based Differentiable Renderer

## Overview
XPR is a framework for point-based differentiable rendering that decouples method-specific logic from the shared rendering pipeline, allowing new methods to be implemented in a few hundred lines of code [S1, unofficial]. It separates the core rendering mechanics—parallelization, data layout, tiling, and differentiation—from the primitive evaluation logic, enabling portable execution across GPUs, TPUs, and CPUs via the XLA compiler [S1, unofficial]. Unlike traditional CUDA/Vulkan implementations that require thousands of lines and manual backward passes for each new primitive type, XPR exposes a four-function interface that captures only the method-specific math [S1, unofficial].

## How it works
XPR decomposes the rendering pipeline into modular, statically shaped parallel operations [S1, unofficial]. It handles the dynamic nature of rendering (variable primitive counts per tile) by fixing tensor dimensions at compile time using upper bounds and padding, converting dynamic loops into fixed-trip-count loops with early exits [S1, unofficial].

### Inputs and Outputs
*   **Inputs:** 3D primitives, camera parameters (`cam`, `view`), image dimensions, and tile configuration [S1, unofficial].
*   **Outputs:** Final color image `img` [S1, unofficial].

### Data Structures
*   **`tile_prim_map`:** A dictionary mapping each tile `t` to a list of 2D primitive data `prim_2D` that intersects that tile, bounded by `Pmax` [S1, unofficial].
*   **`px_data`:** Pixel-specific data returned by `pixel_info`, passed to `evaluate` [S1, unofficial].
*   **`p_sd`:** Primitive shader data returned by `get_shader_data`, containing parameters needed for evaluation (e.g., 2D covariance, color, opacity) [S1, unofficial].

### User-Defined Interface Functions
The programmer implements four functions [S1, unofficial]. The pipeline calls these for every relevant primitive-pixel pair:
1.  **`project(p)`**: Transforms a 3D primitive `p` into 2D screen space, returning `prim_2D` [S1, unofficial].
2.  **`tile_cull(t_min, t_max, p_tcd)`**: Given tile boundaries and primitive culling data, returns a boolean indicating if the primitive intersects the tile [S1, unofficial].
3.  **`pixel_info(px, cam, view)`**: Computes pixel-specific data for pixel `px=(x,y)` [S1, unofficial].
4.  **`evaluate(px_data, p_sd)`**: Computes the contribution of a primitive to a pixel, returning `alpha` (opacity), `valid` (boolean validity flag), and `c` (color) [S1, unofficial].

### Pipeline Steps
1.  **Preprocess (Project):** Apply `project` to all $N$ primitives in parallel to generate `prim_2D` data [S1, unofficial].
2.  **Filter (Tile Assignment):** Perform a conservative axis-aligned bounding box check for each primitive against tiles [S1, unofficial]. Call `tile_cull` for candidate intersections to refine visibility [S1, unofficial]. Populate `tile_prim_map` with valid primitive-tile pairs [S1, unofficial].
3.  **Rasterization (Binning):** Count the number of primitives per tile [S1, unofficial]. Sort tiles by primitive count and partition them into bins, each processed with a static trip count equal to the bin's upper bound [S1, unofficial]. Tiles within the same bin are parallelized using `map_fn` [S1, unofficial].
4.  **Shader (Compositing):** For each tile in a bin, iterate over its pixels [S1, unofficial]. For each pixel, call `pixel_info` once [S1, unofficial]. Iterate over the primitives in `tile_prim_map[t]` (up to `Pmax`) [S1, unofficial]. Call `evaluate` for each primitive-pixel pair [S1, unofficial]. Accumulate color using alpha blending [S1, unofficial].

### Formulas
The alpha blending accumulation for a pixel is:
$$ C = C + c \cdot \alpha \cdot \text{valid} \cdot T $$
$$ T = (1 - \alpha \cdot \text{valid}) \cdot T $$
Where:
*   $C$ is the accumulated color.
*   $c$ is the primitive color returned by `evaluate`.
*   $\alpha$ is the primitive opacity returned by `evaluate`.
*   $\text{valid}$ is the validity flag returned by `evaluate`.
*   $T$ is the accumulated transmittance, initialized to 1 [S1, unofficial].

### Parameters
*   **`Pmax`:** Maximum number of primitives per tile/pixel. Default is 4096 (XPR-4K). XPR-8K matches baseline quality, while lowering to 4096 increases frame rate but may skip contributions [S1, unofficial].
*   **Compilation Bounds:** All tensor dimensions and loop trip counts are fixed at compile time. Dynamic sizes are handled by padding unused entries and replacing dynamic loops with fixed-trip-count loops that exit early [S1, unofficial].

```python
def create_bins(tile_counts, Pmax):
    # Sorts tiles by count, partitions into bins with static upper bounds
    sorted_tiles = sorted(tile_counts.keys(), key=lambda t: tile_counts[t])
    bins = []
    current_bin = []
    current_max = 0
    for t in sorted_tiles:
        count = min(tile_counts[t], Pmax)
        if not current_bin or count > current_max:
            current_max = count
            current_bin.append(t)
        else:
            bins.append({'tiles': current_bin, 'upper_bound': current_max})
            current_bin = [t]
            current_max = count
    if current_bin:
        bins.append({'tiles': current_bin, 'upper_bound': current_max})
    return bins

def pad_to_size(lst, size):
    # Pads list to exact size with None
    return lst + [None] * (size - len(lst))

def zeros_like(shape):
    # Returns zero array of given shape
    return [[0.0 for _ in range(shape[1])] for _ in range(shape[0])]

def render(primitives, cam, view, tiles, Pmax=4096):
    H, W = cam['height'], cam['width']
    img = zeros_like((H, W))

    # 1. Preprocess: map_fn(project) over primitives
    prim_2D_data = [project(p) for p in primitives]

    # 2. Filter: map_fn over primitive-tile pairs
    tile_prim_map = {t: [] for t in tiles}
    for prim_2D in prim_2D_data:
        for t in tiles:
            if intersects(prim_2D, t):
                t_min, t_max = compute_tile_boundaries(t)
                p_tcd = get_shader_data(prim_2D)
                if tile_cull(t_min, t_max, p_tcd):
                    tile_prim_map[t].append(prim_2D)

    # 3. Rasterization: Trip-count binning
    tile_counts = {t: len(prims) for t, prims in tile_prim_map.items()}
    bins = create_bins(tile_counts, Pmax)

    # 4. Shader: Fixed-trip-count loops with early exit
    for bin in bins:
        trip_count = bin['upper_bound']
        for t in bin['tiles']:
            prims = pad_to_size(tile_prim_map[t], trip_count)
            for (x, y) in t['pixels']:
                C = 0.0
                T = 1.0
                px_data = pixel_info((x, y), cam, view)
                for i in range(trip_count):
                    if prims[i] is None:
                        break
                    p_sd = get_shader_data(prims[i])
                    alpha, valid, c = evaluate(px_data, p_sd)
                    C = C + c * alpha * valid * T
                    T = (1.0 - alpha * valid) * T
                img[y][x] = C
    return img
```

### Edge Cases and Pitfalls
*   **Primitive Overflow:** If a tile has more than `Pmax` primitives, contributions beyond `Pmax` are skipped, resulting in quality differences within 0.06 PSNR on 360 and T&T scenes, and within 0.58 PSNR on Synthetic scenes compared to baselines [S1, unofficial].
*   **Compiler Overhead:** JAX/XLA kernel launch overhead can be significant at very high frame rates [S1, unofficial].
*   **Method-Specific Costs:** Methods like 3DGUT, which require per-pixel world-space ray directions in `pixel_info`, may be slower than fused CUDA implementations because XPR separates this computation from blending [S1, unofficial].

## Operating characteristics
*   **Performance:** On NVIDIA L40S GPU, XPR reaches 97.18% of the speed of hand-optimized CUDA baselines on average [S1, unofficial]. Per-scene frame rates are within 2.82% of hand-written CUDA implementations, and up to 208.18% faster for some methods [S1, unofficial].
*   **Code Size:** Implementations require 260 to 304 lines of Python, compared to 2,153+ lines for Base CUDA implementations [S1, unofficial].
*   **Scalability:** Efficiency is bounded by the maturity of the XLA backend for the target hardware. Performance on TPUs, Intel GPUs, and AMD GPUs varies based on backend optimization [S1, unofficial].
*   **Limitations:** XPR cannot express techniques involving ray marching or ray tracing (e.g., NeRFs, physically-based rendering) [S1, unofficial]. It is limited to point-based differentiable rendering [S1, unofficial].

## Background
XPR was introduced in the paper "XPR: An Extensible Cross-Platform Point-Based Differentiable Renderer" [S1, unofficial]. It addresses the limitations of existing frameworks (CUDA/Vulkan) that require thousands of lines of code and manual backward passes for each new rendering method [S1, unofficial]. XPR leverages JAX/XLA to provide a cross-platform, differentiable rendering pipeline that separates method-specific logic from the pipeline structure [S1, unofficial].
