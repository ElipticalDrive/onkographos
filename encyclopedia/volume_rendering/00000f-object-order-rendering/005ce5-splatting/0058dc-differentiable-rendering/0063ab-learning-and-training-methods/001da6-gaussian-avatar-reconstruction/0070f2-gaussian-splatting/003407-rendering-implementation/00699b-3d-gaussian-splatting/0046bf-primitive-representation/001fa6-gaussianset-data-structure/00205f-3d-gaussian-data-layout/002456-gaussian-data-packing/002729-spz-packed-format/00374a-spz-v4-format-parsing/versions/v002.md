# SPZ v4 Format Parsing

Also called: SPZ format decoder, SPZ v4, SPZ v4 Reader, ZSTD streams in KMP splat parser, compressed capture reader, parseSplatSpz

## Overview
SPZ v4 format parsing is the method for decoding binary `.spz` files containing compressed 3D Gaussian splat data into a `SplatCloud` structure [S2]. It solves the problem of loading high-fidelity Gaussian splat captures in environments lacking native system-level decompression libraries, such as web browsers, by using a built-in ZSTD decoder instead of native gzip [S2]. It is distinguished from earlier SPZ versions (1–3) by using one ZSTD stream per attribute instead of a single gzip stream, and from generic PLY parsers by its specific handling of quantized fields and coordinate system transformations [S2].

## How it works
**Inputs and Outputs:**
*   **Input:** A binary file with the `.spz` extension.
*   **Output:** A `SplatCloud` object containing decoded Gaussian attributes (position, covariance, opacity, spherical harmonics up to degree 4) [S2]. The output coordinate system is either the file's native Right-Up-Back (RUB) or a requested Right-Down-Front (RDF) compatible with PLY standards [S2].

**Data Structures:**
The SPZ v4 format stores attributes in separate ZSTD-compressed streams [S2]. Quantized fields are stored as integers and decoded using scaling constants provided by the reference library [S2].

**Numbered Steps:**
1.  **Decompression:** Decompress each attribute stream using a ZSTD decoder (e.g., KTX2 implementation for web compatibility) [S2].
2.  **Quantization Decoding:** Decode quantized integer fields to floating-point values using reference library constants [S2].
3.  **Coordinate System Handling:** By default, return the cloud in the file's native RUB axes [S2]. If PLY coordinates are requested, transform axes from RUB to RDF and flip the signs of the spherical harmonics coefficients to match the coordinate change [S2].
4.  **Validation:** Compare decoded reference positions against expected values using a relative tolerance to account for precision differences inherent in the quantization process [S1, unofficial].
5.  **Extension Check:** If the file name includes an extension indicating a coordinate axis move, refuse to parse the file by name rather than rendering it mirrored, to prevent incorrect coordinate mapping [S2].

def parse_spz_v4(file_path: str, request_ply_coords: bool = False) -> SplatCloud:
    # 1. Decompress each attribute stream using a ZSTD decoder [S2]
    streams = read_attribute_streams(file_path)
    decompressed = {}
    for attr, data in streams.items():
        decompressed[attr] = decompress_zstd(data)

    # 2. Decode quantized fields using reference library constants [S2]
    decoded = {}
    for attr, raw in decompressed.items():
        params = get_quantization_params(attr)
        decoded[attr] = decode_quantized(raw, params)

    positions = decoded['position']
    sh_coeffs = decoded['sh']

    # 3. Coordinate System Handling
    if request_ply_coords:
        # Transform from RUB to RDF by flipping Y and Z axes [G]
        positions = [(p[0], -p[1], -p[2]) for p in positions]
        # Flip signs of spherical harmonics to match coordinate change [S2]
        sh_coeffs = flip_sh_signs(sh_coeffs)

    # 4. Validation: compare reference positions with a relative tolerance [S1, unofficial]
    validate_positions(positions, relative_tolerance=1e-5)

    # 5. Extension Check: refuse files with axis-move extensions by name [S2]
    if has_axis_move_extension(file_path):
        raise ValueError("File with axis-move extension refused by name")

    return SplatCloud(positions=positions, sh_coeffs=sh_coeffs)

**Parameters:**
*   `relative_tolerance`: Used for position validation. Value not explicitly given, but "relative tolerance" is required [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** SPZ v4 reference positions must be compared with a relative tolerance due to quantization precision differences [S1, unofficial].
*   **Coordinate Mapping:** Files with extensions indicating axis moves are refused by name, not rendered mirrored, to prevent incorrect mapping [S2].
*   **Web Compatibility:** Native system decoders are not required; the parser must use web-compatible ZSTD (e.g., KTX2) [S2].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Not given in the sources.
*   **Strengths:** Enables web-compatible decoding without native system libraries [S2]. Supports high-fidelity data with SH degree 4 [S2].
*   **Limitations:** Requires ZSTD implementation. Coordinate system conversion is non-trivial for SH coefficients [S2].
*   **When to use:** When loading SPZ v4 files in web environments or when PLY coordinate compatibility is required [S2].
*   **When not to use:** When native gzip decompression is sufficient (SPZ v1–3) or when coordinate system conversion is not needed and RUB is acceptable [S2].
