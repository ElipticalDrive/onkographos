# Text Embedding Generation with Directional Views


## Overview
This method encodes text prompts into latent embeddings using a frozen CLIP text encoder and generates directional view embeddings by appending view descriptors to prompts [S1, unofficial]. It solves the problem of view-dependent semantic grounding in 3D generation by explicitly conditioning the text embedding on the viewing angle, allowing the model to distinguish between different perspectives of the same object [S1, unofficial][S2, S3]. Unlike sibling methods that rely solely on volumetric consistency or instance-level fusion, this approach modifies the input text representation itself based on camera position [S1, unofficial][S2, S3].

## How it works
**Inputs and Outputs:**
- Input: A base text prompt string (e.g., "a panda"), a set of view descriptors (e.g., "front", "side", "back"), and a tokenizer/text encoder pair (typically CLIP).
- Output: A dictionary mapping view keys to tensor embeddings of shape `[1, 77, 768]` (batch, sequence length, embedding dimension) [S1, unofficial].

**Data Structures:**
- `self.embeddings`: A dictionary where keys are strings (`'pos'`, `'neg'`, `'front'`, `'side'`, `'back'`) and values are PyTorch tensors of shape `[1, 77, 768]` [S1, unofficial].
- `inputs`: Tokenized input tensor with padding to `model_max_length` [S1, unofficial].

**Steps:**
1. **Tokenization:** Tokenize the base prompt with padding to the maximum sequence length of the tokenizer.
   $$ \text{inputs} = \text{tokenizer}(\text{prompt}, \text{padding}=\text{"max\_length"}, \text{max\_length}=\text{tokenizer.model\_max\_length}, \text{return\_tensors}=\text{"pt"}) $$
   [S1, unofficial]
2. **Encoding:** Pass the token IDs through the frozen text encoder to obtain the base embedding.
   $$ \text{embeddings} = \text{text\_encoder}(\text{inputs.input\_ids.to(device)})[0] $$
   [S1, unofficial]
3. **Directional Augmentation:** For each view descriptor $d$ in the set of directions (e.g., `['front', 'side', 'back']`), append the string `', {d} view'` to the base prompt.
   $$ \text{prompt}_d = \text{prompt} + \text{', ' + d + ' view'} $$
   [S1, unofficial]
4. **Directional Encoding:** Tokenize and encode each augmented prompt $\text{prompt}_d$ using the same text encoder.
   $$ \text{embeddings}_d = \text{text\_encoder}(\text{tokenizer}(\text{prompt}_d, \text{padding}=\text{"max\_length"}, \text{max\_length}=\text{tokenizer.model\_max\_length}, \text{return\_tensors}=\text{"pt"}).\text{input\_ids.to(device)})[0] $$
   [S1, unofficial]
5. **Storage:** Store the resulting tensors in `self.embeddings` under keys `'front'`, `'side'`, `'back'`, etc. [S1, unofficial].

**Pseudocode:**
```python
import torch
from transformers import CLIPTextModel, CLIPTokenizer

class TextEmbeddingGenerator:
    def __init__(self, text_encoder: CLIPTextModel, tokenizer: CLIPTokenizer, device: str = "cuda"):
        self.text_encoder = text_encoder
        self.tokenizer = tokenizer
        self.device = device
        self.embeddings = {}

    def encode_text(self, prompt: str, views: list = ['front', 'side', 'back']):
        """
        Encodes a base prompt and its directional variants.
        
        Args:
            prompt: Base text string (e.g., "a panda").
            views: List of view descriptors to append.
            
        Returns:
            Dictionary mapping view keys to embedding tensors.
        """
        # Step 1 & 2: Encode base prompt
        inputs = self.tokenizer(
            prompt, 
            padding="max_length", 
            max_length=self.tokenizer.model_max_length, 
            return_tensors="pt"
        )
        base_embed = self.text_encoder(inputs.input_ids.to(self.device))[0]
        self.embeddings['pos'] = base_embed

        # Encode negative prompt if needed (standard CLIP practice, though not explicitly detailed in S1 steps, 
        # S1 mentions 'neg' key in self.embeddings)
        # Assuming negative prompt is empty or handled separately; for this method, we focus on directional views.
        # If a specific negative prompt is required, it would be encoded similarly.
        # For the purpose of this specific method's core definition from S1:
        
        # Step 3 & 4: Encode directional views
        for view in views:
            directional_prompt = f"{prompt}, {view} view"
            dir_inputs = self.tokenizer(
                directional_prompt, 
                padding="max_length", 
                max_length=self.tokenizer.model_max_length, 
                return_tensors="pt"
            )
            dir_embed = self.text_encoder(dir_inputs.input_ids.to(self.device))[0]
            self.embeddings[view] = dir_embed
            
        return self.embeddings
```

**Parameters:**
- `max_length`: Typically 77 for CLIP [S1, unofficial].
- `embedding_dim`: 768 for CLIP text encoder [S1, unofficial].
- `views`: List of strings. Common values: `['front', 'side', 'back']` [S1, unofficial]. For forward-facing scenes (e.g., LLFF dataset), use `['top-down view', 'front view', 'side view']` [S2].

**Edge Cases and Pitfalls:**
- **Janus Problem:** View-specific prompting does not fully solve the Janus problem (multiple faces appearing on one object), as the loss still encourages matching the input image appearance across all views [S3].
- **Resolution:** Rendering at higher resolutions than 96px or 128px provides no noticeable quality difference for the prior loss, but increases computational cost [S3].

## Subtopics

### [TexGS-VolVis Representation and Optimization](11105-texgs-volvis-representation-and-optimization.md)
TexGS-VolVis is a method for representing and editing volume visualization (VolVis) scenes using textured 2D Gaussian Splatting (2DGS). It solves the problem of decoupling geometry from appearance in text-driven non-photorealistic style editing (NPSE), allowing for geometry-consistent stylization without the elliptical artifacts common in coupled representations. Unlike methods that freeze geometry to prevent distortion, TexGS-VolVis uses explicit 2D texture maps to store appearance, preserving geometric fidelity while enabling rich visual expressiveness.

### [View-Dependent Prompting](19229-view-dependent-prompting.md)
View-Dependent Prompting augments text prompts with directional suffixes based on the camera's position relative to the scene to guide diffusion-based 3D generation. It differs from sibling methods like [TexGS-VolVis Representation and Optimization](11105-texgs-volvis-representation-and-optimization.md) by explicitly conditioning the text embedding on the viewing angle rather than relying solely on volumetric or geometric consistency.

### [Multimodal Object Embedding](21344-multimodal-object-embedding.md)
Multimodal Object Embedding creates a unified semantic representation for 3D objects by fusing vision-based CLIP embeddings with optional text-based CLIP embeddings. It solves the problem of limited semantic grounding in open-vocabulary querying by capturing both visual features and high-level attribute descriptions in a single vector space. Unlike its sibling [Text Embedding Generation with Directional Views](8239-text-embedding-generation-with-directional-views.md), which generates directional view embeddings by appending view descriptors to prompts, this method focuses on instance-level fusion of static object attributes. It differs from [TexGS-VolVis Representation and Optimization](11105-texgs-volvis-representation-and-optimization.md) and [View-Dependent Prompting](19229-view-dependent-prompting.md) by explicitly combining a language-free ontology with an LLM-generated attribute channel.

### Directional Dependent Prompts
Concatenates a text prompt to the input caption depending on the camera location in the scene at each iteration [S2]. Prompts used include `', top-down view'`, `', front view'`, `', side view'`, and `', back view'` [S2]. For forward-facing scenes like the LLFF dataset, only the first three captions are used [S2].

### View-Specific Prompting
When rendering an image from a novel viewpoint, optimizes using a text prompt that includes the view direction, e.g., “An image of a [object], back view”, where [object] is the image-specific token [S3]. A pitfall is that this does not fully solve the Janus problem, as the loss still encourages matching the input image appearance across all views [S3].

## Operating characteristics
- **Time Complexity:** Linear with respect to the number of views and the sequence length of the prompt. The encoding is performed once per prompt/view combination, not per pixel.
- **Memory Complexity:** $O(V \cdot L \cdot D)$, where $V$ is the number of views, $L$ is the sequence length (77), and $D$ is the embedding dimension (768) [S1, unofficial].
- **Measured Performance:** Not given in the sources.
- **Strengths:** Explicitly handles view-dependent semantics, reducing ambiguity in 3D generation.
- **Limitations:** Does not fully resolve the Janus problem [S3]. Computational cost increases with the number of view descriptors.
- **When to use:** When view-dependent semantic consistency is critical for 3D generation or editing.
- **When not to use:** When computational resources are limited and view-dependent semantics are not required.

## Background
Originated in the context of 3D Gaussian Splatting and diffusion-based 3D generation, specifically in methods like DreamGaussian and RealFusion [S1, unofficial][S3]. It addresses the need for consistent semantic representation across different viewing angles in 3D reconstruction and generation tasks.
