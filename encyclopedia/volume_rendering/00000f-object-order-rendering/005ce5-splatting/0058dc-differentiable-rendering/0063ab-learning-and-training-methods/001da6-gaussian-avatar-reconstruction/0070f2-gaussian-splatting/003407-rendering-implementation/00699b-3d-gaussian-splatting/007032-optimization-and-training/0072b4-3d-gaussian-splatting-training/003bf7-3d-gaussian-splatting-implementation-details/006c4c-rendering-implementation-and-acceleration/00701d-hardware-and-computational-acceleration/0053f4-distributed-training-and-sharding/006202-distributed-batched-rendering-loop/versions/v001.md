# Distributed Batched Rendering Loop

Also called: Distributed 3DGS Rendering Loop

## Overview
The Distributed Batched Rendering Loop is a parallelized training and inference pipeline for 3D Gaussian Splatting (3DGS) that processes multiple camera views simultaneously across a cluster of GPUs [S1, unofficial]. It solves the memory and compute bottlenecks of single-GPU training by partitioning the global set of 3D Gaussians and distributing the rendering workload, enabling high-resolution and large-scale scene reconstruction [S1, unofficial]. Unlike standard single-view rendering, this method employs dynamic load balancing and sparse all-to-all communication to ensure efficient data distribution and aggregation across distributed ranks [S1, unofficial].

## How it works
The method iterates over a dataset of camera poses in fixed-size batches, coordinating data movement and computation across multiple GPU devices.

### Inputs and Outputs
*   **Inputs:**
    *   `dataset`: A collection of camera poses and associated ground-truth images.
    *   `gaussians`: The global set of 3D Gaussian parameters (means, covariances, opacities, spherical harmonic coefficients) partitioned across GPUs.
    *   `args.bsz`: The batch size, defining the number of camera views processed per iteration [S1, unofficial].
    *   `args.sample_freq`: Frequency for saving rendered images (if not -1) [S1, unofficial].
    *   `args.generate_num`: Maximum number of images to generate [S1, unofficial].
*   **Outputs:**
    *   Rendered images for the batched cameras, aggregated and saved to disk [S1, unofficial].

### Data Structures
*   `batched_cameras`: A list or tensor containing the camera parameters (extrinsics, intrinsics) for the current batch [S1, unofficial].
*   `batched_strategies`: A data structure defining the workload division, specifying which GPU handles which part of the rendering task for the current batch [S1, unofficial].
*   `gpuid2tasks`: A mapping from GPU ID to the specific rendering tasks assigned to that GPU [S1, unofficial].
*   `batched_screenspace_pkg`: A preprocessed data structure holding the 3DGS data and screenspace packages required for the distributed rendering kernel, generated after the all-to-all communication step [S1, unofficial].

### Numbered Steps
1.  **Batch Initialization:** Iterate through the cameras in steps of `args.bsz`. Calculate the number of cameras to load for the current iteration, ensuring the last batch does not exceed the dataset size [S1, unofficial].
2.  **Camera Fetching:** Retrieve the batch of camera parameters from the dataset [S1, unofficial].
3.  **Strategy Calculation:** Compute the workload division and map rendering tasks to specific GPUs based on the current batch and historical strategy data [S1, unofficial].
4.  **Camera Data Transfer:** Transfer the camera parameters from CPU memory to the global memory of all participating GPUs according to the calculated strategy [S1, unofficial].
5.  **Preprocessing and Communication:**
    *   Preprocess the 3DGS data for the current batch.
    *   Execute a sparse all-to-all communication operation across all GPUs. This step routes the relevant 3D Gaussians to the GPUs responsible for rendering the pixels they affect, based on the dynamic load balancing strategy [S1, unofficial].
    *   The output is `batched_screenspace_pkg` [S1, unofficial].
6.  **Rendering:** Execute the distributed rendering kernel using `batched_screenspace_pkg` and `batched_strategies` to generate the batched images [S1, unofficial].
7.  **Aggregation:** If multiple GPUs are involved (`utils.DEFAULT_GROUP.size() > 1`), perform a sum reduction (`torch.distributed.all_reduce`) to aggregate the rendered images across all ranks [S1, unofficial].
8.  **Post-processing and Saving:** Clamp the pixel values to the valid range $[0.0, 1.0]$ and save the images to disk, respecting the `args.sample_freq` and `args.generate_num` constraints [S1, unofficial].

### Pseudocode
```python
import torch
import torch.distributed as dist
import torchvision.utils

# Assume utils.DEFAULT_GROUP is initialized
# Assume dataset, gaussians, pipeline, background are available globally or passed

num_cameras = len(dataset)
idx = 1

while idx <= num_cameras:
    # Step 1: Calculate batch size
    num_camera_to_load = min(args.bsz, num_cameras - idx + 1)
    
    # Step 2: Fetch cameras
    batched_cameras = dataset.get_batched_cameras(num_camera_to_load)
    
    # Step 3: Compute workload division
    batched_strategies, gpuid2tasks = start_strategy_final(batched_cameras, strategy_history)
    
    # Step 4: Transfer camera data to GPUs
    load_camera_from_cpu_to_all_gpu_for_eval(batched_cameras, batched_strategies, gpuid2tasks)
    
    # Step 5: Preprocess and All-to-All Communication
    batched_screenspace_pkg = distributed_preprocess3dgs_and_all2all_final(
        batched_cameras, 
        gaussians, 
        pipeline, 
        background, 
        batched_strategies=batched_strategies, 
        mode="test"
    )
    
    # Step 6: Render
    batched_image, _ = render_final(batched_screenspace_pkg, batched_strategies)
    
    # Step 7: Aggregate results
    if utils.DEFAULT_GROUP.size() > 1:
        # Sum reduction across all ranks
        dist.all_reduce(batched_image, op=dist.ReduceOp.SUM, group=utils.DEFAULT_GROUP)
    
    # Step 8: Clamp and Save
    image = torch.clamp(batched_image, 0.0, 1.0)
    
    # Check if we should save based on frequency and limit
    if args.sample_freq != -1 and (idx % args.sample_freq == 0):
        if args.generate_num is None or (idx // args.sample_freq) <= args.generate_num:
            torchvision.utils.save_image(image, f"render_{idx}.png")
    
    idx += args.bsz
```

### Parameters
*   `args.bsz`: Batch size for camera processing. Controls how many views are processed per iteration [S1, unofficial].
*   `args.sample_freq`: Sampling frequency for saving renders. If not -1, only saves every `args.sample_freq`-th image [S1, unofficial].
*   `args.generate_num`: Maximum number of images to generate before breaking the loop [S1, unofficial].

### Edge Cases and Pitfalls
*   **Last Batch Size:** The loop must handle the case where the total number of cameras is not divisible by `args.bsz`. The calculation `min(args.bsz, num_cameras - idx + 1)` ensures the final batch is processed correctly without index out-of-bounds errors [S1, unofficial].
*   **Distributed Group Check:** The aggregation step explicitly checks `utils.DEFAULT_GROUP.size() > 1` to avoid unnecessary communication overhead when running on a single GPU [S1, unofficial].
*   **Precision:** Pixel values are clamped to $[0.0, 1.0]$ after aggregation to handle potential floating-point inaccuracies or overflow during the sum reduction [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The rendering time is dominated by the all-to-all communication and the rasterization step. The batched approach allows for better GPU utilization by keeping the compute units busy while communication occurs or by overlapping them, reducing the per-image latency compared to sequential single-view rendering [S1, unofficial].
*   **Memory Complexity:** By partitioning the 3D Gaussians across $M$ GPUs, the memory requirement per GPU is reduced by approximately a factor of $M$, allowing for the training of scenes with tens of millions of Gaussians (e.g., 40.4 million Gaussians on 16 GPUs) that would not fit on a single GPU [S1, unofficial].
*   **Performance:** On the "Rubble" dataset, distributing 40.4 million Gaussians across 16 GPUs achieved a test PSNR of 27.28, compared to 26.28 PSNR with 11.2 million Gaussians on a single GPU [S1, unofficial]. This demonstrates that scaling up the number of Gaussians via distributed rendering improves visual quality [S1, unofficial].
*   **Strengths:** Enables high-resolution and large-scale 3D reconstruction; supports batched training for improved learning rate scaling (sqrt(batch size) rule) [S1, unofficial].
*   **Limitations:** Requires complex communication overhead (all-to-all); dependent on the efficiency of the sparse communication implementation [S1, unofficial].

## Background
The Distributed Batched Rendering Loop is part of the Grendel system, a distributed framework for 3D Gaussian Splatting [S1, unofficial]. It was developed to address the limitations of single-GPU training, which cannot handle high-resolution and large-scale 3D reconstruction tasks due to GPU memory capacity limits [S1, unofficial]. The system relies on sparse all-to-all communication and dynamic load balancing to parallelize computation across multiple GPUs [S1, unofficial]. It builds on the foundational 3D Gaussian Splatting method by Kerbl et al. [S1, 12180, unofficial].
