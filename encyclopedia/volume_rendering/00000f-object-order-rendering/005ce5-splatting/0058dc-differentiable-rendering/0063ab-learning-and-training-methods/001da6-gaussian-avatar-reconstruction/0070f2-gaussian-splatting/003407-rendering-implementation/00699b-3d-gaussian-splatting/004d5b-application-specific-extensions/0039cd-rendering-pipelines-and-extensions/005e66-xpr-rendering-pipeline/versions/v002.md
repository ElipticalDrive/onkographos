# XPR Rendering Pipeline

Also called: Extensible Cross-Platform Point-Based Differentiable Renderer, Extensible Cross-Platform Point-Based Differentiable Renderer pipeline, XPR Framework, XPR: An Extensible Cross-Platform Point-Based Differentiable Renderer

## Overview
XPR is a framework for point-based differentiable rendering that decouples method-specific logic from the shared rendering pipeline, allowing new methods to be implemented in a few hundred lines of code [S1, unofficial]. It separates the core rendering mechanics—parallelization, data layout, tiling, and differentiation—from the primitive evaluation logic, enabling portable execution across GPUs, TPUs, and CPUs via the XLA compiler [S1, unofficial]. Unlike traditional CUDA/Vulkan implementations that require thousands of lines and manual backward passes for each new primitive type, XPR exposes a four-function interface that captures only the method-specific math [S1, unofficial].

## How it works
XPR decomposes the rendering pipeline into modular, statically shaped parallel operations. It handles the dynamic nature of rendering (variable primitive counts per tile) by fixing tensor dimensions at compile time using upper bounds and padding, converting dynamic loops into fixed-trip-count loops with early exits [S1, unofficial].

### Inputs and Outputs
*   **Inputs:** 3D primitives (defined by the method's `project` function), camera parameters (`cam`, `view`), image dimensions, and tile configuration.
*   **Outputs:** Final color image `img`.

### Data Structures
*   **`tile_prim_map`:** A dictionary mapping each tile `t` to a list of 2D primitive data `prim_2D` that intersects that tile. The size of each list is bounded by `Pmax` [S1, unofficial].
*   **`px_data`:** Pixel-specific data returned by `pixel_info`, passed to `evaluate` [S1, unofficial].
*   **`p_sd`:** Primitive shader data returned by `get_shader_data`, containing parameters needed for evaluation (e.g., 2D covariance, color, opacity) [S1, unofficial].

### User-Defined Interface Functions
The programmer implements four functions. The pipeline calls these for every relevant primitive-pixel pair:
1.  **`project(p)`**: Transforms a 3D primitive `p` into 2D screen space. Returns `prim_2D` [S1, unofficial].
2.  **`tile_cull(t_min, t_max, p_tcd)`**: Given tile boundaries and primitive culling data, returns a boolean indicating if the primitive intersects the tile [S1, unofficial].
3.  **`pixel_info(px, cam, view)`**: Computes pixel-specific data for pixel `px=(x,y)`. Returns `px_data` [S1, unofficial].
4.  **`evaluate(px_data, p_sd)`**: Computes the contribution of a primitive to a pixel. Returns `alpha` (opacity), `valid` (boolean validity flag), and `c` (color) [S1, unofficial].

### Pipeline Steps
1.  **Preprocess (Project):** Apply `project` to all $N$ primitives in parallel to generate `prim_2D` data [S1, unofficial].
2.  **Filter (Tile Assignment):**
    *   Perform a conservative axis-aligned bounding box check for each primitive against tiles [S1, unofficial].
    *   Call `tile_cull` for candidate intersections to refine visibility [S1, unofficial].
    *   Populate `tile_prim_map` with valid primitive-tile pairs [S1, unofficial].
3.  **Rasterization (Binning):**
    *   Count the number of primitives per tile.
    *   Sort tiles by primitive count and partition them into bins. Each bin is processed with a static trip count equal to the bin's upper bound [S1, unofficial].
    *   Tiles within the same bin are parallelized using `map_fn` [S1, unofficial].
4.  **Shader (Compositing):**
    *   For each tile in a bin, iterate over its pixels.
    *   For each pixel, call `pixel_info` once [S1, unofficial].
    *   Iterate over the primitives in `tile_prim_map[t]` (up to `Pmax`).
    *   Call `evaluate` for each primitive-pixel pair.
    *   Accumulate color using alpha blending [S1, unofficial].

### Formulas
The alpha blending accumulation for a pixel is:
$$ C = C + c \cdot \alpha \cdot \text{valid} \cdot T $$
$$ T = (1 - \alpha \cdot \text{valid}) \cdot T $$
Where:
*   $C$ is the accumulated color.
*   $c$ is the primitive color returned by `evaluate`.
*   $\alpha$ is the primitive opacity returned by `evaluate`.
*   $\text{valid}$ is the validity flag returned by `evaluate`.
*   $T$ is the accumulated transmittance, initialized to 1 [S1, unofficial].

### Parameters
*   **`Pmax`:** Maximum number of primitives per tile/pixel. Default is 4096 (XPR-4K). Higher values (e.g., 8192/XPR-8K) improve quality but reduce frame rate [S1, unofficial].
*   **Compilation Bounds:** All tensor dimensions and loop trip counts are fixed at compile time. Dynamic sizes are handled by padding unused entries [S1, unofficial].

### Edge Cases and Pitfalls
*   **Primitive Overflow:** If a tile has more than `Pmax` primitives, contributions beyond `Pmax` are skipped. This may cause quality loss (e.g., 0.06-0.58 PSNR drop depending on scene and method) [S1, unofficial].
*   **Compiler Overhead:** JAX/XLA kernel launch overhead can be significant at very high frame rates [S1, unofficial].
*   **Method-Specific Costs:** Methods like 3DGUT, which require per-pixel world-space ray directions in `pixel_info`, may be slower than fused CUDA implementations because XPR separates this computation from blending [S1, unofficial].

## Operating characteristics
*   **Performance:** On NVIDIA L40S GPU, XPR reaches 97.18% of the speed of hand-optimized CUDA baselines on average [S1, unofficial]. Per-scene frame rates are within 2.82% of hand-written CUDA implementations, and up to 208.18% faster for some methods [S1, unofficial].
*   **Code Size:** Implementations require 260 to 304 lines of Python, compared to 2,153+ lines for Base CUDA implementations [S1, unofficial].
*   **Scalability:** Efficiency is bounded by the maturity of the XLA backend for the target hardware. Performance on TPUs, Intel GPUs, and AMD GPUs varies based on backend optimization [S1, unofficial].
*   **Limitations:** XPR cannot express techniques involving ray marching or ray tracing (e.g., NeRFs, physically-based rendering) [S1, unofficial]. It is limited to point-based differentiable rendering.

## Background
XPR was introduced in the paper "XPR: An Extensible Cross-Platform Point-Based Differentiable Renderer" [S1, unofficial]. It addresses the limitations of existing frameworks (CUDA/Vulkan) that require thousands of lines of code and manual backward passes for each new rendering method [S1, unofficial]. XPR leverages JAX/XLA to provide a cross-platform, differentiable rendering pipeline that separates method-specific logic from the pipeline structure [S1, unofficial].
