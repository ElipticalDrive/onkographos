# Distributed Batched Rendering Loop

Also called: Distributed 3DGS Rendering Loop

## Overview
The Distributed Batched Rendering Loop is a training and evaluation pipeline for 3D Gaussian Splatting (3DGS) that parallelizes the rendering of multiple camera views across multiple GPUs to overcome single-GPU memory limits and accelerate large-scale reconstruction [S1, unofficial]. Unlike single-GPU methods that process one view at a time, this method processes batches of camera views, dividing the workload via dynamic load balancing and sparse all-to-all communication to ensure each GPU composites only the pixels it owns [S1, unofficial][S2]. It is distinguished from sibling methods like [BlitzGS](15088-blitzgs.md) by its explicit support for batched training with multiple views and its integration of dynamic scheduling strategies to balance communication and computation overhead [S1, unofficial].

## How it works
The method operates in an iterative loop over camera datasets, distributing the global set of $N$ 3D Gaussians $\mathcal{G}$ across $M$ GPUs. Each GPU $m$ holds a shard $\mathcal{G}^{(m)}$ and corresponding optimizer states [S1, unofficial][S2]. The rendering process for a batch of views involves preprocessing, communication, compositing, and aggregation.

### Inputs and Outputs
*   **Inputs**:
    *   `dataset`: A dataset object providing camera poses and intrinsics.
    *   `gaussians`: The global set of 3D Gaussian parameters (position, covariance, opacity, spherical harmonics), partitioned across GPUs.
    *   `pipeline`: The rendering pipeline configuration (projection matrices, background color).
    *   `args.bsz`: Batch size, controlling the number of camera views processed per iteration [S1, unofficial].
    *   `args.sample_freq`: Frequency for saving rendered images [S1, unofficial].
    *   `args.generate_num`: Maximum number of images to generate [S1, unofficial].
*   **Outputs**:
    *   `batched_image`: Rendered images for the current batch, aggregated across ranks.
    *   `batched_screenspace_pkg`: Intermediate data structure holding preprocessed screenspace packages for distributed rendering [S1, unofficial].

### Data Structures
*   `batched_strategies`: A data structure defining the mapping of camera views and pixel tiles to specific GPUs for the current batch [S1, unofficial].
*   `gpuid2tasks`: A dictionary or mapping assigning rendering tasks (specific pixel blocks or tiles) to GPU IDs [S1, unofficial].
*   `compute_locally[i][j]`: A 2D boolean array used in Pixel Block Scheduling, where `true` indicates the pixel block at row $i$ and column $j$ should be computed by the local GPU [S2].

### Steps
1.  **Batch Iteration**: Iterate through the camera dataset in steps of `args.bsz`. For each iteration `idx`, calculate the number of cameras to load: `num_camera_to_load = min(args.bsz, num_cameras - idx + 1)` [S1, unofficial].
2.  **Fetch Cameras**: Retrieve the batch of camera parameters using `dataset.get_batched_cameras(num_camera_to_load)` [S1, unofficial].
3.  **Strategy Calculation**: Compute the workload division and GPU-to-task mapping using `start_strategy_final(batched_cameras, strategy_history)`. This returns `batched_strategies` and `gpuid2tasks` [S1, unofficial].
4.  **Data Transfer**: Transfer camera data from CPU to all GPUs according to the division strategy using `load_camera_from_cpu_to_all_gpu_for_eval(batched_cameras, batched_strategies, gpuid2tasks)` [S1, unofficial].
5.  **Preprocessing and Communication**: Execute distributed preprocessing of 3DGS data and sparse all-to-all communication. Each GPU projects its local shard $\mathcal{G}^{(m)}$ to screen space. Gaussians are routed to the GPUs owning the tiles they cover. This returns `batched_screenspace_pkg` [S1, unofficial][S2].
6.  **Rendering**: Render the batched images using `render_final(batched_screenspace_pkg, batched_strategies)`. If Pixel Block Scheduling is used, the GPU renders only pixels within blocks where `compute_locally` is true [S1, unofficial][S2].
7.  **Aggregation**: Aggregate rendered images across distributed ranks using a sum reduction: `torch.distributed.all_reduce(image, op=dist.ReduceOp.SUM, group=utils.DEFAULT_GROUP)` if more than one GPU is active [S1, unofficial].
8.  **Post-processing**: Clamp pixel values to the valid range $[0.0, 1.0]$ and save images if `args.sample_freq` dictates [S1, unofficial].

### Parameters
*   `args.bsz`: Batch size for camera processing. Controls how many views are processed per iteration. Larger batches improve GPU utilization but increase memory usage [S1, unofficial].
*   `args.sample_freq`: Sampling frequency for saving renders. If `!= -1`, only saves every `args.sample_freq`-th image [S1, unofficial].
*   `args.generate_num`: Maximum number of images to generate before breaking the loop [S1, unofficial].
*   Block Size (Pixel Block Scheduling): 16x16 pixels. This is the scheduling granularity, trading off scheduler overhead against uneven workloads [S2].

### Edge Cases and Pitfalls
*   **Scheduler Overhead**: If pixel-level scheduling is used without blocking, the overhead of computing the scheduling strategy can become significant for high-resolution images. Grouping pixels into 16x16 blocks mitigates this [S2].
*   **Load Imbalance**: Distributing pixels to balance runtime does not necessarily balance the number of Gaussians each GPU touches. Forward runtime correlates with touched Gaussians, while backward/loss computation depends on pixel count and contributed Gaussian count. Rebalancing Gaussian distribution may be necessary to minimize total communication volume [S2].
*   **Precision**: Pixel values must be clamped to $[0.0, 1.0]$ after aggregation to ensure valid image output [S1, unofficial].

## Subtopics

### Pixel Block Scheduling
A load balancing strategy for distributed 3D Gaussian Splatting training that groups pixels into 16x16 blocks to reduce scheduler overhead while maintaining workload balance across GPUs [S2]. It organizes all pixels from all images in a batch into a single row, divides them into blocks, and allocates these blocks to GPUs. This trades off scheduler overhead against uneven workloads due to additional blocks. After scheduling, a 2D boolean array `compute_locally[i][j]` indicates whether the pixel block at row $i$ and column $j$ should be computed by the local GPU. The GPU then renders only the pixels within the blocks where `compute_locally` is true [S2].

## Operating characteristics
*   **Time Complexity**: The method scales with the number of GPUs $M$ and the batch size. The dominant costs are the sparse all-to-all communication and the rendering/compositing steps. Dynamic load balancing aims to minimize the maximum runtime across GPUs [S1, unofficial][S2].
*   **Memory Complexity**: Memory usage per GPU is reduced by partitioning the global set of Gaussians $\mathcal{G}$ and the image plane. This allows training on scenes with tens of millions of Gaussians that would not fit in a single GPU's memory [S1, unofficial].
*   **Measured Performance**: On the "Rubble" dataset, distributing 40.4 million Gaussians across 16 GPUs achieved a test PSNR of 27.28, compared to 26.28 PSNR with 11.2 million Gaussians on a single GPU [S1, unofficial].
*   **Strengths**: Enables high-resolution and large-scale 3D reconstruction by overcoming single-GPU memory limits. Supports batched training for better GPU utilization.
*   **Limitations**: Requires complex communication patterns (sparse all-to-all). Load balancing is non-trivial due to the varying number of Gaussians affecting different pixels.
*   **When to Use**: Large-scale 3D reconstruction tasks requiring high resolution or large scene sizes that exceed single-GPU memory capacity.
*   **When Not to Use**: Small-scale scenes or real-time inference where the overhead of distributed communication outweighs the benefits.

## Background
The Distributed Batched Rendering Loop is part of the Grendel system, introduced by Kerbl et al. in the paper "On Scaling Up 3D Gaussian Splatting Training" [S2]. It builds on the original 3D Gaussian Splatting method [S1, unofficial] which was limited to single-GPU training. Grendel was designed to partition 3DGS parameters and parallelize computation across multiple GPUs, enabling the training of larger models on high-resolution scenes [S1, unofficial]. The method explores different learning rate scaling strategies, identifying a simple $\sqrt{\text{batch size}}$ scaling rule as highly effective [S1, unofficial].
