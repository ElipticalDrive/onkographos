# RoofGS

Also called: Roofline-Guided End-to-End Acceleration of 3D Gaussian Splatting

## Overview
RoofGS is an end-to-end acceleration method for 3D Gaussian Splatting (3DGS) that optimizes the rendering pipeline based on stage-specific hardware bottlenecks identified via the Roofline model [S1, unofficial]. It addresses the uncoordinated optimization problem where different stages are constrained by different resources: bandwidth-limited front-end stages prioritize reducing global memory traffic, while compute-intensive rasterization stages prioritize lower instruction cost and increased instruction-level parallelism (ILP) [S1, unofficial]. It sets itself apart from generic optimization by explicitly mapping memory-centric strategies (compression, fusion) to bandwidth-bound phases and compute-centric strategies (ILP, fast math) to arithmetic-bound phases [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** 3D Gaussian primitives defined by mean $\mu$, covariance $\Sigma$ (derived from scale $s$ and rotation $q$), opacity $\alpha$, and spherical harmonic (SH) coefficients for color/radiance.
*   **Output:** Rendered 2D image with alpha-blended colors.

**Data Structures:**
*   **Gaussian Attributes:** Stored in a compact format. For third-degree SHs ($D_{SH}=3$), the baseline requires 48 coefficients per RGB channel (192 bytes in single precision) [S1, unofficial]. RoofGS uses low-bit quantization with a single shared scale for all SH coefficients to reduce this footprint [S1, unofficial].
*   **Depth Keys:** Used for sorting. RoofGS employs dynamic depth-key compression to reduce the size of keys passed to the radix sort [S1, unofficial].

**Method Steps:**
The pipeline is divided into two optimization phases:

1.  **Memory-Bound Optimization (Front-End):**
    *   **Compact Attribute Storage:** Quantize SH coefficients using a single shared scale to reduce memory bandwidth demand during attribute streaming [S1, unofficial].
    *   **Dynamic Depth-Key Compression:** Compress the depth keys used for sorting primitives to reduce traffic during the sorting stage [S1, unofficial].
    *   **Cross-Stage Kernel Fusion:** Fuse adjacent kernels in the front-end pipeline to minimize intermediate global memory reads/writes [S1, unofficial].

2.  **Compute-Bound Optimization (Rasterization):**
    *   **Dual-Pixel ILP:** Reformulate the per-pixel Gaussian evaluation to increase instruction-level parallelism within the blending loop [S1, unofficial].
    *   **Fast Exponential Evaluation:** Optimize the computation of the Gaussian power and exponential function [S1, unofficial].

**Formulas:**
For each Gaussian-pixel pair, the baseline rasterizer evaluates the Gaussian power $p(x, y)$ as the exponent term:
$$
p(x, y) = -\frac{1}{2} \left( a(x - w)^2 + b(x - u)(y - v) + c(y - v)^2 \right)
$$
where $(x, y)$ is the target pixel coordinate, $(u, v)$ is the projected 2D Gaussian center, and $a, b, c, w$ are derived from the projected covariance matrix [S1, unofficial].

The unclamped opacity contribution $\tilde{\alpha}(x, y)$ is then:
$$
\tilde{\alpha}(x, y) = o \exp(p(x, y))
$$
where $o$ is the base opacity [S1, unofficial].

## Subtopics

### [Roofline-guided stage-wise optimization](9841-roofline-guided-stage-wise-optimization.md)
A methodology that uses stage-wise performance characterization to match optimization strategies to the dominant hardware constraints of the baseline pipeline, by reducing intermediate data movement in the front end and reducing arithmetic overhead in rasterization. It solves the problem of uncoordinated software optimization in volume rendering contexts, where different stages of the rendering pipeline are bottlenecked by different hardware resources (memory bandwidth vs. compute throughput). It sets itself apart from generic optimization by explicitly using the Roofline model to identify the "knee" point and applying memory-centric optimizations to stages below it and compute-centric optimizations to stages near it.

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Reduced compared to baseline 3DGS due to low-bit attribute compression and dynamic depth-key compression [S1, unofficial].
*   **Measured Performance:** Not given in the sources.
*   **Strengths:** Addresses both memory bandwidth and compute throughput bottlenecks simultaneously. Reduces global memory traffic in front-end stages and increases ILP in rasterization [S1, unofficial].
*   **Limitations:** Requires hardware-aware optimization (Roofline modeling). Quantization may introduce visual artifacts if not carefully calibrated [S1, unofficial].
*   **When to use:** When rendering 3DGS at high resolution or with many primitives where memory bandwidth or compute throughput is the bottleneck [S1, unofficial].
*   **When not to use:** For small-scale scenes where overhead of optimization might outweigh benefits, or on hardware where Roofline characteristics differ significantly from the target deployment [S1, unofficial].

## Background
RoofGS was introduced in the paper "RoofGS: Roofline-Guided End-to-End Acceleration of 3D Gaussian Splatting" [S1, unofficial]. It builds on prior roofline analyses [13, 43, 44] which identified the rasterization stage of 3DGS as compute-bound [S1, unofficial]. The method extends these insights by applying a holistic, stage-specific optimization strategy across the entire rendering pipeline, rather than focusing solely on the rasterizer [S1, unofficial].
