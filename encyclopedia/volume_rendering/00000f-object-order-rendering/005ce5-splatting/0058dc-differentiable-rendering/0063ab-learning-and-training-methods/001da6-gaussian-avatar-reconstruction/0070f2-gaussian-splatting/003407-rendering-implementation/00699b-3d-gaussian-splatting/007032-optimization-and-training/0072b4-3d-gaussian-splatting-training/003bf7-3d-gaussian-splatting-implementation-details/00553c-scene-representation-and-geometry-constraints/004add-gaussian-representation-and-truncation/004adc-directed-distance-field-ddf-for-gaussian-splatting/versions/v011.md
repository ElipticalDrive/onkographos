# Directed Distance Field (DDF) for Gaussian Splatting

Also called: Directed Distance Function, ray-query oracle

## Overview
The Directed Distance Field (DDF) is a neural implicit representation that serves as a constant-time, constant-memory ray oracle for 3D Gaussian Splatting (3DGS) scenes [S1, unofficial]. It solves the problem of performing secondary ray queries—such as shadows, ambient occlusion, and global illumination—without the computational cost of tracing individual Gaussians or the memory overhead of a Bounding Volume Hierarchy (BVH) [S1, unofficial]. Unlike sibling methods that scale linearly with the number of Gaussians or require iterative sphere tracing, the DDF answers any ray query with a single forward pass through a small neural network, making it suitable for real-time global illumination in large-scale captured scenes [S1, unofficial].

## How it works

### Inputs and Outputs
*   **Input:** A ray defined by an origin $\mathbf{x} \in \mathbb{R}^3$ and a unit direction $\mathbf{d} \in S^2$.
*   **Output:** A tuple $(t, \xi)$, where $t \in \mathbb{R}$ is the distance to the first surface along $\mathbf{d}$, and $\xi \in [0, 1]$ is a visibility value representing the probability that the ray hits the scene [S1, unofficial]. The hit point is $\mathbf{x} + t\mathbf{d}$ when $\xi$ is high [S1, unofficial].

### Data Structures
The DDF is implemented as a neural field with a fixed memory footprint of approximately 52 MB, independent of the scene size (number of Gaussians) [S1, unofficial].

1.  **Multiresolution Hash Grid (Point Encoding):**
    *   Encodes the 3D point $\mathbf{x}$.
    *   **Levels:** 16.
    *   **Features per level:** 2.
    *   **Entries per level:** $2^{19}$ (524,288).
    *   **Base resolution:** 16.
    *   **Growth factor:** 1.5.
    *   **Bounding Box:** A box bounding the normalized object.
    *   **Parameter Count:** $\approx 13$ million parameters.
2.  **Sinusoidal Encoding (Direction Encoding):**
    *   Encodes the direction $\mathbf{d}$.
    *   **Bands:** 4 sinusoidal bands.
3.  **Multilayer Perceptron (MLP):**
    *   **Architecture:** Two-layer MLP.
    *   **Width:** 64.
    *   **Input:** Concatenated features from the hash grid and direction encoding.
    *   **Output:** Scalar $t$ and scalar $\xi$.
    *   **Parameter Count:** $\approx 8,000$ parameters.

### Training Procedure

#### Supervision Data
The DDF is trained using samples of the form $(\mathbf{x}, \mathbf{d}, t_{target}, \xi_{target})$ [S1, unofficial]. Three sources of supervision are used:
1.  **GS-Rendered Depth:** Cheap supervision from camera rays, but blurry for thin features [S1, unofficial].
2.  **Neural Surface Sphere Tracing:** Clean distances obtained by sphere tracing a neural surface (e.g., NeuS) fit to the same images. This is mesh-free and recovers thin features [S1, unofficial].
3.  **Ground-Truth Mesh Ray Casting:** Used as an upper bound for evaluation, requiring a mesh [S1, unofficial].

#### Self-Consistency Loss
To sharpen thin features and ensure consistency along rays, a self-consistency term is added [S1, unofficial]. For a ray hitting at distance $t$, a point shifted forward by distance $s$ along the ray is sampled. The DDF evaluated at this shifted point must predict distance $t-s$ [S1, unofficial]. 30% of each training batch is replaced with these ray-march shifted points [S1, unofficial].

#### Loss Function
The total loss is a combination of distance and visibility terms [S1, unofficial]:
$$ L = \text{ClampedL1}(t_{pred}, t_{target}) + 0.3 \times \text{BCE}(\xi_{pred}, \xi_{target}) $$
*   **ClampedL1:** The L1 loss on distance is clamped to a maximum value (the box scale) to prevent far-away surfaces from dominating the gradient [S1, unofficial].
*   **BCE:** Binary Cross-Entropy on the hit flag $\xi$ [S1, unofficial].

#### Optimization Parameters
*   **Optimizer:** Adam.
*   **Steps:** 30,000.
*   **Batch Size:** 16,384 rays.
*   **Learning Rate:** $3 \times 10^{-3}$, decayed by cosine schedule to 5% of its initial value [S1, unofficial].
*   **Hardware:** Single A100 GPU; training takes under one hour per object [S1, unofficial].

### Pseudocode

```python
import torch
import torch.nn as nn
import math

class DDF:
    def __init__(self, num_levels=16, features_per_level=2, 
                 num_entries=2**19, base_resolution=16, growth_factor=1.5, 
                 mlp_width=64, num_directional_bands=4):
        """
        Initializes the Directed Distance Field.
        """
        self.num_levels = num_levels
        self.features_per_level = features_per_level
        self.num_entries = num_entries
        self.base_resolution = base_resolution
        self.growth_factor = growth_factor
        self.num_directional_bands = num_directional_bands
        
        # Multiresolution Hash Grid Encoding
        # Note: In practice, this uses a library like tinycudann for CUDA fusion.
        # Here we simulate the structure.
        self.hash_grid = MultiresolutionHashGrid(
            num_levels=num_levels,
            features_per_level=features_per_level,
            num_entries=num_entries,
            base_resolution=base_resolution,
            growth_factor=growth_factor
        )
        
        # Directional Encoding
        # 4 sinusoidal bands
        self.num_directional_features = num_directional_bands * 2 # sin and cos
        
        # MLP
        # Input dim: hash_grid_features + directional_features
        input_dim = (num_levels * features_per_level) + self.num_directional_features
        self.mlp = nn.Sequential(
            nn.Linear(input_dim, mlp_width),
            nn.ReLU(),
            nn.Linear(mlp_width, mlp_width),
            nn.ReLU(),
            nn.Linear(mlp_width, 2) # Output: t, xi
        )

    def encode_direction(self, d):
        """
        Encodes direction d using 4 sinusoidal bands.
        d: (..., 3) tensor
        """
        # Standard positional encoding for direction
        # bands = 4
        # frequencies = 2^0, 2^1, 2^2, 2^3
        frequencies = torch.tensor([2**i for i in range(self.num_directional_bands)], device=d.device)
        # d is (..., 3), frequencies is (4,)
        # We want to compute sin(2^k * pi * d) and cos(2^k * pi * d)
        # Reshape for broadcasting
        d = d.unsqueeze(-1) # (..., 3, 1)
        frequencies = frequencies.view(1, 1, -1) # (1, 1, 4)
        
        # (..., 3, 4)
        scaled_d = d * frequencies * math.pi
        
        # (..., 3, 8)
        encoded = torch.cat([torch.sin(scaled_d), torch.cos(scaled_d)], dim=-1)
        
        # Reshape to (..., 12)
        return encoded.view(*d.shape[:-2], -1)

    def forward(self, x, d):
        """
        Forward pass of the DDF.
        x: (..., 3) ray origins
        d: (..., 3) ray directions (unit vectors)
        Returns: t (distance), xi (visibility)
        """
        # Encode point x
        x_features = self.hash_grid(x) # (..., 32)
        
        # Encode direction d
        d_features = self.encode_direction(d) # (..., 12)
        
        # Concatenate features
        combined = torch.cat([x_features, d_features], dim=-1) # (..., 44)
        
        # MLP
        output = self.mlp(combined) # (..., 2)
        
        t = output[..., 0]
        xi = torch.sigmoid(output[..., 1]) # Ensure xi is in [0, 1]
        
        return t, xi

    def compute_loss(self, t_pred, xi_pred, t_target, xi_target):
        """
        Computes the training loss.
        """
        # Clamped L1 loss for distance
        # Clamp to box scale. Assuming box_scale is a hyperparameter.
        box_scale = 1.0 # Example value, typically derived from bounding box
        l1_loss = torch.nn.functional.l1_loss(t_pred, t_target, reduction='none')
        l1_loss = torch.clamp(l1_loss, max=box_scale)
        l1_loss = l1_loss.mean()
        
        # BCE loss for visibility
        bce_loss = torch.nn.functional.binary_cross_entropy(xi_pred, xi_target)
        
        # Weighted sum
        loss = l1_loss + 0.3 * bce_loss
        return loss

class MultiresolutionHashGrid(nn.Module):
    def __init__(self, num_levels, features_per_level, num_entries, base_resolution, growth_factor):
        super().__init__()
        self.num_levels = num_levels
        self.features_per_level = features_per_level
        self.num_entries = num_entries
        self.base_resolution = base_resolution
        self.growth_factor = growth_factor
        
        # Initialize hash tables
        # In tinycudann, this is a single contiguous memory block
        # Here we simulate with a list of embeddings
        self.embeddings = nn.ParameterList([
            nn.Parameter(torch.randn(num_entries, features_per_level)) 
            for _ in range(num_levels)
        ])
        
        # Calculate resolutions for each level
        self.resolutions = [
            int(base_resolution * (growth_factor ** i)) 
            for i in range(num_levels)
        ]

    def forward(self, x):
        """
        Simulates the hash grid lookup.
        x: (..., 3)
        Returns: (..., num_levels * features_per_level)
        """
        # Note: This is a simplified simulation. 
        # Real implementation uses CUDA kernels for hashing and interpolation.
        # We assume x is normalized to [0, 1] or within the bounding box.
        
        batch_shape = x.shape[:-1]
        x = x.view(-1, 3)
        
        all_features = []
        
        for i in range(self.num_levels):
            # Map x to grid coordinates
            # Resolution for this level
            res = self.resolutions[i]
            
            # Normalize x to [0, res-1]
            # Assuming x is in [0, 1] for simplicity, or scaled by bounding box
            coords = x * (res - 1)
            
            # Get lower and upper integer coordinates
            x0 = torch.floor(coords).long()
            x1 = x0 + 1
            
            # Wrap around if necessary (periodic boundary)
            x0 = x0 % res
            x1 = x1 % res
            
            # Hash function: simple sum of coordinates modulo num_entries
            # Real tinycudann uses a more complex hash
            hash_x0 = (x0[:, 0] * 73856093 ^ x0[:, 1] * 19349663 ^ x0[:, 2] * 83492791) % self.num_entries
            hash_x1 = (x1[:, 0] * 73856093 ^ x1[:, 1] * 19349663 ^ x1[:, 2] * 83492791) % self.num_entries
            
            # Get embeddings
            emb_x0 = self.embeddings[i][hash_x0] # (N, features)
            emb_x1 = self.embeddings[i][hash_x1] # (N, features)
            
            # Trilinear interpolation weights
            # This is a simplified bilinear interpolation in 3D
            # Weights for x0 and x1
            w0 = 1 - (coords - x0.float())
            w1 = coords - x0.float()
            
            # Interpolate along each dimension
            # This part is complex to simulate perfectly without the actual CUDA kernel
            # We will just return the sum of embeddings for simplicity in this simulation
            # Real implementation: interpolate between 8 corners
            
            # Simplified: just average the two hashes for simulation
            # This is NOT correct for production, but demonstrates the structure
            features = (emb_x0 + emb_x1) / 2.0
            all_features.append(features)
            
        # Concatenate features from all levels
        result = torch.cat(all_features, dim=-1)
        return result.view(*batch_shape, -1)

# Training Loop Example
def train_ddf(ddf, dataloader, optimizer, num_steps=30000):
    ddf.train()
    for step in range(num_steps):
        # Sample batch of rays
        # x: (batch_size, 3), d: (batch_size, 3)
        # t_target: (batch_size,), xi_target: (batch_size,)
        x, d, t_target, xi_target = next(iter(dataloader))
        
        # Forward pass
        t_pred, xi_pred = ddf(x, d)
        
        # Compute loss
        loss = ddf.compute_loss(t_pred, xi_pred, t_target, xi_target)
        
        # Backward pass
        optimizer.zero_grad()
        loss.backward()
        optimizer.step()
        
        if step % 1000 == 0:
            print(f"Step {step}, Loss: {loss.item()}")
```

### Edge Cases and Pitfalls
*   **Thin Features:** Supervising only with GS-rendered depth blurs thin parts (e.g., mug handles, animal legs) because narrow structures are averaged away in soft Gaussians [S1, unofficial]. Clean distance supervision (from sphere-traced neural surfaces or ray-casted meshes) is required to recover thin geometry [S1, unofficial].
*   **Compact Objects:** For compact objects where shape Gaussian depth already captures the geometry, clean distance supervision may not help and can hurt if the sphere-traced point cloud is noisy, causing surface reconstruction to "fatten" the object [S1, unofficial].
*   **Learning from Images:** Learning directly from images (volume-rendering color loss) does not help recover thin parts because most sampled rays land on background, making the path from color to distance output weak [S1, unofficial]. Step-by-step tracing supervision is unstable due to sequential gradient issues [S1, unofficial].
*   **Ray Origin Limitation:** The oracle is accurate only for ray origins it was trained on, which lie on or near the surface. Rays starting far from any surface (e.g., a point on a ground plane below the object) fall outside this set, and the field may report occlusion too often [S1, unofficial].
*   **Ambient Occlusion Accuracy:** Ambient occlusion is weaker (21.3 dB) than shadows (30.3 dB) because averaging many rays accumulates small per-ray errors [S1, unofficial].

## Operating characteristics

### Time and Memory Complexity
*   **Time Complexity:** Constant time $O(1)$ per ray query. The DDF answers in a single forward pass, unlike sphere tracing (sequential loop) or BVH traversal (growing with scene size) [S1, unofficial].
*   **Memory Complexity:** Constant memory $O(1)$ with respect to the number of Gaussians. The field size is fixed at ~52 MB [S1, unofficial].

### Measured Performance
*   **Speed vs. Sphere Tracing SDF:** The DDF is 26 to 72 times faster than sphere tracing an equivalent neural surface [S1, unofficial].
*   **Speed vs. BVH:**
    *   On small scenes (few thousand Gaussians), RT-core BVH is faster per ray due to optimized hardware traversal [S1, unofficial].
    *   On large scenes (hundreds of thousands to millions of Gaussians), DDF becomes competitive or faster. At 1M Gaussians and 100K rays, DDF (with tinycudann) is 0.005 µs/ray vs. BVH 0.009 µs/ray [S1, unofficial].
    *   BVH latency rises by ~9x from 5K to 1M Gaussians, while DDF latency remains flat [S1, unofficial].
*   **Speed vs. Rasterization:**
    *   For sparse queries (1K-10K rays), DDF is 600+ times faster than re-rasterizing with gsplat [S1, unofficial].
    *   At full frame (1M rays), DDF ties rasterization (4.81 ms vs. 4.45 ms) because rasterization is bound by frame buffer writing [S1, unofficial].
*   **Quality (Global Illumination):**
    *   Reproduces reference ray-traced shadows at 30.3 dB [S1, unofficial].
    *   Reproduces ambient occlusion at 21.3 dB [S1, unofficial].
    *   Mesh-free oracle achieves 75.5% shadow-ray agreement, compared to 50.2% for frustum-only baseline and 94.8% for mesh-trained upper bound [S1, unofficial].
*   **Geometry Quality:**
    *   Chamfer distance mean improves from 0.082 to 0.065 (21% drop) when using clean distance supervision instead of GS depth [S1, unofficial].
    *   Hash grid encoding lowers Chamfer distance from 0.187 to 0.117 (37% drop) compared to sinusoidal MLP [S1, unofficial].

### Strengths and Limitations
*   **Strengths:**
    *   Constant time and memory regardless of scene size [S1, unofficial].
    *   No mesh required in the pipeline [S1, unofficial].
    *   No dependence on RT-core hardware [S1, unofficial].
    *   Supports arbitrary ray queries (shadows, AO, GI) [S1, unofficial].
*   **Limitations:**
    *   Ambient occlusion quality is lower than shadows due to error accumulation [S1, unofficial].
    *   Accuracy degrades for ray origins far from the training surface distribution [S1, unofficial].
    *   Mesh-free version is limited by the quality of the underlying neural surface (oversmoothing thin parts) [S1, unofficial].

### When to Use
*   Use when you need global illumination (shadows, AO) for large-scale Gaussian Splatting scenes without the overhead of BVH or mesh generation.
*   Use when scene size exceeds ~155k Gaussians, where BVH memory and latency become prohibitive.
*   Use in mesh-free pipelines or for inverse rendering where differentiable queries are needed.

### When Not to Use
*   Do not use for small scenes (<5k Gaussians) where RT-core BVH is significantly faster per ray.
*   Do not use if you need high-fidelity ambient occlusion, as it is weaker than shadows.
*   Do not use if ray origins are likely to be far from the surface (e.g., volumetric scenes with large empty spaces), as the field may report false occlusions.

## Background

### Origin
The Directed Distance Field (DDF) for Gaussian Splatting was introduced in the paper "Directed Distance Fields for Constant-Time Ray Queries on Gaussian Splatting" [S1, unofficial]. It utilizes multiresolution hash grid encoding from [8] (tinycudann) [S1, unofficial].

### History and Development
The method addresses the limitation of 3D Gaussian Splatting, which is a rasterizer and cannot natively trace secondary rays for global illumination [S1, unofficial]. Previous methods like 3D Gaussian Ray Tracing and RaySplats build BVHs over Gaussians, which scale poorly with scene size [S1, unofficial]. The DDF distills the Gaussian scene into a small neural field that acts as a ray oracle [S1, unofficial].

### Usage
The DDF is used as a secondary-ray oracle for global illumination, shadows, and ambient occlusion in 3D Gaussian Splatting scenes [S1, unofficial]. It is applicable to mesh-free pipelines, differentiable queries for inverse rendering, and moving scenes [S1, unofficial].
