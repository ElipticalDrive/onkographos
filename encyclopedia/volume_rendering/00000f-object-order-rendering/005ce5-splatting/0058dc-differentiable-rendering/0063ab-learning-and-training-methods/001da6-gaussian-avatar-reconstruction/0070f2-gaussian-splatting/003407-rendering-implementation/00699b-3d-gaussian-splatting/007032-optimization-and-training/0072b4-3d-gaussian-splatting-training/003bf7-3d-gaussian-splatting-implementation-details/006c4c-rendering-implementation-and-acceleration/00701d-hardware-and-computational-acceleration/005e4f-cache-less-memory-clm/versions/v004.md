# Cache-Less Memory (CLM)


## Overview
Cache-Less Memory (CLM) is a system design that enables the training and rendering of large or highly detailed 3D Gaussian Splatting scenes on a single consumer-grade GPU by offloading Gaussian parameters and optimizer computation to the CPU [S1]. It solves the problem of GPU memory exhaustion in large-scene training by leveraging sparsity and spatial locality to minimize GPU-CPU communication overhead [S1]. Unlike sibling methods that focus on sorting or tiling acceleration, CLM specifically addresses memory capacity limits through attribute-wise offloading and microbatch pipelining [S1].

## How it works
CLM operates by splitting Gaussian attributes based on their necessity for frustum culling, storing only selection-critical attributes on the GPU while keeping non-critical attributes and optimizer states on the CPU [S1]. The training loop is divided into microbatches (single images) to allow overlapping communication and computation [S1].

### Inputs and Outputs
*   **Input:** A set of training images/views; 3D Gaussian primitives defined by position, rotation, scale, color (spherical harmonics), and opacity [S1].
*   **Output:** Updated Gaussian parameters and rendered images [S1].

### Data Structures and Layout
Gaussian attributes are split into two sets [S1]:
1.  **Selection-critical attributes:** Position (3 floats), Rotation (4 floats), Scale (3 floats). These are stored in GPU memory for all Gaussians to enable frustum culling without loading all Gaussians [S1]. These constitute less than 20% (10 out of 59 floats) of a Gaussian's memory footprint [S1].
2.  **Non-critical attributes:** Color and Opacity. These are stored in CPU memory and loaded into GPU memory only when required [S1].

### Steps
1.  **Attribute-Wise Offload:** Store selection-critical attributes (position, rotation, scale) in GPU memory. Store non-critical attributes (color, opacity) in CPU memory [S1].
2.  **Frustum Culling:** Run frustum culling on the GPU using only the selection-critical attributes. A Gaussian is culled if it is outside 3 standard deviations ($3\sigma$) of its distribution [S1]. This determines the set of active Gaussians $S_i$ for microbatch $i$ [S1].
3.  **Precise Gaussian Caching:** When preparing microbatch $i+1$, identify the intersection of active Gaussians from the previous microbatch $S_i$ and the current microbatch $S_{i+1}$ [S1].
    *   Copy Gaussians in $S_i \cap S_{i+1}$ from microbatch $i$'s GPU tensors (already in GPU memory) [S1].
    *   Load Gaussians in $S_{i+1} \setminus S_i$ from CPU memory [S1].
4.  **Forward/Backward Pass:** Perform forward and backward passes for microbatch $i+1$ [S1].
5.  **Gradient Caching:** After microbatch $i$ finishes:
    *   Transfer gradients only for Gaussians in $S_i \setminus S_{i+1}$ to CPU [S1].
    *   Copy gradients for Gaussians in $S_i \cap S_{i+1}$ into microbatch $i+1$'s gradient buffer for accumulation [S1].
6.  **CPU Adam Update:** Perform Adam optimizer updates on the CPU for Gaussians that are no longer active in subsequent microbatches (i.e., those in $S_i \setminus S_{i+1}$ or finalized) [S1]. This overlaps with the forward/backward GPU computation of subsequent microbatches [S1].
7.  **Pipeline Order Optimization:** Schedule microbatches to maximize spatial locality (overlap) between consecutive microbatches [S1].

### Formulas and Parameters
*   **Culling Threshold:** Gaussians are culled if outside $3\sigma$ of the Gaussian's distribution [S1].
*   **TSP Formulation:** The scheduling problem is formulated as a Traveling Salesman Problem (TSP) where nodes are microbatches and the distance between microbatch $i$ and $j$ is the symmetric difference $|S_i \oplus S_j|$ [S1].
*   **Memory Overhead:** The memory overhead of double-buffering for pipelining is independent of scene and batch size [S1].

### Pseudocode
```python
# Initialization
# Store selection-critical attributes (pos, rot, scale) in GPU memory for all Gaussians
# Store non-critical attributes (color, opacity) in CPU memory
# Initialize optimizer states on CPU
# Define batch of images/views
# Schedule microbatches using TSP heuristic to maximize overlap

for each microbatch i in batch:
    # 1. Frustum Culling (GPU)
    # Use selection-critical attributes in GPU memory
    S_i = frustum_cull_gpu(selection_critical_attributes_gpu, camera_params)
    
    # 2. Precise Gaussian Caching (Data Transfer)
    # Identify intersection with previous microbatch
    if i > 0:
        S_prev = S_{i-1}
        S_common = S_i ∩ S_prev
        S_new = S_i \ S_common
        
        # Copy common Gaussians from previous GPU tensors
        gpu_params_gpu[S_common] = gpu_params_prev_gpu[S_common]
        
        # Load new Gaussians from CPU
        gpu_params_gpu[S_new] = cpu_params_cpu[S_new]
    else:
        # Load all active Gaussians from CPU
        gpu_params_gpu[S_i] = cpu_params_cpu[S_i]
        
    # 3. Forward and Backward Pass (GPU)
    # Process single image
    loss, gradients_gpu = forward_backward_gpu(gpu_params_gpu[S_i], camera_params, image_i)
    
    # 4. Gradient Caching (Data Transfer)
    if i > 0:
        S_prev = S_{i-1}
        S_common = S_i ∩ S_prev
        S_to_cpu = S_prev \ S_common
        
        # Transfer gradients for Gaussians not in next microbatch to CPU
        cpu_gradients_cpu[S_to_cpu] = gradients_gpu[S_to_cpu]
        
        # Copy gradients for common Gaussians to next microbatch's buffer
        gradients_next_buffer[S_common] = gradients_gpu[S_common]
    else:
        # Transfer all gradients to CPU
        cpu_gradients_cpu[S_i] = gradients_gpu[S_i]
        
    # 5. CPU Adam Update (CPU)
    # Update parameters for Gaussians that are finalized or not in next microbatch
    # This overlaps with the next microbatch's GPU computation
    if i == last_microbatch or S_to_cpu is not empty:
        cpu_optimizer_update(cpu_params_cpu[S_to_cpu], cpu_gradients_cpu[S_to_cpu])
        
    # Prepare for next microbatch
    gpu_params_prev_gpu = gpu_params_gpu
    S_{i-1} = S_i
```

## Subtopics

### CPU–GPU tiering
A data placement strategy for scenes exceeding GPU capacity, keeping geometric data for culling on the GPU and attributes/optimizer arrays on the CPU [S2, unofficial]. CLM implements this by keeping geometric data on the GPU and attributes/optimizer arrays on the CPU, using microbatching, prefetching, and caching [S2, unofficial]. GS-Scale coordinates CPU–GPU transfers through parameter forwarding and deferred updates [S2, unofficial]. TideGS uses SSD storage, loading the needed working set onto the GPU and overlapping prefetch, computation, and writeback [S2, unofficial].

## Operating characteristics
*   **Time and Memory Complexity:** The memory overhead of double-buffering for pipelining is independent of scene and batch size [S1].
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Allows training/rendering on a single consumer-grade GPU for large scenes [S1].
*   **Strengths:** Reduces GPU memory requirements by offloading non-critical attributes and optimizer computation to the CPU; overlaps communication with computation [S1].
*   **Limitations:** Requires CPU computation for Adam updates; relies on spatial locality for caching effectiveness [S1].
*   **When to use:** When GPU memory is insufficient to hold all Gaussian parameters for large scenes [S1].
*   **When not:** When CPU-GPU communication bandwidth is a bottleneck or when scenes lack spatial locality [S1].

## Background
CLM was introduced in the paper "CLM: Removing the GPU Memory Barrier for 3D Gaussian Splatting" [S1]. It extends effective GPU memory capacity by offloading Gaussian parameters and optimizer computation to the CPU, while leveraging observations from previous sections to reduce overhead from GPU-CPU communication and CPU computation [S1]. The design is agnostic to the rendering backend and can be ported to the Vulkan platform [S1].
