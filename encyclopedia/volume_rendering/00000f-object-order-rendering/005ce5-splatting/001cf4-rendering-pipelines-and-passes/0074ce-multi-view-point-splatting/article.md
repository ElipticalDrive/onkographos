# Multi-View Point Splatting

Also called: deferred blending multi-view splatting, single-pass multi-view point splatting

## Overview
Multi-View Point Splatting is a rendering algorithm designed for auto-stereoscopic displays that generates $N$ simultaneous perspective views in a single GPU rendering pass [S1]. It solves the linear performance degradation ($N \times t$) and memory overhead associated with standard multi-pass rendering by calculating view-specific intersections on a per-fragment basis [S1]. Unlike conventional approaches that render $N$ full-resolution frame buffers and combine them via masking, this method exploits GPU programmability to interleave views directly into the final spatial image, supporting full resolution without sub-resolution artifacts [S1].

## How it works
The method renders point splats (typically Gaussian or disk primitives) once per frame. For each fragment generated by the rasterizer, the shader calculates the intersection with the splat for each required view zone. In systems using wavelength-selective filters, the Red, Green, and Blue sub-pixels correspond to three different view zones, requiring three distinct intersection calculations per fragment [S1].

### Inputs and Outputs
*   **Inputs:**
    *   Point set $S$: A collection of point samples $\mathbf{p}_i$ with associated properties (position, normal $\mathbf{n}_i$, radius $r_i$, density/color).
    *   Display parameters: Number of views $N$, focal distance $f_d$, maximal view eccentricity $v_d$, and horizontal LCD panel resolution $m$ [S1].
    *   Camera parameters: View matrices for the $N$ virtual cameras, positioned to create off-axis asymmetric sheared view frusta with parallel view directions [S1].
*   **Outputs:**
    *   A single spatial image buffer where pixels are interleaved to form view zones for the auto-stereoscopic display [S1].

### Data Structures
The point set $S$ is stored as a buffer of primitives. Each primitive $i$ contains:
*   $\mathbf{p}_i$: 3D position vector $(x, y, z)$.
*   $\mathbf{n}_i$: Normal vector.
*   $r_i$: Projected radius in screen space (or object space, transformed later).
*   Color/Density attributes.

### Numbered Steps

1.  **Calculate Covering Quad:**
    For each splat, compute an enlarged quadrilateral in screen space that covers the splat's projection across all $N$ views. This accounts for parallax shifts.
    *   Determine the horizontal offset $off$ required to cover the worst-case orientation where the splat normal $\mathbf{n}$ is orthogonal to the focal and camera planes [S1].
    *   Calculate offset using the formula:
        $$ off = v_d \cdot (d - f_d) \cdot d^{-1} $$
        Where $d$ is the depth of the splat (distance from camera), $f_d$ is the focal distance, and $v_d$ is the maximal view eccentricity [S1].
    *   The quad corners $\mathbf{q}$ are defined by extending the projected splat radius $r$ horizontally by $off$ and vertically by the projected height. The horizontal extent includes the parallax shift term $v_d \cdot (\mathbf{p}.z \cdot f_d^{-1})$ [S1].
    *   *Note:* The source provides the start of the corner formula but cuts off. The vertical extent is simply the projected height of the splat. The horizontal extent is $p.x \pm (r + off + \text{parallax term})$.

2.  **Rasterization with Per-Fragment View Calculation:**
    Rasterize the enlarged quads. For each fragment covered by a quad:
    *   Identify which view zone the fragment belongs to. For wavelength-selective displays, the view index $V$ is determined by the sub-pixel component (R, G, or B) [S1].
    *   Calculate the intersection of the fragment's screen position with the splat for the specific view $V$. This involves transforming the splat center $\mathbf{p}$ and the fragment position into the view space of camera $V$ [S1].
    *   Compute the contribution (color/density) based on the splat kernel (e.g., Gaussian) evaluated at the intersection point for view $V$ [S1].

3.  **Deferred Blending:**
    Accumulate contributions from all overlapping splats for the specific view zone of the current fragment using alpha blending. Since the geometry is processed once, the $\epsilon$-z-buffering (fuzzy visibility test) must handle occlusion across the different view perspectives [S1].

4.  **Image Composition:**
    The final image is written directly to the frame buffer. No separate masking or compositing pass is required because the view assignment is handled during the per-fragment intersection calculation [S1].

### Formulas

**Horizontal Display Resolution:**
For wavelength-selective filter arrays, the effective horizontal resolution $X_{Res}$ for $N$ views is:
$$ X_{Res} = \frac{m}{N} \cdot 3 $$
Where $m$ is the horizontal pixel resolution of the LCD panel [S1].

**Splat Covering Offset:**
$$ off = v_d \cdot \frac{d - f_d}{d} $$
Where:
*   $v_d$: Maximal view eccentricity [S1].
*   $d$: Depth of the splat [S1].
*   $f_d$: Focal distance [S1].

**Quad Corners (Horizontal):**
$$ \mathbf{q}.x = \mathbf{p}.x \pm \left( r + v_d \cdot \frac{\mathbf{p}.z}{f_d} + off \right) $$
*Note: The source formula is incomplete: $\mathbf{q}.x = (\mathbf{p}.x \pm (r + vd \cdot (\mathbf{p}.z \cdot fd^{-1})...$. The term $vd \cdot (\mathbf{p}.z \cdot fd^{-1})$ represents the parallax shift. The offset $off$ is added to ensure coverage of the worst-case orientation [S1].*

### Parameters
*   $N$: Number of views (view zones). Typical values depend on the display (e.g., $N=8$ in benchmarks) [S1].
*   $K$: Sub-pixel resolution constant. $K=3$ for RGB wavelength-selective views [S1].
*   $f_d$: Focal distance, matching the focal plane of the auto-stereoscopic display [S1].
*   $v_d$: Maximal view eccentricity, used to calculate the horizontal offset [S1].

### Edge Cases and Pitfalls
*   **Parallax Handling:** For multiple viewpoints, projections of the same pixel may not lie on the same surface element. The algorithm must correctly handle splat intersections per view to avoid artifacts [S1].
*   **Filter Arrays:** The method is optimized for wavelength-selective filters. For lenticular sheets (no sub-pixel view resolution), the performance advantage increases by up to a factor of three compared to conventional rendering, but the constant $K$ changes (likely $K=1$ or requires different handling) [S1].
*   **Quad Size:** The enlarged quad must be large enough to cover the splat's movement across all views. Failure to account for the worst-case orientation (normal orthogonal to focal plane) will result in missing pixels at the edges of view zones [S1].

### Pseudocode

> **Unverified code.** The code below did not pass a test run against a reference implementation, or no test fits it, so it may contain errors.

```python
# Vertex Shader / Geometry Shader Stage
function RenderMultiViewSplat(splat):
    # Calculate the enlarged covering quad for all N views
    # d is the depth of the splat center in camera space
    d = splat.position.z
    
    # Calculate horizontal offset for worst-case parallax coverage
    # vd: maximal view eccentricity, fd: focal distance
    off = vd * (d - fd) / d
    
    # Parallax shift term based on splat depth and focal distance
    parallax_shift = vd * (splat.position.z / fd)
    
    # Base projected radius r (computed from MVP matrix and splat radius)
    r = splat.projected_radius
    
    # Define quad corners in screen space
    # Horizontal extent covers all view zones
    left = splat.screen_x - (r + off + parallax_shift)
    right = splat.screen_x + (r + off + parallax_shift)
    
    # Vertical extent covers the splat height (h)
    top = splat.screen_y + splat.screen_height / 2
    bottom = splat.screen_y - splat.screen_height / 2
    
    # Output quad vertices to rasterizer
    return Quad(left, top, right, bottom)

# Fragment Shader Stage
function FragmentShader(fragment_pos, fragment_color_channel):
    # fragment_color_channel identifies the view zone (e.g., 0 for R, 1 for G, 2 for B)
    # For wavelength-selective displays, this maps to a specific view index V
    
    # Determine the view index V based on the sub-pixel channel
    # Assuming N views and 3 channels, mapping logic depends on display layout
    # Simplified: V = fragment_color_channel (for K=3 case)
    V = fragment_color_channel 
    
    # Get the current splat being rasterized
    splat = GetActiveSplat()
    
    # Transform splat center and fragment position to View V's space
    # This accounts for the different camera positions for each view
    view_matrix_V = GetViewMatrix(V)
    splat_center_V = view_matrix_V * splat.position
    frag_pos_V = view_matrix_V * fragment_pos
    
    # Calculate the distance from the fragment to the splat center in View V
    # This determines the kernel weight for this specific view
    dx = frag_pos_V.x - splat_center_V.x
    dy = frag_pos_V.y - splat_center_V.y
    
    # Evaluate splat kernel (e.g., Gaussian)
    # sigma is the splat's standard deviation in view space
    weight = exp(-(dx*dx + dy*dy) / (2 * sigma*sigma))
    
    # Apply alpha blending with existing buffer content
    # This handles the deferred blending and occlusion (epsilon-z-buffering)
    current_alpha = FrameBuffer[fragment_pos].alpha
    new_alpha = weight * splat.alpha
    
    # Blend color
    FrameBuffer[fragment_pos].color = Blend(current_alpha, FrameBuffer[fragment_pos].color, new_alpha, weight * splat.color)
    FrameBuffer[fragment_pos].alpha = current_alpha + new_alpha * (1 - current_alpha)
```

## Operating characteristics
*   **Time Complexity:** $O(K \cdot t)$, where $t$ is the time for a single mono-view rendering pass and $K$ is the sub-pixel resolution constant (typically 3 for RGB) [S1]. This is independent of the number of views $N$.
*   **Memory Complexity:** $O(1)$ additional memory for frame buffers compared to single-view rendering, as it avoids storing $N$ full-resolution buffers [S1].
*   **Performance:** Benchmarks for $N=8$ views and a $512 \times 512$ window show:
    *   Balljoint (137k points): 18 fps [S1].
    *   Female (303k points): 15 fps [S1].
    *   Dragon (1,100k points): 10 fps [S1].
*   **Strengths:**
    *   Eliminates the $N$-fold cost of multi-pass rendering.
    *   Supports full resolution without sub-resolution artifacts.
    *   No post-processing masking or compositing passes required.
*   **Limitations:**
    *   Requires programmable GPUs (fragment shaders).
    *   Performance advantage is most significant for large $N$ and large datasets where geometry processing is the bottleneck.
    *   Relies on specific display hardware (auto-stereoscopic with wavelength-selective filters or lenticular sheets) [S1].

## Background
The method was introduced by Thomas Hübner, Yanci Zhang, and Renato Pajarola from the Visualization and MultiMedia Lab at the University of Zürich [S1]. It addresses the limitations of existing auto-stereoscopic libraries like the Interactive Stereo Library (ISL) from SGI, which rendered $N$ views individually into $N$ frame buffers, incurring $N \times t$ cost and requiring masking [S1]. The work builds on point splatting techniques described by Pfister et al. [S1].
