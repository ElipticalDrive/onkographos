# Fragment List-Based Rendering Pipeline

Also called: 4-Stage Rendering Pipeline, Smoker Rendering Pipeline

## Overview
The Fragment List-Based Rendering Pipeline is a multi-pass architecture for real-time smoke volume rendering that processes geometry through four distinct stages to store per-pixel fragment data in GPU memory structures [S1, unofficial]. It is chosen to maintain high accuracy and circumvent the self-intersection and global intersection problems inherent in raytracing approaches [S1, unofficial]. Unlike the [Volume Rendering Pipeline](1318-volume-rendering-pipeline.md) which typically evaluates rays directly, or the [Deferred Rendering Pipeline](10584-deferred-rendering-pipeline.md) which separates shading from geometry, this method explicitly decouples fragment construction and insertion from their final evaluation to manage complex storage requirements [S1, unofficial].

## How it works
The pipeline consists of four sequential stages executed by three distinct shader programs: Clear, Render (combining Construction and Insertion), and Display (Evaluation) [S1, unofficial].

**Inputs and Outputs:**
*   **Input:** Smoke volume geometry (triangles), vertex attributes (position, density, flow tangents), and OpenGL buffer objects for fragment storage.
*   **Output:** Final rendered image on the screen buffer.

**Data Structures:**
*   **Fragment Storage:** A GPU-accessible data structure (e.g., atomic counter array, linked list, or buffer) capable of storing per-pixel fragment information. The exact layout depends on the specific visualization method (e.g., simple pixel count vs. complex storage structure) [S1, unofficial].
*   **OpenGL Buffers:** Various buffer objects used for inter-stage communication and reset states [S1, unofficial].

**Steps:**

1.  **Clear Stage:**
    *   Reset all OpenGL buffer objects required for the subsequent frame.
    *   This is initiated by rendering a single screen-filling quad using the **Clear** shader program [S1, unofficial].

2.  **Construction Stage:**
    *   **Vertex Shader:** Performs perspective transformation on vertices. Assigns additional vertex data such as density and flow tangents [S1, unofficial].
    *   **Geometry Shader:** Assembles primitives from vertices. Processes triangle-related data including orientation, topology, and volume information. Forwards the processed results to the Insertion stage [S1, unofficial].
    *   This stage is part of the **Render** shader program [S1, unofficial].

3.  **Insertion Stage:**
    *   **Rasterization:** Primitives constructed in the previous stage are rasterized.
    *   **Fragment Shader:** Processes incoming fragments. The processing logic varies by visualization method, ranging from a simple pixel counter to inserting fragments into a complicated storage data structure [S1, unofficial].
    *   **Constraint:** The type of fragment processing must be compatible with the subsequent Evaluation step [S1, unofficial].
    *   This stage is part of the **Render** shader program [S1, unofficial].

4.  **Evaluation Stage:**
    *   Render a single screen-filling quad using the **Display** shader program.
    *   Interpret and visualize the per-pixel information that was prepared and stored during the Insertion stage [S1, unofficial].

**Parameters:**
*   **Shader Programs:** Clear, Render, Display [S1, unofficial].
*   **Visualization Method:** Determines the complexity of the Insertion stage (e.g., pixel counter vs. complex storage) [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Concurrent Modification:** The Insertion step is the greatest bottleneck due to simultaneous access to shared indexing mechanisms. Unmanaged concurrent access to shared memory can leave it in an inconsistent state because shader threads cannot check if a shared address is currently being modified [S1, unofficial].
*   **Compatibility:** The fragment processing in the Insertion stage must be strictly compatible with the Evaluation step; mismatched data structures will result in incorrect visualization [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Depends on the storage data structure used in the Insertion stage. Complex storage structures require more memory than simple counters [S1, unofficial].
*   **Performance:** The Insertion step is identified as the greatest bottleneck of the entire rendering pipeline due to concurrent access issues [S1, unofficial].
*   **Strengths:** Maintains high accuracy; circumvents raytracing self-intersection and global intersection problems [S1, unofficial].
*   **Limitations:** Concurrent modification of shared memory requires careful management to avoid bottlenecks and inconsistent states [S1, unofficial].
*   **When to use:** Real-time smoke volume rendering where accuracy is prioritized over the simplicity of raytracing [S1, unofficial].
*   **When not to use:** When hardware lacks support for the required OpenGL buffer objects or atomic operations needed for safe concurrent memory access [G].

## Background
The Fragment List-Based Rendering Pipeline was implemented in the **Smoker** application for real-time smoke volume rendering [S1, unofficial]. It was developed as part of a master's thesis by Dirk Sowinski in 2012 [S1, unofficial]. The pipeline was chosen over raytracing to avoid problems arising from raytracing and self or global intersections [S1, unofficial]. The implementation allows switching between different rendering strategies during runtime without re-initializing the smoke volume, facilitating comparison of approaches using identical configurations [S1, unofficial].
