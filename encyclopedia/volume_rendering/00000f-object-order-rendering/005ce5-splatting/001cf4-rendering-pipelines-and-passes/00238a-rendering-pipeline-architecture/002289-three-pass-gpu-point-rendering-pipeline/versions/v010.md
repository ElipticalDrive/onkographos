# Three-Pass GPU Point Rendering Pipeline

Also called: Hardware Accelerated Point Splatting Pipeline

## Overview
The Three-Pass GPU Point Rendering Pipeline is a hardware-accelerated method for point splatting that separates depth testing, color accumulation, and normalization into distinct rendering stages to handle transparency and perspective distortion correctly [S1, unofficial]. It differs from single-pass approaches by explicitly accumulating filter weights to enable accurate normalization of the final color under perspective projection [S1, unofficial].

## How it works
The pipeline renders a volume represented as a set of points (splats) using standard GPU rasterization capabilities, specifically leveraging `GL_POINTS` primitives [S1, unofficial].

### Inputs and Outputs
*   **Input:** A set of $N$ 3D points $\mathbf{p}_i$, each associated with a color $\mathbf{c}_i$ and a reconstruction kernel (typically Gaussian) [S1, unofficial].
*   **Output:** A 2D image where each pixel contains the normalized color value $\mathbf{C}_{final}(x,y)$ [S1, unofficial].

### Data Structures
The method relies on standard GPU framebuffers:
1.  **Depth Buffer:** Stores the depth $z$ of the closest splat fragment [S1, unofficial].
2.  **Color Accumulation Buffer:** Stores the weighted sum of colors $\sum \mathbf{c}_i w_i$ [S1, unofficial].
3.  **Weight Accumulation Buffer:** Stores the sum of weights $\sum w_i$ [S1, unofficial].

### Steps
1.  **Pass 1: Depth Offset Rendering**
    *   Render the scene using `GL_POINTS` [S1, unofficial].
    *   The vertex shader computes the screen-space position and the depth [G].
    *   The depth value written to the depth buffer is offset slightly along the viewing ray [S1, unofficial].
    *   No color or weight accumulation occurs in this pass; only the depth buffer is updated [S1, unofficial].

2.  **Pass 2: Weighted Accumulation**
    *   Render the splats again using `GL_POINTS` [S1, unofficial].
    *   **Depth Test:** Enable depth testing but disable depth buffer updates [S1, unofficial]. Use the depth value from the splat's center to compare against the depth buffer populated in Pass 1 [G]. Only fragments that pass the depth test are processed [S1, unofficial].
    *   **Fragment Shader:** Compute the 2D footprint of the splat on the screen, often involving the variance matrix of the resampling filter ($R_0 + H$ or approximation $Q_{000}$) [S1, unofficial]. Calculate the weight $w_i$ for the fragment based on the distance from the splat center and the kernel variance [G]. Accumulate the weighted color and the weight additively in the framebuffer [S1, unofficial].

3.  **Pass 3: Normalization**
    *   Render a full-screen quad or use a post-processing pass [G].
    *   For each pixel, retrieve the accumulated color and accumulated weight [G].
    *   Compute the final color by dividing the accumulated color by the accumulated weight [S1, unofficial].

### Pseudocode
```python
def three_pass_pipeline(points, width, height, view_proj_matrix):
    # Pass 1: Depth offset rendering
    depth_buffer = [float('inf')] * (width * height)
    for p in points:
        clip = view_proj_matrix.transform(p.position)
        if clip.w > 0:
            uv = (clip.xy / clip.w).astype(int)
            if 0 <= uv[0] < width and 0 <= uv[1] < height:
                idx = uv[1] * width + uv[0]
                offset_depth = clip.z + clip.z * 1e-4  # [G] small fraction along viewing ray
                if offset_depth < depth_buffer[idx]:
                    depth_buffer[idx] = offset_depth

    # Pass 2: Weighted accumulation
    color_accum = [0.0] * (width * height * 3)
    weight_accum = [0.0] * (width * height)
    for p in points:
        clip = view_proj_matrix.transform(p.position)
        if clip.w > 0:
            uv = (clip.xy / clip.w).astype(int)
            if 0 <= uv[0] < width and 0 <= uv[1] < height:
                idx = uv[1] * width + uv[0]
                if depth_buffer[idx] <= clip.z:  # [G] depth test against offset buffer
                    variance = compute_variance(p, view_proj_matrix)  # [G]
                    weight = compute_kernel_weight(uv, p.center, variance)  # [G]
                    for c in range(3):
                        color_accum[idx * 3 + c] += p.color[c] * weight
                    weight_accum[idx] += weight

    # Pass 3: Normalization
    final_image = [0.0] * (width * height * 3)
    for i in range(width * height):
        w = weight_accum[i]
        if w > 0:
            for c in range(3):
                final_image[i * 3 + c] = color_accum[i * 3 + c] / w
        else:
            final_image[i * 3 + c] = 0.0
    return final_image

def compute_variance(point, view_proj_matrix):
    # Standard EWA variance matrix computation from projection Jacobian [G]
    return point.kernel_variance * view_proj_matrix.jacobian

def compute_kernel_weight(uv, center, variance_matrix):
    # Gaussian weight based on Mahalanobis distance [G]
    diff = uv - center
    return exp(-0.5 * diff.T @ variance_matrix @ diff)
```

### Parameters and Edge Cases
*   **Variance Matrix Inversion:** Computing the screen-space kernel variance requires inverting the projective mapping. This can be numerically ill-conditioned if the splat degenerates into a line segment (viewing direction parallel to the splat normal) [S1, unofficial].

## Subtopics

### Standard Point Splatting Assembly
This variant refers to the core assembly logic for point splatting, writing point colors to a canvas based on depth sorting and a fixed or implicit radius [S2, unofficial]. It initializes canvases (`depth_canvas` filled with `float('inf')`, `color_canvas` and `label_canvas` with zeros, `index_canvas` with -1), sorts points by depth in ascending order, and iterates to write colors to pixels where the point's depth is less than the current depth at that pixel [S2, unofficial]. After processing all points, it creates a written mask where `depth_canvas < float('inf')` and sets color, label, and index to 0 (or -1 for index) for pixels not written to [S2, unofficial].

### [Point Cloud Rendering](6750-point-cloud-rendering.md)
Point Cloud Rendering treats raw 3D point data as discrete sprites or spheres to generate 2D images, serving as a bridge between explicit geometric representations and differentiable rendering pipelines. Unlike mesh-based rendering which relies on rasterization of triangles, or voxel-based methods which fill space with grid cells, point cloud rendering directly projects individual points, often using spatial influence functions to handle sparsity and occlusion. It is distinct from its sibling [Deferred Splatting with Temporal Coherency and Bi-Bi-1 Visibility Pass](12274-deferred-splatting-with-temporal-coherency-and-bi-bi-1-visib.md) by its focus on explicit point-to-pixel aggregation rather than deferred visibility buffers, and from [Three-Pass GPU Point Rendering Pipeline](2837-three-pass-gpu-point-rendering-pipeline.md) by its specific algorithmic choices for influence calculation and occlusion handling.

### [Deferred Splatting with Temporal Coherency and Bi-Bi-1 Visibility Pass](12274-deferred-splatting-with-temporal-coherency-and-bi-bi-1-visib.md)
A rendering algorithm that reduces the performance cost of high-quality point-based rendering by performing expensive Elliptical Weighted Average (EWA) splatting computations only on visible surfels, using a multi-pass approach similar to deferred shading. It separates visibility determination from color accumulation, using temporal coherency to accelerate the visibility pass and a secondary visibility pass ($B_i - B_{i-1}$) to fix artifacts caused by hidden points becoming visible. Unlike previous methods that perform low-level selection entirely by the GPU during rendering, this method performs low-level selection (visibility culling) explicitly before the expensive EWA splatting pass, allowing the expensive filtering to be skipped for hidden points.

### [Progressive Point Cloud Rendering](20586-progressive-point-cloud-rendering.md)
A rendering technique where a point cloud is drawn in multiple passes over several frames, progressively increasing the density of visible points until the full dataset is displayed.

## Background
The three-pass approach for hardware-accelerated point splatting was developed to address the limitations of earlier methods that struggled with perspective accuracy and transparency [S1, unofficial]. It builds on the fundamental splatting principle of decomposing volumetric data into primitives and rasterizing them [S1, unofficial]. The specific technique of using a depth offset pass and separate accumulation/normalization passes was introduced to ensure correct weighting under perspective projection [S1, unofficial].
