# Radix Sort for Splat Depth

Also called: 16-bit Radix Sort for Splatting, Depth Sorting via Radix Sort, Tsplat depth sort

## Overview
This method sorts projected 3D Gaussian splats by their depth values to establish a front-to-back rendering order, which is critical for correct alpha blending of translucent splats [S1, unofficial]. It distinguishes itself from comparison-based sorts by leveraging the bit-pattern ordering of IEEE 754 floating-point numbers to achieve $O(n)$ time complexity with small constants, resulting in performance that is consistently 2 times faster for ~100k–200k elements [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A list of `projected` splats, where each splat contains a `depth` field (f32) [S1, unofficial].
- Output: The `projected` list sorted in ascending order of `depth` (front-to-back) [S1, unofficial].
- Auxiliary: `aux` buffer of same size as `projected`; `counts_lo`, `counts_hi` histogram arrays; `offsets` prefix sum array [G].

**Data Structures:**
- `projected`: Array of splat structs. Each struct has `depth: f32` [S1, unofficial].
- `counts_lo`, `counts_hi`: Arrays of `u32` with size 65,536 ($2^{16}$) [S1, unofficial].
- `offsets`: Array of `u32` with size 65,536 [G].
- `aux`: Array of splat structs, same size as `projected` [G].

**Parameters:**
- Parallel sort threshold: 50,000 splats. If splat count < 50,000 or no thread pool is available, use sequential radix sort. Otherwise, use a parallel unstable sort on depth bit patterns [S1, unofficial].

**Algorithm Steps:**
1. **Edge Case:** If the number of splats is $\le 1$, return immediately [S1, unofficial].
2. **Histogram Initialization:** Initialize `counts_lo` and `counts_hi` to zero [S1, unofficial].
3. **Histogram Population:** Iterate through each splat in `projected`:
   - Let $k$ be the bit pattern of `splat.depth` reinterpreted as a `u32` [S1, unofficial].
   - Increment `counts_lo[(k & 0xFFFF)]` [S1, unofficial].
   - Increment `counts_hi[(k >> 16)]` [S1, unofficial].
4. **Pass 1 (Low 16 bits):**
   - Compute prefix sums of `counts_lo` into `offsets` [S1, unofficial].
   - Scatter splats from `projected` to `aux` based on the low 16 bits of their depth bit pattern ($k \& 0xFFFF$) [S1, unofficial].
5. **Pass 2 (High 16 bits):**
   - Compute prefix sums of `counts_hi` into `offsets` [S1, unofficial].
   - Scatter splats from `aux` back to `projected` based on the high 16 bits of their depth bit pattern ($k >> 16$) [S1, unofficial].

**Pseudocode:**
```python
def sort_by_depth(projected: list, aux: list, counts_lo: list, counts_hi: list, offsets: list) -> None:
    n = len(projected)
    if n <= 1:
        return

    # Parallel threshold check
    if n >= 50000:
        # Use a parallel unstable sort on depth bit patterns [G]
        projected.sort(key=lambda s: s.depth.to_bits())
        return

    # Reset histograms
    for i in range(65536):
        counts_lo[i] = 0
        counts_hi[i] = 0

    # Populate histograms
    for splat in projected:
        k = splat.depth.to_bits()  # Reinterpret f32 bits as u32 [G]
        counts_lo[k & 0xFFFF] += 1
        counts_hi[k >> 16] += 1

    # Pass 1: Sort by low 16 bits
    # Compute exclusive prefix sums for offsets
    offsets[0] = 0
    for i in range(1, 65536):
        offsets[i] = offsets[i-1] + counts_lo[i-1]

    # Scatter to aux
    for splat in projected:
        k = splat.depth.to_bits()
        bucket = k & 0xFFFF
        idx = offsets[bucket]
        aux[idx] = splat
        offsets[bucket] += 1

    # Pass 2: Sort by high 16 bits
    # Compute exclusive prefix sums for offsets
    offsets[0] = 0
    for i in range(1, 65536):
        offsets[i] = offsets[i-1] + counts_hi[i-1]

    # Scatter back to projected
    for splat in aux:
        k = splat.depth.to_bits()
        bucket = k >> 16
        idx = offsets[bucket]
        projected[idx] = splat
        offsets[bucket] += 1
```

**Edge Cases and Pitfalls:**
- **Float Bit Pattern:** This method relies on positive float bit patterns preserving ordering when reinterpreted as `u32` [S1, unofficial].
- **Precision:** The method uses the full 32-bit float representation. No precision loss occurs during the bit reinterpretation, but sorting stability is not guaranteed unless the secondary key (e.g., original index) is included, which is not done in this basic variant [S1, unofficial].

## Subtopics

### [Gaussian Sorting](2845-gaussian-sorting.md)
Gaussian Sorting orders 3D Gaussians by their distance from the camera to ensure correct alpha blending during rasterization. It solves the transparency accumulation problem by establishing a front-to-back draw order, which is critical because Gaussians with non-zero opacity must be rendered in depth order. It builds on [Radix Sort for Splat Depth](1207-radix-sort-for-splat-depth.md) by applying the radix sort to a global index buffer of Gaussian attributes rather than just projected splat depths.

### [Fast Splat Sorting](2953-fast-splat-sorting.md)
Fast Splat Sorting is an optimization for volume rendering pipelines that replaces the single 48-bit combined tileID+depth radix sort with two sequential, smaller-key sorts: a 32-bit depth sort of visible splats followed by a 16-bit tileID sort of generated fragments. It sets itself apart from its parent [Radix Sort for Splat Depth](1207-radix-sort-for-splat-depth.md) by decoupling depth ordering from tile assignment, and from [Gaussian Sorting](2845-gaussian-sorting.md) by relying on explicit fragment duplication rather than implicit spatial partitioning. This separation reduces computational complexity by leveraging the fact that the number of visible splats ($n$) is typically smaller than the number of fragments ($m$).

### [Gaussian Splat Sorting](3372-gaussian-splat-sorting.md)
Gaussian Splat Sorting sorts projected 3D Gaussian splats front-to-back within screen-space tiles to enable correct alpha blending. It differs from its parent [Radix Sort for Splat Depth](1207-radix-sort-for-splat-depth.md) by operating on a per-tile basis using a combined tile-ID and depth key, and from [Gaussian Sorting](2845-gaussian-sorting.md) by relying on a simple monotonic depth proxy rather than complex geometric comparisons.

### [Default Camera Sort](7960-default-camera-sort.md)
Default Camera Sort is a compositing technique for oriented Gaussian ellipses (splats) that sorts them back-to-front relative to a camera viewpoint to ensure correct translucent blending. It differs from its siblings by automatically binding the sort order to the active scene camera without requiring explicit provider configuration.

### [32-bit Tile-Depth Pair Sorting](9408-32-bit-tile-depth-pair-sorting.md)
This method compresses the conventional 64-bit depth sorting key into 32 bits to reduce sorting traffic and the number of radix passes required for splat sorting. It differs from popular CUDA implementations that use 64-bit keys by mapping depth to a specific range where only the lower 23 mantissa bits vary, allowing tile IDs to occupy the minimum necessary higher bits. This optimization is particularly beneficial for Vulkan sorting implementations, which are often slower than CUDA's built-in sorting, while maintaining quality metrics comparable to 64-bit approaches.

### DistWar
DistWar is a method that accelerates sorting by exploiting hardware-accelerated visibility ordering in the rasterizer to perform a fast depth test and bypass the CUDA radix sort [S2, unofficial].

### Float16 to uint16 sorting conversion
This method converts float16 values to uint16 such that lexicographical comparison of the uint16 representation preserves the original float16 ordering [S3, unofficial]. It operates by viewing the tensor as uint16, casting to int32, XORing with the sign mask `0x8000`, and casting back to uint16 [S3, unofficial]. The constant `0x8000` flips the sign bit to ensure correct unsigned integer sorting [S3, unofficial].

## Operating characteristics
- **Time Complexity:** $O(n)$ for the radix sort passes, where $n$ is the number of splats [S1, unofficial]. The constant factor is small due to the fixed 2-pass structure [S1, unofficial].
- **Memory Complexity:** $O(n)$ for the auxiliary buffer `aux` and $O(1)$ for the histogram arrays (fixed size 65,536) [S1, unofficial].
- **Performance:** Consistently 2 times faster than comparison-based sorts for ~100k–200k elements [S1, unofficial].
- **Strengths:** Linear time complexity, predictable performance, no recursion depth issues, efficient use of cache due to sequential memory access in scatter/gather phases [G].
- **Limitations:** Requires positive depth values. Not stable by default. Parallelization threshold must be tuned for specific hardware [G].
- **When to Use:** When sorting large numbers of splats for front-to-back rendering where performance is critical and depth values are positive [G].
- **When Not to Use:** When stability is required without additional overhead, or when depth values include negative numbers that are not handled by bit manipulation [G].

## Background
This method is described in the context of optimizing 3D Gaussian Splatting rasterization pipelines [S1, unofficial]. It is part of the broader effort to accelerate splatting by replacing slower comparison-based sorts with hardware-friendly radix sorts [S2, unofficial]. The use of a 2-pass 16-bit radix sort on float bit patterns is a standard optimization for depth sorting in GPU rendering [G].
