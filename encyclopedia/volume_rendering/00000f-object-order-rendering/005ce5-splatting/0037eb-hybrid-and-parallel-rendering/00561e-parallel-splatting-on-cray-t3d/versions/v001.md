# Parallel Splatting on Cray T3D

Also called: Splatter

## Overview
Parallel Splatting on Cray T3D (also known as **Splatter**) is a memory-optimized volume rendering method designed for massively parallel distributed-memory architectures, specifically the Cray T3D [S1, unofficial]. It solves the problem of rendering large volumetric datasets (e.g., Visible Human Project) at interactive rates by distributing both data and workload across multiple Processing Elements (PEs) [S1, unofficial]. Unlike single-processor splatting methods that are limited by RAM capacity for storing shaded slices, this method leverages distributed memory to keep shaded slices resident on individual PEs, avoiding the need to re-read and re-shade raw data for every view [S1, unofficial]. It sets itself apart from sibling parallel methods by its specific tiling-based compositing strategy and its integration of shading and splatting into a unified PE-local pipeline [S1, unofficial].

## How it works
The method operates in three main phases: Data Distribution, Shading, and Parallel Splatting with Tiling Compositing.

### Inputs and Outputs
*   **Input:** Raw volumetric data (CT or RGB cryosection slices) stored on the T3D host filesystem.
*   **Output:** A final 2D raster image (framebuffer) transferred to the T3D host.
*   **Parameters:**
    *   $n$: Total number of slices in the volume.
    *   $p$: Number of Processing Elements (PEs). Constraint: $n \ge p$ [S1, unofficial].
    *   $b$: Sample resolution in bytes per component (R, G, B, A). Supported values: 1, 2, 4, or 8 [S1, unofficial].

### Data Structures
*   **Raw Slice:** Unprocessed voxel data from the filesystem.
*   **Shaded Slice:** Processed slice containing RGBA values.
    *   Size per slice: $W \times H \times 4 \times b$ bytes, where $W, H$ are slice dimensions.
    *   Example: For a $512 \times 512$ slice with $b=1$, size is 1 MB [S1, unofficial].
*   **Tile:** A rectangular sub-region of the image. In the compositing phase, the image is divided into $p$ tiles, each of size $1/p$ of the total image area [S1, unofficial].

### Algorithm Steps

1.  **Data Distribution**
    Distribute contiguous regions of the data volume to each PE. The slices are partitioned such that the workload is balanced.
    Let $q = \lfloor n/p \rfloor$ and $r = n \pmod p$.
    *   The first $r$ PEs (indices $0$ to $r-1$) receive $q+1$ slices.
    *   The remaining $p-r$ PEs (indices $r$ to $p-1$) receive $q$ slices.
    *   No provision is made for allocating parts of a slice to multiple PEs [S1, unofficial].

2.  **Shading Slices (PE-Local)**
    Each PE processes its assigned raw slices independently.
    *   **For CT Data:**
        *   Calculate shaded slice $z$ using raw slices $z-1$, $z$, and $z+1$ [S1, unofficial].
        *   Discard raw slices $z-1$ once slice $z$ is shaded to free memory for subsequent shaded slices [S1, unofficial].
    *   **For Cryosection (RGB) Data:**
        *   Calculate only the transparency (alpha value) for each voxel.
        *   Set alpha to a small value based on the voxel color to enhance red muscle tissue and internal organs [S1, unofficial].
    *   **Memory Management:**
        *   PEs read their own data files directly from the host filesystem. Transfer rates are approximately 3-7 MB/sec [S1, unofficial].
        *   Shaded slices remain in PE memory for subsequent splatting steps [S1, unofficial].

3.  **Splatting (PE-Local)**
    *   Each PE determines the appropriate traversal order (front-to-back) and splatting filter based on the view plane orientation. Since a parallel projection is used, the footprint of a voxel on the raster is constant for all voxels [S1, unofficial].
    *   Each PE generates a partial image from its partition of shaded slices.
    *   This step is independent across PEs; no data or work dependencies exist between PEs during splatting [S1, unofficial].

4.  **Compositing (Tiling Approach)**
    Combine the $p$ partial images into the final image using a ring-based tiling strategy to avoid data dependencies and balance load.
    *   Divide the image into $p$ tiles.
    *   For each stage $t$ from $1$ to $p$:
        *   PE $P(i)$ fetches the $i$-th tile from PE $P((i+t) \pmod p)$.
        *   PE $P(i)$ composites this fetched tile with the corresponding tile of its own current raster.
        *   The compositing follows the standard alpha blending equation for front-to-back rendering:
            $$ C_{out} = C_{in} + C_{src} \cdot \alpha_{src} \cdot (1 - \alpha_{in}) $$
            where $C$ is color and $\alpha$ is opacity [S1, unofficial][G].
    *   After stage $t=p$, each PE owns a $1/p$ tile of the completed image [S1, unofficial].

5.  **Final Transfer**
    *   To avoid contention on the limited I/O gateways (typically two on the Cray T3D), all tiles are transferred to a single designated PE.
    *   This single PE is responsible for transferring the complete final raster to the T3D host [S1, unofficial].

### Edge Cases and Pitfalls
*   **Slice Count vs. PE Count:** The algorithm requires $n \ge p$. If $n < p$, the distribution logic fails as it assumes at least one slice per PE [S1, unofficial].
*   **I/O Contention:** Transferring tiles from all PEs to the host simultaneously causes bottlenecks due to limited I/O gateways. The method mitigates this by funneling all tiles through a single PE before host transfer [S1, unofficial].
*   **Memory Limits:** The number of shaded slices that fit on a PE is limited by PE memory. For large datasets, the sample resolution $b$ may need to be reduced (e.g., from 4 to 1 byte) to fit more slices [S1, unofficial].
*   **Boundary Conditions:** Shading slice $z$ requires $z-1$ and $z+1$. Boundary slices (first and last) must be handled, typically by padding or clamping, though the source does not specify the exact padding strategy [S1, unofficial][G].

## Operating characteristics
*   **Time Complexity:** The shading and splatting phases are $O(n \cdot W \cdot H)$, distributed across $p$ PEs, yielding $O(\frac{n}{p} \cdot W \cdot H)$ per PE. The compositing phase involves $p$ stages of communication and compositing, each taking $O(\frac{W \cdot H}{p})$ time, resulting in $O(p \cdot \frac{W \cdot H}{p}) = O(W \cdot H)$ total compositing time, but with significant communication overhead [S1, unofficial].
*   **Memory Complexity:** Each PE stores $O(\frac{n}{p} \cdot W \cdot H \cdot b)$ bytes for shaded slices. This is significantly less than storing the entire volume if $p$ is large, but requires sufficient PE memory to hold the assigned slices [S1, unofficial].
*   **Measured Performance:**
    *   512x512x1877 CT dataset (1 GB): 6.14 seconds on 128 PEs [S1, unofficial].
    *   1024x608x1878 RGBmale dataset (1.6 GB): 11.8 seconds on 128 PEs [S1, unofficial].
    *   Scalability: Doubling PEs from 64 to 128 roughly halves the render time (11.64s to 6.14s for CT), indicating good scalability [S1, unofficial].
*   **Strengths:**
    *   High performance on massively parallel systems.
    *   Memory efficiency via distributed storage of shaded slices.
    *   Avoids re-shading for multiple views [S1, unofficial].
*   **Limitations:**
    *   Requires $n \ge p$.
    *   Communication overhead in compositing can become a bottleneck if not managed (e.g., via the tiling approach).
    *   Hardware-specific (Cray T3D, PVM, shmem) [S1, unofficial].
*   **When to Use:** Large volumetric datasets on distributed-memory supercomputers where interactive or near-interactive frame rates are required.
*   **When Not to Use:** Small datasets, single-processor systems, or systems without efficient inter-processor communication libraries like shmem [S1, unofficial].

## Background
Parallel Splatting on Cray T3D was developed by Greg Johnson and Jon Genetti at the Arctic Region Supercomputing Center, University of Alaska Fairbanks [S1, unofficial]. The method, named **Splatter**, was presented in 1996 [S1, unofficial]. It was designed to address the limitations of single-processor volume rendering, such as the SGI Onyx, which required over 17 minutes to render the same 512x512x1877 CT dataset that Splatter rendered in 6.14 seconds on 128 PEs [S1, unofficial]. The method was integrated with the AVS visualization system for user control and Spline Animator for animation creation [S1, unofficial]. It represents an early example of memory-optimized parallel volume rendering on distributed-memory architectures [S1, unofficial].
