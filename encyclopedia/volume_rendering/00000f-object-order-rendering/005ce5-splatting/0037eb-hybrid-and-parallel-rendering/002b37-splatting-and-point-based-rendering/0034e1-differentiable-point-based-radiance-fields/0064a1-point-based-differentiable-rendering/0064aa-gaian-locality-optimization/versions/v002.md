# Gaian Locality Optimization

Also called: Gaian's locality-aware assignment, two-stage locality optimization

## Overview
Gaian Locality Optimization is a two-stage procedure (online and offline) designed to optimize data access locality in distributed Point-Based Differentiable Rendering (PBDR) by assigning points to GPUs and images to GPUs to minimize communication overhead [S1, unofficial]. It addresses the problem where random distribution of points and views causes in-frustum points to reside on remote GPUs, making communication time exceed compute time [S1, unofficial]. It sets itself apart from naive random distribution by exploiting spatial locality through graph partitioning and Z-order curve sorting [S1, unofficial].

## How it works
**Inputs:** A large point cloud, a set of camera views for a training batch, and the distributed system topology (machines and GPUs) [S1, unofficial].
**Outputs:** An offline assignment of point groups to GPUs/machines, and an online assignment of image batches to GPUs [S1, unofficial].

**Data Structures:**
1. **Point Cloud:** A list of 3D points [S1, unofficial].
2. **Z-Order Sorted Points:** Points sorted by their Z-order curve value to preserve spatial locality in a linear ordering [S1, unofficial].
3. **Point Groups:** Contiguous blocks of $G$ points from the sorted list, treated as single vertices in the bipartite graph [S1, unofficial].
4. **Bipartite Graph:** Vertices represent point groups and camera views [S1, unofficial].
5. **Graph Weights:** Point group vertices have uniform weight based on point count ($G$) [S1, unofficial]. Image vertices have weight based on rendering complexity, approximated by the number of points accessed by that view [S1, unofficial].

**Parameters:**
* $G$: The number of points per group in the coarsening step. Typical values are 1024–4096 [S1, unofficial].
* $N_{machines}$: Number of machines in the cluster.
* $N_{GPUs}$: Number of GPUs per machine.

**Steps:**
1. **Offline Point Assignment (Spatial Locality):**
   1. **Z-Order Sorting:** Sort all points in the point cloud using Z-order curves to ensure points close in 3D space remain close in the linear ordering [S1, unofficial].
   2. **Coarsening (Grouping):** Group each contiguous block of $G$ points along the Z-order sorted list into a single point group. Each group becomes a single vertex in the bipartite graph [S1, unofficial].
   3. **Hierarchical Graph Partitioning:**
      * Construct a bipartite graph with point group vertices and image view vertices.
      * Assign weights to image vertices based on rendering complexity (number of points accessed) [S1, unofficial].
      * **Machine Partitioning:** Use a weighted graph partitioner to partition the graph across $N_{machines}$, assigning one partition to each machine. This accounts for slower inter-node communication [S1, unofficial].
      * **GPU Partitioning:** Within each machine, partition the assigned point groups among its local $N_{GPUs}$ GPUs using a weighted graph partitioner, balancing node weights [S1, unofficial].
   4. **Stability:** This assignment is stable during training as the optimality does not change significantly [S1, unofficial].
2. **Online Image Assignment (Load Balancing):**
   1. **Batch Sampling:** Randomly sample a batch of camera views for the current training iteration [S1, unofficial].
   2. **Preference Calculation:** For each image in the batch, identify the GPU that stores the most points needed by that view (based on the offline assignment) [S1, unofficial].
   3. **Balanced Assignment:** Assign images to GPUs to co-locate rendering with data while balancing load. Greedy assignment to the most preferred GPU is avoided to prevent severe load imbalance [S1, unofficial].
   4. **Execution:** Distributed Executors handle the forward and backward pass compute and communication on the assigned GPUs [S1, unofficial].

**Edge Cases and Pitfalls:**
* **Precision:** Z-order sorting must be accurate to preserve spatial locality [G].
* **Boundaries:** Hierarchical partitioning must handle cases where a machine has fewer points than GPUs [G].
* **Degenerate Input:** If a view accesses very few points, its weight in the graph should be small to avoid skewing partitioning [G].

## Operating characteristics
* **Time Complexity:** Not given in the sources.
* **Memory Complexity:** Not given in the sources.
* **Measured Performance:** Reduces communication time significantly compared to random distribution, where communication can exceed compute time [S1, unofficial].
* **Scaling:** Scales to hundreds of millions of points by using coarsening ($G=1024-4096$) [S1, unofficial].
* **Strengths:** Minimizes cross-GPU and cross-machine communication. Exploits spatial locality [S1, unofficial].
* **Limitations:** Offline assignment is static and may not adapt to dynamic changes in point cloud density during training. Coarsening compromises placement quality [S1, unofficial].
* **When to use:** Large-scale PBDR with significant communication overhead [S1, unofficial].
* **When not to use:** Small point clouds where communication is negligible [G].

## Background
Gaian Locality Optimization was introduced in the paper "Scaling Point-based Differentiable Rendering for Large-scale Reconstruction" [S1, unofficial]. It addresses the unique workload of PBDR where spatial locality is key. The method uses METIS for graph partitioning and Z-order curves for spatial sorting [S1, unofficial].
