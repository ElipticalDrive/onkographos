# VolumePro 500 Implementation

Also called: VolumePro 500, Cube-4

## Overview
The VolumePro 500 is a specialized hardware architecture for high-performance volume rendering, based on the Cube-4 design [S3, S4, unofficial]. It implements the shear-warp algorithm using true trilinear interpolation and dedicated hardware for gradient estimation, classification, and Phong shading [S3, S4, unofficial]. Unlike its predecessor Cube-3, which used global connectivity for compositing, VolumePro 500 employs simple local interconnections and accumulating compositors, allowing for easy scalability and direct memory-to-pipeline connectivity [S3, S4, unofficial]. It solves the problem of real-time rendering of large volumetric datasets (up to $1024^3$ voxels) by maximizing memory throughput through 3D skewing and parallel processing of ray groups [S3, S4, unofficial].

## How it works
The VolumePro 500 implements the shear-warp factorization $M_{view} = M_{warp2D} \cdot S \cdot P$ [S4, unofficial]. The final 2D warp $M_{warp2D}$ is performed by the host PC's graphics card, while the VolumePro hardware handles the permutation $P$, shear $S$, resampling, compositing, and shading [S3, S4, unofficial].

### Inputs and Outputs
*   **Input:** A 3D volume dataset stored in a skewed memory format. The data is partitioned into sub-volumes or blocks if it exceeds the on-chip memory capacity [S1][S4, unofficial].
*   **Output:** A 2D image composited onto the viewing plane, sent to the host for the final warp [S3, S4, unofficial].

### Data Structures and Memory Layout
*   **Skewed Memory:** The volume data is stored using a 3D skewing scheme [Kaufman and Bakalash 1988] to enable conflict-free access to any axis-aligned voxel slice [S4, unofficial]. This allows the hardware to read blocks and slices efficiently while storing only one copy of the data [S4, unofficial].
*   **Slice Buffers:** On-chip buffers store samples from adjacent slices to exploit data coherency. Specifically, 'ahead', 'current', and 'behind' buffers store samples one slice ahead and one slice behind the current processing slice [S2, S4, unofficial].
*   **Classification Lookup Table (LUT):** A $4k \times 36$ bit LUT maps scalar values to 24-bit color and 12-bit alpha values [S4, unofficial]. Double buffering in hardware allows dynamic loading of this table [S4, unofficial].
*   **Reflectance Maps:** Pre-computed tables storing illumination from all light sources, used for Phong shading [S4, unofficial].

### Processing Steps
The hardware processes groups of rays simultaneously, connecting the pipeline directly to memory [S3, S4, unofficial].

1.  **Memory Access and Skewing:** The hardware accesses the skewed memory to retrieve axis-aligned slices of voxels. The 3D skewing ensures that for any viewing direction, the required voxels can be accessed in a coherent burst mode using the SDRAM's burst capability [S3, S4, unofficial].
2.  **Tri-linear Interpolation:** To prevent undersampling, the hardware performs true tri-linear interpolation between volume slices [S3, S4, unofficial]. Viewing rays can start at sub-pixel locations to prevent popping artifacts during base plane switches and allow over-sampling [S4, unofficial].
3.  **Gradient Estimation:** On-the-fly central-difference gradient estimation is performed at each voxel [S4, unofficial]. The gradients are then tri-linearly interpolated to the resampling locations [S4, unofficial].
    *   *Gradient Correction:* A lookup table maps the gradient magnitude to a user-specified piece-wise linear function to highlight specific values or attenuate modulation effects [S4, unofficial].
    *   *Anisotropy Correction:* The LUT is also used to automatically correct gradient magnitudes in anisotropic volumes [S4, unofficial].
4.  **Classification (Post-classification):** The interpolated scalar values are passed through the classification LUT [S4, unofficial]. The LUT outputs 24-bit color and 12-bit alpha values [S4, unofficial]. Opacity correction for uniform sample spacing is applied in software for each frame [S4, unofficial].
5.  **Shading (Phong Illumination):** Phong shading is implemented at each sample point at the rate of one illuminated sample per clock cycle [S4, unofficial].
    *   Diffuse and specular illumination are looked up in pre-computed reflectance maps [S4, unofficial].
    *   Reflectance maps are reloaded when object and light positions change relative to each other, or to correct the eye vector for anisotropic volumes [S4, unofficial].
6.  **Compositing:** Samples are composited onto the base-plane (intermediate image) using accumulating compositors [S3, S4, unofficial]. This replaces the binary compositing tree used in Cube-3 [S3, unofficial].
7.  **Pixel Output:** A pixel-bus collects and aligns the pixel output from the compositors [S3, S4, unofficial].
8.  **2D Warp:** The composited base-plane image is transferred to the host PC, where the final 2D affine warp $M_{warp2D}$ is performed by the PC's graphics card [S3, S4, unofficial].

### Pseudocode
The following pseudocode describes the data flow and processing stages within the VolumePro 500 hardware pipeline. Note that memory access and interpolation are hardware-accelerated and described functionally.

```python
def volumepro_500_pipeline(volume_data, viewing_direction, light_positions, eye_vector):
    """
    Simulates the data flow of the VolumePro 500 hardware pipeline.
    volume_data: 3D array of voxel values (skewed format in hardware).
    viewing_direction: 3D vector defining the view.
    light_positions: List of light source positions.
    eye_vector: 3D vector for specular shading.
    """
    
    # 1. Memory Access via 3D Skewing
    # Hardware retrieves axis-aligned slices based on viewing_direction.
    # Uses SDRAM burst mode for maximum throughput.
    # Returns a stream of voxel blocks aligned to the shear plane.
    slice_stream = hardware_skewed_memory_access(volume_data, viewing_direction)
    
    # 2. Tri-linear Interpolation
    # Rays start at sub-pixel locations to prevent popping artifacts.
    # Interpolates between adjacent slices using on-chip buffers (ahead, current, behind).
    interpolated_samples = hardware_trilinear_interpolation(slice_stream)
    
    # 3. Gradient Estimation
    # Central-difference hardware computes gradients at each voxel.
    # Gradients are tri-linearly interpolated to resampling locations.
    gradients = hardware_gradient_estimation(slice_stream)
    interpolated_gradients = hardware_trilinear_interpolation(gradients)
    
    # 4. Gradient Magnitude Correction
    # Maps gradient magnitude via LUT to piece-wise linear function.
    # Corrects for anisotropic volumes.
    corrected_gradient_magnitudes = hardware_gradient_correction(interpolated_gradients)
    
    # 5. Classification
    # Post-classification using 4k x 36 bit LUT.
    # Outputs 24-bit color and 12-bit alpha.
    # Opacity correction for uniform spacing is done in software later.
    classified_samples = hardware_classification_LUT(interpolated_samples)
    
    # 6. Shading (Phong Illumination)
    # One illuminated sample per clock cycle.
    # Looks up diffuse and specular in reflectance maps.
    # Reflectance maps depend on light_positions and eye_vector.
    shaded_samples = hardware_phong_shading(classified_samples, light_positions, eye_vector)
    
    # 7. Compositing
    # Accumulating compositors replace binary tree.
    # Samples composited onto base-plane in front-to-back order.
    base_plane_image = hardware_accumulating_compositing(shaded_samples)
    
    # 8. Pixel Output
    # Pixel-bus collects and aligns output.
    output_image = hardware_pixel_bus(base_plane_image)
    
    # 9. Final Warp (Host Side)
    # Performed by PC graphics card.
    final_image = host_2d_warp(output_image, viewing_direction)
    
    return final_image
```

### Parameters and Typical Values
*   **Pipelines:** Four rendering pipelines [S3, S4, unofficial].
*   **Memory:** Four 64 Mbit SDRAMs [S3, unofficial].
*   **Performance:** Renders 500 million interpolated, Phong illuminated, composited samples per second [S3, unofficial].
*   **Resolution:** Sufficient for volumes up to $256^3$ (16 million voxels) at 30 fps [S3, unofficial]. Scalable to $1024^3$ 16-bit voxels [S3, unofficial].
*   **Classification LUT:** $4k \times 36$ bits [S4, unofficial].
*   **Alpha Precision:** 12-bit [S4, unofficial].

### Edge Cases and Pitfalls
*   **No Occlusion Culling:** The system uses a brute-force rendering mode where all rays are cast across the volume; no voxel skipping is performed [S3, unofficial].
*   **Large Volumes:** For volumes larger than the hardware can handle directly, the driver software partitions the volume into smaller blocks, renders each independently, and automatically combines the resulting images [S4, unofficial].
*   **Reflectance Map Updates:** Reflectance maps must be reloaded if object and light positions change relative to each other, or to correct the eye vector for anisotropic volumes [S4, unofficial].

## Subtopics

### Cube-2
Cube-2 is a single-chip VLSI implementation of the Cube-1 prototype [S3, unofficial]. It represents the first commercial VLSI realization of the Cube architecture's interleaved memory organization [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** The performance is independent of the classification or data content due to brute-force processing [S4, unofficial]. It renders at a constant rate of 500 million samples per second [S3, unofficial].
*   **Memory Complexity:** Uses 3D skewing to store only one copy of the volume data while enabling conflict-free access [S4, unofficial]. The architecture is scalable to $1024^3$ 16-bit voxels [S3, unofficial].
*   **Measured Performance:** Renders $256^3$ volumes at 30 frames per second [S3, S4, unofficial].
*   **Strengths:** True trilinear interpolation for high quality; dedicated hardware for gradient estimation, classification, and Phong shading; high memory throughput via 3D skewing and SDRAM burst mode; local interconnections for scalability [S3, S4, unofficial].
*   **Limitations:** No occlusion culling or voxel skipping; requires host PC for final 2D warp; large volumes require software partitioning and recombination [S3, S4, unofficial].
*   **When to use:** Real-time visualization of large volumetric datasets where high-quality interpolation and shading are required, and the dataset fits within the partitioning strategy or on-chip memory limits.
*   **When not to use:** Scenes requiring early ray termination or occlusion culling for performance gains, or where the final 2D warp cannot be offloaded to a standard graphics card.

## Background
The Cube project aims at realizing high-performance volume rendering systems for large datasets and pioneered several hardware architectures [S3, unofficial]. Cube-1 was a first-generation prototype based on specially interleaved memory [S3, unofficial]. Cube-2 was a single-chip VLSI implementation [S3, unofficial]. Cube-3 introduced global communication networks and binary compositing trees [S3, unofficial]. Cube-4, the architecture underlying the VolumePro 500, was developed at Stony Brook University [S2, S4, unofficial]. It simplified Cube-3 by using local interconnections and accumulating compositors [S3, S4, unofficial]. Mitsubishi Electric licensed the Cube-4 technology, improved it, and released the VolumePro 500 as an ASIC in 1999 [S3, S4, unofficial]. It was used in systems like the U-Cube ultrasound visualization system [S2, unofficial].
