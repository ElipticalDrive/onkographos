# Fast volume rotation using binary shear-warp factorization

Also called: Binary shear transformation for rotation, Fast Volume Rotation via Shear-Warp and Super Cells, Fast iso-surface rendering

## Overview
A technique to accelerate volume rotation by using super cells (square regions in slices perpendicular to the principal direction) to skip transparent regions, allowing interactive frame rates without specialized hardware [S1, unofficial]. It precisely skips empty regions along rays to be evaluated without trading image quality for speed or requiring specialized hardware [S2, unofficial]. Unlike classical shear-warp with run-length encoding, this method is surface-oriented and speeds up transfer function based ray casting by precisely skipping empty regions [S1, unofficial].

## How it works
The method extends the binary lookup table technique to viewing directions where the principal component is the z-coordinate by using an incremental binary shear transformation [S1, unofficial]. It shifts bits of the binary mask volume perpendicularly to the viewing direction's principal component [S1, unofficial].

### Inputs and Outputs
**Inputs:**
*   Volume dimensions: $X, Y, Z$ [S1, unofficial].
*   Binary volume mask $B$ indicating opaque voxels (1) and transparent voxels (0) [S2, unofficial].
*   Current viewing direction defined by points $p_0$ and $p_1$ [S1, unofficial].
*   Super cell size $S$ (integer, typically 1-4) [S1, unofficial].

**Outputs:**
*   Rotated binary mask [S1, unofficial].
*   Final rendered image [S1, unofficial].

### Data Structures
The binary volume is stored in an extended integer array to handle bitwise shifts safely [S1, unofficial]:

*   `mask[depth][height][width]`: Extended integer array [S1, unofficial].
    *   `depth = (Z + 31) div 32` [S1, unofficial].
    *   `height = Y + Z` [S1, unofficial].
    *   `width = X + Z` [S1, unofficial].
    *   The array is extended by $Z/2$ rows filled with zeros along the x and y axes in both directions to prevent bits from shifting out of bounds [S1, unofficial].
*   `shift_x[depth]`: Integer array storing binary vectors of size $Z$. Indicates which z-positions (slices) need to be shifted in the current shearing phase [S1, unofficial].
*   `shift_y[depth]`: Integer array for y-direction shifts (analogous to `shift_x`) [S1, unofficial].
*   `trans_x[Z]`, `trans_y[Z]`: Double arrays storing real translations along x and y axes. Contains x and y coordinates of intersection points of the 3D line (connecting $p_0$ and $p_1$) with planes $z=z_k$ [S1, unofficial].

### Steps

1.  **Generate Binary Mask:** Create a binary volume mask indicating the locations of transparent cells based on a fixed opacity threshold or transfer function [S2, unofficial].
2.  **Initialize Super Cells:** Divide slices perpendicular to the principal direction into square super cells of size $S \times S$. Assign a super cell to the binary volume if at least one voxel within it is opaque [S1, unofficial].
3.  **Compute Shift Vectors:** Before shearing, evaluate shift vectors based on the rotation direction. For a clockwise rotation around the y-axis, translate $p_0$ by -1 along x and $p_1$ by +1 along x. Compute intersection points with planes $z=z_k$ to update `trans_x` and `trans_y` [S1, unofficial].
4.  **Incremental Binary Shear:** Perform the shear transformation on the super cell mask. This is done incrementally using small difference angles so no slice needs to be shifted by more than one voxel, allowing efficient bitwise operations [S1, unofficial].
5.  **Ray Casting Acceleration:** Use the transformed mask and a lookup-table technique to find the first non-transparent cell along each ray [S2, unofficial].
6.  **Render:** Render pixel-by-pixel by mapping each pixel location onto the intermediate image and bilinearly interpolating the color from the four closest pixel values [S1, unofficial].

### Formulas and Pseudocode

**Computing Shift Vectors:**
The shift vector `shift_x` is computed by comparing the new interpolated x-coordinate with the previous translation value [S1, unofficial]:

$$ x = \frac{x_0 \cdot (l - z) + x_1 \cdot z}{l} $$

Where:
*   $x_0 = trans\_x[0] - 1.0$ [S1, unofficial].
*   $x_1 = trans\_x[Z-1] + 1.0$ [S1, unofficial].
*   $l = Z - 1$ [S1, unofficial].
*   $z$ is the current slice index [S1, unofficial].

If $\lfloor x \rfloor \neq \lfloor trans\_x[z] \rfloor$, the bit corresponding to $z$ is set in `shift_x` [S1, unofficial].

**Shear Operation:**
The shear operation processes 32 voxels in each step of the internal loop. The direction of the loop depends on the half of the depth array [S1, unofficial]:

```python
import math

def shear_left(mask, shift_x, depth, height, width):
    """
    Performs one shear step in the left direction.
    mask: list of list of list of int
    shift_x: list of int
    """
    # First half of depth array: shift bits from i+1 to i
    for k in range(depth // 2):
        for j in range(height):
            for i in range(width - 1):
                mask[k][j][i] = (mask[k][j][i] & ~shift_x[k]) | (mask[k][j][i+1] & shift_x[k])
            mask[k][j][width - 1] &= ~shift_x[k]
            
    # Second half of depth array: shift bits from i-1 to i
    for k in range(depth // 2, depth):
        for j in range(height):
            for i in range(width - 1, 0, -1):
                mask[k][j][i] = (mask[k][j][i] & ~shift_x[k]) | (mask[k][j][i-1] & shift_x[k])
            mask[k][j][0] &= ~shift_x[k]

def compute_new_shift_x(trans_x, shift_x, Z, depth):
    """
    Computes the new shift_x array based on incremental rotation.
    trans_x: list of float (modified in place)
    shift_x: list of int (modified in place)
    """
    trans_x[0] -= 1.0
    trans_x[Z - 1] += 1.0
    x0 = trans_x[0]
    x1 = trans_x[Z - 1]
    bit = 0x80000000
    l = Z - 1
    
    for z in range(Z):
        x = (x0 * (l - z) + x1 * z) / l
        if math.floor(x) != math.floor(trans_x[z]):
            shift_x[z // 32] |= bit >> (z % 32)
        else:
            # Clear bit at position z % 32 in shift_x[z // 32]
            # Note: Source uses |= ~(...), which is a known typo for &= ~(...)
            shift_x[z // 32] &= ~(bit >> (z % 32))
        trans_x[z] = x
```

### Parameters
*   **Super cell size:** Integer value (1, 2, 3, 4 tested). Optimal size depends on volume resolution and desired balance between shear time and rendering time [S1, unofficial].
*   **Rotation angle:** Small difference angles are used so that no slice needs to be shifted by more than one voxel [S1, unofficial].

### Edge Cases and Pitfalls
*   **Bit Overflow:** Bits can be shifted out of the integer array. The array must be extended by $Z/2$ rows filled with zeros along x and y axes in both directions [S1, unofficial].
*   **Super Cell Size Trade-off:** Large super cell sizes cause the Depth routine to return only a lower bound, forcing rays to trace further to find non-transparent samples, slowing rendering [S1, unofficial].
*   **Low Opacity:** Low opacity transfer functions drastically increase rendering time because alpha-blending semi-transparent segments is computationally expensive after skipping empty regions [S1, unofficial].
*   **Adaptive Thresholding:** The volume must be classified in advance. The opacity function cannot be modified flexibly. A density encoding scheme can be used to allow rapid switching between predefined transfer functions [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Shearing time decreases with larger super cell sizes, while rendering time increases. The optimal cell size balances these two [S1, unofficial].
*   **Memory Complexity:** Requires extended integer arrays for the mask and translation tables [S1, unofficial].
*   **Measured Performance:**
    *   On SGI Indy workstation, for $128 \times 128 \times 113$ CT head:
        *   Cell size 1: 6.87 Hz (0.019s shear, 0.114s render) [S1, unofficial].
        *   Cell size 2: 8.64 Hz (0.005s shear, 0.107s render) [S1, unofficial].
        *   Cell size 3: 8.11 Hz (0.002s shear, 0.118s render) [S1, unofficial].
        *   Cell size 4: 6.26 Hz (0.001s shear, 0.156s render) [S1, unofficial].
    *   On SGI Indy workstation, for $256 \times 256 \times 225$ CT head:
        *   Cell size 1: 1.21 Hz (0.160s shear, 0.590s render) [S1, unofficial].
        *   Cell size 2: 1.81 Hz (0.040s shear, 0.492s render) [S1, unofficial].
        *   Cell size 3: 1.78 Hz (0.017s shear, 0.535s render) [S1, unofficial].
        *   Cell size 4: 1.37 Hz (0.009s shear, 0.709s render) [S1, unofficial].
*   **Strengths:** Provides interactive frame rates without specialized hardware. Precisely skips empty regions [S1, unofficial].
*   **Limitations:** Requires pre-classification of the volume. Low opacity transfer functions significantly slow down rendering [S1, unofficial].
*   **When to use:** Fast previewing of iso-surface rendering with interactive viewing direction. Suitable for surface-oriented algorithms where rays terminate after reaching an opaque surface [S1, unofficial].

## Background
The technique was implemented in C++ and tested on an SGI Indy workstation [S1, unofficial]. It is used as a fast previewer for iso-surface rendering with interactive viewing direction [S1, unofficial]. The method is similar to Cohen-Or and Fleishman's incremental alignment algorithm, used to reduce communication overhead in multi-processor architectures [S1, unofficial].
