# Parallel Perspective Shear-Warp Rendering

Also called: Parallel Perspective Shear-Warp Rendering with MPI, Parallelized Perspective Shear-Warp Algorithm, Perspective Shear-Warp Parallelization, Remote Volume Rendering

## Overview
Parallel Perspective Shear-Warp Rendering is a distributed volume rendering technique that parallelizes the compositing step of the perspective shear-warp algorithm across multiple nodes using Message Passing Interface (MPI) [S1, unofficial]. It solves the problem of rendering high-resolution perspective volumes on distributed memory clusters by offloading the computationally expensive 2D warping step to the graphics hardware of a remote display machine [S1, unofficial]. Unlike parallel projection methods that distribute volume data, this method requires every node to hold a full copy of the volume, partitioning the intermediate image scanlines instead [S1, unofficial]. It is distinct from hardware-based texture mapping approaches by avoiding OpenGL extension dependencies and texture memory limits, making it suitable for clusters without dedicated graphics cards [S1, unofficial].

## How it works
The method extends the standard perspective shear-warp algorithm [Parent](24-shear-warp.md) by distributing the compositing phase. The system consists of a local display machine (running a rendering plug-in) and a remote parallel computer (running the MPI renderer) [S1, unofficial].

### Inputs and Outputs
*   **Inputs:** View matrix, opacity/color transfer functions, interpolation mode, image quality parameters, and volume data (transferred once at startup) [S1, unofficial].
*   **Outputs:** Final 2D image displayed on the local machine [S1, unofficial].

### Data Structures
*   **Volume Data:** Stored on each node as three separate Run-Length Encoded (RLE) datasets, one sorted along each principal axis (x, y, z) [S1, unofficial]. This axis-sorted structure is required by the shear-warp algorithm to handle arbitrary viewing directions without reordering voxels [S1, unofficial].
*   **Intermediate Image:** A 2D RGBA image. Edge lengths are constrained to powers of two to satisfy 2D texturing hardware requirements for the warp step [S1, unofficial]. Typical size is $1024 \times 1024$ pixels (4 MB) for large datasets [S1, unofficial].
*   **Memory Management:** The intermediate image data is stored only once in memory per node; a pointer to it is passed among functions to avoid unnecessary copying [S1, unofficial]. Memory is not reallocated if the image size remains the same or shrinks; reallocation occurs only if the new image is larger than the allocated space [S1, unofficial].

### Algorithm Steps
The rendering loop operates as follows [S1, unofficial]:

1.  **Initialization:**
    *   The display machine establishes a bidirectional TCP socket connection to the remote renderer [S1, unofficial].
    *   The volume data is transferred from disk/memory to the remote cluster [S1, unofficial].
    *   Each node generates and stores the three RLE-encoded versions of the volume [S1, unofficial].

2.  **Per-Frame Rendering (Root Node):**
    *   Receive the view matrix from the local rendering plug-in [S1, unofficial].
    *   Compute the partitioning of the intermediate image into equally sized scanline sections for the available MPI processes [S1, unofficial].
    *   Pass the section partition parameters (start/end scanlines) to all other nodes [S1, unofficial].
    *   Render its own assigned scanline section of the intermediate image via compositing in sheared object space [S1, unofficial].
    *   Receive the rendered intermediate image sections from all other nodes using `MPI_Recv()` with the correct destination memory address to avoid copying [S1, unofficial].
    *   RLE encode the assembled intermediate image. Two encoding strategies are implemented: encoding the entire image or encoding only the rectangular window actually touched by compositing. The window encoding is typically faster [S1, unofficial].
    *   Transfer the RLE-encoded intermediate image and the respective warp matrix to the local rendering plug-in [S1, unofficial].

3.  **Per-Frame Rendering (Other Nodes):**
    *   Receive section parameters from the root node [S1, unofficial].
    *   Render the assigned scanline section of the intermediate image via compositing in sheared object space [S1, unofficial].
    *   Transfer the rendered section to the root node [S1, unofficial].

4.  **Final Display (Local Plug-in):**
    *   Decode the RLE-encoded intermediate image [S1, unofficial].
    *   Apply the 2D warp transformation using the received warp matrix, utilizing 2D texturing hardware if available [S1, unofficial].
    *   Draw the final image to the screen [S1, unofficial].

### Pseudocode
The following pseudocode represents the control flow on the remote MPI cluster. It assumes standard MPI functions and the shear-warp compositing logic defined in the parent article.

```python
# Remote Renderer Initialization
def remote_renderer_init(volume_data, num_nodes, display_host, port):
    # Transfer volume data to all nodes
    # Generate 3 RLE-encoded volumes (one per axis) for each node
    rle_volumes = generate_rle_volumes(volume_data)
    return rle_volumes

# Root Node Logic
def root_node_render_loop(rle_volumes, view_matrix, image_dims, num_nodes):
    # 1. Partition intermediate image into scanline sections
    # Assign equal number of scanlines to each node.
    # Root node may get fewer if scanlines don't divide evenly,
    # as root handles communication overhead.
    partitions = compute_scanline_partitions(image_dims.height, num_nodes)
    
    # 2. Distribute partitions to other nodes
    for node_id in range(1, num_nodes):
        send_partition(node_id, partitions[node_id])
        
    # 3. Root renders its own section
    root_section = partitions[0]
    root_image = composite_sheared_volume(rle_volumes, view_matrix, root_section, image_dims)
    
    # 4. Receive sections from other nodes
    # Use MPI_Recv with pre-allocated memory buffers to avoid copying
    for node_id in range(1, num_nodes):
        recv_image = mpi_recv(node_id, partitions[node_id].size)
        # Place recv_image into the correct position in the global intermediate image buffer
        assemble_intermediate_image(root_image, recv_image, partitions[node_id])
        
    # 5. Encode and transfer
    # Encode only the rectangular window actually touched to save bandwidth
    encoded_image, warp_matrix = rle_encode_window(root_image, view_matrix)
    send_to_display(encoded_image, warp_matrix)

# Other Nodes Logic
def other_node_render_loop(rle_volumes, view_matrix, image_dims):
    # 1. Receive partition parameters
    partition = receive_partition()
    
    # 2. Render assigned section
    # Composite only the scanlines in the partition
    section_image = composite_sheared_volume(rle_volumes, view_matrix, partition, image_dims)
    
    # 3. Transfer result to root
    send_to_root(section_image)

# Core Compositing Step (Shear-Warp)
def composite_sheared_volume(rle_volumes, view_matrix, partition, image_dims):
    # Factorize view matrix into shear and warp components [Parent]
    M_shear, M_warp = factorize_view_matrix(view_matrix)
    
    # Initialize intermediate image buffer for the partition
    image = zeros(partition.size)
    
    # For perspective projection, slices scale down as they go back.
    # Resampling is non-uniform.
    for slice_idx in range(rle_volumes.depth):
        # Shear the slice into sheared object space
        sheared_slice = shear_slice(rle_volumes[slice_idx], M_shear)
        
        # Composite front-to-back
        for y in range(partition.start_y, partition.end_y):
            for x in range(image_dims.width):
                # In perspective, a pixel may require accumulating voxels
                # from multiple lines or an entire slice at the back.
                # Use RLE to skip transparent runs efficiently.
                val, alpha = resample_and_classify(sheared_slice, x, y)
                
                # Front-to-back compositing
                # Note: Standard shear-warp compositing formula
                # C = C_prev + c * alpha * (1 - alpha_prev)
                accumulate(image, x, y, val, alpha)
                
    return image
```

### Parameters and Typical Values
*   **Intermediate Image Size:** Powers of two (e.g., $1024 \times 1024$ for large datasets, $512 \times 512$ for small) [S1, unofficial].
*   **Color Space:** 24-bit RGB [S1, unofficial].
*   **Opacity Transfer Function:** Linear ramp from zero to full opacity [S1, unofficial].
*   **Network:** Bidirectional TCP socket [S1, unofficial].
*   **Remote Renderer Parameters:** Port number and display host address [S1, unofficial].

### Edge Cases and Pitfalls
*   **Memory Constraints:** Because the shear-warp algorithm requires three axis-sorted volume datasets, volume data cannot be distributed across nodes. Every node must hold a full copy of the volume [S1, unofficial]. If memory is constrained on a large cluster, nodes can be split into three groups (one per axis), allowing three times the maximum volume size but limiting rendering to one-third of the nodes simultaneously [S1, unofficial].
*   **Perspective Cost:** Perspective compositing is significantly more expensive than parallel projection. A single intermediate image pixel may require accumulating voxels from an entire voxel slice at the back of the volume, unlike parallel projection which maps voxels 1:1 [S1, unofficial].
*   **Load Balancing:** Compositing time can vary based on view direction and opacity distribution. In tests on SGI Onyx2, the load balancing factor was 2.08, meaning perfect load balancing would improve speed by this factor [S1, unofficial]. The optimal process count may not be the maximum available (e.g., 14 processes was fastest on a 16-processor Onyx2) [S1, unofficial].
*   **Network Bottlenecks:** On fast processors (e.g., PC Cluster), image transfer and idle time can dominate rendering time, whereas on slower processors (e.g., SUN Fire), compositing dominates [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The compositing step dominates the total rendering time on most architectures [S1, unofficial]. The warp step is offloaded to hardware and is nearly independent of output image size [S1, unofficial].
*   **Memory Complexity:** High. Each node must store three full RLE-encoded copies of the volume dataset [S1, unofficial].
*   **Measured Performance:**
    *   **SUN Fire (6 processes):** 3.5 images/sec. Compositing dominates. Encoding: 0.91s, Transfer: 0.89s [S1, unofficial].
    *   **SGI Onyx2 (14 processes):** 2.7 images/sec. Compositing dominates. Transfer: <0.2s (1 Gbit/s Ethernet), Encoding: 2.67s [S1, unofficial].
    *   **PC Cluster (16 processes):** 8.4 images/sec. Transfer and idle time dominate due to fast CPUs. Encoding: 0.27s [S1, unofficial].
    *   **Decoding/Drawing:** Constant ~2.6s decode and ~1.4s draw time on the display machine across tests [S1, unofficial].
*   **Scaling:** Performance scales with the number of processors for compositing, but is limited by load balancing inefficiencies and network bandwidth for data transfer [S1, unofficial].
*   **Strengths:** Works on clusters without graphics hardware; avoids OpenGL extension dependencies; suitable for remote rendering in virtual environments; warp is hardware-accelerated [S1, unofficial].
*   **Limitations:** High memory usage per node; perspective compositing is expensive; network bandwidth can be a bottleneck for large images; load balancing is imperfect [S1, unofficial].
*   **When to use:** Remote rendering on distributed clusters where graphics hardware is unavailable or insufficient, and perspective projection is required [S1, unofficial].
*   **When not to use:** When single-processor performance is critical (hardware texture mapping is faster on single cores); when volume data is too large to fit in memory on each node [S1, unofficial].

## Background
Parallel Perspective Shear-Warp Rendering was developed by Schulze and Lang in 2002 [S1, unofficial]. It is based on their prior work on perspective shear-warp rendering [S1, unofficial] and extends Lacroute's parallel projection parallelization method [S1, unofficial]. The method was designed to support remote rendering for virtual environments requiring perspective projection, high frame rates, stereo projection, and multiple display screens [S1, unofficial]. It was implemented using the Virvo volume renderer framework with a plug-in mechanism [S1, unofficial].
