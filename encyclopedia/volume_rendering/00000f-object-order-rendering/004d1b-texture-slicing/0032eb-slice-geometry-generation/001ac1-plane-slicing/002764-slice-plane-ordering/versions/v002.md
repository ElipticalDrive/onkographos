# Slice Plane Ordering

Also called: Back-to-Front Alpha Blending, Slice Sorting

## Overview
Slice Plane Ordering is a rendering rule that dictates the draw order of transparent volume slices to ensure correct alpha blending and occlusion [S1, unofficial]. It solves the problem of transparent objects appearing blended in front of obscured objects when rendered in arbitrary order [S1, unofficial]. It sets itself apart from sibling methods like [Plane Composing Algorithms](2154-plane-composing-algorithms.md) by focusing strictly on the temporal draw sequence relative to the camera, rather than the geometric assembly of the slices themselves [S2, unofficial].

## How it works
**Inputs:**
- Camera position along the rendering axis, `position.z` [S2, unofficial].
- Number of slices, `count` [S2, unofficial].
- Volume extent parameter, `SIZE` [S2, unofficial].

**Outputs:**
- An ordered list of slice identifiers (and their world Z positions) ready for GPU upload [S2, unofficial].

**Data Structures:**
- `slice`: A dynamic array storing pairs of `(z_world, slice_id)` [S2, unofficial].
- `slice_id`: Integer index `i` identifying the slice [S2, unofficial].

**Parameters:**
- Alpha Test Threshold: Default value `0.1` [S2, unofficial].
- Depth Test: Must be enabled to handle occlusion correctly [S2, unofficial].
- Back-face Culling: Must be disabled to ensure slices facing away from the camera are still rendered [S2, unofficial].

**Steps:**
1. Determine the camera position along the rendering axis (`position.z`) [S2, unofficial].
2. Initialize an empty `slice` list [S2, unofficial].
3. Iterate through slice indices `i` from `0` to `count-1`:
   a. Calculate the slice world position: `pos = -SIZE/2 + SIZE * i / (count-1)` [S2, unofficial].
   b. If `pos >= position.z`, break the loop [S2, unofficial].
   c. Push valid slices (those with `pos < position.z`) into `slice` [S2, unofficial].
4. Iterate through slice indices `i` from `count-1` down to `0`:
   a. Calculate the slice world position: `pos = -SIZE/2 + SIZE * i / (count-1)` [S2, unofficial].
   b. If `pos < position.z`, break the loop [S2, unofficial].
   c. Push valid slices (those with `pos >= position.z`) into `slice` [S2, unofficial].
5. Upload the ordered `slice` list to the GPU buffer [S2, unofficial].

**Pseudocode:**
```python
def order_slices(position_z, size, count):
    slice_list = []
    
    # Pass 1: Collect slices where pos < position_z
    for i in range(count):
        pos = -size / 2.0 + size * i / (count - 1)
        if pos >= position_z:
            break
        slice_list.append((pos, i))
        
    # Pass 2: Collect slices where pos >= position_z
    for i in range(count - 1, -1, -1):
        pos = -size / 2.0 + size * i / (count - 1)
        if pos < position_z:
            break
        slice_list.append((pos, i))
        
    return slice_list
```

**Edge Cases and Pitfalls:**
- If depth testing is enabled but slices are not sorted back-to-front, or if back-face culling is enabled, parts of the volume may disappear or render incorrectly [S2, unofficial].
- Specifically, slices facing away from the camera are culled if back-face culling is on [S2, unofficial].
- If depth testing is disabled, the depth of the slices does not occlude one another. If slices are not sorted back-to-front, front slices may obscure back slices incorrectly, or if sorted front-to-back, back slices may overwrite front slices depending on the blending state [S2, unofficial].
- Slice plane ordering is not important when drawing 3D smoke if all smoke has the same color (only opacity varies), but is important when drawing smoke and fire (different colors) or using elaborate lighting algorithms [S1, unofficial].

## Operating characteristics
- **Time Complexity:** Not given in the sources.
- **Memory Complexity:** Not given in the sources.
- **Strengths:** Ensures correct alpha blending for transparent volumes; handles occlusion correctly when combined with depth testing [S2, unofficial].
- **Limitations:** Requires dynamic sorting per frame if the camera moves; not necessary for single-color opacity-only volumes [S1, unofficial].
- **When to use:** When rendering partially transparent volume data with varying colors or lighting [S1, unofficial][S2, unofficial].
- **When not to use:** When rendering single-color opacity-only volumes where order does not affect the final color [S1, unofficial].

## Background
The concept originates from general computer graphics principles regarding transparent object rendering, where back-to-front ordering is required to prevent inconsistent drawing [S1, unofficial]. It is specifically applied in volume rendering contexts such as Smokeview, a tool for visualizing fire dynamics simulation data, to handle the rendering of smoke and fire slices [S1, unofficial]. Practical implementation details and pitfalls are documented in community discussions on OpenGL volume rendering [S2, unofficial].
