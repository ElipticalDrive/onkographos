# Plane Slicing

Also called: Multi-Directional Slicing, Multi-axis Slicing, Plane Slicing with Marching Cubes, Slice Plane Rendering

## Overview
Plane Slicing is a volume rendering method that approximates a 3D scalar field by intersecting the volume with a dense set of parallel planes perpendicular to the X, Y, and Z axes, generating polygons via a marching cubes variant, and compositing them using hardware alpha blending [S1, S2][S3, unofficial]. It differs from [Sliced Volume Rendering](3568-sliced-volume-rendering.md) by pre-computing slices for all three axes to allow dynamic view orientation without re-slicing, and from [GPU-based Cut-off Slice Generation](948-gpu-based-cut-off-slice-generation.md) by relying on CPU-side tessellation of unstructured or structured cells into planar polygons rather than GPU-driven implicit surface extraction [S1, S2][S3, unofficial].

## How it works
**Inputs:** A 3D scalar field defined on a grid (structured or unstructured); a transfer function mapping scalar values to color and opacity.
**Outputs:** A 2D image.

**Data Structures:**
1.  **Slicing Planes:** Three sets of evenly spaced planes, one set perpendicular to each axis (X, Y, Z). The number of planes is typically "several hundred" per axis [S1, S2].
2.  **Polygon Arrays:** For each plane, an array of polygons (triangles or triangle strips) representing the intersection of the volume cells with that plane.
3.  **Texture Map:** A 1D texture storing the transfer function, indexed by normalized scalar values [S1, S2][S3, unofficial].

**Algorithm Steps:**

1.  **Preprocessing (Slicing):**
    For each cell in the volume:
    a.  Generate three planar slices, one perpendicular to the X-axis, one to the Y-axis, and one to the Z-axis [S3, unofficial].
    b.  Use a variant of the marching cubes algorithm to slice the cell into polygons on these planes [S1, S2][S3, unofficial].
    c.  For each resulting polygon vertex, compute its scalar value.
    d.  Normalize the scalar value $s$ to the range $[0, 1]$ to serve as a 1D texture coordinate for the transfer function [S1, S2][S3, unofficial].
    e.  Store the polygons in arrays grouped by their respective slice planes [S1, S2].

2.  **Rendering Selection:**
    a.  Determine the viewing direction vector $\vec{v}$.
    b.  Calculate the alignment of the three axes (X, Y, Z) with $\vec{v}$.
    c.  Select the set of slices (X, Y, or Z) whose axis is closest to the viewing direction [S1, S2][S3, unofficial]. This minimizes the angle between the slice normal and the view vector, reducing perspective distortion and improving sampling density [S1, S2][S3, unofficial].

3.  **Rendering (Compositing):**
    a.  Sort the selected slices in back-to-front order relative to the viewer [S1, S2][S3, S5, unofficial].
    b.  For each slice, render the polygons using graphics hardware.
    c.  Sample the transfer function texture using the normalized scalar values at the polygon vertices to determine color and opacity [S1, S2][S3, unofficial].
    d.  Composite fragments into the frame buffer using hardware alpha blending:
        $$ C_{dest} = C_{src} \cdot A_{src} + C_{dest} \cdot (1 - A_{src}) $$
        where $C_{src}$ and $A_{src}$ are the color and opacity from the texture sample, and $C_{dest}$ is the current frame buffer color [S3, unofficial].

**Parameters:**
*   **Slice Density:** "Several hundred" evenly spaced planes per axis [S1, S2].
*   **Alpha Dithering:** Used to expand the range of allowable opacity values for 8-bit hardware when slice density is high and per-slice opacity is low [S1, S2][S3, unofficial]. The texture map is adjusted for per-slice opacity when spacing changes [S1, S2][S3, unofficial].

**Edge Cases and Pitfalls:**
*   **Small Cells:** Cells smaller than the slice spacing may be missed between planes or during scan conversion. The method supplements this with anti-aliased ellipsoidal splats for cells below a threshold [S1, S2][S3, unofficial].
*   **Non-planar Faces:** Convex polyhedral cells with non-planar faces can cause sorting and scan conversion issues. A solution involves selectively subdividing such cells into tetrahedra [S1, S2][S3, unofficial].
*   **Perspective Distortion:** In perspective views, viewing rays between slanted slice planes vary in length. The basic method does not account for this per-pixel opacity correction [S1, S2][S3, unofficial].
*   **Ordering Importance:** Slice plane ordering is critical when drawing objects with different colors (e.g., smoke and fire) or elaborate lighting, but less critical for single-color smoke where only opacity varies [S5, unofficial].

## Subtopics

### View-Oriented Planes Technique
A variant using a fixed number of planes oriented to cover the entire data volume. The minimum number of planes required is equal to the number of voxels in the volume diagonal: $\sqrt{W^2 + H^2 + D^2}$, where $W, H, D$ are volume dimensions [S4, unofficial]. For a $181 \times 217 \times 181$ volume, this is 336 planes [S4, unofficial]. Using more planes (e.g., 400) improves quality but significantly reduces speed due to increased fragments, memory accesses, and blending operations, making alpha testing gains negligible [S4, unofficial].

### Slice Plane Ordering
A rendering rule requiring parent objects to be drawn back-to-front to prevent transparent objects from appearing blended in front of obscured objects [S5, unofficial]. This is essential for multi-color scenes (e.g., smoke and fire) or complex lighting, but not for single-color smoke [S5, unofficial].

## Operating characteristics
*   **Time Complexity:** Preprocessing is $O(N)$ where $N$ is the number of cells, as each cell is sliced into three polygons. Rendering is $O(S)$ where $S$ is the number of selected slices.
*   **Memory Complexity:** $O(S \cdot P)$ where $S$ is the number of slices and $P$ is the average number of polygons per slice. Storing three sets of slices triples the memory requirement compared to single-axis slicing [S1, S2][S3, unofficial].
*   **Performance:** High performance for interactive visualization when the view direction is aligned with one of the axes. Performance degrades with perspective views due to lack of per-pixel opacity correction [S1, S2][S3, unofficial]. The View-Oriented Planes Technique suffers from low performance due to excessive memory accesses and blending [S4, unofficial].
*   **Strengths:** Allows dynamic view orientation without re-computing slices; leverages hardware alpha blending; supports progressive refinement [S1, S2][S3, unofficial].
*   **Limitations:** High memory usage for three axis sets; potential for gaps between slices for small cells; sorting complexity for unstructured grids [S1, S2][S3, unofficial].

## Background
Plane Slicing was proposed by Yagel et al. [4] and implemented for curvilinear and unstructured grids by Max et al. in the early 2000s [S1, S2][S3, unofficial]. It was developed to address the need for interactive volume rendering of large scientific datasets, leveraging graphics hardware for compositing [S1, S2][S3, unofficial]. The method is used in scientific visualization tools for unstructured grids [S1, S2][S3, unofficial].
