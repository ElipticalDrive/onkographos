# MC Slicing

Also called: MC Slicing algorithm variant, Marching Cubes Slicing

## Overview
MC Slicing is a volume rendering method that applies the pre-calculated table look-up idea from the Marching Cubes algorithm to efficiently triangulate the intersection of a slicing plane with a hexahedron (volume) [S1][S2, unofficial]. It solves the problem of generating polygon geometry for view-aligned slices by reducing the number of intersection calculations per slice compared to standard convex hull approaches [S1][S2, unofficial]. It sets itself apart from its siblings, [Plane Composing Algorithms](2154-plane-composing-algorithms.md) and [Slice Plane Ordering](4041-slice-plane-ordering.md), by leveraging the 256-case vertex classification of Marching Cubes to determine intersected edges and their ordering in linear time, rather than computing intersections for all 12 edges of the hexahedron [S1][S2, unofficial].

## How it works
**Inputs:**
*   A hexahedron defined by 8 vertices $V_0, \dots, V_7$ in 3D space.
*   A slicing plane defined by an origin point $P_0$ and a normal vector $\mathbf{n}$.
*   A pre-calculated lookup table mapping vertex classification bitmasks to ordered sequences of intersected edges.

**Outputs:**
*   A set of vertices forming triangles (typically arranged for triangle fan generation) representing the intersection of the plane and the hexahedron.

**Data Structures:**
*   **Lookup Table:** An array of size 256 (since $2^8 = 256$ possible vertex combinations). Each entry contains an ordered sequence of edge indices that are intersected by the plane for that specific vertex configuration. The edges are ordered to allow clockwise traversal for triangle fan generation [S1][S2, unofficial].
*   **Bitmask:** An 8-bit integer where the $i$-th bit is set if vertex $V_i$ is behind the plane. The bit weights are powers of 2: $V_0=1, V_1=2, V_2=4, V_3=8, V_4=16, V_5=32, V_6=64, V_7=128$ [S2, unofficial].

**Steps:**
1.  **Vertex Classification:** For each of the 8 vertices $V_i$ of the hexahedron, calculate the vector $\mathbf{v}_i = V_i - P_0$. Compute the dot product $d_i = \mathbf{v}_i \cdot \mathbf{n}$ [S1][S2, unofficial].
    *   If $d_i > 0$, the vertex is in front of the plane.
    *   If $d_i < 0$, the vertex is behind the plane.
    *   If $d_i = 0$, the vertex is on the plane [S1][S2, unofficial].
2.  **Hashing:** Calculate a hashing value (bitmask index) by summing the bit weights of all vertices classified as "behind" the plane. Let $B$ be the set of indices $i$ where $d_i < 0$. The index $I$ is:
    $$ I = \sum_{i \in B} 2^i $$
    [S2, unofficial]
3.  **Table Lookup:** Retrieve the entry from the lookup table at index $I$. This entry provides an ordered sequence of edge indices that the plane intersects [S2, unofficial].
4.  **Intersection Calculation:** For each edge index in the retrieved sequence, calculate the exact intersection point of the slicing plane with that edge.
    *   An edge connects two vertices $V_a$ and $V_b$.
    *   The intersection point $P_{int}$ is found by linear interpolation. Let $t$ be the fraction along the edge:
        $$ t = \frac{-d_a}{d_b - d_a} $$
        $$ P_{int} = V_a + t(V_b - V_a) $$
    *   Note: The algorithm performs at most 6 intersection tests, as opposed to 12 in the Convex Hull method [S1][S2, unofficial].
5.  **Optimization (Convex Hull Optimization):** If slicing planes appear at constant intervals along the view frustum's near plane normal, the intersection points on an edge move at constant intervals [S2, unofficial].
    *   Maintain the previous intersection point $P_{prev}$ on the edge and the constant interval vector $\Delta \mathbf{p}$ along the edge.
    *   If $P_{prev} + \Delta \mathbf{p}$ remains within the edge boundaries (between $V_a$ and $V_b$), omit the intersection calculation and use vector addition: $P_{curr} = P_{prev} + \Delta \mathbf{p}$ [S2, unofficial].
    *   If the point has left the edge boundaries, perform the standard intersection test (2 dot products) [S2, unofficial].
    *   This optimization replaces 2 dot products with 3 vector additions when the assumption holds [S2, unofficial].
6.  **Vertex Ordering:** The edges returned by the lookup table are already ordered clockwise, which is sufficient for creating triangle fans in linear time [S1][S2, unofficial].

**Pseudocode:**
```python
def mc_slice(hexahedron_vertices, plane_origin, plane_normal, lookup_table, prev_intersections=None):
    """
    hexahedron_vertices: list of 8 vectors [V0, ..., V7]
    plane_origin: vector P0
    plane_normal: vector n (assumed normalized)
    lookup_table: list of 256 entries, each entry is a list of edge indices
    prev_intersections: dict mapping edge_index -> (point, delta_vector) from previous slice, or None
    
    Returns: list of intersection points in clockwise order for triangle fan
    """
    # Step 1: Vertex Classification
    dot_products = []
    behind_indices = []
    for i, v in enumerate(hexahedron_vertices):
        vec = v - plane_origin
        d = dot_product(vec, plane_normal)
        dot_products.append(d)
        if d < 0:
            behind_indices.append(i)
            
    # Step 2: Hashing
    index = 0
    for i in behind_indices:
        index += (1 << i)
        
    # Step 3: Table Lookup
    edge_sequence = lookup_table[index]
    
    # Step 4 & 5: Intersection Calculation with Optimization
    result_points = []
    for edge_idx in edge_sequence:
        # Edge connects vertex A and vertex B
        # Assuming edge indices map to pairs of vertex indices. 
        # Standard MC edge numbering: 0:(0,1), 1:(1,2), 2:(2,3), 3:(3,0), 
        # 4:(4,5), 5:(5,6), 6:(6,7), 7:(7,4), 8:(0,4), 9:(1,5), 10:(2,6), 11:(3,7)
        # Note: The exact mapping depends on the specific lookup table definition.
        # We assume a helper function get_edge_vertices(edge_idx) exists or is defined.
        v_a_idx, v_b_idx = get_edge_vertices(edge_idx)
        v_a = hexahedron_vertices[v_a_idx]
        v_b = hexahedron_vertices[v_b_idx]
        d_a = dot_products[v_a_idx]
        d_b = dot_products[v_b_idx]
        
        # Optimization Check
        if prev_intersections and edge_idx in prev_intersections:
            prev_point, delta_vec = prev_intersections[edge_idx]
            candidate_point = prev_point + delta_vec
            
            # Check if candidate is still within edge boundaries
            # Vector from A to candidate
            vec_ac = candidate_point - v_a
            vec_ab = v_b - v_a
            
            # Check if candidate is between A and B
            # Dot product of vec_ac and vec_ab should be between 0 and |ab|^2
            # And cross product magnitude should be 0 (collinear) - but since we move along edge,
            # we just check projection.
            len_ab_sq = dot_product(vec_ab, vec_ab)
            proj = dot_product(vec_ac, vec_ab)
            
            if 0 <= proj <= len_ab_sq:
                # Optimization successful
                result_points.append(candidate_point)
                # Update delta vector for next time? 
                # The delta vector is constant if planes are constant interval.
                # We store it.
                prev_intersections[edge_idx] = (candidate_point, delta_vec)
                continue
        
        # Standard Intersection Test
        # t = -d_a / (d_b - d_a)
        denom = d_b - d_a
        if abs(denom) < 1e-9:
            # Edge is parallel to plane or both on plane. 
            # If both on plane, d_a=0 and d_b=0. 
            # This case is handled by the lookup table logic usually, 
            # but if an edge is on the plane, it might be degenerate.
            # For MC slicing, if vertices are on the plane, they are not "behind".
            # So d_a >= 0 and d_b >= 0. If one is 0, t=0 or t=1.
            if d_a == 0:
                t = 0.0
            elif d_b == 0:
                t = 1.0
            else:
                # Both positive, no intersection on this edge segment for this classification?
                # This shouldn't happen if the lookup table is correct for the bitmask.
                continue 
        else:
            t = -d_a / denom
            
        intersection_point = v_a + t * (v_b - v_a)
        result_points.append(intersection_point)
        
        # Store for optimization
        if prev_intersections is None:
            prev_intersections = {}
        # Calculate delta vector for next slice
        # This requires knowing the plane shift. 
        # If we don't have the previous plane, we can't compute delta.
        # The optimization relies on the caller providing prev_intersections 
        # which includes the delta vector derived from the previous slice's plane shift.
        # Here we just store the point. The delta vector calculation is external 
        # to this pure function if the plane shift isn't passed.
        # For the sake of self-contained pseudocode, we assume the caller handles 
        # the delta vector storage if optimization is active.
        
    return result_points

def get_edge_vertices(edge_idx):
    # Standard Marching Cubes edge indexing
    edges = [
        (0, 1), (1, 2), (2, 3), (3, 0), # Bottom face
        (4, 5), (5, 6), (6, 7), (7, 4), # Top face
        (0, 4), (1, 5), (2, 6), (3, 7)  # Vertical edges
    ]
    return edges[edge_idx]
```

**Parameters:**
*   **Hexahedron Vertices:** 8 vertices [S1].
*   **Lookup Table Size:** 256 entries ($2^8$) [S1][S2, unofficial].
*   **Intersection Tests:** At most 6 per hexahedron [S1][S2, unofficial].

**Edge Cases and Pitfalls:**
*   The algorithm relies on polygon vertices always being found on the edges of the common convex hexahedron [S2, unofficial].
*   The Convex Hull optimization relies on slicing planes appearing at constant intervals. If this assumption does not hold, the optimization must be disabled, and standard intersection tests must be performed [S2, unofficial].
*   Precision issues may arise if the dot product is very close to zero (vertex on plane). The sources define "on the plane" as $d=0$ [S1][S2, unofficial].

## Subtopics

### Plane Slicing
The parent method that defines the overall strategy of slicing cells into polygons on evenly spaced planes. MC Slicing is the specific triangulation technique used within this framework. [Link](845-plane-slicing.md)

### Plane Composing Algorithms
Siblings that may use different methods to compose the final image from slices. MC Slicing is chosen for its efficiency in triangulation. [Link](2154-plane-composing-algorithms.md)

### Slice Plane Ordering
Siblings that determine the order in which slices are processed. MC Slicing's optimization benefits from consistent ordering and spacing. [Link](4041-slice-plane-ordering.md)

## Operating characteristics
*   **Time Complexity:** The vertex classification requires 8 dot products. The lookup is $O(1)$. The intersection calculation is $O(1)$ with at most 6 tests. With the Convex Hull optimization, intersection tests can be reduced to vector additions, further lowering constant factors. The overall complexity per hexahedron is constant and very low [S2, unofficial].
*   **Memory Complexity:** Requires a lookup table of 256 entries. The size of each entry depends on the maximum number of intersected edges (typically small, e.g., 4-6 triangles). This is negligible [S2, unofficial].
*   **Measured Performance:** In tests with density 8 and 20 slices, MC Slicing achieved 68 FPS, compared to 53 FPS for Convex Hull Optimized (CH Opt) and 56 FPS for Convex Hull (CH) [S1].
*   **Strengths:** Significantly faster than classic Convex Hull methods due to reduced intersection tests (6 vs 12) and implicit vertex ordering for triangle fans [S1][S2, unofficial].
*   **Limitations:** The Convex Hull optimization is only valid if slicing planes are at constant intervals [S2, unofficial]. The algorithm is specific to convex hexahedra [S2, unofficial].
*   **When to use:** When rendering volumes using view-aligned slicing planes on hexahedral grids and performance is critical.
*   **When not to use:** If the slicing planes are not at constant intervals and the optimization is needed, or if the volume is not composed of hexahedra.

## Background
MC Slicing was introduced by Y. Vanzine and D. Vrajitoru in 2008 for the real-time volumetric rendering of fire in a production system [S1][S2, unofficial]. It is based on the classic Marching Cubes algorithm by Lorensen and Cline (1987) [S1][S2, unofficial]. The idea of pre-calculating intersections between a plane and a volume was also described in [BPP01] and [BBJL05] [S1]. The method was developed to improve the speed of volume rendering by reducing the computational cost of triangulation [S2, unofficial].
