# Index Texture Cache for Spline Search

Also called: Cache Index Texture, Incremental Spline Search Cache

## Overview
An acceleration technique that caches the indices of spline segments used in previous rendering slices to avoid redundant binary searches for the current slice, leveraging depth-order coherence in front-to-back traversal [S1, unofficial]. Unlike the basic algorithm which requires four spline searches per pixel fragment using binary search, this method uses incremental linear search from the previous slice's position, reducing computational bottleneck [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** The current rendering slice index, the previous slice's cache state, and the Parametric Representation Image (PRI) structure containing spline data.
*   **Output:** Updated cache index texture for the current slice, and the final rendered slice image.

**Data Structures:**
*   **Cache Index Texture:** A 2D texture with resolution equal to the PRI's pixelized sampling plane. Each texel stores the index of the spline segment (knot) currently active for that spatial location [S1, unofficial].
*   **Ping-Pong Textures:** Two textures used to swap read/write roles during the update pass to ensure atomicity and avoid race conditions [S1, unofficial].

**Steps:**
1.  **Initialization:** Initialize the 2D cache index texture with the same resolution as the PRI's pixelized sampling plane. Populate it with the contents of the index texture to cache the first knots of each spline [S1, unofficial].
2.  **Two-Pass Rendering:** For each slice in the rendering stack, perform a two-pass approach.
3.  **Pass 1: Cache Update:**
    *   Set the camera to coincide with the PRI.
    *   Specify the cache index texture (current write target) as the rendering target.
    *   Map the cache index texture to the slice via projective texture mapping using orthogonal projection in the sampling direction of the PRI [S1, unofficial].
    *   At each texel, perform a linear search to find the appropriate spline segment. Start the search from the segment index stored in the previous slice's cache (read from the ping-pong source texture).
    *   If the next slice requires a spline segment not used in the previous slice, the linear search quickly finds the required segment by starting from the segment processed in the previous slice [S1, unofficial].
    *   Write the new segment index to the cache index texture.
    *   Swap ping-pong textures for the next iteration.
4.  **Pass 2: Slice Rendering:**
    *   Render the slice from the user's view.
    *   Use the updated cache index texture and dependent texturing to fetch the correct spline segment data for trilinear interpolation [S1, unofficial].

**Pseudocode:**
```python
def render_slice_with_cache(slice_index, pri, previous_cache_texture, current_cache_texture):
    # Pass 1: Update Cache
    # Set camera to PRI view
    set_camera_to_pri(pri)
    
    # Bind previous cache as read, current as write
    bind_texture(previous_cache_texture, target=GL_TEXTURE0)
    bind_render_target(current_cache_texture)
    
    # Projective texture mapping setup
    # Orthogonal projection in PRI sampling direction
    setup_projective_mapping(pri.sampling_direction)
    
    # Render a full-screen quad to update cache
    # Fragment shader logic:
    # 1. Read segment index from previous_cache_texture at current texel coord
    # 2. Perform linear search starting from that index to find correct segment for current slice depth
    # 3. Write new segment index to current_cache_texture
    
    render_fullscreen_quad(update_cache_shader)
    
    # Pass 2: Render Slice
    # Set camera to user view
    set_camera_to_user_view()
    
    # Bind updated cache as texture
    bind_texture(current_cache_texture, target=GL_TEXTURE1)
    
    # Render slice using dependent texturing
    render_slice(slice_render_shader, cache_texture_unit=GL_TEXTURE1)
    
    # Swap textures for next slice
    return current_cache_texture, previous_cache_texture
```

**Parameters:**
*   **Cache Index Texture Resolution:** Equal to the PRI's pixelized sampling plane resolution [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Screen Resolution Mismatch:** When the user's screen resolution exceeds the PRI's sampling plane resolution, multiple pixel fragments may fall within the same neighborhood of four splines. In this case, bilinear interpolation of scalar values from the four neighboring splines can be used for efficiency [S1, unofficial].
*   **Depth Order:** The method assumes front-to-back traversal, though it can be adapted for back-to-front [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Reduces the search cost from binary search ($O(\log N)$) to incremental linear search. The average case is significantly faster due to coherence between adjacent slices.
*   **Memory Complexity:** Requires additional memory for the cache index texture (2D texture same size as PRI sampling plane) and ping-pong buffers.
*   **Strengths:** Eliminates redundant binary searches by leveraging temporal coherence.
*   **Limitations:** Requires two-pass rendering per slice. Performance may degrade if coherence is low (e.g., large jumps between slices).

## Background
This method is part of the GPU-based cut-off slice generation pipeline for volume rendering, specifically addressing the computational bottleneck of spline searches in unstructured grid rendering [S1, unofficial]. It builds on the incremental intersection and texture coordinates method [997-incremental-intersection-and-texture-coordinates.md].
