# GPU-based Cut-off Slice Generation

Also called: Plane-Cube Clipping, Rezk-Salama method, Slice-Cube Intersection, Vertex Shader Slice Generation, View-Aligned Slicing (Proxy Geometry), ViewSliceCube, Viewport-Aligned Slices Intersection Algorithm

## Overview
GPU-based Cut-off Slice Generation is an object-order volume rendering technique that computes the intersection polygons between a series of parallel slicing planes and the volume's bounding box entirely on the GPU using vertex shaders [S1, unofficial][S2, book][S4, unofficial]. It solves the performance bottleneck of CPU-side geometric intersection calculations by offloading the generation of proxy geometry (polygon meshes) to the graphics pipeline [S1, unofficial][S2, book]. Unlike texture-based slicing which samples a 3D texture directly, this method generates explicit geometry that can be rendered using standard triangle pipelines, facilitating advanced shading models [S2, book][S5]. It sets itself apart from sibling methods like [Plane Slicing](845-plane-slicing.md) by explicitly handling the vertex duplication and sorting required to output valid polygons from a fixed-vertex vertex shader, and from [Sliced Volume Rendering](3568-sliced-volume-rendering.md) by focusing on the geometric intersection logic rather than the ray-casting accumulation.

## How it works
**Inputs and Outputs:**
*   **Inputs:** Volumetric data (bound as 3D textures), Model-View matrix, View direction ($\vec{n}_p$), Number of slices ($N$), Voxel size, Sampling rate.
*   **Outputs:** A vertex array containing triangulated proxy polygons for each slice plane, ready for rasterization.

**Data Structures:**
*   **Bounding Box:** Represented by 8 vertices and 12 edges. Each edge $E_{i \rightarrow j}$ connects vertex $V_i$ to $V_j$.
*   **Edge Flags:** A set of 6 bits stored for each edge, corresponding to the 6 faces of the bounding box. A bit is set if the edge belongs to that face [S3, unofficial].
*   **Render Array:** `renderSliceArray[MAX_SLICES * 12]` of `glm::vec3` (or equivalent float32 RGB). Stores 12 vertices (4 triangles) per slice. Memory layout is contiguous [S4, unofficial].
*   **Parameters:**
    *   `num_slices`: Integer, number of parallel planes. Default: 10 [S4, unofficial].
    *   `viewDir`: `vec3`, direction perpendicular to slice planes. Default: $(0.0, 0.0, -1.0)$ [S4, unofficial].
    *   `EPSILON`: Float, boundary expansion factor. Value: $0.0001$ [S4, unofficial].
    *   `MAX_SLICES`: Integer, maximum capacity. Value: 2000 [S4, unofficial].

**Numbered Steps:**

1.  **Transform Bounding Box:** Transform the 8 vertices of the volume bounding box into view coordinates using the Model-View matrix [S2, book][S5].
2.  **Determine Depth Bounds:** Compute the minimum ($min\_z$) and maximum ($max\_z$) z-coordinates of the transformed vertices by projecting them onto the view direction [S2, book][S4, unofficial].
    $$ min\_z = \min_i (\vec{V}_i \cdot \vec{n}_p) $$
    $$ max\_z = \max_i (\vec{V}_i \cdot \vec{n}_p) $$
    Adjust bounds to avoid missed intersections:
    $$ min\_z \leftarrow min\_z - \text{EPSILON} $$
    $$ max\_z \leftarrow max\_z + \text{EPSILON} $$
3.  **Compute Slice Planes:** Calculate the number of sampling planes and their spacing. The sampling distance is derived from voxel size and current sampling rate [S2, book][S5].
    $$ plane\_dist\_inc = \frac{max\_z - min\_z}{num\_slices} $$
    Initialize $plane\_dist = min\_z$ [S4, unofficial].
4.  **Calculate Intersections (Per Plane):** For each plane at distance $plane\_dist$:
    *   Iterate over the 12 edges of the bounding box.
    *   For each edge $i$, compute the dot product with the view direction:
        $$ edgedot = \vec{e}_{i \rightarrow j} \cdot \vec{n}_p $$
    *   Compute the intersection parameter $\lambda$ [S1, unofficial]:
        $$ \lambda[i] = \begin{cases} \frac{plane\_dist - \vec{V}_i \cdot \vec{n}_p}{edgedot}, & edgedot \neq 0 \\ -1.0, & edgedot = 0 \end{cases} $$
        *   If $edgedot = 0$, the edge is parallel to the plane. Set $\lambda[i] = -1.0$ and $\lambda\_inc[i] = 0.0$ to skip [S4, unofficial].
        *   If $\lambda[i] \in [0, 1]$, the intersection is valid and lies on the edge segment [S1, unofficial].
    *   **Incremental Optimization:** To avoid recomputing $\lambda$ for every plane, compute $\lambda$ for the first plane and update incrementally for subsequent planes [S3, S4, unofficial]:
        $$ \lambda\_inc[i] = \frac{plane\_dist\_inc}{edgedot} \quad (\text{if } edgedot \neq 0) $$
        $$ \lambda_{new}[i] = \lambda_{old}[i] + \lambda\_inc[i] $$
5.  **Sort and Validate Vertices:**
    *   Collect all valid intersection points ($\lambda \in [0, 1]$).
    *   **Edge Flag Validation:** Use the 6-bit edge flags to verify the sequence. A sequence is valid if the bitwise OR of flags for adjacent points is non-zero (indicating a shared face) [S3, unofficial].
    *   **Polygon Formation:** The algorithm must output exactly 6 vertices per slice, even if the polygon has fewer vertices. Duplicate vertices are generated by recalculation or feedback from existing intersections if edges (Yellow, Cyan, Purple) have no intersection [S1, unofficial].
    *   **Sorting:** Sort the vertices to form a closed polygon.
        *   *Method A (Rezk-Salama/Shen):* Traverse edges in a specific order: Red ($E_{0\rightarrow1}, E_{1\rightarrow4}, E_{4\rightarrow7}$), Yellow, Green ($E_{0\rightarrow2}, E_{2\rightarrow5}, E_{5\rightarrow7}$), Cyan, Blue ($E_{0\rightarrow3}, E_{3\rightarrow6}, E_{6\rightarrow7}$), Purple. If an intermediate group (Yellow/Cyan/Purple) has no intersection, duplicate the previous group's intersection [S1, unofficial].
        *   *Method B (Pseudo-Angle):* Compute the center of the proxy polygon by averaging intersection points. Project vertices onto the x-y plane. Sort using a "pseudo-angle" scalar (tangent of angle combined with sign of coordinates) to avoid trigonometry [S2, book][S5].
6.  **Tessellation:** Triangulate the sorted polygon vertices.
    *   Commonly tessellated into 4 triangles using an index array `{0,1,2, 0,2,3, 0,3,4, 0,4,5}` for a 6-vertex quad/polygon [S4, unofficial].
    *   Alternatively, use a triangle fan or strip from the center [S2, book][S5].
7.  **Texture Coordinate Generation:** Compute texture coordinates for the vertices to sample the 3D volume [S1, unofficial][S2, book].
    $$ PI \cdot \vec{k} = \begin{cases} \frac{V_i \vec{k} - min(B_{\vec{k}})}{max(B_{\vec{k}}) - min(B_{\vec{k}})} & \vec{k} \cdot \vec{e}_{i \rightarrow j} = 0 \\ \lambda & \vec{k} \cdot \vec{e}_{i \rightarrow j} > 0 \\ 1 - \lambda & \vec{k} \cdot \vec{e}_{i \rightarrow j} < 0 \end{cases} $$
    Where $\vec{k}$ is the x, y, or z unit vector in texture space, and $B_{\vec{k}}$ is the bounding box length in that direction [S1, unofficial].
8.  **Output:** Upload the vertex array to the GPU (e.g., `glBufferSubData`) for rendering [S4, unofficial].

## Subtopics

### [Incremental Intersection and Texture Coordinates](997-incremental-intersection-and-texture-coordinates.md)
Computes intersection points incrementally using constant deltas for parallel planes, avoiding recomputation.

### [View-Aligned Slicing (Proxy Geometry Generation)](7620-view-aligned-slicing-proxy-geometry-generation.md)
Approximates the volume by intersecting the bounding box with view-aligned planes, generating explicit proxy meshes for standard rasterization.

### [Slice Vertex Sorting via Pseudo-Angle](7642-slice-vertex-sorting-via-pseudo-angle.md)
Sorts intersection vertices around the centroid using a pseudo-angle metric to ensure correct triangulation order.

### [MTCut Algorithm](11789-mtcut-algorithm.md)
Generates cut geometry using a vertex-shader-based Marching Tetrahedra variant, encoding traversal state in 2D textures.

## Operating characteristics
*   **Time Complexity:** $O(N \cdot E)$ per frame, where $N$ is the number of slices and $E$ is the number of edges (constant 12). Incremental updates reduce the cost of intersection calculation to $O(1)$ per edge per slice after the first plane [S3, unofficial].
*   **Memory Complexity:** $O(N \cdot V)$, where $V$ is the number of vertices per slice (constant 6 or 12). The output array size is fixed by `MAX_SLICES` [S4, unofficial].
*   **Performance:** Offloads CPU geometry generation to the GPU, enabling interactive frame rates (<100ms response time) for dynamic view changes [S1, unofficial]. Performance is limited by the number of slices and the complexity of the fragment shader (texture lookups) [S1, unofficial].
*   **Strengths:** Real-time interaction, supports advanced shading (e.g., LTC), avoids CPU-GPU synchronization bottlenecks for geometry generation.
*   **Limitations:** Vertex shaders cannot insert/remove vertices, requiring fixed-output algorithms (6 vertices) and duplicate handling [S1, unofficial]. Cannot rotate more than 180 degrees in one arc-ball drag operation [S1, unofficial]. Precision issues may occur if $\lambda$ is near 0 or 1; EPSILON helps but requires tuning [S4, unofficial].

## Background
The method originates from the work of Rezk-Salama et al. [50], who proposed moving the calculation of cut-off slices from the CPU to the GPU vertex shader [S1, unofficial]. It was further refined by Shen et al. [56] to provide more flexible texture coordinate translation [S1, unofficial]. The technique is described in *GPU Gems* Chapter 39 as "View-Aligned Slicing" [S2, book][S5] and is implemented in various open-source projects [S4, unofficial]. It is widely used in scientific visualization and medical imaging for real-time volume exploration.
