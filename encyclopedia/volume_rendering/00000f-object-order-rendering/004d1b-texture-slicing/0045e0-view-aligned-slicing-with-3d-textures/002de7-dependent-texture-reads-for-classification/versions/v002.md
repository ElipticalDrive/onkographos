# Dependent Texture Reads for Classification

Also called: Dependent Texture Reads, Pixel Texture, Texture-Based Classification

## Overview
Dependent Texture Reads (DTR) is a hardware extension that uses the color components of a fragment to generate texture coordinates, replacing the original color with values looked up from a texture [S1, book][S2]. In volume rendering, it serves as an efficient mechanism for multidimensional transfer function evaluation (classification) and shading by treating fragment colors as inputs to a lookup table [S1, book][S2]. Unlike standard texture sampling where coordinates are explicit attributes, DTR derives coordinates dynamically from the fragment's RGB values, enabling arbitrary function evaluation with up to three variables [S1, book][S2].

## How it works
**Inputs and Outputs:**
*   **Input:** A fragment with RGB color values representing data properties (e.g., scalar values, gradients, or derived features) and a 3D texture containing the transfer function (color and alpha values) [S1, book].
*   **Output:** A new fragment color and alpha value determined by the 3D texture lookup [S1, book].

**Data Structures:**
*   **3D Transfer Function Texture:** A 3D texture where each texel stores the output color (RGB) and opacity (A) [S1, book]. The dimensions of this texture do not need to match the dynamic range of the input data channels, allowing for memory-efficient discretization [S1, book].
*   **Proxy Geometry:** Typically a plane or view-aligned slice across which data values are interpolated [S1, book].

**Steps:**
1.  **Data Interpolation:** Data values are stored in the color components of a 3D texture (or derived from volume data) and interpolated across proxy geometry (e.g., a plane) [S1, book].
2.  **Coordinate Generation:** The RGB channel values of the resulting fragment are scaled to the range $[0, 1]$ [S1, book]. These scaled values serve as the $(u, v, w)$ texture coordinates for the 3D transfer function texture [S1, book].
3.  **Texture Lookup:** A 3D texture lookup is performed using the generated coordinates [S1, book].
4.  **Interpolation:** The lookup uses either nearest-neighbor or linear interpolation to determine the replacement color values [S1, book].
5.  **Replacement:** The original RGB fragment values are replaced by the color and alpha values acquired from the 3D texture lookup [S1, book].

**Pseudocode:**
```python
def clamp(x, lo, hi):
    return max(lo, min(hi, x))

def lerp(a, b, t):
    return a + t * (b - a)

def trilinear_interpolate(tex, u, v, w, dim_x, dim_y, dim_z):
    # Map normalized coordinates [0,1] to texel indices [0, dim-1]
    # This mapping aligns hardware texture sampling with standard raycast references
    ix = u * (dim_x - 1)
    iy = v * (dim_y - 1)
    iz = w * (dim_z - 1)
    
    x0, x1 = int(ix), min(int(ix) + 1, dim_x - 1)
    y0, y1 = int(iy), min(int(iy) + 1, dim_y - 1)
    z0, z1 = int(iz), min(int(iz) + 1, dim_z - 1)
    
    fx = ix - x0
    fy = iy - y0
    fz = iz - z0
    
    # Fetch 8 surrounding texels (RGBA)
    c000 = tex[x0, y0, z0]
    c100 = tex[x1, y0, z0]
    c010 = tex[x0, y1, z0]
    c110 = tex[x1, y1, z0]
    c001 = tex[x0, y0, z1]
    c101 = tex[x1, y0, z1]
    c011 = tex[x0, y1, z1]
    c111 = tex[x1, y1, z1]
    
    # Trilinear interpolation
    c00 = lerp(c000, c100, fx)
    c01 = lerp(c010, c110, fx)
    c10 = lerp(c001, c101, fx)
    c11 = lerp(c011, c111, fx)
    
    c0 = lerp(c00, c01, fy)
    c1 = lerp(c10, c11, fy)
    
    return lerp(c0, c1, fz)

def classify_fragment(frag_rgb, transfer_function_texture, dim_x, dim_y, dim_z):
    # Step 1 & 2: Scale and clamp RGB channels to [0, 1] as per hardware behavior [S1, book]
    u = clamp(frag_rgb.r, 0.0, 1.0)
    v = clamp(frag_rgb.g, 0.0, 1.0)
    w = clamp(frag_rgb.b, 0.0, 1.0)
    
    # Step 3 & 4: Perform 3D texture lookup with linear interpolation
    new_color = trilinear_interpolate(transfer_function_texture, u, v, w, dim_x, dim_y, dim_z)
    
    # Step 5: Return replacement color and alpha
    return new_color
```

**Parameters:**
*   **Texture Dimensions:** The number of elements along an axis of the 3D transfer function texture can differ from the dynamic range of the input component [S1, book]. This flexibility prevents prohibitively large textures [S1, book]. For example, for 8-bit data, an ideal texture might have 256 values per axis, but this is often reduced for performance [S1, book].
*   **Interpolation Mode:** Nearest-neighbor or linear interpolation [S1, book].

**Edge Cases and Pitfalls:**
*   **Memory Size:** Without the ability to scale coordinates, a 3D dependent texture would require dimensions matching the full dynamic range of the input data, leading to prohibitively large memory requirements [S1, book].
*   **Data Range:** Input values must be appropriately scaled to $[0, 1]$ to map correctly to texture coordinates [S1, book].
*   **Boundary Mapping:** Texture coordinates map $0.0$ to the left/bottom edge and $1.0$ to the right/top edge of the texture volume; failing to scale coordinates to $[0, 1]$ or using incorrect index mapping causes systematic sampling bias [G].

## Subtopics

### Classification
The primary use case, where DTR evaluates multidimensional transfer functions per-pixel in screen space [S1, book][S2]. It allows for interactive updates of transfer functions by rasterizing classification widgets [S1, book].

### Shading
DTR can also be used for volumetric shading and shadow calculations, extending its utility beyond simple color mapping [S2].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Not given in the sources.
*   **Performance:** Hardware-accelerated, making it significantly more efficient than software-based lookup tables [S1, book][S2].
*   **Strengths:** Enables real-time interaction with multidimensional transfer functions; leverages existing GPU texture hardware [S1, book][S2].
*   **Limitations:** Limited to up to three variables (RGB channels); texture size constraints limit the resolution of the transfer function [S1, book][S2].

## Background
Dependent texture reads are hardware extensions similar to but more efficient than the earlier "pixel texture" extension [S1, book][S2]. They were introduced to support multidimensional transfer functions in volume rendering, allowing for interactive exploration and classification [S1, book][S2]. The technique is heavily utilized in OpenGL-based volume rendering pipelines [S2].
