# 2D Texture-Based Advection with Tile Reordering

Also called: 2D IBFV advection, Real-Time Advection

## Overview
A method for advecting particle traces in 3D unsteady flow using a single 2D texture on the GPU, avoiding the need for multiple copies of volume data or 3D textures by reordering the stacking direction dynamically [S1]. It sets itself apart from its parent [GPU-based 3D Texture Advection with Logical-to-Physical Mapping](19774-gpu-based-3d-texture-advection-with-logical-to-physical-mapp.md) by dynamically changing the stacking axis during advection to maintain visual quality, whereas the parent uses a fixed logical-to-physical mapping [S1]. It differs from its sibling [2D Texture-Based Advection with Volumetric Illumination](19825-2d-texture-based-advection-with-volumetric-illumination.md) by focusing specifically on the advection mechanism and memory layout rather than the illumination integration [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D unsteady vector field $\mathbf{v}(\mathbf{x}, t)$, a property field $\rho(\mathbf{x}, t)$ stored in a single 2D texture, and a current viewing direction.
*   **Output:** The advected property field $\rho(\mathbf{x}, t + \Delta t)$ stored in the same 2D texture, ready for volume rendering.

**Data Structures:**
*   **Physical Memory:** A single 2D texture of size $W \times H$.
*   **Logical Memory:** A 3D grid of size $N_x \times N_y \times N_z$.
*   **Tiling:** The logical 3D grid is mapped to the 2D texture in "tiles." Each tile corresponds to a 2D slice of the logical grid. The size of a tile is determined by the dimensions of the logical slice (e.g., $N_x \times N_z$ for a y-slice).
*   **Borders:** A one-texel-wide border is added around each tile in physical memory to prevent erroneous influence from neighboring tiles during bilinear interpolation [S1].

**Parameters:**
*   **Threshold Angle:** 45 degrees. The stacking direction is changed if the viewing angle exceeds this threshold relative to the stacking axis [S1].

**Steps:**

1.  **Determine Stacking Direction:** Calculate the angle between the current viewing direction and the current stacking axis. If the angle is greater than 45 degrees, initiate a reordering of the stacking direction [S1].
2.  **Reorder Stacking (if necessary):** If the stacking direction changes (e.g., from y-axis to x-axis), the logical-to-physical mapping must be updated. A tile in the new stacking order is rendered in a stripe-by-stripe fashion, consuming portions of tiles from the old stacking order. The number of tiles, their sizes, and their positions in physical memory may change during this process [S1].
3.  **Backward Lookup:** For each grid point in the logical 3D grid, compute the backward position $\mathbf{x}_b = \mathbf{x} - \mathbf{v}(\mathbf{x}_b, t) \Delta t$.
4.  **Read Access (Trilinear Interpolation):**
    *   Identify the two closest tiles along the current stacking axis (z-axis in the local tile coordinate system) that contain the backward position [S1].
    *   Perform bilinear interpolation within each of these two tiles to get values from the physical 2D texture. This uses built-in 2D texture interpolation [S1].
    *   Perform linear interpolation between the two bilinearly interpolated values to obtain the final property value. This linear interpolation is implemented within a fragment program [S1].
5.  **Write Access:**
    *   Write the interpolated value to the single texel corresponding to the current grid point in the physical 2D texture.
    *   Write access does not require interpolation and is restricted to grid points (single texels) [S1].
    *   The backward lookup fills logical memory slice-by-slice, which corresponds to filling physical memory tile-by-tile [S1].
6.  **Rendering:**
    *   Access tiles in front-to-back order by rendering object-aligned quadrilaterals.
    *   Texture coordinates address the tile in physical memory.
    *   Use dependent-texture lookup in a fragment program for post-classification, mapping density to optical properties (color and opacity) via transfer functions [S1].

**Pseudocode:**

```python
def advect_and_render(property_texture, vector_field, view_direction, threshold_angle=45.0):
    """
    Advects the property field and renders it using 2D texture-based advection with tile reordering.
    
    Args:
        property_texture: 2D texture storing the current property field rho.
        vector_field: 3D unsteady vector field v(x, t).
        view_direction: Current camera view direction vector.
        threshold_angle: Angle in degrees to trigger stacking direction change.
        
    Returns:
        Updated property_texture and rendered image.
    """
    # Determine current stacking axis (e.g., 'y')
    current_stacking_axis = get_current_stacking_axis()
    
    # Calculate angle between view direction and stacking axis
    angle = calculate_angle(view_direction, current_stacking_axis)
    
    # Step 1 & 2: Reorder if necessary
    if angle > threshold_angle:
        new_stacking_axis = choose_new_stacking_axis(current_stacking_axis, view_direction)
        reorder_stacking(property_texture, current_stacking_axis, new_stacking_axis)
        current_stacking_axis = new_stacking_axis
        
    # Step 3-5: Advection
    # Iterate over logical grid points
    for x in grid_x:
        for y in grid_y:
            for z in grid_z:
                # Backward lookup
                x_b, y_b, z_b = backward_lookup(x, y, z, vector_field, current_stacking_axis)
                
                # Identify two closest tiles along stacking axis
                tile1, tile2 = find_adjacent_tiles(x_b, y_b, z_b, current_stacking_axis)
                
                # Read Access: Trilinear Interpolation
                # Bilinear interpolation within each tile
                val1 = bilinear_interpolate(property_texture, tile1, x_b, y_b, z_b)
                val2 = bilinear_interpolate(property_texture, tile2, x_b, y_b, z_b)
                
                # Linear interpolation between tiles
                rho_new = linear_interpolate(val1, val2, z_b, current_stacking_axis)
                
                # Write Access
                write_to_texture(property_texture, x, y, z, rho_new)
                
    # Step 6: Rendering
    render_volume(property_texture, current_stacking_axis, view_direction)
```

**Edge Cases and Pitfalls:**
*   **Holes:** If the stacking direction is not changed when the viewing angle is large, holes may appear in the final display [S1].
*   **Interpolation Errors:** A one-texel border is required around each tile to avoid erroneous influence from neighboring tiles during bilinear interpolation [S1].
*   **Reordering Complexity:** The reordering process must account for changes in the number of tiles, their sizes, and their positions in physical memory [S1].

## Subtopics

### 2D IBFV (Image-Based Flow Visualization)
The foundational technique for injecting property values into the texture [S1].

### Volume Rendering with Texture Slicing
The visualization method used to map particle traces to a graphical representation, similar to 2D texture-based rendering with axis-aligned slices [S1].

## Operating characteristics
*   **Memory:** Uses a single copy of the property field on the GPU, avoiding multiple render passes per slice and multiple copies of volume data [S1].
*   **Performance:** Facilitates visualization of arbitrary vector fields without restriction to velocities with small z components [S1]. Supports independent transport of several materials and provides a more flexible blending scheme [S1].
*   **Limitations:** Requires dynamic reordering of the stacking direction, which adds complexity to the memory management [S1].

## Background
Originated in the paper "Real-Time Advection and Volumetric Illumination for the Visualization of 3D Unsteady Flow" by D. Weiskopf, T. Schafhitzel & T. Ertl [S1]. It builds on the idea of 2D IBFV and addresses limitations of 3D IBFV, such as holes in the display and the need for multiple render passes [S1].
