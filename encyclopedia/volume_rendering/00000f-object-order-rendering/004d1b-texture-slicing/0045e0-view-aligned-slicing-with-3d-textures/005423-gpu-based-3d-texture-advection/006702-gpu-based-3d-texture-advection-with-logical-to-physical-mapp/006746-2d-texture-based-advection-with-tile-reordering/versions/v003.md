# 2D Texture-Based Advection with Tile Reordering

Also called: 2D IBFV advection, Real-Time Advection

## Overview
A method for advecting particle traces in 3D unsteady flow using a single 2D texture on the GPU, avoiding the need for multiple copies of volume data or 3D textures by reordering the stacking direction dynamically [S1]. It sets itself apart from its parent [GPU-based 3D Texture Advection with Logical-to-Physical Mapping](19774-gpu-based-3d-texture-advection-with-logical-to-physical-mapp.md) by dynamically changing the stacking axis during advection to maintain visual quality, whereas the parent uses a fixed logical-to-physical mapping [S1]. It differs from its sibling [2D Texture-Based Advection with Volumetric Illumination](19825-2d-texture-based-advection-with-volumetric-illumination.md) by focusing specifically on the advection mechanism and memory layout rather than the illumination integration [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D unsteady vector field $\mathbf{v}(\mathbf{x}, t)$, a property field $\rho(\mathbf{x}, t)$ stored in a single 2D texture, and a current viewing direction [S1].
*   **Output:** The advected property field $\rho(\mathbf{x}, t + \Delta t)$ stored in the same 2D texture, ready for volume rendering [S1].

**Data Structures:**
*   **Physical Memory:** A single 2D texture of size $W \times H$ [S1].
*   **Logical Memory:** A 3D grid of size $N_x \times N_y \times N_z$ [S1].
*   **Tiling:** The logical 3D grid is mapped to the 2D texture in "tiles," where each tile corresponds to a 2D slice of the logical grid [S1]. The size of a tile is determined by the dimensions of the logical slice (e.g., $N_x \times N_z$ for a y-slice) [S1].
*   **Borders:** A one-texel-wide border is added around each tile in physical memory to prevent erroneous influence from neighboring tiles during bilinear interpolation [S1].

**Parameters:**
*   **Threshold Angle:** 45 degrees. The stacking direction is changed if the viewing angle exceeds this threshold relative to the stacking axis [S1].

**Steps:**

1.  **Determine Stacking Direction:** Calculate the angle between the current viewing direction and the current stacking axis. If the angle is greater than 45 degrees, initiate a reordering of the stacking direction [S1].
2.  **Reorder Stacking (if necessary):** If the stacking direction changes (e.g., from y-axis to x-axis), the logical-to-physical mapping must be updated [S1]. A tile in the new stacking order is rendered in a stripe-by-stripe fashion, consuming portions of tiles from the old stacking order [S1]. The number of tiles, their sizes, and their positions in physical memory may change during this process [S1].
3.  **Backward Lookup:** For each grid point in the logical 3D grid, compute the backward position $\mathbf{x}_b = \mathbf{x} - \mathbf{v}(\mathbf{x}_b, t) \Delta t$ [S1].
4.  **Read Access (Trilinear Interpolation):** Identify the two closest tiles along the current stacking axis (z-axis in the local tile coordinate system) that contain the backward position [S1]. Perform bilinear interpolation within each of these two tiles to get values from the physical 2D texture, which uses built-in 2D texture interpolation [S1]. Perform linear interpolation between the two bilinearly interpolated values to obtain the final property value, implemented within a fragment program [S1].
5.  **Write Access:** Write the interpolated value to the single texel corresponding to the current grid point in the physical 2D texture [S1]. Write access does not require interpolation and is restricted to grid points (single texels) [S1]. The backward lookup fills logical memory slice-by-slice, which corresponds to filling physical memory tile-by-tile [S1].
6.  **Rendering:** Access tiles in front-to-back order by rendering object-aligned quadrilaterals [S1]. Texture coordinates address the tile in physical memory [S1]. Use dependent-texture lookup in a fragment program for post-classification, mapping density to optical properties (color and opacity) via transfer functions [S1].

**Pseudocode:**

```python
import math

def advect(property_texture, vector_field, grid_dims, tile_size, stacking_axis, dt):
    Nx, Ny, Nz = grid_dims
    border = 1
    stride = tile_size + 2 * border

    # [G] Physical texture is a 2D array. Logical slices are packed as tiles.
    # Exact physical layout (row/column major) is implementation-defined [G].

    tiles_x = math.ceil(Nx / tile_size)
    tiles_y = math.ceil(Ny / tile_size)
    tiles_z = math.ceil(Nz / tile_size)

    # Fill logical memory slice-by-slice -> physical memory tile-by-tile
    for tz in range(tiles_z):
        for ty in range(tiles_y):
            for tx in range(tiles_x):
                # [G] Set viewport to tile subregion in physical texture
                # [G] Render quadrilateral covering the tile

                for local_x in range(tile_size):
                    for local_y in range(tile_size):
                        lx = tx * tile_size + local_x
                        ly = ty * tile_size + local_y
                        lz = tz * tile_size + local_y

                        # Backward lookup
                        vx, vy, vz = vector_field(lx, ly, lz)
                        xb, yb, zb = lx - vx * dt, ly - vy * dt, lz - vz * dt

                        # Two tiles along stacking axis (z) containing backward point
                        tile_z1 = int(math.floor(zb / tile_size))
                        tile_z2 = tile_z1 + 1
                        t_z = (zb % tile_size) / tile_size

                        # Bilinear interpolation within each tile (built-in 2D sampling)
                        # We compute it explicitly here for completeness
                        def bilinear(tex, tile_idx, coord, stride, border):
                            px = tile_idx * stride + coord + border
                            # Standard bilinear interpolation over 4 neighboring texels [G]
                            return tex[px][px] # Placeholder for actual interpolation math

                        # Linear interpolation between the two tiles (fragment program)
                        val1 = bilinear(property_texture, tile_z1, xb, stride, border)
                        val2 = bilinear(property_texture, tile_z2, xb, stride, border)
                        rho_new = val1 * (1.0 - t_z) + val2 * t_z

                        # Write access: restricted to single texel, no interpolation
                        px, py = map_to_physical(lx, ly, lz, stacking_axis, stride, border)
                        property_texture[py][px] = rho_new

    return property_texture
```

**Edge Cases and Pitfalls:**
*   **Holes:** If the stacking direction is not changed when the viewing angle is large, holes may appear in the final display [S1].
*   **Interpolation Errors:** A one-texel border is required around each tile to avoid erroneous influence from neighboring tiles during bilinear interpolation [S1].
*   **Reordering Complexity:** The reordering process must account for changes in the number of tiles, their sizes, and their positions in physical memory [S1].

## Subtopics

### 2D IBFV (Image-Based Flow Visualization)
Adopts the basic idea of 2D IBFV for injecting property values into the texture [S1].

### Volume Rendering with Texture Slicing
Maps particle traces to a graphical representation via volume rendering with texture slicing, similar to axis-aligned 2D texture slicing [S1].

## Operating characteristics
*   **Memory:** Uses a single copy of the property field on the GPU, avoiding multiple render passes per slice and multiple copies of volume data [S1].
*   **Performance:** Facilitates visualization of arbitrary vector fields without restriction to velocities with small z components [S1]. Supports independent transport of several materials and provides a more flexible blending scheme [S1].
*   **Limitations:** Requires dynamic reordering of the stacking direction, which adds complexity to the memory management [S1].

## Background
Originated in the paper "Real-Time Advection and Volumetric Illumination for the Visualization of 3D Unsteady Flow" by D. Weiskopf, T. Schafhitzel & T. Ertl [S1]. It builds on the idea of 2D IBFV and addresses limitations of 3D IBFV, such as holes in the display and the need for multiple render passes [S1].
