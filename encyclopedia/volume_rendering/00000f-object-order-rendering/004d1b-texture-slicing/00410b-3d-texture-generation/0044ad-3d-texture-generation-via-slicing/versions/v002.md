# 3D Texture Generation via Slicing

Also called: 3D Texture Slicing, Slice-based Volume Generation

## Overview
3D Texture Generation via Slicing is a method for constructing a 3D texture object from volumetric data by rendering 2D slices of the scene sequentially [S1, S2, unofficial]. It solves the problem of populating a 3D texture buffer for subsequent hardware-accelerated volume rendering by approximating the volume as a stack of 2D planes [S1, unofficial]. It is distinguished from its siblings by its explicit iteration over depth layers using standard 2D rendering pipelines, whereas [AR mapping to 3D texture](884-ar-mapping-to-3d-texture.md) maps arbitrary geometry directly, and [Post-packing Optimisation](11679-post-packing-optimisation.md) focuses on memory layout efficiency after generation [S1, S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A scalar field representing the volume, typically stored as a 2D texture or image data representing individual slices.
*   **Output:** A 3D texture object (e.g., `GL_TEXTURE_3D`) with dimensions $W \times H \times D$, where each texel stores RGBA values. In the basic implementation, the Red channel stores the scalar value, while Green, Blue, and Alpha are often unused or set to 1.0 [S2, unofficial].

**Data Structures:**
*   **3D Texture:** A GPU-resident texture object with internal format `R8` (8-bit unsigned integer per texel) or similar, depending on the precision of the source data [S2, unofficial].
*   **Render Target:** A 2D framebuffer object (FBO) bound to a 2D texture attachment, used to capture each slice [S2, unofficial].
*   **Pixel Buffer:** A temporary CPU-side array (e.g., `Uint8Array` of size $W \times H \times D$) to assemble the final texture data before upload [S2, unofficial].

**Steps:**
1.  **Initialize Storage:** Create a 3D texture object with dimensions $W \times H \times D$. Set texture parameters for linear interpolation (`GL_LINEAR`) to support hardware trilinear sampling during rendering [S1, S2, unofficial].
2.  **Loop Over Slices:** For each slice index $i$ from $0$ to $D-1$:
    a.  **Set Slice Parameter:** Update a shader uniform (e.g., `slice`) to select the current slice. The value is typically normalized: $s = i / D$ [S2, unofficial].
    b.  **Render Slice:** Render a quad or mesh representing the 2D slice to the 2D render target. The fragment shader outputs the scalar value for the current voxel into the Red channel [S2, unofficial].
    c.  **Read Pixels:** Read the rendered pixels from the framebuffer into a CPU-accessible buffer. Extract the Red channel values ($pixels[4 \cdot j]$ for pixel $j$) [S2, unofficial].
    d.  **Assemble Data:** Copy the extracted Red channel data into the corresponding slice offset in the 3D data array. The offset for slice $i$ is $i \times W \times H$ [S2, unofficial].
3.  **Upload Texture:** Upload the assembled 3D data array to the 3D texture object using `glTexImage3D` or `glTexSubImage3D` [S2, unofficial].

**Pseudocode:**
```python
def generate_3d_texture_via_slicing(width, height, depth, slice_data_source):
    """
    Generates a 3D texture by rendering 2D slices sequentially.
    slice_data_source: A callable or array providing scalar values for each slice.
    """
    # 1. Initialize CPU-side storage for the 3D volume
    # Format: R8 (single byte per voxel)
    volume_data = bytearray(width * height * depth)
    
    # 2. Create GPU 3D texture object
    tex_id = create_3d_texture(width, height, depth, internal_format='R8')
    
    # 3. Setup 2D render target (FBO + 2D Texture)
    fbo_id = create_fbo()
    render_tex_id = create_2d_texture(width, height, format='RGBA')
    bind_fbo_texture(fbo_id, render_tex_id)
    
    # 4. Loop over each slice
    for i in range(depth):
        # a. Set slice uniform for the rendering shader
        set_uniform_float("slice", i / depth)
        
        # b. Render the slice geometry to the 2D FBO
        # The fragment shader writes the scalar value to the Red channel
        render_slice_to_fbo(fbo_id)
        
        # c. Read pixels from the FBO
        # glReadPixels returns RGBA, so we only care about the Red channel (index 0)
        pixels = read_pixels_from_fbo(fbo_id, width, height, format='RGBA')
        
        # d. Extract Red channel and copy to volume data
        offset = i * width * height
        for y in range(height):
            for x in range(width):
                pixel_index = (y * width + x) * 4
                voxel_value = pixels[pixel_index] # Red channel
                volume_data[offset + y * width + x] = voxel_value

    # 5. Upload assembled data to the 3D texture
    upload_3d_texture(tex_id, volume_data, format='RED', type='UNSIGNED_BYTE')
    
    return tex_id
```

**Parameters:**
*   **Slice Uniform:** Normalized depth coordinate $[0, 1]$ passed to the fragment shader [S2, unofficial].
*   **Texture Format:** `R8` is sufficient for scalar fields if quantization is acceptable; `R32F` may be used for higher precision [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** Using `R8` limits the scalar range to 256 levels. For high-precision medical or scientific data, `R32F` is required, but this increases memory bandwidth and storage significantly [S2, unofficial].
*   **Boundary Conditions:** The slice index $i$ must be clamped to $[0, D-1]$ to avoid out-of-bounds rendering [S2, unofficial].
*   **Performance:** This method requires $D$ draw calls and $D$ CPU-GPU synchronization points (pixel reads), which can be a bottleneck for large volumes [S2, unofficial].

## Subtopics

### 3D Texture Generation via Vertex Shader Iteration
A technique to render to a specific slice of a 3D texture in a single draw call by iterating over texels of a source depth buffer in the vertex shader and projecting them into the 3D volume [S3, unofficial]. It avoids the performance penalty of multiple draw calls (one per slice) and redundant sampling of the depth texture for every slice [S3, unofficial].
*   **Steps:** Draw points equal to the depth buffer resolution. In the vertex shader, fetch the depth buffer value for the current point. Project the fetched depth value into the cube covered by the 3D texture to determine the Z-coordinate (slice). Set the target slice using the `gl_Layer` variable. In the fragment shader, perform calculations and write to the 3D texture slice [S3, unofficial].
*   **Parameters:** `gl_Layer` specifies the layer/slice index for rendering to a 3D texture [S3, unofficial].
*   **Pitfalls:** `gl_Layer` in the vertex shader is not part of the core OpenGL specification prior to version 4.2; it requires the `GL_AMD_vertex_shader_layer` extension or a geometry shader pass-through [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(D \cdot W \cdot H)$, where $D$ is depth, $W$ is width, and $H$ is height. The linear scan over all voxels is unavoidable, but the constant factor is high due to $D$ draw calls and CPU-GPU syncs [S2, unofficial].
*   **Memory Complexity:** $O(W \cdot H \cdot D)$ for the 3D texture storage plus $O(W \cdot H)$ for the temporary pixel buffer [S2, unofficial].
*   **Scaling:** Performance degrades linearly with volume depth $D$ due to the sequential nature of slice rendering [S2, unofficial].
*   **Strengths:** Simple to implement; leverages standard 2D rendering pipelines; compatible with any hardware that supports 3D textures [S1, unofficial].
*   **Limitations:** High CPU-GPU synchronization overhead; inefficient for very large volumes compared to GPU-only methods [S2, unofficial].
*   **When to use:** Small to medium volumes; prototyping; when GPU-only slice generation is not supported or too complex to implement [S1, unofficial].
*   **When not to use:** Large-scale volumetric datasets where performance is critical; when real-time generation is required [S2, unofficial].

## Background
The method is described as one of the simplest methods for volume visualization, relying on the approximation of volume data as slices [S1, unofficial]. It was implemented in early volumetric render engines using OpenGL, where 2D textures were rendered to populate 3D texture objects for subsequent ray-casting or slicing [S1, unofficial]. The approach predates more advanced GPU-based volume generation techniques and remains relevant for its simplicity and compatibility with legacy hardware [S1, S2, unofficial].
