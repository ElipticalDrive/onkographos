# AR mapping to 3D texture


## Overview
AR mapping to 3D texture is a volume visualization technique that maps scalar data and associated attributes (color and opacity) into a 3D texture using a linear coordinate system, thereby avoiding non-linear transformation formulas during rendering [S1, unofficial]. It solves the performance bottleneck of recalculating texture coordinates for every rotation of parallel polygons by defining coordinates once and storing the geometry in a display list [S1, unofficial]. It is distinguished from Wilson's depth integration by its reliance on linear estimation, which is noted to be less accurate but sufficient for effective visualization [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A set of parallel polygons representing the volume, and a 3D texture space [S1, unofficial].
- Output: A rendered image where color and opacity are composited using linear alpha blending [S1, unofficial].

**Data Structures:**
- **3D Texture:** A volumetric texture object storing color and opacity values mapped from the volume data [S1, unofficial].
- **Display List:** A precomputed group of OpenGL commands cached for execution, used to store the rotated polygon set [S1, unofficial].

**Steps:**
1. **Define Texture Coordinates:** Calculate the linear mapping from the 3D spatial coordinates of the volume to the 3D texture coordinates $(u, v, w)$ [S1, unofficial].
   - Let the volume bounds be $[x_{min}, x_{max}] \times [y_{min}, y_{max}] \times [z_{min}, z_{max}]$ [G].
   - For a point $P = (x, y, z)$, the texture coordinates are:
     $$ u = \frac{x - x_{min}}{x_{max} - x_{min}} $$
     $$ v = \frac{y - y_{min}}{y_{max} - y_{min}} $$
     $$ w = \frac{z - z_{min}}{z_{max} - z_{min}} $$
   - [G] Clamp $u, v, w$ to $[0, 1]$ to handle boundary cases.
2. **Populate Texture:** Fill the 3D texture with the scalar data converted to color and opacity values based on the transfer function [S1, unofficial].
3. **Rotate Polygons:** Apply the desired rotation to the parallel polygons [S1, unofficial]. Because the texture coordinates are defined in the local space of the linear mapping, they do not need to be recalculated for each rotation step [S1, unofficial].
4. **Render:** Use linear alpha blending to composite the fragments [S1, unofficial].

**Parameters:**
- Not given in the sources.

**Edge Cases and Pitfalls:**
- **Precision:** The linear estimation method is noted to be likely worse than Wilson's depth integration [S1, unofficial].
- **Performance:** Recalculating texture coordinates at each rotation is slow; this method avoids that cost [S1, unofficial].
- **Visual Quality:** Despite the estimation error, visualizations remain effective, especially given the context of the goals [S1, unofficial].

## Subtopics

### [Gradient-Isosurface Texture Packing](889-gradient-isosurface-texture-packing.md)
Gradient-Isosurface Texture Packing is a data layout strategy for 3D volume textures that stores pre-computed gradient vectors in the RGB components and the original scalar isovalue in the Alpha component. This allows a single texture to provide both the data for transfer function indexing and the normals for shading, avoiding the need for a second texture copy or expensive runtime gradient calculation. It differs from AR mapping to 3D texture by embedding shading data directly into the volume representation, and from Röttger et al. Rendering by relying on hardware interpolation of pre-computed gradients rather than software-based ray casting optimizations.

### [Röttger et al. Rendering](938-r-ttger-et-al-rendering.md)
Röttger et al. Rendering is a technique that mitigates the high computational cost of volume integration by approximating the rendering integral and moving the computation to a pre-process. It computes a 3D lookup table of colors and opacities parameterized by front scalar value, back scalar value, and distance, which is stored in a 3D texture for hardware-accelerated lookups during rendering. This method builds on AR mapping to 3D texture by using the 3D texture not just for static data storage, but to evaluate the volume composition operator directly via texture interpolation. It is distinguished from standard ray casting by replacing per-voxel integration with texture lookups, and from pure pre-classification by supporting arbitrary transfer functions including isosurface effects through the parameterization of the lookup table.

### Uniform Grid
A variant implementation detail where the underlying data structure is a uniform grid [S2, unofficial].
- **Step:** `set_values` accepts a $(X, Y, Z)$ float32 tensor to update scalar values [S2, unofficial].
- **Parameters:**
  - `aabb_min`: The minimum corner of the bounding box. Default is $[-1, -1, -1]$ [S2, unofficial].
  - `aabb_max`: The maximum corner of the bounding box. Default is $[1, 1, 1]$ [S2, unofficial].
  - `default_value`: Initial scalar value for all points. Default is float max [S2, unofficial].
- **Layout:**
  - `get_points` returns a $(X, Y, Z, 3)$ float32 tensor containing 3D coordinates of all grid points [S2, unofficial].
  - `get_values` returns a $(X, Y, Z)$ float32 tensor containing scalar values [S2, unofficial].

## Operating characteristics
- **Time Complexity:** Not given in the sources.
- **Memory Complexity:** Not given in the sources.
- **Strengths:** Avoids non-linear formulae; allows texture coordinates to be defined once; enables use of display lists for performance improvement [S1, unofficial].
- **Limitations:** The estimation method is likely worse than Wilson's depth integration [S1, unofficial].
- **When to use:** When rendering parallel polygons and performance is critical, and high precision is secondary to effective visualization [S1, unofficial].

## Background
The technique is described in Volume Visualisation Via Variable-Detail Non-Photorealistic Illustration [S1, unofficial]. It was introduced to improve rendering performance by leveraging OpenGL display lists and linear texture mapping to avoid per-rotation coordinate recalculation [S1, unofficial].
