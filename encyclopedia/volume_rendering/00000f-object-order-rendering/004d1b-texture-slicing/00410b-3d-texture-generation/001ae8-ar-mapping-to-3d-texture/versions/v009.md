# AR mapping to 3D texture
Also called: 3D texture mapping, texture-based volume rendering

## Overview
AR mapping to 3D texture is a high-performance object-order volume rendering technique that maps a volumetric dataset directly into a 3D texture object, allowing the graphics hardware to perform trilinear interpolation and compositing during rasterization [S2]. It solves the problem of slow per-voxel integration by offloading the rendering integral to the texture unit, achieving sub-second rendering times for moderately-sized datasets [S2]. It sets itself apart from [3D Texture Generation via Slicing](4891-3d-texture-generation-via-slicing.md) by avoiding explicit polygon generation and depth sorting, and from [Röttger et al. Rendering](938-r-ttger-et-al-rendering.md) by storing raw scalar data rather than pre-integrated color-opacity tuples, relying on hardware blending rather than a 3D lookup table [S1, unofficial][S2].

## How it works
**Inputs and Outputs:**
- Input: A 3D scalar field (volume data) of dimensions $D_x \times D_y \times D_z$.
- Input: A transfer function mapping scalar values to color $(R, G, B)$ and opacity $\alpha$.
- Input: Camera parameters (view matrix, projection matrix).
- Output: A 2D raster image.

**Data Structures:**
1.  **3D Texture:** A hardware texture object of type `GL_TEXTURE_3D` (or equivalent).
    -   Dimensions: $D_x \times D_y \times D_z$.
    -   Internal Format: Typically `GL_RGBA` or `GL_RGBA8` to store pre-classified color and opacity. If storing raw scalars, `GL_R8` or `GL_R32F` is used, but compositing requires additional shader logic. The sources imply storing color/opacity to avoid non-linear formulae in the shader [S1, unofficial].
    -   Filtering: `GL_LINEAR` (trilinear interpolation) for smoothness; `GL_NEAREST` for bit accuracy.
    -   Wrapping: `GL_CLAMP_TO_EDGE` to handle boundary conditions.

**Steps:**
1.  **Texture Population:**
    -   Iterate through all voxels $(i, j, k)$ in the input volume.
    -   For each voxel, apply the transfer function $TF(v)$ to the scalar value $v$ to obtain color $C$ and opacity $\alpha$.
    -   Write $(C, \alpha)$ to the 3D texture at coordinate $(i, j, k)$.
    -   *Note:* If the source data is not already classified, this step is part of the "generation" phase. If raw data is stored, the transfer function is applied in the fragment shader. The sources suggest placing color and opacity into the texture to avoid non-linear formulae [S1, unofficial].

2.  **Geometry Setup:**
    -   Define a set of parallel polygons (typically quads) that cover the volume.
    -   The polygons are oriented perpendicular to the view direction.
    -   Define texture coordinates $(u, v, w)$ for the vertices of these polygons. The mapping is linear:
        $$ u = \frac{x}{D_x}, \quad v = \frac{y}{D_y}, \quad w = \frac{z}{D_z} $$
    -   The texture coordinates are defined once for the parallel polygons [S1, unofficial].

3.  **Rotation and Coordinate Recalculation:**
    -   When the view direction changes, the set of parallel polygons is rotated to remain perpendicular to the new view vector.
    -   Unlike methods that require recalculating texture coordinates for every rotation (which is slow), AR mapping uses the linear mapping. The texture coordinates do not change relative to the texture space; only the geometry's position in world space changes [S1, unofficial].
    -   The polygons are legally rotated to align with the new view.

4.  **Rendering:**
    -   Place the set of polygons in a display list (a precomputed cache of OpenGL commands) to improve performance when redrawing the same geometry multiple times [S1, unofficial].
    -   Enable alpha blending: `glEnable(GL_BLEND)`, `glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA)`.
    -   Rasterize the polygons. The hardware performs trilinear interpolation of the 3D texture values at the fragment positions.
    -   The fragment shader (or fixed-function pipeline) composites the interpolated color and opacity using linear alpha blending.

**Parameters:**
-   **Framebuffer Resolution:** A color/RGBA resolution of at least 16 bits is desirable for good quality [S2].
-   **Interpolation:** Trilinear interpolation is used by default. Nearest-neighbor can be used for bit accuracy but reduces quality [S2].

**Edge Cases and Pitfalls:**
-   **Precision:** The quality is limited by the lack of bit accuracy inherent in floating-point interpolation and blending [S2].
-   **Off-Axis Views:** Image quality degrades at off-axis views due to the distortion of the footprint mapping [S2].
-   **Rotation Cost:** Recalculating texture coordinates at each rotation is slow; using a linear mapping and display lists mitigates this [S1, unofficial].
-   **Estimation Error:** The estimation method (linear mapping with hardware blending) is likely worse than Wilson's depth integration, but visualizations remain effective [S1, unofficial].

**Pseudocode:**
```python
def render_ar_mapping(volume_data, transfer_function, view_matrix, projection_matrix):
    # 1. Populate 3D Texture
    # volume_data: D_x x D_y x D_z array of scalars
    # texture_3d: GL_TEXTURE_3D object
    for x in range(D_x):
        for y in range(D_y):
            for z in range(D_z):
                scalar = volume_data[x, y, z]
                color, alpha = transfer_function(scalar)
                texture_3d.set_texels(x, y, z, color, alpha)
    
    # 2. Setup Geometry (Parallel Polygons)
    # Define quads perpendicular to the view direction
    # Texture coordinates are linear and defined once
    polygons = create_parallel_polygons(view_matrix, D_x, D_y, D_z)
    
    # 3. Create Display List for Performance
    display_list = create_display_list(polygons)
    
    # 4. Render
    gl_enable(GL_BLEND)
    gl_blend_func(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA)
    
    # Rotate polygons to match new view direction
    # Texture coordinates remain unchanged due to linear mapping
    rotate_polygons_to_view(polygons, view_matrix)
    
    # Execute display list
    execute_display_list(display_list)
    
    gl_disable(GL_BLEND)
```

## Subtopics

### [Gradient-Isosurface Texture Packing](889-gradient-isosurface-texture-packing.md)
Gradient-Isosurface Texture Packing is a data layout strategy for 3D volume textures that stores surface gradients in the RGB components and the original scalar isovalue in the Alpha component. This allows a single texture to serve as both the data source for shading (via interpolated normals) and the classification source (via the isovalue), eliminating the need for a second texture copy or runtime gradient calculation. It sets itself apart from [AR mapping to 3D texture](884-ar-mapping-to-3d-texture.md) by embedding geometric shading information directly into the texture coordinates, and from [Uniform Grid](920-uniform-grid.md) by enabling hardware-accelerated normal interpolation during ray casting.

### [Uniform Grid](920-uniform-grid.md)
A uniform grid is a structured mesh where vertices are spaced uniformly along each axis, with geometry and connectivity defined implicitly by bounding box limits and vertex counts. It serves as the foundational data structure for storing scalar fields in volume rendering, enabling efficient spatial indexing and interpolation. Unlike unstructured meshes, it eliminates the need to store explicit connectivity or vertex positions, trading flexibility for computational simplicity and memory efficiency.

### [Röttger et al. Rendering](938-r-ttger-et-al-rendering.md)
Röttger et al. Rendering is a technique that mitigates the high computational cost of volume integration by approximating the rendering integral and moving the computation to a pre-process. It computes a 3D lookup table of colors and opacities parameterized by front scalar value, back scalar value, and distance, which is stored in a 3D texture for hardware-accelerated lookups during rendering. This method builds on [AR mapping to 3D texture](884-ar-mapping-to-3d-texture.md) by using the 3D texture not just for static data storage, but to evaluate the volume composition operator directly via texture interpolation. It is distinguished from standard ray casting by replacing per-voxel integration with texture lookups, and from pure pre-classification by supporting arbitrary transfer functions including isosurface effects through the parameterization of the lookup table.

## Operating characteristics
- **Time Complexity:** Rendering time is largely independent of the volume size, depending instead on the screen resolution and the number of polygons (which is constant for a given view) [S2]. The cost is dominated by trilinear interpolation and blending per fragment.
- **Memory Complexity:** $O(D_x \times D_y \times D_z)$ to store the 3D texture.
- **Measured Performance:** Sub-second rendering times for moderately-sized datasets [S2].
- **Scaling:** Performance degrades at high magnifications due to increased interpolation costs, but frame rates remain high if view frustum culling is applied [S2].
- **Strengths:** High performance, simple implementation, hardware-accelerated.
- **Limitations:** Limited quality due to lack of bit accuracy, degradation of image quality at off-axis views, and inability to handle complex transfer functions that require non-linear compositing without shader support [S2].
- **When to Use:** When high frame rates are required for moderately-sized datasets and high visual fidelity is not critical.
- **When Not to Use:** When bit-accurate rendering is required, or when dealing with very large datasets that exceed texture memory limits.

## Background
AR mapping to 3D texture is a technique that emerged in the late 1990s and early 2000s as 3D texture hardware became available in graphics cards. It was popularized as a fast alternative to ray casting and splatting for real-time volume visualization. The method is described in the context of the "SIV" (Scalar Image Visualization) system and practical evaluations of volume rendering algorithms [S1, unofficial][S2].
