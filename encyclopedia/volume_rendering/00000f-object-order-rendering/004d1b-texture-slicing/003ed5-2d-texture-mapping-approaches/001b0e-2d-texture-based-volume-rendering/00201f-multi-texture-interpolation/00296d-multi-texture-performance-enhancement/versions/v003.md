# Multi-Texture Performance Enhancement
## Overview
Multi-Texture Performance Enhancement is a technique to reduce the number of triangles by mapping textures of multiple slice images onto a single polygon using $n$ independent multi-texture units [S1]. It achieves this by combining $n$ texture images by multi-texturing hardware in one clock cycle and blending the resulting fragment into the frame buffer, theoretically reducing rendering time and frame buffer reads for back-to-front alpha blending by a factor of $1/n$ [S1]. It builds on [Multi-Texture Interpolation](2200-multi-texture-interpolation.md) and differs from [Multi-Texture Pipeline Rendering](4945-multi-texture-pipeline-rendering.md) by focusing on simultaneous combination on a single geometry rather than pipelined stages [G].

## How it works
**Inputs and Outputs:**
*   **Input:** $n$ texture images representing consecutive volume slices (where $n$ is the number of available independent multi-texture units); camera position $\tilde{c}$; slice spacing $d$; base polygon width $w$ and height $h$ [S1].
*   **Output:** A single rendered polygon with fragments containing the combined color and alpha of $n$ slices, blended into the frame buffer [S1].

**Data Structures:**
*   **Polygon:** A single quad with modified dimensions to accommodate perspective displacement.
    *   Width: $W = w + 2 \cdot d \cdot (n-1)$
    *   Height: $H = h + 2 \cdot d \cdot (n-1)$ [S1].
*   **Textures:** $n$ textures, each containing one slice image.
    *   Border: Initialized to zero values to handle out-of-bounds coordinates [S1].
*   **Texture Coordinates:** 2D coordinates $(s, t)$ for each texture unit, calculated per vertex [S1].

**Steps:**
1.  **Polygon Scaling:** Increase the width $w$ and height $h$ of the slice polygon by $2 \cdot d \cdot (n-1)$ to create a bounding area that covers the maximum possible perspective displacement of the $n$ slices [S1].
2.  **Texture Coordinate Calculation:** For each texture unit $k$ (representing slice $i+k$), calculate the texture coordinates for the four vertices of the polygon [S1].
    *   Identify the corner $\tilde{b}$ of the slice image that corresponds to the polygon vertex [S1].
    *   Calculate the view vector $\tilde{v} = (v_x, v_y, v_z)^T = \tilde{c} - \tilde{b}$, where $\tilde{c}$ is the camera position [S1].
    *   Calculate the projected width $w'$ and height $h'$ of the slice at the polygon's depth [S1].
    *   Compute the displacement in $s$ and $t$ directions:
        $$ \Delta s = d \frac{v_x}{v_z} $$
        $$ \Delta t = d \frac{v_y}{v_z} $$ [S1].
    *   The texture coordinates $(s, t)$ at the vertex are given by:
        $$ s = \frac{w'}{w} \left( 1 + \frac{h'}{d} + \frac{h' v_y}{d v_z} \right) $$
        $$ t = \frac{h'}{h} \left( 1 + \frac{w'}{d} + \frac{w' v_x}{d v_z} \right) $$ [S1].
3.  **Hardware Combination:** Configure the multi-texture hardware combiners to combine the $n$ textures in a single clock cycle [S1].
4.  **Rendering:** Draw the single polygon. The hardware samples the $n$ textures, combines them, and blends the resulting fragment into the frame buffer [S1].
5.  **Edge Handling:** Ensure that texture coordinates outside the range $[0, 1]$ result in zero texel values. Since hardware-specific extensions like `SGIS_texture_edge_clamp` may not be supported (e.g., on GeForce 256), use standard OpenGL clamping and initialize the texture borders with zero values [S1].

**Pseudocode:**
```python
def render_multi_texture_slices(camera_pos, d, w, h, n, textures):
    """
    Renders n slices onto a single polygon using multi-texturing.
    
    Args:
        camera_pos: (cx, cy, cz) tuple, camera position in world space.
        d: float, slice spacing.
        w: float, original width of a slice polygon.
        h: float, original height of a slice polygon.
        n: int, number of slices to combine.
        textures: list of n texture objects, each containing slice data and border.
    
    Returns:
        list of lists of (s, t) tuples, one list per texture unit.
    """
    # Step 1: Scale polygon dimensions
    polygon_width = w + 2 * d * (n - 1)
    polygon_height = h + 2 * d * (n - 1)
    
    # Define the four vertices of the scaled polygon in world space
    vertices_world = [
        (-polygon_width/2, -polygon_height/2, 0),
        (polygon_width/2, -polygon_height/2, 0),
        (polygon_width/2, polygon_height/2, 0),
        (-polygon_width/2, polygon_height/2, 0)
    ]
    
    # Step 2: Calculate texture coordinates for each texture unit
    texture_coords = [] 
    
    for k in range(n):
        coords_for_texture = []
        for vertex in vertices_world:
            # Identify the corner b of the slice image corresponding to the vertex
            z_slice = k * d
            b = (vertex[0], vertex[1], z_slice)
            
            # Calculate view vector v = camera_pos - b
            v = (camera_pos[0] - b[0], camera_pos[1] - b[1], camera_pos[2] - b[2])
            vx, vy, vz = v
            
            # Calculate projected width w' and height h' of the slice at the polygon's depth
            # (Computed via perspective projection; base dimensions used here as reference)
            w_prime = w
            h_prime = h
            
            # Compute texture coordinates
            s = (w_prime / w) * (1 + h_prime / d + h_prime * vy / (d * vz))
            t = (h_prime / h) * (1 + w_prime / d + w_prime * vx / (d * vz))
            
            coords_for_texture.append((s, t))
        texture_coords.append(coords_for_texture)
    
    # Step 3: Configure multi-texture hardware combiners to combine n textures in one clock cycle
    # Step 4: Render the single polygon with the calculated texture coordinates
    # Step 5: Ensure texture borders are zero-initialized and use standard OpenGL clamping for coordinates outside [0, 1]
    return texture_coords
```

**Parameters:**
*   $n$: Number of multi-texture units. Not given in the sources.
*   $d$: Slice spacing. Not given in the sources.
*   $w, h$: Base polygon dimensions. Not given in the sources.

**Edge Cases and Pitfalls:**
*   **Texture Coordinates > 1:** Perspective displacement can cause texture coordinates to exceed $[0, 1]$ [S1].
*   **Clamping:** Hardware-specific extensions like `SGIS_texture_edge_clamp` may not be supported (e.g., on GeForce 256) [S1].
*   **Perspective Displacement:** If not compensated, slices will appear shifted [S1].

## Subtopics

### [Multi-Texture Correct Blending](4767-multi-texture-correct-blending.md)
Uses register combiners to combine $n$ texture images on a single polygon such that the resulting fragment blends into the frame buffer with the exact same result as rendering $n$ separate polygons with single textures. It solves the problem of incorrect alpha blending when multiple volume slices are rendered simultaneously on a single geometry, ensuring mathematical equivalence to the standard back-to-front polygon rendering order. It sets itself apart from standard multi-texturing by explicitly computing the composite alpha term $(1 - A_{t0})(1 - A_{t1})$ to preserve the correct transparency accumulation, whereas standard multi-texturing often fails to account for the multiplicative nature of alpha subtraction in sequential blending. Choose this when correct alpha blending is required for transparency.

## Operating characteristics
*   **Time Complexity:** Theoretically reduces rendering time by a factor of $1/n$ compared to rendering $n$ separate polygons, assuming the combination of $n$ texture images can be computed in one clock cycle [S1].
*   **Memory Complexity:** Reduces frame buffer reads for back-to-front alpha blending by a factor of $1/n$ [S1].
*   **Performance:** The actual speedup depends on the hardware's ability to combine $n$ textures in one clock cycle. Not given in the sources.
*   **Strengths:** Significant reduction in draw calls and frame buffer accesses [S1].
*   **Limitations:** Requires $n$ independent multi-texture units. Compensating for perspective displacement requires polygon scaling and coordinate adaptation [S1]. Clamping limitations exist on some hardware [S1].
*   **When to Use:** When $n$ multi-texture units are available and performance is critical [G].
*   **When Not to Use:** When correct alpha blending is required and the hardware does not support the necessary combiner setup (use [Multi-Texture Correct Blending](4767-multi-texture-correct-blending.md) instead) [G].

## Background
This technique was described in the context of interactive volume rendering on standard PC graphics hardware, specifically addressing the limitations of early 2D texture-based rendering methods [S1]. It was developed to leverage the multi-texturing capabilities of graphics hardware (such as the GeForce 256) to improve performance [S1].
