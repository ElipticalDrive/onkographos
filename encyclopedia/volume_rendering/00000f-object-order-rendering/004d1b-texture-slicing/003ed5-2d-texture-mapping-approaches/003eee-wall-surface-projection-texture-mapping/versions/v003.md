# Wall Surface Projection & Texture Mapping

Also called: Axis-aligned Texture Projection, Planar Mapping, renderBlockSurfaces

## Overview
Wall Surface Projection & Texture Mapping is a method for rendering 3D voxel blocks by projecting their visible axis-aligned faces directly onto the 2D screen plane, handling perspective-correct UV mapping and clipping. It differs from ray-casting approaches by operating on discrete geometric primitives (faces) rather than volumetric samples, and from general texture slicing by treating each visible block face as an independent planar quad to be rasterized. This approach is particularly suited for block-based environments where faces are axis-aligned and shading is per-face rather than per-voxel.

## How it works
**Inputs:**
- A 3D voxel grid (chunk) where each block has a state (active/inactive) and a texture index.
- Camera position and orientation (player position `x, y, z` and angles `angle, lookAngle`).
- Screen dimensions (`SCR_WIDTH`, `SCR_HEIGHT`).
- Texture data: a 1D array `textureMap` of RGB values, with dimensions `width` and `height`.

**Outputs:**
- A 2D screen buffer with pixels drawn according to the projected textures.

**Data Structures:**
- `Block`: Contains `visibleFaces` (boolean flags for 6 faces: XPos, XNeg, YPos, YNeg, ZPos, ZNeg) and `textureIndex`.
- `Texture`: Contains `width`, `height`, and `textureMap` (array of size `width * height * 3`).
- `Chunk`: A 3D array of `Block` objects of size `CHUNK_SIZE x CHUNK_SIZE x CHUNK_SIZE`.

**Steps:**

1.  **Visibility Determination:** For each block in the chunk, determine which faces are visible. A face is visible if the adjacent block in that direction is inactive or out of bounds. This is done by checking neighbors for each of the 6 faces.
2.  **Face Projection:** For each visible face, project its 3D corners to 2D screen coordinates. The specific projection logic depends on the face orientation (e.g., XPos, YPos). The source code implies a simplified projection where the face is treated as a quad in screen space.
3.  **Clipping:** Clip the projected face edges to the screen boundaries. If an edge is behind the player (y < 1 in the source's coordinate system), it is clipped using linear interpolation to find the intersection point with the near plane (y=1).
4.  **UV Mapping Calculation:** Calculate the UV coordinates for the corners of the projected quad.
    -   Compute horizontal step: `horizontalStep = (texture.width * uvU) / (xPos2 - xPos1)`.
    -   Clamp `xPos1` and `xPos2` to `[0, SCR_WIDTH]`. Adjust `horizontalStart` accordingly.
    -   Compute distance: `distX = max(1, xPos2 - xPos1)`. This prevents division by zero.
    -   For each x in the clipped range, compute the y-coordinates of the top and bottom edges:
        -   `y1 = bottomPos1 + distBottom * (x - originalX1 + 0.5) / distX`
        -   `y2 = topPos1 + distTop * (x - originalX1 + 0.5) / distX`
    -   Compute vertical step: `verticalStep = (texture.height * uvV) / (y2 - y1)`.
    -   Clamp `y1` and `y2` to `[0, SCR_HEIGHT]`. Adjust `verticalStart` accordingly.
5.  **Rasterization:** For each x in the horizontal range:
    -   For each y from `y1` to `y2`:
        -   Calculate the texture index `p` using modulo wrapping:
            `p = ((texture.height - (verticalStart % texture.height) - 1) * 3 * texture.width + (horizontalStart % texture.width) * 3)`
        -   Retrieve RGB values from `textureMap[p]`, `textureMap[p+1]`, `textureMap[p+2]`.
        -   Apply shading: `r = max(textureMap[p] - shade/2, 0)`. (Note: The source code only applies shading to the red channel, which may be a simplification or bug. In a general implementation, shading should apply to all channels or be a multiplier).
        -   Draw the pixel: `drawPixel(x, y, RgbColor{r, g, b}, distanceToPlayer)`.
        -   Increment `verticalStart` by `verticalStep`.
    -   Increment `horizontalStart` by `horizontalStep`.

**Parameters:**
- `CHUNK_SIZE`: Size of the voxel chunk. Not given in the sources.
- `shade`: Shading intensity. Not given in the sources.
- `uvU`, `uvV`: UV scaling factors. Not given in the sources.

**Edge Cases and Pitfalls:**
- **Division by Zero:** If `xPos2 - xPos1` is 0, `distX` is forced to 1 to prevent division by zero [S1, unofficial].
- **Clipping:** Faces behind the player must be clipped to avoid rendering artifacts. The source uses a simple y < 1 check [S1, unofficial].
- **Shading:** The source code only applies shading to the red channel. This is likely a simplification or bug. In a general implementation, shading should be applied to all channels or as a multiplier [S1, unofficial].

## Operating characteristics
- **Time Complexity:** O(N) where N is the number of visible faces. Each face is processed in time proportional to its screen area.
- **Memory Complexity:** O(V) where V is the number of voxels in the chunk, for storing the voxel grid. Texture memory is O(T) where T is the total size of all textures.
- **Strengths:** Simple to implement for block-based environments. Efficient for scenes with large flat surfaces.
- **Limitations:** Limited to axis-aligned faces. Does not handle curved surfaces or non-axis-aligned geometry well. Shading is per-face, not per-voxel, which may look blocky.
- **When to Use:** Block-based games or voxel editors where performance is critical and geometry is simple.
- **When Not to Use:** Scenes with complex geometry, curved surfaces, or high-fidelity shading requirements.

## Background
This method is derived from early 3D rendering techniques used in voxel-based games, such as those inspired by the 1993 era of PC gaming. The specific implementation details come from an unofficial GitHub repository [S1, unofficial]. It represents a simplified approach to texture mapping in 3D space, focusing on axis-aligned planes.
