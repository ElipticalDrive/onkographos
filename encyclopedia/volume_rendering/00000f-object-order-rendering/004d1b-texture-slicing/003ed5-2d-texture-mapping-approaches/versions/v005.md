# 2D Texture Mapping Approaches

Also called: 2D Texture Mapping, TMRenderAction, Texture Mapping Render Action

## Overview
2D Texture Mapping Approaches are object-order volume rendering techniques that decompose a 3D scalar field into a stack of 2D slices, rasterize them as textured polygons, and composite them into the frame buffer using hardware alpha blending [S1, book][S2]. Unlike view-aligned slicing methods that regenerate geometry per frame to align with the camera, this approach uses object-aligned slices (along X, Y, or Z axes), trading visual accuracy for hardware compatibility and rendering speed on systems lacking native 3D texture support [S1, book][S2]. It solves the problem of rendering 3D scalar fields on graphics hardware that lacks native 3D texture support or requires compatibility with older OpenGL implementations by substituting trilinear interpolation with bilinear interpolation within 2D textures [S1, book].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D scalar field (volume data), typically stored as a `vtkImageData` dataset or equivalent texture memory [S1, book]. A transfer function maps scalar values to color and opacity [S1, book].
*   **Output:** A 2D image (frame buffer) representing the volume from the current viewpoint [S1, book].

**Data Structures:**
*   **Texture Map:** A 2D array of texels where each texel contains 1 to 4 components: Intensity (1), RGB (3), or RGBA (4) [S1, book].
*   **Texture Coordinates:** 2D parameters $(u, v)$ associated with each vertex of the proxy geometry [S1, book].
*   **Render Action Instance:** An object (e.g., `vzTMRenderAction`) that maintains a list of managed shapes and handles the rendering pipeline state [S2].

**Steps:**
1.  **Initialization:** Create the render action instance with a thread count parameter (typical value: 1) [S2]. Manage the shape node containing the volume geometry to ensure textures are resident in graphics memory [S2].
2.  **Geometry Generation:** Generate proxy geometry (quads or triangles) representing the intersection of slicing planes with the volume bounding box [S1, book][S3, unofficial].
3.  **Texture Coordinate Assignment:** Associate texture coordinates $(u, v)$ with each vertex of the proxy geometry so that they map the vertex position into the 2D texture map [S1, book].
4.  **Rasterization:** Begin drawing by calling the render action's draw method with appropriate flags (e.g., `VZ_RESTORE_GL_STATE_BIT`) [S2]. The graphics hardware linearly interpolates texture coordinates across the polygon fragments [S1, book].
5.  **Sampling:** Use the interpolated texture coordinates to index into the 2D texture map and retrieve the resulting texel value (color/intensity/alpha) [S1, book].
6.  **Compositing:** Apply the texel value to the pixel using hardware-supported alpha blending. The standard blending equation is:
    $$ C_{dest} = C_{src} \cdot A_{src} + C_{dest} \cdot (1 - A_{src}) $$
    where $C_{src}$ and $A_{src}$ are the color and opacity from the texture sample, and $C_{dest}$ is the current frame buffer color [G]. Slices must be processed in correct depth order (back-to-front) to ensure correct transparency [S1, book][S3, unofficial][S4, book].
7.  **Completion:** End the drawing sequence [S2].

**Pseudocode:**
```python
# Constants and helper definitions
VZ_RESTORE_GL_STATE_BIT = 0x00000001

class RenderAction:
    def __init__(self, thread_count: int):
        self.managed_shapes = []
        self.thread_count = thread_count
    def manage(self, shape_node):
        self.managed_shapes.append(shape_node)
    def unmanage(self, shape_node):
        if shape_node in self.managed_shapes:
            self.managed_shapes.remove(shape_node)
    def begin_draw(self, flags: int):
        pass
    def draw(self, shape_node):
        pass
    def end_draw(self):
        pass

class ShapeNode:
    def __init__(self, geometry, appearance):
        self.geometry = geometry
        self.appearance = appearance

def initialize_render_action(thread_count: int = 1):
    return RenderAction(thread_count=thread_count)

def create_shape_node(geometry, appearance):
    return ShapeNode(geometry=geometry, appearance=appearance)

def render_volume(render_action, shape_node):
    render_action.begin_draw(flags=VZ_RESTORE_GL_STATE_BIT)
    render_action.draw(shape_node)
    render_action.end_draw()

def cleanup(render_action, shape_node):
    render_action.unmanage(shape_node)
    del render_action
    del shape_node
```

**Parameters:**
*   **Thread Count:** Integer specifying the number of threads the render action can create. Typical value: 1 [S2].
*   **Texture Components:** 1 (Intensity), 3 (RGB), or 4 (RGBA) [S1, book].

**Edge Cases and Pitfalls:**
*   **Power of Two:** Many rendering systems require image dimensions to be exact powers of two. Non-power-of-two textures are automatically converted to power-of-two by some libraries (e.g., VTK) at the expense of extra computation [S1, book].
*   **Alpha Support:** Some renderers only support 2D textures or lack alpha texture support [S1, book].
*   **Precision:** Gross errors in output images may occur if graphics hardware stores insufficient bits per component for texture and frame buffer [S1, book].

## Subtopics

### [2D Texture-Based Volume Rendering](916-2d-texture-based-volume-rendering.md)
A hybrid object-order technique that renders volumetric data by decomposing the volume into a stack of 2D texture slices aligned with the object's coordinate axes, projecting them onto the image plane, and compositing them back-to-front using hardware alpha blending. It solves the problem of rendering 3D scalar fields on graphics hardware that lacks native 3D texture support or requires compatibility with older OpenGL implementations by substituting trilinear interpolation with bilinear interpolation within 2D textures. Unlike [3D Texture-Based Volume Rendering](9841-3d-texture-based-volume-rendering.md), which stores the entire volume in a single 3D texture and allows for view-aligned slicing with trilinear interpolation, this method requires pre-computing three separate stacks of 2D textures (one for each major axis) and selecting the stack most perpendicular to the viewing direction to minimize gaps. It differs from [Shear-Warp Rendering](9840-shear-warp-rendering.md) by avoiding the explicit matrix decomposition (shear and warp) and instead relying on the graphics pipeline's automatic transformation of object-aligned quads, though both share the back-to-front compositing strategy.

### [Palette Texture Volume Rendering](6502-palette-texture-volume-rendering.md)
An acceleration technique for 2D slicing volume visualization on mobile devices, designed to overcome the limited memory and processing power of low-end hardware. It solves the problem of slow interactive rendering by combining adaptive screen-resolution rendering, compressed palette textures, and basic graphics hardware functionality such as rasterization and 2D texture mapping. Unlike standard volume rendering methods that apply transfer functions explicitly on the CPU or use high-resolution full-screen rendering, this approach maps an 8-bit indexed image to RGBA values via a palette, effectively embedding the transfer function into the texture format itself. It sets itself apart from its siblings by prioritizing memory efficiency and fast texture updates through compression, accepting lower visual fidelity (blurred boundaries) in exchange for interactivity on devices like PDAs.

### [Cabral Texture Mapping](7257-cabral-texture-mapping.md)
Implements the filtered back projection (FBP) algorithm for Computed Tomography (CT) reconstruction using 2D texture mapping hardware and an accumulation buffer. It differs from standard ray-casting volume rendering by treating the reconstruction as a back-projection of slice data into a frame buffer, leveraging graphics hardware for interpolation and blending. Unlike [2D Texture-Based Volume Rendering](916-2d-texture-based-volume-rendering.md) which focuses on direct visualization, this method is specifically designed for reconstructing volumetric data from projection data, though it shares the underlying texture-mapping primitives.

### [Wall Surface Projection & Texture Mapping](9883-wall-surface-projection-texture-mapping.md)
Renders 3D voxel blocks by projecting their visible axis-aligned faces directly onto the 2D screen plane, handling perspective-correct UV mapping and clipping. It differs from ray-casting approaches by operating on discrete geometric primitives (faces) rather than volumetric samples, and from general texture slicing by treating each visible block face as an independent planar quad to be rasterized. This approach is particularly suited for block-based environments where faces are axis-aligned and shading is per-face rather than per-voxel.

### [Multi-constraints-based projective texture mapping](12075-multi-constraints-based-projective-texture-mapping.md)
Places textures on iso-surfaces of volume datasets by projecting the surface onto a 2D intermediate template using a plenoptic surface, warping a texture image to align with user-defined key points, and rendering via ray-casting. It solves the problem of ill-conditioned direct projection of 2D textures to 3D voxels by using spatial and semantic constraints (transfer functions) to control texture position. Unlike traditional mesh-based texture mapping, it does not require filling topological holes; regions with artefacts receive the same texture as their radial neighborhood. It differs from [2D Texture-Based Volume Rendering](916-2d-texture-based-volume-rendering.md) by synthesizing/warping detail to match local data and surface geometry using key points, rather than reconstructing existing detail.

### [Projective Space Texture Mapping with Multi-Resolution Templates](13236-projective-space-texture-mapping-with-multi-resolution-templ.md)
Assigns solid textures to any position within a volume object using plenoptic projection functions as pseudo-procedure functional models. It solves the problem of intermixing volumetric rendering with solid texturing without requiring explicit $uv$-parameterization of the volume geometry. Unlike sibling methods that rely on fixed geometric parameterizations, this approach connects 3D positions in the volume to 2D projective positions on a plenoptic surface, and then to integral coordinates in a morphed texture image. It is distinguished by its use of multi-resolution intermediate templates generated via forward projection (DVR/DSR) and inverse projection (projective texture mapping) to mitigate aliasing artifacts known as the "cliff effect".

### [Bilinear Texture Sampling](17394-bilinear-texture-sampling.md)
Retrieves texture values from a 2D texture map at local coordinates $(u, v)$ on a primitive plane using bilinear interpolation combined with border clamping to handle out-of-bounds coordinates. It solves the problem of dark edge artifacts and poor coverage found in bounded sampling approaches that use zero-padding for out-of-bounds areas. It differs from bounded strategies like BBSplat, where color decays from the Gaussian center, by allowing texture information to extend beyond the primitive boundary for smoother transitions.

### [TileTrees](17466-tiletrees.md)
Stores square texture tiles in the leaves of an octree surrounding the surface. At rendering time, the surface is projected onto the tiles, and color is retrieved by a 2D texture fetch into a tile map. This method avoids global planar parameterizations, supports implicit surfaces, and allows adaptive resolution. Unlike volume approaches that store the surface as a thick layer requiring 8 samples for tri-linear interpolation, TileTrees map 2D tiles, requiring only 4 samples and avoiding the 2x data overhead. Unlike polycube maps which require manual intervention and fixed resolution, TileTrees do not require manual intervention and support adaptive resolution.

### Data-Driven Texture Coordinate Generation
A variant where texture coordinates are generated procedurally as a function of local data values to threshold geometry, using a texture map with two entries (fully transparent and fully opaque) [S1, book].
1. Create a texture map with two entries: transparent ($\alpha = 0$) and opaque ($\alpha = 1$) [S1, book].
2. For each vertex/pixel, evaluate the local data value [S1, book].
3. If data value < threshold, set texture coordinate to index into the transparent portion [S1, book].
4. If data value >= threshold, set texture coordinate to index into the opaque portion [S1, book].
The special texture map consists of two entries: Entry 1 is fully transparent (alpha=0), Entry 2 is fully opaque (alpha=1) [S1, book].

### High-Resolution Patching
A technique to overcome resolution limitations by directly importing a high-resolution image (patch) for a specific portion of the morphed texture image during texture mapping [S3, unofficial].
1. Import a high-resolution texture image (patch) during texture mapping, with or without morphing, to replace or composite with the low-resolution area [S3, unofficial].
2. Fine-tune the inverse projection to an extremely small area to digitally composite textures using different texture images (e.g., cliff texture and horse leg texture) [S3, unofficial].
In a horse-on-cliff experiment, the paint area in the low-resolution texture was 66x20 pixels, while the high-resolution horse image was 256x166 pixels. Using the high-res patch preserved details, whereas the low-res patch suffered from alias artifacts and detail loss [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Not given in the sources.
*   **Measured Performance:** High performance on hardware with efficient 2D texture mapping units, suitable for real-time applications like video games where interactivity is required [S1, book].
*   **Scaling:** Performance scales with the number of slices and texture resolution. Non-power-of-two dimensions are automatically converted to power-of-two by some libraries (e.g., VTK) at the expense of extra computation [S1, book].
*   **Strengths:** Compatibility with older hardware lacking 3D texture support; high performance due to hardware acceleration; simplicity of implementation [S1, book].
*   **Limitations:** Lower visual accuracy compared to view-aligned methods due to object-aligned slices and bilinear interpolation; potential for aliasing artifacts if resolution is insufficient [S1, book].
*   **When to Use:** When hardware lacks 3D texture support; when performance is critical and visual accuracy can be traded; for real-time applications [S1, book].
*   **When Not to Use:** When high visual accuracy is required and view-aligned slicing is feasible; when non-linear transfer functions need precise interpolation [S1, book].

## Background
Originating from the general concept of texture mapping in computer graphics, this approach was adapted for volume rendering to leverage existing 2D texture hardware [S1, book]. The `vzTMRenderAction` class, part of the VZ (Volume Visualization) library, provides a concrete implementation of this technique, managing the rendering pipeline for texture-mapped volume slices [S2]. It is used in video games to provide realistic scenes with low numbers of polygons for interactivity [S1, book].
