# Cabral Texture Mapping

Also called: Filtered Back Projection via Texture Mapping, Texture Mapping Backprojection, Trilinear interpolation of texture mapped slices

## Overview
Cabral Texture Mapping implements filtered back projection (FBP) for CT reconstruction by projecting 2D slices into a frame buffer using texture mapping hardware and an accumulation buffer [S2, unofficial]. It differs from direct volume rendering by performing back-projection via texture interpolation and hardware blending rather than ray casting [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A set of 2D projection slices derived from CT projection data [S2, unofficial].
*   **Output:** A reconstructed 3D scalar field accumulated in a frame or accumulation buffer [S2, unofficial].

**Data Structures:**
*   **Texture Maps:** 2D textures representing the projection slices [S2, unofficial].
*   **Accumulation Buffer:** A buffer used to sum the back-projected contributions [S2, unofficial].

**Steps:**
1.  Map each projection slice into volume space using texture coordinates [S2, unofficial].
2.  Tri-linearly interpolate the scalar values and texture-mapped slices [S1, unofficial].
3.  Blend the interpolated slices into the frame buffer in a back-to-front manner [S1, unofficial].

**Formulas:**
*   The mathematical formulation of the filtered back projection algorithm is not provided in the sources [S2, unofficial].
*   Trilinear interpolation weights are not detailed [S1, unofficial].

**Parameters:**
*   **Interpolation Mode:** Trilinear interpolation [S1, unofficial].
*   **Blending Order:** Back-to-front [S1, unofficial].

**Edge Cases and Pitfalls:**
*   Non-linear transfer functions are not interpolated correctly by texture hardware, requiring the volume to be re-shaded and re-loaded whenever viewing parameters change [S2, unofficial].
*   The original implementation depended on specific hardware (Raster Manager Reality Engine Onyx) [S2, unofficial].

**Pseudocode:**
```python
def cabral_texture_mapping(slices, accumulation_buffer, transform_matrix):
    # Initialize accumulation buffer to zero
    accumulation_buffer.fill(0.0)
    # Process slices in back-to-front order
    for slice_data in reversed(slices):
        # Standard affine transformation to map slice coordinates to volume space
        tex_coords = transform_matrix * slice_data.coordinates
        # Tri-linearly interpolate scalar values from the mapped texture
        values = tri_linear_sample(slice_data.texture, tex_coords)
        # Accumulate into frame buffer
        accumulation_buffer += values
    return accumulation_buffer

def tri_linear_sample(texture, coords):
    # Standard tri-linear interpolation over 3D texture coordinates
    x, y, z = coords
    ix, iy, iz = floor(x), floor(y), floor(z)
    dx, dy, dz = x - ix, y - iy, z - iz
    # Fetch 8 corner texels
    v000 = texture[ix, iy, iz]
    v100 = texture[ix+1, iy, iz]
    v010 = texture[ix, iy+1, iz]
    v110 = texture[ix+1, iy+1, iz]
    v001 = texture[ix, iy, iz+1]
    v101 = texture[ix+1, iy, iz+1]
    v011 = texture[ix, iy+1, iz+1]
    v111 = texture[ix+1, iy+1, iz+1]
    # Interpolate along x
    v00 = v000*(1-dx) + v100*dx
    v01 = v010*(1-dx) + v110*dx
    v10 = v001*(1-dx) + v101*dx
    v11 = v011*(1-dx) + v111*dx
    # Interpolate along y
    v0 = v00*(1-dy) + v01*dy
    v1 = v10*(1-dy) + v11*dy
    # Interpolate along z
    return v0*(1-dz) + v1*dz
```

## Subtopics

### Multi-resolution Representation for Intermediate Template
A technique to overcome resolution limitations and glancing angle projection artifacts by generating the intermediate template at different resolutions for different areas, rather than using a single finest resolution for the whole template [S3, unofficial]. It defines resolution intervals $\Delta u = 1/(x_d - 1)$ and $\Delta v = 1/(y_d - 1)$ and uses continuous variables $u$ and $v$ to adjust the origin and direction of the tracing ray during DVR/DSR generation of the intermediate template, allowing different resolution intervals to be used [S3, unofficial]. This is chosen when different areas have different resolution requirements (e.g., wrinkles around eyes), as rendering the whole template at the finest resolution is impractical and unnecessary [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Not given in the sources.
*   **Measured Performance:** The original implementation used four Raster Manager Reality Engine Onyx machines [S2, unofficial].
*   **Strengths:** Leverages existing texture mapping hardware for back-projection [S2, unofficial].
*   **Limitations:** Non-linear transfer functions are not interpolated correctly by texture hardware, requiring re-shading and re-loading when viewing parameters change [S2, unofficial]. High network bandwidth requirements if distributed rendering is used for composition [S2, unofficial].
*   **When to use:** When implementing filtered back projection on hardware with strong texture mapping capabilities and accumulation buffers [S2, unofficial].
*   **When not to use:** When non-linear transfer functions are critical and hardware interpolation is insufficient [S2, unofficial].

## Background
The method was proposed by Cabral et al. [11] and implemented on Raster Manager Reality Engine Onyx machines [S2, unofficial]. It is part of the history of early volume rendering and CT reconstruction techniques that utilized graphics hardware acceleration [S2, unofficial]. The approach is related to other texture-based methods like those by Dachille and Kaufman [19] and shear-warp methods [63] [S2, unofficial].
