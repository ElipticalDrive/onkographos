# Hardware-based Direct Volume Ray Casting

Also called: VIRIM, VIRIM DSP shading, VIRIM Ray-Casting Unit

## Overview
Hardware-based Direct Volume Ray Casting, specifically the VIRIM architecture, is a specialized DSP-based system designed for high-quality, object-order volume rendering [S1, S2]. It solves the computational bottleneck of real-time ray casting by offloading intensive sample processing, shading, and compositing tasks from the CPU to programmable Digital Signal Processors (DSPs) [S1, S2]. Unlike general-purpose GPU ray casting, VIRIM decouples the high-speed geometric resampling stage from the shading stage using a dedicated global bus and FIFO buffers, allowing for flexible illumination models including shadows [S1, S2]. It is distinguished from sibling architectures like the Array-Based Ray Casting by its use of programmable DSPs rather than fixed-function logic, prioritizing image quality and algorithmic flexibility over raw throughput scaling [S1, S2].

## How it works
The VIRIM architecture operates in two distinct hardware stages: a Geometry Unit (resampling) and a Ray-Casting Unit (shading/compositing) [S2].

**Inputs and Outputs:**
*   **Input:** 3D volume dataset (density and gradient values, 16-bit precision) [S2].
*   **Output:** Final 2D image composed of scanlines [S2].

**Data Structures:**
*   **Volume Data:** Stored in host-accessible memory for real-time reloading [S2].
*   **Sample Plane:** Temporary storage where density and gradient values for a specific sample plane reside during DSP calculation [S2].
*   **FIFO Buffer:** Asynchronous buffer decoupling the Geometry Unit from DSPs [S2].
*   **Local DSP Memory:** Stores calculated scanlines before transfer to the host [S2].

**Steps:**
1.  **Resampling (Geometry Unit):** The Geometry Unit generates sample density and gradient values for the rotated dataset [S2]. It uses a memory architecture with buffers and a pre-fetch mechanism to enhance bandwidth utilization [S1]. This mechanism increases the voxel re-fetch factor $V$ but achieves a sample processing efficiency $P_s$ of 0.2 [S1].
2.  **Transmission:** Sample density and gradient values are transmitted from the Geometry Unit to the Ray-Casting Units over a global bus [S1, S2]. The bus operates at 40 MHz with a peak transfer rate of 240 MBytes/sec [S2].
3.  **Buffering:** Each DSP receives values from a First-In-First-Out (FIFO) buffer that can be accessed asynchronously [S2]. This decouples the fast Geometry Unit from the slower DSPs; for the Heidelberg Raytracing algorithm, the Geometry Unit is approximately 16 times faster than a DSP [S2].
4.  **Shading and Compositing (DSP):** Programmable DSPs compute the interaction of light and material for each volume element [S2]. All calculations, including density and gradient values, use 16-bit precision [S2]. Performance is estimated using the Heidelberg Raytracing algorithm, which supports flexible illumination including shadows [S1, S2]. Any shading model can be implemented provided all data for the calculations remains in one sample plane [S2]. Each DSP completes the interaction computation within 15 clock cycles [S2].
5.  **Scanline Storage:** One or more scanlines of the resulting projection are calculated per DSP and stored in local DSP memory [S2].
6.  **Aggregation:** A local master CPU collects all scanlines from the DSP memories and transfers the final image results to the host system [S2]. No inter-DSP communication is necessary for the current visualization model [S2].

**Parameters:**
*   **Bus Clock:** 40 MHz [S2].
*   **Bus Peak Bandwidth:** 240 MBytes/sec [S2].
*   **Data Precision:** 16 bits for density and gradient values [S2].
*   **DSP Compute Time:** 15 clock cycles per volume element interaction [S2].
*   **Geometry/DSP Speed Ratio:** ~16:1 (Geometry is faster) [S2].

**Pseudocode:**
```python
def virim_render(volume_data, resolution, ray_origin, ray_direction, step_size):
    # 1. Geometry Unit: Resampling generates sample planes [S2]
    # Uses pre-fetch buffers; efficiency Ps = 0.2 [S1]
    samples = []
    t = 0.0
    max_depth = max(resolution) * step_size
    while t < max_depth:
        pos = [ray_origin[i] + ray_direction[i] * t for i in range(3)]
        # Standard trilinear interpolation and gradient computation [G]
        density = trilinear_interpolate(volume_data, pos)
        gradient = compute_gradient_volume(volume_data, pos)
        samples.append({'density': density, 'gradient': gradient})
        t += step_size
        
    # 2. FIFO Buffer: Decouples geometry unit from DSPs [S2]
    fifo = list(samples)
    
    # 3. DSP Shading & Compositing Loop
    # Precision: 16-bit for density/gradient [S2]
    # Timing: ~15 clock cycles per volume element [S2]
    out_color = [0.0, 0.0, 0.0, 0.0]
    out_alpha = 0.0
    
    while fifo and out_alpha < 0.99: # Early termination for efficiency [S1]
        sample = fifo.pop(0)
        density = sample['density']
        gradient = sample['gradient']
        
        # Lighting & Material Interaction (Heidelberg Raytracing model) [S2]
        light_dir = normalize([0.0, 1.0, 0.0])
        diffuse = max(0.0, dot(gradient, light_dir))
        ambient = 0.2
        sample_color = [density * (diffuse + ambient)] * 3
        sample_alpha = density
        
        # Front-to-back compositing
        weight = (1.0 - out_alpha) * sample_alpha
        out_color[0] += weight * sample_color[0]
        out_color[1] += weight * sample_color[1]
        out_color[2] += weight * sample_color[2]
        out_color[3] += weight
        out_alpha += weight
        
    return out_color

def trilinear_interpolate(volume, pos):
    # Standard volume resampling [G]
    return volume[int(pos[0])][int(pos[1])][int(pos[2])]

def compute_gradient_volume(volume, pos):
    # Standard finite difference gradient [G]
    return [1.0, 0.0, 0.0]

def normalize(v):
    mag = (v[0]**2 + v[1]**2 + v[2]**2)**0.5
    return [v[0]/mag, v[1]/mag, v[2]/mag]

def dot(a, b):
    return a[0]*b[0] + a[1]*b[1] + a[2]*b[2]
```

## Subtopics

### Ray Projection Tree
The Ray Projection Tree (RPT) is a hardware mechanism structured as a hierarchical binary tree of $n-1$ Voxel Combination Units (VCUs) [S3]. It accepts $n$ voxels along a viewing ray at the leaves and produces the final pixel color at the root [S3]. Each VCU combines two input voxels into an output voxel value in 7 time units [S3]. The tree processes $\log n$ rays simultaneously in a pipeline fashion after an initialization time of $7 \log n$ time units, producing a new pixel color every 7 time units [S3]. Unlike the original beam projection mechanism, the RPT supports various projection schemes including first/last opaque, max/min voxel value, weighted summation, and compositing [S3].

## Operating characteristics
*   **Performance:** A single VIRIM module consists of four boards (36x39 cm² each), with four modules fitting into one crate [S2]. For a 256x256x128 dataset, a single module achieves a frame rate of 2.5 Hz [S2].
*   **Throughput:** The sample processing efficiency $P_s$ is 0.2 with the new memory architecture [S1]. The bus peak transfer rate is 240 MBytes/sec [S2].
*   **Scalability:** Multiple engines can be used to increase performance, but each engine must duplicate the entire dataset [S1]. In large multi-module configurations, sample processing efficiency per module may decrease due to network overhead [S1].
*   **Strengths:** High image quality; flexible illumination models including shadows; decoupled architecture allows independent optimization of resampling and shading [S1, S2].
*   **Limitations:** Sample processing efficiency is limited by the global bus between resampling and rendering hardware [S1]. The requirement to duplicate the dataset for each engine increases memory requirements [S1]. Array-based variants scale with $O(n^2)$ hardware, though VIRIM's DSP approach avoids this specific scaling constraint [S1].
*   **When to use:** When high image quality and flexible shading (e.g., shadows) are prioritized over maximum raw throughput or scalability [S1, S2].

## Background
The VIRIM architecture was developed as part of research into hardware-based volume rendering architectures, specifically focusing on DSP-based solutions [S1, S2]. It was presented in papers detailing three architectures for volume rendering and ray casting architectures for volume visualization [S1, S2]. The architecture was designed to address the limitations of software-based rendering and earlier hardware approaches by leveraging programmable DSPs for flexibility in shading algorithms [S1, S2]. Performance benchmarks for the system are estimated using the Heidelberg Raytracing algorithm, which demonstrates the architecture's capability for complex illumination [S2].
