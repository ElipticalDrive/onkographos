# ATLANTIS FPGA Volume Rendering Architecture

Also called: ATLANTIS computing board, hybrid FPGA/RISC volume rendering

## Overview
The ATLANTIS architecture is a hardware volume rendering system that utilizes Field-Programmable Gate Array (FPGA) reconfiguration to define special-purpose processors for distinct operations, thereby minimizing hardware overhead by reloading configurations for different computing tasks [S1]. It distinguishes itself from static hardware accelerators by dynamically reconfiguring its logic fabric to handle initialization, distance calculation, and rendering phases, while leveraging a hybrid FPGA/RISC approach on a CompactPCI platform [S1]. Unlike general-purpose GPU rendering, it relies on specific algorithmic optimizations like 3D distance transforms for transparent region extension and parallel ray parameter downloading to overlap with rendering time [S1].

## How it works
The system operates by reconfiguring FPGAs into specific modes to handle different stages of the volume rendering pipeline. The architecture is built on a CompactPCI board (the ATLANTIS computing board) with a RISC processor host and FPGA logic [S1].

### Inputs and Outputs
*   **Input:** 3D volume dataset (stored in external memory/subboard), ray parameters (origin, direction, length), transfer function parameters (LUT, reflectance map).
*   **Output:** Rendered 2D image (pixel colors/opacities).

### Data Structures and Layout
The system stores ray parameters in local FPGA RAM to enable overlap between parameter downloading and rendering [S1]. For each ray, the following parameters are stored:
*   **Starting Point:** 3 components, 24 bits each (72 bits total).
*   **Minimal Distance to Next Sampling Point:** 3 components, 16 bits each (48 bits total).
*   **Maximal Ray Length:** 10 bits.
*   **Total per Ray:** 130 bits.

The system processes rays in multithreading bunches of $8 \times 8$, totaling 64 rays per processing unit [S1].

### Configuration Modes
The FPGA is reconfigured into one of four main modes. Each reconfiguration takes between 35 ms and 140 ms, depending on the number of FPGAs reconfigured [S1].

1.  **Initialization:** Used only for loading data into registers and memory [S1].
2.  **LUT and Reflectance Map Adjusting:** Used only for loading data into registers and memory [S1].
3.  **Distance Calculation:** Determines the extension of transparent regions within the dataset using distance transforms. One FPGA is reconfigured with a two-pass non-linear digital filter [S1].
4.  **Rendering Configuration:** Sets internal parameters for the rendering process concerning shading and voxel gray value to opacity assignment. This mode executes three tasks in parallel:
    *   Downloading of ray parameters.
    *   Implementation of the rendering algorithm.
    *   Upload of rendering results [S1].

### Algorithm Steps

1.  **System Initialization:** The RISC host initializes the board. The FPGA is reconfigured into the **Initialization** mode to load initial data into registers and memory [S1].
2.  **Transfer Function Setup:** The FPGA is reconfigured into the **LUT and Reflectance Map Adjusting** mode to load the lookup tables (LUT) and reflectance maps into memory [S1].
3.  **Distance Transform Calculation:**
    *   The FPGA is reconfigured into the **Distance Calculation** mode [S1].
    *   A two-pass non-linear digital filter is executed on the volume data to compute distance transforms [S1].
    *   This step determines the extension of transparent regions, allowing the renderer to skip empty space during ray casting [S1].
4.  **Rendering Configuration:**
    *   The FPGA is reconfigured into the **Rendering Configuration** mode [S1].
    *   Internal parameters for shading and opacity assignment are set [S1].
    *   The rendering pipeline begins. For each frame or batch of rays:
        a.  **Ray Parameter Download:** Ray parameters (starting point, minimal distance, maximal length) are downloaded from host memory to the local FPGA RAM. This is done for bunches of 64 rays ($8 \times 8$) [S1].
        b.  **Parallel Execution:** The system overlaps the downloading of parameters with the rendering of previously downloaded rays. The rendering algorithm executes in parallel with the parameter download for the next batch [S1].
        c.  **Ray Casting:** The FPGA implements the rendering algorithm, using the distance transform information to skip transparent regions and sampling the volume data [S1].
        d.  **Result Upload:** The rendered results are uploaded to the host memory [S1].

### Parameters and Performance
*   **Backplane Ports:** High-speed I/O of 1 GB/s @ 66 MHz, 2*64-bit [S1].
*   **Host Interface:** PCI supports two independent DMA (on demand) channels allowing 125 MB/s max data throughput [S1].
*   **M-Link:** FIFO-like point-to-point link standard, using an 80 MB/s LVDS implementation similar to CERN internal S-Link interface [S1].
*   **Configuration Time:** 35 ms to 140 ms per mode, depending on the number of FPGAs reconfigured [S1].
*   **Performance:** The system achieves 30 Hz rendering rates for $256^3$ data sets [S1].

### Edge Cases and Pitfalls
*   **Reconfiguration Latency:** The reconfiguration time (35-140 ms) is significant compared to frame rates. The architecture mitigates this by reconfiguring only when necessary (e.g., changing transfer functions or volume data) and keeping the rendering configuration stable for multiple frames [S1].
*   **Memory Bottleneck:** The performance of the FPGA system is limited by memory speed (limited to 100 MHz for most devices), whereas recent SDRAMs achieve 150 MHz and RDRAMs allow up to 500 MHz data read-out rates [S1]. This suggests that ASICs could potentially outperform this FPGA design if memory bottlenecks were resolved [S1].
*   **Transparent Regions:** The distance transform is critical for skipping transparent regions. If the distance transform is inaccurate or not computed, the renderer may waste cycles sampling empty space [S1].

## Operating characteristics
*   **Time Complexity:** Not explicitly given in terms of asymptotic complexity. The rendering rate is 30 Hz for $256^3$ data sets [S1].
*   **Memory Complexity:** Not explicitly given. The system uses external memory for the volume and local FPGA RAM for ray parameters [S1].
*   **Performance:** 30 Hz for $256^3$ data sets [S1].
*   **Strengths:**
    *   Flexibility through FPGA reconfiguration [S1].
    *   Minimization of hardware by reloading configurations for different tasks [S1].
    *   Overlap of parameter downloading and rendering time using local FPGA storage [S1].
    *   Algorithmic optimizations like distance transforms for transparent region skipping [S1].
*   **Limitations:**
    *   Reconfiguration latency (35-140 ms) [S1].
    *   Memory speed bottleneck (100 MHz) limits potential performance compared to faster SDRAM/RDRAM [S1].
    *   No other hardware systems at the time used both algorithmic optimizations and hardware acceleration in this manner, making comparison difficult [S1].
*   **When to Use:** Suitable for applications requiring flexible hardware acceleration for volume rendering, particularly where transfer functions or distance transforms need to be updated dynamically, and where the memory bandwidth bottleneck is acceptable [S1].
*   **When Not to Use:** Not suitable for applications requiring very high frame rates with frequent reconfiguration, or where memory bandwidth is the primary bottleneck and faster memory interfaces are available [S1].

## Background
The ATLANTIS architecture was described in the paper "ATLANTIS: A hybrid approach combining the power of FPGA and RISC processor based on CompactPCI" by A. Kugel, H. Singpiel, J. Hesser, and R. Manner, presented at FPGA '99 in Monterey, CA, in 1999 [S1]. It was used in the ATLANTIS computing board, a versatile hardware for volume rendering applications [S1]. The system is related to earlier work such as VIRIM (1995) [S1]. The use of distance transforms for volume rendering is based on earlier work by Levoy (1988) and others [S1].
