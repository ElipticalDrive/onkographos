# 2D Texture-Based Volume Rendering

Also called: 2D Texture Mapping Volume Rendering, 2D Texture Slicing, 2D Texture Volume Rendering, Stack of 2D textures, Texture Plane Volume Rendering, Texture mapped planes, VR Basado en Texturas 2D

## Overview
2D Texture-Based Volume Rendering is a hybrid object-order technique that renders volumetric data by decomposing the volume into a stack of 2D texture slices aligned with the object's coordinate axes, projecting them onto the image plane, and compositing them back-to-front using hardware alpha blending [S1, S4, S5, S6, S13, S14, S24, unofficial]. It solves the problem of rendering 3D scalar fields on graphics hardware that lacks native 3D texture support or requires compatibility with older OpenGL implementations by substituting trilinear interpolation with bilinear interpolation within 2D textures [S6, unofficial][S17, S18][S21, unofficial][S22]. Unlike [3D Texture-Based Volume Rendering](9841-3d-texture-based-volume-rendering.md), which stores the entire volume in a single 3D texture and allows for view-aligned slicing with trilinear interpolation, this method requires pre-computing three separate stacks of 2D textures (one for each major axis) and selecting the stack most perpendicular to the viewing direction to minimize gaps [S4, S7, S10, unofficial][S12]. It differs from [Shear-Warp Rendering](9840-shear-warp-rendering.md) by avoiding the explicit matrix decomposition (shear and warp) and instead relying on the graphics pipeline's automatic transformation of object-aligned quads, though both share the back-to-front compositing strategy [S6, unofficial][S22].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D scalar volume dataset $V$ with dimensions $X \times Y \times Z$. A viewing direction vector $\vec{v}$ derived from the camera's model-view matrix. A transfer function $TF$ mapping scalar values to RGBA color and opacity.
*   **Output:** A 2D image buffer (framebuffer) containing the composited volume.

**Data Structures:**
The method requires storing the volume data in three sets of 2D textures, one set for each axis-aligned slicing direction.
*   **Texture Stacks:** Three arrays of 2D texture IDs: $\text{texX}$, $\text{texY}$, $\text{texZ}$.
    *   $\text{texX}[i]$ contains the slice at $x=i$, stored as a 2D texture of size $Y \times Z$ (or padded to power-of-two, e.g., $256 \times 256$) [S13, S24, unofficial].
    *   $\text{texY}[j]$ contains the slice at $y=j$, stored as $X \times Z$ [S13, unofficial].
    *   $\text{texZ}[k]$ contains the slice at $z=k$, stored as $X \times Y$ [S13, unofficial].
*   **Texture Format:** Each texel stores RGBA values. The RGB components store the emission coefficient $I_{emit}$ (color), and the Alpha component stores the inverse absorption coefficient $(1 - \vartheta_k)$ [S6, unofficial]. The data is typically loaded as `GL_LUMINANCE` or `GL_RGBA` depending on hardware support, with single-component data stored in the red channel or luminance [S13, S24, unofficial].
*   **Slice Geometry:** Each slice is represented as a quad (or triangle fan) defined by four vertices. The vertices are computed by intersecting the slicing plane with the volume's bounding box [S8, S11, unofficial].

**Parameters:**
*   **Number of Slices ($N$):** Typically matches the dimension of the volume along the slicing axis. Some implementations use a formula such as $N = 2 \cdot (10 + \text{max\_planes} \cdot q^3)$ to determine slice count based on quality factor $q$ and maximum planes [S8, unofficial].
*   **Slicing Axis Selection:** The axis is chosen such that its normal is within $\pm 45^\circ$ of the viewing direction [S12, S17, S18, S19, S20].
*   **Opacity Correction:** An optional parameter to scale slice alpha based on the Euclidean distance between slices along the viewing ray to prevent brightness changes [S4, S8, unofficial]. Default is often OFF [S8, unofficial].

**Steps:**

1.  **Preprocessing (Texture Generation):**
    *   Decompose the 3D volume into three stacks of 2D slices parallel to the X, Y, and Z axes [S4, unofficial][S12, S20].
    *   Apply the transfer function to map scalar values to RGBA. Store emission in RGB and inverse absorption in Alpha [S6, S13, S14, unofficial].
    *   Upload these slices to GPU memory as 2D textures [S24, unofficial].
    *   *Note:* This step is performed once per volume or when the volume data changes [S20].

2.  **View Direction Analysis:**
    *   Extract the rotation component from the current Model-View matrix [S6, unofficial].
    *   Transform the initial viewing direction vector $\vec{v}_{init} = (0, 0, -1)$ by this rotation to get $\vec{v}_{world}$ [S6, unofficial].
    *   Find the component of $\vec{v}_{world}$ with the largest absolute value: $n_{max} = \text{argmax}_i |v_i|$ [S6, unofficial].
    *   Select the corresponding texture stack ($\text{texX}$, $\text{texY}$, or $\text{texZ}$) and the direction (positive or negative) based on the sign of the dominant component [S6, S13, unofficial].

3.  **Geometry Generation (Per Frame):**
    *   For the selected axis, generate proxy geometry (quads) for each slice index $i$ from $0$ to $D-1$ (where $D$ is the dimension along that axis) [S13, unofficial].
    *   Compute the world-space position of each slice plane. The distance $dist$ between slices is determined by the step size along the viewing direction [S13, unofficial].
    *   *Alternative:* Use instanced rendering with an Array Buffer Object containing slice positions and texture coordinates [S10, unofficial].

4.  **Rendering Loop:**
    *   Determine the rendering order: Back-to-Front relative to the camera [S13, unofficial][S18, S20].
    *   Disable depth testing to allow correct alpha blending [S26, unofficial].
    *   Set the blend function to `GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA` [S6, unofficial].
    *   For each slice $i$ in the selected stack:
        *   Bind the texture $\text{tex}[i]$ [S13, unofficial].
        *   Set the texture coordinates for the quad vertices to map the 2D texture correctly to the slice plane [S20].
        *   Draw the quad (e.g., using `glDrawArraysInstanced` or immediate mode) [S10, S13, unofficial].
        *   The hardware rasterizer performs bilinear interpolation on the 2D texture [S6, S21, unofficial].
        *   The fragment shader/compositor blends the result into the framebuffer using the alpha blending equation:
            $$ C_{dest} = C_{src} \cdot A_{src} + C_{dest} \cdot (1 - A_{src}) $$
            where $C_{src}$ is the sampled color (emission) and $A_{src}$ is the sampled alpha (inverse absorption) [S6, S14, unofficial].

**Pseudocode:**

```python
def render_2d_texture_volume(volume_data, model_view_matrix, transfer_function):
    # 1. Preprocessing: Generate texture stacks (done once or on data change)
    # volume_data: 3D array (X, Y, Z)
    # texX, texY, texZ: lists of 2D texture IDs
    texX = []
    texY = []
    texZ = []
    
    for x in range(volume_data.shape[0]):
        slice_data = volume_data[x, :, :]
        rgba_slice = transfer_function(slice_data)
        texX.append(create_2d_texture(rgba_slice))
        
    for y in range(volume_data.shape[1]):
        slice_data = volume_data[:, y, :]
        rgba_slice = transfer_function(slice_data)
        texY.append(create_2d_texture(rgba_slice))
        
    for z in range(volume_data.shape[2]):
        slice_data = volume_data[:, :, z]
        rgba_slice = transfer_function(slice_data)
        texZ.append(create_2d_texture(rgba_slice))

    # 2. View Direction Analysis
    rotation_matrix = extract_rotation(model_view_matrix)
    view_vector = mat_vec_multiply(rotation_matrix, [0.0, 0.0, -1.0])
    
    abs_view = [abs(v) for v in view_vector]
    max_idx = argmax(abs_view)
    max_val = abs_view[max_idx]
    
    # Select stack and direction
    if max_idx == 0: # X axis
        stack = texX
        if view_vector[0] > 0:
            order = range(len(texX)) # Positive X
        else:
            order = range(len(texX) - 1, -1, -1) # Negative X
    elif max_idx == 1: # Y axis
        stack = texY
        if view_vector[1] > 0:
            order = range(len(texY))
        else:
            order = range(len(texY) - 1, -1, -1)
    else: # Z axis
        stack = texZ
        if view_vector[2] > 0:
            order = range(len(texZ))
        else:
            order = range(len(texZ) - 1, -1, -1)

    # 3. Rendering Setup
    enable_blending()
    set_blend_func(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA)
    disable_depth_test() # Or use depth test with depth write off
    
    # 4. Render Slices Back-to-Front
    for i in order:
        texture_id = stack[i]
        bind_texture(texture_id)
        
        # Compute slice position and vertices
        # dist is the distance along the viewing ray for this slice
        dist = compute_slice_distance(i, stack, view_vector)
        
        # Generate quad vertices for the slice plane
        # Vertices are in world space, transformed by model-view
        vertices = generate_slice_quad(i, dist, volume_bounds)
        
        # Set texture coordinates
        # Texcoords map the 2D texture to the quad
        texcoords = compute_texcoords(i, stack, volume_bounds)
        
        draw_quad(vertices, texcoords)
```

**Edge Cases and Pitfalls:**
*   **Stack Switching Artifacts:** When the viewing direction crosses the $45^\circ$ threshold between axes, the method switches texture stacks. This causes visible "popping" artifacts due to abrupt changes in sampling positions and interpolation artifacts [S1, S6, S24, unofficial].
*   **Bilinear Interpolation Artifacts:** Since only bilinear interpolation is used within slices, and the third dimension is sampled discretely, severe aliasing and lack of spatial interpolation occur, especially when zooming in [S5, S6, S21, unofficial][S22].
*   **Viewing Angle Limitations:** If the view is close to $45^\circ$ relative to the slice normal, the viewer sees through the edges of the slices, causing gaps and artifacts [S4, unofficial][S17, S18, S19, S20].
*   **Opacity Correction:** Without opacity correction, the apparent brightness changes as the viewing angle changes because the Euclidean distance between slices along the ray varies [S4, unofficial][S22].
*   **Memory Usage:** Requires storing three copies of the volume data in texture memory, which can be prohibitive for large datasets [S3, S6, S7, unofficial].
*   **VTK OIT Conflict:** In VTK 9, Order-Independent Translucency (OIT) breaks the back-to-front compositing, resulting in an X-ray look. It must be disabled [S8, unofficial].
*   **Negative Values:** Applying logarithmic transfer functions to data with zero or negative values results in NaN or -inf, causing rendering errors [S14, S15, unofficial].

## Subtopics

### [Novel Sampling Scheme for Slice Based Volume Rendering](953-novel-sampling-scheme-for-slice-based-volume-rendering.md)
A variant that renders multiple clipped stacks simultaneously to eliminate stack-switching and jagged boundary artifacts. It approximates uniform ray-casting sampling more closely than spherical shell approaches while avoiding their geometry overhead.

### [Interpolation of Arbitrary Slices (Multi-Texture Blending)](2089-interpolation-of-arbitrary-slices-multi-texture-blending.md)
Renders arbitrary slicing planes by interpolating between two adjacent object-aligned texture slices using multi-texturing hardware. It reduces polygon count by half compared to single-texture approaches but is constrained by memory bandwidth.

### [Multi-Texture Interpolation](2200-multi-texture-interpolation.md)
Enables real trilinear interpolation by computing intermediate slices on the fly using hardware combiners. It corrects bilinear artifacts by weighted blending of adjacent fixed slices, providing a constant sampling rate and supersampling capabilities.

### [Slice-Based Volume Rendering with HSV Transfer Function](4329-slice-based-volume-rendering-with-hsv-transfer-function.md)
Uses a GPU-accelerated object-order technique with an HSV transfer function. It manages a texture array (sprite sheet) to simulate 3D trilinear filtering and computes color in HSV space rather than using a pre-baked 1D RGB texture lookup.

### SGI Octane2 Volume Rendering Pipeline
A pipeline for SGI Octane2 with V series graphics cards using 3D pixel textures via `glDrawPixels()` or `glCopyPixels()` to handle multi-dimensional transfer functions and shading. It renders slices, pixel textures them, renders a 'Shade' slice, modulates it with the classified slice, and blends into the framebuffer. It requires a scratch/auxiliary buffer because pixel texture does not occur directly on a per-fragment basis [S27].

## Operating characteristics
*   **Time Complexity:** Rendering time is proportional to the number of slices $N$ and the image resolution, independent of scene complexity [S9, S11, unofficial].
*   **Memory Complexity:** Requires $3 \times X \times Y \times Z$ texels (or padded equivalents) to store the three texture stacks [S3, S6, S7, unofficial]. For a $181 \times 217 \times 181$ volume padded to $256 \times 256$, this results in 579 textures and ~37.9 MB of memory [S24, unofficial].
*   **Performance:** Provides high performance on hardware with fast 2D texturing and blending units, often achieving interactive frame rates on standard PC hardware [S4, S7, S21, unofficial]. Performance improves significantly with subsampling (e.g., factor of 2 in all dimensions yields 8x speedup) [S26, unofficial].
*   **Strengths:** Compatible with older graphics hardware lacking 3D texture support; simple implementation; leverages hardware acceleration for interpolation and blending [S4, S6, S7, unofficial].
*   **Limitations:** Poor image quality due to bilinear interpolation and fixed sampling rate; visible artifacts at stack switches and edge-on views; high memory consumption; cannot easily model refracting volumes or viewing rays that change direction [S5, S6, S11, unofficial][S17, S18, S19][S21, unofficial][S22].
*   **When to Use:** Real-time visualization on older hardware or when 3D texture support is unavailable; moderate quality requirements where speed is prioritized over accuracy [S4, S6, S7, unofficial].
*   **When Not to Use:** High-quality medical visualization requiring trilinear interpolation; scenes with frequent view angle changes near $45^\circ$ thresholds; large volumes where memory is constrained [S5, S6, S21, unofficial][S22].

## Background
The method was pioneered by Cabral et al. in 1994, who demonstrated that the texture capabilities of graphics boards could be used directly for rendering volumetric data sets [S1, unofficial][S2][S5, unofficial]. It was one of the first techniques to exploit hardware texturing for volume rendering, preceding widespread 3D texture support [S2][S5, unofficial]. The approach is closely related to the Shear-Warp algorithm but avoids the explicit matrix decomposition by using object-aligned slices and hardware transformations [S6, unofficial][S22]. Later improvements included pre-integrated volume rendering by Engel et al. in 2001, which improved quality by handling transfer function integration [S2][S5, unofficial]. The method was widely used in early GPU-based volume rendering applications due to its compatibility with OpenGL 1.x and early 2D texture hardware [S4, S7, unofficial][S17, S18, S19, S20].
