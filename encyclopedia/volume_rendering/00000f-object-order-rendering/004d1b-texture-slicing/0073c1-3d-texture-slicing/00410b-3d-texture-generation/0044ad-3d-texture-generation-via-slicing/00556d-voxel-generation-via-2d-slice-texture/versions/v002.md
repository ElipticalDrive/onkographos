# Voxel Generation via 2D Slice Texture
Also called: 2D Slice Texture Voxel Generation

## Overview
This method generates billions of explicit voxels without using 3D textures or compression by treating a single large 2D texture as a column of 2D slices [S1, unofficial]. It solves the memory bottleneck of storing full 3D volumes by rendering voxel data to a bitmap (chunk/page) and discarding it immediately after use [S1, unofficial]. It differs from sibling methods by explicitly generating every voxel in a shader rather than sampling implicit data, and by reusing a single 2D texture buffer for multiple chunks to minimize VRAM allocation [S1, unofficial]. It builds on [3D Texture Generation via Slicing](4891-3d-texture-generation-via-slicing.md).

## How it works
**Inputs and Outputs:**
*   **Input:** A 2D texture representing a column of slices, 2D texture coordinates ($u, v$), world bounds ($worldMin, worldMax$), and the voxel pitch ($volumePitch$) [S1, unofficial].
*   **Output:** 3D world coordinates for each voxel in the current chunk, which are then used to generate voxel data (density, color, etc.) and render depth/normals to screen [S1, unofficial].

**Data Structures:**
*   **Slice Texture:** A 2D texture with dimensions $128 \times 16384$ (width $\times$ height) [S1, unofficial]. The width (128) represents the slice thickness/width, and the height (16384) is the maximum texture width supported by most modern graphics cards [S1, unofficial]. This texture is treated as a column of slices [S1, unofficial].

**Numbered Steps:**
1.  Run the voxel generation shader on the 2D slice texture [S1, unofficial].
2.  For each point on the 2D slice texture, determine the corresponding 3D point clamped in the 0-1 range [S1, unofficial].
3.  Calculate the $x$ coordinate directly from the 2D texture's $x$ coordinate [S1, unofficial].
4.  Calculate the $z$ coordinate (slice number) from the 2D texture's $y$ coordinate [S1, unofficial].
5.  Calculate the $y$ coordinate (distance from top of slice) from the 2D texture's $y$ coordinate [S1, unofficial].
6.  Convert the normalized 3D coordinates to world space using linear interpolation between $worldMin$ and $worldMax$ [S1, unofficial].
7.  Generate voxel data using the calculated world coordinates [S1, unofficial].
8.  Render the generated voxel data to screen by shooting a ray from the front of the chunk to the back [S1, unofficial]. The volume cube is isometric, shaped like an imperfect hexagon with sides having a 0.5 slope [S1, unofficial].
9.  Render depth, normals, and texture information to a 2D texture for each chunk [S1, unofficial].
10. Render chunks to screen in back-to-front order [S1, unofficial].
11. Reuse textures for closer chunks as older ones fall out of distance [S1, unofficial].

**Formulas:**
Let $u, v$ be the 2D texture coordinates in $[0, 1]$, and $volumePitch$ be the number of voxels per chunk side.
*   $y_{pos} = \lfloor volumePitch^2 \cdot v \rfloor$
*   $x = u$
*   $y = \frac{\text{int\_mod}(y_{pos}, volumePitch)}{volumePitch}$
*   $z = \frac{\lfloor y_{pos} / volumePitch \rfloor}{volumePitch}$
*   $worldPos = mix(worldMin, worldMax, [x, y, z])$
where $\text{int\_mod}(a, b) = a - (\lfloor a / b \rfloor \cdot b)$ and $mix(a, b, t) = a + t \cdot (b - a)$ [S1, unofficial].

**Parameters:**
*   $volumePitch$: Number of voxels per chunk side, typically 128 [S1, unofficial].
*   $worldMin, worldMax$: Minimum and maximum coordinates defining the chunk's world space bounds [S1, unofficial].
*   Texture dimensions: $128 \times 16384$ [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** The method relies on integer arithmetic for coordinate mapping to avoid floating-point errors in slice indexing [S1, unofficial].
*   **Collision Detection:** Although voxel data is discarded, collision detection is still possible by using the rendered depth values within the shader or on the CPU side [S1, unofficial].
*   **Rendering Artifacts:** Grass rendered in screen space may exhibit artifacts, though mitigations exist [S1, unofficial].

**Pseudocode:**
```python
def int_mod(lhs: int, rhs: int) -> int:
    return lhs - ((lhs // rhs) * rhs)

def mix(a: float, b: float, t: float) -> float:
    return a + t * (b - a)

def map_2d_to_3d(xy_coords_in: tuple[float, float], volume_pitch: float, world_min: tuple[float, float, float], world_max: tuple[float, float, float]) -> tuple[float, float, float]:
    u, v = xy_coords_in
    x, y, z = 0.0, 0.0, 0.0
    i_volume_pitch = int(volume_pitch)
    y_pos = int(volume_pitch * volume_pitch * v)
    x = u
    y = float(int_mod(y_pos, i_volume_pitch)) / volume_pitch
    z = float(y_pos // i_volume_pitch) / volume_pitch
    world_pos = (
        mix(world_min[0], world_max[0], x),
        mix(world_min[1], world_max[1], y),
        mix(world_min[2], world_max[2], z)
    )
    return world_pos
```

## Operating characteristics
*   **Memory Efficiency:** By discarding voxel data after rendering and reusing a single 2D texture buffer, this method significantly reduces VRAM usage compared to storing full 3D textures [S1, unofficial].
*   **Performance:** The method allows for the generation of billions of voxels in real-time [S1, unofficial].
*   **Scalability:** The texture size can be changed in real-time, allowing for dynamic adjustment based on hardware capabilities [S1, unofficial].
*   **Limitations:** The method is specific to isometric rendering with a 0.5 slope hexagonal shape, which may not be suitable for all camera angles or rendering styles [S1, unofficial].
*   **When to Use:** Real-time voxel-based rendering where memory is constrained and explicit voxel generation is required [S1, unofficial].
*   **When Not to Use:** Not suitable for non-isometric rendering or when implicit volume representation is preferred [S1, unofficial].

## Background
This technique was developed as part of a 3-year timeline project [S1, unofficial]. It was designed to avoid the use of 3D textures and compression, allowing for explicit generation of every voxel [S1, unofficial]. The method leverages the maximum texture width supported by modern graphics cards (16384) to store a large number of slices in a single 2D texture [S1, unofficial].
