# Slice Viewport Scaling and Panning

Also called: Slice Panning, Viewport Scaling

## Overview
Slice Viewport Scaling and Panning maps physical voxel spacing to screen pixels to maintain correct aspect ratio during zoom and pan operations in 2D volume cross-section rendering [S1, unofficial]. It ensures that the rendered slice preserves its physical proportions regardless of the display widget's dimensions, preventing distortion during interactive navigation [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** Widget dimensions (`width`, `height`), slice pixel dimensions (`pix.width()`, `pix.height()`), physical voxel spacing (`su`, `sv`, `sz`), slice axis identifier, current zoom factor (`zoom`), and pan offsets (`pan.x()`, `pan.y()`).
*   **Outputs:** A target rectangle (`target`) defining the position and size of the rendered slice within the widget.

**Data Structures:**
*   `pan`: A 2D vector or struct containing `x` and `y` float/double offsets representing the translation of the view center relative to the widget center.
*   `target`: A rectangle struct with fields `x`, `y`, `width`, `height`.

**Steps:**
1.  **Determine Physical Dimensions:** Calculate the physical width ($pw$) and height ($ph$) of the slice based on the viewing axis and voxel spacing [S1, unofficial]:
    *   If axis is 2 (axial): use spacing $(su, sv)$.
    *   If axis is 1 (coronal): use spacing $(su, sz)$.
    *   If axis is 0 (sagittal): use spacing $(sv, sz)$.
    *   Compute:
        $$pw = pix.width() \times su$$
        $$ph = pix.height() \times sv$$
2.  **Calculate Scale Factor:** Determine the scale factor ($scale$) that fits the physical slice into the widget while respecting a margin and the user's zoom level [S1, unofficial]:
    $$scale = \min\left(\frac{width - 44}{pw}, \frac{height - 44}{ph}\right) \times zoom$$
    *   The constant `44` represents a fixed margin/padding in pixels [S1, unofficial].
3.  **Calculate Target Rectangle:** Compute the dimensions and position of the rendered slice [S1, unofficial]:
    *   Dimensions:
        $$w = pw \times scale$$
        $$h = ph \times scale$$
    *   Position (centered on widget, offset by pan):
        $$target.x = \frac{width - w}{2} + pan.x()$$
        $$target.y = \frac{height - h}{2} + pan.y()$$

**Pseudocode:**
```python
def compute_slice_viewport(widget_width, widget_height, pix_width, pix_height, spacing, axis, zoom, pan_x, pan_y):
    # 1. Determine physical dimensions based on axis
    # spacing is a tuple (sx, sy, sz)
    sx, sy, sz = spacing
    
    if axis == 2: # Axial
        su, sv = sx, sy
    elif axis == 1: # Coronal
        su, sv = sx, sz
    elif axis == 0: # Sagittal
        su, sv = sy, sz
    else:
        raise ValueError("Invalid axis")

    pw = pix_width * su
    ph = pix_height * sv

    # 2. Calculate scale factor
    # Margin is 44 pixels
    margin = 44
    scale_x = (widget_width - margin) / pw
    scale_y = (widget_height - margin) / ph
    
    # Use minimum to fit within both dimensions, then apply zoom
    base_scale = min(scale_x, scale_y)
    scale = base_scale * zoom

    # 3. Calculate target rectangle
    w = pw * scale
    h = ph * scale
    
    target_x = (widget_width - w) / 2 + pan_x
    target_y = (widget_height - h) / 2 + pan_y
    
    return {
        'x': target_x,
        'y': target_y,
        'width': w,
        'height': h
    }
```

**Edge Cases and Pitfalls:**
*   **Negative Dimensions:** If `zoom` is negative or `pw`/`ph` are zero, the scale calculation may produce invalid results. Ensure `zoom > 0` and voxel spacing is non-zero [G].
*   **Margin Constraints:** If the widget width or height is less than or equal to the margin (44 pixels), the scale calculation will yield negative or zero values, resulting in an invalid viewport. The implementation should clamp or handle this case [G].
*   **Precision:** Floating-point precision issues may arise with very large physical dimensions or very small zoom factors. Use double precision for intermediate calculations [G].

## Subtopics

### Z Dimension Scaling Modes
A set of three modes for setting the z-component (height) of the view volume to prevent the image from appearing 2-D due to extreme vertical compression in large view volumes [S2, unofficial].

*   **Mode 1 (Equal Spacing):** Sets the minimum z value to a predefined environment value and the maximum z value to the minimum z value plus the view volume radius. This forces uniform scaling in all three directions [S2, unofficial].
    *   *Pitfall:* May position the view volume below many items of interest when the radius is small, or position all items in the bottom of the display volume when the radius is very large (100,000 to 500,000 meters) [S2, unofficial].
*   **Mode 2 (Constant Z Scaling):** Sets a constant defined maximum and minimum z value. This keeps objects above the bottom of the volume regardless of radius and maintains height position independence from radius [S2, unofficial].
*   **Mode 3 (Manual Control):** Allows the user to manually set the minimum and maximum z values of the view volume [S2, unofficial].

*   *General Pitfall:* Modes with non-equal spacing in x/y compared to z lead to difficulties noticeable when the icon is rotated by the SIMNET rotation matrix [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(1)$ per frame for viewport calculation, as it involves a fixed number of arithmetic operations.
*   **Memory Complexity:** $O(1)$, requiring only a few scalar variables for state (pan, zoom, dimensions).
*   **Strengths:** Maintains physical aspect ratio, preventing distortion. Simple to implement.
*   **Limitations:** The fixed margin (44 pixels) may not be suitable for all UI designs. Does not handle 3D depth scaling automatically (requires separate Z-mode handling).
*   **When to use:** Interactive 2D slice viewing where physical accuracy is important.
*   **When not to use:** When strict pixel-perfect mapping without margins is required, or when 3D depth perception is critical without additional Z-scaling logic.

## Background
This method originates from implementations in medical imaging and 3D visualization software, specifically referenced in the MRI3D project [S1, unofficial] and the DTIC report on a True 3-D Display Device [S2, unofficial]. It addresses the challenge of mapping physical voxel data to screen pixels while allowing interactive navigation (zoom/pan) without distorting the anatomical or spatial relationships in the volume.
