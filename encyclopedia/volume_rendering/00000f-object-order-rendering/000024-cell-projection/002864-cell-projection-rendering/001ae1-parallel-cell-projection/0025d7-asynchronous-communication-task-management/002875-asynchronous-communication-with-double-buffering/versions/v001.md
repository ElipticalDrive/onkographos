# Asynchronous Communication with Double-Buffering

Also called: Asynchronous Send/Receive with Double-Buffering, Double-Buffering with Asynchronous Communication

## Overview
A communication strategy for parallel volume rendering that uses double-buffering in conjunction with asynchronous send and receive operations to reduce overheads and overlap communication of ray segments with rendering calculations [S1, unofficial]. It sets itself apart from synchronous cell projection by allowing processors to proceed independently, multiplexing object-space cell computations with image-space ray merging, and overlapping computation with communication using end buffering [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Local subset of volume data cells assigned to the processor; global image space for merging.
*   **Output:** Completed subimage sent to a host computer.

**Data Structures:**
*   **Communication Buffers:** Two buffers per processor (Double-Buffering scheme) to store ray segments destined for other processors' image regions [S1, unofficial].
*   **Ray Segments:** Geometric primitives generated from scan conversion of local cells, containing color, opacity, and destination coordinates [S1, unofficial].

**Steps:**
1.  **Initialization:** Initialize double-buffering for communication buffers [S1, unofficial].
2.  **Multiplexed Processing:** Proceed with scan conversion of data cells and merging of ray segments in a multiplexed fashion [S1, unofficial].
    *   During scan conversion, each processor converts its local cells to produce many ray segments [S1, unofficial].
    *   These ray segments are routed to their final destinations in image space for merging [S1, unofficial].
    *   Perform asynchronous send and receive operations for ray segments to overlap communication with rendering computations [S1, unofficial].
    *   Use double-buffering for communication buffers to reduce overheads [S1, unofficial].
3.  **Completion:** When scan conversion and ray-segment merging are finished, each processor sends its completed subimage to a host computer [S1, unofficial].
4.  **Assembly:** The host computer assembles the subimages for display [S1, unofficial].

**Pitfalls:**
*   **Overhead:** Without double-buffering, communication overheads may stall the pipeline [S1, unofficial].
*   **Synchronization:** Improper handling of asynchronous operations can lead to race conditions or lost segments if buffers are not managed correctly [S1, unofficial].

## Subtopics

### Double-Buffering für konfliktfreie Voxel-Modifikation
A technique to avoid flickering during simultaneous read and write accesses to contiguous voxel data by duplicating the volume and swapping buffers frame-by-frame [S2, unofficial]. It sets itself apart by preventing race conditions in dynamic voxel modification scenarios where voxels are moved or deleted [S2, unofficial]. Choose this when rendering dynamic volumes with concurrent modifications.
*   **Definition:** Technique to avoid flickering during simultaneous read and write accesses to contiguous voxel data by duplicating the volume and swapping buffers frame-by-frame [S2, unofficial].
*   **Steps:**
    1.  Initialize two volumes: `Volumeold` and `Volumenew` [S2, unofficial].
    2.  When moving a voxel from $\vec{p_i}$ along $\vec{h_i}$: Read and delete the voxel at $\vec{p_i}$ from `Volumeold` [S2, unofficial].
    3.  Write the voxel to the new position $\vec{p_i} + \vec{h_i}$ in `Volumenew` [S2, unofficial].
    4.  Swap the buffers (`Volumeold` $\rightleftharpoons$ `Volumenew`) before each modification phase to prevent race conditions [S2, unofficial].
*   **Pitfalls:** The method doubles the required graphics memory. Alternatively, complex synchronization mechanisms are needed [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** Overlaps communication with computation, potentially reducing total wall-clock time compared to synchronous methods [S1, unofficial].
*   **Memory Complexity:** Requires double the buffer space for communication and potentially double the volume memory if used for voxel modification [S1, S2, unofficial].
*   **Performance:** Reduces communication overheads by allowing asynchronous operations [S1, unofficial].
*   **Strengths:** Overlaps communication with rendering calculations; reduces overheads [S1, unofficial].
*   **Limitations:** Increased memory usage due to double-buffering [S1, S2, unofficial].
*   **When to use:** Parallel volume rendering on distributed systems where communication latency is significant [S1, unofficial].
*   **When not to use:** Memory-constrained environments where doubling buffer/volume size is prohibitive [S2, unofficial].

## Background
Originated in the context of scalable parallel cell-projection volume rendering for three-dimensional unstructured data [S1, unofficial]. Developed to address the communication bottlenecks in parallel rendering by overlapping computation and communication [S1, unofficial].
