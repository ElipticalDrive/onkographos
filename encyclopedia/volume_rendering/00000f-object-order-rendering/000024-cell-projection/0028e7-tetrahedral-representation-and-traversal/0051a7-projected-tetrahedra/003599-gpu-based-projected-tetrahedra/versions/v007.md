# GPU-based Projected Tetrahedra

Also called: Two-Shader PT, Vertex Shader PT, Tetrahedral Projection using Vertex Shaders

## Overview
GPU-based Projected Tetrahedra is a method for interactive volume rendering of unstructured tetrahedral data that shifts the geometric classification and decomposition of cells from the CPU to the GPU using programmable vertex shaders [S1, S2, S3, unofficial]. It solves the performance bottleneck of traditional Projected Tetrahedra (PT) by avoiding redundant projections and pre-processing, allowing for the rendering of large datasets at interactive rates [S1, unofficial]. It differs from standard PT by executing the classification logic within the vertex shader program rather than on the CPU, and from ray-casting approaches by occupying a substantially smaller memory footprint while achieving competitive frame rates [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Unstructured tetrahedral mesh data (vertices and connectivity).
*   **Output:** A composited image in the framebuffer.

**Data Structures:**
*   **Basis Graph:** A fixed topology used for all tetrahedra. It consists of four vertices representing the cell's corners and one additional "phantom" vertex [S2, S3, unofficial].
*   **Triangle Fan:** The primitive type sent to the GPU, comprising the four vertices and the phantom vertex [S2, S3, unofficial].
*   **Texture Memory:** Used to store the model data to avoid redundant projections and improve access speed [S1, unofficial].

**Algorithm Steps:**
1.  **Data Upload:** Store the tetrahedral model in GPU texture memory [S1, unofficial].
2.  **Primitive Submission:** Send the four vertices of a tetrahedron and an invalid/placeholder phantom vertex to the GPU as a triangle fan [S2, S3, unofficial].
3.  **Vertex Shader Classification:** A vertex program performs geometric tests on the input vertices to determine the classification of the cell relative to the view direction [S2, S3, unofficial].
4.  **Basis Graph Mapping:** Based on the classification, map the four vertices to the basis graph topology [S2, S3, unofficial].
5.  **Phantom Vertex Calculation:** Calculate the position of the phantom vertex based on the classification results [S2, S3, unofficial].
6.  **Thickness Interpolation:** Determine the thickness of the cell at the phantom vertex by linearly interpolating the values (e.g., density or scalar field) at the four vertices [S2, S3, unofficial].
7.  **Attribute Assignment:** Assign color and opacity to the phantom vertex using a lookup table indexed by the calculated thickness [S2, S3, unofficial].
8.  **Rasterization and Compositing:** Rasterize the modified faces (triangles formed by the basis graph) and composite them into the framebuffer using hardware blending [S2, S3, unofficial].

**Pseudocode:**
```python
# Vertex Shader Program
def vertex_shader(positions, scalars):
    """
    positions: array of 4 vec3, the vertices of the tetrahedron
    scalars: array of 4 float, the scalar values at the vertices
    Returns: modified positions and scalars for the 5 vertices (4 corners + 1 phantom)
    """
    # 1. Perform geometric tests to classify the tetrahedron
    # This determines the projection order and which faces are visible
    classification = classify_tetrahedron(positions)
    
    # 2. Map vertices to the fixed basis graph topology
    # The basis graph always has 5 vertices: 4 real, 1 phantom
    mapped_positions = map_to_basis_graph(positions, classification)
    
    # 3. Calculate the phantom vertex position
    # The position depends on the classification (e.g., centroid, projection center)
    phantom_pos = calculate_phantom_vertex(mapped_positions, classification)
    
    # 4. Determine thickness at the phantom vertex
    # Linear interpolation of scalar values at the 4 corners
    thickness = interpolate_thickness(scalars, classification)
    
    # 5. Assign color and opacity based on thickness
    # Uses a pre-defined lookup table (transfer function)
    color, opacity = lookup_color_opacity(thickness)
    
    # 6. Return the 5 vertices with updated attributes
    # The first 4 are the mapped corners, the 5th is the phantom
    final_positions = append(mapped_positions, phantom_pos)
    final_scalars = append(scalars, thickness) # Or just pass thickness to fragment shader
    
    return final_positions, final_scalars, color, opacity

# Fragment Shader Program
def fragment_shader(positions, scalars, color, opacity):
    """
    Renders the triangles formed by the basis graph.
    """
    # Standard rasterization and blending

    return blend_into_framebuffer(color, opacity)
```

**Parameters:**
*   **Lookup Table:** Maps thickness (scalar value) to color and opacity. Size depends on the transfer function resolution.
*   **Basis Graph Topology:** Fixed for all cells.

**Edge Cases and Pitfalls:**
*   **Topology Constraints:** Current GPUs cannot change the topology of graphics primitives dynamically. Therefore, the most general topology (the basis graph with 5 vertices) must always be sent, even if the classification results in a simpler geometry [S2, S3, unofficial].
*   **Data Independence:** No data can be saved across vertex primitives. Each primitive must be sent with all relevant data structures, as the GPU does not maintain state between independent draw calls for different tetrahedra [S2, S3, unofficial].
*   **Precision:** Linear interpolation of thickness may introduce approximation errors in regions of high gradient.

## Subtopics

### [Cell Projection with 3D/2D Textures](1996-cell-projection-with-3d-2d-textures.md)
This method extends GPU-based Projected Tetrahedra by pre-computing volume rendering integrals into texture maps, enabling hardware-accelerated compositing of semi-transparent triangles [1996-cell-projection-with-3d-2d-textures.md]. It solves the limitation of standard projected tetrahedra by supporting arbitrary transfer functions via pre-integration, at the cost of increased memory usage for 3D textures or approximation errors for 2D textures. It differs from [Sorted Rasterization of Projected Tetrahedra](3018-sorted-rasterization-of-projected-tetrahedra.md) by relying on texture-based integral approximation rather than explicit sorting of all triangles, and from [On-the-fly Shell Geometry Construction](13927-on-the-fly-shell-geometry-construction.md) by using pre-computed textures instead of dynamic geometry generation.

### [Sorted Rasterization of Projected Tetrahedra](3018-sorted-rasterization-of-projected-tetrahedra.md)
Sorted Rasterization of Projected Tetrahedra is a GPU-based direct volume rendering (DVR) method for unstructured tetrahedral data that achieves interactive rates by treating each tetrahedron as a distinct primitive and rasterizing them using hardware operations. It differs from traditional ray casting by leveraging hardware rasterization and blending to compute pixel color, avoiding explicit per-pixel ray-tetrahedron intersection tests.

### [On-the-fly Shell Geometry Construction](13927-on-the-fly-shell-geometry-construction.md)
On-the-fly shell geometry construction is a method for generating shell geometry (tetrahedrons or prisms) dynamically on the GPU during runtime, enabling shell mapping techniques to be applied to animated surfaces rather than requiring static, offline CPU preprocessing. It differs from traditional shell mapping by eliminating data-dependent preprocessing steps; instead, it uses a deterministic, data-independent rule based on vertex indices to ensure consistency between adjacent prisms, allowing for full parallelization in compute shaders.

### Hardware Caching for Projected Tetrahedra
This variant optimizes the GPU-based PT method by maintaining a buffer holding the four vertices of the current tetrahedron and the additional fifth vertex sometimes created by the algorithm [S4, unofficial]. It swaps the vertices in the buffer as necessary to follow the direction of the strip and caches edge lengths and face areas computed for the current tetrahedron, as these are required by the PT algorithm and are reused by the next tetrahedron in a strip [S4, unofficial]. A pitfall is that computing edge lengths and face areas requires a square root, which impacts running time and complexity [S4, unofficial].

### Bunyk Tetrahedral Projection
A hybrid approach for tetrahedral meshes that projects the complete mesh onto the screen to simplify the problem from 3D to 2D, using precomputed adjacency information for correct accumulation order [S5, unofficial]. The step involves projecting the complete mesh onto the screen [S5, unofficial].

### GPU-based Tetrahedral Projection Code
A method for projecting cells onto the detector, specifically used to simulate the initial set of radiation leaving the hohlraum [S6, unofficial]. It subdivides collapsed cells (single point) and cells with coinciding vertices or nonconvex quadrilateral faces into tetrahedra, and projects remaining hexahedra using the method of Max [S6, unofficial].

## Operating characteristics
*   **Performance:** Capable of rendering over 2.0 million tetrahedra per second (Tet/s) on current graphics hardware [S1, unofficial].
*   **Memory Footprint:** Occupies a substantially smaller memory footprint compared to ray-casting approaches [S1, unofficial].
*   **Pre-processing:** Requires no pre-processing of the data and no additional data structures [S1, unofficial].
*   **Scalability:** Allows interactive viewing of large unstructured datasets on a desktop personal computer [S1, unofficial].
*   **Strengths:** High performance, low memory usage, no pre-processing required, leverages hardware acceleration.
*   **Limitations:** Requires sending the most general topology (basis graph) for all cells, which may involve redundant computation for simple cases; no data persistence across primitives limits optimization strategies that rely on inter-primitive state.

## Background
The method was introduced by Wylie et al. in 2002 as an extension of the Projected Tetrahedra (PT) algorithm [S2, S3, unofficial]. It was designed to leverage the programmable vertex shaders available on commodity graphics cards to perform classification and decomposition of volume cells on the GPU [S2, S3, unofficial]. This shifted the processing burden from the CPU to the GPU, enabling interactive visualization of unstructured data sets [S2, S3, unofficial]. The approach is based on the PT algorithm by Shirley and Tuchman [S2, S3, unofficial].
