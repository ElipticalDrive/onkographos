# Projected Tetrahedra

Also called: PT algorithm, Shirley and Tuchman method, Shirley and Tuchman's algorithm, Shirley and Tuchman's projected tetrahedra, Shirley-Tuchman Method

## Overview
Projected Tetrahedra (PT) is a cell-projection volume rendering technique for unstructured tetrahedral meshes that projects volumetric primitives onto the image plane and composites them in visibility order [S1, unofficial][S4][S6, unofficial]. It solves the problem of rendering non-uniform grids by approximating volume cells with partially transparent polygons that map efficiently to graphics hardware [S7, S8, unofficial]. Unlike ray casting, which operates in image space, PT maintains an object-order nature but requires global visibility sorting of tetrahedra to ensure correct back-to-front compositing [S3, book][S13, unofficial]. It sets itself apart from [Tetrahedral Volume Rendering](820-tetrahedral-volume-rendering.md) by decomposing cells into screen-space triangles rather than casting rays through cells, and from [Marching Tetrahedrons Algorithm](940-marching-tetrahedrons-algorithm.md) by supporting continuous scalar fields with transfer functions rather than discrete isosurfaces [S4][S6, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A tetrahedral mesh $M_T$ where each vertex $V_i$ has a scalar value $s_i$ [S6, unofficial][S10]. The mesh may be derived from subdividing regular lattice cells (e.g., cubes into 5 tetrahedra) [S6, S9, unofficial].
*   **Output:** A 2D image with color and opacity per pixel, composited via the painter's algorithm [S1, unofficial][S4].

**Data Structures:**
*   **Vertex Data:** Each vertex $V_i$ stores 3D coordinates $(x,y,z)$ and a scalar value $s$ [S5, S12]. In hardware implementations, this is often stored in a texture (Vertex Texture) where RGB components hold coordinates and the Alpha component holds $s$ [S5].
*   **Tetrahedron Data:** Each tetrahedron is defined by four vertex indices [S5].
*   **Classification Texture:** A 1D lookup table mapping cross-product test results to projection classes and vertex ordering for triangle fans [S5][S8, unofficial].

**Numbered Steps:**

1.  **Preprocessing (Decomposition):** If the input is a regular grid (e.g., hexahedra), decompose each cell into tetrahedra. For a cube, use 5 tetrahedra. To avoid cracking between adjacent cells, use alternating decomposition orientations (checkerboard pattern) [S6, S9, unofficial]. Ensure consistent vertex ordering (e.g., positive volume) to handle potential inversions [S15, unofficial].
    $$ \text{vol}(T) = \frac{1}{6}(T_a - T_d) \cdot ((T_b - T_d) \times (T_c - T_d)) $$
    where $T_a, T_b, T_c, T_d$ are vertices [S15, unofficial].

2.  **Visibility Sorting:** Sort all tetrahedra front-to-back with respect to the eyepoint. This is a global sort required for correct compositing [S1, unofficial][S3, book]. Common methods include bucket sort (for interactive viewing) or merge sort (for static frames) based on centroid depth [S5]. Note: Sorting is a bottleneck and may fail if tetrahedra form a visibility cycle [S3, book][S13, unofficial].

3.  **Projection and Classification:** For each tetrahedron $T=\{V_0, V_1, V_2, V_3\}$:
    a. Project vertices to screen space: $v_i = \text{proj}(V_i)$ [S5][S8, unofficial].
    b. Compute cross products of projected edges to determine visibility:
       $$ \text{vec1} = v_1 - v_0, \quad \text{vec2} = v_2 - v_0, \quad \text{vec3} = v_3 - v_0 $$
       $$ \text{vec4} = v_1 - v_2, \quad \text{vec5} = v_1 - v_3 $$
       $$ \text{test1} = \text{sign}((\text{vec1} \times \text{vec2}).z) + 1 $$
       $$ \text{test2} = \text{sign}((\text{vec1} \times \text{vec3}).z) + 1 $$
       $$ \text{test3} = \text{sign}((\text{vec2} \times \text{vec3}).z) + 1 $$
       $$ \text{test4} = \text{sign}((\text{vec4} \times \text{vec5}).z) + 1 $$
       where $\text{sign}(x)$ returns $-1, 0, 1$ for $x<0, x=0, x>0$ [S5].
    c. Map tests to one of 14 projection classes (Classes 1-4) using a lookup table [S5][S8, unofficial].
       *   **Class 1:** All 4 faces visible (+ + + +). Decomposes into 3 triangles.
       *   **Class 2:** 3 faces visible, 1 hidden (+ + + -). Decomposes into 4 triangles.
       *   **Class 3/4:** Degenerate cases (vertex on edge or vertex). Handled as zero-area triangles or simplified intersections [S4, S5][S8, unofficial].

4.  **Thick Vertex Computation:** Identify the "thick vertex" $v_t$, the point on the ray segment traversing the maximum distance through the tetrahedron [S4].
    *   For Class 1: $v_t$ is one of the projected vertices (typically the one with the largest depth or specific geometric property) [S4].
    *   For Class 2: $v_t$ is the intersection of the front-facing and back-facing edges [S4][S14, unofficial].
    *   For Class 3/4: $v_t$ is determined by line-line intersections or vertex copying [S5][S14, unofficial].
    *   Compute scalar values at entry ($s_f$) and exit ($s_b$) points of the ray through the tetrahedron. Thin vertices have $s_f = s_b = s_v$ (their scalar value) [S4][S6, unofficial].

5.  **Color and Opacity Assignment:**
    a. Map scalars to color $C(s)$ and extinction coefficient $\tau(s)$ using a transfer function lookup [S4][S6, unofficial].
    b. For thin vertices: Opacity $\alpha = 0$, Color $= C(s_v)$ [S4][S6, unofficial].
    c. For the thick vertex:
       $$ \tau_{\text{avg}} = \frac{\tau(s_f) + \tau(s_b)}{2} $$
       $$ l = \text{thickness} = \text{distance traversed by ray segment} $$
       $$ \alpha = 1 - e^{-\tau_{\text{avg}} l} $$
       $$ C = \text{Average}(C(s_f), C(s_b)) \quad \text{[G: or interpolated based on class]} $$
       [S4, S5]. Note: Some implementations use an approximate formula by Shirley and Tuchman [S10].

6.  **Rasterization:** Render the decomposed triangles (as triangle fans) using hardware rasterization. Interpolate vertex colors and opacities across fragments [S4, S5].

7.  **Compositing:** Composite fragments back-to-front using the painter's algorithm:
    $$ I_{\text{new}} = \alpha C + (1 - \alpha) I $$
    where $I$ is the previous framebuffer color, $C$ is fragment color, and $\alpha$ is fragment opacity [S4, S5].

**Pseudocode:**
```python
def projected_tetrahedra_render(tetrahedra, vertices, view_matrix, proj_matrix, transfer_function):
    # Step 1: Preprocessing (Decomposition)
    # If input is hexahedra, decompose into tetrahedra using alternating pattern to avoid cracks [S9, unofficial]
    mesh = decompose_hexahedra_to_tetrahedra(tetrahedra)
    
    # Step 2: Visibility Sorting
    # Compute centroid depth for each tetrahedron
    centroids = []
    for tet in mesh:
        v0, v1, v2, v3 = tet.vertices
        centroid = (v0 + v1 + v2 + v3) / 4.0
        # Project centroid to view space to get depth
        view_centroid = view_matrix * centroid
        centroids.append((view_centroid.z, tet))
    
    # Sort back-to-front (assuming z increases away from camera or adjust sign)
    # Bucket sort for interactive, Merge sort for static [S5]
    centroids.sort(key=lambda x: x[0], reverse=True)
    sorted_tetrahedra = [item[1] for item in centroids]
    
    # Step 3-5: Project, Classify, Compute Thick Vertex, Assign Color/Opacity
    rendered_primitives = []
    
    for tet in sorted_tetrahedra:
        v0, v1, v2, v3 = tet.vertices
        s0, s1, s2, s3 = tet.scalars
        
        # Project to screen space
        vs = [project_to_screen(v, view_matrix, proj_matrix) for v in [v0, v1, v2, v3]]
        
        # Classification Tests
        vec1 = vs[1] - vs[0]
        vec2 = vs[2] - vs[0]
        vec3 = vs[3] - vs[0]
        vec4 = vs[1] - vs[2]
        vec5 = vs[1] - vs[3]
        
        test1 = sign_z(vec1.cross(vec2)) + 1
        test2 = sign_z(vec1.cross(vec3)) + 1
        test3 = sign_z(vec2.cross(vec3)) + 1
        test4 = sign_z(vec4.cross(vec5)) + 1
        
        # Lookup class and vertex order from Classification Texture/Table [S5]
        class_id, vertex_order = lookup_classification(test1, test2, test3, test4)
        
        # Handle Degenerate Cases (Class 3/4)
        if class_id in [3, 4]:
            # Create zero-area triangles or skip if fully degenerate [S4][S8, unofficial]
            if is_fully_degenerate(vs):
                continue
            # Simplified intersection logic for degenerate cases [S5]
            thick_vertex_idx = determine_thick_vertex_degenerate(vs, class_id)
        else:
            # Class 1 or 2
            thick_vertex_idx = determine_thick_vertex_classic(vs, class_id)
            
        # Compute Thickness l and Entry/Exit Scalars sf, sb
        # l is the distance the ray travels through the tetrahedron [S4]
        # sf, sb are scalar values at entry and exit points [S4]
        l, sf, sb = compute_ray_integral_properties(tet, vs, thick_vertex_idx)
        
        # Assign Colors and Opacities
        # Thin vertices: alpha=0, color=C(sv)
        # Thick vertex: alpha=1-exp(-tau_avg * l), color=avg(C(sf), C(sb))
        tau_sf, tau_sb = transfer_function.get_extinction(sf), transfer_function.get_extinction(sb)
        tau_avg = (tau_sf + tau_sb) / 2.0
        alpha_thick = 1.0 - math.exp(-tau_avg * l)
        color_thick = transfer_function.get_color((sf + sb) / 2.0) # Approximation [S5]
        
        # Build Triangle Fan
        # Vertex order determines the fan structure [S5]
        triangles = build_triangle_fan(vs, vertex_order, thick_vertex_idx)
        
        # Store primitives with attributes
        for tri in triangles:
            # Interpolate attributes for the triangle vertices
            # Note: In hardware, this is done via rasterization interpolation
            primitives.append({
                'vertices': tri,
                'opacities': [0.0, 0.0, 0.0], # Thin vertices have 0 alpha
                'colors': [transfer_function.get_color(s) for s in tet.scalars],
                'thick_alpha': alpha_thick,
                'thick_color': color_thick,
                'is_thick_vertex': [False, False, False] # Mark which vertex is thick
            })
            
    # Step 6-7: Rasterize and Composite
    # Hardware rasterization handles interpolation and back-to-front compositing
    # if depth buffer is disabled and alpha blending is enabled [S4, S5]
    render_primitives_back_to_front(primitives)

def sign_z(cross_product):
    z = cross_product.z
    if z < 0: return -1
    elif z > 0: return 1
    else: return 0

def project_to_screen(vertex, view_matrix, proj_matrix):
    # Standard perspective projection
    clip = proj_matrix * view_matrix * vertex
    if clip.w == 0: return None # Degenerate
    ndc = clip.xyz / clip.w
    return ndc
```

## Subtopics

### [Two-Pass GPU Approach](1339-two-pass-gpu-approach.md)
The Two-Pass GPU Approach is an efficient ray-casting algorithm for tetrahedral meshes implemented on consumer graphics hardware using fragment programs, pre-integration, and multiple rendering passes. It projects tetrahedra into screen space, classifies their geometry, and renders them as triangle fans with interpolated colors and opacities, supporting both volume ray integral and isosurface rendering. It sets itself apart from its parent [Projected Tetrahedra](877-projected-tetrahedra.md) by offloading the heavy projection, classification, and sorting logic to the GPU via a two-pass architecture, thereby reducing CPU–GPU data transfer and enabling interactive frame rates for mid-sized models.

### [Tetrahedral Strips and Fans](1389-tetrahedral-strips-and-fans.md)
Tetrahedral Strips and Fans are specialized rendering primitives designed to reduce the bandwidth bottleneck between main memory and the graphics processor when rendering unstructured tetrahedral meshes. They address the inefficiency of rendering projected tetrahedra as individual triangles or fans by grouping tetrahedra into sequences that share vertices, similar to how triangle strips and fans optimize triangle meshes. Unlike triangle strips, which can be computed statically, tetrahedral decomposition is view-dependent, requiring dynamic generation of these primitives for each frame.

### [Cell Projection of Tetrahedral Meshes (Data Transfer Optimization)](1499-cell-projection-of-tetrahedral-meshes-data-transfer-optimiza.md)
This method addresses the data transfer bottleneck between the CPU and the graphics board in unstructured volume visualization by employing a view-independent description of the mesh. It builds a fixed set of data in a preprocessing step that is reused every frame, allowing for caching and pre-compilation of transfer data. Unlike its sibling [Projected Tetrahedra](877-projected-tetrahedra.md), which generates a continuous stream of triangles requiring view-dependent sorting and rendering, this approach pre-defines the geometry to optimize bandwidth usage through OpenGL mechanisms.

### [Point-based Projected Tetrahedra](5527-point-based-projected-tetrahedra.md)
Point-based Projected Tetrahedra (PBVR) is a technique for interactively visualizing large, unstructured tetrahedral meshes by approximating each tetrahedron with a single point primitive. It decouples footprint generation and reshaping from the compositing stage, using hardware shaders to reshape the point into a circle or ellipsoid and composite fragments based on ray-gap distances rather than pre-assigned alpha values. Unlike [Projected Tetrahedra](877-projected-tetrahedra.md), which generates and sorts triangles, PBVR avoids connectivity processing and convolution operations, making it robust against malformed tetrahedra and efficient for sub-pixel elements.

### [Hardware-Assisted Projection](5625-hardware-assisted-projection.md)
Hardware-Assisted Projection is a family of volume rendering techniques that offload the computationally intensive tasks of projection, scan conversion, and compositing to the graphics processing unit (GPU). It solves the performance bottlenecks of CPU-based projected tetrahedra by leveraging the parallel architecture of modern graphics hardware to achieve interactive rendering rates. Unlike traditional raycasting, which operates in image space, these methods maintain the object-order nature of projected tetrahedra but utilize hardware pipelines for rasterization and fragment processing, often eliminating the need for explicit CPU-side sorting or triangle generation.

## Operating characteristics
*   **Time Complexity:** Linear in the number of tetrahedra $N$ for projection and classification [S8, unofficial]. Visibility sorting is $O(N \log N)$ or $O(N)$ with bucket sort [S5].
*   **Memory Complexity:** $O(N)$ for storing tetrahedra and vertex data. GPU implementations use textures to store vertex data, consuming ~20 bytes per tetrahedron [S5].
*   **Measured Performance:** On an nVidia GeForce4 with a Pentium 4 2GHz, the algorithm achieved up to 2.0 M Tets/s [S4, S5]. Rendering times were several seconds for small datasets in early software implementations [S1, unofficial].
*   **Strengths:** No topology information storage required (reducing memory vs ray casting) [S6, unofficial]. Efficient use of hardware rasterization [S8, unofficial]. Supports arbitrary transfer functions [S4].
*   **Limitations:** Global visibility sorting is a major bottleneck and can fail for cyclic overlaps [S3, book][S13, unofficial]. Degenerate tetrahedra (projected to lines) must be handled to avoid artifacts [S5]. Linear interpolation of opacity can cause Mach banding artifacts [S11, book][S14, unofficial].
*   **When to Use:** Interactive visualization of unstructured tetrahedral meshes where transfer function flexibility is needed and visibility sorting overhead is acceptable.
*   **When Not to Use:** Scenes with cyclic visibility dependencies, or when sub-pixel accuracy is critical without additional techniques (e.g., k-buffer) [S5].

## Background
The Projected Tetrahedra algorithm was proposed by Shirley and Tuchman in 1990 [S1, unofficial][S4][S8, unofficial]. It was one of the first algorithms for projecting cells of unstructured grids, addressing the limitations of early graphics hardware [S1, unofficial]. The method was later adapted for GPU implementation using vertex shaders (e.g., Wylie et al.'s GATOR algorithm) and fragment shaders (e.g., Marroquim et al.'s Two-Pass approach) to achieve interactive rates [S4, S5][S8, unofficial]. It is widely used in volume visualization of medical images, geological data, and fluid simulations [S5].
