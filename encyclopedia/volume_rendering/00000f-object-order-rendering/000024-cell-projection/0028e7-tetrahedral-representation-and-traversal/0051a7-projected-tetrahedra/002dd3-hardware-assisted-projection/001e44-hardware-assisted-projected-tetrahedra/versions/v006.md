# Hardware-Assisted Projected Tetrahedra

Also called: CellFast algorithm, Hardware CellFast

## Overview
Hardware-Assisted Projected Tetrahedra (HAPT) is a flexible, highly efficient volume rendering method for unstructured tetrahedral meshes that performs the entire rendering pipeline on the GPU in a single pass [S1, S2, unofficial]. It builds on [Hardware-Assisted Projection](5625-hardware-assisted-projection.md) by streaming sorted tetrahedra as point primitives, decomposing them into triangles in a geometry shader, and evaluating the volume ray integral per fragment using partial pre-integration [S2, unofficial]. Unlike its sibling [Tetrahedral Projection with Partial Pre-integration](1861-tetrahedral-projection-with-partial-pre-integration.md), which requires a two-pass approach with data read-back, HAPT eliminates GPU memory constraints and read-back latency by processing each tetrahedron independently within the rasterization pipeline [S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** An unstructured tetrahedral mesh defined by vertex positions and scalar values. A camera view and a transfer function mapping scalars to color/opacity.
*   **Output:** A 2D image composited via the Porter-Duff "over" operator [S1, unofficial].

**Data Structures:**
*   **Tetrahedron Stream:** Each tetrahedron is represented as a single point primitive sent to the Vertex Shader (VS).
    *   Position: The position of one vertex (e.g., $v_0$).
    *   Texture Coordinates: The positions of the other three vertices ($v_1, v_2, v_3$) [S2, unofficial].
    *   Scalar Value: The scalar value of the position vertex is passed as the $w$ component of the vertex color/attribute [S2, unofficial].
*   **Sorting Buffer:** An array of indices representing the visibility order of tetrahedra, stored in a Vertex Buffer Object (VBO) or GPU buffer [S2, unofficial].

**Algorithm Steps:**

1.  **Visibility Sorting:**
    Sort the tetrahedra back-to-front relative to the camera. This can be done on the CPU or GPU using various algorithms:
    *   *Approximate:* Centroid sorting (fast, low error) [S2, unofficial].
    *   *Exact:* MPVONC (CPU, requires adjacency lists and face normals, high memory cost) [S2, unofficial].
    *   *GPU:* CUDA Quicksort or Bitonic Sort (requires power-of-two array sizes for Bitonic) [S2, unofficial].
    *   *Note:* Centroid sorting is approximate, covering only 1/3 of pixels exactly, but introduces negligible visual error compared to exact methods [S1, unofficial].

2.  **Vertex Shader (VS) Processing:**
    *   Receive the sorted point primitive.
    *   (Optional) Perform an early discard test: if all four vertices map to zero opacity via the transfer function, discard the primitive [S2, unofficial].

3.  **Geometry Shader (GS) Processing:**
    *   **Decomposition:** Decompose the point primitive (representing the tetrahedron) into one to four triangles based on the projection case [S2, unofficial].
    *   **Classification:** Determine the projection case using PTINT's classification strategy. This involves computing four cross products and performing a table lookup to identify the geometry of the projected tetrahedron [S2, unofficial].
    *   **Vertex Attribute Computation:** For each generated triangle vertex, compute:
        *   **Traversal Length ($l$):** The length of the viewing ray segment within the tetrahedron.
        *   **Scalar Front ($s_f$):** The scalar value at the entry point.
        *   **Scalar Back ($s_b$):** The scalar value at the exit point.
    *   **Vertex Typing:**
        *   *Thick Vertex:* The entry point where the ray traverses the maximum distance $l$. If this point is not a original vertex, $s_f$ must be interpolated, and $l$ may need to be computed if it is not an edge length [S2, unofficial].
        *   *Thin Vertices:* The other projected vertices. For these, $s_f = s_b$ (original scalar value) and $l = 0$ [S2, unofficial].
    *   **Encoding:** Store $s_f$, $s_b$, and $l$ as the RGB color components of the vertex attributes to pass to the fragment shader [S2, unofficial].
    *   **Iso-surface Extraction (Optional):** If rendering iso-surfaces, extract the surface within the GS and output one or two triangles with face normals (flat shading) [S2, unofficial].

4.  **Rasterization and Fragment Shader (FS) Processing:**
    *   The rasterizer interpolates $s_f$, $s_b$, and $l$ across the screen-space triangles [S2, unofficial].
    *   **Partial Pre-integration:** For each fragment, compute the ray integral.
        *   Extract color indices from the interpolated $s_f$ and $s_b$ using the transfer function.
        *   Use the interpolated $l$ and the extracted indices to look up pre-computed values from a partial pre-integration table. This table stores the result of the volume ray integral for arbitrary transfer functions but is independent of the specific transfer function used at render time [S2, unofficial].
        *   Compute the final fragment color and opacity [S2, unofficial].

5.  **Compositing:**
    *   Fragments are composited in back-to-front order using the hardware's depth buffer and blending operations [S1, unofficial].

**Pseudocode:**

```python
# Vertex Shader Input: Point primitive with pos, tex_coords (v1,v2,v3), scalar_w
# Geometry Shader Input: Triangle vertices with attributes (sf, sb, l) encoded in RGB

def process_tetrahedron(point_primitive):
    # Extract vertices
    v0 = point_primitive.position
    v1, v2, v3 = point_primitive.texture_coordinates
    scalar_v0 = point_primitive.w
    
    # 1. Classification (PTINT strategy)
    # Compute cross products to determine projection case
    case = classify_projection(v0, v1, v2, v3)
    
    # 2. Decomposition and Attribute Computation
    triangles = []
    
    if case == CLASS_1:
        # Ray-plane intersection for back/front face
        p_interior = ray_plane_intersection(...)
        # Compute l, sf, sb for thick vertex p_interior
        # Thin vertices have l=0, sf=sb=original_scalar
        triangles = decompose_case_1(v0, v1, v2, v3, p_interior)
        
    elif case == CLASS_2:
        # Two line-line intersections
        p_front = line_line_intersection(...)
        p_back = line_line_intersection(...)
        triangles = decompose_case_2(v0, v1, v2, v3, p_front, p_back)
        
    elif case == CLASS_3:
        # One line-line intersection
        p_edge = line_line_intersection(...)
        triangles = decompose_case_3(v0, v1, v2, v3, p_edge)
        
    elif case == CLASS_4:
        # Degenerate case, no new vertices
        triangles = decompose_case_4(v0, v1, v2, v3)
        
    return triangles

def fragment_shader_interpolated(sf, sb, l):
    # sf, sb, l are interpolated per fragment
    # 1. Map scalars to color indices using transfer function
    idx_f = transfer_function_color_index(sf)
    idx_b = transfer_function_color_index(sb)
    
    # 2. Lookup pre-computed partial pre-integration table
    # Table stores integral results for various l and opacity combinations
    # The table is independent of the specific transfer function
    integral_result = pre_integration_table.lookup(l, idx_f, idx_b)
    
    return integral_result.color, integral_result.opacity
```

**Parameters:**
*   **Sorting Method:** Centroid sort (approximate, fast), MPVONC (exact, high memory), CUDA Quicksort (GPU, fast), CUDA Bitonic Sort (GPU, requires power-of-two) [S2, unofficial].
*   **Pre-integration Table:** Pre-computed table for partial pre-integration. Size depends on the number of discrete opacity levels and traversal lengths supported [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Sorting Error:** Centroid sorting is approximate and may invert the order of adjacent tetrahedra. However, visual error is low (avg ~1 RGB unit, max 1.2-5.1% depending on dataset) [S2, unofficial].
*   **MPVONC Memory:** Exact CPU sorting (MPVONC) requires adjacency lists and face normals, increasing CPU memory by ~4x the volume size [S2, unofficial].
*   **Bitonic Sort Limitation:** Requires power-of-two array sizes, necessitating buffer enlargement and potentially slower performance than Quicksort [S2, unofficial].
*   **Iso-surface Normals:** Face normals are used for flat shading. Smooth Phong shading requires adjacency info, which increases memory and reduces performance [S2, unofficial].
*   **Early Discard:** Early discard in VS is only profitable if there are large empty regions, due to texture fetch overhead [S2, unofficial].

## Subtopics

### [Tetrahedral Projection with Partial Pre-integration](1861-tetrahedral-projection-with-partial-pre-integration.md)
A hybrid method that uses pre-integrated optical depth tables. Unlike HAPT, PTINT uses a two-pass approach requiring data read-back, whereas HAPT performs rendering in a single GPU pass.

## Operating characteristics
*   **Time Complexity:** Dominated by sorting and rasterization. Sorting performance varies by method: CUDA Quicksort achieves ~6 M Tet/s [S1, unofficial].
*   **Memory Complexity:** Low GPU memory usage. Tetrahedra are streamed as point primitives, avoiding the need to store the entire volume in GPU memory. This allows rendering of volumes with several million tetrahedra that would fail in HARC or PTINT [S2, unofficial]. CPU memory for MPVONC sorting is ~4x volume size [S2, unofficial].
*   **Performance:**
    *   HAPT (Quicksort) on spx2 (828K tet): 6.11 M Tet/s, 7.4 FPS [S3, unofficial].
    *   HAPT (Quicksort) on torso (1.08M tet): 5.6 FPS, 6.08 M Tet/s [S3, unofficial].
    *   HAPT (Quicksort) on fighter (1.40M tet): 4.2 FPS, 5.83 M Tet/s [S3, unofficial].
    *   HAPT (Quicksort) on turbjet (1.01M tet/frame): 17.5 FPS [S3, unofficial].
    *   Comparison: HAPT is faster than PTINT (2.06 M Tet/s on spx2), GATOR (0.93 M Tet/s on spx2), and HARC (3.82 M Tet/s on spx2) [S3, unofficial].
*   **Strengths:** Single-pass GPU rendering, low GPU memory consumption, support for time-varying data, support for iso-surface extraction, fast sorting.
*   **Limitations:** Approximate sorting (if centroid sort is used), flat shading for iso-surfaces, requires geometry shader support [S3, unofficial].

## Background
HAPT was introduced by André Maximo, Ricardo Marroquim, and Ricardo Farias in 2010, published in the Journal of Computer Graphics Techniques [S3, unofficial]. It is an adaptation of the Projected Tetrahedra (PT) algorithm [ST90] and PTINT [MMFE08], designed to exploit programmable graphics hardware. The method addresses the visibility ordering problem using fast sorting algorithms (CUDA Quicksort) and leverages the GPU's rasterization pipeline for efficient rendering [S3, unofficial]. It is used for direct volume rendering of unstructured datasets such as torso, fighter, and turbulent jet [S3, unofficial].
