# BCC Marching Tetrahedra with Permutation-Based Lookup

Also called: BCC MT with Reference Tetrahedron, GPU BCC Isosurface Extraction

## Overview
This method extracts explicit, connected triangle mesh isosurfaces from Body-Centered Cubic (BCC) volume datasets on a GPU [S1]. It solves the problem of large lookup tables and complex branching in standard Marching Tetrahedra (MT) by using a single reference tetrahedron and applying 3D permutation transformations to handle all six cell types [S1]. Unlike the triangle-soup output of classic MT, this method produces a manifold mesh with shared vertices, enabling efficient downstream applications such as curvature rendering [S1]. It builds on [Tetrahedralization Schemes](10948-tetrahedralization-schemes.md) by defining a specific BCC connectivity and GPU-optimized data structures.

## How it works
**Inputs:**
*   A 3D scalar field $S$ defined on a BCC lattice.
*   An isosurface threshold $T$.
*   The dimensions of the volume grid $(W, H, D)$.

**Outputs:**
*   A Vertex Buffer containing intersection points $P$.
*   An Index Buffer defining the connectivity of triangles.

**Data Structures:**
1.  **Intersection Buffer:** Stores 5-bit keys indicating which edges of a cell intersect the isosurface. The size is dynamic, equal to the number of intersecting cells.
2.  **Reference Lookup Tables:** Stored in GPU Constant Memory.
    *   **Table 3 (Connectivity):** Defines which edges form triangles for each of the 16 possible intersection patterns (5-bit key) for the *Reference Tetrahedron*.
    *   **Table 4 (Reference Edges):** Defines the 6 edges of the reference tetrahedron using Lattice Offsets and Directions.

**Reference Tetrahedron Edges (Table 4):**
The reference tetrahedron has 6 edges. Each edge $e_i$ is defined by a lattice offset $(o_x, o_y, o_z)$ and a direction vector $(d_x, d_y, d_z)$:

| Edge | Lattice Offset | Direction |
| :--- | :--- | :--- |
| e0 | $(0, 0, 0)$ | $(-1, 1, 1)$ |
| e1 | $(-1, 1, 1)$ | $(1, -1, 1)$ |
| e2 | $(0, 0, 2)$ | $(1, 1, -1)$ |
| e3 | $(0, 0, 0)$ | $(1, 1, 1)$ |
| e4 | $(0, 0, 0)$ | $(0, 0, 2)$ |
| e6 | $(-1, 1, 1)$ | $(2, 0, 0)$ |

*Note: The source lists 'e6' as the sixth edge, implying indices 0-5 or 0-6 with one missing label, but explicitly lists 6 entries [S1].*

**Algorithm Steps:**

1.  **Cell Classification and Permutation:**
    The BCC lattice contains 6 distinct cell types. Instead of storing lookup tables for all 6 types, the algorithm stores only the Reference Tetrahedron's connectivity. For any other cell type, the lattice offsets and edge directions from the reference table are transformed using a 3D permutation matrix specific to that cell type [S1]. This permutation aligns the local tetrahedral coordinate system with the global lattice [S1].

2.  **Intersection Detection (Marking Phase):**
    *   Iterate through all BCC cells.
    *   Evaluate the scalar field values at the 4 vertices of the tetrahedron.
    *   Determine the intersection pattern (5-bit key) based on the signs of $(S_i - T)$ for each vertex.
    *   If the pattern indicates intersection, store the 5-bit key in the Intersection Buffer.
    *   *Optimization:* Use space skipping (min/max blocks) to avoid processing empty cells [S1].

3.  **Vertex Buffer Generation:**
    *   Create one thread per entry in the Intersection Buffer.
    *   The thread reads the 5-bit key to determine the specific edge(s) intersecting the isosurface for the reference tetrahedron (using Table 3).
    *   Apply the permutation transformation corresponding to the current cell type to the reference edge's Lattice Offset and Direction [S1].
    *   Calculate the opposite lattice point: $P_{opp} = P_{current} + \text{Transformed Offset} + \text{Transformed Direction}$.
    *   Read scalar values $S_1$ and $S_2$ at the two ends of the intersected edge.
    *   Compute the intersection point $P$ using linear interpolation:
        $$ P = V_1 + \frac{T - S_1}{S_2 - S_1} (V_2 - V_1) $$
        where $V_1, V_2$ are the positions of the edge endpoints [S1].
    *   Store $P$ in the Vertex Buffer.

4.  **Triangle Buffer (Index) Generation:**
    *   Create one thread per intersecting cell.
    *   Determine the cell type and the 5-bit intersection key.
    *   Use the Reference Lookup Table (Table 3) to identify which edges form the triangles for this pattern.
    *   Apply the cell-specific permutation to the edge indices/offsets to map them to the actual lattice edges [S1].
    *   Generate the indices for the triangle vertices using the positions stored in the Vertex Buffer.
    *   Store the indices in the Index Buffer.

**Pseudocode:**

# Constants
NUM_EDGES_REF = 6
# Table 4: Reference Tetrahedron Edges
# Each entry: (lattice_offset_x, lattice_offset_y, lattice_offset_z, dir_x, dir_y, dir_z)
REF_EDGES = [
    (0, 0, 0, -1, 1, 1),   # e0
    (-1, 1, 1, 1, -1, 1),  # e1
    (0, 0, 2, 1, 1, -1),   # e2
    (0, 0, 0, 1, 1, 1),    # e3
    (0, 0, 0, 0, 0, 2),    # e4
    (-1, 1, 1, 2, 0, 0)    # e6
]

# Table 3: Connectivity for Reference Tetrahedron
# Maps 5-bit key (0-31) to a list of edge indices that form triangles
# Note: Exact mapping depends on the specific reference tetrahedron definition in [S1]
# Assuming a standard mapping for demonstration; actual implementation requires Table 3 from source.
REF_CONNECTIVITY = {
    0: [],
    1: [0],
    # ... other keys ...
    31: []
}

# Permutation tables for the 6 BCC cell types
# Each permutation is a 3x3 matrix or a list of 3 vectors representing the new basis
CELL_PERMUTATIONS = [
    # Permutation for Cell Type 0
    [(1, 0, 0), (0, 1, 0), (0, 0, 1)],
    # Permutation for Cell Type 1
    [(0, 1, 0), (0, 0, 1), (1, 0, 0)],
    # ... other 4 permutations ...
]

def apply_permutation(offset, direction, permutation_matrix):
    """
    Applies 3D permutation to lattice offset and direction vectors.
    permutation_matrix is a list of 3 tuples (x, y, z).
    """
    # The permutation transforms the coordinate system.
    # In GPU implementation, this is done via shuffle instructions.
    # Here we simulate the vector transformation.
    new_offset = (
        offset[0] * permutation_matrix[0][0] + offset[1] * permutation_matrix[0][1] + offset[2] * permutation_matrix[0][2],
        offset[0] * permutation_matrix[1][0] + offset[1] * permutation_matrix[1][1] + offset[2] * permutation_matrix[1][2],
        offset[0] * permutation_matrix[2][0] + offset[1] * permutation_matrix[2][1] + offset[2] * permutation_matrix[2][2]
    )
    new_direction = (
        direction[0] * permutation_matrix[0][0] + direction[1] * permutation_matrix[0][1] + direction[2] * permutation_matrix[0][2],
        direction[0] * permutation_matrix[1][0] + direction[1] * permutation_matrix[1][1] + direction[2] * permutation_matrix[1][2],
        direction[0] * permutation_matrix[2][0] + direction[1] * permutation_matrix[2][1] + direction[2] * permutation_matrix[2][2]
    )
    return new_offset, new_direction

def get_edge_direction_from_key(key, cell_type):
    """
    Determines the edge direction for a given intersection key and cell type.
    Uses Reference Connectivity and Permutation.
    """
    # Get edge indices from reference table for this key
    edge_indices = REF_CONNECTIVITY.get(key, [])
    
    # Apply permutation for the specific cell type to get actual lattice edges
    perm = CELL_PERMUTATIONS[cell_type]
    
    actual_edges = []
    for idx in edge_indices:
        if idx < len(REF_EDGES):
            offset, direction = REF_EDGES[idx][:3], REF_EDGES[idx][3:]
            new_offset, new_direction = apply_permutation(offset, direction, perm)
            actual_edges.append((new_offset, new_direction))
            
    return actual_edges

def process_vertex_thread(intersection_entry):
    """
    Thread function for Vertex Buffer Generation.
    intersection_entry contains: cell_coords, cell_type, intersection_key
    """
    cell_coords = intersection_entry.coords
    cell_type = intersection_entry.cell_type
    key = intersection_entry.key
    
    edges = get_edge_direction_from_key(key, cell_type)
    
    vertices = []
    for offset, direction in edges:
        # Calculate opposite lattice point
        # Note: The source says "Add the edge direction to the current lattice point coordinates 
        # to find the opposite lattice point" after applying permutation to offset/direction.
        # The exact formula for the endpoint depends on the specific BCC vertex indexing.
        # Assuming V1 is at cell_coords + offset_base.
        
        # For simplicity, assume we have the scalar values S1 and S2 at the edge endpoints.
        # In a real implementation, these are fetched from the volume texture.
        v1_pos = get_lattice_position(cell_coords, offset) # Implementation detail [G]
        v2_pos = v1_pos + direction # Direction is already permuted
        
        s1 = sample_volume(v1_pos)
        s2 = sample_volume(v2_pos)
        
        # Linear interpolation
        if abs(s2 - s1) > 1e-6:
            t = (T - s1) / (s2 - s1)
            p = v1_pos + t * (v2_pos - v1_pos)
            vertices.append(p)
            
    return vertices

def process_triangle_thread(cell_entry):
    """
    Thread function for Triangle Buffer Generation.
    cell_entry contains: cell_coords, cell_type, intersection_key
    """
    cell_type = cell_entry.cell_type
    key = cell_entry.key
    
    # Get connectivity edges for this key in the reference tetrahedron
    ref_edge_indices = REF_CONNECTIVITY.get(key, [])
    
    # Apply permutation to get actual edge indices/offsets
    perm = CELL_PERMUTATIONS[cell_type]
    
    # Generate indices for the vertex buffer
    # This requires mapping the calculated intersection points to their positions in the Vertex Buffer
    # The source implies this is done by determining the type of edge/cell and performing different operations [S1]
    
    triangle_indices = []
    for idx in ref_edge_indices:
        # Map reference edge index to vertex buffer index
        # This mapping depends on the order of vertex generation in process_vertex_thread
        # and the permutation applied.
        vertex_idx = get_vertex_index_for_edge(idx, cell_type) # Implementation detail [G]
        triangle_indices.append(vertex_idx)
        
    return triangle_indices

**Parameters:**
*   **Isosurface Threshold $T$:** User-defined.
*   **Memory Allocation:** Pre-allocate a sufficiently large fixed memory space for the triangle mesh, as the mesh size is dynamic and depends on the isosurface shape [S1].

**Edge Cases and Pitfalls:**
*   **Dynamic Mesh Size:** The extracted triangle mesh size varies with the isosurface shape. Pre-calculating the exact size is difficult. For iterative processes (e.g., simulations), pre-allocating a large fixed buffer is more efficient than reallocating every frame [S1].
*   **Space Skipping Ineffectiveness:** The method relies on space skipping (empty space culling). This is ineffective for datasets with high noise or complex isosurfaces with few empty spaces [S1].
*   **GPU Memory Usage:** The method is more complex and requires more GPU memory than existing methods due to the index buffer and permutation logic [S1].

## Operating characteristics
**Time and Memory Complexity:**
*   **Time:** At low resolutions, the method is >2x slower than classic MT due to overhead from creating the triangle mesh structure and low space skipping rates [S1]. At high resolutions, it is significantly faster (up to ~5x) due to high space skipping rates. The time increase with resolution is small [S1].
*   **Memory:** Requires more GPU memory than existing methods due to the index buffer and constant memory for lookup tables [S1].

**Measured Performance:**
*   **Hardware:** Intel Core i5 2500 CPU @ 3.30GHz and NVIDIA GeForce RTX 2080 Ti GPU [S1].
*   **Datasets:** Genus-3 (G1-G5) and Three-Tori (T1-T5) with resolutions ranging from $128^3$ to $1024 \times 512 \times 512$ (Genus-3) and $128^3$ to $512^3$ (Three-Tori) [S1].
*   **Results:** At high resolutions (e.g., G5, T5), the method shows up to ~5x speedup over classic MT [S1].

**Strengths and Limitations:**
*   **Strengths:** Produces a connected manifold mesh with shared vertices, reducing data size and enabling efficient indexing. High performance on high-resolution data with significant empty space.
*   **Limitations:** High memory usage. Ineffective on noisy data or data with complex isosurfaces lacking empty space. More complex implementation than classic MT [S1].

**When to Use:**
*   High-resolution BCC volume data with significant empty space.
*   Applications requiring manifold meshes (e.g., curvature rendering, physics simulation) [S1].

**When Not to Use:**
*   Low-resolution data where overhead dominates.
*   Noisy data or data with complex, space-filling isosurfaces where space skipping is ineffective [S1].

## Background
**Origin:**
The method was proposed in a paper by Korean Computer Graphics Society researchers, published in 2020 [S1]. It aims to provide a real-time GPU technique for extracting mesh isosurfaces from BCC volume datasets.

**History and Development:**
The method builds on the principles of Marching Tetrahedra, specifically adapting them to the BCC lattice structure. It addresses the limitation of large lookup tables in traditional MT by using permutation transformations [S1]. The extracted mesh can be used for curvature rendering, leveraging Griffin's technique to estimate Gaussian curvature on the shared vertices of the triangle mesh [S1].

**Applications:**
*   Curvature rendering (Gaussian curvature estimation) [S1].
*   Real-time visualization of high-resolution BCC volume data.
