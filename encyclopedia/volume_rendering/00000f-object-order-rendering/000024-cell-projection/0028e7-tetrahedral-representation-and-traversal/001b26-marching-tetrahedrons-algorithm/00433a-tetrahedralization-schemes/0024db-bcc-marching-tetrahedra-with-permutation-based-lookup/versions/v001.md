# BCC Marching Tetrahedra with Permutation-Based Lookup

Also called: BCC MT with Reference Tetrahedron, GPU BCC Isosurface Extraction

## Overview
A GPU-based isosurface extraction method for Body-Centered Cubic (BCC) volume datasets that generates an explicit, connected triangle mesh rather than a triangle soup [S1]. It solves the memory and performance overhead of storing large lookup tables for all BCC cell types by using a single reference tetrahedron and applying 3D permutation transformations to handle the remaining five cell types [S1]. Unlike sibling methods that may rely on large static tables or post-processing to connect triangles, this method builds connectivity directly during extraction, enabling efficient applications like curvature rendering [S1].

## How it works
The method extracts isosurfaces from BCC volumes by decomposing cells into tetrahedra, determining intersections, and generating a vertex/index buffer pair. It avoids large lookup tables by storing only the connectivity for one "Reference Tetrahedron" and deriving others via permutation [S1].

### Inputs and Outputs
- **Input**: BCC volume dataset $V$ with resolution $N_x \times N_y \times N_z$; isovalue $I$; pre-allocated GPU memory buffers for vertices and indices [S1].
- **Output**: A connected triangle mesh defined by a Vertex Buffer (positions) and an Index Buffer (triangle connectivity) [S1].

### Data Structures
1.  **Intersection Buffer**: Stores 5-bit keys indicating which edges of a cell are intersected by the isosurface. One entry per cell [S1].
2.  **Triangle Buffer**: Stores information about which triangles are formed. One entry per triangle [S1].
3.  **Reference Tetrahedron Lookup Table**: Stored in GPU Constant Memory. Contains:
    -   **Edge Definitions**: 6 edges defined by lattice offsets and directions (Table 4) [S1].
    -   **Connectivity**: Mapping from 5-bit keys to the specific edges forming triangles (Table 3) [S1].

**Table 4: Six edges of the reference tetrahedron** [S1]

| Edge | Lattice Offset | Direction |
| :--- | :--- | :--- |
| $e_0$ | $(0, 0, 0)$ | $(-1, 1, 1)$ |
| $e_1$ | $(-1, 1, 1)$ | $(1, -1, 1)$ |
| $e_2$ | $(0, 0, 2)$ | $(1, 1, -1)$ |
| $e_3$ | $(0, 0, 0)$ | $(1, 1, 1)$ |
| $e_4$ | $(0, 0, 0)$ | $(0, 0, 2)$ |
| $e_6$ | $(-1, 1, 1)$ | $(2, 0, 0)$ |

*Note: The source lists 6 edges but labels the last one $e_6$ [S1].*

### Permutation Transformation
The BCC lattice contains 6 distinct cell types. Each cell type connected to a lattice point is related by a 3D permutation transformation [S1].
-   **Lattice Offset Permutation**: The lattice offsets from the reference table are permuted to match the current cell type.
-   **Edge Direction Permutation**: The edge directions are similarly permuted [S1].
-   **Implementation**: On GPU, the `shuffle` function (e.g., in OpenCL) is used to perform these permutations efficiently without branching [S1].

### Algorithm Steps

1.  **Space Skipping (Pre-processing)**:
    -   Identify empty blocks (cells where all vertices are on the same side of the isovalue) and skip them. This step is ineffective for high-noise datasets or complex isosurfaces with few empty spaces [S1].

2.  **Intersection Detection (Marking Step)**:
    -   For each non-empty cell, determine which edges intersect the isosurface.
    -   Store the result as a 5-bit key in the Intersection Buffer. The key value ranges from 0 to 31, corresponding to the 5-bit binary representation of intersected edges [S1].
    -   *Note: The source mentions a "5-bit key value from the intersection buffer" but does not explicitly detail the edge-to-bit mapping in the provided text, only that it is used to look up edge directions from Table 2a (not provided in notes) [S1].*

3.  **Vertex Buffer Generation**:
    -   Launch one thread per intersection point (or per edge in the intersection buffer).
    -   **Determine Edge Type**: Use the 5-bit key to look up the edge direction from the reference table (Table 2a/Reference Table) [S1].
    -   **Find Opposite Point**: Add the edge direction to the current lattice point coordinates to find the opposite lattice point of the edge [S1].
    -   **Sample Data**: Read volume data values $V_{start}$ and $V_{end}$ at both ends of the edge [S1].
    -   **Interpolate**: Calculate the intersection position $P$ using linear interpolation:
        $$ P = P_{start} + \frac{I - V_{start}}{V_{end} - V_{start}} (P_{end} - P_{start}) $$
        where $I$ is the isovalue, $P_{start}$ and $P_{end}$ are the lattice coordinates of the edge endpoints [S1].
    -   **Store**: Write $P$ to the Vertex Buffer [S1].

4.  **Triangle Buffer Generation**:
    -   Launch one thread per edge/cell to determine triangle connectivity.
    -   **Determine Cell Type**: Identify the type of the edge/cell being processed. This requires applying the permutation transformation to determine the local cell configuration relative to the reference tetrahedron [S1].
    -   **Lookup Connectivity**: Use the 5-bit key and the determined cell type to look up the connectivity structure from the Reference Tetrahedron Lookup Table (Table 3) [S1].
    -   **Generate Indices**: Based on the connectivity, generate the indices for the triangles formed by the intersected edges. Store these in the Index Buffer [S1].
    -   *Note: Unlike the marking step, this step processes one edge/cell per thread and must handle different operations based on the specific type, requiring the permutation logic [S1].*

### Parameters
-   **Isosurface Value ($I$)**: Scalar threshold for extraction.
-   **Memory Allocation**: Pre-allocate a sufficiently large fixed-size memory space for the triangle mesh. The mesh size is dynamic and depends on the isosurface shape, making pre-calculation difficult [S1].

### Edge Cases and Pitfalls
-   **Dynamic Mesh Size**: The number of triangles varies with the isosurface. Pre-allocating a large fixed buffer is recommended over per-frame reallocation for iterative processes like simulations [S1].
-   **High Noise/Complexity**: Space skipping is ineffective if the dataset has high noise or if the isosurface is complex with few empty spaces. Performance gains diminish in these cases [S1].
-   **Memory Usage**: The method requires more GPU memory than existing triangle-soup methods due to the index buffer and lookup tables [S1].
-   **Lookup Table Size**: Storing separate tables for all 6 cell types would be too large; the permutation approach is essential to keep memory low [S1].

## Operating characteristics
-   **Time Complexity**: Low resolution: >2x slower than classic Marching Tetrahedra (MT) due to overhead from mesh structure creation and low space skipping rates. High resolution: Up to ~5x faster than classic MT due to high space skipping rates. The time increase with resolution is small [S1].
-   **Memory Complexity**: Higher than triangle-soup methods due to the need for an Index Buffer and Constant Memory for lookup tables. Pre-allocation of a large fixed buffer is recommended [S1].
-   **Hardware**: Tested on Intel Core i5 2500 CPU and NVIDIA GeForce RTX 2080 Ti GPU [S1].
-   **Performance Data**:
    -   Datasets: Genus-3 (G1-G5) and Three-Tori (T1-T5) [S1].
    -   Resolutions:
        -   Genus-3: $256 \times 128 \times 128$ to $1024 \times 512 \times 512$ [S1].
        -   Three-Tori: $128^3$ to $512^3$ [S1].
    -   At high resolutions (e.g., G5, T5), the method shows significant speedup (~5x) over classic MT [S1].
-   **Strengths**:
    -   Generates a connected mesh with shared vertices, reducing data size and enabling efficient indexing [S1].
    -   Efficient for high-resolution datasets with significant empty space [S1].
    -   Enables direct applications like curvature rendering (e.g., Griffin's technique) due to shared vertex structure [S1].
-   **Limitations**:
    -   More complex implementation than classic MT [S1].
    -   Higher GPU memory usage [S1].
    -   Space skipping is ineffective for high-noise or complex isosurfaces with few empty spaces [S1].
-   **When to Use**: High-resolution BCC volume datasets with significant empty space where a connected mesh is required for downstream processing (e.g., curvature analysis).
-   **When Not to Use**: Low-resolution datasets, high-noise datasets, or datasets with complex isosurfaces lacking empty space, where space skipping provides little benefit and overhead dominates.

## Background
The method was proposed in a 2020 paper by Korean Computer and Graphics Society researchers [S1]. It addresses the limitations of classic MT, which produces triangle soups that are inefficient for certain rendering techniques and require post-processing for connectivity. By leveraging the regular pattern of BCC tetrahedral decomposition and permutation transformations, it achieves real-time performance on GPUs while maintaining mesh connectivity [S1]. The extracted mesh has been demonstrated for curvature rendering using Griffin's technique [S1].
