# Cell Projection with Scan-line Conversion

Also called: Irregular grid cell projection, Parallel Software Scan Conversion / Cell Projection, Wilhelms et al. Cell Projection with Scan-line Conversion, Y-bucket scan conversion

## Overview
Cell Projection with Scan-line Conversion is a software-based direct volume rendering method for irregular and multiple grids that uses Y-bucket sorting and scanline generation to leverage spatial coherence, avoiding expensive graphics hardware while handling unstructured tetrahedral and curvilinear grids [S1][S2, unofficial]. It sets itself apart from its siblings by relying on software scan-line accumulation rather than hardware rasterization or texture mapping, producing clearer images with fewer artifacts than hardware Gouraud shading methods, though it is slower [S1].

## How it works
The method projects volumetric primitives onto the image plane and accumulates color and opacity front-to-back using scan-line conversion.

**Inputs and Outputs:**
- Input: Volumetric grid data (tetrahedral or curvilinear), camera parameters (viewpoint, projection type), transfer functions (scalar to color $RGB$ and differential opacity $\kappa$).
- Output: Image buffer with accumulated color and opacity.

**Data Structures:**
1.  **Triangle List:** Each volumetric primitive is decomposed into triangles. For a hexahedron, this results in twelve triangles [S2, unofficial].
2.  **Y-Bucket Lists:** A list of lists, where each bucket corresponds to a scan-line (y-coordinate). Each bucket contains triangles that first appear on that scan-line.
3.  **X-Bucket Lists:** Within each Y-bucket, triangles are further organized or processed to maintain x-order coherence [S2, unofficial].
4.  **Pixel Accumulators:** Per-pixel storage for color ($C$) and opacity ($\alpha$), initialized to $(0, 0)$ [S2, unofficial].

**Steps:**
1.  **Decomposition:** Decompose each volumetric primitive into triangles based on the grid type [S2, unofficial].
2.  **Projection:** Project the vertices of each triangle onto the image plane. For orthogonal projection, the length $l$ of the viewing ray segment within the cell varies linearly across the polygon. For perspective projection, screen-space depth $z_s$ is a linear function of eye-space depth $z_e$ ($z_s = c_i + h_i z_e$), but segment length $l$ varies nonlinearly [S1].
3.  **Bucket Population:** Populate the Y-bucket lists with triangles, assigning each triangle to the bucket corresponding to its minimum y-coordinate (scan-line) [S2, unofficial].
4.  **Scan-line Conversion:** Iterate through each scan-line $y$ from top to bottom:
    a. Retrieve triangles from the Y-bucket for $y$.
    b. For each triangle, determine the intersection intervals with the current scan-line.
    c. Sort the intervals by x-coordinate to maintain front-to-back order relative to the viewer (approximate depth sorting may be used here [S3, unofficial]).
    d. For each pixel $x$ within an interval, calculate the ray segment length $l$ and average differential opacity $\kappa_{avg}$ for the cell.
    e. Compute integrated opacity $\alpha = 1 - e^{-\kappa_{avg} l}$ [S1, S4, book].
    f. Accumulate color and opacity front-to-back into the pixel buffer [S2, unofficial].
5.  **Hierarchical Culling (Optional):** For distant views, use a kd-tree to merge polygons based on a user-defined threshold. For close views, traverse the original data. The kd-tree also culls invisible regions [S2, unofficial].

**Formulas:**
- Integrated opacity: $\alpha = 1 - e^{-\kappa_{avg} l}$ [S1, S4, book].
- Linear interpolation of $\kappa_{avg}$ and $l$ across polygons is used to avoid derivative discontinuities in $\alpha$ [S1][S2, unofficial].

**Parameters:**
- User-defined threshold for polygon merging in the hierarchical scheme [S2, unofficial].

**Edge Cases and Pitfalls:**
- Non-planar quadrilateral faces can cause "problem faces" where a ray intersects the same face twice, creating "problem cells" with disjoint ray segments. The standard solution is to subdivide problem cells into tetrahedra with planar faces [S4, book].
- Perfect depth order is impossible because cell depth order may change pixel-by-pixel. Approximate depth sorting (sorting by center of gravity) is used to reduce list manipulation cost [S3, unofficial].

## Subtopics

### Approximate Depth Sorting
A sorting scheme to process scan conversion in depth-sorted order to reduce ray-segment list length and manipulation cost, using the depth order of cell centers of gravity [S3, unofficial]. It differs from octree search by being simpler and less costly, avoiding the computational cost of sorting and list manipulation required for near-perfect order [S3, unofficial]. Perfect depth order is impossible because cell depth order may change pixel-by-pixel, and sorting must be recalculated when the viewpoint changes [S3, unofficial]. This approximation does not cause any quality error in the final image [S3, unofficial].

## Operating characteristics
- **Time Complexity:** Software scan conversion is generally faster than ray casting due to coherence, but slower than hardware Gouraud shading [S1]. Rendering times can be significant (e.g., up to one minute for a $512^2$ viewport on an SGI Onyx with four processors) [S2, unofficial].
- **Memory Complexity:** Depends on the grid size and bucket structures. For example, a space shuttle grid takes 33.9 Mbytes for data and 11.3 Mbytes for transformed vertex locations [S1].
- **Strengths:** Produces image quality equivalent to ray casting with fewer artifacts than hardware methods [S1]. Handles irregular and multiple grids effectively [S1].
- **Limitations:** Slower than hardware methods. Not optimized for opaque datasets where ray casting can halt early [S1].
- **When to use:** When high-quality images are needed for irregular grids and hardware acceleration is not available or insufficient.
- **When not to use:** For opaque datasets where ray casting might be faster, or when interactive performance is critical and hardware methods are acceptable [S1].

## Background
The method was developed by Wilhelms et al. in 1996 [S1][S2, unofficial]. It was designed to provide a software-based alternative to hardware volume rendering, leveraging coherence to handle complex grid structures.
