# Cell Projection with Scan-line Conversion

Also called: Cell-by-Cell Method, Upson and Keeler Method, Upson-Keller Method, Y-bucket scan conversion, Z-buffer algorithm for volume

## Overview
Cell Projection with Scan-line Conversion is a software-based object-order rendering algorithm for direct volume rendering on irregular, unstructured, or curvilinear grids [S1][S5, unofficial]. It solves the problem of efficiently rasterizing volumetric primitives by decomposing them into triangles and processing them via scan-line conversion, leveraging spatial coherence between adjacent pixels and scan-lines to avoid expensive graphics hardware limitations of the era [S1][S3][S4, unofficial]. Unlike its siblings, it explicitly manages depth sorting and compositing in software using bucket lists, offering image quality equivalent to ray casting with fewer artifacts than hardware Gouraud shading, though it is generally slower than hardware-accelerated variants [S1][S5, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A volumetric dataset represented as a grid (tetrahedral, hexahedral, or curvilinear) with scalar values at vertices; a camera view (model-view-projection matrix); transfer functions mapping scalar values to color and opacity.
*   **Output:** A 2D image with accumulated color and opacity per pixel.

**Data Structures:**
1.  **Triangle List:** Each volumetric cell is decomposed into triangles. For a hexahedron, this results in 12 triangles (2 per face) [S2, unofficial][S3][S5, unofficial].
2.  **Y-Bucket Lists:** A list of lists, where each bucket corresponds to a scan-line (y-coordinate). Each bucket contains triangles that intersect that scan-line.
3.  **X-Bucket Lists (or Active Edge List):** Within a scan-line, triangles are sorted by their x-intercepts to determine span boundaries.
4.  **Frame Buffer:** Stores accumulated color and opacity for each pixel.

**Numbered Steps:**

1.  **Decomposition:** Decompose each volumetric primitive into triangles. For a hexahedron, decompose each of the 6 faces into 2 triangles, yielding 12 triangles per cell [S2, unofficial][S3][S5, unofficial].
2.  **Transformation:** Transform the vertices of each triangle from volume space to screen space using the Model-View-Projection (MVP) matrix [S2, unofficial][S3].
3.  **Culling (Optional):** Use a kd-tree or min-max octree to cull invisible regions or cells that do not intersect the view frustum [S2, unofficial][S3].
4.  **Bucket Sorting (Y-Buckets):** For each triangle, determine the range of scan-lines (y-coordinates) it spans. Add the triangle to the y-bucket lists for each scan-line it intersects [S2, unofficial][S5, unofficial].
5.  **Scan-Line Processing:** Iterate through each scan-line $y$ from top to bottom (or bottom to top, depending on coordinate system):
    a.  **X-Sorting:** For the current scan-line, collect all triangles in the corresponding y-bucket. Sort these triangles based on their x-intercepts with the scan-line to form an active edge list [S2, unofficial].
    b.  **Span Generation:** For each triangle in the active list, calculate the intersection polygon with the scan-line. Break this polygon down into smaller polygons called 'spans' when projected onto the image plane [S5, unofficial].
    c.  **Integration:** For each span (pixel column), integrate the scalar values along the ray segment passing through the triangle. Use tri-linear interpolation of the vertex values to find the average contribution to each pixel in the scan line [S5, unofficial].
    d.  **Compositing:** Accumulate the color and opacity of the span into the frame buffer. This accumulation must be done front-to-back to handle transparency correctly [S2, unofficial][S5, unofficial].
6.  **Iteration:** After processing all spans for a scan-line, move to the next scan-line. After processing all scan-lines for a cell, the next cell is scanned [S5, unofficial].

**Formulas:**
*   **Tri-linear Interpolation:** For a point $P$ inside a hexahedral cell, the scalar value $V(P)$ is calculated by interpolating the 8 vertex values $V_i$ based on the barycentric coordinates or normalized distances along the cell edges [S5, unofficial].
*   **Integration:** The contribution $C$ to a pixel is the integral of the color $c(s)$ and opacity $\alpha(s)$ along the ray segment $s$ within the triangle:
    $$ C = \int_{s_1}^{s_2} c(s) \alpha(s) \prod_{s_1}^{s} (1 - \alpha(t)) dt $$
    In practice, this is approximated by summing discrete samples along the span [S5, unofficial].
*   **Depth Sorting (Approximate):** Cells are sorted by the depth of their center of gravity to reduce ray-segment list length, though perfect depth order is impossible as cell depth order may change pixel-by-pixel [S6, unofficial].

**Parameters:**
*   **Macro-cell Size ($m$):** If using a hierarchical approach, the data set is subdivided into macro-cells of size $m^3$, where $m$ is usually between 4 and 10 [S3].
*   **Resolution:** Variable resolution is achieved by changing the height and width of the output screen [S7, unofficial].

**Edge Cases and Pitfalls:**
*   **Sorting Errors:** Using only the centroids of each face as a sorting criterion may lead to incorrect sorting and visual artifacts [S2, unofficial][S3].
*   **Perspective Distortion:** Accurate depths in perspective viewing require specific calculations to ensure correct integration along the ray [S7, unofficial].
*   **Opaque Data:** The method does not optimize for opaque datasets; ray casting can be faster for opaque data because it can halt early when a pixel becomes opaque [S1].
*   **Performance:** Software scan conversion is slower than hardware-accelerated methods but produces clearer images with fewer artifacts [S1].

**Pseudocode:**
```python
def cell_projection_scanline(volume_data, camera, transfer_function):
    # 1. Decompose volume into triangles
    triangles = []
    for cell in volume_data.cells:
        triangles.extend(decompose_into_triangles(cell))
        
    # 2. Transform vertices to screen space
    for tri in triangles:
        tri.vertices = [camera.project(v) for v in tri.vertices]
        
    # 3. Build Y-Bucket Lists
    y_buckets = {}
    for tri in triangles:
        y_min = min(v.y for v in tri.vertices)
        y_max = max(v.y for v in tri.vertices)
        for y in range(int(y_min), int(y_max) + 1):
            if y not in y_buckets:
                y_buckets[y] = []
            y_buckets[y].append(tri)
            
    # 4. Process each scan-line
    for y, tris in y_buckets.items():
        # Sort triangles by x-intercept at this y
        tris.sort(key=lambda t: t.x_intercept(y))
        
        # Process spans for each triangle
        for tri in tris:
            spans = get_spans(tri, y)
            for span in spans:
                # Integrate scalar values along the span
                color, opacity = integrate_span(span, volume_data, transfer_function)
                
                # Composite front-to-back
                composite_pixel(span.x, y, color, opacity)
                
    return frame_buffer

def decompose_into_triangles(cell):
    # Hexahedron: 6 faces, 2 triangles per face = 12 triangles
    if cell.type == 'hexahedron':
        return decompose_hexahedron(cell)
    elif cell.type == 'tetrahedron':
        return [cell] # Already a tetrahedron, or decompose to 4 triangles if needed
    return []

def integrate_span(span, volume_data, transfer_function):
    # Sample along the span using tri-linear interpolation
    total_color = (0, 0, 0)
    total_opacity = 0
    for sample in span.samples:
        value = volume_data.interpolate(sample)
        color, alpha = transfer_function(value)
        # Front-to-back compositing formula
        # C_out = C_in + (1 - C_in.a) * C_sample * alpha_sample
        # A_out = A_in + (1 - A_in.a) * alpha_sample
        total_color, total_opacity = composite(total_color, total_opacity, color, alpha)
    return total_color, total_opacity
```

## Subtopics

### Approximate Depth Sorting
A sorting scheme to process scan conversion in depth-sorted order to reduce ray-segment list length and manipulation cost, using the depth order of cell centers of gravity [S6, unofficial]. Perfect depth order is impossible because cell depth order may change pixel-by-pixel, and sorting must be recalculated when the viewpoint changes [S6, unofficial]. This approximation does not cause any quality error in the final image but is simpler and less costly than octree search, avoiding the computational cost of sorting and list manipulation required for near-perfect order [S6, unofficial].

### Scan-line algorithm for volume rendering of multiple curvilinear grids
A volume rendering technique based on a scan-line algorithm with depth sorting that handles any connected grid, including multiple non-convex intersecting curvilinear grids, designed to run in parallel on a MIMD architecture [S7, unofficial]. Scan conversion and compositing are performed in software, eliminating the need for special graphics hardware and avoiding artifacts associated with graphics hardware [S7, unofficial]. The algorithm includes a solution for rendering accurate depths in perspective viewing [S7, unofficial]. Variable resolution is achieved by changing the height and width of the output screen [S7, unofficial]. It is compared against cell projection with respect to time and accuracy [S7, unofficial].

## Operating characteristics
*   **Time Complexity:** Generally slower than hardware-accelerated methods due to software scan conversion and sorting overhead [S1]. Performance depends on the number of triangles and the coherence between scan-lines [S1].
*   **Memory Complexity:** Requires storage for the triangle list, y-bucket lists, and frame buffer. The size of the transformed vertex locations can be significant (e.g., 11.3 Mbytes for a space shuttle grid) [S1].
*   **Measured Performance:** An average frame rate of 0.8 fps was reported with an image resolution of 512 × 512 pixels on a single PIV 1.9 GHz processor [S3]. Interactive rendering of mid-sized models is possible with 2 to 5 fps on more powerful hardware (e.g., SGI Onyx with four processors) [S3].
*   **Strengths:** Produces image quality equivalent to ray casting with fewer artifacts than hardware Gouraud shading methods [S1]. Handles irregular and multiple grids effectively [S1]. Can be parallelized (e.g., distributing cells round-robin-like among nodes) [S3].
*   **Limitations:** Slower than hardware-accelerated variants [S1]. Not optimized for opaque datasets where ray casting can halt early [S1]. Requires careful handling of depth sorting to avoid artifacts [S2, unofficial][S3].
*   **When to Use:** When high-quality rendering of irregular/unstructured grids is required and hardware acceleration is not available or insufficient [S1]. When software-based control over compositing is needed [S7, unofficial].
*   **When Not to Use:** For real-time rendering of large regular grids where hardware acceleration is preferred [S1]. For opaque datasets where ray casting can provide early termination [S1].

## Background
The method originated as an early software implementation based on projection, proposed by Lucas [Luc92], who sorted projected faces using the Painter’s Algorithm [S3]. Wilhelms et al. [WGTG96] improved this by using software scan conversion with y- and x-bucket lists to leverage coherence between adjacent pixels and scan-lines [S2, unofficial][S3]. Williams et al. [WMS98] developed an elaborate system based on projection, analytically solving the rendering equation for high-quality images [S3]. The method is also associated with Upson and Keeler [UK88], who presented a ray casting method and a projection method using transfer functions [S5, unofficial]. It has been extended to handle curvilinear grids [S3][S7, unofficial] and parallelized for distributed rendering [S3].
