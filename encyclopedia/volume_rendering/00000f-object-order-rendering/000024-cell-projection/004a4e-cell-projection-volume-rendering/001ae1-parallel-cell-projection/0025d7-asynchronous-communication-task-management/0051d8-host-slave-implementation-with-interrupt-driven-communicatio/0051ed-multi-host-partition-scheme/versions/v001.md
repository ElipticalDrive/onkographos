# Multi-Host Partition Scheme

Also called: Hybrid Host-Slave/Symmetry Partition

## Overview
The Multi-Host Partition Scheme is a parallel volume rendering strategy that divides processing nodes into independent groups, each containing one host and multiple slaves, to process subsets of volume slices [S1, unofficial]. It solves the load imbalance and I/O bottlenecks of pure symmetry partitions and the single-host computing bottleneck of pure host-slave schemes by allowing dynamically reassigning idle nodes from finished groups to busy ones [S1, unofficial].

## How it works
**Inputs and Outputs**
- **Input:** A set of $N$ processing nodes and a volume dataset defined by a sequence of slices.
- **Output:** The rendered image and the total count of generated polygons.

**Data Structures**
The system maintains a logical grouping of nodes.
- **Group:** A collection of nodes consisting of exactly one host and $k$ slaves.
- **Slice Assignment:** Each group is assigned a specific subset of slices from the volume.
- **Boundary Overlap:** To ensure correct rendering at group boundaries, the slice subsets of adjacent groups overlap at their edges [S1, unofficial].

**Parameters**
- **Group Size:** In the reported implementation, each group consists of 8 nodes (1 host, 7 slaves) [S1, unofficial].
- **Threshold:** A group broadcasts a "full" status when it has less than half a slice of work remaining [S1, unofficial].

**Algorithm Steps**
1.  **Initialization:** Divide all $N$ nodes into $G$ groups. Each group $g_i$ contains one host node $H_i$ and several slave nodes $S_{i,1} \dots S_{i,k}$.
2.  **Slice Allocation:** Assign a disjoint subset of slices to each group. Ensure that the boundary slices of every group are overlapped with adjacent groups to provide proper boundary conditions for volume calculation [S1, unofficial].
3.  **Independent Processing:** Each group processes its assigned slices independently using the Host-Slave Implementation with Interrupt-Driven Communication [S1, unofficial]. There is no synchronization between groups during processing.
4.  **Progress Broadcasting:** When a group finishes processing a slice, its host broadcasts a message to all other group hosts. This allows every group to maintain an awareness of the remaining work in other groups [S1, unofficial].
5.  **Capacity Broadcasting:** When a group has only half a slice of work remaining, its host broadcasts a message to other group hosts indicating that the group is nearly full. This prevents other groups from reassigning nodes to it [S1, unofficial].
6.  **Completion and Reassignment:**
    - When a group finishes all its assigned slices, its host sends the total amount of calculated polygons to a designated specific node (for final aggregation) and registers that the group is done [S1, unofficial].
    - The nodes of the finished group are re-assigned as slave nodes to other unfinished groups. The number of nodes assigned to a target group is proportional to the unfinished work load of that target group [S1, unofficial].
    - The host of the receiving group sends messages to other group hosts to inform them of the new slaves [S1, unofficial].
7.  **Cleanup:** The very last group host to finish performs cleanup: it obtains the total amount of generated polygons from the designated node and releases all nodes [S1, unofficial].

**Pseudocode**
```python
# Global state
nodes = [Node(i) for i in range(N)]
groups = []
# Initialize groups: 1 host, k slaves per group
# Assume N is divisible by (k+1)
group_size = k + 1
num_groups = N // group_size

for i in range(num_groups):
    host = nodes[i * group_size]
    slaves = nodes[i * group_size + 1 : (i + 1) * group_size]
    groups.append(Group(host=host, slaves=slaves))

# Assign slices to groups with boundary overlap
# Let total_slices be the total number of slices in the volume
# Let overlap be the number of boundary slices shared with neighbors
slices_per_group = total_slices // num_groups
for i, group in enumerate(groups):
    start_idx = i * slices_per_group
    end_idx = (i + 1) * slices_per_group
    # Add overlap to handle boundary conditions
    group.slices = get_slice_subset(start_idx, end_idx, overlap)

# Each group runs its own host-slave loop
# This is a simplified representation of the distributed logic
def run_group(group, all_hosts):
    host = group.host
    slaves = group.slaves
    
    # Process assigned slices
    while group.slices is not empty:
        # Host-Slave processing step
        slice_data = host.read_next_slice()
        host.dispatch_to_slaves(slaves, slice_data)
        host.wait_for_slaves(slaves)
        
        # Broadcast progress to other hosts
        host.broadcast("slice_done", group.id)
        
        # Check if nearly full
        if group.remaining_work < 0.5 * slice_size:
            host.broadcast("nearly_full", group.id)
            
        # Remove processed slice
        group.slices.pop(0)

    # Group finished
    host.broadcast("finished", group.id)
    host.send_polygon_count_to_designated_node()
    
    # Attempt to reassign slaves
    # This logic is distributed; the host of the *receiving* group accepts slaves
    # The host of the *finished* group sends slaves to other hosts
    for other_host in all_hosts:
        if other_host.id != host.id and not other_host.is_full():
            # Calculate proportional assignment
            num_slaves_to_send = calculate_proportional_assignment(group.slaves, other_host.remaining_work)
            assigned_slaves = group.slaves[:num_slaves_to_send]
            
            # Send assignment message
            other_host.receive_slaves(assigned_slaves, host.id)
            
            # Remove assigned slaves from this group
            group.slaves = group.slaves[num_slaves_to_send:]
            
            # Inform other hosts about the new slaves
            other_host.broadcast("new_slaves_assigned", other_host.id, assigned_slaves)

    # Discard remaining slaves to avoid deadlock
    # These become orphans
    for orphan in group.slaves:
        orphan.status = "orphan"
        orphan.stop()

# Main execution
all_hosts = [g.host for g in groups]
for group in groups:
    start_thread(run_group, group, all_hosts)

# Wait for all threads
join_all_threads()

# Cleanup by last host
last_host = find_last_host_to_finish()
last_host.collect_polygon_counts()
last_host.release_all_nodes()
```

**Edge Cases and Pitfalls**
- **Deadlock:** In message-passing systems (e.g., Intel iPSC), communication delays can cause two finished groups to reassign their nodes to each other simultaneously, resulting in deadlock [S1, unofficial].
- **Solution:** Discard newly assigned slave nodes if the receiving group has already finished its work. These discarded nodes become "orphans" with no host and perform no further work [S1, unofficial].
- **I/O Overhead:** Unlike symmetry partitions, this scheme avoids high I/O overhead because each slice is read by only one group (except for the necessary boundary overlaps), preventing redundant reads of compressed data [S1, unofficial].

## Operating characteristics
- **Time Complexity:** The scheme reduces idle time by dynamically balancing load. Without reassignment, the speed/node ratio drops significantly (e.g., from 0.564 to 0.481 for 256 nodes in the reported results) [S1, unofficial]. With reassignment, performance is closer to linear scaling, though slight imbalance remains due to the discrete nature of node reassignment [S1, unofficial].
- **Memory Complexity:** Memory usage is proportional to the number of nodes and the size of the slice subsets assigned to each group. The overlap requires storing boundary slices in adjacent groups' memory buffers [S1, unofficial].
- **Strengths:**
    - Reduces the bottleneck of insufficient host computing power found in single-host schemes by having multiple hosts [S1, unofficial].
    - Avoids the high I/O overhead of symmetry partitions, where slices might be read multiple times or where reading a small region from a compressed slice takes as long as reading the whole slice [S1, unofficial].
    - Provides dynamic load balancing through node reassignment [S1, unofficial].
- **Limitations:**
    - Implementation complexity is higher due to the need for inter-group communication and deadlock avoidance [S1, unofficial].
    - Load imbalance is alleviated but not totally eliminated, especially when there are many groups [S1, unofficial].
    - Extra slave nodes can become a burden for an already busy host if not managed carefully, slightly increasing total processing time as node count grows [S1, unofficial].
- **When to use:** Suitable for large volume datasets where slice processing times vary significantly and the data is stored in compressed form, making symmetry partitions inefficient due to I/O overhead [S1, unofficial].

## Background
The Multi-Host Partition Scheme was introduced in the context of scalar field modeling and visualization on the Intel Delta supercomputer [S1, unofficial]. It was developed to address the limitations of static partitioning strategies (symmetry and host-slave) in distributed memory environments. The scheme is a hybrid approach, combining the simplicity of host-slave models with the parallelism of symmetry partitions, specifically tailored to mitigate the I/O bottlenecks associated with compressed volume data [S1, unofficial].
