# R-Buffer

Also called: Recirculating Fragment Buffer, Wittenbrink's R-Buffer, recirculating buffer

## Overview
The R-Buffer is a hardware architecture proposal for implementing order-independent transparency (OIT) by storing fragments in a large, unordered, recirculating buffer shared across the entire screen, rather than using fixed-size per-pixel buffers [S4, unofficial]. It implements a sorting and compositing method similar to Mammen's software algorithm to handle transparent fragments in front of the front-most opaque one [S1]. Unlike previous hardware implementations that required multiple passes through the geometry, the R-Buffer scan-converts all polygons only once, storing uncomposited fragments in the recirculating buffer for subsequent depth-comparison passes [S3]. It is distinguished from its sibling [Mammen's Technique](1279-mammen-s-technique.md) by moving the sorting logic from software to dedicated hardware logic, and from [k-Buffer](1280-k-buffer.md) by using a single global FIFO buffer instead of fixed-size per-pixel arrays, thereby amortizing storage costs over the screen [S4, unofficial].

## How it works
The R-Buffer operates as a pointerless A-buffer architecture that separates fragment storage from the Z-buffer and frame buffer [S4, unofficial]. It relies on a global recirculating fragment buffer (R-buffer) and a second Z-storage to manage fragments that are neither the closest opaque nor the furthest transparent fragment for a given pixel [S4, unofficial].

### Inputs and Outputs
*   **Input:** A stream of fragments generated by rasterizing geometry (e.g., tetrahedral strips or triangles). Each fragment carries screen coordinates $(X, Y)$, depth $Z$, and color/opacity $(RGBA)$ [S4, unofficial].
*   **Output:** A composited image in the frame buffer with order-independent transparency [S4, unofficial].

### Data Structures
1.  **Frame Buffer:** Stores the accumulated color and opacity of fragments that have been fully composited or are the final opaque fragment [S2, unofficial].
2.  **R-Buffer:** A single, large, circular first-in-first-out (FIFO) queue shared by the entire screen [S4, unofficial]. It stores fragments that require further processing. Each entry in the R-Buffer contains $X, Y, Z$, and $RGBA$ values [S4, unofficial].
3.  **2nd Z-Buffer:** An auxiliary storage used in conjunction with the R-Buffer to assist in depth comparisons [S4, unofficial].

### Algorithm Steps
The rendering process involves two distinct phases: geometry rasterization and fragment recirculation/compositing.

1.  **Rasterization (Single Pass):**
    *   All geometry (e.g., tetrahedra split into triangles) is scan-converted once [S1].
    *   For each generated fragment, the hardware compares its depth $Z$ against the frame buffer's Z-buffer and color buffer [S4, unofficial].
    *   If the fragment is occluded by an opaque fragment in the frame buffer, it is discarded [S4, unofficial].
    *   If the fragment is the closest opaque fragment, it replaces the current frame buffer content [S4, unofficial].
    *   If the fragment is transparent and not occluded, it is sent to the R-Buffer along with its $X, Y, Z$, and $RGBA$ values [S4, unofficial].

2.  **Recirculation and Compositing (Multiple Passes):**
    *   Fragments are retrieved from the R-Buffer in FIFO order [S4, unofficial].
    *   The R-Buffer comparison and control logic performs depth sorting for fragments targeting the same pixel [S4, unofficial].
    *   The two closest fragments to the eye (or the closest fragment and the current frame buffer content) are selected for compositing [S2, unofficial].
    *   **Compositing:** The selected fragments are composited using Porter-Duff operations into the frame buffer [S4, unofficial].
    *   **Recirculation:** Any remaining fragments that were not composited (i.e., those further back in depth) are written back into the R-Buffer [S2, unofficial].
    *   This process repeats until the R-Buffer is empty or an early ray termination condition is met (e.g., accumulated opacity exceeds a threshold) [S2, unofficial].

### Parameters and Edge Cases
*   **k (Buffer Size):** While the R-Buffer is global, the compositing logic often references a "k-buffer" concept where $k$ entries are stored per pixel in the software simulation. In the hardware R-Buffer, $k$ is effectively dynamic and limited by the total R-Buffer size [S2, unofficial].
*   **Holes/Concavities:** Handling holes in the data requires tagging vertices as boundary/internal and k-buffer entries as internal/external. Ray segments with both vertices on the boundary are assigned zero color/opacity [S2, unofficial]. This classification must be dynamically updated, which exceeds current hardware instruction limits in some implementations, leading to improper hole handling in early versions [S2, unofficial].
*   **Screen Position Storage:** To enable per-pixel operations in a global buffer, every fragment must store its original screen position $(X, Y)$ [S5, unofficial]. This increases fragment size compared to per-pixel buffers [S5, unofficial].
*   **Early Ray Termination:** Front-to-back compositing with an adaptive opacity threshold can terminate the sorting process early, limiting the number of layers to be sorted [S4, unofficial].

## Operating characteristics
*   **Time Complexity:** The run time complexity depends on the square of the average depth complexity ($O(D^2)$) [S4, unofficial]. The number of recirculating passes is related to the worst-case depth complexity of any pixel [S4, unofficial].
*   **Memory Complexity:** Memory usage is proportional to the projected area of all faces in the mesh, unlike methods proportional only to the mesh boundary [S1]. Experiments show required memory to be 2.1 to 3.6 times higher than a traditional Z-buffer for detailed CAD models [S4, unofficial]. A factor of 5x frame buffer storage supports an average depth complexity of 10 fragments per pixel [S4, unofficial].
*   **Performance:** On the Phoenix dataset (1022k pixels, depth complexity 27.6), the R-buffer required 66 passes and a total-to-Z bandwidth ratio of 17.4 [S4, unofficial]. On the Head Full dataset (9287k pixels, depth complexity 201.6), it required 475 passes and a ratio of 135.1 [S4, unofficial].
*   **Strengths:** Single pass geometry rasterization; amortized storage cost over the entire screen; handles arbitrary depth complexity without fixed per-pixel limits [S4, unofficial].
*   **Limitations:** High memory overhead for high-depth-complexity scenes; run time increases quadratically with depth complexity; hardware has not been implemented [S1]. Storing screen coordinates in every fragment is a drawback compared to linked-list approaches [S5, unofficial].

## Background
The R-Buffer was proposed by Wittenbrink [S1] as a hardware architecture for rendering tetrahedral primitives, implementing a method similar to Mammen's software algorithm [S1]. It was further developed and simulated by King et al. [S4, unofficial] for unstructured tetrahedral volume rendering. The concept is a pointerless A-buffer hardware architecture [S3]. It was designed to replace per-primitive sorting with per-pixel sorting to handle high depth complexity efficiently in hardware [S4, unofficial].
