# R-Buffer

Also called: Wittenbrink's R-Buffer, Recirculating Fragment Buffer

## Overview
The R-Buffer is a hardware architectural proposal for implementing order-independent transparency (OIT) by storing fragments in a large, unordered, recirculating buffer separate from the Z-buffer and frame buffer [S3, unofficial]. It solves the problem of correctly compositing an arbitrary number of transparent layers per pixel without requiring multiple passes of geometry or per-pixel linked lists [S3, unofficial]. Unlike software-based sorting methods that repeat work for every pixel, the R-buffer amortizes storage costs across the entire screen, allowing fragments to be processed in successive passes until the framebuffer is fully composited [S3, unofficial].

## How it works
The R-buffer implements a fragment-level sorting and compositing mechanism. While originally proposed as dedicated hardware [S1], it is often simulated or approximated in software using Multiple Render Targets (MRT) to store k-buffer entries [S2, unofficial]. The method replaces per-primitive sorting with per-pixel sorting to handle high depth complexity [S3, unofficial].

### Inputs and Outputs
*   **Input:** A stream of fragments generated by rasterizing primitives (e.g., tetrahedra split into triangles). Each fragment carries position ($X, Y, Z$), color ($RGBA$), and scalar data value ($v$) [S3, unofficial].
*   **Output:** A final composited image in the framebuffer with correct order-independent transparency [S3, unofficial].

### Data Structures

**1. Framebuffer**
*   Stores the accumulated color and opacity of fragments that have already been composited and removed from the sorting process [S2, unofficial].
*   Typically stores associated color and opacity [S2, unofficial].

**2. R-Buffer (Recirculating Fragment Buffer)**
*   A circular First-In-First-Out (FIFO) queue shared for the entire screen [S3, unofficial].
*   Stores fragments that are neither the closest opaque fragment nor the furthest transparent fragment in the current framebuffer state [S3, unofficial].
*   **Layout:** Each entry stores $X, Y, Z$ (depth), and $RGBA$ values [S3, unofficial].
*   **Memory Overhead:** Experiments show required memory is 2.1 to 3.6 times higher than a traditional Z-buffer for detailed CAD models [S3, unofficial].

**3. K-Buffer (Hardware Implementation Variant)**
*   In GPU implementations (e.g., using ATI MRT extensions), the R-buffer logic is approximated using a fixed-size "k-buffer" per pixel [S2, unofficial].
*   **Layout:** Each entry consists of a scalar data value $v$ and distance $d$ from the eye [S2, unofficial].
*   **Capacity:** Stores $k$ entries. In the example implementation, $k=3$, allowing the sorting of up to 7 fragments (3 entries + 3 remaining from previous passes + 1 incoming) in a single pass [S2, unofficial].
*   **Tags:** Holes (concavities) can be handled by storing tags as the signs of $v$ and $d$ (internal/external classification) [S2, unofficial].

### Algorithm Steps

The process involves a single geometry pass followed by multiple recirculation passes until all fragments are composited or discarded.

1.  **Rasterization:** Scan-convert all polygons only once. Fragments are generated with their view-space depth $d$ (calculated in the vertex program and passed to the fragment shader) [S1][S2, unofficial].
2.  **Initial Classification:**
    *   If a fragment is opaque and closer than the current framebuffer depth, it replaces the framebuffer content.
    *   If a fragment is transparent, it is compared against the framebuffer. If it is the closest transparent fragment, it may be stored in the framebuffer (if no opaque exists) or sent to the R-buffer [S3, unofficial].
    *   Fragments not stored in the framebuffer are sent to the R-buffer [S3, unofficial].
3.  **Recirculation Pass (Per Pixel):**
    *   Fetch current entries from the R-buffer (or k-buffer).
    *   Find the two closest fragments to the eye by sorting entries based on stored distance $d$ [S2, unofficial].
    *   Compute the ray segment defined by these two entries.
    *   Look up color and opacity from a 3D pre-integrated texture using the scalar values ($v_1, v_2$) and distance difference ($\Delta d = d_2 - d_1$) of the two closest entries [S2, unofficial].
    *   Composite the resulting color and opacity with the color and opacity from the framebuffer (Porter and Duff compositing) [S2, unofficial][S3, unofficial].
    *   Discard the closest fragment (it has been composited).
    *   Write the remaining entries back into the R-buffer (or k-buffer) for the next pass [S2, unofficial][S3, unofficial].
4.  **Termination:**
    *   The process repeats in successive passes.
    *   Termination occurs when the framebuffer opacity exceeds a threshold (early ray termination) or when the R-buffer is empty [S2, unofficial][S3, unofficial].

### Pseudocode (GPU Fragment Sorter, k=3)

```python
# Inputs:
#   f_new: Incoming fragment with depth d_new, scalar v_new, color c_new
#   k_buffer: Array of 3 entries, each with depth d, scalar v, color c
#   fb: Framebuffer entry with depth d_fb, color c_fb, opacity alpha_fb

# Stage 1: Read Framebuffer
c1 = ReadColorFromFramebuffer()
if c1.is_opaque:
    RETURN # Early termination, opaque fragment occludes all others

# Stage 2: Fetch K-Buffer Entries
f1, f2, f3 = ReadFromKBuffer()

# Combine incoming fragment with k-buffer entries
all_fragments = [f_new, f1, f2, f3]

# Find the closest fragment to the eye (minimum depth)
n1 = FindClosest(all_fragments)
remaining = RemoveFromList(all_fragments, n1)

# Find the second closest fragment from the remaining
n2 = FindClosest(remaining)
r1, r2, r3 = remaining # The rest are written back

# Stage 3: Lookup and Composite
d1 = n1.depth
d2 = n2.depth
v1 = n1.scalar
v2 = n2.scalar

delta_d = d2 - d1

# Look up color/opacity for the segment between n1 and n2
# from a pre-integrated 3D texture
c2 = ReadFromPreIntegratedTexture(v1, v2, delta_d)

# Composite the segment color c2 with the accumulated framebuffer color c1
# Assuming standard front-to-back compositing:
# c_out = c1 * (1 - alpha2) + c2 * alpha2
# alpha_out = alpha1 + alpha2 * (1 - alpha1)
# (Exact formula depends on color representation, e.g., associated vs unassociated)
Composite(c1, c2) into Framebuffer

# Stage 4: Write Back
WriteToKBuffer(r1, r2, r3)
```

### Parameters and Typical Values
*   **k (K-Buffer size):** In the cited implementation, $k=3$ [S2, unofficial].
*   **Framebuffer Resolution:** 512x512 pixels in experimental simulations [S3, unofficial].
*   **Memory Factor:** 2.1 to 3.6 times the Z-buffer size for CAD models; supports average depth complexity of 10 fragments per pixel with 5x framebuffer storage [S3, unofficial].

### Edge Cases and Pitfalls
*   **Holes/Concavities:** Properly handling holes requires dynamic tagging of vertices as boundary/internal and k-buffer entries as internal/external. Ray segments with both vertices on the boundary should have zero color/opacity. However, the logic to update these tags dynamically exceeds current hardware instruction limits in the cited implementation. Consequently, the implementation uses only a single tag for initialization and does not handle holes properly [S2, unofficial].
*   **Hardware Status:** The original R-buffer hardware does not exist; implementations are software simulations or GPU shader approximations [S1].
*   **Performance:** The software version does more work than incremental sorting algorithms (like Wilhelms et al.) because sorts are repeated from scratch independently at each pixel [S1].
*   **Precision:** View-space depth $d$ must be accurately calculated in the vertex program and passed to the fragment stage to ensure correct sorting [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** Run time complexity depends on the average depth complexity squared ($O(D^2)$) [S3, unofficial].
*   **Memory Complexity:** Memory usage is proportional to the projected area of all faces in the mesh, unlike methods proportional only to the boundary [S1]. The R-buffer amortizes this over the screen, requiring 2.1 to 3.6 times the Z-buffer memory for detailed models [S3, unofficial].
*   **Measured Performance:**
    *   **Phoenix Dataset:** 1022k pixels, average depth complexity 27.6, 66 passes, tot/Z bandwidth ratio 17.4 [S3, unofficial].
    *   **Head Full Dataset:** 9287k pixels, average depth complexity 201.6, 475 passes, tot/Z bandwidth ratio 135.1 [S3, unofficial].
*   **Strengths:**
    *   Handles arbitrary depth complexity without fixed limits on transparent layers [S3, unofficial].
    *   Single geometry pass required; no repeated rasterization of primitives [S3, unofficial].
    *   Amortizes storage costs across the entire screen, efficient for irregular grids with varying fragment counts [S3, unofficial].
    *   Unassociated color storage with associated compositing reduces triangle artifacts at model edges [S3, unofficial].
*   **Limitations:**
    *   High memory overhead compared to Z-buffering [S3, unofficial].
    *   Performance degrades significantly with high depth complexity due to quadratic pass count [S3, unofficial].
    *   Current hardware implementations struggle with dynamic hole handling (concavities) [S2, unofficial].
    *   Not suitable for volume rendering where the number of fragments is proportional to the entire mesh surface area rather than just the boundary [S1].

## Background
The R-Buffer was proposed by Wittenbrink as a hardware component for rendering tetrahedral primitives [S1]. It is similar in spirit to Carpenter’s software A-buffer but implements the sorting in hardware to avoid the inefficiencies of Z-buffering (which is a read-modify-write operation and does not perform an actual sort) [S3, unofficial]. The concept was further explored in the context of GPU implementations via the "k-buffer" technique by Callahan et al., which uses Multiple Render Targets to simulate the recirculating buffer behavior [S2, unofficial]. It is primarily associated with unstructured tetrahedral volume rendering and order-independent transparency [S3, unofficial].
