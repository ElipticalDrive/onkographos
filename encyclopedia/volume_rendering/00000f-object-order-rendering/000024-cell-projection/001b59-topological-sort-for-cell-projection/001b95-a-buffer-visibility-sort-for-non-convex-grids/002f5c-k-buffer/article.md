# k-buffer

Also called: fixed depth A-buffer, modified A-buffer of fixed depth

## Overview
The k-buffer is a fixed-depth fragment sorting structure used in image-space volume rendering to manage visibility for non-convex grids [S1, unofficial][S4][S5, unofficial]. It acts as a hardware-efficient alternative to the unbounded A-buffer by storing only a constant number $k$ of fragments per pixel, combining incoming fragments with stored ones and discarding the farthest (for front-to-back) or closest (for back-to-front) to manage memory [S2, unofficial][S4]. It is chosen when the fragment stream is approximately sorted (k-nearly sorted), allowing exact visibility sorting on the GPU with $O(n)$ complexity, whereas the unbounded A-buffer requires potentially unbounded memory and the Z-buffer only handles single-layer visibility [S2, unofficial][S4][S5, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A stream of fragments generated by rasterization. Each fragment has a view-space distance $d$, a scalar data value $v$ (e.g., density), and color/opacity. The fragments are assumed to be partially sorted in object space by the CPU [S1, unofficial][S4].
*   **Output:** An accumulated color and opacity in the framebuffer, and the remaining $k-1$ fragments written back to the k-buffer for subsequent processing [S4].

**Data Structures:**
*   **k-buffer:** For each pixel, stores $k$ entries. Each entry contains:
    *   $d$: Distance of the fragment from the viewpoint (view-space depth) [S2, unofficial][S4].
    *   $v$: Scalar data value associated with the fragment [S4].
    *   *Note:* In the hardware implementation, entries are kept **unsorted** to simplify logic [S4].
*   **Framebuffer:** Stores the accumulated color $c$ and opacity $\alpha$ of the ray segment processed so far [S4].
*   **Preintegrated Texture:** A 3D texture used to look up the color and opacity contribution of a ray segment between two scalar values and distance [S4].

**Parameters:**
*   $k$: The number of fragments stored per pixel. Typical value $k=3$ [S4][S5, unofficial].
*   Threshold: Opacity threshold for early ray termination [S4].

**Algorithm Steps:**
The k-buffer operates as a fragment stream sorter. For each incoming fragment $f_{new}$, the following steps are performed in the fragment shader [S4]:

1.  **Read Accumulated Color:** Read the current accumulated color $c_1$ and opacity from the framebuffer.
2.  **Early Ray Termination:** If $c_1$ is opaque (opacity above threshold), terminate execution for this fragment (discard $f_{new}$) [S4].
3.  **Fetch k-buffer Entries:** Read the current $k$ fragments ($f_1, \dots, f_k$) from the k-buffer buffers [S4].
4.  **Identify Closest Fragments:**
    *   Find the single closest fragment $n_1$ among $f_{new}$ and the $k$ stored entries based on distance $d$ [S4].
    *   Identify the remaining fragments $r_1, \dots, r_{k-1}$ (excluding $n_1$) [S4].
    *   Find the second closest fragment $n_2$ among the remaining fragments $r_1, \dots, r_{k-1}$ [S4].
5.  **Compute Segment Properties:**
    *   Let $d_1$ be the depth of $n_1$ and $d_2$ be the depth of $n_2$ [S4].
    *   Let $v_1$ be the scalar value of $n_1$ and $v_2$ be the scalar value of $n_2$ [S4].
    *   Compute the distance $d = d_2 - d_1$ [S4].
6.  **Lookup Contribution:** Read the color $c_2$ and opacity $\alpha_2$ from the preintegrated texture using $v_1, v_2,$ and $d$ [S4].
7.  **Composite:** Composite $c_2$ and $\alpha_2$ into the framebuffer color $c_1$ [S4].
8.  **Update k-buffer:** Write the remaining fragments $r_1, \dots, r_{k-1}$ back into the k-buffer [S4].

**Pseudocode:**
> **Unverified code.** The code below did not pass a test run against a reference implementation, or no test fits it, so it may contain errors.

```python
# GPU-SORT fragment shader logic for k=3
# Inputs: f_new (fragment with distance d_new, scalar v_new)
# Globals: framebuffer (color c1, opacity a1), k_buffer (entries f1, f2, f3)
#          preintegrated_texture (lookup function)

def process_fragment(f_new):
    # Stage 1: Read accumulated color
    c1, a1 = framebuffer.read()
    
    # Early ray termination
    if a1 >= threshold:
        return

    # Stage 2: Fetch k-buffer entries
    f1, f2, f3 = k_buffer.read()
    candidates = [f_new, f1, f2, f3]
    
    # Find closest fragment n1
    n1 = min(candidates, key=lambda f: f.d)
    
    # Identify remaining fragments
    remaining = [f for f in candidates if f != n1]
    
    # Find second closest fragment n2 from remaining
    n2 = min(remaining, key=lambda f: f.d)
    
    # Get properties
    d1 = n1.d
    d2 = n2.d
    v1 = n1.v
    v2 = n2.v
    
    # Compute distance between the two closest fragments
    d = d2 - d1
    
    # Lookup color/opacity for the segment between n1 and n2
    c2, a2 = preintegrated_texture.lookup(v1, v2, d)
    
    # Composite result into framebuffer
    framebuffer.composite(c1, a1, c2, a2)
    
    # Write remaining fragments back to k-buffer
    k_buffer.write(remaining)
```

**Edge Cases and Pitfalls:**
*   **Boundary Cases:** $f_{new}$ may be inserted at the beginning (if closer than all others) or end (if further) of the sorted order. The logic must handle these correctly [S2, S3, unofficial].
*   **Out-of-Order Input:** If the incoming sequence is highly out of order (worse than k-nearly sorted), the output will be incorrect, leading to visible artifacts [S4].
*   **Screen-Space Interpolation:** Projecting vertices to screen to compute 2D texture coordinates for screen-space buffer lookups yields incorrect results due to perspective-correct texture coordinate interpolation. Solution: Compute texture coordinates from the fragment window position or use projective texture mapping [S4].
*   **Read-Write Race Condition:** Simultaneously reading and writing a buffer in the same rendering pass is undefined. Solution: Draw triangles in an order that maximizes distance between fragments of overlapping primitives in the pipeline (e.g., equidistant layers from viewpoint) [S4].
*   **Holes in Data:** Vertices on the boundary must be tagged. Ray segments with both vertices on the boundary are assigned zero color and opacity. A second tag indicates if a k-buffer entry is internal or external. This logic exceeds current hardware capabilities in the original implementation, so holes are not handled properly [S4]. Tags can be stored as the signs of $v$ and $d$ [S4].

## Operating characteristics
*   **Time Complexity:** $O(n)$ to sort a k-nearly sorted sequence of $n$ fragments [S2, S3, unofficial][S4].
*   **Memory Complexity:** Fixed memory per pixel: $k$ entries. For $k=3$, this allows sorting of up to 7 fragments in a single pass (6 entries from k-buffer + 1 incoming fragment) [S4].
*   **Performance:** Achieved rendering rates of over six frames per second for datasets with over 1.4 million cells on tested hardware [S4].
*   **Strengths:** Reduces memory requirement compared to unbounded A-buffer; simple enough to implement on existing graphics architectures; shifts sorting burden to GPU [S1, S2, unofficial][S4].
*   **Limitations:** Less conservative than ZSWEEP; incorrect output if input is highly out of order; limited handling of holes due to hardware instruction limits [S4].
*   **When to Use:** When fragments are partially sorted in object space (k-nearly sorted) and GPU-based visibility sorting is desired [S1, unofficial][S4].
*   **When Not to Use:** When fragments are highly unsorted or when exact handling of holes is required with current hardware limitations [S4].

## Background
The k-buffer was introduced by Steve Silva et al. in the context of Hardware-Assisted Visibility Sorting (HAVS) for unstructured volume rendering [S1, unofficial][S4]. It builds on the A-buffer concept by Carpenter [5] and Danskin and Hanrahan [15], aiming to shift sorting burden to the GPU [S1, unofficial]. The implementation utilized the ATI_draw_buffers OpenGL extension for multiple render targets [S4]. It is a generalized version of the Z-buffer, with classic Z-buffer corresponding to $k=1$ and Z3 buffer to $k=3$ [S5, unofficial].
