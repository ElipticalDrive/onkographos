# k-buffer

Also called: fixed depth A-buffer

## Overview
The k-buffer is a fixed-depth A-buffer used for sorting fragments in image space, introduced to shift the visibility sorting burden from the CPU to the GPU [S1, unofficial]. It serves as a generalized Z-Buffer that allows a limited number of fragments per pixel, enabling correct rendering of non-convex grids and complex volumetric data without requiring a complete, exact visibility sort in object space [S1, unofficial][S2, unofficial]. Unlike the classic Z-buffer which discards fragments behind the closest surface, the k-buffer retains up to $k$ fragments, allowing for accurate layer composition and transparency effects [S2, unofficial].

## How it works
The k-buffer algorithm separates visibility sorting into two distinct phases to balance CPU and GPU workloads [S1, unofficial].

**Inputs and Outputs:**
*   **Input:** A set of primitives (e.g., tetrahedra or cells) with partial visibility ordering established in object space by the CPU; a maximum fragment count $k$ per pixel.
*   **Output:** A sorted list of up to $k$ fragments per pixel, ready for compositing.

**Data Structures:**
The k-buffer is an extension of the A-buffer. For each pixel $(u, v)$, it maintains a list of fragments.
*   **Fragment Structure:** Each fragment stores depth ($z$), color/opacity attributes, and potentially primitive ID.
*   **Buffer Layout:** An array of size $W \times H$ (image dimensions), where each entry points to a linked list or fixed-size array of up to $k$ fragments.
*   **Depth Sorting:** Fragments within the list for a pixel are sorted by depth (typically back-to-front for alpha compositing).

**Algorithm Steps:**
1.  **Partial Object-Space Sort (CPU):** Perform a coarse visibility ordering of primitives. This phase does not guarantee exact visibility order for all fragments during rasterization but reduces the sorting complexity for the GPU [S1, unofficial].
2.  **Rasterization with k-buffer (GPU):**
    *   For each primitive, determine the pixels it covers.
    *   For each covered pixel, compute the fragment's depth $z$ and attributes.
    *   Insert the fragment into the k-buffer for that pixel.
    *   **Insertion Logic:** If the pixel's fragment list has fewer than $k$ entries, add the fragment. If the list is full ($k$ fragments), compare the new fragment's depth with the farthest fragment in the list. If the new fragment is closer (or meets specific composition criteria), replace the farthest fragment or merge it according to the chosen strategy [S2, unofficial].
    *   **Fragment Combination:** Depending on the desired visual effect (e.g., smoke, density), apply strategies for fragment combination and layer composition. This may involve merging overlapping fragments or selecting the most representative ones when the limit $k$ is reached [S2, unofficial].
3.  **Compositing:** Read the sorted fragments from the k-buffer and perform alpha compositing (e.g., over operator) to generate the final pixel color.

**Parameters:**
*   $k$: The maximum number of fragments per pixel.
    *   Classic Z-Buffer: $k=1$ [S2, unofficial].
    *   Z3 Buffer: $k=3$ [S2, unofficial].
    *   Typical values for volume rendering are higher than 1 to capture multiple internal surfaces, but exact typical values are not specified in the sources [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** Depth precision issues may arise if $k$ is large and fragments are very close in depth.
*   **Boundary Conditions:** Handling fragments exactly on pixel boundaries requires consistent rasterization rules.
*   **Degenerate Input:** If primitives are degenerate (zero volume), they may produce no fragments or artifacts.

## Operating characteristics
*   **Time Complexity:** The CPU phase is $O(N \log N)$ or similar depending on the partial sort algorithm. The GPU phase is $O(P \cdot k)$ where $P$ is the number of projected primitives, as each fragment insertion is $O(k)$ or $O(\log k)$ depending on implementation.
*   **Memory Complexity:** $O(W \cdot H \cdot k)$ for the k-buffer storage.
*   **Measured Performance:** Experiments show efficient rendering of datasets with over 1.4 million cells [S1, unofficial]. Performance scales with $k$ and image resolution.
*   **Strengths:** Shifts sorting burden to GPU; handles non-convex grids; robust for dynamic LOD.
*   **Limitations:** Limited by $k$; may miss fragments if $k$ is too small; memory usage increases with $k$.
*   **When to use:** Real-time volume rendering on non-convex grids where exact visibility sort is too expensive.
*   **When not to use:** When exact visibility is critical and $k$ cannot be made large enough, or when memory is severely constrained.

## Background
The k-buffer was introduced by Steve Callahan in his master's thesis, building on previous work by Farias et al., Carpenter, and Danskin and Hanrahan [S1, unofficial]. It was proposed as a contribution to robust LOD rendering systems, aiming to simplify CPU-based processing and leverage GPU programmability for efficient sorting [S1, unofficial]. The concept generalizes the Z-Buffer and Z3 Buffer, allowing for a limited number of fragments per pixel to handle transparency and complex geometry [S2, unofficial].
