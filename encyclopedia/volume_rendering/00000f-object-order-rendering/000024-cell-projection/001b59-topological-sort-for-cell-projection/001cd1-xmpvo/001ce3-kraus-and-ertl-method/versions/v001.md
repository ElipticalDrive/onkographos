# Kraus and Ertl Method

Also called: Cycle handling in MPVO, Hardware compositing for visibility cycles

## Overview
The Kraus and Ertl method is a technique for handling visibility cycles in convex meshes during cell projection volume rendering [S1, S2, unofficial]. It addresses the problem where a global topological sort of cells is impossible due to cyclic visibility dependencies, yet a local sort exists for each pixel center [S1, S2, unofficial]. It sets itself apart from standard MPVO by detecting these cycles and using special hardware compositing methods to scan-convert them, rather than failing or producing artifacts [S1, S2, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A set of convex, non-overlapping cells and their projected images on the screen.
- Output: A correctly sorted and composited image, resolving visibility cycles.

**Data Structures:**
Not given in the sources. The method relies on the basic MPVO sorting algorithm's output to identify cycles.

**Steps:**
1. **Cycle Detection and Isolation:** Apply the basic MPVO sorting algorithm to the cells [S1, S2, unofficial]. The algorithm detects pixels where the cell ordering forms a cycle (i.e., no consistent global order exists) [S1, S2, unofficial]. These pixels and their associated cells are isolated as "cycles" [S1, S2, unofficial].
2. **Hardware Compositing:** For each isolated cycle, use special hardware compositing methods to scan-convert the involved cells [S1, S2, unofficial]. This step resolves the local visibility order for the pixels within the cycle using graphics hardware capabilities [S1, S2, unofficial].

**Pseudocode:**
```python
def kraus_and_ertl_method(cells, screen_resolution):
    # Step 1: Use basic MPVO sorting algorithm to detect and isolate cycles
    # The basic MPVO algorithm returns a sorted list of cells for each pixel,
    # or identifies a cycle if no consistent order exists.
    pixel_cycles = []
    for pixel in screen_resolution:
        sorted_cells = basic_mpvo_sort(cells, pixel)
        if sorted_cells.is_cycle():
            pixel_cycles.append({
                'pixel': pixel,
                'cells': sorted_cells.get_cycle_cells()
            })
    
    # Step 2: Use special hardware compositing methods to scan-convert each cycle
    for cycle in pixel_cycles:
        hardware_composite(cycle['pixel'], cycle['cells'])
    
    # For pixels not in a cycle, standard MPVO compositing is assumed
    for pixel in screen_resolution:
        if not pixel in [c['pixel'] for c in pixel_cycles]:
            sorted_cells = basic_mpvo_sort(cells, pixel)
            standard_composite(pixel, sorted_cells)
```

Not given in the sources.

**Edge Cases and Pitfalls:**
- Rendering costs per cycle increase quadratically in the number of cells involved in the cycle [S1, S2, unofficial].
- The method is designed for convex meshes [S1, S2, unofficial].

## Operating characteristics
- **Time Complexity:** Rendering costs per cycle increase quadratically in the number of cells involved in the cycle [S1, S2, unofficial].
- **Memory Complexity:** Not given in the sources.
- **Strengths:** Handles visibility cycles gracefully for convex non-overlapping cells [S1, S2, unofficial]. For convex non-overlapping cells, there is always a visibility sort for each pixel center even if there is no global visibility sort of the cells [S1, S2, unofficial].
- **Limitations:** Quadratic cost per cycle [S1, S2, unofficial]. Limited to convex meshes in its original form [S1, S2, unofficial].
- **When to use:** When rendering convex meshes with potential visibility cycles where standard MPVO fails.
- **When not to use:** When rendering non-convex meshes without extension (e.g., using SXMPVO) [S1, S2, unofficial]. When performance is critical and cycles are large due to quadratic cost [S1, S2, unofficial].

## Background
The method was introduced by Kraus and Ertl [S1, S2, unofficial]. It is discussed in the context of image-space visibility ordering for cell projection volume rendering of unstructured data [S1, S2, unofficial]. The method could be extended to nonconvex meshes using the SXMPVO algorithm [S1, S2, unofficial].
