# Exact Visibility Ordering for Cell Projection Volume Rendering (SXMPVO)

Also called: SXMPVO (Image-Space Visibility Ordering), SXMPVO algorithm, Scanning Exact MPVO, Scanning Exact Meshed Polyhedra Visibility Ordering

## Overview
SXMPVO is an algorithm that computes image-precision visibility ordering for volume rendering of unstructured meshes by scan-converting exterior faces into an A-Buffer to determine occlusion relations (pseudoneighbor or PN relations) between cells, rather than computing object-precision ray shooting queries [S1][S4, unofficial]. It solves the problem that heuristic methods like MPVO fail for nonconvex meshes because they do not consider ordering relations along viewing rays that cross empty space (ray-gaps) between cells [S3, unofficial]. Unlike its parent method, Topological Sort for Cell Projection, which computes a global topological sort, SXMPVO produces an image identical to one produced by an exact visibility ordering, even though it does not compute a globally exact topological ordering, by using the same image resolution for ordering relations as for volume rendering [S3, unofficial][S4, unofficial]. It differs from [XMPVO](1363-xmpvo.md) by using image-precision scan conversion instead of object-precision ray shooting, and from [BSP-XMPVO](1160-bsp-xmpvo.md) by relying on image-space rasterization rather than a view-independent BSP tree [S1][S4, unofficial][Parent].

## How it works
**Inputs:** An acyclic unstructured mesh (tetrahedral, hexahedral, or "zoo" meshes with mixed cell types) and a viewing direction. The mesh may have nonconvex boundaries and disconnected components. Cells may have nonplanar surfaces provided their edges do not have projections that cross each other ("bow tie" quadrilateral projections) [S1][S3, unofficial][S4, unofficial].

**Outputs:** A directed graph of visibility relations (arrows) between cells, sufficient to perform a depth-first search (DFS) to generate a back-to-front sorting sequence for cell projection volume rendering [S1][S3, unofficial].

**Data Structures:**
1.  **MPVO Data Structures:** As defined in [Topological Sort for Cell Projection](999-topological-sort-for-cell-projection.md). For a tetrahedral mesh, this requires $4f + 14n$ words, where $f$ is the number of interior faces and $n$ is the number of cells [S1][S3, unofficial][S4, unofficial].
2.  **Exterior Face List:** A list holding a record for each exterior face. Each record contains:
    *   A pointer to the face.
    *   A pointer to the cell to which the face belongs.
    *   The face’s centroid (used for sorting).
    *   A next pointer for the list [S1][S3, unofficial][S4, unofficial].
3.  **A-Buffer:** Implemented as an array of pixel (PIX) lists, one per pixel in the screen image. Each PIX list consists of PIX list entry records (PIX entries) [S1][S3, unofficial][S4, unofficial].
    *   **PIX Entry:** Contains:
        *   The distance $z$ from the screen to the intersection point where the ray through pixel $p$ intersects face $f$.
        *   A pointer to face $f$.
        *   A next pointer for the PIX list [S1][S3, unofficial][S4, unofficial].
4.  **PN List:** Every cell has a PN list pointer, initially NULL. The PN list for a cell contains all exterior cells it occludes (its dependencies) [S3, unofficial][S4, unofficial].
    *   **PN Entry:** Contains:
        *   The cell number of the occluded cell.
        *   A next pointer [S3, unofficial][S4, unofficial].

**Parameters:**
*   $n$: Number of cells in the mesh.
*   $b$: Number of exterior cells.
*   $a$: Total area of all exterior faces, measured by the total number of pixels generated in their scan conversion.
*   $w, h$: Image width and height in pixels.
*   Image resolution: The resolution used for computing visibility ordering relations must be the same as that used for the actual volume rendering to ensure image-space correctness [S3, unofficial][S4, unofficial].

**Algorithm Steps:**

1.  **Phase I: Create Partial Ordering (Interior Relations)**
    *   Mark all shared faces with arrows exactly as in MPVO Phase I to determine behind relations from adjacent cells [S1][S3, unofficial][S4, unofficial].
    *   Set a sink cell flag in each cell to true or false as appropriate [S1][S3, unofficial][S4, unofficial].
    *   Create the Exterior Face List.
    *   Complexity: $O(n)$ [S3, unofficial][S4, unofficial].

2.  **Phase II: Sort Exterior Faces**
    *   Sort the exterior faces in the Exterior Face List by increasing distance from the screen to the face's centroid [S1][S3, unofficial][S4, unofficial].
    *   Complexity: $O(b \log b)$ [S3, unofficial][S4, unofficial].

3.  **Phase III: Scan Faces and Add Dependencies (Exterior Relations)**
    *   Create the A-Buffer (array of PIX lists) [S1][S3, unofficial][S4, unofficial].
    *   Remove exterior faces from the sorted queue one at a time and scan-convert their interiors in 3D. For OpenGL, this means sampling at pixel centers [S1][S3, unofficial][S4, unofficial].
    *   For each pixel $p$ of an exterior face $f$ enumerated by scan conversion:
        *   Create a PIX entry containing the distance $z$ from the screen to the intersection point, a pointer to $f$, and a next pointer [S1][S3, unofficial][S4, unofficial].
        *   Insert the PIX entry into the appropriate PIX list in the A-Buffer in order of decreasing $z$. Use an efficient insertion sort. Since faces are sorted by centroid distance, the vast majority of insertions occur at or very near the beginning of the PIX list [S1][S3, unofficial][S4, unofficial].
    *   After rasterizing all exterior faces, process each PIX list:
        *   Discard the first entry of every PIX list (the back-facing face where the ray exits the mesh for the last time, which has no matching front-facing face behind it) [S1][S3, unofficial][S4, unofficial].
        *   If the viewpoint is outside the mesh, discard the last entry (the face where the ray enters the mesh for the first time) [S1][S3, unofficial][S4, unofficial].
    *   Traverse each PIX list. For each pair of consecutive entries (a front-facing face and a back-facing face), there is a "ray-gap". The two cells whose faces make up this pair are pseudoneighbors (PNs) [S3, unofficial][S4, unofficial].
        *   The cell contributing the back-facing face is the **occluding PN**.
        *   The other cell (contributing the front-facing face) is the **occluded PN** [S3, unofficial][S4, unofficial].
    *   For each PN pair:
        *   Check if the PN relation is already recorded in the occluding PN's PN list.
        *   If not, add it to the head of the list. If an entry is found in the list, move it to the head if it is not already there (to exploit coherence and reduce search cost to $O(1)$ in practice) [S3, unofficial][S4, unofficial].
        *   Set the sink cell flag of the occluded PN to false [S3, unofficial][S4, unofficial].
    *   The definition of a sink cell is expanded: a cell is a sink cell if it has no outbound arrows AND is not an occluded PN [S4, unofficial].
    *   Complexity: $O(wh + a)$ for most data sets [S3, unofficial][S4, unofficial].

4.  **Phase IV: Depth First Search (DFS)**
    *   Examine each cell to see which are still marked as sink cells (those whose sink cell flag is still set) [S3, unofficial][S4, unofficial].
    *   Perform a DFS on the directed graph to determine the final visibility order.
    *   Traverse each edge in the directed graph twice.
    *   Occluded neighbors (cells on the PN list of cell $c$) are now eligible neighbors of $c$ in RECURSIVE-DFS [S3, unofficial][S4, unofficial].
    *   Complexity: $O(n + a)$ [S3, unofficial][S4, unofficial].

**Pseudocode:**

```python
def sxmpvo(mesh, image_width, image_height, viewpoint):
    # Phase I: Create Partial Ordering
    # Initialize MPVO structures and mark arrows on shared faces
    # Set sink_cell_flag[c] = True for all cells c
    mpvo_phase_i(mesh)
    
    # Create Exterior Face List
    exterior_face_list = []
    for cell in mesh.cells:
        for face in cell.faces:
            if face.is_exterior:
                exterior_face_list.append({
                    'face': face,
                    'cell': cell,
                    'centroid': face.centroid,
                    'next': None
                })
    
    # Phase II: Sort Exterior Faces
    # Sort by increasing distance from screen to centroid
    exterior_face_list.sort(key=lambda x: distance(viewpoint, x['centroid']))
    
    # Phase III: Scan Faces and Add Dependencies
    # Initialize A-Buffer as array of empty PIX lists
    a_buffer = [[] for _ in range(image_width * image_height)]
    
    for item in exterior_face_list:
        face = item['face']
        # Scan-convert face, sampling at pixel centers
        pixels_covered = scan_convert_face(face, image_width, image_height, viewpoint)
        
        for p in pixels_covered:
            # Calculate z-distance from screen to intersection
            z = ray_face_intersection_z(p, face, viewpoint)
            
            # Create PIX entry
            pix_entry = {
                'z': z,
                'face': face,
                'next': None
            }
            
            # Insert into PIX list in decreasing z order
            pix_list = a_buffer[p.index]
            insert_sorted(pix_list, pix_entry)
            
    # Process PIX lists to find Pseudoneighbors (PNs)
    for pix_list in a_buffer:
        if not pix_list:
            continue
            
        # Discard first entry (back-facing exit)
        pix_list.pop(0)
        
        # If viewpoint is outside mesh, discard last entry (front-facing entry)
        if is_viewpoint_outside_mesh(viewpoint, mesh):
            if pix_list:
                pix_list.pop()
                
        # Traverse remaining entries to find PN pairs
        for i in range(0, len(pix_list) - 1, 2):
            back_face_entry = pix_list[i]
            front_face_entry = pix_list[i+1]
            
            occluding_cell = back_face_entry['face'].owner_cell
            occluded_cell = front_face_entry['face'].owner_cell
            
            # Add PN relation: occluding_cell occludes occluded_cell
            add_pn_relation(occluding_cell, occluded_cell, a_buffer)
            
            # Mark occluded cell as not a sink
            occluded_cell.sink_cell_flag = False
            
    # Phase IV: Depth First Search
    # Find sink cells
    sink_cells = [c for c in mesh.cells if c.sink_cell_flag]
    
    # Perform DFS to generate sort order
    sort_order = []
    visited = set()
    
    def dfs(cell):
        if cell in visited:
            return
        visited.add(cell)
        sort_order.append(cell)
        
        # Traverse edges from shared faces (MPVO arrows)
        for neighbor in cell.mpvo_neighbors:
            dfs(neighbor)
            
        # Traverse edges from PN relations (Phase III)
        for pn_cell in cell.pn_list:
            dfs(pn_cell)
            
    for sink in sink_cells:
        dfs(sink)
        
    return sort_order

def add_pn_relation(occluding_cell, occluded_cell, a_buffer):
    # Check for duplicates in occluding_cell's PN list
    # If not present, add to head. If present, move to head.
    pn_list = occluding_cell.pn_list
    if occluded_cell not in pn_list:
        pn_list.insert(0, occluded_cell)
    else:
        # Move to head for coherence optimization
        pn_list.remove(occluded_cell)
        pn_list.insert(0, occluded_cell)
```

## Operating characteristics
**Time Complexity:** $O(wh + a + n)$ for most data sets, where $w$ and $h$ are image dimensions, $a$ is the projected area (number of pixels scanned), and $n$ is the number of cells [S1][S3, unofficial][S4, unofficial]. The expected cost for data sets seen in practice is $O(wh(\hat{d}_e + 1) + n)$, where $\hat{d}_e$ is the average depth complexity of exterior faces [S1][S3, unofficial].

**Memory Complexity:** $O(wh + a)$ for the A-Buffer (including PIX lists), $O(a)$ for PN lists, plus $O(n)$ for PN list head pointers, and $O(b)$ for the exterior face list [S1][S3, unofficial][S4, unofficial].

**Measured Performance:**
*   On a 250 MHz MIPS R10000 processor, execution times for SXMPVO vary with projected area: 0.32s for 187,395 cells, 0.45s for 450,000 cells, 3.00s for 1,485,000 cells, and 10.85s for 4,500,000 cells [S1][S4, unofficial].
*   On an SGI Power Onyx (R10000 250 MHz), for the helix3.5 data set (3.57 million cells, 375x450 image), SXMPVO uses 3.7 MB for the A-Buffer and 14.5 MB for PN data structures, totaling 367 MB overhead compared to MPVONC's 347.4 MB [S1][S3, unofficial][S4, unofficial].
*   On a 2.53 GHz Pentium 4, SXMPVO achieves a throughput of 500K-600K tetrahedra per second for a 1,050,000 pixel image [S1][S3, unofficial][S4, unofficial].

**Strengths:**
*   Faster than all published algorithms producing exact visibility ordering in object or image space [S1][S3, unofficial][S4, unofficial].
*   Easier to implement than BSP-XMPVO as it does not require implementing a BSP tree, glue code, or handling degeneracies with exact arithmetic [S1][S4, unofficial].
*   Requires no extra preprocessing with respect to MPVO [S1][S3, unofficial][S4, unofficial].
*   Handles nonconvex boundaries, disconnected meshes, cells of different types, and cells with nonplanar surfaces (provided no "bow tie" projections) [S1][S3, unofficial][S4, unofficial].
*   Handles coherence in both x and y because it scan-converts each exterior face as a whole [S3, unofficial][S4, unofficial].

**Limitations:**
*   The mesh must be acyclic for a correct ordering to be found. If a cycle exists, the algorithm reports it [S1][S3, unofficial][S4, unofficial].
*   Tiny cells (those not projecting onto any screen pixels) may be output out of order if they are exterior cells, because the relationship $a <_{vp} b$ is only guaranteed if there is a continuous sequence of adjacent intervening cells. Interior tiny cells are output in correct order [S1][S3, unofficial][S4, unofficial]. Sorting sink cells by increasing distance of their centroid to the viewpoint reduces these errors [S3, unofficial][S4, unofficial].
*   Always slower than MPVONC because it must determine and respect every relationship that MPVONC does, plus create and follow extra relations between exterior faces. However, for data sets with >100,000 cells, SXMPVO generates an exact imagespace visibility ordering at about the same speed as the nonexact MPVONC heuristic [S4, unofficial].
*   Sorting errors may occur for tiny cells if splatting is used for antialiasing [S1][S4, unofficial].

**When to use:** When exact image-space correctness is required for nonconvex unstructured meshes and performance is critical, especially when compared to object-precision methods like XMPVO or BSP-based methods like BSP-XMPVO.

**When not to use:** When the mesh contains cycles (unless cycle detection is the goal), or when tiny cells are rendered using splatting antialiasing without mitigation.

## Background
SXMPVO was introduced by Cláudio T. Silva, João Luiz Dihl Comba, and others as an efficient and exact projection algorithm for unstructured volume rendering [S1][S3, unofficial][S4, unofficial]. It addresses the limitations of MPVO, which fails for nonconvex meshes, and XMPVO, which uses object-precision ray shooting. SXMPVO was designed to provide image-space correctness by leveraging hardware scan conversion and A-Buffer techniques, making it faster and easier to implement than previous exact methods [S1][S3, unofficial][S4, unofficial]. It is used for volume rendering of tetrahedral meshes, zoo meshes, and other unstructured grids [S1][S3, unofficial][S4, unofficial].
