# Sorting-free Pre-integrated Projected Tetrahedra

Also called: Pre-integrated Projected Tetrahedra, Sorting-free approach that controls the fragment rendering by using the opacity value, Sorting-free technique for volume rendering of an irregular volume dataset

## Overview
Sorting-free Pre-integrated Projected Tetrahedra (PBVR) is a stochastic volume rendering technique for irregular volume datasets that eliminates the need for visibility sorting by treating rendering as a probabilistic sampling process [S1]. Unlike conventional projected tetrahedra which require back-to-front sorting to handle transparency, PBVR controls fragment rendering probability based on opacity, allowing semi-transparency to emerge from multiple repetitions without alpha blending [S1]. It builds on [Cell projection](26-cell-projection.md) but replaces deterministic compositing with a stochastic density emitter model to avoid the scalability bottlenecks of sorting in large-scale irregular volumes [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** An irregular volume dataset represented as a set of tetrahedral cells. Each cell contains scalar field values at its vertices. A transfer function mapping scalar values to differential opacity ($\kappa$) and color ($RGB$). Camera parameters (viewpoint, projection).
*   **Output:** A rendered image (brightness/color per pixel).

**Data Structures:**
*   **Tetrahedra:** Defined by 4 vertices in 3D space.
*   **Scalar Field:** Linear interpolation within each tetrahedron.
*   **Pre-integration Texture:** A 2D texture storing the integrated opacity $\alpha$ as a function of segment length $l$ and average differential opacity $\kappa_{avg}$, defined by $\alpha = 1 - e^{-\kappa_{avg} l}$ [S1, S4, book]. This avoids derivative discontinuities from linear interpolation of $\alpha$ [S1, S2].

**Core Concept: Density Emitter Model**
The method models the volume as a distribution of particles. The number of particles in a unit volume follows a Poisson distribution [S1]. The opacity $\tau$ for a ray segment of length $\Delta t$ with particle density $\rho$ is derived from the probability of particle presence:
$$ \tau = 1 - e^{-\rho \cdot \pi r^2 \cdot \Delta t} $$
where $\pi r^2 \rho \Delta t$ represents the expected number of particles in the segment [S1]. In the context of projected tetrahedra, the "particle" concept is abstracted into the opacity value evaluated at the fragment level.

**Algorithm Steps:**
1.  **Pre-computation:** Construct the pre-integration texture for opacity lookup based on the transfer function [S1, S2].
2.  **Projection:** For each tetrahedron, project its vertices onto the image plane. Rasterize the projected faces to generate fragments.
3.  **Opacity Evaluation:** For each fragment, determine the ray segment length $l$ and average differential opacity $\kappa_{avg}$ within the tetrahedron. Use the pre-integration texture to compute the segment opacity $\alpha$ [S1, S2].
4.  **Stochastic Rendering (Repetition Loop):**
    The rendering is repeated $N$ times (repetition level). In each repetition:
    a.  **Fragment Culling:** For each fragment generated by the tetrahedron, generate a random number $r \in [0, 1]$.
    b.  **Probability Test:** If $r > \alpha$ (the opacity of the fragment), discard the fragment. Otherwise, keep it.
    c.  **Color Contribution:** If kept, calculate the brightness contribution. The brightness $B_k$ for a segment is modeled as the expected luminosity. In the stochastic implementation, if the fragment is kept, it contributes its color/brightness value to the pixel accumulator. The specific brightness calculation for a segment with constant luminosity $c_k$ and density $\rho$ is:
        $$ B_k = c_k \times (1 - e^{-\rho \cdot \text{area} \cdot \text{length}}) $$
        [S1]. Note: In the fragment shader implementation, this often simplifies to accumulating the color value weighted by the probability of survival, or simply adding the color if the stochastic test passes, depending on the specific normalization of $c_k$. The source defines the brightness as the expected value [S1].
    d.  **Accumulation:** Add the fragment's color/brightness to the pixel's accumulation buffer.
5.  **Finalization:** After $N$ repetitions, average the accumulated pixel values to produce the final image [S1].

**Pseudocode:**
```python
def render_pbvr(tetrahedra, transfer_function, camera, num_repetitions, image_width, image_height):
    # 1. Pre-compute opacity lookup table
    # alpha_table stores alpha(l, kappa_avg)
    alpha_table = precompute_opacity_table(transfer_function)
    
    # Initialize accumulation buffer
    # Accumulator stores sum of brightness/color values
    accumulator = zeros((image_height, image_width, 3))
    
    # 2. Process each tetrahedron
    for tet in tetrahedra:
        # Project vertices and rasterize to get fragments
        # Each fragment has: screen_coords, l (segment length), kappa_avg, color
        fragments = rasterize_tetrahedron(tet, camera, alpha_table)
        
        for rep in range(num_repetitions):
            for frag in fragments:
                # Stochastic test
                random_val = random_uniform(0, 1)
                
                # If random value is greater than opacity, discard fragment
                if random_val > frag.opacity:
                    continue
                
                # Calculate brightness contribution
                # Based on density emitter model: B = c * (1 - exp(-rho * area * length))
                # In fragment shader context, this is often pre-weighted or simplified.
                # The source indicates brightness is the expected luminosity.
                # We assume frag.color incorporates the luminosity c_k and transfer function.
                # The term (1 - exp(...)) is effectively the opacity alpha.
                # However, the stochastic method treats the fragment as an opaque emitter
                # if it passes the test. The source equation 1 suggests B_k depends on
                # intermediate brightness. For simplicity in stochastic accumulation:
                
                brightness = frag.color # Assuming color is normalized or scaled appropriately
                
                # Accumulate
                accumulator[frag.y, frag.x] += brightness
                
    # 3. Average results
    final_image = accumulator / num_repetitions
    return final_image
```

**Parameters:**
*   **Repetition Level ($N$):** The number of times the rendering loop is executed. Higher $N$ reduces noise/error but increases computation time. Typical values tested: 1, 25, 100, 144 [S1].
*   **Resolution:** Image resolution (e.g., 1024x1024) significantly impacts performance and memory [S1].

**Edge Cases and Pitfalls:**
*   **Precipitous Transfer Functions:** PBVR may generate an insufficient number of particles (fragments) when the density function changes drastically, leading to artifacts compared to Sorted Projected Tetrahedra (SPT) [S1].
*   **Performance Scaling:** Performance is heavily influenced by the number of pixels. Memory consumption increases with image resolution because the number of particles (fragments) scales with pixel count [S1].
*   **Noise:** Low repetition levels result in noisy images. The error decreases with $N$, but convergence is stochastic [S1].

## Operating characteristics
*   **Time Complexity:** The basic brightness calculation without stochastic approximation is $O(n^2)$ if intermediate brightness values are considered [S1]. With stochastic rendering, the cost is proportional to $N \times (\text{Number of Tetrahedra} + \text{Number of Pixels})$ [S1].
*   **Memory Complexity:** Memory usage is influenced by the number of pixels and tetrahedra. It is memory-consuming as image resolution increases the number of particles/fragments [S1]. HAVS requires memory space for sorting cell faces about twice that for tetrahedral cells, whereas PBVR avoids this overhead [S1].
*   **Measured Performance:** On an NVIDIA GeForce 9600GT, PBVR rendered ~10 million particles at 25.7 milliseconds per repetition with 1024x1024 resolution [S1]. For 1024x1024 resolution, the estimated computing time is 1.4 seconds per repetition for larger datasets [S1].
*   **Strengths:**
    *   No visibility sorting required, making it suitable for large-scale irregular volumes distributed across multiple nodes [S1].
    *   Avoids artifacts associated with insufficient k-buffer sizes in hardware-assisted sorting (HAVS) [S1].
    *   Better scalability for very large datasets (>24.5 million tetrahedral cells) compared to HAVS [S1].
*   **Limitations:**
    *   Stochastic noise requires multiple repetitions for high-quality images [S1].
    *   Performance degrades significantly with high image resolutions due to pixel-count dependency [S1].
    *   Struggles with precipitous transfer functions compared to SPT [S1].
*   **When to Use:** Large-scale irregular volumes where visibility sorting is impractical or impossible (e.g., distributed computing environments) and high resolution is not the primary constraint.
*   **When Not to Use:** When real-time performance with high resolution is critical, or when the transfer function has sharp, precipitous changes that require precise sampling (SPT is preferred) [S1].

## Background
*   **Origin:** The method was introduced in the paper "Sorting-free pre-integrated projected tetrahedra" [S1].
*   **History:** It was developed to address the limitations of particle-based volume rendering (visible footprints) and conventional projected tetrahedra (visibility sorting bottlenecks) [S1]. It contrasts with Hardware-Assisted Visibility Sorting (HAVS) and Sorted Projected Tetrahedra (SPT) [S1].
*   **Usage:** Applied to large-scale irregular volumes from CSM and CFD simulations [S1].
