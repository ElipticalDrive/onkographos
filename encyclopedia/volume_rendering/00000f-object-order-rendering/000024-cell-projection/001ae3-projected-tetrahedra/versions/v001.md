# Projected Tetrahedra

Also called: Data Structures for Cell Projection, GPU CP for Int. VR, GPU-Based Cell Projection, Projected Tetrahedra (PT) on GPU, Shirley and Tuchman's projected tetrahedra, Two-GPU Pass Approach, Weiler et al. Rendering, Wylie et al. Rendering

## Overview
Projected Tetrahedra (PT) is a cell-projection volume rendering technique that projects unstructured tetrahedral cells onto the screen as triangle fans, sorting them by depth to ensure correct transparency compositing [S1]. Unlike sibling methods that may rely on vertex shaders or complex auxiliary data structures, this specific GPU implementation uses a two-pass fragment shader approach with texture-based data storage to minimize memory footprint and avoid redundant projections [S1]. It solves the problem of efficiently rendering large unstructured meshes by offloading projection classification and scalar interpolation to the GPU, achieving interactive rates with significantly less memory usage than ray-casting alternatives [S1].

## How it works
### Inputs and Outputs
**Inputs:**
*   Unstructured tetrahedral mesh defined by vertex coordinates and scalar values.
*   Camera view and projection matrices.
*   Transfer function (mapping scalar values to color and extinction coefficient).

**Outputs:**
*   Final composited image with correct transparency.

### Data Structures
The method relies on three primary textures stored in GPU memory [S1]:

1.  **Vertex Texture:** Stores vertex attributes. Each texel is RGBA (32 bits per component).
    *   `RGB`: 3D coordinates $(x, y, z)$ of the vertex.
    *   `A`: Scalar value $s$ associated with the vertex.
2.  **Tetrahedral Texture:** Stores connectivity. Each texel contains four indices (values) used to look up the four vertices of a specific tetrahedron from the Vertex Texture. One texel corresponds to one tetrahedron [S1].
3.  **Classification Texture:** A 1D texture (8 bits per component) containing a ternary truth table. It maps the results of four cross-product tests to the projection class (1–4) and the correct vertex ordering for the triangle fan [S1].

**CPU-side Arrays (for Rendering Pass):**
*   **Vertex Array:** Groups of 5 elements per tetrahedron (1 "thick" vertex + 4 original vertices). Stores coordinates $\{x, y, z\}$.
*   **Color Array:** Groups of 5 elements per tetrahedron. Stores interpolation parameters $\{s_f, s_b, l\}$ rather than final colors. For thin vertices, $s_f = s_b$ and $l=0$.
*   **Indices Array:** Groups of 6 elements per tetrahedron, defining the vertex order for the triangle fan.
*   **Count Array:** Stores the number of vertices in each fan (max 6) [S1].

### Numbered Steps

**Step 1: Projection and Classification (First Fragment Shader Pass)**
1.  Render the Tetrahedral Texture as a full-screen quadrilateral. This ensures one fragment is generated per tetrahedron [S1].
2.  For each fragment (tetrahedron), retrieve the four vertex indices from the Tetrahedral Texture.
3.  Look up the 3D coordinates and scalar values of the four vertices ($v_0, v_1, v_2, v_3$) from the Vertex Texture.
4.  Project the four vertices to screen coordinates.
5.  Compute four cross-product tests to determine the projection class [S1]:
    *   Define vectors:
        $$ \vec{vec1} = v_1 - v_0 $$
        $$ \vec{vec2} = v_2 - v_0 $$
        $$ \vec{vec3} = v_3 - v_0 $$
        $$ \vec{vec4} = v_1 - v_2 $$
        $$ \vec{vec5} = v_1 - v_3 $$
    *   Compute test results $test_i$ for $i \in \{1, 2, 3, 4\}$:
        $$ test_i = \begin{cases} 0 & \text{if } (\vec{cross})_z \le 0 \\ 1 & \text{if } (\vec{cross})_z = 0 \\ 2 & \text{if } (\vec{cross})_z \ge 0 \end{cases} $$
        Specifically:
        $$ test_1 = \text{sign}((\vec{vec1} \times \vec{vec2})_z) + 1 $$
        $$ test_2 = \text{sign}((\vec{vec1} \times \vec{vec3})_z) + 1 $$
        $$ test_3 = \text{sign}((\vec{vec2} \times \vec{vec3})_z) + 1 $$
        $$ test_4 = \text{sign}((\vec{vec4} \times \vec{vec5})_z) + 1 $$
6.  Use the tuple $(test_1, test_2, test_3, test_4)$ to look up the projection class and vertex order in the Classification Texture [S1].
    *   **Class 1:** Produces 3 triangles.
    *   **Class 2:** Produces 4 triangles.
    *   **Class 3:** Degenerate case of Class 1 (one test returns 1).
    *   **Class 4:** Degenerate case of Class 2 (two tests return 1).
    *   **Degenerate (Discard):** If more than two tests return 1, all points are collinear; discard the projection [S1].
7.  Compute the "thick" vertex properties based on the class [S1]:
    *   **Class 2:** The thick vertex $v_t$ is the intersection of the two interior segments. Compute front scalar $s_f$ by interpolating on segment $v_0v_1$ and back scalar $s_b$ on segment $v_2v_3$.
    *   **Class 3:** $s_f = s_{v2}$. Compute $s_b$ by interpolating $s_{v0}$ and $s_{v3}$.
    *   **Class 4:** $s_f = s_{v2}$ and $s_b = s_{v0}$.
8.  Compute the tetrahedron centroid in screen space and extract its $z$-coordinate ($z_c$) for sorting.
9.  Output fragment data to two Multiple Render Targets (MRT) textures [S1]:
    *   **Texture 1:** Intersection vertex coordinates $(x_{vi}, y_{vi})$ (for Class 2), centroid $z_c$, and Ternary Truth Table index $id_{TTT}$.
    *   **Texture 2:** Scalars $s_f, s_b$, thickness $l$, and triangle fan vertex count.

**Step 2: Sorting**
10. Transfer the centroid $z_c$ values to the CPU.
11. Sort tetrahedra in back-to-front order [S1]:
    *   Use **Bucket Sort** (approx. 20 slabs perpendicular to the viewing vector) for dynamic view changes.
    *   Use **Merge Sort** ($O(n \log n)$) for static frames to ensure accuracy [S1].
    *   *Note:* Centroid sorting is an approximation. For perfect accuracy, use MVPO or k-buffer sorting [S1].

**Step 3: Data Preparation**
12. Construct the CPU-side Vertex, Color, Indices, and Count arrays using the data from the MRT textures [S1].
    *   For each tetrahedron, group 5 vertices: 1 thick vertex + 4 original vertices.
    *   Update the thick vertex position and color parameters.
    *   Set thin vertex parameters: $s_f = s_b$ and $l=0$.
    *   Populate the Indices array with the vertex order determined in Step 1.
    *   Populate the Count array with the number of vertices per fan [S1].

**Step 4: Rendering and Compositing (Second Fragment Shader Pass)**
13. Render the primitives using `glMultiDrawElements` with the prepared arrays, invoking the second fragment shader. Primitives are drawn as triangle fans [S1].
14. In the fragment shader, linearly interpolate the vertex parameters $\{s_f, s_b, l\}$ from the three vertices of the current triangle fan fragment [S1].
15. Compute the average scalar $s$:
    $$ s = \frac{s_f + s_b}{2} $$
16. Lookup the final color and extinction coefficient $\tau$ from a 1D Transfer Function texture using $s$ [S1].
17. Compute the opacity $\alpha$ using a 1D texture `Tex1D` pre-computed with $e^{-u}$:
    $$ u = \tau \cdot l $$
    $$ \alpha = \text{Tex1D}(u) = e^{-\tau l} $$
    *(Note: Using a texture lookup for the exponential is faster than computing it in the shader) [S1].*
18. Composite the fragment into the frame buffer in back-to-front order:
    $$ I_{new} = \text{Color} + (1 - \text{Alpha}) \times I $$
    Where $I$ is the previous color in the frame buffer, and Color/Alpha are the interpolated values [S1].

### Pseudocode

```python
# Pass 1: Projection and Classification (Fragment Shader)
def fragment_shader_pass_1(texel_coord):
    # 1. Retrieve tetrahedron indices
    tet_indices = TetrahedralTexture[texel_coord]
    
    # 2. Retrieve vertex data
    v0_data = VertexTexture[tet_indices[0]]
    v1_data = VertexTexture[tet_indices[1]]
    v2_data = VertexTexture[tet_indices[2]]
    v3_data = VertexTexture[tet_indices[3]]
    
    v0 = v0_data.rgb
    v1 = v1_data.rgb
    v2 = v2_data.rgb
    v3 = v3_data.rgb
    
    s0 = v0_data.a
    s1 = v1_data.a
    s2 = v2_data.a
    s3 = v3_data.a
    
    # 3. Project to screen (assuming view/projection matrices are uniforms)
    ps0 = project(v0)
    ps1 = project(v1)
    ps2 = project(v2)
    ps3 = project(v3)
    
    # 4. Compute cross products
    vec1 = ps1 - ps0
    vec2 = ps2 - ps0
    vec3 = ps3 - ps0
    vec4 = ps1 - ps2
    vec5 = ps1 - ps3
    
    cross1 = cross(vec1, vec2)
    cross2 = cross(vec1, vec3)
    cross3 = cross(vec2, vec3)
    cross4 = cross(vec4, vec5)
    
    # 5. Compute test results
    # sign returns -1, 0, 1. We map to 0, 1, 2 as per source definition
    # test_i = sign(cross.z) + 1
    # Note: Source defines: 0 if <=0, 1 if ==0, 2 if >=0. 
    # This implies: sign(-) -> -1 -> 0; sign(0) -> 0 -> 1; sign(+) -> 1 -> 2.
    test1 = sign(cross1.z) + 1
    test2 = sign(cross2.z) + 1
    test3 = sign(cross3.z) + 1
    test4 = sign(cross4.z) + 1
    
    # 6. Check for degenerate (collinear) case
    if (test1 == 1) + (test2 == 1) + (test3 == 1) + (test4 == 1) > 2:
        discard()
        
    # 7. Lookup class and order
    class_info = ClassificationTexture[test1, test2, test3, test4]
    class_id = class_info.class_id
    vertex_order = class_info.vertex_order
    
    # 8. Compute thick vertex properties
    if class_id == 2:
        # Intersection of interior segments
        vt = intersect_segments(ps0, ps1, ps2, ps3) # Simplified logic
        sf = interpolate_scalar(ps0, ps1, vt)
        sb = interpolate_scalar(ps2, ps3, vt)
    elif class_id == 3:
        sf = s2
        sb = interpolate_scalar(s0, s3, ...) # Interpolation on v0-v3
    elif class_id == 4:
        sf = s2
        sb = s0
    else: # Class 1
        # Standard case, thick vertex logic varies
        pass
        
    # 9. Compute centroid z
    centroid = (v0 + v1 + v2 + v3) / 4.0
    centroid_screen = project(centroid)
    zc = centroid_screen.z
    
    # 10. Output to MRTs
    MRT1 = {
        'xvi': vt.x if class_id == 2 else 0,
        'yvi': vt.y if class_id == 2 else 0,
        'zc': zc,
        'idTTT': (test1, test2, test3, test4)
    }
    MRT2 = {
        'sf': sf,
        'sb': sb,
        'l': thickness, # Computed based on geometry
        'count': vertex_order.count
    }
    return MRT1, MRT2

# Pass 2: Rendering (Fragment Shader)
def fragment_shader_pass_2(interpolated_sf, interpolated_sb, interpolated_l):
    # 1. Average scalar
    s = (interpolated_sf + interpolated_sb) / 2.0
    
    # 2. Lookup Color and Tau
    tf_result = TransferFunctionTexture[s]
    Color = tf_result.rgb
    tau = tf_result.a
    
    # 3. Compute Opacity
    u = tau * interpolated_l
    Alpha = ExponentialTexture[u] # Pre-computed e^-u
    
    # 4. Composite
    # I is the current frame buffer color
    I_new = Color + (1 - Alpha) * I
    return I_new
```

### Parameters
*   **Bucket Sort Slabs:** Approximately 20 slabs perpendicular to the viewing vector [S1].
*   **Texture Precision:** 32 bits per component for Vertex and Tetrahedral textures; 8 bits for Classification texture [S1].

### Edge Cases and Pitfalls
*   **Degenerate Tetrahedra:** If more than two cross-product tests return 1, the vertices are projected onto a line. These must be discarded to prevent artifacts [S1].
*   **Sorting Accuracy:** Sorting by centroid is not 100% accurate. For perfect ordering, use Williams’ MVPO or k-buffer sorting [S1].
*   **Perspective Distortion:** In perspective views, linear interpolation of extinction coefficient $\tau$ is an approximation because front and back faces have different perspective distortions. Hardware perspective-correct interpolation is insufficient for the average $\tau$ [S2].
*   **Mach Bands:** Linear interpolation of integrated opacity $\alpha$ across the polygon is not mathematically equivalent to the exponential calculation, potentially causing Mach bands. Using a pre-computed texture for $e^{-\tau l}$ mitigates this [S2].
*   **Non-planar Faces:** Subdividing quadrilateral faces into triangles can cause gaps or overlaps between adjacent cells due to different $z$ interpolations [S2].

## Operating characteristics
*   **Time Complexity:** Sorting is $O(n \log n)$ for merge sort or $O(n)$ for bucket sort (with constant factor for slab assignment). Rendering is $O(n)$ for projection and rasterization. Sorting is identified as a bottleneck [S3].
*   **Memory Complexity:** 20 bytes per tetrahedron (16 bytes for texture elements + overhead for 4 tets/vertex average). This is significantly lower than HARC PPI (96 bytes/tet) or HARC (144 bytes/tet) [S1].
*   **Performance:** Renders over 2.0 M Tet/s on nVidia GeForce 6800 [S1]. Optimized software implementations (Wittenbrink) achieved 15 fps for 12,936 cells and 1 fps for 240,122 cells on older hardware [S3].
*   **Strengths:** Low memory footprint, interactive rates, view-dependent optimization [S1].
*   **Limitations:** Requires sorting (bottleneck), approximation in perspective views, degenerate cases must be handled [S1, S2].

## Background
Projected Tetrahedra was introduced by Shirley and Tuchman as a fast algorithm for unstructured volume visualization [S3]. It generates triangles that can be rendered by hardware acceleration, relying on a view-dependent projection and visibility sort [S3]. The specific GPU-based two-pass fragment shader implementation described here was developed by Marroquim et al. to leverage programmable graphics cards for interactive rendering [S1].
