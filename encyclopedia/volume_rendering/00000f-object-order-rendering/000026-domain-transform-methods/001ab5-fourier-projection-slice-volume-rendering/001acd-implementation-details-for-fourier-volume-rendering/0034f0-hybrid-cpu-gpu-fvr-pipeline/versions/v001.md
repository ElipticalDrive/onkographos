# Hybrid CPU-GPU FVR Pipeline

Also called: Heterogeneous FVR Pipeline, CPU-Computational/GPU-Rendering FVR

## Overview
The Hybrid CPU-GPU FVR Pipeline is a heterogeneous implementation strategy for Fourier Volume Rendering that partitions the computational workload between the CPU and the GPU. The CPU handles the heavy numerical computations, specifically the 3D Fast Fourier Transform (FFT) and resampling, while the GPU handles the rendering context, including texture management, projection-slice extraction via OpenGL, and final display [S1, unofficial]. This approach leverages the hardware-accelerated interpolation and texture handling of OpenGL to simplify the representation of the 3D spectral volume, offering a middle ground between fully CPU-based pipelines and fully GPU-based implementations [S1, unofficial].

## How it works
The pipeline operates by alternating between a CPU computational context and GPU rendering contexts. The process begins on the CPU and concludes on the GPU's on-screen frame buffer.

### Inputs and Outputs
*   **Input:** A 3D volumetric dataset (typically stored as a 3D array on the CPU).
*   **Output:** A 2D reconstructed projection image displayed on the screen.

### Data Structures
1.  **3D Spectral Volume:** A 3D texture object allocated in GPU memory. It stores the frequency spectrum of the input volume.
2.  **Frame Buffer Object (FBO):** An OpenGL object used for off-screen rendering.
3.  **2D Texture (Intermediate):** A 2-component 2D texture attached to the FBO, storing the extracted projection-slice.
4.  **2D Texture (Final):** A 2D texture uploaded to GPU memory containing the final reconstructed image for display.

### Steps
1.  **Load Data:** Load the 3D dataset into CPU memory [S1, unofficial].
2.  **Preprocessing (CPU):**
    *   Perform a spatial shift on the 3D dataset [S1, unofficial].
    *   Compute the forward 3D FFT of the shifted volume to obtain its frequency spectrum [S1, unofficial].
3.  **GPU Context Activation (Off-screen):**
    *   Activate an OpenGL off-screen rendering context [S1, unofficial].
    *   Allocate a 3D OpenGL texture in GPU memory and upload the 3D spectral volume from the CPU to this texture [S1, unofficial].
4.  **Projection-Slice Extraction (GPU):**
    *   Define a proxy quadrant (plane) passing through the origin of the frequency domain [S1, unofficial].
    *   Intersect this proxy quadrant with the 3D spectral texture to extract the projection-slice [S1, unofficial].
    *   Render the intersection result into the Frame Buffer Object (FBO) [S1, unofficial].
    *   Pack the FBO contents into a 2-component 2D texture attached to the FBO [S1, unofficial].
5.  **Data Transfer (GPU to CPU):**
    *   Switch back to the CPU computational context [S1, unofficial].
    *   Download the 2-component 2D texture (containing the projection-slice) from GPU memory to CPU memory [S1, unofficial].
6.  **Resampling (CPU):**
    *   Resample the downloaded projection-slice on the CPU to remove ghosting artifacts [S1, unofficial].
    *   *Note:* This step involves nested loops iterating over slice dimensions and filter kernel weights [S1, unofficial].
7.  **Inverse Transform (CPU):**
    *   Perform an inverse 2D FFT on the resampled slice to produce a shifted image in the spatial domain [S1, unofficial].
    *   Perform a 2D `fft-shift` operation on the image to rearrange it correctly [S1, unofficial].
8.  **Final Upload (CPU to GPU):**
    *   Pack the final reconstructed image into a 2D OpenGL texture [S1, unofficial].
    *   Upload this texture to GPU memory using `glTex2D` [S1, unofficial].
9.  **Display (GPU):**
    *   Activate the on-screen rendering context [S1, unofficial].
    *   Send the final texture to the frame buffer for display [S1, unofficial].

### Edge Cases and Pitfalls
*   **Data Transfer Bottleneck:** The frequent switching between CPU and GPU contexts requires transferring data back and forth. This limits the overall performance to the bandwidth of the communication channel between the CPU and GPU, which is significantly lower than internal GPU bandwidth [S1, unofficial].
*   **Resampling Cost:** The resampling stage is a critical bottleneck. It involves four nested for loops (two for slice dimensions, two for filter kernel). For a projection-slice of size $512 \times 512$, this operation takes considerable time, blocking real-time rendering [S1, unofficial].
*   **3D FFT Latency:** The 3D FFT operation on the CPU (using FFTW) is slow for volumes of size $64^3$ or larger. While executed once during preprocessing, it elongates the pre-processing stage, especially if multiple volumes are processed to reveal depth cues [S1, unofficial].
*   **2D FFT Latency:** The inverse 2D FFT is executed on a per-frame basis. Reducing the time for this operation is crucial for enhancing frame rate [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The 3D FFT is $O(N^3 \log N)$ where $N$ is the volume dimension. The 2D inverse FFT is $O(M^2 \log M)$ where $M$ is the slice dimension. The resampling step is $O(M^2 \cdot K^2)$ where $K$ is the kernel size, making it a significant per-frame cost.
*   **Memory Complexity:** Requires storing the 3D spectral volume in GPU memory and the 2D slice in CPU/GPU memory during transfer.
*   **Performance:** The pipeline lacks interactivity due to bottlenecks in data transfer and CPU-based resampling. The communication channel bandwidth between CPU and GPU is the primary limiting factor for overall performance [S1, unofficial].
*   **Strengths:** Easier to handle than a full CPU-based pipeline due to efficient 3D texture representation and hardware-accelerated interpolation in OpenGL [S1, unofficial].
*   **Limitations:** Not suitable for real-time rendering of large volumes due to CPU resampling and data transfer overheads. The 3D FFT on CPU is a preprocessing bottleneck for large volumes ($64^3+$) [S1, unofficial].
*   **When to use:** When OpenGL texture handling is preferred for spectral volume representation and full GPU implementation is not feasible or desired.
*   **When not to use:** When real-time performance is required for large volumes, or when the overhead of CPU-GPU data transfer and CPU-based resampling is unacceptable.

## Background
The Hybrid CPU-GPU FVR Pipeline was proposed as an improvement over single-threaded CPU-based FVR implementations [S1, unofficial]. It builds on the strategy of using heterogeneous computing to leverage the strengths of both CPU (computation) and GPU (rendering/texture handling) [S1, unofficial]. The reference implementation was adopted from a previous single-threaded version discussed in [24] (cited in [S1, unofficial]). The approach aims to increase flexibility and efficiency in designing GPU pipelines by utilizing OpenGL for rendering contexts [S1, unofficial].
