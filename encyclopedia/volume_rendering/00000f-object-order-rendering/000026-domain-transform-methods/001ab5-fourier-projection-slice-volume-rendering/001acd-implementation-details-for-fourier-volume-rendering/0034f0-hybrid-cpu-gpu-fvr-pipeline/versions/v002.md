# Hybrid CPU-GPU FVR Pipeline

Also called: Heterogeneous FVR Pipeline, CPU-Computational/GPU-Rendering FVR

## Overview
The Hybrid CPU-GPU FVR Pipeline is a heterogeneous implementation strategy for Fourier Volume Rendering that partitions the computational workload between the CPU and the GPU [S1, unofficial]. The CPU handles the heavy numerical computations, specifically the 3D Fast Fourier Transform (FFT) and resampling, while the GPU handles the rendering context, including texture management, projection-slice extraction via OpenGL, and final display [S1, unofficial]. This approach leverages the hardware-accelerated interpolation and texture handling of OpenGL to simplify the representation of the 3D spectral volume, offering a middle ground between fully CPU-based pipelines and fully GPU-based implementations [S1, unofficial].

## How it works
The pipeline operates by alternating between a CPU computational context and GPU rendering contexts [S1, unofficial]. The process begins on the CPU and concludes on the GPU's on-screen frame buffer [S1, unofficial].

### Inputs and Outputs
*   **Input:** A 3D volumetric dataset stored as a 3D array on the CPU [S1, unofficial].
*   **Output:** A 2D reconstructed projection image displayed on the screen [S1, unofficial].

### Data Structures
1.  **3D Spectral Volume:** A 3D texture object allocated in GPU memory that stores the frequency spectrum of the input volume [S1, unofficial].
2.  **Frame Buffer Object (FBO):** An OpenGL object used for off-screen rendering [S1, unofficial].
3.  **2D Texture (Intermediate):** A 2-component 2D texture attached to the FBO, storing the extracted projection-slice [S1, unofficial].
4.  **2D Texture (Final):** A 2D texture uploaded to GPU memory containing the final reconstructed image for display [S1, unofficial].

### Steps
1.  Load the 3D dataset into CPU memory [S1, unofficial].
2.  Perform a spatial shift on the 3D dataset [S1, unofficial].
3.  Compute the forward 3D FFT of the shifted volume to obtain its frequency spectrum [S1, unofficial].
4.  Activate an OpenGL off-screen rendering context [S1, unofficial].
5.  Allocate a 3D OpenGL texture in GPU memory and upload the 3D spectral volume from the CPU to this texture [S1, unofficial].
6.  Define a proxy quadrant (plane) passing through the origin of the frequency domain [S1, unofficial].
7.  Intersect this proxy quadrant with the 3D spectral texture to extract the projection-slice [S1, unofficial].
8.  Render the intersection result into the Frame Buffer Object (FBO) [S1, unofficial].
9.  Pack the FBO contents into a 2-component 2D texture attached to the FBO [S1, unofficial].
10. Switch back to the CPU computational context [S1, unofficial].
11. Download the 2-component 2D texture (containing the projection-slice) from GPU memory to CPU memory [S1, unofficial].
12. Resample the downloaded projection-slice on the CPU to remove ghosting artifacts [S1, unofficial].
13. Perform an inverse 2D FFT on the resampled slice to produce a shifted image in the spatial domain [S1, unofficial].
14. Perform a 2D `fft-shift` operation on the image to rearrange it correctly [S1, unofficial].
15. Pack the final reconstructed image into a 2D OpenGL texture [S1, unofficial].
16. Upload this texture to GPU memory using `glTex2D` [S1, unofficial].
17. Activate the on-screen rendering context [S1, unofficial].
18. Send the final texture to the frame buffer for display [S1, unofficial].

    # 7. Inverse Transform (CPU)
    # Perform inverse 2D FFT to produce shifted image [S1, unofficial]

    # Perform 2D fft-shift to rearrange image [S1, unofficial]
    final_image = fft_shift_2d(shifted_image)
    
    # 8. Final Upload (CPU to GPU)
    # Pack final image into 2D OpenGL texture [S1, unofficial]
    final_texture = create_2d_texture(final_image.shape)
    # Upload texture to GPU memory using glTex2D [S1, unofficial]
    upload_to_gpu(final_texture, final_image)
    
    # 9. Display (GPU)
    # Activate on-screen rendering context [S1, unofficial]
    activate_opengl_onscreen_context()
    # Send texture to frame buffer for display [S1, unofficial]
    display_texture(final_texture)

### Edge Cases and Pitfalls
*   **Data Transfer Bottleneck:** The frequent switching between CPU and GPU contexts requires transferring data back and forth, which limits the overall performance of the pipeline to the bandwidth of the communication channel between the CPU and GPU, which is significantly lower than internal GPU bandwidth [S1, unofficial].
*   **Resampling Cost:** The resampling stage represents the most critical bottleneck in the pipeline [S1, unofficial]. It involves four nested for loops (two for slice dimensions, two for filter kernel) [S1, unofficial]. For a projection-slice of size 512x512, this operation takes considerable time and blocks a real-time rendering loop [S1, unofficial].
*   **3D FFT Latency:** The 3D FFT operation on the CPU (using FFTW) is slow for volumes of size 64^3 or larger [S1, unofficial]. Although executed once during preprocessing, performing it on several volumes elongates the pre-processing stage [S1, unofficial].
*   **2D FFT Latency:** The inverse 2D FFT is executed on a per-frame basis, and reducing its time consumption directly enhances the frame rate [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Not given in the sources.
*   **Performance:** The pipeline lacks interactivity due to bottlenecks in data transfer and CPU-based resampling [S1, unofficial]. The communication channel bandwidth between CPU and GPU limits the overall performance [S1, unofficial].
*   **Strengths:** Easier to handle than a full CPU-based pipeline because the 3D spectral volume can be efficiently represented by 3D OpenGL textures with hardware-accelerated interpolation and built-in interpolation schemes [S1, unofficial].
*   **Limitations:** Not suitable for real-time rendering of large volumes due to CPU resampling and data transfer overheads [S1, unofficial]. The 3D FFT on CPU is a preprocessing bottleneck for large volumes (64^3+) [S1, unofficial].
*   **When to use:** When OpenGL texture handling is preferred for spectral volume representation and full GPU implementation is not feasible or desired [S1, unofficial].
*   **When not to use:** When real-time performance is required for large volumes, or when the overhead of CPU-GPU data transfer and CPU-based resampling is unacceptable [S1, unofficial].

## Background
The Hybrid CPU-GPU FVR Pipeline was proposed as an improvement over single-threaded CPU-based FVR implementations [S1, unofficial]. It builds on the strategy of using heterogeneous computing to leverage the strengths of both CPU (computation) and GPU (rendering/texture handling) [S1, unofficial]. The reference implementation was adopted from a previous single-threaded version discussed in [24] (cited in [S1, unofficial]). The approach aims to increase flexibility and efficiency in designing GPU pipelines by utilizing OpenGL for rendering contexts [S1, unofficial].
