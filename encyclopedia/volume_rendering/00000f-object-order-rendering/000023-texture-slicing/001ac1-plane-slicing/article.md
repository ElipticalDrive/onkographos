# Plane Slicing

Also called: Multi-Directional Slicing, Multi-axis Slicing, Plane Slicing with Marching Cubes, Slice Plane Rendering

## Overview
Plane Slicing is a direct volume rendering method that approximates a volumetric scalar field by slicing individual cells into polygons using a set of evenly spaced, axis-aligned planes [S1, S2][S3, unofficial]. Unlike ray casting, it is an object-order technique that leverages graphics hardware rasterization for interactive performance [S3, unofficial]. It distinguishes itself from standard texture slicing by generating explicit polygonal geometry from the volume data (often using a marching cubes variant) rather than sampling a pre-textured volume, allowing it to handle unstructured or curvilinear grids effectively [S1, S2][S3, unofficial].

## How it works
**Inputs and Outputs**
*   **Input:** A 3D scalar field defined on a grid (structured or unstructured/curvilinear) [S1, S2][S3, unofficial].
*   **Output:** A 2D image with correct transparency and color accumulation [S1, S2][S3, unofficial].

**Data Structures**
1.  **Slicing Planes:** Three sets of evenly spaced parallel planes, perpendicular to the X, Y, and Z axes [S1, S2][S3, unofficial].
    *   *Count:* Several hundred planes per axis [S1, S2][S3, unofficial].
2.  **Polygons:** For each cell in the volume, polygons are generated by intersecting the cell with the slicing planes [S1, S2][S3, unofficial].
    *   *Storage:* Polygons for each slice are grouped into arrays for efficient rendering [S1, S2].
3.  **Transfer Function Texture:** A 1D texture map storing color and opacity values [S1, S2][S3, unofficial].
    *   *Coordinates:* Polygon vertex scalar values are normalized to $[0, 1]$ to serve as texture coordinates [S1, S2][S3, unofficial].

**Algorithm Steps**

1.  **Preprocessing (Slicing):**
    *   Generate several hundred evenly spaced slicing planes perpendicular to the X, Y, and Z axes [S1, S2][S3, unofficial].
    *   For each cell in the grid, use a variant of the marching cubes algorithm to slice the cell incrementally into polygons on these three sets of planes [S1, S2][S3, unofficial].
    *   *Optimization:* Optionally, slice only cells above a specific volume threshold; cells below the threshold may be rendered using anti-aliased ellipsoidal splats to handle small cells missed between planes [S1, S2][S3, unofficial].
    *   Group the resulting polygons for each slice into an array [S1, S2].

2.  **Transfer Function Setup:**
    *   Store the transfer function (mapping scalar values to RGBA) in a 1D texture map [S1, S2][S3, unofficial].
    *   Normalize the scalar values of the polygon vertices to $[0, 1]$ to use as 1D texture coordinates [S1, S2][S3, unofficial].
    *   *Alpha Dithering:* If hardware supports only 8 bits per channel, apply alpha dithering to the texture map to expand the range of allowable opacity values, adjusting for per-slice opacity as slice density changes [S1, S2][S3, unofficial].

3.  **View Selection:**
    *   Determine the viewing direction [S1, S2][S3, unofficial].
    *   Select the set of slices (X, Y, or Z) whose axis is closest to the viewing direction [S1, S2][S3, unofficial].

4.  **Rendering:**
    *   Sort the selected slices from back to front relative to the viewer [S1, S2][S3, unofficial].
    *   Rasterize the polygons using graphics hardware [S1, S2][S3, unofficial].
    *   Composite the slices using opacity blending (e.g., standard alpha blending) [S1, S2][S3, unofficial].
    *   *Lighting/Color:* If using elaborate lighting or multiple colors (e.g., smoke and fire), strict back-to-front ordering is required to prevent transparent objects from appearing in front of obscured objects [S5, unofficial]. If all slices have the same color (varying only opacity), ordering is less critical [S5, unofficial].

5.  **Progressive Refinement (Optional):**
    *   Initially render with a few slices for speed [S1, S2][S3, unofficial].
    *   Increase resolution by rendering with more slices as time permits [S1, S2][S3, unofficial].
    *   Users may request a new set of slices perpendicular to any viewing direction [S1, S2][S3, unofficial].

**Pseudocode**

```python
def plane_slicing(volume_data, transfer_function_texture, view_direction):
    # 1. Preprocessing: Generate slicing planes
    # Generate several hundred evenly spaced planes for X, Y, Z axes
    planes_x = generate_evenly_spaced_planes(axis='X', count=300)
    planes_y = generate_evenly_spaced_planes(axis='Y', count=300)
    planes_z = generate_evenly_spaced_planes(axis='Z', count=300)
    
    # 2. Slice cells into polygons
    # Use a marching cubes variant to slice each cell
    polygons_x = []
    polygons_y = []
    polygons_z = []
    
    for cell in volume_data.cells:
        # Slice cell with X-planes
        polys_x = slice_cell_with_planes(cell, planes_x)
        polygons_x.append(polys_x)
        
        # Slice cell with Y-planes
        polys_y = slice_cell_with_planes(cell, planes_y)
        polygons_y.append(polys_y)
        
        # Slice cell with Z-planes
        polys_z = slice_cell_with_planes(cell, planes_z)
        polygons_z.append(polys_z)
        
    # 3. Select best axis based on view direction
    # Calculate dot products of view direction with axes
    dot_x = abs(dot(view_direction, vector(1, 0, 0)))
    dot_y = abs(dot(view_direction, vector(0, 1, 0)))
    dot_z = abs(dot(view_direction, vector(0, 0, 1)))
    
    if dot_x >= dot_y and dot_x >= dot_z:
        selected_polygons = polygons_x
        axis = 'X'
    elif dot_y >= dot_x and dot_y >= dot_z:
        selected_polygons = polygons_y
        axis = 'Y'
    else:
        selected_polygons = polygons_z
        axis = 'Z'
        
    # 4. Sort slices back-to-front
    # Sort polygons based on their position along the viewing ray
    sorted_slices = sort_back_to_front(selected_polygons, view_direction)
    
    # 5. Render with blending
    clear_framebuffer()
    set_blend_mode(BLEND_ALPHA)
    
    for slice in sorted_slices:
        for polygon in slice:
            # Normalize vertex scalars for texture lookup
            for vertex in polygon.vertices:
                vertex.tex_coord = normalize(vertex.scalar_value)
            
            # Rasterize polygon using transfer function texture
            rasterize_polygon(polygon, transfer_function_texture)
            
    return get_framebuffer()

def slice_cell_with_planes(cell, planes):
    # Variant of marching cubes to intersect cell with planes
    polygons = []
    for plane in planes:
        # Intersect cell geometry with plane
        intersection = intersect_cell_plane(cell, plane)
        if intersection is not None:
            # Assign scalar value to vertices
            for vertex in intersection.vertices:
                vertex.scalar_value = interpolate_scalar(cell, vertex.position)
            polygons.append(intersection)
    return polygons
```

**Parameters**
*   **Slice Density:** Several hundred evenly spaced planes per axis [S1, S2][S3, unofficial].
*   **Threshold:** A volume threshold to determine which cells to slice explicitly; others may be splatted [S1, S2][S3, unofficial].

**Edge Cases and Pitfalls**
*   **Small Cells:** Small cells may fall between slice planes or have no pixel centers inside their slice polygons, causing them to be missed during scan conversion [S1, S2][S3, unofficial]. Solution: Use anti-aliased ellipsoidal splats for cells below a threshold or use adaptive meshes [S1, S2][S3, unofficial].
*   **Non-planar Faces:** Cells with non-planar faces may cause sorting and scan conversion problems; selective subdivision into tetrahedra can be used [S2][S3, unofficial].
*   **Perspective View:** In perspective views, viewing rays between slanted slice planes vary in length, potentially requiring per-pixel opacity corrections [S1, S2][S3, unofficial].
*   **Ordering:** Slice plane ordering is critical when drawing objects with different colors (e.g., smoke and fire) or elaborate lighting, but less important for single-color smoke [S5, unofficial].

## Subtopics

### [Plane Composing Algorithms](2154-plane-composing-algorithms.md)
Plane Composing Algorithms are a category of direct volume rendering methods that operate by compositing several slices which comprise a volumetric model. They tend to work best when the view-plane is fixed parallel to the model, so that each of the voxels being composed may be accessed on separate planes. This approach differs from ray casting by leveraging spatial coherence through slicing, often enhanced by texture-based rendering techniques.

### View-Oriented Planes Technique
A volume rendering technique using oriented planes that covers the entire data volume with a fixed number of planes [S4, unofficial]. The minimum number of planes required is equal to the number of voxels in the volume diagonal to intercept all possible voxels when the volume is rotated to maximum plane size, calculated as $\sqrt{W^2 + H^2 + D^2}$, where $W, H, D$ are volume dimensions [S4, unofficial]. For example, a volume of $181 \times 217 \times 181$ requires at least 336 planes [S4, unofficial]. This technique suffers from low performance due to insufficient optimizations; the high number of memory accesses makes the gain from alpha testing negligible, and increasing the plane count (e.g., to 400) significantly reduces speed due to generated fragments and blending operations [S4, unofficial].

### Slice Plane Ordering
A rendering rule where parent objects are drawn back-to-front to prevent transparent objects from appearing blended in front of obscured objects [S5, unofficial]. Slice plane ordering is not important when drawing 3D smoke if all smoke has the same color (only opacity varies), but is important when drawing smoke and fire (different colors) or using elaborate lighting algorithms [S5, unofficial].

## Operating characteristics
*   **Time Complexity:** Preprocessing is $O(N \cdot P)$ where $N$ is the number of cells and $P$ is the number of planes per axis [S1, S2][S3, unofficial]. Rendering is $O(S)$ where $S$ is the number of slices, dominated by rasterization and blending [S3, unofficial].
*   **Memory Complexity:** Requires storage for polygons for all three axes, which can be significant for large datasets [S1, S2][S3, unofficial].
*   **Performance:** Very fast on modern GPUs due to reliance on rasterization hardware [S2][S3, unofficial]. It is an object-space approach, efficient for modern graphics processors, making it the choice for interactivity [S3, unofficial].
*   **Strengths:** Handles unstructured and curvilinear grids well [S1, S2][S3, unofficial]. Allows for progressive refinement [S1, S2][S3, unofficial]. Leverages hardware acceleration [S2][S3, unofficial].
*   **Limitations:** Requires significant preprocessing time [S1, S2][S3, unofficial]. Polygon count can be high [S1, S2][S3, unofficial]. Small cells may be missed without anti-aliasing [S1, S2][S3, unofficial]. View-dependent axis selection may cause popping if not handled smoothly [S1, S2][S3, unofficial].
*   **When to use:** Interactive visualization of unstructured or curvilinear grid data [S1, S2][S3, unofficial].
*   **When not to use:** When high-quality perspective rendering with accurate ray lengths is required without per-pixel corrections [S1, S2][S3, unofficial]. When the dataset is too large to store all slice polygons in memory [S1, S2][S3, unofficial].
