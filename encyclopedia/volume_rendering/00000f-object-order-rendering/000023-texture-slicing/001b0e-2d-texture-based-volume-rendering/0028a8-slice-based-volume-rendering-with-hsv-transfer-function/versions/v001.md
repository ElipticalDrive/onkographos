# Slice-Based Volume Rendering with HSV Transfer Function

Also called: Slice Rendering, Slice-Based Volume Rendering, Texture Array Volume Rendering

## Overview
Slice-Based Volume Rendering with HSV Transfer Function is a GPU-accelerated technique that renders volumetric data by projecting a series of 2D slices onto the image plane and blending them back-to-front, while mapping scalar values to colors using an HSV (Hue, Saturation, Value) transfer function [S1, S2, unofficial]. It differs from standard texture slicing by explicitly simulating 3D texture access via a 2D texture array (sprite sheet) for slice indexing and employing a parametric HSV color mapping rather than a lookup table [S1, unofficial]. This method allows for real-time performance by leveraging fixed-function texture filtering on the 2D slices while providing intuitive control over color mapping through HSV parameters [S1, S2, unofficial].

## How it works

### Inputs and Outputs
**Inputs:**
*   Volumetric data stored in a 2D texture array (sprite sheet) or a 3D texture [S1, S2, unofficial].
*   Camera parameters (view and projection matrices) to define the slice orientation and position [S2, unofficial].
*   HSV transfer function parameters: `darkness`, `l` (lightness scaling), `s` (saturation scaling), `hMin`, `hMax` [S1, unofficial].
*   Rendering parameters: `uNumberOfSlices` (total slices), `uSlicesOverX` (slices per sprite sheet row) [S1, unofficial].

**Outputs:**
*   A 2D color buffer with the blended volume image [S1, S2, unofficial].

### Data Structures

**1. Volume Texture (Sprite Sheet Array)**
*   **Format:** 2D Texture Array or multiple 2D textures arranged in a grid.
*   **Layout:** Slices are packed into 2D images. If `uSlicesOverX` is the number of slices horizontally in a sprite sheet:
    *   Texture width: `uSlicesOverX * slice_width`
    *   Texture height: `ceil(uNumberOfSlices / uSlicesOverX) * slice_height`
    *   Each slice occupies a sub-region within the 2D texture.
*   **Data Type:** Typically `GL_UNSIGNED_BYTE` or `GL_FLOAT` per channel [S2, unofficial].

**2. Transfer Function Parameters**
*   **HSV Parameters:**
    *   `hMin`, `hMax`: Hue range [0, 360] or [0, 1] depending on implementation [S1, unofficial].
    *   `s`: Saturation scaling factor [S1, unofficial].
    *   `l`: Lightness scaling factor [S1, unofficial].
    *   `darkness`: Global brightness multiplier [S1, unofficial].

**3. Vertex Attributes (for Slice Geometry)**
*   **Attribute 0:** Position (3 floats: `x, y, z`) [S2, unofficial].
*   **Attribute 1:** UV coordinates (2 floats: `u, v`) [S2, unofficial].
*   **Attribute 2:** Normals (3 floats: `nx, ny, nz`) [S2, unofficial].

### Algorithm Steps

The rendering process involves two main phases: slice selection/indexing and color mapping.

#### Phase 1: Slice Indexing and Sampling
For each fragment, the shader determines which slice in the texture array corresponds to the fragment's position in the volume and samples the value [S1, unofficial].

1.  **Compute Original Slice Index:**
    Calculate the continuous slice index based on the fragment's normalized Z-coordinate (`volpos.z`) and the total number of slices (`uNumberOfSlices`) [S1, unofficial]:
    $$ s1_{original} = \lfloor volpos.z \times uNumberOfSlices \rfloor $$

2.  **Determine Texture Array Index:**
    Calculate the index of the 2D texture (sprite sheet) in the array [S1, unofficial]:
    $$ tex1Index = \lfloor s1_{original} / slicesPerSprite \rfloor $$
    Where `slicesPerSprite` is the number of slices stored in one 2D texture image.

3.  **Compute Intra-Slice Coordinates:**
    Determine the position of the slice within the sprite sheet [S1, unofficial]:
    $$ s1 = s1_{original} \pmod{slicesPerSprite} $$
    $$ dx1 = \text{fract}(s1 / uSlicesOverX) $$
    $$ dy1 = \lfloor s1 / uSlicesOverY \rfloor / uSlicesOverY $$
    Where `uSlicesOverY` is the number of slices vertically in the sprite sheet (often derived from total slices and `uSlicesOverX`).

4.  **Compute Normalized Texture Coordinates:**
    Combine the intra-slice offset with the fragment's X and Y coordinates to get the final texture coordinates [S1, unofficial]:
    $$ texpos1.x = dx1 + (volpos.x / uSlicesOverX) $$
    $$ texpos1.y = dy1 + (volpos.y / uSlicesOverY) $$

5.  **Sample Volume Value:**
    Sample the 2D texture at `texpos1` using the `tex1Index` to retrieve the scalar volume value $V$ [S1, unofficial].

#### Phase 2: HSV Transfer Function
Map the sampled volume value $V$ to an RGB color using HSV space [S1, unofficial].

1.  **Map Value to Hue:**
    Normalize $V$ to the range $[hMin, hMax]$ [S1, unofficial]. Let $H$ be the resulting hue value.

2.  **Convert HSV to RGB:**
    Use piecewise linear interpolation based on the hue sector [S1, unofficial].
    *   Normalize hue to $[0, 6)$:
        $$ hue = H / 60.0 $$
    *   Determine integer sector $i$ and fractional part $ff$:
        $$ i = \lfloor hue \rfloor $$
        $$ ff = hue - i $$
    *   Calculate intermediate values using Saturation ($S$) and Value ($V_{val}$) [S1, unofficial]:
        $$ p = V_{val} \times (1.0 - S) $$
        $$ q = V_{val} \times (1.0 - (S \times ff)) $$
        $$ t = V_{val} \times (1.0 - (S \times (1.0 - ff))) $$
    *   Assign RGB components based on sector $i$:
        *   If $i = 0$: $R = V_{val}, G = t, B = p$
        *   If $i = 1$: $R = q, G = V_{val}, B = p$
        *   If $i = 2$: $R = p, G = V_{val}, B = t$
        *   If $i = 3$: $R = p, G = q, B = V_{val}$
        *   If $i = 4$: $R = t, G = p, B = V_{val}$
        *   If $i = 5$: $R = V_{val}, G = p, B = q$

3.  **Apply Darkness and Lightness:**
    Multiply the RGB result by `darkness` and scale by `l` [S1, unofficial].

### Pseudocode

```python
# Vertex Shader: Passes position and UVs to fragment shader
# Fragment Shader:

uniform float uNumberOfSlices;
uniform float uSlicesOverX;
uniform float uSlicesOverY;
uniform float slicesPerSprite; # slicesPerSprite = uSlicesOverX * uSlicesOverY
uniform sampler2DArray uVolumeTexture; # Or simulated via 2D texture array
uniform float darkness;
uniform float l;
uniform float s;
uniform float hMin;
uniform float hMax;

vec3 hsv2rgb(float hue, float sat, float val) {
    float h = hue / 60.0;
    int i = int(floor(h));
    float ff = h - float(i);
    float p = val * (1.0 - sat);
    float q = val * (1.0 - (sat * ff));
    float t = val * (1.0 - (sat * (1.0 - ff)));
    
    if (i == 0) return vec3(val, t, p);
    if (i == 1) return vec3(q, val, p);
    if (i == 2) return vec3(p, val, t);
    if (i == 3) return vec3(p, q, val);
    if (i == 4) return vec3(t, p, val);
    if (i == 5) return vec3(val, p, q);
    return vec3(0.0);
}

void main() {
    // volpos is the fragment's position in normalized volume coordinates [0,1]^3
    float volpos_z = volpos.z;
    
    // Step 1: Compute original slice index
    float s1Original = floor(volpos_z * uNumberOfSlices);
    
    // Step 2: Determine texture array index
    int tex1Index = int(floor(s1Original / slicesPerSprite));
    
    // Step 3: Compute intra-slice coordinates
    float s1 = mod(s1Original, slicesPerSprite);
    float dx1 = fract(s1 / uSlicesOverX);
    float dy1 = floor(s1 / uSlicesOverY) / uSlicesOverY;
    
    // Step 4: Compute normalized texture coordinates
    float texpos1_x = dx1 + (volpos.x / uSlicesOverX);
    float texpos1_y = dy1 + (volpos.y / uSlicesOverY);
    
    // Step 5: Sample volume value
    // Note: Actual sampling depends on texture format (2D array vs 3D)
    float volumeValue = texture(uVolumeTexture, vec3(texpos1_x, texpos1_y, float(tex1Index))).r;
    
    // Step 6: Map to HSV
    // Normalize volume value to hue range [hMin, hMax]
    float hue = hMin + (volumeValue * (hMax - hMin));
    float sat = s;
    float val = l;
    
    // Step 7: Convert HSV to RGB
    vec3 rgb = hsv2rgb(hue, sat, val);
    
    // Step 8: Apply darkness
    rgb *= darkness;
    
    gl_FragColor = vec4(rgb, 1.0);
}
```

### Parameters
*   `uNumberOfSlices`: Total number of volume slices [S1, unofficial].
*   `uSlicesOverX`: Number of slices arranged horizontally in each sprite sheet texture [S1, unofficial].
*   `darkness`: Global brightness/darkness multiplier [S1, unofficial].
*   `l`: Lightness scaling factor [S1, unofficial].
*   `s`: Saturation scaling factor [S1, unofficial].
*   `hMin`, `hMax`: Minimum and maximum hue values [S1, unofficial].
*   `numberOfSlices`: Total number of slices to render (used in CPU-side loop) [S2, unofficial].

### Edge Cases and Pitfalls
*   **Texture Array Indexing:** Miscalculation of `tex1Index` or intra-slice coordinates leads to incorrect slice selection or coordinate wrapping [S1, unofficial].
*   **Boundary Conditions:** Ensure `volpos.z` is clamped to $[0, 1]$ to avoid out-of-bounds texture access [G].
*   **Precision:** Floating-point precision errors in slice index calculation may cause visible seams between slices [G].

## Subtopics

### [Slice-based Volume Rendering using Pixel Bender](5445-slice-based-volume-rendering-using-pixel-bender.md)
A real-time volume rendering technique using view-aligned slices and a static 3D texture (set of cross sections), implemented via Pixel Bender shaders. It differs by using a specific shader language (Pixel Bender) and view-aligned slices rather than object-aligned slices.

## Operating characteristics

*   **Time Complexity:** $O(N \times M)$, where $N$ is the number of slices and $M$ is the number of fragments per slice. The complexity is linear with respect to the number of slices and image resolution.
*   **Memory Complexity:** $O(V)$, where $V$ is the volume of the texture array. The memory usage is dominated by the storage of the 2D texture array.
*   **Performance:** Real-time performance is achievable on modern GPUs due to the use of fixed-function texture filtering and simple fragment shaders [S1, S2, unofficial].
*   **Strengths:**
    *   Simple implementation using standard 2D texture arrays.
    *   Intuitive color mapping via HSV parameters.
    *   Good performance for moderate-resolution volumes.
*   **Limitations:**
    *   Limited to object-aligned slices, which may not be optimal for all viewing angles.
    *   Texture array indexing can be complex to implement correctly.
    *   May suffer from aliasing artifacts if the number of slices is insufficient.
*   **When to Use:** Suitable for real-time applications where intuitive color mapping is required and the volume resolution is moderate.
*   **When Not to Use:** Not suitable for high-resolution volumes requiring high-quality ray-marching or view-aligned slicing.

## Background

The method originates from implementations that simulate 3D texture access using 2D texture arrays (sprite sheets) and apply HSV-based transfer functions for color mapping [S1, unofficial]. It is part of the broader family of slice-based volume rendering techniques, which have been used in various graphics applications for real-time volume visualization [S2, unofficial]. The use of HSV transfer functions provides a more intuitive way to map scalar values to colors compared to traditional lookup tables [S1, unofficial].
