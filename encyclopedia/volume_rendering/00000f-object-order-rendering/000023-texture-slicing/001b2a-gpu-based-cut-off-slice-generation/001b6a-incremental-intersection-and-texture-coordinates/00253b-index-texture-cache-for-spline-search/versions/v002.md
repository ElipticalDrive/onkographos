# Index Texture Cache for Spline Search

Also called: Cache Index Texture, Incremental Spline Search Cache

## Overview
An acceleration technique that caches the indices of spline segments used in previous rendering slices to avoid redundant binary searches for the current slice, leveraging depth-order coherence in front-to-back traversal [S1, unofficial]. Unlike the basic algorithm which requires four spline searches per pixel fragment using binary search, this method uses incremental linear search from the previous slice's position, reducing computational bottleneck [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** The current rendering slice index, the previous slice's cache state (segment indices), and the Parametric Representation Image (PRI) structure containing spline data [S1, unofficial].
*   **Output:** Updated cache index texture for the current slice, and the final rendered slice image [S1, unofficial].

**Data Structures:**
*   **Cache Index Texture:** A 2D texture with resolution equal to the PRI's pixelized sampling plane. Each texel stores the index of the spline segment (knot) currently active for that spatial location [S1, unofficial].
*   **Ping-Pong Textures:** Two textures used to swap read/write roles during the update pass to ensure atomicity and avoid race conditions [S1, unofficial].

**Steps:**
1.  **Initialization:** Initialize the 2D cache index texture with the same resolution as the PRI's pixelized sampling plane. Populate it with the contents of the index texture to cache the first knots of each spline [S1, unofficial].
2.  **Two-Pass Rendering:** For each slice in the rendering stack, perform a two-pass approach [S1, unofficial].
3.  **Pass 1: Cache Update:**
    *   Set the camera to coincide with the PRI [S1, unofficial].
    *   Specify the cache index texture as the rendering target [S1, unofficial].
    *   Map the cache index texture to the slice via projective texture mapping using orthogonal projection in the sampling direction of the PRI [S1, unofficial].
    *   At each texel, perform a linear search to find the appropriate spline segment, starting from the segment index stored in the previous slice's cache (read from the ping-pong source texture) [S1, unofficial].
    *   If the next slice requires a spline segment not used in the previous slice, the linear search quickly finds the required segment by starting from the segment processed in the previous slice [S1, unofficial].
    *   Write the new segment index to the cache index texture [S1, unofficial].
    *   Swap ping-pong textures for the next iteration [S1, unofficial].
4.  **Pass 2: Slice Rendering:**
    *   Render the slice from the user's view [S1, unofficial].
    *   Use the updated cache index texture and dependent texturing to fetch the correct spline segment data for trilinear interpolation [S1, unofficial].

**Pseudocode:**
```python
def render_slice_with_cache(slice_index, pri, prev_cache, curr_cache):
    # Pass 1: Cache Update
    # Camera coincides with PRI; cache index texture is render target
    # Map cache index texture to slice via projective texture mapping using orthogonal projection in PRI sampling direction
    for y in range(pri.height):
        for x in range(pri.width):
            # Read segment index from previous slice's cache (ping-pong source)
            seg_idx = prev_cache[y, x]
            # Linear search starting from seg_idx to find appropriate spline segment for current slice
            # [G] Exact search termination condition depends on slice depth vs spline knot positions
            while seg_idx < len(pri.splines) and not segment_covers_depth(pri.splines[seg_idx], slice_index):
                seg_idx += 1
            # Write new segment index to cache index texture
            curr_cache[y, x] = seg_idx
    # Swap ping-pong textures for next iteration
    prev_cache, curr_cache = curr_cache, prev_cache

    # Pass 2: Slice Rendering
    # Render slice from user's view using updated cache index texture and dependent texturing
    # [G] Fragment shader fetches scalar values from splines using cache indices and performs trilinear interpolation
    for y in range(pri.height):
        for x in range(pri.width):
            seg_idx = prev_cache[y, x]
            value = fetch_and_interpolate(pri, seg_idx)
            write_pixel(x, y, value)
    return prev_cache
```

**Parameters:**
*   **Cache Index Texture Resolution:** Equal to the PRI's pixelized sampling plane resolution [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Screen Resolution Mismatch:** When the user's screen resolution exceeds the PRI's sampling plane resolution, multiple pixel fragments may fall within the same neighborhood of four splines. In this case, bilinear interpolation of scalar values from the four neighboring splines can be used for efficiency [S1, unofficial].
*   **Depth Order:** The method assumes front-to-back traversal, though it can be adapted for back-to-front [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Reduces the search cost from binary search ($O(\log N)$) to incremental linear search. The average case is significantly faster due to coherence between adjacent slices [S1, unofficial].
*   **Memory Complexity:** Requires additional memory for the cache index texture (2D texture same size as PRI sampling plane) and ping-pong buffers [S1, unofficial].
*   **Strengths:** Eliminates redundant binary searches by leveraging temporal coherence [S1, unofficial].
*   **Limitations:** Requires two-pass rendering per slice. Performance may degrade if coherence is low (e.g., large jumps between slices) [S1, unofficial].

## Background
This method is part of the GPU-based cut-off slice generation pipeline for volume rendering, specifically addressing the computational bottleneck of spline searches in unstructured grid rendering [S1, unofficial]. It builds on the incremental intersection and texture coordinates method [997-incremental-intersection-and-texture-coordinates.md].
