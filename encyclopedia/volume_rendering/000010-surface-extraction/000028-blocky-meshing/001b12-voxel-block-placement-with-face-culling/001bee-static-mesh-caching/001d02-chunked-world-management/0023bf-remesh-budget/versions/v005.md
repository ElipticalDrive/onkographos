# Remesh Budget

Also called: RemeshQueue

## Overview
Remesh Budget is a rendering optimization that processes "dirty" voxel chunks nearest to the camera first within a strict time budget per frame [S1]. It solves the problem of frame drops during rapid block placement by decoupling modification detection from geometry generation, ensuring that visible geometry is prioritized while limiting the computational cost of mesh rebuilding [S1]. Unlike immediate synchronous rebuilding, which can cause stuttering, this method guarantees that at least one chunk is processed per frame while capping the total remeshing time [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A set of "dirty" chunks (chunks that have changed since the last mesh generation) and the current camera position.
*   **Output:** Updated mesh data for a subset of dirty chunks, processed within the time budget.

**Data Structures:**
*   **RemeshQueue:** A priority queue storing dirty chunks. The priority is determined by the distance from the camera, with nearest chunks having the highest priority [S1].

**Steps:**
1.  **Identify Dirty Chunks:** Detect chunks that have undergone block modifications [S1].
2.  **Populate Queue:** Add identified dirty chunks to the `RemeshQueue`, ordered by distance to the camera (nearest first) [S1].
3.  **Initialize Timer:** Start a timer for the remeshing phase [G].
4.  **Process Queue:**
    *   While the queue is not empty and the elapsed time is less than the `Frame Budget`:
        *   Dequeue the nearest chunk [S1].
        *   Generate the mesh for this chunk [S1].
        *   Update the chunk's mesh data [G].
    *   *Note:* The loop must ensure at least one chunk is processed even if the budget is exceeded immediately after the first iteration [S1].
5.  **Finalize:** Stop the timer and proceed with rendering [G].

**Parameters:**
*   **Frame Budget:** 3 ms per frame for remeshing [S1].

**Edge Cases and Pitfalls:**
*   **Empty Queue:** If no chunks are dirty, no meshing occurs [G].
*   **Budget Exceeded:** If the budget is exceeded after processing one chunk, the remaining chunks remain dirty and will be processed in subsequent frames [S1].
*   **Precision:** Distance calculations should use squared distances to avoid expensive square root operations if possible, though the source does not specify [G].

**Pseudocode:**
```python
def remesh_budget(camera_position, dirty_chunks, frame_budget_ms=3.0):
    """
    Process dirty chunks within a time budget, prioritizing those nearest the camera.
    
    Args:
        camera_position: The current camera position in world space.
        dirty_chunks: A list of chunk objects that need remeshing.
        frame_budget_ms: Maximum time in milliseconds allowed for remeshing.
        
    Returns:
        None. Modifies the mesh data of processed chunks.
    """
    if not dirty_chunks:
        return

    # Create a priority queue sorted by distance to camera (nearest first)
    # Distance metric: Euclidean distance between chunk center and camera position
    queue = sorted(dirty_chunks, key=lambda chunk: distance(chunk.center, camera_position))
    
    start_time = get_current_time_ms()
    processed_count = 0
    
    while queue:
        current_time = get_current_time_ms()
        elapsed = current_time - start_time
        
        # Check if we have exceeded the budget
        if elapsed > frame_budget_ms:
            break
            
        # Always process at least one chunk
        if processed_count > 0 and elapsed > frame_budget_ms:
            break
            
        chunk = queue.pop(0)
        generate_mesh(chunk)  # [G] Implementation detail of mesh generation
        processed_count += 1
        
    return
```

## Subtopics

### [Chunk Mesh Rebuild Queue](3911-chunk-mesh-rebuild-queue.md)
A queue-based system to batch and process chunk mesh rebuilds asynchronously or on tick. It solves the problem of redundant mesh regeneration by ensuring each modified chunk is processed exactly once per frame or tick cycle. Unlike immediate synchronous rebuilding, which can cause frame drops during rapid block placement, this method decouples modification detection from geometry generation.

## Operating characteristics
*   **Time Complexity:** $O(N \log N)$ for sorting dirty chunks by distance, where $N$ is the number of dirty chunks. The actual meshing time is bounded by the frame budget [S1].
*   **Memory Complexity:** $O(N)$ to store the dirty chunks in the queue [S1].
*   **Measured Performance:** In the "Outpost" scene, which consists of 4 chunks and 10k triangles, the method allows for efficient processing. The scene results in 37 draws and 200k triangles on Low quality, 114 draws and 879k triangles on Balanced, and 153 draws and 1.87M triangles on Ultra quality [S1].
*   **Strengths:** Prevents frame drops during rapid block placement by limiting the time spent on mesh generation [S1]. Prioritizes visible geometry, improving perceived responsiveness [S1].
*   **Limitations:** Chunks far from the camera may be delayed for multiple frames if there are many dirty chunks near the camera [S1]. The total number of triangles drawn can still be high (e.g., 1.87M on Ultra), which may impact rendering performance independently of meshing [S1].
*   **When to Use:** When rapid block placement is expected, and frame rate stability is more important than immediate visibility of all changes.
*   **When Not to Use:** When all changes must be visible immediately, or when the number of dirty chunks is small enough that synchronous processing is feasible.

## Background
Remesh Budget was introduced in the "Draw the blocks: beveled chunk meshing, tier tiles, remesh budget (Phase 2c)" pull request for the "Claude-Survivor-Builder" project by Austin Bryan Price [S1]. It is part of a voxel-based building game where blocks are beveled cubes with procedural tiles and ambient occlusion [S1]. The method is implemented in the `remesh-queue.ts` file within the project's source code [S1].
