# Chunked World Management

Also called: Chunk-based Mesh Caching

## Overview
Chunked World Management splits a voxel world into independent sub-worlds called chunks to allow localized mesh rebuilding when a single block changes [S1, unofficial]. It differs from flat mesh caching by replacing a single monolithic mesh with a collection of smaller meshes, each managing its own voxel data and geometry [S1, unofficial].

## How it works
**Inputs:** World coordinates of a block change (add, remove, or modify).
**Outputs:** Updated chunk data structures and GPU buffers for affected chunks.

**Data Structures:**
1.  **World:** Contains a `HashMap` mapping chunk positions (`IVec3`) to `Chunk` objects [S1, unofficial].
2.  **Chunk:** Contains:
    *   `voxels`: A `HashSet` of local voxel positions (`IVec3`) relative to the chunk origin [S1, unofficial].
    *   `mesh`: An optional mesh object holding vertices and indices [S1, unofficial].
    *   `update`: A boolean flag indicating if the mesh buffers require refreshing [S3, unofficial].
    *   `x`, `y`, `z`: Integer coordinates of the chunk in world space [S3, unofficial].
    *   `indicesLength` or `indices`: Array of vertex indices [S3, unofficial].
    *   `vao`: Vertex Array Object handle [S3, unofficial].
    *   Shader-specific instances: `default` and `alpha` instances of `ChunkMesh`/`ChunkMeshAlpha` [S3, unofficial].

**Parameters:**
*   **Chunk Size:** Fixed at $32 \times 32 \times 32$ blocks [S1, unofficial].

**Algorithm Steps:**

1.  **Coordinate Conversion:**
    When a block at world position $P$ changes:
    *   Calculate chunk position $C$:
        $$C = P \div_{\text{euclid}} S$$
        where $S$ is the chunk size (32) and $\div_{\text{euclid}}$ is Euclidean division (floor division) [S1, unofficial].
    *   Calculate local position $L$:
        $$L = P \bmod_{\text{euclid}} S$$
        where $\bmod_{\text{euclid}}$ is Euclidean remainder [S1, unofficial].
    *   *Pitfall:* Standard integer division/remainder fails for negative coordinates, causing incorrect chunk assignment and uneven chunk sizes [S1, unofficial]. Euclidean operations must be used [S1, unofficial].

2.  **Chunk Lookup/Creation:**
    *   Retrieve the `Chunk` object from the `World.chunks` HashMap using key $C$ [S1, unofficial].
    *   If the chunk does not exist, create a new `Chunk` with empty `voxels` and `mesh`, and insert it into the HashMap [S1, unofficial].

3.  **Data Update:**
    *   Invalidate the chunk's mesh: set `chunk.mesh = none` or `chunk.update = true` [S1, unofficial][S3, unofficial].
    *   Update the local voxel set:
        *   If adding a block: `chunk.voxels.insert(L)` [S1, unofficial].
        *   If removing a block: `chunk.voxels.remove(L)` [S1, unofficial].
        *   If modifying block type: Call `removeBlock` then `addBlock` on the chunk mesh, or update the voxel set and mark dirty [S3, unofficial].

4.  **Rendering:**
    *   Iterate over all chunks in `World.chunks` [S1, unofficial].
    *   For each chunk at position $C$:
        *   If `chunk.update` is true or `chunk.mesh` is null:
            *   Generate mesh from `chunk.voxels` [S1, unofficial].
            *   Upload data to GPU (call `chunkMesh.updateBuffers()`) [S3, unofficial].
            *   Set `chunk.update = false` [S3, unofficial].
        *   Calculate world offset: $O = C \times S$ [S1, unofficial].
        *   Draw the mesh with offset $O$ [S1, unofficial].

## Subtopics

### Remesh Budget
A rendering optimization that processes dirty chunks nearest the camera first within a strict time budget per frame [S2]. Dirty chunks are added to a `RemeshQueue` ordered by distance to the camera [S2]. The system meshes chunks until 3 ms of the frame are spent, but always meshes at least one chunk [S2]. This ensures responsiveness in large worlds where full remeshing is too expensive [S2].

### Chunk Mesh Data Structure & Buffer Update
An implementation detail where `setBlock` calls `removeBlock` or `addBlock` on the relevant chunk mesh [S3, unofficial]. The `loadChunkMesh` function initializes `chunkMeshes` per shader and chunk position [S3, unofficial]. During the draw loop, if `chunkMesh.update` is true, `chunkMesh.updateBuffers()` is called before drawing [S3, unofficial]. This allows incremental buffer updates rather than full regeneration [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(1)$ for block updates due to hash map lookup and set operations [S1, unofficial]. Mesh generation is $O(V)$ where $V$ is the number of voxels in the chunk [S1, unofficial].
*   **Memory Complexity:** $O(N)$ where $N$ is the total number of blocks, distributed across chunk structures [S1, unofficial].
*   **Performance:** In the "Outpost" scene (4 chunks, 10k triangles), draw calls scale with quality settings: 37 draws/200k triangles on Low, 114 draws/879k triangles on Balanced, and 153 draws/1.87M triangles on Ultra [S2].
*   **Strengths:** Localized updates prevent full-world rebuilds [S1, unofficial].
*   **Limitations:** Introduces overhead from managing multiple draw calls and chunk boundaries [S2].
*   **When to use:** Large, dynamic worlds where blocks change frequently [S1, unofficial].
*   **When not to use:** Static worlds or very small worlds where chunk management overhead outweighs the benefits [S1, unofficial].

## Background
The technique is a standard optimization in voxel engines to handle dynamic geometry efficiently [S1, unofficial]. Variants with remesh budgets are used in more complex voxel games like "Survivor Builder" [S2].
