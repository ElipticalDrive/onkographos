# Mesh Assembly and Data Structure


## Overview
This family defines the mechanisms for aggregating raw geometric primitives (quads or triangles) generated by blocky meshing algorithms into contiguous, GPU-ready buffer structures. It solves the problem of fragmented geometry by mapping block types to materials, resolving texture IDs, and packing vertex attributes (such as ambient occlusion and light levels) into unified typed arrays for efficient submission [S1, S2, 4100-chunk-mesh-assembly.md, 6209-block-render-data-structure-instance-generation.md, unofficial]. Unlike [Block Render Data Structure & Instance Generation](6209-block-render-data-structure-instance-generation.md), which operates at the individual block instance level using instancing or separate draw calls, this family typically packs all quads for a chunk into a single mesh object with submesh descriptors [S2, 4100-chunk-mesh-assembly.md, unofficial].

## Shared principles
The core mechanism involves three phases: generation, assembly, and configuration.

1.  **Generation Interface**: Meshing algorithms are decoupled from assembly via a plugin interface (e.g., `IMeshingJob`). The interface accepts voxel data and chunk metadata, and outputs vertex and index buffers compatible with the assembly structure [S1, 4921-mesh-plugin-architecture.md, unofficial]. Algorithms may vary (e.g., greedy meshing for blocky voxels vs. marching cubes for smooth terrain) but must produce a consistent output format [S1, 4921-mesh-plugin-architecture.md, unofficial].
2.  **Buffer Allocation**: The assembly phase allocates contiguous typed arrays based on the total quad count across all render layers. For a chunk with $N$ quads:
    *   Positions: $N \times 4 \times 3$ floats (4 vertices per quad, 3 components).
    *   Normals: $N \times 4 \times 3$ signed bytes (int8).
    *   Indices: $N \times 6$ unsigned integers (2 triangles per quad).
    *   Attributes (Block ID, AO, Lights): $N \times 4$ elements per attribute [S2, 4100-chunk-mesh-assembly.md, unofficial].
3.  **Layer Iteration**: The algorithm iterates over defined render layers (e.g., Opaque, Water, Transparent). For each layer, it records vertex and index offsets, appends the layer's quads to the contiguous buffers, and tracks the layer's geometry in a `MeshBufferGroup` structure [S2, 4100-chunk-mesh-assembly.md, unofficial].
4.  **Material Resolution**: Block types are mapped to materials. If a block type lacks a specific material, a fallback material is used [S3, 4100-chunk-mesh-assembly.md, unofficial]. In some implementations, materials are resolved per block type during quad processing, while others use submesh descriptors [S2, 4100-chunk-mesh-assembly.md, 6209-block-render-data-structure-instance-generation.md, unofficial].
5.  **Mesh Configuration**: The final mesh object is configured with the total vertex count, index format (UInt16 or UInt32 depending on vertex count), and submesh descriptors. Bounds are recalculated, and the mesh is assigned to the chunk's renderer and collider [S1, 4100-chunk-mesh-assembly.md, unofficial].

## Subtopics

### [Chunk Mesh Assembly](4100-chunk-mesh-assembly.md)
Aggregates mesh data from multiple rendering layers into contiguous typed arrays for efficient GPU submission. It maps block types to materials and handles per-vertex attributes (AO, light levels) within a unified buffer structure. Unlike [Block Render Data Structure & Instance Generation](6209-block-render-data-structure-instance-generation.md), it packs all quads for a chunk into a single mesh object with submesh descriptors. Choose this when rendering large chunks with mixed materials and lighting attributes in a single draw call per layer.

### [Mesh Plugin Architecture](4921-mesh-plugin-architecture.md)
Provides an interface (`IMeshingJob`) for pluggable meshing algorithms, decoupling mesh generation logic from chunk management. It allows selection of specific algorithms (e.g., greedy meshing vs. marching cubes) based on voxel data types. Choose this when the meshing strategy needs to be extensible or switchable at runtime.

### [Block Render Data Structure & Instance Generation](6209-block-render-data-structure-instance-generation.md)
Defines the data structure for assembling block-level mesh instances. It resolves texture names to IDs and mixes face-specific tints. It differs from [Chunk Mesh Assembly](4100-chunk-mesh-assembly.md) by operating at the individual block instance level rather than assembling contiguous vertex buffers for entire chunks. Choose this when using instancing or per-block draw calls.

### Mesh Configuration and Data Structures
*   **Data Structures**: Block ID data structures must use native JavaScript `Set` for membership tests to avoid performance penalties associated with `Effect`'s `HashSet` (~400k tests per chunk) [S1, unofficial].
*   **Layout**: Block IDs must be registry-derived; untrusted numeric inputs must be converted using `BlockId.result` API [S1, unofficial].
*   **Transparency**: Transparent solids are split into two sets: `transparentSolidBlockIds` (glass, leaves - atlas material + alpha blend) and `waterBlockIds` (dedicated shader for ripples/refraction/variable height) [S1, unofficial].
*   **Fluids**: `FluidQuad` structure includes `direction`, `flow` (optional, containing `direction` vector and `falling` flag), and geometry properties [S1, unofficial].
*   **Chunk View**: `ChunkView` holds `coord`, per-chunk `height`, and a byte view for meshing. It does not implicitly truncate or zero-pad different heights [S1, unofficial].
*   **Storage**: `blockIndex` storage layout is identical to the reference implementation to allow direct use of reference chunk fixtures as golden inputs [S1, unofficial].

### Material-Based Mesh Sectioning
*   **Definition**: Splits a decoded mesh into separate sections (arrays of triangles) based on the material ID associated with each triangle's vertices [S2, unofficial].
*   **Steps**:
    1.  Decode the input mesh using `GetDecodedMesh` [S2, unofficial].
    2.  Sanity check: if index count < 3, return empty sections [S2, unofficial].
    3.  Iterate through indices in steps of 3 [S2, unofficial].
    4.  Retrieve vertices and add mesh offset to positions [S2, unofficial].
    5.  Determine material ID: start with Vertex 0's ID; if Vertex 1 and 2 share the same ID, use that for consistency [S2, unofficial].
    6.  Resize sections array if `materialID` exceeds current size [S2, unofficial].
    7.  Add triangle to the section corresponding to its material ID [S2, unofficial].

## Background
The concepts originate from voxel game engines (e.g., Minecraft clones) where efficient rendering of large, dynamic voxel worlds is critical. The shift from per-block rendering to chunk-based mesh assembly was driven by the need to reduce draw calls and handle complex lighting/materials efficiently. The plugin architecture emerged to support diverse terrain types (blocky vs. smooth) within a unified engine framework. The specific data structures (e.g., `PackedMeshBuffers`, `MeshBufferGroup`) are derived from implementations in open-source voxel generators and game engine integrations.
