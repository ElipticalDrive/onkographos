# Mesh Assembly and Data Structure

Also called: Mesh Assembly, Blocky Mesh Assembly, Voxel Mesh Assembly

## Overview
Mesh Assembly and Data Structure is the family of methods responsible for aggregating geometric primitives (faces, quads, triangles) generated by blocky meshing algorithms into contiguous, GPU-ready buffer structures. It solves the problem of fragmented geometry by mapping block types to materials, handling per-vertex attributes (such as ambient occlusion, light levels, and texture IDs), and organizing data into contiguous typed arrays for efficient submission to the graphics API [S1, S2, 4100-chunk-mesh-assembly.md, unofficial]. Unlike [Block Render Data Structure & Instance Generation](6209-block-render-data-structure-instance-generation.md), which focuses on per-face attribute variation and instancing, this family packs all quads for a chunk into single mesh objects with submesh descriptors or unified instance buffers [S2, 4100-chunk-mesh-assembly.md, unofficial].

## Shared principles
The core mechanism involves iterating over rendering layers (e.g., opaque, water, transparent) and writing vertex and index data into pre-allocated contiguous arrays. The shared data structures typically include:
- `positions`: Float array (3 floats per vertex).
- `normals`: Integer or float array (3 components per vertex).
- `indices`: Integer array (6 indices per quad for 2 triangles).
- `attributes`: Arrays for block IDs, ambient occlusion (AO), and light levels (block/sky) [S2, 4100-chunk-mesh-assembly.md, unofficial].

The assembly process follows a common pattern:
1.  **Change Detection:** Skip assembly if the chunk has not modified voxel data [S1, 4100-chunk-mesh-assembly.md, unofficial].
2.  **Buffer Allocation:** Allocate arrays based on the total quad count across all layers. For $N$ quads, positions require $N \times 4 \times 3$ floats, indices require $N \times 6$ integers, and attributes require $N \times 4$ entries [S2, 4100-chunk-mesh-assembly.md, unofficial].
3.  **Layer Iteration:** For each layer, iterate over quads, compute vertex positions from bounds, write attributes, and write indices. Materials are looked up per block type, with a fallback to a default material if not found [S2, S3, 4100-chunk-mesh-assembly.md, unofficial].
4.  **Configuration:** Configure the mesh object with vertex/index buffers, submesh descriptors, and bounds. Assign to the chunk's renderer and collider [S1, 4100-chunk-mesh-assembly.md, unofficial].

## Subtopics

### [Chunk Mesh Assembly](4100-chunk-mesh-assembly.md)
Aggregates mesh data from multiple rendering layers into contiguous typed arrays for efficient GPU submission. It solves the problem of fragmented geometry by mapping block types to materials and handling per-vertex attributes such as ambient occlusion and light levels within a unified buffer structure. Unlike [Block Render Data Structure & Instance Generation](6209-block-render-data-structure-instance-generation.md), which may use instancing or separate draw calls per block type, this method packs all quads for a chunk into a single mesh object with submesh descriptors.

### [Mesh Plugin Architecture](4921-mesh-plugin-architecture.md)
Provides an interface for pluggable meshing algorithms, allowing for extensibility in the meshing pipeline. It decouples the mesh generation logic from the chunk management system, enabling the use of different algorithms (e.g., greedy meshing for blocky voxels vs. marching cubes for smooth terrain) without modifying the core assembly infrastructure. It sets itself apart from sibling methods by defining the contract for algorithmic entry points rather than handling buffer assembly or finalization.

### [Block Render Data Structure & Instance Generation](6209-block-render-data-structure-instance-generation.md)
Defines the data structure for block rendering metadata and the process of generating GPU instances for voxel faces. It solves the problem of efficiently batching distinct block types into draw calls by mapping face-specific texture IDs and color tints to a unified instance buffer. It differs from standard mesh assembly by focusing on per-face attribute variation (texture and tint) rather than geometric vertex generation, serving as the bridge between logical block definitions and the rendering engine's instancing API.

### [Mesh Finalization](11478-mesh-finalization.md)
Post-processing stage that transforms raw, potentially fragmented mesh data into a validated, contiguous `RenderMesh` object suitable for rendering or analysis. It solves the problem of ensuring data consistency by extrapolating cell-centered values to vertices, flattening vector buffers, and computing geometric properties like normals and bounds. It is distinct from [Chunk Mesh Assembly](4100-chunk-mesh-assembly.md), which focuses on bulk geometry generation for voxel-based chunks, by handling general unstructured grid topology (polyhedra, polygons) and scalar/vector field association.

### Mesh Configuration and Data Structures
- **Data Structures:** Block IDs must be stored in native JavaScript `Set` objects due to performance constraints (~400k membership tests per chunk); `Effect`'s `HashSet` is forbidden [S1, unofficial].
- **Layout:** BlockId values must be registry-derived. Untrusted numeric inputs must be converted using `BlockId.result` API before building sets/maps [S1, unofficial]. Transparent solids are split into two sets: `transparentSolidBlockIds` (glass, leaves - atlas material + alpha blend) and `waterBlockIds` (dedicated shader for ripples/refraction/variable height) [S1, unofficial].
- **Structures:** `FluidQuad` includes `direction`, `flow` (optional, contains `direction` vector and `falling` flag), and geometry properties. `ChunkView` holds `coord`, per-chunk `height`, and a byte view for meshing, without implicit truncation or zero-padding [S1, unofficial].
- **Storage:** The `blockIndex` storage layout is identical to the reference implementation to allow direct use of reference chunk fixtures as golden inputs [S1, unofficial].

### Material-Based Mesh Sectioning
- **Definition:** Splits a decoded mesh into separate sections (arrays of triangles) based on the material ID associated with each triangle's vertices [S2, unofficial].
- **Steps:**
    1.  Decode the input mesh using `GetDecodedMesh` [S2, unofficial].
    2.  Sanity check: if index count < 3, return empty sections [S2, unofficial].
    3.  Iterate through indices in steps of 3. Retrieve vertices and add mesh offset to positions [S2, unofficial].
    4.  Determine material ID: start with Vertex 0's ID. If Vertex 1 and 2 share the same ID, use that instead [S2, unofficial].
    5.  Ensure sections array size is sufficient (`materialID + 1`). Add triangle to the corresponding section [S2, unofficial].

## Background
The methods described in this family are primarily derived from modern voxel game engines and real-time rendering systems, such as those used in Minecraft-like applications. The specific implementations for chunk assembly and plugin architecture originate from the `nerima-games/mc-meshing` project, which focuses on high-performance, burst-compiled meshing for JavaScript/TypeScript environments [S1, unofficial]. The material-based sectioning and buffer structures are derived from `Jay2645/VoxelGenerator`, a C++-based voxel generator that emphasizes efficient mesh decoding and material handling [S2, unofficial]. These techniques have evolved to address the performance bottlenecks of naive mesh generation, particularly in handling transparency, dynamic lighting, and large-scale chunk updates.
