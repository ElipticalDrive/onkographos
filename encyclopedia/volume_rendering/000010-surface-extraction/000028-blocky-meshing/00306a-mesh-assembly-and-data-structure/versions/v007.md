# Mesh Assembly and Data Structure

Also called: Block Mesh Assembly, Chunk Mesh Assembly, Mesh Data Structure

## Overview
Mesh Assembly and Data Structure aggregates the geometric primitives (quads) generated by blocky meshing algorithms into contiguous, typed GPU buffers for efficient rendering [S2, 4100-chunk-mesh-assembly.md, unofficial]. It solves the problem of fragmented geometry and per-vertex attribute management by mapping block types to materials and packing attributes such as ambient occlusion and light levels into unified buffer structures [S1, S3, 4100-chunk-mesh-assembly.md, unofficial]. Unlike [Block Render Data Structure & Instance Generation](6209-block-render-data-structure-instance-generation.md), which focuses on instance data for per-face material variation, this method packs all quads for a chunk into a single mesh object with submesh descriptors [S2, unofficial].

## Shared principles
The assembly process operates on a per-chunk basis, converting logical voxel data into physical mesh buffers. The core mechanism involves three phases: change detection, buffer allocation, and data population.

1.  **Change Detection**: Assembly is skipped if the chunk's voxel data has not changed since the last mesh generation [S1, unofficial]. This prevents redundant memory allocation and GPU submission.
2.  **Buffer Allocation**: Buffers are allocated based on the total number of quads generated by the mesher. The size is calculated as:
    *   Positions: `quadCount * 4 * 3` floats (4 vertices per quad, 3 components).
    *   Indices: `quadCount * 6` integers (2 triangles per quad).
    *   Attributes: `quadCount * 4` per attribute (block ID, AO, block light, sky light).
3.  **Layer Iteration**: The mesh is often split into render layers (e.g., opaque, water, transparent) [S2, unofficial]. For each layer, quads are processed in order. Vertex positions are computed from block bounds, and attributes are written to the contiguous arrays.
4.  **Material Fallback**: If a block type lacks a specific material definition, a pre-scanned fallback material is used [S3, unofficial].
5.  **Mesh Configuration**: The final mesh object is configured with vertex and index buffers, submesh descriptors, and bounds. The mesh is then assigned to the chunk's render components [S1, unofficial].

## Subtopics

### [Chunk Mesh Assembly](4100-chunk-mesh-assembly.md)
Chunk Mesh Assembly aggregates mesh data from multiple rendering layers into contiguous typed arrays for efficient GPU submission. It differs from [Block Render Data Structure & Instance Generation](6209-block-render-data-structure-instance-generation.md) by packing all quads into a single mesh object rather than using instancing per block type. Choose this method when rendering large volumes of static or semi-static voxel geometry where draw call reduction is critical.

### [Mesh Plugin Architecture](4921-mesh-plugin-architecture.md)
The Mesh Plugin Architecture provides an interface (`IMeshingJob`) for pluggable meshing algorithms, decoupling mesh generation logic from chunk management. It allows the selection of different algorithms (e.g., blocky vs. smooth) based on voxel data types. Choose this when the meshing strategy needs to be dynamic or extensible without modifying the assembly pipeline.

### [Block Render Data Structure & Instance Generation](6209-block-render-data-structure-instance-generation.md)
This method defines the data structure for block rendering metadata and generates GPU instances for visible block faces. It solves the problem of passing per-face texture and color information to the graphics API by packing face-specific attributes into a single struct. Choose this when individual blocks require distinct materials or textures that cannot be handled by a single vertex buffer.

### Mesh Configuration and Data Structures
This variant specifies strict data structure requirements for the assembly process.
*   **Parameter**: Block ID data structures must use native JavaScript `Set` for membership tests, as `Effect`'s `HashSet` is too slow (~400k tests per chunk) [S1, unofficial].
*   **Layout**: Block IDs must be registry-derived; untrusted numeric inputs must be converted via `BlockId.result` [S1, unofficial]. Transparent solids are split into `transparentSolidBlockIds` (glass, leaves) and `waterBlockIds` (dedicated shader) [S1, unofficial]. Fluid quads include `direction`, `flow`, and geometry properties. Chunk views hold coordinates and height data without implicit truncation [S1, unofficial]. Storage layout (`blockIndex`) matches the reference implementation for golden input compatibility [S1, unofficial].

### Material-Based Mesh Sectioning
This variant splits a decoded mesh into separate sections based on material IDs associated with triangle vertices [S2, unofficial].
*   **Definition**: Decodes the mesh and iterates through indices in steps of 3.
*   **Step**: For each triangle, retrieve vertices and add mesh offset to positions. Determine the material ID by checking Vertex 0, then Vertex 1 and 2; if they match, use that ID for consistency [S2, unofficial]. Resize the sections array if the material ID exceeds current size, then add the triangle to the corresponding section [S2, unofficial].

## Background
The concept of assembling voxel meshes into chunked buffers originated with early Minecraft clones and voxel engines that required efficient rendering of large, dynamic worlds. The specific implementation details regarding `PackedMeshBuffers`, layer iteration, and material fallbacks are documented in unofficial repositories such as `nerima-games/mc-meshing` [S1, unofficial] and `Jay2645/VoxelGenerator` [S2, unofficial]. The plugin architecture approach builds on these foundations to support algorithmic extensibility [S1, unofficial].
