# Mesh Plugin Architecture
Also called: IMeshingJob
## Overview
The Mesh Plugin Architecture provides an interface for pluggable meshing algorithms, allowing for extensibility in the meshing pipeline [S1, unofficial]. It decouples the mesh generation logic from the chunk management system, enabling the use of different algorithms (e.g., greedy meshing for blocky voxels vs. marching cubes for smooth terrain) without modifying the core assembly infrastructure [S1, unofficial]. It sets itself apart from sibling methods by defining the contract for algorithmic entry points rather than handling buffer assembly or finalization.

## How it works
The architecture defines a common interface (`IMeshingJob`) that all meshing algorithms must implement [S1, unofficial]. The `ChunkManager` acts as the orchestrator, selecting the appropriate job based on voxel type (blocky vs. smooth) and scheduling it [S1, unofficial].

**Inputs and Outputs:**
- **Input:** Voxel data (e.g., `VoxelData` containing material ID and density) and chunk coordinates.
- **Output:** Geometry data (vertices, indices, attributes) written to pre-allocated buffers managed by the parent assembly structure.

**Data Structures:**
The interface requires methods to process voxel data. Specific internal data structures for the algorithms (e.g., lookup tables for Marching Cubes) are implementation details of the plugin, not the interface itself [S1, unofficial].

**Steps:**
1.  **Selection:** The `ChunkManager` evaluates the voxel type. If blocky, it selects `GreedyMeshingJob`; if smooth, it selects `MarchingCubesJob` [S1, unofficial].
2.  **Execution:** The selected job is executed, typically using a job system (e.g., Burst-compiled jobs in Unity) for performance [S1, unofficial].
3.  **Buffer Writing:** The job writes generated geometry into the contiguous typed arrays defined by the parent [S1, unofficial].
4.  **Completion:** The job signals completion, allowing the assembly process to proceed to finalization [S1, unofficial].

**Parameters:**
- **Job System:** Jobs are often burst-compiled for performance [S1, unofficial].
- **Memory:** Half-precision density can save 50% memory (68KB vs 128KB per 32³ chunk) [S1, unofficial].

**Edge Cases:**
- **Missing Materials:** If a material is missing, a fallback should be used [S3, 4100-chunk-mesh-assembly.md, unofficial].
- **Index Overflow:** If vertex count exceeds 65,535, `UInt32` indices must be used [S1, 4100-chunk-mesh-assembly.md, unofficial].

## Operating characteristics
- **Time Complexity:** Depends on the specific algorithm (Greedy Meshing is generally faster for blocky data; Marching Cubes is more expensive for smooth data).
- **Memory Complexity:** Depends on the voxel data representation (e.g., half-precision density reduces memory usage) [S1, unofficial].
- **Strengths:** Extensibility, performance via job systems, separation of concerns.
- **Limitations:** Requires careful management of job scheduling and buffer synchronization.

## Background
The architecture was introduced in the StraightFour voxel engine project [S1, unofficial]. It allows for the integration of different meshing techniques (greedy meshing, marching cubes) within a unified chunk management system [S1, unofficial].
