# Mesh Assembly and Data Structure

Also called: Block Mesh Assembly, Voxel Mesh Buffering

## Overview
Mesh Assembly and Data Structure aggregates raw geometric primitives (quads or triangles) generated by blocky meshing algorithms into contiguous, GPU-ready buffer structures. It solves the problem of fragmented geometry and metadata mapping by consolidating vertex attributes (positions, normals, block IDs, lighting) and index data into typed arrays, enabling efficient draw calls. Unlike [Block Render Data Structure & Instance Generation](6209-block-render-data-structure-instance-generation.md), which focuses on per-instance metadata aggregation for instanced rendering, this family focuses on packing mesh data into contiguous buffers for direct submission, often handling multiple render layers (opaque, transparent, fluids) within a single mesh object or structured set of submeshes.

## Shared principles
The core mechanism involves allocating contiguous typed arrays for vertex attributes and indices, iterating through generated geometry layers, and writing data into these arrays with strict offset tracking.

**Data Layout:**
Vertex attributes are stored in separate typed arrays (Structure of Arrays, SoA) or interleaved, depending on the specific implementation. Common attributes include:
- `positions`: 3 floats per vertex ($x, y, z$).
- `normals`: 3 signed bytes or floats per vertex.
- `blockIds`: 1 integer per vertex, mapping to material indices.
- `ambientOcclusion` (AO): 1 byte per vertex.
- `blockLight` / `skyLight`: 1 byte per vertex.
- `indices`: 2 integers (or 1 uint16) per triangle, or 6 indices per quad.

**Assembly Process:**
1.  **Change Detection:** Verify if the chunk or block data has changed since the last assembly. If not, skip processing to save performance [S1, 4100-chunk-mesh-assembly.md, unofficial].
2.  **Quota Calculation:** Determine the total number of quads or triangles across all render layers (e.g., opaque, water, transparent) to allocate buffer sizes [S2, 4100-chunk-mesh-assembly.md, unofficial].
3.  **Buffer Allocation:** Allocate arrays based on the total count. For quads, vertex arrays require $N \times 4$ entries and index arrays require $N \times 6$ entries [S2, 4100-chunk-mesh-assembly.md, unofficial].
4.  **Layer Iteration:** Iterate through each render layer. For each layer:
    -   Record current vertex and index offsets.
    -   Write vertex positions, normals, and attributes (block ID, AO, lights) for each quad.
    -   Write index data (typically two triangles per quad: $0-1-2$ and $0-2-3$) [S2, 4100-chunk-mesh-assembly.md, unofficial].
    -   Map block types to materials. If a material is missing, use a fallback [S3, 4100-chunk-mesh-assembly.md, unofficial].
    -   Update offsets.
5.  **Mesh Configuration:** Configure the final mesh object with the total vertex count, index count, and submesh descriptors. Recalculate bounds [S1, 4100-chunk-mesh-assembly.md, unofficial].
6.  **Assignment:** Attach the mesh to the chunk's renderer and collider [S1, 4100-chunk-mesh-assembly.md, unofficial].

**Index Format:**
Indices are typically `UInt16` (2 bytes) for chunks with fewer than 65,535 vertices. If the vertex count exceeds this limit, `UInt32` must be used to prevent overflow [S1, 4100-chunk-mesh-assembly.md, unofficial].

## Subtopics

### [Chunk Mesh Assembly](4100-chunk-mesh-assembly.md)
Aggregates mesh data from multiple rendering layers (opaque, water, transparent solid, fluids) into contiguous typed arrays for efficient GPU submission. It maps block types to materials and handles per-vertex attributes such as ambient occlusion and light levels within a unified buffer structure. Unlike [Block Render Data Structure & Instance Generation](6209-block-render-data-structure-instance-generation.md), which may use instancing or separate draw calls per block type, this method packs all quads for a chunk into a single mesh object with submesh descriptors. It uses `PackedMeshBuffers` with specific types: `Float32Array` for positions, `Int8Array` for normals, and `Uint16Array`/`Uint32Array` for indices.

### [Mesh Plugin Architecture](4921-mesh-plugin-architecture.md)
Provides a standardized interface (`IMeshingJob`) for pluggable meshing algorithms, decoupling generation logic from the assembly system. It allows different algorithms (e.g., greedy meshing for blocky voxels, marching cubes for smooth terrain) to produce standardized `MeshInfo` outputs. The `ChunkManager` orchestrates this by selecting the appropriate mesher based on voxel type (blocky vs. smooth) and updating the `MeshStatus`. This approach enables automatic mesher selection and supports burst-compiled jobs for performance.

### [Block Render Data Structure & Instance Generation](6209-block-render-data-structure-instance-generation.md)
Defines the data structure and generation logic for translating discrete voxel face attributes into GPU-drawable instances. It solves the problem of mapping per-face texture IDs and color tints to a unified instance buffer. It differs from sibling methods by focusing on the specific aggregation of face-level metadata (textures and tints) into a single struct per block (`BlockRenderData`), rather than the broader mesh assembly or plugin architecture. It resolves texture names to IDs and handles tint mixing (element-wise multiplication) before instance generation.

### [Mesh Finalization](11478-mesh-finalization.md)
Prepares a raw `RenderMesh` structure for visualization by validating data integrity, extrapolating cell-centered fields to vertices, and computing geometric attributes like normals and bounds. It serves as the bridge between raw solver output and the graphics pipeline. Unlike [Chunk Mesh Assembly](4100-chunk-mesh-assembly.md), which focuses on GPU buffer packing, Mesh Finalization focuses on data consistency, field interpolation, and geometric validity. It includes steps for validating indices, flattening vector buffers, computing cell centers, and selecting active scalars.

### Mesh Configuration and Data Structures
- **Data Structures:** Block ID data structures must use native JavaScript `Set` for membership tests, as `Effect`'s `HashSet` is too slow (~400k tests per chunk) [S1, unofficial].
- **Layout:** Block IDs must be registry-derived; untrusted numeric inputs must be converted via `BlockId.result` [S1, unofficial].
- **Transparency:** Transparent solids are split into `transparentSolidBlockIds` (glass, leaves - atlas material + alpha blend) and `waterBlockIds` (dedicated shader for ripples/refraction) [S1, unofficial].
- **Fluids:** `FluidQuad` includes `direction`, `flow` (vector and falling flag), and geometry properties [S1, unofficial].
- **Chunk View:** `ChunkView` holds coordinate, height, and a byte view for meshing, without implicit truncation or zero-padding [S1, unofficial].
- **Storage:** The `blockIndex` storage layout is identical to the reference implementation to allow direct use of reference chunk fixtures [S1, unofficial].

### Material-Based Mesh Sectioning
- **Definition:** Splits a decoded mesh into separate sections (arrays of triangles) based on the material ID associated with each triangle's vertices [S2, unofficial].
- **Steps:**
    1.  Decode the input mesh using `GetDecodedMesh` [S2, unofficial].
    2.  Sanity check: if indices < 3, return empty sections [S2, unofficial].
    3.  Iterate through indices in steps of 3 [S2, unofficial].
    4.  Retrieve vertices and add mesh offset to positions [S2, unofficial].
    5.  Determine material ID: start with Vertex 0; if Vertex 1 and 2 match, use that ID for consistency [S2, unofficial].
    6.  Resize sections array if `materialID` exceeds current size [S2, unofficial].
    7.  Add triangle to the corresponding material section [S2, unofficial].

## Background
The methods described in this family are primarily derived from modern voxel engine implementations, specifically those optimizing for real-time rendering in block-based worlds (e.g., Minecraft-like games). The specific implementations cited originate from community-driven projects and unofficial repositories focusing on performance optimization, such as the `mc-meshing` project by Nerima Games and the `VoxelGenerator` by Jay2645. These projects address the computational bottleneck of generating geometry from dense voxel grids by employing face culling, greedy meshing, and efficient buffer assembly techniques. The shift from per-block rendering to chunk-based mesh assembly allows for significant draw call reduction.
