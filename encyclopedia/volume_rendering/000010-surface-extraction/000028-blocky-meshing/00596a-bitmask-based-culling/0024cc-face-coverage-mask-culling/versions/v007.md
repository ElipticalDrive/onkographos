# Face Coverage Mask Culling

Also called: Bitmask Culling, Culling Limitations, Partial Shape Culling

## Overview
Face Coverage Mask Culling is a method for optimizing the mesh generation of voxel-based partial shapes (such as stairs, slabs, and walls) by determining face visibility through bitwise comparison of precomputed coverage masks. It solves the problem where a simple boolean "solid/empty" flag is insufficient for non-cubic blocks, as a single face may have mixed visible and hidden regions. Unlike sibling methods that rely on full Constructive Solid Geometry (CSG) subtraction or complex geometric subdivision, this approach uses a matrix of precomputed bitmasks to rapidly decide if a face is fully occluded, fully visible, or partially occluded, significantly reducing meshing time at the cost of potential overdraw or simplified geometry handling [S1][S2, S2, unofficial].

## How it works
The method operates on the principle that face visibility is determined by comparing the geometric coverage of a block's face against the opposite face of its immediate neighbor.

### Inputs and Outputs
*   **Input:** A voxel grid where each voxel contains a reference to a block shape. Each block shape has precomputed occlusion data for its six faces across all allowed rotations.
*   **Output:** A set of triangles for the chunk, excluding faces that are fully occluded by neighbors.

### Data Structures
The core data structure is the `FaceMask`, which represents the geometric coverage of a single face of a block shape.

**FaceMask Layout:**
*   **Type:** Unsigned 16-bit integer (`u16`).
*   **Resolution:** Represents a $4 \times 4$ grid of cells on the face boundary. Each bit corresponds to one cell in the grid.
*   **Constants:**
    *   `FULL`: A `FaceMask` with value `0xffff` (all 16 bits set), representing a fully opaque, solid face (e.g., a standard cube).
    *   `EMPTY`: A `FaceMask` with value `0x0000` (all 16 bits unset), representing a completely empty face.

**Occlusion Table Layout:**
For each block shape, a lookup table stores the masks for all orientations.
*   **Structure:** `shape.occlusion[rotation][face]`
*   **Rotation:** Index representing the block's orientation (e.g., 0–7 for Minecraft-style rotations).
*   **Face:** Index representing the face direction (e.g., 0–5 for +X, -X, +Y, -Y, +Z, -Z).
*   **Value:** A `FaceMask` constant.

### Algorithm Steps
1.  **Retrieve Masks:** For a given voxel at position $P$ with shape $S$ and rotation $R$, and a neighbor at position $P + d$ with shape $S'$ and rotation $R'$, retrieve the relevant masks:
    *   `current_mask = S.occlusion[R][face]`
    *   `neighbor_mask = S'.occlusion[R'][opposite(face)]`
    *   Here, `face` is the direction from $P$ to the neighbor, and `opposite(face)` is the direction from the neighbor back to $P$.

2.  **Calculate Occlusion:** Determine if the current face is fully occluded by the neighbor. A face is fully occluded if the neighbor's coverage covers all bits that are set in the current face's coverage.
    *   Formula: `is_fully_occluded = (current_mask.0 & !neighbor_mask.0) == 0`
    *   Conceptually: `visible_coverage = current_mask - neighbor_mask` (bitwise subtraction via AND NOT).

3.  **Culling Decision:**
    *   If `is_fully_occluded` is true, the face is completely hidden and is **culled** (no triangles generated for this face).
    *   If `is_fully_occluded` is false, the face is **visible**.

4.  **Geometry Generation:**
    *   **Standard Approach:** Generate the full geometry for the face, even if only partially covered. This results in overdraw for the hidden parts but keeps the mesher simple [S1][S2, unofficial].
    *   **Advanced Approach:** Subdivide or clip the geometry to match the `visible_coverage` mask. This reduces geometry count but increases mesher complexity [S2, unofficial].

### Pseudocode
```python
# Constants
FULL_MASK = 0xFFFF
EMPTY_MASK = 0x0000

# Data structure for block shape
class BlockShape:
    def __init__(self):
        # occlusion[rotation][face] -> u16
        self.occlusion = {} 

# Helper to get opposite face index
def opposite_face(face_index):
    # Assuming face indices 0-5 map to +/- X, +/- Y, +/- Z
    # Example mapping: 0:+X, 1:-X, 2:+Y, 3:-Y, 4:+Z, 5:-Z
    opposites = [1, 0, 3, 2, 5, 4]
    return opposites[face_index]

# Core culling function
def is_face_visible(current_shape, current_rotation, current_face, 
                    neighbor_shape, neighbor_rotation, neighbor_face):
    """
    Returns True if the face should be rendered, False if fully occluded.
    """
    # 1. Retrieve masks
    current_mask = current_shape.occlusion[current_rotation][current_face]
    neighbor_mask = neighbor_shape.occlusion[neighbor_rotation][opposite_face(neighbor_face)]
    
    # 2. Check for full occlusion
    # If (current & ~neighbor) is 0, then all bits in current are also in neighbor
    if (current_mask & ~neighbor_mask) == 0:
        return False
    
    return True

# Meshing loop context
def mesh_chunk_face(chunk, x, y, z, face_index):
    """
    Determines if the face of the voxel at (x,y,z) in the given direction
    should be meshed.
    """
    voxel = chunk.get_voxel(x, y, z)
    if voxel is None or voxel.shape is None:
        return # No shape, treat as air
    
    # Determine neighbor position
    dx, dy, dz = face_directions[face_index]
    nx, ny, nz = x + dx, y + dy, z + dz
    
    neighbor = chunk.get_voxel(nx, ny, nz)
    
    # If neighbor is out of bounds or empty, face is visible
    if neighbor is None or neighbor.shape is None:
        return True
    
    # 3. Perform culling check
    if is_face_visible(voxel.shape, voxel.rotation, face_index,
                       neighbor.shape, neighbor.rotation, opposite_face(face_index)):
        return True
    else:
        return False
```

### Parameters and Edge Cases
*   **Resolution:** The $4 \times 4$ grid is a common default, but the resolution can be adjusted based on the complexity of the shape vocabulary [S2, unofficial].
*   **Precomputation:** Rotations and flips are precomputed per model to eliminate lookup work during the hot meshing loop [S1].
*   **Transparency:** The method does not inherently handle transparency. If a transparent block (e.g., glass) is adjacent to an opaque block, the culling logic may incorrectly hide the transparent block's face if it is geometrically covered, or expose underlying geometry if the opaque block is partially transparent [S1]. This is often mitigated by game design constraints (e.g., no glass slabs in Minecraft) [S1].
*   **Partial Occlusion:** If a face is only partially occluded, the standard implementation leaves the entire face geometry visible, resulting in overdraw [S1].

## Subtopics

### [Face-Culling Geometry Shader](3928-face-culling-geometry-shader.md)
A geometry shader technique that generates cube faces from point primitives based on a bitmask, culling hidden faces to reduce overdraw and vertex processing. It builds on Face Coverage Mask Culling by using the bitmask to determine face visibility at the primitive generation stage [G].

### [Per-face Column-based Face Culling with Opacity Masks](4821-per-face-column-based-face-culling-with-opacity-masks.md)
A face culling technique that uses per-face column arrays and opaque column arrays to determine visibility based on solid and transparent block transitions, allowing full per-face control over opacity. It extends Face Coverage Mask Culling by distinguishing between opaque and transparent surface contributions on partial shapes.

### [Boundary Geometry Classification](5435-boundary-geometry-classification.md)
Boundary Geometry Classification is a geometric filtering step used during octree construction and neighbor-based culling to distinguish surface geometry located on voxel cell boundary planes from internal geometry within complex blocks. It solves the problem where neighbor occlusion tests would incorrectly prune or interact with internal fragments of non-manifold or complex shapes by ensuring that culling logic only applies to polygons strictly lying on the six faces of the current voxel cell. It sets itself apart from sibling methods like Face Coverage Mask Culling by operating at the individual polygon level to identify *which* geometry is eligible for neighbor interaction, rather than determining *how* to cull based on coverage masks.

### Transparent Material Culling
A method to handle culling for transparent or cutout materials by separating geometric coverage from material occlusion behavior [S2, unofficial]. It uses a `FaceOcclusion` struct containing `coverage: FaceMask` and `mode: OcclusionMode`, where `OcclusionMode` expresses behavior such as opaque, cutout, translucent, or never-occluding [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(1)$ per face for the culling check, assuming precomputed masks and direct array access. The overall meshing time is linear with respect to the number of voxel faces, $O(N)$, where $N$ is the number of voxels in the chunk.
*   **Memory Complexity:** $O(S \times R \times F)$ for the occlusion tables, where $S$ is the number of unique block shapes, $R$ is the number of rotations, and $F$ is the number of faces (6). This is typically small and fits in cache.
*   **Performance:** Significantly reduces the number of triangles sent to the GPU by removing interior faces. The use of bitwise operations makes the culling decision extremely fast [S1][S2, unofficial].
*   **Strengths:** Simple to implement, very fast, effective for standard voxel games with partial shapes.
*   **Limitations:** Does not support perfect CSG-style cutting of faces, leading to overdraw for partially occluded faces. Transparency handling is problematic and often requires workarounds [S1].
*   **When to Use:** Ideal for real-time voxel engines where performance is critical and visual artifacts from overdraw are acceptable or unnoticeable (e.g., Minecraft-like games).
*   **When Not to Use:** Not suitable for applications requiring precise geometric intersection, perfect transparency, or complex non-voxel geometry integration.

## Background
Face Coverage Mask Culling originated in the development of voxel-based games, most notably Minecraft, where the need to efficiently render millions of blocks with varying shapes (stairs, slabs, walls) required an optimization beyond simple solid/empty checks. The method was formalized in documentation for voxel tools and community blogs discussing blocky terrain generation [S1][S2, unofficial]. It addresses the limitations of naive meshing, where every block face is rendered regardless of neighbors, leading to excessive triangle counts. The approach leverages the regularity of voxel grids and the limited set of block shapes to precompute visibility data, enabling real-time mesh generation.
