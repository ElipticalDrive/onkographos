# VoxelBlockyTypeLibrary with Attributes

Also called: Minecraft-like block states, VoxelBlockyType

## Overview
`VoxelBlockyTypeLibrary` is an alternative library type that contains a list of `VoxelBlockyType` objects instead of models directly [S1]. A type defines a "block type" with attributes representing states (e.g., orientation, pressed state), similar to Minecraft block states [S1]. It solves the problem of managing complex block behaviors by automatically generating unique numerical IDs for every combination of attribute values [S1]. It differs from the standard `VoxelBlockyLibrary` by decoupling model identity from manual ID assignment, using a combinatorial attribute system instead [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A list of `VoxelBlockyType` definitions, each containing a name and a set of `VoxelBlockyAttribute` definitions [S1].
*   **Output:** A library mapping type/attribute combinations to unique numerical model IDs, resolvable at runtime [S1].

**Data Structures:**
*   **VoxelBlockyType:** Defines a logical block [S1]. Contains a `StringName` identifier and a list of `VoxelBlockyAttribute` objects [S1].
*   **VoxelBlockyAttribute:** Represents a state variable [S1]. Takes integer values between 0 and 255 [S1].
*   **Model ID Map:** An internal mapping linking the canonical string identifier `<type_name>[attr1=val,attr2=val,...]` to a unique integer ID [S1]. IDs are unique within the library instance but not portable across different worlds [S1].

**Numbered Steps:**

1.  **Define Block Types:** Create `VoxelBlockyType` entries with a name and attributes [S1]. Types should usually have very few attributes [S1].
2.  **Assign Attribute Values:** Define possible integer values (0–255) for each attribute [S1]. Use built-in rotation attributes (`VoxelBlockyAttributeAxis`, `VoxelBlockyAttributeDirection`, `VoxelBlockyAttributeRotation`) for common geometric states [S1]. Each rotation attribute has a default rotation; models are authored for this default, and the system generates other rotations automatically [S1].
3.  **Generate Variants:** The system computes the Cartesian product of all attribute values for each type [S1]. For each combination, a unique model instance is created [S1]. If built-in rotation attributes are used, pre-rotated models are generated for all specified axes/directions [S1]. Excluding unnecessary rotations (e.g., vertical for flat blocks) reduces memory cost, as `VoxelBlockyAttributeRotation` generates the highest number of variants [S1].
4.  **Assign Numerical IDs:** The system automatically assigns a unique integer ID to each generated variant based on all combinations of attributes for each type [S1]. IDs are unique within a specific world but not portable across worlds [S1]. Renaming, removing, or adding attributes changes the canonical identifier, effectively creating a different voxel with a potentially different ID [S1].
5.  **Runtime Lookup:** Use library functions to map between type names/attribute values and model IDs [S1]. Cache IDs for performance [S1]. Use `VoxelTool` to get/set model IDs in voxel data [S1].

**Formulas:**
*   **Canonical Identifier:**
    $$ \text{key} = \text{type\_name} + \text{"["} + \text{",".join(attr + "=" + str(val) \text{ for attr, val in attrs.items()})} + \text{"]"} $$
    Where attribute values are integers in $[0, 255]$ [S1].
*   **Total Variants per Type:**
    $$ N_{\text{variants}} = \prod_{i=1}^{n} V_i $$
    Where $n$ is the number of attributes and $V_i$ is the number of possible values for attribute $i$ [S1].

**Pseudocode:**

```python
import itertools

class VoxelBlockyTypeLibrary:
    def __init__(self):
        self.types = {}  # Map: StringName -> VoxelBlockyType
        self.id_map = {} # Map: CanonicalString -> int
        self._next_id = 0

    def add_type(self, type_name: str, attributes: list):
        """Register a block type and generate all variant IDs."""
        # 1. Generate all combinations of attribute values
        value_ranges = [range(len(attr.values)) for attr in attributes]
        combinations = list(itertools.product(*value_ranges))
        
        # 2. Assign IDs and generate models
        for combo in combinations:
            # Construct canonical key: type_name[attr1=val1, attr2=val2]
            key_parts = [f"{attributes[i].name}={attributes[i].values[combo[i]]}" for i in range(len(attributes))]
            canonical_key = f"{type_name}[{','.join(key_parts)}]"
            
            # Assign unique ID
            model_id = self._assign_unique_id(canonical_key)
            
            # Generate or reference the model for this state
            model = self._generate_model_for_state(type_name, attributes, combo)
            
            # Store mapping
            self.id_map[canonical_key] = model_id
            self._store_model(model_id, model)

    def get_model_index_with_attributes(self, type_name: str, attrs: dict) -> int:
        """Get the numerical model ID for a specific type and attribute values.
        Uses StringName (&) for type name in engine, but standard strings for dict keys."""
        key_parts = [f"{attr_name}={val}" for attr_name, val in attrs.items()]
        canonical_key = f"{type_name}[{','.join(key_parts)}]"
        return self.id_map.get(canonical_key, -1)

    def get_model_index_single_attribute(self, type_name: str, attr_val: int) -> int:
        """Shortcut for types with exactly one attribute."""
        # Assumes single attribute name is known or fixed for this type
        # This is a performance optimization
        return self.get_model_index_with_attributes(type_name, {self.types[type_name].attributes[0].name: attr_val})

    def get_model_index_default(self, type_name: str) -> int:
        """Get the model ID for a type with no attributes, or its default state."""
        if type_name not in self.types or not self.types[type_name].attributes:
            return self.id_map.get(f"{type_name}[]", -1)
        default_attrs = {attr.name: attr.values[0] for attr in self.types[type_name].attributes}
        return self.get_model_index_with_attributes(type_name, default_attrs)
```

**Parameters:**
*   **Attribute Values:** Integers between 0 and 255 [S1].
*   **Attribute Count:** Should be very low [S1].
*   **Rotation Attributes:** `VoxelBlockyAttributeAxis`, `VoxelBlockyAttributeDirection`, `VoxelBlockyAttributeRotation` [S1]. Default rotations are assumed for base models [S1].

**Edge Cases and Pitfalls:**
*   **Complex States:** If a block requires complex states (objects, lists), this system fails; fallback to voxel metadata and actual nodes (entities) is required [S1].
*   **Large Variant Lists:** Many attributes or states lead to a very large list of variants (e.g., redstone dust has 1,296 variants); conditional combination of models is preferred over a list of variants [S1].
*   **Memory Cost:** `VoxelBlockyAttributeRotation` has the highest number of variants and incurs significant memory cost for pre-rotated models; exclude unnecessary rotations (e.g., vertical) to reduce cost [S1].
*   **ID Portability:** Numerical IDs are not portable across worlds; renaming types or attributes changes IDs, breaking compatibility with saved worlds [S1].

## Subtopics

### Voxel ID Management
Voxel IDs in `VoxelBlockyLibrary` act like tilemap tiles; for simple games they can directly correspond to a block type, but complex games should define custom "game block types" that map to one or multiple `VoxelBlockyModel` IDs [S1]. Minecraft examples include stairs (multiple IDs for orientations/appearances), crops (multiple IDs for growth stages), doors (2 voxels for top/bottom), and rails (many IDs for straight/slope/turn configurations) [S1]. Managing the correspondence between game block IDs and voxel IDs is handled by the developer [S1].

## Operating characteristics
*   **Time Complexity:** Lookup is $O(1)$ after caching, or $O(k)$ where $k$ is the number of attributes for string construction [S1]. Generation of variants is $O(N_{\text{variants}})$, which can be large [S1].
*   **Memory Complexity:** $O(N_{\text{types}} \times N_{\text{variants}})$ [S1]. Memory usage scales with the number of attribute combinations; pre-rotated models increase the footprint significantly [S1].
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Scales poorly with high attribute counts or high value ranges per attribute; the redstone dust example (1,296 variants) illustrates the limit [S1].
*   **Strengths:** Automatic ID management, intuitive state representation (Minecraft-like), built-in rotation support [S1].
*   **Limitations:** Not suitable for complex states (objects/lists); high memory cost for rotations; non-portable IDs [S1].
*   **When to use:** Simple to moderately complex block states (orientation, on/off, basic connections) [S1].
*   **When not to use:** Blocks requiring complex dynamic states, or when memory is extremely constrained and rotations are not needed [S1].

## Background
Originating from the Voxel Tools library for Godot, this system was inspired by Minecraft's block state system (specifically ForgeModLoader documentation) [S1]. It was introduced as an alternative to `VoxelBlockyLibrary` to better handle the complexity of block states in voxel games [S1]. The system automates model generation and ID assignment, reducing manual configuration effort [S1].
