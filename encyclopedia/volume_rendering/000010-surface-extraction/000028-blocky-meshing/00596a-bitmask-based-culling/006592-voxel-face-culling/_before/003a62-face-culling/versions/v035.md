# Face Culling

Also called: Exposure Culling, Face Occlusion Culling, Neighbor Check Culling, Only render block faces that aren't adjacent to another face, Voxel Neighbor Face Culling

## Overview
Face Culling is a mesh generation optimization that prevents the rendering of block faces occluded by adjacent solid voxels, significantly reducing the triangle count in homogeneous voxel terrain [S1, unofficial][S2, unofficial]. It solves the performance bottleneck of naively rendering all six faces of every cube by ensuring only exposed surfaces are added to the vertex buffer [S2, unofficial]. Unlike [Binary Hidden-Face Culling](8747-binary-hidden-face-culling.md), which uses bitwise operations on linear bitmasks for bulk processing, Face Culling typically iterates through neighbor coordinates using a hash set or grid lookup to determine visibility [S1, unofficial][S2, unofficial].

## How it works
**Inputs:**
- A set of occupied voxel positions, represented as a hash set of integer coordinates $P = (x, y, z)$ [S2, unofficial].
- A list of solid voxels to process.

**Outputs:**
- A vertex buffer containing only the triangles for exposed faces [S2, unofficial].

**Data Structures:**
The implementation relies on two primary structures as described in the parent article [Face Culling and Visibility Optimization](3861-face-culling-and-visibility-optimization.md):
1.  **Hash Set:** `occupied_positions`: A set of `glm::ivec3` (or equivalent integer triplet) representing occupied voxel positions. Lookup is $O(1)$ average case [S2, unofficial].
2.  **Voxel Representation:** Each voxel is processed to determine its six potential faces. A face is defined by its position and normal direction $d \in \{ \pm x, \pm y, \pm z \}$ [S1, unofficial][S2, unofficial].

**Algorithm Steps:**
1.  Initialize an empty vertex buffer.
2.  For each solid voxel at position $P$:
    a.  For each of the six face directions $d$:
        i.  Calculate the neighbor position $P_{neighbor} = P + d$.
        ii. Check if $P_{neighbor}$ exists in `occupied_positions`.
        iii. If $P_{neighbor}$ is **not** in `occupied_positions` (i.e., it is empty or out of bounds), the face is exposed.
        iv. Generate the two triangles for this face and add them to the vertex buffer.
        v. If $P_{neighbor}$ **is** in `occupied_positions`, the face is occluded and is skipped.
3.  Upload the vertex buffer to the GPU [S2, unofficial].

**Pseudocode:**
```python
def generate_mesh(occupied_positions):
    """
    Generates a mesh for voxel terrain using face culling.
    
    Args:
        occupied_positions: A set of (x, y, z) tuples representing solid voxels.
        
    Returns:
        vertices: A list of vertex coordinates for exposed faces.
    """
    vertices = []
    # Define the 6 directions and their corresponding face vertices
    # Assuming unit cubes centered at integer coordinates, 
    # vertices are at +/- 0.5 relative to center.
    directions = [
        (1, 0, 0),  # Right
        (-1, 0, 0), # Left
        (0, 1, 0),  # Top
        (0, -1, 0), # Bottom
        (0, 0, 1),  # Front
        (0, 0, -1)  # Back
    ]
    
    # Define the 2 triangles (6 vertices) for each face normal
    # This is a simplified representation; actual implementation depends on vertex format
    face_triangles = {
        (1, 0, 0): [
            (0.5, 0.5, 0.5), (0.5, -0.5, 0.5), (0.5, -0.5, -0.5),
            (0.5, 0.5, 0.5), (0.5, -0.5, -0.5), (0.5, 0.5, -0.5)
        ],
        (-1, 0, 0): [
            (-0.5, 0.5, -0.5), (-0.5, -0.5, -0.5), (-0.5, -0.5, 0.5),
            (-0.5, 0.5, -0.5), (-0.5, -0.5, 0.5), (-0.5, 0.5, 0.5)
        ],
        (0, 1, 0): [
            (-0.5, 0.5, 0.5), (0.5, 0.5, 0.5), (0.5, 0.5, -0.5),
            (-0.5, 0.5, 0.5), (0.5, 0.5, -0.5), (-0.5, 0.5, -0.5)
        ],
        (0, -1, 0): [
            (-0.5, -0.5, -0.5), (0.5, -0.5, -0.5), (0.5, -0.5, 0.5),
            (-0.5, -0.5, -0.5), (0.5, -0.5, 0.5), (-0.5, -0.5, 0.5)
        ],
        (0, 0, 1): [
            (-0.5, 0.5, 0.5), (-0.5, -0.5, 0.5), (0.5, -0.5, 0.5),
            (-0.5, 0.5, 0.5), (0.5, -0.5, 0.5), (0.5, 0.5, 0.5)
        ],
        (0, 0, -1): [
            (0.5, 0.5, -0.5), (0.5, -0.5, -0.5), (-0.5, -0.5, -0.5),
            (0.5, 0.5, -0.5), (-0.5, -0.5, -0.5), (-0.5, 0.5, -0.5)
        ]
    }

    for pos in occupied_positions:
        x, y, z = pos
        for d in directions:
            dx, dy, dz = d
            neighbor_pos = (x + dx, y + dy, z + dz)
            
            # Check if neighbor is occupied
            if neighbor_pos not in occupied_positions:
                # Face is exposed, add vertices
                # Translate face vertices to world position
                for v in face_triangles[d]:
                    vertices.append((x + v[0], y + v[1], z + v[2]))
                    
    return vertices
```

**Parameters:**
- Chunk Size: Commonly $16 \times 16 \times 16$ voxels [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Chunk Boundaries:** Adjacent cubes across chunk boundaries (e.g., $x=0$ and $x=15$ in a 16-wide chunk) must be checked. If ignored, the outline of each chunk is drawn, killing performance [S1, unofficial].
- **Bottom Faces:** In some implementations, bottom faces are always culled regardless of neighbors below, as indicated by logic where `isBottomFace` sets `renderFlag = false` [S2, unofficial]. This is a specific optimization choice, not a general rule of face culling.
- **Side Face Logic:** Some implementations check for neighbors directly adjacent OR neighbors directly above the neighbor position to cull side faces, which may be a specific heuristic for terrain generation [S2, unofficial].

## Subtopics

### [Binary Hidden-Face Culling](8747-binary-hidden-face-culling.md)
Uses bitwise operations on linear bitmasks to identify exposed surfaces in bulk, replacing random memory access with parallel bitwise math. Choose this when processing large, contiguous volumes where bitwise parallelism outweighs the complexity of mask management.

Uses coverage masks to determine visibility. Choose this when dealing with partial voxel occupancy or non-cube shapes.

## Operating characteristics
- **Time Complexity:** $O(N)$ where $N$ is the number of solid voxels, assuming $O(1)$ hash set lookups. The culling check runs once during mesh creation, resulting in no framerate loss during rendering [S2, unofficial].
- **Memory Complexity:** $O(N)$ for the hash set and vertex buffer.
- **Measured Performance:** With this optimization, performance allows running more than 14,440 chunks on a fairly old PC (Intel Core i7 2.5 GHz, AMD Radeon HD 6770M 1024 MB) while performing GPU-heavy algorithms like cascaded shadow mapping and water shading [S1, unofficial]. Without it, only ~20 chunks could be drawn without lagging [S1, unofficial]. Another measurement shows 4096 cubes rendered at ~60 FPS [S2, unofficial].
- **Scaling:** Performance scales linearly with the number of chunks, provided the hash set lookups remain efficient.
- **Strengths:** Dramatically reduces triangle count (drawing only ~1/1000 of the triangles previously drawn in homogeneous terrain) [S1, unofficial]. Simple to implement.
- **Limitations:** Requires a full world or chunk neighbor lookup, which can be complex in chunked systems if boundary checks are ignored [S1, unofficial]. Not suitable for dynamic scenes where voxels change frequently without re-meshing.
- **When to use:** Homogeneous voxel terrain where most faces are occluded.
- **When not to use:** Sparse voxel clouds where most faces are exposed, or dynamic scenes requiring frequent mesh updates.

## Background
Face Culling is a standard optimization in voxel rendering, widely used in voxel games and terrain generation systems. It was discussed in the context of optimizing voxel world rendering on Game Development Stack Exchange [S1, unofficial] and implemented in the Voxel-Terrain-Generation repository [S2, unofficial]. The technique is fundamental to reducing the GPU load in voxel engines by eliminating interior geometry.
