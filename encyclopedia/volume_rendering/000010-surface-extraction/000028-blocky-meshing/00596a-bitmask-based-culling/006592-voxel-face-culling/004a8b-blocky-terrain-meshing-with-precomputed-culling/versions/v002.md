# Blocky Terrain Meshing with Precomputed Culling

Also called: Minecraft-style meshing, VoxelBlockyLibrary meshing

## Overview
Blocky Terrain Meshing with Precomputed Culling is a surface extraction method for blocky terrains that optimizes mesh generation by avoiding full Constructive Solid Geometry (CSG) operations at runtime. It solves the performance bottleneck of determining face occlusion by using a matrix of precomputed bitmasks to determine if one face covers another, enabling fast culling decisions. Unlike sibling methods that may rely on runtime rasterization or complex polygonal LOD selection, this approach precomputes model rotations and flipping to eliminate work that boils down to simple lookups [S1].

## How it works
The method operates in two phases: a library baking phase and a runtime meshing phase.

### Inputs and Outputs
- **Inputs**: A library of voxel models (e.g., slabs, stairs, blocks). Each model consists of multiple "sides" or faces.
- **Outputs**: A "culling" matrix (bitmask table) and precomputed rotation/flip data for each model.

### Data Structures
1.  **Culling Matrix**: A 2D array or hash map where entry $(A, B)$ indicates if face $A$ covers face $B$. The value is typically a boolean or bitmask.
2.  **Model Metadata**: For each model, store precomputed rotation and flip states to allow lookup instead of geometric transformation during meshing.

### Steps
1.  **Precompute Model Transforms**: For each model in the library, precompute all necessary rotation and flipping states. This eliminates the need for geometric calculations during runtime meshing, reducing the process to simple lookups [S1].
2.  **Library Baking (Shape Detection)**:
    - Gather all shapes from the entire model library.
    - Use rasterization to check if two sides (faces) have the same shape. This involves rendering the silhouette or projection of each face and comparing the resulting pixel data or shape signatures [S1].
    - Compare all shapes against each other to generate the "culling" matrix. If face $A$ is geometrically identical to and occludes face $B$ in a specific orientation, mark $A$ as covering $B$ [S1].
3.  **Runtime Meshing**:
    - When generating a chunk, iterate through voxel faces.
    - Use the precomputed culling matrix to determine if a face should be generated. If a face is marked as covered by another face in the matrix, it is culled (not generated).
    - If not culled, generate the geometry for the face.

### Formulas
Not given in the sources. The culling decision is based on bitmask lookups rather than explicit geometric formulas.

### Parameters
- **Rasterization Resolution**: Not given in the sources. However, using very small triangles or very detailed faces may cause the rasterization-based shape detection to fail [S1].

### Edge Cases and Pitfalls
- **Transparency**: Full culling exposes underlying geometry if models are transparent. There is no general way to avoid this other than ensuring model sides always match (e.g., no glass slabs/stairs, water flow matching sides) [S1].
- **Detailed Geometry**: Relying on very small triangles or very detailed faces may cause the rasterization-based shape detection to not work out perfectly in certain cases [S1].
- **Experimental Status**: The feature is experimental and may have bugs, missing parts, or change over time [S1].

## Subtopics

### [Cube Mesh](13803-cube-mesh.md)
Cube Mesh is a voxel-based terrain rendering acceleration structure that replaces traditional polygonal meshes with a set of axis-aligned cubes enclosing height field data. It solves the convexity limitations of the Envelope method by using adaptive quadtree subdivision to generate a tight bounding volume hierarchy, enabling efficient ray casting with early ray termination. Unlike sibling methods that rely on full Constructive Solid Geometry (CSG) or complex polygonal LOD selection, Cube Mesh precomputes transformed unit cubes to minimize CPU computation for view-frustum culling and level-of-detail selection.

## Operating characteristics
- **Time Complexity**: Runtime meshing is fast due to precomputed lookups. The heavy lifting (rasterization and comparison) is done during the baking phase [S1].
- **Memory Complexity**: Requires storing the culling matrix and precomputed model transforms. Size depends on the number of unique faces and models in the library.
- **Strengths**: Fast runtime meshing; avoids complex CSG operations; simple lookups for occlusion checks [S1].
- **Limitations**: Transparency handling is problematic; rasterization-based shape detection may fail for very detailed geometry; experimental status [S1].
- **When to Use**: Blocky terrains where transparency is not a concern or can be managed by matching model sides (e.g., Minecraft-style games) [S1].
- **When Not to Use**: Scenes requiring transparent blocky models (e.g., glass slabs) or highly detailed non-blocky geometry [S1].

## Background
This method is used in the Voxel Tools engine for Godot, specifically in the `VoxelBlockyLibrary` and `VoxelMesherBlocky` components. It is designed to organize models for games and automate mesh generation for blocky terrains [S1]. The approach is inspired by techniques used in games like Minecraft, where full CSG is too expensive for real-time chunk generation [S1].
