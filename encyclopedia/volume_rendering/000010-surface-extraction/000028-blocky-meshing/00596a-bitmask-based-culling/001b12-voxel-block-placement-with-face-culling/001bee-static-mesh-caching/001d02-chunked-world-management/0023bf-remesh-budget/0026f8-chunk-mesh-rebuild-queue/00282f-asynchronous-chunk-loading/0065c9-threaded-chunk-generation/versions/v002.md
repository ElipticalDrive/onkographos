# Threaded Chunk Generation

Also called: Multi-threaded Chunk Generation

## Overview
Threaded Chunk Generation is a technique that generates chunk data (density, materials, mesh arrays) on worker threads to keep runtime generation smooth while chunks stream around the player [S1, unofficial]. It decouples heavy meshing computation from the main render loop by queuing tasks for background execution [G].

## How it works
**Inputs:** Chunk request coordinates, world seed, and generation parameters [G].
**Outputs:** Mesh arrays and collision data ready for application to the main thread's scene graph [G].

**Data Structures:**
*   **Chunk Request:** Contains world coordinates $(x, y, z)$ and chunk size $S$ [G].
*   **Worker State:** Per-thread buffers for density field $D$ of size $S^3$, material ID array $M$ of size $S^3$, and temporary mesh buffers [G].
*   **Result Buffer:** Thread-safe queue or future object holding the generated mesh data [G].

**Parameters:**
*   `Chunk Worker Count`: int, default 3, number of worker threads for chunk building [S1, unofficial].
*   `Max Chunk Loads Per Frame`: int, default 1, limits chunk loading per frame [S1, unofficial].
*   `Max Chunk Results Applied Per Frame`: int, default 1, limits mesh application per frame [S1, unofficial].

**Steps:**
1. Chunk Request is issued.
2. Worker Thread Builds Density + Materials + Mesh Arrays.
3. Main Thread Applies Mesh + Collision [S1, unofficial].

**Pseudocode:**
```python
import queue
import threading

CHUNK_WORKER_COUNT = 3
MAX_CHUNK_LOADS_PER_FRAME = 1
MAX_CHUNK_RESULTS_APPLIED_PER_FRAME = 1

request_queue = queue.Queue()
result_queue = queue.Queue()

def worker_thread_loop(worker_id):
    while True:
        request = request_queue.get()
        if request is None:
            break
        # Step 2: Worker Thread Builds Density + Materials + Mesh Arrays
        density_field = [0.0] * (request.chunk_size ** 3)  # Generate density field for chunk coordinates [G]
        materials = [0] * (request.chunk_size ** 3)        # Compute material IDs based on density [G]
        mesh_arrays = []                                   # Run surface extraction algorithm on density [G]
        result_queue.put({
            'coords': request.coords,
            'mesh': mesh_arrays,
            'collision': []  # Generate collision data from mesh arrays [G]
        })

def main_thread_loop():
    loads_this_frame = 0
    while loads_this_frame < MAX_CHUNK_LOADS_PER_FRAME:
        if request_queue.empty():
            break
        request = request_queue.get()
        # Dispatch to worker pool
        threading.Thread(target=worker_thread_loop, args=(request,)).start()
        loads_this_frame += 1

    applied_this_frame = 0
    while applied_this_frame < MAX_CHUNK_RESULTS_APPLIED_PER_FRAME:
        if result_queue.empty():
            break
        result = result_queue.get()
        # Apply mesh and collision data to scene graph [G]
        scene_graph.add_mesh(result.coords, result.mesh, result.collision)
        applied_this_frame += 1

workers = []
for _ in range(CHUNK_WORKER_COUNT):
    t = threading.Thread(target=worker_thread_loop, args=(0,))
    t.start()
    workers.append(t)
```

**Edge Cases and Pitfalls:**
*   **Race Conditions:** If the main thread applies a mesh before the worker finishes, data corruption occurs. Use futures or strict queue ordering [G].
*   **Memory Fragmentation:** Frequent allocation of mesh arrays on worker threads can cause fragmentation. Reuse buffers where possible [G].

## Subtopics

### Unity Job System Chunk Rendering
Uses Unity's Job System to generate and render chunks in parallel, storing block types in structs and chunk info as `ushort` arrays [S2, unofficial]. It converts `ushort[]` to `NativeArray`, processes it in a job, and converts back to `ushort[]` after job completion [S2, unofficial]. Each chunk is a separate `GameObject` storing `ushort[chunksize^3]` [S2, unofficial]. Blocktype data is stored in structs, and BlockID is stored as `ushort` [S2, unofficial]. This approach generates and renders $16^3$ chunks of $16^3$ blocks in 3-4 frames at 10fps, or delays ~10 seconds for the whole thing to render at 60fps [S2, unofficial]. A single chunk renders in ~200ms [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Not given in the sources.
*   **Measured Performance:** In Unity implementations, single chunk rendering takes ~200ms [S2, unofficial]. For an infinite world, this multithreaded approach makes heavy math nearly imperceptible as chunks render instantly relative to player movement [S2, unofficial].
*   **Strengths:** Keeps the main thread responsive and smooths out frame rate spikes during chunk streaming [S1, unofficial].
*   **Limitations:** Requires careful synchronization and incurs overhead for thread management and data transfer between worker and main threads [G].
*   **When to Use:** Infinite or large procedural worlds where chunk generation is a bottleneck [S1, unofficial].
*   **When Not to Use:** Small, static worlds where generation cost is negligible compared to threading overhead [G].

## Background
Originated in voxel engine development to handle the computational cost of procedural terrain generation in real-time [G]. The technique is a standard component of modern chunked voxel architectures, building on [Asynchronous Chunk Loading](4216-asynchronous-chunk-loading.md) by adding computational parallelism to the meshing phase [G].
