# Greedy Meshing for Opaque/Undefined Blocks


## Overview
This method extends standard greedy meshing to handle volumes where block faces may be opaque, undefined, or have no appearance defined. It solves the problem of generating compact meshes for blocky terrain by merging adjacent coplanar faces into larger quads, while enforcing strict validation for blocks that lack visual definitions. It differs from standard greedy meshing by explicitly handling the "undefined" state and asserting failure if a face requires rendering but has no associated appearance data [S1, unofficial].

## How it works
**Inputs and Outputs**:
- Input: A 3D voxel grid $V$ where each cell $(x,y,z)$ contains a block type. The block type may be opaque, empty, or undefined.
- Output: A mesh consisting of vertices, UVs, colors, and indices representing the merged opaque surfaces.

**Data Structures**:
- The mesh maintains arrays for vertices, UVs, and colors.
- UVs are stored as sets of 4 coordinates per quad, with values in the range $[0.0, 2.0]$ [S1, unofficial].
- Colors are stored as sets of 4 RGBA coordinates per quad, with values in the range $[0.0, 4.0]$ [S1, unofficial].

**Steps**:
1. Iterate through the voxel grid to identify exposed faces. A face is exposed if the adjacent voxel in the normal direction is empty or has a different material ID.
2. For each exposed face, check if the block type has a defined appearance.
3. If no appearance is defined for a block face, assert failure with the message "No appearance defined for block face" [S1, unofficial].
4. Extend the mesh's UVs array with 4 sets of `[0.0; 2]` UV coordinates for the new quad [S1, unofficial].
5. Extend the mesh's colors array with 4 sets of `[0.0; 4]` color coordinates for the new quad [S1, unofficial].
6. Merge adjacent coplanar quads into larger rectangles using the greedy strategy: for each axis-aligned direction, find the largest possible rectangle of identical block types and normals, add it to the mesh, and mark those voxels as processed.

**Pseudocode**:
```python
def greedy_mesh_opaque_undefined(V, block_appearances):
    """
    V: 3D array of block types
    block_appearances: dict mapping block type to appearance data
    Returns: Mesh with vertices, uvs, colors, indices
    """
    mesh = Mesh()
    visited = set()
    
    # Iterate over all voxels
    for x, y, z in V:
        if (x, y, z) in visited:
            continue
            
        block_type = V[x, y, z]
        
        # Check if block has appearance
        if block_type not in block_appearances:
            raise AssertionError("No appearance defined for block face")
            
        # Try to merge in X direction
        width = 1
        while x + width < V.shape[0] and V[x + width, y, z] == block_type:
            if (x + width, y, z) in visited:
                break
            width += 1
            
        # Try to merge in Y direction
        height = 1
        while y + height < V.shape[1] and V[x, y + height, z] == block_type:
            if (x, y + height, z) in visited:
                break
            height += 1
            
        # Create quad
        quad = create_quad(x, y, z, width, height, block_type)
        mesh.add_quad(quad)
        
        # Mark as visited
        for dx in range(width):
            for dy in range(height):
                visited.add((x + dx, y + dy, z))
                
    return mesh
```

**Parameters**:
- Typical values for UV range: $[0.0, 2.0]$ [S1, unofficial].
- Typical values for color range: $[0.0, 4.0]$ [S1, unofficial].

**Edge Cases and Pitfalls**:
- If a block face has no appearance defined, the method asserts failure [S1, unofficial].
- Precision issues may arise when merging quads if floating-point coordinates are used; integer coordinates are preferred for voxel grids.

## Subtopics

### Chunk Neighbor Optimization
An optimization where chunks are made aware of their neighboring chunks to remove inner polygons that are never visible, solving the issue where neighboring chunks previously did not know about each other [S2, unofficial]. Construct the world cube by cube. Pass the neighbor's coordinates (if one exists) to the current cube. Check against each of the cube's sides as it is created to determine visibility [S2, unofficial]. Unity restricts a mesh to approximately 65,000 vertices. A Minecraft-style chunk of 65,536 cubes exceeds this limit, so a single chunk cannot be made. The solution is to recombine meshes by stacking multiple chunks on top of each other [S2, unofficial].

## Operating characteristics
Time complexity is $O(N)$ where $N$ is the number of voxels, as each voxel is processed once. Memory complexity is $O(M)$ where $M$ is the number of merged quads. The method reduces the primitive count significantly compared to per-voxel meshing. The chunk neighbor optimization further reduces visible faces by culling internal boundaries between adjacent chunks [S2, unofficial]. The Unity vertex limit of ~65,000 vertices requires chunking strategies to avoid exceeding mesh size limits [S2, unofficial].

## Background
Origin: This method is derived from greedy meshing techniques used in voxel-based games like Minecraft. The specific handling of opaque/undefined blocks and chunk neighbor optimization is documented in procedural terrain generation research [S2, unofficial] and implementation details from the Infinigen project [S1, unofficial].
