# Task Shader Block-wise Stream Compaction

Also called: Task Shader Cell Classification and Task Generation

## Overview
Task Shader Block-wise Stream Compaction is a GPU-driven visibility determination technique that identifies volume blocks containing isosurface geometry and generates a compact list of those blocks to drive subsequent mesh shader workgroups [S1, S2]. It solves the problem of high draw times in scenes with high depth complexity by avoiding the extraction and rendering of geometry for blocks that are occluded by closer volume data [S1, S2]. Unlike its siblings, it operates on a flat list of fixed-size blocks rather than a hierarchical structure, using a custom task and mesh shader pipeline to detect occupancy before generating proxy geometry [S1, S2]. It outperforms methods that process depth textures of previously established occluder representations, such as hierarchical occlusion maps [ZMHH97] and iterative depth warping [LKE18] [S1, S2].

## How it works
The method functions as a lightweight raster occlusion culling pass that is a hybrid between basic raster occlusion culling [KT14] and hierarchical raster occlusion culling [LL20] [S1, S2]. It resolves potential visibility only for fixed-size blocks, using a custom task and mesh shader pipeline to efficiently detect occupied blocks before creating proxy geometry [S1, S2].

**Inputs and Outputs:**
*   **Input:** A volume dataset organized into fixed-size blocks; a min-max texture storing the scalar value range for each block; the isovalue for extraction.
*   **Output:** A dense list of indices for occupied blocks; mesh shader workgroups dispatched to process these blocks.

**Data Structures:**
*   **Min-Max Texture:** Stores the minimum and maximum scalar values for each volume block. Accessed via texture sampling.
*   **Block Occupancy Index Array:** A dense array storing the indices of blocks determined to contain isosurface geometry.
*   **Num Occupied Blocks:** A scalar value indicating the total count of occupied blocks found in the current task shader workgroup.

**Parameters:**
*   **Task Shader Workgroup Size:** Processes a localized group of 256 blocks [S1].
*   **Mesh Shader Workgroup Size:** Each mesh shader workgroup processes sets of 32 occupied blocks [S1]. The final workgroup may process between 1 and 32 blocks [S1].
*   **Proxy Geometry:** A single quad per block, rather than three cube faces [S1, S2].

**Steps:**
1.  **Task Shader Analysis:** The task shader analyzes a localized group of 256 blocks [S1]. For each block, it samples the min-max texture at the corresponding location [S1].
2.  **Occupancy Determination:** The occupancy of each block is determined by checking if the isovalue lies between the sampled minimum and maximum values [S1].
3.  **Stream Compaction:** A dense list of occupied blocks is generated in the same manner as a dense list of occupied cells is created in the isosurface extraction stage [S1]. This involves a local prefix sum algorithm for stream compaction, avoiding atomic variables to improve performance [S2]. No list offset or length buffers are required because workgroups operate on fixed-length lists [S1].
4.  **Mesh Shader Dispatch:** The task shader emits mesh shader workgroups. Each workgroup processes 32 occupied blocks, except the final workgroup which may process 1–32 blocks [S1].
5.  **Proxy Geometry Creation:** In the mesh shader, each thread computes an offset into the `block_occupancy_index` array based on thread and workgroup indices, ensuring the index is less than `num_occupied_blocks` [S1]. Each active thread creates proxy geometry for one occupied block [S1].
6.  **Proxy Geometry Definition:** The proxy geometry for each block consists of a single quad containing the bounding box of the block projected into screen space with the minimal z-coordinate of the block's corners [S1, S2]. This reduces triangles from 6 to 2 per block, primitives per workgroup from 224 to 64, and vertices from 224 to 128 [S1].
7.  **Rasterization:** The proxy geometry is passed to the rasterizer [S1]. Fragments that pass the early depth test and representative fragment test write to a buffer to determine the final potentially visible set (PVS) [S1].

**Pseudocode:**

```python
# Task Shader Workgroup
# Processes 256 blocks
task_shader_workgroup(block_indices_256, min_max_texture, isovalue):
    occupied_indices = []
    
    # Step 1 & 2: Identify occupied blocks
    for i in range(256):
        block_idx = block_indices_256[i]
        min_val, max_val = sample_min_max_texture(min_max_texture, block_idx)
        
        # Check if isovalue lies between min and max
        if min_val <= isovalue <= max_val:
            occupied_indices.append(block_idx)
            
    # Step 3: Stream Compaction
    # Generate dense list of occupied blocks
    # Avoid atomic variables; use local prefix sum
    num_occupied = len(occupied_indices)
    
    # Write to shared memory or output buffer
    write_occupied_blocks(occupied_indices)
    write_num_occupied(num_occupied)
    
    # Step 4: Dispatch Mesh Shader Workgroups
    # Each mesh workgroup handles 32 blocks
    num_mesh_workgroups = ceil(num_occupied / 32)
    for w in range(num_mesh_workgroups):
        dispatch_mesh_shader_workgroup(w, num_occupied)

# Mesh Shader Workgroup
# Processes up to 32 occupied blocks
mesh_shader_workgroup(workgroup_id, num_occupied):
    # Step 5: Compute offset
    # Each thread handles one block
    thread_id = get_thread_id()
    
    if thread_id < num_occupied:
        # Compute offset into block_occupancy_index array
        # Based on thread and workgroup indices
        offset = compute_offset(thread_id, workgroup_id)
        block_idx = read_block_occupancy_index(offset)
        
        # Step 6: Create Proxy Geometry
        # Single quad per block
        # Bounding box projected into screen space with minimal z
        vertices = generate_quad_proxy(block_idx)
        
        # Write vertices and indices
        write_geometry(vertices)
```

**Edge Cases and Pitfalls:**
*   **Early Depth Testing:** Rasterizing fewer primitives increases the likelihood of early termination of rasterization via the representative fragment test [KTB*18] extension [S1]. This extension terminates early-depth testing if at least one fragment shader instance is invoked, but cannot terminate for multiple associated primitives [S1].
*   **Multi-View Rendering:** Using multi-view rendering features to rasterize proxy geometry per-eye in a joint pass is facilitated by generating one quad per eye [S1]. Rendering more than 3 sides of a cube would require accounting for blocks located between the viewer's eyes on cardinal axes [S1].
*   **Conservative Visibility:** The method ensures visibility determination is conservative rather than probabilistic [S1, S2].

## Subtopics

### [Raster Occlusion Culling](1562-raster-occlusion-culling.md)
Raster Occlusion Culling is a GPU-driven visibility determination technique that identifies a potentially visible set (PVS) of voxel blocks by rasterizing lightweight proxy geometry, replacing expensive individual hardware occlusion queries with a single efficient rasterization pass followed by GPU-driven stream compaction. It solves the problem of high draw times in scenes with high depth complexity by avoiding the extraction and rendering of geometry for blocks that are occluded by closer volume data. Unlike its siblings, it operates on a flat list of fixed-size blocks rather than a hierarchical structure, using a custom task and mesh shader pipeline to detect occupancy before generating proxy geometry. It outperforms methods that process depth textures of previously established occluder representations, such as hierarchical occlusion maps [ZMHH97] and iterative depth warping [LKE18].

### [PVS Compactification and Temporal Coherence Pass](1563-pvs-compactification-and-temporal-coherence-pass.md)
This compute shader pass compactifies the raw visibility indices generated by the preceding raster occlusion culling stage and constructs two distinct Potentially Visible Set (PVS) datasets: $PVS_{curr}$ and $PVS_{curr-prev}$. It solves the problem of efficiently preparing visibility data for temporal coherence by identifying blocks visible in the current frame and those newly visible since the last frame, enabling the selection of optimal occluders for subsequent rendering passes.

### [GPU-driven Visibility Culling](3640-gpu-driven-visibility-culling.md)
GPU-driven visibility culling is a technique that uses per-subchunk metadata (AABB, terrain/water draw ranges) to test visibility on the GPU and emit indirect draw commands only for visible subchunks. It differs from CPU-side culling by offloading the visibility test and command buffer population to the GPU, allowing the CPU to remain free for scene management and chunk loading. It builds on [Task Shader Block-wise Stream Compaction](1540-task-shader-block-wise-stream-compaction.md) by utilizing the metadata prepared there to drive the compute dispatch and indirect execution.

## Operating characteristics
*   **Time Complexity:** The task shader processes blocks in fixed groups of 256, and mesh shaders process occupied blocks in groups of 32. The complexity is linear with respect to the number of blocks processed, but significantly reduced by culling occluded blocks [S1].
*   **Memory Complexity:** Requires storage for the min-max texture and the block occupancy index array. No list offset or length buffers are required due to fixed-length workgroup operations [S1].
*   **Performance:** Rasterizing fewer primitives (2 triangles per block vs. 6) reduces buffer writes in the fragment shader stage and increases the likelihood of early depth testing termination [S1].
*   **Strengths:** Reduces the number of task shader workgroups launched for blocks that will not contribute to the displayed isosurface [S1]. Avoids atomic variables in stream compaction, improving extraction performance [S2].
*   **Limitations:** Operates on a single level of occlusion culling, unlike hierarchical methods [S1, S2]. Visibility determination is conservative, potentially including some occluded blocks [S1, S2].
*   **When to Use:** Scenes with high depth complexity where ray-marching performance is limited by resolution [S1]. When view-dependent visibility information can be exploited to reduce rendering overhead [S1, S2].
*   **When Not to Use:** Scenes with low depth complexity where the overhead of the culling pass may outweigh the benefits. When probabilistic culling is acceptable and a single level of culling is insufficient [S1, S2].

## Background
The technique was introduced in "Efficient Direct Isosurface Rasterization of Scalar Volumes" by Kubisch and Tavenrath [S1, S2]. It builds on prior work in raster occlusion culling [KT14, LL20] and probabilistic culling for particle rendering [IRR*22] [S1, S2]. The method addresses the linear dependence of ray-marching performance on display resolution by leveraging the optimization of modern GPU rasterization units [S1, S2]. It is used in real-time volume graphics for direct isosurface visualization [S1, S2].
