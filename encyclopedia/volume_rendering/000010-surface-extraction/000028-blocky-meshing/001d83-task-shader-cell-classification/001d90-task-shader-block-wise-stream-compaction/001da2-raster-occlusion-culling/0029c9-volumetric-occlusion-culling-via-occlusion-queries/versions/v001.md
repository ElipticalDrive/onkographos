# Volumetric Occlusion Culling via Occlusion Queries

Also called: Ray-based occlusion culling, Visibility detection using occlusion queries

## Overview
A visibility detection method that determines if a voxel block is visible (not fully occluded by closer voxels) by rasterizing its bounding box and checking for fragment depth test passes [S1, unofficial]. It differs from standard binary occlusion culling by incorporating accumulated opacity into the depth test, ensuring that blocks behind fully opaque foreground volumes are correctly culled [S1, unofficial].

## How it works
**Inputs and Outputs**
*   **Input:** A voxel block to test, defined by its bounding box; the current ray-marched depth buffer (framebuffer) containing the depth at which maximum opacity was reached for each pixel; camera projection and view matrices.
*   **Output:** A boolean visibility flag for the block, or a fragment count used for priority-based loading.

**Data Structures**
*   **Depth Buffer:** A 2D texture or render target storing floating-point depth values. Each pixel $(u, v)$ stores $D_{opacity}$, the depth along the view ray where accumulated opacity reached a threshold (typically 1.0), or 1.0 (near plane or max depth) if the ray did not reach full opacity [S1, unofficial].
*   **Bounding Box Geometry:** A triangulated mesh representing the axis-aligned bounding box (AABB) of the voxel block [S1, unofficial].

**Steps**
1.  **Prepare Depth Buffer:** During the ray marching pass, for each ray, write the depth $D_{opacity}$ at which the ray reaches total opacity to the framebuffer. If the ray does not reach total opacity within the volume, write the maximum depth value (e.g., 1.0 in normalized device coordinates or the far plane distance) [S1, unofficial].
2.  **Initialize Occlusion Query:** Begin an asynchronous GPU occlusion query [S1, unofficial].
3.  **Rasterize Bounding Box:** Rasterize the triangulated bounding box of the voxel block. This is a standard rasterization pass, not a ray trace [S1, unofficial].
4.  **Depth Test:** For each fragment generated by the bounding box, perform a depth test against the prepared depth buffer. A fragment passes if its depth is greater than the value stored in the depth buffer at that pixel location [S1, unofficial].
5.  **Interrogate Result:** Check if the occlusion query is complete. If not, the CPU thread synchronizes and waits for the GPU to finish the rasterization and query execution [S1, unofficial].
6.  **Determine Visibility:** Retrieve the number of fragments that passed the depth test. If the count is greater than zero, the block is considered visible [S1, unofficial].

**Formulas**
Let $D_{opacity}$ be the depth value stored in the framebuffer for a given pixel, representing the depth at which the ray reached total opacity. Let $D_{voxel}$ be the depth of the fragment generated by the voxel block's bounding box at that pixel.

The visibility condition for a specific ray/pixel is:
$$ D_{voxel} > D_{opacity} $$

If $D_{voxel} \le D_{opacity}$, the voxel is occluded by foreground matter that has already reached full opacity. If $D_{voxel} > D_{opacity}$, the voxel is visible [S1, unofficial].

For the entire block, the block is visible if:
$$ \exists \text{ fragment } f \in \text{RasterizedBox} : f.\text{depth} > \text{FrameBuffer}[f.\text{uv}] $$

**Parameters**
*   **Fragment Threshold:** The minimum number of fragments required to trigger block loading. This can be adjusted based on system load to prioritize the most visible blocks (e.g., requiring only 1 fragment for high priority, or a higher count for less visible blocks) [S1, unofficial].

**Pitfalls and Edge Cases**
*   **Projection Alignment:** Requires perfect alignment between the OpenGL projection/viewpoint and the ray tracing projection/viewpoint. Mismatched projections lead to incorrect visibility detection because the projected geometry of the bounding box will not correspond to the rays used in the depth buffer [S1, unofficial].
*   **Asynchronicity and Scheduling:** Occlusion queries are asynchronous. The CPU must anticipate visibility tests before tracing, but too much anticipation ignores unrendered foreground matter that might occlude the block. The scheduling must overlap query times with loading times of already detected visible blocks to hide latency [S1, unofficial].
*   **Degenerate Input:** If the depth buffer is not properly initialized with the $D_{opacity}$ values, standard depth testing will fail to account for opacity, leading to over-rendering of occluded blocks [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(1)$ per block for the query initiation, plus synchronization overhead. The rasterization cost is proportional to the surface area of the bounding box in screen space.
*   **Memory Complexity:** Requires a depth buffer compatible with the ray marching pass. No additional large data structures for the culling logic itself.
*   **Strengths:** Efficiently culls blocks behind fully opaque volumes. Leverages standard GPU hardware occlusion queries.
*   **Limitations:** Sensitive to projection mismatches. Requires careful scheduling to handle asynchronous query results and avoid stalling the CPU. Does not account for semi-transparent occlusion unless the depth buffer is modified to store partial opacity depths (not specified in source) [S1, unofficial].

## Background
This method is described in the context of interactive exploration of extended and detailed procedural volumes [S1, unofficial]. It adapts standard hardware occlusion queries to the specific requirements of volumetric rendering, where visibility depends on accumulated opacity rather than simple geometric occlusion [S1, unofficial].
