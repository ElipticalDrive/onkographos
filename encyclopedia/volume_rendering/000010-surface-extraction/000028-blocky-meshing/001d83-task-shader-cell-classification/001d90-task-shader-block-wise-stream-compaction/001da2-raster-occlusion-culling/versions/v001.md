# Raster Occlusion Culling

Also called: GPU-driven occlusion culling, Hybrid Raster Occlusion Culling, Lightweight Raster Occlusion Culling, Raster Occlusion Culling for Dense Volume Data

## Overview
Raster Occlusion Culling determines the visibility of voxel blocks by replacing expensive individual hardware occlusion queries with a single efficient proxy geometry rasterization pass, followed by GPU-driven stream compaction to create a dense list of occupied subvolumes [S1, S2, S3]. It solves the problem of high draw times in volumes with high depth complexity by avoiding the extraction and rendering of geometry for blocks that are occluded [S2, S3]. Unlike hierarchical methods that process depth textures of previously established occluders (e.g., hierarchical occlusion maps [ZMHH97] or iterative depth warping [LKE18]), this method rasterizes proxy geometry directly [S1, S2]. It is a hybrid between basic raster occlusion culling [KT14] and hierarchical approaches [LL20], resolving potential visibility only for fixed-size blocks using a custom task and mesh shader pipeline [S3].

## How it works
**Inputs:**
*   Volume data with precomputed min-max values for each block, stored in a 2-channel volume texture (min-max grid) [S3].
*   Resolution of the min-max grid: $X/U \times Y/V \times Z/W$, where $X, Y, Z$ are volume dimensions and $U, V, W$ are block dimensions [S3].
*   Isovalue for the isosurface extraction [S2].
*   Camera view and projection matrices [S3].

**Outputs:**
*   A dense list of occupied blocks (Potentially Visible Set, PVS) [S1, S2].
*   Two PVS sets for temporal coherence: $PVS_{curr}$ (blocks visible in the current frame, used as occluders in the next) and $PVS_{curr-prev}$ (blocks visible since the last frame) [S2, S3].

**Data Structures:**
*   **Min-Max Texture:** 2-channel volume texture storing the minimum and maximum scalar values for each block [S3].
*   **Visibility Buffer:** A preallocated buffer where fragments write the implicit ID of the block if it passes depth tests [S2, S3].
*   **Task Shader Interface Block:**
    ```c
    struct Task {
        uint32_t baseID;
        uint32_t num_occupied_blocks;
        uint8_t block_occupancy_index[256];
    };
    ```
    [S3]
*   **Mesh Shader Workgroup:** Processes sets of 32 occupied blocks [S2, S3].

**Steps:**

1.  **Task Shader: Block-wise Stream Compaction**
    The task shader analyzes a localized group of 256 blocks [S2, S3].
    *   For each block in the group, sample the min-max texture at the block's location [S2, S3].
    *   Determine occupancy by checking if the isovalue lies between the sampled minimum and maximum values:
        $$ \text{is\_occupied} = (\text{min} \le \text{isovalue} \le \text{max}) $$
        [S2, S3]
    *   Generate a dense list of occupied blocks. The task shader emits mesh shader workgroups, each processing 32 occupied blocks (except possibly the final workgroup, which processes 1–32 blocks) [S2, S3].
    *   Since mesh shader workgroups operate on lists of fixed lengths, no list offset or length buffers are required in the interface block [S2, S3].

2.  **Mesh Shader: Proxy Geometry Creation**
    Each thread in the mesh shader workgroup computes an offset into the `block_occupancy_index` array based on thread and workgroup indices, ensuring the index is less than `num_occupied_blocks` [S3].
    *   Each active thread creates proxy geometry for one occupied block [S2, S3].
    *   The proxy geometry is a single quad containing the bounding box of the block when projected into screen space, with the minimal z-coordinate of the block's corners [S2, S3].
    *   This reduces the number of triangles per block from 6 to 2, and vertices per workgroup (32 blocks) from 224 to 128 [S2, S3].

3.  **Rasterization**
    The proxy geometry is passed to the rasterizer [S2, S3].
    *   Each fragment that passes the early depth test and the representative fragment test writes into a preallocated slot of the visibility buffer, based on the implicit ID of each block [S2, S3].
    *   The representative fragment test extension allows the rasterizer to terminate early-depth testing earlier if at least one fragment shader instance was invoked [S2].

4.  **PVS Generation and Compactification**
    *   A bit compactification kernel runs for the currently created indices $PVS_{curr}$ [S2, S3].
    *   A final compute shader pass builds two PVS sets: $PVS_{curr}$ and $PVS_{curr-prev}$ [S2, S3].
    *   $PVS_{curr}$ is used in the next frame to render the best occluders based on temporal coherence [S2, S3].
    *   $PVS_{curr-prev}$ determines blocks that became visible since the last frame [S2, S3].
    *   Compute shaders are used for this pass to allow larger block sizes and better utilization of streaming multiprocessors compared to mesh shaders [S2, S3].

**Pseudocode:**

```python
# Task Shader: Block-wise Stream Compaction
# Input: min_max_texture, isovalue, block_group (256 blocks)
# Output: num_occupied_blocks, block_occupancy_index

num_occupied_blocks = 0
for i in range(256):
    # Sample min-max texture for block i
    min_val, max_val = sample_min_max_texture(block_group[i].position)
    
    # Check occupancy
    if min_val <= isovalue <= max_val:
        block_occupancy_index[num_occupied_blocks] = i
        num_occupied_blocks += 1

# Emit mesh shader workgroups
# Each workgroup processes 32 blocks
num_workgroups = ceil(num_occupied_blocks / 32.0)
for wg in range(num_workgroups):
    emit_mesh_shader_workgroup(wg, num_occupied_blocks, block_occupancy_index)

# Mesh Shader: Proxy Geometry Creation
# Input: num_occupied_blocks, block_occupancy_index, thread_id, workgroup_id
# Output: vertex_buffer, index_buffer

thread_offset = workgroup_id * 32
if thread_id + thread_offset < num_occupied_blocks:
    block_idx = block_occupancy_index[thread_id + thread_offset]
    
    # Get block bounding box corners
    corners = get_block_corners(block_idx)
    
    # Project corners to screen space
    screen_corners = [project_to_screen(c) for c in corners]
    
    # Find minimal z-coordinate among corners
    min_z = min(c.z for c in screen_corners)
    
    # Create single quad proxy
    # Quad vertices: screen_corners projected with min_z
    # Indices: 0,1,2, 0,2,3 (2 triangles)
    write_to_vertex_buffer(screen_corners, min_z)
    write_to_index_buffer([0, 1, 2, 0, 2, 3])

# Fragment Shader: Visibility Buffer Update
# Input: fragment_position, block_id
# Output: visibility_buffer

if passes_early_depth_test() and passes_representative_fragment_test():
    visibility_buffer[fragment_position.slot] = block_id

# Compute Shader: PVS Compactification
# Input: visibility_buffer
# Output: PVS_curr, PVS_curr_prev

PVS_curr = compact_indices(visibility_buffer)
PVS_curr_prev = compute_previous_visible(PVS_curr, previous_frame_PVS)
```

**Parameters:**
*   **Block analysis size:** 256 blocks per task shader workgroup [S3].
*   **Mesh shader workgroup size:** 32 blocks [S3].
*   **Min-max texture resolution:** $X/U \times Y/V \times Z/W$ [S3].
*   **Representative Fragment Test:** An extension allowing early-depth termination if at least one fragment shader instance was invoked [S2].

**Edge Cases and Pitfalls:**
*   **Multi-view Rendering:** When using multi-view rendering (per-eye), generating one quad per eye is straightforward. Using three cube faces would require accounting for rendering more than 3 sides if the block is located between the viewer's eyes on any cardinal axis [S2, S3].
*   **Conservatism:** The method is conservative, not probabilistic, ensuring no occupied blocks are incorrectly culled [S3].
*   **Precision:** The min-max texture lookup must be precise enough to determine if the isovalue lies between min and max [S2, S3].

## Subtopics

### [Occlusion Culling Granularity](1671-occlusion-culling-granularity.md)
*   **What it is:** A technique where triangles are marked as visible and forwarded to graphics hardware rather than being rendered by the CPU, allowing the GPU to determine actual visibility and handle occlusion.
*   **How it works:** Project the polygon onto the top meta-tile of a hierarchical structure. Recursively check only those subtiles in which the polygon might be visible, leading to a logarithmic search. If a meta-cell size is approximately the size of a single pixel, stop recursion and forward a single point with an associated normal to the graphics hardware. The normal is estimated by calculating the gradient of the field.
*   **When to choose it:** When logarithmic search time for visibility testing is desired due to a hierarchical structure, and when the graphics accelerator can efficiently determine visible pieces and render them.
*   **Comparison:** Differs from Greene's implementation by not rendering the visible portion on the CPU; instead, it relies on the graphics accelerator to determine visible pieces and render them correctly.

## Operating characteristics
*   **Time Complexity:** Logarithmic search time for visibility testing in hierarchical variants [S4]. The basic raster occlusion culling replaces expensive individual hardware occlusion queries with one efficient proxy geometry rasterization pass [S1, S2].
*   **Memory Complexity:** Requires storage for the min-max texture ($X/U \times Y/V \times Z/W$ 2-channel volume texture) [S3] and visibility buffers [S2, S3].
*   **Measured Performance:** Outperforms methods that process the depth texture of a previously established occluder representation, such as hierarchical occlusion maps [ZMHH97] and iterative depth warping [LKE18] [S1, S2].
*   **Scaling:** Better utilization of streaming multiprocessors when using compute shaders for PVS compactification compared to mesh shaders [S2, S3].
*   **Strengths:** Reduces the number of task shader workgroups launched, avoiding geometry extraction for invisible blocks [S2, S3]. Fewer primitives (2 triangles per block vs 6) increase the likelihood of early-depth termination via the representative fragment test [S2, S3]. Conservative visibility determination ensures no occupied blocks are incorrectly culled [S3].
*   **Limitations:** Requires precomputed min-max values for each block [S3]. Multi-view rendering requires careful handling of proxy geometry per eye [S2, S3].
*   **When to use it:** For volumes with high depth complexity where reducing draw times is critical [S2, S3].
*   **When not to use it:** When probabilistic culling is acceptable and hierarchical structures are already available [S3].

## Background
Raster Occlusion Culling was introduced by Kubisch and Tavenrath [KT14] as the state-of-the-art approach for general scenes [S1, S2]. Historically, GPU-driven occlusion culling was facilitated by occlusion query objects [CCG*07], which required careful use of spatial and temporal coherence to be effective, as shown by Bittner et al. [BWPP04] and Mattausch et al. [MBW08] [S1, S2, S3]. Follow-up works include Lee and Lee [LL20] (iterative version on hierarchy levels) and Lee et al. [LJSL21] (fully GPU-driven hierarchical algorithm refining visibility via ray traversal) [S1, S2, S3]. The method described here is a hybrid between basic raster occlusion culling [KT14] and hierarchical raster occlusion culling [LL20], using a custom task and mesh shader pipeline to efficiently detect occupied blocks before creating proxy geometry [S3]. It is distinct from probabilistic culling methods like those by Ibrahim et al. [IRR*22] [S3].
