# Block face vertex layout

Also called: Block.h block_faces, Cube Geometry Definition, Cube face vertices

## Overview
Block face vertex layout defines the static geometric primitives for a unit cube, serving as the fundamental mesh template for blocky meshing algorithms [S1, S2, unofficial]. It specifies the positions, colors, and texture coordinates for the six faces of a cube, allowing surface extraction methods to generate meshes by instantiating these faces for visible voxel boundaries [S2, unofficial]. It differs from sibling methods like [Greedy Meshing](1776-greedy-meshing.md) or [Boolean Voxel Meshing](971-boolean-voxel-meshing.md) by providing only the raw vertex data for individual faces without performing topology optimization, face culling, or merging of adjacent coplanar faces [G].

## How it works
The method constructs a unit cube mesh centered at the origin or defined in local space, consisting of 6 faces [S1, S2, unofficial]. Each face is composed of 2 triangles, resulting in 6 vertices per face and 36 vertices total for the complete cube [S2, unofficial]. The layout supports instanced rendering where the base geometry is constant, and instance attributes (position, color, texture index) vary per voxel [G].

### Inputs and Outputs
- **Input**: None (static definition) [S1, S2, unofficial].
- **Output**: Vertex buffer data containing positions, colors, and UV coordinates for 36 vertices [S1, S2, unofficial].

### Data Structures
Two primary data structures define the geometry [S1, S2, unofficial]. The first, used in [S1, unofficial], defines a unit cube with corners at $(0,0,0)$ to $(1,1,1)$ and uses an index-based quad-to-triangle mapping. The second, used in [S2, unofficial], defines a cube centered at $(0,0,0)$ with corners at $\pm 0.5$ and uses a flat array of explicit vertex attributes.

#### Index-Based Unit Cube (Source [S1, unofficial])
This structure defines 8 unique vertices and maps them to 12 triangles (6 quads) via indices [S1, unofficial].

1.  **Vertices Array (`Cube.vertices`)**: 8 `Vector3` elements [S1, unofficial].
    -   Index 0: $(0, 0, 0)$
    -   Index 1: $(1, 0, 0)$
    -   Index 2: $(1, 1, 0)$
    -   Index 3: $(0, 1, 0)$
    -   Index 4: $(0, 0, 1)$
    -   Index 5: $(1, 0, 1)$
    -   Index 6: $(1, 1, 1)$
    -   Index 7: $(0, 1, 1)$

2.  **UV Offsets Array (`Cube.uvOffsets`)**: 4 `Vector2` elements [S1, unofficial].
    -   Index 0: $(0, 0)$
    -   Index 1: $(0, 1)$
    -   Index 2: $(1, 0)$
    -   Index 3: $(1, 1)$

3.  **Quad Index Mapping (`Cube.quads`)**: Flattened array of 24 integers, representing 6 quads (4 indices each) [S1, unofficial]. The order corresponds to faces: Front (Z+), Back (Z-), Right (X+), Left (X-), Top (Y+), Bottom (Y-) [S1, unofficial].
    -   Values: `[0, 3, 1, 2, 5, 6, 4, 7, 3, 7, 2, 6, 1, 5, 0, 4, 4, 7, 0, 3, 1, 2, 5, 6]`
    -   Face 0 (Front, Z+): Indices `0, 3, 1, 2` [S1, unofficial]
    -   Face 1 (Back, Z-): Indices `5, 6, 4, 7` [S1, unofficial]
    -   Face 2 (Right, X+): Indices `3, 7, 2, 6` [S1, unofficial]
    -   Face 3 (Left, X-): Indices `1, 5, 0, 4` [S1, unofficial]
    -   Face 4 (Top, Y+): Indices `4, 7, 0, 3` [S1, unofficial]
    -   Face 5 (Bottom, Y-): Indices `1, 2, 5, 6` [S1, unofficial]

4.  **Triangle Offset Mapping (`Cube.quadsOffsetForTris`)**: Array of 6 integers mapping quad indices to triangle vertices [S1, unofficial].
    -   Values: `[0, 1, 2, 2, 1, 3]`
    -   This allows iterating $t$ from 0 to 5 to get the two triangles for each quad [S1, unofficial]. For a given face $f$, the triangle vertices are derived from `quads[4*f + quadsOffsetForTris[t]]` [S1, unofficial].

### Pseudocode
The following Python-like function implements the triangle index generation from the quad mapping described in [S1, unofficial]:

```python
def generate_face_triangles(face_index, quads, quads_offset_for_tris, vertices):
    """Generate 6 vertex indices for a single face from the quad mapping."""
    quad_start = face_index * 4
    tri_indices = []
    for t in range(6):
        quad_idx = quads[quad_start + quads_offset_for_tris[t]]
        tri_indices.append(vertices[quad_idx])
    return tri_indices
```

### Parameters and Edge Cases
- **Cube Size**: The sources define a unit cube (side length 1) [S1, S2, unofficial].
- **Centering**: Source [S1, unofficial] uses $[0,1]^3$, while [S2, unofficial] uses $[-0.5, 0.5]^3$ [S1, S2, unofficial].
- **Color Variation**: [S2, unofficial] assigns different base colors to different faces (Z-faces: 0.9, X-faces: 0.8, Y-faces: 1.0) [S2, unofficial].
- **UV Mapping**: The UVs in [S2, unofficial] are not standard planar projections for all faces; they are specific to the face's orientation to ensure texture alignment [S2, unofficial].

## Operating characteristics
- **Time Complexity**: $O(1)$ to generate the static vertex buffer [G].
- **Memory Complexity**: $O(1)$ for the static mesh data (36 vertices) [G].
- **Performance**: Rendering requires one draw call per visible face if not instanced, or one instanced draw call per chunk/region if instancing is used [G].
- **Strengths**: Simple to implement, minimal memory overhead for the mesh definition, supports instancing efficiently [G].
- **Limitations**: High vertex count for large scenes if not culled, no topology optimization (no greedy meshing), potential for overdraw if backfaces are not culled [G].
- **Culling Dependency**: The lack of face culling in the layout itself means the mesh generation step (handled by parent methods like [Face Culling and Visibility Optimization](3861-face-culling-and-visibility-optimization.md)) determines the actual vertex count sent to the GPU [G].

## Background
The block face vertex layout is a standard technique in voxel rendering, particularly in games like Minecraft and its clones [G]. It provides a simple, unoptimized mesh for each voxel face [G].
