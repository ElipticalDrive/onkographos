# Voxel Block Shape & Culling Configuration

Also called: Block trait interface, Shape enum system

## Overview
This method defines the geometric and rendering properties of individual voxel types within a chunk-based meshing pipeline. It maps specific block IDs to their 3D geometry (shape), transparency behavior (culling mode), and lighting values. It solves the problem of heterogeneous voxel types (e.g., water, glass, slopes) requiring different mesh generation strategies and rendering passes, ensuring that faces are only generated for visible surfaces and that materials are correctly assigned. It sets apart from generic face culling by integrating shape definition and material classification directly into the block's configuration trait, allowing the mesh generator to query geometry and culling rules in a single lookup [S1, unofficial].

## How it works
The system operates as a trait or interface-based configuration where each block type implements specific methods to return its shape, culling mode, and lighting. The mesh generator iterates through non-empty voxels, queries these properties, and generates vertices/indices accordingly.

### Inputs and Outputs
- **Input**: The block type (enum or ID) at voxel position $P$.
- **Output**: A set of vertices and indices for the mesh, along with metadata (lighting, transparency) for the rendering pipeline.

### Data Structures

#### Block Trait Interface
Each block type implements a trait (or interface) that provides:
1.  `shape()`: Returns the geometric shape of the block.
2.  `cull_mode()`: Returns the culling strategy.
3.  `light()`: Returns the lighting value for the block.

#### Shape Enum
The `Shape` enum defines the geometry. Common variants include:
-   `WholeBlock`: A standard 1x1x1 cube.
-   `Cross(CrossInfo)`: A cross-shaped block (e.g., chains, rails) defined by an aligned face and stretch.
-   `Ramp`: A sloped block (see Subtopics).
-   `Fluid`: A block that only generates top faces (see Subtopics).

#### CullMode Enum
The `CullMode` enum defines how faces are culled based on neighbor transparency:
-   `Empty`: No faces generated (e.g., Air).
-   `Opaque`: Standard face culling; faces are hidden if a solid neighbor exists.
-   `TransparentMerged(T)`: Faces are hidden if a neighbor has the same `TransparentGroup` $T$ and is transparent. Shared faces between two transparent blocks with the same group are culled.
-   `TransparentUnmerged`: Faces are never merged with neighbors; all exposed faces are generated.

### Numbered Steps

1.  **Block Query**: For each non-empty voxel at position $P$ with block type $B$:
    a.  Retrieve `shape = B.shape()`.
    b.  Retrieve `cull = B.cull_mode()`.
    c.  Retrieve `light = B.light()`.

2.  **Face Iteration**: Iterate through the 6 faces of the block's geometry. For each face with normal $N_{face}$:
    a.  Calculate neighbor position $P_{neighbor} = P + N_{face}$.
    b.  Check if a voxel exists at $P_{neighbor}$. If not, the face is exposed.
    c.  If a neighbor exists, determine culling:
        i.  If `cull` is `Opaque`, check if the neighbor is solid. If yes, cull the face.
        ii. If `cull` is `TransparentMerged(T)`, check if the neighbor has the same `TransparentGroup` $T$. If yes, cull the shared face.
        iii. If `cull` is `TransparentUnmerged`, do not cull based on neighbor transparency.

3.  **Geometry Generation**:
    a.  If the face is not culled, generate vertices based on `shape`.
    b.  For `WholeBlock`, generate 4 vertices for the face.
    c.  For `Cross`, generate vertices based on the cross geometry.
    d.  For `Ramp`, generate slope and side triangles (see Subtopics).
    e.  For `Fluid`, generate only the top face if exposed (see Subtopics).

4.  **Vertex Assembly**:
    a.  For each vertex, compute `pos`, `uv`, `normal`, `ao`, `smooth_light`, and `block`.
    b.  Add the vertex to the chunk's vertex buffer.
    c.  Add indices to form triangles.

5.  **Mesh Finalization**:
    a.  After all voxels are processed, transfer vertex and index data to the GPU mesh object.

### Formulas
-   **Neighbor Position**: $P_{neighbor} = P + N_{face}$
-   **Culling Condition (TransparentMerged)**: Cull face if $Block(P_{neighbor}).TransparentGroup == Block(P).TransparentGroup$ and $Block(P_{neighbor}).IsTransparent$.

### Parameters
-   `FLUID_ENABLED`: Boolean flag. If true, fluid blocks generate mesh. If false, they are treated as empty.
-   `TransparentGroup`: A value (e.g., integer or hash) assigned to transparent blocks to group them for merging.

### Edge Cases and Pitfalls
-   **Fluid Shape**: Setting `FLUID_ENABLED` to true without implementing the fluid shape logic causes a debug assertion failure rather than silently drawing fluids as cubes [S1, unofficial].
-   **Threading**: In Unity3D, mesh creation must occur on the main thread, while vertex/index calculation can be done on a background thread [S3, unofficial].
-   **Shape Mismatch**: If a block's shape is not defined for a specific face (e.g., a ramp's back face), the system must fallback to a default (e.g., cube back face) or cull the face [S2, unofficial].

## Subtopics

### [Three-Valued Opacity Classification for Meshing](4414-three-valued-opacity-classification-for-meshing.md)
A classification system for block IDs into three mutually exclusive layers: 'opaque', 'water', and 'transparentSolid'. It solves the insufficiency of a single boolean 'transparent' flag by distinguishing between fluids (water) requiring bespoke shaders and see-through solids (glass/leaves) requiring alpha blending. Unlike a boolean transparent flag which collapses water and glass/leaves into one category, this three-valued model allows water to use a bespoke shader (ripple, refraction) while glass/leaves use the ordinary block atlas with alpha blending.

### Ramp Shape Geometry
A shape representing a sloped block face, composed of a slope quad (2 triangles) and two side triangles (left and right) [S2, unofficial]. Instance creation iterates visible faces; if the face is Left, Right, Top, or Front, `drawSlope` is set to true and tint is assigned based on face type (Top/Front: `tints[0]`, Left: `tints[1]`, Right: `tints[2]`). If a specific tint is `Vector3.One`, it falls back to another face's tint. Slope vertices are defined as: (0,1,0) UV[0], (0,0,1) UV[1], (1,1,0) UV[2], (1,1,0) UV[3], (0,0,1) UV[4], (1,0,1) UV[5]. Left triangle vertices: (0,0,1) UV[0], (0,1,0) UV[1], (0,0,0) UV[2]. Right triangle vertices: (1,0,0) UV[0], (1,1,0) UV[1], (1,0,1) UV[2] [S2, unofficial].

### Fluid Surface Stitching
A mesh generation technique where fluid columns share a surface height field with neighbors, stitching surfaces when fluid IDs match [S1, unofficial]. Two adjacent fluid blocks join their surfaces only when their `FluidInfo::id` (u8) values are equal [S1, unofficial].

### Geometry Builder Pattern
A design pattern using an interface to control the type of geometry created for each non-empty voxel, allowing different geometry types (cubes, ramps, X-shapes) to be generated via polymorphism without large switch statements [S3, unofficial]. The interface `IGeometryBuilder` contains a single function `BuildGeometry()`. During mesh creation, `BuildGeometry()` is called once for each non-empty block, passing a reference to the chunk object. The builder adds vertices and indices to the chunk's linked list. After all blocks are processed, the vertex and index data is placed into a Unity3D Mesh object on the main thread [S3, unofficial]. Pitfall: Unity3D functions must be called on the main thread, so final mesh creation must be moved from the background thread where calculation occurs [S3, unofficial].

## Operating characteristics
-   **Time Complexity**: $O(V)$ where $V$ is the number of voxels in the chunk, as each voxel is processed once. Face culling is $O(1)$ per face using hash set or grid lookup.
-   **Memory Complexity**: $O(F)$ where $F$ is the number of visible faces. The vertex and index buffers scale with the surface area of the voxel world.
-   **Performance**: Reduces triangle count significantly compared to brute-force cube instantiation (12 triangles per cube vs. 2-6 triangles per exposed face).
-   **Strengths**: Supports heterogeneous block types, efficient culling, and flexible geometry.
-   **Limitations**: Requires careful handling of threading (e.g., Unity3D main thread constraint) and shape definitions for non-cube blocks.

## Background
This method is commonly used in voxel-based games and simulations (e.g., Minecraft-like worlds) to optimize rendering of large voxel environments. It evolved from simple face culling to include complex shape definitions and material classification to support diverse block types and visual effects.
