# GPU Geometry Assembly and Coordinate Conversion

Also called: GPURenderer, GPURenderer Face Triangulation and Coordinate Conversion

## Overview
This method converts raw voxel face data into typed arrays (position, normal, UV, index, color) suitable for direct upload to a GPU buffer (e.g., WebGL or WebGPU `BufferGeometry`) [S1, unofficial]. It solves the problem of transforming engine-internal voxel coordinates into a target graphics API coordinate system while ensuring correct triangle winding order [S1, unofficial]. It differs from [Voxel Face Mesh Generation](4212-voxel-face-mesh-generation.md) by handling the coordinate system conversion and winding correction logic explicitly, whereas the parent method focuses on populating a generic `MeshData` buffer based on face direction [S1, unofficial].

## How it works
**Inputs and Outputs:**
- **Input:** A list of raw voxel faces (obtained via `engine.getFaces({ raw: true })`), where each face contains vertex coordinates (`v`), a type (`face.type`), and optional style data [S1, unofficial].
- **Output:** A `GPUGeometry` object containing typed arrays: `position` (Float32Array, XYZ), `normal` (Float32Array, XYZ), `uv` (Float32Array, UV), `index` (Uint32Array, triangle indices), and optionally `color` (Float32Array, RGB) [S1, unofficial].

**Data Structures:**
The `GPUGeometry` structure consists of:
- `position`: Float32Array, 3 floats per vertex [S1, unofficial].
- `normal`: Float32Array, 3 floats per vertex (flat-shaded) [S1, unofficial].
- `uv`: Float32Array, 2 floats per vertex [S1, unofficial].
- `index`: Uint32Array, 3 indices per triangle [S1, unofficial].
- `color`: Float32Array, 3 floats per vertex (present only if `options.color` is true) [S1, unofficial].
- `faceCount`: Number of quad faces encoded [S1, unofficial].
- `vertexCount`: Total vertices (`faceCount * 4`) [S1, unofficial].

**Parameters:**
- `yUp` (boolean, default `false`): If true, converts from Heerich's Y-down/Z-into-screen space to Three.js Y-up/Z-toward-viewer space by negating Y and Z coordinates [S1, unofficial].
- `scale` (number, default `1`): Uniform scale applied to vertex positions [S1, unofficial].
- `color` (boolean, default `false`): If true, parses `face.style.fill` and includes a color array [S1, unofficial].
- `defaultColor` (array, default `[1,1,1]`): Fallback color when parsing fails [S1, unofficial].

**Steps:**
1. Initialize empty typed arrays for `position`, `normal`, `uv`, `index`, and optionally `color` [S1, unofficial].
2. Iterate through each face in the input list [S1, unofficial].
3. Skip faces where `face.type` is `'content'` or if vertex data is absent [S1, unofficial].
4. Determine the face normal `n`: use `face.n` if present, otherwise look up `FACE_NORMALS[face.type]`, defaulting to `[0, 0, 0]` [S1, unofficial].
5. Determine the fill color: if `options.color` is true, parse `face.style.fill` using `parseCSSColor`; if parsing fails or `color` is disabled, use `defaultColor` [S1, unofficial].
6. For each of the 4 vertices `v` (indices 0–3) in the face quad:
   - Compute `ySign = yUp ? -1 : 1` and `zSign = yUp ? -1 : 1` [S1, unofficial].
   - Compute position: `x = v[0] * scale`, `y = v[1] * scale * ySign`, `z = v[2] * scale * zSign` [S1, unofficial].
   - Compute normal: `nx = n[0]`, `ny = n[1] * ySign`, `nz = n[2] * zSign` [S1, unofficial].
   - Compute UV: look up `QUAD_UVS[i]` based on vertex index `i` [S1, unofficial].
   - Compute color: if enabled, use the parsed fill color [S1, unofficial].
   - Store these values in the respective arrays [S1, unofficial].
7. Determine winding order for the quad to ensure Counter-Clockwise (CCW) orientation:
   - Let `v0, v1, v2, v3` be the 4 transformed vertices of the quad in order [S1, unofficial].
   - Compute edge vectors: `e1 = v1 - v0`, `e2 = v2 - v0` [S1, unofficial].
   - Compute cross product `cross = e1 × e2` [S1, unofficial].
   - Compute dot product `crossDotN = cross · n` [S1, unofficial].
   - Formula for `crossDotN`:
     $$
     \text{crossDotN} = (e_{1y} e_{2z} - e_{1z} e_{2y}) n_x + (e_{1z} e_{2x} - e_{1x} e_{2z}) n_y + (e_{1x} e_{2y} - e_{1y} e_{2x}) n_z
     $$
   - If `crossDotN >= 0`, the vertices are already CCW relative to the normal. Indices: `[base, base+1, base+2, base, base+2, base+3]` [S1, unofficial].
   - If `crossDotN < 0`, flip the winding. Indices: `[base, base+2, base+1, base, base+3, base+2]` [S1, unofficial].
   - Append these 6 indices to the `index` array [S1, unofficial].
8. Return the `GPUGeometry` object [S1, unofficial].

**Pseudocode:**
```python
def gpu_geometry_assembly(faces, options):
    y_up = options.get('yUp', False)
    scale = options.get('scale', 1.0)
    enable_color = options.get('color', False)
    default_color = options.get('defaultColor', [1.0, 1.0, 1.0])
    
    y_sign = -1 if y_up else 1
    z_sign = -1 if y_up else 1
    
    # Standard quad UV mapping [G]
    quad_uvs = [[0.0, 0.0], [1.0, 0.0], [1.0, 1.0], [0.0, 1.0]]
    
    # Standard face normal lookup table [G]
    FACE_NORMALS = {
        'top': [0, 1, 0], 'bottom': [0, -1, 0],
        'front': [0, 0, 1], 'back': [0, 0, -1],
        'right': [1, 0, 0], 'left': [-1, 0, 0]
    }
    
    # Helper to parse CSS color strings to RGB floats [G]
    def parse_css_color(css_str):
        if not css_str or not isinstance(css_str, str):
            return None
        # Simplified parsing for #rgb, #rrggbb, rgb(), rgba()
        # Returns [r, g, b] in 0-1 range or None on failure
        return None  # Implementation details omitted; returns None if unparseable [G]
    
    position = []
    normal = []
    uv = []
    indices = []
    color = [] if enable_color else None
    
    face_count = 0
    
    for face in faces:
        if face.type == 'content' or face.v is None:
            continue
            
        face_count += 1
        
        # Determine normal
        n = face.n if face.n is not None else FACE_NORMALS.get(face.type, [0, 0, 0])
        
        # Determine color
        if enable_color:
            c = parse_css_color(face.style.fill)
            if c is None:
                c = default_color
        else:
            c = None
            
        # Process 4 vertices
        for i in range(4):
            v = face.v[i]
            # Position
            position.extend([v[0] * scale, v[1] * scale * y_sign, v[2] * scale * z_sign])
            # Normal
            normal.extend([n[0], n[1] * y_sign, n[2] * z_sign])
            # UV
            uv.extend(quad_uvs[i])
            # Color
            if enable_color:
                color.extend(c)
                
        # Winding check on transformed vertices
        v0 = position[-3:]
        v1 = position[-6:-3]
        v2 = position[-9:-6]
        
        e1 = [v1[j] - v0[j] for j in range(3)]
        e2 = [v2[j] - v0[j] for j in range(3)]
        
        cross_x = e1[1] * e2[2] - e1[2] * e2[1]
        cross_y = e1[2] * e2[0] - e1[0] * e2[2]
        cross_z = e1[0] * e2[1] - e1[1] * e2[0]
        
        cross_dot_n = cross_x * n[0] + cross_y * n[1] + cross_z * n[2]
        
        base = len(indices) // 3
        if cross_dot_n >= 0:
            indices.extend([base, base + 1, base + 2, base, base + 2, base + 3])
        else:
            indices.extend([base, base + 2, base + 1, base, base + 3, base + 2])
            
    vertex_count = face_count * 4
    return GPUGeometry(position, normal, uv, indices, color, face_count, vertex_count)
```

**Edge Cases and Pitfalls:**
- **Coordinate System Conversion:** When converting from Heerich (X-right, Y-down, Z-into-screen) to Three.js (X-right, Y-up, Z-toward-viewer), both Y and Z must be negated (`ySign=-1, zSign=-1`) to preserve winding order (determinant +1) [S1, unofficial]. Using `scale.y = -1` alone changes handedness and breaks winding [S1, unofficial].

## Operating characteristics
- **Time Complexity:** Linear with respect to the number of exposed faces $O(F)$, where $F$ is the number of faces [S1, unofficial].
- **Memory Complexity:** Linear with respect to the number of vertices $O(V)$, where $V = 4F$ [S1, unofficial].
- **Measured Performance:** Not given in the sources.
- **Scaling:** Not given in the sources.
- **Strengths:** Handles coordinate system conversion and winding correction in a single pass, producing ready-to-upload typed arrays [S1, unofficial].
- **Limitations:** Does not perform occlusion culling, as this is handled by the engine's `getFaces` call [S1, unofficial].

## Background
This method is part of the Heerich voxel engine's rendering pipeline, specifically the `GPURenderer` component [S1, unofficial]. It bridges the gap between the engine's internal voxel representation and standard GPU graphics APIs [S1, unofficial]. The method was introduced to support WebGL and WebGPU rendering, allowing for efficient batched geometry uploads [S1, unofficial].
