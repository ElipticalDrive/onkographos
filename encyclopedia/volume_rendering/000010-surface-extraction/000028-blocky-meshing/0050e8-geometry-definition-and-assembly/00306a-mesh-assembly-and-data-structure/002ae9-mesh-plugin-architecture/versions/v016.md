# Mesh Plugin Architecture
Also called: IMeshingJob
## Overview
The Mesh Plugin Architecture provides an interface for pluggable meshing algorithms, allowing for extensibility in the meshing pipeline [S1, unofficial]. It decouples the mesh generation logic from the chunk management system, enabling the selection of different algorithms (e.g., greedy meshing for blocky voxels vs. marching cubes for smooth terrain) based on voxel type [S1, unofficial]. This approach complements the [Mesh Assembly and Data Structure](6268-mesh-assembly-and-data-structure.md) by defining *how* geometry is generated before it is assembled into buffers.

## How it works
### Inputs and Outputs
- **Input**: Voxel data (block IDs, density fields, material IDs) and configuration parameters (material references, zoom levels).
- **Output**: A `MeshInfo` structure containing opaque and translucent mesh data, or a status indicating meshing progress.

### Data Structures
The architecture relies on the following core structures:

1.  **`IMeshingJob` Interface**: Defines the contract for meshing algorithms.
    -   Methods: `execute()`, `is_complete()`, `get_result()`.
    -   Implementation: Concrete classes like `GreedyMeshingJob` and `MarchingCubesJob` implement this interface.
    -   Performance: Burst-compiled, zero garbage collection (GC) in C# implementations [S1, unofficial].

2.  **`MeshStatus` Enum**: Tracks the state of a mesh for a given chunk and zoom level.
    -   Variants:
        -   `Empty`: No mesh data exists.
        -   `Meshing`: Mesh generation is in progress.
        -   `Meshed(Arc<MeshInfo>)`: Mesh generation is complete, holding a reference to the generated data.

3.  **`MeshInfo` Structure**: Contains the actual mesh data.
    -   Fields:
        -   `opaque`: Optional opaque mesh data.
        -   `translucent`: Vector of translucent mesh data.

4.  **`Meshes` Resource**: A hash map storing mesh status for the world.
    -   Key: `(ChunkPosition, ZoomLevel)`.
    -   Value: `MeshStatus`.

### Numbered Steps
1.  **Voxel Update**: The `ChunkManager` receives voxel data updates via `SetVoxel()` [S1, unofficial].
2.  **Job Scheduling**: The `ChunkManager` uses a spatial hash to manage chunks and automatically schedules meshing jobs based on voxel changes [S1, unofficial].
3.  **Mesher Selection**: The `ChunkManager` selects the appropriate `IMeshingJob` implementation based on the voxel type (blocky vs. smooth) [S1, unofficial].
4.  **Execution**: The selected job executes the meshing algorithm (e.g., face culling for greedy meshing, simplified marching cubes for smooth terrain) [S1, unofficial].
5.  **Status Update**: Upon completion, the `MeshStatus` for the corresponding `(ChunkPosition, ZoomLevel)` is updated to `Meshed(Arc<MeshInfo>)` [S2, unofficial].
6.  **Assembly**: The [Mesh Assembly and Data Structure](6268-mesh-assembly-and-data-structure.md) consumes the `MeshInfo` to build GPU buffers.

### Parameters
-   **Precision**: Half-precision density fields can save 50% memory (68KB vs 128KB per 32³ chunk) [S1, unofficial].
-   **Job Type**: Sequential job processing is noted as a potential optimization [S1, unofficial].

### Edge Cases and Pitfalls
-   **Lookup Tables**: Full lookup tables for marching cubes are noted as a future implementation, implying current prototypes may use simplified or hardcoded logic [S1, unofficial].
-   **Memory Management**: Use of `Arc` (Atomic Reference Counting) in Rust implementations requires careful handling to avoid reference cycles or excessive memory overhead [S2, unofficial].

## Subtopics

### GreedyMeshingJob
Optimized for blocky voxels with face culling. Burst-compiled and zero GC. Choose when rendering static, block-based terrain [S1, unofficial].

### MarchingCubesJob
Simplified prototype for smooth terrain. Burst-compiled and zero GC. Choose when rendering smooth, density-based terrain [S1, unofficial].

## Operating characteristics
-   **Time Complexity**: Not given in the sources.
-   **Memory Complexity**: Half-precision density reduces memory usage by 50% compared to full precision [S1, unofficial].
-   **Performance**: Burst-compiled jobs offer zero garbage collection overhead in C# environments [S1, unofficial].
-   **Strengths**: Extensibility through pluggable interfaces; automatic job scheduling; support for both blocky and smooth terrain.
-   **Limitations**: Simplified marching cubes implementation lacks full lookup tables; memory savings depend on voxel data type.
-   **When to Use**: When dynamic mesh generation is required for voxel-based worlds with mixed blocky and smooth terrain types.
-   **When Not to Use**: For static meshes or when memory constraints prevent even half-precision storage.

## Background
The Mesh Plugin Architecture was introduced as part of the foundational voxel engine development in the StraightFour project [S1, unofficial]. It evolved to support both generic blocky voxels and smooth terrain with density fields, leveraging job-based parallelism for performance [S1, unofficial]. The architecture is also present in the Infinigen project, which uses Rust and Bevy for its implementation [S2, unofficial].
