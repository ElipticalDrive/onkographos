# Mesh Plugin Architecture
Also called: IMeshingJob
## Overview
The Mesh Plugin Architecture provides an interface for pluggable meshing algorithms, allowing for extensibility in the meshing pipeline [S1, unofficial]. It decouples the mesh generation logic from the chunk management system, enabling the use of different algorithms (e.g., Greedy Meshing for blocky voxels or Marching Cubes for smooth terrain) without modifying the core assembly infrastructure [S1, unofficial]. This approach supports smart mesher selection based on voxel type (blocky vs. smooth) [S1, unofficial].

## How it works
The architecture defines a contract (`IMeshingJob`) that specific meshing implementations must fulfill. The `ChunkManager` acts as the orchestrator, handling spatial hashing, job scheduling, and coordinate conversion [S1, unofficial].

**Inputs and Outputs:**
*   **Input:** Voxel data (solid or smooth density) and chunk position.
*   **Output:** Mesh data structures (positions, normals, indices, etc.) compatible with the `PackedMeshBuffers` layout defined in [Mesh Assembly and Data Structure](6268-mesh-assembly-and-data-structure.md).

**Data Structures:**
*   `IMeshingJob`: An interface defining the method signature for mesh generation.
*   `MeshStatus`: An enum tracking the state of mesh generation for a chunk. Variants include:
    *   `Meshing`: Generation in progress.
    *   `Meshed(Arc<MeshInfo>)`: Generation complete, holding the mesh data.
    *   `Empty`: No mesh data.
*   `MeshInfo`: Contains an optional opaque mesh and a vector of translucent meshes [S2, unofficial].
*   Resource Store: A hash map mapping `(ChunkPosition, ZoomLevel)` to `MeshStatus` [S2, unofficial].

**Steps:**
1.  **Voxel Registration:** The user registers voxel data via `ChunkManager.SetVoxel`, specifying either solid block data or smooth density fields [S1, unofficial].
2.  **Smart Selection:** The `ChunkManager` determines the appropriate meshing algorithm based on the voxel type (blocky vs. smooth) [S1, unofficial].
3.  **Job Scheduling:** The manager schedules the corresponding `IMeshingJob` implementation (e.g., `GreedyMeshingJob` or `MarchingCubesJob`) [S1, unofficial].
4.  **Execution:** The job executes, typically using burst-compiled code for performance and zero garbage collection overhead [S1, unofficial].
5.  **Status Update:** The `MeshStatus` for the chunk is updated to `Meshing` during execution and `Meshed` upon completion [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** Half-precision density can save 50% memory (68KB vs 128KB per 32³ chunk) but may affect smooth terrain quality [S1, unofficial].
*   **Lookup Tables:** Full lookup tables for Marching Cubes are noted for future implementation, implying current versions may use simplified logic [S1, unofficial].

## Operating characteristics
*   **Performance:** Jobs are burst-compiled and designed for zero garbage collection (GC) overhead, ensuring high performance in real-time applications [S1, unofficial].
*   **Memory:** Half-precision density fields reduce memory usage by 50% compared to full precision [S1, unofficial].
*   **Scalability:** The architecture supports automatic job scheduling and spatial hashing, allowing for efficient handling of large worlds [S1, unofficial].
*   **Limitations:** The current Marching Cubes implementation is a prototype; full lookup tables are not yet implemented [S1, unofficial].

## Background
The Mesh Plugin Architecture was introduced as part of the foundational voxel engine development for the StraightFour project [S1, unofficial]. It was designed to support both generic, terrain, and smooth voxel types, providing a flexible foundation for various rendering needs [S1, unofficial]. The architecture is implemented in C# using Unity's Job System and Burst Compiler for performance [S1, unofficial].
