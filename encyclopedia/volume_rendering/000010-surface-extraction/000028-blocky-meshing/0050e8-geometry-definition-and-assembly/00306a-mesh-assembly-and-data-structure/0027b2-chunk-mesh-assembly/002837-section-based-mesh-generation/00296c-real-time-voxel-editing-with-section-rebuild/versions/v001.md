# Real-time Voxel Editing with Section Rebuild

Also called: Incremental Section Mesh Update, Section Rebuild

## Overview
This method enables immediate visual feedback for voxel placement and removal by regenerating mesh data for the affected 16x16x16 section and any adjacent sections if the edit occurs on a section boundary [S1, unofficial]. It differs from full-chunk rebuilds by limiting computation to the minimal set of sections intersecting the modified voxel, and from adjacency-based chunk rebuilding by operating at the sub-chunk section level within a single chunk [S1, S2, unofficial].

## How it works
**Inputs:**
- The 3D coordinates of the edited voxel $(i, j, k)$ within the chunk.
- The new block type (e.g., AIR, STONE).
- The chunk's section side length $mSectionSide$ (typically 16).
- The chunk's total section count $sectionCount$.
- The current voxel data array `mBlocks`.

**Outputs:**
- Updated GPU vertex/index buffers for the affected section(s).
- Updated voxel data in `mBlocks`.

**Data Structures:**
- `mBlocks`: A 1D `TArray` or contiguous memory block storing block types. Access is calculated via `GetPositionInTArray(i, j, k, mSectionSide)`.
- `MeshData`: Contains vertex and index data for a single section.
- `TMap<int32, TFuture<...>*>`: Tracks in-flight chunk generation tasks to prevent duplicate work [S1, unofficial].

**Steps:**
1. **Calculate Array Index:** Compute the linear index of the voxel in `mBlocks` using the section side length.
2. **Update Voxel Data:** Set `mBlocks[index]` to the new block type. If the block type is unchanged, terminate [S1, unofficial].
3. **Determine Affected Sections:**
   - Calculate the primary section index: $section = \lfloor i / mSectionSide \rfloor$.
   - Check for boundary conditions: If $i \pmod{mSectionSide} == 0$ or $(i + 1) \pmod{mSectionSide} == 0$, the edit lies on a section boundary [S1, unofficial].
   - If on boundary, identify the adjacent section:
     - If at the bottom of a section ($i \pmod{mSectionSide} == 0$), include $section - 1$.
     - If at the top of a section ($(i + 1) \pmod{mSectionSide} == 0$), include $section + 1$ [S1, unofficial].
4. **Clear Existing Data:** Call `ClearMeshSection` for each affected section index to free GPU resources [S1, unofficial].
5. **Regenerate Mesh Data:** For each affected section, call `GetMeshData` to generate new vertices and indices based on the updated voxel state [S1, unofficial].
6. **Upload to GPU:** Call `CreateMeshSection_LinearColor` with the new mesh data for each affected section [S1, unofficial].
7. **Handle Inter-Chunk Updates:** If the edit occurs on a chunk boundary (e.g., $j==0$ or $k==0$ in the global coordinate system), notify the adjacent chunk to update its edge voxels [S1, unofficial].

**Pseudocode:**
```python
def UpdateVoxel(i, j, k, new_block_type, mSectionSide, sectionCount, mBlocks, mesh_data_manager):
    # 1. Calculate index and check for no-op
    index = GetPositionInTArray(i, j, k, mSectionSide)
    if mBlocks[index] == new_block_type:
        return

    # 2. Update voxel data
    mBlocks[index] = new_block_type

    # 3. Determine affected sections
    section = i // mSectionSide
    affected_sections = [section]

    # Check boundary conditions
    if i % mSectionSide == 0:
        if section > 0:
            affected_sections.append(section - 1)
    if (i + 1) % mSectionSide == 0:
        if section < sectionCount - 1:
            affected_sections.append(section + 1)

    # 4. Clear and regenerate
    for sec in affected_sections:
        mesh_data_manager.ClearMeshSection(sec)
        new_mesh_data = GetMeshData(sec, mBlocks, mSectionSide, sectionCount)
        mesh_data_manager.CreateMeshSection_LinearColor(sec, new_mesh_data)
```

**Parameters:**
- $mSectionSide$: Typically 16. Determines the granularity of partial rebuilds [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Boundary Precision:** The condition $(i + 1) \pmod{mSectionSide} == 0$ must be checked to ensure the section above is rebuilt if the voxel is at the top of the current section [S1, unofficial].
- **Inter-chunk Consistency:** Edits on chunk boundaries require coordination between adjacent chunks to avoid visual seams [S1, unofficial].
- **Duplicate Generation:** Use a tracking map (e.g., `TMap`) to prevent multiple threads from rebuilding the same chunk simultaneously [S1, unofficial].

## Subtopics

### Adjacency-Based Mesh Rebuilding
A method that rebuilds entire chunk meshes only when a voxel is added or removed, specifically targeting adjacent chunks that share a face with the modified voxel [S2, unofficial]. It identifies the local voxel position $(lx, ly, lz)$ and world position $(wx, wy, wz)$, then rebuilds the mesh of the chunk containing the modified voxel and any adjacent chunk if the voxel is on a chunk boundary (e.g., $lx == 0$ triggers rebuild of chunk at $(wx-1, wy, wz)$) [S2, unofficial]. This approach operates at the chunk level rather than the section level, making it simpler but potentially less efficient for frequent small edits within a chunk [S2, unofficial].

## Operating characteristics
- **Time Complexity:** $O(1)$ per voxel edit for the primary section, plus $O(1)$ for adjacent sections if on boundary. Total work is proportional to the number of affected sections (1 or 2) rather than the entire chunk [S1, unofficial].
- **Memory Complexity:** $O(1)$ additional memory for mesh data of affected sections. No significant increase in peak memory usage compared to full chunk rebuilds [S1, unofficial].
- **Performance:** Significantly faster than full-chunk rebuilds for sparse edits. Performance scales with the number of affected sections, not the chunk size [S1, unofficial].
- **Strengths:** Immediate visual feedback, low latency for single-voxel edits, efficient use of GPU resources by only updating changed sections [S1, unofficial].
- **Limitations:** Requires careful handling of section boundaries and inter-chunk updates. More complex implementation than full-chunk rebuilds [S1, unofficial].
- **When to Use:** Real-time voxel editing where immediate feedback is critical, and edits are sparse [S1, unofficial].
- **When Not to Use:** Batch updates affecting large portions of a chunk, where full-chunk rebuilds might be more efficient due to overhead [S1, unofficial].

## Background
This method is implemented in Unreal Engine 5 Minecraft clone projects, specifically in the `AChunk::UpdateVoxel` function [S1, unofficial]. It builds on the section-based mesh generation approach to allow efficient partial rebuilds [S1, unofficial]. The technique is part of a broader trend in voxel game development towards incremental mesh updates to maintain high frame rates during dynamic world modification [S1, S2, unofficial].
