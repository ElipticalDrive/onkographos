# Mesh Assembly and Data Structure

Also called: Chunk Mesh Assembly, Mesh Plugin Architecture, Block Render Data Structure & Instance Generation

## Overview
Mesh Assembly and Data Structure manages the consolidation of geometric primitives generated by blocky meshing algorithms into GPU-drawable buffers and the management of per-voxel material properties. It solves the problem of fragmented geometry data from parallel or multi-pass meshing by packing it into contiguous typed arrays and mapping texture IDs to draw calls [S2, unofficial]. Unlike [Blocky meshing](31-blocky-meshing.md), which handles face culling and greedy merging, this family handles the final buffer allocation, material assignment, and instance generation [S1, unofficial][S2, unofficial][S3, unofficial].

## Shared principles
The family shares the following mechanisms and data structures:

1.  **Buffer Allocation**: Output arrays are allocated based on the total quad count across all layers.
    *   Positions: `quadCount * 4 * 3` elements (Float32).
    *   Normals: `quadCount * 4 * 3` elements (Int8 or Float32).
    *   Indices: `quadCount * 6` elements (Uint16 or Uint32).
    *   Attributes: `quadCount * 4` elements for block IDs, ambient occlusion, and lighting [S2, unofficial].
2.  **Layer Iteration**: Meshes are processed layer by layer (e.g., opaque, water, transparentSolid). Each layer's quads are appended to the global buffers, and offsets are recorded in a `MeshBufferGroup` structure [S2, unofficial].
3.  **Material Mapping**: A map of block types to materials is used. If a block type is not found, a fallback material is used [S3, unofficial].
4.  **Instance Generation**: Per-voxel attributes (texture IDs, tints) are resolved and passed to the rendering engine via instance rendering [S2, unofficial].

## Subtopics

### [Chunk Mesh Assembly](4100-chunk-mesh-assembly.md)
Aggregates mesh data from multiple voxel layers into contiguous typed arrays for efficient GPU submission. It differs from [Mesh Plugin Architecture](4921-mesh-plugin-architecture.md) by handling the final consolidation of vertex/index buffers rather than defining an interface for generation. Choose this when managing fragmented geometry from parallel meshing.

### [Mesh Plugin Architecture](4921-mesh-plugin-architecture.md)
Provides an interface for pluggable meshing algorithms, decoupling geometric generation logic from chunk management. It differs from [Chunk Mesh Assembly](4100-chunk-mesh-assembly.md) by allowing algorithm selection (e.g., Greedy Meshing vs. Marching Cubes) based on voxel type. Choose this for extensibility in the meshing pipeline.

### [Block Render Data Structure & Instance Generation](6209-block-render-data-structure-instance-generation.md)
Defines the data container (`BlockRenderData`) and procedural logic for generating GPU render instances. It differs from sibling methods by focusing on per-voxel attribute composition and per-face tint mixing. Choose this when granular visual variation on a single voxel's six faces is required.

### Mesh Configuration and Data Structures
*   **Data Structures**: Block IDs must use native JavaScript `Set` for performance (~400k membership tests per chunk) [S1, unofficial].
*   **Layout**: BlockId values must be registry-derived. Untrusted numeric inputs must be converted using `BlockId.result` API [S1, unofficial].
*   **Transparent Solids**: Split into `transparentSolidBlockIds` (glass, leaves - atlas material + alpha blend) and `water` (dedicated shader for ripples/refraction/variable height) [S1, unofficial].
*   **FluidQuad**: Includes `direction`, `flow` (optional, contains `direction` vector and `falling` flag), and geometry properties [S1, unofficial].
*   **ChunkView**: Holds `coord`, per-chunk `height`, and a byte view for meshing. It does not implicitly truncate or zero-pad different heights [S1, unofficial].
*   **Storage Layout**: `blockIndex` is identical to the reference implementation to allow direct use of reference chunk fixtures as golden inputs [S1, unofficial].

### Material-Based Mesh Sectioning
*   **Definition**: Splits a decoded mesh into separate sections (arrays of triangles) based on the material ID associated with each triangle's vertices [S2, unofficial].
*   **Step**:
    1.  Decode the input mesh using `GetDecodedMesh` [S2, unofficial].
    2.  Sanity check: if indices < 3, return empty mesh sections [S2, unofficial].
    3.  Iterate through indices in steps of 3 [S2, unofficial].
    4.  Retrieve vertices and add mesh offset to positions [S2, unofficial].
    5.  Determine material ID: start with Vertex 0's ID. If Vertex 1 and 2 have the same ID, use that instead [S2, unofficial].
    6.  Resize sections array if `materialID` >= current size [S2, unofficial].
    7.  Add triangle to the section corresponding to its material ID [S2, unofficial].

## Background
The concepts originate from implementations in [nerima-games/mc-meshing](https://github.com/nerima-games/mc-meshing) and [Jay2645/VoxelGenerator](https://github.com/Jay2645/VoxelGenerator) [S1, unofficial][S2, unofficial]. The need for efficient mesh assembly arises from the high vertex count in voxel worlds, requiring contiguous buffers for GPU submission [S2, unofficial]. The plugin architecture allows for hybrid rendering pipelines supporting both blocky and smooth terrain [S1, unofficial].
