# Mesh Assembly and Data Structure

Also called: Mesh Assembly, Mesh Data Structure, Chunk Mesh Assembly, Mesh Plugin Architecture, Block Render Data Structure

## Overview
Mesh Assembly and Data Structure aggregates fragmented geometry generated by blocky meshing algorithms into contiguous, GPU-ready buffers and manages the runtime data structures required for rendering [S2, 4100-chunk-mesh-assembly.md, unofficial]. It solves the problem of memory fragmentation and inefficient draw calls by consolidating per-layer mesh data into a single renderable structure, distinct from sibling methods that focus on plugin architecture [4921-mesh-plugin-architecture.md] or instance generation [6209-block-render-data-structure-instance-generation.md].

## Shared principles
The family shares a reliance on contiguous typed arrays for vertex and index data to enable efficient GPU submission. The core mechanism involves iterating over mesh layers (e.g., opaque, water, transparent solid), calculating total quad counts, and writing vertex attributes (positions, normals, block IDs, lighting) into pre-allocated buffers [S2, 4100-chunk-mesh-assembly.md, unofficial]. The data structure must support mapping block types to materials and handling per-vertex attributes such as ambient occlusion and light levels [S1, S3, 4100-chunk-mesh-assembly.md].

## Subtopics

### [Chunk Mesh Assembly](4100-chunk-mesh-assembly.md)
Aggregates mesh data from multiple voxel layers into contiguous typed arrays for efficient GPU submission. It differs from siblings by consolidating per-layer data into a single renderable structure rather than managing plugins or instances. Choose this when you need to submit a complete chunk mesh to the GPU in a single draw call or minimal set of calls.

### [Mesh Plugin Architecture](4921-mesh-plugin-architecture.md)
Provides an interface for pluggable meshing algorithms, decoupling mesh generation logic from chunk management. It differs by supporting multiple concurrent strategies (e.g., greedy meshing vs. marching cubes) within a single engine. Choose this when extensibility and algorithm selection based on voxel type are required.

### [Block Render Data Structure & Instance Generation](6209-block-render-data-structure-instance-generation.md)
Defines the data structure for preparing voxel blocks for instance rendering, mapping face textures and tints to integer IDs. It differs by focusing on per-instance attribute resolution rather than global mesh buffer assembly. Choose this when using GPU instancing to render many similar blocks efficiently.

### Mesh Configuration and Data Structures
*   **Data Structures:** Block ID data structures must use native JavaScript `Set` for membership tests due to performance constraints (~400k tests per chunk); Effect's `HashSet` is forbidden [S1, unofficial].
*   **Layout:** BlockId values must be registry-derived. Untrusted numeric inputs must be converted using `BlockId.result` API before building sets/maps [S1, unofficial].
*   **Transparency Split:** Transparent solids are split into two sets: `transparentSolidBlockIds` (glass, leaves - atlas material + alpha blend) and `waterBlockIds` (dedicated shader for ripples/refraction/variable height) [S1, unofficial].
*   **FluidQuad:** Includes `direction`, `flow` (optional, contains `direction` vector and `falling` flag), and geometry properties [S1, unofficial].
*   **ChunkView:** Holds `coord`, per-chunk `height`, and a byte view for meshing. It does not implicitly truncate or zero-pad different heights [S1, unofficial].
*   **Storage:** `blockIndex` layout is identical to the reference implementation to allow direct use of reference chunk fixtures as golden inputs [S1, unofficial].

### Material-Based Mesh Sectioning
*   **Definition:** Splits a decoded mesh into separate sections (arrays of triangles) based on the material ID associated with each triangle's vertices [S2, unofficial].
*   **Steps:**
    1.  Decode the input mesh using `GetDecodedMesh` [S2, unofficial].
    2.  Sanity check: if index count < 3, return empty mesh sections array [S2, unofficial].
    3.  Iterate through indices in steps of 3 [S2, unofficial].
    4.  Retrieve three vertices using indices; add mesh offset to positions [S2, unofficial].
    5.  Determine material ID: start with Vertex 0's ID. If Vertex 1 and 2 have the same ID, use that instead [S2, unofficial].
    6.  Ensure sections array size is sufficient (`materialID + 1` if needed), zeroing new elements [S2, unofficial].
    7.  Add the triangle to the section corresponding to its material ID [S2, unofficial].

## Background
The concepts originate from implementations in open-source voxel engines such as `nerima-games/mc-meshing` and `Jay2645/VoxelGenerator` [S1, S2, unofficial]. The architecture evolved to address performance bottlenecks in JavaScript-based voxel rendering, specifically regarding set membership tests and memory layout [S1, unofficial]. It is used in blocky meshing pipelines where efficient GPU submission and flexible material handling are critical.
