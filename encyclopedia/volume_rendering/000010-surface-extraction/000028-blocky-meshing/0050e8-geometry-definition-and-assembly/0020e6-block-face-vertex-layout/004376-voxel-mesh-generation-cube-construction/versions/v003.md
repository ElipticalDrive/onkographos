# Voxel Mesh Generation (Cube Construction)

Also called: CreateQuadSmoothVoxel, CreateQuadVoxel, Cube model, FVox::CreateMesh, Single Cube Mesh Generation, VoxelBlockyModelCube

## Overview
Voxel Mesh Generation (Cube Construction) is a surface extraction method that constructs a static, non-indexed cube mesh for a single voxel block by explicitly defining geometry for all six faces, regardless of occlusion [S1, unofficial][S2, unofficial]. It differs from optimized blocky meshing methods (such as [Naive Voxel Mesh Generation](18007-naive-voxel-mesh-generation.md)) by its simplicity and lack of face culling or vertex sharing, resulting in a dense, redundant mesh where each voxel is rendered as an independent unit [S1, unofficial]. This approach is primarily used for legacy conversion, debugging, or simple voxel editors where implementation complexity is prioritized over rendering performance [S3].

## How it works
**Inputs:**
- `relativePosition`: The 3D world coordinates of the voxel block's center or origin.
- `BLOCK_SIZE`: The half-extent of the voxel cube (distance from center to face).
- `blockType`: An integer or enum identifying the voxel material (e.g., grass, dirt, stone).
- `textureAtlas`: A square texture containing up to $16 \times 16$ tiles, used for UV mapping [S3].
- `atlas_size_in_tiles`: The number of tiles along one axis of the atlas (typically 16) [S3].

**Outputs:**
- A mesh buffer containing 24 vertices per voxel (4 vertices per face $\times$ 6 faces) [S2, unofficial].
- 24 normal vectors (duplicated per vertex) [S2, unofficial].
- 24 color values (per-vertex, derived from `blockType`) [S2, unofficial].
- 36 indices (6 quads $\times$ 2 triangles $\times$ 3 indices) or direct vertex attributes depending on the API [S1, unofficial][S2, unofficial].

**Data Structures:**
The mesh stores data in a flat array or interleaved vertex buffer. For a single voxel:
- **Positions:** 24 `vec3` values.
- **Normals:** 24 `vec3` values (axis-aligned).
- **Colors:** 24 `vec4` values (RGBA).
- **TexCoords:** 24 `vec2` values (derived from tile indices) [S3].

**Steps:**

1.  **Calculate Corner Coordinates:**
    Compute the 8 corner points of the cube relative to `relativePosition` using `BLOCK_SIZE`. Let $B = \text{BLOCK\_SIZE}$. The corners are:
    $$
    \begin{aligned}
    P_1 &= (x-B, y-B, z+B) \\
    P_2 &= (x+B, y-B, z+B) \\
    P_3 &= (x+B, y+B, z+B) \\
    P_4 &= (x-B, y+B, z+B) \\
    P_5 &= (x-B, y-B, z-B) \\
    P_6 &= (x+B, y-B, z-B) \\
    P_7 &= (x+B, y+B, z-B) \\
    P_8 &= (x-B, y+B, z-B)
    \end{aligned}
    $$
    where $(x, y, z) = \text{relativePosition}$ [S2, unofficial].

2.  **Define Face Geometry:**
    The cube has 6 faces. Each face is a quad defined by 4 vertices. The standard face definitions (using the points above) are:
    -   **Front (Z+):** $P_1, P_2, P_3, P_4$
    -   **Back (Z-):** $P_5, P_6, P_7, P_8$
    -   **Right (X+):** $P_2, P_6, P_7, P_3$
    -   **Left (X-):** $P_1, P_4, P_8, P_5$
    -   **Top (Y+):** $P_4, P_3, P_7, P_8$
    -   **Bottom (Y-):** $P_1, P_5, P_6, P_2$

3.  **Assign Normals:**
    For each face, assign the corresponding axis-aligned normal to all 4 vertices of that face:
    -   Front: $(0, 0, 1)$
    -   Back: $(0, 0, -1)$
    -   Right: $(1, 0, 0)$
    -   Left: $(-1, 0, 0)$
    -   Top: $(0, 1, 0)$
    -   Bottom: $(0, -1, 0)$
    Normals are duplicated for each vertex [S2, unofficial].

4.  **Assign Colors:**
    Set the per-vertex color based on `blockType`. Common mappings include:
    -   Grass: $(0.0, 1.0, 0.0, 1.0)$
    -   Dirt: $(0.435, 0.305, 0.215, 1.0)$
    -   Stone: $(0.45, 0.45, 0.45, 1.0)$
    All 4 vertices of a face share the same color [S2, unofficial].

5.  **Assign Texture Coordinates:**
    Determine the tile indices $(u_{tile}, v_{tile})$ for each face based on `blockType` [S3]. Calculate UVs for the 4 vertices of each face using the atlas size $N$ (e.g., 16):
    $$
    \begin{aligned}
    u_{min} &= u_{tile} / N, \quad u_{max} = (u_{tile} + 1) / N \\
    v_{min} &= v_{tile} / N, \quad v_{max} = (v_{tile} + 1) / N
    \end{aligned}
    $$
    Assign these UVs to the 4 vertices of the face. Note that coordinates are in tiles, not pixels [S3].

6.  **Add to Mesh Buffer:**
    Append the 24 vertices (position, normal, color, texcoord) to the mesh buffer. If using an index buffer, add 36 indices (6 quads $\times$ 6 indices) or 24 indices if using a strip/adjacency format, though the naive approach often uses non-indexed drawing or simple quad indices [S1, unofficial][S2, unofficial].

**Pseudocode:**

```python
def generate_cube_mesh(relative_position, block_size, block_type, atlas_size=16):
    """
    Generates a non-indexed cube mesh for a single voxel.
    Returns lists of positions, normals, colors, and texcoords.
    """
    x, y, z = relative_position
    B = block_size
    
    # 1. Calculate 8 corners
    # P1: Front-Left-Top, P2: Front-Right-Top, P3: Front-Right-Bottom (wait, check Z)
    # Based on S2: 
    # P1: (x-B, y-B, z+B) -> Front-Left-Bottom? No, Z+B is Front if Z+ is Front.
    # Let's stick to the S2 point definitions exactly.
    points = [
        (x-B, y-B, z+B), # 1
        (x+B, y-B, z+B), # 2
        (x+B, y+B, z+B), # 3
        (x-B, y+B, z+B), # 4
        (x-B, y-B, z-B), # 5
        (x+B, y-B, z-B), # 6
        (x+B, y+B, z-B), # 7
        (x-B, y+B, z-B)  # 8
    ]
    
    # 2. Define faces as indices into points array
    # Front (Z+): 1, 2, 3, 4
    # Back (Z-): 5, 6, 7, 8
    # Right (X+): 2, 6, 7, 3
    # Left (X-): 1, 4, 8, 5
    # Top (Y+): 4, 3, 7, 8
    # Bottom (Y-): 1, 5, 6, 2
    faces = [
        [0, 1, 2, 3], # Front
        [4, 5, 6, 7], # Back
        [1, 5, 6, 2], # Right
        [0, 3, 7, 4], # Left
        [3, 2, 6, 7], # Top
        [0, 4, 5, 1]  # Bottom
    ]
    
    normals = [
        (0, 0, 1),   # Front
        (0, 0, -1),  # Back
        (1, 0, 0),   # Right
        (-1, 0, 0),  # Left
        (0, 1, 0),   # Top
        (0, -1, 0)   # Bottom
    ]
    
    # 3. Get color for block type
    colors = {
        'GRASS': (0.0, 1.0, 0.0, 1.0),
        'DIRT': (0.435, 0.305, 0.215, 1.0),
        'STONE': (0.45, 0.45, 0.45, 1.0)
    }
    color = colors.get(block_type, (1.0, 1.0, 1.0, 1.0))
    
    # 4. Get tile indices for block type (example: assume 0,0 for simplicity)
    # In practice, this comes from Voxel properties under 'Cube tiles'
    u_tile, v_tile = 0, 0 
    
    positions = []
    normals_out = []
    colors_out = []
    texcoords = []
    
    for i, face_indices in enumerate(faces):
        normal = normals[i]
        for vert_idx in face_indices:
            p = points[vert_idx]
            positions.append(p)
            normals_out.append(normal)
            colors_out.append(color)
            
            # Calculate UV
            u_min = u_tile / atlas_size
            u_max = (u_tile + 1) / atlas_size
            v_min = v_tile / atlas_size
            v_max = (v_tile + 1) / atlas_size
            
            # Assign UVs to corners of the quad
            # This is a simplification; real implementation maps specific corners to specific UVs
            # For a naive cube, all vertices of a face might share the same UV or vary.
            # S3 implies per-face tile assignment. We'll assign the bottom-left UV for all vertices
            # as a placeholder for the specific corner mapping which depends on the face orientation.
            # A more correct naive approach assigns the 4 corners of the tile to the 4 vertices.
            # Let's assume standard quad UV mapping:
            if vert_idx == face_indices[0]:
                texcoords.append((u_min, v_min))
            elif vert_idx == face_indices[1]:
                texcoords.append((u_max, v_min))
            elif vert_idx == face_indices[2]:
                texcoords.append((u_max, v_max))
            elif vert_idx == face_indices[3]:
                texcoords.append((u_min, v_max))

    return positions, normals_out, colors_out, texcoords
```

**Parameters:**
- `BLOCK_SIZE`: Half-extent of the voxel cube. Typical value: 0.5 (for a 1x1x1 unit cube) [S2, unofficial].
- `atlas_size_in_tiles`: Must be set to the number of tiles in the texture atlas (e.g., 16) to generate correct texture coordinates [S3].

**Edge Cases and Pitfalls:**
- **Occlusion:** This method does not cull internal faces. Adjacent voxels will render overlapping geometry, causing z-fighting or overdraw [S1, unofficial].
- **Performance:** The mesh density is high. For a chunk of $N^3$ voxels, the vertex count is $24 N^3$. This is significantly less efficient than face-culling methods [S1, unofficial].
- **Instancing:** `VoxelBlockyModel` should not be instantiated directly; derived classes should be used [S3].

## Subtopics

### isocubesGrob
A variant that creates a grid grob of isometric cubes representing voxels at given coordinates, primarily for R/ggplot2 visualization [S4, unofficial]. It differs from standard cube construction by projecting 3D coordinates into an isometric 2D view and handling visibility sorting (back-to-front) automatically [S4, unofficial]. Choose this for data visualization rather than real-time rendering. Parameters include `coords` (x,y,z data frame), `fill` colors, `intensity` shading, and `xyplane` orientation [S4, unofficial].

### Legolizer Polygonization
A procedure that converts voxel representations into a "LEGOr" brick mesh, generating uniform cubes with cylinders on top and disks covering them [S5]. It differs by adding geometric details (cylinders/disks) to simulate LEGO studs. It requires a vertex shader to map vertices to voxel grid indices and emits a triangle strip containing 6 cube faces plus the stud geometry [S5].

### Cube Strip Geometry Generation
Generates a triangle strip representing a 3D box defined by min/max coordinates [S6, unofficial]. It differs by using a single strip of 14 vertices (42 floats) instead of 24 separate vertices, reducing vertex count but requiring specific winding order [S6, unofficial].

### Skybox Mesh Construction
Allocates a mesh buffer with 12 triangles and 24 vertices for a skybox [S7, unofficial]. It differs by using reversed winding order for indices and fixed normal/color attributes, optimized for rendering the environment rather than game objects [S7, unofficial].

## Operating characteristics
- **Time Complexity:** $O(1)$ per voxel. The generation cost is constant regardless of the voxel's position or neighbors.
- **Memory Complexity:** $O(V)$ where $V$ is the number of voxels. Each voxel consumes 24 vertices. For a $128^3$ chunk, this is $128^3 \times 24 \times 4$ bytes $\approx 192$ MB for positions alone, plus normals, colors, and texcoords.
- **Performance:** Very poor for large scenes due to lack of culling and vertex sharing. It is suitable only for small, isolated voxel objects or debugging [S1, unofficial].
- **Strengths:** Simple implementation; no need for neighbor lookups or complex meshing algorithms [S1, unofficial].
- **Limitations:** High overdraw; z-fighting between adjacent voxels; high memory usage [S1, unofficial].

## Background
The method originates from early voxel game implementations and educational graphics tutorials where simplicity was prioritized [S1, unofficial][S2, unofficial]. It is documented in unofficial repositories like `VOX4U` and `VoxelTerrain` as a baseline for voxel meshing [S1, unofficial][S2, unofficial]. The `VoxelBlockyModelCube` class in the Voxel Tools documentation represents a more structured, engine-integrated version of this approach [S3].
