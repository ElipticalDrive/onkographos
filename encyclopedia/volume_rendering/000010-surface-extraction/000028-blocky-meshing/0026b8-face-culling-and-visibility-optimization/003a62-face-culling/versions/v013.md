# Face Culling

Also called: Exposure Culling, Neighbor Check Culling, Voxel Neighbor Face Culling

## Overview
Face Culling is a mesh generation optimization that reduces the number of vertices sent to the GPU by skipping the rendering of voxel faces that are adjacent to existing neighboring voxels [S1, unofficial]. It solves the problem of naively rendering all 6 faces of every cube, including those hidden by neighbors, which results in a primitive count of $6 \times N_{voxels}$ [S1, unofficial]. By only adding faces that are exposed (have no neighbor) to the vertex buffer, the method reduces the primitive count to approximately $2 \times N_{voxels}$ for dense structures [S1, unofficial]. It is distinct from [Voxel Backface Culling and Internal Face Masking](4569-voxel-backface-culling-and-internal-face-culling.md) because it operates during the static mesh construction phase based on spatial adjacency rather than runtime view-dependent orientation, and from [Block Visibility Culling](5334-block-visibility-culling.md) which operates at a coarser block granularity.

## How it works
**Inputs and Outputs:**
*   **Input:** A set of occupied voxel positions, typically stored in a hash set or dense array (e.g., `std::unordered_set<glm::ivec3>` or a boolean grid) [S1, unofficial].
*   **Output:** A vertex buffer containing only the geometry for exposed faces [S1, unofficial].

**Data Structures:**
The method relies on the state of adjacent voxels. Common structures include:
*   **Occupancy Grids:** Hash sets or dense arrays storing voxel states [S1, unofficial].
*   **Visibility Masks:** Bitmasks (e.g., 6-bit integers) tracking which faces of a voxel are visible [S1, unofficial].

**Algorithm Steps:**
The culling check runs once during mesh creation, resulting in no framerate loss during rendering [S1, unofficial].

1.  Iterate through each voxel in the world grid.
2.  For each voxel, check the six adjacent positions in the world grid corresponding to the face normals (e.g., $\pm X, \pm Y, \pm Z$) [S1, unofficial].
3.  For each face direction, calculate the neighbor position:
    $$ P_{neighbor} = P_{voxel} + N_{face} $$
    where $P_{voxel}$ is the voxel's position and $N_{face}$ is the unit vector normal to the face [S1, unofficial].
4.  Check if a solid voxel exists at $P_{neighbor}$ in the occupancy grid [S1, unofficial].
5.  If a neighbor exists, the face is internal and is skipped (not added to the vertex buffer) [S1, unofficial].
6.  If no neighbor exists, the face is exposed and is added to the vertex buffer [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Bottom Face Culling:** In some implementations, bottom faces are always culled (`renderFlag = false`) regardless of neighbors below, as indicated by specific logic where `isBottomFace` triggers a forced false flag [S1, unofficial]. This is a design choice, not a general rule of face culling, and may result in floating structures if not handled by other means.
*   **Side Face Logic:** Side faces (non-bottom) are culled if a neighbor exists directly adjacent OR if a neighbor exists directly above the neighbor position (checking `neighborPos + (0, 1, 0)`). This specific logic implies a "step" or "overhang" culling behavior where faces are hidden if they are underneath another voxel's footprint [S1, unofficial].
*   **Performance:** The naive approach of looping through neighbors for every voxel can lead to poor performance due to random memory access patterns [S2, unofficial]. Using efficient data structures like hash sets or contiguous arrays is critical.

## Subtopics

### Binary Hidden-Face Culling
A technique to reduce the number of faces in a voxel mesh by removing those completely hidden (adjacent to another voxel), using bitwise operations on a bitmask representation of voxels to determine visible faces in bulk [S2, unofficial]. It sets itself apart from standard neighbor checks by operating on 1D arrays or bitmasks rather than 3D spatial lookups, allowing for vectorized or bulk bitwise operations. It is chosen when the voxel data can be linearized (e.g., along a single axis for a specific face direction) and performance is critical. The method involves shifting the bitmask to represent neighbors and using bitwise AND with inverted shifts to find visible faces [S2, unofficial]. A key pitfall is that the original approach of checking each of the six faces by looping through neighbors and performing random memory access leads to very poor performance [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of voxels, assuming $O(1)$ average case lookup in the occupancy grid (hash set) [S1, unofficial]. If using a dense array, lookup is $O(1)$ worst-case.
*   **Memory Complexity:** $O(N)$ to store the occupancy grid and the resulting vertex buffer. The vertex buffer size is reduced from $6 \times N$ faces to approximately $2 \times N$ faces for dense structures [S1, unofficial].
*   **Measured Performance:** 4096 cubes rendered at ~60 FPS on the author's system [S1, unofficial].
*   **Strengths:** Eliminates redundant geometry at the source, reducing GPU draw calls and vertex processing load. The culling check runs once during mesh creation, resulting in no framerate loss during rendering [S1, unofficial].
*   **Limitations:** Requires a complete or incremental mesh rebuild when the voxel world changes. Does not account for camera orientation (backfaces) unless combined with other techniques.
*   **When to use:** Static or semi-static voxel worlds where mesh generation can be performed offline or during chunk loading.
*   **When not to use:** Highly dynamic scenes where voxel changes are frequent and per-frame mesh regeneration is too expensive, or when combined with other culling methods that operate at different granularities.

## Background
Face Culling is a fundamental optimization in voxel-based game development and 3D modeling. It originates from the need to efficiently render voxel terrains, such as in Minecraft-inspired games, where naive rendering of all voxel faces is computationally prohibitive. The technique is widely documented in community devlogs and open-source repositories [S1, unofficial][S2, unofficial].
