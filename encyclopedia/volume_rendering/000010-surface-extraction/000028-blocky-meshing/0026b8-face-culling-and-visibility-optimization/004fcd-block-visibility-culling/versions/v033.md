# Block Visibility Culling

Also called: Block Coordinate Change Detection, Block Rendering & Surface Orientation Culling, Camera-relative Block Culling, Visibility Culling via Normal Dot Product, renderBlock

## Overview
Block Visibility Culling determines which voxel blocks require mesh regeneration or rendering updates based on the camera's position and orientation, avoiding unnecessary geometry processing when the view has not changed significantly [S1, unofficial]. It operates at the coarse block level by comparing the current camera block coordinates and primary viewing direction against the previous frame's values to skip index updates if they match [S1, unofficial]. Unlike its sibling [Voxel Face Visibility Check](6723-voxel-face-visibility-check.md), which evaluates visibility for every face within a block using normal dot products, this method relies on block-level coordinate and direction caching to optimize the broader rendering pipeline [S1, unofficial][S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** Current camera world position $(P_x, P_y, P_z)$, camera rotation angles (specifically the horizontal angle $\theta$ in degrees), previous frame's camera block coordinates $(B_x^{prev}, B_y^{prev}, B_z^{prev})$, and previous frame's greatest viewing direction indicator (e.g., `greatestDir`).
*   **Outputs:** A boolean flag indicating whether the block mesh indices need to be updated, or a list of blocks marked for rendering.

**Data Structures:**
*   **Camera State:** Stores current and previous block coordinates and viewing direction.
*   **Block Face Visibility:** An array or enum `BlockFace` with flags for the six faces: `YNeg`, `XPos`, `YPos`, `XNeg`, `ZNeg`, `ZPos`. These flags are checked before rendering individual faces [S3, unofficial].

**Steps:**
1.  **Compute Camera Block Coordinates:** Calculate the integer block coordinates containing the camera by flooring its world position.
    $$ B_x = \lfloor P_x \rfloor, \quad B_y = \lfloor P_y \rfloor, \quad B_z = \lfloor P_z \rfloor $$
    [S1, unofficial]

2.  **Compute View Vector:** Calculate the view vector components $(v_x, v_y, v_z)$ from the camera's rotation angles. For a horizontal angle $\theta$ (in degrees):
    $$ c_s = \cos\left(\theta \cdot \frac{\pi}{180}\right), \quad s_n = \sin\left(\theta \cdot \frac{\pi}{180}\right) $$
    The view direction is typically derived from these trigonometric components, often aligned with the Z-axis in local space or mapped to world space depending on the coordinate system. [S1, unofficial][S3, unofficial]

3.  **Check for Change:** Compare the current camera block coordinates $(B_x, B_y, B_z)$ and the greatest viewing direction indicator with the previous frame's values.
    *   If both the block coordinates and the viewing direction match the previous frame, skip the index update process entirely.
    *   If they differ, proceed to update the visibility flags for the affected blocks.
    [S1, unofficial]

4.  **Determine Surface Orientation (Optional/Contextual):** For specific rendering implementations (e.g., raycasting or specific block rendering loops), determine the surface orientation relative to the player.
    *   Calculate block boundaries:
        $$ \text{blockX} = \text{chunkX} + x \cdot \text{BLOCK\_SIZE} $$
        $$ \text{blockY} = \text{chunkY} + y \cdot \text{BLOCK\_SIZE} $$
        $$ \text{blockZ}_{\text{bottom}} = \text{chunkZ} + z \cdot \text{BLOCK\_SIZE} $$
        $$ \text{blockZ}_{\text{top}} = \text{blockZ}_{\text{bottom}} + \text{BLOCK\_SIZE} $$
    *   Determine `surfaceOrientation`:
        *   $1$ if $\text{player}_z < \text{blockZ}_{\text{bottom}}$ (looking up)
        *   $2$ if $\text{player}_z > \text{blockZ}_{\text{top}}$ (looking down)
        *   $0$ otherwise
    [S3, unofficial]

5.  **Calculate Visibility Flags:** For each block, determine which faces are visible. This can be done by:
    *   Calculating the center of each surface as the mean of its vertices.
    *   Computing the view direction from the center to the camera position and normalizing it.
    *   Calculating the average normal of the surface.
    *   If the dot product of the average normal and the view direction is greater than 0, the surface is considered visible.
    [S2, unofficial]
    *   Alternatively, use the `surfaceOrientation` and block position to set flags in `block->visibleFaces[BlockFace::...]` before rendering [S3, unofficial].

**Parameters:**
*   **Surface Scale Multiplier:** In some implementations, a surface scale multiplier (e.g., 120) is used for floor/ceiling projection calculations [S3, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** Floating-point inaccuracies in camera position might cause flickering if the block coordinate calculation is not robust. Using `floor` is standard, but boundary conditions (e.g., exactly on a block edge) should be handled consistently.
*   **Direction Ambiguity:** Using a single angle for `greatestDir` might not capture vertical viewing changes. If the camera looks up or down significantly, the horizontal angle might remain the same, leading to missed updates. A more robust system might use a 2D direction vector or discrete vertical states (up, down, level) [S3, unofficial].
*   **Degenerate Input:** If the camera is exactly on a block boundary, the `floor` function will snap to one side. This is generally acceptable as long as it is consistent.

## Subtopics

### [Voxel Face Visibility Check](6723-voxel-face-visibility-check.md)
Determines visibility at the fine-grained face level using normal dot products. Choose this when per-face culling is required for complex block shapes or when block-level caching is insufficient.

## Operating characteristics
*   **Time Complexity:** $O(1)$ for the culling check itself, as it involves simple coordinate and direction comparisons. The actual mesh update is $O(N)$ where $N$ is the number of visible blocks, but this method reduces $N$ by skipping updates when the view is static.
*   **Memory Complexity:** $O(1)$ additional memory for storing previous frame's state.
*   **Strengths:** Extremely fast culling decision; significantly reduces CPU load in static scenes or when the camera moves slowly within a block.
*   **Limitations:** Only effective when the camera is within the same block or the viewing direction hasn't changed. It does not cull faces within a block, only the block's mesh update.
*   **When to use:** Ideal for voxel engines where mesh generation is expensive and the camera often remains stationary or moves slowly.
*   **When not to use:** When the camera moves rapidly between blocks or changes viewing direction frequently, the overhead of checking might be negligible compared to the benefit, but the method still provides a baseline optimization.

## Background
Block Visibility Culling is a technique commonly used in voxel-based games and real-time rendering engines to optimize the rendering of blocky terrain. It was popularized by implementations such as those found in Minecraft clones and custom voxel engines. The method leverages the discrete nature of voxel grids to simplify visibility checks, avoiding the need for complex frustum culling or occlusion culling at the block level.
