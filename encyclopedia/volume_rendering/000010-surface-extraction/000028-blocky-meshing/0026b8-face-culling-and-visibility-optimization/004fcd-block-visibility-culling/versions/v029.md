# Block Visibility Culling

Also called: Block Coordinate Change Detection, Block Rendering & Surface Orientation Culling, Camera-relative Block Culling, Visibility Culling via Normal Dot Product, renderBlock

## Overview
Block Visibility Culling determines which voxel blocks require mesh regeneration or rendering updates based on the camera's position and orientation, avoiding unnecessary geometry processing when the viewing direction or block-relative position remains stable [S1, S3, unofficial]. It solves the problem of redundant computation in dynamic voxel scenes by skipping index updates if the camera has not moved significantly or changed its primary viewing direction relative to the block grid [S1, unofficial]. Unlike sibling methods that operate at the fine-grained face level within a block [6723-voxel-face-visibility-check.md], this method operates at the coarse block level, using camera-relative coordinates and surface orientation flags to prune entire block faces before they are submitted to the rasterizer [S3, unofficial].

## How it works
**Inputs:**
- Camera world position $(P_x, P_y, P_z)$.
- Camera rotation angles (yaw $A$ in degrees, pitch $R$).
- Block size $B$ (typically 16 units, as seen in [S3, unofficial]).
- Previous frame's camera block coordinates $(C_{x,prev}, C_{y,prev}, C_{z,prev})$ and greatest direction indicator.
- Block visibility flags for each of the six faces ($YNeg, XPos, YPos, XNeg, ZNeg, ZPos$) [S3, unofficial].

**Outputs:**
- A set of visible faces for the current block, or a skip flag indicating no update is needed.
- Updated indices for the chunk mesh if faces are visible.

**Data Structures:**
- `BlockFace` enum: Stores visibility flags for the six faces of a voxel.
- `blocksData`: Map or array storing triangle indices for each block position.
- `vertexSlots`: Stack of available vertex indices for reuse.

**Steps:**

1.  **Compute Camera Block Coordinates:**
    Calculate the integer block coordinates containing the camera by flooring the world position:
    $$ C_x = \lfloor P_x / B \rfloor, \quad C_y = \lfloor P_y / B \rfloor, \quad C_z = \lfloor P_z / B \rfloor $$
    [S1, unofficial]

2.  **Check for Stasis (Optimization):**
    Compare the current camera block coordinates $(C_x, C_y, C_z)$ and the primary viewing direction (greatestDir) with the values from the previous frame. If both the block coordinates and the greatest direction match the previous frame, skip the index update process entirely [S1, unofficial].

3.  **Determine Surface Orientation:**
    For a block at chunk-relative coordinates $(x, y, z)$, calculate the absolute block boundaries:
    $$ B_x = C_x \cdot B + x \cdot B $$
    $$ B_y = C_y \cdot B + y \cdot B $$
    $$ B_{z, bottom} = C_z \cdot B + z \cdot B $$
    $$ B_{z, top} = B_{z, bottom} + B $$
    [S3, unofficial]

    Determine the vertical orientation relative to the camera:
    - If $P_z < B_{z, bottom}$, orientation is 1 (Camera is below the block).
    - If $P_z > B_{z, top}$, orientation is 2 (Camera is above the block).
    - Otherwise, orientation is 0 (Camera is within the vertical range of the block).
    [S3, unofficial]

4.  **Calculate View Vector:**
    Compute the view vector components $(v_x, v_y, v_z)$ from the camera's rotation angles (rx, ry). Alternatively, compute the view direction from the block center to the camera position and normalize it [S1, S2, unofficial].

5.  **Evaluate Face Visibility:**
    For each of the six faces of the block, determine if it is visible based on the camera's position and orientation flags [S3, unofficial].
    
    *Method A (Flag-based from [S3, unofficial]):*
    The visibility of specific faces is determined by the `surfaceOrientation` and the loop index `w` (0 to 3 for side walls). The code checks specific flags:
    - If `w == 0` and `!block->visibleFaces[BlockFace::YNeg]`, skip.
    - If `w == 1` and `!block->visibleFaces[BlockFace::XPos]`, skip.
    - If `w == 2` and `!block->visibleFaces[BlockFace::YPos]`, skip.
    - If `w == 3` and `!block->visibleFaces[BlockFace::XNeg]`, skip.
    [S3, unofficial]

    *Method B (Normal Dot Product from [S2, unofficial]):*
    Calculate the average normal $\mathbf{n}$ of the face (mean of vertex normals, normalized). Calculate the view direction $\mathbf{v}$ from the face center to the camera. If the dot product $\mathbf{n} \cdot \mathbf{v} > 0$, the surface is considered visible [S2, unofficial].

6.  **Transform and Project (if rendering):**
    If the face is visible, transform the block corners to camera space.
    Compute trigonometric values:
    $$ c_s = \cos(A \cdot \pi / 180), \quad s_n = \sin(A \cdot \pi / 180) $$
    [S3, unofficial]
    
    For each corner $w$ of the bottom face:
    $$ x_1 = x_{bottom1}[w] - P_x $$
    $$ y_1 = y_{bottom1}[w] - P_y $$
    [S3, unofficial]
    
    Swap $x_1/x_2$ and $y_1/y_2$ if orientation is 1 (camera below) [S3, unofficial].
    
    Project to screen space:
    $$ wallX[w][0] = x_1 \cdot c_s - y_1 \cdot s_n $$
    [S3, unofficial]

7.  **Generate Indices:**
    If the face passes visibility checks, add the four vertices of the square face to the vertex buffer and push 6 indices (two triangles) to the index buffer [S1, unofficial].

**Parameters:**
- `BLOCK_SIZE`: 16 (typical voxel size) [S3, unofficial].
- `surfaceScale`: 120 (multiplier for floor/ceiling projection tile calculation) [S3, unofficial].

**Edge Cases and Pitfalls:**
- **Precision:** When calculating $z$ for perspective division, if $z=0$, it must be clamped to a small epsilon (e.g., 0.0001) to avoid division by zero [S3, unofficial].
- **Boundary Conditions:** Chunk edges must be handled to prevent artifacts; this method relies on the parent's chunking principles [3861-face-culling-and-visibility-optimization.md].
- **Transparency:** Simple neighbor checks may fail for transparent blocks; specialized culling modes or opacity thresholds are required if the block is not opaque [S1, S3, unofficial].

## Subtopics

### [Voxel Face Visibility Check](6723-voxel-face-visibility-check.md)
Operates at the fine-grained face level within a block, evaluating geometric relationships between face normals and the viewer. Choose this when per-face precision is needed within a single block, rather than coarse block-level skipping.

## Operating characteristics
- **Time Complexity:** $O(1)$ per block for the culling decision (constant number of faces and checks). The stasis check [S1, unofficial] reduces this to $O(1)$ with a very small constant when the camera is static.
- **Memory Complexity:** $O(1)$ auxiliary memory per block for storing visibility flags and temporary transformation variables.
- **Performance:** Significantly reduces draw calls and vertex processing by avoiding mesh regeneration for invisible blocks [S3, unofficial]. Performance scales with the number of visible blocks, not total blocks.
- **Strengths:** Simple to implement; effective for static or slowly moving cameras; reduces CPU load on mesh generation.
- **Limitations:** Does not handle occlusion from other blocks (only view direction); requires careful handling of chunk boundaries [S1, unofficial]. Not suitable for highly dynamic scenes where the camera moves rapidly between distant blocks without intermediate frames, as the stasis check might fail to catch necessary updates if not robustly implemented.

## Background
Block Visibility Culling is a technique prevalent in voxel-based rendering engines, particularly those emulating retro-style graphics or optimizing Minecraft-like worlds. It is implemented in projects such as `exolands` [S1, unofficial] and `Voxel1993` [S3, unofficial]. The method leverages the discrete nature of voxel grids to simplify visibility testing to coordinate comparisons and basic trigonometric projections, avoiding the overhead of full frustum culling or ray tracing for every face.
