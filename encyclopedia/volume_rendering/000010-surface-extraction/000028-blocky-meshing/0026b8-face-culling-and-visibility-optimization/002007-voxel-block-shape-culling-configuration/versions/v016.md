# Voxel Block Shape & Culling Configuration

Also called: Block trait interface, Shape enum system

## Overview
Voxel Block Shape & Culling Configuration is a trait-based system that defines block geometry, transparency culling behavior, and lighting properties per block type during mesh generation [S1, unofficial]. It solves the problem of rigid, single-shape voxel meshes by allowing distinct geometric representations (e.g., ramps, fluids) and granular face-culling rules (e.g., merging transparent faces) to be associated with specific block IDs. Unlike sibling methods that focus on bulk optimization (like [Face Coverage Mask Culling](3397-face-coverage-mask-culling.md)) or vertex packing ([ChunkMesh Vertex Packing and Management](3566-chunkmesh-vertex-packing-and-management.md)), this configuration defines the *semantic* rules for how individual block types are rendered and culled.

## How it works
The system operates by associating a configuration object (often a trait or interface implementation) with each block type in the voxel world. This configuration dictates the shape geometry, the culling mode, and the lighting value for any face generated by that block.

### Inputs and Outputs
- **Input**: The block type identifier (e.g., `MyBlock::Glass`) and the face orientation (e.g., `AlignedFace::PosZ`).
- **Output**: A shape definition (geometry), a culling mode (enum), and a lighting value (float/byte).

### Data Structures
The core configuration is typically implemented via a trait or interface. In Rust-like pseudocode (from [S1, unofficial]), the trait `BlockConfig` includes:

```rust
trait BlockConfig {
    /// Returns the shape geometry for a given face.
    fn shape(&self, face: Face) -> Shape;
    
    /// Returns the culling mode for this block type.
    fn cull_mode(&self) -> CullMode;
    
    /// Returns the lighting value for a given face.
    fn light(&self, face: Face) -> u8;
}
```

The `Shape` enum defines the geometry. Common variants include:
- `WholeBlock`: A standard 1x1x1 cube.
- `Cross(CrossInfo)`: A cross-shaped geometry (e.g., for chains), defined by an `AlignedFace` and a `stretch` value.
- `Ramp`: A sloped face (see Subtopics).
- `Fluid`: A surface-stitched fluid column (see Subtopics).

The `CullMode` enum defines how faces are culled relative to neighbors:
- `Empty`: The block is air; no faces generated.
- `Opaque`: Standard opaque culling. Faces are generated if the neighbor is empty or transparent.
- `TransparentMerged(T)`: Shared faces between two transparent blocks are culled if their `TransparentGroup` values (type `T`) are equal. This merges visually identical transparent surfaces.
- `TransparentUnmerged`: Transparent faces are never merged with neighbors, even if they share the same material.

### Numbered Steps
1. **Configuration Lookup**: For each non-empty voxel in the chunk, retrieve its `BlockConfig` implementation based on the block ID.
2. **Face Iteration**: Iterate over the 6 faces of the voxel.
3. **Shape Determination**: Call `config.shape(face)` to determine the geometry for that specific face. If the shape is `Empty` or invalid, skip the face.
4. **Culling Decision**: Call `config.cull_mode()` to get the culling strategy.
   - If `CullMode::Empty`, discard the face.
   - If `CullMode::Opaque`, apply standard neighbor check: generate face if neighbor is empty/transparent.
   - If `CullMode::TransparentMerged(T)`, generate face if neighbor is empty/transparent. Additionally, if the neighbor is transparent and has the same `TransparentGroup` ID, cull the shared face (merge it).
   - If `CullMode::TransparentUnmerged`, generate face if neighbor is empty/transparent, but never cull shared transparent faces.
5. **Lighting Assignment**: Call `config.light(face)` to get the lighting value for the face.
6. **Geometry Generation**: Use the determined shape to generate vertices and indices, applying the lighting value and any shape-specific attributes (e.g., tints for ramps).

### Formulas and Parameters
- **Culling Condition for `TransparentMerged`**:
  Let $B_i$ be the current block with cull mode $C_i = \text{TransparentMerged}(T_i)$ and neighbor $B_j$ with cull mode $C_j = \text{TransparentMerged}(T_j)$.
  A face between $B_i$ and $B_j$ is culled if:
  $$ T_i = T_j \quad \text{AND} \quad B_j \text{ is transparent} $$
  Otherwise, the face is generated.

- **Lighting**:
  Lighting values are typically floats or bytes. For example, `MyBlock::Glass` might have a light value of `2.0`, while `MyBlock::Air` has `0.0` [S1, unofficial].

### Edge Cases and Pitfalls
- **Fluid Shape Implementation**: Setting `FLUID_ENABLED` to true without implementing the fluid shape logic causes a debug assertion failure rather than silently drawing fluids as cubes [S1, unofficial].
- **Threading Constraints**: In engines like Unity3D, mesh data calculation can be done on background threads, but the final `Mesh` object creation must occur on the main thread [S3, unofficial].
- **Tint Fallback**: For ramp shapes, if a specific tint is `Vector3.One`, it should fallback to another face's tint to avoid visual artifacts [S2, unofficial].

### Pseudocode
```python
def generate_chunk_mesh(chunk):
    vertices = []
    indices = []
    
    for x, y, z in chunk.voxels:
        block_id = chunk.get_block(x, y, z)
        config = get_block_config(block_id)
        
        if config.cull_mode() == CullMode.Empty:
            continue
            
        for face in [PosX, NegX, PosY, NegY, PosZ, NegZ]:
            neighbor_id = chunk.get_block(x + face.dx, y + face.dy, z + face.dz)
            neighbor_config = get_block_config(neighbor_id)
            
            # Determine if face should be generated
            should_generate = False
            
            if config.cull_mode() == CullMode.Opaque:
                # Generate if neighbor is empty or transparent
                if neighbor_config.is_empty_or_transparent():
                    should_generate = True
                    
            elif config.cull_mode() == CullMode.TransparentMerged:
                # Generate if neighbor is empty or transparent
                if neighbor_config.is_empty_or_transparent():
                    # Check for merging
                    if neighbor_config.is_transparent() and \
                       config.transparent_group() == neighbor_config.transparent_group():
                        should_generate = False # Merge
                    else:
                        should_generate = True
                        
            elif config.cull_mode() == CullMode.TransparentUnmerged:
                if neighbor_config.is_empty_or_transparent():
                    should_generate = True
            
            if should_generate:
                shape = config.shape(face)
                light = config.light(face)
                
                # Generate vertices/indices based on shape
                verts, idxs = shape.generate_vertices(face, light)
                vertices.extend(verts)
                indices.extend(idxs)
                
    return Mesh(vertices, indices)
```

## Subtopics

### [Three-Valued Opacity Classification for Meshing](4414-three-valued-opacity-classification-for-meshing.md)
A classification system for block IDs into three mutually exclusive layers: 'opaque', 'water', and 'transparentSolid'. It distinguishes between fluids (water) requiring bespoke shaders and see-through solids (glass/leaves) requiring alpha blending. Unlike a boolean transparent flag, this model allows water to use a bespoke shader (ripple, refraction) while glass/leaves use the ordinary block atlas with alpha blending.

### Ramp Shape Geometry
A shape representing a sloped block face, composed of a slope quad (2 triangles) and two side triangles (left and right) [S2, unofficial]. Instance creation involves iterating visible faces; if the face is Left, Right, Top, or Front, `drawSlope` is set to true and tints are assigned (`tints[0]` for Top/Front, `tints[1]` for Left, `tints[2]` for Right). If a tint is `Vector3.One`, it falls back to another face's tint. Slope vertices are defined as: (0,1,0) UV[0], (0,0,1) UV[1], (1,1,0) UV[2], (1,1,0) UV[3], (0,0,1) UV[4], (1,0,1) UV[5]. Left triangle: (0,0,1) UV[0], (0,1,0) UV[1], (0,0,0) UV[2]. Right triangle: (1,0,0) UV[0], (1,1,0) UV[1], (1,0,1) UV[2] [S2, unofficial].

### Fluid Surface Stitching
A mesh generation technique where fluid columns share a surface height field with neighbors, stitching surfaces when fluid IDs match [S1, unofficial]. Two adjacent fluid blocks join their surfaces only when their `FluidInfo::id` (u8) values are equal [S1, unofficial].

### Geometry Builder Pattern
A design pattern using an interface (`IGeometryBuilder`) to control the type of geometry created for each non-empty voxel, allowing different geometry types (cubes, ramps, X-shapes) to be generated via polymorphism without large switch statements [S3, unofficial]. The interface contains a single function `BuildGeometry()`, which is called once for each non-empty block during mesh creation. It takes a reference to the chunk object and adds vertices/indices to the chunk's linked list. After all blocks are processed, the data is placed into a Unity3D Mesh object on the main thread [S3, unofficial].

## Operating characteristics
- **Time Complexity**: $O(N)$ where $N$ is the number of voxels in the chunk, as each voxel is processed once with constant-time configuration lookups.
- **Memory Complexity**: $O(V + I)$ where $V$ is the number of vertices and $I$ is the number of indices generated. The configuration data is typically small and static per block type.
- **Strengths**: Highly flexible; allows complex block types (ramps, fluids) without modifying the core meshing algorithm. Granular control over transparency merging reduces draw calls for transparent blocks.
- **Limitations**: Requires careful implementation of shape generators for non-cube blocks. Threading constraints in some engines (e.g., Unity) require careful management of mesh object creation [S3, unofficial].
- **When to use**: When the voxel world contains diverse block types with different geometries or rendering requirements (e.g., Minecraft-like worlds).
- **When not to use**: For simple, uniform voxel worlds where all blocks are cubes and have identical rendering properties.

## Background
The concept of block-specific configuration in voxel rendering evolved from the need to support complex block types in games like Minecraft. Early implementations used simple boolean flags for transparency, which were insufficient for distinguishing between fluids and see-through solids [S1, unofficial]. The trait-based interface approach, as seen in projects like `finnbear/voxmesh`, provides a clean separation of concerns between block semantics and mesh generation [S1, unofficial]. The Geometry Builder pattern, documented in academic works on procedural voxel generation, offers a scalable way to extend block geometry without code bloat [S3, unofficial].
