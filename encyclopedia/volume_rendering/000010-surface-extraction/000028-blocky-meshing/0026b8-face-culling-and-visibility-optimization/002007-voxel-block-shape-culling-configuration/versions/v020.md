# Voxel Block Shape & Culling Configuration

Also called: Block trait interface, Shape enum system

## Overview
Voxel Block Shape & Culling Configuration is a trait-based system that defines block geometry, transparency culling modes, and lighting properties per block type to optimize mesh generation [S1, unofficial]. It solves the problem of uniform meshing by allowing distinct rendering behaviors (e.g., opaque, transparent merged, transparent unmerged) and complex geometries (e.g., ramps, fluids) to be handled via polymorphism rather than large conditional blocks [S1, unofficial][S3, unofficial]. It sets itself apart from sibling methods like [Face Culling](8735-face-culling.md) by encapsulating the *decision logic* for visibility and shape within the block definition itself, rather than relying solely on global neighbor checks.

## How it works
The system operates by associating a configuration object (trait) with each block type. This object dictates the shape geometry, the culling mode, and the lighting value.

### Inputs and Outputs
- **Input**: Block type identifier (e.g., `MyBlock::Glass`), face orientation (e.g., `AlignedFace::PosZ`), and chunk context.
- **Output**: A set of vertices and indices for the mesh, determined by the block's shape and culling rules.

### Data Structures

#### Shape Enum
Defines the geometric primitive for a block.
```rust
enum Shape {
    WholeBlock,
    Cross(CrossInfo),
    // ... other shapes like Ramp, Fluid, etc.
}

struct CrossInfo {
    face: AlignedFace,
    stretch: f32,
}
```

#### CullMode Enum
Determines how faces are culled based on neighbor occupancy and transparency.
```rust
enum CullMode {
    Empty,
    Opaque,
    TransparentMerged(T),
    TransparentUnmerged,
}
```
- `Empty`: No faces generated.
- `Opaque`: Standard culling; faces generated if neighbor is empty/transparent.
- `TransparentMerged(T)`: Culls shared faces between two transparent blocks if their `TransparentGroup` values (type `T`) are equal. Does not replace `PartialEq` for greedy meshing [S1, unofficial].
- `TransparentUnmerged`: Faces are never merged with other transparent blocks, even if identical.

#### Vertex Layout
Vertices carry per-vertex data for shading and filtering.
```rust
struct Vertex {
    pos: Vec4<f32>,       // Position
    uv: Vec2<f32>,        // Texture coordinates
    normal: Vec3<f32>,    // Surface normal
    ao: f32,              // Ambient occlusion (0.0 = occluded, 1.0 = lit)
    smooth_light: f32,    // Smooth lighting value (0.0..1.0)
    block: MyBlock,       // Block type for render pass filtering
    atlas_offset: f32,    // Atlas tile offset
    two_sided: bool,      // Whether the quad is two-sided
}
```

#### Interpolated Vertex-to-Fragment Data
```rust
struct VsOut {
    uv: Vec2<f32>,
    normal: Vec3<f32>,
    atlas_u_offset: f32,
    ao: f32,
    smooth_light: f32,
}
```

### Steps

1. **Configuration Retrieval**: For each non-empty voxel, retrieve its block configuration trait.
2. **Shape Determination**: Call the `shape()` method on the trait.
   - If the shape is `WholeBlock`, generate standard cube faces.
   - If the shape is `Cross`, generate the specific cross geometry defined in `CrossInfo`.
   - If the shape is a variant (e.g., Ramp, Fluid), delegate to the specific geometry builder.
3. **Culling Decision**: Call the `cull_mode()` method.
   - If `Empty`, skip the block.
   - If `Opaque` or `TransparentUnmerged`, apply standard neighbor checks.
   - If `TransparentMerged(T)`, check if the neighbor is also transparent and has the same `T` value. If so, cull the shared face.
4. **Lighting Calculation**: Call the `light()` method to determine the lighting value for the face.
   - Some blocks (e.g., `Cactus`) have face-dependent lighting.
5. **Geometry Generation**:
   - For standard blocks, generate vertices using the `Vertex` layout.
   - For complex shapes (e.g., Ramps, Fluids), use specific geometry builders or instance creation logic.
6. **Mesh Assembly**: Add generated vertices and indices to the chunk's linked list.
7. **Thread Safety**: Ensure that final mesh object creation (e.g., in Unity3D) occurs on the main thread, while vertex/index calculation occurs on background threads [S3, unofficial].

### Formulas

#### Neighbor Position
The neighbor position for culling is calculated as:
$$ P_{neighbor} = P + N $$
where $P$ is the voxel position and $N$ is the face normal [Parent].

#### Culling Condition
A face is visible if:
$$ \text{Visible} = \neg \text{Occupied}(P_{neighbor}) \lor \text{Transparent}(P_{neighbor}) $$
For `TransparentMerged`, an additional condition applies:
$$ \text{Visible} = \neg \text{Occupied}(P_{neighbor}) \lor (\text{Transparent}(P_{neighbor}) \land \text{Group}(P) \neq \text{Group}(P_{neighbor})) $$

### Parameters

- **FLUID_ENABLED**: Boolean flag. If `true` without fluid shape implementation, causes debug assertion failure [S1, unofficial].
- **TransparentGroup**: Type `T` for `TransparentMerged`. Identifies groups of transparent blocks that should merge (e.g., all water blocks).

### Edge Cases and Pitfalls

- **Fluid Shape**: Setting `FLUID_ENABLED` to `true` without implementing fluid shape causes a debug assertion failure rather than silently drawing fluids as cubes [S1, unofficial].
- **Threading**: Unity3D functions must be called on the main thread. Vertex/index calculation can be done on a background thread, but final mesh creation must be moved to the main thread [S3, unofficial].
- **Greedy Meshing**: `TransparentMerged` does not replace `PartialEq` for greedy meshing, requiring careful handling of merge logic [S1, unofficial].

## Subtopics

### [Three-Valued Opacity Classification for Meshing](4414-three-valued-opacity-classification-for-meshing.md)
A classification system for block IDs into three mutually exclusive layers ('opaque', 'water', 'transparentSolid') to determine rendering material and buffer assignment. It solves the insufficiency of a single boolean 'transparent' flag by distinguishing between fluids (water) requiring bespoke shaders and see-through solids (glass/leaves) requiring alpha blending. Unlike a boolean transparent flag which collapses water and glass/leaves into one category, this three-valued model allows water to use a bespoke shader (ripple, refraction) while glass/leaves use the ordinary block atlas with alpha blending.

### Ramp Shape Geometry
A shape representing a sloped block face, composed of a slope quad (2 triangles) and two side triangles (left and right) [S2, unofficial]. Instance creation involves iterating visible faces. If the face is Left, Right, Top, or Front, `drawSlope` is set to true and tint is assigned to `tints[0]` (Top/Front), `tints[1]` (Left), or `tints[2]` (Right). If a specific tint is `Vector3.One`, it falls back to another face's tint. Instances are added for slope, left triangle, and right triangle using respective shape IDs and tints. If the face is Back or Bottom, an instance is added using `cubeBackFaceShapeID` or `cubeBottomFaceShapeID` [S2, unofficial]. Slope vertices are: (0,1,0) with UV[0], (0,0,1) with UV[1], (1,1,0) with UV[2], (1,1,0) with UV[3], (0,0,1) with UV[4], (1,0,1) with UV[5]. Left triangle vertices are: (0,0,1) with UV[0], (0,1,0) with UV[1], (0,0,0) with UV[2]. Right triangle vertices are: (1,0,0) with UV[0], (1,1,0) with UV[1], (1,0,1) with UV[2] [S2, unofficial].

### Fluid Surface Stitching
A mesh generation technique where fluid columns share a surface height field with neighbors, stitching surfaces when fluid IDs match [S1, unofficial]. Two adjacent fluid blocks join their surfaces only when their `FluidInfo::id` (u8) values match [S1, unofficial].

### Geometry Builder Pattern
A design pattern using an interface to control the type of geometry created for each non-empty voxel, allowing different geometry types (cubes, ramps, X-shapes) to be generated via polymorphism without large switch statements [S3, unofficial]. The interface `IGeometryBuilder` contains a single function `BuildGeometry()`. During mesh creation, `BuildGeometry()` is called once for each non-empty block, passing a reference to the chunk object. Inside `BuildGeometry()`, vertices and indices are added to the chunk's linked list. After all blocks are processed, the vertex and index data is placed into a Unity3D Mesh object on the main thread [S3, unofficial]. Calculating vertex and index data is done on a background thread, but final mesh creation must be on the main thread [S3, unofficial].

## Operating characteristics
- **Time Complexity**: $O(N)$ where $N$ is the number of blocks in the chunk, as each block is processed once.
- **Memory Complexity**: $O(V + I)$ where $V$ is the number of vertices and $I$ is the number of indices.
- **Performance**: Reduces overdraw by culling internal faces and merging transparent faces where appropriate.
- **Strengths**: Flexible geometry support, efficient culling, modular design.
- **Limitations**: Requires careful handling of threading (e.g., Unity3D main thread constraint). Debug assertions can fail if configuration is incomplete (e.g., fluid shape not implemented).

## Background
Originated in voxel game development, particularly in Minecraft-like engines, to support complex block shapes and efficient rendering. The trait-based approach allows for easy extension of block types without modifying core mesh generation code. The Geometry Builder pattern was introduced to support complex shapes like ramps and fluids without large switch statements [S3, unofficial].
