# Voxel Block Shape & Culling Configuration

Also called: Block trait interface, Shape enum system

## Overview
Voxel Block Shape & Culling Configuration is a trait-based system that defines the geometry, transparency culling behavior, and lighting properties for individual block types in a voxel mesh generator. It solves the problem of heterogeneous block types (e.g., glass, water, slopes) requiring different rendering passes and geometric representations by decoupling block identity from mesh generation logic. Unlike the parent method's uniform grid assumption, this configuration allows specific blocks to opt into merged transparent culling, unmerged transparent culling, or opaque culling, and to define non-cubic shapes.

## How it works
The system operates by associating a configuration object (trait) with each block type. This trait determines how the block's faces are processed during mesh generation.

### Inputs and Outputs
- **Input**: A block type identifier (e.g., `MyBlock::Glass`) and the face normal being evaluated.
- **Output**: A `CullMode` enum, a `Shape` enum, and lighting values.

### Data Structures

#### CullMode
Defines how faces are culled based on neighbor states.
- `Empty`: The block is air; no faces are generated.
- `Opaque`: Faces are generated if the neighbor is empty. Standard boundary culling.
- `TransparentMerged(T)`: Faces are generated if the neighbor is empty OR if the neighbor is a transparent block with the same `TransparentGroup` value `T`. Shared faces between two blocks with the same `T` are culled.
- `TransparentUnmerged`: Faces are generated if the neighbor is empty. Transparent faces are never merged with other transparent blocks, even if they are identical.

#### Shape
Defines the geometric primitive for the block.
- `WholeBlock`: A standard 1x1x1 cube.
- `Cross(CrossInfo)`: A cross-shaped block (e.g., chains, rails). Defined by an `AlignedFace` (direction) and `stretch` value.
- `Ramp`: A sloped block (see Subtopics).
- `Fluid`: A fluid surface block (see Subtopics).

#### Vertex Layout
Vertices generated by these shapes include:
- `pos`: `Vec4<f32>` (position).
- `uv`: `Vec2<f32>` (texture coordinates).
- `normal`: `Vec3<f32>` (face normal).
- `ao`: `f32` (ambient occlusion, 0.0=occluded, 1.0=lit).
- `smooth_light`: `f32` (smooth lighting value).
- `block`: Block identifier for render pass filtering.
- `atlas_offset`: `f32` (pre-computed atlas tile offset).
- `two_sided`: `bool` (whether the quad is two-sided).

### Steps

1. **Retrieve Configuration**: For each non-empty voxel at position $P$ with block type $B$, retrieve its trait configuration.
2. **Determine Cull Mode**: Call `cull_mode(B)` to get the culling strategy.
3. **Determine Shape**: Call `shape(B, face)` to get the geometric primitive for the specific face being evaluated.
4. **Evaluate Visibility**:
   - If `CullMode::Empty`, skip.
   - If `CullMode::Opaque`, check if neighbor $N$ at $P + \text{normal}$ is empty. If empty, generate face.
   - If `CullMode::TransparentMerged(T)`, check if neighbor $N$ is empty OR if $N$ is transparent with `TransparentGroup == T`. If so, generate face. Note: `CullMode::TransparentMerged` does not replace `PartialEq` for greedy meshing; greedy meshing must still handle transparency correctly [S1, unofficial].
   - If `CullMode::TransparentUnmerged`, check if neighbor $N$ is empty. If empty, generate face.
5. **Generate Geometry**: Use the `Shape` to generate vertices and indices.
   - For `WholeBlock`, generate 6 faces (if visible).
   - For `Cross`, generate geometry based on `CrossInfo`.
   - For `Ramp`, generate slope quad and side triangles [S2, unofficial].
   - For `Fluid`, stitch surfaces with neighbors if IDs match [S1, unofficial].
6. **Apply Lighting**: Calculate lighting values based on `light(B, face)` [S1, unofficial].
7. **Add to Mesh**: Add vertices and indices to the chunk's buffer.

    """
    Generates mesh geometry for a single block type within a chunk.
    """
    cull_mode = get_cull_mode(block_type)
    if cull_mode == CullMode.Empty:
        return

    # Determine shape for each face
    for face_normal in [Face.X_POS, Face.X_NEG, Face.Y_POS, Face.Y_NEG, Face.Z_POS, Face.Z_NEG]:
        shape = get_shape(block_type, face_normal)
        
        # Check visibility based on cull mode
        neighbor_pos = position + face_normal
        neighbor_type = chunk.get_block(neighbor_pos)
        
        is_visible = False
        if cull_mode == CullMode.Opaque:
            is_visible = (neighbor_type == BlockType.Air)
        elif cull_mode == CullMode.TransparentUnmerged:
            is_visible = (neighbor_type == BlockType.Air)
        elif cull_mode == CullMode.TransparentMerged:
            # Get transparent group of current block
            current_group = get_transparent_group(block_type)
            # Get transparent group of neighbor
            neighbor_group = get_transparent_group(neighbor_type) if is_transparent(neighbor_type) else None
            
            # Visible if neighbor is air OR neighbor is transparent with same group
            is_visible = (neighbor_type == BlockType.Air) or (neighbor_group == current_group)
        
        if is_visible:
            # Generate geometry for this face
            vertices, indices = generate_shape_geometry(shape, position, face_normal, block_type)
            chunk.add_vertices(vertices)
            chunk.add_indices(indices)

### Parameters
- `FLUID_ENABLED`: Boolean flag. If `true` but fluid shape is not implemented, causes debug assertion failure rather than silently drawing fluids as cubes [S1, unofficial].
- `TransparentGroup`: Integer or enum value assigned to transparent blocks. Blocks with the same group are merged during culling [S1, unofficial].

### Edge Cases and Pitfalls
- **Fluid Assertion Failure**: Setting `FLUID_ENABLED` to `true` without implementing the fluid shape logic results in a debug assertion failure [S1, unofficial].
- **Greedy Meshing**: `CullMode::TransparentMerged` does not automatically handle greedy meshing for transparent blocks. Greedy meshing must be implemented separately to merge adjacent transparent faces [S1, unofficial].
- **Threading**: In Unity3D, mesh creation (placing vertex/index data into a `Mesh` object) must occur on the main thread, even if geometry calculation is done on a background thread [S3, unofficial].

## Subtopics

### [Three-Valued Opacity Classification for Meshing](4414-three-valued-opacity-classification-for-meshing.md)
A classification system for block IDs into three mutually exclusive layers: 'opaque', 'water', and 'transparentSolid'. It solves the insufficiency of a single boolean 'transparent' flag by distinguishing between fluids (water) requiring bespoke shaders and see-through solids (glass/leaves) requiring alpha blending. Unlike a boolean transparent flag which collapses water and glass/leaves into one category, this three-valued model allows water to use a bespoke shader (ripple, refraction) while glass/leaves use the ordinary block atlas with alpha blending.

### [VoxelBlockyTypeLibrary with Attributes](12820-voxelblockytypelibrary-with-attributes.md)
`VoxelBlockyTypeLibrary` is a model management system for blocky voxel terrains that organizes meshes by logical "block types" with configurable state attributes, rather than storing individual model references directly. It solves the problem of managing complex block behaviors (e.g., orientation, powered state, connections) by automatically generating unique numerical IDs for every combination of attribute values, similar to Minecraft's block state system. It differs from the standard `VoxelBlockyLibrary` by decoupling model identity from manual ID assignment, using a combinatorial attribute system instead.

### Ramp Shape Geometry
A shape representing a sloped block face, composed of a slope quad (2 triangles) and two side triangles (left and right) [S2, unofficial]. Instance creation iterates visible faces. If face is Left, Right, Top, or Front, `drawSlope` is set to `true` and tint is assigned to `tints[0]` (Top/Front), `tints[1]` (Left), or `tints[2]` (Right). If a specific tint is `Vector3.One`, fallback to another face's tint. Slope vertices are: (0,1,0) with UV[0], (0,0,1) with UV[1], (1,1,0) with UV[2], (1,1,0) with UV[3], (0,0,1) with UV[4], (1,0,1) with UV[5]. Left triangle vertices: (0,0,1) with UV[0], (0,1,0) with UV[1], (0,0,0) with UV[2]. Right triangle vertices: (1,0,0) with UV[0], (1,1,0) with UV[1], (1,0,1) with UV[2] [S2, unofficial].

### Fluid Surface Stitching
A mesh generation technique where fluid columns share a surface height field with neighbors, stitching surfaces when fluid IDs match [S1, unofficial]. Two adjacent fluid blocks join their surfaces only when their `FluidInfo::id` (u8) values match [S1, unofficial].

### Geometry Builder Pattern
A design pattern using an interface to control the type of geometry created for each non-empty voxel, allowing different geometry types (cubes, ramps, X-shapes) to be generated via polymorphism without large switch statements [S3, unofficial]. The interface `IGeometryBuilder` contains a single function `BuildGeometry()`. During mesh creation, `BuildGeometry()` is called once for each non-empty block, passing a reference to the chunk object. The chunk stores vertices and indices in a linked list. After all blocks are processed, the data is placed into a Unity3D Mesh object on the main thread [S3, unofficial]. Pitfall: Unity3D functions must be called on the main thread; vertex/index calculation can be done on a background thread, but final Mesh object creation must be moved to the main thread [S3, unofficial].

## Operating characteristics
- **Time Complexity**: $O(N)$ where $N$ is the number of non-empty voxels, as each voxel is processed once to generate its visible faces.
- **Memory Complexity**: $O(F)$ where $F$ is the number of visible faces, as each visible face generates a constant number of vertices and indices.
- **Strengths**: Allows for complex block types (slopes, fluids, chains) without modifying the core mesh generation algorithm. Decouples block logic from rendering logic.
- **Limitations**: Requires careful management of threading in engines like Unity3D. Transparent merging requires additional logic for greedy meshing.
- **When to Use**: When the voxel world contains diverse block types with different rendering requirements (transparency, shape, lighting).
- **When Not to Use**: For simple, uniform voxel worlds where all blocks are opaque cubes.

## Background
The concept of block traits and shape configurations originated in voxel game development, particularly in Minecraft-like games, where different block types require different geometries and rendering behaviors. The specific implementations cited here are from unofficial sources: `finnbear/voxmesh` [S1, unofficial], `rarefushion/Cubic-Grid_Voxel_Renderer` [S2, unofficial], and a thesis on procedural generation of voxel worlds [S3, unofficial].
