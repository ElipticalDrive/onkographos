# Voxel Block Shape & Culling Configuration

Also called: Block trait interface, Shape enum system

## Overview
Voxel Block Shape & Culling Configuration is a trait-based system that defines the geometry, transparency culling behavior, and lighting properties for individual block types within a voxel mesh generator. It solves the problem of heterogeneous block rendering by allowing each block ID to specify its own shape (e.g., cube, ramp, fluid) and culling mode (e.g., opaque, transparent merged, transparent unmerged), rather than applying a single global rule. It differs from [Face Culling](8735-face-culling.md) by encapsulating block-specific visibility logic and from [Voxel Block Placement with Face Culling](923-voxel-block-placement-with-face-culling.md) by supporting non-cubic geometries and complex transparency merging via a configuration interface.

## How it works
The method operates by associating a configuration object (trait) with each block type. This configuration dictates the vertex layout (shape), the face culling decision logic, and the lighting intensity.

### Inputs and Outputs
*   **Input**: A block ID (e.g., `MyBlock::Glass`) and the face normal $\mathbf{n}$ for which geometry is being generated.
*   **Output**: A set of vertices and indices defining the visible faces for that block at the current position, along with metadata (lighting, transparency group) for the rendering pipeline.

### Data Structures
The core configuration is defined by a trait or interface with three primary methods/fields:

1.  **Shape**: Returns the geometric primitive for the block.
    *   *Layout*: An enum or struct. Common values include `WholeBlock` (standard cube), `Cross` (for thin objects like chains), or custom shapes (ramps, fluids).
    *   *Example*: `Shape::Cross(CrossInfo { face: AlignedFace::PosZ, stretch: 0 })` [S1, unofficial].

2.  **CullMode**: Determines how faces are culled based on neighbors.
    *   *Layout*: An enum.
    *   *Values*:
        *   `Empty`: No geometry generated.
        *   `Opaque`: Standard face culling; shared faces between two opaque blocks are removed.
        *   `TransparentMerged(T)`: Shared faces between two transparent blocks are removed **only if** their `TransparentGroup` values are equal. This allows merging of identical transparent surfaces (e.g., two glass panes) [S1, unofficial].
        *   `TransparentUnmerged`: Faces are never merged with neighbors; every exposed face is rendered. Used for objects that should not visually merge with identical neighbors (e.g., leaves, chains) [S1, unofficial].

3.  **Light**: Returns the lighting intensity for the block.
    *   *Layout*: A float or integer value. Can be static or depend on the face normal (e.g., cactus top vs. side) [S1, unofficial].

### Vertex Data
Vertices generated by these shapes include:
*   `pos`: Position (Vec4<f32>).
*   `uv`: Texture coordinates (Vec2<f32>).
*   `normal`: Face normal (Vec3<f32>).
*   `ao`: Ambient occlusion (f32, 0.0=occluded, 1.0=lit) [S1, unofficial].
*   `smooth_light`: Smooth lighting value (f32) [S1, unofficial].
*   `block`: Block ID for render pass filtering [S1, unofficial].
*   `atlas_offset`: Pre-computed atlas tile offset [S1, unofficial].
*   `two_sided`: Boolean flag for two-sided quads [S1, unofficial].

### Algorithm Steps
1.  **Retrieve Configuration**: For the current voxel at $P$ with block ID $B$, fetch its configuration object $C_B$.
2.  **Determine Shape**: Call $C_B$.shape() to get the geometric primitive. If the shape is `WholeBlock`, generate the standard cube vertices. If it is a custom shape (e.g., `Cross`, `Ramp`), generate the specific vertices defined for that shape.
3.  **Iterate Faces**: For each of the 6 faces of the voxel (or the faces defined by the shape):
    a.  Calculate neighbor position $P_{neighbor} = P + \mathbf{n}$.
    b.  Check if the neighbor is occupied.
    c.  If the neighbor is occupied, determine if the face should be culled based on $C_B$.cull_mode():
        *   If `Opaque`: Cull if neighbor is solid.
        *   If `TransparentMerged(T)`: Cull if neighbor is solid AND neighbor's block ID $B_{neigh}$ has $C_{B_{neigh}}$.transparent_group() == $C_B$.transparent_group().
        *   If `TransparentUnmerged`: Do not cull based on transparency; only cull if the neighbor is the same block type and the specific implementation allows (usually `TransparentUnmerged` implies no merging, so faces are kept unless the neighbor is identical and the algorithm explicitly handles identity culling, but typically it means "do not merge with different transparent types"). *Note: The source indicates `TransparentUnmerged` is used for leaves/chains, implying they do not merge with other leaves or other transparent blocks.* [S1, unofficial].
        *   If `Empty`: Do not generate any faces.
4.  **Generate Geometry**: If the face is visible, generate the vertices and indices for that face using the shape's vertex layout.
5.  **Apply Lighting**: Set the `light` value from $C_B$.light(face) for the generated vertices.
6.  **Assembly**: Add the vertices and indices to the chunk's mesh buffer.

### Pseudocode
```python
def generate_block_mesh(block_id, position, chunk):
    config = get_block_config(block_id)
    shape = config.shape()
    cull_mode = config.cull_mode()
    
    # Get transparent group for merging logic
    transparent_group = config.transparent_group() if cull_mode == CullMode.TransparentMerged else None
    
    for face in shape.faces():
        normal = face.normal
        neighbor_pos = position + normal
        neighbor_id = chunk.get_block(neighbor_pos)
        
        if neighbor_id is None:
            # Neighbor is air/empty, face is visible
            visible = True
        else:
            neighbor_config = get_block_config(neighbor_id)
            neighbor_cull = neighbor_config.cull_mode()
            
            if cull_mode == CullMode.Opaque:
                # Opaque blocks cull shared faces with any solid neighbor
                visible = not neighbor_config.is_solid()
            elif cull_mode == CullMode.TransparentMerged:
                # Merge only if same transparent group
                neighbor_group = neighbor_config.transparent_group()
                visible = (neighbor_group != transparent_group) or not neighbor_config.is_solid()
            elif cull_mode == CullMode.TransparentUnmerged:
                # Do not merge with any transparent neighbor
                visible = not neighbor_config.is_solid() or (neighbor_config.cull_mode() != CullMode.TransparentUnmerged and neighbor_id != block_id)
                # Note: Exact logic for Unmerged may vary; typically it means "never merge with other transparents"
                # Simplified: Visible if neighbor is not solid OR neighbor is not transparent
                # Based on [S1, unofficial], TransparentUnmerged is used for leaves/chains.
                # If neighbor is also TransparentUnmerged, do we merge? Usually no, to preserve detail.
                # Let's assume: Visible if neighbor is not solid AND (neighbor is not same type OR cull_mode is not merged)
                # Standard interpretation: TransparentUnmerged means "render all exposed faces, even if identical neighbor exists"
                visible = not neighbor_config.is_solid()
            else:
                visible = False
        
        if visible:
            vertices = shape.generate_face_vertices(face, position)
            lighting = config.light(face)
            chunk.add_vertices(vertices, lighting, block_id)
```

### Parameters and Typical Values
*   **TransparentGroup**: An integer or string identifier. E.g., Glass might have group `1`, Water `2`. Blocks with the same group merge [S1, unofficial].
*   **Light Values**: Floats from 0.0 to 14.0. E.g., Air=0, Cobblestone=1, Glass=2, Leaves=3, Cactus Top=11, Cactus Side=10 [S1, unofficial].

### Edge Cases and Pitfalls
*   **Fluid Shape**: Setting `FLUID_ENABLED` to true without implementing the fluid shape logic causes a debug assertion failure rather than silently drawing fluids as cubes [S1, unofficial].
*   **Threading**: In Unity3D implementations, vertex/index calculation can be done on a background thread, but the final `Mesh` object creation must be done on the main thread [S3, unofficial].
*   **Degenerate Input**: If a block ID is not registered in the configuration system, the behavior is undefined (likely crash or no rendering).

## Subtopics

### [Three-Valued Opacity Classification for Meshing](4414-three-valued-opacity-classification-for-meshing.md)
A classification system for block IDs into three mutually exclusive layers: 'opaque', 'water', and 'transparentSolid'. It solves the insufficiency of a single boolean 'transparent' flag by distinguishing between fluids (water) requiring bespoke shaders (ripple, refraction) and see-through solids (glass/leaves) requiring alpha blending. Unlike a boolean flag which collapses water and glass into one category, this model allows water to use a bespoke shader while glass/leaves use the ordinary block atlas with alpha blending.

### Ramp Shape Geometry
A shape representing a sloped block face, composed of a slope quad (2 triangles) and two side triangles (left and right). It is used for terrain or custom geometry. Instance creation iterates visible faces; if the face is Left, Right, Top, or Front, `drawSlope` is set to true and tints are assigned (`tints[0]` for Top/Front, `tints[1]` for Left, `tints[2]` for Right). If a specific tint is `Vector3.One`, it falls back to another face's tint. Back and Bottom faces use standard cube back/bottom shapes. Slope vertices are 6 vertices: (0,1,0), (0,0,1), (1,1,0), (1,1,0), (0,0,1), (1,0,1). Left triangle: (0,0,1), (0,1,0), (0,0,0). Right triangle: (1,0,0), (1,1,0), (1,0,1) [S2, unofficial].

### Fluid Surface Stitching
A mesh generation technique where fluid columns share a surface height field with neighbors, stitching surfaces when fluid IDs match. Two adjacent fluid blocks join their surfaces only when their `FluidInfo::id` (u8) values are equal [S1, unofficial].

### Geometry Builder Pattern
A design pattern using an interface `IGeometryBuilder` with a single function `BuildGeometry()` to control the type of geometry created for each non-empty voxel. This allows different geometry types (cubes, ramps, X-shapes) to be generated via polymorphism without large switch statements. During mesh creation, `BuildGeometry()` is called once for each non-empty block, passing a reference to the chunk object. The chunk stores vertices and indices in a linked list. After all blocks are processed, the data is placed into a Unity3D Mesh object on the main thread. Implementations include `BoxBuilder` (standard cubes), `MicroBlockBuilder`, and `WaterBuilder` (top faces only) [S3, unofficial].

## Operating characteristics
*   **Time Complexity**: $O(N)$ where $N$ is the number of voxels in the chunk. Each voxel is processed once, and the number of faces per voxel is constant (6 or fewer for partial shapes).
*   **Memory Complexity**: $O(V)$ where $V$ is the number of visible vertices. The configuration data is static per block type.
*   **Strengths**: Highly flexible; supports heterogeneous worlds with different block types, shapes, and transparency behaviors. Efficient culling reduces draw calls.
*   **Limitations**: Requires careful management of transparent groups to avoid visual artifacts. Custom shapes require additional vertex/index generation logic. Threading constraints in some engines (Unity) require careful synchronization.
*   **When to Use**: When the voxel world contains diverse block types with different visual properties (transparency, shape, lighting) and efficient mesh generation is required.
*   **When Not to Use**: For simple, uniform voxel worlds where a single global culling rule suffices, as the overhead of per-block configuration may be unnecessary.

## Background
The concept of block-specific configuration in voxel rendering evolved from early Minecraft-like games where blocks were simple cubes. As games introduced complex blocks (stairs, slabs, fluids, transparent materials), the need for per-block geometry and culling logic became apparent. The trait-based interface and geometry builder pattern were formalized in academic and open-source projects to manage this complexity without resorting to large switch statements. The specific implementations cited here come from open-source voxel meshing libraries and academic theses on procedural voxel generation.
