# Voxel Block Shape & Culling Configuration

Also called: Block trait interface, Shape enum system

## Overview
Voxel Block Shape & Culling Configuration is a trait-based system that defines block geometry, transparency culling modes, and lighting properties per block type [S1, unofficial]. It solves the problem of heterogeneous block types (opaque, transparent, fluid, complex shapes) requiring different mesh generation and rendering behaviors by centralizing these rules in a single interface [S1, unofficial]. Unlike generic meshing algorithms that assume uniform block geometry, this method allows per-block customization of shape (e.g., ramps, fluids) and culling strategy (e.g., merging transparent faces) [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A voxel grid containing block IDs and metadata (e.g., fluid IDs).
*   **Output:** A set of mesh primitives (vertices, indices) for each block type, filtered by culling rules.

**Data Structures:**
1.  **Block Trait Interface:** Defines methods for `shape()`, `cull_mode()`, and `light()` [S1, unofficial].
2.  **Shape Enum:** Represents the geometric primitive for a block face (e.g., `WholeBlock`, `Cross`, `Ramp`) [S1, unofficial].
3.  **CullMode Enum:** Determines how faces are culled based on neighbor occupancy and transparency [S1, unofficial].
    *   `Empty`: No faces generated.
    *   `Opaque`: Standard internal face culling.
    *   `TransparentMerged(T)`: Culls shared faces between two transparent blocks if their `TransparentGroup` values match [S1, unofficial].
    *   `TransparentUnmerged`: No merging of transparent faces.
4.  **Vertex Structure:** Contains position, UV, normal, ambient occlusion (AO), smooth light, block ID, atlas offset, and two-sided flag [S1, unofficial].

**Steps:**
1.  **Iterate Voxel Grid:** For each non-empty voxel at position $P$ with block type $B$:
    a.  Retrieve the block trait for $B$.
    b.  Call `shape()` to determine the geometric primitive.
    c.  Call `cull_mode()` to determine culling behavior.
    d.  For each face direction $d \in \{\pm X, \pm Y, \pm Z\}$:
        i.  Check neighbor occupancy at $P + d$.
        ii. If the neighbor is empty or the face is visible according to `cull_mode()`, generate geometry.
        iii. For `TransparentMerged(T)`, check if the neighbor has the same `TransparentGroup` $T$. If so, cull the shared face [S1, unofficial].
        iv. Generate vertices and indices based on the `shape()` result.
        v.  Apply lighting values from `light()` [S1, unofficial].
2.  **Assemble Mesh:** Collect all generated vertices and indices into a chunk mesh.

**Formulas:**
*   **Culling Condition for TransparentMerged:**
    $$ \text{Cull}(P, d) = \text{IsTransparent}(B) \land \text{IsTransparent}(B_{neighbor}) \land (T_B == T_{neighbor}) $$
    Where $T_B$ is the `TransparentGroup` of block $B$ [S1, unofficial].

**Parameters:**
*   **FLUID_ENABLED:** Boolean flag to enable fluid meshing [S1, unofficial].
*   **TransparentGroup:** Integer or enum value for grouping transparent blocks [S1, unofficial].

**Edge Cases and Pitfalls:**
*   Setting `FLUID_ENABLED` to true without implementing fluid shape causes a debug assertion failure rather than silently drawing fluids as cubes [S1, unofficial].
*   Unity3D functions must be called on the main thread; mesh calculation can be done on a background thread, but final mesh creation must be moved to the main thread [S3, unofficial].

**Pseudocode:**
```python
def generate_chunk_mesh(chunk):
    vertices = []
    indices = []
    
    for block_id, block_pos in chunk.non_empty_blocks():
        block_trait = get_block_trait(block_id)
        shape = block_trait.shape()
        cull_mode = block_trait.cull_mode()
        light_val = block_trait.light()
        
        for face_dir in [POS_X, NEG_X, POS_Y, NEG_Y, POS_Z, NEG_Z]:
            neighbor_pos = block_pos + face_dir
            neighbor_id = chunk.get_block(neighbor_pos)
            
            if is_face_visible(block_id, neighbor_id, face_dir, cull_mode):
                # Generate geometry based on shape
                if shape == Shape.WHOLE_BLOCK:
                    verts, idxs = generate_cube_face(block_pos, face_dir, light_val)
                elif shape == Shape.RAMP:
                    verts, idxs = generate_ramp_face(block_pos, face_dir, light_val)
                elif shape == Shape.FLUID:
                    verts, idxs = generate_fluid_face(block_pos, face_dir, light_val)
                else:
                    # Handle other shapes or default to cube
                    verts, idxs = generate_cube_face(block_pos, face_dir, light_val)
                
                vertices.extend(verts)
                indices.extend(idxs)
    
    return vertices, indices

def is_face_visible(block_id, neighbor_id, face_dir, cull_mode):
    if cull_mode == CullMode.Empty:
        return False
    if cull_mode == CullMode.Opaque:
        return neighbor_id is EMPTY
    if cull_mode == CullMode.TransparentMerged:
        if neighbor_id is EMPTY:
            return True
        if is_transparent(block_id) and is_transparent(neighbor_id):
            if get_transparent_group(block_id) == get_transparent_group(neighbor_id):
                return False
        return True
    if cull_mode == CullMode.TransparentUnmerged:
        return neighbor_id is EMPTY or not is_transparent(neighbor_id)
    return True
```

## Subtopics

### [Three-Valued Opacity Classification for Meshing](4414-three-valued-opacity-classification-for-meshing.md)
A classification system for block IDs into three mutually exclusive layers ('opaque', 'water', 'transparentSolid') to determine rendering material and buffer assignment. It solves the insufficiency of a single boolean 'transparent' flag by distinguishing between fluids (water) requiring bespoke shaders and see-through solids (glass/leaves) requiring alpha blending. Unlike a boolean transparent flag which collapses water and glass/leaves into one category, this three-valued model allows water to use a bespoke shader (ripple, refraction) while glass/leaves use the ordinary block atlas with alpha blending.

### Ramp Shape Geometry
A shape representing a sloped block face, composed of a slope quad (2 triangles) and two side triangles (left and right) [S2, unofficial]. Instance creation involves iterating visible faces and setting `drawSlope = true` for Left, Right, Top, or Front faces, assigning tints accordingly [S2, unofficial]. Slope vertices are defined as (0,1,0), (0,0,1), (1,1,0), (1,1,0), (0,0,1), (1,0,1) with corresponding UVs [S2, unofficial]. Left triangle vertices are (0,0,1), (0,1,0), (0,0,0) and Right triangle vertices are (1,0,0), (1,1,0), (1,0,1) [S2, unofficial].

### Fluid Surface Stitching
A mesh generation technique where fluid columns share a surface height field with neighbors, stitching surfaces when fluid IDs match [S1, unofficial]. Two adjacent fluid blocks join their surfaces only when their `FluidInfo::id` values match [S1, unofficial].

### Geometry Builder Pattern
A design pattern using an interface to control the type of geometry created for each non-empty voxel, allowing different geometry types (cubes, ramps, X-shapes) to be generated via polymorphism without large switch statements [S3, unofficial]. The `IGeometryBuilder` interface contains a single function `BuildGeometry()` [S3, unofficial]. During mesh creation, `BuildGeometry()` is called once for each non-empty block, passing a reference to the chunk object to add vertices and indices to a linked list [S3, unofficial]. After all blocks are processed, the data is placed into a Unity3D Mesh object on the main thread [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of voxels in the chunk, as each voxel is processed once [S1, unofficial].
*   **Memory Complexity:** $O(V + I)$ where $V$ is the number of vertices and $I$ is the number of indices generated [S1, unofficial].
*   **Strengths:** Flexible support for diverse block types and shapes; efficient culling reduces draw calls; modular design via builder pattern [S3, unofficial].
*   **Limitations:** Requires careful implementation of shape generators to avoid assertion failures; Unity3D-specific threading constraints [S3, unofficial].
*   **When to Use:** When rendering voxel worlds with heterogeneous block types (e.g., Minecraft-like games) requiring different visual treatments and culling behaviors [S1, unofficial].
*   **When Not to Use:** For simple, uniform voxel grids where all blocks share the same geometry and culling rules [S1, unofficial].

## Background
Originating from implementations like `finnbear/voxmesh` and academic projects such as "Procedural Generation of Voxel Worlds with Castles," this method addresses the need for flexible voxel meshing [S1, unofficial][S3, unofficial]. It evolved from simple cube-based meshing to support complex shapes and transparent materials, reflecting the requirements of modern voxel games [S3, unofficial].
