# Voxel Block Shape & Culling Configuration

Also called: Block trait interface, Shape enum system

## Overview
Voxel Block Shape & Culling Configuration is a trait-based system that defines block geometry, transparency culling modes, and lighting properties per block type. It solves the problem of heterogeneous block behavior in voxel worlds by decoupling mesh generation logic from the core culling algorithm. Unlike sibling methods that assume uniform block geometry or simple boolean transparency, this approach allows distinct culling strategies (e.g., merging transparent faces vs. keeping them separate) and complex shapes (e.g., ramps, fluids) to be configured via a single interface [S1, S3, unofficial].

## How it works
The system relies on a trait or interface that every block type implements. This interface exposes methods for determining the block's shape, its culling mode, and its lighting value.

### Inputs and Outputs
*   **Input**: The block type identifier (e.g., `MyBlock::Glass`) and the face normal being evaluated.
*   **Output**: A configuration object containing:
    *   `Shape`: The geometric primitive to generate (e.g., `WholeBlock`, `Cross`, `Ramp`).
    *   `CullMode`: The strategy for handling neighbor occlusion and transparency.
    *   `Light`: The base lighting value for the block.

### Data Structures

#### Block Trait Interface
The core configuration is defined by an interface (or trait) with the following methods:

```python
class BlockConfig:
    def shape(self, face: Face) -> Shape:
        """Returns the geometry shape for a specific face."""
        pass

    def cull_mode(self) -> CullMode:
        """Returns the culling strategy for this block type."""
        pass

    def light(self, face: Face) -> float:
        """Returns the lighting value for a specific face."""
        pass
```

#### CullMode Enum
The `CullMode` enum dictates how faces are culled based on neighbor occupancy and transparency:

*   `Empty`: The block is air; no faces are generated.
*   `Opaque`: Standard culling. Faces are generated only if the neighbor is empty.
*   `TransparentMerged(T)`: Faces are merged with neighbors if they share the same `TransparentGroup` ID `T`. Shared faces between two transparent blocks with equal IDs are culled. This mode does not support `PartialEq` for greedy meshing in some implementations, requiring careful handling of adjacency [S1, unofficial].
*   `TransparentUnmerged`: Faces are never merged with neighbors, even if both are transparent. This is used for blocks like leaves or glass where internal faces should remain visible or distinct.

#### Shape Enum
The `Shape` enum defines the geometry:

*   `WholeBlock`: A standard 6-faced cube.
*   `Cross(CrossInfo)`: A cross-shaped geometry, often used for items like chains or rails. Defined by an `AlignedFace` (e.g., `PosZ`) and a `stretch` value.
*   `Ramp`: A sloped block face (see Subtopics).
*   `Fluid`: A special shape for fluid surfaces (see Subtopics).

### Numbered Steps

1.  **Block Registration**: For each block type in the world, instantiate its configuration object implementing `BlockConfig`.
2.  **Mesh Generation Loop**: Iterate through all voxels in a chunk.
3.  **Face Evaluation**: For each voxel, iterate through its 6 faces.
4.  **Configuration Lookup**: Retrieve the `BlockConfig` for the current voxel's type.
5.  **Culling Decision**:
    *   Call `cull_mode()`.
    *   If `Empty`, skip.
    *   If `Opaque`, check if the neighbor in the direction of the face is empty. If not, skip.
    *   If `TransparentMerged(T)`, check if the neighbor is transparent and has the same `T`. If so, skip (merge).
    *   If `TransparentUnmerged`, generate the face regardless of neighbor transparency (unless the neighbor is empty, depending on specific implementation details of "unmerged" vs "opaque" for air).
6.  **Shape Generation**:
    *   Call `shape(face)` to get the geometry type.
    *   If `WholeBlock`, generate the standard cube face vertices.
    *   If `Cross`, generate the cross geometry using `CrossInfo`.
    *   If `Ramp` or `Fluid`, use specialized geometry builders (see Subtopics).
7.  **Lighting Application**:
    *   Call `light(face)` to get the lighting value.
    *   Apply this value to the generated vertices.
8.  **Vertex/Index Buffer Population**: Add the generated vertices and indices to the chunk's buffer.

### Formulas

*   **Neighbor Position**: $P_{neighbor} = P + N$, where $P$ is the current voxel position and $N$ is the face normal vector [S1, S2, unofficial].
*   **Transparent Merge Condition**: A face is culled if:
    $$ \text{Block}(P_{neighbor}).\text{cull\_mode}() == \text{TransparentMerged}(T) \land \text{Block}(P).\text{cull\_mode}() == \text{TransparentMerged}(T) \land T_{neighbor} == T_{self} $$
    where $T$ is the transparent group identifier [S1, unofficial].

### Parameters

*   **FLUID_ENABLED**: A boolean flag. If set to `true` without implementing the fluid shape logic, it causes a debug assertion failure rather than silently drawing fluids as cubes [S1, unofficial].
*   **TransparentGroup (T)**: An identifier (e.g., `()`, `u8`) used to group transparent blocks for merging. For example, all water blocks might share `T=0`, while all glass blocks share `T=1`.

### Edge Cases and Pitfalls

*   **Fluid Shape Implementation**: Setting `FLUID_ENABLED` to `true` without implementing the corresponding fluid shape geometry causes a debug assertion failure. It does not fall back to a cube [S1, unofficial].
*   **Greedy Meshing with TransparentMerged**: The `TransparentMerged` mode may not support `PartialEq` for greedy meshing in some implementations, requiring manual handling of adjacency checks [S1, unofficial].
*   **Threading Constraints**: In Unity3D implementations, vertex and index calculation can be done on a background thread, but the final `Mesh` object creation must be done on the main thread [S3, unofficial].

### Pseudocode

```python
def generate_chunk_mesh(chunk: Chunk):
    """
    Generates the mesh for a chunk using block-specific shape and culling configuration.
    """
    vertices = []
    indices = []
    
    for x in range(chunk.width):
        for y in range(chunk.height):
            for z in range(chunk.depth):
                block_type = chunk.get_block(x, y, z)
                config = block_type.get_config()
                
                # Skip empty blocks
                if config.cull_mode() == CullMode.Empty:
                    continue
                
                for face in Face.all():
                    neighbor_pos = (x + face.normal.x, y + face.normal.y, z + face.normal.z)
                    neighbor_type = chunk.get_block_at(neighbor_pos)
                    
                    # Culling Logic
                    if should_cull_face(config, neighbor_type, face):
                        continue
                    
                    # Shape Generation
                    shape = config.shape(face)
                    
                    if shape == Shape.WholeBlock:
                        verts, idxs = generate_cube_face(face, config.light(face))
                    elif shape == Shape.Cross:
                        cross_info = config.shape_info(face)
                        verts, idxs = generate_cross_face(face, cross_info, config.light(face))
                    elif shape == Shape.Ramp:
                        verts, idxs = generate_ramp_face(face, config.light(face))
                    elif shape == Shape.Fluid:
                        fluid_id = chunk.get_fluid_id(x, y, z)
                        verts, idxs = generate_fluid_face(face, fluid_id, config.light(face))
                    else:
                        continue # Unknown shape
                    
                    # Add to buffers
                    vertices.extend(verts)
                    indices.extend([i + len(vertices) - len(verts) for i in idxs])
    
    return Mesh(vertices, indices)

def should_cull_face(config: BlockConfig, neighbor_type: BlockType, face: Face) -> bool:
    """
    Determines if a face should be culled based on culling mode.
    """
    neighbor_config = neighbor_type.get_config()
    cull_mode = config.cull_mode()
    
    if cull_mode == CullMode.Opaque:
        # Cull if neighbor is not empty
        return neighbor_config.cull_mode() != CullMode.Empty
    
    elif cull_mode == CullMode.TransparentMerged:
        # Cull if neighbor is also TransparentMerged with same group
        if neighbor_config.cull_mode() == CullMode.TransparentMerged:
            # Assuming TransparentGroup is stored in the config or block type
            # This is a simplified check; actual implementation may require
            # accessing a specific group ID field
            if config.transparent_group() == neighbor_config.transparent_group():
                return True
        return False
    
    elif cull_mode == CullMode.TransparentUnmerged:
        # Never cull based on neighbor transparency, only if neighbor is empty
        return neighbor_config.cull_mode() == CullMode.Empty
    
    return False
```

## Subtopics

### [Three-Valued Opacity Classification for Meshing](4414-three-valued-opacity-classification-for-meshing.md)
A classification system for block IDs into three mutually exclusive layers ('opaque', 'water', 'transparentSolid') to determine rendering material and buffer assignment. It solves the insufficiency of a single boolean 'transparent' flag by distinguishing between fluids (water) requiring bespoke shaders and see-through solids (glass/leaves) requiring alpha blending. Unlike a boolean transparent flag which collapses water and glass/leaves into one category, this three-valued model allows water to use a bespoke shader (ripple, refraction) while glass/leaves use the ordinary block atlas with alpha blending.

### [VoxelBlockyTypeLibrary with Attributes](12820-voxelblockytypelibrary-with-attributes.md)
`VoxelBlockyTypeLibrary` is a model management system for blocky voxel terrains that organizes meshes by logical "block types" with configurable state attributes, rather than storing individual model references directly. It solves the problem of managing complex block behaviors (e.g., orientation, powered state, connections) by automatically generating unique numerical IDs for every combination of attribute values, similar to Minecraft's block state system. It differs from the standard `VoxelBlockyLibrary` by decoupling model identity from manual ID assignment, using a combinatorial attribute system instead.

### Ramp Shape Geometry
A shape representing a sloped block face, composed of a slope quad (2 triangles) and two side triangles (left and right) [S2, unofficial]. Instance creation involves iterating visible faces. If the face is Left, Right, Top, or Front, `drawSlope` is set to `true` and tint is assigned to `tints[0]` (Top/Front), `tints[1]` (Left), or `tints[2]` (Right). If a specific tint is `Vector3.One`, it falls back to another face's tint. Instances for slope, left triangle, and right triangle are added using respective shape IDs and tints. If the face is Back or Bottom, an instance is added using `cubeBackFaceShapeID` or `cubeBottomFaceShapeID` [S2, unofficial]. The slope vertices are: (0,1,0) with UV[0], (0,0,1) with UV[1], (1,1,0) with UV[2], (1,1,0) with UV[3], (0,0,1) with UV[4], (1,0,1) with UV[5]. The left triangle vertices are: (0,0,1) with UV[0], (0,1,0) with UV[1], (0,0,0) with UV[2]. The right triangle vertices are: (1,0,0) with UV[0], (1,1,0) with UV[1], (1,0,1) with UV[2] [S2, unofficial].

### Fluid Surface Stitching
A mesh generation technique where fluid columns share a surface height field with neighbors, stitching surfaces when fluid IDs match [S1, unofficial]. Two adjacent fluid blocks join their surfaces only when their `FluidInfo::id` (u8) values match [S1, unofficial].

### Geometry Builder Pattern
A design pattern using an interface to control the type of geometry created for each non-empty voxel, allowing different geometry types (cubes, ramps, X-shapes) to be generated via polymorphism without large switch statements [S3, unofficial]. During mesh creation, `BuildGeometry()` is called once for each non-empty block. A reference to the chunk object is passed to `BuildGeometry()`, which uses this reference to add vertices and indices to the chunk's linked list. After `BuildGeometry()` has been called on every block for the chunk, the vertex and index data is placed into a Unity3D Mesh object on the main thread [S3, unofficial]. The `IGeometryBuilder` interface contains a single function: `BuildGeometry()` [S3, unofficial]. A pitfall is that Unity3D functions must be called on the main thread; while vertex/index calculation is done on a background thread, the final Mesh object creation must be moved to the main thread [S3, unofficial].

## Operating characteristics
*   **Time Complexity**: $O(V \cdot F \cdot S)$, where $V$ is the number of voxels, $F$ is the number of faces per voxel (6), and $S$ is the cost of shape generation. The trait lookup is $O(1)$.
*   **Memory Complexity**: $O(B)$, where $B$ is the number of block types, for storing the configuration objects. The mesh memory is proportional to the number of visible faces.
*   **Strengths**: Highly flexible; supports complex shapes and varied culling strategies without modifying the core culling algorithm.
*   **Limitations**: Increased overhead per voxel due to function calls and trait lookups. Requires careful implementation of threading constraints in certain engines (e.g., Unity3D) [S3, unofficial].
*   **When to Use**: When the voxel world contains heterogeneous block types with different geometric and rendering requirements.
*   **When Not to Use**: For simple, uniform voxel worlds where a single culling mode and shape suffice, as the overhead may not be justified.

## Background
The concept of block-specific configuration in voxel rendering has evolved from simple boolean flags to complex trait-based systems. Early implementations often used hardcoded switch statements to handle different block types, leading to code bloat and maintenance issues [S3, unofficial]. The introduction of trait-based interfaces (e.g., in Rust's `voxmesh`) and geometry builder patterns (e.g., in Unity3D projects) allowed for more modular and extensible voxel rendering systems [S1, S3, unofficial]. The three-valued opacity classification and fluid surface stitching techniques address specific rendering challenges in games like Minecraft, where different materials require different shaders and visual treatments [S1, unofficial].
