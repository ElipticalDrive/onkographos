# Voxel Block Shape & Culling Configuration

Also called: Block trait interface, Shape enum system

## Overview
Voxel Block Shape & Culling Configuration is a trait-based system that defines the geometry, transparency culling behavior, and lighting properties for individual block types within a voxel mesh generator. It solves the problem of heterogeneous block rendering by allowing each block ID to specify its own shape (e.g., cube, ramp, fluid) and culling mode (e.g., opaque, transparent merged, transparent unmerged) [S1, unofficial]. Unlike generic meshing algorithms that treat all voxels as identical cubes, this method decouples block identity from mesh generation logic, enabling complex shapes and varied transparency handling without large switch statements [S3, unofficial]. It builds on [Face Culling and Visibility Optimization](3861-face-culling-and-visibility-optimization.md) by providing the per-block parameters that determine how the neighbor lookup results are interpreted.

## How it works
The system operates by associating a configuration object (often a trait or interface implementation) with each block type. This configuration dictates the vertex layout, the culling mode, and the lighting value for any face generated by that block.

### Inputs and Outputs
- **Input:** The block type ID (e.g., `MyBlock::Glass`) and the face direction being evaluated (e.g., `AlignedFace::PosZ`).
- **Output:** A configuration struct or object containing:
    - `Shape`: The geometric primitive to generate (e.g., `WholeBlock`, `Cross`, `Ramp`).
    - `CullMode`: The transparency culling strategy (e.g., `Opaque`, `TransparentMerged`, `TransparentUnmerged`).
    - `Light`: The lighting intensity value associated with the block/face.

### Data Structures
The core data structure is a trait or interface that exposes methods for shape, culling, and lighting. In Rust-like pseudocode (from [S1, unofficial]):

> **Unverified code.** The code below did not pass a test run against a reference implementation, or no test fits it, so it may contain errors.

```rust
trait BlockConfig {
    fn shape(&self, face: Face) -> Shape;
    fn cull_mode(&self) -> CullMode;
    fn light(&self, face: Face) -> u8;
}
```

The `Shape` enum defines the geometry:
- `WholeBlock`: A standard 1x1x1 cube.
- `Cross(CrossInfo)`: A cross-shaped block (e.g., chains, rails) defined by an aligned face and stretch parameter.
- `Ramp`: A sloped block (see Subtopics).
- `Fluid`: A fluid surface (see Subtopics).

The `CullMode` enum defines visibility:
- `Empty`: The block is air; no faces generated.
- `Opaque`: Standard culling; face generated if neighbor is empty/transparent.
- `TransparentMerged(T)`: Shared faces between two transparent blocks are culled if their `TransparentGroup` values are equal.
- `TransparentUnmerged`: Faces are never merged with neighbors; always generated if neighbor is opaque.

### Numbered Steps
1. **Configuration Lookup:** For each non-empty voxel at position $P$ with block type $B$, retrieve the configuration object $C_B$.
2. **Face Iteration:** Iterate over the 6 face directions $d \in \{\pm X, \pm Y, \pm Z\}$.
3. **Neighbor Check:** Determine the neighbor block type $B_{neighbor}$ at $P + d$.
4. **Culling Decision:**
   - If $B_{neighbor}$ is empty, the face is potentially visible.
   - If $B_{neighbor}$ is solid/opaque, the face is internal and culled.
   - If $B_{neighbor}$ is transparent, apply the culling mode from $C_B$:
     - If `CullMode` is `TransparentMerged(T)`, check if $B_{neighbor}$ has the same `TransparentGroup` $T$. If yes, cull the face. If no, generate the face.
     - If `CullMode` is `TransparentUnmerged`, generate the face.
     - If `CullMode` is `Opaque`, generate the face (treat transparent neighbors as opaque for culling purposes, or rely on the neighbor's own culling mode).
5. **Geometry Generation:** Call $C_B$.shape(face) to determine the vertex layout. Generate vertices and indices according to the shape definition.
6. **Lighting Assignment:** Call $C_B$.light(face) to assign the lighting value to the generated vertices.
7. **Mesh Assembly:** Add the generated vertices and indices to the chunk's mesh buffer.

### Formulas
- **Culling Condition for TransparentMerged:**
  $$
  \text{CullFace} = \begin{cases} 
  \text{True} & \text{if } \text{CullMode}(B) = \text{TransparentMerged}(T) \land \text{Group}(B_{neighbor}) = T \\
  \text{False} & \text{otherwise}
  \end{cases}
  $$
  Where $\text{Group}(B)$ is the transparency group ID associated with block $B$.

- **Lighting Value:**
  The lighting value $L$ is a scalar (e.g., $0.0$ to $14.0$) assigned per vertex. It is retrieved via $L = C_B.\text{light}(face)$.

### Parameters
- **TransparentGroup (T):** An integer or enum value identifying the transparency group. Blocks with the same $T$ are merged. Typical values: $0$ for air, $1$ for glass, $2$ for water.
- **Light Value:** A floating-point or integer value representing light intensity. Typical values: $0.0$ for air, $1.0$ for stone, $14.0$ for lamps.
- **Fluid ID:** A unique identifier for fluid types. Two adjacent fluid blocks join their surfaces only if their IDs match [S1, unofficial].

### Edge Cases and Pitfalls
- **Fluid Shape Implementation:** Setting `FLUID_ENABLED` to true without implementing the fluid shape logic causes a debug assertion failure rather than silently drawing fluids as cubes [S1, unofficial].
- **Thread Safety:** When using a Geometry Builder pattern, vertex/index calculation can be done on a background thread, but the final mesh object creation must be moved to the main thread to avoid runtime errors [S3, unofficial].
- **Tint Fallback:** For ramp shapes, if a specific tint is `Vector3.One`, fallback to another face's tint to avoid visual artifacts [S2, unofficial].

### Pseudocode
> **Unverified code.** The code below did not pass a test run against a reference implementation, or no test fits it, so it may contain errors.

```python
def generate_block_mesh(block_type, position, neighbor_lookup, config_table):
    """
    Generate mesh for a single block type using its configuration.
    
    Args:
        block_type: ID of the block (e.g., 'Glass', 'Stone')
        position: (x, y, z) coordinates of the block
        neighbor_lookup: Function that returns block_type at given position
        config_table: Dictionary mapping block_type to BlockConfig object
    
    Returns:
        List of vertices and indices for the block's visible faces
    """
    config = config_table[block_type]
    vertices = []
    indices = []
    
    # Define the 6 face directions
    faces = [
        ('+X', (1, 0, 0)), ('-X', (-1, 0, 0)),
        ('+Y', (0, 1, 0)), ('-Y', (0, -1, 0)),
        ('+Z', (0, 0, 1)), ('-Z', (0, 0, -1))
    ]
    
    for face_name, direction in faces:
        neighbor_pos = (position[0] + direction[0], 
                        position[1] + direction[1], 
                        position[2] + direction[2])
        neighbor_type = neighbor_lookup(neighbor_pos)
        
        # Determine if face is visible
        if neighbor_type == 'Air':
            is_visible = True
        elif neighbor_type == 'Solid':
            is_visible = False
        else:
            # Neighbor is transparent
            cull_mode = config.cull_mode()
            if cull_mode == 'TransparentMerged':
                # Check if neighbor has same transparency group
                if config.transparent_group == get_transparent_group(neighbor_type):
                    is_visible = False
                else:
                    is_visible = True
            elif cull_mode == 'TransparentUnmerged':
                is_visible = True
            elif cull_mode == 'Opaque':
                is_visible = True
            else:
                is_visible = False
        
        if is_visible:
            # Get shape and lighting from config
            shape = config.shape(face_name)
            light_value = config.light(face_name)
            
            # Generate vertices and indices based on shape
            shape_vertices, shape_indices = generate_shape_vertices(shape, position, face_name)
            
            # Apply lighting and other attributes
            for v in shape_vertices:
                v.light = light_value
                v.block = block_type
                # Add other attributes like UV, normal, AO, etc.
                vertices.append(v)
            
            # Offset indices by current vertex count
            offset = len(vertices) - len(shape_vertices)
            indices.extend([i + offset for i in shape_indices])
    
    return vertices, indices
```

## Subtopics

### [Three-Valued Opacity Classification for Meshing](4414-three-valued-opacity-classification-for-meshing.md)
A classification system for block IDs into three mutually exclusive layers ('opaque', 'water', 'transparentSolid') to determine rendering material and buffer assignment. It solves the insufficiency of a single boolean 'transparent' flag by distinguishing between fluids (water) requiring bespoke shaders and see-through solids (glass/leaves) requiring alpha blending. Unlike a boolean transparent flag which collapses water and glass/leaves into one category, this three-valued model allows water to use a bespoke shader (ripple, refraction) while glass/leaves use the ordinary block atlas with alpha blending.

### Ramp Shape Geometry
A shape representing a sloped block face, composed of a slope quad (2 triangles) and two side triangles (left and right) [S2, unofficial]. Instance creation involves iterating visible faces; if the face is Left, Right, Top, or Front, `drawSlope` is set to true and tint is assigned based on face direction (Top/Front to `tints[0]`, Left to `tints[1]`, Right to `tints[2]`). If a specific tint is `Vector3.One`, fallback to another face's tint. Slope vertices are defined as: (0,1,0) with UV[0], (0,0,1) with UV[1], (1,1,0) with UV[2], (1,1,0) with UV[3], (0,0,1) with UV[4], (1,0,1) with UV[5]. Left triangle vertices: (0,0,1) with UV[0], (0,1,0) with UV[1], (0,0,0) with UV[2]. Right triangle vertices: (1,0,0) with UV[0], (1,1,0) with UV[1], (1,0,1) with UV[2] [S2, unofficial].

### Fluid Surface Stitching
A mesh generation technique where fluid columns share a surface height field with neighbors, stitching surfaces when fluid IDs match [S1, unofficial]. Two adjacent fluid blocks join their surfaces only when their `FluidInfo::id` (u8) values are equal [S1, unofficial].

### Geometry Builder Pattern
A design pattern using an interface to control the type of geometry created for each non-empty voxel, allowing different geometry types (cubes, ramps, X-shapes) to be generated via polymorphism without large switch statements [S3, unofficial]. The interface `IGeometryBuilder` contains a single function `BuildGeometry()`. During mesh creation, `BuildGeometry()` is called once for each non-empty block, passing a reference to the chunk object. The chunk stores vertices and indices in a linked list. After all blocks are processed, the data is placed into a Unity3D Mesh object on the main thread [S3, unofficial]. Pitfall: Unity3D functions must be called on the main thread; background thread calculations must be synchronized [S3, unofficial].

## Operating characteristics
- **Time Complexity:** $O(N)$ where $N$ is the number of non-empty voxels in the chunk. Each voxel is processed once, and the number of faces generated is bounded by $6N$.
- **Memory Complexity:** $O(N)$ for storing vertices and indices. The size depends on the shape complexity (e.g., ramps have more vertices than cubes).
- **Performance:** The trait-based approach allows for efficient dispatch via vtables or switch statements, avoiding large if-else chains. However, the overhead of virtual function calls may be non-negligible in tight loops.
- **Strengths:** Flexibility in supporting diverse block shapes and transparency behaviors. Decoupling of block configuration from mesh generation logic improves maintainability.
- **Limitations:** Increased complexity in configuration management. Potential for runtime errors if configurations are inconsistent (e.g., missing fluid shape implementation).
- **When to Use:** When the voxel world contains a wide variety of block types with different geometries and transparency requirements.
- **When Not to Use:** For simple voxel worlds with only a few block types, a simpler switch-based approach may be more efficient.

## Background
The concept of block-specific configuration in voxel rendering originated from the need to support complex block types in games like Minecraft, where blocks such as rails, chains, and fluids require non-cube geometries and specific transparency handling [S3, unofficial]. The trait-based interface approach was popularized in modern voxel engines to provide a clean, extensible way to manage these variations [S1, unofficial]. The Geometry Builder pattern was introduced in academic projects to separate mesh generation logic from rendering engine specifics, particularly in Unity3D environments [S3, unofficial].
