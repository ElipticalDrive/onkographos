# Voxel Block Shape & Culling Configuration

Also called: Block trait interface, Shape enum system

## Overview
Voxel Block Shape & Culling Configuration is a trait-based system that defines the geometry, transparency culling behavior, and lighting properties for individual block types within a voxel mesh generator [S1, unofficial]. It solves the problem of hard-coded block logic by decoupling block identity from mesh generation rules, allowing different block types to specify their own shape (e.g., cube, ramp, fluid) and how they interact with neighbors during face culling [S1, unofficial]. Unlike generic meshing algorithms that treat all voxels as opaque cubes, this configuration allows fine-grained control over visibility optimization, such as merging transparent faces or excluding bottom faces for specific materials [S1, unofficial].

## How it works
The system operates by associating a set of configuration rules with each block type. These rules determine the geometric primitives generated, the culling mode applied to faces, and the lighting values used for shading.

### Inputs and Outputs
*   **Input:** A block identifier (e.g., `MyBlock::Glass`) and the face normal being evaluated.
*   **Output:** A `Shape` enum value defining the geometry, a `CullMode` enum defining visibility logic, and a `light` value for shading.

### Data Structures

#### Block Trait Interface
The core configuration is defined via a trait (interface) that each block type implements. The trait exposes three primary methods: `shape()`, `cull_mode()`, and `light()` [S1, unofficial].

> **Unverified code.** The code below did not pass a test run against a reference implementation, or no test fits it, so it may contain errors.

```rust
// Conceptual trait definition based on [S1, unofficial]
trait BlockConfig {
    fn shape(&self, face: Face) -> Shape;
    fn cull_mode(&self) -> CullMode;
    fn light(&self, face: Face) -> u8;
}
```

#### Shape Enum
The `Shape` enum defines the geometric primitives generated for a block face. Common variants include:
*   `WholeBlock`: A standard 1x1x1 cube face.
*   `Cross(CrossInfo)`: A cross-shaped geometry, often used for items like chains or rails, defined by an `AlignedFace` and a `stretch` value [S1, unofficial].
*   `Ramp`: A sloped geometry (see Subtopics).

#### CullMode Enum
The `CullMode` enum determines how the culling logic from the parent article is applied to a specific block type [S1, unofficial].
*   `Empty`: The block is air; no faces are generated.
*   `Opaque`: Standard opaque culling. A face is visible if the neighbor is empty.
*   `TransparentMerged(T)`: Used for transparent blocks that should merge with identical neighbors. A face is culled if the neighbor is transparent AND has the same `TransparentGroup` value `T` [S1, unofficial].
*   `TransparentUnmerged`: Used for transparent blocks that do not merge. A face is visible if the neighbor is empty OR transparent, regardless of group identity.

#### Vertex Layout
Vertices generated by these configurations typically include position, UV coordinates, normal, ambient occlusion (AO), smooth light, block ID, atlas offset, and a two-sided flag [S1, unofficial].

### Numbered Steps
1.  **Identify Block Type:** For each non-empty voxel in the chunk, retrieve its block type.
2.  **Retrieve Configuration:** Call the block's `cull_mode()` and `shape()` methods [S1, unofficial].
3.  **Evaluate Culling:**
    *   If `CullMode::Empty`, skip the block.
    *   If `CullMode::Opaque`, apply standard neighbor check: visible if neighbor is empty.
    *   If `CullMode::TransparentMerged(T)`, visible if neighbor is empty OR (neighbor is transparent AND neighbor's TransparentGroup != T) [S1, unofficial].
    *   If `CullMode::TransparentUnmerged`, visible if neighbor is empty OR neighbor is transparent.
4.  **Generate Geometry:**
    *   If the face is visible, call `shape(face)` to determine the primitive.
    *   For `WholeBlock`, generate a standard quad.
    *   For `Cross`, generate the cross geometry using the `stretch` parameter.
    *   For `Ramp` (see Subtopics), generate the slope quad and side triangles.
5.  **Assign Lighting:** Call `light(face)` to get the lighting value for the generated vertices [S1, unofficial].
6.  **Add to Mesh:** Add the generated vertices and indices to the chunk's mesh buffer.

### Formulas
*   **Transparent Merged Culling:**
    $$ \text{Visible} = \neg \text{Occupied}(P_{neighbor}) \lor (\text{Transparent}(P_{neighbor}) \land \text{Group}(P_{neighbor}) \neq T) $$
    Where $T$ is the transparent group ID associated with the current block's `CullMode::TransparentMerged(T)` [S1, unofficial].

*   **Lighting Value:**
    The lighting value is a discrete integer (0-14 in the reference implementation) mapped to the block type and face orientation [S1, unofficial]. For example, cactus blocks have different lighting values for top/bottom faces versus side faces.

### Parameters
*   **TransparentGroup (T):** An integer or enum value identifying the transparency group for merging. Not given in the sources for a global default, but specific to block implementation [S1, unofficial].
*   **Stretch:** A float value for cross-shaped geometries, defining the length of the cross arms [S1, unofficial].

### Edge Cases and Pitfalls
*   **Fluid Shape Assertion:** Setting a fluid configuration flag (e.g., `FLUID_ENABLED`) to true without implementing the corresponding fluid shape logic causes a debug assertion failure rather than silently rendering fluids as cubes [S1, unofficial].
*   **Threading Constraints:** In implementations using the Geometry Builder pattern, mesh data calculation can occur on a background thread, but the final creation of the mesh object must occur on the main thread to comply with engine constraints (e.g., Unity3D) [S3, unofficial].
*   **Bottom Face Culling:** As per the parent article, bottom faces are often culled entirely for certain block types to reduce geometry, regardless of neighbor occupancy [S1, unofficial].

## Subtopics

### [Three-Valued Opacity Classification for Meshing](4414-three-valued-opacity-classification-for-meshing.md)
A classification system for block IDs into three mutually exclusive layers: 'opaque', 'water', and 'transparentSolid'. It solves the insufficiency of a single boolean 'transparent' flag by distinguishing between fluids (water) requiring bespoke shaders and see-through solids (glass/leaves) requiring alpha blending. Unlike a boolean transparent flag which collapses water and glass/leaves into one category, this three-valued model allows water to use a bespoke shader (ripple, refraction) while glass/leaves use the ordinary block atlas with alpha blending.

### Ramp Shape Geometry
A shape representing a sloped block face, composed of a slope quad (2 triangles) and two side triangles (left and right) [S2, unofficial]. Instance creation involves iterating visible faces; if the face is Left, Right, Top, or Front, `drawSlope` is set to true and tints are assigned based on face direction (Top/Front use `tints[0]`, Left uses `tints[1]`, Right uses `tints[2]`) [S2, unofficial]. If a specific tint is `Vector3.One`, it falls back to another face's tint [S2, unofficial]. Back and Bottom faces use dedicated shape IDs (`cubeBackFaceShapeID`, `cubeBottomFaceShapeID`) [S2, unofficial]. The slope vertices are defined as: (0,1,0) UV[0], (0,0,1) UV[1], (1,1,0) UV[2], (1,1,0) UV[3], (0,0,1) UV[4], (1,0,1) UV[5]. Left triangle vertices: (0,0,1) UV[0], (0,1,0) UV[1], (0,0,0) UV[2]. Right triangle vertices: (1,0,0) UV[0], (1,1,0) UV[1], (1,0,1) UV[2] [S2, unofficial].

### Fluid Surface Stitching
A mesh generation technique where fluid columns share a surface height field with neighbors, stitching surfaces when fluid IDs match [S1, unofficial]. Two adjacent fluid blocks join their surfaces only when their `FluidInfo::id` (u8) values are equal [S1, unofficial].

### Geometry Builder Pattern
A design pattern using an interface to control the type of geometry created for each non-empty voxel, allowing different geometry types (cubes, ramps, X-shapes) to be generated via polymorphism without large switch statements [S3, unofficial]. The interface `IGeometryBuilder` contains a single function `BuildGeometry()` [S3, unofficial]. During mesh creation, `BuildGeometry()` is called once for each non-empty block, passing a reference to the chunk object. The function uses this reference to add vertices and indices to the chunk's linked list. After all blocks are processed, the data is placed into a Mesh object on the main thread [S3, unofficial]. Implementations include `BoxBuilder` (standard cubes), `MicroBlockBuilder`, and `WaterBuilder` (top faces only) [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of voxels in the chunk, as each voxel is processed once to determine its shape and culling status.
*   **Memory Complexity:** $O(F)$ where $F$ is the number of visible faces, as geometry is only generated for exposed faces.
*   **Strengths:** High flexibility in block appearance and rendering behavior; decouples block logic from mesh generation; supports complex shapes like ramps and fluids.
*   **Limitations:** Requires careful implementation of all block types to avoid assertion failures or missing geometry; threading constraints may limit parallelization in some engines.
*   **When to Use:** When the voxel world contains diverse block types with different visual and physical properties (e.g., transparent, sloped, fluid) that require distinct rendering passes or culling behaviors.
*   **When Not to Use:** For simple, uniform voxel worlds where all blocks are opaque cubes, as the overhead of the trait system is unnecessary.

## Background
The concept of block-specific configuration in voxel meshing evolved from early implementations that used hard-coded switch statements to handle different block types. The trait-based interface and geometry builder pattern were introduced to improve code maintainability and extensibility, particularly in projects like "VoxBox" and "GalensUnified" [S1, unofficial][S2, unofficial][S3, unofficial]. The three-valued opacity classification addresses the limitations of binary transparency in games like Minecraft, where water and glass require different rendering techniques [S1, unofficial]. The ramp shape geometry and fluid stitching techniques are common in modern voxel engines to enhance visual fidelity and realism [S2, unofficial][S1, unofficial].
