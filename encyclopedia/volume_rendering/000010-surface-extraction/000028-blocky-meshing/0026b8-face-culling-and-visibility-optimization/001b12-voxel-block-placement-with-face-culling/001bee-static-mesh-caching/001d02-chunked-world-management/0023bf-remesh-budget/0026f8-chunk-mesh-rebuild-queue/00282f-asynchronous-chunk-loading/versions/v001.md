# Asynchronous Chunk Loading

Also called: Async Chunk Streaming, Async Voxel Generation, Chunk Task Queue

## Overview
Asynchronous Chunk Loading offloads the computationally expensive process of generating chunk meshes from the main game thread to a background thread pool, preventing frame stutter caused by procedural voxel generation [S1, unofficial]. It differs from synchronous loading by using futures and task queues to decouple mesh computation from rendering, ensuring the game loop remains responsive while chunk data is prepared [S1, unofficial].

## How it works
**Inputs and Outputs**
*   **Input:** Player chunk coordinates (`newChunkX`, `newChunkY`), a procedural population callback (`PopulateBlock`), and a render distance radius (`ChunkRenderDistance`) [S1, unofficial].
*   **Output:** A queue of `MeshData` structures containing vertices, indices, normals, UVs, and colors for each chunk section, which are subsequently uploaded to the GPU [S1, unofficial].

**Data Structures**
*   `TMap<int32, TFuture<TArray<MeshData*>*>*> chunkResults`: Maps a chunk hash (integer) to a pointer to a future containing the generated mesh data. Used to track in-flight requests and prevent duplicate generation [S1, unofficial].
*   `TQueue<TArray<MeshData*>> chunkLoaderQueue`: A thread-safe queue storing completed mesh data arrays, consumed by the game thread [S1, unofficial].
*   `ChunkMap`: A spatial hash map (`TMap<int32, AChunk*>`) storing already loaded and rendered chunk actors [S1, unofficial].

**Parameters**
*   `ChunkRenderDistance`: Integer radius defining the square area of chunks to load around the player [S1, unofficial].
*   `PopulateBlock`: A callback function signature (`TPopulateBlockFunc`) used to generate voxel data for a given chunk coordinate [S1, unofficial].

**Steps**
1.  **Calculate Load Area:** Determine the square region of chunks to load based on the player's current chunk `(newChunkX, newChunkY)` and `ChunkRenderDistance`. The range is `[newChunkX - ChunkRenderDistance, newChunkX + ChunkRenderDistance]` for both X and Y axes [S1, unofficial].
2.  **Iterate and Submit:** For each chunk `(i, j)` in the calculated area:
    a. Compute the chunk hash using `GetHashFromChunkPosition(i, j)` [S1, unofficial].
    b. Check if the chunk is already loaded in `ChunkMap` or if a generation task is in-flight in `chunkResults` [S1, unofficial].
    c. If neither exists, submit a mesh generation task to the UE5 thread pool using `Async(EAsyncExecution::ThreadPool, ...)` [S1, unofficial].
    d. The task executes `GetMeshDataForChunk(i, j, PopulateBlock)` [S1, unofficial].
    e. Store the returned `TFuture` pointer in `chunkResults` keyed by the chunk hash [S1, unofficial].
3.  **Process Results (Game Thread):** On the game thread, dequeue completed `MeshData` arrays from `chunkLoaderQueue` one per frame [S1, unofficial].
4.  **Create Chunk:** For each dequeued result:
    a. Call `AChunk::CreateChunk(ChunkX, ChunkY, World, chunkData)` [S1, unofficial].
    b. Spawn the `AChunk` actor at the correct world location (`ChunkX * 1600`, `ChunkY * 1600`, `-1000`) [S1, unofficial].
    c. Iterate through the sections in `chunkData` and upload the mesh data (vertices, triangles, normals, UVs, colors, tangents) to the `UProceduralMeshComponent` using `CreateMeshSection_LinearColor` [S1, unofficial].
    d. Enable physics collision data on the mesh component [S1, unofficial].
    e. Add the new chunk actor to `ChunkMap` using its hash [S1, unofficial].

def PlayerMovedToAnotherChunk(newChunkX, newChunkY, PopulateBlock, ChunkRenderDistance):
    # Define the square load area
    min_x = newChunkX - ChunkRenderDistance
    max_x = newChunkX + ChunkRenderDistance
    min_y = newChunkY - ChunkRenderDistance
    max_y = newChunkY + ChunkRenderDistance
    
    for i in range(min_x, max_x + 1):
        for j in range(min_y, max_y + 1):
            # Skip player's current chunk if handled elsewhere to avoid double submission
            if i == newChunkX and j == newChunkY:
                continue
                
            hash = GetHashFromChunkPosition(i, j)
            
            # Check if chunk is already loaded or being generated
            if hash in ChunkMap or hash in chunkResults:
                continue
                
            # Submit async task
            future_ptr = Async(EAsyncExecution.ThreadPool, lambda: GetMeshDataForChunk(i, j, PopulateBlock))
            chunkResults[hash] = future_ptr
            
            # Define callback to handle completion
            def ChunkCallback(fut):
                result = fut.get()
                chunkLoaderQueue.enqueue(result)
                chunkResults.remove(hash)
                
            future_ptr.add_done_callback(ChunkCallback)

    transform = FTransform(location)
    
    if World:
        newChunk = World.SpawnActor(AChunk, transform)
        newChunk.SetActorLabel(f"Chunk_{ChunkX}_{ChunkY}")

**Edge Cases and Pitfalls**
*   **Player Chunk Skipping:** The current implementation logic `if (i != 0 || j != 0)` in the source loop skips the player's exact current chunk relative to itself. If the player's current chunk is not handled elsewhere, it may remain unqueued and unloaded [S1, unofficial].
*   **Duplicate Generation:** Without checking `chunkResults`, concurrent movements could trigger multiple generation tasks for the same chunk. The `TMap` check prevents this [S1, unofficial].
*   **Memory Leaks:** The source code manually deletes `MeshData` objects after upload. Failure to do so or double-deletion (if the queue is processed multiple times) causes memory issues [S1, unofficial].
*   **No Inter-chunk Culling:** Boundary faces between chunks are always rendered, even if occluded by the neighbor, increasing draw calls [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Mesh generation is offloaded, so the game thread complexity is reduced to $O(N)$ where $N$ is the number of chunks dequeued per frame (typically 1). The background thread complexity is proportional to the number of voxels in the chunk.
*   **Memory Complexity:** $O(C)$ where $C$ is the number of chunks in the render distance. Memory is used for `chunkResults` (in-flight futures) and `ChunkMap` (loaded actors).
*   **Performance:** Prevents frame stutter associated with procedural generation. Performance is limited by the thread pool capacity and the cost of uploading mesh data to the GPU [S1, unofficial].
*   **Strengths:** Smooth gameplay experience; decouples heavy computation from rendering.
*   **Limitations:** No inter-chunk face culling; chunk unloading is not implemented in the source (stubbed) [S1, unofficial].

## Background
This method is derived from the architecture of the UE5 Minecraft Clone project, which implements a voxel world generator using Unreal Engine 5's thread pool and procedural mesh components [S1, unofficial]. It builds on [Chunk Mesh Rebuild Queue](3911-chunk-mesh-rebuild-queue.md) by providing the specific asynchronous execution mechanism for the queue's tasks.
