# Remesh Budget

Also called: RemeshQueue

## Overview
Remesh Budget is a rendering optimization that processes dirty chunks nearest the camera first within a strict time budget per frame [S1]. It ensures that visual updates remain responsive by prioritizing high-visibility geometry while deferring distant or less critical mesh rebuilds to subsequent frames [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A set of "dirty" chunks (chunks containing modified blocks that require mesh regeneration) and the current camera position.
*   **Output:** Updated mesh geometry for a subset of dirty chunks, processed within the allocated time budget.

**Data Structures:**
*   **RemeshQueue:** A priority queue or ordered list storing chunk indices. The ordering is determined by the distance from the camera, with nearest chunks having highest priority [S1].
*   **Dirty/Modified State:** A mechanism to track which chunks have changed since the last mesh generation (implied by "dirty chunks" [S1]).

**Steps:**
1.  **Identify Dirty Chunks:** Determine which chunks in the world have been modified and require remeshing [S1].
2.  **Populate RemeshQueue:** Add all dirty chunk indices to the `RemeshQueue`. Sort or insert them such that chunks nearest to the camera are at the front of the queue [S1].
3.  **Initialize Timer:** Start a timer or accumulator for the remeshing phase of the current frame [S1].
4.  **Process Loop:**
    a.  Check if the accumulated remeshing time exceeds the **Frame Budget** (3 ms) [S1].
    b.  If the budget is exceeded, exit the loop [S1].
    c.  Pop the next chunk index from the front of the `RemeshQueue` [S1].
    d.  If the queue is empty, exit the loop [S1].
    e.  Generate the mesh for the popped chunk [S1].
    f.  Add the time taken for this mesh generation to the accumulator [G].
5.  **Guarantee Progress:** Ensure that at least one chunk is meshed per frame, even if the budget is extremely tight or the queue was just populated [S1].

**Parameters:**
*   **Frame Budget:** 3 ms per frame dedicated to remeshing [S1].

**Edge Cases and Pitfalls:**
*   **Empty Queue:** If no chunks are dirty, the loop does not execute, and no time is spent [S1].
*   **Single Chunk Guarantee:** The algorithm must mesh at least one chunk per frame to prevent visual stagnation, regardless of the time budget [S1].
*   **Precision:** Time measurements should be precise enough to handle sub-millisecond mesh operations, though the budget is coarse (3 ms) [S1].

**Pseudocode:**

```python
def process_remesh_budget(camera_position, dirty_chunks, remesh_queue, frame_budget_ms=3.0):
    """
    Processes dirty chunks for remeshing within a strict time budget.
    
    Args:
        camera_position: Current camera location.
        dirty_chunks: List of chunk indices that need remeshing.
        remesh_queue: A queue data structure supporting push, pop, and empty check.
        frame_budget_ms: Maximum time in milliseconds allowed for remeshing per frame.
        
    Returns:
        None. Modifies the world mesh via side effects.
    """
    # Step 1 & 2: Populate RemeshQueue with dirty chunks, ordered by distance to camera
    # Note: The source implies the queue is maintained or populated with this order [S1]
    for chunk_index in dirty_chunks:
        distance = calculate_distance(camera_position, chunk_index)
        remesh_queue.push(chunk_index, distance)
    
    # Clear the dirty chunks list as they are now in the queue
    dirty_chunks.clear()
    
    # Step 3: Initialize Timer
    time_spent_ms = 0.0
    
    # Step 4: Process Loop
    # We must mesh at least one chunk [S1]
    meshed_at_least_one = False
    
    while not remesh_queue.is_empty():
        # Check budget before processing next chunk
        if time_spent_ms > frame_budget_ms:
            break
            
        # Pop nearest chunk
        chunk_index = remesh_queue.pop_nearest()
        
        # Generate mesh for the chunk
        start_time = get_current_time_ms()
        mesh = generate_chunk_mesh(chunk_index)
        end_time = get_current_time_ms()
        
        time_spent_ms += (end_time - start_time)
        update_world_mesh(chunk_index, mesh)
        
        meshed_at_least_one = True
        
        # If we have spent the budget, stop, but we have already meshed this chunk
        # The guarantee of "at least one" is satisfied if the queue was not empty initially
        if time_spent_ms > frame_budget_ms:
            break
            
    # Edge Case: If the queue was empty initially, nothing happens.
    # If the queue had items but budget was 0 (unlikely), we still need to mesh one?
    # The source says "always mesh at least one chunk" [S1].
    # This implies if the queue is not empty, we enter the loop and mesh one,
    # even if time_spent_ms exceeds budget immediately after.
    # The logic above handles this: we pop, mesh, then check budget for NEXT iteration.
    # However, if budget is 0, we might mesh one and then break.
    # To strictly ensure "at least one" if queue is not empty:
    if not remesh_queue.is_empty() and not meshed_at_least_one:
        # This case is tricky if budget is 0. 
        # Assuming budget > 0, the loop runs at least once if queue is not empty.
```

## Subtopics

### Chunk Mesh Rebuild Queue
A queue-based system to batch and process chunk mesh rebuilds asynchronously or on tick [S2, unofficial]. It uses a `RebuildSet` to track chunks currently in the queue to avoid duplicates [S2, unofficial]. The process involves popping the last element from the queue, retrieving chunk data, preparing the mesh, updating the world mesh, and enabling collision if the chunk is near the player (within 1 chunk in X and Y) [S2, unofficial]. This variant differs from Remesh Budget by not explicitly using a camera-distance priority or a strict per-frame time budget in its description, but rather a general queue processing model [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** O(N) where N is the number of dirty chunks, but bounded by the time budget. In practice, only a subset of dirty chunks is processed per frame.
*   **Memory Complexity:** O(D) where D is the number of dirty chunks, stored in the `RemeshQueue` and `RebuildSet` (if applicable).
*   **Measured Performance:** In the "Outpost" scene, which consists of 4 chunks and 10k triangles, the method results in 37 draws and 200k triangles on Low settings, 114 draws and 879k triangles on Balanced, and 153 draws and 1.87M triangles on Ultra [S1].
*   **Strengths:** Ensures responsive rendering by prioritizing visible geometry; prevents frame rate spikes by capping remeshing time per frame [S1].
*   **Limitations:** Distant or less critical chunks may be delayed for multiple frames, potentially causing visual pop-in if the delay is too long [S1]. The 3 ms budget is a fixed parameter that may not be optimal for all hardware [S1].
*   **When to Use:** When real-time responsiveness is critical and the number of dirty chunks per frame is high [S1].
*   **When Not to Use:** When all chunks must be updated immediately regardless of visibility, or when the hardware is too slow to meet the 3 ms budget for even a single chunk [S1].

## Background
Remesh Budget was introduced in the "Draw the blocks" phase (Phase 2c) of the Survivor Builder project [S1]. It is part of a voxel rendering system that uses beveled cubes with procedural tiles and material tiers [S1]. The method was implemented in TypeScript (`src/world/voxels/remesh-queue.ts`) and is used in conjunction with a pure mesher (`src/world/voxels/mesher.ts`) [S1]. The system was tested in Headless Chromium on software GL at 1280x720 resolution [S1].
