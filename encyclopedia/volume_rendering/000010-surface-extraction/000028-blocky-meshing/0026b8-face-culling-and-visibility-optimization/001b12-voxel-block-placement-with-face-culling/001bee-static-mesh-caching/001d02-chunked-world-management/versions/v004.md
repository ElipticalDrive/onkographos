# Chunked World Management

Also called: Chunk-based Mesh Caching

## Overview
Chunked World Management splits a voxel world into smaller, independent sub-worlds called chunks to allow localized mesh rebuilding, solving the performance bottleneck of regenerating geometry for an entire volume when only a small region changes [S1, S1, unofficial]. It differs from its parent [Static Mesh Caching](1138-static-mesh-caching.md) by partitioning the single mesh object into multiple chunk-specific meshes, enabling independent updates per chunk rather than global invalidation.

## How it works
**Inputs:** World position of a voxel edit (e.g., placement or removal); global voxel data structure.
**Outputs:** Updated chunk mesh; modified chunk voxel set.

**Data Structures:**
*   `World`: Contains a `HashMap` mapping `IVec3` chunk positions to `Chunk` objects.
*   `Chunk`: Contains a `HashSet` of local voxel positions (`IVec3`) and an optional `Mesh` object.
*   `Chunk Size`: Fixed at $32 \times 32 \times 32$ blocks [S1, S1, unofficial].

**Coordinate Conversion:**
To map a global world position $P$ to a chunk, two steps are required:
1.  **Chunk Position:** $C = \lfloor P / S \rfloor$ (floor division).
2.  **Local Position:** $L = P \pmod S$ (floor remainder).

Where $S$ is the chunk size (32). It is critical to use **euclidean division** (`div_euclid`) and **euclidean remainder** (`rem_euclid`) for negative coordinates. Standard integer division/remainder fails for negative numbers, causing incorrect chunk assignment (e.g., mapping $-7$ to chunk $0$ with offset $-7$ instead of chunk $-1$ with offset $7$) and resulting in uneven chunk sizes [S1, S1, unofficial].

**Algorithm Steps:**
1.  Calculate `chunk_position` using `position.div_euclid(32)`.
2.  Calculate `local_position` using `position.rem_euclid(32)`.
3.  Retrieve or create the `Chunk` at `chunk_position` in the world's HashMap.
4.  Invalidate the chunk's existing mesh (set to `none`) to trigger regeneration on next render.
5.  Update the chunk's local `HashSet`: remove the voxel if it exists, or insert it if it does not.
6.  During rendering, iterate over all chunks. For each chunk with a valid mesh, draw it with an offset of `chunk_position * 32`. If the mesh is invalid, regenerate it using the chunk's local voxels before drawing.

**Pseudocode:**

```python
# Data Structures
struct World:
    chunks: HashMap<IVec3, Chunk>

struct Chunk:
    voxels: HashSet<IVec3>
    mesh: Optional<Mesh>

# Helper: Get or create chunk
def get_or_create_chunk(world: World, chunk_pos: IVec3) -> Chunk:
    if chunk_pos not in world.chunks:
        world.chunks[chunk_pos] = Chunk(voxels=HashSet(), mesh=None)
    return world.chunks[chunk_pos]

# Core: Flip voxel in chunked world
def flip_voxel(world: World, position: IVec3):
    # Use euclidean division/remainder for correct negative coordinate handling
    chunk_position = position.div_euclid(32)
    local_position = position.rem_euclid(32)

    chunk = get_or_create_chunk(world, chunk_position)

    # Invalidate mesh to force rebuild
    chunk.mesh = None

    # Update local voxel set
    if local_position in chunk.voxels:
        chunk.voxels.remove(local_position)
    else:
        chunk.voxels.insert(local_position)

# Rendering Loop
def render_world(world: World):
    for chunk_pos, chunk in world.chunks.items():
        if chunk.mesh is None:
            # Generate mesh from local voxels
            vertices = []
            for voxel_pos in chunk.voxels:
                vertices.append(draw_cube(voxel_pos))
            chunk.mesh = Mesh.from_vertices(vertices)
        
        # Apply offset for world position
        offset = chunk_pos * 32
        draw_mesh(chunk.mesh, offset)
```

## Subtopics

### [Remesh Budget](3119-remesh-budget.md)
Remesh Budget limits the computational cost of mesh regeneration per frame by processing only the most visually significant dirty chunks. It solves frame-time spikes caused by rebuilding geometry for distant or less important chunks by enforcing a strict time budget, ensuring that mesh updates are prioritized based on camera proximity [3119-remesh-budget.md]. It differs from [Chunk-Based Parallel Voxel Culling & Rendering](3994-chunk-based-parallel-voxel-culling-rendering.md) by focusing on temporal budgeting and spatial prioritization of rebuilds rather than parallel culling strategies [3119-remesh-budget.md].

### [Chunk-Based Parallel Voxel Culling & Rendering](3994-chunk-based-parallel-voxel-culling-rendering.md)
This method accelerates the rendering of blocky voxel meshes by distributing the computationally expensive face culling and instance collection tasks across multiple CPU threads, organized by spatial chunks [3994-chunk-based-parallel-voxel-culling-rendering.md]. It solves the bottleneck of single-threaded mesh generation in large voxel worlds by allowing independent chunks to be processed concurrently [3994-chunk-based-parallel-voxel-culling-rendering.md]. It differs from [Remesh Budget](3119-remesh-budget.md) by focusing on parallelism and spatial partitioning rather than dynamic cost-based remeshing thresholds [3994-chunk-based-parallel-voxel-culling-rendering.md].

### ChunkManager
A manager class that handles spatial hashing, automatic job scheduling, world/local coordinate conversion, and smart meshing algorithm selection (blocky vs smooth) [S2, S2, unofficial]. The manager selects the appropriate meshing algorithm (e.g., `GreedyMeshingJob` for blocky, `MarchingCubesJob` for smooth) based on voxel data, with meshes generated automatically via Unity Jobs [S2, S2, unofficial].

### Dirty Region Remeshing with Mesh Pruning
A remeshing strategy that rebuilds meshes only for a ring of chunks surrounding an edit, combined with pruning meshes for deleted chunks to prevent visual artifacts during undo [S3, S3, unofficial]. When an edit occurs, the owning chunk and any existing neighbor across a shared face are marked dirty, limiting rebuilds to this ring [S3, S3, unofficial]. A key pitfall is that if a chunk is deleted during undo, it leaves no dirty flag to drive a rebuild; without explicit pruning, its mesh quads continue to draw, causing the undone stroke to remain visible on screen despite passing CPU assertions [S3, S3, unofficial].

## Operating characteristics
Time complexity for voxel updates is $O(1)$ per chunk modification, as only the affected chunk's mesh is invalidated and rebuilt, rather than the entire world [S1, S1, unofficial]. Memory complexity scales with the number of active chunks, where each chunk stores its own voxel set and mesh [S1, S1, unofficial]. The method reduces draw calls compared to per-voxel rendering but increases them compared to a single global mesh, as each chunk typically requires a separate draw call (or instanced call) [S1, S1, unofficial]. It is most effective in large, sparse worlds where edits are localized, avoiding the $O(N)$ cost of global mesh regeneration [S1, S1, unofficial].

## Background
Originating from practical implementations of voxel engines, this method was popularized in tutorials such as "Make yourself a Voxel Engine THIS weekend" which detailed the transition from a single global mesh to a chunked architecture for efficient editing [S1, S1, unofficial]. It is a foundational technique in modern voxel game engines, enabling real-time terrain editing and large-scale world management.
