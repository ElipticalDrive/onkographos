# CPU Immediate Mode Marching Cubes

Also called: CPU Immediate Sim, Immediate Mode Marching Cubes, Legacy Marching Cubes

## Overview
CPU Immediate Mode Marching Cubes is a classic surface extraction method that computes a 3D scalar field on the CPU and renders the resulting isosurface directly to the GPU using immediate mode draw calls, without storing a persistent mesh buffer in system memory [S1, unofficial]. It differs from standard batched Marching Cubes implementations by flushing geometry to the GPU every few vertices (or per triangle) to maintain a small, fixed-size working buffer, making it suitable for real-time interactive demos and reference implementations where memory allocation overhead must be minimized [S1, unofficial]. It builds on [Isosurface extraction](30-isosurface-extraction.md) by applying the standard cube traversal and lookup table logic but replaces mesh coherence and vertex merging with immediate, unmerged primitive generation.

## How it works
**Inputs and Outputs**
- **Input**: A 3D grid of scalar values (field data), an isovalue threshold, and a primitive type (typically `TRIANGLES`).
- **Output**: A stream of vertices and normals rendered directly via WebGL draw calls. No final mesh object is retained in CPU memory.

**Data Structures**
The implementation uses fixed-size typed arrays to hold vertex attributes for immediate batching. The maximum buffer size is defined by `maxCount`.

- `maxCount`: Integer, typically 4096 [S1, unofficial].
- `posArray`: `Float32Array` of size `maxCount * 3`. Stores vertex positions $(x, y, z)$.
- `normalArray`: `Float32Array` of size `maxCount * 3`. Stores vertex normals $(nx, ny, nz)$.
- `uvArray`: `Float32Array` of size `maxCount * 2`. Stores UV coordinates (optional).
- `colorArray`: `Float32Array` of size `maxCount * 4`. Stores vertex colors (optional).
- `count`: Integer, tracks the number of vertices currently in the buffer.
- `hasPos`, `hasNormal`, `hasUV`, `hasColor`: Boolean flags indicating which attributes are populated for the current batch.

**Algorithm Steps**

1.  **Field Generation**: For each voxel in the 3D grid, compute the scalar field value $F(x,y,z)$ by accumulating contributions from all metaballs (or sources) and a floor term. The contribution of a metaball $i$ at position $\mathbf{p}_i$ with radius $r_i$ to a point $\mathbf{p}$ is typically $A_i / \|\mathbf{p} - \mathbf{p}_i\|^2$ or similar falloff, summed with a background floor value [S1, unofficial].
2.  **Cube Traversal**: Iterate over every cube in the grid. For each cube, determine the intersection of the isosurface with the cube edges using the standard Marching Cubes lookup table.
3.  **Vertex Interpolation**: For each intersected edge, interpolate the vertex position $\mathbf{v}$ and normal $\mathbf{n}$ linearly between the cube's corner values.
4.  **Immediate Batching**:
    -   Initialize `count = 0` and reset attribute flags.
    -   For each triangle generated by the cube:
        -   Add the three vertices (position and normal) to `posArray` and `normalArray` at indices `count*3` to `(count+2)*3`.
        -   Increment `count` by 3.
        -   Set `hasPos = true` and `hasNormal = true`.
        -   **Overflow Check**: If `count >= maxCount - 3`, flush the buffer immediately (see Step 5).
5.  **Flush and Render**:
    -   If `count == 0`, return.
    -   Zero out any remaining entries in `posArray` and `normalArray` from `count*3` to `maxCount*3` to prevent garbage data from being rendered.
    -   Bind `posArray` to the position attribute buffer using `gl.bufferData` with `DYNAMIC_DRAW`.
    -   Bind `normalArray` to the normal attribute buffer using `gl.bufferData` with `DYNAMIC_DRAW`.
    -   Enable vertex attribute arrays for position and normal.
    -   Set attribute pointers: Position at stride 3, Normal at stride 3 (offset 0).
    -   Call `gl.drawArrays(gl.TRIANGLES, 0, count)`.
    -   Reset `count = 0`.

**Parameters**
- `maxCount`: The size of the immediate buffer. Default is 4096 [S1, unofficial]. Larger values reduce draw call overhead but increase memory usage and potential cache misses.
- `isovalue`: The threshold for surface extraction.

**Edge Cases and Pitfalls**
- **Buffer Overflow**: The code checks `count >= maxCount - 3` before adding a triangle to ensure there is space for 3 vertices. If exceeded, the buffer is flushed immediately [S1, unofficial].
- **Garbage Data**: If the buffer is not zeroed out after flushing, previous data may be rendered. The implementation zeros out `posArray` and `normalArray` from `count*3` to the end of the array before drawing [S1, unofficial].
- **Precision**: Linear interpolation of vertex positions and normals is standard. For high-precision requirements, higher-order interpolation or QEF (as in [Marching Cubes with QEF Vertex Optimization](3831-marching-cubes-with-qef-vertex-optimization.md)) may be needed, but immediate mode typically uses linear interpolation for speed.

## Operating characteristics
- **Time Complexity**: $O(N)$ where $N$ is the number of voxels in the grid. Each voxel is processed once, and the lookup table operations are $O(1)$.
- **Memory Complexity**: $O(1)$ auxiliary memory for the immediate buffer (fixed size `maxCount`), plus $O(N)$ for the grid data. The grid data may be pre-computed or generated on the fly.
- **Measured Performance**: Limited by CPU bottlenecks at high resolutions or high blob counts. The constant flushing of the buffer to the GPU can also introduce overhead compared to batched approaches [S1, unofficial].
- **Scaling**: Performance degrades linearly with grid resolution. The fixed buffer size means the number of draw calls increases with the number of triangles, but remains bounded by `maxCount`.
- **Strengths**: Simple implementation, low memory overhead for mesh storage, suitable for real-time interactive demos where the mesh changes frequently.
- **Limitations**: Poor performance at high resolutions due to CPU processing and frequent GPU calls. No vertex merging, leading to higher vertex counts and potential rendering artifacts at shared edges.
- **When to use**: Reference implementations, educational demos, or scenarios where memory allocation is constrained and the grid size is small.
- **When not to use**: Production applications requiring high-resolution meshes, large datasets, or efficient rendering.

## Background
The CPU Immediate Mode Marching Cubes implementation is inspired by Gregg Tavares' (Greggman) metaballs demo in JavaScript, which demonstrated real-time metaball rendering using WebGL immediate mode [S1, unofficial]. The algorithm itself is based on the classic Marching Cubes algorithm by Williams and Lorensen, with lookup tables provided by Paul Bourke [S1, unofficial]. This approach was popular in early WebGL demos for its simplicity and ability to render dynamic surfaces without complex mesh management.
