# CPU Immediate Mode Marching Cubes

Also called: CPU Immediate Sim, Immediate Mode Marching Cubes, Legacy Marching Cubes

## Overview
CPU Immediate Mode Marching Cubes is a classic CPU-based surface extraction method that generates mesh vertices and normals in immediate mode, rendering them directly via WebGL draw calls without storing a persistent mesh buffer [S1, unofficial]. It differs from modern deferred or GPU-accelerated approaches by performing all scalar field evaluation, topology determination, and geometry generation on the CPU every frame, batching small chunks of geometry to minimize API overhead [S1, unofficial]. This method serves primarily as a reference implementation and for educational comparison, offering simplicity at the cost of significant CPU bottlenecks at high resolutions or complex scenes [S1, unofficial].

## How it works
The method operates on a discretized 3D grid (typically Cartesian) where each voxel stores a scalar value. It iterates over every cell in the grid, determines the intersection of the isosurface with the cell edges using precomputed lookup tables, and generates triangle primitives immediately.

### Inputs and Outputs
*   **Input**: A 3D scalar field $V(x,y,z)$ defined on a regular grid of resolution $N_x \times N_y \times N_z$. The field is often composed of metaball contributions and a floor term.
*   **Input**: An isovalue threshold $T$.
*   **Input**: Precomputed Marching Cubes lookup tables (edge indices and triangle configurations) [S1, unofficial].
*   **Output**: A stream of triangle vertices and normals rendered to the screen. No persistent mesh data structure is retained between frames.

### Data Structures
The implementation uses fixed-size typed arrays to store geometry for immediate batching. The maximum batch size is defined by `maxCount`.

*   `maxCount`: Integer, typically 4096 [S1, unofficial].
*   `posArray`: `Float32Array` of size `maxCount * 3`. Stores vertex positions $(x, y, z)$.
*   `normalArray`: `Float32Array` of size `maxCount * 3`. Stores vertex normals $(n_x, n_y, n_z)$.
*   `uvArray`: `Float32Array` of size `maxCount * 2`. Stores UV coordinates (optional).
*   `colorArray`: `Float32Array` of size `maxCount * 4`. Stores vertex colors (optional).
*   `count`: Integer, tracks the number of vertices currently in the batch.

### Steps

1.  **Initialize Batching**:
    *   Set primitive type `prim` (e.g., `TRIANGLES`).
    *   Set `primsize` (3 for triangles).
    *   Reset `count` to 0.
    *   Reset flags `hasPos`, `hasNormal`, `hasUV`, `hasColor` to false.

2.  **Field Generation**:
    *   For each voxel $(i, j, k)$ in the grid:
        *   Compute scalar value $V_{ijk}$ by accumulating contributions from all metaballs and a floor term [S1, unofficial].
        *   Store $V_{ijk}$ in the grid data structure.

3.  **Grid Traversal and Surface Determination**:
    *   Iterate over every cell $(i, j, k)$ where $0 \le i < N_x-1$, $0 \le j < N_y-1$, $0 \le k < N_z-1$.
    *   Retrieve scalar values at the 8 vertices of the cell: $v_0, \dots, v_7$.
    *   Compute the cell configuration index `config` by comparing each $v_m$ against the isovalue $T$:
        $$ \text{config} = \sum_{m=0}^{7} (v_m \ge T ? 2^m : 0) $$
    *   If `config` is 0 or 255, the cell has no intersection with the isosurface; continue to the next cell.

4.  **Edge Intersection and Vertex Generation**:
    *   Use `config` to look up the list of intersected edges from the Marching Cubes table.
    *   For each intersected edge, calculate the intersection point $P$ and normal $N$:
        *   Let the edge connect vertices with values $v_a$ and $v_b$.
        *   Calculate interpolation factor $t$:
            $$ t = \frac{T - v_a}{v_b - v_a} $$
        *   Interpolate position $P$ between vertex positions $P_a$ and $P_b$:
            $$ P = P_a + t(P_b - P_a) $$
        *   Interpolate normal $N$ between vertex normals $N_a$ and $N_b$ (or compute gradient if normals are not stored at vertices) [S1, unofficial].
    *   Add vertex $P$ and normal $N$ to the batch buffers.

5.  **Primitive Generation and Batching**:
    *   Use `config` to look up the list of triangles to form from the intersected edges.
    *   For each triangle defined by edge indices $e_1, e_2, e_3$:
        *   Retrieve the pre-computed vertex positions and normals for these edges.
        *   Call `AddTriangle` with the three vertices.

6.  **Flush and Render**:
    *   After processing all cells, if `count > 0`, flush the remaining batch to the GPU.

### Parameters and Typical Values
*   `maxCount`: 4096 vertices per batch [S1, unofficial].
*   `primsize`: 3 for triangles [S1, unofficial].
*   Grid Resolution: 16³, 32³, 64³, 128³ [S1, unofficial].
*   Isosurface Threshold: Depends on the scalar field definition (e.g., 0.5 for normalized metaballs).

### Edge Cases and Pitfalls
*   **Buffer Overflow**: The code checks `if count >= maxCount - 3` before adding a triangle. If the batch is full, it flushes immediately to prevent writing out of bounds [S1, unofficial].
*   **Precision**: Floating-point interpolation is used for vertex positions. Degenerate cases (vertex exactly on isosurface) are handled by the `>=` comparison in the config calculation.
*   **Boundary Conditions**: The loop iterates up to `resolution - 1` to avoid accessing out-of-bounds grid cells.

## Operating characteristics
*   **Time Complexity**: $O(N^3)$ where $N$ is the grid resolution, as every cell is processed. Field generation is $O(N^3 \cdot B)$ where $B$ is the number of metaballs, unless optimized with culling.
*   **Memory Complexity**: $O(N^3)$ for the scalar field storage. The batch buffer is constant size $O(1)$ relative to resolution (fixed `maxCount`).
*   **Performance**: Limited by CPU throughput. At high resolutions (e.g., 128³) or with many metaballs, the CPU becomes a bottleneck, leading to low frame rates [S1, unofficial].
*   **Strengths**: Simple implementation, no persistent mesh management, easy to debug, minimal GPU memory usage for geometry.
*   **Limitations**: Poor scalability, high CPU usage, not suitable for real-time applications with large volumes or high resolutions.
*   **When to use**: Educational purposes, reference implementations, low-resolution previews, or scenes with very few objects where CPU overhead is negligible.
*   **When not to use**: High-resolution volume rendering, real-time applications with complex scenes, or when GPU acceleration is available and required.

## Background
The CPU Immediate Mode Marching Cubes method is inspired by Gregg Tavares' (Greggman) metaballs demo in JavaScript [S1, unofficial]. It implements the classic Marching Cubes algorithm described by Paul Bourke [S1, unofficial]. The approach reflects early WebGL practices where immediate mode rendering was common before the widespread adoption of buffer objects and deferred rendering pipelines. It serves as a baseline for comparing GPU-accelerated implementations [S1, unofficial].
