# Point Engine for Scalar Fields

Also called: Simplified Marching Cubes for points, rgridb point generation

## Overview
A method to estimate foot points on an isosurface of a scalar field using a simplified version of Marching Cubes that finds only vertices without computing triangles, avoiding the expense of iterative refinement. It builds on [Marching Cubes Surface Point Extraction](6417-marching-cubes-surface-point-extraction.md) by extracting points directly from voxel edges, serving as the core point generation stage for the rgridb renderer.

## How it works
**Inputs:** A scalar field defined on a voxel grid.
**Outputs:** A list of surface points, each associated with an interpolated gradient vector.

**Data Structures:**
*   **Point List:** A single contiguous list storing points. For rgridb, this list contains all generated points without cell-based partitioning [S1, unofficial].
*   **Point Element:** Contains a 3D position vector ($\mathbf{p}$) and a 3D gradient vector ($\nabla f$).

**Algorithm Steps:**
1.  Iterate over every voxel in the volume grid. Let the current voxel's position be $\mathbf{p}$.
2.  Identify the positions of three neighboring voxels:
    *   $\mathbf{q} = \mathbf{p} + (1, 0, 0)$
    *   $\mathbf{r} = \mathbf{p} + (0, 1, 0)$
    *   $\mathbf{s} = \mathbf{p} + (0, 0, 1)$
    *   [G] Ensure these neighbor coordinates are within the valid bounds of the scalar field grid.
3.  For each neighbor position $\mathbf{n} \in \{\mathbf{q}, \mathbf{r}, \mathbf{s}\}$:
    a.  Check if the edge connecting $\mathbf{p}$ and $\mathbf{n}$ is inside the volume.
    b.  Evaluate the scalar field values $f(\mathbf{p})$ and $f(\mathbf{n})$.
    c.  Determine if the edge intersects the isosurface by checking if $f(\mathbf{p})$ and $f(\mathbf{n})$ lie on different sides of the isovalue $I$ (i.e., $(f(\mathbf{p}) - I) \cdot (f(\mathbf{n}) - I) < 0$).
    d.  If an intersection exists:
        i.  Calculate the intersection point $\mathbf{x}$ using linear interpolation (the standard MC scheme for edge intersections):
            $$ \mathbf{x} = \mathbf{p} + \frac{I - f(\mathbf{p})}{f(\mathbf{n}) - f(\mathbf{p})} (\mathbf{n} - \mathbf{p}) $$
        ii. Interpolate the gradient at $\mathbf{x}$. This typically involves sampling the gradient field at $\mathbf{p}$ and $\mathbf{n}$ and performing linear interpolation weighted by the same factor used for position, or evaluating the gradient at $\mathbf{x}$ directly if the field supports it.
        iii. Add the point $\mathbf{x}$ and its interpolated gradient to the output list.
4.  Repeat for all voxels.

**Parameters:**
*   **Isovalue ($I$):** The scalar threshold defining the surface. Typical values depend on the specific scalar field data.

**Edge Cases and Pitfalls:**
*   **Boundary Conditions:** Neighbors $\mathbf{q}, \mathbf{r}, \mathbf{s}$ may fall outside the grid boundaries. These edges must be skipped or handled with appropriate boundary conditions [S1, unofficial].
*   **Shared Vertices:** Unlike full Marching Cubes, this method visits only three edges per voxel and does not require bookkeeping for shared vertices between adjacent voxels. This simplifies implementation but may result in duplicate points if not managed by the downstream renderer [S1, unofficial].
*   **Precision:** Linear interpolation assumes the isosurface is locally planar between grid points. For highly curved surfaces, this approximation may introduce error, though it avoids the cost of iterative refinement [S1, unofficial].

## Subtopics

## Operating characteristics
*   **Time Complexity:** $O(V)$, where $V$ is the number of voxels. Each voxel requires a constant number of scalar evaluations and interpolations.
*   **Memory Complexity:** $O(P)$, where $P$ is the number of surface points. Since only three edges per voxel are checked, $P \le 3V$.
*   **Performance:** Significantly faster than full Marching Cubes because it avoids triangle construction, table lookups, and vertex sharing bookkeeping [S1, unofficial].
*   **Strengths:** Simple implementation, low memory overhead for connectivity, suitable for point-based rendering techniques like QSplat [S1, unofficial].
*   **Limitations:** Does not produce a mesh; requires a point renderer. Potential for duplicate points at voxel boundaries if the renderer does not handle them.
*   **When to use:** When point-based rendering is acceptable and performance is critical.
*   **When not to use:** When a polygonal mesh is required for further processing (e.g., collision detection, texturing).

## Background
Originated in the context of hardware-accelerated point rendering of isosurfaces, specifically for the rgridb renderer. The method was proposed as a computationally efficient alternative to iterative foot-point estimation, which can be as expensive as Marching Cubes [S1, unofficial]. It leverages the simplicity of the Marching Cubes edge-intersection logic but discards the triangle-generation phase.
