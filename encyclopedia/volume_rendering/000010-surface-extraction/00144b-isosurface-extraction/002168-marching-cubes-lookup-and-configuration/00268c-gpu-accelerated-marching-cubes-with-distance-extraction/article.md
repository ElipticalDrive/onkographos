# GPU-accelerated Marching Cubes with Distance Extraction

Also called: WebGL Signed Distance Function Mesher, glsl-marching-cubes

## Overview
This method extracts an STL mesh from a Signed Distance Function (SDF) by offloading the scalar field evaluation to a GLSL shader to extract vertex distances, thereby reducing GPU/CPU round-trip latency compared to running the full algorithm on the GPU [S1, unofficial]. It builds on [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md) by pre-fetching potentials via texture reads, allowing the CPU to skip empty blocks and process only relevant voxels using parallel worker threads [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A volume defined by dimensions (`dims`), spatial bounds (`bounds`), and a GLSL shader function evaluating the SDF.
*   **Output:** An STL mesh file (potentially split into parts for large meshes) [S1, unofficial].

**Data Structures:**
*   **Volume Object:** Contains `dims` (array of 3 integers), `bounds` (array of 2 arrays of 3 floats), `vertexDims` (array of 3 integers), `vertexCount` (integer), and `size` (integer) [S1, unofficial].
*   **Block Potential Buffers:** An array of `ArrayBuffer` objects. Each buffer has a size of `volume.vertexCount * 4` bytes, storing `Float32` values representing the SDF potential at each vertex [S1, unofficial].

**Steps:**
1.  **Volume Subdivision:** Subdivide the input volume into blocks small enough to fit within the GPU's maximum rendering texture size (`maxSize`). The `maxSize` is capped at 4096 to avoid hardware-specific rendering artifacts [S1, unofficial].
2.  **Shader Execution:** Render the volume blocks using a fragment shader that evaluates the SDF at each vertex. The shader outputs the distance values.
3.  **Data Retrieval:** Read the pixel data from the GPU framebuffer using `gl.readPixels` to populate the `blockPotentialBuffers` on the CPU [S1, unofficial].
4.  **Empty Block Culling:** Analyze the retrieved potentials. If a block contains only negative distances (inside) or only positive distances (outside) relative to the isovalue (0), skip processing that block [S1, unofficial].
5.  **Parallel Marching Cubes:** Distribute the remaining blocks to a pool of CPU worker threads (default `numWorkers` = 4) [S1, unofficial]. Each worker runs the standard Marching Cubes algorithm (using the LUTs from the parent article) on its assigned blocks to generate triangles [S1, unofficial].
6.  **Mesh Assembly:** Combine the triangles generated by all workers into the final mesh. For very large meshes, save the output in parts, which must be recombined externally (e.g., using MeshLab) [S1, unofficial].

**Parameters:**
*   `maxSize`: Maximum texture size for the GPU rendering buffer. Capped at 4096 [S1, unofficial].
*   `numWorkers`: Number of CPU worker threads for parallel processing. Default is 4 [S1, unofficial].
*   `blocks`: Number of chunks to split the volume into for worker distribution. Default is 256 [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Large Meshes:** The method may save large meshes in parts, requiring external recombination [S1, unofficial].
*   **Missing Triangles:** Holes may appear in the resulting mesh due to implementation specifics or boundary handling [S1, unofficial].
*   **Precision:** Reading floats from GPU textures can introduce precision issues if not handled carefully (e.g., using `glsl-read-float` techniques) [S1, unofficial].

## Operating characteristics
*   **Performance:** Faster than running the entire algorithm on the GPU because it avoids the high cost of retrieving large amounts of triangle data back to the CPU. It is slower than pure CPU implementations for simple models but scales better for complex SDFs by leveraging GPU parallelism for field evaluation [S1, unofficial].
*   **Memory:** Requires memory for `blockPotentialBuffers` proportional to `volume.vertexCount * 4` bytes per worker [S1, unofficial].
*   **Strengths:** Reduces GPU/CPU round trips; skips empty space efficiently; leverages parallel CPU processing for mesh generation.
*   **Limitations:** Limited by GPU texture size (capped at 4096); potential for mesh holes; requires external tools for large mesh assembly.

## Background
This method originates from the `glsl-marching-cubes` project by tdhooper, designed for WebGL environments [S1, unofficial]. It addresses the bottleneck of data transfer between GPU and CPU in traditional GPU-based marching cubes implementations. The approach was developed to enable efficient SDF visualization in web browsers using Three.js and related libraries [S1, unofficial].
