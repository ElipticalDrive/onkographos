# Marching Cubes Vertex List Generation

Also called: Edge Vertex Calculation, Marching Cubes Vertex Interpolation, Vertex Interpolation for Marching Cubes

## Overview
This method calculates the precise 3D positions of vertices where the scalar field intersects the edges of a voxel cube, generating the vertex list required for polygonal connectivity [S1, unofficial]. It solves the problem of determining geometric intersection points on a structured grid by performing linear interpolation between corner values [S1, unofficial]. It is distinguished from its parent [Vertex Position Optimization and Error Minimization](10991-vertex-position-optimization-and-error-minimization.md) by using standard linear interpolation rather than optimization heuristics or QEF minimization, and from its sibling [Marching Cubes Surface Point Extraction](6417-marching-cubes-surface-point-extraction.md) by generating a list of vertices for mesh topology rather than a single representative point per voxel [S1, unofficial][S2].

## How it works
**Inputs:**
*   `voxelLocalPosition`: The 3D world coordinates of the voxel's origin (corner 0).
*   `voxelDensities`: An array of 8 scalar values (densities) corresponding to the 8 corners of the voxel, indexed 0–7.
*   `isolevel`: The threshold density value defining the surface.
*   `edgeIndex`: An integer (0–255) representing the cube configuration, where the $i$-th bit indicates if edge $i$ is intersected.
*   `EdgeIndexTable`: A lookup table mapping edge indices (0–11) to the two corner indices that form that edge.
*   `CubeCorners`: An array of 8 vectors representing the local coordinates of the cube corners (typically unit cube coordinates).

**Outputs:**
*   `vertexList`: A list of 3D vectors containing the calculated intersection points for all intersected edges.

**Data Structures:**
*   `EdgeIndexTable`: Array of integers. For edge $i$ ($0 \le i < 12$), the corners are at indices $2i$ and $2i+1$.
*   `CubeCorners`: Array of 8 `int3` or `float3` vectors. Standard Marching Cubes indexing usually maps corners 0–7 to specific binary representations of their position relative to the origin.

**Steps:**
1.  Initialize an empty list `vertexList`.
2.  Iterate $i$ from 0 to 11 (representing the 12 edges of the cube).
3.  Check if the $i$-th bit of `edgeIndex` is set.
    *   If not set, continue to the next edge.
    *   If set, proceed to calculate the vertex.
4.  Retrieve the corner indices for edge $i$ from `EdgeIndexTable`:
    *   `startCornerIndex = EdgeIndexTable[2 * i]`
    *   `endCornerIndex = EdgeIndexTable[2 * i + 1]`
5.  Calculate the world positions of the two corners:
    *   $p_1 = \text{voxelLocalPosition} + \text{CubeCorners}[\text{startCornerIndex}]$
    *   $p_2 = \text{voxelLocalPosition} + \text{CubeCorners}[\text{endCornerIndex}]$
6.  Retrieve the scalar densities for the two corners:
    *   $v_1 = \text{voxelDensities}[\text{startCornerIndex}]$
    *   $v_2 = \text{voxelDensities}[\text{endCornerIndex}]$
    *   *Note: If the input densities are normalized (e.g., 0–255), they must be scaled to match the `isolevel` range. For example, divide by 255.0 if `isolevel` is in [0, 1] [S1, unofficial].*
7.  Calculate the intersection position $p$ using linear interpolation:
    $$ p = p_1 + \frac{(\text{isolevel} - v_1)}{(v_2 - v_1)} (p_2 - p_1) $$
8.  Add $p$ to `vertexList`.

**Pseudocode:**
```python
def generate_vertex_list(voxel_local_position, voxel_densities, isolevel, edge_index, edge_index_table, cube_corners):
    vertex_list = []
    
    # Iterate over the 12 edges of a cube
    for i in range(12):
        # Check if the i-th bit is set in edge_index
        if (edge_index >> i) & 1:
            # Get corner indices for this edge from the lookup table
            start_idx = edge_index_table[2 * i]
            end_idx = edge_index_table[2 * i + 1]
            
            # Get world positions of the corners
            p1 = voxel_local_position + cube_corners[start_idx]
            p2 = voxel_local_position + cube_corners[end_idx]
            
            # Get densities at the corners
            v1 = voxel_densities[start_idx]
            v2 = voxel_densities[end_idx]
            
            # Handle normalization if necessary (example: densities are 0-255, isolevel is 0-1)
            # This step depends on the specific data format; assuming raw values match isolevel scale here.
            # If densities are uint8 and isolevel is float [0,1]:
            # v1 = v1 / 255.0
            # v2 = v2 / 255.0
            # isolevel_normalized = isolevel # if isolevel is already [0,1]
            
            # Avoid division by zero if densities are equal
            if v2 == v1:
                # Degenerate case: edge is parallel to isosurface or density is constant.
                # Standard implementation may skip or use midpoint.
                # Using midpoint as a safe fallback [G].
                p = (p1 + p2) / 2.0
            else:
                # Linear interpolation formula
                t = (isolevel - v1) / (v2 - v1)
                p = p1 + t * (p2 - p1)
            
            vertex_list.append(p)
            
    return vertex_list
```

**Parameters:**
*   `isolevel`: The density level where the surface is created. Densities below this are typically considered inside (solid), and above are outside (air) [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Division by Zero:** If $v_1 = v_2$, the denominator in the interpolation formula becomes zero. The source code does not explicitly handle this, implying inputs are assumed distinct or the case is degenerate/unhandled [S1, unofficial]. Implementers should guard against this, often by using the midpoint or skipping the edge.
*   **Normalization Mismatch:** If voxel densities are stored as integers (e.g., 0–255) and the isolevel is a float in [0, 1], failure to normalize the densities or the isolevel will result in incorrect vertex positions [S1, unofficial].

## Subtopics

### Vertex-centered Data Interpolation
A technique to transition from cell-centered to vertex-centered data by 'diffusing' data values from cells to vertices using interpolation, preparing data for Marching Cubes [S2]. It calculates a vertex's value from its adjacent cells using bi-linear or tri-linear interpolation, contingent on the data's dimensionality [S2]. For example, a vertex's value is derived from its neighbor cell values (e.g., using neighbors 8, 6, 6, and 4 to calculate a central value of 6) [S2]. After interpolation, the size of each dimension of the vertex data increases by one relative to the original cell-centered data [S2]. A key pitfall is that re-sampled vertex-centered data can lead to conflicts between Adaptive Mesh Refinement (AMR) levels, specifically dangling nodes, resulting in discontinuities or cracks in the iso-surfaces [S2].

## Operating characteristics
*   **Time Complexity:** $O(1)$ per voxel, as it involves a fixed number of operations (12 edge checks and interpolations) regardless of grid size.
*   **Memory Complexity:** $O(1)$ auxiliary memory per voxel for the vertex list (up to 12 vertices).
*   **Strengths:** Simple to implement; computationally inexpensive; produces topologically correct meshes when combined with the lookup table [S1, unofficial].
*   **Limitations:** Linear interpolation can introduce geometric error, especially on coarse grids or with high-frequency scalar fields, leading to "jagged" or inaccurate surfaces compared to optimized methods [S1, unofficial].
*   **When to use:** When computational efficiency is prioritized over geometric accuracy, or as a baseline for comparison with optimization techniques.
*   **When not to use:** When high-fidelity surface representation is required on coarse grids, or when the scalar field has significant variation within voxels.

## Background
The method is a fundamental component of the Marching Cubes algorithm, originally described by Lorensen and Cline in 1987 [S2]. It relies on the principle that if a scalar field changes sign across an edge of a cube, the isosurface must intersect that edge. The linear interpolation formula used is a standard approach for estimating the intersection point based on the assumption that the field varies linearly between grid points. The specific implementation details cited here are derived from modern GPU-based voxel terrain generation systems [S1, unofficial].
