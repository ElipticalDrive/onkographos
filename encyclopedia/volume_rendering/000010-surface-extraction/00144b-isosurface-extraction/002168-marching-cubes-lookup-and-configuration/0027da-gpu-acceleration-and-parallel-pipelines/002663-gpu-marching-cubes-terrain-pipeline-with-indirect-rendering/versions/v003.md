# GPU Marching Cubes Terrain Pipeline with Indirect Rendering

Also called: GPU Marching Cubes with Indirect Rendering, Indirect Marching Cubes, Keijiro's GPU Marching Cubes (modified), Marching Cubes/MeshBuilderIndirect, TerrainMeshBuilderIndirect

## Overview
This method generates terrain meshes from voxel data on the GPU using Marching Cubes, utilizing indirect rendering to allow the GPU to generate and render the mesh directly without CPU readback, avoiding performance stalls [S1, unofficial]. It manages multiple LOD levels and renders generated triangles via indirect draw calls to minimize CPU-GPU synchronization overhead [S1, unofficial]. Unlike CPU implementations or standard GPU versions that read back mesh data to the CPU for rendering, this approach keeps RenderThread time low (~1.5ms) by keeping geometry generation and batching entirely on the GPU [S1, unofficial].

## How it works
**Inputs and Outputs**
*   **Inputs**:
    *   `VoxelData`: A 3D buffer of scalar field values for the current chunk.
    *   `Dims`: The voxel resolution of the chunk (must be odd) [S1, unofficial].
    *   `Scale`: The physical size of a single voxel [S1, unofficial].
    *   `Isovalue`: The scalar threshold for surface extraction (default 0.0) [S1, unofficial].
    *   `HalfVoxelOffset`: Offset applied to center the voxel grid, calculated as `Scale * -0.5` [S1, unofficial].
    *   `chunkCenterWS`: The world-space center of the chunk [S1, unofficial].
    *   `triangleTable`: A precomputed `ComputeBuffer` of 256 `ulong` values representing the `triangleTable` from [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md) [S1, unofficial].
    *   `TerrainLod`: Configuration containing LOD level, voxel resolution, and chunk radius [S1, unofficial].
*   **Outputs**:
    *   `VertexBuffers`: An `AppendStructuredBuffer` of `Triangle` structs, where each `Triangle` contains three `VertexGPU` structs. Each `VertexGPU` has `float3 posWS`, `float3 nrmWS`, and `float2 uv` (total 96 bytes per triangle) [S1, unofficial].
    *   `IndirectArgBuffers`: A buffer of 5 `uint` values used for indirect draw calls [S1, unofficial].

**Data Structures**
1.  **Triangle Struct**:
    ```csharp
    struct VertexGPU {
        float3 posWS;
        float3 nrmWS;
        float2 uv;
    };
    struct Triangle {
        VertexGPU v0;
        VertexGPU v1;
        VertexGPU v2;
    };
    ```
2.  **IndirectArgBuffer Layout** (5 uints):
    *   Index 0: Total vertex count (initially 3, updated to `3 * triangleCount`) [S1, unofficial].
    *   Index 1: Instance count (initially 1, updated to `triangleCount`) [S1, unofficial].
    *   Index 2: Start vertex (0) [S1, unofficial].
    *   Index 3: Start instance (0) [S1, unofficial].
    *   Index 4: Unused (0) [S1, unofficial].

**Algorithm Steps**

1.  **Buffer Allocation**:
    For each LOD level $i$, compute the active chunk count using `ManhattanFloodFillCount3D`. For LOD 0, use the full count; for $i > 0$, subtract the previous LOD's count. Allocate `VertexBuffers` as `AppendStructuredBuffer<Triangle>` sized to `voxelRes.x * voxelRes.y * voxelRes.z * activeChunks`. Allocate `IndirectArgBuffers` as 5 `uint` values [S1, unofficial].

2.  **Initialize Indirect Arguments**:
    Set `IndirectArgBuffers` to `{3, 1, 0, 0, 0}` (vertexCountPerInstance=3, instanceCount=1, startVertex=0, startInstance=0, unused=0) [S1, unofficial].

3.  **Dispatch Marching Cubes Compute Kernel**:
    Dispatch the compute shader kernel with the following parameters:
    *   `g_Tris`: Bound to `VertexBuffers` (AppendStructuredBuffer) [S1, unofficial].
    *   `Dims`: Voxel resolution [S1, unofficial].
    *   `Scale`: Voxel size [S1, unofficial].
    *   `Isovalue`: 0.0 [S1, unofficial].
    *   `HalfVoxelOffset`: `Scale * -0.5` [S1, unofficial].
    *   `chunkCenter`: Chunk center in world space [S1, unofficial].
    *   `TriangleTable`: Precomputed LUT [S1, unofficial].
    *   `Voxels`: Input voxel data buffer [S1, unofficial].
    *   Dispatch group counts: `ceil(res/4)` in each dimension (implying a 4x4x4 thread group) [S1, unofficial].

    **Compute Shader Logic (Per Voxel)**:
    *   Calculate the case index $C$ based on the 8 corner vertices of the voxel relative to the isovalue [S7, S8, S12, unofficial].
    *   Lookup `edgeTable[C]` to determine intersected edges.
    *   Lookup `triangleTable[C]` to determine triangle connectivity.
    *   For each triangle defined by edge indices $(a, b, c)$:
        *   Interpolate vertex positions on the edges.
        *   Compute normals.
        *   Append the `Triangle` to `g_Tris` using `AppendStructuredBuffer` [S1, unofficial].

4.  **Update Indirect Arguments**:
    *   Copy the triangle append counter from `VertexBuffers` to `indirectArgsBuffer` at byte offset 0 [S1, unofficial].
    *   Dispatch a helper compute shader (`indirectArgumentSetter`) to multiply `args[0]` by 3 (vertices per triangle) and `args[1]` by 1 (instances) [S1, unofficial].
    *   Resulting `args`: `{3 * triangleCount, triangleCount, 0, 0, 0}` [S1, unofficial].

5.  **Enqueue Draw Call**:
    *   Create an `IndirectDrawCall` entry containing:
        *   `tris`: The `VertexBuffers` (triangle buffer).
        *   `args`: The `IndirectArgBuffers`.
        *   `material`: Terrain material.
        *   `trs`: Identity transform matrix [S1, unofficial].
    *   Register it with `GpuIndirectDrawRegistry.Add()` [S1, unofficial].

6.  **Reset Append Counter**:
    *   Call `vertexBuffer.SetCounterValue(0)` to clear the triangle append buffer for the next frame [S1, unofficial].

**Vertex Shader**
*   Fetch the corner vertex: if corner index is 0, return `t.v0`; if 1, return `t.v1`; else return `t.v2` [S1, unofficial].
*   Transform world-space position to clip space: `TransformWorldToHClip(o.posWS)` [S1, unofficial].

**Fragment Shader**
*   Normalize normal vector `N` [S1, unofficial].
*   If `dot(N, V) < 0` (where `V` is view direction), flip `N` to ensure it points towards the camera [S1, unofficial].
*   Calculate Lambertian lighting using fixed light direction `float3(1,1,0)`. Return value interpolated between 0.25 and 1.0 based on the dot product [S1, unofficial].

**Pitfalls and Edge Cases**
*   **Voxel Resolution**: Must be odd. Even resolutions trigger a validation error and break the pipeline [S1, unofficial].
*   **Chunk Dimensions**: Must be cube-like ($x == y == z$). Non-cubic chunks trigger a validation error [S1, unofficial].
*   **Ambiguity**: Cases 46, 47, 98, 99, 210, 213, 214, 215 contain saddle points where the topology is ambiguous. The standard LUT uses a fixed triangulation, which can cause cracks if adjacent voxels resolve ambiguities differently [S7, S8, unofficial]. This method relies on the parent's LUT configuration and does not specify dynamic ambiguity resolution [S1, unofficial].

## Operating characteristics
*   **Time Complexity**: The GPU compute kernel processes each voxel in constant time relative to the number of triangles per voxel (max 5). The indirect argument update is $O(1)$ per LOD. Rendering is $O(1)$ draw call per LOD due to indirect batching [S1, unofficial].
*   **Memory Complexity**: Scales linearly with voxel volume and active chunks per LOD: $O(\text{VoxelResolution.x} \times \text{VoxelResolution.y} \times \text{VoxelResolution.z} \times \text{activeChunks})$. Each triangle consumes 96 bytes in the append buffer [S1, unofficial].
*   **Performance**: RenderThread time is low (~1.5ms) due to minimal CPU-GPU synchronization [S1, unofficial].
*   **Strengths**: Avoids CPU mesh copy and readback overhead; supports multiple LOD levels; efficient batching via indirect rendering [S1, unofficial].
*   **Limitations**: Requires custom physics/collision solutions since mesh data is not available on CPU [S1, unofficial]. Limited to Unity terrain rendering pipelines using ComputeShader and GpuIndirectDrawRegistry [S1, unofficial]. Shader target version 4.5 required [S1, unofficial].
*   **When to Use**: Real-time terrain rendering where CPU overhead is a bottleneck and physics/collision can be handled separately or approximated [S1, unofficial].
*   **When Not to Use**: When CPU-side mesh access is required for physics or collision detection without custom solutions [S1, unofficial].

## Background
This method is implemented in Unity terrain rendering pipelines using ComputeShader for surface extraction and GpuIndirectDrawRegistry for batched rendering [S1, unofficial]. It is a modification of Keijiro's GPU Marching Cubes, adapted to use indirect rendering to avoid CPU readback [S1, unofficial]. The approach addresses the performance bottleneck of traditional CPU-based Marching Cubes or GPU-based methods that require readback to the CPU for rendering [S1, unofficial].
