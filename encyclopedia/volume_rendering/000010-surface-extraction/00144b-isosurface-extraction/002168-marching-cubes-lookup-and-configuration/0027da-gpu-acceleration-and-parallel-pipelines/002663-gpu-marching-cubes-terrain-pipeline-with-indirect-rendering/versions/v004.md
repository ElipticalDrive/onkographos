# GPU Marching Cubes Terrain Pipeline with Indirect Rendering

Also called: GPU Marching Cubes with Indirect Rendering, Indirect Marching Cubes, Keijiro's GPU Marching Cubes (modified), Marching Cubes/MeshBuilderIndirect, TerrainMeshBuilderIndirect

## Overview
This method generates terrain meshes from voxel data on the GPU using Marching Cubes, utilizing indirect rendering to allow the GPU to generate and render the mesh directly without CPU readback, avoiding performance stalls [S1, unofficial]. It manages multiple LOD levels and renders generated triangles via indirect draw calls to minimize CPU-GPU synchronization overhead [S1, unofficial]. Unlike CPU implementations or earlier GPU versions that required reading back vertex data to the CPU for mesh construction, this pipeline keeps the RenderThread time low (~1.5ms) by eliminating CPU mesh copy operations [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** Voxel scalar field data (stored in a `ComputeBuffer`), voxel resolution (`int3`), voxel size (`float`), isovalue (`float`, typically 0.0), chunk center in world space (`float3`), and the precomputed Marching Cubes `triangleTable` (`ComputeBuffer` of 256 `ulong` values) [S1, unofficial].
*   **Outputs:** A triangle mesh stored in an `AppendStructuredBuffer` of `Triangle` structs, which is subsequently rendered via indirect draw calls [S1, unofficial].

**Data Structures:**
1.  **`Triangle` Struct:** Contains three `VertexGPU` structs (`v0`, `v1`, `v2`) [S1, unofficial].
2.  **`VertexGPU` Struct:** Contains `float3 posWS` (world-space position), `float3 nrmWS` (world-space normal), and `float2 uv` [S1, unofficial].
3.  **Buffer Size:** Each `Triangle` occupies 96 bytes (32 bytes per vertex: 3 floats position + 3 floats normal + 2 floats UV, assuming standard packing) [S1, unofficial].
4.  **`IndirectArgBuffers`:** A buffer containing 5 `uint` values per LOD level [S1, unofficial]:
    *   Index 0: Total vertex count (initially 3, updated to $3 \times \text{triangleCount}$).
    *   Index 1: Instance count (number of triangles).
    *   Index 2: Start vertex (0).
    *   Index 3: Start instance (0).
    *   Index 4: Unused (0).
5.  **`TerrainLod` Struct:** Contains `LOD` (int), `VoxelResolution` (int3), and `chunkRadius` (int) [S1, unofficial]. LODs must be ordered from highest to lowest resolution [S1, unofficial].

**Algorithm Steps:**

1.  **Buffer Allocation:** For each LOD level $i$, calculate the active chunk count using a Manhattan Flood Fill algorithm (`ManhattanFloodFillCount3D`) [S1, unofficial]. For LOD 0, use the full count; for $i > 0$, subtract the previous LOD's count [S1, unofficial]. Allocate `VertexBuffers` as `AppendStructuredBuffer` sized to `voxelRes.x * voxelRes.y * voxelRes.z * activeChunks` and `IndirectArgBuffers` as 5 `uint` values [S1, unofficial].

2.  **Initialization:** Initialize `IndirectArgBuffers` with `{3, 1, 0, 0, 0}` (vertexCountPerInstance=3, instanceCount=1, startVertex=0, startInstance=0, unused=0) [S1, unofficial].

3.  **Compute Dispatch:** Dispatch the Marching Cubes compute kernel (Kernel 0) [S1, unofficial].
    *   **Thread Group:** Dispatch with group counts $\lceil \text{res}/4 \rceil$ in each dimension, implying a 4x4x4 thread group [S1, unofficial].
    *   **Parameters:** Pass `Dims` (voxel resolution), `Scale` (voxel size), `Isovalue` (0.0), `HalfVoxelOffset` (`Scale * -0.5`), `chunkCenter` (chunk center in world space), `TriangleTable` (256 `ulong`), and `Voxels` (voxel data buffer) [S1, unofficial].
    *   **Kernel Logic:** Each thread processes a voxel. It calculates the 8-bit case index $C$ by comparing scalar field values $V$ at the 8 vertices against the isovalue $\tau$ [S7, S8, S12, unofficial]. It uses `edgeTable` to determine intersecting edges and `triangleTable` to map $C$ to edge indices [S4, S8, S12, unofficial]. It computes intersection points via linear interpolation and appends the resulting `Triangle` to the `AppendStructuredBuffer` [S1, unofficial].

4.  **Argument Update:** Copy the triangle append counter from `VertexBuffers` to `indirectArgsBuffer` at byte offset 0 [S1, unofficial]. Dispatch a helper compute shader (`indirectArgumentSetter`) to multiply `args[0]` by 3 (vertices per triangle) and `args[1]` by 1 (instances per triangle) [S1, unofficial].

5.  **Indirect Draw Registration:** Create an `IndirectDrawCall` entry containing the `tris` (vertex buffer), `args` (indirect args buffer), `material` (terrain material), and `trs` (identity transform matrix) [S1, unofficial]. Register it with `GpuIndirectDrawRegistry.Add()` [S1, unofficial].

6.  **Reset:** Call `vertexBuffer.SetCounterValue(0)` to clear the triangle append buffer for the next frame [S1, unofficial].

**Vertex Shader Logic:**
1.  Fetch the corner vertex index from the input primitive ID or attribute.
2.  If corner is 0, return `t.v0`; if 1, return `t.v1`; else return `t.v2` [S1, unofficial].
3.  Transform the world-space position to clip space using `TransformWorldToHClip(o.posWS)` [S1, unofficial].

**Fragment Shader Logic:**
1.  Normalize the normal vector `N` [S1, unofficial].
2.  If $\text{dot}(N, V) < 0$ (where $V$ is the view direction), flip `N` to ensure it points towards the camera [S1, unofficial].
3.  Calculate Lambertian lighting using a fixed light direction `float3(1, 1, 0)` [S1, unofficial].
4.  Return a value interpolated between 0.25 and 1.0 based on the dot product [S1, unofficial].

This method is a procedural terrain generation pipeline that divides a 3D volume into overlapping chunks, populates them with noise-derived node values, and prepares chunk meshes for Marching Cubes surface extraction. It builds on [GPU Marching Cubes Terrain Pipeline with Indirect Rendering](3803-gpu-marching-cubes-terrain-pipeline-with-indirect-rendering.md) by handling the CPU-side data preparation and chunk management required for the GPU-accelerated extraction. Unlike single-volume extraction, this approach manages spatial locality and boundary continuity through overlapping node grids, ensuring seamless transitions between adjacent chunks.

## Operating characteristics
*   **Time Complexity:** The compute kernel dispatch is $O(V)$ where $V$ is the number of voxels, with constant work per voxel. The indirect draw call overhead is minimal, keeping RenderThread time low (~1.5ms) [S1, unofficial].
*   **Memory Complexity:** Memory scales linearly with voxel volume and active chunks per LOD: $O(\text{VoxelResolution.x} \times \text{VoxelResolution.y} \times \text{VoxelResolution.z} \times \text{activeChunks})$ [S1, unofficial]. Each triangle consumes 96 bytes in the append buffer [S1, unofficial].
*   **Strengths:** Eliminates CPU-GPU synchronization stalls by avoiding readback of mesh data. Supports multiple LOD levels efficiently. Low CPU overhead [S1, unofficial].
*   **Limitations:** Requires custom physics/collision solutions since the mesh is not available on the CPU [S1, unofficial]. Voxel resolution must be odd; even resolutions trigger a validation error and break the pipeline [S1, unofficial]. Chunk dimensions must be cube-like ($x == y == z$); non-cubic chunks trigger a validation error [S1, unofficial].
*   **When to Use:** Real-time terrain rendering in Unity where CPU overhead is a bottleneck and physics can be handled via SDFs or other GPU-friendly methods [S1, unofficial].
*   **When Not to Use:** When CPU-side mesh access is required for collision detection or physics without custom solutions [S1, unofficial].

## Background
This method was implemented in Unity terrain rendering pipelines using ComputeShader for surface extraction and GpuIndirectDrawRegistry for batched rendering [S1, unofficial]. It is a modification of Keijiro's GPU Marching Cubes, adapted to use indirect rendering to avoid CPU readback [S1, unofficial]. The shader target version is 4.5 [S1, unofficial].
