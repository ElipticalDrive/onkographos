# Marching Cubes Job Scheduling

Also called: Parallel Marching Cubes Job Scheduling, Chunk-based Marching Cubes Job Scheduling

## Overview
Marching Cubes Job Scheduling is a parallel execution strategy that decomposes a 3D voxel volume into spatial chunks (sub-volumes) and assigns each chunk to an independent compute job (typically a GPU compute shader or CPU job system task). This approach solves the scalability problem of processing large volumes by enabling concurrent processing of disjoint spatial regions, thereby maximizing hardware utilization [S1, unofficial]. It differs from single-pass global scheduling by introducing explicit chunk management and asynchronous job handles, allowing for dynamic loading and mesh generation of specific world regions without blocking the entire volume [S1, unofficial].

## How it works
The method orchestrates the parallel extraction of isosurfaces by managing data dependencies, memory allocation, and asynchronous execution across multiple worker units.

### Inputs and Outputs
*   **Input:** A 3D voxel volume represented as a `VoxelDataVolume<byte>` (scalar field) and optionally a `VoxelDataVolume<Color32>` (color/attribute data) [S1, unofficial]. The volume is logically divided into chunks defined by `ChunkSize` (e.g., $N \times N \times N$ voxels) [S1, unofficial].
*   **Output:** A `JobHandle` representing the asynchronous completion of the mesh generation for a specific chunk, along with the generated vertex and triangle data stored in pre-allocated buffers [S1, unofficial].

### Data Structures
The core scheduling unit is the `MarchingCubesJob` struct, which encapsulates all necessary data for a single chunk's processing [S1, unofficial].

**`MarchingCubesJob` Layout:**
*   `VoxelData`: Reference to the scalar field chunk (`VoxelDataVolume<byte>`) [S1, unofficial].
*   `VoxelColors`: Reference to the color/attribute chunk (`VoxelDataVolume<Color32>`) [S1, unofficial].
*   `Isolevel`: The scalar threshold for surface extraction (`float`) [S1, unofficial].
*   `VertexCountCounter`: A shared atomic counter (`NativeCounter`) used to track the number of generated vertices across all threads in the job [S1, unofficial].
*   `OutputVertices`: A pre-allocated `NativeArray<MeshingVertexData>` to store the resulting vertex positions, normals, and colors [S1, unofficial].
*   `OutputTriangles`: A pre-allocated `NativeArray<ushort>` to store the resulting triangle indices [S1, unofficial].

**Buffer Sizing:**
The output buffers are sized based on the maximum possible triangle count per voxel. A standard Marching Cubes case generates at most 5 triangles (15 vertices) per voxel [S1, unofficial].
*   `voxelCount` = `ChunkSize.x` $\times$ `ChunkSize.y` $\times$ `ChunkSize.z` [S1, unofficial].
*   `maxLength` = $15 \times$ `voxelCount` [S1, unofficial].
*   `OutputVertices` size = `maxLength` [S1, unofficial].
*   `OutputTriangles` size = `maxLength` [S1, unofficial].

### Algorithm Steps
1.  **Chunk Validation:** The scheduler retrieves the `VoxelData` and `VoxelColors` chunks for the target `chunkCoordinate`. If either chunk is unavailable or fails to load, the process returns null or an error state [S1, unofficial].
2.  **Resource Allocation:**
    *   Allocate a `NativeCounter` (`vertexCountCounter`) with temporary allocator [S1, unofficial].
    *   Calculate `maxLength` as $15 \times$ `voxelCount` [S1, unofficial].
    *   Allocate `OutputVertices` (`NativeArray<MeshingVertexData>`) and `OutputTriangles` (`NativeArray<ushort>`) of size `maxLength` with temporary allocator [S1, unofficial].
3.  **Job Initialization:** Instantiate the `MarchingCubesJob` struct, populating it with the retrieved voxel data, color data, the `Isolevel` parameter (default 0.5f), the `vertexCountCounter`, and the output buffers [S1, unofficial].
4.  **Job Scheduling:** Submit the `MarchingCubesJob` to the job system (e.g., Unity Job System or GPU Compute Shader dispatch). The job system returns a `JobHandle` [S1, unofficial].
5.  **Handle Wrapping:** Wrap the `JobHandle` and the associated job data into a generic handle (e.g., `JobHandleWithData<IMesherJob>`) to allow the caller to track completion and retrieve results asynchronously [S1, unofficial].

### Pseudocode
The following pseudocode illustrates the scheduling logic in a Python-like style, focusing on the orchestration rather than the internal voxel processing (which is handled by the compute kernel).

```python
def schedule_marching_cubes_job(chunk_coordinate, voxel_world):
    """
    Schedules a Marching Cubes job for a specific chunk.
    
    Args:
        chunk_coordinate (int3): The (x, y, z) index of the chunk.
        voxel_world (VoxelWorld): The world object containing chunk storage and settings.
        
    Returns:
        JobHandleWithData: A handle to track the asynchronous job.
    """
    # 1. Retrieve chunk data
    # Attempt to get the voxel data chunk and color chunk for the given coordinate.
    voxel_data = voxel_world.chunk_store.get_voxel_data_chunk(chunk_coordinate)
    voxel_colors = voxel_world.chunk_store.get_voxel_color_chunk(chunk_coordinate)
    
    # If either fails, return null/error.
    if voxel_data is None or voxel_colors is None:
        return None

    # 2. Calculate buffer sizes
    chunk_size = voxel_world.world_settings.chunk_size
    voxel_count = chunk_size.x * chunk_size.y * chunk_size.z
    # Max 5 triangles (15 vertices) per voxel
    max_length = 15 * voxel_count

    # 3. Allocate resources
    # NativeCounter for atomic vertex counting
    vertex_count_counter = NativeCounter(allocator=Allocator.TempJob)
    
    # Pre-allocated output arrays
    output_vertices = NativeArrayMeshingVertexData(size=max_length, allocator=Allocator.TempJob)
    output_triangles = NativeArrayUShort(size=max_length, allocator=Allocator.TempJob)

    # 4. Initialize Job Struct
    marching_cubes_job = MarchingCubesJob(
        voxel_data=voxel_data,
        voxel_colors=voxel_colors,
        isolevel=0.5f,  # Default isolevel
        vertex_count_counter=vertex_count_counter,
        output_vertices=output_vertices,
        output_triangles=output_triangles
    )

    # 5. Schedule Job
    # The job system executes the compute kernel in parallel for all voxels in the chunk.
    job_handle = marching_cubes_job.schedule()

    # 6. Wrap and Return
    return JobHandleWithData(IMesherJob, job_handle, marching_cubes_job)
```

### Parameters and Edge Cases
*   **Isolevel:** The density threshold for surface extraction. Default value is 0.5f [S1, unofficial].
*   **Chunk Size:** Determines the granularity of parallelism. Smaller chunks allow finer-grained scheduling but increase overhead; larger chunks reduce overhead but may lead to load imbalance if voxel density varies [S1, unofficial].
*   **Memory Limits:** The `maxLength` calculation assumes the worst-case scenario (every voxel generates 5 triangles). If the volume is sparse or the isosurface is simple, this leads to significant memory waste. This is a known limitation of the fixed-size allocation strategy [S1, unofficial].
*   **Atomic Contention:** The `VertexCountCounter` uses atomic operations. In high-density scenarios with many threads, atomic contention can become a bottleneck. Alternative strategies like two-pass counting or histogram pyramids may be used to mitigate this [Parent].

## Subtopics

### Multi-Process Ground Truth Generation
A variant of job scheduling applied to ground truth data generation for 3D models. It orchestrates parallel processing using multiple worker processes and a queue for synchronization. It reads object names, distributes them among workers based on `idx % num_of_process`, and processes them concurrently. Workers communicate results via a queue with a timeout mechanism to ensure all workers exit cleanly [S2, unofficial].

### Tandem Algorithm with Dumping
A strategy that enhances the tandem algorithm by reducing the number of generated triangles through a dumping mechanism, specifically handling disconnected components to allow interactive exploration. On a 1626x7028x2000 dataset, the parallel tandem approach extracted surfaces in 5 minutes using 56 processors, compared to more than 3 hours for the sequential version. It filters 18,111 initial components down to 328 based on geometric criteria (volume) [S3].

### Surface Rendering for Vectorial Volumes
A surface rendering technique adapted for vectorial volumes by treating each classified material distribution as an independent volume. It extracts surfaces for each material using standard Marching Cubes on these independent material volumes (which are close to binary volumes with values in [0, 1]) and renders them as multiple objects in the same scene to merge materials in the final image [S4].

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of voxels in the chunk. The parallel execution reduces wall-clock time by a factor proportional to the number of available processing units (threads/cores), assuming sufficient parallelism and no memory bottlenecks [Parent, S1].
*   **Memory Complexity:** $O(V)$ where $V$ is the number of voxels in the chunk. The fixed-size allocation of output buffers ($15 \times V$) ensures $O(V)$ memory usage, but may lead to over-allocation if the actual triangle count is significantly lower [S1, unofficial].
*   **Scalability:** Scales well with chunk size and number of processing units. However, atomic contention on the `VertexCountCounter` can limit scalability in dense scenarios [Parent].
*   **Strengths:** Enables asynchronous processing, allowing for dynamic loading of chunks in large worlds (e.g., voxel terrain) without blocking the main thread [S1, unofficial]. Simplifies memory management by isolating chunks.
*   **Limitations:** Fixed-size buffer allocation can waste memory. Atomic counters can become a bottleneck. Requires careful management of chunk dependencies (e.g., boundary voxels) if seamless meshing across chunks is required [S1, Parent, unofficial].

## Background
The concept of job scheduling for Marching Cubes emerged from the need to process large-scale volumetric data efficiently. Early implementations used single-threaded CPU approaches, which were too slow for interactive applications [S3]. The introduction of GPU compute shaders and CPU job systems enabled parallel processing. The specific chunk-based scheduling approach described here is popularized by implementations like Eldemarkki's Marching Cubes Terrain, which uses Unity's Job System to manage asynchronous mesh generation for voxel worlds [S1, unofficial]. The tandem algorithm with dumping was developed for geophysical data analysis to handle massive datasets (e.g., seismic cubes) by reducing triangle count and enabling interactive exploration [S3].
