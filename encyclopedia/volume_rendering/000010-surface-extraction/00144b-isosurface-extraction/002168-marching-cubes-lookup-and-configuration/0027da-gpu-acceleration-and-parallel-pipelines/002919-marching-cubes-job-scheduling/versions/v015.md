# Marching Cubes Job Scheduling

Also called: Unity Burst Marching Cubes Job Scheduling, Chunk-based Parallel Marching Cubes

## Overview
This method implements the Marching Cubes algorithm on the GPU or via multi-threaded CPU jobs by decomposing the volume into spatial chunks and scheduling independent processing units for each chunk [S1, unofficial]. It solves the problem of memory capacity and parallel scalability in large voxel terrains by processing chunks asynchronously and merging results [S1, unofficial]. It differs from immediate-mode CPU approaches by using a job system with explicit memory management and counters, and from histogram-pyramid methods by relying on pre-allocated buffers and atomic counters rather than dynamic prefix sums [S1, 2317-gpu-marching-cubes-with-histogram-pyramid.md, unofficial].

## How it works
The method processes a 3D voxel volume by dividing it into fixed-size chunks. Each chunk is processed by a parallel job that computes vertex positions and triangle indices, writing them to pre-allocated output arrays using atomic operations for synchronization.

**Inputs and Outputs:**
*   **Input:** A voxel data volume (`VoxelDataVolume<byte>`) and an optional color volume (`VoxelDataVolume<Color32>`).
*   **Input:** The isovalue threshold (`Isolevel`), typically a float in $[0, 1]$ [S1, unofficial].
*   **Input:** Chunk coordinates (`int3`) defining the spatial region to process.
*   **Output:** A list of mesh vertices (`NativeArray<MeshingVertexData>`) and triangle indices (`NativeArray<ushort>`).
*   **Output:** A global vertex counter (`NativeCounter`) tracking the total number of generated vertices across all jobs [S1, unofficial].

**Data Structures:**
1.  **`MarchingCubesJob` Struct:** Contains the input volumes, the isovalue, the global vertex counter, and pointers to the output arrays [S1, unofficial].
2.  **Output Buffers:**
    *   `outputVertices`: A `NativeArray` of `MeshingVertexData`. The size is calculated as `maxLength = 15 * voxelCount`, where `voxelCount` is the number of voxels in the chunk ($W \times H \times D$) [S1, unofficial]. This upper bound assumes the maximum of 5 triangles per voxel, with 3 vertices each [Lookup Table and Ambiguity Handling](10327-lookup-table-and-ambiguity-handling.md).
    *   `outputTriangles`: A `NativeArray` of `ushort` with the same size `maxLength` [S1, unofficial].
3.  **Vertex Counter:** A `NativeCounter` initialized to 0, used to atomically allocate space in the output arrays [S1, unofficial].

**Algorithm Steps:**

1.  **Chunk Validation:** Retrieve the voxel data and color data chunks for the given `chunkCoordinate`. If either chunk is missing or invalid, return null/empty [S1, unofficial].
2.  **Buffer Allocation:**
    *   Calculate `voxelCount` as the product of the chunk dimensions ($W \times H \times D$) [S1, unofficial].
    *   Calculate `maxLength` as $15 \times \text{voxelCount}$ [S1, unofficial].
    *   Allocate `outputVertices` and `outputTriangles` with size `maxLength` using temporary job allocators [S1, unofficial].
3.  **Job Initialization:** Populate the `MarchingCubesJob` struct with:
    *   `VoxelData`: Reference to the byte volume.
    *   `VoxelColors`: Reference to the color volume.
    *   `Isolevel`: The threshold value (default 0.5f) [S1, unofficial].
    *   `VertexCountCounter`: Reference to the global atomic counter.
    *   `OutputVertices`: Pointer to the vertex array.
    *   `OutputTriangles`: Pointer to the triangle array [S1, unofficial].
4.  **Job Scheduling:** Schedule the `MarchingCubesJob` to run on the available compute threads (CPU job system or GPU) [S1, unofficial].
5.  **Job Execution (Per Voxel):**
    *   For each voxel in the chunk, determine the case index $C$ based on the 8 corner values relative to `Isolevel` [Lookup Table and Ambiguity Handling](10327-lookup-table-and-ambiguity-handling.md).
    *   If $C = 0$ or $C = 255$, skip the voxel (no surface) [Lookup Table and Ambiguity Handling](10327-lookup-table-and-ambiguity-handling.md).
    *   Look up the edge intersections in `edgeTable` using $C$ [Lookup Table and Ambiguity Handling](10327-lookup-table-and-ambiguity-handling.md).
    *   Look up the triangle connectivity in `triangleTable` using $C$ [Lookup Table and Ambiguity Handling](10327-lookup-table-and-ambiguity-handling.md).
    *   For each triangle defined by edge indices $(e_a, e_b, e_c)$:
        *   Compute the intersection point on each edge using linear interpolation.
        *   Atomically increment `VertexCountCounter` to get a unique vertex ID for each of the 3 vertices [S1, unofficial].
        *   Write the vertex position (and color, if available) to `outputVertices` at the obtained ID.
        *   Write the 3 vertex IDs to `outputTriangles` at the current triangle index [S1, unofficial].
6.  **Result Return:** Return a handle containing the job data and the final vertex count for mesh assembly [S1, unofficial].

struct MarchingCubesJob:

    VoxelColors: VoxelDataVolume<Color32>

    VertexCountCounter: NativeCounter
    OutputVertices: NativeArray<MeshingVertexData>

function CreateMesh(chunkCoordinate, VoxelWorld):
    # 1. Retrieve Chunk Data
    voxelData = VoxelWorld.ChunkStore.GetVoxelData(chunkCoordinate)
    voxelColors = VoxelWorld.ChunkStore.GetVoxelColors(chunkCoordinate)
    
    if voxelData is null or voxelColors is null:
        return null

    # 2. Calculate Sizes and Allocate
    chunkSize = VoxelWorld.WorldSettings.ChunkSize
    voxelCount = chunkSize.x * chunkSize.y * chunkSize.z
    maxLength = 15 * voxelCount
    
    outputVertices = NativeArray<MeshingVertexData>(maxLength, Allocator.TempJob)
    outputTriangles = NativeArray<ushort>(maxLength, Allocator.TempJob)
    vertexCountCounter = NativeCounter(0, Allocator.TempJob)

    # 3. Initialize Job
    job = MarchingCubesJob(
        VoxelData=voxelData,
        VoxelColors=voxelColors,
        Isolevel=0.5f, # Default value [S1, unofficial]
        VertexCountCounter=vertexCountCounter,
        OutputVertices=outputVertices,
        OutputTriangles=outputTriangles
    )

    # 4. Schedule Job
    jobHandle = job.Schedule()
    
    return JobHandleWithData<IMesherJob>(jobHandle, job)

**Edge Cases and Pitfalls:**
*   **Memory Overflow:** If a chunk contains more than 5 triangles per voxel (e.g., due to complex topology or non-standard LUTs), the pre-allocated `maxLength` will overflow. The standard LUT guarantees max 5 triangles [Lookup Table and Ambiguity Handling](10327-lookup-table-and-ambiguity-handling.md).
*   **Atomic Contention:** High triangle density can cause contention on `VertexCountCounter`. Using a per-thread or per-chunk counter and merging later is a common optimization not detailed in the source but implied by the structure [G].
*   **Boundary Consistency:** Vertices on chunk boundaries must be shared or duplicated consistently to avoid cracks. The source does not specify boundary handling, implying either duplicated vertices (simpler) or a global vertex buffer with shared indices (complex) [G].

## Subtopics

### Multi-Process Ground Truth Generation
A variant used for generating training data for neural networks (e.g., NDC) rather than real-time rendering. It orchestrates parallel processing of 3D models (OBJ files) using multiple worker processes and a queue for synchronization [S2, unofficial]. It distributes object names across processes, processes them to extract ground truth masks and point clouds, and aggregates results [S2, unofficial]. It is chosen when generating large-scale datasets for machine learning rather than interactive visualization [S2, unofficial].

### Tandem Algorithm with Dumping
A strategy for very large datasets (e.g., seismic cubes) that reduces the number of generated triangles through a "dumping" mechanism. It filters disconnected components based on geometric criteria (volume) to allow interactive exploration [S3]. On a 1626x7028x2000 dataset, it reduced 18,111 components to 328 significant ones [S3]. It is chosen for geophysical exploration where noise creates many small, irrelevant objects [S3].

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of voxels in the chunk. The parallel execution reduces wall-clock time proportional to the number of available cores/threads [S1, unofficial][S3].
*   **Memory Complexity:** $O(V)$ per chunk, where $V$ is the number of voxels. The buffer size is fixed at $15 \times V$ vertices and triangles [S1, unofficial].
*   **Performance:** The Unity Job System approach allows efficient CPU multi-threading [S1, unofficial]. The Tandem variant achieved 5 minutes on 56 processors for a 40GB dataset, compared to 3 hours sequentially [S3].
*   **Strengths:** Simple implementation, predictable memory usage, easy to integrate with existing Unity pipelines [S1, unofficial].
*   **Limitations:** Fixed buffer size can waste memory if triangles are sparse; no dynamic resizing; boundary handling requires external logic [G].

## Background
The method is based on the Unity Burst Job System implementation for voxel terrain rendering [S1, unofficial]. It builds on the standard Marching Cubes algorithm [Lookup Table and Ambiguity Handling](10327-lookup-table-and-ambiguity-handling.md) and the principles of GPU acceleration and parallel pipelines [4136-gpu-acceleration-and-parallel-pipelines.md]. The Tandem variant originates from geophysical research for large-scale isosurface extraction [S3].
