# Marching Cubes Job Scheduling

Also called: Parallel Marching Cubes Job Scheduling, Chunk-based Marching Cubes Job Scheduling

## Overview
Marching Cubes Job Scheduling is a parallel processing strategy that decomposes a 3D volume into spatial chunks and assigns the extraction of each chunk to independent computational jobs (typically GPU compute shaders or CPU worker threads). It solves the scalability problem of extracting isosurfaces from large volumes by enabling concurrent processing, thereby reducing total extraction time. It differs from single-threaded approaches by managing data dependencies and output buffering through job handles and atomic counters, and from simple grid-based parallelism by operating on discrete, manageable chunks rather than a monolithic global grid.

## How it works
The method orchestrates the distribution of voxel data chunks to worker processes or threads, managing the synchronization of output buffers and the lifecycle of the extraction jobs.

### Inputs and Outputs
*   **Inputs**:
    *   `VoxelDataVolume<byte>`: The scalar field data for the chunk.
    *   `VoxelDataVolume<Color32>`: Optional color data for the chunk [S1, unofficial].
    *   `Isolevel`: The density threshold for surface extraction (default 0.5f) [S1, unofficial].
    *   `ChunkCoordinate`: The spatial index of the chunk being processed [S1, unofficial].
*   **Outputs**:
    *   `outputVertices`: A `NativeArray` of `MeshingVertexData` containing the extracted vertices.
    *   `outputTriangles`: A `NativeArray` of `ushort` containing the triangle indices.
    *   `vertexCountCounter`: An atomic counter tracking the number of vertices generated [S1, unofficial].

### Data Structures
The core data structure is the `MarchingCubesJob` struct, which encapsulates all necessary state for a single chunk extraction [S1, unofficial].

**`MarchingCubesJob` Layout**:
*   `VoxelData`: `VoxelDataVolume<byte>` (Input scalar field) [S1, unofficial].
*   `VoxelColors`: `VoxelDataVolume<Color32>` (Input color field) [S1, unofficial].
*   `Isolevel`: `float` (Extraction threshold) [S1, unofficial].
*   `VertexCountCounter`: `NativeCounter` (Atomic output vertex counter) [S1, unofficial].
*   `OutputVertices`: `NativeArray<MeshingVertexData>` (Output vertex buffer) [S1, unofficial].
*   `OutputTriangles`: `NativeArray<ushort>` (Output triangle index buffer) [S1, unofficial].

### Steps
1.  **Chunk Retrieval**: Attempt to retrieve the `VoxelDataVolume` and `VoxelDataVolume<Color32>` for the specified `chunkCoordinate`. If either fails, return null [S1, unofficial].
2.  **Counter Allocation**: Allocate a `NativeCounter` (`vertexCountCounter`) using `Allocator.TempJob` to track the global vertex count across parallel jobs [S1, unofficial].
3.  **Buffer Sizing**:
    *   Calculate `voxelCount` as the product of the chunk dimensions ($W \times H \times D$) [S1, unofficial].
    *   Calculate `maxLength` as $15 \times \text{voxelCount}$, based on the maximum of 5 triangles per voxel and 3 vertices per triangle [S1, unofficial].
    *   Allocate `outputVertices` as `NativeArray<MeshingVertexData>` of size `maxLength` [S1, unofficial].
    *   Allocate `outputTriangles` as `NativeArray<ushort>` of size `maxLength` [S1, unofficial].
4.  **Job Initialization**: Initialize the `MarchingCubesJob` struct with the retrieved voxel data, colors, isovalue, counter, and output arrays [S1, unofficial].
5.  **Job Scheduling**: Schedule the `MarchingCubesJob` for execution. Wrap the resulting job handle and job data in a `JobHandleWithData<IMesherJob>` structure and return it to the caller [S1, unofficial].

### Pseudocode
The following pseudocode illustrates the scheduling logic for a single chunk, adapted from the Unity Job System implementation [S1, unofficial].

```python
def schedule_chunk_extraction(chunk_coordinate, voxel_world):
    # Step 1: Retrieve chunk data
    voxel_data = voxel_world.get_voxel_data_chunk(chunk_coordinate)
    voxel_colors = voxel_world.get_voxel_color_chunk(chunk_coordinate)
    
    if voxel_data is None or voxel_colors is None:
        return None

    # Step 2: Allocate atomic counter
    vertex_count_counter = allocate_native_counter(allocator=Allocator.TempJob)

    # Step 3: Calculate buffer sizes
    chunk_size = voxel_world.world_settings.chunk_size
    voxel_count = chunk_size.x * chunk_size.y * chunk_size.z
    max_length = 15 * voxel_count  # 5 triangles/voxel * 3 vertices/triangle

    # Allocate output buffers
    output_vertices = allocate_native_array(MeshingVertexData, size=max_length, allocator=Allocator.TempJob)
    output_triangles = allocate_native_array(ushort, size=max_length, allocator=Allocator.TempJob)

    # Step 4: Initialize job struct
    marching_cubes_job = MarchingCubesJob(
        VoxelData=voxel_data,
        VoxelColors=voxel_colors,
        Isolevel=0.5f,  # Default isovalue [S1, unofficial]
        VertexCountCounter=vertex_count_counter,
        OutputVertices=output_vertices,
        OutputTriangles=output_triangles
    )

    # Step 5: Schedule job
    job_handle = marching_cubes_job.schedule()
    
    # Wrap handle and data for return
    return JobHandleWithData(IMesherJob, handle=job_handle, data=marching_cubes_job)
```

### Parameters
*   `Isolevel`: The density threshold. Default value is 0.5f [S1, unofficial].
*   `maxLength`: The size of the output buffers. Calculated as $15 \times \text{voxelCount}$ [S1, unofficial].

### Edge Cases and Pitfalls
*   **Chunk Failure**: If voxel data for a chunk cannot be retrieved, the function returns null, potentially leaving gaps in the mesh if not handled by the caller [S1, unofficial].
*   **Buffer Overflow**: The buffer size is calculated based on the theoretical maximum (5 triangles per voxel). If the actual number of triangles exceeds this limit, memory corruption or truncation will occur. This is mitigated by the $15 \times \text{voxelCount}$ calculation, which assumes the worst-case scenario for Marching Cubes [S1, unofficial].
*   **Atomic Contention**: The `VertexCountCounter` is shared across parallel jobs. High contention on this counter can become a bottleneck in highly parallelized scenarios [S1, unofficial].

## Subtopics

### Multi-Process Ground Truth Generation
A variant that orchestrates parallel processing of 3D models to generate ground truth data using multiple worker processes and a queue for synchronization. It distributes object names across processes based on an even distribution list, creates worker processes targeting a specific ground truth extraction function, and manages synchronization via a queue with a timeout mechanism. This approach is used for generating large-scale ground truth datasets for machine learning or validation [S2, unofficial].

### Tandem Algorithm with Dumping
A strategy that enhances the tandem algorithm by reducing the number of generated triangles through a dumping mechanism, specifically handling disconnected components to allow interactive exploration. It filters out small components based on geometric criteria (volume), reducing 18,111 components to 328 in tested scenarios. This method drastically reduces memory consumption and extraction time compared to brute-force approaches, making it suitable for large seismic datasets [S3].

## Operating characteristics
*   **Time Complexity**: Linear with respect to the number of voxels, $O(N)$, where $N$ is the total number of voxels in the volume. Parallelization reduces the constant factor significantly.
*   **Memory Complexity**: Linear with respect to the number of voxels, $O(N)$, for storing the output buffers. The buffer size is fixed at $15 \times \text{voxelCount}$ per chunk [S1, unofficial].
*   **Measured Performance**: On a 1626x7028x2000 dataset (40 GB), the parallel tandem approach extracted surfaces in 5 minutes using 56 processors, compared to more than 3 hours for the sequential tandem algorithm [S3].
*   **Strengths**: High scalability with the number of processors; efficient handling of large datasets; modular design allowing for easy integration of different extraction algorithms (e.g., tandem, brute-force).
*   **Limitations**: Requires careful management of memory allocation and deallocation for job buffers; potential bottlenecks in atomic counter contention; complexity in handling edge cases where chunk data is unavailable.
*   **When to Use**: Large-scale volume rendering where extraction time is a critical bottleneck; scenarios requiring interactive exploration of simplified surfaces.
*   **When Not to Use**: Small volumes where the overhead of job scheduling outweighs the benefits; environments with limited memory for buffering large output arrays.

## Background
The concept of job scheduling for Marching Cubes emerged from the need to handle increasingly large 3D datasets in fields like geophysics and terrain generation. The specific implementation detailed in [S1, unofficial] is part of the Eldemarkki Marching Cubes Terrain project, which aims to provide a performant, chunk-based Marching Cubes implementation for real-time applications. The tandem algorithm with dumping, described in [S3], was developed for seismic data interpretation, highlighting the importance of parallel processing and component filtering for interactive exploration of large geological datasets.
