# Marching Cubes Job Scheduling

Also called: Unity Job System Marching Cubes, Chunk-based Parallel MC Scheduling

## Overview
This method implements the Marching Cubes algorithm by distributing voxel chunk processing across multiple CPU threads using the Unity Job System [S1, unofficial]. It solves the problem of high CPU latency in real-time terrain generation by parallelizing the lookup, vertex interpolation, and triangle assembly steps per chunk [S1, unofficial]. It differs from [GPU Acceleration and Parallel Pipelines](4136-gpu-acceleration-and-parallel-pipelines.md) by executing on the CPU using managed job structures rather than GPU compute shaders, and from [CPU Immediate Mode Marching Cubes](2463-cpu-immediate-mode-marching-cubes.md) by explicitly managing memory allocation via `NativeArray` and synchronization via `JobHandle` to ensure thread safety and zero-allocation during the critical path [S1, unofficial].

## How it works
The method processes a 3D volume by dividing it into fixed-size chunks [S1, unofficial]. Each chunk is processed independently by a `MarchingCubesJob` [S1, unofficial]. The job reads voxel data, determines the isosurface topology using the standard lookup tables defined in [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md), and writes the resulting vertices and triangles to pre-allocated buffers [S1, unofficial].

### Inputs and Outputs
*   **Input**: A voxel chunk defined by `chunkCoordinate` (x, y, z indices). The chunk contains:
    *   `VoxelData`: A `NativeArray<byte>` representing scalar field values [S1, unofficial].
    *   `VoxelColors`: A `NativeArray<Color32>` representing per-vertex colors (optional, but present in the reference implementation) [S1, unofficial].
    *   `Isolevel`: A `float` threshold for surface extraction [S1, unofficial].
*   **Output**:
    *   `OutputVertices`: A `NativeArray<MeshingVertexData>` containing the generated vertices [S1, unofficial].
    *   `OutputTriangles`: A `NativeArray<ushort>` containing the indices of the generated triangles [S1, unofficial].
    *   `VertexCountCounter`: A `NativeCounter` tracking the number of vertices written, used for buffer management [S1, unofficial].

### Data Structures
The implementation relies on specific data structures to manage parallel execution and memory:

1.  **`MarchingCubesJob` Struct**:
    *   `VoxelData`: Reference to the scalar field data for the chunk [S1, unofficial].
    *   `VoxelColors`: Reference to the color data for the chunk [S1, unofficial].
    *   `Isolevel`: The threshold value [S1, unofficial].
    *   `VertexCountCounter`: A `NativeCounter` (atomic integer) to safely increment the vertex count across threads or within the job context [S1, unofficial].
    *   `OutputVertices`: `NativeArray<MeshingVertexData>` for output vertex positions, normals, and colors [S1, unofficial].
    *   `OutputTriangles`: `NativeArray<ushort>` for output triangle indices [S1, unofficial].

2.  **`MeshingVertexData`**:
    *   Typically contains `Vector3 position`, `Vector3 normal`, and `Color32 color` [G].
    *   The exact layout depends on the renderer's requirements, but it must be blittable for use in `NativeArray` [G].

3.  **Lookup Tables**:
    *   `edgeTable`: 256 entries, 12-bit masks [10327-lookup-table-and-ambiguity-handling].
    *   `triangleTable`: 256 rows, 16 columns (terminated by -1) [10327-lookup-table-and-ambiguity-handling].

### Algorithm Steps

1.  **Chunk Initialization**:
    *   Retrieve the voxel data and color data for the specified `chunkCoordinate` [S1, unofficial].
    *   If data is unavailable, return null or an empty mesh [S1, unofficial].
    *   Calculate `voxelCount` as the product of the chunk dimensions ($W \times H \times D$) [S1, unofficial].
    *   Calculate `maxLength` for output buffers: $15 \times \text{voxelCount}$ [S1, unofficial]. This assumes a maximum of 5 triangles per voxel, with 3 indices per triangle, plus a safety margin or vertex count tracking [S1, unofficial].
    *   Allocate `outputVertices` and `outputTriangles` with size `maxLength` [S1, unofficial].

2.  **Job Configuration**:
    *   Instantiate `MarchingCubesJob` [S1, unofficial].
    *   Assign `VoxelData`, `VoxelColors`, `Isolevel`, `VertexCountCounter`, `OutputVertices`, and `OutputTriangles` to the job struct [S1, unofficial].

3.  **Job Scheduling**:
    *   Call `marchingCubesJob.Schedule()` [S1, unofficial].
    *   The job executes on a background thread [G]. It iterates over all voxels in the chunk [G].

4.  **Per-Voxel Processing (Inside Job)**:
    *   Read the 8 corner scalar values $V_0 \dots V_7$ [G].
    *   Compute the case index $C$:
        $$ C = \sum_{i=0}^{7} b_i 2^i $$
        where $b_i = 1$ if $V_i < \text{Isolevel}$ (or $> \text{Isolevel}$, depending on convention), else 0 [10327-lookup-table-and-ambiguity-handling].
    *   Look up `edgeTable[C]` to determine intersected edges [10327-lookup-table-and-ambiguity-handling].
    *   If no edges intersect, continue to next voxel [G].
    *   Look up `triangleTable[C]` to get edge indices for triangles [10327-lookup-table-and-ambiguity-handling].
    *   For each triangle triplet $(e_a, e_b, e_c)$:
        *   Interpolate vertex positions on the intersected edges using linear interpolation:
            $$ P = P_1 + \frac{I - V_1}{V_2 - V_1} (P_2 - P_1) $$
            where $P_1, P_2$ are corner positions, $V_1, V_2$ are corner values, and $I$ is the isovalue [G].
        *   Compute normals (via gradient or interpolation) [G].
        *   Write vertex data to `OutputVertices` at index `VertexCountCounter.Value` [G].
        *   Increment `VertexCountCounter` [G].
        *   Write triangle indices $(idx_a, idx_b, idx_c)$ to `OutputTriangles` [G].

5.  **Completion**:
    *   The job handle is returned to the caller [S1, unofficial]. The caller must wait for the handle before reading the output buffers or constructing the final mesh [S1, unofficial].

### Pseudocode

```python
# Standard edge-to-corner mapping for Marching Cubes
EDGE_TO_CORNERS = [
    (0, 1), (1, 2), (2, 3), (3, 0),  # Bottom face
    (4, 5), (5, 6), (6, 7), (7, 4),  # Top face
    (0, 4), (1, 5), (2, 6), (3, 7)   # Vertical edges
]

# Precomputed lookup tables from parent article [10327-lookup-table-and-ambiguity-handling]
edgeTable = [0] * 256
triangleTable = [[-1] * 16 for _ in range(256)]

def interpolate(v1, v2, p1, p2, isolevel):
    t = (isolevel - v1) / (v2 - v1)
    return p1 + t * (p2 - p1)

def compute_normal(p1, p2, p3):
    u = p2 - p1
    v = p3 - p1
    return normalize(cross(u, v))

def corner_pos(c):
    # Returns 3D coordinate of corner c relative to voxel origin
    return Vector3(c & 1, (c >> 1) & 1, (c >> 2) & 1)

def execute_job(voxel_data, voxel_colors, isolevel, counter, out_verts, out_tris, chunk_dims):
    for z in range(chunk_dims[2]):
        for y in range(chunk_dims[1]):
            for x in range(chunk_dims[0]):
                # Read 8 corner scalar values
                corners = [
                    voxel_data[x, y, z], voxel_data[x+1, y, z],
                    voxel_data[x+1, y+1, z], voxel_data[x, y+1, z],
                    voxel_data[x, y, z+1], voxel_data[x+1, y, z+1],
                    voxel_data[x+1, y+1, z+1], voxel_data[x, y+1, z+1]
                ]
                # Compute case index
                case_index = 0
                for i in range(8):
                    if corners[i] < isolevel:
                        case_index |= (1 << i)

                if edgeTable[case_index] == 0:
                    continue

                tri_edges = triangleTable[case_index]
                idx = 0
                while tri_edges[idx] != -1:
                    e_a, e_b, e_c = tri_edges[idx], tri_edges[idx+1], tri_edges[idx+2]
                    idx += 3

                    # Interpolate vertices
                    c1_a, c2_a = EDGE_TO_CORNERS[e_a]
                    c1_b, c2_b = EDGE_TO_CORNERS[e_b]
                    c1_c, c2_c = EDGE_TO_CORNERS[e_c]

                    p_a = interpolate(corners[c1_a], corners[c2_a], corner_pos(c1_a), corner_pos(c2_a), isolevel)
                    p_b = interpolate(corners[c1_b], corners[c2_b], corner_pos(c1_b), corner_pos(c2_b), isolevel)
                    p_c = interpolate(corners[c1_c], corners[c2_c], corner_pos(c1_c), corner_pos(c2_c), isolevel)

                    n_a = compute_normal(p_a, p_b, p_c)

                    base_idx = counter.increment()
                    out_verts[base_idx] = (p_a, n_a, voxel_colors[0])
                    out_verts[base_idx + 1] = (p_b, n_a, voxel_colors[0])
                    out_verts[base_idx + 2] = (p_c, n_a, voxel_colors[0])

                    out_tris[base_idx] = base_idx
                    out_tris[base_idx + 1] = base_idx + 1
                    out_tris[base_idx + 2] = base_idx + 2

def create_mesh(chunk_coordinate):
    voxel_data = get_voxel_data(chunk_coordinate)
    if voxel_data is None:
        return None
    
    chunk_dims = get_chunk_dimensions()
    voxel_count = chunk_dims[0] * chunk_dims[1] * chunk_dims[2]
    max_length = 15 * voxel_count
    
    vertex_count_counter = NativeCounter(Allocator.TempJob)
    output_vertices = NativeArray(max_length, Allocator.TempJob)
    output_triangles = NativeArray(max_length, Allocator.TempJob)
    
    job = MarchingCubesJob(
        voxel_data=voxel_data,
        voxel_colors=get_voxel_colors(chunk_coordinate),
        isolevel=0.5,
        vertex_count_counter=vertex_count_counter,
        output_vertices=output_vertices,
        output_triangles=output_triangles
    )
    
    job_handle = job.schedule()
    return JobHandleWithData(job_handle, job)
```

### Parameters
*   **Isolevel**: The density threshold. Default value is `0.5f` [S1, unofficial].
*   **Chunk Size**: Defined in `VoxelWorld.WorldSettings.ChunkSize`. Typical values are $16^3$, $32^3$, or $64^3$ voxels.
*   **Allocator**: `Allocator.TempJob` is used for temporary allocations within the job context [S1, unofficial].

### Edge Cases and Pitfalls
*   **Precision**: Linear interpolation can introduce small gaps if the isovalue is exactly equal to a vertex value. Standard MC handles this by strict inequality ($<$ or $>$) [G].
*   **Ambiguity**: Cases 46, 47, 98, 99, 210, 213, 214, 215 contain saddle points. The standard LUT uses a fixed triangulation, which can cause cracks if adjacent voxels resolve ambiguity differently [10327-lookup-table-and-ambiguity-handling]. This method uses the standard LUT, so cracks may occur in ambiguous regions [10327-lookup-table-and-ambiguity-handling].
*   **Buffer Overflow**: The `maxLength` calculation ($15 \times \text{voxelCount}$) assumes a maximum of 5 triangles per voxel. If the topology is complex, this may overflow. The sources do not specify a dynamic resizing strategy [S1, unofficial].
*   **Thread Safety**: The `VertexCountCounter` must be atomic to prevent race conditions when multiple threads write to the same output buffer (though in this chunk-based approach, each chunk is processed by one job, so intra-chunk parallelism is not used in the basic implementation) [G].

## Subtopics

### Multi-Process Ground Truth Generation
A variant that orchestrates parallel processing of 3D models to generate ground truth data using multiple worker processes and a queue for synchronization. It reads object names from a list, distributes them among processes based on `idx % num_of_process`, and uses a `Queue` to collect results. Workers process point clouds, build KD-trees, and query KNN neighbors. This is used for generating training data for neural networks, not for real-time rendering [S2, unofficial].

### Tandem Algorithm with Dumping
A strategy that enhances the tandem algorithm by reducing the number of generated triangles through a dumping mechanism, specifically handling disconnected components to allow interactive exploration. It filters small components based on geometric criteria (volume). On a 1626x7028x2000 dataset, it extracted surfaces in 5 minutes using 56 processors, compared to 3+ hours for the sequential version. It reduces the number of disconnected components from 18,111 to 328. This is applied to seismic cubes for hydrocarbon exploration [S3].

## Operating characteristics
*   **Time Complexity**: $O(N)$ where $N$ is the number of voxels in the chunk. The constant factor is reduced by parallelization across chunks [G].
*   **Memory Complexity**: $O(N)$ for the output buffers. The `maxLength` allocation can lead to significant memory overhead if the actual triangle count is much lower than the worst-case 5 triangles per voxel [G].
*   **Performance**: Depends on the number of CPU cores and chunk size. Smaller chunks allow better load balancing but increase scheduling overhead. Larger chunks reduce overhead but may lead to load imbalance if some chunks have more complex geometry [G].
*   **Strengths**: Easy to implement in Unity using the Job System. No GPU programming required. Good for real-time terrain generation on CPU-bound systems [S1, unofficial].
*   **Limitations**: CPU-bound. Memory allocation for `NativeArray` can be costly if not managed carefully. The fixed buffer size may lead to waste or overflow [S1, unofficial].
*   **When to Use**: Real-time terrain generation in Unity where GPU compute shaders are not available or desirable. When the volume data is already on the CPU [S1, unofficial].
*   **When Not to Use**: Very large volumes where memory bandwidth is a bottleneck. When GPU acceleration is available and preferred [G].

## Background
This method is derived from the implementation in the `Eldemarkki/Marching-Cubes-Terrain` repository, which uses the Unity Job System to parallelize Marching Cubes [S1, unofficial]. It builds on the standard Marching Cubes algorithm and the lookup tables defined in [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md). The approach is part of the broader family of [GPU Acceleration and Parallel Pipelines](4136-gpu-acceleration-and-parallel-pipelines.md), but adapted for CPU execution [S1, unofficial].
