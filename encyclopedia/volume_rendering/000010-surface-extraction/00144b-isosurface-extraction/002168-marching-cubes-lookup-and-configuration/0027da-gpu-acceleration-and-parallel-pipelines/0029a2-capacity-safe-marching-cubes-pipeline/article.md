# Capacity-Safe Marching Cubes Pipeline

Also called: Proposed Framework, Two-pass exact-allocation strategy

## Overview
A GPU-based isosurface extraction method that avoids buffer overflow by determining the exact vertex count before geometry generation, using a two-pass approach: first computing counts/offsets, then allocating exact buffers and generating triangles [S1]. Unlike fixed-capacity baselines that reserve static buffers, this method determines the exact vertex count before generation, ensuring stability and preventing buffer overflow without excessive static reservation [S1]. It builds on [GPU Acceleration and Parallel Pipelines](4136-gpu-acceleration-and-parallel-pipelines.md) by adding a precise memory management layer to the parallel voxel processing.

## How it works
The extraction process consists of four sequential stages: cell classification, prefix-sum computation, exact VBO (Vertex Buffer Object) allocation, and triangle generation [S1].

**Inputs and Outputs:**
*   **Input:** A 3D scalar field volume $V$ of resolution $N_x \times N_y \times N_z$. Scalar values are normalized to the range $[0, 1]$ using the dataset's minimum and maximum values [S1]. An isovalue $\tau$ is specified within this normalized range [S1].
*   **Output:** A vertex buffer containing positions and normals for the extracted isosurface.

**Data Structures:**
1.  **Cell Classification Array:** A 3D array (or flattened 1D array) storing the 8-bit case index $C$ for each voxel, derived from the scalar field values $V$ at the 8 vertices relative to $\tau$ [S7, S8, S12, unofficial].
2.  **Count Buffer:** A 1D array of size equal to the number of voxels, storing the number of triangles generated by each voxel.
3.  **Offset Buffer:** A 1D array of size equal to the number of voxels, storing the starting index in the output vertex buffer for each voxel's triangles, computed via exclusive prefix sum [S1].
4.  **Output Vertex Buffer:** A dynamically allocated buffer sized exactly to the total number of vertices required, determined by the sum of triangle counts [S1].

**Steps:**
1.  **Cell Classification:** For each voxel, calculate the case index $C$ based on the sign of $V(v_i) - \tau$ for its 8 vertices $v_i$. Use the `edgeTable` to identify intersected edges and the `triangleTable` to identify the sequence of edge indices forming triangles [S4, S8, S12, unofficial].
2.  **Triangle Counting:** For each voxel, determine the number of triangles $T_v$ generated. This is typically 0, 1, or 2 for standard Marching Cubes. Store $T_v$ in the Count Buffer.
3.  **Prefix-Sum Computation:** Perform an exclusive prefix sum (scan) on the Count Buffer to generate the Offset Buffer. The offset for voxel $v$ is the sum of triangle counts for all voxels $u < v$. This determines the starting write index for each voxel's output in the final buffer [S1].
4.  **Exact Buffer Allocation:** Calculate the total number of vertices $V_{total} = \sum T_v \times 3$ (assuming 3 vertices per triangle). Allocate the Output Vertex Buffer with exactly this capacity [S1].
5.  **Triangle Generation:** For each voxel, using the case index $C$, interpolate vertex positions on the intersected edges. Write the resulting triangle vertices to the Output Vertex Buffer at the index specified by the Offset Buffer for that voxel [S1].

**Parameters:**
*   **Isovalue ($\tau$):** Specified in the normalized scalar range $[0, 1]$. Typical tested values are 0.35, 0.50, and 0.65 [S1].

**Edge Cases and Pitfalls:**
*   **Buffer Overflow:** Using a fixed-capacity single-pass output buffer causes failure at high resolutions (e.g., $512^3$) because the generated output exceeds available buffer capacity, resulting in overwritten or missing vertex data and incomplete geometry [S1].
*   **Precision:** Scalar values must be normalized to $[0, 1]$ before comparison with $\tau$ to ensure consistent behavior across different datasets [S1].

A GPU-accelerated Marching Cubes pipeline that classifies voxels, uses exclusive prefix sums to count active voxels and required vertices, compacts the voxel index array to remove empty voxels, and extracts the isosurface only for active voxels. It sets itself apart from naive parallel Marching Cubes by avoiding buffer overflow and dynamic memory allocation during geometry generation through a two-pass counting and compaction strategy, building on the [Capacity-Safe Marching Cubes Pipeline](4596-capacity-safe-marching-cubes-pipeline.md).

## Operating characteristics
*   **Time Complexity:** The method involves a linear pass over all voxels for classification and counting, a prefix-sum operation (logarithmic or linear depending on implementation), and a linear pass for triangle generation. Overall complexity is $O(N)$ where $N$ is the number of voxels.
*   **Memory Complexity:** Peak VRAM usage includes the input scalar volume, intermediate count and offset buffers, and the generated position and normal buffers [S1]. The exact allocation prevents over-reservation but requires storing the count and offset buffers.
*   **Measured Performance:**
    *   At $512^3$ resolution with isovalue 0.35, the method generates 42.81 million vertices in 44.7 ms with 10.9 GB peak VRAM usage, rendering at 28.6 FPS [S1].
    *   At $128^3$ resolution with isovalue 0.35, the method generates 1.28 million vertices in 5.8 ms with 1.9 GB peak VRAM usage, rendering at 221.4 FPS [S1].
    *   At $128^3$ resolution with isovalue 0.50, the method generates 0.94 million vertices in 4.9 ms with 1.7 GB peak VRAM usage, rendering at 264.7 FPS [S1].
    *   At $128^3$ resolution with isovalue 0.65, the method generates 0.61 million vertices in 4.1 ms with 1.6 GB peak VRAM usage, rendering at 312.5 FPS [S1].
*   **Strengths:** Ensures stability and prevents buffer overflow without excessive static reservation [S1]. Remains stable at high resolutions where fixed-capacity methods fail [S1].
*   **Limitations:** Requires additional memory for count and offset buffers. The two-pass nature adds overhead compared to a single-pass method, but this is mitigated by the efficiency of GPU prefix-sum operations.
*   **When to Use:** When extracting isosurfaces from large volumes where the output size is unknown or highly variable, and buffer overflow is a concern.
*   **When Not to Use:** When memory is extremely constrained and the output size can be tightly bounded, allowing for a smaller fixed buffer.

## Background
The method was proposed in the context of visualizing 3D plasma simulation data, specifically electromagnetic potential values from fusion plasma datasets [S1]. It was developed to address the limitations of fixed-capacity GPU Marching Cubes implementations that fail at high resolutions due to buffer overflow [S1]. The evaluation was performed on a workstation equipped with an AMD Ryzen Threadripper PRO 3955WX CPU, 256 GB of system memory, and an NVIDIA RTX 3090 GPU with 24 GB of VRAM [S1].
