# Capacity-Safe Marching Cubes Pipeline

Also called: Proposed Framework, Two-pass exact-allocation strategy

## Overview
A GPU-based isosurface extraction method that avoids buffer overflow by determining the exact vertex count before geometry generation, using a two-pass approach: first computing counts/offsets, then allocating exact buffers and generating triangles [S1]. It sets itself apart from naive parallel Marching Cubes by avoiding buffer overflow and dynamic memory allocation during geometry generation through a two-pass counting and compaction strategy, building on the [GPU Acceleration and Parallel Pipelines](4136-gpu-acceleration-and-parallel-pipelines.md).

## How it works
The extraction process consists of four sequential stages: cell classification, prefix-sum computation, exact VBO (Vertex Buffer Object) allocation, and triangle generation [S1].

**Inputs and Outputs:**
*   **Input:** A 3D scalar field $V$ of resolution $N_x \times N_y \times N_z$. Scalar values are normalized to the range $[0, 1]$ using the dataset's minimum and maximum values [S1]. An isovalue $\tau \in [0, 1]$ is specified [S1].
*   **Output:** A set of vertices and normals forming the isosurface, stored in a GPU Vertex Buffer Object (VBO) [S1].

**Data Structures:**
1.  **Cell Classification Array:** A 1D array of size $N_x N_y N_z$, where each element stores the 8-bit case index $C$ for the corresponding voxel. $C$ is computed based on the sign of $V(v_i) - \tau$ at the 8 vertices $v_i$ of the voxel, matching the standard LUT vertex ordering [10327-lookup-table-and-ambiguity-handling].
2.  **Count/Offset Buffers:** Intermediate buffers used during the prefix-sum phase to store per-block or per-thread counts and final offsets [S1].
3.  **Exact VBO:** A vertex buffer allocated with size $V_{count} \times \text{sizeof(Vertex)}$, where $V_{count}$ is the exact number of generated vertices [S1].

**Algorithm Steps:**

1.  **Cell Classification:**
    For each voxel $(i, j, k)$ in the grid:
    *   Read the scalar values $V_0, \dots, V_7$ at the 8 corners.
    *   Compute the case index $C$:
        $$ C = \sum_{m=0}^{7} b_m 2^m $$
        where $b_m = 1$ if $V_m < \tau$ (or $> \tau$, depending on convention), else $0$ [10327-lookup-table-and-ambiguity-handling].
    *   Store $C$ in the classification array.

2.  **Prefix-Sum Computation (Counting Pass):**
    *   Determine the number of triangles $T(C)$ for each case index $C$ using the `triangleTable` from [10327-lookup-table-and-ambiguity-handling]. Note that each triangle consists of 3 vertices.
    *   Compute the total number of vertices $V_{total}$ required:
        $$ V_{total} = \sum_{\text{all voxels}} T(C_{voxel}) \times 3 $$
    *   This is typically implemented on the GPU using an exclusive prefix sum (scan) over the triangle counts of active voxels to determine the write offset for each voxel's output [S1].

3.  **Exact VBO Allocation:**
    *   Allocate a vertex buffer of size exactly $V_{total}$ vertices [S1]. This prevents the buffer overflow issues seen in fixed-capacity baselines [S1].

4.  **Triangle Generation (Rendering Pass):**
    *   Launch a kernel where each thread/block processes a voxel.
    *   Using the case index $C$, lookup the edge intersections from `edgeTable` [10327-lookup-table-and-ambiguity-handling].
    *   Interpolate the intersection points on the cube edges to determine vertex positions.
    *   Compute vertex normals (e.g., via gradient of the scalar field or averaging adjacent face normals) [S1].
    *   Write the generated vertices to the VBO at the offset determined by the prefix sum [S1].

**Edge Cases and Pitfalls:**
*   **Buffer Overflow:** Using a fixed-capacity single-pass output buffer causes failure at high resolutions (e.g., $512^3$) because the generated output exceeds available buffer capacity, resulting in overwritten or missing vertex data and incomplete geometry [S1].
*   **Ambiguity:** Cases 46, 47, 98, 99, 210, 213, 214, 215 contain saddle points where the topology is ambiguous. The standard LUT uses a fixed triangulation, which can cause cracks if adjacent voxels resolve the ambiguity differently [10327-lookup-table-and-ambiguity-handling]. This method does not inherently resolve ambiguity but relies on the standard LUT configuration.

## Subtopics

## Operating characteristics
*   **Time Complexity:** The method involves a linear pass over all voxels for classification and counting, followed by a linear pass for generation. The complexity is $O(N)$ where $N$ is the number of voxels.
*   **Memory Complexity:** Peak VRAM usage includes the input scalar volume, intermediate count and offset buffers, and the generated position and normal buffers [S1].
*   **Measured Performance:**
    *   Hardware: NVIDIA RTX 3090 GPU, 24 GB VRAM [S1].
    *   At $128^3$ resolution, isovalue 0.35: 1.28 million vertices, 5.8 ms extraction, 221.4 FPS, 1.9 GB VRAM [S1].
    *   At $512^3$ resolution, isovalue 0.35: 42.81 million vertices, 44.7 ms extraction, 28.6 FPS, 10.9 GB VRAM [S1].
*   **Strengths:** Stability at high resolutions; no buffer overflow; exact memory allocation avoids excessive static reservation [S1].
*   **Limitations:** Requires two passes (counting and generation); peak memory usage scales with output size [S1].

## Background
The method was proposed in the context of visualizing 3D plasma simulation data, specifically electromagnetic potential fields [S1]. It addresses the limitations of fixed-capacity GPU Marching Cubes implementations which fail at high resolutions due to buffer overflow [S1]. The approach is part of a "Proposed Framework" for GPU-based isosurface extraction [S1].
