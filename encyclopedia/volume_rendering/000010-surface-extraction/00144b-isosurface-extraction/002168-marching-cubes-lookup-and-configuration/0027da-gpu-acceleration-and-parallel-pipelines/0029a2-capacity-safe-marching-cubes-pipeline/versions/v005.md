# Capacity-Safe Marching Cubes Pipeline

Also called: Proposed Framework, Two-pass exact-allocation strategy

## Overview
The Capacity-Safe Marching Cubes Pipeline is a GPU-accelerated isosurface extraction method that eliminates buffer overflow by determining the exact vertex count before geometry generation [S1]. It sets itself apart from fixed-capacity single-pass approaches by using a two-pass strategy: first computing counts and offsets, then allocating exact buffers and generating triangles [S1]. This ensures stability at high resolutions where naive parallel implementations would fail due to insufficient buffer capacity [S1].

## How it works
The pipeline consists of four sequential stages: cell classification, prefix-sum computation, exact Vertex Buffer Object (VBO) allocation, and triangle generation [S1].

**Inputs and Outputs:**
*   **Input:** A 3D scalar field (e.g., electromagnetic potential) normalized to the range $[0, 1]$ [S1].
*   **Output:** A mesh consisting of position and normal buffers containing the extracted isosurface geometry [S1].

**Data Structures:**
1.  **Scalar Field:** Stored in GPU memory (e.g., CUDA–OpenGL interoperable VBO or texture) [S1].
2.  **Count/Offset Buffers:** Intermediate buffers used during the prefix-sum phase to store per-voxel vertex counts and global offsets [S1].
3.  **Output Buffers:** Dynamically allocated buffers sized exactly to the total vertex count [S1].

**Steps:**
1.  **Cell Classification:** Each GPU thread processes a voxel. It samples the 8 corner values from the scalar field and classifies the voxel as active or inactive based on the isovalue $\tau$ [S1, S2].
2.  **Prefix-Sum Computation:** An exclusive prefix sum (scan) is performed on the array of active voxel counts to determine the starting offset for each voxel's output data in the final buffer [S1]. This step calculates the exact total number of vertices required.
3.  **Exact VBO Allocation:** Based on the final value from the prefix sum, the pipeline allocates a vertex buffer of exact size [S1]. This avoids the need for large static reservations or dynamic resizing [S1].
4.  **Triangle Generation:** Threads re-process active voxels. Using the offsets computed in Step 2, each thread writes its generated vertices directly into the pre-allocated buffer at the correct position [S1].

**Parameters:**
*   **Isovalue ($\tau$):** Specified in the normalized scalar range $[0, 1]$ [S1]. Typical tested values are $0.35$, $0.50$, and $0.65$ [S1].

    # Determine configuration index (0-255)

# Output: array of starting offsets for each voxel
def compute_offsets(counts):
    # Exclusive prefix sum
    offsets = [0] * len(counts)
    current_sum = 0
    for i in range(len(counts)):
        offsets[i] = current_sum
        current_sum += counts[i]

## Operating characteristics
*   **Time Complexity:** The method involves two passes over the voxel grid (classification/counting and generation), plus a prefix-sum operation. Extraction time scales with resolution and geometric complexity [S1].
*   **Memory Complexity:** Peak VRAM usage includes the input scalar volume, intermediate count/offset buffers, and the exact-sized output position and normal buffers [S1]. It avoids the excessive static reservation of fixed-capacity baselines [S1].
*   **Performance:**
    *   At $128^3$ resolution with isovalue $0.35$: 1.28 million vertices, 5.8 ms extraction, 221.4 FPS, 1.9 GB VRAM [S1].
    *   At $512^3$ resolution with isovalue $0.35$: 42.81 million vertices, 44.7 ms extraction, 28.6 FPS, 10.9 GB VRAM [S1].
*   **Strengths:** Stability at high resolutions; no buffer overflow; no wasted memory from over-allocation [S1].
*   **Limitations:** Requires two passes over the data (classification and generation); higher memory overhead for intermediate buffers compared to single-pass atomic counter methods [S1].
*   **When to use:** High-resolution volume rendering where buffer overflow is a risk and exact memory usage is desired [S1].
*   **When not to use:** When memory is extremely constrained and approximate geometry is acceptable, or when single-pass performance is prioritized over exact allocation [S1].

## Background
The method was proposed in the context of visualizing 3D plasma simulation data, specifically electromagnetic potential fields [S1]. It addresses the limitations of fixed-capacity GPU Marching Cubes implementations that fail at high resolutions (e.g., $512^3$) due to buffer overflow [S1]. The evaluation was conducted on an NVIDIA RTX 3090 GPU [S1].
