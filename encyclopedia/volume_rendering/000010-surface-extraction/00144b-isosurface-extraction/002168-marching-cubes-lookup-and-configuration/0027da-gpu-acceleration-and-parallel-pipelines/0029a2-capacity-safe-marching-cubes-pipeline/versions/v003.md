# Capacity-Safe Marching Cubes Pipeline

Also called: Proposed Framework, Two-pass exact-allocation strategy

## Overview
The Capacity-Safe Marching Cubes Pipeline is a GPU-accelerated isosurface extraction method that prevents buffer overflow by determining the exact vertex count before geometry generation [S1]. Unlike fixed-capacity baselines that reserve static buffers and risk failure at high resolutions, this method uses a two-pass approach: first computing counts and offsets, then allocating exact buffers and generating triangles [S1]. It builds on [GPU Acceleration and Parallel Pipelines](4136-gpu-acceleration-and-parallel-pipelines.md) and [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md).

## How it works
The pipeline consists of four sequential stages: cell classification, prefix-sum computation, exact Vertex Buffer Object (VBO) allocation, and triangle generation [S1].

**Inputs and Outputs:**
*   **Input:** A 3D scalar volume grid of dimensions $D_x \times D_y \times D_z$. Scalar values are normalized to the range $[0, 1]$ using the dataset's minimum and maximum values [S1].
*   **Output:** A VBO containing position and normal data for the extracted isosurface.
*   **Parameters:** The isovalue $\tau$ is specified in the normalized range $[0, 1]$. Typical tested values are $0.35$, $0.50$, and $0.65$ [S1].

**Data Structures:**
1.  **Input Volume:** $D_x \times D_y \times D_z$ scalar values.
2.  **Count Buffer:** An array of size $D_x \times D_y \times D_z$ storing the number of vertices generated per voxel.
3.  **Offset Buffer:** An array of size $D_x \times D_y \times D_z$ storing the starting index in the output buffer for each voxel's vertices.
4.  **Output VBO:** A dynamically allocated buffer of size $N_{total} \times 3$ vertices, where $N_{total}$ is the sum of all counts.

**Steps:**

1.  **Cell Classification:**
    Each GPU thread processes one voxel cube. It samples the scalar values $V_i$ at the 8 vertices. It computes the 8-bit configuration index $C$:
    $$
    C = \sum_{i=0}^{7} \mathbb{I}(V_i < \tau) \cdot 2^i
    $$
    where $\mathbb{I}$ is the indicator function [S1, S2, unofficial].

2.  **Vertex Counting:**
    For the active voxel, the thread determines the number of vertices to be generated. Based on the `triangleTable[C]` from [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md), the number of triangles $T_C$ is known. Each triangle has 3 vertices. The thread writes $3 \times T_C$ to the **Count Buffer** at the index corresponding to its voxel [S1].

3.  **Prefix-Sum Computation:**
    An exclusive prefix-sum (scan) operation is performed on the **Count Buffer** to generate the **Offset Buffer**. The offset for a voxel is the sum of vertex counts of all preceding voxels. The total number of vertices $N_{total}$ is the final value of the scan [S1].

4.  **Exact VBO Allocation:**
    A buffer of size $N_{total} \times 3$ vertices is allocated. This ensures no overflow and no wasted space [S1].

5.  **Triangle Generation:**
    Each thread processes its voxel again. It computes the intersection points for the edges defined by `edgeTable[C]`. For an edge connecting vertices with values $v_1, v_2$ and positions $\mathbf{p}_1, \mathbf{p}_2$:
    $$
    \lambda = \frac{\tau - v_1}{v_2 - v_1}
    $$
    $$
    \mathbf{p} = \text{lerp}(\mathbf{p}_1, \mathbf{p}_2, \lambda)
    $$
    The thread looks up the triangle indices in `triangleTable[C]`. For each triangle, it writes the 3 intersection positions to the **Output VBO** at the base index given by the **Offset Buffer** for this voxel, plus the triangle's offset [S1].

## Subtopics

### [GPU Marching Cubes with Scan-Based Compaction](6632-gpu-marching-cubes-with-scan-based-compaction.md)
A GPU-accelerated Marching Cubes pipeline that classifies voxels, uses exclusive prefix sums to count active voxels and required vertices, compacts the voxel index array to remove empty voxels, and extracts the isosurface only for active voxels. It sets itself apart from naive parallel Marching Cubes by avoiding buffer overflow and dynamic memory allocation during geometry generation through a two-pass counting and compaction strategy, building on the [Capacity-Safe Marching Cubes Pipeline](4596-capacity-safe-marching-cubes-pipeline.md).

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N = D_x \times D_y \times D_z$ for classification and counting. The prefix sum is $O(N)$ with a small constant factor. Triangle generation is $O(M)$ where $M$ is the number of active voxels.
*   **Memory Complexity:** $O(N)$ for input volume, count buffer, and offset buffer. $O(M)$ for the output VBO. Peak VRAM usage includes all these buffers [S1].
*   **Measured Performance:**
    *   At $512^3$ resolution with isovalue $0.35$: 42.81 million vertices, 44.7 ms extraction time, 28.6 FPS rendering, 10.9 GB peak VRAM [S1].
    *   At $128^3$ resolution with isovalue $0.35$: 1.28 million vertices, 5.8 ms extraction time, 221.4 FPS rendering, 1.9 GB peak VRAM [S1].
*   **Strengths:** Prevents buffer overflow at high resolutions; exact memory allocation avoids waste; stable geometry generation [S1].
*   **Limitations:** Requires two passes (counting and generation); prefix sum adds overhead; peak VRAM is higher than single-pass methods due to intermediate buffers [S1].
*   **When to Use:** High-resolution volumes where buffer overflow is a risk; applications requiring stable and predictable memory usage [S1].
*   **When Not to Use:** Low-resolution volumes where fixed buffers are sufficient; memory-constrained environments where peak VRAM is critical [S1].

## Background
The method was proposed in the context of visualizing fusion plasma simulations [S1]. It addresses the limitations of fixed-capacity buffers which fail at high resolutions like $512^3$ [S1]. The evaluation was performed on an NVIDIA RTX 3090 GPU [S1].
