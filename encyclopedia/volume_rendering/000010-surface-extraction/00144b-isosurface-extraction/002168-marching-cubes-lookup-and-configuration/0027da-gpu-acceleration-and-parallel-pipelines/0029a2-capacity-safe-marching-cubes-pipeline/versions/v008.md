# Capacity-Safe Marching Cubes Pipeline

Also called: Proposed Framework, Two-pass exact-allocation strategy

## Overview
The Capacity-Safe Marching Cubes Pipeline is a GPU-accelerated isosurface extraction method that prevents buffer overflow by determining the exact vertex count before geometry generation [S1]. Unlike fixed-capacity baselines that reserve static buffers and risk failure at high resolutions, this method uses a two-pass approach: first computing counts and offsets, then allocating exact buffers and generating triangles [S1]. It builds on [GPU Acceleration and Parallel Pipelines](4136-gpu-acceleration-and-parallel-pipelines.md) by replacing dynamic or fixed-size output emission with a deterministic allocation strategy.

## How it works
The extraction process consists of four sequential stages: cell classification, prefix-sum computation, exact VBO (Vertex Buffer Object) allocation, and triangle generation [S1].

**Inputs and Outputs:**
*   **Input:** A 3D scalar volume grid $V$ of resolution $N_x \times N_y \times N_z$. Scalar values are normalized to the range $[0, 1]$ using the dataset's minimum and maximum values [S1].
*   **Output:** A Vertex Buffer Object (VBO) containing position and normal data for the extracted isosurface, and an index buffer (if indexed) or a flat vertex array [S1].

**Data Structures:**
1.  **Scalar Volume:** 3D array of floats, normalized to $[0, 1]$.
2.  **Count Buffers:**
    *   `voxel_active`: Boolean or integer array of size $N_x \times N_y \times N_z$, indicating if a voxel intersects the isosurface.
    *   `vertex_counts`: Integer array of size $N_x \times N_y \times N_z$, storing the number of vertices generated per voxel (0, 1, 2, or 3 for standard MC, potentially more for variants, but standard MC generates up to 3 triangles per voxel, each with 3 vertices, so max 9 vertices per voxel if not shared, but typically counted as unique vertices or triangle indices. The source notes "vertices", implying unique output vertices or triangle vertices. Given "42.81 million vertices" for 512^3, and max 3 triangles/voxel * 3 verts = 9, max possible is $512^3 \times 9 \approx 1.2$ billion. 42M is well within bounds. The buffer stores the count of vertices *generated* by that voxel's contribution to the final stream, likely before sharing optimization or simply the raw output count per voxel).
3.  **Offset Buffer:** Result of an exclusive prefix sum (scan) on `vertex_counts`, used to determine write offsets in the output buffer.

**Parameters:**
*   **Isovalue ($\tau$):** Specified in the normalized scalar range $[0, 1]$. Typical tested values are 0.35, 0.50, and 0.65 [S1].

**Steps:**

1.  **Cell Classification:**
    Each GPU thread processes one voxel. It computes the 8-bit case index $C$ based on the sign of the scalar values at the 8 corners relative to $\tau$. It determines if the voxel is active (intersects the isosurface) [Parent, S1].

2.  **Prefix-Sum Computation:**
    *   Compute `vertex_counts` for each active voxel. The number of vertices generated by a voxel depends on the number of triangles in its MC case (each triangle has 3 vertices). Let $T(C)$ be the number of triangles for case $C$. The vertex count for voxel $i$ is $3 \times T(C_i)$.
    *   Perform an exclusive prefix sum (scan) on the `vertex_counts` array to produce the `offsets` array. `offsets[i]` gives the starting index in the output buffer for the vertices generated by voxel $i$.

3.  **Exact VBO Allocation:**
    *   The total number of vertices $N_{verts}$ is the sum of all `vertex_counts` (or the last value in the inclusive scan).
    *   Allocate a GPU buffer of exact size $N_{verts} \times \text{sizeof(Vertex)}$ for positions and normals. This prevents overflow and avoids the memory waste of over-allocating [S1].

4.  **Triangle Generation:**
    *   Each thread processes an active voxel.
    *   It computes the intersection points $\mathbf{p}$ and normals $\mathbf{n}$ for the active edges using linear interpolation [Parent]:
        $$
        \mathbf{p} = \mathbf{p}_1 + \frac{\tau - V_1}{V_2 - V_1} (\mathbf{p}_2 - \mathbf{p}_1)
        $$
    *   It uses the `edgeTable` and `triangleTable` to determine which edges are active and how they form triangles [Parent].
    *   It writes the generated vertices to the output buffer at the offset specified by `offsets[i]` for the current voxel $i$.

**Pseudocode:**

```python
# Kernel 1: Classification and Counting
@compute_shader
def classify_and_count(thread_id: int, voxel_pos: vec3, scalar_volume: texture3d, isovalue: float):
    # Get 8 corner values
    values = [scalar_volume.sample(voxel_pos + corner_offset) for corner_offset in CORNER_OFFSETS]
    
    # Compute case index
    case_index = 0
    for i in range(8):
        if values[i] < isovalue:
            case_index |= (1 << i)
            
    # Determine if active
    is_active = case_index != 0 and case_index != 255
    
    # Determine vertex count for this voxel
    # Standard MC: 0 to 3 triangles per voxel. Each triangle has 3 vertices.
    # Note: In a raw output stream without shared vertex optimization, 
    # we count 3 vertices per triangle.
    num_triangles = TRIANGLE_TABLE[case_index].length # Number of triangles for this case
    vertex_count = num_triangles * 3
    
    # Write to count buffer
    vertex_counts[thread_id] = vertex_count
    
    # Write active flag if needed for subsequent passes or debugging
    # active_flags[thread_id] = is_active

# Kernel 2: Prefix Sum (Scan)
# This is typically done using a parallel scan algorithm (e.g., Blelloch scan)
# on the vertex_counts buffer to produce offsets.
# offsets[i] = sum(vertex_counts[0...i-1])

# Kernel 3: Geometry Generation
@compute_shader
def generate_geometry(thread_id: int, voxel_pos: vec3, scalar_volume: texture3d, isovalue: float, 
                      vertex_counts: buffer, offsets: buffer, output_positions: buffer, output_normals: buffer):
    
    # Get vertex count and offset for this voxel
    count = vertex_counts[thread_id]
    if count == 0:
        return
        
    base_offset = offsets[thread_id]
    
    # Get 8 corner values and positions
    values = [scalar_volume.sample(voxel_pos + corner_offset) for corner_offset in CORNER_OFFSETS]
    positions = [voxel_pos + corner_offset for corner_offset in CORNER_OFFSETS]
    
    # Compute case index
    case_index = 0
    for i in range(8):
        if values[i] < isovalue:
            case_index |= (1 << i)
            
    # Get triangles for this case
    triangles = TRIANGLE_TABLE[case_index]
    
    current_vert_idx = base_offset
    
    for triangle in triangles:
        for edge_idx in triangle:
            # Interpolate vertex on edge
            edge = EDGES[edge_idx]
            p1 = positions[edge[0]]
            p2 = positions[edge[1]]
            v1 = values[edge[0]]
            v2 = values[edge[1]]
            
            # Linear interpolation
            t = (isovalue - v1) / (v2 - v1)
            p = p1 + t * (p2 - p1)
            
            # Compute normal (gradient interpolation)
            # Normal n = gradient of scalar field at p
            # Approximated by interpolating corner gradients or computing central difference
            # For simplicity, assume a function compute_normal(p, scalar_volume) exists
            n = compute_normal(p, scalar_volume)
            
            # Write to output buffers
            output_positions[current_vert_idx] = p
            output_normals[current_vert_idx] = n
            current_vert_idx += 1
```

**Edge Cases and Pitfalls:**
*   **Buffer Overflow:** Using a fixed-capacity single-pass output buffer causes failure at high resolutions (e.g., $512^3$) because the generated output exceeds available buffer capacity, resulting in overwritten or missing vertex data and incomplete geometry [S1].
*   **Precision:** Scalar values must be normalized to $[0, 1]$ to ensure consistent isovalue interpretation across different datasets [S1].

## Subtopics

### [GPU Marching Cubes with Scan-Based Compaction](6632-gpu-marching-cubes-with-scan-based-compaction.md)
A GPU-accelerated Marching Cubes pipeline that classifies voxels, uses exclusive prefix sums to count active voxels and required vertices, compacts the voxel index array to remove empty voxels, and extracts the isosurface only for active voxels. It sets itself apart from naive parallel Marching Cubes by avoiding buffer overflow and dynamic memory allocation during geometry generation through a two-pass counting and compaction strategy, building on the [Capacity-Safe Marching Cubes Pipeline](4596-capacity-safe-marching-cubes-pipeline.md).

## Operating characteristics
*   **Time Complexity:** The method involves a constant-time classification per voxel, a linear-time prefix sum ($O(N)$ where $N$ is the number of voxels), and a constant-time geometry generation per active voxel. The total time is dominated by the prefix sum and memory bandwidth for large volumes.
*   **Memory Complexity:** Peak VRAM usage includes the input scalar volume, intermediate count and offset buffers, and the generated position and normal buffers [S1]. The exact allocation minimizes memory waste compared to fixed-capacity buffers.
*   **Measured Performance:**
    *   At $512^3$ resolution with isovalue 0.35, the method generates 42.81 million vertices in 44.7 ms with 10.9 GB peak VRAM usage, rendering at 28.6 FPS [S1].
    *   At $128^3$ resolution with isovalue 0.35, the method generates 1.28 million vertices in 5.8 ms with 1.9 GB peak VRAM usage, rendering at 221.4 FPS [S1].
    *   At $128^3$ resolution with isovalue 0.50, it generates 0.94 million vertices in 4.9 ms with 1.7 GB peak VRAM usage, rendering at 264.7 FPS [S1].
    *   At $128^3$ resolution with isovalue 0.65, it generates 0.61 million vertices in 4.1 ms with 1.6 GB peak VRAM usage, rendering at 312.5 FPS [S1].
*   **Strengths:** Stability at high resolutions; no buffer overflow; efficient memory usage due to exact allocation.
*   **Limitations:** Requires two passes (counting and generation); prefix sum computation adds overhead.
*   **When to Use:** When extracting isosurfaces from high-resolution volumes where buffer overflow is a concern, and interactive performance is required.
*   **When Not to Use:** For very small volumes where the overhead of the prefix sum is not justified, or when memory is extremely constrained and the overhead of intermediate buffers is prohibitive.

## Background
The method was proposed in the context of visualizing 3D plasma simulation data, specifically electromagnetic potential values from fusion plasma simulations [S1]. It was developed to address the limitations of fixed-capacity GPU Marching Cubes implementations that fail at high resolutions [S1]. The evaluation was performed on a workstation with an AMD Ryzen Threadripper PRO 3955WX CPU, 256 GB of system memory, and an NVIDIA RTX 3090 GPU with 24 GB of VRAM [S1].
