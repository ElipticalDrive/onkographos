# GPU Acceleration and Parallel Pipelines

Also called: GPU Marching Cubes, Compute Shader Marching Cubes, Parallel Isosurface Extraction

## Overview
GPU Acceleration and Parallel Pipelines refers to the family of techniques that map the voxel-wise, data-parallel nature of Marching Cubes to GPU architectures (Compute Shaders, OpenCL, or Geometry Shaders) to achieve real-time or near-real-time isosurface extraction [S1, S2, unofficial]. It solves the performance bottleneck of CPU-based immediate mode rendering by offloading the classification, interpolation, and triangle emission steps to thousands of parallel threads [S1, unofficial]. What sets this family apart from its siblings is the diversity of output management strategies: while some variants use fixed-capacity buffers with atomic counters or cleanup passes, others employ hierarchical structures like Histogram Pyramids or two-pass slab-based counting to ensure exact buffer allocation and crack-free boundaries [S1, S2, unofficial].

## Shared principles
The family relies on the precomputed data structures defined in [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md): the `edgeTable` (256-entry bitmask) and `triangleTable` (256x16 edge index array) [S1, Parent, unofficial].

**Parallel Dispatch:** The 3D grid of voxels is mapped to a 3D grid of GPU threads (or thread groups). Each thread (or group) is responsible for processing one voxel cube [S1, S2, unofficial]. The dispatch dimensions typically match the grid resolution $(N_x-1) \times (N_y-1) \times (N_z-1)$ [S1, S2, unofficial].

**Voxel Classification:** Each thread samples the scalar field values at the 8 corners of its assigned voxel. It computes the 8-bit case index (selector) by comparing these values against the isovalue $\tau$ [S1, S2, unofficial].

**Edge Interpolation:** For active edges (where `edgeTable[selector]` has the corresponding bit set), the thread computes the intersection point using linear interpolation:
$$
\mathbf{p} = \mathbf{p}_1 + \frac{\tau - V_1}{V_2 - V_1} (\mathbf{p}_2 - \mathbf{p}_1)
$$
where $V_1, V_2$ are the scalar values at corners $\mathbf{p}_1, \mathbf{p}_2$ [S1, S2, unofficial]. Normals are typically computed via gradient interpolation or finite differences [S1, S2, unofficial].

**Triangle Emission:** The thread looks up the `triangleTable[selector]` to determine which edges form triangles. It then emits these triangles to a shared output structure [S1, S2, unofficial].

**Output Management:** The core challenge of parallel Marching Cubes is managing the variable number of output triangles per voxel without race conditions or buffer overflows. Strategies include:
1.  **Atomic Counters:** Using a global atomic counter to reserve slots in a fixed-size buffer [S1, S2, unofficial].
2.  **Histogram Pyramids:** Using a hierarchical prefix-sum structure to compute exact offsets before writing [S1, unofficial].
3.  **Slab Partitioning:** Partitioning the grid into slabs to compute exact counts per slab, ensuring boundary consistency [S1, unofficial].
4.  **Append Buffers:** Using hardware-supported append buffers (e.g., `AppendStructuredBuffer`) that handle atomic allocation internally [S1, S2, unofficial].
5.  **Indirect Rendering:** Generating draw arguments on the GPU to avoid CPU-GPU synchronization stalls [S1, unofficial].

## Subtopics

### [Primal Grid Marching Cubes](1211-primal-grid-marching-cubes.md)
A GPU-accelerated technique that processes a 3D scalar volume grid using compute shaders to output a triangle mesh. It differs from CPU implementations by offloading voxel processing and triangle generation entirely to the GPU, and from other GPU variants by relying on a fixed-size output buffer managed by a global atomic counter and a subsequent cleanup pass, rather than hierarchical reduction or capacity-safe slab-based allocation. This method builds on [GPU Acceleration and Parallel Pipelines](4136-gpu-acceleration-and-parallel-pipelines.md) by mapping the primal grid directly to parallel thread groups.

### [GPU Marching Cubes with Histogram Pyramid](2317-gpu-marching-cubes-with-histogram-pyramid.md)
This method extracts isosurfaces from volumetric scalar fields on the GPU using OpenCL and OpenGL, employing a Histogram Pyramid (HP) to count triangles per voxel and compactly store vertex data in a Vertex Buffer Object (VBO) without atomic operations or sorting. It builds on the lookup tables and parallel dispatch principles defined in [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md) and [GPU Acceleration and Parallel Pipelines](4136-gpu-acceleration-and-parallel-pipelines.md).

### [Marching Cubes with Gaussian Deformation](3769-marching-cubes-with-gaussian-deformation.md)
This method extracts an isosurface from a scalar field using a Geometry Shader pipeline, applying a Gaussian-based deformation to the resulting mesh vertices along a user-defined force vector. It differs from standard GPU Marching Cubes implementations by integrating the deformation directly into the geometry shader's vertex emission phase, allowing for real-time, dynamic modification of the terrain or mesh shape without CPU-side geometry regeneration. Unlike methods that use append buffers or histogram pyramids for output management, this variant typically relies on the geometry shader's primitive stream, often coupled with specific matrix transformations for rendering.

### [GPU Marching Cubes Terrain Pipeline with Indirect Rendering](3803-gpu-marching-cubes-terrain-pipeline-with-indirect-rendering.md)
This method generates terrain meshes from voxel data on the GPU using Marching Cubes, utilizing indirect rendering to allow the GPU to generate and render the mesh directly without CPU readback, avoiding performance stalls. It manages multiple LOD levels and renders generated triangles via indirect draw calls to minimize CPU-GPU synchronization overhead. Unlike CPU implementations or earlier GPU versions that required readback, this approach keeps RenderThread time low (~1.5ms) by eliminating CPU mesh copy operations.

### [GPU Marching Cubes with Atomic Counter Emission](4082-gpu-marching-cubes-with-atomic-counter-emission.md)
This method is a real-time GPU-based isosurface extraction technique that generates a mesh from a scalar density field by dispatching one compute thread per grid cell. It distinguishes itself from sibling methods by avoiding prefix sums or histogram pyramids for output management; instead, it reserves vertex slots via atomic addition directly on indirect draw arguments and renders the result using `drawIndirect` with vertex pulling. This approach minimizes synchronization overhead and CPU-GPU readback, making it suitable for real-time applications like fluid simulation.

### [Capacity-safe slab-based Marching Cubes](4595-capacity-safe-slab-based-marching-cubes.md)
Capacity-safe slab-based Marching Cubes is a GPU-accelerated isosurface extraction pipeline that partitions the z-axis into slabs to compute exact vertex counts per slab via a two-pass strategy (classify/scan then generate), allowing for exact buffer allocation and crack-free surfaces at slab boundaries. It differs from standard Marching Cubes by resolving topological discontinuities and holes via boundary-consistent slab processing, and differs from HistoPyramids/Flying Edges by specializing counting/compaction for tightly coupled extraction, rendering, and engine integration.

### [Capacity-Safe Marching Cubes Pipeline](4596-capacity-safe-marching-cubes-pipeline.md)
The Capacity-Safe Marching Cubes Pipeline is a GPU-accelerated isosurface extraction method that eliminates buffer overflow by determining the exact vertex count before geometry generation. It sets itself apart from fixed-capacity single-pass approaches by using a two-pass strategy: first computing counts and offsets, then allocating exact buffers and generating triangles. This ensures stability at high resolutions where naive parallel implementations would fail due to insufficient buffer capacity.

### [GPU Marching Cubes (Compute Shader)](4687-gpu-marching-cubes-compute-shader.md)
This method extracts an isosurface from a 3D scalar field by mapping the Marching Cubes algorithm to a GPU compute shader, processing voxels in parallel. It differs from CPU-based implementations by leveraging hardware parallelism for voxel classification and triangle generation, and from geometry shader approaches by using explicit compute kernels with append buffers for output management. It builds on [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md) for the topological logic and [GPU Acceleration and Parallel Pipelines](4136-gpu-acceleration-and-parallel-pipelines.md) for the dispatch and data access patterns.

### GPU Marching Cubes (Potential Triangles)
**Definition:** Renders the isosurface on the GPU by enumerating all possible triangles per voxel in a single draw call, letting the vertex shader compute and discard inactive triangles [S1, unofficial].
**Steps:** Calculate `numVoxels = (gridSize - 1)^3`. Set `maxTrisPerVoxel = 5`, `vertsPerTri = 3`. Compute `vertexCount = numVoxels * maxTrisPerVoxel * vertsPerTri`. Allocate `Uint32Array` of size `vertexCount * 3`. Fill indices with nested loops: for each voxel `v`, triangle `t` (0-4), vertex `k` (0-2), store `(v, t, k)`. Create VAO and buffer data with `gl.STATIC_DRAW`. Enable vertex attributes 0, 1, 2. Set `vertexAttribIPointer` with stride 12, offsets 0, 4, 8, type `UNSIGNED_INT` [S1, unofficial].
**Parameters:** `isoLevel`: isosurface threshold, default 80.0 [S1, unofficial].
**Layout:** Index buffer layout: 3 `UNSIGNED_INT` components per entry, stride 12 bytes. Component 0: voxel index. Component 1: triangle index (0-4). Component 2: vertex index (0-2) [S1, unofficial].
**Comparison:** Uses a single static index buffer enumerating all potential triangles instead of dynamic per-frame triangle lists, reducing CPU-GPU transfer overhead [S1, unofficial].
**Usage:** Implemented in `GpuMarchingCubesRenderer` class [S1, unofficial].

### GPU Scalar Field Generation (Tiled Texture)
**Definition:** Computes the scalar field values on the GPU using a fragment shader over a full-screen quad, outputting to a tiled 2D texture [S1, unofficial].
**Steps:** Determine tiling based on `gridSize`: 16->4x4, 32->8x4, 64->8x8, 128->8x16. Calculate `texWidth = tilesX * gridSize`, `texHeight = tilesY * gridSize`. Create `R32F` texture with `CLAMP_TO_EDGE` wrapping and `NEAREST` filtering. Bind framebuffer with `tiledTexture` as `COLOR_ATTACHMENT0`. Set viewport to `texWidth`, `texHeight`. Pass blob parameters as `Float32Array` of size `numBlobs * 4`. Compute blob params on CPU: `pos.x = sin(i + 1.26 * time * (1.03 + 0.5*cos(0.21*i))) * 0.27 + 0.5`, `pos.y = abs(cos(i + 1.12 * time * cos(1.22 + 0.1424*i))) * 0.77`, `pos.z = cos(i + 1.32 * time * 0.1*sin((0.92 + 0.53 * i))) * 0.27 + 0.5`, `strength = 1.2 / ((sqrt(numBlobs)- 1) / 4 + 1)` [S1, unofficial].
**Parameters:** `tilesX`, `tilesY`: number of tiles in X and Y directions, determined by `gridSize`. `texWidth`, `texHeight`: dimensions of the tiled texture [S1, unofficial].
**Usage:** Implemented in `GpuFieldGenerator` class [S1, unofficial].

### Incremental Chunk Re-meshing
**Definition:** A technique to keep deformation fast and seamless by only re-meshing chunks affected by edits, rather than the entire world [S2, unofficial].
**Steps:** Divide the world into chunks. When a dig or build operation modifies the density field, mark only the affected chunks as 'dirty'. In the `LateUpdate` phase of the frame, iterate through dirty chunks and re-mesh them using Marching Cubes [S2, unofficial].

## Background
The application of GPU acceleration to Marching Cubes emerged in the mid-2000s as hardware parallelism became sufficient to handle the data-parallel nature of volume rendering. Early implementations utilized Geometry Shaders to transform point primitives (voxel centers) into triangle streams, leveraging the GPU's ability to generate geometry on-the-fly [S1, S2, unofficial]. As Compute Shaders became standard, more sophisticated pipelines were developed, focusing on efficient memory management and avoiding CPU-GPU synchronization bottlenecks through techniques like indirect rendering and atomic counters [S1, S2, unofficial]. The family has since expanded to include capacity-safe methods that guarantee buffer integrity and crack-free surfaces, essential for real-time applications like fluid simulation and terrain generation [S1, S2, unofficial].
