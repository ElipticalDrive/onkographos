# GPU Acceleration and Parallel Pipelines

Also called: Parallel Marching Cubes, GPU Marching Cubes, Compute Shader MC

## Overview
This family encompasses methods that offload the isosurface extraction workload from the CPU to the GPU or parallel processing units to achieve real-time performance on large scalar volumes. It solves the computational bottleneck of voxel classification and triangle generation by leveraging massive parallelism. It sets itself apart from CPU-based implementations (like [CPU Immediate Mode Marching Cubes](2463-cpu-immediate-mode-marching-cubes.md)) by utilizing compute shaders, atomic counters, or hierarchical data structures (like HistoPyramids) to manage memory and output compaction without CPU-GPU synchronization overhead.

## Shared principles
The family relies on the precomputed data structures defined in [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md): the `edgeTable` (12-bit bitmask) and `triangleTable` (256x16 array).

**Parallel Execution Model:**
*   **Voxel-to-Thread Mapping:** Typically, each GPU thread (or thread group) processes one voxel cube. The thread index maps to the 3D grid coordinate $(i, j, k)$.
*   **Boundary Checks:** Threads must check if their assigned voxel is within the valid grid bounds $[0, N_x-2] \times [0, N_y-2] \times [0, N_z-2]$.
*   **Case Index Calculation:** Each thread computes the 8-bit case index $C$ based on the scalar values at its 8 vertices relative to the isovalue $\tau$.
*   **Early Exit:** If $C=0$ or $C=255$, the thread terminates immediately, generating no geometry.

**Output Management:**
Since the number of triangles per voxel varies (0 to 5), parallel writes to a shared output buffer require synchronization. Common strategies include:
1.  **Atomic Counters:** Using atomic increment operations to allocate unique indices in a pre-allocated buffer [S1, unofficial].
2.  **Two-Pass Counting:** First pass counts triangles per voxel; second pass uses a prefix sum (scan) to compute exact offsets for direct writes without atomics [S1, S2, unofficial][S3].
3.  **Append Buffers:** Using hardware-supported append buffers that automatically handle indexing [S1, unofficial].

**Ambiguity Handling:**
Standard implementations use the fixed triangulation from the lookup table. Cases 46, 47, 98, 99, 210, 213, 214, 215 remain ambiguous and may cause cracks if adjacent voxels resolve them inconsistently [Lookup Table and Ambiguity Handling].

## Subtopics

### [Primal Grid Marching Cubes](1211-primal-grid-marching-cubes.md)
A GPU-accelerated technique using a compute shader to process voxels simultaneously. It distinguishes itself by using a fixed-size buffer with a global atomic counter and a cleanup pass to manage memory, ensuring deterministic usage. Unlike direct volume rendering, it produces an explicit geometric representation.

### [GPU Marching Cubes with Histogram Pyramid](2317-gpu-marching-cubes-with-histogram-pyramid.md)
Uses a hierarchical histogram structure (HistoPyramid) to count and locate surface triangles without atomic operations or sorting. It builds on [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md) and [GPU Acceleration and Parallel Pipelines](4136-gpu-acceleration-and-parallel-pipelines.md). Unlike [GPU Marching Cubes (Compute Shader)](4687-gpu-marching-cubes-compute-shader.md) which often relies on atomics or sorting for compaction, this method uses the HistoPyramid to deterministically map voxel contributions to a compact Vertex Buffer Object (VBO).

### [CPU Immediate Mode Marching Cubes](2463-cpu-immediate-mode-marching-cubes.md)
A classic CPU-based surface extraction method that generates mesh vertices and normals in immediate mode, rendering them directly via WebGL draw calls without storing a persistent mesh buffer. It serves as a reference implementation for comparison against GPU-accelerated variants, solving the problem of real-time isosurface visualization for scalar fields (such as metaballs) on the CPU. It differs from sibling methods like [GPU Marching Cubes (Compute Shader)](4687-gpu-marching-cubes-compute-shader.md) by performing all geometry generation and field computation on the CPU, relying on immediate-mode rendering APIs rather than persistent buffers or compute shaders.

### [Marching Cubes Job Scheduling](4446-marching-cubes-job-scheduling.md)
A parallel processing strategy that decomposes a 3D volume into spatial chunks and assigns the extraction of each chunk to independent computational jobs (typically GPU compute shaders or CPU worker threads). It solves the scalability problem of extracting isosurfaces from large volumes by enabling concurrent processing, thereby reducing total extraction time. It differs from single-threaded approaches by managing data dependencies and output buffering through job handles and atomic counters, and from simple grid-based parallelism by operating on discrete, manageable chunks rather than a monolithic global grid.

### [Capacity-safe slab-based Marching Cubes](4595-capacity-safe-slab-based-marching-cubes.md)
This method is a GPU-accelerated isosurface extraction pipeline that partitions the z-axis into slabs and uses a two-pass counting/exact allocation strategy to prevent output-buffer overflow and slab-boundary omissions. It differs from standard Marching Cubes by resolving topological discontinuities via boundary-consistent inclusive slab indexing, and differs from HistoPyramids/Flying Edges by specializing counting/compaction for tightly coupled extraction and rendering.

### [Capacity-Safe Marching Cubes Pipeline](4596-capacity-safe-marching-cubes-pipeline.md)
A GPU-based isosurface extraction method that avoids buffer overflow by determining the exact vertex count before geometry generation, using a two-pass approach: first computing counts/offsets, then allocating exact buffers and generating triangles. It sets itself apart from naive parallel Marching Cubes by avoiding buffer overflow and dynamic memory allocation during geometry generation through a two-pass counting and compaction strategy, building on [GPU Acceleration and Parallel Pipelines](4136-gpu-acceleration-and-parallel-pipelines.md). Unlike fixed-capacity baselines that reserve static buffers, this method determines the exact vertex count before generation, ensuring stability and preventing buffer overflow without excessive static reservation.

### [GPU Marching Cubes (Compute Shader)](4687-gpu-marching-cubes-compute-shader.md)
A GPU-based implementation of the Marching Cubes algorithm that offloads isosurface extraction from the CPU to a compute shader, typically within a framework like Unity. It solves the performance bottleneck of CPU-based volume rendering by parallelizing voxel processing across the GPU. It differs from CPU immediate mode implementations by using append buffers and indirect draw calls to handle variable triangle counts per voxel without CPU-GPU synchronization overhead.

### [Parallel Marching Cubes](12211-parallel-marching-cubes.md)
Parallel Marching Cubes is a parallel implementation of the Marching Cubes algorithm designed to compute isosurfaces of huge datasets that cannot fit entirely into a single machine's memory. It solves the memory bottleneck of traditional sequential extraction by dividing the 3D volume into slices along the k-direction, allowing only a few slices to reside in physical memory at any time. Unlike commercial packages that assume the entire volume fits in RAM, this method uses a piecewise slice strategy where at least two slices fit into physical memory, enabling the processing of datasets with millions of grid values.

### GPU Scalar Field Generation (Tiled Texture)
- **Definition:** Computes the scalar field values on the GPU using a fragment shader over a full-screen quad, outputting to a tiled 2D texture [S1, unofficial].
- **Steps:** Determine tiling based on `gridSize`: 16->4x4, 32->8x4, 64->8x8, 128->8x16. Calculate `texWidth = tilesX * gridSize`, `texHeight = tilesY * gridSize`. Create an R32F texture with `CLAMP_TO_EDGE` wrapping and `NEAREST` filtering. Bind framebuffer with `tiledTexture` as `COLOR_ATTACHMENT0`. Set viewport to `texWidth`, `texHeight`. Pass blob parameters as `Float32Array` of size `numBlobs * 4`. Compute blob params on CPU: `pos.x = sin(i + 1.26 * time * (1.03 + 0.5*cos(0.21*i))) * 0.27 + 0.5`, `pos.y = abs(cos(i + 1.12 * time * cos(1.22 + 0.1424*i))) * 0.77`, `pos.z = cos(i + 1.32 * time * 0.1*sin((0.92 + 0.53 * i))) * 0.27 + 0.5`, `strength = 1.2 / ((sqrt(numBlobs)- 1) / 4 + 1)` [S1, unofficial].
- **Parameters:** `tilesX`, `tilesY` (determined by `gridSize`); `texWidth`, `texHeight` [S1, unofficial].
- **Usage:** Implemented in `GpuFieldGenerator` class [S1, unofficial].

### Incremental Chunk Re-meshing
- **Definition:** A technique to keep deformation fast and seamless by only re-meshing chunks affected by edits, rather than the entire world [S2, unofficial].
- **Steps:** Divide the world into chunks. When a dig or build operation modifies the density field, mark only the affected chunks as 'dirty'. In the `LateUpdate` phase of the frame, iterate through dirty chunks and re-mesh them using Marching Cubes [S2, unofficial].

### Adaptive Hull Subdivision for Linearization Error
- **Steps:** Approximate the error $E_T$ for a given triangle $T$ via numerical integration over its surface. Subdivide $T$ based on the magnitude of $E_T$ to ensure error stays below a given threshold. This is done via hardware tessellation when rendering the hull mesh [S3].
- **Formula:** The linearization error at a point $p$ on the deformed surface is $E(p) = \| \mathbf{p} - D(\widetilde{D^{-1}}(\mathbf{p})) \|$, where $\widetilde{D^{-1}}$ is the approximate inverse from the hull. The error over the surface of a deformed space triangle $T$ is the integral of $E(p)$ over $T$: $E_T = \int_T E(\mathbf{p}) \, d\mathbf{p}$ [S3].
- **Pitfall:** Increasing grid resolution in Marching Cubes to reduce triangle size scales poorly (8x more cells for double resolution) and requires regenerating the hull every frame [S3].
- **Comparison:** Unlike methods that linearize deformation over volumetric space, this method only linearizes on a 2D manifold (the hull surface), allowing easier quantification of error [S3].

## Background
The shift from CPU to GPU for Marching Cubes began with the availability of programmable shaders and compute units. Early implementations utilized fragment shaders for field generation and vertex shaders for geometry, evolving into dedicated compute shaders (e.g., in Unity or CUDA/OpenCL) for general-purpose parallel processing. The primary challenge addressed has been the variable output size of Marching Cubes, which complicates parallel memory allocation. Solutions evolved from simple atomic counters to sophisticated hierarchical structures like HistoPyramids and slab-based prefix sums to achieve buffer-safe, high-throughput extraction.
