# Marching Cubes 3
## Overview
Marching Cubes 3 is a specific implementation variant of the Marching Cubes algorithm for extracting polygonal meshes from 3D scalar fields [S1, unofficial]. It builds on the standard 256-entry lookup table topology but is distinguished by its explicit C++/Python binding interface that passes array bounds, value accessors, and output containers directly [S1, unofficial]. Unlike generic wrappers, it exposes the core extraction loop through a typed function signature expecting `double` precision and explicit dimension counts [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** `lower` and `upper` bounds, `numx`, `numy`, `numz` dimensions, a value accessor `PyArrayToCFunc(arr)` mapping indices to `double` values, an `isovalue` threshold, and mutable containers `vertices` and `polygons` [S1, unofficial].
*   **Outputs:** Populated `vertices` (3D coordinates) and `polygons` (triangle indices) vectors [S1, unofficial].

**Data Structures:**
The method expects a contiguous 3D array layout. `PyArrayToCFunc` abstracts memory layout and type conversion, providing a uniform `double get_value(int x, int y, int z)` interface [S1, unofficial]. `vertices` and `polygons` are dynamic arrays/vectors passed by reference [S1, unofficial].

**Steps:**
1.  **Validation:** Verify the input data is 3-dimensional [S1, unofficial].
2.  **Shape Extraction:** Extract the shape to determine `numx`, `numy`, and `numz` [S1, unofficial].
3.  **Bounds Initialization:** Compute or accept the `lower` and `upper` bounds of the scalar field [S1, unofficial].
4.  **Vector Initialization:** Initialize empty dynamic arrays (vectors) for `vertices` and `polygons` [S1, unofficial].
5.  **Core Extraction:** Invoke `mc::marching_cubes3<double>(lower, upper, numx, numy, numz, PyArrayToCFunc(arr), isovalue, vertices, polygons)` [S1, unofficial].

**Pseudocode:**
```python

    vertices = []
    polygons = []
```

## Subtopics

### [Marching Cubes with Lewiner 2003 Ambiguity Resolution](2292-marching-cubes-with-lewiner-2003-ambiguity-resolution.md)
This variant resolves topological ambiguities (Ambiguous face and Internal ambiguity) present in the original 1987 algorithm to guarantee a manifold surface. It tests faces and interior points of the cube to disambiguate cases where the standard 256-entry table yields non-manifold geometry or cracks. It is chosen when topological correctness is critical, at the cost of larger lookup tables and increased computational overhead.

### [Ray-Unit Parallel Marching Cubes](5169-ray-unit-parallel-marching-cubes.md)
Ray-Unit Parallel Marching Cubes (rupMC) is an enhanced version designed for CPU/GPU heterogeneous architectures. It replaces the standard cubic voxel with a "ray unit" to ensure each edge intersection is calculated exactly once, eliminating redundant computations on shared edges. It embeds topological relationships directly into triangle composition using unique intersection indices and parallelizes I/O via OpenMPI and computation via CUDA. It is chosen for large-scale datasets requiring efficient parallel processing and explicit topological connectivity.

### SurfaceExtractorMC
SurfaceExtractorMC is a Marching Cubes extraction class built over an `Image3` structure, utilizing the standard Marching Cubes 256-entry table [S2, unofficial]. It replaces the upstream pure virtual `Extract` method with `extractVoxel(level, perturb, F)` which returns a tuple `{valid, mesh}` and `extract(level, perturb)` [S2, unofficial]. Only the canonical query keeps the plain name `extract` [S2, unofficial]. It is used within the `gtengine-js` ported surface extractor framework [S2, unofficial].
