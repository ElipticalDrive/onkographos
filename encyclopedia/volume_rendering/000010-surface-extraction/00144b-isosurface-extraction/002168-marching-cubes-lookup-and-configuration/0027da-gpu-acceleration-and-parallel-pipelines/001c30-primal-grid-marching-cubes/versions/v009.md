# Primal Grid Marching Cubes

Also called: Compute Shader Marching Cubes, Marching Cube

## Overview
Primal Grid Marching Cubes is a GPU-accelerated isosurface extraction technique that processes a 3D scalar volume grid using a compute shader to output a triangle mesh [S1, S2, unofficial][S3, S4, unofficial]. It distinguishes itself from CPU-based implementations by leveraging massive parallelism to process voxels simultaneously, utilizing a fixed-size buffer with a global atomic counter and a cleanup pass to manage memory, ensuring deterministic memory usage and GPU-friendly parallelism [S1, unofficial][S2, unofficial]. Unlike direct volume rendering, it produces an explicit geometric representation suitable for standard rasterization or ray tracing [S3, S20, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D scalar field (volume data) stored in a texture or structured buffer, an isovalue threshold, grid dimensions, and a transformation scale [S1, S3, S4, unofficial].
*   **Output:** A triangular mesh consisting of vertex positions, normals, and indices, stored in raw byte-address buffers [S1, S3, unofficial].

**Data Structures:**
1.  **Triangle Table (`TriangleTable`):** A structured buffer of 256 entries. Each entry is a `uint2` (or equivalent 64-bit value) storing the triangle configuration for one of the 256 possible cube states. The first 8 edge indices are packed into the lower 32 bits of the first `uint`, and edges 8-15 (if any) into the second `uint` [S1, S2, unofficial]. The table is derived from Paul Bourke's geometry reference [S2, unofficial].
2.  **Vertex Buffer:** A `RWByteAddressBuffer` storing vertex positions (`float3`) and normals (`float3`) sequentially. Each vertex occupies 24 bytes (12 bytes for position, 12 bytes for normal) [S1, S4, unofficial].
3.  **Index Buffer:** A `RWByteAddressBuffer` storing triangle indices. Each triangle consists of 3 `uint32` indices, occupying 12 bytes [S1, S4, unofficial].
4.  **Counter:** A `ComputeBuffer` of type Counter, size 1 `uint`, used to atomically allocate triangle slots in the vertex and index buffers [S1, S4, unofficial].

**Algorithm Steps:**
The algorithm is typically executed in two compute shader passes or kernels:

1.  **Initialization:**
    *   Allocate the `TriangleTable` buffer (256 entries) and the `Counter` buffer (1 uint) [S1, S4, unofficial].
    *   Allocate the `VertexBuffer` and `IndexBuffer` with a capacity of `MaxTriangle` triangles. `MaxTriangle` is a user-defined budget to prevent buffer overflow [S1, S4, unofficial].
    *   Initialize the mesh with vertex attributes: Position (Float32, 3) and Normal (Float32, 3), and index format UInt32 [S1, S4, unofficial].

2.  **Mesh Reconstruction Kernel:**
    *   Launch with a thread group size, e.g., `[4, 4, 4]`, where each thread processes one voxel cube at grid coordinate `id` [S1, S4, unofficial].
    *   **Boundary Check:** If any component of `id + 1` is greater than or equal to the grid dimensions `Dims`, return immediately [S1, S4, unofficial].
    *   **Sample Vertices:** For each vertex index $i \in [0, 7]$, calculate the grid coordinate `id + CubeVertex(i)`. `CubeVertex(i)` maps the bit index $i$ to 3D coordinates: $x = i \& 1 \oplus (i \& 2) >> 1$, $y = (i \& 2) >> 1$, $z = (i \& 4) >> 2$ [S1, S4, unofficial]. Sample the scalar value and gradient at these 8 vertices. Store results in `float4 samples[8]`, where `xyz` is the gradient and `w` is the scalar value [S1, S4, unofficial].
    *   **Calculate Selector:** Compute the 8-bit case index (selector) $C$. For each vertex $i$, if `samples[i].w < Isovalue`, set bit $i$ in $C$: $C = \sum_{i=0}^{7} (\text{samples}[i].w < \text{Isovalue}) \ll i$ [S1, S4, unofficial].
    *   **Edge Intersection:** If $C == 0$ or $C == 255$ (all vertices on one side of the isovalue), return immediately [S1, S4, unofficial].
    *   **Retrieve Configuration:** Look up the triangle configuration from `TriangleTable[C]` [S1, S4, unofficial].
    *   **Generate Triangles:** Iterate through the configuration data in steps of 3. For each triplet of edge indices $(e_1, e_2, e_3)$:
        *   If $e_1 == 15$ (or -1, depending on table encoding), the configuration is exhausted; break [S1, S2, S4, unofficial].
        *   For each edge index $e$, determine the two vertex indices $v_a, v_b$ using `EdgeVertexPair(e)` [S1, S4, unofficial].
        *   Calculate the interpolation parameter: $\text{param} = \frac{\text{Isovalue} - \text{samples}[v_a].w}{\text{samples}[v_b].w - \text{samples}[v_a].w}$ [S1, S4, unofficial].
        *   Compute the intersection point: $\mathbf{p} = \text{TransformPoint}(\text{lerp}(\mathbf{v}_a, \mathbf{v}_b, \text{param}))$ [S1, S4, unofficial].
        *   Compute the normal: $\mathbf{n} = -\text{normalize}(\text{lerp}(\text{samples}[v_a].\text{xyz}, \text{samples}[v_b].\text{xyz}, \text{param}))$ [S1, S4, unofficial].
        *   *Note:* Some implementations use a fixed midpoint `(verts[e0] + verts[e1]) * 0.5f` if scalar values are binary, but linear interpolation is standard for accuracy [S4, unofficial].
    *   **Atomic Allocation:** Atomically increment the `Counter` to get the current triangle index count `count`. If `count >= MaxTriangle`, return to prevent overflow [S1, S4, unofficial].
    *   **Write Output:** Calculate vertex index `vidx = count * 3`. Write the three intersection points and their normals to the `VertexBuffer` at offsets `vidx*24`, `(vidx+1)*24`, `(vidx+2)*24`. Write the indices `vidx`, `vidx+1`, `vidx+2` to the `IndexBuffer` at offset `vidx*12` [S1, S4, unofficial].

3.  **Cleanup Pass:**
    *   After the reconstruction dispatch, run a `ClearUnused` kernel (e.g., with `[64, 1, 1]` threads) [S1, S4, unofficial].
    *   This kernel atomically increments the counter until it reaches `MaxTriangle`, writing zeroed vertices and indices to the remaining buffer space to ensure clean data for the mesh [S1, S4, unofficial].

4.  **Rendering:**
    *   Draw the triangular mesh using vertex and fragment shaders, binding the `VertexBuffer` and `IndexBuffer` [S1, S3, S4, unofficial].

**Pseudocode:**

                       TriangleTable: buffer[256], Voxels: buffer, 
                       VertexBuffer: RWBuffer, IndexBuffer: RWBuffer, 
                       Counter: Counter, MaxTriangle: int):

    if any(id + 1 >= Dims):
        return

    # 2. Sample 8 Vertices
    samples = array[8] of float4 # xyz: gradient, w: scalar value
    for i in 0..7:
        # Map bit index i to 3D corner offset
        x_bit = i & 1
        y_bit = (i & 2) >> 1
        z_bit = (i & 4) >> 2
        # CubeVertex: x^y, y, z
        corner_offset = uint3(x_bit ^ y_bit, y_bit, z_bit)
        grid_pos = id + corner_offset
        
        # Sample value and gradient
        # VoxelValueWithGradient returns float4(grad_x, grad_y, grad_z, value)
        samples[i] = VoxelValueWithGradient(grid_pos, Voxels, Dims)

    # 5. Retrieve Triangle Configuration
    tri_data = TriangleTable[selector] # uint2 containing edge indices

    # 6. Process Triangles
    count = Counter.Increment()
    if count >= MaxTriangle:

    count = Counter.Increment()
    if count >= MaxTriangle:
        return
    vidx = count * 3
    
    # Extract 3 edge indices at a time from tri_data
    # Assuming tri_data is packed such that we can iterate 5 triangles max
    for t in 0..4:

        if e1 == -1: break

        WriteVertex(VertexBuffer, vidx, p1, n1)
        WriteIndex(IndexBuffer, vidx, vidx)
        vidx += 1
        
        # Process e2

        WriteVertex(VertexBuffer, vidx, p2, n2)
        WriteIndex(IndexBuffer, vidx, vidx)
        vidx += 1

        WriteVertex(VertexBuffer, vidx, p3, n3)
        WriteIndex(IndexBuffer, vidx, vidx)
        vidx += 1

def ComputeIntersection(edge_idx, samples, id, Scale, Dims, Isovalue):
    v1, v2 = EdgeVertexPair(edge_idx)
    corner1 = id + CubeVertex(v1)
    corner2 = id + CubeVertex(v2)
    pos1 = TransformPoint(corner1, Scale, Dims)
    pos2 = TransformPoint(corner2, Scale, Dims)
    
    val1 = samples[v1].w
    val2 = samples[v2].w
    param = (Isovalue - val1) / (val2 - val1)
    
    pos = lerp(pos1, pos2, param)
    grad1 = samples[v1].xyz
    grad2 = samples[v2].xyz
    normal = -normalize(lerp(grad1, grad2, param))
    
    return pos, normal

def TransformPoint(grid_coord, Scale, Dims):
    # Example from S1: (p + 0.5 - Dims / 2) * Scale
    # Or simpler: grid_coord * Scale
    return grid_coord * Scale

**Parameters:**
*   `Isovalue`: The threshold value for isosurface extraction. Vertices with values below this are considered inside [S1, S3, S4, unofficial].
*   `Scale`: A scalar factor used to transform grid coordinates to object space [S1, S4, unofficial].
*   `MaxTriangle`: The maximum number of triangles allowed in the output mesh, used to prevent buffer overflow [S1, S4, unofficial].
*   `Dims`: The dimensions of the 3D grid (x, y, z) [S1, S4, unofficial].

**Edge Cases and Pitfalls:**
*   **Ambiguity:** Cases 46, 47, 98, 99, 210, 213, 214, 215 contain saddle points where the topology is ambiguous. The standard LUT uses a fixed triangulation, which can cause cracks or holes if adjacent voxels resolve the ambiguity differently [10327-lookup-table-and-ambiguity-handling].
*   **Buffer Overflow:** If the mesh exceeds `MaxTriangle`, triangles are dropped. A cleanup pass ensures unused buffer space is zeroed [S1, S4, unofficial].
*   **Midpoint Interpolation:** Some naive implementations use fixed midpoints for vertex positions, assuming binary scalar values. This leads to inaccurate surfaces for continuous fields [S4, unofficial].
*   **Shared Memory:** Shared memory is often rejected in this implementation because while adjacent threads share four common vertices, all vertices in a block only share one vertex, making shared memory redundant for the entire block [S4, unofficial].

## Subtopics

### [Marching Cubes](774-marching-cubes.md)
Marching Cubes is the foundational isosurface extraction algorithm that converts a 3D scalar field into a polygonal mesh by classifying voxel corners and using a lookup table for triangulation. It is distinguished by its reliance on a precomputed 256-entry lookup table based on linear interpolation, which is computationally efficient but can suffer from topological ambiguities and non-manifold artifacts. See [Marching Cubes](774-marching-cubes.md).

### [Dual Marching Cubes](906-dual-marching-cubes.md)
Dual Marching Cubes (DMC) generates topological manifold surfaces by unifying standard MC fragments into polygonal patches and constructing a dual mesh. Unlike standard MC, it ensures manifold connectivity by associating dual vertices with lattice edges shared by four cells. It differs from Primal Grid MC by operating on a dual grid structure. See [Dual Marching Cubes](906-dual-marching-cubes.md).

### [GPU Marching Cubes with Lookup Tables](3690-gpu-marching-cubes-with-lookup-tables.md)
This variant explicitly emphasizes the use of pre-computed lookup tables stored in 2D textures or structured buffers to determine edge intersections and triangle configurations. It generates a triangle mesh from a 3D scalar field using compute shaders, processing each voxel independently. See [GPU Marching Cubes with Lookup Tables](3690-gpu-marching-cubes-with-lookup-tables.md).

### CPU Marching Cubes Fallback
A CPU-based fallback for Marching Cubes in hybrid implementations (e.g., CuMCubes). It samples a function at grid points to create a density grid on the CPU, then transfers the grid to the GPU to call the GPU Marching Cubes implementation [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N^3)$ for a 3D grid of resolution $N \times N \times N$, as each voxel is processed in parallel [S4, unofficial].
*   **Memory Complexity:** $O(N^3)$ for the geometry buffer, as each grid cell outputs a fixed maximum of 15 vertices (5 triangles) [S4, unofficial]. The vertex and index buffers are allocated with a fixed `MaxTriangle` budget [S1, S4, unofficial].
*   **Performance:** Leverages massive parallelism on the GPU via compute shaders (e.g., CUDA, DirectX Compute) [S1, S2, S3, S4, unofficial]. Performance scales with the number of GPU cores and memory bandwidth.
*   **Strengths:** Deterministic memory usage, GPU-friendly parallelism, no dynamic allocation overhead during kernel execution [S1, unofficial].
*   **Limitations:** Fixed buffer size requires estimation of `MaxTriangle`; topological ambiguities in specific LUT cases can cause artifacts [S1, S4, unofficial][10327-lookup-table-and-ambiguity-handling].
*   **When to Use:** Real-time isosurface extraction from volumetric data or implicit functions where performance is critical [S1, S2, S3, S4, unofficial].
*   **When Not to Use:** When topological correctness is paramount and ambiguity handling is required without post-processing, or when memory is extremely constrained and `MaxTriangle` cannot be estimated [S1, S4, unofficial].

## Background
Primal Grid Marching Cubes is a GPU adaptation of the classic Marching Cubes algorithm, originally described by Lorensen and Cline [S1, S3, S4, unofficial]. The lookup tables used are sourced from Paul Bourke's 'Polygonise' geometry reference [S1, S2, unofficial]. The specific GPU implementations described here (e.g., ComputeMarchingCubes, CuMCubes) were developed to accelerate the algorithm for real-time applications and differentiable rendering pipelines [S1, S2, unofficial].
