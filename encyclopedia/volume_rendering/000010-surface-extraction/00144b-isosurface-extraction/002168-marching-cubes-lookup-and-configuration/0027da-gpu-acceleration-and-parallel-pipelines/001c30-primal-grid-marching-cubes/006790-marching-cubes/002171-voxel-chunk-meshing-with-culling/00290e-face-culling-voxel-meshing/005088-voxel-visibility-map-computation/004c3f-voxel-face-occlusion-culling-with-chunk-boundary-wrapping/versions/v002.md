# Voxel Face Occlusion Culling with Chunk Boundary Wrapping


## Overview
This method computes the occlusion status for all six faces of every voxel within a chunk, determining which faces are visible for mesh generation by checking the existence of solid neighbors. It distinguishes itself by explicitly handling chunk boundaries through coordinate wrapping, allowing local chunk processing to correctly account for adjacent chunks without requiring global scene knowledge or complex boundary condition logic. Unlike sibling methods that may propagate state across large distances, this approach relies on immediate neighbor checks with wrapped coordinates [S1, unofficial].

## How it works
**Inputs and Outputs**
- **Input**: 
  - `DIM`: A 3D integer vector (`IVec3`) representing the chunk dimensions $(X, Y, Z)$.
  - `kind`: A data structure mapping voxel coordinates to their material/occupancy kind (e.g., solid, empty).
  - `neighboorhood`: An array of optional pointers/references to neighbor chunk storage, indexed by chunk side (e.g., left, right, top, bottom, front, back).
- **Output**: 
  - `faces_occlusion`: A 3D map where each entry corresponds to a voxel in the chunk and stores a 6-bit flag (or similar structure) indicating whether each of the 6 faces is occluded by a neighbor.

**Data Structures**
- `IVec3`: A 3D integer vector with fields $x, y, z$.
- `ChunkVoxel`: A structure representing a voxel coordinate within a chunk, convertible from/to `IVec3`.
- `FacesOcclusion`: A structure holding 6 boolean flags, one for each side (e.g., +X, -X, +Y, -Y, +Z, -Z).
- `ChunkSide`: An enumeration representing the 6 sides of a chunk.

**Steps**
1. Initialize `faces_occlusion` for the chunk.
2. Iterate through every voxel coordinate $(x, z, y)$ in the chunk, where $0 \le x < X$, $0 \le z < Z$, and $0 \le y < Y$.
3. For each voxel, retrieve its `kind` from the `kind` map.
4. If the voxel is empty (i.e., `kind` is `None` or equivalent):
   - Mark all 6 faces as fully occluded.
   - Store this state in `faces_occlusion`.
5. If the voxel is solid (i.e., `kind` exists):
   - Initialize a `FacesOcclusion` structure with default values (all faces potentially visible).
   - For each of the 6 sides (directions):
     a. Compute the neighbor voxel coordinate: $\vec{n} = \vec{v} + \vec{d}$, where $\vec{v}$ is the current voxel coordinate and $\vec{d}$ is the direction vector for the side.
     b. Determine the `neighbor_kind`:
        i. If $\vec{n}$ is within the current chunk bounds (i.e., can be converted to a valid `ChunkVoxel`):
           - Retrieve `neighbor_kind` from `kind` using $\vec{n}$.
        ii. If $\vec{n}$ is outside the current chunk:
           - Identify the `chunk_side` corresponding to the direction $\vec{d}$.
           - If a neighbor chunk exists for this side (i.e., `neighboorhood[chunk_side]` is not `None`):
             - Wrap the coordinate using Euclidean remainder: $\vec{n}_{wrapped} = \text{math::euclid\_rem}(\vec{n}, \text{DIM})$.
             - Convert $\vec{n}_{wrapped}$ to a valid `ChunkVoxel`.
             - Retrieve `neighbor_kind` from the neighbor chunk's `kind` map using $\vec{n}_{wrapped}$.
           - If no neighbor chunk exists for this side, skip this side (treat as occluded or undefined, depending on implementation; the source code returns early from the fold if no neighbor kind is found, effectively leaving the face flag unset or default, but logically it implies no solid neighbor).
        iii. If no neighbor kind is found (empty space or out of bounds with no chunk), the face is not occluded by a solid neighbor.
     c. Set the occlusion flag for the current side: if `neighbor_kind` is not `None` (i.e., a solid neighbor exists), mark the face as occluded.
   - Store the resulting `FacesOcclusion` in `faces_occlusion` for the current voxel.

**Edge Cases and Pitfalls**
- **Boundary Wrapping**: Correctly handling boundary voxels requires `math::euclid_rem` (or equivalent) to ensure coordinates wrap correctly into the neighbor chunk. Failure to use Euclidean remainder (e.g., using modulo with negative numbers) can lead to incorrect neighbor lookups [S1, unofficial].
- **Missing Neighbor Chunks**: If a neighbor chunk is missing for a boundary side, the method must handle this gracefully. The source code skips the side, which may leave the face flag in a default state. This should be documented as "face not occluded by a known solid neighbor" or explicitly marked as occluded if the absence of a chunk implies empty space [S1, unofficial].
- **Empty Voxels**: Empty voxels are marked as fully occluded, which may be counter-intuitive if "occluded" means "not visible". However, in the context of mesh generation, empty voxels do not contribute faces, so this is a valid optimization [S1, unofficial].

## Subtopics

### [Integer Rasterization for Occlusion Masks](16081-integer-rasterization-for-occlusion-masks.md)
A method for calculating occlusion between cells by rasterizing boundary polygons onto 2D domains using integer arithmetic and exact AABB unions. It replaces continuous analytical clipping constraints with grid-level precision, generating 2D occlusion masks for cell boundaries without sub-pixel accuracy. This approach is distinct from sibling methods by relying on deterministic integer Bresenham rasterization and exact 2D rectangle unions rather than floating-point polygon clipping or 3D projection.

## Operating characteristics
- **Time Complexity**: $O(N)$, where $N$ is the number of voxels in the chunk ($X \times Y \times Z$). Each voxel is processed once, and for each voxel, 6 neighbor checks are performed, each taking $O(1)$ time.
- **Memory Complexity**: $O(N)$ for storing the `faces_occlusion` map. The `kind` map and `neighboorhood` array are inputs and not counted in the method's additional memory usage.
- **Measured Performance**: Not given in the sources.
- **Scaling**: Scales linearly with chunk size. Larger chunks may benefit from parallelization (e.g., processing voxels in parallel), but the dependency on neighbor chunks requires careful synchronization if chunks are processed concurrently.
- **Strengths**: Simple to implement, efficient for local chunk processing, handles boundaries correctly via wrapping.
- **Limitations**: Requires access to neighbor chunks, which may not be available in all scenarios (e.g., streaming data). The method assumes a regular grid structure.
- **When to Use**: When generating meshes for voxel chunks in a larger world, and neighbor chunks are available or can be loaded on demand.
- **When Not to Use**: When memory is extremely constrained and storing the `faces_occlusion` map is prohibitive, or when neighbor chunks are not available and cannot be loaded.
