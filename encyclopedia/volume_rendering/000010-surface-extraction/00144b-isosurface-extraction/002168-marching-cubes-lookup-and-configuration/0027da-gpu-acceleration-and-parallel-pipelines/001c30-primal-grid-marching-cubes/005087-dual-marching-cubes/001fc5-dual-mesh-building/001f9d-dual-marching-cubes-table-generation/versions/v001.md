# Dual Marching Cubes Table Generation

Also called: Dual Marching Cubes Edge Encoding, DualMC table builder, DualMC table generation

## Overview
Dual Marching Cubes Table Generation is the offline algorithm that constructs the lookup table used by the Dual Marching Cubes (DualMC) surface extraction method. It maps each of the 256 possible voxel corner configurations (inside/outside) to a set of dual point edge masks that define the extracted surface geometry [S1, S2, unofficial]. Unlike standard Marching Cubes, which outputs triangles directly from edge intersections, DualMC generates a dual mesh where vertices are placed on the edges of the voxel grid. This table generation process determines which edges are intersected by the isosurface for every possible configuration, encoding these intersections as bitmasks to facilitate efficient parallel mesh construction on the GPU [S1, S2, unofficial]. It builds on [Dual Mesh Building](1423-dual-mesh-building.md), which consumes these masks to create the final indexed mesh.

## How it works
The algorithm generates a static lookup table by iterating through all 256 possible cube configurations. For each configuration, it identifies connected subgraphs of "inside" corners and determines the edges that connect these inside corners to "outside" corners. These edges form the boundaries of the dual surface patches.

### Inputs and Outputs
*   **Input:** None (the algorithm is deterministic and static). It relies on the geometric definition of a cube's corners and edges.
*   **Output:** A flat array `dualPointsList` of size $256 \times 4$. Each row $i$ (where $i \in [0, 255]$) contains up to 4 `uint32_t` values representing edge masks for the dual points generated by configuration $i$. Unused entries in a row are set to 0.

### Data Structures
1.  **Corner Edge Mapping (`cornerEdges`):** A static table of size $8 \times 3$. It maps each of the 8 cube corners (indexed by Morton code $c \in [0, 7]$) to the edge codes of the three adjacent edges in the x, y, and z directions.
    *   The edge codes are defined by the enum `DMCEdgeCode`, where `EDGE0` to `EDGE11` correspond to powers of 2 from $2^0$ to $2^{11}$ (i.e., $1, 2, 4, \dots, 2048$) [S1, S2, unofficial].
    *   The coordinate system is defined as:
        ```
              y
              |
              |
              |
              0-----x
             /
            /
           z
        ```
    *   The specific mapping for corner $c$ to edges $(e_x, e_y, e_z)$ is:
        *   Corner 0: `{EDGE0, EDGE8, EDGE3}`
        *   Corner 1: `{EDGE0, EDGE9, EDGE1}`
        *   Corner 2: `{EDGE2, EDGE8, EDGE7}`
        *   Corner 3: `{EDGE4, EDGE9, EDGE5}`
        *   Corner 4: `{EDGE2, EDGE11, EDGE3}`
        *   Corner 5: `{EDGE2, EDGE10, EDGE1}`
        *   Corner 6: `{EDGE6, EDGE11, EDGE7}`
        *   Corner 7: `{EDGE6, EDGE10, EDGE5}` [S1, unofficial]

2.  **Cube Corner Code:** A helper structure representing a single corner of the cube. It stores the Morton code index and provides a method `getMask()` which returns a `uint32_t` with the bit at position $c$ set (i.e., $1 \ll c$).

3.  **Dual Points List:** The output table. In C++, this is often declared as `int32_t const DualMC<T>::dualPointsList[256][4]` or `glm::uint dualPointsList[256][4]` [S1, S2, unofficial].

### Algorithm Steps
1.  **Initialize Output:** Allocate `dualPointsList` as a vector or array of size $256 \times 4$.
2.  **Iterate Configurations:** Loop through all cube configuration indices `i` from 0 to 255. Let `cubeMask` be the integer `i`.
3.  **Handle Empty/Full Cases:** If `cubeMask == 0` (all outside) or `cubeMask == 255` (all inside), there are no intersection edges. Set all 4 entries in `dualPointsList[i]` to 0 and continue to the next iteration [S1, S2, unofficial].
4.  **Handle Ambiguous Configurations:** If `cubeMask` is 126, 189, 219, or 231, invert the mask: `cubeMask ^= 0x000000ffu`. This is because the standard traversal merges two original Marching Cubes patches into one for these cases. The correct patches are identical to the results of the inverted configurations [S1, unofficial].
5.  **Initialize Traversal State:**
    *   `processedCornersMask = 0`
    *   `numDualPoints = 0`
    *   `cornerStack` (empty stack of `CubeCornerCode`)
    *   Pointer `cubeDualPointCodes` to `dualPointsList[i]`
6.  **Find Connected Subgraphs:** Loop through all 8 corners `c` from 0 to 7:
    *   Create `startCorner` with index `c`.
    *   Check if `startCorner` has already been visited: if `(startCorner.getMask() & processedCornersMask) != 0`, mark it as visited (`processedCornersMask |= startCorner.getMask()`) and continue.
    *   Check if the corner is outside: if `(cubeMask & startCorner.getMask()) == 0`, mark it as visited and continue.
    *   **Start New Subgraph:**
        *   Push `startCorner` onto `cornerStack`.
        *   Initialize `connectedCornersMask = startCorner.getMask()`.
        *   Initialize `dualPointCode = 0`.
        *   **Traverse Subgraph:** While `cornerStack` is not empty:
            *   Pop `currentCorner` from `cornerStack`.
            *   For each of the 3 adjacent edges of `currentCorner` (using `cornerEdges[currentCorner.index][dir]` for `dir` in $\{0, 1, 2\}$):
                *   Let `edgeCode` be the edge mask.
                *   Determine the `neighborCorner` index. The neighbor is reached by flipping the bit corresponding to the direction. Specifically, if the edge connects corner $c$ to $c'$, and the edge code is $E$, the neighbor's mask is $c' = c \oplus 1$ (in terms of Morton bit position relative to the edge axis). *Note: The exact neighbor calculation depends on the edge definition. In the source, the traversal implicitly finds neighbors by checking if the edge connects an inside corner to an outside corner.*
                *   More precisely, for each edge adjacent to `currentCorner`:
                    *   Identify the `neighborCorner` index.
                    *   If the `neighborCorner` is classified as **outside** (i.e., `(cubeMask & neighborCorner.getMask()) == 0`):
                        *   Add `edgeCode` to `dualPointCode` (bitwise OR).
                    *   If the `neighborCorner` is classified as **inside** and has not been visited in this subgraph:
                        *   Add `neighborCorner` to `connectedCornersMask`.
                        *   Push `neighborCorner` onto `cornerStack`.
            *   Mark `currentCorner` as visited in `processedCornersMask`.
        *   **Store Result:** Set `cubeDualPointCodes[numDualPoints] = dualPointCode`. Increment `numDualPoints`.
7.  **Finalize Row:** Set any remaining entries in `dualPointsList[i]` from index `numDualPoints` to 3 to 0.

                current_mask = 1 << current_c

### Parameters and Edge Cases
*   **Corner Edge Mapping:** The `cornerEdges` table is critical. Any error in this mapping will result in incorrect dual points. The edge codes must be consistent with the Morton code ordering of corners [S1, unofficial].
*   **Ambiguous Configurations:** Configurations 126, 189, 219, and 231 are handled by inverting the mask. This relies on the topological symmetry that the dual mesh generated by the inverted configuration is identical to the correct dual mesh for the ambiguous case [S1, unofficial].
*   **Precision:** The algorithm uses integer bitmasks, so there are no floating-point precision issues during table generation.
*   **Boundaries:** The table is static and covers all 256 cases. No boundary checks are needed during generation.

## Subtopics

### Dual Marching Cubes Edge Lookup Table
A variant of the lookup table structure used in some Dual Marching Cubes implementations. It contains 232 entries (indexed 0 to 231), where each entry consists of four fields. The first two fields are bitmasks of edges (EDGE0-EDGE11) representing the active edges for the case, and the last two fields are always zero. This structure is a compact representation of the edge configurations for the 232 non-trivial cases (excluding the all-inside and all-outside cases which are often handled separately or implicitly) [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** The table generation is an offline, static process. It iterates through 256 configurations, and for each, performs a constant-time traversal of at most 8 corners and 12 edges. The total time is $O(1)$ relative to the input data size, but depends on the fixed constant of 256 cases.
*   **Memory Complexity:** The output table is fixed at $256 \times 4 \times 4$ bytes = 4 KB (assuming `uint32_t`). This is negligible.
*   **Performance:** The generation is extremely fast, taking milliseconds on modern hardware. It is typically run once at application startup or precomputed and embedded in the binary.
*   **Strengths:** The bitmask-based approach allows for very efficient runtime lookup and bitwise operations on the GPU. The handling of ambiguous configurations via inversion simplifies the runtime logic.
*   **Limitations:** The table is specific to the Dual Marching Cubes topology. It cannot be easily adapted for other isosurface extraction methods without regeneration. The reliance on the `cornerEdges` mapping requires careful verification.

## Background
Dual Marching Cubes is a surface extraction method that generates a dual mesh, placing vertices on the edges of the voxel grid. The table generation algorithm was developed as part of the DualMC project by Dominik Wodniok [S1, unofficial]. It was designed to provide a robust and efficient way to handle the complex topology of isosurface extraction, particularly in the context of GPU-based volume rendering. The method addresses the ambiguities and topological issues present in standard Marching Cubes by working in the dual space. The implementation is available in the `gentables` application of the DualMC repository [S1, unofficial].
