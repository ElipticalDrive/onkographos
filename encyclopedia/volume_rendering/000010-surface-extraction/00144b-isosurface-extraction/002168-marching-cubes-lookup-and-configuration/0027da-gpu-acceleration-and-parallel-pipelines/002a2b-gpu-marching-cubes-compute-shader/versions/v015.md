# GPU Marching Cubes (Compute Shader)
Also called: Marching Cubes GPU, Unity Marching Cubes Compute Shader

## Overview
A GPU-based implementation of the Marching Cubes algorithm that offloads isosurface extraction from the CPU to a compute shader, typically within a framework like Unity [S1, unofficial]. It solves the performance bottleneck of CPU-based volume rendering by parallelizing voxel processing across the GPU [S1, unofficial]. It differs from CPU immediate mode implementations by using append buffers and indirect draw calls to handle variable triangle counts per voxel without CPU-GPU synchronization overhead [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D scalar field (density texture) of resolution $N \times N \times N$, an isovalue $I$, and the Marching Cubes lookup tables (`edgeTable`, `triangleTable`) embedded in the shader [S1, unofficial].
*   **Output:** A mesh representing the isosurface, generated as a stream of triangles [S1, unofficial].

**Data Structures:**
1.  **Append Vertex Buffer (`appendVertexBuffer`):** A `ComputeBuffer` of type `Append`.
    *   **Capacity:** $(N-1) \times (N-1) \times (N-1) \times 5$ elements [S1, unofficial]. This accounts for the maximum 5 triangles per voxel [Lookup Table and Ambiguity Handling].
    *   **Element Size:** 18 bytes per element. Each element represents one triangle, defined by 3 vertices. Each vertex has 2 attributes (position `float3`, normal `float3`), totaling 6 floats ($6 \times 4$ bytes = 24 bytes) or potentially packed. The source specifies `sizeof(float) * 18`, implying a specific packing or attribute set (e.g., position only, or specific shader requirements) [S1, unofficial]. *Note: The source code comment says "3 triangles * 3 vertices * 2 floats per vertex attribute * 2 attributes" which equals 36, but the allocation is 18. The struct definition says `Triangle` contains 3 `Vertex` structs, each with `float3 vPosition` and `float3 vNormal`. This is 6 floats = 24 bytes. The source text contains a contradiction regarding the byte size (18 vs 24). We follow the explicit allocation code: `sizeof(float) * 18` [S1, unofficial].*
2.  **Argument Buffer (`argBuffer`):** A `ComputeBuffer` of type `IndirectArguments`.
    *   **Size:** 4 integers (16 bytes) [S1, unofficial].
    *   **Layout:** `[vertexCount, instanceCount, startVertex, startInstance]` [S1, unofficial].

**Numbered Steps:**
1.  **Initialization:** Locate the compute shader kernel named "MarchingCubes" [S1, unofficial].
2.  **Buffer Allocation:**
    *   Allocate `appendVertexBuffer` with capacity $(N-1)^3 \times 5$ and element size 18 bytes [S1, unofficial].
    *   Allocate `argBuffer` with 4 integers [S1, unofficial].
3.  **Parameter Setup:**
    *   Set `_gridSize` to $N$ [S1, unofficial].
    *   Set `_isoLevel` to the threshold (default 0.5) [S1, unofficial].
    *   Bind the input density texture (e.g., `Texture3D`) [S1, unofficial].
    *   Bind `appendVertexBuffer` to the shader's `triangleRW` buffer [S1, unofficial].
4.  **Reset Counter:** Call `appendVertexBuffer.SetCounterValue(0)` to clear the append buffer count from previous frames [S1, unofficial].
5.  **Dispatch:** Dispatch the compute shader kernel with thread groups sized $(N/8, N/8, N/8)$, assuming 8x8x8 threads per group [S1, unofficial].
6.  **Read Count:**
    *   Initialize `argBuffer` with `{0, 1, 0, 0}` [S1, unofficial].
    *   Use `ComputeBuffer.CopyCount` to copy the append buffer's current count to `argBuffer` at offset 0 [S1, unofficial].
    *   Read back the count from `argBuffer` to the CPU [S1, unofficial].
7.  **Adjust Arguments:**
    *   Let $V$ be the read vertex count. The total index count for triangles is $V \times 3$ (assuming 3 indices per triangle) [S1, unofficial].
    *   Update `argBuffer` with the new vertex/index count [S1, unofficial].
8.  **Draw:**
    *   Bind the material and the `appendVertexBuffer` to the shader's `triangles` buffer [S1, unofficial].
    *   Call `Graphics.DrawProceduralIndirect` with `MeshTopology.Triangles` and the `argBuffer` [S1, unofficial].

**Parameters:**
*   `Resolution` ($N$): Grid resolution. Determines buffer sizes and dispatch dimensions [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Hardware Support:** The implementation assumes DX11 hardware. Mobile support is uncertain [S1, unofficial].
*   **Density Generation:** The example generates the density field on the CPU, which is a bottleneck. Real applications should use `RenderTexture` instead of `Texture3D` [S1, unofficial].
*   **Ambiguity:** The standard LUT is used, which may cause topological ambiguities (cracks/holes) in cases 46, 47, 98, 99, 210, 213, 214, 215 if adjacent voxels resolve differently [Lookup Table and Ambiguity Handling].

## Operating characteristics
*   **Time Complexity:** $O(N^3)$ for processing all voxels, parallelized across GPU threads [S1, unofficial].
*   **Memory Complexity:** $O(N^3)$ for the input texture and output buffer capacity [S1, unofficial].
*   **Performance:** Offloads computation from CPU to GPU, enabling real-time extraction for moderate resolutions [S1, unofficial].
*   **Strengths:** High parallelism, no CPU-GPU sync during extraction (using append buffers) [S1, unofficial].
*   **Limitations:** Fixed maximum buffer size (waste if few triangles), DX11 dependency, CPU density generation bottleneck in the example [S1, unofficial].
*   **When to use:** Real-time isosurface extraction in Unity/DX11 environments [S1, unofficial].
*   **When not to use:** Mobile platforms (uncertain support), or when density generation is the bottleneck and cannot be moved to GPU [S1, unofficial].

## Background
This implementation was developed for Unity 5.6, potentially compatible with older versions [S1, unofficial]. It relies on the algorithm and lookup tables by Paul Bourke [S1, unofficial]. Gradient normals calculation is based on work from "MCImproved" [S1, unofficial]. The specific codebase was contributed by Pavel Kouril and Vilém Otte [S1, unofficial].
