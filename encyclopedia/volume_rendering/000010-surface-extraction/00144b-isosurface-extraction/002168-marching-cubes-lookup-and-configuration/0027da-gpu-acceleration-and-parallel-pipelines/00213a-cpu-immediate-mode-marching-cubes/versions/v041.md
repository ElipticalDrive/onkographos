# CPU Immediate Mode Marching Cubes

Also called: CPU Immediate Sim, Immediate Mode Marching Cubes, Legacy Marching Cubes

## Overview
CPU Immediate Mode Marching Cubes is a classic CPU-based surface extraction method that generates mesh vertices and normals and renders them directly via WebGL draw calls without storing a persistent mesh buffer in GPU memory [S1, unofficial]. It differs from GPU-accelerated variants by performing all scalar field computation and geometry generation on the CPU, relying on immediate-mode batching to minimize draw calls [S1, unofficial]. This approach serves as a reference implementation and allows for easy comparison with GPU pipelines, though it suffers from CPU bottlenecks at high resolutions or high blob counts [S1, unofficial].

## How it works
The method operates in three phases: field generation, marching cubes extraction, and immediate rendering. It builds on the precomputed data structures defined in [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md).

### Inputs and Outputs
*   **Inputs:**
    *   3D scalar field grid of size $N_x \times N_y \times N_z$.
    *   Isosurface threshold $\tau$.
    *   List of metaballs (or other scalar field sources) with positions and radii.
    *   WebGL context and shader program.
*   **Outputs:**
    *   Rendered mesh geometry (triangles) on the screen.
    *   No persistent mesh data structure is retained after the frame.

### Data Structures
The implementation uses typed arrays to store vertex attributes for batching. The maximum number of vertices per batch is `maxCount` = 4096 [S1, unofficial].

*   `posArray`: `Float32Array` of size `maxCount * 3`. Stores vertex positions $(x, y, z)$.
*   `normalArray`: `Float32Array` of size `maxCount * 3`. Stores vertex normals $(nx, ny, nz)$.
*   `uvArray`: `Float32Array` of size `maxCount * 2`. Stores UV coordinates (optional).
*   `colorArray`: `Float32Array` of size `maxCount * 4`. Stores vertex colors (optional).
*   `count`: Integer tracking the number of vertices currently in the batch.
*   `hasPos`, `hasNormal`, `hasUV`, `hasColor`: Boolean flags indicating which attributes are populated.

### Field Generation
For each voxel in the 3D grid, the scalar value is computed by accumulating contributions from all metaballs and a floor term [S1, unofficial]. For a voxel at grid coordinate $(i, j, k)$, the scalar value $V(i,j,k)$ is:

$$ V(i,j,k) = \sum_{b \in \text{blobs}} \frac{r_b^2}{\| \mathbf{p}_{voxel} - \mathbf{p}_b \|^2} + V_{\text{floor}} $$

where $\mathbf{p}_{voxel}$ is the world position of the voxel center, $\mathbf{p}_b$ is the position of metaball $b$, and $r_b$ is its radius. This step is optimized by culling blobs that do not influence the current voxel's region [S1, unofficial].

### Marching Cubes Extraction
For each cube in the grid:
1.  Compute the 8-bit case index $C$ by comparing the scalar values at the 8 vertices to the isovalue $\tau$.
2.  If $C=0$ or $C=255$, skip the cube (no intersection).
3.  Use `edgeTable` and `triangleTable` from [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md) to determine which edges are intersected and the topology of the generated triangles.
4.  For each intersected edge, interpolate the vertex position and normal.
5.  Add the resulting vertices to the batch buffers.

### Immediate Rendering (Batching)
The rendering phase batches geometry to reduce draw calls. The process is managed by a primitive batching system [S1, unofficial]:

1.  **Begin Primitive Batching:** Set primitive type (e.g., `TRIANGLES`), calculate primitive size (3 for triangles), store program reference, reset `count` to 0, and reset attribute flags (`hasPos`, `hasNormal`, etc.) to false.
2.  **Add Vertex Position:** Store $x, y, z$ into `posArray` at indices `[count*3 + 0]`, `[count*3 + 1]`, `[count*3 + 2]`. Set `hasPos = true`.
3.  **Add Vertex Normal:** Store $nx, ny, nz$ into `normalArray` at indices `[count*3]`, `[count*3 + 1]`, `[count*3 + 2]`. Set `hasNormal = true`.
4.  **Add Triangle:** Copy positions from `posArray` at offsets $o_1, o_2, o_3$ and normals from `normalArray` at offsets $o_1, o_2, o_3$ into `posArray` and `normalArray` starting at index `count*3`. Increment `count` by 3.
    *   **Overflow Check:** If `count >= maxCount - 3`, call `draw()` to flush the buffer before adding the triangle.
5.  **Advance Vertex Count:** Increment `count`. If `count >= maxCount - 3` and `count` is divisible by `primsize`, call `draw()` to flush the buffer.
6.  **Flush and Render:**
    *   If `count == 0`, return.
    *   Zero out remaining `posArray` entries from `count*3` to length.
    *   Bind buffers for any enabled attributes using `gl.bufferData` with `DYNAMIC_DRAW`.
    *   Enable vertex attribute arrays and set pointers.
    *   Call `gl.drawArrays` with the primitive type, offset 0, and count.
    *   Reset `count` to 0.

### Edge Cases and Pitfalls
*   **Buffer Overflow:** The code checks if `count >= maxCount - 3` before drawing to ensure space for a triangle (3 vertices). If exceeded, it flushes immediately [S1, unofficial].
*   **Ambiguity:** Standard implementations use the fixed triangulation from the lookup table. Cases 46, 47, 98, 99, 210, 213, 214, 215 remain ambiguous and may cause cracks if adjacent voxels resolve them inconsistently [Lookup Table and Ambiguity Handling].
*   **Performance:** Limited by CPU bottlenecks at high resolutions or blob counts [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N_x N_y N_z \cdot B)$ for field generation, where $B$ is the number of blobs. $O(N_x N_y N_z)$ for marching cubes extraction.
*   **Memory Complexity:** $O(N_x N_y N_z)$ for the scalar field. $O(1)$ for the mesh buffer (fixed size `maxCount`).
*   **Measured Performance:** Limited performance at high resolutions or blob counts due to CPU bottlenecks [S1, unofficial].
*   **Strengths:** Simple implementation, serves as a reference, minimal GPU memory usage for mesh data.
*   **Limitations:** Poor scalability with resolution and blob count, CPU-bound.
*   **When to use:** Reference implementation, low-resolution scenes, educational purposes.
*   **When not to use:** High-resolution scenes, real-time applications with many objects.

## Background
The CPU Immediate Mode Marching Cubes implementation is inspired by Greggman's metaballs demo [S1, unofficial]. It uses classic Marching Cubes algorithm and tables from Paul Bourke [S1, unofficial]. The project is part of the WebGL2-GPU-Marching-Cubes repository by 3merillon [S1, unofficial].
