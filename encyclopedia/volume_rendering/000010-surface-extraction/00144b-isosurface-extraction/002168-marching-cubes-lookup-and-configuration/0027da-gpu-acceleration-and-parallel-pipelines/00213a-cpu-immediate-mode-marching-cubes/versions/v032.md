# CPU Immediate Mode Marching Cubes

Also called: CPU Immediate Sim, Immediate Mode Marching Cubes, Legacy Marching Cubes

## Overview
CPU Immediate Mode Marching Cubes is a classic CPU-based surface extraction method that generates mesh vertices and normals in immediate mode, rendering them directly via WebGL draw calls without storing a persistent mesh buffer [S1, unofficial]. It builds on the precomputed data structures defined in [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md), specifically the `edgeTable` and `triangleTable`. Unlike GPU-accelerated variants that use atomic counters or append buffers for parallel dispatch, this method processes voxels sequentially on the CPU and batches geometry for rendering [S1, unofficial]. It serves as a reference implementation and for performance comparison, but is limited by CPU bottlenecks at high resolutions or high blob counts [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D scalar field grid (voxels), isosurface threshold, and precomputed Marching Cubes lookup tables (`edgeTable`, `triangleTable`) from [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md).
*   **Output:** Rendered triangles via WebGL `drawArrays` calls. No persistent mesh object is created in memory.

**Data Structures:**
The implementation uses a class `ImmSim` with the following buffers and arrays [S1, unofficial]:
*   `posBuf`, `normalBuf`, `uvBuf`, `colorBuf`: WebGLBuffer objects.
*   `posArray`: `Float32Array` of size `maxCount * 3`. Stores vertex positions $(x, y, z)$.
*   `normalArray`: `Float32Array` of size `maxCount * 3`. Stores vertex normals $(nx, ny, nz)$.
*   `uvArray`: `Float32Array` of size `maxCount * 2`. Stores UV coordinates.
*   `colorArray`: `Float32Array` of size `maxCount * 4`. Stores vertex colors.
*   `maxCount`: Integer, typically 4096 [S1, unofficial]. This defines the capacity of the immediate mode buffer.
*   `count`: Integer, tracks the number of vertices currently in the buffer.
*   `hasPos`, `hasNormal`, `hasUV`, `hasColor`: Boolean flags indicating which attributes are enabled for the current batch.

**Numbered Steps:**

1.  **Field Generation:** For each voxel in the 3D grid, compute the scalar field value $f(x,y,z)$ by accumulating contributions from all metaballs (or sources) and a floor term [S1, unofficial].
2.  **Marching Cubes Extraction:** For each voxel cube:
    a. Determine the cube index by comparing the 8 corner scalar values to the isosurface threshold.
    b. Use the `edgeTable` to identify which edges of the cube are intersected by the isosurface.
    c. Use the `triangleTable` to determine the topology of the triangles formed by these intersections.
    d. For each triangle defined by the `triangleTable`, interpolate the vertex positions and normals at the edge intersections.
3.  **Primitive Batching Initialization:** Before processing a batch of voxels (or at the start of a frame):
    a. Set `prim` to the primitive type (e.g., `TRIANGLES`).
    b. Calculate `primsize` (3 for triangles, 2 for lines, 1 for points).
    c. Store program reference.
    d. Reset `count` to 0.
    e. Reset `hasPos`, `hasNormal`, `hasUV`, `hasColor` flags to `false`.
4.  **Vertex Addition:** For each vertex of a generated triangle:
    a. **Add Position:** Store $x, y, z$ into `posArray` at indices `[count*3 + 0]`, `[count*3 + 1]`, `[count*3 + 2]`. Set `hasPos = true`.
    b. **Add Normal:** Store $nx, ny, nz$ into `normalArray` at indices `[count*3]`, `[count*3 + 1]`, `[count*3 + 2]`. Set `hasNormal = true`.
    c. (Optional) Add UV and Color similarly if enabled.
5.  **Triangle Emission and Buffer Management:** For each triangle (3 vertices):
    a. Copy positions from the interpolated values into `posArray` starting at `count*3`.
    b. Copy normals into `normalArray` starting at `count*3`.
    c. Increment `count` by 3.
    d. **Overflow Check:** If `count >= maxCount - 3`, call `draw()` to flush the buffer immediately to prevent overflow [S1, unofficial].
6.  **Advance Vertex Count:** Increment `count` for each vertex added. If `count >= maxCount - 3` and `count` is divisible by `primsize`, call `draw()` to flush the buffer [S1, unofficial].
7.  **Flush and Render:** After all voxels are processed:
    a. If `count == 0`, return.
    b. Zero out remaining `posArray` entries from `count*3` to `length` to ensure clean data.
    c. Bind buffers for any enabled attributes (pos, normal, uv, color) using `gl.bufferData` with `DYNAMIC_DRAW`.
    d. Enable vertex attribute arrays and set pointers.
    e. Call `gl.drawArrays` with the primitive type, offset 0, and count.
    f. Reset `count` to 0.

**Parameters:**
*   `maxCount`: 4096 [S1, unofficial]. Determines the batch size before a flush is forced.
*   `prim`: Primitive type, typically `TRIANGLES` [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Buffer Overflow:** If `count >= maxCount - 3`, the buffer must be flushed immediately to ensure space for a full triangle (3 vertices) [S1, unofficial].
*   **Boundary Handling:** Threads/voxels at the grid boundary must check if neighbors exist to avoid out-of-bounds memory access when sampling the 8 corners of the cube [S1, unofficial].
*   **Precision:** Floating-point interpolation of vertex positions and normals must be consistent with the field generation to avoid artifacts.

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of voxels in the grid. Each voxel is processed once.
*   **Memory Complexity:** $O(1)$ relative to the grid size, as only the immediate mode buffer (fixed size `maxCount`) and lookup tables are stored. The scalar field may require $O(V)$ memory if not computed on the fly.
*   **Measured Performance:** Limited by CPU bottlenecks at high resolutions (e.g., $128^3$) or high blob counts (e.g., 100 blobs) [S1, unofficial]. Suitable for low-resolution demonstrations or reference comparisons.
*   **Scaling:** Does not scale well with increasing grid resolution or number of metaballs due to sequential CPU processing.
*   **Strengths:** Simple implementation, no complex parallel synchronization, easy to debug, minimal CPU-GPU transfer overhead for small batches.
*   **Limitations:** Poor performance at scale, limited by CPU speed, not suitable for real-time high-resolution rendering.
*   **When to use:** Reference implementation, educational purposes, low-resolution scenes, or when GPU acceleration is unavailable.
*   **When not to use:** High-resolution scenes, real-time applications with many metaballs, or when GPU parallelism is required.

## Background
CPU Immediate Mode Marching Cubes is inspired by Gregg Tavares' (Greggman) metaballs demo [S1, unofficial]. It represents a classic approach to real-time rendering where geometry is generated and sent to the GPU every frame without persistent storage. This method was common in early WebGL and OpenGL applications before the widespread adoption of compute shaders and append buffers for efficient geometry generation. It is used in educational contexts and as a baseline for comparing GPU-accelerated marching cubes implementations [S1, unofficial].
