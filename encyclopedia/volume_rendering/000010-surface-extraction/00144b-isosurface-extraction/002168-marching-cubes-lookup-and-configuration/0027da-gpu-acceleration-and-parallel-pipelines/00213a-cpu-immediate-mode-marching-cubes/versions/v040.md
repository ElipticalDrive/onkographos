# CPU Immediate Mode Marching Cubes

Also called: CPU Immediate Sim, Immediate Mode Marching Cubes, Legacy Marching Cubes

## Overview
CPU Immediate Mode Marching Cubes is a classic CPU-based surface extraction method that generates mesh vertices and normals in immediate mode, rendering them directly via WebGL draw calls without storing a persistent mesh buffer [S1, unofficial]. It serves as a reference implementation for comparison against GPU-accelerated variants, solving the problem of real-time isosurface visualization for scalar fields (such as metaballs) on the CPU [S1, unofficial]. It differs from sibling methods like [GPU Marching Cubes (Compute Shader)](4687-gpu-marching-cubes-compute-shader.md) by performing all geometry generation and field computation on the CPU, relying on immediate-mode rendering APIs rather than persistent buffers or compute shaders [S1, unofficial].

## How it works
The method operates in two main phases: scalar field generation on the CPU, followed by immediate-mode mesh extraction and rendering. It builds on the topology logic defined in [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md).

### Inputs and Outputs
*   **Inputs**:
    *   Grid resolution $N \times N \times N$ [S1, unofficial].
    *   Scalar field parameters (e.g., metaball positions, radii, floor term) [S1, unofficial].
    *   Isosurface threshold value $I$ [S1, unofficial].
    *   WebGL context and shader programs [S1, unofficial].
*   **Outputs**:
    *   Rendered mesh geometry (vertices and normals) displayed in the viewport [S1, unofficial].

### Data Structures
The implementation uses fixed-size typed arrays to store vertex attributes for batching. The maximum number of vertices per batch is `maxCount = 4096` [S1, unofficial].

*   **Position Array (`posArray`)**: `Float32Array` of size `maxCount * 3`. Stores $(x, y, z)$ coordinates.
*   **Normal Array (`normalArray`)**: `Float32Array` of size `maxCount * 3`. Stores $(nx, ny, nz)$ vectors.
*   **UV Array (`uvArray`)**: `Float32Array` of size `maxCount * 2`. (Not used in basic metaball demo, but allocated) [S1, unofficial].
*   **Color Array (`colorArray`)**: `Float32Array` of size `maxCount * 4`. (Not used in basic metaball demo, but allocated) [S1, unofficial].
*   **WebGL Buffers**: `posBuf`, `normalBuf`, `uvBuf`, `colorBuf` are `WebGLBuffer` objects bound to `ARRAY_BUFFER` targets [S1, unofficial].

### Algorithm Steps

1.  **Field Generation**:
    For each voxel in the $N \times N \times N$ grid, compute the scalar field value $V$ at the voxel center by accumulating contributions from all metaballs and a floor term [S1, unofficial].
    $$ V(x,y,z) = \sum_{j} \frac{r_j^2}{\| \mathbf{p} - \mathbf{c}_j \|^2} + V_{floor} $$
    Where $\mathbf{p}$ is the voxel center, $\mathbf{c}_j$ is the center of metaball $j$, and $r_j$ is its radius [S1, unofficial].

2.  **Batch Initialization**:
    Set the primitive type `prim` (e.g., `TRIANGLES`), `primsize` (3), and reset the vertex `count` to 0. Reset flags `hasPos`, `hasNormal`, `hasUV`, `hasColor` to false [S1, unofficial].

3.  **Voxel Processing**:
    Iterate through each voxel in the grid.
    a.  **Case Index**: Compute the 8-bit case index $C$ using the scalar values at the 8 vertices of the voxel cube. If $V(v_i) < I$, set bit $i$ of $C$ to 1 [S1, unofficial].
    b.  **Edge Intersections**: Use `edgeTable[C]` to identify intersected edges. Interpolate the intersection points on the cube edges using the scalar values at the vertices [S1, unofficial].
    c.  **Triangle Generation**: Use `triangleTable[C]` to retrieve the triplet of edge indices defining each triangle. For each triangle, compute the vertex positions and normals [S1, unofficial].
    d.  **Vertex Addition**:
        *   Add position: Store $x, y, z$ into `posArray` at indices `[count*3 + 0]`, `[count*3 + 1]`, `[count*3 + 2]`. Set `hasPos = true` [S1, unofficial].
        *   Add normal: Store $nx, ny, nz$ into `normalArray` at indices `[count*3]`, `[count*3 + 1]`, `[count*3 + 2]`. Set `hasNormal = true` [S1, unofficial].
        *   Increment `count` by 1 for each vertex added [S1, unofficial].

4.  **Buffer Flush Check**:
    After adding a triangle (3 vertices), check if `count >= maxCount - 3`. If true, call the `draw()` function to flush the current batch [S1, unofficial].

5.  **Rendering (Draw Function)**:
    a.  If `count == 0`, return [S1, unofficial].
    b.  Zero out remaining entries in `posArray` and `normalArray` from `count*3` to the end of the array to prevent garbage data [S1, unofficial].
    c.  Bind `posBuf` and `normalBuf` using `gl.bufferData` with `DYNAMIC_DRAW` hint, copying data from `posArray` and `normalArray` [S1, unofficial].
    d.  Enable vertex attribute arrays for position and normal using `gl.enableVertexAttribArray` [S1, unofficial].
    e.  Set pointers using `gl.vertexAttribPointer` for position (3 components) and normal (3 components) [S1, unofficial].
    f.  Call `gl.drawArrays` with `prim`, offset 0, and `count` [S1, unofficial].
    g.  Reset `count` to 0 [S1, unofficial].

### Edge Cases and Pitfalls
*   **Buffer Overflow**: The code checks if `count >= maxCount - 3` before drawing to ensure space for a triangle (3 vertices). If exceeded, it flushes immediately [S1, unofficial].
*   **Ambiguity**: Cases 46, 47, 98, 99, 210, 213, 214, 215 contain saddle points where the topology is ambiguous. The standard LUT uses a fixed triangulation, which can cause cracks or holes if adjacent voxels resolve the ambiguity differently [S1, unofficial].
*   **Performance**: Limited in performance at high resolutions or blob counts due to CPU bottlenecks [S1, unofficial].

## Operating characteristics
*   **Time Complexity**: $O(N^3 \cdot B)$, where $N$ is the grid resolution and $B$ is the number of metaballs (for field generation). The marching cubes step is $O(N^3)$ per frame.
*   **Memory Complexity**: $O(N^3)$ for the scalar field storage (if not computed on the fly) and $O(1)$ for the immediate mode buffers (fixed size `maxCount`) [S1, unofficial].
*   **Measured Performance**: Limited by CPU throughput. Performance degrades significantly with increasing grid resolution (e.g., $128^3$) or number of blobs (e.g., 100) [S1, unofficial].
*   **Strengths**: Simple implementation, serves as a good reference for algorithm correctness, minimal CPU-GPU transfer overhead for small datasets [S1, unofficial].
*   **Limitations**: Poor scalability, CPU-bound, not suitable for real-time high-resolution rendering with complex scenes [S1, unofficial].
*   **When to use**: For debugging, educational purposes, or low-resolution previews [S1, unofficial].
*   **When not to use**: For production real-time applications requiring high resolution or many objects [S1, unofficial].

## Background
The CPU Immediate Mode Marching Cubes implementation is inspired by Greggman's metaballs demo [S1, unofficial]. It uses the classic Marching Cubes algorithm with precomputed lookup tables (Paul Bourke's tables) [S1, unofficial]. The project is part of the `WebGL2-GPU-Marching-Cubes` repository by 3merillon, which also includes GPU-accelerated variants [S1, unofficial].
