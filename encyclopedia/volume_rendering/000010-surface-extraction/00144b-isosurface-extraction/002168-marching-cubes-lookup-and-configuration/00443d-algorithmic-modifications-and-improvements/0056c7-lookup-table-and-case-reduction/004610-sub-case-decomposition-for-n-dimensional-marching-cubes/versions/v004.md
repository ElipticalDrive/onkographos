# Sub-case decomposition for n-dimensional marching cubes

Also called: Major-case secondary table, Sub-case method, Sub-case secondary table

## Overview
Sub-case decomposition reduces the configuration space explosion in n-dimensional marching cubes by decomposing complex "major cases" into edge-connected "sub-cases" (fragments of boundary where vertices share the same status relative to the threshold) [S1]. Unlike sibling methods that rely on symmetry grouping alone, this approach stores geometric primitives (simplices) for these smaller fragments, allowing the algorithm to handle higher dimensions (e.g., 4D) where the number of major cases becomes prohibitive [S1]. It sets itself apart by using a primary/secondary table structure where the primary table maps cell configurations to sub-case indices and orientation matrices, rather than storing full triangulations for every symmetric variant [S1].

## How it works

### Inputs and Outputs
**Inputs:**
*   An n-dimensional structured grid of scalar values.
*   An isovalue threshold.
*   The dimension $n$ of the grid (typically $n \ge 3$).

**Outputs:**
*   A set of simplices (tetrahedra in 3D, pentachora in 4D, etc.) representing the isosurface.

### Data Structures

**1. Orientation Matrix**
Represents the transformation from the primary table's standard orientation to the current cell's orientation.
*   **Layout:** 32-bit integer.
*   **Encoding:** Uses 2 bits per matrix position. Values $1, 0, -1$ are mapped to binary `00`, `01`, `10` respectively.
*   **Purpose:** Aligns stored geometric data with the current cell's rotation/mirror state [S1].

**2. Primary Table**
Maps the 2D index (derived from vertex signs) to a sub-case index and orientation.
*   **Layout (Method 3b):** Array of 65,536 entries. Each entry is a pointer to a list of 2-tuples `(Orientation, Sub-Index)` [S1].
*   **Note:** Method 3a uses `(Orientation, Major-Index)` tuples, but Method 3b is the specific sub-case decomposition variant [S1].

**3. Secondary Table**
Stores the actual geometric primitives (simplices) for the sub-cases.
*   **Layout:** Array of pointers to arrays of tetrahedra.
*   **Tetrahedron Storage:** 4 bytes per tetrahedron (1 byte for each vertex label) [S1].

### Pre-processing: Generating Major and Sub-Cases

Before runtime, the lookup tables must be constructed. This involves identifying unique cases and decomposing them.

**Step 1: Identify Major Cases**
1.  Initialize two lists: `searched_cases` and `major_cases`.
2.  While `searched_cases` does not contain all possible indices ($0$ to $2^n - 1$):
    a.  Take the next unmarked index $I$ from the search space.
    b.  Add $I$ to `major_cases`.
    c.  Generate all symmetric variants of $I$ using rotation ($R$), mirror ($M$), and complement ($C$) operators.
    d.  Mark all generated variants as "searched" in `searched_cases`.
3.  Result: A list of representative major cases. In 3D, there are 14 (or 15 with Complement) major cases. In 4D, there are 222 major cases [S1].

**Step 2: Decompose into Sub-Cases**
1.  For each major case, divide it into disjoint **sub-cases**.
2.  A sub-case is defined as an edge-connected fragment of the boundary where all vertices have the same status (sign) with respect to the threshold.
3.  In 3D, this results in 74 sub-cases. In 4D, the number of sub-cases remains 74 (though the geometry is more complex) [S1].

**Step 3: Tetrahedronization (Simplification) of Sub-Cases**
To store sub-cases efficiently, they are decomposed into simplices (tetrahedra in 3D). The algorithm uses a greedy vertex removal strategy with backtracking.

1.  Represent the sub-case geometry as a list of vertices, where each vertex is linked to a list of its neighbors. Initially, all vertices have three connections (in 3D).
2.  Select the next vertex from the list with the **fewest incident edges**.
3.  Remove this vertex from the object. This operation generates one or two tetrahedra.
    *   A vertex with 3 connections yields 1 tetrahedron.
    *   A vertex with 4 connections yields 2 tetrahedra.
4.  Update the connectivity of the remaining object by connecting the neighbors of the removed vertex according to the base of the generated tetrahedron(s).
5.  **Backtracking Check:** If any remaining vertex has 5 or more incident edges, backtrack to the previous level and attempt a different split (choose a different vertex or split configuration) [S1].
    *   *Note:* Using the "fewest edges" method, backtracking occurs for only 3 of the 74 sub-cases in 3D [S1].

**Step 4: Create Orientation Matrix**
1.  For each sub-case variant, rotate it into the "standard" sub-case configuration.
2.  Calculate the inverse transformation matrix of this operation.
3.  Encode this matrix into the 32-bit integer format described above [S1].

### Runtime Algorithm

**Inputs:**
*   Current cell configuration index $C$ (0 to 65,535).
*   Grid data and isovalue.

**Steps:**
1.  **Lookup:** Access the Primary Table at index $C$. Retrieve the list of `(Orientation, Sub-Index)` tuples.
2.  **Iterate Tuples:** For each tuple $(O, S)$:
    a.  Retrieve the sub-case geometry from the Secondary Table using $S$.
    b.  For each simplex (tetrahedron) in the sub-case geometry:
        i.  Get the vertex labels (indices relative to the cell edges).
        ii. Apply the transformation defined by $O$ to map these labels to the actual grid edge intersection points.
        iii. Output the simplex.
3.  **Disambiguation:** If the cell configuration contains an "ambiguous face" (surface intersects one face through each of its four edges), use separate complementary case configurations to resolve spurious holes or additional segments [S1].

### Parameters and Typical Values

*   **Tetrahedron Storage:** 4 bytes per tetrahedron (1 byte per vertex label) [S1].
*   **3D Statistics:** 14 major cases, 74 sub-cases.
*   **4D Statistics:** 222 major cases, 74 sub-cases.
*   **Memory Usage (Method 2 - Complete Simplex Table):** 1.75 Mbytes. Calculated as $4 \times 356,817$ (tetrahedra data) + $5 \times 65,536$ (array pointers) for 356,817 tetrahedra across 222 major cases [S1].
*   **Memory Usage (Method 3a - Major Cases):** ~328 Kbytes for primary table + 10.2 Kbytes for secondary table [S1].
*   **Memory Usage (Method 3b - Sub-Cases):** Not explicitly quantified in bytes in the source, but described as using pointers to `(Orientation, Sub-Index)` tuples [S1].

### Edge Cases and Pitfalls

*   **Ambiguities:** Occur when the surface intersects one face of the n-cube through each of its four edges. This can generate spurious holes or additional surface segments. This face ambiguity occurs in 2D and propagates to higher dimensions [S1].
*   **Disambiguation Strategy:** Use separate complementary case configurations for each major case. This maintains vertex order (clockwise relative to the surface-object) aiding the renderer [S1].
*   **Backtracking:** During tetrahedronization, if a vertex has 5 or more incident edges, the algorithm must backtrack. Using the "fewest edges" method, this happens for only 3 of the 74 sub-cases in 3D [S1].
*   **High Resolution Anomalies:** At high data resolutions, anomalies may become unobservable, but at high magnifications, discontinuous surfaces may still be visible [S1].

## Operating characteristics

*   **Time Complexity:**
    *   **Pre-processing:** High. Generating sub-cases and tetrahedronizing them requires complex geometric decomposition and backtracking [S1].
    *   **Runtime:** Moderate. Requires a lookup in the primary table, which may return multiple tuples (one per sub-case variant), followed by geometry transformation. Slower than Method 1 (Dynamic Simplex Enumeration) but faster than Method 2 (Complete Simplex Enumeration) in terms of memory access patterns for sparse cases [S1].
*   **Memory Complexity:**
    *   **Method 3b (Sub-case):** Significantly lower than Method 2 (1.75 MB for 4D complete table) because it stores only unique sub-case geometries and uses orientation matrices to handle symmetry. Method 3a (Major-case) uses ~338 KB total [S1].
    *   **Method 1 (Dynamic):** Uses the least memory but takes the longest to calculate at runtime [S1].
*   **Strengths:**
    *   Scalable to higher dimensions (4D+) where the full $2^n$ table is impossible.
    *   Reduces table size by exploiting symmetry and decomposing complex cases.
*   **Limitations:**
    *   Ambiguities require careful handling (complementary cases).
    *   Pre-processing is non-trivial due to the need for tetrahedronization and backtracking.
*   **When to Use:**
    *   When working in 4D or higher dimensions.
    *   When memory is constrained but pre-processing time is acceptable.
    *   When topological correctness is critical and symmetry reduction is needed.
*   **When Not to Use:**
    *   In 3D, where storing all 256 cases is feasible and simpler (Method 2 or standard MC).
    *   When real-time performance is critical and pre-processing cannot be done offline.

## Background

*   **Origin:** The method was introduced in the paper "Piecewise linear hypersurfaces using the marching cubes algorithm" [S1].
*   **History:** The technique addresses the "configuration explosion" problem in n-dimensional marching cubes. While 3D marching cubes has 256 configurations (reducible to 14-15 major cases), 4D has 65,536 configurations. The number of major cases in 4D (222) is comparable to the total configurations in 3D, making full table storage impractical. Sub-case decomposition was proposed to further reduce this complexity by breaking major cases into smaller, edge-connected fragments [S1].
*   **Usage:** Used in scientific visualization for higher-dimensional data (e.g., 4D spacetime volumes, phase space analysis) where traditional 3D MC tables are insufficient [S1].
