# Sub-case decomposition for n-dimensional marching cubes

Also called: Major-case secondary table, Sub-case method, Sub-case secondary table

## Overview
Sub-case decomposition reduces the combinatorial explosion of configuration cases in n-dimensional marching cubes by decomposing major cases into edge-connected sub-cases (fragments of boundary where vertices have the same status with respect to the threshold) [S1]. It sets itself apart from siblings like [Snap Marching Cubes](2181-snap-marching-cubes.md) and [Bitwise Marching Cubes](7374-bitwise-marching-cubes.md) by explicitly managing the geometry of the isosurface intersection via tetrahedronization of sub-components rather than relying on static lookup tables for all possible vertex configurations or field snapping [S1].

## How it works
The method operates on a structured grid to extract isosurfaces in $n$-dimensions. It replaces the standard single-lookup approach with a two-level table structure (Primary and Secondary) and a pre-processing phase that decomposes major cases into sub-cases.

### Inputs and Outputs
- **Input**: Scalar field values at grid vertices, isovalue threshold, grid dimensions.
- **Output**: A triangle (or simplex) mesh representing the isosurface.

### Data Structures

**1. Orientation Matrix**
Represents the transformation from the primary table index into individual simplex elements.
- **Layout**: 32-bit integer.
- **Encoding**: Uses 2 bits per position in the transformation matrix.
- **Values**: Rotations are by $90^\circ$. Values $1, 0, -1$ are mapped to binary `00`, `01`, `10` respectively [S1].

**2. Primary Table**
Maps the 65536 possible vertex configurations (indices $0 \dots 65535$) to secondary table entries.
- **Method 3a (Major Cases)**: Array of 65536 tuples `(Orientation, Major-Index)`. Size: ~328 KB (assuming 5 bytes per tuple, though padding may increase this) [S1].
- **Method 3b (Sub-Cases)**: Array of 65536 pointers to arrays of `(Orientation, Sub-Index)` tuples. The array size includes the number of sub-cases per major case [S1].

**3. Secondary Table**
Contains the actual simplex (tetrahedron) definitions.
- **Tetrahedron Layout**: 4 bytes per tetrahedron. Each byte represents one vertex label (integer index) [S1].
- **Method 2 (Complete)**: Stores all simplices for all 65536 indices directly. Total size: 1.75 MB (calculated as $4 \times 356,817$ bytes for tetrahedra + $5 \times 65,536$ bytes for array pointers) [S1].
- **Method 3a/3b**: Stores simplices only for the reduced set of major or sub-cases. For 3D/4D, this involves 222 major cases and 74 sub-cases [S1].

### Pre-processing: Generating Major and Sub-Cases

**Step 1: Identify Major Cases**
1. Create two lists: `searched_cases` and `major_cases`.
2. Initialize `searched_cases` with all unmarked indices ($0 \dots 65535$).
3. While `searched_cases` is not empty:
    a. Take the next unmarked index $I$ from `searched_cases`.
    b. Add $I$ to `major_cases`.
    c. Exhaustively transform $I$ using rotation ($R$), mirror ($M$), and complement ($C$) operators.
    d. Mark all generated configurations as searched in `searched_cases`.
4. Repeat until all indices are searched [S1].

**Step 2: Tetrahedronization of Sub-Cases**
Sub-cases are defined as edge-connected fragments of a major case where vertices share the same status (inside/outside) relative to the threshold. The geometry of each sub-case is decomposed into tetrahedra.

1. Represent the sub-case object as a list of vertices. Each vertex is linked to a list of its neighbors. Initially, all vertices have three connections [S1].
2. Select the next vertex (in order on the list) with the fewest incident edges.
3. Remove this vertex from the object, generating one or two tetrahedra.
    - A vertex with 3 connections generates 1 tetrahedron.
    - A vertex with 4 connections generates 2 tetrahedra.
4. Update the connectivity of the remaining object by connecting the remaining vertices in the same configuration as the base of the split tetrahedron.
5. If any vertex has 5 or more incident edges, backtrack to the previous level and attempt a different split.
    - In practice, using the "fewest edges" strategy, backtracking occurs for only 3 of the 74 sub-cases in 3D/4D [S1].

**Step 3: Create Orientation Matrix**
For each sub-case derived from a major case:
1. Rotate the sub-case into the standard sub-case configuration.
2. Calculate the inverse transformation matrix of the whole operation.
3. Encode this matrix into the 32-bit Orientation Matrix [S1].

### Disambiguation Strategy
Ambiguities occur when the surface intersects one face of the $n$-cube through each of its four edges, potentially generating spurious holes or additional surface segments. This face occurs in 2D and propagates to higher dimensions [S1].

- **Strategy**: Use separate complementary case configurations.
- For each ambiguous face $f$ in a given $n$-cube, there are $2^{\#f}$ possible sub-case configurations, but in practice only a subset is required (similar under rotation).
- This maintains vertex order (clockwise relative to the surface-object), aiding the renderer [S1].

    using sub-case decomposition.
    """
    # Step 1: Identify Major Cases
    searched_cases = set(range(65536))
    major_cases = []
    
    while searched_cases:
        # Take next unmarked index
        idx = min(searched_cases)
        searched_cases.remove(idx)
        major_cases.append(idx)
        
        # Exhaustively transform and mark
        transformed = generate_transformations(idx)
        for t in transformed:
            searched_cases.discard(t)
            
    # Step 2: Decompose into Sub-Cases and Tetrahedronize
    # Note: This is a high-level representation. 
    # The actual tetrahedronization is complex and specific to each sub-case geometry.
    sub_case_data = {}
    
    for major_idx in major_cases:
        # Identify edge-connected sub-components for this major case
        sub_components = decompose_into_subcases(major_idx)
        
        for sub_comp in sub_components:
            # Tetrahedronize the sub-component
            tetrahedra = tetrahedronize(sub_comp)
            
            # Calculate orientation matrix
            orientation = calculate_orientation_matrix(sub_comp, major_idx)
            
            # Store in secondary table structure
            # Key could be a combination of major_idx and sub_comp_id
            sub_case_data[(major_idx, sub_comp)] = {
                'tetrahedra': tetrahedra,
                'orientation': orientation
            }
            
    # Step 3: Build Primary and Secondary Tables
    # Method 3b: Primary table points to sub-case arrays
    primary_table = [None] * 65536
    secondary_table = [] # List of sub-case entries
    
    for major_idx in major_cases:
        # Find all sub-cases associated with this major index
        sub_cases_for_major = [
            (k[1], v) for k, v in sub_case_data.items() if k[0] == major_idx
        ]
        
        # Build pointer array for this major case
        # Each entry is (orientation, sub_index)
        sub_case_entries = []
        for sub_idx, data in sub_cases_for_major:
            sub_case_entries.append((data['orientation'], sub_idx))
            
        # Store in primary table
        # Assuming a structure where primary_table[i] points to a list of tuples
        primary_table[major_idx] = sub_case_entries
        
    return primary_table, secondary_table, sub_case_data

### Parameters and Typical Values
- **Tetrahedron Storage**: 4 bytes per tetrahedron (1 byte per vertex label) [S1].
- **3D Major Cases**: 14 (or 15 if Complement operator is used) [S1].
- **3D/4D Sub-Cases**: 74 [S1].
- **4D Major Cases**: 222 (under R, M operators) [S1].
- **Memory Usage (Method 2)**: 1.75 MB for the complete simplex table in 4D (356,817 tetrahedra) [S1].

### Edge Cases and Pitfalls
- **Ambiguities**: Occur when the surface intersects one face of the $n$-cube through each of its four edges. This creates spurious holes or additional surface segments. This face occurs in 2D and propagates to higher dimensions [S1].
- **Backtracking**: During tetrahedronization, if a vertex has 5 or more incident edges, the algorithm must backtrack. In practice, with the "fewest edges" strategy, this happens for only 3 of the 74 sub-cases in 3D/4D [S1].
- **Complement Operator**: The number of major cases varies (14 vs 15) depending on whether the complement operator is included in the symmetry group [S1].

## Operating characteristics
- **Time Complexity**: Pre-processing is expensive. Method 1 (Dynamic Simplex Enumeration) takes the longest to calculate but uses the least memory. Method 2 (Complete Simplex Enumeration) pre-calculates and stores all divisions, requiring significant memory but fast runtime lookup [S1].
- **Memory Complexity**: 
    - Method 1: Minimal memory, dynamic calculation.
    - Method 2: 1.75 MB for 4D complete table.
    - Method 3a: ~328 KB for primary table + 10.2 KB for secondary table (pointers) [S1].
    - Method 3b: Similar to 3a but optimized for sub-cases.
- **Scaling**: The number of major cases grows rapidly with dimension. In 4D, there are nearly as many major cases as there are configurations in 3D [S1]. Sub-case decomposition mitigates this by reducing the number of cases that need explicit storage or complex handling.
- **Strengths**: Reduces table size for higher dimensions. Handles complex geometries via sub-case decomposition.
- **Limitations**: Pre-processing is complex. Ambiguities still require disambiguation strategies. Backtracking may be needed for tetrahedronization.

## Background
The method was introduced by [S1] to address the combinatorial explosion of configuration cases in n-dimensional marching cubes. It builds on the standard Marching Cubes algorithm but extends it to higher dimensions by decomposing major cases into sub-cases. The work highlights the limitations of static lookup tables in higher dimensions and proposes a hybrid approach using orientation matrices and sub-case decomposition.
