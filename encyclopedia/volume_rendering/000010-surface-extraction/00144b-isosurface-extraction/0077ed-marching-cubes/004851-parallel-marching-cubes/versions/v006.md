# Parallel Marching Cubes

Also called: Marching Cubes with Slice Strategy, PBIG, Parallel Isosurface Generator, Piecewise Marching Cubes

## Overview
Parallel Marching Cubes is a distributed-memory or multi-process implementation of the Marching Cubes algorithm designed to extract isosurfaces from volumetric datasets too large to fit entirely into a single machine's physical memory [S1, unofficial]. It solves the memory bottleneck of traditional sequential Marching Cubes by employing a piecewise slice strategy along the k-direction, where the volume is partitioned into slices that fit into RAM [S1, unofficial]. Unlike [GPU Marching Cubes (Compute Shader)](4687-gpu-marching-cubes-compute-shader.md) which relies on GPU parallelism and shared VRAM, this method uses CPU-based process parallelism (via `fork`, `sproc`, or `pthreads`) to process independent slices concurrently, requiring only that at least two slices fit into physical memory [S1, unofficial].

## How it works
The method partitions a 3D structured grid along the k-axis into $N$ slices, where $N$ is the number of parallel processes. Each process reads its assigned slice, computes the isosurface polygons using the standard Marching Cubes lookup tables, and writes the results to a shared output file using synchronization primitives to prevent data corruption.

### Inputs and Outputs
**Inputs:**
1.  **Grid File:** A PLOT3D-format file containing the structured mesh coordinates $(x, y, z)$ for the volume [S1, unofficial]. The grid can be regular or irregular but must be oriented such that it can be sliced along the k-direction [S1, unofficial].
2.  **Solution File:** A PLOT3D-format file containing the scalar field values $F(x,y,z)$ associated with the grid nodes [S1, unofficial].
3.  **Command Line Parameters:**
    *   `argv[1]`: Path to the Grid File.
    *   `argv[2]`: Path to the Solution File.
    *   `argv[3]`: Path to the output Bop file.
    *   `argv[4]`: Integer index into the Solution File for the scalar defining the isosurface.
    *   `argv[5]`: Integer index into the Solution File for the scalar mapped onto the surface for color.
    *   `argv[6]`: Floating-point isovalue $S$ [S1, unofficial].
    *   `argv[7]`: Integer `Kstep`, controlling the number of planes to step in the k-direction (typically 2 or 3) [S1, unofficial].
    *   `argv[8]`: Integer `Num_procs`, the number of child processes to spawn [S1, unofficial].

**Outputs:**
*   **Bop File:** A binary "Bag-O-Polygons" file containing the generated isosurface [S1, unofficial].

### Data Structures

**1. Partition Structure (Parent to Child)**
The parent process creates a structure for each child process to define the data range it must read. While the exact C struct definition is not fully enumerated in the source, it logically contains:
*   `start_k`: The starting index of the k-dimension for this slice.
*   `end_k`: The ending index of the k-dimension for this slice.
*   `i_dim`, `j_dim`: The dimensions of the i and j axes (constant across all slices).
*   `file_offset`: The byte offset in the grid and solution files corresponding to the start of this slice's data.

**2. Bop Polygon Structure (`boply`)**
Each polygon written to the output file is defined by the following structure [S1, unofficial]:
```c
struct boply {
    int num_vertices; // Typically 3 for triangles
    float x[3];       // X coordinates of vertices
    float y[3];       // Y coordinates of vertices
    float z[3];       // Z coordinates of vertices
    float scalar[3];  // Mapping scalar values for each vertex
};
```

### Algorithm Steps

1.  **Initialization (Parent Process):**
    *   Open the Grid and Solution files.
    *   Read header information to determine the total dimensions $I, J, K$ and verify there is exactly one grid [S1, unofficial].
    *   Calculate the slice boundaries based on `Kstep` and `Num_procs`.
    *   Create `Num_procs` child processes. The mechanism depends on the platform:
        *   `fork`: Standard UNIX copy-on-write. Writes are not visible to other processes [S1, unofficial].
        *   `sproc`: SGI-specific share group process. Shares virtual address space (shared memory/mapped files) but has unique stack/program counters [S1, unofficial].
        *   `pthreads`: Used on KSR1 machines [S1, unofficial].

2.  **Slice Processing (Child Process):**
    *   Read the header information from the parent (dimensions, file offsets).
    *   Read only the data corresponding to the assigned k-slice from the Grid and Solution files into local memory [S1, unofficial].
    *   Iterate through every voxel in the assigned slice.
    *   For each voxel, calculate the 8-bit case index $C$ based on the scalar values at the 8 vertices relative to the isovalue $S$ [S1, unofficial].
    *   Look up the topology in the `triangleTable` (from [Lookup Table and Ambiguity Handling](10327-lookup-table-and-ambiguity-handling.md)) [G].
    *   For each triangle defined by the lookup:
        *   Determine the intersection points on the cube edges using linear interpolation [S1, unofficial].
        *   Construct the `boply` structure for the triangle.
        *   Store the polygon in a local buffer.

3.  **Output Serialization:**
    *   Child processes write their generated polygons to the Bop file.
    *   Because multiple processes may attempt to write simultaneously, a semaphore is used to enforce mutual exclusion [S1, unofficial].
    *   Only one child process is allowed to write to the Bop file at any given time.
    *   After writing, the semaphore is released.

4.  **Termination:**
    *   Child processes exit after writing their data.
    *   The parent process waits for all children to complete.
    *   The Bop file is closed.

### Pseudocode

```python
# Parent Process
def parallel_marching_cubes(grid_file, sol_file, bop_file, scalar_idx, map_idx, isovalue, kstep, num_procs):
    # 1. Open files and read headers
    grid_header = read_plot3d_header(grid_file)
    sol_header = read_plot3d_header(sol_file)
    
    I, J, K = grid_header.dimensions
    total_slices = K // kstep
    
    # 2. Partition workload
    # Create a list of slice definitions
    slices = []
    for p in range(num_procs):
        start_k = p * kstep
        end_k = min(start_k + kstep, K)
        # Calculate file offsets based on grid structure
        # Assuming row-major or standard PLOT3D layout
        offset = calculate_offset(grid_header, start_k)
        slices.append({
            'start_k': start_k,
            'end_k': end_k,
            'offset': offset,
            'i_dim': I,
            'j_dim': J
        })
        
    # 3. Spawn Child Processes
    children = []
    for i in range(num_procs):
        # Platform-specific spawn: fork, sproc, or pthread
        child = spawn_child(slice_data=slices[i], 
                            grid_file=grid_file, 
                            sol_file=sol_file, 
                            bop_file=bop_file,
                            scalar_idx=scalar_idx,
                            map_idx=map_idx,
                            isovalue=isovalue)
        children.append(child)
        
    # 4. Wait for completion
    for child in children:
        child.join()

# Child Process
def child_process(slice_data, grid_file, sol_file, bop_file, scalar_idx, map_idx, isovalue):
    # 1. Read assigned slice
    # Seek to slice_data['offset'] in grid and sol files
    # Read only the vertices and scalars for k in [start_k, end_k)
    local_grid = read_slice(grid_file, slice_data)
    local_scalars = read_slice(sol_file, slice_data)
    
    # 2. Process Voxels
    polygons = []
    for k in range(slice_data['start_k'], slice_data['end_k'] - 1):
        for j in range(slice_data['j_dim'] - 1):
            for i in range(slice_data['i_dim'] - 1):
                # Get 8 vertices of the voxel
                v = get_voxel_vertices(local_grid, i, j, k)
                s = get_voxel_scalars(local_scalars, i, j, k, scalar_idx)
                
                # Calculate Case Index
                case_index = 0
                for bit in range(8):
                    if s[bit] >= isovalue:
                        case_index |= (1 << bit)
                
                # Lookup Triangles
                triangles = lookup_triangles(case_index)
                
                for tri in triangles:
                    # Intersect edges
                    points = []
                    scalars_out = []
                    for edge_idx in tri:
                        if edge_idx == -1: break
                        p, s_val = interpolate_edge(v, s, edge_idx)
                        points.append(p)
                        scalars_out.append(s_val)
                    
                    # Create Bop Polygon
                    poly = boply(num_vertices=3, x=[p.x for p in points], 
                                 y=[p.y for p in points], z=[p.z for p in points],
                                 scalar=scalars_out)
                    polygons.append(poly)
    
    # 3. Write Output with Semaphore
    acquire_semaphore()
    try:
        write_bop_file(bop_file, polygons)
    finally:
        release_semaphore()
```

### Edge Cases and Pitfalls
*   **Grid Orientation:** The grid must be oriented such that it can be sliced in the k-direction. If the data structure does not support efficient slicing along k, the method may fail or require preprocessing [S1, unofficial].
*   **Simultaneous Writes:** Without semaphores, simultaneous writes by multiple child processes to the Bop format output function cause collisions and data corruption [S1, unofficial].
*   **Memory Constraints:** The method requires that at least two slices fit into physical memory. If the slice size exceeds available RAM, the process will fail [S1, unofficial].
*   **Process Creation Overhead:** The choice of `fork` vs `sproc` vs `pthreads` affects performance and memory sharing. `fork` uses copy-on-write, which is safe but may duplicate memory pages on write. `sproc` shares memory but is platform-specific (SGI) [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N \cdot V)$, where $N$ is the number of voxels and $V$ is the average number of triangles per voxel. The parallel execution reduces wall-clock time by a factor of approximately $P$ (number of processes), assuming I/O and synchronization overheads are low.
*   **Memory Complexity:** $O(S)$, where $S$ is the size of a single slice. This is significantly lower than the $O(V)$ required by sequential methods for huge datasets [S1, unofficial].
*   **Measured Performance:** On a dataset of ~2.2M grid values and ~11M scalar values, generating ~60,000 polygons, the wall-clock time was reduced from ~20 minutes (sequential) to ~90 seconds (parallel) on an 8-processor SGI Challenge or KSR1 machine [S1, unofficial].
*   **Strengths:**
    *   Handles datasets larger than physical RAM.
    *   Platform-independent parallelism (supports UNIX, SGI, KSR1).
    *   Flexible output via Bop format and TCP/IP streaming to Bop_View [S1, unofficial].
*   **Limitations:**
    *   Requires grid orientation compatible with k-slicing.
    *   Synchronization overhead for file writing can become a bottleneck if the number of processes is very high or the output volume is large.
    *   Limited to CPU-based parallelism; does not leverage GPU acceleration [S1, unofficial].

## Background
Parallel Marching Cubes was developed as part of the Parallel Isosurface Generator (PBIG) project, documented in a report from the U.S. Army Research Laboratory (DTIC ADA284030) [S1, unofficial]. It was designed to address the limitations of commercial and public domain visualization packages (such as those using SciAn or Bop libraries) which assumed the entire volume fit in memory [S1, unofficial]. The implementation was tested on SUN4, SGI Challenge, and KSR1 architectures, utilizing computational data from CTH and HULL codes, as well as medical resonance data [S1, unofficial]. The core algorithm relies on the original Marching Cubes method by Lorenson and Cline (1987) [S1, unofficial].
