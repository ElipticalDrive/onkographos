# Parallel Marching Cubes

Also called: Parallel Isosurface Generator, PBIG, Marching Cubes with Slice Strategy, Piecewise Marching Cubes

## Overview
Parallel Marching Cubes (Slice Strategy) is a CPU-based parallel algorithm designed to extract isosurfaces from volumetric datasets that exceed the capacity of a single machine's physical memory [S1, unofficial]. It solves the memory bottleneck of traditional Marching Cubes by decomposing the 3D volume into 2D slices along the k-direction, processing them concurrently using multiple processes or threads [S1, unofficial]. Unlike GPU-based parallel methods that rely on atomic counters or histogram pyramids for output buffering, this method uses a piecewise calculation approach where child processes write directly to a shared output file, coordinated by semaphores to prevent write collisions [S1, unofficial].

## How it works

### Inputs and Outputs
**Inputs:**
1.  **Grid File:** A PLOT3D-format file defining the structured mesh coordinates $(x, y, z)$ [S1, unofficial].
2.  **Solution File:** A PLOT3D-format file containing scalar fields $v(x,y,z)$, $F(x,y,z)$, etc. [S1, unofficial].
3.  **Parameters:**
    *   `isosurface_value` ($S$): The scalar threshold for extraction [S1, unofficial].
    *   `kstep`: The number of planes to step in the k-direction (controls slice thickness/overlap) [S1, unofficial]. Typical value: 2 or 3 [S1, unofficial].
    *   `num_procs`: The number of parallel processes/threads to spawn [S1, unofficial].
    *   `scalar_index`: Index into the solution file for the scalar defining the isosurface [S1, unofficial].

**Outputs:**
*   **Bop File:** A binary "Bag-O-Polygons" file containing the extracted isosurface [S1, unofficial].

### Data Structures
**Bop Polygon Structure (`boply`):**
Each polygon in the output is defined by a C structure containing:
*   `num_vertices`: Integer specifying the number of vertices (typically 3 for triangles) [S1, unofficial].
*   `vertices`: An array of vertex data. Each vertex consists of:
    *   `x, y, z`: Floating-point coordinates [S1, unofficial].
    *   `mapping_scalar`: Floating-point value mapped onto the surface (e.g., color or secondary field) [S1, unofficial].

**Partitioning Structure:**
The parent process creates a structure for each child process containing:
*   The range of k-indices assigned to the child [S1, unofficial].
*   File offsets for reading the grid and solution files corresponding to that slice [S1, unofficial].

### Algorithm Steps
The algorithm operates in two phases: Partitioning and Execution.

1.  **Initialization:** The parent process opens the Grid and Solution files to read headers, determining the total dimensions $(N_i, N_j, N_k)$ and verifying there is one grid [S1, unofficial].
2.  **Partitioning:** The parent divides the volume along the k-direction into `num_procs` slices. It calculates the k-index range for each child and stores this in a partitioning structure [S1, unofficial].
3.  **Process Creation:** The parent spawns `num_procs` child processes. The mechanism depends on the platform:
    *   `fork`: Standard UNIX copy-on-write (writes not visible to other processes) [S1, unofficial].
    *   `sproc`: SGI-specific share group process (shared virtual address space) [S1, unofficial].
    *   `pthreads`: Thread-based parallelism (used on KSR1) [S1, unofficial].
4.  **Slice Processing (Child Process):**
    a.  **Data Loading:** The child reads its assigned slice of the grid and solution data into memory. The method relies on the constraint that at least two slices fit into physical memory [S1, unofficial].
    b.  **Marching Cubes Execution:** For each voxel cube in the slice:
        i.  **Case Index Calculation:** Determine the 8-bit case index $C$. For each vertex $v_i$ ($i=0..7$) of the cube, if $V(v_i) \ge S$, set bit $i$ of $C$ to 1; otherwise 0 [S1, unofficial].
        ii. **Early Exit:** If $C=0$ or $C=255$, the voxel is fully inside or outside the isosurface; skip to the next voxel [S1, unofficial].
        iii. **Topology Lookup:** Retrieve the triangulation configuration from the `triangleTable` using $C$. This yields a list of edges to intersect [S1, unofficial].
        iv. **Intersection Calculation:** For each active edge, calculate the intersection point $P$ via linear interpolation between the scalar values at the edge endpoints $A$ and $B$:
            $$ P = A + \frac{S - V(A)}{V(B) - V(A)} (B - A) $$
            where $V(A)$ and $V(B)$ are the scalar values at vertices A and B [S1, unofficial].
        v.  **Polygon Assembly:** Collect the intersection points to form triangles (three-sided polygons) [S1, unofficial].
    c.  **Output Serialization:** The child writes its generated polygons to the Bop file. To prevent simultaneous writes from multiple children causing data corruption, a semaphore enforces mutual exclusion, allowing only one child to write at a time [S1, unofficial].
5.  **Completion:** Children exit after writing their data. The parent waits for all children to complete [S1, unofficial].

    partitions = []
    k_slice_height = dims.Nk // num_procs

        k_start = i * k_slice_height
        k_end = (i + 1) * k_slice_height if i < num_procs - 1 else dims.Nk

            'k_end': k_end,
            'file_offset': calculate_file_offset(dims, k_start)

### Edge Cases and Pitfalls
*   **Grid Orientation:** The grid must be oriented such that it can be sliced in the k-direction. If the data structure does not support this, the method fails or requires preprocessing [S1, unofficial].
*   **Write Collisions:** Simultaneous writes by multiple child processes to the Bop format cause data corruption. This is handled by semaphores, but introduces serialization overhead [S1, unofficial].
*   **Memory Constraint:** The method requires that at least two slices fit into physical memory. If slices are too large, the system will swap, negating performance gains [S1, unofficial].

## Operating characteristics

*   **Time Complexity:** $O(N)$ where $N$ is the total number of voxels, but with a constant factor reduced by parallelism. The serialization of output adds overhead proportional to the number of polygons and processes.
*   **Memory Complexity:** $O(S)$ where $S$ is the size of a single slice (plus overhead for the partitioning structure). This is significantly lower than $O(V)$ where $V$ is the total volume size, allowing processing of datasets larger than RAM [S1, unofficial].
*   **Measured Performance:** On a dataset of ~2.2M grid values and ~11M scalar values, wall-clock time was reduced from ~20 minutes (single process) to ~90 seconds using parallel execution on an 8-processor SGI Challenge or KSR1 machine [S1, unofficial].
*   **Strengths:**
    *   Handles datasets larger than physical memory [S1, unofficial].
    *   Portable across UNIX platforms (SGI, Sun, KSR) using standard parallel primitives (`fork`, `sproc`, `pthreads`) [S1, unofficial].
    *   Simple implementation logic compared to GPU atomic/histogram approaches [S1, unofficial].
*   **Limitations:**
    *   Output serialization via semaphores can become a bottleneck if the number of polygons is very high [S1, unofficial].
    *   CPU-bound; does not leverage GPU parallelism [S1, unofficial].
    *   Requires specific grid orientation (k-slicing) [S1, unofficial].
*   **When to use:** When processing huge volumetric datasets on a multi-core CPU cluster where the data does not fit in RAM, and GPU acceleration is not available or suitable.
*   **When not to use:** When the entire dataset fits in memory and interactive frame rates are required (GPU methods are faster); when the grid cannot be sliced in the k-direction.

## Background

*   **Origin:** The Parallel Isosurface Generator (PBIG) was developed by researchers at the Supercomputer Research Institute and Florida State University, documented in a 1994 report [S1, unofficial].
*   **History:** It was designed to address the limitations of commercial and public domain visualization packages (like SciAn) that assumed the entire volume fit in memory [S1, unofficial]. It utilized existing PLOT3D file formats and Bop output libraries [S1, unofficial].
*   **Applications:** Applied to computational fluid dynamics data from CTH and HULL codes, as well as medical resonance data [S1, unofficial].
*   **Platforms:** Tested on SUN4, SGI Challenge, and KSR1 architectures [S1, unofficial].
