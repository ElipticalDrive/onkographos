# Marching Cubes (Lewiner variant)
Also called: MCB
## Overview
Marching Cubes (Lewiner variant) is an isosurface extraction method that resolves topological ambiguities in the standard Marching Cubes algorithm by performing local interior and face tests on ambiguous cube configurations [S1, unofficial]. It differs from standard implementations by guaranteeing a manifold, non-self-intersecting mesh for all 256 cube cases, whereas standard implementations often require heuristic disambiguation or produce non-manifold geometry in ambiguous cases [S1, unofficial].

## How it works
**Inputs:** A 3D scalar field defined on a regular grid with dimensions `dim[3]`, processing bounds `lo[3]` and `hi[3]`, and a scalar threshold `isolevel` [S1, unofficial].
**Outputs:** A triangular mesh consisting of a list of triangles, where each triangle is defined by three vertex indices [S1, unofficial].

**Data Structures:**
*   **Scalar Grid:** A 3D array of floats storing the scalar values at voxel vertices [G].
*   **Vertex Cache:** To avoid redundant interpolation, pre-computed vertex indices on shared edges are stored. The implementation uses specific accessors `get_x_vert`, `get_y_vert`, `get_z_vert` and setters `set_x_vert`, `set_y_vert`, `set_z_vert` indexed by edge coordinates [S1, unofficial].
*   **Triangle:** A struct containing three integers `v1`, `v2`, `v3` representing vertex indices in the output mesh [S1, unofficial].
*   **Lookup Tables:**
    *   `triTable[256][16]`: Maps the 256 cube configurations (bitmasks of vertex signs) to a sequence of triangle edge indices. Each row contains 16 integers; the first integer indicates the number of triangles (0, 1, or 2), followed by pairs of edge indices [S1, unofficial].
    *   `test3[24]`: A lookup table for ambiguous cases that identifies which face to test for ambiguity resolution. The values correspond to specific face indices [S1, unofficial].
    *   `tilingTable`: Contains the specific triangulation edge indices for the ambiguous cases, dependent on the result of the face test [S1, unofficial].

**Algorithm Steps:**

1.  **Initialization:** Initialize an empty list for triangles. Initialize the vertex cache for edge intersections [S1, unofficial].
2.  **Volume Traversal:** Iterate through each unit cube in the grid from `lo` to `hi` inclusive. Let the cube be defined by corner $(i, j, k)$ [S1, unofficial].
3.  **Configuration Evaluation:** For the current cube, evaluate the sign of the scalar value $S$ at each of its 8 vertices relative to `isolevel`. Construct an 8-bit configuration index `cfg` where the $n$-th bit is 1 if $S_n > isolevel$ and 0 otherwise [S1, unofficial].
4.  **Lookup:** Retrieve the triangle count and edge indices from `triTable[cfg]` [S1, unofficial].
5.  **Ambiguity Resolution:** If `cfg` corresponds to an ambiguous case, consult `test3` to determine which face to test [S1, unofficial]. Call `test_face` or `test_interior` to evaluate the scalar field's behavior on that face or interior [S1, unofficial]. Select the appropriate triangulation from `tilingTable` based on the test result [S1, unofficial].
6.  **Intersection Computation:** For each edge index in the selected triangulation:
    a.  Identify the two vertices of the cube connected by the edge.
    b.  Compute the intersection point using linear interpolation:
        $$ P = V_1 + \frac{isolevel - S_1}{S_2 - S_1} (V_2 - V_1) $$
        where $V_1, V_2$ are the cube vertex positions and $S_1, S_2$ are their scalar values [S1, unofficial].
    c.  Store the intersection point in the vertex cache using the appropriate axis-specific setter (`set_x_vert`, `set_y_vert`, `set_z_vert`) to ensure shared edges between adjacent cubes yield identical vertex positions [S1, unofficial].
7.  **Triangle Generation:** For each triangle in the triangulation, create a `Triangle` struct with the indices of the three computed intersection points [S1, unofficial].
8.  **Mesh Assembly:** Add the triangle to the output mesh list [S1, unofficial].

    triangles = []

**Parameters:**
*   `isolevel` (float): The scalar threshold value. Vertices are interpolated where data crosses this value [S1, unofficial].
*   `dim[3]` (int): Volume dimensions [S1, unofficial].
*   `lo[3]` (int): Lower processing bounds [S1, unofficial].
*   `hi[3]` (int): Upper processing bounds [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** Linear interpolation can suffer from precision issues if scalar values are very close to `isolevel`. A small epsilon should be used to avoid division by zero [G].
*   **Boundary Conditions:** The algorithm assumes the scalar field is defined for all vertices in the range `[lo, hi]`. Accessing out-of-bounds vertices must be handled (e.g., by clamping or assuming zero) [G].
*   **Degenerate Input:** If the scalar field is constant, no intersections are generated. If the field has flat regions exactly at `isolevel`, the sign test may be ambiguous; a consistent tie-breaking rule (e.g., `>=` vs `>`) must be chosen [G].

## Operating characteristics
**Time Complexity:** $O(N)$, where $N$ is the number of cubes in the processing volume. Each cube is processed in constant time [G].
**Memory Complexity:** $O(N)$ for the output mesh. The vertex cache size is proportional to the number of unique edges, which is also $O(N)$ [G].
**Measured Performance:** Not given in the sources.
**Scaling:** Scales linearly with volume size. Parallelization is straightforward as cubes are independent [G].
**Strengths:** Guarantees manifold output for all cases [S1, unofficial].
**Limitations:** Requires lookup tables. Ambiguity resolution adds computational overhead compared to standard Marching Cubes [G].

## Background
The Marching Cubes (Lewiner variant) was developed by Thomas Lewiner at the Department of Mathematics, PUC-Rio. Version 0.2 was released on 12/08/2002. A C translation was performed by Ziad S. Saad on November 30, 2004 [S1, unofficial]. It is used in medical imaging and scientific visualization for robust surface extraction.
