# General-purpose Contour Extraction Routine Generator

Also called: ndarray-extract-contour

## Overview
The General-purpose Contour Extraction Routine Generator is a code generator that produces a JavaScript function to extract surfaces from multi-dimensional `ndarray` data structures. It solves the problem of traversing a discretized domain and generating vertices and faces based on phase comparisons between adjacent grid cells [S1, unofficial]. It differs from static isosurface algorithms (like Marching Cubes) by being a meta-algorithm: it accepts callbacks for phase evaluation, vertex creation, and cell (face) creation, allowing the user to define arbitrary topological rules and output formats rather than being restricted to a fixed triangulation scheme [S1, unofficial].

## How it works
The method operates by generating a specialized JavaScript function at runtime. This function iterates over the grid cells in a specified order, maintaining a buffer of phase values for neighboring cells to detect boundaries. When a boundary is detected (a change in phase between adjacent cells), it invokes user-provided callbacks to generate geometry.

### Inputs and Outputs
**Inputs:**
1.  `args`: An object containing the configuration parameters:
    *   `order`: Array specifying the iteration order of array dimensions (e.g., `[1,0]` for 2D).
    *   `arrayArguments`: Integer, number of input `ndarray` objects (must be $\ge 1$).
    *   `scalarArguments`: Integer, number of extra scalar arguments passed to callbacks (must be $\ge 0$).
    *   `phase`: Function `(a, b, s) -> number`. Computes the phase of a cell given array components and scalars.
    *   `vertex`: Function `(x, y, ..., a_{00}, ..., b_{00}, ..., p_{00}, ..., s) -> void`. Adds a vertex to the output. Receives grid coordinates, array values at all $2^D$ corners, phases of all $2^D$ corners, and scalars.
    *   `cell`: Function `(v_0, v_1, ..., a_0, ..., b_0, ..., p_0, ..., s) -> void`. Adds a cell (face) to the output. Receives vertex coordinates, array values for front/back cells, phases, and scalars.
    *   `getters`: Array of booleans indicating whether to use `.get()` or direct bracket access `[]` for array data.
2.  `arrays`: The input `ndarray` objects. Each ndarray has properties: `.data` (typed array), `.shape` (array of dimensions), `.stride` (array of strides), `.offset` (integer offset).
3.  `scalars`: The scalar arguments.

**Outputs:**
*   A JavaScript function `extractContour(...)` that, when called with the arrays and scalars, executes the contour extraction.

### Data Structures
The generated code manages memory using a pool for phase values and vertex IDs.
*   **Phase Buffer (`PHASES`)**: A `Uint32Array` (or equivalent) storing the phase value for each cell.
*   **Vertex ID Buffer (`VERTEX_IDS`)**: A `Uint32Array` mapping the current cell pointer to a unique vertex ID.
*   **Pool Size**: Calculated as $2 \times \prod_{i=0}^{D-2} S_{order[i]}$, where $S$ is the shape and $D$ is the dimension. This size is sufficient to hold the phase/vertex data for the current "slice" and the next, facilitating the sliding window of phase checks [S1, unofficial].

### Algorithm Steps
1.  **Validation**: Ensure `dimension` (length of `order`) is $\ge 2$. If not, throw an error [S1, unofficial].
2.  **Initialization**:
    *   Extract `.data`, `.offset`, `.stride`, and `.shape` for all input arrays.
    *   Initialize pointers to the start of the data (`pointer(i) = offset(i)`).
    *   Compute `delta(i, j)` for each array `i` and corner bitmask `j` ($1 \le j < 2^D$). `delta` is the memory offset to the $j$-th corner of the current cell, calculated by summing strides for set bits in `j` [S1, unofficial].
    *   Compute `step(i, k)` for each array `i` and dimension `k`. This is the memory increment required to move to the next cell in dimension `k`, accounting for wrapping around smaller dimensions [S1, unofficial].
    *   Allocate `PHASES` and `VERTEX_IDS` buffers of size `POOL_SIZE`.
    *   Initialize `POINTER` (index into buffers) to 0 and `VERTEX_COUNT` to 0.
3.  **Iteration**:
    *   The generator creates nested loops based on the `order` array.
    *   For each cell in the grid:
        1.  Read the data values for the current cell's 0-th corner (origin) into local variables `cube(i, 0)`.
        2.  Compute the phase for the current cell using the `phase` callback and store it in `PHASES[POINTER]`.
        3.  Read the pre-computed phases for the other $2^D - 1$ corners from the buffer using `pdelta` offsets. `pdelta` maps the local corner index to the offset in the phase buffer relative to the current pointer.
        4.  **Boundary Check**: Compare the current cell's phase `pcube(0)` with the phases of all other corners `pcube(j)`. If `pcube(0) !== pcube(j)` for any $j$, a boundary crossing exists.
        5.  **Vertex Generation**: If a boundary is detected:
            *   Read the data values for all $2^D$ corners of the cell.
            *   Call the `vertex` callback with coordinates, all corner data, all corner phases, and scalars.
            *   Store the new vertex ID in `VERTEX_IDS[POINTER]` and increment `VERTEX_COUNT`.
        6.  **Face/Cell Generation**:
            *   Check for face crossings. For each dimension $j$, check if the phase of the "base" corner (all bits set, $2^D-1$) differs from the phase of the corner with bit $j$ unset.
            *   If they differ, call the `cell` callback with the relevant vertex IDs, data values, and phases [S1, unofficial].
        7.  Increment `POINTER`.
4.  **Loop Management**:
    *   The generated code handles the iteration order by updating pointers using `step` variables.
    *   When moving to a new slice (higher dimension in `order`), the phase buffer pointer may need to be reset or the `pdelta` values flipped to maintain correct relative indexing for the sliding window [S1, unofficial].
    *   Specifically, `flip()` swaps `pdelta` and `qcube` values to handle the direction of iteration changes [S1, unofficial].
5.  **Cleanup**: Free the allocated `PHASES` and `VERTEX_IDS` buffers.

### Parameters and Typical Values
*   `order`: Typically matches the memory layout for cache efficiency (e.g., `[1, 0]` for row-major 2D).
*   `arrayArguments`: 1 for single-field scalar fields, 2+ for multi-component fields (e.g., vector magnitude calculation in `phase`).
*   `scalarArguments`: 0 for simple thresholding, 1+ for passing isovalue or other constants.
*   `getters`: `true` if the ndarray uses a `.get()` method (common in typed arrays with bounds checking or specific ndarray implementations), `false` for direct indexing.

### Edge Cases and Pitfalls
*   **Dimension < 2**: The algorithm throws an error if the dimension is less than 2. It is designed for 2D and higher [S1, unofficial].
*   **Memory Pool Size**: The pool size calculation `2 * product of shapes` assumes a specific sliding window behavior. If the iteration order or shape dimensions are 1, the logic for `step` and `pdelta` must handle wrapping correctly to avoid out-of-bounds access [S1, unofficial].
*   **Phase Equality**: The boundary check uses strict inequality (`!==`). If the phase function returns NaN, comparisons may fail unexpectedly.
*   **Vertex ID Consistency**: The `VERTEX_IDS` buffer maps the current cell's pointer to a vertex ID. If the pointer wraps or resets incorrectly during loop transitions, vertex IDs may be reused or lost, leading to incorrect mesh connectivity.

## Operating characteristics
*   **Time Complexity**: Proportional to the number of grid cells, $O(N)$, where $N$ is the total number of cells in the domain. The constant factor depends on the dimension $D$ ($2^D$ phase checks per cell) and the cost of the user-provided callbacks.
*   **Memory Complexity**: $O(S)$, where $S$ is the pool size ($2 \times \prod S_i$). This is significantly less than storing the entire grid's phase map if the grid is large, as it only stores the necessary window for the sliding iteration.
*   **Strengths**: Highly flexible; allows custom phase definitions and output primitives (not just triangles). Efficient memory usage due to the sliding window buffer.
*   **Limitations**: The generated code is JavaScript-specific. The interface is complex and "horrible" as noted by the author, making it difficult to use directly without understanding the internal callback signatures [S1, unofficial]. Performance is limited by JavaScript engine overhead compared to native C++ implementations.

## Background
The method is implemented in the `ndarray-extract-contour` library by Mikola Lysenko. It is designed as an internal component for other higher-level surface extraction libraries, such as `surface-nets` [S1, unofficial]. It generalizes the contour extraction process by separating the traversal logic from the geometric interpretation, allowing for various surface reconstruction techniques to be built on top of the same traversal engine.
