# Interval Tree with Cell Grouping

Also called: Grouped Interval Tree

## Overview
The Interval Tree with Cell Grouping is a memory-optimized variant of the Standard Interval Tree for Isosurface Extraction [S1, unofficial]. It reduces the memory overhead of the auxiliary lists by having each pointer reference a group of eight adjacent cells rather than a single cell, resulting in a tree size approximately 1/8th that of a regular interval tree [S1, unofficial]. This reduction comes at the cost of increased query time, as intersecting groups require checking all eight constituent cells individually [S1, unofficial].

## How it works
**Inputs:** A 3D scalar volume grid and an isovalue $q$ [S1, unofficial].
**Outputs:** A list of active cells intersecting the isovalue $q$ [S1, unofficial].

**Data Structures:**
The tree structure mirrors the Standard Interval Tree but uses grouped pointers [S1, unofficial]. Each node contains a splitting value $q_x$ and two auxiliary lists, `I-Left` and `I-Right` [S1, unofficial]. Each pointer in these lists references a group of eight adjacent cells [S1, unofficial]. The volume is partitioned into disjoint groups of eight adjacent cells [S1, unofficial]. Within each group, the cell with the lowest coordinates $(x, y, z)$ serves as the representative [S1, unofficial]. The group's bounding box is defined by the global minimum value $v_{min}$ and global maximum value $v_{max}$ across all eight constituent cells [S1, unofficial].

**Algorithm Steps:**
1. **Construction:** Partition the volume into disjoint groups of eight adjacent cells [S1, unofficial]. For each group, compute the global minimum value $v_{min}$ and global maximum value $v_{max}$ across all eight cells [S1, unofficial]. Insert the group into the interval tree using $v_{min}$ and $v_{max}$ as the interval bounds, treating the group as a single entity [S1, unofficial]. Store the pointer to the group in the appropriate auxiliary lists [S1, unofficial].
2. **Query:** Traverse the tree to find nodes where the interval $[v_{min}, v_{max}]$ intersects the query isovalue $q$ [S1, unofficial]. For each intersecting node, iterate through the `I-Left` and `I-Right` lists [S1, unofficial]. Stop iterating a list as soon as a group is found that does not intersect the query value $q$ [S1, unofficial]. For each intersecting group, check all eight composing cells individually [S1, unofficial]. Check each of the eight cells to determine if the isovalue $q$ lies within their specific scalar range [S1, unofficial].

**Pseudocode:**
```python
def query_grouped_interval_tree(root, q):
    active_cells = []
    traverse(root, q, active_cells)
    return active_cells

def traverse(node, q, active_cells):
    if node is None:
        return
    # Check if node interval intersects q
    if node.max_val < q or node.min_val > q:
        return
    # Iterate I-Left list
    for group in node.i_left:
        if group.max_val < q or group.min_val > q:
            break
        for cell in group.cells:
            if cell.min_val <= q <= cell.max_val:
                active_cells.append(cell)
    # Iterate I-Right list
    for group in node.i_right:
        if group.max_val < q or group.min_val > q:
            break
        for cell in group.cells:
            if cell.min_val <= q <= cell.max_val:
                active_cells.append(cell)
    # Recurse
    if node.left_child:
        traverse(node.left_child, q, active_cells)
    if node.right_child:
        traverse(node.right_child, q, active_cells)
```

**Parameters:**
Group size is fixed at 8 cells per pointer [S1, unofficial].

**Edge Cases and Pitfalls:**
The worst-case query complexity degrades to $O(\log(n) + 8k)$ when the isosurface intersects exactly one cell from each group of eight [S1, unofficial]. This scenario is rare in practical data volumes but represents the theoretical upper bound [S1, unofficial]. Floating-point precision issues may affect boundary conditions where $q$ exactly equals a cell's minimum or maximum value [G].

## Subtopics

### Ordered Grouped Interval Tree
An extension that combines cell grouping with sorting information to accelerate queries [S1, unofficial]. It stores pointers to groups of eight cells in two lists: one sorted in ascending order by the group's minimum value, and the other in decreasing order by the maximum value [S1, unofficial]. For each group, it stores an order vector of eight numbers (1–8) indicating the permutation of cells within the group [S1, unofficial]. This vector requires 3 bits per number, totaling 24 bits (3 bytes) per group [S1, unofficial]. The space overhead is 1.75 bytes per cell, calculated as $2 \times (4 \text{ bytes pointer} + 3 \text{ bytes order}) / 8 \text{ cells}$ [S1, unofficial]. Query times lie between the standard interval tree and the unsorted grouped tree [S1, unofficial].

## Operating characteristics
Query time complexity is $O(\log(n) + 8k)$, where $k$ is the number of active cells in the original un-grouped tree [S1, unofficial]. The factor of 8 arises from the worst-case need to check all sub-cells in intersecting groups [S1, unofficial]. Memory complexity reduces the total interval tree size to approximately 1/8th of a regular interval tree [S1, unofficial]. The tree height is also reduced because it effectively manages 1/8th the number of nodes [S1, unofficial]. Tests on 8-bit volumes demonstrate significant size reduction compared to the standard tree [S1, unofficial]. Query times are slower than the standard interval tree but faster than the unsorted grouped variant when ordering is applied [S1, unofficial]. The method excels when memory is constrained, but suffers from increased query time due to per-cell verification within groups [S1, unofficial].

## Background
The Interval Tree with Cell Grouping was introduced to address the prohibitive memory requirements of standard interval trees for isosurface extraction, which can require up to nine times the size of the volume data [S1, unofficial].
