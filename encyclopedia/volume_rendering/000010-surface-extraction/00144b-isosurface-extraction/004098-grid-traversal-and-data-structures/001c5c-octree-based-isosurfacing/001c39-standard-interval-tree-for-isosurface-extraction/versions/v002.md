# Standard Interval Tree for Isosurface Extraction

Also called: Cignoni et al. Interval Tree, Interval Tree, Interval-Tree Based Isosurface Extraction, Normal Interval Tree

## Overview
The Standard Interval Tree is a spatial indexing structure used to efficiently identify "active cells" (cells intersected by an isosurface) in volumetric data, serving as a pre-processing step for surface extraction algorithms like Marching Cubes or Marching Tetrahedra [S1, S3, unofficial]. It solves the problem of $O(N)$ brute-force traversal by achieving optimal output-sensitive query complexity, reporting only the cells relevant to a specific isovalue [S1, S3, unofficial]. It sets itself apart from its parent [Octree-based Isosurfacing](1247-octree-based-isosurfacing.md) by operating on a fixed Cartesian grid structure rather than an adaptive octree, and from siblings like [Wilhelms and Van Gelder Octree](2107-wilhelms-and-van-gelder-octree.md) by using a binary tree of value intervals rather than a spatial hierarchy, thereby decoupling spatial locality from value-based filtering [S1, S3, unofficial].

## How it works
**Inputs:**
- A structured 3D volume grid of dimensions $\Delta x \times \Delta y \times \Delta z$.
- Scalar field values $V$ for each cell.
- A target isovalue $t$.

**Outputs:**
- A list of active cells whose scalar range $[v_{min}, v_{max}]$ contains $t$.

**Data Structures:**
The interval tree is a binary tree where each node stores a subset of cells.
- **Node Structure:** Each node contains two sorted lists of pointers to cells:
  1. `min-list`: Cells sorted by increasing $v_{min}$.
  2. `max-list`: Cells sorted by decreasing $v_{max}$.
- **Cell Storage:** Each cell reference in the lists stores:
  - $v_{min}$: Minimum scalar value in the cell (2 bytes).
  - $v_{max}$: Maximum scalar value in the cell (2 bytes).
  - Pointer to the cell data (4 bytes).
  - Total per-cell overhead: 12 bytes [S3, unofficial].
- **Tree Construction:**
  1. Calculate $v_{min}$ and $v_{max}$ for every cell in the volume.
  2. Choose a threshold $t_0$ (typically the median of all $v_{min}$ and $v_{max}$ values to balance the tree) [S3, unofficial].
  3. Partition cells into three sets:
     - $S_{contain}$: Cells where $v_{min} \le t_0 \le v_{max}$.
     - $S_{below}$: Cells where $v_{max} < t_0$.
     - $S_{above}$: Cells where $v_{min} > t_0$.
  4. Store $S_{contain}$ in the current node's `min-list` and `max-list`.
  5. Recursively build the left child from $S_{below}$ and the right child from $S_{above}$ [S3, unofficial].

**Query Algorithm:**
To find all active cells for isovalue $t$:
1. Start at the root node with threshold $t_0$.
2. If $t < t_0$:
   - Iterate through the `min-list`. Report all cells where $v_{min} \le t$.
   - Stop when encountering a cell with $v_{min} > t$ (since the list is sorted ascending, subsequent cells will also fail).
   - Recurse into the left child.
3. If $t > t_0$:
   - Iterate through the `max-list`. Report all cells where $v_{max} \ge t$.
   - Stop when encountering a cell with $v_{max} < t$ (since the list is sorted descending, subsequent cells will also fail).
   - Recurse into the right child.
4. If $t = t_0$:
   - Report all cells in the current node's lists.
   - Terminate search (no further recursion needed as all containing intervals are stored here) [S3, unofficial].

**Pseudocode:**

```python
def query_interval_tree(node, t):
    """
    Recursively query the interval tree for cells containing isovalue t.
    node: The current tree node containing min_list and max_list.
    t: The target isovalue.
    node.threshold: The threshold t0 used to partition this node.
    """
    active_cells = []
    
    # Case 1: Target is below the node's threshold
    if t < node.threshold:
        # Check min-list (sorted by increasing vmin)
        for cell in node.min_list:
            if cell.vmin <= t:
                active_cells.append(cell)
            else:
                # Since vmin is increasing, all subsequent cells will have vmin > t
                break
        
        # Recurse left
        if node.left_child is not None:
            active_cells.extend(query_interval_tree(node.left_child, t))
            
    # Case 2: Target is above the node's threshold
    elif t > node.threshold:
        # Check max-list (sorted by decreasing vmax)
        for cell in node.max_list:
            if cell.vmax >= t:
                active_cells.append(cell)
            else:
                # Since vmax is decreasing, all subsequent cells will have vmax < t
                break
        
        # Recurse right
        if node.right_child is not None:
            active_cells.extend(query_interval_tree(node.right_child, t))
            
    # Case 3: Target equals the node's threshold
    else: # t == node.threshold
        # All cells in this node contain the threshold
        active_cells.extend(node.min_list)
        # Note: min_list and max_list may contain duplicates if implemented naively,
        # but typically one list is sufficient or duplicates are handled by the caller.
        # Based on [S3, unofficial], the entire list is reported.
        
    return active_cells
```

**Parameters:**
- **Pointer Size:** 4 bytes [S1, unofficial].
- **Value Type:** Typically 2 bytes (16-bit) for $v_{min}, v_{max}$ [S3, unofficial].
- **Threshold Selection:** Not explicitly defined in sources, but optimal balance requires median selection [S3, unofficial].

**Edge Cases and Pitfalls:**
- **Precision:** Floating-point comparisons must handle the equality case $t = t_0$ carefully to avoid missing cells or double-counting if lists overlap [S3, unofficial].
- **Memory Overhead:** The structure is space-inefficient. For 8-bit volumes, the total space usage is approximately 9 times the size of the raw volume data (1x volume + 8x overhead for pointers and lists) [S1, unofficial].
- **Degenerate Input:** If all cells have the same $v_{min}$ and $v_{max}$, the tree depth becomes 1, and all cells are stored in the root. Query time becomes $O(k)$ but construction is trivial [S3, unofficial].

## Subtopics

### [Fixed-Sized Buckets for Isosurface Extraction](1252-fixed-sized-buckets-for-isosurface-extraction.md)
Fixed-Sized Buckets is an output-optimal algorithm for accelerated isosurface extraction from volumetric data sets. It identifies active cells (cells intersected by the isosurface) with work proportional to the output size rather than the input size, using a logical 2D array data structure to sort cells by intensity ranges. It sets itself apart from its parent [Standard Interval Tree for Isosurface Extraction](1230-standard-interval-tree-for-isosurface-extraction.md) by using a simpler array-based structure that avoids tree traversal overhead, and from siblings like [Interval Table for Isosurface Extraction](4357-interval-table-for-isosurface-extraction.md) by relying on two-pass sorting rather than interval merging.

### [Interval Tree with Cell Grouping](1342-interval-tree-with-cell-grouping.md)
The Interval Tree with Cell Grouping is a memory-optimized variant of the Standard Interval Tree for Isosurface Extraction. It reduces the memory overhead of the auxiliary lists by having each pointer reference a group of eight adjacent cells rather than a single cell, resulting in a tree size approximately 1/8th that of a regular interval tree. This reduction comes at the cost of increased query time, as intersecting groups require checking all eight constituent cells individually.

### [Span Space Isosurface Extraction](1750-span-space-isosurface-extraction.md)
Span Space Isosurface Extraction is a method for rapidly locating cells intersecting an isosurface in large scalar datasets by mapping cell extrema to a 2D "span space" and indexing them with a kd-tree. It solves the problem of efficient interval search by reducing the dimensionality of the query from interval containment to point location relative to the diagonal $y=x$. Unlike the Standard Interval Tree for Isosurface Extraction, which achieves $O(\log n + k)$ query complexity, this method achieves a worst-case search complexity of $O(\sqrt{n} + k)$. It is chosen when a simpler, pointerless kd-tree implementation is preferred over complex interval tree structures, accepting a slightly higher worst-case asymptotic bound for potentially better constant factors and memory locality.

### [Out-of-core Interval Tree Extraction](2146-out-of-core-interval-tree-extraction.md)
Out-of-core Interval Tree Extraction is a method for isosurface extraction that stores the interval tree and associated min/max lists on disk in blocks, loading only the necessary blocks based on isovalue intervals. It builds on [Standard Interval Tree for Isosurface Extraction](1230-standard-interval-tree-for-isosurface-extraction.md) by partitioning the tree structure to fit within fixed-size disk blocks, enabling the processing of datasets larger than available main memory. Unlike its siblings, it explicitly models the I/O cost of reading tree nodes and min/max lists as a function of isovalue probability distributions.

### [Interval Table for Isosurface Extraction](4357-interval-table-for-isosurface-extraction.md)
The Interval Table is a pre-processing data structure that maps scalar value intervals to tetrahedron IDs, allowing the extraction algorithm to skip tetrahedra whose function span does not contain the isovalue. It differs from the Standard Interval Tree by using a fixed-size array of buckets (intervals) rather than a dynamic tree structure, offering a simpler implementation with comparable performance for uniform scalar distributions.

### [Search Data Structure Based Isosurface Extraction](6738-search-data-structure-based-isosurface-extraction.md)
Search Data Structure Based Isosurface Extraction is a family of methods that utilize external search structures (indices) to accelerate isosurface extraction for multiple queries on the same dataset. By creating an index that allows the algorithm to disregard regions containing only non-active cells, these methods achieve significant performance gains over brute-force traversal when repeated queries are required. This approach is distinct from single-pass methods because the overhead of index construction must be amortized over multiple queries; it is not feasible if the dataset is examined only once or if the index transfer overhead is prohibitive.

### Matryoshka Layer Insertion
Matryoshka Layer Insertion is a data structure construction where cells are inserted into layers defined by six planes (X=x0, X=x1, Y=y0, Y=y1, Z=z0, Z=z1) based on coordinate minima, allowing O(1) insertion and O(k) total construction time for k cells [S1, unofficial]. The algorithm calculates `min*1` as the minimum of the cell's coordinates $(cellx, celly, cellz)$ and `min*2` as the minimum of the distances to the opposite boundaries $((\Delta x-1)-cellx, (\Delta y-1)-celly, (\Delta z-1)-cellz)$. The layer index is the minimum of `min*1` and `min*2`. Inside the layer, the cell is inserted into the appropriate plane list based on which coordinate matches the boundary plane. To avoid a second processing round, this insertion is merged into the query process of the interval tree [S1, unofficial]. Construction complexity is $O(k)$ where $k$ is the number of active cells, with memory overhead directly proportional to $k$ [S1, unofficial].

### Edge-Covering Space Reduction
Edge-Covering Space Reduction is a space reduction technique for interval/kd-trees by restricting the data structure to a subset of cells that covers all edges, reducing storage by a factor of 4 [S3, unofficial]. The method selects a subset of cells such that every edge in the volume grid is covered by at least one selected cell. Since an edge is shared by four cells, only one out of four neighboring cells needs to be considered. After extraction from the data structure, the isosurface is propagated from the reported active cells onto neighboring cells that were not covered in the data structure. This increases extraction time but significantly reduces memory requirements [S3, unofficial].

## Operating characteristics
- **Time Complexity:** Query time is $O(\log n + k)$, where $n$ is the number of cells and $k$ is the number of active cells reported [S1, S3, unofficial]. In practice, for scalar volumes, $k$ dominates $\log n$ as active cells often number in the hundreds of thousands or millions [S1, unofficial]. Search complexity is also described as $O(k + \log h)$, where $h$ is the number of nodes in the tree [S3, unofficial].
- **Memory Complexity:** $O(n)$. The space overhead is significant. For a volume of size $(\Delta x - 1)(\Delta y - 1)(\Delta z - 1)$, the overhead is $8(\Delta x - 1)(\Delta y - 1)(\Delta z - 1)$ bytes for pointers alone (2 pointers per cell, 4 bytes each), plus the volume data itself, totaling 9 times the volume size [S1, unofficial]. A more precise analysis for general interval trees states memory overhead is $3h + 2m$ words, where $h$ is the number of distinct extremes and $m$ is the number of cells [S2, book].
- **Strengths:** Optimal output-sensitive performance for single-query isosurface extraction; significantly faster than brute-force traversal for sparse isosurfaces [S2, book].
- **Limitations:** High memory consumption makes it prohibitive for very large high-resolution datasets without variants like Cell Grouping or Edge-Covering [S1, S3, unofficial].
- **When to use:** When memory is sufficient and fast single-query extraction is required.
- **When not to use:** When memory is constrained (use [Interval Tree with Cell Grouping](1342-interval-tree-with-cell-grouping.md) or [Edge-Covering Space Reduction]) or when multiple queries are needed (consider [Search Data Structure Based Isosurface Extraction](6738-search-data-structure-based-isosurface-extraction.md)).

## Background
The Standard Interval Tree for isosurface extraction was proposed by Cignoni, Marino, Montani, and Puppo [S1, S3, unofficial]. It was introduced as an alternative to kd-trees for spatial indexing in volume visualization, addressing the space inefficiency of kd-trees while maintaining optimal query complexity [S3, unofficial]. The method is detailed in the *Visualization Handbook* (2005) and various conference papers [S1, unofficial][S2, book]. It is widely used in scientific visualization pipelines where adaptive resolution is not required, but speed of active cell identification is critical [S2, book].
