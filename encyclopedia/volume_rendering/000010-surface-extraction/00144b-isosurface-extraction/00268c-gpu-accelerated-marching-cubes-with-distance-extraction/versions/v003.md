# GPU-accelerated Marching Cubes with Distance Extraction

Also called: WebGL Signed Distance Function Mesher, glsl-marching-cubes

## Overview
This method extracts a triangular mesh (STL) from a Signed Distance Function (SDF) by offloading the scalar field evaluation to the GPU via a fragment shader, while performing the topological connectivity and mesh generation on the CPU. It differs from pure GPU implementations by avoiding the performance penalty of reading large volumes of vertex data back from GPU memory, and from pure CPU implementations by leveraging the GPU's parallelism for the expensive distance function evaluations [S1, unofficial].

## How it works
**Inputs:**
- A signed distance function $f(x, y, z)$ defined in GLSL.
- Volume dimensions `dims` (array of 3 integers: $N_x, N_y, N_z$).
- Volume bounds `bounds` (array of 2 arrays of 3 floats: min and max coordinates).

**Outputs:**
- A triangular mesh (STL format).

**Data Structures:**
- `volume`: An object containing:
  - `dims`: Array of 3 integers.
  - `bounds`: Array of 2 arrays of 3 floats.
  - `vertexCount`: Integer, calculated as $(N_x + 1)(N_y + 1)(N_z + 1)$.
  - `size`: Integer, the texture dimension required to store vertices, calculated as $\lceil \sqrt{\text{vertexCount}} \rceil$.
- `blockPotentialBuffers`: An array of `ArrayBuffer` objects. Each buffer has size `volume.vertexCount * 4` bytes, storing `Float32` values.

**Parameters:**
- `maxSize`: Maximum texture size for the GPU rendering buffer. Capped at 4096 [S1, unofficial].
- `numWorkers`: Number of worker threads for parallel processing. Default 4 [S1, unofficial].
- `blocks`: Number of chunks to split the volume into for worker distribution. Default 256 [S1, unofficial].

**Steps:**

1.  **Volume Subdivision**:
    The volume defined by `dims` and `bounds` is subdivided into smaller blocks (chunks) such that the vertex data for each block fits within a square texture of size `maxSize` $\times$ `maxSize`. The total number of vertices per block is limited by `maxSize`$^2$.

2.  **Distance Extraction (GPU)**:
    For each block:
    a.  Initialize `numWorkers` `ArrayBuffer`s of size `volume.vertexCount * 4` bytes.
    b.  Map the block's vertices to a 2D texture coordinate space.
    c.  Render a full-screen quad (or appropriate geometry) using a fragment shader that evaluates the SDF $f(x, y, z)$ for each vertex position.
    d.  Read the resulting pixel values (distances) from the GPU framebuffer using `gl.readPixels`.
    e.  Store these distances in the `blockPotentialBuffers`.

3.  **Block Filtering**:
    Analyze the extracted distances for each block. If all vertices in a block have distances $> 0$ (outside) or all have distances $< 0$ (inside), the block is skipped. This optimization saves CPU processing time for empty or fully contained regions [S1, unofficial].

4.  **Marching Cubes (CPU)**:
    For each non-skipped block:
    a.  Pass the distance values to a CPU-based Marching Cubes implementation.
    b.  Generate triangles based on the standard Marching Cubes lookup tables.
    c.  Output the triangles.

5.  **Mesh Assembly**:
    Combine the triangles from all blocks into a final mesh. Note that adjacent blocks may produce duplicate vertices or edges if not handled by a global vertex merging step, though the source implementation notes that large meshes are saved in parts and may require external tools like MeshLab for recombination [S1, unofficial].

## Operating characteristics
- **Time Complexity**: Dominated by the GPU fragment shader evaluation for distance calculation and the CPU-based Marching Cubes traversal. The GPU acceleration reduces the cost of distance evaluation compared to a pure CPU approach, but the CPU bottleneck remains for mesh generation.
- **Memory Complexity**: Requires storing vertex distances for each block. The memory footprint is proportional to the number of vertices in the volume, specifically `vertexCount * 4` bytes per block.
- **Performance**: The method is faster than running the entire algorithm on the GPU due to the high cost of reading large amounts of data back from GPU memory [S1, unofficial]. It is slower than a pure CPU implementation for simple models because of the overhead of GPU-CPU communication and shader compilation, but scales better for complex SDFs [S1, unofficial].
- **Strengths**: Efficient for complex SDFs where distance evaluation is expensive; reduces GPU/CPU round trips by batching distance extraction.
- **Limitations**: Large meshes are saved in parts and must be recombined externally; missing triangles (holes) may appear in the resulting mesh [S1, unofficial]. The method is specific to WebGL/GLSL environments.

## Background
This method was developed as part of the `glsl-marching-cubes` project by tdhooper, leveraging WebGL and Three.js to provide a browser-based signed distance function mesher [S1, unofficial]. It addresses the limitation of pure CPU Marching Cubes for complex implicit surfaces and the performance issues of pure GPU implementations in web contexts.
