# Dual Contouring with Schmitz Particle Method

Also called: CalculateCellVertex, DC with Schmitz Particles, Schmitz Particle Method, Schmitz Particle Vertex Smoothing, Voxel terrain meshing

## Overview
A mesh generation and vertex smoothing technique that refines vertex positions within voxel cells by accumulating forces derived from surface intersection data (position and normal) at cell corners [S1, unofficial]. It sets itself apart from standard Dual Contouring by replacing the Quadratic Error Function (QEF) minimization with an iterative force-based optimization using "Schmitz particles," which is particularly suited for GPU compute shaders in voxel terrain generation where material indices and smooth texture transitions are required [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A voxel volume buffer containing CSG operations, world space offset, intersection data (position, normal, material index) at cell corners, and optimization parameters.
*   **Output:** A mesh with vertices positioned inside cells, each associated with a dominant material index and smoothed normals.

**Data Structures:**
*   `Intersection`: `float3 position`, `float3 normal`, `uint materialIndex` [S1, unofficial].
*   `CellVertexInfo`: `uint index`. Initialized to `nullVertexIndex` (-1) [S1, unofficial].
*   `GPUVertex`: Contains material index information, retrieved via `Mesh.MeshData.GetVertexData<GPUVertex>` [S1, unofficial].
*   `GPUVoxelVolumeCSGOperation`: Struct for CSG operations buffer, size defined by `GPUVoxelVolumeCSGOperation.SizeInBytes` [S1, unofficial].
*   `GPUGenerationGraphNode`: Struct for generation graph nodes buffer, size defined by `GPUGenerationGraphNode.SizeInBytes` [S1, unofficial].

**Parameters:**
*   `VoxelVolumeToWorldSpaceOffset`: `vector3` defining the world space offset of the voxel volume [S1, unofficial].
*   `maxNumberOfIntersections`: Maximum intersections stored per cell. Value: 6 [S1, unofficial].
*   `schmitzParticleIterations`: Number of smoothing iterations [S1, unofficial].
*   `schmitzParticleStepSize`: Step size for each Schmitz particle iteration [S1, unofficial].
*   `NumberOfVoxelVolumeCSGOperations`: Integer indicating the number of CSG operations in the buffer [S1, unofficial].

**Algorithm Steps:**

1.  **Generate Voxel Volume:** Set the `VoxelVolumeToWorldSpaceOffset` and voxel volume buffer on the compute shader. Dispatch the compute shader with the number of voxels as the thread group count [S1, unofficial].
2.  **Apply CSG Operations:** Iterate through the list of CSG operations in chunks of size 'stride' (limited by buffer capacity `m_voxelVolumeCSGOperationsBufferCapacity`). For each chunk, set the operations buffer and count, then dispatch the compute shader [S1, unofficial].
3.  **Request Mesh Generation:** Call `WorldManager.DualContouring.RequestMeshAsync` with the voxel volume buffer, current LOD, target LOD, vertex count, triangle count, world position, and a callback delegate [S1, unofficial].
4.  **Initialize Vertex:** For each cell, initialize the vertex with the center position (average of intersection positions) and average normal (normalized). Determine the `materialIndex` using `GetDominantMaterialIndex()` [S1, unofficial].
5.  **Calculate Corner Forces:** For each of the 8 cell corners, calculate the force vector:
    *   Calculate distance from corner to plane: $d = \text{dot}(\text{normal}, \text{corner} - \text{position})$.
    *   Calculate voxel corner to plane vector: $\vec{v} = -d \times \text{normal}$.
    *   Store these as `forces[cornerIndex]` [S1, unofficial].
6.  **Calculate Combined Force:** Interpolate forces between opposite corners of the cell using barycentric-like weights based on the vertex's center coordinates $(x, y, z)$, mapped to $(\alpha, \gamma, \beta)$ for interpolation order:
    *   Interpolate along X:
        *   $F_{03} = (1-\alpha)F_0 + \alpha F_3$
        *   $F_{47} = (1-\alpha)F_4 + \alpha F_7$
        *   $F_{12} = (1-\alpha)F_1 + \alpha F_2$
        *   $F_{56} = (1-\alpha)F_5 + \alpha F_6$
    *   Interpolate along Z:
        *   $F_{0347} = (1-\gamma)F_{03} + \gamma F_{47}$
        *   $F_{1256} = (1-\gamma)F_{12} + \gamma F_{56}$
    *   Interpolate along Y:
        *   $\vec{F}_{final} = (1-\beta)F_{0347} + \beta F_{1256}$
    *   Where $\alpha=x, \beta=y, \gamma=z$ [S1, unofficial].
7.  **Iterative Smoothing:** Iterate `schmitzParticleIterations` times:
    *   Update vertex position: $\text{vertex}.SetPosition(\text{vertex}.GetPosition() + \text{schmitzParticleStepSize} \times \vec{F}_{final})$ [S1, unofficial].
8.  **Transform Position:** Transform the final vertex position from local space to voxel volume space: $\text{vertex}.SetPosition(\text{VoxelToVoxelVolumeSpace}(\text{coordinate}, \text{vertex}.GetPosition()))$ [S1, unofficial].

MAX_INTERSECTIONS = 6

# Data Structures
class Intersection:
    position: float3
    normal: float3
    materialIndex: uint

    index: uint = NULL_VERTEX_INDEX

class GPUVertex:
    materialIndex: uint

# Helper: Get Dominant Material Index
def GetDominantMaterialIndex(intersections: list[Intersection], num_intersections: int) -> uint:
    # Count occurrences of each material index in the cell corners
    # Store counts in uint4 arrays to save registers
    counts = [0] * 256 # Assuming uint8 material indices, or appropriate size
    for i in range(num_intersections):
        mat_idx = intersections[i].materialIndex
        counts[mat_idx] += 1
    
    max_count = 0
    dominant_idx = 0
    for i in range(256):
        if counts[i] > max_count:
            max_count = counts[i]
            dominant_idx = i
    return dominant_idx

# Helper: Calculate Force for a single corner
def CalculateForce(corner_pos: float3, intersection: Intersection) -> float3:
    # distance = dot(normal, corner - position)
    distance = dot(intersection.normal, corner_pos - intersection.position)
    # voxelCornerToPlaneVector = -distance * normal
    return -distance * intersection.normal

# Main Vertex Generation Kernel
def GenerateCellVertex(cell_corners: list[float3], cell_intersections: list[Intersection], num_intersections: int, 
                       center_pos: float3, center_normal: float3, alpha: float, beta: float, gamma: float) -> GPUVertex:
    
    # Initialize vertex
    vertex_pos = center_pos
    vertex_normal = normalize(center_normal)
    vertex_mat_idx = GetDominantMaterialIndex(cell_intersections, num_intersections)
    
    # Calculate forces for each cell corner
    forces = [CalculateForce(cell_corners[i], cell_intersections[i]) for i in range(8)]
    
    # Iterative Schmitz Particle Smoothing
    for _ in range(schmitzParticleIterations):
        # Calculate Combined Force using barycentric-like weights
        # Interpolate along X
        force_03 = lerp(forces[0], forces[3], alpha)
        force_47 = lerp(forces[4], forces[7], alpha)
        force_12 = lerp(forces[1], forces[2], alpha)
        force_56 = lerp(forces[5], forces[6], alpha)
        
        # Interpolate along Z
        force_0347 = lerp(force_03, force_47, gamma)
        force_1256 = lerp(force_12, force_56, gamma)
        
        # Interpolate along Y
        combined_force = lerp(force_0347, force_1256, beta)
        
        # Update position
        vertex_pos = vertex_pos + schmitzParticleStepSize * combined_force
        
    # Transform to voxel volume space
    vertex_pos = VoxelToVoxelVolumeSpace(cell_corners[0], vertex_pos) # coordinate derived from cell
    
    return GPUVertex(materialIndex=vertex_mat_idx)

**Edge Cases and Pitfalls:**
*   **CSG Operation Buffer Capacity:** The number of CSG operations processed per dispatch is limited by the buffer capacity. Operations must be processed in chunks to handle larger lists [S1, unofficial].
*   **Register Usage:** Static arrays (intersections, forces, etc.) should be declared globally/statically rather than passed as function parameters to avoid excessive temporary register usage by the compiler [S1, unofficial].
*   **Material Index Handling:** If neighboring vertices have different material indices, duplicate the neighboring vertices, assign the same material index to the duplicates, and form the triangle using the current cell's vertex and the neighboring duplicates [S1, unofficial].

## Subtopics

### Linear Edge Intersection for Dual Contouring
*   **What it is:** A method for determining intersection points on cell edges using linear interpolation.
*   **Difference:** Provides the raw intersection data used by Schmitz Particle Method; does not handle vertex placement or smoothing.
*   **When to choose:** When precise edge intersection calculation is needed before applying vertex optimization.
*   **Link:** [Linear Edge Intersection for Dual Contouring](926-linear-edge-intersection-for-dual-contouring.md)

### Occupancy Dual Contouring
*   **What it is:** A variant of Dual Contouring that uses occupancy data rather than explicit normals for vertex placement.
*   **Difference:** Simpler data requirements but potentially less accurate surface representation compared to normal-based methods like Schmitz Particles.
*   **When to choose:** When only binary occupancy data is available.
*   **Link:** [Occupancy Dual Contouring](3665-occupancy-dual-contouring.md)

### Dual Contouring on Octree
*   **What it is:** Dual Contouring adapted for octree data structures.
*   **Difference:** Handles hierarchical data and variable resolution, whereas Schmitz Particle Method typically operates on uniform voxel grids.
*   **When to choose:** For scenes requiring adaptive resolution.
*   **Link:** [Dual Contouring on Octree](4469-dual-contouring-on-octree.md)

### Dual Contouring Octree Data Structures
*   **What it is:** Specific data structures for storing octree-based Dual Contouring data.
*   **Difference:** Focuses on memory layout and traversal efficiency for octrees.
*   **When to choose:** When implementing Octree-based Dual Contouring.
*   **Link:** [Dual Contouring Octree Data Structures](5012-dual-contouring-octree-data-structures.md)

### Dual Contouring Feature Point Iterative Projection
*   **What it is:** An iterative method to project vertices onto feature points.
*   **Difference:** Uses feature points for convergence, whereas Schmitz Particle Method uses force accumulation from all corners.
*   **When to choose:** When preserving sharp features is critical.
*   **Link:** [Dual Contouring Feature Point Iterative Projection](8388-dual-contouring-feature-point-iterative-projection.md)

### Dual Contouring Edge Normal Calculation
*   **What it is:** Methods for calculating normals at edge intersections.
*   **Difference:** Provides the input normals for Schmitz Particle Method.
*   **When to choose:** When accurate normals are needed for the force calculation.
*   **Link:** [Dual Contouring Edge Normal Calculation](8397-dual-contouring-edge-normal-calculation.md)

### DCx (Dual Contouring over Expanded Cubes)
*   **What it is:** A variant that expands the cube to handle more complex intersections.
*   **Difference:** Handles cases where standard Dual Contouring fails due to complex topology.
*   **When to choose:** For complex voxel terrains with overhangs or tunnels.
*   **Link:** [DCx (Dual Contouring over Expanded Cubes)](9342-dcx-dual-contouring-over-expanded-cubes.md)

### Fast Dual Contouring
*   **What it is:** Optimizations for speed in Dual Contouring.
*   **Difference:** Focuses on computational efficiency, potentially sacrificing some accuracy or feature preservation.
*   **When to choose:** When performance is the primary constraint.
*   **Link:** [Fast Dual Contouring](15258-fast-dual-contouring.md)

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of voxels and CSG operations, with an additional factor of `schmitzParticleIterations` for the smoothing step.
*   **Memory Complexity:** Linear with respect to the number of voxels for storing vertex information and intersection data.
*   **Measured Performance:** Performance is heavily dependent on GPU compute shader efficiency and register usage. Processing CSG operations in chunks is necessary to avoid buffer overflow [S1, unofficial].
*   **Scaling:** Scales well with GPU parallelism, but readback to CPU can be a bottleneck [S1, unofficial].
*   **Strengths:** Suitable for GPU implementation, handles material indices and smooth texture transitions via geometry shaders [S1, unofficial].
*   **Limitations:** Requires careful management of buffer capacities and register usage. Readback to CPU may be suboptimal [S1, unofficial].
*   **When to use:** Voxel terrain generation with multiple materials and smooth texture blending.
*   **When not to use:** When strict QEF-based accuracy is required or when CPU-side processing is preferred.

## Background
The Schmitz Particle Method is an implementation detail from a GPU-based voxel terrain generation project, specifically designed to handle multiple materials and smooth texture transitions in Unity [S1, unofficial]. It was developed as part of a broader effort to implement various voxel terrain algorithms, including Marching Cubes and Cubical Marching Squares, with a focus on performance and feature completeness like Level of Detail (LOD) [S1, unofficial]. The method was published as an open-source project on GitHub, though the author noted that the implementation might be suboptimal due to the need for CPU readback and lack of complete feature set [S1, unofficial].
