# CPU Immediate Mode Marching Cubes

Also called: CPU Immediate Sim, Immediate Mode Marching Cubes, Legacy Marching Cubes

## Overview
CPU Immediate Mode Marching Cubes is a classic surface extraction method that computes a 3D scalar field on the CPU and renders the resulting isosurface directly to the GPU via immediate-mode draw calls, without storing a persistent mesh buffer in system memory [S1, unofficial]. It differs from buffered approaches by generating and flushing geometry in small batches every frame, making it suitable for dynamic scenes like metaballs where the field changes frequently, but it suffers from CPU bottlenecks at high resolutions or high blob counts [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D grid of voxels (resolution $N_x \times N_y \times N_z$), a set of metaball sources (position, radius, strength), and an isovalue $I$.
*   **Output:** A stream of triangle vertices and normals rendered to the screen.

**Data Structures:**
The implementation relies on the precomputed lookup tables defined in [Marching Cubes Lookup and Configuration](2518-marching-cubes-lookup-and-configuration.md):
1.  `edgeTable`: 256-entry array of 12-bit integers.
2.  `triangleTable`: $256 \times 16$ array of integers.

**Buffers (Immediate Mode State):**
To support immediate rendering, the CPU maintains typed arrays in memory that act as a temporary buffer before being uploaded to the GPU [S1, unofficial]:
*   `posArray`: `Float32Array` of size `maxCount * 3`. Stores vertex positions $(x, y, z)$.
*   `normalArray`: `Float32Array` of size `maxCount * 3`. Stores vertex normals $(nx, ny, nz)$.
*   `uvArray`: `Float32Array` of size `maxCount * 2`. (Optional, not always used in basic metaball demos).
*   `colorArray`: `Float32Array` of size `maxCount * 4`. (Optional).
*   `maxCount`: A fixed integer, typically 4096, defining the maximum number of vertices the buffer can hold before flushing [S1, unofficial].
*   `count`: An integer tracking the current number of vertices stored in the arrays.

**Algorithm Steps:**

1.  **Field Generation:**
    For each voxel corner $(i, j, k)$ in the grid, compute the scalar field value $V(i, j, k)$ by summing contributions from all metaballs and a floor term [S1, unofficial]. For a metaball with center $C_m$, radius $R_m$, and strength $S_m$, the contribution is typically:
    $$ V_m(x, y, z) = \frac{S_m}{(x-C_{mx})^2 + (y-C_{my})^2 + (z-C_{mz})^2} $$
    The total value is $V(i, j, k) = \sum_m V_m(i, j, k) + V_{floor}$ [S1, unofficial].

2.  **Primitive Batching Initialization:**
    Before processing voxels, initialize the rendering state [S1, unofficial]:
    *   Set primitive type `prim` (e.g., `TRIANGLES`).
    *   Set `primsize` (3 for triangles).
    *   Reset `count` to 0.
    *   Reset flags `hasPos`, `hasNormal`, `hasUV`, `hasColor` to false.

3.  **Voxel Processing:**
    Iterate through every voxel in the grid. For each voxel:
    a.  **Case Index Calculation:** Determine the 8-bit case index $C$ by comparing the scalar field values $V(v_i)$ at the 8 corners $v_i$ ($i=0..7$) against the isovalue $I$. If $V(v_i) < I$, set bit $i$ of $C$ to 1; otherwise 0 [S7, S8, S12, unofficial].
    b.  **Lookup:** Retrieve the edge intersection mask from `edgeTable[C]` and the triangle configuration from `triangleTable[C]`.
    c.  **Edge Intersection:** For each intersected edge $e_k$ (where bit $k$ is set in the mask):
        i.  Identify the two vertices $v_a, v_b$ of the edge.
        ii. Interpolate the intersection point $P$ and its normal $N$ using linear interpolation based on the field values at $v_a$ and $v_b$.
        iii. **Add Vertex:** Call `addVertexPosition(P.x, P.y, P.z)` and `addVertexNormal(N.x, N.y, N.z)`.
    d.  **Add Triangles:** For each triplet $(a, b, c)$ in `triangleTable[C]` (until `-1` is reached):
        i.  Retrieve the positions and normals for the three vertices corresponding to edges $a, b, c$.
        ii. Call `addTriangle(o1, o2, o3)` where $o1, o2, o3$ are the offsets in `posArray` and `normalArray` for the three vertices.
        iii. **Overflow Check:** If `count >= maxCount - 3`, call `draw()` to flush the buffer [S1, unofficial].

4.  **Buffer Management (Pseudocode):**
    The following functions manage the immediate mode buffers [S1, unofficial]:

    ```python
    # Global state
    posArray = Float32Array(maxCount * 3)
    normalArray = Float32Array(maxCount * 3)
    count = 0
    maxCount = 4096

    def addVertexPosition(x, y, z):
        """Store vertex position and set flag."""
        idx = count * 3
        posArray[idx + 0] = x
        posArray[idx + 1] = y
        posArray[idx + 2] = z
        hasPos = true

    def addVertexNormal(x, y, z):
        """Store vertex normal and set flag."""
        idx = count * 3
        normalArray[idx + 0] = x
        normalArray[idx + 1] = y
        normalArray[idx + 2] = z
        hasNormal = true

    def addTriangle(o1, o2, o3):
        """
        Copy vertex data from offsets o1, o2, o3 into the current count slot.
        o1, o2, o3 are indices into posArray/normalArray (in vertex units, not byte units).
        """
        # Copy positions
        for k in range(3):
            posArray[count * 3 + k] = posArray[o1 * 3 + k]
            posArray[count * 3 + 1 + k] = posArray[o2 * 3 + k] # Note: Source implies copying specific offsets, 
            posArray[count * 3 + 2 + k] = posArray[o3 * 3 + k] # Simplified for 3 vertices per triangle
            
        # Copy normals
        for k in range(3):
            normalArray[count * 3 + k] = normalArray[o1 * 3 + k]
            normalArray[count * 3 + 1 + k] = normalArray[o2 * 3 + k]
            normalArray[count * 3 + 2 + k] = normalArray[o3 * 3 + k]
            
        count += 3
        
        # Flush if buffer is full
        if count >= maxCount - 3:
            draw()

    def draw():
        """Flush the current buffer to the GPU."""
        if count == 0:
            return
            
        # Zero out remaining buffer space to prevent garbage data
        for i in range(count * 3, maxCount * 3):
            posArray[i] = 0
        for i in range(count * 3, maxCount * 3):
            normalArray[i] = 0
            
        # Upload to GPU
        # gl.bufferData(GL_ARRAY_BUFFER, posArray, DYNAMIC_DRAW)
        # gl.bufferData(GL_ARRAY_BUFFER, normalArray, DYNAMIC_DRAW)
        
        # Enable attributes and set pointers
        # gl.enableVertexAttribArray(posLoc)
        # gl.vertexAttribPointer(posLoc, 3, FLOAT, false, 0, 0)
        # gl.enableVertexAttribArray(normalLoc)
        # gl.vertexAttribPointer(normalLoc, 3, FLOAT, false, 0, 0)
        
        # Render
        # gl.drawArrays(TRIANGLES, 0, count)
        
        # Reset state
        count = 0
    ```

5.  **Final Flush:**
    After all voxels are processed, if `count > 0`, call `draw()` one last time to render the remaining geometry [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Buffer Overflow:** The check `count >= maxCount - 3` ensures there is enough space for a full triangle. If exceeded, the buffer is flushed immediately [S1, unofficial].
*   **Ambiguity:** Cases 46, 47, 98, 99, 210, 213, 214, 215 contain topological ambiguities. The standard LUT uses a fixed triangulation, which can cause cracks if adjacent voxels resolve ambiguities differently [S7, S8, unofficial].
*   **Precision:** Linear interpolation assumes the field is smooth. Discontinuities in the scalar field (e.g., from discrete metaball boundaries) can lead to artifacts.

## Operating characteristics
*   **Time Complexity:** $O(N^3 \cdot B)$, where $N$ is the grid resolution and $B$ is the number of metaballs (for field generation). The extraction step is $O(N^3)$ assuming a constant number of triangles per voxel.
*   **Memory Complexity:** $O(N^3)$ for the scalar field grid. The immediate mode buffer is fixed at $O(maxCount)$, independent of $N$ (though `maxCount` must be large enough to hold the output of a frame, which scales with $N^3$).
*   **Performance:** Limited by CPU throughput for field calculation and buffer management. At high resolutions (e.g., $128^3$) or high blob counts (e.g., 100), the CPU becomes a bottleneck, leading to low frame rates [S1, unofficial].
*   **Strengths:** Simple implementation; no persistent mesh storage overhead; suitable for dynamic scenes where the mesh changes every frame.
*   **Limitations:** Poor scalability; high CPU usage; frequent GPU buffer uploads can stall the pipeline.
*   **When to use:** Low-resolution previews, educational purposes, or scenes with very few dynamic objects where GPU-based extraction is not available.
*   **When not to use:** High-resolution production rendering, scenes with many dynamic objects, or when persistent mesh data is required for further processing (e.g., physics).

## Background
The CPU Immediate Mode Marching Cubes approach is inspired by Gregg Tavares' (Greggman) "Metaballs in JavaScript" demo, which demonstrated real-time metaball rendering using WebGL immediate mode [S1, unofficial]. It builds on the classic Marching Cubes algorithm by Lorensen and Cline (1987) and the lookup table configurations provided by Paul Bourke [S1, unofficial]. The specific implementation details, including the buffer management and field generation, are derived from the `WebGL2-GPU-Marching-Cubes` repository by 3merillon [S1, unofficial].
