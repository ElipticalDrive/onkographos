# Triangular Mesh Scene Rendering
## Overview
Triangular Mesh Scene Rendering is a method for rendering a scene composed of a list of triangular mesh objects, allowing multiple contour surfaces or related data sets to be displayed in a single plot [S1]. It differs from volume rendering methods by operating directly on explicit geometric primitives (triangles) rather than sampling a scalar field, enabling the visualization of multiple distinct isosurfaces or datasets simultaneously [S1]. The primary trade-off is that standard back-to-front rasterization engines may render intersecting surfaces with visible artifacts (ragged edges), whereas engines with proper depth buffering handle intersections correctly [S1].

## How it works
**Inputs and Outputs:**
- **Input:** A list of triangular mesh objects. Each object consists of a set of vertices and a set of triangles defining connectivity [G].
- **Output:** A 2D image where each pixel is colored based on the visible triangle at that location [G].

**Data Structures:**
- **Triangle:** Defined by three vertices $\mathbf{v}_0, \mathbf{v}_1, \mathbf{v}_2$. Each vertex $\mathbf{v}_i$ has 3D coordinates $(x, y, z)$ [G].
- **Scene:** A list or array of these triangle sets [G].

**Steps:**
1. **Scene Construction:** Assemble the list of triangular meshes. This may involve extracting meshes from scalar fields at specific isovalue ranges (e.g., $[-1, 1]$) to form basic scenes [S2, unofficial].
2. **Rasterization:** For each triangle in the scene, determine which pixels it covers. This is typically done using barycentric coordinate rasterization [G].
3. **Depth Testing:** Maintain a depth buffer (Z-buffer) to handle visibility. For each pixel covered by a triangle, compare the triangle's depth $z$ with the current value in the depth buffer. If the triangle is closer, update the pixel color and the depth buffer [G].
4. **Shading:** Compute the color of each visible pixel. This can involve directional Lambertian shading, which calculates lighting based on surface normals and a light direction [S3, unofficial].
5. **Rendering Engine Selection:**
   - **Proper Depth Handling:** Use engines (e.g., `rgl`) that support depth buffering to correctly render intersecting surfaces [S1].
   - **Back-to-Front Drawing:** In engines without proper depth handling (e.g., standard or grid engines), triangles are drawn back-to-front, leading to ragged artifacts at intersections [S1].

**Pitfalls:**
- **Intersecting Surfaces:** In standard rasterization engines that do not use a depth buffer, intersecting surfaces appear ragged due to the back-to-front drawing order of triangles [S1].
- **Performance:** Rendering large meshes can be computationally expensive. For example, a composed isosurface scene with 53.9 million triangles requires significant memory and processing power [S2, unofficial].

**Pseudocode:**
```python
import numpy as np

def render_triangular_mesh_scene(triangles, camera, light_direction, width, height):
    """
    Render a scene of triangular meshes using a Z-buffer.
    
    Args:
        triangles: List of triangles, each defined by 3 vertices (x, y, z).
        camera: Object with .view and .projection matrices (4x4).
        light_direction: 3D vector for directional light.
        width, height: Image dimensions.
        
    Returns:
        Image buffer (height x width x 3).
    """
    depth_buffer = np.full((height, width), np.inf)
    color_buffer = np.zeros((height, width, 3))
    
    for tri in triangles:
        v0, v1, v2 = tri.vertices
        
        # Transform vertices to screen space
        s0 = transform_to_screen(v0, camera, width, height)
        s1 = transform_to_screen(v1, camera, width, height)
        s2 = transform_to_screen(v2, camera, width, height)
        
        # Skip if behind camera or outside viewport
        if not is_in_viewport(s0, s1, s2, width, height):
            continue
            
        # Compute bounding box for rasterization
        min_x, max_x = max(0, int(min(s0[0], s1[0], s2[0]))), min(width - 1, int(max(s0[0], s1[0], s2[0])))
        min_y, max_y = max(0, int(min(s0[1], s1[1], s2[1]))), min(height - 1, int(max(s0[1], s1[1], s2[1])))
        
        if min_x > max_x or min_y > max_y:
            continue
            
        # Compute triangle normal for shading
        normal = compute_normal(v0, v1, v2)
        normal = normal / np.linalg.norm(normal)
        
        # Rasterize triangle
        for y in range(min_y, max_y + 1):
            for x in range(min_x, max_x + 1):
                # Check if pixel (x, y) is inside triangle using barycentric coordinates
                if is_inside_triangle(s0, s1, s2, x, y):
                    # Interpolate depth at pixel (perspective-correct)
                    z_interp = interpolate_depth(s0, s1, s2, x, y)
                    
                    # Depth test
                    if z_interp < depth_buffer[y, x]:
                        # Compute lighting (Lambertian)
                        diffuse = max(0.0, np.dot(normal, light_direction))
                        color = np.array([diffuse, diffuse, diffuse]) # Simplified shading
                        
                        # Update buffers
                        depth_buffer[y, x] = z_interp
                        color_buffer[y, x] = color
                        
    return color_buffer

def transform_to_screen(v, camera, width, height):
    """Apply view/projection matrices and perspective divide to get screen coordinates."""
    clip = camera.projection @ (camera.view @ np.append(v, 1.0))
    if clip[3] <= 0.0:
        return None
    ndc = clip[:3] / clip[3]
    return np.array([(ndc[0] + 1) * width / 2, (ndc[1] + 1) * height / 2, ndc[2]])

def compute_normal(v0, v1, v2):
    """Compute face normal via cross product of edge vectors."""
    return np.cross(v1 - v0, v2 - v0)

def is_in_viewport(s0, s1, s2, width, height):
    """Check if any vertex is valid and within camera frustum."""
    if s0 is None or s1 is None or s2 is None:
        return False
    return (min(s0[0], s1[0], s2[0]) < width and max(s0[0], s1[0], s2[0]) >= 0 and
            min(s0[1], s1[1], s2[1]) < height and max(s0[1], s1[1], s2[1]) >= 0)

def is_inside_triangle(s0, s1, s2, x, y):
    """Barycentric coordinate test for point inclusion."""
    v0 = s0 - np.array([x, y, 0])
    v1 = s1 - np.array([x, y, 0])
    v2 = s2 - np.array([x, y, 0])
    d00 = np.dot(v0, v0); d01 = np.dot(v0, v1); d11 = np.dot(v1, v1)
    d20 = np.dot(v0, v2); d21 = np.dot(v1, v2)
    denom = d00 * d11 - d01 * d01
    if denom == 0: return False
    v = (d11 * d20 - d01 * d21) / denom
    w = (d00 * d21 - d01 * d20) / denom
    u = 1.0 - v - w
    return u >= 0.0 and v >= 0.0 and w >= 0.0

def interpolate_depth(s0, s1, s2, x, y):
    """Perspective-correct interpolation of depth using barycentric weights."""
    v0 = s0 - np.array([x, y, 0])
    v1 = s1 - np.array([x, y, 0])
    v2 = s2 - np.array([x, y, 0])
    d00 = np.dot(v0, v0); d01 = np.dot(v0, v1); d11 = np.dot(v1, v1)
    d20 = np.dot(v0, v2); d21 = np.dot(v1, v2)
    denom = d00 * d11 - d01 * d01
    v = (d11 * d20 - d01 * d21) / denom
    w = (d00 * d21 - d01 * d20) / denom
    u = 1.0 - v - w
    # Perspective-correct: interpolate 1/z, then invert
    inv_z = u / s0[2] + v / s1[2] + w / s2[2]
    return 1.0 / inv_z
```

## Subtopics

### Isosurface Scene Representation
Isosurface Scene Representation is a technique where isosurface scenes are represented by extracting triangular meshes at different isovalues over a value range (e.g., $[-1, 1]$) to form basic scenes, which are then trained jointly [S2, unofficial]. Unlike direct triangular mesh extraction, this method (e.g., ECoNGS) achieves high fidelity with a much smaller model size (e.g., 1.57 MB vs 1002.9 MB for a composed scene) and higher FPS (331 vs 101), but has a slightly higher GPU/host memory footprint during rendering (3.30/7.61 GB vs 0.31/1.86 GB) [S2, unofficial]. The memory cost stays constant regardless of scene complexity [S2, unofficial].

### [Water Surface Rendering](5636-water-surface-rendering.md)
Water Surface Rendering is a technique for rendering water surfaces using a triangle fan geometry with vertex positions in 3D space $(x, 0, y)$. It differs from its sibling Stream Surface Rendering by utilizing a single planar mesh with specific shader-driven animations rather than streamlines or complex volumetric projections.

### [Stream Surface Rendering](7716-stream-surface-rendering.md)
Stream Surface Rendering visualizes 3D vector fields by seeding stream lines along a curve and triangulating the space between neighboring pairs of lines to form a continuous surface. Unlike individual stream lines, which can be difficult to perceive in 3D space, stream surfaces provide shaded geometry that is easily seen in 3D. The method distinguishes itself by processing line pairs independently (often in parallel on GPUs) and dynamically adapting the triangulation topology to handle streamline divergence, preventing overlapping or degenerate triangles. It builds on Triangular Mesh Scene Rendering by providing the mesh generation logic for these specific flow-based surfaces.

### CPU-based Software Rasterizer with Orbital Camera
CPU-based Software Rasterizer with Orbital Camera is a standalone CPU-based rendering engine that performs barycentric triangle rasterization, depth buffering (Z-buffer), and directional Lambertian shading [S3, unofficial]. It features an interactive orbital camera controlled by spherical coordinates [S3, unofficial].

### Optimized Triangle Representation
Optimized Triangle Representation is a 3D triangle primitive defined by 3D vertices, sharpness parameter $\sigma$, opacity, and spherical harmonic color coefficients [S4]. It is optimized by minimizing rendering error from posed views [S4]. The spherical harmonics degree is typically set to 3, resulting in 59 parameters per triangle, matching the parameter count of a single 3D Gaussian primitive in 3DGS [S4].

## Operating characteristics
- **Time Complexity:** Depends on the number of triangles $N$ and image resolution $W \times H$. Rasterization is typically $O(N)$ for triangle setup and $O(W \times H)$ for pixel processing, though bounding box culling reduces the latter [G].
- **Memory Complexity:** $O(N)$ for storing triangle data and $O(W \times H)$ for the depth and color buffers [G].
- **Performance:** Rendering large meshes (e.g., 53.9M triangles) can be slow on standard rasterization (101 FPS) but faster with optimized representations like ECoNGS (331 FPS) [S2, unofficial].
- **Strengths:** Allows multiple contour surfaces or datasets to be displayed in a single plot [S1]. Efficient for explicit geometry.
- **Limitations:** Intersecting surfaces may appear ragged in engines without proper depth buffering [S1]. High memory usage for very large meshes.

## Background
Triangular mesh scene rendering is a fundamental technique in computer graphics for visualizing explicit geometric data [S1]. It is often used in conjunction with isosurface extraction methods to visualize multiple contour surfaces of a single function or related functions in a single plot [S1]. The method is supported by various rendering engines, with differences in how they handle depth and intersection artifacts [S1].
