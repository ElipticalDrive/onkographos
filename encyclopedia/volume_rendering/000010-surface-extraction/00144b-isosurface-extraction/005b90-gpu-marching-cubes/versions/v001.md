# GPU Marching Cubes

Also called: Compute Shader Marching Cubes, Marching Cubes Compute Shader

## Overview
GPU Marching Cubes is a method for extracting an isosurface from a 3D scalar field by executing the marching cubes algorithm within a GPU compute shader [S1, unofficial]. It differs from CPU-based implementations by leveraging massive parallelism to process grid cells simultaneously, and from traditional graphics pipeline approaches by using a compute shader to generate geometry into a storage buffer, which is then rendered via an indirect draw call [S1, unofficial]. It is particularly suited for dynamic scalar fields, such as fluid simulations using metaballs, where the surface topology changes frequently [S1, unofficial].

## How it works
The method maps the 3D grid of scalar values to a 3D grid of compute shader threads. Each thread is responsible for processing one or more grid cells, determining the intersection of the isosurface with the cell edges, and writing the resulting triangle vertices to a global storage buffer. The final mesh is rendered using an indirect draw command that reads the actual number of generated vertices from a separate buffer.

### Inputs and Outputs
**Inputs:**
- A 3D scalar field defined on a regular grid of resolution $N_x \times N_y \times N_z$.
- An isosurface threshold value $T$.
- Precomputed triangle case indices and edge intersection indices for the marching cubes algorithm [S1, unofficial].
- Metaball parameters (e.g., positions and radii) if the scalar field is generated on-the-fly [S1, unofficial].

**Outputs:**
- A vertex buffer containing the extracted triangle vertices.
- An indirect draw buffer containing the total count of generated vertices.

### Data Structures
1.  **Grid Resolution:** Defined by `GRID_SIZE: [u32; 3]`. A typical value is `[64, 64, 64]` [S1, unofficial].
2.  **Vertex Storage Buffer:** A storage buffer of type `[[f32; 4]]` (float4), where each element represents a vertex with 3D position and potentially a fourth component (e.g., for normals or padding) [S1, unofficial].
    -   **Size:** $3 \times \text{MAX\_VERTICES\_PER\_THREAD} \times \text{NUM\_THREADS}$ [S1, unofficial].
    -   **Usage:** `STORAGE_BUFFER` (required for write access by the compute shader) [S1, unofficial].
3.  **Indirect Draw Buffer:** Contains a single `DrawIndirectCommand` structure [S1, unofficial].
    -   **Fields:** `vertex_count` (u32), `instance_count` (u32), `first_vertex` (u32), `first_instance` (u32) [S1, unofficial].
    -   **Initialization:** `vertex_count` is initialized to 0 [S1, unofficial].

### Parameters
-   `GRID_SIZE`: `[u32; 3]`, e.g., `[64, 64, 64]` [S1, unofficial].
-   `MAX_VERTICES_PER_THREAD`: `u32`, e.g., `5` [S1, unofficial]. This is a conservative upper bound on the number of vertices a single thread might write, based on the maximum number of triangles per cell (14 triangles $\times$ 3 vertices = 42 vertices, but often optimized or limited in specific implementations; the source specifies 5 as a practical limit for the described implementation) [S1, unofficial].
-   Thread Group Size: `[32, 32, 32]` [S1, unofficial].

### Algorithm Steps
1.  **Dispatch Initialization:** Calculate the total number of threads as the product of the grid dimensions: $\text{NUM\_THREADS} = N_x \times N_y \times N_z$. Dispatch the compute shader with a thread group size of `[32, 32, 32]` [S1, unofficial].
2.  **Buffer Allocation:**
    -   Allocate the vertex storage buffer with size $3 \times \text{MAX\_VERTICES\_PER\_THREAD} \times \text{NUM\_THREADS}$, initialized to zero [S1, unofficial].
    -   Allocate the indirect draw buffer with a `DrawIndirectCommand` where `vertex_count` is 0 [S1, unofficial].
3.  **Descriptor Binding:** Bind the following resources to the compute pipeline:
    -   Vertex storage buffer (Storage Buffer) [S1, unofficial].
    -   Indirect draw buffer (Storage Buffer) [S1, unofficial].
    -   Precomputed triangle/edge indices (Uniform Buffer or Storage Buffer) [S1, unofficial].
    -   Scalar field data and metaball parameters (Uniform Buffer or Storage Buffer) [S1, unofficial].
4.  **Compute Shader Execution:** For each thread $(i, j, k)$ in the dispatch:
    -   Map the thread ID to a grid cell coordinate $(x, y, z)$ [S1, unofficial].
    -   Sample the scalar values at the 8 vertices of the grid cell [S1, unofficial].
    -   Determine the marching cubes case index based on the sign of the scalar values relative to the threshold $T$ [S1, unofficial].
    -   Calculate the intersection points on the cell edges using linear interpolation [S1, unofficial].
    -   Generate the triangle vertices for the case [S1, unofficial].
    -   Atomically increment a counter in the indirect draw buffer to track the total number of vertices generated [S1, unofficial].
    -   Write the generated vertices to the vertex storage buffer at the offset indicated by the atomic counter [S1, unofficial].
5.  **Rendering:** Use the `DrawIndirectCommand` from the indirect draw buffer to issue an indirect draw call, rendering the vertices in the vertex storage buffer as triangles [S1, unofficial].

### Edge Cases and Pitfalls
-   **Buffer Allocation:** The vertex buffer must be allocated with `STORAGE_BUFFER` usage, not `VERTEX_BUFFER`, to allow write access from the compute shader [S1, unofficial].
-   **Memory Over-allocation:** Buffer sizes are statically calculated based on `MAX_VERTICES_PER_THREAD` and `NUM_THREADS`, which may lead to significant memory over-allocation if the actual number of generated vertices is much lower [S1, unofficial].
-   **Atomic Contention:** Using atomic operations to write to the vertex buffer can lead to contention in high-density scenarios, potentially impacting performance [G].
-   **Boundary Conditions:** The algorithm must handle grid boundaries correctly, ensuring that cells on the edge of the grid do not access out-of-bounds scalar values [G].

## Operating characteristics
-   **Time Complexity:** $O(N_x N_y N_z)$, where $N_x, N_y, N_z$ are the grid dimensions, as each cell is processed by one thread [S1, unofficial].
-   **Memory Complexity:** $O(N_x N_y N_z \times \text{MAX\_VERTICES\_PER\_THREAD})$ for the vertex buffer, which is an upper bound [S1, unofficial].
-   **Performance:** Performance scales with the number of GPU cores and the efficiency of the compute shader. The use of compute shaders allows for parallel processing of all grid cells [S1, unofficial].
-   **Strengths:** High parallelism, suitable for dynamic scalar fields, integrates well with GPU-based simulations [S1, unofficial].
-   **Limitations:** Potential for memory over-allocation, requires careful handling of atomic operations and buffer management [S1, unofficial].

## Background
GPU Marching Cubes implementations have emerged with the advent of general-purpose computing on GPUs (GPGPU) and compute shaders. The specific implementation described here is part of the "Rhyolite" rendering engine, a personal project by breitnw for research into sphere blending performance for fluid simulation applications [S1, unofficial]. It utilizes the Vulkano library for Vulkan API interaction [S1, unofficial].
