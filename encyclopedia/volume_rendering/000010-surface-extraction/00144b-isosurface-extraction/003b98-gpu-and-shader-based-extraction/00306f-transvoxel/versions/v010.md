# Transvoxel

Also called: LOD-aware Marching Cubes, Transvoxel Geometry Shader Implementation, Transvoxel Marching Cubes

## Overview
Transvoxel is an extension to the Marching Cubes technique that introduces a specific set of polygon configurations for "transition cells" to connect meshes extracted from voxel grids with different levels of detail (LOD) [S1]. It solves the problem of visual discontinuities and non-watertight surfaces that occur when neighboring voxels have different resolutions, ensuring a continuous isosurface across LOD boundaries [S2, unofficial]. Unlike standard Marching Cubes which assumes uniform voxel resolution, Transvoxel dynamically adjusts vertex positions and normals in transition zones to maintain surface integrity [S2, unofficial].

## How it works
**Inputs:**
- A 3D voxel grid (volume data).
- An isovalue threshold.
- A LOD function `lod_function(vec3)` that determines the resolution level for any given voxel coordinate.
- Pre-computed transition cell lookup tables (`transitionCellClass`, `transitionCellData`, `transitionCellVertexData`) [S2, unofficial].

**Outputs:**
- A watertight triangle mesh representing the isosurface.

**Data Structures:**
- `transitionCellClass`: Texture or array mapping a 9-bit index (derived from corner samples) to a transition cell class ID [S2, unofficial].
- `transitionCellData`: Array storing geometry counts for each transition cell class. The value encodes `geometry_count = (trans_vertex_count << 4) | trans_triangle_count` [S2, unofficial].
- `transitionCellVertexData`: Array storing vertex indices for transition cells. Each entry contains vertex index, `corner_1`, and `corner_2` [S2, unofficial].
- `transvoxel_adjust`: Array of offsets used to adjust vertex positions in standard MC cells adjacent to transition cells [S2, unofficial].

**Algorithm Steps:**

1.  **Voxel Positioning and LOD Determination:**
    For each voxel, calculate the base position by rounding down coordinates to the nearest multiple of $2 \times \text{voxel\_size}$:
    $$ x_{base} = (x - (x \% 2)) \times \text{voxel\_size} $$
    Determine the LOD of the current voxel using `lod_function(vec3(x_base, y_base, z_base))` and store in `voxel_size_lod` [S2, unofficial].

2.  **Transition Cell Identification:**
    If `voxel_size_lod == 2` (the highest LOD, where transitions occur) and any coordinate is odd (`x % 2 == 1 || y % 2 == 1 || z % 2 == 1`), this voxel is a potential transition cell. Set `draw_voxel = false` (it will be handled by the transition logic) and calculate `pos` offset based on parity bits [S2, unofficial].
    
    Query the LOD of six neighbors (left, right, down, top, front, back) at distance $2 \times \text{voxel\_size}$. If a neighbor has a lower resolution (e.g., `lod_left == 1`), add `transvoxel_size` to specific indices of `transvoxel_adjust` and set `transvoxel = true` [S2, unofficial].

3.  **Volume Sampling:**
    Sample the volume at 13 positions:
    - 8 corners (indices 0-7).
    - 4 face centers (indices 1, 3, 5, 7).
    - 1 center (index 4).
    - 4 additional positions defined by `transvoxel_adjust` (indices 9-12) [S2, unofficial].
    
    Compute `left_index` by iterating `i` from 0 to 8, sampling `corner_sample[i]`, and setting bit `k` if `corner_sample[i] < iso_value` [S2, unofficial].
    
    Copy corner samples to indices 9-12 to prepare for transition sampling:
    ```python
    corner_sample[9] = corner_sample[0]
    corner_sample[10] = corner_sample[2]
    corner_sample[11] = corner_sample[4]
    corner_sample[12] = corner_sample[6]
    ```
    Sample the volume at positions 9-12 [S2, unofficial].

4.  **Transition Cell Lookup:**
    If `left_index != 0 && left_index != 511`, fetch `trans_cell_class` from `transitionCellClass` texture using `left_index` [S2, unofficial].
    
    Fetch `geometry_count` from `transitionCellData` using `trans_cell_class & 0x7F`. Derive:
    $$ \text{trans\_vertex\_count} = \text{geometry\_count} >> 4 $$
    $$ \text{trans\_triangle\_count} = \text{geometry\_count} \& 0x0F $$
    
    Fetch 12 vertex data entries from `transitionCellVertexData` using `left_index` [S2, unofficial].

5.  **Vertex Generation for Transition Cells:**
    For each vertex `i` from 0 to `trans_vertex_count - 1`:
    - Fetch vertex index. Break if 0.
    - Extract `corner_1` and `corner_2`.
    - Interpolate vertex position if signs differ or use endpoint if values are close [S2, unofficial].

6.  **Triangle Emission for Transition Cells:**
    For each triangle, fetch 3 vertex indices from `transitionCellData`, retrieve positions, compute normal via cross product, and emit vertices [S2, unofficial].

7.  **Standard Marching Cubes with Adjustments:**
    If `transvoxel` is true, compute adjusted vertex positions `a_adj` and `b_adj` using `transvoxel_adjust` and `transvoxel_cell_multiplier` [S2, unofficial].
    
    Compute normals for adjusted vertices by interpolating gradients: `normal_a` and `normal_b` are computed via `compute_gradient`, then interpolated based on `iso_value` [S2, unofficial].
    
    If `project_transvoxel == 1`, project adjusted vertices onto the triangle plane defined by the interpolated normal [S2, unofficial].

## Subtopics

### [Transvoxel Smooth Terrain Texturing](7280-transvoxel-smooth-terrain-texturing.md)
This method applies procedural and texture-based color blending to surfaces extracted by the Transvoxel algorithm, solving the visual discontinuity of flat shading on dynamically changing isosurfaces. It differs from standard single-texture approaches by using triplanar mapping to avoid UV seams and blending between top/side textures based on surface normal orientation. It also supports multi-material blending via texture arrays and vertex weights for complex terrain features like grass, stone, and forest patches.

## Operating characteristics
- **Time Complexity:** Linear with respect to the number of voxels, but with a higher constant factor due to neighbor lookups and transition cell processing.
- **Memory Complexity:** Requires storage for the volume data plus lookup tables for transition cells. The lookup tables are relatively small but must be pre-computed.
- **Performance:** Efficient on GPU due to parallel voxel processing. The geometry shader implementation allows for on-the-fly mesh generation without CPU intervention [S2, unofficial].
- **Strengths:** Handles dynamic LOD changes seamlessly; maintains watertight surfaces; no manual mesh stitching required.
- **Limitations:** Requires pre-computed transition cell data; complex implementation due to multiple cell types; potential for artifacts if LOD function is not smooth.
- **When to use:** Dynamic terrain rendering, large-scale environments with varying detail levels.
- **When not to use:** Static scenes with uniform resolution; scenes requiring extremely high precision at boundaries.

## Background
The Transvoxel algorithm was introduced as a solution to the Level-of-Detail (LOD) problem in volumetric rendering [S1]. It extends the Marching Cubes technique by adding specific polygon configurations for transition cells [S1]. The method is particularly relevant for GPU-based extraction, where geometry shaders can handle the complex logic of transitioning between different voxel resolutions [S2, unofficial]. It is widely used in terrain rendering and large-scale scientific visualization.
