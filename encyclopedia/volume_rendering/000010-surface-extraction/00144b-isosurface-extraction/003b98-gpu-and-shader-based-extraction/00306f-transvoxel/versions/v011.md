# Transvoxel

Also called: LOD-aware Marching Cubes, Transvoxel Geometry Shader Implementation, Transvoxel Marching Cubes

## Overview
Transvoxel is a level-of-detail (LOD) aware extension to the Marching Cubes algorithm designed to extract watertight isosurfaces from voxel grids where neighboring cells have different resolutions [S1]. It solves the topological discontinuities (holes and cracks) that occur when standard Marching Cubes meshes are generated at varying LODs by introducing specialized "transition cells" that bridge the geometric gap between high-resolution and low-resolution regions [S1]. Unlike standard GPU Marching Cubes implementations which assume uniform voxel size, Transvoxel dynamically adjusts vertex positions and normals in transition zones to maintain surface continuity [S2, unofficial].

## How it works
**Inputs and Outputs**
*   **Input:** A 3D scalar field (voxel grid), an isovalue threshold, a voxel size, and a LOD function that determines the resolution level for any given spatial coordinate.
*   **Output:** A triangle mesh representing the isosurface, emitted via a geometry shader or vertex buffer.

**Data Structures**
*   **Transition Cell Configuration:** A lookup table (texture or array) mapping a 9-bit "left index" (derived from corner samples) to a set of precomputed transition polygons. This table defines the topology for connecting different LODs [S2, unofficial].
*   **Transition Cell Data:** Stores vertex indices and counts for each transition configuration. Typically packed such that the upper bits store vertex count and lower bits store triangle count [S2, unofficial].
*   **Transition Cell Vertex Data:** Stores the 3D coordinates of the vertices used in transition cells. These vertices are not standard cube corners but are interpolated or projected points that ensure watertightness [S2, unofficial].

**Algorithm Steps**

1.  **Voxel Positioning and LOD Determination:**
    For a given voxel coordinate $(x, y, z)$, calculate the base position in world space. The base position is rounded down to the nearest multiple of $2 \times \text{voxel\_size}$ to align with the LOD grid boundaries:
    $$ x_{base} = (x - (x \pmod 2)) \times \text{voxel\_size} $$
    Determine the LOD level for this voxel using a LOD function:
    $$ \text{lod} = \text{lod\_function}(vec3(x_{base}, y_{base}, z_{base})) $$
    Store the resulting voxel size multiplier as $\text{voxel\_size\_lod}$ [S2, unofficial].

2.  **Transition Cell Identification:**
    If the current voxel is at the highest LOD (e.g., $\text{voxel\_size\_lod} == 2$ in a binary LOD scheme) and any of its coordinates are odd, it is a candidate for a transition cell. Mark `draw_voxel = false` for standard rendering and calculate a position offset based on the parity bits of the coordinates [S2, unofficial].

3.  **Neighbor LOD Query:**
    For transition candidates, query the LOD of the six immediate neighbors (left, right, down, top, front, back) at a distance of $2 \times \text{voxel\_size}$. If any neighbor has a lower resolution (higher LOD index), mark the cell as a transition cell (`transvoxel = true`) and populate a `transvoxel_adjust` array with offsets corresponding to the direction of the lower-resolution neighbor [S2, unofficial].

4.  **Volume Sampling:**
    Sample the scalar field at 13 specific positions to determine the surface intersection topology:
    *   8 corners of the voxel.
    *   4 face centers (specifically indices 1, 3, 5, 7 in the implementation's indexing scheme).
    *   1 center point (index 4).
    *   4 additional positions defined by the `transvoxel_adjust` array (indices 9-12), which lie on the edges or faces connecting to lower-resolution neighbors [S2, unofficial].

5.  **Index Calculation:**
    Compute a `left_index` by iterating through the 9 corner samples (indices 0-8). For each sample $i$, if `corner_sample[i] < iso_value`, set the $k$-th bit of the index. This 9-bit integer serves as the key for the transition cell lookup [S2, unofficial].

6.  **Corner Sample Propagation:**
    Copy specific corner samples to the additional sample indices to maintain consistency for the transition geometry:
    ```python
    corner_sample[9] = corner_sample[0]
    corner_sample[10] = corner_sample[2]
    corner_sample[11] = corner_sample[4]
    corner_sample[12] = corner_sample[6]
    ```
    Re-sample the volume at these new positions (9-12) if necessary to ensure the transition vertices align with the scalar field [S2, unofficial].

7.  **Transition Configuration Lookup:**
    If `left_index != 0` and `left_index != 511` (avoiding empty or full cells), fetch the `trans_cell_class` from the `transitionCellClass` texture using `left_index` as the coordinate [S2, unofficial].

8.  **Geometry Extraction:**
    *   Fetch `geometry_count` from `transitionCellData` using `trans_cell_class & 0x7F`.
    *   Derive the number of transition vertices and triangles:
        $$ \text{trans\_vertex\_count} = \text{geometry\_count} \gg 4 $$
        $$ \text{trans\_triangle\_count} = \text{geometry\_count} \& 0x0F $$
    *   Fetch 12 vertex data entries from `transitionCellVertexData` using `left_index` [S2, unofficial].

9.  **Vertex Interpolation:**
    For each vertex $i$ from $0$ to $\text{trans\_vertex\_count}-1$:
    *   Fetch the vertex index. If 0, break.
    *   Extract `corner_1` and `corner_2` indices.
    *   If the scalar values at `corner_1` and `corner_2` have different signs (or are close to the isovalue), interpolate the vertex position linearly between the two corners. Otherwise, use the endpoint position [S2, unofficial].

10. **Triangle Emission:**
    For each triangle, fetch 3 vertex indices from `transitionCellData`. Retrieve the interpolated positions. Compute the normal via the cross product of two edge vectors. Emit the vertices with positions and normals [S2, unofficial].

11. **Standard Marching Cubes Adjustment (if `transvoxel` is true):**
    For vertices in standard MC cells adjacent to transition zones:
    *   Compute adjusted vertex positions $a_{adj}$ and $b_{adj}$ using `transvoxel_adjust` and `transvoxel_cell_multiplier` to snap vertices to the transition plane [S2, unofficial].
    *   Compute normals for adjusted vertices by interpolating gradients: `normal_a` and `normal_b` are computed via `compute_gradient` and interpolated based on the `iso_value` [S2, unofficial].
    *   If `project_transvoxel == 1`, project the adjusted vertices onto the triangle plane defined by the interpolated normal to eliminate gaps [S2, unofficial].

**Parameters and Typical Values**
*   **LOD Function:** Typically based on distance from the camera or viewer. A common heuristic is $LOD = \lfloor \log_2(\text{distance}) \rfloor$.
*   **Isovalue:** Scene-dependent.
*   **Voxel Size:** Depends on the resolution of the input volume.

**Edge Cases and Pitfalls**
*   **Precision:** Floating-point precision errors in interpolation can cause micro-gaps. Projecting vertices onto the transition plane (`project_transvoxel == 1`) mitigates this [S2, unofficial].
*   **Boundary Conditions:** The LOD function must handle the boundaries of the volume grid correctly to avoid querying out-of-bounds neighbors.
*   **Degenerate Input:** If the scalar field is constant, `left_index` may be 0 or 511, resulting in no geometry. This is handled by the check `left_index != 0 && left_index != 511` [S2, unofficial].

## Subtopics

### [Transvoxel Smooth Terrain Texturing](7280-transvoxel-smooth-terrain-texturing.md)
This method applies procedural and texture-based color blending to surfaces extracted by the Transvoxel algorithm, solving the visual discontinuity of flat shading on dynamically changing isosurfaces. It differs from standard single-texture approaches by using triplanar mapping to avoid UV seams and blending between top/side textures based on surface normal orientation. It also supports multi-material blending via texture arrays and vertex weights for complex terrain features like grass, stone, and forest patches.

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of voxels, but with a higher constant factor due to neighbor lookups and transition cell processing. The transition cell lookup is $O(1)$ via texture/array access.
*   **Memory Complexity:** $O(N)$ for the voxel grid plus $O(1)$ for the transition cell lookup tables (which are small and fixed-size).
*   **Performance:** Transvoxel is efficient on GPUs because the transition logic is encapsulated in the geometry shader, allowing parallel processing of voxels. However, the branching logic for transition cells can cause divergence in SIMD execution units.
*   **Strengths:** Produces watertight meshes at varying LODs, reducing polygon count in distant areas without visual artifacts.
*   **Limitations:** More complex to implement than standard Marching Cubes. The transition cell configurations are specific to the binary LOD scheme (e.g., factor of 2). Non-binary LODs require different transition configurations.
*   **When to Use:** Real-time terrain rendering, dynamic voxel-based environments where LOD is critical.
*   **When Not to Use:** Static scenes where precomputed LODs are sufficient, or when non-binary LOD steps are required without significant modification.

## Background
The Transvoxel algorithm was introduced as a solution to the Level-of-Detail (LOD) problem in voxel-based rendering. Standard Marching Cubes fails to produce watertight surfaces when adjacent cells have different resolutions, leading to cracks and holes. Transvoxel extends the Marching Cubes technique by introducing a new set of polygon configurations for "transition cells" that connect meshes of different LODs [S1]. The algorithm was notably implemented in a geometry shader context for WebGL, enabling real-time LOD-aware terrain rendering [S1]. The specific implementation details described in the notes are based on a GitHub repository demonstrating an OpenGL-based Transvoxel geometry shader [S2, unofficial].
