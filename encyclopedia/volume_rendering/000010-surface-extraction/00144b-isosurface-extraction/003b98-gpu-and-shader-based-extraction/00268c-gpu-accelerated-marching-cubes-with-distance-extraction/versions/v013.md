# GPU-accelerated Marching Cubes with Distance Extraction

Also called: WebGL Signed Distance Function Mesher, glsl-marching-cubes

## Overview
This method extracts an STL mesh from a signed distance function (SDF) by offloading the distance evaluation to a GLSL shader to minimize GPU/CPU round trips, then processing the resulting data on the CPU [S1, unofficial]. It avoids the high retrieval costs of running the full algorithm on the GPU by extracting vertex distances first [S1, unofficial].

## How it works
**Inputs:** A signed distance function (SDF) defined as a GLSL shader, volume dimensions (`dims`), and volume bounds (`bounds`) [S1, unofficial].
**Outputs:** An STL mesh file [S1, unofficial].

**Data Structures:**
* `volume`: An object containing `dims` (array of 3 integers), `bounds` (array of 2 arrays of 3 floats), `vertexDims` (array of 3 integers), `vertexCount` (integer), and `size` (integer) [S1, unofficial].
* `blockPotentialBuffers`: An array of `ArrayBuffer` objects, each of size `volume.vertexCount * 4` bytes, storing `Float32` values [S1, unofficial].

**Parameters:**
* `maxSize`: The maximum texture size for the GPU rendering buffer, capped at 4096 [S1, unofficial].
* `numWorkers`: The number of worker threads used for parallel processing, set to 4 [S1, unofficial].
* `blocks`: The number of chunks to split the volume into for worker distribution, set to 256 [S1, unofficial].

**Steps:**
1. **Volume Subdivision:** Subdivide the volume into blocks small enough to fit within `maxSize` [S1, unofficial].
2. **Distance Extraction:** Extract distances for each cube vertex from the shader [S1, unofficial].
3. **Culling:** Skip any blocks which are entirely inside (negative distance) or outside (positive distance) the surface [S1, unofficial].
4. **CPU Marching Cubes:** Run the marching cubes algorithm on the CPU for the remaining blocks [S1, unofficial].

**Pseudocode:**
```python
def extract_mesh(sdf_shader, dims, bounds):
    vertex_count = (dims[0] + 1) * (dims[1] + 1) * (dims[2] + 1)
    size = int(ceil(sqrt(vertex_count)))
    max_size = min(4096, size)
    volumes = split_volume_into_blocks(dims, bounds, max_size)
    all_triangles = []
    num_workers = 4
    for volume in volumes:
        block_potential_buffers = [bytearray(volume.vertex_count * 4) for _ in range(num_workers)]
        distances = extract_vertex_distances_from_shader(sdf_shader, volume)
        if all(d > 0 for d in distances) or all(d < 0 for d in distances):
            continue
        for i in range(num_workers):
            block_potential_buffers[i] = distances
        for buf in block_potential_buffers:
            triangles = marching_cubes_cpu(buf, volume.dims, volume.bounds)
            all_triangles.extend(triangles)
    return assemble_stl(all_triangles)

# split_volume_into_blocks: partitions dims/bounds into sub-volumes fitting max_size texture dimensions
# extract_vertex_distances_from_shader: renders vertex positions to a framebuffer, reads back RGBA floats, unpacks to distance array
# marching_cubes_cpu: standard iterative Marching Cubes algorithm on the distance array (sources do not provide implementation)
# assemble_stl: combines triangle vertex lists into a single STL file (sources do not provide implementation)
```

## Operating characteristics
* **Time Complexity:** Dominated by GPU rendering and CPU readback for distance extraction, followed by CPU Marching Cubes [S1, unofficial].
* **Memory Complexity:** Requires memory for `blockPotentialBuffers` proportional to `vertexCount` [S1, unofficial].
* **Performance:** Extracting distances first reduces round trips compared to extracting full triangle data [S1, unofficial].
* **Strengths:** Reduces GPU/CPU communication overhead for distance evaluation [S1, unofficial].
* **Limitations:** Large meshes are saved in parts and must be re-combined externally (e.g., with MeshLab); missing triangles (holes) may appear in the resulting mesh [S1, unofficial].

## Background
This method originates from the `glsl-marching-cubes` project by tdhooper, implemented using WebGL, three.js, and TWGL [S1, unofficial]. It addresses the performance bottleneck of pure CPU Marching Cubes for complex SDFs by utilizing the GPU for distance evaluation, while avoiding the complexity and overhead of full GPU-side mesh generation and retrieval [S1, unofficial].
