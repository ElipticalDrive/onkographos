# GPU-accelerated Marching Cubes with Distance Extraction

Also called: WebGL Signed Distance Function Mesher, glsl-marching-cubes

## Overview
This method extracts an STL mesh from a signed distance function (SDF) by decoupling the distance evaluation from the topology generation. It renders vertex distances to a GPU texture to minimize expensive GPU-to-CPU data transfers, then processes the resulting data on the CPU using a standard Marching Cubes implementation [S1, unofficial]. It differs from pure GPU extraction methods by acknowledging that retrieving large volumes of triangle data from the GPU is often slower than the extraction itself, opting instead for a hybrid approach where the GPU acts only as a fast distance evaluator [S1, unofficial].

## How it works
**Inputs:**
- A signed distance function (SDF) defined as a GLSL shader.
- Volume dimensions (`dims`): array of 3 integers representing the number of cells in x, y, z.
- Volume bounds: array of 2 arrays of 3 floats, representing the minimum and maximum coordinates of the volume.

**Outputs:**
- An STL mesh file (potentially split into parts for large meshes).

**Data Structures:**
- `volume`: An object containing:
  - `dims`: Array of 3 integers.
  - `bounds`: Array of 2 arrays of 3 floats.
  - `vertexCount`: Integer, calculated as $(dims[0] + 1) \times (dims[1] + 1) \times (dims[2] + 1)$.
  - `size`: Integer, the texture dimension required to hold the vertices, calculated as $\lceil \sqrt{vertexCount} \rceil$.
- `blockPotentialBuffers`: An array of `ArrayBuffer` objects. Each buffer has a size of $volume.vertexCount \times 4$ bytes, storing `Float32` values.

**Parameters:**
- `maxSize`: The maximum texture size for the GPU rendering buffer. Capped at 4096 [S1, unofficial].
- `numWorkers`: The number of worker threads used for parallel processing. Default is 4 [S1, unofficial].
- `blocks`: The number of chunks to split the volume into for worker distribution. Default is 256 [S1, unofficial].

**Steps:**

1.  **Volume Subdivision:**
    Subdivide the volume into blocks small enough to fit within `maxSize`. The texture size `size` is determined by $\lceil \sqrt{vertexCount} \rceil$. If `size` exceeds `maxSize`, the volume is split into multiple sub-volumes (chunks) [S1, unofficial].

2.  **Distance Extraction (GPU):**
    For each sub-volume:
    a.  Resize the GPU rendering context to `size` x `size`.
    b.  Initialize `numWorkers` `ArrayBuffer` objects, each of size $vertexCount \times 4$ bytes. Create corresponding `Float32Array` views for each buffer.
    c.  Render the SDF shader to a framebuffer. The shader computes the distance for each vertex in the current block.
    d.  Read the pixel data from the GPU using `gl.readPixels`.
    e.  Unpack the RGBA float values into the `blockPotentialBuffers`.
    f.  Check if the block contains geometry. If all distances are strictly positive (outside) or strictly negative (inside), mark the block as empty and skip further processing for it [S1, unofficial].

3.  **Parallel Processing (CPU):**
    a.  Distribute the blocks among `numWorkers` threads.
    b.  Each worker processes a subset of the blocks.
    c.  For each block, apply the standard Marching Cubes algorithm using the extracted distances to determine triangle topology.
    d.  Generate the triangle vertices and normals.

4.  **Mesh Assembly:**
    Combine the triangles from all workers. For very large meshes, the output may be saved in parts, requiring external tools (e.g., MeshLab) for recombination [S1, unofficial].

**Pseudocode:**

```python
def gpu_accelerated_marching_cubes(sdf_shader, dims, bounds):
    # 1. Setup
    vertex_count = (dims[0] + 1) * (dims[1] + 1) * (dims[2] + 1)
    size = ceil(sqrt(vertex_count))
    max_size = min(size, 4096)
    
    # Split volume if necessary
    volumes = split_volume(dims, bounds, max_size)
    
    num_workers = 4
    blocks_per_worker = 256 // num_workers # Simplified distribution
    
    # 2. GPU Distance Extraction
    block_potential_buffers = []
    
    for volume in volumes:
        # Initialize buffers for this volume
        buffers = []
        for _ in range(num_workers):
            buf = ArrayBuffer(volume.vertex_count * 4)
            buffers.append(Float32Array(buf))
        
        # Render SDF to texture
        render_sdf_to_texture(sdf_shader, volume.dims, volume.bounds, size)
        
        # Read pixels
        pixels = gl_read_pixels(0, 0, size, size)
        
        # Unpack and store
        contains_geometry = False
        previous_value = None
        
        for i in range(volume.vertex_count):
            value = unpack_float_rgba(pixels, i)
            
            # Check for surface intersection
            if previous_value is not None:
                if (value > 0) != (previous_value > 0):
                    contains_geometry = True
            
            previous_value = value
            
            # Distribute to worker buffers
            worker_idx = i % num_workers
            buffers[worker_idx][i] = value
            
        if not contains_geometry:
            continue # Skip empty blocks
            
        block_potential_buffers.append(buffers)
        
    # 3. CPU Marching Cubes
    all_triangles = []
    
    # Parallel execution would happen here
    for buffers in block_potential_buffers:
        for worker_buffers in buffers:
            triangles = marching_cubes_cpu(worker_buffers, volume.dims)
            all_triangles.extend(triangles)
            
    return all_triangles
```

**Edge Cases and Pitfalls:**
- **Missing Triangles:** Holes may appear in the resulting mesh if the distance extraction or unpacking is imprecise [S1, unofficial].
- **Large Meshes:** The method may save large meshes in parts, requiring external recombination [S1, unofficial].
- **Texture Size Limits:** The `maxSize` cap at 4096 is critical; exceeding this can cause undefined behavior on some GPUs [S1, unofficial].

## Operating characteristics
- **Time Complexity:** Dominated by GPU rendering time for distance extraction and CPU Marching Cubes processing. The hybrid approach avoids the high latency of reading back large triangle buffers from the GPU.
- **Memory Complexity:** Requires memory for `numWorkers` buffers per volume, each of size $vertexCount \times 4$ bytes.
- **Strengths:** Reduces GPU/CPU round trips by only transferring distance values (scalars) rather than triangle indices and vertices. Efficient for models with large empty spaces, as empty blocks are skipped.
- **Limitations:** Requires CPU processing power for the actual mesh generation. Not suitable for real-time extraction where the entire pipeline must be on the GPU. Large meshes may require post-processing for recombination.
- **When to use:** When extracting static meshes from SDFs for storage or further processing, and when the SDF evaluation is expensive but the topology generation is manageable on the CPU.
- **When not to use:** For real-time visualization where the mesh must be generated entirely on the GPU.

## Background
This method originates from the `glsl-marching-cubes` project by tdhooper, implemented as a WebGL application using three.js and TWGL [S1, unofficial]. It was developed to address the performance bottlenecks of running the entire Marching Cubes algorithm on the GPU, where data retrieval costs made it too slow for practical use [S1, unofficial]. The approach leverages the GPU's strength in parallel scalar computation (distance evaluation) while offloading the complex topology logic to the CPU.
