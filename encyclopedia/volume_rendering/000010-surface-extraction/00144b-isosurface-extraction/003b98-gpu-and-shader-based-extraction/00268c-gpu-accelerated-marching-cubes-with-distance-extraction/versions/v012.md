# GPU-accelerated Marching Cubes with Distance Extraction

Also called: WebGL Signed Distance Function Mesher, glsl-marching-cubes

## Overview
This method extracts an STL mesh from a signed distance function (SDF) by offloading the distance evaluation to a GLSL shader to minimize GPU/CPU round trips, then processing the resulting data on the CPU [S1, unofficial]. It differs from pure GPU extraction by avoiding the high cost of retrieving large volumes of triangle data back to the host, and from pure CPU extraction by using the GPU for the expensive SDF evaluation step [S1, unofficial].

## How it works
**Inputs:** A signed distance function (SDF) defined as a GLSL shader, volume dimensions (`dims`), and volume bounds (`bounds`).
**Outputs:** An STL mesh file.

**Data Structures:**
*   `volume`: An object containing:
    *   `dims`: Array of 3 integers representing the grid resolution in X, Y, Z.
    *   `bounds`: Array of 2 arrays of 3 floats, representing the minimum and maximum coordinates of the volume.
    *   `vertexCount`: Integer, calculated as $(dims[0] + 1) \times (dims[1] + 1) \times (dims[2] + 1)$.
    *   `size`: Integer, the texture dimension required to store vertices, calculated as $\lceil \sqrt{vertexCount} \rceil$.
*   `blockPotentialBuffers`: An array of `ArrayBuffer` objects. Each buffer has a size of `volume.vertexCount * 4` bytes, storing `Float32` values representing the distance at each vertex.

**Parameters:**
*   `maxSize`: The maximum texture size for the GPU rendering buffer, capped at 4096 [S1, unofficial].
*   `numWorkers`: The number of worker threads used for parallel processing, set to 4 [S1, unofficial].
*   `blocks`: The number of chunks to split the volume into for worker distribution, set to 256 [S1, unofficial].

**Steps:**
1.  **Volume Subdivision:** Subdivide the volume into blocks small enough to fit within `maxSize`. The volume is split such that the texture dimensions required to store the vertex data do not exceed `maxSize` [S1, unofficial].
2.  **Distance Extraction:** For each block, render a geometry covering the block's vertices to a framebuffer using a fragment shader that evaluates the SDF. Read the pixel values (distances) back from the GPU using `readPixels` [S1, unofficial].
3.  **Culling:** Check if the extracted distances indicate the block is entirely inside (all negative) or outside (all positive) the surface. If so, skip processing for that block [S1, unofficial].
4.  **CPU Marching Cubes:** Run the standard Marching Cubes algorithm on the CPU for the remaining blocks using the extracted distance values to determine vertex positions and triangle connectivity [S1, unofficial].
5.  **Assembly:** Combine the triangles from all processed blocks into a final mesh [S1, unofficial].

**Pseudocode:**

## Operating characteristics
*   **Time Complexity:** Dominated by GPU rendering and CPU readback for distance extraction, followed by CPU Marching Cubes. Skipping empty blocks improves performance for sparse volumes [S1, unofficial].
*   **Memory Complexity:** Requires memory for `blockPotentialBuffers` proportional to `vertexCount`.
*   **Performance:** Extracting distances first reduces round trips compared to extracting full triangle data. Running the entire algorithm on the GPU was found to be too slow due to data retrieval costs [S1, unofficial].
*   **Strengths:** Reduces GPU/CPU communication overhead for distance evaluation; leverages CPU parallelism for mesh generation.
*   **Limitations:** Large meshes are saved in parts and must be re-combined externally (e.g., with MeshLab); missing triangles (holes) may appear in the resulting mesh [S1, unofficial].

## Background
This method originates from the `glsl-marching-cubes` project by tdhooper, implemented using WebGL, three.js, and TWGL [S1, unofficial]. It addresses the performance bottleneck of pure CPU Marching Cubes for complex SDFs by utilizing the GPU for distance evaluation, while avoiding the complexity and overhead of full GPU-side mesh generation and retrieval [S1, unofficial].
