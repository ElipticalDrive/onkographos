# GPU-accelerated Marching Cubes with Distance Extraction

Also called: WebGL Signed Distance Function Mesher, glsl-marching-cubes

## Overview
This method extracts an STL mesh from a Signed Distance Function (SDF) by offloading the scalar field evaluation to a GPU shader to extract vertex distances, thereby reducing the number of GPU/CPU round trips compared to running the entire algorithm on the GPU [S1, unofficial]. It differs from pure GPU implementations by performing the topology construction (Marching Cubes) on the CPU after retrieving only the necessary vertex potentials, addressing the performance bottleneck of data retrieval costs associated with full GPU-side execution [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A volumetric SDF defined by dimensions `dims` (array of 3 integers) and spatial `bounds` (array of 2 arrays of 3 floats).
*   **Output:** An STL mesh file.

**Data Structures:**
*   **Volume Object:** Contains `dims`, `bounds`, `vertexDims` (derived from dims), `vertexCount` (integer), and `size` (integer).
*   **Block Potential Buffers:** An array of `ArrayBuffer` objects. Each buffer has a size of `volume.vertexCount * 4` bytes, storing `Float32` values representing the SDF potential at each vertex [S1, unofficial].

**Algorithm Steps:**
1.  **Volume Subdivision:** Subdivide the volume into blocks small enough to fit within the maximum supported texture size (`maxSize`). The `maxSize` is capped at 4096 pixels to avoid hardware-specific rendering artifacts [S1, unofficial].
2.  **Shader Execution:** For each block, render a geometry representing the cube vertices. Use a fragment shader to evaluate the SDF at each vertex coordinate and output the distance value.
3.  **Data Retrieval:** Read the pixel data from the GPU framebuffer using `gl.readPixels` to populate the `blockPotentialBuffers` on the CPU [S1, unofficial].
4.  **Culling:** Analyze the retrieved potentials. If a block is entirely inside (all negative distances) or entirely outside (all positive distances) the surface, skip further processing for that block [S1, unofficial].
5.  **CPU Marching Cubes:** Pass the valid potential buffers to a CPU-based Marching Cubes implementation (e.g., based on `mikolalysenko/isosurface`) to generate the mesh geometry [S1, unofficial].
6.  **Parallel Processing:** Distribute the volume blocks across a pool of worker threads (`numWorkers`, typically 4) to process blocks in parallel [S1, unofficial].

**Pseudocode:**

```python
def gpu_accelerated_marching_cubes(dims, bounds):
    # 1. Setup and Subdivision
    vertex_count = (dims[0] + 1) * (dims[1] + 1) * (dims[2] + 1)
    size = ceil(sqrt(vertex_count))
    max_size = min(gl.drawingBufferWidth, 4096)
    
    # Split volume into chunks fitting within max_size
    volumes = split_volume(dims, bounds, max_size)
    
    num_workers = 4
    worker_pool = WorkerPool(count=num_workers)
    
    for volume in volumes:
        # 2. Prepare Buffers
        block_potential_buffers = []
        for i in range(num_workers):
            buffer = ArrayBuffer(volume.vertex_count * 4)
            block_potential_buffers.append(buffer)
            
        # 3. GPU Shader Execution
        uniforms = {
            "boundsA": volume.bounds[0],
            "boundsB": volume.bounds[1],
            "dims": volume.dims
        }
        
        # Draw geometry and evaluate SDF in fragment shader
        scene.draw(program=potentials_prog, uniforms=uniforms)
        
        # 4. Retrieve Data
        pixels = gl.readPixels(0, 0, volume.width, volume.height, RGBA, FLOAT)
        
        # Unpack floats and populate buffers
        contains_geometry = False
        previous_value = None
        
        for i in range(volume.vertex_count):
            value = unpack_float(pixels[i])
            
            # Check for sign change to detect geometry presence
            if previous_value is not None:
                if (value > 0) != (previous_value > 0):
                    contains_geometry = True
            
            # Distribute data to worker buffers
            for bl in range(num_workers):
                block_potential_buffers[bl][i] = value
            
            previous_value = value
            
        # 5. Culling
        if not contains_geometry:
            continue
            
        # 6. CPU Processing via Workers
        # Send buffers to workers for Marching Cubes execution
        worker_pool.execute('march', block_potential_buffers, volume)
        
    # 7. Combine results
    # Note: Large meshes may be saved in parts and require external recombination
    return combine_meshes()
```

**Parameters:**
*   `maxSize`: Maximum texture size for the GPU rendering buffer. Default/Capped at 4096 [S1, unofficial].
*   `numWorkers`: Number of worker threads for parallel processing. Default 4 [S1, unofficial].
*   `blocks`: Number of chunks to split the volume into for worker distribution. Default 256 [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Missing Triangles:** Holes may appear in the resulting mesh if the SDF evaluation or interpolation is imprecise at boundaries [S1, unofficial].
*   **Large Meshes:** The method may save large meshes in parts, requiring external tools like MeshLab to recombine them [S1, unofficial].
*   **Precision:** Reading floats from the GPU framebuffer can be sensitive to driver-specific behavior; capping `maxSize` at 4096 mitigates "weird" rendering issues on some hardware [S1, unofficial].

## Operating characteristics
*   **Performance:** Faster than running the entire Marching Cubes algorithm on the GPU because it avoids the high cost and difficulty of retrieving large amounts of generated geometry data back to the CPU [S1, unofficial].
*   **Memory:** Requires memory proportional to the volume size for storing potential buffers (`vertexCount * 4` bytes per worker) [S1, unofficial].
*   **Limitations:** Dependent on WebGL/GPU capabilities for texture size limits. Output may require post-processing to fix holes or merge parts [S1, unofficial].
*   **When to use:** Suitable for extracting meshes from SDFs where the scalar field evaluation is complex or expensive, and where a CPU-based MC implementation is preferred for topology handling.
*   **When not to use:** When real-time, fully GPU-resident rendering is required, or when the overhead of CPU-GPU synchronization is unacceptable for very small volumes.

## Background
This method originates from the `glsl-marching-cubes` project by tdhooper, implemented using WebGL, three.js, and TWGL [S1, unofficial]. It was developed to address the performance limitations of pure GPU-based Marching Cubes in JavaScript environments, leveraging the GPU for function evaluation while retaining CPU flexibility for mesh construction [S1, unofficial].
