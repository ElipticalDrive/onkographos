# 4D Cell Complex Slicing

Also called: 4D Polytope Slicing, Hierarchical Slicing

## Overview
4D Cell Complex Slicing is a method for extracting the 3D cross-section of a four-dimensional object represented as a Cell Complex (CW-Complex) against a slicing hyperplane [S1, unofficial]. It solves the problem of rendering 4D volumes by reducing the primitive count compared to full tetrahedralization, as it processes polytopes directly rather than decomposing them into tetrahedra first [S1, unofficial]. It sets itself apart from its siblings by maintaining a hierarchical structure of vertices, edges, faces, and cells, avoiding the overhead of generating intermediate tetrahedral meshes [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 4D Cell Complex defined by vertices, edges, faces, and cells, and a 4D slicing hyperplane $H$.
*   **Output:** A 3D Cell Complex representing the cross-section, consisting of new vertices, edges, and faces.

**Data Structures:**
The complex is stored hierarchically [S1, unofficial]:
1.  **Vertices:** An array of 4D coordinate vectors.
2.  **Edges:** An array of pairs of indices referencing vertices.
3.  **Faces:** An array of lists of indices referencing edges.
4.  **Cells:** An array of lists of indices referencing faces.

**Algorithm Steps:**
The algorithm proceeds sequentially from lower to higher dimensions [S1, unofficial]:

1.  **Vertex Classification:** Determine the position of each vertex relative to the slicing hyperplane $H$. Classify each vertex as being on the positive side, negative side, or on the plane.
2.  **Edge Intersection:** For each edge, check if its two endpoint vertices lie on opposite sides of $H$.
    *   If yes, calculate the intersection point of the edge with $H$. This point becomes a new vertex in the cross-section.
    *   If no, no intersection occurs for this edge.
3.  **Face Slicing:** For each face, check if its constituent edges produced intersection points in Step 2.
    *   If yes, connect these intersection points to form the edges of the cross-section face.
    *   *Pitfall:* This step assumes the object is convex. If the object is non-convex, an edge might intersect the plane at more than two points, creating "illegal" edges with more than two endpoints, which breaks the algorithm [S1, unofficial].
4.  **Cell Slicing:** For each cell, check if its constituent faces produced intersection lines (edges) in Step 3.
    *   If yes, connect these intersection lines to form the faces of the cross-section cell.
    *   Cells whose boundaries were not intersected are ignored.
5.  **Triangulation:** The resulting cross-section faces may be non-triangular polygons. Triangulate these faces to prepare for rendering.
    *   For convex shapes, select one vertex and connect it to all non-adjacent vertices to form triangles [S1, unofficial].

**Pseudocode:**

```python
def slice_cell_complex(complex, hyperplane):
    """
    Slices a 4D Cell Complex against a 4D hyperplane.
    Returns a 3D Cell Complex representing the cross-section.
    """
    # Step 1: Classify vertices
    # hyperplane is defined by normal n and distance d: n . x + d = 0
    vertex_signs = []
    for v in complex.vertices:
        sign = dot(hyperplane.normal, v) + hyperplane.distance
        vertex_signs.append(sign)
    
    # Step 2: Intersect edges
    new_vertices = []
    edge_intersections = {} # Maps edge_index to list of intersection points
    
    for i, edge in enumerate(complex.edges):
        v0_idx, v1_idx = edge
        s0 = vertex_signs[v0_idx]
        s1 = vertex_signs[v1_idx]
        
        # Check if endpoints are on opposite sides (or one is on the plane)
        if s0 * s1 <= 0:
            # Calculate intersection point
            # Linear interpolation: P = v0 + t * (v1 - v0)
            # t = -s0 / (s1 - s0)
            if abs(s1 - s0) > 1e-9:
                t = -s0 / (s1 - s0)
                p = lerp(complex.vertices[v0_idx], complex.vertices[v1_idx], t)
                new_vertices.append(p)
                edge_intersections[i] = [p]
            else:
                # Edge lies on the plane (degenerate case)
                # For simplicity, treat as no intersection or handle separately
                pass

    # Step 3: Slice faces
    new_faces = []
    face_edges = {} # Maps face_index to list of new vertex indices
    
    for i, face in enumerate(complex.faces):
        intersecting_points = []
        for edge_idx in face:
            if edge_idx in edge_intersections:
                intersecting_points.extend(edge_intersections[edge_idx])
        
        if len(intersecting_points) >= 2:
            # Create new face from intersection points
            # Note: Points must be ordered correctly along the face boundary
            # This requires geometric sorting or adjacency knowledge
            ordered_points = sort_points_on_plane(intersecting_points, hyperplane.normal)
            new_faces.append(ordered_points)
            face_edges[i] = ordered_points

    # Step 4: Slice cells
    new_cells = []
    
    for i, cell in enumerate(complex.cells):
        intersecting_face_edges = []
        for face_idx in cell:
            if face_idx in face_edges:
                intersecting_face_edges.append(face_edges[face_idx])
        
        if len(intersecting_face_edges) > 0:
            # Create new cell from intersection faces
            # This forms the boundary of the 3D cross-section volume
            new_cells.append(intersecting_face_edges)

    # Step 5: Triangulate non-triangular faces
    triangulated_faces = []
    for face in new_faces:
        if len(face) < 3:
            continue
        if len(face) == 3:
            triangulated_faces.append(face)
        else:
            # Fan triangulation from first vertex
            v0 = face[0]
            for k in range(1, len(face) - 1):
                triangulated_faces.append([v0, face[k], face[k+1]])

    return {
        'vertices': new_vertices,
        'faces': triangulated_faces,
        'cells': new_cells
    }

def lerp(a, b, t):
    return [a[i] + t * (b[i] - a[i]) for i in range(len(a))]

def sort_points_on_plane(points, normal):
    """
    Sorts points lying on a plane into a convex polygon order.
    Uses the plane normal to define a rotation axis.
    """
    if len(points) < 3:
        return points
    
    # Find centroid
    centroid = [0, 0, 0, 0]
    for p in points:
        for i in range(4):
            centroid[i] += p[i]
    for i in range(4):
        centroid[i] /= len(points)
        
    # Project to 2D basis on the plane
    # Create two orthogonal vectors u, v perpendicular to normal
    u = find_orthogonal(normal)
    v = cross(normal, u)
    
    projected = []
    for p in points:
        # Remove component along normal
        p_proj = [p[i] - dot(p, normal) * normal[i] for i in range(4)]
        # Project onto u and v
        # Note: u and v must be normalized
        x = dot(p_proj, u)
        y = dot(p_proj, v)
        projected.append((x, y, p))
        
    # Sort by angle
    projected.sort(key=lambda pt: atan2(pt[1], pt[0]))
    
    return [pt[2] for pt in projected]

def find_orthogonal(v):
    """Find a vector orthogonal to v."""
    # Simple heuristic: pick a vector not parallel to v
    if abs(v[0]) < 0.9:
        u = [1, 0, 0, 0]
    else:
        u = [0, 1, 0, 0]
    # Subtract projection
    proj = dot(u, v) * v
    return [u[i] - proj[i] for i in range(4)]

def cross(a, b):
    """Cross product in 4D is not unique; this is a placeholder for 
    finding an orthogonal vector in the subspace. 
    For sorting, a simpler 2D projection might be used if the plane is known."""
    # This function is illustrative. In practice, a basis for the hyperplane
    # should be precomputed.
    return [0, 0, 0, 0]
```

**Parameters:**
*   **Hyperplane:** Defined by a 4D normal vector and a scalar distance. Typical values depend on the specific 4D scene being rendered.
*   **Convexity:** The algorithm assumes convexity. Non-convex objects require preprocessing or result in invalid "illegal" edges [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Non-convex Objects:** If the object is non-convex, an edge may intersect the plane at more than two points, creating edges with more than two endpoints. This breaks the hierarchical assumption of the algorithm [S1, unofficial].
*   **Parallelization:** The algorithm is inherently sequential (vertices $\to$ edges $\to$ faces $\to$ cells) due to data dependencies. Parallelizing is difficult because the number of boundary elements varies per face/cell. It is best suited for CPU execution [S1, unofficial].
*   **Texture Coordinates:** The method does not natively support texture coordinates because the data structure only stores face indices, not explicit vertex attributes for intermediate points. Texture mapping requires converting the complex to tetrahedra first [S1, unofficial].

## Subtopics

### [4D Tetrahedron Slicing (Geometry Shader)](19630-4d-tetrahedron-slicing-geometry-shader.md)
A GPU-based method to compute the 3D cross-section of a 4D tetrahedron against a slicing hyperplane using the Geometry Shader. It outputs 0, 1, or 2 triangles representing the intersection. It sets itself apart from its sibling [4D Tetrahedron Slicing (Vertex Shader)](19631-4d-tetrahedron-slicing-vertex-shader.md) by avoiding adjacency primitives and data replication, instead replicating vertex data four times to drive parallel computation in the Vertex Shader, at the cost of increased conditional branching.

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of vertices, edges, faces, and cells, but with significant constant factors due to the sequential nature of the algorithm.
*   **Memory Complexity:** Proportional to the size of the Cell Complex. The output size is generally smaller than the tetrahedralized version.
*   **Performance:** The algorithm is efficient for objects with few faces, such as regular polytopes (e.g., hypercubes, hyperspheres approximated by polytopes) [S1, unofficial]. It is not suitable for highly complex, non-convex meshes.
*   **Strengths:** Reduces primitive count compared to tetrahedralization; intuitive hierarchical structure.
*   **Limitations:** Requires convexity; difficult to parallelize; no native texture support; CPU-bound.
*   **When to Use:** Rendering simple, convex 4D objects on CPU where primitive count optimization is critical.
*   **When Not to Use:** Rendering complex, non-convex 4D objects; when GPU acceleration is required; when texture mapping is needed.

## Background
The method originates from the field of 4D computer graphics, specifically in the context of rendering 4D scenes. It was proposed as an improvement over tetrahedralization methods, which can generate a large number of primitives for complex 4D shapes [S1, unofficial]. The author implemented this method in a software renderer called "4dViewer" and later in the "Tesserxel" engine, where it was used as a modeling tool before conversion to tetrahedra for rendering [S1, unofficial]. The approach leverages the properties of CW-Complexes to handle 4D geometry without explicit decomposition into 4D simplices.
