# Multi-type Voxel Storage

Also called: HashMap-based Voxel Storage, VoxelKind Enum Storage

## Overview
Multi-type Voxel Storage extends the binary existence model of sparse voxel structures by associating a discrete material identifier with each occupied voxel, allowing a voxel world to distinguish between different material kinds (e.g., dirt, stone) rather than treating all voxels as identical solid entities [S1, unofficial]. It builds on [Voxel World Data Structure](1101-voxel-world-data-structure.md) by introducing a specific enumeration-based type system for voxel content.

## How it works
**Inputs:** World position ($P \in \mathbb{Z}^3$), Voxel Kind ($K \in \text{VoxelKind}$ or None).
**Outputs:** Updated chunk state.

**Data Structures:**
*   `VoxelKind`: An enumeration defining material types (e.g., `Dirt`, `Stone`, `Air`).
*   `Chunk`: A structure containing:
    *   `position`: 3D integer vector representing the chunk's grid coordinates.
    *   `voxels`: A `HashMap` mapping local 3D integer coordinates ($L \in \mathbb{Z}^3, 0 \le L_i < 32$) to `VoxelKind`.
    *   `mesh`: A reference or handle to the generated mesh geometry (or `None` if invalid).
*   `World`: A collection of `Chunk` objects, indexed by their global chunk position.

**Algorithm:**
The storage divides the 3D space into $32 \times 32 \times 32$ chunks. The absence of a key in a chunk's `voxels` HashMap represents air/nothing.

1.  **Chunk Addressing:** Given a world position $P$, calculate the chunk position $C$ and local position $L$:
    $$ C = P \div 32 \quad (\text{integer division, floor towards negative infinity}) $$
    $$ L = P \pmod{32} \quad (\text{remainder, non-negative}) $$
    *Note: The source uses `div_euclid` and `rem_euclid`, ensuring consistent behavior for negative coordinates [S1, unofficial].*

2.  **Chunk Retrieval:** Retrieve or create the `Chunk` at $C$. If creating a new chunk, initialize `voxels` as an empty HashMap.

3.  **Voxel Update:**
    *   If $K$ is `None` (removal): Remove $L$ from `chunk.voxels`.
    *   If $K$ is a valid type: Insert $(L, K)$ into `chunk.voxels`.
    *   Invalidate the chunk's mesh by setting `chunk.mesh = None`.

4.  **Chunk Generation (Initialization):**
    When a new chunk is created, it may be pre-filled based on its world Y-coordinate:
    *   If $C.y == 0$: Iterate $x, z \in [0, 31]$. Insert $(x, 0, z)$ with `VoxelKind::Dirt`.
    *   General generation: Iterate $x, y, z \in [0, 31]$. Calculate world position $W = C \times 32 + L$.
        *   If $W.y == 0$: Insert `VoxelKind::Dirt`.
        *   If $W.y < 0$: Insert `VoxelKind::Stone`.
        *   Otherwise: Do not insert (remains air).

**Pseudocode:**

```python
def set_voxel(world: World, position: IVec3, kind: Optional[VoxelKind]):
    """
    Sets or removes a voxel at the given world position.
    """
    # Calculate chunk and local coordinates using Euclidean division
    chunk_position = position.div_euclid(32)
    local_position = position.rem_euclid(32)

    # Get or create the chunk
    chunk = get_or_create_chunk(world, chunk_position)

    # Invalidate mesh to force regeneration on next draw
    chunk.mesh = None

    if kind is None:
        # Remove voxel (air)
        if local_position in chunk.voxels:
            chunk.voxels.pop(local_position)
    else:
        # Insert voxel with specific kind
        chunk.voxels[local_position] = kind

def get_or_create_chunk(world: World, chunk_position: IVec3) -> Chunk:
    """
    Retrieves an existing chunk or creates a new one with procedural generation.
    """
    if chunk_position not in world.chunks:
        voxels = {}
        
        # Procedural generation logic
        # Iterate through all 32^3 local positions
        for z in range(32):
            for y in range(32):
                for x in range(32):
                    offset = IVec3(x, y, z)
                    # Calculate world position of this local voxel
                    world_voxel_position = chunk_position * 32 + offset
                    
                    if world_voxel_position.y == 0:
                        voxels[offset] = VoxelKind.Dirt
                    elif world_voxel_position.y < 0:
                        voxels[offset] = VoxelKind.Stone
                    # Else: air (do not insert)
        
        chunk = Chunk(position=chunk_position, voxels=voxels, mesh=None)
        world.chunks[chunk_position] = chunk
    
    return world.chunks[chunk_position]
```

**Edge Cases and Pitfalls:**
*   **Negative Coordinates:** Standard modulo operators can return negative remainders in some languages. `div_euclid` and `rem_euclid` must be used to ensure $L$ is always in $[0, 31]$ [S1, unofficial].
*   **Mesh Invalidation:** Setting `mesh = None` is critical. The source does not specify automatic mesh regeneration triggers; the implementation must check this flag before rendering [S1, unofficial].
*   **HashMap Overhead:** Using a HashMap for every chunk introduces memory overhead for the hash table structure itself, not just the voxel data.

## Operating characteristics
*   **Time Complexity:**
    *   Lookup/Insert: $O(1)$ average case for HashMap operations [S1, unofficial].
    *   Chunk Generation: $O(32^3) = O(32768)$ operations per new chunk during initialization [S1, unofficial].
*   **Memory Complexity:**
    *   Proportional to the number of *occupied* voxels plus the overhead of the HashMap entries. Empty space is not stored.
    *   Each entry stores an `IVec3` key and a `VoxelKind` enum value.
*   **Strengths:**
    *   Sparse: Efficiently handles large worlds with low voxel density.
    *   Flexible: Supports multiple material types natively.
    *   Simple: Easy to implement using standard library HashMaps.
*   **Limitations:**
    *   Hash collisions (though rare with good hash functions) can degrade performance.
    *   Iterating over all voxels in a chunk requires iterating the HashMap, which is not cache-friendly compared to dense arrays.
    *   No built-in support for hierarchical structures (e.g., octrees) within the chunk.
*   **When to Use:** Small to medium-sized voxel worlds where material variety is required, and extreme performance optimization (like SIMD or cache-aware layouts) is not the primary goal.
