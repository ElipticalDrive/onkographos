# Cell Reconstruction via Octree Hashing

Also called: Frisken and Perry hashing scheme, Octree Hashing Scheme

## Overview
Cell Reconstruction via Octree Hashing locates leaf nodes and retrieves adjacent forward neighbor voxels in a sparse octree volume, enabling isosurface reconstruction from scalar data stored with only one value per leaf voxel [S1, S2, S3]. It solves the requirement for 8 corner values in a cell intersection primitive by retrieving the 7 forward neighbors at intersection time using a bitwise arithmetic hash scheme for point location [S2, S3]. Unlike [Cell Retrieval via Neighbor-Finding](1822-cell-retrieval-via-neighbor-finding.md), which relies on spatial locality to skew toward O(1) performance, this method guarantees O(log N) point location from the root without explicit parent pointers [S1, S2, S3].

## How it works
**Inputs and Outputs:**
*   **Input:** 3D integer coordinates $(x, y, z)$ representing a voxel center or corner, and the root of the sparse octree [S2].
*   **Output:** The leaf node containing the coordinate, or the set of 7 forward neighbor leaf nodes required to define the 2x2x2 cell for intersection testing [S3].

**Data Structures:**
The method operates on an implicit octree where nodes are identified by their spatial position [S2]. The octree depth is bounded by $d_{max}$ [S2]. Each node maps to a point $P$ in the interval $[0, 2^{d_{max}}]^3$ using bitwise arithmetic [S2]. Cap nodes reside at depth $d_{max}-1$ and contain 8 finest-level scalar leaves [S2]. Interior nodes store pointers to 8 children and min/max pairs for each child [S2]. Scalar leaves store a single coarser-resolution scalar value embedded in their parent [S2].

**Steps:**
1.  **Coordinate Mapping:** Map the 3D integer coordinates $(x, y, z)$ to a structured bit pattern by interleaving the bits of the X, Y, and Z coordinates [S2].
2.  **Point Location:** Start at the octree root. Determine the octant index by performing a bitwise-AND with a left-shifted mask on the interleaved coordinates [S2]. Traverse to the corresponding child. Repeat until a leaf node is reached [S2].
3.  **Neighbor Finding:** Given an origin leaf and a destination direction, find the nearest common ancestor (NCA) of the origin leaf and the target location [S2]. Perform point location from the NCA to the target leaf [S2]. Retrieve the scalar values from the 7 forward neighbors [S3].

**Formulas:**
*   **Octant Index:** $i = (x \& M_x) | (y \& M_y) | (z \& M_z)$, where $M_x, M_y, M_z$ are masks derived from the current depth level, and the bits are interleaved [S2].
*   **Complexity:** Worst-case neighbor finding is $O(\log N)$; best-case and average-case are $O(1)$ when neighbors share a parent node [S2].

**Parameters:**
*   $d_{max}$: The maximum depth of the octree. Structures start at $d_{max}-1$ for cap nodes [S2].

**Pitfalls:**
*   **Optimization:** Precompute masks and use constant interleaving for interactivity to avoid expensive arbitrary left-shifts during traversal [S2].

**Pseudocode:**
```python
def point_location(root, x, y, z, d_max):
    """Locates the leaf node at integer coordinates (x, y, z)."""
    node = root
    for depth in range(d_max, -1, -1):
        # Determine octant index using bitwise-AND with left-shifted mask
        octant = 0
        if (x >> depth) & 1: octant |= 1
        if (y >> depth) & 1: octant |= 2
        if (z >> depth) & 1: octant |= 4
        if node.is_leaf:
            return node
        if node.children[octant] is None:
            return None
        node = node.children[octant]
    return node

def find_nca(origin_x, origin_y, origin_z, target_x, target_y, target_z, d_max):
    """Finds the depth of the nearest common ancestor via bitwise comparison [G]."""
    for depth in range(d_max, -1, -1):
        if ((origin_x ^ target_x) >> depth) & 1 or \
           ((origin_y ^ target_y) >> depth) & 1 or \
           ((origin_z ^ target_z) >> depth) & 1:
            return depth + 1
    return 0

def find_neighbor(origin_leaf, direction, d_max):
    """Finds a forward neighbor leaf given an origin and a direction vector."""
    origin_x, origin_y, origin_z = origin_leaf.coords
    target_x = origin_x + direction.x
    target_y = origin_y + direction.y
    target_z = origin_z + direction.z
    # 1. Find the nearest common ancestor
    nca_depth = find_nca(origin_x, origin_y, origin_z, target_x, target_y, target_z, d_max)
    # 2. Perform point location from root to target
    return point_location(origin_leaf.root, target_x, target_y, target_z, d_max)
```

## Subtopics

### Min/Max Tree Construction with Forward Neighbors
A bounding volume hierarchy built on the octree where each node stores the min/max of the isosurface values within its spatial extent [S3]. Because cells are defined by forward neighbors, the min/max for a node must consider not just its 8 children, but also their forward neighbors [S3]. To compute the min/max tree: for leaf nodes, compute the min/max of the 8-voxel cell (current voxel + 7 forward neighbors); for interior nodes, compute the min/max of the min/max pairs of all 8 children, effectively considering 27 voxel values for each parent node's bounding box [S3]. Storage overhead is approximately 22% additional footprint on top of raw scalar octree-compressed data, achieved by computing extrema temporarily at leaf nodes and storing the min/max tree starting at depth $d_{max}-1$ [S3]. Storing min/max pairs for every scalar voxel would demand over three times the storage of the raw octree data; to avoid this, min/max pairs are omitted at leaf nodes and computed on the fly during neighbor lookup [S3].

## Operating characteristics
*   **Time Complexity:** Point location is $O(\log N)$ in the worst case. Neighbor finding is $O(\log N)$ in the worst case but $O(1)$ in the best and average cases when neighbors share a parent node [S2].
*   **Memory Complexity:** The base octree stores one scalar per leaf [S3]. The Min/Max Tree variant adds ~22% overhead [S3].
*   **Strengths:** Efficient point location and neighbor retrieval without explicit parent pointers; suitable for interactive ray tracing [S1, S2].
*   **Limitations:** Worst-case neighbor finding is slower than methods that guarantee O(1) via spatial locality assumptions [S2].
*   **When to use:** When memory is constrained and the octree is sparse, and interactive performance is required [S1].

## Background
Point location and neighbor-finding algorithms were pioneered by Glassner [6] and Samet [17] for use in ray tracing [S1]. Frisken and Perry [4] proposed an efficient hashing scheme using binary arithmetic on integer coordinates, which serves as the foundation for this method [S1]. The method was further optimized for interactive isosurface ray tracing of large octree volumes [S1, S2].
