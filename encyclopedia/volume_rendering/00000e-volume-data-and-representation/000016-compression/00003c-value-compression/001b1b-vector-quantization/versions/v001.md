# Vector Quantization

Also called: Cg decoding module, Codebook-based compression, Fixed-to-fixed compression, GPU-based Vector Quantization Decoding, Improved vector quantizer, LBG algorithm modification, Vector Quantization for Color Features

## Overview
Vector Quantization (VQ) is a lossy data compression algorithm that maps a set of $n$-dimensional input vectors to a single fixed-length index referencing an entry in a pre-defined $n$-dimensional codebook [S1, S3]. It solves the problem of storing large volumes of high-dimensional data (such as voxel color features or time-varying volumetric blocks) by exploiting redundancy: instead of storing every vector individually, it stores a compact codebook and a mapping index for each data element [S2]. Unlike scalar quantization, VQ operates on multi-dimensional vectors, allowing it to capture correlations between data components [S3]. It is distinguished from its siblings by its "fixed-to-fixed" nature (mapping $n$-dimensional vectors to $r$-bit indices) and its reliance on a learned codebook, whereas [Hierarchical Vector Quantization](827-hierarchical-vector-quantization.md) uses a tree structure, and [Triadic frequency band decomposition](828-triadic-frequency-band-decomposition.md) operates in the frequency domain.

## How it works
**Inputs:** A set of $N$ input vectors $S = \{\vec{x}_1, \vec{x}_2, \dots, \vec{x}_N\}$, where each $\vec{x}_i \in \mathbb{R}^n$. For GPU-based decoding, inputs are also the compressed indices and the codebook.
**Outputs:** A codebook $C$ of size $K = 2^r$ codewords, and for each input vector $\vec{x}_i$, an index $j \in \{0, \dots, K-1\}$ such that $\vec{x}_i \approx \vec{c}_j$, where $\vec{c}_j$ is the codeword at index $j$ in $C$.

**Data Structures:**
1.  **Codebook ($C$):** A list of $K$ vectors, each of dimension $n$. Stored in memory (e.g., as a 3D texture in GPU implementations).
2.  **Index Map:** For each input vector $\vec{x}_i$, an integer index $j$ of $r$ bits. In volumetric rendering, this is often stored as a 3D texture where each texel holds the index for the corresponding voxel or block [S1, S2].

**Algorithm Steps:**

1.  **Codebook Initialization:** Generate an initial set of $K$ codewords. Common methods include random selection from the input data or using Principal Component Analysis (PCA) to split the data space [S1, S3].
2.  **Assignment (Partitioning):** For each input vector $\vec{x}_i$, find the codeword $\vec{c}_j$ in $C$ that minimizes the distortion metric $\delta(\vec{x}_i, \vec{c}_j)$. The most common metric is the squared Euclidean distance:
    $$ \delta(\vec{x}, \vec{y}) = \|\vec{x} - \vec{y}\|^2_2 $$
    Assign $\vec{x}_i$ to the partition $p_j$ associated with index $j$ [S3].
3.  **Codebook Update:** Recalculate each codeword $\vec{c}_j$ as the centroid of all vectors currently assigned to partition $p_j$:
    $$ \vec{c}_j = \frac{1}{|p_j|} \sum_{\vec{x} \in p_j} \vec{x} $$
    If a partition $p_j$ is empty (the "empty cell problem"), the codeword must be re-initialized or merged with another, as it contributes no distortion reduction but consumes index space [S1, S3].
4.  **Convergence Check:** Calculate the average distortion $D_{avg}$:
    $$ D_{avg} = \frac{1}{N} \sum_{i=1}^N \|\vec{x}_i - \vec{c}_{j_i}\|^2_2 $$
    If the change in $D_{avg}$ is below a threshold or a maximum iteration count is reached, stop. Otherwise, return to Step 2.

**GPU Decoding Implementation (Cg/GL):**
When decoding on a GPU using Cg (which lacks bitwise/shift operations and uses float coordinates), specific transformations are required [S1]:

1.  **Coordinate Mapping:** Map integer voxel coordinates $(x, y, z)$ to float texture coordinates in $[-1.0, 1.0]$:
    $$ x_{float} = \frac{x}{D_x - 1} - 1.0, \quad y_{float} = \frac{y}{D_y - 1} - 1.0, \quad z_{float} = \frac{z}{D_z - 1} - 1.0 $$
    where $D_x, D_y, D_z$ are the dimensions of the volume [S1].
2.  **Simulate Integer Division:** To simulate $\lfloor x/4 \rfloor$ without shift operations, use `GL_NEAREST` texture filtering on a specific address texture. Map integers $4, 5, 6, 7$ to texture coordinates that sample the same texel. The transformation for texture $I$ is:
    $$ x' = (x \cdot 0.5 + 0.5) \cdot \frac{D_x - 1}{\frac{D_x - 4}{D_y - 1}} - \frac{2 D_x - 8}{3} $$
    (Similar formulas apply for $y'$ and $z'$). Clamp results to $[0.0, 1.0]$ using `GL_CLAMP` if they fall outside [S1].
3.  **Address Texture Sampling:** Use a 3D address texture (Texture A) of size $4^3$ to retrieve block-specific weights. The texture coordinates for this lookup are:
    $$ x_A = (x \cdot 0.5 + 0.5) \cdot \frac{D_x}{4}, \quad y_A = (y \cdot 0.5 + 0.5) \cdot \frac{D_y}{4}, \quad z_A = (z \cdot 0.5 + 0.5) \cdot \frac{D_z}{4} $$
    Use `GL_REPEAT` to handle coordinates exceeding the texture bounds [S1].
4.  **Reconstruction:** The decoded value is computed by sampling the address texture and combining it with the codebook lookup. For time-varying data, add the decompressed difference (P-frame) to the previously reconstructed volume (accumulated from I-frames) [S1].

**Parameters:**
*   **Index Bit-size ($r$):** Determines codebook size $K=2^r$. Typical value is 8 bits ($K=256$), balancing compression ratio and distortion [S1].
*   **Dimension ($n$):** Dimensionality of the input vectors (e.g., 3 for RGB color, or higher for multi-parameter features) [S3].

**Edge Cases and Pitfalls:**
*   **Empty Cells:** Iterative algorithms like LBG can result in empty partitions, increasing distortion and execution time [S1, S3]. Using PCA-based splitting avoids this [S1].
*   **Accumulated Error:** In time-varying sequences, repeatedly adding difference data causes error accumulation. Mitigated by using I-frames (original data) periodically [S1].
*   **GPU Limitations:** Cg does not support bitwise operations or shifts. Integer coordinates must be carefully mapped to float ranges, and border conditions must be clamped [S1].

## Subtopics

### [Progressive Encoding of Time-Varying Sequences](959-progressive-encoding-of-time-varying-sequences.md)
A scheme for encoding time-varying volumetric data where frames are encoded individually but reuse codebooks from previous frames to improve performance and compression.

## Operating characteristics
*   **Time Complexity:** Encoding (codebook generation) is iterative and can be slow, especially with the LBG algorithm [S3]. Decoding is $O(1)$ per vector (index lookup), making it suitable for real-time rendering [S1].
*   **Memory Complexity:** Storage is $O(K \cdot n + N)$, where $K$ is codebook size, $n$ is vector dimension, and $N$ is the number of input vectors (stored as indices). This is significantly smaller than storing $N \cdot n$ raw vectors [S2].
*   **Performance:** High compression ratios are achieved for data with high spatial or temporal redundancy (e.g., highly sparse data or time-varying sequences) [S1].
*   **Strengths:** Fast decoding; effective for high-dimensional data; portable via texture-based GPU implementation [S1].
*   **Limitations:** Lossy compression; encoding can be slow; sensitive to the "empty cell problem" in naive implementations; requires careful handling of GPU coordinate systems [S1, S3].
*   **When to use:** Large time-varying volumetric data, highly sparse volumetric data, or compressing color features in neural radiance fields [S1, S2].
*   **When not to use:** Lossless compression requirements; data with low redundancy; real-time encoding constraints where LBG speed is insufficient [S1, S3].

## Background
Vector Quantization was developed in the context of speech and image compression, with the Linde-Buzo-Gray (LBG) algorithm introduced in 1980 by Linde, Buzo, and Gray, improving upon scalar quantizers by Max (1960) and Lloyd (1982) [S3]. In volume rendering, it was adapted to handle large volumetric datasets by exploiting spatial and temporal redundancy [S1]. Recent applications include compressing Volumetric Radiance Fields (NeRFs) to reduce storage by ~100x [S2].
