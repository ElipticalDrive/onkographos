# Cell-Definition-Shape Geometry Model

Also called: Immutable Definition and Compact Cell Storage, VXL-042, VXL-03, VXL-044, VXL-045

## Overview
The Cell-Definition-Shape (CDS) geometry model is a lightweight, immutable data structure for representing non-regular volumes within a voxel rendering system. It solves the problem of efficiently storing and sharing complex geometric definitions without requiring a global registry or heavy reference counting overhead. It sets itself apart from sibling methods by decoupling the geometric definition (Shape) from its instance placement (Cell) via an intermediate immutable Definition object, allowing multiple cells to share geometry and material bindings through value semantics and shared pointers.

## How it works

### Inputs and Outputs
*   **Input:** A set of polygons defining a Shape, vertex positions, normals, UVs, and material slots.
*   **Output:** A `Volume` containing a local table of `Definition` objects and a compact array of `Cell` indices. Public API exposes `Cell` values.

### Data Structures

#### MeshVertex
The fundamental vertex structure for shapes.
*   `position`: `spk::Vector3Int` (Integer coordinates, quantized to 1/1000 grid, range 0-1000).
*   `normal`: `spk::Vector3` (Float).
*   `uv`: `spk::Vector2` (Float).
*   `materialIndex`: `std::uint32_t` (Local index to Model).

#### Shape
A collection of polygons.
*   **Polygon Constraints:** Each polygon must be planar, convex, and have at least three vertices [S1]. Globally concave shapes are represented as a union of multiple convex polygons, not a single concave polygon [S1].
*   **Shell Classification:** Polygons are classified into `outerShell` or `innerShell` at construction [S1].
    *   `outerShell`: All vertices lie on the same unit cube boundary plane (coordinate X, Y, or Z is constant and equal to 0 or 1000) [S1].
    *   `innerShell`: All other polygons [S1].
*   **Boundary Coverage:** Six 2D boundary coverages are calculated exclusively from `outerShell` polygons [S1]. These coverages must be decomposable into unions of axis-aligned 2D rectangles on the 1000x1000 grid, not a single bounding box, to avoid false occlusions [S1]. `innerShell` polygons retain their 3D data, UVs, and material slots independently of these coverages [S1].

#### Definition
An immutable object that associates a `Shape` with semantic material slots of a `Model`.
*   **Layout:** Contains a `std::shared_ptr<const Data>` pointing to the immutable geometry data [S1].
*   **Properties:** Does not contain concrete palette materials [S1]. Copying a Definition is lightweight because it shares the underlying `Data` pointer [S1].

#### Cell
A lightweight value type stored in the Volume.
*   **Layout:** Contains a `Definition` by value (light copy) and an `orientation` [S1].
*   **Orientation:** Discrete set of 8 variants: 4 rotations of 90 degrees around the Y-axis and one vertical flip [S1].
*   **Storage:** Stored compactly in the Volume using indices [S1]. The Volume maintains a local table of definitions and reconstructs `Cell` values on public reads [S1].

### Steps

1.  **Shape Construction:**
    *   Validate that all polygons are planar, convex, and have $\ge 3$ vertices [S1].
    *   Classify each polygon:
        *   If all vertices share a constant coordinate (0 or 1000) on X, Y, or Z, assign to `outerShell` [S1].
        *   Otherwise, assign to `innerShell` [S1].
    *   Calculate 2D boundary coverages for the six faces of the unit cube using only `outerShell` polygons [S1].
    *   Store `innerShell` polygons with their 3D data, UVs, and material slots [S1].

2.  **Definition Creation:**
    *   Create an immutable `Definition` object [S1].
    *   Associate the `Shape` with the `Definition` [S1].
    *   Bind semantic material slots from the `Model` to the `Definition` [S1].
    *   Encapsulate the geometry data in a `std::shared_ptr<const Data>` [S1].

3.  **Cell Creation:**
    *   Instantiate a `Cell` by value [S1].
    *   Assign the `Definition` to the `Cell` [S1].
    *   Assign an `orientation` from the 8 discrete variants (4 Y-rotations $\times$ 2 flips) [S1].

4.  **Volume Population:**
    *   Store `Definition` objects in a local table within the `Volume` [S1].
    *   Store `Cell` indices compactly in the `Volume` [S1].
    *   On public read, reconstruct the `Cell` value from the stored index and the local definition table [S1].

### Parameters
*   **Vertex Quantization:** Coordinates are quantized to a 1/1000 integer grid (`spk::Vector3Int`) ranging from 0 to 1000 [S1]. This applies to both Shape definition and visible fragments after occlusion culling [S1].
*   **Boundary Grid Resolution:** 2D boundary coverages are evaluated on integer grids of resolution 1000 $\times$ 1000 [S1].
*   **Orientation Variants:** 8 total (4 rotations $\times$ 2 flips) [S1].

### Edge Cases and Pitfalls
*   **Empty Boundary Coverages:** Shapes with no boundary polygons (e.g., vegetation, small centered shapes) may have six empty coverages while retaining a non-empty `innerShell` [S1]. The Mesher must handle emitting or discarding interior faces based on occlusion, not just geometric presence [S1].
*   **False Occlusions:** Filled boundary coverages must be decomposable into unions of axis-aligned 2D rectangles. Using a single bounding box can produce false occlusions [S1].
*   **No Global Registry:** No global Catalog is mandatory for resolving Shapes and bindings [S1].
*   **Degenerate Input:** Exact conventions for vertex winding, UV indexing, and handling degenerate inputs are not fully defined in the sources [S1].

## Operating characteristics

*   **Time Complexity:** Shape construction is linear in the number of polygons. Cell creation is constant time. Volume population is linear in the number of cells.
*   **Memory Complexity:** Memory usage is proportional to the number of unique Definitions and Cells. Sharing of `Data` via `shared_ptr` reduces memory footprint for repeated geometries.
*   **Performance:** The use of integer coordinates (1/1000 grid) simplifies boundary coverage calculations and occlusion culling. The compact storage of Cells reduces memory bandwidth during rendering.
*   **Strengths:** Lightweight value semantics for Cells. No global registry required. Efficient sharing of geometry and materials.
*   **Limitations:** Limited to convex polygons. Global concavity requires decomposition. Boundary coverage calculation is restricted to axis-aligned planes.
*   **When to Use:** Suitable for voxel-based rendering systems requiring efficient storage and sharing of complex, non-regular geometric shapes.
*   **When Not to Use:** Not suitable for scenes requiring global concave shapes without decomposition or non-axis-aligned boundary coverage.

## Background

The Cell-Definition-Shape geometry model is part of the Voxel Rendering System design, specifically defined in the VXL-042, VXL-043, VXL-044, and VXL-045 specifications [S1]. It was developed as part of the Sparkle voxel engine project [S1]. The model emphasizes immutability and value semantics to simplify resource management and improve performance in voxel-based rendering.
