# VisIt Data Parallel Volume Rendering

Also called: Parallel Volume Rendering with AMR, VisIt AMR Parallelization, VisIt AMR Volume Rendering, VisIt Childs & Miller (2006) method, VisIt Data Parallel Volume Rendering for AMR, VisIt parallel volume rendering

## Overview
VisIt Data Parallel Volume Rendering is a data-parallel volume rendering scheme implemented in the VisIt visualization tool that resolves complex sorting issues in unstructured Adaptive Mesh Refinement (AMR) meshes while handling load balancing challenges specific to AMR hierarchies [S1, S2, unofficial]. It sets itself apart from sibling methods by treating AMR patches as atomic units for distribution and explicitly ignoring ghost cells to ensure correct sampling at refinement boundaries, whereas its parent method [AMR Structure-Preserving Parallel Volume Rendering](17552-amr-structure-preserving-parallel-volume-rendering.md) focuses on preserving block structure through raycasting with adaptive sampling without specifying this specific atomic patch assignment and ghost-cell filtering strategy.

## How it works
**Inputs and Outputs:**
*   **Input:** An AMR dataset consisting of patches at various refinement levels, where each patch is an atomic unit of data. Each cell in the mesh may be marked as "ghost" or "active."
*   **Output:** A rendered image (framebuffer) generated by parallel processors.

**Data Structures:**
*   **Patch:** An atomic unit of AMR data assigned to a processor. It contains the grid cells and their associated attributes (e.g., scalar values).
*   **Ghost Flag:** A boolean attribute per cell indicating whether the cell is a ghost cell (used for interpolation across patch boundaries) or an active cell (used for rendering).

**Parameters:**
*   **Number of Processors ($P$):** The number of parallel processors in the VisIt server.
*   **Refinement Level:** The depth of the octree or hierarchy. Coarser levels have larger spatial footprints.
*   **Typical Values:** Not given in the sources.

**Steps:**
1.  **Partitioning:** Partition the input AMR dataset among the $P$ parallelized processors. Each patch is treated as an atomic unit and assigned to exactly one processor [S1, S2, unofficial].
    *   *Load Balancing Strategy:* To counteract load imbalance, the assignment algorithm minimizes the number of patches at coarse refinement levels on any given processor. This is because coarse patches occupy a larger spatial footprint, cover more of the picture, contribute more samples, and take much longer to sample than finer patches [S1, S2, unofficial].
2.  **Raycasting/Sampling:** For each pixel, cast a ray through the volume.
    *   For each sample point along the ray, determine which patch contains the point.
    *   If a sample point is contained by multiple patches at different refinement levels, only the value from the finest level is accepted [S1, S2, unofficial].
    *   Check the ghost flag of the cell at the sample point in the selected patch.
    *   If the cell is marked as **ghost**, ignore the sample (do not accumulate color/opacity) [S1, S2, unofficial].
    *   If the cell is **active**, compute the transfer function value (color and opacity) and accumulate it into the framebuffer.
3.  **Compositing:** Composite the accumulated samples along the ray to produce the final pixel color.

**Pseudocode:**

```python
def visit_amr_volume_rendering(patches, num_processors, ray_origin, ray_direction, framebuffer):
    """
    Simulates the VisIt Data Parallel Volume Rendering scheme.
    
    Args:
        patches: List of patch objects. Each patch has:
            - level: int (refinement level)
            - cells: list of cell objects. Each cell has:
                - is_ghost: bool
                - value: float (scalar data)
            - owner: int (processor ID)
        num_processors: int
        ray_origin: Vector3
        ray_direction: Vector3
        framebuffer: Array of pixel colors
        
    Returns:
        framebuffer: Updated array of pixel colors
    """
    
    # Step 1: Partitioning (Simplified for demonstration)
    # In reality, VisIt uses a load-balancing algorithm to assign patches.
    # Here we assume patches are already assigned to processors.
    processor_patches = [[] for _ in range(num_processors)]
    for patch in patches:
        processor_patches[patch.owner].append(patch)
        
    # Each processor renders its assigned patches
    for proc_id in range(num_processors):
        my_patches = processor_patches[proc_id]
        
        # Render pixels assigned to this processor (simplified)
        for pixel in framebuffer:
            # Cast ray
            sample_points = cast_ray(ray_origin, ray_direction, pixel.bounds)
            
            accumulated_color = (0.0, 0.0, 0.0, 0.0) # RGBA
            
            for point in sample_points:
                # Find the finest patch containing this point
                # Note: In a real implementation, spatial indexing (e.g., BVH) is used.
                candidate_patches = find_patches_containing_point(point, my_patches)
                
                if not candidate_patches:
                    continue
                
                # Select the finest level patch
                # If multiple patches at the same finest level overlap, 
                # VisIt's specific tie-breaking is not detailed, but ghost flags resolve most conflicts.
                finest_patch = max(candidate_patches, key=lambda p: p.level)
                
                # Find the cell in the finest patch containing the point
                cell = find_cell_in_patch(point, finest_patch)
                
                if cell is None:
                    continue
                
                # Step 2: Ghost Cell Check
                if cell.is_ghost:
                    # Ignore samples from ghost cells
                    continue
                
                # Compute transfer function
                color, opacity = compute_transfer_function(cell.value)
                
                # Composite
                accumulated_color = composite(accumulated_color, color, opacity)
            
            framebuffer[pixel.index] = accumulated_color

    return framebuffer

def composite(current_color, new_color, new_opacity):
    """
    Front-to-back compositing.
    """
    # current_color is (R, G, B, A)
    # new_color is (R, G, B)
    # new_opacity is alpha
    
    current_r, current_g, current_b, current_a = current_color
    new_r, new_g, new_b = new_color
    
    # Alpha blending
    # C_out = C_in * (1 - alpha_new) + C_new * alpha_new
    # A_out = A_in + alpha_new * (1 - A_in)
    
    out_a = current_a + new_opacity * (1 - current_a)
    if out_a == 0:
        return (0, 0, 0, 0)
        
    out_r = (current_r * (1 - new_opacity) + new_r * new_opacity) / out_a
    out_g = (current_g * (1 - new_opacity) + new_g * new_opacity) / out_a
    out_b = (current_b * (1 - new_opacity) + new_b * new_opacity) / out_a
    
    return (out_r, out_g, out_b, out_a)
```

**Edge Cases and Pitfalls:**
*   **Load Imbalance:** Coarser refinement level patches occupy a larger spatial footprint, cover a much larger portion of the picture, contribute more samples, and typically take much longer to sample than patches at finer refinement levels. This causes significant load imbalance if not managed by minimizing coarse patches per processor [S1, S2, unofficial].
*   **Ghost Cells:** If ghost cells are not ignored, incorrect values from coarser levels may be used when finer levels are present, or interpolation artifacts may occur. VisIt explicitly ignores all samples from cells marked ghost [S1, S2, unofficial].
*   **Multiple Patches at Same Point:** If a sample point is contained by many patches at different refinement levels, only the value at the finest level is accepted. The other levels have the corresponding cell marked as ghost, ensuring consistency [S1, S2, unofficial].

## Operating characteristics
*   **Time Complexity:** The running time is dependent on the amount of data and the amount of samples [S2, unofficial]. Specifically, it is proportional to the number of active (non-ghost) samples across all patches.
*   **Memory Complexity:** Not given in the sources.
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Scales with the number of processors, provided the load balancing is effective. The load balancing challenge is specific to AMR meshes due to the varying sizes of patches at different refinement levels [S1, S2, unofficial].
*   **Strengths:** Resolves complex sorting issues in unstructured meshes [S1, S2, unofficial]. Handles load balancing for AMR by minimizing coarse patches per processor [S1, S2, unofficial]. Correctly handles interpolation and rendering across patch boundaries using ghost cells [S1, S2, unofficial].
*   **Limitations:** Load imbalance can still occur if the distribution of coarse patches is uneven. The performance is heavily dependent on the ratio of coarse to fine patches and the view-dependent coverage of coarse patches [S1, S2, unofficial].
*   **When to use:** When visualizing large-scale AMR data using the VisIt tool and requiring correct handling of unstructured mesh sorting and load balancing.
*   **When not to use:** When using a different visualization framework that does not support VisIt's specific AMR parallelization scheme.

## Background
*   **Origin:** The method is part of the VisIt visualization tool, developed by Childs and Miller (2006) [S1, S2, unofficial].
*   **History:** VisIt is a client-server visualization tool for large datasets. The server is parallelized using data parallel partitioning. The specific handling of AMR data, including the atomic patch assignment and ghost cell filtering, was described in subsequent works on AMR visualization with VisIt [S1, S2, unofficial].
*   **Usage:** VisIt is used for visualization and analysis of massive scale data sets, including computing statistical moments, distribution functions, and derived quantities [S1, S2, unofficial].
