# Time-varying AMR Interpolation Framework

Also called: Kaehler et al. (2005) method, Kaehler et al. framework, Time-Varying AMR Interpolation

## Overview
The Time-varying AMR Interpolation Framework is a method for visualizing time-varying Adaptive Mesh Refinement (AMR) data that addresses the inconsistency of refinement configurations between subsequent time steps [S1, S2, unofficial]. It solves the problem where finer AMR patches update more frequently than coarse patches by ensuring both time steps share an identical refinement configuration through interpolation, thereby enabling consistent feature tracking and rendering [S1, S2, unofficial]. It differs from static AMR interpolation by explicitly handling temporal evolution and remote data access for interpolated values [S1, S2, unofficial].

## How it works
**Inputs:** Two subsequent time steps of AMR simulation data ($T_i$ and $T_{i+1}$), where each time step consists of a hierarchy of patches with varying refinement levels.
**Outputs:** Interpolated values for cells in the coarser time step that correspond to refined regions in the finer time step, and intermediate values for regions covered by coarser levels to ensure temporal consistency.

**Data Structures:**
The framework operates on the existing AMR data structure (e.g., octree or grid hierarchy). No new global data structure is defined; instead, it modifies the interpretation of existing cells during the interpolation phase. The refinement configuration is represented by a boolean mask or hierarchy tree indicating which parent cells are refined at each level for each time step.

**Steps:**
1.  **Configuration Alignment:** Compare the refinement configuration of time step $T_i$ and $T_{i+1}$. Identify cells that are refined in one time step but not the other.
    *   Let $R_i$ be the set of refined cells in $T_i$ and $R_{i+1}$ be the set of refined cells in $T_{i+1}$.
    *   Identify the symmetric difference: cells in $R_i \setminus R_{i+1}$ and $R_{i+1} \setminus R_i$.
2.  **Spatial Interpolation for Configuration Mismatch:** For any cell $c$ that is refined in $T_{i+1}$ but not in $T_i$ (or vice versa), compute the value for $c$ in the time step where it is not refined.
    *   This is achieved by interpolating values from the neighboring cells that *are* refined in that specific time step.
    *   The goal is to ensure that for every cell location, a value exists regardless of whether the local refinement level changed between $T_i$ and $T_{i+1}$ [S1, S2, unofficial].
3.  **Temporal Interpolation for Coarse Regions:** Define an interpolation scheme to compute intermediate values in regions covered by coarser levels.
    *   Since coarse levels are updated less frequently, values for intermediate time points or consistent spatial sampling in these regions must be interpolated from the available coarse data [S1, S2, unofficial].
    *   This ensures that the visualization pipeline receives a temporally consistent dataset, preventing artifacts caused by asynchronous updates of fine and coarse patches.
4.  **Remote Data Access and Computation:** The framework automatically handles remote data access.
    *   Interpolated values are computed on the machine running the simulation (or the data source) rather than the visualization client [S1, S2, unofficial].
    *   This reduces network bandwidth usage by sending only the necessary interpolated values rather than raw high-resolution data for every time step.

**Edge Cases and Pitfalls:**
*   **Precision:** Interpolation introduces approximation errors, particularly when refining from very coarse to very fine levels.
*   **Boundaries:** Interpolation at the boundaries of AMR patches must respect patch boundaries to avoid data leakage.
*   **Degenerate Input:** If a cell is refined in one step but has no refined neighbors in the other step (e.g., isolated refinement), interpolation may fail or produce artifacts. The sources do not specify a fallback.

## Operating characteristics
*   **Time Complexity:** Not given in the sources. Depends on the number of cells in the symmetric difference of refinement configurations and the cost of the interpolation kernel.
*   **Memory Complexity:** Not given in the sources. The framework requires storing interpolated values for cells that were not originally refined in a given time step, potentially increasing memory usage.
*   **Measured Performance:** Not given in the sources.
*   **Strengths:** Ensures consistent visualization of features across time steps despite asynchronous AMR updates; reduces network bandwidth by computing interpolated values on the simulation machine.
*   **Limitations:** Introduces interpolation artifacts; requires significant computational overhead to align refinement configurations and interpolate values for every time step pair.
*   **When to Use:** When visualizing time-varying AMR data where fine patches update more frequently than coarse patches, and consistent feature tracking is required.
*   **When Not to Use:** When real-time performance is critical and interpolation overhead is prohibitive, or when the AMR data is already temporally consistent.

## Background
The framework was described by Kaehler et al. in 2005 [S1, S2, unofficial]. It was developed to address the challenges of visualizing time-varying AMR data, where the asynchronous update rates of fine and coarse patches lead to inconsistent refinement configurations between time steps. The method is part of a broader effort to create custom AMR visualization tools, alongside systems like ChomboVis and VisIt [S1, S2, unofficial].
