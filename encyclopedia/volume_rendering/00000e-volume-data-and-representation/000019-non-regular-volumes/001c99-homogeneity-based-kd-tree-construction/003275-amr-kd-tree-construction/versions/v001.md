# AMR KD-Tree Construction

Also called: kd-tree build, kd-tree builder, kd-tree structure for AMR, kd-tree traversal for AMR, median-split kd-tree

## Overview
A general method for representing and traversing block-structured (Berger-Colella) Adaptive Mesh Refinement (AMR) data using a kd-tree structure to enable efficient query, sampling, and direct rendering [S1, unofficial]. It solves the problem of efficiently locating cells in native AMR datasets without requiring data reformatting or voxel replication, which was necessary in previous multi-octree approaches [S1, unofficial]. It sets itself apart from homogeneous page tables by grouping same-level cells into patches and building a KD-tree based on level homogeneity, avoiding the memory waste and performance penalty associated with flat hierarchical structures [Parent].

## How it works
**Inputs and Outputs**
*   **Input:** A `vtkHierarchicalBoxDataSet` structure containing block-structured AMR data (bricks) across multiple levels [S1, unofficial].
*   **Output:** A kd-tree data structure where leaves cover spatial regions, enabling efficient cell location and dual-cell queries [S1, unofficial].

**Data Structures**
*   **kd-tree Nodes:** Internal nodes store a partitioning plane (axis-aligned) and pointers to left/right children.
*   **kd-tree Leaves:** Each leaf refers to a spatial region that contains exactly one brick per level it covers. A brick may be referenced by multiple leaves. Leaves typically cover many cells [S1, unofficial].
*   **Block Representation:** Blocks are defined by their spatial boundaries. The tree is built over unique block regions [S1, unofficial].

**Algorithm Steps**
1.  **Compute Global Bounds:** Calculate the world-space bounding box encompassing all bricks across all AMR levels [S1, unofficial].
2.  **Recursive Partitioning:** Define a function `BuildKDTree(current_region, blocks_in_region)`:
    a.  **Identify Boundaries:** Determine the list of all block boundaries that intersect `current_region`. Each boundary defines an axis-aligned plane [S1, unofficial].
    b.  **Select Partition Plane:** Pick one boundary plane as the partitioning plane. The current implementation uses the plane closest to the spatial median of the current region [S1, unofficial].
    c.  **Partition Blocks:** Sort the `blocks_in_region` into three categories:
        i.  Blocks overlapping the left half of the partition.
        ii. Blocks overlapping the right half of the partition.
        iii. Blocks overlapping both halves (common in Berger-Colella AMR due to nested refinement). These blocks are added to *both* the left and right lists [S1, unofficial].
    d.  **Recurse:**
        i.  If no boundary plane overlaps the current region (or the region is sufficiently small/atomic), create a leaf node containing the relevant bricks [S1, unofficial].
        ii. Otherwise, recursively call `BuildKDTree` on the left half with the left block list, and on the right half with the right block list [S1, unofficial].

**Pseudocode**
```python
def build_amr_kd_tree(blocks, current_bounds):
    """
    Recursively builds a kd-tree for AMR data.
    
    Args:
        blocks: List of block objects, each having a spatial bounding box.
        current_bounds: The spatial region (bounding box) currently being partitioned.
        
    Returns:
        A kd-tree node (internal or leaf).
    """
    # Base case: No more partitioning planes intersect the current region
    # In practice, this is checked by the absence of valid split planes in step 2a
    if not has_intersecting_boundaries(blocks, current_bounds):
        return LeafNode(blocks)

    # Step 2a: Determine all block boundaries intersecting current_bounds
    boundaries = get_intersecting_boundaries(blocks, current_bounds)
    
    # Step 2b: Pick the plane closest to the spatial median
    split_plane = select_median_closest_plane(boundaries, current_bounds)
    
    # Step 2c: Partition blocks
    left_blocks = []
    right_blocks = []
    
    for block in blocks:
        if block.overlaps_left_half(split_plane):
            left_blocks.append(block)
        if block.overlaps_right_half(split_plane):
            right_blocks.append(block)
            
    # Step 2d: Recurse
    left_child = build_amr_kd_tree(left_blocks, split_plane.left_region(current_bounds))
    right_child = build_amr_kd_tree(right_blocks, split_plane.right_region(current_bounds))
    
    return InternalNode(split_plane, left_child, right_child)

def has_intersecting_boundaries(blocks, bounds):
    """Check if any block boundary intersects the current bounds."""
    # Implementation detail: Iterate blocks, extract their min/max coordinates,
    # check if they fall strictly inside bounds.
    return any(is_boundary_inside(b.min, b.max, bounds) for b in blocks)

def get_intersecting_boundaries(blocks, bounds):
    """Return list of axis-aligned planes defined by block boundaries inside bounds."""
    planes = []
    for block in blocks:
        # Add min and max planes for x, y, z axes if they intersect bounds
        for axis in [0, 1, 2]:
            if block.min[axis] > bounds.min[axis] and block.min[axis] < bounds.max[axis]:
                planes.append(Plane(axis, block.min[axis]))
            if block.max[axis] > bounds.min[axis] and block.max[axis] < bounds.max[axis]:
                planes.append(Plane(axis, block.max[axis]))
    return planes

def select_median_closest_plane(planes, bounds):
    """Select the plane closest to the center of bounds."""
    center = bounds.center()
    best_plane = None
    min_dist = infinity
    
    for plane in planes:
        dist = abs(plane.position - center[plane.axis])
        if dist < min_dist:
            min_dist = dist
            best_plane = plane
            
    return best_plane
```

**Parameters**
*   **Split Strategy:** Median-closest boundary plane [S1, unofficial].
*   **Data Structure:** `vtkHierarchicalBoxDataSet` [S1, unofficial].

**Edge Cases and Pitfalls**
*   **Block Overlap:** In Berger-Colella AMR, blocks at different levels can overlap spatially. The algorithm explicitly handles blocks overlapping both partition halves by including them in both child lists [S1, unofficial].
*   **Precision:** Using floating-point coordinates for cell centers and widths minimizes register pressure and avoids int-to-float conversions during traversal [S1, unofficial].

## Subtopics

### Packetized Cell/Dual-Cell Query
An optimized query method implemented in ISPC that performs $N$ reconstructions and cell/dual-cell queries in parallel using a packet paradigm to traverse the KD-tree [S1, unofficial]. It is a special variant of the dual-cell query that performs all 8 corner queries in a single traversal by viewing the 8 vertex locations as the intersection of three sets of parallel planes [S1, unofficial]. It references cells by their (float) center point and levels by their (float) center width to utilize floating point units, minimize register pressure, avoid int-to-float conversions, and allow multiply-add capabilities [S1, unofficial]. It realizes recursion with a software-maintained stack. At each kd-tree node, it checks on which side of the node's partitioning plane the respective query planes lie. It tracks, with only 6 state variables, which of the planes are active in a given subtree. Once a leaf is reached, the 6 active planes define which of the 8 corner values are active, and those are filled from the brick stored in the leaf [S1, unofficial]. $N$ is the vector width of the underlying CPU architecture [S1, unofficial]. These optimized kernels are an order of magnitude faster than the scalar reference code [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Not explicitly given in the sources. However, the packetized query variant is reported to be an order of magnitude faster than scalar reference code [S1, unofficial].
*   **Memory Complexity:** The structure avoids replicating voxels, storing data in the original `vtkHierarchicalBoxDataSet` format [S1, unofficial]. However, any brick may be referenced by multiple leaves, potentially increasing pointer overhead compared to a strict partitioning scheme [S1, unofficial].
*   **Performance:** Demonstrated on a dual-Xeon workstation and a KNL node on Stampede 2 [S1, unofficial]. Performance varies with reconstruction filters and maximum AMR levels [S1, unofficial].
*   **Strengths:** Enables direct volume rendering of BC AMR data without reformatting or resampling. Efficient cell location via packetized traversal.
*   **Limitations:** Relies on CPU ray tracing (OSPRay). Performance depends on vector width $N$ [S1, unofficial].
*   **When to use:** Interactive CPU-based volume rendering of block-structured AMR data where direct access to native VTK data is required [S1, unofficial].
*   **When not to use:** When GPU-based rendering is preferred or when data can be pre-resampled into a structured volume [S1, unofficial].

## Background
Originated in work by Ingo Wald et al. for the OSPRay interactive CPU ray tracing framework [S1, unofficial]. It was developed to address the limitations of previous multi-octree structures that required data reformatting and copying [S1, unofficial]. The method was integrated into VTK 7.1 and ParaView 5.0, replacing the previous approach of loading AMR data into a `vtkAMR` structure and resampling it into a structured volume for rendering [S1, unofficial]. It supports Berger-Colella AMR layouts as used by ParaView’s and VitIt’s Chombo readers [S1, unofficial].
