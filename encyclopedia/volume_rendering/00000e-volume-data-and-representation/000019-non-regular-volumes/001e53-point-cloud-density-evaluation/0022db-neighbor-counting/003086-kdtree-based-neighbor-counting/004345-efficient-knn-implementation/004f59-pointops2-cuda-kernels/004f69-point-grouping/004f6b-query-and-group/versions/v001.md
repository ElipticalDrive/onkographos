# Query and Group
## Overview
Query and Group is a combined operation that finds $k$-nearest neighbors for a set of query points and groups their features and coordinates into fixed-size tensors for local feature aggregation [S1, unofficial]. It differs from its parent [Point Grouping](13932-point-grouping.md) by integrating the neighbor search step (`knnquery`) directly into the grouping logic, allowing for dynamic index computation when pre-computed indices are not provided [S1, unofficial].
## How it works
**Inputs:**
- `xyz`: Source point coordinates, shape $(n, 3)$.
- `new_xyz`: Query point coordinates, shape $(m, 3)$.
- `feat`: Source point features, shape $(n, c)$.
- `idx`: Pre-computed neighbor indices, shape $(m, nsample)$. If `None`, indices are computed dynamically.
- `use_xyz`: Boolean flag to include coordinates in the output. Default: `True`.
- `relative`: Boolean flag to compute relative coordinates (neighbor - query). Default: `True`.

**Outputs:**
- `grouped_feat`: Grouped features, shape $(m, nsample, c)$ or $(m, nsample, c+3)$ if `use_xyz` is `True`.

**Steps:**
1. **Index Computation:** If `idx` is `None`, compute it using `knnquery(new_xyz, xyz)` to find the $k$-nearest neighbors for each query point [S1, unofficial].
2. **Coordinate Gathering:** Gather source coordinates using the indices:
   $$ \text{grouped\_xyz} = \text{xyz}[\text{idx.view}(-1).long(), :].\text{view}(m, nsample, 3) $$
   [S1, unofficial]
3. **Relative Coordinate Calculation:** If `relative` is `True`, subtract the query point coordinates from the grouped coordinates:
   $$ \text{grouped\_xyz} \leftarrow \text{grouped\_xyz} - \text{new\_xyz.unsqueeze}(1) $$
   [S1, unofficial]
4. **Feature Gathering:** Gather source features using the indices:
   $$ \text{grouped\_feat} = \text{feat}[\text{idx.view}(-1).long(), :].\text{view}(m, nsample, c) $$
   [S1, unofficial]
5. **Concatenation:** If `use_xyz` is `True`, concatenate `grouped_xyz` and `grouped_feat` along the feature dimension:
   $$ \text{output} = \text{concat}(\text{grouped\_feat}, \text{grouped\_xyz}, \text{dim}=-1) $$
   [S1, unofficial]

**Pseudocode:**
```python
def query_and_group(xyz, new_xyz, feat, idx=None, use_xyz=True, relative=True):
    """
    Args:
        xyz: (n, 3) source coordinates
        new_xyz: (m, 3) query coordinates
        feat: (n, c) source features
        idx: (m, nsample) neighbor indices, or None
        use_xyz: bool, include coordinates in output
        relative: bool, compute relative coordinates
    Returns:
        grouped_feat: (m, nsample, c) or (m, nsample, c+3)
    """
    m = new_xyz.shape[0]
    n = xyz.shape[0]
    
    # Step 1: Compute indices if not provided
    if idx is None:
        idx = knnquery(new_xyz, xyz) # Shape: (m, nsample)
        
    # Step 2: Gather coordinates
    # Flatten idx for indexing, then reshape
    grouped_xyz = xyz[idx.view(-1).long(), :].view(m, -1, 3)
    
    # Step 3: Compute relative coordinates if requested
    if relative:
        # new_xyz.unsqueeze(1) broadcasts to (m, 1, 3)
        grouped_xyz = grouped_xyz - new_xyz.unsqueeze(1)
        
    # Step 4: Gather features
    grouped_feat = feat[idx.view(-1).long(), :].view(m, -1, feat.shape[1])
    
    # Step 5: Concatenate if use_xyz is True
    if use_xyz:
        # Concatenate along the last dimension (features)
        output = torch.cat([grouped_feat, grouped_xyz], dim=-1)
    else:
        output = grouped_feat
        
    return output
```

**Edge Cases and Pitfalls:**
- **Precision:** Indexing operations (`idx.view(-1).long()`) require careful handling of tensor layouts to avoid memory access errors [S1, unofficial].
- **Boundaries:** `knnquery` must handle cases where fewer than $k$ neighbors exist (e.g., at boundaries) by padding or returning valid indices only [S1, unofficial].
- **Degenerate Input:** If `xyz` or `feat` are empty, the operation should return empty tensors of the expected shape [G].

## Subtopics
## Operating characteristics
**Time Complexity:** $O(m \cdot k \log n)$ for the `knnquery` step if indices are not pre-computed, where $m$ is the number of query points, $k$ is the number of neighbors, and $n$ is the number of source points. The grouping step is $O(m \cdot k)$.
**Memory Complexity:** $O(m \cdot k \cdot (c + 3))$ for the output tensor.
**Performance:** Implemented via CUDA kernels for efficiency, leveraging GPU parallelism for neighbor search and feature gathering [S1, unofficial].
**Strengths:** Combines search and grouping in a single operation, reducing overhead. Supports relative coordinates and optional coordinate inclusion.
**Limitations:** Requires `knnquery` implementation if indices are not pre-computed. Performance depends on the efficiency of the underlying neighbor search algorithm.
**When to Use:** When dynamic neighbor search is needed or when integrating neighbor search and feature grouping into a single pipeline step.
**When Not to Use:** When pre-computed indices are available and memory bandwidth is a bottleneck, consider using [Point Grouping](13932-point-grouping.md) directly.

## Background
Originated in the context of 4D Gaussian Splatting research, specifically in the `4d-gaussian-splatting` repository by LogosIntelligenceLab [S1, unofficial]. It is part of the PointOps2 CUDA kernels suite, designed for efficient point cloud processing in neural rendering pipelines.
