# Distributed Ortholidar Processing via Spark

Also called: Distributed Dimensionality-Based Lidar Rendering, Distributed point cloud aggregation, Ortholidar rendering via Spark, Spark-based point cloud rendering

## Overview
Distributed Ortholidar Processing via Spark is a method for rendering massive Mobile Mapping System (MMS) lidar point clouds into 2D orthographic images by leveraging the Apache Spark framework for distributed in-memory processing [S1]. It solves the usability bottleneck of visualizing billions of points by aggregating dimensionality-based attributes into sparse tiles, enabling scalable, out-of-core visualization that conveys 3D scene structure (e.g., vertical vs. horizontal surfaces) without ground elevation estimation [S1]. Unlike standard map-reduce approaches that may require final shuffles for image assembly, this method groups pixels into tiles within the distributed memory to improve locality and prevent network bottlenecks during aggregation [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** Lidar files (PLY/LAS) stored in a distributed file system (e.g., HDFS), containing attributes: $x, y$ (position), $r$ (reflectance), $D1, D2$ (dimensionality), $z1, z3$ (eigenvector components) [S1].
*   **Output:** A tile pyramid of ortholidar images (PNG/JPEG) or a single on-demand canvas image [S1].

**Data Structures:**
1.  **Point Record:** Stores 7 attributes in single-precision float (4 bytes each), totaling 28 bytes per point [S1].
    *   Fields: `x`, `y`, `r`, `d1`, `d2`, `z1`, `z3` [S1].
2.  **Tile(w, h):** A sparse data structure representing a tile of width $w$ and height $h$. It stores accumulated floating-point values for non-empty pixels to reduce overhead compared to dense arrays [S1].
    *   Accumulated Vector $A \in \mathbb{R}^7$ per pixel: $A = (A_r, A_h, A_D)$, where $A_D \in \mathbb{R}^5$ [S1].
    *   $A_r = \sum_{p \in P_{xy}} d_h^2(p) r(p)$ [S1].
    *   $A_h = \sum_{p \in P_{xy}} d_h^2(p)$ [S1].
    *   $A_D = \sum_{p \in P_{xy}} D(p)$ [S1].
    *   Note: $D3$ is redundant ($D3 = 1 - D1 - D2$) and not stored [S1].

**Parameters:**
*   **Color Palette $C$:** A vector in $\mathbb{R}^5$ for dimensionality-based coloring [S1]. Default values: $c_{1h}=(0,1,1)$ (yellow), $c_{1v}=(0,0,1)$ (blue), $c_{2h}=(1,1,1)$ (white), $c_{2v}=(1,0,0)$ (red), $c_{2v}=(0,1,0)$ (green) [S1].
*   **Infinitesimal Term $\epsilon$:** Added to denominators to prevent division by zero [S1].
*   **Tone-mapping $f$:** Clamped linear mapping $f(r) = \min(1, \max(0, \frac{r - r_{min}}{r_{max} - r_{min}}))$ [S1].

**Steps:**
1.  **Load:** Load lidar files from HDFS into Spark Dataframes using custom header readers and Hadoop InputFormat [S1].
2.  **Select:** Extract relevant attributes: $x, y, r, D1, D2, |eigenVector1z|, |eigenVector3z|$ [S1].
3.  **Filter:** Filter points by tile extent $[x_0, x_1] \times [y_0, y_1]$ [S1].
4.  **Map:** Transform points to tile-local coordinates:
    $$ Point(w \cdot \frac{x-x_0}{x_1-x_0}, h \cdot \frac{y-y_0}{y_1-y_0}, r, z1, z3, d1, d2) $$
    [S1].
5.  **Aggregate:** Aggregate points into sparse tiles using `RDD[Tile]`.
    *   Use operator `_:+_` for local aggregation within a partition/file split [S1].
    *   Use operator `_++_` for global aggregation across partitions [S1].
6.  **Render:** Compute final pixel colors using Equation 5 and tone-mapping $f$ via `tile.setRGB(canvas, f, C)` [S1].

**Formulas:**
The color of an ortholidar pixel $c(x, y)$ is computed as [S1]:
$$ c(x, y) = f\left( \frac{A_r + A_h}{A_D \cdot C + \epsilon} \right) $$
Where $A_D \cdot C$ is the scalar product in $\mathbb{R}^5$ [S1].

**Pseudocode:**
```python
# 1. Load lidar files from HDFS
location = "HDFS://ip:port/path/*.ply"
df = sqlContext.plyFiles(location)

# 2. Select and rename relevant attributes
# Attributes: x, y, reflectance (r), D1, D2, |eigenVector1z| (z1), |eigenVector3z| (z3)
df = df.select(
    'x, 'y, 
    'reflectance.alias('r), 
    'D1, 'D2, 
    abs('eigenVector1z).alias('z1), 
    abs('eigenVector3z).alias('z3)
)

# 3. Filter points by tile extent [x0, x1] x [y0, y1]
df = df.where(('x >= x0) & ('x < x1))
df = df.where(('y >= y0) & ('y < y1))

# 4. Map points to tile-local coordinates
# Point(w*(x-x0)/(x1-x0), h*(y-y0)/(y1-y0), r, z1, z3, d1, d2)
df = df.map(lambda row: Point(
    w * (row.x - x0) / (x1 - x0),
    h * (row.y - y0) / (y1 - y0),
    row.r, row.z1, row.z3, row.d1, row.d2
))

# 5. Aggregate points into sparse tiles
# _:+_ is local aggregation (within partition), _++_ is global aggregation (across partitions)
tile = df.aggregate(Tile(w, h))(_:+_, _++_)

# 6. Compute final pixel colors and write to canvas
# Equation 5: c(x,y) = f((Ar + Ah) / (AD . C + epsilon))
tile.setRGB(canvas, f, C)
```

**Tile Pyramid Generation:**
1.  Start at the base level. Output tile ID as the key [S1].
2.  Aggregate base tiles independently [S1].
3.  Iteratively write tiles to disk, aggregating 4 child quarter-tiles into a parent tile [S1].
4.  Terminate when a single tile remains [S1].

**Edge Cases and Pitfalls:**
*   **White Background Artifacts:** Long-range lidar returns have low reflectance, appearing as sparse dark dots on a white background, which is disturbing to users [S1].
*   **Aliasing and Compressibility:** The method uses nearest-neighbor filtering, causing aliasing artifacts and high-frequency content when lidar sampling density is lower than ortholidar resolution, making the output poorly compressible [S1].
*   **Division by Zero:** An infinitesimal term $\epsilon$ is added to denominators to prevent division by zero [S1].

## Operating characteristics
*   **Time Complexity:** Sublinear with respect to total points, as tiles without points are not considered [S1].
*   **Memory Complexity:** Constant memory per pixel accumulation; sparse encoding reduces overhead for scattered long-range points [S1].
*   **Measured Performance:** On an 81.439 GB MMS dataset (1.017 billion points) on an 8-slave Spark cluster (6GB memory per driver/executor):
    *   Tile pyramid computation: 41 min at 1cm resolution, 17 min at 2cm resolution [S1].
    *   Preprocessing (dimensionality analysis): 2 hours on 8 nodes [S1].
    *   On-demand query: 30s to 5 minutes depending on extent, after caching and partition pruning [S1].
*   **Strengths:** Scales to arbitrary large datasets; robust to non-flat areas; no hard-to-tune parameters; sparse encoding handles scattered points efficiently [S1].
*   **Limitations:** Nearest-neighbor filtering causes aliasing; poor compressibility at low sampling densities; latency during preprocessing [S1].
*   **When to Use:** Large-scale MMS lidar visualization where 3D structure context is needed; web-based mapping interfaces [S1].
*   **When Not to Use:** When high-frequency smoothness is required without additional smoothing steps; when interactive response times <30s are critical without caching [S1].

## Background
*   **Origin:** Proposed by Mathieu Bredif, Bruno Vallet, and Benjamin Ferrand from Université Paris-Est, IGN/SR, MATIS [S1].
*   **Paper:** "Distributed dimensionality-based rendering of lidar point clouds," ISPRS Annals of the Photogrammetry, Remote Sensing and Spatial Information Sciences, 2015 [S1].
*   **History:** Developed to address the usability bottleneck of visualizing huge MMS lidar datasets for non-expert users in applications like urban planning and 3D reconstruction [S1].
*   **Usage:** Deployed in the IQmulus European project cloud infrastructure, served via standard JavaScript webmapping HTML pages (e.g., Leaflet) [S1].
