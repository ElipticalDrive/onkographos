# Cell Count Algorithm for Adaptive-Resolution Load Balancing

Also called: Adaptive-resolution data decomposition, Shuttle algorithm for block assignment, Spatial Division of Adaptive-Resolution Data

## Overview
The Cell Count Algorithm is a load-balancing strategy for distributed volume rendering that assigns spatial data blocks to processors based on their computational cost (cell count) rather than their spatial extent or block count [S1, unofficial]. It solves the inefficiency of uniform spatial decomposition in adaptive-resolution datasets, where processors handling low-resolution regions finish early and remain idle while others process high-resolution regions [S1, unofficial]. It sets itself apart from siblings like [Scalable Distributed Volume Rendering (SDVR)](863-scalable-distributed-volume-rendering-sdvr.md) and [MPI Volume Rendering (1D/2D Decomposition)](2249-mpi-volume-rendering-1d-2d-decomposition.md) by explicitly decoupling the number of assigned blocks from the workload, ensuring that each processor renders approximately the same total number of voxels [S1, unofficial].

## How it works
**Inputs:**
*   A set of $n$ data blocks $B = \{B_1, B_2, \dots, B_n\}$.
*   For each block $B_i$, the cell count $C_i$ (number of voxels/cells), representing its resolution and computational cost [S1, unofficial].
*   The number of available processors $P$ [S1, unofficial].

**Outputs:**
*   An assignment map mapping each processor $p_j$ to a subset of blocks such that the sum of cell counts for each processor is approximately equal [S1, unofficial].

**Data Structures:**
*   **Block List:** A list of objects containing at least the field `cell_count` (integer).
*   **Processor List:** A list of processor identifiers or objects, initially containing all $P$ processors.
*   **Sorted Blocks:** The Block List sorted in descending order of `cell_count`.

**Parameters:**
*   $P$: Number of processors.
*   $n$: Number of blocks.
*   Note: If $P > n$, the algorithm may assign one block per processor and ignore the rest, or subdivide blocks (implementation detail not specified in source) [S1, unofficial].

**Steps:**
1.  **Calculate Total Cells:** Compute the total number of cells in the dataset:
    $$ C_{total} = \sum_{i=1}^{n} C_i $$
2.  **Calculate Optimal Load:** Determine the target number of cells per processor:
    $$ C_{opt} = \lceil C_{total} / P \rceil $$
    Where $\lceil \cdot \rceil$ denotes rounding up to the nearest integer [S1, unofficial].
3.  **Sort Blocks:** Sort the blocks in descending order of their cell count $C_i$ [S1, unofficial].
4.  **Initialize:** Create an active list of processors containing all $P$ processors. Initialize a pointer to the start of the sorted blocks list [S1, unofficial].
5.  **Assign Blocks (Shuttle):** While there are unassigned blocks:
    a. Select the next available processor from the active list (cycling through processors) [S1, unofficial].
    b. Select the next block from the sorted blocks list [S1, unofficial].
    c. Assign the block to the processor.
    d. Update the processor's accumulated cell count.
    e. If the processor's accumulated cell count $\ge C_{opt}$, mark the processor as full and remove it from the active list [S1, unofficial].
6.  **Termination:** The algorithm ends when all blocks are assigned [S1, unofficial].

**Pseudocode:**

def cell_count_algorithm(blocks, num_processors):

    """

    total_cells = sum(b['cell_count'] for b in blocks)

            # we break or handle error. For strict adherence to source loop:
            break

        # and "remove it from the active list" when full.

        # But the source pseudocode uses `processor_list.get_next()` and `mark_processor_full`.
        # It implies a queue or list where full items are removed.
        
        # Re-reading source pseudocode:

        # Let's assume a simple round-robin over the active list indices.
        # To keep it simple and self-contained:
        if not active_processors:
            break
            
        # Get the first active processor (Round Robin style on active set)
        # If we want to cycle, we might need an index. 
        # Source: "Get the next available processor from the list (cycling through processors)"
        # If we remove from the list, "cycling" is ambiguous. 
        # However, standard shuttle algorithms often just pick the next in a queue.
        # Let's assume `processor_list` is a queue.
        
        proc_idx = active_processors.pop(0) # Get next active processor
        proc = processors[proc_idx]
        
        # Get next block
        block = sorted_blocks[block_idx]
        block_idx += 1
        
        # Assign
        proc['assigned_blocks'].append(block['id'])
        proc['current_load'] += block['cell_count']

        if proc['current_load'] >= optimal_cells:

    return assignment

**Edge Cases and Pitfalls:**
*   **Precision:** Cell counts are integers. The optimal load is an integer ceiling. Small discrepancies in total load distribution are inevitable if block sizes do not divide evenly [S1, unofficial].
*   **Boundaries:** If the number of processors $P$ is greater than the number of blocks $n$, the source suggests ignoring extra processors or subdividing blocks [S1, unofficial].
*   **Degenerate Input:** If a single block has a cell count greater than $C_{opt}$, that processor will exceed the optimal load significantly. The algorithm does not specify splitting such blocks, so the load balance will be suboptimal for that specific processor [S1, unofficial].

## Subtopics

### Uniform Resolution Decomposition
Assigns equal spatial portions or equal numbers of blocks regardless of resolution. Inefficient for adaptive data as low-resolution processors finish early [S1, unofficial].

### Shuttle Algorithm
The specific assignment mechanism used within the Cell Count Algorithm, cycling through processors and assigning sorted blocks until capacity is reached [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Sorting blocks takes $O(n \log n)$. The assignment loop is $O(n)$ as each block is visited once. Total: $O(n \log n)$ [S1, unofficial].
*   **Memory Complexity:** $O(n)$ to store block metadata and assignments [S1, unofficial].
*   **Performance:** Balances computational load by ensuring each processor renders approximately the same number of cells. Prevents idle time caused by low-resolution blocks finishing early [S1, unofficial].
*   **Strengths:** Simple to implement; effective for datasets with known block resolutions; reduces idle time in adaptive-resolution scenarios [S1, unofficial].
*   **Limitations:** Requires pre-calculation of cell counts; assumes cell count is a perfect proxy for rendering time (ignores transfer function complexity, etc.); does not handle dynamic load changes during rendering [S1, unofficial].
*   **When to use:** Adaptive-resolution volume datasets where block resolutions vary significantly and static load balancing is required [S1, unofficial].
*   **When not to use:** Uniform resolution data (where simple spatial decomposition suffices) or dynamic datasets where block costs change unpredictably [S1, unofficial].
