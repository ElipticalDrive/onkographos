# Cell Count Algorithm for Adaptive-Resolution Load Balancing

Also called: Adaptive-resolution data decomposition, Shuttle algorithm for block assignment, Spatial Division of Adaptive-Resolution Data

## Overview
The Cell Count Algorithm is a load-balancing strategy for distributed volume rendering of adaptive-resolution datasets, where data is partitioned into blocks of varying resolutions [S1, unofficial]. It solves the problem of processor idle time caused by uneven computational costs: in adaptive data, high-resolution blocks require significantly more rendering time than low-resolution ones, so assigning equal spatial extents or equal block counts leads to severe load imbalance [S1, unofficial]. Unlike uniform decomposition or simple round-robin distribution, this method balances the total number of cells (voxels) assigned to each processor, ensuring that all processors complete their work at approximately the same time [S1, unofficial].

## How it works
**Inputs:**
- A set of $n$ data blocks $B = \{B_1, B_2, \dots, B_n\}$.
- For each block $B_x$, the cell count $C_x$ (number of voxels/cells in the block).
- The number of available processors $P$.

**Outputs:**
- An assignment mapping each block $B_x$ to a processor $p_i$.
- Each processor $p_i$ receives a subset of blocks such that the sum of cell counts is balanced across all processors.

**Data Structures:**
- `blocks`: A list of objects, each containing `id` (block identifier) and `cell_count` (integer).
- `processors`: A list of $P$ processor objects, each containing `id`, `assigned_cells` (integer, initialized to 0), and `is_full` (boolean, initialized to false).
- `sorted_blocks`: A list of blocks sorted in descending order of `cell_count`.

**Parameters:**
- $P$: Number of processors.
- $n$: Number of data blocks.

**Algorithm Steps:**
1.  **Calculate Total Cells:** Compute the total number of cells in the dataset:
    $$ C_{total} = \sum_{x=1}^{n} C_x $$
2.  **Calculate Optimal Load:** Determine the target number of cells per processor:
    $$ C_{optimal} = \lceil C_{total} / P \rceil $$
    [G] Rounding up ensures that if $C_{total}$ is not divisible by $P$, the last processor may exceed the average slightly, but no processor is assigned less than the floor value unnecessarily.
3.  **Sort Blocks:** Sort the list of blocks in descending order based on `cell_count`. This greedy approach handles large blocks first, which is critical for balancing because large blocks are harder to fit into remaining space.
4.  **Initialize Processors:** Create a list of $P$ processors. Initialize `assigned_cells` to 0 for all. Maintain a pointer or index to the next available processor in a round-robin fashion.
5.  **Assign Blocks:** Iterate through the sorted blocks. For each block:
    a. Select the next available processor from the list (cycling through $0$ to $P-1$).
    b. Assign the current block to this processor.
    c. Update the processor's `assigned_cells` by adding the block's `cell_count`.
    d. Check if the processor's `assigned_cells` $\ge C_{optimal}$. If true, mark the processor as `is_full = true` and remove it from the active assignment list.
    e. Repeat until all blocks are assigned.

**Pseudocode:**

```python
def cell_count_algorithm(blocks, num_processors):
    """
    blocks: List of dicts with keys 'id' and 'cell_count'
    num_processors: Integer P
    Returns: List of lists, where result[i] contains block IDs assigned to processor i
    """
    # Step 1 & 2: Calculate total and optimal cells
    total_cells = sum(b['cell_count'] for b in blocks)
    optimal_cells = (total_cells + num_processors - 1) // num_processors # Ceiling division
    
    # Step 3: Sort blocks descending by cell count
    sorted_blocks = sorted(blocks, key=lambda b: b['cell_count'], reverse=True)
    
    # Step 4: Initialize processors
    processors = []
    for i in range(num_processors):
        processors.append({
            'id': i,
            'assigned_cells': 0,
            'is_full': False,
            'assigned_blocks': []
        })
    
    active_processor_index = 0
    
    # Step 5: Assign blocks
    for block in sorted_blocks:
        # Find next active processor
        while processors[active_processor_index]['is_full']:
            active_processor_index = (active_processor_index + 1) % num_processors
            
        current_proc = processors[active_processor_index]
        
        # Assign block
        current_proc['assigned_blocks'].append(block['id'])
        current_proc['assigned_cells'] += block['cell_count']
        
        # Check if processor is full
        if current_proc['assigned_cells'] >= optimal_cells:
            current_proc['is_full'] = True
            
        # Move to next processor for next block
        active_processor_index = (active_processor_index + 1) % num_processors
        
    return [p['assigned_blocks'] for p in processors]
```

**Edge Cases and Pitfalls:**
- **Uneven Division:** If $C_{total}$ is not divisible by $P$, some processors will have more cells than others. The algorithm minimizes the maximum load but does not guarantee perfect equality.
- **Large Blocks:** If a single block's cell count exceeds $C_{optimal}$, that processor will exceed the optimal load. The source notes that if the number of processors is less than the number of blocks, this algorithm is used; however, if a block is larger than the average, it cannot be split without breaking the "consistent resolution" constraint mentioned in the source [S1, unofficial].
- **Processor Count vs Block Count:** If $P > n$, some processors will receive no blocks. The algorithm handles this naturally as the loop terminates when blocks are exhausted. If $P < n$, blocks are distributed among fewer processors.
- **Consistent Resolution:** The source emphasizes that each processor should ideally have blocks of consistent resolution or a mix that balances the total cells. The algorithm does not enforce resolution consistency within a processor, only cell count balance [S1, unofficial].

## Operating characteristics
- **Time Complexity:** Sorting blocks takes $O(n \log n)$. The assignment loop takes $O(n)$ assuming constant-time processor selection. Total time is $O(n \log n)$.
- **Memory Complexity:** $O(n)$ to store the block list and processor states.
- **Performance:** This method significantly reduces idle time compared to uniform spatial decomposition or equal block count assignment. In the example from the source with 4 processors and blocks of sizes 16, 16, 4, 4, 4, 4, 1, 1, the algorithm assigns loads of 16, 16, 9, and 9 cells, whereas equal block assignment might assign 17, 20, etc., leading to imbalance [S1, unofficial].
- **Strengths:** Simple to implement; effective for adaptive-resolution data where resolution correlates with computational cost; balances load based on actual work units (cells).
- **Limitations:** Does not account for other factors like transfer function evaluation cost or opacity variations; assumes cell count is a perfect proxy for rendering time; may result in suboptimal cache locality if blocks are spatially disjoint.

## Background
The algorithm was described in the context of volume visualization of time-varying data using parallel, multiresolution, and adaptive-resolution techniques [S1, unofficial]. It addresses the inefficiency of dividing adaptive-resolution data equally by spatial extent, which causes processors handling low-resolution portions to finish early and sit idle [S1, unofficial]. The method is also referred to as the "shuttle algorithm" for block assignment in some contexts [S1, unofficial].
