# Dynamic load balancing using kd-trees

Also called: kd-tree based load balancing, hierarchical load balancing

## Overview
This method uses a hierarchical kd-tree to partition volume data and track workload statistics, enabling dynamic redistribution of rendering tasks among processors [S1, unofficial]. It sets itself apart from static decomposition methods by storing load statistics in inner nodes to guide traversal and rebalancing, and from queue-based approaches by maintaining explicit spatial hierarchy for tasks like empty-space skipping and compositing order determination [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Volume dataset (often represented as uniform texture bricks), number of processors $P$, current load statistics (estimated cost or occlusion information) [S1, unofficial].
*   **Output:** Assignment of work partitions to processors, maintaining correct compositing order [S1, unofficial].

**Data Structures:**
*   **kd-tree:** A binary tree encoding the decomposition of the data space [S1, unofficial].
    *   **Inner Nodes:** Store aggregated load statistics (e.g., estimated cost or occlusion information) chosen for the balancing strategy [S1, unofficial].
    *   **Leaf Nodes:** Contain effective partitions of work (subsets of bricks) [S1, unofficial].
    *   **Splitting:** At each level, data is split alternating along orthogonal axes [S1, unofficial].

**Steps:**
1.  **Tree Construction:** Build a kd-tree over the volume data space by splitting data alternating along orthogonal axes at each level [S1, unofficial].
2.  **Statistics Aggregation:** Populate inner nodes with the chosen load statistics (estimated rendering cost or occlusion information) [S1, unofficial].
3.  **Traversal for Balancing:** Traverse the kd-tree in specific orders to balance partitions according to the chosen strategy [S1, unofficial].
4.  **Work Assignment:** Assign leaf node partitions to processors based on the traversal and load statistics [S1, unofficial].
5.  **Compositing Order Determination:** Use the kd-tree structure to determine the front-to-back compositing order of partial rays [S1, unofficial].
6.  **Boundary Handling:** Replicate boundary data between partitions to ensure correct compositing when using the kd-tree for order determination [S1, unofficial].

**Formulas:**
*   The goal is to minimize the maximum workload across processors, as defined in the parent principles [Parent](5624-distributed-computing-and-load-balancing.md).

**Parameters:**
*   **Splitting Axis:** Alternating orthogonal axes (x, y, z) [S1, unofficial].
*   **Load Statistic:** Estimated cost or occlusion information [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Boundary Replication:** Replication of boundary data is necessary when using kd-trees for compositing order determination [S1, unofficial].
*   **Precision:** Not given in the sources.
*   **Degenerate Input:** Not given in the sources.

**Pseudocode:**
```python
def build_kd_tree(bricks, depth=0):
    """Build kd-tree. bricks: list of dicts with 'center' (list) and 'cost' (float)."""
    if not bricks:
        return None
    axis = depth % 3
    sorted_bricks = sorted(bricks, key=lambda b: b['center'][axis])
    mid = len(sorted_bricks) // 2
    left_bricks = sorted_bricks[:mid]
    right_bricks = sorted_bricks[mid:]
    node = {'axis': axis, 'split_val': sorted_bricks[mid-1]['center'][axis], 'left': None, 'right': None, 'load': 0, 'is_leaf': False}
    if len(left_bricks) == 0 or len(right_bricks) == 0:
        node['is_leaf'] = True
        node['bricks'] = bricks
        node['load'] = sum(b['cost'] for b in bricks)
        return node
    node['left'] = build_kd_tree(left_bricks, depth + 1)
    node['right'] = build_kd_tree(right_bricks, depth + 1)
    node['load'] = node['left']['load'] + node['right']['load']
    return node

def traverse_for_balance(node, assignments, proc_loads, num_procs, current_proc):
    """Assign leaf partitions to processors by traversing the tree."""
    if node['is_leaf']:
        best = min(range(num_procs), key=lambda p: proc_loads[p])
        assignments[best].extend(node['bricks'])
        proc_loads[best] += node['load']
        return
    # Specific traversal orders depend on the balancing strategy [S1, unofficial]
    traverse_for_balance(node['left'], assignments, proc_loads, num_procs, current_proc)
    traverse_for_balance(node['right'], assignments, proc_loads, num_procs, (current_proc + 1) % num_procs)

def get_compositing_order(node, view_dir):
    """Determine front-to-back compositing order using kd-tree structure."""
    order = []
    def visit(n):
        if n['is_leaf']:
            order.append(n['bricks'])
            return
        # Determine traversal order based on view direction relative to split axis [G]
        split_normal = [0.0, 0.0, 0.0]
        split_normal[n['axis']] = 1.0
        dot = sum(v * s for v, s in zip(view_dir, split_normal))
        if dot >= 0:
            visit(n['right'])
            visit(n['left'])
        else:
            visit(n['left'])
            visit(n['right'])
    visit(node)
    return order
```

## Subtopics

### [Incremental Load Balancing with Brick Caching](9862-incremental-load-balancing-with-brick-caching.md)
A dynamic load balancing technique for distributed volume rendering that incrementally moves bricks between cluster nodes to correct imbalance, using a caching mechanism to reduce transfer costs when reversing moves. It sets itself apart from full-tree balancing methods by processing only one node per frame to respect limited computation time, and from naive incremental methods by employing a brick cache to mitigate oscillation and stagnation caused by high network transfer costs.

### [Domain Block Decomposition](10898-domain-block-decomposition.md)
Domain Block Decomposition is a view-independent parallel volume rendering strategy that distributes a homogenizing kd-tree into roughly equal-cost subtrees, assigning each subtree to a distinct rendering node. It differs from Cost-range Decomposition by allowing the final image to be generated by any node (specifically the one assigned the "farthest" subtree) rather than always the master node, which may necessitate an additional communication step to send the final image to the master.
