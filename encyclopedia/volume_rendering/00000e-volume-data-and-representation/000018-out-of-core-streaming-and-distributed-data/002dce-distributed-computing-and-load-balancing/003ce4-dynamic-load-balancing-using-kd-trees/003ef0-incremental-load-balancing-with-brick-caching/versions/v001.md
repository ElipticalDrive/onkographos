# Incremental Load Balancing with Brick Caching


## Overview
A dynamic load balancing technique for distributed volume rendering that incrementally moves bricks between cluster nodes to correct imbalance, using a caching mechanism to reduce transfer costs when reversing moves [S1]. It sets itself apart from full-tree balancing methods by processing only one node per frame to respect limited computation time, and from naive incremental methods by employing a brick cache to mitigate oscillation and stagnation caused by high network transfer costs [S1].

## How it works
**Inputs:**
*   A distributed volume rendering scene represented by a kd-tree of bricks.
*   Current load metrics $t_l$ and $t_r$ for the left and right subtrees of a node.
*   System-measured average brick transfer time $c$ [S1].
*   User-defined parameters $f_o$ (penalty for opposite direction), $f_s$ (reward for same direction), and initial $f_l, f_r$ [S1].

**Outputs:**
*   Modified load distribution across nodes via brick transfers.
*   Updated kd-tree node factors $f_l, f_r$.

**Data Structures:**
*   **kd-tree Node:**
    *   `left_subtree_load`: Load metric for the left child.
    *   `right_subtree_load`: Load metric for the right child.
    *   `f_l`: Factor modeling cost of moving bricks from right to left (opposite to previous left-to-right moves).
    *   `f_r`: Factor modeling cost of moving bricks from left to right (opposite to previous right-to-left moves).
    *   `subdivision_plane`: The axis/plane along which bricks are split.
*   **Brick Cache:**
    *   A local main memory buffer on each node storing copies of bricks recently sent to neighbors.
    *   Uses a Least Recently Used (LRU) replacement strategy [S1].
    *   Tracks ownership/validity of cached bricks to negotiate transfers [S1].

**Parameters:**
*   $c$: Average time to move a brick from one node to another. Measured by the system while running [S1].
*   $f_o$: User-defined amount by which $f_r$ is increased when moving bricks from left to right, to penalize moving them back [S1].
*   $f_s$: User-defined amount by which $f_l$ is decreased when moving bricks in the same direction [S1].
*   Initial $f_l, f_r$: Depend on dataset and hardware [S1].

**Steps:**
1.  **Evaluate Root Condition:** Calculate the weighting factor $f$ for the root node of the kd-tree:
    $$
    f = \begin{cases} 
    f_l & \text{if } t_l > t_r \\
    f_r & \text{otherwise}
    \end{cases}
    $$
    where $t_l$ and $t_r$ are the loads of the left and right subtrees, respectively [S1].

2.  **Check Imbalance:** Evaluate inequality (4) for the current node:
    $$
    s \bar{t} + s f c < |t_l - t_r|
    $$
    where $s$ is a sign/direction indicator (implied by context of moving a slice), $\bar{t}$ is the average load per brick (implied by context of "slice of bricks"), and $c$ is the average transfer time [S1]. Note: The source text presents the formula as $s\bar{t} + sfc < |t_l - t_r|$. The term $s\bar{t}$ likely represents the benefit of balancing (reduction in load variance), while $sfc$ represents the cost. If the benefit exceeds the cost, a move is justified [S1].

3.  **Execute Move (if condition holds):**
    *   Transfer one slice of bricks along the subdivision plane represented by the current node [S1].
    *   **Update Factors:**
        *   If moving bricks from left to right:
            *   Increase $f_r$ by $f_o$: $f_r \leftarrow f_r + f_o$ [S1].
            *   Decrease $f_l$ by $f_s$: $f_l \leftarrow f_l - f_s$ [S1].
        *   If moving bricks from right to left:
            *   Increase $f_l$ by $f_o$: $f_l \leftarrow f_l + f_o$ [S1].
            *   Decrease $f_r$ by $f_s$: $f_r \leftarrow f_r - f_s$ [S1].
    *   **Cache Management:**
        *   The sending node keeps a copy of the moved brick in its local main memory [S1].
        *   The receiving node adds the brick to its local cache if space permits (LRU policy) [S1].
        *   Nodes send small negotiation messages to determine which bricks are sent and which are cached [S1].
    *   **Suspend:** Finish load balancing for the current frame. Restart at the root node after the next image is rendered [S1].

4.  **Traverse Tree (if condition does not hold at root):**
    *   Test other nodes in a preorder traversal [S1].
    *   If the condition holds for a non-root node, execute the move (Step 3) for that node.
    *   After the first slice of bricks has been moved, suspend load balancing until the next frame [S1].

5.  **Reverse Move (Caching):**
    *   If the system decides to move a brick back to its initial node:
        *   Check if the brick is present in the local cache of the current node [S1].
        *   If cached, reactivate the local copy instead of transferring over the network [S1].
        *   This reduces the effective transfer cost $c$ for reverse moves, mitigating oscillation [S1].

## Subtopics

### Dynamic Load Balancing using kd-trees
The parent method that provides the hierarchical structure for identifying load imbalances and subdivision planes. Incremental Load Balancing with Brick Caching builds on this by adding the incremental execution and caching layers [S1].

### Full-Tree Balancing
A contrasting approach that attempts to balance the entire kd-tree in one go. Incremental processing is chosen when full-tree balancing would exceed the available computation time per frame [S1].

## Operating characteristics
*   **Time Complexity:** O(1) per frame for the load balancing step, as it processes at most one node (or a few in preorder until a move is found) [S1]. This addresses the limited computation time available per frame [S1].
*   **Memory Complexity:** O(B) where B is the number of bricks, due to the brick cache storing copies of moved bricks [S1]. The cache uses LRU replacement [S1].
*   **Measured Performance:** Tested on a cluster of eight dual 2.1 GHz Opteron PCs with 4 GB RAM, GeForce 6800 Ultra GPUs, and Infiniband network [S1]. The caching mechanism allows for more aggressive load balancing, achieving better balance between nodes compared to non-cached incremental methods [S1].
*   **Strengths:**
    *   Respects strict per-frame time limits by processing only one node [S1].
    *   Reduces network overhead for reverse moves via caching [S1].
    *   Mitigates oscillation through factors $f_l$ and $f_r$ [S1].
*   **Limitations:**
    *   **Oscillation:** The system may still alternately move bricks along one subdivision plane, though caching mitigates this [S1].
    *   **Stagnation:** If $f_l$ and $f_r$ are too high, the system may get stuck in a suboptimal configuration because transfer costs appear too high [S1].
    *   **Parameter Sensitivity:** Choosing $f_o$, $f_s$, and initial $f_l, f_r$ is difficult and depends on the dataset, number of bricks, and hardware [S1].
*   **When to use:** When distributed volume rendering requires dynamic load balancing but has strict per-frame time constraints for the balancing algorithm itself [S1].
*   **When not to use:** When the hardware or dataset makes parameter tuning for $f_o, f_s$ infeasible, or when network latency is so high that even cached moves are prohibitive (though caching helps) [S1].

## Background
*   **Origin:** The method was introduced in the paper "Optimized volume raycasting for graphics-hardware-based cluster systems" [S1].
*   **History:** It was developed to address the performance decrease caused by frequent brick transfers in distributed volume rendering on cluster systems [S1]. The authors observed that moving bricks is time-consuming and that naive load balancing could lead to oscillation [S1].
*   **Usage:** Used in distributed volume rendering systems, specifically those using graphics-hardware-based cluster systems with Infiniband networks [S1].
