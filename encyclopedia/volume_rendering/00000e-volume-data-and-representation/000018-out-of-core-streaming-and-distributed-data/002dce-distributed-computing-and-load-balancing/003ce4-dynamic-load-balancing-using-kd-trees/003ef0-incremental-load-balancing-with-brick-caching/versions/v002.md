# Incremental Load Balancing with Brick Caching


## Overview
A dynamic load balancing technique for distributed volume rendering that incrementally moves bricks between cluster nodes to correct imbalance, using a caching mechanism to reduce transfer costs when reversing moves [S1]. It sets itself apart from full-tree balancing methods by processing only one node per frame to respect limited computation time, and from naive incremental methods by employing a brick cache to mitigate oscillation and stagnation caused by high network transfer costs [S1].

## How it works
**Inputs:**
*   A distributed volume rendering scene represented by a kd-tree of bricks [S1].
*   Current load metrics $t_l$ and $t_r$ for the left and right subtrees of a node [S1].
*   System-measured average brick transfer time $c$ [S1].
*   User-defined parameters $f_o$ (penalty for opposite direction), $f_s$ (reward for same direction), and initial $f_l, f_r$ [S1].

**Outputs:**
*   Modified load distribution across nodes via brick transfers [S1].
*   Updated kd-tree node factors $f_l, f_r$ [S1].

**Data Structures:**
*   **kd-tree Node:** `left_subtree_load`, `right_subtree_load`, `f_l`, `f_r`, `subdivision_plane` [S1].
*   **Brick Cache:** A local main memory buffer on each node storing copies of bricks recently sent to neighbors [S1]. Uses a Least Recently Used (LRU) replacement strategy [S1]. Tracks ownership/validity of cached bricks to negotiate transfers [S1].

**Parameters:**
*   $c$: Average time to move a brick from one node to another. Measured by the system while running [S1].
*   $f_o$: User-defined amount by which $f_r$ is increased when moving bricks from left to right, to penalize moving them back [S1].
*   $f_s$: User-defined amount by which $f_l$ is decreased when moving bricks in the same direction [S1].
*   Initial $f_l, f_r$: Depend on dataset and hardware [S1].

**Steps:**
1.  Evaluate inequality (4) for the root node of the kd-tree [S1].
2.  If the condition holds, transfer one slice of bricks along the subdivision plane represented by the root node [S1].
3.  Suspend load balancing for the current frame and restart at the root node after the next image is rendered [S1].
4.  If the condition does not hold at the root, test other nodes in a preorder traversal [S1].
5.  After the first slice of bricks has been moved, suspend load balancing until the next frame [S1].
6.  When moving a brick to a neighboring node, keep a copy of this brick in local main memory [S1].
7.  Use a least recently used (LRU) replacement strategy for the brick cache [S1].
8.  If moving a cached brick back to the initial node, reactivate the local copy instead of transferring over the network [S1].
9.  Send small negotiation messages between nodes to determine which bricks are sent and which are cached [S1].

**Formulas:**
*   Weighting factor: $f = f_l$ if $t_l > t_r$, else $f = f_r$ [S1].
*   Move condition: $s\bar{t} + sfc < |t_l - t_r|$ [S1]. Here, $s$ is the number of bricks in a slice and $\bar{t}$ is the average load per brick [S1].
*   Factor update (left to right): $f_r \leftarrow f_r + f_o$, $f_l \leftarrow f_l - f_s$ [S1].
*   Factor update (right to left): $f_l \leftarrow f_l + f_o$, $f_r \leftarrow f_r - f_s$ [S1].

    if hasattr(node, 'right'):

**Pitfalls:**
*   **Oscillation:** The system may alternately move bricks along one subdivision plane [S1].
*   **Stagnation:** If $f_l$ and $f_r$ are too high, the system may get stuck in a configuration worse than the initial partitioning because transfer costs seem too high [S1].
*   **Parameter Sensitivity:** Choosing $f_o$, $f_s$, and initial $f_l, f_r$ is difficult and depends on the dataset, number of bricks, and hardware [S1].

## Subtopics

### Dynamic Load Balancing using kd-trees
The parent method that provides the hierarchical structure for identifying load imbalances and subdivision planes. Sets apart by enabling incremental node evaluation rather than full-tree processing. Choose when computation time per frame is strictly limited. [Dynamic load balancing using kd-trees](9365-dynamic-load-balancing-using-kd-trees.md)

### Domain Block Decomposition
A sibling method for distributed volume rendering partitioning. Sets apart by using static domain decomposition instead of kd-tree incremental balancing with caching. Choose when static partitioning suffices or when brick caching overhead is undesirable. [Domain Block Decomposition](10898-domain-block-decomposition.md)

## Operating characteristics
*   **Time Complexity:** O(1) per frame for the load balancing step, as it processes at most one node per frame [S1]. This addresses the limited computation time available per frame [S1].
*   **Memory Complexity:** O(B) where B is the number of bricks, due to the brick cache storing copies of moved bricks [S1]. The cache uses LRU replacement [S1].
*   **Measured Performance:** Tested on a cluster of eight dual 2.1 GHz Opteron PCs with 4 GB RAM, GeForce 6800 Ultra GPUs, and Infiniband network [S1]. The caching mechanism allows for more aggressive load balancing, achieving better balance between nodes compared to non-cached incremental methods [S1].
*   **Strengths:** Respects strict per-frame time limits by processing only one node [S1]. Reduces network overhead for reverse moves via caching [S1]. Mitigates oscillation through factors $f_l$ and $f_r$ [S1].
*   **Limitations:** Oscillation may still occur along one subdivision plane [S1]. Stagnation if $f_l$ and $f_r$ are too high [S1]. Parameter sensitivity for $f_o$, $f_s$, and initial $f_l, f_r$ [S1].
*   **When to use:** When distributed volume rendering requires dynamic load balancing but has strict per-frame time constraints for the balancing algorithm itself [S1].
*   **When not to use:** When hardware or dataset makes parameter tuning for $f_o, f_s$ infeasible, or when network latency is so high that even cached moves are prohibitive [S1].

## Background
*   **Origin:** The method was introduced in the paper "Optimized volume raycasting for graphics-hardware-based cluster systems" [S1].
*   **History:** It was developed to address the performance decrease caused by frequent brick transfers in distributed volume rendering on cluster systems [S1]. The authors observed that moving bricks is time-consuming and that naive load balancing could lead to oscillation [S1].
*   **Usage:** Used in distributed volume rendering systems, specifically those using graphics-hardware-based cluster systems with Infiniband networks [S1].
