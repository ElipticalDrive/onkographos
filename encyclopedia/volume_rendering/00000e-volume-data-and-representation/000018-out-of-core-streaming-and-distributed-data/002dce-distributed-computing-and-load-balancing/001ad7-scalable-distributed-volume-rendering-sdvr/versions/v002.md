# Scalable Distributed Volume Rendering (SDVR)

Also called: Cluster-based Distributed Volume Rendering, Distributed Volume Rendering System, Distributed rendering system for unstructured data, Distributed slicing rendering, MPI-based distributed volume rendering

## Overview
Scalable Distributed Volume Rendering (SDVR) is a distributed rendering system for unstructured data targeting large PC clusters, designed to maintain constant rendering time as dataset size and node count increase [S1][S2, unofficial]. It solves the scalability problem in volume visualization by partitioning the dataset into load-balanced chunks, distributing them to cluster nodes, and accumulating subimages over the interconnect [S1][S2, unofficial]. It differs from sibling methods like [MPI Volume Rendering (1D/2D Decomposition)](2249-mpi-volume-rendering-1d-2d-decomposition.md) by using an out-of-core modified k-d decomposition for preprocessing and explicit subimage accumulation over the network rather than pixel-based accumulation or image-based assembly by a root process [S1][S2, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A large unstructured volume dataset (e.g., curvilinear or unstructured grids) [S1][S2, unofficial].
- Output: A single composite image of the entire volume [S1][S2, unofficial].

**Data Structures:**
- **Chunks:** Brick-shaped subsets of the original dataset. These are the atomic units of distribution [S1][S2, unofficial].
- **Subimages:** Partially composited images generated by each node from its assigned chunks [S1][S2, unofficial].

**Preprocessing (Partitioning):**
1. The dataset is partitioned into small, load-balanced chunks [S1][S2, unofficial].
2. This is performed using an out-of-core algorithm based on a modified k-d decomposition [S1][S2, unofficial].
3. The specific details of the "modified k-d decomposition" algorithm are not provided in the sources [G]. The goal is load balancing across the cluster nodes [S1][S2, unofficial].

**Distribution:**
1. The brick-shaped chunks are distributed to the nodes of the cluster [S1][S2, unofficial].
2. Communication is handled via MPI [S1][S2, unofficial].

**Local Rendering:**
1. Each node receives its assigned chunks [S1][S2, unofficial].
2. Each node slices, clips, and renders its chunks [S1][S2, unofficial].
3. The rendering method is slicing-based [S1][S2, unofficial].
4. Graphics hardware (e.g., OpenGL-accelerated) is optional but recommended for peak performance; the system runs without it on any platform [S1][S2, unofficial].

**Compositing/Assembly:**
1. The resulting subimages from all nodes are gathered [S1][S2, unofficial].
2. The subimages are accumulated over the interconnect system to form the final image [S1][S2, unofficial].

**Pseudocode:**

```python
# SDVR Distributed Volume Rendering
# Assumptions: MPI environment, dataset D, number of nodes N

def sdvr_render(dataset, num_nodes):
    # Step 1: Preprocessing - Partitioning
    # Partition dataset into load-balanced brick-shaped chunks
    # using out-of-core modified k-d decomposition
    chunks = partition_dataset_out_of_core(dataset, num_nodes)
    
    # Step 2: Distribution
    # Distribute chunks to cluster nodes
    # This is handled by MPI scatter/gather or similar collective operations
    my_chunks = distribute_chunks(chunks)
    
    # Step 3: Local Rendering
    # Initialize rendering context (OpenGL if available, software otherwise)
    renderer = initialize_renderer(use_hardware_acceleration=True)
    
    # Slice, clip, and render each chunk
    subimages = []
    for chunk in my_chunks:
        # Slice the chunk to generate a partial image
        # Clip based on view parameters (not detailed in sources)
        subimage = renderer.slice_clip_render(chunk)
        subimages.append(subimage)
        
    # Step 4: Compositing/Assembly
    # Gather and accumulate subimages over the interconnect
    final_image = accumulate_subimages_over_network(subimages)
    
    return final_image
```

**Parameters:**
- **Graphics Hardware:** Optional. The system runs with or without it, though peak performance requires hardware [S2, unofficial].
- **APIs:** OpenGL and MPI [S1][S2, unofficial].
- **Cluster Size:** Targeted for large clusters (16-1000+ nodes) [S2, unofficial].

**Edge Cases and Pitfalls:**
- **Communication Overhead:** The sources note that speed-up curves level out after a certain number of threads (e.g., 5 for slicing, 18 for projection) due to communications overhead [S1][S2, unofficial]. This implies that excessive parallelism or small chunk sizes can degrade performance due to network latency [S1][S2, unofficial].
- **Platform Independence:** While the system is designed to run on any platform without graphics hardware, performance will not be at peak levels [S1][S2, unofficial].

## Subtopics

### [Distributed Volume Ray Tracing with Global Kd-Tree](1774-distributed-volume-ray-tracing-with-global-kd-tree.md)
A distributed rendering method for load balancing where adjacent tetrahedra are scattered across nodes rather than clustered, using a global kd-tree to restore ordering during rendering.

### [Distributed Shared Virtual Memory Volume Rendering](1916-distributed-shared-virtual-memory-volume-rendering.md)
Distributed Shared Virtual Memory (DSVM) Volume Rendering is a method for rendering tera-scale volumes on GPU clusters by mapping the entire volume into a single shared 3D virtual memory space accessible by all nodes. It solves the problem of managing massive datasets that exceed the physical memory of individual GPUs by using on-demand paging of small voxel blocks, allowing multiple nodes to render disjoint parts of the volume simultaneously without explicit data partitioning or load balancing. It differs from sibling methods like Distributed Volume Ray Tracing with Global Kd-Tree by relying on a flat virtual memory address space with hardware-assisted page fault handling rather than a distributed spatial index, and by targeting small GPU clusters where implicit load balancing via interleaved distribution units suffices.

## Operating characteristics
- **Scalability:** The primary goal is scalability: rendering time remains constant as the dataset size increases, provided additional computational nodes are added [S1][S2, unofficial].
- **Performance:** A prototype ran successfully at interactive rates on up to 32 nodes of a PC cluster equipped with Nvidia GeForce-3 graphics cards [S1][S2, unofficial].
- **Hardware Requirements:** Runs on LINUX/UNIX systems [S1]. Uses OpenGL and MPI [S1][S2, unofficial]. Graphics hardware is optional but required for peak performance [S2, unofficial].
- **Limitations:** Speed-up is limited by communications overhead, which causes the performance curve to level out after a certain number of threads (5 for slicing, 18 for projection) [S1][S2, unofficial].
- **When to Use:** Suitable for large PC clusters (16-1000+ nodes) rendering large unstructured or curvilinear grid datasets where scalability is critical [S1][S2, unofficial].
- **When Not to Use:** Not suitable for small clusters where communication overhead dominates, or when hardware acceleration is unavailable and peak performance is required [S1][S2, unofficial].
