# Static Round-Robin Partitioning

Also called: Round-Robin Static Load Balancing, Round-Robin Subvolume Distribution, Static Load Balancing Scheme

## Overview
Static Round-Robin Partitioning is a load balancing strategy for distributed volume rendering that partitions a data volume into many small subvolumes and distributes them round-robin across processors to average out projected area and element count differences [S1, S2, unofficial]. It sets itself apart from its siblings, [Scattered Assignment](4204-scattered-assignment.md) and [Randomized Data Decomposition](11592-randomized-data-decomposition.md), by using a deterministic, sequential assignment pattern rather than random or purely scattered mapping, though it shares the trait of destroying spatial locality [S1, S2, unofficial]. Unlike dynamic methods, it fixes the data-to-node mapping permanently after initial empirical tuning [S1, unofficial].

## How it works
**Inputs:**
- A data volume (e.g., unstructured grid or structured grid).
- $p$: The number of available processors.
- $n$: The total number of subvolumes to create (a "magic number" determined empirically).

**Outputs:**
- A mapping of subvolumes to processors.
- Rendered image fragments from each processor, which are composited into the final image.

**Data Structures:**
- **Subvolume List:** An array of $n$ subvolumes. Each subvolume is a contiguous or disjoint subset of the original volume data. The sources do not specify the exact geometric definition of a "subvolume" (e.g., axis-aligned bounding box, grid chunk), only that they are disjoint [S1, S2, unofficial].
- **Processor Assignment Map:** An array or hash map where index $i$ (for $0 \le i < n$) stores the processor ID assigned to subvolume $i$.

**Steps:**
1. **Determine $n$:** Perform one or two test runs to empirically determine a "magic number" $n$ [S1, S2, unofficial]. The sources do not provide a formula for calculating $n$, only that it is found via trial [S1, S2, unofficial].
2. **Partition:** Divide the input data volume into $n$ disjoint subvolumes [S1, S2, unofficial].
3. **Distribute:** Assign the $n$ subvolumes to the $p$ processors in a round-robin fashion. Specifically, subvolume $i$ is assigned to processor $i \pmod p$ [S1, S2, unofficial].
4. **Render:** Each processor renders all subvolumes assigned to it. Since the subvolumes are disjoint and potentially spatially scattered, each processor may render multiple disjointed subvolumes instead of a single large volume [S1, S2, unofficial].
5. **Composite:** The image fragments generated by each processor are composited to form the final image [S1, S2, unofficial].

**Pseudocode:**
```python
def static_round_robin_partition(volume, p):
    """
    volume: The input data volume to be partitioned.
    p: The number of processors.
    Returns: A list of assignments, where assignments[i] is the processor ID for subvolume i.
    """
    # Step 1: Determine n empirically.
    # The source does not provide an algorithm for this.
    # [G] In practice, n might be chosen based on memory limits or cache size,
    # but here we assume n is provided as a parameter derived from test runs.
    n = get_magic_number(volume, p) 

    # Step 2: Partition the volume into n subvolumes.
    # The source does not specify the partitioning geometry.
    # [G] Assuming a simple linear split of the data array for implementation purposes,
    # though the source mentions "subvolumes" implying spatial chunks.
    subvolumes = partition_volume_into_n_chunks(volume, n)

    # Step 3: Distribute subvolumes round-robin across p processors.
    assignments = []
    for i in range(n):
        processor_id = i % p
        assignments.append(processor_id)

    return assignments, subvolumes

def render_subvolumes(subvolumes, assignments):
    """
    Each processor executes this function for its assigned subvolumes.
    """
    my_processor_id = get_current_processor_id()
    my_subvolumes = [subvolumes[i] for i in range(len(subvolumes)) if assignments[i] == my_processor_id]
    
    # Step 4: Render assigned disjointed subvolumes.
    image_fragments = []
    for subvol in my_subvolumes:
        fragment = render_volume(subvol)
        image_fragments.append(fragment)
        
    return image_fragments
```

**Parameters:**
- $n$: The number of subvolumes. Increasing $n$ reduces differences in average projected area and element count per processor but increases the number of ray segments generated [S1, S2, unofficial].
- $p$: The number of processors.

**Edge Cases and Pitfalls:**
- **Compositing Cost:** Increasing $n$ generates many more ray segments, resulting in higher image compositing cost [S1, S2, unofficial].
- **Ray Casting Cost:** The method does not consistently or significantly improve ray casting cost despite balancing load [S1, S2, unofficial].
- **Zoom-in Problem:** It fails for zoom-in views on adaptive grids, as the static partitioning cannot adapt to the changing density of visible elements [S1, S2, unofficial].
- **Load Imbalance:** While it reduces differences in projected area and element count, it may not achieve perfect balance, with reported imbalance above 20% in some implementations [S1, unofficial].

## Subtopics

### [Static Data Partition Method](11605-static-data-partition-method.md)
A load balancing strategy for distributed isocontour visualization that partitions a massive dataset among computational nodes at the preprocessing stage to minimize communication overhead. It is chosen over dynamic redistribution because PC clusters have low bandwidth, making inter-node data transfer the least scalable factor as data size increases. It sets itself apart from dynamic methods by fixing the data-to-node mapping permanently, relying on careful initial partitioning rather than runtime migration.

## Operating characteristics
- **Time Complexity:** Not explicitly given. The rendering time depends on the number of ray segments, which increases with $n$ [S1, S2, unofficial].
- **Memory Complexity:** Not explicitly given. Each processor stores only its assigned subvolumes [S1, S2, unofficial].
- **Measured Performance:** Timing results did not show consistent and significant improvement in overall rendering time compared to non-partitioned or other static methods [S1, S2, unofficial].
- **Scaling:** The method does not scale well for zoom-in views on adaptive unstructured grids [S1, S2, unofficial].
- **Strengths:** Reduces differences in average projected area and element count per processor as $n$ increases [S1, S2, unofficial].
- **Limitations:** Increases image compositing cost; does not consistently improve ray casting cost; fails for zoom-in views; static nature prevents adaptation to dynamic changes [S1, S2, unofficial].
- **When to use:** When a simple, fixed load distribution is acceptable and dynamic balancing is too complex or costly to implement [S1, unofficial].
- **When not to use:** For zoom-in views on adaptive grids, or when dynamic load balancing is feasible and required for performance [S1, S2, unofficial].

## Background
Static Round-Robin Partitioning was proposed as a static load balancing scheme for parallel volume ray-casting of unstructured-grid data on distributed-memory architectures [S1, S2, unofficial]. It was developed in the context of direct volume rendering for scientific and engineering applications, where large unstructured-grid data sets cause significant load imbalance [S1, S2, unofficial]. The authors noted that achieving load balancing statically is difficult due to factors like projected area, opacity transfer functions, viewing angle, and zoom level [S1, S2, unofficial]. The method was part of an effort to improve the performance of the "Tenderer" system, though it was acknowledged that dynamic load balancing would be a more effective but harder-to-implement solution [S1, S2, unofficial].
