# MPI Volume Rendering (1D/2D Decomposition)

Also called: Domain Decomposition Ray Casting, Domain Decomposition Volume Rendering, MPI-based Parallel Volume Rendering with Domain Decomposition, MPI-based Ray Casting, MPICH Volume Rendering, Parallel Volume Rendering with MPI

## Overview
MPI Volume Rendering (1D/2D Decomposition) is a distributed-memory parallel volume rendering technique that partitions a 3D scalar dataset into 1D (row-based) or 2D (block-based) spatial subdomains, assigning each to an independent MPI process for local ray casting [S1, S2, S4, unofficial]. It solves the scalability problem of rendering large volumetric datasets that exceed the memory or compute capacity of a single node by distributing both data and computation across a cluster [S1, S4, unofficial]. Unlike its sibling [MPI Volume Rendering (3D Decomposition)](2254-mpi-volume-rendering-3d-decomposition.md), which splits the volume along X, Y, and Z axes simultaneously, this method restricts decomposition to the X and/or Y axes, keeping the full depth (Z-axis) intact for each process [S2, S3, unofficial]. This allows each process to cast rays along the Z-axis independently, eliminating per-ray communication overhead and enabling local compositing before final assembly [S2, unofficial]. It differs from [Parallel Volume Rendering via k-d Tree Subdivision and Binary-Swap Compositing](5944-parallel-volume-rendering-via-k-d-tree-subdivision-and-binar.md) by using fixed-axis aligned subdomains rather than k-d tree based spatial subdivision, which avoids tree construction overhead but may lead to load imbalance if volume density is non-uniform [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D scalar volume dataset (typically `float32`), opacity transfer function (TF), color transfer function (TF), decomposition strategy (1D or 2D), ray marching step size, and bounding box coordinates [S2, S4, unofficial].
*   **Output:** A final 2D RGBA image assembled from sub-images generated by each process, along with statistics such as early ray termination counts and computation time [S2, unofficial].

**Data Structures:**
*   **Volume Data:** Stored as a contiguous array. In C++ implementations, a `std::vector<float>` of size $X \times Y \times Z$ is used, with index calculation `idx = z * Y * X + y * X + x` (assuming X is the fastest varying dimension in memory layout for the specific implementation, though some Python implementations transpose to C-order) [S1, S4, unofficial]. In Python, a NumPy array of shape $(X, Y, Z)$ in C-order is common [S2, S4, unofficial].
*   **Transfer Functions:**
    *   **Opacity TF:** A list of scalar keys and corresponding opacity values. Often stored as alternating lines in a text file (key, value) or parsed into a dictionary for fast lookup [S2, unofficial].
    *   **Color TF:** A list of scalar keys and RGB triplets. Stored as groups of 4 lines (key, R, G, B) in text files or parsed into a dictionary [S2, unofficial].
*   **Local Image Buffer:** Each process maintains a local buffer for its sub-image. In C++, this is often a 3D array `eachImage[eachYlen][eachXlen][4]` storing RGBA floats [S3, unofficial]. In Python, a NumPy array of shape $(rows, cols, 4)$ [S2, unofficial].

**Algorithm Steps:**

1.  **Initialization:**
    *   Initialize MPI communicator. Retrieve process `rank` and total `size` [S2, S4, unofficial].
    *   Parse command-line arguments: filename, partitioning type (1 for 1D, 2 for 2D), step size, and bounding box [S2, unofficial].
    *   Load transfer functions. Each process reads the TF files and creates local dictionaries (`op_dictionary`, `color_dictionary`) mapping scalar values to opacity/color to avoid repeated I/O during rendering [S2, unofficial].

2.  **Domain Decomposition and Data Distribution:**
    *   **Rank 0** reads the full volume data.
    *   **1D Decomposition (Partitioning=1):**
        *   Calculate `chunk_size = X_dim // size`.
        *   Process `i` gets X-range `[i * chunk_size, (i+1) * chunk_size)`. The last process gets the remainder [S2, S4, unofficial].
        *   Y and Z ranges are full ($0$ to $Y_{dim}$, $0$ to $Z_{dim}$) [S2, unofficial].
    *   **2D Decomposition (Partitioning=2):**
        *   Find best split $(N_x, N_y)$ such that $N_x \times N_y = size$, $N_x \ge N_y$, and $N_x, N_y$ are close to $\sqrt{size}$ [S2, unofficial].
        *   Calculate `chunk_x = X_dim // N_x`, `chunk_y = Y_dim // N_y` [S2, unofficial].
        *   Process `rank` maps to grid coordinates: `proc_x = rank % N_x`, `proc_y = rank // N_x` [S2, unofficial].
        *   Start/End indices are calculated similarly to 1D, with the last chunk in each dimension absorbing the remainder [S2, S4, unofficial].
    *   **Distribution:** Rank 0 slices the volume data according to the bounds and sends the sub-domain to each process using `MPI_Send`/`MPI_Recv` [S1, S2, S4, unofficial]. Non-root processes receive their data into a local buffer [S3, unofficial].

3.  **Local Ray Casting:**
    *   Each process iterates over its assigned pixel grid $(x, y)$ [S1, S2, unofficial].
    *   For each pixel, initialize accumulated color $C' = (0,0,0)$ and accumulated opacity $A' = 0$ [S1, S2, unofficial].
    *   **Ray Marching:** Iterate along the Z-axis from $z=0$ to $Z_{dim}$ with step `step_size` [S2, S4, unofficial].
        *   Calculate sample point $z_{sample}$.
        *   **Interpolation:**
            *   Determine integer indices $z_{idx} = \lfloor z_{sample} \rfloor$ and $z_{next} = \lceil z_{sample} \rceil$ [S1, S2, unofficial].
            *   Compute weight $\alpha = z_{sample} - z_{idx}$ [S2, unofficial].
            *   Interpolate scalar value $V_p = (1-\alpha)V_{z_{idx}} + \alpha V_{z_{next}}$ [S2, unofficial].
            *   **Transfer Function Lookup:**
                *   Use `bisect` or linear interpolation on the local dictionaries to find opacity $A$ and color $C$ for $V_p$ [S2, unofficial].
                *   Handle boundary conditions: if $V_p$ is outside TF range, clamp to first/last values [S2, S4, unofficial].
                *   Clamp color indices to prevent out-of-bounds access (e.g., if index equals length, decrement by 1) [S2, unofficial].
        *   **Compositing (Front-to-Back):**
            *   Update accumulated values using the standard volume rendering equation [S2, unofficial]:
                $$C_i' = C_{i-1}' + (1 - A_{i-1}') C_i A_i$$
                $$A_i' = A_{i-1}' + (1 - A_{i-1}') A_i$$
            *   Where $C_i, A_i$ are the interpolated color and opacity of the current sample [S2, unofficial].
            *   Clamp RGB channels to $[0, 1]$ and opacity to $< 1.0$ if necessary [S1, S3, unofficial].
        *   **Early Ray Termination (ERT):**
            *   If $A_i' \ge 0.97$ (or $1.0$ depending on implementation), terminate the ray for this pixel [S1, S2, S4, unofficial].
            *   Increment `early_ray_terminations` counter [S2, unofficial].
            *   Break the Z-loop [S1, S2, unofficial].

4.  **Result Assembly:**
    *   Each process generates an RGBA sub-image from its local buffer [S2, unofficial].
    *   **Global Reduction (Root Assembly):**
        *   Processes send their sub-images, early termination counts, and timing information to Rank 0 [S2, unofficial].
        *   Rank 0 receives all sub-images.
        *   Rank 0 creates a final image array and places each sub-image in its correct spatial position based on the decomposition grid [S2, unofficial].
        *   Rank 0 saves the final image to disk (e.g., PNG) [S1, S2, unofficial].
    *   *Note:* Some implementations use a **Binary Swap** reduction for compositing if the decomposition involves splitting the image domain itself (e.g., in [MPI Volume Rendering (3D Decomposition)](2254-mpi-volume-rendering-3d-decomposition.md) or specific image-space variants), but the standard 1D/2D object-space decomposition described here typically gathers sub-images to a root for assembly [S3, S2, unofficial]. The provided notes for 1D/2D specifically mention sending results to a root process [S1, S2, unofficial].

```python
import numpy as np
from mpi4py import MPI
import bisect

def interpolate_tf(value, keys, values):
    """Linear interpolation for TF values."""
    if value <= keys[0]:
        return values[0]
    if value >= keys[-1]:
        return values[-1]
    
    idx = bisect.bisect(keys, value)
    # Clamp index to valid range
    if idx >= len(keys):
        idx = len(keys) - 1
    if idx == 0:
        idx = 1
        
    key_left = keys[idx-1]
    key_right = keys[idx]
    val_left = values[idx-1]
    val_right = values[idx]
    
    alpha = (value - key_left) / (key_right - key_left)
    return val_left + alpha * (val_right - val_left)

def ray_cast_subdomain(local_data, step_size, op_keys, op_vals, col_keys, col_vals, x_start, x_end, y_start, y_end, z_dim):
    """
    Performs ray casting for a local subdomain.
    local_data shape: (x_len, y_len, z_dim)
    Returns: sub_image (RGBA), early_terminations
    """
    x_len = x_end - x_start
    y_len = y_end - y_start
    sub_image = np.zeros((y_len, x_len, 4), dtype=np.float32)
    early_terminations = 0
    
    for y in range(y_len):
        for x in range(x_len):
            acc_r, acc_g, acc_b, acc_a = 0.0, 0.0, 0.0, 0.0
            
            z_sample = 0.0
            while z_sample < z_dim - 1:
                z_idx = int(np.floor(z_sample))
                z_next = z_idx + 1
                alpha = z_sample - z_idx
                
                # Interpolate scalar value
                v1 = local_data[x, y, z_idx]
                v2 = local_data[x, y, z_next]
                v_p = (1 - alpha) * v1 + alpha * v2
                
                # Lookup Color and Opacity
                c_r = interpolate_tf(v_p, col_keys, col_vals[:, 0])
                c_g = interpolate_tf(v_p, col_keys, col_vals[:, 1])
                c_b = interpolate_tf(v_p, col_keys, col_vals[:, 2])
                a = interpolate_tf(v_p, op_keys, op_vals)
                
                # Front-to-Back Compositing
                one_minus_acc_a = 1.0 - acc_a
                factor = one_minus_acc_a * a
                
                acc_r += factor * c_r
                acc_g += factor * c_g
                acc_b += factor * c_b
                acc_a += factor
                
                # Early Termination
                if acc_a >= 0.97: # Threshold from [S1, unofficial]
                    early_terminations += 1
                    break
                
                z_sample += step_size
            
            # Store result (RGBA)
            sub_image[y, x, 0] = acc_r
            sub_image[y, x, 1] = acc_g
            sub_image[y, x, 2] = acc_b
            sub_image[y, x, 3] = acc_a
            
    return sub_image, early_terminations
```

## Subtopics

### [MPI Volume Rendering (3D Decomposition)](2254-mpi-volume-rendering-3d-decomposition.md)
MPI Volume Rendering (3D Decomposition) partitions the volume into a 3D grid of subdomains, assigning each to a distinct MPI process. It solves scalability for datasets exceeding single-node memory by distributing data and computation along X, Y, and Z axes. Unlike 1D/2D decomposition, it allows better matching of data aspect ratio to process grid but requires more complex communication for ray crossing boundaries or image compositing if not fully independent. It differs from [Parallel Volume Rendering via k-d Tree Subdivision and Binary-Swap Compositing](5944-parallel-volume-rendering-via-k-d-tree-subdivision-and-binar.md) by using fixed-axis aligned subdomains.

### [Parallel Volume Rendering with Static Load Balancing](2547-parallel-volume-rendering-with-static-load-balancing.md)
This method combines spatial partitioning with static load balancing for unstructured meshes, distributing data and computation across processors. It solves efficient rendering of large unstructured grids by performing local ray-casting independently and overlapping global image compositing with local computation. It differs from [MPI Master Node Parallel Rendering Workflow](2625-mpi-master-node-parallel-rendering-workflow.md) by using a fully distributed, view-independent static partitioning scheme that minimizes synchronization overhead.

### [MPI Master Node Parallel Rendering Workflow](2625-mpi-master-node-parallel-rendering-workflow.md)
This method implements a master-slave architecture where a single master node coordinates spawning slave processes, distributes rendering parameters, and assembles the final image from per-slice fragments received over TCP. It is distinguished from [MPI Parallel Slice-Based Volume Rendering](3827-mpi-parallel-slice-based-volume-rendering.md) by explicitly handling domain decomposition and image concatenation within a pre-defined master-slave workflow abstraction.

### [Parallel Volume Ray Casting (PVR) Library Interface](3206-parallel-volume-ray-casting-pvr-library-interface.md)
The PVR Library Interface enables in-place rendering of rectilinear grid data on distributed-memory systems without transferring large datasets to a host. It separates the pipeline into local resampling and global compositing, allowing interactive monitoring of parallel CFD simulations. Unlike sibling methods that may rely on binary-swap compositing, this interface selects direct compositing to remain independent of the specific data partitioning scheme.

### [Parallel Distributed Axis-aligned Volume Rendering using MPI](3804-parallel-distributed-axis-aligned-volume-rendering-using-mpi.md)
This method performs axis-aligned volume rendering by decomposing a 3D scalar dataset across multiple MPI processes, where each process renders a spatial subdomain by casting rays along the Z-axis and compositing front-to-back. It differs from global ray casting by distributing data spatially along the view axis rather than distributing rays, which eliminates per-ray communication overhead. It supports 1D and 2D data decomposition.

### [Parallel DVR Algorithm (Object-Space Decomposition)](4258-parallel-dvr-algorithm-object-space-decomposition.md)
The Parallel DVR Algorithm (OS-DVR) decomposes the volumetric dataset into clusters to minimize inter-processor communication and redundant ray calculations. Unlike standard domain decomposition methods that fix the data distribution, OS-DVR employs a view-dependent remapping phase to dynamically reassign clusters based on the current viewing parameters, thereby optimizing load balance and communication overhead for each visualization instance. It builds on [MPI Volume Rendering (1D/2D Decomposition)](2249-mpi-volume-rendering-1d-2d-decomposition.md) by introducing a graph-partitioning-based remapping step.

### Distributed INR Volume Rendering
A deep learning-based volume rendering method integrated with the Ascent in-situ infrastructure, validating INR compression at HPC scale [S5, unofficial]. It trains one independent INR per MPI rank on its local data partition, using ghost cells and half-Gaussian sampling for continuity [S5, unofficial]. It adaptsively tunes parameters to scale each rank’s hash table size proportionally to its local voxel count and uses weight caching from previous timesteps [S5, unofficial]. Tested on up to 512 MPI ranks on the Polaris supercomputer, demonstrating near-ideal weak scaling efficiency on domains up to $2,580^3$ [S5, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N \cdot P^{-1} \cdot D)$, where $N$ is the total number of pixels in the image, $P$ is the number of processes, and $D$ is the average ray depth (number of samples per ray) [S1, S2, unofficial]. Early ray termination reduces the effective $D$ [S1, unofficial].
*   **Memory Complexity:** $O(V/P)$ per process, where $V$ is the volume data size, plus $O(I/P)$ for the sub-image, where $I$ is the image size [S1, S2, unofficial]. Rank 0 requires $O(V + I)$ to assemble the final result [S2, unofficial].
*   **Measured Performance:** On a 2000x2000x400 float32 dataset, the method was used on an MPI cluster [S2, unofficial]. Early termination was reported to reduce execution time by 15% in one implementation [S1, unofficial].
*   **Strengths:** Simple implementation; no communication during ray casting; efficient for view-independent static scenes; leverages standard MPI for data distribution [S1, S2, unofficial].
*   **Limitations:** Load imbalance if volume density or view direction causes some processes to render more opaque regions or larger subdomains; communication bottleneck at Rank 0 during final assembly if many processes are used; fixed decomposition may not adapt to view changes [S1, S2, S3, unofficial].
*   **When to Use:** Large static volumetric datasets that fit within the cluster's aggregate memory; view-independent rendering; clusters with high-speed interconnects for the final assembly phase [S1, S2, unofficial].
*   **When Not to Use:** Highly dynamic scenes requiring frequent view-dependent load balancing (consider [Parallel DVR Algorithm (Object-Space Decomposition)](4258-parallel-dvr-algorithm-object-space-decomposition.md)); datasets where the aspect ratio does not match the 1D/2D decomposition grid well (consider [MPI Volume Rendering (3D Decomposition)](2254-mpi-volume-rendering-3d-decomposition.md)); interactive applications with very low latency requirements for compositing [S2, S3, unofficial].

## Background
MPI Volume Rendering (1D/2D Decomposition) originated from the need to scale volume rendering to large datasets on distributed-memory clusters using the Message Passing Interface (MPI) [S1, S2, unofficial]. It is based on the principle of object-space decomposition, where the volume is partitioned spatially [S1, S2, unofficial]. The method has been implemented in various academic and open-source projects, such as those using MPICH or standard MPI libraries [S1, S2, unofficial]. It is commonly used in scientific visualization for large-scale simulations, such as computational fluid dynamics (CFD) and climate modeling, where datasets can reach terabytes in size [S2, S4, unofficial]. The approach is a foundational technique in distributed volume rendering, often serving as a baseline for more complex load-balancing and compositing strategies [S1, S2, unofficial].
