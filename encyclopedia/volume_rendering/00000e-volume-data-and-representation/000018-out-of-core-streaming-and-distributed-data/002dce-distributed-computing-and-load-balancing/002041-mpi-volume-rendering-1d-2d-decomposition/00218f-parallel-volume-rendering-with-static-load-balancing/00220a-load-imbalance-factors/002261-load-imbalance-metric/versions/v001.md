# Load Imbalance Metric

Also called: Load Imbalance Factor, Rendering Load Imbalance Metric

## Overview
The Load Imbalance Metric quantifies the performance degradation caused by uneven workload distribution across processors in parallel volume ray-casting on unstructured grids [S1, S2, unofficial]. It is distinct from raw timing measurements by normalizing the disparity between the slowest and average processors, providing a dimensionless ratio of inefficiency [S1, S2, unofficial]. Unlike metrics that track per-pixel variance, this metric aggregates the global impact of static load balancing failures on the total rendering time [S1, S2, unofficial].

## How it works
**Inputs and Outputs**
- **Inputs**: $t_{max}$, the maximum rendering time among all processors; $t_{avg}$, the average rendering time across all processors.
- **Output**: $l$, the load imbalance metric value, where $0 \le l < 1$.

**Data Structures**
No specific data structures are required for the calculation itself. The inputs are scalar values derived from timing logs of the parallel rendering execution.

**Formula**
The metric is calculated as:
$$ l = 1 - \frac{t_{avg}}{t_{max}} $$
where:
- $t_{avg} = \frac{1}{P} \sum_{i=1}^{P} t_i$ is the mean rendering time across $P$ processors.
- $t_{max} = \max_{i=1}^{P} t_i$ is the maximum rendering time observed among the $P$ processors.
- $P$ is the total number of processors.

**Steps**
1. Measure the total rendering time $t_i$ for each processor $i$ from $1$ to $P$.
2. Compute the average time $t_{avg}$ by summing all $t_i$ and dividing by $P$.
3. Identify the maximum time $t_{max}$ from the set of all $t_i$.
4. Calculate the ratio $t_{avg} / t_{max}$.
5. Subtract the ratio from 1 to obtain $l$.

**Pseudocode**
```python
def calculate_load_imbalance(processor_times):
    """
    Calculate the load imbalance metric for a set of processor rendering times.
    
    Args:
        processor_times (list of float): List of total rendering times for each processor.
        
    Returns:
        float: The load imbalance metric l.
    """
    if not processor_times:
        return 0.0
    
    # Step 1 & 2: Calculate average time
    t_avg = sum(processor_times) / len(processor_times)
    
    # Step 3: Identify maximum time
    t_max = max(processor_times)
    
    # Guard against division by zero if all times are zero
    if t_max == 0:
        return 0.0
        
    # Step 4 & 5: Calculate metric
    l = 1.0 - (t_avg / t_max)
    
    return l
```

**Edge Cases and Pitfalls**
- **Distribution Blindness**: The formulation does not reveal the actual distribution of the imbalanced load. It only provides an aggregate measure of degradation [S1, S2, unofficial]. For example, two scenarios with the same $l$ may have vastly different variance profiles among the intermediate processors.
- **Sensitivity to Outliers**: Since $t_{max}$ is in the denominator, a single straggler processor significantly increases the metric, potentially masking the efficiency of the majority of processors.
- **Zero Time**: If rendering time is zero (e.g., empty volume or immediate termination), the metric is undefined or requires a guard [G].

## Operating characteristics
**Time and Memory Complexity**
- **Time**: $O(P)$ to compute $t_{avg}$ and $t_{max}$ from $P$ processor times.
- **Memory**: $O(1)$ auxiliary space if times are streamed, or $O(P)$ to store the list of times.

**Measured Performance**
In tests on flow data with a 480x480 image size using 32 processors, load imbalance degraded overall performance by at least 20% [S1, S2, unofficial]. When using a zoom-in view, the difference between maximum and minimum time increased from 40% to 66%, causing the proportion of time devoted to ray casting due to load imbalance to rise to approximately 33% [S1, S2, unofficial].

**Strengths and Limitations**
- **Strengths**: Simple to compute from standard timing logs; provides a single scalar for comparing different load balancing strategies or decomposition schemes.
- **Limitations**: Does not indicate which processors are imbalanced or the nature of the imbalance (e.g., geometric vs. data-driven). It is less effective for detecting minor imbalances that are spread across many processors rather than concentrated in a few [S1, S2, unofficial].

**When to Use**
Use this metric for high-level evaluation of static load balancing effectiveness in distributed volume rendering, particularly when comparing different decomposition strategies (1D/2D) or subvolume sizes [S1, S2, unofficial].

## Background
The metric was introduced in the context of parallel volume ray-casting for unstructured-grid data on distributed-memory architectures [S1, S2, unofficial]. It was developed to quantify the impact of five primary factors causing uneven workload distribution: subvolume size, data density, view-dependent visibility, ray traversal complexity, and communication overhead [S1, S2, unofficial]. The metric has been used to analyze the performance of ray-segment merging and other optimization techniques in unstructured grid rendering [S1, S2, unofficial].
