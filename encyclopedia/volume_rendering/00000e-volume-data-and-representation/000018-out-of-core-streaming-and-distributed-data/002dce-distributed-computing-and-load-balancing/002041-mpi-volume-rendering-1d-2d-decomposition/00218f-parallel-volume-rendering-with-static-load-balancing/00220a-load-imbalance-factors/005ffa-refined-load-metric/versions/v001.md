# Refined Load Metric

Also called: Load Balancing Metrics, Total real Work load formula, Work load approximation formulas

## Overview
The Refined Load Metric is a cost model used to estimate the computational workload of a rectangular subregion in parallel volume ray-casting on unstructured grids, enabling static load balancing across processors [S1, unofficial]. It improves upon simpler bounding-box approximations by explicitly accounting for triangles, spans, and pixels, thereby reducing load imbalance errors, particularly those introduced by vertical divisions [S1, unofficial]. It is a refinement of the basic [Load Imbalance Metric](2763-load-imbalance-metric.md) by adding terms for clipped geometry and explicit error estimation.

## How it works
The method calculates two values: the Total Real Work Load ($W$) and the Total Approximated Work Load ($A$). The real work load is a weighted sum of geometric primitives and rasterization outputs, while the approximated work load subtracts the error introduced by the estimation process.

**Inputs and Outputs:**
- **Input:** Counts of triangles ($T$), spans ($S$), pixels ($P$), clipped triangles ($CT$), and clipped spans ($CS$) within a subregion.
- **Output:** Scalar values $W$ (real work) and $A$ (approximated work).

**Data Structures:**
No complex data structures are required for the metric calculation itself; it operates on scalar counts derived from the geometry of the subregion. The counts $T, S, P, CT, CS$ are typically obtained via a simple rasterization process (e.g., Z-Buffer) or bounding box approximations [S1, unofficial].

**Parameters:**
- $a$: Task done per triangle (weight for $T$).
- $b$: Task done per span (weight for $S$).
- $c$: Task done per pixel (weight for $P$).
- $d$: Task done per clipped triangle (weight for $CT$).
- $e$: Task done per clipped span (weight for $CS$).
- $E$: Error introduced by approximations.

These weights ($a, b, c, d, e$) are determined empirically through sample runs of the specific rendering implementation to reflect the relative computational cost of each operation [S1, unofficial].

**Formulas:**
The Total Real Work Load $W$ is defined as:
$$ W = (a \times T) + (b \times S) + (c \times P) + (d \times CT) + (e \times CS) + E $$

The Total Approximated Work Load $A$ is defined as:
$$ A = W - E $$

Where:
- $T$: Total number of Triangles. Workload due to clipping and insertion into y-bucket/active polygon lists is proportional to $T$ [S1, unofficial].
- $S$: Total number of Spans. Workload associated with creation of x-spans and insertion into x-bucket lists [S1, unofficial].
- $P$: Total number of Pixels. Workload from interpolation and composition operations [S1, unofficial].
- $CT$: Total number of Clipped Triangles.
- $CS$: Total number of Clipped Spans.
- $E$: Error introduced by approximations.

**Steps:**
1. Determine the rectangular subregion boundaries for a processor.
2. Count the total number of triangles ($T$) intersecting the subregion.
3. Count the total number of spans ($S$) generated by rasterizing the triangles within the subregion.
4. Count the total number of pixels ($P$) covered by the spans.
5. Count the total number of clipped triangles ($CT$) and clipped spans ($CS$) resulting from boundary intersections.
6. Retrieve the empirical weights $a, b, c, d, e$ and the error estimate $E$ for the specific implementation.
7. Calculate $W$ using the formula above.
8. Calculate $A$ by subtracting $E$ from $W$.
9. Use $A$ (or $W$ if $E$ is negligible) to compare workloads across subregions and adjust division boundaries if necessary [S1, unofficial].

**Pseudocode:**
```python
def calculate_refined_load_metric(T, S, P, CT, CS, a, b, c, d, e, E):
    """
    Calculate the Total Real Work Load (W) and Total Approximated Work Load (A).
    
    Args:
        T (int): Total number of Triangles
        S (int): Total number of Spans
        P (int): Total number of Pixels
        CT (int): Total number of Clipped Triangles
        CS (int): Total number of Clipped Spans
        a (float): Task done per triangle
        b (float): Task done per span
        c (float): Task done per pixel
        d (float): Task done per clipped triangle
        e (float): Task done per clipped span
        E (float): Error introduced by approximations
        
    Returns:
        tuple: (W, A) where W is Total real Work load and A is Total Approximated work load
    """
    # Calculate Total Real Work Load
    W = (a * T) + (b * S) + (c * P) + (d * CT) + (e * CS) + E
    
    # Calculate Total Approximated Work Load
    A = W - E
    
    return W, A
```

**Edge Cases and Pitfalls:**
- **Empirical Weights:** The weights $a, b, c, d, e$ are implementation-specific. Using weights from a different renderer or hardware configuration will yield inaccurate load estimates [S1, unofficial].
- **Error Estimation:** The term $E$ is difficult to quantify precisely. If $E$ is ignored or poorly estimated, the approximation $A$ may still exhibit significant imbalance [S1, unofficial].
- **Clipping Costs:** The inclusion of $CT$ and $CS$ addresses errors from vertical divisions, which create new spans and edges. Ignoring these terms leads to underestimating the work in regions with many boundary intersections [S1, unofficial].
- **Rasterization Overhead:** Using a simple Z-Buffer to count $T, S, P$ adds preprocessing overhead. The cost of this counting must be less than the benefit of improved load balance [S1, unofficial].

## Operating characteristics
- **Time Complexity:** The calculation of $W$ and $A$ is $O(1)$ given the counts. However, obtaining the counts $T, S, P, CT, CS$ requires rasterization or geometric traversal, which depends on the number of primitives in the subregion.
- **Memory Complexity:** $O(1)$ for the metric calculation itself.
- **Performance:** The metric provides a more accurate approximation of real work than simpler bounding-box methods, leading to better load balance [S1, unofficial].
- **Strengths:** Explicitly models the costs of clipping, span creation, and pixel composition. Reduces errors from vertical divisions.
- **Limitations:** Requires empirical calibration of weights. The error term $E$ is hard to determine. Rasterization for counting adds overhead.
- **When to Use:** When static load balancing is required for parallel volume ray-casting on unstructured grids and simple geometric approximations (like bounding box volume) are insufficient to balance the load.
- **When Not to Use:** When dynamic load balancing is feasible, or when the overhead of counting primitives outweighs the benefit of improved balance.

## Background
The Refined Load Metric was introduced in a thesis from Bilkent University [S1, unofficial]. It was developed to address load imbalance in parallel volume ray-casting on unstructured grids, where simple geometric partitions (like bounding boxes) fail to account for the varying computational cost of rendering different parts of the scene. The method builds on the observation that workload is proportional to the number of triangles, spans, and pixels, and refines this by including clipped geometry and an error term. It is used in the context of MPI-based volume rendering with 1D/2D decomposition and static load balancing.
