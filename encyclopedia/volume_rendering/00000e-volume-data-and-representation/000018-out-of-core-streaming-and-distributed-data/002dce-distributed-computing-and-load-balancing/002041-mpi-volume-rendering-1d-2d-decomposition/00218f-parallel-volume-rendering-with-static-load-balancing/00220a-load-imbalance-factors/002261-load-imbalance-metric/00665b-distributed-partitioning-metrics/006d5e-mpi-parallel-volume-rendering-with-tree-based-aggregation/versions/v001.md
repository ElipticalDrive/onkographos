# MPI Parallel Volume Rendering with Tree-Based Aggregation

Also called: Parallel 3D Volume Rendering using MPI, Tree-based Composite Volume Rendering

## Overview
This method implements distributed volume rendering by partitioning a 3D scalar field across multiple MPI processes and aggregating the resulting sub-images using a binary tree reduction. It solves the bottleneck of sending all rendered sub-images to a single root process for final assembly, which becomes a communication and memory constraint at scale. Unlike naive all-to-one compositing, this approach distributes the compositing workload across the process hierarchy, reducing peak memory usage on the root and balancing network traffic during the aggregation phase [S1, unofficial].

## How it works

### Inputs and Outputs
**Inputs:**
*   `filename`: Path to the raw volume data file. The filename encodes dimensions at fixed indices: $x_{dim}$ at `[7:11]`, $y_{dim}$ at `[12:16]`, and $z_{dim}$ at `[17:20]` [S1, unofficial].
*   `px, py, pz`: Integers specifying the number of processes along the x, y, and z axes respectively [S1, unofficial].
*   `step_size`: Float for the ray casting step size [S1, unofficial].
*   `opacity_TF, color_TF`: Strings identifying opacity and color transfer functions [S1, unofficial].
*   `size`: Total number of MPI processes (`comm.Get_size()`). The algorithm assumes `size` is a power of two, $2^d$, where $d = \lfloor \log_2(size) \rfloor$ [S1, unofficial].

**Outputs:**
*   `final_image`: A composite RGBA image assembled by rank 0.

### Data Structures and Layout
*   **Volume Data:** Read as `np.float32`, reshaped to $(z_{dim}, y_{dim}, x_{dim})$, transposed to $(x_{dim}, y_{dim}, z_{dim})$, and made contiguous (`np.ascontiguousarray`) [S1, unofficial].
*   **Chunk Boundaries:** Calculated via `divide_data_3d`. For a process with `rank`:
    $$
    \begin{aligned}
    proc\_z &= rank // (px \times py) \\
    remainder &= rank \% (px \times py) \\
    proc\_y &= remainder // px \\
    proc\_x &= remainder \% px
    \end{aligned}
    $$
    Chunk dimensions are $chunk\_x = x_{dim} // px$, etc. The local chunk ranges are:
    $$
    \begin{aligned}
    start\_x &= proc\_x \times chunk\_x, \quad end\_x = (proc\_x + 1) \times chunk\_x \\
    start\_y &= proc\_y \times chunk\_y, \quad end\_y = (proc\_y + 1) \times chunk\_y \\
    start\_z &= proc\_z \times chunk\_z, \quad end\_z = (proc\_z + 1) \times chunk\_z
    \end{aligned}
    $$
*   **Sub-Image:** An RGBA array of shape $(x_{local}, y_{local}, 4)$, where the first 3 channels are RGB and the 4th is opacity [S1, unofficial].
*   **Image List:** A list of sub-images accumulated during the tree aggregation phase [S1, unofficial].

### Algorithm Steps

1.  **Initialization:**
    *   Rank 0 reads the entire volume data.
    *   All processes compute their local chunk boundaries using `divide_data_3d`.
    *   Rank 0 stores the spatial coordinates (`START_OF_Xs`, `END_OF_Xs`, etc.) for all ranks to map sub-images to the global output later [S1, unofficial].

2.  **Tree Data Distribution (Aggregation Phase):**
    *   Iterate $i$ from $0$ to $d$.
    *   **Receivers:** Processes with `rank < 2^d` and `rank % (2^(d-i)) == 0` act as receivers.
    *   **Iteration $i=0$:** Rank 0 slices the whole volume into chunks for all `size` processes. It sends each chunk to the corresponding rank. Rank 0 keeps its own chunk in `curr_data` [S1, unofficial].
    *   **Iteration $i>0$:**
        *   Receivers determine the `source_rank` from which to receive data:
            $$
            source\_rank = rank - \lceil 2^d / 2^i \rceil
            $$
        *   Receivers allocate space for incoming data shapes (determined by `get_shape`) and receive chunks from `source_rank` [S1, unofficial].
        *   **Senders:** After receiving, processes with `rank < 2^d` send the upper half of their accumulated `curr_data` list to their parent in the tree. The destination rank $r$ is:
            $$
            r = rank + \lceil 2^d / 2^{i+1} \rceil
            $$
        *   If `len(curr_data) == 2`, only the second half is sent; otherwise, the upper half of the list is sent. The sender retains the lower half [S1, unofficial].
    *   **Non-Tree Processes:** Processes with `rank >= 2^d` do not participate in the tree. After the tree phase (when $i=d$), Rank 0 sends their specific data chunk directly to them [S1, unofficial].

3.  **Local Ray Casting:**
    *   Each process performs volume rendering on its local `curr_data`.
    *   It calls `generate_sub_image(curr_data, step_size, color_dictionary, op_dictionary)` to produce a sub-image (RGB) and sub-opacity.
    *   The result is stacked into an RGBA image: `rgba_image = np.dstack((sub_image, sub_opacity))` [S1, unofficial].
    *   The process records its computation time (`max_time`) and `early_ray_terminations` [S1, unofficial].

4.  **Tree Image Compositing (Reduction Phase):**
    *   Iterate $i$ from $d$ down to $0$.
    *   **Odd Ranks (Senders):** If `rank < 2^d` and `rank % 2 != 0`, the process sends its `rgba_image`, `max_time`, and `early_ray_terminations` to `rank - 1` (its partner) [S1, unofficial].
    *   **Even Ranks (Receivers):** If `rank < 2^d` and `rank % (2^(d-i)) == 0`:
        *   Determine `source_rank`:
            $$
            source\_rank = rank + \lceil 2^d / 2^{i+1} \rceil
            $$
        *   Receive images from children into `image_list`.
        *   Receive timing and termination counts. Update global `max_time` if the received time is larger [S1, unofficial].
    *   **Recursive Sending:** If `rank < 2^d` and `rank % (2^(d-i+1)) != 0`, the process sends all accumulated images in `image_list` to its parent:
        $$
        destination\_rank = rank - \lceil 2^d / 2^i \rceil
        $$
        along with `max_time` and `early_ray_terminations` [S1, unofficial].

5.  **Final Image Assembly (Rank 0):**
    *   Rank 0 collects images from all processes with `rank >= 2^d` (sent directly in step 2).
    *   Rank 0 assembles the final image by placing each sub-image into a global `z_split` image array at the correct spatial position defined by the stored `START/END` coordinates [S1, unofficial].
    *   **Compositing:** The final image is computed by compositing the z-split images using front-to-back alpha compositing. For each z-slice, the RGB values are blended:
        $$
        \begin{aligned}
        final\_image[:, :, :3] &+= z\_split[:, :, :3] \times (1.0 - final\_image[:, :, 3:4]) \\
        final\_image[:, :, 3] &+= z\_split[:, :, 3] \times (1.0 - final\_image[:, :, 3])
        \end{aligned}
        $$
        This effectively accumulates color weighted by the remaining transparency [S1, unofficial].

### Edge Cases and Pitfalls
*   **Dimension Parsing:** The method parses volume dimensions directly from the filename string using fixed indices (`[7:11]`, `[12:16]`, `[17:20]`). This is brittle and assumes a strict filename format [S1, unofficial].
*   **Data Contiguity:** Arrays must be contiguous (`np.ascontiguousarray`) before MPI Send/Recv operations to avoid stride-related errors or implicit copying [S1, unofficial].
*   **Power of Two:** The tree structure assumes `size` is a power of two. Processes with `rank >= 2^d` are handled separately, receiving data directly from Rank 0 after the tree phase [S1, unofficial].

## Operating characteristics

*   **Time Complexity:** The data distribution and image compositing phases follow a binary tree pattern, resulting in $O(\log(size))$ communication steps. Local computation is $O(N)$ where $N$ is the number of voxels per process.
*   **Memory Complexity:** Each process stores only its local chunk of the volume and a portion of the image list during aggregation. This is significantly more memory-efficient than sending all sub-images to Rank 0, which would require $O(size \times ImageSize)$ memory on the root.
*   **Strengths:** Reduces the bottleneck on Rank 0 during the compositing phase. Distributes network load during both data distribution and image aggregation.
*   **Limitations:** Requires `size` to be a power of two for the tree logic to work cleanly (non-powers of two are handled by direct send from Rank 0, which may create imbalance). The rigid filename parsing is a maintenance risk.
*   **When to use:** Suitable for large volumes that do not fit in the memory of a single node, where the number of processes is a power of two.
*   **When not to use:** If the number of processes is not a power of two and the overhead of direct sends from Rank 0 is prohibitive, or if the volume fits entirely in shared memory, a shared-memory approach might be simpler.

## Background

This method is derived from an implementation of parallel 3D volume rendering using MPI, specifically focusing on tree-based aggregation for both data distribution and image compositing. It addresses the scalability issues of naive parallel volume rendering where a single process handles all compositing. The approach is documented in an unofficial GitHub repository [S1, unofficial].
