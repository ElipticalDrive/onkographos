# Visapult

Also called: Visapult Parallel IBRAVR Architecture

## Overview
Visapult is a parallel and distributed implementation of an Image Based Rendering Assisted Volume Rendering (IBRAVR) engine designed for the interactive visualization of massive (terabyte-scale) scientific datasets over Wide Area Networks (WAN) [S1][S2, unofficial]. It solves the problem of network-I/O bottlenecks and latency in remote visualization by decoupling the heavy volume rendering computation from the final image assembly [S2, unofficial]. Unlike pure object-order parallel rendering methods that require transmitting large raw data chunks or complex intermediate structures, Visapult uses a slab-based decomposition where each process renders a subdomain into a 2D image, which is then transmitted and assembled by a viewer using IBR techniques [S1][S2, unofficial]. This approach reduces the viewer-side data load to $O(n^2)$ relative to the raw volume data size of $O(n^3)$, allowing software-only graphics systems to handle the final compositing without being overwhelmed [S1].

## How it works
Visapult operates as a three-component pipeline: a raw data source, an MPI-based back end, and a viewer [S2, unofficial]. The system relies on a custom TCP-based protocol over striped sockets for network communication [S1].

### Inputs and Outputs
*   **Input:** Raw scientific volume data (potentially stored on remote supercomputers or clusters) and a viewpoint specification [S1][S2, unofficial].
*   **Output:** A single composite 3D visualization rendered on the client workstation [S1][S2, unofficial].

### Data Structures
*   **Volume Data:** Partitioned into slabs based on spatial decomposition [S1].
*   **Image Tiles:** 2D images generated by each back-end process, corresponding to the rendered slab [S1].
*   **Scene Graph:** A structure on the viewer side that holds the 2D images as textures mapped onto static geometry [S1][S2, unofficial].
*   **Synchronization Primitives:** Semaphores are used for scene graph access control to manage asynchronous updates [S1].

### Algorithm Steps
1.  **Data Partitioning:** The back end receives the raw volume data. The volume is domain-decomposed into smaller units (slabs) [S2, unofficial].
2.  **Parallel Rendering:** Each back-end process reads its assigned slab of data in parallel [S1]. The process performs software volume rendering on this subset to produce a single 2D image [S1][S2, unofficial].
3.  **Image Transmission:** The resulting 2D images are transmitted over the network to the viewer [S1].
4.  **Viewer Assembly (IBR):** The viewer receives the images and inserts them into the scene graph as 2D textures [S1].
5.  **Compositing:** The viewer texture-maps these images onto static geometry and renders them using OpenGL to composite them into the final scene [S2, unofficial].

### Pseudocode
The following pseudocode describes the asynchronous, multithreaded architecture of Visapult. It separates the back-end rendering logic from the viewer assembly logic.

```python
# Global State
scene_graph = SceneGraph()
semaphore = Semaphore(1) # For scene graph access control
network_protocol = CustomTCPOverStripedSockets()

class BackEndProcess:
    def __init__(self, data_source, slab_id, total_slabs):
        self.data_source = data_source
        self.slab_id = slab_id
        self.total_slabs = total_slabs

    def run(self):
        # 1. Read data in parallel
        # Data is partitioned amongst back-end processors using slab-based decomposition
        slab_data = self.data_source.read_slab(self.slab_id)
        
        # 2. Perform software volume rendering on the subset
        # Each processor performs volume rendering on some subset of the data
        image = software_volume_render(slab_data)
        
        # 3. Transmit image to viewer
        # The resulting image is transmitted over the network to a peer receiver
        network_protocol.send(image)

class ViewerThread:
    def __init__(self, back_end_count):
        self.back_end_count = back_end_count
        self.received_images = {}
        # One thread dedicated to receiving data
        self.receiver_thread = Thread(target=self.receive_data_loop)
        self.receiver_thread.start()

    def receive_data_loop(self):
        for i in range(self.back_end_count):
            # Receive image from specific back-end process
            image = network_protocol.receive()
            
            # 4. Insert into scene graph as 2D texture
            # Except for a small amount of scene graph access control with semaphores,
            # I/O and rendering occur in an asynchronous fashion
            with semaphore:
                scene_graph.add_texture(i, image)

class InteractiveRendererThread:
    def run(self):
        # One thread dedicated to interactive rendering
        while True:
            # 5. Render scene graph using OpenGL
            # The viewer texture maps the images onto static geometry and renders them
            # using OpenGL to composite them into a single scene
            current_viewpoint = get_user_viewpoint()
            render_opengl(scene_graph, current_viewpoint)

# Main Execution
# Visapult is composed of three components: a raw data source, a viewer, and an MPI-based back end
data_source = RawDataSource()
back_end_processes = []
for i in range(num_processors):
    be = BackEndProcess(data_source, i, num_processors)
    back_end_processes.append(Thread(target=be.run))
    back_end_processes[-1].start()

viewer = ViewerThread(num_processors)
renderer = InteractiveRendererThread()
renderer.start()
```

### Parameters and Edge Cases
*   **Network Protocol:** Custom TCP-based protocol over striped sockets [S1].
*   **Data Source:** Can be local or remote; may utilize the LBL DPSS (Data Parallel Storage System) as a cache for datasets too large for local workstations [S1][S2, unofficial].
*   **Axis Switching:** When the model is rotated off-axis, visual artifacts can appear. Disabling axis-switching within Visapult prevents viewing slices along unintended axes (e.g., X-axis) [S1].
*   **Fidelity vs. Bandwidth:** The system has parameters to reduce I/O utilization to fit within network-imposed limits, but this requires a trade-off in visual fidelity [S2, unofficial].

## Subtopics

### [Overlapped Visapult Back End](20721-overlapped-visapult-back-end.md)
A variant that overlaps volume data loading and rendering within a single distributed processing element (PE) to hide I/O latency. It uses a detached reader thread and SystemV shared memory semaphores to decouple data transfer from rendering, avoiding large data block transmission between MPI processes in favor of shared memory within a single node.

## Operating characteristics
*   **Network Efficiency:** The system achieves 88-98% of maximum theoretical available bandwidth on multi-gigabit WANs using connectionless protocols [S2, unofficial].
*   **Scalability:** Relatively little communication is required between back-end processes, so the system scales very well to large numbers of processors [S2, unofficial].
*   **Performance Bottleneck:** Effective performance is network-I/O bound unless network communications are extremely efficient [S2, unofficial].
*   **Data Load Reduction:** The amount of viewer-side data to be rendered is $O(n^2)$, whereas the size of the raw volume data is $O(n^3)$ [S1]. This allows software-only graphics systems to handle the load without being overwhelmed.
*   **Strengths:** Enables interactive visualization of terabyte-scale datasets over WANs; decouples interactivity on the desktop from network latencies; leverages hardware-accelerated rendering on low-cost client workstations [S2, unofficial].
*   **Limitations:** Requires efficient network I/O; visual fidelity may need to be reduced to fit within bandwidth limits; potential CPU contention on single-CPU nodes if using the overlapped back-end variant [S1][S2, unofficial].

## Background
Visapult was developed by the NERSC/LBNL Visualization group to address "Grand Challenge" problems in data management and analysis, where growth in supercomputing storage capabilities outpaced Moore's law [S2, unofficial]. It was presented in publications related to the use of high-speed WANs and network data caches for remote visualization [S1][S2, unofficial]. The system was applied in case studies involving ultra-high performance distributed visualization, such as studying gravitational waveforms of colliding black holes using Cactus-enabled physics simulations [S2, unofficial]. It represents a high-performance extension to the IBRAVR algorithm described in previous literature [S2, unofficial].
