# MPI Collective Noncontiguous Read for Octree Data
Also called: MPI-IO Collective Read for Octree Blocks, Single Collective and Noncontiguous Read (MPI-IO)

## Overview
This method is a parallel I/O strategy for reading large volume datasets stored as hexahedral cell data reconstructed from node data based on octree blocks [S1]. It uses MPI-IO collective operations to allow input processors to fetch roughly equal numbers of cells from disk simultaneously [S1]. It sets itself apart from independent reading strategies by relying on `MPI_FILE_READ_ALL` to handle the noncontiguous nature of octree block data, thereby avoiding the need for post-read merging of scattered data chunks at the rendering stage [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A dataset consisting of node data and octree structure data represented as 1D arrays [S1]. The data is distributed across $m$ input processors [S1].
*   **Output:** Each input processor holds a subset of the current time step's cell data to be distributed among the rendering processors [S1].

**Data Structures:**
*   **Octree Data:** Represented as 1D arrays containing node information and structural hierarchy [S1].
*   **Cell Data:** Hexahedral cells reconstructed from the node data [S1].
*   **Derived Data Type:** An MPI datatype created to describe the noncontiguous memory layout of the specific octree block data to be read [S1].

**Steps:**
1.  **Grouping:** Group cell data according to the octree data structure and the load balancing strategy [S1].
2.  **Merging Octree Data:** Merge octree data for each rendering processor to avoid duplicating node data across input processors [S1].
3.  **Derive Data Type:** Each input processor uses `MPI_TYPE_CREATE_INDEXED_BLOCK` to derive a data type from the octree data [S1]. The derived data type describes one reading pattern [S1].
4.  **Set View:** Use `MPI_FILE_SET_VIEW` to set the derived data type as the reading pattern for the current input processor [S1].
5.  **Collective Read:** Use `MPI_FILE_READ_ALL` to collectively read the data along with the other input processors [S1].

**Pseudocode:**
```python
# Helper definitions for MPI-IO operations
def MPI_TYPE_CREATE_INDEXED_BLOCK(blocklengths, indices, basic_type):
    """Creates an indexed datatype describing a noncontiguous memory layout."""
    return DerivedDatatype(blocklengths, indices, basic_type)

def MPI_TYPE_COMMIT(datatype):
    """Finalizes the datatype for use in I/O operations."""
    pass

def MPI_FILE_SET_VIEW(file_handle, disp, etype, filetype, order):
    """Sets the file view for collective I/O on the given file handle."""
    pass

def MPI_FILE_READ_ALL(file_handle, buf, count, datatype, status):
    """Collective read across all input processors."""
    pass

def MPI_TYPE_FREE(datatype):
    """Releases resources for the datatype."""
    pass

def collective_noncontiguous_read(file_handle, octree_data, m, processor_file_offset):
    # Step 1 & 2: Grouping and merging are handled by application logic prior to I/O.
    # octree_data is merged per rendering processor to avoid duplication [S1].

    # Step 3: Derive data type
    # Compute block lengths and offsets from the merged octree structure
    octree_block_lengths = [len(block.nodes) for block in octree_data.blocks]
    octree_block_offsets = [block.node_offset for block in octree_data.blocks]
    derived_type = MPI_TYPE_CREATE_INDEXED_BLOCK(octree_block_lengths, octree_block_offsets, 'float')
    MPI_TYPE_COMMIT(derived_type)

    # Step 4: Set view
    MPI_FILE_SET_VIEW(file_handle, processor_file_offset, 'float', derived_type, 'native')

    # Step 5: Collective read
    total_elements = sum(octree_block_lengths)
    cell_data = [0.0] * total_elements
    MPI_FILE_READ_ALL(file_handle, cell_data, total_elements, 'float', 'ignore')

    # Cleanup
    MPI_TYPE_FREE(derived_type)
    return cell_data
```

**Parameters and Edge Cases:**
*   **$m$ (Input Processors):** The number of processors performing the I/O [S1].
*   **Precision:** Not given in the sources.

## Subtopics

### MPI Independent Contiguous Read
An alternative file reading strategy where each input processor independently reads a contiguous chunk ($m_1$) of node data, then scans octree data to create a mapping to local node data, forwarding both to rendering processors [S1]. Rendering processors merge incoming data [S1]. Steps: 1. Each input processor independently reads a contiguous chunk ($m_1$) of node data [S1]. 2. Each input processor scans octree data to create a mapping between local node data and octree blocks [S1]. 3. Each input processor forwards node data and the map to rendering processors according to load balancing [S1]. 4. Each rendering processor merges incoming data to form complete local octree blocks of data [S1]. No inter-processor communication is needed for merging [S1]. This strategy is superior if the overhead of collective I/O becomes too high [S1].

## Operating characteristics
*   **Time Complexity:** The collective read (`MPI_FILE_READ_ALL`) scales with the number of input processors $m$ [S1].
*   **Memory Complexity:** Memory usage is proportional to the size of the cell data subset held by each input processor [S1].
*   **Measured Performance:** Tested on LeMieux, an HP/Compaq AlphaServer with 3,000 processors, visualizing 100 million hexahedral elements (400 MB per time step) [S1]. The method was evaluated with 64 rendering processors and a 512×512 image size [S1].
*   **Strengths:** Efficient for large datasets where collective I/O is supported and beneficial [S1].
*   **Limitations:** Relies on MPI-IO support [S1].
*   **When to Use:** When the dataset is large and the file system supports efficient collective I/O [S1].
*   **When Not to Use:** When the overhead of collective I/O is too high, in which case the Independent Contiguous Read variant is preferred [S1].

## Background
This method was developed as part of a parallel volume rendering system for large time-varying volume data [S1]. It was presented in the context of visualizing ground motion simulation data [S1]. The work was conducted by researchers associated with the Pittsburgh Supercomputing System [S1].
