# MPI Master Node Parallel Rendering Workflow

Also called: MPI Image Assembly, Master-Slave Volume Rendering

## Overview
This method implements a master-slave parallel volume rendering architecture where a single master node coordinates the spawning of slave processes, distributes rendering parameters, and assembles the final image from per-slice fragments [S1, unofficial]. It is distinguished from sibling methods like [MPI Parallel Slice-Based Volume Rendering](3827-mpi-parallel-slice-based-volume-rendering.md) by explicitly handling domain decomposition and image concatenation within a pre-defined master-slave workflow abstraction, rather than embedding the logic within the rendering loop itself [S1, unofficial].

## How it works
**Inputs and Outputs:**
- **Inputs:** Command-line arguments for `width`, `height`, `slave_size`, `thread_nums`, and `vifo_path` (volume data path) [S1, unofficial].
- **Outputs:** A JPEG-encoded image file written to disk [S1, unofficial].

**Data Structures:**
- `ibuf`: A 2D array of type `char` with layout `ibuf[slave_size][ibuf_size]`, where `ibuf_size` is calculated as $\lceil \text{height} / \text{slave\_size} \rceil \times \text{width} \times 3$ [S1, unofficial]. This buffer stores the raw RGB pixel data received from each slave [S1, unofficial].
- `slave_request`: An array of `MPI_Request` objects of size `slave_size` for non-blocking receives [S1, unofficial].
- `msg_buf`: A character buffer of size `MSG_BUF_SIZE` used for control messages [S1, unofficial].

**Steps:**
1. **Initialization and Spawning:** Parse command-line arguments to extract volume dimensions, slave count, and file path [S1, unofficial]. Construct a message string containing dimensions, brick sizes, bounding box, `mmu_ratio`, and file path [S1, unofficial]. Spawn `slave_size` slave processes using `MPI_Comm_spawn` with the command `./VolumeRendererServer_slave` [S1, unofficial]. Send the transfer function data to all slaves via `send_tf1d` [S1, unofficial].
2. **Buffer Allocation and Setup:** Calculate `ibuf_size` using the formula: $\text{ibuf\_size} = \lceil \frac{\text{height}}{\text{slave\_size}} \rceil \times \text{width} \times 3$ [S1, unofficial]. Allocate `ibuf[slave_size][ibuf_size]` and `slave_request[slave_size]` [S1, unofficial]. Set up a TCP acceptor on a designated `PORT` [S1, unofficial].
3. **Rendering Loop:** Iterate `image_nums` times (default 5) [S1, unofficial]. Accept a TCP connection [S1, unofficial]. Read `MSG_BUF_SIZE` bytes from the socket [S1, unofficial]. Broadcast `msg_buf` to all slaves via `MPI_Send` [S1, unofficial]. Record start time $t_1$ [S1, unofficial]. Issue non-blocking receives for each slave $i$ (from $0$ to `slave_size`-1) into `ibuf[i]` [S1, unofficial]. Wait for all receives to complete using `MPI_Waitall` [S1, unofficial]. Record end time $t_2$ [S1, unofficial]. Print rendering time $t_2 - t_1$ [S1, unofficial].
4. **Image Assembly:** Initialize `dst_base` pointer to the start of the final image buffer `ibuf_dst` (size `height * width * 3`) [S1, unofficial]. Iterate `row` from $0$ to `height`-1: determine the slave responsible for this row via $\text{slave\_no} = \text{row} \pmod{\text{slave\_size}}$ and $\text{slave\_row} = \lfloor \text{row} / \text{slave\_size} \rfloor$ [S1, unofficial]. Copy `width * 3` bytes from `ibuf[slave_no]` at offset `slave_row * width * 3` to `dst_base` [S1, unofficial]. Advance `dst_base` by `width * 3` bytes [S1, unofficial].
5. **Output:** Encode the assembled `ibuf_dst` to JPEG format [S1, unofficial]. Write the JPEG size and buffer to a socket or write directly to disk as shown in `write_image_disk` [S1, unofficial]. Close connections and finalize MPI [S1, unofficial].

**Pseudocode:**
```python
def master_render_workflow(width, height, slave_size, thread_nums, vifo_path):
    # 1. Initialization
    slave_comm = MPI_Comm_spawn("./VolumeRendererServer_slave", slave_size)
    send_tf1d(volume_data, slave_comm)

    # 2. Buffer setup
    ibuf_size = math.ceil(height / slave_size) * width * 3
    ibuf = [[0] * ibuf_size for _ in range(slave_size)]
    slave_request = [None] * slave_size

    # 3. Rendering loop
    for image_num in range(image_nums):
        accept_tcp_connection()
        msg_buf = read_socket(MSG_BUF_SIZE)
        MPI_Send(msg_buf, dest=MPI_ANY_SOURCE, tag=0, comm=slave_comm)
        t1 = MPI_Wtime()

        for i in range(slave_size):
            MPI_Irecv(ibuf[i], ibuf_size, MPI_CHAR, source=i, tag=i, comm=slave_comm, request=slave_request[i])

        MPI_Waitall(slave_request)
        t2 = MPI_Wtime()
        print(t2 - t1)

    # 4. Assembly
    dst_base = bytearray(height * width * 3)
    for row in range(height):
        slave_no = row % slave_size
        slave_row = row // slave_size
        src_offset = slave_row * width * 3
        dst_offset = row * width * 3
        dst_base[dst_offset:dst_offset + width * 3] = ibuf[slave_no][src_offset:src_offset + width * 3]

    # 5. Output
    encode_to_jpeg(dst_base)
    write_to_socket_or_disk()
    close_connections()
    MPI_Finalize()
```

**Pitfalls:**
- The image assembly assumes a round-robin row distribution across slaves [S1, unofficial]. If `height` is not divisible by `slave_size`, the last rows are distributed unevenly, but the modulo and division logic handles this correctly by assigning remaining rows to the first few slaves in the round-robin sequence [S1, unofficial].

## Subtopics

### [MPI Master-Slave Octree Volume Rendering](2744-mpi-master-slave-octree-volume-rendering.md)
Uses spatial octree encoding to partition hexahedral elements, allowing efficient traversal of empty space and one-time distribution of the octree subtree structure. Chosen when hierarchical empty-space traversal is required over uniform blocks.

### [MPI Parallel Slice-Based Volume Rendering](3827-mpi-parallel-slice-based-volume-rendering.md)
Decomposes the volume along the slicing axis (typically Z) among processes, handling domain decomposition and image concatenation within the rendering loop itself, operating on uniform slice blocks rather than hierarchical structures. Chosen when explicit in-loop decomposition logic is preferred over a pre-defined master-slave abstraction.

## Operating characteristics
- **Time Complexity:** Not given in the sources.
- **Memory Complexity:** Not given in the sources.
- **Strengths:** Simple master-slave abstraction; explicit control over parameter distribution; handles uneven row distributions gracefully [S1, unofficial].
- **Limitations:** Master node becomes a bottleneck for image assembly and control message broadcasting; TCP/MPI hybrid communication may introduce overhead [S1, unofficial].
