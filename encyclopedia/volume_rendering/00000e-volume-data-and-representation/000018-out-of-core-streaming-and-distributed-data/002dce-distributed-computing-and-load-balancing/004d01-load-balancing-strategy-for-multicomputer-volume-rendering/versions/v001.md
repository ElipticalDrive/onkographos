# Load Balancing Strategy for Multicomputer Volume Rendering

Also called: Dynamic tile assignments, Preferred tile-node pairing

## Overview
This method minimizes the maximum completion time (makespan) of distributed volume rendering tasks across identical nodes by using predicted rendering times to guide task assignment [S1, unofficial]. It sets itself apart from static distribution methods by dynamically assigning tasks based on computational cost estimates, while explicitly optimizing for data locality through preferred tile-node pairing [S1, unofficial][S2, unofficial].

## How it works
**Inputs and Outputs**
*   **Inputs**: A set of visualization tasks $V$, where each task $v$ is defined by volume data, camera pose, and transfer function. A set of $N$ identical computing nodes. Predicted rendering times $t(v)$ for each task.
*   **Outputs**: An assignment map $A: N \rightarrow V$ mapping nodes to tasks, and the resulting rendered images.

**Data Structures**
*   **Task List**: A list of tasks $V$, each containing metadata (volume ID, pose ID, transfer function ID) and a predicted time $t(v)$.
*   **Node State**: For each node $n \in N$, a current load accumulator $L_n$ initialized to 0.

**Numbered Steps**
1.  **Estimate Rendering Time**: Calculate the predicted rendering time $t(v)$ for every task $v \in V$. This prediction is typically derived from a learning-based model or historical data [S1, unofficial].
2.  **Sort Tasks**: Sort the set of tasks $V$ in descending order of their estimated rendering times $t(v)$ [S1, unofficial].
3.  **Initialize Nodes**: Initialize the load $L_n = 0$ for all nodes $n \in N$ [S1, unofficial].
4.  **Assign Tasks**: Iterate through the sorted tasks. For each task $v$:
    a. Identify the node $n^*$ with the currently minimum total load $L_{n^*} = \min_{n \in N} L_n$ [S1, unofficial].
    b. Assign task $v$ to node $n^*$, updating the load: $L_{n^*} \leftarrow L_{n^*} + t(v)$ [S1, unofficial].
    c. Apply **Preferred Tile-Node Pairing**: If the task involves specific spatial tiles, constrain the assignment to nodes that already hold the relevant volume data or tiles to optimize data locality [S2, unofficial].
5.  **Constrain View Positions**: Ensure that the sequence of camera poses assigned to a node maintains effective load balancing, potentially restricting view positions to avoid clustering high-cost poses on single nodes [S2, unofficial].

**Formulas**
The objective is to minimize the maximum load across all nodes:
$$ \min_{A: N \rightarrow V} \left( \max_{n \in N} \sum_{v \in A(n)} t(v) \right) $$
Where:
*   $N$ is the set of nodes.
*   $V$ is the set of visualization tasks.
*   $t(v)$ is the predicted rendering time for task $v$.
*   $A(n)$ is the set of tasks assigned to node $n$.

**Parameters**
*   $N$: Number of identical machines (nodes). Typical values in experiments range from small clusters to large-scale systems [S1, unofficial].
*   $V$: Set of tasks. In the reference experiment, $V$ consisted of 384 tasks (6 time steps $\times$ 64 camera poses) [S1, unofficial].

**Edge Cases and Pitfalls**
*   **Prediction Accuracy**: If $t(v)$ is inaccurate, the load balance degrades. The method relies on high prediction accuracy to maintain low overhead [S1, unofficial].
*   **Data Locality vs. Balance**: Strict preferred tile-node pairing may force a suboptimal load balance if data distribution is uneven. A trade-off must be managed [S2, unofficial].
*   **Degenerate Input**: If all tasks have identical $t(v)$, the algorithm reduces to a round-robin distribution, which may not be optimal for data locality [S1, unofficial].

**Pseudocode**
```python
def load_balance_volume_rendering(tasks, nodes):
    """
    tasks: List of dicts with keys 'id', 'volume', 'pose', 'tf', 'predicted_time'
    nodes: List of node objects with attribute 'current_load'
    Returns: List of assignments (node_index, task_id)
    """
    # Step 1 & 2: Sort tasks by predicted time descending
    sorted_tasks = sorted(tasks, key=lambda t: t['predicted_time'], reverse=True)
    
    assignments = []
    
    # Step 3: Initialize loads (assumed done in node objects)
    
    for task in sorted_tasks:
        # Step 4a: Find node with minimum load
        min_node_idx = min(range(len(nodes)), key=lambda i: nodes[i].current_load)
        target_node = nodes[min_node_idx]
        
        # Step 4b & 4c: Assign and update load
        # Note: Preferred tile-node pairing logic would check if target_node 
        # has the required volume data. If not, it might select the next best node 
        # or trigger data transfer. For simplicity, we assume the min-load node 
        # is acceptable or that the prediction accounts for transfer cost.
        target_node.current_load += task['predicted_time']
        assignments.append((min_node_idx, task['id']))
        
    return assignments
```

## Subtopics

### Dynamic Tile Assignments
A technique where screen tiles are dynamically mapped to nodes based on current load and data availability, preventing static bottlenecks [S2, unofficial].

### Preferred Tile-Node Pairing
A strategy that binds specific spatial tiles to specific nodes to minimize data redistribution, enhancing data locality at the potential cost of perfect computational balance [S2, unofficial].

## Operating characteristics
*   **Time Complexity**: Sorting tasks takes $O(|V| \log |V|)$. Assigning tasks takes $O(|V| \log N)$ if using a priority queue for node loads, or $O(|V| \cdot N)$ if scanning for the minimum. The overall complexity is dominated by sorting and assignment [S1, unofficial].
*   **Memory Complexity**: $O(|V| + N)$ to store task predictions and node loads [S1, unofficial].
*   **Measured Performance**: In experiments with 384 tasks, ENTIRE-based prediction incurred less than 4% additional cost compared to Ground Truth (GT) predictions for large $N$, whereas Uniform assignment suffered nearly 20% overhead [S1, unofficial].
*   **Strengths**: High accuracy in balancing load when predictions are good; reduces idle time significantly compared to uniform distribution [S1, unofficial].
*   **Limitations**: Relies heavily on the accuracy of $t(v)$; prediction errors can lead to imbalance; data locality constraints may complicate assignment [S1, unofficial][S2, unofficial].
*   **When to Use**: Large-scale distributed rendering with heterogeneous or variable-cost tasks (e.g., varying camera poses or transfer functions) where prediction models are available [S1, unofficial].
*   **When Not to Use**: When prediction overhead is too high or predictions are unreliable; when data locality is not a concern and simple round-robin suffices [S1, unofficial].

## Background
This strategy is based on the ENTIRE method, which uses learning-based volume rendering time prediction to guide load balancing [S1, unofficial]. It builds on the general taxonomy of volume rendering algorithms for multicomputers, which emphasizes dynamic tile assignments and preferred tile-node pairing for effective load balancing [S2, unofficial]. The approach addresses the NP-hard nature of optimal task assignment by using the Longest Processing Time First (LPT) greedy algorithm [S1, unofficial].
