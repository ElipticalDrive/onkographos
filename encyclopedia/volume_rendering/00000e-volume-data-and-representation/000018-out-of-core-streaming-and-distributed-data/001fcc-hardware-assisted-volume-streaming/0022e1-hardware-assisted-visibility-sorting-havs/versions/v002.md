# Hardware Assisted Visibility Sorting (HAVS)

Also called: Hardware-Assisted Volume Rendering System

## Overview
Hardware Assisted Visibility Sorting (HAVS) is a hybrid volume rendering algorithm for unstructured grids that combines object-space sorting on the CPU with image-space fragment sorting on the GPU [S2, unofficial]. It solves the visibility ordering problem for arbitrary non-convex meshes without requiring topological connectivity or preprocessing, relying instead on a fixed-depth "k-buffer" to incrementally sort fragments and composite colors [S2, S3, unofficial]. Unlike [ZSWEEP](52-zsweep.md), which suffers from inefficient object-space sorting, HAVS achieves higher efficiency by shifting the bulk of sorting work to the GPU, and unlike pure ray casting, it is bounded by main memory rather than texture memory limits [S2, S3, unofficial].

## How it works
HAVS operates in two phases: object-space partial sorting on the CPU and image-space complete sorting/compositing on the GPU using a k-buffer [S2, unofficial].

### Inputs and Outputs
*   **Input:** Unstructured mesh (e.g., tetrahedral cells) defined by vertices and faces; scalar field values associated with vertices; camera parameters (ModelView, Projection matrices); transfer function (3D pre-integrated table).
*   **Output:** Final composited image in the framebuffer.

### Data Structures
*   **Face List:** A list of triangles (faces) extracted from the mesh cells. Vertices are marked as internal or boundary to handle mesh boundaries correctly [S2, unofficial].
*   **k-buffer:** A per-pixel buffer of fixed size $k$ (typically $k=6$ in the reference implementation, storing 6 entries plus the current fragment) [S2, unofficial]. Each fragment entry in the buffer stores:
    *   Scalar value ($v$)
    *   Distance to eye ($d$)
*   **Textures:**
    *   **Framebuffer (Tex 0):** 2D RGBA texture (16/32-bit float) storing accumulated color and opacity [S2, unofficial].
    *   **k-buffer Entries (Tex 1-3):** 2D textures storing the k-buffer entries. Each texture stores 2 entries (e.g., Tex 1 stores entries 1 and 2) [S2, unofficial].
    *   **Transfer Function (Tex 4):** 3D RGBA texture (8/16-bit int) of size $128^3$ [S2, unofficial].
*   **Parameters:**
    *   `mvp[4]`: 4x4 Model-View-Projection matrix [S2, unofficial].
    *   `mv[4]`: 4x4 ModelView matrix [S2, unofficial].
    *   `sz`: Scale and bias vector $\{1/p_w, 1/p_h, (1-1/z_{size})/max\_len, 1/(2 \cdot z_{size})\}$ for texture coordinate normalization [S2, unofficial].
    *   `e`: Eye position vector [S2, unofficial].

### Algorithm Steps

#### 1. Object-Space Sorting (CPU)
The CPU sorts the mesh faces to generate a nearly sorted fragment stream for the GPU [S2, unofficial].
1.  Compute the centroid for each face.
2.  Sort the faces based on centroid depth.
    *   **Method:** Use LSD radix sort and counting sort [S1].
    *   **Conversion:** Convert floating-point depth coordinates $f$ to 32-bit unsigned integers for sorting using:
        $$ f = f \times (-(f>>31)|0x80000000) $$
        where `>>` is bitwise right shift and `|` is bitwise OR [S1].
    *   **Sorting:** Divide the integers into four 8-bit blocks and use counting sort for each block [S1].
    *   **Complexity:** $O(n+k)$, where $n$ is the number of faces and $k$ is the bucket size [S1].
3.  Send the sorted faces to the GPU for rasterization [S2, unofficial].

#### 2. GPU Rasterization and Fragment Processing
The GPU rasterizes the sorted faces. For each fragment, a fragment shader performs visibility sorting using the k-buffer and composites the result [S2, unofficial].

**Vertex Program:**
1.  Transform vertex to clip coordinates:
    ```python
    oPos.x = dot(mvp[0], iPos)
    oPos.y = dot(mvp[1], iPos)
    oPos.z = dot(mvp[2], iPos)
    oPos.w = dot(mvp[3], iPos)
    ```
2.  Transform vertex to eye coordinates:
    ```python
    oTex1.x = dot(mv[0], iPos)
    oTex1.y = dot(mv[1], iPos)
    oTex1.z = dot(mv[2], iPos)
    ```
3.  Pass scalar data value:
    ```python
    oTex0 = iTex0
    ```

**Fragment Program:**
1.  **Framebuffer Lookup:** Compute texture coordinates from window position to avoid perspective interpolation errors, then lookup current framebuffer color/opacity ($c_0$) [S2, unofficial].
    ```python
    t.xy = p.xy * sz.xy
    c0 = texture2D(texture[0], t)
    ```
2.  **Early Termination:** Kill fragment if framebuffer opacity $\ge 0.99$ [S2, unofficial].
    ```python
    if (0.99 - c0.w) < 0: discard
    ```
3.  **Load k-buffer:** Load existing k-buffer entries from textures into temporaries $a_1 \dots a_6$ [S2, unofficial].
    ```python
    a1 = texture2D(texture[1], t)
    a3 = texture2D(texture[2], t)
    a5 = texture2D(texture[3], t)
    a2 = a1.zwzw
    a4 = a3.zwzw
    a6 = a5.zwzw
    ```
4.  **Compute Current Fragment Properties:** Calculate distance to eye ($d_{new}$) and scalar value ($v_{new}$) for the current fragment $a_0$ [S2, unofficial].
    ```python
    dist_sq = dot(e, e)
    d_new = rsqrt(dist_sq) * e.x # Simplified from source logic: MUL a0.y, t.x, t.y; where t.y is rsqrt
    a0.x = v.x # Scalar value
    a0.y = d_new
    ```
5.  **Find Nearest Fragment ($r_0$):** Use a sorting network to find the fragment with the minimum distance among $a_0 \dots a_6$. Store the minimum in $r_0$ and the rest in $r_1 \dots r_6$ [S2, unofficial].
    ```python
    # Example for first two entries a0, a1
    diff = a0.y - a1.y
    r1 = (diff < 0) ? a1 : a0
    r0 = (diff < 0) ? a0 : a1
    
    # Iteratively compare r0 with a2...a6 to find global minimum r0
    # and store non-minimums in r2...r6
    ```
6.  **Find Second Nearest Fragment ($r_7$):** Find the minimum distance among the remaining entries $r_1 \dots r_6$ [S2, unofficial].
    ```python
    # Iteratively find min among r1, r2, ..., r6
    r7 = min(r1.y, r2.y, ..., r6.y)
    ```
7.  **Transfer Function Lookup:** Use the scalar values ($r_0.x, r_7.x$) and distance difference ($r_7.y - r_0.y$) to lookup pre-integrated color/opacity ($c$) from the 3D texture [S2, unofficial].
    ```python
    t.x = r0.x
    t.y = r7.x
    t.z = (r7.y - r0.y) * sz.z + sz.w
    c = texture3D(texture[4], t)
    ```
8.  **Nullify Invalid Entry:** If the winning fragment's scalar value $< 0$, nullify the result [S2, unofficial].
    ```python
    c = (r0.x < 0.0) ? 0 : c
    ```
9.  **Composite:** Blend the result with the framebuffer color using front-to-back blending [S2, unofficial].
    ```python
    alpha = 1.0 - c0.w
    result_color[0] = c * alpha + c0
    ```
10. **Write Back k-buffer:** Write the remaining $k$ fragments (excluding the one composited/deserted) back to the output buffers [S2, unofficial].
    ```python
    # Move remaining entries to output registers
    result_color[1] = r1
    result_color[2] = r3
    result_color[3] = r5
    ```

### Parameters and Edge Cases
*   **k-buffer Size:** The implementation uses $k=6$ [S2, unofficial]. Smaller $k$ increases speed but reduces precision; larger $k$ improves accuracy but increases comparison cost [S1].
*   **Perspective Interpolation:** Texture coordinates for the framebuffer lookup must be computed from the window position in the fragment shader, not interpolated, to avoid errors [S2, unofficial].
*   **Out-of-Order Fragments:** If fragments are highly out of order, the k-buffer (which only considers $k$ fragments) may produce incorrect rendering results [S1].
*   **Hardware Dependency:** Requires advanced read/write framebuffer access (e.g., ATI Draw Buffers extension), which is hardware-dependent [S3, unofficial].

## Subtopics

### [HAVS with Dynamic LOD](4110-havs-with-dynamic-lod.md)
Extends HAVS by dynamically adjusting the number of internal mesh faces rendered to maintain a target frame rate. It separates boundary and internal faces, sorts internal faces by importance, and selectively discards less important faces.

### [Optimized HAVS (Sorted k-buffer)](4735-optimized-havs-sorted-k-buffer.md)
Refines HAVS by maintaining the k-buffer in a strictly sorted state (ascending order of fragment distance). This reduces the computational cost of fragment-level visibility sorting from $2k-1$ comparisons to $k$ comparisons per fragment after the buffer is full.

## Operating characteristics
*   **Time Complexity:** Object-space sorting is $O(n+k)$ [S1]. Image-space sorting requires $2k-1$ comparisons per pixel per fragment in the unsorted k-buffer variant [S1].
*   **Memory Complexity:** Low memory overhead as it requires essentially no topological information [S2, unofficial]. Maximum data size is bounded by main memory, not texture memory [S2, unofficial].
*   **Performance:** Tested on ATI Radeon 9800 with a $512^2$ viewport and $128^3$ pre-integrated table [S2, unofficial].
    *   **GPU Only (k=2):** F117: 9.71 fps (2331K tets/sec); Fighter: 2.41 fps (3387K tets/sec) [S2, unofficial].
    *   **GPU Only (k=6):** F117: 4.42 fps (1062K tets/sec); Fighter: 1.56 fps (2190K tets/sec) [S2, unofficial].
    *   **Total (CPU+GPU, k=2):** F117: 6.8 fps; Fighter: 1.3 fps [S2, unofficial].
    *   With early ray termination and high opacity, over 6 million cells/sec were achieved on the Fighter dataset [S2, unofficial].
*   **Strengths:** Simple implementation (<200 lines of code), robust, handles arbitrary non-convex meshes, no preprocessing required, supports dynamic data and transfer function changes [S2, S3, unofficial].
*   **Limitations:** Not guaranteed to generate correct images if fragments are highly out of order; relies on unstable hardware features (read/write framebuffer) [S1][S3, unofficial].

## Background
HAVS was introduced by Steven Callahan, Milan Ikits, Joao Comba, and Claudio Silva in their 2005 thesis and subsequent publications [S2, S3, unofficial]. It was developed as a solution for interactive volume rendering of large unstructured grids, addressing the limitations of previous methods that required extensive preprocessing or connectivity information [S3, unofficial]. The method is considered a best compromise in implementation complexity, robustness, and image quality among tested GPU-based unstructured grid rendering techniques [S3, unofficial].
