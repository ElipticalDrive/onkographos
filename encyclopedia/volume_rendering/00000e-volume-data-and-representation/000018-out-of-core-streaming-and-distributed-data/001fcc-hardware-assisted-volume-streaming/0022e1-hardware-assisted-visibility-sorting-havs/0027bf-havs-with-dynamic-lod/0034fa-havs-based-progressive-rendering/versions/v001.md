# HAVS-based Progressive Rendering

Also called: Progressive Volume Rendering, Progressive Volume Rendering of Unstructured Grids

## Overview
HAVS-based Progressive Rendering is a level-of-detail framework for the interactive exploration of tetrahedral datasets that are too large to be rendered fully using conventional approaches [S1]. It incrementally streams portions of the mesh to a hardware-assisted volume renderer, displaying approximations that increase in quality until a full-quality rendering is achieved [S1]. Unlike conventional approaches that render the full dataset, this method provides a reduced representation during interaction and incrementally refines the progressive image during idle frames [S1]. It builds on [HAVS with Dynamic LOD](4110-havs-with-dynamic-lod.md), which separates boundary and internal faces and sorts them by importance, by exploiting the HAVS mechanism of object-space and image-space sorting to maintain a lightweight image representation between rendering steps [S1].

## How it works
The algorithm operates by maintaining state in GPU memory across multiple rendering passes, reusing results from previous steps to accelerate convergence [S1].

### Inputs and Outputs
*   **Input:** A tetrahedral mesh (unstructured grid) containing boundary and internal triangles, sorted by centroid in object-space [S1].
*   **Output:** A sequence of increasingly accurate volume-rendered images, culminating in a full-quality rendering [S1].

### Data Structures
The method relies on two primary GPU-resident data structures:

1.  **K-buffer:** A fixed-size A-buffer implemented with textures, used for image-space sorting of fragments on the GPU [S1]. It stores the $k$ closest fragments to the viewpoint for each pixel.
2.  **Off-screen Framebuffer:** A framebuffer object (FBO) used to store the composited results of the two closest fragments, including their scalar values and the distance between them [S1].

### Parameters
*   **K-buffer size:** Fixed size, implemented as a texture [S1].
*   **3D Pre-integrated Table:** A texture containing the volume integral used to composite fragments into the framebuffer [S1].
*   **Batch Size:** The number of internal geometry triangles rasterized in each iteration of the progression [S1].

### Algorithm Steps

1.  **Object-Space Sorting:** The triangles composing the tetrahedral mesh are sorted by their centroid and sent to the GPU [S1].
2.  **Initial Boundary Rendering:** During interaction, the boundary of the mesh is rendered. Front and back fragments of the boundary are inserted into the k-buffer [S1].
3.  **Iterative Refinement Loop:** For each iteration of the progression:
    a.  **Rasterization:** The next batch of internal geometry is rasterized [S1].
    b.  **Image-Space Sorting:** Incoming fragments are sorted into the k-buffer using the fixed-size A-buffer implementation [S1].
    c.  **Fragment Selection:** The stored k-buffer entries and incoming fragments are used to identify the two fragments closest to the viewpoint [S1].
    d.  **Compositing to Off-screen Buffer:** The two closest fragments are composited into the off-screen framebuffer using their scalar values and the distance between them [S1].
    e.  **K-buffer Update:** The front-most fragment is discarded, and the remaining fragments are stored back in the k-buffer [S1].
    f.  **Approximation Generation:** An approximation for the rasterized portion is created by compositing the off-screen framebuffer with the contribution of the gap between the front and back fragments still in the k-buffer [S1].
    g.  **Display and State Maintenance:** The approximation is displayed. The off-screen framebuffer and the k-buffer are maintained for subsequent iterations from the same view [S1].
4.  **Reset on Interaction:** If the user renews the exploration process through interaction (changes view), the off-screen framebuffer and the k-buffer are cleared, and the process begins again from step 2 [S1].

### Edge Cases and Pitfalls
*   **Interaction Reset:** If the user interacts (changes view), the incremental state becomes invalid. The off-screen framebuffer and k-buffer must be cleared and the process restarted [S1].
*   **Convergence:** The algorithm only renders each triangle in the mesh once per viewpoint, leading to an efficient LOD algorithm that quickly converges to a full-quality image [S1].

## Operating characteristics
*   **Time Complexity:** The algorithm is efficient because it renders each triangle in the mesh only once per viewpoint [S1].
*   **Memory Complexity:** It maintains only a light-weight image representation of the volume between rendering steps, keeping incremental data in GPU memory [S1].
*   **Measured Performance:** The method is capable of rendering datasets consisting of about 14 million tetrahedra (e.g., the SF1 dataset) interactively [S1].
*   **Strengths:** Provides a reduced representation during interaction and incrementally refines the progressive image during idle frames [S1]. It gives the same effect as the progressive transmission of JPEG images over the web [S1].
*   **Limitations:** Requires programmable GPU features such as Framebuffer Objects (FBOs) and Multiple Render Targets (MRTs) [S1].
*   **When to use:** Interactive exploration of large tetrahedral datasets in scientific computing domains like computational fluid dynamics and structural mechanics [S1].
*   **When not to use:** When the dataset is small enough to be rendered fully using conventional approaches [S1].

## Background
The HAVS-based Progressive Rendering technique was developed by Callahan, Bavovl, Pascucci, and Silva [S1]. It builds upon the Hardware-Assisted Visibility Sorting (HAVS) algorithm by Callahan et al. (2005), which pushed much of the direct volume rendering burden to the GPU and was capable of rendering datasets of about one million tetrahedra interactively [S1]. The progressive renderer was introduced in 2006 to handle larger datasets that required level-of-detail approaches for exploration [S1]. It is used in scientific computing domains such as computational fluid dynamics and structural mechanics [S1].
