# I/O-Conscious Volume Rendering

Also called: Data-driven block-based volume rendering, I/O-Conscious Ray Casting, Prefetching ray casting, data-driven ray casting, out-of-core rendering, program-driven approach

## Overview
I/O-Conscious Volume Rendering is an out-of-core rendering technique that minimizes end-to-end rendering time by overlapping disk I/O with rendering computation using a data-driven execution model where data blocks are accessed as indivisible units [S1]. It sets itself apart from its siblings, such as [Out-of-core brick-based volume rendering](6288-out-of-core-brick-based-volume-rendering.md), by tightly integrating algorithm-specific prefetching with the ray casting traversal to ensure data is available exactly when needed, rather than relying on general-purpose disk prefetching or fixed memory budgets [S1]. Unlike program-driven approaches where the renderer controls the I/O, this method uses a dedicated prefetch thread that mirrors the ray caster's traversal logic to hide latency [S1].

## How it works
**Inputs and Outputs:**
- **Input:** A volumetric dataset stored on disk, decomposed into cubic macro-voxels of size $B \times B \times B$ [S1].
- **Output:** A 2D image (e.g., $128 \times 128$ pixels) [S1].

**Data Structures:**
- **Macro-voxel:** A cubic block of voxels stored contiguously on disk and fetched as an indivisible unit [S1].
- **Ray Group:** A set of rays cast concurrently to exploit processing parallelism [S1].
- **Thread State:** Two threads are used: one for ray casting and one for prefetching, chosen to minimize context switch overhead compared to processes [S1].

**Parameters:**
- **Macro-voxel size ($B$):** The dimension of the cubic block. $B$ must be chosen such that prefetching rays spaced by $B$ pixels cover the entire volume [S1].
- **Ray group size:** Tested sizes include 128, 64, 32, and 16. Larger groups improve performance by increasing parallelism, outweighing state maintenance overhead [S1].
- **Sampling distance:** Fixed at 1 along rays for both rendering and prefetching [S1].

**Numbered Steps:**
1. **Decomposition:** Decompose the volumetric dataset into 3D sub-cubes (macro-voxels) of size $B \times B \times B$, stored contiguously on disk [S1].
2. **Thread Initialization:** Initialize two threads: a rendering thread and a prefetching thread [S1].
3. **Ray Group Casting:** Cast a group of rays concurrently rather than one at a time to enable processing parallelism and reduce CPU idle time [S1].
4. **Prefetching Traversal:** The prefetching module executes the same traversal code as the ray casting module to determine which macro-voxels to fetch [S1].
5. **Macro-voxel Check:** During prefetching traversal, check if each sample on each ray steps into a new macro-voxel [S1].
6. **Disk Fetch:** If a new macro-voxel is entered, fetch it from disk; otherwise, continue sampling along the ray [S1].
7. **Rendering:** The rendering thread samples the volume using the fetched macro-voxels, ensuring a data block is completed exercised once brought into memory to achieve ideal overlap [S1].
8. **Optimization:** Approximate floating-point computation with integer arithmetic without causing perceptible loss of quality [S1].
9. **Interpolation Optimization:** Speed up address generation for the eight voxels used in tri-linear interpolation by exploiting fixed relationships among them [S1].
10. **Vectorization:** Employ MMX instructions to execute multiple instructions simultaneously during computation [S1].

**Formulas:**
- **Minimum End-to-End Time:**
  $$ T_{\text{min}} = T_{\text{fetch\_first}} + T_{\text{memory\_resident}} $$
  Where $T_{\text{fetch\_first}}$ is the time to fetch the first macro-voxel and $T_{\text{memory\_resident}}$ is the time to render the dataset when completely memory-resident [S1].
- **Prefetching Ray Spacing:**
  Ray origins for prefetching must be at most $B$ pixels apart on the image plane, with sampling distance along rays remaining at 1, to ensure all macro-voxels are covered [S1].

```python
def get_macro_voxel_id(x, y, z, B):

    return (x // B, y // B, z // B)

def tri_linear_interpolation(v000, v100, v010, v110, v001, v101, v011, v111, fx, fy, fz):
    """
    Perform tri-linear interpolation.
    [G] Integer arithmetic approximation exploits fixed relationships among 8 voxels
    """
    return (v000 * (1-fx)*(1-fy)*(1-fz) + v100 * fx*(1-fy)*(1-fz) +
            v010 * (1-fx)*fy*(1-fz) + v110 * fx*fy*(1-fz) +
            v001 * (1-fx)*(1-fy)*fz + v101 * fx*(1-fy)*fz +
            v011 * (1-fx)*fy*fz + v111 * fx*fy*fz)

def ray_march(o, d, step, B, Dx, Dy, Dz, cache):
    """March a single ray, fetching macro-voxels and compositing."""
    color, opacity = 0.0, 0.0
    x, y, z = o
    current_mv = get_macro_voxel_id(int(x), int(y), int(z), B)
    if current_mv not in cache:
        cache[current_mv] = fetch_macro_voxel(current_mv)

    while x >= 0 and x < Dx and y >= 0 and y < Dy and z >= 0 and z < Dz:
        fx, fy, fz = x % 1, y % 1, z % 1
        # [G] Extract 8 neighboring voxel values from the loaded macro-voxel cache
        voxels = [cache[current_mv][i] for i in range(8)]
        value = tri_linear_interpolation(*voxels, fx, fy, fz)
        
        alpha = 1.0 - value
        color += value * (1.0 - opacity)
        opacity += alpha * (1.0 - opacity)
        if opacity >= 1.0:
            break

        x += d[0] * step
        y += d[1] * step
        z += d[2] * step

        next_mv = get_macro_voxel_id(int(x), int(y), int(z), B)
        if next_mv != current_mv:
            if next_mv not in cache:
                cache[next_mv] = fetch_macro_voxel(next_mv)
            current_mv = next_mv
    return color, opacity

def prefetch_thread(B, W, H, Dx, Dy, Dz, cache):
    """Prefetch thread: casts rays spaced by B pixels with step 1 to detect boundaries."""
    for y in range(0, H, B):
        for x in range(0, W, B):
            # [G] Standard ray setup for pixel (x, y)
            o = (x, y, 0.0)
            d = (0.0, 0.0, 1.0)
            ray_march(o, d, 1.0, B, Dx, Dy, Dz, cache)

def render_thread(B, W, H, Dx, Dy, Dz, cache):
    """Rendering thread: casts all rays, compositing as it marches."""
    for y in range(H):
        for x in range(W):
            # [G] Standard ray setup for pixel (x, y)
            o = (x, y, 0.0)
            d = (0.0, 0.0, 1.0)
            ray_march(o, d, 1.0, B, Dx, Dy, Dz, cache)

def main():
    B = 16
    W, H = 128, 128
    Dx, Dy, Dz = 128, 128, 128
    cache = {}
    
    # Prefetch thread precedes rendering thread for each macro-voxel accessed
    prefetcher = threading.Thread(target=prefetch_thread, args=(B, W, H, Dx, Dy, Dz, cache))
    renderer = threading.Thread(target=render_thread, args=(B, W, H, Dx, Dy, Dz, cache))
    
    prefetcher.start()
    renderer.start()
    
    renderer.join()
    prefetcher.join()
```

## Operating characteristics
- **Time Complexity:** The minimum end-to-end time is $T_{\text{min}} = T_{\text{fetch\_first}} + T_{\text{memory\_resident}}$ [S1].
- **Memory Complexity:** Insensitive to main memory size. Rendering times for a $256 \times 256 \times 256$ dataset varied by less than 8% when memory capacity increased from 1MB to 16MB [S1].
- **Measured Performance:** On a 300-MHz Pentium-II, rendering a $128 \times 128 \times 128$ dataset to a $128 \times 128$ image took an average of 1 second end-to-end (including disk I/O), compared to 0.68-1.0 seconds for memory-resident rendering and 0.33 seconds for disk retrieval [S1].
- **Scaling:** Performance gain from parallelism outweighs state maintenance overhead as ray group size increases. Tested sizes: 128, 64, 32, 16 [S1].
- **Strengths:** Hides most disk I/O delay; insensitive to main memory size; data-driven approach is faster than program-driven approach (e.g., 1.10s vs 1.25s for $128^3$ data) [S1].
- **Limitations:** Achieving ideal overlap between disk I/O and rendering computation is difficult in practice; implementation must ensure a data block is completed exercised once brought into memory [S1].
- **When to use:** When rendering large volumetric datasets that do not fit in main memory on hardware with slow disk I/O, and when end-to-end latency is critical [S1].
- **When not to use:** When datasets fit entirely in memory, or when compression is preferred over computation optimization [S1].

## Background
- **Origin:** Developed by researchers investigating volume rendering on desktop personal workstations [S1].
- **Paper:** "I/O-Conscious Volume Rendering" (2001) [S1].
- **History:** The work re-examined implementation strategies of ray casting, taking into account both computation and I/O overheads. It proposed a data-driven execution model to achieve maximum overlap between rendering computation and disk I/O [S1].
- **Usage:** Used for out-of-core visualization of large-scale volumetric datasets where traditional in-core assumptions fail [S1].
