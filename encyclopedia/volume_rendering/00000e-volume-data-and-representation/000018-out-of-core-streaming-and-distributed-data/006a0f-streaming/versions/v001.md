# Streaming
Also called: Data Streaming, On-theory Processing

## Overview
Streaming is a technique where volume data is processed as it becomes available, circumventing the need for the entire dataset to be resident in memory or fully loaded before visualization begins [S1]. It enables the rendering of incomplete data and supports interactive visualization of extreme-scale datasets [S1]. Unlike pure on-demand processing which typically relies on a pull model, streaming supports both pull and push dataflow models [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A stream of data chunks or tiles from storage/network; a rendering pipeline configuration.
*   **Output:** Partial or complete rendered images; updated visualization state.

**Data Structures:**
*   **Stream Buffer:** A temporary storage structure holding the current chunk of data being processed. The layout depends on the underlying data representation (e.g., bricked, grid-based).
*   **Ghost Data:** Boundary voxels or cells generated on-the-fly to ensure correct interpolation and compositing at chunk boundaries [S1].

**Steps:**
1.  **Data Acquisition:** Retrieve the next chunk of data from the source. This can be initiated by the renderer requesting data (pull model) or by the source pushing data to the renderer (push model) [S1].
2.  **Preprocessing (Optional):** Perform on-the-fly operations such as segmentation, registration, or multi-resolution hierarchy computation if required by the visualization task [S1].
3.  **Boundary Handling:** Generate ghost data for the current chunk to handle interpolation across chunk boundaries [S1].
4.  **Rendering:** Render the current chunk. If using composite volume rendering, this may produce a partial image or a set of depth-sorted primitives.
5.  **Compositing:** Combine the result of the current chunk with the accumulated image state. In distributed or streaming contexts, this may involve sending partial images for final compositing [S1].
6.  **Repeat:** Continue to step 1 until the dataset is exhausted or the user interaction stops the stream.

**Pseudocode:**
```python
def streaming_render(stream_source, renderer, compositor):
    """
    Renders a volume by streaming data chunks.
    
    Args:
        stream_source: An object providing next_chunk() method.
        renderer: An object with render_chunk(chunk, ghost_data) method.
        compositor: An object with add_result(partial_image) method.
    """
    while True:
        try:
            # Step 1: Data Acquisition (Pull or Push)
            # If push model, stream_source might call a callback instead.
            chunk = stream_source.next_chunk()
            if chunk is None:
                break
                
            # Step 2: Preprocessing (Optional)
            # chunk = preprocess(chunk) # e.g., segmentation, registration
            
            # Step 3: Boundary Handling
            ghost_data = create_ghost_data(chunk)
            
            # Step 4: Rendering
            partial_image = renderer.render_chunk(chunk, ghost_data)
            
            # Step 5: Compositing
            compositor.add_result(partial_image)
            
        except StopIteration:
            break
```

**Parameters:**
*   **Chunk Size:** Not given in the sources. Determined by memory constraints and I/O bandwidth.
*   **Model Type:** Pull or Push [S1].

**Edge Cases and Pitfalls:**
*   **Latency:** In pull models, network or disk latency can stall the rendering pipeline.
*   **Boundary Artifacts:** Incorrect generation of ghost data leads to visual discontinuities at chunk boundaries [S1].
*   **Ordering:** For correct alpha compositing, the order in which chunks are rendered and composited must respect the view-dependent depth order [G].

## Subtopics

### Out-Of-Core Techniques
Techniques that partition data and/or computation to process subsets independently, lowering in-core memory requirements by using out-of-core, in-situ, or distributed processing strategies [S1]. These methods include algorithms for accessing and prefetching data, creating on-the-fly ghost data for bricked representations, and computing multi-resolution hierarchies or other processing tasks like segmentation, PDE solvers, image registration, or level set computation [S1].

## Operating characteristics
*   **Memory Usage:** Significantly lower than in-core methods, as only a subset of the data resides in memory at any time [S1].
*   **Latency:** Initial latency may be low as rendering can start immediately with the first chunk, but overall frame rate depends on data delivery speed [S1].
*   **Scalability:** Scales well with data size, limited primarily by I/O bandwidth and processing power per chunk [S1].
*   **Strengths:** Enables visualization of datasets larger than available memory; supports interactive exploration of extreme-scale data [S1].
*   **Limitations:** Performance is sensitive to I/O bottlenecks; complex to implement correctly, especially regarding boundary handling and compositing order [S1].

## Background
Streaming approaches have been used to analyze connectivity in large-scale electron microscopy volumes, such as in the ConnectomeExplorer framework [S1]. Hadwiger et al. described a system for streaming extreme-scale electron microscopy data for interactive visualization, later extended to include on-the-fly registration and multi-volume visualization of segmented data [S1]. Vo et al. presented a dataflow visualization system built on VTK that implements push and pull models for streaming [S1]. Silva et al. provided a comprehensive overview of out-of-core methods for visualization and graphics, including streaming techniques [S1].
