# Sub-volume partitioning


## Overview
Sub-volume partitioning is a parallel volume rendering technique that divides a volumetric dataset into smaller sub-volumes, each processed by a dedicated processing pipeline, to enable hardware-accelerated ray casting on custom computing machines [S1]. It addresses the scalability limits of single-pipeline architectures by distributing the voxel processing load across multiple units, combining intermediate results to yield the final image [S1]. Unlike beam partitioning, which adjusts beam widths to processing elements, sub-volume partitioning subdivides the volume into spatial cubes, requiring complex synchronization for non-orthogonal viewing directions [S1].

## How it works
**Inputs and Outputs**
*   **Input:** A volumetric dataset of size $n^3$, a viewing direction, a compositing order (front-to-back or back-to-front), and a sub-volume resolution $p$ where $p < n$ [S1].
*   **Output:** The final composited image [S1].

**Data Structures**
*   **Sub-volume:** A cubic block of resolution $p \times p \times p$ (or $p \times p \times n$ depending on partitioning axis, though S1 implies cubic processing units) [S1].
*   **Intermediate Result Buffer:** A memory buffer storing the accumulated color and opacity (transmittance) for rays that traverse sub-volume boundaries [S1].
*   **Overlap Region:** Additional voxels at the boundaries of each sub-volume to support tri-linear interpolation and gradient estimation [S1].

**Steps**
1.  **Partitioning:** Divide the volumetric dataset of size $n^3$ into smaller sub-volumes of resolution $p$ [S1].
2.  **Overlap Addition:** Expand each sub-volume at its boundaries to include neighboring voxars required for tri-linear interpolation and gradient estimation. This overlap is necessary because the voxel neighborhood at a sub-volume boundary cannot be provided by the sub-volume itself [S1].
3.  **Ordering:** Determine the processing order of the sub-volumes based on the viewing direction and the compositing order (front-to-back or back-to-front). This ensures that rays crossing sub-volume boundaries access the intermediate compositing results in the correct sequence [S1].
4.  **Processing:** Each sub-volume is processed by $p$ pipelines (or a dedicated set of processing elements) [S1].
5.  **Compositing:** The images generated from each sub-volume are combined. For rays crossing boundaries, the intermediate results stored in the buffer are accessed during the processing of the subsequent sub-volume [S1].
6.  **Final Image:** The combined results from all sub-volumes yield the final image [S1].

**Formulas**
*   **Memory Overhead:** The percentage of memory overhead due to boundary-voxel overlap for a $128^3$ dataset is given in [S1]:
    *   $p=8$: 61%
    *   $p=16$: 34%
    *   $p=32$: 18%
    *   $p=64$: 10%
    *   Formula not explicitly provided, but values are empirical [S1].

**Parameters**
*   **Sub-volume resolution ($p$):** Must be less than the dataset size $n$ [S1]. Typical values tested: 8, 16, 32, 64 [S1].
*   **Dataset size ($n$):** Example given: $n=128$ [S1].

**Edge Cases and Pitfalls**
*   **Non-orthogonal Viewing Directions:** Rays may traverse multiple sub-volumes, requiring the storage and access of intermediate compositing results [S1].
*   **Global Connectivity:** Accessing the buffer of intermediate compositing results requires global connectivity between processing pipelines, which can be a hardware limitation [S1].
*   **Memory Overhead:** The overlap required for interpolation leads to substantial memory overhead and higher execution time [S1].
*   **Boundary Conditions:** Tri-linear interpolation and gradient estimation at sub-volume boundaries are the primary drivers for the overlap requirement [S1].

## Operating characteristics
*   **Time Complexity:** Not explicitly given, but execution time is affected by memory overhead and the number of sub-volumes [S1].
*   **Memory Complexity:** Substantial memory overhead due to boundary-voxel overlap. For a $128^3$ dataset, overhead ranges from 61% ($p=8$) to 10% ($p=64$) [S1].
*   **Hardware Requirements:** Requires global connectivity between processing pipelines to access intermediate compositing result buffers [S1]. This limits the maximum size of datasets on hardware with limited connectivity [S1].
*   **Strengths:** Enables parallel processing of large datasets on custom computing machines like Teramac [S1].
*   **Limitations:** High memory overhead, need for global connectivity, and complexity in handling non-orthogonal viewing directions [S1].
*   **When to Use:** When rendering large datasets on hardware with multiple processing elements and sufficient global connectivity [S1].
*   **When Not to Use:** When memory bandwidth is limited or global connectivity is not available [S1].

## Background
Sub-volume partitioning was developed for implementations on the Teramac Custom Computing Machine [S1]. It was one of two approaches (the other being beam partitioning) designed to render datasets of size $n^3$ with $p < n$ processing elements [S1]. The first prototype implementation on Teramac revealed problems with voxel neighborhood overlap and intermediate result buffering, leading to the development of beam partitioning [S1].
