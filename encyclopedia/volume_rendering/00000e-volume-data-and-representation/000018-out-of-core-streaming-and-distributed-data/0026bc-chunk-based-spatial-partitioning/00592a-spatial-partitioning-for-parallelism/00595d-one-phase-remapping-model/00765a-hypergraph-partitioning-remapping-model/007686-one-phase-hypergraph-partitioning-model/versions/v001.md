# One-Phase Hypergraph Partitioning Model

Also called: Hypergraph Partitioning Model (HP), Hypergraph Partitioning Remapping Model with Special Vertices, One-Phase Hypergraph Partitioning (IIP)

## Overview
The One-Phase Hypergraph Partitioning (IIP) model is a remapping strategy for image-space (IS) parallel volume rendering that simultaneously determines screen-processor and data-processor mappings [S1, unofficial]. It solves the remapping problem by representing the interaction between object-space (OS) clusters and image-space processors as a hypergraph, minimizing communication volume and load imbalance in a single partitioning phase [S1, unofficial]. Unlike the standard Hypergraph Partitioning Remapping Model which may require separate phases or heuristics for processor assignment, IIP integrates processor assignment directly into the partitioning constraints using special vertices [S1, unofficial]. It builds on [Hypergraph Partitioning Remapping Model](23463-hypergraph-partitioning-remapping-model.md).

## How it works
**Inputs:**
*   $V$: Set of vertices representing data clusters in object-space.
*   $N$: Set of nets representing interactions between clusters.
*   $K$: Number of processors.
*   $W_v$: Weight of vertex $v \in V$ (representing computational cost or data size).
*   Initial cluster-processor mapping: A function indicating which processor initially holds each cluster.

**Outputs:**
*   Partition $\Pi$: A mapping of vertices to parts (processors).
*   Cluster mapping $M_C$: A function mapping each cluster to its target processor.
*   Communication pattern: Derived from $M_C$.

**Data Structures:**
*   Hypergraph $H' = (V', N')$:
    *   $V'$: Vertex set. Contains original vertices $V$ and $K$ special vertices $P = \{p_1, p_2, ..., p_K\}$.
    *   $N'$: Net set. Contains original nets $N$ and new "pin" nets connecting special vertices to original nets.
    *   Weights: Original vertices have weight $W_v$. Special vertices $p_i$ have weight 0.
    *   Pins: A pin exists between special vertex $p_i$ and net $n_j$ if the cluster represented by $n_j$ initially resides in the memory of processor $P_i$ [S1, unofficial].

**Steps:**

1.  **Construct Hypergraph $H'$:**
    *   Initialize $V' = V \cup P$, where $P$ is the set of $K$ special vertices.
    *   Initialize $N' = N$.
    *   For each net $n_j \in N$ and each special vertex $p_i \in P$:
        *   If the cluster represented by $n_j$ is initially located on processor $P_i$ (based on initial cluster-processor mapping), add a pin between $p_i$ and $n_j$ [S1, unofficial].

2.  **Apply Constraints:**
    *   Add a constraint that each special vertex $p_i$ must be assigned to exactly one part (processor) [S1, unofficial].

3.  **Coarsening Phase:**
    *   Perform hypergraph coarsening (e.g., using PaToLL) with modifications:
        *   Prevent matching two special vertices together.
        *   Allow a special vertex to be grouped with ordinary vertices into a supernode.
        *   If a supernode contains a special vertex, the supernode inherits the special vertex status [S1, unofficial].

4.  **Initial Partitioning Phase:**
    *   Assign each special vertex $p_i$ to a distinct part (processor) $S_i$.
    *   Lock these special vertices in their assigned parts. They cannot move during subsequent uncoarsening and refinement phases [S1, unofficial].

5.  **Uncoarsening and Refinement:**
    *   Uncoarsen the hypergraph back to its original size.
    *   Perform refinement to minimize cut size and balance load, respecting the locked positions of special vertices [S1, unofficial].

6.  **Calculate Cluster Mapping $M_C$:**
    *   After partitioning, determine the mapping of clusters to processors using Equation 5.2 from [S1, unofficial]:
        $$ M_C(c_j) = P_i \iff p_i \in S_k \text{ and } c_j \in S_k $$
        Where $c_j$ is a cluster (vertex), $S_k$ is a part (set of vertices), and $p_i$ is the special vertex assigned to $S_k$. Essentially, a cluster is mapped to the processor corresponding to the special vertex in the same partition [S1, unofficial].

7.  **Generate Mappings:**
    *   Use $M_C$ to determine the final screen-processor and data-processor mappings [S1, unofficial].

**Pseudocode:**

```python
def one_phase_hypergraph_partitioning(vertices, nets, initial_ownership, num_processors):
    """
    vertices: List of cluster objects with weight and initial_owner_id
    nets: List of net objects connecting clusters
    initial_ownership: Dict mapping cluster_id to processor_id
    num_processors: K, integer
    Returns: partition_map (cluster_id -> processor_id)
    """
    # Step 1: Construct Hypergraph H'
    # V' includes original vertices and K special vertices
    special_vertices = [f"special_{i}" for i in range(num_processors)]
    all_vertices = vertices + special_vertices
    
    # N' includes original nets and new pin nets
    # A pin net connects a special vertex to an original net if the cluster 
    # in that net is initially owned by the processor represented by the special vertex
    new_pin_nets = []
    for net in nets:
        # Identify the primary cluster or representative for the net
        # Assuming net has a reference to a cluster_id
        cluster_id = net.representative_cluster_id
        owner_id = initial_ownership.get(cluster_id)
        
        if owner_id is not None and 0 <= owner_id < num_processors:
            # Create a pin between the special vertex for this processor and the net
            pin_net = {
                'type': 'pin',
                'special_vertex': special_vertices[owner_id],
                'original_net': net
            }
            new_pin_nets.append(pin_net)
    
    all_nets = nets + new_pin_nets
    
    # Step 2: Define Constraints
    # Each special vertex must be in a unique part
    constraints = {
        'special_vertex_unique_assignment': True
    }
    
    # Step 3: Coarsening with Modifications
    # Use a modified PaToLL-like coarsener
    # Prevent matching two special vertices
    # Allow special vertex to merge with ordinary vertices
    # Supernode inherits special status if it contains a special vertex
    coarse_graph = coarsen(all_vertices, all_nets, constraints)
    
    # Step 4: Initial Partitioning
    # Assign each special vertex to a distinct part and lock it
    # This assumes the coarsener supports locked vertices
    initial_assignment = {}
    for i in range(num_processors):
        initial_assignment[special_vertices[i]] = i
        # Lock the vertex in part i
        lock_vertex(special_vertices[i], part=i)
    
    # Perform initial partitioning on the coarse graph
    # The coarsener must respect the locked special vertices
    partition = initial_partition(coarse_graph, initial_assignment)
    
    # Step 5: Uncoarsening and Refinement
    # Uncoarsen back to original graph size
    # Refine to minimize cut size and balance load
    # Special vertices remain locked
    refined_partition = uncoarsen_and_refine(partition, coarse_graph, all_vertices, all_nets)
    
    # Step 6: Calculate Cluster Mapping M_C
    # Equation 5.2: M_C(c_j) = P_i iff p_i is in the same part as c_j
    # Map each original cluster to the processor ID of the special vertex in its part
    cluster_to_processor = {}
    
    # Build a map from part_id to special_vertex_id
    part_to_special = {}
    for vertex in refined_partition.vertices:
        if vertex in special_vertices:
            part_id = refined_partition.get_part(vertex)
            part_to_special[part_id] = vertex
            
    # Map each original cluster to the processor ID
    for cluster in vertices:
        part_id = refined_partition.get_part(cluster)
        special_vertex = part_to_special.get(part_id)
        if special_vertex:
            processor_id = int(special_vertex.split('_')[1])
            cluster_to_processor[cluster.id] = processor_id
        else:
            # Fallback: if a part has no special vertex (should not happen with K parts and K special vertices)
            # Assign to a default processor or handle error
            cluster_to_processor[cluster.id] = 0
            
    return cluster_to_processor
```

**Parameters:**
*   $K$ (Number of processors): Tested values {4, 8, 12, 16, 20, 24} [S1, unofficial].
*   Image Sizes: Tested values 400x400, 800x800, 1200x1200 [S1, unofficial].

**Pitfalls:**
*   The hypergraph partitioning phase is run sequentially by each processor, which limits speedup and can result in poor efficiency for very small image sizes where the sequential time $T_{seq}$ approaches the parallel time $T_{par}$ [S1, unofficial].
*   Initial data distribution affects the topology of the hypergraph and thus the partitioning quality and communication cost [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The partitioning phase is sequential, creating a bottleneck. Efficiency decreases for small image sizes due to this sequential overhead [S1, unofficial].
*   **Memory Complexity:** Not given in the sources.
*   **Performance:** At 24 processors, IIP performs approximately 30% less communication than Jagged Partitioning (JP) [S1, unofficial]. On average, IIP produces 10% less communication overhead at comparable load imbalance values for small-scale datasets [S1, unofficial]. IIP incurs slightly less preprocessing overhead than JP [S1, unofficial].
*   **Strengths:** Minimizes communication volume effectively, especially as the number of processors increases. Provides a single-phase solution for both screen and data mapping.
*   **Limitations:** Sequential partitioning step limits scalability. Performance degrades for small image sizes.
*   **When to use:** Large image and data sizes where communication minimization is critical.
*   **When not to use:** Very small image sizes where the sequential overhead dominates, or when strict real-time constraints prevent sequential partitioning.

## Background
The One-Phase Hypergraph Partitioning model was proposed as a solution to the remapping problem in image-space parallel volume rendering [S1, unofficial]. It was developed to address the limitations of previous models like Jagged Partitioning (JP) by reducing communication volume and preprocessing overhead [S1, unofficial]. The model uses a modified version of the PaToLL hypergraph partitioning tool, employing recursive bisection due to the lack of a K-way tool at the time [S1, unofficial]. It represents the interaction between object-space and image-space as a hypergraph, with special vertices representing processors [S1, unofficial].
