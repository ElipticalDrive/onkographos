# Slice-Based Data-Space Parallel Distribution

Also called: Data-space parallelism, Slice distribution

## Overview
Slice-Based Data-Space Parallel Distribution partitions a 3D voxel dataset into contiguous 2D slices and assigns them to parallel processors to enable local processing while minimizing communication overhead [S1, unofficial]. Unlike display-space parallelism, which distributes rendering tasks across the image plane, this method distributes the source data itself, reducing memory requirements per node and leveraging the typically higher resolution in the X-Y plane for efficient loop execution [S1, unofficial]. It is a specific implementation of [Spatial Partitioning for Parallelism](16344-spatial-partitioning-for-parallelism.md) optimized for medical imaging workloads where data is naturally recorded on a slice basis.

## How it works
**Inputs:** A 3D voxel dataset $V$ of dimensions $W \times H \times D$ (width, height, depth).
**Outputs:** A composite rendered image or processed volume, generated by merging partial results from all nodes.

**Data Structures:**
Each processor node $i$ maintains a local memory buffer $L_i$ containing a subset of the global volume. The buffer layout corresponds to contiguous 2D slices. If the volume is divided among $N$ nodes, node $i$ stores slices from index $s_{start}^{(i)}$ to $s_{end}^{(i)}$.

**Steps:**
1.  **Partitioning:** The 3D volume is divided into contiguous 2D slices. The orientation is aligned with the X-Y planes, assuming $W, H \ge D$ or that X-Y resolution is higher [S1, unofficial].
2.  **Assignment:** Each slice (or group of slices) is assigned to a specific processor node. The assignment ensures that geometrically neighboring slices are often assigned to geometrically neighboring processors to facilitate efficient merging [S1, unofficial].
3.  **Local Storage:** The assigned slices are stored in the private memory of each node. This creates a "data-segment" which is a unique part of the complete voxel set [S1, unofficial].
4.  **Local Processing:** Each node processes its local slices independently. This includes visualization, merging, or other image processing operations. The processing loops run over the X and Y dimensions, maximizing cache locality and loop efficiency [S1, unofficial].
5.  **Merging:** Partial results (sub-images or intermediate volumes) from all nodes are combined. The merging is performed on a "back-to-front" basis. If neighboring processors hold geometrically neighboring slice data, the partial result from one node is added to the partial result of its direct neighbor [S1, unofficial].

**Formulas:**
Let $N$ be the number of processors. The number of slices per processor $S_p$ is approximately:
$$
S_p = \lfloor D / N \rfloor
$$
The local memory requirement $M_i$ for node $i$ is:
$$
M_i = S_p \times W \times H \times B
$$
where $B$ is the bytes per voxel.

**Parameters:**
*   **Slice Orientation:** X-Y planes. This choice maximizes the size of data segments in two directions, allowing longer loop runs for X-Y processing [S1, unofficial].
*   **Merging Order:** Back-to-front. This preserves the geometric order of the dataset and allows incremental addition of partial results [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Merging Overhead:** The requirement to merge partial results introduces communication overhead, which is the primary disadvantage compared to pure display-space parallelism [S1, unofficial].
*   **Redundant Computation:** Nodes may compute voxel contributions that are not visible in the final image (e.g., occluded voxels), leading to wasted computation [S1, unofficial].
*   **Load Balancing:** Load balancing is effective only if the voxel data sizes assigned to each node are equal. Uneven distribution of slices or variable data density can skew performance [S1, unofficial].
*   **Boundary Artifacts:** While the parent method mentions overlap for chunk-based partitioning, slice-based distribution typically relies on contiguous assignment. If convolution or filtering is required across slice boundaries, additional overlap handling (see [Distributed Convolution with Data Overlap](20361-distributed-convolution-with-data-overlap.md)) is necessary [S1, unofficial].

## Subtopics

### [Distributed Convolution with Data Overlap](20361-distributed-convolution-with-data-overlap.md)
Extends slice-based distribution to handle local spatial filtering by maintaining redundant copies of boundary data (overlap) on each node, minimizing network traffic for operations that depend on neighboring voxels across slice boundaries.

## Operating characteristics
*   **Memory:** Lower memory requirement per node compared to display-space parallelism, as each node only stores a fraction of the total voxel data [S1, unofficial].
*   **Communication:** Reduced communication overhead during the processing phase compared to display-space parallelism, as nodes do not need to exchange pixel data for every view. However, merging overhead exists [S1, unofficial].
*   **Performance:** Fast access to local voxel data. Efficient for generating a large number of views from a single dataset because the data distribution cost is amortized [S1, unofficial].
*   **Strengths:** Good load balancing when data sizes are equal; efficient 2D processing loops; natural fit for slice-based storage formats.
*   **Limitations:** Merging overhead; computation of occluded voxels; requires careful handling of boundary conditions for cross-slice operations.
*   **When to use:** When generating multiple views from a single large volume dataset, or when the hardware architecture favors local data access and 2D processing loops.
*   **When not to use:** When memory per node is extremely constrained and the volume is too large to fit even a slice subset, or when real-time single-view rendering with minimal latency is critical and merging overhead is prohibitive.

## Background
This method was implemented in a voxel-processor system using Transputers, as described in a TNO report [S1, unofficial]. The decision to use slice-based distribution over block distribution or display-space parallelism was driven by the need to maximize loop efficiency in X-Y processing, the 2D nature of many image processing algorithms, and the fact that voxel data is often recorded on a slice basis [S1, unofficial]. The system was designed to farm out work to processors in a network, leveraging the lower communication needs of data-space parallelism for multi-view generation [S1, unofficial].
