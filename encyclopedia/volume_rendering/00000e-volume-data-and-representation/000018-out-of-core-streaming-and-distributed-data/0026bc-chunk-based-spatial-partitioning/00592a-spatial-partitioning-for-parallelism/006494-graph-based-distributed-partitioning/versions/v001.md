# Graph-Based Distributed Partitioning

Also called: METIS Bipartite Graph Partitioning, METIS graph partitioning, Offline METIS Bipartite Graph Partitioning, Offline Point Placement via Bipartite Graph Partitioning, Offline graph partitioning, Point placement

## Overview
Graph-Based Distributed Partitioning is an offline strategy for assigning 3D points (such as 3D Gaussian splats) to distributed GPUs or machines by modeling data access patterns as a bipartite graph and partitioning it to minimize cross-partition communication edges while balancing memory usage [S1, unofficial]. Unlike geometric proximity methods (e.g., KD-trees, k-means) that ignore camera view dependency, this method explicitly accounts for the fact that points far apart in 3D space may be visible to the same camera, thereby reducing the need for inter-GPU communication during rendering [S1, unofficial]. It serves as the core locality-aware distribution framework for point assignment in large-scale distributed rendering systems [S1, unofficial].

## How it works
The method assigns points to compute devices by constructing a bipartite graph representing the relationship between points and camera views (images), then using a graph partitioning library (METIS) to solve the assignment problem.

### Inputs and Outputs
*   **Inputs**:
    *   A set of $N$ 3D points (e.g., Gaussian splats).
    *   A set of $D$ camera views (images or patches) with defined frustums.
    *   The number of target partitions (machines/GPUs), $P$.
    *   A coarsening parameter $G$ (points per group).
*   **Outputs**:
    *   An assignment map mapping each point group to a specific partition index $p \in \{0, \dots, P-1\}$.

### Data Structures
1.  **Point Groups**: The raw points are grouped into larger units to reduce graph size. Each group contains $G$ points.
2.  **Bipartite Graph $G_{bip} = (V, E)$**:
    *   **Vertices $V$**:
        *   $V_P$: Set of point group vertices. Size $|V_P| = N/G$.
        *   $V_I$: Set of image/view vertices. Size $|V_I| = D$.
        *   Total vertices $|V| = N/G + D$. In practice, this is reduced to tens of thousands [S1, unofficial].
    *   **Edges $E$**: An edge exists between point group vertex $i$ and image vertex $j$ if any point in group $i$ lies within the frustum of image $j$.
    *   **Vertex Weights**: Weights are assigned to point group vertices to enforce load balancing (equal memory usage across partitions) [S1, unofficial].

### Steps
1.  **Sort Points**: Sort all $N$ points in the point cloud using Z-order curves (Morton order) to preserve spatial locality, ensuring points close in 3D space remain close in the linear ordering [S1, unofficial].
2.  **Coarsen (Grouping)**: Group each contiguous block of $G$ points along the Z-ordered list into a single point group. Each group is represented by a single vertex in the bipartite graph [S1, unofficial].
3.  **Construct Bipartite Graph**:
    *   Create vertices for each point group and each image/view.
    *   For each image $j$, determine which point groups fall within its frustum.
    *   Add edges between the corresponding point group vertices and image vertex $j$ [S1, unofficial].
4.  **Assign Weights**: Assign weights to the point group vertices. These weights incorporate load balancing constraints to ensure that each partition receives roughly equal memory/compute load [S1, unofficial].
5.  **Partition Graph**:
    *   Use the METIS library to partition the bipartite graph into $P$ partitions [S1, unofficial].
    *   **Hierarchical Partitioning**: To account for non-uniform communication costs (inter-node vs. intra-node), partitioning is performed hierarchically:
        1.  First, partition the point cloud across machines (one partition per machine).
        2.  Then, partition each machine’s assigned points among its local GPUs [S1, unofficial].
    *   The objective is to minimize the number of cut edges (cross-partition edges) while maintaining balanced partition sizes [S1, unofficial].

def graph_based_distributed_partitioning(points, images, num_partitions, G):
    """
    Assigns points to partitions using bipartite graph partitioning.
    
    Args:
        points: List of 3D point objects.
        images: List of image/view objects with frustum definitions.
        num_partitions: Number of target GPUs/machines.
        G: Number of points per group for coarsening.
        
    Returns:
        assignment: Dictionary mapping point index to partition index.
    """
    # Step 1: Sort points using Z-order curve
    # Z-order preserves spatial locality
    sorted_indices = compute_z_order_sort(points)
    sorted_points = [points[i] for i in sorted_indices]
    
    # Step 2: Coarsen into groups
    # Group contiguous blocks of G points
    num_groups = len(sorted_points) // G
    point_groups = []
    for i in range(num_groups):
        group_points = sorted_points[i * G : (i + 1) * G]
        point_groups.append(group_points)
        
    # Step 3: Construct Bipartite Graph
    # Vertices: Point groups (0 to num_groups-1) and Images (num_groups to num_groups + len(images)-1)
    graph = BipartiteGraph()
    
    # Add point group vertices
    for i in range(num_groups):
        # Weight assignment for load balancing [S1, unofficial]
        # Weight could be proportional to number of points or estimated memory usage
        weight = G 
        graph.add_vertex("point", i, weight=weight)
        
    # Add image vertices
    for j, image in enumerate(images):
        graph.add_vertex("image", num_groups + j, weight=1)
        
    # Add edges based on frustum intersection
    for j, image in enumerate(images):
        image_vertex_id = num_groups + j
        for i, group in enumerate(point_groups):
            # Check if any point in the group is in the image's frustum
            if any(point_in_frustum(point, image.frustum) for point in group):
                graph.add_edge(i, image_vertex_id)
                
    # Step 4: Partition using METIS
    # METIS minimizes edge cuts while balancing vertex weights
    # Hierarchical partitioning is handled by METIS or by calling METIS twice
    # First partition across machines, then intra-node [S1, unofficial]
    
    # For simplicity, assuming single-level partitioning for the core algorithm
    # METIS returns a partition array where partition[i] is the partition ID for vertex i
    partition_map = metis_partition(graph, num_partitions)
    
    # Step 5: Map back to individual points
    assignment = {}

            # We need to track original indices
            original_idx = sorted_indices[point_groups.index(group) * G + group.index(point)]
            assignment[original_idx] = partition_id
            
    return assignment

### Parameters
*   **$G$ (Group Size)**: The number of points per group for coarsening. Typical value: 1024–4096 [S1, unofficial].
    *   **Trade-off**: Coarser grouping (higher $G$) reduces graph size and speeds up partitioning but compromises placement quality (spatial locality) [S1, unofficial].
*   **METIS Parameters**: Standard METIS partitioning parameters (e.g., number of partitions, balance factor) are used. The graph size after coarsening is typically tens of thousands of vertices ($N/G + D$) [S1, unofficial].

### Edge Cases and Pitfalls
*   **Partitioning Time**: Partitioning time varies by scene complexity. Scenes with complex topologies and large view frustums (e.g., Campus, BigCity Street) take longer to partition [S1, unofficial].
*   **Graph Construction Cost**: Determining frustum intersections for all point groups and images can be expensive if not optimized, though the coarsening step mitigates this [S1, unofficial].
*   **Hierarchical Overhead**: Performing partitioning in two stages (inter-node then intra-node) adds complexity but is necessary to minimize slow inter-node communication [S1, unofficial].

## Operating characteristics
*   **Time Complexity**: The graph partitioning step using METIS is efficient due to coarsening. The graph size is reduced to $N/G + D$ vertices, typically tens of thousands [S1, unofficial].
*   **Measured Performance**: METIS partitioning time ranges from 3.4s to 46.9s across various scenes, which is less than 1% of total training time [S1, unofficial].
*   **Memory Complexity**: The bipartite graph requires memory proportional to the number of point groups and images. With $G=1024-4096$, the graph is small enough to fit in CPU memory easily [S1, unofficial].
*   **Strengths**:
    *   Minimizes cross-partition communication by accounting for camera view dependency [S1, unofficial].
    *   Outperforms geometric proximity methods (KD-trees, k-means) and manual heuristics for irregular point clouds [S1, unofficial].
    *   Scalable to large-scale scenes with hundreds of millions of points due to coarsening [S1, unofficial].
*   **Limitations**:
    *   Offline process: Requires prior knowledge of camera views or an iterative approach.
    *   Sensitive to scene topology: Complex scenes with large frustums increase partitioning time [S1, unofficial].
*   **When to Use**: Large-scale distributed volume rendering or 3D Gaussian splatting where communication overhead is a bottleneck and camera views are known or predictable.
*   **When Not to Use**: Real-time online partitioning without pre-computation, or scenes with very few points where overhead dominates.

## Background
Graph-Based Distributed Partitioning was introduced in the context of scaling point-based differentiable rendering (specifically 3D Gaussian Splatting) for large-scale reconstruction. The method is a core component of the "Gaian" system, which uses offline METIS bipartite graph partitioning combined with online linear sum assignment to reduce communication overhead [S1, unofficial]. It addresses the limitations of prior partitioning techniques (manual heuristics, KD-trees, k-means) that fail to account for camera view dependency in irregular point cloud structures [S1, unofficial].
