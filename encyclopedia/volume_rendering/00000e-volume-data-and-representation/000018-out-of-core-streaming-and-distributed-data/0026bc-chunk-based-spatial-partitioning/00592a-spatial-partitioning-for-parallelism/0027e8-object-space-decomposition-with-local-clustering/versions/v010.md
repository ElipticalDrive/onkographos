# Object-space decomposition with local clustering

Also called: Graph-based clustering for unstructured grids, Local clustering via MeTiS

## Overview
Object-space decomposition with local clustering is a parallel volume rendering technique for unstructured grids that partitions data into clusters to enable independent, simultaneous rendering of subvolumes [S1, unofficial]. It differs from sibling methods like [MPI-based Volume Partitioning](1093-mpi-based-volume-partitioning.md) by using a view-independent preprocessing phase to create static clusters, which are then dynamically remapped based on the viewing parameters to handle load imbalance and communication overhead [S1, unofficial]. Unlike [ShardedVolume](12593-shardedvolume.md), which typically relies on fixed spatial sharding, this method constructs a visualization graph and uses graph partitioning (MeTiS) to group topologically connected cells, ensuring that clusters maintain internal connectivity while minimizing inter-cluster communication during the rendering pipeline [S1, unofficial].

## How it works
The method operates in two main phases: a view-independent preprocessing phase (local clustering) and a view-dependent remapping phase. This article details the preprocessing phase, which establishes the static cluster structure.

### Inputs and Outputs
**Inputs:**
- Unstructured grid data (tetrahedral cells) distributed across $A$ processors $P_1, \dots, P_A$.
- Global visualization graph $Q_v = (N_v, E_v)$, where nodes represent cells and edges represent face-sharing neighbors [S1, unofficial].

**Outputs:**
- A global clustering solution $C = [C_1, C_2, \dots, C_K]$, where $K$ is the total number of clusters [S1, unofficial].
- Local data structures (`ClusterData`, `ClusterMapArray`) on each processor.
- A contracted visualization graph $Q_c = (N_c, E_c)$ and migration cost function $T_c$ [S1, unofficial].

### Data Structures

**1. CellArray and VertexArray**
- **VertexArray**: Stores vertex coordinates for the cluster. Uses local indexing within the cluster.
- **CellArray**: Stores tetrahedral cells for the cluster. Uses local indexing.
- **Connectivity Modification**: In the `CellArray`, the four global neighbor-cell identifiers for each cell are replaced by a pair: `(global_cluster_id, local_index)`. This maintains connectivity between cell-clusters within the local indexing scheme [S1, unofficial].

**2. ClusterData**
- Maintained by each processor for each of its local cell-clusters.
- **Components**:
  - `VertexArray`: Local vertex data.
  - `CellArray`: Local cell data with modified neighbor pointers.
  - `TotalVolume`: The sum of the volumes (in World Space Coordinates, WSC) of all constituent cells in the cluster [S1, unofficial].

**3. ClusterMapArray**
- Maintained by each processor. Holds two components for *every* cell-cluster in the global environment:
  1. `Mapping`: The current mapping function $M_e$, indicating which processor owns the cluster.
  2. `Pointer`: A pointer to the `ClusterData` structure if the cluster is local to the processor; otherwise null or empty [S1, unofficial].

### Algorithm Steps

1. **Construct Local Visualization Graph**:
   Each processor $P_k$ constructs its local view-independent visualization graph $Q_{local}^k$. This graph is the subgraph of the global graph $Q_v$ induced by the node subset corresponding to the local cells of $P_k$ [S1, unofficial].

2. **Local Clustering via MeTiS**:
   Each processor $P_k$ concurrently performs a $q_k$-way clustering of its local graph $Q_{local}^k$ using the MeTiS graph partitioning library [S1, unofficial].
   - **Parameter Selection**: The local number of resulting clusters $q_k$ is selected to be proportional to the total node weight in its local graph. Specifically:
     $$ \sum_{k=1}^{A} q_k = c \cdot a $$
     where $c$ and $a$ are constants chosen to balance the workload and reduce variations in cluster weights for efficient remapping [S1, unofficial].
   - **Global Solution**: The $A$ local $q_k$-way partitions effectively constitute a global $K$-way clustering solution $C = [C_1, \dots, C_K]$ [S1, unofficial].

3. **Assign Global Identifiers and Mapping**:
   - Each cluster in the global environment is assigned a unique global cluster identifier.
   - The global mapping function $M_e$ is determined, assigning each cluster to a specific processor [S1, unofficial].

4. **Build Local ClusterData**:
   - For each local cell-cluster, construct the `ClusterData` structure.
   - Populate `VertexArray` and `CellArray` with local cell and vertex data.
   - Replace global neighbor-cell IDs in `CellArray` with `(global_cluster_id, local_index)` pairs to preserve inter-cluster connectivity [S1, unofficial].
   - Compute `TotalVolume` for the cluster as the sum of the volumes of its constituent cells [S1, unofficial].

5. **Build ClusterMapArray**:
   - Initialize `ClusterMapArray` on each processor.
   - For each global cluster, store its current mapping $M_e$ and a pointer to its `ClusterData` if local [S1, unofficial].

6. **Construct Contracted Visualization Graph $Q_c$**:
   - The contracted graph $Q_c = (N_c, E_c)$ is the contraction of the global graph according to the clustering solution $C$.
   - **Nodes**: Each node in $N_c$ represents a cluster $C_i$.
   - **Edges**: An edge $C_{ij}$ exists between clusters $C_i$ and $C_j$ if they share at least one face through two neighbor cells in those clusters [S1, unofficial].
   - **Topology**: The topology of $Q_c$ is view-independent and identical to the view-independent contracted graph. It differs from view-dependent graphs only in node and edge weights [S1, unofficial].
   - Each processor constructs its local portion of $Q_c$ [S1, unofficial].

7. **Broadcast Global Graph and Migration Costs**:
   - **Graph Replication**: Perform an all-to-all broadcast to replicate the global graph $Q_c$ in each processor. This allows each processor to compute view-dependent weights locally without further communication during the remapping phase [S1, unofficial].
   - **Migration Cost Function $T_c$**:
     - The migration cost of a cell-cluster is defined as the ratio of the size of its `ClusterData` structure to the size of an individual ray-segment information.
     - Since this cost is view-independent, it is computed once.
     - Perform an all-to-all broadcast to disseminate the migration costs of all clusters to all processors, ensuring every processor knows $T_c$ for all clusters [S1, unofficial].

    Performs view-independent local clustering for a single processor.

    # Step 4: Assign Global Cluster Identifiers

    # This requires a global coordination step to ensure unique IDs across all processors.
    # Let's assume a global unique ID generator or a pre-agreed mapping scheme.
    global_cluster_ids = assign_global_ids(local_partition, processor_id, total_processors)
    
    # Step 5: Build ClusterData for each local cluster
    cluster_data_list = []
    for cluster_id in range(q_k):
        # Get local cells and vertices belonging to this cluster
        cluster_local_cells = [cell for cell, part in zip(local_cells, local_partition) if part == cluster_id]

        )

    # Holds mapping and pointer for ALL global clusters (not just local)
    # This requires knowing the mapping of all clusters.
    # In practice, this is built after global coordination.

    # Step 7: Construct Local Portion of Contracted Graph Qc
    # Nodes are local clusters. Edges exist if local clusters share a face.

                local_Qc_edges.append((current_cluster_id, neighbor_cluster_id))

        cluster_data_size = get_structure_size(cluster_data)

        migration_costs.append(cost)

### Edge Cases and Pitfalls
- **Precision**: Volume calculations must be consistent across processors to ensure accurate load balancing during the remapping phase.
- **Boundaries**: The replacement of global neighbor-cell identifiers with `(global_cluster_id, local_index)` must correctly handle cells on the boundary of the local processor's domain. If a neighbor cell is not local to the current processor, its `local_index` refers to its index within its own processor's `ClusterData`, not the current one.
- **Degenerate Input**: If a processor has no cells, $q_k$ should be 0, and no clustering operations should be performed. The global coordination must handle empty processors gracefully.
- **Graph Connectivity**: The contracted graph $Q_c$ must accurately reflect face-sharing relationships. If two clusters share multiple faces, a single edge is sufficient, but the weight (if used in remapping) might need to aggregate these connections.

## Subtopics

### [Remapping Phase](4250-remapping-phase.md)
The Remapping Phase is a view-dependent preprocessing step in chunk-based spatial partitioning for parallel volume rendering, designed to reassign data clusters to processors based on the current viewing parameters. It solves load imbalance and communication overhead when the camera changes, ensuring clusters with high interaction remain co-located. It adapts the static clustering solution from Object-space decomposition with local clustering to the current view via a dynamic graph-partitioning loop.

## Operating characteristics
- **Time Complexity**: The local clustering step uses MeTiS, which has sublinear complexity relative to the number of nodes in the local graph. The global coordination steps (broadcasts) have $O(P)$ communication complexity, where $P$ is the number of processors.
- **Memory Complexity**: Each processor stores `ClusterData` for its local clusters and a `ClusterMapArray` for all global clusters. The memory usage is proportional to the size of the unstructured grid data plus the overhead of the graph structures.
- **Measured Performance**: Not given in the sources.
- **Scaling**: The method scales well with the number of processors as long as the local clustering remains balanced. The all-to-all broadcasts can become a bottleneck for very large numbers of processors or clusters.
- **Strengths**: Reduces view-independent preprocessing overhead by performing clustering locally. The contracted graph $Q_c$ allows for efficient view-dependent remapping without reconstructing the graph topology.
- **Limitations**: The initial clustering is view-independent, which may lead to suboptimal load distribution for specific views until the remapping phase is executed. The all-to-all broadcasts require significant communication bandwidth.
- **When to Use**: Suitable for unstructured grid volume rendering where the data distribution is static but the viewing parameters change frequently, requiring dynamic load balancing.
- **When Not to Use**: Not suitable for highly dynamic data where the grid structure itself changes frequently, as the preprocessing overhead would need to be repeated.
