# Streaming Ghost Data Generation

Also called: Streaming Ghost Data, Streaming generation of ghost data for structured grids, Parallel and Streaming Generation of Ghost Data for Structured Grids, Parallel Ghost Data Generation for Structured Grids, parallel streaming ghost data algorithm

## Overview
Streaming Ghost Data Generation is an algorithm for generating ghost data (boundary values) for structured grids partitioned into blocks, enabling out-of-core processing where only one block plus edge data from previous blocks resides in memory at any time [S1, unofficial]. Unlike standard approaches that require the entire dataset or all blocks to be in memory simultaneously, this method processes blocks one by one, allowing ghost data generation and downstream computation (e.g., isocontouring) to run on far fewer processors than available for simulation [S1, unofficial]. It sets itself apart from non-streaming methods by maintaining a constant memory footprint per processor, scaling efficiently to large datasets by interleaving loading, communication, and computation [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A structured grid partitioned into $m$ blocks. The grid cells or nodes store scalar values.
*   **Output:** $m$ blocks enhanced with one layer of ghost data. The output blocks, when stripped of ghost data, cover the domain exactly but differ slightly in size from the input blocks [S1, unofficial].

**Data Structures:**
The algorithm maintains a lightweight data structure describing block adjacency. It does **not** store actual block data. For each block, it stores:
1.  **Index:** The partition index (processor ID) the block belongs to [S1, unofficial].
2.  **Receive Counter:** The number of partition edges (faces in 3D) to be received from remote neighbors [S1, unofficial].
3.  **Send Counter:** The number of partition edges to be sent to remote neighbors [S1, unofficial].
4.  **Dependency Pointer:** A pointer to another block that must be processed before this one (used to prevent deadlocks in parallel execution) [S1, unofficial].
5.  **Origin/Size:** The offset within the whole grid and the dimensions of the block [S1, unofficial].
6.  **Edge Pointers:** For each edge (2D) or face (3D), a pointer to the stored edge data if it is being kept for a future neighbor [S1, unofficial].

**Core Logic:**
Ghost data is created by declaring data along the boundaries of a block to be "ghost data," effectively shrinking the block's actual data content. This data is then used to "grow" adjacent neighbor blocks. When creating one layer of ghost data, the algorithm keeps two layers of data in memory for each edge/face:
1.  The layer declared as ghost data in the current block (which becomes actual data in the neighbor).
2.  The layer adjacent to it (which serves as ghost data for the neighbor) [S1, unofficial].

**Rules for Block Selection:**
To ensure correct data propagation without storing the whole grid, specific rules govern which block can be processed next:
*   **Edge Rule (3D):** The selected block cannot touch already processed blocks only along an edge. It must also be adjacent to at least one face incident to such an edge [S1, unofficial].
*   **Corner Rule (3D):** The selected block cannot touch already processed blocks only at a corner. It must also be adjacent to at least one face incident to such a corner [S1, unofficial].
*   **Global Travel Direction:** In parallel execution, a global direction is established for faces along partition boundaries. Blocks send data to remote neighbors "below" them and receive from neighbors "above" them. "Above" means right (1), top (3), or behind (5); "Below" means left (0), beneath (2), or front (4) [S1, unofficial]. This prevents circular dependencies [S1, unofficial].

**Single-Processor Algorithm:**
On a single processor, blocks are processed row-by-row and layer-by-row (zigzag/typewriter order) to minimize memory usage and avoid special cases [S1, unofficial].

```python
def streaming_ghost_data_single_processor(blocks, grid_reader, grid_writer):
    """
    Generates ghost data for structured grids on a single processor.
    Processes blocks row-by-row, layer-by-layer.
    """
    # Initialize adjacency structure
    adjacency = build_adjacency_structure(blocks)
    
    # Track processed blocks
    processed = set()
    
    # Track edge data in memory: key=(block_id, edge_id), value=data_array
    edge_data_in_memory = {}
    
    # Order: layer-by-layer, row-by-row
    for layer in layers:
        for row in rows:
            for block in blocks_in_layer_row(layer, row):
                # 1. Select
                if not passes_corner_rule(block, processed, adjacency):
                    continue # Should not happen in strict row-by-row order
                
                # 2. Read
                block_data = grid_reader.read(block)
                
                # 3. Grow
                for neighbor in adjacency.get_edge_neighbors(block):
                    if neighbor in processed:
                        # Absorb edge data from processed neighbor
                        edge_key = (neighbor, get_opposite_edge(block, neighbor))
                        if edge_key in edge_data_in_memory:
                            block_data = grow_block(block_data, edge_data_in_memory[edge_key], neighbor)
                            del edge_data_in_memory[edge_key]
                
                # 4. Keep
                for neighbor in adjacency.get_edge_neighbors(block):
                    if neighbor not in processed:
                        # Copy edge data for future neighbor
                        edge_key = (block, get_edge(block, neighbor))
                        # Store two layers: the boundary (ghost) and the one inside (actual for neighbor)
                        edge_data_in_memory[edge_key] = extract_edge_layers(block_data, neighbor)
                
                # 5. Write
                # Output block with ghost data
                grid_writer.write(block, block_data)
                
                # Discard original block data from memory
                del block_data
                
                # Mark as processed
                processed.add(block)
```

**Parallel Algorithm:**
In parallel execution, each processor owns a subset of blocks. Communication uses non-blocking MPI `Isend` and `Irecv` calls [S1, unofficial].

```python
def streaming_ghost_data_parallel(blocks, my_rank, num_procs, grid_reader, grid_writer, mpi_comm):
    """
    Generates ghost data for structured grids in parallel.
    Uses non-blocking MPI communication.
    """
    # Initialize adjacency structure with partition info
    adjacency = build_adjacency_structure(blocks)
    
    # Initialize counters and dependencies
    receive_counters = {b: 0 for b in blocks}
    send_counters = {b: 0 for b in blocks}
    dependency_pointers = {b: None for b in blocks}
    
    # Determine global travel direction and set counters
    for block in blocks:
        if block.owner == my_rank:
            for neighbor in adjacency.get_face_neighbors(block):
                if neighbor.owner != my_rank:
                    if is_above(block, neighbor):
                        receive_counters[block] += 1
                    else:
                        send_counters[block] += 1
                        # Post non-blocking receive for this neighbor? 
                        # Actually, we post receives for blocks we expect to receive FROM.
                        # So if neighbor is above, we receive from neighbor.
            
            # Check for deadlock conditions (corner/edge dependencies across processors)
            # If block A is corner-adjacent to remote block B, and local blocks C, D 
            # (edge-adjacent to both) wait for B, then A must wait for B.
            check_and_add_dependencies(block, adjacency, dependency_pointers)

    # Post non-blocking receives for all expected incoming edges
    requests = []
    for block in blocks:
        if block.owner == my_rank:
            for neighbor in adjacency.get_face_neighbors(block):
                if neighbor.owner != my_rank and is_above(block, neighbor):
                    # Post Irecv for edge data from neighbor
                    req = mpi_comm.Irecv(buffer, source=neighbor.owner, tag=...)
                    requests.append((req, neighbor, block))

    processed = set()
    edge_data_in_memory = {} # Local edge data
    
    while len(processed) < len(blocks):
        # 1. Receive Check
        completed = []
        for req, neighbor, waiting_block in requests:
            if req.test():
                # Update block data structure
                associate_edge(waiting_block, neighbor, req.buffer)
                mark_processed(neighbor) # Neighbor is now processed
                waiting_block.receive_counter -= 1
                completed.append((req, neighbor, waiting_block))
        
        for item in completed:
            requests.remove(item)
            
        # 2. Select
        candidate = None
        for block in blocks:
            if block.owner != my_rank:
                continue
            if block in processed:
                continue
            if block.receive_counter > 0:
                continue
            if block.dependency_pointer and block.dependency_pointer not in processed:
                continue
            if passes_corner_rule(block, processed, adjacency):
                candidate = block
                break
        
        if candidate is None:
            # Stall temporarily if no allowable blocks
            continue
            
        # 3. Read
        block_data = grid_reader.read(candidate)
        
        # 4. Grow
        for neighbor in adjacency.get_face_neighbors(candidate):
            if neighbor in processed:
                # Absorb face data from processed neighbor
                face_key = (neighbor, get_opposite_face(candidate, neighbor))
                if face_key in edge_data_in_memory:
                    block_data = grow_block(block_data, edge_data_in_memory[face_key], neighbor)
                    del edge_data_in_memory[face_key]
                elif neighbor.owner != my_rank:
                    # Receive from remote neighbor (handled by MPI)
                    # In a real implementation, this data would be in a buffer
                    pass
        
        # 5. Keep
        for neighbor in adjacency.get_face_neighbors(candidate):
            if neighbor not in processed:
                face_key = (candidate, get_face(candidate, neighbor))
                face_data = extract_face_layers(block_data, neighbor)
                
                if neighbor.owner == my_rank:
                    edge_data_in_memory[face_key] = face_data
                else:
                    # Send to remote neighbor
                    mpi_comm.Isend(face_data, dest=neighbor.owner, tag=...)
        
        # 6. Write
        grid_writer.write(candidate, block_data)
        del block_data
        processed.add(candidate)
```

**Edge Cases and Pitfalls:**
*   **Corner Duplication:** Data at the corners of a block is sometimes duplicated in two edges and stored but not used. This simplifies implementation by avoiding separate corner maintenance, though it is slightly wasteful in memory [S1, unofficial].
*   **Deadlock Prevention:** If block A is corner-adjacent to remote block B, and edge-adjacent blocks C and D (on A's processor) wait for B, processing A before B causes deadlock. Solution: Add dependency pointer from A to B; A waits for edge data from B [S1, unofficial].
*   **Stalling:** A process stalls temporarily only if there are no allowable blocks for processing because all remaining blocks are waiting for dependencies [S1, unofficial].
*   **Block-Structured/Unstructured Grids:** Cannot establish a global travel direction for faces that avoids communication and deadlocks; requires a different approach like master-slave [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The algorithm processes each block once. Communication overhead depends on the block assignment strategy. Cut-like assignments minimize dependencies and communication, leading to high efficiency (92% on 64 processors for RM8 dataset) [S1, unofficial]. Metis assignments can lead to excessive dependencies and ragged boundaries, dropping efficiency to 16% on 240 processors due to waiting time [S1, unofficial].
*   **Memory Complexity:** $O(1)$ per processor relative to total dataset size. Each processor stores only one block plus one sheet of ghost data spanning the domain (or edge/face data for neighbors) [S1, unofficial]. For the RM8 dataset, streaming uses less than 0.5 GB per node regardless of processor count, whereas non-streaming requires over 6 GB per processor [S1, unofficial].
*   **Measured Performance:** On LLNL’s ASC Prism machine (128-node Linux cluster, 16 GB RAM/node, InfiniBand), streaming ghost data generation enabled isocontouring of the 8-billion-element RM8 dataset on as few as 4 processors, compared to 64 required for non-streaming [S1, unofficial]. Execution time for isocontouring on 64 processors was 250 seconds for streaming vs. 349 seconds for non-streaming [S1, unofficial].
*   **Strengths:** Enables out-of-core processing on limited memory; reduces memory footprint significantly; allows visualization on fewer processors than simulation; integrates seamlessly with downstream computations (isocontouring, gradient calculation) [S1, unofficial].
*   **Limitations:** Implementation complexity increases with non-cut block assignments (e.g., Metis) due to the need for edge/corner rules and dependency management; random assignments may have high communication overhead despite good load balancing for some tasks [S1, unofficial].

## Background
The algorithm was introduced in the paper "Parallel and Streaming Generation of Ghost Data for Structured Grids" [S1, unofficial]. It was implemented in the VisIt visualization tool and evaluated on large-scale scientific datasets, including the Richtmyer-Meshkov instability (RM8) and Rayleigh-Taylor instability (RT27) simulations [S1, unofficial]. The method addresses the bottleneck where visualization tools require more memory than available on analysis clusters, which often have fewer processors than the simulation clusters that generated the data [S1, unofficial].
