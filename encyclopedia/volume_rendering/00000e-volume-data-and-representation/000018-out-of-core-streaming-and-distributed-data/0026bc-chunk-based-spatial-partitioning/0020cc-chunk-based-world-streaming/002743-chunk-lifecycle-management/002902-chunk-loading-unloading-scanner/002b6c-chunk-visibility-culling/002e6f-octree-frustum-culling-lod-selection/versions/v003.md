# Octree Frustum Culling & LOD Selection

Also called: CPU Frustum Culling, CPU-based Octree LOD & Frustum Culling, Octree Frustum Culling, Octree-based Visibility Culling

## Overview
This method uses an octree spatial partitioning structure to efficiently determine which chunks of a voxel world are visible within the camera's view frustum and to select the appropriate Level of Detail (LOD) for each visible chunk [S1, S2, unofficial]. It solves the problem of rendering massive voxel worlds (e.g., $256^3$ cubes) by avoiding the transfer of invisible geometry to the GPU, which would otherwise consume prohibitive amounts of VRAM (e.g., ~4.5 GB for a full $256^3$ world) [S1, unofficial]. It is distinguished from sibling methods by its explicit integration of LOD selection based on distance during the culling traversal, rather than relying solely on static distance sorting or out-of-core clipping [S2, unofficial].

## How it works
### Inputs and Outputs
**Inputs:**
*   Camera state: `cam.frustum_planes` (6 planes defining the view frustum), `cam.lod_origin` (camera position for distance calculation).
*   Chunk Set: `set` containing:
    *   `set->root`: Base chunk size in voxels.
    *   `set->max[3]`: Maximum chunk coordinates in the world.
    *   `set->max_bitw[3]`: Bit width required to index the maximum chunk coordinates.
    *   `set->gsvl[lod][x][y][z]`: Array of `GeometrySVL*` pointers for high-LOD geometry.
    *   `set->gmesh[index]`: Array of `GeometryMesh*` pointers for base-LOD geometry.
*   Current traversal coordinates: `(x, y, z)` at current `lod`.

**Outputs:**
*   Populated render queues:
    *   `queue_gsvl[0xFFFF]`: Array of `GeometrySVL*` pointers.
    *   `queue_mesh[0xFFFF]`: Array of `GeometryMesh*` pointers.
    *   `queue_misc[0xFFFF]`: Array of `uint32_t` indices.
    *   Counts: `queue_gsvl_count`, `queue_mesh_count`, `queue_misc_count`.

### Data Structures
The geometry is stored in a hierarchical manner indexed by LOD and chunk coordinates.
*   `GeometrySVL`: Struct representing a geometry object at a specific LOD. Contains a `vbo` field (boolean/pointer) indicating if valid vertex buffer data exists.
*   `GeometryMesh`: Struct representing base-level geometry. Contains a `vbo` field.
*   The index into `set->gsvl` is calculated using a flattened 3D coordinate system. The bit width for flattening depends on the current LOD and the maximum bit width of the world.

### Parameters
*   `lod`: Current level of detail (unsigned 8-bit integer).
*   `ws_root`: World space root size, calculated as `set->root << lod`.
*   `LOD_SCALE`: Distance scale factor, value `1024`.
*   `FRUSTUM_RADIUS_MULTIPLIER`: Multiplier for the frustum culling bounding box, value `0.85`.

### Algorithm Steps
1.  **Compute World-Space Center**: Calculate the center of the current chunk in world space.
    $$ center[i] = (coord[i] \times ws\_root) + \frac{ws\_root}{2} $$
    for $i \in \{0, 1, 2\}$.

2.  **Boundary Check**: Verify if the current chunk coordinates exceed the world bounds.
    $$ \text{if } (coord[i] \ll lod) \ge set->max[i] \text{ for any } i, \text{ return.} $$

3.  **Frustum Culling**: Check if the chunk's bounding box intersects the view frustum. The bounding box is defined by the chunk center and a radius of $ws\_root \times 0.85$.
    $$ \text{if } \neg \text{gfx\_fcull\_visible}(cam.frustum\_planes, center, ws\_root \times 0.85), \text{ return.} $$

4.  **Distance Calculation**: Compute the Euclidean distance from the camera's LOD origin to the chunk center.
    $$ distance = \text{glm\_vec\_distance}(cam.lod\_origin, center) $$

5.  **LOD Selection and Enqueue**:
    *   If $distance > lod \times 1024$:
        *   The chunk is visible but at a distance requiring a specific LOD.
        *   Calculate the bit width for the current LOD's geometry index:
            $$ octree\_bitw[i] = set->max\_bitw[i] - \min(lod, set->max\_bitw[i]) $$
        *   Flatten the chunk coordinates $(x, y, z)$ using `octree_bitw` to get the index.
        *   Retrieve the geometry object `g = set->gsvl[lod][index]`.
        *   If `g->vbo` exists, enqueue `g` into `queue_gsvl`.
        *   If `lod == 0`, also retrieve the base mesh `m = set->gmesh[flatten3(x,y,z, set->max_bitw)]`. If `m->vbo` exists, enqueue `m` into `queue_mesh` and its index into `queue_misc`.
        *   Return (do not recurse).
    *   Else ($distance \le lod \times 1024$):
        *   Decrement `lod`.
        *   Recurse into the 8 children of the current octree node.

### Pseudocode
```python
def octree_cull(set, lod, x, y, z):
    ws_root = set.root << lod
    
    # 1. Compute world-space center
    center = [0, 0, 0]
    for i in range(3):
        center[i] = (x if i==0 else y if i==1 else z) * ws_root + (ws_root // 2)
        # Note: The source uses coord[i] in the formula, mapped to x,y,z here
        
    # 2. Boundary check
    # The source checks: if ((coord[i]<<lod) >= set->max[i]) return
    # Here coord is the chunk coordinate at the current lod level? 
    # Actually, the source implies 'coord' is the absolute chunk coordinate.
    # In the recursive step, x,y,z are absolute chunk coordinates.
    # The shift '<< lod' seems to be checking against max_bitw or max?
    # Source: if ((coord[i]<<lod) >= set->max[i]) return.
    # This logic in the source is slightly ambiguous regarding 'coord'.
    # Assuming x,y,z are the chunk indices at the current LOD level relative to the root?
    # Or absolute? The recursion passes (x*2)+nx. So x,y,z are absolute chunk indices.
    # The check (coord[i] << lod) >= max[i] seems to imply coord is a lower-level index?
    # Let's stick to the source formula literally.
    for i in range(3):
        coord = x if i==0 else y if i==1 else z
        if ((coord << lod) >= set.max[i]):
            return

    # 3. Frustum cull
    radius = ws_root * 0.85
    if not gfx_fcull_visible(set.cam.frustum_planes, center, radius):
        return

    # 4. Calculate distance
    distance = glm_vec_distance(set.cam.lod_origin, center)

    # 5. LOD check
    if distance > lod * 1024:
        # Enqueue geometry for this LOD
        octree_bitw = [0, 0, 0]
        for i in range(3):
            coord = x if i==0 else y if i==1 else z
            octree_bitw[i] = set.max_bitw[i] - min(lod, set.max_bitw[i])
        
        # Flatten 3D coordinate to 1D index
        coords = [x, y, z]
        index = flatten3(coords, octree_bitw)
        
        g = set.gsvl[lod][index]
        if g.vbo:
            queue_gsvl[queue_gsvl_count] = g
            queue_gsvl_count += 1
            
        if lod == 0:
            # Enqueue base mesh
            base_index = flatten3(coords, set.max_bitw)
            m = set.gmesh[base_index]
            if m.vbo:
                queue_mesh[queue_mesh_count] = m
                queue_mesh_count += 1
                queue_misc[queue_misc_count] = base_index
                queue_misc_count += 1
        return

    # 6. Recurse
    lod -= 1
    for nx in range(2):
        for ny in range(2):
            for nz in range(2):
                octree_cull(set, lod, (x * 2) + nx, (y * 2) + ny, (z * 2) + nz)

def flatten3(coords, bitw):
    # Helper to flatten 3D coordinates using bit widths
    # Assuming bitw[i] is the number of bits for dimension i
    # This is a standard spatial hashing flattening
    # Implementation detail: [G] Standard bit-packing flattening
    idx = 0
    stride = 1
    for i in range(2, -1, -1):
        idx += coords[i] * stride
        stride <<= bitw[i]
    return idx
```

### Edge Cases and Pitfalls
*   **VRAM Exhaustion**: Without culling, a $256 \times 256 \times 256$ world contains 16,777,216 cubes. At 48 bytes per cube (6 faces $\times$ 4 vertices $\times$ 12 bytes/vertex for float positions), this requires ~4.5 GB of GPU RAM, which is often unavailable [S1, unofficial].
*   **Temporal Coherency**: The method exploits temporal coherency. When a cube is removed, previously hidden cubes become visible. When a cube is added, it only affects the visibility of the six adjacent cubes on its primary faces [S1, unofficial].
*   **Backface Culling**: Invisible faces (those not facing the camera) are typically handled by GPU backface culling, not this CPU method [S1, unofficial].

## Operating characteristics
*   **Time Complexity**: The octree approach achieves visibility determination in $O(\log(N))$ time complexity, where $N$ is the number of cubes [S1, unofficial].
*   **Memory Complexity**: Depends on the octree structure and the geometry storage. The queues are fixed-size arrays (`0xFFFF`), limiting the number of enqueued objects per frame.
*   **Strengths**: Significantly reduces the number of cubes sent to the GPU, preventing VRAM exhaustion and reducing bandwidth consumption [S1, unofficial]. Efficiently handles large static worlds by leveraging spatial partitioning [S1, unofficial].
*   **Limitations**: Requires CPU overhead for traversal and culling calculations. The LOD selection is discrete and based on distance thresholds, which may cause popping if not smoothed [S2, unofficial].
*   **When to Use**: Suitable for large, static voxel worlds where frustum culling and LOD are critical for performance [S1, S2, unofficial].
*   **When Not to Use**: Not suitable for highly dynamic worlds where the octree structure changes frequently and the overhead of updating the tree outweighs the culling benefits, or if the world is small enough that brute-force culling is sufficient.

## Background
The concept of using octrees for visibility culling in voxel worlds was discussed in the context of manual occlusion culling and space partitioning algorithms [S1, unofficial]. The specific implementation details, including the LOD selection logic and queue structures, are derived from the "voxplat" project [S2, unofficial]. The method addresses the limitations of naive rendering approaches that fail to account for the massive data volume of high-resolution voxel grids [S1, unofficial].
