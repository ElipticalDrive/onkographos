# Octree Frustum Culling & LOD Selection

Also called: CPU Frustum Culling, CPU-based Octree LOD & Frustum Culling, Octree Frustum Culling, Octree-based Visibility Culling

## Overview
This method uses an octree spatial partitioning structure to efficiently determine which chunks of a voxel world are visible within the camera's view frustum and to select the appropriate Level of Detail (LOD) for each visible chunk [S2, unofficial]. It solves the problem of rendering massive voxel worlds by avoiding the transfer of invisible geometry to the GPU, which would otherwise consume prohibitive amounts of VRAM (e.g., ~4.5 GB for a full $256^3$ world) [S1, unofficial]. It is distinguished from sibling methods by its explicit integration of distance-based LOD selection during the culling traversal, rather than relying solely on static distance sorting or out-of-core clipping [S2, unofficial].

## How it works
### Inputs and Outputs
**Inputs:**
*   Camera state: `cam.frustum_planes` (6 planes defining the view frustum) and `cam.lod_origin` (camera position for distance calculation) [S2, unofficial].
*   Chunk Set: `set` containing `set->root` (base chunk size), `set->max[3]` (maximum chunk coordinates), `set->max_bitw[3]` (bit width for indexing), `set->gsvl[lod][x][y][z]` (array of `GeometrySVL*` pointers), and `set->gmesh[index]` (array of `GeometryMesh*` pointers) [S2, unofficial].
*   Current traversal coordinates: `(x, y, z)` at current `lod` [S2, unofficial].

**Outputs:**
*   Populated render queues: `queue_gsvl[0xFFFF]` (array of `GeometrySVL*`), `queue_mesh[0xFFFF]` (array of `GeometryMesh*`), `queue_misc[0xFFFF]` (array of `uint32_t` indices), and their respective counts `queue_gsvl_count`, `queue_mesh_count`, `queue_misc_count` [S2, unofficial].

### Data Structures
The geometry is stored in a hierarchical manner indexed by LOD and chunk coordinates [S2, unofficial].
*   `GeometrySVL`: Struct representing a geometry object at a specific LOD. Contains a `vbo` field indicating if valid vertex buffer data exists [S2, unofficial].
*   `GeometryMesh`: Struct representing base-level geometry. Contains a `vbo` field [S2, unofficial].
*   The index into `set->gsvl` is calculated using a flattened 3D coordinate system [S2, unofficial]. The bit width for flattening depends on the current LOD and the maximum bit width of the world [S2, unofficial].

### Parameters
*   `lod`: Current level of detail (unsigned 8-bit integer) [S2, unofficial].
*   `ws_root`: World space root size, calculated as `set->root << lod` [S2, unofficial].
*   `LOD_SCALE`: Distance scale factor, value `1024` [S2, unofficial].
*   `FRUSTUM_RADIUS_MULTIPLIER`: Multiplier for the frustum culling bounding box, value `0.85` [S2, unofficial].

### Algorithm Steps
1.  **Compute World-Space Center**: Calculate the center of the current chunk in world space.
    $$ center[i] = (coord[i] \times ws\_root) + \frac{ws\_root}{2} $$
    for $i \in \{0, 1, 2\}$, where $coord$ corresponds to $(x, y, z)$ [S2, unofficial].

2.  **Boundary Check**: Verify if the current chunk coordinates exceed the world bounds.
    $$ \text{if } (coord[i] \ll lod) \ge set->max[i] \text{ for any } i, \text{ return.} $$
    This converts the current LOD coordinate back to LOD 0 scale to compare against the world maximum [S2, unofficial].

3.  **Frustum Culling**: Check if the chunk's bounding box intersects the view frustum. The bounding box is defined by the chunk center and a radius of $ws\_root \times 0.85$ [S2, unofficial].
    $$ \text{if } \neg \text{gfx\_fcull\_visible}(cam.frustum\_planes, center, ws\_root \times 0.85), \text{ return.} $$

4.  **Distance Calculation**: Compute the Euclidean distance from the camera's LOD origin to the chunk center.
    $$ distance = \text{glm\_vec\_distance}(cam.lod\_origin, center) $$

5.  **LOD Selection and Enqueue**:
    *   If $distance > lod \times 1024$:
        *   Calculate the bit width for the current LOD's geometry index:
            $$ octree\_bitw[i] = set->max\_bitw[i] - \min(lod, set->max\_bitw[i]) $$
        *   Flatten the chunk coordinates $(x, y, z)$ using `octree_bitw` to get the index [S2, unofficial].
        *   Retrieve the geometry object `g = set->gsvl[lod][index]` [S2, unofficial].
        *   If `g->vbo` exists, enqueue `g` into `queue_gsvl` [S2, unofficial].
        *   If `lod == 0`, also retrieve the base mesh `m = set->gmesh[flatten3(x,y,z, set->max_bitw)]` [S2, unofficial]. If `m->vbo` exists, enqueue `m` into `queue_mesh` and its index into `queue_misc` [S2, unofficial].
        *   Return (do not recurse) [S2, unofficial].
    *   Else ($distance \le lod \times 1024$):
        *   Decrement `lod` [S2, unofficial].
        *   Recurse into the 8 children of the current octree node [S2, unofficial].

### Pseudocode
```python
import math

# Module-level render queues as defined in the source
queue_gsvl = [None] * 0xFFFF
queue_gsvl_count = 0
queue_mesh = [None] * 0xFFFF
queue_mesh_count = 0
queue_misc = [None] * 0xFFFF
queue_misc_count = 0

def flatten3(coords, bitw):
    idx = 0
    stride = 1
    for i in range(2, -1, -1):
        idx += coords[i] * stride
        stride <<= bitw[i]
    return idx

def check_frustum(center, radius, frustum_planes):
    # Standard bounding sphere vs frustum planes test [G]
    for plane in frustum_planes:
        dist = plane.normal.dot(center) - plane.d
        if dist < -radius:
            return False
    return True

def octree_cull(set, lod, x, y, z):
    ws_root = set.root << lod
    center = [x * ws_root + ws_root / 2, y * ws_root + ws_root / 2, z * ws_root + ws_root / 2]

    if (x << lod) >= set.max[0] or (y << lod) >= set.max[1] or (z << lod) >= set.max[2]:
        return

    if not check_frustum(center, ws_root * 0.85, set.cam.frustum_planes):
        return

    distance = math.sqrt(sum((center[i] - set.cam.lod_origin[i]) ** 2 for i in range(3)))

    if distance > lod * 1024:
        octree_bitw = [set.max_bitw[i] - min(lod, set.max_bitw[i]) for i in range(3)]
        index = flatten3([x, y, z], octree_bitw)
        g = set.gsvl[lod][index]
        if g.vbo:
            queue_gsvl[queue_gsvl_count] = g
            queue_gsvl_count += 1
        if lod == 0:
            base_index = flatten3([x, y, z], set.max_bitw)
            m = set.gmesh[base_index]
            if m.vbo:
                queue_mesh[queue_mesh_count] = m
                queue_mesh_count += 1
                queue_misc[queue_misc_count] = base_index
                queue_misc_count += 1
        return

    new_lod = lod - 1
    for nx in range(2):
        for ny in range(2):
            for nz in range(2):
                octree_cull(set, new_lod, x * 2 + nx, y * 2 + ny, z * 2 + nz)
```

### Edge Cases and Pitfalls
*   **VRAM Exhaustion**: Without culling, a $256 \times 256 \times 256$ world contains 16,777,216 cubes. At 48 bytes per cube (6 faces $\times$ 4 vertices $\times$ 12 bytes/vertex for float positions), this requires ~4.5 GB of GPU RAM, which is often unavailable [S1, unofficial].
*   **Temporal Coherency**: The method exploits temporal coherency. When a cube is removed, previously hidden cubes become visible. When a cube is added, it only affects the visibility of the six adjacent cubes on its primary faces [S1, unofficial].
*   **Backface Culling**: Invisible faces (those not facing the camera) are typically handled by GPU backface culling, not this CPU method [S1, unofficial].

## Operating characteristics
*   **Time Complexity**: The octree approach achieves visibility determination in $O(\log(N))$ time complexity, where $N$ is the number of cubes [S1, unofficial].
*   **Memory Complexity**: Depends on the octree structure and the geometry storage. The queues are fixed-size arrays (`0xFFFF`), limiting the number of enqueued objects per frame [S2, unofficial].
*   **Strengths**: Significantly reduces the number of cubes sent to the GPU, preventing VRAM exhaustion and reducing bandwidth consumption [S1, unofficial]. Efficiently handles large static worlds by leveraging spatial partitioning [S1, unofficial].
*   **Limitations**: Requires CPU overhead for traversal and culling calculations. The LOD selection is discrete and based on distance thresholds, which may cause popping if not smoothed [S2, unofficial].
*   **When to Use**: Suitable for large, static voxel worlds where frustum culling and LOD are critical for performance [S1, S2, unofficial].
*   **When Not to Use**: Not suitable for highly dynamic worlds where the octree structure changes frequently and the overhead of updating the tree outweighs the culling benefits, or if the world is small enough that brute-force culling is sufficient.

## Background
The concept of using octrees for visibility culling in voxel worlds was discussed in the context of manual occlusion culling and space partitioning algorithms [S1, unofficial]. The specific implementation details, including the LOD selection logic and queue structures, are derived from the "voxplat" project [S2, unofficial]. The method addresses the limitations of naive rendering approaches that fail to account for the massive data volume of high-resolution voxel grids [S1, unofficial].
