# Chunk Visibility Culling

Also called: Chunk Frustum Culling, Frustum Culling for Chunk Visibility, Frustum Culling for Chunks

## Overview
Chunk Visibility Culling determines which spatial chunks of a volume dataset are visible to the camera by testing their world-space bounding boxes against the camera's view frustum [S1, S2, unofficial]. It differs from its sibling methods by operating on a flat list of chunks rather than a hierarchical tree (unlike [Octree Frustum Culling & LOD Selection](5771-octree-frustum-culling-lod-selection.md)) and by performing only binary visibility tests without geometric clipping or resolution selection (unlike [Out-of-Core Frustum Clipping](6688-out-of-core-frustum-clipping.md)). It serves as the primary filter before distance sorting or LOD assignment.

## How it works
**Inputs:**
- Camera object containing `projectionMatrix` and `matrixWorldInverse` (view matrix) [S1, unofficial].
- List of chunks, each with world-space position data (e.g., grid coordinates or direct world coordinates) [S1, S2, unofficial].
- `renderRadius`: The maximum distance (in chunk coordinates) from the center chunk to consider for culling [S1, unofficial].

**Outputs:**
- A list of visible chunk identifiers or positions [S1, unofficial].

**Data Structures:**
- **Frustum:** A representation of the view frustum derived from the projection and view matrices. In the source implementation, this is constructed via `frustum.setFromProjectionMatrix(projScreenMatrix)` where `projScreenMatrix = camera.projectionMatrix * camera.matrixWorldInverse` [S1, unofficial].
- **Chunk Bounds:** Each chunk is represented by an axis-aligned bounding box (AABB) in world space. The sources imply chunks are cubic or rectangular prisms defined by their world position and size [S1, S2, unofficial].

**Steps:**
1. **Calculate Center Chunk:** Determine the chunk containing the camera position to define the search radius.
   $$ \text{center\_chunk\_coords} = \left( \lfloor \frac{\text{camera.position.x}}{\text{CHUNK\_WORLD\_SIZE}} \rfloor, \lfloor \frac{\text{camera.position.y}}{\text{CHUNK\_WORLD\_SIZE}} \rfloor, \lfloor \frac{\text{camera.position.z}}{\text{CHUNK\_WORLD\_SIZE}} \rfloor \right) $$
   [S1, unofficial]

2. **Iterate Chunks:** For each chunk within `renderRadius` of `center_chunk_coords`:
   a. **Get World Position:** Retrieve the chunk's world-space coordinates.
      - Source [S2, unofficial] uses explicit getters: `wx = chunk->GetXWorldPos() * Chunk::m_XSize`, `wz = chunk->GetZWorldPos() * Chunk::m_ZSize`.
      - Source [S1, unofficial] implies the bounds are directly accessible or computed from chunk coordinates.
   b. **Construct Bounding Box:** Define the AABB for the chunk. Let $B$ be the box defined by the chunk's world position and its physical dimensions (e.g., `Chunk::m_XSize`, `Chunk::m_ZSize`, and height) [S1, S2, unofficial].
   c. **Frustum Intersection Test:** Check if the frustum intersects the bounding box $B$.
      - Source [S1, unofficial] uses: `if (this.#frustum.intersectsBox(bounds))`.
      - Source [S2, unofficial] uses: `frustum.IsChunkInFrustum(wx, wz)`.
   d. **Add to Visible List:** If the intersection test returns true, add the chunk to the visible list [S1, unofficial].

3. **Sort Visible Chunks:** Sort the resulting list of visible chunks by their squared distance from the camera (or center chunk) to prepare for rendering order [S1, unofficial].
   $$ \text{distance}^2 = (x_{chunk} - x_{camera})^2 + (y_{chunk} - y_{camera})^2 + (z_{chunk} - z_{camera})^2 $$
   [S1, unofficial]

**Pseudocode:**
```python
def chunk_visibility_culling(camera, chunks, render_radius, chunk_world_size):
    """
    Determine visible chunks by frustum culling and sort by distance.
    
    Args:
        camera: Object with projectionMatrix and matrixWorldInverse.
        chunks: List of chunk objects. Each chunk has world position data.
        render_radius: Max distance in chunk coordinates from center.
        chunk_world_size: Physical size of a chunk in world units.
        
    Returns:
        List of visible chunks sorted by squared distance from camera.
    """
    # 1. Calculate center chunk coordinates
    cx = floor(camera.position.x / chunk_world_size)
    cy = floor(camera.position.y / chunk_world_size)
    cz = floor(camera.position.z / chunk_world_size)
    
    # 2. Set up frustum from camera matrices
    # Note: Implementation details of frustum.setFromProjectionMatrix are assumed
    # to handle the standard 6-plane extraction from the combined matrix.
    proj_screen_matrix = multiply_matrices(camera.projectionMatrix, camera.matrixWorldInverse)
    frustum = Frustum(proj_screen_matrix)
    
    visible_chunks = []
    
    # 3. Iterate through chunks (optimization: only check those within render_radius)
    for chunk in chunks:
        # Get chunk world coordinates
        # Source [S2, unofficial] uses grid coords * size. Source [S1, unofficial] implies bounds are available.
        # We assume chunk has a method to get its AABB or world center.
        chunk_bounds = get_chunk_aabb(chunk, chunk_world_size)
        
        # 4. Frustum intersection test
        if frustum.intersects_box(chunk_bounds):
            # 5. Calculate distance for sorting
            # Squared distance to avoid sqrt
            dx = chunk.world_center.x - camera.position.x
            dy = chunk.world_center.y - camera.position.y
            dz = chunk.world_center.z - camera.position.z
            dist_sq = dx*dx + dy*dy + dz*dz
            
            visible_chunks.append((chunk, dist_sq))
            
    # 6. Sort by squared distance
    visible_chunks.sort(key=lambda item: item[1])
    
    # Return just the chunks, or (chunk, distance) pairs depending on downstream needs
    return [item[0] for item in visible_chunks]
```

**Parameters:**
- `camera`: PerspectiveCamera [S1, unofficial].
- `renderRadius`: Number, radius in chunk coordinates around the center chunk to check [S1, unofficial].
- `chunk_world_size`: Physical size of a chunk in world units (implied by [S1, unofficial] and [S2, unofficial]).

**Edge Cases and Pitfalls:**
- **Precision:** Floating-point errors in frustum-plane vs. box intersection tests can cause flickering at frustum boundaries. [G] Use a small epsilon tolerance in intersection tests if available.
- **Degenerate Input:** If the camera is inside a chunk, the frustum test still works, but the `center_chunk_coords` calculation must handle the floor function correctly for negative coordinates.
- **Bounding Box Accuracy:** If chunks are not axis-aligned or have irregular shapes, the AABB approximation may cause false positives (culling nothing) or false negatives (if the box is too tight). The sources assume axis-aligned chunks [S1, S2, unofficial].

## Operating characteristics
- **Time Complexity:** $O(N)$ where $N$ is the number of chunks within the `renderRadius`. The frustum intersection test is $O(1)$ per chunk. Sorting is $O(V \log V)$ where $V$ is the number of visible chunks.
- **Memory Complexity:** $O(V)$ to store the list of visible chunks.
- **Performance:** Fast, as it avoids complex geometric clipping. The primary cost is the matrix multiplication for frustum setup (done once per frame) and the intersection tests.
- **Strengths:** Simple to implement, low overhead, effective for large datasets with many chunks.
- **Limitations:** Does not handle LOD or resolution selection. May cull chunks that are partially visible but still require rendering if the bounding box test is conservative (though standard AABB tests are exact for the box).
- **When to use:** When chunks are relatively uniform in size and LOD is handled separately or not needed.
- **When not to use:** When hierarchical LOD is required (use [Octree Frustum Culling & LOD Selection](5771-octree-frustum-culling-lod-selection.md)) or when memory constraints require clipping to specific resolutions (use [Out-of-Core Frustum Clipping](6688-out-of-core-frustum-clipping.md)).

## Background
Chunk Visibility Culling is a standard technique in voxel-based rendering and out-of-core volume visualization. It is widely used in game engines and scientific visualization tools to manage large datasets. The specific implementations cited here are from open-source voxel terrain and engine projects [S1, S2, unofficial].
