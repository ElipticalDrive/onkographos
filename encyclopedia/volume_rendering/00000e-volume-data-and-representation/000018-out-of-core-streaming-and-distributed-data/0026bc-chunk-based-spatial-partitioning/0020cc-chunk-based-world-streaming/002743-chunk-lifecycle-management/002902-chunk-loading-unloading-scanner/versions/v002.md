# Chunk Loading/Unloading Scanner

Also called: Scanner, ScannerPlugin

## Overview
The Chunk Loading/Unloading Scanner identifies which spatial chunks need to be loaded or unloaded based on the camera's current and previous chunk positions, using offset grids to determine load and unload areas [S1, unofficial]. It differs from its sibling [Dynamic Chunk Generation with Radius](4002-dynamic-chunk-generation-with-radius.md) by relying on explicit offset grids and queue management rather than a dynamic radius calculation, and from [Budget Plans](5497-budget-plans.md) by not capping the number of processed chunks per frame via a budget but instead processing all determined changes [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Camera transform (translation vector), previous chunk position, configuration parameters (`checks_per_frame`, `data_distance`, `mesh_distance`).
*   **Output:** Sets of chunk coordinates to load (`data_load`, `mesh_load`) and unload (`data_unload`, `mesh_unload`), updated internal queues.

**Data Structures:**
The `Scanner` struct maintains the state [S1, unofficial]:
*   `prev_chunk_pos: IVec3`: The chunk coordinates from the previous frame.
*   `checks_per_frame: usize`: Number of chunks visited per frame. Default: $32 \times 32 \times 32$ [S1, unofficial].
*   `data_offset: usize`: Radius for data loading offsets. Calculated as `distance + 1` [S1, unofficial].
*   `mesh_offset: usize`: Radius for mesh loading offsets. Calculated as `distance` [S1, unofficial].
*   `unresolved_data_load: Vec<IVec3>`: Queue for chunks needing data loading.
*   `unresolved_mesh_load: Vec<IVec3>`: Queue for chunks needing mesh generation.
*   `unresolved_data_unload: VecDeque<IVec3>`: Queue for chunks needing data unloading.
*   `unresolved_mesh_unload: VecDeque<IVec3>`: Queue for chunks needing mesh unloading.
*   `data_sampling_offsets: Vec<IVec3>`: Precomputed offsets for data loading area.
*   `mesh_sampling_offsets: Vec<IVec3>`: Precomputed offsets for mesh loading area.

**Steps:**
1.  **Calculate Current Chunk Position:** Convert the camera's world translation to chunk coordinates. The formula is:
    $$ \text{chunk\_pos} = \left\lfloor \frac{\text{translation} - 16.0}{32.0} \right\rfloor $$
    In integer arithmetic (assuming 32-unit chunks and 16-unit offset for centering):
    ```python
    chunk_pos = ((camera_translation - 16.0) / 32.0).as_ivec3()
    ```
    [S1, unofficial]

2.  **Check for Movement:** Compare `chunk_pos` with `prev_chunk_pos`. If they are identical, skip processing for this frame [S1, unofficial].

3.  **Generate Load/Unload Areas:** Create bounding boxes (sets of chunk coordinates) around the current and previous positions using the sampling offsets.
    *   `load_data_area = chunk_pos + data_sampling_offsets`
    *   `unload_data_area = previous_chunk_pos + data_sampling_offsets`
    *   `load_mesh_area = chunk_pos + mesh_sampling_offsets`
    *   `unload_mesh_area = previous_chunk_pos + mesh_sampling_offsets`
    [S1, unofficial]

4.  **Compute Differences:** Determine the symmetric difference between the new and old areas to find chunks that need to change state.
    *   `data_load = load_data_area - unload_data_area`
    *   `data_unload = unload_data_area - load_data_area`
    *   `mesh_load = load_mesh_area - unload_mesh_area`
    *   `mesh_unload = unload_mesh_area - load_mesh_area`
    [S1, unofficial]

5.  **Update Queues:**
    *   Add chunks in `data_load` and `mesh_load` to their respective unresolved queues.
    *   Remove chunks in `data_unload` and `mesh_unload` from their respective load queues (if present) and add them to unload queues.
    *   Remove chunks that are already loaded from the unload queues [S1, unofficial].

6.  **Sort Load Queues:** Sort the `unresolved_data_load` and `unresolved_mesh_load` queues by the squared distance to the current camera chunk position to prioritize closer chunks [S1, unofficial].

**Pseudocode:**
```python
def update_scanner(camera_translation: Vec3, prev_chunk_pos: IVec3, 
                   data_offset: int, mesh_offset: int, 
                   data_sampling_offsets: List[IVec3], mesh_sampling_offsets: List[IVec3]) -> Tuple[List[IVec3], List[IVec3], List[IVec3], List[IVec3]]:
    # Step 1: Calculate current chunk position
    # Assuming chunk size is 32 and origin offset is 16
    chunk_pos = ((camera_translation - 16.0) / 32.0).as_ivec3()
    
    # Step 2: Check for movement
    if chunk_pos == prev_chunk_pos:
        return [], [], [], []
    
    # Step 3: Generate load/unload areas
    # Note: In implementation, these are sets of chunk coordinates
    load_data_area = set()
    for offset in data_sampling_offsets:
        load_data_area.add(chunk_pos + offset)
        
    unload_data_area = set()
    for offset in data_sampling_offsets:
        unload_data_area.add(prev_chunk_pos + offset)
        
    load_mesh_area = set()
    for offset in mesh_sampling_offsets:
        load_mesh_area.add(chunk_pos + offset)
        
    unload_mesh_area = set()
    for offset in mesh_sampling_offsets:
        unload_mesh_area.add(prev_chunk_pos + offset)
        
    # Step 4: Compute differences
    data_load = list(load_data_area - unload_data_area)
    data_unload = list(unload_data_area - load_data_area)
    mesh_load = list(load_mesh_area - unload_mesh_area)
    mesh_unload = list(unload_mesh_area - load_mesh_area)
    
    # Step 5: Update Queues (Logic depends on specific queue implementation)
    # Add to unresolved loads
    unresolved_data_load.extend(data_load)
    unresolved_mesh_load.extend(mesh_load)
    
    # Remove from loads if they are being unloaded
    for chunk in data_unload:
        if chunk in unresolved_data_load:
            unresolved_data_load.remove(chunk)
        unresolved_data_unload.append(chunk)
        
    for chunk in mesh_unload:
        if chunk in unresolved_mesh_load:
            unresolved_mesh_load.remove(chunk)
        unresolved_mesh_unload.append(chunk)
        
    # Step 6: Sort load queues by distance squared to camera chunk position
    unresolved_data_load.sort(key=lambda c: (c - chunk_pos).length_squared())
    unresolved_mesh_load.sort(key=lambda c: (c - chunk_pos).length_squared())
    
    return data_load, data_unload, mesh_load, mesh_unload
```
[S1, unofficial]

**Parameters:**
*   `checks_per_frame`: Default $32 \times 32 \times 32$ [S1, unofficial].
*   `data_distance`: Radius for data loading offsets. Value is `distance + 1` [S1, unofficial].
*   `mesh_distance`: Radius for mesh loading offsets. Value is `distance` [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** The chunk position calculation involves floating-point division and truncation. Ensure consistent rounding behavior (floor) to avoid jitter when the camera is near chunk boundaries [S1, unofficial].
*   **Degenerate Input:** If the camera is stationary, the scanner skips processing, which is efficient but requires the initial frame to correctly populate the queues [S1, unofficial].

## Subtopics

### [Chunk Visibility Culling](5031-chunk-visibility-culling.md)
Determines visibility via frustum culling and distance sorting. Chosen when geometric occlusion is more important than streaming logic.

### [Dynamic Chunk Generation with Radius](4002-dynamic-chunk-generation-with-radius.md)
Uses a dynamic radius based on camera speed/distance. Chosen when a fixed offset grid is insufficient for varying performance needs.

### [Budget Plans](5497-budget-plans.md)
Limits processing per frame. Chosen when frame-time stability is critical and some chunks may be delayed.

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of chunks in the load/unload areas (proportional to the offset radius cubed). Sorting takes $O(K \log K)$ where $K$ is the number of new chunks to load.
*   **Memory Complexity:** $O(K)$ for storing the unresolved queues.
*   **Performance:** Depends heavily on the size of `data_sampling_offsets` and `mesh_sampling_offsets`. Larger offsets increase the number of chunks processed per frame but reduce the frequency of loading/unloading events.
*   **Strengths:** Simple logic, deterministic behavior based on camera position, efficient for steady movement.
*   **Limitations:** Does not account for occlusion (unlike visibility culling), may load unnecessary chunks if the camera moves erratically.
*   **When to use:** When a simple, predictable streaming strategy is sufficient and occlusion culling is handled separately or not needed.
*   **When not to use:** When frame-time spikes must be strictly bounded (use Budget Plans) or when occlusion significantly reduces visible chunks (use Visibility Culling).

## Background
The Chunk Loading/Unloading Scanner is part of the chunk lifecycle management system in voxel-based rendering engines. It is implemented in the Binary Greedy Voxel Meshing Algorithm demo [S1, unofficial]. The method relies on offset grids to determine load/unload areas based on the camera's current and previous chunk position [S1, unofficial].
