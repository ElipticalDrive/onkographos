# Budget Plans

Also called: chunk budget policies

## Overview
Budget Plans provide a system for managing chunk loading policies in chunk-based volume streaming, replacing the previous single octree-focused policy with configurable presets for exploration, whole-volume visualization, and frame-rate maintenance [S1, unofficial]. This method allows an application to switch loading strategies mid-session to balance visual fidelity against performance constraints, addressing the limitation where a single policy was "right for exploring and wrong for a whole-volume figure or for holding a frame rate while rotating" [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** Current chunk state (`minLevel`, `halo`), a named preset string (`'focus'`, `'uniform'`, `'interactive'`), or an explicit plan object [S1, unofficial].
*   **Outputs:** A resolved `BudgetPlan` object containing parameters for the chunk loader, including `radius`, `minLevel`, and `halo` settings [S1, unofficial].

**Data Structures:**
*   `BudgetPlan`: An object containing loading parameters; specific fields vary by variant (e.g., `gridDims` for Exact Lattice Grid) [S1, unofficial].
*   Presets: Three predefined configurations: `focus` (baseline octree-focused), `uniform` (uniform detail shrink pass), and `interactive` (frame-rate holding) [S1, unofficial].

**Parameters:**
*   **Presets:** `focus`, `uniform`, `interactive` [S1, unofficial].
*   **Precedence (lowest to highest):** focus baseline, named preset, explicit plan object, individual options [S1, unofficial].
*   **`targetFrameMs`:** Resolved and readable but inert (nothing acts on it yet) [S1, unofficial].

**Steps:**
1.  **Resolve Plan:** Call `resolveBudgetPlan` with the desired input. The function applies the precedence rules to determine the final configuration [S1, unofficial].
2.  **Switch Plan:** Call `setBudgetPlan` to apply the resolved plan mid-session. This function "re-folds over load options" to update the streaming state [S1, unofficial].
3.  **Preserve State:** During the switch, `minLevel` and `halo` are taken from the current state. This prevents the switch from undoing a user-set `setMaxDetail` or undercutting a wider kernel already streamed [S1, unofficial].
4.  **Uniform Radius:** If the `radius` parameter is set to `'volume'`, it enables a uniform detail shrink pass. This pass only affects levels beyond the specified radius, and the budget pass converges on the finest uniform level that fits within that radius [S1, unofficial].

**Pseudocode:**
```python
def resolve_budget_plan(input_config, current_state):
    """
    Resolves the final budget plan based on precedence.
    input_config: str or dict. Can be 'focus', 'uniform', 'interactive', 
                  or a dict with explicit options.
    current_state: dict with 'minLevel' and 'halo'.
    """
    # Precedence 1: Focus baseline (lowest)
    plan = {
        'radius': 'default',
        'minLevel': current_state['minLevel'],
        'halo': current_state['halo']
    }
    
    # Precedence 2: Named preset
    if isinstance(input_config, str):
        if input_config == 'uniform':
            plan['radius'] = 'volume'
        elif input_config == 'interactive':
            pass # Uses baseline or preset defaults
        elif input_config == 'focus':
            pass # Remains default
        return plan

    # Precedence 3 & 4: Explicit plan object or individual options
    if isinstance(input_config, dict):
        if 'radius' in input_config:
            plan['radius'] = input_config['radius']
        if 'minLevel' in input_config:
            plan['minLevel'] = input_config['minLevel']
        if 'halo' in input_config:
            plan['halo'] = input_config['halo']
            
    return plan

def set_budget_plan(new_plan, current_state):
    """
    Switches the budget plan mid-session.
    """
    # Re-fold over load options
    final_plan = resolve_budget_plan(new_plan, current_state)
    
    # Preserve state: minLevel and halo come from current state
    # to prevent undoing setMaxDetail or undercutting wider kernels
    final_plan['minLevel'] = current_state['minLevel']
    final_plan['halo'] = current_state['halo']
    
    # Apply final_plan to the chunk loader
    # Note: targetFrameMs is resolved but currently inert
    return final_plan
```

**Edge Cases and Pitfalls:**
*   **State Undoing:** Switching plans must not reset `minLevel` or `halo` to defaults, as this would undo user controls like `setMaxDetail` or disrupt active streaming kernels [S1, unofficial].
*   **Inert Parameter:** `targetFrameMs` is part of the plan but does not currently influence loading behavior [S1, unofficial].

## Subtopics

### Exact Lattice Grid
Replaces octree-based brick sizing with an exact lattice defined by `gridDims`, allowing specific block counts previously unreachable due to scalar `cellEdge` sizing [S1, unofficial]. Choose this when specific block dimensions are required for hardware or rendering constraints [S1, unofficial].
*   **Definition:** Uses `gridDims[a]` bricks per axis, all drawn from `minLevel` [S1, unofficial].
*   **Steps:**
    1.  Set real `gridDims` and `stride` on the plan so `chunkAtVoxel` indexes it correctly [S1, unofficial].
    2.  An axis grows if a brick would exceed `deviceLimit`, because `emitBrick` clamps oversize textures and squashes sampling [S1, unofficial].
    3.  Callers read the built plan's own `gridDims` back to verify dimensions [S1, unofficial].
*   **Pitfall:** Previous `chunkVolumeMultiLOD` sized bricks from scalar `cellEdge`, causing reachable counts to step irregularly (e.g., 2, 8, 12, 16, 27, 4 on `hoa_heart` L5), making counts like 4 or 9 unreachable [S1, unofficial]. `maxBricks` only coarsened by raising the level floor, fighting level control [S1, unofficial].

### Block Loading Badges
Per-pane block-loading badges indicating GPU upload queue status, keyed on resident count movement rather than plan total [S1, unofficial]. Choose this for accurate UI feedback on GPU load [S1, unofficial].
*   **Definition:** Badges key on resident count moving, counting against what the stream actually asked for, not the plan total [S1, unofficial].
*   **Steps:**
    1.  Badge keys on resident count moving [S1, unofficial].
    2.  Counts against what the stream actually asked for, not plan total [S1, unofficial].
    3.  Absent/empty bricks are never fetched, and LRU evicts them [S1, unofficial].
    4.  Holds a per-episode high-water mark so the bar only moves forward [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Not given in the sources.
*   **Measured Performance:** Not given in the sources.
*   **Strengths:** Allows mid-session switching of loading strategies without losing user-set detail levels; supports precise block counts via Exact Lattice Grid [S1, unofficial].
*   **Limitations:** `targetFrameMs` is currently inert; Exact Lattice Grid requires careful handling of `deviceLimit` to avoid texture squashing [S1, unofficial].
*   **When to use:** Use when the application needs to switch between exploration (`focus`), full-volume visualization (`uniform`), or performance-critical rotation (`interactive`) [S1, unofficial]. Use Exact Lattice Grid when specific block counts are required [S1, unofficial].

## Background
Budget Plans were introduced in the `niivue` project to address the limitations of a single octree-focused chunk loading policy [S1, unofficial]. The design doc is located at `docs/budget-plans.md`, with remaining streaming work tracked in `docs/streaming-todos.md` [S1, unofficial]. The implementation includes fixes for chunk eviction issues (e.g., chunk 0 eviction blanking the volume in WebGL2) and adapts to both WebGL2 and WebGPU backends [S1, unofficial]. The Exact Lattice Grid variant was added to support specific block counts in demos like the Zarr demo, which uses a "Blocks control" to choose factorizations closest to cubic [S1, unofficial].
