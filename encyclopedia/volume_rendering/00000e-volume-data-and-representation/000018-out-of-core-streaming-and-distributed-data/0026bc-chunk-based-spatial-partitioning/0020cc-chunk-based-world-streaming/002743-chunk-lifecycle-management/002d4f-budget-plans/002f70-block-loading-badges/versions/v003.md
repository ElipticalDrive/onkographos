# Block Loading Badges

Also called: pending badge

## Overview
Block Loading Badges provide per-pane visibility into the status of GPU upload queues for chunk-based volume rendering [S1, unofficial]. They solve the problem of opaque streaming progress by tracking the resident count movement of fetched blocks, distinguishing actual data acquisition from planned requests [S1, unofficial]. Unlike plan budgets that only shape the octree, badges specifically monitor the GPU upload queue depth keyed on resident count movement rather than the plan total [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: The stream of chunk requests from the renderer (the "asked-for" count per pane) and the current set of resident blocks in GPU memory [S1, unofficial].
- Output: A badge value representing the current pending upload load, bounded by a per-episode high-water mark [S1, unofficial].

**Data Structures:**
- `resident_count`: Integer tracking the number of blocks currently resident in GPU memory for the specific pane [G].
- `high_water_mark`: Integer tracking the maximum `resident_count` observed for the current episode [G].
- `pending_load`: Integer representing the current GPU upload queue depth, calculated as `high_water_mark - resident_count` [S1, unofficial].

**Steps:**
1. **Key on Movement:** The badge state derives from the movement of the resident count rather than the total planned budget [S1, unofficial].
2. **Count Actual Requests:** The badge counts against the number of blocks the stream actually asked for and fetched, not the plan total [S1, unofficial].
3. **Handle Evictions:** When the GPU memory limit is reached, the Least Recently Used (LRU) eviction policy removes blocks from residency [S1, unofficial].
4. **Maintain High-Water Mark:** The system maintains a per-episode high-water mark of the resident count so the progress bar only moves forward [S1, unofficial].

**Pseudocode:**
```python
class BlockLoadingBadge:
    def __init__(self):
        self.resident_count = 0
        self.high_water_mark = 0
        self.pending_load = 0

    def on_block_fetched(self):
        self.resident_count += 1
        if self.resident_count > self.high_water_mark:
            self.high_water_mark = self.resident_count
        self.pending_load = self.high_water_mark - self.resident_count

    def on_block_evicted(self):
        self.resident_count -= 1
        self.pending_load = self.high_water_mark - self.resident_count

    def get_badge_value(self):
        return self.pending_load
```

**Edge Cases and Pitfalls:**
- **Absent/Empty Bricks:** Requests for non-existent or empty data are never fetched, so they do not increment the resident count or the badge load [S1, unofficial].
- **Precision:** The badge relies on integer counts of blocks. Sub-block or partial-fetch states are not described; the method assumes atomic block fetches [G].

## Operating characteristics
- **Time Complexity:** O(1) for badge updates per block fetch or eviction, involving simple integer arithmetic and comparisons [G].
- **Memory Complexity:** O(1) additional memory for the badge state (two integers) [G].
- **Performance:** Verified against a fake clock in isolation, then live on both backends [S1, unofficial].
- **Strengths:** Provides accurate, real-time feedback on GPU upload queue status without being skewed by planned but unfetched blocks [G].
- **Limitations:** Tied to the specific pane and episode context; not a global volume metric [G].

## Background
Block Loading Badges were introduced as part of the Niivue streamed multi-LOD rendering fixes and budget plans implementation [S1, unofficial]. They operate alongside budget plans, which shape the octree structure, while GPU residency is capped separately by the renderer [S1, unofficial].
