# Block Loading Badges

Also called: pending badge

## Overview
Block Loading Badges provide per-pane visibility into the GPU upload queue status for chunk-based volume streaming [S1, unofficial]. Unlike static budget plans that define a target resident count, these badges track the *actual* number of blocks currently being uploaded or held in the queue, keyed on the movement of the resident count rather than the plan's total allocation [S1, unofficial]. This distinction allows the system to accurately reflect the live workload of the streaming engine, which re-requests its working set every frame, independent of the octree's structural budget [S1, unofficial].

## How it works
The method operates as a real-time monitoring and state-tracking mechanism for the GPU upload pipeline. It ensures that the reported "pending" count reflects only the blocks actively requested by the stream, excluding those that are absent, empty, or already evicted.

**Inputs and Outputs:**
*   **Input:** The current stream request set (blocks asked for by the viewer), the current resident block set (blocks currently in GPU memory), and the LRU eviction state.
*   **Output:** A badge value representing the number of blocks in the GPU upload queue, and a high-water mark for the current session.

**Data Structures:**
The badge maintains two primary integer counters:
1.  `pending_count`: The number of blocks currently in the GPU upload queue.
2.  `high_water_mark`: The maximum value `pending_count` has reached during the current episode/session.

**Steps:**
1.  **Initialize Counters:** Set `pending_count` to 0 and `high_water_mark` to 0 at the start of an episode or viewer instance [S1, unofficial].
2.  **Track Resident Movement:** Monitor the resident count. The badge is keyed on the *movement* of this count. When a block is requested and not yet resident, it is added to the upload queue [S1, unofficial].
3.  **Filter Requests:** The badge counts only against what the stream *actually asked for*. It does not count against the total budget defined in the plan [S1, unofficial].
    *   **Exclusion Rule:** Absent bricks (blocks that do not exist in the source data) and empty bricks (blocks with no data) are never fetched. Consequently, they are never added to the upload queue and do not increment the badge [S1, unofficial].
4.  **Handle Evictions:** When the LRU (Least Recently Used) policy evicts a block from GPU memory, the `pending_count` is decremented if that block was still in the upload queue or resident [S1, unofficial].
5.  **Update High-Water Mark:** After updating `pending_count`, compare it to `high_water_mark`. If `pending_count > high_water_mark`, update `high_water_mark = pending_count` [S1, unofficial].
6.  **Report Status:** The badge value is `pending_count`. The high-water mark is used to ensure the UI bar only moves forward, providing a stable historical context for the peak load experienced [S1, unofficial].

**Pseudocode:**
```python
class BlockLoadingBadge:
    def __init__(self):
        self.pending_count = 0
        self.high_water_mark = 0

    def on_block_requested(self, block_id, is_present, is_empty):
        # Absent or empty bricks are never fetched
        if not is_present or is_empty:
            return
        
        # Block is requested and valid; add to upload queue
        self.pending_count += 1
        
        # Update high-water mark
        if self.pending_count > self.high_water_mark:
            self.high_water_mark = self.pending_count

    def on_block_evicted(self, block_id):
        # Block removed from GPU memory/queue
        self.pending_count -= 1

    def get_status(self):
        return {
            "pending": self.pending_count,
            "high_water_mark": self.high_water_mark
        }
```

**Parameters and Edge Cases:**
*   **Per-Pane Scope:** The badge is maintained per-pane, allowing multiple viewers to have independent status tracking [S1, unofficial].
*   **Episode Scope:** The high-water mark is reset per episode, ensuring the bar only moves forward within a single viewing session [S1, unofficial].
*   **Precision:** The badge relies on accurate tracking of the stream's actual requests. If the stream logic fails to distinguish between "asked for" and "actually fetched," the badge will be inaccurate [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** O(1) for badge updates, as it involves simple integer increments/decrements and comparisons [S1, unofficial].
*   **Memory Complexity:** O(1) per pane, storing only two integer counters [S1, unofficial].
*   **Performance:** Verified against a fake clock in isolation and live on both backends (CPU and GPU) [S1, unofficial].
*   **Strengths:** Provides accurate, real-time feedback on GPU upload pressure, decoupled from the octree's structural budget. It correctly ignores non-existent or empty data, preventing false positives in load reporting [S1, unofficial].
*   **Limitations:** It does not control the loading policy; it only reports status. The actual loading is still governed by the Budget Plans and LRU eviction policies [S1, unofficial].

## Background
Block Loading Badges were introduced as part of the "feat(niivue): streamed multi-LOD rendering fixes, LOD compensation, budget plans, and block inspection" pull request [S1, unofficial]. They were developed to address the need for better visibility into the GPU upload queue in chunk-based volume streaming systems, particularly in the context of the DANDI app where a single OME-Zarr store drives both volumetric and deep-zoom views [S1, unofficial]. The badges were verified against a fake clock in isolation and then deployed live on both backends [S1, unofficial].
