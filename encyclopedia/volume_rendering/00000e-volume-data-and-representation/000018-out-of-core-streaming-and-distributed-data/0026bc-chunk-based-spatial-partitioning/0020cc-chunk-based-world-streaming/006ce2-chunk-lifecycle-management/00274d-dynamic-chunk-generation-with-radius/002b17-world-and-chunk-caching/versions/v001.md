# World and Chunk Caching

Also called: Chunk Generation Status and Data Cache

## Overview
World and Chunk Caching manages the state of a procedurally generated voxel world by maintaining a cache of chunk generation statuses and their associated data [S1, unofficial]. It solves the problem of coordinating asynchronous chunk generation with rendering and physics by decoupling the request for a chunk from its availability [S1, unofficial]. Unlike [Dynamic Chunk Generation with Radius](4002-dynamic-chunk-generation-with-radius.md), which focuses on the spatial radius and lifecycle states (KEEP, DRAW, DONE) for streaming, this method explicitly tracks the generation status (`Generating`, `Generated`, `Empty`) and stores the resulting voxel data structures in a cache for immediate access [S1, unofficial].

## How it works
**Inputs and Outputs:**
The system takes a world coordinate and zoom level as input to query or update the cache. It outputs the current `ChunkStatus` or the fully generated `ChunkInfo` if generation is complete.

**Data Structures:**
The core data structure is the `World` object, which contains:
1.  `generator`: An implementation of `Arc<dyn WorldGen>` responsible for producing chunk data [S1, unofficial].
2.  `cache`: An `AHashMap` mapping `(ChunkPosition, ZoomLevel)` to `ChunkStatus` [S1, unofficial].

The `ChunkStatus` is an enum with three variants [S1, unofficial]:
*   `Empty`: The chunk has not been generated or is explicitly empty.
*   `Generating`: The chunk is currently being computed by the generator.
*   `Generated(Arc<ChunkInfo>)`: The chunk is fully computed and ready for use.

The `ChunkInfo` structure holds the actual voxel data [S1, unofficial]:
*   `opaque`: A `Box<Array3Chunk>` containing opaque voxel blocks.
*   `translucents`: A `Vec<Array3Chunk>` containing translucent voxel blocks.
*   `faces`: A `StaticCopyMap<Direction, ChunkFace>` storing precomputed face data for each of the 6 directions (likely for culling or mesh generation).

**Initialization:**
1.  Create a `World` instance [S1, unofficial].
2.  Initialize the `generator` with an `Empty` generator, which returns `None` for any chunk request [S1, unofficial].
3.  Initialize the `cache` as an empty `AHashMap` [S1, unofficial].

**Generation and Caching Logic:**
When a chunk is requested at `(pos, zoom)`:
1.  Check the `cache` for the key `(pos, zoom)` [S1, unofficial].
2.  If the status is `Empty`:
    *   Transition status to `Generating` [S1, unofficial].
    *   Spawn an asynchronous task or thread to call `generator.generate(pos, zoom)` [S1, unofficial].
    *   Upon completion, wrap the result in `ChunkInfo`, create an `Arc<ChunkInfo>`, and update the cache status to `Generated(Arc<ChunkInfo>)` [S1, unofficial].
3.  If the status is `Generating`:
    *   Return a future or handle to wait for completion, or block until the status changes to `Generated` [S1, unofficial].
4.  If the status is `Generated`:
    *   Return the `Arc<ChunkInfo>` directly from the cache [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Concurrency:** The `AHashMap` must be thread-safe or accessed via a mutex, as multiple threads may request the same chunk simultaneously [S1, unofficial].
*   **Memory Leaks:** `Arc<ChunkInfo>` must be properly dereferenced when chunks are removed from the cache to avoid holding memory indefinitely [S1, unofficial].
*   **Degenerate Input:** The `Empty` generator returns `None`, which must be handled to prevent null pointer exceptions when accessing `ChunkInfo` fields [S1, unofficial].

## Subtopics

### Chunk Data Transfer for Snapshots
Serializes chunk contents (SDF, material, fill, fillMat) for late-join snapshots or resyncs, filtering by explicit keys or modification version [S2, unofficial].
*   **Definition:** A mechanism to export chunk data for synchronization or snapshotting [S2, unofficial].
*   **Steps:**
    1.  Filter chunks: If explicit keys are provided, map them to `world.chunks`; otherwise, filter chunks where `initVersion` mismatches [S2, unofficial].
    2.  For each chunk, create an object `{ key, fill, fillMat, sdf: c.sdf ? c.sdf.slice() : null, mat: c.mat ? c.mat.slice() : null }` [S2, unofficial].
    3.  If `sdf` exists, transfer `d.sdf.buffer` and `d.mat.buffer` [S2, unofficial].
    4.  Return the list of chunk data objects [S2, unofficial].
*   **Parameters:** `modified` (boolean, default `false`): If true, return only chunks edited since initialization [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** Cache lookup is $O(1)$ average case for `AHashMap` [S1, unofficial]. Generation time depends on the `WorldGen` implementation.
*   **Memory Complexity:** Proportional to the number of generated chunks. Each chunk stores opaque, translucent, and face data [S1, unofficial].
*   **Strengths:** Decouples generation from rendering; allows asynchronous generation without blocking the main thread [S1, unofficial].
*   **Limitations:** Requires careful management of `Arc` references to avoid memory leaks; cache size can grow unbounded if not pruned [S1, unofficial].
*   **When to use:** When chunk generation is expensive and asynchronous processing is required [S1, unofficial].
*   **When not to use:** For small, static worlds where synchronous generation is sufficient [S1, unofficial].

## Background
Originated in the Infinigen project, which uses a chunk-based spatial partitioning approach for procedural world generation [S1, unofficial]. The method is part of a larger system that includes dynamic chunk generation with radius and chunk lifecycle management [S1, unofficial].
