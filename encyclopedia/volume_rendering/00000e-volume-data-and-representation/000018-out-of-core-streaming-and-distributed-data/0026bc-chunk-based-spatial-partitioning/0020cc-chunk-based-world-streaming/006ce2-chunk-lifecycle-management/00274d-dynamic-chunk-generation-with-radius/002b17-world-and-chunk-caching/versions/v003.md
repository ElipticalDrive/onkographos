# World and Chunk Caching

Also called: Chunk Generation Status and Data Cache

## Overview
World and Chunk Caching manages the state of a procedurally generated voxel world by maintaining a cache of chunk generation statuses and their associated data [S1, unofficial]. Unlike its parent method, Dynamic Chunk Generation with Radius, which focuses on spatial radius and lifecycle states (KEEP, DRAW, DONE) for creation and deletion, this method specifically handles the data structure mapping positions to generation states and the serialization of chunk data for snapshots [S1, unofficial][S2, unofficial].

## How it works
**Inputs and Outputs:**
- Input: World position, zoom level, and optional modification filters.
- Output: Chunk status enum, serialized chunk data objects (for snapshots).

**Data Structures:**
The core state is held in a `World` object [S1, unofficial].
1. `World`: Contains an `Arc<dyn WorldGen>` trait object for chunk generation and an `AHashMap` mapping `(ChunkPosition, ZoomLevel)` to `ChunkStatus` [S1, unofficial].
2. `ChunkStatus`: An enum with three variants [S1, unofficial]:
   - `Generating`: Indicates the chunk is currently being computed.
   - `Generated(Arc<ChunkInfo>)`: Indicates the chunk is complete, holding a reference to the data.
   - `Empty`: Indicates the chunk is empty or not yet generated.
3. `ChunkInfo`: Contains the actual voxel data [S1, unofficial]:
   - `opaque`: A `Box<Array3Chunk>` storing opaque voxel blocks.
   - `translucents`: A `Vec<Array3Chunk>` storing translucent voxel blocks.
   - `faces`: A `StaticCopyMap<Direction, ChunkFace>` storing surface face data for optimization.

**Initialization:**
1. Create a `World` instance [S1, unofficial].
2. Initialize the `generator` with an `Empty` generator implementation, which returns `None` for any chunk request [S1, unofficial].
3. Initialize the `chunks` cache as an empty `AHashMap` [S1, unofficial].

**Chunk Data Transfer for Snapshots (Resync/Late-join):**
This sub-process serializes chunk contents for late-join snapshots or resyncs [S2, unofficial].
1. Filter Chunks: If explicit keys (chunk positions) are provided, map them to entries in `world.chunks` [S2, unofficial]. If no keys are provided, filter `world.chunks` to include only those where the chunk's `initVersion` mismatches the current client's version [S2, unofficial].
2. Serialize Data: For each selected chunk `c`, create a data object `d` [S2, unofficial]:
   - `key`: The chunk position identifier.
   - `fill`: The chunk's fill data.
   - `fillMat`: The chunk's fill material data.
   - `sdf`: If `c.sdf` exists, create a slice `c.sdf.slice()`; otherwise `null` [S2, unofficial].
   - `mat`: If `c.mat` exists, create a slice `c.mat.slice()`; otherwise `null` [S2, unofficial].
3. Transfer Buffers: If `d.sdf` is not null, transfer `d.sdf.buffer` [S2, unofficial]. If `d.mat` is not null, transfer `d.mat.buffer` [S2, unofficial].
4. Return: Return the list of chunk data objects [S2, unofficial].

**Parameters:**
- `modified`: A boolean flag. If `true`, only chunks edited since initialization are returned. Default is `false` [S2, unofficial].

**Edge Cases and Pitfalls:**
- Concurrency: The `AHashMap` and `Arc` usage implies thread-safe access. Implementers must ensure that `ChunkStatus` transitions from `Generating` to `Generated` are atomic or properly locked to prevent race conditions during rendering [G].
- Memory: `Arc<ChunkInfo>` allows multiple references to the same chunk data. When a chunk is removed from the cache, the data is only freed when the last `Arc` is dropped [G].
- Empty Generator: The default `Empty` generator returns `None`. Implementers must handle `None` results by setting the cache status to `Empty` or skipping cache insertion [G].

## Subtopics

### Chunk Data Transfer for Snapshots
A mechanism for serializing chunk contents (SDF, material, fill, fillMat) to support late-join clients or resynchronization [S2, unofficial]. It filters chunks by explicit keys or by modification version (`initVersion` mismatch) and transfers underlying buffers [S2, unofficial]. Choose this when network synchronization or snapshot creation is required [S2, unofficial]. It differs from the core caching by focusing on serialization and network transfer rather than in-memory state management [S2, unofficial].

## Operating characteristics
**Time and Memory Complexity:**
- Lookup: $O(1)$ average case for `AHashMap` access by `(ChunkPosition, ZoomLevel)` [S1, unofficial].
- Serialization: $O(N \cdot V)$ where $N$ is the number of filtered chunks and $V$ is the volume of a chunk, as it slices and transfers SDF and material buffers [S2, unofficial].
- Memory: Proportional to the number of generated chunks. Each `ChunkInfo` holds `Box<Array3Chunk>` and `Vec<Array3Chunk>`, which scale with chunk size [S1, unofficial].

**Strengths and Limitations:**
- Strengths: Decouples generation from rendering via the `ChunkStatus` enum. Supports efficient resyncs by filtering only modified chunks [S2, unofficial].
- Limitations: The `Empty` generator default requires explicit handling for non-empty worlds. Buffer transfer logic is specific to the SDF/material structure [S2, unofficial].

**When to Use:**
- Use when managing a dynamic voxel world with asynchronous generation [G].
- Use when network synchronization or snapshot features are required [S2, unofficial].

**When Not to Use:**
- Do not use for static, pre-generated worlds where caching overhead is unnecessary [G].
- Do not use if the underlying data structure does not support `Arc` or thread-safe maps [G].

## Background
This method is documented in open-source voxel engine implementations [S1, unofficial][S2, unofficial]. It builds on the dynamic chunk generation radius concept by adding a robust caching layer for status and data [S1, unofficial].
