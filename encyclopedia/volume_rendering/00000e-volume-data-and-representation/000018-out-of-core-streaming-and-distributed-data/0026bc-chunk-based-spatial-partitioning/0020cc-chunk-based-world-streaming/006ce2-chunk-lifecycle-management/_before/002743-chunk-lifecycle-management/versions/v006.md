# Chunk Lifecycle Management

Also called: Chunk Management, Chunk Spawning and Despawn

## Overview
Chunk Lifecycle Management maintains the set of active volume data chunks during streaming by computing which chunks to spawn and despawn based on camera proximity [S1, unofficial]. It differs from [Synchronous Chunk Loading](3904-synchronous-chunk-loading.md) by explicitly separating the residency decision logic from I/O scheduling, and from [Chunk-Based World Management & Asynchronous Loading](6440-chunk-based-world-management-asynchronous-loading.md) by providing the deterministic core logic that asynchronous schedulers execute [G].

## How it works
**Inputs:**
- `camera_position`: The current world position of the viewer [S1, unofficial].
- `render_distance`: The radius (in chunk units) defining the desired visible area [S1, unofficial].
- `chunk_size`: The physical size of a single chunk [G].
- `chunks`: A hash map mapping chunk positions to existing chunk objects [S1, unofficial].

**Outputs:**
- `newChunks`: A list of newly instantiated chunk objects ready for terrain generation [S1, unofficial].
- `chunksToDelete`: A list of chunk positions for chunks removed from memory [S1, unofficial].

**Data Structures:**
- `ChunkPosition`: A 3-tuple of integers representing grid coordinates [G].
- `Chunk`: An object containing voxel data and rendering state for a specific chunk [G].

**Algorithm Steps:**
1. **Identify Desired Region:** Compute the set of all chunk positions within the render distance from the camera [S1, unofficial].
2. **Identify Existing Region:** Extract the set of positions currently held in the `chunks` hash map [S1, unofficial].
3. **Determine Unloads:** Iterate through `_chunksAlreadyExist` [S1, unofficial]. For each position $p \in \_chunksAlreadyExist$, if $p \notin \_nearbyPositionsSet$, the chunk is no longer needed [S1, unofficial].
4. **Determine Loads:** Iterate through `_nearbyPositionsSet` [S1, unofficial]. For each position $p \in \_nearbyPositionsSet$, if $p \notin \_chunksAlreadyExist$, the chunk is missing [S1, unofficial].
5. **Generate Content:** Generate terrain for all chunks in `newChunks` using `Chunk::MultithreadGenerateTerrain` [S1, unofficial].

**Formulas:**
A chunk at grid position $p = (x, y, z)$ is within the render distance $r$ from the camera's chunk coordinate $c = (c_x, c_y, c_z)$ if $(x - c_x)^2 + (y - c_y)^2 + (z - c_z)^2 \leq r^2$ [S1, unofficial].

**Pseudocode:**
```python
import math

class Chunk:
    def __init__(self, pos):
        self.pos = pos
    def remove_from_draw_calls(self):
        pass
    def multithread_generate_terrain(self):
        pass

def manage_chunk_lifecycle(camera_pos, render_dist, chunk_size, chunks):
    # Step 1: Identify desired region
    _nearbyPositionsSet = set()
    center = (camera_pos[0] / chunk_size, camera_pos[1] / chunk_size, camera_pos[2] / chunk_size)
    for x in range(math.floor(center[0]) - render_dist, math.floor(center[0]) + render_dist + 1):
        for y in range(math.floor(center[1]) - render_dist, math.floor(center[1]) + render_dist + 1):
            for z in range(math.floor(center[2]) - render_dist, math.floor(center[2]) + render_dist + 1):
                if (x - center[0])**2 + (y - center[1])**2 + (z - center[2])**2 <= render_dist**2:
                    _nearbyPositionsSet.add((x, y, z))

    # Step 2: Identify existing region
    _chunksAlreadyExist = set(chunks.keys())

    newChunks = []
    chunksToDelete = []

    # Step 3: Determine Unloads
    for pos in _chunksAlreadyExist:
        if pos not in _nearbyPositionsSet:
            chunks[pos].remove_from_draw_calls()
            del chunks[pos]
            chunksToDelete.append(pos)

    # Step 4: Determine Loads
    for pos in _nearbyPositionsSet:
        if pos not in _chunksAlreadyExist:
            new_chunk = Chunk(pos)
            chunks[pos] = new_chunk
            newChunks.append(new_chunk)

    # Step 5: Generate Content
    for chunk in newChunks:
        chunk.multithread_generate_terrain()

    return newChunks, chunksToDelete
```

**Parameters:**
- `render_distance`: Not given in the sources [S1, unofficial].
- `camera_position`: Not given in the sources [S1, unofficial].

**Edge Cases:**
- **Precision:** The sources do not specify floating-point handling for `camera_position` relative to integer chunk grids [S1, unofficial]. Typically, the camera position is converted to chunk coordinates via floor division by chunk size before distance calculation [G].
- **Boundaries:** The sources do not specify behavior at world boundaries (e.g., negative coordinates) [S1, unofficial]. Standard integer arithmetic applies unless a specific world origin offset is defined [G].

## Subtopics

### [Dynamic Chunk Generation with Radius](4002-dynamic-chunk-generation-with-radius.md)
Manages chunk instantiation and removal based on a spherical render distance around the player, using set difference operations to determine which chunks to load or unload. It builds on [Chunk Lifecycle Management](3987-chunk-lifecycle-management.md) by replacing static triggers with a continuous distance check against the player's current position [G]. Unlike [Chunk Loading/Unloading Scanner](4404-chunk-loading-unloading-scanner.md), which scans discrete regions, this method evaluates every chunk within a calculated bounding box relative to the player to maintain a consistent spherical visibility volume [G].

### [Chunk Loading/Unloading Scanner](4404-chunk-loading-unloading-scanner.md)
Determines which chunks of a volume dataset need to be loaded or unloaded based on the camera's current and previous positions. It solves the problem of efficiently streaming large voxel worlds by identifying load and unload areas using offset grids, then computing the symmetric difference between these areas to generate precise queue updates. It differs from [Chunk Visibility Culling](5031-chunk-visibility-culling.md) by operating on loaded chunks and using distance thresholds rather than frustum intersection tests.

### [Budget Plans](5497-budget-plans.md)
Manages chunk loading policies for chunked volume rendering, replacing the single octree-focused policy with presets for exploration, whole-volume figures, and frame-rate holding. It solves the problem of rigid streaming behavior by allowing mid-session switching and re-folding of load options based on user intent. Unlike siblings that focus on geometric generation or scanner mechanics, Budget Plans shape the octree structure and residency targets to balance detail and performance.

## Operating characteristics
- **Time Complexity:** Not given in the sources [S1, unofficial]. The algorithm performs $O(N + M)$ set operations and allocations, where $N$ is the number of chunks in the render distance and $M$ is the number of currently loaded chunks [G].
- **Memory Complexity:** Not given in the sources [S1, unofficial]. Auxiliary space is $O(N + M)$ for the position sets, plus proportional to the number of loaded chunks [G].
- **Strengths:** Simple, deterministic, and easy to implement [G]. It guarantees that no chunk within the render distance is missing and no chunk outside is present [S1, unofficial].
- **Limitations:** It does not handle asynchronous I/O scheduling or priority [G]. It assumes that chunk generation and draw call management are implemented elsewhere [S1, unofficial].
- **When to use:** When a simple, synchronous determination of chunk residency is required, or as the logical core for more complex asynchronous schedulers [G].
