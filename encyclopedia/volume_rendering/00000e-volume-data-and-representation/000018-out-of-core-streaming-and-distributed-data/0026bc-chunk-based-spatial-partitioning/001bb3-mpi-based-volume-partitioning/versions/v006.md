# MPI-based Volume Partitioning
Also called: Chunk-based MPI parallelism, Spatial Division of Uniform Resolution Data

## Overview
MPI-based Volume Partitioning is a data-parallel strategy where a volume dataset is spatially divided into contiguous chunks (typically slices along one axis), with each chunk assigned to a distinct MPI process for independent rendering [S1][S2, unofficial]. It solves the problem of scaling volume rendering to large datasets that exceed the memory or processing capacity of a single node by distributing the I/O and computation load across a cluster [S1][S2, unofficial]. It differs from tree-based or adaptive partitioning methods by using a fixed, regular grid of chunks, which simplifies load balancing for uniform-resolution data but requires explicit handling of boundary artifacts [S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A volume dataset (e.g., a single time step) stored as a sequence of contiguous slices in a file [S2, unofficial].
*   **Output:** A set of scattered binary files, one per MPI process, containing the rendered results or intermediate mesh data [S1].

**Data Structures:**
*   **Chunk Assignment:** A mapping from process ID $p$ to a range of slice indices $[start_p, end_p]$ [S2, unofficial].
*   **Triangle Table (for isosurface extraction):** A concatenation of partial vertex and triangle tables generated by each process [S1].

**Algorithm Steps:**
1.  **Partitioning:** Divide the total number of slices $S$ among $n$ processors such that the difference in slice count between any two processors is at most one [S2, unofficial]. The number of slices assigned to processor $p$ (where $0 \le p < n$) is calculated as:
    $$
    \text{slices}_p = \begin{cases} 
    \lfloor S/n \rfloor + 1 & \text{if } p < (S \bmod n) \\
    \lfloor S/n \rfloor & \text{otherwise}
    \end{cases}
    $$
    The starting slice index for processor $p$ is:
    $$
    \text{start}_p = \sum_{i=0}^{p-1} \text{slices}_i
    $$
    [S2, unofficial].

2.  **Data Access:** Each process $p$ reads only the slices in its assigned range $[start_p, end_p]$ from the input file [S1][S2, unofficial]. This is efficient if the file storage order matches the spatial order (e.g., Z-axis slices stored contiguously) [S2, unofficial].

3.  **Rendering/Processing:** Each process renders its assigned chunk independently. For isosurface extraction, this generates a partial triangle table [S1]. For ray-casting, this generates a partial image or slice buffer [S2, unofficial].

4.  **Boundary Handling (Overlap):** To prevent boundary artifacts (e.g., black stripes) caused by missing opacity/color calculations at the division boundaries, a small overlap of data is included in adjacent datasets [S2, unofficial]. These extra/duplicated slices are used for boundary calculations but must be removed before final compositing to prevent image stretching [S2, unofficial].

5.  **Sewing (Optional):** If the output is a mesh (e.g., isosurface), the partial triangle tables from all processes are concatenated. The vertex indices in the triangle table are updated to account for the union of vertex tables from all processes [S1]. This step is optional if the scattered files are used as input for subsequent parallel processing steps [S1].

6.  **Compositing:** If the output is image-based, the partial results are composited. If slice order matches storage order, ray segments can be combined without additional mappings [S2, unofficial].

**Pseudocode:**
```python
def mpi_volume_partitioning(total_slices, num_processors, my_rank, file_path):
    """
    Each MPI process executes this function.
    """
    # Step 1: Calculate slice assignment
    base_slices = total_slices // num_processors
    remainder = total_slices % num_processors
    
    if my_rank < remainder:
        num_slices = base_slices + 1
        start_slice = my_rank * (base_slices + 1)
    else:
        num_slices = base_slices
        start_slice = remainder * (base_slices + 1) + (my_rank - remainder) * base_slices
        
    end_slice = start_slice + num_slices
    
    # Step 2: Read assigned slices
    # Assuming file format allows seeking to slice start
    slices = read_slices_from_file(file_path, start_slice, num_slices)
    
    # Step 3: Render/Process
    # For isosurface:
    local_vertices, local_triangles = extract_isosurface(slices)
    
    # For ray-casting:
    # local_image = ray_cast(slices)
    
    # Step 4: Write output
    # For isosurface: write local_vertices and local_triangles to a binary file
    write_mesh_file(my_rank, local_vertices, local_triangles)
    
    # For ray-casting: write local_image to a binary file
    # write_image_file(my_rank, local_image)
```

**Parameters:**
*   **Overlap Size:** Not given in the sources. [G] Typically small (e.g., 1-2 voxels) to cover the ray step or marching cubes cell boundary.
*   **Chunk Dimension:** Slices along the Z-axis are the primary example [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Boundary Artifacts:** Naive non-overlapping division causes black stripes or discontinuities because opacity/color calculations are missing at the boundary where data division occurs [S2, unofficial].
*   **Image Stretching:** If overlap slices are not removed before compositing, the final image will be stretched due to the addition of extra slices [S2, unofficial].
*   **Load Imbalance:** For uniform-resolution data, this method is efficient. For adaptive-resolution data, workload may not be equal, requiring different partitioning strategies [S2, unofficial].

## Subtopics

### Chunk-based World Streaming
Streams chunks from disk to memory as needed, focusing on temporal/spatial traversal rather than static MPI partitioning [2369-chunk-based-world-streaming.md].

### Chunk-based Training
Applies chunking to machine learning training data for volume rendering, focusing on data augmentation and batch processing [3168-chunk-based-training.md].

### Chunk Trees
Uses a hierarchical tree structure for adaptive chunking, allowing for variable resolution and more complex spatial queries [4050-chunk-trees.md].

### Object-space decomposition with local clustering
Partitions space based on object density rather than uniform grid, useful for scenes with varying object distribution [4156-object-space-decomposition-with-local-clustering.md].

### Uniform Block Partitioning with Acceleration
Uses uniform blocks but adds acceleration structures (like BVH) for ray traversal, differing from the simple slice-based approach [6098-uniform-block-partitioning-with-acceleration.md].

### Moving Walls Algorithm
A dynamic partitioning technique for time-varying data, moving a "wall" of processed data through the volume [9715-moving-walls-algorithm.md].

### Tide: Trajectory-Adaptive Differential Streaming
Adapts streaming based on camera trajectory, focusing on predictive loading rather than static MPI chunks [10150-tide-trajectory-adaptive-differential-streaming.md].

## Operating characteristics
*   **Time Complexity:** $O(S/P)$ for reading and processing, where $S$ is the number of slices and $P$ is the number of processors, assuming uniform workload [S2, unofficial].
*   **Memory Complexity:** $O(S/P)$ per process, as each process only loads its assigned slices [S1][S2, unofficial].
*   **Scaling:** Scales well for uniform-resolution data where I/O and computation are balanced across processors [S2, unofficial].
*   **Strengths:** Simple implementation, efficient I/O for contiguous data, no need for complex data structures [S2, unofficial].
*   **Limitations:** Load imbalance for adaptive-resolution data, boundary artifacts if not handled, overhead for sewing meshes [S1][S2, unofficial].
*   **When to use:** Large uniform-resolution volumes on MPI clusters where I/O bandwidth is a bottleneck [S1][S2, unofficial].
*   **When not to use:** Adaptive-resolution data, scenes requiring complex spatial queries, or when memory per node is extremely limited and streaming is preferred [S2, unofficial].

## Background
The method was developed as part of parallel volume visualization techniques for time-varying data [S2, unofficial]. It is based on the principle of spatial division of uniform resolution data, where the volume is partitioned along one axis to allow independent rendering by multiple processors [S2, unofficial]. The sewing step for isosurface extraction was introduced to handle the concatenation of partial meshes generated by parallel processes [S1].
