# MPI-based Volume Partitioning

Also called: Chunk-based MPI parallelism, Spatial Division of Uniform Resolution Data

## Overview
MPI-based Volume Partitioning is a data-parallel strategy where a volumetric dataset is divided into contiguous spatial chunks (typically slices along one axis) and assigned to distinct MPI processes for independent rendering [S1][S2, unofficial]. It solves the problem of scaling volume rendering to large datasets by minimizing inter-process communication during the core rendering phase, relying on post-processing assembly rather than distributed memory management [S1][S2, unofficial]. It differs from [Chunk-based World Streaming](2369-chunk-based-world-streaming.md) by processing a static snapshot (single time step) rather than streaming dynamic data, and from [Chunk-based Training](3168-chunk-based-training.md) by focusing on visualization output rather than model parameter updates.

## How it works
**Inputs and Outputs:**
- **Input:** A single time-step volume dataset (uniform resolution) and a set of $P$ MPI processes.
- **Output:** A set of scattered binary files (one per process) containing partial results (e.g., rendered images or mesh fragments) [S1][S2, unofficial].

**Data Structures:**
The global volume is decomposed into a 1D grid of chunks along the $z$-axis. Each chunk $k$ consists of a contiguous range of slices.
- **Slice Assignment:** For $S$ total slices and $P$ processors, the number of slices assigned to processor $p$ (where $0 \le p < P$) is determined by:
  $$ N_p = \begin{cases} \lfloor S/P \rfloor + 1 & \text{if } p < (S \bmod P) \\ \lfloor S/P \rfloor & \text{otherwise} \end{cases} $$
  This ensures the difference in slice count between any two processors is at most one [S2, unofficial].
- **File Offset:** Since slice order matches storage order, the file offset for processor $p$ is the cumulative sum of slice sizes of all preceding processors [S2, unofficial].

**Steps:**
1. **Partitioning:** The global volume is divided into contiguous blocks of slices. Processor $p$ is assigned a specific range of slice indices $[start_p, end_p)$ [S2, unofficial].
2. **Data Access:** Each process reads only the slices belonging to its assigned chunk from the input file. This is efficient because slices are contiguous in memory/storage [S2, unofficial].
3. **Rendering:** Each process renders its assigned chunk independently.
   - **Overlap Handling:** To prevent boundary artifacts (e.g., black stripes in compositing due to missing opacity/color calculations at division boundaries), each chunk includes a small overlap of data from adjacent chunks [S2, unofficial].
   - **Boundary Removal:** Before final assembly, the extra/duplicated slices at the boundaries of each chunk are removed to prevent image stretching [S2, unofficial].
4. **Output:** Each process writes its result to a separate binary file [S1][S2, unofficial].
5. **Sewing (Optional):** If the output is a mesh (e.g., isosurface), a sewing step updates the triangle table. Vertex indices in the concatenated partial triangle tables are modified to account for the union of vertex tables from all processes [S1]. If the output is a composite image, slices are combined based on their established front-to-back order without additional mapping [S2, unofficial].

**Pseudocode:**
```python
def mpi_volume_partitioning(rank, num_procs, total_slices, slice_size_bytes, overlap_slices):
    # 1. Determine slice assignment
    base_slices = total_slices // num_procs
    remainder = total_slices % num_procs
    
    if rank < remainder:
        num_slices = base_slices + 1
        start_idx = rank * (base_slices + 1)
    else:
        num_slices = base_slices
        start_idx = remainder * (base_slices + 1) + (rank - remainder) * base_slices
        
    end_idx = start_idx + num_slices
    
    # 2. Calculate file offset for reading
    # Assuming uniform slice size and contiguous storage
    file_offset = start_idx * slice_size_bytes
    
    # 3. Read data with overlap
    # Read base slices
    data = read_file_chunk(file_offset, num_slices * slice_size_bytes)
    
    # Add overlap from previous chunk (if not first)
    if rank > 0:
        prev_end = start_idx - 1
        prev_offset = prev_end * slice_size_bytes
        overlap_data = read_file_chunk(prev_offset, overlap_slices * slice_size_bytes)
        data = concat(overlap_data, data)
        
    # Add overlap from next chunk (if not last)
    if rank < num_procs - 1:
        next_start = end_idx
        next_offset = next_start * slice_size_bytes
        overlap_data = read_file_chunk(next_offset, overlap_slices * slice_size_bytes)
        data = concat(data, overlap_data)
        
    # 4. Render
    # Render function handles the overlap region internally or masks it
    result = render_volume(data)
    
    # 5. Remove overlap from result before writing
    # Assuming overlap was added to both ends
    if rank > 0:
        result = result[overlap_slices:]
    if rank < num_procs - 1:
        result = result[:-overlap_slices]
        
    # 6. Write output
    write_binary_file(f"output_rank_{rank}.bin", result)
```

**Parameters:**
- **Overlap Size:** Small number of slices (e.g., 1-2) sufficient to cover the rendering kernel's footprint [S2, unofficial].
- **Sewing:** Optional; disabled if output is not a mesh [S1].

**Edge Cases and Pitfalls:**
- **Boundary Artifacts:** Naive non-overlapping division causes visual artifacts (black stripes) because opacity/color calculations are missing at the division boundaries [S2, unofficial].
- **Load Imbalance:** If the volume has adaptive resolution, equal slice counts do not guarantee equal workload [S2, unofficial]. This method is designed for uniform resolution data.
- **Index Mismatch:** In mesh sewing, vertex indices must be globally unique; failure to update indices leads to corrupted geometry [S1].

## Subtopics

### Spatial Division of Adaptive-Resolution Data
Divides data into blocks based on workload rather than equal slice counts to balance processing time [S2, unofficial].

### Chunk-based World Streaming
Handles dynamic, time-varying data by streaming chunks over time, whereas this method processes a static snapshot [2369-chunk-based-world-streaming.md].

## Operating characteristics
- **Time Complexity:** $O(S/P)$ for reading and rendering, where $S$ is total slices and $P$ is number of processors. Sewing is $O(V)$ where $V$ is total vertices [S1][S2, unofficial].
- **Memory Complexity:** $O(S_{chunk})$ per process, where $S_{chunk}$ is the number of slices assigned to that process plus overlap.
- **Performance:** Efficient for uniform resolution data due to simple sequential file access patterns [S2, unofficial]. Scaling is linear with processor count if I/O bandwidth allows [S2, unofficial].
- **Strengths:** Simple implementation, minimal communication during rendering, efficient I/O for contiguous data [S1][S2, unofficial].
- **Limitations:** Not suitable for adaptive resolution without modification; requires post-processing assembly; load imbalance if data density varies significantly across slices [S2, unofficial].

## Background
Originated in parallel volume visualization pipelines for GPU clusters [S1]. It was developed to address the complexity of balanced partitioning of active cells by adopting a simpler data-parallel approach [S1]. The technique is described in the context of multiresolution and adaptive-resolution time-varying data visualization [S2, unofficial].
