# MPI-based Volume Partitioning

Also called: Chunk-based MPI parallelism, Spatial Division of Uniform Resolution Data

## Overview
MPI-based Volume Partitioning is a data-parallel strategy where a volume dataset is partitioned into contiguous chunks of slices, with each MPI process reading and rendering only its assigned subset [S1][S2, unofficial]. It differs from image-based parallelism (e.g., [Chunk-based World Streaming](2369-chunk-based-world-streaming.md)) by distributing the raw data access and local rendering workload rather than compositing final pixel buffers, and from adaptive methods (e.g., [Uniform Block Partitioning with Acceleration](6098-uniform-block-partitioning-with-acceleration.md)) by relying on fixed spatial slice boundaries rather than workload-balanced adaptive blocks [S1][S2, unofficial].

## How it works
**Inputs:** A volume dataset stored as a sequence of contiguous 2D slices (typically along the Z-axis) [S2, unofficial].
**Outputs:** A set of scattered binary files, one per MPI rank, containing the rendered results or intermediate mesh data [S1].

**Data Structures:**
*   **Volume File:** A linear file where slices are stored sequentially. Each slice is a 2D grid of voxel values [S2, unofficial].
*   **Slice Assignment Map:** A mapping of MPI rank $p$ to a range of slice indices $[start_p, end_p]$ [S2, unofficial].
*   **Triangle Table (Optional):** If extracting isosurfaces, a list of triangles with vertex indices. Each process maintains a local table [S1].

**Parameters:**
*   $N$: Total number of slices in the volume.
*   $P$: Total number of MPI processes (ranks).
*   $Overlap$: Number of extra slices added to adjacent chunks to handle boundary artifacts [S2, unofficial].

**Algorithm Steps:**

1.  **Partition Calculation:** Determine the number of slices assigned to each processor $p \in [0, P-1]$. The distribution ensures the difference in slice count between any two processors is at most one [S2, unofficial].
    *   Let $base = \lfloor N / P \rfloor$.
    *   Let $remainder = N \pmod P$.
    *   For processor $p$:
        *   If $p < remainder$, assign $base + 1$ slices.
        *   Else, assign $base$ slices.
    *   *Example:* For $N=31, P=5$: $base=6, remainder=1$. Processor 0 gets 7 slices; Processors 1-4 get 6 slices each [S2, unofficial].
    *   *Example:* For $N=34, P=5$: $base=6, remainder=4$. Processors 0-3 get 7 slices; Processor 4 gets 6 slices [S2, unofficial].

2.  **Boundary Handling (Overlap):** To prevent boundary artifacts (e.g., black stripes) caused by missing opacity/color calculations at division boundaries, each processor reads a small overlap of data from adjacent chunks [S2, unofficial].
    *   Processor $p$ reads its assigned slices plus $Overlap$ slices from the preceding chunk (if $p>0$) and $Overlap$ slices from the succeeding chunk (if $p<P-1$) [S2, unofficial].
    *   These extra slices are used for local rendering calculations but are discarded or masked before final assembly to prevent image stretching [S2, unofficial].

3.  **Local Rendering:** Each MPI rank $p$ seeks to the appropriate position in the input file based on its assigned slice range and the overlap [S2, unofficial]. It renders its assigned slices independently using a standard volume rendering algorithm (e.g., ray casting) [S1][S2, unofficial].

4.  **Output Generation:**
    *   **Image-Based:** Each process writes its rendered image to a separate binary file [S1].
    *   **Mesh-Based (Isosurface):** Each process generates a local triangle table [S1].

5.  **Sewing (Optional, Mesh Only):** If the output is a mesh, the partial triangle tables from all processes are concatenated. The vertex indices in the triangle table must be updated to account for the union of vertex tables from all processes. Specifically, indices for triangles generated by rank $p > 0$ must be offset by the total number of vertices generated by ranks $0$ to $p-1$ [S1]. This step is optional if the scattered files are used as input for subsequent parallel processing [S1].

```python
import numpy as np

def calculate_slice_assignment(num_slices, num_procs):
    """
    Distributes slices among processors such that the difference in count
    between any two processors is at most one.
    Returns a list of (start_index, end_index) for each processor.
    """
    base_count = num_slices // num_procs
    remainder = num_slices % num_procs
    
    assignments = []
    current_start = 0
    
    for p in range(num_procs):
        # First 'remainder' processors get one extra slice
        count = base_count + 1 if p < remainder else base_count
        current_end = current_start + count
        assignments.append((current_start, current_end))
        current_start = current_end
        
    return assignments

def render_chunk(rank, num_procs, total_slices, overlap_slices, input_file):
    """
    Each MPI rank renders its assigned portion of the volume.
    """
    # 1. Determine slice range
    assignments = calculate_slice_assignment(total_slices, num_procs)
    start_slice, end_slice = assignments[rank]
    
    # 2. Handle overlap for boundary correctness
    # Read extra slices from neighbors to ensure boundary calculations are correct
    read_start = max(0, start_slice - overlap_slices)
    read_end = min(total_slices, end_slice + overlap_slices)
    
    # 3. Read data
    # In a real implementation, this involves MPI_File_read or fseek/fread
    # assuming the file stores slices contiguously.
    local_data = read_slices_from_file(input_file, read_start, read_end)
    
    # 4. Render
    # Render the local data. The overlap slices contribute to the visual 
    # continuity but must be excluded from the final output image dimensions.
    rendered_image = volume_render(local_data)
    
    # 5. Crop overlap from output
    # Remove the extra slices added for boundary handling
    # The valid output corresponds to indices [start_slice, end_slice)
    # relative to the original volume.
    # Assuming rendered_image covers [read_start, read_end)
    crop_start = start_slice - read_start
    crop_end = end_slice - read_start
    
    final_output = rendered_image[crop_start:crop_end]
    
    # 6. Write output
```

## Operating characteristics
*   **Complexity:** Time complexity is linear with respect to the number of slices assigned to each processor, $O(N/P)$, assuming uniform slice processing cost [S1][S2, unofficial]. Memory complexity is $O(N/P + Overlap)$ per processor [S2, unofficial].
*   **Performance:** Reading is efficient because slice order matches storage order, allowing direct seeking without additional mappings [S2, unofficial]. Compositing is efficient if slice order matches storage order, as ray segments can be combined without additional mappings [S2, unofficial].
*   **Strengths:** Simple implementation; efficient I/O for uniform data; avoids complex load balancing for uniform-resolution volumes [S2, unofficial].
*   **Limitations:** Not suitable for adaptive-resolution data where workload varies significantly per slice (requires [Uniform Block Partitioning with Acceleration](6098-uniform-block-partitioning-with-acceleration.md) or similar) [S2, unofficial]. Naive non-overlapping division causes boundary artifacts [S2, unofficial].
*   **When to use:** Uniform-resolution volumes where I/O efficiency and simplicity are prioritized over perfect load balancing [S2, unofficial].
*   **When not to use:** Adaptive-resolution data or scenes with highly non-uniform computational cost per slice [S2, unofficial].

## Background
This method was described in the context of parallel volume visualization of time-varying data [S2, unofficial] and parallel isosurface extraction on GPU clusters [S1]. It addresses the challenge of balancing data access and rendering workload in distributed memory environments by leveraging the spatial locality of volume data [S1][S2, unofficial].
