# Bandwidth-based Streaming Interval Calculation

Also called: N_skip calculation, t_delta calculation

## Overview
Bandwidth-based Streaming Interval Calculation is a method to calculate the minimum time interval between data fetches and the number of simulation slices to skip, based on system bandwidth limits to ensure real-time streaming from HDD to GPU [S1, unofficial]. It solves the problem of managing large volumetric datasets that exceed GPU and RAM capacity by calculating a safe skip count ($N_{\text{skip}}$) that accounts for transfer latency and user-defined time multipliers [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:**
    *   $B_{\text{HDD} \rightarrow \text{RAM}}$: Throughput from hard disk to RAM [S1, unofficial].
    *   $B_{\text{RAM} \rightarrow \text{GPU}}$: Throughput from RAM to GPU memory [S1, unofficial].
    *   $\text{size}(\mathcal{S})$: Size of a single time slice in bytes [S1, unofficial].
    *   $t_0, t_1$: Start and end time of the simulation [S1, unofficial].
    *   $N_S$: Number of slices in the simulation [S1, unofficial].
    *   $m_{\text{app}}$: Application time multiplier [S1, unofficial].
    *   $m_{\text{func}}$: Function time multiplier [S1, unofficial].
*   **Outputs:**
    *   $t_\Delta$: Minimum time interval between fetches [S1, unofficial].
    *   $N_{\text{skip}}$: Number of slices to skip for the next fetch [S1, unofficial].

**Data Structures:**
The method relies on two ring buffers:
1.  **Host Layer:** A ring buffer of 6 items in heap memory [S1, unofficial]. Each item stores one flow slice [S1, unofficial]. Items 2 and 4 are the center items containing slices before and after the current function time $t_{\text{func}}$ [S1, unofficial]. A queue manages more than 6 items for smooth buffering [S1, unofficial].
2.  **Device Layer:** A ring buffer of 4 items [S1, unofficial]. Each item is a composition of one host-layer item and a chunk of allocated device memory, managed by a CUDA queue [S1, unofficial]. Items 1 and 2 are the center items corresponding to time slices around $t_{\text{func}}$ [S1, unofficial].

**Formulas:**
1.  **Minimum Bandwidth:**
    $$B_{\min} = \min(B_{\text{HDD} \rightarrow \text{RAM}}, B_{\text{RAM} \rightarrow \text{GPU}})$$
    Where $B_{\min}$ is the bottleneck bandwidth [S1, unofficial].

2.  **Minimum Time Interval:**
    $$t_\Delta = \frac{\text{size}(\mathcal{S})}{B_{\min}}$$
    Where $t_\Delta$ is the minimum time required to transfer one slice [S1, unofficial].

3.  **Data Time Spacing:**
    $$t_S = \frac{t_1 - t_0}{N_S - 1}$$
    Where $t_S$ is the temporal distance between consecutive slices [S1, unofficial].

4.  **Skip Count:**
    $$N_{\text{skip}} = \frac{t_\Delta}{t_S} \cdot m_{\text{app}} \cdot m_{\text{func}}$$
    Where $N_{\text{skip}}$ is the number of slices to skip [S1, unofficial]. This is a floating-point value [S1, unofficial].

**Parameters:**
*   $B_{\text{HDD} \rightarrow \text{RAM}}$: Typical value 1.2 GB/s [S1, unofficial].
*   $B_{\text{RAM} \rightarrow \text{GPU}}$: Typical value 1.6 GB/s [S1, unofficial].
*   $m_{\text{app}}$: Range $[0, 1]$ [S1, unofficial].
*   $m_{\text{func}}$: Range $\mathbb{R}$ [S1, unofficial].

**Steps:**
1.  Calculate $B_{\min}$ using the minimum of the HDD-to-RAM and RAM-to-GPU throughputs [S1, unofficial].
2.  Calculate $t_\Delta$ by dividing the size of a single time slice $\mathcal{S}$ by $B_{\min}$ [S1, unofficial].
3.  Calculate $t_S$ using the simulation start time $t_0$, end time $t_1$, and number of slices $N_S$ [S1, unofficial].
4.  Calculate $N_{\text{skip}}$ by dividing $t_\Delta$ by $t_S$ and multiplying by $m_{\text{app}}$ and $m_{\text{func}}$ [S1, unofficial].
5.  **Host Layer Management:**
    *   Maintain a ring buffer of 6 items [S1, unofficial].
    *   Ensure items 2 and 4 contain the slices immediately before and after the current function time $t_{\text{func}}$ [S1, unofficial].
    *   If $t_{\text{func}}$ moves past the interval between items 2 and 3 in the positive time direction, pop item 0 from the left of the buffer and push it to the right [S1, unofficial].
    *   Upon inserting a new item (e.g., ID 5), schedule it to load a future time slice from the hard disk [S1, unofficial]. The ID of this slice is determined by $N_{\text{skip}}$ relative to the current position [S1, unofficial].
    *   **Synchronization:** After popping a new item from the host buffer queue, block the host thread if the associated host memory is still subject to device or host layer transfer [S1, unofficial].
6.  **Device Layer Management:**
    *   Maintain a ring buffer of 4 items [S1, unofficial].
    *   Upon insertion of a new item into the host ring buffer, pop one item from the left of the device ring buffer [S1, unofficial].
    *   Send the popped item's associated memory chunk back to the CUDA queue [S1, unofficial].
    *   Copy the previously last (fully loaded) host-buffer item by reference to the device layer, combine it with a CUDA memory object, and schedule for asynchronous memory transfer [S1, unofficial].
    *   **Synchronization:** After popping a new item from the device buffer queue, block the host thread if the associated host memory is still subject to host layer transfer [S1, unofficial]. Assign a unique CUDA stream object to every device layer item to synchronize transfers [S1, unofficial].
7.  **CUDA Launch Synchronization:**
    *   After performing all tasks on both layers, synchronize device layer items with IDs 1 and 2 before launching CUDA kernels [S1, unofficial]. This asserts that the time slices are fully loaded when accessed [S1, unofficial].

    B_min = min(B_hdd_ram, B_ram_gpu)
    t_delta = size_S / B_min
    t_S = (t1 - t0) / (N_S - 1)
    N_skip = (t_delta / t_S) * m_app * m_func
    return t_delta, N_skip

**Pitfalls:**
*   Using $t_\Delta$ directly for skip calculation assumes constant transfer rates and function time, which can be disturbed by user input or system load. Synchronization rules are required to handle these deviations [S1, unofficial].
*   Queue items in both host and device layers consume allocated memory even when unused. On the device layer, memory is scarce, so the number of items should be kept to a minimum [S1, unofficial].

## Subtopics

## Operating characteristics
*   **Time Complexity:** The calculation of $N_{\text{skip}}$ is $O(1)$ [S1, unofficial]. The streaming overhead is dominated by I/O latency, which is hidden by asynchronous transfers [S1, unofficial].
*   **Memory Complexity:** $O(1)$ with respect to the total dataset size, as only a fixed number of slices (6 host, 4 device) are held in memory [S1, unofficial].
*   **Measured Performance:** In the source example, a system with 1.2 GB/s HDD and 1.6 GB/s RAM-to-GPU bandwidth was used [S1, unofficial]. The method allows rendering of datasets like 100 time slices of $128^3$ points (2,500 MB) which would otherwise exceed GPU memory [S1, unofficial].
*   **Scaling:** Scales well with dataset size as it does not depend on the total number of slices $N_S$ for memory allocation, only for calculating $t_S$ [S1, unofficial]. It scales with bandwidth; faster storage allows higher $m_{\text{app}}$ or $m_{\text{func}}$ values [S1, unofficial].
*   **Strengths:** Decouples rendering speed from dataset size; allows real-time exploration of large simulations; handles user interaction (time manipulation) gracefully via synchronization [S1, unofficial].
*   **Limitations:** Relies on constant transfer rates for $N_{\text{skip}}$ calculation; actual transfer may take longer than $t_\Delta$ (up to twice as long), requiring the safety margin provided by the multi-layered buffer structure [S1, unofficial]. Memory is scarce on the device layer, so buffer sizes must be minimized [S1, unofficial].
*   **When to use:** When streaming volumetric data from slow storage (HDD) to GPU for real-time visualization, especially when the dataset is too large for GPU memory [S1, unofficial].

## Background
The method originates from the work of Dirk Sowinski in his 2012 Master's thesis "Real-Time Smoke Volume Rendering" [S1, unofficial]. It was developed to address the limitations of uploading entire simulation outputs to the GPU, which is infeasible for large datasets [S1, unofficial]. The approach uses a multi-layered streaming architecture (Host and Device layers) with specific synchronization rules to handle the asynchronous nature of data transfer and user interaction [S1, unofficial].
