# Out-of-Core Volume Rendering Pipeline

Also called: 3D+t+w Out-of-Core Rendering, FRIGAS Application Architecture, FRIGAS Implementation, FRIGAS Pipeline

## Overview
The Out-of-Core Volume Rendering Pipeline is an adaptive, modular architecture for the interactive visualization of large-scale 3D temporal multivariate (3D+t+w) gas and fluid datasets [S1, unofficial]. It solves the problem of managing simultaneous multivariate and temporal data access without requiring High-Performance Computing (HPC) systems by employing out-of-core brick-based storage and on-demand GPU transfers [S1, unofficial]. Unlike AMR-based bricking approaches, this method leverages prestructured datasets to enable parallel brick loading with a shared ID across different variables [S1, unofficial]. It builds on the virtual page table strategy described in [Out-of-Core Rendering with Virtual Page Tables](5359-out-of-core-rendering-with-virtual-page-tables.md), extending it to handle temporal and multivariate dimensions [S1, unofficial].

## How it works
The pipeline is implemented in the FRIGAS (Fluid Rendering Infrastructure for Gas and Atmospheric Simulations) application [S1, unofficial]. It is structured into three main steps: preprocessing, visualization interface handling, and rendering engine execution [S1, unofficial].

### Inputs and Outputs
*   **Input:** Large-scale 3D+t+w datasets in formats such as NSDF, NetCDF, or DICOM [S1, unofficial].
*   **Output:** Rendered frames (images) generated via CUDA/OpenGL, supporting modes like DVR, MIP, MeanIP, and MIDA [S1, unofficial].

### Data Structures
**Bricks**
*   **Layout:** Structured blocks of voxels [S1, unofficial].
*   **Size:** Default fixed-size block dimension is $64^3$ voxels [S1, unofficial].
*   **Content:** Encodes $d$ variables selected from $w$ available variables [S1, unofficial].
*   **Normalization:** Values are normalized to a standardized range during preprocessing [S1, unofficial].
*   **LOD:** Bricks are formed with Level of Detail (LOD) information during preprocessing [S1, unofficial].
*   **Bit Limit:** The current implementation enforces a 128-bit limit for multivariate bricks [S1, unofficial].

**CuGLContext**
*   **Layout:** A structure managing the interface between ImGUI, OpenGL, and CUDA [S1, unofficial].
*   **Fields:**
    *   Handles the CPU Request Manager [S1, unofficial].
    *   Interacts with the GPU Cache Manager [S1, unofficial].
    *   Retrieves Pixel Buffer Object (PBO) textures for result frames [S1, unofficial].

### Numbered Steps
1.  **Import:** The user imports a dataset (e.g., NSDF, NetCDF, DICOM) [S1, unofficial].
2.  **Bricking:** The 3D+t+w input data is subdivided into structured bricks of fixed size (default $64^3$) [S1, unofficial].
3.  **Variable Selection:** The user selects $d$ variables from the $w$ available variables to be visualized [S1, unofficial].
4.  **Encoding & Normalization:** The selected variables are encoded into the bricks and normalized to a standardized range [S1, unofficial].
5.  **LOD Formation:** Bricks are formed with LOD information [S1, unofficial].
6.  **UI Interaction:** The User Interface (UI), implemented via ImGUI and GLFW, allows the user to control the camera, navigate temporally, and adjust visualization settings [S1, unofficial].
7.  **Request Generation:** The UI sends requests to the Rendering Interface, never directly to the engine [S1, unofficial].
8.  **Interface Handling:** The Rendering Interface acts as a virtual controller, interpreting requests and managing data from preload to final rendering [S1, unofficial].
9.  **Context Setup:** A `CuGLContext` is established between ImGUI, OpenGL, and CUDA [S1, unofficial].
10. **Request Management:** The CPU Request Manager, handled by the `CuGLContext`, processes memory mode requests and interacts with the GPU Cache Manager [S1, unofficial].
11. **Rendering:** The CUDA Rendering Engine receives specific rendering tasks [S1, unofficial].
12. **Ray Traversal:** The engine uses standard ray traversal algorithms to request virtual positions, triggering CPU-GPU transfers as needed [S1, unofficial].
13. **Frame Retrieval:** The `CuGLContext` retrieves the PBO texture containing the result frame [S1, unofficial].

### Edge Cases and Pitfalls
*   **LOD Support:** The system does not fully support Level of Detail (LOD) modes at runtime [S1, unofficial]. If a brick is not empty, it will only access the finest possible value, despite preprocessing forming bricks with LOD [S1, unofficial].
*   **Memory Constraints:** The addition of the $d$ (variable) dimension can exceed VRAM capacity, requiring careful memory mode request handling by the CPU request manager [S1, unofficial].
*   **Work in Progress:** The implementation is described as a Work in Progress, with temporal and multivariate full support still in progress to improve performances and interactivity [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources [S1, unofficial].
*   **Memory Complexity:** Dependent on the number of bricks loaded into the GPU Cache Manager and the 128-bit limit per brick [S1, unofficial].
*   **Measured Performance:** Early visualization timing results on various datasets are provided in [S1, unofficial]:
    *   **Tacc_turbulence (NSDF 3D):** 515.87 FPS, 1.94 ms frame time [S1, unofficial].
    *   **StagBeetle (NSDF 3D):** 499.74 FPS, 2.00 ms frame time [S1, unofficial].
    *   **Dataset 1 (NetCDF):** 194.28 FPS (1t/f), 697.07 ms frame time [S1, unofficial].
    *   **Dataset 2 (NetCDF):** 454.46 FPS (1t/f), 696.62 ms frame time [S1, unofficial].
    *   **Dataset 3 (FS3D/Binaries):** 12.03 FPS (1t/f), 73.20 ms frame time [S1, unofficial].
    *   *Note:* Measurements are mean host times for Volume Rendering with 250 samples per ray [S1, unofficial].
*   **Scaling:** The system is designed for large-scale data, leveraging prestructured datasets for parallel brick loading [S1, unofficial].
*   **Strengths:** Handles 3D+t+w data without HPC systems; modular architecture; supports multiple rendering modes (DVR, MIP, MeanIP, MIDA) [S1, unofficial].
*   **Limitations:** Incomplete LOD support; 128-bit limit for multivariate bricks; work in progress status [S1, unofficial].
*   **When to use:** Interactive visualization of large-scale 3D temporal multivariate gas and fluid datasets on consumer or workstation GPUs [S1, unofficial].
*   **When not to use:** When full LOD support is required at runtime [S1, unofficial].

## Background
The pipeline is implemented in the FRIGAS (Fluid Rendering Infrastructure for Gas and Atmospheric Simulations) application [S1, unofficial]. It builds on out-of-core rendering proposed by [6], which was initially demonstrated for 3D datasets on GPUs [S1, unofficial]. The current work integrates the temporal aspect from [5] and adds the multivariate aspect, enabling broader applications in scientific visualization [S1, unofficial]. The approach differs from AMR-based bricking by leveraging prestructured datasets to allow parallel brick loading with a shared ID across different variables [S1, unofficial].
