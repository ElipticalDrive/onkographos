# Virtual Multi-Resolution Volume with Page Table Hierarchy

Also called: Virtual Multi-Resolution Volume with Hierarchical Page Tables, Virtual Multi-Resolution Volume Representation with Page Table Hierarchy, Virtual Volume

## Overview
A virtual memory architecture for out-of-core volume visualization that replaces explicit tree structures (such as octrees or kD-trees) with a virtual multi-resolution volume addressed via normalized coordinates and translated to physical cache blocks via a hierarchy of page tables [S1, unofficial][S2]. It differs from its parent [Out-of-Core Rendering with Virtual Page Tables](5359-out-of-core-rendering-with-virtual-page-tables.md) by explicitly defining the resolution hierarchy as a set of discrete levels with arbitrary, axis-dependent down-sampling ratios, managed through a recursive page table structure rather than a single flat table [S1, unofficial][S2]. It avoids the overhead of tree traversal and maintenance, offering higher efficiency for deep resolution hierarchies where all visible data of a specific resolution are resident in the cache [S1, unofficial][S2].

## How it works

### Inputs and Outputs
*   **Input:** A 3D bounding box of the tissue block (queryable from the source, e.g., electron microscope), a current transfer function, and a ray-casting request specifying a desired level of detail [S1, unofficial][S2].
*   **Output:** Voxel values sampled from the block cache, or cache miss signals triggering asynchronous data construction [S1, unofficial][S2].

### Data Structures

**Virtual Multi-Resolution Volume**
*   Defined by the 3D bounding box of the imaged tissue [S2].
*   Addressed by a tuple $(l, p)$, where:
    *   $l$: Integer resolution level, $0 \le l \le l_{max}$. $l=0$ is highest resolution, $l_{max}$ is coarsest [S2].
    *   $p = (x, y, z) \in [0, 1]^3$: Normalized floating-point coordinates within the bounding box [S2].
*   Each level $l$ represents a volume in the normalized space $[0, 1]^3$ [S2]. The voxel count at level $l$ is not constrained to be a fixed fraction of level $l-1$ [S1, unofficial].

**Block Cache**
*   Implemented as a 3D texture serving as "physical" memory [S2].
*   Stores small voxel blocks, typically of size $32^3$ [S1, unofficial].

**Page Table Hierarchy**
*   A recursive structure of depth $t$ [S2].
*   **Root (Level 0):** The **Multi-Resolution Page Directory**. Always resident in GPU memory. Not virtualized [S2].
*   **Levels 1 to $t-1$:** Virtualized page tables [S2].
*   **Level $t$ (Leaf):** Page table entries referencing voxel blocks in the block cache [S1, unofficial].
*   **Page Table Entry (PTE) Layout:**
    *   `xyz`: Indices/addresses. References either the next level of page table entries (if $t > 2$) or a block of voxels in the block cache [S2].
    *   `w`: Paging flag. One of:
        *   `UNMAPPED`: Block not mapped to cache. Access generates a cache miss [S2].
        *   `EMPTY`: Block is known to be empty. No cache miss generated [S2].
        *   `MAPPED` (flag cleared): Block is valid and mapped to cache [S2].

### Parameters
*   $l_{max}$: Maximum resolution level [S2].
*   $t$: Depth of the page table hierarchy [S2].
*   $r_{pd}(l)$: Resolution (dimensions in voxels) of the page directory at level $l$ [S2].
*   $r_{pt}(l)$: Resolution (dimensions in voxels) of the page table at level $l$ [S2].
*   $r_{voxel}(l)$: Resolution (dimensions in voxels) of the data at level $l$ [S2].
*   $b_{pt}$: Block size of page table entries for modulo wrapping [S2].
*   $b_{voxel}$: Block size of voxel data (typically $32^3$) [S1, unofficial].
*   Down-sampling ratios: Arbitrary per axis [S1, unofficial]. Chosen to reduce anisotropy gradually (e.g., if anisotropy is 1:2 in $x,y:z$ at $l=0$, $z$ resolution may remain constant at $l=1$ while $x,y$ halve, achieving 1:1 anisotropy) [S2].

### Algorithm: Address Translation and Sampling

The following pseudocode implements the on-the-fly translation of a virtual address $(l, p)$ to a physical voxel sample [S1, unofficial]. It assumes standard 3D texture sampling functions `texture3D(tex, coord)` and vector operations [G].

```python
# Constants
UNMAPPED = 0
EMPTY = 1
BLOCK_SIZE = 32  # Voxel block size in each dimension

# State for spatial coherence optimization
last_p_dir_index = None
last_p_table_index = None

def sample_current_position(l, p):
    """
    Samples the virtual volume at level l and normalized coordinate p.
    Returns the voxel value.
    """
    sample = 0.0

    # 1. Page Directory Lookup
    # Calculate directory index for this level and position
    p_dir_index = (p * r_pd(l)).astype(int) % r_pd(l).shape

    if p_dir_index != last_p_dir_index:
        # Fetch page directory entry
        # pageDirBase[l].xyz is the base address (xyz) for level l in the directory texture
        p_dir_address = pageDirBase[l].xyz + p_dir_index
        p_dir_entry = texture3D(texPageDir, p_dir_address)
        last_p_dir_index = p_dir_index
    else:
        p_dir_entry = last_p_dir_entry

    paging_flag = p_dir_entry.w
    last_p_dir_entry = p_dir_entry

    if paging_flag != UNMAPPED and paging_flag != EMPTY:
        # 2. Page Table Lookup
        # Calculate page table index
        p_table_index = (p * r_pt(l)).astype(int) % r_pt(l).shape
        p_table_address = p_dir_entry.xyz + (p_table_index % b_pt)

        if p_table_index != last_p_table_index:
            p_table_entry = texture3D(texPageTableCache, p_table_address)
            last_p_table_index = p_table_index
        else:
            p_table_entry = last_p_table_entry

        paging_flag = p_table_entry.w
        last_p_table_entry = p_table_entry

        if paging_flag != UNMAPPED and paging_flag != EMPTY:
            # 3. Voxel Block Lookup
            # Calculate voxel address within the block cache
            voxel_index = (p * r_voxel(l)).astype(int) % BLOCK_SIZE
            voxel_address = p_table_entry.xyz + voxel_index
            sample = texture3D(texBlockCache, voxel_address)

    return sample
```

The exact adjustment of `p` to local block coordinates is handled by scaling `p` with the resolution at level $l$ and taking the modulo of the block size, as shown in the pseudocode [S2].

### Edge Cases and Pitfalls
*   **Page Table Size:** For very large volumes, a single page table becomes too large to fit in memory, necessitating the recursive hierarchy [S2].
*   **Anisotropy:** Down-sampling ratios must be chosen carefully to reduce anisotropy gradually. Fixed-ratio mipmaps may not be optimal for highly anisotropic data (e.g., microscopy data) [S2].
*   **Empty vs. Unmapped:** Distinguish between blocks that are truly empty (zero/missing data) and those that are unmapped (data not yet loaded). Empty blocks allow skipping without cache misses; unmapped blocks trigger asynchronous requests [S2].
*   **Transfer Function Changes:** Blocks may become "empty" if they are transparent under the current transfer function. This state must be updated when the transfer function changes [S2].

## Subtopics

### Multi-Volume Rendering with Segmentation
Visualizes segmentation data (object IDs) stored as slices of image data as an additional volume in the pipeline [S1, unofficial]. It sets itself apart by using nearest-neighbor or rank filters for downsampling to avoid interpolating object IDs, and stores IDs as 24-bit data per pixel for over 16 million distinct objects [S1, unofficial]. Choose it when rendering segmented connectomics data alongside EM intensity data [S1, unofficial]. Separate cache textures and virtual memory instances are allocated for each volume type [S1, unofficial].

### Multi-Volume Segmented Rendering
Maintains a separate page table hierarchy for every volume in a multi-volume setup [S1, unofficial]. It sets itself apart by allowing sparse segmentation data to be stored in a smaller cache than dense EM data [S1, unofficial]. Choose it when managing multiple distinct data volumes with different sparsity and bit-depth requirements [S1, unofficial].

## Operating characteristics

*   **Time Complexity:** Address translation is $O(t)$ where $t$ is the page table hierarchy depth, involving $t$ texture lookups (page directory + page tables) [S1, unofficial]. This is generally faster than tree traversal for deep hierarchies as it avoids pointer chasing and conditional branching associated with tree structures [S1, unofficial].
*   **Memory Complexity:** The page directory is always resident in GPU memory [S2]. Its size depends on the number of resolution levels and the granularity of the directory [S1, unofficial]. Page tables are virtualized and stored in the block cache, consuming memory only for accessed regions [S2].
*   **Performance:** Efficient for deep resolution hierarchies. Maximum efficiency is achieved when all visible data of the desired resolution are resident in the cache [S1, unofficial].
*   **Strengths:** Scales well to extremely large volume sizes. No tree structure maintenance required. Supports arbitrary down-sampling ratios per axis [S1, unofficial].
*   **Limitations:** Requires asynchronous data construction pipeline to handle cache misses. Performance degrades if cache misses are frequent due to poor data locality or insufficient cache size [S1, unofficial].

## Background

*   **Origin:** Developed for the interactive visualization of petascale microscopy data streams [S1, unofficial].
*   **Key Paper:** Hadwiger et al., "Interactive Volume Exploration of Petascale Microscopy Data Streams" (2012) [S1, unofficial].
*   **History:** Designed to overcome the limitations of tree-based structures (octrees/kD-trees) for extremely large volumes, where tree traversal overhead and memory consumption become prohibitive [S1, unofficial]. It leverages the GPU's texture hardware for efficient address translation and caching [S1, unofficial].
*   **Usage:** Used in visualization pipelines for electron microscopy data, where data is streamed from 2D image tiles and constructed on-the-fly [S1, unofficial].
