# Sparse Texture Binding

Also called: Hardware Page Tables, Hardware-managed page tables for sparse volumes

## Overview
Sparse Texture Binding is a lossless, hardware-level mechanism in modern graphics APIs (Vulkan, Direct3D 12) that decouples the virtual volume size from the physical memory footprint by using hardware-managed page tables [S1]. It allocates physical memory pages only for specific subregions actively being sampled [S1]. Unlike its parent method, [Out-of-Core Rendering with Virtual Page Tables](5359-out-of-core-rendering-with-virtual-page-tables.md), it utilizes uniform page tables managed in hardware, where the fragment shader queries page residency and decides how to handle missing pages [S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A virtual volume texture defined by its full logical dimensions and a set of physical memory pages containing the actual voxel data bricks [S1].
*   **Output:** A bound texture resource that behaves like a standard 3D texture to the shader, but transparently handles missing data via hardware page faults [S1].

**Data Structures:**
The hardware maintains an internal page table structure [S1]. The exact layout is opaque to the application, but logically it maps virtual page indices to physical page pointers [G].
*   **Virtual Address:** The coordinate $(x, y, z)$ in the virtual volume space [S2, unofficial].
*   **Page Size:** The granularity of allocation, typically matching the brick size used in the parent method (e.g., $64^3$ or $128^3$ voxels) [G].
*   **Page Table Entry (PTE):** Contains a valid bit, a physical page base address, and residency status flags [G].

**Steps:**
1.  **Texture Creation:** The application creates a sparse texture resource with flags indicating sparse residency (e.g., `VK_IMAGE_CREATE_SPARSE_RESIDENCY_BIT` in Vulkan or `GL_ARB_sparse_texture` in OpenGL) [S2, unofficial].
2.  **Physical Allocation:** The application allocates physical memory pages and binds them to specific regions of the virtual texture using API-specific binding commands [S1]. Only the pages required for the current view or dataset subset are bound [S1].
3.  **Hardware Translation:** When the fragment shader samples the texture at a virtual coordinate $(x, y, z)$:
    *   The hardware calculates the virtual page index: $P_{idx} = \lfloor V_{coord} / S_{brick} \rfloor$ [S2, unofficial].
    *   The hardware looks up $P_{idx}$ in the internal page table [S2, unofficial].
    *   If the page is resident (bound), the hardware computes the physical address: $A_{phys} = P_{base} + (V_{coord} \pmod{S_{brick}})$ [S2, unofficial].
    *   If the page is not resident, the hardware triggers a page fault or returns a default value, and the fragment shader decides how to handle the missing page [S2, unofficial].
4.  **Page Fault Handling:** The driver or application loads the required brick from disk or CPU memory into a physical page and binds it to the virtual page index [S1].

**Formulas:**
*   Virtual Page Index: $P_{idx} = \lfloor V_{coord} / S_{brick} \rfloor$
*   Physical Address: $A_{phys} = P_{base} + (V_{coord} \pmod{S_{brick}})$
    *   Where $V_{coord}$ is the sample coordinate, $S_{brick}$ is the brick/page size in voxels, and $P_{base}$ is the base address of the physical page [S2, unofficial].

**Parameters:**
*   **Page Size:** Determined by the hardware and API. Common brick sizes are powers of two (e.g., 64, 128) [G].
*   **Maximum Dimensions:** Hardware imposes limits on the virtual texture size. For example, 32,000 for 2D and 16,000 for 3D dimensions [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Maximum Size Limitations:** The virtual volume dimensions cannot exceed hardware limits (e.g., 16k for 3D) [S2, unofficial].
*   **Page Fault Overhead:** Frequent page faults can stall the GPU pipeline. Missing bricks act as cache misses, requiring the application to ensure the working set fits in physical memory or that page loading is asynchronous and overlapped with rendering [S2, unofficial][G].

        self.voxel_size_bytes = voxel_size_bytes
        self.page_table = {}  # Maps virtual page index to PageTableEntry

    def bind_physical_page(self, virtual_page_index, base_address):
        self.page_table[virtual_page_index] = PageTableEntry(valid=True, base_address=base_address)

    def sample(self, coord):
        # Hardware translation logic
        page_idx = coord // self.brick_size
        offset = coord % self.brick_size
        if page_idx in self.page_table and self.page_table[page_idx].valid:
            base = self.page_table[page_idx].base_address

            return read_memory(base + phys_offset)
        else:
            # Page fault: missing brick
            return handle_page_fault(page_idx)

## Subtopics

### Virtual Texturing
Virtual texturing is similar to CPU virtual memory but applied in 2D/3D texture space [S2, unofficial]. It defines a virtual image or volume with the extent of the original data, performs domain decomposition of the virtual texture space into pages, stores the working set of physical pages in a cache texture, and uses a page table to map from virtual pages to physical pages [S2, unofficial]. Concepts were introduced by Kraus and Ertl in 2002 and Hadwiger et al. in 2005 [S2, unofficial].

### Hardware Virtual Textures
This variant refers to the specific API implementations of sparse textures that provide hardware-managed page tables [S2, unofficial]. It is implemented in OpenGL via `ARB_sparse_texture` and `ARB_sparse_texture2`, in Vulkan via `VK_IMAGE_CREATE_SPARSE_RESIDENCY_BIT`, and in CUDA via unified memory with on-demand page migration (though CUDA applies this only to regular global memory, not textures) [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** Address translation is $O(1)$ in hardware [G]. Page fault handling latency depends on the data source [G].
*   **Memory Complexity:** Physical memory usage scales with the number of resident pages, not the total volume size [S1].
*   **Strengths:** Lossless quality, hardware-managed translation, simple shader code [S1].
*   **Limitations:** Hardware limits on maximum texture dimensions (e.g., 16k for 3D) [S2, unofficial].
*   **When to use:** Rendering large, sparse volumes where only a small fraction is visible, and hardware sparse texture support is available [S1].

## Background
The concept of virtual texturing was introduced by Kraus and Ertl in 2002 and Hadwiger et al. in 2005 [S2, unofficial]. Hardware support for sparse textures was later introduced in modern graphics APIs like OpenGL, Vulkan, and Direct3D 12, allowing the GPU to handle page table management natively [S1][S2, unofficial].
