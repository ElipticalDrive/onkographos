# Hierarchical Vector Quantization

Also called: HVQ Compression, HVQ rendering, Hierarchical Decomposition, Hierarchical Vector Quantization (VQ) for Time-Varying Scalar Fields, Hierarchical Vector Quantization for Volume Rendering, VQ compression

## Overview
Hierarchical Vector Quantization (HVQ) is a lossy compression algorithm for volumetric data that achieves high compression ratios (typically ~20:1) with minimal artifacts by representing volume blocks as indices into learned codebooks [S2, S3, unofficial]. It is distinguished from sibling methods like [Wavelet Compression](52-wavelet-compression.md) and [S3 Texture Compression](958-s3-texture-compression.md) by its ability to decode and render compressed data directly on the GPU during the rendering pass, thereby minimizing CPU-to-GPU data transfer and circumventing limited texture memory [S2, S3, unofficial]. Unlike [Vector Quantization](907-vector-quantization.md) which uses a single dictionary, HVQ employs multiple resolution levels (codebooks) to capture both coarse and fine details, allowing for efficient handling of large-scale and time-varying data [S3, unofficial][S4].

## How it works
**Inputs:** Static or time-varying volumetric scalar data $S_t$ at time $t$ [S2, S3, unofficial].
**Outputs:** Compressed file containing headers, two codebooks (A and B), and RGB index triplets for rendering [S2, unofficial].

**Data Structures:**
1.  **Codebook A:** 256 entries, each 64-dimensional (stores difference level 1 vectors) [S2, unofficial]. Size: $256 \times 64$ bytes (assuming 8-bit elements).
2.  **Codebook B:** 256 entries, each 8-dimensional (stores detail level 1 vectors) [S2, unofficial]. Size: $256 \times 8$ bytes.
3.  **Index Texture:** RGB texture of size $(D_x'/4) \times (D_y'/4) \times (D_z'/4)$ [S2, unofficial]. Each voxel stores an RGB triplet where R, G, B are 8-bit indices into Codebook A, Codebook B, and a scalar mean value (or color) respectively [S2, S3, unofficial].
4.  **Header:**
    *   Flag (8-bit): Endianness indicator [S2, unofficial].
    *   Integer Size (bytes): Machine-independent integer size [S2, unofficial].
    *   Mode (variable): 1 if data is difference-encoded, 0 if original [S2, unofficial].
    *   Dimensions ($sizeX, sizeY, sizeZ$): $D_x'/4 \times D_y'/4 \times D_z'/4$ [S2, unofficial].
    *   $scaleDiff0$: Largest absolute value in difference level 0 [S2, unofficial].
    *   $scaleDetl0$: Largest absolute value in detail level 0 [S2, unofficial].
    *   Codebook A data [S2, unofficial].
    *   Codebook B data [S2, unofficial].
    *   RGB Triplets data [S2, unofficial].

**Parameters:**
*   Block Size: $4^3 = 64$ voxels [S2, unofficial].
*   Codebook Size: 256 entries (8-bit indices) [S2, unofficial].
*   Data Type: 8-bit integers for indices and difference values [S2, unofficial].
*   Interpolation: Nearest neighbor only during rendering [S3, unofficial].

**Steps:**

1.  **Preprocessing (Resampling):**
    If original dimensions $D_x, D_y, D_z$ are not powers of two, re-sample the volume to the nearest power-of-two dimensions (e.g., $60 \times 120 \times 79 \to 64 \times 128 \times 128$) using trilinear interpolation [S2, unofficial]. Let the re-sampled data be $S_t'$.

2.  **Preprocessing (Time Difference):**
    For time-varying data, exploit temporal redundancy by computing the difference between consecutive time steps:
    $$ D_t = S_{t+1}' - S_t' $$
    where $D_t$ is the difference volume and $S_t'$ is the re-sampled data at time $t$ [S2, unofficial]. This results in sparse data with many zeros, improving VQ performance [S2, unofficial].

3.  **Hierarchical Decomposition:**
    Divide the difference volume (or static volume) into disjoint $4^3$ blocks [S2, unofficial]. For each block, perform a multiresolution decomposition:
    *   **Step 3.1 (Level 0):** Divide the $4^3$ block into 8 disjoint $2^3$ sub-blocks [S2, unofficial]. Compute the mean value of each $2^3$ sub-block [S2, unofficial]. These 8 mean values form "Detail Level 0" (a down-sampled $2^3$ block) [S2, unofficial].
    *   **Step 3.2 (Level 1):** Compute the differences between the original 64 samples in the $4^3$ block and their corresponding mean values from Step 3.1 [S2, unofficial]. Store these 64 differences in an array. The mapping index for location $(x, y, z)$ in the $4^3$ block is:
        $$ idx = x + 4 \cdot y + 16 \cdot z $$
        where $x, y, z$ are coordinates within the block [S2, unofficial].
    *   **Step 3.3 (Mean):** Apply the same mean-computation process to the Detail Level 0 block ($2^3$) [S2, unofficial]. This yields one overall mean value for the entire $4^3$ block and 8 difference values (samples in Detail Level 0 relative to its mean) [S2, unofficial].
    *   **Step 3.4 (Storage Layout):** Replace the values in Detail Level 0 with the 8 differences from Step 3.3 to save memory [S2, unofficial]. The block is represented in memory as: Difference Level 1: Array of size 64 [S2, unofficial]; Detail Level 0: Array of size 8 [S2, unofficial]; Detail Level 1: Single variable (the overall mean) [S2, unofficial].

4.  **Covariance Analysis & Codebook Generation:**
    Perform covariance analysis on the original domain data at each resolution level to determine initial codebook entries [S3, unofficial]. **Codebook A (64-dim):** Generated from the 64-dimensional difference vectors (Step 3.2) [S2, unofficial]. **Codebook B (8-dim):** Generated from the 8-dimensional detail vectors (Step 3.3) [S2, unofficial]. Refine codebooks using the LBG algorithm [S2, S6, unofficial]. The number of entries is fixed to 256 [S2, unofficial].

5.  **Quantization:**
    For each decomposed block, find the best matching codeword in Codebook A for the 64-dim vector and Codebook B for the 8-dim vector [S2, unofficial]. Store the 8-bit indices for Codebook A and Codebook B. Store the overall mean value (or RGB color triplet if applicable) in the index texture [S2, unofficial].

6.  **GPU Rendering (Decoding):**
    Upload the index texture and Codebooks A and B to GPU memory as 2D dependent textures [S3, unofficial]. For each fragment, use the Pixel Shader API (DirectX9/OpenGL ARB fragment program) to look up the codewords using the RGB indices [S3, unofficial]. Reconstruct the scalar value by summing the mean, the decoded difference vector, and the decoded detail vector according to the hierarchical structure [S2, S6, unofficial]. Use early z-test to discard fragments decoding empty space [S3, unofficial].

    # block_64: list of 64 floats
    sub_blocks = [block_64[i*8:(i+1)*8] for i in range(8)]
    detail_0 = [sum(sb)/8.0 for sb in sub_blocks]
    diff_1 = []
    for i, sb in enumerate(sub_blocks):
        m = detail_0[i]
        diff_1.extend([v - m for v in sb])
    overall_mean = sum(detail_0) / 8.0
    diff_0 = [v - overall_mean for v in detail_0]
    return diff_1, diff_0, overall_mean

## Subtopics

### [Temporal/Spatial Vector Quantization](5743-temporal-spatial-vector-quantization.md)
Temporal/Spatial Vector Quantization (TSVQ) is a compression technique for multivariate time-varying volumetric data that groups voxels into blocks either along the temporal axis or the spatial axis to apply vector quantization algorithms. It differs from static volume compression by explicitly exploiting temporal coherence, and from purely spatial methods by allowing the grouping dimension to be chosen based on the data's coherence characteristics. Choose it when data exhibits strong directional coherence that static spatial methods miss.

### [Hierarchical Vector Quantization on Delta](5744-hierarchical-vector-quantization-on-delta.md)
Hierarchical Vector Quantization on Delta is a compression method for time-varying volumetric data that combines temporal delta encoding with hierarchical vector quantization (HVQ) to achieve high compression ratios while maintaining direct rendering capabilities on programmable graphics hardware. It sets itself apart from sibling methods like Temporal/Spatial Vector Quantization by explicitly decoupling temporal redundancy (via delta encoding) from spatial redundancy (via HVQ), allowing the quantization codebooks to adapt to the residual data distribution rather than the raw data. Choose it when rendering large time-varying datasets on GPUs with limited memory.

## Operating characteristics
**Time Complexity:** The computational complexity of HVQ is $O(N \times M)$, where $N$ is the number of blocks and $M$ is the number of dictionaries (hierarchy levels) [S4, S5]. For $M=1$, it reduces to standard VQ complexity. Pre-processing time is critical, especially for massive volumes, as dictionary generation is costly [S4].

**Memory Complexity:** The compressed size is significantly smaller than the original. For example, a $256^3$ dataset (16 MB) is encoded into 0.78 MB [S3, unofficial]. The codebooks occupy fixed memory (16384 bytes for A, 2048 bytes for B) [S2, unofficial].

**Performance:**
*   **Compression Ratio:** Achieves ~20:1 to 25:1 compression ratios with minimal artifacts [S2, S3, unofficial]. Visible Human data achieved 25.29:1 with 26.02 dB SNR [S3, unofficial].
*   **Rendering Speed:** On an ATI 9700, rendering a 256^3 uncompressed dataset (16 MB) runs at 11 fps, while a 70 MB compressed sequence of a 1.4 GB shock wave simulation runs at 24 fps at a 512^2 viewport [S3, unofficial].
*   **Quality:** Bits-per-sample (bps) of 0.63 (Chameleon), 0.17 (Supernova), and 0.71 (Turbulence) [S1, unofficial]. Debloked SSIM scores: 0.78 (Chameleon), 0.76 (Supernova), 0.89 (Turbulence) [S1, unofficial].

**Strengths:**
*   Minimal CPU-GPU data transfer due to on-the-fly GPU decoding [S2, unofficial].
*   Handles large datasets that exceed texture memory [S3, unofficial].
*   Exploits temporal coherence for time-varying data [S3, unofficial].
*   Early z-test optimization skips empty space [S3, unofficial].

**Limitations:**
*   Restricted to nearest-neighbor interpolation; trilinear interpolation is not natively supported and requires decoding 8 neighbors, which slows performance [S3, unofficial].
*   Dictionary size imposes a hard limit on quality and compression rate [S4].
*   Pre-processing time is high [S4].
*   Codebooks handle only 64 time instances in some implementations; switching codebooks can cause rendering stalls [S6, unofficial].
*   Highly sparse data allows lossless compression, but most volumetric data is not sparse enough for this [S2, unofficial].

## Background
HVQ was first introduced in volume rendering by [NH92, NH93] [S4]. The first GPU implementation was proposed by Schneider et al. in 2003 [S5, S4]. Fout et al. later combined HVQ with domain transformation [S5]. It is used in real-time rendering of large time-varying volumetric datasets, such as shock wave simulations and medical imaging, where minimizing data transfer and maximizing frame rates are critical [S2, S3, unofficial].
