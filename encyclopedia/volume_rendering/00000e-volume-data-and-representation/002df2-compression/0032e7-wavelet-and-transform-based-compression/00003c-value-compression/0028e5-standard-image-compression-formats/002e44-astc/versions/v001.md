# ASTC
Also called: ASTC Decompression, Adaptive Scalable Texture Compression

## Overview
ASTC is a flexible, hardware-supported, fixed-rate lossy compression method that uses various block-size configurations to cover a wide range of bit rates [S1][S2]. It solves the problem of efficient on-the-fly decompression for direct volume rendering by allowing real-time value reconstruction from voxel coordinates without storing the entire decompressed volume in memory [S1][S2]. It sets itself apart by proposing a general method for representing value sequences using a fractional number of bits per value and constructing per-texel color weights from sparse samples, aiming to improve upon standards like DXT, ETC2, and PVRTC [S1][S2].

## How it works
**Inputs and Outputs:**
*   Input: A compressed bitstream representing a block of volumetric data (texels/voxels).
*   Output: Reconstructed per-texel values (color weights) for the block.

**Data Structures:**
The specific binary layout of the ASTC bitstream is not detailed in the provided sources. The method relies on hardware support to interpret the compressed blocks [S1][S2].

**Steps:**
1.  **Block Configuration Selection:** The system selects a block-size configuration from a scalable set. This determines the spatial dimensions of the block (e.g., $3\times3\times3$ or $6\times6\times6$ for 3D textures) and the resulting bit rate [S1][S2].
2.  **Value Sequence Representation:** The method represents value sequences within the block using a fractional number of bits per value [S1][S2]. This allows for adaptive precision based on the block's content.
3.  **Weight Reconstruction:** A system constructs per-texel color weights from sparse samples encoded in the bitstream [S1][S2]. This step enables the reconstruction of the full block's values on-the-fly.
4.  **Real-time Rendering:** The reconstructed values are used directly during rendering, accessing voxel coordinates and reconstructing values in real-time, avoiding the need to store the entire decompressed volume [S1][S2].

**Parameters:**
*   **Block Sizes:** The method supports different block-size configurations. Specific examples for 3D textures include:
    *   $6\times6\times6$ blocks result in 0.56 bits per sample (bps) [S1][S2].
    *   $3\times3\times3$ blocks result in 4.74 bps [S1][S2].
*   **Bit Rate:** The method is fixed-rate, but the rate varies depending on the chosen block size [S1][S2].

**Edge Cases and Pitfalls:**
*   The 3D part of the full ASTC specification was noted as undergoing detailed evaluation for inclusion in next OpenGL releases at the time of the sources' writing, implying potential instability or lack of universal hardware support for 3D volumes [S1][S2].
*   Precision issues may arise from the "fractional number of bits per value" representation if not handled correctly by the hardware decoder [S1][S2].

## Operating characteristics
*   **Time and Memory Complexity:** The method allows rendering to be performed directly by accessing voxel coordinates and reconstructing values in real-time, requiring no additional memory to store the entire decompressed volume [S1][S2]. This implies $O(1)$ memory overhead per block during rendering, but the computational cost depends on the hardware decoder's efficiency.
*   **Measured Performance:** The sources claim results are competitive with advanced HW-supported formats and improve over DXT, ETC2, and PVRTC [S1][S2]. Specific performance metrics (FPS, compression ratio vs. quality) are not provided in the sources.
*   **Scaling:** The method is scalable via different block-size configurations, covering a wide range of bit rates [S1][S2].
*   **Strengths:** Hardware support, fixed-rate lossy compression, scalability, on-the-fly decompression, fractional bit representation for adaptability [S1][S2].
*   **Limitations:** The 3D specification was still under evaluation for OpenGL inclusion at the time of the sources, suggesting potential lack of mature hardware support or standardization for 3D volumes [S1][S2].
*   **When to use:** When hardware-accelerated, on-the-fly decompression of volumetric data is required, and the target platform supports ASTC (particularly for 3D if available).
*   **When not to use:** If the target hardware does not support ASTC, or if the 3D specification is not yet stable/available for the target platform [S1][S2].

## Background
ASTC (Adaptive Scalable Texture Compression) was introduced in [NLP* 12] [S1][S2]. It is an adaptation of Block Truncated Coding (BTC) that supports hardware-accelerated random access, sharing similarities with S3TC [S2]. It was proposed to improve upon industry standards such as DXT [Bro01], ETC2 [SP07], and PVRTC [Fen03] [S1][S2]. The method is particularly relevant for real-time rendering of time-varying volumetric datasets, where limited bandwidth makes compressed representations essential [S2]. The 3D part of the full ASTC specification was noted as undergoing detailed evaluation for inclusion in next OpenGL releases at the time of the sources' writing [S1][S2].
