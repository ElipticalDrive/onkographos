# Bin Coder

Also called: Hybrid Bin Coder Utilizing VV Codes, Hybrid Bin Scheme

## Overview
The Bin Coder is a zero-order entropy coding method that partitions a memoryless source into multiple sub-sources (bins) based on bit probability, encoding each with a specialized coder optimized for that specific probability range [S1, unofficial]. It solves the problem of efficiently encoding nonstationary or skewed bit streams by avoiding the computational overhead of arithmetic coding while maintaining high compression ratios through specialized codes (VV and Golomb) [S1, unofficial]. It differs from State-Tree Codes by dividing bits by probability rather than switching codes after parsing a string, and from Boliek et al.'s hardware bin coder by eliminating output interleaving overhead [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A stream of bits where each bit $i$ has an associated probability $q_i$ of being 1.
*   **Output:** A single compressed bitstream.

**Data Structures:**
The coder uses a fixed set of bins. The primary implementation described uses 22 bins [S1, unofficial]. Each bin is defined by:
*   **Bin Number:** Identifier (1–22).
*   **Bin Type:** Either "VV" (Viterbi-Viterbi) or "Golomb".
*   **Code q:** The probability threshold or range associated with the bin.
*   **W:** Maximum parse tree string length (for VV bins).
*   **C:** Maximum code length (for VV bins).

The 22-bin structure consists of 18 VV bins (Bins 1–18) and 4 Golomb bins (Bins 19–22) [S1, unofficial].

**Parameters:**
*   $q$: Probability of encountering a 1-bit.
*   $W$: Maximum parse tree string length for VV codes. Range: $7 \le W \le 15$ [S1, unofficial].
*   $C$: Maximum code length for VV codes. Range: $7 \le C \le 13$ [S1, unofficial].
*   Bins are defined at granularity 0.01 for $0.01 \le q \le 0.49$ [S1, unofficial].

**Algorithm Steps:**
1.  **Read Input:** Read the next bit from the input stream.
2.  **Determine Probability:** The probability modeler determines the current bit's probability $q$ of being 1.
3.  **Bin Assignment:** Assign the bit to the appropriate bin based on $q$.
    *   If $q \ge 0.04$, the bit is assigned to a VV bin.
    *   If $0 < q \le 0.04$, the bit is assigned to a Golomb bin [S1, unofficial].
4.  **Encode:**
    *   **VV Bins:** Accumulate bits in the bin. When a sufficient number of bits are accumulated, output a codeword using the precomputed VV code corresponding to the bin's $q$.
    *   **Golomb Bins:** Accumulate bits. Encode runs of bits using Golomb coding, optimized for the expected run lengths in this low-probability range [S1, unofficial].
5.  **Output:** Output the codewords directly to the final stream. **No interleaving** is performed between bins [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision at q ≈ 0.04:** At probabilities around 0.04, the inefficiency of merged VV codes exceeds 1%. This necessitates the switch to Golomb coding for $0 < q \le 0.04$ to maintain efficiency below 1% [S1, unofficial].
*   **Skewed Distributions:** Skewed probability distributions can cause experimental error in inefficiency measurements, particularly resulting in negative inefficiency for arithmetic coders due to insufficient measurement bits [S1, unofficial].
*   **Interleaving:** The hybrid bin scheme explicitly avoids interleaving to reduce overhead, which differs from other bin coder implementations [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Execution time is generally constant regardless of bit distribution, assuming incoming bits' probabilities are reasonably modeled [S1, unofficial].
*   **Memory Complexity:** Not given in the sources.
*   **Measured Performance:** Tested on a 1-GHz Intel Pentium III running Red Hat Linux. Execution time is an average over 5 runs [S1, unofficial]. The 25-bin hybrid coder improved best-case coding inefficiency from 0.27% to 0.23% at $x=1.1$ compared to the 22-bin version, with relatively unchanged execution time [S1, unofficial].
*   **Strengths:** Fast, simple mechanisms (Golomb and VV coding); consistent execution time across varying bit distributions; high performance for high-performance computing applications [S1, unofficial].
*   **Limitations:** Bin and code selection is manual in the described implementation; not suitable for sources with highly variable probability distributions that are not well-modeled by the fixed bins [S1, unofficial].
*   **When to Use:** High-performance computing applications where consistent execution time and high compression ratios are required for memoryless or near-memoryless sources [S1, unofficial].
*   **When Not to Use:** Sources with highly non-stationary probabilities that cannot be accurately modeled by the fixed bin probabilities; applications requiring dynamic adaptation to changing probability distributions without manual bin reconfiguration [S1, unofficial].

## Background
The Bin Coder was proposed in the context of length-limited data transformation and compression [S1, unofficial]. It was benchmarked against ELS-coder, Z-coder, and arithmetic coders [S1, unofficial]. The hybrid bin scheme was developed to address the inefficiency of VV codes at low probabilities by incorporating Golomb coding [S1, unofficial]. The 22-bin and 25-bin implementations were tested on nonstationary sources generated using the equation $P(i) = \frac{i^x}{2 \cdot 256^x}$ for $1 < x \le 10.1$ and $0 < i \le 256$ [S1, unofficial].
