# Table-Lookup Encoding/Decoding
Also called: Direct Lookup Table Method
## Overview
Table-Lookup Encoding/Decoding is a method for implementing entropy coders by replacing complex parsing logic with direct memory access to a precomputed table [S1, unofficial]. It solves the problem of computational overhead in parse-tree-based codes (such as BV, VB, and VV codes) by allowing the encoder or decoder to determine the next codeword and consumed input bits in a single memory operation [S1, unofficial]. It is distinguished from sibling methods like the Bin Coder by its reliance on a static, full-index lookup table rather than a collection of specialized zero-order coders [S1, unofficial][17560-bin-coder.md].

## How it works
**Inputs and Outputs:**
*   **Input:** A stream of bits representing the source data.
*   **Output:** A stream of bits representing the encoded codewords.
*   **Parameters:**
    *   $W$: The window size in bits. This must be equal to the length of the longest string on the parse tree for encoding, or the length of the longest codeword for decoding [S1, unofficial].
    *   $T$: The lookup table, an array of size $2^W$ [S1, unofficial].

**Data Structures:**
The lookup table $T$ contains $2^W$ entries. Each entry at index $i$ (where $0 \le i < 2^W$) stores three values:
1.  $l$: The number of bits actually consumed from the input stream for this match.
2.  $c$: The length of the resulting codeword.
3.  $code$: The actual codeword bits.

The size of the table is determined by $W$. If each entry is 32 bits wide, the total size is $2^W \times 32$ bits [S1, unofficial].

**Algorithm Steps:**
1.  Read the next $W$ bits from the input stream. Let this value be $idx$.
2.  Use $idx$ as an index into the lookup table $T$.
3.  Retrieve the entry $E = T[idx]$.
4.  Let $l = E.l$, $c = E.c$, and $code = E.code$.
5.  Advance the input stream pointer by $l$ bits.
6.  Advance the output stream pointer by $c$ bits.
7.  Write the bits in $code$ to the output stream.
8.  Repeat until the input stream is exhausted.

**Pseudocode:**
```python
def table_lookup_encode(input_bits, lookup_table, window_size):
    """
    Encodes input_bits using a direct lookup table.
    
    Args:
        input_bits: A list or buffer of bits (0 or 1).
        lookup_table: A list of tuples (l, c, code_bits) of size 2^window_size.
        window_size: The integer W.
        
    Returns:
        A list of bits representing the encoded output.
    """
    output_bits = []
    input_idx = 0
    n = len(input_bits)
    
    # Precompute the integer value of the window to avoid repeated bit extraction
    # Note: In a real implementation, bit extraction from a stream is handled 
    # via bit-shifting registers. Here we simulate reading W bits.
    
    while input_idx <= n - window_size:
        # Extract next W bits as an integer index
        # Assuming input_bits is a list of integers 0/1
        window_val = 0
        for k in range(window_size):
            window_val = (window_val << 1) | input_bits[input_idx + k]
            
        # Lookup table entry
        l, c, code_bits = lookup_table[window_val]
        
        # Advance input pointer by l bits
        input_idx += l
        
        # Append codeword to output
        output_bits.extend(code_bits)
        
    # Handle remaining bits if input length is not a multiple of window consumption
    # The source notes do not specify behavior for partial windows at EOF.
    # [G] Typically, remaining bits are either padded or handled by a special 
    # end-of-stream symbol. Without explicit source definition, this loop 
    # assumes valid input where W bits are always available for a valid parse.
    
    return output_bits
```

**Edge Cases and Pitfalls:**
*   **Table Size Explosion:** The table size grows exponentially with $W$. If the longest code length is 16 bits, a 32-bit entry table is 256 KB. If the longest code length is 20 bits, the table grows to 4 MB, a 1600% increase [S1, unofficial].
*   **Cache Performance:** If the table is excessively large, it will not fit in CPU cache, negating the speed benefits of the lookup [S1, unofficial].
*   **Worst-Case Input:** If there are $N$ possible inputs, the longest possible code length is $N-1$ bits, which makes the table size unmanageable ($2^{N-1}$ entries) [S1, unofficial].

## Subtopics

### [Bin Coder](17560-bin-coder.md)
A collection of zero-order entropy coders designed for specific probability ranges, covering 0.5 ≤ p ≤ 1.0. It avoids large lookup tables by using specialized small tables or logic for each bin, unlike the single large table of Table-Lookup Encoding.

## Operating characteristics
*   **Time Complexity:** Encoding and decoding are $O(1)$ per codeword, assuming table lookup is $O(1)$. The loop is described as "very tight" and fast [S1, unofficial].
*   **Memory Complexity:** $O(2^W)$, where $W$ is the window size. This is the primary constraint [S1, unofficial].
*   **Performance:** Extremely fast due to minimal computational overhead (no complex parsing or arithmetic) [S1, unofficial].
*   **Strengths:** High speed, simple implementation, low computational overhead [S1, unofficial].
*   **Limitations:** High memory usage for long codewords; cache misses if the table is large; not suitable for sources with very long codewords or large alphabets where $N$ is large [S1, unofficial].
*   **When to use:** When the parse tree or code lengths are short enough that the lookup table fits in cache, and speed is the primary concern [S1, unofficial].
*   **When not to use:** When the longest code length is large (e.g., > 20 bits) or the input alphabet size $N$ is large, leading to unmanageable table sizes [S1, unofficial].

## Background
The method was explored by the author of *Length-Limited Data Transformation and Compression* as a way to achieve fast compression rates for parse-tree-based codes (BV, VB, VV) where traditional methods like Run-Length or Golomb codes were either too slow or required specific probability distributions [S1, unofficial]. The approach was motivated by the observation that table lookups significantly reduce computational overhead compared to parsing [S1, unofficial].
