# Entropy Encoding

Also called: Arithmetic Coding, Data Compression and Encoding, Huffman Coding, Lossless Compression, 熵编码

## Overview
Entropy encoding is a lossless compression method that minimizes storage or transmission costs for a discrete dataset by mapping each data point to a variable-length bit string, which a receiver inverts to recover the exact original data [S2]. It solves the problem of redundant data representation by assigning shorter codewords to more frequent symbols and longer codewords to less frequent symbols [S3, S4, S5]. Unlike its parent [Arithmetic Encoding](2127-arithmetic-encoding.md), which anchors attributes into a binary bitstream using probabilities estimated by a context model, entropy encoding is the broader category of techniques that includes both Huffman coding and arithmetic coding, as well as variants like Golomb-Rice encoding [S4, S5]. It sets itself apart from siblings like [Variable-Length Coding](7012-variable-length-coding.md) by assigning codes based on symbol frequency rather than a fixed bit depth for a data block, and from [rANS](5011-rans-asymmetric-numeral-systems.md) by using the specific interval subdivision or tree-traversal logic defined below.

## How it works
Entropy encoding operates on a discrete dataset $X = (x_1, \dots, x_N)$ [S2]. The core principle is to exploit the statistical distribution of the input symbols to achieve a bit rate close to the Shannon entropy lower bound [S2].

### Inputs and Outputs
- **Input**: A sequence of symbols (e.g., voxel values, quantized coefficients, or codebook indices) $X$.
- **Output**: A binary bitstream representing the compressed data.

### Data Structures
The specific data structures depend on the variant (Huffman vs. Arithmetic).
- **Huffman**: A binary tree where leaves represent symbols and edges represent bits (0/1). Codebook indices are often stored as 32-bit unsigned integers before encoding [S1].
- **Arithmetic**: A current interval $[L, H)$ within $[0, 1)$ and a probability model for the symbols [S3].

### Formulas
The theoretical limit for compression is the Shannon entropy $H$, which provides the minimum expected number of bits per element [S2]:
$$ H = - \sum_{x} p_x(x) \log p_x(x) $$
where $p_x(x)$ is the underlying probability distribution of symbol $x$ [S2].

The bit rate $R(X)$ for the entire dataset $X$ is:
$$ R(X) = -\frac{1}{N} \sum_{i=1}^{N} \log p_x(x_i) $$
where $N$ is the number of elements [S2].

### Parameters
- **Probability Model**: The estimated probability $p_x(x)$ for each symbol. In practice, these are often derived from the frequency of occurrence in the data [S3].
- **Codebook Size**: Determines the bit-length required for indices if Huffman coding is used [S1].

### Steps (Huffman Coding)
Huffman coding assigns variable-length codewords based on symbol frequency [S3]. The algorithmic steps are [S3]:
1.  **Calculate Probabilities**: Determine the probability of each and every symbol in the input.
2.  **Sort Probabilities**: Arrange the symbol probabilities in decreasing order.
3.  **Merge Lowest Probabilities**: Iteratively merge the two lowest probabilities until only two probabilities remain. This builds the tree from the bottom up.
4.  **Generate Tree and Allocate Bits**: Generate the Huffman Tree based on the merged probabilities. Assign bits (0 for left, 1 for right, or vice versa) to the branches.
5.  **Encode/Decode**: Traverse the constructed Huffman Tree to assign codewords to symbols (encoding) or recover symbols from codewords (decoding).

### Steps (Arithmetic Coding)
Arithmetic coding represents a sequence of symbols as a real-valued interval of $[0, 1)$, narrowing the interval with each symbol [S3]. The steps are [S3]:
1.  **Initialize Range**: Take the range of real numbers as $[0, 1)$. Divide it into subranges according to the input symbols, where each subrange's size equals the source symbol probability.
2.  **Select Subrange**: For the first input symbol, find the subrange it belongs to.
3.  **Subdivide**: Subdivide the selected subrange again into smaller subranges proportional to the symbol probabilities.
4.  **Iterate**: Move to the next symbol and repeat the subrange finding process (Step 2) and subdivision (Step 3).
5.  **Terminate**: Repeat Steps 3 and 4 until all symbols in the input are parsed. The final interval represents the encoded data.

### Edge Cases and Pitfalls
- **Random Access**: Variable-length encoding hinders quick random access reconstruction, which is critical in massively parallel GPU settings [S4, S5]. Decoding requires significantly more computational work compared to fixed-length schemes [S4, S5].
- **Precision**: Arithmetic coding requires high-precision arithmetic to avoid interval collapse or overflow, though practical implementations use renormalization [S3].
- **Degenerate Input**: If a symbol has zero probability, it cannot be encoded. The probability model must account for all possible symbols or handle unseen symbols gracefully [G].

### Pseudocode (Huffman Encoding)
```python
def huffman_encode(data, symbol_probabilities):
    """
    Encodes data using Huffman coding.
    data: list of symbols
    symbol_probabilities: dict mapping symbol -> probability
    Returns: list of bits
    """
    # Step 1 & 2: Sort symbols by probability (descending)
    sorted_symbols = sorted(symbol_probabilities.items(), key=lambda x: x[1], reverse=True)
    
    # Step 3: Build Huffman Tree
    # Each node is (probability, symbol_or_none, left_child, right_child)
    # For simplicity, assume leaf nodes contain the symbol
    nodes = [(prob, sym, None, None) for sym, prob in sorted_symbols]
    
    while len(nodes) > 1:
        # Pick two nodes with lowest probabilities
        # Note: In a real implementation, use a priority queue
        nodes.sort(key=lambda x: x[0])
        left = nodes.pop(0)
        right = nodes.pop(0)
        
        # Merge them
        merged_prob = left[0] + right[0]
        merged_node = (merged_prob, None, left, right)
        nodes.append(merged_node)
        
    root = nodes[0]
    
    # Step 4 & 5: Generate Codewords by traversing tree
    codewords = {}
    def traverse(node, current_code):
        if node[1] is not None: # Leaf node
            codewords[node[1]] = current_code
            return
        if node[2] is not None: # Left child
            traverse(node[2], current_code + '0')
        if node[3] is not None: # Right child
            traverse(node[3], current_code + '1')
            
    traverse(root, "")
    
    # Encode data
    bitstream = []
    for symbol in data:
        bitstream.extend(codewords[symbol])
        
    return bitstream
```

### Pseudocode (Arithmetic Encoding)
```python
def arithmetic_encode(data, symbol_probabilities):
    """
    Encodes data using Arithmetic coding.
    data: list of symbols
    symbol_probabilities: dict mapping symbol -> probability
    Returns: list of bits
    """
    # Initialize range [L, H)
    L = 0.0
    H = 1.0
    
    # Precompute cumulative probabilities for efficient subrange lookup
    sorted_syms = sorted(symbol_probabilities.keys())
    cum_probs = []
    current = 0.0
    for sym in sorted_syms:
        current += symbol_probabilities[sym]
        cum_probs.append((sym, L, current)) # sym, low, high
        L = current
        
    bitstream = []
    
    for symbol in data:
        # Find subrange for the symbol
        low = 0.0
        high = 0.0
        for sym, l, h in cum_probs:
            if sym == symbol:
                low = l
                high = h
                break
        
        # Update range
        range_size = H - L
        new_H = L + range_size * high
        new_L = L + range_size * low
        L = new_L
        H = new_H
        
        # Renormalization (simplified)
        # In practice, bits are emitted when L and H share the same leading bit
        # This is a simplified placeholder for the bit emission logic
        while True:
            if H < 0.5:
                bitstream.append('0')
                # Emit 0 and shift
                L *= 2
                H *= 2
            elif L >= 0.5:
                bitstream.append('1')
                # Emit 1 and shift
                L = (L - 0.5) * 2
                H = (H - 0.5) * 2
            else:
                break
                
    return bitstream
```

## Subtopics

### [Variable-Length Coding](7012-variable-length-coding.md)
Variable-Length Coding (VLC) is a lossless compression technique for volume data that reduces storage by encoding voxel values relative to a base value within a data block (brick). It solves the problem of inefficient fixed-width storage when data values in a local region have a small dynamic range. Unlike its parent [Entropy Encoding](5360-entropy-encoding.md), which assigns codes based on symbol frequency, VLC assigns a fixed bit depth $n$ to an entire brick based on its local value range.

### [Entropy Coding Implementation](12628-entropy-coding-implementation.md)
Entropy coding implementation finalizes the compression of volumetric data by mapping quantized syntax elements to bitstreams using statistical models. It solves the problem of residual storage overhead after prediction and quantization. Unlike [Variable-Length Coding](7012-variable-length-coding.md), which relies on fixed prefix codes, this method typically employs arithmetic coding or Huffman coding to achieve near-entropy-limit compression ratios.

### Golomb-Rice Encoding
Golomb-Rice encoding is an entropy encoder favored over arithmetic and Huffman coding for volume rendering because it has better random access capabilities due to its lower computational complexity [S5]. It is particularly useful when quick random access reconstruction is required in massively parallel GPU settings, where the variable-length nature of standard entropy encoders hinders performance [S4, S5].

## Operating characteristics
- **Time Complexity**: Encoding and decoding time depends on the specific algorithm. Huffman coding requires tree traversal, which is $O(\log K)$ per symbol where $K$ is the alphabet size, but can be optimized with lookup tables. Arithmetic coding involves interval updates and is generally more computationally expensive than Huffman coding [S6, unofficial].
- **Memory Complexity**: Huffman coding requires storing the tree structure. Arithmetic coding requires storing the current interval and probability model. Both are generally low compared to the data size they compress.
- **Measured Performance**: Arithmetic coding provides better compression ratios than Huffman coding but is more computationally expensive [S6, unofficial]. Golomb-Rice encoding offers a trade-off with lower computational complexity and better random access [S5].
- **Strengths**: High compression ratios for data with skewed probability distributions; lossless reconstruction.
- **Limitations**: Variable-length encoding hinders quick random access reconstruction, which is critical in massively parallel GPU settings [S4, S5]. Decoding requires significantly more computational work [S4, S5].
- **When to Use**: When storage or transmission cost is the primary concern and random access is not critical, or when combined with other techniques (like RLE) to accelerate decoding [S4, S5].
- **When Not to Use**: When fast random access is required for interactive rendering on GPUs, in which case Golomb-Rice or fixed-length schemes might be preferred [S4, S5].

## Background
Entropy encoding is a fundamental technique in data compression, rooted in Shannon's source coding theorem [S2]. Huffman coding, introduced by David A. Huffman in 1952, is a classic algorithm that assigns variable-length codewords based on symbol frequency [S3]. Arithmetic coding, developed later, represents sequences as intervals and can achieve compression closer to the Shannon entropy limit, especially for non-integer bit lengths [S2, S3]. In the context of volume rendering, entropy encoding is frequently used in compressed volume rendering, often combined with Run-Length Encoding (RLE) or prediction methods like DPCM to improve compression ratios [S5][S6, unofficial]. It is commonly used in conjunction with DPCM and prediction methods [S6, unofficial]. The technique is widely used in compressed GPU-based direct volume rendering, where it helps reduce the memory bandwidth requirements [S4, S5].
