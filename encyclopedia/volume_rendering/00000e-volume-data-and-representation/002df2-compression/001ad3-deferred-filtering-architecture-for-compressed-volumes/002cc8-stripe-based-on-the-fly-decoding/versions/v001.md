# Stripe-based On-the-fly Decoding

Also called: Fraedrich stripe decoding, Stripe-based Block Decompression (Fraedrich)

## Overview
Stripe-based On-the-fly Decoding is a GPU-accelerated technique for decompressing compressed volume data blocks directly into renderable textures during a single rendering pass [S1][S2]. It solves the problem of high memory bandwidth and latency associated with transferring fully decompressed data from CPU or system memory to the GPU by performing the decompression as a fragment shader operation. It sets itself apart from sibling methods like [Compression Domain Rendering](960-compression-domain-rendering.md) by operating in the spatial domain (decoding to scalar values) rather than the transform domain, allowing for standard volume rendering pipelines while maintaining the benefits of compression [S1][S2].

## How it works
The method relies on the parallel processing capabilities of the GPU's fragment shader unit to decode compressed blocks in parallel.

**Inputs and Outputs:**
*   **Input:** A compressed data block (typically a 3D sub-volume) and its associated index/encoding metadata.
*   **Output:** A set of render targets (textures) containing the decoded scalar voxel values, ready for use in a subsequent volume rendering pass.

**Data Structures:**
*   **Compressed Block:** The specific format depends on the underlying compression scheme (e.g., DXT, ETC, or custom sequential compression). The sources do not specify a single universal bit-packing layout, but note that the approach is general for "common sequential data compression schemes" [S1][S2].
*   **Index Texture:** A texture storing the block indices or metadata required to identify which part of the compressed data corresponds to which spatial location. Its dimensions match the spatial extent of the block being decoded.

**Steps:**
1.  **Stripe Decomposition:** The 3D block of voxels is conceptually decomposed into parallel stripes. In the context of the GPU implementation, these stripes correspond to the fragments processed by the fragment shader [S1][S2].
2.  **Quad Rendering:** A single quad (two triangles forming a rectangle) is rendered. The dimensions of this quad are set to match the size of the index texture associated with the block [S1][S2].
3.  **Fragment Decoding:** For each fragment generated by the rasterizer of the quad:
    a. The fragment shader reads the corresponding index/metadata from the index texture.
    b. The shader uses this metadata to locate and decode the relevant portion of the compressed data.
    c. The fragment decodes one "stripe" of the block. In a 3D context mapped to a 2D fragment shader, this typically implies decoding a slice or a set of voxels along one dimension per fragment invocation, or mapping the 3D block to the 2D quad such that each fragment handles a specific voxel or small group of voxels [S1][S2]. *Note: The sources describe "parallel stripes of voxels" and "each fragment decodes one stripe," implying a mapping where the 2D fragment grid covers the 3D block's extent, likely flattening one dimension or processing slices.*
4.  **Write to Render Targets:** The decoded scalar values are written into different color channels of multiple render targets (MRTs). If the data type requires more than 4 channels (e.g., RGBA), multiple render targets are used to store the complete voxel data [S1][S2].
5.  **Subsequent Rendering:** The resulting render targets are bound as textures and used in a standard volume rendering pass (e.g., ray casting) to visualize the data [S1][S2].

**Parameters:**
*   **Block Size:** Not given in the sources.
*   **Stripe Width:** Not given in the sources.
*   **Compression Scheme:** The method is general, but examples in the sources mention DXT, ETC2, PVRTC, and ASTC as industry standards it aims to improve upon or compete with [S1][S2].

**Edge Cases and Pitfalls:**
*   **Precision:** The sources do not discuss precision issues, but writing to color channels (typically 8-bit or 16-bit) may limit the precision of the decoded scalar values compared to the original data [S1][S2].
*   **Boundary Conditions:** The mapping of 3D blocks to 2D fragments must handle block boundaries correctly. If a block does not align with the fragment grid, padding or partial decoding may be required [G].
*   **Degenerate Input:** If the compressed data is corrupted or the index is invalid, the decoding step will fail. Error handling is not discussed in the sources [S1][S2].

## Subtopics

### [Independent Block Encoding](5373-independent-block-encoding.md)
A local encoding pass that works independently on blocks, potentially using information gathered during a global step (e.g., learned dictionaries). It is often applied within a multiresolution framework encoding blocks at various resolution levels obtained by digital filtering and subsampling. This encoding strategy complements the decoding approach by defining how the data is structured before it is striped and decoded.

## Operating characteristics
*   **Time Complexity:** The decoding time is proportional to the number of fragments rendered, which corresponds to the number of voxels in the block. Since it is done in parallel on the GPU, the effective time is low, limited by the fragment shader execution speed and memory bandwidth [S1][S2].
*   **Memory Complexity:** The method requires memory for the compressed data, the index texture, and the multiple render targets for the decoded data. It avoids storing the fully decompressed data in system memory, reducing overall memory pressure [S1][S2].
*   **Measured Performance:** The sources do not provide specific performance benchmarks for this method. They mention it as an improvement over industry standards like DXT, ETC2, and PVRTC, but do not quantify the improvement [S1][S2].
*   **Strengths:**
    *   On-the-fly decoding reduces memory bandwidth requirements.
    *   Leverages GPU parallelism for fast decompression.
    *   Compatible with standard volume rendering pipelines [S1][S2].
*   **Limitations:**
    *   Requires GPU support for fragment shaders and multiple render targets.
    *   The decoding logic is embedded in the shader, which may be complex to implement for arbitrary compression schemes [S1][S2].
    *   Precision may be limited by the color channel format [G].
*   **When to Use:** When rendering large compressed volumes on GPU with limited memory bandwidth, and when the compression scheme can be efficiently decoded in a fragment shader [S1][S2].
*   **When Not to Use:** When the compression scheme is too complex to decode in a fragment shader, or when higher precision is required than what color channels can provide [G].

## Background
The method was proposed by Fraedrich et al. in 2007 [S1][S2]. It is part of the broader field of compressed GPU-based direct volume rendering, which seeks to optimize the rendering of large volumetric datasets by keeping data in compressed format as long as possible [S1][S2]. The approach is discussed in the context of improving upon existing industry compression standards like DXT, ETC2, and PVRTC, and relates to the evaluation of the 3D part of the ASTC specification [S1][S2].
