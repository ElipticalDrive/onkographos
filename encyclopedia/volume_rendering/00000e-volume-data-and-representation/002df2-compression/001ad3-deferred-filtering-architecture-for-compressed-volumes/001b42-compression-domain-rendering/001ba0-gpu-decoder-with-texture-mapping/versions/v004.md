# GPU Decoder with Texture Mapping

Also called: Texture-based VQ decoding

## Overview
This method reconstructs volumetric data values on the GPU by mapping output coordinates to texture memory indices, retrieving codebook vectors via dependent texture fetches, and combining them with mean values [S1, unofficial]. It differs from CPU-based decoding by moving the decoding process to the GPU to minimize data exchange between main memory and GPU memory, leveraging texture hardware for parallel reconstruction of compressed vector-quantized data [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Compressed volumetric data consisting of a 3D texture $I$ containing RGB triplets, a 2D texture $C_a$ for Codebook A (difference vectors), and a 2D texture $C_b$ for Codebook B (detail vectors) [S1, unofficial].
*   **Output:** Reconstructed scalar volumetric value $w(x, y, z)$ for each voxel coordinate $(x, y, z)$ [S1, unofficial].

**Data Structures and Layout:**
*   **Texture $I$ (RGB Triplets):** A 3D texture storing indices and mean values [S1, unofficial]. The dimensions are $D_x' \times D_y' \times D_z'$, where $D_x' = D_x/4$, $D_y' = D_y/4$, and $D_z' = D_z/4$ [S1, unofficial]. Each texel contains three components: $r$ (8-bit index for Codebook A), $g$ (8-bit index for Codebook B), and $b$ (mean value) [S1, unofficial].
*   **Texture $C_a$ (Codebook A):** A 2D texture storing difference vectors for 4x4x4 blocks [S1, unofficial]. Dimensions are $256 \times 64$ [S1, unofficial]. The $s$-coordinate corresponds to the index in $I.r$, and the $w$-coordinate (0–63) corresponds to the local position within the 4x4x4 block [S1, unofficial].
*   **Texture $C_b$ (Codebook B):** A 2D texture storing detail vectors for 2x2x2 blocks [S1, unofficial]. Dimensions are $256 \times 8$ [S1, unofficial]. The $s$-coordinate corresponds to the index in $I.g$, and the $w$-coordinate (0–7) corresponds to the local position within the 2x2x2 block [S1, unofficial].

**Coordinate Mapping:**
The global voxel coordinates $(x, y, z)$ are mapped to texture coordinates as follows:
1.  **Block Index:** The base coordinates in texture $I$ are calculated using integer division:
    $$ x' = \lfloor x/4 \rfloor, \quad y' = \lfloor y/4 \rfloor, \quad z' = \lfloor z/4 \rfloor $$
    Constraints: $0 \le x' < D_x'$, $0 \le y' < D_y'$, $0 \le z' < D_z'$ [S1, unofficial].
2.  **Local Indices:**
    *   For Codebook A (4x4x4 block), the local index $w_a$ is:
        $$ w_a = (x \bmod 4) + 4 \cdot (y \bmod 4) + 16 \cdot (z \bmod 4) $$
    *   For Codebook B (2x2x2 block), the local index $w_b$ is:
        $$ w_b = \lfloor (x \bmod 4)/2 \rfloor + 2 \cdot \lfloor (y \bmod 4)/2 \rfloor + 4 \cdot \lfloor (z \bmod 4)/2 \rfloor $$
    The local indices $w_a$ and $w_b$ are derived from the modulo arithmetic of the voxel coordinates [S1, unofficial].

**Decoding Formula:**
The reconstructed value $w(x, y, z)$ is computed by substituting the mappings into the general decoding equation [S1, unofficial]:
$$ w(x, y, z) = I(\lfloor x/4 \rfloor, \lfloor y/4 \rfloor, \lfloor z/4 \rfloor) \cdot b + C_b(I(\lfloor x/4 \rfloor, \lfloor y/4 \rfloor, \lfloor z/4 \rfloor) \cdot g, w_b) + C_a(I(\lfloor x/4 \rfloor, \lfloor y/4 \rfloor, \lfloor z/4 \rfloor) \cdot r, w_a) $$
Where:
*   $I(\dots) \cdot b$ is the mean value retrieved from the blue component of texture $I$ [S1, unofficial].
*   $C_a(\dots)$ retrieves the difference vector from Codebook A using the red component of $I$ as the $s$-coordinate and $w_a$ as the $w$-coordinate [S1, unofficial].
*   $C_b(\dots)$ retrieves the detail vector from Codebook B using the green component of $I$ as the $s$-coordinate and $w_b$ as the $w$-coordinate [S1, unofficial].

**Implementation Details and Pitfalls:**
*   **Texture Coordinates:** GPU texture coordinates are floating-point values in the range $[0.0, 1.0]$ [S1, unofficial]. Integer voxel coordinates $(x, y, z)$ must be normalized to this range before sampling [S1, unofficial].
*   **Arithmetic Operations:** The programming language Cg (used for portability to GLSL on ATI GPUs) does not support bitwise operations (e.g., `&`, `>>`) [S1, unofficial]. Therefore, $\lfloor x/4 \rfloor$ must be implemented using arithmetic division (e.g., `floor(x / 4.0)`) and $x \bmod 4$ using the modulo operator or subtraction, rather than bitwise shifts or ANDs [S1, unofficial].
*   **Precision:** The indices $r$ and $g$ are 8-bit values, allowing for 256 entries in each codebook [S1, unofficial].

**Pseudocode:**
```python
import math

def decode_voxel(x, y, z, I, Ca, Cb):
    # 1. Calculate block indices (floor division)
    # Cg does not support bitwise shift, so use float division and floor
    x_prime = int(x / 4.0)
    y_prime = int(y / 4.0)
    z_prime = int(z / 4.0)
    
    # 2. Sample the RGB triplet from texture I
    # In a real shader, this is a texture lookup. Here we assume direct component access.
    r_index = I[x_prime, y_prime, z_prime][0]
    g_index = I[x_prime, y_prime, z_prime][1]
    mean_val = I[x_prime, y_prime, z_prime][2]
    
    # 3. Calculate local indices for Codebook A (4x4x4 block)
    # Cg does not support bitwise AND, so use modulo
    x_mod_4 = x % 4
    y_mod_4 = y % 4
    z_mod_4 = z % 4
    
    w_a = x_mod_4 + 4 * y_mod_4 + 16 * z_mod_4

    # 4. Calculate local indices for Codebook B (2x2x2 block)
    # Using floor division on the modulo results
    w_b = int(x_mod_4 / 2.0) + 2 * int(y_mod_4 / 2.0) + 4 * int(z_mod_4 / 2.0)

    # 5. Retrieve vectors from Codebook Textures
    # Ca is 2D texture: s = r_index, t = w_a
    # Cb is 2D texture: s = g_index, t = w_b
    # Standard texture normalization maps discrete indices to [0.0, 1.0] [G]
    s_a = r_index / 255.0
    t_a = w_a / 63.0
    diff_a = Ca[s_a, t_a]
    
    s_b = g_index / 255.0
    t_b = w_b / 7.0
    diff_b = Cb[s_b, t_b]

    # 6. Compute final value
    w = mean_val + diff_b + diff_a
    
    return w
```

## Operating characteristics
*   **Time Complexity:** $O(1)$ per voxel, as decoding involves a constant number of texture lookups and arithmetic operations [G].
*   **Memory Complexity:** The memory footprint is determined by the size of the compressed data: $D_x' D_y' D_z'$ triplets for indices/means, plus $256 \times 64$ entries for Codebook A and $256 \times 8$ entries for Codebook B [S1, unofficial].
*   **Performance:** The method is optimized for real-time rendering by minimizing data exchange between main memory and GPU memory [S1, unofficial].
*   **Strengths:** High compression ratio, real-time capability on GPU hardware, portability across GPU vendors via Cg/GLSL compilation [S1, unofficial].
*   **Limitations:** Limited by the fixed codebook sizes (256 entries), which may reduce accuracy for complex data distributions [S1, unofficial]. The lack of bitwise operations in older GPU shading languages (like Cg) requires less efficient arithmetic alternatives [S1, unofficial].

## Background
This method was developed as part of a system for real-time rendering of compressed time-varying volume data [S1, unofficial]. It addresses the bottleneck of data exchange between main memory and GPU memory by moving the decoding process to the GPU [S1, unofficial]. The approach uses Vector Quantization (VQ) with two codebooks (Codebook A for difference levels and Codebook B for detail levels) and stores the compressed data in GPU texture memory [S1, unofficial]. The implementation utilized the Cg programming language to ensure portability between NVIDIA and ATI GPUs, as Cg could compile to GLSL for ATI hardware, unlike CUDA which was NVIDIA-specific at the time [S1, unofficial].
