# Compression Domain Rendering

Also called: Hardware accelerated texture decoding, On-chip decoding

## Overview
Compression Domain Rendering is a technique that reconstructs volumetric data on the GPU per-fragment by fetching indices from a compressed RGB index texture, using dependent texture fetches to retrieve difference vectors from codebook textures, and adding them to the mean value [S1, unofficial]. It differs from CPU-based decoding by minimizing data transfer between main memory and GPU memory, leveraging the GPU's texture hardware for parallel reconstruction of compressed vector-quantized data [S1, unofficial].

## How it works
**Inputs and Outputs**
*   **Input:** A compressed volumetric dataset represented as a 3D index texture $I$ and two dependent codebook textures $C_1$ and $C_2$. The index texture stores RGB values where $R$ is the mean value, and $G, B$ are indices into the codebooks. An address texture $A$ provides relative coordinates within codewords.
*   **Output:** Color and opacity values drawn to the framebuffer.

**Data Structures**
*   **Index Texture $I$:** A 3D texture map. Each texel is an RGB vector. The resolution is $1/4$ of the original data size in every dimension (assuming $4^3$ blocks).
*   **Codebook Textures $C_1, C_2$:** Dependent 2D textures storing difference vectors.
*   **Address Texture $A$:** A 3D texture of the same size as the encoded texel region ($4^3$ in the example). It stores relative addresses to access components within a codeword.
    *   $R$-component of $A$: Stores 64 different addresses to index $C_1$.
    *   $G$-component of $A$: Stores 8 different addresses to index $C_2$. Blocks of $2^3$ adjacent texels share the same address.

**Parameters**
*   **Texture Coordinate Wrap Mode:** `GL_REPEAT` for the index texture [S1, unofficial].
*   **Address Texture Interpolation:** Nearest neighbor [S1, unofficial].

**Algorithm Steps**
1.  **Slicing:** Render the 3D index texture sliced in back-to-front or front-to-back order via planes orthogonal to the viewing direction. The number of slices must be sufficient to render the original data, accounting for the expansion of each texel to a $4^3$ block [S1, unofficial].
2.  **Index Fetch:** For each fragment, fetch the texture sample from the index texture $I$. Let the sample be $I_{rgb} = (I_r, I_g, I_b)$.
3.  **Codebook Fetch:**
    *   Use $I_g$ and $I_b$ to determine the $s$ texture coordinates for $C_1$ and $C_2$.
    *   Determine the $t$ texture coordinates using the address texture $A$. Let $A_{rgb} = (A_r, A_g, A_b)$.
    *   Fetch the difference vector from $C_1$ using coordinates $(I_g, A_r)$. Let this be $d_1$.
    *   Fetch the difference vector from $C_2$ using coordinates $(I_b, A_g)$. Let this be $d_2$.
4.  **Reconstruction:** Add the mean value $I_r$ to the fetched difference information. The final scalar value $v$ is:
    $$ v = I_r + d_1 + d_2 $$
    [S1, unofficial]
5.  **Shading:** Map the final scalar value $v$ to color and opacity via a 1D dependent texture map (color table).
6.  **Rendering:** Draw the color and opacity to the framebuffer.

**Pseudocode**
```python
# Fragment shader logic for Compression Domain Rendering
# Inputs:
#   I: 3D Index Texture (GL_REPEAT wrap)
#   C1: 2D Codebook Texture 1
#   C2: 2D Codebook Texture 2
#   A: 3D Address Texture (Nearest Neighbor interpolation)
#   ColorTable: 1D Texture for scalar-to-color/opacity mapping
#   fragCoord: Current fragment coordinates in the slice

# 1. Fetch index sample
# Note: fragCoord must be scaled appropriately for the compressed resolution
# and wrapped if necessary.
I_sample = texture(I, fragCoord)
mean_val = I_sample.r
index_g = I_sample.g
index_b = I_sample.b

# 2. Fetch address sample
# The address texture is repeated over the domain.
# fragCoord for A should align with the block structure.
A_sample = texture(A, fragCoord)
addr_r = A_sample.r
addr_g = A_sample.g

# 3. Fetch difference vectors from dependent textures
# C1 is indexed by (index_g, addr_r)
diff1 = texture(C1, vec2(index_g, addr_r))

# C2 is indexed by (index_b, addr_g)
diff2 = texture(C2, vec2(index_b, addr_g))

# 4. Reconstruct scalar value
scalar_value = mean_val + diff1 + diff2

# 5. Map to color and opacity
color_opacity = texture(ColorTable, scalar_value)

# 6. Output
gl_FragColor = color_opacity
```

**Edge Cases and Pitfalls**
*   **Slice Count:** Because each texel of the index texture is expanded to a $4^3$ block during rendering, care must be taken to perform the slicing with as many slices as necessary to render the original data [S1, unofficial].
*   **Address Texture Size:** The address texture only holds addresses for one single block. An enlarged texture as large as the original dataset would allow correct addressing but negates memory savings. The solution is to use `GL_REPEAT` for the index texture and periodically repeat the address texture over the domain [S1, unofficial].
*   **Performance:** There is a loss in performance of about a factor of 2-3 compared to rendering uncompressed data, primarily due to the overhead of dependent texture fetches and shader execution [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The per-fragment cost involves multiple texture fetches (index, address, two codebooks, color table). The total time is proportional to the number of fragments and the cost of dependent texture lookups.
*   **Memory Complexity:** The index texture is $1/4$ the size of the original data in every dimension, resulting in a significant reduction in memory footprint compared to uncompressed data. The codebook textures and address texture add overhead but are generally small relative to the full dataset.
*   **Performance:** The method suffers a performance loss of a factor of 2-3 compared to rendering uncompressed data [S1, unofficial]. This is attributed to the computational cost of the on-chip decoding process.
*   **Strengths:** Minimizes data transfer between main memory and GPU memory. Leverages GPU texture hardware for parallel reconstruction.
*   **Limitations:** Performance overhead compared to uncompressed rendering. Requires careful handling of texture coordinates and slicing to ensure correct reconstruction of the original data blocks.

## Background
Compression Domain Rendering was introduced in a 2003 paper by researchers at the Technical University of Munich (TUM) [S1, unofficial]. The method addresses the challenge of rendering massive volumetric datasets by keeping data in compressed format at all stages except during transient local reconstruction. It builds on the Deferred Filtering Architecture for Compressed Volumes, which coordinates visibility- and resolution-aware adaptive data loading with GPU-accelerated per-frame data decompression, deblocking, and rendering.
