# Volume Loading and Preprocessing

Also called: CT Volume Loading

## Overview
This method ingests volumetric data from medical imaging formats and raw files, performing normalization, coordinate alignment, and memory preparation for downstream rendering [S1, S2, S3, unofficial]. It distinguishes itself by combining MONAI-based tensor pipelines for spacing and intensity scaling with brick-based out-of-core loading that includes thread-level pre-processing and empty-brick optimization [S1, S3, unofficial].

## How it works
### Inputs and Outputs
- **Inputs**: Source files (DICOM series, raw binary slices, or SciData files), configuration parameters (target voxel spacing, intensity clipping ranges, thresholds) [S1, S2, S3, unofficial].
- **Outputs**: A normalized, contiguous volume tensor or brick grid aligned to a world coordinate system, ready for GPU upload [S1, S2, S3, unofficial].

### Data Structures
1. **Volume Tensor**: A 3D array of voxels. In MONAI-based workflows, this is a PyTorch tensor with shape `(1, C, D, H, W)` after batch expansion [S1, unofficial].
2. **BrickGrid**: A 3D structure indexed by `(x, y, z)` brick coordinates for out-of-core storage [S2, unofficial].
3. **Affine Matrix**: A 4x4 matrix representing the transformation from voxel indices (IJK) to world coordinates (RAS) [S1, unofficial].

### Steps
1. **Metadata Extraction**: Extract the IJK-to-RAS affine matrix from volume metadata [S1, unofficial]. For Ocean Data, parse SciData files to determine location and concentration bounds [S2, unofficial].
2. **Intensity Pre-processing**: Apply scaling methods to convert raw values to a standard range [S3, unofficial]. 
   - **Scale**: Divide each value $v$ by a user-defined constant $C$: $v' = v / C$.
   - **ScaleToMax**: Divide each value by the channel's approximate maximum $M$ (determined from the lowest resolution representation): $v' = v / M$.
   - **LogTransform**: Apply the common logarithm: $v' = \log_{10}(v)$.
   - **Thresholding**: Apply user-defined bounds $min, max \in [0, 1]$. Values outside $[min \times 255, max \times 255]$ are set to zero [S3, unofficial].
3. **Coordinate Alignment**: Compute the inverse affine matrix $A_{ras \to ijk} = A_{ijk \to ras}^{-1}$ for use in rendering shaders [S1, unofficial].
4. **Resampling & Spacing**: Apply target voxel spacing (e.g., `[2.5, 2.5, 3.0]` mm) using interpolation to map source voxels to the target grid [S1, unofficial].
5. **Intensity Clipping & Scaling**: Clip values to a specified range (e.g., $[-3024, 3024]$ for HU) and scale to $[0, 1]$: $v_{final} = (v_{clipped} - v_{min}) / (v_{max} - v_{min})$ [S1, unofficial].
6. **Memory Layout & GPU Upload**: Add a batch dimension with `unsqueeze(0)` [S1, unofficial]. Move the tensor to CUDA [S1, unofficial]. For brick-based loading, initialize `BrickGrid` with resolution `vol_res.x(), vol_res.y(), vol_res.z()` [S2, unofficial]. Iterate over the Y-axis from $0$ to $\lfloor vol\_res.y() \rfloor$, compute offsets, and load slices via `loadVolSlice` [S2, unofficial]. Check index bounds before setting brick data [S2, unofficial]. If a brick contains only zero values after pre-processing, transmit a special `EMPTY` value instead of the brick data [S3, unofficial].

### Pseudocode
```python
def load_and_preprocess_volume(file_paths, config):
    raw_slices = []
    affine_ijk_to_ras = None
    for path in file_paths:
        # Read file bytes and parse slice values
        with open(path, 'rb') as f:
            data = f.read()
        raw_slices.append(parse_slice_values(data))
        if affine_ijk_to_ras is None:
            # Extract 4x4 affine matrix from file metadata
            affine_ijk_to_ras = extract_affine_from_metadata(data)
    
    # Flatten slices into a single volume array
    volume = [v for s in raw_slices for v in s]
    
    # Step 2: Intensity Pre-processing
    if config.scale_method == 'scale':
        volume = [v / config.scale_constant for v in volume]
    elif config.scale_method == 'scaleToMax':
        max_val = max(volume)
        volume = [v / max_val for v in volume]
    elif config.scale_method == 'logTransform':
        volume = [math.log10(v) for v in volume]
        
    # Step 3: Thresholding
    min_thresh = config.threshold_min * 255
    max_thresh = config.threshold_max * 255
    volume = [max(0, min(v, max_thresh)) if min_thresh <= v <= max_thresh else 0 for v in volume]
    
    # Step 4: Coordinate Alignment
    affine_ras_to_ijk = invert_matrix(affine_ijk_to_ras)
    
    # Step 5: Resampling & Spacing
    if config.spacing is not None:
        volume = resample_volume(volume, config.spacing)
        
    # Step 6: Intensity Clipping & Scaling
    v_min, v_max = config.intensity_min, config.intensity_max
    volume = [(max(v_min, min(v, v_max)) - v_min) / (v_max - v_min) for v in volume]
    
    # Step 7: Memory Layout & GPU Upload
    volume = [volume] # Add batch dimension
    volume = transfer_to_cuda(volume)
    return volume, affine_ras_to_ijk
```

### Parameters
- **Spacing**: Target voxel spacing in mm, e.g., `[2.5, 2.5, 3.0]` [S1, unofficial].
- **ScaleIntensityRange**: Clipping and scaling range, e.g., `[-3024, 3024]` to `[0, 1]` [S1, unofficial].
- **Thresholds**: User-defined `min` and `max` in `[0, 1]` for filtering [S3, unofficial].
- **iso_min, iso_max**: Thresholds for CT data loading in brick-based systems, defaulting to `0` and `USHRT_MAX` [S2, unofficial].
- **m_density_mult**: Multiplier applied to density values in `BrickDensityRegion` [S2, unofficial].

### Edge Cases and Pitfalls
- **Precision**: Converting high-precision data (e.g., 16-bit) to 8-bit can lose detail. Use `ScaleToMax` based on the lowest resolution representation to preserve dynamic range [S3, unofficial].
- **Boundaries**: Index bounds checking is critical in brick-based loading. The `set()` method must verify that `i, j, k` are within `m_brickData` dimensions [S2, unofficial].
- **Empty Bricks**: Detect bricks containing only zero values after pre-processing and transmit an `EMPTY` flag instead of data to save bandwidth [S3, unofficial].
- **Coordinate Systems**: Incorrect affine matrix inversion leads to misaligned rendering. Ensure `ras2ijk` is correctly computed from the source metadata [S1, unofficial].

## Subtopics

### [DICOM CT Projection Loading and Geometry Extraction](2661-dicom-ct-projection-loading-and-geometry-extraction.md)
This method loads raw CT projection data from a directory of DICOM files, extracts scanner geometry parameters, applies Hounsfield Unit (HU) calibration, and constructs a ConeBeamGeometry object suitable for tomographic reconstruction. It specifically addresses the challenge of interpreting non-standard or vendor-specific DICOM metadata (such as angle definitions and flying focal spot offsets) to correctly map 2D detector coordinates to 3D ray paths. It differs from standard CT loading by explicitly handling cylindrical-to-rectangular coordinate conversion for the ray transform and correcting for pixel-center vs. pixel-corner detector geometry.

### Brick Density Volume Loading
This variant loads volume data into a `BrickGrid` structure for out-of-core rendering [S2, unofficial]. It iterates over the Y-axis, loading slices via `loadVolSlice` and handling both CT and Ocean Data formats [S2, unofficial]. For CT data, it uses `iso_min` and `iso_max` thresholds (defaulting to `0` and `USHRT_MAX`) [S2, unofficial]. For Ocean Data, it parses SciData files, normalizes locations and O2 concentration to `[0, 1]` based on min/max values, and applies a density multiplier `m_density_mult` [S2, unofficial]. It includes strict index bounds checking to prevent out-of-bounds access [S2, unofficial].

### Brick Loading Pre-processing
This method applies pre-processing steps in a dedicated brick-loading thread to convert volume data to unsigned 8-bit integers [S3, unofficial]. It supports three scaling methods: `scale` (divide by constant), `scaleToMax` (divide by auto-detected max from lowest resolution), and `logTransform` (common logarithm) [S3, unofficial]. User-defined thresholds `[min, max]` in `[0, 1]` are applied to filter noise, setting out-of-range values to zero [S3, unofficial]. Bricks containing only zero values are replaced with a special `EMPTY` value to optimize GPU transfer [S3, unofficial].

### [DICOM Slice Processing](5072-dicom-slice-processing.md)
This method loads DICOM slices from a directory, determines intensity range, and sorts slices. It scans for `*.IMA` files, initializes min/max intensity to `99999` and `-1` respectively, and iterates through slices to update global min/max based on `LargestImagePixelValue` and `SmallestImagePixelValue`. The slices are then sorted to ensure correct spatial ordering.

## Operating characteristics
- **Time Complexity**: Linear with respect to the number of voxels for loading and normalization $O(N)$ [G]. Resampling adds complexity based on the interpolation kernel [G].
- **Memory Complexity**: Linear with respect to the volume size $O(N)$ [G]. Brick-based loading reduces peak memory usage by loading only active bricks [G].
- **Performance**: GPU upload time depends on PCIe bandwidth and volume size. Pre-processing on the CPU (brick-loading thread) overlaps with GPU rendering [S3, unofficial].
- **Strengths**: Handles various medical formats, ensures coordinate correctness, and optimizes transfer with empty brick detection [S1, S2, S3, unofficial].
- **Limitations**: Requires careful handling of affine matrices. Resampling can be computationally expensive for large volumes [G].

## Background
This method is part of the `VolumeLoader` framework, which supports various medical imaging formats [S1, S2, S3, unofficial]. It builds on techniques from MONAI for medical image processing [S1, unofficial] and brick-based rendering systems for out-of-core visualization [S2, S3, unofficial]. The brick-based pre-processing and empty brick optimization are derived from scalable web-based volume rendering systems [S3, unofficial].
