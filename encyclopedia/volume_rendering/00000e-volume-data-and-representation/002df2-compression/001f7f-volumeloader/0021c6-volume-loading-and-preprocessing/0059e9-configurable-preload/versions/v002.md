# Configurable Preload

Also called: Preload with Retrieve Configuration

## Overview
Configurable Preload is a volume loading strategy that allows the application to explicitly define the order in which volume data is retrieved, rather than relying on a fixed default sequence [S1, unofficial]. It solves the problem of inefficient data access patterns (such as end-to-end sweeps) by enabling interleaved or progressive loading orders that improve cache locality and reduce perceived load time [S2, unofficial]. It differs from sibling methods by operating at the volume-level retrieval configuration stage, allowing the loader to prioritize specific subsets of images before filling in the gaps [S1, S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A volume loader instance and an optional `retrieveConfiguration` object passed to the `load()` function [S1, unofficial].
*   **Output:** A sequence of image load requests and volume state transitions (`idle`, `loading`, `updating`, `complete`) [S1, unofficial].

**Data Structures:**
*   **Retrieve Configuration:** An object controlling the loading strategy via the `progressiveRendering` flag and `imageRetrieveMetadataProvider` reference [S1, unofficial].
*   **Volume State:** Tracks current status and a generation number to handle restarts and discard stale batch results [S1, unofficial].
*   **Cache:** Stores retrieved images and is checked before issuing new requests to avoid redundant fetches [S2, unofficial].

**Steps:**
1.  **Resolve Configuration:** Determine the effective retrieve configuration using the following precedence order [S1, unofficial]:
    1.  The `retrieveConfiguration` argument passed directly to the `load()` function.
    2.  The `progressiveRendering` option defined on the volume loader instance.
    3.  The default configuration from `imageRetrieveMetadataProvider`.
2.  **Initialize Load:** If a progressive configuration is selected, the loader behaves like a viewport load [S1, unofficial]:
    *   It takes in any images already present in the cache [S2, unofficial].
    *   It removes any existing prefetch requests [S1, unofficial].
    *   It sets the internal flag `isLoadingProgressively()` to true [S1, unofficial].
3.  **Generate Requests:** Based on the resolved configuration, generate the sequence of image indices to load [S1, unofficial]:
    *   If using the default non-progressive mode, requests follow the order defined by `getImageLoadRequests` [S1, unofficial].
    *   If using `coarseInterleavedRetrieveStages`, requests follow the interleaved bit-reversed order [S2, unofficial].
4.  **Execute Load:** Fetch the images in the generated order [S2, unofficial]:
    *   Each image is retrieved once at full resolution [S2, unofficial].
    *   As images arrive, they are marked as dirty in the texture system [S1, unofficial].
    *   Renders may occur periodically (e.g., after every 2% of frames) to update the display [S1, unofficial].
5.  **Completion:** Once all requested images are loaded, the volume state becomes `complete` [S1, unofficial]. The `completeUpdate()` function reduces and uploads all pending slices, then renders [S1, unofficial].

**Parameters:**
*   `progressiveRendering`:
    *   `true`: Selects `ProgressiveRetrieveImages.coarseInterleavedRetrieveStages` [S1, unofficial].
    *   `object`: Selects the provided configuration object [S1, unofficial].
    *   `false`: Selects the standard request order from `getImageLoadRequests` [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Volume Length Not Multiple of 64:** The `initialImages` step retrieves the middle image and the last image to close the tail of the volume [S2, unofficial].
*   **Restart/Cancel:** Calling `restart()` clears the queue, resets the cursor, marks all slices dirty, and increments a generation number [S1, unofficial].
*   **Cache Stalls:** If all images are already cached, the load does not stall and completes immediately [S2, unofficial].
*   **Precision:** The bit-reversed order relies on integer arithmetic for offsets [S2, unofficial].

**Pseudocode:**
```python
def bit_reverse(n, bits):
    result = 0
    for _ in range(bits):
        result = (result << 1) | (n & 1)
        n >>= 1
    return result

def load_volume(volume_loader, retrieve_config=None):
    # Step 1: Resolve Configuration
    if retrieve_config is not None:
        config = retrieve_config
    elif volume_loader.progressiveRendering is not None:
        config = volume_loader.progressiveRendering
    else:
        config = volume_loader.imageRetrieveMetadataProvider

    # Step 2: Initialize Load
    is_progressive = (config is True) or (isinstance(config, dict))
    if is_progressive:
        volume_loader.isLoadingProgressively = True
        volume_loader.take_cached_images()
        volume_loader.remove_prefetch_requests()

    # Step 3: Generate Requests
    if is_progressive and config is True:
        requests = []
        gap = 64
        bits = 6
        for _ in range(64):
            for offset in range(gap):
                idx = bit_reverse(offset, bits)
                requests.append(idx)
            gap >>= 1
            bits -= 1
    else:
        requests = volume_loader.getImageLoadRequests()

    # Step 4: Execute Load
    for image_index in requests:
        if not volume_loader.is_cancelled():
            image_data = standard_fetch(image_index) # [G] standard network fetch
            volume_loader.cache_image(image_index, image_data)
            volume_loader.mark_texture_dirty(image_index)
            if volume_loader.should_re_render():
                volume_loader.render()

    # Step 5: Completion
    volume_loader.state = "complete"
    volume_loader.completeUpdate()
```

## Subtopics

### Progressive Volume Loading with Interleaved Stages
A loading strategy that retrieves images in interleaved stages to avoid sweeping from one end to another, improving cache locality and reducing load time [S2, unofficial]. It differs from the previous configuration which had three coarse stages of every 64th image followed by stock stages of every 4th image, causing an end-to-end sweep [S2, unofficial]. It has no lossy stage and no thumbnail stage, so an HTJ2K server gets no fast lossy first pass from it [S2, unofficial].

**Configuration Details:**
*   **Stages:** 64 stages of every 64th image [S2, unofficial].
*   **Offsets:** Follow the bit-reversed order: 0, 32, 16, 48, 8, 40, and so on [S2, unofficial].
*   **Gap Halving:** Each level of stages halves the gap between the retrieved images over the whole volume: 64, 32, 16, 8, 4, 2, and 1 [S2, unofficial].
*   **Frame Filling:** Each image fills the frames up to half the gap of its level, and each image is retrieved once, at full resolution [S2, unofficial].
*   **Initial Images:** Retrieves the middle image and the last image. The last image closes the tail of a volume whose length is not a multiple of 64 [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** The interleaved strategy reduces load time by improving cache locality compared to sequential loading [S2, unofficial]. The number of stages is fixed at 64 for the coarse interleaved mode [S2, unofficial].
*   **Memory Complexity:** Depends on the cache size and the number of images loaded in parallel [S2, unofficial]. The loader takes in cached images, reducing redundant fetches [S2, unofficial].
*   **Performance:** Measured on large volumes, the interleaved approach prevents the "end-to-end sweep" behavior, leading to more consistent performance [S2, unofficial].
*   **Strengths:** Improves cache locality, reduces load time for large volumes, handles non-multiples of 64 gracefully [S2, unofficial].
*   **Limitations:** No lossy or thumbnail stage, which may result in slower initial perception for HTJ2K servers compared to strategies with a fast lossy first pass [S2, unofficial].
*   **When to Use:** When loading large volumes where cache locality is critical and the volume length is large [S2, unofficial].

## Background
Configurable Preload was introduced in the cornerstone3D project to address issues with volume loading efficiency and cache management [S1, S2, unofficial]. The specific interleaved stages feature was added in a pull request titled "feat(core): load a large volume in 64 stages of every 64th image" [S2, unofficial]. The broader context of volume texture management, including brick copies and paced renders, was discussed in issue #2966 [S1, unofficial].
