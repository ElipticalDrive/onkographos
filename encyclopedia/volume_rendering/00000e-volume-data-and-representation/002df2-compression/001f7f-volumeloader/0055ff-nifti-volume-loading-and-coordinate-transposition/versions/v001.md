# NIfTI Volume Loading and Coordinate Transposition

Also called: NIfTI Volume Loader, SimpleITK NIfTI Loading

## Overview
This method loads NIfTI-1 volumetric data files, handling optional gzip compression, header validation, and linear intensity scaling to produce a contiguous `float32` array. It specifically addresses the coordinate system mismatch between NIfTI’s native storage order (often Z, Y, X) and the standard spatial indexing required by volume rendering pipelines (X, Y, Z). It differs from raw binary readers by handling NIfTI-specific metadata (scaling, offsets) and from DICOM loaders by operating on a single consolidated file format rather than a directory of slices.

## How it works
**Inputs:** A path to a NIfTI file (`.nii`, `.nii.gz`, or separate `.hdr`/`.img` pair).
**Outputs:** A contiguous `float32` NumPy array with shape `(X, Y, Z)` and a spacing vector `(spacing_x, spacing_y, spacing_z)` as `float64`.

### Data Structures
The NIfTI-1 header is a fixed-size structure. Key fields used:
- `sizeof_hdr` (int32): Must be 348.
- `datatype` (int16): Voxel type (e.g., `DT_UINT8`, `DT_UINT16`, `DT_INT16`, `DT_FLOAT32`).
- `dim[1..7]` (int16): Dimensions. `dim[1]`, `dim[2]`, `dim[3]` correspond to X, Y, Z in the file's native order.
- `vox_offset` (float32): Byte offset from the start of the file to the voxel data.
- `scl_slope` (float32): Scaling slope.
- `scl_inter` (float32): Scaling intercept.

### Steps
1. **File Detection:** Determine if the file is `.nii`, `.nii.gz`, or separate `.hdr`/`.img`. If `.gz`, open with gzip decompression; otherwise, open in binary read mode.
2. **Header Validation:** Read the first 4 bytes to check endianness. If the reversed byte order of `sizeof_hdr` equals 348, the file is not valid or endianness is mismatched. Ensure `sizeof_hdr` is exactly 348.
3. **Data Type Check:** Verify `datatype` is one of `DT_UINT8`, `DT_UINT16`, `DT_INT16`, or `DT_FLOAT32`.
4. **Scaling Setup:** If `scl_slope` is 0.0, set it to 1.0 to prevent division by zero or null scaling.
5. **Raw Data Reading:** Calculate total voxels $N = dim[1] \times dim[2] \times dim[3]$. Allocate a raw buffer. Seek to `vox_offset` (if > 0) and read $N \times \text{bytes\_per\_voxel}$ bytes into the raw buffer.
6. **Linear Scaling:** Allocate a `float32` output array. For each voxel $i$:
   $$ \text{img32}[i] = (\text{imgRaw}[i] \times \text{scl\_slope}) + \text{scl\_inter} $$
   The conversion from raw types (uint8, uint16, int16, float32) must preserve precision before scaling.
7. **Coordinate Transposition:** Convert the loaded data to a NumPy array. The native NIfTI order is typically $(Z, Y, X)$. Transpose the axes to $(X, Y, Z)$ to match standard volume rendering indexing.
8. **Spacing Extraction:** Extract the voxel spacing from the header or SimpleITK metadata and store as `float64`.

### Parameters
- `scl_slope`: Scaling factor for raw data. Defaults to 1.0 if 0.0.
- `scl_inter`: Scaling offset applied after multiplication.
- `datatype`: Supported values are `DT_UINT8`, `DT_UINT16`, `DT_INT16`, `DT_FLOAT32`.
- `vox_offset`: Byte offset to skip in the file before reading voxel data.

### Pitfalls
- **Endianness:** Endianness mismatch is detected by checking if the reversed byte order of `sizeof_hdr` equals 348. If true, the function should error out.
- **Scaling Zero:** If `scl_slope` is 0.0, it must be set to 1.0 to avoid nullifying the data.
- **Coordinate Order:** NIfTI files often store data in $(Z, Y, X)$ order. Failing to transpose to $(X, Y, Z)$ will result in incorrect volume rendering geometry.

## Operating characteristics
- **Time Complexity:** $O(N)$ where $N$ is the number of voxels, for reading, scaling, and transposing.
- **Memory Complexity:** $O(N)$ for storing the raw data and the final `float32` array.
- **Performance:** SimpleITK-based loading is robust but may have higher overhead due to library initialization. Raw loading is faster but requires careful handling of binary formats and endianness.
- **Strengths:** Handles compressed files, validates headers, applies linear scaling correctly, and ensures correct coordinate ordering.
- **Limitations:** Limited to NIfTI-1 format. Does not handle multi-volume NIfTI files (4D) without additional logic.

## Background
NIfTI (Neuroimaging Informatics Technology Initiative) is a common format for neuroimaging data. The method described here is based on implementations found in open-source medical imaging tools. The raw loading logic is derived from `nii2mesh` [S1, unofficial], while the SimpleITK-based approach is derived from `medviewer` [S2, unofficial].
