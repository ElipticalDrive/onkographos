# VolumeLoader

Also called: Volumetric Data Loader
## Overview
VolumeLoader is a method for loading volumetric data from various medical imaging formats, handling loading, optional resimming, and coordinate system alignment [S1, unofficial]. It solves the problem of converting heterogeneous source files (e.g., NIfTI, NumPy) into a standardized tensor on a target device while managing memory constraints through automatic downscaling [S1, unofficial].
## How it works
**Inputs and Outputs:**
- Input: File path to volumetric data (e.g., `.nii`, `.gz`, `.npy`).
- Output: A tensor on the specified `device` with shape `target_shape` (or original shape) and dtype `storage_dtype`.

**Data Structures:**
- Configuration object containing:
  - `target_shape`: Optional tuple `(D, H, W)` for resampling.
  - `device`: Target compute device.
  - `downscale_factor`: Integer factor for resolution reduction.
  - `storage_dtype`: One of `{'fp32', 'fp16', 'bf16'}`.
  - `enable_overflow_guard`: Boolean flag for automatic large-volume handling.

**Steps:**
1. **Initialization:** Create a `VolumeLoader` instance with the configuration parameters [S1, unofficial].
2. **Validation:** Verify that `storage_dtype` is in `{'fp32', 'fp16', 'bf16'}`. Raise `ValueError` if not [S1, unofficial].
3. **Raw Range Peeking:** Load the raw data into a temporary float32 numpy array to determine the data range and dimensions:
   - For `.nii` or `.gz` files: Use `nibabel` to load and convert to `float32` numpy array [S1, unofficial].
   - For `.npy` files: Use `numpy.load` [S1, unofficial].
4. **Overflow Guard Check:** If `enable_overflow_guard` is True, check if the total voxel count exceeds ~16 million. If it does, automatically apply `downscale_factor` to reduce dimensions to `(D//factor, H//factor, W//factor)` [S1, unofficial].
5. **Resampling:** If `target_shape` is provided, or if `downscale_factor` > 1, resample the volume to the target dimensions. If `target_shape` is None, keep original dimensions (subject to overflow guard) [S1, unofficial].
6. **Device Transfer:** Cast the data to `storage_dtype` [S1, unofficial]. Transfer to the specified `device` [G].

**Pseudocode:**
```python
import numpy as np
import nibabel as nib
import scipy.ndimage
from typing import Optional, Tuple

def load_volume(
    filepath: str,
    target_shape: Optional[Tuple[int, int, int]] = None,
    device: str = "cpu",
    downscale_factor: int = 1,
    storage_dtype: str = "fp32",
    enable_overflow_guard: bool = True
) -> np.ndarray:
    # 1. Validate storage_dtype
    valid_dtypes = {"fp32", "fp16", "bf16"}
    if storage_dtype not in valid_dtypes:
        raise ValueError(f"storage_dtype must be one of {valid_dtypes}, got {storage_dtype}")

    # 2. Peek raw range and load into float32 numpy array
    if filepath.endswith(('.nii', '.gz')):
        nib_img = nib.load(filepath)
        raw_data = nib_img.get_fdata().astype(np.float32)
    elif filepath.endswith('.npy'):
        raw_data = np.load(filepath).astype(np.float32)
    else:
        raise ValueError(f"Unsupported file format: {filepath}")

    original_shape = raw_data.shape
    total_voxels = np.prod(original_shape)

    # 3. Overflow Guard Check
    if enable_overflow_guard and total_voxels > 16_000_000:
        if downscale_factor <= 1:
            downscale_factor = 2
        new_shape = tuple(dim // downscale_factor for dim in original_shape)
        # Standard resampling (e.g., linear interpolation) [G]
        zoom_factors = [t / o for t, o in zip(new_shape, original_shape)]
        raw_data = scipy.ndimage.zoom(raw_data, zoom_factors, order=1)
        original_shape = new_shape

    # 4. Resampling to target_shape
    if target_shape is not None:
        # Standard resampling (e.g., linear interpolation) [G]
        zoom_factors = [t / o for t, o in zip(target_shape, raw_data.shape)]
        raw_data = scipy.ndimage.zoom(raw_data, zoom_factors, order=1)
    elif downscale_factor > 1:
        new_shape = tuple(dim // downscale_factor for dim in original_shape)
        # Standard resampling (e.g., linear interpolation) [G]
        zoom_factors = [t / o for t, o in zip(new_shape, raw_data.shape)]
        raw_data = scipy.ndimage.zoom(raw_data, zoom_factors, order=1)

    # 5. Cast and Transfer
    dtype_map = {
        "fp32": np.float32,
        "fp16": np.float16,
        "bf16": np.float16
    }
    np_dtype = dtype_map[storage_dtype]
    result = raw_data.astype(np_dtype)
    return result
```

**Parameters:**
- `target_shape`: Optional tuple `(D, H, W)`. If `None`, original dimensions are kept [S1, unofficial].
- `downscale_factor`: Integer. When > 1, volumes are resampled to `(D//factor, H//factor, W//factor)` [S1, unofficial].
- `storage_dtype`: One of `{'fp32', 'fp16', 'bf16'}` [S1, unofficial].
- `enable_overflow_guard`: Boolean. Automatically resamples very large volumes to avoid downstream operations failing on >~16M voxels [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Precision:** `bf16` is not natively supported in standard NumPy; implementation may require casting to `fp16` or using device-specific tensors [G].
- **Boundaries:** Integer division in `downscale_factor` may truncate dimensions, potentially losing data if dimensions are not perfectly divisible by the factor [G].

## Subtopics

### [Volume Data Loading and Normalization](2157-volume-data-loading-and-normalization.md)
Implements a C++ class for loading 3D/4D volumetric data from `.npy` files, normalizing scalar values, and managing frame indices for time-varying volumes. It differs from sibling methods like the Raw Volume Data Reader and DICOM loader by strictly relying on the NumPy binary format and applying a specific min-subtraction normalization strategy rather than standard min-max scaling to $[0, 1]$. It solves the problem of ingesting pre-saved NumPy volume arrays into a rendering pipeline while ensuring consistent data types and value ranges.

### [Raw Volume Data Reader](2259-raw-volume-data-reader.md)
The Raw Volume Data Reader loads raw binary volume data files directly into memory. It parses a fixed header, reads voxel values, applies density clamping and normalization, and maps the data to 3D coordinates. It differs from generic loaders by handling coordinate mapping and density scaling directly during the load phase rather than treating the data as opaque bytes.

### [DICOM Volume Loading and Coordinate Reconstruction](2574-dicom-volume-loading-and-coordinate-reconstruction.md)
This method loads a 3D volumetric dataset from a series of DICOM image files, reconstructs the physical voxel grid by resolving coordinate system conventions, and converts raw pixel values into physical density. It specifically addresses the discrepancy between DICOM's pixel-center coordinate convention and the corner-point convention required by downstream volume rendering engines, while handling the non-cubic nature of medical voxels. It differs from generic volume loaders by explicitly managing DICOM-specific metadata (Rescale Slope/Intercept, Pixel Spacing, Slice Thickness) and orientation flips (rot90) necessary for correct anatomical alignment.

### [VTK Volume Loading & Normalization](2620-vtk-volume-loading-normalization.md)
This method parses VTK Structured Points files, extracts voxel data, and normalizes scalar values to an 8-bit unsigned integer range $[0, 255]$. It converts arbitrary-precision medical or scientific volume data into a standardized format suitable for GPU-based raycasting or texture upload. It is distinguished from generic loaders by its specific reliance on the VTK Structured Points header format and its mandatory min-max normalization step, unlike [Raw Volume Data Reader](2259-raw-volume-data-reader.md) which assumes raw binary continuity, or [DICOM Volume Loading and Coordinate Reconstruction](2574-dicom-volume-loading-and-coordinate-reconstruction.md) which handles multi-frame DICOM series.

### [Volume Loading and Preprocessing](2623-volume-loading-and-preprocessing.md)
This method ingests volumetric data from medical imaging formats and raw files, performing normalization, coordinate alignment, and memory preparation for downstream rendering. It distinguishes itself by combining MONAI-based tensor pipelines for spacing and intensity scaling with brick-based out-of-core loading that includes thread-level pre-processing and empty-brick optimization.

### [SOG Volume Reader](3580-sog-volume-reader.md)
The SOG Volume Reader is a recursive algorithm that loads a hierarchical volumetric format (SOG) into a dense 3D grid by parsing a binary header and traversing internal, empty, leaf, and pseudo-leaf node types. It differs from flat raw readers by reconstructing the full voxel array from a compressed octree-like structure, enabling efficient storage of sparse or block-structured medical imaging data.

### AVS FLD Volume Loader
Parses legacy AVS FLD format to extract 3D scalar volume data and dimensions [S2, unofficial]. It reads the first 16 bytes to verify the magic string "# AVS field file", scans for the `\f` byte to determine header length, and decodes header fields (ndim, dim1, dim2, dim3, etc.) using regex splitting [S2, unofficial]. It validates `ndim==3`, `veclen==1`, and `data=="uniform"`, then reads `dim_x * dim_y * dim_z * data_type` bytes, unpacking as 'B' (byte) or 'H' (short) and reshaping to `(dim_x, dim_y, dim_z)` with Fortran order [S2, unofficial]. Pitfall: Only data types 1 (byte) and 2 (short) are supported; others raise an exception [S2, unofficial]. Choose this for legacy AVS FLD data.

### DICOM Node
A node that loads DICOM data, handles mesh escalation to match stored scale, interpolates voxel values, and applies jittering to improve quality during ray casting with few steps [S3, unofficial]. It escalates the mesh according to DICOM data specifications, considers three data types based on storage bytes, interpolates values between nearest voxels, and applies jittering so rays do not start at the same distance every time [S3, unofficial]. Node color is grey if empty, orange if a DICOM file is uploaded [S3, unofficial].

### NeXus to NRRD/NPZ Conversion
A method to load volume data from a NeXus HDF5 file, handling NXdata groups and axis attributes, and save it as NRRD or NPZ format with normalized float32 data and spatial metadata [S4, unofficial]. It opens the NeXus file using `h5py`, loads the volume from the specified group and data name, extracts spacings and origin from axes, and creates an NRRD header with space "right-anterior-superior" [S4, unofficial]. Pitfall: If `v_max` equals `v_min` during normalization, division by zero occurs and results in NaN values [S4, unofficial].
