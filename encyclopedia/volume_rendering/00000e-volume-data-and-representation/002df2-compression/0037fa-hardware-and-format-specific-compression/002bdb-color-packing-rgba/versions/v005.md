# Color Packing (RGBA)


## Overview
Color Packing (RGBA) compresses a 4-component floating-point color vector into a 4-byte unsigned integer array with 8-bit precision per channel [S1, unofficial]. It serves as a basic quantization step for storing volumetric color data in formats compatible with standard 8-bit texture units or network transmission [S1, unofficial]. It differs from [16-bit Floating Point Format for Spectra](1163-16-bit-floating-point-format-for-spectra.md) by using lower precision (8-bit vs 16-bit) and from [ELSCINT1/PMSCT_RLE1 Delta Decoding](11897-elscint1-pmsct-rle1-delta-decoding.md) by not employing run-length encoding or delta prediction, relying solely on per-channel quantization [S1, unofficial][S2, unofficial].

## How it works
**Inputs:** A 4-component floating-point vector $C = [c_0, c_1, c_2, c_3]$ representing Red, Green, Blue, and Alpha channels.
**Outputs:** A 4-byte unsigned integer array $B = [b_0, b_1, b_2, b_3]$ where each byte corresponds to a quantized channel.

**Data Structure:**
The output is a contiguous block of 4 bytes.
- $b_0$: Quantized Red channel.
- $b_1$: Quantized Green channel.
- $b_2$: Quantized Blue channel.
- $b_3$: Quantized Alpha channel.

**Steps:**
1. For each component index $i \in \{0, 1, 2, 3\}$:
   a. Compute the scaled value: $v_i = c_i \times 255.0$.
   b. Cast $v_i$ to an 8-bit unsigned integer ($u8$). This operation typically truncates the fractional part.
   c. Assign the result to $b_i$.

**Formulas:**
$$ b_i = \text{cast\_to\_u8}(c_i \times 255.0) $$
where $c_i$ is the floating-point value of the $i$-th channel.

**Parameters:**
- Scaling factor: $255.0$. This maps the input range $[0.0, 1.0]$ to $[0, 255]$.
- Output type: `uint8_t` (8-bit unsigned integer).

**Edge Cases and Pitfalls:**
- **Input Range:** The method assumes input values are in the range $[0.0, 1.0]$. Values outside this range will overflow or underflow the 8-bit integer representation. For example, $c_i > 1.0$ results in a value $> 255$, which wraps or saturates depending on the casting implementation. $c_i < 0.0$ results in negative values, which wrap to large positive integers in unsigned arithmetic.
- **Precision Loss:** Quantization to 8 bits introduces discretization error. The maximum error per channel is $1/255 \approx 0.0039$.
- **Alpha Channel:** The alpha channel is treated identically to color channels. If the alpha channel represents opacity, values outside $[0.0, 1.0]$ may lead to incorrect blending behavior.

**Pseudocode:**
```python
def pack_color_rgba(c: list[float]) -> list[int]:
    """
    Packs a 4-component float color vector into a 4-byte unsigned integer array.
    
    Args:
        c: A list of 4 floats [r, g, b, a] in the range [0.0, 1.0].
        
    Returns:
        A list of 4 integers [r, g, b, a] in the range [0, 255].
    """
    if len(c) != 4:
        raise ValueError("Input must be a 4-component vector.")
    
    b = [0] * 4
    for i in range(4):
        # Multiply by 255.0 and cast to 8-bit unsigned integer
        # Note: In Python, int() truncates towards zero. 
        # For strict u8 behavior, one might need to handle negatives explicitly,
        # but the source implies a direct cast.
        val = c[i] * 255.0
        # Cast to u8: truncate and mask to 8 bits
        b[i] = int(val) & 0xFF
        
    return b
```

### RGBE HDR Encoding
A variant for storing High Dynamic Range (HDR) color data in 4 bytes [S2, unofficial]. It encodes the maximum channel value as an exponent and the other channels as mantissas scaled by that exponent.

**Steps:**
1. Compute $d = \max(c_x, c_y, c_z)$.
2. If $d \le 10^{-32}$, return `HDRPixel(0, 0, 0, 0)`.
3. Extract exponent $e$ and mantissa $m$ from $d$ using `frexp(d, &e)`, such that $d = m \times 2^e$.
4. Compute scale factor $s = m \times 256.0 / d$.
5. Return `HDRPixel` with components:
   - $r = \text{uint8\_t}(c_x \times s)$
   - $g = \text{uint8\_t}(c_y \times s)$
   - $b = \text{uint8\_t}(c_z \times s)$
   - $e = \text{uint8\_t}(e + 128)$

**Parameters:**
- Threshold: $10^{-32}$ to avoid division by zero.
- Exponent bias: $128$ to keep the exponent positive in 8-bit storage.

**Layout:**
`HDRPixel`: 4-byte struct with fields `uint8_t r, g, b, e` in that order.

**Pitfalls:**
- Channel values $c_x, c_y, c_z$ can exceed $1.0$ after scaling, causing overflow when cast to `uint8_t`. The code does not clamp them, relying on the HDR format's ability to store values $>1$ via the exponent.

## Operating characteristics
**Time Complexity:** $O(1)$ per pixel, as it involves a fixed number of arithmetic operations and casts.
**Memory Complexity:** $O(1)$ per pixel, reducing 16 bytes (4 floats) to 4 bytes (4 uint8s), achieving a 4:1 compression ratio.
**Measured Performance:** Not given in the sources.
**Strengths:** Simple to implement, low computational overhead, compatible with standard 8-bit texture formats.
**Limitations:** Low precision (8-bit), no dynamic range adaptation (unlike RGBE), sensitive to input range assumptions.
**When to use:** When storage or bandwidth is limited and the color data is known to be in the $[0, 1]$ range with acceptable quantization error.
**When not to use:** When high dynamic range is required (use RGBE or 16-bit float) or when color accuracy is critical.

## Background
The method is described in the context of in-game key bindings and volume rendering data loading in unofficial repositories [S1, unofficial][S2, unofficial]. It is a standard technique in computer graphics for converting floating-point color data to fixed-point formats for display or storage.
