# Tensor Times Matrix (TTM) Reconstruction

Also called: CUDA Tensor Times Matrix (TTM) Reconstruction, TTM Reconstruction, TTM-based decoding, n-mode product reconstruction

## Overview
Tensor Times Matrix (TTM) Reconstruction is a GPU-accelerated method for decoding compressed volume data represented by Tucker decomposition. It reconstructs a volume brick from a core tensor and factor matrices by sequentially applying three n-mode products, thereby reducing the computational complexity per voxel from cubic to linear with respect to the rank $R$ [S1]. Unlike naive reconstruction that loads the entire core tensor into each thread, this approach stores intermediate tensors in global memory, optimizing for shared memory constraints and enabling interactive frame rates on large datasets [S1].

## How it works

### Inputs and Outputs
*   **Inputs:**
    *   Core tensor $B$ of size $R \times R \times R$.
    *   Factor matrices $U^{(1)}, U^{(2)}, U^{(3)}$, each of size $B \times R$, where $B$ is the brick dimension (typically 32) and $R$ is the Tucker rank (typically 16) [S1].
    *   Quantization parameters (min/max values) for dequantization [S1].
*   **Outputs:**
    *   Final volume brick $A_f$ of size $B \times B \times B$ [S1].

### Data Structures and Layout
The reconstruction is performed in three successive steps (TTM1, TTM2, TTM3). Intermediate results are stored in device linear memory.

1.  **TTM1:**
    *   **Input:** $U^{(1)}$ and slices of $B$.
    *   **Output:** Intermediate tensor $B'$ of size $B \times R \times R$.
2.  **TTM2:**
    *   **Input:** $U^{(2)}$ and slices of $B'$.
    *   **Output:** Intermediate tensor $B''$ of size $B \times B \times R$.
3.  **TTM3:**
    *   **Input:** $U^{(3)}$ and slices of $B''$.
    *   **Output:** Final volume brick $A_f$ of size $B \times B \times B$.

### Grid Configuration
*   One thread block is assigned per decoded brick [S1].
*   The grid size is determined by the number of bricks to be decoded in the current frame [S1].
*   For TTM2 and TTM3, each block computes only half of a slice to optimize shared memory usage [S1].

### Shared Memory Usage
Shared memory is used to cache factor matrices and tensor slices to avoid bank conflicts. Data is dequantized to 32-bit floating point words before upload [S1].

*   **TTM1:** $(B \cdot R \cdot 4 + R \cdot R \cdot 4)$ bytes per block [S1].
*   **TTM2/TTM3:** $(B/2 \cdot R \cdot 4 + B \cdot R \cdot 4)$ bytes per block [S1].
*   **Constraints:** Maximum 16 KB for CUDA 1.x and 48 KB for CUDA 2.x per multiprocessor. Maximum 8 blocks per multiprocessor [S1].

### Formulas
The full reconstruction is defined as the sequential n-mode product:
$$ A_f = B \times_1 U^{(1)} \times_2 U^{(2)} \times_3 U^{(3)} $$
where $B$ is the core tensor and $U^{(n)}$ are the factor matrices for mode $n$ [S1].

### Parameters
*   **Brick Size ($B$):** 32 [S1].
*   **Rank ($R$):** 16 [S1].
*   **Quantization:** 16-bit for factor matrices $U^{(n)}$ and core tensor $B$ [S1].

### Pseudocode

```python
# Common Dequantization Helper
def dequantize(value, min_val, max_val, bits=16):
    """
    Linearly dequantize a value.
    value: quantized integer.
    min_val, max_val: range of the quantized data.
    """
    # Assuming standard linear quantization mapping [0, 2^bits-1] to [min_val, max_val]
    # Note: Exact quantization formula depends on preprocessing; this is a placeholder
    # for the linear dequantization mentioned in [S1].
    return min_val + (value / (2**bits - 1)) * (max_val - min_val)

# TTM1 Kernel
def ttm1_kernel(U1, B, B_prime, min_U1, max_U1, min_B, max_B):
    """
    Computes B' = B x_1 U1.
    B_prime size: B x R x R.
    """
    # Load U1 and B slices to shared memory
    # Dequantize U1 elements to 32-bit float
    # Dequantize B elements to 32-bit float
    # Synchronize
    
    # Each thread computes one element of B'
    # i1 is the thread's output index along mode 1
    # r2, r3 are indices along modes 2 and 3
    
    voxel = 0.0
    for r1 in range(R):
        # U1[i1, r1] * B[r1, r2, r3]
        # Note: B is accessed via slice determined by blockId
        voxel += dequantize(U1[i1, r1], min_U1, max_U1) * dequantize(B[r1, r2, r3], min_B, max_B)
    
    B_prime[i1, r2, r3] = voxel

# TTM2 Kernel
def ttm2_kernel(U2, B_prime, B_double_prime, min_U2, max_U2, min_Bp, max_Bp):
    """
    Computes B'' = B' x_2 U2.
    B_double_prime size: B x B x R.
    """
    # Load U2 and half slice of B' to shared memory
    # Dequantize U2 elements
    # Dequantize B' elements
    # Synchronize
    
    # Each thread computes one element of B''
    # i1, i2 are output indices for modes 1 and 2
    # r3 is index for mode 3
    
    voxel = 0.0
    for r2 in range(R):
        # U2[i2, r2] * B_prime[i1, r2, r3]
        voxel += dequantize(U2[i2, r2], min_U2, max_U2) * dequantize(B_prime[i1, r2, r3], min_Bp, max_Bp)
    
    B_double_prime[i1, i2, r3] = voxel

# TTM3 Kernel
def ttm3_kernel(U3, B_double_prime, A_f, min_U3, max_U3, min_Bpp, max_Bpp, hot_corner_val):
    """
    Computes A_f = B'' x_3 U3.
    A_f size: B x B x B.
    """
    # Load U3 and half slice of B'' to shared memory
    # Dequantize U3 elements
    # Dequantize B'' elements
    # Synchronize
    
    # Each thread computes one element of A_f
    # i1, i2, i3 are output indices
    
    voxel = 0.0
    for r3 in range(R):
        # U3[i3, r3] * B_double_prime[i1, i2, r3]
        voxel += dequantize(U3[i3, r3], min_U3, max_U3) * dequantize(B_double_prime[i1, i2, r3], min_Bpp, max_Bpp)
    
    # Add contribution of hot-corner core value B(0,0,0)
    # This is handled separately to avoid special case in inner loop
    # The quantized coefficient at B(0,0,0) is encoded as zero
    voxel += hot_corner_val
    
    A_f[i1, i2, i3] = voxel
```

### Edge Cases and Pitfalls
*   **Shared Memory Bank Conflicts:** Avoided by dequantizing factor matrices and core tensor to 32-bit floating point words before uploading to shared memory, ensuring all accesses are aligned on 32-bit words [S1].
*   **Hot-Corner Coefficient:** The coefficient $B(0,0,0)$ is handled separately in TTM3. To simplify decoding and avoid special case handling in the inner loop, a zero quantized coefficient is encoded at the corresponding core tensor position, and the unquantized value is added directly [S1].
*   **Memory Limits:** Shared memory usage must fit within the limits of the CUDA architecture (16 KB for 1.x, 48 KB for 2.x). The configuration described works for 32-cubed bricks [S1].

## Operating characteristics

### Time and Memory Complexity
*   **Computational Complexity:** The sequential TTM approach reduces the computational complexity per reconstructed voxel to linear growth with rank $R$, compared to cubic order $R^3$ in naive triple-loop implementations [S1].
*   **Memory Efficiency:** By storing intermediate results ($B'$ and $B''$) in global memory and loading only slices into shared memory, the method is more memory efficient than approaches requiring the complete core tensor in each thread [S1].

### Measured Performance
*   **Hardware:** GeForce GTX 480, Intel Core 2 E8500, 4GB RAM [S1].
*   **Frame Rates:** Interactive rendering frame rates higher than 12Hz in demanding situations, averaging 50-100Hz [S1].
*   **Overhead:** Tensor reconstruction constitutes negligible overhead compared to ray-casting and data transfer [S1]. The most costly part is the final copy of decoded bricks to texture cache [S1].
*   **Preprocessing Time:**
    *   2GB chameleon dataset: 25min 15sec, producing a 231M file [S1].
    *   17GB tooth dataset: 8h 45min, producing a 5.5GB file [S1].

### Strengths and Limitations
*   **Strengths:** High performance on GPUs, linear complexity with rank, suitable for interactive rendering of large volumes [S1].
*   **Limitations:** Requires significant preprocessing time for large datasets. Performance is limited by texture cache coherence during the final copy step [S1].

## Background

### Origin and History
The method was introduced in the paper "Interactive Multiscale Tensor Reconstruction for Multiresolution Volume Rendering" [S1]. It builds on the Tucker decomposition framework, specifically addressing the computational bottleneck of reconstructing volume bricks from compressed tensor representations on GPUs.

### Usage
The method is used in multiresolution volume rendering, particularly for large-scale micro-CT datasets such as the veiled chameleon and dental enamel (tooth) scans [S1]. It is integrated into adaptive GPU ray-casters to provide interactive frame rates [S1].
