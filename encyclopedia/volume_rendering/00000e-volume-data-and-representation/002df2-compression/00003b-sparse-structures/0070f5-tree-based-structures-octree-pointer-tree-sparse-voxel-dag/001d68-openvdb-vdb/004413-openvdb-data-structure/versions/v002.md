# OpenVDB Data Structure

Also called: Blender Volume Object (OpenVDB), OpenVDB Volume, OpenVDB Volume Object, Volume Object, Volume Object Data Structure

## Overview
The OpenVDB Data Structure method provides a 1:1 mapping of the OpenVDB sparse tree representation to a rectangular grid, enabling efficient storage and rendering of volumetric data such as smoke and fluids [S1][S2, unofficial]. It utilizes a hierarchical tree structure with $8 \times 8 \times 8$ leaf nodes to represent the volume [S1]. Unlike dense volume representations, it supports multiple named grids (e.g., density, color) within a single object, facilitating complex material shading in VFX pipelines [S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A file path to an OpenVDB (`.vdb`) file or a procedural generation modifier; grid names (strings); transform matrices (linear or perspective) [S1][S2, unofficial].
*   **Output:** A `Volume` datablock containing a list of `VolumeGrid` objects, each holding an OpenVDB grid structure [S1].

**Data Structures:**
The data hierarchy comprises the following components [S1]:
1.  **Volume Datablock:** Contains a list of `VolumeGrid` objects and a `filepath` string [S1]. It manages on-demand loading of grid metadata and tree data [S1].
2.  **VolumeGrid:** Contains a single OpenVDB grid [S1].
3.  **OpenVDB Grid:** Composed of Metadata (name and other fields), a Transform (linear or perspective matrix mapping voxel indices to object space), and a Tree (hierarchical node structure with leaf nodes containing a fixed-size grid of $8 \times 8 \times 8$ voxels) [S1].

**Loading Process:**
The system employs lazy loading to manage memory [S1]:
1.  `BKE_volume_load()` reads the file path and loads the list of grids, including their names, metadata, and transform matrices, into memory [S1].
2.  `BKE_volume_grid_load()` is called when the grid tree and voxel data are required (e.g., for rendering or modifier evaluation) [S1]. It loads the tree structure and voxel values into memory [S1].
3.  Memory sharing between original and Copy-on-Write (CoW) datablocks is handled to optimize performance during edits [S1].

**Rendering Integration:**
The `Principled Volume` shader is the default renderer [S2, unofficial]. It automatically maps specific grid names to shader inputs: `density`, `color`, and `temperature` [S2, unofficial]. If these default names are absent, the user must manually assign grid names to shader inputs in the node editor [S2, unofficial]. Workbench renderer displays only one grid at a time, whereas Cycles and Eevee composite multiple grids via the shader [S2, unofficial].

**Parameters and Defaults:**
*   **OpenVDB Version:** 7 [S2, unofficial]. The implementation maintains upward compatibility with older VDB files [S2, unofficial].
*   **Default Grid Names:** `density`, `color`, `temperature` [S2, unofficial].
*   **Leaf Node Size:** $8 \times 8 \times 8$ voxels [S1].

**Edge Cases and Pitfalls:**
*   **Animation Sequences:** Importing VDB animation sequences fails if frame numbers lack consistent zero-padding (e.g., `explosion_1` vs `explosion_001`) [S2, unofficial].
*   **Viewport Rendering:** FumeFX volumes may display as a chaotic group of planes in Cycles viewport, though final renders are correct [S2, unofficial].
*   **Sparse Grids:** Sparse grid rendering is not fully implemented in Cycles and Eevee, causing higher memory usage than necessary [S2, unofficial].
*   **Large Datasets:** Large volume datasets in solid display mode may cause performance issues; lower resolution loading is planned for high-resolution thresholds [S2, unofficial].
*   **Selection:** Viewport selection is restricted to center point or wireframe; bounds display is toggled on selection to avoid clutter [S2, unofficial].
*   **Format Limitations:** Loading density from image sequences or video files is not supported; external conversion to VDB is required [S2, unofficial].
*   **Mesh Conversion:** Mesh-to-volume and volume-to-mesh conversion are not supported [S2, unofficial].
*   **3D Textures:** Volume meshes cannot be used as 3D textures, as this prevents sparse volume optimizations [S2, unofficial].

## Operating characteristics
*   **Memory Usage:** Higher than optimal when sparse grid rendering is not fully utilized, as the system may load more data than necessary [S2, unofficial].
*   **Performance:** On-demand loading (`BKE_volume_load` vs `BKE_volume_grid_load`) helps manage initial load times and memory footprint for large files [S1].
*   **Scalability:** Large datasets may require resolution reduction in viewport modes to maintain interactivity [S2, unofficial].
*   **Strengths:** Efficient sparse storage via tree structure; compatibility with VFX standards (OpenVDB 7); support for multiple attribute grids [S1][S2, unofficial].
*   **Limitations:** Lack of sparse rendering optimization in some engines; strict filename requirements for sequences; no direct mesh conversion [S2, unofficial].
*   **When to Use:** Animation and VFX pipelines requiring smoke, fluid, or procedural volume simulation data [S2, unofficial].
*   **When Not to Use:** Scientific visualization workflows requiring direct image or video input; scenarios requiring mesh-to-volume conversion; applications requiring Python-based volume modifiers [S2, unofficial].

## Background
The OpenVDB Data Structure method was introduced in Blender 2.83, aligning with the OpenVDB 7 library to match the VFX Platform reference standard [S2, unofficial]. It was developed to support smoke simulation, procedural volume generation, and the import of OpenVDB files from external applications like Houdini and 3ds Max [S1]. The primary use case targets animation and VFX pipelines rather than scientific visualization [S2, unofficial].
