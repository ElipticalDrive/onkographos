# Volume Rendering (Cycles and Eevee)

Also called: Cycles Volume Rendering, Eevee Volume Rendering

## Overview
This article describes Blender's implementation of volume rendering for OpenVDB datasets, supporting the Cycles, Eevee, and Workbench renderers. It solves the problem of integrating sparse, large-scale VFX volume data into Blender's rendering pipeline by mapping the OpenVDB sparse tree structure 1:1 to a volume object [S2, unofficial]. It differs from its parent [VDB Volume Rendering with OpenVDB/NanoVDB](804-vdb-volume-rendering-with-openvdb-nanovdb.md) by providing the specific application-layer integration, shader binding, and renderer-specific optimizations (such as NanoVDB conversion for Cycles and dense 3D texture fallback for Eevee) required for end-user animation and VFX workflows [S1][S2, unofficial].

## How it works

### Inputs and Outputs
**Inputs:**
*   OpenVDB (`.vdb`) files containing sparse voxel grids [S2, unofficial].
*   Grid names: The system expects specific default grid names to bind data to physical properties [S2, unofficial].
*   Frame numbers: For animation sequences, files must follow zero-padded naming conventions [S2, unofficial].

**Outputs:**
*   Rendered images via Cycles (path-traced), Eevee (rasterized/voxel-based), or Workbench (preview).
*   Volume objects in the 3D viewport [S2, unofficial].

### Data Structures
The underlying volume data structure is a 1:1 mapping to the OpenVDB sparse tree representing a rectangular grid [S2, unofficial].
*   **Cycles:** The OpenVDB data structure is converted to NanoVDB format for rendering [S1]. This allows for fast, low-overhead decompression and sampling on the GPU [S1].
*   **Eevee/Workbench:** Volumes are rendered as dense 3D textures [S1]. This approach is noted as a temporary implementation that is to be optimized [S1].

### Grid Names and Shader Binding
The **Principled Volume** shader is the default shader for volume objects [S2, unofficial]. It maps OpenVDB grids to material properties using the following default names [S2, unofficial]:
*   `density`: Volume density.
*   `color`: Volume color (implied by shader context, though `temperature` is explicitly listed for fire) [S2, unofficial].
*   `temperature`: Used for fire simulations, representing temperature in units of Kelvin/1000 [S1].
*   `velocity`: Used for motion blur, representing 3D velocity vectors [S1].

If the default grid names are not present in the OpenVDB file, the user must manually specify the correct grid names in the shader nodes [S2, unofficial].

### Rendering Steps

1.  **Import and Validation:**
    *   Load the `.vdb` file(s).
    *   Validate frame numbering for sequences. If files lack consistent zero-padded digit counts (e.g., mixing `explosion_1` and `explosion_001`), the import fails or sequence playback fails [S2, unofficial].
    *   Construct the volume object. The internal data structure mirrors the OpenVDB sparse tree [S2, unofficial].

2.  **Bounding Mesh Construction (Cycles):**
    *   Build a bounding mesh around the volume data [S1].
    *   This mesh is used to determine if a ray is inside or outside the volume bounds, optimizing the sampling process [S1].

3.  **Data Conversion (Cycles):**
    *   Convert the OpenVDB data structure to NanoVDB [S1].
    *   This conversion enables the GPU to access the sparse data efficiently [S1].

4.  **Sampling and Rendering:**
    *   **Cycles:** Use the NanoVDB tree for sampling along rays [S1]. The renderer performs sparse volume dataset optimizations [S2, unofficial].
    *   **Eevee/Workbench:** Render the volume as a dense 3D texture [S1]. Note that sparse grid rendering is not yet implemented in these engines, leading to higher memory usage than theoretically necessary [S2, unofficial].

5.  **Viewport Display:**
    *   Display the volume object using the selected display mode (Solid, Wireframe, or Bounds) [S2, unofficial].
    *   In Solid mode, large datasets may be loaded at lower resolution to prevent performance issues (planned feature) [S2, unofficial].
    *   Selection is restricted to center point or wireframe to avoid cluttering Material and Rendered modes [S2, unofficial].

### Parameters and Configuration
*   **OpenVDB Version:** The implementation aligns with OpenVDB 7, matching the VFX Platform reference standard [S2, unofficial]. It maintains upward compatibility with older VDB files [S2, unofficial].
*   **Grid Visibility:** Grid visibility controls (eye icons) are planned to allow displaying only one grid at a time in the viewport, separate from the final shader result [S2, unofficial]. Currently, Workbench displays only one grid at a time, while Cycles and Eevee composite multiple grids via the Principled Volume shader [S2, unofficial].
*   **Motion Blur:** Motion blur support is planned to utilize velocity grids generated by external physics simulation software [S2, unofficial]. Currently, the `velocity` grid is defined but full motion blur integration is a future target [S1][S2, unofficial].

### Edge Cases and Pitfalls
*   **Sparse Grid Rendering:** Sparse grid rendering is not yet implemented in Cycles and Eevee, causing the system to use more memory than necessary [S2, unofficial].
*   **Viewport Artifacts:** Importing FumeFX volumes in Cycles may display as a chaotic group of planes in the viewport, although the final rendered image is correct [S2, unofficial].
*   **Sequence Import:** Importing VDB animation sequences fails if frame numbers lack consistent digit padding (e.g., 'explosion_1' vs 'explosion_001') [S2, unofficial].
*   **Mesh/Volume Conversion:** Mesh-to-volume and volume-to-mesh conversion are not yet supported; implementation is deferred to future volume modifiers [S2, unofficial].
*   **3D Textures:** Volume meshes cannot currently be used as 3D textures, as doing so would prevent the renderer from applying sparse volume dataset optimizations [S2, unofficial].
*   **Image/Video Import:** Loading density from image sequences or video files is not supported; users must convert to VDB format externally [S2, unofficial].
*   **Origin Repositioning:** Origin repositioning support is requested and considered a useful feature for volume objects but is not currently implemented [S2, unofficial].
*   **Metadata:** Per-file and per-grid metadata (float, vector, string types) is planned for future implementation [S2, unofficial].

### Pseudocode
The following pseudocode illustrates the logical flow of volume rendering in Blender, focusing on the Cycles renderer's conversion and sampling process. Note that specific OpenVDB/NanoVDB library calls are abstracted as they are C++ internals.

```python
def render_volume_object(volume_object, camera, samples):
    """
    Renders a volume object using the Cycles renderer.
    
    Args:
        volume_object: The Blender Volume Object containing OpenVDB data.
        camera: The camera object defining the view.
        samples: Number of samples for path tracing.
    """
    # 1. Load OpenVDB Data
    # The underlying data structure is a 1:1 mapping to the OpenVDB sparse tree
    openvdb_tree = volume_object.load_openvdb_data()
    
    # 2. Convert to NanoVDB for GPU Rendering
    # This step enables fast, low-overhead decompression and sampling
    nanovdb_tree = convert_to_nanovdb(openvdb_tree)
    
    # 3. Build Bounding Mesh
    # Determines when a ray is inside or outside the volume
    bounding_mesh = build_bounding_mesh(openvdb_tree)
    
    # 4. Setup Shader
    # Bind grids to Principled Volume shader properties
    shader = PrincipledVolumeShader()
    shader.bind_grid("density", openvdb_tree.get_grid("density"))
    shader.bind_grid("temperature", openvdb_tree.get_grid("temperature"))
    shader.bind_grid("velocity", openvdb_tree.get_grid("velocity"))
    
    # 5. Ray Marching / Sampling
    for each pixel in image:
        ray = camera.generate_ray(pixel)
        
        # Check intersection with bounding mesh
        if not bounding_mesh.intersects(ray):
            pixel.color = background_color
            continue
            
        # Sample volume along ray using NanoVDB
        color = vec3(0.0, 0.0, 0.0)
        alpha = 0.0
        t = ray.origin
        
        while t < ray.max_distance:
            # Sample density from NanoVDB tree
            density = nanovdb_tree.sample_density(t)
            
            # Accumulate color and alpha (Beer-Lambert law approximation)
            # Note: Actual implementation involves complex integration
            absorption = density * ray.step_size
            color += shader.get_color(t) * absorption * (1.0 - alpha)
            alpha += absorption * (1.0 - alpha)
            
            if alpha >= 1.0:
                break
                
            t += ray.step_size
            
        pixel.color = color
```

## Subtopics

### NanoVDB
A GPU-friendly, compressed format for OpenVDB data, enabling fast random access and decompression on the GPU [S1]. Chosen for Cycles to handle sparse data efficiently.

### Principled Volume Shader
The default shader for volume objects, binding OpenVDB grids to physical properties like density and temperature [S2, unofficial]. Chosen for its flexibility in VFX workflows.

### Dense 3D Texture Rendering
The method used by Eevee and Workbench to render volumes, converting sparse data to dense textures [S1]. Chosen for compatibility with rasterization pipelines, though less memory-efficient than sparse methods [S1][S2, unofficial].

## Operating characteristics

### Time and Memory Complexity
*   **Memory:** Cycles uses NanoVDB, which reduces memory footprint through compression [S1]. However, Eevee and Workbench render volumes as dense 3D textures, which uses significantly more memory than necessary for sparse data [S1][S2, unofficial]. Sparse grid rendering is not yet implemented in Cycles and Eevee, further increasing memory usage [S2, unofficial].
*   **Time:** Cycles path tracing performance depends on the complexity of the volume and the number of samples. The conversion to NanoVDB adds an initial overhead but speeds up rendering [S1]. Eevee's dense 3D texture approach is faster for preview but may be slower for high-resolution final renders due to memory bandwidth constraints [S1].

### Measured Performance
*   Specific performance metrics are not provided in the sources. However, the use of NanoVDB in Cycles is designed for "fast, low-overhead" rendering [S1].
*   Eevee and Workbench rendering of volumes as dense 3D textures is noted as "to be optimized" [S1].

### Scaling
*   **Resolution:** Large volume datasets in solid display mode are planned to load at lower resolution by default when exceeding a certain resolution threshold [S2, unofficial].
*   **Hardware:** Cycles leverages GPU acceleration via NanoVDB [S1]. Eevee and Workbench performance depends on the GPU's ability to handle dense 3D textures [S1].

### Strengths and Limitations
*   **Strengths:**
    *   Integration with OpenVDB 7, aligning with the VFX Platform reference standard [S2, unofficial].
    *   Support for multiple grids and shader binding via the Principled Volume shader [S2, unofficial].
    *   NanoVDB conversion in Cycles enables efficient rendering of sparse data [S1].
*   **Limitations:**
    *   Sparse grid rendering is not yet implemented in Cycles and Eevee, leading to higher memory usage [S2, unofficial].
    *   Limited support for non-VDB formats (e.g., image sequences, video) [S2, unofficial].
    *   Viewport display issues with certain volume types (e.g., FumeFX) [S2, unofficial].
    *   Lack of mesh-to-volume and volume-to-mesh conversion [S2, unofficial].

### When to Use
*   Use Cycles for high-quality, path-traced volume rendering in VFX and animation pipelines [S2, unofficial].
*   Use Eevee for real-time preview and faster renders, accepting lower quality and higher memory usage [S1].
*   Use Workbench for quick viewport previews [S2, unofficial].

### When Not to Use
*   Avoid for scientific visualization requiring non-VDB formats (e.g., image sequences) [S2, unofficial].
*   Avoid for applications requiring mesh-to-volume conversion [S2, unofficial].

## Background
Volume rendering in Blender was introduced in version 2.83, aligning with the OpenVDB 7 library to match the VFX Platform reference standard [S2, unofficial]. The primary use case targets animation and VFX pipelines rather than scientific visualization [S2, unofficial]. The implementation was developed to provide robust support for OpenVDB volumes, a standard format in the VFX industry for storing sparse voxel data [S2, unofficial].
