# Delayed Loading with Memory Mapping

Also called: Lazy Grid Loading, Mapped File I/O

## Overview
Delayed Loading with Memory Mapping loads OpenVDB (VDB) files on-demand by mapping the file into virtual memory rather than reading all grids into RAM immediately, thereby minimizing memory usage [S1, unofficial]. It solves the problem of high memory overhead from broad tile initialization by deferring physical memory allocation until specific data pages are accessed [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A file path, a boolean `delayLoad` flag, and a threshold `copyMaxBytes` for temporary file creation [S1, unofficial].
- Output: An input stream configured to read from either a temporary copy or a memory-mapped buffer [S1, unofficial].

**Data Structures:**
- `MappedFile`: Manages the file descriptor and memory mapping lifecycle, holding the filename and an `autoDelete` flag [S1, unofficial].
- `TempFile`: Creates a temporary file in the system directory to store a copy of the source file [S1, unofficial].
- `std::ifstream` / `std::istream`: Standard C++ stream interfaces used for direct file reading and the final returned stream [S1, unofficial].

**Parameters:**
- `DEFAULT_COPY_MAX_BYTES`: 500,000,000 bytes (500 MB). Files smaller than this threshold are copied to a temporary location to prevent read corruption during concurrent modification [S1, unofficial]. The threshold is overridable via the environment variable `OPENVDB_DELAY_LOAD_COPY_MAX_BYTES` [S1, unofficial].

**Steps:**
1. Check if delayed loading is enabled globally and if the caller requested it [S1, unofficial].
2. If disabled, open the file directly using a standard binary input stream [S1, unofficial].
3. If enabled, compare the file size against `copyMaxBytes` [S1, unofficial].
4. If the file is smaller, copy it to a temporary file using a standard copy routine, set the temporary path as the working filename, and mark it for auto-deletion [S1, unofficial].
5. If the copy fails, log a warning and fall back to direct reading from the original file [S1, unofficial].
6. If the file is larger, use the original filename and mark it for no auto-deletion [S1, unofficial].
7. Instantiate a memory-mapped file object with the chosen filename and deletion flag [S1, unofficial].
8. Generate a stream buffer from the memory mapping and wrap it in a standard input stream [S1, unofficial].

**Pseudocode:**
```python
def delayed_load_file(filename: str, delay_load: bool, copy_max_bytes: int = 500000000) -> io.IOBase:
    """
    Loads a VDB file using delayed loading/memory mapping if enabled.
    Returns a stream object backed by either a direct file read or a memory-mapped buffer.
    """
    # Check global and local flags for delayed loading
    # Note: Global check implementation not specified in sources [G]
    if not delay_load or not is_delayed_loading_enabled():
        return open(filename, 'rb')

    is_temp_file = False
    current_filename = filename

    # Determine if we need to copy the file for safety
    file_size = os.path.getsize(filename)
    if file_size < copy_max_bytes:
        try:
            import tempfile
            with tempfile.NamedTemporaryFile(delete=False) as temp_file:
                current_filename = temp_file.name
                is_temp_file = True
                with open(filename, 'rb') as src:
                    temp_file.write(src.read())
        except Exception:
            # Log warning and fall back to direct reading if copy fails
            log_warning("Failed to copy file for delayed loading, falling back to direct read.")
            return open(filename, 'rb')

    # Create memory-mapped file object
    mapped_file = MappedFile(current_filename, auto_delete=is_temp_file)
    
    # Create buffer from memory mapping
    stream_buffer = mapped_file.create_buffer()
    
    # Wrap buffer in stream
    stream = io.BufferedReader(stream_buffer)
    return stream
```

**Edge Cases and Pitfalls:**
- **Concurrent Modification:** If the source file is modified while being read via memory mapping, data corruption may occur [S1, unofficial]. This is mitigated by copying small files (< 500 MB) to a temporary location, ensuring the mapped view remains stable [S1, unofficial].
- **Copy Failure:** If copying to a temporary file fails (e.g., due to permissions or disk space), the system logs a warning and falls back to standard file reading, potentially losing the benefits of delayed loading for that specific file [S1, unofficial].
- **Large Files:** Files larger than `copy_max_bytes` are memory-mapped directly [S1, unofficial]. If these files are modified concurrently, the reader may see inconsistent data or crashes [S1, unofficial].

## Subtopics

### Deferred Leaf Loading
This technique significantly reduces the in-memory footprint, especially when rendering very large volumes that are culled by a camera frustum or dominated by early ray termination [S2, unofficial]. It encodes file offsets into the LeafNodes and delays the loading of `mLeafDATs` until the voxel values, rather than just the grid topology, are actually needed [S2, unofficial].

### Out-of-Core VDB Storage
A storage mode for VDB where data is stored on disk and loaded into memory on demand, supporting load-on-read applications like volume rendering but not dynamic topology or stencil-based finite-difference computations [S2, unofficial]. Configuration `[Hash,5,4,3]` uses a smaller tree structure compared to `[Hash,4,3,2]`, resulting in a smaller memory footprint for out-of-core storage [S2, unofficial]. At resolution 16,384^3, the out-of-core `[Hash,5,4,3]` VDB uses 468.2 MB, compared to 6,722.9 MB for in-core storage [S2, unofficial]. Out-of-core VDB configurations have a memory footprint almost an order of magnitude smaller than in-core configurations, whereas in-core VDB is less than twice the size of DT-Grid [S2, unofficial].

## Operating characteristics
- **Time Complexity:** Initialization is $O(1)$ for memory mapping setup, but actual data access incurs page fault latency [G]. Total load time is proportional to the amount of data accessed, not the file size [G].
- **Memory Complexity:** $O(1)$ relative to file size for the mapping overhead, plus the memory required for the accessed tiles [G]. Significantly lower than eager loading for sparse or large grids [G].
- **Measured Performance:** Effective for scenes where only a fraction of the volume is visible or processed at any time [G]. Performance degrades if the working set exceeds physical RAM, causing thrashing [G].
- **Strengths:** Drastically reduces peak memory usage for large VDB files [G]. Enables loading of files larger than available RAM (provided the working set fits) [G].
- **Limitations:** Not suitable for concurrent modification of source files without copying [G]. Page faults can cause latency spikes during initial access [S1, unofficial].
- **When to Use:** When memory is constrained, or when loading very large VDB files where only a subset of voxels is needed [G].
- **When Not to Use:** When the entire file must be accessed immediately, or when the source file is actively being written to and cannot be safely copied [S1, unofficial].

## Background
This technique is implemented within the OpenVDB library to address the high memory overhead associated with loading large sparse voxel grids [S1, unofficial]. It leverages the operating system's virtual memory manager to map file contents directly into the process address space, deferring physical memory allocation until pages are accessed [S1, unofficial].
