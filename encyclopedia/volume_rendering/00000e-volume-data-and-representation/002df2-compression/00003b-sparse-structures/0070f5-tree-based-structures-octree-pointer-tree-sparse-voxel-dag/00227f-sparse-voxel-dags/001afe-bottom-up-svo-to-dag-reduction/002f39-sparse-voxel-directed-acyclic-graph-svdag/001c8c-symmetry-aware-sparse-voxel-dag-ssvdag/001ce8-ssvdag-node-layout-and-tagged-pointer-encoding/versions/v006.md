# SSVDAG Node Layout and Tagged Pointer Encoding

Also called: Compact representation, Tagged pointer encoding

## Overview
This method defines the memory layout and pointer encoding scheme for Symmetry-aware Sparse Voxel Directed Acyclic Graphs (SSVDAGs) to minimize memory consumption while maintaining GPU-friendly traversal performance. It replaces fixed-size child pointers with variable-length tagged pointers (2 or 4 bytes) that embed transformation codes, addressing a key limitation of standard SVDAGs where all non-null pointers consume 4 bytes [S1, unofficial]. By exploiting the skewed distribution of node references, it significantly reduces the memory footprint for high-resolution scenes without requiring decompression during ray traversal [S1, unofficial].

## How it works

### Inputs and Outputs
*   **Input:** A Sparse Voxel DAG structure where nodes may share subtrees via symmetry transforms (planar reflections).
*   **Output:** A compact binary layout for inner-level nodes consisting of a 16-bit header followed by variable-length child pointer data.

### Data Structures

#### Inner-Level Node Header
Each inner-level node begins with a 16-bit header. This header contains 8 entries, one for each potential child (corresponding to the 8 octants). Each entry is a 2-bit code:
*   `00`: Null pointer (child does not exist). No data follows for this child.
*   `01`: Child pointer is 16 bits (2 bytes).
*   `10`: Child pointer is 32 bits (4 bytes).
*   `11`: Child pointer is 32 bits (4 bytes).

#### Child Pointer Encoding
The format of the child pointer data immediately following the header depends on the tag in the header. The pointer encodes both the offset to the child node and a 3-bit transformation code.

**1. 16-bit Pointer (Tag `01`)**
*   **Size:** 2 bytes.
*   **Layout:**
    *   Bits [15:13] (3 bits): Transformation code (reflection tag).
    *   Bits [12:0] (13 bits): Offset in number of *level-words* from the start of the next level's array.
*   **Addressing Range:**
    *   For inner levels: Level-word size is 2 bytes. Max offset $2^{13}$ words $\times$ 2 bytes/word = $2^{14}$ bytes (16 KB).
    *   For leaf levels: Level-word size is 8 bytes. Max offset $2^{13}$ words $\times$ 8 bytes/word = $2^{16}$ bytes (64 KB).

**2. 32-bit Pointer (Tags `10` and `11`)**
*   **Size:** 4 bytes.
*   **Layout:**
    *   Bits [31:29] (3 bits): Transformation code (reflection tag).

### Algorithm: Traversal with Tagged Pointers

To traverse the SSVDAG, the shader must compute the byte offset to the $i$-th child pointer within the node's header data. Because pointers have variable sizes (0, 2, or 4 bytes), this requires summing the sizes of all preceding pointers.

**Pseudocode:**

```python
def get_child_pointer(node_header, child_index):
    """
    Extracts the child pointer and transformation status for a given child index.
    
    Args:
        node_header (int): The 16-bit header value.
        child_index (int): The index of the child (0-7).
        
    Returns:
        tuple: (pointer_data, transformation_code, pointer_size_bytes)
               pointer_data is the raw offset bits.
               transformation_code is the 3-bit reflection tag.
               pointer_size_bytes is 0 if null, 2 or 4.
    """
    # Extract the 2-bit tag for the specific child
    # Each child occupies 2 bits in the 16-bit header
    tag = (node_header >> (child_index * 2)) & 0x3
    
    if tag == 0x0:
        # Null pointer
        return (0, 0, 0)
    
    # Determine pointer size and transformation code extraction
    if tag == 0x1: # Tag 01: 16-bit pointer
        # In a real implementation, this data would be read from memory
        # at the calculated byte offset. Here we assume 'raw_ptr' is fetched.
        # raw_ptr = read_16bit_from_memory(...)
        # For the purpose of this layout definition, we define the structure:
        # Bits [15:13] are transformation. Bits [12:0] are offset.
        transformation_code = (raw_ptr >> 13) & 0x7
        offset_bits = raw_ptr & 0x1FFF
        return (offset_bits, transformation_code, 2)
        
    else: # Tag 10 or 11: 32-bit pointer
        # raw_ptr = read_32bit_from_memory(...)
        # Bits [31:29] are transformation.
        # Bits [28:0] are lowest 29 bits of offset.
        # Bit [29] of offset is derived from header tag LSB.
        transformation_code = (raw_ptr >> 29) & 0x7
        offset_low_29 = raw_ptr & 0x1FFFFFF
        header_lsb = tag & 0x1
        offset_high_bit = header_lsb << 29
        full_offset = offset_low_29 | offset_high_bit
        return (full_offset, transformation_code, 4)

def compute_byte_offset(node_header, child_index):
    """
    Computes the byte offset from the start of the child pointer data 
    to the beginning of the i-th child's pointer.
    """
    offset = 0
    for i in range(child_index):
        tag = (node_header >> (i * 2)) & 0x3
        if tag == 0x0:
            size = 0
        elif tag == 0x1:
            size = 2
        else: # 10 or 11
            size = 4
        offset += size
    return offset
```

**Traversal State Management:**
1.  **Initialization:** The traversal maintains a 3-bit `transformation_status`, initialized to 0. This status indicates which reflections must be applied to indices for child pointers in inner nodes or voxel contents in leaf nodes.
2.  **Descent:** When descending to a child, the `transformation_status` is updated by XOR-ing it with the 3-bit `transformation_code` extracted from the child's tagged pointer.
3.  **Backtracking:** The previous `transformation_status` is pushed to a stack along with the current node to allow restoration upon backtracking.

### Parameters and Edge Cases
*   **Level-Word Size:** Inner levels use 2-byte words; leaf levels use 8-byte words. This distinction is critical for interpreting the offset in 16-bit pointers.
*   **Precision/Boundaries:** The 16-bit pointer is limited to the first 16 KB (inner) or 64 KB (leaf) of the next level. If a shared node lies beyond this range, the 32-bit pointer must be used.
*   **Pitfall:** Accessing the $i$-th child requires computing the sum of sizes of pointers $0$ to $i-1$. Since sizes are 0, 2, or 4 bytes, this cannot be done with simple multiplication as in fixed-size layouts. The source notes this computation is performed in the shader using a manually unrolled loop [S1, unofficial].

## Subtopics

### [Compact SSVDAG Encoding](5227-compact-ssvdag-encoding.md)
A GPU-friendly memory layout that combines leaf grouping, frequency-based pointer compaction, and half-word memory alignment. It distinguishes itself by leveraging highly skewed reference distributions to reduce memory footprint further.

### [SVDAG Parameter Configurations](5945-svdag-parameter-configurations.md)
Defines the exact bit-widths for the Child Node Mask (CHNM) and the three distinct Child Pointer Types (PT1, PT2, PT3). It differs from fixed-size SVO layouts by allowing mixed pointer lengths to adapt to spatial locality.

## Operating characteristics
*   **Memory Footprint:** Significantly reduced compared to standard SVDAGs. In a 64K³ Powerplant dataset, the most common 10% of nodes account for nearly 90% of pointers at level 14 and nearly 50% at level 11, allowing the variable-length encoding to be highly effective [S1, unofficial].
*   **Complexity:** Traversal complexity increases slightly due to the need to compute variable byte offsets for child pointers. This is mitigated by using a manually unrolled loop in the shader [S1, unofficial].
*   **Addressing Range:** Supports addressing >2GB into inner levels and >8GB into leaves, sufficient for very large scenes [S1, unofficial].
*   **Strengths:** Lossless compression, GPU-friendly (no decompression needed), handles symmetry transforms natively.
*   **Limitations:** Limited addressing range for 16-bit pointers; requires careful handling of variable-length offsets in shaders.

## Background
The SSVDAG structure was introduced by Kämpe et al. in 2016 as an extension of the Sparse Voxel DAG (SVDAG) [S1, unofficial]. While SVDAGs merged identical subtrees, SSVDAGs further merged subtrees that were identical through similarity transforms (specifically planar reflections). The compact node layout with tagged pointers was developed to address the memory overhead of storing transformation codes and child pointers separately, building on the SVDAG foundation [Kämpe et al. 2013] [S1, unofficial].
