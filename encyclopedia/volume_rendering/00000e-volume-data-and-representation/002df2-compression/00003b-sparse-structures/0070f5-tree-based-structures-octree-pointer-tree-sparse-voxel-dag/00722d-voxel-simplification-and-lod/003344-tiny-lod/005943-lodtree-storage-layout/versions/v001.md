# LODTree Storage Layout
Also called: LODTree
## Overview
LODTree is a sparse, hierarchical storage layout for volumetric data that enables efficient level-of-detail (LOD) traversal and compression by organizing voxels into a tree structure with virtual expansion [S1, unofficial]. It differs from sibling methods like [Trilinear Evaluation on Compressed Trees](7074-trilinear-evaluation-on-compressed-trees.md) by explicitly managing virtual voxel expansion across multiple LOD levels to bound storage overhead, whereas siblings may focus on different compression primitives or evaluation strategies [S1, unofficial]. It solves the problem of storing large volumetric datasets with minimal memory footprint while supporting dynamic LOD selection, outperforming static geometry representations when multiple isosurface thresholds are required [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A structured grid volume dataset with $k$ original voxels (cells).
- Output: An LODTree file containing $V$ nodes, where each node stores an index and keys for min, max, and LOD.

**Data Structures:**
Each node in the LODTree requires exactly 6 bytes of storage:
- 4 bytes for an index.
- 2 bytes for the combined min, max, and LOD keys [S1, unofficial].
The layout relies on heavy use of bit-mapped cell data representation to achieve this compactness [S1, unofficial].

**Formulas and Parameters:**
Let $n$ be the number of levels-of-detail and $k$ be the number of voxels in the original data file. The total number of nodes $V$ in the LODTree file is determined by the virtual voxel expansion process, where each level of detail creates additional cells equal to the original number of cells divided by the cube of the cell size scaling factor [S1, unofficial].

The total number of nodes is given by:
$$ V = n \times k^3 $$
*Note: The source text contains a garbled formula here, but explicitly states "where n is the number of levels-of-detail and k is the number of voxels (cells) in the data file" in the context of the total node count derivation [S1, unofficial]. However, the subsequent analysis of the Riemann zeta function suggests a geometric series summation rather than a simple product. The text states: "there are a total of ... nodes in the LODTree file". The formula $V = n \times k^3$ appears to be a misinterpretation or typo in the source's transcription, as the subsequent calculation of overhead uses a factor derived from the Riemann zeta function $\zeta(3)$.*

The fractional number of LODTree cells required for each voxel in the simulation data file is bounded by the Riemann zeta function $\zeta(3)$:
$$ \zeta(3) = \sum_{i=1}^{\infty} \frac{1}{i^3} \approx 1.20206 $$
This value constitutes the upper bound for the fractional number of LODTree cells required per original voxel [S1, unofficial].

**Typical Values and Examples:**
- For $n=10$ levels of detail, the overhead factor is calculated as:
  $$ \text{Overhead Factor} = \zeta(3) \times 6 \text{ bytes} \approx 1.20206 \times 6 \approx 7.21 \text{ bytes} $$
  *Correction based on source text:* The source explicitly states: "For an LODTree that contains ten levels of detail... yields 6.72 bytes of overhead per cell". This implies the factor used is not exactly $\zeta(3)$ but a truncated sum or specific constant derived for $n=10$. The source states: "which multiplied by the number of bytes occupied by each LODTree cell (six) yields 6.72 bytes". Thus, the multiplier is $6.72 / 6 = 1.12$.
- If the base voxel storage is 4 bytes, the approximate byte overhead factor is:
  $$ \frac{6.72}{4} = 1.7 $$
  This means the LODTree adds 1.7 times the storage of the original voxel data [S1, unofficial].

**Pseudocode:**
The source does not provide algorithmic pseudocode for building or traversing the LODTree, only storage layout and overhead calculations. Implementation details for the bit-mapped representation and virtual expansion logic are not given in the provided text [S1, unofficial].

**Edge Cases and Pitfalls:**
- The source notes that the actual storage consumed by each voxel in the data file is slightly higher than 4 bytes to account for data points constituting the edges of the structured grid [S1, unofficial].
- The overhead calculation assumes an infinite number of levels of detail for the $\zeta(3)$ bound, but practical implementations use finite $n$ [S1, unofficial].

## Subtopics

### Dynamic Isosurface Extraction
The primary application context for LODTree, allowing efficient view of multiple isosurface thresholds without storing separate static geometry for each [S1, unofficial].

### Comparison with Geometry Representations
LODTree is compared to isosurface geometry representations, which are more compact per threshold but require separate storage for each threshold, making them less efficient when many thresholds are needed [S1, unofficial].

## Operating characteristics
- **Time Complexity:** Not given in the sources.
- **Memory Complexity:** The storage overhead is bounded by the Riemann zeta function $\zeta(3) \approx 1.20206$ times the original data size in terms of cell count, translating to approximately 6.72 bytes of overhead per original cell for 10 LOD levels [S1, unofficial].
- **Measured Performance:** For a structured grid dataset with 10 LOD levels, the overhead is 6.72 bytes per cell, resulting in an approximate byte overhead factor of 1.7 relative to the 4-byte base voxel storage [S1, unofficial].
- **Scaling:** The overhead factor converges to the $\zeta(3)$ bound as the number of levels of detail increases [S1, unofficial].
- **Strengths:** Compact storage through bit-mapped representation; efficient for dynamic LOD and multiple isosurface thresholds compared to static geometry [S1, unofficial].
- **Limitations:** Overhead is significant (1.7x base size); implementation complexity of bit-mapped representation and virtual expansion is not detailed [S1, unofficial].
- **When to use:** When dynamic LOD and multiple isosurface thresholds are required for large volumetric datasets [S1, unofficial].
- **When not to use:** When only a single isosurface threshold is needed, as static geometry may be more efficient [S1, unofficial].
