# LODTree Storage Layout

Also called: LODTree

## Overview
The LODTree storage layout is a sparse, hierarchical data structure designed to store volumetric data with multiple levels of detail (LOD) in a compact format, enabling efficient dynamic isosurface extraction [S1, unofficial]. It differs from sibling methods like [Trilinear Evaluation on Compressed Trees](7074-trilinear-evaluation-on-compressed-trees.md) by explicitly managing virtual voxel expansion across discrete LOD levels using a bit-mapped cell representation to minimize storage overhead [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A structured grid volume dataset with $k$ original voxels (cells).
*   **Output:** An LODTree file containing $V$ nodes, where each node represents a virtual voxel at a specific level of detail [S1, unofficial].

**Data Structures:**
Each node in the LODTree file is stored as a fixed-size record of 6 bytes [S1, unofficial]:
1.  **Index:** 4 bytes. An integer index pointing to the node or its parent/children within the tree structure [S1, unofficial].
2.  **Keys:** 2 bytes. A combined field storing the minimum value, maximum value, and Level-of-Detail (LOD) identifier for the cell [S1, unofficial].
    *   *Note:* The exact bit-packing scheme for the min, max, and LOD keys within these 2 bytes is not specified in the sources, but heavy use of bit-mapped representation is required to achieve this compactness [S1, unofficial].

**Construction Steps:**
1.  Define the original voxel count $k$ and the target number of LOD levels $n$ [S1, unofficial].
2.  Determine the expansion ratio $r$ per level, where each level creates additional cells equal to the original number of cells divided by the cube of the cell size scaling factor [S1, unofficial].
3.  Compute the total node count using the geometric series: $V = k \sum_{i=0}^{n-1} r^i$ [S1, unofficial].
4.  Pack each of the $V$ nodes into the 6-byte layout (4-byte index + 2-byte keys) using bit-mapped representation [S1, unofficial].

**Storage Calculation and Geometry:**
*   Let $k$ be the number of voxels in the original data file [S1, unofficial].
*   Let $n$ be the number of levels of detail [S1, unofficial].
*   Each level of detail creates additional cells equal to the original number of cells divided by the cube of the cell size scaling factor [S1, unofficial].
*   For an infinite number of levels of detail, the fractional number of LODTree cells required per original voxel converges to the Riemann zeta function $\zeta(3) \approx 1.20206$ [S1, unofficial]. This value serves as an upper bound for the fractional number of LODTree cells required for each voxel in the simulation data file [S1, unofficial].

**Parameters and Values:**
*   **Riemann Zeta Bound:** The series $\sum_{i=1}^{\infty} \frac{1}{i^3}$ converges to $\zeta(3) \approx 1.20206$ [S1, unofficial].
*   **Node Size:** 6 bytes per LODTree cell (4 bytes index + 2 bytes keys) [S1, unofficial].
*   **Example Overhead:** For $n=10$ levels of detail, the multiplier factor is 1.12, yielding 6.72 bytes of overhead per cell in the original structured grid data set [S1, unofficial].
*   **Overhead Factor:** Assuming 4 bytes per original voxel, the approximate byte overhead factor is 1.7 ($6.72 / 4$) [S1, unofficial].

**Pseudocode:**
The following pseudocode calculates the theoretical storage overhead for an LODTree given the number of original voxels, levels of detail, and the expansion ratio per level, based on the geometric series described in the sources.

```python
def calculate_lodtree_overhead(num_original_voxels: int, num_levels: int, expansion_ratio: float) -> tuple:
    """
    Calculates the storage overhead for an LODTree structure.
    
    Args:
        num_original_voxels (int): k, the number of voxels in the original structured grid.
        num_levels (int): n, the number of levels of detail.
        expansion_ratio (float): r, the fractional cell count added per level relative to the previous level.
        
    Returns:
        tuple: (total_nodes, overhead_bytes_per_original_voxel, overhead_factor)
    """
    bytes_per_node = 6  # 4 bytes index + 2 bytes keys [S1, unofficial]
    original_voxel_size = 4.0  # Approximation used in source [S1, unofficial]
    
    # Geometric series sum: 1 + r + r^2 + ... + r^(n-1)
    if expansion_ratio == 1.0:
        multiplier = num_levels
    else:
        multiplier = (1.0 - expansion_ratio**num_levels) / (1.0 - expansion_ratio)
        
    total_nodes = num_original_voxels * multiplier
    total_overhead_bytes = total_nodes * bytes_per_node
    overhead_per_original_voxel = total_overhead_bytes / num_original_voxels
    overhead_factor = overhead_per_original_voxel / original_voxel_size
    
    return total_nodes, overhead_per_original_voxel, overhead_factor
```
*Note: The exact expansion ratio $r$ is not provided in the sources [S1, unofficial]. For $n=10$, the source specifies a multiplier of 1.12, which yields the stated 6.72 bytes/voxel overhead [S1, unofficial].*

**Edge Cases and Pitfalls:**
*   **Precision:** The source notes that the actual storage consumed by each voxel in the data file is slightly higher than 4 bytes to account for data points constituting the edges of the structured grid [S1, unofficial]. Implementers must account for this when calculating the exact overhead factor [S1, unofficial].
*   **Infinite Levels:** The Riemann zeta bound $\zeta(3) \approx 1.20206$ is an upper bound for infinite levels [S1, unofficial]. For finite levels, the geometric series must be used [S1, unofficial].
*   **Bit-mapping:** Achieving the 6-byte node size requires heavy use of bit-mapped cell data representation [S1, unofficial]. Improper packing will increase the node size and degrade performance [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** The storage overhead is approximately 1.7 times the size of the original voxel data for 10 levels of detail [S1, unofficial]. The theoretical upper bound for infinite levels is a fractional cell count of $\zeta(3) \approx 1.20206$ per original voxel [S1, unofficial].
*   **Measured Performance:** For 10 levels of detail, the overhead is 6.72 bytes per cell in the original structured grid data set [S1, unofficial].
*   **Strengths:** Compact storage for multi-resolution data; enables dynamic isosurface extraction without pre-computing static geometry for each threshold [S1, unofficial].
*   **Limitations:** Overhead increases with the number of LOD levels; requires careful bit-packing to maintain the 6-byte node size; not suitable if static geometry is preferred for very few thresholds [S1, unofficial].
*   **When to use:** When dynamic isosurface extraction at multiple thresholds and LODs is required for large volumetric datasets [S1, unofficial].
*   **When not to use:** When the number of required isosurface thresholds is very small (e.g., <10), as static geometry representations may be more efficient [S1, unofficial].

## Background
The method is discussed in the context of dynamic isosurface extraction and level-of-detail techniques in voxel space [S1, unofficial]. It addresses storage overhead concerns associated with large simulation volume datasets while maintaining the functionality of dynamic isosurface viewing [S1, unofficial]. The method relies on the mathematical properties of the Riemann zeta function to bound the storage expansion [S1, unofficial].
