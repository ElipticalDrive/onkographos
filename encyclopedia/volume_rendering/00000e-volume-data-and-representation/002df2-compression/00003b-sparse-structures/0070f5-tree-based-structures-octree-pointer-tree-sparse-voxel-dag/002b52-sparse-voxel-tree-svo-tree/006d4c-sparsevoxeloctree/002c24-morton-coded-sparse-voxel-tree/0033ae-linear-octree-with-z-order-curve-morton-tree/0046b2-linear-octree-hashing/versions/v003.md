# Linear Octree Hashing

Also called: Gargantini's linear octree, Linear Octree, Linear Quadtree, Sorted leaf array lookup

## Overview
Linear Octree Hashing is a pointerless sparse octree storage method where only leaf nodes are stored in a contiguous memory array, sorted by their Morton (Z-order) code to enable binary search [S1, unofficial][S2, unofficial]. It solves the problem of memory overhead in traditional octrees by eliminating interior nodes and pointers, trading lookup speed for significant storage reduction [S1, unofficial][S2, unofficial]. Unlike its parent [Linear Octree with Z-order curve (Morton tree)](7054-linear-octree-with-z-order-curve-morton-tree.md), which eliminates inner nodes by storing nodes in a linear array generated using a Z-order curve, this variant relies strictly on the sorted leaf array for all spatial queries [S1, unofficial][S2, unofficial].

## How it works
**Inputs:** A set of 3D voxel coordinates $(x, y, z)$ representing occupied leaf nodes within a bounded cubic domain [S1, unofficial][S2, unofficial].
**Outputs:** A sorted array of leaf nodes, where each entry contains the Morton code and associated voxel data [S1, unofficial][S2, unofficial].

**Data Structures:**
The core structure is a linear array `Leaves`. Each element `Leaves[i]` contains:
- `morton_code`: An integer representing the Z-order curve index of the leaf node [S1, unofficial][S2, unofficial].
- `data`: The voxel value or metadata associated with the leaf [S1, unofficial][S2, unofficial].

**Steps:**
1. **Morton Encoding:** For each occupied leaf node at coordinates $(x, y, z)$, compute its Morton code $M$ by interleaving the bits of the coordinates [G].
2. **Collection:** Store pairs $(M, \text{data})$ for all leaf nodes in a temporary list [S1, unofficial][S2, unofficial].
3. **Sorting:** Sort the list of pairs based on the `morton_code` in ascending order [S1, unofficial][S2, unofficial].
4. **Storage:** Write the sorted list into the contiguous `Leaves` array [S1, unofficial][S2, unofficial].

**Point Location (Query):**
To find the node containing a query point $P(x_q, y_q, z_q)$:
1. Compute the Morton code $M_q$ for the query point [G].
2. Perform a binary search on the `Leaves` array for $M_q$ [S1, unofficial][S2, unofficial].
3. If $M_q$ is found, return the associated data [S1, unofficial][S2, unofficial].
4. If not found, check the predecessor leaf's Morton interval to determine if the query falls within an occupied voxel or empty space [S3, unofficial].

**Parameters:**
- $D$: Depth of the octree. Not given in the sources.
- $L$: Number of leaf nodes [S1, unofficial][S2, unofficial].

**Edge Cases and Pitfalls:**
- **Empty Regions:** The structure does not store empty interior nodes [S2, unofficial]. Queries for points in empty space require interval checking against predecessor/successor leaves to skip free space [S3, unofficial].
- **Neighbor Finding:** Finding spatial neighbors is difficult because neighbors may not be adjacent in the sorted array [S2, unofficial].
- **Precision:** Morton codes grow with tree depth. Standard integer types must be used to avoid overflow [G].

**Pseudocode:**
```python
def build_linear_octree(voxels):
    # voxels: list of ((x, y, z), data)
    leaves = []
    for (x, y, z), data in voxels:
        m = morton_encode(x, y, z)
        leaves.append((m, data))
    leaves.sort(key=lambda pair: pair[0])
    return leaves

def query_linear_octree(leaves, x, y, z):
    m_q = morton_encode(x, y, z)
    # Binary search for m_q
    idx = bisect_left([m for m, _ in leaves], m_q)
    if idx < len(leaves) and leaves[idx][0] == m_q:
        return leaves[idx][1], 1  # Exact hit
    if idx > 0:
        m_prev, data_prev = leaves[idx-1]
        # Check if query falls within predecessor's Morton interval
        # Interval bounds depend on the tree level of the predecessor [G]
        if m_prev <= m_q < m_prev + (1 << (3 * current_level)):
            return data_prev, 1  # Occupied voxel
    return None, 0  # Empty space
```

## Subtopics

### [Linear Level Octree (LLO)](16467-linear-level-octree-llo.md)
Linear Level Octree (LLO) is a hierarchical data structure for volume data that stores only leaf nodes, implicitly encoding location, size, and path from root to nodes to reduce memory and processing cost. It extends the linear octree scheme by using a specific labeling system that allows efficient estimation of spatial relations between points and nodes. Unlike its parent [Linear Octree Hashing](11794-linear-octree-hashing.md), which relies on hash tables for lookup, LLO uses a deterministic coordinate-based key system that facilitates direct geometric calculations without hashing overhead.

### Sparse Octree Query via Morton Encoding
Sparse Octree Query via Morton Encoding is a method to query a sparse voxel field stored in a flat, sorted array of Morton codes [S3, unofficial]. It maps a query point to its finest-level Morton code and uses binary search to find the occupied voxel containing the point or the largest empty voxel interval to skip [S3, unofficial]. If the successor code equals the query code, it returns the successor leaf as an exact hit [S3, unofficial]. If the query code falls within the Morton interval covered by the predecessor leaf, it returns the predecessor leaf as an occupied voxel [S3, unofficial]. It iterates from level $l = 0$ to $L$, computing the Morton code at each level and checking if the finest-level successor interval is contained within the current level's predecessor and successor intervals, returning the current level and empty voxel if so [S3, unofficial].

## Operating characteristics
- **Time Complexity:** Node lookup is $O(\log_2(L))$, where $L$ is the number of leaf nodes [S1, unofficial][S2, unofficial]. This is slower than pointer octrees ($O(\log_8(N))$) for general cases [S2, unofficial].
- **Memory Complexity:** $O(L)$, storing only leaf nodes [S2, unofficial]. No memory is wasted on interior nodes or pointers [S2, unofficial].
- **Performance:** Generally slower to hash than pointer octrees, except in highly vertical trees with few leaf nodes relative to interior nodes [S2, unofficial].
- **Strengths:** Minimal memory footprint; suitable for applications where storage is critical and only leaf data is needed [S2, unofficial].
- **Limitations:** Unsuitable for applications requiring traversal of non-leaf structures or efficient neighbor finding without additional data [S2, unofficial].

## Background
The linear octree was originally proposed by Gargantini for quadtrees [S1, unofficial] and later extended to octrees using Morton's interleaved base-8 code [S1, unofficial][S2, unofficial]. It is a pointerless structure designed to minimize storage overhead by eliminating interior nodes and pointers [S2, unofficial]. While not directly applied to volume rendering in the cited survey, it is noted for its potential in compression-based adaptive octree methods [S2, unofficial].
