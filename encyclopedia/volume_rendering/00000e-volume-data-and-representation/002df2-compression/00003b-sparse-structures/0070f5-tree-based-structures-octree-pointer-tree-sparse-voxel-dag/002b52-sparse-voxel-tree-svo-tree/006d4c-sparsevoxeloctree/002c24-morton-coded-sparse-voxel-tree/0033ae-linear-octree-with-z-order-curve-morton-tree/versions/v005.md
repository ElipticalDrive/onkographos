# Linear Octree with Z-order curve (Morton tree)
Also called: Morton tree
## Overview
A storage method for sparse octrees that stores nodes in a linear array generated using a Z-order curve, eliminating the storage of inner nodes [S1, unofficial]. It solves the problem of memory overhead in traditional octrees by replacing recursive pointers with a contiguous memory layout [S1, unofficial]. It differs from its parent [Morton-coded Sparse Voxel Tree](5212-morton-coded-sparse-voxel-tree.md) by explicitly discarding interior nodes from the primary storage structure, whereas the parent retains them [S1, unofficial].
## How it works
**Inputs and outputs:**
- Input: A sparse octree structure (typically precalculated) [S1, unofficial].
- Output: A linear array of leaf nodes sorted by Morton code, and a secondary data texture for voxel attributes [S1, unofficial].

**Data structures:**
1. **Linear Tree Array:** A contiguous array containing only leaf nodes, sorted by their Z-order (Morton) code [S1, unofficial].
2. **Data Texture:** A secondary storage structure (e.g., a 2D texture or array) that holds the actual voxel data [S1, unofficial].

**Steps:**
1. Identify all leaf nodes in the sparse octree.
2. Compute the Morton code (Z-order curve index) for each leaf node based on its 3D coordinates [S1, unofficial].
3. Sort the leaf nodes by their Morton codes [S1, unofficial].
4. Store the sorted leaf nodes in a linear array [S1, unofficial].
5. Store the voxel data in a separate data texture, indexed by the leaf node identifiers or Morton codes [S1, unofficial].

**Formulas:**
- Morton Code $M(x, y, z)$: The exact bit-interleaving algorithm is not given in the sources [S1, unofficial]. Standard implementations interleave the bits of the 3D coordinates $x, y, z$ into a single integer [G].

**Parameters:**
- Tree depth: Determined by the resolution of the sparse space [G]. For a cube size of $(2^{10})^3$, the depth is 10 [G].
- Fill factor: The method is efficient for sparse data, such as a scene that is approximately 20% full [S1, unofficial].

**Edge cases and pitfalls:**
- Accessing voxel data requires cross-referencing the linear tree array with the second data texture [S1, unofficial].
- Inner nodes are eliminated from the primary storage, so spatial queries must navigate directly to leaf nodes [S1, unofficial].
- Precision issues may arise if Morton codes exceed integer limits for large coordinate spaces [G].

**Pseudocode:**
```python
def compute_morton_code(x, y, z):
    """
    Computes the Morton code (Z-order curve index) for a 3D point.
    Assumes x, y, z are non-negative integers.
    Standard bit-interleaving algorithm [G].
    """
    code = 0
    for i in range(32):  # Assuming 32-bit coordinates
        code |= ((x >> i) & 1) << (3 * i)
        code |= ((y >> i) & 1) << (3 * i + 1)
        code |= ((z >> i) & 1) << (3 * i + 2)
    return code

def build_linear_octree(leaf_nodes):
    """
    Builds a linear octree from a list of leaf nodes.
    leaf_nodes: List of tuples (x, y, z, data_id)
    Returns: Sorted list of (morton_code, data_id)
    """
    nodes_with_morton = []
    for x, y, z, data_id in leaf_nodes:
        morton = compute_morton_code(x, y, z)
        nodes_with_morton.append((morton, data_id))
    
    nodes_with_morton.sort(key=lambda item: item[0])
    return nodes_with_morton

def query_voxel(morton_code, linear_tree_array, data_texture):
    """
    Queries voxel data using the linear octree.
    morton_code: The Morton code of the target voxel.
    linear_tree_array: Sorted list of (morton_code, data_id).
    data_texture: Secondary storage for voxel data.
    Returns: Voxel data or None if not found.
    """
    left, right = 0, len(linear_tree_array) - 1
    while left <= right:
        mid = (left + right) // 2
        current_morton, data_id = linear_tree_array[mid]
        if current_morton == morton_code:
            return data_texture[data_id]
        elif current_morton < morton_code:
            left = mid + 1
        else:
            right = mid - 1
    return None
```
## Subtopics

### [Linear Octree Hashing](11794-linear-octree-hashing.md)
A variant that uses hashing instead of binary search for lookups, trading memory for speed. Choose when random access speed is critical and memory is abundant.

## Operating characteristics
- **Time Complexity:** Building the linear array requires $O(N \log N)$ sorting, where $N$ is the number of leaves [G]. Querying requires $O(\log N)$ binary search [G].
- **Memory Complexity:** $O(N)$ for the linear array, plus $O(D)$ for the data texture, where $D$ is the number of unique data entries [S1, unofficial].
- **Performance:** Efficient for raycasting/voxel applications where the tree can be precalculated and resources are limited (e.g., GPU textures) [S1, unofficial].
- **Strengths:** Cache-friendly linear layout, easy implementation in HLSL [S1, unofficial].
- **Limitations:** Requires precalculation, necessitates secondary data texture access [S1, unofficial].
- **When to use:** Sparse voxel rendering with static geometry, GPU-based raycasting [S1, unofficial].
- **When not to use:** Dynamic scenes requiring frequent insertions/deletions [S1, unofficial].
## Background
Originated from discussions on efficient sparse octree storage for GPU-based raycasting [S1, unofficial]. The method leverages the Z-order curve (Morton curve) to spatially sort data, a technique common in spatial indexing [S1, unofficial].
