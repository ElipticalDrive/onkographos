# Linear Octree Hashing
Also called: Gargantini's linear octree, Sorted leaf array lookup

## Overview
Linear Octree Hashing is a pointerless sparse octree storage method where only leaf nodes are stored in a contiguous memory array sorted by their Morton (Z-order) code [S1, unofficial]. It solves the problem of memory overhead in traditional octrees by eliminating interior nodes and pointers, replacing tree traversal with a binary search on the sorted leaf array [S1, unofficial]. It differs from its parent [Linear Octree with Z-order curve (Morton tree)](7054-linear-octree-with-z-order-curve-morton-tree.md) by explicitly sorting the leaves to enable binary search, whereas the Morton tree typically relies on the implicit ordering of the linear array for direct indexing or simpler traversal [S1, unofficial].

## How it works
**Inputs:** A set of non-empty leaf nodes from a sparse octree, each defined by its 3D spatial coordinates $(x, y, z)$ and associated data.
**Outputs:** A contiguous array of leaf nodes sorted by their Morton code.

**Data Structures:**
*   **Leaf Node:** A struct containing:
    *   `morton_code`: An integer representing the Z-order curve index of the leaf's position.
    *   `data`: The volumetric value or metadata associated with the leaf.
*   **Storage:** A single dynamic array (or vector) of `Leaf Node` structs.

**Steps:**
1.  **Generate Morton Codes:** For each leaf node at position $(x, y, z)$, compute its Morton code $M$. The Morton code interleaves the bits of the coordinates:
    $$ M = \text{interleave}(x, y, z) $$
    Where $\text{interleave}$ packs the $i$-th bit of $x$, $y$, and $z$ into the $3i$-th, $3i+1$-th, and $3i+2$-th bits of $M$, respectively [S1, unofficial].
2.  **Store Leaves:** Create a list of leaf nodes, each containing its computed $M$ and its associated data.
3.  **Sort:** Sort the list of leaf nodes in ascending order based on $M$ [S1, unofficial].
4.  **Lookup (Point Location):** To find the leaf node containing a query point $P$:
    *   Compute the Morton code $M_P$ for $P$.
    *   Perform a binary search on the sorted array for $M_P$ [S1, unofficial].
    *   If found, return the associated data. If not found, the point lies in an empty region (or requires further subdivision if the tree is dynamic) [S1, unofficial].

**Parameters:**
*   **Bit Depth:** The number of bits used for coordinates determines the resolution. Not given in the sources.
*   **Array Size:** $L$, the number of leaf nodes.

**Edge Cases and Pitfalls:**
*   **Interior Node Absence:** The structure does not store interior nodes. Applications requiring traversal of the full tree hierarchy or neighbor finding without additional data structures are unsuitable [S1, unofficial].
*   **Precision:** Morton code computation must handle coordinate quantization correctly to ensure consistent ordering [G].
*   **Dynamic Updates:** Insertion or deletion requires re-sorting or maintaining a sorted structure, which can be costly compared to pointer-based trees [G].

## Subtopics

### [Linear Level Octree (LLO)](16467-linear-level-octree-llo.md)
A hierarchical data structure for volume data that stores only leaf nodes, implicitly encoding location, size, and path from root to nodes to reduce memory and processing cost. It differs by explicitly encoding the level/size information, whereas Linear Octree Hashing relies solely on Morton code sorting for location. Choose LLO when size information is critical for rendering or culling.

## Operating characteristics
*   **Time Complexity:** Node lookup is $O(\log_2(L))$ where $L$ is the number of leaf nodes [S1, unofficial].
*   **Memory Complexity:** $O(L)$, storing only leaf nodes. No memory is wasted on interior nodes or pointers [S1, unofficial].
*   **Performance:** Generally slower to hash than pointer octrees ($O(\log_8(N))$ vs $O(\log_2(L))$) except in highly vertical trees with few leaf nodes relative to interior nodes [S1, unofficial].
*   **Strengths:** Minimal memory footprint; no pointer overhead; cache-friendly contiguous storage [S1, unofficial].
*   **Limitations:** No support for interior node traversal; neighbor finding is difficult without additional data; dynamic updates are expensive [S1, unofficial].
*   **Use Cases:** Applications where storage is of utmost importance and only leaf node access is required [S1, unofficial].

## Background
The linear octree was originally proposed by Gargantini for quadtrees [S1, unofficial]. It was later adapted for octrees using Morton's interleaved base-8 code [S1, unofficial]. While not directly applied to volume rendering in the surveyed literature, it is considered an intriguing structure for its potential compression abilities in adaptive octree methods on volume data [S1, unofficial].
