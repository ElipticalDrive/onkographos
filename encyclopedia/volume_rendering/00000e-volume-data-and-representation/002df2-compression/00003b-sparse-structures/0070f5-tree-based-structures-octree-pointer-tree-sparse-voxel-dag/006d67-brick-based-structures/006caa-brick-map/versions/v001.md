# Brick Map

Also called: Sparse Voxel Octree alternative, Two-level sparse voxel grid

## Overview
A Brick Map is a two-level sparse spatial data structure for ray tracing that combines a low-resolution full voxel grid with high-resolution sparse 'bricks' to store triangle indices, avoiding the traversal complexity of BVHs and SVOs while skipping free space [S1, unofficial]. It is designed specifically for real-time ray tracing of secondary rays (reflections/refractions) starting from surfaces, supporting dynamic content and allowing ray bouncing with controlled execution time [S1, unofficial]. Unlike SVOs which require stack-based or recursive traversal, the Brick Map allows hard-coded, branch-free traversal by always reading the low-resolution cell to determine if a brick is present, resulting in low shader divergence [S1, unofficial].

## How it works
**Inputs:** A structured buffer containing all scene triangles (captured from skins, deformers, instancing, and generated geometry like marching cubes) [S1, unofficial].
**Outputs:** A low-resolution volume texture (grid) and a structured buffer (bricks) containing triangle linked lists.

**Data Structures:**
1.  **Low-Resolution Grid:** A volume texture where each cell contains a `uint` index. The index is either 0 (empty) or points to a brick in the structured buffer [S1, unofficial].
2.  **Brick Buffer:** A structured buffer (or volume texture) containing `uint` values that point to triangle linked lists. Each brick covers a fixed region of the high-resolution space (e.g., $8 \times 8 \times 8$ cells) [S1, unofficial].
3.  **Triangle Storage:** Linked lists of triangle indices stored per cell within the bricks [S1, unofficial].

**Parameters:**
*   Low-resolution grid size: Typically $64 \times 64 \times 64$ cells [S1, unofficial].
*   Brick dimensions: Typically $8 \times 8 \times 8$ cells per brick [S1, unofficial].
*   Effective resolution: Low-res size multiplied by brick size (e.g., $64 \times 4 = 256$, resulting in $256 \times 256 \times 256$ effective resolution) [S1, unofficial].
*   Brick buffer allocation: Preallocated based on expected fill rate, typically 10-20% of the low-res grid cells [S1, unofficial].
*   Coordinate space: Can be generated in camera space, world space, or a moving grid [S1, unofficial].

**Build Steps:**
1.  **Geometry Capture:** Run a first pass to capture all scene triangles into a single structured buffer. This handles skins, deformers, instancing, and generated geometry. Time: ~0.3 ms per frame [S1, unofficial].
2.  **Mark Low-Res Grid:** Render geometry to the low-resolution voxel grid to mark which cells are filled. This is done using a geometry shader and pixel shader combination. The geometry shader expands triangles to handle small/perpendicular triangles that might otherwise be skipped by rasterization. The pixel shader performs a distance-from-triangle test [S1, unofficial].
3.  **Allocate Bricks:** Post-process the low-res grid to allocate bricks for filled cells and store brick indices in the volume texture. The brick buffer is preallocated based on expected fill (10-20%) [S1, unofficial].
4.  **Fill High-Res Grid:** Render geometry to the high-resolution grid (low-res size $\times$ brick size). For each cell, read the low-res grid to find the brick, locate the position in the brick, and atomically append the triangle index to the cell's linked list. To reduce atomic contention, this can be split into 2 passes over the geometry instead of 1 [S1, unofficial]. The rasterizer handles 2D components (X, Y) while a loop in the pixel shader handles the Z depth [S1, unofficial].

**Ray Traversal Steps:**
1.  **Step Low-Res:** Step along the low-resolution voxel grid using DDA [S1, unofficial].
2.  **Check Empty:** If the current low-res cell is empty, continue stepping. If filled, read the brick index [S1, unofficial].
3.  **Step High-Res:** Look up the brick data and step along the high-resolution brick cells. Always read the low-res cell at every iteration to determine if a brick is present (this allows consistent code paths) [S1, unofficial].
4.  **Intersect:** When a brick cell contains triangles, trace against the linked list of triangles in that cell [S1, unofficial].
5.  **Bend/Bounce:** To bounce a ray, change the ray direction and DDA coefficients, then continue stepping through the same two-level structure. The shader execution loop can be limited by the number of cells marched rather than the number of bounces to prevent infinite loops from quick local bounces [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Build time is 2-10 ms per frame for scenes in '5 Faces', depending on triangle count and contention [S1, unofficial]. Geometry capture is ~0.3 ms per frame [S1, unofficial].
*   **Memory Complexity:** Memory usage is proportional to the number of filled low-res cells times the brick size. High-resolution grids consume significant VRAM; running out of VRAM can occur if managing different allocation sizes dynamically [S1, unofficial].
*   **Strengths:** Simple and fast to build; much more memory-efficient than a regular voxel grid for high resolution; skips free space; efficient shader with no complex tree traversal and little divergence; easy ray bending; supports dynamic content; finds exact leaf cell in 2 steps [S1, unofficial].
*   **Limitations:** Hard limited on scene complexity (triangles per cell); atomic contention during build; small/perpendicular triangles may be skipped without special handling; not suitable for primary camera rays or millions of triangles [S1, unofficial].
*   **When to use:** Real-time ray tracing of secondary rays (reflections/refractions) from surfaces; dynamic scenes; solid geometry; when low divergence and controlled execution time are critical [S1, unofficial].
*   **When not to use:** Primary camera rays; scenes with millions of triangles; when hardware BVH/SVO support is available and preferred [S1, unofficial].

## Background
The Brick Map was introduced by the author of the "direct to video" blog in 2013 for use in the '5 Faces' demo and production settings [S1, unofficial]. It was designed for a real-time raytracer handling secondary rays, where rays start on surfaces and need to bounce multiple times [S1, unofficial]. The structure is also used by Pixar's RenderMan for Global Illumination (GI) and by Marcos Fajardo in the Arnold renderer (using uniform grids as a 2-level hierarchy of ugrids) [S1, unofficial]. The author notes that Brick Maps are tailored to specific use cases (secondary rays, dynamic, solid, low divergence) and are not expected to replace structures used in Octane or Optix [S1, unofficial].
