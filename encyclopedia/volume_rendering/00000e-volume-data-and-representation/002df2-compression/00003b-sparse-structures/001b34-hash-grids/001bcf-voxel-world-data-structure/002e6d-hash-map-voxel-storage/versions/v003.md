# Hash-Map Voxel Storage

Also called: Sparse Voxel Storage, VoxelData

## Overview
Hash-Map Voxel Storage is a sparse voxel representation that maps 3D coordinates to voxel attributes using a hash table, enabling efficient storage of large, sparse volumetric datasets without allocating memory for empty space [S1, unofficial]. It differs from its parent [Voxel World Data Structure](1101-voxel-world-data-structure.md) by storing full voxel data (such as color) rather than just existence flags, and from [Multi-type Voxel Storage](1104-multi-type-voxel-storage.md) by using a single hash map for uniform data access rather than type-specific containers.

## How it works
**Inputs:** A collection of voxels, each defined by integer coordinates $(x, y, z)$ and an associated color value.
**Outputs:** A `VoxelData` structure containing a hash map of packed voxel data and grid bounds.

**Data Structures:**
The primary structure is `VoxelData`, which contains:
- `datas`: A hash map (dictionary) mapping a packed 32-bit integer key to a 32-bit integer value.
- `count`: An integer representing the number of stored voxels.
- `width`, `height`, `depth`: Integers tracking the bounding box dimensions of the stored voxels.

**Packing and Key Generation:**
1.  **Coordinate Key:** The 3D integer coordinates $(x, y, z)$ are packed into a single 32-bit integer key. The exact bit-packing scheme is not specified in the sources, but it must uniquely map the 3D vector to a 32-bit integer [S1, unofficial].
2.  **Value Packing:** The voxel color is packed into a 32-bit integer in BGR + Alpha format [S1, unofficial].

**Algorithm:**
1.  Initialize an empty `VoxelData` structure.
2.  Iterate through the input voxel list.
3.  For each voxel, compute the bounding box dimensions ($width, height, depth$) by tracking the maximum coordinate values encountered [S1, unofficial].
4.  Pack the voxel's color into a 32-bit integer.
5.  Pack the voxel's $(x, y, z)$ coordinates into a 32-bit integer key.
6.  Insert the packed color into the `datas` hash map using the packed coordinate key.
7.  Update `count` to reflect the number of inserted voxels.

**Edge Cases and Pitfalls:**
-   **Coordinate Range:** Packing 3D coordinates into 32 bits limits the addressable space. If coordinates exceed the capacity of the packing scheme, collisions or overflow will occur [S1, unofficial].
-   **Hash Collisions:** If the coordinate packing is a hash rather than a direct mapping, collisions must be handled by the underlying hash map implementation [S1, unofficial].

## Subtopics

### [Voxel Hash Chunk Map](12207-voxel-hash-chunk-map.md)
The Voxel Hash Chunk Map (voxlvoxl) is a sparse 3D point cloud representation that partitions space into independent, hash-addressed cubic chunks to mitigate memory overhead for large-scale maps. Unlike sibling structures like Rolling Bonxai that enforce a fixed 3x3x3 active window, voxlvoxl uses a hash function for chunk indexing, allowing unlimited degrees of freedom for dynamic summoning and dismissing of regions.

### [Voxel Hash for Gaussian Splat Indexing](12601-voxel-hash-for-gaussian-splat-indexing.md)
Voxel Hash is a sparse data structure that maps each 3D Gaussian Splat to the voxel cell containing its center $\mu$, enabling efficient lookup of splats within specific voxel regions for operations like carving or stacking. It differs from sibling structures by maintaining a direct bidirectional mapping between splat indices and voxel keys, allowing for rapid identification of splats to remove or modify within a target voxel.

### Online Random Access
**Definition:** A variant supporting random access to values directly from in-memory NeuralVDB data without full reconstruction, balancing memory footprint and access time for real-time applications [S2].

**Steps:**
1.  Use standard accelerated random access techniques (level {3, 2, 1}) to determine if a query point maps to a tile or a voxel (level 0) [S2].
2.  If the query maps to a tile, return the value explicitly encoded in the standard VDB structure [S2].
3.  If the query maps to a voxel (level 0), predict the voxel value using the regressor [S2].
4.  This configuration, denoted as [Hash, 5, 4, NN(3)], can be trivially reconstructed from [Hash, 5, NN(4), NN(3)] by leaving the voxel regressor unchanged, acting as a pre-cached representation [S2].

**Parameters:**
-   Configuration: [Hash, 5, 4, NN(3)] [S2].

**Comparison:**
-   Performance characteristics are the same as standard VDB tree except leaf values require additional regression [S2].
-   Memory footprint is an order of magnitude smaller than [Hash, 5, 4, 3] [S2].

### Voxel Table Registry
**Definition:** A central voxel registry providing O(1) lookup by ID and name. It manages voxel definitions, supporting loading from a ScriptableObject database or falling back to hardcoded definitions. ID 0 is reserved for air/null [S3, unofficial].

**Steps:**
1.  **LoadFromDatabase:** Convert the database to runtime definitions. Create the name-to-ID map by iterating through `_runtimeVoxels`, using index $i + 1$ as the ID. Skip voxels with null/empty `InternalName` [S3, unofficial].

**Parameters:**
-   `DATABASE_RESOURCE_PATH`: The path to the default database asset in the Resources folder. Value: "VoxelDatabase" [S3, unofficial].

**Layout:**
-   `_runtimeVoxels`: A static array of `VoxelDefinition` objects, indexed by $(id - 1)$ [S3, unofficial].
-   `_nameIdMap`: A static `Dictionary<string, uint>` mapping internal voxel names to their IDs [S3, unofficial].

## Operating characteristics
-   **Time Complexity:** Lookup and insertion are $O(1)$ on average for hash map operations [S1, unofficial]. Bounding box updates are $O(1)$ per voxel [S1, unofficial].
-   **Memory Complexity:** Memory usage is proportional to the number of non-empty voxels, $O(N)$, where $N$ is the count of stored voxels [S1, unofficial]. This is significantly more efficient than dense voxel grids for sparse data.
-   **Strengths:** Efficient storage for sparse volumes; simple implementation; supports direct random access to voxel data via hash keys [S1, unofficial].
-   **Limitations:** Limited by 32-bit coordinate packing; no inherent spatial locality optimization beyond the hash map; collision handling depends on the specific hash implementation [S1, unofficial].
-   **When to use:** Suitable for applications requiring sparse voxel storage with direct coordinate-based access, such as voxel-based games or simulations with large empty spaces [S1, unofficial].
-   **When not to use:** Not suitable for dense volumes or when spatial coherence is required for efficient traversal (e.g., ray marching through dense media) without additional acceleration structures [S1, unofficial].

## Background
The Hash-Map Voxel Storage structure is described in the context of voxel-based game development and simulation, specifically within the `AfterHumanDeclined` project [S1, unofficial]. It builds upon the concept of storing voxel existence in a HashSet, extending it to store full voxel data. The NeuralVDB variant (Online Random Access) was introduced by [S2] to enable real-time access to sparse volumetric data represented by hierarchical neural networks. The Voxel Table Registry is part of the `vektor-voxels` project [S3, unofficial], providing a centralized management system for voxel types in Unity-based applications.
