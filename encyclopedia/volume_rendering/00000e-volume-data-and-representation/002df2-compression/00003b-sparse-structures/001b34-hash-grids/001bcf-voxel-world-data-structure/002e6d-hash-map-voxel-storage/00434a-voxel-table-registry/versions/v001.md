# Voxel Table Registry

Also called: Voxel Registry, VoxelTable

## Overview
The Voxel Table Registry is a centralized lookup structure that provides $O(1)$ access to voxel definitions by both unique identifier and internal name. It solves the problem of redundant disk I/O and inconsistent state by maintaining a static, in-memory map of voxel types, serving as the authoritative source for chunk generation and rendering logic. It differs from sibling hash-grid storage methods by focusing on semantic definition management rather than spatial coordinate mapping.

## How it works
The registry operates as a static singleton or global state manager. It maps integer IDs to voxel properties and string names to integer IDs.

**Inputs and Outputs**
- **Input**: A serialized database asset (e.g., JSON or ScriptableObject) containing voxel definitions.
- **Output**: An in-memory structure allowing constant-time retrieval of voxel metadata given an ID or name.

**Data Structures**
The registry maintains two primary static data structures:
1.  `_runtimeVoxels`: A static array of `VoxelDefinition` objects. The array is indexed such that the element at index $i$ corresponds to voxel ID $i + 1$.
2.  `_nameIdMap`: A static hash map (Dictionary) mapping `string` (internal voxel names) to `uint` (voxel IDs).

**Layout Details**
-   **ID 0**: Reserved for "air" or "null" voxels. It is implicitly defined and does not require an entry in the database or runtime array.
-   **Indexing**: If a voxel has ID $k$ (where $k > 0$), it is stored at `_runtimeVoxels[k - 1]`.

**Initialization Steps**
1.  Load the database resource from the path specified by `DATABASE_RESOURCE_PATH`. The default value is `"VoxelDatabase"` located in the `Resources` folder [S1, unofficial].
2.  Iterate through the loaded database entries.
3.  For each entry with a non-null and non-empty `InternalName`:
    -   Assign the next available integer ID starting from 1.
    -   Create a `VoxelDefinition` object.
    -   Store the object in `_runtimeVoxels` at index `ID - 1`.
    -   Insert the mapping `InternalName -> ID` into `_nameIdMap`.
4.  Skip any entries with null or empty names to prevent map corruption [S1, unofficial].

**Pseudocode**
```python
class VoxelRegistry:
    # Static members
    _runtimeVoxels: list[VoxelDefinition] = []
    _nameIdMap: dict[str, uint] = {}
    DATABASE_RESOURCE_PATH: str = "VoxelDatabase"

    @staticmethod
    def initialize():
        """Load voxel definitions from the database asset."""
        # Load database asset from Resources/DATABASE_RESOURCE_PATH [S1, unofficial]
        database = load_asset(VoxelRegistry.DATABASE_RESOURCE_PATH)
        
        current_id = 1
        
        # Iterate through database entries
        for entry in database.entries:
            name = entry.InternalName
            
            # Skip voxels with null or empty internal names [S1, unofficial]
            if name is None or name == "":
                continue
            
            # Create definition object
            definition = VoxelDefinition(
                id=current_id,
                name=name,
                properties=entry.properties
            )
            
            # Store in array at index id - 1
            # Ensure array is large enough or append
            while len(VoxelRegistry._runtimeVoxels) < current_id:
                VoxelRegistry._runtimeVoxels.append(None)
            
            VoxelRegistry._runtimeVoxels[current_id - 1] = definition
            
            # Map name to ID
            VoxelRegistry._nameIdMap[name] = current_id
            
            current_id += 1

    @staticmethod
    def get_definition_by_id(voxel_id: uint) -> VoxelDefinition:
        """Retrieve voxel definition by ID. O(1) access."""
        if voxel_id == 0:
            return None # Air/Null
        if voxel_id <= 0 or voxel_id > len(VoxelRegistry._runtimeVoxels):
            raise IndexError(f"Invalid voxel ID: {voxel_id}")
        return VoxelRegistry._runtimeVoxels[voxel_id - 1]

    @staticmethod
    def get_id_by_name(name: str) -> uint:
        """Retrieve voxel ID by internal name. O(1) access."""
        if name in VoxelRegistry._nameIdMap:
            return VoxelRegistry._nameIdMap[name]
        raise KeyError(f"Voxel name not found: {name}")
```

**Parameters**
-   `DATABASE_RESOURCE_PATH`: String path to the default database asset. Default: `"VoxelDatabase"` [S1, unofficial].

**Edge Cases and Pitfalls**
-   **ID 0 Handling**: ID 0 is reserved for air. The registry must ensure no database entry is assigned ID 0 [S1, unofficial].
-   **Empty Names**: Voxels with empty `InternalName` fields must be skipped during initialization to maintain map integrity [S1, unofficial].
-   **Index Out of Bounds**: Accessing `_runtimeVoxels` requires careful boundary checking since the array is 0-indexed but IDs start at 1.

## Subtopics

### Voxel Registry Caching
VoxelRegistry definitions are loaded once at initialization to prevent redundant disk access during chunk generation. This caching strategy minimizes I/O overhead, ensuring that procedural chunk regeneration (which bypasses disk saving) relies solely on the in-memory registry [S2, unofficial].

## Operating characteristics
-   **Time Complexity**: Lookup by ID or name is $O(1)$ due to array indexing and hash map usage. Initialization is $O(N)$ where $N$ is the number of voxel types.
-   **Memory Complexity**: $O(N)$ for storing voxel definitions and the name-to-ID map.
-   **Strengths**: Fast lookup, centralized management of voxel semantics, reduced I/O latency during runtime generation.
-   **Limitations**: Static nature means dynamic addition of voxel types at runtime requires reloading or complex extension logic. Memory usage scales with the number of unique voxel types, not world size.
-   **When to use**: When voxel types are fixed or rarely change, and fast lookup is critical for procedural generation.
-   **When not to use**: When voxel types are highly dynamic or user-generated in real-time without restart.

## Background
The Voxel Table Registry originates from the VektorKnight/vektor-voxels project, an unofficial implementation of voxel-based world generation and rendering [S1, unofficial]. It is designed to support procedural pipelines where chunks are regenerated from seeds rather than saved to disk, requiring efficient access to voxel definitions [S2, unofficial]. The caching mechanism was introduced to optimize performance by avoiding repeated disk reads during chunk generation [S2, unofficial].
