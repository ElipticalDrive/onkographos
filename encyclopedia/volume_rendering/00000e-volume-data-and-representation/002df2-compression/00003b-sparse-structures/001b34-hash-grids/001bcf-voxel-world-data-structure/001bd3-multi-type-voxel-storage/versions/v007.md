# Multi-type Voxel Storage

Also called: HashMap-based Voxel Storage, VoxelKind Enum Storage

## Overview
Multi-type Voxel Storage is a sparse voxel data structure that maps 3D integer coordinates to discrete material identifiers (kinds) using a hash map, enabling the representation of heterogeneous voxel worlds where different blocks have distinct properties [S1, unofficial]. It sets itself apart from its sibling [Hash-Map Voxel Storage](5782-hash-map-voxel-storage.md) by explicitly associating a `VoxelKind` enum with each occupied entry rather than storing a single generic type or binary existence flag, and from [Brick-based Sparse Voxel Lookup with Open-Addressing Hash](2587-brick-based-sparse-voxel-lookup-with-open-addressing-hash.md) by using a flat hash map per chunk rather than a brick-based open-addressing scheme [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A world state containing a collection of chunks, a 3D integer position (`IVec3`) in world space, and an optional `VoxelKind` (or `none` for air).
*   **Output:** Updated world state with the voxel kind set or removed at the specified position, and the associated chunk marked for mesh regeneration.

**Data Structures:**
1.  **Chunk:**
    *   `position`: `IVec3` representing the chunk's coordinate in chunk-space (each chunk is $32 \times 32 \times 32$ voxels).
    *   `voxels`: `HashMap<IVec3, VoxelKind>`. Maps local 3D integer coordinates (relative to the chunk origin) to the material type. The absence of a key implies air.
    *   `mesh`: Optional mesh object. `none` indicates the mesh is invalid and needs regeneration.
2.  **VoxelKind:** An enumeration defining material types (e.g., `Dirt`, `Stone`, `Air`).
3.  **World:** A collection (e.g., `HashMap<IVec3, Chunk>`) mapping chunk positions to `Chunk` objects.

**Algorithm Steps:**

1.  **Chunk Localization:** Given a world position $P$, calculate the chunk position $C$ and the local position $L$ within that chunk:
    $$ C = \text{div\_euclid}(P, 32) $$
    $$ L = \text{rem\_euclid}(P, 32) $$
    Where $\text{div\_euclid}$ and $\text{rem\_euclid}$ are Euclidean division and remainder operations, ensuring correct handling of negative coordinates.

2.  **Chunk Retrieval/Creation:** Retrieve the `Chunk` at $C$ from the world. If it does not exist, create it.
    *   Initialize `Chunk.voxels` as an empty hash map.
    *   **Initial Generation:** If the chunk is being created for the first time, populate it based on world geometry rules:
        *   Iterate $x, y, z$ from $0$ to $31$.
        *   Calculate world position $W = C \times 32 + (x, y, z)$.
        *   If $W.y == 0$, insert $(x, y, z)$ with `VoxelKind::Dirt`.
        *   If $W.y < 0$, insert $(x, y, z)$ with `VoxelKind::Stone`.
        *   (Other rules may apply, such as air above $y=0$).

3.  **Voxel Update:**
    *   If the requested `kind` is `none` (air):
        *   Remove the key $L$ from `Chunk.voxels`.
    *   Otherwise:
        *   Insert the key $L$ with value `kind` into `Chunk.voxels`.

4.  **Invalidation:** Set `Chunk.mesh` to `none` to signal that the visual representation is out of date.

**Pseudocode:**

```python
def set_voxel(world: World, position: IVec3, kind: Optional[VoxelKind]):
    # 1. Calculate chunk and local coordinates
    chunk_position = position.div_euclid(32)
    local_position = position.rem_euclid(32)

    # 2. Get or create chunk
    chunk = get_or_create_chunk(world, chunk_position)

    # 3. Invalidate mesh
    chunk.mesh = None

    # 4. Update voxel data
    if kind is None:
        # Remove voxel if it exists
        if local_position in chunk.voxels:
            del chunk.voxels[local_position]
    else:
        # Insert or update voxel
        chunk.voxels[local_position] = kind

def get_or_create_chunk(world: World, chunk_position: IVec3) -> Chunk:
    if chunk_position not in world.chunks:
        chunk = Chunk()
        chunk.position = chunk_position
        chunk.voxels = {}
        
        # Initial generation logic for new chunks
        for z in range(32):
            for y in range(32):
                for x in range(32):
                    offset = IVec3(x, y, z)
                    world_voxel_position = chunk_position * 32 + offset
                    
                    if world_voxel_position.y == 0:
                        chunk.voxels[offset] = VoxelKind.Dirt
                    elif world_voxel_position.y < 0:
                        chunk.voxels[offset] = VoxelKind.Stone
                    # Else: Air (not stored in hash map)
        
        world.chunks[chunk_position] = chunk
    
    return world.chunks[chunk_position]
```

**Parameters and Edge Cases:**
*   **Chunk Size:** Fixed at $32^3$ voxels.
*   **Coordinate System:** Uses Euclidean division/remainder to handle negative world coordinates correctly, ensuring consistent chunk mapping for negative indices [S1, unofficial].
*   **Air Representation:** Air is implicit. Only non-air voxels are stored in the hash map. This optimizes memory for empty space but requires checking for key existence during lookups [S1, unofficial].
*   **Mesh Invalidation:** Every modification to a voxel invalidates the chunk's mesh. Frequent updates can lead to performance bottlenecks if mesh generation is expensive [S1, unofficial].

## Subtopics

### [Typed Voxels](1399-typed-voxels.md)
Extends this structure by enforcing a strict enumeration-based type system for voxel content, allowing distinct material properties beyond simple existence.

### [Voxel Hashing](2702-voxel-hashing.md)
Uses a flat spatial hash table for O(1) block access, prioritizing GPU parallelism and constant-time lookup over the chunk-based typed array indexing of this method.

### [Adaptive Bit-Packed Voxel Array](4986-adaptive-bit-packed-voxel-array.md)
Implements adaptive bit-packing within a single section to optimize memory for homogeneous regions, differing from this method's direct hash map storage.

## Operating characteristics
*   **Time Complexity:** Lookup and insertion are $O(1)$ average case due to hash map operations. Chunk localization is $O(1)$. Mesh regeneration is $O(N)$ where $N$ is the number of voxels in the chunk.
*   **Memory Complexity:** Proportional to the number of non-air voxels. Each entry stores a 3D integer key and an enum value, plus hash map overhead. Empty space is not stored.
*   **Strengths:** Simple implementation; efficient storage for sparse worlds; easy to add new voxel types via enum extension; supports arbitrary chunk sizes.
*   **Limitations:** Hash map overhead can be significant for dense voxels; frequent voxel updates cause frequent mesh invalidations; not optimized for GPU direct access without additional data restructuring.
*   **When to Use:** Ideal for voxel engines where world sparsity is high, and dynamic modification of voxel types is frequent. Not suitable for highly dense, static volumes where contiguous arrays or octrees might be more efficient.

## Background
This method originates from practical implementations of voxel engines, specifically described in "Make yourself a Voxel Engine THIS weekend" [S1, unofficial]. It builds upon the concept of storing voxel existence in a `HashSet` of integer-based 3D vectors [Parent](1101-voxel-world-data-structure.md) by adding a `VoxelKind` enum to distinguish between different material types, allowing for heterogeneous voxel worlds [S1, unofficial].
