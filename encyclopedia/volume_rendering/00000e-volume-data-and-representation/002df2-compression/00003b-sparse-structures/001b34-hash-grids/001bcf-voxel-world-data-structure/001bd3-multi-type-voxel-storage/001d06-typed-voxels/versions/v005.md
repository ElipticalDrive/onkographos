# Typed Voxels

Also called: Voxel Kind Storage, Material-Tagged Voxels

## Overview
Typed Voxels extend sparse voxel storage by associating a discrete material identifier (type) with each occupied voxel, allowing a world to distinguish between different material kinds (e.g., Dirt, Stone) rather than treating all voxels as identical [S1, unofficial]. This builds on [Multi-type Voxel Storage](1104-multi-type-voxel-storage.md) by replacing the binary existence check with a typed lookup, enabling material-specific rendering or physics. It differs from [Adaptive Bit-Packed Voxel Array](4986-adaptive-bit-packed-voxel-array.md) by using a hash map for sparse access rather than bit-packing dense or semi-dense regions, trading memory efficiency for flexible type association [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A chunk coordinate system (e.g., chunk position `chunk_pos`), a list of voxel local coordinates `IVec3`, and a set of material definitions.
- Output: A chunk data structure capable of storing and retrieving voxel types, and a mesh or data structure ready for material-aware processing.

**Data Structures:**
1.  **VoxelKind Enum:** A simple enumeration defining the available material types.
    ```cpp
    enum VoxelKind {
        Dirt,
        Stone
        // ... other types
    };
    ```
2.  **Chunk Storage:** The chunk's voxel storage changes from a set of coordinates to a hash map mapping local coordinates to types.
    ```cpp
    struct Chunk {
        // Replaces HashSet<IVec3>
        std::unordered_map<IVec3, VoxelKind> voxels; 
        // ... other chunk data (mesh, etc.)
    };
    ```

**Steps:**
1.  **Initialize VoxelKind:** Define the enumeration of supported material types [S1, unofficial].
2.  **Update Chunk Storage:** Replace the existing `HashSet<IVec3>` (or similar binary existence structure) in the `Chunk` struct with a `HashMap<IVec3, VoxelKind>` [S1, unofficial].
3.  **Insert Voxel:** When adding a voxel at local coordinate `p` with material `m`:
    -   Compute the chunk offset if necessary (e.g., `offset = chunk_pos * 32` for 32-bit chunks, though this is specific to the rendering offset, not the map key) [S1, unofficial].
    -   Insert into the map: `chunk.voxels[p] = m`.
4.  **Query Voxel:** To retrieve the type at `p`:
    -   Check if `p` exists in `chunk.voxels`.
    -   If present, return `chunk.voxels[p]`.
    -   If absent, return a default "empty" or "air" type.

**Parameters:**
-   **Chunk Size:** The example uses a 32-unit chunk size [S1, unofficial].
-   **Map Type:** `HashMap` (or `unordered_map` in C++/Python-like pseudocode) is required to support key-value pairs [S1, unofficial].

**Edge Cases and Pitfalls:**
-   **Empty Voxel Handling:** The map only stores occupied voxels. Queries for non-existent keys must return a consistent "empty" type to distinguish from stored materials [S1, unofficial].
-   **Hash Collisions:** Standard hash map collisions are handled by the underlying container implementation [G].
-   **Serialization:** Serializing a `HashMap` requires iterating over all entries, which may be slower than a dense array if the chunk is nearly full [G].

## Subtopics

### Voxel Flag System & Filled State Logic
This variant extends typed voxels with a 5-bit flag system to track geometric and topological state (e.g., whether a voxel is filled, inside, surface, solid, or clipped) [S2, unofficial]. It is chosen when the rendering or physics engine requires explicit state propagation for culling or collision detection, rather than just material identity. It differs from basic typed voxels by adding metadata bits to each voxel [S2, unofficial].

-   **Layout:**
    -   `VoxelFlagsEnum`: A 5-bit bitmask.
        -   `FILLED = 0x01 << 0`
        -   `INSIDE = 0x01 << 1`
        -   `SURFACE = 0x01 << 2`
        -   `SOLID = 0x01 << 3`
        -   `CLIPPED = 0x01 << 4`
    -   `VoxelMeta`: Stores `VoxelIndex index_` and `VoxelFlags flags_` [S2, unofficial].
-   **Steps:**
    1.  **Initialize Flags:** `ClearFlags()` sets all flags to 0 and sets the `INSIDE` bit [S2, unofficial].
    2.  **Update Filled State:** `UpdateFilled()` computes the `FILLED` state:
        -   Set `FILLED` if `!Clipped() && (Solid() || (Surface() && Inside()))`.
        -   Otherwise, unset `FILLED` [S2, unofficial].
    3.  **Modify Flags:** Functions `SetInside()`, `UnsetInside()`, `SetSurface()`, `UnsetSurface()`, `SetSolid()`, `UnsetSolid()`, `SetClipped()`, and `UnsetClipped()` modify their respective bits and call `UpdateFilled()` to propagate state changes [S2, unofficial].

## Operating characteristics
-   **Time Complexity:** Lookup and insertion are $O(1)$ average case for hash maps, but $O(N)$ worst case due to collisions [G]. Iterating over all voxels for mesh generation is $O(V)$ where $V$ is the number of voxels in the chunk.
-   **Memory Complexity:** $O(V)$ where $V$ is the number of occupied voxels. Hash maps have higher overhead per entry than dense arrays or bit-packed structures due to hash table buckets and pointer storage [G].
-   **Performance:** Suitable for sparse worlds with diverse materials. Less memory-efficient than [Adaptive Bit-Packed Voxel Array](4986-adaptive-bit-packed-voxel-array.md) for dense or uniform regions [S1, unofficial].
-   **Strengths:** Flexible material assignment, easy to extend with new types, sparse storage.
-   **Limitations:** Higher memory overhead per voxel, potential hash map overhead, slower iteration than contiguous arrays.
-   **When to use:** When material diversity is high and the world is sparse.
-   **When not to use:** When memory is extremely constrained or the world is dense and uniform.

## Background
Typed voxels were popularized in indie voxel engine tutorials as a step beyond binary voxel worlds. The specific implementation using `HashMap<IVec3, VoxelKind>` was detailed in "Make yourself a Voxel Engine THIS weekend" [S1, unofficial]. The flag system variant was described in the `topskychen/voxelizer` repository [S2, unofficial].
