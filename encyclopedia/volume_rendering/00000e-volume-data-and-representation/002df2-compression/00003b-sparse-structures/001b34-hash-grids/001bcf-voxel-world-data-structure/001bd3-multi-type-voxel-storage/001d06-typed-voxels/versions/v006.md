# Typed Voxels


## Overview
Typed Voxels associate a discrete material identifier (type) with each occupied voxel to distinguish between different material kinds, such as Dirt or Stone [S1, unofficial]. This builds on [Multi-type Voxel Storage](1104-multi-type-voxel-storage.md) by replacing a binary existence check with a typed lookup [S1, unofficial]. It differs from [Adaptive Bit-Packed Voxel Array](4986-adaptive-bit-packed-voxel-array.md) by using a hash map for sparse access rather than bit-packing dense regions [S1, unofficial].

## How it works
**Inputs and Outputs:**
Not given in the sources.

**Data Structures:**
1. **VoxelKind Enum:** Defines supported material types (e.g., `Dirt`, `Stone`) [S1, unofficial].
2. **Chunk Storage:** The chunk's voxel storage uses a hash map mapping local 3D coordinates to types. Layout: `voxels: HashMap<IVec3, VoxelKind>` [S1, unofficial].

**Steps:**
1. Define the `VoxelKind` enumeration with supported material types [S1, unofficial].
2. Replace the chunk's voxel storage from a `HashSet<IVec3>` to a `HashMap<IVec3, VoxelKind>` [S1, unofficial].
3. Insert a voxel at local coordinate `p` with material `m` by assigning `chunk.voxels[p] = m` [S1, unofficial].
4. Query a voxel at `p` by checking map existence; return the stored type if present, or a default empty type if absent [S1, unofficial].

**Formulas:**
- Chunk rendering offset: `offset = chunk_pos * 32` [S1, unofficial].

**Parameters:**
- Chunk stride multiplier: 32 units per chunk position [S1, unofficial].
- Map type: Hash map supporting `IVec3` keys and `VoxelKind` values [S1, unofficial].

**Edge Cases and Pitfalls:**
- Empty voxels are not stored in the hash map; queries must return a consistent default type (e.g., air) for missing keys [S1, unofficial].
- Hash map overhead increases memory usage compared to dense arrays [G].
- Serialization requires iterating over map entries [G].

**Pseudocode:**
```python
class VoxelKind:
    Dirt = 0
    Stone = 1

class Chunk:
    def __init__(self, chunk_pos):
        self.chunk_pos = chunk_pos
        self.voxels = {}  # HashMap<IVec3, VoxelKind>
        self.mesh = None

    def insert(self, local_pos, kind):
        self.voxels[local_pos] = kind

    def query(self, local_pos):
        return self.voxels.get(local_pos, VoxelKind.Dirt)

    def render(self):
        offset = self.chunk_pos * 32
        if self.mesh is None:
            self._create_mesh()
        self._draw_mesh(self.mesh, offset)
```

## Subtopics

### Voxel Flag System & Filled State Logic
This variant extends typed voxels with a 5-bit flag system to track geometric and topological state (filled, inside, surface, solid, clipped) [S2, unofficial]. It is chosen when the rendering or physics engine requires explicit state propagation for culling or collision detection rather than just material identity [S2, unofficial]. It differs from basic typed voxels by attaching metadata bits to each voxel [S2, unofficial].

- **Layout:**
  - `VoxelFlagsEnum`: 5-bit bitmask. `FILLED = 0x01 << 0`, `INSIDE = 0x01 << 1`, `SURFACE = 0x01 << 2`, `SOLID = 0x01 << 3`, `CLIPPED = 0x01 << 4` [S2, unofficial].
  - `VoxelMeta`: Stores `VoxelIndex index_` and `VoxelFlags flags_` [S2, unofficial].
- **Steps:**
  1. `ClearFlags()` initializes flags to 0 and sets the `INSIDE` bit [S2, unofficial].
  2. `UpdateFilled()` computes the `FILLED` state: sets `FILLED` if `!Clipped() && (Solid() || (Surface() && Inside()))`, otherwise unsets `FILLED` [S2, unofficial].
  3. `SetInside()`, `UnsetInside()`, `SetSurface()`, `UnsetSurface()`, `SetSolid()`, `UnsetSolid()`, `SetClipped()`, and `UnsetClipped()` modify their respective flag bits and call `UpdateFilled()` to propagate state changes [S2, unofficial].

## Operating characteristics
- **Time Complexity:** Lookup and insertion are $O(1)$ average case for hash maps, with $O(N)$ worst case due to collisions [G]. Iterating over all voxels for mesh generation is $O(V)$ where $V$ is the number of occupied voxels [G].
- **Memory Complexity:** $O(V)$ for occupied voxels, plus hash table bucket and pointer overhead [G].
- **Performance:** Not given in the sources.
- **Scaling:** Not given in the sources.
- **Strengths:** Sparse storage, flexible material assignment, easy extension with new types [S1, unofficial].
- **Limitations:** Higher memory overhead per voxel, hash map collision handling, slower iteration than contiguous arrays [G].
- **When to use:** Sparse worlds with high material diversity [S1, unofficial].
- **When not to use:** Dense or uniform regions where bit-packing is more efficient [G].
