# Typed Voxels

Also called: Voxel Kind, Material Type Voxel

## Overview
Typed Voxels extend the binary existence model of sparse voxel structures by associating a discrete material identifier with each occupied voxel. This allows a voxel world to distinguish between different material kinds (e.g., dirt, stone) rather than treating all voxels as identical solid entities. It builds on [Multi-type Voxel Storage](1104-multi-type-voxel-storage.md) by introducing a specific enumeration-based type system for voxel content.

## How it works
**Inputs and Outputs:**
*   Input: A chunk coordinate system and a world generation or modification request.
*   Output: A chunk data structure containing a map of voxel positions to material types, and optionally a rendered mesh.

**Data Structures:**
The core change is in the `Chunk` structure. Instead of storing only the presence of a voxel, it stores the type.

1.  **VoxelKind Enum:** A user-defined enumeration defining the available material types.
    *   Example: `enum VoxelKind { Dirt, Stone }` [S1, unofficial].
2.  **Chunk Storage:** The voxel storage within a `Chunk` is changed from a set of coordinates to a hash map mapping coordinates to types.
    *   Layout: `HashMap<IVec3, VoxelKind>` [S1, unofficial].
    *   `IVec3` represents the integer 3D offset within the chunk.
    *   `VoxelKind` is the enum value.

**Algorithm:**
The rendering loop remains largely unchanged, but the mesh generation must now account for the type.

1.  Iterate through active chunk positions.
2.  For each chunk, retrieve or create the chunk object.
3.  If the chunk has a cached mesh, draw it.
4.  If not, generate the mesh from the `HashMap<IVec3, VoxelKind>` data.
5.  Draw the mesh with an appropriate offset.

**Pseudocode:**
```python
# Define the voxel type enum
class VoxelKind(Enum):
    DIRT = 0
    STONE = 1

# Define the Chunk structure

    mesh: Optional[Mesh] = None
```

**Edge Cases and Pitfalls:**
*   **Mesh Generation:** The `create_mesh` function must be aware of `VoxelKind`. A generic mesh generator that assumes all voxels are identical will fail to render distinct materials correctly.
*   **Memory:** Using a `HashMap` instead of a `HashSet` or dense array increases memory overhead per voxel due to hash map entry overhead and the storage of the enum value.

## Subtopics

### Voxel Flag System & Filled State Logic
This variant extends the typed voxel concept by adding a bitmask to track the geometric and topological state of each voxel, enabling optimized culling and collision detection. It is chosen when the engine requires efficient determination of whether a voxel is part of the solid interior, surface, or clipped by a bounding volume.

*   **Layout:**
    *   `VoxelFlagsEnum`: A 5-bit bitmask [S2, unofficial].
        *   `FILLED` = `0x01 << 0` (Bit 0)
        *   `INSIDE` = `0x01 << 1` (Bit 1)
        *   `SURFACE` = `0x01 << 2` (Bit 2)
        *   `SOLID` = `0x01 << 3` (Bit 3)
        *   `CLIPPED` = `0x01 << 4` (Bit 4)
    *   `VoxelMeta`: Stores the voxel index and flags.
        *   Fields: `index_` (VoxelIndex), `flags_` (VoxelFlagsEnum) [S2, unofficial].

*   **Steps:**
    1.  **Initialization:** `ClearFlags()` sets all flags to 0 and sets the `INSIDE` bit [S2, unofficial].
    2.  **State Update:** `UpdateFilled()` computes the `FILLED` state.
        *   Formula: `FILLED = !Clipped() && (Solid() || (Surface() && Inside()))` [S2, unofficial].
        *   If the condition is true, set `FILLED`; otherwise, unset it [S2, unofficial].
    3.  **Flag Modification:** Helper functions (`SetInside`, `UnsetInside`, `SetSurface`, `UnsetSurface`, `SetSolid`, `UnsetSolid`, `SetClipped`, `UnsetClipped`) modify their respective bits and call `UpdateFilled()` to propagate state changes [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** Lookup and insertion in the `HashMap` are $O(1)$ on average. Mesh generation complexity depends on the number of voxels and the complexity of the meshing algorithm (e.g., Marching Cubes), but now includes material assignment overhead.
*   **Memory Complexity:** Higher than binary voxel storage. Each voxel stores an integer index and an enum value (typically 1-4 bytes) plus hash map overhead. The flag system variant adds a 5-bit flag structure (padded to at least 1 byte or integrated into a larger metadata struct) per voxel [S2, unofficial].
*   **Strengths:** Enables complex world generation with varied terrain; supports material-specific rendering and physics.
*   **Limitations:** Increased memory usage; mesh generation is more complex as it must handle multiple material types.

## Background
The concept of typed voxels is a common extension in voxel engine tutorials and implementations to move beyond simple binary worlds. It is popularized in indie game development contexts, such as the "Voxel Engine THIS weekend" tutorial series, which demonstrates adding material types like dirt and stone to a basic voxel engine [S1, unofficial]. The flag-based state system is found in open-source voxelization tools like `topskychen/voxelizer`, which use flags to manage the filled state of voxels during mesh generation [S2, unofficial].
