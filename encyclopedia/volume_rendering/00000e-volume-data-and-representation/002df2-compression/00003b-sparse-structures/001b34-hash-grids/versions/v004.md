# Hash Grids

Also called: Coordinate Hashing, Vertex Hashing for Voxel Grid, Hashed Grid Construction (Row Displacement Compression), Row Displacement Compression

## Overview
Hash Grids compress a static sparse 3D matrix by mapping non-empty voxel coordinates to a compact linear array using a perfect hash function, eliminating the storage overhead of empty cells [S1, unofficial]. Unlike sibling structures like [SparseGrid](904-sparsegrid.md) or [Tree-based structures](4139-tree-based-structures-octree-pointer-tree-sparse-voxel-dag.md) which rely on dynamic allocation or tree traversal, Hash Grids achieve $O(1)$ access time with a fixed memory footprint determined by the grid dimensions and the number of occupied cells, making them ideal for static scenes where the spatial distribution is known beforehand [S1, unofficial].

## How it works
**Inputs:** A set of 3D items (e.g., triangles or voxels) with bounding boxes, and a target grid resolution heuristic.
**Outputs:** Four static arrays: $L$ (item indexes), $H$ (hash table), $O$ (offset table), and $D$ (domain bits).

**Data Structures:**
1.  **Array $L$**: A 1D array of machine words containing the indexes of all cell items.
2.  **Array $H$**: A linearized and hashed 3D array of machine word indexes into $L$. The item list size for cell $i$ is $H[i] - H[i+1]$.
3.  **Array $O$**: A linearized 2D array of machine word indexes into $H$, with size $M_y \times M_z$.
4.  **Array $D$**: Domain bits, a bit array of size $N = M_x \times M_y \times M_z$. $D[i]$ is 1 if cell $i$ is not empty, 0 otherwise.

**Construction Steps (Row Displacement Compression):**
1.  Compute the scene's bounding box.
2.  Determine grid dimensions $M_x \times M_y \times M_z = N$ using a grid heuristic [S1, unofficial].
3.  Allocate Array $D$ of size $N$ and initialize all bits to zero.
4.  For each item whose bounding box intersects a grid cell $i$, set $D[d(x,y,z)]$ to 1. The 1D index $d(x,y,z)$ is calculated as:
    $$d(x, y, z) = ((M_y \times z) + y) \times M_x) + x$$
5.  Allocate Offset Table $O$ of size $M_y \times M_z$.
6.  Allocate a temporary bit array $b_H$ with size double the number of non-empty cells, initialized to zero.
7.  For each grid row $(y,z)$ in $O$:
    a. Find the smallest offset starting from the last offset.
    b. If bits in the row $D[d(0, y,z) \dots d(M_x-1, y,z)]$ collide, handle collision via displacement logic (text cuts off, but implies shifting rows to find empty slots in $H$) [S1, unofficial].
8.  Populate Array $H$ and $L$ based on the computed offsets and occupied cells.

**Hashing for Dynamic/Neural Variants:**
For dynamic or neural rendering contexts (e.g., Instant-NGP, F2-NeRF), a multiplicative hash with prime constants is used to map 3D coordinates to bucket indices [S2, unofficial].

**Pseudocode for Coordinate Hashing (Neural/General Purpose):**
```python
# Constants for hashing 3D coordinates
# Using large primes to minimize collisions
PRIMES = [1, 2654435761, 805459861, 3674653429, 2097192037, 1434869437, 2165219737]

def hash_coords(coords, log2_hashmap_size):
    """
    Hashes 3D coordinates to a bucket index.
    coords: Tensor of shape (..., 3) or (N, 3)
    log2_hashmap_size: Logarithm of hash table size T w.r.t 2.
    Returns: Bucket indices.
    """
    # Extract x, y, z components
    x = coords[..., 0]
    y = coords[..., 1]
    z = coords[..., 2]
    
    # Multiplicative hash with prime constants
    # Formula: ((x * p1) ^ (y * p2) ^ (z * p3)) % T
    # Note: The source [S2, unofficial] uses specific primes. 
    # Common implementation uses:
    hash_val = (x * PRIMES[1]) ^ (y * PRIMES[2]) ^ (z * PRIMES[3])
    
    # Modulo to fit in hash table size T = 2^log2_hashmap_size
    T = 1 << log2_hashmap_size
    bucket_index = hash_val % T
    
    return bucket_index

def hash_coords_multi_leaf(coords, leaf_index, log2_hashmap_size, L_table_length):
    """
    Hashes coordinates using leaf-node specific hash functions (F2-NeRF variant).
    coords: Tensor of shape (..., 3)
    leaf_index: Index of the leaf node
    L_table_length: Length of the hash table L
    """
    # Retrieve random large primes and offsets for this leaf node
    # pi_i,k and delta_i,k are fixed for leaf node i and coordinate k
    pi = get_primes_for_leaf(leaf_index) # Shape (3,)
    delta = get_offsets_for_leaf(leaf_index) # Shape (3,)
    
    x = coords[..., 0]
    y = coords[..., 1]
    z = coords[..., 2]
    
    # Formula: Hash_i(v_hat) = ( (v_hat_1 XOR pi_i,1) + delta_i,1 XOR (v_hat_2 XOR pi_i,2) + delta_i,2 XOR (v_hat_3 XOR pi_i,3) + delta_i,3 ) mod L
    # Note: The source [S7] notation is ambiguous regarding operator precedence. 
    # Standard interpretation of XOR folding with addition:
    term1 = (x ^ pi[0]) + delta[0]
    term2 = (y ^ pi[1]) + delta[1]
    term3 = (z ^ pi[2]) + delta[2]
    
    # Bitwise XOR of the terms
    hash_val = term1 ^ term2 ^ term3
    
    bucket_index = hash_val % L_table_length
    return bucket_index
```

**Edge Cases and Pitfalls:**
*   **Collisions:** In static construction, row displacement ensures a perfect hash (no collisions) for the given static set [S1, unofficial]. In dynamic/neural hashing, collisions are inevitable and managed by the hash table size and probing/chaining [S2, unofficial].
*   **Precision:** Floating-point coordinates must be discretized to integer grid indices before hashing [S1, unofficial].
*   **Memory Leaks:** If using chaining for hash maps, ensure destructors traverse all chains to delete nodes [S4, unofficial].

## Subtopics

### [Voxel World Data Structure](1101-voxel-world-data-structure.md)
The Voxel World Data Structure is a sparse storage method that maintains a set of occupied voxel coordinates using a hash set of integer-based 3D vectors ($IVec3$). It solves the problem of efficiently tracking voxel existence in a voxel world while ensuring strict grid alignment by converting floating-point positions to integers. It differs from its siblings by using a flat, unstructured hash set of coordinates rather than hierarchical bricks or multi-level grids, making it suitable for simple, dynamic voxel manipulation where spatial coherence optimization is secondary to implementation simplicity.

### [Hash Grid Loss](2093-hash-grid-loss.md)
Hash Grid Loss is a regularization term used in compressive neural volume rendering to minimize the bit consumption of the binary occupancy structure of a hash grid during training. It operates by modeling the probability distribution of the binary hash grid values and optimizing the negative log-likelihood, effectively driving the model to create a more concentrated hash grid structure. It is distinct from sibling methods like Voxel World Data Structure which manage spatial indexing, and from Entropy Loss which focuses on the continuous or quantized attribute values stored within active cells rather than the occupancy bits themselves.

### [Dual Point Map Insertion with Linear Probing](3043-dual-point-map-insertion-with-linear-probing.md)
This method stores dual points in a hash table using linear probing to handle collisions, mapping unique point identifiers to their 3D positions via a combined 64-bit key-value pair. It builds on the hashing strategy of [Hash Grids](936-hash-grids.md) by hashing vertex positions to bucket indices [G].

### [Multi-Level Hashed Grid Construction](3402-multi-level-hashed-grid-construction.md)
Multi-Level Hashed Grid Construction is a method for rapidly building a sparse acceleration structure that combines the low memory footprint of hashed grids with the traversal efficiency of multi-level grids. It solves the problem of high memory consumption in classic non-compressed multi-level grids while maintaining fast render times for large, sparse scenes. Unlike one-level hashed grids, it uses macrocells to skip empty regions in larger steps, providing approximately twice the render time performance for large scanned scenes. It builds on [Hash Grids](936-hash-grids.md) by adding hierarchical resolution levels and spatial skipping structures.

### [Universal Hash Optimization](3456-universal-hash-optimization.md)
Universal Hash Optimization is a technique used within Sparse Voxel Octree (SVO) structures to mitigate hash collisions in the underlying hash table. It replaces standard deterministic hashing with a randomized universal hash function, ensuring that distinct non-isomorphic nodes are distributed uniformly across hash table buckets. This reduces the average number of equality checks required during lookups, thereby improving search performance compared to naive hashing methods that may cluster nodes in specific buckets.

### SpatialHash3D
SpatialHash3D is a spatial index structure using a uniform 3D hash grid to enable efficient nearest-neighbor and radius-based queries for static datasets, providing O(1) cell lookup [S1, unofficial]. It differs from its siblings by prioritizing implementation simplicity and predictable performance for static data over the adaptive granularity of octrees or the complex balancing of KD-trees, making it suitable for straightforward radius queries where data does not change during the query phase [S1, unofficial].

### Integer Hash Map with Chaining
A hash table implementation for integer keys using open addressing via chaining. Supports hashing 2 or 4 integer keys into a single index, with separate structures for storing associated integer or float data [S4, unofficial]. Key generation for 2 keys masks each key to 10 bits, shifts k1 left by 10, ORs with k2, and masks to 20 bits. For 4 keys, masks to 5 bits and shifts accordingly [S4, unofficial]. Parameters: `HASH_LENGTH` 20, `MAX_HASH` $2^{20}$ (1,048,576), `HASH_BIT_2` 10, `HASH_BIT_4` 5 [S4, unofficial]. Pitfall: Memory leaks if destructor is not called; constructor initializes all `MAX_HASH` pointers to NULL [S4, unofficial].

### 3D Coordinate Packing
Packs three 16-bit voxel coordinates (x, y, z) into a single 64-bit integer key for hash map indexing [S5, unofficial]. Uses a union containing a struct with three short fields and a `__int64` field. Assigning x, y, z to the struct fields directly populates the 64-bit key via memory overlap [S5, unofficial]. Formula: `key = (z << 32) | (y << 16) | x` (assuming little-endian and no padding) [S5, unofficial]. Pitfall: Relies on little-endian architecture and struct alignment; coordinates limited to 16-bit signed range (-32768 to 32767) [S5, unofficial].

### Hash Grid with Multiple Hash Functions
Maps a point $x$ in the $i$-th leaf node to warp space $z = F_i(x)$, finds $z$'s eight neighboring grid vertices $\hat{v}$ with integer coordinates, and computes a hash value for each vertex using a leaf-conditioned hash function [S7]. Formula: $\text{Hash}_i(\hat{\mathbf{v}}) = \left( \bigoplus_{k=1}^3 \hat{\mathbf{v}}_k \pi_{i,k} + \Delta_{i,k} \right) \bmod L$, where $\pi_{i,k}$ and $\Delta_{i,k}$ are random large prime numbers fixed for leaf node $i$, and $L$ is hash table length [S7]. This alleviates conflict problems by using different hash functions for different leaf nodes [S7].

## Operating characteristics
*   **Time Complexity:** Access is $O(1)$ on average for hash lookups, though with a larger constant factor than dense arrays due to hashing overhead [S4, unofficial]. Construction is $O(N)$ where $N$ is the number of cells, but requires additional passes for collision resolution in perfect hashing [S1, unofficial].
*   **Memory Complexity:** $O(N)$ for the domain bits and hash table, where $N$ is the total grid volume. The actual memory usage is proportional to the number of non-empty cells if perfect hashing is used, as empty cells are not stored in $L$ or $H$ [S1, unofficial].
*   **Performance:** For static scenes, row displacement compression provides optimal memory usage with no collisions [S1, unofficial]. For neural rendering, hash grids offer significant speedups over dense grids by only computing features for active cells [S7].
*   **Strengths:** Constant time access, low memory overhead for sparse data, simple implementation.
*   **Limitations:** Static construction requires pre-processing; dynamic updates are expensive due to potential re-hashing or collision handling; hash collisions can degrade performance in dynamic settings [S1, unofficial].

## Background
Hash Grids originated from the need to efficiently store and access sparse 3D data in computer graphics, particularly for voxelization and ray tracing [S1, unofficial]. The specific construction method using row displacement compression was described by Lagae and Dutre in 2008 [S1, unofficial]. The technique has been widely adopted in modern neural rendering pipelines, such as Instant-NGP and F2-NeRF, to accelerate feature lookup for neural radiance fields [S3, unofficial][S7].
