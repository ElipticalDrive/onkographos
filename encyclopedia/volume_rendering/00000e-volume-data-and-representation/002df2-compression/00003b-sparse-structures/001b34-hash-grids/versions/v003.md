# Hash Grids
Also called: Coordinate Hashing, Vertex Hashing for Voxel Grid, Hashed Grid Construction (Row Displacement Compression), Row Displacement Compression

## Overview
Hash Grids compress a static sparse 3D matrix by mapping occupied voxel coordinates to a compact hash table using a perfect hash function with no collisions, eliminating the storage overhead of empty cells [S1, unofficial]. Unlike tree-based sparse structures that require traversal overhead or dense grids that waste memory on empty space, Hash Grids provide $O(1)$ constant-time access to voxel data by combining a domain bit array with row displacement compression [S1, unofficial]. This method is distinct from its sibling [SparseGrid](904-sparsegrid.md) by relying on static perfect hashing rather than dynamic sparse indexing, and from [Brick-based Hierarchical Storage](2793-brick-based-hierarchical-storage.md) by operating on a single resolution level without hierarchical macrocells [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A set of static 3D items (e.g., triangles or voxels) with known bounding boxes, and a grid heuristic determining dimensions $M_x \times M_y \times M_z = N$.
*   **Output:** Four static arrays ($L, H, O, D$) enabling constant-time lookup of voxel data from 3D coordinates.

**Data Structures:**
The structure consists of four static arrays [S1, unofficial]:
1.  **Array L (Item List):** A 1D array of machine words containing the indexes of all cell items.
2.  **Array H (Hash Table):** A linearized and hashed 3D array of machine word indexes into $L$. The item list size for cell $i$ is given by $H[i] - H[i+1]$.
3.  **Array O (Offset Table):** A linearized 2D array of machine word indexes into $H$, with size $M_y \times M_z$.
4.  **Array D (Domain Bits):** A bit array of size $N = M_x \times M_y \times M_z$. $D[i]$ is 1 if cell $i$ is not empty, and 0 otherwise.

**Numbered Steps:**
1.  **Compute Bounding Box:** Determine the scene's bounding box.
2.  **Determine Grid Dimensions:** Use the grid heuristic to calculate $M_x, M_y, M_z$ such that $N = M_x \times M_y \times M_z$ [S1, unofficial].
3.  **Initialize Domain Bits:** Allocate Array $D$ of size $N$ and initialize all bits to zero.
4.  **Mark Occupied Cells:** For each item whose bounding box intersects cell $i$, set $D[d(x,y,z)] = 1$. The 1D index is calculated as:
    $$d(x, y, z) = ((M_y \times z) + y) \times M_x) + x$$
    [S1, unofficial].
5.  **Allocate Offset Table:** Allocate Array $O$ of size $M_y \times M_z$.
6.  **Allocate Temporary Buffer:** Allocate a temporary bit array $bH$ with size equal to double the number of non-empty cells, initialized to zero [S1, unofficial].
7.  **Row Displacement Compression:** For each grid row $(y, z)$ in $O$:
    *   Find the smallest offset starting from the last offset.
    *   Map the row bits $D[d(0, y, z) \dots d(M_x-1, y, z)]$ into the hash table $H$.
    *   If bits collide (i.e., multiple items map to the same location in $H$ for a given row), handle collision via displacement logic (text cuts off, but implies shifting entries to find an empty slot) [S1, unofficial].
8.  **Finalize Hash Table:** Populate $H$ and $O$ such that $H$ contains the compressed indices into $L$, and $O$ contains the offsets into $H$ for each $(y, z)$ row.

        bit_idx = cell_idx % 32

**Parameters:**
*   **Grid Heuristic:** Determines $M_x, M_y, M_z$. Typical values depend on scene bounding box and desired voxel resolution [S1, unofficial].
*   **Hash Table Size:** Determined by the number of non-empty cells and the displacement overhead [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Static Data Only:** This method assumes static data. Dynamic updates require rebuilding the hash table [S1, unofficial].
*   **Collision Handling:** The row displacement compression must handle collisions efficiently. Poor collision resolution can lead to large hash tables or slow lookups [S1, unofficial].
*   **Precision:** Grid indexing uses integer arithmetic. Floating-point coordinates must be converted to integer grid indices before hashing [S1, unofficial].

## Subtopics

### [Voxel World Data Structure](1101-voxel-world-data-structure.md)
The Voxel World Data Structure is a sparse storage method that maintains a set of occupied voxel coordinates using a hash set of integer-based 3D vectors ($IVec3$). It solves the problem of efficiently tracking voxel existence in a voxel world while ensuring strict grid alignment by converting floating-point positions to integers. It differs from its siblings by using a flat, unstructured hash set of coordinates rather than hierarchical bricks or multi-level grids, making it suitable for simple, dynamic voxel manipulation where spatial coherence optimization is secondary to implementation simplicity.

### [Hash Grid Loss](2093-hash-grid-loss.md)
Hash Grid Loss is a regularization term used in compressive neural volume rendering to minimize the bit consumption of the binary occupancy structure of a hash grid during training. It operates by modeling the probability distribution of the binary hash grid values and optimizing the negative log-likelihood, effectively driving the model to create a more concentrated hash grid structure. It is distinct from sibling methods like Voxel World Data Structure which manage spatial indexing, and from Entropy Loss which focuses on the continuous or quantized attribute values stored within active cells rather than the occupancy bits themselves.

### [Dual Point Map Insertion with Linear Probing](3043-dual-point-map-insertion-with-linear-probing.md)
This method manages a sparse collection of "dual points" (typically edge midpoints or specific geometric features) by mapping unique point identifiers to their 3D positions using a hash table with linear probing. It solves the problem of efficiently storing and retrieving geometric data associated with specific IDs in a compact, cache-friendly structure, building on the hashing strategy of [Hash Grids](936-hash-grids.md). It is distinguished from sibling structures like [Voxel World Data Structure](1101-voxel-world-data-structure.md) by its explicit handling of point IDs rather than spatial coordinates, and from [SpatialHash3D](5113-spatialhash3d.md) by its fixed-size 64-bit key-value packing and specific 18-bit ID masking.

### [Multi-Level Hashed Grid Construction](3402-multi-level-hashed-grid-construction.md)
Multi-Level Hashed Grid Construction is a method for rapidly building a sparse acceleration structure for volume rendering and ray tracing that combines the memory efficiency of hashed grids with the traversal speed of multi-level structures. It solves the problem of high memory consumption in classic multi-level array grids and the poor traversal performance of one-level hashed grids by using row displacement compression to eliminate empty cells and macrocells to skip large empty regions. Unlike its sibling [Hash Grids](936-hash-grids.md), which uses a single resolution level, this method employs multiple resolutions to balance detail and coverage, and unlike [Voxel World Data Structure](1101-voxel-world-data-structure.md), it avoids storing explicit empty voxels by compressing the grid topology.

### [Universal Hash Optimization](3456-universal-hash-optimization.md)
Universal Hash Optimization is a technique used within Sparse Voxel Octree (SVO) structures to mitigate hash collisions in the underlying hash table. It replaces standard deterministic hashing with a randomized universal hash function, ensuring that distinct non-isomorphic nodes are distributed uniformly across hash table buckets. This reduces the average number of equality checks required during lookups, thereby improving search performance compared to naive hashing methods that may cluster nodes in specific buckets.

### SpatialHash3D
SpatialHash3D is a spatial index structure using a uniform 3D hash grid to enable efficient nearest-neighbor and radius-based queries for static datasets, providing O(1) cell lookup [S1, unofficial]. It differs from its siblings by prioritizing implementation simplicity and predictable performance for static data over the adaptive granularity of octrees or the complex balancing of KD-trees, making it suitable for straightforward radius queries where data does not change during the query phase [S1, unofficial].

### Integer Hash Map with Chaining
A hash table implementation for integer keys using open addressing via chaining. Supports hashing 2 or 4 integer keys into a single index, with separate structures for storing associated integer or float data [S4, unofficial]. Key generation for 2 keys masks each key to 10 bits, shifts k1 left by 10, ORs with k2, and masks to 20 bits. For 4 keys, each is masked to 5 bits, shifted by 15, 10, 5, and 0 respectively, then ORed and masked to 20 bits [S4, unofficial]. Lookup traverses the chain at `table[ind]` comparing n1..n4. Insertion creates a new node, sets fields, and prepends to the chain at `table[ind]` [S4, unofficial]. Parameters: `HASH_LENGTH` is 20, `MAX_HASH` is $1 \ll 20$ (1,048,576), `HASH_BIT_2` is 10, `HASH_BIT_4` is 5 [S4, unofficial]. Layout: `HashMap` table is `ElementList* table[MAX_HASH]`, where `ElementList` contains `int n1, n2, index, location` and `ElementList* next`. `HashMap2` table is `ElementList2* table[MAX_HASH]`, where `ElementList2` contains `int n1, n2; float v[3]` and `ElementList2* next`. `HashMap4` table is `ElementList4* table[MAX_HASH]`, where `ElementList4` contains `int n1, n2, n3, n4, index` and `ElementList4* next` [S4, unofficial]. Pitfall: Memory leaks if the destructor is not called. The destructor iterates all buckets, traverses each chain, and deletes nodes. The constructor initializes all `MAX_HASH` pointers to NULL [S4, unofficial].

### 3D Coordinate Packing
Packs three 16-bit voxel coordinates (x, y, z) into a single 64-bit integer key for hash map indexing [S5, unofficial]. Uses a union containing a struct with three short fields and a `__int64` field. Assigning x, y, z to the struct fields directly populates the 64-bit key via memory overlap [S5, unofficial]. Formula: `key = (z << 32) | (y << 16) | x` (assuming little-endian and no padding, derived from struct layout) [S5, unofficial]. Pitfall: Relies on little-endian architecture and struct alignment. Coordinates are limited to 16-bit signed range (-32768 to 32767) [S5, unofficial].

### Hash Map Operations
CUDA implementations for hash map insertion and lookup operations, including 3D specific variants and one where the 3D index is used as the value [S6, unofficial].

## Operating characteristics
*   **Time Complexity:** Lookup is $O(1)$ constant time after construction [S1, unofficial]. Construction is $O(N)$ where $N$ is the number of cells, but depends on the efficiency of the row displacement compression algorithm [S1, unofficial].
*   **Memory Complexity:** Memory usage is proportional to the number of non-empty cells plus the overhead of the hash table and offset arrays. It is significantly more memory-efficient than dense grids for sparse scenes [S1, unofficial].
*   **Measured Performance:** Timings for the Buddha scene show performance improvements with grid density, though specific numbers are not provided in the notes [S1, unofficial].
*   **Strengths:** Constant-time access, memory efficiency for static sparse data, simple data structure.
*   **Limitations:** Static data only (rebuilding required for updates), complex construction algorithm (row displacement), potential for hash collisions if not implemented correctly [S1, unofficial].
*   **When to Use:** Static volume rendering, ray tracing acceleration structures for sparse scenes.
*   **When Not to Use:** Dynamic scenes requiring frequent updates, non-static data.

## Background
Hash Grids were introduced in the context of sparse 3D matrix compression for volume rendering and ray tracing. The method uses row displacement compression, originally described by Lagae and Dutre (2008), to avoid storing empty array cells [S1, unofficial]. The technique is cited in various graphics programming contexts, including voxelization and neural radiance fields [S1, S3, unofficial].
