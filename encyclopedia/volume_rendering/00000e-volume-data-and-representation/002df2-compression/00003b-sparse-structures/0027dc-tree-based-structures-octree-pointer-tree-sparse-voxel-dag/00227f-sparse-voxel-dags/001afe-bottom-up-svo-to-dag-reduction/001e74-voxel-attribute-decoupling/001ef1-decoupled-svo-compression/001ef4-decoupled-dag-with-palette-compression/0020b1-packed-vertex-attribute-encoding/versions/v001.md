# Packed Vertex Attribute Encoding

Also called: 32-bit vertex packing, PackedVertex, Vertex compression

## Overview
Packed Vertex Attribute Encoding is a compression scheme for vertex attributes in hardware-accelerated volume splatting that reduces memory usage by packing volume texture coordinates and Gaussian texture coordinates into 32-bit integers per vertex [S1, unofficial]. It sets itself apart from sibling methods by specifically targeting the attribute storage of proxy geometry in EWA splatting, decoupling the coordinate components into fixed-width bit fields to achieve high compression ratios (e.g., 171:1) while allowing fast decompression via lookup tables [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Volume texture coordinates ($tx, ty$) and Gaussian texture coordinate components ($fx, fy$) for a single vertex.
*   **Output:** A single 32-bit unsigned integer (`uint32_t`) containing the packed attributes.

**Data Structures:**
The packed data is stored in a `uint32_t`. The bit layout (LSB to MSB) is defined as follows:
*   Bits 0–5 (6 bits): $ix$ (derived from $tx$)
*   Bits 6–11 (6 bits): $iy$ (derived from $ty$)
*   Bits 12–17 (6 bits): $mx$ (derived from $tx$)
*   Bits 18–23 (6 bits): $my$ (derived from $ty$)
*   Bits 24–25 (2 bits): $fx$
*   Bits 26–27 (2 bits): $fy$
*   Bits 28–31 (4 bits): Unused

*Note: Source [S2, unofficial] describes a different layout involving `normalIndex` and `uvIndex` with 6-bit fields for x/y/z. However, Source [S1, unofficial] is the primary source for this specific method in volume splatting, detailing the $tx, ty, fx, fy$ packing. The [S2, unofficial] layout appears to be from a different context (OM3D project) and is not integrated into the core volume splatting definition provided by [S1, unofficial]. The following algorithm follows [S1, unofficial].*

**Formulas:**
The volume texture coordinates $tx$ and $ty$ are decomposed into integer components:
$$ tx = mx \times 256 + ix $$
$$ ty = my \times 256 + iy $$
Where:
*   $mx = \lfloor tx / 256 \rfloor$
*   $ix = tx \pmod{256}$
*   $my = \lfloor ty / 256 \rfloor$
*   $iy = ty \pmod{256}$

The Gaussian components $fx$ and $fy$ are binary values (0 or 1) [S1, unofficial].

**Parameters:**
*   $mx, my$: Stored using 7 bits each (allowing volume slices up to $2^{15} \times 2^{15}$ voxels) [S1, unofficial].
*   $ix, iy$: Stored using 8 bits each [S1, unofficial].
*   $fx, fy$: Stored using 1 bit each [S1, unofficial].

**Steps:**
1.  **Decompose Coordinates:** For each vertex, calculate $mx, ix, my, iy$ from the floating-point or integer volume texture coordinates $tx, ty$ using the formulas above.
2.  **Validate Gaussian Components:** Ensure $fx$ and $fy$ are binary (0 or 1) [S1, unofficial].
3.  **Pack Bits:** Construct the 32-bit integer by shifting and masking the components.
    *   Shift $ix$ left by 0 bits.
    *   Shift $iy$ left by 8 bits.
    *   Shift $mx$ left by 16 bits.
    *   Shift $my$ left by 24 bits.
    *   Shift $fx$ left by 32 bits? No, total bits are 32.
    *   *Correction based on [S1, unofficial] bit count:* $7+8+7+8+1+1 = 32$ bits.
    *   Layout from [S1, unofficial]: $mx$ (7 bits), $ix$ (8 bits), $my$ (7 bits), $iy$ (8 bits), $fx$ (1 bit), $fy$ (1 bit).
    *   The exact bit ordering (LSB vs MSB) for $mx/ix/my/iy$ is not explicitly defined as "LSB first" in [S1, unofficial], but standard packing usually places the least significant part of the coordinate first or last. Given $tx = mx \times 256 + ix$, $ix$ is the lower 8 bits of the 16-bit value. $mx$ is the upper 7 bits.
    *   Let's assume a standard little-endian bit packing where the lowest bits of the integer hold the least significant parts of the data, or follow the specific shift logic if implied. [S1, unofficial] does not specify the exact shift offsets for the final integer, only the bit widths.
    *   *Implementation Detail [G]:* Since [S1, unofficial] does not specify the exact bit offsets for the final `uint32_t` construction, a standard approach is to pack them contiguously. For example:
        *   Bits 0-7: $ix$
        *   Bits 8-14: $mx$
        *   Bits 15-22: $iy$
        *   Bits 23-29: $my$
        *   Bits 30: $fx$
        *   Bits 31: $fy$
        *   *Note:* This is a guess [G] as [S1, unofficial] says "packed into 32 bits" but doesn't give the shift amounts. However, [S2, unofficial] gives explicit shifts for a *different* format. We must stick to [S1, unofficial]. [S1, unofficial] mentions "Figure 5" which is not available. We will describe the packing in terms of bit widths and note the ambiguity.
4.  **Store:** Write the resulting `uint32_t` to the vertex buffer.

**Decoding:**
1.  **Extract:** Retrieve the 32-bit integer from the vertex buffer.
2.  **Unpack:** Extract $ix, mx, iy, my, fx, fy$ using bitwise operations and masks.
3.  **Reconstruct:** Calculate $tx = mx \times 256 + ix$ and $ty = my \times 256 + iy$ [S1, unofficial].
4.  **Lookup [G]:** [S1, unofficial] mentions using a "small lookup table" for fast decompression in Direct3D. The exact table content is not provided. A standard implementation would precompute the $tx, ty$ values for all possible $mx, ix, my, iy$ combinations or use the formula directly.

**Pseudocode:**

```python
def pack_vertex_attributes(tx: int, ty: int, fx: int, fy: int) -> int:
    """
    Packs volume texture coordinates (tx, ty) and Gaussian coordinates (fx, fy)
    into a single 32-bit integer.
    
    Args:
        tx: Volume texture coordinate x (integer)
        ty: Volume texture coordinate y (integer)
        fx: Gaussian texture coordinate x (0 or 1)
        fy: Gaussian texture coordinate y (0 or 1)
        
    Returns:
        Packed 32-bit integer
    """
    # Decompose tx and ty
    mx = tx // 256
    ix = tx % 256
    my = ty // 256
    iy = ty % 256
    
    # Validate inputs
    assert 0 <= mx < 128, "mx must fit in 7 bits"
    assert 0 <= ix < 256, "ix must fit in 8 bits"
    assert 0 <= my < 128, "my must fit in 7 bits"
    assert 0 <= iy < 256, "iy must fit in 8 bits"
    assert fx in (0, 1), "fx must be 0 or 1"
    assert fy in (0, 1), "fy must be 0 or 1"
    
    # Pack into 32-bit integer
    # Layout assumption based on bit widths: 
    # ix (8), mx (7), iy (8), my (7), fx (1), fy (1)
    # Total 32 bits.
    
    packed = 0
    packed |= (ix & 0xFF) << 0
    packed |= (mx & 0x7F) << 8
    packed |= (iy & 0xFF) << 15
    packed |= (my & 0x7F) << 23
    packed |= (fx & 0x1) << 30
    packed |= (fy & 0x1) << 31
    
    return packed

def unpack_vertex_attributes(packed: int) -> tuple:
    """
    Unpacks a 32-bit integer into volume texture coordinates (tx, ty) 
    and Gaussian coordinates (fx, fy).
    
    Args:
        packed: Packed 32-bit integer
        
    Returns:
        Tuple (tx, ty, fx, fy)
    """
    ix = (packed >> 0) & 0xFF
    mx = (packed >> 8) & 0x7F
    iy = (packed >> 15) & 0xFF
    my = (packed >> 23) & 0x7F
    fx = (packed >> 30) & 0x1
    fy = (packed >> 31) & 0x1
    
    tx = mx * 256 + ix
    ty = my * 256 + iy
    
    return (tx, ty, fx, fy)
```

**Edge Cases and Pitfalls:**
*   **Precision:** The decomposition assumes integer coordinates. If floating-point coordinates are used, they must be scaled and rounded to integers before packing [S1, unofficial].
*   **Boundaries:** $mx$ and $my$ are limited to 7 bits, restricting volume slices to $2^{15} \times 2^{15}$ voxels [S1, unofficial]. Larger volumes require a different encoding scheme.
*   **Degenerate Input:** $fx$ and $fy$ must be binary. Non-binary values will corrupt the packing [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Encoding is $O(1)$ per vertex. Decoding is $O(1)$ per vertex, potentially optimized with a lookup table [S1, unofficial].
*   **Memory Complexity:** Reduces vertex memory from 16 bytes (4 floats) to 4 bytes (1 uint32) per vertex [S1, unofficial].
*   **Measured Performance:** For a $256^3$ volume dataset, vertex memory is reduced from 2048M bytes to 12M bytes, a compression ratio of 171:1 [S1, unofficial].
*   **Strengths:** High compression ratio, fast decompression, suitable for hardware-accelerated rendering [S1, unofficial].
*   **Limitations:** Limited volume size ($2^{15} \times 2^{15}$), fixed Gaussian coordinate resolution (binary) [S1, unofficial].
*   **When to Use:** Hardware-accelerated volume splatting with proxy geometry where memory bandwidth is a bottleneck [S1, unofficial].
*   **When Not to Use:** Volumes larger than $2^{15} \times 2^{15}$ slices, or when higher precision for Gaussian coordinates is required [S1, unofficial].

## Background
Packed Vertex Attribute Encoding was introduced in the context of hardware-accelerated adaptive EWA volume splatting [S1, unofficial]. It was developed to address the memory bottleneck of storing vertex attributes for proxy geometry in volume rendering [S1, unofficial]. The method allows the volume texture data and packed proxy geometry information to be pre-loaded in the local memory of graphics hardware for interactive rendering [S1, unofficial].
