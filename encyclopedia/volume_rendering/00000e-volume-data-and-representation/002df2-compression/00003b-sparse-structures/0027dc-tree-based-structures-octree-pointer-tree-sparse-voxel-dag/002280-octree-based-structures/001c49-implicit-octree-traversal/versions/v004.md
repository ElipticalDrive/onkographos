# Implicit Octree Traversal
Also called: ImplicitOctree
## Overview
Implicit Octree Traversal is a method for building and traversing a sparse octree representation of a distance field to extract isosurfaces, specifically designed for dual contouring and marching cubes algorithms. It solves the problem of efficiently locating leaf nodes and retrieving adjacent "forward neighbor" voxels in a sparse volume representation, enabling the reconstruction of 2x2x2 cells required for isosurface intersection primitives. It sets itself apart from sibling methods like [Pointerless Octree for Seed Placement](5280-pointerless-octree-for-seed-placement.md) by focusing specifically on the bitwise arithmetic mapping for neighbor retrieval rather than seed placement, and differs from [Cell Retrieval via Neighbor-Finding](1822-cell-retrieval-via-neighbor-finding.md) by relying on direct coordinate hashing rather than geometric neighbor-finding techniques that skew toward O(1) only when neighbors share a parent [S1, S2, S3].

## How it works
**Inputs:**
- A distance field function or sampled data.
- Maximum octree depth $N$.

**Outputs:**
- A sparse octree structure containing distance values at leaf nodes.
- A collection of primal vertices mapped to their Morton keys and levels.
- A mesh generated via callbacks invoked for each 2x2x2 cube of neighboring leaf vertices.

**Data Structures:**
1.  **ImplicitOctree:** Contains `max_depth` (usize). Internally uses `LinearHashedOctree` for node storage.
2.  **primal_vertices:** A `HashMap<Morton, usize>` mapping Morton coordinates to their corresponding octree level.
3.  **Morton Key:** A 3D coordinate encoded into a 1D integer using Z-order curve (Morton code).

**Algorithm Steps:**

1.  **Initialization:**
    Create an `ImplicitOctree` with `max_depth` $N$. This defines a cubic grid with dimensions $2^N$ along each axis.

2.  **Collect Primal Vertices:**
    Initialize an empty `HashMap` named `primal_vertices`.
    Walk the leaves of the octree. For each leaf key:
    - Iterate $i$ from 0 to 7 (representing the 8 corners of the leaf cell).
    - Compute `vertex` = `key.primal_vertex(level, i)`. This function derives the Morton code of the primal vertex at corner $i$ for the given leaf level.
    - If `vertex` is not the null Morton key (`Morton::with_key(0)`):
        - Check if `vertex` exists in `primal_vertices`.
        - If it exists and the current `level` is greater than the stored `existing_level`, update the entry: `primal_vertices[vertex] = level`.
        - Otherwise, insert the entry: `primal_vertices[vertex] = level`.

3.  **Traverse Primal Vertices:**
    For each `(key, level)` pair in `primal_vertices`:
    - Iterate $i$ from 0 to 7.
    - Compute `m` = `key.dual_vertex(level, REMAP_CUBE[i])`. This computes the Morton code for the dual vertex associated with corner $i$, remapped according to `REMAP_CUBE`.
    - While `m` is greater than `Morton::new()` (null key):
        - Query the octree: `result = octree.get_node(&m)`.
        - If `result` returns `Some(distance)`:
            - Set `keys[i] = m`.
            - Set `corners[i] = m.center()`.
            - Set `values[i] = distance`.
            - Break the while loop.
        - If `result` returns `None`:
            - Set `m = m.parent()`. (Move to the parent node in the octree hierarchy).

**Formulas:**
- **Linear Interpolation for Crossing Point:**
  Given two points $P_a$ and $P_b$ with distance values $a$ and $b$:
  $$ \Delta = b - a $$
  $$ t = \begin{cases} 0.5 & \text{if } \Delta = 0.0 \\ -a / \Delta & \text{otherwise} \end{cases} $$
  $$ P_{cross} = P_a (1 - t) + P_b t $$

- **Directed Distance Field Crossing (Dominant Axis):**
  For directed distance fields, the crossing is computed along the dominant axis of the segment $P_a \to P_b$:
  $$ \text{axis} = \text{argmax}_d (|P_a.d - P_b.d|) $$
  $$ \Delta = b.\text{axis} - a.\text{axis} $$
  $$ t = \begin{cases} 0.5 & \text{if } \Delta = 0.0 \\ -a.\text{axis} / \Delta & \text{otherwise} \end{cases} $$
  $$ P_{cross} = P_a (1 - t) + P_b t $$

**Parameters:**
- `max_depth` ($N$): Typical values depend on the required resolution and volume size. Not given in the sources.

**Edge Cases and Pitfalls:**
- **Directed Distance Field:** Constructing an octree over a directed distance field is not fully implemented in the reference code; it requires specific handling for the dominant axis calculation [S1, unofficial].
- **Null Keys:** The algorithm checks against `Morton::with_key(0)` to identify invalid or empty nodes.
- **Precision:** Floating-point comparisons for distance values should account for epsilon if exact zero-crossing is critical.

**Pseudocode:**

```python
class ImplicitOctreeTraversal:
    def __init__(self, max_depth: int):
        self.max_depth = max_depth
        self.octree = LinearHashedOctree(max_depth)
        self.primal_vertices = {}  # HashMap<Morton, usize>

    def collect_primal_vertices(self):
        # Walk leaves of octree
        for leaf_key, leaf_level in self.octree.get_leaves():
            for i in range(8):
                vertex = leaf_key.primal_vertex(leaf_level, i)
                if vertex != Morton.with_key(0):
                    if vertex in self.primal_vertices:
                        existing_level = self.primal_vertices[vertex]
                        if leaf_level > existing_level:
                            self.primal_vertices[vertex] = leaf_level
                    else:
                        self.primal_vertices[vertex] = leaf_level

    def traverse_and_extract(self):
        keys = [None] * 8
        corners = [None] * 8
        values = [None] * 8

        for key, level in self.primal_vertices.items():
            for i in range(8):
                m = key.dual_vertex(level, REMAP_CUBE[i])
                while m > Morton.new():
                    node_data = self.octree.get_node(m)
                    if node_data is not None:
                        keys[i] = m
                        corners[i] = m.center()
                        values[i] = node_data.distance
                        break
                    else:
                        m = m.parent()
            # Invoke callback for the 2x2x2 cube defined by keys, corners, values
            self.invoke_callback(keys, corners, values)

    def find_crossing_point(self, a: float, b: float, p_a: Vec3, p_b: Vec3) -> Vec3:
        delta = b - a
        if delta == 0.0:
            t = 0.5
        else:
            t = -a / delta
        return p_a * (1.0 - t) + p_b * t

    def find_crossing_point_directed(self, a: Directed, b: Directed, p_a: Vec3, p_b: Vec3) -> Vec3:
        axis = (p_a - p_b).abs().max_component_index()
        delta = b.axis[axis] - a.axis[axis]
        if delta == 0.0:
            t = 0.5
        else:
            t = -a.axis[axis] / delta
        return p_a * (1.0 - t) + p_b * t
```

## Subtopics

### [Cell Reconstruction via Octree Hashing](1595-cell-reconstruction-via-octree-hashing.md)
Cell Reconstruction via Octree Hashing is a method for locating leaf nodes and retrieving adjacent "forward neighbor" voxels in a sparse octree volume representation, enabling the reconstruction of 2x2x2 cells required for isosurface intersection primitives. It solves the problem of needing 8 corner scalar values for a cell intersection when only 1 scalar value is stored per leaf node, by using a bitwise arithmetic hash scheme to map 3D coordinates to integer indices for O(log N) point location and O(1) average-case neighbor finding. It sets itself apart from sibling methods like [Pointerless Octree for Seed Placement](5280-pointerless-octree-for-seed-placement.md) by focusing specifically on the bitwise arithmetic mapping for neighbor retrieval rather than seed placement, and differs from [Cell Retrieval via Neighbor-Finding](1822-cell-retrieval-via-neighbor-finding.md) by relying on direct coordinate hashing rather than geometric neighbor-finding techniques that skew toward O(1) only when neighbors share a parent.

### [Pointerless Octree for Seed Placement](5280-pointerless-octree-for-seed-placement.md)
This method provides a memory-efficient, runtime mechanism for selecting seed points for volume hatching strokes, avoiding the pre-generation and storage of all potential seeds. It builds on [Implicit Octree Traversal](1220-implicit-octree-traversal.md) by using a hierarchical pyramid structure to dynamically determine where and how densely to place seeds based on local geometric properties (curvature and gradient). Unlike sibling methods that may reconstruct cells via hashing, this approach explicitly uses a pointerless octree to prune empty or planar regions early in the traversal.

## Operating characteristics
- **Time Complexity:** Point location is O(log N) where N is the number of nodes. Neighbor finding is O(1) average-case using the hash scheme [S1, S2, S3].
- **Memory Complexity:** Proportional to the number of non-empty leaf nodes. Uses a HashMap for primal vertices, which may introduce overhead compared to dense arrays.
- **Strengths:** Efficient handling of sparse data; avoids storing zero-valued voxels; enables adaptive resolution.
- **Limitations:** Directed distance field support is incomplete in the reference implementation [S1, unofficial]. HashMap lookups may have higher constant factors than array indexing.
- **When to Use:** Suitable for sparse volume data where isosurface extraction is required, particularly for dual contouring or marching cubes.
- **When Not to Use:** Dense volume data where a simple grid is more efficient; real-time applications requiring extremely low latency for neighbor lookups where hash overhead is prohibitive.

## Background
The method originates from the `isosurface` library by Tristam MacDonald, which implements dual contouring and marching cubes algorithms on sparse octrees [S1, unofficial]. It builds on the principles of implicit octree traversal and spatial hashing for efficient neighbor retrieval in sparse volumes.
