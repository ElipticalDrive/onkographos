# Cell Retrieval via Neighbor-Finding

Also called: 8-voxel cell intersection, Cell-based ray tracing, Forward-neighbor retrieval, Neighbor-Finding for Cell Retrieval, Neighbor-Finding on Octree, Octree Hashing, Octree Scalar Field Mapping via Forward Neighbors, voxel to cell mapping

## Overview
This method enables isosurface reconstruction (e.g., Marching Cubes) on sparse octree volumes that store only a single scalar value per leaf voxel, by logically mapping each voxel to the lower-left corner of an 8-voxel cell and retrieving the 7 forward neighbors at intersection time [S2]. It solves the storage explosion problem of explicitly storing full cells (which would require 8x the original data size) by performing neighbor-finding on the octree structure to assemble the required 8 corner values on the fly [S3]. It differs from [Cell Reconstruction via Octree Hashing](1595-cell-reconstruction-via-octree-hashing.md) in its specific application to the "forward-neighbor" retrieval pattern for cell-based primitives, and from [Octree Hashing for Point Location and Neighbor Finding](1984-octree-hashing-for-point-location-and-neighbor-finding.md) by focusing on the runtime assembly of the intersection primitive rather than just the point location mechanism itself [S5, unofficial].

## How it works

### Inputs and Outputs
*   **Input:** An octree structure where each leaf node stores a single scalar value $v$ at its center [S1]. A ray $\mathbf{r}(t) = \mathbf{o} + t\mathbf{d}$ intersecting the volume [G].
*   **Output:** A set of 8 scalar values corresponding to the corners of the 8-voxel cell containing the intersection point, used for isosurface reconstruction [S5, unofficial].

### Data Structures
The octree topology remains unchanged, but the scalar field is logically mapped to cells by shifting positions backward by half a voxel width [S1]. Interior nodes contain pointers to 8 children (octants) [G]. The spatial layout assumes a regular grid where voxel width is 1 unit [G]. The scalar field is defined at voxel centers [S6, unofficial].

### Logical Mapping and Coordinate Shift
To support cell-based intersection (where values are at corners), the field is logically shifted backward by half a voxel width [S3].
*   Let a leaf node be at integer grid coordinates $(i, j, k)$ [G].
*   This voxel is mapped to the minimum vertex (lower-left-front corner) of a cell [S6, unofficial].
*   The cell spans the range $[i, i+1] \times [j, j+1] \times [k, k+1]$ [G].
*   The 8 corners of this cell correspond to the 8 voxels with indices:
    $$ (i+\delta_x, j+\delta_y, k+\delta_z) $$
    where $\delta_x, \delta_y, \delta_z \in \{0, 1\}$ [G].
*   The target voxel is $(i, j, k)$ ($\delta_x=\delta_y=\delta_z=0$) [G].
*   The 7 forward neighbors are those where at least one $\delta$ is 1 [G].

### Algorithm Steps

1.  **Ray Traversal:** Traverse the octree using standard ray-triangle or ray-box intersection logic for interior nodes [S5, unofficial]. Identify the leaf node $L$ intersected by the ray [S5, unofficial]. Let the grid coordinates of $L$ be $(i, j, k)$ [G].
2.  **Target Value Retrieval:** Retrieve the scalar value $v_{0,0,0}$ stored in leaf $L$ [S2].
3.  **Neighbor-Finding:** For each of the 7 forward neighbor directions $(\delta_x, \delta_y, \delta_z) \in \{0,1\}^3 \setminus \{(0,0,0)\}$:
    *   Compute the target grid coordinates $(i+\delta_x, j+\delta_y, k+\delta_z)$ [G].
    *   Perform neighbor-finding on the octree to locate the leaf node at these coordinates [S2].
    *   Retrieve the scalar value $v_{\delta_x, \delta_y, \delta_z}$ from that leaf [S5, unofficial].
    *   **Edge Case:** Values outside the octree data are defined to be zero [S4, unofficial].
4.  **Cell Assembly:** Assemble the 8 values $\{v_{\delta_x, \delta_y, \delta_z}\}$ into the cell primitive [S5, unofficial].
5.  **Intersection:** Perform the isosurface intersection test (e.g., Marching Cubes) on the 8-voxel cell using the retrieved values [S5, unofficial].

### Pseudocode

```python
def retrieve_cell_values(octree_root, leaf_coords):
    """
    Retrieves the 8 scalar values for the cell defined by the target leaf.
    leaf_coords: tuple (i, j, k) of the intersected leaf node.
    Returns: list of 8 values [v_000, v_001, v_010, v_011, v_100, v_101, v_110, v_111]
    """
    i, j, k = leaf_coords
    values = []
    
    # Iterate through all 8 combinations of deltas (0 or 1)
    for dx in [0, 1]:
        for dy in [0, 1]:
            for dz in [0, 1]:
                # Compute neighbor coordinates
                ni, nj, nk = i + dx, j + dy, k + dz
                
                # Retrieve value from octree using point location
                val = point_location(octree_root, ni, nj, nk)
                values.append(val)
                
    return values

def point_location(node, x, y, z):
    """
    Performs recursive point location to retrieve the scalar value
    at grid coordinates (x, y, z). Returns 0.0 if the path does not exist.
    """
    if node.is_leaf:
        return node.scalar_value
    
    # Determine child index based on coordinate bits at current depth [G]
    depth = node.depth
    child_idx = ((x >> depth) & 1) << 2 | ((y >> depth) & 1) << 1 | ((z >> depth) & 1)
    
    if node.children[child_idx] is None:
        return 0.0
    return point_location(node.children[child_idx], x, y, z)
```

### Parameters and Typical Values
*   **Voxel Width:** 1 unit (logical) [G].
*   **Shift:** 0.5 units backward [S3].
*   **Out-of-Bounds Value:** 0.0 [S4, unofficial].

### Pitfalls and Edge Cases
*   **Boundary Conditions:** Neighbors may lie outside the octree. Values outside the octree data are defined to be zero [S4, unofficial].
*   **Complexity Skew:** While worst-case neighbor-finding is $O(\log N)$, it skews heavily toward $O(1)$ when neighbors reside in the same parent node [S3]. Implementations should optimize for this common case.
*   **Cache Performance:** Unlike 3D arrays where neighbor queries are trivial and typically cache-friendly, octree neighbor-finding is more intensive [S3].

### Subtopics
*   **Octree Hashing for Point Location and Neighbor Finding:** A specific hashing scheme using binary arithmetic on integer coordinates to accelerate point location and neighbor finding in regular binary trees [S6, unofficial]. It differs by focusing on the underlying hash mechanism for coordinate lookup, whereas Cell Retrieval focuses on the application of that lookup to assemble 8-voxel cells [S5, unofficial]. Choose when the octree is static and coordinate-based hashing is feasible [G]. Link: [Octree Hashing for Point Location and Neighbor Finding](1984-octree-hashing-for-point-location-and-neighbor-finding.md).
*   **Min/Max Tree Construction with Forward Neighbors:** A method to compute min/max pairs for interior nodes based on the min/max pairs of their 8 children, specifically for ray tracing cells defined by forward neighbors [S2]. It differs as an acceleration structure construction step that complements cell retrieval, allowing early ray termination [S2]. Choose when ray tracing performance is critical and the volume has significant empty space [G]. Link: [Min/Max Tree Construction with Forward Neighbors](2020-min-max-tree-construction-with-forward-neighbors.md).
*   **Neighbor Cell Access via Hash Table and Morton Code:** Uses Morton codes and hash tables to map voxel coordinates to values, enabling fast neighbor access [G]. It differs by using a flat hash table structure rather than a hierarchical octree pointer structure for neighbor lookup [G]. Choose when memory layout favors flat arrays and Morton code generation is efficient [G]. Link: [Neighbor Cell Access via Hash Table and Morton Code](6715-neighbor-cell-access-via-hash-table-and-neighbor-finding.md).

## Operating characteristics

*   **Time Complexity:** Worst-case $O(\log N)$ per neighbor lookup, where $N$ is the number of leaf nodes. In practice, it skews heavily toward $O(1)$ when neighbors are in the same parent node [S3].
*   **Memory Complexity:** No additional storage for neighbor data (unlike the 8x expansion alternative) [S1].
*   **Performance:** Neighbor-finding on octrees is more intensive than array indexing ($O(1)$, cache-friendly) [S3]. It must compete with the performance of uncompressed 3D array lookups [S3].
*   **Strengths:** Allows ray tracing of compressed sparse data without expanding storage. Enables traversal of interior nodes while intersecting well-defined cell primitives [S1].
*   **Limitations:** Higher computational cost per intersection compared to dense grids [S3].
*   **When to use:** When storage is a constraint and the volume is sparse [S1].
*   **When not to use:** When the volume is dense and fits in memory, or when cache performance is critical and the overhead of neighbor-finding outweighs the benefits of sparsity [S3].

## Background

*   **Origin:** The concept of mapping voxels to cells for isosurface reconstruction in octrees was introduced by Parker et al. [15, 17, 18] in the context of interactive isosurface ray tracing of large octree volumes [S1, S2, S3][S4, unofficial].
*   **History:** Point location and neighbor-finding algorithms were pioneered by Glassner [32] and Samet [105] in ray tracing [S6, unofficial]. Frisken and Perry [26] proposed an efficient hashing scheme using binary arithmetic on integer coordinates, which later works built upon [S6, unofficial].
*   **Usage:** Used in interactive isosurface ray tracing of large volumes, particularly where compression is a goal [S1, S2, S3][S4, unofficial].
