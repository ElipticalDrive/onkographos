# Cell Reconstruction via Octree Hashing

Also called: Frisken and Perry hashing scheme, Octree Hashing Scheme

## Overview
Cell Reconstruction via Octree Hashing is a method for locating leaf nodes and retrieving adjacent "forward" neighbor voxels in a sparse octree volume representation, enabling isosurface reconstruction from scalar data stored with only one value per leaf voxel [S1, unofficial][S2, S3]. It solves the problem of needing 8 corner values for a cell intersection primitive when only 1 scalar value is stored per leaf node by retrieving the 7 forward neighbors at intersection time [S2, S3]. Unlike [Cell Retrieval via Neighbor-Finding](1822-cell-retrieval-via-neighbor-finding.md), which relies on neighbor-finding techniques that skew heavily toward O(1) performance when neighbors share a parent node, this method uses a bitwise arithmetic hash scheme for point location, allowing point location from the root in O(log N) time [S1, unofficial][S2, S3].

## How it works
**Inputs and Outputs:**
*   **Input:** 3D integer coordinates $(x, y, z)$ representing a voxel center or corner, and the root of the sparse octree.
*   **Output:** The leaf node containing the coordinate, or the set of 7 forward neighbor leaf nodes required to define the 2x2x2 cell for intersection testing.

**Data Structures:**
The method operates on an implicit octree where nodes are identified by their spatial position. The key data structure is the coordinate mapping, which maps each octree node to a point $P$ in the interval $[0, 2^{d_{max}}]^3$ using bitwise arithmetic [S2]. The octree depth is bounded by $d_{max}$.

**Steps:**

1.  **Coordinate Mapping:** Map the 3D integer coordinates $(x, y, z)$ to a single integer key or a structured bit pattern suitable for hashing. This involves interleaving the bits of the X, Y, and Z coordinates.
2.  **Point Location:** To find the leaf node for a given coordinate:
    *   Start at the octree root.
    *   Determine the octant index by performing a bitwise-AND with a left-shifted mask on the interleaved coordinates [S2].
    *   Traverse to the corresponding child.
    *   Repeat until a leaf node is reached. This process takes $O(\log N)$ time in the worst case, where $N$ is the number of nodes [S2].
3.  **Neighbor Finding:** To find a neighbor given an origin leaf and a destination direction:
    *   Find the nearest common ancestor (NCA) of the origin leaf and the target neighbor location [S2].
    *   Perform point location from the NCA to the target leaf [S2].
    *   Retrieve the scalar values from the 7 forward neighbors. A "forward" neighbor is defined relative to the cell being reconstructed; for a leaf at $(x,y,z)$, the neighbors are those at $(x+1,y,z), (x,y+1,z), \dots, (x+1,y+1,z+1)$ [S3].

**Formulas:**
*   **Octant Index:** $i = (x \& M_x) | (y \& M_y) | (z \& M_z)$, where $M_x, M_y, M_z$ are masks derived from the current depth level, and the bits are interleaved [S2].
*   **Complexity:** Worst-case neighbor finding is $O(\log N)$; best-case and average-case are $O(1)$ when neighbors share a parent node [S2].

**Parameters:**
*   $d_{max}$: The maximum depth of the octree. Structures start at $d_{max}-1$ for cap nodes [S2].

**Pitfalls:**
*   **Precision:** Integer coordinates must be handled carefully to avoid overflow when interleaving bits for large $d_{max}$.
*   **Boundaries:** Neighbor finding must handle edge cases where neighbors lie outside the defined volume bounds [S2].
*   **Optimization:** Precompute masks and use constant interleaving for interactivity to avoid expensive arbitrary left-shifts during traversal [S2].

**Pseudocode:**

    """
    Finds the leaf node at integer coordinates (x, y, z).

    node = root
    for depth in range(d_max, -1, -1):
        # Interleave bits of x, y, z for the current depth level
        # Mask to get the relevant bits for this octant
        mask = 1 << depth
        # Determine octant index using bitwise operations
        # This assumes a standard Morton-like interleaving or specific hash scheme
        # Simplified: using bitwise AND with shifted masks
        octant = 0
        if (x >> depth) & 1: octant |= 1
        if (y >> depth) & 1: octant |= 2
        if (z >> depth) & 1: octant |= 4
        
        if node.is_leaf:
            return node
        if node.children[octant] is None:
            return None # Not found
        node = node.children[octant]
    return node

## Subtopics

### Min/Max Tree Construction with Forward Neighbors
A bounding volume hierarchy built on the octree where each node stores the min/max of the isosurface values within its spatial extent [S3]. Because cells are defined by forward neighbors, the min/max for a node must consider not just its 8 children, but also their forward neighbors [S3]. To compute the min/max tree: for leaf nodes, compute the min/max of the 8-voxel cell (current voxel + 7 forward neighbors); for interior nodes, compute the min/max of the min/max pairs of all 8 children, effectively considering 27 voxel values for each parent node's bounding box [S3]. Storage overhead is approximately 22% additional footprint on top of raw scalar octree-compressed data, achieved by computing extrema temporarily at leaf nodes and storing the min/max tree starting at depth $d_{max}-1$ [S3]. Storing min/max pairs for every scalar voxel would demand over three times the storage of the raw octree data; to avoid this, min/max pairs are omitted at leaf nodes and computed on the fly during neighbor lookup [S3].

## Operating characteristics
*   **Time Complexity:** Point location is $O(\log N)$ in the worst case. Neighbor finding is $O(\log N)$ in the worst case (when finding distant neighbors) but $O(1)$ in the best and average cases (when neighbors share a parent node) [S2].
*   **Memory Complexity:** The base octree stores one scalar per leaf. The Min/Max Tree variant adds ~22% overhead [S3].
*   **Strengths:** Efficient point location and neighbor retrieval without explicit parent pointers; suitable for interactive ray tracing [S1, unofficial][S2].
*   **Limitations:** Worst-case neighbor finding is slower than methods that guarantee O(1) via spatial locality assumptions; requires careful handling of boundary conditions [S2].
*   **When to use:** When memory is constrained and the octree is sparse, and interactive performance is required [S1, unofficial].
*   **When not to use:** When the octree is dense or when neighbor access patterns are highly irregular and distant [S2].

## Background
Point location and neighbor-finding algorithms were pioneered by Glassner [6] and Samet [17] for use in ray tracing [S1, unofficial]. Frisken and Perry [4] proposed an efficient hashing scheme using binary arithmetic on integer coordinates, which serves as the foundation for this method [S1, unofficial]. The method was further optimized for interactive isosurface ray tracing of large octree volumes [S1, unofficial][S2].
