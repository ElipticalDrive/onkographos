# NanoVDB Linear Representation

Also called: Linear VDB, NanoVDB, NanoVDB Museth, Open-VDB GPU Port, VDB / NanoVDB

## Overview
NanoVDB is a linear, GPU-optimized implementation of the OpenVDB sparse voxel structure [S1]. It solves the problem of efficiently transferring and sampling large, sparse volumetric datasets on the GPU by eliminating CPU-dependent memory pointers and enabling compact memory copying via `memcpy` [S1]. Unlike its parent [OpenVDB (VDB)](1508-openvdb-vdb.md), which supports complex runtime modifications, NanoVDB is designed as an immutable "linear snapshot" optimized strictly for fast retrieval and on-the-fly decompression during rendering [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** An OpenVDB grid containing sparse voxel data [S1].
*   **Output:** A contiguous, 32-byte aligned block of memory representing the linearized VDB structure, ready for GPU transfer [S1][S2, unofficial].

**Data Structures and Layout:**
The NanoVDB structure is a linearized, pointer-free snapshot of the OpenVDB tree [S1]. The underlying topology is a shallow B+tree with an unbounded root, internal nodes of size $32^3$ and $16^3$, and leaf nodes of size $8^3$ [S3]. Each node entry stores either a pointer to a child node or a constant "tile" value [S3]. To ensure GPU compatibility, the entire tree topology and data are serialized into a single continuous memory block [S2, unofficial]. The layout is strictly 32-byte aligned [S1].

**Steps for Conversion and Usage:**
1. **Compression & Quantization:** Apply variable bit-rate quantization to leaf values, followed by dithering to randomize quantization noise, reducing memory footprint by 4–6× compared to OpenVDB [S2, unofficial].
2. **Linearization:** Convert the OpenVDB grid to NanoVDB using builtin tools, which removes CPU pointers and linearizes the tree structure [S1].
3. **Transfer:** Copy the resulting linear memory block to GPU global memory using standard memory copy operations (e.g., `cudaMemcpy`) [S1].
4. **Sampling:** On the GPU, instantiate accessor and sampler classes to retrieve voxel data [S1]. Samplers support 0th-order (nearest neighbor) and 1st-order (trilinear) interpolation, with optional support for up to 3rd-order interpolation and gradient computation [S1].

**Pseudocode:**
```python
def convert_and_transfer(openvdb_grid):
    # 1. Quantize leaf values with variable bit-rate
    quantized = [int(round(v / step)) for v in openvdb_grid.leaves] # [S2, unofficial]
    # 2. Dither to randomize quantization noise
    dithered = [v + (random.random() - 0.5) for v in quantized] # [S2, unofficial]
    # 3. Serialize tree topology and data into contiguous memory
    buffer = openvdb_grid.topology.serialize(dithered) # [S1][S2, unofficial]
    # 4. Align to 32-byte boundary
    pad = (32 - (len(buffer) % 32)) % 32
    aligned_buffer = buffer + bytes(pad) # [S1]
    # 5. Allocate GPU memory and copy linear buffer
    gpu_ptr = allocate_gpu_memory(len(aligned_buffer)) # [G]
    for i in range(len(aligned_buffer)):
        gpu_ptr[i] = aligned_buffer[i] # [G]
    return gpu_ptr

def sample_on_gpu(gpu_ptr, ray_origin, order=1):
    # 1. Create accessor from GPU pointer
    accessor = create_accessor_from_ptr(gpu_ptr) # [G]
    # 2. Create sampler with interpolation order (0-3)
    sampler = create_sampler(accessor, order) # [G]
    # 3. Sample voxel value
    value = sampler.sample(ray_origin) # [S1]
    # 4. Compute gradient if order > 0
    gradient = sampler.compute_gradient(ray_origin) if order > 0 else None # [S1]
    return value, gradient
```

**Edge Cases and Pitfalls:**
*   **Modification:** NanoVDB does not support arbitrary modification; it is optimized for retrieval/sampling only [S1]. Modification support is rudimentary and essentially limited to altering the values of voxels that are already in the VDB and are active [S1].
*   **Immutability:** Once converted, the NanoVDB representation is immutable [S1].
*   **Topology Assumption:** The tree topology must be static, as the entire tree is serialized into a single continuous block of memory [S2, unofficial].

## Subtopics

### [NanoVDB Volume Loading and GPU Transfer](4997-nanovdb-volume-loading-and-gpu-transfer.md)
Describes reading a NanoVDB volume file, validating data types, and transferring raw voxel data to GPU memory. It bridges the CPU-side linear representation to GPU compute buffers for ray marching or splatting. It is distinct from general VDB loading because it operates directly on the contiguous memory layout, enabling `memcpy`-style transfers without CPU-side tree traversal.

## Operating characteristics
*   **Time Complexity:** Retrieval is optimized for GPU execution, leveraging on-the-fly decompression [S1].
*   **Memory Complexity:** Compact representation due to variable bit-rate quantization, reducing memory footprint by 4–6× relative to OpenVDB [S2, unofficial].
*   **Performance:** Fast, low-overhead retrieval suitable for Monte Carlo path tracing and real-time contexts [S1].
*   **Strengths:** Drop-in replacement for 3D texture-based renderers; significantly reduces memory requirements; compatible with CUDA and other GPGPU languages [S1].
*   **Limitations:** No arbitrary modification; requires CPU-side conversion step; assumes static tree topology [S1][S2, unofficial].

## Background
NanoVDB was introduced by Museth [Mus21] as NVIDIA's linear VDB implementation [S1]. It adapts the shallow B+tree design of OpenVDB, which is conceptually similar to an extended brickmap, for GPU ray tracing [S3]. The representation is primarily aimed at simulation and film volumes rather than interactive game editing [S3]. It bridges the authoring capabilities of OpenVDB with the performance requirements of GPU-based volume rendering [S1].
