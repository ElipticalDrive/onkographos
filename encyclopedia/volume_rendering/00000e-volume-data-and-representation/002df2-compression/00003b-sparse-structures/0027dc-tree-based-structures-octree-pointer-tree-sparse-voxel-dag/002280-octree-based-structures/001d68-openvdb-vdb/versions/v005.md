# OpenVDB (VDB)
Also called: OpenVDB Hierarchical Compression, VDB

## Overview
OpenVDB is a sparse voxel representation used for the hierarchical encoding and compression of volumetric grids, featuring fast $O(1)$ random access for both modification and retrieval operations [S1]. It solves the problem of managing large, sparse volumetric datasets (such as those from fluid simulations) by providing a shallow, four-level tree structure that balances compression with efficient random access [S1]. Unlike implicit octree variants that rely on complex traversal logic or fixed-rate compression, OpenVDB uses explicit 64-bit direct access bit masks at every level to encode topology and representative values, enabling fast runtime modifications and out-of-core streaming [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D volumetric domain (typically axis-aligned bounding box) and a set of voxel values.
*   **Output:** An in-memory tree structure consisting of root, internal (tile), and leaf nodes, along with associated bit masks and data pointers.

**Data Structures:**
The structure is a shallow tree with exactly four levels [S1]. Each node stores a 64-bit direct access bit mask [S1].

1.  **Root Level:**
    *   Contains a variable number of children [S1].
    *   The 64-bit mask encodes the presence and ID of child nodes [S1].
2.  **Internal Nodes (Tiles):**
    *   Have a fixed number of child nodes [S1].
    *   The 64-bit mask encodes the child ID or other representative values for the entire tile [S1].
3.  **Leaf Nodes:**
    *   Store a fixed number of voxels. The default configuration is $8 \times 8 \times 8$ voxels per leaf [S1].
    *   The 64-bit mask encodes the leaf origin using $3 \times 20$ bits (60 bits total) [S1].
    *   Remaining bits in the mask encode additional metadata, such as compression or quantization status [S1].
    *   The leaf node contains a separate bit mask indicating which voxels are active [S1].
    *   The leaf node contains a raw pointer to the voxel data array [S1].

**Algorithm Steps:**
1.  **Initialization:** Define the global bounding box and the leaf size (default $8^3$) [S1].
2.  **Subdivision:** Recursively subdivide the domain. If a region is empty or meets a homogeneity criterion, create a leaf node. Otherwise, create an internal node [S1].
3.  **Mask Construction:**
    *   For **Root** and **Internal** nodes: Construct the 64-bit mask to map child indices to their existence or representative values [S1].
    *   For **Leaf** nodes: Construct the 64-bit mask to store the 3D origin coordinates ($3 \times 20$ bits) and metadata flags [S1].
4.  **Data Storage:**
    *   For **Leaf** nodes: Store the active voxel mask and allocate memory for the voxel values, linking them via a raw pointer [S1].
5.  **Access:** Use the 64-bit masks at each level to perform direct random access to children or leaf data, bypassing pointer chasing for topology [S1].

**Pseudocode:**
```python
# Pseudocode for accessing a value in an OpenVDB grid
# Assumes a 4-level tree: Root -> Internal -> Internal -> Leaf

def get_value(root_node, x, y, z, leaf_size=8):
    """
    Retrieves the voxel value at (x, y, z) from the OpenVDB structure.
    """
    # Level 1: Root
    # The root mask provides direct access to the first internal node.
    # The mask encodes child IDs. We must decode the child index from the global coordinate.
    # Note: Exact decoding logic depends on the specific root mask encoding,
    # but it generally maps the coarse coordinate to a child index.
    root_child_idx = decode_root_mask(root_node.mask, x, y, z)
    internal_node_1 = root_node.children[root_child_idx]

    # Level 2: Internal (Tile)
    # The internal mask encodes child ID or representative values.
    # We decode the next level child index.
    internal_child_idx = decode_internal_mask(internal_node_1.mask, x, y, z)
    internal_node_2 = internal_node_1.children[internal_child_idx]

    # Level 3: Internal (Tile)
    # Decode the leaf node index.
    leaf_idx = decode_internal_mask(internal_node_2.mask, x, y, z)
    leaf_node = internal_node_2.children[leaf_idx]

    # Level 4: Leaf
    # The leaf mask contains the origin (3x20 bits).
    # We verify the coordinate is within this leaf's bounds.
    leaf_origin = decode_leaf_origin(leaf_node.mask)
    
    # Calculate local coordinate within the leaf
    local_x = x - leaf_origin.x
    local_y = y - leaf_origin.y
    local_z = z - leaf_origin.z

    # Check if the voxel is active using the leaf's active mask
    if not is_active(leaf_node.active_mask, local_x, local_y, local_z):
        return None # Or background value

    # Retrieve value from the raw pointer
    voxel_data = leaf_node.data_pointer
    return voxel_data[local_z * leaf_size * leaf_size + local_y * leaf_size + local_x]

# Helper functions would decode the 64-bit masks.
# For example, decode_root_mask might use bit shifts to extract child indices
# based on the spatial position.
```

**Parameters:**
*   **Leaf Size:** Default is $8 \times 8 \times 8$ voxels [S1].

**Edge Cases and Pitfalls:**
*   **Precision:** The leaf origin is stored in $3 \times 20$ bits. This limits the maximum coordinate range representable within a single leaf's metadata if not handled carefully, though the hierarchical structure mitigates this by storing origins relative to the tree level [S1].
*   **Memory Layout:** The use of raw pointers means the data is not contiguous in memory across the entire grid, which can impact cache performance if not accessed in a locality-aware manner [S1].

## Operating characteristics
*   **Time Complexity:** Random access and modification are $O(1)$ [S1]. Traversal depth is fixed at 4 levels [S1].
*   **Memory Complexity:** Scales with the number of active voxels and the tree structure overhead (masks and pointers). Compression is achieved by storing only active regions and using representative values in internal nodes [S1].
*   **Performance:** Well-suited for visual effects rendering of fluid simulations [S1]. Fast access allows for out-of-core streaming [S1].
*   **Strengths:** Fast random access, runtime modification support, integration with production tools (Houdini, Cycles) [S1].
*   **Limitations:** Data remains in CPU address space in the base OpenVDB format, requiring explicit transfer mechanisms (like NanoVDB) for GPU rendering [S1].

## Background
OpenVDB was introduced by Museth [Mus13] as an open-source library for hierarchical encoding and compression of volumetric grids. It is popular in production rendering and industry-strength libraries, particularly for NVIDIA GPU optimization [S1]. It is widely used in visual effects software such as Houdini [Sid25] and Cinema, and integrated into renderers like Cycles [Ble24]. The structure is noted for its similarity to B+ trees [Mus13].
