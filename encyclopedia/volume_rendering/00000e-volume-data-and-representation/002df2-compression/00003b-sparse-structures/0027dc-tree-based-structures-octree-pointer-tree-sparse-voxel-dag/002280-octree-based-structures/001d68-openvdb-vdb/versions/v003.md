# OpenVDB (VDB)

Also called: OpenVDB Hierarchical Compression, VDB

## Overview
OpenVDB is a sparse voxel representation designed for the hierarchical encoding and compression of volumetric grids, enabling fast $O(1)$ random access for both modification and retrieval [S1]. It solves the problem of managing large, sparse volumetric datasets (such as those from fluid simulations) by providing a shallow, four-level tree structure that supports efficient in-memory manipulation and out-of-core streaming [S1]. Unlike deep recursive octrees, OpenVDB uses fixed-size leaf nodes and direct-access bitmasks at every level to minimize traversal overhead, making it a standard in production rendering and visual effects software [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D volumetric grid (dense or sparse) with associated scalar or vector values per voxel.
*   **Output:** A four-level tree structure consisting of a root node, internal nodes (tiles), and leaf nodes, along with compressed voxel data.

**Data Structures:**
The structure is a shallow tree with exactly four levels [S1].
1.  **Root Node:** Has a variable number of children.
2.  **Internal Nodes (Tiles):** Have a fixed number of child nodes.
3.  **Leaf Nodes:** Store a fixed number of voxels. The default leaf size is $8 \times 8 \times 8$ voxels [S1].

At each level, the structure stores a 64-bit direct access bit mask. This mask provides direct random access to the binary representation of the local topology [S1].

**Bit Mask Layout:**
The 64-bit mask encodes different information depending on the tree level [S1]:
*   **Internal Nodes (Tiles):** The bit mask encodes the child ID or other representative values for the entire tile [S1].
*   **Leaf Nodes:** The bit mask encodes the leaf origin using $3 \times 20$ bits. Other bits encode additional metadata, such as whether the voxels are compressed or quantized. Additionally, leaf nodes contain a separate bit mask indicating which voxels are active, and a raw pointer to the voxel data itself [S1].

**Algorithm Steps:**
1.  **Grid Construction:** Initialize the root node. Subdivide the 3D domain recursively until the desired depth (4 levels) is reached or a stopping criterion is met.
2.  **Leaf Population:** For each leaf node, populate the $8 \times 8 \times 8$ voxel grid. If the data is sparse, mark inactive voxels in the leaf's active bit mask.
3.  **Mask Generation:**
    *   For internal nodes, generate the 64-bit mask encoding the child ID or representative value.
    *   For leaf nodes, generate the 64-bit mask encoding the origin ($3 \times 20$ bits) and metadata, plus the active voxel bitmask.
4.  **Pointer Assignment:** Assign a raw pointer from each leaf node to its associated voxel data array [S1].
5.  **Compression (Optional):** Apply lossy or lossless compression to the voxel data and metadata before storage or transmission [S1].

**Parameters:**
*   **Leaf Size:** Default is $8 \times 8 \times 8$ voxels [S1].
*   **Tree Depth:** Fixed at 4 levels [S1].

**Edge Cases and Pitfalls:**
*   **Memory Visibility:** The data structure prevails in address spaces visible to the CPU. Direct GPU access requires conversion to a linear representation (e.g., NanoVDB) or careful pointer management [S1].
*   **Precision:** The use of 64-bit masks limits the number of children per internal node to 64. If the branching factor exceeds this, the structure must adjust leaf sizes or depth, though OpenVDB fixes the depth at 4 [S1].

## Subtopics

### [VDB Volume Rendering with OpenVDB/NanoVDB](804-vdb-volume-rendering-with-openvdb-nanovdb.md)
Enables GPU volume rendering of large, sparse datasets by combining offline CPU compression with fast GPU decompression. It uses a uniform majorant grid for traversal, differing from hierarchical space-skipping methods.

### [NanoVDB Linear Representation](1527-nanovdb-linear-representation.md)
A linear, GPU-optimized implementation of OpenVDB. It eliminates CPU pointers for compact memory copying and immutable fast retrieval, unlike the mutable CPU-centric OpenVDB.

### [VDB 3-4-5 Tree Traversal](4996-vdb-3-4-5-tree-traversal.md)
Retrieves leaf data from OpenVDB files stored in compressed texture atlases using a 3-4-5 tree topology. It differs from standard OpenVDB by using texture atlases instead of explicit pointers.

### [OpenVDB File Format Parsing](5173-openvdb-file-format-parsing.md)
Parses binary OpenVDB files to reconstruct the hierarchical tree in memory. It focuses on data loading rather than rendering traversal.

## Operating characteristics
*   **Time Complexity:** Random access and modification are $O(1)$ due to the shallow tree and direct-access bitmasks [S1].
*   **Memory Complexity:** Scales with the sparsity of the data. Empty regions are represented by single nodes or null pointers, providing compression proportional to sparsity [S1].
*   **Performance:** Well-suited for visual effects rendering of fluid simulations. The shallow tree structure minimizes traversal overhead [S1].
*   **Strengths:** Fast $O(1)$ random access, out-of-core streaming support, and integration with production tools (Houdini, Cycles) [S1].
*   **Limitations:** Data resides in CPU-visible address space, requiring conversion for efficient GPU rendering. The fixed 4-level depth may not be optimal for all resolution ranges [S1].

## Background
OpenVDB was introduced by Ken Museth in a paper that established the sparse voxel representation for volumetric grids [S1]. It has become popular in production rendering and industry-strength libraries, particularly for NVIDIA GPU optimization [S1]. The library is well-established due to its integration into visual effects software like Houdini and Cinema, and production renderers like Cycles [S1].
