# Sparse GPU Volume Data Structure with JIT Compilation

Also called: JIT Compiled Search Tree, JiTTree, JiTTree Hybrid Data Structure, Just-in-Time Compiled Sparse GPU Volume Data Structure

## Overview
JiTTree is a sparse hybrid volume data structure that combines multiple elemental data structures (empty, voxel list, octree, dense) to minimize memory consumption while using just-in-time (JIT) compilation to generate GPU code tailored to a specific dataset [S1, unofficial]. It solves the problem of increased traversal overhead inherent in conventional hybrid structures by inlining access logic and removing dead code at runtime, shifting the burden from the GPU's memory cache to the instruction cache [S1, unofficial]. Unlike its siblings, which suffer from branch divergence and pointer-chasing overhead when mixing elemental types, JiTTree's traversal overhead depends on the homogeneity of the dataset rather than the number of elemental structures used [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D volume dataset, a set of candidate brick sizes $m$ (powers of two), and optimization criteria (memory, performance, or combined) [S1, unofficial].
*   **Output:** A JIT-compiled OpenCL kernel containing specialized traversal code and the memory layout for the optimal hybrid data structure [S1, unofficial].

**Data Structures:**
The volume is decomposed into bricks of size $m^3$. Each brick is assigned one of four elemental node types based on local sparsity [S1, unofficial]:
1.  **Empty:** Omitted from storage; requires zero memory [S1, unofficial].
2.  **Voxel List:** Stores sparse data as a list of quadruples $(x, y, z, \text{value})$. Coordinates are 2-byte integers; values are stored in a separate buffer. The list is sorted in Morton order [S1, unofficial].
3.  **Pointer Octree:** A modified octree where leaf nodes store 8 data values (block size $2^3$) instead of single scalars. Internal nodes store 8 pointers. This reduces overhead to $\sim 1/6$ pointer per data entry for a full octree [S1, unofficial].
4.  **Dense Volume:** A Cartesian grid storing $m^3$ values per brick [S1, unofficial].

**Root Level Layout:**
The root level is an array of nodes. Each node stores a tuple `(type, pointer)` [S1, unofficial].
*   `type`: Enum identifying the elemental structure (empty, voxel list, octree, dense) [S1, unofficial].
*   `pointer`: Two 4-byte integers. The interpretation depends on the type:
    *   **Dense:** Pointer into the global dense volume array. Size is $m^3 \times N_{dense}$ [S1, unofficial].
    *   **Voxel List:** Pointer to the last element in a global list offset array. Access requires binary search on Morton-sorted coordinates [S1, unofficial].
    *   **Octree:** Pointer to the root of the subtree in a global octree pointer array. Leaf values are in a separate memory region [S1, unofficial].
    *   **Empty:** Null pointer [S1, unofficial].

**Algorithm Steps:**

1.  **Brick Classification:** Divide the volume into bricks of size $m^3$. For each brick, determine the optimal elemental node type by comparing memory requirements for all four types. Select the type with the minimum memory footprint [S1, unofficial].
2.  **Global Optimization:** Repeat Step 1 for all candidate brick sizes $m$. Select the global minimum across all sizes as the memory-optimal solution [S1, unofficial].
3.  **KD-Tree Construction:** Build a KD-tree to index the elemental bricks. Split the set of bricks at brick boundaries into large homogeneous regions containing only one elemental type. The splitting criterion maximizes information gain (minimizes entropy $E$ of brick types in a region $S$) [S1, unofficial].
4.  **JIT Code Generation:** Transform the KD-tree and the root-level data into a single OpenCL kernel.
    *   Inline the comparison logic from the KD-tree nodes directly into the code, eliminating memory fetches for node keys [S1, unofficial].
    *   Perform dead code removal: Remove branches corresponding to elemental types not present in the optimal structure (e.g., if no voxel lists exist, remove voxel list traversal code) [S1, unofficial].
    *   Implement empty space skipping: Use a simplified kd-restart algorithm. When an empty brick is hit, advance the ray to the most distant point on the empty brick's bounding box [S1, unofficial].
    *   (Optional) Implement a software stack cache for regular access patterns to benefit ray traversal for small work group sizes [S1, unofficial].
5.  **Data Initialization:**
    *   Initialize voxel lists on the GPU using histogram pyramids, ensuring Morton order sorting [S1, unofficial].
    *   Generate octree nodes using a variant of OcPyramids (combining multiple histogram pyramids) [S1, unofficial].

**Pseudocode:**
The following pseudocode illustrates the JIT-compiled search logic for a simplified binary search tree example provided in the source, demonstrating the elimination of memory fetches for node keys [S1, unofficial].

```python
# JIT-compiled find function
# The tree structure and keys are hardcoded into the control flow.
# k is the lookup key, assumed to exist in the tree.
def jit_find(k):
    # Compare key to root key (106)
    if k < 106:
        # Traverse left subtree
        if k < 8:
            # Traverse left-left subtree
            if k < 4:
                return 0
            elif k > 4:
                return 2
            else:
                return 1
        else:
            # Traverse left-right subtree
            if k < 13:
                return 4
            elif k > 13:
                return 6
            else:
                return 5
    else:
        # Traverse right subtree
        # Code omitted for brevity, follows similar pattern
        # ...
        return 7
```

For the full JiTTree, the generated kernel replaces the recursive `find(key, node)` calls with this flattened, data-dependent conditional logic, routing lookups to specialized functions for each elemental type [S1, unofficial].

**Parameters:**
*   $m$: Side length of a data block (brick). Must be a power of two [S1, unofficial].
*   $n$: Number of non-zero elements inside a data block [S1, unofficial].
*   $d$: Size of one data entry in bits [S1, unofficial].
*   $p$: Pointer size, sufficiently large to address elements [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Compiler Limits:** JIT compilation is limited to 32,768 leaf nodes due to OpenCL compiler capabilities. Higher node counts cause inconsistent compile times [S1, unofficial].
*   **Missing Keys:** The simplified pseudo-code assumes the lookup key exists. If the key is missing, behavior is undefined or requires additional handling not shown in the core logic [S1, unofficial].
*   **Ray Casting Performance:** The JIT approach performs poorly for ray casting on large datasets with high brick counts due to branch divergence from ray access patterns, unlike stencil access patterns in mean filtering [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Traversal overhead depends on the homogeneity of the dataset rather than the number of elemental structures [S1, unofficial]. The number of leaf nodes in the JIT-generated KD-tree does not grow linearly with the number of bricks because bricks of the same type are grouped [S1, unofficial].
*   **Memory Complexity:** The structure never exceeded three times the size of the theoretical lower bound solution in experiments [S1, unofficial]. Overhead ranges from 1.8 to 27.7 bits per non-zero voxel, broader than perfect spatial hashing (3-7 bits) but applicable to higher densities [S1, unofficial].
*   **Measured Performance:** Tested on NVIDIA GeForce GTX TITAN X, Intel Core i7-4770K @ 3.50 GHz, 16 GB RAM, 768x768 resolution [S1, unofficial].
    *   Mean Filtering: Average speedup of 1.29x over direct volume bricking; highest speedup 1.79x (Stag Beetle, brick size $32^3$) [S1, unofficial].
    *   Degradation: Performance decrease by factor 0.96 observed for Kingsnake dataset with brick size $128^3$ [S1, unofficial].
    *   Compilation Time: For Connectomics dataset ($1024^3$, 32,768 bricks, 2,148 leaves, max branch depth 22), KD-tree generation took 1085.25 ms and OpenCL compilation took 78,306 ms [S1, unofficial].
*   **Strengths:** Superior memory usage for datasets with locally varying sparsity; reduces traversal overhead by eliminating pointer chasing and dead code [S1, unofficial].
*   **Limitations:** Poor performance for ray casting on large, heterogeneous datasets due to branch divergence; limited by compiler leaf node count (32,768) [S1, unofficial].
*   **When to Use:** Mean filtering (stencil access) on sparse GPU volumes with moderate brick counts.
*   **When Not to Use:** Ray casting on large datasets with high brick counts or when exceeding compiler leaf node limits [S1, unofficial].

## Background
JiTTree is based on partial evaluation of programs described by Jones et al. and data-aware compilation approaches by Rompf et al. and Sujeeth et al. [S1, unofficial]. It is the first volumetric data structure to simultaneously adapt memory layout and traversal code in a just-in-time manner [S1, unofficial]. The work was published in 2015/2016 [S1, unofficial].
