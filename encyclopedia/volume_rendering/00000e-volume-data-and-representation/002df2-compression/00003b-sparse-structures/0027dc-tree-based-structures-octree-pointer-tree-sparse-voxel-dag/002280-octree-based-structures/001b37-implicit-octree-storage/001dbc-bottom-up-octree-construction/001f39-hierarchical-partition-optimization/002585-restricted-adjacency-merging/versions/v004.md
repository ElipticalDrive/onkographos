# Restricted Adjacency Merging

Also called: Brother/Nephew Merging

## Overview
Restricted Adjacency Merging is a topological optimization strategy for parallel isosurface extraction from sparse voxel data. It solves the load-balancing problem in hierarchical partitioning by allowing a processed block to merge with a sibling (brother) or a cousin (nephew) if they share a geometric common boundary, rather than restricting merges to immediate siblings only [S1]. This approach reduces the number of final mesh components and communication overhead compared to strict brother-only merging, while avoiding the geometric discontinuities of unrestricted merging [S1]. It differs from [Boundary Point Identification and Merge Simplification](5296-boundary-point-identification-and-merge-simplification.md) by handling the topological eligibility of the merge; the latter handles the subsequent geometric vertex alignment and mesh simplification [S1, 5296].

## How it works
**Inputs:** An octree structure where nodes are marked as "processed" (extracted) or "unprocessed". Each node has a defined `type` based on its position relative to its father's split.
**Outputs:** A set of merged blocks, where merged blocks are marked as "completely processed" and their constituent leaves are removed from the active extraction queue.

**Data Structures:**
*   **Node:** Contains geometry data, a `type` field (enum: `left`, `right`, `up`, `down`, `front`, `back`), and a `status` field (`processed`, `completely_processed`, `unprocessed`).
*   **Type Definition:** The type is determined by the split direction of the father node. If the father splits along the x-axis, children are `left` and `right`. If along y, `up` and `down`. If along z, `front` and `back` [S1].
*   **Opposite Operator:** Defined as:
    *   $left = right$
    *   $right = left$
    *   $up = down$
    *   $down = up$
    *   $front = back$
    *   $back = front$ [S1]

**Algorithm Steps:**
1.  **Iterative Traversal:** Traverse the tree to identify processed leaf nodes.
2.  **Candidate Selection:** For a processed block $p1$, identify potential merge partners. These can be:
    *   Its brother $p2$ (if $p2$ is also processed).
    *   A nephew node $n$ belonging to the tree of the brother ($T_{p2}$), provided $n$ is processed and not yet completely processed [S1].
3.  **Restricted Adjacency Check:** To determine if a nephew $n$ (from the brother's subtree $T_{c_{p2}}$) shares a common boundary with $p1$, compute the ancestry set $A_{c_{p2}, n}$ and verify the type constraint [S1].
    *   **Ancestry Set Definition:** The ancestry of node $n$ up to root $p$ is defined recursively:
        $$ A_{p,n} = \begin{cases} n & \text{if } n = p \\ n \cup A_{p,f_n} & \text{else} \end{cases} $$
        where $f_n$ is the father of $n$ [S1].
    *   **Boundary Condition:** A nephew $n$ belonging to $T_{c_{p2}}$ has a common boundary with $p1$ if and only if:
        $$ \forall n' \in A_{c_{p2},n}, \text{type}(n') \neq \text{type}(p1) $$
        This ensures that no ancestor of the nephew shares the same type (and thus the same split orientation/position relative to the split plane) as the target block $p1$, which would imply they do not share a direct geometric boundary [S1].
4.  **Merge Execution:** If the condition is met, merge $p1$ and $n$ (or $p1$ and its brother). The resulting merged node is marked as `completely_processed`.
5.  **Completion:** When two brothers are merged, their father node is considered completely processed [S1].

**Pseudocode:**
```python
def check_restricted_adjacency(target_node, candidate_node, root_node):
    """
    Checks if candidate_node shares a common boundary with target_node
    using the restricted adjacency criterion.
    """
    # Determine the subtree root of the candidate relative to the target's sibling
    # In practice, this requires traversing up to find the common uncle/aunt
    # For the formula provided in [S1], we assume we are checking a nephew n
    # in the tree of the brother of target_node.
    
    # Let p1 be target_node, p2 be the brother of p1.
    # Let n be the candidate nephew in T_p2.
    # We need to check ancestry of n up to p2 (c_p2 in source notation refers to the brother node).
    
    current = candidate_node
    while current is not None and current != root_node:
        # Check if current node's type matches target_node's type
        if current.type == target_node.type:
            return False
        current = current.father
        
    # If we reached the root or the brother node without finding a matching type,
    # the condition is satisfied. Note: The source formula specifies ancestry up to c_p2.
    # If the loop terminates at the brother node, we must ensure the brother itself
    # doesn't invalidate the boundary (though typically the brother is the split point).
    # Based on [S1], the check is strictly on the ancestry nodes within the nephew's branch.
    return True

def merge_blocks(block_a, block_b):
    """
    Merges two blocks and marks the result as completely processed.
    """
    merged_node = create_merged_node(block_a, block_b)
    merged_node.status = "completely_processed"
    return merged_node

def restricted_adjacency_merge(isosurface_extractor):
    """
    Main loop for restricted adjacency merging.
    """
    processed_blocks = isosurface_extractor.get_processed_blocks()
    
    for p1 in processed_blocks:
        if p1.status == "completely_processed":
            continue
            
        # Check for brother merge
        brother = p1.father.children[opposite(p1.type)]
        if brother and brother.status == "processed" and brother.status != "completely_processed":
            merge_blocks(p1, brother)
            continue
            
        # Check for nephew merges
        # Iterate through the brother's subtree to find processed nephews
        for nephew in get_processed_leaves_in_tree(brother):
            if nephew.status == "completely_processed":
                continue
                
            if check_restricted_adjacency(p1, nephew, p1.father):
                merge_blocks(p1, nephew)
                break # One merge per block per pass, or merge all valid
```

**Edge Cases and Pitfalls:**
*   **Ancestry Check Failure:** If any ancestor of the nephew shares the same type as the target block, they do not share a common boundary, and merging is forbidden [S1].
*   **Processing Order:** The algorithm relies on nodes being marked `completely_processed` to prevent re-merging. If a node is merged, it must be excluded from further merge candidates [S1].
*   **Numerical Inaccuracy:** While the topological merge is defined by tree structure, the actual geometric merging requires handling vertex coordinates. Simple coordinate comparison is insufficient due to numerical inaccuracies in isosurface extraction [S1].

## Subtopics

### [Boundary Point Identification and Merge Simplification](5296-boundary-point-identification-and-merge-simplification.md)
Handles the geometric vertex alignment and mesh simplification constraints after the topological merge eligibility has been determined by Restricted Adjacency Merging.

## Operating characteristics
*   **Complexity:** The ancestry check requires traversing up the tree from the nephew to the common ancestor. In the worst case, this is $O(h)$ where $h$ is the tree height. The number of potential merge candidates is limited by the local neighborhood in the octree.
*   **Performance:** Allows merging of non-sibling components, reducing the total number of mesh parts and potentially improving cache coherence and reducing post-processing overhead [S1].
*   **Limitations:** Requires careful management of node states (`processed` vs `completely_processed`) to avoid invalid merges. The geometric merging step (not covered here) must handle the boundary points identified by this topological step [S1, 5296].

## Background
Restricted Adjacency Merging was introduced in the context of parallel extraction and simplification of large isosurfaces using an extended tandem algorithm. It addresses the issue where iso-surface components are not uniformly distributed, causing load imbalance if only brothers are merged [S1]. The method was proposed to allow merging with nephews under strict topological constraints to maintain geometric continuity [S1].
