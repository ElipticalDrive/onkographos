# Bottom-up Octree Construction

Also called: Bottom-up Octree, Bottom-up Octree Building

## Overview
Bottom-up octree construction is a spatial domain compression technique that organizes quantized scalar volume data into an adaptive-resolution octree by recursively fusing neighboring voxels with similar values into "macro voxels" [S1, unofficial][S6]. It solves the problem of high memory footprint and traversal cost in large structured volumes by creating a hierarchical structure where leaf nodes store fine-grained data and interior nodes represent coarser resolutions or structural pointers [S2, S8, unofficial]. Unlike top-down approaches that split empty or uniform regions, this method visits each data value exactly once, making it approximately two times faster and avoiding redundant evaluation calculations [S1, unofficial]. It differs from sibling methods like [Octree Construction from Structured Volumes](1854-octree-construction-from-structured-volumes.md) by explicitly defining the consolidation logic and implicit storage format for the encoded tree, serving as the foundational spatial compression step for acceleration structures like the Min/Max Tree [S1, unofficial][S6].

## How it works
**Inputs and Outputs:**
- **Input:** A 3D scalar array of volume data. The dimensions are typically zero-padded to the smallest power of two $N$ such that $N \ge \max(W, H, D)$ [S2, S7, S8, unofficial].
- **Output:** An octree structure where leaf nodes contain scalar values (or caps containing 8 scalars) and interior nodes contain pointers to children and optional metadata (min/max pairs) [S8, S10, unofficial].

**Data Structures:**
The implementation uses a node-based structure. A common layout for an interior node includes:
- `m_children`: A pointer to an `OctreeChildren` structure.
- `OctreeChildren` layout:
  - `field`: A `uint8_t` bitmask where bit $i$ is set if child $i$ exists [S3, unofficial].
  - `children`: An array of 8 pointers (`Octree*`) to child nodes [S3, unofficial].
- Leaf nodes may be represented implicitly by the absence of children in the parent's `field` or by a dedicated leaf flag [S1, S3, unofficial].
- For min/max acceleration, interior nodes store `min` and `max` scalar values derived from their children [S8, S10, unofficial].

**Parameters:**
- **Variance Threshold ($\tau$):** A scalar value determining the maximum allowed variance for 8 voxels to be consolidated. If variance $< \tau$, voxels are merged. For lossless compression, $\tau = 0$ (voxels must be identical) [S5][S7, S10, unofficial].
- **Maximum Depth ($d_{max}$):** Defined as $\log_2(N)$, where $N$ is the padded dimension size [S7, S8, unofficial].
- **Isovalue Clamping Range:** Optional range to clamp input data to reduce memory footprint (e.g., 64–127 for specific datasets) [S9].

**Algorithm Steps:**
1. **Initialization:** Determine $N$, the smallest power of two encompassing the largest volume dimension. Set $d_{max} = \log_2(N)$. Initialize vectors of node containers for the current and next depth levels. At the finest level (depth $d_{max}$), the data is treated as groups of 8 voxels assigned to "caps" [S7, S8, unofficial].
2. **Bottom-Up Consolidation Loop:** Iterate from depth $d_{max}-1$ up to depth 0 (root).
   - For each group of 8 nodes/voxels at the current level:
     - Calculate the variance of the 8 values.
     - If the variance is below the threshold (or zero for lossless):
       - Compute the average value of the 8 voxels.
       - Create a single parent node at the previous depth level containing this average (or a cap of 8 scalars if at $d_{max}-1$) [S5][S7, S10, unofficial].
       - Remove the 8 child nodes from memory or mark them as consolidated [S7, S8, unofficial].
     - If the variance is above the threshold:
       - Keep the 8 children as distinct nodes. The parent node will have a `field` bitmask indicating which of the 8 children exist [S3, unofficial].
3. **Min/Max Tree Construction (Optional but common):** Simultaneously or subsequently, compute min/max bounds for interior nodes.
   - For leaf nodes (caps), retrieve the 7 forward neighbors to compute the min/max of the 27-voxel cell corner [S8, S10, unofficial].
   - For interior nodes, compute the min/max as the minimum of children's mins and maximum of children's maxs [S8, S10, unofficial].
4. **Pointer Filling:** Fill pointers from parent nodes to their existing children until the root node is reached [S7, S8, unofficial].

**Edge Cases and Pitfalls:**
- **Thread Safety:** In parallel implementations, updating the `field` bitmask of a parent node is not thread-safe if multiple children are processed concurrently. The bitmask update should be deferred to the main thread after joining parallel tasks [S3, unofficial].
- **Memory Leaks:** If not using smart pointers, the destructor must manually delete all child nodes to avoid memory leaks [S3, unofficial].
- **Precision:** For 8-bit data, fusing voxels based on error tolerance (non-zero variance threshold) often produces images unacceptable for visualization. Lossless fusion (threshold=0) is preferred for such data [S1, unofficial].
- **Boundary Conditions:** Voxels outside the octree data are defined to be zero when computing min/max bounds for cells at the boundary [S8, unofficial].

## Subtopics

### [Min/Max Tree Construction](1623-min-max-tree-construction.md)
Min/Max Tree Construction builds an acceleration structure embedded within an octree to accelerate volume rendering and isosurface extraction by allowing the traversal algorithm to skip nodes whose scalar value range does not contain the target isovalue. It differs from sibling methods like [Octree Construction from Structured Volumes](1854-octree-construction-from-structured-volumes.md) by specifically computing and storing extrema pairs at interior nodes to enable early culling, rather than relying solely on occupancy or variance thresholds.

### [Octree Construction from Structured Volumes](1854-octree-construction-from-structured-volumes.md)
This method compresses large structured scalar volumes into an adaptive-resolution octree to reduce memory footprint while serving as an acceleration structure for ray tracing. It generates an octree from a 3D grid by consolidating voxels with zero inter-voxel variance, extending the principle of quadtree generation from 2D grids (consolidating pixels with zero inter-pixel variance) to 3D. Unlike [Min/Max Tree Construction](1623-min-max-tree-construction.md) which focuses on the hierarchy bounds, this method focuses on the data consolidation and tree topology. It differs from [Velasco and Torres](https://www.researchgate.net/publication/261082346_Interactive_Isosurface_Ray_Tracing_of_Large_Octree_Volumes) by encapsulating actual individual voxels rather than eight-voxel cells.

### [Hierarchical Partition Optimization](1953-hierarchical-partition-optimization.md)
Hierarchical Partition Optimization (HPO) is an offline preprocessing method that computes an optimal adaptive partitioning of a volume dataset and assigns extraction methods to each partition block to minimize a combined cost of memory usage and extraction time. It solves the problem of balancing memory constraints against rendering performance by constructing a hierarchical tree of partitions where each node is either a single block or a subdivision into children, optimized via a Lagrangian relaxation. It sets itself apart from sibling methods like [Min/Max Tree Construction](1623-min-max-tree-construction.md) by explicitly optimizing for a trade-off between two competing metrics (space and time) rather than just geometric homogeneity or structural compactness.

### [Omnitree Refinement](2222-omnitree-refinement.md)
Omnitree refinement transforms an initial hierarchical dyadic partition of a $d$-dimensional Cartesian domain into a target partition with higher resolution in specific dimensions. It solves the problem of anisotropically increasing the granularity of a sparse voxel representation by attaching refinement markers to nodes and propagating them through the tree structure. The method explicitly supports per-dimension refinement levels ($\vec{m} \in \mathbb{N}^d$), allowing for non-cubic, rectangular subdomains. It builds on [Bottom-up Octree Construction](1590-bottom-up-octree-construction.md) by providing the mechanism to adjust the topology of the resulting tree after initial construction or during dynamic updates.

### [Octree Compaction & Construction](2857-octree-compaction-construction.md)
This method compacts a logically built, pointer-based octree into a dense, cache-friendly array layout to accelerate ray traversal and splatting by reducing memory overhead and handling invisible material costs. It differs from sibling methods like [Min/Max Tree Construction](1623-min-max-tree-construction.md) by focusing on the physical memory layout of the tree nodes rather than just bounding volume acceleration, and from [Octree Encoding](5851-octree-encoding.md) by producing a mutable, contiguous memory block suitable for direct pointer arithmetic during traversal rather than a bit-stream for storage.

### [Octree Encoding](5851-octree-encoding.md)
Octree encoding is a spatial domain compression technique for volumetric data that organizes quantized voxel data hierarchically using recursive spatial subdivision. It solves the problem of storing and processing 3D grids by fusing immediate neighboring voxels with identical values into "macro voxels," thereby reducing memory footprint and I/O costs. Unlike sibling methods that may focus on unbalanced structures or specific construction optimizations, this method specifically defines the *fusion* logic and the resulting *implicit storage* format for the encoded tree, serving as the spatial counterpart to temporal difference encoding.

### [Unbalanced Octree Construction](7230-unbalanced-octree-construction.md)
This method constructs an adaptive-resolution octree from a sorted array of leaf nodes (typically bounding spheres of mesh primitives) by recursively grouping them into clusters of up to eight. It is designed for 3-manifold solids where an unbalanced octree is preferred over an unbalanced quadtree to increase the average branching factor, thereby reducing the number of interior nodes, memory footprint, and traversal time.

### DMC Octree Build
DMC Octree Build constructs the DMC octree from a scalar field, using a QEF solver and various split policies [S11, unofficial]. It validates that the root size is greater than 0 and a power of two, throwing an error if not. It initializes build arguments with the field, solver, scaled epsilon, split policies, and a seeded RNG. It collapses the root node and then calls `buildNode` on the root with the minimum corner at $(-m_{rootSize}/2, -m_{rootSize}/2, -m_{rootSize}/2)$ and size $m_{rootSize}$ [S11, unofficial]. The epsilon is scaled according to the QEF scale: $\text{scaled\_epsilon} = \epsilon / (m_{globalScale} \times m_{globalScale})$ [S11, unofficial].

## Operating characteristics
**Time Complexity:**
The bottom-up construction algorithm is $O(N)$ with respect to the total number of voxels $N$, as it visits each data value only once [S1, S10, unofficial]. This is approximately two times faster than top-down methods [S1, unofficial].

**Memory Complexity:**
The space overhead is generally acceptable if large macro voxels are created. The maximum overhead is approximately $v \times b$, where $v$ is the total number of voxels and $b$ is the number of bytes used to store information about each internal tree node [S1, unofficial]. Using a linear octree, it could take as few as 1 bit per node to indicate if it is a leaf node or not [S1, unofficial]. However, building an expanded full octree structure can occupy a footprint of four times the raw volume size, requiring significant memory (e.g., nearly 40 GB for Richtmyer-Meshkov data) [S10, unofficial].

**Measured Performance:**
- On a single core of a 16-core 2.4 GHz Opteron workstation, building a single timestep of the $30^3$ heptane volume requires 8 seconds and a negligible memory footprint [S10, unofficial].
- Building a timestep of the Richtmyer-Meshkov data requires 45 minutes and a footprint of nearly 40 GB [S10, unofficial].

**Strengths and Limitations:**
- **Strengths:** Efficient construction time ($O(N)$), effective compression for homogeneous regions, and provides a foundation for acceleration structures (Min/Max trees) [S1, S8, unofficial].
- **Limitations:** For 8-bit data, lossy fusion (error tolerance) often degrades visualization quality [S1, unofficial]. The method may require significant memory for the expanded tree structure before compaction [S10, unofficial]. Parallel implementation requires careful handling of thread safety for bitmask updates [S3, unofficial].

**When to Use:**
Use when the volume data has large homogeneous regions suitable for compression and when an acceleration structure for ray tracing is needed. It is preferred over top-down construction for speed [S1, unofficial].

**When Not to Use:**
Avoid for 8-bit data where lossy compression artifacts are unacceptable [S1, unofficial]. Avoid if the memory overhead of the expanded tree is prohibitive and compaction is not feasible [S10, unofficial].

## Background
Bottom-up octree construction originated as a method for spatial domain compression of volumetric data [S1, unofficial]. It was developed to address the high memory and I/O costs of rendering large time-varying volume datasets [S1, unofficial]. The method extends the principle of quadtree generation from 2D grids to 3D octrees by consolidating voxels with low inter-voxel variance [S1, S2, unofficial]. It is closely associated with the work of Wald et al. on interactive isosurface ray tracing of large octree volumes, where it is used to build the octree volume structure and the embedded min/max tree for acceleration [S5, S6][S7, S8, S10, unofficial]. The method is also discussed in the context of efficient encoding and rendering of time-varying volume data [S1, unofficial] and interactive multiresolution visualization [S2, unofficial].
