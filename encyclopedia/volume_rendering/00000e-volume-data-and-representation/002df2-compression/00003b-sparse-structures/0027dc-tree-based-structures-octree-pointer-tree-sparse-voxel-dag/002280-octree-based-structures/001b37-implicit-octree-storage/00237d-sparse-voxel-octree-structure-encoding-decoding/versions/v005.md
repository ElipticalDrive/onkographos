# Sparse Voxel Octree Structure Encoding/Decoding


## Overview
Sparse Voxel Octree (SVO) structure encoding and decoding are CPU-side methods for serializing and deserializing the hierarchical topology of a sparse voxel octree [S1, unofficial]. They solve the problem of converting an in-memory tree structure into a compact, persistent byte stream (or vice versa) for storage or transmission, enabling efficient loading and unloading of volumetric data for CPU-based ray casting [S1, unofficial]. Unlike file-system-based indexing methods that distribute nodes across directories, this method stores the entire octree structure in a single contiguous file or buffer, separating structural metadata from voxel data to allow efficient memory mapping [S1, unofficial][S2, unofficial].

## How it works
The encoding process converts the logical octree hierarchy into a linear sequence of bits or bytes, typically using Morton codes (Z-order curves) to determine node positions and parent-child relationships implicitly or explicitly. Decoding reverses this process, reconstructing the tree in memory.

**Inputs and Outputs:**
*   **Input (Encode):** An in-memory SVO data structure containing nodes with child pointers and leaf data.
*   **Output (Encode):** A binary buffer or file containing the serialized header, root node, and node payloads.
*   **Input (Decode):** A binary buffer or file containing the serialized SVO data.
*   **Output (Decode):** An in-memory SVO data structure ready for traversal.

**Data Structures:**
The serialized format typically consists of:
1.  **Header:** Metadata including version, maximum Morton depth, and compression flags.
2.  **Root Node:** The top-level node of the octree.
3.  **Node Payloads:** Binary representations of internal nodes (pointers to children) and leaf nodes (voxel data).
    *   *Internal Node:* Often encoded as a bitmask indicating which of the 8 children exist, followed by the serialized children.
    *   *Leaf Node:* Contains the voxel value (e.g., density, color) and potentially a Morton code or offset.

**Numbered Steps for Encoding:**
1.  **Finalization:** If the octree is not yet finalized, pad empty voxels to match the maximum Morton code depth [S3, unofficial].
    *   If current Morton depth < max Morton depth, call `FastAddEmptyVoxel` with difference + 1 [S3, unofficial].
2.  **Write Root:** Write the root node (`m_Children[0][0]`) to the output stream [S3, unofficial].
3.  **Write Header:** Write the structural header containing metadata (e.g., max depth, compression type) [S3, unofficial].
4.  **Compression (Optional):** If compression is enabled (not `NONE`), call `CompressFileIncremental(true)` to compress the written data [S3, unofficial].
5.  **Close:** Close the file or finalize the buffer [S3, unofficial].

**Numbered Steps for Decoding:**
1.  **Read Header:** Parse the header to determine max depth, compression status, and version.
2.  **Decompress (Optional):** If compressed, decompress the buffer.
3.  **Read Root:** Read the root node from the stream.
4.  **Reconstruct Tree:** Traverse the stream, using the header and node bitmasks to recursively allocate child nodes and leaf data, reconstructing the parent-child relationships.

**Formulas:**
*   **Morton Code Mapping:** Nodes are often mapped to 3D space using Morton codes. The position $(x, y, z)$ is interleaved into a single integer $M$.
    $$ M = \text{interleave}(x, y, z) $$
    *   $x, y, z$: Integer coordinates of the voxel.
    *   $\text{interleave}$: Bitwise interleaving of the binary representations of $x, y, z$.

**Parameters:**
*   **Max Morton Depth:** The maximum depth of the octree, determining the finest voxel resolution. Not given in the sources.
*   **Compression Type:** Flag indicating whether to apply incremental compression (e.g., `NONE`, `LZ4`, etc.). Not given in the sources.

**Edge Cases and Pitfalls:**
*   **Empty Voxels:** Empty regions must be handled efficiently. Padding empty voxels to the max depth ensures a consistent structure but may increase size if not compressed [S3, unofficial].
*   **Precision:** Morton codes can overflow for very large volumes. Use 64-bit integers for coordinates if the volume exceeds $2^{21}$ in any dimension.
*   **Boundary Conditions:** Ensure AABB (Axis-Aligned Bounding Box) padding is applied correctly if the volume does not align with the grid origin [S1, unofficial].

    """
    Recursively writes a node and its children to the buffer.
    """
    if node.is_leaf():
        # Write leaf marker
        buffer.append(0) # 0 for leaf
        # Write leaf data (e.g., voxel value)
        buffer.extend(struct.pack('<f', node.value))
    else:
        # Write internal node marker
        buffer.append(1) # 1 for internal
        # Write child mask (bitmask of which children exist)
        child_mask = 0
        for i in range(8):
            if node.children[i] is not None:
                child_mask |= (1 << i)
        buffer.append(child_mask)

        for i in range(8):
            if node.children[i] is not None:
                write_node(node.children[i], buffer)

    """
    Recursively reads a node and its children from the buffer.
    """
    marker = buffer.pop(0)
    
    if marker == 0:

        value = struct.unpack('<f', buffer[:4])[0]

        return LeafNode(value)

        # Internal node
        child_mask = buffer.pop(0)
        children = [None] * 8
        for i in range(8):
            if child_mask & (1 << i):
                children[i] = read_node(buffer)
        return InternalNode(children)

## Subtopics

### [Octree File I/O Format](5032-octree-file-i-o-format.md)
This format defines the ASCII header and binary payload structure for serializing a Sparse Voxel Octree (SVO) to disk, enabling efficient loading and unloading of volumetric data. It solves the problem of persistent storage for CPU-based ray casting by separating structural metadata from voxel data, allowing the renderer to map memory efficiently without parsing complex binary headers for every access. It differs from file-system-based indexing methods (like [Octree-based Space Subdivision with File System Indexing](5866-octree-based-space-subdivision-with-file-system-indexing.md)) by storing the entire octree structure in a single contiguous file rather than distributing nodes across the directory hierarchy.

### [Tolerance-based Voxel Fusion](5866-tolerance-based-voxel-fusion.md)
Tolerance-based Voxel Fusion is a performance optimization strategy that renders volume data at variable resolutions across the spatial domain by fusing voxels with similar values. It solves the trade-off between rendering fidelity and computational cost by coarsening the representation in regions where visual detail is less critical, achieving significant savings in storage and rendering time without perceptible quality loss in moderate coarsening modes. It differs from image-space skipping, which creates blocky artifacts, by operating in the spatial domain to maintain visual continuity.

### [Temporal Difference Encoding](5869-temporal-difference-encoding.md)
Temporal Difference Encoding is a compression technique for time-varying volume data that exploits high temporal correlation between consecutive time steps. It predicts each sample based on past data and encodes the difference between the prediction and the actual value. Structurally, it merges octrees from consecutive time steps by storing pointers to unchanged subtrees from previous steps instead of duplicating data. Unlike methods that treat all dimensions uniformly, this approach applies difference encoding specifically to the time domain.

### Sparse Voxel DAG
An extension to SVO that merges identical nodes and redirects parent pointers to single nodes to decrease memory footprint further [S2, unofficial]. Limited Utility for Radiance: Merging nodes is less effective when storing complex data like diffuse albedo compared to simple occlusion values, as identical child nodes become rare [S2, unofficial].

### Octree Finalization & Empty Voxel Padding
Finalizes the octree by padding empty voxels to match maximum Morton code depth, writing the root node, header, and optionally compressing [S3, unofficial]. Steps: 1. If current Morton depth < max Morton depth, call FastAddEmptyVoxel with difference + 1. 2. Write root node (m_Children[0][0]). 3. Write header. 4. If compression != NONE, call CompressFileIncremental(true). 5. Close file [S3, unofficial].

### Sparse Voxel Octree Attribute Encoding (Light)
A storage method for light values (0-15) that packs four 4-bit nibbles into a single 32-bit integer per 2x2x2 voxel region, reducing memory overhead and removing the need for the lowest octree layer [S4, unofficial]. Steps: 1. Initialize light values to 0 for non-illuminated blocks. 2. Assign 1-15 to light-emitting blocks. 3. Propagate light by decrementing the value by 1 for each neighboring block until it reaches 0. 4. Pack four 4-bit light values (one per voxel in a 2x2x2 region) into a single 32-bit integer. 5. Store packed integers in a 4-layer octree per 16x16x16 area. 6. Stack multiple octrees vertically to cover the full 256-block chunk height [S4, unofficial]. Formula: $light(Pos) = \max(\{0\} \cup \{LVal - \|LPos - Pos\|_1 \mid (LPos, LVal) \in Lights\})$ [S4, unofficial]. Layout: Each 2x2x2 voxel region is stored as a single 32-bit integer. Four 4-bit nibbles represent the light value of each voxel. The octree uses 4 layers instead of 5 due to the 2x2x2 packing granularity. Multiple octrees are stacked vertically to cover the 256-block chunk height [S4, unofficial]. Comparison: Unlike naive byte-per-block storage which wastes 50% of allocated memory per block, bit-packing utilizes 100% of the allocated 32-bit integer space for four voxels [S4, unofficial].

## Operating characteristics
*   **Time Complexity:** Encoding and decoding are linear with respect to the number of nodes in the octree, $O(N)$, where $N$ is the number of non-empty nodes.
*   **Memory Complexity:** The serialized size is proportional to the number of nodes, with overhead for headers and bitmasks. Compression can significantly reduce this size.
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Scales well with sparse data, as empty regions are not stored. Performance degrades if the volume becomes dense, as the tree depth increases.
*   **Strengths:** Efficient storage for sparse data, fast traversal for ray casting, supports variable resolution.
*   **Limitations:** Overhead for tree structure, less effective for dense data, merging nodes (DAG) is less effective for complex attributes.
*   **When to use:** When dealing with sparse volumetric data, especially for CPU-based ray casting or persistent storage.
*   **When not to use:** For dense volumes where grid-based storage is more efficient, or when complex attributes prevent effective node merging.

## Background
The Sparse Voxel Octree (SVO) was introduced as a method for efficient storage and rendering of volumetric data [S2, unofficial]. It extends the concept of octrees to voxel data, allowing for adaptive resolution and sparse storage. The encoding and decoding methods described here are CPU-side implementations for serializing these structures [S1, unofficial]. The Sparse Voxel DAG is an extension that further reduces memory usage by merging identical nodes [S2, unofficial].
