# Implicit Octree Storage
Also called: Implicit Order Storage
## Overview
Implicit Octree Storage is a memory-efficient serialization format for sparse voxel octrees that eliminates explicit node pointers by mapping tree nodes to a linear array via a deterministic spatial ordering, such as breadth-first or Morton order [S1]. It solves the problem of high memory overhead and fragmentation associated with pointer-based tree structures, making it suitable for streaming, persistent storage, and bandwidth-constrained environments [S1]. Unlike pointer-based variants or traversal-optimized structures like [Implicit Octree Traversal](1220-implicit-octree-traversal.md), this method prioritizes compact storage over random-access speed, as the implicit order is not designed for efficient on-the-fly traversal [S1].
## How it works
**Inputs and Outputs:**
- Input: A sparse voxel octree structure (nodes and children relationships).
- Output: A linear array (or stream) of node data, where the position in the array implicitly defines the parent-child relationships.

**Data Structures:**
The output is a contiguous array of node records. Each record must contain the necessary attribute data (e.g., scalar value, min/max bounds, or flags) and potentially child offsets if the ordering is not strictly fixed (e.g., Morton order requires storing child indices or deriving them from the Morton code). In the specific breadth-first implicit order described by Schnabel and Klein, the array index itself serves as the pointer [S1].

**Steps:**
1.  **Traverse the Octree:** Perform a traversal of the input octree using the chosen implicit ordering algorithm (e.g., Breadth-First Search (BFS) or Morton Z-order).
2.  **Serialize Nodes:** For each node visited, extract its attribute data (value, flags, etc.).
3.  **Store in Linear Array:** Append the node data to the output array at the index corresponding to the node's position in the traversal order.
    - In BFS, the root is at index 0. For a node at index $i$, its children are stored at fixed offsets (e.g., $2i+1, 2i+2, ..., 2i+8$ for an octree, assuming a complete binary tree mapping, though sparse nodes may require padding or explicit child pointers if the tree is not perfectly balanced/compressed).
    - In Morton order, nodes are sorted by their 3D-to-1D Morton code. The array is sorted such that spatial locality is preserved.
4.  **Handle Sparsity:** Empty subtrees are represented by null entries or omitted nodes, depending on the specific implicit scheme. If using a fixed-index scheme (like BFS on a dense grid approximation), empty nodes may be stored as null values. If using Morton order, only existing nodes are stored, and child relationships are derived from the Morton code's bit structure.

**Formulas:**
- Morton Code for 3D coordinate $(x, y, z)$:
  $$ M(x, y, z) = \text{interleave bits}(x, y, z) $$
  This maps 3D coordinates to a 1D integer key preserving spatial locality.

- BFS Indexing (for a complete octree):
  $$ \text{ChildIndex}(i, c) = 2i + c + 1 \quad \text{for } c \in [1, 8] $$
  (Note: This assumes a binary heap-like mapping; for octrees, the factor is typically $8i + c$ or similar depending on the specific implicit layout definition. Schnabel and Klein [S1] specify "breadth-first order" without detailing the exact arithmetic, implying a standard level-order traversal array representation).

**Parameters:**
- Ordering Type: BFS or Morton (Z-order).
- Node Size: Depends on attribute precision (e.g., 32-bit float for value, 8-bit flags).

**Edge Cases and Pitfalls:**
- **Traversal Efficiency:** The implicit order is not suitable for efficient ray traversal because children are not necessarily contiguous in memory in a way that facilitates quick descent, and parent pointers are not explicit [S1].
- **Sparsity Handling:** If the tree is highly sparse, a fixed-index BFS array may contain many null entries, wasting space. Morton order is more compact for sparse data but requires sorting.
- **Precision:** Morton codes can overflow for very large resolutions (e.g., >1024^3) if not using 64-bit integers.

**Pseudocode:**
```python
def implicit_octree_storage(root_node, ordering='bfs'):
    """
    Serializes an octree into a linear array using implicit ordering.
    """
    nodes = []
    
    if ordering == 'bfs':
        queue = [root_node]
        while queue:
            current = queue.pop(0)
            # Serialize current node attributes
            nodes.append(current.serialize())
            # Add children to queue
            if current.has_children:
                for child in current.children:
                    queue.append(child)
                    
    elif ordering == 'morton':
        # Collect all nodes with their Morton codes
        node_list = []
        collect_nodes_with_morton(root_node, node_list)
        # Sort by Morton code
        node_list.sort(key=lambda x: x.morton_code)
        # Serialize in sorted order
        for node in node_list:
            nodes.append(node.serialize())
            
    return nodes
```

## Subtopics

### [Bottom-up Octree Construction](1590-bottom-up-octree-construction.md)
A method for compressing a 3D scalar array into an adaptive-resolution octree by recursively grouping 8 voxels into a parent node if they are identical (lossless) or have combined variance below a threshold (lossy), storing the average value at the parent. It solves the problem of efficiently storing and rendering large scalar fields by reducing memory footprint while enabling accelerated ray traversal via a simultaneously built min/max tree. It differs from top-down approaches by starting from the finest grid and merging up, and from static structures by integrating compression and acceleration data (min/max) into a single cohesive build process.

### [Packed Tensor Representation](1611-packed-tensor-representation.md)
Packed Tensor Representation is a data structure designed to store samples from rays that have varying numbers of valid samples, avoiding the memory inefficiency of fixed-size tensors with masks when large portions of space are empty. It packs per-sample ray indices into per-ray chunk information (start index and count) for flattened tensors. This approach is similar to those used in Instant-NGP [17] and PyTorch3D [22], but is explicitly described here as a solution to the memory inefficiency of storing data as a tensor with shape $(n\_rays, n\_samples, ...)$ and an extra mask.

### [Octree Volume Structure](1978-octree-volume-structure.md)
The Octree Volume Structure is a memory-efficient storage scheme for 3D scalar fields that represents an octree by storing nodes corresponding to the parents of logical octree nodes. It solves the problem of high memory overhead in standard octree representations by eliminating explicit leaf nodes for the deepest level of interior nodes, instead embedding scalar values directly within parent structures. This approach serves as a lossless compression format for scalar data while simultaneously providing an acceleration structure for ray traversal via a built-in min/max tree. It differs from standard octrees by using "cap" nodes at the maximum depth and "scalar leaves" embedded in interior nodes, rather than distinct leaf node types.

### [Octree Volume Compression](1979-octree-volume-compression.md)
Octree Volume Compression is a lossless (or semi-lossless) technique that reduces the memory footprint of structured volume data by converting it into an octree structure and consolidating voxels with zero variance. It achieves compression factors of 3 to 5 for typical simulation data by exploiting spatial coherence, where large uniform regions are represented by single nodes. It differs from sibling methods like [SVO Node Encoding](2705-svo-node-encoding.md) by focusing on the initial construction-phase compression of the raw grid into the hierarchy, often utilizing iso-range clamping to discard irrelevant data values before or during tree construction.

### [Sparse Voxel Octree Attribute Encoding (Neighbor)](2641-sparse-voxel-octree-attribute-encoding-neighbor.md)
Encode the attribute of a sparse voxel octree into deltas from its neighbors.

### [SVO Node Encoding](2705-svo-node-encoding.md)
A 32-bit integer encoding used for octree nodes. The most significant bit (MSB) distinguishes between leaf nodes and internal nodes (addresses).

## Operating characteristics
- **Time Complexity:** Construction is $O(N \log N)$ for Morton sorting or $O(N)$ for BFS, where $N$ is the number of nodes. Traversal is $O(\log N)$ or worse depending on the implicit order and cache locality, as it is not optimized for traversal [S1].
- **Memory Complexity:** $O(N)$, where $N$ is the number of non-empty nodes. It eliminates pointer overhead, reducing memory usage compared to pointer-based octrees [S1].
- **Measured Performance:** Schnabel and Klein [S1] report significant memory reduction for point clouds discretized into octrees, suitable for streaming.
- **Strengths:** Compact storage, no pointer overhead, suitable for serialization and streaming.
- **Limitations:** Not suitable for efficient traversal; random access requires recomputing indices or sorting [S1].
- **When to use:** Persistent storage, streaming, bandwidth-constrained environments.
- **When not to use:** Real-time rendering requiring fast traversal.

## Background
Implicit Octree Storage was proposed by Schnabel and Klein [S1] to decrease the memory consumption of point clouds discretized into octrees. Their work focused on 4K^3 resolution octrees and demonstrated that sorting the tree in an implicit order (e.g., breadth-first) allows storage without pointers, significantly reducing size for streaming or storage [S1]. This approach is related to subtree merging techniques by Webber and Dillencourt [S1], which compress quadtrees by merging common subtrees.
