# Implicit Octree Storage
Also called: Implicit Order Storage
## Overview
Implicit Octree Storage is a serialization method for sparse voxel octrees that eliminates explicit node pointers by sorting tree nodes into a linear array using a deterministic spatial order, such as breadth-first order [S1]. It solves the problem of high memory overhead and fragmentation in pointer-based tree structures, making it suitable for streaming and persistent storage [S1]. Unlike traversal-optimized variants like [Implicit Octree Traversal](1220-implicit-octree-traversal.md), this method prioritizes compact storage over random-access speed, as the implicit ordering is explicitly noted as unsuitable for efficient traversal [S1].
## How it works
**Inputs and Outputs:**
- Input: A sparse voxel octree structure containing nodes and their parent-child relationships [S1].
- Output: A linear array (or stream) of node data, where the position in the array implicitly defines the parent-child relationships [S1].

**Data Structures:**
The output is a contiguous array of node records [S1]. Each record stores the necessary attribute data for the octree node (e.g., scalar values, flags, or bounding information) [S1]. The exact layout and size of each node record are Not given in the sources [S1].

**Steps:**
1. **Traverse the Octree:** Perform a traversal of the input octree using the chosen implicit ordering algorithm (e.g., Breadth-First Search (BFS)) [S1].
2. **Serialize Nodes:** For each node visited during traversal, extract its attribute data [G].
3. **Store in Linear Array:** Append the serialized node data to the output array at the index corresponding to the node's position in the traversal order [G].
4. **Handle Sparsity:** Empty subtrees are omitted from the array, relying on the implicit ordering to reconstruct hierarchy during reconstruction or by storing explicit markers if required by the implementation [G].

**Formulas:**
- BFS Indexing (for a complete octree): Not given in the sources [S1]. Schnabel and Klein specify "breadth-first order" without detailing the exact arithmetic for child index calculation.
- Morton Code for 3D coordinate $(x, y, z)$: $M(x, y, z) = \text{interleave bits}(x, y, z)$ [G]. This maps 3D coordinates to a 1D integer key preserving spatial locality [G].

**Parameters:**
- Ordering Type: BFS [S1].
- Node Size: Not given in the sources [S1].

**Edge Cases and Pitfalls:**
- **Traversal Efficiency:** The implicit order is not suitable for efficient traversal [S1].
- **Sparsity Handling:** If the tree is highly sparse, a fixed-index BFS array may contain many null entries, wasting space [G].
- **Precision:** Morton codes can overflow for very large resolutions (e.g., >1024^3) if not using 64-bit integers [G].

**Pseudocode:**
```python
def implicit_octree_storage(root_node, ordering='bfs'):
    """
    Serializes an octree into a linear array using implicit ordering.
    Assumes node is a dict with keys: 'data', 'children' (list of nodes or None).
    """
    nodes = []
    
    if ordering == 'bfs':
        queue = [root_node]
        while queue:
            current = queue.pop(0)
            nodes.append(current['data'])
            if current['children']:
                for child in current['children']:
                    queue.append(child)
    elif ordering == 'morton':
        node_list = []
        collect_nodes_with_morton(root_node, node_list, depth=0, offset=(0, 0, 0))
        node_list.sort(key=lambda x: x['morton_code'])
        for item in node_list:
            nodes.append(item['node']['data'])
    return nodes

def collect_nodes_with_morton(node, node_list, depth, offset):
    """
    Helper to collect nodes and compute Morton codes.
    """
    m_code = interleave_bits(offset[0], offset[1], offset[2])
    node_list.append({'node': node, 'morton_code': m_code})
    
    if node['children']:
        for i, child in enumerate(node['children']):
            new_offset = list(offset)
            for axis in range(3):
                if (i >> axis) & 1:
                    new_offset[axis] += 1
            collect_nodes_with_morton(child, node_list, depth + 1, tuple(new_offset))

def interleave_bits(x, y, z):
    """
    Standard bit interleaving for Morton code [G].
    """
    return (x | (y << 1) | (z << 2))
```
## Subtopics

### [Bottom-up Octree Construction](1590-bottom-up-octree-construction.md)
A spatial domain compression technique that organizes quantized volume data into an adaptive-resolution octree by recursively fusing neighboring voxels with identical values or low variance into macro voxels. It sets itself apart from top-down approaches by visiting each voxel exactly once, making it faster for memory-constrained systems. Choose it when lossless or low-variance structural consolidation is required over hierarchical prediction.

### [Packed Tensor Representation](1611-packed-tensor-representation.md)
A data structure designed to store samples from rays that have varying numbers of valid samples, avoiding the memory inefficiency of fixed-size tensors with masks when large portions of space are empty. It packs per-sample ray indices into per-ray chunk information for flattened tensors [G]. Choose it when ray sampling counts vary significantly across frames [G].

### [Octree Volume Structure](1978-octree-volume-structure.md)
A memory-efficient storage format for sparse voxel octrees that eliminates explicit leaf nodes by storing nodes corresponding to the parents of logical octree nodes. It sets itself apart from standard octrees by embedding scalar values directly within interior nodes and using a specialized cap structure at maximum depth. Choose it when interactive ray tracing requires unified compression and acceleration data.

### [Octree Volume Compression](1979-octree-volume-compression.md)
A lossless technique that reduces the memory footprint of structured volume data by converting it into an octree structure and consolidating voxels with zero variance. It sets itself apart from sibling methods by focusing on initial construction-phase compression of the raw grid into the hierarchy. Choose it when spatial coherence is high and iso-range clamping is acceptable.

### [Sparse Voxel Octree Attribute Encoding (Neighbor)](2641-sparse-voxel-octree-attribute-encoding-neighbor.md)
Encodes attribute values of a sparse voxel octree by computing deltas relative to neighboring voxels rather than hierarchical parents. It sets itself apart by targeting spatially smooth attribute fields. Choose it when spatial continuity is stronger than hierarchical correlation.

### [SVO Node Encoding](2705-svo-node-encoding.md)
A compact binary serialization format for Sparse Voxel Octrees that stores both structural topology and leaf attributes within a single 32-bit integer per node. It sets itself apart by eliminating separate child pointer arrays and embedding address offsets directly in node values. Choose it when contiguous array storage and fast CPU parsing are prioritized.

### [Sparse Voxel Octree Structure Encoding/Decoding](3012-sparse-voxel-octree-structure-encoding-decoding.md)
CPU-side methods for serializing and deserializing the hierarchical topology of a sparse voxel octree into a contiguous byte stream. It sets itself apart from file-system-based indexing by storing the entire structure in a single payload. Choose it when bandwidth-constrained transmission or disk storage of tree topology is required.

### [Hierarchical Data Structure Storage](3333-hierarchical-data-structure-storage.md)
A method for compactly storing precomputed illumination samples in a spatial hierarchy to accelerate volume rendering in participating media. It sets itself apart by maintaining two separate, redundant tree structures for single and multiple scattering to maximize data locality. Choose it when illumination caching dominates rendering cost.

### [Sparse Volume Data Structures](6804-sparse-volume-data-structures.md)
A representation where empty bricks are omitted when data is uploaded to the GPU, requiring zero memory storage. It sets itself apart by leveraging hardware upload mechanisms to skip empty regions entirely. Choose it when GPU memory bandwidth is the primary bottleneck.

## Operating characteristics
- **Time Complexity:** Construction is $O(N)$ for BFS or $O(N \log N)$ for Morton sorting, where $N$ is the number of nodes [G]. Traversal complexity is Not given in the sources, but the method is explicitly noted as unsuitable for efficient traversal [S1].
- **Memory Complexity:** $O(N)$, where $N$ is the number of non-empty nodes [G]. It eliminates pointer overhead, reducing memory usage compared to pointer-based octrees [S1].
- **Measured Performance:** Schnabel and Klein report significant memory reduction for point clouds discretized into octrees, suitable for streaming [S1].
- **Strengths:** Compact storage, no pointer overhead, suitable for serialization and streaming [S1].
- **Limitations:** Not suitable for efficient traversal [S1].
- **When to use:** Persistent storage, streaming, bandwidth-constrained environments [S1].
- **When not to use:** Real-time rendering requiring fast traversal [S1].
## Background
Implicit Octree Storage was proposed by Schnabel and Klein to decrease the memory consumption of point clouds discretized into octrees [S1]. Their work focused on 4K^3 resolution octrees and demonstrated that sorting the tree in an implicit order (e.g., breadth-first) allows storage without pointers, significantly reducing size for streaming or storage [S1]. This approach is related to subtree merging techniques by Webber and Dillencourt, which compress quadtrees by merging common subtrees [S1].
