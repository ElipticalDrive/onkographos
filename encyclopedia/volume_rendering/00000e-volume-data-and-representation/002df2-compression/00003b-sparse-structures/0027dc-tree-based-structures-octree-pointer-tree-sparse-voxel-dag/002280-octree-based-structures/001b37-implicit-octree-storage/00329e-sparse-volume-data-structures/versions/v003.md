# Sparse Volume Data Structures

Also called: Elemental Node Types

## Overview
Sparse Volume Data Structures is a family of hybrid volume data structures that decompose a 3D volume into cubic bricks of side length $m$ (a power of two), assigning each brick one of four elemental node types (empty, voxel list, pointer octree, or dense) based on local sparsity to minimize memory consumption [S1, unofficial].

## Shared principles
The family decomposes the volume into cubic bricks of side length $m$ (a power of two) and classifies each brick into one of four elemental node types based on the number of non-zero elements $n$ and the data size $d$ [S1, unofficial]. The selection criterion minimizes the memory footprint for each brick, and the global optimization selects the optimal brick size $m$ across the volume [S1, unofficial].

The four elemental node types are:

1. **Empty:** Bricks with no non-zero elements are omitted from storage, requiring zero memory [S1, unofficial]. They allow empty space skipping during traversal [S1, unofficial].
2. **Voxel List:** Stores sparse data as a list of quadruples $(x, y, z, \text{value})$ [S1, unofficial]. Coordinates require $\lceil \log_2(m) \rceil$ bits per axis, totaling $3 \log_2(m)$ bits per element [S1, unofficial]. Access time is $O(n)$ for unsorted lists, or $O(\log n)$ with binary search on sorted lists [S1, unofficial]. It does not allow empty space skipping within the brick [S1, unofficial].
3. **Pointer Octree:** An adaptive structure where leaf nodes store bricks of size $2^3$ (8 values) and internal nodes store 8 pointers to children (indices into a 1D array) [S1, unofficial]. A full pointer octree has $(m^3 - 1) / 7$ internal nodes [S1, unofficial]. The pointer overhead is approximately $p/7$ bits per non-empty voxel, or roughly $1/6$ of the values in a dense volume [S1, unofficial]. Access time is $O(\log m)$ [S1, unofficial]. Octrees are shift sensitive, meaning the number of internal nodes depends on the exact location of the octree within the volume [S1, unofficial]. They allow empty space skipping [S1, unofficial].
4. **Dense Volume:** A Cartesian grid storing $m^3$ values per brick with $O(1)$ access time [S1, unofficial]. Memory size is $d \cdot m^3$ bits [S1, unofficial]. It has the lowest overhead per data voxel but the highest overhead for single values [S1, unofficial]. It does not allow empty space skipping within the brick [S1, unofficial].

| Type | Access Time | Bit Overhead / Non-Empty Voxel | Shift Sensitive | Allows Empty Space Skipping |
| :--- | :--- | :--- | :--- | :--- |
| **Empty** | N/A | 0 | N/A | Yes |
| **Voxel List** | $O(\log n)$ | $3 \log_2(m)$ | No | No |
| **Pointer Octree** | $O(\log m)$ | $\sim p/7$ | Yes | Yes |
| **Dense Volume** | $O(1)$ | 0 | No | No |

*Note: $p$ is the pointer size [S1, unofficial].*

The JIT-compiled variant flattens recursive tree traversal into data-dependent conditional logic to eliminate memory fetches for node keys [S1, unofficial]. The following pseudocode illustrates this flattening using a simplified binary search tree example provided in the source:

```python
def jit_find(k):
    if k < 106:
        if k < 8:
            if k < 4:
                return 0
            elif k > 4:
                return 2
            else:
                return 1
        else:
            if k < 13:
                return 4
            elif k > 13:
                return 6
            else:
                return 5
    else:
        return 7
```

## Subtopics

### [Sparse GPU Volume Data Structure with JIT Compilation](6834-sparse-gpu-volume-data-structure-with-jit-compilation.md)
JiTTree is a sparse hybrid volume data structure that combines multiple elemental data structures (empty, voxel list, octree, dense) to minimize memory consumption while using just-in-time (JIT) compilation to generate GPU code tailored to a specific dataset. It solves the problem of increased traversal overhead inherent in conventional hybrid structures by inlining access logic and removing dead code at runtime. Unlike its siblings, which suffer from branch divergence and pointer-chasing overhead when mixing elemental types, JiTTree's traversal overhead depends on the homogeneity of the dataset rather than the number of elemental structures used.

## Background
The elemental node type approach was introduced in "A Just-in-Time Compiled Sparse GPU Volume Data Structure" [S1, unofficial]. The authors observed that single data structures like pure octrees or dense grids are suboptimal for volumes with varying sparsity, and proposed combining empty, voxel list, pointer octree, and dense representations to balance memory overhead and access performance [S1, unofficial].
