# Brick-based Hierarchical Storage

Also called: Brick Maps, Brick-based Sparse Structures, Multi-resolution Brick Storage

## Overview
Brick-based Hierarchical Storage organizes sparse volume data into fixed-size cubic blocks (bricks) arranged in a spatial hierarchy to optimize memory access and enable efficient ray traversal. It sets itself apart from tree-based structures like Octrees by using flat or semi-flat spatial subdivisions (such as page tables or active regions) rather than explicit pointer-heavy node hierarchies, and from hash grids by providing structured multi-resolution access patterns suitable for filtering and out-of-core rendering.

## Shared principles
The family shares the following mechanism:

1.  **Brick Decomposition:** The 3D domain is partitioned into fixed-size cubic blocks called bricks. Each brick contains a dense array of voxels (e.g., $8^3$ or $10^3$). This allows the use of standard 3D texture sampling hardware (trilinear filtering) and cache-friendly memory access patterns [S1, unofficial][S2].
2.  **Spatial Mapping:** A mapping structure (such as a page table, ABR list, or hash map) links logical 3D coordinates to resident bricks. Empty regions are represented by null entries in this mapping, enabling empty-space skipping [S1, unofficial][S2].
3.  **Residency Management:** Bricks are loaded into a limited-capacity pool (GPU memory or cache) on demand. The mapping structure tracks which bricks are currently resident, allowing the renderer to skip unloaded regions or trigger loading [S1, unofficial][S2].
4.  **Aporn Padding:** To support hardware trilinear filtering across brick boundaries, bricks are often padded with an apron (one or more voxels) containing data from neighboring logical cells, ensuring interpolation samples do not fall off the edge of the resident data [S1, unofficial].

## Subtopics

### [ExaBricks Hierarchy](2182-exabricks-hierarchy.md)
ExaBricks is a rendering method for Block-Structured Adaptive Mesh Refinement (BS-AMR) data that re-organizes input cells into compact, non-overlapping bricks and uses a secondary spatial partitioning called Active Brick Regions (ABRs) to enable smooth, high-quality interpolation across level boundaries. It sets itself apart from prior methods by eliminating costly per-sample cell location kernels (required by the basis method [37]) and deep AMR hierarchy traversals, instead relying on ABRs for fast sample reconstruction and an RTX BVH for hardware-accelerated ray marching. See [ExaBricks Hierarchy](2182-exabricks-hierarchy.md).

### [Sparse Page Table and Brick Pool](2550-sparse-page-table-and-brick-pool.md)
Sparse Page Table and Brick Pool is a memory-bounded sparse volume representation that avoids materializing a dense 3D grid by using a two-level structure: a page table mapping logical $8^3$-texel regions to resident bricks, and a pool of apron-padded bricks. It enables full source resolution (up to 2048 cells per axis) while bounding memory usage and enabling empty-space skipping. Unlike its sibling [ExaBricks Hierarchy](2182-exabricks-hierarchy.md) which relies on a fixed hierarchical hierarchy, or [Compressed Segmentation Volume](4985-compressed-segmentation-volume.md) which focuses on segmentation, this method uses a flat page table for spatial subdivision and a fixed-size brick pool for residency, allowing efficient raymarching with hardware depth compositing. See [Sparse Page Table and Brick Pool](2550-sparse-page-table-and-brick-pool.md).

### [Compressed Segmentation Volume](4985-compressed-segmentation-volume.md)
A compression technique for segmentation volumes (uint32_t labels) that uses a multi-grid hierarchy and run-length-like encoding with rANS secondary compression to store label data efficiently. See [Compressed Segmentation Volume](4985-compressed-segmentation-volume.md).

### Brick Maps
#### definition
- [S1, unofficial] A multi-resolution storage structure for 3D volume caches, analogous to 2D mipmaps, used to reduce aliasing (jiggle/noise) when rendering distant objects.
#### step
- [S1, unofficial] Create downsized versions of the original grid data by averaging 8 voxels from the previous level to form one voxel in the next level.
- [S1, unofficial] Iterate through levels n=1 to numLevels-2, where baseResolution is halved each level.
#### formula
- [S1, unofficial] The value of a voxel at level n is the average of 8 voxels from level n-1: $V_{n}(x,y,z) = 0.125 \times \sum_{i=0}^{1}\sum_{j=0}^{1}\sum_{k=0}^{1} V_{n-1}(2x+i, 2y+j, 2z+k)$
#### parameter
- [S1, unofficial] numLevels: The number of resolution levels, calculated as $\log_2(baseResolution)$.
#### pitfall
- [S1, unofficial] The downsizing process is trivial only if the grid resolution is a power of 2.
#### usage
- [S1, unofficial] Supported by production renderers and formats such as OpenVDB.

### Brick ID Page Table Layout
#### parameter
- [S2] Page table ID uniquely identifies $(m \times k) \le 256$ page tables, where $m$ is number of channels and $k$ is number of resolution levels representable on GPU.
#### layout
- [S2] Multi-channel page table hierarchy uses unsigned 32-bit integers for brick IDs.
- [S2] Brick ID structure: 24 bits for spatial offset (8 bits each for x, y, z coordinates relative to origin), remaining bits for page table ID.

## Background
The concept of brick maps was coined by the Pixar Renderman team, though the exact origin is uncertain [S1, unofficial]. The idea of storing multiple resolutions of volume data is not new, but the specific adaptation of 3D caching with brick maps allows for efficient rendering of large-scale volume data by leveraging hardware texture filtering [S1, unofficial]. Brick maps are supported by production renderers and formats such as OpenVDB [S1, unofficial]. The use of page tables and brick pools for residency management is described in the context of scalable web volume rendering, specifically for handling large datasets like MRMS weather data [S2].
