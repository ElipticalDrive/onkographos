# Memory Pool Sizing
## Overview
Memory pool sizing configures the capacity and allocation limits for the node pool and brick pool in sparse brick-based volume representations, bounding resident memory while enabling the referencing of large logical volumes [S1, unofficial]. It differs from dense grid approaches by using a fixed-size node pool to map logical regions to a resident brick pool, which enables empty-space skipping and on-the-fly brick generation [S1, unofficial].
## How it works
### Inputs and outputs
- **Inputs**: Target logical volume dimensions, brick resolution, and available memory budget [S1, unofficial].
- **Outputs**: Configured pool sizes (number of entries/bricks) and memory allocation parameters [S1, unofficial].

### Data structures
The method relies on two primary pools defined in the parent structure [Sparse Page Table and Brick Pool](2550-sparse-page-table-and-brick-pool.md):
1.  **Node Pool**: A sparse page table mapping logical regions to resident bricks [S1, unofficial].
    -   **Layout**: Array of indices or pointers [S1, unofficial].
    -   **Size**: Fixed by the allocated memory budget [S1, unofficial].
2.  **Brick Pool**: A pool of apron-padded bricks containing actual volume data [S1, unofficial].
    -   **Layout**: Array of brick structures [S1, unofficial].
    -   **Size**: Fixed by the allocated memory budget [S1, unofficial].

### Steps
1.  **Allocate Node Pool**: Reserve a fixed memory budget for the node pool [S1, unofficial].
2.  **Allocate Brick Pool**: Reserve a fixed memory budget for the brick pool [S1, unofficial].
3.  **Configure Brick Dimensions**: Select the brick resolution to determine how many logical indices each brick covers [S1, unofficial].
4.  **Initialize Node Pool**: Set all node pool entries to null or invalid [G].
5.  **Initialize Brick Pool**: Mark all brick pool entries as free [G].

### Formulas
-   **General Sizing Formulas**: Not given in the sources. The method relies on fixed memory budgets rather than derived mathematical formulas [S1, unofficial].
-   **Instance Values**: The node pool is allocated to 4 MB, yielding $64^3$ entries [S1, unofficial]. The brick pool is allocated to 430 MB, yielding $42^3$ bricks [S1, unofficial]. Using $16^3$ bricks with these pool sizes allows $1024^3$ logical indices to be referenced [S1, unofficial].

### Parameters
-   **Node Pool Budget**: Typically 4 MB [S1, unofficial].
-   **Node Pool Capacity**: $64^3$ entries [S1, unofficial].
-   **Brick Pool Budget**: Typically 430 MB [S1, unofficial].
-   **Brick Pool Capacity**: $42^3$ bricks [S1, unofficial].
-   **Brick Resolution**: $16^3$ [S1, unofficial].
-   **Logical Resolution**: $1024^3$ indices referenced [S1, unofficial].
-   **Virtual Resolution**: Up to $2048^3$ cells per axis [S1, unofficial].

### Edge cases and pitfalls
-   **Computation Trade-off**: The method trades computation time for memory efficiency by computing normals and procedural noise on-the-fly rather than storing them [S1, unofficial].
-   **Precision**: Brick size calculations must account for apron padding to avoid boundary errors during rendering [S1, unofficial].
-   **Thrashing**: If the brick pool is too small for the active view, frequent swapping between resident and non-resident bricks occurs [S1, unofficial].
## Subtopics

### Memory Pooling for Chunk Arrays
Recycles typed arrays from the main thread to avoid garbage collection per edit, storing them in `chunkPool` or `windowPool` based on length [S2, unofficial].
-   **Step**:
    1.  Check if `msg.recycle` exists [S2, unofficial].
    2.  For each array `a` in `recycle`, determine pool: `a.length === N3 ? chunkPool : a.length === P3 ? windowPool : null` [S2, unofficial].
    3.  If pool exists and `pool.length < 256`, push `a` into pool [S2, unofficial].
    4.  Reuse pooled arrays for future chunk/window allocations [S2, unofficial].
-   **Parameters**:
    -   `P3`: $(CHUNK + 2 \times PAD)^3$, size for padded mesher windows [S2, unofficial].
    -   `pool capacity`: Maximum number of arrays retained per pool. Default: 256 [S2, unofficial].

## Operating characteristics
-   **Time Complexity**: Pool lookups are $O(1)$ [G].
-   **Memory Complexity**: Bounded by the fixed pool budgets (e.g., 4 MB + 430 MB) [S1, unofficial].
-   **Performance**: Enables interactive rendering of large volumes (e.g., $2048^3$) on limited hardware (e.g., NVIDIA 8800 GTS with 512 MB VRAM) [S1, unofficial].
-   **Strengths**: Memory efficiency, scalability to large logical volumes, and support for on-the-fly GPU brick generation [S1, unofficial].
-   **Limitations**: Requires careful tuning of pool sizes to avoid thrashing or overflow, and relies on fixed budgets rather than dynamic sizing formulas [S1, unofficial].
## Background
Originated in Ray-Guided Streaming for Efficient and Detailed Voxel Rendering (2009) [S1, unofficial]. Used in interactive volume rendering systems to manage large voxel datasets on GPUs with limited memory [S1, unofficial]. All tests in the source were performed on a Core2 bi-core E6600 at 2.4 GHz and an NVIDIA 8800 GTS 512 graphics card, with images rendered at $512 \times 512$ [S1, unofficial].
