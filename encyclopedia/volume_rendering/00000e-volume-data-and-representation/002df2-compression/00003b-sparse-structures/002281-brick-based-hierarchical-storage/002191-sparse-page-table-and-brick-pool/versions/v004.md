# Sparse Page Table and Brick Pool

Also called: MRMS sparse volume, VDB-style sparse volume for web

## Overview
Sparse Page Table and Brick Pool is a memory-bounded sparse volume representation that avoids materializing a dense 3D grid by mapping logical $8^3$-texel regions to a pool of resident, apron-padded bricks [S1, unofficial]. It enables full source resolution (up to 2048 cells per axis) while bounding memory usage and supporting empty-space skipping, distinguishing it from dense grids that cap resolution or require coarsening [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A logical volume grid (e.g., MRMS weather data) defined by logical dimensions and voxel values.
*   **Output:** A Page Table (GPU texture) and a Brick Pool (GPU buffer).

**Data Structures:**
1.  **Page Table:** A 2D texture (or 3D texture with depth 1) where each entry corresponds to a logical $8^3$-texel page.
    *   **Format:** RG8 (8-bit Red, 8-bit Green).
    *   **Encoding:**
        *   Value `0`: The page is empty (no echo/data).
        *   Value `>0`: The page is resident. The value encodes the pool slot index $+ 1$. Specifically, if the entry is $V$, the brick is located at index $V-1$ in the Brick Pool.
2.  **Brick Pool:** A linear array of resident bricks.
    *   **Brick Layout:** Each brick consists of an $8^3$ texel core wrapped in a one-texel apron, resulting in a total size of $10^3$ texels.
    *   **Apron Construction:** The apron voxels are filled by copying neighboring logical texels from the source grid. Values are clamped at the grid edges to prevent out-of-bounds access. This ensures trilinear filtering remains within the brick boundaries [S1, unofficial].
    *   **Size:** Each brick is 2 KB ($10^3$ texels $\times$ 2 bytes/texel for RG8, assuming 8-bit per channel).

**Parameters:**
*   **MAX_VOLUME_BRICKS:** The maximum number of resident bricks allowed in the pool. Default: 8192. This caps the pool size at approximately 16.4 MB [S1, unofficial].
*   **Extinction Power:** The extinction ramp uses a power function $pow(t, 2.75)$ to correct for the fact that source-resolution rendering does not artificially inflate light echo compared to max-pooled dense grids. This value matches the visual brightness of the previous renderer within 4% across multiple scenes [S1, unofficial].
*   **MAX_RAY_STEPS:** Remains at 384. The sparse representation reduces per-pixel work but does not change the maximum step count [S1, unofficial].

**Build Phase (CPU/WASM):**
The `build_volume_texture` function emits the page table and brick pool.
1.  Iterate through the logical grid pages.
2.  For each $8^3$ page:
    *   If the page is empty, set the corresponding Page Table entry to `0`.
    *   If the page contains data:
        *   Check if `current_brick_count < MAX_VOLUME_BRICKS`.
        *   If yes, allocate a brick in the pool. Copy the $8^3$ core data. Fill the apron from neighboring logical texels (clamped). Set the Page Table entry to `current_brick_count + 1`. Increment `current_brick_count`.
        *   If no, the grid must coarsen. Perform a count-only pass to determine the next whole footprint multiple for coarsening, then rebuild with the new coarsening factor.
3.  Compute `buildGroundPageMax`: For terrain occlusion, compute the highest ground height under each page column, including a one-column halo for linear filtering. Store this for raymarching checks [S1, unofficial].

**Raymarching Step (GPU Shader):**
For each ray step:
1.  Calculate the logical page index for the current ray position.
2.  Fetch the RG8 entry from the Page Table.
3.  **Empty Space Skipping:**
    *   If entry == `0`:
        *   Check terrain occlusion: If the entire page lies wholly above the `buildGroundPageMax` value for that column, jump the ray to the exit face of that $8^3$ page in one loop iteration.
        *   Adjust the ray position to land back on the jittered sample lattice to maintain consistent sampling cadence [S1, unofficial].
        *   Continue to the next step.
    *   If entry != `0`:
        *   Lookup the brick in the Brick Pool at index `(entry - 1)`.
        *   Sample the volume trilinearly using the brick data.
        *   Perform standard volume integration/compositing.

## Subtopics

### [Sparse Brickmap Volume Rendering](2978-sparse-brickmap-volume-rendering.md)
Sparse Brickmap Volume Rendering is a voxel rendering technique that uses a two-level data structure (coarse brick grid and fine voxel bricks) to render sparse volumes efficiently, integrating hardware depth for correct compositing with rasterized geometry. It builds on [Sparse Page Table and Brick Pool](2550-sparse-page-table-and-brick-pool.md) by replacing the generic page-table indirection with a fixed $8^3$ brick hierarchy optimized for two-level Digital Differential Analyzer (DDA) traversal. Unlike dense voxel grids, it significantly reduces memory footprint by collapsing fully-buried terrain into uniform entries and storing only mixed (surface) bricks in a compact pool.

### Memory Pool Sizing
In related implementations (e.g., Ray-Guided Streaming), the node pool is typically small (4 MB), corresponding to $64^3$ entries. Using $16^3$ bricks, $1024^3$ indices can be referenced. The brick pool uses 430 MB, giving room for $42^3$ bricks [S2, unofficial].

### Multi-Resolution Multi-Channel Page Table (MRMCPT)
MRMCPT is a baseline out-of-core rendering method using a multi-resolution hierarchy managed via page tables for spatial subdivision and cache residency [S3]. It lacks the fine-grained empty-space skipping of octrees and residency octrees, resulting in higher cache usage and lower performance on sparse or multi-channel datasets. It is limited to skipping only entirely empty bricks, potentially accessing bricks containing values outside the current visible transfer function range [S3].

## Operating characteristics
**Time and Memory Complexity:**
*   **Memory:** Bounded by `MAX_VOLUME_BRICKS`. With 8192 bricks at 2 KB each, the pool is ~16.4 MB [S1, unofficial]. The page table size is proportional to the logical grid dimensions divided by $8^3$.
*   **Time:** Empty space skipping reduces the number of volume fetches and integrations. The ray jumps over empty pages in one iteration [S1, unofficial].

**Measured Performance:**
*   On live KATL (wide) data: Old dense grid 6.11M, Cubic at source res 5.08M (-17%), 2.75 power 6.12M (0%) [S1, unofficial].
*   On KATL close: Old 4.57M, Cubic 3.65M (-20%), 2.75 power 4.75M (+4%) [S1, unofficial].
*   On KSEA stratiform: Old 270k, Cubic 193k (-28%), 2.75 power 259k (-4%) [S1, unofficial].
*   Smoke Test: On a live KATL weather payload (456 × 385 × 96 logical texels at 1× coarsening), the system used 2,158 bricks and a 5.0 MB pool [S1, unofficial].

**Strengths and Limitations:**
*   **Strengths:** Full source resolution (up to 2048 cells/axis) without coarsening. Bounded memory usage. Efficient empty-space skipping.
*   **Limitations:** Requires careful handling of terrain occlusion to avoid skipping rays that intersect terrain within an empty page. Phase bleed can occur where empty texels bordering echo adopt the neighbor's phase in cores and aprons [S1, unofficial].

## Background
This method was implemented in the `approach-viz` project to render MRMS weather volumes in the web raymarcher, replacing a dense RG8 3D texture capped at 256 cells per axis [S1, unofficial]. It applies OpenVDB/NanoVDB concepts (empty-space skipping, leaf bricks with page table) to the web context without the library overhead [S1, unofficial].
