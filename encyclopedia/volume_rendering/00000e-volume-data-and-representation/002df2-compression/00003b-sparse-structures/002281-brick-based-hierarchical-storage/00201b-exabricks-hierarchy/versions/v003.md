# ExaBricks Hierarchy

Also called: ExaBricks, ExaBricks data structure

## Overview
ExaBricks is a rendering method for Block-Structured Adaptive Mesh Refinement (BS-AMR) data that reorganizes input cells into compact, non-overlapping bricks and uses Active Brick Regions (ABRs) to enable high-quality smooth interpolation across level boundaries without costly cell-location kernels [S1]. It sets itself apart from prior AMR rendering methods by decoupling storage (bricks) from spatial traversal (ABRs/BVH), allowing hardware-accelerated ray marching on RTX hardware while maintaining continuity at refinement interfaces [S1]. Unlike [Sparse Page Table and Brick Pool](2550-sparse-page-table-and-brick-pool.md) which focuses on general sparse volume residency, ExaBricks specifically addresses the topological discontinuities of AMR grids using a basis reconstruction filter [S1].

## How it works
The method operates in three stages: brick generation, ABR construction, and BVH traversal.

### Inputs and Outputs
*   **Input:** A set of AMR cells, each defined by lower-left coordinates $(i, j, k)$, level $l$, and a scalar value $v$. Level 0 is the finest level with implicit cell size $1^3$; level $l$ has cell size $2^l$. Coordinates are multiples of $2^l$. Cells do not overlap [S1].
*   **Output:** An RTX BVH built over ABRs, where each leaf contains a list of brick IDs and metadata, enabling ray marching and sample reconstruction.

### Data Structures

**1. Brick**
A brick is a compact, non-overlapping group of cells from the same AMR level.
*   **Fields:**
    *   `lower_left`: $(i, j, k)$ integer coordinates.
    *   `level`: Integer $l$.
    *   `dims`: $(N, M, K)$ number of cells in each dimension.
    *   `data`: A 3D array of scalars of size $N \times M \times K$.
*   **Layout:** Scalars are stored in a separate contiguous 3D array per brick [S1].

**2. Active Brick Region (ABR)**
An ABR is a leaf in a spatial partitioning structure that defines a region of space and the bricks influencing it.
*   **Fields:**
    *   `bounding_box`: Axis-aligned bounding box (AABB) of the region.
    *   `active_bricks`: List of brick IDs whose support overlaps this region.
    *   `min_val`: Minimum scalar value of any cell whose support overlaps the region.
    *   `max_val`: Maximum scalar value of any cell whose support overlaps the region.
    *   `finest_cell_width`: Cell width of the finest AMR level influencing the region.
*   **Layout:** Stored as nodes in a BVH [S1].

**3. Brick Support Fragment**
An intermediate structure used during ABR construction.
*   **Fields:**
    *   `box`: AABB representing the support region of a brick.
    *   `brick_id`: ID of the brick.

### Step 1: Brick Generation
Reorganize input AMR cells into bricks. The original AMR hierarchy is discarded [S1].

1.  **Build k-d Tree:** Construct a k-d tree top-down from the unordered list of input cells.
2.  **Splitting:** At each inner node, split the current set of cells along the longest axis of their combined bounding box.
3.  **Rounding:** Round split positions to an integer multiple of the current coarsest cell width among the cells in the node.
4.  **Leaf Creation:** Create a leaf node if:
    *   All cells in the node are on the same AMR level.
    *   The cells completely fill their combined bounding box (no gaps).
    *   The resulting brick is at most 32 cells wide on any axis.
5.  **Storage:** Store each leaf as a `Brick` with its lower-left corner, level, dimensions, and scalar data [S1].

### Step 2: ABR Construction
Build a spatial partitioning over the support regions of the bricks.

1.  **Compute Supports:** For each brick $B$ with cell width $C_w$, compute its support box. The support of a cell extends half a cell width beyond the cell. The support of a brick is the union of its cells' supports, resulting in a box exactly half the brick's cell width larger than the brick itself [S1].
2.  **Create Fragments:** Create a list of `Brick Support Fragments`, one per brick, containing the support box and brick ID.
3.  **Global Bounds:** Compute the bounding box of all fragments.
4.  **Recursive Subdivision:**
    *   **Input:** Current region (initially global bounds) and list of overlapping fragments.
    *   **Partitioning Plane:** Iterate through fragment boundaries. Select a plane from the fragment faces closest to the region's spatial center. Prefer the widest dimension for the split.
    *   **Leaf Condition:** If no valid partitioning plane exists (e.g., all fragments are identical or region is too small), create a leaf. The leaf's `active_bricks` is the list of fragment IDs overlapping the region.
    *   **Recurse:** If a plane exists, partition the region into left and right sub-regions. Sort fragments into left/right subtrees based on overlap. Recurse on both [S1].

### Step 3: BVH Construction and Rendering
1.  **Build BVH:** Construct an RTX BVH over the ABRs.
2.  **Ray Marching:** For each ray, traverse the BVH.
3.  **Space Skipping:** Use `min_val` and `max_val` in ABRs to skip regions where the scalar value is outside the transfer function range or isosurface threshold.
4.  **Adaptive Sampling:** Use `finest_cell_width` in ABRs to determine sampling density, ensuring the sampling frequency adapts to the finest level cell size [S1].

### Sample Reconstruction
When a ray sample point $p$ falls within an ABR leaf, reconstruct the value using the basis method.

1.  **Identify Influencing Cells:** Iterate over each brick ID in `active_bricks`.
2.  **Find Cells:** For each brick, find cells $C_i$ whose support contains $p$. Since bricks are regular 3D grids, this is a trivial coordinate lookup.
3.  **Compute Basis Function:** For each cell $C_i$ with width $C_w$ and center $C_{center}$:
    $$ \hat{h}(x) = \max(1 - x, 0) $$
    $$ \hat{H}_{C_i}(p) = \hat{h}\left(\frac{|C_{i,x} - p_x|}{C_w}\right) \hat{h}\left(\frac{|C_{i,y} - p_y|}{C_w}\right) \hat{h}\left(\frac{|C_{i,z} - p_z|}{C_w}\right) $$
    where $C_{i,x}$ is the coordinate of the cell center in the x-dimension [S1].
4.  **Reconstruct Value:**
    $$ B(p) = \frac{\sum_{C_i} \hat{H}_{C_i}(p) C_{v_i}}{\sum_{C_i} \hat{H}_{C_i}(p)} $$
    where $C_{v_i}$ is the scalar value of cell $C_i$. If the denominator is zero, the value is undefined or zero [S1].

### Parameters
*   **Brick Size Limit:** Maximum 32 cells wide on any axis [S1].
*   **Common Brick Sizes:** At level boundaries, bricks can be as small as $1^3$, $2^3$, or $4^3$ cells [S1].
*   **Basis Function:** Hat function $\hat{h}(x) = \max(1 - x, 0)$ [S1].

### Edge Cases and Pitfalls
*   **Empty Regions:** ABRs with no active bricks or zero support should be handled by space skipping using `min_val`/`max_val` [S1].
*   **Precision:** Coordinate rounding during brick generation must be consistent to avoid gaps or overlaps in the reconstructed field [S1].
*   **Support Overlap:** Smooth interpolants cause large support overlaps between neighboring bricks at different levels. The ABR structure is essential to handle this without per-sample k-d tree traversals [S1].

## Subtopics

### [Octant Method](2648-octant-method.md)
A reconstruction strategy for BS-AMR data that maps sample points to scalar values by decomposing the domain into non-overlapping rectilinear octants. It solves discontinuous interpolation at level boundaries by using octants that do not extend beyond parent cell bounds, unlike ExaBricks which uses overlapping support regions managed by ABRs. Choose when strict non-overlapping geometric decomposition is required over smooth filtering.

## Operating characteristics
*   **Time Complexity:** Brick generation is $O(N \log N)$ due to k-d tree construction. ABR construction is recursive and depends on the complexity of support overlaps. Ray traversal is $O(\log M)$ where $M$ is the number of ABRs. Sample reconstruction is proportional to the number of active bricks and cells in the support region, which is typically small and constant for local filters [S1].
*   **Memory Complexity:** Stores all cell data in bricks plus ABR metadata. The ABR structure adds overhead but avoids storing the full AMR hierarchy [S1].
*   **Performance:** Enables hardware-accelerated ray marching on RTX hardware. Avoids costly per-sample cell location kernels required by prior methods like Wald et al. [37] [S1].
*   **Strengths:** High-quality smooth interpolation across AMR level boundaries; efficient space skipping and adaptive sampling; simple data layout (regular 3D arrays per brick).
*   **Limitations:** Discards original AMR hierarchy, potentially losing some semantic information; support overlap can increase the number of cells accessed per sample compared to nearest-neighbor methods [S1].
*   **When to use:** Interactive direct volume rendering of AMR data requiring smooth gradients and isosurfaces.
*   **When not to use:** When preserving the exact AMR hierarchy is critical, or when nearest-neighbor performance is prioritized over smoothness [S1].

## Background
ExaBricks was introduced by Wald et al. in 2020 in the paper "Ray Tracing Structured AMR Data Using ExaBricks" [S1]. It builds on prior work by Kähler et al. [17] for brick organization and Wald et al. [37] for the basis reconstruction filter. The method addresses the limitations of previous AMR rendering techniques that suffered from discontinuous interpolation or high computational cost for cell location [S1].
