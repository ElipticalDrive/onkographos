# Segmented Dataset Quantization


## Overview
Segmented Dataset Quantization is a compression technique for volumetric segmentation data that reduces storage by restricting small spatial blocks to contain only one or two distinct label values [S1]. It solves the problem of high memory bandwidth and storage requirements for large-scale segmented volumes by encoding the block type and the geometric splitting plane that separates the two components [S1], distinguishing it from sibling methods like [Compressed Segmentation Volume](4985-compressed-segmentation-volume.md), [Multi-resolution Brick Encoding](5775-multi-resolution-brick-encoding.md), and [Random Access CSGV](10177-random-access-csgv.md) which employ different hierarchical or brick-based strategies [S1].

## How it works
**Inputs and Outputs:**
- Input: A 3D segmentation volume containing discrete label values [S1].
- Output: A compressed bitstream containing block type identifiers and splitting plane parameters [S1].

**Data Structures:**
For each spatial block, the method stores a block type identifier and, when applicable, a splitting plane that subdivides the block [S1].

**Steps:**
1. Partition the input volume into small, non-overlapping 3D blocks [G].
2. Analyze each block to count the number of unique label values present [G].
3. Assign a block type based on the unique label count: "single-label" if exactly one unique label exists, or "two-label split" if exactly two unique labels exist [S1].
4. For blocks assigned "two-label split", determine the splitting plane that subdivides the block [S1].
5. Encode the sequence of block types and splitting plane parameters [S1].
6. Compress the encoded sequence using an entropy coder [G].

**Formulas:**
Not given in the sources. [S1]

**Parameters:**
- Block size: Not given in the sources. [S1]
- Label precision: Not given in the sources. [S1]

**Edge Cases and Pitfalls:**
- Blocks containing more than two unique labels are not handled by the described method [S1].
- The exact encoding format, precision, and orientation constraints for the splitting plane are not specified [S1].
- Implementation requires a fallback strategy for $>2$ label blocks, which is not defined in the source [G].

**Pseudocode:**
```python
def segmented_dataset_quantization(volume, block_size):
    encoded_data = []
    for z in range(0, volume.shape[0], block_size):
        for y in range(0, volume.shape[1], block_size):
            for x in range(0, volume.shape[2], block_size):
                block = volume[z:z+block_size, y:y+block_size, x:x+block_size]
                unique_labels = set(block.flatten())
                num_labels = len(unique_labels)
                if num_labels == 1:
                    label_id = unique_labels.pop()
                    encoded_data.append(("single", label_id))
                elif num_labels == 2:
                    # Source does not specify algorithm for plane computation [S1]
                    plane_params = [0.0, 0.0, 0.0, 0.0] # Plane orientation and position [G]
                    encoded_data.append(("split", plane_params))
                else:
                    # Fallback for >2 labels not defined in source [S1]
                    encoded_data.append(("multi", 0))
    # 6. Compress the encoded sequence using an entropy coder [G]
    return encoded_data
```

## Subtopics

### [Evolutionary Volumetric Data Structure (EVDS) / L-Block Compression (LBC)](11032-evolutionary-volumetric-data-structure-evds-l-block-compress.md)
The Evolutionary Volumetric Data Structure (EVDS), stored as an L-block Covering (LBC), is a hierarchical sparse data structure designed for the real-time incremental compression and segmentation of filamentary volumetric data, such as neuronal tissue. It solves the problem of managing massive, sparse datasets by packaging significant data into connected L-blocks while ignoring empty space, allowing on-the-fly generation without storing the entire volume in memory. Unlike standard AABB-trees, the LBC allows for easy incremental box building and maintains connectivity between nodes without requiring traversal through a parent node. Choose this variant when working with highly sparse, filamentary datasets requiring incremental updates; avoid it for dense, uniformly distributed volumes.

## Operating characteristics
- **Time Complexity**: Not given in the sources. [S1]
- **Memory Complexity**: Proportional to the number of blocks times the average bits per block (1 label vs. 2 labels + plane) [S1].
- **Measured Performance**: Not given in the sources. [S1]
- **Strengths**: Reduces storage for homogeneous or bi-modal blocks [S1].
- **Limitations**: Limited to blocks with at most two labels; not suitable for complex multi-label regions without fallback [S1].
- **When to use**: Segmented volumes with large uniform regions or simple planar boundaries [S1].
- **When not to use**: Highly mixed label regions within small blocks [S1].

## Background
The method was proposed by Agus et al. [AGIM10] as a way to handle segmented datasets [S1]. It is designed for real-time rendering of time-varying volumetric datasets where limited bandwidth makes compressed representations essential [S1].
