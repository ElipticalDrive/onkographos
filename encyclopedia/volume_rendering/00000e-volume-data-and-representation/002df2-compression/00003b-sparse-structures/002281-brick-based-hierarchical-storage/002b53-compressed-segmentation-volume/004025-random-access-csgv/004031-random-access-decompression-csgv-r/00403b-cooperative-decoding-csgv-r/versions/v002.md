# Cooperative Decoding (CSGV-R)
Also called: Brick-wise Decompression Stage, brick cache (sm)

## Overview
Cooperative decoding is a GPU shader stage for Compressed Segmentation Volume Random Access (CSGV-R) where a single wavefront cooperatively decompresses one brick, eliminating the thread divergence inherent in serial CSGV decoding [S1]. It enables true random access rendering without the memory overhead and latency of a brick cache by leveraging shared memory for the wavelet tree [S1].

## How it works
**Inputs and Outputs:**
*   Input: Compressed brick data (wavelet tree) in global memory, requested Level of Detail (LOD), and voxel coordinates within the brick [S1].
*   Output: Decompressed volume label for the target voxel [G].

**Data Structures:**
*   **Shared Memory Cache:** A buffer sized to hold the wavelet tree of the current brick, referred to as "brick cache (sm)" [S1].
*   **Wavelet Tree:** The compressed representation of the brick's labels, stored in global memory and copied to shared memory [S1].

**Steps:**
1.  **Identify Brick:** The wavefront identifies the brick containing the requested voxel [G].
2.  **Load to Shared Memory:** The entire wavelet tree for the identified brick is copied from global memory to shared memory [S1]. This step is critical for performance [S1].
3.  **Cooperative Decompression:** Threads within the wavefront cooperate to decompress the brick [G]. Threads iterate over output voxels in the requested LOD [S1]. Each thread reads its specific volume label using the random access mechanism provided by CSGV-R [S1].
4.  **Return Label:** The decompressed label is returned to the rendering pipeline [G].

**Parameters:**
*   **LOD:** The level of detail requested by the renderer. Coarser LODs are faster to access [S1].

**Edge Cases and Pitfalls:**
*   **Shared Memory Size:** The shared memory must be large enough to hold the wavelet tree for the largest brick size supported [G].
*   **Wavefront Size:** The method assumes a wavefront size that matches or exceeds the number of voxels being cooperatively processed or the number of threads required for the decomposition logic [G].

**Pseudocode:**
```python
# Module-level constants for standard GPU kernel simulation
MAX_BRICK_DATA_SIZE = 4096
BRICK_TREE_SIZES = {0: 256, 1: 512, 2: 1024}
CHILDREN_PER_NODE = 8
LABEL_OFFSET = 1024

def cooperative_decode_brick(brick_id, target_voxel_coords, lod):
    # 1. Identify brick data location in global memory
    global_tree_offset = brick_id * MAX_BRICK_DATA_SIZE
    tree_size = get_brick_tree_size(brick_id)

    # 2. Copy wavelet tree to shared memory (brick cache (sm))
    shared_tree = [0] * tree_size
    for i in range(thread_id, tree_size, wavefront_size):
        shared_tree[i] = global_memory[global_tree_offset + i]

    # 3. Cooperative decomposition
    #    Threads in the wavefront iterate over output voxels in the requested LOD
    #    and read volume labels with random access as usual
    label = random_access_decode(shared_tree, target_voxel_coords, lod)

    return label

def get_brick_tree_size(brick_id):
    # Returns the exact byte count of the wavelet tree for the brick
    return BRICK_TREE_SIZES.get(brick_id, 256)

def random_access_decode(tree, coords, lod):
    # Standard CSGV-R random access traversal on the shared tree
    node_index = 0
    for level in range(lod, -1, -1):
        child_idx = coords[level]
        node_index = tree[node_index * CHILDREN_PER_NODE + child_idx]
    return tree[node_index * LABEL_OFFSET]
```

## Subtopics

### Brick Caching (CSGV)
CSGV supports caching full bricks decompressed by a separate shader up to a requested LOD with a one-frame latency [S1]. Cache regions are assigned as in shading atlas streaming [S1]. When a brick is first accessed and not present in the cache, a random sample from the brick palette or the most frequent label (first palette entry) is used as a placeholder [S1]. This results in visible popping artifacts [S1]. The CSGV cache barely fits all bricks for ambient occlusion configurations, and deeper traversal in path tracing will not allow decoding all visible voxels [S1].

## Operating characteristics
**Time and Memory Complexity:**
*   **Memory:** CSGV-R with cooperative decoding has no extra memory overhead during rendering beyond the VRAM required for the compressed volume itself [S1]. In contrast, CSGV requires extra memory for the cache of visible bricks [S1].
*   **Time:** Cooperative decoding avoids thread divergence caused by serial decoding (one thread per brick accessing different global memory regions) [S1].

**Measured Performance:**
Performance is measured in frame times (ms) for local shading [S1]:

| Dataset | CSGV rANS (brick cache) | CSGV-R (brick cache (sm)) |
| :--- | :--- | :--- |
| CELLS | 11.8 ms | 8.1 ms |
| FIBER | 6.0 ms | 4.5 ms |
| H01 | 4.1 ms | Not given in the sources. |
| AZBA | 10.3 ms | 9.3 ms |

For the FIBER dataset, cooperative decoding of bricks achieves the fastest rendering [S1].

**Strengths and Limitations:**
*   **Strengths:** Eliminates thread divergence, removes brick cache memory overhead, avoids popping artifacts associated with CSGV caching, and provides faster rendering for certain datasets (e.g., FIBER) [S1].
*   **Limitations:** Requires sufficient shared memory for the wavelet tree. Performance gains are dataset-dependent [S1].

**When to Use:**
Use when rendering CSGV-R volumes on GPUs with sufficient shared memory and when avoiding thread divergence and cache overhead is critical [S1].

## Background
Cooperative decoding was introduced as an alternative brick-wise decompression shader stage for CSGV-R in the paper "Random Access Segmentation Volume Compression for Interactive Volume Rendering" [S1]. It addresses the limitations of the original CSGV approach, which suffered from thread divergence and cache latency [S1].
