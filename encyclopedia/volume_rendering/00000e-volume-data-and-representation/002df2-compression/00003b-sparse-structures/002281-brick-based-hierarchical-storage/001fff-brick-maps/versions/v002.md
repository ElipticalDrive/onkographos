# Brick Maps

Also called: 3D Mipmaps

## Overview
Brick maps are a multi-resolution storage structure for 3D volume caches, analogous to 2D mipmaps, used to reduce aliasing (jiggle/noise) when rendering distant objects [S1, unofficial]. They provide automatic level-of-detail representation, avoiding the memory overhead of explicit LOD methods that require modeling objects multiple times [S2].

## How it works
**Inputs and Outputs:**
- Input: A base-resolution 3D voxel grid (typically a power of 2, e.g., 128³) [S1, unofficial].
- Output: A hierarchy of downsized grids (levels) stored in a single data structure [S1, unofficial].

**Data Structures:**
The structure consists of an array of grids [S1, unofficial]. Each grid at level $n$ has dimensions $R_n \times R_n \times R_n$, where $R_n$ is the base resolution at that level [S1, unofficial]. The data is typically stored as a contiguous array of floats (e.g., density) [S1, unofficial].

**Parameters:**
- `baseResolution`: The resolution of the finest level (level 0). Must be a power of 2 for trivial downsizing [S1, unofficial].
- `numLevels`: The total number of resolution levels, calculated as $\log_2(\text{baseResolution})$ [S1, unofficial]. The implementation often ignores the finest two levels (resolutions 2 and 4) to avoid excessive memory overhead or insufficient detail for very close views, resulting in `numLevels - 2` usable levels [S1, unofficial].

**Algorithm:**
1. Initialize level 0 with the original high-resolution voxel data [S1, unofficial].
2. Calculate `numLevels` based on `baseResolution` [S1, unofficial].
3. Iterate from level $n = 1$ to `numLevels - 2`:
   a. Set the resolution for level $n$ as half of level $n-1$: $R_n = R_{n-1} / 2$ [S1, unofficial].
   b. For each voxel $(x, y, z)$ in level $n$:
      i. Compute the value as the average of the 8 corresponding voxels from level $n-1$ [S1, unofficial].
      ii. Formula:
      $$ V_{n}(x,y,z) = 0.125 \times \sum_{i=0}^{1}\sum_{j=0}^{1}\sum_{k=0}^{1} V_{n-1}(2x+i, 2y+j, 2z+k) $$
      iii. This is equivalent to $0.125 \times \sum V_{n-1}(\dots)$ [S1, unofficial].
4. Store the resulting grid for level $n$ [S1, unofficial].

**Pseudocode:**
```python
import math

def create_brick_maps(level_0_data: list, base_resolution: int) -> list:
    """
    Creates a brick map hierarchy from a base resolution.
    level_0_data: flat list of floats for level 0.
    Memory layout: index = x * R^2 + y * R + z (x is slowest varying).
    """
    if base_resolution <= 0 or (base_resolution & (base_resolution - 1)) != 0:
        raise ValueError("Base resolution must be a positive power of 2")

    num_levels = int(math.log2(base_resolution))
    # Ignore resolutions 2 and 4 as per common practice
    # Iterate through levels n=1 to numLevels-2
    last_level = num_levels - 2

    brick_maps = [level_0_data]
    current_res = base_resolution

    for n in range(1, last_level + 1):
        next_res = current_res // 2
        new_data = [0.0] * (next_res ** 3)

        for x in range(next_res):
            for y in range(next_res):
                for z in range(next_res):
                    # Average of 8 voxels from the previous level
                    prev = brick_maps[n-1]
                    avg = (prev[(x*2)*current_res*current_res + (y*2)*current_res + (z*2)] +
                           prev[(x*2+1)*current_res*current_res + (y*2)*current_res + (z*2)] +
                           prev[(x*2)*current_res*current_res + (y*2+1)*current_res + (z*2)] +
                           prev[(x*2+1)*current_res*current_res + (y*2+1)*current_res + (z*2)] +
                           prev[(x*2)*current_res*current_res + (y*2)*current_res + (z*2+1)] +
                           prev[(x*2+1)*current_res*current_res + (y*2)*current_res + (z*2+1)] +
                           prev[(x*2)*current_res*current_res + (y*2+1)*current_res + (z*2+1)] +
                           prev[(x*2+1)*current_res*current_res + (y*2+1)*current_res + (z*2+1)])
                    new_data[x * next_res * next_res + y * next_res + z] = avg * 0.125

        brick_maps.append(new_data)
        current_res = next_res

    return brick_maps
```

**Edge Cases and Pitfalls:**
- The downsizing process is trivial only if the grid resolution is a power of 2 [S1, unofficial].
- If the camera gets too close (closer than the detail level the data were originally generated at), the finest brick map level is insufficient, and voxel disks become visible [S2].

## Subtopics

### Brick Map Level of Detail (LOD)
A technique using brick maps to provide automatic level-of-detail representation, avoiding the memory overhead of explicit LOD methods that require modeling objects multiple times [S2]. PRMan automatically chooses the appropriate level in the brick map based on size on screen or ray differential [S2]. If the object covers only a few pixels, only the top level bricks are read in [S2]. Parameters `detail1` and `detail2` determine at which size the brick map fades out and the original geometry fades in [S2]. The RIB idiom uses `Detail [xmin xmax ymin ymax zmin zmax]` as a ruler, then `DetailRange [0 0 detail1 detail2]` for the brick map and `DetailRange [detail1 detail2 1e38 1e38]` for the original geometry to switch between them [S2]. If the camera gets too close (closer than the detail level the data were originally generated at), the finest brick map level is insufficient, and voxel disks become visible [S2]. The solution is to switch to the original geometric primitive [S2].

## Operating characteristics
- **Time Complexity:** Building the brick map takes $O(N)$ time relative to the total number of voxels across all levels [S1, unofficial].
- **Memory Complexity:** The total memory required is the sum of all levels [S1, unofficial]. For a base resolution $R$, the total voxels are $R^3 (1 + 1/8 + 1/64 + \dots) \approx \frac{8}{7} R^3$ [S1, unofficial]. Ignoring the finest two levels reduces this slightly [S1, unofficial].
- **Performance:** Reduces aliasing (jiggle/noise) when rendering distant objects by sampling from lower-resolution bricks [S1, unofficial]. When an object covers only a few pixels, only the top-level bricks are read in [S2].
- **Strengths:** Automatic LOD, no need to model objects multiple times, reduces memory usage for distant objects [S2].
- **Limitations:** Cannot handle non-power-of-2 resolutions trivially; visible voxel artifacts if camera is too close; displacement shading on brick maps can cause torn geometry or is ignored for ray tracing [S2].

## Background
The term "brick map" was coined by the Pixar RenderMan team, though the exact origin is uncertain [S1, unofficial]. The concept of storing multiple resolutions of 3D data is not new, but the specific application to volume caches for rendering was popularized by RenderMan [S1, unofficial]. It is supported by production renderers and formats such as OpenVDB [S1, unofficial].
