# Volume Utility Functions

Also called: volume size fixing, region normalization, volpack normal encoding, memory alignment, scale unpacking, nifti analysis, modality detection

## Overview
Volume Utility Functions constitute a collection of low-level preprocessing and post-processing operations required to prepare volumetric data for rendering, compression, or analysis. They solve problems related to tensor dimensionality, intensity normalization, geometric resampling, memory alignment, and format-specific metadata handling. Unlike [Volume Normalization](1823-volume-normalization.md), which focuses on global intensity scaling strategies, these utilities provide specific, atomic operations such as Hounsfield unit clamping, voxel-scale resampling, and binary format conversions. They differ from [Preprocessing Pipeline](6733-preprocessing-pipeline.md) by being individual functional components rather than a sequential workflow.

## How it works
The following subsections detail the specific utility functions found in the source codebases.

### make_nd
Prepends singleton dimensions to a tensor until it reaches a target dimensionality $n$.

**Inputs:**
- `t`: Input tensor (NumPy or PyTorch).
- `n`: Target number of dimensions (integer).

**Outputs:**
- A tensor of shape $(1, 1, \dots, 1, t.shape[0], t.shape[1], \dots)$ with total length $n$.

**Steps:**
1. Check if $n < t.ndim$. If true, raise an exception.
2. Calculate the number of dimensions to prepend: $k = n - t.ndim$.
3. Prepend $k$ singleton dimensions to `t`.

**Pseudocode:**
```python
def make_nd(t, n):
    """
    Prepends singleton dimensions to tensor t until it is n-dimensional.
    Raises exception if n < t.ndim.
    """
    if n < t.ndim:
        raise ValueError(f"Target dimensions {n} is less than current dimensions {t.ndim}")
    
    # Prepend (n - t.ndim) dimensions of size 1
    # In NumPy/PyTorch, this is equivalent to adding axes at the front
    for _ in range(n - t.ndim):
        t = t.unsqueeze(0)
        
    return t
```

### normalize_hounsfield
Normalizes a volume assuming Hounsfield Unit (HU) scale, clamping values to $[0, 1]$.

**Inputs:**
- `vol`: Input volume (NumPy array or PyTorch tensor).
- `dtype`: Optional output data type.

**Outputs:**
- Normalized volume with values in $[0, 1]$.

**Steps:**
1. Divide all voxel values in `vol` by 4095.
2. Clamp the result to the range $[0, 1]$.

**Formula:**
$$ v_{out} = \text{clamp}\left(\frac{v_{in}}{4095}, 0, 1\right) $$

**Pseudocode:**
```python
def normalize_hounsfield(vol, dtype=None):
    """
    Normalizes volume by 4095 and clamps to [0, 1].
    Handles torch tensors and numpy arrays.
    """
    # Divide by 4095
    normalized = vol / 4095.0
    
    # Clamp to [0, 1]
    normalized = torch.clamp(normalized, 0.0, 1.0) if hasattr(torch, 'clamp') else np.clip(normalized, 0.0, 1.0)
    
    if dtype is not None:
        normalized = normalized.to(dtype)
        
    return normalized
```

### Volume Size Fixing
Corrects the Z dimension (frame count) of a volume based on actual data byte length.

**Inputs:**
- `volumeSize`: Array $[X, Y, Z]$ from file header.
- `data`: Raw byte buffer of the volume.

**Outputs:**
- Corrected `volumeSizeFixed`.

**Steps:**
1. Calculate `realFrameCount` as `data.byteLength` divided by `(volumeSize[0] * volumeSize[1])`.
2. If `realFrameCount` does not equal `volumeSize[2]`, log a warning.
3. Update `volumeSizeFixed[2]` to `realFrameCount`.
4. Return `volumeSizeFixed`.

**Pitfall:** The original file's `image_size[2]` attribute may be incorrect, requiring correction based on actual data size [S2, unofficial].

**Pseudocode:**
```python
def volume_size_fixing(volume_size, data_byte_length):
    """
    Corrects the volume size's Z dimension based on actual data byte length.
    """
    x, y, z = volume_size
    real_frame_count = data_byte_length // (x * y)
    
    if real_frame_count != z:
        print(f"Warning: Correcting Z dimension from {z} to {real_frame_count}")
        
    volume_size_fixed = [x, y, real_frame_count]
    return volume_size_fixed
```

### Region Normalization and Validation
Clamps region coordinates to valid chunk bounds and checks for empty regions.

**Inputs:**
- `region`: Array $[min_x, min_y, min_z, max_x, max_y, max_z]$.
- `height`: Height of the volume.
- `chunk_size`: Size of the processing chunk.
- `first_index`: Minimum valid index.

**Outputs:**
- Clamped region coordinates and boolean indicating if empty.

**Steps:**
1. Extract min and max coordinates from the region.
2. Clamp min coordinates:
   - $X, Z \in [\text{FIRST\_INDEX}, \text{CHUNK\_SIZE}]$
   - $Y \in [\text{FIRST\_INDEX}, \text{height}]$
3. Clamp max coordinates:
   - $X, Z \in [\text{min\_x}, \text{CHUNK\_SIZE}]$
   - $Y \in [\text{min\_y}, \text{height}]$
4. Check if region is empty: if $\text{min} \ge \text{max}$ in any axis, the region is empty.

**Pseudocode:**
```python
def region_normalization(region, height, chunk_size, first_index):
    """
    Clamps region coordinates to valid chunk bounds and checks if a region is empty.
    """
    min_x, min_y, min_z, max_x, max_y, max_z = region
    
    # Clamp min coordinates
    min_x = max(first_index, min_x)
    min_z = max(first_index, min_z)
    min_y = max(first_index, min_y)
    
    # Clamp max coordinates
    max_x = min(chunk_size, max_x)
    max_z = min(chunk_size, max_z)
    max_y = min(height, max_y)
    
    # Check if empty
    is_empty = (min_x >= max_x) or (min_y >= max_y) or (min_z >= max_z)
    
    return [min_x, min_y, min_z, max_x, max_y, max_z], is_empty
```

### Memory Alignment / Word Alignment
Rounds up a byte count to the nearest word size.

**Inputs:**
- `byteCount`: Input byte count.
- `wordSize`: Alignment size in bytes.

**Outputs:**
- Aligned byte count.

**Steps:**
1. Calculate aligned size: $\lceil \frac{\text{byteCount}}{\text{wordSize}} \rceil \times \text{wordSize}$.

**Pseudocode:**
```python
def align_up(byte_count, word_size):
    """
    Rounds up byteCount to the nearest wordSize.
    """
    return ((byte_count + word_size - 1) // word_size) * word_size
```

### Scale Unpacking
Decodes packed scale data from a buffer into floating-point log-scale values.

**Inputs:**
- `src`: Byte buffer.
- `coordCount`: Number of scale values (pointCount * 3).

**Outputs:**
- `out`: Array of floating-point log-scale values.

**Steps:**
1. Iterate `coordCount` times.
2. For each byte `src[i]`, compute `out[i] = src[i] / 16.0f - 10.0f`.

**Pseudocode:**
```python
def scale_unpacking(src, coord_count):
    """
    Decodes packed scale data from a buffer into floating-point log-scale values.
    """
    out = [0.0] * coord_count
    for i in range(coord_count):
        out[i] = src[i] / 16.0 - 10.0
    return out
```

### Modality Detection via Intensity Threshold
Heuristically classifies volume data as CT or MRI based on minimum scalar value.

**Inputs:**
- `volume`: Volume array.

**Outputs:**
- String: 'CT' or 'MRI'.

**Steps:**
1. Calculate the minimum intensity value in the volume array.
2. If $\min < -500$, classify as 'CT'.
3. Otherwise, classify as 'MRI'.

**Pseudocode:**
```python
def modality_detection(volume):
    """
    Heuristically classifies loaded volume data as CT or MRI based on minimum scalar value.
    """
    min_val = np.min(volume)
    if min_val < -500:
        return 'CT'
    else:
        return 'MRI'
```

## Subtopics

### [Volume Resize and Save](2904-volume-resize-and-save.md)
Performs post-processing on a reconstructed 3D volume by resizing it to a target dimension, normalizing intensity values, and optionally saving the data as image slices or raw binary files. It solves the problem of converting raw reconstruction outputs into standardized formats for visualization or downstream analysis. It differs from [Image Resizing Utilities](11843-image-resizing-utilities.md) by including specific normalization and rotation steps, and from [Vector Normalization](3145-vector-normalization.md) by handling 3D tensor structures and file I/O.

### [Vector Normalization](3145-vector-normalization.md)
Converts a 3D vector into a unit vector (magnitude 1) or identifies its dominant axis, serving as a fundamental preprocessing step for vector field visualization, compression, and geometric calculations in volume rendering. It differs from [Octahedral Normal Encoding](5029-octahedral-normal-encoding.md) by producing a full 3D float vector rather than a compressed 2D coordinate, and from [Half-Precision Float Conversion](3267-half-precision-float-conversion.md) by focusing on directional magnitude rather than bit-depth reduction.

### [Half-Precision Float Conversion](3267-half-precision-float-conversion.md)
Converts between 32-bit IEEE 754 single-precision floats and 16-bit binary16 half-precision floats, and vice versa. It solves the problem of reducing memory bandwidth and storage for volume data while maintaining sufficient precision for rendering, avoiding undefined behavior associated with direct type punning. Unlike sibling utilities that normalize vectors or resize images, this method performs strict numerical format conversion with specific handling for subnormal numbers, overflow, and NaN preservation.

### [Image Resizing Utilities](11843-image-resizing-utilities.md)
Provides a suite of deterministic functions for manipulating image arrays, including resizing (downsampling, upsampling, rescaling), type conversion, and geometric adjustments. They solve the problem of preparing image data for neural network inputs or downstream processing by ensuring correct data types, dimensions, and divisibility constraints. Unlike generic resizing libraries, these utilities enforce strict integer-scale operations where possible to avoid interpolation artifacts and provide specific helpers like `make_divisible` to align dimensions to hardware or model requirements.

### [VTK Image Data Construction from NumPy](15604-vtk-image-data-construction-from-numpy.md)
Imports volume data from NumPy arrays or NIfTI files into VTK, ensuring correct memory layout, data spacing, and origin configuration for normalized volume rendering, particularly for Diffusion Weighted Imaging (DWI) images. It differs from generic array conversion by explicitly handling the geometric metadata (spacing/origin) required to prevent visual artifacts such as volumes appearing too thin.

## Operating characteristics
The utility functions are generally $O(N)$ with respect to the number of voxels or bytes processed, where $N$ is the volume size or data length. Memory complexity is $O(1)$ auxiliary space for functions like `make_nd` (which may allocate a new tensor) and $O(N)$ for resampling functions like `normalize_voxel_scale` which produce a new volume. Performance is dominated by memory bandwidth for I/O-heavy utilities (e.g., `volume_size_fixing`, `scale_unpacking`) and interpolation cost for `normalize_voxel_scale`. These functions are lightweight and suitable for preprocessing pipelines. They are not suitable for real-time rendering without caching, as they are designed for data preparation.

## Background
These utilities originate from various open-source volume rendering and medical imaging projects. `make_nd` and `normalize_hounsfield` are from `flashdrr` [S1, unofficial]. `volume_size_fixing` is from `web-vol-viewer` [S2, unofficial]. `region_normalization` is from `mc-meshing` [S3, unofficial]. `VolPack` functions are from the VolPack User's Guide [S4]. `align_up` is from OpenVDB [S5]. `scale_unpacking` is from `spz` [S6, unofficial]. `nifti_analysis` is from `vrdf-sdk` [S7, unofficial]. `modality_detection` is from `medviewer` [S8, unofficial].
