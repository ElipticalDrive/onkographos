# Dodecahedron Subdivision Normal Quantization

Also called: Static Normal Vector Quantizer (Dodecahedron Subdivision)

## Overview
Dodecahedron Subdivision Normal Quantization is a static method for generating a set of normal vector directions by tessellating a unit sphere using a subdivided regular dodecahedron [S1]. It solves the problem of directional aliasing in volume rendering, where gradient vectors are quantized to a discrete set of directions [S1]. It is distinguished from its parent [Spherical Tessellation for Normal Quantization](6262-spherical-tessellation-for-normal-quantization.md) by its specific geometric construction using the dodecahedron's pentagonal faces, and from [Gradient Quantization via Polyhedron Tesselation](#gradient-quantization-via-polyhedron-tesselation) by its fixed 240-vector output rather than a variable count based on refinement levels.

## How it works
**Inputs:** A continuous gradient vector $\mathbf{g}$ (or normal vector) derived from volume data.
**Outputs:** A quantized normal vector $\mathbf{n}_{q}$ chosen from a precomputed set of 240 directions.

**Data Structures:**
The method relies on a static lookup table (LUT) of 240 unit vectors. These vectors correspond to the centers of gravity of the triangles in the tessellated sphere. The table is generated once and stored as 240 $(x, y, z)$ coordinates, typically as 32-bit floats or 16-bit fixed-point values.

**Steps:**
1.  **Initialization (Offline):**
    1.  Start with a regular dodecahedron inscribed in the unit sphere.
    2.  Identify the 12 pentagonal faces of the dodecahedron.
    3.  Subdivide each pentagonal face into triangles. The source describes this as "triangulating each pentagon uniformly" [S3, unofficial] or implicitly via the subdivision process that yields 60 initial triangles [S1].
    4.  Subdivide each of the resulting 60 triangles into four smaller triangles by connecting the midpoints of the sides and projecting the new vertices onto the unit sphere [S1][S3, unofficial].
    5.  This yields a tessellation of 240 triangles ($60 \times 4$) [S1].
    6.  Calculate the center of gravity (centroid) for each of the 240 triangles.
    7.  Normalize these centroids to unit length to form the quantization codebook $\mathcal{C} = \{\mathbf{c}_1, \mathbf{c}_2, ..., \mathbf{c}_{240}\}$ [S1][S3, unofficial].

2.  **Quantization (Runtime):**
    1.  For a given input gradient vector $\mathbf{g}$, normalize it to $\hat{\mathbf{g}} = \mathbf{g} / \|\mathbf{g}\|$.
    2.  Determine which triangle in the tessellation contains $\hat{\mathbf{g}}$. This is equivalent to finding the codebook entry $\mathbf{c}_i$ that maximizes the dot product $\hat{\mathbf{g}} \cdot \mathbf{c}_i$ (or minimizes the angular distance) [S1].
    3.  Quantize $\hat{\mathbf{g}}$ to the center of gravity of that triangle: $\mathbf{n}_{q} = \mathbf{c}_i$ [S1].

**Parameters:**
*   **Total normal vectors:** 240 [S1].
*   **Angle between adjacent normals:** Approximately 23 degrees [S3, unofficial].

**Pseudocode:**
```python
# Precomputed codebook generation (Offline)
def generate_dodecahedron_quantizer():
    # 1. Define regular dodecahedron vertices and faces
    # A regular dodecahedron has 12 pentagonal faces.
    # Each pentagon is subdivided into triangles. 
    # The source states this results in 60 initial triangles before the 4-split.
    # We assume a standard triangulation of the 12 pentagons into 60 triangles.
    
    initial_triangles = triangulate_dodecahedron_faces() # Returns 60 triangles
    
    subdivided_triangles = []
    for tri in initial_triangles:
        # Subdivide each triangle into 4 smaller triangles
        # Connect midpoints of sides
        m1 = midpoint(tri.v1, tri.v2)
        m2 = midpoint(tri.v2, tri.v3)
        m3 = midpoint(tri.v3, tri.v1)
        
        # Project midpoints to unit sphere
        m1 = normalize(m1)
        m2 = normalize(m2)
        m3 = normalize(m3)
        
        # The 4 new triangles are:
        # (v1, m1, m3), (m1, v2, m2), (m3, m2, v3), (m1, m2, m3)
        # Note: The source [S1] says "subdivide each of the 60 triangles into four smaller triangles"
        # and [S3, unofficial] says "performing a four-split operation on the resulting triangles".
        
        new_tris = [
            Triangle(tri.v1, m1, m3),
            Triangle(m1, tri.v2, m2),
            Triangle(m3, m2, tri.v3),
            Triangle(m1, m2, m3)
        ]
        subdivided_triangles.extend(new_tris)
        
    # 2. Calculate centers of gravity for the 240 triangles
    codebook = []
    for tri in subdivided_triangles:
        centroid = (tri.v1 + tri.v2 + tri.v3) / 3.0
        codebook.append(normalize(centroid))
        
    return codebook

# Runtime quantization
def quantize_normal(g, codebook):
    # Normalize input gradient
    g_hat = normalize(g)
    
    # Find best match
    best_idx = 0
    best_dot = -1.0
    
    for i, c in enumerate(codebook):
        dot = dot_product(g_hat, c)
        if dot > best_dot:
            best_dot = dot
            best_idx = i
            
    return codebook[best_idx]
```

**Edge Cases and Pitfalls:**
*   **Zero Gradient:** If $\mathbf{g}$ is a zero vector, normalization fails. A default normal (e.g., $(0,0,1)$) or the nearest codebook entry to a predefined axis should be used [G].
*   **Boundary Precision:** The "center of gravity" calculation assumes planar triangle vertices. On a sphere, the centroid of spherical triangle vertices is not the same as the centroid of the spherical surface area. The source specifies using the center of gravity of the triangle [S1], which implies the Euclidean centroid of the vertices projected to the sphere, rather than the spherical centroid [S1][S3, unofficial].
*   **Directional Aliasing:** The method exhibits strong "directional aliasing" because the distribution, while better than octahedral, is not perfectly uniform [S1].

## Subtopics

### Gradient Quantization via Polyhedron Tesselation
A variant that combines the icosahedron (12 vertices) and dodecahedron (20 vertices) to start with 32 vertices and 60 congruent (but not equilateral) triangles [S2, unofficial]. It refines quantization via recursive subdivision by connecting midpoints, yielding $g = 30 \cdot 4^k + 2$ vertices after $k$ levels [S2, unofficial]. Typical value is $k=4$, yielding 7682 vertices [S2, unofficial]. It is superior to octahedron-based subdivision because octahedron triangles retain 90° angles causing uneven distribution, whereas icosahedron/dodecahedron triangles are more nearly planar and undergo less distortion [S2, unofficial].

### Point-Based Data Encoding with Quantized Normals
A storage scheme that uses the 240 dodecahedron-subdivision normals to reduce file size [S3, unofficial]. It stores point positions relative to the first valid point, with z-values implicit, and x/y coordinates explicit [S3, unofficial]. It uses background-images to zero out histogram entries for background colors to prevent noise from inflating storage [S3, unofficial]. Worst-case storage is approx 256 Gigabytes for a $4096^3$ volume with 255 colors [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** Quantization is $O(N)$ where $N=240$ is the number of codebook entries. This is constant time relative to scene complexity but linear relative to codebook size.
*   **Memory Complexity:** The codebook requires storage for 240 vectors. If stored as 32-bit floats, this is $240 \times 12 = 2880$ bytes [S1].
*   **Performance:** The method is computationally inexpensive compared to data-dependent methods like Simulated Annealing [S1].
*   **Strengths:** Simple to implement; provides better uniformity than octahedral subdivision; fits within standard 256-entry hardware color maps (using 240 entries) [S1].
*   **Limitations:** Static distribution may not be optimal for specific datasets; directional aliasing is still present [S1].
*   **When to use:** When hardware limits color maps to 256 entries and a static, uniform normal distribution is sufficient [S1].
*   **When not to use:** When data-dependent optimization is required for higher quality [S1].

## Background
The method was introduced in the context of interactive volume rendering using 3D texture mapping [S1]. It was developed to address the limitations of previous methods that did not allow for directional lighting effects or required recalculation after rotation [S2, unofficial]. The specific 240-vector quantizer is described as the "normal vector quantizer used in current implementations" at the time of writing [S1]. It is part of the Voltx method family [S1].
