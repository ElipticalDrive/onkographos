# Octahedral Direction Encoding for Gradient Storage

Also called: Octahedral Normal Quantization, Octahedral Sphere Subdivision for Gradients, Precomputed Gradient Storage with Octahedral Direction Encoding

## Overview
Octahedral Direction Encoding is a technique to reduce memory usage for precomputed volume gradients by quantizing direction using uniform fractal subdivision of an octahedron into a sphere, rather than storing raw floating-point vectors [S1, book]. It solves the problem of excessive memory consumption in precomputed radiance transfer or similar gradient-based volume rendering methods, where storing full 3D gradient vectors for every voxel is prohibitive [S1, book]. It sets itself apart from naive component-wise quantization by providing a uniform distribution of directions on the sphere, avoiding the clustering artifacts inherent in dividing bits among three independent components [S1, book].

## How it works
**Inputs and Outputs:**
*   **Input:** A target recursion depth $d$ determining the resolution of the tessellation.
*   **Output:** A lookup table mapping 3D gradient direction vectors to integer indices, and a method to decode indices back to approximate direction vectors.

**Data Structures:**
*   **Index Table:** An array of size $N$ where $N$ is the total number of indices generated by the tessellation. For recursion depth $d=6$, $N=16,642$ [S1, book].
*   **Storage Type:** Unsigned short (16-bit) is sufficient for $d \le 6$ [S1, book].

**Algorithm Steps:**

1.  **Tessellation Generation:**
    Generate vertices by recursively replacing each triangle of the initial octahedron with four new triangles. The recursion depth $d$ determines the resolution.
    *   Initial octahedron has 8 triangular faces.
    *   At each recursion step, every triangle is subdivided into 4 smaller triangles by connecting the midpoints of the edges.
    *   Project the new vertices onto the unit sphere to maintain the spherical shape [S1, book].
    *   The vector directions encoded are all directions formed by creating a ray originating at the sphere's center and passing through a vertex of the sphere [S1, book].

2.  **Projection to Octahedron Faces:**
    Map the spherical vertices back to the surface of the original octahedron. This is done by "pushing" each vertex radially outward until it intersects the plane of the nearest octahedron face.
    *   For a vertex $\mathbf{v} = (x, y, z)$, determine which face of the octahedron it belongs to based on the maximum absolute component.
    *   Normalize the vector such that the maximum absolute component is 1. For example, if $|x|$ is the maximum, the projected point is $(\text{sgn}(x), y/x, z/x)$ [S1, book].

3.  **Flattening:**
    Flatten the projected vertices onto the plane $z=0$. This effectively creates a 2D grid representation of the octahedron's faces [S1, book].

4.  **Rotation:**
    Rotate the resulting 2D grid by $45^\circ$. This alignment ensures that the grid axes align with the coordinate axes for easier indexing [S1, book].

5.  **Indexing:**
    Label the vertices in the rotated grid with indices starting at 0 at the top-left vertex. Continue labeling across the rows, then down the columns.
    *   The labeling covers the positive $z$ hemisphere first.
    *   Indices $0$ through $40$ represent vectors with a positive or zero $z$ component [S1, book].
    *   Index 40 is located at the lower right vertex of the positive $z$ grid [S1, book].

6.  **Negative Z Handling:**
    Use indices $41$ through $81$ to represent vectors with a negative $z$ component.
    *   This separation is necessary because flattening the octahedron places two vertices on top of each other for all but the edge locations [S1, book].
    *   The negative $z$ indices correspond to the same geometric positions but represent the opposite hemisphere [S1, book].

7.  **Edge Case Handling:**
    Vertices on the edges of the octahedron represent vectors with a zero $z$ component.
    *   Although these could be represented with a single index, using two indices (one from the positive set and one from the negative set, or duplicating the index) keeps the indexing scheme consistent and easier to implement [S1, book].
    *   Specifically, for vectors with $z=0$, the scheme allows representation via two indices to maintain consistency [S1, book].

def generate_octahedral_indices(recursion_depth):
    """
    Generates indices for octahedral direction encoding.
    
    Args:
        recursion_depth (int): The depth of recursive subdivision.
        
    Returns:
        dict: A mapping from (x, y, z) direction vectors to indices.
              Note: In practice, this is often precomputed and stored as a lookup table.
    """
    # Step 1: Generate vertices via recursive subdivision
    # Start with the 8 faces of an octahedron
    # Vertices of initial octahedron: (±1, 0, 0), (0, ±1, 0), (0, 0, ±1)
    # For recursion_depth d, the number of vertices grows exponentially.
    # We need to collect all unique vertex positions on the sphere.
    
    vertices = get_initial_octahedron_vertices()
    
    for _ in range(recursion_depth):
        new_vertices = []
        for triangle in get_triangles(vertices):
            # Subdivide triangle into 4 smaller triangles
            midpoints = [
                normalize((triangle[0] + triangle[1]) / 2),
                normalize((triangle[1] + triangle[2]) / 2),
                normalize((triangle[2] + triangle[0]) / 2)
            ]
            # Create 4 new triangles
            new_triangles = [
                (triangle[0], midpoints[0], midpoints[2]),
                (midpoints[0], triangle[1], midpoints[1]),
                (midpoints[2], midpoints[1], triangle[2]),
                (midpoints[0], midpoints[1], midpoints[2])
            ]
            new_vertices.extend([t[0] for t in new_triangles] + 
                                [t[1] for t in new_triangles] + 
                                [t[2] for t in new_triangles])
        vertices = list(set(new_vertices)) # Remove duplicates

    # Step 2 & 3: Project to octahedron faces and flatten
    # Map spherical vertex v to octahedron face
    projected_vertices = []
    for v in vertices:
        x, y, z = v
        # Determine max absolute component
        abs_x, abs_y, abs_z = abs(x), abs(y), abs(z)
        if abs_x >= abs_y and abs_x >= abs_z:
            # Project to x-face
            p = (1 if x > 0 else -1, y/x, z/x)
        elif abs_y >= abs_x and abs_y >= abs_z:
            # Project to y-face
            p = (x/y, 1 if y > 0 else -1, z/y)
        else:
            # Project to z-face
            p = (x/z, y/z, 1 if z > 0 else -1)
        projected_vertices.append(p)

    # Step 4: Rotate by 45 degrees
    # Rotation matrix for 45 degrees around z-axis
    cos_45 = 1 / sqrt(2)
    sin_45 = 1 / sqrt(2)
    rotated_vertices = []
    for p in projected_vertices:
        x, y, z = p
        # Rotate (x, y) in the plane
        x_new = x * cos_45 - y * sin_45
        y_new = x * sin_45 + y * cos_45
        rotated_vertices.append((x_new, y_new, z))

    # Step 5 & 6: Indexing
    # Separate into positive and negative z
    pos_indices = {}
    neg_indices = {}
    
    # Sort vertices to assign indices consistently
    # The source specifies starting at top-left, across rows, then down columns.
    # This implies a grid structure. We need to map the continuous coordinates to a grid.
    # For recursion depth 6, there are 16,642 indices.
    
    # Simplified indexing logic based on source description:
    # Indices 0-40 for positive z (half the normals)
    # Indices 41-81 for negative z (in the small example)
    # For depth 6, the range is larger.
    
    # The source states: "This leads to 16,642 indices representing 16,386 unique directions."
    # This implies some indices are duplicates or edge cases.
    
    # Implementation note: The exact mapping requires sorting the rotated vertices
    # into a grid and assigning indices. The source does not provide the exact sorting key
    # other than "top-left". Typically, this is done by sorting by y (descending) then x (ascending).
    
    # For the purpose of this article, we assume a precomputed lookup table is used.
    # The key is the direction vector (or its quantized form).
    
    return pos_indices, neg_indices

def encode_gradient(gradient_vector, lookup_table):
    """
    Encodes a gradient vector into an index.
    
    Args:
        gradient_vector (tuple): (gx, gy, gz)
        lookup_table (dict): Mapping from normalized direction to index.
        
    Returns:
        int: The encoded index.
    """
    # Normalize the gradient vector
    norm = sqrt(gx**2 + gy**2 + gz**2)
    if norm == 0:
        return 0 # Handle zero vector appropriately [G]
    
    normalized = (gx/norm, gy/norm, gz/norm)
    
    # Look up the index
    # Note: Due to floating point precision, exact match might fail.
    # In practice, a nearest-neighbor search in the lookup table is used.
    index = lookup_table.get(normalized)
    
    if index is None:
        # Fallback: find nearest vertex in the octahedral tessellation
        index = find_nearest_index(normalized, lookup_table)
        
    return index

def decode_index(index, lookup_table_reverse):
    """
    Decodes an index back to a direction vector.
    
    Args:
        index (int): The encoded index.
        lookup_table_reverse (dict): Mapping from index to direction vector.
        
    Returns:
        tuple: (dx, dy, dz)
    """
    return lookup_table_reverse[index]

**Parameters:**
*   **Recursion Depth:** Determines the number of quantization levels. Depth 6 is a common choice, yielding 16,642 indices [S1, book].
*   **Storage Type:** Unsigned short (16-bit) is sufficient for depth 6 [S1, book].

**Edge Cases and Pitfalls:**
*   **Zero Z-Component:** Vertices on the edges of the octahedron have a zero $z$ component. The scheme uses two indices for these to maintain consistency, rather than a single index [S1, book].
*   **Precision:** Floating-point comparisons for direction matching may require tolerance or nearest-neighbor search [G].
*   **Memory:** While reduced compared to full float storage, the lookup table itself consumes memory. For depth 6, the table size is manageable [S1, book].

## Subtopics

### Gradient Direction Encoding via Octahedron Flattening
A method to encode 3D gradient directions into a compact index by flattening an octahedron, using two sets of indices to handle positive and negative z-components [S1, book]. It uses indices 0 through 40 to represent vectors with a positive or zero z component, where index 40 is at the lower right vertex [S1, book]. It uses indices 41 through 81 to represent vectors with a negative z component [S1, book]. For vertices on the edges (vectors with no z component), it uses two indices instead of one to keep the indexing scheme consistent [S1, book]. Storage type is unsigned short [S1, book]. Recursion depth is 6 when generating vertices with unsigned short storage [S1, book]. Degenerate edge cases (vectors with zero z component) are handled by duplicating indices to maintain consistency, rather than using a single index [S1, book]. With recursion depth 6, there are 16,642 indices representing 16,386 unique directions [S1, book].

## Operating characteristics
**Time and Memory Complexity:**
*   **Memory:** Naive storage for a $256^3$ dataset with 1-byte scalars increases from 16 Mbytes to 218 Mbytes when storing 4-byte floats per gradient component per scalar [S1, book]. Octahedral encoding significantly reduces this by storing only indices (e.g., 2 bytes per index) plus a small lookup table [S1, book].
*   **Time:** Encoding requires normalizing the gradient and looking up the index. Decoding requires a table lookup. Precomputing illumination for each index allows fast rendering [S1, book].

**Measured Performance:**
*   For a $256^3$ dataset, naive storage is 218 Mbytes [S1, book].
*   With recursion depth 6, 16,642 indices are used [S1, book].

**Scaling:**
*   Memory usage scales linearly with the number of voxels and the size of the lookup table (which grows exponentially with recursion depth) [S1, book].

**Strengths and Limitations:**
*   **Strengths:** Uniform distribution of directions, significant memory reduction, simple indexing scheme [S1, book].
*   **Limitations:** Limited number of directions (quantization error), only applicable to precomputed gradients [S1, book].

**When to Use:**
*   Use when memory is constrained and gradients are precomputed [S1, book].
*   Do not use when high-fidelity direction representation is required or when gradients are computed on the fly [S1, book].
