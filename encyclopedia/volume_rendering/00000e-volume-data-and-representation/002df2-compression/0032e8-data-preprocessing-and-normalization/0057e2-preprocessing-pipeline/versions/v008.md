# Preprocessing Pipeline

Also called: VolCon and Compress Pipeline, Volume Preprocessing Pipeline, buildVolumeImage, crop-downsample-convert

## Overview
The Preprocessing Pipeline prepares raw volumetric data for rendering by applying label banding, cropping to the body bounding box, downsampling, adjusting spacing, and optionally converting to 16-bit float before wrapping in VTK `imageData` [S2, unofficial]. It solves the problem of preparing heterogeneous raw volume inputs into a standardized, memory-efficient format suitable for GPU rendering. It differs from the [Volume Partitioning Pipeline](11585-volume-partitioning-pipeline.md) by processing the volume as a monolithic entity rather than splitting it into disjoint foreground regions, and from the [3D Seismic Data Compression Pipeline](11727-3d-seismic-data-compression-pipeline.md) by using generic intensity thresholds rather than seismic-specific physics [S1].

## How it works
**Inputs:** Raw volume data (e.g., DICOM slices, NIfTI, or raw binary files), optional label maps, and configuration parameters (`PERF` object).
**Outputs:** A VTK `imageData` object containing the processed voxel data, spacing, origin, and dimensions.

**Data Structures:**
*   `PERF`: Configuration object containing:
    *   `crop` (boolean): Enable body bounding box cropping.
    *   `down` (integer): Downsampling factor.
    *   `tex` (string): Texture format flag. `'f16'` triggers 16-bit float conversion.
*   `AIR_HU`: Constant threshold value for air outside the body, typically -500 [S2, unofficial].

**Steps:**
1.  **Label Banding:** If label maps exist, apply `bandLabeledHuValues` to map raw Hounsfield Unit (HU) values to labeled bands. If no labels exist, use raw values [S2, unofficial].
2.  **Cropping:** If `PERF.crop` is true:
    *   Compute the body bounding box by identifying the extent of voxels with values greater than `AIR_HU` (-500) [S2, unofficial].
    *   Crop the volume to this bounding box.
    *   Shift the volume origin to preserve world coordinates relative to the original dataset [S2, unofficial].
3.  **Downsampling:** Apply `strideDownsample` to the volume using the factor `PERF.down`. This reduces the spatial resolution by selecting every $n$-th voxel along each axis [S2, unofficial].
4.  **Spacing Adjustment:** Multiply the original voxel spacing by `PERF.down` to maintain the correct physical dimensions of the cropped volume [S2, unofficial].
5.  **Format Conversion:** If `PERF.tex` is `'f16'`:
    *   Convert the voxel data values to 16-bit floating-point format [S2, unofficial].
    *   Set the mapper's `preferSizeOverAccuracy` flag to true, prioritizing rendering speed over precision [S2, unofficial].
6.  **VTK Wrapping:** Construct a `vtkImageData` object using the new dimensions, adjusted spacing, shifted origin, and processed scalar data [S2, unofficial].
7.  **Binding:** Bind the `vtkImageData` data to the volume mapper for rendering [S2, unofficial].

**Pitfalls:**
*   **Precision and Endianness:** When handling raw binary buffers in JavaScript environments, reinterpreting a `Uint8Array` buffer as a `Float32Array` is safe because JS engines are natively little-endian and metadata validates `byte_order === 'little'`. Using `DataView` for byte-by-byte reading is significantly slower (~15s+ for a 145MB volume) and causes stale canvas frames during dataset switches [S2, unofficial].

**Pseudocode:**
```python
def preprocess_volume(raw_data, labels, perf_config):
    """
    Preprocess raw volume data for rendering.
    
    Args:
        raw_data: 3D array or buffer of raw voxel values.
        labels: Optional 3D array of label IDs.
        perf_config: Dict with keys 'crop' (bool), 'down' (int), 'tex' (str).
        
    Returns:
        vtkImageData object.
    """
    AIR_HU = -500
    
    # Step 1: Label Banding
    if labels is not None:
        # Apply banding function to map HU values to labels
        # Implementation detail: bandLabeledHuValues is assumed to be defined elsewhere
        data = band_labeled_hu_values(raw_data, labels)
    else:
        data = raw_data.copy()
        
    # Step 2: Cropping
    origin = [0, 0, 0] # Placeholder for original origin
    if perf_config['crop']:
        # Compute bounding box of voxels > AIR_HU
        mask = data > AIR_HU
        if not np.any(mask):
            raise ValueError("No body tissue found above AIR_HU threshold")
        
        coords = np.argwhere(mask)
        min_coords = coords.min(axis=0)
        max_coords = coords.max(axis=0)
        
        # Crop to bounding box
        data = data[min_coords[0]:max_coords[0]+1, 
                    min_coords[1]:max_coords[1]+1, 
                    min_coords[2]:max_coords[2]+1]
        
        # Shift origin to preserve world coordinates
        # Assuming original origin was (0,0,0) for simplicity, 
        # new origin corresponds to min_coords in world space
        origin = min_coords # In voxel indices, converted to world space later if needed
        
    # Step 3: Downsampling
    down_factor = perf_config['down']
    if down_factor > 1:
        # Stride downsampling
        data = data[::down_factor, ::down_factor, ::down_factor]
        
    # Step 4: Spacing Adjustment
    # Original spacing is assumed to be stored in metadata
    # New spacing = Original spacing * down_factor
    # This is handled by the VTK wrapper, but logically:
    # spacing = original_spacing * down_factor
    
    # Step 5: Format Conversion
    use_f16 = (perf_config['tex'] == 'f16')
    if use_f16:
        # Convert to 16-bit float
        # Note: Direct casting may lose precision if values are large; 
        # ensure data fits in float16 range [-65504, 65504]
        data = data.astype(np.float16)
        
    # Step 6: VTK Wrapping
    # Construct vtkImageData
    # Dimensions are data.shape
    # Spacing is adjusted as per Step 4
    # Origin is adjusted as per Step 2
    vtk_image_data = build_vtk_image_data(
        dimensions=data.shape,
        spacing=original_spacing * down_factor, # Logic from Step 4
        origin=origin,
        scalars=data
    )
    
    # Step 7: Binding
    # In a real renderer, this would bind to a mapper
    # mapper.SetInputData(vtk_image_data)
    # if use_f16: mapper.PreferSizeOverAccuracyOn()
    
    return vtk_image_data
```

## Subtopics

### [VolumeSegmenter Pipeline](11584-volumesegmenter-pipeline.md)
An end-to-end method for compressing large RAW volumetric datasets into compact, spatially mapped bricks organized into selectable logical groups, enabling efficient rendering in WebGL2. It reduces stored and GPU-resident voxel data significantly, though it may increase rendering time due to sparse lookup and ray-marching overhead compared to monolithic source rendering. It differs from the [Volume Partitioning Pipeline](11585-volume-partitioning-pipeline.md) by explicitly grouping bricks via intensity bands and adjacency rather than purely spatial partitioning, and builds on the general [Preprocessing Pipeline](6733-preprocessing-pipeline.md) framework [G].

### [Volume Partitioning Pipeline](11585-volume-partitioning-pipeline.md)
A data preprocessing method that splits a 3D volume into disjoint foreground regions, optionally partitions them spatially or by intensity, crops them to bounding boxes, downsamples, and exports them as raw files with metadata. It solves the problem of managing large 3D datasets by reducing memory footprint and enabling efficient out-of-core or chunked processing. It differs from its sibling [VolumeSegmenter Pipeline](11584-volumesegmenter-pipeline.md) by focusing on intensity-based foreground extraction and spatial partitioning rather than semantic segmentation, and from [3D Seismic Data Compression Pipeline](11727-3d-seismic-data-compression-pipeline.md) by using a generic intensity-threshold approach rather than seismic-specific physics.

### [3D Seismic Data Compression Pipeline](11727-3d-seismic-data-compression-pipeline.md)
A lossy compression method for 3D seismic data that processes volumes in 3D blocks (cubes), applying normalization, closed-loop differential pulse-code modulation (DPCM) with quantization, and Deflate compression to reduce file size while preserving trace integrity. It operates on fixed 3D spatial-temporal blocks rather than semantic segments or arbitrary partitions.

### [Wild Scene Preprocessing & Test Set Selection](13103-wild-scene-preprocessing-test-set-selection.md)
A coarse pre-filtering pipeline to remove low-quality images dominated by transient objects from unconstrained photo collections, ensuring robust training and evaluation for view synthesis systems. It differs from sibling pipelines by focusing specifically on semantic quality (NIMA) and transient occlusion metrics (DeepLab) rather than geometric consistency or voxel-based segmentation.

### [Video Frame Extraction and Preprocessing](15598-video-frame-extraction-and-preprocessing.md)
This method extracts and cleans video frames from laparoscopic surgical recordings to create a high-quality input dataset for 3D scene reconstruction. It solves the problem of degraded input quality caused by camera motion artifacts, lighting inconsistencies, and redundant video borders. It is distinguished from general volume preprocessing by its specific focus on surgical video characteristics, such as discarding frames based on camera pose discontinuities and handling specific black-bar cropping ratios.

### Slice Preprocessing
A preprocessing phase used for creating cropped slices to be distributed across the network for rendering. Each raw data slice is read once. Non-empty regions are segmented using a mask volume, cropped and written to disc memory. Out-of-core region growing is used if no mask has been provided. Concurrently, data extent information is consolidated into a series of slab-projection slices [S4, unofficial].

### Feature Map Preprocessing for Visualization
A procedure to transform and normalize feature maps from encoders (LSeg or SAM) for visualization by centering, projecting, and scaling values to a consistent range [S5]. It uses PCA with 3 components (RGB channels), calculating the mean by sampling every third element along $h \times w$ vectors (dim 512 for LSeg, 256 for SAM), centering features, projecting onto PCA components, and normalizing based on min/max values with outliers removed [S5].

### Raw Image Tile Processing
A pipeline stage that generates 2D mipmaps for image tiles emitted by the EM as they arrive, chopping them into sub-tiles for efficient storage and resampling [S6]. It chops image tiles into $128 \times 128$ sub-tiles, stores them in the visualization archive (inheriting the transformation matrix from the image tile augmented by an offset), and optionally compresses sub-tiles using JPEG at 2bpp [S6]. This stage is independent of registration and subsequent alignment/stitching, allowing it to be fully interleaved with dynamic registration and data acquisition [S6].

### TripoSR Image Preprocessing
Image preprocessing pipeline that removes background, resizes foreground, and converts to a 50% gray background format required by the TripoSR model [S7, unofficial]. It initializes a `rembg` session, removes the background, resizes the foreground to a target ratio (default 0.85), converts to float32 and normalizes to [0, 1], composites RGB over a 50% gray background using the alpha channel, and converts back to uint8 [S7, unofficial].

## Operating characteristics
*   **Time Complexity:** The preprocessing time depends on the volume size and the complexity of the cropping and downsampling operations. For the VolCon/Compress variant, preprocessing time scales with the octree depth and wavelet compression levels, with deeper octrees increasing file access overhead [S1].
*   **Memory Complexity:** The pipeline reduces memory footprint by downsampling (`PERF.down`) and converting to 16-bit float (`f16`), which halves the precision compared to 32-bit float. Cropping further reduces memory by removing empty space [S2, unofficial].
*   **Performance:** On a Core2Duo laptop with 2GB RAM, preprocessing times vary by dataset size and octree depth [S1]. The use of `Float32Array` reinterpretation in JS environments avoids the ~15s+ overhead of `DataView` for large volumes (e.g., 145MB) [S2, unofficial].
*   **Strengths:** Standardizes input data, reduces memory usage, and prepares data for efficient GPU rendering. The monolithic approach is simple and avoids the overhead of managing multiple partitions.
*   **Limitations:** Does not handle semantic segmentation or complex spatial partitioning. The `f16` conversion may lose precision for high-dynamic-range data. Cropping relies on a fixed `AIR_HU` threshold, which may not be suitable for all tissue types or imaging modalities [S2, unofficial].
*   **When to use:** When rendering monolithic volumes where semantic segmentation is not required, and memory efficiency is critical. Suitable for web-based rendering where data transfer and GPU memory are constrained.
*   **When not to use:** When semantic segmentation or complex spatial partitioning is needed (use [VolumeSegmenter Pipeline](11584-volumesegmenter-pipeline.md) or [Volume Partitioning Pipeline](11585-volume-partitioning-pipeline.md)). When high precision is required (avoid `f16`).

## Background
The Preprocessing Pipeline, specifically the VolCon and Compress variant, originates from research on gigascale multiresolution volume rendering on distributed display clusters [S1]. It was developed to handle large medical imaging datasets by computing octree structures and wavelet representations in a two-stage process. The general concept of preparing raw volume data for rendering, including filtering, interpolation, and segmentation, has been discussed in broader volume rendering literature [S3, unofficial]. The specific implementation details involving VTK `imageData` and JavaScript-based preprocessing are documented in unofficial repositories related to reinforcement learning for volume rendering transfer functions [S2, unofficial].
