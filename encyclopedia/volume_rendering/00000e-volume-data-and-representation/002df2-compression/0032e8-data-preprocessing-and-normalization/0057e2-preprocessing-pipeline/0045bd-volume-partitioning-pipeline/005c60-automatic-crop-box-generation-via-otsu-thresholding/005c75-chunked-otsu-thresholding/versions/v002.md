# Chunked Otsu Thresholding

Also called: Otsu in parts, Otsu thresholding in parts

## Overview
Chunked Otsu Thresholding is a memory-efficient implementation of Otsu's method for computing a global histogram threshold on large volume datasets by processing data in small chunks [S1, unofficial]. It solves the problem of high memory peaks caused by loading entire volume arrays into high-precision formats for histogram calculation, allowing the threshold to be computed with significantly reduced peak memory usage while maintaining numerical identity with the full-dataset result [S1, unofficial]. It sets itself apart from naive implementations by avoiding the creation of a full copy of the volume data, instead accumulating partial histogram counts [S1, unofficial]. Otsu threshold results are identical whether counted 1, 7, or 64 values at a time, with or without padding [S1, unofficial]. It builds on [Automatic Crop Box Generation via Otsu Thresholding](17117-automatic-crop-box-generation-via-otsu-thresholding.md) [G].

## How it works
**Inputs and Outputs:**
- Input: A large volume dataset containing voxel values [S1, unofficial].
- Output: A single scalar threshold value computed via Otsu's method [S1, unofficial].

**Data Structures:**
- **Histogram Array:** A 1D array of integer counts [S1, unofficial]. The size is determined by the number of bins defined by the fixed range [S1, unofficial]. The bin edges are stored as `float64` values to maintain precision consistency with previous implementations [S1, unofficial].
- **Chunk Buffer:** A temporary buffer holding a subset of the volume data to fit within memory constraints [S1, unofficial].

**Numbered Steps:**
1. **Initialize Histogram:** Define the bin edges for the histogram using a fixed range [S1, unofficial]. The range edges are taken as `float64` values to ensure deterministic binning [S1, unofficial]. Initialize a count array of zeros with length equal to the number of bins [S1, unofficial].
2. **Chunk Processing:** Iterate through the volume data in chunks of a few million values [S1, unofficial].
3. **Bin Assignment:** For each value in the current chunk, determine its bin index based solely on its value and the fixed bin edges [S1, unofficial]. This operation is deterministic and independent of other values [S1, unofficial].
4. **Accumulate Counts:** Increment the corresponding bin count in the histogram array for each value in the chunk [S1, unofficial]. Because binning is value-dependent only, summing these partial counts yields the exact total histogram for the entire volume [S1, unofficial].
5. **Calculate Threshold:** Once all chunks are processed and the full histogram is accumulated, apply Otsu's algorithm to the accumulated histogram counts to compute the optimal threshold [S1, unofficial].

**Pseudocode:**
```python
import numpy as np

def chunked_otsu_threshold(volume_data, num_bins, bin_edges, chunk_size):
    """
    Compute Otsu threshold by accumulating histogram counts in chunks.
    
    Args:
        volume_data: The full volume array (can be large).
        num_bins: Number of histogram bins.
        bin_edges: Array of bin edges (float64).
        chunk_size: Number of values to process per chunk.
        
    Returns:
        threshold: The Otsu threshold value.
    """
    # Step 1: Initialize histogram
    histogram = np.zeros(num_bins, dtype=np.int64)
    
    # Step 2, 3, 4: Chunk processing, bin assignment, and accumulation
    total_size = volume_data.size
    for i in range(0, total_size, chunk_size):
        end = min(i + chunk_size, total_size)
        chunk = volume_data[i:end]
        
        # np.histogram bins each value solely based on its value
        chunk_counts, _ = np.histogram(chunk, bins=bin_edges)
        
        # Sum partial counts to get total histogram
        histogram += chunk_counts
        
    # Step 5: Calculate Otsu threshold
    threshold = compute_otsu_threshold(histogram, bin_edges)
    
    return threshold

def compute_otsu_threshold(histogram, bin_edges):
    """
    Compute Otsu's threshold from accumulated histogram counts [G].
    """
    N = np.sum(histogram)
    bin_centers = (bin_edges[:-1] + bin_edges[1:]) / 2.0
    total_sum = np.sum(histogram * bin_centers)
    
    max_variance = 0.0
    best_threshold = bin_edges[0]
    
    cumulative_sum = 0.0
    cumulative_count = 0
    
    for i in range(num_bins):
        cumulative_count += histogram[i]
        cumulative_sum += histogram[i] * bin_centers[i]
        
        w1 = cumulative_count
        w2 = N - cumulative_count
        
        if w1 == 0 or w2 == 0:
            continue
            
        u1 = cumulative_sum / w1
        u2 = (total_sum - cumulative_sum) / w2
        
        variance = w1 * w2 * (u1 - u2) ** 2
        
        if variance > max_variance:
            max_variance = variance
            best_threshold = (bin_edges[i] + bin_edges[i+1]) / 2.0
            
    return best_threshold
```

**Parameters:**
- `chunk_size`: The number of values to process in each iteration [S1, unofficial]. Typical values are a few million values [S1, unofficial].
- `num_bins`: Not given in the sources. Typical values depend on data precision and range [G].
- `bin_edges`: The edges of the histogram bins, taken as `float64` [S1, unofficial].

**Edge Cases and Pitfalls:**
- **NaN Handling:** NaN values in the data are treated as the lowest value, comparing below every level as `-inf` did, ensuring consistency with previous implementations [S1, unofficial].
- **Precision:** Using `float64` for bin edges ensures consistency with previous implementations and avoids precision errors in bin assignment [S1, unofficial].
- **Memory:** The method is designed to reduce peak memory usage [S1, unofficial]. Previous methods copying data to `float64` caused high memory peaks, while this method reduces it significantly [S1, unofficial].

## Operating characteristics
- **Time Complexity:** $O(N)$, where $N$ is the total number of voxels [G]. Each voxel is processed once to determine its bin, and the histogram is accumulated [G]. The final Otsu calculation is $O(B)$, where $B$ is the number of bins [G].
- **Memory Complexity:** $O(B + C)$, where $B$ is the number of bins and $C$ is the chunk size [G]. This is significantly lower than $O(N)$ for the full data copy [G].
- **Measured Performance:** In a test case with a whole-body MR at 2 mm resolution, the peak memory usage dropped from 911 MB to 355 MB [S1, unofficial].
- **Strengths:** Significantly reduced memory footprint; identical results to full-dataset Otsu thresholding; scalable to large volumes [S1, unofficial].
- **Limitations:** Requires multiple passes over the data; depends on efficient chunking and histogram accumulation [S1, unofficial].
- **When to use:** When processing large volume datasets with limited memory; when a global threshold is needed for preprocessing or segmentation [G].
- **When not to use:** When memory is not a constraint and a simpler, single-pass method is preferred; when the data distribution is highly non-uniform and local thresholds are more appropriate [G].

## Background
Chunked Otsu Thresholding was introduced in a pull request to address memory issues in surface rendering and contour sheet generation [S1, unofficial]. It is an optimization of the existing Otsu thresholding implementation, which previously required copying the entire volume to `float64`, leading to high memory peaks [S1, unofficial]. The method leverages the deterministic nature of histogram binning to allow partial counts to be summed, enabling efficient processing of large datasets [S1, unofficial].
