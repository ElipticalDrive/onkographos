# Run-Length Encoding for Voxel Data

Also called: CompressBooleanArray, CompressByteArray, CompressIntArray, CompressShortArray, RLE Voxel Compression, Run-Length Encoding, Run-Length Encoding (RLE) Compression

## Overview
Run-Length Encoding (RLE) is a lossless compression technique that represents consecutive uniform voxels—particularly empty or transparent runs—as compact lists of start positions, lengths, and values, enabling rays to skip entire homogeneous regions in a single operation [S1]. Unlike [Sparse structures](5-sparse-structures.md) which use complex tree or hash indices to locate non-empty data, RLE relies on linear scanline or block traversal, making it exceptionally fast for hardware acceleration and simple ray-marching pipelines [S1, S3]. It excels in datasets with long empty stretches, such as simulated fluid dynamics or terrain blocks, where it achieves compression ratios exceeding 10:1 and reduces rendering times by 5–15 times relative to naive traversal [S1].

## How it works
### Inputs and Outputs
*   **Input:** A voxel data array `voxel_data` (e.g., `Uint8Array` for values 0–255, `int[]`, `short[]`, or `boolean[]`) and its size `N` (number of voxels) [S2, S5, S6, unofficial].
*   **Output:** A compressed array `compressed_data` containing alternating pairs of `(count, value)` [S2, S6, unofficial].

### Data Structures and Layout
The compressed data is stored as a linear array of alternating elements: `[count_0, value_0, count_1, value_1, ...]` [S2, S6, unofficial].
*   **Standard Types (Byte, Short, Int):** Both `count` and `value` are stored as elements of the same type [S2, unofficial].
    *   **Byte RLE:** Count is limited to `Byte.MAX_VALUE` (127) [S2, unofficial].
    *   **Short RLE:** Count is limited to `Short.MAX_VALUE` (32767) [S2, unofficial].
    *   **Int RLE:** Count is limited to `Integer.MAX_VALUE` [S2, unofficial].
*   **Boolean RLE:** A specialized optimization where the `count` is stored as a signed byte. The sign bit indicates the boolean value: a negative count implies `true` (with the magnitude being the run length), and a positive count implies `false` [S2, unofficial]. This allows a single byte to store both the count and the boolean value for a run [S2, unofficial].

### Algorithm Steps
1.  **Initialization:** Create a temporary output array. To prevent overflow during the worst-case scenario (no compression, e.g., alternating values), allocate an array twice the size of the input [S2, unofficial]. Initialize a `count` variable to 1 and a `current_value` to the first voxel [S2, S6, unofficial].
2.  **Scan and Count:** Iterate through the input `voxel_data` starting from the second element (index 1) [S2, S6, unofficial].
    *   If the current voxel equals `current_value`, increment `count` [S2, S6, unofficial].
    *   If the current voxel differs from `current_value`:
        *   Store the pair `(count, current_value)` in the compressed array [S2, S6, unofficial].
        *   Reset `count` to 1.
        *   Update `current_value` to the current voxel [S2, S6, unofficial].
    *   **Boundary Check:** If `count` reaches the type-specific maximum limit (e.g., 127 for Byte), store the current run and reset `count` to 1 to start a new run for the same value [S2, unofficial].
3.  **Finalize:** After the loop, store the final `(count, current_value)` pair [S6, unofficial].
4.  **Resize:** Resize the temporary array to the actual number of written elements (index) and return it [S2, unofficial].

def rle_encode_byte(voxel_data: list[int]) -> list[int]:
    """
    Encodes a byte array (0-255) using Run-Length Encoding.
    Returns a list of alternating [count, value] pairs.
    Count is capped at 127 (Byte.MAX_VALUE).
    """
    if not voxel_data:
        return []

    compressed = []
    # Pre-allocate with double size to avoid bounds checks during write
    # In practice, append to a dynamic list or track index
    temp_buffer = [0] * (len(voxel_data) * 2)
    idx = 0
    
    count = 1
    current_value = voxel_data[0]
    
    for i in range(1, len(voxel_data)):
        next_value = voxel_data[i]
        
        if next_value == current_value:
            count += 1
            # Cap count at 127 for byte RLE
            if count == 127:
                temp_buffer[idx] = count
                temp_buffer[idx + 1] = current_value
                idx += 2
                count = 1
                # current_value remains the same
        else:
            # Store the completed run
            temp_buffer[idx] = count
            temp_buffer[idx + 1] = current_value
            idx += 2
            
            # Start new run
            count = 1
            current_value = next_value
            
    # Store the final run
    temp_buffer[idx] = count
    temp_buffer[idx + 1] = current_value
    idx += 2
    
    # Return only the used portion
    return temp_buffer[:idx]

def rle_decode_byte(compressed: list[int]) -> list[int]:
    """
    Decodes a byte RLE array back to the original voxel data.
    """
    if not compressed:
        return []
        
    output = []
    # Estimate size to pre-allocate if needed, or append
    for i in range(0, len(compressed), 2):
        count = compressed[i]
        value = compressed[i + 1]
        # Extend output with 'count' copies of 'value'
        output.extend([value] * count)
        
    return output

### Parameters and Edge Cases
*   **Run Length Limit:** For Byte RLE, the maximum run length is 127. If a homogeneous region exceeds 127 voxels, the encoder must split it into multiple runs (e.g., 127, 127, 3) [S2, unofficial].
*   **Precision:** RLE is lossless [S2, unofficial][S3][S4].
*   **Degenerate Input:** If the input has no consecutive identical values (e.g., alternating 0, 1, 0, 1), the compressed size will be exactly double the input size (plus overhead if headers are used). The temporary buffer allocation strategy handles this [S2, unofficial].
*   **Ray Traversal:** During rendering, the ray traverses the compressed runs. If a run's value is transparent (e.g., 0), the ray advances by the run's length without sampling individual voxels [S1].

## Subtopics

### [Chunk Serialization with RLE](5162-chunk-serialization-with-rle.md)
Uses RLE to serialize voxel chunks, likely optimizing for block-based access patterns common in voxel engines. It applies RLE within the boundaries of fixed-size chunks, allowing for efficient random access to chunk headers while compressing the interior data.

### [VOXLAP RLE Voxel Storage](5172-voxlap-rle-voxel-storage.md)
An in-memory compressed voxel storage format using RLE, organized as a 2D array of columns. This structure supports batched edits, allowing multiple voxel changes to be processed efficiently before re-encoding or updating the RLE runs. It optimizes for scenarios with frequent localized updates rather than static volumes.

### Window-Length Encoding
A variant of RLE applied to intermediate rendered images (e.g., 500x500 pixels) in distributed rendering pipelines to reduce network transfer time. It encodes contiguous color runs in the image data. Encoding and decoding take ~1 ms each. It is highly efficient for distant views with large uniform color areas but inefficient for complex internal views. Compared to uncompressed transfer (~10 ms over Gigabit Ethernet), it reduces propagation time to <1 ms [S7].

## Operating characteristics
*   **Time Complexity:** Encoding is $O(N)$, where $N$ is the number of voxels, as it requires a single linear scan [S2, S6, unofficial]. Decoding is also $O(N)$ [S6, unofficial].
*   **Memory Complexity:** The compressed size ranges from $N/2$ (best case, all identical) to $2N$ (worst case, alternating values) elements [S2, unofficial].
*   **Performance:** In simulated fluid dynamics volumes, RLE achieves compression ratios exceeding 10:1 and reduces rendering times by 5–15 times relative to naive traversal [S1]. Hardware implementations, such as the VolumePro ASIC, integrate RLE directly into the ray-casting pipeline for real-time performance on 512^3 grids [S1].
*   **Strengths:** Extremely fast decoding; simple hardware implementation; effective for sparse volumes with large empty regions [S1, S3].
*   **Limitations:** Poor compression ratio for noisy or high-frequency data (e.g., alternating patterns); run-length limits require splitting for very long homogeneous regions [S2, unofficial].
*   **When to Use:** Sparse volumes, terrain blocks, fluid simulations with large empty spaces, or when hardware acceleration is available [S1][S2, unofficial].
*   **When Not to Use:** Dense, noisy volumes with little redundancy; scenarios requiring random access to arbitrary voxels without decoding the entire stream (unless combined with chunking) [S3].

## Background
Run-Length Encoding was widely used in early compressed Direct Volume Rendering (DVR) applications, dating back to the early 1990s [S3][S4]. It is often combined with entropy encoders (like Huffman or Arithmetic coding) to further compress the run-length counts and values, although this adds decoding complexity [S3][S4]. The method forms the basis for many GPU-accelerated ray casters and was integrated into specialized hardware like the VolumePro ASIC [S1].
