# Bricking with Boundary Voxel Duplication

Also called: Texture Bricking

## Overview
Bricking with Boundary Voxel Duplication is a technique to solve incorrect interpolation at texture tile boundaries in 3D volume rendering by duplicating a plane of voxels at each brick boundary, allowing texture units to deliver correct interpolation results across shared planes [S1, unofficial]. It sets itself apart from sibling methods like [Level-wise Texture Merging](5274-level-wise-texture-merging.md) by maintaining a uniform 3D texture structure with explicit overlap rather than merging levels, and from its parent [Brick-based Volume Rendering with Overlap and LRU Swapping](3782-brick-based-volume-rendering-with-overlap-and-lru-swapping.md) by specifically addressing the geometric continuity of trilinear interpolation at brick interfaces.

## How it works
**Inputs and Outputs:**
*   Input: A dense 3D volume dataset $V$ of dimensions $D_x \times D_y \times D_z$.
*   Output: A set of 3D texture bricks $B_{i,j,k}$ ready for GPU upload.

**Data Structures:**
The volume is partitioned into a 3D grid of bricks. Each brick $B$ is a 3D texture object.
*   Brick dimensions: $W \times H \times D$ (width, height, depth).
*   Voxel data: Scalar values $v \in \mathbb{R}$.
*   Boundary handling: Each brick includes an extra layer of voxels on its boundaries shared with neighbors.

**Numbered Steps:**
1.  **Partitioning:** Divide the input volume $V$ into a regular 3D grid of bricks. Let the brick size be $S_x \times S_y \times S_z$ voxels.
2.  **Boundary Duplication:** For every internal brick boundary, duplicate the plane of voxels adjacent to the boundary into the neighboring brick.
    *   Specifically, if brick $B_1$ is adjacent to brick $B_2$ along the X-axis, the last column of voxels of $B_1$ (at $x=S_x-1$) is identical to the first column of voxels of $B_2$ (at $x=0$).
    *   This applies to all three axes (X, Y, Z) for internal bricks. Boundary bricks (on the volume exterior) do not duplicate outward.
3.  **Texture Upload:** Upload each brick $B_{i,j,k}$ as a separate 3D texture object to GPU memory. The texture coordinates for sampling must be normalized to $[0, 1]$.
4.  **Sampling:** During ray casting, when a ray crosses a brick boundary, the texture unit performs trilinear interpolation. Because the boundary voxels are duplicated, the interpolation kernel has access to data from both sides of the boundary within the same texture object, ensuring continuity.

**Formulas:**
Let $V(x,y,z)$ be the original volume. Let $B_{i,j,k}(u,v,w)$ be the texture of brick at grid indices $(i,j,k)$, where $u,v,w \in [0,1]$.
The mapping from volume coordinates to brick-local coordinates for a point $P$ inside brick $B_{i,j,k}$ is:
$$ u = \frac{x - i \cdot S_x}{S_x + 1} $$
$$ v = \frac{y - j \cdot S_y}{S_y + 1} $$
$$ w = \frac{z - k \cdot S_z}{S_z + 1} $$
Note: The denominator is $S+1$ because the brick size effectively includes the duplicated boundary layer, increasing the logical dimension by 1 in each direction for internal bricks. For boundary bricks, the dimension remains $S$ if no external duplication occurs, but typically uniform brick sizes are used with padding.

**Parameters:**
*   Brick size ($S_x, S_y, S_z$): Typically chosen to fit within GPU texture size limits (e.g., $64^3$, $128^3$). Not given in the sources.
*   Overlap width: 1 voxel plane.

**Edge Cases and Pitfalls:**
*   **Interpolation Artifacts:** Without duplication, trilinear interpolation at the boundary is incorrect because the texture unit lacks information from the neighboring brick [S1, unofficial].
*   **Memory Overhead:** Duplicating boundary planes increases memory usage. For a brick of size $S^3$, the volume is $(S+2)^3$ if all sides are duplicated, or $S^3 + \text{boundary planes}$.
*   **Precision:** Standard floating-point precision is assumed. No specific precision issues noted other than general interpolation errors.

**Pseudocode:**
```python
def create_bricked_volume(volume_data, brick_size):
    """
    volume_data: 3D numpy array (Dx, Dy, Dz)
    brick_size: tuple (Sx, Sy, Sz)
    Returns: list of 3D arrays representing bricks
    """
    Dx, Dy, Dz = volume_data.shape
    Sx, Sy, Sz = brick_size
    
    # Calculate number of bricks
    num_x = (Dx + Sx - 1) // Sx
    num_y = (Dy + Sy - 1) // Sy
    num_z = (Dz + Sz - 1) // Sz
    
    bricks = []
    
    for k in range(num_z):
        for j in range(num_y):
            for i in range(num_x):
                # Determine slice indices in original volume
                x_start = i * Sx
                y_start = j * Sy
                z_start = k * Sz
                
                x_end = min(x_start + Sx, Dx)
                y_end = min(y_start + Sy, Dy)
                z_end = min(z_start + Sz, Dz)
                
                # Extract base brick data
                base_bricks = volume_data[x_start:x_end, y_start:y_end, z_start:z_end]
                
                # Determine if we need to duplicate boundaries
                # We need to pad to ensure trilinear interpolation works across boundaries
                # Pad left/top/back if not at volume start
                pad_left = 1 if i > 0 else 0
                pad_top = 1 if j > 0 else 0
                pad_back = 1 if k > 0 else 0
                
                # Pad right/bottom/front if not at volume end
                pad_right = 1 if x_end < Dx else 0
                pad_bottom = 1 if y_end < Dy else 0
                pad_front = 1 if z_end < Dz else 0
                
                # Create padded brick
                # Dimensions will be (Sx + pad_left + pad_right, ...)
                # However, standard bricking often uses fixed size bricks with overlap
                # For simplicity, we assume the brick texture includes the overlap
                
                # Extract with overlap from neighbors if available
                # This is a simplified implementation; real implementation might
                # handle overlap by reading from adjacent bricks or pre-computing
                
                # For this method, we duplicate the boundary voxels into the brick
                # If i > 0, the first column of this brick should match the last column of brick (i-1)
                # We assume volume_data is the source of truth
                
                # Re-extract with explicit overlap handling
                # Left boundary
                if i > 0:
                    left_voxels = volume_data[x_start-1, y_start:y_end, z_start:z_end]
                else:
                    left_voxels = None
                    
                # Right boundary
                if x_end < Dx:
                    right_voxels = volume_data[x_end, y_start:y_end, z_start:z_end]
                else:
                    right_voxels = None
                    
                # Top boundary
                if j > 0:
                    top_voxels = volume_data[x_start:x_end, y_start-1, z_start:z_end]
                else:
                    top_voxels = None
                    
                # Bottom boundary
                if y_end < Dy:
                    bottom_voxels = volume_data[x_start:x_end, y_end, z_start:z_end]
                else:
                    bottom_voxels = None
                    
                # Back boundary
                if k > 0:
                    back_voxels = volume_data[x_start:x_end, y_start:y_end, z_start-1]
                else:
                    back_voxels = None
                    
                # Front boundary
                if z_end < Dz:
                    front_voxels = volume_data[x_start:x_end, y_start:y_end, z_end]
                else:
                    front_voxels = None
                    
                # Construct the brick with duplicated boundaries
                # This is a conceptual construction; actual GPU upload requires
                # a contiguous 3D array
                
                # For a brick at (i,j,k), the texture coordinates map to:
                # u in [0,1] covering x from x_start to x_end + (1 if right else 0)
                # But typically, the brick size is fixed, e.g., 64x64x64, and
                # the overlap is part of that size.
                
                # Let's assume the brick size includes the overlap.
                # Effective size = Sx + 2 (if internal) or Sx + 1 (if boundary)
                # To simplify, we create a brick of size (Sx+2, Sy+2, Sz+2) for internal bricks
                # and handle boundaries appropriately.
                
                # However, the source says "duplicating a plane of voxels at each brick boundary".
                # This implies the brick texture itself contains the duplicated plane.
                
                # Let's create a brick of size (Sx + pad_left + pad_right, ...)
                # But for uniformity, let's assume all bricks are the same size,
                # including the overlap.
                
                # Final brick dimensions
                bx = Sx + pad_left + pad_right
                by = Sy + pad_top + pad_bottom
                bz = Sz + pad_back + pad_front
                
                brick = np.zeros((bx, by, bz), dtype=volume_data.dtype)
                
                # Fill center
                brick[pad_left:pad_left+(x_end-x_start), 
                      pad_top:pad_top+(y_end-y_start), 
                      pad_back:pad_back+(z_end-z_start)] = base_bricks
                
                # Fill left overlap
                if pad_left:
                    brick[0, :, :] = volume_data[x_start-1, y_start:y_end, z_start:z_end]
                
                # Fill right overlap
                if pad_right:
                    brick[-1, :, :] = volume_data[x_end, y_start:y_end, z_start:z_end]
                    
                # Fill top overlap
                if pad_top:
                    brick[:, 0, :] = volume_data[x_start:x_end, y_start-1, z_start:z_end]
                    
                # Fill bottom overlap
                if pad_bottom:
                    brick[:, -1, :] = volume_data[x_start:x_end, y_end, z_start:z_end]
                    
                # Fill back overlap
                if pad_back:
                    brick[:, :, 0] = volume_data[x_start:x_end, y_start:y_end, z_start-1]
                    
                # Fill front overlap
                if pad_front:
                    brick[:, :, -1] = volume_data[x_start:x_end, y_start:y_end, z_end]
                    
                bricks.append(brick)
                
    return bricks
```

## Subtopics

### [Continuous Level Transitions](5275-continuous-level-transitions.md)
A procedure to ensure continuity of the 3D scalar field at level transitions by adapting brick textures on the finer level to interpolate from the coarser level, restricting transitions to differ by at most one level.

## Operating characteristics
**Time and Memory Complexity:**
*   Memory: Increases by a factor related to the boundary duplication. For a brick of size $S^3$, the memory usage is approximately $(S+2)^3$ for internal bricks, leading to a constant overhead factor.
*   Time: Upload time increases due to larger brick sizes. Sampling time is similar to standard 3D texture sampling, but with potentially larger textures.

**Measured Performance:**
*   For large volume data sets, the bricking strategy is extremely inefficient, resulting in significantly lower frame rates compared to 2D-texture solutions [S1, unofficial].
*   Image quality is superior to 2D-texture based solutions due to hardware support for trilinear interpolation [S1, unofficial].

**Strengths and Limitations:**
*   Strengths: Correct interpolation at brick boundaries, high image quality, preserves benefits of bricking (memory management, data locality).
*   Limitations: Inefficient for large datasets, increased memory usage due to duplication.

**When to Use:**
*   Use when image quality is critical and dataset size is manageable.
*   Avoid for very large volume datasets where frame rate is a priority.

## Background
Originated in the context of general purpose graphics hardware for volume rendering. The technique addresses artifacts caused by incorrect interpolation at texture tile boundaries [S1, unofficial]. It is part of the broader field of brick-based volume rendering.
