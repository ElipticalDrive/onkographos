# Brick-based Volume Rendering with Overlap and LRU Swapping

Also called: Texture Bricking

## Overview
This method manages volumetric data larger than GPU memory by dividing the volume into smaller 3D texture bricks, rendering them individually, and composing the final image. It distinguishes itself from traditional bricking by using significantly smaller bricks to exploit void detection and Least Recently Used (LRU) swapping, thereby reducing bus transfer overhead and alleviating the bottleneck caused by reloading void bricks [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A volumetric dataset (scalar or vector field), a transfer function, and GPU texture memory constraints.
*   **Output:** A rendered 2D image.

**Data Structures:**
*   **Bricks:** Cubic sub-volumes of size $b \times b \times b$ voxels.
*   **Texture Memory:** Holds resident bricks as 3D textures.
*   **Main Memory:** Holds the complete volume data and swapped-out bricks.

**Steps:**
1.  **Brick Partitioning:** Divide the volume into bricks of size $b \times b \times b$. If the volume dimensions do not divide evenly by $b$, add a layer of partially empty bricks in each direction or use smaller "rest-bricks" to fill the remainder [S1, unofficial].
2.  **Overlap Calculation:** Determine the overlap size $n$ based on the interpolation kernel.
    *   Nearest neighbor: $n = 0$.
    *   Trilinear: $n = 1$.
    *   Pre-integrated rendering or on-the-fly gradient calculation: $n = 2$ (trilinear + 1) [S1, unofficial].
3.  **Texture Loading:** Load bricks into video memory as 3D textures. Note that many graphics cards require 3D texture dimensions to be powers of 2; handle non-power-of-2 dimensions via padding or rest-bricks [S1, unofficial].
4.  **Rendering Loop:**
    *   For each frame, determine the required bricks for the current view.
    *   Check if a required brick is resident in texture memory.
    *   If not resident, load the brick from main memory.
    *   If texture memory is full, swap out a resident brick using an LRU policy [S1, unofficial].
    *   Render the resident bricks. Void bricks (those completely transparent after applying the transfer function) are skipped during rendering.
5.  **Optimization:** Choose brick sizes $b$ considerably smaller than the maximum possible size. Smaller bricks increase the probability of being completely void. Once a void brick is swapped out, it is never reloaded, reducing bus traffic [S1, unofficial].

**Formulas:**
*   **Memory Overhead:** The percentage of memory overhead due to overlap is approximately:
    $$ \text{Overhead} \approx \frac{3 \cdot n}{b} \cdot 100\% $$
    where $b$ is the brick dimension in voxels (assuming cubic bricks) and $n$ is the overlap size in voxels [S1, unofficial].

**Parameters:**
*   **Brick Size ($b$):** Should be chosen considerably smaller than the maximum possible size to maximize void detection benefits [S1, unofficial].
*   **Overlap Size ($n$):** Depends on the interpolation kernel. For trilinear, $n=1$. For pre-integrated rendering or gradient calculation, $n=2$ [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Power of 2 Constraints:** Graphics cards often require 3D texture sizes to be powers of 2 in every direction. Non-power-of-2 dimensions must be handled via padding or rest-bricks [S1, unofficial].
*   **Bus Bottleneck:** Traditional bricking loads large bricks sequentially, transferring the entire volume over the bus per frame. This method avoids this by using smaller bricks and LRU swapping [S1, unofficial].
*   **Cache Trashing:** Even if the volume fits in texture memory, smaller bricks can improve data locality and reduce cache trashing on the graphics card [S1, unofficial].

## Subtopics

### [Bricking with Boundary Voxel Duplication](4198-bricking-with-boundary-voxel-duplication.md)
A technique to solve incorrect interpolation at texture tile boundaries in 3D volume rendering by duplicating a plane of voxels at each brick boundary, allowing texture units to deliver correct interpolation results across shared planes.

### [Level-wise Texture Merging](5274-level-wise-texture-merging.md)
A technique to minimize texture memory overhead by merging texture data of adjacent bricks into a single texture map, creating an octree-like hierarchy where the number of bricks sharing a texture map is multiplied by a factor of 8 on each consecutive level.

## Operating characteristics
*   **Time Complexity:** Depends on the number of resident bricks and the swapping frequency. LRU swapping adds overhead for memory management but reduces rendering time by skipping void bricks.
*   **Memory Complexity:** Proportional to the number of resident bricks plus the overlap overhead. The overhead is approximately $(3 \cdot n / b) \cdot 100\%$ [S1, unofficial].
*   **Measured Performance:** Reduces bus traffic compared to traditional bricking by avoiding reloading void bricks [S1, unofficial].
*   **Scaling:** Performance improves with smaller brick sizes due to increased void detection, up to the point where overlap overhead and swapping frequency become significant.
*   **Strengths:** Reduces bus bottleneck, improves data locality, handles volumes larger than GPU memory.
*   **Limitations:** Overlap increases memory usage; small bricks may increase swapping frequency if not managed well.
*   **When to Use:** When the volume exceeds GPU memory or when void detection can significantly reduce rendering time.
*   **When Not to Use:** When the volume is small enough to fit in memory without swapping, or when the overhead of overlap and swapping outweighs the benefits.

## Background
Originated in the context of optimizing GPU volume rendering, this method addresses the limitations of traditional bricking which transfers the entire volume over the bus per frame [S1, unofficial]. It leverages LRU swapping and void detection to improve performance [S1, unofficial].
