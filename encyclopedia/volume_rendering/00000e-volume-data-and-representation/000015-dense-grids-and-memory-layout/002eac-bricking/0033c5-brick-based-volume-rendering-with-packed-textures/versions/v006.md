# Brick-based volume rendering with packed textures

Also called: Index-Texture brick mapping, Packed-Texture volume rendering

## Overview
Brick-based volume rendering with packed textures is a technique for rendering volumetric datasets that exceed the capacity of local GPU video memory by dividing the data into smaller sub-volumes (bricks) and storing only the non-transparent ones in a compact 2D or 3D texture [S1, unofficial][S2, unofficial]. It sets itself apart from standard bricking by decoupling the spatial layout of bricks from their storage layout: an "Index-Texture" maps 3D spatial coordinates to indices in a "Packed-Texture" that contains only active data, thereby reducing memory bandwidth and storage requirements [S2, unofficial].

## How it works
**Inputs:**
- A volumetric dataset defined on a cube $[0, 1]^3$.
- A transfer function mapping voxel values to opacity.
- A brick dimension $N \times N \times N$ (number of bricks per axis).

**Outputs:**
- A rendered image.

**Data Structures:**
1.  **Packed-Texture:** A dense texture (2D or 3D) containing only the bricks determined to be non-transparent. The layout is a linear or packed array of these bricks.
2.  **Index-Texture:** A texture storing the index of the brick in the Packed-Texture for any given 3D coordinate. This allows the shader to look up which packed brick contains a specific sample point.

**Algorithm Steps:**

1.  **Brick Partitioning:** Divide the volume cube into $N \times N \times N$ equal-sized bricks [S2, unofficial].
2.  **Transparency Culling:** Evaluate the transfer function for each brick. If a brick is fully transparent, it is excluded from the Packed-Texture [S2, unofficial].
3.  **Packing:** Store only the non-transparent bricks into the Packed-Texture [S2, unofficial].
4.  **Index Mapping:** Create the Index-Texture. For every spatial position, the Index-Texture stores the index of the corresponding brick in the Packed-Texture [S2, unofficial].
5.  **Rendering (Ray Casting):**
    a. For each sample point along a ray, calculate the brick index and the fractional position within that brick [S2, unofficial].
    b. Access the Index-Texture using the sample point's coordinates to retrieve the brick index [S2, unofficial].
    c. Use the retrieved index to sample from the Packed-Texture [S2, unofficial].

**Formulas:**
Let $P$ be the fractional 3D coordinate of a sample point in the volume cube $[0, 1]^3$. Let $N$ be the number of bricks along each axis.

1.  **Scaled Position:**
    $$ P_{scaled} = P \times N $$
2.  **Brick Index:**
    $$ I = \lfloor P_{scaled} \rfloor $$
    Where $\lfloor \cdot \rfloor$ is the floor function, resulting in an integer index $I \in [0, N^3-1]$ (conceptually, before packing).
3.  **Sub-block (Local) Position:**
    $$ P_{local} = P_{scaled} - I $$
    This gives the fractional position within the specific brick [S2, unofficial].

**Parameters:**
- $N$: Number of bricks per dimension. Sources suggest keeping bricks small enough so that more than one fits in video memory [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Interpolation Across Boundaries:** Incorrect interpolation can occur across brick boundaries if one plane of voxels is not duplicated at the edges of each brick [S1, unofficial].
- **Filtering:** When storing blocks into a regular packed texture, hardware filtering must be disabled. The implementation must handle the "fencepost problem" and perform all filtering/interpolation manually in the shader [S2, unofficial].
- **Bus Bandwidth:** Bricking can suffer from bus-bandwidth problems and unbalanced load between the GPU and memory bus if not managed carefully [S1, unofficial].
- **CPU Load:** Performing parallel transfer and rendering increases CPU load for intersection calculations [S1, unofficial].

**Pseudocode:**

```python
# Pre-computation (CPU or Setup)
def setup_bricks(volume_data, transfer_function, N):
    """
    volume_data: 3D array of size [N*N*N, brick_size, brick_size, brick_size]
    transfer_function: function(value) -> opacity
    N: number of bricks per axis
    """
    packed_bricks = []
    index_map = {} # Maps (i, j, k) to index in packed_bricks
    
    # Iterate over all bricks
    for i in range(N):
        for j in range(N):
            for k in range(N):
                brick = volume_data[i, j, k]
                # Check if brick is transparent
                if is_transparent(brick, transfer_function):
                    continue
                
                # Store non-transparent brick
                index = len(packed_bricks)
                packed_bricks.append(brick)
                index_map[(i, j, k)] = index
                
    return packed_bricks, index_map

def render_ray(ray_origin, ray_direction, packed_bricks, index_map, N, brick_size):
    """
    Simulates the shader logic for a single ray.
    """
    t_min, t_max = compute_intersection(ray_origin, ray_direction, volume_bounds)
    
    # Sample along ray
    t = t_min
    while t < t_max:
        # 1. Calculate 3D position in volume cube [0,1]^3
        pos = ray_origin + t * ray_direction
        frac_pos = normalize_to_01(pos)
        
        # 2. Calculate brick index and local position
        scaled_pos = frac_pos * N
        brick_idx_global = floor(scaled_pos) # Vector of 3 integers
        local_pos = scaled_pos - brick_idx_global
        
        # 3. Look up brick index in Packed-Texture via Index-Texture logic
        # In a real implementation, this is a texture lookup.
        # Here we simulate the lookup.
        brick_key = tuple(brick_idx_global)
        
        if brick_key in index_map:
            packed_idx = index_map[brick_key]
            brick_data = packed_bricks[packed_idx]
            
            # 4. Sample from the specific brick
            # Note: Manual interpolation is required as per [S2, unofficial]
            value = sample_brick(brick_data, local_pos)

            # ...
        else:

        t += step_size
```

## Subtopics

### [Virtual Texture Memory for Magnification Lenses](7444-virtual-texture-memory-for-magnification-lenses.md)
This method enables interactive magnification of large volume datasets by keeping all bricks in a single GPU texture memory pool and using an index volume to locate them dynamically. It allows arbitrary coordinate transformations (such as zooming) in the fragment shader without rebinding textures, solving the problem where modified texture coordinates would otherwise point into unbound bricks. It sets itself apart from standard brick-based rendering by introducing a virtual-to-physical address translation layer that handles boundary overlaps and dynamic coordinate mapping.

### [Compact Volume Rendering with Page-Table Indirection and Masked Storage](11586-compact-volume-rendering-with-page-table-indirection-and-mas.md)
Compact Volume Rendering is a rendering mode that stores only selected groups of voxels (bricks) in a packed 2D array texture, using a page table for spatial indexing and an optional bitmask for sparse storage, to fit within a 1024 MiB GPU memory budget. It differs from the original mode, which loads the full volume into a single 3D texture, by enabling rendering of datasets that exceed `MAX_3D_TEXTURE_SIZE` or the available GPU memory through spatial partitioning and indirection. It builds on [Brick-based volume rendering with packed textures](7106-brick-based-volume-rendering-with-packed-textures.md).

### Brick Entry Point Offsetting
A proposed technique to correct sampling seam visibility during interaction-time when sampling distance is increased. It involves offsetting the entry point in each brick to be a multiple along the entire ray [S3, unofficial]. Compute the entry point from the eye pose to ensure it is a multiple for each different brick, offsetting the entry point in each brick accordingly [S3, unofficial]. During interaction-time, the sampling distance is increased, which causes the sampling seams to become visible again [S3, unofficial].

## Operating characteristics
- **Memory Efficiency:** By storing only non-transparent bricks, the method reduces the memory footprint compared to storing the full volume [S2, unofficial].
- **Bandwidth:** Bricking can suffer from bus-bandwidth problems and unbalanced load for the GPU and memory bus, making it inefficient if not managed carefully [S1, unofficial].
- **Performance:** Keeping bricks small enough ensures more than one fits in video memory, allowing parallel transfer and rendering to balance the load, though this increases CPU load for intersection calculations [S1, unofficial].
- **Complexity:** Requires manual handling of filtering and interpolation due to the packed nature of the texture, increasing shader complexity [S2, unofficial].

## Background
This method is a variation of bricking, which addresses the problem of volumetric data sets being too large to fit into local video memory [S1, unofficial]. It was discussed in the context of GPU-based volume rendering and online forums for implementing large dataset visualization [S1, unofficial][S2, unofficial].
