# Virtual Texture Memory for Magnification Lenses

Also called: Index volume brick mapping, Virtual texture coordinates

## Overview
Virtual Texture Memory for Magnification Lenses is a method for mapping virtual volume coordinates to physical texture coordinates in GPU-based volume rendering, enabling arbitrary coordinate transformations (such as magnification) without rebinding textures [S1, unofficial]. It solves the problem of accessing high-resolution data subsets from a large dataset when on-board texture memory is limited, by keeping bricks in a single memory pool and using an index volume to locate them [S1, unofficial]. It sets itself apart from its siblings by using a single memory pool with an index texture for indirection, allowing dynamic coordinate modification in the fragment shader, whereas [Compact Volume Rendering with Page-Table Indirection and Masked Storage](11586-compact-volume-rendering-with-page-table-indirection-and-mas.md) uses page-table indirection and masked storage for compact representation.

## How it works
**Inputs and Outputs:**
*   **Input:** Virtual texture coordinate $t_v$ (normalized 0-1), number of voxels in the virtual space $n_v$, number of bricks along the axis $n_b$, brick size $s_b$, number of voxels in the physical memory space $n_p$, and an index texture storing brick indices $i_b$.
*   **Output:** Physical texture coordinate $t_p$ for sampling the single bound texture pool.

**Data Structures:**
*   **Index Texture:** A small texture storing integer brick indices. The resolution corresponds to the virtual space grid.
*   **Brick Pool:** A single large texture object containing all bricks packed contiguously.

**Steps:**
1.  Compute the index texture coordinate $t_i$ from the virtual texture coordinate $t_v$, $n_v$, and $n_b$:
    $$ t_i = \frac{t_v n_v - 0.5}{n_v - n_b} $$
2.  Terminate execution if $t_i < 0$ or $t_i > 1$.
3.  Look up the brick index $i_b$ from the index texture at $t_i$. Compute the physical brick base address $t_{pb}$:
    $$ t_{pb} = \frac{i_b s_b}{n_p} $$
4.  Compute the virtual offset $t_{vo}$ within the brick by taking the fractional part of $t_i n_b$. Compute the physical offset $t_{po}$:
    $$ t_{po} = \frac{t_{vo} (s_b - 1) + 0.5}{n_p} $$
5.  Add $t_{po}$ to $t_{pb}$ to obtain the final physical address $t_p$:
    $$ t_p = t_{pb} + t_{po} $$

**Parameters:**
*   **Voxel Overlap:** Assumes a single voxel overlap at brick boundaries [S1, unofficial].
*   **Typical Values:** Not given in the sources.

**Edge Cases and Pitfalls:**
*   Without virtual-to-physical translation, modified texture coordinates might point into a different brick than the currently bound bricks in the shader [S1, unofficial].
*   The index texture is usually small, adding minimal overhead [S1, unofficial].
*   If magnification is not used, steps 1 and 2 can be eliminated by computing index texture coordinates on the CPU [S1, unofficial].

**Pseudocode:**
```python
def virtual_to_physical(t_v, n_v, n_b, s_b, n_p, index_texture):
    # Step 1: Compute index texture coordinate
    t_i = (t_v * n_v - 0.5) / (n_v - n_b)
    
    # Step 2: Terminate if out of bounds
    if t_i < 0 or t_i > 1:
        return None
        
    # Step 3: Look up brick index and compute physical brick address
    i_b = index_texture.sample(t_i)
    t_pb = (i_b * s_b) / n_p
    
    # Step 4: Compute virtual offset and physical offset
    t_vo = frac(t_i * n_b)
    t_po = (t_vo * (s_b - 1) + 0.5) / n_p
    
    # Step 5: Compute final physical address
    t_p = t_pb + t_po
    return t_p
```

## Subtopics

### [Hierarchical Index/Address Translation](8371-hierarchical-index-address-translation.md)
Hierarchical Index/Address Translation is a method for mapping virtual volume coordinates to physical texture coordinates in GPU-based volume rendering, supporting multi-resolution rendering and memory management. It enables arbitrary coordinate transformations, such as magnification, in the fragment shader without rebinding textures by locating bricks within a single memory pool [Parent]. It sets itself apart from flat index textures by using a page table hierarchy to handle multi-resolution data and anisotropic down-sampling, which prevents storage as a regular mipmap.

## Operating characteristics
*   **Time Complexity:** The address translation adds minimal overhead [S1, unofficial].
*   **Memory Complexity:** Keeps only the required portion of high-resolution data in texture memory [S1, unofficial].
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Useful for browsing very large datasets with limited resources, especially when only a small part of the original data can be placed in on-board texture memory [S1, unofficial].
*   **Strengths:** Allows arbitrary coordinate transformations (magnification, deformation, perturbation) without rebinding textures [S1, unofficial].
*   **Limitations:** Requires an index texture and indirection overhead [S1, unofficial].
*   **When to use:** When browsing very large datasets with limited resources and other multi-resolution strategies fail [S1, unofficial].
*   **When not:** When magnification is not needed and CPU-side coordinate computation is preferred to eliminate shader overhead [S1, unofficial].

## Background
Originated in "A Focus and Context Interface for Interactive Volume Rendering" by I. Kits et al. [S1, unofficial]. It is used for interactive volume rendering, particularly for focus and context interfaces where a high-resolution version is used in the focus area and a downsampled version in the context [S1, unofficial].
