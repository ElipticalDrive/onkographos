# Volume Access Caching


## Overview
Volume Access Caching is a technique within the Evaluation Cache framework that caches the back sample of the current integration step for reuse as the front sample of the next iteration [S1]. It reduces redundant volume data fetches by exploiting temporal coherence along a single ray [S1]. It sets itself apart from sibling methods like [Edge Point Caching](891-edge-point-caching.md) by focusing on consecutive sample reuse along a ray rather than spatial coherence across neighboring pixels [S1].

## How it works
**Inputs and Outputs:**
*   Input: Ray origin $o$, ray direction $d$, step size $\Delta t$, volume data structure, and number of steps $N$ [S1].
*   Output: Interpolated voxel values at the front and back sample positions for compositing or integration [S1].

**Data Structures:**
*   `cached_t`: Scalar storing the ray parameter $t$ of the cached back sample [S1].
*   `cached_value`: Scalar or vector storing the interpolated value at `cached_t` [S1].
*   `cache_valid`: Boolean flag indicating whether the cache contains a valid value [G].

**Steps:**
1.  **Initialize Cache:** Set `cache_valid = false`, `cached_t = 0`, and `cached_value = 0` [G].
2.  **Compute Step Parameters:** For iteration $i$ from $0$ to $N-1$, calculate the front parameter $t_{start} = i \cdot \Delta t$ and the back parameter $t_{end} = t_{start} + \Delta t$ [S1].
3.  **Check Cache Hit:** Compare $t_{start}$ with `cached_t`. If `cache_valid` is true and $|t_{start} - \text{cached\_t}| < \epsilon$, retrieve `cached_value` as the front sample $V_{start}$ [S1]. Otherwise, fetch $V_{start}$ from the volume data at $o + t_{start} \cdot d$ [S1].
4.  **Fetch Back Sample:** Fetch the volume value $V_{end}$ at $o + t_{end} \cdot d$ [S1].
5.  **Update Cache:** Store $t_{end}$ in `cached_t`, $V_{end}$ in `cached_value`, and set `cache_valid = true` for the next iteration [S1].
6.  **Return Values:** Pass $V_{start}$ and $V_{end}$ to the compositing or integration routine [S1].

**Formulas:**
Let $V(t)$ be the volume function sampled at parameter $t$.
Let $t_i = i \cdot \Delta t$ be the parameter for the $i$-th step.
The cache hit condition is:
$$ |t_i - \text{cached\_t}| < \epsilon $$
If the condition holds, $V(t_i)$ is retrieved from cache. Otherwise, $V(t_i)$ is computed via trilinear interpolation or higher-order scheme, and the back sample $V(t_i + \Delta t)$ is stored in cache for the next iteration ($i+1$) [S1].

**Parameters:**
*   Step size $\Delta t$: Determined by sampling density or adaptive criteria [S1].
*   Tolerance $\epsilon$: Small floating-point threshold for comparison, e.g., $10^{-6}$ [G].

**Edge Cases and Pitfalls:**
*   **First Iteration:** The cache is invalid, forcing a full fetch for both front and back samples [S1].
*   **Variable Step Size:** If $\Delta t$ varies per iteration, the cache stores absolute $t$ values, so the hit condition remains valid without modification [G].
*   **Precision Errors:** Floating-point drift may cause $t_i$ to deviate slightly from exact multiples of $\Delta t$. Using a small tolerance $\epsilon$ prevents cache thrashing [G].

**Pseudocode:**
```python
def volume_access_caching(ray_origin, ray_direction, step_size, volume_data, num_steps):
    # Cache state initialization
    cached_t = 0.0
    cached_value = 0.0
    cache_valid = False
    epsilon = 1e-6

    for i in range(num_steps):
        # Compute current step parameters
        t_start = i * step_size
        t_end = t_start + step_size

        # Check cache hit for front sample
        if cache_valid and abs(t_start - cached_t) < epsilon:
            v_start = cached_value
        else:
            v_start = volume_data.sample(ray_origin + t_start * ray_direction)

        # Fetch back sample
        v_end = volume_data.sample(ray_origin + t_end * ray_direction)

        # Update cache for next iteration
        cached_t = t_end
        cached_value = v_end
        cache_valid = True

        # Integration/compositing uses v_start and v_end
        # ...
    return v_start, v_end
```

## Subtopics

### [VDB Value Accessor Caching](8756-vdb-value-accessor-caching.md)
VDB Value Accessor Caching is a mechanism for coordinate-based value retrieval in OpenVDB structures that achieves average constant time complexity by exploiting the fixed four-level tree depth and spatial coherence of access patterns. Unlike traditional top-down tree traversal, this method effectively performs a bottom-up versus top-down traversal, which is very fast for typical access patterns like Finite-Difference stencils that are spatially coherent.

### Volume File Caching
Volume File Caching manages the loading and sharing of volume grid data from disk to reduce I/O and memory duplication [S2]. It operates as follows:
*   **On-Demand Loading:** Volume datablocks with a filepath are loaded on-demand during modifier evaluation, drawing, UI updates, or Python access [S2].
*   **Two-Stage Load:** `BKE_volume_load()` loads the list of grids, names, metadata, and transforms. `BKE_volume_grid_load()` loads the grid tree and voxel data into memory [S2].
*   **Global Cache:** A global volume file cache shares grid memory between original and Copy-on-Write (CoW) datablocks, and between different volume datablocks referencing the same filepath. Only file-loaded grids are cached; procedurally generated grids are not [S2].
*   **Reference Counting:** Grid memory is freed immediately when the user count drops to zero [S2].
*   **Metadata vs. Tree Separation:** The cache distinguishes between metadata users and tree users. If tree users drop to zero, the grid tree is freed, but metadata remains in memory for metadata users [S2].
*   **Access Functions:** Specific functions like `BKE_volume_grid_openvdb_for_metadata()` and `BKE_volume_grid_openvdb_for_read()` ensure the correct level of data is loaded and locked [S2].

## Operating characteristics
*   **Time Complexity:** $O(1)$ per sample after the first fetch, assuming a cache hit [S1].
*   **Memory Complexity:** $O(1)$ additional memory per ray or thread, storing only the last sample's parameter and value [S1].
*   **Performance:** Reduces total texture accesses to exactly $N$ for $N$ steps, as the back sample is cached for the next iteration [S1]. For second-order pre-integration, this maintains efficiency while lowering computational cost [S1].
*   **Strengths:** Simple to implement, low overhead, effective for coherent sampling patterns [S1].
*   **Limitations:** Only effective when consecutive samples overlap or are adjacent [S1].
*   **When to Use:** Direct volume rendering with ray marching, especially with constant or smoothly varying step sizes [S1].
*   **When Not to Use:** Random access volume queries or non-overlapping adaptive steps [S1].

## Background
Volume Access Caching originates from second-order pre-integrated volume rendering, where caching the back sample minimizes discrepancy between interpolated values and reduces branching penalties on consumer graphics hardware [S1]. The technique is standard in direct volume rendering implementations that use pre-integration or higher-order schemes [S1]. It leverages the fact that integration steps share endpoints, making back-sample reuse a fundamental optimization [S1].
