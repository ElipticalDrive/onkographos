# Priority Queue Based Field Update

Also called: Level Manager, Coarse-to-Fine Update Queue

## Overview
Priority Queue Based Field Update is a dynamic optimization method for sparse voxel octrees that ensures volume field updates proceed from coarser to finer levels [S1]. This ordering is essential for interactive display, as it prevents visual artifacts caused by updating fine details before their coarser parents are consistent [S1]. It differs from recursive depth-first approaches, which miss this coarse-to-fine requirement, by using a priority queue sorted by cell level and tool identity to manage the update sequence [S1].

## How it works
### Inputs and Outputs
- **Input**: A Tool/Action couple applied to the volume [S1].
- **Output**: A modified Sparse Voxel Octree where cells intersected by the tool are updated and subdivided/simplified as needed, maintaining coarse-to-fine consistency [S1].

### Data Structures
The method relies on three primary data structures, enclosed within a **Level Manager** [S1]:

1.  **ToolCopy**: A frozen snapshot of the tool at the moment of application [S1].
    -   **Fields**: State information (position, orientation, scale, color, etc.), a reference to the original tool and action, and a unique integer identifier acting as a time-counter/timestamp [S1].
2.  **Cell-Queue**: A simple FIFO queue used to temporarily store cells intersected by the tool at a specific level [S1].
    -   **Operations**: Constant-time `pushback` and `popfront` [S1].
    -   **Indexing**: Indexed by the `ToolCopy` and the size (level) of the cells it contains [S1].
    -   **Access**: Only the update thread accesses the Cell-queues it empties or fills; the draw process accesses cells directly through the hierarchy, so no locking is needed inside Cell-queues [S1].
3.  **Level Manager Priority Queue**: The central scheduler [S1].
    -   **Elements**: Cell-queues (not individual ToolCopies) [S1].
    -   **Sorting Criteria**: Sorted by **Level** (cell size, coarser first) and then by **Tool/Action** (sequential application) [S1].
    -   **Implementation**: Typically implemented using a standard library priority queue (e.g., STL `priority_queue` relying on `vector`) [S1].

### Algorithm Steps

1.  **Initialization (User Thread)**:
    -   When a user applies a tool, the system creates a `ToolCopy` from the Tool/Action couple [S1].
    -   A new `Cell-Queue` is created, containing only the current root cell [S1].
    -   This `Cell-Queue` is inserted into the `Level Manager` priority queue [S1].

2.  **Update Loop (Update Thread)**:
    -   The update thread runs continuously in the background [S1].
    -   It extracts the highest-priority `Cell-Queue` from the `Level Manager` [S1].
    -   It processes cells in the queue using the modified `Apply` procedure [S1].
    -   If the priority queue becomes empty, the thread performs a **Simplification** step (as defined in the parent method) and then suspends itself using a blocking lock mechanism to save processor resources [S1].

3.  **Modified Apply Procedure**:
    -   The `Apply` procedure receives a `Cell-Queue` as an extra parameter [S1].
    -   It updates the internal vertices of the current cell and subdivides it if necessary [S1].
    -   **Crucial Difference**: Instead of recursively calling `Apply` on existing children immediately, it identifies children that intersect the tool [S1].
    -   These intersecting children are appended to the `Cell-Queue` associated with the next finer level [S1].
    -   If the `Cell-Queue` for the next level does not exist in the manager, it is created and inserted into the `Level Manager` priority queue [S1].

4.  **Interruption Handling**:
    -   If a coarser level is inserted into the `Level Manager` (e.g., from a new user action or undo/redo) while the update thread is processing a finer level's `Cell-Queue`, the current processing is interrupted [S1].
    -   The interrupted `Cell-Queue` is re-inserted into the `Level Manager` priority queue [S1].
    -   When the update thread returns to this queue, it resumes handling from where it was suspended [S1].

5.  **Threading Synchronization**:
    -   Two threads are used: one for user interaction/display and one for background updates [S1].
    -   Blocking access (locking) is limited strictly to the insertion and removal of `Cell-Queues` in the `Level Manager` priority queue [S1].
    -   No exclusion mechanism is needed inside `Cell-Queues` or for accessing cells through the hierarchy, as the update process is the only one modifying the queue structure, and the draw process reads cells directly [S1].

        self.cells.append(cell)

        return self.cells.pop(0)

            heapq.heappush(self._pq, (level, tool_copy.timestamp, cell_queue))

### Parameters and Edge Cases
-   **Timestamps**: The unique identifier in `ToolCopy` acts as a time-counter [S1]. This ensures that if the same tool is applied multiple times, the order is preserved, and redundant computations can be avoided [S1].
-   **Interrupts**: If a coarser level is inserted while processing a finer level, the finer level's queue is suspended and re-queued [S1]. This ensures coarse-to-fine order is strictly maintained even with interleaved user actions [S1].
-   **Simplification**: When the queue is empty, a simplification step is performed [S1]. This step is not detailed in this article but is part of the parent method [S1].
-   **Thread Safety**: Locking is only required for the `Level Manager` priority queue operations [S1]. No locks are needed for `Cell-Queue` internal operations [S1].

## Operating characteristics
-   **Time Complexity**: The priority queue operations (insertion and removal) are $O(\log N)$, where $N$ is the number of cell-queues [S1]. The `Apply` procedure processes each cell once per level [S1]. The total time is proportional to the number of cells intersected by the tool across all levels [S1].
-   **Memory Complexity**: Additional memory is required for `ToolCopy` objects and `Cell-Queue` structures [S1]. The `Cell-Queue` structures are temporary and are consumed as the update proceeds [S1].
-   **Performance**: The two-thread approach (update thread + user thread) minimizes blocking [S1]. The update thread suspends when idle, saving CPU resources [S1]. The locking overhead is minimal because access to the `Level Manager` is infrequent compared to cell processing [S1].
-   **Strengths**: Ensures correct coarse-to-fine update order for interactive display [S1]. Handles interruptions gracefully [S1]. Simple synchronization model [S1].
-   **Limitations**: Requires a priority queue data structure [S1]. The recursive approach is simpler but incorrect for interactive display [S1]. Handling multiple concurrent tools is possible without requiring any modification to the base implementation [S1].

## Background
The method was introduced by Eric Ferley, Marie-Paule Cani, and Jean-Dominique Gascuel in their paper "Resolution Adaptive Volume Sculpting" [S1]. It addresses the limitation of recursive field update methods, which process depth-first and fail to maintain the coarse-to-fine consistency required for real-time interaction [S1]. The implementation was tested with POSIX threads, IRIX sprocs, and Windows threads, showing no significant performance differences [S1].
