# Sparse Voxel Octree Representation

Also called: Basic SVO in rust, Octree Representation, Sparse Voxel Octree (SVO) - Basic Implementation, Sparse Voxel Octrees, Voxel Octrees, pointer-based sparse octree

## Overview
A Sparse Voxel Octree (SVO) is a hierarchical data structure used to represent the geometry of 3D voxelized scenes where the proportion of active voxels is low [S1, S2]. It solves the memory inefficiency of dense grids by recursively decomposing space into octants, storing only the structure necessary to reach active voxels [S1, S2]. Unlike its parent [Chunk-based Voxel Data Structure](1818-chunk-based-voxel-data-structure.md), which uses fixed-size blocks, the SVO adapts its granularity to the scene's sparsity, enabling efficient traversal and culling [S2][S3, unofficial]. It differs from [Pointerless Sparse Voxel Octrees (PSVO)](2340-sparse-voxel-octree-representation.md#pointerless-sparse-voxel-octrees-psvo) by using explicit pointers to child nodes, trading increased binary size for faster traversal speeds [S2].

## How it works
**Inputs:** A 3D scene defined on a grid of dimensions $N^3$, where $N = 2^m$ for integer $m \ge 1$ [S2]. Each voxel has a geometry attribute (active or passive) [S2].
**Outputs:** An SVO data structure consisting of a root node and a hierarchy of internal nodes (INODEs) and leaf nodes (LNODEs) [S2].

**Data Structures:**
The SVO is defined by the following Backus-Naur Form (BNF) [S1, S2]:
```bnf
SVO ::= (n)<NODE>
NODE ::= <INODE>|<LNODE>
INODE ::= <CHNM>(p)<BIT><PTS>
LNODE ::= <CHNM>(q)<BIT>
CHNM ::= (8)<HT>
PTS ::= (1)*(8)<PT>
PT ::= (r)<BIT>
HT ::= <BIT>
BIT ::= "0" | "1"
```
*   **CHNM (Child Node Mask):** An 8-bit vector where each bit is a Header Tag (HT) corresponding to one of the 8 child octants [S2].
*   **HT (Header Tag):** A single bit. `0` indicates a passive octant (all voxels are passive); `1` indicates an active octant (at least one voxel is active) [S2].
*   **PTS (Pointer Table Segment):** A variable-length array of pointers (PTs) to child nodes, ordered according to the active HTs in the CHNM [S2]. The number of PTs, $n$, is between 1 and 8 [S2].
*   **PT (Pointer):** An $r$-bit value encoding the address of a child node [S2].
*   **Parameters:**
    *   $p$: Reserved bits for INODE alignment. Typical value: 24 [S2].
    *   $q$: Reserved bits for LNODE alignment. Typical value: 24 [S2].
    *   $r$: Bits per pointer. Typical value: 32 [S2].

**Construction Algorithm:**
1.  **Initialization:** Create a root node representing the entire $N^3$ volume [S2].
2.  **Decomposition:** Recursively divide the current node's volume into 8 child octants [S2]. For the root, child octants have dimensions $(N/2)^3$ [S2].
3.  **Classification:** For each child octant, determine if it is passive or active [S2].
    *   If all voxels in the octant are passive, set the corresponding HT to `0`.
    *   If at least one voxel is active, set the corresponding HT to `1` [S2].
4.  **Recursion:**
    *   If the octant is passive, no further action is taken for this branch [S2].
    *   If the octant is active, create a child node and recursively apply decomposition [S2].
5.  **Termination:** Stop recursion at layer $m-1$, which corresponds to octants of size $2 \times 2 \times 2$ voxels [S2]. These are Leaf Nodes (LNODEs) [S2].
    *   Note: Child nodes representing single $1 \times 1 \times 1$ voxels are not created. The status of such voxels is recorded directly in the HT of the parent LNODE [S2].
6.  **Pointer Assignment:** For each INODE, concatenate the CHNM, alignment bits, and the PTS array to its binary representation [S2]. The order of PTs in PTS matches the order of active HTs in CHNM (typically Morton order) [S2].

**Lookup Algorithm (Iterative):**
Given coordinates $(x, y, z)$ and current node `this` with size `s`:
1.  Loop:
2.  If `this` is a Leaf, return the voxel data.
3.  If `this` is an INODE:
    a. Calculate child index: $idx = ((x \ge s) \ll 0) | ((y \ge s) \ll 1) | ((z \ge s) \ll 2)$ [S3, unofficial].
    b. Retrieve the pointer $PT$ from the PTS array at the position corresponding to the active HT at index $idx$ [S2].
    c. Follow $PT$ to the next node.
    d. Update coordinates: $x \leftarrow x \pmod s$, $y \leftarrow y \pmod s$, $z \leftarrow z \pmod s$ [S3, unofficial].
    e. Update size: $s \leftarrow s / 2$ [S3, unofficial].
    f. Repeat.

**Insertion Algorithm:**
1.  Traverse the tree to the appropriate leaf position based on $(x, y, z)$ [S3, unofficial].
2.  If the current node is a Leaf containing a voxel:
    a. Clone the existing voxel [S3, unofficial].
    b. Replace the Leaf with a new Branch node where all 8 children are Leaves containing the cloned voxel [S3, unofficial].
    c. Recursively insert the new voxel into the new Branch [S3, unofficial].
3.  If the current node is a Branch, calculate the child index and recursively insert into the corresponding child [S3, unofficial].
4.  If the target depth is reached, update the leaf data [S3, unofficial].

**Node Sizes:**
*   INODE size: $SVO_{INODEsize} = p + SVO_{CHNMsize} + n \times PT_{size} + 8 + n \times r$ [S2].
    *   With $p=24, q=24, r=32$: Size ranges from 64 bits (1 child) to 288 bits (8 children) [S2].
*   LNODE size: $SVO_{LNODEsize} = q + SVO_{CHNMsize}$ [S2].
    *   With $q=24$: Size is up to 4 times larger than PSVO LNODEs [S2].

**Edge Cases and Pitfalls:**
*   **Ad-hoc Modification:** Modifying geometry in a static SVO requires decompression, modification, and recompression, which is computationally demanding [S1].
*   **GPU Mapping:** The pointer-based structure maps poorly to GPU memory models, preventing benefits from hardware texture caching and filtering [S6, unofficial].
*   **Binary Size:** The binary representation of internal nodes is significantly larger than in pointerless variants (8-to-36 times increase with typical parameters) [S2].

## Subtopics

### [Sparse Voxel Octree with Bricks](2354-sparse-voxel-octree-with-bricks.md)
Stores filtered lighting information in 3x3x3 voxel volumes (bricks) attached to octree nodes. It solves memory inefficiency by positioning voxel centers at node corners, allowing hardware trilinear interpolation to cover 2x2x2 nodes without expensive one-voxel borders. Choose this for real-time indirect illumination.

### [Naive Octree Node Representation](2445-naive-octree-node-representation.md)
Direct memory layout where each non-leaf node explicitly stores pointers to its eight children, and leaf nodes store a single data value. It solves the problem of implementing a standard octree with minimal abstraction overhead. Choose this for implementation simplicity and direct pointer dereferencing.

### [SVRaster](2464-svraster.md)
A real-time, high-fidelity novel-view synthesis framework that renders adaptive sparse voxels using a custom rasterizer. It distinguishes itself by partitioning 3D space into disjoint voxels and using ray direction-dependent Morton ordering to ensure correct depth sorting. Choose this for neural-free voxel rendering with high PSNR and FPS.

### [Dynamic Update Optimization](4120-dynamic-update-optimization.md)
Heuristic techniques for accelerating indirect illumination calculation by separating static and dynamic scene components. It solves the performance bottleneck of recalculating global illumination for every frame. Choose this for scenes with moving geometry.

### [Sparse Voxel Octree (SVO)](8749-sparse-voxel-octree-svo.md)
A specific implementation of the SVO for efficient ray traversal, frustum culling, and visual level-of-detail (LoD). It is distinguished by shader-based traversal and specific SDF storage formats. Choose this for geometry-independent LoD and tight compression.

## Operating characteristics
**Time Complexity:** Lookup and insertion require tree traversal, which is $O(\log N)$ in depth, but involves more overhead than direct index access in dense grids [S6, unofficial]. Traversal performance is slower than dense grids due to pointer chasing [S7, unofficial].
**Memory Complexity:** Highly efficient for sparse scenes (e.g., 0.01% active voxels) as it does not store empty volumes [S2][S6, unofficial]. However, internal nodes are significantly larger than in pointerless variants (PSVO) [S2].
**Measured Performance:** With $p=24, q=24, r=32$, INODE sizes range from 64b to 288b [S2].
**Strengths:** Tight compression for sparsely populated spaces; uniform subdivision allows smooth LoD degradation [S2, S4].
**Limitations:** Poor mapping to GPU texture caching; ad-hoc modifications are expensive [S1][S6, unofficial].
**When to Use:** Static or semi-static scenes with low voxel density where traversal speed is prioritized over memory compactness [S2].
**When Not to Use:** Scenes requiring frequent ad-hoc geometry modifications or when maximum memory compactness is required (use PSVO) [S1, S2].

## Background
The Sparse Voxel Octree was introduced as a hierarchical data structure for representing 3D voxelized scenes with a small proportion of active voxels [S1]. A two-step out-of-core algorithm for SVO construction was created in 2013, involving voxelization of triangle meshes followed by SVO construction [S1]. In 2015, an algorithm was presented enabling voxelization into SVO without an intermediate product [S1]. Crassin presented a GPU implementation of an octree for voxel cone tracing global illumination [S6, unofficial]. The structure is an extension of the quadtree representation of 2D images [S5, unofficial].
