# Naive Octree Node Representation
Also called: Branch Tree Node, Direct Memory Octree Node, Pointer-based Octree Node

## Overview
The Naive Octree Node Representation is a direct memory layout for hierarchical voxel data where each non-leaf node explicitly stores pointers to its eight children, and leaf nodes store voxel data. It solves the problem of implementing a standard octree structure with minimal abstraction overhead, serving as the baseline for more complex sparse voxel representations. It differs from its siblings by allocating explicit memory for every node in the hierarchy, including leaves, which results in higher memory consumption compared to compressed variants like [Bitmask Leaf Compression](3603-bitmask-leaf-compression.md) or brick-based layouts like [Sparse Voxel Octree with Bricks](2354-sparse-voxel-octree-with-bricks.md).

## How it works
**Inputs:** A voxel position $(x, y, z)$, a voxel value (e.g., color or density), and the current octree root node.
**Outputs:** An updated octree structure with the voxel inserted or retrieved.

**Data Structures:**
The core structure is the `OctreeNode`. Two primary layouts are cited in the sources:

1.  **Layout A (S1):**
    ```cpp
    struct Node {
        Node * children[8]; // Array of 8 pointers
        int8_t voxelColorIndex; // Stored if leaf
        bool isLeaf; // Flag indicating leaf status
    };
    ```
    *   **Size:** 72 Bytes on a 64-bit processor (8 pointers $\times$ 8 bytes + 1 byte + 1 byte padding/alignment = 66 bytes, likely padded to 72 or including overhead). 40 Bytes on a 32-bit processor (8 pointers $\times$ 4 bytes + 1 byte + padding). [S1, unofficial]

2.  **Layout B (S3):**
    ```cpp
    struct OctreeNode {
        bool isLeaf;
        uint32_t value; // Stores voxel value if leaf, or acts as a marker
        OctreeNode* children; // Pointer to array of 8 children if not leaf
        uint8_t centerX, centerY, centerZ; // Center coordinates
        uint8_t depth; // Current depth in the tree
    };
    ```
    *   **Memory Order:** Matches declaration order. [S3, unofficial]

3.  **Layout C (S2):**
    ```cpp
    template <typename Scalar>
    struct branch_tree_node : tree_node<Scalar> {
        std::array<base_type*, 8> children_;
    };
    ```
    *   Inherits from a base `tree_node`. [S2, unofficial]

**Numbered Steps:**

1.  **Root Initialization:**
    *   Set `depth = 0`.
    *   Set `isLeaf = true`.
    *   Set `value = 0` (or initial voxel value).
    *   Set `centerX = centerY = centerZ = 0`.
    *   [S3, unofficial]

2.  **Non-Root Initialization (for child nodes):**
    *   Set `depth` based on parent depth + 1.
    *   Set `isLeaf = true`.
    *   Set `value = 0`.
    *   Calculate `childDepth = depth - 1`.
    *   Calculate `childSize = 1 << childDepth` (i.e., $2^{depth-1}$).
    *   Calculate `centerX = x + childSize`, `centerY = y + childSize`, `centerZ = z + childSize`.
    *   [S3, unofficial]

3.  **Insert Voxel (`SetVoxel`):**
    *   **Base Case:** If `depth == 0`, set `this->value = value` and return. [S3, unofficial]
    *   **Leaf Optimization:** If `isLeaf` is true and `this->value == value`, return (no change needed). [S3, unofficial]
    *   **Split Leaf:** If `isLeaf` is true but value differs or depth > 0:
        *   Call `initChildren()` to allocate and initialize 8 child nodes.
        *   Copy `this->value` to all 8 children (propagating the previous leaf value).
        *   Set `isLeaf = false`.
    *   **Recurse:**
        *   Compute `childIndex` using `GetChildIndex(x, y, z)`. This function maps global coordinates to one of 8 octants (0-7).
        *   Recursively call `children[childIndex].SetVoxel(x, y, z, value)`.
    *   **Collapse:** Call `TryCollapse()` to check if children can be merged back into a leaf if they share the same value. [S3, unofficial]

4.  **Retrieve Voxel (`GetValue`):**
    *   If `isLeaf` is true, return `value`. [S3, unofficial]
    *   Else, compute `childIndex` via `GetChildIndex(x, y, z)`.
    *   Return `children[childIndex].GetValue(x, y, z)`. [S3, unofficial]

5.  **Initialize Children (`initChildren`):**
    *   Set `childDepth = depth - 1`.
    *   Set `childSize = 1 << childDepth`.
    *   Allocate `children = new OctreeNode[8]`.
    *   Compute base coordinates: `baseX = centerX - childSize`, `baseY = centerY - childSize`, `baseZ = centerZ - childSize`.
    *   Initialize 8 children with offsets relative to the base:
        *   Indices 0-7 correspond to octants. For example, child 0 might be at `(baseX, baseY, baseZ)`, child 1 at `(baseX + childSize, baseY, baseZ)`, etc.
        *   Each child is initialized with `isLeaf = true`, `value = 0` (or copied from parent), and appropriate `centerX/Y/Z` and `depth`.
    *   [S3, unofficial]

**Parameters:**
*   **Memory Cost:** 72 Bytes per node on 64-bit systems, 40 Bytes on 32-bit systems. [S1, unofficial]
*   **Depth:** Typically starts at 0 (root) and increases. Depth 0 is the base case. [S3, unofficial]

**Edge Cases and Pitfalls:**
*   **Depth 0 Recursion:** Attempting to recurse below depth 0 is prevented by the explicit `depth == 0` check in `SetVoxel`. [S3, unofficial]
*   **Undefined Helpers:** `GetChildIndex` and `TryCollapse` are referenced but not defined in the source snippets. Implementation requires a robust child index mapping function and a post-insertion collapse check. [S3, unofficial]
*   **Memory Overhead:** Storing explicit leaf nodes causes memory usage to approach 8 times that of a full octree of depth $d-1$. [S1, unofficial]

## Subtopics

### [Bitmask Leaf Compression](3603-bitmask-leaf-compression.md)
A memory optimization technique that eliminates explicit leaf nodes by packing their voxel data into a single integer field within their parent node. It reduces the memory cost factor $mc$ from 8 to 1 for the deepest level. Choose this when memory is constrained and leaf nodes are frequent.

### [Octree Data Structure Layout](4518-octree-data-structure-layout.md)
Defines the memory layout and class structure for a naive octree representation used in CPU-based voxel rendering, encapsulating the node structure within a higher-level `Octree` class. It differs from Bitmask Leaf Compression by storing all nodes explicitly without compressing leaf status.

## Operating characteristics
*   **Time Complexity:** Insertion and retrieval are $O(d)$ where $d$ is the depth of the octree, as each operation traverses one node per level. [S3, unofficial]
*   **Memory Complexity:** $O(N)$ where $N$ is the number of nodes. Due to explicit storage of all nodes, including leaves, memory usage is high. The memory cost factor $mc$ approaches 8 for deep, sparse trees. [S1, unofficial]
*   **Performance:** Fast to implement and traverse due to simple pointer chasing. However, cache performance may suffer due to scattered node allocations (unless nodes are allocated in contiguous blocks, which is not guaranteed in the naive representation). [S1, unofficial]
*   **Strengths:** Simple implementation, direct mapping to octree theory, easy to debug.
*   **Limitations:** High memory overhead, especially for sparse data with many leaves. Not suitable for real-time applications with large scenes without compression. [S1, unofficial]
*   **When to Use:** Prototyping, educational purposes, or when memory is not a constraint and simplicity is prioritized.
*   **When Not to Use:** Real-time rendering of large sparse scenes, mobile devices with limited memory, or when high cache locality is required.

## Background
The Naive Octree Node Representation is a fundamental concept in spatial data structures, originating from the general theory of octrees. It is commonly used in computer graphics for voxel-based rendering and collision detection. The specific implementations cited here come from various sources:
