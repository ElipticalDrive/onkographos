# Naive Octree Node Representation

Also called: Branch Tree Node, Direct Memory Octree Node, Pointer-based Octree Node

## Overview
The Naive Octree Node Representation is a direct memory layout for hierarchical voxel data where each non-leaf node explicitly stores pointers to its eight children, and leaf nodes store a single voxel value. It solves the problem of organizing sparse 3D data in a recursive spatial partitioning structure without complex indexing or bit-packing overhead [S1, S3, unofficial]. It differs from its siblings, such as [Sparse Voxel Octree with Bricks](2354-sparse-voxel-octree-with-bricks.md) which uses fixed-size blocks for cache locality, and [Bitmask Leaf Compression](3603-bitmask-leaf-compression.md) which packs leaf status into parent nodes, by prioritizing implementation simplicity and direct pointer access over memory efficiency [S1, S3, unofficial].

## How it works
**Inputs:** A voxel position $(x, y, z)$ and a value (e.g., color or density).
**Outputs:** An updated octree structure containing the voxel.

**Data Structures:**
The core structure is the `OctreeNode`. The layout varies slightly by source, but generally includes:
1.  **Children:** An array of 8 pointers to child nodes. For leaf nodes, this field is null or unused [S1, S3, unofficial].
2.  **Leaf Status:** A boolean flag `isLeaf` indicating if the node is a leaf [S1, S3, unofficial].
3.  **Value:** A `uint32_t` or similar type storing the voxel data if `isLeaf` is true [S3, unofficial]. Some implementations use an `int8_t voxelColorIndex` [S1, unofficial].
4.  **Metadata:** Fields such as `depth`, `centerX/Y/Z`, and `childSize` to facilitate traversal and coordinate mapping [S3, unofficial].

**Memory Layout:**
On a 64-bit processor, the node size is 72 bytes. On a 32-bit processor, it is 40 bytes [S1, unofficial].
A typical C-style struct layout is:
```cpp
struct Node {
    Node * children[8]; // 8 pointers
    int8_t voxelColorIndex; // or uint32_t value
    bool isLeaf;
};
```

**Algorithm Steps:**

1.  **Root Initialization:**
    Create the root node with `depth = 0`, `isLeaf = true`, `value = 0`, and center coordinates $(0, 0, 0)$ [S3, unofficial].

2.  **Non-Root Initialization:**
    When creating a child node at depth $d$, set `isLeaf = true`, `value = 0`. Calculate `childDepth = d - 1`, `childSize = 1 << childDepth`. Set center coordinates based on the parent's offset [S3, unofficial].

3.  **Insertion (`SetVoxel`):**
    To insert a voxel at $(x, y, z)$ with `value`:
    a. If `depth == 0`, set `this->value = value` and return [S3, unofficial].
    b. If `isLeaf` and `this->value == value`, return (optimization) [S3, unofficial].
    c. If `isLeaf`, call `initChildren()` to expand the node. Copy `this->value` to all 8 new children [S3, unofficial].
    d. Compute `childIndex` using `GetChildIndex(x, y, z)` [S3, unofficial].
    e. Recurse: `children[childIndex].SetVoxel(x, y, z, value)` [S3, unofficial].
    f. Call `TryCollapse()` to merge children if they are identical leaves [S3, unofficial].

4.  **Retrieval (`GetValue`):**
    To get the value at $(x, y, z)$:
    a. If `isLeaf`, return `value` [S3, unofficial].
    b. Compute `childIndex` using `GetChildIndex(x, y, z)` [S3, unofficial].
    c. Return `children[childIndex].GetValue(x, y, z)` [S3, unofficial].

5.  **Child Initialization (`initChildren`):**
    a. Set `childDepth = depth - 1`, `childSize = 1 << childDepth` [S3, unofficial].
    b. Allocate `children = new OctreeNode[8]` [S3, unofficial].
    c. Calculate base coordinates: $baseX = centerX - childSize$, $baseY = centerY - childSize$, $baseZ = centerZ - childSize$ [S3, unofficial].
    d. Initialize 8 children with offsets corresponding to the 8 octants:
       - $(0,0,0), (childSize,0,0), (0,childSize,0), (childSize,childSize,0)$
       - $(0,0,childSize), (childSize,0,childSize), (0,childSize,childSize), (childSize,childSize,childSize)$
       relative to the base coordinates [S3, unofficial].

## Subtopics

### [Bitmask Leaf Compression](3603-bitmask-leaf-compression.md)
A compression technique that eliminates leaf nodes at the last level by packing their information (8 voxels) into a 64-bit integer in their parent node.

### [Octree Data Structure Layout](4518-octree-data-structure-layout.md)
This article defines the memory layout and class structure for a naive octree representation used in CPU-based voxel rendering. It solves the problem of organizing hierarchical voxel data in contiguous memory to facilitate traversal. It differs from its parent [Naive Octree Node Representation](2445-naive-octree-node-representation.md) by encapsulating the node structure within a higher-level `Octree` class that manages global state, bounds, and the node vector, rather than just defining the node itself. It differs from [Bitmask Leaf Compression](3603-bitmask-leaf-compression.md) by storing all nodes explicitly in a vector without compressing leaf status into bitmasks.

## Operating characteristics
**Time Complexity:** Insertion and retrieval are $O(d)$ where $d$ is the depth of the octree, as each step traverses one level [S3, unofficial].
**Memory Complexity:** Each non-leaf node consumes significant memory due to 8 pointers. On 64-bit systems, this is 72 bytes per node; on 32-bit, 40 bytes [S1, unofficial]. For a full octree of depth $d$, the memory overhead is approximately 8 times that of a full octree of depth $d-1$ due to the leaf node overhead [S1, unofficial].
**Strengths:** Simple implementation, direct pointer access, easy to debug.
**Limitations:** High memory usage for sparse data with many leaf nodes. Pointer chasing can lead to cache misses.
**When to use:** Small-scale prototypes, educational purposes, or when memory bandwidth is not the primary bottleneck and implementation speed is critical [S1, S3, unofficial].
**When not to use:** Large-scale real-time rendering where memory footprint and cache efficiency are critical; consider [Sparse Voxel Octree with Bricks](2354-sparse-voxel-octree-with-bricks.md) or [Bitmask Leaf Compression](3603-bitmask-leaf-compression.md) instead.

## Background
The naive octree representation is a fundamental concept in spatial data structures, originating from the general theory of octrees [S2, unofficial]. It is widely used in early voxel-based rendering systems and terrain generation as a straightforward way to handle sparse 3D data [S3, unofficial]. The specific memory cost analysis (72/40 bytes) comes from a study on SVO compression efficiency [S1, unofficial].
