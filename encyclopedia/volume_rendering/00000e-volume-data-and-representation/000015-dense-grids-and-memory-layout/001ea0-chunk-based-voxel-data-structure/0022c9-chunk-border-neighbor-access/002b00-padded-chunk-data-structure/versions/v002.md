# Padded Chunk Data Structure

Also called: Chunk Padding, Extra padding layer, Halo Voxels, PaddedChunk, Padding chunk sizes

## Overview
The Padded Chunk Data Structure is a memory layout strategy for dense voxel grids that allocates a 1-voxel boundary shell around each chunk to store neighbor data [S1, unofficial]. This allows neighbor lookups during mesh generation (such as greedy meshing) to proceed without bounds checks or explicit cross-chunk pointer dereferencing, treating chunk borders semantically identical to internal voxels [S1, unofficial]. It differs from sibling methods like Chunk Neighbor Referencing, which maintain explicit links to adjacent chunks, by duplicating boundary data within the chunk's own memory space [S1, unofficial].

## How it works
### Inputs and Outputs
- **Input**: Unpadded chunk dimensions (typically a multiple of 2, e.g., $32^3$) [S2, unofficial].
- **Output**: A flat memory array of size $(S+2)^3$ containing voxel data, where $S$ is the unpadded chunk size [S1, unofficial].

### Data Structures
The core structure is a flat 1D array representing a 3D volume [S1, unofficial].
- **Type**: Array of `VoxelBlock` (or equivalent voxel type) [S1, unofficial].
- **Dimensions**:
  - Let $S$ be the unpadded chunk size [S2, unofficial].
  - Padded size: $L = S + 2$ [S1, unofficial].
  - Total volume: $V_{padded} = L^3$ [S1, unofficial].
- **Layout**: The array is linearized in row-major order (X fastest, then Y, then Z) [S1, unofficial].

### Steps
1. Allocate chunk memory with a padded size $L = S + 2$ [S2, unofficial].
2. Populate the inner region with the chunk's local voxel data [S2, unofficial].
3. Populate the outer 1-voxel shell with data from neighboring chunks [S2, unofficial].
4. During mesh generation, ignore the padded voxels and only mesh the inner region [S2, unofficial].

### Formulas
**Linearization Index**:
For a 3D coordinate $(x, y, z)$ within the padded chunk of size $L$:
$$ \text{index} = x + L \cdot (y + L \cdot z) $$
where $0 \le x, y, z < L$ [S1, unofficial].

**Inner Region Bounds**:
The valid voxel data for meshing lies in:
$$ 1 \le x \le S, \quad 1 \le y \le S, \quad 1 \le z \le S $$
where $S = L - 2$ [S2, unofficial].

### Parameters
- **Padding Size**: 2 voxels along all three axes (1-voxel shell on each side) [S2, unofficial].
- **Unpadded Chunk Size**: A multiple of 2 (e.g., $32^3$) [S2, unofficial].

### Edge Cases and Pitfalls
- **Consistency**: Block updates require updating block data in two separate chunks (the original and its neighbor) to keep the padding shell consistent [S2, unofficial].
- **Thread Safety**: In multi-threaded environments, padding population must be handled exclusively on worker threads to avoid race conditions [S2, unofficial].

### Pseudocode
```python
def allocate_padded_chunk(unpadded_size: int) -> list:
    padded_size = unpadded_size + 2
    total_volume = padded_size ** 3
    return [0] * total_volume

def populate_chunk(chunk_data: list, unpadded_size: int, local_voxels: list, neighbor_faces: dict) -> None:
    padded_size = unpadded_size + 2
    for z in range(unpadded_size):
        for y in range(unpadded_size):
            for x in range(unpadded_size):
                idx = x + 1 + padded_size * (y + 1 + padded_size * (z + 1))
                chunk_data[idx] = local_voxels[x + unpadded_size * (y + unpadded_size * z)]
    copy_face(chunk_data, padded_size, unpadded_size, neighbor_faces[(-1, 0, 0)], "x_min")
    copy_face(chunk_data, padded_size, unpadded_size, neighbor_faces[(1, 0, 0)], "x_max")
    copy_face(chunk_data, padded_size, unpadded_size, neighbor_faces[(0, -1, 0)], "y_min")
    copy_face(chunk_data, padded_size, unpadded_size, neighbor_faces[(0, 1, 0)], "y_max")
    copy_face(chunk_data, padded_size, unpadded_size, neighbor_faces[(0, 0, -1)], "z_min")
    copy_face(chunk_data, padded_size, unpadded_size, neighbor_faces[(0, 0, 1)], "z_max")

def copy_face(chunk_data: list, padded_size: int, unpadded_size: int, neighbor_face: list, face: str) -> None:
    for z in range(unpadded_size):
        for y in range(unpadded_size):
            for x in range(unpadded_size):
                if face == "x_min": tx, ty, tz = 0, y + 1, z + 1
                elif face == "x_max": tx, ty, tz = padded_size - 1, y + 1, z + 1
                elif face == "y_min": tx, ty, tz = x + 1, 0, z + 1
                elif face == "y_max": tx, ty, tz = x + 1, padded_size - 1, z + 1
                elif face == "z_min": tx, ty, tz = x + 1, y + 1, 0
                elif face == "z_max": tx, ty, tz = x + 1, y + 1, padded_size - 1
                else: continue
                idx = tx + padded_size * (ty + padded_size * tz)
                chunk_data[idx] = neighbor_face[x + unpadded_size * (y + unpadded_size * z)]

def generate_mesh(chunk_data: list, unpadded_size: int) -> list:
    mesh_faces = []
    padded_size = unpadded_size + 2
    for z in range(1, unpadded_size + 1):
        for y in range(1, unpadded_size + 1):
            for x in range(1, unpadded_size + 1):
                idx = x + padded_size * (y + padded_size * z)
                if chunk_data[idx] != 0:
                    mesh_faces.append((x, y, z))
    return mesh_faces
```

## Subtopics

### [Chunk Neighbor Referencing for Boundary Meshing](4171-chunk-neighbor-referencing-for-boundary-meshing.md)
Maintains explicit pointers to adjacent chunks instead of duplicating data. Choose when memory is constrained and chunk management complexity is acceptable.

### [Chunk Neighbor Retrieval](6783-chunk-neighbor-retrieval.md)
Dynamically fetches neighbor data on demand. Choose when neighbor access is sparse or unpredictable.

## Operating characteristics
- Enables efficient greedy meshing in multi-threaded environments by eliminating bounds checks and cross-chunk synchronization during meshing [S2, unofficial].
- Requires updating two chunks (original and neighbor) on block changes, increasing update complexity [S2, unofficial].
- Not suitable for highly dynamic scenes with frequent block updates unless update propagation is optimized [S2, unofficial].
- Time and memory complexity are not given in the sources.

## Background
The technique is used in multi-threaded voxel engines, such as those built with Unity, where padding is handled on worker threads [S2, unofficial]. The approach is also referenced in projects like Infinigen, which uses padded chunk structures for world generation [S1, unofficial].
