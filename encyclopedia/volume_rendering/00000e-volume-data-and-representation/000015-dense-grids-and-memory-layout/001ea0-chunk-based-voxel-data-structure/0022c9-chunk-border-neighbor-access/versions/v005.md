# Chunk Border Neighbor Access

Also called: Read-only neighborhood view, VoxelNeighborhood trait

## Overview
Chunk Border Neighbor Access is a strategy for handling neighbor lookups at chunk boundaries in chunk-based voxel data structures by providing a read-only neighborhood view trait [S1, unofficial]. It solves the problem of distinguishing between internal voxels and boundary voxels during operations like meshing or rendering, treating chunk borders as semantically identical to internal voxels [S1, unofficial]. This approach separates the logic of neighbor retrieval from the logic of neighbor occlusion or processing, allowing the meshing or rendering code to query local and cross-chunk neighbors through a uniform interface [S1, unofficial]. It differs from sibling methods like [Padded Chunk Data Structure](4918-padded-chunk-data-structure.md) by avoiding memory duplication of boundary voxels, and from [Chunk Neighbor Retrieval](6783-chunk-neighbor-retrieval.md) by providing a direct data access interface rather than just coordinate offsets.

## How it works
**Inputs:**
- A chunk-based voxel world where data is divided into fixed-size 3D blocks (chunks) [Parent].
- A specific voxel position within a chunk, represented as a 3D integer coordinate `IVec3` relative to the chunk's local origin.
- A mechanism to resolve the global chunk ID or pointer for a given local position if it lies on a boundary.

**Outputs:**
- The `BlockState` (or equivalent voxel data) of the neighbor at the queried position, or an indication that the neighbor is missing/unknown.

**Data Structures:**
The core data structure is a trait or interface, typically named `VoxelNeighborhood` [S1, unofficial]. It does not store voxel data itself but provides the method to retrieve it.
- `trait VoxelNeighborhood`:
  - `fn get(&self, position: IVec3) -> Option<BlockState>` [S1, unofficial]
    - `position`: The 3D integer coordinate of the neighbor to retrieve. This coordinate is typically relative to the current voxel being processed, allowing for negative offsets (e.g., `(-1, 0, 0)` for the left neighbor).
    - `BlockState`: The data type representing the voxel content (e.g., material ID, density, color).
    - `Option<BlockState>`: Returns `Some(state)` if the neighbor exists and is available, or `None` if the neighbor chunk is not currently loaded or available.

**Steps:**
1. **Initialize Neighborhood View:** Create an instance of the `VoxelNeighborhood` trait implementation. This implementation must have access to the global chunk map or a way to resolve chunk IDs from voxel coordinates [S1, unofficial].
2. **Query Neighbor:** When processing a voxel at local position `p` within a chunk, the algorithm needs to check a neighbor at offset `o`. The absolute position in the chunk's coordinate space is `p + o`.
3. **Resolve Boundary:**
   - If `p + o` is within the chunk's internal bounds (excluding the boundary shell if not padded), retrieve the voxel directly from the chunk's local data array.
   - If `p + o` lies on or outside the chunk boundary, the `VoxelNeighborhood` implementation must determine the global chunk ID of the neighbor chunk.
   - Retrieve the neighbor chunk from the world storage.
   - Calculate the local position within the neighbor chunk.
   - Retrieve the voxel data from the neighbor chunk.
4. **Handle Missing Data:** If the neighbor chunk is not available (e.g., not yet loaded in a streaming world), the `get` method returns `None` [S1, unofficial]. The calling algorithm must handle this case according to a predefined policy.

**Parameters:**
- `IVec3`: A 3D integer vector type.

**Edge Cases and Pitfalls:**
- **Missing Neighbor Chunks:** If a neighbor chunk is not currently available, the engine must define a policy explicitly [S1, unofficial]. Common options include: treating missing data as air and remeshing later, delaying meshing until required neighbors are present, or using an explicit unknown state [S1, unofficial]. The correct choice depends on the world-streaming model [S1, unofficial].
- **Boundary Semantics:** Chunk borders are not special semantically; a face on the edge of a chunk still has a normal voxel neighbor [S1, unofficial]. The only difference is where you retrieve that neighbor from [S1, unofficial].
- **Transparency Rules:** Geometry coverage and render opacity are related but not identical [S1, unofficial]. For example, two adjacent glass blocks may geometrically cover each other, but whether their shared face should be removed depends on material/rendering semantics [S1, unofficial]. A robust culling decision must account for these material properties, which may require additional information beyond just the `BlockState` [S1, unofficial].

## Subtopics

### [Chunk Neighbor Referencing for Boundary Meshing](4171-chunk-neighbor-referencing-for-boundary-meshing.md)
Precomputes pointers to adjacent chunks to handle meshing at chunk boundaries without global lookups. Builds on Chunk Border Neighbor Access by providing specific data structures and logic to resolve neighbor identities efficiently.

### [Padded Chunk Data Structure](4918-padded-chunk-data-structure.md)
Allocates a 1-voxel boundary shell around each chunk to store neighbor data, allowing neighbor lookups to proceed without bounds checks or explicit cross-chunk pointer dereferencing. Differs by duplicating boundary data within the chunk's own memory space.

### [Chunk Neighbor Retrieval](6783-chunk-neighbor-retrieval.md)
Determines the spatial coordinates of neighboring chunks relative to a center chunk. Differs by explicitly returning coordinate offsets rather than providing a read-only view trait.

## Operating characteristics
- **Time Complexity:** Neighbor lookup is $O(1)$ if the neighbor chunk is cached and the boundary resolution is efficient. If chunk resolution requires a global map lookup, it may be $O(\log N)$ or $O(1)$ depending on the hash map implementation.
- **Memory Complexity:** $O(1)$ additional memory per chunk for the neighborhood view interface, as it does not duplicate voxel data.
- **Strengths:** Clean separation of concerns; uniform interface for local and cross-chunk neighbors; no memory overhead for boundary duplication.
- **Limitations:** Requires a robust mechanism to resolve chunk IDs from voxel coordinates; handling missing chunks requires careful policy definition; potential performance overhead from chunk resolution if not optimized.
- **When to Use:** When memory efficiency is critical and chunk boundaries are frequent; when the world streaming model allows for deferred processing or explicit missing data handling.
- **When Not to Use:** When real-time performance is critical and chunk resolution overhead is unacceptable; when boundary duplication is already handled by other means (e.g., Padded Chunk Data Structure).

## Background
Chunk Border Neighbor Access is a conceptual strategy for managing neighbor lookups in chunk-based voxel data structures. It is discussed in the context of face culling for voxel cubes and partial shapes [S1, unofficial]. The approach emphasizes treating chunk borders as semantically identical to internal voxels, simplifying the meshing and rendering logic by providing a uniform interface for neighbor queries [S1, unofficial].
