# VDB Data Loading & 3D Texture Setup

Also called: VDB Loader, VDB to 3D Texture, getVDBData

## Overview
This method loads a VDB-formatted binary file, parses its sparse voxel coordinates and tile data, and uploads the resulting density field as a 3D texture for GPU rendering [S1, unofficial]. It bridges the gap between CPU-side sparse data structures and the GPU's dense 3D texture sampling capabilities, serving as the initialization step for [3D Texture Storage and Sampling](3064-3d-texture-storage-and-sampling.md) [G]. Unlike [Brick-based storage and caching](4138-brick-based-storage-and-caching.md) which manages hierarchical tiling for streaming, this method typically loads the entire sparse dataset into a single dense volume texture, making it suitable for scenes where the total voxel count fits within GPU memory limits [G].

## How it works
**Inputs:** A VDB binary file (`ArrayBuffer`) and a WebGL context [S1, unofficial].
**Outputs:** A WebGL 3D texture object containing the density data [S1, unofficial].

**Data Structures:**
1. **File Header:** Fixed-size binary structure containing `width` (uint16, offset 0), `height` (uint16, offset 2), `depth` (uint16, offset 4), and `count` (uint16, offset 6) [S1, unofficial].
2. **Coordinates:** `Uint16Array` of size `3 * nodeCount`, starting at offset 8 [S1, unofficial].
3. **Node Data:** `Uint8Array` of size `512 * nodeCount`, starting immediately after coordinates [S1, unofficial]. Each node contains 512 bytes (8x8x8 tiles of 8-bit data) [S1, unofficial].
4. **Cloud Data:** `Uint8Array` of size `width * height * depth`, allocated in CPU memory to hold the dense volume [S1, unofficial].

**Parameters:**
* Texture Format: `gl.R8` / `gl.RED` [S1, unofficial].
* Texture Type: `gl.UNSIGNED_BYTE` [S1, unofficial].
* Texture Unit: `gl.TEXTURE0` [S1, unofficial].

**Steps:**
1. **Cache Check:** Check if a texture for this specific VDB file already exists in the `dataRepository` [S1, unofficial].
2. **Texture Initialization:** Create a new 3D texture object [S1, unofficial]. Bind it to `gl.TEXTURE0` [S1, unofficial]. Initialize it as a minimal `1x1x1` texture with format `gl.RED` and type `gl.UNSIGNED_BYTE` to satisfy WebGL state requirements before upload [S1, unofficial].
3. **File Parsing:** Read `resolution` array: `[getUint16(0), getUint16(2), getUint16(4)]` [S1, unofficial]. Read `nodeCount`: `getUint16(6)` [S1, unofficial]. Calculate `dimensions`: `[resolution[0]/8, resolution[1]/8, resolution[2]/8]` [S1, unofficial]. Allocate `cloudData` as a `Uint8Array` of size `resolution[0] * resolution[1] * resolution[2]` [S1, unofficial].
4. **Data Extraction:** Parse `coordinates` from offset 8 as a `Uint16Array` [S1, unofficial]. Parse `nodeData` from offset `8 + coordinates.byteLength` as a `Uint8Array` [S1, unofficial].
5. **Tile Placement:** Iterate `i` from `0` to `nodeCount - 1` [S1, unofficial]. Extract tile coordinates: `coords = coordinates.subarray(i*3, i*3+3)` [S1, unofficial]. Extract tile data: `tile = nodeData.subarray(i*512, i*512+512)` [S1, unofficial]. Call `setTile(cloudData, dimensions, coords, tile)` to place the 8x8x8 tile into the correct position in `cloudData` [S1, unofficial].
6. **GPU Upload:** Upload `cloudData` to the bound 3D texture using `gl.texImage3D` with dimensions `resolution`, format `gl.RED`, type `gl.UNSIGNED_BYTE`, and data `cloudData` [S1, unofficial].

**Pseudocode:**
```python
import struct

def load_vdb_to_texture(file_buffer, gl, data_repository):
    # 1. Cache Check
    texture_key = id(file_buffer)
    if texture_key in data_repository:
        return data_repository[texture_key]

    # 2. Texture Initialization
    texture = gl.createTexture()
    gl.bindTexture(gl.TEXTURE_3D, texture)
    gl.texImage3D(gl.TEXTURE_3D, 0, gl.RED, 1, 1, 1, 0, gl.RED, gl.UNSIGNED_BYTE, None)

    # 3. File Parsing
    width = struct.unpack_from('<H', file_buffer, 0)[0]
    height = struct.unpack_from('<H', file_buffer, 2)[0]
    depth = struct.unpack_from('<H', file_buffer, 4)[0]
    node_count = struct.unpack_from('<H', file_buffer, 6)[0]

    dimensions = [width // 8, height // 8, depth // 8]
    cloud_data = bytearray(width * height * depth)

    # 4. Data Extraction
    coords_offset = 8
    coords_byte_length = node_count * 3 * 2
    coordinates = struct.unpack_from('<' + 'H' * (node_count * 3), file_buffer, coords_offset)
    data_offset = coords_offset + coords_byte_length
    node_data = struct.unpack_from('<' + 'B' * (node_count * 512), file_buffer, data_offset)

    # 5. Tile Placement
    for i in range(node_count):
        x = coordinates[i * 3]
        y = coordinates[i * 3 + 1]
        z = coordinates[i * 3 + 2]
        # Row-major linear indexing: I = x + y * S_x + z * S_x * S_y
        base_index = x + y * dimensions[0] + z * dimensions[0] * dimensions[1]
        for k in range(512):
            cloud_data[base_index + k] = node_data[i * 512 + k]

    # 6. GPU Upload
    gl.texImage3D(gl.TEXTURE_3D, 0, gl.RED, width, height, depth, 0, gl.RED, gl.UNSIGNED_BYTE, cloud_data)
    data_repository[texture_key] = texture
    return texture
```

**Edge Cases and Pitfalls:**
* **Offset Calculation:** Coordinates and data offsets must be calculated precisely based on `coordinates.byteLength`. Mismatched offsets result in reading garbage data [S1, unofficial].
* **Resolution Alignment:** The method assumes resolution is a multiple of 8. If not, `dimensions` calculation may fail or produce incorrect tile counts [S1, unofficial].
* **Memory Usage:** The `cloudData` array is dense. For large volumes with high sparsity, this can exceed GPU memory limits [S1, unofficial].

## Subtopics

### VDB 16-bit Tile Loading
Loads a VDB file format consisting of 8^3 leaf tiles, parsing the binary header and tile data, and uploading it as a 3D texture [S1, unofficial]. It differs from the standard 8-bit loader by handling 16-bit data and compressing it to 8-bit for texture upload [S1, unofficial].

**Definition:** Parses a more complex VDB header (including format, sparse, block size, normalization, and offsets) and loads 16-bit tile data, compressing it to 8-bit for GPU storage [S1, unofficial].

**Steps:**
1. **Parse Header:** Extract resolution (rounded up to multiples of 8), dimensions (resolution/8), and nodeCount from the extended header [S1, unofficial].
2. **Extract Data:** Extract coordinates and nodeData arrays from the binary buffer. Coordinates are `int32[3] * nodeCount`. Node data is `uint16[512] * nodeCount` [S1, unofficial].
3. **Tile Placement:** For each node `i`, call `setTile(cloudData, dimensions, coordinates[i], nodeData[i*512])` [S1, unofficial].
4. **Compression:** Compress 16-bit data to 8-bit: if `cloudData[i] > 0`, `compressedData[i] = 255 * (cloudData[i] / 65535)` [S1, unofficial].
5. **Upload:** Upload `compressedData` to a 3D texture with format `R8` [S1, unofficial].

**Layout:**
* Offset 0-1: width (uint16, little endian) [S1, unofficial]
* Offset 2-3: height (uint16) [S1, unofficial]
* Offset 4-5: depth (uint16) [S1, unofficial]
* Offset 6-7: format (uint16) [S1, unofficial]
* Offset 8-9: sparse (uint16) [S1, unofficial]
* Offset 10-11: block size (uint16) [S1, unofficial]
* Offset 12-15: nodeCount (uint32) [S1, unofficial]
* Offset 16-19: normalization (float32) [S1, unofficial]
* Offset 20-31: offsets (int32[3]) [S1, unofficial]
* Offset 32+: coordinates (int32[3] * nodeCount) [S1, unofficial]
* Followed by nodeData (uint16[512] * nodeCount) [S1, unofficial].

### Redshift Volume Object
Used to load heterogeneous volumes (varying density such as clouds, smoke, fire, explosions) [S2]. It reads a VDB file or an animated VDB sequence and shows a bounding box or a point cloud preview in the viewport [S2].

## Operating characteristics
* **Time Complexity:** $O(N)$ where $N$ is the number of nodes, as each node is processed once [S1, unofficial]. Parsing and upload are linear in the size of the sparse data [S1, unofficial].
* **Memory Complexity:** $O(W \times H \times D)$ for the dense cloud data, where $W, H, D$ are the volume dimensions [S1, unofficial]. This is the primary limitation; memory usage is independent of sparsity [S1, unofficial].
* **Performance:** Upload time depends on the size of the dense volume. For large volumes, this can be a bottleneck [S1, unofficial].
* **Strengths:** Simple implementation; leverages GPU hardware filtering; fast sampling during rendering.
* **Limitations:** High memory consumption for large or sparse volumes; not suitable for very large datasets that exceed GPU memory [S1, unofficial].
* **When to Use:** Small to medium volumes that fit in GPU memory; scenes requiring fast, hardware-accelerated ray marching [S1, unofficial].
* **When Not to Use:** Very large volumes; highly sparse volumes where memory efficiency is critical [S1, unofficial].

## Background
This method represents a common approach in WebGL-based volume rendering where sparse data structures are converted to dense textures for compatibility with GPU texture sampling units [S1, unofficial].
