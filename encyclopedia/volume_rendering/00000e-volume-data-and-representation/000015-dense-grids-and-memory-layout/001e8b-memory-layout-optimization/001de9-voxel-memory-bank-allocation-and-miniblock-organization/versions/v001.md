# Voxel Memory Bank Allocation and Miniblock Organization

Also called: Miniblock Reordering for SDRAM, Voxel Memory Layout, Voxel Memory Organization (Miniblocks and Skewing)

## Overview
Voxel Memory Bank Allocation and Miniblock Organization is a hardware-level memory layout strategy designed to maximize memory bandwidth and eliminate bank conflicts in SDRAM-based volume rendering systems [S1, unofficial]. It solves the problem of inefficient memory access patterns during ray casting by organizing voxels into fixed-size **miniblocks** and applying a two-level skewing scheme across memory modules and internal SDRAM banks [S1, unofficial]. Unlike general-purpose texture mapping, which relies on cache hierarchies, this method ensures that any ray parallel to the coordinate axes can access a full beam of voxels in consecutive memory cycles without pipeline stalls [S1, unofficial]. It is distinct from [Volume Interleaving](2174-volume-interleaving.md) by using fixed 2x2x2 blocks rather than arbitrary interleaving, and from [Memory-Insensitive Rendering](2774-memory-insensitive-rendering.md) by relying on strict geometric alignment rather than algorithmic tolerance to latency [S1, unofficial].

## How it works
**Inputs:**
- Volume data in host memory with arbitrary dimensions.
- View direction (used for reordering logic).

**Outputs:**
- Voxel data arranged in Voxel Memory such that four adjacent miniblocks are in separate memory modules and separate SDRAM banks.
- Data streamed to rendering pipelines in slice order.

**Data Structures:**
1.  **Miniblock:** A 2x2x2 array of voxels. Stored linearly in a single memory module at consecutive memory addresses. Size: 8 voxels.
2.  **Voxel Memory:** A collection of memory modules. Each module contains SDRAM chips.
3.  **SDRAM Chip:** Contains 4 internal memory banks (for 64-megabit chips) [S1, unofficial].

**Layout and Allocation:**
1.  **Padding:** The volume dimensions in Voxel Memory must be padded to multiples of 32 voxels in each dimension. This is derived from the miniblock structure: $2 \times 4 \times 4 = 32$ [S1, unofficial]. Arbitrary host volumes are stored with these padded dimensions and automatically cropped to their original size during rendering [S1, unofficial].
2.  **Miniblock Distribution (Module Skewing):** Miniblocks are distributed across memory modules such that any group of four adjacent miniblocks in any cardinal direction (x, y, or z) is stored in four separate memory modules. This prevents access conflicts between modules [S1, unofficial].
3.  **Bank Skewing:** Within a memory module, miniblocks are skewed so that adjacent miniblocks never fall into the same internal memory bank of an SDRAM chip. A 4x4x4 cube of miniblocks is skewed across the four memory banks [S1, unofficial].

**Mapping Formulas:**
Let voxel coordinates be $(u, v, w)$.
1.  Calculate miniblock coordinates $(u_m, v_m, w_m)$:
    $$ u_m = \lfloor u / 2 \rfloor, \quad v_m = \lfloor v / 2 \rfloor, \quad w_m = \lfloor w / 2 \rfloor $$
    *(Note: Integer division)* [S1, unofficial]

2.  Determine Memory Module Index ($M$):
    $$ M = (u_m + v_m + w_m) \bmod 4 $$
    This ensures that adjacent miniblocks along any axis differ in module index by 1 (mod 4), distributing them across 4 modules [S1, unofficial].

3.  Determine Memory Bank Index ($B$) within the module:
    $$ B = ((\lfloor u_m / 4 \rfloor) + (\lfloor v_m / 4 \rfloor) + (\lfloor w_m / 4 \rfloor)) \bmod 4 $$
    This ensures that a 4x4x4 block of miniblocks maps to all 4 banks, allowing back-to-back access without bank conflicts [S1, unofficial].

**Data Flow and Processing Steps:**
1.  **Read:** The Voxel Memory interface reads two slices of voxels at a time. Data is read in bursts of miniblocks (8 voxels) to exploit SDRAM burst capabilities [S1, unofficial].
2.  **Reorder (Miniblock Level):** Inside each miniblock, voxels are read in a fixed sequential order. However, the order is rearranged based on the current view direction. This logic ensures that the voxels correspond to the canonical positions assumed for tri-linear interpolation (e.g., ensuring the "left-most" voxel in the beam is processed first) [S1, unofficial].
3.  **De-skew (Global Level):** The four miniblocks output by the Voxel Memory controllers are de-skewed by a global de-skewing network. This reverses the module/bank skewing so that the left-most voxel along the x-axis flows down the leftmost rendering pipeline, and adjacent voxels in x flow down neighboring pipelines [S1, unofficial].
4.  **Buffer:** The de-skewed miniblocks are written into the voxel slice buffers of the four rendering pipelines [S1, unofficial].
5.  **Gradient Computation:** The slice buffers store three slices worth of data. This allows the computation of z-gradients using central differences [S1, unofficial].

**Pseudocode:**
```python
def allocate_voxel_memory(volume_dims):
    """
    Pads volume dimensions to multiples of 32 and calculates layout metadata.
    """
    # Pad dimensions to multiples of 32
    padded_u = ((volume_dims.u + 31) // 32) * 32
    padded_v = ((volume_dims.v + 31) // 32) * 32
    padded_w = ((volume_dims.w + 31) // 32) * 32
    
    return {
        'padded_dims': (padded_u, padded_v, padded_w),
        'miniblock_size': 8, # 2x2x2 voxels
        'sdram_banks': 4
    }

def get_miniblock_location(u, v, w):
    """
    Returns the memory module and bank index for a voxel at (u, v, w).
    Assumes 64-megabit SDRAMs with 4 banks.
    """
    # Integer division for miniblock coordinates
    um = u // 2
    vm = v // 2
    wm = w // 2
    
    # Module index: ensures adjacent miniblocks are in different modules
    module_idx = (um + vm + wm) % 4
    
    # Bank index: ensures adjacent miniblocks are in different banks
    # Uses 4x4x4 grouping of miniblocks
    bank_idx = ((um // 4) + (vm // 4) + (wm // 4)) % 4
    
    return module_idx, bank_idx

def reorder_miniblock_for_view(miniblock_voxels, view_direction):
    """
    Rearranges the 8 voxels within a miniblock to match canonical
    interpolation order for the given view direction.
    """
    # Logic depends on specific view direction (e.g., x-aligned, y-aligned)
    # For x-aligned view, ensure voxel with smallest x is first
    # This is handled by hardware logic in the memory interface
    return sorted(miniblock_voxels, key=lambda v: v.x) # Simplified representation

def process_slice_buffer(slice_buffer, view_direction):
    """
    Reads from slice buffer to compute interpolated samples and gradients.
    Requires 3 slices for central difference z-gradients.
    """
    if len(slice_buffer) < 3:
        raise ValueError("Need 3 slices for z-gradient computation")
    
    # De-skewing has already occurred, so voxels are in pipeline order
    # Compute gradients using central differences on the z-axis
    z_gradient = compute_central_difference(slice_buffer)
    
    # Compute tri-linear interpolation using reordered miniblock data
    sample = tri_linear_interpolate(slice_buffer, view_direction)
    
    return sample, z_gradient
```

**Edge Cases and Pitfalls:**
-   **Dimension Alignment:** If volume dimensions are not multiples of 32, the hardware must handle the cropping. Failure to pad correctly may lead to miniblock misalignment and bank conflicts [S1, unofficial].
-   **Supervolumes:** For volumes exceeding 256 voxels per edge, software must partition the volume into blocks (supervolumes). Adjacent blocks must duplicate 3 voxels in each dimension to maintain correct interpolation and gradients at boundaries [S1, unofficial].
-   **View Direction Dependency:** The reordering logic is specific to the view direction. Changing the view direction requires updating the reordering logic in the memory interface [S1, unofficial].

## Subtopics

### [Skewed Memory Organization for Conflict-Free Ray Access](2351-skewed-memory-organization-for-conflict-free-ray-access.md)
A specific application of miniblock skewing for Cubic Frame Buffers (CFBs) that maps $n^3$ voxels into $n$ memory banks to ensure conflict-free access for rays parallel to desired directions. Choose this when hardware supports CFB architecture and requires conflict-free access for arbitrary ray angles within a set of canonical directions.

## Operating characteristics
-   **Time Complexity:** Memory access is $O(1)$ per miniblock with no bank conflicts for axis-aligned rays. The overhead is the fixed cost of reordering and de-skewing logic.
-   **Memory Complexity:** Requires padding volume dimensions to multiples of 32 voxels. For a volume of size $N^3$, the memory usage is slightly higher than $N^3$ due to padding.
-   **Performance:** Achieves burst rates of up to 532 million voxels per second with four 133 MHz memory interfaces, provided voxels are organized in miniblocks [S1, unofficial].
-   **Strengths:** Eliminates memory bank conflicts for axis-aligned rays; maximizes SDRAM burst efficiency; simple hardware logic for reordering.
-   **Limitations:** Restricted to axis-aligned or near-axis-aligned rays for optimal performance; requires fixed miniblock size (2x2x2); not suitable for arbitrary non-grid-aligned sampling without significant overhead.
-   **When to Use:** High-performance, real-time volume rendering on hardware with SDRAM-based Voxel Memory (e.g., VolumePro).
-   **When Not to Use:** When rendering non-axis-aligned rays with high angular diversity; when memory bandwidth is not the bottleneck; when using modern GPU architectures with unified memory and cache hierarchies that handle coalesced access differently.

## Background
This method was developed for the VolumePro real-time ray-casting system by MERL (Mitsubishi Electric Research Laboratory) [S1, unofficial]. It was described in the technical report "The VolumePro Real-Time Ray-Casting System" (TR99-19) [S1, unofficial]. The system was designed to overcome the memory bandwidth limitations of early 2000s hardware by exploiting the regularity of volumetric data and the burst capabilities of SDRAM. The approach is specific to the VolumePro hardware architecture, which includes dedicated ASICs (vg500) for memory management and rendering pipelines [S1, unofficial].
