# Parallel Memory Access with Cubic Addressing

Also called: Cubic memory organization, Memory Access Buffering (FIFO)

## Overview
Parallel Memory Access with Cubic Addressing is a hardware memory layout and access strategy that accelerates trilinear interpolation in volume rendering by retrieving the eight required sample voxels in a single memory cycle [S2]. It differs from standard interleaved memory layouts by grouping voxels into contiguous $s^3$ sub-cubes distributed across eight parallel memory modules, which increases memory usage by approximately eightfold but enables single-cycle retrieval of interpolation neighborhoods [S2].

## How it works
**Inputs and Outputs:**
*   **Input:** Ray parameters (origin, direction), volume dataset, and sub-cube size $s$ (typically $s=2$ for the basic cubic addressing unit) [S1].
*   **Output:** Eight voxel values for trilinear interpolation, delivered to the rendering pipeline [S2].

**Data Structures:**
*   **Memory Banks:** Eight parallel memory modules ($M_0$ to $M_7$) or logical banks within SDRAMs, where each sample point requires one voxel from each module [S1].
*   **FIFO Buffers:** A First-In-First-Out buffer is associated with each memory module to store addresses and voxel values, decoupling the ray casting pipeline from memory access latency [S1].
*   **Address Modification Unit:** An incrementer used to adjust base addresses when crossing sub-cube boundaries [S1].

**Layout Details:**
Voxels are arranged in memory as continuous cubes rather than interleaved [S2]. This means that for a given $2 \times 2 \times 2$ neighborhood, each of the eight voxels resides in a different memory bank [S1]. This layout introduces duplications of voxels in memory, increasing memory requirements to approximately eight times the dataset size [S2].

**Algorithm Steps:**
1.  **Coordinate Normalization:** If the sample point coordinates $(V_z, V_y, V_x)$ are divisible by two, the coordinates used to calculate the address for each memory are the original coordinates divided by two, implemented as a bitwise shift right by one [S1]. Each memory stores only every second voxel along each axis [S1].
2.  **Address Calculation:** Calculate the eight memory addresses for the trilinear neighborhood [S1]. The address is $A = s^3 AC + A_v$, where $AC$ is the sub-cube address and $A_v$ is the voxel address within the sub-cube [S1]. The voxel address components depend on the modulus of the coordinates: $A_v = (V_z \mod s) + s(V_y \mod s) + s^2(V_x \mod s)$ [S1]. For a new sample $S_2$ relative to $S_1$, the addresses for $M_0, M_1, M_2, M_3$ change, while the addresses for $M_4, M_5, M_6, M_7$ remain the same [S1].
3.  **Boundary Handling:** When the sample point lies between two neighborhoods, the base address of a neighborhood is modified using an address modification unit (incrementer) before each memory bank [S1].
4.  **Buffering and Fetching:** Addresses are pushed into the FIFO buffers of the respective memory modules [S1]. Voxel values are fetched from the SDRAMs [S1]. The pipeline stalls only when the voxel FIFO of a particular memory is empty at the same time that this memory requires a cache refill [S1].
5.  **Interpolation:** The eight fetched voxel values are used for trilinear interpolation to compute the color and opacity at the sample point [S2].

**Pseudocode:**
```python
def parallel_memory_access(Vz, Vy, Vx, fifo_buffers, subcube_size=2, volume_dims=(100, 100, 100)):
    # Step 1: Coordinate normalization
    # Each memory stores only every second voxel, so divide by subcube_size (shift) [S1]
    base_z = Vz >> 1
    base_y = Vy >> 1
    base_x = Vx >> 1

    # Step 2: Calculate addresses for the 8 memory banks
    addresses = []
    for i in range(8):
        # Decode bank index i into corner offsets (0 or 1)
        x_off = (i >> 0) & 1
        y_off = (i >> 1) & 1
        z_off = (i >> 2) & 1

        # Voxel address within sub-cube: Av = (Vz mod s) + s*(Vy mod s) + s^2*(Vx mod s) [S1]
        av = (z_off * subcube_size * subcube_size) + \
             (y_off * subcube_size) + \
             (x_off)

        # Sub-cube address AC (linearized from shifted coordinates) [G]
        nx, ny, nz = volume_dims
        ac = (base_z * ny * nx) + (base_y * nx) + base_x

        # Final address: A = s^3 * AC + Av [S1]
        addresses.append((subcube_size ** 3) * ac + av)

    # Step 3: Boundary handling
    # When crossing neighborhoods, the base address is modified using an
    # address modification unit (incrementer) before each memory bank [S1].

    # Step 4: Buffering and Fetching
    voxels = []
    for i in range(8):
        fifo_buffers[i].append(addresses[i])
        # Pipeline stalls only if FIFO is empty AND cache refill is needed [S1]
        if len(fifo_buffers[i]) == 0:
            # [G] Standard cache refill logic would be invoked here
            pass
        voxels.append(fifo_buffers[i].pop(0))

    return voxels
```

**Edge Cases and Pitfalls:**
*   **Sub-cube Boundary Crossing:** When a ray crosses the y-z plane of the next $s^3$ sub-cube, memories $M_0, M_2, M_4, M_6$ change coordinates and refresh their cache, while $M_1, M_3, M_5, M_7$ remain in the current sub-cube. If cache refreshes happen in separate pipeline cycles, the pipeline stalls twice [S1].
*   **Cache Misses:** Without buffering, frame time depends on the sum of the slowest SDRAM access at every read of a trilinear neighborhood. With buffering, it depends only on the performance of the slowest SDRAM [S1].
*   **Memory Duplication:** The layout requires approximately eight times the dataset size in memory due to voxel duplication [S2].
*   **Accumulative Rendering:** Not employed for accumulative rendering mode because that mode only renders two slices and does not require the specific spatial locality of cubic memory for trilinear interpolation of a full volume [S2].

## Subtopics

### Peano Addressing
A data addressing scheme that produces a high probability that spatially close points are also close in a linear address space, resulting in contiguously addressed data points for macros [S3, unofficial]. Peano addressing has good implications for cache coherence during ray casting and simplifies addressing during macro redistribution compared to non-contiguous addressing [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** Enables single-cycle retrieval of the eight voxels required for trilinear interpolation using a 64-bit data bus [S2].
*   **Memory Complexity:** Memory requirement is approximately eight times the dataset size due to voxel duplication [S2].
*   **Performance:** Buffered memory access makes frame time dependent on the performance of the slowest SDRAM, whereas unbuffered memory access makes frame time dependent on the sum of the slowest SDRAM access at every read of a trilinear neighborhood [S1].
*   **Strengths:** Fast retrieval of trilinear interpolation neighborhoods; reduced pipeline stalls due to FIFO buffering [S1, S2].
*   **Limitations:** High memory usage (8x dataset size); pipeline stalls can still occur if cache refills are not aligned with FIFO availability [S1].
*   **When to use:** Suitable for hardware implementations where parallel memory banks and FIFO buffers can be implemented, and where trilinear interpolation is the dominant operation [S2].
*   **When not to use:** Not employed for accumulative rendering mode because that mode only renders two slices and does not require the specific spatial locality of cubic memory for trilinear interpolation of a full volume [S2].

## Background
The method was introduced in the context of low-cost, PCI-based interactive ray casting systems [S1]. It builds on the Cubic Addressing Scheme to optimize memory access for trilinear interpolation [S2]. The approach was implemented on hardware such as the Celoxica RC340 FPGA Development board and deployed for clinical experiments in volume rendering of LSCEM images [S2]. The use of FIFO buffers to minimize pipeline stalling was a key innovation to handle the latency of SDRAM accesses [S1].
