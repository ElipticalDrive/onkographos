# Block Skewed Memory

Also called: EM-Cube memory organization, Hierarchical Blocks

## Overview
Block Skewed Memory is a memory organization scheme for volume rendering that stores data in cubic blocks of $b \times b \times b$ voxels [S1, unofficial]. It optimizes DRAM page-mode bandwidth while maintaining conflict-free ray access [S1, unofficial]. It differs from its parent, [Skewed Memory Organization for Conflict-Free Ray Access](2351-skewed-memory-organization-for-conflict-free-ray-access.md), by applying skew at the block granularity rather than the voxel granularity [S1, unofficial]. This allows all voxels of a block to be stored linearly within a single DRAM page [S1, unofficial]. The approach reduces inter-chip communication overhead compared to voxel-level skewing, at the cost of requiring on-chip reordering buffers [S1, unofficial].

## How it works
**Inputs:** Volume data of size $N \times N \times N$ voxels; block dimension $b$; number of memory chips $C$ [S1, unofficial].
**Outputs:** Memory layout mapping voxel coordinates $(x, y, z)$ to memory addresses and chip IDs [S1, unofficial].

**Data Structures:**
1.  **Block:** A cubic sub-volume of $b^3$ voxels [S1, unofficial].
2.  **Memory Layout:**
    *   The volume is partitioned into blocks of size $b \times b \times b$ [S1, unofficial].
    *   Blocks are distributed across $C$ memory chips [S1, unofficial].
    *   Within a chip, blocks are skewed to ensure that any ray accesses at most one voxel per chip per cycle [S1, unofficial].
    *   Inside a chip, all $b^3$ voxels of a block are stored linearly in contiguous memory addresses (a single DRAM page) [S1, unofficial].
3.  **Reordering Buffer:** An on-chip buffer of size $b^3$ voxels, used by each rendering chip to reorder voxel access within a block according to the current view direction [S1, unofficial].

**Parameters:**
*   $b$: Block dimension [S1, unofficial].
    *   **PageBlock:** $b$ is maximized to fit $b^3$ voxels into a single DRAM page [S1, unofficial]. For 512-byte pages: $b=8$ for 8-bit voxels, $b=4$ for 16/32-bit voxels [S1, unofficial].
    *   **MiniBlock:** $b$ is minimized to overlap row access overhead [S1, unofficial]. $b=2$ is typical for 16-bit voxels on 125MHz SDRAM [S1, unofficial].
    *   **Constraint:** $b \leq N/C$ to avoid conflicts for any view direction [S1, unofficial].
*   $C$: Number of memory chips/modules [S1, unofficial].

**Algorithm Steps:**
1.  **Partition:** Divide the $N \times N \times N$ volume into non-overlapping blocks of size $b \times b \times b$ [S1, unofficial].
2.  **Assign Chips:** Assign each block to a memory chip such that the blocks are skewed [S1, unofficial]. The skew ensures that for any ray direction, the sequence of blocks accessed by the ray maps to distinct chips, preventing bank conflicts [S1, unofficial].
3.  **Linearize Blocks:** Within each chip, store the $b^3$ voxels of a block in linear, contiguous memory addresses [S1, unofficial]. This allows the DRAM to operate in fast page mode, transferring the entire block (or miniblock) in a single burst [S1, unofficial].
4.  **Fetch and Reorder:** When a ray enters a block, the rendering chip fetches the block (or miniblock) from DRAM into the on-chip reordering buffer [S1, unofficial]. The chip reorders the voxels in the buffer to match the ray's traversal order for the current view direction [S1, unofficial]. The chip processes the voxels using the Cube-4 algorithm logic, but operating on "partial block-beams" instead of partial beams [S1, unofficial].
5.  **Inter-chip Communication:** Voxels inside the block are processed on-chip [S1, unofficial]. Only voxels near the faces of the block require communication with neighboring chips [S1, unofficial]. The area of a block face is $b^2$ [S1, unofficial]. The number of voxels per block is $b^3$ [S1, unofficial]. Inter-chip communication per voxel scales as $1/b$ [S1, unofficial].

**Pseudocode:**
```python
def compute_block_skewed_layout(N, b, C, voxel_size_bytes):
    """
    Computes the chip ID and linear offset for a voxel (x, y, z).
    Assumes N is divisible by b for simplicity.
    """
    blocks_per_dim = N // b
    def get_chip_and_offset(x, y, z):
        # Determine block coordinates
        bx, by, bz = x // b, y // b, z // b
        # Determine chip ID via block-level skew
        chip_id = (bx + by + bz) % C
        # Local coordinates within the block
        lx, ly, lz = x % b, y % b, z % b
        # Linear index within the b^3 block (row-major)
        block_offset = (lz * b * b) + (ly * b) + lx
        # Global block index (row-major over all blocks)
        global_block_idx = (bz * blocks_per_dim * blocks_per_dim) + \
                           (by * blocks_per_dim) + bx
        # Chip memory offset (round-robin block assignment)
        chip_block_offset = global_block_idx // C
        chip_base_offset = chip_block_offset * (b * b * b)
        final_offset = chip_base_offset + block_offset
        return chip_id, final_offset
    return get_chip_and_offset

def process_block(chip_id, block_voxels, view_direction):
    """
    Processes a block of voxels on a rendering chip.
    block_voxels is a list of b^3 voxels in linear DRAM order.
    """
    # Reorder voxels to match ray traversal order for the current view direction
    # The exact reordering permutation depends on the view direction and is not specified in the sources [G]
    reordered_voxels = [None] * len(block_voxels)
    for i in range(len(block_voxels)):
        reordered_voxels[i] = block_voxels[i]
    # Process voxels using the Cube-4 algorithm logic on partial block-beams
    # The exact compositing/trilinear steps are not specified in the sources [G]
    results = []
    for voxel in reordered_voxels:
        results.append(voxel)
    return results
```

**Edge Cases and Pitfalls:**
*   **Block Size Too Large (PageBlock):** Requires a large on-chip buffer ($b^3$ voxels) [S1, unofficial]. For 32-bit voxels, $b=4$ requires a 256-voxel buffer [S1, unofficial].
*   **Block Size Too Small (MiniBlock):** Increases inter-chip communication overhead [S1, unofficial]. For $b=2$, the face area is 4, but the volume is 8, leading to a high ratio of boundary voxels to internal voxels [S1, unofficial].
*   **Voxel Size Dependency:** PageBlock size $b$ is directly dependent on voxel size [S1, unofficial]. Changing voxel precision (e.g., from 8-bit to 32-bit) may require changing $b$ to fit the DRAM page [S1, unofficial].
*   **Boundary Conditions:** If $N$ is not divisible by $b$, boundary blocks must be handled, potentially requiring padding or special logic [G].

## Subtopics

### PageBlock
Maximizes $b$ to fit a DRAM page [S1, unofficial]. Best for high bandwidth when voxel size is fixed and small [S1, unofficial]. Requires large on-chip buffers [S1, unofficial].

### MiniBlock
Minimizes $b$ (e.g., $b=2$) to overlap row access latency [S1, unofficial]. Best for reducing on-chip buffer size, but increases inter-chip communication [S1, unofficial].

### Hierarchical Blocks
Combines PageBlock and MiniBlock by tiling large blocks with small miniblocks [S1, unofficial]. Miniblocks are fetched on demand, reducing buffer requirements while maintaining page-mode efficiency [S1, unofficial]. Blocks are skewed, but miniblocks within a block are not [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Fetching a block is $O(1)$ in terms of DRAM accesses (one page load), but the constant factor depends on $b^3$ [S1, unofficial]. Reordering is $O(b^3)$ [S1, unofficial].
*   **Memory Complexity:** On-chip buffer size is $O(b^3)$ per rendering chip [S1, unofficial].
*   **Inter-chip Communication:** Scales as $1/b$ per voxel [S1, unofficial]. A design with $b=4$ requires up to 4 times less inter-chip communication bandwidth than Cube-4 ($b=1$) [S1, unofficial].
*   **Strengths:** High DRAM bandwidth utilization due to page mode [S1, unofficial]. Reduced inter-chip communication compared to voxel-level skewing [S1, unofficial]. View-independent rendering support [S1, unofficial].
*   **Limitations:** Requires on-chip buffering proportional to $b^3$ [S1, unofficial]. Block size is sensitive to voxel size (for PageBlock) [S1, unofficial]. Increased complexity in memory layout and reordering logic [S1, unofficial].
*   **When to Use:** When DRAM bandwidth is the bottleneck and on-chip buffer resources are available [S1, unofficial]. Suitable for fixed-voxel-size applications [S1, unofficial].
*   **When Not to Use:** When on-chip buffer space is extremely limited (consider MiniBlock or Hierarchical) or when voxel size varies frequently [S1, unofficial].

## Background
Block Skewed Memory was introduced in the EM-Cube architecture paper by Harvard's Visual Computing Group in 1997 [S1, unofficial]. It was designed to leverage the high bandwidth of SDRAM in fast page mode for real-time volume rendering [S1, unofficial]. The method addresses the limitations of voxel-level skewed memory (Cube-4) by grouping voxels into blocks, thereby reducing the overhead of inter-chip communication and improving memory access efficiency [S1, unofficial]. The concept of hierarchical blocking was also discussed in related work [12], but EM-Cube distinguished itself by keeping all voxels of a block in the same memory module and using miniblocks for pipelined burst access [S1, unofficial].
