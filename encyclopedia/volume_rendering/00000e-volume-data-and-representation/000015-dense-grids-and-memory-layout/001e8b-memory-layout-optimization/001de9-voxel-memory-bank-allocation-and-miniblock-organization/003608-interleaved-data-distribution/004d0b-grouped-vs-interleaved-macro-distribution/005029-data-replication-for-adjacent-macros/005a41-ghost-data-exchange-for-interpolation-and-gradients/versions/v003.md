# Ghost Data Exchange for Interpolation and Gradients

Also called: Boundary Voxel Replication for Distributed Memory, Ghost Cell Stitching for Distributed Memory, Ghost Data (Halo) Exchange

## Overview
Ghost Data Exchange maintains data consistency across node boundaries in distributed-memory volume rendering [G]. It solves the problem of accessing neighboring voxels required for local resampling (trilinear interpolation) and gradient estimation (central differences) without incurring frequent inter-node fetches during the raycasting phase [S2]. It is chosen when the rendering algorithm requires spatial derivatives or multi-voxel sampling that extends beyond the local node's data partition [G].

## How it works
**Inputs and Outputs:**
- Input: Local volume data block (macro) of size $D_x \times D_y \times D_z$, neighbor topology information [G].
- Output: Extended local volume data block including ghost layers, ready for raycasting [G].

**Data Structures:**
The local data structure is extended by adding a halo region around the boundary of the local macro [G].
- **Local Data:** $V_{local}$ of size $D_x \times D_y \times D_z$ [G].
- **Ghost Layers:** Two layers of voxels are added to each face of the local block [S1, S2].
- **Total Extended Size:** $(D_x + 4) \times (D_y + 4) \times (D_z + 4)$ assuming 1-voxel wide ghost layers on all sides [G].

**Numbered Steps:**
1. **Identify Neighbors:** Determine which adjacent macros share a boundary with the local macro based on the grid decomposition topology (e.g., 3D torus or grid) [G].
2. **Prepare Send Buffers:** For each neighbor, identify the voxels in the local macro that are adjacent to the shared boundary to serve as source data [G].
3. **Prepare Receive Buffers:** Allocate space in the local ghost layers for data coming from each neighbor [G].
4. **Execute Exchange:** Perform communication to swap boundary voxels between neighbors [G].
5. **Fill Ghost Layers:** The received data is placed into the appropriate ghost layer positions [G]. Layer 1 (Inner Ghost) is adjacent to the local data boundary [S1, S2]. Layer 2 (Outer Ghost) is adjacent to Layer 1 [S1, S2].

**Formulas:**
- **Trilinear Interpolation:** Requires access to 8 neighboring voxels [G]. If a ray samples a voxel at the boundary of the local macro, it accesses voxels from the ghost layer [S2].
  $$ V_{sample} = \sum_{i=0}^{1} \sum_{j=0}^{1} \sum_{k=0}^{1} w_{ijk} V_{x+i, y+j, z+k} $$
  where $V_{x+i, y+j, z+k}$ can reside in the local data or the ghost layers [G].
- **Central Difference Gradient:** Requires access to voxels at $x \pm 1, y \pm 1, z \pm 1$ [S2].
  $$ \frac{\partial V}{\partial x} \approx \frac{V_{x+1, y, z} - V_{x-1, y, z}}{2\Delta x} $$
  For a voxel at the local boundary, $V_{x+1, y, z}$ or $V_{x-1, y, z}$ may reside in the ghost layers [G].

**Parameters:**
- **Number of Ghost Layers:** 2 [S1, S2].
  - Layer 1: Supports trilinear interpolation of sampled values [S1, S2].
  - Layer 2: Supports computing the gradient field using central differences [S1, S2].
  - Note: Gradients are not precomputed for the dataset in the reference implementation [S2].

**Edge Cases and Pitfalls:**
- **Boundary Conditions:** The outermost ghost layers (Layer 2) do not have neighbors to exchange with [G]. They must be filled with a default value (e.g., zero, or replicated boundary values) [G].
- **Precision:** Ensure that the data type used for ghost layers matches the local data type to avoid precision loss during exchange [G].
- **Deadlock:** Use non-blocking communication or careful ordering of send/receive operations to avoid deadlock in distributed systems [G].

**Pseudocode:**
```python
def exchange_ghost_data(local_macro, neighbors, ghost_layers=2):
    """
    Exchanges ghost data between local macro and its neighbors.
    
    Args:
        local_macro: 3D list/array of shape (Dx, Dy, Dz)
        neighbors: List of tuples (neighbor_id, direction)
                   direction is a tuple (dx, dy, dz) indicating the relative position
        ghost_layers: Number of ghost layers (default 2)
        
    Returns:
        extended_macro: 3D list/array with ghost layers added
    """
    Dx, Dy, Dz = local_macro.shape
    
    # Initialize extended array with zeros (2 layers on each side)
    extended_macro = [[[0.0] * (Dz + 4) for _ in range(Dy + 4)] for _ in range(Dx + 4)]
    
    # Copy local data to the center (indices 2 to Dx+1, etc.)
    for i in range(Dx):
        for j in range(Dy):
            for k in range(Dz):
                extended_macro[i + 2][j + 2][k + 2] = local_macro[i][j][k]
                
    # Exchange data with neighbors
    for neighbor_id, direction in neighbors:
        dx, dy, dz = direction
        if dx == 1:  # Neighbor in +x direction
            # Send local +x boundary (Layer 1 at index Dx+1)
            send_buf = [extended_macro[Dx + 1][j][k] for j in range(Dy + 4) for k in range(Dz + 4)]
            # MPI communication assumed; sources do not specify exact calls [G]
            # receive_buf = mpi_comm.recv(source=neighbor_id, tag=0)
            # Place received data into local -x Layer 1 (index 1)
            for j in range(Dy + 4):
                for k in range(Dz + 4):
                    extended_macro[1][j][k] = receive_buf[j * (Dz + 4) + k]
        elif dx == -1:  # Neighbor in -x direction
            # Send local -x boundary (Layer 1 at index 1)
            send_buf = [extended_macro[1][j][k] for j in range(Dy + 4) for k in range(Dz + 4)]
            # receive_buf = mpi_comm.recv(source=neighbor_id, tag=0)
            # Place received data into local +x Layer 1 (index Dx+2)
            for j in range(Dy + 4):
                for k in range(Dz + 4):
                    extended_macro[Dx + 2][j][k] = receive_buf[j * (Dz + 4) + k]
        # Similar logic applies for dy and dz directions
    # Layer 2 (indices 0 and Dx+3) is typically filled by copying Layer 1 or via a second exchange [G]
    return extended_macro
```

## Subtopics

### [Data Replication for Adjacent Macros](14149-data-replication-for-adjacent-macros.md)
A data distribution strategy for adjacent macro groups where nodes replicate boundary voxels from neighbors to allow local resampling without inter-node fetches at data boundaries.

## Operating characteristics
- **Time Complexity:** The time complexity of the ghost data exchange is proportional to the surface area of the local macro, i.e., $O(D_y D_z + D_x D_z + D_x D_y)$ per neighbor [G].
- **Memory Complexity:** The memory overhead is proportional to the surface area of the local macro times the number of ghost layers [G]. For 2 layers, the overhead is approximately $2 \times (D_y D_z + D_x D_z + D_x D_y)$ voxels [G].
- **Measured Performance:** The MPI-hybrid approach requires less exchange and storage of ghost data by roughly 40% across all concurrencies compared to MPI-only, because it uses fewer, larger blocks in its decomposition [S2].
- **Strengths:** Reduces the frequency of inter-node communication during raycasting by providing necessary neighbor data locally [G].
- **Limitations:** Increases memory usage per node [G]. The communication overhead can become significant if the local blocks are too small (high surface-to-volume ratio) [G].
- **When to Use:** When the rendering algorithm requires trilinear interpolation or central difference gradients, and the data is distributed across multiple nodes [G].
- **When Not to Use:** When the rendering algorithm uses nearest-neighbor interpolation and does not require gradients, or when the data fits entirely within a single node's memory [G].

## Background
The concept of ghost data exchange in volume rendering was discussed in the context of MPI-hybrid parallelism for large, multi-core systems [S1, S2]. The specific requirement of two layers of ghost data for trilinear interpolation and central difference gradients was detailed in research by M. Howison, E.W. Bethel, & H. Childs [S1, S2]. The comparison between MPI-hybrid and MPI-only approaches highlighted the efficiency gains from using fewer, larger blocks [S2].
