# Voxel Buffer Memory Layout and Loop Optimization

Also called: 3D-to-1D Voxel Indexing, Array-Order Layout, Cache-Optimized Voxel Access, Dense Field Implementation, Index Computation Optimization, Z-Order Layout

## Overview
This method defines the memory organization of a dense 3D voxel grid as a contiguous 1D array and the corresponding loop structures required to access it efficiently on modern hardware [S1, unofficial][S2, unofficial]. It solves the problem of cache thrashing and memory bandwidth bottlenecks that occur when 3D coordinates are mapped to linear memory without regard for spatial locality or CPU/GPU cache line alignment [S2, unofficial][S3, unofficial]. It focuses on contiguous 1D array mapping and loop ordering for cache efficiency, whereas sibling methods address hardware-specific bank conflicts or attribute interleaving [S2, unofficial][S3, unofficial]. The primary trade-off is between simple row-major indexing (fast index calculation, poor spatial locality for non-sequential access) and Z-order indexing (excellent spatial locality, high index calculation cost) [S3, unofficial].

## How it works
### Inputs and Outputs
- **Input**: 3D voxel grid dimensions $(x_{size}, y_{size}, z_{size})$ and a coordinate triplet $(i, j, k)$ representing the voxel to access [S2, unofficial].
- **Output**: A 1D linear index $I$ into a contiguous memory buffer, and the associated voxel data [S1, unofficial].

### Data Structures
The voxel buffer is a contiguous 1D array [S2, unofficial]. In C++, this is typically implemented as `std::vector<T>` or a raw pointer allocated with `malloc`/`new` [S2, unofficial].
- **Layout**: Row-major order. The x-axis is the innermost dimension (varies fastest), followed by y, then z [S2, unofficial][S3, unofficial].
- **Total Size**: $x_{size} \times y_{size} \times z_{size}$ elements of type $T$ [S1, unofficial].
- **Lookup Tables (Optional)**: For optimized index computation, lookup tables are stored in GPU constant memory [S3, unofficial].

### Indexing Formulas
Two primary layout schemes are defined in the sources:

1.  **Array-Order (Row-Major)**:
    The index $I$ for coordinate $(i, j, k)$ is:
    $$ I = i + j \cdot x_{size} + k \cdot x_{size} \cdot y_{size} $$
    where $i \in [0, x_{size})$, $j \in [0, y_{size})$, $k \in [0, z_{size})$ [S2, unofficial][S3, unofficial].
    For cubic grids where $x_{size} = y_{size} = z_{size} = size$:
    $$ idx(x, y, z) = x + size \times (y + size \times z) $$
    [S1, unofficial]

2.  **Z-Order (Morton Order)**:
    A method where points nearby in index space are nearby in physical memory [S3, unofficial]. The index is computed via bitwise interleaving of the coordinates using the formulation by Pascucci and Frank [S3, unofficial].

### Loop Optimization
To optimize cache performance, loops must be reordered so the x-axis is the innermost dimension, ensuring sequential memory access [S2, unofficial].

**Naive (Incorrect) Loop:**
```cpp
// x is outermost, z is innermost
for (int i = 0; i < xSize; ++i) {
  for (int j = 0; j < ySize; ++j) {
    for (int k = 0; k < zSize; ++k) {
      buffer.lvalue(i, j, k) = 0.0f;
    }
  }
}
```
This causes a memory stride of $x_{size} \cdot y_{size}$ between consecutive accesses in the inner loop, leading to a cache miss at every step [S2, unofficial].

**Optimized Loop:**
```cpp
// x is innermost
for (int k = 0; k < zSize; ++k) {
  for (int j = 0; j < ySize; ++j) {
    for (int i = 0; i < xSize; ++i) {
      buffer.lvalue(i, j, k) = 0.0f;
    }
  }
}
```
This ensures sequential memory access [S2, unofficial].

### Index Computation Optimization
Direct multiplication for array-order indexing requires three multiplications and two additions per access [S3, unofficial]. Z-order calculation on the fly requires $12n$ bitwise operations (where $n$ is bits per dimension) [S3, unofficial]. To optimize:
1.  **Array-Order**: Use two table lookups and three additions [S3, unofficial].
2.  **Z-Order**: Use three table lookups and two logical OR operations [S3, unofficial].
These lookup tables are stored in GPU constant memory for fast access [S3, unofficial].

### Pseudocode
The following Python-like pseudocode demonstrates the optimized iteration and index calculation using precomputed strides and lookup tables.

```python
def process_array_order(buffer, x_size, y_size, z_size):
    stride_y = x_size
    stride_z = x_size * y_size
    for k in range(z_size):
        offset_z = k * stride_z
        for j in range(y_size):
            offset_y = offset_z + j * stride_y
            for i in range(x_size):
                buffer[offset_y + i] = 0.0

def process_z_order(buffer, x_size, y_size, z_size, morton_tables):
    # morton_tables: dict with keys 'x', 'y', 'z' mapping index to precomputed Morton code
    for k in range(z_size):
        mk = morton_tables['z'][k]
        for j in range(y_size):
            mj = morton_tables['y'][j]
            for i in range(x_size):
                mi = morton_tables['x'][i]
                idx = mi | (mj << 1) | (mk << 2)
                buffer[idx] = 0.0
```

### Edge Cases and Pitfalls
- **Cache Thrashing**: Naive loops with the x-dimension outermost cause cache misses because the inner loop steps along the z-axis, resulting in a memory stride of $x_{size} \cdot y_{size}$ [S2, unofficial].
- **Index Calculation Cost**: Calculating Z-order index on the fly is computationally expensive ($12n$ bitwise operations) compared to lookup tables [S3, unofficial].
- **Bounds Checking**: Explicit loops require manual bounds checks [S2, unofficial]. Iterators or `std::fill` are preferred to avoid explicit bounds checks and multiplication overhead [S2, unofficial].
- **Non-Cubic Grids**: The formulas must account for different $x_{size}$ and $y_{size}$; assuming cubic grids ($size^3$) leads to incorrect indexing if dimensions differ [S2, unofficial][S3, unofficial].

### Shared Position Buffer with Per-Chunk Color
An optimization where vertex positions for all voxels in all chunks are stored in a single global structured buffer (`m_shared_chunk_position_buffer`), while colors are stored per-chunk [S4, unofficial]. This reduces memory bandwidth for positions if many chunks share similar geometry structures [S4, unofficial].
- **Steps**: Pre-calculate all vertex positions for all voxels in a chunk [S4, unofficial]. For each voxel `i`, get its 3D index, calculate its offset in world space (`index_3d * EDGE_LENGTH`), and add the 8 local vertex offsets to create 8 global positions [S4, unofficial]. Store these in `chunk_position_data` [S4, unofficial].
- **Layout**: 
  - Shared Position Buffer: `StructuredBuffer<DirectX::XMFLOAT3>` [S4, unofficial]. Size is `Chunk::NUMBER_OF_VOXELS * 8` per chunk [S4, unofficial]. Each voxel contributes 8 vertices [S4, unofficial].
  - Chunk Constant Buffer (`ChunkConstantBuffer`): Contains `translation_vector` (XMVECTOR4: chunk world offset), `position_buffer_index` (u32: SRV index of shared position buffer), `color_buffer_index` (u32: SRV index of this chunk's color buffer) [S4, unofficial].

## Operating characteristics
- **Time Complexity**: Index calculation is $O(1)$ for array-order with precomputed strides, or $O(1)$ with lookup tables for Z-order [S3, unofficial]. On-the-fly Z-order calculation is $O(n)$ where $n$ is bit width [S3, unofficial].
- **Memory Complexity**: $O(x_{size} \cdot y_{size} \cdot z_{size})$ for the dense buffer [S1, unofficial].
- **Performance**: Cache-optimized loops (x-innermost) significantly outperform naive loops by eliminating cache misses [S2, unofficial]. Lookup tables for index computation are significantly faster than bitwise operations or multiplications [S3, unofficial].
- **Strengths**: Simple implementation, high throughput for sequential access, leverages hardware cache lines effectively [S2, unofficial].
- **Limitations**: Array-order layout has poorer spatial locality for random access compared to Z-order [S3, unofficial]. High memory usage for resolutions exceeding $1000^3$ without sparsity [S2, unofficial].
- **When to Use**: Sequential access patterns (e.g., ray marching) benefit from cache-optimized loops [S2, unofficial]. Z-order is preferred when random access to nearby voxels is frequent, as lookup tables mitigate the high index computation cost [S3, unofficial].

## Background
The concept of mapping 3D grids to 1D arrays is fundamental to dense field implementations [S2, unofficial]. The specific optimization of loop ordering for cache performance is a standard technique in high-performance computing [S2, unofficial]. The Z-order (Morton) curve layout for volume rendering was explored in the context of parallel raycasting optimization, with formulations by Pascucci and Frank cited [S3, unofficial]. The shared position buffer optimization is a more recent technique in voxel engine implementations for reducing GPU memory bandwidth [S4, unofficial].
