# Voxel Memory Layout & Stride Calculation

Also called: EX Macro, IJK to Linear Index Mapping, NRRD Volume Data Layout & Indexing, Volume Array Stride Calculation, Voxel Indexing Macro

## Overview
This method defines the mapping between 3D voxel coordinates $(i, j, k)$ and their linear offset in a contiguous 1D memory buffer, enabling efficient random access to volume data [S2, unofficial]. It establishes the row-major storage order where the $i$-coordinate varies fastest, followed by $j$, then $k$, which is the standard layout for dense grid representations [S2, unofficial]. Unlike planar de-interleaving which separates channels, this method assumes a single contiguous block of memory for the scalar or vector field values [S1, S2, unofficial].

## How it works
**Inputs:**
- `xLength`, `yLength`, `zLength`: Integer dimensions of the volume in the IJK coordinate system. If not provided, they default to 1 [S2, unofficial].
- `buffer`: A 1D TypedArray or contiguous memory block of size `xLength * yLength * zLength` [S2, unofficial].

**Outputs:**
- Linear index $I$ for a given voxel $(i, j, k)$ [S2, unofficial].
- Voxel coordinates $(i, j, k)$ for a given linear index $I$ [S2, unofficial].

**Data Structures:**
The volume data is stored in a single 1D array. The memory order is row-major with respect to the IJK coordinate system: the $i$ (x) coordinate varies fastest, followed by $j$ (y), then $k$ (z) [S2, unofficial].

In some implementations, explicit strides are defined for clarity or compatibility with specific hardware architectures, such as in the Multivox system [S1, unofficial]:
- `VOXEL_X_STRIDE`: Stride for the x-dimension.
- `VOXEL_Y_STRIDE`: Stride for the y-dimension.
- `VOXEL_Z_STRIDE`: Stride for the z-dimension.
- `VOXEL_FIELD_STRIDE`: Defined as `PANEL_FIELD_HEIGHT * VOXEL_Z_STRIDE` [S1, unofficial].

**Formulas:**
The linear index $I$ for voxel $(i, j, k)$ is computed as [S2, unofficial]:
$$ I = k \cdot x_{\text{Length}} \cdot y_{\text{Length}} + j \cdot x_{\text{Length}} + i $$

The reverse mapping from linear index $I$ to IJK coordinates $(x, y, z)$ uses integer division and modulo arithmetic [S2, unofficial]:
$$ z = \lfloor I / (y_{\text{Length}} \cdot x_{\text{Length}}) \rfloor $$
$$ y = \lfloor (I - z \cdot y_{\text{Length}} \cdot x_{\text{Length}}) / x_{\text{Length}} \rfloor $$
$$ x = I - z \cdot y_{\text{Length}} \cdot x_{\text{Length}} - y \cdot x_{\text{Length}} $$

**Pseudocode:**
```python
def compute_linear_index(i, j, k, x_length, y_length, z_length):
    """
    Computes the linear index for a voxel (i, j, k) in a row-major 1D array.
    """
    return k * x_length * y_length + j * x_length + i

def compute_ijk_from_linear_index(index, x_length, y_length, z_length):
    """
    Computes the voxel coordinates (x, y, z) from a linear index.
    """
    # Calculate z
    z = index // (y_length * x_length)
    
    # Calculate y
    remainder_after_z = index - z * y_length * x_length
    y = remainder_after_z // x_length
    
    # Calculate x
    x = remainder_after_z - y * x_length
    
    return x, y, z

def validate_buffer_size(x_length, y_length, z_length, buffer_size):
    """
    Validates that the buffer size matches the expected volume size.
    """
    expected_size = x_length * y_length * z_length
    if buffer_size != expected_size:
        raise ValueError(f"Buffer size {buffer_size} does not match expected size {expected_size}")
```

**Edge Cases and Pitfalls:**
- If the provided `arrayBuffer` size does not exactly match `xLength * yLength * zLength`, the constructor throws an error to prevent out-of-bounds memory access [S2, unofficial].
- Dimensions default to 1 if not provided, which may lead to incorrect indexing if the volume is actually empty or has different dimensions [S2, unofficial].

## Operating characteristics
- **Time Complexity:** Index calculation is $O(1)$ with basic arithmetic operations [S2, unofficial].
- **Memory Complexity:** $O(N)$ where $N$ is the total number of voxels, stored in a contiguous 1D array [S2, unofficial].
- **Strengths:** Simple implementation, cache-friendly due to row-major layout, efficient for dense volumes [S2, unofficial].
- **Limitations:** Not suitable for sparse volumes due to high memory overhead [S2, unofficial].
- **When to use:** Ideal for dense, uniformly sampled volume data where random access is frequent [S2, unofficial].
- **When not to use:** For sparse volumes, consider [Paged Block Array](12102-paged-block-array.md) [S2, unofficial].

## Background
The row-major memory layout for 3D arrays is a standard convention in computer graphics and scientific computing, originating from early linear algebra libraries and C/C++ array conventions [S2, unofficial]. The specific implementation details, such as the EX macro and stride calculations, are found in various open-source volume rendering projects like Multivox and Vis2_Schott2010 [S1, S2, unofficial].
