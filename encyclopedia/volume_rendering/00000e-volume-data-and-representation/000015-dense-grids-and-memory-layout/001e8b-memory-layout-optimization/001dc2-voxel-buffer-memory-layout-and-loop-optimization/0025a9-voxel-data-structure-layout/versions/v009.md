# Voxel Data Structure Layout

Also called: Array2, Array2<T>, Structure Field Alignment, Voxel Field Ordering

## Overview
Voxel Data Structure Layout defines the memory organization of individual voxel elements within a dense grid, solving the problem of efficient storage and retrieval of geometric and material properties (such as density, color, normals, and occupancy) [S1, unofficial][S2][S3, unofficial]. It differs from [Voxel Data Layout](4076-voxel-data-layout.md) by focusing on the payload content and memory footprint of a single voxel element rather than the array indexing scheme, and from [Paged Block Array](12102-paged-block-array.md) by defining the element structure rather than chunk allocation [S1, unofficial][S2]. It serves as the base layer for optimizations like [Voxel Material Packing](4907-voxel-material-packing.md) and [Voxel Renderer with Top-Level Grid and Bricks](8114-voxel-renderer-with-top-level-bricks.md) [G].

## How it works
**Inputs and Outputs:**
- Input: A set of voxel attributes (e.g., scalar, normal, gradient) and their data types.
- Output: A contiguous memory block where each voxel element is stored according to a specific struct layout.

**Data Structures:**
The fundamental unit is a C-style struct or class representing a single voxel. The layout must account for machine alignment restrictions to avoid padding waste [S2].

Example Voxel Structure:
```cpp
typedef unsigned char Scalar;
typedef unsigned short Normal;
typedef unsigned char Gradient;

typedef struct {
    Normal normal;   // 16-bit
    Scalar scalar;   // 8-bit
    Gradient gradient; // 8-bit
} Voxel;
```
Fields: `Normal` (16-bit), `Scalar` (8-bit), `Gradient` (8-bit) [S2].

**Numbered Steps:**
1. **Define Attributes:** Identify all fields required for rendering (e.g., shading) and classification (e.g., surface detection) [S2].
2. **Order Fields:** Place fields required for shading first, followed by fields used only for classification. This ordering allows storing just the shading fields for fast rendering algorithms, saving memory and improving cache performance [S2].
3. **Check Alignment:** Verify that the structure size matches expectations using `sizeof()`. Many machines require two-byte quantities to be aligned to two-byte boundaries, and four-byte quantities to four-byte boundaries. Improper ordering may cause the compiler to insert wasted padding space [S2].
4. **Initialize Buffer:** Create a contiguous array (e.g., `std::vector<T>`) to hold the voxels. The 3D coordinates $(i, j, k)$ map to a 1D index. While the parent [Voxel Buffer Memory Layout and Loop Optimization](1598-voxel-buffer-memory-layout-and-loop-optimization.md) uses row-major ordering ($x$ is innermost), specific implementations like `Array2` use a 2D mapping $i + ni \times j$ for the underlying array `a` [S1, unofficial].
5. **Access Elements:** Access elements with bounds checking. Accessing index $i$ or $j$ outside $[0, ni)$ or $[0, nj)$ triggers an assertion failure [S1, unofficial].

**Formulas:**
- 2D element at $(i, j)$ maps to 1D index:
  $$ \text{index} = i + ni \times j $$
  where $ni$ is the dimension size in the first axis, and $j$ is the index in the second axis [S1, unofficial].
- 3D index calculation with explicit strides (alternative layout):
  $$ \text{EX}(x, y, z) = x \cdot \text{VOXEL\_X\_STRIDE} + y \cdot \text{VOXEL\_Y\_STRIDE} + z \cdot \text{VOXEL\_Z\_STRIDE} $$
  where $\text{VOXEL\_FIELD\_STRIDE} = \text{PANEL\_FIELD\_HEIGHT} \cdot \text{VOXEL\_Z\_STRIDE}$ [S4, unofficial].

**Parameters:**
- Typical types: `unsigned char` (8-bit), `unsigned short` (16-bit), `float` (32-bit) [S2].
- Typedefs provided for common types: `Array2d` (double), `Array2f` (float), `Array2i` (int), `Array2ui` (unsigned int), `Array2s` (short), `Array2us` (unsigned short), `Array2c` (char), `Array2uc` (unsigned char), `Array2ll` (long long), `Array2ull` (unsigned long long) [S1, unofficial].

**Pseudocode:**
```python
# Example of a Voxel Data Structure Layout implementation in Python-like pseudocode
# Note: Python handles memory layout differently; this illustrates the logical structure and alignment checks.

import ctypes
import sys

class Voxel(ctypes.Structure):
    _fields_ = [
        ("normal", ctypes.c_ushort),   # 16-bit, placed first for shading
        ("scalar", ctypes.c_ubyte),    # 8-bit
        ("gradient", ctypes.c_ubyte)   # 8-bit
    ]

def check_alignment():
    """Verify that the struct size matches expectations without padding waste."""
    expected_size = 2 + 1 + 1  # 16-bit + 8-bit + 8-bit = 4 bytes
    actual_size = ctypes.sizeof(Voxel)
    if actual_size != expected_size:
        print(f"Warning: Voxel struct size is {actual_size}, expected {expected_size}. "
              f"Padding may be present due to alignment restrictions.")
    return actual_size == expected_size

def create_voxel_buffer(ni, nj):
    """
    Create a contiguous buffer of voxels.
    Maps 2D coordinates (i, j) to 1D index.
    """
    if ni < 0 or nj < 0:
        raise ValueError("Dimensions must be non-negative")
    
    total_elements = ni * nj
    # In C++, this would be std::vector<Voxel> or similar contiguous array
    # Here we simulate the layout logic
    buffer = (Voxel * total_elements)()
    return buffer, ni, nj

def access_voxel(buffer, ni, nj, i, j):
    """
    Access voxel at (i, j) with bounds checking.
    Index formula: i + ni * j
    """
    if i < 0 or i >= ni:
        raise AssertionError(f"Index i={i} out of bounds [0, {ni})")
    if j < 0 or j >= nj:
        raise AssertionError(f"Index j={j} out of bounds [0, {nj})")
    
    index = i + ni * j
    return buffer[index]

def resize_buffer(buffer, ni, nj, new_ni, new_nj):
    """
    Resize the buffer to new dimensions.
    """
    if new_ni < 0 or new_nj < 0:
        raise ValueError("Dimensions must be non-negative")
    
    new_total = new_ni * new_nj
    new_buffer = (Voxel * new_total)()
    
    # Copy existing data if dimensions overlap (simplified)
    old_total = ni * nj
    copy_count = min(old_total, new_total)
    for k in range(copy_count):
        new_buffer[k] = buffer[k]
        
    return new_buffer, new_ni, new_nj

def clear_buffer(buffer, ni, nj):
    """
    Empty the buffer and reset dimensions.
    """
    # In C++, this would set ni=0, nj=0 and clear the vector
    # Here we just return zeroed dimensions
    return (Voxel * 0)(), 0, 0

def swap_buffers(buf1, ni1, nj1, buf2, ni2, nj2):
    """
    Exchange contents and dimensions with another buffer instance.
    """
    return buf2, ni2, nj2, buf1, ni1, nj1
```

**Edge Cases and Pitfalls:**
- **Alignment Padding:** Failing to order fields correctly can lead to compiler-inserted padding, increasing memory usage and reducing cache efficiency [S2].
- **Bounds Checking:** Accessing indices outside valid ranges triggers assertion failures in safe implementations [S1, unofficial].
- **Sparse Data:** Dense layouts store every voxel in a fixed-size slot, making them memory-inefficient for sparse scenes compared to hierarchical structures [G].

## Subtopics

### [Voxel Data Structure](3982-voxel-data-structure.md)
The Voxel Data Structure is the fundamental memory unit for storing per-voxel attributes in dense grid-based volume rendering and voxel engines. It solves the problem of efficient storage and retrieval of geometric and material properties (such as density, color, normals, and occupancy) for individual voxels, which are often the primary memory bottleneck in large-scale volumetric scenes. It differs from sibling structures like [Voxel Data Layout](4076-voxel-data-layout.md) (which focuses on array indexing) and [Paged Block Array](12102-paged-block-array.md) (which manages chunk allocation) by defining the actual payload content and memory footprint of a single voxel element.

### [Voxel Data Layout](4076-voxel-data-layout.md)
Voxel Data Layout refers to the fundamental memory organization of voxel data in a dense 3D grid, typically implemented as a contiguous array or tensor indexed by world coordinates $[x, y, z]$. It solves the problem of mapping 3D spatial positions to linear memory addresses for efficient access during rendering or processing [G]. Unlike hierarchical structures (e.g., [Voxel Data Structure](3982-voxel-data-structure.md)) which use pointers or bitmasks to skip empty space, this layout stores every voxel in a fixed-size slot, making it simple to implement but potentially memory-inefficient for sparse scenes [G]. It serves as the base layer for optimizations like [Voxel Material Packing](4907-voxel-material-packing.md) and [Voxel Renderer with Top-Level Grid and Bricks](8114-voxel-renderer-with-top-level-grid-and-bricks.md) [G].

### [Voxel Data Planar De-interleaving](6794-voxel-data-planar-de-interleaving.md)
Voxel Data Planar De-interleaving converts an Array of Structures (AoS) of voxel data into a Structure of Arrays (SoA) planar format to optimize memory access patterns and enable data reduction techniques such as slice reuse. It serves as the inverse operation of planar re-interleaving, restoring the AoS layout from planar buffers when required by rendering or simulation pipelines.

### [Paged Block Array](12102-paged-block-array.md)
The Paged Block Array is a dynamic array implementation that stores elements in fixed-size blocks (pages) to optimize memory allocation and cache locality, avoiding the need for contiguous reallocation of the entire array. It differs from standard dynamic arrays by using fixed-size blocks instead of contiguous reallocation, reducing allocation overhead and fragmentation at the cost of slightly higher pointer indirection and fixed block sizes.

### SerializedArray Binary Layout
The binary layout for SerializedArray structures, including name, dtype, shape, and data [S3, unofficial].
Layout: 8 bytes uint64 name_size, N bytes char name (N=name_size), 4 bytes uint32 dtype, 8 bytes uint64 shape_dim_count, M*8 bytes uint64 shape dimensions (M=shape_dim_count), 8 bytes uint64 data_byte_count, K bytes uint8 data (K=data_byte_count) [S3, unofficial].

### Voxel Memory Layout & Stride Calculation
Voxels are stored in a 3D array with explicit strides. The index for coordinates $(x, y, z)$ is calculated as $\text{EX}(x,y,z) = x \cdot \text{VOXEL\_X\_STRIDE} + y \cdot \text{VOXEL\_Y\_STRIDE} + z \cdot \text{VOXEL\_Z\_STRIDE}$. The field stride is defined as $\text{VOXEL\_FIELD\_STRIDE} = \text{PANEL\_FIELD\_HEIGHT} \cdot \text{VOXEL\_Z\_STRIDE}$ [S4, unofficial].

### Buffer View Linkage
The `voxelVolume.primitives.bufferView` field holds an integer index pointing into a separate `bufferViews` array. Each entry in `bufferViews` contains an index into a `buffers` array, which ultimately stores the raw voxel data bytes [S5, unofficial].

## Operating characteristics
- **Time Complexity:** Access is $O(1)$ given the index calculation [S1, S4, unofficial].
- **Memory Complexity:** $O(N \cdot M \cdot P \cdot S)$ where $N, M, P$ are grid dimensions and $S$ is the size of the voxel structure in bytes [S2].
- **Measured Performance:** Not given in the sources.
- **Scaling:** Linear with grid size. Cache performance is improved by ordering shading fields first [S2].
- **Strengths:** Simple implementation, fast access, cache-friendly if fields are ordered correctly [S2].
- **Limitations:** Memory-inefficient for sparse scenes due to fixed-size slots for every voxel [G].
- **When to use:** Dense volumes where memory overhead is acceptable and fast access is critical.
- **When not to use:** Sparse scenes where hierarchical or sparse data structures are more appropriate.

## Background
The concept of voxel data structure layout originates from early volume rendering systems like VolPack, which emphasized the importance of field ordering for performance [S2]. The `Array2` structure is implemented in various open-source projects such as NMC [S1, unofficial]. The SerializedArray binary layout is used in sparse voxel implementations [S3, unofficial]. Multivox uses explicit stride calculations for 3D arrays [S4, unofficial]. The Buffer View Linkage is part of the OpenVoxel File Format specification [S5, unofficial].
