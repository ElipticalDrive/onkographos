# Scion Layout Language

Also called: Layout specification language, Physical Layout Language, Scion, Scion's layout language

## Overview
The Scion Layout Language is a declarative domain-specific language (DSL) that decouples the logical definition of algebraic data types (ADTs), specifically Bounding Volume Hierarchies (BVHs), from their physical memory representation [S1]. It defines the "destructor" mapping, specifying how to extract logical fields from a physical tree structure [S1]. Unlike general-purpose languages that tightly couple data layout with traversal logic, Scion enables independent optimization of storage (e.g., Structure of Arrays, bit-packing) and algorithms [S1]. It serves as the counterpart to the Scion Build Language, which defines the "constructor" mapping (logical to physical) [S1].

## How it works
The language specifies the physical layout through a signature, groups, and relational primitives. The compiler generates code to reconstruct logical ADT terms from the physical memory buffers described by the layout [S1].

### Inputs and Outputs
- **Input**: A logical ADT definition (e.g., BVH with Interior/Leaf variants) and a layout specification written in Scion syntax.
- **Output**: A memory layout description that maps logical fields to physical storage offsets, alignments, and interpretations, enabling the generation of destructor code [S1].

### Data Structures and Layout
The layout is defined by the following components:

1.  **Reference Type**: A concrete type (e.g., `u32`) declared in the layout signature that uniquely identifies an ADT term in memory. It enables coarse-grain optimizations like Structure of Arrays (SoA) [S1].
2.  **Global Fields**: Fields declared outside of node groups, such as primitive counts or global primitive arrays [S1].
3.  **Direct Groups**: Indexed by a component of the reference type. They correspond to primary storage. A direct group specifies:
    -   Size (e.g., `size=N`)
    -   Alignment (e.g., `align=32`)
    -   Indexing variable (e.g., `by I`) [S1]
4.  **Stored Fields**: Fields within a group that occupy specific bits in memory (e.g., `bounds: AABB`, `nprims: u16`) [S1].
5.  **Derived Fields**: Identifiers bound to expressions (r-values) that are computed lazily and at most once per field destruction. They span the compute-memory tradeoff spectrum (e.g., `left = I + 1`) [S1].
6.  **Split Construct**: A safe tagged union mechanism that discriminates between variants based on a stored field's value (e.g., `nprims`). It performs conditional branching and bit reinterpretation [S1].
7.  **Indirect Groups**: Labeled via `indirect`, representing auxiliary storage accessed from direct groups using the `from` operator. Effective for heterogeneous data [S1].
8.  **Separator (`---`)**: Splits a group into multiple adjoining groups while preserving lexical scope, allowing derivations to refer to one another [S1].

### Numbered Steps for Layout Specification
1.  **Declare Reference Type**: Define the layout signature with the reference type (e.g., `layout LinearBVH(I: u32)`). This type identifies ADT terms and enables SoA layouts [S1].
2.  **Declare Global Fields**: Define global data (e.g., primitive counts, primitive arrays) outside of node groups [S1].
3.  **Define Direct Group**: Create a group for the main node array, specifying size, alignment, and indexing variable (e.g., `group nodes[size=N, align=32] by I`) [S1].
4.  **Define Stored Fields**: Within the group, specify fields that occupy memory bits (e.g., `bounds: AABB`, `nprims: u16`) [S1].
5.  **Define Split Construct**: Use `split e` to create a tagged union based on expression `e` (e.g., `nprims`).
    -   **Arms**: Define unary conditions. Simple constants (e.g., `0`) are treated as equality tests. Other comparisons must be explicit (e.g., `< 42`, `≥ 0`).
    -   **Wildcard**: Use `_` as a catch-all for unmatched cases [S1].
    -   **Sub-layout**: The right-hand side of an arm defines the sub-layout and variant type [S1].
6.  **Define Derived Fields**: Within split arms, compute logical references from stored fields and the reference index (e.g., `left = I + 1; right = I + c_o`) [S1].
7.  **Define SoA Layouts**: Use adjacent single-field groups sharing a common index, or use the separator `---` within a single group to create adjoining groups with shared scope [S1].
8.  **Handle Indirect Groups**: Use `indirect` labels for auxiliary storage. Access fields using the `from` operator with a key or range of keys [S1].
9.  **Define Recursive References**: Ensure recursive fields match the layout's reference type. Use tree-carried dependencies (hierarchical encoding) to pass shared data into the reference, reducing per-term storage. Use the `parent` prefix (e.g., `parent.x`) to incorporate parent information into the reference and layout signature [S1].

### Formulas and Definitions
-   **Reference Type**: $T_{ref}$ (e.g., `u32`). Identifies an ADT term [S1].
-   **Derived Field**: $x = e$, where $e$ is an r-value. Evaluated lazily [S1].
-   **Split Condition**: $e$ is evaluated. If $e = c$ (constant), it is an equality test. Otherwise, explicit comparison operators are used. Wildcard `_` matches any value [S1].
-   **Tree-Carried Dependency**: Reference type includes parent context, e.g., $T_{ref} = (index, parent\_data)$. Access via `parent.x` [S1].

### Parameters and Typical Values
-   **Reference Type**: Typically `u32` (index), a set of indices (nested direct groups), or a pointer type [S1].
-   **Alignment**: Often 32 bytes or cache-line aligned for performance [S1].
-   **Split Discriminator**: Commonly `nprims` (number of primitives) to distinguish Interior (nprims=0) from Leaf (nprims>0) nodes [S1].

### Edge Cases and Pitfalls
-   **Precision**: Bit-field exploitation (bit-stealing) requires careful handling of padding and alignment to avoid data corruption [S1].
-   **Boundaries**: The `from` operator in indirect groups requires correct key ranges to avoid out-of-bounds access [S1].
-   **Scope**: Fields in indirect groups have different scoping rules than direct groups. Derivations must respect these scopes [S1].
-   **Consistency**: Layout and Build specifications must be consistent. A field in a layout's split branch must be populated by a corresponding build statement [S1].

### Pseudocode
```python
# Example Scion Layout Specification for a BVH
# Reference type: u32 index I
# Global fields: num_prims, primitives array

layout LinearBVH(I: u32):
    # Global fields
    num_prims: u32
    primitives: Triangle[num_prims]

    # Direct group for nodes
    group nodes[size=N, align=32] by I:
        # Stored fields
        bounds: AABB
        nprims: u16
        
        # Split construct based on nprims
        split nprims:
            # Leaf case: nprims > 0
            case > 0:
                # Stored field for leaf
                p_o: u32 # Offset into primitives array
                # Derived field for data array
                data = primitives[p_o : p_o + nprims]
            
            # Interior case: nprims == 0
            case 0:
                # Derived fields for children
                left = I + 1
                right = I + c_o # c_o is a stored offset field
            
            # Wildcard catch-all
            case _:
                pass # Error or default handling

    # Indirect group example (if needed)
    indirect auxiliary:
        aux_data: u32
```

## Subtopics

### [Scion Build Language](22867-scion-build-language.md)
The Scion Build Language is a declarative language for specifying the transformation from logical trees to physical representations. It defines the constructor: how to populate physical storage from a logical term. It serves as the counterpart to the Scion Layout Language, which defines the destructor (physical → logical). Together, they express a bidirectional mapping between logical and physical representations.

What sets it apart from its siblings is its explicit control over memory materialization order (preorder/postorder) and its ability to compute relative offsets and pack auxiliary metadata directly into reference types during construction. Unlike single-phase construction methods that build specialized layouts directly during tree construction, Scion adopts a two-phase approach, treating the logical tree as immutable input to cleanly separate topology optimization from physical layout optimization.

## Operating characteristics
-   **Time Complexity**: Constructor specialization lowering proceeds in linear time [S1].
-   **Memory Complexity**: The compiler analyzes layout specifications to compute the size of each contiguous buffer, ensuring each buffer requires only a single allocation [S1].
-   **Performance**: Scion enables Pareto-optimal layouts along performance and memory footprint axes, varying across algorithms, architectures, and workloads [S1]. It achieves Pareto-optimality across diverse architectures and scenes by combining optimization techniques from prior work [S1].
-   **Strengths**: Decouples data layout from traversal logic, enabling independent optimization. Supports diverse techniques: AoS/SoA, bit-field exploitation, increased branching factors, specialized bounding volumes, implicit indices, and compression [S1].
-   **Limitations**: Requires a compiler to generate backend code. Layout and build specifications must be consistent [S1].
-   **When to Use**: When independent optimization of data layouts and algorithms is required, especially for performance-critical data structures like BVHs in ray tracing [S1].
-   **When Not to Use**: When simplicity of implementation is prioritized over performance optimization, or when the workload does not benefit from specialized layouts [S1].

## Background
Scion was introduced by Christophe Gyurgyik, Alexander J. Root, and Fredrik Kjolstad in the paper "Decoupling Data Layouts from Bounding Volume Hierarchies" [S1]. The work addresses the entanglement of data layouts and traversal logic in general-purpose languages, which prevents independent optimization [S1]. Scion provides a domain-specific language and compiler for specifying data layouts of BVHs independent of tree traversal algorithms [S1]. It demonstrates that Pareto-optimal layouts vary across algorithms, architectures, and workload characteristics, and identifies a novel ray tracing layout that achieves Pareto-optimality across diverse contexts [S1].
