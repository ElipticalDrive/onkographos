# Voxel Data Structure

Also called: VoxelData

## Overview
The Voxel Data Structure is a compact memory layout for storing per-voxel attributes in dense volume rendering and voxel-based engines. It solves the problem of memory bandwidth and capacity constraints by packing essential voxel state into a minimal footprint, serving as the primary memory consumer in voxel systems. It differs from sibling structures like [Voxel Data Layout](4076-voxel-data-layout.md) by offering specific implementation variants that trade attribute richness for size, such as bit-packed formats or floating-point density fields.

## How it works
The core method involves defining a struct that holds voxel attributes. Two primary implementations exist in the source literature, differing in attribute selection and size.

### Inputs and Outputs
*   **Input:** Voxel coordinates (implicit or explicit), material properties, density values, and geometric normals.
*   **Output:** A contiguous memory block of voxel structs, accessible via linear indexing or spatial hashing.

### Data Structures and Layouts
Two distinct layouts are documented:

1.  **Rich Attribute Layout [S1, unofficial]:**
    *   `morton`: `uint64_t` (64 bits). Stores the Morton code for spatial ordering.
    *   `color`: `vec3` (3 floats, 96 bits). RGB color data.
    *   `normal`: `vec3` (3 floats, 96 bits). Surface normal data.
    *   **Total Size:** $8 + 3 \times 4 + 3 \times 4 = 32$ bytes per voxel.
    *   **Comparison:** Operators `>` and `<` are defined based on the `morton` code value [S1, unofficial].

2.  **Compact Density Layout [S2, unofficial]:**
    *   `density`: `half` (fp16, 16 bits). Density representation.
    *   `materialId`: `uint` or `int` (32 bits). Identifier for the material type.
    *   `flags`: `bool` or `uint` (variable, typically packed to fit 4 bytes total).
    *   **Total Size:** 4 bytes per voxel.
    *   **Precision:** Uses half-precision (fp16) for density to balance precision and memory usage [S2, unofficial].

### Numbered Steps for Implementation
1.  **Define the Struct:** Choose the layout based on the rendering/meshing requirements. For density-based meshing (e.g., Marching Cubes), use the 4-byte layout [S2, unofficial]. For raycasting with shading, use the 32-byte layout [S1, unofficial].
2.  **Initialize Memory:** Allocate a flat array of the chosen struct type. For a chunk of size $N^3$, allocate $N^3 \times \text{sizeof(VoxelData)}$ bytes.
3.  **Set Voxel Data:**
    *   For solid blocks: Set `materialId` and clear density/flags [S2, unofficial].
    *   For smooth terrain: Set `density` (e.g., 0.7f) and `materialId` [S2, unofficial].
4.  **Access:** Retrieve voxel data using linear index $i = x + y \cdot W + z \cdot W \cdot H$.

### Formulas
*   **Memory Savings (Density):** Using fp16 for density reduces memory usage by 50% compared to fp32.
    $$ \text{Size}_{\text{fp16}} = \frac{1}{2} \text{Size}_{\text{fp32}} $$
*   **Chunk Memory (32³):**
    *   fp16 Density: $32^3 \times 2 \text{ bytes (density)} + \text{overhead} \approx 68 \text{ KB}$ [S2, unofficial].
    *   fp32 Density: $32^3 \times 4 \text{ bytes (density)} + \text{overhead} \approx 128 \text{ KB}$ [S2, unofficial].

### Parameters
*   **Density Precision:** `half` (fp16) [S2, unofficial].
*   **Chunk Size:** Default $32^3$ [S2, unofficial].

### Edge Cases and Pitfalls
*   **Precision Loss:** fp16 has limited dynamic range and precision. For high-contrast density fields, artifacts may appear [S2, unofficial].
*   **Alignment:** Ensure struct padding is controlled. The 4-byte layout requires careful packing of `materialId` and `flags` to avoid compiler-inserted padding [S2, unofficial].
*   **Morton Code Overflow:** In the 32-byte layout, `morton` codes must fit in `uint64_t`. For very large grids, coordinate encoding must be verified [S1, unofficial].

### Pseudocode
```python
# Variant 1: Compact 4-byte layout [S2, unofficial]
class VoxelDataCompact:
    density: float16
    material_id: uint32
    flags: uint8 # Packed into remaining bits to total 4 bytes

    @staticmethod
    def create_solid(material_id: uint32) -> 'VoxelDataCompact':
        return VoxelDataCompact(density=0.0, material_id=material_id, flags=0)

    @staticmethod
    def create_smooth(density: float, material_id: uint32) -> 'VoxelDataCompact':
        # Convert float to fp16
        density_fp16 = float_to_half(density)
        return VoxelDataCompact(density=density_fp16, material_id=material_id, flags=0)

# Variant 2: Rich 32-byte layout [S1, unofficial]
class VoxelDataRich:
    morton: uint64
    color: vec3 # 3 floats
    normal: vec3 # 3 floats

    def __gt__(self, other: 'VoxelDataRich') -> bool:
        return self.morton > other.morton

    def __lt__(self, other: 'VoxelDataRich') -> bool:
        return self.morton < other.morton
```

## Subtopics

### 64-bit Bit-packed Voxel Format
A 64-bit packed structure storing voxel metadata using bit fields, accessed via template-based bit set/get utilities [S3, unofficial]. It stores Voxel Index (bits 0-15, 16 bits), State Bit (bit 15, 1 bit), Type Info (bits 16-31, 16 bits), and User Data (bits 32-63, 32 bits) in a single `uint64_t` [S3, unofficial]. Bit manipulation uses `util::bset<beg_val, size_val>(n_, value_)` which applies `n_ = (n_ & cmask_) | vmask_;` where `cmask_ = ~(width_ << beg_val)` and `vmask_ = (value_ & width_) << beg_val` [S3, unofficial]. A pitfall is that the State Bit (bit 15) overlaps with the Voxel Index field (bits 0-15), which may cause data corruption if both are written independently without masking [S3, unofficial].

## Operating characteristics
*   **Memory Complexity:** $O(N)$ where $N$ is the number of voxels. The 4-byte layout uses 4 bytes/voxel, while the 32-byte layout uses 32 bytes/voxel [S1, S2, unofficial].
*   **Performance:** The compact layout enables higher cache efficiency and reduced memory bandwidth usage, crucial for real-time meshing jobs (e.g., Marching Cubes) [S2, unofficial].
*   **Strengths:** Minimal memory footprint (4 bytes/voxel) allows for larger world chunks or higher resolution grids within fixed memory budgets [S2, unofficial].
*   **Limitations:** The 4-byte layout lacks per-voxel normals and colors, requiring external data structures or interpolation for shading [S2, unofficial]. The 32-byte layout is memory-intensive [S1, unofficial].
*   **When to Use:** Use the 4-byte layout for density-based terrain and blocky meshing where memory is constrained [S2, unofficial]. Use the 32-byte layout for raycasting or rendering requiring per-voxel shading data [S1, unofficial].

## Background
The concept of compact voxel data structures emerged with the need for efficient voxel-based terrain and volume rendering in real-time applications. The 4-byte layout was implemented in the "StraightFour" voxel engine to support generic, terrain, and smoothed voxel features using Unity's Job System and Burst compiler [S2, unofficial]. The 32-byte layout with Morton codes is associated with CPU-based voxel raycasting implementations [S1, unofficial]. The 64-bit bit-packed format is found in spatial voxel octree implementations [S3, unofficial].
