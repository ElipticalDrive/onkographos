# Voxel Data Structure

Also called: Voxel class, VoxelData, block class

## Overview
The Voxel Data Structure defines the memory layout and payload for a single voxel element in dense grid-based volume rendering and voxel engines [S1, S2, S3, unofficial]. It solves the problem of storing per-voxel attributes such as density, color, normals, material IDs, and geometric metadata [S1, S2, S3, unofficial]. It differs from sibling structures like [Voxel Data Layout](4076-voxel-data-layout.md) (which focuses on array indexing) and [Paged Block Array](12102-paged-block-array.md) (which manages chunk allocation) by defining the actual payload content and memory footprint of a single voxel element [S1, S2, unofficial].

## How it works
### Inputs and Outputs
*   **Inputs:** Spatial coordinates, material properties, and geometric metadata [S1, S2, S3, unofficial].
*   **Outputs:** A contiguous memory block representing a single voxel, accessible via linear indexing or spatial hashing [S2, S3, unofficial].

### Data Structures and Layouts
The evidence describes three distinct payload structures from different implementations:
*   **Source [S1, unofficial] VoxelData:** Contains `morton` (`uint64_t`), `color` (`vec3`), and `normal` (`vec3`) [S1, unofficial]. The total size is `sizeof(uint64_t) + 2 * (3 * sizeof(float))` [S1, unofficial].
*   **Source [S2, unofficial] VoxelData:** Contains `density` (`half`/fp16), `materialId` (`uint`/`int`), and `flags` (`bool`/`uint`) [S2, unofficial]. The total size is 4 bytes per voxel [S2, unofficial].
*   **Source [S3, unofficial] block class:** Contains `side` (`GLuint`), `position` (`glm::vec3`), `is_solid` (`bool`), `verticies` (`vector<int>`), and `indicies` (`vector<int>`) [S3, unofficial].

### Numbered Steps
1.  **Initialization:** Set fields according to the target structure [S1, S2, S3, unofficial].
2.  **Comparison:** For the Source [S1, unofficial] structure, comparison operators are defined based on the morton code: `operator>` returns `morton > a.morton`, and `operator<` returns `morton < a.morton` [S1, unofficial].
3.  **Population:** Use `VoxelData.CreateSolid(materialId)` to set a voxel with full occupancy, or `VoxelData.CreateSmooth(density, materialId)` to set a specific density value [S2, unofficial].
4.  **Bit-Packed Access:** For the 64-bit variant, use `util::bset<beg_val, size_val>(n_, value_)` which applies `n_ = (n_ & cmask_) | vmask_` where `cmask_ = ~(width_ << beg_val)` and `vmask_ = (value_ & width_) << beg_val` [S4, unofficial]. Use `util::bget` which applies `value_ = (n_ >> bel_val) & mask` [S4, unofficial].

### Formulas
*   **Vertex Generation:** `hside = side / 2.0` [S3, unofficial].
*   **Bit Set Masking:** `cmask_ = ~(width_ << beg_val)` and `vmask_ = (value_ & width_) << beg_val` [S4, unofficial].
*   **Bit Get Masking:** `value_ = (n_ >> bel_val) & mask` [S4, unofficial].

### Parameters and Typical Values
*   **Chunk Size:** $32^3$ is a common default for the Source [S2, unofficial] structure to balance cache locality and memory overhead [S2, unofficial].
*   **Precision:** fp16 (half) is used for density to balance precision and memory usage [S2, unofficial].
*   **Morton Code:** 64-bit integer for the Source [S1, unofficial] structure, allowing for large spatial ranges [S1, unofficial].

### Edge Cases and Pitfalls
*   **Bit Overlap:** In the 64-bit bit-packed format, the State Bit (bit 15) overlaps with the Voxel Index field (bits 0-15), which may cause data corruption if both are written independently without masking [S4, unofficial].
*   **Precision Loss:** Using fp16 for density reduces memory usage by 50% but may introduce quantization artifacts [S2, unofficial].
*   **Memory Alignment:** The Source [S2, unofficial] structure must be packed tightly to achieve the stated 68 KB per $32^3$ chunk efficiency versus 128 KB for single precision [S2, unofficial].

### Pseudocode
```python
import struct

class VoxelDataS1:
    def __init__(self, morton: int, color: list, normal: list):
        self.morton = morton
        self.color = color
        self.normal = normal
    def __lt__(self, other: 'VoxelDataS1') -> bool:
        return self.morton < other.morton
    def __gt__(self, other: 'VoxelDataS1') -> bool:
        return self.morton > other.morton

class VoxelDataS2:
    def __init__(self, density: float, material_id: int, flags: int):
        self.density = struct.unpack('<H', struct.pack('<e', density))[0]
        self.material_id = material_id
        self.flags = flags
    @staticmethod
    def CreateSolid(material_id: int) -> 'VoxelDataS2':
        return VoxelDataS2(density=1.0, material_id=material_id, flags=1)
    @staticmethod
    def CreateSmooth(density: float, material_id: int) -> 'VoxelDataS2':
        return VoxelDataS2(density=density, material_id=material_id, flags=0)

class BlockS3:
    def __init__(self, position: list, side: int):
        self.position = position
        self.side = side
        self.is_solid = True
        self.vertices = self._generate_vertices()
    def _generate_vertices(self) -> list:
        hside = self.side / 2.0
        x, y, z = self.position
        verts = []
        # Vertices 0-3: Back Face
        verts.extend([x-hside, y-hside, z-hside, 1.0])
        verts.extend([x+hside, y-hside, z-hside, 1.0])
        verts.extend([x+hside, y+hside, z-hside, 1.0])
        verts.extend([x-hside, y+hside, z-hside, 1.0])
        # Vertices 4-7: Front Face
        verts.extend([x-hside, y-hside, z+hside, 1.0])
        verts.extend([x-hside, y+hside, z+hside, 1.0])
        verts.extend([x+hside, y+hside, z+hside, 1.0])
        verts.extend([x+hside, y-hside, z+hside, 1.0])
        # Vertices 8-11: Left Face
        verts.extend([x-hside, y-hside, z-hside, 1.0])
        verts.extend([x-hside, y-hside, z+hside, 1.0])
        verts.extend([x-hside, y+hside, z+hside, 1.0])
        verts.extend([x-hside, y+hside, z-hside, 1.0])
        # Vertices 12-15: Right Face
        verts.extend([x+hside, y-hside, z-hside, 1.0])
        verts.extend([x+hside, y+hside, z-hside, 1.0])
        verts.extend([x+hside, y+hside, z+hside, 1.0])
        verts.extend([x+hside, y-hside, z+hside, 1.0])
        # Vertices 16-19: Top Face
        verts.extend([x-hside, y+hside, z-hside, 1.0])
        verts.extend([x+hside, y+hside, z-hside, 1.0])
        verts.extend([x+hside, y+hside, z+hside, 1.0])
        verts.extend([x-hside, y+hside, z+hside, 1.0])
        # Vertices 20-23: Bottom Face
        verts.extend([x-hside, y-hside, z-hside, 1.0])
        verts.extend([x-hside, y-hside, z+hside, 1.0])
        verts.extend([x+hside, y-hside, z+hside, 1.0])
        verts.extend([x+hside, y-hside, z-hside, 1.0])
        return verts

class BitPackedVoxelS4:
    def __init__(self):
        self.packed = 0
    def set_field(self, beg_val: int, size_val: int, value: int) -> None:
        total_bits = 64
        width = (1 << size_val) - 1 if size_val < total_bits else -1
        cmask = ~(width << beg_val)
        vmask = (value & width) << beg_val
        self.packed = (self.packed & cmask) | vmask
    def get_field(self, bel_val: int, size_val: int) -> int:
        width = (1 << size_val) - 1 if size_val < 64 else -1
        return (self.packed >> bel_val) & width
```

## Subtopics

### 64-bit Bit-packed Voxel Format
A compact 64-bit structure storing voxel metadata using bit fields, accessed via template-based bit set/get utilities [S4, unofficial]. It packs Voxel Index (bits 0-15), State Bit (bit 15), Type Info (bits 16-31), and User Data (bits 32-63) into a single `uint64_t` [S4, unofficial]. It is chosen when memory bandwidth is critical and metadata is sparse [S4, unofficial]. The primary pitfall is the overlap of the State Bit (bit 15) with the Voxel Index field (bits 0-15), which can cause data corruption if written independently without masking [S4, unofficial].

## Operating characteristics
*   **Memory Complexity:** The Source [S1, unofficial] structure uses 32 bytes per voxel [S1, unofficial]. The Source [S2, unofficial] structure uses 4 bytes per voxel, resulting in 68 KB per $32^3$ chunk versus 128 KB for single precision [S2, unofficial].
*   **Time Complexity:** Direct access is $O(1)$ [S2, unofficial]. Bit-packed access is $O(1)$ with a higher constant factor due to bitwise operations [S4, unofficial].
*   **Strengths:** The Source [S2, unofficial] structure maximizes voxel count per chunk and balances precision with memory usage [S2, unofficial]. The Source [S1, unofficial] structure stores detailed surface information for visualization [S1, unofficial].
*   **Limitations:** The Source [S2, unofficial] structure's fp16 density reduces precision [S2, unofficial]. The Source [S3, unofficial] structure generates immediate-mode geometry and requires manual meshing for large scenes [S3, unofficial].
*   **When to Use:** Use the Source [S2, unofficial] structure for terrain or voxel games where memory is the bottleneck [S2, unofficial]. Use the Source [S1, unofficial] structure for raycasting or visualization requiring normals and colors [S1, unofficial]. Use the Source [S3, unofficial] structure for immediate rendering of blocky geometry [S3, unofficial].

## Background
The concept of voxel data structures originated with the need to represent 3D space in computer graphics and medical imaging [S1, S2, S3, unofficial]. The Source [S1, unofficial] structure is derived from CPU-based voxel raycasters emphasizing spatial locality via Morton codes [S1, unofficial]. The Source [S2, unofficial] structure stems from game engine development supporting discrete blocky materials and smooth surfaces via Marching Cubes [S2, unofficial]. The Source [S3, unofficial] structure is associated with OpenGL-based voxelizers focusing on immediate geometric rendering [S3, unofficial]. The bit-packed variant originates from high-performance spatial data structures optimizing for cache efficiency in sparse voxel octrees [S4, unofficial].
