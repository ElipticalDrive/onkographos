# Voxel Data Structure

Also called: Voxel class, VoxelData, block class

## Overview
The Voxel Data Structure is the fundamental memory unit for storing per-voxel attributes in dense grid-based volume rendering and voxel engines. It solves the problem of efficient storage and retrieval of geometric and material properties (such as density, color, normals, and occupancy) for individual voxels, which are often the primary memory bottleneck in large-scale volumetric scenes [S1, S2, S3, unofficial]. It differs from sibling structures like [Voxel Data Layout](4076-voxel-data-layout.md) (which focuses on array indexing) and [Paged Block Array](12102-paged-block-array.md) (which manages chunk allocation) by defining the actual payload content and memory footprint of a single voxel element [S1, S2, unofficial].

## How it works
The implementation of the Voxel Data Structure varies significantly depending on the rendering or simulation requirements, primarily falling into two categories: attribute-rich structures for raycasting/visualization and compact structures for terrain/meshing.

### Inputs and Outputs
*   **Inputs:** Spatial coordinates (x, y, z), material properties (color, density, type), and geometric metadata (normals, occupancy).
*   **Outputs:** A contiguous memory block representing a single voxel, accessible via linear indexing or spatial hashing.

### Data Structures and Layouts
There are two primary layouts cited in the sources, serving different use cases:

**Layout A: Attribute-Rich (Raycasting/Visualization)**
Used in CPU voxel raycasters to store detailed surface information.
*   **Fields:**
    *   `morton`: `uint64_t`. The Morton code (Z-order curve index) for spatial sorting and traversal.
    *   `color`: `vec3` (3 floats). RGB color values.
    *   `normal`: `vec3` (3 floats). Surface normal vector.
*   **Size:** `sizeof(uint64_t) + 2 * (3 * sizeof(float))`. Assuming standard 64-bit integer and 32-bit float, this is $8 + 24 = 32$ bytes per voxel [S1, unofficial].

**Layout B: Compact (Terrain/Meshing)**
Used in game engines and terrain systems to maximize voxel count per chunk.
*   **Fields:**
    *   `density`: `half` (fp16). Half-precision floating-point density value.
    *   `materialId`: `uint` or `int`. Identifier for the material type.
    *   `flags`: `bool` or `uint`. Occupancy or state flags.
*   **Size:** 4 bytes per voxel [S2, unofficial].
*   **Optimization:** Using fp16 for density reduces memory usage by 50% compared to fp32. For a standard $32^3$ chunk, this results in 68 KB (vs 128 KB for fp32) [S2, unofficial].

**Layout C: Geometric Block (OpenGL/Immediate Mode)**
Used for immediate rendering of blocky geometry rather than density fields.
*   **Fields:**
    *   `side`: `GLuint`. Voxel width/height/depth.
    *   `position`: `glm::vec3`. Center coordinates $(x, y, z)$.
    *   `is_solid`: `bool`. Occupancy flag.
    *   `vertices`: `vector<int>` or fixed array. Indices or packed data.
    *   `indices`: `vector<int>`. Default empty.
*   **Vertex Generation:** The `block` class generates 24 vertices (glm::vec4) relative to `position` and `side`.
    *   $hside = side / 2.0$.
    *   Vertices 0-3: Back Face.
    *   Vertices 4-7: Front Face.
    *   Vertices 8-11: Left Face.
    *   Vertices 12-15: Right Face.
    *   Vertices 16-19: Top Face.
    *   Vertices 20-23: Bottom Face [S3, unofficial].

### Numbered Steps for Usage

1.  **Initialization:**
    *   For Layout A: Initialize `morton` using spatial-to-Morton conversion. Set `color` and `normal` based on surface shading or material definition [S1, unofficial].
    *   For Layout B: Initialize `density` to 0.0 (empty) or a specific value. Set `materialId` and `flags` [S2, unofficial].
    *   For Layout C: Set `position`, `side`, and `is_solid`. Generate vertex coordinates if `is_solid` is true [S3, unofficial].

2.  **Comparison and Sorting (Layout A):**
    *   Voxels are often sorted by spatial locality. Define comparison operators based on the `morton` code:
        *   `operator<(a, b)` returns `a.morton < b.morton`.
        *   `operator>(a, b)` returns `a.morton > b.morton` [S1, unofficial].

3.  **Population:**
    *   **Solid Voxel (Layout B):** Call `VoxelData.CreateSolid(materialId)` to set a voxel with full density/occupancy [S2, unofficial].
    *   **Smooth/Density Voxel (Layout B):** Call `VoxelData.CreateSmooth(density, materialId)` to set a specific density value (e.g., 0.7) for marching cubes or gradient-based rendering [S2, unofficial].

4.  **Bit-Packed Access (Variant: 64-bit Bit-packed):**
    *   If using the bit-packed variant, access fields via bit manipulation utilities [S4, unofficial]:
        *   **Set:** `util::bset<beg_val, size_val>(n_, value_)` computes `n_ = (n_ & cmask_) | vmask_`, where `cmask_ = ~(width_ << beg_val)` and `vmask_ = (value_ & width_) << beg_val`.
        *   **Get:** `util::bget<beg_val, size_val>(n_)` computes `value_ = (n_ >> bel_val) & mask` [S4, unofficial].

### Parameters and Typical Values
*   **Chunk Size:** $32^3$ is a common default for Layout B to balance cache locality and memory overhead [S2, unofficial].
*   **Precision:** fp16 (half) for density in Layout B; fp32 for color/normal in Layout A [S1, S2, unofficial].
*   **Morton Code:** 64-bit integer for Layout A, allowing for large spatial ranges [S1, unofficial].

### Edge Cases and Pitfalls
*   **Bit Overlap (Layout Variant):** In the 64-bit bit-packed format, the "State Bit" is located at bit 15, which overlaps with the "Voxel Index" field (bits 0-15). Writing to these fields independently without masking can cause data corruption [S4, unofficial].
*   **Precision Loss:** Using fp16 for density (Layout B) may introduce quantization artifacts in smooth terrain or high-precision volume rendering. It is suitable for blocky or low-resolution smooth surfaces but may fail for high-fidelity medical or scientific visualization [S2, unofficial].
*   **Memory Alignment:** Layout A (32 bytes) is naturally aligned, but Layout B (4 bytes) must be packed tightly to achieve the stated 68 KB/chunk efficiency. Padding or alignment directives must be avoided [S2, unofficial].

### Pseudocode

```python
# Layout B: Compact Voxel Data (Unity-like Job System)
class VoxelData:
    def __init__(self, density: float = 0.0, material_id: int = 0, flags: int = 0):
        # Density stored as half-precision (fp16)
        self.density = self._to_fp16(density)
        self.material_id = material_id
        self.flags = flags

    def _to_fp16(self, value: float) -> int:
        # Convert float to 16-bit integer representation
        # Implementation depends on language; here conceptual
        import struct
        return struct.unpack('<H', struct.pack('<e', value))[0]

    @staticmethod
    def CreateSolid(material_id: int) -> 'VoxelData':
        return VoxelData(density=1.0, material_id=material_id, flags=1)

    @staticmethod
    def CreateSmooth(density: float, material_id: int) -> 'VoxelData':
        return VoxelData(density=density, material_id=material_id, flags=0)

# Layout A: Attribute-Rich Voxel (Raycaster)
class VoxelDataRich:
    def __init__(self, morton: int, color: list, normal: list):
        self.morton = morton
        self.color = color  # [r, g, b]
        self.normal = normal # [nx, ny, nz]

    def __lt__(self, other: 'VoxelDataRich') -> bool:
        return self.morton < other.morton

    def __gt__(self, other: 'VoxelDataRich') -> bool:
        return self.morton > other.morton

# Layout C: Geometric Block (OpenGL)
class Block:
    def __init__(self, position: list, side: int):
        self.position = position # [x, y, z]
        self.side = side
        self.is_solid = True
        self.vertices = self._generate_vertices()

    def _generate_vertices(self) -> list:
        hside = self.side / 2.0
        x, y, z = self.position
        # 24 vertices for 6 faces, 4 vertices per face
        # Format: [x, y, z, w] (w=1.0)
        verts = []
        # Back Face (z - hside)
        verts.extend([x-hside, y-hside, z-hside, 1.0])
        verts.extend([x+hside, y-hside, z-hside, 1.0])
        verts.extend([x+hside, y+hside, z-hside, 1.0])
        verts.extend([x-hside, y+hside, z-hside, 1.0])
        # Front Face (z + hside)
        verts.extend([x-hside, y-hside, z+hside, 1.0])
        verts.extend([x-hside, y+hside, z+hside, 1.0])
        verts.extend([x+hside, y+hside, z+hside, 1.0])
        verts.extend([x+hside, y-hside, z+hside, 1.0])
        # Left Face (x - hside)
        verts.extend([x-hside, y-hside, z-hside, 1.0])
        verts.extend([x-hside, y-hside, z+hside, 1.0])
        verts.extend([x-hside, y+hside, z+hside, 1.0])
        verts.extend([x-hside, y+hside, z-hside, 1.0])
        # Right Face (x + hside)
        verts.extend([x+hside, y-hside, z-hside, 1.0])
        verts.extend([x+hside, y+hside, z-hside, 1.0])
        verts.extend([x+hside, y+hside, z+hside, 1.0])
        verts.extend([x+hside, y-hside, z+hside, 1.0])
        # Top Face (y + hside)
        verts.extend([x-hside, y+hside, z-hside, 1.0])
        verts.extend([x+hside, y+hside, z-hside, 1.0])
        verts.extend([x+hside, y+hside, z+hside, 1.0])
        verts.extend([x-hside, y+hside, z+hside, 1.0])
        # Bottom Face (y - hside)
        verts.extend([x-hside, y-hside, z-hside, 1.0])
        verts.extend([x-hside, y-hside, z+hside, 1.0])
        verts.extend([x+hside, y-hside, z+hside, 1.0])
        verts.extend([x+hside, y-hside, z-hside, 1.0])
        return verts

# Bit-Packed Variant (C++ Conceptual)
class BitPackedVoxel:
    def __init__(self):
        self.packed: int = 0

    def set_field(self, beg_val: int, size_val: int, value: int):
        # Calculate masks
        total_bits = 64
        width = (1 << size_val) - 1 if size_val < total_bits else -1
        cmask = ~(width << beg_val)
        vmask = (value & width) << beg_val
        self.packed = (self.packed & cmask) | vmask

    def get_field(self, bel_val: int, size_val: int) -> int:
        width = (1 << size_val) - 1 if size_val < 64 else -1
        return (self.packed >> bel_val) & width
```

## Subtopics

### 64-bit Bit-packed Voxel Format
A compact 64-bit structure storing voxel metadata using bit fields, accessed via template-based bit set/get utilities. It packs Voxel Index (bits 0-15), State Bit (bit 15), Type Info (bits 16-31), and User Data (bits 32-63) into a single `uint64_t`. It is chosen when memory bandwidth is critical and metadata is sparse. The primary pitfall is the overlap of the State Bit (bit 15) with the Voxel Index field (bits 0-15), which can cause data corruption if not handled with proper masking [S4, unofficial].

## Operating characteristics
*   **Memory Complexity:**
    *   Layout A: 32 bytes/voxel. High memory usage, suitable for sparse octrees or raycasting where attributes are essential [S1, unofficial].
    *   Layout B: 4 bytes/voxel. 50% memory savings compared to fp32 density. Enables $32^3$ chunks to fit in 68 KB, improving cache efficiency [S2, unofficial].
*   **Time Complexity:**
    *   Access is $O(1)$ for direct indexing.
    *   Sorting/Layout A: $O(N \log N)$ if sorted by Morton code for cache-friendly traversal [S1, unofficial].
    *   Bit-Packed: $O(1)$ but with higher constant factor due to bit manipulation [S4, unofficial].
*   **Strengths:**
    *   Layout B is highly efficient for GPU job systems (e.g., Unity Burst) and terrain generation [S2, unofficial].
    *   Layout A supports high-fidelity visualization with normals and colors [S1, unofficial].
*   **Limitations:**
    *   Layout B's fp16 density may lack precision for scientific volume rendering [S2, unofficial].
    *   Layout C is immediate-mode and not suitable for large-scale dynamic scenes without instancing or meshing [S3, unofficial].
*   **When to Use:**
    *   Use Layout B for terrain, voxel games, or large-scale sparse volumes where memory is the bottleneck.
    *   Use Layout A for raycasting, visualization, or when surface normals/colors are required per voxel.
    *   Use Layout C for simple, static block rendering or prototyping [S1, S2, S3, unofficial].

## Background
The concept of voxel data structures originated with the need to represent 3D space in computer graphics and medical imaging. The specific implementations cited here reflect modern optimizations:
*   **Layout A** is derived from CPU-based voxel raycasters, emphasizing spatial locality via Morton codes [S1, unofficial].
*   **Layout B** stems from game engine development (e.g., Unity), leveraging job systems and burst compilation for real-time terrain generation [S2, unofficial].
*   **Layout C** is associated with OpenGL-based voxelizers and educational projects, focusing on immediate geometric rendering [S3, unofficial].
*   **Bit-Packed Variant** comes from high-performance spatial data structures (e.g., Rapid SVO), optimizing for cache efficiency in sparse voxel octrees [S4, unofficial].
