# Voxel Data Volume Storage and Access

Also called: Memory Zone Orientation, Native Voxel Array, Voxel Storage Orientation, VoxelDataVolume, VoxelGrid Data Layout & Access

## Overview
This method defines the memory layout and access patterns for dense voxel volumes, storing data in a single contiguous 1D array mapped from 3D coordinates [S1, unofficial]. It solves the problem of efficient spatial indexing and boundary validation by replacing multi-dimensional array overhead with linear memory access [S1, unofficial].

## How it works
**Inputs:**
- `Width`, `Height`, `Depth`: Integer dimensions defining the volume bounds [S1, unofficial].
- `T`: Generic data type for voxel content [S1, unofficial].

**Outputs:**
- A contiguous 1D array `_voxelData` of type `T` [S1, unofficial].
- Safe access to voxel values via index or coordinate [S1, unofficial].

**Data Structures:**
- `_voxelData`: A 1D array of size `Width * Height * Depth` [S1, unofficial].
- `Width`, `Height`, `Depth`: Fields storing the volume dimensions [S1, unofficial].
- `dims`: Optional array of 3 `uint32` elements for dimensions, alongside `data` flat array and `label` `uint32` [S3, unofficial].

**Index Calculation:**
3D coordinates $(x, y, z)$ are mapped to a 1D index using a (Z, Y, X) logical ordering to align with NumPy C-order contiguity, where $x$ varies fastest, then $y$, then $z$ [S2, unofficial]. The formula is:
$$
\text{index} = x + y \times \text{Width} + z \times \text{Width} \times \text{Height}
$$
This alignment avoids costly real-time 3D array transpositions on load [S2, unofficial].

**Steps:**
1. Allocate `_voxelData` with size `Width * Height * Depth` [S1, unofficial].
2. To access a voxel at $(x, y, z)$, compute `index` using the formula above [S3, unofficial].
3. Validate bounds: $0 \le x < \text{Width}$, $0 \le y < \text{Height}$, $0 \le z < \text{Depth}$ [S1, unofficial].
4. If valid, return `_voxelData[index]`; if invalid, return an error or default value [S1, unofficial].

**Pseudocode:**
```python
class VoxelVolume:
    def __init__(self, width: int, height: int, depth: int, data_type: type):
        self.width = width
        self.height = height
        self.depth = depth
        self._voxel_data = [data_type() for _ in range(width * height * depth)]

    def _xyz_to_index(self, x: int, y: int, z: int) -> int:
        """Map 3D coordinates to 1D index using C-order (X fastest, Z slowest) layout."""
        return x + y * self.width + z * self.width * self.height

    def try_get_voxel_data(self, index: int):
        """
        Safe access to voxel data by 1D index.
        Returns (True, value) if valid, (False, default) if out of bounds.
        """
        if 0 <= index < len(self._voxel_data):
            return True, self._voxel_data[index]
        return False, None

    def try_get_voxel_at(self, x: int, y: int, z: int):
        """
        Safe access to voxel data by 3D coordinates.
        Returns (True, value) if valid, (False, default) if out of bounds.
        """
        if not (0 <= x < self.width and 0 <= y < self.height and 0 <= z < self.depth):
            return False, None
        index = self._xyz_to_index(x, y, z)
        return self.try_get_voxel_data(index)
```

**Parameters:**
- `Width`, `Height`, `Depth`: Integer dimensions used for index calculation and bounds validation [S1, unofficial].
- `T`: Data type size affects memory usage; typical types include `byte` for density or `float` for scalar fields [S1, unofficial].

**Edge Cases and Pitfalls:**
- Direct access via computed index without bounds checking throws `IndexOutOfRangeException` [S1, unofficial].
- Safe access via `TryGetVoxelData` checks `index >= 0 && index < _voxelData.Length`, returns `false` on failure, and sets the output parameter to `default` (0 for byte types) [S1, unofficial].
- In some implementations, out-of-bounds access triggers a panic with a formatted error [S3, unofficial].
- Coordinate order must match the layout assumption (C-order: X fastest, Z slowest) [S2, unofficial].

## Operating characteristics
- **Time Complexity:** Index calculation is $O(1)$; access is $O(1)$ with bounds check [S1, unofficial].
- **Memory Complexity:** $O(\text{Width} \times \text{Height} \times \text{Depth})$ for contiguous storage [S1, unofficial].
- **Performance:** Contiguous layout enables cache-friendly access and efficient serialization [S2, unofficial].
- **Strengths:** Simple indexing, no pointer indirection, optimal for dense volumes [S2, unofficial].
- **Limitations:** Fixed memory allocation relative to volume dimensions [S1, unofficial].
- **When to Use:** Dense voxel grids where alignment with NumPy C-order contiguity is required [S2, unofficial].
- **When Not to Use:** Not given in the sources.

## Background
The layout aligns with NumPy C-order contiguity to avoid costly real-time 3D array transpositions on load, with coordinate mapping performed offline inside map maker and forge scripts [S2, unofficial]. The implementation uses a single contiguous native array for voxel data alongside dimension fields for bounds validation [S1, unofficial].
