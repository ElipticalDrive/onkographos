# Voxel Renderer with Top-Level Grid and Bricks

Also called: Brick-based voxel rendering with dynamic synchronization, Two-level grid structure with bricks

## Overview
This method renders voxel data using a two-level grid structure (top-level grid containing 8x8x8 voxel bricks) to optimize memory transfer and cache locality [S1, unofficial]. It solves the bottleneck of transferring large voxel datasets to the GPU by synchronizing only changed bricks and leveraging high internal GPU bandwidth for staging [S1, unofficial]. It differs from flat dense grid renderers by introducing spatial tiling for cache efficiency and dynamic update budgets [S1, unofficial].

## How it works
**Inputs:**
- Top-level grid data (8MB) [S1, unofficial].
- List of changed bricks (max 8192 bricks/frame) [S1, unofficial].
- Camera parameters for ray generation [G].

**Outputs:**
- Rendered image buffer [G].

**Data Structures:**
1. **Top-Level Grid:** Stored as a 3D image buffer on the GPU [S1, unofficial].
2. **Brick:** 8x8x8 voxels, 512 bytes total [S1, unofficial].
3. **Staging Buffer:** GPU memory buffer used for intermediate data transfer [G].
4. **Destination Buffer:** GPU 3D image buffer holding the final grid layout [S1, unofficial].

**Steps:**

1. **Data Synchronization:** Identify bricks that have changed since the last frame. Send these bricks to a staging buffer on the GPU. The budget is capped at 8192 bricks (512KB) per frame [S1, unofficial].
2. **Commit Kernel:** Execute a GPU kernel to copy data from the staging buffer to the final destination 3D image buffer. This utilizes `clEnqueueCopyBufferToImage` (or equivalent) which reformats data during the copy [S1, unofficial].
3. **Ray Traversal:** For each pixel, trace a primary ray through the screen plane. Use Amanatides and Woo’s 3D-DDA traversal algorithm to step through the top-level grid [S1, unofficial]. The traversal function `TraceRay` returns the hit voxel index or 0 if the ray leaves the scene, along with the intersection normal [S1, unofficial].
4. **Shading:** Shade the hit voxel using precalculated values for 6 unique hemispheres (corresponding to the 6 unique normals of axis-aligned voxels), integrated over a skydome [S1, unofficial].
5. **Optional Diffuse Bounce:** Perform a single diffuse bounce by distributing rays over the hemisphere using blue noise with limited length [S1, unofficial].

**Parameters:**
- Max bricks synchronized per frame: 8192 [S1, unofficial].
- Brick size: 8x8x8 voxels [S1, unofficial].
- Brick size in bytes: 512 bytes [S1, unofficial].

**Edge Cases:**
- **PCIe Bandwidth:** The method relies on the fact that GPU internal copy bandwidth (~320GB/s) is significantly higher than PCIe bus bandwidth (~16GB/s for PCI 3.0 x16), making the commit kernel fast [S1, unofficial].
- **Cache Locality:** The 8x8x8 brick size is chosen to fit in a handful of cache lines, optimizing for spatial locality regardless of ray direction [S1, unofficial].

## Operating characteristics
- **Performance:** Up to 1G Ray/s, producing over 60fps at 1600x900 resolution on a 2070 laptop GPU [S1, unofficial].
- **Memory Transfer:** Only changed bricks are sent to the GPU, capped at 512KB per frame (8192 bricks) [S1, unofficial].
- **Strengths:** High cache locality due to brick tiling; efficient use of GPU internal bandwidth for data updates; simple shading model using precalculated hemispheres [S1, unofficial].
- **Limitations:** Limited to axis-aligned voxel normals for the basic shading model; dynamic synchronization requires tracking changed bricks on the CPU [S1, unofficial].
