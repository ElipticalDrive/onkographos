# Voxel Material Packing

Also called: Voxel Data Packing, Voxel uint32_t layout

## Overview
Voxel Material Packing is a memory layout optimization that encodes a voxel's material ID and RGB color into a single 32-bit integer. This approach allows a renderer to fetch material properties and color data in a single memory access, reducing bandwidth and simplifying the ray-marching loop. It differs from [Voxel Data Layout](4076-voxel-data-layout.md) by strictly binding material identity and color to the voxel value itself, rather than storing them in separate structures or using indirect indexing for color.

## How it works
**Inputs:** Material ID (integer), Red channel (integer), Green channel (integer), Blue channel (integer).
**Outputs:** A single 32-bit unsigned integer (`uint32_t`).

**Data Structure:**
The 32-bit integer is divided into four 8-bit fields. The layout is big-endian in terms of significance (MSB first):
- Bits [31..24]: Material ID (8 bits)
- Bits [23..16]: Red channel (8 bits)
- Bits [15..8]: Green channel (8 bits)
- Bits [7..0]: Blue channel (8 bits)

**Constraints:**
- The Material Manager supports a maximum of 256 distinct materials, fitting within the 8-bit material ID field [S1, unofficial].

**Packing Formula:**
Given `mat_id`, `r`, `g`, `b` as 8-bit integers:
$$
\text{packed} = (\text{mat\_id} \ll 24) \ | \ (r \ll 16) \ | \ (g \ll 8) \ | \ b
$$

**Unpacking Formula:**
Given `packed`:
$$
\text{mat\_id} = (\text{packed} \gg 24) \ \& \ 0xFF
$$
$$
r = (\text{packed} \gg 16) \ \& \ 0xFF
$$
$$
g = (\text{packed} \gg 8) \ \& \ 0xFF
$$
$$
b = \text{packed} \ \& \ 0xFF
$$

**Pseudocode:**
```python
def pack_voxel_material(mat_id: int, r: int, g: int, b: int) -> int:
    """
    Packs material ID and RGB color into a single 32-bit integer.
    
    Args:
        mat_id: Material index (0-255)
        r: Red channel value (0-255)
        g: Green channel value (0-255)
        b: Blue channel value (0-255)
        
    Returns:
        Packed 32-bit integer
    """
    # Validate inputs are within 8-bit range
    if not (0 <= mat_id <= 255 and 0 <= r <= 255 and 0 <= g <= 255 and 0 <= b <= 255):
        raise ValueError("All components must be 8-bit values (0-255)")
        
    return (mat_id << 24) | (r << 16) | (g << 8) | b

def unpack_voxel_material(packed: int) -> tuple:
    """
    Unpacks a 32-bit integer into material ID and RGB color.
    
    Args:
        packed: Packed 32-bit integer
        
    Returns:
        Tuple of (mat_id, r, g, b)
    """
    mat_id = (packed >> 24) & 0xFF
    r = (packed >> 16) & 0xFF
    g = (packed >> 8) & 0xFF
    b = packed & 0xFF
    return (mat_id, r, g, b)
```

**Edge Cases and Pitfalls:**
- **Material Limit:** The system cannot support more than 256 materials without expanding the bit width or changing the layout [S1, unofficial].
- **Precision:** Since color is stored as 8-bit integers, dithering or compression artifacts may be visible if higher precision is required.
- **Byte Order:** The layout assumes a specific bit significance (MSB = Material ID). Endianness of the host system does not affect the logical bit positions if bitwise operations are used, but direct memory interpretation of the `uint32_t` must account for endianness if the integer is read as raw bytes.

## Subtopics

### Voxel Block Data Layout
A variant where the 32-bit integer stores voxel coordinates (x, y, z) rather than material properties. Bits 24–31 hold x, bits 16–23 hold y, and bits 8–15 hold z. The color is stored separately as an 8-bit palette index in the Block object, not packed into the integer [S2, unofficial]. Coordinates are packed using bitwise shifts and masks, with color passed as a second argument [S2, unofficial]. A pitfall in this layout is that while inline comments may list byte order as color, x, y, z, the implementation packs x, y, z into the integer with x as the most significant byte, and color is excluded from the integer [S2, unofficial].

## Operating characteristics
- **Memory Efficiency:** Uses 4 bytes per voxel for both material and color, which is efficient compared to storing separate arrays or using higher-precision floats.
- **Access Speed:** Single memory fetch retrieves both material ID and color, reducing cache misses and memory bandwidth usage during ray marching.
- **Limitations:** Limited to 256 materials and 8-bit color depth. Not suitable for scenes requiring high dynamic range or complex material definitions beyond ID and color.
- **When to Use:** Ideal for voxel-based ray tracers or renderers with a fixed, limited palette of materials where performance is critical and memory bandwidth is a bottleneck.

## Background
This method is used in voxel ray tracing implementations, such as the bad-apple-voxel-raytracer, where efficient material management is required for rendering voxel-based scenes [S1, unofficial]. It represents a common optimization in graphics programming where data locality and access patterns are optimized for parallel processing.
