# Dense grids and memory layout

Also called: Dense volume data structures, Regular grid storage, Voxel grid layout

## Overview
Dense grids and memory layout define how a continuous volumetric field $f(\mathbf{x})$ is discretized into a regular lattice and stored in linear memory. It solves the problem of mapping 3D spatial coordinates to hardware-accessible memory addresses while balancing spatial locality, memory overhead, and interpolation accuracy. It differs from [Compression](4-compression.md) by focusing on raw data placement rather than entropy reduction, and from [Non-regular volumes](9-non-regular-volumes.md) by enforcing a fixed, uniform topology where every cell in the bounding box exists, regardless of whether it contains data.

## Shared principles
All volume representations must support two fundamental operations: **storage** (mapping a field $f(\mathbf{x})$ to memory) and **query** (evaluating $f(\mathbf{x})$ at arbitrary coordinates $\mathbf{x}$). The choice of representation dictates the trade-off between spatial locality, memory overhead, and interpolation accuracy.

1.  **Domain Discretization:** The continuous domain $\Omega \subset \mathbb{R}^3$ is discretized into a set of elements or samples. For regular grids, this is a lattice $\mathbf{x}_{ijk} = \mathbf{x}_0 + i\Delta x \hat{i} + j\Delta y \hat{j} + k\Delta z \hat{k}$. For irregular volumes, it is a set of nodes and connectivity graphs.
2.  **Value Encoding:** Scalar values are stored as discrete integers or floating-point numbers. The precision (e.g., 8-bit unsigned, 16-bit float, 32-bit float) determines the dynamic range and quantization error [S1, unofficial].
3.  **Interpolation:** Since rays or query points rarely align with sample centers, values must be interpolated. Common kernels include:
    *   **Nearest Neighbor:** $V(P) = V(\text{round}(\mathbf{x}))$. Fast, discontinuous.
    *   **Trilinear:** $V(P) = \sum_{i,j,k \in \{0,1\}} w_i w_j w_k V_{ijk}$, where $w$ are distances to grid nodes. Continuous, first-order derivatives.
    *   **Higher-Order:** Bilinear/Bicubic splines or cubic convolution for smoother gradients [S1, S3, unofficial].
4.  **Coordinate Mapping:** A transformation maps world coordinates to texture/grid coordinates. For GPU rendering, this often involves normalizing coordinates to $[0, 1]$ for texture sampling [G].

## Subtopics

### [Evaluation Cache](874-evaluation-cache.md)
Evaluation Cache is a memory optimization technique that eliminates redundant computation by storing previously computed field values and their derivatives at shared grid locations. It differs from its siblings, which focus on spatial data layout (e.g., [Bricking](914-bricking.md)) or hardware texture sampling (e.g., [3D Texture Storage and Sampling](3064-3d-texture-storage-and-sampling.md)), by operating at the algorithmic level to cache the *results* of expensive evaluations rather than optimizing the *access* to the source data.

### [Bricking](914-bricking.md)
Bricking is a memory management technique for volume rendering that partitions a volumetric dataset larger than the available GPU memory (or texture unit limits) into smaller, fixed-size sub-volumes called "bricks". Each brick is loaded into GPU memory, rendered independently, and the resulting images are composited to form the final image. It differs from [Chunk-based Voxel Data Structure](1818-chunk-based-voxel-data-structure.md) by typically using uniform, fixed-size blocks optimized for texture sampling, and from [Tile-based Volume Ray Marching](1678-tile-based-volume-ray-marching.md) by operating on 3D spatial subdivisions rather than 2D screen tiles.

### [Tile-based Volume Ray Marching](1678-tile-based-volume-ray-marching.md)
Tile-based volume ray marching is a dense grid rendering technique that stores 3D volume data in a 1D texture array organized into tiles, using ray marching to sample the volume and composite the result using front-to-back accumulation. It solves the problem of mapping large 3D scalar fields onto 2D texture hardware by decomposing the Z-axis into discrete tiles, allowing efficient sampling via linear interpolation between adjacent tile slices. It is distinguished from standard 3D texture sampling by its explicit tile-indexing arithmetic and from bricking by its reliance on a 1D texture array layout with linear interpolation rather than discrete brick selection.

### [Spatial Indexing and Ordering](1797-spatial-indexing-and-ordering.md)
Spatial Indexing and Ordering provides the mechanisms to map multi-dimensional voxel coordinates to linear memory indices and to organize data in memory to maximize spatial locality for cache-coherent access. It solves the problem of inefficient memory access patterns in volume rendering by ensuring that spatially adjacent voxels are stored in adjacent memory locations, thereby reducing cache misses during ray marching and data loading. It sets itself apart from hierarchical indexing methods (like [Morton Code Generation for Octrees](4673-morton-code-generation-for-octrees.md)) by focusing on flat linearization and sorting strategies rather than tree-based culling, and from pure storage formats by defining the algorithmic mapping between logical space and physical memory.

### [Memory Layout Optimization](1798-memory-layout-optimization.md)
Memory Layout Optimization encompasses techniques for arranging volumetric data in linear memory to maximize bandwidth utilization, minimize cache misses, and eliminate hardware-level memory bank conflicts during ray casting. It solves the problem that standard row-major or column-major layouts suffer from poor spatial locality when rays traverse 3D volumes along arbitrary directions, leading to inefficient memory access patterns. What sets this family apart from its siblings is the focus on low-level data placement (bit interleaving, bank skewing, block packing) rather than high-level traversal algorithms or indexing structures; it builds on [Dense grids and memory layout](3-dense-grids-and-memory-layout.md) by defining exactly how the dense grid is laid out in bytes.

### [Chunk-based Voxel Data Structure](1818-chunk-based-voxel-data-structure.md)
The Chunk-based Voxel Data Structure organizes a 3D voxel grid into fixed-size 3D blocks (chunks) to enable spatial locality, flat array indexing, and incremental updates. It solves the problem of managing infinite or large-scale voxel worlds by dividing space into manageable units that can be independently meshed, serialized, and loaded/unloaded. Unlike dense grids that allocate memory for the entire world volume, or sparse octrees that use complex tree traversal, chunks provide a flat, predictable memory layout with constant-time access, trading some memory overhead for simplified meshing and I/O operations.

### [Global Uniform Data Layout](2955-global-uniform-data-layout.md)
Global Uniform Data Layout is a GPU buffer structure that aggregates global rendering state, camera matrices, and lighting parameters into a single uniform buffer object (UBO) or buffer texture buffer (SSBO) for efficient access by volume rendering shaders. It solves the problem of minimizing uniform buffer binding overhead and ensuring consistent data transmission from the CPU to the GPU for every draw call. It is distinguished from sibling methods like [Evaluation Cache](874-evaluation-cache.md) and [Bricking](914-bricking.md) by focusing on global control state rather than volumetric data storage or spatial indexing.

### [FCC Dataset Indexing Scheme](3200-fcc-dataset-indexing-scheme.md)
The FCC Dataset Indexing Scheme is a method for storing and accessing Four-Cubic Closest (FCC) lattice volume data on graphics hardware that lacks native support for non-Cartesian datasets. It solves the problem of efficiently mapping FCC voxel values to standard 3D texture units by packing four FCC lattice points into a single four-channel (RGBA) Cartesian 3D texture. This approach reduces memory footprint compared to storing each FCC point in a separate 1-channel texture, while avoiding the overhead of loading multiple separate textures or shifting layers. It sets itself apart from sibling methods like [Bricking](914-bricking.md) or [3D Texture Storage and Sampling](3064-3d-texture-storage-and-sampling.md) by specifically addressing the geometric irregularity of FCC lattices through a parity-based channel mapping.

### Frustum-shaped voxel buffers
**Definition:** A voxel buffer where voxel size adapts to distance from the camera: voxels close to the camera are small, those far away are large. These buffers are tied to a camera and follow camera animation [S2, unofficial].
**Layout:** Resolution in the XY plane is normally locked to camera resolution times a multiplier. The number of Z slices is a user parameter, usually on the order of a few hundred. When viewed from the camera, each row of voxels lines up perfectly with the projection of a pixel into the scene [S2, unofficial].
**Implementation:** The transform from world space to voxel space can be implemented by mapping world coordinates to the camera's 0..1 NDC space, then applying a local-to-voxel transform:
```cpp
void FrustumMapping::worldToVoxel(const V3f &wsP, V3f &vsP) {
    V3f nsP;
    m_camera->worldToNdc(wsP, nsP);
    localToVoxel(nsP, vsP);
}
```
**Comparison:** Can be combined with sparse buffers to optimize memory use. Since the coordinate transform is independent of the data structure used for voxel storage, this is straightforward, combining finer detail close to the camera with empty space optimization [S2, unofficial].

### Tiled Volume Textures
**Definition:** A DirectX 11.3/12 feature using hardware virtual addressing to load high-resolution 3D textures by only loading part of the texture onto the GPU at any given time, targeting memory issues while maintaining performance [S3, unofficial].
**Step:** Mark blocks of the texture as unused to maintain sparseness similar to SVOs/DAGs. The CPU must map tiles in the volume texture [S3, unofficial].
**Pitfall:** Dynamic Object Latency: Dynamic objects must flag bricks to the CPU, which takes a few frames to process, meaning dynamic objects may not be fully voxelized across brick bounds immediately [S3, unofficial].

### Z-curve Texture Memory Layout
**Definition:** A memory layout for 3D texture memory where z-curves (Morton order) are applied in each 2D slice to enhance spatial locality [S4].
**Formula:** Memory stride ratio along X, Y, Z axes is $1 : 2 : 6$. $Stride_X : Stride_Y : Stride_Z = 1 : 2 : 6$ [S4].
**Pitfall:** Taking samples across different 2D slices results in a big memory stride and low texture cache hit rates. Taking samples on the same 2D slice is expected to yield good texture cache performance [S4].

### Z-order Curve Flattening
**Definition:** A flattening function that converts 3D voxel coordinates to a 1D index, placing voxels nearby in space nearby in memory to improve GPU cache locality [S5, unofficial].
**Performance:** 102 FPS at 2048^3 grid resolution and 1000x1000 screen resolution, which is over 8 times faster than the original 12 FPS [S5, unofficial].
**Comparison:** Compared to standard flattening (layer-by-layer), Z-order curve improves memory performance by increasing the likelihood that the next voxel in traversal is already in cache and that nearby rays access the same memory [S5, unofficial].

### BCC Grid Rendering
**Definition:** Using a Body-Centered Cartesian (BCC) grid instead of a cubic Cartesian (CC) grid to reduce the number of required sample points while maintaining lossless compression for spherically bandlimited signals [S6, unofficial].
**Step:** Apply all usual point rendering methods. Shift slices by 1/2 when rendering BCC grids [S6, unofficial].
**Performance:** BCC grid reduces required point samples to 70.3% of cubic grid; 4D BCC requires 50% of equivalent 4D cubic grid samples [S6, unofficial]. Neophytou '02: Turbulent Jet 4D BCC rendered in 1.01s (71% of CC time) with 138 time steps vs 99 for CC [S6, unofficial].

## Background
The use of dense grids for volume rendering dates back to the early 1990s, with the first 3D texture-based implementation of ray-casting by Levoy (1988), Cullip and Neumann (1993), and Cabral et al. (1994) [S4]. Early methods relied on view-aligned or axis-aligned 2D texture arrays. As hardware evolved, the focus shifted to optimizing memory access patterns, leading to the development of Z-order (Morton) curve flattening to improve cache locality [S4]. Modern implementations leverage GPU-specific features like Tiled Resources (DirectX 11.3+) and specialized indexing schemes (FCC, BCC) to handle larger datasets and irregular lattices [S3, S6, unofficial].
