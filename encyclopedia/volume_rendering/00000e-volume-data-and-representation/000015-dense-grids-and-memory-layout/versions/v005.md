# Dense grids and memory layout

Also called: Regular grids, Voxel grids, Cartesian grids

## Overview
Dense grids store volumetric data as a rectangular mesh of voxels, mapping a continuous field $f(\mathbf{x})$ to a discrete lattice $\mathbf{x}_{ijk}$ [S1, unofficial]. This representation solves the problem of efficient spatial evaluation and disk storage when analytical equations are too slow or unavailable [S1, unofficial]. It sets itself apart from sparse representations (like [Octree](../octree.md)) by guaranteeing $O(1)$ access and hardware acceleration support at the cost of cubic memory complexity, making it ideal for dense, editable, or uniformly sampled data [S3].

## Shared principles
All dense grid implementations share the following mechanisms:

1.  **Domain Discretization:** The continuous domain $\Omega \subset \mathbb{R}^3$ is discretized into a lattice $\mathbf{x}_{ijk} = \mathbf{x}_0 + i\Delta x \hat{i} + j\Delta y \hat{j} + k\Delta z \hat{k}$ for $i,j,k \in \{0, \dots, M-1\}$ [S1, unofficial]. The grid dimensions $M$ define the upper bound indices [S1, unofficial].
2.  **Value Encoding:** Values are stored as discrete integers or floats. Common formats include 8-bit unsigned integers (e.g., material IDs) [S3], 16-bit floats (e.g., density/pressure) [S2, unofficial], or 32-bit floats [G].
3.  **Linear Indexing:** Multi-dimensional coordinates $(x,y,z)$ are mapped to a 1D linear index $I$ for storage in contiguous arrays. The standard row-major formula is $I = x + y \cdot S_x + z \cdot S_x \cdot S_y$, where $S_x, S_y$ are strides derived from grid dimensions [S3].
4.  **Interpolation:** Since query points rarely align with sample centers, values are interpolated. Trilinear interpolation is standard for GPU textures, computed as $V(\mathbf{p}) = \sum_{i,j,k \in \{0,1\}} w_i w_j w_k V_{ijk}$ [G].

## Subtopics

### [Evaluation Cache](874-evaluation-cache.md)
Caches evaluation results (field value and gradient) keyed by quantized grid positions to ensure each geometric corner is processed only once, primarily in manifold dual contouring. It sets itself apart from siblings by focusing on spatial coherence at geometry boundaries rather than temporal coherence along a ray.

### [Dual Grid Traversal](1233-dual-grid-traversal.md)
Generates isosurfaces by constructing a mesh on a grid shifted relative to the input data. Dual vertices are placed at primal cell centers, ensuring mesh vertices correspond directly to data values without interpolation. It differs from standard marching cubes by operating on a shifted lattice where each dual vertex is influenced by a 3x3x3 neighborhood in the primal grid.

### [Tile-based Volume Ray Marching](1678-tile-based-volume-ray-marching.md)
A GPU-accelerated technique partitioning the 3D volume into a 1D texture array organized by Z-tiles. It solves inefficient memory access by aligning texture storage with the traversal order of rays along the Z-axis, improving spatial locality. It is distinguished from standard 3D texture sampling by its explicit 1D array indexing scheme for Z-tiles.

### [Spatial Indexing and Ordering](1797-spatial-indexing-and-ordering.md)
Maps multi-dimensional coordinates into linear memory structures to optimize spatial locality and cache coherence. It solves the problem of inefficient random access by ensuring spatially neighboring voxels are stored in adjacent memory locations, using space-filling curves (SFCs) like Morton codes or Hilbert curves to preserve locality better than arithmetic strides.

### [Memory Layout Optimization](1798-memory-layout-optimization.md)
Arranges volumetric data in contiguous memory buffers to maximize spatial locality and minimize cache misses or SDRAM bank conflicts. It solves the problem where naive linear indexing causes cache thrashing. It sets itself apart from siblings by focusing exclusively on the physical storage arrangement of the voxel data itself.

### [Chunk-based Voxel Data Structure](1818-chunk-based-voxel-data-structure.md)
Divides a large 3D voxel world into fixed-size 3D blocks (chunks) to manage memory usage and update locality. It solves the problem of unbounded memory consumption by allowing operations on manageable units. It differs from [Sparse Voxel Octree Representation](2340-sparse-voxel-octree-representation.md) by using fixed-size dense arrays per chunk rather than hierarchical tree structures.

### [3D Texture Representation (CPU/GPU Indexing)](2393-3d-texture-representation-cpu-gpu-indexing.md)
Stores voxel data in a dense 3D texture or equivalent linear array with dimensions matching the voxel grid. It fully leverages hardware acceleration for 3D textures, including caching and filtering, offering high runtime performance but low memory efficiency due to its inability to address sparse memory.

### [Global Uniform Data Layout](2955-global-uniform-data-layout.md)
A GPU buffer structure used to transmit global rendering state, camera parameters, and lighting configurations from the CPU to volume rendering shaders. It solves the problem of efficiently passing per-frame constants without frequent buffer updates. It is distinguished from sibling methods by its focus on scalar and matrix constants rather than volumetric density data.

### [3D Texture Storage and Sampling](3064-3d-texture-storage-and-sampling.md)
Stores volumetric data directly in GPU 3D texture resources, leveraging hardware-optimized memory layouts and sampling units. It solves the problem of inefficient CPU-side or naive GPU-side memory access patterns by utilizing sophisticated hardware caching and interpolation mechanisms superior to software-implemented Z-order curves.

### [FCC Dataset Indexing Scheme](3200-fcc-dataset-indexing-scheme.md)
Stores Four-Cubic Closest (FCC) lattice volume data on graphics hardware lacking native support for non-Cartesian datasets. It maps the non-Cartesian lattice into a four-channel (RGBA) 3D texture, avoiding the overhead of shifting layers. It sets itself apart by specifically addressing the geometric structure of FCC lattices through a parity-based channel mapping.

### [Density Bitfield Packing](3788-density-bitfield-packing.md)
Compresses a floating-point density grid into a binary bitfield to accelerate volume ray marching by enabling efficient empty-space skipping. It differs from siblings by operating at the voxel level to create a compact spatial index of occupied vs. empty regions, rather than caching shader results or organizing data into hierarchical bricks.

### [Brick-based storage and caching](4138-brick-based-storage-and-caching.md)
Decomposes volumetric datasets larger than available GPU texture memory into smaller, fixed-size sub-volumes called bricks, enabling out-of-core visualization. It solves the hardware limitation where a single 3D texture cannot hold the entire volume. It sets itself apart by explicitly managing the cache lifecycle (e.g., LRU replacement) and handling boundary interpolation via overlap.

### [VDB Data Loading & 3D Texture Setup](4880-vdb-data-loading-3d-texture-setup.md)
Loads a VDB-formatted binary file, parses its sparse voxel coordinates and tile data, and uploads the resulting density field as a 3D texture for GPU rendering. It bridges the gap between CPU-side sparse data structures and the GPU's dense 3D texture sampling capabilities. Unlike [Bricking](914-bricking.md) which manages hierarchical tiling for streaming, this method typically loads the entire sparse dataset into a single dense volume texture.

### [3D Transfer Function Texture Layout](5646-3d-transfer-function-texture-layout.md)
Defines the memory layout and storage requirements for hardware-based volume rendering using multi-dimensional transfer functions (MTFs). It addresses the problem that graphics hardware cannot compute transfer function variables (such as gradient magnitude) on the fly, requiring all necessary classification variables to be pre-computed and stored at each voxel sample point.

#### Frustum-shaped voxel buffers
A voxel buffer where voxel size adapts to distance from the camera: voxels close to the camera are small, those far away are large. Tied to a camera and follow camera animation [S4, unofficial]. Resolution in the XY plane is normally locked to camera resolution times a multiplier, with Z slices being a user parameter (usually a few hundred). When viewed from the camera, each row of voxels lines up perfectly with the projection of a pixel into the scene [S4, unofficial]. The transform from world space to voxel space can be implemented as:
```cpp
void FrustumMapping::worldToVoxel(const V3f &wsP, V3f &vsP) {
    V3f nsP;
    m_camera->worldToNdc(wsP, nsP);
    localToVoxel(nsP, vsP);
}
```
It can be combined with sparse buffers to optimize memory use, combining finer detail close to the camera with empty space optimization [S4, unofficial].

#### Tiled Volume Textures
A DirectX 11.3/12 feature using hardware virtual addressing to load high-resolution 3D textures by only loading part of the texture onto the GPU at any given time, targeting memory issues while maintaining performance [S5, unofficial]. Blocks of the texture are marked as unused to maintain sparseness similar to SVOs/DAGs. The CPU must map tiles in the volume texture. Dynamic objects must flag bricks to the CPU, which takes a few frames to process, meaning dynamic objects may not be fully voxelized across brick bounds immediately [S5, unofficial].

#### Z-curve Texture Memory Layout
A memory layout for 3D texture memory where z-curves (Morton order) are applied in each 2D slice to enhance spatial locality [S6]. The memory stride ratio along X, Y, Z axes is $1 : 2 : 6$ ($Stride_X : Stride_Y : Stride_Z = 1 : 2 : 6$) [S6]. Taking samples across different 2D slices results in a big memory stride and low texture cache hit rates, while taking samples on the same 2D slice yields good performance [S6].

#### Z-order Curve Flattening
A flattening function that converts 3D voxel coordinates to a 1D index, placing voxels nearby in space nearby in memory to improve GPU cache locality [S7, unofficial]. Compared to standard flattening (layer-by-layer), Z-order curve improves memory performance by increasing the likelihood that the next voxel in traversal is already in cache and that nearby rays access the same memory. Performance gains can be significant (e.g., 102 FPS at $2048^3$ grid resolution vs 12 FPS for standard flattening) [S7, unofficial].

#### BCC Grid Rendering
Using a Body-Centered Cartesian (BCC) grid instead of a cubic Cartesian (CC) grid to reduce the number of required sample points while maintaining lossless compression for spherically bandlimited signals [S8, unofficial]. BCC grid reduces required point samples to 70.3% of cubic grid; 4D BCC requires 50% of equivalent 4D cubic grid samples [S8, unofficial]. Rendering requires shifting slices by 1/2 [S8, unofficial].

#### MERF Scene Representation
Represents a scene using a low-resolution 3D voxel grid and three high-resolution 2D grids (one for each cardinal plane) to store feature vectors. The continuous field is the sum of trilinearly interpolated 3D values and bilinearly interpolated 2D values [S9]. Query eight neighbors on the low-resolution 3D grid and project the location onto the three axis-aligned planes, querying four neighbors on each high-resolution 2D grid. The feature vector sum is $t(x, y, z) = V(x, y, z) + P_x(x, y) + P_y(x, z) + P_z(y, z)$, where $V$ is trilinear interpolation and $P$ is bilinear interpolation [S9]. Grid Structure: One low-resolution 3D voxel grid $V$ of size $N_v \times N_v \times N_v$. Three high-resolution 2D grids $P_x, P_y, P_z$ of size $N_h \times N_h$. Each element stores a vector with $d = 4 + d_f$ channels. Default $N_v = 512$, $N_h = 2048$, $d_f = 8$ (so $d=12$) [S9].

## Background
Dense grids are the foundational representation for volume rendering, preferred when analytical equations are too slow to evaluate or when data is inherently discrete (e.g., simulation outputs) [S1, unofficial]. The approach allows for efficient ray marching and disk storage [S1, unofficial]. Early implementations relied on simple 3D textures [S6]. Modern applications, such as the game *Teardown*, use dense grids for every shape, storing each voxel as a single byte indexing a material palette, which allows for fast access and editing but does not scale to planetary sizes due to memory constraints [S3]. To mitigate this, engines often move to brick-based or sparse structures, though dense grids remain the standard for GPU-accelerated rendering pipelines due to hardware texture sampling support [S3].
