# Priority Queue Based Field Update


## Overview
Priority Queue Based Field Update is a scheduling mechanism for hierarchical volume data structures that ensures field modifications are applied from coarser levels to finer levels [S1]. It solves the problem of visual inconsistency in interactive volume sculpting, where a depth-first recursive update would modify fine details before their coarser parents are adjusted, violating the hierarchical dependency required for correct resolution-adaptive rendering [S1]. Unlike sibling methods that handle memory management or texture uploads, this method specifically manages the temporal and spatial order of geometric updates using a priority queue of cell queues [S1].

## How it works
The method replaces the standard recursive application of tools on a hierarchical volume structure with an asynchronous, priority-driven workflow [S1]. It guarantees that for any given tool action, all cells at level $L$ are updated before any cells at level $L+1$ are processed, regardless of the tree's branching factor or the specific geometry of the tool's intersection [S1].

### Inputs and Outputs
*   **Input:** A Tool/Action couple applied to a hierarchical volume structure (e.g., Sparse Voxel Octree) [S1].
*   **Output:** A modified volume state where all affected cells are updated according to the tool's effect, respecting the coarse-to-fine update order [S1].

### Data Structures

**1. ToolCopy**
A frozen copy of the tool at application time [S1]. It contains state information (position, orientation, scale, color, etc.), a reference to the tool and action involved, and a unique identifier (an integer acting as a time-counter/timestamp) [S1].

**2. Cell-Queue**
A simple queue with constant-time pushback and popfront operations [S1]. It temporarily stores cells intersected by the tool from one level to the next [S1]. It is indexed by a ToolCopy and the size of the cells it contains [S1].

**3. Level Manager Priority Queue**
The central scheduler enclosing queueing internals [S1]. Elements are Cell-queues rather than individual ToolCopies, allowing direct insertion and handling of cell-queues inside the manager [S1]. It is sorted on the level addressed (cell size) and the tool/action concerned to ensure updates proceed from coarser to finer levels [S1]. The implementation uses a standard priority queue structure (e.g., STL priority queue relying on a vector by default) [S1].

### Algorithm Steps

1.  **Initialization:** When a user applies a tool, the Level Manager creates a ToolCopy from the Tool/Action couple and inserts it with the current root-cell's size into its priority queue [S1]. This is done by creating one Cell-queue containing only the current root-cell and inserting it into the Level Manager [S1].
2.  **Update Loop:** An update-thread created at startup empties the priority queue of the Level Manager in the background [S1].
3.  **Processing:** The update-thread extracts the highest-priority Cell-queue. For each cell in the queue, the Apply procedure is executed [S1]. The Apply procedure receives a Cell-queue as an extra parameter [S1]. It updates internal vertices and subdivides if needed, then instead of recursively calling Apply on existing children, it identifies all child cells that intersect the tool and appends them to the provided Cell-queue for the next level [S1].
4.  **Queue Insertion & Interruption:** After processing a level, the populated Cell-queue for the next level is inserted into the Level Manager priority queue [S1]. If a coarser level is inserted into the manager while processing a Cell-queue, the current processing is interrupted [S1]. The interrupted Cell-queue is re-inserted in the manager priority queue and handled from where it was suspended when the task returns [S1].
5.  **Simplification & Suspension:** When the priority queue of Cell-queues becomes empty, the update-thread conducts the simplification step [S1]. Once achieved, the update-thread suspends using the blocking facility of lock system calls to save processor resources [S1].
6.  **Threading & Synchronization:** Two threads are used: an update-thread and a user interaction thread [S1]. Blocking access is limited to insertion and removal of Cell-queues in the Level Manager priority queue, handled via a classical locking mechanism [S1]. The update process is the only one accessing the Cell-queues it empties or fills; the draw process accesses Cells through the hierarchy, so no exclusion mechanism is needed inside Cell-queues [S1].

### Parameters and Edge Cases
*   **Threading:** The system uses two threads: an update thread and a user interaction thread [S1].
*   **Synchronization:** Blocking access is limited to the insertion and removal of `Cell-Queue` objects in the `Level Manager`. The update process is the sole accessor of the `Cell-Queue` it is currently processing, so no internal locking is needed within the queues themselves [S1].
*   **Interruption:** If a coarser level is inserted while a finer level is being processed, the finer level's queue is suspended and re-queued. This ensures correctness by enforcing the coarse-to-fine dependency [S1].
*   **Tool Overlap:** The system can handle multiple tools acting on the field simultaneously if they are inserted as separate entries in the priority queue, though the primary implementation assumes sequential tool application [S1].

## Operating characteristics
*   **Time Complexity:** The complexity is dominated by the tree traversal required to find intersecting cells. By using `Cell-Queues`, the method avoids re-walking the hierarchy from the root for every level, reducing the overhead of intersection tests [S1].
*   **Memory Complexity:** Requires additional memory for the `Level Manager` priority queue and the temporary `Cell-Queue` objects [S1].
*   **Performance:** The two-thread approach minimizes blocking and deadlock risks. The update thread runs in the background, allowing the user interface to remain responsive. The use of standard threading primitives (Posix, Windows, IRIX sprocs) has no remarkable speed impact [S1].
*   **Strengths:** Guarantees coarse-to-fine update order, essential for visual consistency in interactive sculpting. Handles interruptions gracefully.
*   **Limitations:** Introduces latency between user input and visual feedback due to the asynchronous background processing. The priority queue management adds a small overhead compared to direct recursive application, but this is offset by the avoidance of redundant hierarchy walks [S1].

## Background
The method was introduced by Eric Ferley, Marie-Paule Cani, and Jean-Dominique Gascuel in their work on "Resolution Adaptive Volume Sculpting" [S1]. It addresses the limitations of recursive field update methods, which fail to maintain visual consistency during interactive editing because they do not respect the hierarchical dependency of coarse-to-fine updates [S1]. The approach was implemented and tested on various operating systems including IRIX, Linux, and Windows NT/2000 [S1].
