# Octree Memory Size Calculation

Also called: Full octree size, Geometric series octree size

## Overview
Calculates the maximum memory footprint of a 100% dense octree by summing the number of nodes at every level up to the maximum depth and multiplying by the size of a single octant [S1, unofficial]. It serves as a strict upper bound for buffer allocation in naive octree implementations where the tree is guaranteed to be fully populated [S1, unofficial]. Builds on [Octree Data Structure Layout](4518-octree-data-structure-layout.md).

## How it works
**Inputs:**
*   `depth` ($n$): The maximum depth of the octree (integer $> 0$) [S1, unofficial].
*   `octantSize`: The size of a single octant (node) in bytes [S1, unofficial].

**Outputs:**
*   `totalBytes`: The total memory required for a fully dense octree of the given depth [S1, unofficial].

**Data Structures:**
No complex data structures are required for the calculation itself; it is a pure arithmetic computation [G]. The result is typically used to allocate a contiguous linear memory block, such as an `ArrayBuffer` [S1, unofficial].

**Steps:**
1.  Calculate the total number of nodes $S(n)$ in a full octree of depth $n$ using the closed-form geometric series sum formula [S1, unofficial]:
    $$ S(n) = \frac{8^{n+1} - 1}{7} $$
    Where $n$ is the maximum depth [S1, unofficial].
2.  Multiply $S(n)$ by `octantSize` to obtain the total memory footprint in bytes [S1, unofficial]:
    $$ \text{totalBytes} = S(n) \times \text{octantSize} $$

**Parameters:**
*   `depth` ($n$): The maximum depth of the tree. Standard floating-point arithmetic loses precision for $n > 24$ [S1, unofficial].
*   `octantSize`: The size of a single octant in bytes. In the reference implementation, this is hardcoded to 8 bytes [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision Errors:** For depths greater than 24, standard floating-point exponentiation may produce incorrect node counts due to precision loss [S1, unofficial]. Implementers should use integer arithmetic or arbitrary-precision libraries for deep trees [G].
*   **Zero Depth:** The reference implementation explicitly throws an error if `depth` is 0, so the formula is not evaluated for that case [S1, unofficial].
*   **Buffer Alignment:** The calculated size is often rounded up to the nearest power of two to satisfy GPU texture binding or memory alignment requirements [S1, unofficial].

**Pseudocode:**
```python
def calculate_full_octree_size(depth: int, octant_size: int) -> int:
    """
    Calculates the maximum memory footprint of a 100% dense octree.
    
    Args:
        depth: The maximum depth of the octree (n). Must be > 0.
        octant_size: The size of a single octant in bytes.
        
    Returns:
        The total number of bytes required for a fully dense octree.
    """
    if depth <= 0:
        raise ValueError("Depth must be greater than 0")
        
    # Calculate sum of nodes using geometric series formula: S(n) = (8^(n+1) - 1) / 7
    # Using integer arithmetic to avoid floating-point precision errors for depth > 24
    total_nodes = (8 ** (depth + 1) - 1) // 7
    
    return total_nodes * octant_size
```

## Subtopics

### Octree Reductions
A GPU-based reduction algorithm to determine the exact number of internal and leaf nodes in a pointer octree (or quadtree) to calculate memory requirements for dynamic, sparse data structures [S2, unofficial]. Unlike the full dense calculation, this method counts only the nodes that actually exist [S2, unofficial].
*   **Leaf Nodes:** Apply a standard summation reduction to the data set to determine the number of nonzero values per brick [S2, unofficial]. The reduction stops at the first level to identify empty bricks (e.g., if a brick sums to 0, it is empty) [S2, unofficial].
*   **Internal Nodes:** Use a customized internal node reduction [S2, unofficial]. On the first level, check if all leaf nodes in a subtree are zero [S2, unofficial]. If they are, start the reduction with 0; if not, start with 1 [S2, unofficial]. On every subsequent reduction level, sum the child values and add 1 for the internal node if at least one child is non-zero [S2, unofficial]. The final step returns the total number of internal nodes [S2, unofficial].
*   **2x2x2 Leaf Bricks:** For octrees where leaf nodes contain 2x2x2 bricks, apply the initial internal node reduction step one additional time before calculating the final number of leaves and internal nodes to determine if a leaf brick contains at least one value [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(1)$ arithmetic operations [G].
*   **Memory Complexity:** $O(1)$ auxiliary space for the calculation itself [G].
*   **Strengths:** Simple, fast, and provides a strict upper bound for buffer allocation [S1, unofficial].
*   **Limitations:** Highly inaccurate for sparse data, overestimating memory usage by orders of magnitude [G]. Precision issues arise for depths $> 24$ with standard floating-point types [S1, unofficial].
*   **When to use:** When allocating a fixed-size buffer for a dense octree or when a safe upper bound is required before dynamic allocation [S1, unofficial].

## Background
The geometric series formula for octree node counts is a standard mathematical result in computer graphics [G]. The specific implementation details, including the JavaScript function `sump8` and the warning about precision errors at depth 24, originate from the `voctopus` library [S1, unofficial]. The GPU-based reduction method for sparse octrees was developed to optimize memory usage for dynamic data structures on the GPU, as described in the thesis "Eine adaptive, hybride Datenstruktur für Volumen Datensätze auf der GPU" [S2, unofficial].
