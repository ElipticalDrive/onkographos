# Chunking
Also called: Voxel Chunking
## Overview
Chunking manages large voxel worlds by dividing the voxel space into fixed-size, axis-aligned blocks (chunks), trading faster meshing for more draw calls [S1, unofficial]. It builds on [Chunk-Based World Storage](2858-chunk-based-world-storage.md) by providing the spatial granularity for efficient mesh generation and culling. Unlike sibling methods that focus on loading/unloading logic or coordinate mapping, chunking specifically addresses the meshing performance bottleneck in dense voxel environments [S1, unofficial].
## How it works
Chunking partitions the global voxel grid into non-overlapping, fixed-dimension blocks. Each chunk is processed independently for mesh generation (e.g., via greedy meshing) and rendering.

**Inputs:**
- Global voxel data structure (dense grid or sparse hash map).
- Chunk dimensions ($W, H, D$).

**Outputs:**
- A list of renderable mesh objects, one per chunk (or per visible chunk).

**Data Structures:**
- **Chunk:** A fixed-size 3D array of voxel types.
  - Layout: `VoxelType[width][height][depth]` or flattened `VoxelType[width * height * depth]`.
  - Size: Determined by chunk dimensions.
- **World Map:** A hash map or sparse array mapping chunk coordinates $(cx, cy, cz)$ to Chunk objects.

**Steps:**
1. **Partitioning:** Divide the world into chunks. For a world of size $W_{world} \times H_{world} \times D_{world}$ and chunk size $W_c \times H_c \times D_c$, the number of chunks is $\lceil W_{world}/W_c \rceil \times \lceil H_{world}/H_c \rceil \times \lceil D_{world}/D_c \rceil$.
2. **Meshing:** For each chunk, generate a mesh from its voxel data. Common algorithms include greedy meshing, which merges adjacent coplanar faces of the same voxel type to reduce triangle count [S1, unofficial].
3. **Culling:** Discard chunks that are entirely empty or fully opaque and occluded by other chunks (visibility check).
4. **Rendering:** Submit the mesh of each visible chunk to the graphics API as a separate draw call.

**Parameters:**
- **Minecraft-style:** $16 \times 16 \times 256$ (divided vertically into smaller segments for rendering) [S1, unofficial].
- **Demo Engine:** $32 \times 32 \times 32$ [S1, unofficial].
- **Typical Values:** $16-32$ units per side is common to balance draw call overhead vs. meshing complexity.

**Edge Cases:**
- **Boundary Chunks:** Chunks at the world edge may be partially empty. The meshing algorithm must handle missing neighbors correctly (treating out-of-bounds voxels as empty or air).
- **Precision:** Coordinate translation from world space to chunk-local space must be exact to avoid artifacts at chunk boundaries.
- **Draw Call Overhead:** Small chunks increase the number of draw calls, potentially bottlenecking the CPU [S1, unofficial].

## Subtopics

### Chunk-based Rendering (Minecraft Style)
A spatial partitioning strategy specific to voxel engines like Minecraft, using 2D chunks (planes) rather than 3D octrees, leveraging the fact that visibility checks are simpler and more efficient in the X-Y plane [S2, unofficial]. Compared to octrees, chunks reduce computation complexity because 2D visibility checks are simpler than 3D checks, and the horizontal plane typically contains more visible surfaces [S2, unofficial]. This approach is chosen when the view is primarily horizontal and 2D culling offers significant performance gains over 3D tree traversal [S2, unofficial].

## Operating characteristics
- **Time Complexity:** Meshing is $O(N)$ where $N$ is the number of voxels in the chunk. Rendering is $O(C)$ where $C$ is the number of visible chunks (draw calls).
- **Memory Complexity:** $O(W \times H \times D)$ for the voxel data, plus overhead for chunk metadata.
- **Measured Performance:** Fewer draw calls than per-voxel rendering, but more than octree-based rendering. Greedy meshing significantly reduces polygon count [S1, unofficial].
- **Strengths:** Simple implementation, efficient meshing for large flat areas, easy to parallelize chunk processing.
- **Limitations:** High draw call count for small chunks; less efficient for highly irregular or sparse 3D structures compared to octrees.
- **When to Use:** Large, dense voxel worlds with significant horizontal surface area (e.g., terrain).
- **When Not to Use:** Sparse 3D structures or scenes requiring fine-grained occlusion culling where octrees excel.

## Background
Chunking originated in voxel game engines like Minecraft to handle massive voxel worlds efficiently [S1, unofficial]. It was adopted to balance the computational cost of mesh generation with the overhead of rendering many small objects. The technique is widely used in voxel-based games and simulations where deterministic world generation and simple spatial partitioning are prioritized [S1, unofficial].
