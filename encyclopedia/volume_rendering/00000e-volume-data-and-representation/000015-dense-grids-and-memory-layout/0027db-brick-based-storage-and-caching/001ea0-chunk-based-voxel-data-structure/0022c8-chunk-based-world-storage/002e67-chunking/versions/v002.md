# Chunking
Also called: Voxel Chunking
## Overview
Chunking manages large voxel worlds by dividing them into fixed-size chunks, trading faster meshing for more draw calls [S1, unofficial].
## How it works
**Inputs and Outputs:** Not given in the sources.
**Data Structures:** Not given in the sources.
**Steps:**
1. Partition the global voxel world into fixed-size, axis-aligned chunks [S1, unofficial].
2. Apply greedy meshing to each chunk, which scans across voxel slices and merges faces of adjacent voxels of the same value [S1, unofficial].
3. Render the resulting chunk meshes, accepting the inherent tradeoff of more draw calls for faster meshing [S1, unofficial].
**Formulas:** Not given in the sources.
**Parameters:**
- Minecraft-style: $16 \times 16 \times 256$, divided vertically [S1, unofficial].
- Demo engine: $32 \times 32 \times 32$ [S1, unofficial].
**Edge Cases and Pitfalls:**
- The technique inherently trades faster meshing for a higher number of draw calls [S1, unofficial].
## Subtopics

### Chunk-based Rendering (Minecraft Style)
A spatial partitioning strategy specific to voxel engines like Minecraft, using 2D chunks (planes) rather than 3D octrees, leveraging the fact that visibility checks are simpler and more efficient in the X-Y plane [S2, unofficial]. Compared to octrees, chunks reduce computation complexity because 2D visibility checks are simpler than 3D checks, and the horizontal plane typically contains more visible surfaces [S2, unofficial]. This approach is chosen when the view is primarily horizontal and 2D culling offers significant performance gains over 3D tree traversal [S2, unofficial].
