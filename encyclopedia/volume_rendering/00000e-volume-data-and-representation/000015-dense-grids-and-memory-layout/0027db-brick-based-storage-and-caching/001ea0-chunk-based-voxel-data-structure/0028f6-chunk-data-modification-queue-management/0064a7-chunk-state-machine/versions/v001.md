# Chunk State Machine

Also called: Chunk Processing State Flags

## Overview
The Chunk State Machine manages the lifecycle of individual voxel chunks within a brick-based volume rendering system, tracking their processing status through a series of bitwise flags [S1, unofficial]. It operates in conjunction with the parent [Chunk Data Modification & Queue Management](4427-chunk-data-modification-queue-management.md) to ensure that mesh generation and rendering occur only when chunks are in a valid state, preventing race conditions during asynchronous updates. It is distinct from the broader Volume State Management, which handles global volume lifecycle events such as loading and texture allocation [S2, unofficial].

## How it works
The method relies on a single byte per chunk to store its state using specific bitwise flags. The system transitions chunks between states based on meshing operations, visibility checks, and global volume events.

**Inputs and Outputs:**
- Input: Chunk identifier, current state byte, event trigger (e.g., mesh complete, visibility change).
- Output: Updated state byte, queue actions (e.g., add to render queue, mark dirty).

**Data Structures:**
The state is stored in a single byte (`uint8`) using the following flags [S1, unofficial]:
- `V3_C_NONE (0x00)`: Initial or reset state.
- `V3_C_WAITING (0x01)`: Chunk is queued for processing.
- `V3_C_BUILT (0x02)`: Voxel data structure is built.
- `V3_C_READY (0x04)`: Chunk is ready for meshing.
- `V3_C_MESHED (0x08)`: Mesh geometry has been generated.
- `V3_C_IN_VIEW (0x10)`: Chunk is currently within the camera frustum.
- `V3_C_GLOBY (0x20)`: Chunk is marked for global update.
- `V3_C_MESHING (0x40)`: Mesh generation is in progress.
- `V3_C_REMESH (0x80)`: Chunk requires remeshing due to data changes.

**Steps:**
1. **Initialization**: Set chunk state to `V3_C_NONE`.
2. **Queuing**: When a chunk is modified or needs processing, set `V3_C_WAITING` and add to the modification queue [S1, unofficial].
3. **Building**: Once dequeued, transition to `V3_C_BUILT` if voxel data is prepared, then `V3_C_READY` if meshing can begin [S1, unofficial].
4. **Meshing**: Set `V3_C_MESHING` during geometry generation. Upon completion, clear `V3_C_MESHING` and set `V3_C_MESHED` [S1, unofficial].
5. **Visibility**: Update `V3_C_IN_VIEW` based on frustum culling. This flag influences rendering priority but does not block meshing [S1, unofficial].
6. **Remeshing**: If chunk data changes, set `V3_C_REMESH`. The system must clear `V3_C_MESHED` and re-queue the chunk [S1, unofficial].
7. **Global Updates**: Set `V3_C_GLOBY` for chunks affected by global volume changes. These are processed after local updates [S1, unofficial].

**Pseudocode:**
```python
def update_chunk_state(chunk, event):
    """
    Updates the chunk state based on the event.
    chunk.state is a uint8 bitmask.
    """
    if event == "START_MESHING":
        # Ensure chunk is ready and not already meshing
        if (chunk.state & V3_C_READY) and not (chunk.state & V3_C_MESHING):
            chunk.state |= V3_C_MESHING
            chunk.state &= ~V3_C_READY  # Clear ready flag
            return True
    elif event == "FINISH_MESHING":
        # Clear meshing flag and set meshed flag
        chunk.state &= ~V3_C_MESHING
        chunk.state |= V3_C_MESHED
        return True
    elif event == "DATA_CHANGED":
        # Mark for remeshing
        chunk.state |= V3_C_REMESH
        chunk.state &= ~V3_C_MESHED  # Invalidate old mesh
        return True
    elif event == "VISIBILITY_UPDATE":
        # Update view flag
        chunk.state &= ~V3_C_IN_VIEW
        if chunk.in_frustum:
            chunk.state |= V3_C_IN_VIEW
        return True
    elif event == "GLOBAL_UPDATE":
        # Mark for global processing
        chunk.state |= V3_C_GLOBY
        return True
    return False
```

**Parameters:**
- Bitmask constants: Defined as per [S1, unofficial].
- Frustum check: Standard view frustum culling algorithm.

**Edge Cases:**
- **Concurrent Access**: The state byte must be updated atomically if multiple threads access the same chunk.
- **Invalid Transitions**: Attempting to mesh a chunk that is not `V3_C_READY` should be ignored or logged as an error.
- **Stale States**: If a chunk is in `V3_C_MESHING` when a global update occurs, the meshing must be aborted or the chunk re-queued after completion.

## Subtopics

### Volume State Management
Manages the global state of the entire volume (idle, loading, updating, complete) rather than individual chunks [S2, unofficial]. It handles high-level events like `completeUpdate()` which reduces and uploads all pending slices, and `restart()` which clears queues and resets generation numbers [S2, unofficial]. It uses a generation number to discard stale batch or worker results [S2, unofficial]. Priority is given to the focal reduced slice of the active viewport, while oblique views use a round-robin cursor [S2, unofficial].

## Operating characteristics
- **Time Complexity**: State updates are $O(1)$ per chunk. Global updates may require $O(N)$ where $N$ is the number of chunks.
- **Memory Complexity**: $O(1)$ per chunk for the state byte.
- **Performance**: Bitwise operations are extremely fast. The system scales well with the number of chunks as long as the queue management is efficient.
- **Strengths**: Fine-grained control over chunk processing. Prevents redundant meshing.
- **Limitations**: Requires careful synchronization to avoid race conditions. Complex state transitions can be error-prone.
- **When to Use**: When rendering large volumes with dynamic data changes requiring incremental mesh updates.
- **When Not to Use**: For static volumes where full meshing at load time is sufficient.

## Background
The Chunk State Machine is part of the voxel rendering pipeline described in the 42-Vox project [S1, unofficial]. It complements the Volume State Management system from cornerstone3D [S2, unofficial], which handles texture and slice management. The bitwise flag approach is a common technique in game engines and real-time rendering systems for efficient state tracking.
