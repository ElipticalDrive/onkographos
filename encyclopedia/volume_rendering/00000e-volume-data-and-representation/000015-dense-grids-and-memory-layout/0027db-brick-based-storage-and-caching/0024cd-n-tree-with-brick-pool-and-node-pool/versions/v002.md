# N³-tree with Brick Pool and Node Pool

Also called: Adaptive Space Subdivision, N³-tree

## Overview
The N³-tree with Brick Pool and Node Pool is a hierarchical data structure for voxel rendering that combines an N³-tree for spatial subdivision with a brick pool for volume data and a node pool for tree structure, allowing efficient level-of-detail (LOD) and visibility culling [S1, unofficial]. It solves the problem of rendering large volumetric models by adapting the spatial resolution to the required precision, using small 3D texture units (bricks) that can be efficiently evaluated through ray marching [S1, unofficial]. What sets it apart from its siblings, such as [Bricked Volume Hierarchy](5036-bricked-volume-hierarchy.md) or [Brick Caching with LRU Replacement](879-brick-caching-with-lru-replacement.md), is its use of a single pointer per node stored in a 3D texture node pool, which reduces memory requirements by 16x compared to methods requiring eight child pointers and neighbor pointers [S1, unofficial]. This design improves cache coherence during traversal and minimizes the amount of data read from the structure [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A volumetric dataset, a viewpoint (camera position and direction), and a proxy geometry (e.g., screen-covering quad on the near plane) to initialize rays.
*   **Output:** A rendered image with color and opacity values accumulated along view rays.

**Data Structures:**
1.  **Node Pool:** A 3D texture organized into blocks of $N^3$ nodes. Each node is stored as 64 bits (two 32-bit values) in a single texel [S1, unofficial]. The layout is:
    *   [30 bits: child pointer]
    *   [1 bit: max refinement flag]
    *   [1 bit: constant/brick flag]
    *   [30/32 bits: brick pointer or RGBA8 constant value]
    *   Specifically: 30 bits encode a pointer to child nodes for non-leaves (zero means no child); 1 bit indicates if the node is refined to a maximum; 1 bit stores whether the content is a constant RGBA8 value (e.g., empty or core regions) or described by a brick; the remaining 30/32 bits represent either a pointer to an $M^3$ brick for non-constant leaves or the average value for homogenous leaves [S1, unofficial].
2.  **Brick Pool:** A large 3D texture on the GPU containing all bricks. Each brick is a small voxel grid of predefined size $M^3$ (usually $M=32$) [S1, unofficial].

**Parameters:**
*   $N$: The branching factor of the tree. $N=2$ is a standard octree. Trade-off: low $N$ for memory efficiency (deep tree), high $N$ for traversal efficiency (shallow tree) [S1, unofficial].
*   $M$: The side length of a brick (voxel grid). Typically $M=32$ [S1, unofficial].

**Steps:**
1.  **Initialization:** Rasterize proxy geometry (e.g., screen-covering quad on near plane) to deliver ray origins and directions to the fragment shader. Compute entry/exit points using depth buffers. One efficient method is to activate alpha blending set to maximum, drawing the depth of front-facing surfaces in the luminance and one minus the depth of back-facing ones in the alpha channel [S1, unofficial].
2.  **Top-Down Descent:** Start at the ray origin. Locate the current position in the N³-tree using local coordinates $x \in [0,1]^3$. Calculate the child offset: $\text{int}(x \cdot N)$. Fetch the child node at `pointer + offset`. Update $x$: $x \cdot N - \text{int}(x \cdot N)$. Repeat until the LOD condition is met [S1, unofficial].
3.  **LOD Check:** Stop descent when the current node's resolution is sufficient such that a voxel projects to at most one pixel. This determines the appropriate level-of-detail dynamically in the shader [S1, unofficial].
4.  **Node Evaluation:**
    *   If the node is constant, integrate the value analytically along the ray distance traversed in the node [S1, unofficial].
    *   If the node contains a brick, perform standard ray-marching through the brick until leaving the node [S1, unofficial].
5.  **Mipmap Collection:** During top-down traversal, collect bricks required for high-quality filtering into a small queue of three elements [S1, unofficial].
6.  **Brick Sampling:** Perform ray-marching through the brick using quadrilinear filtering across three mipmap levels to approximate cone integration and reduce aliasing [S1, unofficial].

**Pseudocode:**
```python
# Constants
N = 2  # Branching factor
M = 32 # Brick size

# Data structures (simulated)
# node_pool: 3D texture of 64-bit nodes
# brick_pool: 3D texture of M^3 voxel bricks

def render_volume(ray_origin, ray_direction):
    # 1. Initialization: Compute entry/exit points
    entry_point, exit_point = compute_entry_exit(ray_origin, ray_direction)
    
    # 2. Top-Down Descent
    current_pos = entry_point
    current_node_ptr = get_root_node_pointer()
    
    while current_pos < exit_point:
        # Convert world position to local coordinates [0,1]^3
        local_x = (current_pos - volume_min) / (volume_max - volume_min)
        
        # Calculate child offset
        offset = int(local_x * N)
        
        # Fetch child node
        node_data = fetch_node(current_node_ptr + offset)
        
        # Check node type
        if node_data.is_constant:
            # Integrate analytically
            value = integrate_constant(node_data.constant_value, current_pos, next_pos)
            accumulate(value)
            current_pos = next_pos # Move to next node boundary
        else:
            # Get brick pointer
            brick_ptr = node_data.brick_pointer
            
            # 3. LOD Check: Determine if we need to go deeper or march
            # Stop if voxel projects to <= 1 pixel
            if is_lod_sufficient(local_x, node_data):
                # 4. Mipmap Collection: Collect required bricks
                bricks = collect_bricks_for_filtering(current_node_ptr, N)
                
                # 5. Brick Sampling: Ray-march with quadrilinear filtering
                march_through_brick(brick_ptr, bricks, current_pos, exit_point)
                break # Left the node/volume
            else:
                # Continue descent
                current_node_ptr = current_node_ptr + offset
                # Update local coordinates for next level
                local_x = local_x * N - offset
                # Update current_pos to the child node boundary
                current_pos = update_position(current_pos, local_x, N)

def fetch_node(ptr):
    # Fetch 64-bit value from node_pool
    bits = read_64bit(ptr)
    child_ptr = bits[0:30]
    is_max_refined = bits[30]
    is_constant = bits[31]
    value_or_brick_ptr = bits[32:64]
    return {
        'child_ptr': child_ptr,
        'is_max_refined': is_max_refined,
        'is_constant': is_constant,
        'value_or_brick_ptr': value_or_brick_ptr
    }

def integrate_constant(value, start, end):
    # Analytical integration of constant value along ray segment
    distance = length(end - start)
    return value * distance

def march_through_brick(brick_ptr, bricks, start, end):
    # Ray-march through the brick using quadrilinear filtering
    # bricks is a queue of 3 mipmap levels
    step_size = compute_step_size(brick_ptr, bricks)
    pos = start
    while pos < end:
        sample = quadrilinear_sample(brick_ptr, bricks, pos)
        accumulate(sample)
        pos += ray_direction * step_size

def collect_bricks_for_filtering(node_ptr, N):
    # Collect bricks from nodes encountered during traversal
    # Returns a queue of 3 bricks for mipmap levels
    bricks = []
    for i in range(3):
        # Logic to fetch bricks from parent/child nodes
        bricks.append(fetch_brick_from_node(node_ptr, i))
    return bricks
```

## Subtopics

### N3-Tree Structure Update Strategy
A strategy to modify the hierarchical structure when LOD bounds are reached, either by merging bricks or decomposing them [S2, unofficial]. If the useful LOD level is higher than the upper bound of bricks connected to the same tree node, the bricks are merged [S2, unofficial]. If the lower bound is reached, the concerned brick is decomposed into $N^3$ new bricks [S2, unofficial]. This specific aspect of tree modification was not implemented in the described work and is left for future work [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** The traversal is iterative and efficient on GPUs because it avoids recursive DDA and dynamic indexing, which are inefficient due to the lack of fast indexable memory within shader processors [S1, unofficial]. The descent is fast because coordinates can be used directly to locate nodes [S1, unofficial].
*   **Memory Complexity:** The node pool uses 64 bits per node, which fits in a single texel of a luminance-alpha texture, making the performance cost of using 64 bits minor [S1, unofficial]. The method reduces memory requirements by 16x compared to Gobbetti et al. [GMAG08] by using a single pointer per node instead of eight child pointers and neighbor pointers [S1, unofficial].
*   **Measured Performance:** The method allows for efficient rendering of large volumetric models by combining memory efficiency with small 3D texture units [S1, unofficial]. Updates to the structure can be achieved with significantly less information transfer from the CPU [S1, unofficial].
*   **Strengths:** High cache coherence due to 3D texture organization; reduced memory footprint; dynamic LOD determination in the shader minimizes update operations; high-quality filtering via quadrilinear interpolation [S1, unofficial].
*   **Limitations:** The structure update strategy (merging/decomposing bricks) was not implemented, limiting dynamic adaptation [S2, unofficial]. The method relies on a 3D texture cache, which may have limitations on some hardware [S1, unofficial].
*   **When to use:** When rendering large volumetric datasets on GPUs with limited memory, requiring efficient LOD and caching [S1, unofficial].
*   **When not to use:** When dynamic tree structure updates are required, as this was not implemented [S2, unofficial].

## Background
The N³-tree with Brick Pool and Node Pool was introduced in the paper "Ray-Guided Streaming for Efficient and Detailed Voxel Rendering" by [S1, unofficial]. It builds on the concept of adaptive space subdivision, similar to [LHN05a], which is well adapted to store regular data like voxels [S1, unofficial]. The method was developed to address the challenges of rendering large volumetric models by combining the memory efficiency of an adapted structure with small 3D texture units [S1, unofficial]. The approach was further discussed in the thesis "Représentation et algorithmes pour l'exploration interactive de volumes procéduraux étendus et détaillés" [S2, unofficial], which explored the memory management and structure update strategies.
