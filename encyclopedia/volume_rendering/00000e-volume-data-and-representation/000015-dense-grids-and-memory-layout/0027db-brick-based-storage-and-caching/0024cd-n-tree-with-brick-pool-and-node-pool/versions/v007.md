# N³-tree with Brick Pool and Node Pool

Also called: Adaptive Space Subdivision, N³-tree

## Overview
The N³-tree with Brick Pool and Node Pool is a hierarchical data structure for voxel rendering that combines an N³-tree for spatial subdivision with a brick pool for volume data and a node pool for tree structure, allowing efficient Level-of-Detail (LOD) and visibility culling [S1, unofficial]. It differs from sibling methods like [Brick Caching with LRU Replacement](879-brick-caching-with-lru-replacement.md) by integrating the tree traversal logic directly into the GPU shader using a compact, cache-coherent node representation, and from [Bricked Volume Hierarchy](5036-bricked-volume-hierarchy.md) by using a single pointer per node to reduce memory overhead and improve cache coherence [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A volumetric dataset, a viewing ray (origin and direction), and the N³-tree structure parameters ($N$, $M$) [S1, unofficial].
*   **Output:** Accumulated color and opacity for the ray [S1, unofficial].

**Data Structures:**
1.  **Node Pool:** A 3D texture organized into blocks of $N^3$ nodes [S1, unofficial]. Each node is stored as 64 bits (two 32-bit values) to fit in a single texel of a luminance-alpha texture [S1, unofficial]. The layout is:
    *   **30 bits:** Child pointer (for non-leaves; zero means no child) [S1, unofficial].
    *   **1 bit:** Max refinement flag (indicates if the node is refined to maximum or if original volume contains more data) [S1, unofficial].
    *   **1 bit:** Constant/Brick flag (stores whether content is a constant RGBA8 value or described by a brick) [S1, unofficial].
    *   **30/32 bits:** Depending on the flag:
        *   If Brick: A pointer to an $M^3$ brick in the Brick Pool (30 bits) [S1, unofficial].
        *   If Constant: The average RGBA8 value (4 * 8 bits) for homogenous leaves [S1, unofficial].
2.  **Brick Pool:** A large 3D texture containing all bricks [S1, unofficial]. Bricks are $M^3$ voxel grids (typically $M=32$) with 1-voxel padding on all sides for trilinear interpolation [S1, unofficial][S2, unofficial]. The stored voxel count per brick is $V_{brick} = (B_x+1)(B_y+1)(B_z+1)$, where $B_x, B_y, B_z$ are the logical brick dimensions [S1, unofficial].

**Parameters:**
*   $N$: Branching factor of the tree. $N=2$ is a standard octree. Trade-off: low $N$ for memory efficiency (deep tree), high $N$ for traversal efficiency (shallow tree) [S1, unofficial].
*   $M$: Side length of a brick in voxels. Typically $M=32$ [S1, unofficial].

**Algorithm Steps:**
1.  **Initialization:** Rasterize proxy geometry (e.g., a screen-covering quad on the near plane or the volume bounding box) to deliver ray origins and directions to the fragment shader [S1, unofficial]. Compute entry and exit points using depth buffers (e.g., front-facing surfaces for entry, back-facing for exit) [S1, unofficial].
2.  **Iterative Top-Down Descent:** Start at the ray origin [S1, unofficial]. Locate the current position in the N³-tree using local coordinates $x \in [0, 1]^3$ relative to the volume's bounding box [S1, unofficial]. Calculate the child offset: $offset = \lfloor x \cdot N \rfloor$ (integer part of $x \cdot N$) [S1, unofficial]. Fetch the child node from the Node Pool at `pointer + offset` [S1, unofficial]. Update local coordinates: $x \leftarrow x \cdot N - offset$ [S1, unofficial]. Repeat until the LOD condition is met [S1, unofficial].
3.  **LOD Check:** Stop descent when the current node's resolution is sufficient such that a voxel projects to at most one pixel [S1, unofficial]. This determines the appropriate LOD dynamically in the shader, avoiding the need for the structure to explicitly store correct LODs [S1, unofficial].
4.  **Node Evaluation:** If Constant: Integrate the constant value analytically along the ray distance traversed within the node [S1, unofficial]. If Brick: Perform standard ray-marching through the brick until leaving the node [S1, unofficial]. The new position serves as the origin for the next descent [S1, unofficial].
5.  **Mipmap Collection:** During top-down traversal, collect bricks required for high-quality filtering into a small queue of three elements [S1, unofficial]. This queue is implemented in shader registers without dynamic indexing [S1, unofficial].
6.  **Brick Sampling:** Perform ray-marching through the brick using quadrilinear filtering across the three collected mipmap levels to approximate cone integration and reduce aliasing [S1, unofficial].
7.  **Accumulation:** Accumulate color and opacity using pre-integrated transfer functions [S1, unofficial]. Lighting (e.g., pseudo-Phong) can be accounted for using the density gradient as the normal [S1, unofficial].

**Pseudocode:**
```python
def floor_componentwise(v, n):
    return tuple(int(x * n) for x in v)

def main(ray_origin, ray_direction, root_node_ptr, volume_bounds, N, M):
    # 1. Initialization: Entry/Exit points computed externally from proxy geometry rasterization.
    current_pos = ray_origin
    current_node_ptr = root_node_ptr
    # Map ray origin to local coordinates in [0, 1]^3
    local_coords = (ray_origin - volume_bounds.min) / (volume_bounds.max - volume_bounds.min)
    # Queue of 3 elements for high-quality filtering, implemented in shader registers
    mipmap_queue = [None, None, None]
    queue_idx = 0

    while current_pos is within volume:
        # 2. Iterative Descent
        offset = floor_componentwise(local_coords, N)
        # Read 64-bit node from Node Pool 3D texture at base_ptr + offset
        node = read_node_pool(current_node_ptr + offset)

        # Update local coordinates for next level
        local_coords = tuple(local_coords[i] * N - offset[i] for i in range(3))

        # 3. LOD Check: Stop when voxel projects to at most one pixel [G]
        # Computed in shader based on current traversal depth and view projection
        if is_lod_sufficient(node, local_coords):
            break

        # Collect brick for mipmap queue during traversal
        if not node['is_constant']:
            mipmap_queue[queue_idx % 3] = node['value_or_brick_ptr']
            queue_idx += 1

        current_node_ptr = node['child_ptr']

    # 4. Node Evaluation
    if node['is_constant']:
        # Integrate analytically along ray distance traversed in the node [G]
        segment_dist = compute_distance_in_node(current_pos, node['extent'])
        color, opacity = integrate_constant(node['value_or_brick_ptr'], segment_dist)
    else:
        # 5 & 6. Mipmap Collection & Brick Sampling
        # Ray-march using quadrilinear filtering across 3 mipmap levels [S1, unofficial]
        brick_ptr = node['value_or_brick_ptr']
        color, opacity = ray_march_brick(brick_ptr, current_pos, ray_direction, node['extent'], mipmap_queue)

    # 7. Accumulation: Standard volume rendering accumulation with pre-integrated transfer functions [G]
    return accumulate(color, opacity)
```

## Subtopics

### N3-Tree Structure Update Strategy
A strategy to modify the hierarchical structure when LOD bounds are reached, either by merging bricks or decomposing them [S2, unofficial]. If the useful LOD level is higher than the upper bound of bricks connected to the same tree node, those bricks are merged [S2, unofficial]. If the lower bound is reached, the concerned brick is decomposed into $N^3$ new bricks [S2, unofficial]. This aspect was not implemented in the described work and is left for future work [S2, unofficial].

## Operating characteristics
*   **Memory Efficiency:** Uses a single pointer per node (stored in a 3D texture node pool) instead of eight child pointers and neighbor pointers, reducing memory requirements by 16x compared to Gobbetti et al. [GMAG08] [S1, unofficial].
*   **Cache Coherence:** Grouping children of a node in one block of the 3D texture improves cache coherence during traversal, leveraging 3D texture caches on modern GPUs [S1, unofficial].
*   **Traversal Efficiency:** Iterative descent is used instead of recursive DDA to avoid inefficient dynamic indexable memory stacks on GPUs [S1, unofficial].
*   **Performance:** The performance cost of using 64-bit nodes is minor as they fit in a single texel [S1, unofficial].
*   **Limitations:** The method relies on the GPU's 3D texture cache; performance may vary based on hardware cache efficiency. The structure update strategy (merging/decomposing) is not implemented in the base method [S2, unofficial].

## Background
The approach addresses the need for efficient rendering of large volumetric models by combining adaptive space subdivision with GPU-friendly data structures [S1, unofficial]. It builds on the N³-tree concept similar to [LHN05a] and is well adapted to store regular data like voxels [S1, unofficial].
