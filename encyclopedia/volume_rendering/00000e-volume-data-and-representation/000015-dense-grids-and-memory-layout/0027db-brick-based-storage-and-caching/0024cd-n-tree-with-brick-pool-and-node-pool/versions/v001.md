# N³-tree with Brick Pool and Node Pool

Also called: Adaptive Space Subdivision, N³-tree

## Overview
The N³-tree with Brick Pool and Node Pool is a hierarchical data structure for voxel rendering that combines an N³-tree for spatial subdivision with a brick pool for volume data and a node pool for tree structure, allowing efficient LOD and visibility culling [S1, unofficial]. It solves the problem of rendering large volumetric models by adapting the spatial resolution to the required precision, using small 3D texture units (bricks) that can be efficiently evaluated through ray marching [S1, unofficial]. What sets it apart from its siblings, such as [Brick Caching with LRU Replacement](879-brick-caching-with-lru-replacement.md) or [Brick-based Volume Raycasting](3341-brick-based-volume-raycasting.md), is its use of a single pointer per node stored in a 3D texture node pool, which reduces memory requirements by 16x compared to methods requiring eight child pointers and neighbor pointers [S1, unofficial]. This design improves cache coherence during traversal and minimizes the amount of data read during tree traversal [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A large volumetric dataset, a viewpoint (camera position and direction), and a proxy geometry (e.g., screen-covering quad on the near plane) to deliver ray origins and directions.
*   **Output:** A rendered image with color and opacity, accumulated via ray marching.

**Data Structures:**
1.  **Node Pool:** A 3D texture organized into blocks of $N^3$ nodes. Each node is stored as 64 bits (two 32-bit values) in a luminance-alpha texture format [S1, unofficial]. The layout is:
    *   [30 bits: child pointer]
    *   [1 bit: max refinement flag]
    *   [1 bit: constant/brick flag]
    *   [30/32 bits: brick pointer or RGBA8 constant value]
    *   Specifically: 30 bits encode a pointer to child nodes for non-leaves (zero means no child); 1 bit indicates if the node is refined to a maximum; 1 bit stores whether the content is a constant RGBA8 value (e.g., empty or core regions) or described by a brick; the remaining 30/32 bits represent either a pointer to an $M^3$ brick for non-constant leaves (30 bits) or the average value at this location for homogenous leaves (4*8 bits) [S1, unofficial].
2.  **Brick Pool:** A large 3D texture containing all bricks. A brick is a small voxel grid of predefined size $M^3$ (usually $M=32$) that approximates the part of the original volume corresponding to the N³-tree’s node [S1, unofficial].

**Parameters:**
*   $N$: The branching factor of the tree. $N=2$ is a standard octree. Trade-off: low $N$ for memory efficiency (deep tree), high $N$ for traversal efficiency (shallow tree) [S1, unofficial].
*   $M$: The side length of a brick (voxel grid). Typically $M=32$ [S1, unofficial].

**Numbered Steps:**
1.  **Initialization:** Rasterize proxy geometry (e.g., screen-covering quad on near plane) to deliver ray origins and directions to the fragment shader. Compute entry/exit points using depth buffers. This can be done in a single pre-rendering by activating alpha blending set to maximum and drawing the depth of front-facing surfaces in the luminance, and one minus the depth of back-facing ones in the alpha channel [S1, unofficial].
2.  **Top-Down Descent:** Start at ray origin. Locate current position in N³-tree using local coordinates $x \in [0,1]^3$. Calculate child offset: $\text{int}(x \times N)$. Fetch child node at pointer + offset. Update $x$: $x \times N - \text{int}(x \times N)$. Repeat until LOD condition is met [S1, unofficial].
3.  **LOD Check:** Stop descent when the current node's resolution is sufficient such that a voxel projects to at most one pixel. This determines the appropriate level-of-detail dynamically in the shader [S1, unofficial].
4.  **Node Evaluation:**
    *   If node is constant, integrate value analytically along the ray distance traversed in the node.
    *   If node contains a brick, perform standard ray-marching through the brick until leaving the node [S1, unofficial].
5.  **Mipmap Collection:** During top-down traversal, collect bricks required for high-quality filtering into a small queue of three elements [S1, unofficial].
6.  **Brick Sampling:** Perform ray-marching through the brick using quadrilinear filtering across three mipmap levels to approximate cone integration and reduce aliasing [S1, unofficial].

**Pseudocode:**
```python
# Assume ray origin O and direction D are passed from fragment shader
# Assume node_pool is a 3D texture containing the N3-tree structure
# Assume brick_pool is a 3D texture containing the bricks
# N is the branching factor, M is the brick size

def render_ray(O, D):
    # Step 1: Initialization
    # Proxy geometry rasterization provides O and D.
    # Entry and exit points are computed via depth buffers.
    # For simplicity, assume O is the entry point and we march until exit or max distance.
    
    current_pos = O
    current_node_ptr = root_node_pointer # Pointer to the root block in node_pool
    
    # Queue for mipmap collection
    mipmap_queue = [] 
    
    accumulated_color = vec4(0.0)
    accumulated_opacity = 0.0
    
    while current_pos is within volume bounds:
        # Step 2: Top-Down Descent
        # Local coordinates in [0,1]^3
        x = (current_pos - volume_min) / (volume_max - volume_min)
        
        # Calculate child offset
        offset = int(x.x * N) + int(x.y * N) * N + int(x.z * N) * N * N
        
        # Fetch child node
        # Note: In practice, this involves texture lookup at current_node_ptr + offset
        # For pseudocode, assume fetch_node returns the 64-bit node data
        node_data = fetch_node(current_node_ptr, offset)
        
        # Parse node data
        is_constant = (node_data & 0x2) != 0 # 1 bit flag
        is_max_refined = (node_data & 0x4) != 0 # 1 bit flag
        child_ptr = (node_data >> 34) & 0x3FFFFFFF # 30 bits
        brick_ptr_or_value = node_data & 0xFFFFFFFF # 32 bits
        
        # Step 3: LOD Check
        # Stop descent if voxel projects to at most one pixel.
        # This is determined in the shader based on current view.
        # If LOD is sufficient, break descent.
        if is_lod_sufficient(x, current_pos, D):
            break
            
        # Update for next descent if not leaf
        if not is_constant and child_ptr != 0:
            current_node_ptr = child_ptr
            # Update local coordinates for next level
            x = x * N - vec3(float(int(x.x * N)), float(int(x.y * N)), float(int(x.z * N)))
            current_pos = volume_min + x * (volume_max - volume_min)
            continue
        else:
            # Reached a leaf node (constant or brick)
            break
            
    # Step 4: Node Evaluation
    if is_constant:
        # Integrate value analytically along the ray distance traversed in the node
        # Value is stored in brick_ptr_or_value (RGBA8)
        constant_value = decode_constant_value(brick_ptr_or_value)
        distance_in_node = compute_distance_in_node(current_pos, D, node_bounds)
        accumulated_color += constant_value * distance_in_node
        accumulated_opacity += distance_in_node
    else:
        # Brick ray-marching
        # Step 5: Mipmap Collection
        # Collect bricks for high-quality filtering into a queue of 3
        # This happens during top-down traversal, so we assume mipmap_queue is populated
        # For this step, we use the collected bricks
        
        # Step 6: Brick Sampling
        # Perform ray-marching through the brick using quadrilinear filtering
        # across three mipmap levels
        brick_data = fetch_brick(brick_ptr_or_value)
        march_result = ray_march_brick(current_pos, D, brick_data, mipmap_queue)
        accumulated_color += march_result.color
        accumulated_opacity += march_result.opacity
        
    return accumulated_color, accumulated_opacity
```

**Edge Cases and Pitfalls:**
*   Recursive DDA traversal is inefficient on GPUs due to lack of fast indexable memory for stacks. Iterative descent is used instead [S1, unofficial].
*   The method does not require the structure to indicate correct level-of-details; this is determined in the shader, which minimizes update operations [S1, unofficial].
*   Neighbor pointers are not used, which simplifies the structure but requires careful handling of filtering across brick boundaries [S1, unofficial].

## Subtopics

### N3-Tree Structure Update Strategy
A strategy to modify the hierarchical structure when LOD bounds are reached, either by merging bricks or decomposing them [S2, unofficial]. If the useful LOD level is higher than the upper bound of bricks connected to the same tree node, the bricks are merged. If the lower bound is reached, the concerned brick is decomposed into $N^3$ new bricks [S2, unofficial]. This specific aspect of tree modification was not implemented in the described work and is left for future work [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** The traversal is iterative and efficient due to the N³-tree structure. The coordinates of a point can be used directly to locate it in the tree, and mostly the same pointers in the structure will be followed, thus the hardware texture cache is very well prepared [S1, unofficial].
*   **Memory Complexity:** Memory requirements are largely reduced compared to methods using eight child pointers and neighbor pointers. The use of a single pointer per node stored in a 3D texture node pool reduces memory requirements by 16x [S1, unofficial]. The 64-bit node data fits in a single texel of a luminance-alpha texture, so the performance cost of using 64 instead of 32 bits is minor [S1, unofficial].
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** The method is well adapted to store regular data like voxels and can handle large volumetric models by adapting the spatial resolution to the required precision [S1, unofficial].
*   **Strengths:** High cache coherence, reduced memory requirements, efficient traversal, and high-quality filtering via mipmap collection [S1, unofficial].
*   **Limitations:** The tree update strategy (merging/decomposing bricks) was not implemented, which may limit dynamic adaptation [S2, unofficial].
*   **When to use:** When rendering large volumetric models with regular voxel data, especially on GPUs where cache coherence and memory efficiency are critical [S1, unofficial].
*   **When not to use:** When dynamic tree updates are required and the implementation does not support them [S2, unofficial].

## Background
The N³-tree with Brick Pool and Node Pool was introduced in the paper "Ray-Guided Streaming for Efficient and Detailed Voxel Rendering" by Lhote et al. (2009) [S1, unofficial]. It builds on the concept of adaptive space subdivision, which is key to rendering large volumetric models [S1, unofficial]. The method improves upon previous work, such as Gobbetti et al. [GMAG08], by using a single pointer per node instead of eight child pointers and neighbor pointers, reducing memory requirements and improving cache coherence [S1, unofficial]. The structure is well adapted to store regular data like voxels and allows for efficient LOD and visibility culling [S1, unofficial].
