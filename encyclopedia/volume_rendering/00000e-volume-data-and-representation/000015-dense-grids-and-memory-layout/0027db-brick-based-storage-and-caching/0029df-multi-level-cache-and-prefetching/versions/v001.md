# Multi-Level Cache and Prefetching

Also called: HTTP Range Request Caching, Luxar Viewer Cache Architecture

## Overview
Multi-Level Cache and Prefetching is a memory management strategy for volumetric and splat-based data that organizes storage into four distinct tiers to bridge the gap between slow remote storage and fast rendering. It solves the problem of high-latency network fetches by combining spatial locality (prefetching adjacent chunks) and temporal locality (caching decoded slices). It differs from sibling methods like [Brick Caching with LRU Replacement](879-brick-caching-with-lru-replacement.md) by explicitly separating compressed and decompressed states across heap-aware tiers and utilizing an S-cache to bypass chunk decoding entirely for repeated slice access.

## How it works
The method manages data flow from remote HTTP sources through a four-level hierarchy.

**Inputs and Outputs**
*   **Input:** Remote data chunks (e.g., Zarr archives), user navigation events (orbit, slider playback).
*   **Output:** Decoded geometry ready for rendering (splat positions, attributes).

**Data Structures**
The cache consists of four levels with specific storage media and size constraints:
1.  **L2 (Disk/OPFS):** Browser Origin Private File System. Fixed size of 2 GB. Stores compressed chunks.
2.  **L1 (Memory):** Compressed in-memory chunks. Ceiling of 100 MB.
3.  **L0 (Memory):** Decompressed in-memory chunks. Ceiling of 200 MB.
4.  **S-cache (Memory):** Fully decoded slice ladders. Default size 128 MB, scalable up to 2 GB.

**Numbered Steps**
1.  **Fetch Request:** The renderer requests a data chunk.
2.  **L2 Check:** If the compressed chunk exists in L2 (OPFS), load it into L1. If not, fetch via HTTP Range Request.
3.  **L1 Check:** If the compressed chunk is in L1, proceed to decompression. If not, load from L2 or remote.
4.  **Decompression:** Decompress the chunk using Blosc/zstd codecs (typically in WebAssembly).
5.  **L0 Storage:** Store the decompressed chunk in L0.
6.  **S-cache Optimization:** If the chunk belongs to a slice ladder, fully decode the slice ladder and store it in the S-cache. This allows subsequent accesses to the same slice to skip the chunk path entirely.
7.  **Prefetching:**
    *   **Immediate:** After an on-disk hit or remote fetch, request the adjacent chunk in the data ordering.
    *   **Idle-time:** During user orbit or slider playback, warm the adjacent slice to hide remote-fetch latency.
8.  **Eviction and Scaling:**
    *   If heap memory is tight, L0 and L1 shrink below their configured ceilings.
    *   The S-cache grows with available heap memory, up to its 2 GB limit.

**Formulas**
*   **Effective Radius for Splat Intersection:** When determining if a splat intersects the display hyperplane, the effective radius $r_{eff}$ is calculated as:
    $$ r_{eff} = \sqrt{r^2 - d^2} $$
    Where $r$ is the splat's original radius and $d$ is the Euclidean distance from the splat center to the hyperplane. [S1, unofficial]

**Parameters**
*   **L2 Size:** 2 GB (Fixed).
*   **L1 Ceiling:** 100 MB.
*   **L0 Ceiling:** 200 MB.
*   **S-cache Default:** 128 MB.
*   **S-cache Max:** 2 GB.
*   **Remote Fetch Latency:** ~100 ms. [S1, unofficial]

**Pseudocode**
```python
class MultiLevelCache:
    def __init__(self):
        self.l2_opfs = Storage(media="OPFS", max_size_gb=2.0)
        self.l1_compressed = Storage(media="RAM", max_size_mb=100)
        self.l0_decompressed = Storage(media="RAM", max_size_mb=200)
        self.s_cache_slices = Storage(media="RAM", min_size_mb=128, max_size_mb=2000)
        
    def get_chunk(self, chunk_id):
        # Check L2
        if self.l2_opfs.contains(chunk_id):
            compressed_data = self.l2_opfs.read(chunk_id)
            self.l1_compressed.put(chunk_id, compressed_data)
        else:
            # Remote fetch
            compressed_data = fetch_remote(chunk_id)
            self.l2_opfs.put(chunk_id, compressed_data)
            self.l1_compressed.put(chunk_id, compressed_data)
            
        # Check L1
        if not self.l1_compressed.contains(chunk_id):
            compressed_data = self.l2_opfs.read(chunk_id)
            self.l1_compressed.put(chunk_id, compressed_data)
            
        # Decompress
        decompressed_data = decompress_blosc_zstd(self.l1_compressed.get(chunk_id))
        self.l0_decompressed.put(chunk_id, decompressed_data)
        
        # S-cache optimization
        slice_id = get_slice_id_from_chunk(chunk_id)
        if self.s_cache_slices.contains(slice_id):
            return self.s_cache_slices.get(slice_id)
        else:
            # Decode full slice ladder
            full_slice = decode_slice_ladder(decompressed_data)
            self.s_cache_slices.put(slice_id, full_slice)
            return full_slice

    def prefetch(self, current_chunk_id):
        # Immediate prefetch of adjacent chunks
        next_chunk = get_adjacent_chunk(current_chunk_id, direction=1)
        prev_chunk = get_adjacent_chunk(current_chunk_id, direction=-1)
        self.get_chunk(next_chunk)
        self.get_chunk(prev_chunk)

    def idle_prefetch(self, current_slice_id):
        # Warm adjacent slice during idle time
        next_slice = get_adjacent_slice(current_slice_id)
        self.get_chunk(get_chunk_id_from_slice(next_slice))

    def manage_heap_pressure(self, available_heap_mb):
        # Shrink L0 and L1 if heap is tight
        if available_heap_mb < threshold:
            self.l0_decompressed.shrink()
            self.l1_compressed.shrink()
        # Grow S-cache if heap allows
        if available_heap_mb > threshold:
            self.s_cache_slices.grow()
```

## Operating characteristics
*   **Time Complexity:** Lookup is $O(1)$ for cache hits. Remote fetches introduce latency of ~100 ms, mitigated by prefetching. [S1, unofficial]
*   **Memory Complexity:** Total memory usage is bounded by the sum of L1, L0, and S-cache ceilings, dynamically adjusted by heap availability.
*   **Strengths:** Hides network latency via idle-time prefetching; reduces decoding overhead via S-cache; adapts to mobile memory constraints.
*   **Limitations:** Complex eviction logic across four tiers; dependent on HTTP Range Request support.
*   **When to use:** Interactive web visualization of large multidimensional scientific data where network latency is significant.

## Background
This architecture was introduced in the Luxar viewer for Gaussian splatting microscopy and scalable interactive web visualization. It addresses the challenges of rendering high-dimensional data in browsers by leveraging the Origin Private File System (OPFS) and WebAssembly for efficient decoding. [S1, unofficial]
