# Multi-Level Cache and Prefetching

Also called: HTTP Range Request Caching, Luxar Viewer Cache Architecture

## Overview
Multi-Level Cache and Prefetching is a memory management strategy for volumetric and splat-based data that utilizes a four-tier hierarchy to bridge the latency gap between remote storage and the rendering engine. It solves the problem of high-latency network fetches (order of 100 ms) by combining on-disk persistence, compressed in-memory caching, and fully decoded slice ladders. It sets itself apart from sibling methods like [Brick Caching with LRU Replacement](879-brick-caching-with-lru-replacement.md) by explicitly managing distinct data states (compressed vs. decompressed vs. slice-ladder) and employing heap-aware dynamic resizing rather than fixed-size eviction policies.

## How it works
**Inputs and Outputs:**
*   **Input:** A sequence of data requests (chunks or slices) triggered by user interaction (orbit, slider playback) or rendering needs.
*   **Output:** Ready-to-render data structures (decompressed chunks or slice ladders) served from the fastest available cache tier.

**Data Structures:**
The system implements a four-level cache hierarchy. The total memory footprint is constrained by the available heap, with specific tiers having fixed or dynamic ceilings.

1.  **L2 Cache (Disk/OPFS):**
    *   **Location:** Browser’s Origin Private File System (OPFS).
    *   **Capacity:** Fixed 2 GB.
    *   **Content:** Persisted compressed chunks. Survives browser restarts.
    *   **Access:** Via HTTP Range Requests.

2.  **L1 Cache (Compressed In-Memory):**
    *   **Location:** RAM.
    *   **Capacity:** Ceiling of 100 MB.
    *   **Content:** Compressed chunks.
    *   **Behavior:** Heap-aware. Shrinks from its ceiling when heap pressure is high.

3.  **L0 Cache (Decompressed In-Memory):**
    *   **Location:** RAM.
    *   **Capacity:** Ceiling of 200 MB.
    *   **Content:** Decompressed chunks.
    *   **Behavior:** Heap-aware. Shrinks from its ceiling when heap pressure is high.

4.  **S-cache (Slice Ladder):**
    *   **Location:** RAM.
    *   **Capacity:** Dynamic, from 128 MB default up to 2 GB.
    *   **Content:** Fully decoded slice ladders.
    *   **Behavior:** Grows with available heap. Allows revisited slices to skip the chunk path entirely.

**Numbered Steps:**
1.  **Request Initiation:** The renderer requests a data unit (chunk or slice).
2.  **L0 Check:** Check if the decompressed chunk exists in L0. If yes, serve it.
3.  **L1 Check:** If not in L0, check if the compressed chunk exists in L1.
    *   If yes, decompress it using the Zarr client’s WebAssembly (WASM) codec (Blosc/zstd) and insert into L0. Evict from L1 if necessary.
4.  **L2 Check:** If not in L1, check if the compressed chunk exists in L2 (OPFS).
    *   If yes, read from disk, insert into L1, then proceed to decompress into L0.
5.  **Remote Fetch:** If not in L2, issue an HTTP Range Request to the remote server.
    *   Store the result in L2 (if space permits).
    *   Store the result in L1.
    *   Decompress into L0.
6.  **S-cache Optimization:** If the request corresponds to a full slice, check the S-cache. If a fully decoded slice ladder exists, serve it directly, bypassing the chunk-based L0/L1/L2 path.
7.  **Prefetching:**
    *   **Immediate Prefetch:** After an on-disk hit or remote fetch, request the adjacent chunk in the data ordering.
    *   **Idle Prefetch:** During user orbit or slider playback, warm the adjacent slice to hide remote-fetch latency.

**Formulas:**
*   **Effective Radius for Splat Intersection:**
    $$ r_{eff} = \sqrt{r^2 - d^2} $$
    Where $r$ is the splat radius and $d$ is the Euclidean distance from the splat center to the display hyperplane. [S1, unofficial]
*   **Heap-Aware Scaling:**
    The capacity $C_i$ of tier $i$ (L0, L1, S-cache) is a function of available heap $H$:
    $$ C_{L0}(H) \le 200 \text{ MB} $$
    $$ C_{L1}(H) \le 100 \text{ MB} $$
    $$ C_{S}(H) \in [128 \text{ MB}, 2 \text{ GB}] $$
    [S1, unofficial]

**Parameters:**
*   **Remote Fetch Latency:** Order of 100 ms. [S1, unofficial]
*   **L2 Capacity:** 2 GB (Fixed). [S1, unofficial]
*   **L1 Ceiling:** 100 MB. [S1, unofficial]
*   **L0 Ceiling:** 200 MB. [S1, unofficial]
*   **S-cache Default:** 128 MB. [S1, unofficial]
*   **S-cache Max:** 2 GB. [S1, unofficial]

**Edge Cases and Pitfalls:**
*   **Heap Pressure:** When memory is tight, L0 and L1 shrink. Implementers must ensure eviction logic correctly handles the transition between compressed and decompressed states to avoid data loss or redundant decompression. [G]
*   **Dimensionality:** For datasets with $n > 3$ dimensions, the viewer displays three spatial dimensions and uses sliders for non-displayed dimensions. The cache must handle requests for these non-spatial dimensions correctly. [S1, unofficial]
*   **Encoding:** Data uses semantic encoding (8 types) with width-aware Blosc-zstd level 9. Byte shuffle is applied for multi-byte integer codes but not for single-byte codes or floating-point arrays. [S1, unofficial]

## Operating characteristics
*   **Time Complexity:** Lookup is $O(1)$ for cache hits. Remote fetches introduce latency of ~100 ms, mitigated by prefetching. [S1, unofficial]
*   **Memory Complexity:** Total memory usage is bounded by the sum of tier ceilings, dynamically adjusted by heap availability. Max theoretical RAM usage is ~2.4 GB (100+200+2000 MB) plus overhead. [S1, unofficial]
*   **Performance:** Hides remote-fetch latency during user interaction (orbit/slider) via idle-time prefetching. [S1, unofficial]
*   **Strengths:** Reduces redundant decompression and network requests. Persistent L2 cache survives restarts.
*   **Limitations:** Complex state management across four tiers. Heap-aware resizing adds implementation complexity.
*   **When to Use:** Interactive web-based visualization of large multidimensional scientific data where network latency is significant. [S1, unofficial]
*   **When Not to Use:** Offline batch processing where latency is less critical than throughput, or systems with abundant memory where a simpler flat cache suffices.

## Background
This method originates from the Luxar viewer, a tool for Gaussian splatting in microscopy and scalable interactive web visualization of multidimensional scientific data. It was developed to handle the challenges of loading large Zarr archives in a browser environment, leveraging HTTP range requests and WebAssembly for efficient decoding. [S1, unofficial]
