# Brick-based Volume Rendering with Overlap and LRU Swapping

Also called: Texture Bricking

## Overview
Brick-based Volume Rendering with Overlap and LRU Swapping manages volumetric data exceeding GPU memory by partitioning the volume into small 3D texture bricks, rendering them individually, and composing the final image [S1, unofficial]. It distinguishes itself from traditional bricking [Bricking](914-bricking.md) by using significantly smaller bricks to exploit void detection and an LRU swapping policy, thereby reducing bus transfer overhead and alleviating the bottleneck caused by reloading void bricks [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A volumetric dataset (scalar or vector field), a transfer function, and GPU texture memory constraints.
*   **Output:** A rendered 2D image.

**Data Structures:**
*   **Bricks:** Cubic sub-volumes of size $b \times b \times b$ voxels.
*   **Overlap:** A border of $n$ voxels duplicated around each brick to support interpolation.
*   **Memory State:** A set of resident bricks in GPU texture memory and a set of non-resident bricks in main memory.

**Parameters:**
*   **Brick dimension ($b$):** The side length of a brick in voxels. Sources recommend choosing $b$ considerably smaller than the maximum possible size to increase the probability of bricks being completely void [S1, unofficial].
*   **Overlap size ($n$):** The number of voxels shared between adjacent bricks.
    *   Nearest neighbor: $n=0$ [S1, unofficial].
    *   Trilinear interpolation: $n=1$ [S1, unofficial].
    *   Pre-integrated rendering or on-the-fly gradient calculation: $n=2$ (trilinear + 1) [S1, unofficial].
*   **Texture Size Constraints:** Many graphics cards require 3D texture dimensions to be powers of 2. Non-power-of-2 dimensions require padding or rest-bricks [S1, unofficial].

**Steps:**
1.  **Partitioning:** Divide the volume into $b \times b \times b$ bricks. If the volume dimensions do not divide evenly by $b$, add an additional layer of partially empty bricks in each direction or use smaller "rest-bricks" to fill the remaining space [S1, unofficial].
2.  **Overlap Application:** Duplicate a plane of $n$ voxels at each brick boundary. This ensures correct interpolation results across shared planes [S1, unofficial]. The memory overhead percentage is approximately:
    $$ \text{Overhead} \approx \frac{3 \cdot n}{b} \cdot 100\% $$
    where $b$ is the brick dimension and $n$ is the overlap size [S1, unofficial].
3.  **Loading:** Load bricks into video memory as 3D textures.
4.  **Swapping:** When the amount of data exceeds available texture memory, swap textures between main memory and texture memory using a Least Recently Used (LRU) policy [S1, unofficial].
    *   If a requested brick is not resident, load it from main memory.
    *   Replace a resident texture (the least recently used one) to make space [S1, unofficial].
5.  **Rendering:** Render each resident brick. If a brick is completely void after applying the transfer function, skip drawing it. Once a void brick is swapped out, it is never reloaded, reducing bus traffic [S1, unofficial].

**Pitfalls:**
*   **Power of 2 Requirement:** Graphics cards often require 3D texture sizes to be powers of 2. Handling non-power-of-2 dimensions via padding increases memory usage and overlap overhead [S1, unofficial].
*   **Overlap Overhead:** Smaller bricks reduce bus traffic but increase the relative overhead of the overlap region. The optimal brick size depends on available memory and the specific interpolation kernel [S1, unofficial].

## Subtopics

### [Bricking with Boundary Voxel Duplication](4198-bricking-with-boundary-voxel-duplication.md)
Specifically addresses the geometric continuity of trilinear interpolation at brick interfaces by duplicating boundary voxels. Choose this when interpolation artifacts at brick edges are critical.

### [Level-wise Texture Merging](5274-level-wise-texture-merging.md)
Merges adjacent bricks into larger texture maps to reduce state-switching overhead. Choose this when GPU state-switching costs dominate rendering time.

### [Wang Cubes for Volume Rendering](6980-wang-cubes-for-volume-rendering.md)
Uses non-periodic 3D Wang Cubes to store volume data and segmentation masks, reducing texture memory usage. Choose this when memory usage is the primary constraint and segmentation masks are involved.

## Operating characteristics
*   **Time Complexity:** Rendering time depends on the number of non-void bricks rendered per frame. LRU swapping overhead depends on the cache miss rate of bricks.
*   **Memory Complexity:** Memory usage is proportional to the number of resident bricks plus the overlap overhead. The overhead is $\approx (3 \cdot n / b) \cdot 100\%$ [S1, unofficial].
*   **Performance:** Using smaller bricks and LRU swapping alleviates the bus bottleneck compared to traditional bricking, which transfers the entire volume over the bus per frame [S1, unofficial]. Void bricks are not drawn and, once swapped out, are never reloaded, further reducing bus traffic [S1, unofficial].
*   **Strengths:** Reduces bus transfer overhead, improves data locality, and reduces cache trashing on the graphics card [S1, unofficial].
*   **Limitations:** Smaller bricks introduce larger overhead due to the overlap needed for interpolation [S1, unofficial]. Power-of-2 texture size requirements may lead to inefficient memory usage [S1, unofficial].
*   **When to use:** When the volume exceeds GPU memory, or when improving data locality and reducing bus traffic is beneficial even if the volume fits in memory [S1, unofficial].
*   **When not to use:** When the overhead of overlap and LRU swapping outweighs the benefits of reduced bus traffic, or when the volume is small enough to fit entirely in texture memory without swapping.

## Background
The method was described by Danny Ruijters in "Optimizing GPU Volume Rendering" [S1, unofficial]. It builds on the concept of bricking [Bricking](914-bricking.md) but introduces smaller brick sizes and LRU swapping to optimize for bus bandwidth and void detection. The approach references earlier work on texture-based rendering [SWND03] and data locality [HG97, CBS98, IEP98].
