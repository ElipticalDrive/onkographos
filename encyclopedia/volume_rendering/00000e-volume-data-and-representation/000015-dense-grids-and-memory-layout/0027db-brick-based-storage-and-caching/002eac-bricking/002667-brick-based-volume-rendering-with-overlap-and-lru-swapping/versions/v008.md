# Brick-based Volume Rendering with Overlap and LRU Swapping

Also called: Object Space Partitioning with Uniform Texture Bricks, Texture Bricking, Uniform texture bricks

## Overview
Brick-based volume rendering with overlap and LRU swapping manages volumetric data larger than GPU memory by dividing the volume into smaller 3D texture bricks, rendering them individually, and composing the final image [S1, unofficial][S2]. It sets itself apart from traditional bricking by using considerably smaller bricks to exploit void detection and Least Recently Used (LRU) swapping, thereby reducing bus transfer overhead and alleviating the bottleneck of reloading the entire volume per frame [S1, unofficial]. Unlike [Dynamic Rebricking](2823-dynamic-rebricking.md) which adapts brick structure to view or data changes, this method uses fixed uniform bricks when dimensions align, but handles boundaries with partially empty or smaller rest-bricks to maintain memory management optimization [S1, unofficial].

## How it works
**Inputs:** A volumetric dataset stored in main memory, GPU texture memory with limited capacity, and a rendering view (camera position and projection) [G].
**Outputs:** A 2D composited image [G].

**Data Structures:**
1.  **Volume Data:** Stored in main memory as a contiguous array or structured grid [G].
2.  **Bricks:** Uniform 3D sub-volumes of size $b \times b \times b$ voxels, with remainder bricks used when dimensions do not divide evenly [S1, unofficial].
3.  **Texture Memory:** Holds resident bricks as 3D textures [S1, unofficial].
4.  **LRU State:** A tracking mechanism (implicit in OpenGL implementations) to identify the least recently used resident texture for eviction [S1, unofficial].

**Parameters:**
*   $b$: Brick dimension in voxels (assuming cubic bricks). Sources recommend choosing brick sizes considerably smaller than the maximum possible size to increase the probability of bricks being completely void after transfer function application [S1, unofficial].
*   $n$: Overlap size in voxels.
    *   For nearest neighbor interpolation: $n = 0$ [S1, unofficial].
    *   For trilinear interpolation: $n = 1$ voxel in every direction [S1, unofficial].
    *   For pre-integrated rendering or on-the-fly gradient calculation: $n = 2$ voxels (trilinear overlap + 1 additional voxel) [S1, unofficial].
*   $V_{dim}$: Dimensions of the original volume [G].

**Steps:**

1.  **Partitioning:** Split the volume data into uniform texture bricks [S2]. If $V_{dim}$ does not divide evenly into brick dimensions $b$, add an additional layer of partially empty bricks in each direction or use smaller "rest-bricks" to cover the remaining volume [S1, unofficial].
2.  **Overlap Handling:** To ensure continuous tri-linear interpolation across brick boundaries, replicate boundary voxels into adjacent bricks. Specifically, duplicate a plane of voxels at each brick boundary to prevent artifacts such as black strips or holes in isosurfaces [S2][S1, unofficial].
3.  **Memory Management (LRU Swapping):**
    *   Load bricks into video memory as 3D textures [S1, unofficial].
    *   When the amount of data in textures exceeds available texture memory, swap textures between main memory and texture memory using an LRU policy [S1, unofficial].
    *   If a requested brick is not resident in texture memory, load it from main memory, replacing the resident texture identified as least recently used [S1, unofficial].
    *   Once a void brick is swapped out, it is never reloaded, as it is not drawn [S1, unofficial].
4.  **Rendering:**
    *   Process each brick like a separate volume following the basic raycasting concept [S2].
    *   Draw the front faces of the proxy geometry of each brick in depth-sorted order [S2].
    *   For each sample point, obtain color and opacity values from classification and accumulate them using front-to-back blending [S2].
    *   Clamp outbound rays at brick boundaries to ensure correct transitions between bricks [S2].
5.  **Composition:** Compute the final image by alpha blending the resulting fragments from all bricks [S2].

**Formulas:**
*   **Memory Overhead:** The memory overhead percentage due to overlap is approximately:
    $$ \text{Overhead} \approx \left( \frac{3 \cdot n}{b} \right) \cdot 100\% $$
    where $b$ is the brick dimension in voxels (assuming cubic bricks $b \times b \times b$) and $n$ is the overlap size in voxels [S1, unofficial].

**Pseudocode:**

```python
def render_volume_with_bricks(volume_data, camera_pos, transfer_function, brick_size_b, overlap_n):
    """
    Renders a volume using brick-based rendering with LRU swapping and overlap.
    """
    vol_dims = (len(volume_data), len(volume_data[0]), len(volume_data[0][0]))
    num_bricks_x = (vol_dims[0] + brick_size_b - 1) // brick_size_b
    num_bricks_y = (vol_dims[1] + brick_size_b - 1) // brick_size_b
    num_bricks_z = (vol_dims[2] + brick_size_b - 1) // brick_size_b
    
    bricks = []
    for z in range(num_bricks_z):
        for y in range(num_bricks_y):
            for x in range(num_bricks_x):
                x_start, y_start, z_start = x * brick_size_b, y * brick_size_b, z * brick_size_b
                x_end, y_end, z_end = min(x_start + brick_size_b, vol_dims[0]), min(y_start + brick_size_b, vol_dims[1]), min(z_start + brick_size_b, vol_dims[2])
                base_data = volume_data[x_start:x_end, y_start:y_end, z_start:z_end]
                padded_data = pad_edge(base_data, overlap_n)
                bricks.append({'id': (x, y, z), 'data': padded_data, 'dims': (x_end-x_start, y_end-y_start, z_end-z_start)})
                
    max_gpu_memory = 1024  # Capacity in bricks [G]
    lru_cache = LRUCache(max_gpu_memory)
    
    sorted_bricks = sorted(bricks, key=lambda b: distance_to_camera(b['id'], camera_pos, brick_size_b))
    
    final_image = []
    for brick in sorted_bricks:
        if brick['id'] not in lru_cache:
            if len(lru_cache) >= max_gpu_memory:
                evicted = lru_cache.get_lru_key()
                lru_cache.evict(evicted)
            lru_cache.put(brick['id'], brick['data'])
            
        if is_void(brick['data'], transfer_function):
            lru_cache.access(brick['id'])
            continue
            
        brick_image = raycast_brick(lru_cache.get(brick['id']), camera_pos, transfer_function, brick['dims'], overlap_n)
        final_image = alpha_blend(final_image, brick_image)
        lru_cache.access(brick['id'])
        
    return final_image

class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.cache = {}
        self.order = []
    def __len__(self): return len(self.cache)
    def __contains__(self, key): return key in self.cache
    def get(self, key): return self.cache[key]
    def put(self, key, value):
        if key in self.cache: self.order.remove(key)
        self.cache[key] = value
        self.order.append(key)
    def get_lru_key(self): return self.order[0]
    def evict(self, key):
        del self.cache[key]
        self.order.remove(key)
    def access(self, key):
        if key in self.order: self.order.remove(key)
        self.order.append(key)

def pad_edge(data, n):
    # Replicate boundary voxels in all 3 dimensions for interpolation continuity [S2]
    padded = data
    for _ in range(n):
        padded = [padded[0]] + padded + [padded[-1]]
    return padded

def is_void(data, transfer_function):
    # Checks if all voxels in the brick map to zero opacity [S1, unofficial]
    for row in data:
        for voxel in row:
            if transfer_function(voxel) > 0:
                return False
    return True

def distance_to_camera(brick_id, camera_pos, brick_size_b):
    # Approximate depth for sorting proxy geometry [S2]
    x, y, z = brick_id
    center = (x * brick_size_b + brick_size_b / 2, y * brick_size_b + brick_size_b / 2, z * brick_size_b + brick_size_b / 2)
    return (center[0] - camera_pos[0])**2 + (center[1] - camera_pos[1])**2 + (center[2] - camera_pos[2])**2

def raycast_brick(texture, camera_pos, transfer_function, dims, overlap_n):
    # Iterative front-to-back raycasting within brick bounds [S2]
    image = []
    for y in range(dims[1]):
        row = []
        for x in range(dims[0]):
            color, opacity = 0.0, 0.0
            for z in range(dims[2]):
                sample = texture[z][y][x]
                c, o = transfer_function(sample)
                alpha = o * (1.0 - opacity)
                color += c * alpha
                opacity += alpha
                if opacity >= 1.0:
                    break
            row.append((color, opacity))
        image.append(row)
    return image

def alpha_blend(image1, image2):
    # Compose brick fragments into final image [S2]
    result = []
    for r1, r2 in zip(image1, image2):
        row = []
        for (c1, o1), (c2, o2) in zip(r1, r2):
            alpha = o2 * (1.0 - o1)
            c = c1 * o1 + c2 * alpha
            o = o1 + alpha
            row.append((c, o))
        result.append(row)
    return result
```

## Subtopics

### [Bricking with Boundary Voxel Duplication](4198-bricking-with-boundary-voxel-duplication.md)
Bricking with Boundary Voxel Duplication is a technique to solve incorrect interpolation at texture tile boundaries in 3D volume rendering by duplicating a plane of voxels at each brick boundary. It prevents black strips at cut boundaries in composited images by ensuring features at the cut are not dropped. It sets itself apart from sibling methods like [Level-wise Texture Merging](5274-level-wise-texture-merging.md) by focusing on spatial continuity of the scalar field at fixed brick boundaries rather than hierarchical level-of-detail transitions, and from [Wang Cubes for Volume Rendering](6980-wang-cubes-for-volume-rendering.md) by addressing hardware texture interpolation artifacts rather than geometric surface representation.

### [Level-wise Texture Merging](5274-level-wise-texture-merging.md)
Level-wise texture merging minimizes texture memory overhead in hierarchical volume rendering by merging the texture data of adjacent bricks into single, larger texture maps. It creates an octree-like hierarchy where the number of bricks sharing a single texture map is multiplied by a factor of 8 on each consecutive level. This method reduces the number of distinct texture objects required for coarse levels of detail compared to assigning individual textures to every brick.

### [Wang Cubes for Volume Rendering](6980-wang-cubes-for-volume-rendering.md)
Wang Cubes is a texture synthesis method that creates non-periodic 3D textures using cubes with colored faces to overcome the memory and time limits of storing high-resolution volumetric data. It reduces texture memory usage by storing a small set of synthesized cube templates rather than the full volume, allowing the generation of arbitrary-sized textures on the fly. Unlike [Bricking with Boundary Voxel Duplication](4198-bricking-with-boundary-voxel-duplication.md) which duplicates boundary voxels for continuity, Wang Cubes enforce continuity through face-color matching and explicit edge-volume synthesis.

### [Virtual Texture Management with Bricking](12603-virtual-texture-management-with-bricking.md)
Virtual Texture Management with Bricking handles textures larger than available texture memory by virtually partitioning them into bricks, managing their loading and sorting transparently to prevent fragmentation. It sets itself apart from its siblings by automating the padding of non-power-of-two dimensions and the virtualization of oversized textures without requiring manual brick creation or management from the application layer.

### View-dependent brick upload
View-dependent brick upload is a variant where the unit of texture copy is a brick (e.g., 64 × 64 × 64 voxels), allowing the render to copy only the bricks that the view needs, avoiding copying whole slices for oblique views [S3, unofficial]. The render copies only the out-of-date bricks that its view crosses: MPR views copy bricks crossed by the plane or slab, and 3D views copy bricks in the view volume [S3, unofficial]. The copy respects the limit for each render (rendering.reducedTextureFill) and copies bricks nearest to the centre of the view first [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** Rendering time depends on the number of non-void bricks and the cost of raycasting per brick [S1, unofficial][S2]. Void detection significantly reduces the number of bricks processed [S1, unofficial].
*   **Memory Complexity:** Memory usage is bounded by the GPU texture memory capacity plus the storage for the volume data in main memory [G]. The overhead due to overlap is approximately $(3 \cdot n / b) \cdot 100\%$ [S1, unofficial].
*   **Measured Performance:** Using smaller bricks alleviates the bus bottleneck by avoiding the transfer of the entire volume per frame, as void bricks are swapped out and not reloaded [S1, unofficial]. It also improves data locality, resulting in less cache trashing on the graphics card [S1, unofficial].
*   **Scaling:** Performance scales with the number of bricks and the efficiency of the LRU policy [G]. Smaller bricks increase the chance of void detection but increase overhead due to overlap [S1, unofficial].
*   **Strengths:** Reduces bus traffic, improves data locality, handles volumes larger than GPU memory, and supports empty-space skipping [S1, unofficial][S2].
*   **Limitations:** Requires careful selection of brick size to balance overlap overhead and void detection probability [S1, unofficial]. Graphics cards may require power-of-2 texture dimensions, necessitating padding or rest-bricks [S1, unofficial].
*   **When to use:** When rendering large volumetric datasets that exceed GPU memory, especially when significant portions of the volume are void or low-opacity [S1, unofficial][S2].
*   **When not to use:** When the volume is small enough to fit entirely in GPU memory without bricking, or when the overhead of overlap and LRU swapping outweighs the benefits of void detection [G].

## Background
The method originates from the need to render volumetric data sets that exceed the size of the texture memory of graphics hardware [S1, unofficial]. Traditional bricking loaded large bricks sequentially, transferring the entire volume over the bus per frame [S1, unofficial]. The approach of using smaller bricks with LRU swapping and void detection was introduced to alleviate this bus bottleneck [S1, unofficial]. The concept of subdividing volume data sets into smaller blocks for distributed processing and empty-space-skipping is also widely used in cluster-based volume rendering [S2].
