# Bricking

Also called: Block replacement rendering, Brick-based memory management, Divide-and-conquer volume rendering, Large Volume Rendering via Partitioning, Supervolumes, Volume Bricking, Volumetric texture bricking, Voxel bricking

## Overview
Bricking is a memory management technique for volume rendering that partitions a volumetric dataset larger than the available GPU memory (or texture unit limits) into smaller, fixed-size sub-volumes called "bricks" [S1][S2, S3, unofficial]. Each brick is loaded into GPU memory, rendered independently, and the resulting images are composited to form the final image [S1][S3, unofficial]. It differs from [Chunk-based Voxel Data Structure](1818-chunk-based-voxel-data-structure.md) by typically using uniform, fixed-size blocks optimized for texture sampling, and from [Tile-based Volume Ray Marching](1678-tile-based-volume-ray-marching.md) by operating on 3D spatial subdivisions rather than 2D screen tiles [S2, unofficial][S4, unofficial].

## How it works
**Inputs:** A large 3D volumetric dataset $V$ with dimensions $(D_x, D_y, D_z)$ exceeding hardware limits [S1][S2, S3, unofficial].
**Outputs:** A final 2D image $I$ [S3, unofficial].

**Data Structures:**
The volume is partitioned into a grid of bricks $B_{i,j,k}$ [S2, unofficial].
*   **Brick Size:** Typically limited by hardware constraints, such as a maximum of 256 voxels per edge for VolumePro [S7, unofficial] or GPU texture limits [S3, unofficial]. Optimal sizes are typically $64^3$ or $128^3$ cubes depending on the dataset [S6].
*   **Overlap:** To handle interpolation artifacts, bricks include overlapping boundary layers where a plane of voxels is duplicated at each brick boundary [S5, unofficial]. The overlap count follows the formula $\text{Overlap} = N + 1$, where $N$ is the distance to the neighbor voxel accessed for gradient calculation [S3, unofficial]. For non-lit visualization, $N=1$ (1 voxel overlap); for lit visualization, $N=2$ (2 voxel overlap) [S3, unofficial].

**Steps:**
1.  **Partitioning:** Divide the original volume into uniform sub-volumes (bricks) such that each fits within the GPU's texture memory [S2, S3, unofficial]. If global dimensions are not divisible by the desired brick size, bricks at the farthest boundaries from the origin take the residual size ($D \pmod{\text{brick\_size}}$) [S3, unofficial].
2.  **Overlap Handling:** Duplicate voxels at the boundaries of adjacent bricks to ensure consistent texture interpolation across brick edges [S5, unofficial]. Without this, texture units lack the information to interpolate correctly across boundaries, causing visible artifacts [S5, unofficial].
3.  **Loading:** Transfer bricks from host memory to GPU memory [S2, unofficial]. If the supervolume does not fit in GPU memory, bricks are swapped in and out using an oldest-out-first strategy [S2, unofficial]. Caching loaded blocks avoids multiple uploads [S2, unofficial].
4.  **Sorting:** Order bricks by distance from the observer to the center of the brick [S3, unofficial]. Render far bricks first, near bricks last to prevent distant pixels from overwriting closer ones [S3, unofficial].
5.  **Rendering:** Render each brick independently using a volume rendering algorithm (e.g., raycasting) [S3, unofficial]. Apply sub-pixel accurate initial offsets in $x$ and $y$ to align rays correctly when passing between blocks [S7, unofficial]. An initial $z$ offset maintains correct supersampling in the $z$-direction between blocks [S7, unofficial].
6.  **Clipping:** Pass a clipping box to the shader for each brick, derived from the brick texture without the overlap offset, to ensure only non-overlapping voxels contribute to the image and prevent double-counting at boundaries [S3, unofficial].
7.  **Compositing:** Composite the resulting base planes from back-to-front into a single base plane [S7, unofficial]. Warp the resulting blended base plane to the final image coordinates [S7, unofficial].

**Pseudocode:**
```python
import math
import numpy as np

def render_bricked_volume(volume_data, brick_size, overlap_voxels, camera_origin, camera_direction, image_width, image_height):
    # 1. Determine grid of bricks
    dims = volume_data.shape
    num_bricks_x = math.ceil(dims[0] / brick_size)
    num_bricks_y = math.ceil(dims[1] / brick_size)
    num_bricks_z = math.ceil(dims[2] / brick_size)

    # 2. Initialize final image accumulator
    final_image = np.zeros((image_height, image_width, 4), dtype=np.float32)

    # 3. Calculate brick centers and sort far-to-near
    brick_list = []
    for k in range(num_bricks_z):
        for j in range(num_bricks_y):
            for i in range(num_bricks_x):
                center = np.array([(i + 0.5) * brick_size, (j + 0.5) * brick_size, (k + 0.5) * brick_size])
                dist = np.dot(center - camera_origin, camera_direction)
                brick_list.append((dist, i, j, k))
    brick_list.sort(key=lambda x: x[0])

    # 4. Iterate over sorted bricks
    for dist, i, j, k in brick_list:
        # Extract brick with overlap
        x_start = max(0, i * brick_size - overlap_voxels)
        x_end = min(dims[0], (i + 1) * brick_size + overlap_voxels)
        y_start = max(0, j * brick_size - overlap_voxels)
        y_end = min(dims[1], (j + 1) * brick_size + overlap_voxels)
        z_start = max(0, k * brick_size - overlap_voxels)
        z_end = min(dims[2], (k + 1) * brick_size + overlap_voxels)

        brick = volume_data[x_start:x_end, y_start:y_end, z_start:z_end]

        # 5. Render brick to a temporary buffer
        brick_buffer = np.zeros((image_height, image_width, 4), dtype=np.float32)
        # Raycasting loop omitted: standard front-to-back DVR with tri-linear sampling
        # Apply sub-pixel offsets in x and y for ray alignment [S7, unofficial]
        # Apply z offset for supersampling continuity [S7, unofficial]
        # Use clipping box (brick without overlap) to prevent double-counting [S3, unofficial]

        # 6. Composite brick result into final image (back-to-front order handled by sort)
        alpha_base = final_image[:, :, 3]
        alpha_brick = brick_buffer[:, :, 3]
        color_base = final_image[:, :, :3]
        color_brick = brick_buffer[:, :, :3]
        alpha_out = alpha_base + alpha_brick * (1.0 - alpha_base)
        safe_alpha = np.where(alpha_out == 0, 1.0, alpha_out)
        color_out = (color_base * alpha_base + color_brick * alpha_brick * (1.0 - alpha_base)) / safe_alpha
        final_image[:, :, :3] = color_out
        final_image[:, :, 3] = alpha_out

    return final_image
```

## Subtopics

### [Dynamic Rebricking](2823-dynamic-rebricking.md)
A scheme where bricks are stored on disk in a large size (e.g., $256^3$) but presented to the renderer as small bricks (e.g., $32^3$) [2823-dynamic-rebricking.md]. Small bricks are dynamically generated from large ones on request to balance disk performance (favored by large bricks) with early ray termination/empty space skipping (favored by small bricks) [2823-dynamic-rebricking.md].

### [Brick-based Volume Rendering with Overlap and LRU Swapping](3782-brick-based-volume-rendering-with-overlap-and-lru-swapping.md)
Divides a volume into smaller 3D texture bricks to manage memory, improve data locality, and reduce bus transfer overhead by avoiding reloading void bricks [3782-brick-based-volume-rendering-with-overlap-and-lru-swapping.md].

### [Scalable Multi-field Bricking](6847-scalable-multi-field-bricking.md)
Technique to visualize large video datasets that cannot fit in GPU memory by subdividing the domain into smaller sections (bricks) handled by the GPU [6847-scalable-multi-field-bricking.md]. Uses a ring-buffer data structure for dynamic swapping [6847-scalable-multi-field-bricking.md].

### [Brick-based volume rendering with packed textures](7106-brick-based-volume-rendering-with-packed-textures.md)
Not given in the sources.

### Brick-based View-Aligned Rendering
An approach by Weiskopf et al. (2004) that breaks 3D volumes into smaller bricks and reorganizes them into different orientations to average out performance variations from different viewing angles [S9].
*   **Pitfalls:** The entire volume must be within the viewing frustum for this approach to work [S9]. It requires a data pre-processing stage, which may not be feasible for in-situ visualizations [S9]. Deriving the best brick resolution and handling overlap between neighboring bricks complicates the pre-processing [S9].

## Operating characteristics
*   **Time Complexity:** Rendering time increases due to limited PCI download bandwidth when loading large supervolumes [S3, unofficial]. Real-time rendering speed is hard to achieve with simple bricking because CPU-GPU inter-connection speed is insufficient for the required data transfer rates [S1].
*   **Memory Complexity:** Bricking does not reduce the total memory required to represent the original data; it increases it due to extra layers (overlap) required for each sub-volume to eliminate inconsistent interpolation at brick boundaries [S1][S2, unofficial].
*   **Strengths:** Allows rendering of volumes larger than GPU memory [S1][S2, unofficial]. Enables parallel rendering by distributing sub-volumes to data servers (e.g., in ParaView) [S1].
*   **Limitations:** High data transfer overhead [S1]. Artifacts at brick boundaries if overlap is not handled correctly [S2, unofficial]. Performance variations depending on viewing angle if not reorganized (e.g., view-aligned) [S5, unofficial].
*   **When to use:** When the dataset exceeds available GPU texture memory or hardware limits (e.g., 256 voxels/edge) [S3, unofficial]. When parallel rendering across multiple nodes is desired [S1].
*   **When not to use:** When real-time performance is critical and bandwidth is a bottleneck [S1]. When in-situ visualization pre-processing is not feasible [S5, unofficial].

## Background
Bricking was developed to address the limitations of early GPU hardware, which had small texture memory capacities (e.g., 128 MB on VolumePro PCI cards) and limits on texture dimensions (e.g., 256 voxels per edge) [S3, unofficial]. The VolumePro system (1999) popularized the "supervolume" concept, where software partitions the volume, handles data duplication, and composites results [S3, unofficial]. Later, with the rise of general-purpose GPU computing, bricking was adapted for GPU-based raycasting to handle massive out-of-core datasets [S4, unofficial]. It is used in parallel rendering software like ParaView, where it serves as a form of data parallelism [S1].
