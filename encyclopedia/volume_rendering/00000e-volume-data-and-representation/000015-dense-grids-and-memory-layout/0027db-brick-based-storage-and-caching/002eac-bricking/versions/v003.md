# Bricking

Also called: Brick Processing, Brick Processing for Large Volumes, Brick-Based Memory Management, Bricked Volume Rendering, Volume Bricking, Volume Bricks, Voxel bricking

## Overview
Bricking is a memory management technique that subdivides volumetric datasets larger than the available GPU texture memory into smaller, equally-sized sub-volumes called bricks, allowing them to be loaded on-demand and rendered individually [S2, unofficial][S3, unofficial][S5, unofficial]. It solves the hardware limitation where a single 3D texture cannot hold the entire volume, enabling out-of-core visualization by treating the GPU memory as a cache for these bricks [S2, unofficial][S6, unofficial]. Unlike [Brick-based Volume Raycasting](3341-brick-based-volume-raycasting.md), which focuses on the ray traversal logic, or [Dynamic Rebricking](2823-dynamic-rebricking.md), which decouples physical and logical sizes, standard Bricking uses fixed-size bricks for both storage and rendering, relying on overlap and sorting to maintain visual continuity [S3, unofficial].

## How it works
**Inputs:** A 3D volumetric dataset stored in CPU memory (RAM) with global dimensions $D_x, D_y, D_z$ and voxel data type (e.g., 8-bit unsigned integer).
**Outputs:** A final composited image on the GPU framebuffer.

**Data Structures:**
1.  **Brick Metadata:** For each brick, store:
    *   Origin voxel coordinates $(o_x, o_y, o_z)$ in the global volume.
    *   Logical brick dimensions $(B_x, B_y, B_z)$ [S3, unofficial].
    *   Overlap size $N$ (number of duplicated voxels per side) [S3, unofficial].
    *   Bounding box of the full brick (including overlap) [S3, unofficial].
    *   Bounding box for clipping (excluding overlap) [S3, unofficial].
2.  **Brick Data:** A contiguous memory block for each brick. The stored voxel count per brick is:
    $$ V_{brick} = (B_x + 2N)(B_y + 2N)(B_z + 2N) $$
    where $B_x, B_y, B_z$ are the logical dimensions and $N$ is the overlap [S3, unofficial][S4, unofficial]. For tri-linear filtering, $N=1$; for tri-cubic filtering, $N=2$ or $3$ [S3, unofficial][S7].

**Steps:**
1.  **Subdivision:** Divide the global volume into a 3D grid of bricks. If global dimensions are not divisible by the desired brick size, bricks at the farthest boundaries from the origin take the residual size: $size_{residual} = global\_dim \pmod{brick\_size}$ [S3, unofficial].
2.  **Overlap Generation:** Duplicate voxels from neighboring bricks into the current brick's boundary layers to support interpolation. For a logical brick of size $B$, the stored size is $(B+2N)^3$ [S3, unofficial][S4, unofficial]. This adds approximately 10% overhead for $32^3$ bricks with $N=1$ [S4, unofficial].
3.  **Sorting:** Calculate the distance from the camera/observer to the center of each brick. Sort bricks in back-to-front order (farthest to nearest) to ensure correct alpha compositing and enable early ray termination [S3, unofficial][S7].
4.  **Culling:** Optionally, cull bricks that do not contribute to the final image (e.g., outside the view frustum or fully empty) to reduce upload overhead [S10, unofficial][S7].
5.  **Upload:** Transfer each brick from CPU RAM to GPU local memory (texture memory) [S3, unofficial]. If GPU memory is full, use an LRU (Least Recently Used) or oldest-out-first strategy to swap bricks [S2, unofficial][S3, unofficial].
6.  **Rendering:** For each brick in sorted order:
    *   Bind the brick as a 3D texture.
    *   Apply a texture matrix transformation to map the brick's local coordinates to the global view space. The transformation typically involves:
        1.  Translate by $(0.5, 0.5, 0.5)$ [S3, unofficial].
        2.  Translate by the normalized difference between the brick's global center and the volume center [S3, unofficial].
        3.  Scale by the ratio of the volume diagonal to the brick dimensions [S3, unofficial].
        4.  Multiply by the inverse of the current modelview rotation [S3, unofficial].
    *   Render the brick using proxy planes (quads perpendicular to the view direction) sized to the volume diagonal [S3, unofficial].
    *   Apply a clipping box to the shader to exclude the overlapping boundary voxels, preventing double-counting of shared voxels [S3, unofficial].
    *   Composite the result into the framebuffer [S7].
7.  **Cleanup:** Unload bricks from GPU memory when they are no longer needed to free space for subsequent bricks [S2, unofficial].

**Pseudocode:**
```python
def render_bricked_volume(volume_data, camera, brick_size, overlap):
    # 1. Subdivide and generate bricks
    bricks = []
    dims = volume_data.dimensions
    for x in range(0, dims.x, brick_size):
        for y in range(0, dims.y, brick_size):
            for z in range(0, dims.z, brick_size):
                # Handle residual bricks at boundaries
                bx = min(brick_size, dims.x - x)
                by = min(brick_size, dims.y - y)
                bz = min(brick_size, dims.z - z)
                
                # Extract data with overlap
                # Note: In practice, this requires careful indexing to duplicate neighbors
                brick_data = extract_bricks_with_overlap(volume_data, x, y, z, bx, by, bz, overlap)
                
                # Calculate center for sorting
                center = (x + bx/2, y + by/2, z + bz/2)
                dist = distance(camera.position, center)
                
                bricks.append({
                    'data': brick_data,
                    'origin': (x, y, z),
                    'size': (bx, by, bz),
                    'overlap': overlap,
                    'distance': dist
                })
    
    # 2. Sort back-to-front
    bricks.sort(key=lambda b: b['distance'], reverse=True)
    
    # 3. Render
    for brick in bricks:
        # Check if brick is in GPU cache; if not, upload
        if not is_in_gpu_cache(brick):
            upload_to_gpu(brick['data'])
        
        # Apply texture transformation
        apply_texture_matrix(brick['origin'], brick['size'], camera)
        
        # Render proxy planes with clipping
        render_proxy_planes(clip_box=brick['size'] - 2*brick['overlap'])
        
        # Optional: Read back framebuffer for early termination check
        # if early_termination_detected():
        #     break
```

**Parameters:**
*   **Brick Size:** Typically $64^3$ or $128^3$ voxels [S7]. Must fit in GPU memory (typically 128MB–512MB) [S3, unofficial]. ATI cards historically required power-of-2 dimensions, while NVIDIA allowed any size [S3, unofficial].
*   **Overlap ($N$):** 1 voxel for tri-linear filtering, 2–3 voxels for tri-cubic filtering [S3, unofficial][S7].
*   **Max Block Size:** Hardware limits may cap dimensions at 256 voxels per edge [S9, unofficial] or 4096x4096 texture limits [S12, unofficial].

**Edge Cases and Pitfalls:**
*   **Boundary Artifacts:** Naive subdivision causes interpolation errors at brick boundaries because texture units lack neighbor information. Overlap is mandatory [S6, unofficial][S4, unofficial].
*   **Double Counting:** If a ray exits exactly on a border, samples may be blended twice. Clipping boxes must exclude the overlap region [S9, unofficial][S3, unofficial].
*   **Performance Bottleneck:** CPU-GPU transfer speed is the primary bottleneck. Caching is crucial [S2, unofficial]. Too small bricks increase draw call overhead; too large bricks reduce the benefit of empty-space skipping [S7][S10, unofficial].
*   **Memory Management:** Sending a texture to the GPU creates a copy in RAM on some architectures (e.g., older NVIDIA Quadro). Failure to unload bricks causes RAM overflow [S3, unofficial].

## Subtopics

### [Dynamic Rebricking](2823-dynamic-rebricking.md)
Dynamic Rebricking decouples the physical storage size of bricks from their logical rendering size. It generates small logical bricks from large physical bricks on demand to optimize disk I/O throughput (large bricks) and ray-casting efficiency (small bricks) [2823-dynamic-rebricking.md].

### [Brick-based Volume Rendering with Overlap and LRU Swapping](3782-brick-based-volume-rendering-with-overlap-and-lru-swapping.md)
This variant manages volumes exceeding GPU memory by partitioning data into small 3D texture bricks, rendering them individually, and using LRU swapping. It distinguishes itself by using significantly smaller bricks than standard bricking to exploit void detection and reduce bus transfer overhead [3782-brick-based-volume-rendering-with-overlap-and-lru-swapping.md].

### [Scalable Multi-field Bricking](6847-scalable-multi-field-bricking.md)
This method partitions data only in the temporal dimension to handle video datasets that exceed GPU memory. It cycles through a fixed number of texture objects to visualize dynamic frames, treating time as the primary subdivision axis rather than space [6847-scalable-multi-field-bricking.md].

### [Brick-based volume rendering with packed textures](7106-brick-based-volume-rendering-with-packed-textures.md)
This technique packs only non-transparent bricks into a dense 3D texture, using an auxiliary "Index-Texture" to map spatial coordinates to the compacted layout. This reduces memory bandwidth and storage compared to storing all bricks in a regular grid [7106-brick-based-volume-rendering-with-packed-textures.md].

### Brick-based View-Aligned Rendering
Introduced by Weiskopf et al. (2004), this approach reorganizes bricks into different orientations to average out performance variations from viewing angles. It requires the entire volume to be in the frustum and involves a pre-processing stage to derive optimal resolutions and handle overlaps [S13].

### GPU-based Brick Assembly
A CUDA kernel method that assembles compressed bricks into a 3D texture format. It distributes work across 64-thread blocks, assigning each thread an x-coordinate to ensure memory coalescing. This achieves ~5 GB/s throughput for on-device copying, limited by the internal 3D CUDA array format [S1].

### Parallel Bricking
A method for rendering large datasets by splitting data into blocks, rendering each in a separate pass or process, and compositing the results back-to-front. Artifacts may arise due to discontinuous sampling and gradient computation at block edges [S14, unofficial].

## Operating characteristics
*   **Time Complexity:** Rendering time is dominated by the number of bricks $N_b$ and the transfer time $T_{transfer}$. Total time $\approx N_b \times (T_{upload} + T_{render})$. Sorting is $O(N_b \log N_b)$ [S3, unofficial].
*   **Memory Complexity:** Requires CPU memory for the full volume and GPU memory for one (or a few) bricks. GPU memory usage is $O(B^3)$ where $B$ is brick size [S2, unofficial].
*   **Performance:** Performance is heavily dependent on PCI-e bandwidth. Simple DVR is ~3x faster than tri-cubic DVR, despite the latter requiring 8x samples, due to sampling overhead [S7]. On-device copy to 3D CUDA arrays can be slow (~5 GB/s vs 110 GB/s max) [S1].
*   **Strengths:** Enables rendering of volumes far larger than GPU memory; simple to implement; supports standard raycasting algorithms [S3, unofficial].
*   **Limitations:** Does not compress data (may even increase size due to overlap); transfer overhead is high; artifacts at boundaries if overlap is mishandled; requires careful sorting [S3, unofficial][S5, unofficial].
*   **When to Use:** When the volume fits in RAM but not GPU memory, and real-time performance is not strictly dependent on minimizing transfer latency.
*   **When Not to Use:** When the volume fits entirely in GPU memory (use direct 3D textures); when compression is required (use [Brick-based Volume Rendering with Packed Textures](7106-brick-based-volume-rendering-with-packed-textures.md)); when dynamic updates are frequent and I/O is the bottleneck (use [Dynamic Rebricking](2823-dynamic-rebricking.md)).

## Background
Bricking was introduced to circumvent the fixed memory limits of GPU texture hardware (e.g., 256 voxels per edge or 4096x4096 limits) [S9, unofficial][S12, unofficial]. It is based on the divide-and-conquer principle [S5, unofficial]. Early implementations used 2D textures for octants [S8, unofficial][S12, unofficial], later evolving to 3D textures. It is used in parallel rendering software like ParaView for data parallelism [S5, unofficial][S11] and in out-of-core visualization systems [S2, unofficial].
