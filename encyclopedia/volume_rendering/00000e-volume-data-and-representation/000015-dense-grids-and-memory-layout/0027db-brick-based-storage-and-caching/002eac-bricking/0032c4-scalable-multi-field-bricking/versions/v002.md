# Scalable Multi-field Bricking

Also called: Bricked video spans, Bricking-based Volume Rendering, Dynamic bricking

## Overview
Scalable Multi-field Bricking is a rendering method for large video datasets that partitions data only in the temporal dimension to overcome GPU memory limitations [S1, unofficial]. It supports dynamic updates via a loop, allowing the visualization of video spans, flow geometry, and dynamic streamlines by cycling through a fixed number of texture objects [S1, unofficial]. Unlike traditional spatial bricking, this method treats the temporal axis as the primary dimension for subdivision, enabling the handling of datasets where the total number of frames $N$ exceeds the GPU's capacity to store all frames simultaneously [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A video volume $V$ consisting of $N$ consecutive 2D image frames $I_i$ [S1, unofficial].
*   **Input:** A pre-computed seed point list for flow geometry, shared across bricks [S1, unofficial].
*   **Output:** Rendered image with volume data and flow geometry [S1, unofficial].

**Data Structures:**
1.  **Logical Brick:** Described by two integer values: the starting frame number and the number of frames in the brick [S1, unofficial].
2.  **Ring Buffer:** A pointer structure containing $k$ 3D texture objects [S1, unofficial].
3.  **Shared Seed List:** An input used by all bricks [S1, unofficial]. It contains a flag for each point indicating whether it is used for constructing geometry for the specific brick [S1, unofficial].

**Parameters:**
*   $N$: Total number of frames in the video volume.
*   $K$: Total number of bricks the volume is divided into ($K \ge 1$).
*   $k$: Number of bricks rendered at a time ($1 \le k \le K$).
*   $m$: Number of frames per brick.
*   $n$: Number of frames currently held in GPU memory.
*   Condition: $k \cdot m = n$, with $n \le N$. If $n < N$, dynamic bricking is applied [S1, unofficial].

**Steps:**
1.  **Partitioning:** Divide the video volume $V$ into $K$ bricks [S1, unofficial]. Each brick $B_j$ contains $m$ frames. Bricks are disjoint ($B_j \cap B_l = \emptyset$ for $j \neq l$) [S1, unofficial].
2.  **Initialization:** Allocate memory for $k$ 3D texture objects [S1, unofficial]. Fill the first $k$ bricks with their corresponding video frames [S1, unofficial].
3.  **Dynamic Update Loop:** Render the current $k$ bricks [S1, unofficial]. Reassign pointers in a cyclic way to form a ring-buffer structure [S1, unofficial]. The last texture object in the ring buffer is overwritten with newly entering frames [S1, unofficial]. Update the logical brick descriptions (starting frame, frame count) for the next iteration [S1, unofficial].
4.  **Rendering:** For each fragment, transform Cartesian texture coordinates to horseshoe coordinates [S1, unofficial]. Perform a 3D texture lookup [S1, unofficial]. Apply a transfer function to map volume data to color [S1, unofficial].

**Formulas:**
The mapping from Cartesian coordinates $P$ (texture coordinates) to cylindrical horseshoe coordinates $C$ is defined by the fragment program logic [S1, unofficial]:

1.  Scale texture coordinates to $[-1, 1]$:
    $$ txCrd.x = ((txCrd.x \cdot 2.0) - 1.0) \cdot (-1.0) $$
    This maps the range to permit cylindrical horseshoe coordinates between $-\pi$ and $\pi$ [S1, unofficial].

2.  Compute radius $r$ and angle $\theta$ in the $xz$-plane:
    $$ rp.x = \sqrt{txCrd.x^2 + txCrd.z^2} $$
    $$ rp.y = \text{atan2}(txCrd.z, txCrd.x) $$
    This leads to a half circle in the $xz$ plane [S1, unofficial].

3.  Map to local brick coordinates $lkup = (u, v, w)$:
    $$ lkup.x = \frac{rp.x - g\_fInRad}{g\_fOutRad - g\_fInRad} $$
    $$ lkup.y = txCrd.y $$
    $$ tmpZ = \frac{rp.y}{\pi} $$
    $$ lkup.z = (tmpZ - g\_vScaleCrd.x) \cdot g\_vScaleCrd.y $$
    Where $g\_fInRad$ and $g\_fOutRad$ are the inner and outer radii of the horseshoe, and $g\_vScaleCrd$ are scaling parameters for the temporal dimension [S1, unofficial].

4.  Lookup and Color:
    $$ volData = \text{tex3D}(VOLsmp, lkup) $$
    $$ Output.RGBColor = \text{tex1D}(TFsmp, volData.x) $$

**Pseudocode:**
```python
import math

# Standard GPU operations defined as [G]
def allocate_3d_texture(depth): return [None] * depth
def fill_texture(tex, frames): 
    for i, f in enumerate(frames): tex[i] = f
def render_brick(tex, tf): 
    for v in tex: yield tf(v)
def tex3D_lookup(u, v, w): return 0.0  # Hardware texture fetch [G]
def tex1D_lookup(val): return (val, val, val)  # Transfer function lookup [G]

def initialize(video_volume, k, m):
    ring_buffer = [allocate_3d_texture(m) for _ in range(k)]
    for i in range(k):
        start_idx = i * m
        fill_texture(ring_buffer[i], video_volume[start_idx : start_idx + m])
    current_window_start = 0
    return ring_buffer, current_window_start

def render_active_bricks(ring_buffer, transfer_function):
    for tex_obj in ring_buffer:
        for color in render_brick(tex_obj, transfer_function):
            pass  # Write to framebuffer [G]

def update_ring_buffer(ring_buffer, current_window_start, video_volume, k, m):
    overwrite_idx = (current_window_start // m) % k
    new_start = current_window_start + k * m
    new_end = new_start + m
    if new_end <= len(video_volume):
        fill_texture(ring_buffer[overwrite_idx], video_volume[new_start : new_end])
    return (current_window_start + k * m) % len(video_volume)

def fragment_program(txCrd, g_fInRad, g_fOutRad, g_vScaleCrd):
    txCrd_x = ((txCrd.x * 2.0) - 1.0) * (-1.0)
    rp_x = math.sqrt(txCrd_x**2 + txCrd.z**2)
    rp_y = math.atan2(txCrd.z, txCrd_x)
    lkup_x = (rp_x - g_fInRad) / (g_fOutRad - g_fInRad)
    lkup_y = txCrd.y
    tmp_z = rp_y / math.pi
    lkup_z = (tmp_z - g_vScaleCrd.x) * g_vScaleCrd.y
    vol_data = tex3D_lookup(lkup_x, lkup_y, lkup_z)
    output_color = tex1D_lookup(vol_data)
    return output_color
```

**Edge Cases and Pitfalls:**
*   **Memory Limit:** If $N > k \cdot m$, dynamic bricking is mandatory [S1, unofficial].
*   **Seed Point Consistency:** The shared seed point list must correctly flag points for each brick to ensure flow geometry is constructed accurately across brick boundaries [S1, unofficial].
*   **Coordinate Mapping:** The mapping from Cartesian to horseshoe coordinates must handle the discontinuity at the cut of the horseshoe (typically at $\pi$ or $-\pi$) to avoid artifacts [S1, unofficial].

## Subtopics

### Dynamic Rebricking
A method that adjusts the brick structure dynamically based on view-dependent criteria or memory availability, unlike the fixed temporal partitioning of Scalable Multi-field Bricking [G]. [Link](2823-dynamic-rebricking.md)

### Brick-based Volume Rendering with Overlap and LRU Swapping
Uses spatial bricking with overlap to reduce artifacts and LRU swapping for memory management, contrasting with the temporal-only partitioning and ring-buffer approach of Scalable Multi-field Bricking [G]. [Link](3782-brick-based-volume-rendering-with-overlap-and-lru-swapping.md)

### Brick-based volume rendering with packed textures
Focuses on efficient memory layout of spatial bricks using texture packing, whereas Scalable Multi-field Bricking focuses on temporal partitioning for video data [G]. [Link](7106-brick-based-volume-rendering-with-packed-textures.md)

## Operating characteristics
*   **Strengths:** Enables interactive rendering of video volumes that exceed GPU memory [S1, unofficial]. Supports multi-field visualization (volume + flow geometry) within the same bricking framework [S1, unofficial].
*   **Limitations:** Limited to temporal partitioning [S1, unofficial]. Requires pre-computation of optical flow and seed points [S1, unofficial].
*   **When to use:** Ideal for large video datasets (e.g., time-varying scalar fields) where the spatial resolution is manageable but the temporal depth is not [S1, unofficial].

## Background
Scalable Multi-field Bricking was introduced in the context of the VVR (Video Volume Renderer) system by Botchen, Chen, Weiskopf, and Ertl [S1, unofficial]. The work was part of a project supporting a user study on visual signatures in video visualization [S1, unofficial]. The method adapts traditional volume bricking techniques, which typically partition data spatially, to partition data temporally for video streams [S1, unofficial]. It builds on earlier work in GPU-assisted volume rendering and optical flow estimation [S1, unofficial].
