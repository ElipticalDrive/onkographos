# Address Translation

Also called: Page table lookup, Virtual to physical address mapping

## Overview
Address translation is the process of mapping virtual volume coordinates (specifying sample locations along viewing rays) to physical addresses (coordinates in actual texture space) to access volume data stored in individual bricks, enabling out-of-core rendering [S1]. It allows the renderer to specify sample locations in a unified space covering the whole bounding box of the volume, independent of individual brick storage, and then resolve the actual texture coordinates where the brick's data resides [S1]. This method is distinct from hierarchical approaches like octree rendering, which can be viewed as address translation where the octree itself acts as a hierarchical page table and tree traversal performs the lookup [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** Virtual volume coordinates $(u, v, w)$ representing a sample location along a viewing ray, typically normalized in a $[0,1]^3$ unit cube covering the entire volume bounding box [S1].
*   **Output:** Physical texture coordinates $(u', v', w')$ pointing to the specific sub-region within a texture (e.g., a 3D texture or packed texture) that stores the data for the brick containing the sample [S1].

**Data Structures:**
*   **Page Table:** A data structure storing the mapping from virtual addresses to physical addresses [S1]. In the context of bricked volumes, a "page" refers to a volume brick [S1].
*   **Index Texture:** The page table is commonly stored in a linear texture (e.g., a single 3D texture) with one entry (texel) per page (brick) [S1]. Each texel contains the information necessary to translate the virtual address to the physical address for that specific brick [S1].

**Steps:**
1.  **Brick the Volume:** The original volume data is divided into bricks for out-of-core rendering [S1].
2.  **Store Page Table:** Construct the page table (index texture) where each entry maps a virtual brick identifier to its current physical storage location (texture coordinates) [S1].
3.  **Translate Coordinates:** For each sample along a viewing ray:
    a. Identify the virtual brick containing the sample based on the virtual volume coordinates [S1].
    b. Perform a lookup in the page table using the virtual brick identifier to retrieve the physical storage information [S1].
    c. Compute the physical texture coordinates by combining the offset within the brick and the physical location retrieved from the page table [S1].

**Pseudocode:**
```python
def address_translation(virtual_coords, page_table):
    """
    Translates virtual volume coordinates to physical texture coordinates.
    
    Args:
        virtual_coords: Tuple (u, v, w) in normalized [0,1]^3 space.
        page_table: A lookup structure (e.g., texture) mapping virtual brick IDs 
                    to physical storage metadata (e.g., base texture coordinates, 
                    brick dimensions).
    
    Returns:
        Tuple (u_phys, v_phys, w_phys) representing the physical texture coordinates.
    """
    # 1. Determine which brick contains the virtual sample
    # Assuming bricks are arranged in a regular grid covering [0,1]^3
    # brick_size is the normalized size of one brick in each dimension
    brick_id = get_brick_id(virtual_coords, brick_size)
    
    # 2. Lookup physical storage info from the page table
    # page_table[brick_id] returns metadata such as:
    # - base_u, base_v, base_w: The starting coordinates of this brick in the physical texture
    # - brick_dims: The physical dimensions of the brick in the texture
    physical_info = page_table.lookup(brick_id)
    
    if physical_info is None:
        # Handle case where brick is not currently resident in physical memory
        return None
        
    # 3. Calculate offset within the brick
    # Normalize virtual_coords to [0,1] relative to the brick's local space
    local_coords = (virtual_coords - brick_id * brick_size) / brick_size
    
    # 4. Compute final physical texture coordinates
    # Scale local coordinates by the brick's physical dimensions and add base offset
    u_phys = physical_info.base_u + local_coords.x * physical_info.brick_dims.x
    v_phys = physical_info.base_v + local_coords.y * physical_info.brick_dims.y
    w_phys = physical_info.base_w + local_coords.z * physical_info.brick_dims.z
    
    return (u_phys, v_phys, w_phys)

def get_brick_id(virtual_coords, brick_size):
    """
    Determines the brick ID for a given virtual coordinate.
    """
    # Integer division to find the brick index in each dimension
    bx = int(virtual_coords.x / brick_size.x)
    by = int(virtual_coords.y / brick_size.y)
    bz = int(virtual_coords.z / brick_size.z)
    # Flatten 3D brick index to 1D ID if needed by the page table structure
    # Assuming row-major order for brick grid
    return bx + by * grid_size_x + bz * grid_size_x * grid_size_y
```

**Parameters:**
*   **Brick Size:** The dimensions of each brick in the virtual volume space. Not given in the sources.
*   **Grid Size:** The number of bricks in each dimension of the virtual volume grid. Not given in the sources.

**Edge Cases and Pitfalls:**
*   **Out-of-Core Access:** If the brick corresponding to the virtual address is not currently loaded into physical memory, the page table lookup may return no valid physical address. The renderer must handle this, potentially by triggering a load request or skipping the sample [S1].
*   **Dynamic Management:** In early dynamically managed page table approaches, the working set of active bricks was determined independently of view-dependent occlusions, which could lead to inefficient memory usage [S1].

## Subtopics

### Single-Level, Single-Resolution Page Tables
Address translation for bricked, single-resolution volumes using a single page table look-up per sample [S1]. The page table is stored in a linear texture (index texture) with one entry per brick [S1]. This approach allows for out-of-core volume rendering but only with volume bricks from the original resolution and no down-sampling [S1]. It is suitable when multi-resolution rendering is not required and scalability is limited [S1]. A key pitfall in early implementations was that the working set of active bricks was determined independently of view-dependent occlusions [S1].

## Operating characteristics
*   **Time Complexity:** $O(1)$ per sample for the page table lookup, assuming constant-time access to the index texture [S1].
*   **Memory Complexity:** Proportional to the number of bricks in the volume, as the page table stores one entry per brick [S1].
*   **Strengths:** Enables out-of-core rendering of large volumes by managing brick residency dynamically [S1]. Simple to implement for single-resolution data [S1].
*   **Limitations:** Limited scalability for multi-resolution rendering as it does not support down-sampling [S1]. Early dynamic management approaches did not account for view-dependent occlusions, potentially leading to suboptimal memory usage [S1].
*   **When to Use:** When rendering large, single-resolution volumes that do not fit in memory, and multi-resolution rendering is not required [S1].
*   **When Not to Use:** When multi-resolution rendering or hierarchical culling based on view-dependent occlusions is needed [S1].

## Background
The concept of address translation in volume rendering is analogous to standard CPU virtual memory terminology, where a "page table" maps virtual addresses to physical addresses [S1]. The term "page" in this context commonly refers to a volume brick [S1]. The first introduction of adaptive texture maps for GPUs, which can be viewed as an early form of address translation using a small index texture, was by Kraus and Ertl [KE02] [S1]. More recent hardware support for partially resident textures (e.g., OpenGL `GL_ARB_sparse_texture`) allows the GPU hardware to manage the page table and perform address translation directly in the texture unit [S1].
