# Virtual Texture Memory for Magnification Lenses

Also called: Index volume brick mapping, Virtual texture coordinates

## Overview
This method enables interactive magnification of large volume datasets by keeping all bricks in a single GPU texture memory pool and using an index volume to locate them dynamically [S1, unofficial]. It allows arbitrary coordinate transformations (such as zooming) in the fragment shader without rebinding textures, solving the problem where modified texture coordinates would otherwise point into unbound bricks [S1, unofficial]. It sets itself apart from standard brick-based rendering by introducing a virtual-to-physical address translation layer that handles boundary overlaps and dynamic coordinate mapping [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   Input: Virtual texture coordinate $t_v$, number of voxels in the full dataset $n_v$, number of bricks along the axis $n_b$, brick size $s_b$, number of voxels in the physical memory space $n_p$, and the index texture containing brick indices $i_b$.
*   Output: Physical texture coordinate $t_p$ for data lookup.

**Data Structures:**
*   **Index Volume:** A small texture storing the brick index $i_b$ for each region of the virtual address space.
*   **Brick Pool:** A single large texture object containing all bricks packed sequentially.

**Steps:**
1.  Compute the index texture coordinate $t_i$ from the virtual texture coordinate $t_v$, the total number of voxels $n_v$, and the number of bricks $n_b$ along the axis:
    $$t_i = \frac{t_v n_v - 0.5}{n_v - n_b}$$
2.  Terminate execution if $t_i < 0$ or $t_i > 1$ [S1, unofficial].
3.  Look up the brick index $i_b$ from the index texture at $t_i$. Compute the physical brick base address $t_{pb}$:
    $$t_{pb} = \frac{i_b s_b}{n_p}$$
    where $s_b$ is the brick size and $n_p$ is the number of voxels along the corresponding axis in physical memory space [S1, unofficial].
4.  Compute the virtual offset $t_{vo}$ within the brick by taking the fractional part of $t_i n_b$. Compute the physical offset $t_{po}$:
    $$t_{po} = \frac{t_{vo} (s_b - 1) + 0.5}{n_p}$$
5.  Add $t_{po}$ to $t_{pb}$ to obtain the final physical address $t_p$:
    $$t_p = t_{pb} + t_{po}$$

**Parameters:**
*   **Voxel Overlap:** Assumes a single voxel overlap at brick boundaries [S1, unofficial].

**Pitfalls:**
*   Without virtual-to-physical translation, modified texture coordinates might point into a different brick than the currently bound bricks in the shader [S1, unofficial].
*   Precision issues may arise if $n_v$ is extremely large; however, the sources do not specify limits [G].

**Pseudocode:**
```python
def virtual_to_physical_address(t_v, n_v, n_b, s_b, n_p, index_texture):
    # Step 1: Compute index texture coordinate
    t_i = (t_v * n_v - 0.5) / (n_v - n_b)
    
    # Step 2: Terminate if out of bounds
    if t_i < 0 or t_i > 1:
        return None
        
    # Step 3: Look up brick index and compute base address
    i_b = index_texture.sample(t_i)
    t_pb = (i_b * s_b) / n_p
    
    # Step 4: Compute virtual offset and physical offset
    # Fractional part of t_i * n_b
    t_vo = (t_i * n_b) % 1.0
    t_po = (t_vo * (s_b - 1) + 0.5) / n_p
    
    # Step 5: Combine to get physical address
    t_p = t_pb + t_po
    return t_p
```

**Optimization:**
When not using magnification (only high-resolution rendering), compute index texture coordinates on the CPU to eliminate steps 1 and 2 [S1, unofficial].

## Subtopics
## Operating characteristics
*   **Performance:** The index texture is usually small, and the address translation adds minimal overhead [S1, unofficial].
*   **Use Case:** Useful for browsing very large datasets with limited resources, especially when only a small part of the original data can be placed in on-board texture memory and other multiresolution strategies fail [S1, unofficial].
*   **Limitations:** Requires managing an index volume and handling boundary overlaps explicitly [S1, unofficial].

## Background
Originated in the work of I. K. et al. (2004) for a Focus and Context Interface for Interactive Volume Rendering [S1, unofficial]. It builds on the concept of virtual texture memory proposed in [18] of the source, adapting it for volume bricks with boundary overlaps [S1, unofficial].
