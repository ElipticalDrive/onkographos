# Brick-based volume rendering with packed textures

Also called: Index-Texture brick mapping, Packed-Texture volume rendering

## Overview
Brick-based volume rendering with packed textures is a technique to handle volumetric datasets that exceed the capacity of local GPU video memory by dividing the data into smaller sub-volumes (bricks) [S1, unofficial]. It sets itself apart from standard bricking by storing only non-transparent bricks into a compact "Packed-Texture" and using a separate "Index-Texture" to map spatial coordinates to brick indices, thereby reducing memory usage and allowing efficient rendering of sparse or large datasets [S2, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A volumetric dataset (typically normalized to a cube from $[0, 1]^3$), a transfer function, and GPU memory constraints [S1, unofficial].
- Output: A rendered image where voxels are sampled from the Packed-Texture based on spatial location [S2, unofficial].

**Data Structures:**
1.  **Packed-Texture:** A texture containing only the voxel data of bricks deemed non-transparent by the transfer function [S2, unofficial].
2.  **Index-Texture:** A texture that stores the index of the corresponding brick in the Packed-Texture for every spatial location [S2, unofficial].

**Algorithm Steps:**

1.  **Brick Partitioning:** Divide the volume cube into $N \times N \times N$ bricks (blocks) of equal size [S2, unofficial].
2.  **Transparency Culling:** Evaluate the transfer function for each brick to determine transparency; exclude fully transparent bricks from the Packed-Texture [S2, unofficial].
3.  **Texture Construction:** Store the voxel data of all non-transparent bricks into the Packed-Texture [S2, unofficial].
4.  **Index Mapping:** Create the Index-Texture [S2, unofficial]. For every spatial position, store the index of the corresponding brick in the Packed-Texture [S2, unofficial].
5.  **Ray Casting and Sampling:** During ray casting, for each sample point, calculate its brick index and local fractional position, then access the Index-Texture to retrieve the brick index [S2, unofficial].

**Formulas:**
Let $P_{global}$ be the fractional coordinate of the sample point in the global volume cube $[0, 1]^3$ [S2, unofficial]. Let $N$ be the number of bricks along each axis [S2, unofficial].

1.  Scale the coordinate:
    $$ P_{scaled} = P_{global} \times N $$
2.  Calculate the brick index (integer part):
    $$ I_{brick} = \lfloor P_{scaled} \rfloor $$
3.  Calculate the fractional position within the sub-block (brick):
    $$ P_{local} = P_{scaled} - I_{brick} $$

**Parameters:**
-   $N$: Number of bricks per dimension. Sources suggest keeping bricks small enough so that more than one brick fits into video memory to allow parallel transfer and rendering [S1, unofficial].
-   Transfer Function: Thresholds or ranges used to determine brick transparency [S2, unofficial].

**Edge Cases and Pitfalls:**
-   **Interpolation Across Boundaries:** Incorrect interpolation can occur across brick boundaries if one plane of voxels is not duplicated at the edges of each brick [S1, unofficial].
-   **Filtering:** When storing blocks into a regular packed texture, hardware filtering must be disabled. The implementation must handle the "fencepost problem" and perform all filtering/interpolation manually in the shader [S2, unofficial].
-   **Bus Bandwidth:** Bricking can suffer from bus-bandwidth problems and unbalanced load for the GPU and memory bus if not managed carefully [S1, unofficial]. Keeping bricks small enough allows transfer and rendering to overlap, but increases CPU load for intersection calculations [S1, unofficial].

**Pseudocode:**

```python
import math

def brick_render(global_frac_pos, N, index_texture, packed_texture):
    # 1. Scale coordinate to brick grid
    scaled_pos = [p * N for p in global_frac_pos]

    # 2. Calculate brick index (integer part)
    brick_idx = [int(math.floor(s)) for s in scaled_pos]

    # 3. Calculate fractional position within the brick
    local_pos = [s - b for s, b in zip(scaled_pos, brick_idx)]

    # 4. Look up brick ID from Index-Texture using nearest-neighbor sampling.
    # The index texture is sampled at integer brick coordinates to retrieve the brick ID.
    brick_id = index_texture[brick_idx[0], brick_idx[1], brick_idx[2]]

    # 5. Check for transparent/empty brick (typically stored as -1 or 0)
    if brick_id < 0:
        return [0.0, 0.0, 0.0]

    # 6. Sample voxel data from Packed-Texture at the local fractional position.
    # The exact coordinate mapping for the Packed-Texture depends on the implementation's
    # packing scheme (e.g., 1D linear array mapped to 3D texture coordinates) [G].
    # Assuming a standard per-brick sampling where local_pos maps to [0,1]^3 within the brick's data:
    color = packed_texture[brick_id][tuple(local_pos)]
    return color
```

## Subtopics

### [Virtual Texture Memory for Magnification Lenses](7444-virtual-texture-memory-for-magnification-lenses.md)
This method enables interactive magnification of large volume datasets by keeping all bricks in a single GPU texture memory pool and using an index volume to locate them dynamically. It allows arbitrary coordinate transformations (such as zooming) in the fragment shader without rebinding textures, solving the problem where modified texture coordinates would otherwise point into unbound bricks. It sets itself apart from standard brick-based rendering by introducing a virtual-to-physical address translation layer that handles boundary overlaps and dynamic coordinate mapping.

### [Compact Volume Rendering with Page-Table Indirection and Masked Storage](11586-compact-volume-rendering-with-page-table-indirection-and-mas.md)
Compact Volume Rendering is a rendering mode that stores only selected groups of voxels (bricks) in a packed 2D array texture, using a page table for spatial indexing and an optional bitmask for sparse storage, to fit within a 1024 MiB GPU memory budget. It differs from the original mode, which loads the full volume into a single 3D texture, by enabling rendering of datasets that exceed `MAX_3D_TEXTURE_SIZE` or the available GPU memory through spatial partitioning and indirection. It builds on [Brick-based volume rendering with packed textures](7106-brick-based-volume-rendering-with-packed-textures.md) [G].

### [Interactive Multi-pipe 4D Rendering](16711-interactive-multi-pipe-4d-rendering.md)
Interactive Multi-pipe 4D Rendering is a parallel volume rendering algorithm designed for time-varying (4D) oceanography datasets on multi-pipe graphics hardware, such as the SGI Onyx2. It solves the problem of real-time visualization for datasets significantly larger than available texture memory by partitioning volume data into bricks and distributing them across multiple graphics pipes. Unlike offline parallel rendering which prioritizes high-quality isocontouring, this method relies on color-mapping to enable interactive control of camera parameters, time steps, and lookup tables in real-time. It builds on [Brick-based volume rendering with packed textures](7106-brick-based-volume-rendering-with-packed-textures.md) by explicitly managing brick distribution across heterogeneous hardware pipes to minimize texture swapping overhead.

### Brick Entry Point Offsetting
A proposed technique to correct sampling seam visibility during interaction-time when sampling distance is increased [S3, unofficial]. It involves offsetting the entry point in each brick to be a multiple along the entire ray [S3, unofficial]. Compute the entry point from the eye pose to ensure it is a multiple for each different brick, offsetting the entry point in each brick accordingly [S3, unofficial]. During interaction-time, the sampling distance is increased, which causes the sampling seams to become visible again [S3, unofficial].

## Operating characteristics
-   **Time Complexity:** Rendering time is proportional to the number of rays and samples per ray [G]. The overhead of brick management (transfer, culling) is added [S1, unofficial].
-   **Memory Complexity:** Memory usage is proportional to the number of non-transparent bricks [S2, unofficial]. This can be significantly less than the full volume if the data is sparse [G].
-   **Performance:** Performance is limited by GPU memory bandwidth and bus bandwidth [S1, unofficial]. Parallel transfer and rendering can help balance the load, but CPU load for intersection calculations increases [S1, unofficial].
-   **Strengths:** Handles datasets larger than GPU memory [S1, unofficial]. Reduces memory usage for sparse data [S2, unofficial].
-   **Limitations:** Interpolation artifacts at brick boundaries if not handled correctly [S1, unofficial]. Bus bandwidth bottlenecks [S1, unofficial]. Increased CPU load [S1, unofficial].
-   **When to use:** Large volumetric datasets that do not fit in GPU memory, especially if sparse [S1, unofficial].
-   **When not to use:** Dense datasets where most bricks are non-transparent, or when interpolation artifacts are unacceptable without additional processing [S2, unofficial].

## Background
Bricking was introduced as a technique to handle data sets too large for local video memory by dividing the data set into smaller chunks (bricks) [S1, unofficial]. The specific method of using packed textures and index textures was discussed in the context of GPU-based volume rendering [S2, unofficial]. The technique has been used in various forms in real-time volume graphics [S1, unofficial].
