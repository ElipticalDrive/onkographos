# Brick-based volume rendering with packed textures

Also called: Index-Texture brick mapping, Packed-Texture volume rendering

## Overview
Brick-based volume rendering with packed textures handles volumetric datasets too large for local GPU video memory by dividing the data into smaller sub-volumes (bricks) and storing only the non-transparent ones in a compact 2D or 3D texture [S1, unofficial]. It sets itself apart from standard brick-based rendering by using an "Index-Texture" to map spatial coordinates to the compacted storage layout, allowing efficient rendering of sparse or large volumes without rebinding textures for every brick [S2, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A volumetric dataset (typically a cube $[0, 1]^3$), a transfer function, and GPU memory constraints.
- Output: A rendered image where each pixel is colored based on ray casting through the packed brick data.

**Data Structures:**
1.  **Packed-Texture:** A single 2D or 3D texture containing only the bricks determined to be non-transparent. The bricks are stored contiguously or in a specific packing order.
2.  **Index-Texture:** A texture (typically 3D or 2D depending on the index mapping) that stores the index of the brick in the Packed-Texture for any given spatial coordinate. The value stored is an integer representing the position in the Packed-Texture array.

**Algorithm Steps:**

1.  **Brick Partitioning:**
    Divide the volume cube into $N \times N \times N$ bricks (blocks) of equal size [S2, unofficial]. For a volume cube spanning $[0, 1]^3$, the brick index and fractional position within that brick are calculated from a sample point's fractional coordinate $p \in [0, 1]$ as follows [S2, unofficial]:
    $$
    \begin{aligned}
    \text{volcube\_pos} &= p \times N \\
    \text{volcube\_index} &= \lfloor \text{volcube\_pos} \rfloor \\
    \text{subblock\_pos} &= \text{volcube\_pos} - \text{volcube\_index}
    \end{aligned}
    $$
    Here, $\text{volcube\_index}$ is the integer index of the brick, and $\text{subblock\_pos}$ is the normalized position within that brick.

2.  **Transparency Culling:**
    Evaluate the transfer function for each brick. If a brick is fully transparent (or below a visibility threshold), it is excluded from the Packed-Texture [S2, unofficial].

3.  **Packing:**
    Store only the non-transparent bricks into the Packed-Texture. The order of storage determines the indices stored in the Index-Texture [S2, unofficial].

4.  **Index-Texture Generation:**
    Create the Index-Texture. For every voxel position in the original volume grid, store the index of the corresponding brick in the Packed-Texture. If a brick is transparent, the index may store a sentinel value (e.g., -1) or the brick may be omitted from the index lookup if handled by the shader [S2, unofficial].

5.  **Rendering (Ray Casting):**
    For each sample point along a ray:
    a. Calculate the brick index and sub-block position using the formulas above [S2, unofficial].
    b. Sample the Index-Texture at the brick index to retrieve the packed texture index [S2, unofficial].
    c. If the retrieved index is valid, sample the Packed-Texture at the sub-block position to get the voxel value.
    d. If the index is invalid (transparent brick), skip the sample or treat it as empty [S2, unofficial].

**Pseudocode:**

```python
# Vertex/Fragment Shader Pseudocode for Ray Casting with Packed Textures

# Constants
N = 16  # Number of bricks per dimension (example)
MAX_PACKED_BRICKS = 1000  # Max bricks in packed texture

# Textures
uniform sampler3D index_texture;
uniform sampler3D packed_texture;
uniform sampler3D transfer_function;

# Function to get voxel value from packed bricks
float get_voxel_value(vec3 world_pos):
    # 1. Calculate brick index and sub-block position
    volcube_pos = world_pos * N
    volcube_index = floor(volcube_pos)
    subblock_pos = volcube_pos - volcube_index
    
    # 2. Get the index of the brick in the packed texture
    # Note: Index texture stores integer indices. 
    # We need to sample it. Since it's integer data, we might use 
    # a specific format or convert float to int.
    packed_idx = texture(index_texture, world_pos)
    
    # 3. Check if brick is transparent (sentinel value, e.g., -1)
    if packed_idx < 0:
        return 0.0  # Transparent
    
    # 4. Sample the packed texture
    # The packed texture contains bricks concatenated.
    # We need to map the brick index and subblock position to the 
    # packed texture coordinates.
    # Assuming packed_texture is a 3D texture where bricks are stored 
    # in a specific order (e.g., row-major).
    # This mapping depends on the packing strategy.
    # A simple approach: packed_texture is actually a 1D or 2D texture 
    # of bricks, but for simplicity, let's assume a 3D packed texture 
    # where each "voxel" in the packed texture corresponds to a voxel 
    # in a brick, and the brick index is used to offset the coordinate.
    
    # More robust approach: 
    # The index_texture returns the brick ID.
    # We need to compute the coordinate in the packed texture.
    # If packed_texture is a 3D texture of size (BrickSize, BrickSize, BrickSize) 
    # for each brick, we need a way to address it.
    # Common approach: Use a 1D texture for packed bricks, or a 3D texture 
    # with a large dimension.
    
    # Let's assume a 3D packed texture where the first dimension is the brick index.
    # This is not standard. A more standard approach is:
    # packed_texture is a 3D texture of size (BrickSize, BrickSize, BrickSize).
    # We need to know which brick we are in.
    # The index_texture gives us the brick ID.
    # We need to map (brick_id, subblock_pos) to a coordinate in packed_texture.
    
    # Alternative: Use a 1D texture for packed bricks.
    # packed_texture_1D is a 1D texture containing all voxel data of all bricks.
    # We need to compute the offset in the 1D texture.
    # offset = brick_id * (BrickSize^3) + (subblock_pos.x * BrickSize^2 + ...)
    
    # Let's stick to the 3D packed texture assumption for simplicity, 
    # but note that addressing is complex.
    # A simpler implementation uses a 2D texture for packed bricks 
    # where each brick is a 2D slice or a 3D block.
    
    # For the purpose of this pseudocode, let's assume:
    # packed_texture is a 3D texture of size (BrickSize, BrickSize, BrickSize).
    # We need to know the brick ID to select the correct brick.
    # This requires a texture array or a large 3D texture.
    # Let's assume a texture array: packed_texture_array.
    
    # Re-defining for clarity:
    # packed_texture_array: array of 3D textures, one per brick.
    # index_texture: 3D texture storing the array index.
    
    brick_id = texture(index_texture, world_pos)
    
    if brick_id < 0:
        return 0.0
    
    # Sample from the specific brick in the array
    # subblock_pos is in [0, 1)
    voxel_value = texture(packed_texture_array[brick_id], subblock_pos)
    
    return voxel_value

# Main Ray Casting Loop
for each sample along ray:
    voxel = get_voxel_value(sample_pos)
    color = apply_transfer_function(voxel)
    accumulate_color(color)
```

**Parameters:**
- $N$: Number of bricks per dimension. Typical values depend on GPU memory and brick size. Not given in the sources.
- Brick Size: Must be small enough so that more than one brick fits into video memory [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Interpolation Across Boundaries:** Incorrect interpolation can occur across brick boundaries if one plane of voxels is not duplicated [S1, unofficial].
- **Filtering:** When storing blocks into a regular, packed 3D texture, filtering must be disabled, and all filtering interpolation must be done manually to avoid artifacts [S2, unofficial].
- **Fencepost Problem:** Care must be taken with boundary conditions when packing bricks [S2, unofficial].
- **Bus Bandwidth:** Bricking can suffer from bus-bandwidth problems and unbalanced load for the GPU and memory bus if not managed carefully [S1, unofficial].

## Subtopics

### [Virtual Texture Memory for Magnification Lenses](7444-virtual-texture-memory-for-magnification-lenses.md)
This method enables interactive magnification of large volume datasets by keeping all bricks in a single GPU texture memory pool and using an index volume to locate them dynamically. It allows arbitrary coordinate transformations (such as zooming) in the fragment shader without rebinding textures, solving the problem where modified texture coordinates would otherwise point into unbound bricks. It sets itself apart from standard brick-based rendering by introducing a virtual-to-physical address translation layer that handles boundary overlaps and dynamic coordinate mapping.

### [Compact Volume Rendering with Page-Table Indirection and Masked Storage](11586-compact-volume-rendering-with-page-table-indirection-and-mas.md)
Compact Volume Rendering is a rendering mode that stores only selected groups of voxels (bricks) in a packed 2D array texture, using a page table for spatial indexing and an optional bitmask for sparse storage, to fit within a 1024 MiB GPU memory budget. It differs from the original mode, which loads the full volume into a single 3D texture, by enabling rendering of datasets that exceed `MAX_3D_TEXTURE_SIZE` or the available GPU memory through spatial partitioning and indirection. It builds on [Brick-based volume rendering with packed textures](7106-brick-based-volume-rendering-with-packed-textures.md).

### Brick Entry Point Offsetting
A proposed technique to correct sampling seam visibility during interaction-time when sampling distance is increased. It involves offsetting the entry point in each brick to be a multiple along the entire ray [S3, unofficial]. Compute the entry point from the eye pose to ensure it is a multiple for each different brick, offsetting the entry point in each brick accordingly [S3, unofficial]. During interaction-time, the sampling distance is increased, which causes the sampling seams to become visible again [S3, unofficial].

## Operating characteristics
- **Time Complexity:** Depends on the number of samples per ray and the number of bricks. The index lookup adds a small overhead.
- **Memory Complexity:** Proportional to the number of non-transparent bricks. Transparent bricks are not stored, saving memory [S2, unofficial].
- **Performance:** Efficient for sparse volumes. For dense volumes, the overhead of index lookups and potential cache misses may reduce performance [S1, unofficial].
- **Strengths:** Handles large datasets that exceed GPU memory. Efficient storage for sparse data.
- **Limitations:** Bus-bandwidth bottlenecks. Unbalanced load for GPU and memory bus. Artifacts at brick boundaries if not handled correctly [S1, unofficial].
- **When to Use:** Large volumetric datasets with significant empty space or transparency.
- **When Not to Use:** Dense volumes where most bricks are non-transparent, or when high-quality interpolation across brick boundaries is critical and cannot be achieved with duplicated boundary voxels.
