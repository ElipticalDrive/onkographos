# Brick-based Volume Raycasting

Also called: Brick-wise raycasting, Bricked volume layout

## Overview
Brick-based volume raycasting decomposes volume data into fixed-size, power-of-two bricks to achieve high CPU cache coherency without the memory overhead of spread memory layouts [S1, unofficial]. Unlike linear raycasting, which suffers from view-dependent performance drops due to cache misses, this method provides nearly constant rendering performance regardless of viewing direction [S1, unofficial]. It builds on [Brick-based storage and caching](4138-brick-based-storage-and-caching.md) by defining the specific ray-marching algorithm and addressing scheme required to traverse this one-level subdivision hierarchy efficiently [G].

## How it works
**Inputs:**
*   Volume data stored in a one-level brick hierarchy [S1, unofficial].
*   Ray origin $\mathbf{o}$ and direction $\mathbf{d}$ for each pixel [G].
*   Brick dimensions $B_x, B_y, B_z$ (must be powers of two) [S1, unofficial].
*   Transfer function and compositing parameters [G].

**Outputs:**
*   Final color and opacity for each pixel [G].

**Data Structures:**
The volume is divided into bricks. Each brick contains voxel data stored in linear xyz-order [S1, unofficial]. Bricks themselves are stored in a linear array in xyz-order [S1, unofficial].
*   **Direct Addressing:** To avoid the overhead of multi-level addressing, a direct addressing scheme is used [S1, unofficial]. Given a voxel coordinate $(x, y, z)$, the brick index $k$ and local offset are computed using integer division and modulo operations [S1, unofficial].
*   **Ray Grouping:** Rays are processed in groups corresponding to bricks [S1, unofficial]. This allows the CPU/GPU to load a single brick into cache and process all relevant rays for that brick before moving to the next [S1, unofficial].

**Algorithm Steps:**
1.  **Initialization:** For each pixel, compute the ray $\mathbf{o}, \mathbf{d}$ and initialize front-to-back compositing accumulators [G].
2.  **Brick Traversal:** Step along the ray parameter $t$ to compute current voxel coordinates $(x, y, z)$ [G].
3.  **Addressing:** Compute the brick index and local voxel offset using direct integer arithmetic [S1, unofficial].
4.  **Sampling:** Fetch the voxel density from the brick cache using the computed offset [G].
5.  **Compositing:** Apply the transfer function to obtain color and opacity, then blend into the accumulated pixel buffer [G].
6.  **Termination:** Exit when the ray exits the volume bounds or opacity reaches a threshold [G].

**Pseudocode:**
```python
def get_brick_index(x, y, z, Bx, By, Bz, Nx_b, Ny_b):
    # Compute brick coordinates and linear index in xyz-order [S1, unofficial]
    bx = x // Bx
    by = y // By
    bz = z // Bz
    return bz * (Nx_b * Ny_b) + by * Nx_b + bx

def get_local_offset(x, y, z, Bx, By, Bz):
    # Compute local voxel coordinates and linear offset in xyz-order [S1, unofficial]
    lx = x % Bx
    ly = y % By
    lz = z % Bz
    return lz * (Bx * By) + ly * Bx + lx

def raycast_bricked_volume(ray_o, ray_d, vol_dims, brick_dims, brick_data, transfer_func):
    # Initialize compositing state [G]
    acc_color = [0.0, 0.0, 0.0]
    acc_opacity = 0.0
    t = 0.0
    step = 1.0 / max(vol_dims)
    # Precompute brick grid dimensions [G]
    Nx_b = vol_dims.x // brick_dims.x
    Ny_b = vol_dims.y // brick_dims.y
    
    while t < 1.0:
        # Map ray parameter to voxel coordinates [G]
        vx = int(ray_o.x + ray_d.x * t * vol_dims.x)
        vy = int(ray_o.y + ray_d.y * t * vol_dims.y)
        vz = int(ray_o.z + ray_d.z * t * vol_dims.z)
        
        # Boundary check [G]
        if not (0 <= vx < vol_dims.x and 0 <= vy < vol_dims.y and 0 <= vz < vol_dims.z):
            break
            
        # Address brick and sample [S1, unofficial]
        b_idx = get_brick_index(vx, vy, vz, brick_dims.x, brick_dims.y, brick_dims.z, Nx_b, Ny_b)
        l_off = get_local_offset(vx, vy, vz, brick_dims.x, brick_dims.y, brick_dims.z)
        density = brick_data[b_idx][l_off]
        
        # Transfer function and compositing [G]
        c, a = transfer_func(density)
        alpha = a * (1.0 - acc_opacity)
        acc_color[0] += c[0] * alpha
        acc_color[1] += c[1] * alpha
        acc_color[2] += c[2] * alpha
        acc_opacity += alpha
        
        t += step
    return acc_color, acc_opacity
```

**Formulas:**
*   **Brick Index:** For a voxel $(x, y, z)$ and brick dimensions $(B_x, B_y, B_z)$, the brick index $k$ in the linear brick array is:
    $$ k = \left\lfloor \frac{z}{B_z} \right\rfloor \cdot N_x N_y + \left\lfloor \frac{y}{B_y} \right\rfloor \cdot N_x + \left\lfloor \frac{x}{B_x} \right\rfloor $$
    where $N_x$ and $N_y$ are the number of bricks along the x and y dimensions of the volume [S1, unofficial].
*   **Local Offset:** The offset within the brick is:
    $$ \text{offset} = (z \bmod B_z) \cdot (B_x B_y) + (y \bmod B_y) \cdot B_x + (x \bmod B_x) $$
    [S1, unofficial]

**Parameters:**
*   **Brick Size:** Must be a power of two. The optimal size identified is 64KB, corresponding to $32 \times 32 \times 32$ voxels for 16-bit data [S1, unofficial].
*   **Padding:** 1-voxel padding on all sides for trilinear interpolation [G].

**Pitfalls:**
*   **Cache Exceedance:** Increasing brick size beyond the optimal point (64KB) leads to performance decreases due to exceeding cache capacity and increased bricking overhead [S1, unofficial].
*   **Addressing Overhead:** Multi-level subdivision increases addressing costs; a one-level hierarchy is preferred for efficiency [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of voxels traversed, but with a significantly lower constant factor due to cache hits [G].
*   **Memory Complexity:** $O(V)$ where $V$ is the volume size, plus minimal overhead for brick headers. Unlike spread layouts, it does not increase memory usage by a factor of four [S1, unofficial].
*   **Measured Performance:** On a Pentium 4 Xeon with 512KB L2 cache, brick-based raycasting with a 64KB brick size achieves a speedup of approximately 2.8 compared to common raycasting on a linear volume. A 1KB brick size yields a speedup of about 2.0 [S1, unofficial].
*   **Scaling:** Performance is nearly constant regardless of viewing direction, unlike linear layouts which show enormous performance decreases depending on viewing direction [S1, unofficial].
*   **Strengths:** High cache coherency, constant performance, low memory overhead [S1, unofficial].
*   **Limitations:** Suboptimal brick sizes lead to performance drops; one-level hierarchy may not be sufficient for very large volumes without additional caching strategies [G].
*   **When to Use:** Real-time rendering on hardware with limited cache (e.g., older CPUs, embedded GPUs) where view-dependent performance is unacceptable [G].
*   **When Not to Use:** When memory bandwidth is the primary bottleneck and spread layouts are viable, or when adaptive resolution is strictly required without additional tree structures [G].

## Background
The method was introduced in the context of real-time mono- and multi-volume rendering of large medical datasets on standard PC hardware [S1, unofficial]. It addresses the limitations of linear raycasting, which suffers from poor CPU utilization due to cache misses, and spread memory layouts, which increase memory usage dramatically [S1, unofficial]. The approach was developed to support semitransparent views with high real-time performance without increasing memory usage [S1, unofficial].
