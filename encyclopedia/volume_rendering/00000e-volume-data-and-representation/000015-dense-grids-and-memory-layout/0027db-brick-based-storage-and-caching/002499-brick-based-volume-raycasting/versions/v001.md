# Brick-based Volume Raycasting

Also called: Brick-wise raycasting, Bricked volume layout

## Overview
Brick-based volume raycasting decomposes volume data into small, fixed-size bricks to achieve high cache coherency on CPU architectures without the dramatic memory overhead associated with spread memory layouts [S1, unofficial]. Unlike spread layouts which increase memory usage by a factor of four and are limited by memory bandwidth, this method maintains low memory usage and provides constant performance behavior with nearly no view-dependent performance variation, whereas large bricks in linear layouts show enormous performance decreases depending on viewing direction [S1, unofficial]. It builds on [Brick-based storage and caching](4138-brick-based-storage-and-caching.md).

## How it works
**Inputs:** A 3D volume dataset $V$ with dimensions $D_x \times D_y \times D_z$ and voxel data type (e.g., 16-bit unsigned integer). A brick dimension $B \times B \times B$ where $B$ is a power of two. Camera parameters for ray generation.

**Outputs:** A rendered 2D image.

**Data Structures:**
The volume is decomposed into bricks. The total number of bricks along each axis is $N_x = \lceil D_x / B \rceil$, $N_y = \lceil D_y / B \rceil$, $N_z = \lceil D_z / B \rceil$.
1.  **Brick Data:** Each brick contains $B^3$ voxels. The data within a brick is stored linearly in common xyz-order (x varies fastest, then y, then z).
2.  **Brick Array:** The bricks themselves are stored linearly in common xyz-order. The index of a brick $(i, j, k)$ in the linear array is:
    $$ Index(i, j, k) = i + j \cdot N_x + k \cdot N_x \cdot N_y $$
    where $0 \le i < N_x$, $0 \le j < N_y$, $0 \le k < N_z$.
    This forms a one-level subdivision hierarchy [S1, unofficial].

**Algorithm Steps:**
1.  **Preprocessing:**
    *   Divide the volume $V$ into bricks of size $B \times B \times B$.
    *   Store bricks in a single linear array in xyz-order.
    *   [G] Handle boundary conditions: if $D_x, D_y, D_z$ are not multiples of $B$, pad the last bricks with dummy voxels or handle partial reads carefully.

2.  **Ray Casting Loop:**
    For each pixel $(u, v)$ in the image:
    *   Generate a ray $R(t) = O + t \cdot D$ from the camera origin $O$ with direction $D$.
    *   Determine the entry and exit points of the ray into the volume bounding box.
    *   Initialize ray parameters: step size $\Delta t$, current position $t_{curr} = t_{entry}$.

3.  **Brick Traversal and Integration:**
    While $t_{curr} < t_{exit}$:
    *   **Brick Identification:** Calculate the 3D voxel coordinates $(x, y, z)$ corresponding to $t_{curr}$. Determine the brick indices $(i, j, k)$ containing this voxel:
        $$ i = \lfloor x / B \rfloor, \quad j = \lfloor y / B \rfloor, \quad k = \lfloor z / B \rfloor $$
    *   **Brick Loading:** Calculate the linear index of the brick:
        $$ BrickIndex = i + j \cdot N_x + k \cdot N_x \cdot N_y $$
        Load the brick data from memory into a cache-friendly buffer. [G] Ensure the buffer size is at least $B^3 \times \text{voxel\_size}$.
    *   **Ray-Brick Intersection:** Calculate the intersection interval $[t_{start}, t_{end}]$ of the ray with the current brick.
        *   If the ray does not intersect the brick, skip to the next brick along the ray.
        *   Otherwise, clamp $t_{curr}$ to $t_{start}$.
    *   **Sample Integration:**
        While $t_{curr} < t_{end}$:
        *   Calculate local voxel coordinates $(x', y', z')$ within the brick.
        *   Sample the voxel value $v$ from the loaded brick data.
        *   Apply transfer function to get color $C$ and opacity $\alpha$.
        *   Perform front-to-back compositing:
            $$ C_{out} = C_{in} + C \cdot \alpha \cdot (1 - C_{in}.A) $$
            $$ A_{out} = A_{in} + \alpha \cdot (1 - A_{in}) $$
        *   Advance $t_{curr}$ by $\Delta t$.
    *   Update $t_{curr}$ to $t_{end}$ to move to the next brick.

4.  **Finalization:**
    *   Write the final accumulated color and opacity to the pixel buffer.

**Parameters:**
*   **Brick Size ($B$):** Must be a power of two. The optimal brick size identified is 64KB, corresponding to $32 \times 32 \times 32$ voxels for 16-bit data [S1, unofficial].
*   **Step Size ($\Delta t$):** Determined by the desired sampling rate relative to the voxel size and camera distance.

**Edge Cases and Pitfalls:**
*   **Brick Size:** Increasing brick size beyond the optimal point (64KB) leads to performance decreases due to exceeding cache capacity and bricking overhead [S1, unofficial].
*   **View Dependency:** Unlike linear layouts, this method exhibits nearly no view-dependent performance variation [S1, unofficial].
*   **Boundary Handling:** Partial bricks at the volume boundaries must be handled correctly to avoid out-of-bounds memory access [G].

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of voxels along the ray, but with a significantly lower constant factor due to cache efficiency.
*   **Memory Complexity:** $O(V)$ where $V$ is the total volume size, similar to linear storage, unlike spread layouts which use $4 \times$ memory [S1, unofficial].
*   **Measured Performance:** On a Pentium 4 Xeon with 512KB L2 cache, brick-based raycasting with a 64KB brick size achieves a speedup of approximately 2.8 compared to common raycasting on a linear volume [S1, unofficial]. A 1KB brick size yields a speedup of about 2.0 [S1, unofficial].
*   **Scaling:** Performance is relatively constant regardless of viewing direction, unlike linear layouts which suffer from view-dependent performance drops [S1, unofficial].
*   **Strengths:** High cache coherency, low memory overhead, constant performance across viewing angles.
*   **Limitations:** Overhead from brick addressing; performance degrades if brick size exceeds cache capacity [S1, unofficial].
*   **When to Use:** Real-time rendering on CPU hardware where cache efficiency is critical and memory bandwidth is a bottleneck.
*   **When Not to Use:** When GPU acceleration is available and memory bandwidth is less of a constraint, or when extremely large bricks are needed for other reasons.

## Background
Brick-based volume raycasting was developed to address the poor CPU utilization in real-time volume rendering, particularly for semitransparent views [S1, unofficial]. The concept of bricking data into small fixed-size chunks was identified as an effective way to achieve high cache coherency without increasing memory usage dramatically [S1, unofficial]. The specific one-level subdivision hierarchy and efficient addressing scheme were detailed in research focusing on real-time mono- and multi-volume rendering of large medical datasets on standard PC hardware [S1, unofficial].
