# Brick-based Volume Raycasting

Also called: Brick-wise raycasting, Bricked volume layout

## Overview
Brick-based volume raycasting is a rendering technique that decomposes a dense volume dataset into fixed-size cubic bricks to achieve high CPU cache coherency without the memory overhead of spread memory layouts [S1, unofficial]. Unlike linear raycasting, which suffers from severe view-dependent performance drops due to cache misses, this method provides nearly constant performance regardless of viewing direction by ensuring that ray samples for a given brick remain in the L2 cache [S1, unofficial]. It builds on [Brick-based storage and caching](4138-brick-based-storage-and-caching.md) by defining the specific ray-marching algorithm and addressing scheme required to traverse these bricks efficiently.

## How it works
**Inputs and Outputs:**
- Input: A volume dataset of dimensions $D_x \times D_y \times D_z$ with 16-bit voxel values, decomposed into bricks of size $B \times B \times B$.
- Input: Camera parameters (origin $\mathbf{o}$, direction $\mathbf{d}$, field of view).
- Input: Transfer function mapping voxel values to color and opacity.
- Output: A 2D image where each pixel is the result of front-to-back compositing along the corresponding ray.

**Data Structures:**
1.  **Brick Storage:** The volume is partitioned into a grid of $N_x \times N_y \times N_z$ bricks, where $N_x = \lceil D_x / B \rceil$, etc. Bricks are stored in a linear array in common xyz-order. The index of brick $(i, j, k)$ is:
    $$ Index(i, j, k) = i + j \cdot N_x + k \cdot N_x \cdot N_y $$
    [S1, unofficial]
2.  **Voxel Layout:** Within each brick, voxels are stored in linear xyz-order. To support trilinear interpolation at brick boundaries without accessing adjacent bricks, each brick is stored with a padding layer of voxels, resulting in a stored size of $(B+1)^3$ voxels [S1, unofficial].
3.  **Ray Structures:** For each pixel, a ray is defined. In a brute-force implementation (used for benchmarking in sources), all rays are processed. In optimized implementations, rays are grouped by the bricks they traverse.

**Numbered Steps:**
1.  **Initialization:** For each pixel $(u, v)$ in the image, compute the ray origin $\mathbf{o}$ and direction $\mathbf{d}$ in world space. Initialize the accumulated color $C_{acc} = (0,0,0,0)$ and density $\alpha_{acc} = 0$.
2.  **Ray-Brick Intersection:** Determine the entry and exit points of the ray into the volume bounding box. Calculate the sequence of bricks the ray intersects. This requires computing the intersection of the ray with the brick grid boundaries.
3.  **Brick Loading:** For each intersected brick, check if it is in the cache. If not, load the brick data (including padding) from storage into the cache [S1, unofficial].
4.  **Ray Marching:** For each sample step $\Delta t$ along the ray within the current brick:
    a. Compute the 3D sample position $\mathbf{p} = \mathbf{o} + t \cdot \mathbf{d}$.
    b. Sample the voxel value $v$ at $\mathbf{p}$ using trilinear interpolation from the padded brick data.
    c. Map $v$ to color $c$ and opacity $\alpha$ using the transfer function.
    d. Perform front-to-back compositing:
       $$ C_{acc} = C_{acc} + c \cdot \alpha \cdot (1 - \alpha_{acc}) $$
       $$ \alpha_{acc} = \alpha_{acc} + \alpha \cdot (1 - \alpha_{acc}) $$
    e. If $\alpha_{acc} \ge 1$, terminate the ray (early ray termination) [S1, unofficial].
5.  **Output:** Write $C_{acc}$ to the pixel buffer.

**Parameters:**
-   **Brick Size $B$:** Must be a power of two. The optimal size identified is $32 \times 32 \times 32$ voxels, corresponding to 64KB of data (assuming 16-bit voxels and padding) [S1, unofficial].
-   **Voxel Precision:** 16-bit per voxel [S1, unofficial].

**Edge Cases and Pitfalls:**
-   **Brick Size Optimization:** Increasing brick size beyond 64KB leads to performance decreases due to exceeding L2 cache capacity and increased bricking overhead (addressing costs) [S1, unofficial].
-   **View Dependency:** Unlike linear layouts, this method exhibits nearly no view-dependent performance variation, provided the brick size is small enough to fit in cache [S1, unofficial].
-   **Padding:** Failure to pad bricks by one voxel on each face will cause incorrect interpolation at brick boundaries [S1, unofficial].

**Pseudocode:**
```python
def brick_based_raycasting(volume_dims, brick_size, camera, transfer_function):
    """
    volume_dims: (Dx, Dy, Dz)
    brick_size: B (power of two)
    camera: object with origin o and direction d for each pixel
    transfer_function: function v -> (color, opacity)
    """
    B = brick_size
    # Calculate number of bricks
    Nx = ceil(volume_dims[0] / B)
    Ny = ceil(volume_dims[1] / B)
    Nz = ceil(volume_dims[2] / B)
    
    # Precompute brick grid boundaries for fast intersection
    # This is a simplification; real implementation uses ray-box intersection
    brick_grid = create_brick_grid(Nx, Ny, Nz, B, volume_dims)
    
    image = empty_image(camera.width, camera.height)
    
    for u in range(camera.width):
        for v in range(camera.height):
            ray_o, ray_d = camera.get_ray(u, v)
            acc_color = (0.0, 0.0, 0.0, 0.0)
            acc_alpha = 0.0
            
            # Get sequence of bricks intersected by ray
            intersected_bricks = get_intersected_bricks(ray_o, ray_d, brick_grid)
            
            for brick in intersected_bricks:
                # Load brick data (with padding)
                # In a real system, this checks cache first
                brick_data = load_brick(brick.index)
                
                # Determine ray segment within this brick
                t_start, t_end = get_bray_segment(ray_o, ray_d, brick)
                
                # March through the brick
                t = t_start
                while t < t_end:
                    # Compute sample position
                    p = ray_o + t * ray_d
                    
                    # Sample voxel value with trilinear interpolation
                    # Note: brick_data includes padding, so boundary samples are valid
                    v = sample_voxel(brick_data, p, B)
                    
                    # Transfer function
                    color, alpha = transfer_function(v)
                    
                    # Front-to-back compositing
                    weight = alpha * (1.0 - acc_alpha)
                    acc_color = acc_color + color * weight
                    acc_alpha = acc_alpha + alpha * (1.0 - acc_alpha)
                    
                    if acc_alpha >= 1.0:
                        break # Early ray termination
                    
                    t += step_size # Step size depends on desired resolution
                    
                if acc_alpha >= 1.0:
                    break
            
            image[u, v] = acc_color
            
    return image
```

## Operating characteristics
-   **Time Complexity:** $O(N \cdot M)$ where $N$ is the number of pixels and $M$ is the average number of samples per ray. The constant factor is significantly reduced compared to linear raycasting due to cache hits.
-   **Memory Complexity:** $O(D_x D_y D_z)$ for the volume data, plus cache overhead. Unlike spread memory layouts, it does not increase memory usage by a factor of four [S1, unofficial].
-   **Measured Performance:** On a Pentium 4 Xeon with 512KB L2 cache, brick-based raycasting with a 64KB brick size achieves a speedup of approximately 2.8 compared to common raycasting on a linear volume. A 1KB brick size yields a speedup of about 2.0 [S1, unofficial].
-   **Scaling:** Performance is nearly constant with respect to viewing direction, unlike linear layouts which show enormous performance decreases depending on the viewing direction [S1, unofficial].
-   **Strengths:** High cache coherency, constant performance, low memory overhead.
-   **Limitations:** Bricking overhead (addressing costs) increases with smaller bricks. Performance drops if brick size exceeds L2 cache capacity [S1, unofficial].

## Background
This method was developed to support real-time mono- and multi-volume rendering of large medical datasets on standard PC hardware [S1, unofficial]. It addresses the limitations of linear volume layouts, which suffer from poor CPU utilization due to cache misses during ray traversal. The approach uses a one-level subdivision hierarchy to minimize addressing costs compared to two-level hierarchies [S1, unofficial].
