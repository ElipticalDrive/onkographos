# Brick-based storage and caching

Also called: Bricking, Brick Caching, Brick-based Volume Raycasting, N³-tree with Brick Pool, Multi-Level Cache, Bricked Volume Hierarchy, Raymarching with LOD-based Brick Caching

## Overview
Brick-based storage and caching decomposes a large volumetric dataset into fixed-size, regular sub-volumes called "bricks" to optimize memory access patterns and enable out-of-core rendering. It solves the problem of limited GPU memory capacity and transfer bandwidth by ensuring that only the bricks intersecting the current view or required for the current ray-marching step are resident in fast memory [S1, unofficial]. It differs from [Brick-based Volume Raycasting](3341-brick-based-volume-raycasting.md) by explicitly managing a resident cache with eviction policies (e.g., LRU) to handle datasets larger than available VRAM, whereas the latter focuses on the traversal and integration logic within a cached or pre-loaded brick structure [S1, unofficial]. It differs from [Brick Caching with LRU Replacement](879-brick-caching-with-lru-replacement.md) by encompassing the broader family of techniques including hierarchical structures (N³-tree) and multi-level caching, rather than just the specific LRU block management unit.

## Shared principles
All brick-based methods share the fundamental principle of spatial decomposition. The continuous domain $\Omega \subset \mathbb{R}^3$ is discretized into a regular grid, which is then partitioned into cubic or rectangular bricks of size $B \times B \times B$ (or $B_x \times B_y \times B_z$).

1.  **Brick Decomposition:** The volume dimensions $D_x, D_y, D_z$ are divided into brick dimensions $N_x, N_y, N_z$:
    $$ N_x = \lceil D_x / B \rceil, \quad N_y = \lceil D_y / B \rceil, \quad N_z = \lceil D_z / B \rceil $$
    Bricks are indexed linearly or hierarchically. In a flat layout, the index of brick $(i, j, k)$ is:
    $$ Index(i, j, k) = i + j \cdot N_x + k \cdot N_x \cdot N_y $$
    [S1, unofficial]

2.  **Neighbor Padding:** To support trilinear or higher-order interpolation without accessing adjacent bricks, each brick is often stored with an additional layer of voxels on each face. A brick of logical size $B$ is stored as $(B+1)^3$ voxels. This ensures that sampling near the brick boundary can be performed using data within the same brick. [S1, unofficial]

3.  **Cache Management:** Since the total number of bricks often exceeds available memory, a cache mechanism is required. The cache maps brick coordinates to memory slots. When a brick is requested, it is loaded from slow storage (disk or host RAM) into the cache. If the cache is full, an eviction policy (e.g., Least Recently Used) determines which brick to discard. [S2, unofficial]

4.  **Empty Brick Detection:** To optimize performance, metadata (such as a count buffer) is often used to identify empty or transparent bricks. If a brick contains no relevant data for the current transfer function, it is skipped, avoiding unnecessary memory transfers and ray-marching steps. [S2, unofficial]

## Subtopics

### [Brick Caching with LRU Replacement](879-brick-caching-with-lru-replacement.md)
Manages a fixed-size pool of volume data blocks, mapping brick coordinates to pool indices and evicting least-recently-used blocks when the pool is full. It solves the problem of limited GPU memory capacity and transfer bandwidth by ensuring that expensive data transfers from slower host memory are minimized. It differs from [Brick-based Volume Raycasting](3341-brick-based-volume-raycasting.md) by decoupling the volume size from GPU resolution restrictions through a re-arranged brick structure and a resident cache texture.

### [Brick-based Volume Raycasting](3341-brick-based-volume-raycasting.md)
Decomposes volume data into small, fixed-size bricks to achieve high cache coherency on CPU architectures without the dramatic memory overhead associated with spread memory layouts. Unlike spread layouts which increase memory usage by a factor of four and are limited by memory bandwidth, this method maintains low memory usage and provides constant performance behavior with nearly no view-dependent performance variation, whereas large bricks in linear layouts show enormous performance decreases depending on viewing direction. It builds on [Brick-based storage and caching](4138-brick-based-storage-and-caching.md).

### [N³-tree with Brick Pool and Node Pool](3407-n-tree-with-brick-pool-and-node-pool.md)
The N³-tree with Brick Pool and Node Pool is a hierarchical data structure for voxel rendering that combines an N³-tree for spatial subdivision with a brick pool for volume data and a node pool for tree structure, allowing efficient LOD and visibility culling. It solves the problem of rendering large volumetric models by adapting the spatial resolution to the required precision, using small 3D texture units (bricks) that can be efficiently evaluated through ray marching. What sets it apart from its siblings, such as [Brick Caching with LRU Replacement](879-brick-caching-with-lru-replacement.md) or [Brick-based Volume Raycasting](3341-brick-based-volume-raycasting.md), is its use of a single pointer per node stored in a 3D texture node pool, which reduces memory requirements by 16x compared to methods requiring eight child pointers and neighbor pointers. This design improves cache coherence during traversal and minimizes the amount of data read during tree traversal.

### [Bricked Volume Hierarchy](5036-bricked-volume-hierarchy.md)
A data organization scheme where a volume dataset is partitioned into chunks called bricks across multiple resolution levels. Each brick is a chunk of voxel data belonging to a specific resolution level.

### [Raymarching with LOD-based Brick Caching](5776-raymarching-with-lod-based-brick-caching.md)
A visualization method for Compressed Segmentation Volumes (CSVs) that uses raymarching to render volumes. It decompresses bricks on-demand at the required Level of Detail (LOD), stores them in a GPU cache, and exploits temporal coherency by allowing a one-frame lag for decompression requests.

### Homogeneous Brick Optimization
#### step
- [S2, unofficial] Nodes corresponding to homogeneous bricks (all voxels contain the same value up to a user-defined threshold) store the average value in the brick instead of a pointer to the brick's location in the brick cache.

#### pitfall
- [S2, unofficial] For multi-channel data, a node can only be marked homogeneous if its corresponding bricks in all channels are homogeneous.

## Background
Brick-based rendering originated as a solution to the memory bandwidth and capacity limitations of early GPU hardware for volume visualization. The concept of decomposing volumes into bricks was introduced to improve cache locality and enable out-of-core rendering of datasets larger than available video memory. Early implementations focused on flat brick layouts with simple caching mechanisms [S1, unofficial]. Later developments introduced hierarchical structures like the N³-tree to reduce memory overhead and improve traversal efficiency [S1, unofficial]. The technique is widely used in scientific visualization, medical imaging, and real-time rendering of large volumetric datasets.
