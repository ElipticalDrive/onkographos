# Multi-Level Cache and Prefetching

Also called: HTTP Range Request Caching, Luxar Viewer Cache Architecture

## Overview
Multi-Level Cache and Prefetching is a memory management strategy for dense volume data that utilizes a hierarchical cache structure combined with predictive data loading to hide network and disk latency during interactive visualization [S1, unofficial]. It differs from sibling methods like [Brick Caching with LRU Replacement](879-brick-caching-with-lru-replacement.md) by explicitly separating compressed and decompressed states across distinct memory tiers (L0–L2) and an S-cache, while dynamically adjusting tier sizes based on available heap memory rather than using a static replacement policy [S1, unofficial]. It also differs from [Tile-based Volume Ray Marching](1678-tile-based-volume-ray-marching.md) by operating at the chunk/slice level with HTTP range requests rather than fixed geometric tiles [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A volume dataset stored in a chunked archive format (e.g., Zarr) accessible via HTTP range requests; current user interaction state (orbit, slider position).
*   **Output:** A four-level cache hierarchy containing compressed chunks, decompressed chunks, and fully decoded slice ladders; prefetched data in adjacent memory slots.

**Data Structures and Layout:**
The cache consists of four levels with specific memory roles and size constraints [S1, unofficial]:
1.  **L2 (Disk/OPFS):** Stores compressed chunks in the browser’s Origin Private File System (OPFS).
    *   Size: Fixed 2 GB.
    *   Persistence: Survives browser restarts.
2.  **L1 (Compressed Memory):** Stores decompressed chunks in RAM.
    *   Size: Ceiling of 100 MB.
    *   Behavior: Shrinks from ceiling when heap is tight.
3.  **L0 (Decompressed Memory):** Stores fully decompressed chunks in RAM.
    *   Size: Ceiling of 200 MB.
    *   Behavior: Shrinks from ceiling when heap is tight.
4.  **S-cache (Slice Ladder):** Stores fully decoded slice ladders, allowing revisited slices to skip the chunk path.
    *   Size: Default 128 MB, grows with heap up to 2 GB.

**Numbered Steps:**
1.  **Request Initiation:** When a ray-caster or viewer requires data, it first checks the S-cache. If present, the slice is served directly. If not, it checks L0 (decompressed chunks), then L1 (compressed chunks), then L2 (disk).
2.  **Fetch and Decode:**
    *   If data is in L2, it is fetched via HTTP range request.
    *   The chunk is decompressed using a codec (e.g., Blosc/zstd in WebAssembly) [S1, unofficial].
    *   The decompressed data is placed in L0.
    *   The compressed data is placed in L1.
    *   The compressed data is persisted to L2 (OPFS).
3.  **Heap Management:**
    *   Monitor available heap memory.
    *   If heap is tight, reduce the active size of L0 and L1 below their configured ceilings (100 MB and 200 MB respectively) to free memory [S1, unofficial].
    *   If heap is abundant, allow the S-cache to grow from its 128 MB default up to 2 GB [S1, unofficial].
4.  **Prefetching (On-Demand):**
    *   Upon an on-disk hit or a remote fetch, trigger a prefetcher.
    *   The prefetcher requests the chunk on either side of the current chunk in the data ordering [S1, unofficial].
5.  **Prefetching (Idle-Time):**
    *   Detect user idle states (e.g., orbiting or playing a slider).
    *   Warm the adjacent slice in memory to hide remote-fetch latency (order of 100 ms) [S1, unofficial].

**Formulas:**
*   Effective Radius for Point Clouds (used in slice membership resolution):
    $$ r_{eff} = \sqrt{r^2 - d^2} $$
    Where $r$ is the original radius and $d$ is the Euclidean distance from the point to the display hyperplane [S1, unofficial].

**Parameters:**
*   **L2 Size:** 2 GB (Fixed) [S1, unofficial].
*   **L1 Ceiling:** 100 MB [S1, unofficial].
*   **L0 Ceiling:** 200 MB [S1, unofficial].
*   **S-cache Default:** 128 MB [S1, unofficial].
*   **S-cache Max:** 2 GB [S1, unofficial].
*   **Remote Fetch Latency:** Order of 100 ms [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Heap Pressure:** If the heap is tight, L0 and L1 must shrink. Implementers must ensure that eviction from L0/L1 does not corrupt the S-cache or L2 consistency [S1, unofficial].
*   **Latency Hiding:** The idle-time prefetcher is critical for hiding the ~100 ms remote fetch latency. Failure to implement this results in visible stutter during interaction [S1, unofficial].
*   **Encoding:** Data encoding uses semantic types (8 types) and a width-aware Blosc-zstd policy (byte shuffle for multi-byte integers, no shuffle for single-byte/floats) [S1, unofficial]. Incorrect decoding policy will result in data corruption.

**Pseudocode:**
```python
class MultiLevelCache:
    def __init__(self):
        self.l2_opfs = OPFSStorage(max_size_gb=2)
        self.l1_compressed = MemoryPool(max_size_mb=100)
        self.l0_decompressed = MemoryPool(max_size_mb=200)
        self.s_cache_slice_ladders = MemoryPool(max_size_mb=2000, default_mb=128)
        self.heap_monitor = HeapMonitor()
        self.prefetcher = Prefetcher()

    def get_data(self, chunk_id):
        # 1. Check S-cache (Slice Ladder)
        if self.s_cache_slice_ladders.contains(chunk_id):
            return self.s_cache_slice_ladders.get(chunk_id)

        # 2. Check L0 (Decompressed Chunks)
        if self.l0_decompressed.contains(chunk_id):
            return self.l0_decompressed.get(chunk_id)

        # 3. Check L1 (Compressed Chunks)
        if self.l1_compressed.contains(chunk_id):
            compressed_data = self.l1_compressed.get(chunk_id)
            decompressed_data = self.decompress(compressed_data)
            self.l0_decompressed.put(chunk_id, decompressed_data)
            return decompressed_data

        # 4. Check L2 (OPFS / Disk)
        if self.l2_opfs.contains(chunk_id):
            compressed_data = self.l2_opfs.get(chunk_id)
            decompressed_data = self.decompress(compressed_data)
            self.l1_compressed.put(chunk_id, compressed_data)
            self.l0_decompressed.put(chunk_id, decompressed_data)
            return decompressed_data

        # 5. Remote Fetch
        compressed_data = self.fetch_remote(chunk_id)
        decompressed_data = self.decompress(compressed_data)
        
        # Store in all tiers
        self.l2_opfs.put(chunk_id, compressed_data)
        self.l1_compressed.put(chunk_id, compressed_data)
        self.l0_decompressed.put(chunk_id, decompressed_data)
        
        # Trigger on-demand prefetching
        self.prefetcher.request_adjacent_chunks(chunk_id)
        
        return decompressed_data

    def decompress(self, data):
        # Uses Blosc/zstd codec (e.g., in WASM)
        return blosc_decompress(data)

    def update_heap_management(self):
        available_heap = self.heap_monitor.get_available()
        if available_heap < THRESHOLD_TIGHT:
            self.l0_decompressed.shrink()
            self.l1_compressed.shrink()
        else:
            self.s_cache_slice_ladders.grow(available_heap)

    def idle_prefetch(self, current_slice_id):
        # Warms adjacent slice to hide ~100ms latency
        self.prefetcher.request_adjacent_slice(current_slice_id)

class Prefetcher:
    def request_adjacent_chunks(self, current_chunk_id):
        # Requests chunk on either side in ordering
        left_id = current_chunk_id - 1
        right_id = current_chunk_id + 1
        # Asynchronous fetch
        fetch_async(left_id)
        fetch_async(right_id)

    def request_adjacent_slice(self, current_slice_id):
        # Warms adjacent slice
        adjacent_id = current_slice_id + 1
        fetch_async(adjacent_id)
```

## Subtopics

### [VxlSlabColumn Priority Cache](4742-vxlslabcolumn-priority-cache.md)
The VxlSlabColumn Priority Cache is a memory management mechanism for voxel volume data that loads and recompiles slab columns based on priority levels to ensure spatial neighbors are available for surface operations. It differs from sibling caches like the Rolling 3-Row Slab Cache by explicitly managing dirty/clean states via a priority enum (`Edit`, `Neighbor`, `Support`) and triggering recompilation only when necessary, rather than relying solely on spatial sliding windows.

### [Rolling 3-Row Slab Cache](4747-rolling-3-row-slab-cache.md)
The Rolling 3-Row Slab Cache is a memory structure that stores voxel column data across a rolling window of three Y-rows to support incremental updates and neighbor-dependent recompilation in dense voxel grids. It sets itself apart from sibling caches like the [VxlSlabColumn Priority Cache](4742-vxlslabcolumn-priority-cache.md) by maintaining a fixed-size sliding window of Y-indices rather than priority-based or full-grid storage, optimizing for locality during column-wise edits. It builds on the principles of [Multi-Level Cache and Prefetching](4631-multi-level-cache-and-prefetching.md) by restricting active memory to a narrow spatial band.

### Dataset Prefetching
Runs a background thread to prefetch batches into a queue for asynchronous data loading [S2, unofficial]. It initializes a queue with size 3, starts the thread in daemon mode, and in an infinite loop, calls the appropriate next function (`_next_train` or `_next_test`) and puts the result into the queue [S2, unofficial].

### Page Table and Cache Management
Management of the multi-resolution page directory, page table cache, and block cache using LRU/MRU schemes, where updates are initiated by cache misses reported by the ray-caster [S3]. On a cache miss, the CPU first checks if the required block is resident in the CPU block cache (a larger version in CPU memory of the GPU block cache) [S3]. If the block is in the CPU block cache, it is downloaded into the GPU block cache, and the page directory and page table cache are updated accordingly [S3]. If the block is not in the CPU block cache, a request for the 3D volume data block is issued asynchronously to the volume data construction stage. The download of block data and page table updates are deferred until the constructed block arrives [S3].

## Operating characteristics
*   **Time Complexity:** Lookup is $O(1)$ for cache hits. Remote fetch is $O(1)$ network call but incurs ~100 ms latency [S1, unofficial]. Prefetching is asynchronous and non-blocking [S1, unofficial].
*   **Memory Complexity:** Total memory usage is bounded by the sum of tier ceilings: 2 GB (L2) + 100 MB (L1) + 200 MB (L0) + up to 2 GB (S-cache) = ~4.3 GB max, but L0/L1 shrink under heap pressure [S1, unofficial].
*   **Measured Performance:** Hides remote-fetch latency of ~100 ms during user orbit or slider playback [S1, unofficial].
*   **Strengths:** Dynamic memory adaptation to heap availability; effective hiding of network latency via idle-time prefetching; persistent storage via OPFS [S1, unofficial].
*   **Limitations:** Complex state management across four tiers; dependency on HTTP range request support; WebAssembly decoding overhead [S1, unofficial].
*   **When to Use:** Interactive web-based visualization of large multidimensional scientific data where network latency is significant and heap memory is variable [S1, unofficial].
*   **When Not to Use:** Offline rendering with local SSD access where latency is negligible; environments without WebAssembly support [S1, unofficial].

## Background
The Multi-Level Cache and Prefetching method was introduced in the Luxar viewer for Gaussian splatting microscopy and scalable interactive web visualization of multidimensional scientific data [S1, unofficial]. It addresses the challenge of visualizing large, chunked datasets (Zarr archives) in web browsers by leveraging the Origin Private File System (OPFS) and HTTP range requests [S1, unofficial]. The approach was developed to handle up to 16 dimensions of data, falling back to TypeScript for higher dimensions [S1, unofficial].
