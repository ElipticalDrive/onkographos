# Multi-Level Cache and Prefetching

Also called: HTTP Range Request Caching, Luxar Viewer Cache Architecture

## Overview
Multi-Level Cache and Prefetching is a memory management strategy for dense volume data that decouples data retrieval from rendering by organizing storage into distinct tiers of compression and resolution, while using background threads to anticipate access patterns. It solves the problem of high-latency remote fetches (order of 100 ms) stalling interactive rendering by ensuring that frequently accessed or spatially adjacent data is available in faster memory tiers. It sets itself apart from sibling methods like [Brick Caching with LRU Replacement](879-brick-caching-with-lru-replacement.md) by explicitly managing a hierarchy of compressed vs. decompressed states and heap-aware resizing, and from [Raymarching with LOD-based Brick Caching](5776-raymarching-with-lod-based-brick-caching.md) by focusing on the storage and prefetching of raw data chunks rather than geometric level-of-detail selection.

## How it works
The method organizes volume data into a four-level cache hierarchy, managed by a prefetcher that reacts to cache misses and idle time. The implementation relies on specific data structures for each tier and a state machine for data movement.

### Inputs and Outputs
- **Inputs**: Volume data stored in a chunked archive format (e.g., Zarr), accessed via HTTP range requests.
- **Outputs**: Render-ready voxel or splat data from the L0 cache; persistent storage in L2.

### Data Structures
The cache consists of four distinct tiers with specific layouts and size constraints:

1.  **L2 (Browser OPFS)**:
    -   **Content**: Compressed chunk files on disk.
    -   **Layout**: Directory structure of chunk files or a single `.luxar.zarr.zip` archive.
    -   **Size**: Fixed 2 GB.
    -   **Persistence**: Survives browser restarts.

2.  **L1 (Compressed In-Memory)**:
    -   **Content**: Decompressed but still compressed (e.g., Blosc/zstd) chunks.
    -   **Layout**: In-memory buffer holding compressed byte arrays.
    -   **Size**: Ceiling of 100 MB.
    -   **Behavior**: Shrinks from ceiling when heap is tight.

3.  **L0 (Decompressed In-Memory)**:
    -   **Content**: Fully decompressed chunks ready for rendering.
    -   **Layout**: In-memory buffer holding raw voxel/splat data.
    -   **Size**: Ceiling of 200 MB.
    -   **Behavior**: Shrinks from ceiling when heap is tight.

4.  **S-cache (Slice Ladder)**:
    -   **Content**: Fully decoded slice ladders.
    -   **Layout**: Pre-decoded slices allowing direct access without chunk path traversal.
    -   **Size**: Default 128 MB, grows up to 2 GB based on available heap.
    -   **Behavior**: Grows with heap; allows revisited slices to skip the chunk path.

### Numbered Steps

1.  **Initialization**:
    -   Allocate L2 storage with 2 GB limit.
    -   Initialize L1, L0, and S-cache with default/ceiling sizes (100 MB, 200 MB, 128 MB respectively).
    -   Start idle-time prefetcher thread.

2.  **Cache Miss Handling**:
    -   When a render request requires data not in L0:
        -   Check if data exists in L1. If yes, decompress to L0.
        -   Check if data exists in L2. If yes, fetch via HTTP range request to L1, then decompress to L0.
        -   If not in L2, fetch from remote server via HTTP range request to L1, then decompress to L0.
    -   Update L2 with new chunks if space permits (up to 2 GB).

3.  **Prefetching**:
    -   **On-Miss Prefetch**: After an on-disk hit (L2) or remote fetch, request the chunk on either side in the data ordering.
    -   **Idle-Time Prefetch**: During user orbit or slider playback, warm the adjacent slice to hide remote-fetch latency.

4.  **Memory Management**:
    -   Monitor heap usage.
    -   If heap is tight, shrink L0 and L1 from their configured ceilings.
    -   If heap has surplus, grow S-cache from its 128 MB default up to 2 GB.

### Pseudocode

```python
class MultiLevelCache:
    def __init__(self):
        self.l2_opfs = DiskStorage(max_size=2*1024*1024*1024) # 2 GB
        self.l1_compressed = MemoryBuffer(max_size=100*1024*1024) # 100 MB
        self.l0_decompressed = MemoryBuffer(max_size=200*1024*1024) # 200 MB
        self.s_cache_slice_ladders = MemoryBuffer(max_size=128*1024*1024, max_growth=2*1024*1024*1024)
        self.heap_monitor = HeapMonitor()
        self.prefetcher = PrefetcherThread()
        self.prefetcher.start()

    def get_data(self, chunk_id):
        # Check L0
        if chunk_id in self.l0_decompressed:
            return self.l0_decompressed[chunk_id]
        
        # Check L1
        if chunk_id in self.l1_compressed:
            data = self.l1_compressed[chunk_id]
            decompressed = decompress(data) # Blosc/zstd
            self.l0_decompressed.put(chunk_id, decompressed)
            return decompressed
        
        # Check L2 (Disk)
        if self.l2_opfs.exists(chunk_id):
            compressed_data = self.l2_opfs.read(chunk_id)
            self.l1_compressed.put(chunk_id, compressed_data)
            decompressed = decompress(compressed_data)
            self.l0_decompressed.put(chunk_id, decompressed)
            return decompressed
        
        # Remote Fetch
        compressed_data = fetch_remote(chunk_id) # HTTP Range Request
        self.l2_opfs.write(chunk_id, compressed_data)
        self.l1_compressed.put(chunk_id, compressed_data)
        decompressed = decompress(compressed_data)
        self.l0_decompressed.put(chunk_id, decompressed)
        
        # Trigger On-Miss Prefetch
        self.prefetcher.request_adjacent_chunks(chunk_id)
        
        return decompressed

    def manage_memory(self):
        heap_usage = self.heap_monitor.get_usage()
        # Shrink L0 and L1 if heap is tight
        if heap_usage > THRESHOLD_TIGHT:
            self.l0_decompressed.shrink_from_ceiling()
            self.l1_compressed.shrink_from_ceiling()
        # Grow S-cache if heap has surplus
        elif heap_usage < THRESHOLD_SURPLUS:
            self.s_cache_slice_ladders.grow_towards_ceiling()

class PrefetcherThread:
    def start(self):
        while True:
            if is_user_interacting():
                self.warm_adjacent_slice()
            else:
                sleep(IDLE_INTERVAL)

    def request_adjacent_chunks(self, current_chunk_id):
        # Request chunk on either side in ordering
        left_chunk = get_chunk_id(current_chunk_id, offset=-1)
        right_chunk = get_chunk_id(current_chunk_id, offset=1)
        fetch_async(left_chunk)
        fetch_async(right_chunk)

    def warm_adjacent_slice(self):
        # Warm adjacent slice to hide remote-fetch latency
        current_slice = get_current_slice_index()
        adjacent_slice = get_slice_index(current_slice, offset=1)
        prefetch_slice_ladder(adjacent_slice)
```

### Parameters
-   **Remote Fetch Latency**: Order of 100 ms [S1, unofficial].
-   **L2 Size**: 2 GB fixed [S1, unofficial].
-   **L1 Ceiling**: 100 MB [S1, unofficial].
-   **L0 Ceiling**: 200 MB [S1, unofficial].
-   **S-cache Default**: 128 MB [S1, unofficial].
-   **S-cache Max**: 2 GB [S1, unofficial].

### Edge Cases and Pitfalls
-   **Heap Tightness**: L0 and L1 must dynamically shrink to prevent OOM errors [S1, unofficial].
-   **Concurrency**: Prefetching must not block the main rendering thread [S1, unofficial].
-   **Data Consistency**: L2 writes must be atomic to prevent corruption during crashes [S1, unofficial].

## Subtopics

### [VxlSlabColumn Priority Cache](4742-vxlslabcolumn-priority-cache.md)
The VxlSlabColumn Priority Cache is a memory management mechanism for voxel volume data that loads and recompiles slab columns based on priority levels to ensure spatial neighbors are available for surface operations. It differs from sibling caches like the Rolling 3-Row Slab Cache by explicitly managing dirty/clean states via a priority enum (`Edit`, `Neighbor`, `Support`) and triggering recompilation only when necessary, rather than relying solely on spatial sliding windows.

### [Rolling 3-Row Slab Cache](4747-rolling-3-row-slab-cache.md)
The Rolling 3-Row Slab Cache is a memory structure that stores voxel column data across a rolling window of three Y-rows to support incremental updates and neighbor-dependent recompilation in dense voxel grids. It sets itself apart from sibling caches like the [VxlSlabColumn Priority Cache](4742-vxlslabcolumn-priority-cache.md) by maintaining a fixed-size sliding window of Y-indices rather than priority-based or full-grid storage, optimizing for locality during column-wise edits. It builds on the principles of [Multi-Level Cache and Prefetching](4631-multi-level-cache-and-prefetching.md) by restricting active memory to a narrow spatial band.

### [Dataset Prefetching](14225-dataset-prefetching.md)
Dataset Prefetching is a technique that decouples data retrieval from the rendering loop by running a background thread to prefetch batches into a queue. It solves the problem of CPU-bound data loading stalling the GPU by ensuring that volume data is available in memory before it is needed for rendering. Unlike sibling methods that focus on spatial caching hierarchies (e.g., [VxlSlabColumn Priority Cache](4742-vxlslabcolumn-priority-cache.md) or [Rolling 3-Row Slab Cache](4747-rolling-3-row-slab-cache.md)), this method focuses on temporal overlap of I/O and computation.

### Page Table and Cache Management
Management of the multi-resolution page directory, page table cache, and block cache using LRU/MRU schemes, where updates are initiated by cache misses reported by the ray-caster [S2]. On a cache miss, the CPU first checks if the required block is resident in the CPU block cache (a larger version in CPU memory of the GPU block cache) [S2]. If the block is in the CPU block cache, it is downloaded into the GPU block cache, and the page directory and page table cache are updated accordingly [S2]. If the block is not in the CPU block cache, a request for the 3D volume data block is issued asynchronously to the volume data construction stage. The download of block data and page table updates are deferred until the constructed block arrives [S2].

## Operating characteristics
-   **Time Complexity**: Cache hit is O(1) for L0/L1 lookup. Cache miss involves O(1) disk I/O or O(latency) network I/O. Prefetching is asynchronous and does not block rendering.
-   **Memory Complexity**: O(N) where N is the total volume size, but bounded by cache ceilings (2 GB L2, 100 MB L1, 200 MB L0, up to 2 GB S-cache).
-   **Measured Performance**: Hides remote-fetch latency of ~100 ms during user orbit or slider playback [S1, unofficial].
-   **Strengths**: Reduces perceived latency through prefetching; efficient memory usage via tiered compression; persistent storage via OPFS.
-   **Limitations**: Complex memory management logic; heap-dependent performance; requires HTTP range request support.
-   **When to Use**: Interactive web-based volume visualization with large datasets.
-   **When Not to Use**: Offline batch rendering where latency is not critical; environments without HTTP range request support.

## Background
Originating from the Luxar viewer for microscopy data, this method was developed to enable scalable interactive web visualization of multidimensional scientific data [S1, unofficial]. It addresses the limitations of traditional brick caching by integrating web-specific storage mechanisms (OPFS) and network optimizations (HTTP range requests) [S1, unofficial]. The approach is also related to multi-resolution page table management in petascale volume exploration systems [S2].
