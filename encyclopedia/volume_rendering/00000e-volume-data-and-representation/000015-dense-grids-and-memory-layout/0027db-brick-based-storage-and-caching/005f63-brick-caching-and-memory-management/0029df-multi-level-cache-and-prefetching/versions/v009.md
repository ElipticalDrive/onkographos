# Multi-Level Cache and Prefetching

Also called: HTTP Range Request Caching, Luxar Viewer Cache Architecture

## Overview
Multi-Level Cache and Prefetching is a data management strategy for dense volume rendering that decouples storage, decompression, and rendering through a tiered caching hierarchy and asynchronous prefetching. It solves the problem of high-latency remote data fetching and expensive on-the-fly decompression by maintaining multiple resolution and state levels in memory and persistent storage. It differs from sibling methods like [Brick Caching with LRU Replacement](879-brick-caching-with-lru-replacement.md) by explicitly separating compressed and decompressed states across distinct memory tiers (L0/L1/L2) and integrating an S-cache for fully decoded slices, while its prefetching mechanism is tailored to HTTP range requests and idle-time windowing rather than simple spatial sliding windows [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A multi-resolution volume dataset (e.g., Zarr archives, Luxar files) stored on remote or local disk; user interaction signals (orbit, slider playback).
*   **Output:** Ready-to-render voxel or splat data in GPU memory; updated cache states.

**Data Structures:**
The system employs a four-level cache structure [S1, unofficial]:
1.  **L2 (Persistent Storage):** Origin Private File System (OPFS) in the browser. Fixed size of 2 GB. Stores compressed chunks. Survives browser restarts.
2.  **L1 (Compressed In-Memory):** Stores decompressed chunks in RAM. Ceiling of 100 MB.
3.  **L0 (Decompressed In-Memory):** Stores fully decompressed chunks in RAM. Ceiling of 200 MB.
4.  **S-cache (Slice Cache):** Stores fully decoded slice ladders. Default size 128 MB, grows up to 2 GB based on available heap. Allows revisited slices to skip the chunk path entirely.

The L0 and L1 tiers are heap-aware: their ceilings shrink dynamically when system memory is tight [S1, unofficial].

**Steps:**
1.  **Request Initiation:** The renderer requests a data block (chunk or slice) for the current view.
2.  **Cache Lookup:**
    *   Check S-cache for fully decoded slice ladder. If hit, return immediately [S1, unofficial].
    *   Check L0 for decompressed chunk. If hit, return [S1, unofficial].
    *   Check L1 for compressed chunk. If hit, decompress in WebAssembly (WASM) and store in L0 [S1, unofficial].
    *   Check L2 (OPFS) for compressed chunk. If hit, load into L1 [S1, unofficial].
3.  **Remote Fetch:** If not found in any cache, issue an HTTP Range Request to fetch the compressed chunk from the server.
4.  **Decompression:** Upon arrival, decompress the chunk using Blosc/zstd codecs in WASM. Store in L0 and L1 as appropriate [S1, unofficial].
5.  **Prefetching:**
    *   **Immediate Prefetch:** After an on-disk hit or remote fetch, request the adjacent chunk in the data ordering [S1, unofficial].
    *   **Idle-Time Prefetch:** During user orbit or slider playback, warm the adjacent slice to hide remote-fetch latency (order of 100 ms) [S1, unofficial].

**Pseudocode:**
```python
def get_volume_data(requested_chunk_id):
    # Check S-cache first (fully decoded slice ladder)
    if requested_chunk_id in s_cache:
        return s_cache[requested_chunk_id]
    
    # Check L0 (decompressed in-memory)
    if requested_chunk_id in l0_cache:
        return l0_cache[requested_chunk_id]
    
    # Check L1 (compressed in-memory)
    if requested_chunk_id in l1_cache:
        compressed_data = l1_cache[requested_chunk_id]
        decompressed_data = decompress_wasm(compressed_data)
        l0_cache.put(requested_chunk_id, decompressed_data)
        # Evict from L0 if heap tight
        if l0_cache.size > l0_ceiling:
            l0_cache.evict_lru()
        return decompressed_data
    
    # Check L2 (OPFS persistent storage)
    if requested_chunk_id in l2_cache:
        compressed_data = l2_cache.read(requested_chunk_id)
        l1_cache.put(requested_chunk_id, compressed_data)
        # Evict from L1 if heap tight
        if l1_cache.size > l1_ceiling:
            l1_cache.evict_lru()
        # Fall through to decompress
        decompressed_data = decompress_wasm(compressed_data)
        l0_cache.put(requested_chunk_id, decompressed_data)
        if l0_cache.size > l0_ceiling:
            l0_cache.evict_lru()
        return decompressed_data
    
    # Remote Fetch
    compressed_data = fetch_http_range(requested_chunk_id)
    l2_cache.write(requested_chunk_id, compressed_data)
    # Evict from L2 if full (fixed 2GB limit)
    if l2_cache.size > l2_ceiling:
        l2_cache.evict_lru()
    
    l1_cache.put(requested_chunk_id, compressed_data)
    if l1_cache.size > l1_ceiling:
        l1_cache.evict_lru()
        
    decompressed_data = decompress_wasm(compressed_data)
    l0_cache.put(requested_chunk_id, decompressed_data)
    if l0_cache.size > l0_ceiling:
        l0_cache.evict_lru()
        
    # Immediate Prefetch
    prefetch_adjacent_chunk(requested_chunk_id)
    
    return decompressed_data

def idle_prefetch_loop():
    while user_is_interacting():
        adjacent_slice = get_next_slice_in_order()
        if adjacent_slice not in s_cache:
            prefetch_slice(adjacent_slice)
        sleep(short_interval)
```

**Parameters:**
*   L2 Size: 2 GB (fixed) [S1, unofficial].
*   L1 Ceiling: 100 MB [S1, unofficial].
*   L0 Ceiling: 200 MB [S1, unofficial].
*   S-cache Default: 128 MB [S1, unofficial].
*   S-cache Max: 2 GB [S1, unofficial].
*   Remote Fetch Latency: ~100 ms [S1, unofficial].

**Edge Cases:**
*   **Heap Pressure:** L0 and L1 ceilings shrink dynamically when memory is tight [S1, unofficial].
*   **Browser Restart:** L2 data persists, but L0/L1/S-cache are lost and must be refilled [S1, unofficial].

## Subtopics

### [VxlSlabColumn Priority Cache](4742-vxlslabcolumn-priority-cache.md)
The VxlSlabColumn Priority Cache is a memory management mechanism for voxel volume data that loads and recompiles slab columns based on priority levels to ensure spatial neighbors are available for surface operations. It differs from sibling caches like the Rolling 3-Row Slab Cache by explicitly managing dirty/clean states via a priority enum (`Edit`, `Neighbor`, `Support`) and triggering recompilation only when necessary, rather than relying solely on spatial sliding windows.

### [Rolling 3-Row Slab Cache](4747-rolling-3-row-slab-cache.md)
The Rolling 3-Row Slab Cache is a memory structure that stores voxel column data across a rolling window of three Y-rows to support incremental updates and neighbor-dependent recompilation in dense voxel grids. It sets itself apart from sibling caches like the [VxlSlabColumn Priority Cache](4742-vxlslabcolumn-priority-cache.md) by maintaining a fixed-size sliding window of Y-indices rather than priority-based or full-grid storage, optimizing for locality during column-wise edits. It builds on the principles of [Multi-Level Cache and Prefetching](4631-multi-level-cache-and-prefetching.md) by restricting active memory to a narrow spatial band.

### [Dataset Prefetching](14225-dataset-prefetching.md)
Dataset Prefetching is a technique that decouples data retrieval from the rendering loop by running a background thread to prefetch batches into a queue. It solves the problem of CPU-bound data loading stalling the GPU by ensuring that volume data is available in memory before it is needed for rendering. Unlike sibling methods that focus on spatial caching hierarchies (e.g., [VxlSlabColumn Priority Cache](4742-vxlslabcolumn-priority-cache.md) or [Rolling 3-Row Slab Cache](4747-rolling-3-row-slab-cache.md)), this method focuses on temporal overlap of I/O and computation.

### Page Table and Cache Management
Management of the multi-resolution page directory, page table cache, and block cache using LRU/MRU schemes, where updates are initiated by cache misses reported by the ray-caster [S2]. On a cache miss, the CPU first checks if the required block is resident in the CPU block cache (a larger version in CPU memory of the GPU block cache) [S2]. If the block is in the CPU block cache, it is downloaded into the GPU block cache, and the page directory and page table cache are updated accordingly [S2]. If the block is not in the CPU block cache, a request for the 3D volume data block is issued asynchronously to the volume data construction stage. The download of block data and page table updates are deferred until the constructed block arrives [S2].

## Operating characteristics
*   **Time Complexity:** Cache hits are O(1) for lookup. Decompression is O(N) where N is chunk size. Remote fetch is O(L) where L is latency (~100 ms) [S1, unofficial].
*   **Memory Complexity:** Bounded by cache ceilings: L2 (2 GB), L1 (100 MB), L0 (200 MB), S-cache (up to 2 GB) [S1, unofficial].
*   **Performance:** Hides remote-fetch latency via prefetching during idle times (orbit/slider) [S1, unofficial].
*   **Strengths:** Efficient use of persistent storage (OPFS), adaptive memory usage based on heap pressure, fast access to frequently revisited slices via S-cache [S1, unofficial].
*   **Limitations:** Complex cache coherence management between tiers. Dependency on browser features (OPFS, WASM).
*   **When to Use:** Interactive web-based volume rendering of large multidimensional datasets where network latency is significant and memory is constrained [S1, unofficial].
*   **When Not to Use:** Offline rendering with local SSD access where latency is negligible, or systems without browser/WASM support.

## Background
Originated in the Luxar viewer for interactive web visualization of multidimensional scientific data, specifically Gaussian splatting for microscopy [S1, unofficial]. The architecture leverages browser-native storage (OPFS) and WebAssembly for decompression to enable scalable interactive visualization [S1, unofficial].
