# Multi-Level Cache and Prefetching

Also called: HTTP Range Request Caching, Luxar Viewer Cache Architecture

## Overview
Multi-Level Cache and Prefetching is a memory management strategy for dense volume data that organizes cached resources into distinct tiers (disk, compressed memory, decompressed memory, and fully decoded slices) to minimize remote fetch latency and redundant decoding [S1, unofficial]. It differs from sibling methods like [Brick Caching with LRU Replacement](879-brick-caching-with-lru-replacement.md) by explicitly separating compressed and decompressed states across heap-aware tiers, and from [Tile-based Volume Ray Marching](1678-tile-based-volume-ray-marching.md) by utilizing HTTP range requests for granular chunk retrieval rather than pre-fetching entire tiles [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A sequence of volume data chunks (e.g., Zarr archives) stored on remote or local disk; user interaction events (orbit, slider playback).
*   **Output:** Ready-to-render voxel or splat data from the appropriate cache tier; prefetching requests for adjacent data.

**Data Structures:**
The system employs a four-level cache hierarchy [S1, unofficial]:
1.  **L2 (Disk/OPFS):** Origin Private File System storage. Fixed size of 2 GB. Stores compressed chunks.
2.  **L1 (Compressed Memory):** In-memory storage for compressed chunks. Ceiling of 100 MB.
3.  **L0 (Decompressed Memory):** In-memory storage for decompressed chunks. Ceiling of 200 MB.
4.  **S-cache (Slice Ladder):** Fully decoded slice ladders. Default size 128 MB, scalable up to 2 GB.

**Parameters:**
*   Remote fetch latency: ~100 ms [S1, unofficial].
*   L2 Size: 2 GB (fixed) [S1, unofficial].
*   L1 Ceiling: 100 MB [S1, unofficial].
*   L0 Ceiling: 200 MB [S1, unofficial].
*   S-cache Default: 128 MB [S1, unofficial].

**Steps:**
1.  **Request Processing:** When a ray-caster or viewer requests a chunk:
    *   Check **S-cache**. If present, return fully decoded slice data immediately [S1, unofficial].
    *   If not in S-cache, check **L0** (decompressed chunks). If present, return data [S1, unofficial].
    *   If not in L0, check **L1** (compressed chunks). If present, decompress using WASM-accelerated Blosc/zstd codecs and store in L0 [S1, unofficial].
    *   If not in L1, fetch from **L2** (OPFS) or remote server via HTTP range request. Store compressed data in L1 and decompressed data in L0 [S1, unofficial].
2.  **Heap-Aware Eviction:**
    *   Monitor available heap memory.
    *   If heap is tight, shrink L0 and L1 ceilings dynamically below their configured maximums to free memory [S1, unofficial].
    *   If heap is abundant, allow S-cache to grow from its 128 MB default up to 2 GB [S1, unofficial].
3.  **Prefetching:**
    *   **On-Disk/Remote Hit:** After fetching a chunk, trigger a prefetcher to request the adjacent chunk in the data ordering (left or right neighbor) [S1, unofficial].
    *   **Idle-Time:** During user orbit or slider playback, an idle-time prefetcher warms the adjacent slice to hide remote-fetch latency (~100 ms) [S1, unofficial].

**Pseudocode:**
```python
class MultiLevelCache:
    def __init__(self):
        self.l2_opfs = DiskStorage(capacity_gb=2.0) # Fixed 2 GB
        self.l1_compressed = MemoryStorage(ceiling_mb=100)
        self.l0_decompressed = MemoryStorage(ceiling_mb=200)
        self.s_cache_slices = MemoryStorage(default_mb=128, max_mb=2048)
        self.heap_monitor = HeapMonitor()

    def get_chunk(self, chunk_id):
        # 1. Check S-cache (Fully decoded slice ladders)
        if self.s_cache_slices.contains(chunk_id):
            return self.s_cache_slices.get(chunk_id)

        # 2. Check L0 (Decompressed in-memory chunks)
        if self.l0_decompressed.contains(chunk_id):
            return self.l0_decompressed.get(chunk_id)

        # 3. Check L1 (Compressed in-memory chunks)
        if self.l1_compressed.contains(chunk_id):
            compressed_data = self.l1_compressed.get(chunk_id)
            decompressed_data = self.decompress(compressed_data) # WASM Blosc/zstd
            self.l0_decompressed.put(chunk_id, decompressed_data)
            return decompressed_data

        # 4. Fetch from L2 or Remote
        # Try L2 (OPFS) first
        if self.l2_opfs.contains(chunk_id):
            compressed_data = self.l2_opfs.get(chunk_id)
        else:
            # Remote fetch via HTTP range request
            compressed_data = self.remote_fetch(chunk_id)
            self.l2_opfs.put(chunk_id, compressed_data)

        # Store in L1 and L0
        self.l1_compressed.put(chunk_id, compressed_data)
        decompressed_data = self.decompress(compressed_data)
        self.l0_decompressed.put(chunk_id, decompressed_data)

        # Trigger prefetching
        self.prefetch_adjacent(chunk_id)

        return decompressed_data

    def prefetch_adjacent(self, chunk_id):
        # Request chunk on either side in the ordering
        neighbor_id_left = self.get_neighbor_id(chunk_id, direction=-1)
        neighbor_id_right = self.get_neighbor_id(chunk_id, direction=1)
        
        # Asynchronous prefetch
        self.async_fetch(neighbor_id_left)
        self.async_fetch(neighbor_id_right)

    def update_heap_limits(self):
        # Shrink L0 and L1 if heap is tight
        if self.heap_monitor.is_tight():
            self.l0_decompressed.shrink_ceiling()
            self.l1_compressed.shrink_ceiling()
        # Grow S-cache if heap is abundant
        else:
            self.s_cache_slices.grow_ceiling()

    def idle_prefetch(self, current_slice_id):
        # Warm adjacent slice during orbit/slider
        adjacent_slice_id = self.get_adjacent_slice(current_slice_id)
        self.async_fetch_slice(adjacent_slice_id)
```

## Subtopics

### [VxlSlabColumn Priority Cache](4742-vxlslabcolumn-priority-cache.md)
The VxlSlabColumn Priority Cache is a memory management mechanism for voxel volume data that loads and recompiles slab columns based on priority levels to ensure spatial neighbors are available for surface operations. It differs from sibling caches like the Rolling 3-Row Slab Cache by explicitly managing dirty/clean states via a priority enum (`Edit`, `Neighbor`, `Support`) and triggering recompilation only when necessary, rather than relying solely on spatial sliding windows.

### [Rolling 3-Row Slab Cache](4747-rolling-3-row-slab-cache.md)
The Rolling 3-Row Slab Cache is a memory structure that stores voxel column data across a rolling window of three Y-rows to support incremental updates and neighbor-dependent recompilation in dense voxel grids. It sets itself apart from sibling caches like the [VxlSlabColumn Priority Cache](4742-vxlslabcolumn-priority-cache.md) by maintaining a fixed-size sliding window of Y-indices rather than priority-based or full-grid storage, optimizing for locality during column-wise edits. It builds on the principles of [Multi-Level Cache and Prefetching](4631-multi-level-cache-and-prefetching.md) by restricting active memory to a narrow spatial band.

### Dataset Prefetching
Runs a background thread to prefetch batches into a queue for asynchronous data loading [S2, unofficial]. It initializes a queue with size 3, starts the thread in daemon mode, and in an infinite loop, calls the appropriate next function (`_next_train` or `_next_test`) and puts the result into the queue [S2, unofficial].

### Page Table and Cache Management
Management of the multi-resolution page directory, page table cache, and block cache using LRU/MRU schemes, where updates are initiated by cache misses reported by the ray-caster [S3]. On a cache miss, the CPU first checks if the required block is resident in the CPU block cache (a larger version in CPU memory of the GPU block cache) [S3]. If the block is in the CPU block cache, it is downloaded into the GPU block cache, and the page directory and page table cache are updated accordingly [S3]. If the block is not in the CPU block cache, a request for the 3D volume data block is issued asynchronously to the volume data construction stage. The download of block data and page table updates are deferred until the constructed block arrives [S3].

## Operating characteristics
*   **Time Complexity:** Cache hits (L0/L1/S-cache) are O(1) memory access. Cache misses involve O(1) disk I/O or network latency (~100 ms) plus decompression time [S1, unofficial].
*   **Memory Complexity:** Bounded by the sum of cache ceilings: 2 GB (L2) + 100 MB (L1) + 200 MB (L0) + up to 2 GB (S-cache) = ~4.3 GB maximum [S1, unofficial].
*   **Strengths:** Hides remote fetch latency via prefetching; reduces redundant decoding by separating compressed and decompressed tiers; adapts to device memory constraints via heap-aware eviction [S1, unofficial].
*   **Limitations:** Complex state management across four tiers; requires efficient WASM codecs for decompression; fixed L2 size may not suit all datasets [S1, unofficial].
*   **When to use:** Interactive web-based visualization of large, multidimensional scientific data (e.g., microscopy) where network latency is significant and memory is constrained [S1, unofficial].
*   **When not to use:** Offline batch processing where latency is less critical; environments without browser support for OPFS or WASM [S1, unofficial].

## Background
The method originates from the Luxar viewer architecture for interactive web visualization of multidimensional scientific data, specifically Gaussian splatting for microscopy [S1, unofficial]. It leverages browser-native storage (OPFS) and HTTP range requests to enable scalable, progressive loading of large datasets [S1, unofficial].
