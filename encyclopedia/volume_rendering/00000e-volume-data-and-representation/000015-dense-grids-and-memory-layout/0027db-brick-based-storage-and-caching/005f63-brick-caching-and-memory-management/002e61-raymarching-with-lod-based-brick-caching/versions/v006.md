# Raymarching with LOD-based Brick Caching

Also called: Brick Caching and Decoding, Compressed Segmentation Volume (CSV) Visualization

## Overview
Raymarching with LOD-based Brick Caching is a visualization method for Compressed Segmentation Volumes (CSVs) that renders volumes by decompressing bricks on-demand at the required Level of Detail (LOD) and storing them in a GPU cache [S1]. It solves the problem of efficiently rendering massive segmentation datasets by exploiting temporal coherency and empty-space skipping, allowing a one-frame lag for decompression requests to decouple rendering speed from data decompression [S1]. It differs from Shading Atlas Streaming (SAS) by testing bricks for empty space using palettes before requesting cache locations, omitting superblock/column concepts in favor of contiguous base elements, and decompressing bricks during location assignment [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** Compressed Segmentation Volume (CSV) data, Transfer Function (TF), camera position and orientation.
*   **Output:** Rendered image.

**Data Structures:**
1.  **CSV Storage:**
    *   Coarse LOD data (palette and data) stored in GPU memory.
    *   Fine LOD data stored in CPU memory, streamed to GPU on demand [S1].
    *   Each compressed brick contains a palette of labels. The palette has orders of magnitude fewer entries than the voxels in the brick [S1].
2.  **Cache Structure:**
    *   Pool of base elements, each of size $2^3$ voxels [S1].
    *   Blocks of size $2^{3 \cdot l}$ (where $l = 1..N$) are formed from contiguous base elements to store decompressed bricks of LOD level $l$ [S1].
    *   Bricks at the coarsest resolution ($l=0$) do not need decompression; their data is stored as the first palette entry [S1].
    *   One stack $S_l$ per LOD level stores indices of free blocks [S1].
    *   A shared cache top pointer is atomically advanced to allocate new base elements if stacks are empty [S1].
3.  **Request Buffer:**
    *   Buffer of brick indices requiring fine detail levels [S1].
    *   Upload buffer size: 8 MB (sufficient in most frames; if insufficient, upload is distributed across several frames) [S1].

**Algorithm Steps:**

1.  **Raymarching and LOD Determination:**
    *   Perform straightforward raymarching with one ray per pixel [S1].
    *   For visible bricks intersected by a ray, determine the required LOD based on the distance of the brick's center to the camera, targeting approximately one voxel per pixel on screen [S1].
    *   If the desired LOD is not in the cache, request it for the next frame. Allow a one-frame lag; if not yet decompressed, fall back to the coarsest LOD (stored as the first palette entry) [S1].
    *   **Shadow Rays:** For hit voxels above a user-defined opacity threshold, send an additional shadow ray. Optionally approximate ambient occlusion by accumulating shadow rays over time [S1].

2.  **Empty-Space Skipping:**
    *   Check if any palette entry is mapped to opacity > 0. If none, skip the entire brick (do not decompress) [S1].

3.  **Cache Assignment (Post-Frame):**
    *   After rendering a frame, determine required bricks/LODs for the next frame [S1].
    *   Test visibility against Transfer Function (TF). Mark visible bricks with ascending indices [S1].
    *   Count bricks per LOD [S1].
    *   Evict invisible bricks from cache, pushing their blocks onto respective stacks $S_l$ [S1].
    *   Check if stacks $S_l$ have enough free blocks for all requests of level $l$.
    *   If not, allocate new blocks by advancing the cache top pointer. If insufficient base elements exist, rebuild the cache (clear all blocks/stacks and re-decompress all visible bricks) [S1].

4.  **Decompression and Streaming:**
    *   Decompress requested bricks in parallel on the GPU and store results in the assigned cache locations [S1].
    *   Determine if fine detail levels are needed. Add brick indices to a request buffer [S1].
    *   Transfer buffer to CPU memory [S1].
    *   Generate a buffer of requested detail levels in parallel to rendering the next frame and asynchronously upload to GPU [S1].
    *   Handle lag: Decompress a brick only up to the finest available level in GPU memory, or predictively upload detail information for bricks close to the camera [S1].

**Pseudocode:**

```python
def render_frame(csv_data, tf, camera):
    # 1. Raymarching
    for each pixel:
        ray = cast_ray(camera, pixel)
        brick = find_intersected_brick(ray)
        
        # Empty-Space Skipping
        if not is_brick_visible(csv_data[brick].palette, tf):
            continue
            
        # LOD Determination
        lod = determine_lod(brick.center, camera.position)
        
        # Cache Check
        if lod in cache[brick]:
            voxel_data = cache[brick][lod]
        else:
            # Request for next frame, fallback to coarsest (l=0)
            request_buffer.add((brick, lod))
            voxel_data = cache[brick][0] # Coarsest LOD always available
            
        # Raymarch through voxel_data
        color = raymarch(voxel_data, ray, tf)
        
        # Shadow Ray
        if opacity_above_threshold(color):
            shadow_color = cast_shadow_ray(ray)
            color = apply_shadow(color, shadow_color)
            
    return image

def cache_assignment(csv_data, tf, previous_requests):
    # Determine required bricks/LODs for next frame
    next_requests = {}
    
    # Evict invisible bricks
    for brick in cache:
        if not is_brick_visible(csv_data[brick].palette, tf):
            evict_brick_from_cache(brick)
            push_to_stack(brick.lod, brick.block_index)
            
    # Mark visible bricks and count
    for brick, lod in previous_requests:
        if is_brick_visible(csv_data[brick].palette, tf):
            next_requests[(brick, lod)] = True
            
    # Allocate cache space
    for lod in next_requests:
        needed_blocks = count_bricks_at_lod(next_requests, lod)
        free_blocks = size_of_stack(lod)
        
        if free_blocks < needed_blocks:
            allocated = allocate_from_top_pointer(lod, needed_blocks - free_blocks)
            if allocated < needed_blocks:
                rebuild_cache(csv_data, tf)
                return
                
    # Decompress and Store
    for brick, lod in next_requests:
        if lod > 0:
            decompressed = decompress(csv_data[brick], lod)
            cache[brick][lod] = decompressed
            
    # Handle Fine Detail Streaming
    fine_detail_requests = []
    for brick, lod in next_requests:
        if lod == 0: # Need finest detail, but only coarse is in GPU
            fine_detail_requests.append(brick)
            
    upload_buffer = generate_upload_buffer(fine_detail_requests)
    transfer_to_cpu(upload_buffer)
    
    # Asynchronous upload for next frame
    async_upload_to_gpu(upload_buffer)
```

**Parameters:**
*   **Upload Buffer Size:** 8 MB [S1].
*   **Opacity Threshold:** User-defined threshold for sending shadow rays [S1].
*   **LOD Target:** Approximately one voxel per pixel on screen [S1].

**Edge Cases and Pitfalls:**
*   **Cache Rebuild:** If insufficient base elements exist, the cache is rebuilt. This happens extremely seldom for reasonably sized cache pools [S1].
*   **Lag Artifacts:** Allowing a one-frame lag for decompression results in small artifacts, but is acceptable for reasonably high frame rates [S1].
*   **Buffer Overflow:** If more detail data is requested than the 8 MB buffer can hold, the upload is distributed across several frames, trading LOD adaptation for responsivity/interactivity [S1].

## Operating characteristics
*   **Time Complexity:** Decompression is performed in parallel on the GPU. Cache assignment and eviction are linear with respect to the number of visible bricks [S1].
*   **Memory Complexity:** Depends on the cache size and the separation of coarse/fine LOD data. For the CORTEX dataset (6144x9216x4096 voxels), memory consumption for L0 (finest detail) is 9.2 GB, while all other levels take 4.3 GB [S1].
*   **Performance:** Efficiently handles large CSVs by streaming fine detail levels only when required [S1].
*   **Strengths:** Exploits temporal coherency, empty-space skipping, and LOD-based caching to reduce memory bandwidth and decompression overhead [S1].
*   **Limitations:** One-frame lag for decompression may cause visual artifacts during rapid camera movement [S1]. Cache rebuilds, though rare, can cause stuttering [S1].

## Background
The method is described in "Fast Compressed Segmentation Volumes for Scientific Visualization" [S1]. It builds on Shading Atlas Streaming (SAS) but introduces optimizations specific to Compressed Segmentation Volumes (CSVs) [S1]. The approach is designed for scientific visualization of large segmentation datasets [S1].
