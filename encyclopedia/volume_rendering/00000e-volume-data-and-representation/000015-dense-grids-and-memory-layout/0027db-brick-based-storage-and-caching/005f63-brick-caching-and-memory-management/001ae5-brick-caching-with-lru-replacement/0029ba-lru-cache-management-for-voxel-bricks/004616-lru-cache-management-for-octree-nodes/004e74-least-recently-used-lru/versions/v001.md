# Least Recently Used (LRU)

Also called: Least Recently Used Strategy

## Overview
Least Recently Used (LRU) is a demand-based page replacement algorithm used to manage the caching of octree nodes in volume rendering. It operates by evicting the node that has not been accessed for the longest period, providing a good approximation to the optimal algorithm without requiring pre-paging or knowledge of future access patterns [Parent]. It is distinguished from its siblings by its simplicity and lack of application-specific logic, serving as a generic baseline for evaluating more complex prefetching strategies [S1].

## How it works
LRU maintains a cache of octree nodes and tracks the last access time for each node. When a new node is requested, it is loaded into the cache and marked as the most recently used. If the cache is full and a new node must be loaded, the node with the oldest access timestamp is evicted.

**Inputs and Outputs:**
- Input: A sequence of node access requests.
- Output: Cache state updates (load, evict, update timestamp).

**Data Structures:**
1.  **Cache Set**: A collection of cached octree nodes.
2.  **Access Timestamps**: A mapping from node ID to the time of its last access.
3.  **LRU List/Stack**: A doubly-linked list or stack ordered by recency of access, where the head represents the most recently used node and the tail represents the least recently used node.

**Steps:**
1.  **Request**: When a node $N$ is requested:
    a.  If $N$ is in the cache, update its timestamp to the current time and move it to the head of the LRU list.
    b.  If $N$ is not in the cache:
        i.  If the cache is full, identify the node $E$ at the tail of the LRU list (the least recently used).
        ii. Evict $E$ from the cache and remove it from the LRU list.
        iii. Load $N$ into the cache, add it to the LRU list at the head, and set its timestamp.
2.  **Eviction**: The eviction decision is deterministic based solely on the last access time.

**Parameters:**
- Cache Size: The maximum number of octree nodes to hold in memory. Not given in the sources.

**Edge Cases and Pitfalls:**
- **Belady’s Anomaly**: LRU does not suffer from Belady’s anomaly, meaning increasing the cache size will never decrease performance [Parent].
- **Precision**: Timestamps must have sufficient precision to distinguish between recent and older accesses. [G] In practice, monotonic counters or high-resolution timers are used.

## Subtopics

### Cache Retention Policy
A cache policy that favors reusable prerequisite blocks by assigning retention scores based on near-future demand, shared base membership, dependency centrality, age, and size. It is asymmetric, keeping lower-layer prerequisites more aggressively than transient higher-layer refinements [S2, unofficial]. It applies freshness, version, expiry, and digest checks before retention scoring to ensure reuse cannot silently mix stale blocks from different scene versions [S2, unofficial]. The retention score for block $r$ is calculated as:
$$ H_x(r) = \beta_1 \rho_x(r) + \beta_2 [r \in B_x] + \beta_3 \text{cent}(r) - \beta_4 \text{age}(r) - \beta_5 s(r) $$
where $\rho_x(r)$ is near-future demand, $[r \in B_x]$ is 1 if in shared base else 0, $\text{cent}(r)$ is dependency centrality, $\text{age}(r)$ is age, and $s(r)$ is size. All terms are normalized over the currently cached set [S2, unofficial].

## Operating characteristics
- **Time Complexity**: $O(1)$ for access and update if implemented with a hash map and doubly-linked list. $O(N)$ if implemented with a simple array.
- **Memory Complexity**: $O(N)$ where $N$ is the number of cached nodes.
- **Strengths**: Simple to implement; does not suffer from Belady’s anomaly; provides a good approximation to the optimal algorithm [Parent].
- **Limitations**: Contains a very limited amount of application-specific logic, making it less effective than knowledge-based predictors in scenarios with complex access patterns [S1].
- **When to use**: As a baseline for evaluating other algorithms; scenarios where simplicity is preferred over predictive accuracy [S1].
- **When not to use**: When application-specific access patterns (e.g., ray-driven or history-based) can significantly improve hit rates [S1].

## Background
LRU is a simple memory management algorithm discussed extensively in many textbooks on operating systems [S1]. It is used in volume rendering research as a baseline for evaluating out-of-core prefetching strategies, such as Ray Driven Predictor (RDP), Access Path Predictor (APP), and History-based Access Predictor (HAP) [S1].
