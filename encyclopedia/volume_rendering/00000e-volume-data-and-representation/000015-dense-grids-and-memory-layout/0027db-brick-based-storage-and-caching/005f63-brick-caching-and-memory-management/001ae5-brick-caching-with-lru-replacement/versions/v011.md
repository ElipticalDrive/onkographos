# Brick Caching with LRU Replacement

Also called: Block Memory Management Unit (MMU) with LRU Eviction, Brick Pool Manager, Dynamic Brick Cache, Volume Block Cache

## Overview
Brick Caching with LRU Replacement manages a fixed-size pool of volume data blocks, mapping brick coordinates to pool indices and evicting least-recently-used blocks when the pool is full [S2, unofficial]. It solves the problem of limited GPU memory capacity and slow data transfer rates by ensuring that the most frequently or recently needed brick data remains in the fast working set [S1][S2, unofficial]. It distinguishes itself from its siblings by maintaining a direct mapping between logical brick coordinates and a physical memory pool, often utilizing a precomputed count buffer to skip empty bricks efficiently [S2, unofficial]. Unlike [Multi-Level Cache and Prefetching](4631-multi-level-cache-and-prefetching.md) which focuses on hierarchical prediction, or [Raymarching with LOD-based Brick Caching](5776-raymarching-with-lod-based-brick-caching.md) which ties caching to traversal depth, this method focuses on the static management of a flat brick pool with strict LRU eviction policies [S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Volume dimensions, brick size, brick pool ratio, isovalue (for active brick determination), and file handles for brick storage.
*   **Output:** A pointer to a valid brick block given a 3D coordinate $(x, y, z)$, or `nullptr` if the brick is not resident or empty.

**Data Structures:**
The core structure is the Block Memory Management Unit (MMU) [S2, unofficial].
1.  **dims**: Vector3i, total volume dimensions in voxels.
2.  **brick_dims**: Vector3i, calculated as $\lceil \text{dims} / \text{brick\_size} \rceil$.
3.  **brick_size**: Vector3i, dimensions of each brick in voxels.
4.  **entries**: Array of `Entry` structs, size `brick_dims.x * brick_dims.y * brick_dims.z`.
    *   `Entry` layout:
        *   `valid`: bool, indicates if the entry maps to a valid block.
        *   `blk_idx`: int, index into the `blocks` array.
5.  **blocks**: Array of `Block` structs, size `blk_nums`.
    *   `blk_nums`: int, total number of blocks in the pool, calculated as `brick_dims.x * brick_dims.y * brick_dims.z * _brick_num_ratio`.
6.  **data**: `uchar*`, a contiguous memory pool of size `blk_nums * (brick_size.x + 1) * (brick_size.y + 1) * (brick_size.z + 1)` [S2, unofficial]. Bricks are stored with size $(n+1)^3$ to include neighbor samples for filtering [S1].
7.  **cnt_buf**: `int*`, a count buffer of size `brick_dims.x * brick_dims.y * brick_dims.z * 256`. Used to quickly determine if a brick is empty based on color transfer function samples [S2, unofficial].
8.  **clock_pos**: int, current position in the LRU clock algorithm [S2, unofficial].
9.  **blk_used**: int, number of currently used blocks in the pool [S2, unofficial].
10. **mutex**: pthread_mutex_t, for thread-safe access [S2, unofficial].
11. **fin**: ifstream, file handle for loading bricks [S2, unofficial].

**Parameters:**
*   **brick_size**: Dimensions of each brick in voxels. Typical values depend on the volume; e.g., $32^3$ bricks for a $512^3$ volume [S1].
*   **_brick_num_ratio**: Fraction of total bricks to keep in memory pool. Example: 0.5 for 50% [S2, unofficial].
*   **GPU Resolution Limit**: Hardware constraint, e.g., $512^3$ on NVIDIA GeForce 6 [S1].
*   **Memory Limit**: Hardware constraint, e.g., 256MB [S1].

**Algorithm Steps:**

1.  **Initialization:**
    *   Calculate `brick_dims` from volume `dims` and `brick_size`.
    *   Allocate `entries` array of size `brick_dims.x * brick_dims.y * brick_dims.z`. Initialize all `valid` to false.
    *   Calculate `blk_nums` using `_brick_num_ratio`.
    *   Allocate `blocks` array of size `blk_nums`.
    *   Allocate `data` buffer of size `blk_nums * (brick_size.x + 1) * (brick_size.y + 1) * (brick_size.z + 1)`.
    *   Load `cnt_buf` from disk. Size is `brick_dims.x * brick_dims.y * brick_dims.z * 256` [S2, unofficial].

2.  **Get Block (Lookup):**
    *   Input: Brick coordinates $(bx, by, bz)$.
    *   If $(bx, by, bz)$ exceeds `brick_dims`, return `nullptr`.
    *   If a 1D transfer function `tf1d` is provided:
        *   Calculate `cnt_base = (bz * brick_dims.y + by) * brick_dims.x + bx`.
        *   Iterate `idx` from 0 to 255:
            *   If `cnt_buf[cnt_base + idx] != 0` AND `tf1d->sampleSimple(idx).w != 0`:
                *   Break loop (brick is potentially active).
        *   If `idx == 256` (loop completed without match), return `nullptr` (brick is empty for current isovalue) [S2, unofficial].
    *   Check `entries[bz * brick_dims.y * brick_dims.x + by * brick_dims.x + bx]`.
    *   If `entry.valid` is true:
        *   Mark block as used (update LRU state, e.g., move to front of LRU list or update timestamp) [S2, S3, unofficial].
        *   Return pointer to block data in `data` array.
    *   If `entry.valid` is false:
        *   Lock `mutex` [S2, unofficial].
        *   If `blk_used < blk_nums`:
            *   Assign next free slot from `blocks` array.
        *   Else (pool full):
            *   Use `clock_pos` to find the first unused block in the `blocks` array (LRU-like eviction) [S2, unofficial].
            *   Mark the old entry in `entries` as invalid.
            *   Reuse the slot.
        *   Load block data from file into the assigned slot in `data` [S2, unofficial].
        *   Mark `entry.valid` to true, store `blk_idx`.
        *   Increment `blk_used` if a new slot was assigned.
        *   Unlock `mutex`.
        *   Return pointer to block data.

    def __init__(self, dims, brick_size, brick_num_ratio):
        self.brick_size = brick_size
        self.brick_dims = Vector3i(
            ceil(dims.x / brick_size.x),
            ceil(dims.y / brick_size.y),
            ceil(dims.z / brick_size.z)
        )
        self.blk_nums = int(self.brick_dims.x * self.brick_dims.y * self.brick_dims.z * brick_num_ratio)
        self.entries = [Entry() for _ in range(self.brick_dims.x * self.brick_dims.y * self.brick_dims.z)]
        self.blocks = [Block() for _ in range(self.blk_nums)]
        self.data = [0] * (self.blk_nums * (brick_size.x + 1) * (brick_size.y + 1) * (brick_size.z + 1))
        self.cnt_buf = load_cnt_buf_from_disk(self.brick_dims)
        self.clock_pos = 0
        self.blk_used = 0
        self.mutex = Mutex()

    def get_block(self, bx, by, bz, tf1d=None):
        if bx >= self.brick_dims.x or by >= self.brick_dims.y or bz >= self.brick_dims.z:
            return None

        # Check if brick is empty for current isovalue
        if tf1d is not None:
            cnt_base = (bz * self.brick_dims.y + by) * self.brick_dims.x + bx
            is_active = False
            for idx in range(256):
                if self.cnt_buf[cnt_base + idx] != 0 and tf1d.sample_simple(idx).w != 0:
                    is_active = True
                    break
            if not is_active:
                return None

        entry_idx = (bz * self.brick_dims.y + by) * self.brick_dims.x + bx
        entry = self.entries[entry_idx]

        if entry.valid:
            # Mark as used (LRU update logic)
            self.update_lru(entry.blk_idx)
            return self.get_block_data(entry.blk_idx)

        with self.mutex:
            if self.blk_used < self.blk_nums:
                blk_idx = self.blk_used
                self.blk_used += 1
            else:
                # LRU Eviction
                blk_idx = self.find_lru_block()
                old_entry_idx = self.blocks[blk_idx].entry_idx
                self.entries[old_entry_idx].valid = False

            # Load block
            self.load_block_from_disk(blk_idx, bx, by, bz)
            
            entry.valid = True
            entry.blk_idx = blk_idx
            self.blocks[blk_idx].entry_idx = entry_idx
            
        return self.get_block_data(blk_idx)

    def find_lru_block(self):

        self.clock_pos = (self.clock_pos + 1) % self.blk_nums
        return self.clock_pos

**Edge Cases and Pitfalls:**
*   **Precision:** Brick coordinates must be correctly mapped to volume coordinates. Off-by-one errors in `brick_dims` calculation can lead to out-of-bounds access [S2, unofficial].
*   **Boundaries:** Bricks at the volume boundary may have incomplete neighbor samples if not padded to $(n+1)^3$ [S1].
*   **Degenerate Input:** Empty bricks (all zeros) should be detected via `cnt_buf` to avoid unnecessary cache fills and memory usage [S2, unofficial].
*   **Concurrency:** The cache must be thread-safe if accessed by multiple rays or threads. A mutex is required for pool management [S2, unofficial].

## Subtopics

### [Block-based Ray Cache](2260-block-based-ray-cache.md)
The Block-based Ray Cache is a memory management technique for volume rendering that reduces reconstruction overhead by caching reconstructed voxel blocks in memory for reuse by adjacent rays. It solves the problem of redundant computation in high-resolution volume rendering where data exceeds physical memory, by maintaining a sequence of blocks along completed rays and retrieving them for subsequent ray traces. It distinguishes itself from standard spatial traversal by decoupling the processing order of blocks from the ray order within a frame, relying on a sorted auxiliary list structure to ensure cache hits for spatially coherent rays.

### [LRU Cache Eviction with Residency Update](3115-lru-cache-eviction-with-residency-update.md)
This method couples LRU brick cache eviction with hierarchical residency octree updates. When the cache lacks a free slot, it evicts the least recently accessed brick and resets bitmask entries in affected leaf and non-leaf nodes to reflect the loss of resident data. It differs from standard LRU caches by synchronizing cache state with octree metadata after each eviction.

### [Brick Cache Implementation](3222-brick-cache-implementation.md)
The Brick Cache is a single-channel 3D texture cache that stores bricks from a multi-resolution multi-volume hierarchy. It is agnostic to the number of data channels in the underlying dataset. It differs from general-purpose CPU caches by being implemented as a GPU-resident texture managed via LRU replacement using WebGPU compute passes.

### [GPU-Steered LRU Cache Management](3654-gpu-steered-lru-cache-management.md)
This method enables the GPU to steer data loading for volume rendering by indicating which nodes were helpful, using spatial and temporal coherence to update an LRU cache on the CPU without significant overhead. It solves the problem of CPU-side cache management overhead and visibility query costs by unifying the rendering and visibility update phases, allowing the GPU to dictate brick and node pool states based on actual traversal history. It sets itself apart from sibling methods like [Block-based Ray Cache](2260-block-based-ray-cache.md) by explicitly managing the hierarchical N³-tree node pool alongside the brick pool, and from [LRU Cache Eviction with Residency Update](3115-lru-cache-eviction-with-residency-update.md) by offloading the decision logic to the GPU rather than relying on CPU-driven occlusion queries or simple residency flags.

### [LRU Cache Management for Voxel Bricks](4571-lru-cache-management-for-voxel-bricks.md)
LRU Cache Management for Voxel Bricks is a memory management strategy for out-of-core volume rendering that prioritizes the retention of recently accessed voxel bricks to optimize memory reuse. It solves the problem of limited GPU memory capacity and slow data transfer rates by ensuring that the most frequently or recently needed brick data remains in the fast working set. Unlike sibling methods that may rely on complex prediction models or GPU-steered updates, this approach typically manages the cache state on the CPU to bypass shader memory write limitations, or uses specific GPU buffers to track access timestamps.

### [CPU Cache with Write-Back](10163-cpu-cache-with-write-back.md)
CPU DRAM serves as a warm cache between SSD storage and GPU VRAM, maintaining an LRU cache over volume blocks with per-block dirty bits. It decouples GPU residency from SSD write latency by staging evicted blocks in CPU memory before persisting them, turning frequent small updates into batched sequential appends. This method builds on [Brick Caching with LRU Replacement](879-brick-caching-with-lru-replacement.md) by adding a write-back policy that distinguishes between clean and dirty blocks, preventing unnecessary SSD writes for blocks that are still being actively reused.

### Brick Cache Updates
Uploads a user-defined number of brick data from the file server to the GPU each frame. Each brick comprises its global brick ID and either the EMPTY value (if all zeros) or the pre-processed brick. The brick's global brick ID is translated to a local brick ID. If the brick's channel is not represented by the multi-channel page-table hierarchy, the brick is discarded. If the brick is EMPTY, the corresponding page in the multi-channel page-table hierarchy is marked as EMPTY. Otherwise, the page is marked as MAPPED, and the brick's data is added to the brick cache. The LRU buffer is used to find free cache entries or entries not accessed recently. When a brick is removed from the cache, its corresponding page is marked as UNMAPPED. Two lists of local brick IDs are passed to the residency octree: 1) IDs of bricks marked EMPTY or MAPPED, 2) IDs of bricks marked UNMAPPED [S3, unofficial].

### Two-Step Eviction and Write-Back
When a block is evicted from VRAM, it is transferred via D2H and inserted into the CPU cache. Clean blocks are inserted as clean; dirty blocks as dirty. When a dirty block is evicted from the CPU cache, it is asynchronously flushed to SSD patch segments, appending a new version and updating Index[k]. On re-admission, blocks are fetched via Index[k] to ensure the GPU materializes the most recent version [S4, unofficial].

## Operating characteristics
**Time Complexity:**
*   Cache Hit: $O(1)$ average [S2, unofficial].
*   Eviction Search: $O(1)$ amortized [S2, unofficial].
*   Empty Brick Check: $O(256)$ worst-case for checking the count buffer [S2, unofficial].

**Memory Complexity:**
*   $O(\text{blk\_nums} \times \text{brick\_volume} + \text{brick\_count} \times 256 \times \text{sizeof(int)})$ [S2, unofficial].
*   Brick storage overhead is inversely proportional to brick size due to the $(n+1)^3$ padding for neighbor samples [S1].

**Measured Performance:**
*   Example: 512^3 volume on NVIDIA GeForce 6 with 256MB memory limit [S1].
*   Reference texture size: 16^3 for a 512^3 volume with 32^3 bricks [S1].

**Strengths and Limitations:**
*   **Strengths:** Decouples volume size from GPU resolution and memory limits [S1]. Efficiently skips empty bricks using precomputed count buffers [S2, unofficial]. Simple LRU policy is easy to implement [S2, unofficial].
*   **Limitations:** LRU may not be optimal for all access patterns. Mutex contention can be a bottleneck in multi-threaded environments [S2, unofficial].

**When to Use:**
*   When rendering large volumes that exceed GPU memory.
*   When isovalue changes are frequent, and active brick determination is needed [S1].

**When Not to Use:**
*   When memory bandwidth is the primary bottleneck and prefetching would be more effective.
*   When complex hierarchical access patterns require more sophisticated caching strategies like multi-level caches [4631-multi-level-cache-and-prefetching.md].

## Background
Originated in real-time ray-casting of discrete isosurfaces to handle volumes larger than GPU memory [S1]. The method uses a low-resolution reference texture to map volume coordinates to a brick cache texture, allowing dynamic management of resident bricks [S1]. It builds on the idea of adaptive texture maps [KE02] but maintains the reference and cache textures dynamically [S1].
