# Block-based Ray Cache

Also called: Buffered-block list, Cache Data Structure for Ray Tracing

## Overview
The Block-based Ray Cache is a memory optimization technique for volume rendering that reduces reconstruction overhead by retaining reconstructed voxel blocks in memory for reuse by adjacent rays [S1, unofficial]. It solves the problem of redundant computation in high-resolution volume rendering where data exceeds physical memory, allowing rendering times to drop from days to minutes [S1, unofficial]. It sets itself apart from sibling methods by explicitly maintaining a sorted list of blocks along the ray depth to facilitate immediate lookup, rather than relying solely on generic LRU eviction without spatial locality awareness [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A ray trace request for a specific voxel coordinate; the current state of the cache (buffered blocks).
*   **Output:** The voxel value (if cached) or a newly reconstructed block added to the cache.

**Data Structures:**
The core structure is an auxiliary list called the **buffered-block list** [S1, unofficial].
*   **Node Layout:** Each node in the list represents a reconstructed block.
    *   `block_id`: Identifier for the block.
    *   `boundaries`: The 3D spatial boundaries (min/max coordinates) of the block.
    *   `data`: The voxel values of the reconstructed block.
    *   `timestamp` or `position`: Used to determine the "oldest" block for replacement.
*   **Ordering:** The list is maintained in sorted order according to the depth of the blocks along the current ray [S1, unofficial].

**Algorithm Steps:**
1.  **Ray Tracing Initiation:** Begin tracing a projection ray through the volume.
2.  **Cache Lookup:** For each voxel access along the ray:
    a.  Search the buffered-block list for a node whose `boundaries` contain the requested voxel coordinate [S1, unofficial].
    b.  **Hit:** If found, retrieve the voxel value immediately from the cached block data.
    c.  **Miss:** If not found, invoke the block reconstruction procedure to generate the block containing the voxel.
3.  **Buffering:** After a block is reconstructed, buffer it in cache memory instead of discarding it [S1, unofficial]. Add a new node to the buffered-block list with the block's boundaries and data.
4.  **List Maintenance:** Ensure the buffered-block list remains sorted by depth along the ray [S1, unofficial].
5.  **Replacement:** If the cache is full:
    a.  Identify the oldest block in the buffered-block list (based on the replacement policy) [S1, unofficial].
    b.  Remove the oldest node from the list.
    c.  Substitute the oldest block with the newly reconstructed block.
    d.  Update the buffered-block array with the new block's boundaries [S1, unofficial].
6.  **Completion:** After the ray tracing is complete, the sequence of blocks reconstructed along that ray remains in the cache for potential use by adjacent rays [S1, unofficial].

**Formulas:**
*   **Cache Size Requirement:** In 3D, for an image resolution of $N \times N$ and a block size of $s \times s \times s$, the total number of blocks to store in the cache is:
    $$ \text{Total Blocks} = 2 \times s \times N \times N $$
    This accounts for two layers of sub-volumes sufficient to cover worst-case access patterns [S1, unofficial].

**Parameters:**
*   $N$: Volume data dimension (e.g., 256, 1024).
*   $s$: Block size dimension (e.g., 16, 32).
*   Typical Cache Sizes:
    *   For $N=256$: 0.5 MB ($s=16$) or 1 MB ($s=32$) [S1, unofficial].
    *   For $N=1024$: 2 MB ($s=16$) or 4 MB ($s=32$) [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Cache Size Too Small:** If the cache memory size is too small, the hit rate becomes very small, degrading performance [S1, unofficial].
*   **Redundant Reconstruction:** Failing to cache blocks leads to significant performance loss, as voxels reconstructed along one ray are likely used by adjacent rays [S1, unofficial].
*   **Boundary Conditions:** The block-wise reconstruction method must handle extended block boundaries correctly to ensure seamless access across block edges [S1, unofficial].

**Pseudocode:**
```python
class BufferedBlockNode:
    def __init__(self, block_id, boundaries, data):
        self.block_id = block_id
        self.boundaries = boundaries  # Tuple of (min_x, min_y, min_z, max_x, max_y, max_z)
        self.data = data
        self.depth = calculate_depth(boundaries)  # Depth along the ray

def search_cache(buffered_block_list, voxel_coord):
    """
    Search the buffered-block list for a block containing the voxel.
    Returns the block data if found, else None.
    """
    for node in buffered_block_list:
        if is_voxel_in_block(voxel_coord, node.boundaries):
            return node.data
    return None

def is_voxel_in_block(voxel, boundaries):
    min_x, min_y, min_z, max_x, max_y, max_z = boundaries
    return (min_x <= voxel.x <= max_x and
            min_y <= voxel.y <= max_y and
            min_z <= voxel.z <= max_z)

def replace_oldest(buffered_block_list, new_node):
    """
    Remove the oldest block (lowest depth) and insert the new node.
    Assumes list is sorted by depth.
    """
    if len(buffered_block_list) > 0:
        # Remove the first element (oldest)
        buffered_block_list.pop(0)
    # Insert new node maintaining sorted order by depth
    insert_sorted(buffered_block_list, new_node)

def insert_sorted(block_list, new_node):
    """
    Insert new_node into block_list maintaining sort order by depth.
    """
    # Simple insertion sort for demonstration
    for i, node in enumerate(block_list):
        if new_node.depth < node.depth:
            block_list.insert(i, new_node)
            return
    block_list.append(new_node)

def render_ray(ray, cache_capacity):
    """
    Render a single ray using the block-based ray cache.
    """
    buffered_block_list = []  # The cache structure
    voxel_values = []

    for voxel in ray.voxels:
        # Step 1: Search cache
        cached_data = search_cache(buffered_block_list, voxel)
        
        if cached_data is not None:
            # Hit: Retrieve immediately
            voxel_values.append(cached_data[voxel.relative_index])
        else:
            # Miss: Reconstruct block
            block_id = get_block_id(voxel)
            reconstructed_block = reconstruct_block(block_id)
            boundaries = get_block_boundaries(block_id)
            
            # Create new cache node
            new_node = BufferedBlockNode(block_id, boundaries, reconstructed_block)
            
            # Step 2: Buffer and manage cache
            if len(buffered_block_list) >= cache_capacity:
                replace_oldest(buffered_block_list, new_node)
            else:
                insert_sorted(buffered_block_list, new_node)
            
            # Retrieve from newly cached block
            voxel_values.append(reconstructed_block[voxel.relative_index])

    return accumulate(voxel_values)
```

## Subtopics

### Block-Wise Reconstruction Cache
A technique to reduce reconstruction overhead by caching reconstructed voxel blocks in memory. It leverages the observation that voxels reconstructed along one ray are likely used by adjacent rays, retaining these blocks to avoid re-reconstruction [S1, unofficial]. Using this cache technique reduces rendering time from a few days to a few minutes [S1, unofficial]. It saves approximately 50% of the reconstruction time compared to point-wise reconstruction [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Lookup is $O(B)$ where $B$ is the number of blocks in the cache, assuming linear search of the buffered-block list. Reconstruction is avoided for cached blocks, significantly reducing total rendering time.
*   **Memory Complexity:** The cache size grows at a rate of $2^2$ (quadratic) with respect to resolution $N$, while the original data grows at $2^3$ (cubic) [S1, unofficial]. This makes caching efficient for high-resolution data that exceeds physical memory.
*   **Measured Performance:** For $N=256$ and $s=16$, cache size is 0.5 MB; for $N=1024$ and $s=16$, cache size is 2 MB [S1, unofficial]. Rendering time can be reduced from days to minutes [S1, unofficial].
*   **Strengths:** Efficient for high-resolution data; reduces redundant computation; small memory footprint relative to original data.
*   **Limitations:** Performance degrades if cache size is too small; requires sorted list maintenance; not given in the sources whether parallel access to the cache is supported.
*   **When to use:** Scientific visualization applications with high-resolution volume data that exceeds physical memory.
*   **When not to use:** Low-resolution data where reconstruction overhead is negligible; scenarios where cache hit rates are expected to be very low due to poor spatial locality.

## Background
The method originates from research on direct rendering of multiresolution decomposed volume data [S1, unofficial]. It was proposed to address issues related to volume rendering of multiresolution data, introducing a novel abstract mathematical definition of the volume rendering equation [S1, unofficial]. The technique builds on the observation that block-wise reconstruction is more efficient than point-wise reconstruction [S1, unofficial].
