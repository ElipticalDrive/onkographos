# Brick Caching with LRU Replacement

Also called: Block Memory Management Unit (MMU) with LRU Eviction, Brick Pool Manager, Dynamic Brick Cache, Volume Block Cache

## Overview
Brick Caching with LRU Replacement manages a fixed-size pool of volume data blocks, mapping brick coordinates to pool indices and evicting least-recently-used blocks when the pool is full [S2, unofficial]. It solves the problem of limited GPU or host memory capacity by allowing rendering of volumes larger than physical memory, using a precomputed count buffer to skip empty bricks and avoid unnecessary memory transfers [S2, unofficial]. It sets itself apart from sibling methods by implementing a flat, CPU-managed (or explicitly managed) pool with a specific "clock" based LRU eviction strategy and tight integration with a 256-bin occupancy count buffer for transfer function culling, rather than relying on hierarchical residency trees or GPU-steered visibility queries [S2, S3, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Volume dimensions $D_x, D_y, D_z$, brick dimensions $B_x, B_y, B_z$, brick pool ratio $\rho$ (fraction of bricks to keep in memory), and optionally a 1D transfer function $tf1d$.
*   **Output:** A pointer to the voxel data of the requested brick $(x, y, z)$, or `nullptr` if the brick is empty, not resident, or out of bounds.

**Data Structures:**
The cache maintains the following state [S2, unofficial]:
1.  **Dimensions:**
    *   `dims`: Total volume dimensions $(D_x, D_y, D_z)$.
    *   `brick_dims`: Number of bricks in each dimension: $N_x = \lceil D_x / B_x \rceil$, $N_y = \lceil D_y / B_y \rceil$, $N_z = \lceil D_z / B_z \rceil$.
    *   `brick_size`: Brick voxel dimensions $(B_x, B_y, B_z)$.
2.  **Entries Array:**
    *   `entries`: Array of size $N_x \cdot N_y \cdot N_z$.
    *   Each `Entry` contains:
        *   `valid`: Boolean, true if the brick is currently in the pool.
        *   `blk_idx`: Integer index into the `blocks` array.
3.  **Blocks Array:**
    *   `blocks`: Array of size $blk\_nums$.
    *   $blk\_nums = \lceil N_x \cdot N_y \cdot N_z \cdot \rho \rceil$.
    *   Each `Block` represents a physical memory slot.
4.  **Data Buffer:**
    *   `data`: A contiguous `uchar*` buffer of size $blk\_nums \times (B_x+1)(B_y+1)(B_z+1)$.
    *   Each brick is stored with neighbor padding: logical size $B$ is stored as $(B+1)^3$ voxels to support trilinear interpolation without accessing adjacent bricks [S1][S2, unofficial].
5.  **Count Buffer:**
    *   `cnt_buf`: Array of size $N_x \cdot N_y \cdot N_z \cdot 256$.
    *   Stores the count of voxels with intensity value $v \in [0, 255]$ for each brick. Used for empty brick detection [S2, unofficial].
6.  **LRU State:**
    *   `blk_used`: Current number of valid bricks in the pool.
    *   `clock_pos`: Integer index pointing to the next candidate for eviction in a circular buffer or list [S2, unofficial].
7.  **I/O:**
    *   `fin`: File stream handle for loading bricks from disk [S2, unofficial].
    *   `mutex`: Synchronization primitive for thread-safe access [S2, unofficial].

**Algorithm Steps:**

1.  **Initialization:**
    *   Calculate `brick_dims` from `dims` and `brick_size`.
    *   Allocate `entries` array of size $N_x N_y N_z$. Initialize all `valid` to false.
    *   Calculate $blk\_nums = \lceil N_x N_y N_z \cdot \rho \rceil$.
    *   Allocate `blocks` array of size $blk\_nums$.
    *   Allocate `data` buffer of size $blk\_nums \times (B_x+1)(B_y+1)(B_z+1)$.
    *   Load `cnt_buf` from disk. Size is $N_x N_y N_z \cdot 256$ integers [S2, unofficial].
    *   Initialize `blk_used = 0`, `clock_pos = 0` [S2, unofficial].

2.  **Request Brick `getBlock(x, y, z)`:**
    *   **Bounds Check:** If $x \ge N_x$ or $y \ge N_y$ or $z \ge N_z$, return `nullptr` [S2, unofficial].
    *   **Empty Brick Check:**
        *   If a transfer function $tf1d$ is provided:
            *   Calculate base index in `cnt_buf`: $base = (x + y \cdot N_x + z \cdot N_x \cdot N_y) \cdot 256$.
            *   Iterate $v$ from 0 to 255:
                *   If `cnt_buf[base + v] != 0` AND `tf1d.sampleSimple(v).w != 0` (opacity > 0):
                    *   Brick is potentially visible. Break loop.
            *   If loop completes without break (i.e., all contributing counts are zero or opacity is zero), return `nullptr` [S2, unofficial].
    *   **Cache Lookup:**
        *   Calculate brick index $idx = x + y \cdot N_x + z \cdot N_x \cdot N_y$.
        *   If `entries[idx].valid` is true:
            *   Mark block as used (update LRU state, e.g., move to front of list or update timestamp) [S2, S3, unofficial].
            *   Return pointer to block data in `data` buffer at `entries[idx].blk_idx` [S2, unofficial].
    *   **Cache Miss / Eviction:**
        *   Lock `mutex` [S2, unofficial].
        *   If `blk_used < blk_nums`:
            *   Find first free slot in `blocks` (or maintain a free list). Let this be $slot$.
        *   Else:
            *   Perform LRU Eviction:
                *   Use `clock_pos` to identify the victim block. The sources describe a "clock" strategy where `clock_pos` scans for the first unused block [S2, unofficial]. In a standard LRU implementation, this would be the least recently accessed block.
                *   Let $victim\_idx$ be the index of the victim block in `blocks`.
                *   Let $victim\_brick\_idx$ be the brick index stored in `entries` corresponding to $victim\_idx$.
                *   Mark `entries[victim_brick_idx].valid = false` [S2, unofficial].
                *   Decrement `blk_used`.
                *   Update `clock_pos` to the next position [S2, unofficial].
            *   Assign $slot = victim\_idx$ [S2, unofficial].
        *   **Load Brick:**
            *   Read brick data from `fin` at coordinates $(x, y, z)$.
            *   Store data into `data` buffer at offset $slot \times (B_x+1)(B_y+1)(B_z+1)$.
        *   **Update Entry:**
            *   Set `entries[idx].valid = true`.
            *   Set `entries[idx].blk_idx = slot`.
            *   Increment `blk_used`.
            *   Mark block as used (update LRU state) [S2, unofficial].
        *   Unlock `mutex` [S2, unofficial].
        *   Return pointer to the newly loaded block data [S2, unofficial].

**Parameters:**
*   `brick_num_ratio` ($\rho$): Fraction of total bricks to keep in memory. Typical value: 0.5 (50%) [S2, unofficial].
*   `brick_size`: Dimensions of each brick in voxels. Common sizes are $32^3$ or similar powers of 2 [S1][S2, unofficial].
*   GPU Resolution Limit: Historically, GPU volume rendering was limited by texture size (e.g., $512^3$ on NVIDIA GeForce 6) and video memory (e.g., 256MB) [S1].

**Edge Cases and Pitfalls:**
*   **Precision:** The count buffer uses 256 bins (uint8 counts). If voxel intensities exceed 255 or are floating point, they must be quantized or scaled before counting [S2, unofficial].
*   **Boundaries:** Accessing bricks outside $[0, N_x-1] \times [0, N_y-1] \times [0, N_z-1]$ must return `nullptr` to prevent out-of-bounds memory access [S2, unofficial].
*   **Concurrency:** The cache requires mutex protection for `blk_used`, `clock_pos`, and `entries` updates during eviction and loading [S2, unofficial].

## Subtopics

### [Block-based Ray Cache](2260-block-based-ray-cache.md)
Retains reconstructed voxel blocks for reuse by adjacent rays, maintaining a sorted list along the ray depth. Chosen when redundant computation is the primary bottleneck, rather than memory transfer.

### [LRU Cache Eviction with Residency Update](3115-lru-cache-eviction-with-residency-update.md)
Couples LRU eviction with hierarchical octree mask updates. Chosen when rendering artifacts from non-resident data in a multi-resolution hierarchy must be prevented.

### [Brick Cache Implementation](3222-brick-cache-implementation.md)
GPU-resident texture cache managed via WebGPU compute passes. Chosen for fully GPU-driven pipelines avoiding CPU-GPU synchronization overhead.

### [GPU-Steered LRU Cache Management](3654-gpu-steered-lru-cache-management.md)
GPU reports usage to steer CPU loading. Chosen to eliminate CPU-side visibility queries and tree traversal overhead.

### [LRU Cache Management for Voxel Bricks](4571-lru-cache-management-for-voxel-bricks.md)
Explicit CPU-side coordination for LRU lifecycle. Chosen when shader models lack random memory write capabilities for cache management.

### Brick Cache Updates
Manages the synchronization between a file server, GPU cache, and residency octree. It uploads a user-defined number of bricks per frame, translating global IDs to local IDs. If a brick is EMPTY, the corresponding page in the multi-channel page-table hierarchy is marked EMPTY. If MAPPED, data is added to the cache and the page is marked MAPPED. Removal marks the page UNMAPPED. Two lists of local brick IDs (EMPTY/MAPPED and UNMAPPED) are passed to the residency octree for processing [S3, unofficial].

## Operating characteristics
*   **Time Complexity:**
    *   Cache Hit: $O(1)$ average [S2, unofficial].
    *   Eviction Search: $O(1)$ amortized using the clock pointer [S2, unofficial].
    *   Empty Brick Check: $O(256)$ worst-case if iterating the count buffer [S2, unofficial].
*   **Memory Complexity:** $O(blk\_nums \times brick\_volume + brick\_count \times 256 \times sizeof(int))$. The count buffer dominates metadata size if brick count is large [S2, unofficial].
*   **Performance:** Decouples volume size from GPU memory limits (e.g., rendering $512^3$ volumes on 256MB VRAM) [S1].
*   **Strengths:** Simple implementation, effective empty space skipping via count buffer, predictable memory usage via fixed pool size.
*   **Limitations:** CPU-side mutex contention can become a bottleneck. The flat LRU clock may not capture spatial locality as well as hierarchical methods. The 256-bin count buffer may lose precision for high-bit-depth data.
*   **When to Use:** When volume data exceeds available memory and a simple, robust caching mechanism is needed without complex hierarchical structures.
*   **When Not to Use:** When high spatial locality is critical and can be exploited by hierarchical caches, or when GPU-steered loading is required to hide latency.

## Background
The method originates from real-time ray-casting techniques for discrete isosurfaces, specifically addressing the limitations of GPU texture resolution and memory [S1]. It builds on the concept of adaptive texture maps and brick-based storage to allow dynamic management of volume data [S1]. The specific implementation details, including the count buffer and clock-based eviction, are documented in open-source volume rendering projects [S2, unofficial]. Variants involving multi-channel page-table hierarchies and residency octrees are discussed in research on scalable web-based volume rendering [S3, unofficial].
