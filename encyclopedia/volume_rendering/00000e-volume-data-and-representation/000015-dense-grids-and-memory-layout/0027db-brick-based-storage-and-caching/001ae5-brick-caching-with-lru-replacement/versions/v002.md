# Brick Caching with LRU Replacement

Also called: Block Memory Management Unit (MMU) with LRU Eviction, Brick Pool Manager, Dynamic Brick Cache, Volume Block Cache

## Overview
Brick Caching with LRU Replacement manages a fixed-size pool of volume data blocks, mapping brick coordinates to pool indices and evicting least-recently-used blocks when the pool is full [S2, unofficial]. It solves the problem of limited GPU memory capacity and transfer bandwidth by ensuring that expensive data transfers from slower host memory are minimized [S1]. It differs from [Brick-based Volume Raycasting](3341-brick-based-volume-raycasting.md) by decoupling the volume size from GPU resolution restrictions through a re-arranged brick structure and a resident cache texture [S1].

## How it works
**Inputs and Outputs:**
- **Input:** Volume dimensions, brick size, brick pool ratio, file handle to volume data, optional transfer function for active brick determination [S2, unofficial].
- **Output:** A block pointer or `nullptr` if the brick is empty or not resident [S2, unofficial].

**Data Structures:**
The cache is managed by a Block Memory Management Unit (MMU) containing the following fields [S2, unofficial]:
1.  `dims`: `Vector3i`, total volume dimensions.
2.  `brick_dims`: `Vector3i`, number of bricks in each dimension, calculated as $\lceil \text{dims} / \text{brick\_size} \rceil$ [S2, unofficial].
3.  `brick_size`: `Vector3i`, dimensions of each brick in voxels [S2, unofficial].
4.  `entries`: Array of `Entry` structures, size `brick_dims.x * brick_dims.y * brick_dims.z` [S2, unofficial].
    -   `Entry` layout: `{ bool valid; int blk_idx; }` [S2, unofficial].
    -   `valid`: Indicates if the entry maps to a resident block [S2, unofficial].
    -   `blk_idx`: Index into the `blocks` array [S2, unofficial].
5.  `blocks`: Array of `Block` structures, size `blk_nums` [S2, unofficial].
    -   `blk_nums`: Total number of blocks in the pool, calculated as `brick_dims.x * brick_dims.y * brick_dims.z * _brick_num_ratio` [S2, unofficial].
6.  `data`: `uchar*`, contiguous memory pool of size `blk_nums * (brick_size.x+1) * (brick_size.y+1) * (brick_size.z+1)` [S2, unofficial]. Bricks are stored with size $(n+1)^3$ to include neighbor samples for filtering [S1].
7.  `cnt_buf`: `int*`, count buffer of size `brick_dims.x * brick_dims.y * brick_dims.z * 256` used to skip empty bricks [S2, unofficial].
8.  `clock_pos`: `int`, position in the LRU clock for eviction [S2, unofficial].
9.  `blk_used`: `int`, number of currently used blocks in the pool [S2, unofficial].
10. `mutex`: `pthread_mutex_t`, for thread-safe access [S2, unofficial].
11. `fin`: `ifstream`, file handle for loading bricks [S2, unofficial].

**Parameters:**
-   `_brick_num_ratio`: Fraction of total bricks to keep in memory (e.g., 0.5 for 50%) [S2, unofficial].
-   `brick_size`: Dimensions of each brick in voxels [S2, unofficial]. Small blocks fit the isosurface tightly for empty space skipping, while larger bricks avoid excessive storage overhead [S1].
-   GPU Resolution Limit: Example 512³ on NVIDIA GeForce 6 [S1].
-   Memory Limit: Example 256MB [S1].

**Algorithm Steps:**
1.  **Initialization:** Calculate `brick_dims` from volume `dims` and `brick_size` [S2, unofficial]. Allocate `entries` array of size `brick_dims.x * brick_dims.y * brick_dims.z` [S2, unofficial]. Calculate `blk_nums` using `_brick_num_ratio` [S2, unofficial]. Allocate `blocks` array of size `blk_nums` [S2, unofficial]. Allocate `data` buffer of size `blk_nums * (brick_size.x+1) * (brick_size.y+1) * (brick_size.z+1)` [S2, unofficial]. Load `cnt_buf` of size `brick_dims.x * brick_dims.y * brick_dims.z * 256` from disk [S2, unofficial]. Initialize `clock_pos = 0`, `blk_used = 0`, and all `entries` as invalid [S2, unofficial].
2.  **Get Block (x, y, z):** If brick coordinates exceed `brick_dims`, return `nullptr` [S2, unofficial]. If a transfer function `tf1d` is provided, check `cnt_buf` for the brick: iterate `idx` from 0 to 255, if `cnt_buf[cnt_base + idx] != 0` and `tf1d->sampleSimple(idx).w != 0`, break [S2, unofficial]. If `idx == 256`, return `nullptr` (empty brick) [S2, unofficial]. Check `entries` array for existing mapping [S2, unofficial]. If valid, mark block as used and return it [S2, unofficial]. If not, lock `mutex` [S2, unofficial]. If `blk_used < blk_nums`, assign next free slot [S2, unofficial]. Else, use `clock_pos` to find first unused block (LRU-like eviction), mark old entry invalid, and reuse slot [S2, unofficial]. Load block from file [S2, unofficial]. Mark entry valid, store `blk_idx`, and unlock `mutex` [S2, unofficial].

**Edge Cases and Pitfalls:**
-   **Precision:** Brick coordinates must be correctly mapped to entry indices to avoid out-of-bounds access [S2, unofficial].
-   **Boundaries:** Bricks at the volume boundary may have incomplete neighbor samples if the volume size is not a multiple of brick size [S1].
-   **Concurrency:** The mutex ensures thread safety but may become a bottleneck [S2, unofficial].
-   **Empty Bricks:** The `cnt_buf` check is critical for performance [S2, unofficial].

## Subtopics

### [Block-based Ray Cache](2260-block-based-ray-cache.md)
The Block-based Ray Cache is a memory optimization technique for volume rendering that reduces reconstruction overhead by retaining reconstructed voxel blocks in memory for reuse by adjacent rays. It solves the problem of redundant computation in high-resolution volume rendering where data exceeds physical memory, allowing rendering times to drop from days to minutes. It sets itself apart from sibling methods by explicitly maintaining a sorted list of blocks along the ray depth to facilitate immediate lookup, rather than relying solely on generic LRU eviction without spatial locality awareness.

### [LRU Cache Eviction with Residency Update](3115-lru-cache-eviction-with-residency-update.md)
This method manages the consistency between a Least Recently Used (LRU) brick cache and a hierarchical residency octree. When the cache is full, it evicts the least recently accessed brick and propagates the resulting change in spatial coverage up the octree by resetting bits in leaf and non-leaf node masks. It ensures that the residency structure accurately reflects which resolution levels are partially mapped in memory, preventing rendering artifacts from accessing non-resident data. It differs from standard LRU caches by coupling eviction side-effects with hierarchical metadata updates.

### [Brick Cache Implementation](3222-brick-cache-implementation.md)
The Brick Cache is a single-channel 3D texture cache that stores bricks from a multi-resolution multi-volume hierarchy. It is agnostic to the number of data channels. It differs from general-purpose CPU caches by being implemented as a GPU-resident texture managed via LRU replacement using WebGPU compute passes.

### [GPU-Steered LRU Cache Management](3654-gpu-steered-lru-cache-management.md)
This method enables the GPU to steer CPU-side data loading for voxel rendering by reporting node usage, thereby eliminating the overhead of CPU-driven visibility queries and tree traversal. It differs from sibling methods by unifying the management of the brick pool and node pool into two LRU-controlled caches where the GPU determines refinement needs and missing data, rather than relying on occlusion queries or frustum containment checks performed on the CPU.

### [LRU Cache Management for Voxel Bricks](4571-lru-cache-management-for-voxel-bricks.md)
LRU Cache Management for Voxel Bricks is a memory management strategy that prioritizes reusing voxel brick data that has not been accessed for the longest time, thereby optimizing memory reuse while retaining useful data in the cache. It solves the problem of limited GPU memory capacity and transfer bandwidth by ensuring that expensive data transfers from slower host memory are minimized. Unlike sibling methods that may rely on hardware-specific features or different replacement policies, this approach explicitly manages the cache lifecycle using a Last Recently Used (LRU) policy, often requiring CPU-side coordination due to the limitations of standard shader models regarding random memory writes.

### Brick Cache Updates
A user-defined number of brick data is uploaded from the file server to the GPU each frame [S3, unofficial]. Each brick comprises its global brick ID and either the EMPTY value (if all zeros) or the pre-processed brick [S3, unofficial]. The global brick ID is translated to a local brick ID [S3, unofficial]. If the brick's channel is not represented by the multi-channel page-table hierarchy, the brick is discarded [S3, unofficial]. If EMPTY, the corresponding page is marked EMPTY; otherwise, it is marked MAPPED and added to the brick cache using the LRU buffer to find free or unused entries [S3, unofficial]. When a brick is removed, its page is marked UNMAPPED [S3, unofficial]. Two lists of local brick IDs (EMPTY/MAPPED and UNMAPPED) are passed to the residency octree [S3, unofficial].

## Operating characteristics
-   **Time Complexity:** O(1) average for cache hit, O(1) for eviction search (amortized), O(256) worst-case for empty brick check [S2, unofficial].
-   **Memory Complexity:** O(blk_nums × brick_volume + brick_count × 256 × sizeof(int)) [S2, unofficial].
-   **Performance:** The method allows rendering of volumes larger than GPU memory (e.g., 512³ on 256MB VRAM) by streaming bricks [S1].
-   **Strengths:** Efficient memory usage for large volumes; effective empty space skipping via `cnt_buf`; decouples volume size from GPU constraints [S1][S2, unofficial].
-   **Limitations:** Overhead of $(n+1)^3$ storage for bricks; mutex contention may limit parallelism [S1][S2, unofficial].
-   **When to use:** When rendering large volumes that exceed GPU memory, especially with dynamic isovalue changes requiring active brick determination [S1].
-   **When not to use:** For small volumes that fit entirely in GPU memory, where a simple resident texture is more efficient [S1].

## Background
The concept of brick-based caching with LRU replacement originated in the context of real-time ray-casting of discrete isosurfaces, where decoupling volume size from GPU resolution restrictions was necessary [S1]. The specific implementation details, including the MMU structure and `cnt_buf` optimization, are documented in open-source projects and academic works on parallel volume rendering [S2, unofficial]. The integration with residency octrees and GPU-steered management further evolved the technique to handle multi-resolution hierarchies and web-based rendering scenarios [S4][S5, S6, unofficial].
