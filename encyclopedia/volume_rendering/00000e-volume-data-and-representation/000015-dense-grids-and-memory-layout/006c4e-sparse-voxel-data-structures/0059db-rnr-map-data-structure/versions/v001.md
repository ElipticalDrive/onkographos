# RNR-Map Data Structure

Also called: Global Map, Local Map

## Overview
The RNR-Map is a dense 3D tensor used to store averaged latent feature vectors for visual navigation and rendering, mapping 2D spatial positions to high-dimensional latent codes [S1]. It differs from traditional sparse voxel structures by aggregating pixel features into a fixed-resolution grid to enable efficient decoder-based image reconstruction, whereas siblings like VDB use sparse octrees for explicit geometry and MERF uses hash grids for neural field approximation [21071-sparse-voxel-data-structures.md].

## How it works
**Inputs:**
- A set of registered 2D pixel features (e.g., from camera observations).
- Map resolution parameters: grid dimensions $U \times V$ and latent dimension $D$ [S1].

**Outputs:**
- An RNR-Map tensor $m \in \mathbb{R}^{U \times V \times D}$ containing the aggregated latent features [S1].

**Data Structures:**
- **RNR-Map ($m$):** A 3D tensor of size $U \times V \times D$. Each cell $(u, v)$ stores a latent feature vector $c_{u,v} \in \mathbb{R}^D$ [S1].
- **Map Struct (Variant):** In specific optimization contexts (e.g., boat rendering), the map is implemented as an array of structs. Each struct contains:
    - 4 bytes: Tile pointer.
    - 4 bytes: Additional data (e.g., a 32-bit 'boat bit' flag) [S2, unofficial].

**Steps:**
1. **Normalization:** For each input pixel, normalize its position using the map resolution $s$ to determine the grid coordinates $(u, v)$ [S1].
2. **Aggregation:** Collect all pixel features that map to the same grid position $(u, v)$ [S1].
3. **Averaging:** Compute the average of the aggregated features for each grid cell to produce the final latent vector $c_{u,v}$ [S1].
4. **Storage:** Store $c_{u,v}$ in the tensor $m$ at index $(u, v)$ [S1].

**Formulas:**
The map position $(u, v)$ is derived from the normalized position (details of normalization function not explicitly defined in sources, assumed standard linear mapping) [S1]. The latent vector for a cell is:
$$ c_{u,v} = \frac{1}{N_{u,v}} \sum_{i \in \text{pixels mapping to } (u,v)} f_i $$
where $f_i$ is the feature vector of pixel $i$, and $N_{u,v}$ is the count of pixels mapping to $(u, v)$ [S1].

**Parameters:**
- $U, V$: Grid dimensions (height and width in grid cells) [S1].
- $D$: Latent dimension (channel size) [S1].
- Map Size (Variant): Can be doubled (e.g., 64 KB to 128 KB) to accommodate auxiliary flags in struct layouts [S2, unofficial].

**Edge Cases and Pitfalls:**
- **Cache Performance:** Doubling map size to store auxiliary data (like the 'boat bit') may reduce cache hit rates for pointer traversal. However, in arbitrary traversal patterns, cache hits are already slim, making the impact negligible [S2, unofficial].
- **Memory Access:** Avoiding repeated memory access for static per-frame data (e.g., boat position) by embedding flags in the map structure reduces rendering loop overhead [S2, unofficial].

**Pseudocode:**
```python
def build_rnr_map(pixels, U, V, D):
    """
    Build an RNR-Map from registered pixel features.
    
    Args:
        pixels: List of tuples (u_norm, v_norm, feature_vector)
        U: Grid height
        V: Grid width
        D: Latent dimension
        
    Returns:
        m: Tensor of shape (U, V, D)
    """
    # Initialize map with zeros
    m = zeros((U, V, D))
    # Initialize count map to track number of pixels per cell
    counts = zeros((U, V))
    
    for u_norm, v_norm, f in pixels:
        # Normalize and map to grid indices
        # Note: Exact normalization formula from source is implicit; 
        # assuming standard integer conversion from normalized coordinates
        u = int(u_norm * U)
        v = int(v_norm * V)
        
        # Clamp to bounds to handle edge cases
        u = max(0, min(u, U - 1))
        v = max(0, min(v, V - 1))
        
        # Aggregate features
        m[u, v] += f
        counts[u, v] += 1
        
    # Average aggregated features
    for u in range(U):
        for v in range(V):
            if counts[u, v] > 0:
                m[u, v] /= counts[u, v]
                
    return m

def update_boat_flags(map_structs, boat_tiles):
    """
    Update the 'boat bit' in the map structs for the current frame.
    
    Args:
        map_structs: Array of 8-byte structs (4-byte pointer, 4-byte data)
        boat_tiles: List of tile indices occupied by the boat
    """
    for tile_idx in boat_tiles:
        # Set the boat bit in the additional data field
        # Assuming bit 0 is the boat bit
        map_structs[tile_idx].data |= 1
```

## Subtopics

### Map Struct Expansion for Boat Optimization
A variant where the map stores 8-byte structs (4-byte tile pointer + 4-byte auxiliary data) instead of 4-byte pointers. The auxiliary data includes a 32-bit 'boat bit' marking tiles the boat occupies. This avoids repeated memory access for boat position data during rendering. The map size is doubled (e.g., 64 KB to 128 KB) to accommodate the larger structs. Cache impact is negligible due to arbitrary traversal patterns [S2, unofficial].

## Operating characteristics
- **Time Complexity:** Building the map is linear in the number of pixels $O(N)$, where $N$ is the number of input pixels, due to aggregation and averaging [S1].
- **Memory Complexity:** $O(U \times V \times D)$ for the standard RNR-Map [S1]. For the struct variant, memory usage is doubled compared to a pointer-only map [S2, unofficial].
- **Performance:** The struct variant reduces rendering loop overhead by embedding static per-frame data (boat position) directly in the map structure, avoiding repeated memory accesses [S2, unofficial].
- **Strengths:** Efficient aggregation of visual information into a fixed grid; reduced memory access penalties in specific rendering loops [S1][S2, unofficial].
- **Limitations:** Fixed resolution limits detail; doubling map size for auxiliary data increases memory usage [S1][S2, unofficial].

## Background
The RNR-Map was introduced in the paper "Renderable Neural Radiance Map for Visual Navigation" [S1]. It is used for visual navigation tasks, reconstructing RGBD images from latent codes using a decoder similar to the Generative Scene Network (GSN) [S1]. The struct expansion variant is described in a developer log about building a 3D engine for the Playdate platform [S2, unofficial].
