# Sparse Voxel Data Structures

Also called: Sparse grids, sparse voxel clouds, sparse volumetric representations

## Overview
Sparse Voxel Data Structures store volumetric data by explicitly recording only the coordinates and values of non-empty (or active) voxels, discarding the vast majority of empty space that dense grids must allocate [S1, unofficial]. This approach solves the memory explosion problem inherent in high-resolution volumetric rendering, allowing for the representation of large-scale or highly detailed scenes that would otherwise exceed available RAM or VRAM. Unlike [Dense grids and memory layout](3-dense-grids-and-memory-layout.md), which allocate a fixed contiguous block for the entire domain, sparse structures dynamically allocate resources proportional to the actual content density, enabling efficient storage of unbounded or highly heterogeneous volumes.

## Shared principles
The family of sparse voxel structures shares the following mechanisms:

1.  **Explicit Sparsity:** The data structure does not assume a full lattice. Instead, it maintains a list or tree of active elements (voxels, tiles, or nodes). Empty regions are represented by the absence of data rather than zero-valued entries [S1, unofficial].
2.  **Coordinate-Based Addressing:** Access to data relies on spatial coordinates $(x, y, z)$ rather than simple linear array indices. This requires a spatial indexing mechanism (e.g., hash maps, trees, or sorted lists) to map 3D coordinates to stored values efficiently [S1, unofficial].
3.  **Hierarchical or Flat Organization:** Data is typically organized either as a flat list of active voxels (suitable for simple point clouds or COO formats) or hierarchically (e.g., octrees, grids of tiles) to support efficient traversal, culling, and multi-resolution rendering [S1, unofficial].
4.  **Dynamic Memory Allocation:** Memory usage scales with the number of active voxels $N$ rather than the domain volume $M^3$. This allows for adaptive resolution, where detail is concentrated in regions of interest [S1, unofficial].

## Subtopics

### [VDB Data Loading & 3D Texture Setup](4880-vdb-data-loading-3d-texture-setup.md)
This method bridges CPU-side sparse VDB formats with GPU-side dense 3D textures. It parses a VDB binary file to extract sparse tile coordinates and data, then reconstructs a dense volume in CPU memory before uploading it to the GPU. Unlike [Brick-based storage and caching](4138-brick-based-storage-and-caching.md), which streams hierarchical tiles, this method loads the entire sparse dataset into a single dense texture, making it suitable only when the total voxel count fits within GPU memory limits.

### [MERF Scene Representation](10192-merf-scene-representation.md)
MERF is a hybrid radiance field representation for real-time rendering of large-scale unbounded scenes. It combines a sparse low-resolution 3D voxel grid with three high-resolution 2D feature planes (XY, YZ, ZX). Unlike standard sparse grids that store raw density/color, MERF stores feature vectors that are summed and nonlinearly mapped. It uses piecewise-projective contraction to handle unbounded space, offering a lower memory footprint than dense grids while maintaining high-frequency detail via the 2D planes.

### [RNR-Map Data Structure](16569-rnr-map-data-structure.md)
The RNR-Map is a dense 3D tensor used for visual navigation, mapping 2D spatial positions to high-dimensional latent feature vectors. Unlike traditional sparse voxel structures like VDB that use octrees for explicit geometry, the RNR-Map aggregates pixel features into a fixed-resolution grid. It differs from MERF's hash grids by using a dense tensor for efficient decoder-based image reconstruction, trading sparsity for computational simplicity in latent space aggregation.

### [Dynamic Topology Evolution](23506-dynamic-topology-evolution.md)
This method provides bulk-synchronous operators for evolving the topology of NanoVDB index-grids on the GPU. It supports morphological dilation, pruning, merging, coarsening, and refinement. Unlike [OpenVDB](21071-sparse-voxel-data-structures.md), which relies on pointer-heavy nodes, this method uses a linearized memory layout with relative addressing and bit-parallel algorithms. It targets the reconstruction of trees with hundreds of millions of voxels in milliseconds, solving the static constraint of prior sparse grid versions.

### Sparse-Dense Interop (COO Arrays)
**Definition:** Allows sparse voxel functions to accept `scipy.sparse.coo_array` objects directly, treating them as equivalent to $(N, 3)$ index arrays. Operations return compatible sparse formats [S1, unofficial].
**Step:** 1. Accept COO array as input. 2. Extract coordinates (row, col, 0) as voxels. 3. Extract data as values. 4. Process using standard sparse voxel logic. 5. Return result as COO array if the operation returns a voxel set [S1, unofficial].
**Usage:** Used in `sc.mesh`, `sc.measure.volume`, `sc.binary.dilate`, `sc.teasar_skeletonize` [S1, unofficial].

## Background
Sparse voxel representations originated from the need to render complex 3D scenes efficiently, moving away from the memory inefficiencies of dense voxel grids. The Volume Data Base (VDB) format, developed by DreamWorks Animation, popularized the use of sparse octrees for large-scale VFX and simulation data [S1, unofficial]. More recently, sparse representations have been adapted for neural radiance fields (NeRFs) and real-time rendering, such as in MERF and NanoVDB, to handle unbounded spaces and dynamic topologies with high performance on modern GPUs [S1, unofficial]. The integration with scientific Python libraries like `scipy.sparse` further extends their utility to general scientific computing and mesh processing [S1, unofficial].
