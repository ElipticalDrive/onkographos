# Global Uniform Data Layout

Also called: App State Buffer, GlobalUniformData

## Overview
Global Uniform Data Layout is a GPU buffer structure used to transmit global rendering state, camera parameters, and lighting configurations from the CPU to volume rendering shaders [S1, unofficial]. It solves the problem of efficiently passing large, frequently updated uniform data (such as view/projection matrices and light positions) to the GPU without per-frame allocation overhead [S1, unofficial]. It is distinguished from sibling methods like [3D Texture Storage and Sampling](3064-3d-texture-storage-and-sampling.md) (which handle volumetric data) and [3D Transfer Function Texture Layout](5646-3d-transfer-function-texture-layout.md) (which handle opacity/color mapping) by containing only scalar, vector, and matrix control data rather than spatial field samples [S1, unofficial].

## How it works
The method defines a specific memory layout for a uniform buffer object (UBO) or constant buffer. The layout is typically defined in a shading language (e.g., Metal, HLSL) and mirrored in CPU-side code to ensure correct alignment and packing.

### Inputs and Outputs
*   **Input:** CPU-side application state (camera pose, light positions, rendering flags).
*   **Output:** A GPU-accessible buffer bound to a specific descriptor set or binding point, readable by vertex, fragment, or compute shaders.

### Data Structures
The primary structure is `GlobalUniformData`. It inherits from a `Settings` struct and includes lighting and camera data [S1, unofficial].

**1. `Settings` (Base)**
Contains boolean flags for rendering features.
*   `indirectSpecularLight`: bool
*   `indirectDiffuseLight`: bool
*   `directLight`: bool
*   `shadows`: bool
*   [G] Other settings implied by the parent context (e.g., mipmap generation method) are not explicitly listed in the base struct but may be handled separately.

**2. `PointLight`**
*   `position`: `packed_float3` (3 floats, 12 bytes)
*   `color`: `packed_float3` (3 floats, 12 bytes)
*   [G] Intensity is often a separate scalar or embedded in color; the source defines `POINT_LIGHT_INTENSITY` as a macro, suggesting intensity might be a global constant or part of the color field.

**3. `GlobalUniformData` Layout**
The layout follows the `Settings` struct. The exact field order and sizes are critical for GPU alignment (typically 16-byte or 256-bit boundaries).

| Field | Type | Size | Offset | Notes |
| :--- | :--- | :--- | :--- | :--- |
| `settings` | `Settings` | Varies | 0 | Base struct. Contains 4 bools. |
| `pointLights` | `PointLight[MAX_LIGHTS]` | $16 \times N$ | After Settings | Array of lights. |
| `numberOfLights` | `int` | 4 bytes | After Lights | Count of active lights. |
| `V` | `glm::mat4` | 64 bytes | After Count | View matrix. |
| `P` | `glm::mat4` | 64 bytes | After V | Projection matrix. |
| `cameraPosition` | `vec3` | 12 bytes | After P | Camera world position. |
| `voxelTextureSize` | `uint32_t` | 4 bytes | After CamPos | Dimensions of the voxel grid. |
| `state` | `int32_t` | 4 bytes | After TexSize | General state flag. |
| `padding` | `uint32_t[3]` | 12 bytes | After State | Alignment padding. |

*Note: The exact offset of `pointLights` depends on the size of `Settings`. In Metal, `packed_float3` is 16 bytes (3 floats + 1 padding). `bool` is typically 4 bytes. If `Settings` has 4 bools, it is 16 bytes. Thus `pointLights` starts at offset 16.*

### Parameters
*   `MAX_LIGHTS`: Maximum number of point lights supported. Default: 1 [S1, unofficial].
*   `POINT_LIGHT_INTENSITY`: Macro defining light intensity. Default: 1 [S1, unofficial].

### Pseudocode
The following Python-like pseudocode demonstrates how to construct the buffer data on the CPU side, respecting the layout defined in [S1, unofficial].

```python
import struct
import numpy as np

def pack_global_uniform_data(camera, lights, settings, voxel_size):
    """
    Packs global uniform data into a byte buffer for GPU upload.
    Assumes Metal-style packing (16-byte alignment for vectors/matrices).
    """
    # 1. Pack Settings (4 bools -> 4 ints/bytes, padded to 16 bytes)
    # bools are typically stored as 4-byte integers in GLSL/Metal uniform buffers
    settings_bytes = struct.pack('<4I', 
        int(settings.indirect_specular),
        int(settings.indirect_diffuse),
        int(settings.direct_light),
        int(settings.shadows)
    )
    # Pad settings to 16 bytes if necessary (4 bytes is already aligned to 4, but next field might need 16)
    # In Metal, structs are aligned to their largest member. 
    # Assuming Settings is small, we pad to 16 bytes to align the next array or matrix.
    settings_bytes = settings_bytes.ljust(16, b'\x00')
    
    buffer = bytearray()
    buffer.extend(settings_bytes)
    
    # 2. Pack Point Lights
    # MAX_LIGHTS is typically 1 in the source example
    max_lights = 1
    for i in range(max_lights):
        if i < len(lights):
            light = lights[i]
            # packed_float3: 3 floats, padded to 16 bytes
            light_pos = struct.pack('<3f', *light.position) + b'\x00'
            light_col = struct.pack('<3f', *light.color) + b'\x00'
            buffer.extend(light_pos)
            buffer.extend(light_col)
        else:
            # Empty light
            buffer.extend(b'\x00' * 24) # 2 * 12 bytes
            
    # 3. Number of Lights
    buffer.extend(struct.pack('<i', min(len(lights), max_lights)))
    
    # 4. View Matrix (4x4 float, column-major usually in GLM/Metal)
    # glm::mat4 is 16 floats = 64 bytes
    view_mat = camera.view_matrix # Assume 4x4 numpy array or list of 16 floats
    buffer.extend(struct.pack('<16f', *view_mat.flatten()))
    
    # 5. Projection Matrix
    proj_mat = camera.proj_matrix
    buffer.extend(struct.pack('<16f', *proj_mat.flatten()))
    
    # 6. Camera Position (vec3)
    cam_pos = camera.position
    buffer.extend(struct.pack('<3f', *cam_pos))
    buffer.extend(b'\x00') # Pad vec3 to 16 bytes? 
    # Note: The source lists cameraPosition as vec3 followed by uint32_t.
    # vec3 is 12 bytes. uint32_t is 4 bytes. Total 16 bytes. No extra padding needed here.
    
    # 7. Voxel Texture Size (uint32_t)
    buffer.extend(struct.pack('<I', voxel_size))
    
    # 8. State (int32_t)
    buffer.extend(struct.pack('<i', camera.state))
    
    # 9. Padding (uint32_t[3])
    buffer.extend(struct.pack('<3I', 0, 0, 0))
    
    return bytes(buffer)
```

### Edge Cases and Pitfalls
*   **Alignment:** GPU drivers require strict alignment. `vec3` must be padded to 16 bytes if followed by a 16-byte aligned type, or the next field must be 4-byte aligned. The source specifies `padding[3]` at the end, suggesting the total size is a multiple of 16 bytes [S1, unofficial].
*   **Matrix Layout:** Ensure matrices are stored in the correct order (column-major for OpenGL/Metal, row-major for DirectX/HLSL). The source uses `glm::mat4`, which is column-major [S1, unofficial].
*   **Light Count:** If `numberOfLights` is less than `MAX_LIGHTS`, unused light entries should be zeroed out to prevent undefined behavior [S1, unofficial].

## Subtopics

### [Camera Uniform Layout](3619-camera-uniform-layout.md)
Camera Uniform Layout defines the memory layout and update protocol for the `CameraUniform` GPU buffer structure, which transmits camera pose, temporal state, and lighting parameters from the CPU to the volume rendering and shading shaders. It solves the problem of maintaining consistent reprojection history for temporal anti-aliasing (TAA) and lighting caches across frame boundaries, ensuring that cached shadow and ambient occlusion values can be correctly mapped from the previous frame to the current frame even when the camera moves or the world origin shifts. It is distinguished from generic camera matrices by its inclusion of explicit previous-frame basis vectors, world-voxel origin offsets, and specific flags controlling the validity of reprojection caches.

### Instance Data Layout
Instance Data Layout is a tightly packed data structure used to pass instance data (position, texture, tint, shape ID, orientation) to the GPU for instanced rendering of voxel shapes [S2, unofficial]. It is distinguished from global uniforms by being an array of instance-specific data rather than a single global state block.

**Layout (`ShapeInstance`)**
*   Total Size: 32 bytes.
*   `position`: `Vector3` (float[3], 12 bytes, offset 0).
*   `texture`: `int` (4 bytes, offset 12).
*   `shape`: `ushort` (2 bytes, offset 16).
*   `rotation`: `ushort` (2 bytes, offset 18).
*   `tint`: `Vector3` (float[3], 12 bytes, offset 20).
*   [G] The `shape` and `rotation` fields are combined in shader code into a single `uint` `shapeRotation`.

**Parameters**
*   `rotation encoding`: Calculated as `(int)up * 4 + forward`. `up` is a `Direction` enum, `forward` is an integer range 0-3 representing clockwise rotation perpendicular to up [S2, unofficial].

**Pitfalls**
*   The `shape` field is truncated to `ushort` (2 bytes) despite the constructor accepting an `int`. This limits the number of unique shapes to 65535 [S2, unofficial].

### WebGPU Uniform Buffer Packing
WebGPU Uniform Buffer Packing defines a specific linear memory layout for a `Float32Array` of size 64 (256 bytes) used to pass volumetric cloud rendering parameters [S3, unofficial]. It is distinguished by its explicit index-based mapping for a flat array rather than a struct-based layout.

**Layout (Indices in Float32Array)**
*   0: `width`
*   1: `height`
*   2: `time`
*   3: `coverage`
*   4: `cloudBottom`
*   5: `cloudTop`
*   6: `densityMultiplier`
*   7: `maxSteps` (via `Uint32View`)
*   8: `lightSteps` (via `Uint32View`)
*   9: `stepSize`
*   10-11: `padding`
*   12-14: `sunDirection`
*   15: `padding`
*   16-18: `camPos`
*   19: `padding`
*   20-35: `invProj` matrix (16 floats)
*   36-51: `invView` matrix (16 floats)

## Operating characteristics
*   **Time Complexity:** $O(1)$ to pack the data on the CPU, as the size is fixed and small (typically < 256 bytes) [S1, unofficial].
*   **Memory Complexity:** $O(1)$ fixed size. The buffer size is determined by the maximum number of lights and the fixed set of matrices [S1, unofficial].
*   **Performance:** Uploading this buffer every frame is efficient due to its small size. It fits within a single cache line or two, minimizing GPU cache misses [G].
*   **Strengths:** Simple to implement, low overhead, supports dynamic updates for camera and lights [S1, unofficial].
*   **Limitations:** Not suitable for large datasets (e.g., voxel grids, which require [3D Texture Storage and Sampling](3064-3d-texture-storage-and-sampling.md) or [Bricking](914-bricking.md)). The fixed `MAX_LIGHTS` limit may require multiple buffers or dynamic indexing if more lights are needed [S1, unofficial].

## Background
The Global Uniform Data Layout is a common pattern in GPU programming, particularly in Vulkan, Metal, and OpenGL. The specific layout described in [S1, unofficial] originates from the "VoxelConeTracingMetal" project, which implements voxel-based cone tracing for real-time global illumination [S1, unofficial]. The layout is designed to support dynamic lighting and shadowing in a voxel-based rendering pipeline.
