# Global Uniform Data Layout

Also called: App State Buffer, GlobalUniformData

## Overview
Global Uniform Data Layout organizes GPU uniform buffers to transmit global rendering state, camera parameters, and lighting configurations from the CPU to volume rendering shaders [G]. It differs from sibling methods like [3D Texture Representation](2393-3d-texture-representation-cpu-gpu-indexing.md) by handling pipeline configuration rather than volumetric data, and from [Camera Uniform Layout](3619-camera-uniform-layout.md) by encompassing the full rendering state rather than temporal reprojection data alone [G].

## How it works
### Inputs and Outputs
- **Input:** CPU-side data structures containing camera matrices, light positions, material properties, and rendering flags [G].
- **Output:** A contiguous block of memory (uniform buffer) uploaded to GPU memory, accessible by vertex, fragment, or compute shaders [G].

### Data Structures and Layout
The layout is defined by a struct or array with specific field orders and alignment rules [G]. Implementations vary by graphics API:
- **Metal:** The `GlobalUniformData` struct inherits `Settings`, followed by `PointLight pointLights[MAX_LIGHTS]` (where `MAX_LIGHTS = 1`), `int numberOfLights`, `glm::mat4 V` (view matrix), `glm::mat4 P` (projection matrix), `vec3 cameraPosition`, `uint32_t voxelTextureSize`, `int32_t state`, and `uint32_t padding[3]` [S1, unofficial]. The `PointLight` struct contains `packed_float3 position` and `packed_float3 color` [S1, unofficial].
- **WebGPU/WGSL:** A tightly packed `Float32Array` of 64 elements (256 bytes) is used [S3, unofficial]. Indices map to: 0=`width`, 1=`height`, 2=`time`, 3=`coverage`, 4=`cloudBottom`, 5=`cloudTop`, 6=`densityMultiplier`, 7=`maxSteps` (via `Uint32View`), 8=`lightSteps` (via `Uint32View`), 9=`stepSize`, 10-11=`padding`, 12-14=`sunDirection`, 15=`padding`, 16-18=`camPos`, 19=`padding`, 20-35=`invProj` matrix, 36-51=`invView` matrix [S3, unofficial].
- **Vulkan (`std140`):** The `AppearanceFrame` uniform buffer uses `std140` layout, set 0, binding 0, with a total size of 2336 bytes (584 words) [S4, unofficial]. Fields are packed with 16-byte alignment padding: `camera_clip` (mat4, 64B), `light_clip` (mat4, 64B), `eye_near` (vec4, 16B), `camera_right` (vec4, 16B), `camera_up` (vec4, 16B), `camera_forward_focal` (vec4, 16B), `viewport` (vec4, 16B), `brush_cm` (vec4, 16B), `flags` (uvec4, 16B), `palette` (vec4[5], 80B), `shadow_params` (vec4, 16B), `selected` (uvec4[125], 2000B) [S4, unofficial].

### Formulas and Alignment Rules
- **Offset Alignment Rule:** `offset = (offset + 15) // 16 * 16` [S4, unofficial].
- **Size Calculation:** `size = (64 if kind == 'mat4' else 16) * count` [S4, unofficial].
- **Rotation Encoding (Instance Data):** `rotation = (int)up * 4 + forward`, where `up` is a `Direction` enum and `forward` is an integer range 0-3 representing clockwise rotation perpendicular to `up` [S2, unofficial].

### Parameters
- `MAX_LIGHTS`: Maximum number of point lights supported. Default: 1 [S1, unofficial].
- `voxelTextureSize`: Dimensions of the voxel texture [S1, unofficial].
- `state`: Rendering state flag [S1, unofficial].

### Pseudocode
The following Python-like pseudocode demonstrates the calculation of offsets for the `std140` layout, applying the alignment rule and size formula from the evidence:

```python
def calculate_std140_offsets(fields):
    """
    Calculate byte offsets for a std140 uniform buffer.
    fields: List of tuples (name, kind, count)
    kind: 'mat4' (64 bytes) or 'vec4'/'uvec4' (16 bytes)
    count: Number of elements for arrays
    """
    current_offset = 0
    layout = []
    
    for name, kind, count in fields:
        # Calculate size of one element based on kind
        elem_size = 64 if kind == 'mat4' else 16
        total_size = elem_size * count
        
        # Apply std140 alignment rule: offset must be a multiple of 16
        if current_offset % 16 != 0:
            current_offset = (current_offset + 15) // 16 * 16
            
        layout.append({
            'name': name,
            'offset': current_offset,
            'size': total_size,
            'kind': kind
        })
        
        current_offset += total_size
        
    return layout, current_offset

# Example usage for Vulkan AppearanceFrame
fields = [
    ('camera_clip', 'mat4', 1),
    ('light_clip', 'mat4', 1),
    ('eye_near', 'vec4', 1),
    ('camera_right', 'vec4', 1),
    ('camera_up', 'vec4', 1),
    ('camera_forward_focal', 'vec4', 1),
    ('viewport', 'vec4', 1),
    ('brush_cm', 'vec4', 1),
    ('flags', 'uvec4', 1),
    ('palette', 'vec4', 5),
    ('shadow_params', 'vec4', 1),
    ('selected', 'uvec4', 125)
]

layout, total_size = calculate_std140_offsets(fields)
# Source asserts total size is 2336 bytes; the calculated sum is 2320 bytes,
# implying 16 bytes of trailing padding or an unlisted field to satisfy 
# the largest alignment requirement [S4, unofficial].
assert total_size == 2336, f"Expected 2336, got {total_size}"
```

### Edge Cases and Pitfalls
- **Truncation:** Fields may be truncated to smaller types (e.g., `ushort` for shape IDs), limiting the range of unique values to 65535 [S2, unofficial].
- **Padding Requirements:** Explicit padding fields (e.g., `uint32_t padding[3]`) may be required to align subsequent fields or the buffer end to specific boundaries [S1, unofficial].
- **Shader Access:** In some implementations, multiple fields are combined into a single `uint` in shader code (e.g., `shape` and `rotation` combined into `shapeRotation`) to optimize sampling [S2, unofficial].

## Subtopics

### [Camera Uniform Layout](3619-camera-uniform-layout.md)
Camera Uniform Layout defines the memory layout and update protocol for the `CameraUniform` GPU buffer structure, which transmits camera pose, temporal state, and lighting parameters from the CPU to the volume rendering and shading shaders. It solves the problem of maintaining consistent reprojection history for temporal anti-aliasing (TAA) and lighting caches across frame boundaries, ensuring that cached shadow and ambient occlusion values can be correctly mapped from the previous frame to the current frame even when the camera moves or the world origin shifts. It is distinguished from generic camera matrices by its inclusion of explicit previous-frame basis vectors, world-voxel origin offsets, and specific flags controlling the validity of reprojection caches.

### Instance Data Layout
A tightly packed data structure used to pass instance data (position, texture, tint, shape ID, orientation) to the GPU for instanced rendering of voxel shapes [S2, unofficial]. The `ShapeInstance` struct uses `LayoutKind.Explicit, Pack = 1` with a total size of 32 bytes [S2, unofficial]. Fields are ordered: `position` (Vector3, float[3], 12 bytes, offset 0), `texture` (int, 4 bytes, offset 12), `shape` (ushort, 2 bytes, offset 16), `rotation` (ushort, 2 bytes, offset 18), `tint` (Vector3, float[3], 12 bytes, offset 20) [S2, unofficial]. The `shape` and `rotation` fields are combined in shader code into a single `uint` named `shapeRotation` [S2, unofficial].

### WebGPU Uniform Buffer Packing
A specific layout for WebGPU/WGSL implementations using a `Float32Array` of size 64 (256 bytes) [S3, unofficial]. Indices map to specific parameters including width, height, time, coverage, cloud bounds, density multiplier, step counts, sun direction, camera position, and inverse projection/view matrices [S3, unofficial].

### Appearance Frame Uniform Layout
The `AppearanceFrame` uniform buffer uses `std140` layout, set 0, binding 0, with a total size of 2336 bytes (584 words) [S4, unofficial]. Fields are packed with 16-byte alignment padding in the order: `camera_clip`, `light_clip`, `eye_near`, `camera_right`, `camera_up`, `camera_forward_focal`, `viewport`, `brush_cm`, `flags`, `palette`, `shadow_params`, `selected` [S4, unofficial]. A Python script `vulkan/tools/build_shaders.py` generates the GLSL uniform block definition and helper functions for word access [S4, unofficial].

## Operating characteristics
- **Time Complexity:** Upload time is O(N) where N is the number of bytes in the uniform buffer [G]. For typical sizes (256-2336 bytes), this is negligible [G].
- **Memory Complexity:** O(1) fixed size per frame [G].
- **Performance:** Uniform buffers are cached by the GPU driver; frequent updates (e.g., every frame) are efficient if the buffer size is small [G]. Large uniform buffers may cause cache thrashing [G].
- **Strengths:** Simple to implement and widely supported across all graphics APIs [G].
- **Limitations:** Limited by maximum uniform buffer size (typically 64KB-128KB) [G]. Not suitable for large datasets; volumetric data should use [3D Texture Representation](2393-3d-texture-representation-cpu-gpu-indexing.md) or [Chunk-based Voxel Data Structure](1818-chunk-based-voxel-data-structure.md) instead [G].

## Background
Global Uniform Data Layout is a standard pattern in GPU programming, originating from the need to pass shader constants efficiently across the CPU-GPU boundary [G]. It is implemented across various voxel rendering projects, including Metal-based voxel cone tracing [S1, unofficial], C#-based cubic grid renderers [S2, unofficial], WebGPU volumetric cloud simulations [S3, unofficial], and Vulkan-based voxel editors [S4, unofficial]. The specific layouts vary by API and implementation details, but the core concept remains consistent: a structured block of memory for global state [G].
