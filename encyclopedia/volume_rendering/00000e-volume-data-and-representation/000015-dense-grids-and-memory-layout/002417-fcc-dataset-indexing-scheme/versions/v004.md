# FCC Dataset Indexing Scheme
Also called: Four-channel 3D Texture Storage for FCC

## Overview
The FCC Dataset Indexing Scheme is a method for storing Face-Centered Cubic (FCC) volume datasets in standard hardware-supported 3D textures, circumventing the lack of native non-Cartesian volume rendering support [S1]. It maps an FCC lattice to a four-channel (RGBA) Cartesian 3D texture, reducing memory footprint by half compared to a naive one-channel storage scheme [S1]. It sets itself apart from sibling methods like [Bricking](914-bricking.md) or [3D Texture Storage and Sampling](3064-3d-texture-storage-and-sampling.md) by specifically addressing the geometric irregularity of FCC lattices through a parity-based channel mapping, rather than relying on spatial locality optimizations like Morton codes or hierarchical bricking [S1].

## How it works
**Inputs:**
*   An FCC dataset embedded in a Cartesian bounding box of size $N_x \times N_y \times N_z$.
*   The FCC lattice points $\mathbb{Z}_{\text{fcc}}$.

**Outputs:**
*   A four-channel 3D texture of dimensions $W \times H \times D \times 4$, where $W = \lceil N_x/2 \rceil$, $H = \lceil N_y/2 \rceil$, $D = \lceil N_z/2 \rceil$.
*   A mapping function to retrieve the value of any FCC lattice point $j$ from the texture.

**Data Structures:**
*   **Texture:** A 3D texture object supporting `texelFetch` (or equivalent hardware sampling). Each texel holds 4 scalar values (R, G, B, A).
*   **Index Mapping:** A bitwise mapping logic that converts an FCC integer coordinate $j = (j_x, j_y, j_z)$ into a texture coordinate $(x, y, z)$ and a channel index $c$.

**Mathematical Formulation:**
The FCC lattice is grouped into sets of four points relative to a base point $j \in 2\mathbb{Z}$ (where $2\mathbb{Z}$ denotes even integers):
$$ \mathbb{Z}_{\text{fcc}} = \{j, j + \xi_{110}, j + \xi_{101}, j + \xi_{011} : j \in 2\mathbb{Z}\} $$
where $\xi_{110} = (1, 1, 0)$, $\xi_{101} = (1, 0, 1)$, and $\xi_{011} = (0, 1, 1)$. This grouping allows the conversion of the FCC dataset into a four-channel Cartesian dataset [S1].

For any FCC index $j$, the parity vector $\mathbf{p}_j$ is defined as:
$$ \mathbf{p}_j := (j_x \bmod 2, j_y \bmod 2, j_z \bmod 2) $$
Since $j \in \mathbb{Z}_{\text{fcc}}$, the sum $j_x + j_y + j_z$ is always even. Consequently, the parity vector $\mathbf{p}_j$ can only take values from the set $\{\mathbf{0}, \xi_{110}, \xi_{101}, \xi_{011}\}$ [S1].

The channel index $c$ is calculated as:
$$ c = 2p_{j,x} + p_{j,y} $$
where $p_{j,x}$ and $p_{j,y}$ are the x and y components of $\mathbf{p}_j$. This results in $c \in \{0, 1, 2, 3\}$ [S1].

The mapping from FCC index $j$ to texture coordinates $(x, y, z)$ and channel $c$ is:
$$ j \mapsto \left( \lfloor j_x/2 \rfloor, \lfloor j_y/2 \rfloor, \lfloor j_z/2 \rfloor, 2(j_x \bmod 2) + (j_y \bmod 2) \right) $$

**Algorithm Steps:**
1.  **Initialization:** Create a 3D texture of size $\lceil N_x/2 \rceil \times \lceil N_y/2 \rceil \times \lceil N_z/2 \rceil$ with 4 channels.
2.  **Population:** For each FCC lattice point $j$ in the source dataset:
    a. Calculate the texture coordinates: $x = j_x >> 1$, $y = j_y >> 1$, $z = j_z >> 1$ (integer division by 2).
    b. Calculate the channel index: $c = ((j_x \& 1) << 1) | (j_y \& 1)$.
    c. Write the value of the dataset at $j$ to `texelFetch(tex, x, y, z)[c]`.
3.  **Query:** To retrieve the value at FCC index $j$:
    a. Calculate $x, y, z$ and $c$ as above.
    b. Fetch the texel at $(x, y, z)$.
    c. Return the component at index $c$.

**Pseudocode:**
```python
# Assuming a texture object `tex` with method fetch(x, y, z) returning a vec4 (r, g, b, a)
# and a method store(x, y, z, channel_index, value)

def store_fcc_value(tex, j_x, j_y, j_z, value):
    """
    Stores a value from an FCC lattice point j into the 4-channel texture.
    """
    # Calculate texture coordinates (integer division by 2)
    x = j_x >> 1
    y = j_y >> 1
    z = j_z >> 1
    
    # Calculate channel index using bitwise operations
    # p_j_x = j_x & 1
    # p_j_y = j_y & 1
    # c = 2 * p_j_x + p_j_y
    c = ((j_x & 1) << 1) | (j_y & 1)
    
    # Store value in the specific channel
    # Note: Direct channel assignment depends on the API. 
    # If the API only allows overwriting the whole texel, 
    # one must fetch, modify, and store back, or use a specialized store function.
    # For the purpose of this indexing scheme description, we assume direct channel access or 
    # a helper that handles the read-modify-write.
    texel = tex.fetch(x, y, z)
    if c == 0:
        texel.r = value
    elif c == 1:
        texel.g = value
    elif c == 2:
        texel.b = value
    elif c == 3:
        texel.a = value
    tex.store(x, y, z, texel)

def get_fcc_value(tex, j_x, j_y, j_z):
    """
    Retrieves a value from an FCC lattice point j from the 4-channel texture.
    """
    x = j_x >> 1
    y = j_y >> 1
    z = j_z >> 1
    c = ((j_x & 1) << 1) | (j_y & 1)
    
    texel = tex.fetch(x, y, z)
    if c == 0:
        return texel.r
    elif c == 1:
        return texel.g
    elif c == 2:
        return texel.b
    elif c == 3:
        return texel.a
```

**Edge Cases and Pitfalls:**
*   **Hardware Channel Fetching:** Current graphics hardware does not allow selective fetching of a single texture channel without fetching all four [S1]. To retrieve a value, the implementation must fetch all four channels and then select the desired one. This can be implemented as a dot product with a selector vector: `dot(texelFetch(tex, x, y, z), vec4(idx==0, idx==1, idx==2, idx==3))` [S1]. This results in massive performance degradation compared to fetching a single channel [S1].
*   **Boundary Conditions:** The texture dimensions are $\lceil N/2 \rceil$. Ensure that the source FCC lattice points fit within the calculated texture bounds.
*   **Parity Constraint:** The mapping relies on the property that $j_x + j_y + j_z$ is even for all FCC points. If the input data is not a valid FCC lattice, the mapping will be incorrect.

## Subtopics

### BCC Dataset Indexing Scheme
A scheme to convert a Body-Centered Cubic (BCC) dataset to a two-channel 3D texture, accessed similarly to the FCC scheme [S1]. The access pattern is `texelFetch(texid, j.x >> 1, j.y >> 1, j.z >> 1)[x & 1]` [S1]. It uses half the channels of the FCC scheme because the BCC lattice has a different symmetry and density relative to the Cartesian grid [S1].

## Operating characteristics
**Time Complexity:**
*   **Storage:** $O(N)$, where $N$ is the number of FCC lattice points. Each point requires a constant number of bitwise operations and one texture write.
*   **Query:** $O(1)$ per point, but with a high constant factor due to the hardware limitation of fetching all four channels and performing a dot product for selection [S1].

**Memory Complexity:**
*   The four-channel scheme requires half the memory footprint of a one-channel scheme that would store the same FCC data in a larger Cartesian grid [S1]. Specifically, if the Cartesian grid is $N_x \times N_y \times N_z$, the FCC grid has roughly half the points, and the 4-channel texture stores them compactly. The one-channel scheme required twice the memory footprint of the four-channel scheme [S1].

**Measured Performance:**
*   On an MRI-Head dataset, the 4-channel scheme achieved 33.6 fps, while the 1-channel scheme achieved 65.2 fps [S1].
*   On a VisMale dataset, the 4-channel scheme achieved 31.5 fps, while the 1-channel scheme achieved 68.9 fps [S1].
*   The performance degradation is attributed to the inability to selectively fetch channels on current hardware [S1].

**Strengths:**
*   Reduces memory usage by 50% compared to naive Cartesian storage [S1].
*   Efficient bitwise mapping for index calculation [S1].
*   Compatible with standard 3D texture hardware [S1].

**Limitations:**
*   Significant performance penalty due to hardware limitations on selective channel fetching [S1].
*   Not suitable for real-time applications where the performance gap between 4-channel and 1-channel schemes is critical [S1].

**When to Use:**
*   When memory bandwidth or capacity is the primary bottleneck, and the performance hit from channel fetching is acceptable [S1].
*   When rendering FCC datasets on hardware that does not support native non-Cartesian volume rendering [S1].

**When Not to Use:**
*   When maximum rendering performance is required, and memory is not a constraint (use the 1-channel scheme instead) [S1].
*   When the hardware supports selective channel fetching (not currently common) [S1].

## Background
The FCC Dataset Indexing Scheme was proposed in the paper "GPU Isosurface Raycasting of FCC Datasets" by Kim et al. [S1]. The paper addresses the challenge of rendering FCC datasets, which are denser than Cartesian grids and offer better isotropic properties, but lack direct hardware support [S1]. Previous attempts to load FCC layers into separate textures were deemed inefficient due to data fetching overhead [S1]. The scheme was developed to provide a compact and hardware-compatible storage format for FCC volumes, enabling efficient raycasting on GPUs [S1].
