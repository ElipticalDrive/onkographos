# FCC Dataset Indexing Scheme
Also called: Four-channel 3D Texture Storage for FCC

## Overview
The FCC Dataset Indexing Scheme is a method for storing and accessing Four-Cubic Closest (FCC) lattice volume data on graphics hardware that lacks native support for non-Cartesian datasets [S1]. It solves the problem of efficiently mapping FCC voxel values to standard 3D texture units by packing four FCC lattice points into a single four-channel (RGBA) Cartesian 3D texture [S1]. This approach reduces memory footprint compared to storing each FCC point in a separate 1-channel texture, while avoiding the overhead of loading multiple separate textures or shifting layers [S1]. It sets itself apart from sibling methods like [Bricking](914-bricking.md) or [3D Texture Storage and Sampling](3064-3d-texture-storage-and-sampling.md) by specifically addressing the geometric irregularity of FCC lattices through a parity-based channel mapping [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** An FCC dataset embedded in a Cartesian bounding box of size $N_x \times N_y \times N_z$.
*   **Output:** A four-channel 3D texture of size $W \times H \times D \times 4$, where $W = \lfloor (N_x + 1)/2 \rfloor$, $H = \lfloor (N_y + 1)/2 \rfloor$, and $D = \lfloor (N_z + 1)/2 \rfloor$ [S1].

**Data Structures:**
The data is stored in a standard 3D texture object (`texid`) with four channels (R, G, B, A). Each texel at coordinates $(x, y, z)$ holds four scalar values corresponding to four distinct FCC lattice points [S1].

**Mathematical Mapping:**
The FCC lattice $\mathbb{Z}_{\text{fcc}}$ is defined by grouping points as [S1]:
$$
\mathbb{Z}_{\text{fcc}} = \{j, j + \xi_{110}, j + \xi_{101}, j + \xi_{011} : j \in 2\mathbb{Z}\}
$$
where $\xi_{110}, \xi_{101}, \xi_{011}$ represent the offset vectors for the FCC neighbors relative to the base even lattice [S1].

For any FCC index $j \in \mathbb{Z}_{\text{fcc}}$, the parity vector $\mathbf{p}_j$ is calculated as [S1]:
$$
\mathbf{p}_j := (j(1) \bmod 2, j(2) \bmod 2, j(3) \bmod 2)
$$
Since $j \in \mathbb{Z}_{\text{fcc}}$, the sum $j(1)+j(2)+j(3)$ is always even. Consequently, $\mathbf{p}_j$ takes values in $\{\mathbf{0}, \xi_{110}, \xi_{101}, \xi_{011}\}$ [S1]. The channel index $c$ is derived from the parity vector as [S1]:
$$
c = 2p_j(1) + p_j(2)
$$
This ensures $c \in \{0, 1, 2, 3\}$ [S1].

The mapping from an FCC index $j$ to the texture coordinates $(x, y, z, c)$ is [S1]:
$$
j \mapsto (\lfloor j(1)/2 \rfloor, \lfloor j(2)/2 \rfloor, \lfloor j(3)/2 \rfloor, 2p_j(1) + p_j(2))
$$

**Implementation Steps:**
1.  **Calculate Texture Coordinates:** For an input FCC index $j$, compute the base 3D coordinates by integer division by 2 (equivalent to bitwise right shift by 1).
    *   $x = j(1) \gg 1$
    *   $y = j(2) \gg 1$
    *   $z = j(3) \gg 1$
2.  **Calculate Channel Index:** Compute the channel index using bitwise operations on the least significant bits of the coordinates.
    *   $c = ((j(1) \& 1) \ll 1) \mid (j(2) \& 1)$
3.  **Fetch Data:** Retrieve the value from the texture at $(x, y, z)$ and select the $c$-th channel.

**Pseudocode:**
The following Python-like pseudocode demonstrates the indexing logic. It assumes `tex` is an object with a `fetch` method returning a tuple `(r, g, b, a)`.

```python
def get_fcc_value(tex, j_x, j_y, j_z):
    """
    Fetches the value for an FCC lattice point j from a 4-channel 3D texture.
    
    Args:
        tex: Texture object supporting fetch(x, y, z) -> (r, g, b, a)
        j_x: x-coordinate of the FCC index
        j_y: y-coordinate of the FCC index
        j_z: z-coordinate of the FCC index
        
    Returns:
        The scalar value stored at the corresponding FCC lattice point.
    """
    # Step 1: Calculate base 3D texture coordinates
    # Integer division by 2 is equivalent to bitwise right shift
    x = j_x >> 1
    y = j_y >> 1
    z = j_z >> 1
    
    # Step 2: Calculate channel index (0-3)
    # Derived from parity: 2*(j.x mod 2) + (j.y mod 2)
    # Using bitwise AND to get the least significant bit
    channel_idx = ((j_x & 1) << 1) | (j_y & 1)
    
    # Step 3: Fetch the texel
    # Note: Hardware does not support selective channel fetching efficiently.
    # We must fetch all four channels and select the required one.
    r, g, b, a = tex.fetch(x, y, z)
    
    # Step 4: Select the correct channel
    if channel_idx == 0:
        return r
    elif channel_idx == 1:
        return g
    elif channel_idx == 2:
        return b
    elif channel_idx == 3:
        return a
    else:
        raise ValueError("Invalid channel index")
```

**Edge Cases and Pitfalls:**
*   **Hardware Limitation:** Current graphics hardware does not allow selective fetching of a single texture channel without overhead [S1]. Fetching all four channels and using a dot product or conditional selection results in massive performance degradation [S1]. The efficient GLSL implementation requires fetching all channels and masking: `dot(texelFetch(tex, x, y, z), vec4(idx==0, idx==1, idx==2, idx==3))` [S1].
*   **Boundary Conditions:** The texture size is determined by $\lfloor (N_i + 1)/2 \rfloor$. Ensure that input indices $j$ are within the valid FCC lattice bounds before mapping to avoid out-of-bounds texture fetches [S1].
*   **Parity Constraint:** The mapping relies on the property that $j(1)+j(2)+j(3)$ is even for all $j \in \mathbb{Z}_{\text{fcc}}$. If the input data does not strictly follow the FCC lattice definition, the mapping will be incorrect [S1].

## Subtopics

### BCC Dataset Indexing Scheme
A scheme to convert a Body-Centered Cubic (BCC) dataset to a two-channel 3D texture, accessed similarly to the FCC scheme [S1]. The access pattern uses a single bit for channel selection: `texelFetch(texid, j.x >> 1, j.y >> 1, j.z >> 1)[j.x & 1]` [S1]. This reduces memory usage compared to a 1-channel scheme but retains the hardware limitation of fetching multiple channels if selective access is not supported [S1].

## Operating characteristics
**Time and Memory Complexity:**
*   **Memory:** The four-channel scheme requires half the memory footprint of a one-channel scheme that stores each FCC point in a separate texture [S1]. The one-channel scheme required twice the memory footprint of the four-channel scheme [S1].
*   **Time:** The index mapping involves bitwise operations, which are computationally cheap [S1]. However, the inability to selectively fetch texture channels on current hardware introduces significant overhead [S1].

**Measured Performance:**
Performance was measured on MRI-Head and other datasets [S1]. The four-channel scheme achieved 33.6 fps, while the one-channel scheme achieved 65.2 fps on the MRI-Head dataset [S1]. The speed-up of the one-channel scheme over the four-channel scheme was 1.9x for MRI-Head, 2.2x for VisMale, 2.2x for CT-Head, and 1.3x for Carp [S1].

**Strengths and Limitations:**
*   **Strengths:** Compact memory storage; efficient bitwise indexing; reduces cache misses compared to sparse storage [S1].
*   **Limitations:** Severe performance degradation due to hardware limitations in selective channel fetching [S1]. The computational overhead of fetching and selecting channels can negate the memory benefits in bandwidth-bound scenarios [S1].

**When to Use:**
Use this scheme when memory bandwidth is constrained and the hardware supports efficient bitwise operations, but be aware of the potential performance penalty from multi-channel fetching [S1]. It is suitable for FCC datasets where memory footprint is a critical constraint [S1].

**When Not to Use:**
Avoid this scheme if the target hardware allows efficient selective channel fetching or if performance is prioritized over memory usage, as the one-channel scheme offers significantly higher frame rates [S1].

## Background
The FCC Dataset Indexing Scheme was proposed in a paper by Kim et al. [S1]. The work addresses the lack of hardware support for non-Cartesian volume datasets, specifically FCC lattices, which are common in certain scientific visualizations and isosurface raycasting applications [S1]. The scheme was developed to provide an efficient way to store FCC datasets as four-channel 3D textures, circumventing the need for separate textures or complex layer shifting [S1].
