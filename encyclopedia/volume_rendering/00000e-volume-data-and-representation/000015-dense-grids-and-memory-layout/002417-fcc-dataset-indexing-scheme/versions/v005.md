# FCC Dataset Indexing Scheme
Also called: Four-channel 3D Texture Storage for FCC

## Overview
The FCC Dataset Indexing Scheme is a method for storing and sampling Four-Cubic Closest (FCC) lattice volume data on graphics hardware that lacks native support for non-Cartesian datasets [S1]. It solves the problem of efficiently accessing FCC voxels by mapping the non-Cartesian lattice into a four-channel (RGBA) 3D texture, thereby avoiding the overhead of shifting layers or loading separate textures for each lattice subset [S1]. It sets itself apart from sibling methods like [Bricking](914-bricking.md) or [3D Texture Storage and Sampling](3064-3d-texture-storage-and-sampling.md) by specifically addressing the geometric structure of FCC lattices through a parity-based channel mapping, trading memory efficiency for potential sampling overhead due to hardware limitations on selective channel fetching [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** An FCC dataset embedded in a Cartesian bounding box of size $N_x \times N_y \times N_z$.
*   **Output:** A four-channel 3D texture of size $W \times H \times D \times 4$, where $W = \lfloor (N_x + 1)/2 \rfloor$, $H = \lfloor (N_y + 1)/2 \rfloor$, and $D = \lfloor (N_z + 1)/2 \rfloor$ [S1].

**Data Structures:**
The data is stored in a 3D texture object. Each texel contains four components (R, G, B, A), corresponding to the four subsets of the FCC lattice. The memory layout is contiguous per texel, with channels packed together [S1].

**Mathematical Mapping:**
The FCC lattice $\mathbb{Z}_{\text{fcc}}$ is defined as the set of points generated by grouping:
$$ \mathbb{Z}_{\text{fcc}} = \{j, j + \xi_{110}, j + \xi_{101}, j + \xi_{011} : j \in 2\mathbb{Z}\} $$
where $2\mathbb{Z}$ denotes points with even integer coordinates, and $\xi_{110}, \xi_{101}, \xi_{011}$ are the standard basis vectors for the FCC offsets [S1].

For any FCC index $j \in \mathbb{Z}_{\text{fcc}}$, the mapping to the texture coordinates $(x, y, z, c)$ is performed as follows:

1.  **Calculate Parity Vector:** Compute the parity vector $\mathbf{p}_j$ of the index $j$:
    $$ \mathbf{p}_j := (j(1) \bmod 2, j(2) \bmod 2, j(3) \bmod 2) $$
    Since $j \in \mathbb{Z}_{\text{fcc}}$, the sum $j(1)+j(2)+j(3)$ is always even. Consequently, $\mathbf{p}_j$ is restricted to the set $\{\mathbf{0}, \xi_{110}, \xi_{101}, \xi_{011}\}$ [S1].

2.  **Determine Channel Index:** Compute the channel index $c$ using the first two components of the parity vector:
    $$ c = 2p_j(1) + p_j(2) $$
    This maps the parity to an integer in $\{0, 1, 2, 3\}$ [S1].

3.  **Compute Texture Coordinates:** The spatial coordinates are obtained by integer division by 2 (equivalent to bitwise right shift by 1):
    $$ x = \lfloor j(1)/2 \rfloor, \quad y = \lfloor j(2)/2 \rfloor, \quad z = \lfloor j(3)/2 \rfloor $$

**Pseudocode:**
The mapping is implemented using bitwise operations for efficiency. Given an FCC index `j` (with components `j.x`, `j.y`, `j.z`) and a texture object `tex`:

```python
# Calculate spatial coordinates (integer division by 2)
tex_x = j.x >> 1
tex_y = j.y >> 1
tex_z = j.z >> 1

# Calculate channel index from parity bits
# p_j(1) is (j.x & 1), p_j(2) is (j.y & 1)
# c = 2 * (j.x & 1) + (j.y & 1)
channel_idx = ((j.x & 1) << 1) | (j.y & 1)

# Fetch the texel
# Note: Hardware limitation requires fetching all channels if selective access is not supported
texel = texelFetch(tex, tex_x, tex_y, tex_z)

# Select the specific channel
value = texel[channel_idx]
```

**Edge Cases and Pitfalls:**
*   **Hardware Channel Fetching:** Current graphics hardware does not allow selective fetching of a single texture channel without loading all four. To access a specific channel, the implementation must fetch all four channels and use a dot product to select the desired one:
    $$ \text{value} = \text{dot}(\text{texelFetch}(tex, x, y, z), \text{vec4}(idx==0, idx==1, idx==2, idx==3)) $$
    This results in massive performance degradation compared to a single-channel scheme [S1].
*   **Boundary Conditions:** The texture dimensions are derived from the ceiling of half the original dimensions. Indices outside the range $[0, W-1] \times [0, H-1] \times [0, D-1]$ must be handled via clamping or boundary checks to avoid out-of-bounds access [S1].

## Subtopics

### BCC Dataset Indexing Scheme
A scheme to convert a Body-Centered Cubic (BCC) dataset to a two-channel 3D texture, accessed similarly to the FCC scheme [S1]. The access pattern uses the least significant bit of the x-coordinate to select the channel: `texelFetch(texid, j.x >> 1, j.y >> 1, j.z >> 1)[x & 1]` [S1].

## Operating characteristics
**Time and Memory Complexity:**
*   **Memory:** The four-channel scheme requires half the memory footprint of a one-channel scheme that stores the same FCC data explicitly [S1].
*   **Time:** The index mapping involves bitwise operations, which are computationally cheap. However, the sampling cost is higher due to the hardware limitation on selective channel fetching, requiring a dot product operation [S1].

**Measured Performance:**
Performance comparisons on an MRI-Head dataset show that the four-channel scheme achieved 33.6 fps, while the one-channel scheme achieved 65.2 fps [S1]. The speed-up varies by dataset size; for example, on the VisMale dataset, the one-channel scheme was 2x faster, while on MRI-Head it was 1.9x faster [S1].

**Strengths and Limitations:**
*   **Strengths:** Compact memory storage; avoids overhead of multiple texture objects or layer shifting [S1].
*   **Limitations:** Significant performance penalty due to the inability of current hardware to fetch single channels efficiently [S1].

**When to Use:**
Use this scheme when memory bandwidth or texture object overhead is a bottleneck, and the performance cost of the dot-product selection is acceptable. Avoid if maximum sampling throughput is required and memory is not constrained [S1].

## Background
The FCC Dataset Indexing Scheme was proposed in the context of GPU isosurface raycasting for non-Cartesian volume datasets [S1]. It addresses the lack of hardware support for FCC lattices directly, building on the need to efficiently store and sample such data without resorting to inefficient layer-shifting or multiple texture loads [S1]. The method was evaluated using datasets from the "vollib library" and MATLAB interpolation [S1].
