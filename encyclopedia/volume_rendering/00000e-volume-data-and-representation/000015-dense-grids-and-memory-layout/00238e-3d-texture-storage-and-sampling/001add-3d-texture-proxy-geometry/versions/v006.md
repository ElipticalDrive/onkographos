# 3D Texture Proxy Geometry

Also called: 3D Texture Proxy, 3D Texture-Based Volume Rendering, 3D Texture Volume Rendering, 3D Texture Mapping for Volume Rendering, Direct Volume Rendering via 3D Textures

## Overview
3D Texture Proxy Geometry is a direct volume rendering method that represents a rectilinear volume as a stack of parallel planar polygons (slabs) textured with 3D texture maps, leveraging hardware-accelerated tri-linear interpolation to sample volume data at arbitrary locations [S2, S3, unofficial]. It solves the problem of efficient hardware-accelerated volume rendering with directional lighting by pre-computing color and opacity per voxel and storing them in 3D textures, allowing the graphics pipeline to handle interpolation and compositing [S3, unofficial]. Unlike shear-warp methods which fix plane counts to volume resolution, this method allows the number of rendering planes to be adjusted at runtime independent of volume resolution, and unlike coherent projection, it supports perspective views without a time penalty, though perspective projection causes irregular sampling along rays [S3, unofficial][S4, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A rectilinear volume dataset $V$ with logical dimensions $(n_x, n_y, n_z)$, spacing $(\Delta x, \Delta y, \Delta z)$, and origin offset. A viewing direction defined by a rotation matrix $R$ and projection type (parallel or perspective).
*   **Output:** A 2D image composed of blended polygonal slices.

**Data Structures:**
1.  **3D Texture Object:** A single texture resource (e.g., `GL_TEXTURE_3D`) with dimensions $(N_x, N_y, N_z)$, where $N_i$ is the smallest power of two such that $N_i \ge n_i$ [S3, S17, unofficial]. The texture stores pre-classified optical properties (color and opacity) or raw scalar data [S1, unofficial][S18].
2.  **Proxy Geometry:** A set of 2D polygons (quads) representing slices through the volume. Each polygon has vertices with 3D texture coordinates $(s, t, r)$ [S12, S18].

**Coordinate Mapping:**
The mapping from world coordinates $(x, y, z)$ to texture coordinates $(s, t, r)$ involves scaling and translation. Let $L_x = N_x \Delta x$, $L_y = N_y \Delta y$, $L_z = N_z \Delta z$ be the physical dimensions of the padded texture space [S3, unofficial]. The base mapping for a volume centered at the origin is:
$$
s(x) = \frac{x + \frac{1}{2}n_x \Delta x}{N_x \Delta x}, \quad t(y) = \frac{y + \frac{1}{2}n_y \Delta y}{N_y \Delta y}, \quad r(z) = \frac{z + \frac{1}{2}n_z \Delta z}{N_z \Delta z}
$$
[S3, unofficial]. This maps the volume corners to the appropriate texture regions. For arbitrary viewing angles, the texture matrix applies the inverse rotation $R^{-1}$ and uniform scaling $D^{-1}$ (where $D$ scales by the bounding cube diagonal $d = \sqrt{L_x^2 + L_y^2 + L_z^2}$) [S3, unofficial]. The correct order of operations is rotation followed by non-uniform scaling to avoid shearing distortion [S3, unofficial].

**Algorithm Steps:**
1.  **Initialization:**
    *   Allocate a 3D texture with power-of-two dimensions $(N_x, N_y, N_z)$ [S17, unofficial].
    *   Upload the volume data (pre-classified into color/opacity or raw scalars) into the texture [S1, unofficial][S11].
    *   Set texture parameters: `GL_TEXTURE_MIN_FILTER` and `GL_TEXTURE_MAG_FILTER` to `GL_LINEAR` for tri-linear interpolation [S2, S5, unofficial]. Set wrap modes to `GL_CLAMP_TO_EDGE` [S5, unofficial].
    *   If using dependent texture reads for classification, set up the transfer function lookup texture [S19, book].

2.  **View Update (Per Frame):**
    *   Determine the current viewing direction and projection matrix [S7].
    *   Compute the proxy geometry: Generate a series of polygons (slices) perpendicular to the viewing direction. The number of slices $N_{slices}$ is typically chosen as $d/\Delta z$ (for parallel projection) or adjusted for perspective [S3, unofficial][S8].
    *   Calculate the 3D texture coordinates for each vertex of the proxy polygons. This involves applying the texture transformation matrix (rotation $R^{-1}$, scaling $D^{-1}$, translation $T$) to the world-space vertices [S3, S14, unofficial].
    *   Sort the polygons back-to-front relative to the camera [S6, unofficial].

3.  **Rendering:**
    *   Disable lighting and depth buffer writing (if compositing over opaque geometry) [S18].
    *   Enable alpha blending with equation: $C_{out} = C_{src} + C_{dst}(1 - A_{src})$ [S18].
    *   For each polygon in back-to-front order:
        *   Bind the 3D volume texture.
        *   Rasterize the polygon. The GPU interpolates the $(s, t, r)$ texture coordinates across the polygon surface [S12].
        *   **Fragment Shader / Hardware Sampling:**
            *   Perform a dependent texture lookup: Use the interpolated $(s, t, r)$ to sample the 3D volume texture [S12][S19, book].
            *   If pre-classified: Retrieve color $C_i$ and opacity $A_i$ directly [S18].
            *   If raw data: Use the sampled scalar value as an index into a 1D or 3D transfer function texture to retrieve $C_i$ and $A_i$ [S19, book].
            *   Apply the emission-absorption model: $C_{final} = \sum_{i} C_i \cdot A_i \cdot \prod_{j=1}^{i-1} (1 - A_j)$ [S18]. Note: In the proxy geometry method, this integration is often approximated by the hardware alpha blending of the slices [S6, unofficial].

**Pseudocode:**
```python
def render_3d_texture_proxy(volume_data, view_matrix, num_slices):
    # 1. Setup 3D Texture (One-time or when data changes)
    tex_id = create_3d_texture(volume_data.dimensions)
    upload_volume_data(tex_id, volume_data)
    set_texture_filter(tex_id, GL_LINEAR)
    set_texture_wrap(tex_id, GL_CLAMP_TO_EDGE)
    
    # 2. Compute Proxy Geometry (Per Frame)
    # Determine slice positions perpendicular to view direction
    slices = compute_view_aligned_slices(volume_data.bounding_box, view_matrix, num_slices)
    
    # Sort slices back-to-front
    slices.sort_by_depth(view_matrix)
    
    # 3. Render Loop
    enable_alpha_blending(src=GL_ONE, dst=GL_ONE_MINUS_SRC_ALPHA)
    disable_depth_write()
    disable_lighting()
    bind_texture(tex_id, unit=0)
    
    for slice in slices:
        # Apply texture matrix to transform slice vertices to texture space
        # The texture matrix handles rotation R^-1, scaling D^-1, and translation T
        apply_texture_matrix(view_matrix.inverse())
        
        # Rasterize the slice polygon
        # Hardware interpolates (s,t,r) across the quad
        draw_polygon(slice.vertices)
        
    disable_alpha_blending()
    enable_depth_write()
    enable_lighting()

def compute_view_aligned_slices(bbox, view_matrix, num_slices):
    # Calculate the diagonal length of the bounding box
    d = sqrt(bbox.width**2 + bbox.height**2 + bbox.depth**2)
    
    # Determine slice spacing
    # For parallel projection, spacing is often related to voxel depth
    slice_spacing = d / num_slices
    
    slices = []
    # Generate planes perpendicular to view direction
    # Intersect planes with bbox to form quads
    for i in range(num_slices):
        plane_offset = i * slice_spacing
        plane_normal = view_matrix.get_view_direction()
        plane_origin = plane_offset * plane_normal
        
        # Compute intersection of plane with bbox to get polygon vertices
        vertices = intersect_plane_with_bbox(plane_origin, plane_normal, bbox)
        
        # Calculate texture coordinates for vertices
        # Apply the inverse transformation to map world coords to texture coords
        tex_coords = []
        for v in vertices:
            # s, t, r mapping as defined in S3
            s = (v.x + 0.5 * volume_data.nx * dx) / (Nx * dx)
            t = (v.y + 0.5 * volume_data.ny * dy) / (Ny * dy)
            r = (v.z + 0.5 * volume_data.nz * dz) / (Nz * dz)
            
            # Apply rotation and scaling from view matrix
            # (s,t,r) = (x,y,z) * R^-1 * D^-1 * S * T
            tex_coords.append(transform_texture_coords(v, view_matrix))
            
        slices.append(Polygon(vertices, tex_coords))
        
    return slices
```

**Parameters:**
*   **Number of Slices:** Default is $d/\Delta z$ for parallel projection, ensuring one sample per voxel depth [S3, unofficial]. Can be increased (2-4x) for higher accuracy [S3, unofficial].
*   **Texture Resolution:** $(N_x, N_y, N_z)$ are powers of two $\ge (n_x, n_y, n_z)$ [S3, unofficial].
*   **Interpolation:** Tri-linear (`GL_LINEAR`) is standard; nearest-neighbor is possible but lower quality [S1, unofficial][S12].

**Edge Cases and Pitfalls:**
*   **Perspective Sampling:** In perspective projection, the sampling rate varies with the angle between the slice polygon and the viewing ray, causing visual artifacts in fly-throughs [S4, S14, unofficial].
*   **Shearing:** If volume spacing is non-uniform, the non-uniform scaling matrix $S$ does not commute with rotation $R$. The texture matrix must apply rotation before scaling to avoid distortion [S3, unofficial].
*   **Memory Limits:** Large volumes may exceed texture memory, requiring partitioning into subvolumes (bricking) which incurs swapping overhead [S1, unofficial][S12].
*   **Data Type Mismatch:** Using `sampler3D` for `unsigned short` data results in zero values; use `usampler3D` [S5, unofficial].

## Subtopics

### [Tri-linear Interpolation via LRP](913-tri-linear-interpolation-via-lrp.md)
Tri-linear interpolation via LRP is a GPU-accelerated method for estimating scalar values at arbitrary floating-point coordinates within a 3D volume grid by interpolating the eight surrounding voxel values. It solves the problem of sampling continuous volume data from discrete voxel grids, providing smooth rendering compared to direct voxel rendering which exhibits less structural detail. It is distinguished from other interpolation methods by its specific implementation using the GPU's LRP (linear interpolation) instruction, leveraging hardware rasterization to interpolate texture coordinates "for free" between vertices, thereby optimizing memory bandwidth usage.

### [Multi-Volume Rendering with Multiple Textures](1568-multi-volume-rendering-with-multiple-textures.md)
This method renders multiple distinct volumetric classes (e.g., tissue types) simultaneously by storing each class in a separate 3D texture and combining them during the fragment shader execution. It solves the problem of visualizing heterogeneous data where different channels require independent transfer functions and opacities. It sets itself apart from single-volume approaches by allowing independent control of each channel's appearance, and from out-of-core techniques by relying entirely on GPU memory residency for all active channels.

### [Proxy Geometry Compression](1917-proxy-geometry-compression.md)
Proxy Geometry Compression is a technique for storing volume data and proxy geometry locally in graphics hardware to avoid CPU-GPU bandwidth bottlenecks associated with immediate mode rendering. It sets itself apart from immediate-mode splatting by pre-loading compressed proxy geometry templates into GPU memory, leveraging the regularity of rectilinear volumes to achieve high compression ratios (e.g., 171:1). This allows the entire volume representation to reside in local graphics memory, enabling interactive rendering speeds that are significantly faster than sending each splat separately.

### [Sm2D (2D Volume Texture Experiment)](3150-sm2d-2d-volume-texture-experiment.md)
Sm2D is a 2-dimensional test application implemented as a 2D ray tracer to investigate the applicability of a texture-based approach for smoke volumes. It simplifies the 3D volume rendering problem into a 1D viewport function where tetrahedra are represented by triangles. It sets itself apart from its siblings by serving as a diagnostic tool to demonstrate the precision limits and rotational artifacts inherent in texture-based approximations compared to explicit geometric calculations.

### Dependent Texture Reads for Classification
Dependent Texture Reads for Classification is a hardware extension (OpenGL) that uses color fragments to generate texture coordinates, replacing the color fragments with entries from a texture. It acts as an arbitrary function evaluation with up to three variables via a lookup table [S19, book]. The method involves storing data values in color components of a 3D texture, interpolating these values across proxy geometry, converting interpolated values to texture coordinates, and using these coordinates to acquire color and alpha values from a transfer-function texture per-pixel in screen space [S19, book].

## Operating characteristics
**Time and Memory Complexity:**
*   **Time:** The computational cost scales with the number of pixels in the output image (image-order rendering), independent of the number of geometric primitives in the scene [S14, unofficial]. The cost is dominated by rasterization and texture fetches.
*   **Memory:** Requires a single 3D texture of size $N_x \times N_y \times N_z$ [S5, unofficial]. For large volumes, this may exceed GPU memory, requiring out-of-core techniques or bricking [S1, unofficial][S12].

**Measured Performance:**
*   Historically provided tremendous speedup due to high rasterization performance [S6, unofficial].
*   Optimization techniques like occlusion clipping in fragment programs can yield an average 2.8x speedup [S2, unofficial].
*   Performance is highly dependent on hardware support for 3D textures and tri-linear interpolation [S6, S14, unofficial].

**Strengths and Limitations:**
*   **Strengths:** Supports arbitrary viewing angles without fixed slice counts; avoids the "popping" artifact of 2D texture methods; leverages hardware acceleration for real-time rendering [S17, S14, unofficial].
*   **Limitations:** Cannot skip unseen voxels (unlike ray casting); perspective projection causes variable sampling rates and artifacts; limited by texture memory size; lower image quality than ray casting due to aliasing and limited optical modeling [S1, S14, S4, unofficial].

**When to Use:**
*   Real-time interactive rendering of reasonably sized volumes on hardware with 3D texture support [S14, unofficial][S15].
*   Scenarios requiring arbitrary viewing angles and directional lighting [S3, unofficial].

**When Not to Use:**
*   Very large volumes that exceed texture memory without efficient bricking strategies [S1, unofficial].
*   Applications requiring precise optical modeling (e.g., refraction) or accurate skipping of transparent regions [S14, S1, unofficial].
*   Fly-through applications with large field-of-view angles where perspective sampling artifacts are unacceptable [S4, unofficial].

## Background
3D Texture Proxy Geometry was popularized by Cabral et al. in 1994 for nonshaded volume rendering [S1, unofficial][S15]. It was examined on the SGI RealityEngine, the first hardware to implement 3D texture mapping [S2, S14, unofficial]. The method became mainstream with the introduction of affordable GPUs supporting 3D textures, such as the ATI Radeon (2000) and NVIDIA GeForce 3 [S4, S14, unofficial]. It was included in OpenGL 1.2 [S4, S17, unofficial]. Modern implementations often use vertex shaders to compute proxy geometry and fragment shaders for transfer function lookups [S2, unofficial][S18].
