# 3D Texture Proxy Geometry

Also called: 3D Texture Proxy, 3D Texture-Based Volume Rendering, 3D Texture Volume Rendering, 3D Texture Mapping for Volume Rendering, Direct Volume Rendering via 3D Textures

## Overview
3D Texture Proxy Geometry is a direct volume rendering method that represents a rectilinear volume as a stack of parallel planar polygons (slabs) textured with 3D texture maps, leveraging hardware-accelerated tri-linear interpolation to sample volume data at arbitrary locations [S2, S3, unofficial]. It solves the problem of efficient hardware-accelerated volume rendering with directional lighting by pre-computing color and opacity per voxel and storing them in 3D textures, allowing the graphics pipeline to handle interpolation and compositing [S3, unofficial]. Unlike shear-warp methods which fix plane counts to volume resolution, this method allows the number of rendering planes to be adjusted at runtime independent of volume resolution, and unlike coherent projection, it supports perspective views without a time penalty, though perspective projection causes irregular sampling along rays [S3, unofficial][S4, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A rectilinear volume dataset of dimensions $n_x \times n_y \times n_z$ with spacing $\Delta x, \Delta y, \Delta z$. A viewing direction defined by a rotation matrix $R$.
*   **Output:** A 2D image where each pixel contains the accumulated color and opacity of the volume along the viewing ray.

**Data Structures:**
1.  **3D Texture Object:** A single 3D texture object in GPU memory.
    *   **Dimensions:** $(N_x, N_y, N_z)$, where $N_i$ is the smallest power of two such that $N_i \ge n_i$ [S3, S17, unofficial].
    *   **Internal Format:** Matches the input data type (e.g., `GL_R16UI` for unsigned short) [S5, unofficial].
    *   **Filtering:** `GL_LINEAR` for minification and magnification to enable tri-linear interpolation [S2, S5, unofficial].
2.  **Proxy Geometry:** A set of 2D polygons (quads) representing slices through the volume.
    *   **Vertices:** Each vertex has 3D spatial coordinates $(x, y, z)$ and associated 3D texture coordinates $(s, t, r)$ [S12, S18].
    *   **Layout:** The polygons are arranged in a stack parallel to the image plane (viewport-aligned) [S13, unofficial][S15].

**Numbered Steps:**

1.  **Pre-classification (Optional but Recommended):**
    Apply the transfer function to the raw volume data on the CPU to compute color $(C)$ and opacity $(A)$ for each voxel. Store these values in the 3D texture. If post-classification is used, store raw data and perform lookup in the fragment shader [S1, unofficial][S18].

2.  **Texture Upload:**
    Upload the volume data to the GPU as a 3D texture object.
    *   Set wrap modes to `GL_CLAMP_TO_EDGE` to prevent sampling errors at boundaries [S5, unofficial].
    *   Set min/mag filters to `GL_LINEAR` [S2, S5, unofficial].
    *   Note: The `depth` parameter in `glTexImage3D` corresponds to the first dimension of the array; passing the wrong dimension causes index confusion [S5, unofficial].

3.  **Bounding Cube Definition:**
    Define a bounding cube centered at the origin with side length $d = \sqrt{L_x^2 + L_y^2 + L_z^2}$, where $L_i = N_i \Delta i$ [S3, unofficial]. This cube must contain the entire volume during any rotation [S17, unofficial].

4.  **View-Dependent Slice Generation:**
    Compute a series of polygons that cut through the volume perpendicular to the current viewing direction [S7, S8, S9, S10].
    *   The number of slices $N_{slices}$ is typically chosen as $d / \Delta z$ (for uniform spacing) or adjusted to match the texel dimensions [S3, unofficial][S7, S8].
    *   For each slice, determine the intersection with the bounding cube to form a polygon (typically a quad or clipped polygon) [S2, S14, unofficial].
    *   Compute the 3D texture coordinates $(s, t, r)$ for each vertex of the polygon.

5.  **Texture Coordinate Transformation:**
    Map world coordinates $(x, y, z)$ to texture coordinates $(s, t, r)$ using a transformation matrix. For a volume in its original orientation, the mapping is:
    $$
    s(x) = \frac{x + \frac{1}{2}n_x \Delta x}{N_x \Delta x}, \quad t(y) = \frac{y + \frac{1}{2}n_y \Delta y}{N_y \Delta y}, \quad r(z) = \frac{z + \frac{1}{2}n_z \Delta z}{N_z \Delta z}
    $$
    [S3, unofficial].
    
    For an arbitrary viewing angle defined by rotation matrix $R$, the transformation is:
    $$
    (s, t, r) = (x, y, z) R^{-1} D^{-1} S T
    $$
    where $D$ is uniform scaling by $d$, $S$ is non-uniform scaling by $(d/L_x, d/L_y, d/L_z)$, and $T$ is translation by $(\frac{n_x}{2N_x}, \frac{n_y}{2N_y}, \frac{n_z}{2N_z})$ [S3, unofficial].
    
    *Critical:* If the volume has non-uniform spacing ($\Delta x \neq \Delta y \neq \Delta z$), the scaling matrix $S$ does not commute with rotation. The correct order of operations is **rotation first, then scaling** to avoid shearing distortion [S3, unofficial].

6.  **Clipping:**
    Use six programmable world-space clipping planes positioned at the faces of the volume bounding box to clip out parts of the rendered squares that lie outside the volume [S3, unofficial]. This avoids rendering empty space and artifacts from clipped edges [S3, S4, unofficial].

7.  **Rasterization and Blending:**
    *   Disable lighting and depth buffer writing (enable depth testing only if compositing over opaque geometry) [S18].
    *   Enable alpha blending with equation: $Src = 1$, $Dst = 1 - SrcAlpha$ [S18].
    *   Render the proxy polygons from **back to front** relative to the viewer [S1, S6, S13, unofficial].
    *   The graphics hardware performs tri-linear interpolation of the $(s, t, r)$ coordinates across the polygon [S12].
    *   The interpolated coordinates are used as dependent texture lookups into the 3D texture to fetch color and opacity [S6, unofficial][S18].
    *   If pre-classified, the fetched values are blended. If post-classified, the fragment shader applies the transfer function to the fetched scalar value and then blends [S18].

**Pseudocode:**

```python
def render_3d_texture_proxy(volume_data, view_matrix, num_slices):
    # 1. Setup 3D Texture
    # Determine power-of-two dimensions
    Nx = next_power_of_two(volume_data.dim_x)
    Ny = next_power_of_two(volume_data.dim_y)
    Nz = next_power_of_two(volume_data.dim_z)
    
    # Calculate bounding cube diagonal
    Lx = Nx * volume_data.spacing_x
    Ly = Ny * volume_data.spacing_y
    Lz = Nz * volume_data.spacing_z
    d = sqrt(Lx**2 + Ly**2 + Lz**2)
    
    # Create and upload texture
    tex_id = create_3d_texture(Nx, Ny, Nz, volume_data.data)
    set_texture_filter(tex_id, GL_LINEAR, GL_LINEAR)
    set_texture_wrap(tex_id, GL_CLAMP_TO_EDGE)
    
    # 2. Compute Proxy Geometry
    # Inverse rotation matrix for texture coordinate transformation
    R_inv = invert(view_matrix.rotation_part)
    
    # Scaling and Translation matrices for texture coordinates
    # S scales by d/Li, T translates by ni/(2Ni)
    S = scale_matrix(d/Lx, d/Ly, d/Lz)
    T = translate_matrix(volume_data.dim_x/(2*Nx), 
                       volume_data.dim_y/(2*Ny), 
                       volume_data.dim_z/(2*Nz))
    
    # Combined transformation matrix for texture coords: R_inv * D^-1 * S * T
    # Note: D is uniform scale by d, which commutes with R, so D^-1 can be merged into S/T or handled separately.
    # The core mapping is: (s,t,r) = (x,y,z) * R_inv * D^-1 * S * T
    texture_transform = R_inv @ invert(scale_matrix(d, d, d)) @ S @ T
    
    # Generate slice polygons
    slices = []
    for i in range(num_slices):
        # Determine slice plane position in view space
        # Assuming slices are evenly spaced through the bounding cube depth
        z_slice = -d/2 + (i + 0.5) * (d / num_slices)
        
        # Compute intersection of plane with bounding cube to get polygon vertices
        # This is typically done by clipping a large quad against the 6 volume faces
        polygon_vertices = compute_slice_polygon(z_slice, view_matrix, d)
        
        # Compute texture coordinates for each vertex
        for v in polygon_vertices:
            # v is (x, y, z) in world space
            # Apply transformation to get (s, t, r)
            # Note: In OpenGL, texture coordinates are often set via glTexGen or vertex attributes
            # Here we compute them explicitly for clarity
            v.s, v.t, v.r = apply_texture_transform(v.x, v.y, v.z, texture_transform)
        
        slices.append(polygon_vertices)
    
    # 3. Render
    enable_alpha_blending(src=1, dst=1-src_alpha)
    disable_lighting()
    disable_depth_write()
    enable_depth_test() # Optional, if compositing over background
    
    bind_texture(tex_id, unit=0)
    
    # Set up clipping planes to clip against volume bounds
    setup_clipping_planes(volume_bounds)
    
    # Draw slices back-to-front
    for polygon in slices:
        draw_polygon(polygon)
        
    disable_clipping_planes()
    restore_render_state()
```

## Subtopics

### [Tri-linear Interpolation via LRP](913-tri-linear-interpolation-via-lrp.md)
Tri-linear interpolation via LRP is a GPU-accelerated method for estimating scalar values at arbitrary floating-point coordinates within a 3D volume grid by interpolating the eight surrounding voxel values. It solves the problem of sampling continuous volume data from discrete voxel grids, providing smooth rendering compared to direct voxel rendering which exhibits less structural detail. It is distinguished from other interpolation methods by its specific implementation using the GPU's LRP (linear interpolation) instruction, leveraging hardware rasterization to interpolate texture coordinates "for free" between vertices, thereby optimizing memory bandwidth usage.

### [Multi-Volume Rendering with Multiple Textures](1568-multi-volume-rendering-with-multiple-textures.md)
This method renders multiple distinct volumetric classes (e.g., tissue types) simultaneously by storing each class in a separate 3D texture and combining them during the fragment shader execution. It solves the problem of visualizing heterogeneous data where different channels require independent transfer functions and opacities. It sets itself apart from single-volume approaches by allowing independent control of each channel's appearance, and from out-of-core techniques by relying entirely on GPU memory residency for all active channels.

### [Proxy Geometry Compression](1917-proxy-geometry-compression.md)
Proxy Geometry Compression is a technique for storing volume data and proxy geometry locally in graphics hardware to avoid CPU-GPU bandwidth bottlenecks associated with immediate mode rendering. It sets itself apart from immediate-mode splatting by pre-loading compressed proxy geometry templates into GPU memory, leveraging the regularity of rectilinear volumes to achieve high compression ratios (e.g., 171:1). This allows the entire volume representation to reside in local graphics memory, enabling interactive rendering speeds that are significantly faster than sending each splat separately.

### [Sm2D (2D Volume Texture Experiment)](3150-sm2d-2d-volume-texture-experiment.md)
Sm2D is a 2-dimensional test application implemented as a 2D ray tracer to investigate the applicability of a texture-based approach for smoke volumes. It simplifies the 3D volume rendering problem into a 1D viewport function where tetrahedra are represented by triangles. It sets itself apart from its siblings by serving as a diagnostic tool to demonstrate the precision limits and rotational artifacts inherent in texture-based approximations compared to explicit geometric calculations.

## Operating characteristics
*   **Time Complexity:** Image-order rendering. Computational cost scales with the number of pixels in the output image and the number of slices, independent of the number of geometric primitives in the scene [S14, unofficial].
*   **Memory Complexity:** Requires a single 3D texture of size $N_x \times N_y \times N_z$ in GPU memory. For large volumes, this may exceed texture memory capacity, requiring partitioning into subvolumes (bricks) swapped in and out, which incurs significant overhead [S1, unofficial][S12].
*   **Measured Performance:** Historically provided tremendous speedup due to high rasterization performance, treating all viewing rays simultaneously [S6, unofficial]. On SGI InfiniteReality2, max texture size was $128^3$ voxels [S12]. Modern hardware natively supports 3D textures, but performance is specific to hardware capabilities [S6, unofficial].
*   **Strengths:**
    *   Supports arbitrary viewing angles and perspective views without the time penalty of shear-warp [S3, S4, unofficial].
    *   Eliminates 'popping' artifacts associated with switching texture sets in 2D methods [S17, unofficial].
    *   Hardware-accelerated tri-linear interpolation provides smooth sampling [S3, unofficial].
    *   Requires only one copy of the data in memory, unlike 2D-texture methods which require three [S4, unofficial][S18].
*   **Limitations:**
    *   Cannot skip unseen voxels; all voxels are rendered [S1, unofficial].
    *   Perspective projection causes irregular sampling rates along rays, leading to visual artifacts in fly-through applications [S4, S14, unofficial].
    *   Limited by texture memory size; large volumes require inefficient bricking strategies [S3, unofficial][S12].
    *   Image quality is generally lower than ray casting due to aliasing and limited optical modeling capabilities [S14, unofficial].
    *   Standard implementations perform unnecessary operations on non-contributing fragments [S14, unofficial].
*   **When to Use:** Real-time interactive rendering of reasonably sized volumes on hardware with 3D texture support, especially when directional lighting is required and the volume fits in GPU memory [S14, unofficial][S15].
*   **When Not to Use:** Very large volumes that exceed texture memory, applications requiring high-fidelity optical models (e.g., refraction), or fly-throughs with large field-of-view angles where sampling artifacts are unacceptable [S4, S14, unofficial].

## Background
3D Texture Proxy Geometry was popularized by Cabral et al. in 1994 for nonshaded volume rendering [S1, unofficial][S15]. It was examined by Cabral et al. on the SGI RealityEngine, the first hardware to implement 3D texture mapping [S2, unofficial]. The method was further optimized by Rezk-Salama et al. using vertex shaders to offload slice computation [S2, unofficial]. 3D textures were available in OpenGL as an extension (EXT texture 3D) for a long time before being included in OpenGL 1.2 [S4, unofficial]. The first consumer product with support was the ATI Radeon in spring 2000, followed by NVIDIA GeForce 3 [S4, unofficial]. Historically used by Silicon Graphics in their InfiniteReality workstations, it is now a standard technique on modern graphics hardware [S14, unofficial][S15].
