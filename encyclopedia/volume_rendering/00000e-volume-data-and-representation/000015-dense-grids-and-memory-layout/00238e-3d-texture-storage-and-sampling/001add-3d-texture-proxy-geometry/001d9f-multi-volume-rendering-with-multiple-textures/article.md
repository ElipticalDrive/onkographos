# Multi-Volume Rendering with Multiple Textures

Also called: Composición de 4 clases simultáneamente, Visualización de múltiples volúmenes utilizando texturas 3D, Viv multi-channel rendering

## Overview
This method renders multiple distinct volumetric classes (e.g., tissue types) simultaneously by storing each class in a separate 3D texture and combining them during the fragment shader execution. It solves the problem of visualizing heterogeneous data where different channels require independent transfer functions and opacities. It sets itself apart from single-volume approaches by allowing independent control of each channel's appearance, and from out-of-core techniques by relying entirely on GPU memory residency for all active channels [S1, S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** $N$ 3D textures, where each texture stores the scalar field (opacity/density) for one specific class. Each texture is bound to a distinct texture unit.
*   **Input:** A set of $N$ transfer function parameters (colors and opacities) for each class.
*   **Input:** Ray coordinates (texture coordinates) generated by the proxy geometry.
*   **Output:** A single RGBA color value per fragment, representing the accumulated color of all classes along the ray.

**Data Structures:**
*   **Textures:** $N$ instances of `sampler3D`. The internal format is not strictly defined by the method but is constrained by hardware limits.
*   **Uniforms:** An array of color vectors, `tissueColor[N]`, where each element contains the RGB color and alpha opacity for the corresponding class.

**Steps:**
1.  **Texture Binding:** Assign an independent texture unit for each class in the rendering context. In OpenGL, this is done using `glActiveTextureARB` followed by binding the specific 3D texture to the active unit [S2, unofficial].
2.  **Primitive Drawing:** Draw the proxy geometry (e.g., view-aligned slices or quads) that covers the volume of interest [S2, unofficial].
3.  **Sampling:** For each fragment, sample the scalar value (luminance/opacity) from each of the $N$ textures using the fragment's texture coordinates [S2, unofficial].
4.  **Color Computation:** Multiply the sampled scalar value by the pre-defined color and opacity for that class [S2, unofficial].
5.  **Accumulation:** Sum the resulting color vectors from all classes to produce the final output color [S2, unofficial].

**Formulas:**
Let $C_i$ be the color vector (RGB) and $\alpha_i$ be the opacity scalar for class $i$.
Let $L_i$ be the sampled scalar value (luminance/opacity) from texture $i$ at the current coordinate.
The contribution color $K_i$ for class $i$ is:
$$ K_i = \text{float4}(C_i.rgb \cdot L_i.r, C_i.a \cdot L_i.r) $$
The final output color $K_{final}$ is:
$$ K_{final} = \sum_{i=1}^{N} K_i $$

**Parameters:**
*   **Number of Channels ($N$):** Limited by the number of available texture bind points. WebGL 2.0 guarantees a minimum of 8 [S1, unofficial]. Older hardware like GeForce FX supports up to 4 with ARB multitexture or up to 16 with NV fragment program extensions [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Memory Limits:** The method does not employ out-of-core techniques. It is strictly limited by the available GPU memory [S1, unofficial]. Large-scale datasets may not fit if the number of channels is high.
*   **Hardware Limits:** The maximum number of simultaneous textures is hardware-dependent [S2, unofficial].
*   **Shader Adaptation:** Unlike some modern frameworks, this method may require manual adaptation of the fragment shader to handle different numbers of channels or specific channel switching at runtime [S1, unofficial].

**Pseudocode:**
> **Unverified code.** The code below did not pass a test run against a reference implementation, or no test fits it, so it may contain errors.

```python
# Fragment Shader Logic
# Inputs:
#   texCoord: float3, texture coordinates from vertex shader
#   tissueColor: array of float4, size N. Each element is [R, G, B, A] for a class.
#   textures: array of sampler3D, size N. Each sampler corresponds to a class.

def render_multi_volume(texCoord, tissueColor, textures):
    final_color = float4(0.0, 0.0, 0.0, 0.0)
    
    # Iterate over all active classes
    for i in range(len(textures)):
        # Sample the scalar value (opacity/luminance) from the i-th texture
        # Note: tex3D returns a float4, we use the red channel as the scalar value
        luminance = tex3D(textures[i], texCoord).r
        
        # Calculate color contribution for this class
        # Color = BaseColor * Luminance
        # Alpha = BaseAlpha * Luminance
        color_contribution = float4(
            tissueColor[i].rgb * luminance,
            tissueColor[i].a * luminance
        )
        
        # Accumulate
        final_color = final_color + color_contribution
        
    return final_color
```

## Subtopics

### Viv Multi-Channel Rendering
A web-based implementation using this method. It supports runtime channel switching by changing texture bindings but lacks out-of-core support [S1, unofficial].

### Neuroglancer Multi-Channel
Uses the same multi-texture accumulation technique but adds bricking for data management. It chooses a global resolution level per frame, which can lead to suboptimal working sets [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of channels $N$ per fragment, as $N$ texture fetches and additions are performed.
*   **Memory Complexity:** $O(N \cdot V)$, where $V$ is the volume of the data. All $N$ textures must reside in GPU memory simultaneously [S1, unofficial].
*   **Strengths:** Simple implementation; allows independent transfer functions per class; supports runtime channel switching [S1, unofficial].
*   **Limitations:** Strictly limited by GPU memory capacity; no out-of-core support; hardware-dependent maximum channel count [S1, S2, unofficial].
*   **When to use:** Small to medium-sized datasets where all channels fit in GPU memory and independent class visualization is required.
*   **When not to use:** Large-scale datasets requiring out-of-core streaming or when the number of channels exceeds hardware texture unit limits [S1, unofficial].

## Background
The technique originates from early GPU volume rendering research, specifically utilizing OpenGL's multitexturing capabilities. It was documented in the context of visualizing biomedical data with multiple tissue classes (gray matter, muscle, skin, fat, bone) using GeForce FX hardware [S2, unofficial]. It is also referenced in modern web-based volume renderers like Viv and Neuroglancer [S1, unofficial].
