# 3D Texture Storage and Sampling

Also called: 3D image storage, hardware-accelerated volume sampling, tri-linear texture sampling

## Overview
3D Texture Storage and Sampling maps a discrete volumetric field $f(\mathbf{x})$ to GPU hardware-accelerated 3D texture resources, enabling efficient spatial queries via built-in interpolation [S1, S2, unofficial]. It solves the problem of memory bandwidth bottlenecks in ray traversal by leveraging hardware caches optimized for spatial locality, which outperform software-managed layouts like Z-order curves [S1, unofficial]. Unlike bricking or chunk-based structures that manage memory hierarchy explicitly, this method delegates locality optimization to the graphics driver and hardware, trading explicit control for significant performance gains in regular grid rendering [S1, unofficial].

## How it works
**Inputs:**
*   Volumetric data: A 3D array of scalar or vector values (e.g., density, color, gradient).
*   Grid dimensions: $(W, H, D)$ representing the number of voxels in x, y, and z directions.
*   Coordinate system: Typically normalized to $[0, 1]$ or $[-1, 1]$ depending on the graphics API [G].

**Outputs:**
*   A GPU 3D texture object (e.g., `GL_TEXTURE_3D` or `VK_IMAGE_TYPE_3D`) containing the voxel data.
*   Sampled values $V(\mathbf{p})$ at arbitrary query points $\mathbf{p} \in [0, 1]^3$ using tri-linear interpolation.

**Data Structures:**
The data is stored in a 3D texture resource. The internal memory layout is determined by the GPU driver, often using sophisticated tiling or swizzling patterns superior to simple Z-order curves to maximize cache hit rates for neighboring voxel accesses [S1, unofficial]. The logical layout remains a 3D grid where index $(i, j, k)$ maps to a specific memory location.

**Steps:**
1.  **Allocation:** Allocate a 3D texture object with dimensions $(W, H, D)$ and appropriate internal format (e.g., `GL_RGBA32F`, `GL_R8`) matching the data precision [S1, S2, unofficial].
2.  **Upload:** Transfer the host-side voxel array to the GPU texture memory using a bulk copy operation (e.g., `glTexSubImage3D`, `vkCmdCopyBufferToImage`) [S1, S2, unofficial].
3.  **Configuration:** Set filtering modes to `GL_LINEAR` (or equivalent) to enable tri-linear interpolation and wrap modes to `GL_CLAMP_TO_EDGE` to handle boundary queries safely [G].
4.  **Sampling:** In the rendering shader, compute normalized texture coordinates $\mathbf{u} = \frac{\mathbf{x} - \mathbf{x}_{min}}{\mathbf{x}_{max} - \mathbf{x}_{min}}$ for a world-space position $\mathbf{x}$ [G].
5.  **Interpolation:** Sample the texture using the hardware sampler: $V = \text{tex3D}(tex, \mathbf{u})$. The hardware performs tri-linear interpolation across the 8 neighboring voxels based on the fractional part of $\mathbf{u}$ [S2, unofficial].

**Formulas:**
Tri-linear interpolation at normalized coordinate $\mathbf{u} = (u, v, w)$:
$$ V(\mathbf{u}) = \sum_{i=0}^{1} \sum_{j=0}^{1} \sum_{k=0}^{1} w_i(u) w_j(v) w_k(w) V_{ijk} $$
where $w_0(u) = 1-u$, $w_1(u) = u$, and $V_{ijk}$ is the value at the grid corner $(\lfloor u \cdot W \rfloor + i, \lfloor v \cdot H \rfloor + j, \lfloor w \cdot D \rfloor + k)$ [S2, unofficial].

**Parameters:**
*   **Filtering:** Tri-linear (standard) or nearest-neighbor (for discrete voxel art or specific artistic styles) [S1, S2, unofficial].
*   **Precision:** 8-bit unsigned (density), 16-bit float (half-precision), or 32-bit float (high dynamic range) [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Boundary Conditions:** Queries outside $[0, 1]$ must be clamped or handled explicitly to avoid undefined behavior or artifacts [G].
*   **Precision Loss:** Using 8-bit textures for high-dynamic-range data may introduce banding artifacts during integration [S1, unofficial].
*   **Memory Limits:** Maximum texture dimensions are hardware-dependent (e.g., 2048 or 4096 in older APIs, higher in modern Vulkan/DirectX) [S5, unofficial].

**Pseudocode:**
```python
# Initialization (Host Side)
def setup_3d_texture(width, height, depth, data_array):
    # 1. Allocate 3D texture object
    texture_id = glCreateTexture(GL_TEXTURE_3D)
    
    # 2. Allocate memory and specify layout
    # Internal format depends on data type (e.g., GL_RGBA32F for float4)
    glTexImage3D(
        GL_TEXTURE_3D, 
        0, 
        GL_RGBA32F, 
        width, height, depth, 
        0, 
        GL_RGBA, 
        GL_FLOAT, 
        None # Empty allocation
    )
    
    # 3. Upload data
    # data_array is a contiguous 1D buffer of the 3D grid
    glTexSubImage3D(
        GL_TEXTURE_3D, 
        0, 
        0, 0, 0, 
        width, height, depth, 
        GL_RGBA, 
        GL_FLOAT, 
        data_array
    )
    
    # 4. Set filtering for tri-linear interpolation
    glTexParameteri(GL_TEXTURE_3D, GL_TEXTURE_MIN_FILTER, GL_LINEAR)
    glTexParameteri(GL_TEXTURE_3D, GL_TEXTURE_MAG_FILTER, GL_LINEAR)
    glTexParameteri(GL_TEXTURE_3D, GL_TEXTURE_WRAP_S, GL_CLAMP_TO_EDGE)
    glTexParameteri(GL_TEXTURE_3D, GL_TEXTURE_WRAP_T, GL_CLAMP_TO_EDGE)
    glTexParameteri(GL_TEXTURE_3D, GL_TEXTURE_WRAP_R, GL_CLAMP_TO_EDGE)
    
    return texture_id

# Sampling (Shader Side Conceptual)
def sample_volume(texture_id, world_position, volume_bounds):
    # Normalize world position to [0, 1]
    u = (world_position.x - volume_bounds.min.x) / (volume_bounds.max.x - volume_bounds.min.x)
    v = (world_position.y - volume_bounds.min.y) / (volume_bounds.max.y - volume_bounds.min.y)
    w = (world_position.z - volume_bounds.min.z) / (volume_bounds.max.z - volume_bounds.min.z)
    
    # Clamp to handle boundary errors
    u = clamp(u, 0.0, 1.0)
    v = clamp(v, 0.0, 1.0)
    w = clamp(w, 0.0, 1.0)
    
    # Hardware tri-linear interpolation
    value = texture(texture_id, vec3(u, v, w))
    
    return value
```

### Texture Array Sampling with Alpha Discard
Samples a texture array in a GLSL fragment shader, discarding transparent pixels below a threshold ($\alpha < 0.01$) to optimize rendering [S3, unofficial].

### Ambient Occlusion Volume
Stores precomputed ambient occlusion factors (and optionally bent normals) directly in a 3D texture to avoid runtime reconstruction costs [S4, unofficial].

### Sparse Volume Texture (SVT)
Compresses voxel data into tiles for large datasets; limited by signed int32 overflow at ~2 gigavoxels and uint32 at ~4GB upload buffers [S5, unofficial].

### Splat Texture Layout & Mapping
Maps splat data to two 3D textures backed by Uint32Arrays, where each splat corresponds to two 16-byte records [S6, unofficial].

## Operating characteristics
*   **Time Complexity:** Sampling is $O(1)$ per query due to hardware interpolation [S1, unofficial].
*   **Memory Complexity:** $O(W \times H \times D \times B)$, where $B$ is bytes per voxel [S1, unofficial].
*   **Performance:** Achieves 121 FPS at $2048^3$ resolution and $1000 \times 1000$ screen resolution, a 10x improvement over Z-order curve implementations (12 FPS) [S1, unofficial].
*   **Strengths:** High hardware optimization for data locality; simple API; fast tri-linear interpolation [S1, S2, unofficial].
*   **Limitations:** Fixed resolution; high memory consumption for large volumes; no explicit control over cache eviction [S1, unofficial].
*   **When to Use:** Real-time rendering of dense, regular grids where memory bandwidth is the bottleneck [S1, unofficial].
*   **When Not to Use:** Sparse volumes (use bricking/chunks) or extremely large datasets exceeding VRAM (use out-of-core) [S5, unofficial].

## Background
Originated with the adoption of 3D texture hardware in GPUs, allowing direct storage of volumetric data in texture units [S1, unofficial]. Popularized in real-time volume rendering as a replacement for software-managed memory layouts like Z-order curves, which suffered from cache inefficiencies [S1, unofficial]. Used extensively in modern real-time raycasting and slicing-based volume rendering pipelines [S2, S5, unofficial].
