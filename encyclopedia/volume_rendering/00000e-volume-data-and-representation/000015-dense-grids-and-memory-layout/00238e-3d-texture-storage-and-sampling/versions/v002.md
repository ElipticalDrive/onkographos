# 3D Texture Storage and Sampling

Also called: 3D image storage, GPU 3D texture, hardware-accelerated volume sampling

## Overview
3D Texture Storage and Sampling maps a discretized volumetric field $f(\mathbf{x})$ into a GPU-accessible 3D texture object, leveraging hardware-optimized memory layouts and tri-linear interpolation to evaluate $f(\mathbf{x})$ at arbitrary coordinates [S1, S2, unofficial]. It sets itself apart from CPU-side dense grids by utilizing sophisticated hardware caching and locality optimizations that significantly outperform software implementations or simpler Z-order curves, and from [Bricking](914-bricking.md) by treating the volume as a single contiguous texture resource rather than a hierarchy of independent blocks [S1, unofficial].

## How it works
**Inputs:**
*   Volumetric data array $V$ of dimensions $W \times H \times D$.
*   Data type (e.g., 8-bit unsigned integer, 16-bit float, 32-bit float) [S1, S2, unofficial].
*   Texture parameters (filtering mode, coordinate wrapping) [S1, unofficial].

**Outputs:**
*   A GPU 3D texture object bound to a sampler.
*   Interpolated scalar or vector values $V(\mathbf{x})$ for any $\mathbf{x} \in [0, 1]^3$ [S1, S2, unofficial].

**Data Structures:**
The volume is stored in a 3D texture object. The internal memory layout is managed by the GPU driver and is optimized for data locality, often employing strategies more sophisticated than simple Z-order (Morton) curves to ensure that spatially adjacent voxels are stored in adjacent memory locations, improving cache hit rates during ray traversal [S1, unofficial].

**Steps:**
1.  **Allocation:** Allocate a 3D texture object on the GPU with dimensions matching the volume resolution $(W, H, D)$ and the specified internal format (e.g., `GL_RGBA32F`, `GL_R8`) [S1, S2, unofficial].
2.  **Upload:** Transfer the host-side volumetric data array $V$ to the GPU texture memory. This is typically done via `glTexImage3D` or equivalent API calls [S1, S2, unofficial].
3.  **Configuration:** Set texture parameters:
    *   **Filtering:** Enable tri-linear interpolation (`GL_LINEAR`) to allow smooth sampling between voxel centers [S2, unofficial].
    *   **Wrapping:** Set wrapping modes (e.g., `GL_CLAMP_TO_EDGE`) to handle boundary conditions [G].
4.  **Sampling:** In the rendering shader (e.g., fragment shader), sample the texture at normalized coordinates $\mathbf{u} \in [0, 1]^3$:
    $$ V(\mathbf{u}) = \text{texture}(\text{sampler3D}, \mathbf{u}) $$
    The hardware performs tri-linear interpolation using the 8 neighboring voxels of $\mathbf{u}$ [S2, unofficial].

**Formulas:**
Tri-linear interpolation at coordinate $\mathbf{u} = (u, v, w)$ within a voxel defined by corners $(0,0,0)$ to $(1,1,1)$:
$$ V(\mathbf{u}) = \sum_{i,j,k \in \{0,1\}} w_i w_j w_k V_{ijk} $$
where $w_u = u, w_v = v, w_w = w$, and $V_{ijk}$ are the voxel values at the grid corners [S2, S3, unofficial].

**Parameters:**
*   **Filtering Mode:** `GL_LINEAR` (tri-linear) is standard for volume rendering to ensure continuity [S2, unofficial]. `GL_NEAREST` is used for speed or specific discrete effects [S3, unofficial].
*   **Coordinate System:** Coordinates are typically normalized to $[0, 1]$ for texture sampling [G].

**Edge Cases and Pitfalls:**
*   **Boundary Conditions:** Sampling outside $[0, 1]$ requires defined wrapping behavior. `GL_CLAMP_TO_EDGE` is standard to prevent artifacts [G].
*   **Precision:** The choice of internal format (e.g., 8-bit vs. 32-bit float) affects dynamic range and quantization error [S1, unofficial].
*   **Memory Limits:** Large volumes may exceed GPU memory limits. For example, in-core implementations of sparse volume textures can crash at ~2 gigavoxels due to signed int32 overflow, and upload buffers may hit uint32 limits at 4 GB [S5, unofficial].

**Pseudocode:**
```python
# Pseudocode for setting up and sampling a 3D texture
# Assumes a graphics API context (e.g., OpenGL/Vulkan/DirectX) is initialized

def setup_3d_texture(width, height, depth, data_array):
    """
    Allocates and uploads volumetric data to a GPU 3D texture.
    
    Args:
        width, height, depth: Dimensions of the volume.
        data_array: Host-side array of voxel values.
        
    Returns:
        texture_id: Handle to the GPU 3D texture.
    """
    # 1. Generate texture ID
    texture_id = generate_texture_id()
    
    # 2. Bind the texture
    bind_texture(GL_TEXTURE_3D, texture_id)
    
    # 3. Allocate memory and upload data
    # Internal format depends on data type (e.g., GL_RGBA32F for floats)
    glTexImage3D(
        target=GL_TEXTURE_3D,
        level=0,
        internal_format=GL_RGBA32F, # Example format
        width=width,
        height=height,
        depth=depth,
        border=0,
        format=GL_RGBA,
        type=GL_FLOAT,
        data=data_array
    )
    
    # 4. Set filtering for tri-linear interpolation
    glTexParameteri(GL_TEXTURE_3D, GL_TEXTURE_MIN_FILTER, GL_LINEAR)
    glTexParameteri(GL_TEXTURE_3D, GL_TEXTURE_MAG_FILTER, GL_LINEAR)
    
    # 5. Set wrapping mode to clamp to edge
    glTexParameteri(GL_TEXTURE_3D, GL_TEXTURE_WRAP_S, GL_CLAMP_TO_EDGE)
    glTexParameteri(GL_TEXTURE_3D, GL_TEXTURE_WRAP_T, GL_CLAMP_TO_EDGE)
    glTexParameteri(GL_TEXTURE_3D, GL_TEXTURE_WRAP_R, GL_CLAMP_TO_EDGE)
    
    return texture_id

def sample_volume(texture_id, u, v, w):
    """
    Samples the 3D texture at normalized coordinates.
    
    Args:
        texture_id: Handle to the GPU 3D texture.
        u, v, w: Normalized coordinates in [0, 1].
        
    Returns:
        value: Interpolated voxel value.
    """
    # In a shader, this would be: texture(sampler3D, vec3(u, v, w))
    # Here we describe the logical operation
    normalized_coords = (u, v, w)
    value = hardware_trilinear_interpolation(texture_id, normalized_coords)
    return value
```

## Subtopics

### [3D Texture Proxy Geometry](870-3d-texture-proxy-geometry.md)
Represents a rectilinear volume as a stack of parallel planar polygons (slabs) textured with 3D texture maps. It leverages hardware-accelerated tri-linear interpolation to sample volume data, allowing the number of rendering planes to be adjusted at runtime independent of volume resolution.

### [AR mapping to 3D texture](884-ar-mapping-to-3d-texture.md)
Maps scalar data (color and opacity) into a 3D texture object to avoid complex non-linear formulae during rendering. It relies on direct texture coordinate mapping rather than geometric proxy approximation.

### [Volume Texture Creation](1857-volume-texture-creation.md)
The process of allocating GPU memory and populating it with volumetric data and rendering targets. It focuses on API-level allocation and data upload steps rather than the sampling logic.

### [Texture Uniting (Multi-Channel Packing)](2470-texture-uniting-multi-channel-packing.md)
Combines multiple separate 3D textures (e.g., noise, detail, light) into a single RGBA 3D texture to optimize for simultaneous access patterns and reduce memory bandwidth consumption.

### [PixelFlow Volume Rendering](3443-pixelflow-volume-rendering.md)
A polygon-based resampling method for the PixelFlow graphics system that performs trilinear interpolation and Phong shading in software on dedicated pixel processors.

### [Hardware Volume Rendering Pipeline with Pixel Textures](5641-hardware-volume-rendering-pipeline-with-pixel-textures.md)
Implements volume rendering on hardware supporting pixel textures (dependent textures), using color fragments to generate texture coordinates for lookups from a 3D texture, often requiring rendering slices to an auxiliary buffer first.

### [3D Transfer Function Texture Layout](5646-3d-transfer-function-texture-layout.md)
Defines the memory layout for hardware-based volume rendering using multi-dimensional transfer functions, storing pre-computed auxiliary data (e.g., normals) at each voxel sample point.

### [Memory Organization and Layout](7154-memory-organization-and-layout.md)
Not given in the sources.

### [3D Volume Atlas Packing](7158-3d-volume-atlas-packing.md)
Packs multiple volumes or timesteps into a single 3D texture by calculating a 3D grid resolution and allocating a flat buffer.

#### Texture Array Sampling with Alpha Discard
Samples a texture array in a GLSL fragment shader, discarding transparent pixels below a threshold (approx 0.01) to optimize rendering. It uses `vec3(in_var_TEXCOORD0, float(in_var_TEXCOORD1))` for sampling and outputs color with alpha [S3, unofficial].

#### Ambient Occlusion Volume
Stores precomputed ambient occlusion factors (and optionally bent normals) directly in a 3D texture, avoiding runtime reconstruction computation and reducing runtime cost compared to methods like Kontkanen and Laine's [S4, unofficial].

#### Sparse Volume Texture (SVT)
An in-core implementation that compresses voxel data into tiles to reduce memory footprint. It faces limits due to signed int32 overflow at ~2 gigavoxels and uint32 overflow at 4 GB for upload buffers, requiring out-of-core implementations for true large-scale rendering [S5, unofficial].

#### Splat Texture Layout & Mapping
Maps splat data to two 3D textures backed by Uint32Arrays, where each splat corresponds to two 16-byte texture records. It calculates layer bits using `SPLAT_TEX_WIDTH_BITS` and height to determine capacity [S6, unofficial].

## Operating characteristics
*   **Time Complexity:** Sampling is $O(1)$ per query due to hardware interpolation [S1, unofficial].
*   **Memory Complexity:** $O(W \times H \times D)$, where $W, H, D$ are volume dimensions [S1, unofficial].
*   **Performance:** Storing voxels in a 3D texture on the GPU can yield significant performance improvements over CPU-side or Z-order optimized software implementations. For example, one implementation reported 121 FPS at $2048^3$ grid resolution and $1000 \times 1000$ screen resolution, a 10x improvement over the original 12 FPS [S1, unofficial].
*   **Strengths:** High performance due to hardware acceleration, efficient data locality, and simplified shader code [S1, S2, unofficial].
*   **Limitations:** Limited by GPU memory capacity. Large volumes may require out-of-core techniques or compression (e.g., SVT) [S5, unofficial]. Precision is limited by the chosen internal format [S1, unofficial].
*   **When to use:** Real-time volume rendering on GPUs where performance is critical and volume size fits within GPU memory [S1, unofficial].
*   **When not to use:** When volume size exceeds GPU memory limits and out-of-core techniques are not feasible, or when extremely high precision is required beyond the capabilities of standard texture formats [S5, unofficial].

## Background
The method originated with the need for efficient real-time volume rendering on GPUs. Early implementations used CPU-side traversal, but the shift to GPU-based rendering leveraged the hardware's optimized texture units. The use of 3D textures specifically was highlighted as a significant optimization over Z-order curves, providing better data locality and cache performance [S1, unofficial]. The technique is widely used in medical imaging, scientific visualization, and real-time graphics [S1, S2, unofficial].
