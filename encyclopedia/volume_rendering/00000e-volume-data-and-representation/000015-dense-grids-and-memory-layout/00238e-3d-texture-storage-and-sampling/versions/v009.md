# 3D Texture Storage and Sampling

Also called: 3D image storage, GPU 3D texture mapping

## Overview
3D Texture Storage and Sampling maps a discrete volumetric field $f(\mathbf{x})$ to GPU hardware 3D texture resources, leveraging hardware-accelerated tri-linear interpolation to sample values at arbitrary coordinates [S1, S2, S3, S4, unofficial]. It solves the problem of efficient data locality and memory bandwidth utilization by replacing software-managed linear arrays or Z-order curves with GPU-native texture units that optimize cache coherence for neighboring voxel access [S1, unofficial]. Unlike [Bricking](914-bricking.md) which manages memory hierarchy via software-defined tiles, or [Evaluation Cache](874-evaluation-cache.md) which caches computed results, this method relies on the graphics API's internal texture management for spatial coherence [S1, unofficial]. It differs from [3D Texture Proxy Geometry](870-3d-texture-proxy-geometry.md) by treating the volume as a continuous texture field sampled during ray marching, rather than a discrete set of textured polygons [S3, unofficial].

## How it works
**Inputs:**
*   Volumetric data array $V$ of dimensions $D_x \times D_y \times D_z$.
*   Data type (e.g., 8-bit unsigned integer, 16-bit float, 32-bit float) [S1, S4, unofficial].
*   Texture coordinate system (typically normalized $[0, 1]$ or $[0, 1]^3$) [G].

**Outputs:**
*   GPU 3D texture object bound to a texture unit.
*   Interpolated scalar or vector values $V(\mathbf{u})$ for texture coordinates $\mathbf{u} \in [0, 1]^3$ [S2, S4, unofficial].

**Data Structures:**
The volume data is stored in a 3D texture resource. The layout is determined by the GPU API (e.g., OpenGL, Vulkan, DirectX).
*   **Dimensions:** The texture dimensions $W, H, D$ are typically powers of two or match the volume resolution, subject to hardware limits (e.g., max dimension 2048 or 4096) [S1, S4, unofficial].
*   **Internal Format:** Matches the data type of $V$ (e.g., `GL_RGB`, `GL_RGBA`, `GL_R32F`) [S4, unofficial].
*   **Filtering:** Tri-linear interpolation is enabled to allow smooth sampling between voxel centers [S2, S3, S4, unofficial].

**Steps:**
1.  **Allocation:** Allocate a 3D texture object on the GPU with dimensions matching the volume resolution or a power-of-two approximation [S4, unofficial].
2.  **Upload:** Copy the host-side volumetric data array $V$ into the GPU texture memory using a bulk transfer operation (e.g., `glTexImage3D`, `vkCmdCopyBufferToImage`) [S2, S4, unofficial].
3.  **Configuration:** Set texture parameters:
    *   Minification/Magnification filter to `LINEAR` (tri-linear) [S4, unofficial].
    *   Wrap mode to `CLAMP_TO_EDGE` to handle boundary conditions [G].
4.  **Sampling:** In the shader, sample the texture at normalized coordinates $\mathbf{u} = (u, v, w)$:
    $$ V(\mathbf{u}) = \text{texture}(Tex, \mathbf{u}) $$
    where $\mathbf{u}$ is derived from the world position $\mathbf{x}$ via:
    $$ \mathbf{u} = \frac{\mathbf{x} - \mathbf{x}_{min}}{\mathbf{x}_{max} - \mathbf{x}_{min}} $$
    [S2, S4, unofficial].

**Parameters:**
*   **Rendering Scale:** In some implementations, a scale parameter $S$ maps voxel indices to texture coordinates, allowing multiple voxels to map to a single texture unit or vice versa [S2, unofficial].
*   **Mipmap Generation:** Optional, but often disabled for volume rendering to preserve high-frequency detail, or generated for coarse-level culling [G].

**Edge Cases and Pitfalls:**
*   **Boundary Conditions:** Accessing coordinates outside $[0, 1]^3$ requires clamping to avoid wrapping artifacts [G].
*   **Resolution Limits:** If the volume dimensions exceed the GPU's maximum 3D texture size, the volume must be split or compressed (e.g., using [Sparse Volume Texture](7011-sparse-volume-texture-svt.md)) [S1, unofficial].
*   **Precision:** Low-precision formats (e.g., 8-bit) may introduce banding artifacts in smooth gradients [G].

**Pseudocode:**
```python
# Initialization
def init_3d_texture(volume_data, dims):
    """
    Allocates and uploads volume data to a GPU 3D texture.
    volume_data: numpy array of shape (Dx, Dy, Dz)
    dims: tuple (W, H, D) for texture dimensions
    """
    # 1. Generate texture ID
    tex_id = glGenTextures(1)
    
    # 2. Bind and allocate
    glBindTexture(GL_TEXTURE_3D, tex_id)
    glTexImage3D(
        GL_TEXTURE_3D, 
        0, 
        GL_RGB, # Internal format
        dims[0], dims[1], dims[2], 
        0, 
        GL_RGB, 
        GL_UNSIGNED_BYTE, 
        volume_data.ctypes.data
    )
    
    # 3. Set filtering for tri-linear interpolation
    glTexParameteri(GL_TEXTURE_3D, GL_TEXTURE_MIN_FILTER, GL_LINEAR)
    glTexParameteri(GL_TEXTURE_3D, GL_TEXTURE_MAG_FILTER, GL_LINEAR)
    glTexParameteri(GL_TEXTURE_3D, GL_TEXTURE_WRAP_S, GL_CLAMP_TO_EDGE)
    glTexParameteri(GL_TEXTURE_3D, GL_TEXTURE_WRAP_T, GL_CLAMP_TO_EDGE)
    glTexParameteri(GL_TEXTURE_3D, GL_TEXTURE_WRAP_R, GL_CLAMP_TO_EDGE)
    
    return tex_id

# Sampling
def sample_volume(tex_id, world_pos, volume_bounds):
    """
    Samples the 3D texture at a world position.
    world_pos: (x, y, z)
    volume_bounds: (min_x, min_y, min_z, max_x, max_y, max_z)
    """
    # Normalize to [0, 1]
    u = (world_pos[0] - volume_bounds[0]) / (volume_bounds[3] - volume_bounds[0])
    v = (world_pos[1] - volume_bounds[1]) / (volume_bounds[4] - volume_bounds[1])
    w = (world_pos[2] - volume_bounds[2]) / (volume_bounds[5] - volume_bounds[2])
    
    # Clamp to prevent out-of-bounds access
    u = max(0.0, min(1.0, u))
    v = max(0.0, min(1.0, v))
    w = max(0.0, min(1.0, w))
    
    # Sample (conceptual, actual implementation depends on shader)
    # color = texture(tex_id, vec3(u, v, w))
    return (u, v, w) # Placeholder for shader return
```

## Subtopics

### [3D Texture Proxy Geometry](870-3d-texture-proxy-geometry.md)
Represents the volume as a stack of textured slabs, using 3D textures for interpolation but rendering via geometry. Chosen when directional lighting and hardware-accelerated compositing are required without ray marching.

### [Volume Texture Creation](1857-volume-texture-creation.md)
Focuses on the API-level allocation, data upload, and configuration of GPU texture objects. Chosen when implementing the data transfer pipeline rather than the sampling logic.

### [Texture Uniting (Multi-Channel Packing)](2470-texture-uniting-multi-channel-packing.md)
Packs multiple attribute channels (e.g., noise, light, mask) into a single RGBA 3D texture. Chosen to optimize memory bandwidth and reduce sampling overhead for multi-channel volumes.

### [PixelFlow Volume Rendering](3443-pixelflow-volume-rendering.md)
Uses 3D textures in a polygon resampling context for on-the-fly lighting. Chosen for hardware that supports dependent texture reads for pixel-level manipulation.

### [Texture Array Sampling with Alpha Discard](3993-texture-array-sampling-with-alpha-discard.md)
Samples a 3D texture array and discards low-alpha fragments. Chosen to optimize performance by avoiding overdraw in transparent regions.

### [Hardware Volume Rendering Pipeline with Pixel Textures](5641-hardware-volume-rendering-pipeline-with-pixel-textures.md)
Uses 3D lookup textures for transfer functions in older hardware. Chosen for legacy systems requiring multi-dimensional transfer function evaluation.

### [Sparse Volume Texture (SVT)](7011-sparse-volume-texture-svt.md)
Maps large logical volumes to smaller physical textures using a page table. Chosen when volume dimensions exceed hardware limits or memory is constrained.

### [Splat Texture Layout & Mapping](7089-splat-texture-layout-mapping.md)
Organizes splat data into 3D textures. Chosen for Gaussian splatting rendering.

### [Memory Organization and Layout](7154-memory-organization-and-layout.md)
Defines linear address mapping for cache optimization. Chosen when tuning low-level memory access patterns.

### [3D Volume Atlas Packing](7158-3d-volume-atlas-packing.md)
Packs multiple discrete volumes into one texture. Chosen to reduce state changes and memory fragmentation.

### Ambient Occlusion Volume
Stores precomputed ambient occlusion factors in a 3D texture, optionally with bent normals. Chosen to avoid runtime reconstruction costs associated with methods like Kontkanen and Laine's [S3, unofficial].

### OpenGL Texture Output
Uses OpenGL texture objects to render results efficiently. Chosen for simple output pipelines where texture mapping to a screen quad is sufficient [S4, unofficial].

## Operating characteristics
**Time Complexity:** Sampling is $O(1)$ per voxel access due to hardware interpolation [S1, S4, unofficial].
**Memory Complexity:** $O(D_x D_y D_z)$ for dense storage [S1, unofficial].
**Performance:** Storing voxels in 3D textures can improve performance significantly (e.g., 10x improvement from 12 FPS to 121 FPS at 2048^3 resolution) compared to linear arrays or Z-order curves, due to better cache locality [S1, unofficial].
**Strengths:** Hardware-accelerated tri-linear interpolation, optimized cache coherence for neighboring access, simple API usage [S1, S2, S4, unofficial].
**Limitations:** Limited by maximum texture dimensions (e.g., 2048^3), potential precision loss with low-bit formats, less flexible than software-managed structures for non-uniform grids [S1, S4, unofficial].
**When to use:** When rendering dense, uniform volumes on modern GPUs with sufficient texture memory [S1, S4, unofficial].
**When not to use:** For very large sparse volumes (use [Sparse Volume Texture](7011-sparse-volume-texture-svt.md)) or irregular grids [G].

## Background
Originated with the introduction of 3D texture support in graphics APIs (e.g., OpenGL 1.2) [S4, unofficial]. Early implementations used 3D textures for direct volume rendering, leveraging hardware interpolation for speed [S2, S4, unofficial]. The method evolved to support various optimizations like multi-channel packing and sparse storage to address memory and performance constraints [S1, S3, S4, unofficial].
