# Volume Texture Creation

Also called: 3D Volume Texture Creation

## Overview
Volume Texture Creation allocates GPU memory and loads volumetric data (such as scalar fields, gradients, or transfer functions) into GPU-accessible texture objects for subsequent rendering [S1, S2, S3, S4, S5, S6, unofficial]. It solves the problem of mapping host-side volumetric fields to device-local memory with appropriate access patterns [S1, S2, unofficial][S3, unofficial].

## How it works
**Inputs and Outputs:**
- Inputs: Host-side volumetric data (scalar fields, gradient 3-tuples, transfer function tables, or image URLs), volume dimensions (`width`, `height`, `depth` or `dimX`, `dimY`, `dimZ`), and format specifications [S1, S2, S3, S4, S5, S6, unofficial].
- Outputs: GPU texture objects, CUDA arrays, or texture arrays configured for sampling [S1, S2, S3, S4, S5, S6, unofficial].

**Data Structures:**
- CUDA: `cudaResourceDesc`, `cudaTextureDesc`, `cudaMemcpy3DParms`, `cudaChannelFormatDesc`, and `cudaArray_t` [S2, unofficial].
- OpenGL: 3D textures for attenuation and gradients, 1D texture for transfer functions [S4, unofficial].
- WebGPU: `GPUTexture` descriptors with `GPUTextureUsage.TEXTURE_BINDING | GPUTextureUsage.COPY_DST` [S3, unofficial].
- VTK: `vtkVolume` pointer containing transfer function metadata [S1, unofficial].

**Numbered Steps:**
1. Allocate device memory or texture storage matching the volume dimensions [S1, S2, S3, S4, S5, S6, unofficial].
2. Configure memory copy or texture upload parameters (source pointers, pitches, extents, formats) [S2, S3, S4, unofficial].
3. Transfer host-side data to device-local memory or texture storage [S2, S3, S4, unofficial].
4. Bind or initialize texture descriptors with sampling parameters (filter mode, coordinate normalization, address modes) [S2, S4, unofficial].
5. Create the final texture object or array for shader access [S2, S3, S4, unofficial].

**Formulas:**
- Attenuation storage: $\tau[x,y,z]$ stored as 16-bit values in range $[0,1]$ representing attenuation per distance [S4, unofficial].
- Gradient storage: $\nabla\tau[x,y,z]$ stored as 3-tuples where each component is a 16-bit float in range $[-1,+1]$ [S4, unofficial].
- Transfer function mapping: $f: \tau \rightarrow k_d, \tau'$ stored in 1D texture where RGB components store $k_d$ and Alpha stores $\tau'$, both 16-bit in $[0,1]$ [S4, unofficial].

**Parameters:**
- Transfer function texture size: typically 256, providing enough precision; larger arrays provide more precision [S4, unofficial].
- `numberOfScalarComponents`: must be exactly 1 or 4 for VTK volume creation [S1, unofficial].

**Edge Cases and Pitfalls:**
- VTK creation fails or is invalid if `numberOfScalarComponents` is not 1 or 4 [S1, unofficial].
- Splat texture management prevents degenerate dimensions by clamping zero or undefined data lengths to 1 via `Math.max(1, 0)` [S5, unofficial].
- WebGPU upload requires correct `bytesPerRow` (`width * 2` for 16-bit formats) and `rowsPerImage` to avoid stride misalignment [S3, unofficial].

**Pseudocode (Unified API Implementations):**
```python
# CUDA Texture Object Creation
channelDesc = cudaCreateChannelDesc(32, 0, 0, 0, cudaChannelFormatKindFloat)
extent = cudaExtent(dim.x, dim.y, dim.z)
cudaMalloc3DArray(m_arrayField, channelDesc, extent)

copyParams = {
    'srcPtr': make_cudaPitchedPtr(hostScalar, dim.x * sizeof(float), dim.x, dim.y),
    'dstArray': m_arrayField,
    'extent': extent,
    'kind': cudaMemcpyHostToDevice
}
cudaMemcpy3D(copyParams)

resourceDesc = {
    'resType': cudaResourceTypeArray,
    'res': {'array': {'array': m_arrayField}}
}

textureDesc = {
    'normalizedCoords': True,
    'filterMode': cudaFilterModeLinear,
    'addressMode': [cudaAddressModeClamp, cudaAddressModeClamp, cudaAddressModeClamp],
    'readMode': cudaReadModeElementType
}
cudaCreateTextureObject(textureObject, resourceDesc, textureDesc, None)

# OpenGL Volume Texture Setup
glTexImage3D(GL_TEXTURE_3D, 0, GL_R16, dimX, dimY, dimZ, 0, GL_RED, GL_UNSIGNED_SHORT, volumeTexMap)
glTexImage3D(GL_TEXTURE_3D, 0, GL_RGB16F, dimX, dimY, dimZ, 0, GL_RGB, GL_FLOAT, gradientTexMap)
glTexImage1D(GL_TEXTURE_1D, 0, GL_RGBA16, 256, 0, GL_RGBA, GL_UNSIGNED_SHORT, transferTex)

# WebGPU Volume Texture Upload
textureDescriptor = {
    'size': {'width': width, 'height': height, 'depthOrArrayLayers': slices},
    'dimension': '2d',
    'format': 'r16float',
    'usage': GPUTextureUsage.TEXTURE_BINDING | GPUTextureUsage.COPY_DST
}
texture = device.createTexture(textureDescriptor)

for i in range(slices):
    device.queue.writeTexture(
        texture=texture,
        data=rawData.buffer,
        textureOffset={'x': 0, 'y': 0, 'z': i},
        bytesPerRow=width * 2,
        rowsPerImage=height,
        size={'width': width, 'height': height, 'depthOrArrayLayers': 1}
    )

# VTK Volume Texture Creation
if numberOfScalarComponents not in [1, 4]:
    raise ValueError("numberOfScalarComponents must be 1 or 4")

if vol.transfer_function_changed:
    allocate_gpu_memory(vol)
    load_transfer_function_table(vol)
```

## Subtopics

### [Trilinear Volume Sampling for Texture Generation](2726-trilinear-volume-sampling-for-texture-generation.md)
Retrieves scalar or vector attributes from a 3D voxel grid at continuous surface positions by interpolating values from the surrounding 2x2x2 neighborhood of active grid points. It enables spatially coherent attribute coding and direct surface queries without UV mapping.

### [Texture Generation](2769-texture-generation.md)
Creates an empty 2D RGBA texture in OpenGL for storing rendered image data. It differs from [Trilinear Volume Sampling for Texture Generation](2726-trilinear-volume-sampling-for-texture-generation.md) by focusing on the allocation and configuration of the destination buffer rather than the interpolation logic, and from [Volume Texture Setup](4055-volume-texture-setup.md) by specifically targeting 2D image output rather than 3D volume input.

### [Texture Array Loading](3575-texture-array-loading.md)
Constructs a WebGL 2D array texture from a list of external image URLs, assembling them into a contiguous 3D volume representation for rendering. It solves the problem of efficiently loading discrete 2D slices into a GPU texture object that supports 3D coordinate sampling. It differs from monolithic volume loading by treating the texture as a collection of independent 2D layers, allowing for dynamic assembly based on a directory structure rather than a single dense buffer.

### [Volume Context and Configuration](3577-volume-context-and-configuration.md)
Establishes the rendering state and data layout metadata required by a volume rendering engine to interpret raw voxel data. It solves the problem of decoupling the raw memory layout of a 3D scalar/vector field from the rendering algorithm's expectations. Unlike [Volume Texture Creation](1857-volume-texture-creation.md), which handles GPU memory allocation and texture object generation, this method configures the logical description of the volume (dimensions, voxel structure, field offsets) so that the renderer can correctly traverse and shade the data.

### [Volume Texture Setup](4055-volume-texture-setup.md)
Configures GPU-accessible 3D texture resources with specific memory layouts, sampling parameters, and lifecycle states to prepare volumetric data for rendering. It solves the problem of translating discrete, host-side volumetric representations into optimized GPU textures that support efficient ray marching or voxel cone tracing. It differs from [3D Texture Upload](4419-3d-texture-upload.md) by focusing on the configuration of texture objects (filters, wrap modes, mipmaps) rather than the raw data transfer, and from [Sparse Volume Texture Setup](7432-sparse-volume-texture-setup.md) by targeting dense grid textures rather than sparse tile-based structures.

### [Texture Slabs](7262-texture-slabs.md)
Loads 3D density data into graphics card texture map memory, treating the volume as a series of slabs between slices. It differs from standard ray casting by enabling pre-integration of the volume rendering integral, which allows efficient accumulation of color and opacity along rays.

### [GPU Memory and Buffer Construction](8345-gpu-memory-and-buffer-construction.md)
Defines the mechanisms for allocating, initializing, and managing GPU-accessible memory resources (textures, buffers, framebuffers) required to store and render volumetric data. It solves the problem of transferring host-side volumetric representations into device-local memory structures that shaders can efficiently sample. It differs from [Volume Texture Creation](1857-volume-texture-creation.md) by focusing on the low-level resource allocation and memory management (staging buffers, texture objects, framebuffers) rather than the high-level API calls for texture generation, and from [Trilinear Volume Sampling for Texture Generation](2726-trilinear-volume-sampling-for-texture-generation.md) by handling the data layout and binding rather than the interpolation logic.

### GPU Volume Rendering Data Setup
Storage of attenuation values $\tau[x,y,z]$ in a 3D texture of scalar values, typically 16-bit in range $[0,1]$, representing attenuation per distance [S4, unofficial]. Storage of pre-computed gradients $\nabla\tau[x,y,z]$ in a 3D texture of 3-tuples, where each component is a 16-bit float in range $[-1,+1]$ [S4, unofficial]. Storage of transfer function $f: \tau \rightarrow k_d, \tau'$ in a 1D texture of 4-tuples [S4, unofficial]. RGB components store $k_d$, Alpha component stores $\tau'$ [S4, unofficial]. Both are 16-bit values in $[0,1]$ [S4, unofficial]. Transfer function texture size is typically 256, providing enough precision [S4, unofficial]. Larger arrays provide more precision [S4, unofficial].

### Splat Texture Management
Creates and manages textures for Gaussian splats using `THREE.DataArrayTexture` [S5, unofficial]. It constructs a texture from a `Uint32Array` by instantiating `THREE.DataArrayTexture` with `data`, `width`, `height`, `depth`, then setting format to `THREE.RGBAIntegerFormat`, type to `THREE.UnsignedIntType`, magFilter and minFilter to `THREE.NearestFilter`, and generateMipmaps to `false` [S5, unofficial]. When ensuring an SH texture, it calculates padded size as `maxSplats * 4` [S5, unofficial]. If the input data length is less than padded size, it allocates a new `Uint32Array` of that size, copies data into it, and replaces the original reference [S5, unofficial]. `maxSplats` is the maximum number of splats supported by the texture buffer, used to compute padding dimensions and buffer capacity [S5, unofficial]. If `data.length` is zero or undefined, `getTextureSize` receives `Math.max(1, 0) = 1` to prevent degenerate texture dimensions [S5, unofficial].

### Volume Texture Atlas Export
Exports a 3D volume to a 2D RGBA atlas for Unreal Engine 5 [S6, unofficial]. It creates an RGBA uint8 atlas array of shape `(rows * height, cols * width, 4)` initialized to zero [S6, unofficial]. It sets Alpha channel to 255: `atlas[:, :, 3] = 255` [S6, unofficial]. It iterates `z_index` from 0 to `depth-1`, calculates row and column via `row, column = divmod(z_index, cols)`, calculates y0, x0 offsets via `y0, x0 = row * height, column * width`, and copies `result.density[z_index]` to `atlas[y0:y0+height, x0:x0+width, 0]` [S6, unofficial]. `tile_columns` is the number of columns in the atlas, typically equal to the volume size (`width`) [S6, unofficial]. `tile_rows` is the number of rows in the atlas, typically 1 for single-row layout [S6, unofficial]. The atlas is imported as a Texture2D (Masks/Linear), then 'Create Volume Texture' is used to generate the 3D resource [S6, unofficial].

### [Texture Creation from Palette](12958-texture-creation-from-palette.md)
Constructs a 2D RGBA8 texture from a 1D palette array for use in volume rendering, specifically handling the byte-order conversion required when the source data is stored as little-endian 32-bit integers. It differs from general volume texture generation by treating the palette as a 1D lookup table mapped to a 256x1 texture, and explicitly addresses the endianness reversal pitfall where shader sRGB interpretation relies on the specific R, G, B, A byte layout resulting from the little-endian interpretation of the reversed uint.
