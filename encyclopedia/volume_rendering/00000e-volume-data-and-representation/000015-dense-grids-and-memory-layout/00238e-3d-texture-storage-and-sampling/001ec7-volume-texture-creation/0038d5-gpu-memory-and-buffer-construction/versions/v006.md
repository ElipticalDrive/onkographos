# GPU Memory and Buffer Construction


## Overview
GPU Memory and Buffer Construction defines the mechanisms for transferring volumetric scalar data and associated rendering metadata from host memory to GPU-accessible textures and framebuffers, while managing memory constraints, format compatibility, and the lifecycle of rendering resources [S1, unofficial]. It differs from [Trilinear Volume Sampling for Texture Generation](2726-trilinear-volume-sampling-for-texture-generation.md) by focusing on the memory layout and resource binding rather than the interpolation algorithm, and from [Texture Generation](2769-texture-generation.md) by explicitly handling the host-to-device transfer and framebuffer setup required for rendering [S1, unofficial].

## Shared principles
The family shares the principle of mapping dense 3D grids or mesh-derived data into GPU hardware resources (textures, buffers, framebuffers) while ensuring data integrity and format compatibility. Key shared constraints include:
1.  **Format Matching:** The GPU texture or buffer format must match the source data type (e.g., `R32F` for floats, `R8UI` for unsigned char) to prevent precision loss or corruption [S1, unofficial][G].
2.  **Memory Hierarchy:** Data is often transferred via staging buffers or direct mapping to separate host-visible memory from device-local storage, especially when the source data is not coherent for the GPU [S1, unofficial].
3.  **Resource Lifecycle:** Resources (textures, framebuffers, buffers) must be created, bound, and destroyed in a specific order to avoid dangling references or undefined behavior [S1, unofficial].
4.  **Metadata Association:** Rendering metadata (bounding boxes, dimensions, value ranges) is bundled with the GPU resource handles in a layout structure for shader access [S1, unofficial][S2].

## Subtopics

### [Device Volume Snapshot](2246-device-volume-snapshot.md)
The Device Volume Snapshot creates an immutable, compact representation of volume data and metadata optimized for direct consumption by GPU kernels. It solves the problem of passing complex, mutable volume structures to shaders by freezing the state into a lightweight struct containing texture handles and geometric parameters. Unlike mutable builders, snapshots are copy-lightweight via shared internal resources and never modify underlying data once built [2246-device-volume-snapshot].

### [GPU Data Layout](2469-gpu-data-layout.md)
GPU Data Layout defines the specific memory organization and resource binding structure for transferring volumetric scalar data and associated rendering metadata from host memory to GPU-accessible textures and framebuffers. It solves the problem of efficiently mapping dense 3D grids to GPU hardware while managing memory constraints, format compatibility, and the lifecycle of rendering resources [2469-gpu-data-layout]. It differs from [Tiled 2D Texture Storage for 3D Fields](2740-tiled-2d-texture-storage-for-3d-fields.md) by using native 3D texture objects rather than packing 3D data into 2D tile arrays, and from [CUDA-accelerated Vector Field Reading with Magnitude](2581-cuda-accelerated-vector-field-reading-with-magnitude.md) by focusing on scalar fields rather than vector fields with magnitude pre-computation [2469-gpu-data-layout].

### [ClearView Unified Buffer Construction](2475-clearview-unified-buffer-construction.md)
ClearView Unified Buffer Construction is a preprocessing technique that converts a hexahedral mesh (positions, connectivity, and scalar values) into four GPU-friendly texture buffers—vertices, edges, faces, and cellScalar—optimized for the ClearView volume rendering pipeline [2475-clearview-unified-buffer-construction]. It differs from standard volume texture creation by explicitly encoding topological connectivity (faces and edges) alongside geometric data to support the pipeline's specific fragment-based shading and focus-control mechanisms [2475-clearview-unified-buffer-construction].

### [Volume Upload via Staging Buffer](15388-volume-upload-via-staging-buffer.md)
This method transfers dense 3D volume data from host memory to device-local GPU memory using an intermediate staging buffer. It solves the problem of moving large, non-coherent host data into a format accessible by GPU shaders, ensuring data integrity through explicit copy operations. Unlike direct mapping or unified memory approaches, it explicitly separates host-visible staging memory from device-local storage, which is necessary when the source data resides in standard host memory that is not directly accessible or coherent for the GPU [15388-volume-upload-via-staging-buffer].

### GPU Texture Upload and Composition
- **Definition:** Draws the voxel map to a GPU texture, optionally compositing with rasterized scene objects [S1, unofficial].
- **Step:** Dispatch compute work groups based on the resolution of `outputTexture` to render the voxel map into it [S1, unofficial].
- **Parameter:** `outputTexture`: `GLuint` handle to the target texture. Must have internal format `GL_RGBA32F`. Its resolution determines the number of compute work groups dispatched [S1, unofficial]. `rasterColorTexture`: `int` handle to the color buffer for rasterized objects. Use -1 to disable composition [S1, unofficial]. `rasterDepthTexture`: `int` handle to the depth buffer for rasterized objects. Use -1 to disable composition [S1, unofficial].
- **Pitfall:** `outputTexture` must be `GL_RGBA32F`; using a different format will cause undefined behavior or rendering failure [S1, unofficial].

### GPU Data Structure Memory Management
- **Parameter:** The new buffer allocates double the size of the existing data structure to handle the worst case where each segment is split, as the number of splits is unknown beforehand [S2]. The theoretical minimum storage is four floats per segment and two integer values per pixel, but the implementation uses double the size for safety [S2].
- **Layout:** Data structures for all pixels are stored in one memory pool in global GPU memory. Two arrays maintain the size and offset of the respective data structure in the pool for per-pixel access [S2].

### Texture Buffer Object for Block Types
- **Definition:** A technique to store block type colors in a Texture Buffer Object (TBO) and bind it as a texture to allow the vertex shader to look up colors based on the block type index stored in the vertex data [S3, unofficial].
- **Step:** Define an array of 5 RGBA colors (each 4 floats) corresponding to block types: 0=air (black, alpha 0), 1=grass, 2=dirty, 3=water, 4=stone [S3, unofficial]. Upload the color array to the TBO using `tbo.data(colors)` [S3, unofficial]. Bind the TBO texture to texture unit 0 using `mogl::active_texture(0)` and `tbo_texture.bind()` [S3, unofficial]. Configure the TBO as a texture buffer with internal format `GL_R32F` using `tbo.tex_buffer(GL_R32F)` [S3, unofficial]. In the render loop, bind the TBO texture and set the uniform `texture_uniform_id` to 0 [S3, unofficial].
- **Layout:** The TBO stores 5 colors, each as 4 floats (R32F format implies single channel, but the data is 4 floats per entry, likely interpreted as RGBA in the shader). The vertex data stores the block type as a `GLubyte` index into this texture [S3, unofficial].

## Background
The techniques described in this family originate from various implementations of volume rendering pipelines, including CUDA-based ray marchers [S2], OpenGL-based renderers [S1, unofficial], and Vulkan-based engines [S1, unofficial]. The use of staging buffers for volume upload is a standard practice in Vulkan to handle non-coherent host memory [15388-volume-upload-via-staging-buffer]. The ClearView unified buffer construction is specific to the ClearView pipeline [2475-clearview-unified-buffer-construction]. The GPU data layout structure is derived from VTK-based rendering systems [2469-gpu-data-layout].
