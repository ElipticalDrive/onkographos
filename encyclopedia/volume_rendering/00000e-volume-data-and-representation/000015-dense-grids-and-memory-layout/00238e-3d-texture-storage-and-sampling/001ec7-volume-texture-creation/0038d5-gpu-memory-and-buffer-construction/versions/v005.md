# GPU Memory and Buffer Construction

Also called: Device Memory Allocation, Texture Buffer Objects, Staging Buffers

## Overview
GPU Memory and Buffer Construction defines the mechanisms for allocating, populating, and binding volumetric data structures in GPU memory to enable efficient raycasting and rendering. It solves the problem of transferring host-side volumetric representations (voxel grids, hexahedral meshes, or metadata) into GPU-accessible formats (3D textures, unified buffers, or texture buffer objects) while ensuring memory coherence and format compatibility. This family is distinguished from [Volume Texture Creation](1857-volume-texture-creation.md) by focusing on the low-level memory management, buffer allocation, and resource binding steps rather than the high-level texture generation or sampling logic.

## Shared principles
All methods in this family share the following core principles regarding memory management and resource binding:

1.  **Memory Hierarchy Awareness**: Data must reside in memory regions accessible to the GPU shaders (e.g., `DEVICE_LOCAL` or global GPU memory). Host-side data must be transferred via explicit copy operations or staging buffers if the source data is not already in host-visible, coherent memory [S1, unofficial].
2.  **Format Specification**: The GPU texture or buffer format (e.g., `R32F`, `RGBA32F`, `RG32UI`) must match the data type and channel count of the source volume data to prevent corruption or alignment errors [S1, unofficial].
3.  **Resource Lifecycle**: Resources (buffers, textures, framebuffers) must be created, bound, and destroyed in a specific order to avoid dangling pointers or invalid memory access. Destruction must occur in reverse order of creation [S1, unofficial].
4.  **Immutable Metadata**: For snapshot-based approaches, metadata (dimensions, voxel size, origin) is often bundled with texture handles into a compact struct to minimize transfer overhead and ensure thread safety [S1, unofficial][S2].

## Subtopics

### [Device Volume Snapshot](2246-device-volume-snapshot.md)
Creates a compact, immutable representation of volume metadata and texture handles optimized for passing to CUDA kernels. It solves the problem of efficiently transferring volumetric data from host-side builders to device-side renderers while ensuring thread safety and memory consistency through an immutable snapshot pattern. Unlike mutable buffer constructions, this method guarantees that once built, the volume data cannot be modified, allowing lightweight copying via shared internal resources.

### [GPU Data Layout](2469-gpu-data-layout.md)
Defines the host-side C++ structures and OpenGL resource bindings required to transfer volumetric scalar fields, transfer functions, and auxiliary buffers to the GPU for raycasting. It solves the problem of mapping logical VTK data components (scalars, opacity tables, depth buffers) to specific GPU texture and framebuffer objects with strict format constraints. It differs from [Volume Upload via Staging Buffer](15388-volume-upload-via-staging-buffer.md) by focusing on the final resource binding and layout definition rather than the transfer mechanism, and from [ClearView Unified Buffer Construction](2475-clearview-unified-buffer-construction.md) by using distinct OpenGL texture IDs for separate data types rather than a unified buffer approach.

### [ClearView Unified Buffer Construction](2475-clearview-unified-buffer-construction.md)
A preprocessing technique that converts a hexahedral mesh (positions, connectivity, and scalar values) into four GPU-friendly texture buffers—vertices, edges, faces, and cell scalars—optimized for the ClearView volume rendering pipeline. It differs from standard volume texture creation by explicitly linearizing hexahedral topology (faces and edges) into 2D texture arrays to facilitate efficient fragment-based rendering and focus-control masking, rather than relying on 3D voxel grids or sparse structures.

### [Volume Upload via Staging Buffer](15388-volume-upload-via-staging-buffer.md)
Transfers dense volumetric field data from host memory to GPU device-local memory using an intermediate staging buffer. It solves the problem of populating a 3D texture with data that resides on the CPU, ensuring memory coherence and allowing the GPU to optimize access patterns for sampling. It is distinguished from direct mapping methods by explicitly decoupling the host-side data population phase from the GPU residency phase, which is necessary when the source data is not already in a host-visible, coherent memory region or when asynchronous transfer is required.

### GPU Texture Upload and Composition
- **Definition**: Draws the voxel map to a GPU texture, optionally compositing with rasterized scene objects [S1, unofficial].
- **Step**: Dispatch compute work groups based on the resolution of `outputTexture` to render the voxel map into it [S1, unofficial].
- **Parameter**: `outputTexture`: `GLuint` handle to the target texture. Must have internal format `GL_RGBA32F`. Its resolution determines the number of compute work groups dispatched [S1, unofficial]. `rasterColorTexture`: `int` handle to the color buffer for rasterized objects. Use `-1` to disable composition [S1, unofficial]. `rasterDepthTexture`: `int` handle to the depth buffer for rasterized objects. Use `-1` to disable composition [S1, unofficial].
- **Pitfall**: `outputTexture` must be `GL_RGBA32F`; using a different format will cause undefined behavior or rendering failure [S1, unofficial].

### GPU Data Structure Memory Management
- **Parameter**: The new buffer allocates double the size of the existing data structure to handle the worst case where each segment is split, as the number of splits is unknown beforehand [S2]. The theoretical minimum storage is four floats per segment and two integer values per pixel, but the implementation uses double the size for safety [S2].
- **Layout**: Data structures for all pixels are stored in one memory pool in global GPU memory. Two arrays maintain the size and offset of the respective data structure in the pool for per-pixel access [S2].

### Texture Buffer Object for Block Types
- **Definition**: A technique to store block type colors in a Texture Buffer Object (TBO) and bind it as a texture to allow the vertex shader to look up colors based on the block type index stored in the vertex data [S3, unofficial].
- **Step**: Define an array of 5 RGBA colors (each 4 floats) corresponding to block types: 0=air (black, alpha 0), 1=grass, 2=dirty, 3=water, 4=stone [S3, unofficial]. Upload the color array to the TBO using `tbo.data(colors)` [S3, unofficial]. Bind the TBO texture to texture unit 0 using `mogl::active_texture(0)` and `tbo_texture.bind()` [S3, unofficial]. Configure the TBO as a texture buffer with internal format `GL_R32F` using `tbo.tex_buffer(GL_R32F)` [S3, unofficial]. In the render loop, bind the TBO texture and set the uniform `texture_uniform_id` to 0 [S3, unofficial].
- **Layout**: The TBO stores 5 colors, each as 4 floats (R32F format implies single channel, but the data is 4 floats per entry, likely interpreted as RGBA in the shader). The vertex data stores the block type as a `GLubyte` index into this texture [S3, unofficial].

## Background
The techniques described in this family are foundational to modern GPU-based volume rendering and visualization. The use of staging buffers for host-to-device transfer is a standard practice in APIs like Vulkan and OpenGL to ensure memory coherence and optimize bandwidth [S1, unofficial]. The immutable snapshot pattern for device data is common in high-performance rendering engines to avoid race conditions during kernel execution [S1, unofficial][S2]. The ClearView unified buffer approach is specific to hexahedral mesh visualization, adapting traditional voxel-based techniques to unstructured grids [S1, unofficial]. The Texture Buffer Object (TBO) technique is a general GPU programming pattern used for data-driven shading, applied here to block-type color lookup [S3, unofficial].
