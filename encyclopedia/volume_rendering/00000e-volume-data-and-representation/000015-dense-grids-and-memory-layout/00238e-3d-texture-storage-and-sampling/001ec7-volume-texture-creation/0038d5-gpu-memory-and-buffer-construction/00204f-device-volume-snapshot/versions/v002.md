# Device Volume Snapshot

Also called: DeviceVolume, VXL-042 Storage, Volume Immutable Storage, toDevice

## Overview
The Device Volume Snapshot creates an immutable, compact representation of volume data and metadata optimized for direct consumption by GPU kernels. It solves the problem of passing complex, mutable volume structures to shaders by freezing the state into a lightweight struct containing texture handles and geometric parameters. Unlike mutable builders, snapshots are copy-lightweight via shared internal resources and never modify underlying data once built [S1][S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A `Volume::Builder` instance (mutable) or a `Volume::Description` (metadata).
*   **Output:** A `DeviceVolume` (or `DeviceScene`) struct containing CUDA texture objects and scalar metadata, ready for device-side access.

**Data Structures:**
The core output is the `DeviceVolume` struct (often embedded in `DeviceScene`). Its layout is defined as [S2, unofficial]:

```cpp
struct DeviceVolume {
    cudaTextureObject_t field_tex;   // Primary density field
    cudaTextureObject_t grad_tex;    // Gradient field (can be 0 if unused)
    int3 dim;                      // Volume dimensions (width, height, depth)
    float3 voxel_size;             // Physical size per voxel
    float3 origin;                 // World-space origin of the volume
    float2 value_range;            // Min and max density values
    float density_scale;           // Scaling factor for density values
};
```

**Steps:**
1.  **Build Volume:** Use `Volume::Builder` to populate the volume. The builder accepts `Cell` objects by value. Internally, it maintains a local table of unique `Definition` objects (sharing `Data`) and a compact grid of cells that index this table, storing orientations as needed [S1].
2.  **Create Texture Objects:** Generate `cudaTextureObject_t` handles for the density (`field_tex`) and optional gradient (`grad_tex`) data. Ensure the texture format matches the source data type (e.g., `R32F`) [S1][S2, unofficial].
3.  **Initialize Snapshot:** Construct the `DeviceVolume` struct. Populate `dim`, `voxel_size`, `origin`, `value_range`, and `density_scale` from the `Volume::Description` or computed bounds [S2, unofficial].
4.  **Commit/Transfer:** Copy the `DeviceVolume` struct to device memory. This is a lightweight copy because the texture objects are handles to GPU resources, not the data itself [S1][S2, unofficial].

**Pseudocode:**
```python
def create_device_volume_snapshot(volume_builder, stream):
    # 1. Build the immutable volume
    # The builder deduplicates definitions and stores a compact grid
    volume = volume_builder.build()
    
    # 2. Extract metadata
    dim = volume.extents()
    voxel_size = volume.voxel_size()
    origin = volume.origin()
    value_range = volume.value_range()
    density_scale = volume.density_scale()
    
    # 3. Create CUDA texture objects
    # Assumes volume has methods to get raw data pointers and dimensions
    field_tex = create_cuda_texture(
        data=volume.get_density_data(),
        width=dim.x,
        height=dim.y,
        depth=dim.z,
        format=CUDA_FORMAT_R32F
    )
    
    grad_tex = 0
    if volume.has_gradients():
        grad_tex = create_cuda_texture(
            data=volume.get_gradient_data(),
            width=dim.x,
            height=dim.y,
            depth=dim.z,
            format=CUDA_FORMAT_RG32F
        )
        
    # 4. Construct the snapshot struct
    snapshot = DeviceVolume(
        field_tex=field_tex,
        grad_tex=grad_tex,
        dim=dim,
        voxel_size=voxel_size,
        origin=origin,
        value_range=value_range,
        density_scale=density_scale
    )
    
    # 5. Copy to device memory
    # The struct itself is small; texture objects are handles
    device_snapshot_ptr = allocate_device_memory(DeviceVolume)
    copy_struct_to_device(device_snapshot_ptr, snapshot, stream)
    
    return device_snapshot_ptr
```

**Edge Cases and Pitfalls:**
*   **Dangling Pointers:** The public API must not expose `std::span<const Cell>` or raw pointers to the internal compact storage. Access must be via `cell(position)` which returns values or views, preventing invalidation when internal grids change [S1].
*   **Texture Format Mismatch:** The CUDA texture format must match the source data layout to prevent corruption [S1].
*   **Immutable Guarantee:** Once `build()` is called, the `Volume` is immutable. Copying is cheap because it shares the underlying data structures [S1].

## Operating characteristics
*   **Time Complexity:** Building the snapshot is $O(N)$ where $N$ is the number of voxels, due to deduplication and grid construction. Copying the snapshot struct to the device is $O(1)$ relative to volume size, as it only copies handles and scalars.
*   **Memory Complexity:** The snapshot struct itself is small (approx. 64-80 bytes). The bulk of memory is held by the GPU texture objects, which are shared with the original volume data.
*   **Strengths:** Lightweight copying, thread-safe (immutable), minimal overhead for passing to kernels.
*   **Limitations:** Not suitable for dynamic updates; requires rebuilding the snapshot for any volume change.
*   **When to use:** When passing volume data to CUDA kernels for rendering or simulation.
*   **When not to use:** When the volume data needs to be modified frequently on the host or device without rebuilding the entire structure.

## Background
The concept originates from the Sparkle Voxel Engine design, specifically the VXL-042 storage specification, which emphasizes immutable volume representations and compact cell storage [S1]. The implementation details for CUDA integration are found in the cuVRender engine, which demonstrates the practical application of this pattern for GPU-accelerated volume rendering [S2, unofficial].
