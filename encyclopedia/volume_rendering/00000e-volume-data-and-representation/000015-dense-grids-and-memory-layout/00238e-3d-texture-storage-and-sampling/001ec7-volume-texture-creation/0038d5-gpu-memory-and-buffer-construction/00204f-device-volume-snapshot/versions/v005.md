# Device Volume Snapshot

Also called: DeviceVolume, VXL-042 Storage, Volume Immutable Storage, toDevice

## Overview
The Device Volume Snapshot is an immutable, compact representation of volume data and metadata optimized for GPU consumption. It solves the problem of efficiently transferring volume state from a mutable host-side builder to CUDA kernels without exposing internal memory layouts or risking dangling pointers. It sets itself apart from sibling methods by enforcing immutability upon construction and using a shared-resource model for lightweight copying, ensuring thread-safe sharing across multiple frames or kernels [S1][S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A mutable `Volume::Builder` containing cells, definitions, and grid dimensions.
*   **Output:** An immutable `DeviceVolume` (or `DeviceScene` snapshot) struct containing texture handles and metadata, ready for device-side access.

**Data Structures:**
The core data structure is the `DeviceVolume` (referred to as `DeviceScene` in the reference implementation [S2, unofficial]). It contains the following fields:

*   `field_tex`: `cudaTextureObject_t` – The primary volume texture handle.
*   `grad_tex`: `cudaTextureObject_t` – The gradient texture handle. Can be `0` if gradients are not computed or required [S2, unofficial].
*   `dim`: `int3` – The dimensions of the volume grid $(D_x, D_y, D_z)$ [S2, unofficial].
*   `voxel_size`: `float3` – The physical size of a single voxel $(S_x, S_y, S_z)$ [S2, unofficial].
*   `origin`: `float3` – The world-space origin of the volume grid [S2, unofficial].
*   `value_range`: `float2` – The minimum and maximum scalar values in the volume $(V_{min}, V_{max})$ [S2, unofficial].
*   `density_scale`: `float` – A scalar multiplier for density values [S2, unofficial].

**Internal Storage Layout (Builder Phase):**
Before snapshotting, the `Volume` class uses a specific internal layout defined by the VXL-042 specification [S1]:
1.  **Definition Table:** A local table storing unique `Definition` objects. Multiple cells can share the same `Definition` (and its underlying `Data`) to save memory.
2.  **Compact Grid:** A grid of cells that does not store full definitions. Instead, it stores indices into the Definition Table and orientation data.
3.  **Immutability:** Once `build()` is called on the `Builder`, the internal table and grid are frozen. The `Volume` object shares these resources internally, making copies lightweight [S1].

**Numbered Steps:**
1.  **Build:** The `Volume::Builder` accepts `Cell` objects by value. It deduplicates `Definition` objects and populates the compact grid with indices and orientations [S1].
2.  **Construct Snapshot:** Upon calling `build()` or `commit()`, the system creates the immutable `Volume` snapshot [S1].
3.  **Initialize Device Struct:** The `DeviceVolume` struct is populated with values derived from the `Volume::Description` and the bound texture handles [S2, unofficial].
4.  **Transfer to Device:** The `DeviceVolume` struct is copied to device memory (e.g., via `cudaMemcpy`) to be accessed by CUDA kernels [S2, unofficial].

**Pseudocode:**
The following pseudocode illustrates the construction and usage flow based on the reference implementations [S1][S2, unofficial].

```python
# 1. Builder Phase (Host-side, Mutable)
class VolumeBuilder:
    def __init__(self, dim: int3):
        self.dim = dim
        self.definitions = {} # Map: Definition -> Index
        self.grid = []        # List of (def_index, orientation)

    def set_cell(self, pos: int3, cell: Cell):
        # Deduplicate definition
        if cell.definition not in self.definitions:
            self.definitions[cell.definition] = len(self.definitions)
        
        def_idx = self.definitions[cell.definition]
        # Store compact representation: index + orientation
        self.grid.append((def_idx, cell.orientation))

    def build(self) -> Volume:
        # Create immutable Volume from compact grid and definitions
        return Volume(self.dim, self.definitions, self.grid)

# 2. Snapshot Phase (Host-side, Immutable)
class DeviceVolume:
    def __init__(self, volume: Volume, tex_handles):
        self.field_tex = tex_handles.field
        self.grad_tex = tex_handles.grad # Can be 0
        self.dim = volume.dim
        self.voxel_size = volume.voxel_size
        self.origin = volume.origin
        self.value_range = volume.value_range
        self.density_scale = volume.density_scale

# 3. Usage Phase (Device-side Access)
def render_kernel(device_vol: DeviceVolume, output_buffer):
    # Access texture using cudaTextureObject_t
    # Note: Public API must NOT expose std::span<const Cell>
    # to prevent dangling pointers if internal grid changes
    pass
```

**Edge Cases and Pitfalls:**
*   **Dangling Pointers:** The public API must not expose `std::span<const Cell>` or raw pointers to the internal compact storage. Internal indices or pointers may become invalid if the storage layout changes or if the snapshot is shared across threads [S1]. Use `cell(position)` returning values or views instead [S1].
*   **Gradient Handling:** The `grad_tex` field may be `0`. Kernels must check for this before sampling gradients [S2, unofficial].
*   **Immutability:** Once a `Volume` is built, it must not be modified. Modifications require creating a new `Builder` and a new snapshot [S1].

## Operating characteristics
*   **Time Complexity:** Construction is $O(N)$ where $N$ is the number of cells, due to deduplication and grid population. Copying the snapshot is $O(1)$ because it shares internal resources [S1].
*   **Memory Complexity:** Storage is compact, storing only indices and orientations in the grid, plus a single copy of each unique `Definition` [S1].
*   **Strengths:** Thread-safe sharing via immutability; lightweight copying; optimized for coalesced texture access on GPU [S1][S2, unofficial].
*   **Limitations:** Not suitable for frequent updates; requires rebuilding the snapshot for changes [S1].
*   **When to use:** When volume data is static for multiple frames or kernels and needs to be passed to CUDA code [S2, unofficial].
*   **When not to use:** For dynamic, per-frame voxel updates where mutable access is required [S1].

## Background
The concept originates from the Sparkle Voxel Engine design, specifically the VXL-042 storage specification, which emphasizes immutable volume representations and compact cell storage [S1]. The implementation details for CUDA integration, including the `DeviceScene` struct and texture handling, are derived from the cuVRender project [S2, unofficial]. The approach aligns with general GPU memory principles of immutability and safety for shared resources [8345-gpu-memory-and-buffer-construction.md].
