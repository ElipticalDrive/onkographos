# Device Volume Snapshot

Also called: DeviceVolume, VXL-042 Storage, Volume Immutable Storage, toDevice

## Overview
The Device Volume Snapshot is an immutable, compact representation of volume metadata and GPU texture handles, designed for efficient passing to CUDA rendering kernels. It differs from mutable staging buffers by providing a thread-safe, lightweight snapshot where copying shares internal resources, ensuring that old volumes are never modified once built [S1][S2, unofficial].

## How it works
**Inputs and Outputs**
*   **Input**: A `Volume::Builder` containing cells (defined by value) and a `Volume::Description` (dimensions, voxel size, origin, value range, density scale).
*   **Output**: A `DeviceVolume` (or `DeviceScene` in the context of the full scene) struct containing CUDA texture objects and scalar metadata, ready for device-side access.

**Data Structures**
The core data structure is `DeviceVolume` (or `DeviceScene` in the reference implementation). It contains the following fields [S2, unofficial]:

| Field | Type | Description |
| :--- | :--- | :--- |
| `field_tex` | `cudaTextureObject_t` | The primary volume texture handle. |
| `grad_tex` | `cudaTextureObject_t` | The gradient texture handle (can be 0 if not computed). |
| `dim` | `int3` | Volume dimensions $(D_x, D_y, D_z)$. |
| `voxel_size` | `float3` | Physical size of a single voxel $(s_x, s_y, s_z)$. |
| `origin` | `float3` | The world-space origin of the volume grid. |
| `value_range` | `float2` | The min and max scalar values in the volume $(v_{min}, v_{max})$. |
| `density_scale` | `float` | A scalar multiplier for density values. |

**Internal Storage Layout (Builder Phase)**
Before snapshotting, the `Volume` uses a compact storage layout validated by the VXL-042 specification [S1]:
1.  **Definition Table**: A local table of unique `Definition` objects. Multiple cells sharing the same physical data share the same `Data` pointer.
2.  **Compact Grid**: A grid of cells that indexes into the Definition table. Each cell entry stores an index into the Definition table and orientation information.
3.  **Immutability**: The `Volume` stores this table and data in a shared immutable snapshot. The `Builder` produces a new snapshot; it never modifies an existing `Volume`.

**Steps**
1.  **Build**: The `Volume::Builder` accepts cells by value. It deduplicates definitions and constructs the compact grid.
2.  **Snapshot Creation**: The `commit()` method (or equivalent builder finalization) initializes the `DeviceVolume` struct.
3.  **Texture Binding**: CUDA texture objects (`cudaTextureObject_t`) are created from the underlying GPU memory buffers associated with the volume data.
4.  **Metadata Population**: The `dim`, `voxel_size`, `origin`, `value_range`, and `density_scale` are copied from the `Volume::Description` into the `DeviceVolume` struct.
5.  **Device Transfer**: The `DeviceVolume` struct is copied to device memory (often via a staging buffer or direct mapping if supported) to be accessed by kernels [S2, unofficial].

**Edge Cases and Pitfalls**
*   **Dangling Pointers**: The public API must not expose `std::span<const Cell>` or raw pointers to the internal compact storage. Instead, use `cell(position)` which returns values or views. This prevents dangling pointers when the internal grid changes or is accessed concurrently [S1].
*   **Immutability**: Once a `Volume` is built, it must not be modified. Any changes require creating a new `Builder` and a new snapshot. Copying a `Volume` is lightweight because it shares the underlying immutable data [S1].
*   **Gradient Handling**: The `grad_tex` field can be 0. Kernels must check for this before sampling gradients [S2, unofficial].

## Operating characteristics
*   **Time Complexity**: Snapshot creation is $O(N)$ where $N$ is the number of unique cells, due to deduplication and grid construction. Texture object creation is $O(1)$ relative to volume size but involves GPU driver overhead.
*   **Memory Complexity**: The `DeviceVolume` struct itself is small (constant size). The bulk of memory is held by the underlying volume data and texture objects, which are shared.
*   **Performance**: Lightweight copying makes it suitable for passing to multiple kernels or frames without deep copying data [S1].
*   **Strengths**: Thread-safe, immutable, compact metadata, efficient GPU access via texture objects.
*   **Limitations**: Not suitable for frequent updates; updates require rebuilding the snapshot.

## Background
The concept of immutable volume snapshots with compact storage is described in the Sparkle Voxel Engine design specification (VXL-042) [S1]. The specific `DeviceVolume` struct and its usage in a CUDA rendering pipeline are documented in the cuVRender project [S2, unofficial].
