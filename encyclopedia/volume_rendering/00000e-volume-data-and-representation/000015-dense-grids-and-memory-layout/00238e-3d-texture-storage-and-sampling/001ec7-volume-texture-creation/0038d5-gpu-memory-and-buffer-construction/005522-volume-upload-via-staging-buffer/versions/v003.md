# Volume Upload via Staging Buffer

Also called: GPU Memory Transfer via Staging, Staging Buffer Upload

## Overview
This method transfers dense 3D volume data from host memory to GPU device-local memory using an intermediate staging buffer. It solves the problem of moving large, non-coherent host data into a format accessible by GPU shaders, ensuring alignment and format correctness. It is distinct from [Device Volume Snapshot](2246-device-volume-snapshot.md) (which captures existing GPU data) and [ClearView Unified Buffer Construction](2475-clearview-unified-buffer-construction.md) (which may use unified memory or direct mapping).

## How it works
**Inputs:** Host-side volume data (typically `std::span<const float>` or similar), volume dimensions (`dims`), and channel count (`kChannels`).
**Outputs:** A GPU 3D texture (image) ready for sampling.

**Data Structures:**
1.  **Volume Dimensions (`dims`):** Contains `nx`, `ny`, `nz`.
2.  **Staging Buffer:** Host-visible, host-coherent memory.
3.  **Device Image:** Device-local memory, optimal tiling.

**Steps:**
1.  **Validate Dimensions:** Check if `dims.nx`, `dims.ny`, or `dims.nz` exceed `limits.maxImageDimension3D`. If so, return `Errc::unsupported_configuration` [S1, unofficial].
2.  **Calculate Size:** Compute the byte size of the volume data:
    $$ \text{byteSize} = \text{dims.count()} \times kChannels \times \text{sizeof(float)} $$
    where `dims.count()` is $nx \times ny \times nz$ [S1, unofficial].
3.  **Allocate Staging Buffer:** Allocate host-visible, host-coherent memory of size `byteSize` with usage flag `eTransferSrc` and sharing mode `eExclusive` [S1, unofficial].
4.  **Populate Staging Buffer:** Map the staging memory. Create a `std::span<float>` of size `dims.count() * kChannels`. Call `deriveField<T>` to populate this span with the source field data, returning `autoRange` [S1, unofficial]. Unmap the memory.
5.  **Allocate Device Image:** Allocate device-local memory for a 3D image.
6.  **Create Image:** Create the 3D image with the following properties:
    *   Type: `e3D`
    *   Format: `kVolumeFormat` (must match source data type, e.g., `R32F`)
    *   Extent: `(dims.nx, dims.ny, dims.nz)`
    *   Mip Levels: 1
    *   Array Layers: 1
    *   Samples: `e1`
    *   Tiling: `eOptimal`
    *   Usage: `eSampled | eTransferDst | eTransferSrc`
    *   Initial Layout: `eUndefined` [S1, unofficial].
7.  **Copy Data:** Issue a memory copy command from the staging buffer to the device image. Transition the image layout from `eUndefined` to `eShaderReadOnlyOptimal` (or equivalent sampled layout) [S1, unofficial].
8.  **Create Image View:** Create a 3D image view with:
    *   View Type: `e3D`
    *   Format: `kVolumeFormat`
    *   Subresource Range: Aspect `eColor`, Base Mip Level 0, Level Count 1, Base Array Layer 0, Layer Count 1 [S1, unofficial].

**Pseudocode:**
```python
def upload_volume_via_staging(field_data: list[float], dims: Dimensions, k_channels: int):
    # 1. Validate dimensions
    if dims.nx > MAX_DIM or dims.ny > MAX_DIM or dims.nz > MAX_DIM:
        raise Error(Errc::unsupported_configuration)

    # 2. Calculate size
    total_voxels = dims.nx * dims.ny * dims.nz
    byte_size = total_voxels * k_channels * 4  # sizeof(float)

    # 3. Allocate staging buffer (host-visible, coherent)
    staging_mem = allocate_memory(size=byte_size, usage=USAGE_TRANSFER_SRC, host_visible=True)

    # 4. Populate staging buffer
    staging_span = map_memory(staging_mem)
    # deriveField populates the span with field data
    auto_range = derive_field(staging_span, field_data, dims, k_channels)
    unmap_memory(staging_mem)

    # 5 & 6. Allocate and create device image
    image = create_image(
        type=IMAGE_TYPE_3D,
        format=VOLUME_FORMAT,
        extent=(dims.nx, dims.ny, dims.nz),
        mip_levels=1,
        array_layers=1,
        samples=1,
        tiling=OPTIMAL,
        usage=USAGE_SAMPLED | USAGE_TRANSFER_DST | USAGE_TRANSFER_SRC,
        initial_layout=UNDEFINED
    )
    image_mem = allocate_memory_for_image(image, usage=USAGE_DEVICE_LOCAL)
    bind_memory(image, image_mem)

    # 7. Copy and transition
    copy_buffer_to_image(staging_mem, image, byte_size)
    transition_image_layout(image, from=UNDEFINED, to=SHADER_READ_ONLY_OPTIMAL)

    # 8. Create image view
    view = create_image_view(
        image=image,
        view_type=IMAGE_VIEW_TYPE_3D,
        format=VOLUME_FORMAT,
        subresource_range=SubresourceRange(
            aspect=COLOR,
            base_mip_level=0,
            level_count=1,
            base_array_layer=0,
            layer_count=1
        )
    )

    return VolumeTexture(image=image, view=view, range=auto_range)
```

**Edge Cases and Pitfalls:**
*   **Destruction Order:** Resources must be destroyed in reverse order of creation to avoid freeing memory bound to destroyed objects. The correct order is: `imageMem`, `image`, `view`, `stagingMem`, `staging` [S1, unofficial].
*   **Format Mismatch:** The GPU texture format must match the source data type and channel count to prevent corruption [S1, unofficial].

## Subtopics

### Volume Readback via Staging Buffer
This variant transfers data from GPU device memory back to host memory. It allocates a host-visible, host-coherent staging buffer with usage `eTransferDst` and size `byteSize` (calculated as `dims.count() * kChannels * sizeof(float)`). It copies the device image to the staging buffer, maps the staging memory, copies the bytes into a `std::vector<float>`, unmaps the memory, and returns a `VolumeReadback` struct containing dimensions and data [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of voxels, dominated by the memory copy operation.
*   **Memory Complexity:** $O(N)$ for the staging buffer in addition to the device texture.
*   **Performance:** Efficient for one-time uploads or infrequent updates. The staging buffer introduces an extra memory allocation and copy step compared to direct mapping, but ensures data integrity and compatibility with non-coherent host memory.
*   **Strengths:** Works with any host memory layout; ensures format and dimension validation; standard approach for Vulkan/DirectX.
*   **Limitations:** Requires explicit synchronization (fences/semaphores) to ensure the copy completes before the texture is sampled. Not suitable for real-time, per-frame updates of large volumes due to copy overhead.

## Background
This method is a standard technique in GPU programming, particularly in Vulkan and DirectX 12, where explicit memory management is required. It is used in the `imaginaryVolumes` library for uploading 3D field data to the GPU for ray marching [S1, unofficial].
