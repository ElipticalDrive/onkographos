# GPU Data Layout


## Overview
GPU Data Layout defines the host-side C++ structures and OpenGL resource bindings required to map volumetric scalar fields, transfer functions, and rendering targets to the GPU for raycasting. It solves the problem of organizing heterogeneous data (textures, framebuffers, metadata) into a cohesive state object that the GPU mapper can access efficiently. It differs from [Device Volume Snapshot](2246-device-volume-snapshot.md) by focusing on the active construction and binding of mutable resources rather than creating immutable thread-safe copies, and from [Volume Upload via Staging Buffer](15388-volume-upload-via-staging-buffer.md) by defining the final resource schema rather than the transfer mechanism.

## How it works
The method constructs a host-side state container that holds OpenGL object IDs and metadata arrays. This container is passed to the GPU mapper to bind resources to shader stages.

**Inputs and Outputs**
- **Input**: Volumetric scalar data (1-component or 4-component unsigned char), transfer function data (1D color/opacity tables), and rendering target dimensions.
- **Output**: A populated `TextureObjects` array and associated framebuffer/renderbuffer IDs ready for binding.

**Data Structures**
The core layout is defined by the following host-side structures:

1.  **TextureObjects**: An array of 5 `unsigned int` OpenGL texture IDs.
    -   Index 0: 3D scalar texture (volume data).
    -   Index 1: 1D color table texture.
    -   Index 2: 1D opacity table texture.
    -   Index 3: 2D grabbed depth buffer.
    -   Index 4: 2D color buffer.
2.  **MaxValueFrameBuffer** and **MaxValueFrameBuffer2**: Two `unsigned int` framebuffer IDs used for ping-pong accumulation in Multi-Image Projection (MIP) mode.
3.  **FrameBufferObject**: An `unsigned int` ID for the primary offscreen framebuffer object.
4.  **DepthRenderBufferObject**: An `unsigned int` ID for the depth renderbuffer attached to the primary framebuffer.
5.  **BoundingBox**: A `double` array of size `[8][3]` storing the world coordinates of the 8 corners of the dataset bounding box.
6.  **NoiseTexture**: A `float` array storing procedural noise data for speckle reduction.
7.  **NoiseTextureSize**: An `int` specifying the 1D dimension size of the noise texture.
8.  **NoiseTextureId**: An `unsigned int` OpenGL ID for the noise texture.
9.  **TextureCoord_1toN**: An array of `vtkTransform` pointers mapping texture coordinates from the primary volume to additional volumes.

**Validation and Constraints**
Before layout construction, the data must satisfy specific component and type constraints [S1, unofficial]:
1.  Only 1-component scalars or 4-component scalars with non-independent components are supported.
2.  If 4 components are present, the data type must be `VTK_UNSIGNED_CHAR` (RGBA).
3.  Additive blend mode is only supported with 1-component scalars.

**Pseudocode**
The following pseudocode demonstrates the validation and initialization of the layout structure.

```python
def initialize_gpu_data_layout(volume_data, blend_mode):
    """
    Validates input data and initializes the GPU data layout structure.
    
    Args:
        volume_data: Object with GetDataType() and GetNumberOfComponents()
        blend_mode: Integer constant for blend mode (e.g., ADDITIVE_BLEND)
        
    Returns:
        dict: The populated layout structure or None if validation fails.
    """
    num_components = volume_data.GetNumberOfComponents()
    data_type = volume_data.GetDataType()
    
    # Validation Step 1: Component and Type Check
    # Only 1-component or 4-component (unsigned char) are supported
    if num_components == 1:
        valid = True
    elif num_components == 4:
        if data_type != VTK_UNSIGNED_CHAR:
            raise ValueError("Only unsigned char is supported for 4-component scalars!")
            valid = False
        else:
            valid = True
    else:
        raise ValueError("Only one component scalars, or four component with non-independent components, are supported.")
        valid = False

    # Validation Step 2: Blend Mode Check
    if valid and blend_mode == ADDITIVE_BLEND:
        if num_components != 1:
            raise ValueError("Additive mode only works with 1-component scalars!")
            valid = False

    if not valid:
        return None

    # Layout Construction
    layout = {
        "TextureObjects": [0] * 5,  # [3D Scalar, 1D Color, 1D Opacity, 2D Depth, 2D Color]
        "MaxValueFrameBuffer": 0,
        "MaxValueFrameBuffer2": 0,
        "FrameBufferObject": 0,
        "DepthRenderBufferObject": 0,
        "BoundingBox": [[0.0, 0.0, 0.0] for _ in range(8)],
        "NoiseTexture": [],
        "NoiseTextureSize": 0,
        "NoiseTextureId": 0,
        "TextureCoord_1toN": []
    }
    
    # Note: Actual OpenGL object creation (glGenTextures, glGenFramebuffers) 
    # and data upload are performed by the renderer using these IDs.
    # The layout structure serves as the handle container.
    
    return layout
```

**Edge Cases and Pitfalls**
-   **Precision Loss**: Mapping host `float` data to `RGBA8` without proper normalization or using `R32F` when bandwidth is constrained can lead to visual artifacts or performance drops.
-   **Additive Mode Limitation**: Attempting to use additive blending with multi-component data will fail validation; the mapper must enforce single-component inputs for this mode.
-   **Bounding Box Accuracy**: The `BoundingBox` array must store precise world coordinates to ensure correct ray-volume intersection calculations.

## Subtopics

### [GPU Texture Loading](2473-gpu-texture-loading.md)
Transfers volumetric scalar data from host memory or binary files into GPU-accessible 3D textures. It differs from [Tiled 2D Texture Storage for 3D Fields](2740-tiled-2d-texture-storage-for-3d-fields.md) by using native 3D texture objects rather than packing 3D data into 2D tile arrays.

### [Tiled 2D Texture Storage for 3D Fields](2740-tiled-2d-texture-storage-for-3d-fields.md)
Stores a 3D scalar field in a 2D texture by tiling the volume into 2D slices. It is chosen when 3D texture support is inefficient or unavailable, mapping 3D coordinates to 2D UV space.

## Operating characteristics
-   **Memory Complexity**: Linear with respect to the number of textures and framebuffers. The layout itself is small (fixed-size array of IDs), but the resources it points to scale with volume resolution ($W \times H \times D$).
-   **Performance**: Binding efficiency depends on the GPU driver's handling of texture objects. Using a single array of IDs (`TextureObjects`) minimizes state change overhead during shader binding.
-   **Strengths**: Centralized management of all volume-related resources; explicit validation prevents runtime shader errors due to incompatible data types.
-   **Limitations**: Tightly coupled to OpenGL (via `unsigned int` IDs); not directly portable to Vulkan or DirectX without significant adaptation. Additive blending is restricted to scalar data.

## Background
The layout originates from the VTK (Visualization Toolkit) GPU volume rendering infrastructure, specifically the `vtkGPUMultiVolumeRayCastMapper` and related classes. It was developed to support multi-volume rendering and advanced blending modes (like MIP) by organizing OpenGL resources into a predictable host-side structure. The validation logic ensures compatibility with the underlying raycasting shaders, which expect specific component counts and data types.
