# PixelFlow Volume Rendering

Also called: PixelFlow Polygon Texturing, PixelFlow Volume Rendering Variant

## Overview
PixelFlow Volume Rendering is a polygon resampling method designed for the PixelFlow graphics system that overcomes the lighting and data size limitations of the RealityEngine by allowing pixel processors to manipulate texture values directly [S1, unofficial]. It differs from its siblings by computing lighting coefficients from interpolated data gradients in software on the pixel processors, rather than relying on precomputed shading coefficients or fixed light positions [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D volume dataset stored in texture memory; a set of object-space resampling polygons covering the volume.
*   **Output:** A composited image in the frame buffer.

**Data Structures:**
*   **Texture Memory:** Stores 32-bit values. Each 32-bit value is treated as four 8-bit components: three for the normalized data gradient ($\nabla V$) and one for the raw data value ($V$) [S1, unofficial].
*   **Pixel Processor State:** Each of the $128^2$ pixel processors holds an 8-bit ALU, hardware multiply, and hardware-assisted square root and divide instructions [S1, unofficial].

**Steps:**
1.  **Fetch:** Access eight arbitrarily-addressed 32-bit values in texture memory. The hardware does not perform operations on these values; they are loaded as ordinary data for user program manipulation [S1, unofficial].
2.  **Interpolate:** Perform trilinear interpolation of all four 8-bit components (three gradient, one raw data) concurrently on all $128^2$ pixel processors [S1, unofficial].
3.  **Normalize Gradient:** Normalize the interpolated gradient vector $\mathbf{g} = (g_x, g_y, g_z)$ [S1, unofficial].
4.  **Compute Lighting:** Compute Phong shaded lighting coefficients using the normalized gradient and fixed image-space light sources [S1, unofficial].
5.  **Classify:** Compute piecewise-linear transformations to translate the interpolated raw data value into color ($C$) and opacity ($\alpha$) [S1, unofficial].
6.  **Composite:** Multiply the color by the shading coefficient and composite the result into the frame buffer [S1, unofficial].

**Pseudocode:**
```python
# Executed concurrently on each of the 128^2 pixel processors
def process_pixel(polygon_id, pixel_coords):
    # 1. Fetch 8 arbitrarily-addressed 32-bit values from texture memory
    # The hardware provides raw access; no internal arithmetic is performed by the texture unit.
    texture_values = fetch_texture_values(polygon_id, pixel_coords)
    
    # 2. Interpret as four 8-bit components per value
    # Assuming texture_values contains the necessary neighbors for trilinear interpolation
    # Component layout: [grad_x, grad_y, grad_z, raw_data]
    interpolated_grad_x, interpolated_grad_y, interpolated_grad_z, interpolated_raw = \
        trilinear_interpolate_8bit_components(texture_values)
    
    # 3. Normalize the interpolated gradient
    gradient_magnitude = sqrt(interpolated_grad_x**2 + interpolated_grad_y**2 + interpolated_grad_z**2)
    if gradient_magnitude > 0:
        norm_grad_x = interpolated_grad_x / gradient_magnitude
        norm_grad_y = interpolated_grad_y / gradient_magnitude
        norm_grad_z = interpolated_grad_z / gradient_magnitude
    else:
        norm_grad_x, norm_grad_y, norm_grad_z = 0.0, 0.0, 0.0
        
    # 4. Compute Phong shaded lighting coefficients
    # Light direction and normal are derived from norm_grad and fixed image-space light positions
    lighting_coeff = compute_phong_shading(norm_grad_x, norm_grad_y, norm_grad_z)
    
    # 5. Compute piecewise-linear transformations for color and opacity
    color, opacity = piecewise_linear_transform(interpolated_raw)
    
    # 6. Composite into frame buffer
    final_color = color * lighting_coeff
    composite_into_framebuffer(final_color, opacity)
```

**Parameters:**
*   **Pixel Processors:** $128^2$ processors per card [S1, unofficial].
*   **Texture Access Time:** Under 500 µs for eight arbitrarily-addressed 32-bit values [S1, unofficial].
*   **Card Memory:** 0.5 million texture values per processor card [S1, unofficial].
*   **Typical Performance:** 43 processor cards, $256^3$ volume, 640x512 window, 400 resampling polygons, >10 frames/second [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Gradient Zero:** If the interpolated gradient magnitude is zero, normalization must handle division by zero (e.g., default to zero vector) [G].
*   **Precision:** Using 8-bit components for gradients may limit shading accuracy compared to floating-point representations [G].

## Operating characteristics
*   **Time Complexity:** Performance is inversely proportional to the number of screen pixels and resampling polygons used [S1, unofficial]. Doubling the number of resampling polygons halves the frame rate [S1, unofficial].
*   **Memory Complexity:** Scales with the number of processor cards. Each card holds 0.5M texture values, allowing system scalability by adding cards [S1, unofficial].
*   **Measured Performance:** A system with 43 processor cards renders a $256^3$ volume into a 640x512 window using 400 object-space resampling polygons at over 10 frames/second [S1, unofficial].
*   **Strengths:** Supports general lighting by sources fixed in image-space; scalable memory via multiple cards; high performance for large volumes [S1, unofficial].
*   **Limitations:** Requires specialized PixelFlow hardware; performance degrades with increased polygon count or resolution [S1, unofficial].
*   **When to Use:** When using PixelFlow hardware and requiring realistic lighting with large volume datasets [S1, unofficial].
*   **When Not to Use:** On standard graphics hardware without PixelFlow texturing capabilities [S1, unofficial].

## Background
The PixelFlow graphics system was under development at the University of North Carolina at Chapel Hill [S1, unofficial]. The method was proposed to overcome the limitations of the RealityEngine, specifically regarding realistic lighting and data size [S1, unofficial]. It leverages the PixelFlow texturing hardware, which allows pixel processors to access and manipulate texture values directly [S1, unofficial]. The approach was described in a technical report from UNC Chapel Hill in 1991 [S1, unofficial].
